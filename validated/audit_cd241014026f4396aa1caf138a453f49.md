### Title
Remote panic via forged `payload_len` in P2P push-message validators — ([File: stackslib/src/net/chat.rs])

### Summary
The `BondingCurvePool` bug is a class of vulnerability where a value the code implicitly trusts as *coupled* to another quantity (KAS balance vs. tokens actually sold) can be independently manipulated by an attacker via a side channel (self-destruct), breaking an assumed invariant and causing an unhandled failure downstream. The Stacks P2P layer has a directly analogous defect: `Preamble.payload_len` is trusted by several message-push validators to accurately describe the length of the deserialized payload, but the connection-buffering logic never enforces that equality — it only enforces `buffered_bytes.len() >= payload_len`. This decoupling lets a remote, unprivileged peer forge a small `payload_len` while still delivering a fully-parseable push message, driving a plain `assert!()` in `ConversationP2P::validate_transaction_push` / `validate_stackerdb_push` / `validate_nakamoto_block_push` / `validate_blocks_push` / `validate_microblocks_push` to fail and panic.

### Finding Description
Incoming P2P bytes are buffered and split into messages in `ConnectionInbox::consume_payload_known_length`: [1](#0-0) 

This routine only checks `buf_bytes.len() >= payload_len` before attempting to parse a message; the actual number of bytes consumed to build the `StacksMessageType` (`message_len`, returned by `protocol.read_payload`) is used to advance the buffer pointer, but is never checked for equality against `preamble.payload_len`. `payload_len` is a raw, sender-chosen `u32` field of the signed `Preamble` — the signature only proves the message came from that peer's key, not that `payload_len` accurately reflects the payload's true content length.

Several `ConversationP2P` "push" validators in `chat.rs` treat `preamble.payload_len` as if it were exactly the serialized payload length and use plain `assert!` to enforce a lower bound before subtracting a fixed header size for bandwidth accounting: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

Because `payload_len` is not required to equal the true parsed length of the message body, a peer can send a message whose body deserializes successfully into `StacksMessageType::Transactions`, `StackerDBPushChunk`, `NakamotoBlocks`, `Blocks`, or `Microblocks` while declaring a `payload_len` of `0` or `1` (or `≤5` for the blocks/microblocks variants). When such a message reaches the corresponding `validate_*_push` function, `assert!(preamble.payload_len > 1)` (or `> 5`) fails. Unlike `debug_assert!`, `assert!` panics in all build profiles, unwinding the thread that is processing the peer's messages.

This mirrors the reported bug's root cause exactly: an invariant relied upon by downstream logic (`kasCollected` bounded by tokens sold ⇔ here, `payload_len` bounded/equal to actual message size) is enforceable only under "normal" conditions, but a remote, unprivileged actor can break the coupling via a channel the validation logic doesn't account for (self-destruct-forced balance ⇔ here, independently-chosen wire length field), causing a hard failure in code that assumed the invariant always holds.

### Impact Explanation
A successful trigger panics the thread handling the malicious peer's inbound message processing. Given the P2P networking stack's connection/message dispatch is centrally driven (`stackslib/src/net/p2p.rs`/`chat.rs` conversation processing loop), an unhandled panic here can abort processing for the affected peer connection at minimum, and — depending on whether callers wrap conversation processing in `catch_unwind` (not confirmed in the reviewed code) — potentially crash the node process entirely. Either way this is an unauthenticated, remote, single-message DoS primitive reachable by any peer that can complete a standard P2P handshake, which places it at least at "Critical - remote crash/unauthenticated DoS from few messages" per the given severity rubric.

### Likelihood Explanation
Likelihood is high for reaching the panic: no special privileges, keys, or admin roles are needed — only a standard, unprivileged P2P handshake, after which the attacker fully controls the raw bytes of subsequent messages, including `Preamble.payload_len`, since it is a plain wire field not checked against the deserialized payload's actual size before dispatch. The only remaining uncertainty (noted honestly) is whether the surrounding conversation-processing code isolates panics per-connection (in which case impact is "drop this connection") or whether an unhandled panic propagates to crash the whole node process — I was not able to fully verify the panic-isolation boundary in the reviewed portions of `stackslib/src/net/p2p.rs` within the available time, so the exact blast radius (single connection vs. whole-node crash) remains unconfirmed.

### Recommendation
Enforce that `preamble.payload_len` is truly bound to the parsed message content rather than trusting it as an independent quantity:
- In `ConnectionInbox::consume_payload_known_length` (`stackslib/src/net/connection.rs`), require `message_len == payload_len` (or at least reject if `message_len < payload_len` combined with declared type-specific minimums), returning `net_error::InvalidMessage` on mismatch instead of silently accepting.
- In the `validate_*_push` functions in `stackslib/src/net/chat.rs`, replace the `assert!(preamble.payload_len > N)` calls with graceful error returns (e.g., `Err(net_error::InvalidMessage)` or a NACK), consistent with how other malformed-message conditions are already handled elsewhere in this file, so that a malformed/forged length cannot panic the process.

### Proof of Concept
1. As an unprivileged remote peer, complete a normal handshake with the target node.
2. Construct a valid P2P message body that deserializes as `StacksMessageType::Transactions(vec![])` (minimal valid encoding), `StackerDBPushChunk`, `NakamotoBlocks`, `Blocks`, or `Microblocks`.
3. Craft the `Preamble` for this message with `payload_len` set to `0` or `1` (or `≤5` for the Blocks/Microblocks variants), sign it with the attacker's own P2P key (this is a normal, unprivileged action).
4. Send the preamble followed by the actual (longer) payload bytes; because `consume_payload_known_length` only checks `buf_bytes.len() >= payload_len` (trivially true since `payload_len` is tiny) before calling `read_payload`, the full message is parsed successfully despite the mismatched declared length.
5. Once dispatched to `validate_transaction_push`/`validate_stackerdb_push`/`validate_nakamoto_block_push`/`validate_blocks_push`/`validate_microblocks_push`, the `assert!(preamble.payload_len > 1)` (or `> 5`) check fails and panics, since the message type matched but its declared `payload_len` is below the checked minimum.

    fn consume_payload_known_length(
        &mut self,
        protocol: &mut P,
        preamble: &P::Preamble,
    ) -> Result<Option<P::Message>, net_error> {
        let payload_len_opt = protocol.payload_len(preamble);
        let payload_len = payload_len_opt.expect("BUG: payload length assumed to be known");
        let buf_bytes = self.buf.get(self.message_ptr..).ok_or_else(|| {
            net_error::RecvError(format!("Message ptr {} overran buffer", self.message_ptr))
        })?;

        // reading a payload of known length
        if buf_bytes.len() >= payload_len {
            // definitely have enough data to form a message
            if let Some(ref pubk) = self.public_key {
                protocol.verify_payload_bytes(pubk, preamble, buf_bytes)?;
            }

            // consume the message
            let message_opt = match protocol.read_payload(preamble, buf_bytes) {
                Ok((message, message_len)) => {
                    test_debug!("Got message of {} bytes with {:?}", message_len, preamble);
                    let next_message_ptr = self.message_ptr.checked_add(message_len).ok_or(
                        net_error::OverflowError("Overflowed buffer pointer".to_string()),
                    )?;

                    // begin parsing at the end of this message
                    let data = self.buf.get(next_message_ptr..).ok_or_else(|| {
                        net_error::RecvError(format!(
                            "Next message ptr {next_message_ptr} overran buffer"
                        ))
                    })?;

                    self.message_ptr = 0;
                    self.payload_ptr = 0;
                    self.buf = data.to_vec();

            warn!("Drop pushed blocks -- invalid relayers {:?}", &relayers);
            self.stats.msgs_err += 1;

        }
