Based on my research, I found a genuine analog to the apoc `startsWith`-based partial path traversal in Bazel's ijar zip extraction code, not in the Starlark repository-rule helpers (which already do boundary-aware prefix checks).

### Title
Partial Path Prefix Check in ijar's Zip Extractor Allows Directory Traversal via Crafted Zip Archive - (File: third_party/ijar/zip_main.cc)

### Summary
`UnzipProcessor::Process` in ijar's zip extraction tool validates that an extracted entry stays inside `output_root_` using a raw byte-prefix `std::string::compare`, with no check that the matched prefix is followed by a path separator or string terminator. This is exactly the CWE-22 "partial path traversal" pattern from the apoc `startsWith` advisory (`/usr/out` matching `/usr/outnot`).

### Finding Description
The extraction containment check is: [1](#0-0) 

```
char path[PATH_MAX];
concat_path(path, sizeof(path), output_root_, output_file_name);
std::string normalized_root = normalize_path(output_root_);
std::string normalized = normalize_path(path);
if (normalized.compare(0, normalized_root.size(), normalized_root) != 0) {
  ... abort();
}
``` [2](#0-1) 

`output_file_name` comes directly from the zip entry name supplied by `Accept`/`Process`, which is driven by attacker-controlled archive content, since `ZipExtractor::Create` walks all entries of a caller-supplied zip file. `concat_path` joins `output_root_` and the (attacker-controlled) entry name with a `/`; the result is then string-normalized and compared to `normalized_root` using a plain byte-prefix `compare`. Because the comparison does not require that byte `normalized[normalized_root.size()]` be `/` (or end-of-string), any resolved path whose bytes merely start with the same characters as `normalized_root` — including a sibling directory such as `<output_root>-evil/...` or, when the entry contains an uplevel reference (`../sibling-dir/...`), a directory located outside `output_root_` entirely — passes the check and is written to disk via `make_dirs`/`write_file`. [3](#0-2) 

This mirrors the apoc `apoc.log.stream` bug precisely: a `startsWith`/`compare(0,...)`-style prefix test used as a containment boundary, without verifying the boundary is a full path-segment match.

### Impact Explanation
A malicious zip archive fed to ijar's unzip/extraction path (`extract()` in `zip_main.cc`) can cause files to be written outside the intended `output_root_` directory — e.g., into a sibling directory that happens to share the same string prefix, or (via an entry containing `..`) into an arbitrary directory reachable from the filesystem root supplied to the tool. This is a concrete write-outside-boundary primitive (CWE-22), matching the accepted-impact criteria (write outside the intended extraction root).

### Likelihood Explanation
Exploitation requires only that an attacker control the bytes of a zip archive consumed by this extractor (e.g., a hostile artifact/dependency archive), which matches the "unprivileged attacker who serves content a victim's build consumes" threat model. No credentials, sandbox escape, or local machine access are needed — only the ability to craft entry names in a zip file that is later extracted through this code path.

### Recommendation
Change the containment check to a boundary-aware comparison, e.g. require that `normalized.size() == normalized_root.size()` or `normalized[normalized_root.size()] == '/'` in addition to the prefix match (mirroring the correct pattern already used in `_starts_with` in `paths.bzl`, which checks `norm_a[len(norm_b)] == "/"`). [4](#0-3) 

### Proof of Concept
1. Build a zip archive whose entry name is set to escape the last path segment of the intended output root, e.g. an entry literally named `../<output_root_basename>-evil/payload`, where `<output_root_basename>` is the final path segment of `output_root_` (attacker can predict/observe this from the target directory name, e.g. `pkg` if `output_root_` is `/tmp/pkg`).
2. Run the ijar extractor (`extract()`/`UnzipProcessor`) against this archive with `exdir` pointing at `/tmp/pkg`.
3. `concat_path` produces `/tmp/pkg/../pkg-evil/payload`; `normalize_path` resolves it to `/tmp/pkg-evil/payload`.
4. `normalized.compare(0, normalized_root.size(), normalized_root)` compares only the first `strlen("/tmp/pkg")` bytes of `/tmp/pkg-evil/payload`, which are identical to `normalized_root` (`/tmp/pkg`), so the check passes and `payload` is written to `/tmp/pkg-evil/`, outside the intended `/tmp/pkg` extraction root.
5. A JUnit/shell-level reproduction should assert that after extraction, no file exists outside `output_root_`; this PoC demonstrates that assertion fails.

**Caveat / uncertainty:** I was not able to fully confirm, within this indexed snapshot, every production call site that feeds this `UnzipProcessor::Process`/`extract()` code path with attacker-controlled (non-test) zip content — e.g., whether it's wired into `http_archive`/`download_and_extract` (which appears to use a separate Java `DecompressorValue`/`ZipDecompressor` implementation not present in this index) versus only being exposed via the standalone ijar `unzip`/`zipper` command-line tool. This should be verified by tracing all Bazel build rules and internal tooling that invoke the compiled `unzip`/`zip_main` binary on externally-supplied archives before treating this as fully confirmed end-to-end. Given index size limits, some relevant Java source files (e.g., `StripPrefixedPath.java`, `ZipDecompressor.java`) were not available for cross-checking; a Devin session with full repository access would be needed to trace those call sites definitively.

// Concatene 2 path, path1 and path2, using / as a directory separator and
// putting the result in "out". "size" specify the size of the output buffer. If
// the result would overflow the output buffer, print an error message and
// return false.
bool concat_path(char *out, const size_t size, const char *path1,
                 const char *path2) {
  int len1 = strlen(path1);
  size_t l = len1;
  strncpy(out, path1, size - 1);
  out[size - 1] = 0;
  if (l < size - 1 && path1[len1] != '/' && path2[0] != '/') {
    out[l] = '/';
    l++;
    out[l] = 0;
  }
  if (l >= size - 1) {
    fprintf(stderr, "paths too long to concat: %s + %s", path1, path2);
    return false;
  }
  strncat(out, path2, size - 1 - l);
  return true;
}

def _starts_with(path_a, path_b):
    """Returns True if and only if path_b is an ancestor of path_a.

    Does not handle OS dependent case-insensitivty."""
    if not path_b:
        # all paths start with the empty string
        return True
    norm_a = _normalize(path_a)
    norm_b = _normalize(path_b)
    if len(norm_b) > len(norm_a):
        return False
    if not norm_a.startswith(norm_b):
        return False
    return len(norm_a) == len(norm_b) or norm_a[len(norm_b)] == "/"
