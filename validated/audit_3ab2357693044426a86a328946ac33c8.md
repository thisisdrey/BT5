## Title
Unbounded array allocation from attacker-controlled ABI length field in `BatchValidateSign` precompile causes OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` TVM precompiled contract (address `0x...09`, reachable via `STATICCALL`/`CALL` from any smart contract) decodes an ABI `address[]` argument through `extractBytes32Array`, which allocates a Java array sized directly from an attacker-controlled 32-byte length word taken from calldata, with no upper bound and no relation to the actual size of the supplied calldata buffer.

### Finding Description
`extractBytes32Array` reads the array length straight from a `DataWord` in the decoded calldata and immediately allocates a reference array of that size: [1](#0-0) 

This helper is invoked unconditionally in `BatchValidateSign.doExecute` to extract the `address[]` parameter: [2](#0-1) 

Note the size guard (`sigArraySize`/`addrArraySize > MAX_SIZE`) that would prevent this is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is active; when that governance-activated hard-fork flag is not enabled (fresh private/side chains, low-activity networks, or any deployment where this proposal has not been voted in), `extractBytes32Array` is reached with **no bound at all** on the decoded length. Unlike `extractBytesArray`, it also lacks the `offset > words.length - 1` sanity check present at line 400.

Because `getEnergyForData` computes energy purely from the physical `data.length` of the calldata buffer (not from the decoded length field), a caller can submit a very small calldata buffer whose embedded "array length" word is set to a huge value (e.g., `0x7FFFFFFF`), paying minimal energy while forcing the node to attempt an allocation of a multi-gigabyte array of references before the array is ever populated or validated: [3](#0-2) 

This is the same bug class as CVE-2026-14362: a length field taken from untrusted, remotely-supplied data drives an allocation with no upper bound, letting a single message/transaction exhaust the process's memory.

### Impact Explanation
A successful call triggers a JVM `OutOfMemoryError` while attempting to allocate the array. Even though `BatchValidateSign.execute` wraps `doExecute` in a `try/catch(Throwable)` that gracefully absorbs the error and returns a zero result, the underlying attempted allocation still stresses the shared JVM heap, can trigger GC thrashing across the whole node process, and in memory-constrained validator/full-node deployments can crash or hang the node — a node crash/halt caused by a single crafted, unprivileged transaction/contract call.

### Likelihood Explanation
Reachable by any account able to deploy a contract and issue a `CALL`/`STATICCALL` to precompile address `0x...09` (`batchValidateSign`) with crafted calldata — no special permission, stake, or witness/SR privilege required. The trigger condition depends on `allowTvmSelfdestructRestriction` not being active on the target network; on networks where this dynamic parameter proposal has not been (or cannot yet be) activated, the path is unconditionally exposed.

### Recommendation
Apply the `MAX_SIZE` (and an `offset` bounds check equivalent to `extractBytesArray`'s) unconditionally inside `extractBytes32Array` itself, rather than gating it behind the `allowTvmSelfdestructRestriction` feature flag, so the mitigation is not dependent on hard-fork activation status. Also enforce a sane length cap based on the actual remaining `words.length` before allocating, mirroring the guard already present in `extractBytesArray`/`extractSigArray`.

### Proof of Concept
1. Deploy a trivial contract that performs `STATICCALL` to precompile address `0x000...09` (`batchValidateSign`).
2. Construct calldata: 5 header words (`hash`, offset-to-sigs, offset-to-addrs, plus padding) followed by a minimal `sigs` array (length 0) and an `addrs` array whose length word is set to `0x7FFFFFFF`, with no actual address entries following.
3. Ensure `allowTvmSelfdestructRestriction` is not active (default/fresh chain state).
4. Submit the transaction; `extractBytes32Array` executes `new byte[0x7FFFFFFF][]`, attempting a multi-gigabyte allocation and triggering `OutOfMemoryError` on the processing node.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }
