## Analysis

The external report's core broken invariant: **a payout function computes an "owed" amount from an internal accounting formula that is decoupled from the actual on-chain balance held in the payer contract**, causing legitimate claimants to be permanently unable to collect (transfer reverts on insufficient balance).

The closest local analog is `pallet-asset-rewards` (`substrate/frame/asset-rewards/src/lib.rs`), which implements a StakingRewards-style pool. Its `reward_per_token` accrual is computed purely from `reward_rate_per_block * elapsed_blocks / total_tokens_staked` [1](#0-0) , with **no coupling whatsoever to the actual reward-asset balance held in `pool_info.account`**. Contrast this with the sibling `pallet-nomination-pools`, whose `RewardPool::current_reward_counter` explicitly bounds accrual by `Self::current_balance(id)` (the pot's real balance) [2](#0-1)  — precisely the fix the VeTokenMinter report recommends. `pallet-asset-rewards` lacks this safeguard.

`create_pool` requires no upfront funding of the reward asset [3](#0-2) , and reward deposits are a separate, optional, permissionless call `deposit_reward_tokens` [4](#0-3) . Meanwhile `harvest_rewards` transfers `staker_info.rewards` — a value computed entirely from the unbacked rate-accrual formula — straight out of `pool_info.account` [5](#0-4) . If the actual asset balance in `pool_info.account` is less than the accrued (virtual) `staker_info.rewards` — which happens naturally whenever deposits lag behind the promised `reward_rate_per_block`, or whenever an earlier staker's `harvest_rewards` drains the account first — the `T::Assets::transfer` call reverts with insufficient balance, and the whole extrinsic fails. There is no `adjust_pool_deposit`-style recovery as in nomination-pools; the staker's accrued claim is stuck until an unrelated third party tops up the pool via `deposit_reward_tokens`.

### Title
Reward accrual decoupled from actual pool balance causes permanent harvest failure / first-claimant drain in `pallet-asset-rewards` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` tracks staker rewards via a pure rate-based accumulator (`reward_per_token_stored`) that never checks the pool account's real reward-asset balance. Any unfunded or underfunded pool lets accrued "virtual" rewards exceed the account's real balance, so `harvest_rewards` permanently reverts for stakers who try to claim after the real balance is exhausted, and/or allows the fastest staker to drain the pot at the expense of others who accrued in parallel.

### Finding Description
`reward_per_token` is computed solely as a function of elapsed blocks, `reward_rate_per_block`, and `total_tokens_staked` [1](#0-0) . It is never clamped to, or reconciled with, `Assets::balance(reward_asset_id, &pool_info.account)`. `create_pool` does not require the creator to pre-fund the pool with any reward tokens [3](#0-2) ; funding happens only via the separate, unenforced `deposit_reward_tokens` call. `harvest_rewards` then attempts to move the full virtually-accrued `staker_info.rewards` out of the pool account [6](#0-5) . Because nothing ties the accrual rate to the real balance, multiple concurrent stakers can each accrue claims against the same pot; whichever staker calls `harvest_rewards` first is paid in full, and stakers who call afterward find the pool underfunded relative to their own (equally legitimate, per the ledger) accrued balance, and their `harvest_rewards` call reverts with an `Assets` insufficient-balance error. Unlike `pallet-nomination-pools`, which explicitly computes `current_reward_counter` from `current_balance(id)` [2](#0-1)  so the counter can never promise more than what is truly in the pot, `pallet-asset-rewards` has no analogous cap, and no `adjust_pool_deposit`-style repair mechanism.

### Impact Explanation
Stakers with a legitimately-computed reward balance can be permanently blocked from calling `harvest_rewards` for their own funds (fund lock), and the outcome is order-dependent: the first caller to harvest effectively receives real tokens funded partly by/for other stakers, while later callers are denied — a form of duplicate/unfair settlement over a single shared pot. This matches the "permanent user-fund lock" and "public underpriced/unbacked payout" impact categories, all triggerable by ordinary unprivileged stakers/pool creators, with no admin or governance action required as the root cause.

### Likelihood Explanation
Likelihood is high in realistic usage: `create_pool` never validates that the pool is (or will be) sufficiently funded relative to `reward_rate_per_block` and pool duration, and `deposit_reward_tokens` is a fully separate, unenforced, permissionless call. Any pool that is underfunded relative to its rate, or that has multiple stakers racing to harvest before the next `deposit_reward_tokens` lands, will hit this condition without any special privilege or malicious insider.

### Recommendation
Bound `reward_per_token`/harvestable rewards by the pool account's actual reducible balance of the reward asset at the time of accrual/harvest (mirroring `pallet-nomination-pools`'s `current_balance`-based `current_reward_counter`), or require `create_pool`/`set_pool_reward_rate_per_block` to atomically fund (or escrow) enough reward tokens to cover the promised rate through `expiry_block` before increasing the rate, and provide a permissionless top-up/reconciliation extrinsic analogous to `adjust_pool_deposit` so any deficit can be corrected without abandoning stuck claims.

### Proof of Concept
1. Pool admin calls `create_pool` with `reward_rate_per_block = R` and no reward-asset funding (call to `deposit_reward_tokens` skipped or minimal) [3](#0-2) .
2. Staker A and Staker B both `stake` in the same block, splitting `total_tokens_staked` evenly.
3. Time passes; `reward_per_token` accrues for both based purely on `R * elapsed / total_tokens_staked`, regardless of whether any reward tokens were ever deposited [7](#0-6) .
4. Suppose only a small deposit `D < (accrued_A + accrued_B)` was made via `deposit_reward_tokens`.
5. Staker A calls `harvest_rewards` first and successfully drains up to `D` from `pool_info.account` [6](#0-5) .
6. Staker B calls `harvest_rewards`; `T::Assets::transfer` reverts (insufficient balance), and Staker B's accrued rewards remain permanently unpayable until a third party deposits more reward tokens — which may never happen.

		pub fn harvest_rewards(
			origin: OriginFor<T>,
			pool_id: PoolId,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool and staker rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info =
				PoolStakers::<T>::get(pool_id, &staker).ok_or(Error::<T>::NonExistentStaker)?;
			let (pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Transfer unclaimed rewards from the pool to the staker.
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&staker,
				staker_info.rewards,
				// Could kill the account, but only if the pool was already almost empty.
				Preservation::Expendable,
			)?;

			// Emit event.
			Self::deposit_event(Event::RewardsHarvested {
				caller,
				staker: staker.clone(),
				pool_id,
				amount: staker_info.rewards,
			});

			// Reset staker rewards.
			staker_info.rewards = 0u32.into();

			if staker_info.amount.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
