## Title
Unbounded token minting via repeated `one_yocto_on_promise` subsidy on a zero-balance account - (File: `runtime/near-vm-runner/src/logic/logic.rs`)

### Summary
`promise_batch_action_function_call_weight` and `promise_yield_create_with_id` contain a "1 yoctoNEAR on zero balance" exemption intended to let zero-balance accounts (ZBAs, NEP-448) attach exactly one yoctoNEAR to a promise once, without failing for lack of balance. The exemption fires whenever `current_account_balance.is_zero()` at the moment of the call, with no per-receipt cap and no actual deduction. Because it never mutates `current_account_balance` (it just adds to `subsidized_amount` instead of calling `deduct_balance`), balance remains zero across repeated invocations within the same function-call execution, so the contract can invoke this host function many times, each one minting exactly 1 yoctoNEAR of new token supply that is later subtracted from `total_balance_burnt`, i.e., created from nothing.

### Finding Description
The relevant logic: [1](#0-0) 

```
// Allow attaching exactly 1 yoctoNEAR to a promise function call
// when the contract has zero balance. ...
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self
        .result_state
        .subsidized_amount
        .checked_add(amount)
        .expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
```

The same pattern is duplicated in `promise_yield_create_with_id` [2](#0-1)  and in the wasmtime backend [3](#0-2) , [4](#0-3) .

Crucially, the guard is only `current_account_balance.is_zero()` — a state, not a one-shot flag or counter. Since the "skip" branch never calls `deduct_balance`, the balance stays at zero after each exempted call. A single WASM function execution can call `promise_batch_action_function_call_weight` (or `promise_yield_create_with_id`) in a loop, attaching 1 yoctoNEAR each time to distinct outgoing promises, and every call qualifies for the exemption because `current_account_balance` never changes. Each exempted call increments `ExecutionResultState::subsidized_amount` [5](#0-4)  unboundedly (limited only by attached gas, which the caller pays for separately in gas fees, not in NEAR principal).

This `subsidized_amount` is explicitly documented as newly minted supply and is subtracted from `total_balance_burnt` for the chunk: [6](#0-5) [7](#0-6) 

```
// Theoretically this may become negative but the subsidized amount is many orders
// of magnitude lower than the burned amount for each promise, so it should not happen.
let total_balance_burnt =
    burnt.checked_sub(apply_result.stats.balance.subsidized_amount).ok_or_else(...)?;
```

The comment explicitly assumes the subsidy is "many orders of magnitude lower than the burned amount for each promise" — i.e., the protocol design assumes at most one subsidized yoctoNEAR per promise/receipt, not an attacker-controlled unbounded count of subsidized promises inside a single receipt. Each of the resulting outgoing promise-batch actions carries a real 1 yoctoNEAR deposit that is credited to receiver accounts as part of a `FunctionCall`/`PromiseYield` action — meaning the minted yoctoNEAR is not merely an accounting artifact, but is actually transferred to arbitrary receiver accounts as attached deposit, backed by nothing.

This is the direct analog of the audited bug: a value that is supposed to represent an exceptional/degenerate one-time state (debt-free ⇒ ratio 0; zero-balance ⇒ one-time subsidy allowance) is treated by a re-entrant/repeatable check as a persistently valid bypass condition, because the check does not distinguish "first time reaching zero" from "still zero because we keep skipping the debit."

### Impact Explanation
This allows **token inflation**: an attacker-controlled zero-balance account (trivially created via NEP-616 deterministic accounts or NEP-448 zero-balance accounts, i.e., completely permissionless, unprivileged flows) can mint an amount of yoctoNEAR bounded only by how many `promise_batch_action_function_call_weight`/`promise_yield_create_with_id` calls fit in one receipt's gas budget (hundreds of millions of such host calls are plausible within the max gas per receipt), each minting 1 yoctoNEAR that becomes real, spendable deposit balance on receiver accounts. Repeated across receipts/transactions this is an unbounded inflation vector that corrupts the protocol's total-supply invariant (`new_total_supply = prev + minted - burnt`), directly violating the documented invariant that `subsidized_amount` should be negligible relative to burnt amount per promise.

### Likelihood Explanation
High: this is reachable from an ordinary, unprivileged NEAR account with a zero-balance/deterministic account and a deployed contract issuing a WASM loop of promise batch actions — no special permission or validator status is required. The only cost to the attacker is gas, which is far smaller than the value of minted NEAR at scale.

### Recommendation
Cap the `one_yocto_on_promise` exemption to at most once per receipt (e.g., track a boolean "already subsidized this execution" in `ExecutionResultState` instead of relying on `current_account_balance.is_zero()`, which is not consumed by the skip branch), or subtract the subsidized amount from `current_account_balance` in a way that prevents it from staying at zero for subsequent calls within the same execution.

### Proof of Concept
1. Create a deterministic/zero-balance account and deploy the reference test contract's `call_promise` handler (as used in `create_with_id_one_yocto_exemption_on_drained_zba` [8](#0-7) ).
2. Instead of a single `yield_create_with_id`/`promise_batch_action_function_call_weight` op attaching 1 yoctoNEAR, submit a batch of, e.g., `N = 1_000_000` such ops in one function call (well within `max_total_prepaid_gas`/`max_actions_per_receipt`, since each op's cost is only the small `function_call_base`/`function_call_byte` gas fee), each attaching exactly 1 yoctoNEAR to a distinct outgoing promise/receiver.
3. Because `current_account_balance` remains `Balance::ZERO` throughout (the skip branch never calls `deduct_balance`), every one of the `N` calls satisfies `skip_deduct` and each adds 1 yoctoNEAR to `subsidized_amount`.
4. Confirm (as the existing test does) that `apply_result.stats.balance.subsidized_amount` grows by `N` yoctoNEAR instead of the intended maximum of 1, and that this reduces `total_balance_burnt` and therefore increases `new_total_supply` by `N` yoctoNEAR of real, unbacked deposit delivered to the receiver accounts.

#[test]
fn create_with_id_one_yocto_exemption_on_drained_zba() {
    use testlib::runtime_utils::alice_account;
    let (node, zba_id) = setup_zba_global_contract();
    let alice_id = alice_account();
    let balance_before = node.user().view_account(&zba_id).unwrap().amount;
    let subsidized_before = node.client.read().cumulative_subsidized;

    // Sign as alice (not zba) so that the gas reservation comes out of alice's
    // balance — keeping zba's balance untouched until the wasm runs. The gas
    // reward still goes to the receiver (zba).
    let args = drain_then_yield_args(&alice_id, balance_before, &[20u8; 32], &[6u8; 16], 1);
    let args_len = args.len() as u64;
    let res = node
        .user()
        .function_call(alice_id, zba_id.clone(), "call_promise", args, MAX_GAS, Balance::ZERO)
        .unwrap();

    assert_eq!(
        res.status,
        FinalExecutionStatus::SuccessValue(vec![]),
        "drain + 1-yocto via the exemption should succeed on a ZBA; got {res:?}",
    );

    // The exemption fires exactly once — confirm the runtime tracked it.
    let subsidized_after = node.client.read().cumulative_subsidized;
    let subsidy = subsidized_after.checked_sub(subsidized_before).unwrap();
    assert_eq!(
        subsidy,
        Balance::from_yoctonear(1),
        "expected exactly 1 yoctoNEAR of subsidy (the exemption), got {} yoctoNEAR",
        subsidy.as_yoctonear(),
    );

    // The wasm drains the entire account_balance, then the 1-yocto deduction is
    // skipped via the exemption — leaving VMLogic balance at 0. The runtime
    // sets account.amount = 0, the ZBA check lets that stand, and finally the
    // receiver gas reward is credited on top, so balance_after = reward exactly.
    let reward = contract_function_call_reward(&fee_helper(&node), &res, "call_promise", args_len);
    let view = node.user().view_account(&zba_id).unwrap();
    assert_eq!(
        view.amount, reward,
        "expected zba balance to equal exactly the gas reward (drained + subsidized + reward)",
    );
    assert!(
        view.storage_usage <= 770,
        "zba should still qualify as a ZBA after the call: storage_usage = {}",
        view.storage_usage,
    );
}
