Based on the confirmed code path, this vulnerability does not exist. The mechanism the question describes is exactly what the existing code prevents through two independent layers.

### Title
No vulnerability found — RecordedStorageExceeded correctly discards all pending promises

### Summary
The scenario described (promises created before a failing host call being flushed to outgoing receipts despite the failing action) is not reachable. `ReceiptManager` is a local, per-`FunctionCall`-action buffer that is only drained into the receipt's `new_receipts` when the VM run succeeds, and any receipt-level failure separately clears `new_receipts` before receipts are ever handed to the `ReceiptSink`.

### Finding Description
`action_function_call` creates a fresh `ReceiptManager` per `FunctionCall` action invocation and passes it into `RuntimeExt`, which the VM's `create_action_receipt`/`promise_*` host calls populate as the contract calls `promise_batch_create`/`promise_batch_action_*` [1](#0-0) . If a later host call in the same `FunctionCall` (e.g. `storage_read`) triggers `RecordedStorageCounter::observe_size`, it returns `HostError::RecordedStorageExceeded`, which propagates up through the VM run as `VMOutcome.aborted = Some(FunctionCallError::HostError(RecordedStorageExceeded))` [2](#0-1) [3](#0-2) .

Back in `action_function_call`, `execution_succeeded` is computed as `outcome.aborted.is_none()` [4](#0-3) , and the block that converts `receipt_manager.action_receipts`/`data_receipts` into `Receipt`s and appends them to `result.new_receipts` is gated entirely by `if execution_succeeded` [5](#0-4) . Since the abort makes `execution_succeeded == false`, the promises recorded in the local `ReceiptManager` are simply dropped and never reach `result.new_receipts` — they never even reach the receipt-level `ActionReceiptResult`, let alone the `ReceiptSink`.

As a second, independent safety net, even if a receipt contained multiple actions and an earlier action's promises had already been merged into the receipt-level accumulator, `ActionReceiptResult::merge` calls `set_error` on any action error, which explicitly clears `new_receipts`, `validator_proposals`, `tokens_burnt`, and `subsidized_amount` [6](#0-5) . Receipts are only turned into outgoing receipts and handed to `ReceiptSink::forward_or_buffer_receipt` after the full action loop completes and `result.result.is_ok()` is checked [7](#0-6) ; a failed `FunctionCall` (or any action) leaves `new_receipts` empty by the time this code runs.

So there is no window in which promises created before the `RecordedStorageExceeded`-triggering host call are "already added to receipt_manager" in a way that survives the failure — the `ReceiptManager` contents are receipt-manager-local and discarded on abort, matching the documented all-or-nothing action invariant [8](#0-7) .

### Impact Explanation
None. No outgoing receipt, and therefore no balance deduction or theft/freezing of funds, can result from promises queued before a `RecordedStorageExceeded` abort in the same `FunctionCall` action.

### Likelihood Explanation
Not applicable — the described precondition (promises surviving into `outgoing_receipts` after the triggering action fails) cannot occur given the `execution_succeeded` gate and `set_error`/`merge` discard logic.

### Recommendation
No fix needed. If desired for regression protection, `runtime/runtime/src/tests/apply.rs` already contains adjacent tests (`test_add_keys_after_large_read_exceed_receipt_storage_proof_limit`, storage-proof-exceeded tests) that assert on `ActionErrorKind::ReceiptStorageProofSizeExceeded`/`RecordedStorageExceeded`; an additional assertion that `apply_result.outgoing_receipts` is empty after such a failure would make the existing invariant explicit, but this is a test-hardening suggestion, not a bug fix.

### Proof of Concept
Not applicable (no bug to reproduce). A confirmatory test would: create a `FunctionCall` action whose contract first issues several `promise_batch_create`/`promise_batch_action_*` calls, then performs `storage_read`/`storage_write` calls large enough to exceed `per_receipt_storage_proof_size_limit`; apply the receipt via `runtime.apply(...)`; assert the outcome status is `Failure(... RecordedStorageExceeded ...)` and assert `apply_result.outgoing_receipts.is_empty()` — this is expected to already pass given the code above.
