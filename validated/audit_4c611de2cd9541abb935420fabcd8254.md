### Title
Cross-StackerDB Signature Replay via Missing Domain Separation in `SlotMetadata::auth_digest()` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` binds a signer's signature only to `(slot_id, slot_version, data_hash)`. It never includes the target StackerDB's identity (`smart_contract_id`/`stackerdb_id`) or any network/epoch discriminator. Because the `.signers` boot contracts deploy *many* separate StackerDB instances (`signers-{0|1}-{message_id}`) that share an identical slot→signer assignment within a signer set, a chunk validly signed for one StackerDB is also a valid signature for the same slot in every other sibling StackerDB. Neither the chunk-store path (`StackerDBs::try_replace_chunk`) nor the peer-validation path (`PeerNetwork::validate_received_chunk`) re-binds the signature to the specific contract being written to, so a replayed chunk is accepted as authentic in a context the signer never signed for. This is the same bug class as the report's "missing chain ID" issue: the signed digest fails to include the domain (here, the specific StackerDB contract) that the verifier is implicitly trusting.

### Finding Description
`SlotMetadata::auth_digest()` computes: [1](#0-0) 

only over `slot_id`, `slot_version`, and `data_hash`. `verify()` recovers the pubkey from this digest and compares its hash to the expected `StacksAddress`, explicitly noting the address *version* is ignored as well: [2](#0-1) 

The Stacks signer subsystem deploys one StackerDB contract per `(signer-set, message-type)` pair, e.g. `signers-0-2`, `signers-0-5`, `signers-1-3`, generated via: [3](#0-2) 

Crucially, the slot ordering (signer → slot_id mapping) is identical across all `message_id` contracts of the same signer set, as directly demonstrated by the test that checks the same `expected_stackerdb_slots` list for every `message_id` value: [4](#0-3) 

When a chunk is received (either pushed unsolicited over p2p or via the HTTP write endpoint), the verification never checks that the signature was produced for *this* contract — it only looks up the expected signer address for `(smart_contract_id, slot_id)` and calls `SlotMetadata::verify`, which is contract-agnostic: [5](#0-4) 

The same pattern is used by the local storage path `StackerDBTx::try_replace_chunk` (backed by `inner_get_slot_validation`, which is also purely keyed by `stackerdb_id`/`slot_id`, not by anything present in the signed bytes): [6](#0-5) 

Because the digest contains no contract/domain separator, a signature `sig` over `(slot_id=K, slot_version=V, data_hash=H)` produced (and legitimately broadcast) for contract A (e.g. `signers-0-2`, a `BlockResponse` DB) is simultaneously a valid signature for the identical `(K, V, H)` triple in sibling contract B (e.g. `signers-0-5`, a `MockSignature` DB), as long as the same signer occupies slot `K` in both — which is guaranteed by design within a signer set. An attacker who observes any legitimately signed chunk (chunks are gossiped and are also retrievable via the public HTTP `GET .../chunks` endpoint) can resubmit the exact same `(slot_id, slot_version, sig, data)` tuple to a different sibling StackerDB contract and have it accepted as authentic there, since:
- `get_slot_signer(contract_B, K)` returns the same address as in contract A,
- `slot_metadata.verify(&addr)` succeeds (digest is contract-agnostic),
- the target contract's independent version counter can easily be lower than `V`, satisfying the freshness check.

### Impact Explanation
This breaks the equality "signed for context X" vs "accepted in context Y": StackerDB writes are supposed to be authenticated per-database, but the signature does not actually commit to the database identity. An unauthenticated network participant can:
- Inject data that a signer authored for one message type/DB into a different sibling DB (cross-message-type replay), corrupting the state read by consumers such as `StackerDBListener`/`GlobalStateEvaluator` that deserialize chunk bytes as a specific `SignerMessageV0` variant.
- Propagate this forged/mis-attributed write across the network, since receiving peers apply the identical broken verification via `handle_unsolicited_StackerDBPushChunk`/`validate_received_chunk`.

This matches the "Critical: unauthenticated/unauthorized write to state or StackerDB; network-wide propagation of forged data" category, since no signer's private key is needed — only a previously-observed, legitimately-signed chunk from any signer, replayed to a sibling database.

### Likelihood Explanation
Chunks are routinely broadcast over the p2p network (`StackerDBPushChunkData`) and are also readable from any node's public HTTP API. The attacker only needs to capture one validly-signed chunk and repost it, unmodified, against a different `smart_contract_id` for which the same signer occupies the same `slot_id` — a condition guaranteed by construction for all `signers-{set}-*` contracts in the same signer set. No node secret, admin role, or other party's private key is required, making this reachable by any remote, unprivileged network participant.

### Recommendation
Include the target StackerDB's domain in the signed digest, analogous to including a chain ID in EIP-712 hashing. Concretely, extend `SlotMetadata::auth_digest()` (and correspondingly `sign()`/`verify()`) to also hash the `smart_contract_id` (and ideally the network/chain id) so a signature is only valid for the exact StackerDB it was produced for: [1](#0-0) 
This requires a coordinated protocol/version change since it alters what signers hash, and all verifying call sites (`validate_received_chunk`, `try_replace_chunk`/`inner_get_slot_validation`) must pass the contract id into verification.

### Proof of Concept
1. Signer `S` legitimately produces and signs `StackerDBChunkData { slot_id: K, slot_version: V, sig, data }` for contract `signers-0-2` (e.g. a `BlockResponse` message); the chunk is broadcast/observed on the network or fetched via the node's HTTP chunk-read endpoint.
2. Attacker determines (from `signers.clar`/`stackerdb-get-signer-slots-page`) that `signers-0-5` (e.g. `MockSignature`) uses the identical signer→slot ordering for signer set 0, so slot `K` is also owned by `S` there.
3. Attacker POSTs the *same, unmodified* `StackerDBChunkData` bytes to `signers-0-5`'s write endpoint (or relays it as an unsolicited `StackerDBPushChunkData` with `contract_id = signers-0-5`).
4. `validate_received_chunk`/`try_replace_chunk` looks up the slot-5-signer for `signers-0-5` (= `S`), calls `SlotMetadata::verify(&S)`, which succeeds because the digest never referenced `signers-0-2`; if `V` exceeds `signers-0-5`'s current slot version, the write is accepted and gossiped as authentic `MockSignature` data from `S`, even though `S` never signed anything for that contract.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
