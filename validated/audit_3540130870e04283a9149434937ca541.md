## Title
Unsynchronized shared static `LRUMap` in `Program.getProgramPrecompile()` causes concurrent structural corruption / node crash under ordinary smart-contract transaction load - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

## Summary
The CVE describes `NSSToken` objects referenced through raw/direct pointers being accessed unsafely from multiple threads, causing a use-after-free/corruption crash. The structural analog in java-tron is `Program`'s static, non-thread-safe `LRUMap` cache (`programPrecompileLRUMap`), which is read and mutated by every TVM execution thread without any synchronization, even though many independent transactions (from different peers/threads) execute concurrently through it.

## Finding Description
`Program` declares a process-wide static cache used to avoid recomputing JUMPDEST analysis for contract bytecode: [1](#0-0) 

`getProgramPrecompile()` performs a classic unsynchronized check-then-act on this shared, mutable map from whatever thread is executing the contract call: [2](#0-1) 

`LRUMap` (an ordered/linked map implementation, imported via `import ... LRUMap;` in this file) is **not** thread-safe: `get()` and `put()` both mutate its internal doubly-linked access-order list to track recency, so concurrent, unsynchronized `containsKey()`/`get()`/`put()` calls from different threads can corrupt that internal linked structure (dangling/cyclic links) — the same class of bug as the CVE's "objects referenced via direct pointers ... accessed in an unsafe way on different threads."

This cache is reachable from ordinary, unprivileged transaction processing:
- `TransactionsMsgHandler` dispatches every non-smart-contract... actually every *smart contract* transaction (`TriggerSmartContract`/`CreateSmartContract`) received from peers to a multi-threaded pool (`trxHandlePool`, size `threadNum = Args.getInstance().getValidateSignThreadNum()`), each of which independently executes the transaction (and thus `VMActuator`/`Program`): [3](#0-2) [4](#0-3) 

- Local API/JSON-RPC/gRPC calls (`triggersmartcontract`, `triggerconstantcontract`, `eth_call`, etc.) also invoke `VMActuator` concurrently on a pooled RPC executor, e.g. `Wallet.callConstantContract`: [5](#0-4) 

Because `getProgramPrecompile()` is invoked on every non-constant-call TVM execution (`isConstantCall` false branch), and the pool sizes above are >1 by default, multiple threads can race on `programPrecompileLRUMap.containsKey/get/put` for the same or different keys at effectively the same moment with no `synchronized`, lock, or use of a concurrent map wrapper.

## Impact Explanation
`LRUMap`'s internal linked-list bookkeeping is not safe for concurrent mutation. Concurrent unsynchronized access can:
- Corrupt the map's internal linked structure, leading to infinite loops, `NullPointerException`, `ArrayIndexOutOfBoundsException`, or other unchecked exceptions during ordinary contract execution — a node-crash/DoS reachable by any account broadcasting `TriggerSmartContract`/`CreateSmartContract` transactions or by API callers hitting `triggerconstantcontract`/`triggersmartcontract`.
- In a milder failure mode, a corrupted eviction order could cause an entry to be silently dropped/overwritten so a different (stale/wrong) `ProgramPrecompile` object is associated with a JUMPDEST-analysis cache key, potentially returning incorrect JUMPDEST validity information for a contract and diverging execution results for that contract call versus what a race-free node would compute. Because this cache is shared across ALL contract executions running on the node (not scoped per-transaction), a corrupted cache entry can affect completely unrelated subsequent transactions/contracts, which is difficult to reproduce deterministically and could contribute to non-deterministic block validation results across nodes (chain-split risk) if it affects consensus-critical bytecode analysis in the `contains/get/put` window during otherwise-normal parallel transaction processing.

This satisfies the "node crash or halt" / potential "chain split" impact bar required by the validation rules, and is reachable purely by an unprivileged transaction broadcaster or API caller — no malicious SR/witness/peer role is required.

## Likelihood Explanation
The trigger condition is simply "more than one thread executing TVM contract calls concurrently while the LRU cache is warm," which is the normal steady-state of a fullnode processing peer-broadcast smart-contract transactions (`validateSignThreadNum`/`threadNum` > 1 by default) or serving concurrent RPC/API `triggerconstantcontract` calls. No special crafting of the transaction contents is required beyond simply invoking a smart contract, so likelihood of hitting a race window under moderate transaction throughput is realistic, though the exact failure (exception vs. silent wrong cache read) is non-deterministic and timing-dependent, making this harder to reliably trigger on demand than to occur under sustained load.

## Recommendation
Replace `programPrecompileLRUMap` with a thread-safe bounded cache (e.g., Guava `Cache`/`LoadingCache` as already used elsewhere in the codebase — see `AdvService`'s `CacheBuilder`-based caches, or wrap accesses in a lock/`Collections.synchronizedMap`). Ensure the check-then-act sequence in `getProgramPrecompile()` is atomic (e.g., via `computeIfAbsent` on a concurrent-safe map) so no two threads can race on `containsKey`/`get`/`put` for the shared static cache.

## Proof of Concept
Not independently reproducible as a standalone PoC without running the full node under concurrent transaction load; the race depends on JVM thread scheduling. The mechanism can be demonstrated conceptually:
1. Configure `validateSignThreadNum` (or `threadNum`) > 1 (default in `reference.conf`).
2. Broadcast many `TriggerSmartContract`/`CreateSmartContract` transactions concurrently (or drive concurrent `triggerconstantcontract` RPC calls) targeting several different contract addresses so that `Program.getProgramPrecompile()` is invoked concurrently on the shared static `programPrecompileLRUMap` from multiple worker threads for both new and already-cached keys.
3. Under sufficient concurrency/load, `LRUMap`'s internal linked-list corruption can surface as an unexpected runtime exception in the VM execution thread, terminating (or repeatedly failing) contract execution and, in the worst case, corrupting cache state used by other transactions.

I could not execute this against a live cluster in this environment to confirm exact JVM-level corruption symptoms (this would require a running multi-threaded node under load); this is noted as an unverified-in-practice but architecturally sound finding based on `LRUMap`'s documented non-thread-safety and the confirmed unsynchronized concurrent access path shown above.
