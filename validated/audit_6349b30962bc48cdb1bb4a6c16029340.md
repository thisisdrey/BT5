## Analysis

The external report describes a class of bug where **losses/precision drift accumulate in a shared pooled-asset system without being fairly reconciled**, causing the pool's outstanding claims to exceed its actual backing, and new participants unknowingly inherit pre-existing deficits. The closest reachable analog in java-tron is the **TRC10 Bancor-style Exchange** (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract`), where a shared two-token reserve pool is publicly tradable by any account, but its bonding-curve math historically used unsafe floating point (`double`) arithmetic.

### Title
Floating-point precision drift in TRC10 Exchange bonding-curve math causes unbacked reserve balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The legacy `ExchangeProcessor` computes Bancor-formula trades using `double`-precision `Math.pow` operations [1](#0-0)  instead of the exact `BigDecimal`-based `SafeExchangeProcessor` [2](#0-1) . Which processor is used is gated per-transaction by dynamic parameters (`allowStrictMath`, `allowHarden`) read at execute time in `ExchangeCapsule.transaction` [3](#0-2)  and passed straight through from `ExchangeTransactionActuator.execute`/`doValidate` [4](#0-3) . Any unprivileged account can call `ExchangeTransactionContract` against any exchange's pool.

### Finding Description
Like the aETH/ETH backing described in the report, the Exchange pool's `firstTokenBalance`/`secondTokenBalance` are meant to represent conserved, fungible-claim value: a liquidity provider injects proportional amounts via `ExchangeInjectActuator` and later withdraws proportionally via `ExchangeWithdrawActuator` [5](#0-4) . Public trades (`ExchangeTransactionActuator`, callable by anyone) mutate this pool via the Bancor-relay curve. When the legacy (non-hardened, non-strict) `double`-based `ExchangeProcessor` path is exercised, repeated small trades accumulate floating-point rounding error in both `exchangeToSupply` and `exchangeFromSupply` [1](#0-0) , producing outputs that differ from the exact BigDecimal computation, as confirmed by the project's own test asserting the two paths diverge (`Assert.assertNotEquals(anotherTokenQuant, result)`) [6](#0-5) . This drift is not attributable to any single trader's contribution and is never redistributed or reconciled — exactly the "no mechanism to distribute losses among all users" gap in the report. Because subsequent `ExchangeInjectActuator` calls compute the paired-token amount from the *already-drifted* current balances [7](#0-6) , any new liquidity provider joining after drift has occurred inherits the existing deficit/surplus baked into the pool ratio, unknowingly assuming risk accrued before their participation — mirroring the report's second concern about new depositors inheriting pre-existing losses.

### Impact Explanation
If the exchange creator (the only party permitted to call `ExchangeWithdrawActuator`, per the `is not creator` check [8](#0-7) ) attempts to withdraw the full pool after prolonged public trading against the double-precision path, the reserve backing one side of the pool can be lower than the accounting implies, and the "not enough" balance check [9](#0-8)  can fail or return a shortfall relative to the fair proportional share, i.e., an unbacked-balance / partial-freezing-of-funds condition analogous to the reported issue.

### Likelihood Explanation
This requires the exchange to be operating with the legacy floating-point path active (`allowStrictMath`/`allowHarden` not enabled by committee), and requires many trades to accumulate meaningful drift — the deviation per trade is small (sub-unit rounding), so material impact needs sustained public trading volume against a given pool over many transactions, which is achievable by any unprivileged account without special permission.

### Recommendation
Ensure the exact `SafeExchangeProcessor`/`BigDecimal` path is unconditionally used for all Exchange bonding-curve computations (not gated behind a governance-toggled legacy path), and add invariant checks after every trade/inject/withdraw that the product `firstTokenBalance * secondTokenBalance` (or equivalent conserved quantity net of trades) cannot decrease beyond expected fee/rounding tolerance, rejecting the transaction otherwise.

### Proof of Concept
1. Create an Exchange with two TRC10 tokens via `ExchangeCreateContract`.
2. With `allowStrictMath`/`allowHarden` disabled (default/legacy state), repeatedly submit small `ExchangeTransactionContract` trades from an unprivileged account.
3. Compare the resulting `firstTokenBalance`/`secondTokenBalance` against the exact BigDecimal computation from `SafeExchangeProcessor` for the same trade sequence, as demonstrated by `ExchangeProcessorTest.testStrictMath` showing `anotherTokenQuant != result` for the double-based path versus the hardened path across many sampled data points [10](#0-9) .
4. Have the creator attempt `ExchangeWithdrawActuator` for the full pool amount and observe the "exchange balance is not enough" validation failure or a proportionally smaller-than-expected payout.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
