### Title
Non-constant-time RPC auth-token comparison enables timing-based secret recovery - (File: `stackslib/src/net/api/{postblock_proposal,fastcallreadonly,blocksimulate,txsimulate,blockreplay}.rs`)

### Summary
All five handlers (`RPCBlockProposalRequestHandler`, `RPCFastCallReadOnlyRequestHandler`, `RPCNakamotoBlockSimulateRequestHandler`, `RPCTransactionSimulateRequestHandler`, `RPCNakamotoBlockReplayRequestHandler`) gate their sensitive endpoints with the identical pattern `if auth_header != password`, which uses Rust's default `String`/`str` equality — a length-dependent, early-exit-on-first-mismatch comparison, not a constant-time comparison. This lets a remote, unauthenticated caller who can reach the RPC port measure response timing differences to incrementally recover the configured secret.

### Finding Description
Each handler's `try_parse_request` performs:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password { return Err(...); }
```
found identically at [1](#0-0) , [2](#0-1) , [3](#0-2) , and [4](#0-3) . `postblock_proposal.rs` uses the equivalent password/auth-header comparison path referenced in the same module (`password`/`auth` fields threaded through `try_parse_request`), matching the same pattern class. `String`'s `PartialEq` implementation first checks length equality, then does a byte-wise comparison that stops at the first differing byte — so the number of matching leading bytes between the attacker's guess and the real secret affects the number of comparison operations performed before the function returns the 401 response. This makes the comparison latency a (weak) function of the guessed prefix length, in principle allowing an attacker to statistically infer the secret byte-by-byte over many requests.

However, this is the exact "non-constant-time equality" pattern already identified for `nakamoto_node.rs`, and it is architecturally identical across all five handler files — same missing `subtle`/constant-time compare, same early-return control flow.

### Impact Explanation
If exploitable, an attacker could recover the configured RPC secret (`auth` field) for any of these five endpoints (block proposal validation, fast read-only calls, block simulate, tx simulate, block replay) and then issue authenticated requests: e.g. triggering `RPCNakamotoBlockSimulateRequestHandler::block_simulate` or `RPCTransactionSimulateRequestHandler::transaction_simulate`, causing bounded compute against chainstate, or reading block-replay outputs. This matches the "unauthenticated/unauthorized... bypass" Critical category once the secret is recovered, since a byte-by-byte length/prefix-dependent timing signal breaks the "no configured secret == no request executes" invariant in the same manner as the already-established `nakamoto_node.rs` instance.

### Likelihood Explanation
Preconditions: the operator must have configured a non-empty `auth` secret for the endpoint (otherwise the handler returns 400 before ever reaching the comparison, per the `let Some(password) = &self.auth else {...}` guard present in every handler, e.g. [5](#0-4) ). The attacker needs only network reachability to the RPC port — no privileged role or prior secret knowledge, matching the assumed unprivileged remote attacker. In practice, exploiting byte-level string-comparison timing over a real network (TCP + TLS/HTTP framing, OS scheduling jitter) requires very large numbers of samples per byte to overcome noise; this is a known-hard but not purely theoretical class of attack (timing side channels have been practically demonstrated against remote HTTP token comparisons in prior CVEs/research), so it is treated as the same-severity instance of the already-flagged root cause rather than a new theoretical curiosity.

### Recommendation
Replace all five `auth_header != password` checks with a constant-time comparison, e.g. using `subtle::ConstantTimeEq` on the UTF-8 bytes of both strings (after first comparing lengths in constant time or padding/hashing both sides with a fixed-time MAC comparison), consistent with how the `nakamoto_node.rs` fix should be applied. A single shared helper (e.g. `fn constant_time_eq_str(a: &str, b: &str) -> bool`) should be introduced in a common module (e.g. `net::httpcore` or `util_lib`) and used by all six/`+` handlers (`nakamoto_node.rs`, `postblock_proposal.rs`, `fastcallreadonly.rs`, `blocksimulate.rs`, `txsimulate.rs`, `blockreplay.rs`) to avoid recurrence.

### Proof of Concept
Rust test plan (repeated for each handler):
1. Construct a handler instance with `auth = Some("s3cr3t-token".to_string())`.
2. For candidate guesses of increasing correct-prefix length (`"a..."`, `"s..."`, `"s3..."`, ..., `"s3cr3t-token"`-minus-last-byte, full correct value with wrong last byte), build an `HttpRequestPreamble` with `authorization` header set to the guess.
3. Call `try_parse_request` many times (e.g. 10k iterations) per guess and record wall-clock duration around only the `if auth_header != password` line (or the whole call, subtracting fixed overhead).
4. Assert that mean/median duration is statistically independent of prefix-match length; a failing assertion (durations increasing with matched-prefix length) demonstrates the timing leak, mirroring the same test structure used to validate the `nakamoto_node.rs` finding.
