### Title
Missing slippage/minimum-output protection in `ExchangeWithdrawActuator` allows frontrunning-based fund loss on liquidity withdrawal - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The TRC10 bancor-style `Exchange` AMM pool in java-tron lets a liquidity provider withdraw their share via `ExchangeWithdrawContract`. Unlike the sibling swap contract `ExchangeTransactionContract`, which carries an `expected` field enforced in `doValidate()`, `ExchangeWithdrawContract` carries **no minimum-output / slippage parameter at all**. This is the same bug class as the reported HydraDX `remove_liquidity` finding: a withdrawer has no way to bound the amount of the "other" token they receive, so a frontrunning swap immediately before the withdrawal transaction is applied can shift the pool ratio and cause the withdrawer to receive materially less value than expected, with the difference captured by the frontrunner/other pool participants.

### Finding Description
`ExchangeWithdrawContract` is defined with only `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/minimum amount field: [1](#0-0) 

Compare this to `ExchangeTransactionContract` (the swap contract), which explicitly adds an `expected` field precisely to protect against price movement between submission and execution: [2](#0-1) 

In `ExchangeTransactionActuator.doValidate()`, the actuator computes the counter-token amount from the current pool state and rejects the transaction if it is below `tokenExpected`: [3](#0-2) 

In contrast, `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` purely proportionally from whatever `firstTokenBalance`/`secondTokenBalance` happen to be at execution time, with no comparison to any caller-supplied minimum: [4](#0-3) 

The corresponding `doValidate()` for withdraw only checks that the token is part of the exchange, that `tokenQuant > 0`, that the pool isn't already drained, and (in "hardened" mode) a rounding-precision tolerance — none of which protects against price/ratio movement between submission and inclusion: [5](#0-4) 

Because Tron's mempool/broadcast model lets any account submit an `ExchangeTransactionContract` (swap) transaction, an attacker can observe a pending `ExchangeWithdrawContract` transaction and race a swap ahead of it (or simply submit swaps opportunistically before block packing) to shift `firstTokenBalance`/`secondTokenBalance`, directly reducing the `anotherTokenQuant` the withdrawer will receive — exactly the “frontrun the liquidity withdrawer” mechanism described in the source report.

### Impact Explanation
A liquidity provider withdrawing from an `Exchange` pool has no mechanism to guarantee a minimum amount of the counter-token, so a single unprivileged, signed `ExchangeTransactionContract` broadcast immediately ahead of the withdrawal can extract value from the withdrawer proportional to the swap size, resulting in unauthorized value transfer (loss of funds) for the withdrawer and profit for the frontrunner/remaining LPs. This matches the accepted medium-severity classification of the original finding (MEV / missing slippage check causing concrete loss of user funds), reachable purely through ordinary signed transactions with no special privilege.

### Likelihood Explanation
Any address can submit `ExchangeTransactionContract` and `ExchangeWithdrawContract` transactions; no special role or permission is required. Exchange pools of any size are naturally more exploitable when thin, and the incentive (guaranteed value extraction with bounded risk) makes this practically exploitable whenever a withdrawal transaction is visible in the mempool or is otherwise anticipated.

### Recommendation
Add an `expected`/`min_receive` field (or similar) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.execute()`/`doValidate()` by comparing the computed `anotherTokenQuant` against the caller-supplied minimum, aborting with `ContractValidateException`/`ContractExeException` if not met — mirroring the existing `expected` check already implemented in `ExchangeTransactionActuator`.

### Proof of Concept
1. Alice holds LP-equivalent balance in `firstTokenID`/`secondTokenID` of exchange `X` and broadcasts `ExchangeWithdrawContract` to withdraw `tokenQuant` of `firstTokenID`.
2. Attacker observes Alice's pending transaction and broadcasts an `ExchangeTransactionContract` selling a large amount of `firstTokenID` into the pool (with `expected=1`, guaranteeing inclusion), which is processed first due to fee/ordering, shifting `firstTokenBalance`/`secondTokenBalance` heavily.
3. When Alice's `ExchangeWithdrawContract` executes, `anotherTokenQuant` in `ExchangeWithdrawActuator.execute()` (lines 79–86) is computed from the now-skewed balances, producing a value far below what Alice would have received pre-attack, with no validation check available to reject the unfavorable outcome (contrast with `ExchangeTransactionActuator.doValidate()` lines 217–221 where such a check exists via `expected`).
4. Attacker can subsequently reverse the swap to realize a net profit, while Alice permanently receives less counter-token than intended, with no recourse since the actuator provides no slippage protection field to set.
