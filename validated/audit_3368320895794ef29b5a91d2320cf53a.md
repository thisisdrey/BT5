Based on the investigation, I found a genuine analog of the reported bug class in this repo's P2P/RPC client code.

### Title
Unbounded-depth JSON parsing into `serde_json::Value` in HTTP-response decoding allows a malicious peer to crash a requesting node via stack overflow - (File: stackslib/src/net/http/response.rs, stackslib/src/net/httpcore.rs)

### Summary
The Vapor advisory's bug class is "attacker-controlled, unbounded recursive parsing of a nested wire format leads to unbounded stack growth and a crash." In `stackslib/src/net/api`, several client-side response decoders parse an HTTP response body into a generic, arbitrarily-deep `serde_json::Value` before converting it into a typed struct, with no depth limit and only a coarse byte-size bound (`MAX_MESSAGE_LEN`). `serde_json`'s value/struct deserializer is recursive-descent (one native stack frame per nesting level of `[`/`{`), so a peer that serves a deeply-nested JSON document (e.g., `[[[[[...]]]]]`) can drive the parsing node's stack past its limit and crash the process — the same class of fault as the Vapor CVE (`array[_0][0][array]...` nesting).

### Finding Description
When a node acts as an HTTP client to another Stacks peer (e.g., fetching a StackerDB chunk-ack, fee estimate, or any RPC JSON response), the response body is first parsed generically:

- `stackslib/src/net/httpcore.rs:1259-1266` parses arbitrary error-response bodies as JSON directly into `serde_json::Value` via `serde_json::from_reader`, bounded only by `MAX_MESSAGE_LEN` bytes, not by nesting depth: [1](#0-0) 
- `StacksHttpResponse::decode_stackerdb_chunk_ack` (and similarly `decode_fee_estimate`) convert the payload `TryInto<serde_json::Value>` before further typed decoding: [2](#0-1) 
- `HttpResponsePayload::JSON(serde_json::Value)` is the generic representation used across the response-parsing pipeline: [3](#0-2) 

`serde_json`'s `Deserializer` does not impose a nesting-depth cap by default (its "recursion limit" concept only guards against certain zero-copy edge cases, not general struct/array depth), so decoding a document like `[[[[[[[[...]]]]]]]]` recurses one native call frame per bracket. `MAX_MESSAGE_LEN` (`1 + 16 * 1024 * 1024` bytes, see `stacks-common/src/codec/mod.rs:243`) permits a payload with millions of nesting levels (`[` × N bytes), which is more than enough to exhaust the thread stack well before the byte-size cap is reached — directly analogous to the `URLEncodedFormDecoder`'s unbounded stack growth from nested `array[_0][0][array]...` keys in the CVE.

This differs from the constant-time, iterative, depth-checked Clarity `Value` deserializer (`clarity-types/src/types/serialization.rs`), which explicitly guards against this exact bug class with `UNSANITIZED_DEPTH_CHECK`/`MAX_TYPE_DEPTH` limits and an explicit stack-based (non-recursive) parser. No equivalent guard exists for the generic JSON decoding path used for peer-to-peer HTTP RPC responses.

### Impact Explanation
Any Stacks node that makes outbound HTTP RPC requests to another peer (e.g., during StackerDB chunk sync, or fee-estimate queries) is exposed: a malicious or compromised peer server can return a small, deeply-nested JSON body as the HTTP response, causing the requesting node's connection-handling thread to crash via native stack overflow when the response is parsed. This is a remote, unauthenticated denial-of-service against the *requesting* node, triggered by a single crafted response — matching the "Critical: remote crash/unauthenticated DoS from few messages" impact bar.

### Likelihood Explanation
Likelihood is High: the P2P StackerDB/fee-estimate/JSON RPC-response client code path is exercised routinely during normal peer operation (e.g., every StackerDB chunk push/fetch cycle), so any node this node contacts (or is redirected to via existing peer-discovery mechanisms) can serve the malicious response. No authentication, secret key, or special role is required — only the ability to respond to an HTTP RPC request the target node initiates.

### Recommendation
- Configure `serde_json` deserialization for all attacker-influenced response bodies with an explicit recursion/depth guard (e.g., wrap with `serde_stacker::Deserializer` as already done for Clarity JSON deserialization in `clarity/src/vm/database/structures.rs`, or reject documents exceeding a fixed nesting depth before/while parsing).
- Alternatively, avoid materializing responses as an unconstrained `serde_json::Value` tree; deserialize directly into the bounded target type with a depth-limited deserializer.
- Add a defense-in-depth limit on JSON nesting depth in `stackslib/src/net/httpcore.rs`'s generic response/error-JSON parsing path and in `HttpResponsePayload`'s JSON conversions.

### Proof of Concept
1. Stand up a malicious peer HTTP server that a target node will query (e.g., respond to a `POST /v2/stackerdb/.../chunks` request, or any RPC endpoint the client fetches).
2. Craft the HTTP response body as a JSON document consisting of millions of nested opening array brackets, e.g. `"[".repeat(5_000_000) + "]".repeat(5_000_000)` (well under `MAX_MESSAGE_LEN` = ~16MB), with `Content-Type: application/json`.
3. When the target node calls `StacksHttpResponse::decode_stackerdb_chunk_ack` (or any code path hitting `TryInto<serde_json::Value>` / `serde_json::from_reader` on this body), `serde_json`'s recursive-descent parser recurses once per `[`, exhausting the calling thread's stack and crashing the process.
