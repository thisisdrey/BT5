## Analysis

This maps cleanly onto the "claimer fee exploitation" bug class: an attacker uses cheap, self-issued transactions to force entries into a **victim's** list-based state, and the victim later bears an unbounded, attacker-controlled cost when that list is processed.

### Root Cause

`FreezeBalanceActuator.delegateResource()` lets **any account (owner)** freeze even a minimal amount of TRX to an arbitrary **receiver** address. When the network has not enabled the `AllowDelegateOptimization` proposal (`supportAllowDelegateOptimization() == false`, the pre-upgrade/default legacy path), each freeze call appends the owner to the receiver's `DelegatedResourceAccountIndexCapsule.fromAccountsList`, and the receiver to the owner's `toAccountsList`: [1](#0-0) 

Because a fresh account has an empty list, an attacker can generate an unlimited number of new accounts, freeze a tiny (e.g. 1 SUN) balance from each toward the same victim receiver, and each transaction adds one more distinct entry to the victim's `fromAccountsList`, growing it without bound — the victim never consents to or initiates this: [2](#0-1) 

Later, whenever the victim's own freeze/unfreeze/delegate-related actuators touch this key, the entire list must be deserialized, linearly scanned/mutated, and re-serialized as a single protobuf value, e.g. in `UnfreezeBalanceActuator`: [3](#0-2) 

and in `DelegatedResourceAccountIndexStore.convert()`, which migrates the *entire* legacy list, iterating over every entry: [4](#0-3) 

There is no cap enforced anywhere on the size of `toAccountsList`/`fromAccountsList` — confirmed by the absence of any bound check in `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, or the capsule/store classes.

### Title
Unbounded Growth of `DelegatedResourceAccountIndexCapsule` Lists via Attacker-Controlled `FreezeBalanceContract` Enables Victim DoS/Freezing of Funds - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator` allows any account to freeze a minimal balance to an arbitrary receiver address, unconditionally appending an entry into the receiver's `DelegatedResourceAccountIndexCapsule.fromAccountsList` (legacy, non-optimized index path). An attacker can spin up unlimited fresh accounts and freeze trivial amounts against a single victim, growing that victim's index list without bound, with no minimum-freeze-amount safeguard or list-size cap.

### Finding Description
The victim never initiates or consents to being targeted as a freeze receiver, yet each attacker transaction permanently mutates the victim's `DelegatedResourceAccountIndexCapsule`. Every subsequent operation that touches this capsule (`UnfreezeBalanceActuator`, `DelegatedResourceAccountIndexStore.convert()`, `getIndex`/`getWithPrefix` prefix scans) must deserialize, scan, and re-serialize the whole list, so cost grows linearly (or worse) with the number of attacker-created entries — directly analogous to the `claimerToBuyers` per-entry flat-fee/gas exhaustion pattern in the report, where an attacker inflates a data structure another party must pay to process.

### Impact Explanation
As the attacker-inflated list grows arbitrarily large, any transaction the victim submits that must read/rewrite this capsule (e.g., unfreezing expired balance, or triggering the one-time `convert()` migration) becomes proportionally more expensive in CPU/energy, potentially exceeding practical processing limits within a block and effectively preventing the victim from ever unfreezing/withdrawing their locked TRX — a permanent freezing-of-funds condition for the victim, achievable at negligible attacker cost (repeated minimal freezes from disposable accounts).

### Likelihood Explanation
Reachable by any unprivileged account broadcasting ordinary `FreezeBalanceContract` transactions on any deployment where `AllowDelegateOptimization` has not been enabled via governance proposal (this is the legacy/default code path still present and compiled into the actuator). No special privilege, contract deployment, or victim cooperation is required — only creation of many low-cost accounts/transactions.

### Recommendation
Enforce a minimum frozen balance for delegation-with-receiver operations, and/or cap the size of `fromAccountsList`/`toAccountsList` per account (or migrate fully off the legacy non-optimized index structure), rejecting further additions once a maximum threshold is reached, mirroring the "minimum purchase amount" remediation from the original report.

### Proof of Concept
1. Deploy/observe a chain state where `supportAllowDelegateOptimization()` returns `false`.
2. From account `A1`, broadcast `FreezeBalanceContract{ownerAddress=A1, receiverAddress=Victim, frozenBalance=1, resource=BANDWIDTH}`.
3. Repeat with freshly generated accounts `A2 ... An`, each freezing a minimal balance to the same `Victim` address.
4. Observe `DelegatedResourceAccountIndexStore.get(Victim).getFromAccountsList()` grows by one entry per attacker account with no upper bound (see `FreezeBalanceActuator` lines 334–345 and `DelegatedResourceAccountIndexCapsule.addFromAccount`).
5. As `n` grows large, any subsequent `UnfreezeBalanceActuator` execution or store `convert()` call touching `Victim`'s capsule incurs cost proportional to `n`, degrading/blocking the victim's ability to process their own freeze/unfreeze transactions.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
