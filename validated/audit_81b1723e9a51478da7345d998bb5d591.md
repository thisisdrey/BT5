### Title
Stale StackerDB signer authorization persists across signer-set config changes when new config has empty signers - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` decides whether to push a newly-evaluated on-chain StackerDB config (signer list) down into the local replica's per-slot authorization table. When the freshly-evaluated config differs from the stored one but has an **empty** signer list, the code skips calling `reconfigure_stackerdb` — yet it unconditionally records the new config as authoritative in `self.stacker_db_configs`. This mirrors the MasterChef bug class: dependent state (`chunks.signer` rows used for write authentication) is not refreshed when the authoritative configuration changes, so accounting/authorization becomes stale and inconsistent with the canonical (current) state.

`reconfigure_stackerdb` is the only path that updates the `chunks.signer` column in the local SQLite replica [2](#0-1) , which is what `try_replace_chunk` uses to authenticate incoming writes: [3](#0-2) 

```rust

    .ok_or(...)?;

if !slot_desc.verify(&slot_validation.signer)? {
    return Err(net_error::BadSlotSigner(...));
```

Whenever the contract-evaluated config transitions to an empty signer set (a legitimate, reachable state — e.g. `update_signers` in the Nakamoto signer-set boot logic sets the `.signer-stackerdb` list to `vec![]` when `has_participation` is `false` [4](#0-3) , or `eval_config`/`from_smart_contract` fails and falls back to `StackerDBConfig::noop()`, whose `signers` field is also empty [5](#0-4) ), the guard `!new_config.signers.is_empty()` is false, so `reconfigure_stackerdb` is never invoked. The on-disk `chunks.signer` rows therefore keep referencing whichever addresses were valid under the **previous** cycle's configuration, while `self.stacker_db_configs` — used elsewhere for e.g. chunk-size/max-writes bounds checks in `validate_received_chunk` — is overwritten with the new, empty-signer config. The result is a divergence between "the canonical, current authorization state" (empty — nobody should be able to write) and "the stored authorization state actually enforced by `try_replace_chunk`/`get_slot_validation`" (the old signer set, still accepted).

### Impact Explanation
A signer whose write authorization has been revoked by the chain state (empty signer list for the new cycle) can continue to sign and submit chunks to the previously-assigned slot, because slot ownership verification is driven entirely by the stale `chunks.signer` DB rows, not by the freshly loaded contract config. Such chunks pass `try_replace_chunk`'s `slot_desc.verify(&slot_validation.signer)` check, get stored, and are then broadcast network-wide via `process_stacker_db_chunks`, which relays any successfully-stored chunk to peers as `StackerDBPushChunk` [6](#0-5) . This is an unauthorized write to replicated state that propagates across the network, matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact category.

### Likelihood Explanation
The empty-signers transition is not a hypothetical edge case — it is explicitly modeled in the reward-set boot code (`has_participation == false` produces an empty stackerdb list) and is also the fallback behavior on any transient config-evaluation failure (`unwrap_or_else(|e| ... StackerDBConfig::noop())`). Both paths are reachable during normal node operation across reward-cycle boundaries or contract-eval hiccups, without requiring attacker-controlled input beyond already having been a legitimately-configured signer in a prior cycle. The remaining uncertainty is how long the stale-signer window persists in practice (until the config transitions again to a non-empty, changed value or the slot count mismatches), which would require dynamic testing/observation of a live reward-cycle transition to bound precisely.

### Recommendation
Do not gate `reconfigure_stackerdb` on `new_config.signers.is_empty()`. Whenever `new_config != stackerdb_config`, always call `reconfigure_stackerdb` (or equivalently, explicitly clear/revoke all slot authorizations when the new signer list is empty) so that the local replica's per-slot `signer` records are always kept in sync with the latest canonical on-chain config, mirroring the "always mass-update before applying new state" fix pattern from the referenced report.

### Proof of Concept
1. Configure a StackerDB contract so that `stackerdb-get-signer-slots` initially returns a non-empty signer list including address `A`, and let the node create/reconfigure the replica so slot `S` is owned by `A` (`create_or_reconfigure_stackerdbs` inserts `A` into `chunks.signer` for slot `S`).
2. Advance the chain state so that the contract legitimately (or via a transient eval failure) now returns an empty signer list for the next cycle — e.g. trigger the `has_participation == false` path in `update_signers`, or force `StackerDBConfig::from_smart_contract` to error so it falls back to `StackerDBConfig::noop()`.
3. Call `create_or_reconfigure_stackerdbs` again. Because `new_config.signers.is_empty()`, the `else if` condition is false, so `reconfigure_stackerdb` is skipped; `chunks.signer` for slot `S` still equals `A`. Meanwhile `self.stacker_db_configs[contract]` now holds the empty-signer config.
4. Have the (now supposedly de-authorized) key `A` sign and push a new chunk for slot `S` with an incremented version. `try_replace_chunk` calls `get_slot_validation` (still returns signer `A`) and `slot_desc.verify(&A)` succeeds, so the chunk is accepted and stored.
5. `process_stacker_db_chunks` broadcasts this chunk via `StackerDBPushChunk` to the node's peers, propagating writes from a party that should have zero authorized slots under the current canonical configuration.
