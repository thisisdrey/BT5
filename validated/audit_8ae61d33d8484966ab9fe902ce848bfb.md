### Title
Unprivileged attacker can fill an account's token list to `MAX_TOKENS_PER_USER` via dust transfers, DoS-ing deposits, withdrawals, liquidations and borrowing - (File: contracts/DepositToken.sol)

### Summary
CVE-2023-27788 is a remotely triggerable denial of service caused by an unguarded endpoint. The Metronome analog is the per-account token registry in `Pool`/`DepositToken`: every `DepositToken` transfer that gives a recipient a nonzero balance calls `Pool.addToDepositTokensOfAccount(recipient_)`, which reverts with `UserReachedMaxTokens` once the account holds 30 tokens across `debtTokensOfAccount + depositTokensOfAccount`. Because `DepositToken.transfer`/`transferFrom` are public and there is no opt-in or minimum-amount check for the recipient, any EOA can force-add tokens to a victim's set by sending dust. Once the cap is reached, every code path that would add a *new* token to that account's set reverts, blocking protocol-critical operations.

### Finding Description
`DepositToken._transfer` unconditionally registers the token on the recipient when their balance moves from 0:

```solidity
// contracts/DepositToken.sol
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` enforces a shared cap:

```solidity
// contracts/Pool.sol
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
```

There is no consent check: the recipient never opted in, and `transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked(sender_)`), so an attacker can dust each registered `DepositToken` to a target address (or to the `feeCollector` / `Treasury`-adjacent addresses) until its combined list hits `MAX_TOKENS_PER_USER = 30`.

After the set is full, any operation that would insert a new entry reverts atomically:

- `DepositToken.deposit` → `_mint` → `pool.addToDepositTokensOfAccount` reverts: the victim cannot open a position in any collateral they don't already hold.
- `DepositToken._withdraw` → `_transfer(account_, feeCollector, _fee)` reverts: if the attack targets `feeCollector`, all withdrawals and all `liquidate` calls that take a protocol fee revert protocol-wide.
- `DebtToken.issue`/`_mint` → `pool.addToDebtTokensOfAccount` reverts: the victim cannot mint debt in any synth they don't already hold.
- `Pool.liquidate` → `depositToken_.seize(account_, liquidator, ...)` reverts when the *liquidator's* set is full: attacker dust-fills known liquidator/keeper EOAs to block liquidations.

### Impact Explanation
- Targeted freezing: a victim who already carries debt cannot add the dust tokens back out if their unlocked balance is 0 (locked collateral cannot be transferred), so slots cannot be freed while unhealthy — their ability to receive new collateral, mint new synth debt, or be topped up via `deposit(amount, onBehalfOf)` is DoS-ed.
- Protocol-wide freezing: dusting `feeCollector` to the cap makes every `withdraw` (withdraw fee path calls `_transfer` to `feeCollector`), every `deposit` with `depositFee > 0`, and every `liquidate` with `protocolFee > 0` revert — temporary freezing of user funds and of the liquidation mechanism, lasting until governance repoints `feeCollector` or the attacker is stopped.
- This satisfies "temporary freezing of funds" / liveness breakage; with liquidations blocked during a market crash it can additionally contribute to bad debt.

### Likelihood Explanation
- Fully permissionless: only requires an EOA depositing a dust amount of each registered collateral once, then calling `DepositToken.transfer(victim, 1 wei)`.
- Feasibility precondition: the pool must have enough distinct registered `DepositToken`s (plus victim's existing debt-token entries) to reach 30 — i.e. the attack is strongest on pools with many collaterals, and the `feeCollector` variant additionally requires nonzero deposit/withdraw/liquidation fees in the deployed config.
- No modifier stops it: `transfer` only checks the sender's locked balance; `addToDepositTokensOfAccount` intentionally lacks a consent mechanism; `nonReentrant`/pause flags don't apply. Requires a reproducible Hardhat/Foundry fork proof against the target deployment's registered token count.

### Recommendation
- Make set insertion non-reverting for forced dust: e.g. in `DepositToken._transfer`, skip `addToDepositTokensOfAccount` for recipients at cap and track "unregistered" balances separately, or revert only the attacker-initiated transfer path while allowing `seize`/`_mint` to bypass the cap.
- Alternatively require recipient opt-in (whitelist/allowlist of receivable tokens) or enforce a minimum transfer amount per deposit token.
- Exclude `feeCollector` from the per-account cap (it never borrows), or route fees through a pull-based claim instead of `_transfer`.
- Consider removing the cap for `depositTokensOfAccount` additions triggered by `seize`/liquidation so liquidations can never be griefed.

### Proof of Concept
Hardhat (fork against a deployment with ≥30 registered collateral+debt tokens, or a local fixture registering N deposit tokens):

```ts
it('dust-fills victim token list and blocks deposits/withdrawals', async () => {
  const victim = alice.address;
  // attacker deposits dust into each registered DepositToken and transfers 1 wei to victim
  const depositTokens: DepositToken[] = await getAllDepositTokens(pool); // registered collaterals
  for (const dt of depositTokens) {
    await depositAsAttacker(dt, '1');          // attacker deposits dust
    await dt.connect(attacker).transfer(victim, 1); // adds token to victim's set
  }
  // victim already has some debt-token entries pushing combined length to 30
  expect(await pool.getDepositTokensOfAccount(victim)).to.have.lengthOf(/*cap reached*/);

  // 1. victim cannot receive a new deposit token type
  await expect(newCollateral.connect(bob).deposit(parseEther('10'), victim))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // 2. victim cannot issue a new synth (debt token add reverts)
  await expect(newDebtToken.connect(alice).issue(amount, alice.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens');

  // 3. protocol-wide variant: dust-fill feeCollector
  const feeCollector = await poolRegistry.feeCollector();
  for (const dt of depositTokens) await dt.connect(attacker).transfer(feeCollector, 1);
  await expect(msdMET.connect(alice).withdraw(parseEther('1'), alice.address))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens'); // _transfer to feeCollector reverts
});
```

For a fork test, iterate `pool.getDepositTokens()` and `pool.getDebtTokens()`, fund the attacker via whale/`setBalance`, dust `feeCollector` and a target victim, then assert `withdraw`/`deposit`/`liquidate` revert with `UserReachedMaxTokens`.
