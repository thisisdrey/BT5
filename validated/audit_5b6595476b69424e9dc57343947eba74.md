## Analysis Result

The described accounting drift is real and reproducible in the current code.

### Title
Entry byte budget reservation is never released on non-MaxHeightReached record failures (e.g. `ChannelFull`), causing permanent per-slot byte-budget leakage - ([File: core/src/banking_stage/consumer.rs])

### Summary
In `Consumer::execute_and_commit_transactions_locked`, `bank.entry_bytes_budget().reserve(entry_bytes)` is called and succeeds *before* `record_transactions()` is attempted. If `record_transactions` subsequently fails with `PohRecorderError::ChannelFull` (or `ChannelDisconnected`) rather than `MaxHeightReached`, the code only calls `Self::remove_added_transaction_costs(bank, &transaction_costs)` to undo cost-tracker state, but never releases the bytes already reserved in `EntryBytesBudget`.

### Finding Description
The reservation and record call are sequenced at [1](#0-0) . `EntryBytesBudget::reserve` only ever increments an atomic `consumed` counter and has no corresponding release/refund method: [2](#0-1) .

`TransactionRecorder::record_transactions` maps a `RecordSenderError::Full` (bounded record channel full) into `PohRecorderError::ChannelFull`, and `RecordSenderError::Disconnected` into `PohRecorderError::ChannelDisconnected` — both distinct from `MaxHeightReached`: [3](#0-2) . The record channel itself has a small, bounded capacity (`BankIdAllowedInsertions::MAX_ALLOWED_INSERTIONS`), and `RecordSender::try_send` returns `Err(RecordSenderError::Full)` immediately whenever the allowed-insertion counter is exhausted, without blocking: [4](#0-3) , [5](#0-4) .

When `record_transactions` returns any `Err(recorder_err)`, `execute_and_commit_transactions_locked` executes: [6](#0-5) 
`remove_added_transaction_costs` reverts only the `CostTracker` state, and `entry_bytes` reserved just above is never given back — there is no call path that decrements `EntryBytesBudget.consumed` anywhere in the codebase (grep for `entry_bytes_budget` shows only `reserve()` call sites and the constructor in `runtime/src/bank.rs`). Since `EntryBytesBudget` is only reset once per slot (`apply_slot_time_runtime_changes`) [7](#0-6) , every reservation lost to a `ChannelFull`/`ChannelDisconnected` failure is permanently unrecoverable for the remainder of that slot.

Under high-throughput bursts of scheduled and executed transactions (attacker-controllable via flooding the leader's TPU with a large volume of valid, fee-paying transactions across multiple worker threads), multiple banking-stage worker threads can concurrently attempt `record_transactions` faster than `PohService` drains the bounded record channel, causing repeated `RecordSenderError::Full` → `PohRecorderError::ChannelFull` results. Each such failure "burns" `entry_bytes` from the slot's budget without ever producing a corresponding entry.

### Impact Explanation
This causes `entry_bytes_budget` to over-count relative to real entry bytes actually hashed into the PoH stream, matching the "wrongly throttling correct entries" scoped impact in the question. As reservations accumulate against `slot_limit` without matching entries, legitimate transactions later in the same slot can be spuriously rejected via `EntryBytesReserveError::ExceedsSlotLimit` → `PohRecorderError::MaxHeightReached`, reducing the leader's effective block capacity/throughput for the remainder of the slot. This is a leader self-DoS/throughput-degradation bug, not a consensus-safety or invalid-block issue (no invalid entry ever exceeds the real per-slot byte limit — quite the opposite, it under-utilizes it).

### Likelihood Explanation
Reachable purely by an unstaked remote client sending a high rate of valid transactions to the leader's TPU port. Feasibility depends on the exact size of `BankIdAllowedInsertions::MAX_ALLOWED_INSERTIONS` and worker-thread concurrency vs. `PohService` drain rate, which was not directly inspected here but the channel is explicitly bounded and non-blocking, so back-pressure conditions are structurally possible with enough throughput/thread contention, especially given multiple concurrent consuming worker threads in `BankingStage`.

### Recommendation
Add a `release(bytes)` (or `unreserve`) method to `EntryBytesBudget` that decrements `consumed` (saturating at 0), and call it in `execute_and_commit_transactions_locked`'s error branch alongside `remove_added_transaction_costs` whenever `recording_result` is `Err` and the reservation had actually succeeded (i.e., whenever `entry_bytes` were reserved but `record_transactions` did not succeed in enqueuing them).

### Proof of Concept
Rust unit test plan for `runtime/src/bank/entry_bytes_budget.rs` plus an integration-style test in `core/src/banking_stage/consumer.rs`:
1. Add `EntryBytesBudget::release(&self, bytes: u64)` and unit-test that `reserve(N)` followed by `release(N)` returns `consumed` to 0, and that budget doesn't drift after alternating reserve/release cycles under concurrent CAS loops (matches existing `test_reserve`/`test_reserve_rejects_over_limit` style tests at [8](#0-7) ).
2. In `consumer.rs` tests (alongside `test_bank_process_and_record_transactions` at [9](#0-8) ), construct a `TestFrame` where the record channel is artificially saturated (fill `RecordSender` to `MAX_ALLOWED_INSERTIONS` via direct `try_send` calls before invoking `consumer.process_and_record_transactions`), forcing `record_transactions` to return `Err(PohRecorderError::ChannelFull)`. Assert:
   - Before fix: `bank.entry_bytes_budget()`'s internal `consumed` value (expose a test-only getter) remains incremented by the failed transaction's `entry_bytes` even though `commit_transactions_result` is `Err(ChannelFull)` and no entry was produced.
   - After fix: `consumed` returns to its pre-call value, matching real recorded entry bytes over many repeated rounds (loop N times, assert budget invariant: `consumed == sum(bytes of all successfully recorded entries)`).

    pub fn reserve(&self, bytes: u64) -> std::result::Result<(), EntryBytesReserveError> {
        loop {
            let current = self.consumed.load(Ordering::Acquire);
            let next = current.saturating_add(bytes);
            if next > self.slot_limit {
                return Err(EntryBytesReserveError::ExceedsSlotLimit);
            }

            if self
                .consumed
                .compare_exchange(current, next, Ordering::AcqRel, Ordering::Acquire)
                .is_ok()
            {
                return Ok(());
            }
        }
    }

    pub fn try_send(&self, record: Record) -> Result<Option<usize>, RecordSenderError> {
        let num_transactions = record.transactions.len();
        assert!(num_transactions > 0);
        loop {
            // Grab lock on `transaction_indexes` here to ensure we are sending
            // sequentially, ONLY if this exists.
            let transaction_indexes = self
                .transaction_indexes
                .as_ref()
                .map(|transaction_indexes| transaction_indexes.lock().unwrap());

            // Get the current bank_id and allowed insertions.
            // If there are no allowed insertions, the channel is full - just return immediately.
            // If the `record`'s bank_id is different from the current bank_id,
            // return immediately.
            let current_bank_id_allowed_insertions =
                self.bank_id_allowed_insertions.0.load(Ordering::Acquire);
            let (bank_id, allowed_insertions) = (
                BankIdAllowedInsertions::bank_id(current_bank_id_allowed_insertions),
                BankIdAllowedInsertions::allowed_insertions(current_bank_id_allowed_insertions),
            );

            if bank_id == BankIdAllowedInsertions::DISABLED_BANK_ID {
                return Err(RecordSenderError::Shutdown);
            }
            if bank_id != record.bank_id {
                return Err(RecordSenderError::InactiveBankId);
            }
            if allowed_insertions == 0 {
                return Err(RecordSenderError::Full);
            }
