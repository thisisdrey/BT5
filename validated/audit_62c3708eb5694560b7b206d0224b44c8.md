### Title
Missing rounding/precision-deviation check in `ExchangeInjectActuator` allows AMM pool-ratio manipulation, unlike the symmetric `ExchangeWithdrawActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeWithdrawActuator.doValidate()` enforces a "Not precise enough" bound (≤0.01% rounding deviation) whenever liquidity is removed from a TRC10 bancor-style exchange pool, but the symmetric liquidity-add path, `ExchangeInjectActuator.doValidate()`, performs no equivalent check. This is the same class of bug as the reported issue: a price/ratio-integrity check is enforced on one side of a mint/burn-style operation pair but omitted on the other, letting the unprotected side silently skew the pool ratio that other, unrelated transactions (trades) rely on.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` computes `anotherTokenQuant` via `BigDecimal` division and then explicitly re-derives the "true" ratio with extra precision to bound the rounding error to ≤0.01%, rejecting the transaction with `"Not precise enough"` if the truncation from `long` division is too large: [1](#0-0) 

`ExchangeInjectActuator.doValidate()`, which performs the mirror-image operation (increasing both `firstTokenBalance` and `secondTokenBalance` together), computes `anotherTokenQuant` the same truncating way but only checks that the result is `> 0` — there is no bound on how much rounding error/ratio drift is tolerated: [2](#0-1) 

The `execute()` method of `ExchangeInjectActuator` then commits this unchecked ratio directly into `exchangeCapsule.setBalance(...)`, which is the exact same pool state (`firstTokenBalance`/`secondTokenBalance`) that `ExchangeCapsule.transaction()` uses to price every subsequent trade placed by any unrelated user through `ExchangeTransactionActuator`: [3](#0-2) [4](#0-3) 

Because `tokenQuant` is attacker-chosen (bounded only by `tokenQuant <= 0` and the exchange balance limit) and the floor-division truncation for `anotherTokenQuant` has no upper bound on the resulting drift (unlike the ±0.01% cap enforced on withdraw), the exchange creator can pick an injection amount that maximizes rounding-induced ratio skew in a single call, moving the effective AMM price away from the ratio the pool's other liquidity/participants expect.

### Impact Explanation
Every open, order-placer-reachable trade against this exchange (`ExchangeTransactionActuator`, invoked via `/wallet/exchangetransaction`) is priced off the balances that `ExchangeInjectActuator` mutates without a precision guard. A creator can use the unguarded inject path to bias the pool ratio in their favor, then execute (or have a colluding account execute) an `ExchangeTransactionContract` swap that extracts value from the skewed pool at the expense of the pool's backing assets — an unbacked-balance / theft-of-funds vector reachable from a normal signed transaction, mirroring the original "no deviation check on one side of a symmetric mint/burn operation" bug class.

### Likelihood Explanation
Requires only that the actor be (or control) the exchange's `creatorAddress` — a role obtainable by anyone who creates a TRC10 exchange via `ExchangeCreateActuator` — and then submit ordinary, broadcastable `ExchangeInjectContract` and `ExchangeTransactionContract` transactions. No special privilege beyond being the pool creator (a normal, permissionless action) is needed, and no witness/SR/consensus role is involved.

### Recommendation
Add the same rounding/deviation bound used in `ExchangeWithdrawActuator.doValidate()` (lines 228–243, 256–271) to `ExchangeInjectActuator.doValidate()`, rejecting injects whose implied `anotherTokenQuant` deviates from the precise BigDecimal ratio by more than the same tolerance (e.g. 0.01%), so both liquidity-add and liquidity-remove paths enforce identical ratio-integrity guarantees.

### Proof of Concept
1. Attacker creates a TRC10 exchange pool `(tokenA, tokenB)` via `ExchangeCreateActuator`, becoming `creatorAddress`.
2. Attacker calls `ExchangeInjectContract` with a `tokenQuant` chosen so that `bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)` truncates favorably, per `ExchangeInjectActuator.doValidate()` lines 215–220/221–226 — no check rejects this beyond `anotherTokenQuant > 0` (line 229–231).
3. The resulting skewed `firstTokenBalance`/`secondTokenBalance` is persisted via `Commons.putExchangeCapsule(...)` in `execute()` (lines 100–103).
4. Attacker (or a colluding account) submits `ExchangeTransactionContract` through `ExchangeTransactionActuator`, whose pricing (`exchangeCapsule.transaction(...)`, line 68) now reflects the skewed ratio, allowing extraction of value from the pool that would not have been possible had the inject path enforced the same "Not precise enough" bound that `ExchangeWithdrawActuator` applies.
