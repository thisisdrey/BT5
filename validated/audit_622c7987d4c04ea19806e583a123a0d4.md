### Title
Self-sandwich of `pallet-asset-conversion` spot price lets an XCM program pay execution/delivery fees far below real cost - (File: `cumulus/primitives/utility/src/lib.rs`, `polkadot/xcm/xcm-executor/src/lib.rs`)

### Summary
The external report's core broken invariant is: a settlement mechanism prices a trade off a manipulable on-chain AMM spot price with no price-band/oracle check, letting an attacker sandwich their own settlement inside one atomic operation to extract value cheaply. The same broken invariant exists in the Polkadot SDK's XCM fee-swap machinery: `SwapFirstAssetTrader::buy_weight` (execution fees) and the `AssetExchanger`/`take_fee` path (delivery fees) both convert whatever asset a user offers into the fee asset by calling straight into `pallet-asset-conversion`'s constant-product pool at its *current* spot reserves, with no minimum-price / price-band protection against reserves that were just moved earlier in the very same XCM program.

### Finding Description
`pallet-asset-conversion`'s own `QuotePrice` trait documents the risk explicitly: [1](#0-0) 

i.e. the pool's swap price is only "safe" if nothing else swaps against the same pool in between the quote and the execution — exactly the assumption the external SpotHedgeBaseMaker report showed is unsafe once an attacker can move the pool and reverse it inside one atomic transaction.

Two consumers rely on this un-protected spot price for pricing *protocol* fees, not user-controlled trades:

1. `SwapFirstAssetTrader::buy_weight` (used as the `Trader` in Asset Hub's and Penpal's `xcm_executor::Config`) swaps whatever asset the XCM message brings for the chain's execution-fee asset using `SwapCredit::swap_tokens_for_exact_tokens`, which is driven purely by the pool's live reserves: [2](#0-1) 

2. `xcm_executor::Config::AssetExchanger` (`SingleAssetExchangeAdapter` wrapping `pallet-asset-conversion`) is invoked from `take_fee` to swap the fee-payer's chosen asset into the asset actually needed for delivery/execution fees, again driven by whatever the pool's reserves happen to be at that instant: [3](#0-2) 

Both `AssetExchange::exchange_asset` and `QuotePrice::quote_price_*` derive their price from `Self::get_reserves`, which just reads the pool account's live token balances: [4](#0-3) 

Nothing in this call chain checks the pool price against an oracle, a TWAP, or a bounded deviation from a reference price — unlike the fix the SpotHedgeBaseMaker report converged on ("impose some restrictions on the average price ... to prevent avg price from deviating too much from the oracle" / "price band").

Because a single `Xcm` program is a sequence of instructions executed atomically against shared runtime storage (each instruction's storage effects are visible to the next instruction in the same message, all rolled back together on failure via `transactional_process`), an attacker can build one XCM program that:
1. Issues `ExchangeAsset` (or a native swap extrinsic in the same block/transaction context, e.g. via `utility.batch_all`) to dump a large amount of Asset A into the A/Fee pool, collapsing the pool's A→Fee price.
2. Immediately triggers `BuyExecution`/`PayFees` (hits `SwapFirstAssetTrader::buy_weight`) or a cross-chain send needing delivery fees (hits `AssetExchanger::exchange_asset` via `take_fee`), paying the execution/delivery fee in Asset A at the now-collapsed price — i.e. paying a small fraction of the fee's real value.
3. Issues a second `ExchangeAsset` reversing step 1, restoring the pool and recovering nearly all of the capital used to skew it (losing only the pool's LP fee, e.g. 0.3%, on the round trip).

This is the same primitive as the SpotHedgeBaseMaker case: a self-sandwich around a public settlement mechanism that trusts the AMM's instantaneous reserves as ground truth.

### Impact Explanation
This falls under the accepted "public underpriced work that degrades block production or stalls bridge processing" impact: an attacker can get their own message's execution weight, or their own cross-chain delivery fee, paid for far below its real cost, at the expense of the AssetConversion pool's liquidity providers (an unbacked value transfer out of LPs, and — if the fee asset is the chain's execution-fee/StakingPot/DapBuffer target or a Snowbridge delivery-fee asset — an under-collection of the fee the runtime/bridge is economically depending on to pay collators/relayers for real work performed). Because `SwapFirstAssetTrader`/`SingleAssetExchangeAdapter` are configured on Asset Hub, Penpal, and other production runtimes for both execution fees and (per PR `pr_5131`) delivery fees, any deployment that pairs a permissionless AMM pool with the fee-asset used for XCM execution/delivery is exposed.

### Likelihood Explanation
The primitives required — a permissionless AMM pool between the fee asset and some other asset, and the ability to include an `ExchangeAsset`/swap before and after a fee-consuming instruction in the same atomic XCM program (or batch) — are all part of normal, unprivileged usage; no malicious relayer, validator, collator, or governance actor is required, matching the "Discard: malicious peer/validator/..." exclusion list (this needs none of those). The magnitude of the extractable value scales with how thin the specific pool's liquidity is relative to the attacker's capital, exactly as debated in the underlying Sherlock report (nirohgo vs. IllIllI000) — it is bounded by pool depth and LP fee, but is non-zero and grows with attacker capital, and the pool itself provides no circuit breaker.

### Recommendation
- Add a maximum-price-impact / price-band check to `pallet-asset-conversion` swaps used for fee payment (reject if resulting price deviates more than X% from a TWAP or governance-set reference), or
- Require `SwapFirstAssetTrader`/`SingleAssetExchangeAdapter` to compare the realized swap rate against a bounded reference rate (e.g. last block's closing price) before accepting it as fee payment, and
- Consider disallowing multiple pool-affecting instructions (`ExchangeAsset`, `add_liquidity`, `remove_liquidity`, `swap_*`) against the same pool within one XCM program/transactional batch that also consumes that pool for fee pricing.

### Proof of Concept
Conceptual sketch (not a working exploit script, since it requires a live pool and specific liquidity/fee parameters, matching the caveats debated in the source report):
```
1. Attacker holds AssetA and has a large balance of AssetA relative to the AssetA/Fee pool's reserves.
2. XCM program / batched calls (all within one atomic unit):
   a. ExchangeAsset { give: AssetA (large amount), want: Fee (maximal) }
      -> collapses AssetA/Fee pool price in attacker's favor.
   b. BuyExecution { fees: AssetA (small amount) } or PayFees { asset: AssetA }
      -> SwapFirstAssetTrader::buy_weight / AssetExchanger::exchange_asset
         swaps AssetA for Fee at the now-collapsed rate, paying far less Fee-equivalent value than the real weight/delivery cost.
   c. ExchangeAsset { give: Fee (from step a), want: AssetA (maximal) }
      -> reverses the skew, recovering most of the capital spent in (a), net of the pool's LP fee.
3. Net result: attacker's real-world execution/delivery fee cost is a small fraction of its true value; the AssetConversion pool's LPs absorb the loss.
```
