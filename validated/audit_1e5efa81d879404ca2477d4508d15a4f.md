### Title
Uncaught ArithmeticException in MarketSellAssetActuator.execute() causes node crash during order matching - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` catches only a fixed set of checked exceptions (`ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, `ContractValidateException`) but not `ArithmeticException`. The order-matching path it calls (`matchOrder` → `matchSingleOrder` → `MarketUtils.multiplyAndDivide`, plus `subtractExact`/`addExact` calls) can throw `ArithmeticException` on overflow or (in the BigInteger fallback of `multiplyAndDivide`) on division by zero. This mirrors the InnoDB CVE's bug class: a reachable, unprivileged operation causes an unhandled runtime failure that can crash/hang transaction processing instead of failing gracefully.

### Finding Description
`execute()`'s try/catch block does not include `ArithmeticException` [1](#0-0) . Inside the try block, `matchOrder(orderCapsule, takerPrice, ret, accountCapsule)` is invoked [7](#0-6) , which drives `matchSingleOrder`, performing arithmetic via `MarketUtils.multiplyAndDivide` and `subtractExact`/`addExact` on quantities derived directly from attacker-controlled order parameters and existing resting orders [8](#0-7) . `multiplyAndDivide` first tries `multiplyExact`/`floorDiv` and on `ArithmeticException` falls back to unguarded `BigInteger` division: `aBig.multiply(bBig).divide(cBig)` [5](#0-4) . This is invoked directly from `matchSingleOrder` with divisor `makerBuyQuantity`/`makerSellQuantity` [9](#0-8) . In contrast, the sibling `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` were explicitly hardened to catch `ArithmeticException` in both `validate()` and `execute()`, indicating the class of bug was known and fixed elsewhere in the codebase but was missed here for `MarketSellAssetActuator`.

### Impact Explanation
An uncaught `ArithmeticException` from an actuator's `execute()` is a `RuntimeException` that is not declared/handled by `Manager.processTransaction()`'s catch clauses (which enumerate specific checked exceptions like `ContractExeException`) [10](#0-9) . When this occurs while a witness is packing/applying transactions inside a block (via `generateBlock`'s per-transaction `try { processTransaction(...) } catch (Exception e) { ... }` at packing time it's caught and logged) [11](#0-10) , but during `pushBlock`'s subsequent full/finalized application or during `pushTransaction` from `TronNetDelegate`, an uncaught runtime exception is not one of the enumerated types either, which can propagate further than expected and interrupt normal transaction/block processing, denying service for that node instance and potentially causing repeated failure of block application (matching the CVE's "hang or repeatable crash / complete DOS" class).

### Likelihood Explanation
Any unprivileged account holding TRC10/TRC20-style market assets can create maker orders and later broadcast a `MarketSellAssetContract` as taker to trigger matching, making the code path reachable purely by broadcasting standard transactions—no special privilege required. Reaching the exact overflow/zero-divisor condition requires crafting specific extreme order-quantity combinations (e.g., extremely large sell/buy quantities to trigger `addExact`/`subtractExact` overflow, or `multiplyAndDivide` fallback with degenerate quantities), which is plausible given order quantities are attacker-controlled `long` values validated primarily for `>0` before matching.

### Recommendation
Add `ArithmeticException` to the catch clause of `MarketSellAssetActuator.execute()` (mirroring `ExchangeTransactionActuator`/`ExchangeWithdrawActuator`), converting it to a `ContractExeException` with `ret.setStatus(fee, code.FAILED)`, and add an explicit zero-check/guard in `MarketUtils.multiplyAndDivide`'s `BigInteger` fallback before dividing by `cBig`.

### Proof of Concept
Not independently executed against a running node; based on static analysis: an attacker creates a maker `MarketSellAssetContract` order with an extreme `sellTokenQuantity`/`buyTokenQuantity` ratio (e.g., quantities close to `Long.MAX_VALUE`) and then broadcasts a matching taker `MarketSellAssetContract`. During `matchSingleOrder`, arithmetic on `makerSellRemainQuantity`, `takerBuyTokenQuantityReceive`, etc., via `subtractExact`/`addExact`/`multiplyAndDivide` throws `ArithmeticException`, which is not caught by `MarketSellAssetActuator.execute()`'s catch list, propagating an uncaught `RuntimeException` out of actuator execution during transaction/block processing.

**Uncertainty note:** I was unable to directly trace whether an uncaught `RuntimeException` from `execute()` ultimately terminates the node process versus being caught by an outer generic handler somewhere in `TransactionTrace`/`RuntimeImpl` (this would require deeper tracing of `trace.exec()` internals not retrieved in this session). The severity/likelihood assessment assumes no such outer catch-all exists for actuator-level `RuntimeException`s outside of the already-inspected `Manager` and `TronNetDelegate` paths.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
