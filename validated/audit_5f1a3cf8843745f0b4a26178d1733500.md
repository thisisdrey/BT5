## Title
Priority-floor pre-filter parses transactions differently than the downstream scheduler, letting spam that would be dropped bypass the CPU-expensive sigverify gate - (File: `core/src/transaction_priority.rs`, `core/src/sigverify.rs`)

## Summary
The Gearbox/Uniswap bug is a class of vulnerability where one component makes a security-relevant decision based on a *partial/lightweight parse* of a payload, while the component that actually acts on that payload uses a *different, more complete parse*. The attacker exploits the gap between the two parses. In `agave`, the sigverify-stage priority-floor mechanism computes a transaction's "priority" from raw, unresolved packet bytes (`calculate_priority_from_bytes` in `core/src/transaction_priority.rs`) to decide whether to bother running expensive ed25519 verification at all (`apply_priority_floor_to_batch` in `core/src/sigverify.rs`). The banking-stage scheduler later computes the "real" priority from a fully resolved transaction (with address-lookup-table accounts resolved) via the identical formula but different inputs (`translate_to_runtime_view` / `calculate_priority_and_cost` in `core/src/banking_stage/transaction_scheduler/receive_and_buffer.rs`). These two parses are not guaranteed to agree for V0 transactions using address-lookup tables, which is a structural analog of the Gearbox `tokenA/tokenB/tokenC` mismatch: one component (Gearbox's collateral check / here, the priority floor) parses a "short" view of the data, while the other (Uniswap's actual swap / here, the real scheduler priority and cost model) parses a "resolved" view. A crafted V0 transaction can therefore obtain a priority estimate from the floor-check pass that overstates its real value, letting otherwise-floor-rejected junk packets consume full sigverify CPU for free.

## Finding Description
`core/src/sigverify.rs` applies a scheduler-published priority floor to a packet batch before signature verification is performed, in order to save CPU on low-value packets: [1](#0-0) 

The priority used for this floor decision is computed directly from raw packet bytes: [2](#0-1) 

Note that this bytes-path builds only a `RuntimeTransaction<SanitizedTransactionView<_>>` and passes `None` for loaded addresses — it never resolves address-lookup-table (ALT) accounts for V0 transactions, unlike the real ingestion path.

The banking-stage scheduler, by contrast, computes the transaction's real priority and cost only *after* resolving ALT accounts into a `ResolvedTransactionView`: [3](#0-2) [4](#0-3) 

Both paths eventually call the same `calculate_priority_and_cost` formula: `P = R / (1 + C)`, where the cost `C` comes from `CostModel::calculate_cost_for_executed_transaction`, which depends on the number and writability of accounts touched by the transaction: [5](#0-4) 

For a legacy or already-fully-static transaction, both paths see the same account set, so priority agrees — and the codebase even has a regression test asserting this equivalence for a simple transfer: [6](#0-5) 

However, that test only exercises a transaction with **no address-lookup-table accounts**. For a V0 transaction that loads additional accounts via ALTs, the bytes-path (`calculate_priority_from_bytes`) computes cost using only the *static* account keys (ALT accounts unresolved/absent), while the scheduler's real path (`translate_to_runtime_view`) computes cost using the *fully resolved* account set (static + ALT-loaded accounts). Because `CostModel::calculate_cost_for_executed_transaction` scales with number/writability of accounts, these two cost computations — and therefore the two priority values `P = R/(1+C)` — can diverge for the exact same bytes on the wire, exactly mirroring how Gearbox's `_extractTokens()` parsed a different token pair than Uniswap's `SwapRouter` executed for the same `path` bytes.

## Impact Explanation
This is a QoS-evasion / underpriced-pre-fee-work analog: the sigverify priority floor exists specifically to protect validator CPU from being wasted on expensive ed25519 verification of low-value spam before the scheduler even sees it (`apply_priority_floor_to_batch`, `core/src/sigverify.rs:413-440`). If an attacker can craft V0 transactions with ALT lookups whose *bytes-path* priority estimate is inflated relative to the account set actually used by the real cost model, those transactions bypass the cheap pre-filter and receive full (expensive) ed25519 signature verification that the validator intended to skip for such low-fee traffic. This is a form of "grossly underpriced pre-fee work" — the attacker gets CPU-expensive verification work performed essentially for free/underpriced, at scale, purely by exploiting the parsing gap between the two priority computations, an unprivileged-user-reachable QoS bypass in the sigverify/streamer path.

## Likelihood Explanation
Reachable by any unprivileged network sender submitting normal QUIC/UDP transaction packets — no special validator/operator role required. It requires only the ability to construct a V0 transaction using address lookup tables (a standard, publicly documented feature) with a chosen combination of static vs. ALT-loaded writable/readonly accounts to shift the two cost-model computations relative to each other. Because the priority floor is scheduler-controlled and adaptive (`SchedulerPriorityFloor`), the practical magnitude of the divergence needed depends on current network load, but the underlying parsing-inconsistency mechanism is deterministic and always present for ALT-using transactions.

## Recommendation
Ensure that any priority/cost value used to make a security- or resource-allocation-relevant decision (the sigverify priority floor) is computed from the same resolved view of the transaction that the downstream scheduler will use, or conservatively bound the bytes-only estimate so it can never be artificially inflated relative to the ALT-resolved cost (e.g., always assume the maximum possible additional ALT-loaded account cost when computing the floor-check priority for V0 transactions, matching how `translate_to_runtime_view` treats ALT accounts as full-cost accounts). Alternatively, extend the existing equivalence test (`floor_priority_from_bytes_matches_typed_path`) to cover V0 transactions with address-lookup tables to close this gap, and add a hard invariant in code (not just tests) that the bytes-path priority can never exceed the eventual resolved-path priority.

## Proof of Concept
1. Construct a `VersionedMessage::V0` transaction whose static account keys include few/no writable accounts (minimizing the apparent cost visible in `calculate_priority_from_bytes`, which only sees static keys because `RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(..., None)` is passed no loaded addresses).
2. Populate its `address_table_lookups` with a large number of writable indexes pointing into an attacker-controlled ALT, so that once resolved by the real ingestion pipeline (`translate_to_runtime_view` → `RuntimeTransaction::<ResolvedTransactionView<_>>::try_new`), the transaction's true cost `C` is large and its true fee `R` is tiny — i.e., its **real** priority `P = R/(1+C)` is very low.
3. Set the transaction's declared `compute_unit_price` such that the **unresolved** bytes-path cost estimate (which ignores the ALT-loaded accounts and therefore computes a much smaller `C`) yields a priority `P_bytes` above the current `SchedulerPriorityFloor`, while the resolved real priority `P_real` computed later by `translate_to_runtime_view`/`calculate_priority_and_cost` would fall below the floor.
4. Send a burst of such packets to the TPU/QUIC ingest path. `apply_priority_floor_to_batch` (`core/src/sigverify.rs:413-440`) will keep them (since `priority <= floor` check uses `calculate_priority_from_bytes`, which reports `P_bytes` above the floor), causing `sigverify::ed25519_verify_serial` to run full expensive signature verification on packets that the floor mechanism was intended to discard before verification, and that the scheduler would subsequently drop anyway as too-low-priority — demonstrating CPU work performed for underpriced/should-have-been-filtered transactions.

Note: I was unable to fully trace through `cost-model/src/cost_model.rs`'s exact per-account cost weighting (the file read for that section did not complete within the available tool budget), so the precise magnitude of divergence achievable and the exact `SchedulerPriorityFloor` wiring in `scheduler_controller.rs` should be independently verified/exercised by a background agent with fuller tool access before treating the magnitude as confirmed.

```rust
fn apply_priority_floor_to_batch(
    batch: &mut PacketBatch,
    floor: u64,
    bank: &Bank,
) -> (usize, bool) {
    let mut dropped: usize = 0;
    let mut any_kept = false;
    for mut packet in batch.iter_mut() {
        if packet.meta().discard() {
            continue;
        }
        let Some(data) = packet.data(..) else {
            // Zero-length or otherwise unreadable: leave to downstream
            // stages to reject.
            any_kept = true;
            continue;
        };
        // Unparseable packets are kept and left for downstream rejection.
        match calculate_priority_from_bytes(bank, data) {
            Some(priority) if priority <= floor => {
                packet.meta_mut().set_discard(true);
                dropped = dropped.saturating_add(1);
            }
            _ => any_kept = true,
        }
    }
    (dropped, !any_kept)
}
```

```rust
/// Calculate priority and cost for a transaction:
///
/// Cost is calculated through the `CostModel`,
/// and priority is calculated through a formula here that attempts to sell
/// blockspace to the highest bidder.
///
/// The priority is calculated as:
/// P = R / (1 + C)
/// where P is the priority, R is the reward,
/// and C is the cost towards block-limits.
///
/// Current minimum costs are on the order of several hundred,
/// so the denominator is effectively C, and the +1 is simply
/// to avoid any division by zero due to a bug - these costs
/// are calculated by the cost-model and are not direct
/// from user input. They should never be zero.
/// Any difference in the prioritization is negligible for
/// the current transaction costs.
pub(crate) fn calculate_priority_and_cost<Tx: TransactionMeta + SVMStaticMessage>(
    bank: &Bank,
    transaction: &Tx,
    transaction_configuration: &TransactionConfiguration,
) -> (u64, u64) {
    let cost = CostModel::calculate_cost_for_executed_transaction(
        transaction,
        u64::from(transaction_configuration.compute_unit_limit),
        transaction_configuration.loaded_accounts_data_size_limit,
        &bank.feature_set,
    )
    .sum();
```

```rust
/// Evaluate raw packet bytes against the pf-floor, returning the computed
/// priority.
///
/// Returns `None` if the bytes don't parse as a valid transaction, in which
/// case the caller should leave the packet to downstream stages to reject.
pub(crate) fn calculate_priority_from_bytes(bank: &Bank, data: &[u8]) -> Option<u64> {
    let view = SanitizedTransactionView::try_new_sanitized(data, &sanitize_config()).ok()?;
    let runtime_tx = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    )
    .ok()?;
    let transaction_configuration = runtime_tx
        .transaction_configuration(&bank.feature_set)
        .ok()?;
    let (priority, _cost) =
        calculate_priority_and_cost(bank, &runtime_tx, &transaction_configuration);

    Some(priority)
}
```

```rust
/// Perform sanitization checks and transition from data to an executable
/// [`RuntimeTransaction`]. This additionally returns the minimum slot for
/// ALT deactivation, if any. If no minimum slot, Slot::MAX is returned.
pub(crate) fn translate_to_runtime_view<D: TransactionData>(
    data: D,
    bank: &Bank,
    transaction_account_lock_limit: usize,
    sanitize_config: &SanitizeConfig,
) -> Result<(RuntimeTransaction<ResolvedTransactionView<D>>, u64), PacketHandlingError> {
    // Parsing and basic sanitization checks
    let Ok(view) = SanitizedTransactionView::try_new_sanitized(data, sanitize_config) else {
        return Err(PacketHandlingError::Sanitization);
    };

    let Ok(view) = RuntimeTransaction::<SanitizedTransactionView<_>>::try_new(
        view,
        MessageHash::Compute,
        None,
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Discard non-vote packets if in vote-only mode.
    if bank.vote_only_bank() && !view.is_simple_vote_transaction() {
        return Err(PacketHandlingError::Sanitization);
    }

    if usize::from(view.total_num_accounts()) > transaction_account_lock_limit {
        return Err(PacketHandlingError::LockValidation);
    }

    let (loaded_addresses, deactivation_slot) = load_addresses_for_view(&view, bank)?;

    let Ok(view) = RuntimeTransaction::<ResolvedTransactionView<_>>::try_new(
        view,
        loaded_addresses,
        bank.get_reserved_account_keys(),
    ) else {
        return Err(PacketHandlingError::Sanitization);
    };

    // Validate no duplicate accounts (must be after resolution to catch ALT duplicates)
    if validate_account_locks(view.account_keys(), transaction_account_lock_limit).is_err() {
        return Err(PacketHandlingError::LockValidation);
    }

    Ok((view, deactivation_slot))
}
```
