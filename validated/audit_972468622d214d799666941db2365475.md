### Title
Unbounded growth of `DelegatedResourceAccountIndexCapsule.toAccountsList`/`fromAccountsList` allows cheap, attacker-triggered DoS of resource-delegation actuators and query APIs - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
Analogous to the Symmetrical `partyAPendingQuotes` bug, java-tron's legacy (pre-`AllowDelegateOptimization`) delegated-resource bookkeeping appends to an index list on every `DelegateResourceContract`/`FreezeBalanceContract` (delegating variant) call without any upper bound on list size, and that unbounded list is later iterated in full by both broadcastable actuators and public query paths.

### Finding Description
`DelegatedResourceAccountIndexCapsule` stores two repeated protobuf fields, `toAccounts` and `fromAccounts`, with no size limit: [1](#0-0) 

When `AllowDelegateOptimization` is not yet enabled, `FreezeBalanceActuator.delegateResource` grows the owner's `toAccountsList` and the receiver's `fromAccountsList` by one entry for every distinct counterparty, with only a linear `contains()` de-duplication check (no cap enforced): [2](#0-1) 

Because `receiverAddress` in a `FreezeBalanceContract` (delegating variant) is fully attacker-controlled and any account can be used as a receiver, an attacker can trivially generate many distinct receiver addresses (or have many distinct senders target one victim receiver) to make one account's `toAccountsList`/`fromAccountsList` grow without bound, each entry costing only ordinary bandwidth (the actuator's `calcFee()` returns 0, so there is no compensating energy/fee cost for the O(n) work this creates later): [3](#0-2) 

This bloated list is then walked in full by the `convert()` migration routine — triggered from other resource-related actuators once `AllowDelegateOptimization` is turned on — which loops over every entry and performs a DB write (`this.delegate(...)`) per element: [4](#0-3) 

The same unbounded list is also rebuilt and returned by `getIndex`/`getV2Index`/`getWithPrefix`, which perform a full prefix scan over the underlying store and materialize the entire list in memory, sorted, on every call: [5](#0-4) 

`UnfreezeBalanceActuator` and `UnDelegateResourceActuator` also perform a linear scan and rebuild of the same lists on removal, using `contains()`/`remove()` on a full-list copy: [6](#0-5) 

This mirrors the reported vulnerability class exactly: an unbounded, attacker-append-only list is iterated by multiple downstream state-transition functions (freeze, unfreeze, delegate, undelegate) with no size validation at append time.

### Impact Explanation
An attacker can cheaply inflate a victim account's (or their own account's) `DelegatedResourceAccountIndexCapsule` to a very large size using ordinary, low-cost `FreezeBalanceContract`/`DelegateResourceContract` transactions (these consume only bandwidth, `calcFee()==0`). Once bloated:
- Every subsequent freeze/unfreeze/delegate/undelegate transaction touching that account triggers O(n) work (linear scans, and for `convert()` an O(n) sequence of additional DB writes), inflating per-transaction CPU cost during block validation/application in `Manager`, without a corresponding energy/fee charge.
- Any client (including the node itself, and any full node serving HTTP/gRPC queries) calling `getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` triggers a full prefix scan and in-memory sort of the entire list, which can be used to degrade the query-serving path.

This can degrade block processing throughput and the responsiveness of resource-delegation-related transactions and read APIs for the affected account(s), which is a protocol-operation availability concern analogous to the original report (though the "liquidation" concept doesn't map 1:1, the DoS-via-unbounded-list-growth class does map to block application / API query paths).

### Likelihood Explanation
Reachable by any unprivileged transaction sender using only standard `FreezeBalanceContract` (delegating) or `DelegateResourceContract` transactions with attacker-chosen receiver addresses — no special privileges required. The cost to the attacker is proportional to ordinary transaction bandwidth costs, not to the O(n) cost imposed on the victim/network later, making this an economically asymmetric (cheap-to-trigger, costly-to-process) DoS vector. However, exploitation is somewhat mitigated because the legacy (`toAccounts`/`fromAccounts`) code path is only exercised while `AllowDelegateOptimization` is not yet enabled on the live network; I was not able to fully confirm from the available index whether this legacy path is still reachable on current mainnet configuration (this flag's on-chain state and rollout status could not be verified within the tool/index limits).

### Recommendation
Enforce a maximum size (mirroring the `pendingQuotesValidLength`-style bound recommended in the original report) on `toAccountsList`/`fromAccountsList` inside `DelegatedResourceAccountIndexCapsule.addToAccount`/`addFromAccount`, rejecting (via `ContractValidateException`) further additions once the limit is reached; additionally, cap the number of entries processed per call in `DelegatedResourceAccountIndexStore.convert()` and in the `getIndex`/`getV2Index` prefix-scan helpers, or paginate/rate-limit them, to bound worst-case per-transaction and per-query CPU cost.

### Proof of Concept
1. Ensure `AllowDelegateOptimization` is not yet enabled (legacy delegation bookkeeping active).
2. From an attacker-controlled account `A`, repeatedly submit `FreezeBalanceContract` transactions with `resource=BANDWIDTH`, `receiver_address` set to a large number of distinct, freshly generated addresses (as demonstrated at scale in the existing test `testMultiFreezeDelegatedBalanceForBandwidth`, which creates 101 receivers) — each transaction costs ordinary bandwidth only: [7](#0-6) 
3. Repeat this thousands of times to grow `A`'s `toAccountsList` to a very large size.
4. Trigger `AllowDelegateOptimization` (or any subsequent freeze/delegate/unfreeze on account `A`) to invoke `DelegatedResourceAccountIndexStore.convert(A)`, which iterates the entire bloated list, performing one DB write per entry — demonstrating unbounded, attacker-controlled per-transaction cost.
5. Separately, query `getDelegatedResourceAccountIndex`/`V2` for account `A` via the HTTP/gRPC API to observe the full prefix-scan/list-materialization cost scale with the attacker-inflated list size.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }
