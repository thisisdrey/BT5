### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust deposits/transfers, permanently blocking new collateral deposits and rescue of unhealthy positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The Pool tracks every deposit token and debt token an account touches in `depositTokensOfAccount` / `debtTokensOfAccount`, capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Both `DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance is 0 (`contracts/DepositToken.sol:486-488`, `contracts/DepositToken.sol:518-520`), and `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list size reaches 30 (`contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`). Because `deposit(amount_, onBehalfOf_)` and `transfer`/`transferFrom` are permissionless, any unprivileged attacker can dust-fill a victim's list, after which every `deposit` of a new collateral type and every incoming transfer of a new deposit token to the victim reverts.

### Finding Description
`DepositToken.deposit` mints to an arbitrary `onBehalfOf_` (`contracts/DepositToken.sol:211-237`), and `transfer`/`transferFrom`/`seize` mint-and-add on first balance (`_transfer` at `contracts/DepositToken.sol:498-526`). The recipient has no way to opt out and the add is performed inside the same transaction, so the revert poisons the entire action.

Attack:
1. Victim has an open debt position (e.g., debt tokens already occupying some of the 30 slots).
2. Attacker calls `depositToken_i.deposit(1 wei, victim)` (or `transfer(victim, 1)`) for every registered deposit token until `depositTokensOfAccount[victim] + debtTokensOfAccount[victim] == 30`.
3. If the victim's position is unhealthy or becomes unhealthy, the victim cannot `deposit` any *new* collateral type to restore health — `addToDepositTokensOfAccount` reverts `UserReachedMaxTokens`.
4. Worse, the dust balances the attacker pushed onto the victim are *locked* collateral: `unlockedBalanceOf` only returns withdrawable amount net of required collateral (`contracts/DepositToken.sol:383-398`), so the victim may be unable to `withdraw`/`transfer` enough dust to free a slot, making the freeze effectively permanent rather than self-healing.
5. The victim is then liquidated via `Pool.liquidate`, suffering liquidation losses that could have been avoided by topping up collateral.

The analogous bug class to CVE-2022-21339 (availability impact via a reachable, easily triggered condition) maps here to a liveness freeze of the deposit/receive path, driven entirely by an unprivileged EOA.

### Impact Explanation
Direct impact is temporary-to-permanent freezing of the victim's ability to add collateral and to receive deposit tokens, which in turn enables forced liquidation of an otherwise rescuable position — a loss of user funds via liquidation penalties and price slippage on seized collateral. The invariant broken is the expected liveness of `deposit`/`transfer` for any user, gated by attacker-controllable state.

### Likelihood Explanation
Fully reachable by any EOA: `deposit` and `transfer` are public, `onBehalfOf_` is attacker-chosen, and only dust amounts are needed. The only constraint is the number of distinct deposit tokens registered in the pool plus the victim's debt tokens must reach 30; on pools with many listed collaterals this is cheap. No governance, oracle manipulation, or privileged actor is required. This is a griefing-style DoS — the attacker does not profit directly, but can combine with self-liquidation of the victim's position to capture liquidation fees.

### Recommendation
- Move the max-tokens check to a best-effort model: in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, silently skip (or emit an event) instead of reverting when the cap is reached, accepting that `depositOf`/`debtOf` may then iterate over a list that misses some entries — alternatively, bound iterations elsewhere.
- Or restrict who can add entries: only allow `deposit(..., onBehalfOf_)` to add when `onBehalfOf_ == _msgSender()` or when the beneficiary opts in, and make `transfer` adds opt-in.
- Or allow users to evict zero/dust entries: add a public `removeDustToken(account, token)` callable when `balanceOf(account) < threshold`, so a victim can always free slots even when the dust balance is locked.

### Proof of Concept
Hardhat fork sketch (pseudocode, using deployed pool + deposit tokens):

```ts
// contracts/Pool.sol: MAX_TOKENS_PER_USER = 30
const pool = await ethers.getContractAt('Pool', POOL);
const depositTokens: string[] = await pool.getDepositTokens(); // registered collaterals

// victim already holds some debt tokens (debtTokensOfAccount[victim] = k)
// attacker dust-deposits each deposit token into victim's account
for (const dt of depositTokens.slice(0, 30 - k)) {
  const depositToken = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await depositToken.underlying());
  await underlying.approve(depositToken.address, 1);
  await depositToken.deposit(1, victim.address); // adds dt to victim's list
}

expect((await pool.getDepositTokensOfAccount(victim.address)).length +
       (await pool.getDebtTokensOfAccount(victim.address)).length).to.eq(30);

// victim can no longer deposit a new collateral type to restore health
const newDt = await ethers.getContractAt('DepositToken', depositTokens[30 - k]);
await expect(newDt.connect(victim).deposit(parseUnits('10', 6), victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// incoming transfers of any new deposit token also revert
await expect(depositTokens.connect(attacker).transfer(victim.address, 1))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
