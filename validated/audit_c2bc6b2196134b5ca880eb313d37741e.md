### Title
Front-running/sandwich manipulation of the on-chain Bancor-style TRC10 Exchange pool price in `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
The TRC10 `Exchange` feature computes token-swap output amounts from the exchange pool's *current* on-chain reserve balances at execution time, exactly analogous to a Uniswap spot-price read. Because any unprivileged account can broadcast an `ExchangeTransactionContract` against a given `exchangeId`, an attacker can submit a swap immediately before a victim's swap to shift the pool ratio, let the victim's trade execute at the manipulated ratio, and then reverse the position afterward — a classic sandwich attack. The only mitigation is a client-supplied `tokenExpected` minimum, which (as in the referenced report's `_applySlippage`) is computed off-chain against a price the attacker can still legally satisfy while extracting value.

### Finding Description
`ExchangeTransactionActuator.execute` (and its `doValidate`) call `ExchangeCapsule.transaction(tokenID, tokenQuant, ...)`, which delegates to `ExchangeProcessor.exchange`/`SafeExchangeProcessor.exchange`. These compute the swap output purely from the pool's live `firstTokenBalance`/`secondTokenBalance` reserves: [1](#0-0) [2](#0-1) [3](#0-2) 

The only protection against price movement between when a caller computes an acceptable rate off-chain and when the transaction is actually applied on-chain is the `tokenExpected` field, validated as a simple minimum-output check: [4](#0-3) 

This is structurally identical to the reported pattern: a spot-derived quote (`quoteExactOutputSingle`) plus a slippage bound (`_applySlippage`) that an attacker who moves the price first can still satisfy while capturing the difference. Here, the pool's reserves (`firstTokenBalance`/`secondTokenBalance`) play the role of the manipulable spot price, and `tokenExpected` plays the role of `_applySlippage`'s output — both bound the *worst case* the victim will accept, but neither bounds what the attacker can extract in between. Since `ExchangeTransactionContract` is broadcastable by any account against any existing exchange id (no special permission needed, see `AbstractExchangeActuator`/contract type wiring), an attacker can:
1. Observe a pending victim `ExchangeTransactionContract` (via mempool/API broadcast) targeting a given `exchangeId`.
2. Broadcast their own `ExchangeTransactionContract` swap for the same pair with better ordering priority (e.g. faster propagation to the block-producing SR), shifting `firstTokenBalance`/`secondTokenBalance` unfavorably against the victim.
3. Let the victim's swap execute against the shifted reserves — still passing the `tokenExpected` check if the victim's slippage tolerance is not zero.
4. Immediately reverse the position with a second `ExchangeTransactionContract`, extracting the price impact as profit, funded by the victim's loss.

### Impact Explanation
The victim receives materially less of the counter-asset than the fair/pre-attack pool ratio would have provided, while the attacker profits risklessly from round-tripping reserves. This is a direct value-extraction/theft vector against any user of the on-chain TRC10 Exchange, reachable purely through ordinary signed `ExchangeTransactionContract` transactions with no elevated privilege.

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` transactions for any exchange pool, so the barrier to executing the attack is only transaction-ordering influence (a capability external MEV-style actors on TRON already have via broadcast timing/relationships with SRs), not any special permission. Victims must also select non-zero slippage tolerance to get any swap executed at all (since real reserves always move slightly between quote and execution due to concurrent activity), which normal usage requires, keeping likelihood Medium rather than trivial-always-exploitable.

### Recommendation
Do not rely solely on a single instantaneous reserve ratio plus a user-chosen slippage bound for TRC10 Exchange swaps. Consider adding pool-level protections such as a maximum single-transaction price-impact cap, a per-block price-movement limit on `ExchangeCapsule.transaction`, or exposing a time-weighted average reserve ratio for validation, so that `tokenExpected` cannot be trivially satisfied by an attacker who has just moved the pool in the same block.

### Proof of Concept
1. Attacker monitors the transaction broadcast for a target `exchangeId` and detects a pending `ExchangeTransactionContract` from Victim swapping `tokenA` for `tokenB` with `tokenExpected` set to a modest slippage tolerance below the current fair quote.
2. Attacker broadcasts `ExchangeTransactionContract` (front-run) selling a large amount of `tokenA` into the same pool, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:124-169`) so the pool ratio moves against future `tokenA→tokenB` sellers.
3. Victim's transaction executes: `ExchangeTransactionActuator.doValidate` recomputes `anotherTokenQuant` against the now-worse reserves and still passes because `anotherTokenQuant >= tokenExpected` (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java:217-221`), so the swap executes at a worse-than-fair rate for Victim.
4. Attacker broadcasts a second `ExchangeTransactionContract` selling `tokenB` back for `tokenA`, restoring the reserves and capturing the price-impact spread as profit — net loss borne by Victim.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
