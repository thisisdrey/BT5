### Title
Stale `PromiseYieldReceipt` / `PromiseYieldStatus` / `YieldIdToDataId` / `DataIdToYieldId` trie entries survive `remove_account`, enabling authorization-escalation via yield-resume replay after account recreation - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:504-575) only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` entries belonging to that account. Because these keys are addressed purely by `(receiver_id, yield_id/data_id)` with no account-incarnation nonce, deleting and then recreating an account under the same `AccountId` leaves the old account's abandoned yield-resume state fully intact and resumable by whoever controls the new incarnation.

### Finding Description
`set_yield_id_mapping` writes both `TrieKey::YieldIdToDataId{receiver_id, yield_id}` and `TrieKey::DataIdToYieldId{receiver_id, data_id}` [1](#0-0) , and `create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs` also stores a `PromiseYieldStatus::Yielded` entry and (via the receipt manager / `set_promise_yield_receipt`) the pending `PromiseYieldReceipt` itself [2](#0-1) .

These entries are only ever cleaned up on the *normal* resume path, inside `apply_action_receipt`'s handling of `VersionedReceiptEnum::PromiseResume`, which removes the yield receipt, its status, and (if `YieldWithId` is enabled) the bidirectional yield_id mappings [3](#0-2) .

However, `remove_account` — the function invoked when a `DeleteAccount` action is processed — has no knowledge of yield/resume state at all: [4](#0-3) 
It removes the `Account` and `ContractCode` records, iterates and deletes access keys/gas key nonces, and iterates and deletes `ContractData`, but never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` keyed to the same `account_id`.

All of these trie keys are addressed only by the textual `receiver_id` (account name) plus a `yield_id`/`data_id`, with no incarnation counter distinguishing "this account before deletion" from "this account after being recreated" (`core/primitives/src/trie_key.rs:520-577`). Consequently:

1. Account `C` creates a self-targeted promise yield via `promise_yield_create_with_id(yield_id=Y)`, producing `data_id=D`, storing `YieldIdToDataId{C,Y}=D`, `DataIdToYieldId{C,D}=Y`, `PromiseYieldStatus{C,D}=Yielded`, and a `PromiseYieldReceipt{C,D}` containing the callback actions to run on resume (predecessor_id set to `C` itself, per the common self-callback pattern).
2. `C` is deleted via a `DeleteAccount` action. `remove_account` clears the account/keys/contract data but leaves the four yield-related trie entries in state.
3. `C` (same `AccountId` string) is recreated — either by the original attacker or by a third party who registers the now-available name and deploys a new (potentially unrelated) contract, funding it.
4. Anyone can then trigger `promise_yield_resume_with_yield_id(Y, data)` (`runtime/near-vm-runner/src/logic/logic.rs`, `wasmtime_runner/logic.rs:4236`) from a receipt executing on `C`. This calls `submit_promise_resume_data_with_yield_id`, which calls `get_data_id_for_yield_id(trie, self.account_id=C, Y)` — this still resolves to the stale `D` because the mapping was never deleted [5](#0-4) .
5. `submit_promise_resume_data` then checks `has_promise_yield_receipt`/`has_promise_yield_status` for `(C, D)` — both still true — and creates a `PromiseResume` receipt [6](#0-5) .
6. When that `PromiseResume` receipt is applied, `get_promise_yield_receipt(state_update, C, D)` still returns the stale, pre-deletion `Receipt` object with its original stored actions, and those actions execute with `predecessor_id == receiver_id == C` against the *new* account's state/balance [7](#0-6) .

Since the stale receipt's actions execute as a self-call on the recreated account, any contract logic in the new deployment that trusts `predecessor_id == current_account_id` as an authorization check (a common and otherwise-safe pattern for "only I can call my own callback") will unconditionally execute attacker-predetermined actions (e.g., a `FunctionCall` invoking a privileged method) that were fixed at the time the *old* account created the yield — regardless of the fact that the account has since been deleted and recreated with entirely different code/state/ownership. No existing check in `remove_account`, `submit_promise_resume_data_with_yield_id`, or the `PromiseResume` handling path validates that the yield receipt was created by the *current* incarnation of the account.

### Impact Explanation
This is an authorization-escalation / cross-incarnation replay bug: actions belonging to a deleted account's abandoned yield-resume state can be forced to execute against a newly created account bearing the same `AccountId`, with `predecessor_id == receiver_id`, satisfying naive self-call authorization checks in the new contract. Depending on the redeployed contract's logic, this can be leveraged to invoke privileged self-only methods (fund transfers, permission grants, state mutation) that the new account's owner never authorized — a concrete authorization-escalation-across-promises impact, potentially leading to theft of the new account's funds if the replayed action set includes a transfer or withdrawal call.

### Likelihood Explanation
Fully reachable by an unprivileged attacker: creating an account, calling `promise_yield_create_with_id`, deleting the account, and later calling `promise_yield_resume_with_yield_id` are all ordinary transactions/actions available to any funded account (no validator/node privilege required). The only external dependency is that the same `AccountId` gets reused after deletion (attacker can simply reuse their own account, or wait for/induce a third party to register the freed name), which is a normal, supported NEAR operation with no cooldown enforced by this code path. The attack is deterministic and repeatable since `yield_id`/`data_id` values and the stale trie entries persist indefinitely until an actual resume occurs.

### Recommendation
Extend `remove_account` (core/store/src/utils/mod.rs) to enumerate and delete all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` entries scoped to the account being deleted (analogous to how access keys and contract data are iterated and removed), so that no dangling yield-resume state can be resumed against a future incarnation of the same account name.

### Proof of Concept
Runtime/test-loop integration test:
1. Create account `C` with a contract exposing a self-callback method gated by `predecessor_id == current_account_id`.
2. From `C`, call `promise_yield_create_with_id(yield_id=Y)` targeting that self-callback with a marker action (e.g., transfer balance to attacker).
3. Submit `DeleteAccount` for `C`; assert `Account{C}` is gone from state but `YieldIdToDataId{C,Y}` / `DataIdToYieldId{C,D}` / `PromiseYieldReceipt{C,D}` / `PromiseYieldStatus{C,D}` still exist in the trie.
4. Recreate `C` with a fresh contract/state and fund it.
5. From `C` (new incarnation), invoke `promise_yield_resume_with_yield_id(Y, data)`.
6. Assert the stale marker action executes with `predecessor_id == C == receiver_id`, and observe the funds/state effect against the new account — confirming replay of the deleted owner's stale callback against the recreated account.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }

    fn submit_promise_resume_data(
        &mut self,
        data_id: CryptoHash,
        data: Vec<u8>,
    ) -> Result<bool, VMLogicError> {
        let has_yield_receipt_in_state =
            has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }
