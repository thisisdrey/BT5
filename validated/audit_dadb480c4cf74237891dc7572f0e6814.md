## Analysis

The Velocimeter bug's core broken invariant: a price used to determine economically-critical parameters (discount/fee) is computed only from a batch of past observations and never reconciled against the *current* market price, so the derived value can lag the real price by a bounded but significant window (up to 30 minutes), letting the protocol under-collect value.

The closest structural analog in this repository is the Snowbridge outbound-queue fee model, where the ETH/DOT `exchange_rate` (and the fixed relayer `reward` denominated in wei) used to price every outbound message is a single on-chain snapshot that is *only* refreshed by a manual governance call, with no automatic reconciliation against the real market price between updates.

### Where this lives

`calculate_fee()` converts the ETH-denominated remote cost into the local currency purely using the stored `PricingParameters::exchange_rate` snapshot: [1](#0-0) 

That snapshot is read at message-submission time via `T::PricingParameters::get()` in `validate()`, which is the public, unprivileged, permissionless entry point every user calls indirectly through XCM export to charge the delivery fee: [2](#0-1) 

The module doc explicitly acknowledges the parameters are static between governance updates spaced "every few weeks", with only a fixed `Multiplier` safety margin to absorb rate drift: [3](#0-2) 

The only way to refresh `exchange_rate` on-chain is the root-only `set_pricing_parameters` extrinsic: [4](#0-3) 

The reward paid to relayers on Ethereum is likewise fixed at message-commit time from the same stale snapshot (`pricing_params.rewards.remote`), baked permanently into the committed message: [5](#0-4) 

### Why this is the direct analog, and why it matters

Exactly like `getTimeWeightedAveragePrice()`, the fee/reward calculation here uses a value that is inherently allowed to become stale relative to the real-time ETH/DOT price, and there is no on-chain mechanism analogous to `Pair.current()` to fold in a live price at submission time — the `Multiplier` is a fixed static buffer, not a live correction. If the real ETH/DOT price moves beyond the multiplier's buffer during the (weeks-long) interval between governance updates, any unprivileged user submitting a message via `validate()`/`deliver()` pays a fee computed from the outdated rate. Because the wei-denominated `reward` is baked into the immutable committed message at commit time (`do_process_message`), an underpriced message can become permanently unprofitable for relayers to deliver on Ethereum — the message sits in the committed set indefinitely undelivered, matching the impact-gate category "public underpriced work that ... stalls bridge processing," and the user's paid fee for that message is effectively locked with no service rendered.

This is not caused by a malicious governance actor, relayer, or validator — the flaw is structural: the design has no automated freshness check or fallback (no equivalent of incorporating a live oracle/AMM read), so ordinary, non-adversarial market drift between scheduled governance updates is sufficient to break the fee invariant.

### Title
Outbound-queue message fees use a governance-set `exchange_rate`/`reward` snapshot with no live-price reconciliation, allowing stale pricing to under-fund relayer rewards and stall bridge delivery - (File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs)

### Summary
`OutboundQueue::calculate_fee` and the committed-message reward are both derived solely from the `PricingParameters` storage value, which is refreshed only by an infrequent root-only governance call. Between updates there is no mechanism to reconcile the stored `exchange_rate`/`reward` with the real ETH/DOT market price, mirroring the TWAP staleness flaw in the external report.

### Finding Description
`calculate_fee()` divides the remote (wei) fee by `params.exchange_rate` and multiplies by `params.multiplier` to get the local-currency fee charged to the user; both fields come from a single stored snapshot with no live update path. `do_process_message()` reads the same stale snapshot to fix `reward` and `max_fee_per_gas` permanently into the `CommittedMessage` sent to Ethereum. The only "freshness" mechanism is the fixed `Multiplier` buffer, chosen once by governance and not adjusted in response to real-time volatility, unlike the recommended TWAP fix of folding in `Pair.current()`.

### Impact Explanation
If ETH/DOT market price diverges from the stored `exchange_rate` beyond what `Multiplier` covers (a multi-week window between governance calls), messages committed during that window carry an on-Ethereum `reward` too small to incentivize relayer delivery. These messages can remain undelivered indefinitely — a stalled bridge-processing condition and a de-facto lock of the fee already paid by the user for that message, matching the accepted impact categories for underpriced work and fund lock.

### Likelihood Explanation
This requires no malicious actor — any unprivileged user submitting a bridge message during a period of natural ETH/DOT price drift after a governance update is affected. Likelihood scales with market volatility and the interval between `set_pricing_parameters` calls, both of which are outside the protocol's control once configured.

### Recommendation
Introduce an automated or bounded-staleness check on `PricingParameters.exchange_rate` (e.g., reject/hold fee calculation if the parameters are older than a defined threshold, or source `exchange_rate` from a live DEX/oracle reading at submission time similar to incorporating `Pair.current()`), and consider re-pricing/refunding committed-but-undelivered messages if pricing parameters are later found to have been stale relative to the market during their commit window.

### Proof of Concept
1. Governance sets `PricingParameters{ exchange_rate: 1/400, multiplier: 4/3, rewards.remote: 1 meth, ... }` via `set_pricing_parameters` [6](#0-5) .
2. Weeks pass; real ETH/DOT price rises well beyond the 4/3 buffer (no code path refreshes `exchange_rate` automatically).
3. A user calls the bridge export, which invokes `OutboundQueue::validate` → `calculate_fee(gas_used_at_most, T::PricingParameters::get())`, paying a fee computed off the stale rate [7](#0-6) .
4. `do_process_message` commits the message with `reward = pricing_params.rewards.remote` fixed at the stale rate [8](#0-7) .
5. On Ethereum, `Min(GasPrice, MaxFeePerGas) * GasUsed + Reward` is insufficient at current market conditions, so no relayer submits the message profitably; the message (and the user's paid fee) is permanently stranded until governance updates parameters — too late for already-committed messages.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}
