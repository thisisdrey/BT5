### Title
Unbounded HTTP response body streamed into `tar` process causes disk exhaustion DoS - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
`s.untar` fetches the response body from an attacker/operator-influenced `HttpUrl` and pipes it directly into a `tar -xvf -` subprocess with no `Content-Length` check, no `io.LimitReader`, and no maximum extracted-size enforcement. A malicious or compromised HTTP endpoint can stream an effectively infinite byte stream, causing unbounded disk growth under the target repository's storage path until the storage volume is exhausted.

### Finding Description
In `untar`, the HTTP response body (`rsp.Body`) is passed straight into `command.WithStdin(rsp.Body)` for a `tar` extraction process without any size cap: [1](#0-0) 
There is no `io.LimitReader`, no check of `Content-Length`, and no accounting of extracted bytes/files. The `httpClient`/`httpTransport` configuration only bounds connection timeouts (dial, TLS handshake, response header, idle) but not total body transfer size or duration: [2](#0-1) 
The extraction target is a freshly created repository directory under the storage path via `repoutil.Create`: [3](#0-2) 
The code comment itself acknowledges the trust assumption: "The received archive is trusted *a lot*. Before pointing this RPC at endpoints not under our control, it should undergo a lot of hardening," confirming this is a known, unaddressed gap rather than a validated safe design.

### Impact Explanation
If an endpoint reachable via `HttpUrl` (and, when set, `ResolvedAddress`) is controlled by an attacker or misbehaves, a never-ending tar stream will cause `tar` to keep writing data to the target repository's directory on the storage volume indefinitely, exhausting disk space on that Gitaly storage node. Because Gitaly storages are shared across many repositories/projects, this results in a storage-wide denial of service affecting all tenants using that storage, not just the attacker's own repository.

### Likelihood Explanation
Exploitability depends entirely on whether an unprivileged, ordinary GitLab user can cause Gitaly to invoke `CreateRepositoryFromSnapshot` with an `HttpUrl` value pointing at infrastructure they control. In the codebase as scoped, this RPC's request fields (`HttpUrl`, `HttpAuth`, `ResolvedAddress`) are not shown to be filled from raw, unauthenticated end-user input in this repo — they are typically populated internally by GitLab Rails/Workhorse for repository fork/import/replication flows pointing at Gitaly-internal snapshot endpoints, not arbitrary attacker-supplied URLs. I was unable to fully verify, within the available index, whether any code path lets a normal user directly control the `HttpUrl` field end-to-end without additional validation/allowlisting performed by GitLab Rails before the RPC reaches Gitaly. This is a material precondition gap that could not be confirmed from the Gitaly repo alone.

### Recommendation
Wrap `rsp.Body` in an `io.LimitReader` bounded by a configured maximum snapshot size (and reject/abort early if `Content-Length` exceeds that bound), enforce a maximum extraction time via context deadline, and consider tracking bytes written by `tar` (or post-extraction directory size) to abort and clean up if a configurable threshold is exceeded.

### Proof of Concept
```go
func TestUntar_UnboundedStream(t *testing.T) {
    srv := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // Stream an endless tar-like byte sequence with no Content-Length.
        for {
            if _, err := w.Write(make([]byte, 4096)); err != nil {
                return
            }
        }
    }))
    defer srv.Close()

    tmpDir := testhelper.TempDir(t)
    req := &gitalypb.CreateRepositoryFromSnapshotRequest{HttpUrl: srv.URL}

    // Run s.untar(ctx, tmpDir, req) with a timeout; assert that disk usage
    // under tmpDir grows without bound over time and that no size-limiting
    // mechanism (io.LimitReader around rsp.Body) stops it before hitting
    // an externally imposed timeout/OOM/disk-full condition.
}
```
Expected assertion: absent a fix, disk usage under `tmpDir` (or the process) grows continuously with no cap until the test's own timeout, disk-full, or OOM kills it — demonstrating the missing bound in `s.untar`.
