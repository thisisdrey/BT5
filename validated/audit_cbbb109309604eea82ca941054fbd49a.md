### Title
Denied/banned peers are still discoverable via `/v2/stackerdb/{principal}/{contract_name}/replicas` StackerDB replica listing - (File: stackslib/src/net/db.rs, stackslib/src/net/api/liststackerdbreplicas.rs)

### Summary
The unauthenticated `GET /v2/stackerdb/.../replicas` RPC endpoint is intended to expose only "sensible", currently-usable peer addresses for StackerDB replication. However, the underlying query `PeerDB::find_stacker_db_replicas` selects rows straight from the `frontier` table filtering only on `smart_contract_id`, `network_id`, and `last_contact_time`, with no check of the `denied` (or `allowed`) columns that the rest of the p2p stack uses to decide whether a peer should be trusted/contacted. `RPCListStackerDBReplicasRequestHandler::try_handle_request` post-filters the returned neighbors only for `is_anynet()` and (conditionally) `is_in_private_range()` — it never calls `PeerDB::is_peer_denied` or checks `Neighbor::is_denied()`. This mirrors the Moodle bug class: an entity (a tag / here, a denied peer) that is supposed to be hidden from a "visible listing" surface is still served because the listing code path doesn't apply the same visibility predicate that gates other parts of the system (e.g. `connect_peer_deny_checks` and `can_register_peer` in `stackslib/src/net/p2p.rs`, which do check denial).

### Finding Description
Elsewhere in the codebase, denial is treated as a hard access-control gate: `PeerNetwork::connect_peer_deny_checks` and `PeerNetwork::can_register_peer` in `stackslib/src/net/p2p.rs` explicitly call `PeerDB::is_peer_denied` before connecting to or registering a peer, and `handle_getneighbors` in `stackslib/src/net/chat.rs` sources its neighbor sample from `PeerDB::get_fresh_random_neighbors`, whose SQL query for the non-"always_include_allowed" branch still does not filter by `denied` in the general random-peer path either — but crucially, `find_stacker_db_replicas` has *no* denial filter whatsoever, not even a partial one. [3](#0-2) [4](#0-3) 

Because a peer's `denied` state is set via `PeerDB::set_deny_peer`/CIDR deny rules (used by node operators to ban abusive or malicious peers), this analog breaks the equality that "a denied peer is not exposed as a usable network endpoint." An attacker who is denied (banned) by the local operator, or any third-party peer that the operator has explicitly denied for security reasons, will still appear in the unauthenticated `/v2/stackerdb/{principal}/{contract_name}/replicas` response, letting any remote unauthenticated caller learn that this address participates in the StackerDB set and attempt further probing/attacks toward it — steering other nodes' sync/discovery decisions off the operator-curated peer set.

### Impact Explanation
This is a High-severity issue by the given rubric: it serves non-canonical/filtered state (which should exclude denied peers) as if it were canonical/trusted replica information, potentially steering StackerDB sync clients toward peers the local operator has deliberately blacklisted (e.g. malicious signers or spam contributors), and it leaks the network presence of banned nodes to any unauthenticated remote caller.

### Likelihood Explanation
Likelihood is high: the endpoint is unauthenticated (`security: []` in the OpenAPI spec) and requires no special privileges — any remote client can call `GET /v2/stackerdb/{principal}/{contract_name}/replicas` and immediately observe the gap, since it merely requires that a denied peer has ever handshaked/be present in the local `frontier` table with a recent-enough `last_contact_time`. [5](#0-4) 

### Recommendation
Update `PeerDB::find_stacker_db_replicas` to exclude rows where `denied >= <now>` or `denied < 0` (i.e., apply the same `denied`/CIDR check used in `PeerDB::is_peer_denied`), or alternatively filter the returned neighbor list in `RPCListStackerDBReplicasRequestHandler::try_handle_request` using `PeerDB::is_peer_denied` before returning results, matching the checks already performed in `PeerNetwork::connect_peer_deny_checks` / `can_register_peer`.

### Proof of Concept
1. Operator runs a node and bans a peer P via `deny_nodes` config or RPC, which calls `PeerDB::set_deny_peer`, setting `denied` in the `frontier` table for P. [6](#0-5) 
2. P had previously handshaked and is recorded as replicating some StackerDB contract `SC`.
3. Any unauthenticated remote client sends `GET /v2/stackerdb/{principal}/{SC}/replicas` to the operator's node.
4. `RPCListStackerDBReplicasRequestHandler::try_handle_request` calls `PeerDB::find_stacker_db_replicas`, which returns P's address unconditionally (no `denied` check), and the handler's only filters are `is_anynet()`/`is_in_private_range()`; P is not private/anynet, so its address (and port) is returned in the JSON `naddrs` list. [7](#0-6) 
5. The banned peer P's continued network presence and StackerDB participation is thus disclosed to any unauthenticated caller, despite the operator's explicit denial.

    /// Find out which peers replicate a particular stacker DB.
    /// Return a randomized list of up to the given size, where all
    /// peers returned have a last-contact time greater than the given minimum age.
    pub fn find_stacker_db_replicas(
        conn: &DBConn,
        network_id: u32,
        smart_contract: &QualifiedContractIdentifier,
        min_age: u64,
        max_count: usize,
    ) -> Result<Vec<Neighbor>, db_error> {
        if max_count == 0 {
            return Ok(vec![]);
        }
        let qry = "SELECT frontier.* FROM frontier JOIN stackerdb_peers ON stackerdb_peers.peer_slot = frontier.slot WHERE stackerdb_peers.smart_contract_id = ?1 AND frontier.network_id = ?2 AND frontier.last_contact_time >= ?3 ORDER BY RANDOM() LIMIT ?4";
        let max_count_u32 = u32::try_from(max_count).unwrap_or(u32::MAX);
        let args = params![
            smart_contract.to_string(),
            network_id,
            u64_to_sql(min_age)?,
            max_count_u32,
        ];
        Self::query_peers(conn, qry, args)
    }
