## Analog Found

### Title
`PendingOrder` relayer-reward fees become permanently unrecoverable once the Ethereum light client is halted, with no cancel/refund path in `snowbridge-pallet-outbound-queue-v2` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge V2 outbound queue commits every outgoing message as a `PendingOrder { nonce, fee, block_number }` and only clears it (paying the fee to the relayer) when `submit_delivery_receipt` succeeds. That call's only gate on Ethereum-side proofs is the shared `Verifier::verify`, implemented in `snowbridge-pallet-ethereum-client`, which unconditionally rejects verification whenever the beacon light client is in `Halted` operating mode. There is no other extrinsic, hook, or governance call in the outbound-queue-v2 pallet that can settle, cancel, or refund a `PendingOrder` when the light client is halted, so any order created before (or during) a halt is stuck in storage indefinitely — exactly the "value cannot be returned during exodus/emergency mode" pattern from the external report.

### Finding Description
`do_process_message` inserts a `PendingOrder` carrying the accrued `fee` for every outbound message, keyed by `nonce`: [1](#0-0) 

The only way to resolve (pay out and remove) that order is `process_delivery_receipt`, called from `submit_delivery_receipt`, which first requires `T::Verifier::verify` to succeed: [2](#0-1) [3](#0-2) 

`Verifier::verify` (the shared implementation for both `inbound_queue_v2::submit` and `outbound_queue_v2::submit_delivery_receipt`) unconditionally errors when the beacon client's operating mode is halted — a state entered by governance when it "suspects a compromise (e.g. sync committee takeover)": [4](#0-3) 

The pallet's own test suite confirms the resulting stuck state: while halted, `submit_delivery_receipt` is rejected and the `PendingOrder`'s fee remains untouched in storage: [5](#0-4) 

Crucially, `outbound-queue-v2` exposes no admin/root call to cancel a `PendingOrder`, refund its fee to whoever paid it, or otherwise settle it out-of-band. The pallet's entire `#[pallet::call]` surface is just `submit_delivery_receipt`: [6](#0-5) 
If governance halts the light client permanently (the documented "compromise" scenario — the bridge's own analog of an exit/exodus condition, since the light client can never be safely trusted again without a full re-bootstrap), every outstanding `PendingOrder` fee is frozen forever: it can never be paid to a relayer (verification always fails) and there is no mechanism to unwind or refund it to the party who originally funded the fee. This is structurally identical to the `WITHDRAWAL_STAKE` in the external report: a value earmarked for release only through one gated success path, with no fallback release path for the "mass exit"/halted case.

### Impact Explanation
This is a permanent user-fund/bridge-state lock: relayer reward fees attached to in-flight messages become permanently unreachable once the light client enters a sustained halted state, with no code path to reclaim or redirect them. It aligns with the "permanent user-fund or bridge-state lock" impact category for the Snowbridge BridgeHub scope.

### Likelihood Explanation
Medium: halting the light client is an intended governance safety mechanism used precisely when a compromise is suspected, so it is not attacker-triggerable directly, but it is a realistic operational scenario (as evidenced by the pallet's own `Halted` error variant and dedicated tests), and any messages processed shortly before or during such a halt will carry stuck `PendingOrder` fees with no recovery instrument.

### Recommendation
Add a governance/root-only (or time-locked) extrinsic in `snowbridge-pallet-outbound-queue-v2` to force-resolve or refund `PendingOrders` that remain unresolved after the light client has been halted for longer than a defined grace period, mirroring how other halt-recovery paths (e.g., `safe-mode`'s `force_release_deposit`) allow deposits to be reclaimed even while the protective mode remains active.

### Proof of Concept
1. A message is processed via `do_process_message`, creating `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee, block_number })`.
2. Governance sets the ethereum-client `OperatingMode` to `Halted` (e.g., suspected sync-committee compromise), which is a supported, expected code path, not an attack.
3. A relayer calls `submit_delivery_receipt(origin, event)` with a fully valid proof; `Verifier::verify` still returns `Err(VerificationError::Halted)` per `ethereum-client/src/impls.rs:28`, so `process_delivery_receipt` never runs and the `PendingOrder` is untouched — demonstrated directly by the existing test `poc_m1`: [7](#0-6) 
4. If the halt is never lifted (or lifted only after a lengthy governance process/re-bootstrap), the `PendingOrder`'s fee remains in storage indefinitely with no extrinsic capable of releasing or refunding it — there is no analog to `notarizeSettlement()`'s exodus-fallback in this pallet.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

	fn verify(event_log: &Log, proof: &Proof) -> Result<(), VerificationError> {
		// Refuse to verify any Ethereum-side proof while the beacon light client is halted.
		// Governance halts the light client when it suspects a compromise (e.g. sync committee
		// takeover), at which point any signed headers/receipts must be treated as untrusted.
		// Covers every Verifier consumer, including `inbound_queue_v2::submit` and
		// `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain
		// pending relayer rewards while the bridge is halted).
		ensure!(!Self::operating_mode().is_halted(), VerificationError::Halted);

		Self::verify_execution_proof(&proof.execution_proof)
			.map_err(|e| InvalidExecutionProof(e.into()))?;

// Reward processing must be blocked while the bridge is halted: `submit_delivery_receipt`
// should not pay out `PendingOrder` fees if the verifier reports the bridge as halted.
#[test]
fn poc_m1() {
	new_tester().execute_with(|| {
		let nonce = 1;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_event_proof());

		set_verifier_halted(true);

		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);

		let order_after = PendingOrders::<Test>::get(nonce).expect("order still present");
		assert_eq!(order_after.fee, fee);

		set_verifier_halted(false);
	});
}
