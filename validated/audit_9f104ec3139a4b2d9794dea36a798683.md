### Title
Unbounded array allocation from attacker-controlled length word in TVM precompiled-contract Sapling proof parsers — remote node DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a 32-byte "count" word directly from the precompiled-contract call data and use it, unvalidated, as the size for a Java array allocation (`new byte[len][]`), exactly mirroring the RFC6587 pattern of trusting a sender-supplied size field for allocation with no upper bound.

### Finding Description
These three helper methods parse the length prefix of a dynamic array from the ABI-encoded call data passed to a TVM precompiled contract: [1](#0-0) [2](#0-1) [3](#0-2) 

In each case, `len` is derived from `words[offset].intValueSafe()` — a 256-bit value coerced into an `int` — and is used immediately to size a new array (`new byte[len][]`) with no upper-bound sanity check (unlike, e.g., `ModExp.execute`, which explicitly caps `baseLen/expLen/modLen` against `UPPER_BOUND` at line 698 of the same file: `if (VMConfig.allowTvmOsaka() && (baseLen > UPPER_BOUND ...))`). Because the length word is fully attacker-controlled and independent of the actual physical size of the call data, a caller can set it to a very large value (up to `Integer.MAX_VALUE`), causing the JVM to attempt to allocate an object-reference array of that size (potentially many GB of reference storage) before any subsequent bounds validation occurs. These helpers are invoked from the Sapling shielded-transaction precompiled contracts (`verifyMintProof`, `verifyTransferProof`, `verifyBurnProof`), which parse `spendCount`/`receiveCount` and related array counts out of call data supplied by the caller of the precompile, as seen in the surrounding logic that builds `spendCv`, `rk`, `spendProof`, etc. from these counts: [4](#0-3) 

### Impact Explanation
A crafted call to a Sapling verification precompile with an oversized count word can force the executing node to attempt an outsized heap allocation, throwing `OutOfMemoryError` or causing severe GC pressure/stall on the JVM handling the transaction. Because this runs inside normal TVM execution triggered by any `TriggerSmartContract`/`TriggerConstantContract` request, it can degrade or crash the block-producing/validating node process, denying service to legitimate users — matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
This precompile path is reachable by any unprivileged account that can submit or simulate a smart-contract call (a `TriggerSmartContract` transaction or a constant/read-only call via the JSON-RPC/HTTP `TriggerConstantContract` API) targeting the shielded-transaction precompile addresses. No special privileges, staking, or witness/SR status is required — only the ability to construct call data with an inflated length word ahead of the actual proof bytes.

### Recommendation
Add an explicit upper bound (mirroring the `ModExp.UPPER_BOUND` pattern already used elsewhere in the same file) on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating the resulting arrays, and/or validate that `len` is consistent with the actual remaining length of `data` before allocation.

### Proof of Concept
1. Craft `TriggerSmartContract` (or constant-call) data targeting the Sapling `verifyMintProof`/`verifyTransferProof`/`verifyBurnProof` precompile address, embedding a `spendCount`/`receiveCount` word (e.g., `0x7fffffff`) far larger than the actual accompanying proof bytes.
2. Submit/simulate the call; `extractBytesArray`/`extractSigArray` (or the direct `spendCount`/`receiveCount` usage building `spendCv`, `rk`, `spendProof`, etc.) allocate arrays sized by the attacker-controlled count before any length-vs-data-size validation, triggering excessive memory allocation and potential `OutOfMemoryError` on the node.
