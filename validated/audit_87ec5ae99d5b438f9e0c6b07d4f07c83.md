### Title
Unrestricted caller of `init_global_fee_state` allows front-running to hijack global fee admin/wallet - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The `InitFeeState` instruction, like the vulnerable `initialize` functions described in the external report (`WormholeBridge.sol`, `LayerZeroBridge.sol`, `USX.sol`), has no restriction on who may call it and performs no validation of the supplied parameters before setting critical, permanent protocol state.

### Finding Description
`init_global_fee_state` is documented as a "Runs once per program" instruction that sets the global `FeeState` PDA (seeded solely by the constant `FEE_STATE_SEED`, i.e. one per program deployment). The account list requires only a generic `Signer` as `payer` — there is no admin/authority check restricting who can invoke this instruction: [1](#0-0) 

The handler blindly writes attacker-controlled `admin_key` and `fee_wallet` parameters into the `FeeState` account with zero validation (no zero-address check, no caller check): [2](#0-1) 

Because this is a PDA `init` (fails if the account already exists), whoever calls it first wins permanently — the same "unsafe contract initialization" root cause described in the external report: any unprivileged actor can front-run the legitimate deployer's initialization transaction (which is always visible in the mempool/leader schedule before confirmation) and become the `global_fee_admin`, and set `global_fee_wallet` to an address they control.

`global_fee_admin` set here is subsequently trusted to configure all protocol-wide fee parameters via `edit_fee_state` (program_fee_rate, program_fee_fixed, liquidation_max_fee, bank_init_flat_sol_fee, etc.), with no independent re-validation: [3](#0-2) 

The `global_fee_wallet` set here is also the destination for all bank-add fees, liquidation fees, and order fees across every group and bank created under the program (referenced via `has_one = global_fee_wallet` constraints, e.g. in `PlaceOrder` and `LendingPoolAddBankWithSeed`): [4](#0-3) [5](#0-4) 

### Impact Explanation
If an attacker front-runs the legitimate `init_global_fee_state` call:
- They become `global_fee_admin`, permanently able (via `edit_fee_state`) to set malicious fee parameters (e.g., maximum program fee rate/fixed fee) that are then applied against every group's bank operations program-wide.
- They control `global_fee_wallet`, redirecting all future protocol fee flows (bank-add fees, liquidation fees, order-execution fees) to an address they own — concrete unauthorized fund diversion/theft.
- Because the PDA is unique per program and `init` cannot be repeated, this is a permanent, unrecoverable hijack (no re-initialization path is shown in the codebase other than `edit_fee_state`, which is itself gated by the attacker-controlled admin) — a permanent protocol-wide compromise, not a per-user or per-group issue.

### Likelihood Explanation
Deployment/initialization transactions on Solana are broadcast before confirmation and the PDA address (`["feestate"]`) is fully deterministic and computable by anyone ahead of time, so an attacker monitoring program deployment activity can trivially construct and submit a competing `init_global_fee_state` transaction with higher priority fees. This requires no privileged role — it is a pure front-running/race condition exploitable by any actor, matching the exact bug class in the external report.

### Recommendation
Restrict `init_global_fee_state` to a specific, hardcoded authority (e.g., require `payer` or a dedicated `admin` signer to match the program's upgrade authority or a hardcoded pubkey compiled into the program), and/or validate that `admin_key` and `fee_wallet` are non-default/expected values, mirroring the report's suggested fix of requiring `msg.sender == <specific address>` and non-zero parameter checks. Consider also invoking this instruction atomically during deployment (e.g., within the same transaction as program upgrade finalization) to eliminate the front-running window.

### Proof of Concept
1. Attacker observes/derives the `FEE_STATE_SEED` PDA address for the newly deployed marginfi program (deterministic, requires no special knowledge).
2. Before the legitimate deployer's `init_global_fee_state` transaction confirms, the attacker submits their own `init_global_fee_state(admin_key: attacker, fee_wallet: attacker_wallet, ...)` transaction, referencing the same PDA and using generous fees to be included first.
3. `InitFeeState` account constraints only require a signer as `payer` (see `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs:37-55`) — the attacker's transaction succeeds and permanently sets `fee_state.global_fee_admin = attacker` and `fee_state.global_fee_wallet = attacker_wallet`.
4. The legitimate deployer's transaction now fails (`init` on an already-initialized PDA).
5. Attacker subsequently calls `edit_fee_state` to set maximal fee rates, and all protocol fees for every bank/group created thereafter flow to the attacker's `global_fee_wallet`.
