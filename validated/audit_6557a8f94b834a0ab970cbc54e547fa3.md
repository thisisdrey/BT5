### Title
`liquidate-multi` swallows per-position `liquidate` failures, letting partial state mutations (seized collateral, repaid debt, partial bad-debt socialization) persist without atomic rollback — analog to missing `#[transactional]` on multi-mutation extrinsics - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`liquidate` performs several sequential storage mutations (debt repay, collateral removal, and — when the position has no collateral left — a `fold` over multiple debt assets that individually calls `vault-socialize-debt`, writes `index-cache`, and calls `debt-remove-scaled` for each asset) before an `asserts!` can still fail deep in that sequence. When `liquidate` is invoked directly, a failing assertion aborts the whole transaction and none of the intermediate mutations persist. But `liquidate-multi` calls `liquidate` through `call-liquidate` inside `(map call-liquidate positions)` and wraps the *entire* result in `(ok ...)`, so an internal failure of one position's `liquidate` no longer aborts the top-level transaction. Because Clarity only guarantees automatic rollback at contract-call? boundaries and at the top-level transaction boundary — not for a same-contract function whose error return is caught rather than propagated — every write already committed before the failing `asserts!` (collateral sent to the liquidator, debt-remove-scaled already applied, any already-succeeded per-asset socialization in the `fold`) stays on-chain even though that position's liquidation is reported as failed in the returned list.

### Finding Description
`liquidate` in `mainnet/contracts/market/v0-4-market.clar` [1](#0-0)  executes, in order: `vault-system-repay` (moves real tokens), `debt-remove-scaled` and `collateral-remove` via `contract-call?` to `.v0-market-vault` [2](#0-1) , and, only when the position's collateral is exhausted, a `fold` over the borrower's remaining debt assets calling `socialize-debt-asset` [3](#0-2) . `socialize-debt-asset` itself performs three sequential mutations per asset — a `contract-call?` to socialize debt in the vault, a direct `map-set` on `index-cache`, and another `contract-call?` for `debt-remove-scaled` — and returns an accumulator with `success: false` on the first failure while leaving prior loop iterations' writes intact [4](#0-3) . If the fold's overall `success` flag is false, `liquidate` fails via `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` [5](#0-4) , which normally aborts the whole transaction and rolls back every step above.

`liquidate-multi`, however, calls `liquidate` only through the plain (non-`contract-call?`) helper `call-liquidate` inside `(map call-liquidate positions)`, and wraps the whole map result in `(ok ...)`: `(ok (map call-liquidate positions))` [6](#0-5) . Because the error from an individual `liquidate` call is captured in the returned list rather than propagated with `try!`/`unwrap!` to the top level, the enclosing transaction still returns `ok`. Clarity's automatic write-rollback-on-error only fires at a `contract-call?` boundary (for that specific nested call) or at the outermost transaction boundary — not for an in-contract function call whose `err` is caught and ignored by the caller. Consequently, all mutations `liquidate` already committed before hitting the failing `asserts!` (already-succeeded `contract-call?`s to `.v0-market-vault` for `debt-remove-scaled`/`collateral-remove`, `vault-system-repay`'s token transfer, and any completed prefix of the `socialize-debt-asset` fold, including its direct `index-cache` `map-set`) remain permanently on-chain, while that position is simply reported as a failed entry in the batch's result list.

### Impact Explanation
This produces exactly the storage-corruption pattern the reported bug class describes: a logically single "extrinsic" (one position's liquidation) with multiple sequential storage mutations partially applies and is not rolled back as a unit when invoked through the batch path. Concretely, a borrower can end up with: collateral already fully seized and sent to the liquidator, some debt on one asset already removed and its bad debt already socialized (loss distributed to vault LPs) — while remaining bad debt on other assets is left un-socialized and now permanently uncollateralized (the position has zero collateral, so a follow-up `liquidate` call fails with `ERR-ZERO-LIQUIDATION-AMOUNTS`, and there is no other path to write off that debt). The vault continues to count this unrecoverable debt as a live asset, meaning the protocol silently accrues unresolved bad debt/insolvency risk — this lands squarely in the Critical "protocol insolvency" impact category, reachable by any ordinary principal simply by calling `liquidate-multi` against a borrower whose bad-debt socialization is likely to fail partway (e.g., because one of several debt assets it holds is paused/capped/has an edge condition causing `vault-socialize-debt` or `debt-remove-scaled` to fail for that asset).

### Likelihood Explanation
No privileged role is required — `liquidate-multi` is a public, unprivileged entry point in the core market accounting/liquidation surface explicitly in scope. The only requirement is a borrower position whose bad-debt socialization fails partway through the multi-asset fold (e.g., due to a per-asset pause, cap, or rounding edge case in one of several debt assets), which is realistically triggerable given multiple independent vault contracts each with their own pausability/cap state.

### Recommendation
Ensure `liquidate-multi` (and any other batched entry point calling `liquidate`) treats each position's liquidation as its own atomic unit: invoke `liquidate` via `contract-call?` (or otherwise force each position's mutation set to be checkpointed) so that an internal failure rolls back only that position's writes, or explicitly detect partial socialization failure and revert that position's already-applied mutations before recording it as failed in the batch result.

### Proof of Concept
1. Identify (or construct) a borrower position with debt spread across two or more debt assets and no remaining collateral safety margin.
2. Ensure the vault backing one of the non-primary debt assets is in a state that makes `vault-socialize-debt` (or the subsequent `debt-remove-scaled`) fail for that asset (e.g., a pause flag or cap condition on that vault), while the primary debt/collateral asset for the liquidation succeeds normally.
3. Call `liquidate-multi` with a single position entry targeting this borrower for the asset that will fully consume its collateral.
4. Observe: `vault-system-repay`, `collateral-remove`, and `debt-remove-scaled` for the primary asset all commit (collateral moves to the liquidator, debt removed); the `socialize-debt-asset` fold succeeds for earlier debt assets in the list (socializing their bad debt for real) but fails on the constrained asset, so `liquidate`'s `asserts!` fires and it returns `(err ...)`.
5. Because `liquidate-multi` wraps this in `(ok (map call-liquidate positions))`, the overall transaction succeeds. Query the borrower's remaining debt/collateral and the vault's accounting afterward: collateral is gone, some debt was written off via socialization, but debt on the still-failing asset remains recorded as live/collateralized debt in vault accounting even though the position now has zero collateral to back it — a permanently stuck, uncollateralized debt entry that cannot be liquidated again.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
