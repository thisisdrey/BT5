### Title
Duplicate witness entries in `VoteWitnessContract.votes` are not merged by `VoteWitnessActuator`, allowing per-witness vote-count amplification beyond the intended `MAX_VOTE_NUMBER` cap - (File: actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java)

### Summary
`VoteWitnessActuator#countVoteAccount` appends every entry of the caller-supplied `votes` list directly to `accountCapsule` and `votesCapsule` without deduplicating or merging entries that target the same witness address. This is the same missing-collision-check root cause as the reported Convergence issue: the actuator only enforces an aggregate bound (`sum <= tronPower`) and an array-length bound (`MAX_VOTE_NUMBER`), but never validates that each witness identifier appears only once, so a single transaction can encode the same witness `MAX_VOTE_NUMBER` times.

### Finding Description
In `validate()`, the only checks performed per vote entry are address validity, witness/account existence, and that the running `sum` of vote counts does not exceed the voter's `tronPower`; there is no check preventing the same `voteAddress` from appearing multiple times in `contract.getVotesList()`. [1](#0-0) 

In `execute()` → `countVoteAccount`, the actuator iterates `voteContract.getVotesList()` and calls `votesCapsule.addNewVotes(...)` and `accountCapsule.addVotes(...)` once per list entry, with no merging/aggregation by witness address: [2](#0-1) 

This is notably different from the TVM-native path, `VoteWitnessProcessor`, which explicitly merges duplicate witness entries into a `Map<ByteString, Long>` before writing them (`// merge vote for same witness`) — proving the developers recognized duplicate-collapsing was required, but only implemented it in one of the two code paths that share the same underlying vote-accounting invariant: [3](#0-2) 

As a result, `accountCapsule.getVotesList()` (and the `VotesCapsule` new/old votes lists) can contain multiple separate `Vote` entries for the same witness address instead of one merged entry.

### Impact Explanation
The regression from a "one canonical vote per witness per account" invariant to "possible duplicate entries per witness" undermines downstream logic that assumes `getVotesList()`/`getNewVotes()`/`getOldVotes()` contain at most one entry per witness:
- `MaintenanceManager#countVote` sums `getNewVotes()`/`getOldVotes()` per `VotesCapsule` by witness address into a map, so duplicates for the same witness within a single account's vote list are additively counted (not clobbering), which is not itself an overflow bug on its own since `sum` was already bounded by `tronPower` in `validate()`. However, the missing collision check breaks the `MAX_VOTE_NUMBER` invariant's intent: a user can encode up to 30 (or whatever `MAX_VOTE_NUMBER` is) duplicate entries for a *single* witness, which the docstring/spirit of the cap (spreading power across distinct candidates, bounding per-account list size sent to consensus) does not anticipate, and which was clearly guarded against in the parallel `VoteWitnessProcessor` implementation via explicit merging.
- Because `sum` in `validate()` is computed by simple accumulation over the raw list (not deduplicated first), this is bounded to `tronPower`, so this does not by itself create unbacked voting power beyond the account's real `tronPower`. Given the strict validation rules requiring concrete unauthorized fund theft, freezing, unbacked balance, crash, or key disclosure, I could not establish a concrete high/critical impact beyond a data-model/invariant inconsistency (duplicate `Vote` entries per witness stored on-chain) that differs from the merged-list invariant maintained by the VM path.

### Likelihood Explanation
Any unprivileged account holder can trigger this by broadcasting a normal `VoteWitnessContract` transaction with repeated `vote_address` entries; no special privilege is required, matching the reachable "order placer / signed transaction" surface. The `VoteWitnessActuatorTest#vote1WitnssOneMoreTiems` test in the repo confirms 30 identical vote entries for the same witness are currently accepted and processed: [4](#0-3) 

### Recommendation
Mirror the `VoteWitnessProcessor` merge behavior in `VoteWitnessActuator#countVoteAccount`: aggregate `voteContract.getVotesList()` into a `Map<ByteString, Long>` keyed by witness address before writing to `accountCapsule`/`votesCapsule`, and/or add an explicit `validate()` check rejecting duplicate `voteAddress` entries within a single `VoteWitnessContract`, consistent with the `MAX_VOTE_NUMBER` cap's intent of bounding distinct witness targets.

### Proof of Concept
Using the existing test harness pattern (`getRepeateContract` in `VoteWitnessActuatorTest`), submit a `VoteWitnessContract` with the same `voteAddress` repeated up to `MAX_VOTE_NUMBER` (30) times, each with `voteCount` summing to no more than the account's `tronPower`: [5](#0-4) 
`validate()` passes because the array-length and sum checks are satisfied, and `execute()` stores all 30 duplicate `Vote` entries into `accountCapsule` rather than a single merged entry, unlike the equivalent TVM path which merges them via `voteMap`.

**Caveat:** I was unable to fully confirm, within the tool budget available, whether any other downstream consumer of `AccountCapsule.getVotesList()` (besides `MaintenanceManager#countVote`, which sums correctly regardless of duplication) relies on the "one Vote entry per witness" invariant in a way that would produce a concrete fund-theft/freeze/crash impact; this would require further review of `AccountCapsule#addVotes`/`getVotesList` consumers to establish a High/Critical impact rather than a data-invariant inconsistency.
