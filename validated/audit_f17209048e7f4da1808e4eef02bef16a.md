## Title
Reentrancy guard (`has_in_flight_tx`) in the eth-implicit Wallet Contract can be permanently stuck to `true`, freezing all future actions - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract (used by eth-implicit accounts) implements a manual reentrancy/concurrency guard, `has_in_flight_tx`, to ensure only one Ethereum-emulated transaction is "in flight" at a time [1](#0-0) . The guard is set to `true` before a cross-contract promise chain is dispatched and is only reset to `false` inside the corresponding `#[private]` callback methods [2](#0-1) . Because NEAR rolls back *all* state changes of a receipt if that receipt's execution fails, any panic/failure inside a callback (even after the line that resets the flag) discards the flag reset together with the rest of the failed execution, leaving `has_in_flight_tx` stuck at `true` forever and permanently locking the account out of `rlp_execute`.

### Finding Description
`rlp_execute` refuses to start a new transaction while `has_in_flight_tx == true`, and each helper (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`) resets the flag to `false` as its very first executed statement before doing further work with promise results [3](#0-2) [4](#0-3) [5](#0-4) .

However, in NEAR's receipt execution model a failed action receipt causes a full rollback of that receipt's state changes: *"a receipt whose result is Err triggers `state_update.rollback()`, so no state changes persist except the outcome/gas accounting"* [6](#0-5) . This means the order of statements inside the callback function body does not matter for durability — if the callback panics or runs out of prepaid gas anywhere during its execution (e.g., while deserializing an attacker-influenced `PromiseResult`, or because the target contract's own execution/return payload makes the callback exceed its allotted static gas), the entire callback receipt fails and *every* state mutation performed in it — including the earlier `self.has_in_flight_tx = false` — is discarded.

Each callback's static gas budget is a small fixed constant (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) [7](#0-6) , computed independently of the untrusted `target`/token contract's behavior. Callbacks such as `nep_141_storage_balance_callback` deserialize a `StorageBalance` JSON value returned by an arbitrary, user/relayer-specified `token_id` contract [8](#0-7) , and `address_check_callback` deserializes a response from the registrar lookup without first checking `promise_results_count` [9](#0-8) . If the counterparty contract returns a payload that is more expensive to process than budgeted (oversized/malformed JSON, or simply enough logging/return data to make the callback exceed prepaid gas), the callback receipt fails, and `has_in_flight_tx` reverts back to `true` permanently, since there is no other code path that ever resets it.

Once stuck, `rlp_execute` unconditionally rejects every future call with `"transaction already in progress, please try again later."` [10](#0-9) , and there is no admin/recovery method to clear the flag. This is confirmed by the contract's own test asserting the guard blocks concurrent calls [11](#0-10)  — the test only exercises the intended concurrency-rejection path, not the failure/rollback path that leaves the guard permanently set.

### Impact Explanation
Because the wallet contract is the sole execution gateway for the eth-implicit account (all outgoing actions, including plain NEAR transfers, must go through `rlp_execute`), a permanently stuck `has_in_flight_tx` flag permanently freezes the user's ability to move funds or execute any action from that account — effectively a permanent freeze of funds under this account, satisfying the "permanent freezing of funds" impact category.

### Likelihood Explanation
Triggering the bug requires the account owner (or a relayer acting on their behalf) to submit a transaction whose `target` is an untrusted or malicious contract (e.g., a spoofed ERC-20/NEP-141 token or a target whose `FunctionCall` action produces expensive/oversized output), which then causes the fixed-gas callback to fail. This is a plausible interaction pattern for eth-implicit accounts doing ERC-20-style transfers to arbitrary token contracts, and does not require any privileged access — a hostile counterparty contract chosen as `target`/`token_id` is enough to brick the caller's wallet.

### Recommendation
Do not rely on statement ordering within a single receipt to guarantee `has_in_flight_tx` is reset; a receipt-wide rollback on failure defeats that assumption. Instead:
- Reset the guard from a dedicated, low/fixed-cost path that is guaranteed to succeed regardless of the deserialization/processing outcome of promise results (e.g., check `promise_results_count`/`PromiseResult` status first and short-circuit before doing any additional gas-variable work), and/or
- Increase and bound callback gas budgets independent of the untrusted counterparty's response size, and defensively fail closed with a minimal amount of logic before touching `has_in_flight_tx`.
- Add an explicit recovery/unlock mechanism (e.g., only callable by the account owner or via a timeout) to clear a stuck `has_in_flight_tx` flag.

### Proof of Concept
1. Register an eth-implicit account and add a relayer key restricted to `rlp_execute`, as in `create_rlp_execute_tx`/`test_wallet_contract_interaction` [12](#0-11) .
2. Deploy a malicious "token" contract implementing `storage_balance_of` that returns a payload engineered to make JSON deserialization in `nep_141_storage_balance_callback` exceed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (e.g., deeply nested or oversized JSON within receipt size limits).
3. Submit an RLP-encoded `ERC20Transfer`-emulated Ethereum transaction via `rlp_execute` targeting this malicious token contract; `inner_rlp_execute` sets `has_in_flight_tx = true` and schedules `storage_balance_of(...).then(nep_141_storage_balance_callback(...))` [13](#0-12) .
4. When the callback executes and exceeds its prepaid gas while deserializing the malicious response, the callback receipt fails and its state changes (including the `has_in_flight_tx = false` reset) are rolled back per the NEAR execution model [6](#0-5) .
5. Any subsequent call to `rlp_execute` on this account now unconditionally returns `"transaction already in progress, please try again later."` indefinitely, permanently freezing the account.
