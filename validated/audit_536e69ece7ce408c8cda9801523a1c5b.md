### Title
Floor-rounded resource usage estimate in `DelegateResourceActuator`/`DelegateResourceProcessor` allows delegating more BANDWIDTH/ENERGY than a frozen balance actually backs - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`validate()` in `DelegateResourceActuator` (and its TVM native-contract twin `DelegateResourceProcessor.validate()`) computes how much of an account's already-used bandwidth/energy is attributable to `FrozenV2` balance by casting a `double` computation to `long`, which truncates toward zero (floor) instead of rounding up. This underestimates "used" resource, which inflates the computed "available to delegate" capacity (`frozenV2Balance - v2Usage`), letting a user delegate more BANDWIDTH/ENERGY than their FrozenV2 stake actually backs — the same rounding-direction class of bug as the MetaMorpho `supplyCap` report, where under-rounding a "used/consumed" quantity lets a limit check be bypassed.

### Finding Description
In `DelegateResourceActuator.validate()`: [1](#0-0) 

the account's bandwidth usage is scaled to a FrozenV2-equivalent amount via:
```
long netUsage = (long) (accountNetUsage * TRX_PRECISION * ((double)
    (dynamicStore.getTotalNetWeight()) / dynamicStore.getTotalNetLimit()));
long v2NetUsage = getV2NetUsage(ownerCapsule, netUsage, this.disableJavaLangMath());
if (ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance) {
  throw new ContractValidateException(...);
}
```
The `(long)` cast on a positive double truncates toward zero, i.e. it always rounds **down** `netUsage`/`v2NetUsage`. The same pattern is used for ENERGY: [2](#0-1) 

Exactly analogous logic — reachable via a TVM native contract call (the `delegateresource` precompile), not just an externally signed `DelegateResourceContract` — exists in: [3](#0-2) 

This is the security-relevant analog of the MetaMorpho bug: in MetaMorpho, `supplyAssets` (a "used" quantity subtracted from a cap) is rounded down, letting `toSupply` overestimate the room left under `supplyCap`. Here, `v2NetUsage`/`v2EnergyUsage` (also a "used" quantity subtracted from the FrozenV2 balance to get "room left to delegate") is rounded down via truncating cast, letting `delegateBalance` pass validation even when the true available (unused) FrozenV2 balance is smaller. The cap being protected is the invariant that delegated BANDWIDTH/ENERGY must be backed 1:1 by the account's own non-consumed FrozenV2 stake.

### Impact Explanation
If the check under-detects real resource usage, an account can successfully delegate BANDWIDTH/ENERGY (`execute()` immediately moves the amount into `DelegatedFrozenV2Balance...` and reduces `FrozenV2Balance...` — see execute path) for an amount that exceeds what its actual (rounded-up) usage would allow. Because the receiver's `AcquiredDelegatedFrozenV2Balance...` is increased by the full `delegateBalance` and the network's `TotalNetWeight`/`TotalEnergyWeight` accounting assumes resource is properly backed by frozen TRX, this can result in resource (bandwidth/energy) being granted to a receiver that is not actually backed by unused frozen stake — an unbacked-balance condition for network resource accounting. Because bandwidth/energy translate directly into free transaction/contract-execution capacity, this can be leveraged to consume network resources (or serve as underpriced smart-contract execution capacity) beyond what the delegator's real stake supports.

### Likelihood Explanation
The trigger requires only an ordinary signed `DelegateResourceContract` transaction (or equivalently a smart-contract call into the `delegateresource` TVM native/precompiled contract), reachable by any account with `FreezeBalanceV2` stake and some level of prior resource usage — no privileged role, no malicious SR/witness assumption needed. The magnitude of the rounding error is generally small per call (bounded by the fractional part lost in the double→long truncation, scaled by `TRX_PRECISION`/weight ratio), so a single call typically only marginally exceeds the true cap; exploitation to a materially significant degree would likely require repeated/crafted calls tuned to usage windows to accumulate the discrepancy, which lowers immediate severity even though the code path itself is straightforwardly reachable.

### Recommendation
Round the computed usage (`netUsage`/`energyUsage`, and their `v2NetUsage`/`v2EnergyUsage` derivatives) **up**, not down, before subtracting from the FrozenV2 balance, mirroring the MetaMorpho fix of rounding the subtracted quantity up so that the resulting "room available" value is conservative (rounded down). Concretely, replace the truncating `(long) (... )` cast with a ceiling computation (e.g. `Math.ceil` before casting, or perform the multiplication/division in integer/BigInteger arithmetic with explicit `divideCeil` as already used elsewhere in the codebase, e.g. `RepositoryImpl.divideCeil`/`divideCeilExact`) in both `DelegateResourceActuator.validate()` and `DelegateResourceProcessor.validate()` (and correspondingly in `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`, which use the same formula for the public "max delegatable size" API and should stay consistent, even though that path itself is only a query and not itself an enforcement check).

### Proof of Concept
Conceptual sequence (cannot be executed in this read-only review, but derivable directly from the code):
1. Freeze TRX for BANDWIDTH via `FreezeBalanceV2Contract` to obtain `FrozenV2BalanceForBandwidth = F`.
2. Consume bandwidth over time so that the *true* (mathematically rounded-up) FrozenV2-equivalent usage would be `U_true`, but the floor-truncated `(long)` cast in `DelegateResourceActuator.validate()` computes `U_floor < U_true` (any fractional double result between two integers exhibits this).
3. Submit `DelegateResourceContract` with `delegateBalance = F - U_floor` (which passes the check `F - U_floor >= delegateBalance`), even though the true remaining unused balance is `F - U_true < delegateBalance`.
4. `execute()` moves `delegateBalance` from `FrozenV2BalanceForBandwidth` into `DelegatedFrozenV2BalanceForBandwidth`, and grants the receiver `AcquiredDelegatedFrozenV2BalanceForBandwidth += delegateBalance`, exceeding what the owner's actual unused stake supports — the delegated/acquired total across both accounts is now backed by less real frozen TRX than the protocol assumes.
