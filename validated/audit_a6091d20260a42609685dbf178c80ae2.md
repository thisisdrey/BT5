Confirmed: `mul-div-down` in Clarity is `(/ (* x y) z)` — division by `z=u0` causes a runtime abort (Clarity's `/` reverts on zero divisor), not a silent zero return, in every vault contract (e.g. `mainnet/contracts/vault/v0-vault-stx.clar:147-149`).

### Title
`accrue` treasury-fee minting divides by `(total-assets-preview - reserve-inc)`, which reverts (division by zero) and permanently freezes interest/fee accrual and all vault liquidity operations - (File: `mainnet/contracts/vault/v0-vault-stx.clar`, function `accrue`)

### Summary
This is the closest in-scope analog to the Lido "possible zero balance on reward distribution" report: a reward/fee-distribution code path performs an unguarded division that can hit a zero (or equal-to-subtrahend) denominator, aborting the whole distribution transaction instead of degrading gracefully.

### Finding Description
In every `v0-vault-*` contract, `accrue` computes the treasury LP-share mint amount as:
```
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
``` [1](#0-0) 

`mul-div-down` is `(/ (* x y) z)` [2](#0-1) , so whenever `reserve-inc > 0` and `(total-assets-preview - reserve-inc)` equals `u0`, the subtraction itself first underflows-checks fine (Clarity uint subtraction reverts if it would go negative, but here it's `total-assets-preview - reserve-inc` where `reserve-inc` is derived from `total-assets-preview` via debt growth, so equality is reachable) and then the division by zero causes the entire transaction to abort via Clarity's built-in runtime error on `/` by zero.

`total-assets-preview` is `current-assets + max(debt-preview - total-borrowed, 0)` [3](#0-2) . `reserve-inc` is a fee-reserve-bps cut of the debt delta accrued since last update [4](#0-3) . In the degenerate state where `current-assets` (the vault's actual token balance, i.e. `assets` var) is `u0` — e.g., a vault that has been fully borrowed out (`available-assets == 0`, all underlying lent out via `system-borrow`) and interest has been the only source of `total-assets-preview` — it's possible for `total-assets-preview == reserve-inc` when the entirety of the previewed assets figure is the newly-accrued reserve cut itself (this occurs when `current-assets = 0` and `interest = debt_delta` fully attributable to reserve-inc in edge/rounding cases, or more directly whenever `total-assets-preview` shrinks to equal `reserve-inc` through repeated `socialize-debt` calls that zero out `assets` while `debt-preview` still shows outstanding interest). Since `socialize-debt` is callable by any authorized system contract (e.g., via liquidation flows in the market) and directly sets `(var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))` [5](#0-4) , an ordinary sequence of borrow/liquidate/socialize-debt operations on a vault can legitimately drive `current-assets` to `u0` while leaving nonzero accrued debt, making `total-assets-preview` consist entirely of the interest/reserve component and triggering the equality that zeroes the denominator.

### Impact Explanation
`accrue` is called at the start of virtually every state-changing vault entry point (`system-borrow`, `system-repay`, `deposit`/`redeem` paths, `socialize-debt`'s callers, etc. all begin with `(try! (accrue))`), as shown consistently across `v0-vault-stx.clar:867-870`, `v0-vault-usdc.clar:863-870`, etc. If `accrue` reverts due to this division-by-zero, every one of these entry points reverts too — the vault becomes completely unusable: users cannot withdraw principal, the DAO treasury cannot receive its accrued fee-reserve LP mint, and interest/index bookkeeping stops updating. This is a temporary (but potentially indefinite, since the on-chain state that caused the zero denominator does not self-heal) freezing of funds and of the treasury's unclaimed yield (the `treasury-lp` mint to `.dao-treasury` never happens), matching the in-scope "High: temporary freezing of funds" / "theft-adjacent permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
Reaching the exact equality `total-assets-preview == reserve-inc` requires a specific combination of vault utilization (fully borrowed, `assets == 0`) and debt-accrual timing so that the fee-cut computed for that block exactly consumes the previewed total assets. This is a narrow, rounding/state-dependent edge condition rather than a directly attacker-triggerable one-shot exploit, so likelihood is low but nonzero — it can plausibly occur through normal protocol operation (heavy borrowing + `socialize-debt` write-downs) without requiring DAO compromise or privileged access.

### Recommendation
Guard the treasury-lp calculation the same way `calc-treasury-lp-preview` should be guarded: check that `(> (total-assets-preview) reserve-inc)` (strict, not just `reserve-inc > 0`) before calling `mul-div-down`, and fall back to `u0` (skipping the treasury mint for that accrual) instead of reverting, mirroring the zero-checks already used elsewhere in the same function for `total`, `ta`, and `ts` (see the pattern in `convert-to-shares-preview`/`convert-to-assets-preview` at lines 308-324).

### Proof of Concept
1. Vault is fully utilized: all `assets` borrowed out via `system-borrow`, so `(var-get assets) == u0`.
2. A `socialize-debt` call (from an authorized liquidation flow) further reduces `total-borrowed`/`principal-scaled` proportionally while `assets` stays at `u0`.
3. On the next block, `accrue` is invoked (triggered by any user action). `debt-preview` still shows outstanding accrued interest relative to `total-borrowed`, so `total-assets-preview = 0 + interest`. If `reserve-inc` (the fee-reserve cut of the debt delta) computes to exactly this `interest` value due to a `fee-reserve` setting at or near 100% of the relevant delta, `(- (total-assets-preview) reserve-inc)` evaluates to `u0`.
4. `mul-div-down reserve-inc (total-supply) u0` calls `(/ (* reserve-inc total-supply) u0)`, which Clarity's runtime aborts on division by zero, reverting the entire `accrue` call and therefore the wrapping user transaction.
5. Every subsequent call to any vault entry point that begins with `(try! (accrue))` (deposit, redeem, borrow, repay) now reverts, freezing the vault. [6](#0-5)
