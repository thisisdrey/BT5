### Title
Stake-weighted QoS uses raw QUIC-measured RTT (a single, peer-manipulable data point) to size `max_concurrent_uni_streams`, allowing stream-limit inflation - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`SwQos::cache_new_connection` derives the per-connection concurrent-stream budget from `connection.rtt()`, a live, unauthenticated measurement that the remote peer directly influences by delaying its ACKs. This is structurally the same bug class as the reported `slot0` issue: a single "spot" read of a value that can be freely manipulated by the party being measured is fed straight into a security/allocation decision, with no averaging, bounding by trusted data, or sanity cross-check against the peer's actual stake-derived entitlement.

### Finding Description
`compute_max_allowed_uni_streams_with_rtt` computes the number of concurrent unidirectional streams granted to a staked QUIC peer: [1](#0-0) 

The stream count is first bounded by the peer's stake ratio (clamped to `[QUIC_MIN_STAKED_CONCURRENT_STREAMS, QUIC_MAX_STAKED_CONCURRENT_STREAMS]`), but is then scaled up by a "BDP scaling" factor derived from `rtt_millis`, uncapped after that multiplication: [2](#0-1) 

`rtt_millis` is taken directly from `connection.rtt()` in `cache_new_connection`, right before it is used to set `max_concurrent_uni_streams` on the connection: [3](#0-2) 

`Connection::rtt()` (quinn) reflects the QUIC-stack's smoothed round-trip-time estimate, which is derived from how quickly the peer acknowledges packets. A client fully controls when (or whether) it sends ACKs, so it can artificially delay acknowledgment of the server's packets to inflate its own measured RTT before/while the connection is admitted. There is no validation, smoothing across multiple samples, or cross-check against the peer's stake that would prevent this — the value is read once, at connection-admission time, exactly like the single-block `slot0` read in the reported Uniswap issue.

### Impact Explanation
Because the final scaling step (`streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS)) / REFERENCE_RTT_MS`) is applied after the stake-based clamp and is itself unclamped, a peer that fakes a high RTT (up to `MAX_RTT_MS = 350`) instead of a low one (`REFERENCE_RTT_MS = 50`) can obtain up to ~7x more concurrent uni-streams than the stake-weighted design intends (e.g., from a stake-clamped `QUIC_MAX_STAKED_CONCURRENT_STREAMS = 512` up to ~3584). This is a QoS evasion: a minimally-staked, unprivileged remote peer can grab a disproportionate share of the TPU QUIC streamer's per-connection stream budget relative to their actual stake, undermining the fairness guarantee that stake-weighted QoS is designed to enforce, and increasing per-connection resource consumption (buffers/streams) on the validator beyond what that peer's stake should be priced for.

### Likelihood Explanation
Any remote peer establishing a QUIC connection to the TPU (`transactions_quic_sockets`) or TPU-forward port goes through `SwQos::cache_new_connection` on connection admission, so the path is reachable by any unprivileged network peer with even minimal recorded stake (this logic only applies to `ConnectionPeerType::Staked`, but the stake-ratio gate that would otherwise reclassify very-low-stake peers as `Unstaked` only bounds the *base* stream count — the RTT multiplier is applied afterward and is not similarly gated). Manipulating perceived RTT by delaying ACKs is a well-understood, low-effort client-side technique against RTT-based estimators; no cryptographic or protocol-level safeguard in this code prevents it.

### Recommendation
Do not use a single instantaneous `connection.rtt()` sample as an unbounded multiplier on the granted stream budget. Either (a) cap the final scaled result to the same stake-derived bound used before scaling (`QUIC_MIN_STAKED_CONCURRENT_STREAMS..QUIC_MAX_STAKED_CONCURRENT_STREAMS`) rather than letting the RTT term escape that clamp, or (b) base the scaling on a smoothed/verified RTT signal (e.g., server-side round-trip measurement independent of peer-controlled ACK timing, or an average over multiple connections/samples) rather than trusting the QUIC stack's peer-influenced RTT estimate outright.

### Proof of Concept
1. Stand up the TPU QUIC listener with `spawn_stake_weighted_qos_server` and a `StakedNodes` table containing the attacker's pubkey with a small but non-zero stake (enough to pass the `min_stake_ratio` check in `build_connection_context`, i.e., not reclassified to `Unstaked`). [4](#0-3) 
2. From the client, intentionally delay ACKs to the server (e.g., configure/patch the QUIC client to withhold ACK-eliciting responses) so that the server-observed `connection.rtt()` approaches `MAX_RTT_MS` (350 ms) instead of a realistic LAN/WAN RTT (< `REFERENCE_RTT_MS` = 50 ms).
3. On connection admission, `cache_new_connection` reads this inflated RTT and calls `compute_max_allowed_uni_streams_with_rtt`, producing a `max_uni_streams` value up to ~7x higher than the value a truthful RTT would have produced, which is then applied via `connection.set_max_concurrent_uni_streams(max_uni_streams)`. [5](#0-4) 
4. The attacker now opens streams up to this inflated limit, consuming disproportionately more of the TPU streamer's per-connection stream capacity than their stake entitles them to, at the expense of honest higher-stake peers competing for the same `QUIC_TOTAL_STAKED_CONCURRENT_STREAMS` budget.

// that seems to maximize TPS on GCE (higher values don't seem to

pub const QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS: u32 = 128;
pub const QUIC_MIN_STAKED_CONCURRENT_STREAMS: u32 = 128;

// Set the maximum concurrent stream numbers to avoid excessive streams.
// The value was lowered from 2048 to reduce contention of the limited
// receive_window among the streams which is observed in CI bench-tests with
// forwarded packets from staked nodes.
pub const QUIC_MAX_STAKED_CONCURRENT_STREAMS: u32 = 512;

pub const QUIC_TOTAL_STAKED_CONCURRENT_STREAMS: u32 = 100_000;

/// RTT after which we start BDP scaling
const REFERENCE_RTT_MS: u32 = 50;

/// Above this RTT we stop scaling for BDP
const MAX_RTT_MS: u32 = 350;

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
