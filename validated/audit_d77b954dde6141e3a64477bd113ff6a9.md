### Title
Inbound handshake key-rotation lacks signature verification against the newly claimed public key - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_handshake` only calls `message.verify_secp256k1(&handshake_data.node_public_key)` when `self.connection.get_public_key()` is `None` (chat.rs:1058-1070). Once a public key is already bound to the connection (`Some(_)` branch, chat.rs:1072-1091), the only check performed is an address/port equality check, and that check is gated on `self.stats.outbound` — for inbound connections it does nothing at all. `update_from_handshake_data` (chat.rs:1131-1167) then unconditionally calls `self.connection.set_public_key(Some(pubk.clone()))` using whatever `node_public_key` is embedded in the new `HandshakeData`, without ever verifying that *this* message was signed by that new key.

### Finding Description
The broken equality: "authenticated" (the message envelope was validly signed) is checked against the **currently bound key** (`self.connection.get_public_key()`), not against the **newly claimed key** (`handshake_data.node_public_key`). The code assumes these are the same identity, but on a key-rotation Handshake they are not.

Exploit flow on one inbound `ConversationP2P`:
1. Attacker connects inbound, sends Handshake #1 signed by `key1`, claiming `node_public_key = key1`. `self.connection.get_public_key()` is `None`, so `validate_handshake` takes the `None` branch and calls `verify_secp256k1(&key1)`, which succeeds. `update_from_handshake_data` binds the connection to `key1`.
2. Attacker sends Handshake #2 on the *same* connection, still signed by `key1` (so the message-level signature check that produces `authenticated=true` succeeds against the already-bound `key1`), but sets `handshake_data.node_public_key = key2` (a different key it may not even control the private key for beyond formatting it validly).
3. `handle_handshake` passes `authenticated=true`, so the `disable_inbound_handshakes` guard at chat.rs:1221 is irrelevant/bypassed as designed.
4. `validate_handshake` now takes the `Some(_)` branch (chat.rs:1072-1091). Since the connection is inbound, `self.stats.outbound` is `false`, so the entire address-check condition short-circuits to false — no check is performed on `key2` at all. The only remaining checks are format validity, non-staleness, and "not equal to our own local key" — none of which prove the attacker possesses `key2`'s private key.
5. `update_from_handshake_data` sets `self.connection.set_public_key(Some(key2))` (chat.rs:1164), rebinding the conversation's authenticated identity to `key2` even though the actual signed bytes were produced with `key1`.

This breaks the intended invariant that a connection's bound public key always corresponds to a key that has produced a verified signature over some message on that connection.

### Impact Explanation
This is an authentication/identity-binding bypass on the P2P inbound path: an attacker who has completed one handshake can rebind their `ConversationP2P`'s recognized identity to an arbitrary `node_public_key` without proving ownership of the corresponding private key. Downstream logic that trusts `self.connection.get_public_key()` / the conversation's peer identity (e.g. neighbor bookkeeping, StackerDB replica identification, peer-info exposed via RPC, banning/allow-listing decisions keyed on pubkey hash) can now be fed a spoofed identity for an already-open, "authenticated" socket. This matches the Critical "auth bypass" category: unauthenticated write of identity state that other node logic treats as verified.

### Likelihood Explanation
Preconditions are default and cheap: `disable_inbound_handshakes=false` (default), and the attacker only needs to open one inbound TCP connection and send two Handshake messages, both signed with a key it actually controls (`key1`); the second message's claimed `node_public_key` field (`key2`) can be any syntactically valid Secp256k1 public key, non-expired. No privileged role, secret, or victim key is required — fully remote, unprivileged, and repeatable per-connection.

### Recommendation
In `validate_handshake`'s `Some(cur_pubk)` branch, always verify `message.verify_secp256k1(&handshake_data.node_public_key)` when `handshake_data.node_public_key != cur_pubk`, regardless of inbound/outbound, before allowing `update_from_handshake_data` to rebind the connection's public key. The address/port check should be an *additional* constraint for outbound peers, not a substitute for signature verification of the new key.

### Proof of Concept
Rust test in `stackslib/src/net/chat.rs` test module:
1. Build a `ConversationP2P` for an inbound connection (`stats.outbound = false`).
2. Construct Handshake #1 signed with `key1`, `node_public_key = key1`; call `handle_handshake(..., authenticated=true, ...)`. Assert `self.connection.get_public_key() == Some(key1)`.
3. Construct Handshake #2 with `node_public_key = key2` (different keypair), but sign the outer `StacksMessage` with `key1` (simulating the pre-existing authenticated session), call `handle_handshake(..., authenticated=true, ...)`.
4. Assert that `self.connection.get_public_key()` is currently patched to `Some(key2)` after step 3 (demonstrates the bug) — the correct/fixed behavior should reject this with `net_error::InvalidMessage`/`InvalidHandshake` because the message was not actually signed by `key2`, i.e. `message.verify_secp256k1(&key2)` was never checked in the `Some(_)` branch.
