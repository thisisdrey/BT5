### Title
`CreateRepositoryFromSnapshot` extraction path lacks the symlink/traversal validation enforced in the equivalent `extractTarToDirectory` extractor - (File: `internal/gitaly/service/repository/create_repository_from_snapshot.go`)

### Summary
Gitaly implements two functionally equivalent "extract an incoming tar archive into a repository directory" code paths. One of them, `extractTarToDirectory` (used by `ReplicateRepository`'s snapshot extraction), validates every tar entry — regular files, hard links, and especially symlinks — to ensure the resolved target stays within the destination directory before writing anything to disk. The other, `untar` (used by the `CreateRepositoryFromSnapshot` RPC), pipes the exact same class of untrusted, attacker-suppliable archive directly into the system `tar` binary with **no path or symlink validation at all**, and the code explicitly acknowledges this via source comment.

### Finding Description
`extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go` carefully validates path-traversal and symlink escape for every entry type before allowing writes: [1](#0-0) 

By contrast, `untar` in `internal/gitaly/service/repository/create_repository_from_snapshot.go`, which is invoked from the `CreateRepositoryFromSnapshot` RPC handler, fetches an archive from an attacker/caller-controlled `HttpUrl` and streams it directly into the OS `tar -C <path> -xvf -` command with zero validation of entry names, hard-link targets, or symlink targets: [2](#0-1) 

The RPC handler itself performs no additional sanitation of the archive content before or after extraction — it only validates the destination repository path, not the archive's internal entries: [3](#0-2) 

The code comment even flags this gap explicitly: "the received archive is trusted *a lot*... it should undergo a lot of hardening" — confirming the extraction path was never hardened the way the sibling `extractTarToDirectory` implementation was, despite serving the identical purpose (populating a repository directory from an untrusted tar stream).

This is the same bug class as the external report: one code path (`Inch_Module` / `extractTarToDirectory`) fully validates a resource before use, while a sibling code path (`Bera_Module` / `untar`) performing the analogous operation omits the validation, creating an inconsistent security boundary reachable from ordinary RPC input (`HttpUrl`).

### Impact Explanation
Because extraction is delegated to the system `tar` binary without any symlink/absolute-path/`..`-traversal filtering, a malicious or compromised HTTP endpoint referenced by `HttpUrl` (attacker-controlled or subject to SSRF/response tampering) can supply a tar archive containing:
- Absolute-path entries or `../` traversal sequences that write files outside the intended repository directory.
- Symlink entries pointing outside the destination, which subsequent regular-file entries in the same or later archive processing could then write through, escaping the repository storage root.

This can result in files being written to arbitrary locations on the Gitaly storage node, i.e., a storage escape / arbitrary file write via archive extraction, which is far more severe than "objects get stuck" — it violates repository storage isolation entirely.

### Likelihood Explanation
`CreateRepositoryFromSnapshot` is a Gitaly RPC that accepts `HttpUrl`, `HttpAuth`, and `ResolvedAddress` fields directly from the caller (crafted RPC field), and the destination path is determined by Gitaly (`repositoryFullPath`), not the caller — but the archive content is fetched from a caller-specified URL and extracted unfiltered. Any caller able to invoke this RPC (e.g., during repository import/fork/replication flows) with a URL under their control, or able to influence/intercept the response to that URL (SSRF/MITM-like data poisoning of the response body only, not the transport), can trigger the unfiltered extraction. Given the existing self-documented "trusted a lot" comment, this is a known, reachable weakness in a production RPC handler.

### Recommendation
Replace the raw `tar -C path -xvf -` invocation in `untar` (`internal/gitaly/service/repository/create_repository_from_snapshot.go`) with the same Go-based, validated extraction routine used by `extractTarToDirectory` in `internal/gitaly/service/repository/replicate.go` (or a shared helper), enforcing:
- Rejection of absolute paths and `..`-traversal in entry names.
- Verification that resolved symlink and hard-link targets remain within the destination directory.
before any file is written to disk.

### Proof of Concept
Conceptually mirroring the external report's PoC pattern (validate one side, not the other):
1. Stand up an HTTP server that serves a tar stream containing an entry such as `Linkname: ../../../../etc/cron.d/malicious` via `tar.TypeSymlink`, followed by a regular file entry that writes through that symlink.
2. Call `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at that server.
3. Because `untar` calls raw `tar -xvf -` with no symlink/traversal filtering (unlike `extractTarToDirectory`, which explicitly tests and rejects this exact scenario as shown in `internal/gitaly/service/repository/replicate_test.go` lines 850-884), the extraction proceeds and writes outside the intended repository directory — whereas the equivalent `ReplicateRepository` snapshot path would reject it with `"symlink target escapes extraction directory"`. func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}

func (s *server) CreateRepositoryFromSnapshot(ctx context.Context, in *gitalypb.CreateRepositoryFromSnapshotRequest) (*gitalypb.CreateRepositoryFromSnapshotResponse, error) {
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository, storage.WithSkipRepositoryExistenceCheck()); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	if err := repoutil.Create(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, repository, func(repo *gitalypb.Repository) error {
		path, err := s.locator.GetRepoPath(ctx, repo, storage.WithRepositoryVerificationSkipped())
		if err != nil {
			return structerr.NewInternal("getting repo path: %w", err)
		}

		// The archive contains a partial git repository, missing a config file and
		// other important items. Initializing a new bare one and extracting the
		// archive on top of it ensures the created git repository has everything
		// it needs (especially, the config file and hooks directory).
		//
		// NOTE: The received archive is trusted *a lot*. Before pointing this RPC
		// at endpoints not under our control, it should undergo a lot of hardening.
		if err := s.untar(ctx, path, in); err != nil {
			return structerr.NewInternal("extracting snapshot: %w", err)
		}

		return nil
	}); err != nil {
		return nil, structerr.NewInternal("creating repository: %w", err)
	}
