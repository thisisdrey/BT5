### Title
Housekeeping scheduling timer resets on "pending" state even when the optimization heuristic performs no work, allowing unauthenticated write RPCs to indefinitely stall repository maintenance - (File: internal/grpc/middleware/housekeeping/middleware.go)

### Summary
`Middleware.scheduleHousekeeping` in `internal/grpc/middleware/housekeeping/middleware.go` tracks per-repository write activity and decides when to run `OptimizeRepository` based on an RPC-count "timer" (`writeCountAtLastRun`) similar in structure to the reward-rate "last update" timestamp in the reported `MultiFeeDistribution._notifyUnseenReward` bug: a cheap, attacker-controlled action can reset the timer used to gate a beneficial background action, even though the actual condition that action addresses never gets resolved.

### Finding Description
`pendingOperations` computes, per operation type (`OpRepackRefs`, `OpRepackObjects`, `OpPruneObjects`, `OpWriteCommitGraph`), whether the number of writes since the last run exceeds `RPCInterval`: [1](#0-0) 

When the threshold is crossed, `scheduleHousekeeping` immediately marks **all** pending operations as having just run — by writing the *current* `writeCount` into `writeCountAtLastRun[op]` — before `OptimizeRepository` has actually executed or determined whether any real work is needed: [2](#0-1) 

The actual decision of whether to repack/prune/write-commit-graph is delegated to `SelectiveOptimizationStrategy`, which only restricts operations to `enabledOps`, then internally consults `HeuristicalOptimizationStrategy`'s heuristics (loose-object counts, packfile counts, time-since-last-full-repack, etc.): [3](#0-2) 

Because `writeCountAtLastRun[op]` is stamped at *scheduling* time rather than after confirming real optimization work happened, the RPC-interval countdown restarts on every trigger regardless of outcome. An unprivileged client that can send any mutator RPC (`OpMutator`, e.g. `WriteRef`, or any push/write RPC) against a target repository can keep the RPC counter oscillating around the threshold, repeatedly resetting `writeCountAtLastRun` for every operation type and effectively pushing the "last run" baseline forward on each trigger. This starves the actual housekeeping run and the repository is left with unbounded accumulation of loose objects, stale packfiles, and un-repacked references — a very close structural analog to the reported `_notifyUnseenReward`/`rewardPerSecond` dust-griefing bug where a cheap, low-cost external stimulus repeatedly resets a state variable (`periodFinish` / `lastUpdateTime`) that governs when a beneficial recalculation should occur, permanently deferring the intended effect.

Additionally, `scheduleHousekeeping` returns early without doing anything if housekeeping is already `active` for a repository (`if a.active { return }`), and `writeCount` still increments during that window — this means the timer bookkeeping design already assumes counters march forward under attacker influence via ordinary write traffic, since `writeCount` has no cap and no per-client attribution.

### Impact Explanation
An attacker who repeatedly issues low-cost mutator RPCs (e.g. `WriteRef`, small commits, or ref updates) against a repository they can write to can indefinitely delay `OptimizeRepository` invocations for that repository by keeping `writeCountAtLastRun` freshly reset relative to `writeCount`, without ever letting the interval margin grow large enough that a "forced" scheduling with real heuristic evaluation actually results in a repack/prune. Over time this leads to unbounded growth of loose objects, un-pruned stale objects, and fragmented packfiles/reflog structures — a denial-of-service on repository maintenance that degrades read/fetch/clone performance and increases storage usage, without requiring any privileged access or specific external conditions.

### Likelihood Explanation
Any actor with write access to a repository (an ordinary contributor, or, on forks/CI-driven push flows, potentially any user who can trigger mutator RPCs) can perform this at negligible cost using standard git operations, entirely through the normal push/write path — no crafted payloads, race conditions, or privileged roles are needed. This mirrors the "no external conditions, low-cost, high-impact griefing" profile that elevated the original finding to High severity.

### Recommendation
Set `writeCountAtLastRun[op]` only after `OptimizeRepository` has actually confirmed (via the heuristic strategy) that the corresponding optimization ran or determined no work was needed, rather than at scheduling time. Alternatively, track "writes observed since last actual optimization outcome" using a monotonically advancing baseline that is only updated post-hoc based on real heuristic results (loose object count, packfile count, etc.), so that repeatedly triggering scheduling without resolving the underlying condition cannot indefinitely reset the interval countdown.

### Proof of Concept
1. Configure `RPCInterval` for `OpRepackObjects` (e.g., default 20) and observe `writeCount`/`writeCountAtLastRun` behavior in `pendingOperations`/`scheduleHousekeeping`.
2. Simulate a repository where loose objects accumulate slowly with each write RPC (e.g. via `WriteRef` calls that also touch the object store, or ordinary small pushes).
3. Issue mutator RPCs at intervals timed to always land just past `RPCInterval` writes since the last scheduling trigger; each time, `scheduleHousekeeping` fires, immediately sets `writeCountAtLastRun[OpRepackObjects] = writeCount` (per code at lines 364-367), and dispatches `OptimizeRepository`, but the heuristic strategy may find that, e.g., `LooseObjects.Count` is still under `LooseObjectLimit` and elect not to repack.
4. Because the timer has already been reset regardless of whether repacking actually occurred, the next repack opportunity is deferred another full `RPCInterval` writes — repeat indefinitely to keep the repository from ever being optimized while loose objects/packfiles continue to accumulate from ordinary write traffic.
5. This can be verified against the existing test scaffolding in `internal/grpc/middleware/housekeeping/middleware_test.go` (e.g. `TestIndependentOperationThresholds`) by asserting that `writeCountAtLastRun` advances on every threshold-crossing call to `scheduleHousekeeping` even when `mockHousekeepingManager.OptimizeRepository` is stubbed to perform no actual optimization work. // pendingOperations returns operations that have exceeded their RPC interval thresholds.
func (m *Middleware) pendingOperations(a *activity, force bool) []config.OperationType {
	var pending []config.OperationType

	for _, op := range allOperations {
		thresholds := m.getThresholds(op)
		lastRun := a.writeCountAtLastRun[op]
		writesSinceLastRun := a.writeCount - lastRun

		if force || writesSinceLastRun > thresholds.RPCInterval {
			pending = append(pending, op)
		}
	}

	return pending
}
