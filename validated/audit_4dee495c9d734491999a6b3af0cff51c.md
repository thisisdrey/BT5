### Title
Dust transfers permanently fill a victim's token lists to `MAX_TOKENS_PER_USER`, DoS-ing deposits, transfers, borrows and collateral top-ups - ([File: contracts/Pool.sol])

### Summary
The `Pool` tracks per-account deposit/debt tokens in two `MappedEnumerableSet.AddressSet` lists (`depositTokensOfAccount`, `debtTokensOfAccount`) capped by the constant `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Any `DepositToken` balance change from `0` pushes the token into the recipient's list via `Pool.addToDepositTokensOfAccount`, and the modifier `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once the combined list size reaches 30 (`contracts/Pool.sol:143-148`, `contracts/Pool.sol:216-220`). `DepositToken.transfer`/`transferFrom` have no opt-in — any EOA can push dust deposit-token balances to an arbitrary victim, populating the victim's list without consent. Once at the cap, every action that would add a new entry for the victim reverts, causing a state-transition DoS analogous to the crafted-input crash of CVE-2017-6441: a cheap, attacker-controlled input (dust transfer) forces all subsequent legitimate state changes for that account to revert.

### Finding Description
- `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` are invoked by `DepositToken`/`DebtToken` whenever a balance transitions `0 → >0`, and are guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)` (`contracts/Pool.sol:204-220`).
- `DepositToken.transfer(to_, amount_)` is permissionless and only checks `unlockedBalanceOf(sender)` — nothing restricts the `to_` address or requires it to opt in (`contracts/DepositToken.sol:348-354`). `_transfer` mints the balance to `to_` and calls `pool.addToDepositTokensOfAccount(to_)`.
- Attack path: the attacker deposits dust (e.g., `1 wei`) into every listed collateral `DepositToken` (and every listed `DebtToken` via issuing dust debt) and transfers a dust amount to the victim. Each dust transfer adds one entry to `depositTokensOfAccount[victim]`. With ~30 collateral/debt tokens a victim's combined list hits the cap.
- Consequences for the victim:
  - `DepositToken.deposit` for any *new* collateral type reverts inside `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`. A victim who needs to add a different collateral to restore health before liquidation cannot — the position becomes unrescuable and is force-liquidated (`Pool.liquidate`, `contracts/Pool.sol:537-596`).
  - `DebtToken.issue`/`mint` for any new synthetic asset reverts (`contracts/DebtToken.sol:235-271`).
  - Incoming `transfer`s/`seize`s of deposit tokens the victim does not yet hold revert, breaking `Pool.liquidate` when the liquidator is also saturated, and any contract-mediated flows (Operator.execute, gateways) that mint to a saturated recipient.
- The victim can evict a dust token only by transferring/withdraw-ing its full balance back to 0 (`Pool.removeFromDepositTokensOfAccount`, `contracts/Pool.sol:630-634`), but the attacker can re-top dust cheaply and front-run evictions, making the DoS persistent.

### Impact Explanation
Temporary-to-persistent freezing of user funds and forced loss: a victim saturated with dust entries cannot deposit new collateral to cure an unhealthy position, cannot open new debt, and cannot receive deposit tokens of types not already held. If the account is at or near the liquidation threshold, the block on collateral top-ups directly converts into seized collateral and liquidation-fee loss. Cost to the attacker is a few wei per token across ≤30 tokens plus gas; no privileged role is needed.

### Likelihood Explanation
High feasibility: it requires only public entry points (`DepositToken.deposit` + `transfer`, or `DebtToken.issue`) and dust amounts. Effectiveness depends on the pool listing enough distinct deposit/debt tokens to reach 30 entries; the cap is a shared bound across both lists, so each list only needs partial saturation. Recovery is possible but race-able, so the freeze is at least temporary and can be renewed indefinitely.

### Recommendation
- Do not revert in `onlyIfAdditionWillNotReachMaxTokens` when the token is already in the set (the current code is fine here — the revert only applies to new entries; instead apply the cap only to *net-new* additions and allow `remove`+`add` in the same tx), and/or raise/remove the cap by moving health computation to iterate over the pool's global token lists with balance checks instead of per-account sets.
- Alternatively, only add an account to the list via `deposit`/`issue` initiated by the account itself (record list membership on first interaction rather than on any incoming `transfer`), so dust `transfer`s cannot populate it.

### Proof of Concept
Hardhat-style sketch (full test not executed in this review):

```ts
// Given: pool with deposit tokens D1..D30 (or mix of deposit+debt tokens)
// Victim already holds e.g. msETH deposit (1 entry used).
const attacker = alice
const victim = bob

for (const dt of depositTokens) {
  // deposit dust and push 1 wei of the msd token to the victim
  await underlying.mint(attacker.address, 1)
  await underlying.approve(dt.address, 1)
  await dt.deposit(1, attacker.address)
  await dt.transfer(victim.address, 1) // adds entry to victim's list
}

// Victim's list is now at MAX_TOKENS_PER_USER (30).
// 1) Victim cannot deposit a *new* collateral type:
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 2) If victim's position turns unhealthy, topping up collateral in a new
//    token is impossible -> forced liquidation by a third party succeeds.
await pool.connect(liquidator).liquidate(msUsd.address, victim.address, repayAmt, victimCollateral.address)

// 3) Incoming transfers of un-held deposit tokens to the victim revert:
await expect(
  someOtherDepositToken.transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
