## Analysis

The CVE describes a length-validation gap: a private/optional-field length is not accounted for during header validation, so downstream parsing code trusts other fields to be present and reads past the validated bounds. The closest reachable analog in java-tron is in the `ValidateMultiSign` precompiled contract, which parses attacker-controlled TVM calldata using nested offset/length words without validating that those internal offsets stay within the decoded word array.

### Title
Unvalidated nested offset/length fields in `ValidateMultiSign` precompile allow out-of-bounds array access from contract calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign.execute()` only validates the *overall* ABI shape of its input via `isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)`, added as a TIP‑854 hardening guard [1](#0-0) . This check confirms only that total calldata length matches `header_words + n*item_words`; it does **not** validate the *internal* offset/length words that `extractBytesArray`/`extractSigArray` subsequently dereference [2](#0-1) [3](#0-2) .

### Finding Description
`extractBytesArray` computes `bytesOffset` and `bytesLen` directly from attacker-supplied `DataWord` values inside the `words` array and then reads `data` at `(bytesOffset + offset + 2) * WORD_SIZE` for `bytesLen` bytes, with no check that `offset + bytesOffset + 1` is within `words.length`, or that `bytesLen` fits inside `data` [2](#0-1) . `extractSigArray` has the same pattern using a fixed `SIG_LENGTH` copy [3](#0-2) .

In `ValidateMultiSign.execute`, this extraction call sits **outside** the method's only `try { ... } catch (Throwable t)` block, which wraps solely the permission/weight computation loop [4](#0-3) . So an `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` thrown from `extractBytesArray`/`extractSigArray` (lines 1072–1074) is unhandled by `execute()` itself. This is structurally the same class of bug as the GUE issue: an overall-length/shape check passes, but a nested length/offset field that the following code implicitly assumes is well-formed is never validated, so parsing proceeds into invalid memory ranges.

By contrast, the sibling `BatchValidateSign` precompile explicitly wraps its entire `doExecute` call in `try/catch (Throwable t)` and returns a safe default `Pair.of(true, new byte[WORD_SIZE])` [5](#0-4) , showing the defensive pattern that `ValidateMultiSign` lacks around its extraction step.

### Impact Explanation
This precompile is reachable by any contract deployer or caller via a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompiled address with fully attacker-controlled calldata — no privileged role is required. If the resulting exception is not caught somewhere higher in the TVM call/interpreter loop, it could interrupt VM execution of the containing block in unexpected ways; at minimum it produces an uncontrolled exception path in consensus-critical code that other precompiles in the same file explicitly guard against.

### Likelihood Explanation
High reachability (any account can invoke a precompiled contract from a deployed contract), but the ultimate severity depends on how the outer TVM/`Program` exception handling treats a `RuntimeException` escaping `PrecompiledContract.execute()`. I was not able to fully trace that top-level exception handling within the available tool budget — the relevant call site (`Program.callToPrecompiledAddress`-style dispatch) could not be located/read in this session, so I cannot confirm whether this results in mere transaction revert (lower impact) versus a broader node-level fault.

### Recommendation
Add explicit bounds validation in `extractBytesArray` and `extractSigArray` (verify `offset + bytesOffset + 1 < words.length` and `bytesLen`/`SIG_LENGTH` fit within `data.length`) before performing the `arraycopy`/`Arrays.copyOfRange`, and wrap the extraction calls in `ValidateMultiSign.execute` in the same defensive `try/catch (Throwable)` pattern already used by `BatchValidateSign`.

### Proof of Concept
Not fully constructible without confirming the outer VM exception-handling behavior; conceptually, calldata crafted so that `words[3]` (or the offset word inside the sig-array header) points to an index near `words.length`, causing `words[offset + i + 1]` in `extractBytesArray`/`extractSigArray` to throw `ArrayIndexOutOfBoundsException` when `ValidateMultiSign` is invoked via a contract call.

**Note on confidence**: Given I could not verify the outer exception-handling path (`Program.java` content was not indexed/available), this finding should be treated as a code-quality/robustness gap with a plausible but unconfirmed DoS-class impact rather than a fully proven critical vulnerability. I recommend a Devin session with full filesystem access to trace the exact call path from `OperationActions` → `Program` → `PrecompiledContracts.execute()` to confirm exception propagation behavior before treating this as consensus-critical.
