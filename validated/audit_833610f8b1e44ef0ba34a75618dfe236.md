## Analysis

The Solana report's core broken invariant is: **a user-supplied destination is used in a value-transfer instruction without validating that it can actually receive the value, and the record of "already paid/settled" is finalized before or independently of that transfer actually landing at a valid destination — so funds can become permanently stuck with no way to retry.**

The closest verified local analog is in the Snowbridge relayer-reward claim flow on BridgeHub.

### Flow

`claim_rewards_to` lets any signed relayer claim their accrued reward to an arbitrary, unvalidated `beneficiary`: [1](#0-0) 

`do_claim_rewards` removes the reward from storage and calls `PaymentProcedure::pay_reward`. Because this happens inside `try_mutate_exists`, the removal is only reverted if `pay_reward` returns an `Err` — i.e. reward removal is treated as final the instant `pay_reward` returns `Ok(())`: [2](#0-1) 

For `BridgeReward::Snowbridge`, the beneficiary is a `Location` (wrapped in `BridgeRewardBeneficiaries::AssetHubLocation`), only version-checked, never checked for resolving to an actual receivable account: [3](#0-2) 

The actual payment is `PayAccountOnLocation::pay_reward`, which builds an XCM containing `ReserveAssetDeposited` + `DepositAsset { beneficiary, .. }` and sends it to AssetHub. It returns `Ok(())` as soon as the message is **delivered**, not once the remote `DepositAsset` has actually succeeded: [4](#0-3) 

### Why existing guards don't stop it

- `Location::try_from(VersionedLocation)` in `bridge_common_config.rs` only validates the XCM *version*, not whether the location is a valid, existing, receivable account on AssetHub (e.g., it could be a `Location` with no `AccountId32`/`AccountKey20` junction, or one whose implied account can't hold the asset because it's below existential deposit, or lacks the sufficient/trust configuration for the reserve-deposited asset).
- `pay_reward` on BridgeHub only checks `validate_send` and `deliver` succeeded locally — it has no way to know, and doesn't wait to know, whether the remote `DepositAsset` on AssetHub actually executes successfully.
- Because `do_claim_rewards` commits the reward removal on `Ok(())` from `pay_reward`, and `pay_reward` returns `Ok(())` purely based on local delivery success, the relayer's reward entry is permanently deleted from `RelayerRewards` **before** it is known whether the beneficiary can actually receive the minted asset.
- If the remote `DepositAsset` instruction fails on AssetHub (invalid/unreceivable beneficiary location), the reserve-deposited asset is trapped in the XCM executor's asset-trap registry there, and the relayer has no straightforward path to reclaim it through the reward-claim flow — the reward is gone from `RelayerRewards`, and recovering trapped assets normally requires governance/root-level `claim_assets`, not something the relayer can do themselves.

This mirrors the report's exact bug class: an unvalidated destination is used for a value-moving instruction, and the "settled" bookkeeping (removal of `RelayerRewards` entry) is finalized on a success condition (local delivery) that is weaker than the real success condition (remote receipt), leading to a fund-loss/lock path from an entirely unprivileged, self-inflicted (but plausible, e.g. malformed tooling or an unsupported Location shape) or attacker-crafted beneficiary.

### Title
Snowbridge relayer reward is deleted from storage before remote `DepositAsset` to beneficiary is confirmed, permanently losing reward on invalid/unreceivable beneficiary `Location` - (File: `bridges/snowbridge/primitives/core/src/reward.rs`, `bridges/modules/relayers/src/lib.rs`)

### Summary
`claim_rewards_to` allows a relayer to supply an arbitrary `Location` beneficiary for `BridgeReward::Snowbridge`. The reward accounting entry is removed from `RelayerRewards` as soon as `PayAccountOnLocation::pay_reward` returns `Ok(())`, which only reflects successful local XCM delivery, not successful remote asset deposit on AssetHub.

### Finding Description
`do_claim_rewards` ( [5](#0-4) ) takes the reward out of storage and only restores it if `pay_reward` errors. `PayAccountOnLocation::pay_reward` ( [6](#0-5) ) treats `XcmSender::deliver` success as final success, even though the constructed XCM's last instruction, `DepositAsset { beneficiary, .. }`, executes asynchronously on AssetHub and can fail there for reasons entirely determined by the caller-supplied `beneficiary` (unsupported junction structure, non-existent/non-sufficient account, etc.), none of which are validated on BridgeHub before commit.

### Impact Explanation
A relayer's accrued cross-chain reward can be permanently and irrecoverably erased from on-chain accounting while the corresponding minted asset is trapped on AssetHub, unreachable through the normal reward-claim path. This is a permanent user-fund-lock condition directly reachable by any registered relayer through a public extrinsic (`claim_rewards_to`), with no privileged actor involved.

### Likelihood Explanation
Any relayer that has accrued a reward can call `claim_rewards_to` with a `BridgeRewardBeneficiaries::AssetHubLocation` value that is a syntactically valid, version-compatible `Location` but does not correspond to a receivable account (e.g., missing/incorrect final junction, or a location that AssetHub's `AssetTransactor`/`DepositAsset` filter rejects). No special privileges, front-running, or malicious infrastructure are required — only crafting an unusual `Location` value, which is easy given the public, permissionless nature of the call.

### Recommendation
Do not remove/finalize the `RelayerRewards` entry based solely on local XCM delivery success. Either (a) validate that `beneficiary` resolves to a well-formed, receivable account (e.g., contains a supported `AccountId32`/`AccountKey20` junction under a network/parachain this beneficiary type supports) before accepting `claim_rewards_to`, mirroring how the audited fix required `fee_destination` to be a validated `TokenAccount` bound to the correct mint, or (b) make the reward settlement conditional on confirmation of successful remote execution (e.g., via a receipt/ack mechanism) rather than on local delivery alone, restoring the reward on remote failure.

### Proof of Concept
1. Accrue a `BridgeReward::Snowbridge` reward for a relayer account on BridgeHub (via normal message-delivery reward registration).
2. Call `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(some_location))` where `some_location` is a version-valid `Location` that does not correspond to a receivable account on AssetHub (e.g., an interior structure without an `AccountId32`/`AccountKey20` junction, or one AssetHub's asset transactor won't accept for the reserve-deposited Ether asset).
3. On BridgeHub: `Location::try_from` succeeds, `pay_reward` succeeds (XCM validated and delivered), and `RelayerRewards` entry is deleted — `RewardPaid` event emitted.
4. On AssetHub: the XCM executes `ReserveAssetDeposited` then `DepositAsset` targeting the invalid beneficiary; `DepositAsset` fails, and the asset is trapped rather than credited to any usable account.
5. The relayer's reward is now unrecoverable through the reward pallet; recovering it requires a governance-level `claim_assets`/trapped-asset recovery mechanism, which the relayer cannot self-serve.

			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,

			RelayerRewards::<T, I>::try_mutate_exists(

						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;

						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
