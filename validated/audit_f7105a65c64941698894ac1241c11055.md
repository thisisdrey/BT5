Based on my investigation, I found a concrete local analog in the Snowbridge outbound-queue-v2 delivery receipt handling.

### Title
Relayer reward paid out regardless of Ethereum delivery outcome, ignoring `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`Pallet::process_delivery_receipt`, invoked from the public `submit_delivery_receipt` extrinsic, decodes a `DeliveryReceipt` (which carries a `success: bool` field reflecting whether the message dispatch succeeded on Ethereum) but never reads or checks that field before paying out the relayer reward. [1](#0-0)  This mirrors the reported bug class: a value that is supposed to gate execution of critical logic (here, the payout) is silently never consulted, so the payout path executes unconditionally instead of only after successful settlement.

### Finding Description
`DeliveryReceipt` is decoded from the `InboundMessageDispatched(nonce, topic, success, reward_address)` Ethereum event log, and explicitly contains a `success` field describing whether the relayed message was actually executed successfully on Ethereum. [2](#0-1) 

The dispatchable `submit_delivery_receipt` verifies the Merkle/receipt proof and decodes the log into a `DeliveryReceipt`, then calls `process_delivery_receipt`: [3](#0-2) 

`process_delivery_receipt` only validates the gateway address and looks up the `PendingOrder` by nonce; it never checks `receipt.success` before paying the reward and removing the order: [4](#0-3) 

Existing guards (`ensure!(T::GatewayAddress::get() == receipt.gateway, ...)`, `PendingOrders::<T>::get(nonce).ok_or(...)`) only bind the *nonce* and *gateway*, not the delivery outcome. Because `success` is decoded straight from the on-chain-verifiable Ethereum event and is a completely legitimate field of the event (it is emitted by the real Gateway contract whether the dispatched command succeeded or reverted on the Ethereum side), an unprivileged relayer can submit a valid proof for a delivery event where `success == false` and still collect `order.fee`, since the reward branch is gated only by `order.fee > 0`, not by `receipt.success`.

This breaks the pivot requirement that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — settlement (reward registration + `PendingOrders` removal) advances even when execution (the Ethereum-side dispatch) did not succeed.

### Impact Explanation
This is a public, unprivileged-entrypoint bug (`submit_delivery_receipt` can be called by any signed account) that results in a bridge reward payout that is not conditioned on the underlying settlement actually succeeding. This falls under "duplicate settlement or payout" / "public underpriced work that ... stalls bridge processing," since relayers are incentivized to always report/settle receipts regardless of the real outcome, decoupling the fee economics from actual message delivery.

### Likelihood Explanation
The bug is triggered by data an ordinary relayer legitimately possesses (a valid Ethereum receipt with `success:false`, which occurs naturally when a `Command` reverts on Ethereum, e.g. due to insufficient gas or contract-side revert). No malicious peer, admin, governance, or validator collusion is required — only a real Ethereum event with `success:false`, which is a normal occurrence, not an attacker-crafted proof.

### Recommendation
Add an explicit `ensure!(receipt.success, Error::<T>::DeliveryFailed)` (or equivalent branch) in `process_delivery_receipt` before registering the reward, or otherwise define distinct handling (e.g., no reward, or reduced reward) for failed deliveries, so the `success` flag actually gates settlement.

### Proof of Concept
1. A relayer sends a message that is committed via `do_process_message`, creating a `PendingOrder { nonce, fee, .. }`. [5](#0-4) 
2. The message is delivered to the real Gateway contract on Ethereum but the dispatched command reverts (e.g., insufficient gas at the destination), causing the Gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any relayer submits `submit_delivery_receipt` with a valid proof of this real event.
4. `process_delivery_receipt` verifies the proof, looks up the order by nonce, and — because it never inspects `receipt.success` — calls `T::RewardPayment::register_reward(...)` and removes the `PendingOrder`, paying the full fee despite the failed delivery. [6](#0-5)

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
