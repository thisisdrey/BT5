### Title
Unauthenticated frontier hijack via self-reported handshake address in outbound re-key path - ([File: stackslib/src/net/chat.rs])

### Summary
When a node has an OUTBOUND conversation and the peer sends a handshake with an upgraded public key, `handle_handshake` re-keys the peer DB using the address fields taken from the attacker-supplied `HandshakeData` (`handshake_data.addrbytes`/`port`) rather than the connection's actually-dialed address. Because `PeerDB::update_peer` (invoked via `Neighbor::save_update`) is keyed only on `(network_id, addrbytes, port)`, an attacker who is dialed outbound by the victim node can claim a different, already-known peer's address in the handshake payload and overwrite that peer's stored `public_key`/`expire_block_height` with their own key.

### Finding Description
`ConversationP2P::update_from_handshake_data` unconditionally stores the self-reported address fields from the wire message into connection state: [1](#0-0) 

`handle_handshake` then, for outbound conversations whose key changed, calls `Neighbor::load_and_update`/`save_update` using this same attacker-supplied `handshake_data` (not the connection's verified `self.peer_addrbytes`/`self.peer_port`, i.e. the address the node itself dialed): [2](#0-1) 

`Neighbor::save_update` writes straight through to `PeerDB::update_peer` with no re-validation of the target row's prior key: [3](#0-2) 

The root cause is that the guard `self.stats.outbound` is intended to assert "we know this address is authentic because we dialed it ourselves," but the code path never actually uses the dialed address — it substitutes the self-declared `handshake_data.addrbytes/port` when constructing the `NeighborKey` used for the DB write. An attacker who gets dialed outbound by the node (e.g., by being gossiped/discovered as a candidate neighbor) can present a valid signature over their own real key (satisfying `validate_handshake`) while declaring an unrelated victim address/port in the handshake payload. This breaks the intended invariant that a frontier row's `public_key` only changes in response to a handshake actually originating from that row's address.

### Impact Explanation
This is an unauthenticated write to `PeerDB` frontier state: an attacker can overwrite the stored `public_key` and `expire_block_height` of an arbitrary existing peer entry (any address/port the node has previously learned and later dials), substituting the victim's identity with the attacker's key. Since PeerDB entries feed neighbor-walk peer selection and StackerDB replica lookups, this lets the attacker hijack a victim peer's identity from the node's perspective, poisoning future outbound connection targets and StackerDB replica trust decisions. This matches the "Critical: unauthenticated/unauthorized write to state" category.

### Likelihood Explanation
Preconditions: the attacking node must be dialed outbound by the victim node (achievable by advertising itself so it gets added to the node's frontier/walk candidates — no privileged role needed), it must complete a valid handshake with its own real keypair, and it must know of an address/port tuple already present in the target's frontier to target for overwrite (obtainable by gossip/`GetNeighbors`). No secrets or special roles are required; the attack is repeatable on each re-handshake.

### Recommendation
Build the `NeighborKey` used in the outbound re-key path (`Neighbor::load_and_update`) from the connection's verified dialed address (`self.peer_addrbytes`/`self.peer_port`), not from the self-reported `handshake_data.addrbytes`/`port`. Additionally, `PeerDB::update_peer`'s WHERE clause should be constrained to also match the row's existing `public_key` (or equivalently, callers should verify the existing row's key matches the previously-authenticated key for that address before allowing an overwrite).

### Proof of Concept
1. Set up a `PeerDB` with a pre-existing frontier row for victim `(network_id, addr_V, port_V, pubkey_V)`.
2. Establish an outbound `ConversationP2P` (`self.stats.outbound = true`) from the node to attacker-controlled address `addr_A:port_A`.
3. Attacker sends a `Handshake` with a valid signature under attacker's real key `pubkey_A`, but `HandshakeData.addrbytes/port` set to `addr_V:port_V`.
4. Call `handle_handshake`; observe `update_from_handshake_data` returns `updated = true`, triggering `Neighbor::load_and_update(&tx, ..., &handshake_data)` and `save_update`.
5. Assert `PeerDB::get_peer(conn, network_id, &addr_V, port_V).public_key == pubkey_A` (overwritten from `pubkey_V`), proving the victim's frontier row was hijacked by an unrelated connection.
