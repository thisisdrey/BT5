## Analysis

The reported bug class — an unbounded-cost cleanup routine that a single call must fully complete, with no cap on the amount of accumulated state it processes — maps to Gitaly's `DeleteRefs` RPC, specifically the `ExceptWithPrefix` code path.

### Title
Unbounded reference enumeration and deletion in a single `DeleteRefs` RPC causes handler-level resource exhaustion - (File: `internal/gitaly/service/ref/delete_refs.go`)

### Summary
`DeleteRefs` accepts an `ExceptWithPrefix` filter that causes the handler to load **every** reference in the repository and then iterate over the resulting (unbounded) list to validate, delete, and vote on each one — all inside a single synchronous RPC call with no pagination, batching, or size cap.

### Finding Description
When `req.GetExceptWithPrefix()` is set (and `req.GetRefs()` is empty), `refsToRemove` calls `repo.GetReferences(ctx)` to fetch the complete set of references in the repository, then appends every reference that doesn't match an excluded prefix into `refs`, with no upper bound: [1](#0-0) 

That unbounded `refnames` slice is then iterated multiple times in the same request: once to validate each ref name, once to call `updater.Delete(ref)` for every entry, and again to feed each ref name into a cumulative vote hash — none of which have a size limit: [2](#0-1) 

The RPC is a unary `MUTATOR`, not a stream, even though the underlying working set (all refs in a repo) is exactly the kind of "repeated collection that can grow without limit" that Gitaly's own RPC-development conventions say must be streamed: [3](#0-2) 

Because Git repositories routinely accumulate large numbers of refs over time through ordinary, unprivileged activity (branches, tags, CI pipeline refs, merge-request refs, keep-around refs, etc.), an attacker or ordinary caller does not need to submit a large request payload — a tiny request (`{"except_with_prefix": ["zzz/"]}`) is enough to force the server to enumerate and process however many references already exist on disk. This directly parallels the `onUninstall()` bug: a function meant to complete unconditionally as part of a request/lifecycle event has cost proportional to attacker-influenced accumulated state rather than to the size of the current call.

### Impact Explanation
A single `DeleteRefs` call against a repository with a very large ref count can consume unbounded CPU, memory (the `refnames`, `invalidRefnames`, and vote-hash buffers), and wall-clock time on the Gitaly node handling the request, tying up a request-handling goroutine and the `updateref` transaction for the whole duration. In a multi-tenant Gitaly/Praefect deployment this is a denial-of-service vector against the RPC handler: the request may exceed configured RPC timeouts, hold locks/transactions open, or in the worst case make the operation impossible to complete within any practical resource budget — mirroring the "impossible to ever succeed" characteristic called out in the original report.

### Likelihood Explanation
Any client authorized to call `RefService.DeleteRefs` (a standard `MUTATOR` RPC, reachable from ordinary repository-management flows such as branch/ref cleanup) can trigger this with a minimal, well-formed request as long as the target repository has accumulated a large number of references — a condition that is common and can itself be grown by an ordinary, unprivileged user over time by creating many refs (branches, MR refs, pipeline refs) before issuing the `ExceptWithPrefix` deletion.

### Recommendation
Bound the amount of work performed per `DeleteRefs` call: enforce a maximum number of references processed (rejecting or paginating on `ExceptWithPrefix`), and/or convert the RPC to a streaming design consistent with Gitaly's own rule that unbounded/repeated results must not be handled in a single unary message. Alternatively, cap the number of refs resolved from `ExceptWithPrefix` server-side and require the client to retry/paginate for larger sets.

### Proof of Concept
1. Populate a repository with a very large number of references (e.g., via ordinary CI/MR/branch creation over time, or programmatically for testing).
2. Call `RefService.DeleteRefs` with `ExceptWithPrefix: ["nonexistent-prefix/"]` and an empty `Refs` list.
3. Observe that `refsToRemove` loads and iterates over the entire ref set (`internal/gitaly/service/ref/delete_refs.go:139-153`), and the main handler loop then performs `Delete` + vote-hash writes for every one of them synchronously (`internal/gitaly/service/ref/delete_refs.go:49-78`), with total request cost scaling linearly (or worse, given `git-update-ref` transaction overhead) with the total ref count rather than any bounded/paginated value.
