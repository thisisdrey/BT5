### Title
Single-lighthouse address poisoning without multi-source corroboration - ([File: lighthouse.go])

### Summary
The external report describes an oracle system that trusts a VWAP computed from third-party price feeds without detecting or discounting a single malicious/malfunctioning provider, letting one bad source poison the on-chain value. The analogous condition in this codebase is `LightHouseHandler.handleHostQueryReply` in `lighthouse.go`, which accepts and installs a target host's underlay addresses into the querying node's `RemoteList` cache based on a reply from a single lighthouse, with no cross-checking against other configured lighthouses or any corroboration/quorum requirement.

### Finding Description
When a node queries for a peer's address, it broadcasts the query to every configured lighthouse via `innerQueryServer` [1](#0-0) . Each lighthouse that answers is treated independently and immediately trusted: `handleHostQueryReply` verifies only that the reply came from *some* known lighthouse address (`IsAnyLighthouseAddr`), then merges the reported `V4AddrPorts`/`V6AddrPorts` for the target `certVpnAddr` directly into the cache, keyed by that individual lighthouse as the "owner" of the record: [2](#0-1) 

`unlockedSetV4`/`unlockedSetV6` (in `remote_list.go`) simply reset and repopulate the reported-address slot for that one owner/lighthouse on every reply, running only the caller-supplied `check` predicate (`unlockedShouldAddV4`/`unlockedShouldAddV6`), which filters for things like "not in my own VPN network," not for consistency with what other lighthouses have reported: [3](#0-2) 

All owners' cached addresses are then unconditionally unioned together into the single deduplicated `addrs` list used for handshake attempts, in `unlockedCollect`: [4](#0-3) 

There is no logic anywhere in this path that compares the addresses reported by multiple lighthouses for the same target and flags/drops an outlier, nor any mechanism to temporarily distrust a lighthouse whose reports are wildly inconsistent with the others — exactly the missing "detect and disable the malfunctioning provider" control called out in the reference report for the oracle price-feeder.

### Impact Explanation
If an operator configures multiple lighthouses (a common resiliency practice, directly analogous to querying multiple price providers), a single compromised or malfunctioning lighthouse can unilaterally inject a bogus underlay address for any target VPN address into a client's `RemoteList`. That poisoned address is merged into the same address pool used to attempt outbound handshakes (`SendMessageToVpnAddr`/handshake dialing), causing the victim to attempt a handshake toward an attacker-chosen host/port. This mirrors the reported bug class: trust in a single unverified source pollutes an aggregate value (VWAP → address list) that downstream logic acts on without a corroboration/outlier-detection safeguard. Because address records are merely inputs to a handshake attempt (which still requires certificate authentication to complete a tunnel), this is a lower-severity variant than the original financial-loss oracle bug, but it is a real address/hostmap-trust weakness reachable by any single compromised lighthouse in the mesh.

### Likelihood Explanation
Likelihood is moderate: it requires a validator/operator to have configured more than one lighthouse and for one of them to be compromised or malfunctioning (e.g., through operator error, a supply-chain compromise, or a rogue admin), which is the same "single bad provider" scenario the reference report treats as realistic for price-feeder operators using multiple third-party providers.

### Recommendation
Add cross-lighthouse corroboration before trusting a `HostQueryReply`/`HostUpdateNotification`-derived address for a given target: require agreement (or majority/quorum) among the addresses reported by different lighthouses before merging them into the actively-tried address set, or at minimum flag/deprioritize addresses reported by only one lighthouse when other lighthouses report a different, non-overlapping address set for the same target. Consider tracking per-lighthouse report history to detect a lighthouse whose answers diverge persistently from the others and temporarily exclude it, mirroring the recommended "detect and disable the malfunctioning provider" mitigation from the reference report.

### Proof of Concept
1. Configure a node with two lighthouses, `LH1` (honest) and `LH2` (attacker-controlled).
2. Node queries for peer `V`'s address via `innerQueryServer`; both lighthouses receive the `HostQuery`.
3. `LH1` replies with `V`'s real address; `LH2` replies with an attacker-chosen `V4AddrPort` pointing at attacker infrastructure.
4. Both replies pass the sole check in `handleHostQueryReply` (`IsAnyLighthouseAddr`) and are merged into `RemoteList.cache` under their respective lighthouse-owner keys via `unlockedSetV4` [5](#0-4) .
5. `unlockedCollect` unions both entries into the single deduplicated `addrs` list with no outlier rejection [4](#0-3) , so the node may attempt (and retry) a handshake toward the attacker's address alongside the legitimate one, with no mechanism ever having compared `LH1`'s and `LH2`'s answers for consistency.

func (lhh *LightHouseHandler) handleHostQueryReply(n *NebulaMeta, fromVpnAddrs []netip.Addr) {
	if !lhh.lh.IsAnyLighthouseAddr(fromVpnAddrs) {
		return
	}

	certVpnAddr, _, err := n.Details.GetVpnAddrAndVersion()
	if err != nil {
		if lhh.l.Enabled(context.Background(), slog.LevelDebug) {
			lhh.l.Error("dropping malformed HostQueryReply",
				"error", err,
				"vpnAddrs", fromVpnAddrs,
			)
		}
		return
	}
	relays := n.Details.GetRelays()

	lhh.lh.Lock()
	am := lhh.lh.unlockedGetRemoteList([]netip.Addr{certVpnAddr})
	am.Lock()
	lhh.lh.Unlock()

	am.unlockedSetV4(fromVpnAddrs[0], certVpnAddr, n.Details.V4AddrPorts, lhh.lh.unlockedShouldAddV4)
	am.unlockedSetV6(fromVpnAddrs[0], certVpnAddr, n.Details.V6AddrPorts, lhh.lh.unlockedShouldAddV6)
	am.unlockedSetRelay(fromVpnAddrs[0], relays)
	am.Unlock()

func (r *RemoteList) unlockedSetV4(ownerVpnIp, vpnIp netip.Addr, to []*V4AddrPort, check checkFuncV4) {
	r.shouldRebuild = true
	c := r.unlockedGetOrMakeV4(ownerVpnIp)

	// Reset the slice
	c.reported = c.reported[:0]

	// We can't take their array but we can take their pointers
	for _, v := range to[:minInt(len(to), MaxRemotes)] {
		if check(vpnIp, v) {
			c.reported = append(c.reported, v)
		}
	}
}
