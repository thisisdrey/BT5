### Title
Non-void-returning FT `ft_transfer` causes double credit in `ft_resolve_withdraw` for non-`is_call` withdrawals - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
`ft_resolve_withdraw` treats a non-`is_call` `ft_transfer` as failed and refunds the full `amount` whenever the promise's returned bytes are non-empty, even though NEAR already executed and settled the transfer. A `token` contract that is spec-non-compliant (returns any non-empty JSON on success instead of NEP-141's mandated void) can make a genuinely successful transfer be reported as `used=0`, causing `sender_id` to be re-credited the full withdrawn amount while `receiver_id` has already received the tokens externally.

### Finding Description
The binding that must hold is: `internal_balance_debited(sender_id, TokenId) == real_tokens_delivered(receiver_id) + internal_balance_recredited(sender_id, TokenId)` for that `TokenId`. In `ft_resolve_withdraw`, for the non-`is_call` branch: [1](#0-0) 

`used` is decided solely by `promise_result_checked_void(0).is_ok()`. That helper is documented and implemented to require the promise's returned bytes to be empty (it calls `env::promise_result_checked(result_idx, 0)`, i.e. max allowed length is `0`): [2](#0-1) 

Because `token` is a fully attacker-controlled account (the withdrawer picks any FT contract they've deposited balance for), an attacker can deploy an FT contract whose `ft_transfer` performs the real balance mutation (as any compliant `ft_transfer` would — moving `amount` from the Verifier's real holdings to `receiver_id`) but then returns a non-empty JSON value, violating NEP-141's void-return requirement. NEAR then reports the promise's result as non-empty, `promise_result_checked_void` fails to satisfy its `max_len=0` constraint, `is_ok()` is `false`, so `ft_resolve_withdraw` sets `used = 0` and refunds the entire `amount.0` back to `sender_id` via `self.deposit(...)`: [3](#0-2) 

Since the real transfer already succeeded and moved `amount` out of the Verifier's actual FT holdings to `receiver_id`, this refund is unbacked: the Verifier's internal ledger for that `TokenId` now claims more tokens than it actually custodies with the real `token` contract. `withdraw()`'s earlier debit is already applied before this callback runs, so there's no other guard preventing the fabricated recredit.

### Impact Explanation
This is a resolver credit that does not match what actually failed to settle (the transfer did settle). If the same `token` `TokenId` is shared by other, unrelated depositors who trusted and deposited that token's real balance into the Verifier, the attacker's repeated exploit of this refund path drains real custodied `token` balance out to `receiver_id` while re-inflating the attacker's own internal Verifier balance for that `TokenId`, leaving the Verifier internally insolvent for that `TokenId` — other genuine holders of that `TokenId` will find their subsequent withdrawals fail or be short, i.e., their funds are effectively lost/frozen. This matches the Critical category "a refund or resolver credit that does not match what failed to settle" and, at scale, "the Verifier owes more than it custodies" for that `TokenId`.

### Likelihood Explanation
The attacker needs only to: (1) deploy their own FT contract with a spec-violating `ft_transfer` that performs the real transfer but returns non-empty bytes on success, (2) get Verifier balance credited for that `TokenId` (either by depositing their own minted tokens, or by having other users independently deposit that same token), and (3) call `ft_withdraw` with `msg: None`. No special role, relayer key, or DAO permission is needed — only a standard `ft_withdraw` call with 1 yoctoNEAR attached. This is fully repeatable per withdraw call and scales with the amount deposited into that `TokenId`.

### Recommendation
Do not conflate "promise succeeded" with "promise returned exactly the NEP-141-mandated empty payload" for security-critical accounting. Either: (a) treat any successful promise result (regardless of byte length) as a successful `ft_transfer` for accounting purposes (matching the actual on-chain balance mutation, since the call site does not care about the return payload for `ft_transfer`), or (b) if strict spec compliance must gate accounting, ensure the "non-compliant success" case is still treated as `used = amount` (transfer happened) rather than `used = 0`, since NEAR promise success already proves the token contract did not panic/revert.

/// Returns `Ok(())` if the promise at `result_idx` succeeded with an empty result.
/// This is the expected outcome for void-returning cross-contract calls
/// (e.g. `ft_transfer`, `nft_transfer`, `mt_batch_transfer`).
#[inline]
pub fn promise_result_checked_void(result_idx: u64) -> PromiseResult<()> {
    let data = env::promise_result_checked(result_idx, 0)?;
    debug_assert!(data.is_empty());
    Ok(())
}
