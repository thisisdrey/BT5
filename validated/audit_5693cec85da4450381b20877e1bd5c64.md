### Title
Unbounded attacker-controlled length used to allocate arrays before size validation in `ValidateMultiSign` precompile (legacy branch), causing `OutOfMemoryError`/`NegativeArraySizeException` node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (invoked via a normal `CALL` from any smart contract at address `0x0...1001` in java-tron) reads a signature-array length directly from attacker-controlled call data and allocates a `byte[len][]` array with it **before** any bound check is applied, when the `allowTvmSelfdestructRestriction` hard fork flag is not yet active (legacy code path is retained for compatibility and still reachable pre/at-fork boundary and in any deployment where this fork has not been enabled).

### Finding Description
`extractBytesArray`/`extractBytes32Array` read a 32-byte word from the caller-supplied precompile input and use it verbatim as an allocation size: [1](#0-0) 

In `ValidateMultiSign.execute`, the size check (`sigArraySize > MAX_SIZE`) is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is true, and even then it is checked using `extractSigArray`'s safer path. When that flag is false, `extractBytesArray(words, ..., rawData)` is called directly with the attacker-controlled `len` with **no upper bound check at all** before allocation: [2](#0-1) 

`len = words[offset].intValueSafe()` comes straight from `DataWord`, which is fully attacker-controlled call data to the precompile; there is no `MAX_SIZE`/energy-based upper bound enforced prior to `new byte[len][]`. This mirrors the TensorFlow `Mfcc` bug class: an oversized, unchecked, attacker-supplied integer is used directly as an array/collection allocation size, causing the process to crash (`NegativeArraySizeException` for corrupted/negative values or `OutOfMemoryError`/uncontrolled large allocation for huge positive values) rather than being rejected gracefully during input validation.

Additionally, even in the "protected" branch, the `sigArraySize` bound check happens only for the length field itself; the nested `extractBytes32Array`/`extractSigArray` still perform `new byte[len][]` unconditionally based on attacker input if `len` is used before the `MAX_SIZE` gate is reached in other call sites of these shared helper methods (e.g., other precompiles reusing `extractBytesArray`/`extractBytes32Array` for their own list decoding), so any additional caller of these two helpers without a preceding length check is equally exposed.

### Impact Explanation
A crafted `TriggerSmartContract`/`CreateSmartContract` transaction that calls the `ValidateMultiSign` precompile with a malformed/huge length word (e.g., `0x7fffffff`) can force the executing node to attempt a massive array allocation, resulting in `OutOfMemoryError` or an uncaught `NegativeArraySizeException`, either of which is likely to be unhandled where it propagates outside VM-level exception guards, causing a full-node crash or halt. Because this executes during transaction/block processing, it could crash validating/processing nodes, potentially causing a chain-wide denial of service if triggered in a block that must be applied by all full nodes (not merely local/isolated resource exhaustion, since the node itself halts). This matches the required "node crash or halt" impact bar.

### Likelihood Explanation
The precompile is reachable by any account that can send a plain smart-contract call transaction — no special privilege, SR/witness status, or trusted role is needed. The vulnerable branch depends on the `allowTvmSelfdestructRestriction` fork/config flag being disabled (this is a hard-fork feature flag; historically not enabled on all networks/heights, and any private/test/consortium chain instance that has not activated it remains exposed indefinitely). Where the flag is active, exposure is reduced but the underlying `extractBytesArray`/`extractBytes32Array` helper itself still performs no defensive bound check, so any future or existing caller that omits the `MAX_SIZE` pre-check reintroduces the same crash primitive.

### Recommendation
Add an explicit upper bound check (e.g., against `MAX_SIZE` or a sane maximum derived from the remaining `rawData` length) inside `extractBytesArray` and `extractBytes32Array` themselves, before the `new byte[len][]` allocation, rather than relying on each caller to gate the value beforehand. Also validate that `len >= 0` and that `offset + len` fits within `words.length` to avoid negative-size and out-of-bounds allocations regardless of feature-flag state.

### Proof of Concept
1. Deploy or call an existing contract that performs a low-level `CALL` to the `ValidateMultiSign` precompiled contract address, passing ABI-encoded parameters where the signature-array length word (at the offset referenced by `words[3]`) is set to a very large value (e.g., `0x7fffffff`) instead of a legitimate small count.
2. On a network/environment where `allowTvmSelfdestructRestriction` is not enabled, this reaches `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)` [3](#0-2)  which executes `new byte[len][]` [4](#0-3)  with the attacker-supplied `len`, crashing the node with `OutOfMemoryError`/`NegativeArraySizeException` during transaction execution.

**Note on uncertainty:** I was unable to fully verify the exact current on-chain activation status of `allowTvmSelfdestructRestriction` across all deployed java-tron networks, nor exhaustively confirm every other caller of `extractBytesArray`/`extractBytes32Array` beyond `ValidateMultiSign` within the indexed portion of `PrecompiledContracts.java`. If `allowTvmSelfdestructRestriction` is permanently enabled on all production networks with no legacy fallback path, the practical exposure is reduced to the unguarded helper functions only, but the root-cause allocation pattern remains present in the code as shown above.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {

      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
