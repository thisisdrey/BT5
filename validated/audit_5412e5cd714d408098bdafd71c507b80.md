### Title
Unprivileged attacker can grief users by force-filling their `MAX_TOKENS_PER_USER` token list via dust deposits/transfers - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the hPAL cooldown griefing (a sender imposing a cost/state change on an unwilling receiver via small transfers), Metronome lets any user add entries to another account's per-account token list by depositing dust `onBehalfOf` them or sending them dust `transfer`s. `Pool.MAX_TOKENS_PER_USER = 30` caps the combined size of `depositTokensOfAccount` + `debtTokensOfAccount`; once filled, every subsequent first-time deposit, first-time receipt of a deposit token, and first borrow (debt token mint) for that account reverts with `UserReachedMaxTokens`. The attacker only pays dust amounts; the victim is blocked from opening new collateral or debt positions until they clear the dust entries.

### Finding Description
- `Pool` enforces a shared 30-entry cap on a user's debt + deposit token lists via `onlyIfAdditionWillNotReachMaxTokens` in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (`contracts/Pool.sol:143-148`, `204-220`).
- `DepositToken.deposit(amount_, onBehalfOf_)` accepts an arbitrary beneficiary with no opt-in and calls `_mint(onBehalfOf_, ...)`, which calls `pool.addToDepositTokensOfAccount(account_)` when the recipient's balance was zero (`contracts/DepositToken.sol:211-237`, `485-488`).
- `DepositToken.transfer`/`transferFrom`/`seize` route through `_transfer`, which likewise calls `pool.addToDepositTokensOfAccount(recipient_)` for a first-time recipient — and the dust is `unlocked` so `_revertIfLocked` passes (`contracts/DepositToken.sol:348-376`, `498-525`; lock check at `180-182`).
- An attacker therefore deposits dust of each registered deposit token to the victim (or transfers dust), filling the victim's list to 30. From then on:
  - the victim cannot deposit a collateral type they don't already hold (`addToDepositTokensOfAccount` reverts, reverting the whole `deposit`);
  - the victim cannot borrow a synth they don't already owe (`DebtToken` mint calls `addToDebtTokensOfAccount`, same revert);
  - anyone (including the liquidator path `Pool.liquidate` → `DepositToken.seize` → `_transfer`) cannot move a new deposit-token type to the victim.

### Impact Explanation
Temporary freezing of victim functionality: the victim is unable to add new collateral or open new borrows — including adding collateral needed to cure an unhealthy position — until they manually clear dust entries by transferring/withdrawing the dust back out (zeroing the balance triggers `removeFromDepositTokensOfAccount`, `DepositToken.sol:522-525`). For a leveraged victim near liquidation, this can block self-recovery and make the position liquidatable, converting griefing into indirect loss of funds via liquidation fees/seizure.

### Likelihood Explanation
Same profile as the reference finding: feasible but costly/malicious. Cost is bounded — the attacker must hold (or dust-deposit) up to 30 distinct pool-registered deposit tokens and sacrifice the dust (plus deposit fees and gas). It requires deliberate malice and yields no direct profit; mitigations such as the victim redeeming dust restore functionality. Consistent with the judge's medium classification for the analogous issue.

### Recommendation
Decouple the per-account list cap from consent-less state changes, e.g.: do not add a token to `depositTokensOfAccount` for sub-dust amounts (enforce a minimum first-deposit threshold), exempt `seize`/`liquidate` paths from the cap, or make `addTo*TokensOfAccount` a no-op (tracked off-list) instead of reverting when the cap is hit so core actions never revert on account-list accounting.

### Proof of Concept
```solidity
// Victim V holds positions in < 30 tokens. Pool has N registered deposit tokens.
for each depositToken_i registered in pool (until V's list == 30) {
    underlying_i.approve(depositToken_i, dust);
    // no victim consent needed; depositToken_i now occupies a slot in V's list
    depositToken_i.deposit(dust, V);
}
// Now: pool.getDepositTokensOfAccount(V).length + debtTokensOfAccount.length == 30

// 1) Victim tries to deposit a new collateral type -> reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositToken_new.deposit(amount, V); // via addToDepositTokensOfAccount

// 2) Victim tries to issue a new synth -> reverts inside DebtToken._mint
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
debtToken_new.issue(amount, V);

// 3) Anyone sending V a new deposit token reverts too
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
depositToken_new.transfer(V, 1);
```
Reproducible in a Hardhat fork: deploy-time list grows only via `addTo*TokensOfAccount`; dust deposit of each listed `depositTokenOf[underlying]` is enough to reach `MAX_TOKENS_PER_USER` (`Pool.sol:79`).
