Based on my research, I found a concrete analog in the TRC10 `Exchange` (Bancor-style AMM) module. This is the closest reachable equivalent to an AMM/DEX pool that an unprivileged, single-signed transaction can manipulate — mirroring the Ara flash-loan price-manipulation bug class.

### Title
Floating-point Bancor-formula pricing in the TRC10 Exchange pool allows precision-based value extraction across `ExchangeInject`/`ExchangeTransaction`/`ExchangeWithdraw` - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The default (non-hardened) code path for TRON's native TRC10 token-swap "Exchange" (a constant-formula AMM analogous to a DEX pool) computes swap output using IEEE-754 `double` arithmetic and `Math.pow`, rather than exact integer/BigDecimal math [1](#0-0) . Any account can call `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` — all reachable from a single signed transaction with no special permission — to inject liquidity, swap, and withdraw against the same pool [2](#0-1) [3](#0-2) .

### Finding Description
The core pricing formula lives in `ExchangeCapsule.transaction()`, which selects between the legacy `ExchangeProcessor` (double-based) and `SafeExchangeProcessor` (BigDecimal-based) depending on the `allowHarden` flag, itself gated by the chain parameter `allowHardenExchangeCalculation()` [4](#0-3) . In the legacy path, `exchangeToSupply`/`exchangeFromSupply` use `double` math and truncate to `long` via `(long) issuedSupply` and `(long) exchangeBalance`, which is exactly the class of rounding/precision bug that lets an attacker execute crafted sequences of small trades or inject/withdraw combinations to skew the pool's effective exchange rate and extract more value than deposited — conceptually the same "price/ratio manipulation across pool state" bug class as the Ara flash-loan incident, just implemented as TRON's native pool instead of a Solidity AMM [5](#0-4) .

The test suite itself demonstrates the repo authors are aware of this precision gap: `ExchangeProcessorTest.testStrictMath` explicitly shows that the legacy (non-strict) `ExchangeProcessor` and the hardened `SafeExchangeProcessor` diverge on identical inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the legacy formula is not exact/consistent [6](#0-5) . `ExchangeWithdrawActuator.doValidate` also enforces only a 0.01% tolerance ("Not precise enough") on the withdraw ratio rather than exact equality, tacitly acknowledging built-in slippage in the formula that a repeat-transaction attacker could try to accumulate [7](#0-6) .

### Impact Explanation
If the hardened path is not active by default (I was unable to conclusively confirm the default value of `allowHardenExchangeCalculation` from the indexed source — `DynamicPropertiesStore.java` content beyond its imports was not available in the index), the legacy floating-point Bancor formula remains the live, unprivileged code path for all TRC10 exchange pools on mainnet. An attacker able to string together a sequence of Inject/Transaction/Withdraw calls against a low-liquidity pool could exploit compounding rounding errors to drain value from the pool's balances, which is unbacked-balance / theft-of-funds impact consistent with Medium/High severity.

### Likelihood Explanation
Likelihood depends entirely on whether `allowHardenExchangeCalculation` defaults to disabled on the current network. All exchange actuators are unauthenticated beyond needing enough balance/fee, and no special permission is required to create or interact with an exchange pool, so if the vulnerable path is live, exploitation only requires ordinary signed transactions.

### Recommendation
Confirm and, if necessary, force-enable `allowHardenExchangeCalculation` (routing all Exchange calculations through `SafeExchangeProcessor`) as the default/only code path, and remove or hard-deprecate the double-based `ExchangeProcessor` entirely rather than keeping it behind a feature flag.

### Proof of Concept
Not concretely demonstrable without confirming the default state of `allowHardenExchangeCalculation`; conceptually, a PoC would deploy/find a low-liquidity TRC10 exchange, then repeatedly call `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` [8](#0-7)  with quantities chosen to maximize the double-precision rounding error accumulated by `ExchangeProcessor.exchange()` [9](#0-8) .

**Note on confidence**: This finding required inferring the default state of a chain governance parameter (`allowHardenExchangeCalculation`) that I could not directly verify in the indexed code (the `DynamicPropertiesStore.java` content was not fully retrievable). If this parameter defaults to enabled on the target network, this finding would be already mitigated and should be treated as informational rather than an exploitable vulnerability.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
