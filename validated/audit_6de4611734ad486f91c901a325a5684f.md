## Title
Rounding-to-zero in TRC10 DEX exact-match order fill lets a taker drain a maker's escrowed tokens for free - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator#matchSingleOrder` computes cross-rate amounts with integer division (`MarketUtils.multiplyAndDivide`), which truncates toward zero exactly like the reported Bond Protocol `quoteAmount` rounding bug. Two of the three code paths in this method explicitly guard against the division rounding down to `0` and return the assets instead of completing the trade for free. The third path — the "taker == maker" exact-match branch — has no such guard, so when the maker's TRX-equivalent payout rounds down to zero, the maker's entire remaining sell-token balance is transferred to the taker while the taker pays nothing.

### Finding Description
In `matchSingleOrder`, when the taker's calculated buy amount exactly equals the maker's remaining sell quantity: [1](#0-0) 

`makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)`, which is a plain multiply-then-floor-divide operation: [2](#0-1) 

If `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, the result rounds down to `0` — the exact same class of truncation bug as `amount_.mulDiv(strikePrice, 10**decimals)` in the Bond Protocol report. Unlike this branch, the other two branches of `matchSingleOrder` explicitly check for this and refund the sell-side asset instead of proceeding:

- `takerBuyTokenQuantityRemain == 0` guard: [3](#0-2) 
- `makerBuyTokenQuantityReceive == 0` guard in the "taker > maker" branch: [4](#0-3) 

But in the "taker == maker" branch, when `makerBuyTokenQuantityReceive` rounds to `0`:
- `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (full remaining maker balance) is still credited to the taker via `addTrxOrToken`.
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` closes out the maker's order, discarding its remaining escrowed asset.
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive` subtracts `0`, so the taker's own remaining sell-side balance (already escrowed via `transferBalanceOrToken` at order creation) is left completely untouched.
- `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` credits the maker `0`.

The taker thus receives the maker's escrowed tokens without paying anything, and the maker's remaining balance is permanently lost.

### Impact Explanation
This lets an unprivileged order placer (anyone who can submit `MarketSellAssetContract` transactions) drain another user's escrowed TRC10/TRX order balance without paying the counter-asset, resulting in a concrete unauthorized transfer/theft of funds already escrowed by the protocol's DEX order book. A taker can deliberately craft an order whose `sellTokenQuantity`/`buyTokenQuantity` produce a `takerBuyTokenQuantityRemain` that exactly matches a maker's small remaining order quantity where the maker's price ratio (`makerBuyQuantity/makerSellQuantity`) causes the payout to floor to zero.

### Likelihood Explanation
Reaching a maker order with a very small `sellTokenQuantityRemain` is straightforward: an attacker can create their own maker order with a favorable ratio (`makerBuyQuantity < makerSellQuantity`) and repeatedly partially fill it themselves (or wait for natural partial fills) until the remainder is small enough that `remain * buyQuantity / sellQuantity == 0`, then submit a final taker order engineered to exactly match that remainder. This requires only standard signed `MarketSellAssetContract` transactions and no special privileges, and the DEX matching engine is reachable on every `MarketSellAssetActuator.execute` call once `supportAllowMarketTransaction` is enabled.

### Recommendation
Add the same `makerBuyTokenQuantityReceive == 0` (or `takerBuyTokenQuantityReceive == 0`) guard to the "taker == maker" exact-match branch of `matchSingleOrder` that already exists in the other two branches, refunding the maker's remaining sell-token quantity via `MarketUtils.returnSellTokenRemain` instead of zeroing it out and transferring it to the taker for free.

### Proof of Concept
1. Attacker creates a maker sell order: sell `A` token, `sellTokenQuantity = 1_000_000`, `buyTokenQuantity = 1` (extremely low price for `A`).
2. Through self-trades or normal partial fills, the order's `sellTokenQuantityRemain` is reduced to `1`.
3. Attacker (as taker, potentially a second account) submits a `MarketSellAssetContract` selling `buyTokenId`'s counter-asset such that `takerBuyTokenQuantityRemain` computed in `matchSingleOrder` equals exactly `1` (the maker's remaining quantity), triggering the "taker == maker" branch.
4. `makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 1_000_000) = 0`.
5. The taker receives `1` unit of `A` (`takerBuyTokenQuantityReceive`) via `addTrxOrToken`, while `takerOrderCapsule`'s own remaining sell balance is left unchanged (no deduction), and the maker's order is closed with `addTrxOrToken(makerOrderCapsule, 0)` — the maker receives nothing for the asset given up.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
