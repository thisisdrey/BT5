### Title
Dangling postponed receipts survive `DeleteAccount`, enabling privilege escalation on account re-creation - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) only removes `TrieKey::Account`, `ContractCode`, access/gas keys, and `ContractData`, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` entries keyed by the deleted `account_id` [1](#0-0) . `process_action_receipt` writes these entries keyed purely by `receiver_id` (the account ID string) with no per-incarnation/generation nonce [2](#0-1) , so a postponed receipt created before deletion silently resumes execution against whatever account later reoccupies that same account ID.

### Finding Description
`process_action_receipt` stores a postponed action receipt's pending-data counter and receipt-id-to-data-id linkage under keys namespaced only by the receiver account ID: `TrieKey::PostponedReceiptId{receiver_id, data_id}` and `TrieKey::PendingDataCount{receiver_id, receipt_id}`, plus `set_postponed_receipt` [2](#0-1) . These keys have no concept of "account generation" — they are indistinguishable before and after a `DeleteAccount`/`CreateAccount` cycle on the same ID.

`remove_account`, which backs the `DeleteAccount` action, removes `Account`, `ContractCode`, all access keys/gas key nonces, and `ContractData`, but never scans or removes `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` entries [3](#0-2) . Consequently, if an attacker engineers a postponed `ActionReceipt` (e.g. containing `AddKey` with full access, gated on an `input_data_id` that never resolves in that block) against their own account `x.a.near`, then deletes `x.a.near` via `DeleteAccount`, the postponed receipt and its pending-data bookkeeping remain in the trie under the `x.a.near` namespace. If the attacker (still controlling parent `a.near`) later re-creates `x.a.near` and a victim funds/uses it, and the attacker finally supplies the missing data receipt, `process_receipt`'s data-receipt path will decrement the surviving `PendingDataCount` to zero and dispatch the stale postponed `AddKey` receipt against the *new* incarnation of the account — even though the new account owner never authorized it.

### Impact Explanation
This is an authorization-escalation path: a promise (the postponed `AddKey` action receipt) retains and later exercises privileges its creator did not hold over the current incarnation of the account, letting the attacker install a full-access key on a victim-funded account and steal funds. This matches the "authorization escalation across accounts or promises" / "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions are attacker-controlled and require no privileged access: owning a parent account, being able to send self-targeted receipts with unresolved data dependencies, and issuing `DeleteAccount`/`CreateAccount`. The only extra requirement is a victim independently choosing to reuse/fund the deleted sub-account name after deletion — a real but not attacker-controlled event, so likelihood depends on social/economic conditions (victim depositing into `x.a.near` post-deletion) rather than purely technical feasibility. I was not able to fully verify (tool budget exhausted) whether `action_delete_account` in `runtime/runtime/src/actions.rs` imposes any additional guard (e.g., checking for outstanding postponed receipts) before allowing deletion, which would materially affect exploitability; this should be confirmed before assigning final severity.

### Recommendation
`remove_account` should also iterate and remove all `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries under the account's prefix (or `DeleteAccount` should be blocked while such pending entries exist for the account), ensuring no cross-incarnation receipt execution is possible.

### Proof of Concept
Runtime/test-loop integration test: (1) submit a self-directed `ActionReceipt` on `x.a.near` with an `AddKey(full_access)` action gated on a data dependency that is not resolved this block, confirming `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie entries exist for `x.a.near`; (2) submit `DeleteAccount{beneficiary_id: attacker}` on `x.a.near` and assert via direct trie/`TrieUpdate` inspection that these three column entries for `x.a.near` are still present after `remove_account` returns; (3) re-create `x.a.near` via `CreateAccount` from `a.near`, have a distinct "victim" key added; (4) deliver the missing `DataReceipt`, and assert the stale `AddKey` executes and installs the attacker's full-access key on the new account without any signature/authorization from the new owner.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
