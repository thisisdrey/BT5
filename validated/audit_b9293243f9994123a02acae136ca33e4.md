## Analysis

The HatsSignerGate bug reduces to: an immutable per-deployment cap (`maxSigners`) is checked in a core, universally-invoked function (`checkTransaction`/`reconcileSignerCount`), and if a dynamic on-chain quantity (actual valid-signer count) ever exceeds that immutable cap, the check reverts on *every* subsequent invocation of that core path, permanently bricking the wrapped object with no in-protocol way to shrink the offending quantity (since shrinking itself may require going through the same guarded path).

The direct structural analog in this repo is `pallet-bridge-grandpa`'s handling of `MaxBridgedAuthorities` (`ChainWithGrandpa::MAX_AUTHORITIES_COUNT`), an immutable runtime-config constant, versus the *actual* size of the bridged chain's GRANDPA authority set, which is fully controlled by the bridged (external) chain and can grow over time without any coordination with the bridging chain's configuration.

### Title
Bridge GRANDPA light client can be permanently bricked when a mandatory header's authority set exceeds the immutable `MaxBridgedAuthorities` bound - (File: `bridges/modules/grandpa/src/lib.rs`)

### Summary
`pallet-bridge-grandpa` stores the bridged chain's GRANDPA authority set in a `BoundedVec` capped by the constant `T::BridgedChain::MAX_AUTHORITIES_COUNT` (`MaxBridgedAuthorities`) [1](#0-0) . This bound is fixed at runtime-build time and cannot be changed without a runtime upgrade. When a "mandatory" header (one that schedules a GRANDPA authority-set change) is submitted via `submit_finality_proof_ex`, `try_enact_authority_change` calls `save_authorities_set`, which fails with `Error::TooManyAuthoritiesInSet` if the new authority list from the bridged chain exceeds this bound [2](#0-1) . Because "the pallet can't go further without importing" mandatory headers [3](#0-2) , this single rejected mandatory header permanently halts all future header imports for the bridge instance — mirroring the HSG bug where a fixed cap set once, when trespassed by dynamic state, bricks the core check-path for good.

### Finding Description
The `ChainWithGrandpa` trait explicitly documents this exact risk: "Max number of GRANDPA authorities at the chain. This is a strict constant. If bridged chain will have more authorities than that, the GRANDPA bridge pallet may halt." [1](#0-0) 

The `StoredAuthoritySet::try_new`/`save_authorities_set` functions use `TryFrom`/`try_into` on `BoundedVec<_, MaxBridgedAuthorities>` and return `Error::TooManyAuthoritiesInSet` on overflow [4](#0-3) [2](#0-1) .

In `submit_finality_proof_ex`, this failure occurs after the justification has already been verified against the *current* authority set, but before the header is inserted, meaning the call as a whole fails and the mandatory header is never accepted [5](#0-4) . Since GRANDPA justifications for all subsequent headers are signed by the *new* authority set that the bridge never learned about, `verify_justification` on the next header will also fail (unknown authority keys) — there is no path forward. This is confirmed by the pallet's own test `importing_header_rejects_header_with_too_many_authorities`, which shows the call unconditionally erroring with no recovery path other than the privileged `force_set_pallet_state`/root call [6](#0-5) .

Critically, the corrupted/mismatched value is `T::BridgedChain::MAX_AUTHORITIES_COUNT` (an immutable, compile-time/config-time constant on the bridging chain) versus the bridged chain's actual live authority-set size, which is entirely outside the bridging chain's control — a permissionless GRANDPA authority-set rotation on the *bridged* chain (validator additions via its own governance, not requiring any privileged action on the bridging chain) can silently exceed the configured bound. Once this happens, the bridge's public, permissionless `submit_finality_proof_ex` entry point (any relayer, unprivileged, can call it) can no longer make progress, since every relayer submission of the mandatory header (or anything after it) fails with `TooManyAuthoritiesInSet`. The only remedy is the privileged `force_set_pallet_state` call restricted to root/pallet owner [7](#0-6) , which is exactly the "changeable only by owner"/manual-intervention workaround the original report recommended as a fix, not a preventative guard — i.e., today's code has no preventative check at configuration/wiring time equivalent to `maxSigners >= hat.currentSupply`.

### Impact Explanation
Once the bridged chain's real authority-set size exceeds `MaxBridgedAuthorities`, the bridge GRANDPA light client permanently stalls: no further headers can be finalized on-chain, all downstream consumers (bridge messages pallet, bridge parachains pallet, XCM/Snowbridge-style bridging flows relying on this header chain for storage proofs) are blocked, matching "permanent... bridge-state lock" and "public underpriced work that... stalls bridge processing" in the impact gate. This requires no malicious relayer, admin, or governance action — it is triggered purely by benign authority-set growth on the bridged chain, an event the bridging-chain configuration does not automatically track.

### Likelihood Explanation
This is a config/parameter-sizing risk rather than a routinely-triggered bug: `MaxBridgedAuthorities` is normally set generously relative to expected validator counts, so triggering it requires the bridged chain's authority set to actually grow past that bound. However, unlike the HSG case (where owners control both sides), here the two "sides" (bridging-chain governance for `MaxBridgedAuthorities`, and bridged-chain governance for its own validator count) are decoupled and not necessarily incentive-aligned or coordinated, making a future mismatch plausible without any single actor being at fault or malicious — it is a real, non-adversarial configuration-drift risk, analogous to the "not high severity because incentive aligned" caveat in the original report, but arguably worse here because the two parties are different chains' governances.

### Recommendation
- Add an early warning/telemetry (e.g., emit an event or metric) when an incoming mandatory header's authority-set size approaches `MaxBridgedAuthorities`, so operators can react before the hard limit is hit.
- Consider making the halt recoverable without requiring the `force_set_pallet_state` fallback to fully re-synchronize state (currently it discards verification of the intervening chain), or add a dedicated, less destructive recovery call that only updates the authority set with an increased runtime-configured bound after a scheduled upgrade.
- Document/lint at runtime-construction time that `MaxBridgedAuthorities` should be provisioned with sufficient headroom relative to the bridged chain's session/validator-count growth policy, and consider a runtime upgrade migration path that can atomically raise `MaxBridgedAuthorities` together with a state-migration for `CurrentAuthoritySet`.

### Proof of Concept
1. Deploy `pallet-bridge-grandpa` bridging to chain X, with `BridgedChain::MAX_AUTHORITIES_COUNT = N` configured at genesis/runtime-build time (immutable without upgrade), as in `bridges/modules/grandpa/src/lib.rs` `initialize_bridge` [8](#0-7) .
2. Over time, chain X's own governance (unrelated to the bridging chain) legitimately increases its GRANDPA validator count above `N`.
3. Chain X produces a mandatory header enacting the new, larger authority set.
4. Any relayer (unprivileged, public) calls `submit_finality_proof_ex` with this mandatory header and a valid justification signed by the *current* (still-known) authority set.
5. `try_enact_authority_change` → `save_authorities_set` attempts `new_authorities.try_into()` into `BoundedVec<_, MaxBridgedAuthorities>` and fails with `Error::TooManyAuthoritiesInSet` [2](#0-1) , exactly as exercised by the existing unit test `importing_header_rejects_header_with_too_many_authorities` [6](#0-5) .
6. This mandatory header can never be imported by any relayer going forward (its justification set is fixed), so all subsequent, correctly-signed justifications from the new authority set will also fail `verify_justification` since the pallet's `CurrentAuthoritySet` was never updated — the bridge is permanently stuck until a privileged `force_set_pallet_state` root call intervenes.

			new_current_set_id: SetId,

			// known to the pallet - it changes nothing (except for the fact that previously
			// imported headers may still be used to prove something)
			let new_best_header_hash = new_best_header.hash();

	pub(crate) fn initialize_bridge<T: Config<I>, I: 'static>(
		init_params: super::InitializationData<BridgedHeader<T, I>>,
	) -> Result<(), Error<T, I>> {
		let super::InitializationData { header, authority_list, set_id, operating_mode } =
			init_params;
		let authority_set_length = authority_list.len();
		let authority_set = StoredAuthoritySet::<T, I>::try_new(authority_list, set_id)
			.inspect_err(|_| {
				tracing::error!(
					target: LOG_TARGET,
					%authority_set_length,
					max_count=%T::BridgedChain::MAX_AUTHORITIES_COUNT,
					"Failed to initialize bridge. Number of authorities in the set is larger than the configured value"
				);
			})?;
		let initial_hash = header.hash();

		<InitialHash<T, I>>::put(initial_hash);
		<ImportedHashesPointer<T, I>>::put(0);
		insert_header::<T, I>(*header, initial_hash);

		<CurrentAuthoritySet<T, I>>::put(authority_set);

		<PalletOperatingMode<T, I>>::put(operating_mode);

		Ok(())
	}
