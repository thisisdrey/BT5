Based on the codebase investigation, there's a valid analog to the reported go-ethereum GraphQL DoS pattern: **unbounded server-side memory allocation before any pagination/limit is applied**, reachable via a single, unprivileged, crafted RPC field.

### Title
Unbounded in-memory tree materialization in `GetTreeEntries` allows single-request DoS via `recursive=true` - (File: `internal/gitaly/service/commit/get_tree_entries.go`)

### Summary
`CommitService.GetTreeEntries` accepts a `Recursive` flag and a `PaginationParameter.Limit`, but the pagination limit is only applied *after* the entire tree has already been walked and materialized into memory as `[]*gitalypb.TreeEntry`.

### Finding Description
In `sendTreeEntriesUnified`, when `recursive=true` is requested, the server calls `repo.ReadTree(...)` with `localrepo.WithRecursive()` and then walks the *complete* resulting tree, appending every entry into an in-memory slice: [1](#0-0) 

Only after this full walk completes does the code apply sorting and then pagination: [2](#0-1) 

`paginateTreeEntries` itself only slices the already-fully-populated `entries` array — it does not bound how much was read/allocated upstream: [3](#0-2) 

The RPC's own benchmark confirms the scale of allocation involved even for a moderately sized synthetic tree: a single recursive request from root produces 40,419 tree entries fully materialized in memory before any limiting occurs: [4](#0-3) 

For repositories with very large or very deep trees (e.g., monorepos with millions of blobs, as exist in real-world large GitLab instances), a client can set `Recursive=true`, omit or set a huge `PaginationParameter.Limit`, and force Gitaly to allocate one `*gitalypb.TreeEntry` (plus intermediate `localrepo.TreeEntry` walk objects) per file/subtree in the entire history tree in a single RPC call, before truncating to the requested page size. This mirrors the go-ethereum GraphQL issue: the endpoint accepts a single client-controlled query shape that is not bounded up front, causing the server to do unbounded work/allocation to satisfy an unprivileged request.

### Impact Explanation
An authenticated but otherwise unprivileged user with read access to any repository (a routine capability for any project member, or even public repos with public-project APIs proxied to Gitaly) can trigger significant, repeatable memory pressure and CPU consumption per single gRPC call by pointing `Revision`/`Path` at the root of a large tree with `Recursive=true`. Repeated or concurrent calls of this nature can degrade or hang the Gitaly node servicing that repository/storage shard, affecting all other repositories co-located on that storage due to shared process memory — a denial-of-service condition consistent with the "RPC-handler resource limits" analog class in scope.

### Likelihood Explanation
The request shape (`Recursive: true`, no/large `Limit`) is trivially constructible by any client with read access to the `CommitService.GetTreeEntries` RPC and requires no privileged action, leaked token, or malicious peer — only a repository with a sufficiently large tree, which is common in real GitLab installations. Gitaly does have generic `[[concurrency]]` per-RPC queueing/backpressure controls, but these throttle *concurrent* requests rather than bound the *cost* of a single request, so they mitigate but do not eliminate the risk: [5](#0-4) 

### Recommendation
Apply the pagination `Limit` (and any depth/size caps) during the tree walk itself rather than after full materialization — e.g., have the `tree.Walk` callback stop once `limit` entries have been collected instead of collecting the entire tree unconditionally in `sendTreeEntriesUnified`. Consider also enforcing a hard maximum entry count independent of client-supplied `Limit` to cap worst-case memory usage per request.

### Proof of Concept
1. Create or use an existing repository with a very large recursive tree (e.g., hundreds of thousands to millions of blobs across nested directories) — realistic for large GitLab monorepos.
2. As an ordinary user with read access, issue a `GetTreeEntries` RPC with:
   - `Recursive: true`
   - `Path: "."`
   - `PaginationParams` omitted or with a large `Limit`
3. Observe that Gitaly walks and allocates a `TreeEntry` object for every file/subtree in the entire tree (confirmed by the existing benchmark producing 40,419 entries for a synthetic small-scale tree) before applying any pagination cutoff, consuming CPU and memory proportional to total repository tree size rather than the requested page size. [4](#0-3)

func paginateTreeEntries(ctx context.Context, entries []*gitalypb.TreeEntry, p *gitalypb.PaginationParameter, rootTreeOID git.ObjectID) ([]*gitalypb.TreeEntry, string, error) {
	limit := int(p.GetLimit())

	start, tokenTreeOID, tokenType := decodePageToken(p.GetPageToken())

	index := -1

	// No token means we should start from the top
	if start == "" {
		index = 0
	} else {
		for i, entry := range entries {
			if buildEntryToken(entry, tokenType) == start {
				index = i + 1
				break
			}
		}
	}

	if index == -1 {
		return nil, "", structerr.NewInvalidArgument("could not find starting OID: %s", start).WithMetadataItems(
			structerr.MetadataItem{Key: "page_token_tree_oid", Value: tokenTreeOID},
			structerr.MetadataItem{Key: "tree_oid", Value: rootTreeOID.String()},
			structerr.MetadataItem{Key: "token_type", Value: tokenType},
		)
	}

	if limit == 0 {
		return nil, "", nil
	}

	if limit < 0 || (index+limit >= len(entries)) {
		return entries[index:], "", nil
	}

	paginated := entries[index : index+limit]

	newPageToken, err := encodePageToken(paginated[len(paginated)-1], rootTreeOID)
	if err != nil {
		return nil, "", fmt.Errorf("encode page token: %w", err)
	}

	return paginated, newPageToken, nil
}

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
