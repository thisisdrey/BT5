### Title
StorageDeposit intent burns signer's wNEAR with no refund path when target contract rejects the deposit - (File: contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs)

### Summary
`Contract::storage_deposit` in `contracts/defuse/src/contract/intents/state.rs` unconditionally debits the signer's wNEAR balance and unwraps it to real NEAR before the external `storage_management::storage_deposit` call is ever attempted. `do_storage_deposit` schedules that external call but has no `#[private]` resolver to inspect its outcome, so if the target contract rejects or panics on the deposit (e.g. amount below its `storage_balance_bounds().min`), the refunded NEAR is credited back to the Defuse contract's own account balance rather than to the signer, and the signer's internal wNEAR ledger balance is never restored.

### Finding Description
The claimed binding is: `wNEAR debited from signer_id == NEAR that purchased storage on contract_id for deposit_for_account_id OR was returned to signer_id`.

Trace:
1. `Contract::storage_deposit` [1](#0-0)  calls `self.withdraw(...)` which performs `internal_sub_balance` on the signer's wNEAR balance immediately, unconditionally, before any validation against the target contract's actual minimum.
2. It then chains `near_withdraw(...).then(do_storage_deposit(storage_deposit))`, converting the internal wNEAR balance into real NEAR and scheduling the deposit-forwarding callback.
3. `do_storage_deposit` [2](#0-1)  only checks that `near_withdraw` succeeded, then returns `ext_storage_management::ext(storage_deposit.contract_id).with_attached_deposit(storage_deposit.amount)....storage_deposit(...)` as the final promise in the chain (`.detach()` back in `state.rs`).
4. There is no further `.then(...)` callback attached to this final promise, unlike `ft_resolve_withdraw` [3](#0-2)  which explicitly checks the cross-contract result and re-credits (`self.deposit(...)`) any unspent amount back to the sender on failure.
5. If `contract_id`'s `storage_deposit` panics/rejects for being below its minimum bound, the NEAR runtime refunds the attached deposit to the predecessor of that failed call — which is the Defuse contract account itself, not the signer. No code path re-wraps that refunded NEAR into wNEAR or credits the signer's Verifier balance.

Root cause: `do_storage_deposit` has no resolver at all, in contrast to the `ft_withdraw`+`storage_deposit` combo, which at least has `ft_resolve_withdraw` to refund the FT-transfer portion (even though that path has its own gaps for the storage-deposit sub-call). For the standalone `StorageDeposit` intent, there is zero refund/resolve logic on any failure of the forwarded `storage_deposit` call.

None of the existing guards (`MultiPayload::verify`, nonce checks, `assert_one_yocto`, `#[private]`) address this: they only ensure the intent itself is authentically signed and once-only; they do nothing to prevent silent loss of value after a legitimately-authorized `StorageDeposit` intent triggers a failing downstream call.

### Impact Explanation
The signer's wNEAR balance is permanently destroyed from the Verifier's internal accounting whenever the forwarded `storage_deposit` call to `contract_id` fails for any reason (insufficient amount vs. minimum bound, non-existent account, paused contract, etc.), since the resulting refunded NEAR lands on the Defuse contract's own account, outside of the internal ledger, and can never be reclaimed by the signer or reconciled with any balance. This is a guaranteed, repeatable, permanent loss of user funds for every account attempting `StorageDeposit` against any target whose deposit call can reject the amount, matching the Critical category "user funds permanently frozen."

### Likelihood Explanation
Trivial to trigger: the attacker only needs standard wNEAR holdings and knowledge of a public FT contract's `storage_balance_bounds().min` (a routinely queryable view method), then self-sign a `StorageDeposit` intent with an amount below that bound. No privileged role, relayer key, or victim key is required — the attacker acts against their own account and their own funds, but the same defect equally destroys value for any unwitting signer whose `StorageDeposit` intent happens to be rejected by the target contract for any reason.

### Recommendation
Add a `#[private]` resolver analogous to `ft_resolve_withdraw` that is chained after the `ext_storage_management::storage_deposit` promise in `do_storage_deposit`, inspects the promise result, and on failure re-wraps the un-consumed NEAR back into wNEAR (via `ext_wnear::near_deposit` or similar) and credits it back to the signer's account via `self.deposit(...)`. Alternatively, validate the target's `storage_balance_bounds().min` before debiting/unwrapping, though a resolver is still required to handle any other failure modes (paused/removed accounts, arbitrary panics).

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
