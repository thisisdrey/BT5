### Title
Path traversal (zip-slip) during tar extraction in Gitaly recovery/replay and recovery/restore tooling due to missing path-containment validation - ([File: internal/cli/gitaly/subcmd_recovery_replay.go])

### Summary
`extractArchive()` (used by `gitaly recovery replay` to unpack archived WAL log entries) and `extractBackup()` (used by `gitaly recovery restore` to unpack partition backups) both join tar header names directly onto a destination directory without verifying the resulting path stays inside that directory. This is the same bug class as the reported "missing whitelist/validation check" finding: a security check that exists elsewhere in the very same codebase (path-containment validation) is simply absent here, allowing crafted archive entries to write outside the intended staging directory.

### Finding Description
In `internal/cli/gitaly/subcmd_recovery_replay.go`, `extractArchive()` computes the extraction target as: [1](#0-0) 
with no check that `target` remains within `path`. The same pattern exists in `internal/cli/gitaly/subcmd_recovery_restore.go`'s `extractBackup()`: [2](#0-1) 

This is the exact commented-out-whitelist analog: Gitaly already implements the correct containment check elsewhere, in `internal/gitaly/service/repository/replicate.go`'s `extractTarToDirectory()`, which explicitly validates that every regular file, directory, hard link, and symlink target stays under `targetDir` before writing: [3](#0-2) [4](#0-3) 

Neither `extractArchive()` nor `extractBackup()` perform this validation. `extractArchive()` is fed WAL log entries pulled from `rc.logEntryStore` (archived transaction log entries written during ordinary repository writes/replication), and `extractBackup()` is fed backup tarballs of partition filesystem state pulled from the configured backup sink: [5](#0-4) [6](#0-5) 

If any tar entry name in these archives can be influenced (e.g. `../../../etc/cron.d/x`), a symlink or `..`-containing path in `header.Name` will escape the `stagingDir`/`partitionTempDir` and write attacker-controlled content to arbitrary locations reachable by the Gitaly recovery process, before the extracted contents are subsequently trusted and either appended to the WAL (`logWriter.CompareAndAppendLogEntry`) or moved into the live storage (`moveRepositoryToStorage`).

### Impact Explanation
Because this analog concerns extraction of backup/log data used to restore repository/partition state, a successful path traversal could overwrite arbitrary files on the Gitaly node's filesystem (outside the intended staging directory), potentially leading to data corruption of unrelated files, or planting files in sensitive locations depending on the privileges of the Gitaly process. This satisfies "concrete storage escape" / "extraction escape" per the accepted impact categories.

### Likelihood Explanation
Exploitation requires that archived WAL entries or partition backups contain a tar entry whose `Name` includes path-traversal sequences, and that an operator subsequently runs `gitaly recovery replay` or `gitaly recovery restore` against the affected partition/storage. The missing validation is unconditional (no gating at all), unlike the properly hardened `extractTarToDirectory()` used by the `ReplicateRepository` RPC, so any archive content that ends up containing such names — whether from internal miscoding, corruption, or content influenced by earlier transactional writes — will not be rejected.

### Recommendation
Add the same containment checks used in `extractTarToDirectory()` (in `internal/gitaly/service/repository/replicate.go`) to both `extractArchive()` and `extractBackup()`: for every tar entry, verify `filepath.Clean(target)` is equal to or a descendant of the destination root (`strings.HasPrefix(target, root+string(os.PathSeparator))`) before creating directories/files, and reject or safely resolve symlink/hardlink targets that would escape the destination directory.

### Proof of Concept
1. Construct a tar archive (to be consumed as a WAL log entry or backup) containing an entry with `Name: "../../../../tmp/evil"` and `Typeflag: tar.TypeReg`.
2. Feed this archive through `processLogEntry` → `extractArchive` (`internal/cli/gitaly/subcmd_recovery_replay.go:196` calling `extractArchive` at line 218) or through `extractBackup` (`internal/cli/gitaly/subcmd_recovery_restore.go:84`).
3. Observe that `target := filepath.Join(path, header.Name)` resolves outside `stagingDir`/`partitionTempDir`, and `os.OpenFile(target, ...)` writes the file outside the intended staging area — unlike `extractTarToDirectory()` in `replicate.go`, which would reject such an entry with `"invalid file path in tar"`.
