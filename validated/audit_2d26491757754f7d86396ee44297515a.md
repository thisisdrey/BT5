### Title
Unbounded token inflation via zero-balance `skip_deduct` exemption in `promise_yield_create_with_id` - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
`promise_yield_create_with_id` allows a zero-balance account to attach `amount = 1 yoctoNEAR` to a self-targeted `FunctionCall` action while skipping the real balance deduction whenever `current_account_balance.is_zero()` and `one_yocto_on_promise` is enabled. Because the created yield receipt's receiver is the calling account itself, the eventual resolution of the receipt will credit that same account's balance by `amount` through the standard receipt-processing path, while the sending side never debited anything, and `subsidized_amount` is only accumulated with `checked_add` and never reconciled against real, spendable balance.

### Finding Description
In `promise_yield_create_with_id` [1](#0-0) , the yield receipt is always created against `self.context.current_account_id.clone()` [2](#0-1) , i.e. the created `FunctionCall` action is a self-callback. When the attacker calls it with `amount = 1 yoctoNEAR`, `one_yocto_on_promise` enabled, and `current_account_balance` already at zero, the code takes the `skip_deduct` branch and only bumps an in-memory `subsidized_amount` counter via `checked_add` instead of calling `deduct_balance` [3](#0-2) . The outgoing action is still built with the real, non-zero `amount` field [4](#0-3) , so when the resulting receipt is later processed by the runtime (either via `promise_yield_resume` or via the timeout path), the receiving side's standard action-application logic will credit the (same) account's balance by that `amount`, since receipt processing has no notion of "subsidized" deposits and credits balance unconditionally based on the action's `amount` field. No code was found in the reachable portion of `logic.rs` or `runtime/runtime/src/lib.rs` that reconciles `subsidized_amount` against the account's real balance at the end of the transaction/receipt, nor any cap bounding how many times this branch can be hit besides the ambient gas metering (`pay_base`, `prepay_gas`, `pay_gas_for_new_receipt`).

An unprivileged attacker can deploy a contract whose account balance is fully consumed by storage staking (a realistic and attacker-controllable state, i.e. `amount == 0`), then submit a `FunctionCall` transaction that loops calling `promise_yield_create_with_id` with `amount = 1`, `gas` set low, and a fresh 32-byte `yield_id` each iteration. Each iteration is bounded only by the transaction's `max_gas_burnt`/`max_number_logs`-style gas limits, not by a per-call or per-account cap tied to actual balance, allowing many (bounded by gas headroom) 1-yoctoNEAR self-credited yield promises per transaction, repeatable across further transactions with no lifetime cap.

### Impact Explanation
This breaks value conservation: balance is created ("minted") on the resolution side of a receipt without ever having been deducted on the creation side, for accounts whose real balance is (and remains) zero. This maps to NEAR's "token inflation or loss" bounty category. The magnitude per receipt is tiny (1 yoctoNEAR), so a single transaction's impact is economically negligible, but the mechanism has no explicit lifetime/global cap tying `subsidized_amount` back to actually-available funds, meaning it is repeatable indefinitely across transactions by any account that maintains a zero liquid balance.

### Likelihood Explanation
Preconditions are attacker-controlled and unprivileged: deploy a contract, drain/keep its liquid balance at exactly zero (e.g., by having balance fully absorbed into storage staking), and issue a wasm call looping `promise_yield_create_with_id` with `amount=1`. No special permissions, validator access, or leaked keys are required. It is fully repeatable across arbitrary numbers of transactions, at ordinary gas cost. Feasibility of a large-scale, materially significant inflation event is not established here — I was not able to fully trace the exact receipt-processing/action-application code path in `runtime/runtime/src/lib.rs` that ultimately credits the receiving account's balance for `FunctionCallAction.amount`, nor confirm whether `subsidized_amount` is used for a distinct reconciliation check elsewhere in the transaction/receipt lifecycle that I did not reach before running out of investigation budget. This is a real gap in my verification, not a confirmed absence.

### Recommendation
- Track `subsidized_amount` against a hard per-transaction/per-receipt cap (or eliminate the exemption for `promise_yield_create_with_id` entirely), and ensure that whatever mechanism ultimately applies the `FunctionCallAction.amount` on receipt execution is made aware of "subsidized" (non-debited) deposits so it does not credit real balance for them.
- Alternatively, do not allow `skip_deduct` to bypass balance deduction when the promise's receiver is the same account as the sender (self-callback), since in that case the "exemption" directly becomes a self-mint rather than a genuine fee waiver on a transfer to a third party.
- Add an explicit reconciliation step at the end of function execution (or at receipt application) that validates total subsidized/credited amounts against the account's actual, provable balance capacity.

2. Loop calling `promise_yield_create_with_id` with `amount = 1`, a fresh 32-byte `yield_id` each iteration, and minimal `gas`, until gas is exhausted.
3. Assert `result_state.subsidized_amount` grows unboundedly (proportional to iteration count) rather than being capped.
4. In a runtime-level integration test (e.g. extending `runtime/runtime/src/tests/apply.rs`), drive the created receipts to resolution (via `promise_yield_resume` or timeout) and assert whether the self-account's final `amount`/balance increases beyond what was ever debited from it, demonstrating net balance creation with no corresponding deduction — this is the key assertion that would confirm actual on-chain token inflation versus a purely local/no-op counter.
