### Title
Exchange creator can front-run a trader's `ExchangeTransactionContract` with inject/withdraw to extract value beyond the trader's slippage protection - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The bounty report describes an artist front-running a `buy()` transaction by adjusting fee parameters right before the trade executes, extracting extra value while only being bounded by the user's loose slippage (`msg.value`) protection. The equivalent construct in java-tron is the bancor-style TRC10 `Exchange`: any unprivileged account can submit an `ExchangeTransactionContract` (a swap) specifying `expected` as its only slippage guard, while the exchange's `creatorAddress` can submit `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions that instantly change the pool ratio just before the trader's transaction is applied in the same block.

### Finding Description
`ExchangeTransactionActuator.doValidate()` checks that the swap output is at least `tokenExpected` computed from the *current* pool ratio at validation time [1](#0-0) , and `execute()` recomputes the swap using `exchangeCapsule.transaction(...)` against whatever pool state exists at execution time, with no re-check against `tokenExpected` in `execute()` itself [2](#0-1) . The exchange's `creatorAddress` freely controls the pool ratio through `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, both of which only require that the caller equal `exchangeCapsule.getCreatorAddress()` and require no cooldown or timelock [3](#0-2) . Because the creator can place an `ExchangeWithdrawContract` transaction ahead of a pending trader's `ExchangeTransactionContract` in the same block (analogous to the reported Flashbots-style fee-change-then-buy-then-restore sequence), the creator can shift the exchange ratio to the least favorable value the trader's `tokenExpected` will still tolerate, extracting the difference for themselves - exactly the class of attack described in the report, where a privileged/insider party manipulates state between transaction broadcast and execution and the victim's only protection is a loose value the trader is forced to set generously to avoid unrelated failures.

### Impact Explanation
An order placer's trade can be executed at a materially worse price than the pool state visible at broadcast time, with the difference captured by the exchange creator, constituting unauthorized value extraction from a counterparty's transaction (theft of expected trade value) without the trader's consent.

### Likelihood Explanation
The creator address is a normal (non-SR, non-committee) account that legitimately owns and can freely rebalance its exchange at will, and can observe pending swap transactions in the mempool before block packing, making this an low-cost, repeatable value-extraction pattern for any TRC10 exchange creator, similar to the reported artist behavior.

### Recommendation
Bound how much a single creator inject/withdraw can move the pool ratio per block, or apply a time-weighted/TWAP-based execution price for `ExchangeTransactionActuator` instead of the instantaneous spot ratio, and/or require the trader's `tokenExpected` check to also be re-validated in `execute()` against a price captured at submission rather than a value recomputed after arbitrary pool changes in the same block.

### Proof of Concept
1. Creator sets up an exchange with tokens A/B at ratio 100:100.
2. Trader broadcasts `ExchangeTransactionContract` selling A for B with a loosely-set `expected` (e.g., accepting up to 20% slippage) [1](#0-0) .
3. Creator observes the pending transaction and submits `ExchangeWithdrawContract` in the same block ahead of it, draining liquidity to shift the ratio to the edge of what the trader's `expected` will still accept [3](#0-2) .
4. Trader's `ExchangeTransactionActuator.execute()` swaps at the now-worse ratio, receiving the minimum tolerated amount while the creator captures the surplus [2](#0-1) .
5. Creator can optionally re-inject liquidity afterward to restore the original ratio, hiding the manipulation.
