### Title
Per-receipt storage-proof limit is silently bypassed for non-`FunctionCall` actions when `EnforcePerReceiptStorageProofLimit` is enabled without `EnforceStorageProofLimitForAllActions` - (File: `runtime/runtime/src/lib.rs`)

### Summary
In `apply_action_receipt`, the receipt-level storage-proof-size check that catches trie growth from actions outside the wasm VM (e.g. `Transfer`, `AddKey`, `DeleteKey`) is guarded by a *second*, independently-gated feature (`EnforceStorageProofLimitForAllActions`). When only `EnforcePerReceiptStorageProofLimit` is active, `storage_proof_size_before_receipt` is computed but never compared against any limit, so a receipt composed solely of non-`FunctionCall` actions can grow the recorded storage proof without bound, because the only other enforcement mechanism, `RecordedStorageCounter`, is wired exclusively into the VM path for `FunctionCall` actions.

### Finding Description
`apply_action_receipt` computes `storage_proof_size_before_receipt` whenever `EnforcePerReceiptStorageProofLimit` is enabled: [1](#0-0) 

But the actual comparison against the limit only runs when `storage_proof_limit_for_all_actions` is `Some`, which is only set when the *separate* feature `EnforceStorageProofLimitForAllActions` is enabled: [2](#0-1) 

The comment directly preceding this logic states the root cause explicitly: "The in-VM `RecordedStorageCounter` only bounds `FunctionCall` actions." [3](#0-2) . `RecordedStorageCounter` is instantiated and consulted only inside the VM logic path (`runtime/near-vm-runner/src/logic/logic.rs`, `wasmtime_runner/mod.rs`), which is only invoked for `FunctionCall` actions — it has no visibility into `Transfer`, `AddKey`, `DeleteKey`, `DeleteAccount`, etc.

Consequently, in a protocol-version window where `EnforcePerReceiptStorageProofLimit` is enabled but `EnforceStorageProofLimitForAllActions` is not, a receipt whose actions are exclusively non-`FunctionCall` (e.g. many `DeleteKey`/`AddKey` actions touching many distinct trie paths) can grow `state_update.trie.recorded_storage_size_upper_bound()` arbitrarily within the loop at line 892-951 without ever hitting a size check, because the `if let (true, Some(size_before), Some(limit))` guard at line 928 fails on the `None` `limit` and the per-action check is skipped entirely for the whole receipt.

An unprivileged attacker only needs to submit a transaction/receipt with many `AddKey`/`DeleteKey` (or similar non-`FunctionCall`) actions against keys/paths that force many distinct trie node reads, inflating the storage witness/proof size that the limit was designed to cap, all without needing to deploy or call any contract code.

### Impact Explanation
The per-receipt storage-proof-size limit exists to bound the size of the storage proof (state witness) associated with executing a single receipt, which is central to stateless validation — an oversized, unbounded proof directly threatens chunk-witness generation/validation feasibility for chunk producers/validators. If the receipt-level guard is bypassed for non-`FunctionCall` actions under the described protocol-version configuration, an attacker can grow the recorded storage proof of a chunk beyond intended bounds using ordinary account-management actions, undermining the stateless-validation size guarantees the feature is meant to provide. This falls into the "state-root divergence / chain-halt-adjacent resource limit" category to the extent the bypassed limit was relied upon as a hard bound for witness size, though the ultimate severity is contingent on whether the described intermediate protocol-version state is ever a real, sustained configuration on mainnet (i.e., both features stabilized at different, non-adjacent protocol versions, with a nontrivial rollout window between them).

### Likelihood Explanation
Reaching this bug requires no privileged access — a normal signed transaction with a batch of cheap non-`FunctionCall` actions suffices, and the flaw is triggered purely by which protocol-version feature flags are active, not by any contract logic. However, exploitability hinges entirely on whether `EnforcePerReceiptStorageProofLimit` and `EnforceStorageProofLimitForAllActions` are ever active independently at the same time on a live network (i.e., whether they are stabilized at different protocol versions with a real window in between). I was not able to confirm from the indexed code the exact protocol version numbers assigned to each feature in `core/primitives-core/src/version.rs`, so I cannot confirm whether such an intermediate, reachable mainnet protocol-version state exists or has ever existed (the repository's index only exposed general enum declarations, not the specific version constants for these two entries). This is a material uncertainty for real-world exploitability.

### Recommendation
Make the receipt-level storage-proof check unconditional on `EnforcePerReceiptStorageProofLimit` alone (using `per_receipt_storage_proof_size_limit` directly) rather than requiring the second, independent `EnforceStorageProofLimitForAllActions` flag, or merge the two features into a single gate so they can never be enabled independently. At minimum, ensure `EnforceStorageProofLimitForAllActions` is stabilized at the same or an earlier protocol version than `EnforcePerReceiptStorageProofLimit` so no window exists where the limit is silently unenforced for non-`FunctionCall` actions.

### Proof of Concept
1. In `runtime/runtime/src/tests/apply.rs`, construct a test `ApplyState` pinned to a protocol version where `ProtocolFeature::EnforcePerReceiptStorageProofLimit::enabled()` returns `true` and `ProtocolFeature::EnforceStorageProofLimitForAllActions::enabled()` returns `false` (verify such a version value exists by inspecting `core/primitives-core/src/version.rs`'s `PROTOCOL_VERSION`/`ProtocolFeature` stabilization table).
2. Set `wasm_config.limit_config.per_receipt_storage_proof_size_limit` to a small value (e.g. a few hundred bytes).
3. Build an action receipt with no `FunctionCall` action — e.g. many `AddKey` actions targeting distinct keys, or many `DeleteKey` actions against an account pre-populated with many access keys spread across many distinct trie paths — sized so that reading/removing the associated trie nodes provably exceeds `per_receipt_storage_proof_size_limit` in recorded storage size.
4. Call `apply_action_receipt` (or run through `Runtime::apply`) with this receipt and assert:
   - `state_update.trie.recorded_storage_size_upper_bound()` growth exceeds the configured limit.
   - `result.result` is `Ok(..)` (execution succeeds) and no `ActionErrorKind::ReceiptStorageProofSizeExceeded` error is produced.
5. Re-run the same test with `EnforceStorageProofLimitForAllActions` also enabled and confirm the error *is* now raised, demonstrating the gap is caused specifically by the independent gating shown in `runtime/runtime/src/lib.rs:879-889,928-945`.
