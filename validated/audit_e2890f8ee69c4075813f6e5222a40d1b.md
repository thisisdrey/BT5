### Title
Instantaneous-Utilization Interest Index Applied Retroactively Over Stale Time-Delta Enables Same-Block Collateral/Debt Value Manipulation - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar])

### Summary
The vault interest-index accrual mechanism computes the borrow/liquidity multiplier using the **current, spot** utilization-derived rate and applies it over the **entire elapsed time** since the last accrual (`last-update`), without any check that the rate held constant over that period. Because this rate is trivially manipulable by an ordinary principal within the same transaction, and the resulting index is cached and trusted for the rest of the block by the market's per-block `index-cache-`, this is a direct analog of the reported "auto-roll price" bug: an unverified, single-observation value (there: last executed order price; here: instantaneous utilization rate) is trusted to compute a downstream value (there: `estimatedAutoRollUnitPrice`; here: `next-index`/`next-liquidity-index`) used by many other operations, and it can be skewed with minimal capital right before the value is captured.

### Finding Description
Each vault's accrual logic is: [1](#0-0) 

`next-index` and `next-liquidity-index` compute `rate`/`liquidity-rate` from `(interest-rate)`, which is `(interpolate-rate (utilization) utils rates)` — i.e., the **utilization at the moment of the call**: [2](#0-1) 

That instantaneous rate is then multiplied by `time-delta = stacks-block-time - last-update`, which can be large if the vault has been idle (no borrow/repay/supply/redeem for hours or days), via `calc-multiplier-delta`. The resulting `next`/`nliq` are written back and used to mint treasury LP shares in `accrue`: [3](#0-2) 

The market contract caches whichever index/lindex value is produced by the **first** call touching a given asset within a block, and reuses it for every subsequent operation in that same block: [4](#0-3) 

This cached `lindex` is used unmodified to price zTokens used as collateral: [5](#0-4) 

and the cached `index` is used to compute the USD value of debt in health/liquidation calculations: [6](#0-5) 

Because `interest-rate()` depends only on the utilization at call time, and utilization is itself a function of the vault's `available-assets`/`total-debt` (both mutable by ordinary borrow/supply/redeem calls), an attacker's own contract can, in one atomic transaction:
1. Spike (or collapse) a target vault's utilization with a large borrow (using their own capital, not a flashloan) right before the vault has its first accrual of the block.
2. Trigger `accrue-and-cache` for that asset (e.g., by touching it as collateral/debt in a market call), which computes `next-liquidity-index`/`next-index` using the manipulated instantaneous rate compounded over the vault's entire stale `time-delta`, producing an artificially inflated index.
3. Immediately consume that cached, inflated `lindex` via `resolve-ztoken` to overvalue zToken collateral (or the inflated `index` to under/overstate debt) in a borrow, liquidation, or health-check call in the same block.
4. Reverse the utilization-spiking action (e.g., repay) before the transaction ends, restoring the vault to its prior state.

This is the same bug class as the report: a value that should reflect a verified, time-weighted, manipulation-resistant observation is instead derived from a single unverified spot sample and then trusted for downstream financial calculations for an entire settlement period (there: the whole next market epoch; here: the whole idle time-delta and the whole subsequent block).

### Impact Explanation
An attacker can use an artificially inflated `lindex` (cached for the block) to overstate the USD value of zToken collateral they hold, enabling them to borrow more than their real collateral backs — direct theft of protocol funds and potential protocol insolvency. Alternatively, they can manipulate `index` to distort other users' debt valuation within the same block, affecting liquidation health checks. This lands squarely on the Critical impact category: direct theft of user funds and protocol insolvency risk.

### Likelihood Explanation
The precondition (a vault idle for a meaningful `time-delta` since its `last-update`) is common for low-activity vaults (e.g., stSTXbtc, USDH). The manipulation requires only capital the attacker already controls to move utilization momentarily and does not require any privileged role, oracle compromise, or flashloan whitelist access — it can be executed entirely from the attacker's own deployed contract in a single atomic call, matching the "ordinary principal / own deployed contract" reachability required by scope.

### Recommendation
Do not apply a single spot-utilization rate over an unbounded elapsed `time-delta`. Instead, checkpoint/accrue on every state-changing operation that alters utilization (so `time-delta` between rate changes stays minimal), or use a time-weighted/twap utilization rate for the interval, or cap the impact of a single block's rate change on the multiplier. Additionally, the per-block `index-cache-` should not let one caller's rate-affecting action silently determine the index used for all other participants in the same block for high-value operations (borrow against collateral, liquidation) — consider recomputing or bounding the index change permitted within one block.

### Proof of Concept
1. Deploy attacker contract `Atk`.
2. Wait/observe a vault (e.g., `v0-vault-ststxbtc`) that has not been accrued for a long period (`stacks-block-time - last-update` large).
3. In one atomic call from `Atk`:
   a. Call `system-borrow`/market borrow to sharply raise `utilization()` on the target vault using attacker-owned liquidity.
   b. Perform a market action that touches the same asset as collateral (triggering `accrue-and-cache`, which computes and caches an inflated `next-liquidity-index` because `interest-rate()` is now high and `time-delta` is large).
   c. Immediately borrow against zToken collateral of that vault; `resolve-ztoken` prices it using the newly-cached inflated `lindex`, permitting a larger borrow than actual collateral value supports.
   d. Repay/undo step (a) to restore vault state, ending the atomic transaction with extracted excess borrowed value.

This confirms the root cause is the unverified, spot-rate-over-stale-interval index computation (`next-index`/`next-liquidity-index` in `v0-vault-*.clar`) combined with the market's per-block trust of that single cached value (`accrue-and-cache`/`resolve-ztoken` in `v0-4-market.clar`), directly paralleling the reported `estimatedAutoRollUnitPrice` unverified-price manipulation.
