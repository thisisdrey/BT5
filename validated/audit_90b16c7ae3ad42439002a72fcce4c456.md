### Title
Object-directory quarantine bypass allows cross-repository object directory escape - ([File: internal/git/localrepo/paths.go])

### Summary
`Repo.ObjectDirectoryPath` in `internal/git/localrepo/paths.go` computes the effective git object directory for an RPC-supplied `Repository.GitObjectDirectory` field. It contains a special-case bypass, `isTransactionQuarantineDir`, that is supposed to recognize paths created internally by Gitaly's transaction manager (which live at `<tmpdir>/quarantine[/tmp_objdir-*]`). However the condition only checks the *basename* of the path, not its actual origin, so any client-supplied `GitObjectDirectory` value whose final path component is literally `quarantine` (or a `tmp_objdir*`-prefixed sibling under a `quarantine` parent) skips the stricter repository-scoped validation entirely — exactly the same class of bug as the source report: a validation condition intended to restrict acceptable values is too permissive and effectively lets attacker-controlled input through unchecked.

### Finding Description
The relevant logic: [1](#0-0) 

Flow:
1. `filepath.Join(repoPath, objectDirectoryPath)` is validated only against `storagePath` (the whole storage root, which may contain many repositories), via `storage.ValidateRelativePath(storagePath, ...)`. This first check only prevents escaping the *storage*, not the specific repository. [2](#0-1) 
2. `isTransactionQuarantineDir` is computed purely from `filepath.Base` of the resulting relative path: `baseDir == "quarantine"` or (`parentDir == "quarantine"` and `baseDir` has prefix `tmp_objdir`). [3](#0-2) 
3. If `isTransactionQuarantineDir` is true, the code **skips** the second, repository-scoped check (`storage.ValidateRelativePath(repoPath, objectDirectoryPath)` plus the `expectedQuarantinePrefix` hash-based ownership check) entirely. [4](#0-3) 

Because the bypass only inspects the final path component's literal name rather than proving the path was actually produced by `quarantine.New`/`storage.QuarantineDirectoryPrefix` (which ties a quarantine directory to a specific repository via a SHA1 hash of its relative path, as seen in `internal/gitaly/storage/locator.go:206-212` and used correctly in the code path that is being skipped), an attacker who controls the `GitObjectDirectory` field of a `Repository` message in an RPC request can supply any storage-relative path (e.g. pointing into another repository's directory tree, or an arbitrary directory in the storage) as long as its last path segment is named `quarantine`. That value only needs to satisfy the loose, storage-wide `ValidateRelativePath` check in step 1 — it does not need to actually be a directory created by the transaction manager. This effectively defeats the ownership check that the second, correct validation path (`expectedQuarantinePrefix` `HasPrefix`) was designed to enforce.

This is directly analogous to the audited bug: a boolean validation condition (`isTransactionQuarantineDir`) meant to accept only a narrow, well-defined class of paths ends up accepting a much broader class due to insufficiently strict matching logic, silently disabling the "real" validation step that follows.

### Impact Explanation
`GitObjectDirectory`/`GitAlternateObjectDirectories` are used throughout Gitaly (e.g. size calculations, alternates files, object lookups) to point git at an alternate object store for a repository. If `ObjectDirectoryPath` returns a path belonging to a different repository (or an attacker-influenced directory) due to this bypass, subsequent git operations performed against the "object directory" of the repository can read from or, depending on the calling RPC, potentially be influenced to interact with objects outside the intended repository boundary — a cross-repository object access issue. This can be leveraged for information disclosure across repositories that share a storage, or as a building block to corrupt/confuse consumers relying on `ObjectDirectoryPath`'s validation to guarantee repository-scoping.

### Likelihood Explanation
`GitObjectDirectory` is a normal, client-settable field on the `Repository` protobuf message that ordinary RPC callers pass, and `ObjectDirectoryPath` is invoked on the server side to resolve that field to a filesystem path (e.g. from `internal/gitaly/service/repository/size.go`). No special privilege is required beyond issuing an RPC that carries a `Repository` message with a crafted `GitObjectDirectory` value ending in `.../quarantine` or `.../quarantine/tmp_objdir-*`, which is easily reachable for any ordinary user/client of Gitaly's gRPC surface. The bypass condition is a pure string/basename check with no cryptographic or unpredictable component, and construction of a colliding path (e.g. `"../<other-repo>/quarantine"`) is straightforward as long as the storage-wide `ValidateRelativePath` check permits it.

### Recommendation
Do not treat any path whose basename is `quarantine`/`tmp_objdir*` as trusted merely based on name. Instead, always perform the repository-scoped `storage.ValidateRelativePath(repoPath, objectDirectoryPath)` check first, and only invoke the special-cased "transaction quarantine directory" logic as a fallback that must additionally verify the path lies under the repository/storage's expected temp directory and carries the repository-specific `QuarantineDirectoryPrefix` hash (the same ownership check already implemented for the non-quarantine fallback branch). In other words, unify the two branches so that *every* path outside `repoPath` — including ones whose basename happens to be `quarantine` — is required to match `expectedQuarantinePrefix` derived from `storage.QuarantineDirectoryPrefix(repo)`, never accepted purely by name.

### Proof of Concept
1. Attacker sends an RPC (any RPC that accepts a `Repository` message and internally resolves `ObjectDirectoryPath`, e.g. via `internal/gitaly/service/repository/size.go`) with:
   - `StorageName`: the shared storage
   - `RelativePath`: attacker's own repository
   - `GitObjectDirectory`: a relative path such as `"../victim-repo.git/quarantine"` (or any storage-relative path ending in `/quarantine`) that exists on disk within the same storage (e.g. an attacker can even create an arbitrary directory named `quarantine` under a repository they control, then reference it via a `..` traversal to point elsewhere, or target a path under a real victim repository if such a directory name coincidentally exists).
2. `ObjectDirectoryPath` joins `repoPath` with the given `objectDirectoryPath`; `storage.ValidateRelativePath(storagePath, ...)` succeeds because the resulting path stays inside `storagePath` (the whole storage root, not the specific repo).
3. `baseDir` is computed as `"quarantine"`, causing `isTransactionQuarantineDir` to evaluate `true`.
4. The repository-scoped check (`storage.ValidateRelativePath(repoPath, objectDirectoryPath)` plus the `QuarantineDirectoryPrefix` ownership check) is skipped entirely.
5. `ObjectDirectoryPath` returns the joined path pointing outside `repoPath`, into another location in the storage, without verifying it belongs to the calling repository.
