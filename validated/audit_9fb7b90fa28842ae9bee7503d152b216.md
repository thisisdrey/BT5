## Title
StackerDB chunk signatures omit the target smart-contract ID, enabling cross-contract chunk replay for the `signers-{0,1}-{message_id}` databases - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The bug-class hint (an authorization check that can be satisfied by data that was never actually authorized for the checked context) maps onto the StackerDB chunk-authentication scheme: a chunk's signature commits only to `(slot_id, slot_version, data_hash)` and never to the StackerDB smart-contract identifier it is destined for. Since several distinct StackerDB contracts (`signers-0-0`, `signers-0-1`, `signers-0-2`, i.e. one per `MessageSlotID`) share the exact same signer→slot_id mapping for a given signer set, a chunk that a signer legitimately authored and broadcast for one contract (e.g. `BlockResponse`) is a fully valid, verifiable chunk for a *different* contract (e.g. `BlockPreCommit`) at the same slot id — without the signer ever having authorized that content for that message type.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::sign`/`verify` operate purely on this digest, with no domain separation for the smart contract that owns the slot: [2](#0-1) 

Both the write path (`StackerDBTx::try_replace_chunk`) and the read/verification path (`PeerNetwork::validate_received_chunk`) look up the expected signer *per (contract, slot_id)* and then call `slot_desc.verify(&signer)`, but the signature itself carries no binding to which contract it was made for: [3](#0-2) [4](#0-3) 

Critically, the `.signers` boot contract assigns the *same* slot ordering to *every* message-type contract for a given signer set (`page u0`/`page u1`, shared across all `signers-{set}-{message_id}` contracts): [5](#0-4) [6](#0-5) 

and `MessageSlotID` enumerates multiple distinct contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) that are all resolved via `NakamotoSigners::make_signers_db_contract_id`, differing only by the numeric message-type suffix in the contract name: [7](#0-6) 

Because a given signer occupies the same `slot_id` in every one of these sibling contracts, and the signature that authenticates a chunk write never encodes *which* contract it is for, a chunk that signer `S` legitimately produces and broadcasts for contract `signers-0-1` (`BlockPreCommit`) is byte-for-byte a valid, correctly-signed chunk for contract `signers-0-0` (`BlockResponse`) at the same slot, provided the target slot's current stored version is lower than the replayed chunk's version. Any network peer that observes the legitimately-gossiped chunk (chunks are pushed/relayed via `StackerDBPushChunk` p2p messages and served over `GET /v2/stackerdb/...`) can resubmit it against the other contract; `validate_received_chunk`/`try_replace_chunk` will accept it because the only fields checked are slot id, version, hash and address — none of which differ across the sibling contracts — and the node will store it and further gossip it via `process_stacker_db_chunks`, causing forged/misattributed data to be propagated network-wide as if it were an authentic message of the wrong type: [8](#0-7) 

### Impact Explanation
This lets an unprivileged network participant relay a signer's message for one signer-protocol message type (e.g. a `BlockPreCommit`) into another message type's StackerDB replica (e.g. `BlockResponse`) as if the signer authored that data for that purpose, without possessing the signer's private key. Because `process_stacker_db_chunks` re-broadcasts anything successfully stored, this is a network-wide propagation of forged/misattributed data into a StackerDB context that the signer never authorized, satisfying the "network-wide propagation of forged data" criterion. It can corrupt the signer-message state consumed by other signers/miners (e.g. tricking the `StackerDBListener`/global state evaluator or signer client that reads out of the wrong contract's slots) since consumers key off `slot_id` and signer address only, and would parse whatever bytes are stored as the message type expected for that contract, potentially causing parse-failures, stale/duplicate views, or acceptance of attacker-selected data as if authored for that message type/version.

### Likelihood Explanation
No secret key material is required — only the ability to observe a legitimately-gossiped/served chunk (public by design) and resend it to a different, but existing, StackerDB endpoint reachable by any peer. The preconditions (same signer occupying the same `slot_id` across sibling `signers-{set}-{message_id}` contracts, and the target slot's stored version being behind the replayed version) are naturally satisfied during ordinary signer-set operation, making this readily reachable without special timing tricks.

### Recommendation
Bind the target StackerDB's smart-contract identifier (and ideally the reward-cycle/signer-set epoch) into `SlotMetadata::auth_digest()` so that a signature is only valid for the specific `(smart_contract_id, slot_id, slot_version, data_hash)` tuple it was created for, preventing replay of a validly-signed chunk across sibling or unrelated StackerDB contracts.

### Proof of Concept
1. Signer `S` is assigned `slot_id = k` in both `signers-0-0` (BlockResponse) and `signers-0-1` (BlockPreCommit) contracts, per the shared `stackerdb-get-signer-slots-page` mapping shown above.
2. `S` signs and pushes chunk `C = (slot_id=k, slot_version=v, data=D)` to `signers-0-1`; the signature only commits to `(k, v, hash(D))` per `auth_digest()`.
3. Any peer observes `C` (via `StackerDBPushChunk` p2p relay or `GET /v2/stackerdb/.../chunks/{k}` on `signers-0-1`) and resends the identical `(slot_id, slot_version, sig, data)` tuple to `signers-0-0` via `POST /v2/stackerdb/.../chunks` (or as an unsolicited `StackerDBPushChunk` targeting `signers-0-0`'s contract id), where the current stored version for slot `k` is `< v`.
4. `PeerNetwork::validate_received_chunk` / `StackerDBTx::try_replace_chunk` for `signers-0-0` looks up the same signer address for slot `k`, calls `slot_desc.verify(&addr)`, which succeeds because the digest never referenced the contract id — the chunk is accepted, stored, and re-broadcast via `process_stacker_db_chunks`, even though `S` never authorized `D` as a `BlockResponse` message.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
