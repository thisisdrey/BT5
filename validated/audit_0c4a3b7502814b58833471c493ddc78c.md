### Title
Stale `YieldIdToDataId`/`DataIdToYieldId` trie entries survive `DeleteAccount`, causing spurious duplicate detection and silent yield-creation failure after account name reuse - (`core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/ext.rs`)

### Summary
`remove_account` — invoked by `action_delete_account` when a `DeleteAccount` action is processed — clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows, but never clears `TrieKey::YieldIdToDataId` / `TrieKey::DataIdToYieldId` (or `PromiseYieldReceipt`/`PromiseYieldStatus`) rows for the deleted account. If the account name is later reused, `has_yield_id_mapping` still finds the stale `YieldIdToDataId` entry and `create_promise_yield_receipt_with_id` incorrectly treats a brand-new `promise_yield_create_with_id` call as a duplicate, returning `None` and causing the host function to return the `u64::MAX` sentinel instead of creating a real promise.

### Finding Description
`promise_yield_create_with_id` (`runtime/near-vm-runner/src/logic/logic.rs:3727-3813`, mirrored in the wasmtime runner) calls `create_promise_yield_receipt_with_id`, whose implementation for the runtime `Ext` is: [1](#0-0) 

This checks `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)` and returns `Ok(None)` (→ `u64::MAX` sentinel at the VM logic layer) whenever the `TrieKey::YieldIdToDataId { receiver_id, yield_id }` row already exists in the trie: [2](#0-1) 

The mapping is written by `set_yield_id_mapping` when a yield is first created: [3](#0-2) 

It is only ever cleared by `remove_yield_id_mappings`, which runs solely on the `PromiseResume` path when a live `PromiseYieldReceipt` is resolved (`runtime/runtime/src/lib.rs:1523-1537`) — never on account deletion. `remove_account`, called from `action_delete_account`, enumerates and removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`: [4](#0-3) 

Note that `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` explicitly lists `YIELD_ID_TO_DATA_ID` and `DATA_ID_TO_YIELD_ID` as per-account columns: [5](#0-4) 

yet `remove_account`'s implementation does not sweep these columns, unlike `ContractData`. As a result, any `YieldIdToDataId`/`DataIdToYieldId` row written before deletion remains in the trie for the account name, keyed purely by `(receiver_id, yield_id)`, with no association to the account's lifetime/incarnation.

Exploit flow: an attacker who controls the account "a.near" at some point (e.g., a subaccount momentarily controlled by the attacker under a shared-parent/factory naming pattern, or any account the attacker can create and later delete) calls `promise_yield_create_with_id` with a chosen `yield_id = Y`, writing the `YieldIdToDataId`/`DataIdToYieldId` rows, then deletes the account via `DeleteAccountAction`. When the account name "a.near" is later reused (e.g. re-created by a factory contract for a different session/user, or a different controlling party under the naming scheme in use), and that new occupant independently calls `promise_yield_create_with_id(Y)` for the same low-entropy `Y` (e.g., derived from block height or another predictable value), `has_yield_id_mapping` finds the attacker's leftover row and returns `true`, so `create_promise_yield_receipt_with_id` returns `None` and the host call returns `u64::MAX` — no promise is created, and the callback the victim's contract logic depends on to resolve state (and potentially release escrowed funds) is silently never scheduled.

### Impact Explanation
This is a liveness/determinism bug scoped to denial-of-service: a legitimate `promise_yield_create_with_id` call is silently dropped (sentinel returned instead of a real promise) because of stale state from an unrelated, already-deleted incarnation of the same account name. Contract logic that branches on the sentinel may misbehave, and if funds are escrowed pending resolution of the intended yield/resume callback, they can become stuck. This matches the "denial of service / stuck contract logic, potentially freezing funds tied to a pending callback" category rather than direct fund theft.

### Likelihood Explanation
Exploitability depends on the attacker being able to (a) get one incarnation of an account name to write a chosen `yield_id`, delete it, and (b) have a different party later reuse the same account name and independently pick the same `yield_id`. This is plausible in shared-subaccount/factory patterns (e.g., dapps that create and tear down per-session subaccounts under one parent and later reuse names), especially if the dapp derives `yield_id` deterministically/predictably (e.g., from block height, a counter, or other low-entropy input) as the prompt's precondition assumes. It is not exploitable against a "normal" account that is never deleted and recreated. The attacker's cost is limited to normal account creation/deletion fees; the bug is fully repeatable since nothing ever clears these trie rows.

### Recommendation
Have `remove_account` (and/or `action_delete_account`) also enumerate and remove any `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldReceipt`, and `TrieKey::PromiseYieldStatus` rows for the account being deleted, mirroring the existing `ContractData`/`AccessKey` sweep, so no stale yield bookkeeping survives account deletion and possible name reuse.

### Proof of Concept
Unit test in `core/store` / `runtime/runtime` crate:
1. Create account `a.near`, call `set_yield_id_mapping(&mut state_update, &"a.near".parse().unwrap(), yield_id, data_id)` to simulate a prior `promise_yield_create_with_id(Y)`.
2. Call `remove_account(&mut state_update, &"a.near".parse().unwrap())` to simulate `DeleteAccount`.
3. Assert `has_yield_id_mapping(&state_update, &"a.near".parse().unwrap(), yield_id)` still returns `true` even though no live `PromiseYieldReceipt` exists for `data_id` (confirm via `has_promise_yield_receipt`/`get_promise_yield_receipt` returning `None`).
4. Re-create the account and call `create_promise_yield_receipt_with_id(&mut ext, "a.near", yield_id)`; assert it returns `Ok(None)` (equivalently, at the VM-logic layer, `promise_yield_create_with_id` returns `u64::MAX`) instead of creating a fresh receipt, demonstrating the victim's legitimate yield request is silently dropped.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
