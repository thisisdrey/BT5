### Title
`Pool.liquidate` permanently reverts for debts in the `[debtFloorInUsd, debtFloorInUsd/(1-maxLiquidable))` band — feature-interaction DoS on liquidations - ([File: contracts/Pool.sol])

### Summary
The CVE-2020-8621 bug class is a crash/liveness failure that only manifests when two individually-valid features are enabled together (QNAME minimization + `forward first`). The Metronome analog is the interaction between `maxLiquidable` (partial-liquidation cap, 50% by default) and `debtFloorInUsd` (minimum remaining debt) inside `Pool.liquidate`. When both are active, an entire band of unhealthy positions becomes unliquidatable: every possible `amountToRepay_` either exceeds `maxLiquidable` or leaves a remainder below the floor. [1](#0-0) 

### Finding Description
`liquidate` enforces two independent bounds on `amountToRepay_`:

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` → `AmountGreaterThanMaxLiquidable`. With the default `maxLiquidable = 0.5e18` (set in `initialize`), at most 50% of the debt token balance may be repaid per call. [2](#0-1) [3](#0-2) 
2. If `debtFloorInUsd > 0`, the remaining debt `_debtTokenBalance - amountToRepay_` must be either `0` or `>= debtFloorInUsd`, otherwise `RemainingDebtIsLowerThanTheFloor`. [4](#0-3) 

For a debt position whose total USD value `D` satisfies `debtFloorInUsd < D < debtFloorInUsd / (1 - maxLiquidable)` (e.g. `floor = $100`, `maxLiquidable = 50%`: `$100 < D < $200`):

- Repaying everything (`amountToRepay_ = balance`) is required to satisfy the floor (`remaining = 0`), but `wadDiv = 1e18 > 0.5e18` → reverts `AmountGreaterThanMaxLiquidable`.
- Repaying the maximum allowed (`0.5 * balance`) leaves `0.5 * D ∈ ($50, $100)`, which is `> 0` and `< floor` → reverts `RemainingDebtIsLowerThanTheFloor`.
- Any smaller repayment leaves an even larger sub-floor remainder.

Every input reverts; the position cannot be liquidated at all. An attacker creates such a position deliberately: mint debt `D` in the band (health is checked at `DebtToken.issue` time, but interest accrual via `accrueInterest()` pushes the position underwater shortly after — the attacker does not need oracle manipulation, just normal interest accrual or any collateral price drift). The window is self-widening for the attacker since unpaid debt keeps growing, and remains unliquidatable until `D` crosses `floor/(1-maxLiquidable)` — during which the position accrues bad debt with zero liquidation pressure. Unlike BIND, this requires `debtFloorInUsd > 0` to be configured, but on deployed pools that set a floor this is a pure code-level contradiction, not a parameter misconfiguration.

### Impact Explanation
Liquidation is the solvency backstop of the pool. A reachable class of unhealthy positions that deterministically reverts in `liquidate` produces unliquidatable bad debt → protocol insolvency (debt outlives its collateral backing). This maps to the CVE's availability-failure class and to the accepted "protocol insolvency" / "temporary freezing of funds" (underwater collateral cannot be recovered while the position sits in the dead band) impact criteria.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` (governor-set via `updateDebtFloor`) and `maxLiquidable < 1e18` — both are ordinary, documented configs (`maxLiquidable` defaults to 50%). Any EOA can open a position sized inside the band at near-zero cost beyond normal collateral, and positions also drift into the band organically through interest accrual and price movement, so the stuck band is hit in normal operation, not only by adversaries.

### Recommendation
In `liquidate`, when `_debtTokenBalance - amountToRepay_` would land under `debtFloorInUsd`, clamp the effective repay to the full balance (i.e. allow full repayment to bypass `maxLiquidable` when the remainder would be sub-floor), mirroring how many lending protocols force close-out of dust positions. Alternatively, exempt repayments that leave `remaining == 0` from the `maxLiquidable` check whenever `remaining > 0` is impossible under both constraints. [5](#0-4) 

### Proof of Concept
Hardhat-style sketch (mirroring `test/Pool.test.ts` liquidation setup at lines 315–404):

```ts
// setup: pool with maxLiquidable = 0.5e18 (default), debtFloorInUsd = $100
await pool.updateDebtFloor(parseEther('100'))

// 1. alice deposits MET collateral, issues msETH debt worth ~$150 (healthy at issue)
await msdMET.connect(alice).deposit(alice.address, depositAmount)
await msEthDebtToken.connect(alice).issue(debtWorth150Usd, alice.address)

// 2. position becomes unhealthy via interest accrual / small price move
await masterOracle.updatePrice(met.address, slightlyLowerPrice)
expect((await pool.debtPositionOf(alice.address))._isHealthy).false
// debt is $150: 100 < 150 < 200  → inside the dead band

// 3. any liquidate call reverts
const debt = await msEthDebtToken.balanceOf(alice.address)

// full repay: exceeds 50% cap
await expect(
  pool.connect(liq).liquidate(msEth.address, alice.address, debt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

// max-allowed repay (50%): leaves $75 remainder < $100 floor
await expect(
  pool.connect(liq).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')
```

No valid `amountToRepay_` exists: the position is unliquidatable until interest grows the debt past `$200`, accumulating bad debt the whole time. [6](#0-5)
