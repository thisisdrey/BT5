### Title
Handshake initiation messages carry no expiry/deadline, allowing indefinite replay of captured stage-0 packets - (File: `handshake_manager.go`, `handshake/machine.go`, `handshake/payload.go`)

### Summary
Nebula's handshake payload includes a `Time` field (`HandshakeTime`) that is only ever used to compare "is this handshake newer than the one I already have" — it is never validated against the responder's wall-clock time or any bounded validity window. This is the direct analog of the reported issue: a signed request (the handshake stage-0/msg1 packet) has no deadline, so once captured it remains valid and acceptable forever.

### Finding Description
The handshake payload structure only carries a `Time` value with no expiry semantics: [1](#0-0) 

When a responder processes an incoming handshake message, it decodes this field and stores it directly into the result with no comparison to the current time: [2](#0-1) 

The only place `HandshakeTime` (as `lastHandshakeTime`) is later used is a relative comparison against a possibly pre-existing hostinfo, not an absolute freshness/deadline check: [3](#0-2) 

`beginHandshake` — the entry point that processes a stage-0 (`msg1`) packet from an unauthenticated peer — builds a full `Machine`, calls `ProcessPacket`, verifies the peer cert, and creates a `HostInfo`/pending tunnel state, all without ever checking whether the handshake packet is "fresh": [4](#0-3) 

Notably, the codebase's own end-to-end test explicitly documents and exercises this: after a handshake times out and the initiator discards all pending state, the *same, old* captured msg1 packet is redelivered to the responder, and the responder still processes it and produces a stage-2 response / creates a tunnel-in-progress: [5](#0-4) 

This differs from certificate expiry (`Expired(t time.Time)`), which is separately and correctly enforced at verification time: [6](#0-5) [7](#0-6) 
Certificate expiry only bounds the *identity* credential's lifetime (which can be very long, e.g. months), not the *individual handshake message's* freshness. Nothing prevents a captured, still-cert-valid stage-0 packet from being replayed at any later point within that certificate's lifetime.

### Impact Explanation
An attacker who observes/captures a legitimate stage-0 handshake packet on the wire (no CA-signed certificate of their own is required — they only need to record and later resend UDP bytes) can replay it to the responder at any time in the future, as long as the embedded certificate hasn't expired. Consequences:
- The responder will process the replayed packet as a legitimate new handshake attempt, allocate a fresh local index, build a `HostInfo`, and respond with a stage-2 message, consuming CPU/memory resources and creating stale/duplicate pending handshake state (`hm.indexes`, `hm.vpnIps`) — a remote state-poisoning / resource-exhaustion vector.
- Since `lastHandshakeTime` is attacker-replayable and only used in a relative "is newer" comparison (`CheckAndComplete`), a stale replayed handshake can interact with `ErrExistingHostInfo`/`ErrAlreadySeen` logic in ways not intended for legitimately-timed handshakes, e.g. resurrecting/duplicating a tunnel long after the original attempt should have lapsed.
- This is a medium-severity issue analogous to the reported finding: lack of a deadline check on a signed request permits indefinite-window replay, undermining the initiator's expectation that a handshake attempt is only valid for a bounded window (the local retry/timeout window), not indefinitely.

### Likelihood Explanation
Any passive on-path or off-path attacker capable of capturing a single UDP handshake packet (msg1) can trivially replay it — no cryptographic material or valid CA certificate of their own is needed. The codebase's own e2e test (`TestHandshakeLateResponse`) demonstrates the exact scenario end-to-end and shows the responder accepting the stale packet, confirming this is reachable in the current implementation, not merely theoretical.

### Recommendation
Bind `Time` (or add a dedicated field) to an enforceable freshness window on the responder side: reject stage-0 handshake payloads whose `Time` is outside an acceptable clock-skew/deadline window of the responder's current time (similar to `checkCAConstraints`/`Expired` style bounding, but scoped to the handshake message itself, not just the certificate). Additionally, consider tracking a short-lived anti-replay cache (or nonce) of recently seen stage-0 packets independent of certificate validity, since certificate lifetime is not a proxy for handshake-message freshness.

### Proof of Concept
The existing `TestHandshakeLateResponse` test is direct proof of this behavior: [8](#0-7) 
It shows: (1) a handshake is initiated and its msg1 captured, (2) the initiator's pending handshake state times out and is deleted, (3) the same captured msg1 is delivered to the responder afterward, and (4) the responder still accepts it and generates a stage-2 response (`resp := theirControl.GetFromUDP(true); assert.NotNil(t, resp)`), demonstrating that a captured handshake-initiation packet remains indefinitely acceptable with no deadline enforcement on the message itself.

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}

	if result == nil {
		// Multi-message pattern: the responder Machine would need to be
		// registered in hm.indexes so a future inbound packet finds it via
		// continueHandshake. The current manager doesn't do that yet, so
		// fail loudly rather than silently dropping the in-flight handshake.
		// TODO: support multi-message responder flows (XX, pqIX, etc.).
		// See also the IX-shaped cipher key assignment in handshake.Machine.
		f.l.Error("multi-message handshake responder is not supported",
			"from", via, "error", handshake.ErrMultiMessageUnsupported)
		return
	}

	remoteCert := result.RemoteCert
	if remoteCert == nil {
		f.l.Error("Handshake did not produce a peer certificate", "from", via)
		return
	}

	// Validate peer identity
	vpnAddrs, anyVpnAddrsInCommon, ok := hm.validatePeerCert(via, remoteCert)
	if !ok {
		return
	}

	hostinfo := &HostInfo{
		ConnectionState:   newConnectionStateFromResult(result),
		localIndexId:      result.LocalIndex,
		remoteIndexId:     result.RemoteIndex,
		vpnAddrs:          vpnAddrs,
		HandshakePacket:   make(map[uint8][]byte, 0),
		lastHandshakeTime: result.HandshakeTime,

func TestHandshakeLateResponse(t *testing.T) {
	t.Parallel()
	// After a handshake times out, a late response should be silently ignored
	// with no new tunnels created.

	ca, _, caKey, _ := cert_test.NewTestCaCert(cert.Version1, cert.Curve_CURVE25519, time.Now(), time.Now().Add(10*time.Minute), nil, nil, []string{})
	myControl, myVpnIpNet, _, _ := newSimpleServer(cert.Version1, ca, caKey, "me", "10.128.0.1/24", m{
		"handshakes": m{
			"try_interval": "200ms",
			"retries":      2,
		},
	})
	theirControl, theirVpnIpNet, theirUdpAddr, _ := newSimpleServer(cert.Version1, ca, caKey, "them", "10.128.0.2/24", nil)

	myControl.InjectLightHouseAddr(theirVpnIpNet[0].Addr(), theirUdpAddr)

	myControl.Start()
	theirControl.Start()

	t.Log("Trigger handshake from me")
	myControl.InjectTunPacket(BuildTunUDPPacket(theirVpnIpNet[0].Addr(), 80, myVpnIpNet[0].Addr(), 80, []byte("Hi")))

	t.Log("Grab msg1 but don't deliver")
	msg1 := myControl.GetFromUDP(true)

	t.Log("Wait for handshake to time out")
	for i := 0; i < 5; i++ {
		time.Sleep(300 * time.Millisecond)
		myControl.GetFromUDP(false)
	}

	t.Log("Confirm no pending handshakes remain")
	assert.Empty(t, myControl.ListHostmapHosts(true))

	t.Log("Deliver old msg1 to them, they create a tunnel")
	theirControl.InjectUDPPacket(msg1)
	resp := theirControl.GetFromUDP(true)
	assert.NotNil(t, resp)
