### Title
Global fee admin can set `FeeState.liquidation_max_fee` with no upper bound, enabling near-total collateral seizure during receivership liquidation - ([File: programs/marginfi/src/instructions/marginfi_group/edit_global_fee.rs])

### Summary
This is a structural analog of the reported `SwapFacility` bug: an owner-controlled fee-rate setter with no maximum cap that gates the value a counterparty can extract from an unvigilant/unprivileged user in a single atomic operation. In marginfi, `edit_global_fee_state` lets the `global_fee_admin` set `FeeState.liquidation_max_fee` to any `WrappedI80F48` value with **no validation or ceiling**, and `end_liquidation` uses that raw value (only floored, never capped) to bound how much collateral a receivership liquidator may seize relative to debt repaid.

### Finding Description
`edit_fee_state` in `edit_global_fee.rs` directly assigns any admin-supplied `liquidation_max_fee` to `fee_state.liquidation_max_fee` with no upper-bound check: [1](#0-0) 

That value is consumed in `end_liquidation`, where the maximum seizable premium is computed as the **larger** of the admin-configured fee and a fixed floor — there is only a floor (`LIQUIDATION_BONUS_FEE_MINIMUM`), never a ceiling: [2](#0-1) 

The relevant constant confirms only a minimum bound exists in the codebase for this fee: [3](#0-2) 

Contrast this with the analogous per-user protection that *does* exist for limit orders: user-supplied `max_slippage` is hard-capped at `MAX_ORDER_SLIPPAGE` (~10%) at order placement time, and enforced independently of `fee_state.order_execution_max_fee` via a redundant `&&` check in `end_execute_order`, which is why that path is not exploitable the same way: [4](#0-3) [5](#0-4) 

No such independent, user-controlled ceiling exists on the liquidation path. `start_liquidation`/`end_liquidation` is permissionless (any liquidator, "with zero dollars," per the docs), and the check that bounds a liquidator's profit is purely a function of the admin-controlled `liquidation_max_fee`: [6](#0-5) 

### Impact Explanation
If the `global_fee_admin` key is malicious, compromised, or colludes with a liquidator, they can pack a single atomic transaction that: (1) calls `edit_global_fee_state` to spike `liquidation_max_fee` to a very large value, (2) `start_liquidation` on any already-unhealthy target account, (3) `withdraw` essentially all collateral while repaying a minimal/negligible amount of debt, (4) `end_liquidation` (the inflated `max_fee` makes the `seized <= repaid * max_fee` check trivially pass), and optionally (5) reset the fee afterward. This lets the attacker seize far more than the intended ~10% liquidation premium — up to nearly all of the victim's remaining collateral — directly causing theft of user funds/unauthorized transfer from an unprivileged user's margin account. This is a stronger primitive than the original report (no even frontrunning race is needed, since the admin and the exploit steps can be composed atomically in one transaction), constrained only by the target needing to already be liquidatable (unhealthy).

### Likelihood Explanation
Requires control of the `global_fee_admin` key (a single-purpose privileged signer per `FeeState`, separate from group admins), so it is not exploitable by an arbitrary unprivileged attacker. However, per the bug class in scope, the same "no validated bound on an owner fee setter that gates value extractable from users" pattern that was previously flagged and partially fixed in `SwapFacility` (`MAX_BPS` cap added) has **no equivalent cap** for `liquidation_max_fee` in this codebase. Given the analog is explicitly meant to be judged on privileged-setter-affecting-unprivileged-user paths (liquidation is listed as in-scope), and there is no redundant per-user protection (unlike the order path), this is a concrete, currently-reachable gap.

### Recommendation
Enforce a hard-coded maximum ceiling (e.g., similar to `MAX_ORDER_SLIPPAGE`) on `liquidation_max_fee` inside `edit_fee_state`, rejecting values above a sane bound (e.g. 10-20%) regardless of what the `global_fee_admin` supplies. Additionally, consider timelocking `edit_global_fee_state` changes to `liquidation_max_fee` (and other value-capturing fee/rate fields) so they cannot take effect atomically within the same transaction as a liquidation, closing the same-tx composition vector described above.

### Proof of Concept
1. Global fee admin (or an entity that has taken control of that key) submits a single transaction containing:
   - `edit_global_fee_state(liquidation_max_fee = extremely_large_value)`
   - `start_liquidation` targeting an unhealthy victim account (see `check_pre_liquidation_condition_and_get_account_health` gating in `liquidate_start.rs`)
   - `lending_account_withdraw` seizing nearly all victim collateral
   - `lending_account_repay` for a minimal amount of debt
   - `end_liquidation`
2. In `end_liquidation`, `max_fee = max(1 + fee_state.liquidation_max_fee, 1 + LIQUIDATION_BONUS_FEE_MINIMUM)` becomes very large due to the inflated `liquidation_max_fee`, so `check!(seized <= repaid * max_fee, ...)` passes even though `seized` vastly exceeds a fair ~10% liquidation premium over `repaid`.
3. Result: the liquidator (attacker or colluding party) walks away with nearly all of the victim's collateral for a token debt repayment — full or near-full asset drain of the victim's margin account.

Note: I could not find any additional validation logic (e.g., in `type-crate/src/types/fee_state.rs` or elsewhere) that clamps `liquidation_max_fee` upon write; based on available indexed code, no such cap exists. If a bound exists in code not covered by the index, this would need to be re-verified via a full repository checkout.
