### Title
Floating-point AMM pricing in `ExchangeProcessor` can push the Bancor pool balance negative and let a trader extract more tokens than the exchange pool actually holds - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The `WORLD CONQUEST` incident is a "rule exploitation" attack: the game's own payout/tax rule, when driven with adversarial inputs, let the attacker drain the entire prize pool because the contract never verified that computed payouts stayed inside the pool's real reserves. The closest reachable analog in java-tron is the Bancor-style relay-token pricing formula used by `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` through `ExchangeCapsule.transaction()`. On the default (non-hardened) code path, the payout amount is computed with IEEE-754 `double` arithmetic (`StrictMath.pow`) and then simply subtracted from the pool's `long` balance with **no invariant check** that the result stays non-negative. Only when the `AllowHardenExchangeCalculation` chain parameter is turned on (an SR/committee-controlled proposal, off by default) does the code route through `SafeExchangeProcessor`, which explicitly re-adds the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard that the legacy path lacks.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine based on the `hardenedCalc` flag: [1](#0-0) 

- When `hardenedCalc` is `false` (the default, since `AllowHardenExchangeCalculation` is a governance-gated parameter not enabled by default), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` arithmetic and **no bounds check is performed at all** — the `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))` guard is skipped entirely.
- The actual payout (`buyTokenQuant`) in that default path comes from `ExchangeProcessor.exchange()`, which chains two `double`-based Bancor formula steps using `StrictMath.pow` with fixed exponents (`0.0005` and `2000.0`): [2](#0-1) 

Floating-point `pow`/division on extreme reserve ratios or large `sellTokenQuant` values can produce a `buyTokenQuant` whose subsequent subtraction from `secondTokenBalance` (or `firstTokenBalance`) yields a negative pool balance, since nothing clamps or rejects that outcome on this path.

The exploitability of this exact class of error is corroborated by the project's own hardened-path tests, which had to add a dedicated invariant assertion that does not exist for the legacy processor: [3](#0-2) 
and by the explicit "hardened" guard only added under `hardenedCalc`: [4](#0-3) 

`ExchangeTransactionActuator.execute()` unconditionally credits the trader with whatever `anotherTokenQuant` the (unguarded, default) processor returns and persists the resulting pool state without any sanity check that the pool still holds non-negative reserves: [5](#0-4) 

This mirrors the WORLD CONQUEST bug class: a rule (here, the AMM pricing/payout rule) that is exploitable via crafted inputs to pay out more than the pool's real reserve supports, ultimately draining the shared fund pool for all other exchange participants — reachable by any account that issues an `ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction, no privileged role required.

### Impact Explanation
If a trader can craft `tokenID`/`tokenQuant` inputs (via extreme reserve ratios, injected large amounts, or many small successive trades) that push the floating-point payout above what the legacy `ExchangeProcessor` guard would allow, the on-chain `Exchange`/`ExchangeV2` pool balance for one side can go negative while the trader's account is credited the full (unbacked) amount. This is a direct theft/drain of the shared liquidity pool funds belonging to the exchange creator and other participants, corresponding to the Medium/High-severity "Loss of funds via rule exploitation" class in the report.

### Likelihood Explanation
The vulnerable path is the **default** production path: `AllowHardenExchangeCalculation` is a governance-gated dynamic parameter, so unless it has been explicitly enabled on-chain, every `ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction runs through the unguarded `ExchangeProcessor`. Any account holder can submit such a transaction; no special privilege, precompile, or contract deployment is required — only crafting the sell/buy token IDs and quantities against an existing exchange pair.

### Recommendation
Enforce the same non-negative-balance invariant (`newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0`) unconditionally in `ExchangeCapsule.transaction()`, regardless of the `hardenedCalc` flag, and/or make the `SafeExchangeProcessor` (BigDecimal-based, exact-rounding, invariant-checked) the only processor used in production, retiring the double-based `ExchangeProcessor` for balance-affecting execution paths.

### Proof of Concept
Not independently reproduced in this analysis — I was not able to execute the AMM math against extreme reserve/quantity combinations to confirm a concrete negative-balance trigger within the available read-only tooling. This should be validated with a unit test that feeds `ExchangeProcessor.exchange()` (via `ExchangeTransactionActuator`, `hardenedCalc=false`) reserve/quantity pairs at the extremes exercised by `ExchangeProcessorTest.testSafeProcessorNoOvershootForTypicalInputs` (e.g. highly asymmetric reserves such as `{1L, 10_140_000_000_000L, 2_897_000_000_000L}`) and asserting whether the resulting pool balance can go negative on the non-hardened path, contrasting with the guarded hardened path.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
