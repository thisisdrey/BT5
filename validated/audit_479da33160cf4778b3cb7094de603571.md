### Title
Unauthenticated `RecvError` packet can force-close a legitimate tunnel before the remote address is learned - (File: outside.go)

### Summary
`handleRecvError` in `outside.go` processes the plaintext, unauthenticated `header.RecvError` message type and tears down an existing tunnel (`closeTunnel` + `handshakeManager.DeleteHostInfo`) based solely on a guessed `RemoteIndex` and a weak anti-spoof check. This mirrors the reported bug class: an internal validation gate (meant to reject bad/unauthorized actors) that instead allows the failure/abort path to fire and disrupt a legitimate operation for an unrelated, already-authenticated peer.

### Finding Description
`RecvError` packets are handled before any decryption or certificate check — they are looked up purely by `h.RemoteIndex` against the main hostmap: [1](#0-0) 

The only defense against spoofing is:
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
``` [2](#0-1) 

This check only rejects a spoofed sender when `hr.IsValid()` is true (i.e., the hostinfo already has a confirmed remote and the attacker's source address doesn't match it). If `hr.IsValid()` is false — e.g., a hostinfo has not yet had its remote confirmed, or any state where `GetRemote()` returns an invalid/zero `AddrPort` — the whole condition short-circuits to `false` and the tunnel is torn down unconditionally, regardless of who sent the packet. An attacker who does not hold a CA-signed certificate can send this bare 12-byte header packet (`header.RecvError`, no payload, no MAC) with a guessed/brute-forced `RemoteIndex` (a 32-bit value) to any victim's UDP listener and force a legitimate, healthy tunnel to be destroyed — deleting it from both the main hostmap (`closeTunnel`) and the pending hostmap (`DeleteHostInfo`).

This is directly analogous to the reported bug class: a validation routine (`Disqualifier`'s `require`/state check in the original report) is invoked as a side-effect of normal, legitimate protocol handling and its gate can be bypassed/triggered by conditions outside the legitimate party's control, aborting a legitimate operation (staking/withdrawal there; an established VPN tunnel here) instead of only rejecting the illegitimate one.

### Impact Explanation
An unauthenticated remote attacker can repeatedly force-close arbitrary tunnels between two legitimately-provisioned Nebula peers, causing denial of service and requiring costly re-handshakes. Because the check depends on `hr.IsValid()`, the window is not merely theoretical: it exists whenever a hostinfo's remote hasn't been latched yet (freshly established tunnels, or ones where `SetRemote` hasn't executed for whatever reason), and the guarded case (`hr.IsValid() && hr != addr`) still lets a "valid-looking" match through unconditionally as well. This can be weaponized as a repeated DoS primitive against the mesh with no cryptographic material of the attacker's own.

### Likelihood Explanation
Exploitation requires only UDP reachability to the target's listener and knowledge/guessing of a live `RemoteIndex` (32-bit). Indexes are generated pseudo-randomly (see `generateIndex`), so blind guessing is impractical, but the index is observable to any on-path or off-path observer that can see even one packet of the target's traffic (e.g., a co-located NAT peer, a compromised intermediate router, or anyone who was previously a peer and retains the index), making exploitation feasible in realistic mesh deployments (`listen.accept_recv_error`/`send_recv_error` config also affects who can trigger it, but does not close the `hr.IsValid()` gap). This is a config-independent logic gap, not merely a config-hardening opportunity.

### Recommendation
- Require `hr.IsValid()` before honoring any `RecvError`; if the remote hasn't been confirmed yet, do not act on the message rather than defaulting to "trust it".
- Do not fully delete/close the tunnel from a single unauthenticated `RecvError`; instead, use it only as a hint to trigger a re-handshake/keepalive probe (authenticated) and let the existing authenticated tunnel state machine make the teardown decision.
- Consider gating `RecvError` handling more strictly by default (`accept_recv_error` narrowed, e.g., only private/local ranges) and rate-limit acceptance per source/index to blunt guessing attempts.

### Proof of Concept
1. Establish a legitimate Nebula tunnel between host A and host B.
2. As an attacker with no CA-signed certificate, observe or otherwise learn A's `localIndexId` for the tunnel with B (e.g., by sniffing one packet, or from a config/log leak, or via a prior relay/legacy session).
3. Before `A`'s `HostInfo.remote` has been confirmed for a given tunnel (a hostinfo whose `GetRemote()` returns an invalid `AddrPort`, e.g., right after being created via `beginHandshake`/`continueHandshake` before `SetRemote` completes, or in `!via.IsRelayed` paths where remote hasn't yet been re-latched), send a bare `header.RecvError` UDP packet to A with `RemoteIndex` set to that index, from any source address.
4. Observe in `outside.go`'s `handleRecvError` that `hr.IsValid()` is `false`, so the spoof check is skipped and `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` execute, tearing down A's legitimate tunnel to B without any cryptographic proof of authorization.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}
