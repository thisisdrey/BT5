### Title
Attacker can fill a victim's per-account token list (`MAX_TOKENS_PER_USER`) via dust deposits/transfers, blocking the victim from depositing new collateral or receiving deposit tokens - (File: contracts/Pool.sol)

### Summary
`Pool` tracks each account's deposit and debt tokens in a shared `MappedEnumerableSet` capped at `MAX_TOKENS_PER_USER = 30` ( [1](#0-0) ). `DepositToken._mint` and `DepositToken._transfer` unconditionally call `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance goes from zero to non-zero ( [2](#0-1) [3](#0-2) ), and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined list is full ( [4](#0-3) ). Because `deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` ( [5](#0-4) ) and `transfer` is permissionless, an unprivileged attacker can push dust amounts of every registered deposit token into a victim's list. Once full, every subsequent mint/transfer of a *new* deposit token to the victim reverts, and, analogously to the reported gas-griefing pattern, the attacker can front-run the victim's deposit transaction with a single dust deposit/transfer to make it revert.

### Finding Description
The analog of the "replace the delegate to make the executor's pending tx revert" bug is state-mutation front-running against per-account list insertion:

1. `DepositToken.deposit(amount_, onBehalfOf_)` has no restriction on `onBehalfOf_` (only non-zero and not the treasury), and mints `msdTOKEN` to that address ( [6](#0-5) [7](#0-6) ).
2. `DepositToken._transfer`/`_mint` add the token to the recipient's per-account list whenever `balanceOf[recipient]` was previously 0 ( [3](#0-2) ).
3. `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, which counts `depositTokensOfAccount.length + debtTokensOfAccount.length` against `MAX_TOKENS_PER_USER` and reverts with `UserReachedMaxTokens` ( [4](#0-3) ; error at [8](#0-7) ). The same pattern exists for `addToDebtTokensOfAccount`.
4. There is no opt-in, allowance, or minimum-amount check protecting the recipient list — anyone can force entries into any account's list for the cost of a 1-wei deposit or transfer per token.

Concrete attack:
- Persistent variant: for each registered `DepositToken` (governance-capped globally by `ReachedMaxDepositTokens`, but typically enough slots exist), the attacker calls `depositToken.deposit(1, victim)` or `depositToken.transfer(victim, 1)` until `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`. From then on, any mint of a new deposit token to the victim — their own deposit of a collateral type they don't yet hold, a deposit-on-behalf, a transfer — reverts with `UserReachedMaxTokens`.
- Front-run variant: the attacker monitors the mempool for the victim's `deposit`, `depositTo`/`leverage`, or inbound `msdTOKEN` transfer and front-runs it with a 1-wei dust transfer of a token the victim doesn't hold, causing the victim's transaction to revert — the same "invalidate a pending legitimate transaction" mechanism as the delegate-swap griefing, but additionally denying the intended state change rather than only wasting gas.

### Impact Explanation
- Denial of collateral top-ups: a victim whose position is deteriorating cannot deposit a collateral type they do not already hold (balance 0 → `_mint` → `addToDepositTokensOfAccount` → revert). Combined with a falling collateral price, this blocks the standard rescue path and can force avoidable liquidations — i.e., temporary freezing of the victim's ability to move funds into the position.
- Denial of inbound transfers/airdrops of `msdTOKEN`s the victim doesn't hold, and denial of `SmartFarmingManager.leverage`-style flows that mint a new deposit token to the user.
- Gas griefing of any third party sending the victim a new deposit token (their transaction reverts).
This exceeds pure gas waste: it is a repeatable liveness break on deposits/receipts, fitting the accepted "temporary freezing of funds" impact. The victim can clear a slot only by fully transferring a dust token out (triggering `removeFromDepositTokensOfAccount` at [9](#0-8) ), which the attacker can re-fill by front-running, so the freeze persists as long as the attacker is willing to spend dust.

### Likelihood Explanation
- Fully permissionless: `deposit` accepts any `onBehalfOf_` and `transfer`/`transferFrom` are public; the attacker needs only dust amounts of underlying or existing `msdTOKEN`s, and can withdraw/recycle most of it.
- No modifier stops it: `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` are satisfied by normal operation; there is no whitelist or minimum-amount check on mints/transfers, and the list check actively produces the revert.
- Constraint: the victim's combined list must reach 30, and entries must be *new* tokens for the victim (a token they already hold costs nothing to block). Since the pool-level deposit-token count is itself capped ( [10](#0-9)  shows the combined accounting), filling may be limited by how many deposit/debt tokens exist; on deployments with few registered deposit tokens the persistent variant is weaker, but the single-dust front-run variant always works for any one new token.

### Recommendation
- Do not auto-add tokens to `depositTokensOfAccount` for unsolicited inbound transfers/on-behalf mints below a threshold; e.g., require `amount_` above a dust floor, or make `transfer`/`deposit(onBehalfOf != msg.sender)` skip list insertion and settle list membership lazily.
- Alternatively, replace the revert-on-max in `onlyIfAdditionWillNotReachMaxTokens` with ignoring the addition and handling unlisted balances in `depositOf`/`debtPositionOf`, or let users remove entries without holding a zero balance.
- At minimum, add an allowlist/opt-in per account for third-party `onBehalfOf_` deposits, or allow victims to "reject" dust tokens cheaply in the same transaction that removes them.

### Proof of Concept
Hardhat-style sketch against deployed-style fixtures (as in `test/Pool.test.ts`):

```ts
// Setup: pool with N registered DepositTokens; alice is the victim.
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber(); // 30

// 1) Fill alice's per-account list with dust.
for (const dt of registeredDepositTokens) {
  // Option A: forced deposit on behalf of victim
  await underlying.connect(attacker).approve(dt.address, MaxUint256);
  await dt.connect(attacker).deposit(1, alice.address); // or dt.transfer(alice.address, 1)
}
// ... repeat with debt/other deposit tokens until:
expect(
  (await pool.getDepositTokensOfAccount(alice.address)).length +
  (await pool.getDebtTokensOfAccount(alice.address)).length
).to.eq(max);

// 2) Victim's deposit of a collateral they don't hold reverts.
await newUnderlying.connect(alice).approve(newDepositToken.address, MaxUint256);
await expect(
  newDepositToken.connect(alice).deposit(parseEther('10'), alice.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) Front-run variant: attacker sees alice's pending deposit in mempool,
//    sends `depositToken.transfer(alice.address, 1)` first; alice's tx reverts.

// 4) Alice frees one slot by sending a dust token fully away:
//    balance -> 0 triggers removeFromDepositTokensOfAccount (DepositToken.sol:522-525),
//    but attacker front-runs again to re-fill -> persistent griefing.
```
