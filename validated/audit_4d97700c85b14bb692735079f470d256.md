### Title
Unbounded recursion in the Go assembler's expression parser causes stack-exhaustion panic on deeply nested/unary-prefixed operands - (File: src/cmd/asm/internal/asm/parse.go)

### Summary
`Parser.expr`/`Parser.term`/`Parser.factor` and `Parser.floatExpr` in `src/cmd/asm/internal/asm/parse.go` implement a classic recursive-descent expression evaluator for immediate/constant operands in Go assembly (`.s`) source, mirroring the exact bug class in NASM's `expr0..expr6` (CVE-2019-20334): each nested `(`, unary `+`, `-`, or `~` causes a new, unbounded recursive call with no depth counter or limit. A `.s` file (part of an ordinary Go module/package processed by `go build`/`go vet`/`go test`) containing a long run of unary operators or parentheses in a constant expression, e.g. `$----------...0`, drives `factor()`/`floatExpr()` into recursion deep enough to exhaust the goroutine stack, crashing the assembler.

### Finding Description
Attacker input is a crafted `.s` assembly source file inside a Go module (a normal victim workflow: cloning/building a third-party module). The Go toolchain's assembler entry point (`cmd/asm`, driven by `asm.Parser.Parse` in `src/cmd/asm/internal/asm/parse.go`) tokenizes operands and evaluates constant expressions via:
- `Parser.factor()` [1](#0-0)  — recurses on `'+' factor`, `'-' factor`, `'~' factor`, and `'(' expr ')'` with no recursion-depth guard.
- `Parser.floatExpr()` [2](#0-1)  — recurses on `'(' floatExpr ')'`, `'+' floatExpr`, `'-' floatExpr`, likewise unguarded.
- `Parser.expr()`/`Parser.term()` mutually call `factor()` in a loop and also recurse into `expr()` for parenthesized sub-expressions [3](#0-2) .

There is no equivalent of the `nestLev`/`incNestLev`/`maxNestLev` guard that Go's own general-purpose expression parser (`go/parser`) added specifically to prevent this bug class: `go/parser.parseBinaryExpr`/`parseUnaryExpr` call `incNestLev`, which panics with a controlled `bailout` once `p.nestLev > maxNestLev` (1e5) [4](#0-3) [5](#0-4) . The assembler's expression evaluator has no such check, so unbounded input directly controls native call-stack depth, and a sufficiently long chain of unary operators/parens triggers an unrecoverable runtime stack-overflow crash (not a caught panic), unlike `go/parser`'s bounded, catchable `bailout`.

### Impact Explanation
This is a denial-of-service crash of the `go` toolchain (assembler) when building a package containing a malicious/corrupted `.s` file — e.g., a supply-chain scenario where a dependency ships an assembly file with a pathological constant expression. The crash is an unrecoverable Go runtime stack-overflow fatal error, terminating the build process; it is not memory corruption or code execution. Under Go's triage this would be a PUBLIC-track, low-severity availability bug (crash/DoS in a build tool on crafted-but-plausible source), analogous to the class of `go/parser`/`go/scanner` stack-exhaustion fixes that were already applied elsewhere in the tree.

### Likelihood Explanation
The victim workflow is simply running `go build`/`go vet`/`go test` on a Go module that includes an architecture-specific assembly file (common in packages using hand-written asm, e.g. crypto/vendor code) authored or tampered with by an attacker. No special privileges are required beyond getting the victim to build the module — an ordinary "malicious module consumed by a normal build" scenario. Exploitability is straightforward: a single-line file with thousands of unary `-`/`~`/parenthesis characters is enough.

### Recommendation
Add a recursion-depth counter/guard to `Parser.expr`, `Parser.term`, `Parser.factor`, and `Parser.floatExpr` (mirroring `go/parser`'s `nestLev`/`maxNestLev`/`incNestLev` pattern) that reports a normal parse error (`p.errorf(...)`) once a reasonable nesting limit is exceeded, instead of allowing unbounded native recursion.

```go
import (
    "cmd/asm/internal/lex"

// TestExprDeepRecursionCrashes demonstrates unbounded recursion in
// Parser.factor via a long run of unary '-' operators, mirroring
// CVE-2019-20334's expr0..expr6 stack-consumption bug in NASM.
func TestExprDeepRecursionCrashes(t *testing.T) {
    p := NewParser(nil, nil, nil)
    // A few million unary minuses is enough to exhaust the goroutine
    // stack in factor()'s unbounded recursion; on affected builds this
    // crashes the process with a fatal stack overflow instead of
    // returning a parse error.
    input := strings.Repeat("-", 5_000_000) + "0"
    p.start(lex.Tokenize(input))
    _ = p.expr() // expected: bounded parse error; actual: stack overflow crash
}
```
Expected (fixed) behavior: `p.expr()` returns after emitting a bounded "expression nested too deeply" style error, analogous to `go/parser`'s `"exceeded max nesting depth"` (see `src/go/parser/parser_test.go:649-693` `TestParseDepthLimit`). Actual behavior on the unguarded assembler parser: unbounded recursion depth proportional to attacker-controlled input length, risking a fatal, unrecoverable stack-overflow crash of the `go build`/`go vet` process.

```go
// expr = term | term ('+' | '-' | '|' | '^') term.
func (p *Parser) expr() uint64 {
	value := p.term()
	for {
		switch p.peek() {
		case '+':
			p.next()
			value += p.term()
		case '-':
			p.next()
			value -= p.term()
		case '|':
			p.next()
			value |= p.term()
		case '^':
			p.next()
			value ^= p.term()
		default:
			return value
		}
	}
}
```

```go
func (p *Parser) factor() uint64 {
	tok := p.next()
	switch tok.ScanToken {
	case scanner.Int:
		return p.atoi(tok.String())
	case scanner.Char:
		str, err := strconv.Unquote(tok.String())
		if err != nil {
			p.errorf("%s", err)
		}
		r, w := utf8.DecodeRuneInString(str)
		if w == 1 && r == utf8.RuneError {
			p.errorf("illegal UTF-8 encoding for character constant")
		}
		return uint64(r)
	case '+':
		return +p.factor()
	case '-':
		return -p.factor()
	case '~':
		return ^p.factor()
	case '(':
		v := p.expr()
		if p.next().ScanToken != ')' {
			p.errorf("missing closing paren")
		}
		return v
	}
	p.errorf("unexpected %s evaluating expression", tok)
	return 0
```

```go
// maxNestLev is the deepest we're willing to recurse during parsing
const maxNestLev int = 1e5

func incNestLev(p *parser) *parser {
	p.nestLev++
	if p.nestLev > maxNestLev {
		p.error(p.pos, "exceeded max nesting depth")
		panic(bailout{})
	}
	return p
}

// decNestLev is used to track nesting depth during parsing to prevent stack exhaustion.
// It is used along with incNestLev in a similar fashion to how un and trace are used.
func decNestLev(p *parser) {
	p.nestLev--
}
```

```go
func (p *parser) parseUnaryExpr() ast.Expr {
	defer decNestLev(incNestLev(p))

	if p.trace {
		defer un(trace(p, "UnaryExpr"))
	}

	switch p.tok {
	case token.ADD, token.SUB, token.NOT, token.XOR, token.AND, token.TILDE:
		pos, op := p.pos, p.tok
		p.next()
		x := p.parseUnaryExpr()
		return &ast.UnaryExpr{OpPos: pos, Op: op, X: x}

	case token.ARROW:
		// channel type or receive expression
		arrow := p.pos
		p.next()

		// If the next token is token.CHAN we still don't know if it
		// is a channel type or a receive operation - we only know
		// once we have found the end of the unary expression. There
		// are two cases:
		//
		//   <- type  => (<-type) must be channel type
		//   <- expr  => <-(expr) is a receive from an expression
		//
		// In the first case, the arrow must be re-associated with
		// the channel type parsed already:
		//
		//   <- (chan type)    =>  (<-chan type)
		//   <- (chan<- type)  =>  (<-chan (<-type))

		x := p.parseUnaryExpr()

		// determine which case we have
		if typ, ok := x.(*ast.ChanType); ok {
			// (<-type)

			// re-associate position info and <-
			dir := ast.SEND
			for ok && dir == ast.SEND {
				if typ.Dir == ast.RECV {
					// error: (<-type) is (<-(<-chan T))
					p.errorExpected(typ.Arrow, "'chan'")
				}
				arrow, typ.Begin, typ.Arrow = typ.Arrow, arrow, arrow
				dir, typ.Dir = typ.Dir, ast.RECV
				typ, ok = typ.Value.(*ast.ChanType)
			}
			if dir == ast.SEND {
				p.errorExpected(arrow, "channel type")
			}

			return x
		}

		// <-(expr)
		return &ast.UnaryExpr{OpPos: arrow, Op: token.ARROW, X: x}

	case token.MUL:
		// pointer type or unary "*" expression
		pos := p.pos
		p.next()
		x := p.parseUnaryExpr()
		return &ast.StarExpr{Star: pos, X: x}
	}

	return p.parsePrimaryExpr(nil)
}

func (p *parser) tokPrec() (token.Token, int) {
	tok := p.tok
	if p.inRhs && tok == token.ASSIGN {
		tok = token.EQL
	}
	return tok, tok.Precedence()
}

// parseBinaryExpr parses a (possibly) binary expression.
// If x is non-nil, it is used as the left operand.
//
// TODO(rfindley): parseBinaryExpr has become overloaded. Consider refactoring.
func (p *parser) parseBinaryExpr(x ast.Expr, prec1 int) ast.Expr {
	if p.trace {
		defer un(trace(p, "BinaryExpr"))
	}

	if x == nil {
		x = p.parseUnaryExpr()
	}
	// We track the nesting here rather than at the entry for the function,
	// since it can iteratively produce a nested output, and we want to
	// limit how deep a structure we generate.
	var n int
	defer func() { p.nestLev -= n }()
	for n = 1; ; n++ {
		incNestLev(p)
		op, oprec := p.tokPrec()
		if oprec < prec1 {
			return x
		}
		pos := p.expect(op)
		y := p.parseBinaryExpr(nil, oprec+1)
		x = &ast.BinaryExpr{X: x, OpPos: pos, Op: op, Y: y}
	}
}
```
