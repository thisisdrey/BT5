### Title
Contract-funded energy cap (`origin_energy_limit`) is not enforced atomically at contract deployment, letting any caller drain owner-funded energy before the owner sets the real limit - (File: `chainbase/src/main/java/org/tron/core/capsule/ContractCapsule.java`)

### Summary
`origin_energy_limit` is the on-chain analog of a "deposit cap": it bounds how much of a smart contract's energy cost the contract's own frozen resources (paid for by the deployer) can absorb per call. Like the reported `depositCap`, this cap is not required to be meaningfully set inside the "initializer" transaction (`CreateSmartContract`) prior to the post-`ENERGY_LIMIT` hard-fork check; it silently falls back to a large, hard-coded default (`Constant.CREATOR_DEFAULT_ENERGY_LIMIT`) and is only tightened later through a separate `UpdateEnergyLimitContract` transaction. Any unprivileged account can call `TriggerSmartContract` in the window between deployment and the owner's follow-up `UpdateEnergyLimitContract` transaction to consume energy against the permissive default cap.

### Finding Description
`ContractCapsule.getOriginEnergyLimit()` returns the deployer-declared value unless it equals the proto default, in which case it substitutes a fixed fallback constant: [1](#0-0) 

This fallback/"cap" is only forced to be explicitly set (`> 0`) at deployment time when the energy-limit hard fork is active, via `VMActuator`'s `create()` path: [2](#0-1) 

The actual, deliberate cap-narrowing mechanism is a separate, later transaction, `UpdateEnergyLimitContractActuator`, which the contract owner must broadcast independently after deployment: [3](#0-2) [4](#0-3) 

The `CreateSmartContract` message allows `origin_energy_limit` to be omitted/zero, and `UpdateEnergyLimitContract` is the officially documented mechanism to set it afterward: [5](#0-4) 

Combined with `consumeUserResourcePercent`, which controls how much of the per-call energy bill is charged to the *caller* versus the *contract account* (i.e., ultimately the deployer's frozen resources), a contract left with a low/zero `consumeUserResourcePercent` and a fallback `origin_energy_limit` means the contract's own resources absorb call costs up to the large default cap: [6](#0-5) 

This mirrors the reported bug class exactly: the cap-defining parameter is not bound atomically inside the creation/initializer transaction; instead, it is left at a permissive default and only reduced by a subsequent, independent transaction. Any account can broadcast `TriggerSmartContract` calls against the freshly-deployed contract during that window and consume energy funded by the deployer's frozen TRX before the owner's `UpdateEnergyLimitContract` transaction lands.

### Impact Explanation
An attacker who observes a newly deployed contract (before its owner submits `UpdateEnergyLimitContract` to lower the cap) can repeatedly call it, consuming the contract account's frozen energy up to the large default `CREATOR_DEFAULT_ENERGY_LIMIT` per transaction, at the deployer's expense rather than their own. This can exhaust/burn the deployer's frozen resource allocation (or force real TRX burn for over-limit energy), which is an unauthorized consumption of another account's committed funds/resources — directly analogous to the "malicious mint/deposit exceeding the intended cap before the admin sets it" scenario in the original report.

### Likelihood Explanation
Reachable by any account able to broadcast a `TriggerSmartContract` transaction targeting a just-deployed contract, with no special privilege required. The likelihood depends on the deployer's own choices (leaving `origin_energy_limit` at 0/default and `consumeUserResourcePercent` low) and the delay before they issue the tightening `UpdateEnergyLimitContract` transaction — a realistic operational gap, since these are two independent, non-atomic transactions.

### Recommendation
Require `origin_energy_limit` (and, ideally, `consumeUserResourcePercent`) to be validated and bound to a safe, conservative default at `CreateSmartContract` validation time regardless of hard-fork status, rather than silently substituting a permissive constant in `ContractCapsule.getOriginEnergyLimit()`. Consider requiring deployers to explicitly set the intended cap as part of `CreateSmartContract`, eliminating the reliance on a follow-up `UpdateEnergyLimitContract` transaction to reach the intended security posture.

### Proof of Concept
1. Deployer submits `CreateSmartContract` without setting `origin_energy_limit` (or before the `ENERGY_LIMIT` hard fork gates it), and with `consumeUserResourcePercent` left at 0/low so the contract account absorbs most energy cost, per `ContractCapsule.getConsumeUserResourcePercent`.
2. `ContractCapsule.getOriginEnergyLimit()` returns `Constant.CREATOR_DEFAULT_ENERGY_LIMIT` (permissive fallback) instead of an owner-chosen safe cap.
3. Before the deployer's follow-up `UpdateEnergyLimitContract` transaction is mined, an attacker broadcasts multiple `TriggerSmartContract` calls against the new contract; each call is processed by `VMActuator.create()`/execution paths using the permissive fallback limit, consuming the deployer's frozen energy resources.
4. Once the deployer's `UpdateEnergyLimitContract` transaction (see `UpdateEnergyLimitContractActuator.execute`) finally lands, the cap is lowered, but the attacker has already drained resources during the exposed window.
