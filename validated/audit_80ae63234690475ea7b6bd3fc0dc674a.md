### Title
Unauthenticated OOM via unvalidated array-length field in `BatchValidateSign` precompile before allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract decodes an attacker-controlled length word from calldata and uses it directly to size a Java array (`new byte[len][]`) before validating that the length is bounded or consistent with the actual calldata size. This mirrors the Mattermost TIFF bug class: a length/offset value embedded in untrusted input is trusted for memory allocation before it is checked against the real payload size, allowing a memory-exhaustion denial of service.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read a 32-byte word from calldata (`words[offset].intValueSafe()`) and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

In `BatchValidateSign.doExecute`, the size-bounding check (`MAX_SIZE`) that would normally cap `sigArraySize`/`addrArraySize` is only executed when the `allowTvmSelfdestructRestriction` hard-fork flag is active: [3](#0-2) 

When that flag is not enabled (or on any network/config where it isn't yet active), `extractBytesArray`/`extractBytes32Array` are invoked directly on attacker-supplied length words with no upper bound check, allowing `len` to be set to an arbitrarily large 31-bit integer via `intValueSafe()`, driving `new byte[len][]` to attempt a multi-gigabyte allocation before any subsequent index/bounds validation against `words.length` occurs.

The energy cost model for this precompile is computed purely from the linear calldata length (`data.length / WORD_SIZE`), not from the decoded `len` field, so an attacker can craft a small calldata payload (few hundred bytes) that embeds a huge length word, paying minimal energy while forcing the node to attempt an enormous heap allocation: [4](#0-3) 

### Impact Explanation
An `OutOfMemoryError` triggered synchronously during transaction execution inside a JVM node can destabilize or crash the node process, or at minimum cause severe GC pressure/service degradation across the whole node (affecting all TVM execution, API serving, and consensus participation on that node) — a full node crash/halt qualifies as a valid Medium/High impact under the DoS rules of this scan.

### Likelihood Explanation
This is reachable by any unprivileged account: simply deploy or call an existing contract that performs a `CALL`/`STATICCALL` to the `BatchValidateSign` precompiled contract address with crafted calldata containing an oversized length word at the referenced offset. No special permission, staking, or witness/SR role is required — only enough TRX/energy to submit the triggering transaction, and the crafted length word costs no proportional energy.

### Recommendation
Bound `len` in `extractBytes32Array`/`extractBytesArray`/`extractSigArray` against `MAX_SIZE` (and against the actual remaining `words.length`) unconditionally, before allocation, rather than gating the check behind the `allowTvmSelfdestructRestriction` feature flag. The length value should also be validated against the calldata's actual capacity so `len` cannot exceed what the buffer can plausibly contain, consistent with the pattern used elsewhere (`isValidAbiEncoding`).

### Proof of Concept
1. Construct calldata for `BatchValidateSign` where word[0] = hash, word[1] = offset to the "signatures" array header, word[2] = offset to the "addresses" array header.
2. At the addresses-array header offset, set the length word to a large value (e.g., `0x7FFFFFFF`).
3. Deploy a minimal contract that forwards `STATICCALL`/`CALL` to the `BatchValidateSign` precompile address with this calldata, or trigger it directly if externally callable.
4. Submit the triggering transaction with a modest fee limit; `extractBytes32Array` executes `new byte[0x7FFFFFFF][]` (~16GB of object-reference memory) inside `doExecute` before any bounds check against `words.length`, causing an `OutOfMemoryError` in the node's JVM. [5](#0-4)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
