### Title
Remote panic via `assert!(preamble.payload_len > 5)` in `validate_blocks_push`/`validate_microblocks_push` on an empty `Blocks`/`Microblocks` payload - (File: stackslib/src/net/chat.rs)

### Summary
`validate_blocks_push` and `validate_microblocks_push` both start with a hard `assert!(preamble.payload_len > 5)` that is meant to guarantee at least one byte of actual block data beyond the 1-byte type tag and 4-byte vector-length prefix. A remote peer can send a syntactically valid `StacksMessageType::Blocks` (or `Microblocks`) message whose vector is empty, which serializes to exactly 5 bytes of payload (`payload_len == 5`), tripping the assert and panicking the thread that services the P2P connection.

### Finding Description
`handle_data_message` dispatches any inbound `StacksMessageType::Blocks(_)` directly into `self.validate_blocks_push(network, &msg.preamble, msg.relayers.clone())` with no prior check that `preamble.payload_len` exceeds 5 [1](#0-0) . Inside `validate_blocks_push`, the very first statement is a hard assertion rather than a recoverable error path: [2](#0-1) 

The comment states the invariant this assert is trying to enforce: "don't count 1-byte type prefix + 4-byte vector length" — i.e. it assumes there must be at least one byte of real block data. But a `Blocks` payload with an *empty* vector of blocks is a perfectly valid encoding: 1 byte for the enum/type tag + 4 bytes for a vector length of `0`, totaling exactly 5 bytes, with no trailing block data. This means a well-formed, correctly parsed message naturally produces `preamble.payload_len == 5`, which fails `> 5` and panics — no tampering with the wire preamble is even required, though the question's proposed proof (forcing `payload_len` to 5 or less) reaches the exact same crash site. The identical off-by-one pattern also exists in `validate_microblocks_push` for an empty microblocks list [3](#0-2) .

No prior fallible check in `handle_data_message` establishes `payload_len > 5` before these functions are called; the value is used as-is from the deserialized preamble that arrived over the wire.

### Impact Explanation
Any peer that can complete a P2P handshake (an unprivileged remote party, since handshakes do not require the RPC secret or any admin role) can trigger `assert!` failure and cause the connection-processing thread to unwind/panic with a single crafted or even legitimately-empty `Blocks`/`Microblocks` message. In Rust, an `assert!` failure is not caught anywhere in this call path shown, so it manifests as a panic in the network-processing thread — a remote, single-message, repeatable DoS against the node's P2P networking. This matches the "Critical - remote crash/unauthenticated DoS from few messages" impact category.

### Likelihood Explanation
- Preconditions: attacker only needs an established/authenticated P2P conversation (standard handshake, no secrets or privileged role needed) and the ability to send one `Blocks` or `Microblocks` push message with zero entries (or a manipulated `payload_len` of ≤5 alongside a `Blocks` payload).
- Attacker cost: trivial — one connection, one message.
- Repeatability: fully repeatable against any reachable node, and against every peer the message is relayed through, since block push messages are relayed across the network.
- Remote reachability: yes, via the P2P port; no privileged role, secret, or slot ownership required.

### Recommendation
Replace the `assert!` in `validate_blocks_push` and `validate_microblocks_push` (and the analogous ones in `validate_transaction_push`, `validate_stackerdb_push`, `validate_nakamoto_block_push`) with a graceful check that returns `Err(net_error::InvalidMessage)` (or simply accepts `payload_len >= 5` since an empty vector is a valid message and should not be rejected as malformed, just handled without underflowing the later `(preamble.payload_len as u64) - 5` subtraction). Ensure the guard is `>=` the true minimum and never panics on attacker-controlled input.

### Proof of Concept
1. In `stackslib/src/net/chat.rs` tests (or a new test module), construct a `StacksMessage` with `payload = StacksMessageType::Blocks(BlocksData { blocks: vec![] })` and a valid, correctly-relayer-populated preamble/relayers, signed as a normal relay message.
2. Serialize it — observe that `preamble.payload_len` naturally computes to `5`.
3. Feed the message through `ConversationP2P::handle_data_message` (or through the full `chat_neighbor`/`recv_signed_request` P2P dispatch, if a public entry point is preferred) using an established test `ConversationP2P`/`PeerNetwork` pair.
4. Assert that this call panics (thread unwind) via `std::panic::catch_unwind`, at the exact site `assert!(preamble.payload_len > 5)` in `validate_blocks_push` (chat.rs:2095), instead of returning `Err(net_error::InvalidMessage)`.
5. Repeat with `StacksMessageType::Microblocks(MicroblocksData { microblocks: vec![] })` to confirm the identical panic in `validate_microblocks_push` (chat.rs:2135).
