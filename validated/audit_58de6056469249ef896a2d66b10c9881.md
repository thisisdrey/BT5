### Title
Missing time-of-check-to-time-of-use (TOCTOU) negotiation timeout in `PostUploadPack` (Smart HTTP) allows stale-authorization data exfiltration — ([File: internal/gitaly/service/smarthttp/upload_pack.go])

### Summary
Gitaly's own SSH-based `git-upload-pack`/`git-upload-archive` handlers contain an explicit, documented mitigation for a TOCTOU race between the access check performed at RPC start and the actual data transfer that happens later, once the client completes negotiation. The equivalent Smart HTTP `PostUploadPack` handler does not appear to apply this same mitigation, which is the class of bug described in the external report: a value/decision computed at "check time" (access is allowed) can become stale by "use time" (objects are actually served) if the client can delay the intervening step.

### Finding Description
The `runUploadCommand` helper used by the SSH transport wraps the client-supplied stdin with a `pktline.ReadMonitor` and a `timeoutTicker`, and explicitly documents why: [1](#0-0) 

The accompanying comment makes the root cause explicit — this is the same bug class as the report's "value computed at check-time is stale by use-time": [2](#0-1) 

`pktline.ReadMonitor` itself is documented as a general fix for "use-after-check" issues where a Git process is spawned after an access check, but the client controls stdin and can delay it indefinitely, potentially gaining access long after the check completed: [3](#0-2) 

Searching the codebase, `pktline.NewReadMonitor` / `boundaryPacket` / `timeoutTicker` / `runUploadCommand` only appear in `internal/gitaly/service/ssh/upload_command.go`, `upload_pack.go`, and `upload_archive.go` — i.e., only in the SSH transport package. No equivalent usage was found in `internal/gitaly/service/smarthttp/upload_pack.go`, which implements the analogous `PostUploadPack` RPC for HTTP-based clone/fetch traffic. Because Gitaly's access check (via the GitLab Rails `/internal/allowed`-style callback, analogous to the pre-receive access-check flow documented for pushes) happens once, before `git-upload-pack` is spawned, the same "user permissions change between check and use" race that SSH explicitly guards against is potentially unguarded on the HTTP path: [4](#0-3) 

### Impact Explanation
If confirmed, an authenticated user who is in the process of losing access to a repository (e.g., project made private, membership revoked, personal access token/deploy key revoked) could hold open the negotiation phase of an HTTP fetch/clone (`PostUploadPack`) — by delaying sending the "done"/flush packet that signals end of negotiation — well beyond the point where the access check was evaluated, and still receive object data belonging to the repository once negotiation completes. This is analogous to the bond contract bug: a decision ("allowed", like "current epoch max") computed at one point in time is used to authorize/serve a much later, and by-then potentially invalid, operation. The impact is unauthorized disclosure of repository contents (confidentiality) via a legitimate, unprivileged RPC path (`PostUploadPack`) reachable by any client performing an ordinary HTTP fetch.

### Likelihood Explanation
Likelihood is moderate to low-confidence given the depth of verification possible here: the absence of the `pktline.ReadMonitor` symbols in the smarthttp package is a strong signal from grep searches, but the exact code path and command construction inside `internal/gitaly/service/smarthttp/upload_pack.go` was not read in full during this investigation. It is possible that the smarthttp path enforces a different, equally effective mitigation (e.g. an overall RPC deadline, or a different negotiation-boundary check) that was not surfaced by the search terms used. This should be verified directly before treating it as confirmed.

### Recommendation
- Read `internal/gitaly/service/smarthttp/upload_pack.go` and its call chain in full to determine whether it applies an equivalent negotiation-phase timeout (via `pktline.ReadMonitor` or another mechanism) to `git-upload-pack` invocations.
- If no equivalent protection exists, apply the same `pktline.ReadMonitor`/boundary-packet timeout pattern used in `internal/gitaly/service/ssh/upload_command.go` to the Smart HTTP `PostUploadPack` handler so both transports enforce a consistent bound on the time between the access check and the start of data transfer.
- Consider centralizing this negotiation-timeout logic (e.g., as a shared helper) so that any future upload-pack-style RPC automatically inherits the TOCTOU mitigation rather than requiring each transport to opt in individually.

**File:** internal/git/pktline/read_monitor.go (L14-30)
```go
// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//
// This approach is better than placing a timeout on the overall git operation
// because there is a conflict between mitigating the use-after-check with a
// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.
```
