## Finding: Unbounded loop over `VotesStore` in maintenance-period vote tallying causes block-processing DoS

### Title
Unbounded loop over `VotesStore` entries in `MaintenanceManager.countVote`/`doMaintenance` can cause excessive block-application time / DoS - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
This is the same bug class as the AntePool report: a loop over an attacker-growable, unbounded collection is executed as a mandatory step of a critical state transition. In java-tron, every account that casts a vote via `VoteWitnessContract` creates/updates an entry keyed by the voter's address in `VotesStore` [1](#0-0) . Each maintenance cycle (every 6 hours by default), `MaintenanceManager.doMaintenance()` — invoked from `applyBlock()`, which is part of block application — calls `countVote(votesStore)`, which iterates the **entire** `VotesStore` via `votesStore.iterator()` with no cap on the number of entries, then deletes each entry as it goes [2](#0-1) .

### Finding Description
`VotesStore` grows one entry per distinct voter address; there is no limit on how many distinct accounts may vote, only a per-transaction limit on the number of witnesses one vote can target (`MAX_VOTE_NUMBER`). An attacker who creates many accounts, freezes a small amount of TRX in each, and casts one `VoteWitnessContract` per account, causes `VotesStore` to accumulate one entry per attacker account. At the next maintenance boundary, every full node must execute `doMaintenance()` → `countVote()`, which loops over all of these entries as part of `applyBlock()` — a step every node performs identically and deterministically to advance the chain [3](#0-2) . Unlike an EVM call, this loop is not gas metered, but it is unbounded CPU/DB-iteration work executed synchronously inside block application, so an attacker-inflated `VotesStore` can materially slow down (or in extreme cases stall) block processing for every node on the network at the deterministic maintenance boundary.

The same unbounded-loop logic is duplicated in the public query path `Wallet.getPaginatedNowWitnessList`, which re-implements `countVote(votesStore)` and iterates the full `VotesStore` on every call from any anonymous API client, independent of the `limit`/`offset` pagination parameters requested [4](#0-3) [5](#0-4) . This means any anonymous caller of this Wallet/gRPC/HTTP API can trigger a full unbounded scan of `VotesStore` per request, and the cost scales with the number of distinct voter accounts an attacker previously created — an attacker-controlled, unbounded input.

### Impact Explanation
- In the consensus path, an inflated `VotesStore` makes `doMaintenance()` (called from block application) more expensive for every full node simultaneously, at a deterministic and predictable time — a synchronized, network-wide slowdown that risks delayed block production/propagation or falling behind consensus deadlines.
- In the API path, `getPaginatedNowWitnessList` can be repeatedly invoked by any anonymous client to force full-store scans regardless of pagination parameters, degrading node responsiveness ("an API the node can no longer serve").

### Likelihood Explanation
Creating many voting accounts requires only minimal TRX per account (enough to freeze for TronPower and pay the vote transaction fee), similar cost profile to the original AntePool report's "attacker creates many accounts" scenario. No special privilege is needed — any unprivileged transaction broadcaster can grow `VotesStore` over time, and the resulting cost is paid by every node at maintenance time or by the node servicing the query API.

### Recommendation
- Bound the number of distinct voter entries counted/iterated per maintenance cycle (or amortize the tally incrementally as votes are cast/changed rather than scanning the whole store at maintenance time).
- For `Wallet.getPaginatedNowWitnessList`, avoid a full-store `countVote` scan per request; cache/tally vote deltas incrementally, or ensure the cost of the RPC is bounded independent of `VotesStore` size.

### Proof of Concept
1. Create N accounts, each with enough TRX to freeze a small balance for TronPower.
2. From each account, broadcast a `VoteWitnessContract` transaction voting for any single witness with a minimal vote count, populating `VotesStore` with N entries [1](#0-0) .
3. Wait for/observe the next maintenance-period block application; `MaintenanceManager.doMaintenance()` executes `countVote(votesStore)`, iterating all N entries as part of block application [6](#0-5) .
4. Alternatively, repeatedly call the `getPaginatedNowWitnessList` gRPC/HTTP API; each call re-scans the full `VotesStore` regardless of `offset`/`limit` [7](#0-6) .
5. Measure increasing latency of block application / API responses as N grows.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }
