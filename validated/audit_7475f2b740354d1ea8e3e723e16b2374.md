### Title
`Contract::native_withdraw` debits signer's wNEAR balance before `near_withdraw` succeeds, with no refund on failure - ([File: contracts/defuse/src/contract/intents/state.rs])

### Summary
`native_withdraw` calls `self.withdraw(...)` to debit the signer's internal wNEAR balance synchronously, then schedules `near_withdraw` followed by `do_native_withdraw` as separate cross-contract promises. If `near_withdraw` fails (e.g., because the wNEAR contract cannot satisfy the unwrap amount), `do_native_withdraw`'s `require!(promise_result_checked_void(0).is_ok(), ...)` panics, but this only reverts state changes made within that specific receipt — it does **not** undo the balance debit that was already committed in the prior, separate `execute_intents` receipt.

### Finding Description
The broken binding is: `wNEAR_debited(signer)` (internal ledger deduction) should equal `wNEAR_unwrapped_and_delivered(receiver)` whenever `native_withdraw` completes — i.e., a failed `near_withdraw` must leave the signer's balance unchanged.

Tracing `contracts/defuse/src/contract/intents/state.rs::native_withdraw` (lines 212-240):
1. `self.withdraw(owner_id, [(wnear_token_id, amount)], ..., false)` — this synchronously debits `owner_id`'s `token_balances` via `internal_sub_balance`, and this debit is committed as part of the current receipt's state (the `execute_intents`/`do_native_withdraw`-scheduling call).
2. It then fires `ext_wnear::near_withdraw(amount)` as an async cross-contract call, `.then()`-chained to `do_native_withdraw`.
3. `do_native_withdraw` (`contracts/defuse/src/contract/tokens/nep141/native.rs`, lines 12-19) checks `promise_result_checked_void(0).is_ok()` and `require!`s on it. If `near_withdraw` failed (e.g., wNEAR contract doesn't have enough NEAR reserve to unwrap the requested `amount`), this `require!` panics.

Because NEAR promises/receipts are separate execution units, a panic inside `do_native_withdraw`'s receipt only reverts state mutations attempted *in that receipt* (there are none — it doesn't touch `self` at all, it's a pure `#[private]` function returning a `Promise`). It has **no ability** to restore the balance that was already debited and committed in the earlier receipt where `self.withdraw` ran. There is no `*_resolve_*`-style refund logic analogous to `ft_resolve_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs`, lines 155-195) which explicitly re-credits `sender_id` via `self.deposit(...)` on partial/failed transfer. `do_native_withdraw` has no equivalent re-credit path — it only transfers to `receiver_id` on success or panics on failure, permanently losing the debited balance.

This means an attacker (or even an honest user, but the query specifies attacker capability) who signs a `NativeWithdraw{receiver_id, amount}` intent where `amount` exceeds what the wNEAR contract can actually unwrap (its own NEAR reserve) will have their internal balance debited with no recovery path.

### Impact Explanation
This causes user funds to be **permanently frozen/destroyed**: the signer's internal wNEAR balance is debited from the Verifier's ledger, but the NEAR is never delivered to `receiver_id` (the `near_withdraw` call failed) and the balance is never restored to the signer. This matches the listed Critical impact category "user funds permanently frozen" — value (the debited wNEAR balance) leaves the signer's ledger entry with no corresponding delivery and no refund, breaking the net-zero balance invariant for the Verifier's custodied assets vs. book-keeping.

However, note this is primarily a **self-inflicted loss** scenario (the signer signs their own withdrawal and loses their own funds) rather than one attacker draining a victim's funds — there's no victim other than the signer themselves, and no way to target another account's balance since `withdraw_intent`'s debit only happens against the signer who authorized the intent via signature. It does not let an attacker steal another user's balance; it lets an attacker (or their own account) trigger loss of their own already-debited balance with no upside. This limits blast radius to self-harm rather than cross-account theft, which is a meaningfully different risk profile than the rule's primary target ("value leaving the Verifier that the signer never authorised" — here the signer *did* authorize the withdrawal debit, it's the failure-refund path that's missing).

### Likelihood Explanation
Triggering this requires making the wNEAR contract's `near_withdraw` fail for a specific amount — which under normal wNEAR contract semantics (backed 1:1 by ft_balance and typically able to unwrap up to the caller's ft balance) should not normally fail if the amount doesn't exceed the Verifier's own internal wNEAR ft balance, since `self.withdraw` already validated the debit doesn't exceed the ledger's book balance. The proof idea in the question suggests forcing failure via requesting more than the wNEAR contract's own NEAR reserve, but the amount is bounded by what the Verifier's internal ledger allows to debit (which should correspond to the Verifier's actual wNEAR ft balance) — so whether this divergence is practically reachable depends on wNEAR contract's actual reserve invariants, which is outside this repo (`crates/near/wnear` if in-repo, else third-party). This introduces uncertainty about real-world exploitability without access to the wNEAR contract's exact accounting guarantees.

### Recommendation
Add a refund path in `do_native_withdraw` analogous to `ft_resolve_withdraw`: on `near_withdraw` failure, re-credit the signer's wNEAR balance via `self.deposit(...)` instead of (or in addition to) panicking, ensuring the debit-then-fail path restores the ledger balance.

### Proof of Concept
Not conclusively demonstrable from static analysis alone — while the code path confirms `do_native_withdraw` lacks any refund/re-credit logic on `near_withdraw` failure (unlike `ft_resolve_withdraw`), reproducing the described exploit requires confirming that `near_withdraw` can actually fail for an amount that the Verifier's own internal balance-tracking would otherwise allow to be debited (i.e., that the wNEAR contract's ft-balance-backed reserve can diverge from the Verifier's internal book balance). This depends on wNEAR contract internals not fully covered by my search, and the existing sandbox test `tests/src/tests/defuse/intents/native_withdraw.rs` only exercises the success path. A definitive sandbox reproduction (forcing wNEAR's `near_withdraw` to fail below the signer's tracked balance, then asserting the signer's `mt_balance_of` for the wNEAR `TokenId` remains debited with no restoring `Transfer`/deposit event) could not be completed within available exploration. impl Contract {

    #[private]
    pub fn do_native_withdraw(withdraw: NativeWithdraw) -> Promise {
        require!(
            promise_result_checked_void(0).is_ok(),
            "near_withdraw failed",
        );

        Promise::new(withdraw.receiver_id).transfer(withdraw.amount)
    }

impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
}
