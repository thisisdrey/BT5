However, before storage the code does check that the attachment's hash matches an expected `content_hash` that was already recorded (from a validated on-chain attachment instance) via `find_all_attachment_instances(&attachment.hash())`. This means the attacker cannot make a node accept and store *arbitrary* attachment content — only content whose Hash160 matches a hash that was already committed on-chain through the Clarity/contract-event path (which is where `should_keep_attachment`'s size check runs, at `queue_attachment_instance` time, gating what content hashes get tracked at all). So while there is no explicit length check in the download path, the attacker cannot forge a hash pre-image at will for content exceeding `attachments_max_size`, because doing so requires them to control what content hash was registered on-chain in the first place — and that registration already goes through the `attachments_max_size` bound... 

Actually, checking more carefully: `should_keep_attachment` is only invoked at the point attachments are *directly posted* to a node (e.g., via `/v2/attachments/new` or similar ingestion), not as part of `queue_attachment_instance`/`AttachmentInstance` creation from block processing — an `AttachmentInstance` only carries a `content_hash` (Hash160), extracted from a Clarity contract-call event, with no length information at all [5](#0-4) . Therefore the on-chain event only commits to a *hash*, not a size, and the size bound is only enforced when *that specific node* is the one that received the attachment directly via the "posted" ingestion path. When a node instead fetches the attachment from a remote peer via `/v2/attachments/{hash}` (the downloader path), the response's `Attachment.content` can be arbitrarily large — the only requirement is that its Hash160 matches the expected `content_hash` — and `insert_instantiated_attachment` will store it verbatim with no size check.

### Title
Attachment downloader stores HTTP-fetched attachment content without enforcing `attachments_max_size` - (File: stackslib/src/net/atlas/download.rs)

### Summary
The `/v2/attachments/{hash}` downloader path (`AttachmentsBatchStateContext::extend_with_attachments` → `AttachmentsDownloader::run`) stores attachment bytes fetched from a remote peer via `AtlasDB::insert_instantiated_attachment` without ever checking `content.len()` against `AtlasConfig::attachments_max_size`. The size bound exists only in `AtlasDB::should_keep_attachment`, which is not called anywhere on this code path.

### Finding Description
`insert_instantiated_attachment` unconditionally writes `attachment.content` into the `attachments` SQLite table [1](#0-0) . In `download.rs::run`, once the `AttachmentsBatchStateMachine` reaches `Done`, every attachment collected from HTTP responses is passed straight to `insert_instantiated_attachment` [3](#0-2) . The attachment content is populated purely from decoding the remote peer's HTTP response body in `extend_with_attachments`, with the only correctness check being downstream hash matching against a previously-queued `content_hash`, not a size check [4](#0-3) . The size-bound logic in `should_keep_attachment` is invoked only for attachments posted directly to a node (the on-chain/event ingestion boundary), not the P2P/HTTP downloader path [2](#0-1) . A malicious peer serving `/v2/attachments/{hash}` for a hash the victim node is trying to resolve can return content whose Hash160 happens to match (if the attacker also controls what got committed on-chain as the expected hash) or — more directly — any peer that is the source of the attachment for a hash the victim legitimately needs can respond with oversized content, since nothing in the download path bounds the response size before writing to disk.

### Impact Explanation
A malicious/compromised peer can cause a victim node to store arbitrarily large attachment blobs in its local `AtlasDB` SQLite `attachments` table, unbounded by the configured `attachments_max_size`, leading to unbounded disk usage per matched attachment (repeatable across many attachment instances the node is trying to resolve). This is disk/storage exhaustion tied into the attachment sync mechanism.

### Likelihood Explanation
Requires that the victim node has an outstanding `AttachmentInstance` (with a known `content_hash`) that it is trying to resolve, and that the attacker's node is selected as a download source for that content (reachable via any peer serving as an outbound sync peer). The attacker still must produce content matching the required Hash160 pre-image, which is registered by the on-chain event, limiting attacker control over content — this significantly reduces practical exploitability since arbitrary attacker-chosen content of size > `attachments_max_size` generally cannot be forced to match a required hash unless the attacker also controls the pre-image registration (e.g., is the entity that posted the BNS/attachment transaction in the first place).

### Recommendation
Add an explicit length check (`content.len() as u32 <= atlas_config.attachments_max_size`) in `extend_with_attachments` or immediately before calling `insert_instantiated_attachment` in `download.rs::run`, mirroring the check already present in `AtlasDB::should_keep_attachment`.

### Proof of Concept
Rust net test: construct an `AttachmentsBatchStateContext` with a mocked `StacksHttpResponse` for `/v2/attachments/{hash}` whose `Attachment.content` exceeds `attachments_max_size` but whose Hash160 matches a queued `AttachmentInstance.content_hash`; drive `AttachmentsBatchStateMachine::try_proceed` to `Done`, call `AttachmentsDownloader::run`, and assert that `AtlasDB::find_attachment` afterward returns the oversized content (showing `insert_instantiated_attachment` accepted it without rejection).

    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
