### Title
Cross-lane StackerDB chunk signature replay lets an unprivileged party overwrite a signer's slot in the wrong signer contract - ([File: libstackerdb/src/libstackerdb.rs], [File: stackslib/src/net/stackerdb/db.rs])

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures only commit to `(slot_id, slot_version, data_hash)`, never to the StackerDB contract (`QualifiedContractIdentifier`) the chunk is destined for. Because the same signer occupies the same numeric slot index across all of the reward cycle's `signer-<cycle>-<message_id>` StackerDB contracts (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`), a chunk that a signer legitimately signed and published for one message-lane contract is also a valid signature for the same slot in the sibling contracts. Any observer (no private key needed) can copy a chunk that was already broadcast publicly and POST it into a *different* signer-message contract's slot, and the write-path (`SlotMetadata::verify`, `StackerDBs::try_replace_chunk`, `PeerNetwork::validate_received_chunk`) will accept it because none of these checks bind the signature to the contract being written.

### Finding Description
`SlotMetadata::auth_digest` (`libstackerdb/src/libstackerdb.rs:159-166`) computes the signed digest as:
```
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
``` [1](#0-0) 
There is no contract identifier, message-lane ID, or any other domain separator baked into what is signed. `StackerDBChunkData::verify`/`recover_pk` (`libstackerdb/src/libstackerdb.rs:233-244`) reuses this same digest to authenticate a chunk against a given `StacksAddress`. [2](#0-1) 

The write-side check `StackerDBs::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-437`) resolves the expected signer address purely from `(smart_contract, slot_id)` via `get_slot_validation`, then calls `slot_desc.verify(&slot_validation.signer)`, never checking that the signature was produced *for this contract*: [3](#0-2) 
The same pattern exists in the p2p gossip/replication path, `PeerNetwork::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:679-697`), which likewise looks up the signer solely by `(smart_contract_id, slot_id)` and verifies the chunk's self-contained signature with no cross-check against the contract: [4](#0-3) 

Slot assignment is per-reward-cycle and shared across the sibling `signer-<cycle>-<message_id>` contracts (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`), as evidenced by `MessageSlotID::stacker_db_contract` deriving each contract from the same reward-cycle signer-set ordering, and by the signers boot contract `stackerdb-get-signer-slots-page`, which stores one shared slot list per reward cycle used by every message-id contract instance: [5](#0-4) [6](#0-5) 

This means a signer's given slot index `K` is the *same* `K` in the `BlockResponse`, `StateMachineUpdate` and `BlockPreCommit` contracts for that reward cycle, and each contract independently tracks its own lamport `slot_version` counter for slot `K`. Since all StackerDB chunks are public (retrievable via `GetChunk`/inventory sync), an attacker can take a chunk `S` legitimately signed by signer `X` for slot `K` in contract `signer-N-1` and resubmit the identical `(slot_id, slot_version, sig, data)` tuple as a POST to `signer-N-2` or `signer-N-3` for the same slot `K`. The signature verification passes (digest is identical, address lookup for `(contract, K)` still resolves to `X`), and if the target contract's current version for slot `K` is lower than the replayed `slot_version`, the write succeeds — with no need for `X`'s private key at all.

Notably, one specific consumer (`SignerEvent::TryFrom<StackerDBChunksEvent>` in `libsigner/src/events.rs:568-596`) already contains an explicit, commented mitigating filter (`signer_message_payload_matches_lane`) that drops chunks whose payload type-prefix doesn't belong to the contract's message-id lane — this is direct evidence that lane-crossing chunks are expected to reach that code path and must be filtered there. However, this filter operates only at message-interpretation time in that one consumer path; it does not prevent the write itself (the polluted chunk is still persisted and gossiped as the "current" chunk for that slot in the wrong contract), and other consumers (e.g., the generic `get_messages`/`get_latest_chunks` polling helpers in `stacks-signer/src/client/stackerdb.rs`) were not confirmed to apply an equivalent lane check.

### Impact Explanation
An unprivileged, keyless attacker can overwrite a legitimate signer's slot content in a StackerDB contract they were never authorized to write to, using only publicly-observable data. This is an unauthorized write to StackerDB state performed under a signature that was never produced for that (contract, slot) — the exact "authenticated vs. stored" equality (signature validity is scoped to slot+version+hash, but enforcement treats it as scoped to a specific contract) is broken. At minimum, this corrupts the target slot's data (denial-of-service against the affected signer/lane, since the legitimate signer must now race to publish a higher version to reclaim the slot), and — for any consumer path that does not itself validate the payload type against the contract's message-lane — it can also constitute forged-data propagation into a wrong signer message lane.

### Likelihood Explanation
Requires no privileged access: it only needs the ability to observe an already-published StackerDB chunk (trivial, since chunks are public) and re-submit it via the ordinary `PutChunk` HTTP RPC or p2p StackerDBPushChunk path to a different, but related, StackerDB contract for the same reward cycle. No cryptographic secret of any party is needed.

### Recommendation
Bind the signed digest to the destination context: include the StackerDB contract identifier (and/or the `MessageSlotID`/message-lane) in `SlotMetadata::auth_digest`, so a signature produced for one contract/lane cannot verify against another. Alternatively/additionally, enforce the lane-vs-payload-type check (already present ad hoc in `libsigner/src/events.rs`) uniformly at the write path (`StackerDBs::try_replace_chunk` / `PeerNetwork::validate_received_chunk`) rather than only in one downstream consumer.

### Proof of Concept
1. Wait for reward cycle `N` and note that signer `X` occupies slot `K` in both `signer-N-1` (`BlockResponse`) and `signer-N-3` (`BlockPreCommit`) — true because both derive slot ordering from the same per-cycle signer list [5](#0-4) .
2. Fetch signer `X`'s currently-published chunk for slot `K` in `signer-N-1` via the public `GetChunk` RPC (`slot_id=K, slot_version=V, sig, data`).
3. POST the identical `(slot_id=K, slot_version=V, sig, data)` to `signer-N-3`'s `PutChunk` endpoint, without possessing `X`'s private key.
4. `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:411-423`) resolves the slot-`K` signer for `signer-N-3` as `X`, calls `slot_desc.verify(&X)`, which succeeds because `auth_digest` never referenced the contract; if `V` exceeds `signer-N-3`'s current slot-`K` version, the chunk is accepted and persisted, overwriting/polluting `X`'s `BlockPreCommit` slot with `BlockResponse` content the attacker never had authorization to write.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn recover_pk(&self) -> Result<StacksPublicKey, Error> {
        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
