### Title
Smart-HTTP `PostUploadPackWithSidechannel` lacks the negotiation-phase timeout that mitigates time-of-check-to-time-of-use (TOCTOU) access-permission races - (File: internal/gitaly/service/smarthttp/upload_pack.go)

### Summary
Gitaly already recognizes and mitigates a TOCTOU class of bug that is directly analogous to the reported oracle-price-staleness issue: an access check (e.g., permission/oracle-price validation) is performed at the *start* of a long-running operation, but the operation itself is only carried out later, after client-controlled negotiation. If the negotiation can be stalled indefinitely, the operation executes under authorization state that may no longer be valid — exactly the "gap between request creation and execution" flaw described in the report. Gitaly's SSH `upload-pack`/`upload-archive` paths defend against this with `pktline.ReadMonitor`, but the functionally-equivalent smart-HTTP `PostUploadPackWithSidechannel` path does not use this protection.

### Finding Description
The SSH implementation of `upload-pack` explicitly documents and mitigates this exact race in `internal/gitaly/service/ssh/upload_command.go`: [1](#0-0) 

It wraps stdin with a `pktline.ReadMonitor` that cancels the underlying git process if the client does not send the "done"/flush packet within `timeoutTicker`, specifically to bound the time between the access check (performed once, at RPC start) and the actual pack-generation/negotiation-completion (time of use): [2](#0-1) [3](#0-2) 

`SSHUploadArchive` uses the same `runUploadCommand` helper and therefore the same protection: [4](#0-3) 

In contrast, the smart-HTTP counterpart `PostUploadPackWithSidechannel` → `runUploadPack` performs `validateUploadPackRequest` (which validates the repository/authorization context) once, then directly execs `git upload-pack --stateless-rpc` with the raw sidechannel connection as stdin, with no equivalent `pktline.ReadMonitor` or timeout ticker bounding how long the client can hold the negotiation open: [5](#0-4) 

Because access/permission checks for a Gitaly RPC (whether internal repository ACLs or external `pre-receive`/`custom hooks`-style checks orchestrated by GitLab Rails) happen at RPC invocation time, a client that opens the HTTP/gRPC sidechannel connection but delays sending the pack negotiation ("want"/"done") lines can keep the connection open indefinitely. If the caller's authorization changes during that window (e.g., a repository is made private, the user's access is revoked, or a protected-branch/permission policy is updated), the eventual pack transfer still proceeds using the stale, now-invalid authorization state established at connection open — the same "prices are valid at request time but not re-validated at execution time" defect pattern described in the report.

### Impact Explanation
This allows a user whose access was originally valid (or is in the process of being revoked) to keep a `PostUploadPackWithSidechannel` connection open and later exfiltrate repository objects (via the eventual pack transfer) after the point their permissions should have been cut off. This is a real information-disclosure/authorization-bypass primitive, not a low-impact race — it is precisely the vulnerability class that GitLab's own SSH code comments identify and patch (`internal/git/pktline/read_monitor.go`), but the HTTP transport path lacks the equivalent control.

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged access or malicious peer/MITM is required, only an ordinary client using the standard HTTP smart protocol (`git clone`/`git fetch` over HTTP), which is the default transport for most GitLab deployments. The only requirement is the ability to delay sending the negotiation packet after the connection/RPC has been accepted, which any HTTP client trivially controls.

### Recommendation
Apply the same `pktline.ReadMonitor`/timeout-ticker mechanism used in `internal/gitaly/service/ssh/upload_command.go` to the smart-HTTP `runUploadPack` path in `internal/gitaly/service/smarthttp/upload_pack.go`, bounding the maximum time between RPC start (access check) and negotiation completion, and canceling the `git upload-pack` process if the client does not send the terminating packet in time.

### Proof of Concept
1. A client with valid repository read access initiates `git fetch` over HTTP, invoking `PostUploadPackWithSidechannel`.
2. `validateUploadPackRequest` succeeds (access check performed once, at start).
3. The client establishes the sidechannel connection but deliberately withholds the git pack-protocol "done"/flush packet, keeping the negotiation open (no timeout enforced on this stage, unlike SSH's `runUploadCommand`).
4. During this window, the operator revokes the client's access to the repository (e.g., removes them from the project, makes the repo private).
5. The client finally sends "done"; `git upload-pack --stateless-rpc` proceeds to generate and transfer the full pack based on the original, now-stale authorization, since no re-check or negotiation timeout occurs in `runUploadPack`.
6. The client receives repository objects it should no longer be authorized to access.

// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//
// This approach is better than placing a timeout on the overall git operation
// because there is a conflict between mitigating the use-after-check with a
// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.
```

func (s *server) validateUploadPackRequest(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest) (string, []gitcmd.ConfigPair, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return "", nil, err
	}
	repoPath, err := s.locator.GetRepoPath(ctx, repository)
	if err != nil {
		return "", nil, err
	}

	gitcmd.WarnIfTooManyBitmaps(ctx, s.logger, s.locator, repository.GetStorageName(), repoPath)

	config, err := gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())
	if err != nil {
		return "", nil, err
	}

	return repoPath, config, nil
}

func (s *server) runUploadPack(ctx context.Context, req *gitalypb.PostUploadPackWithSidechannelRequest, repoPath string, gitConfig []gitcmd.ConfigPair, stdin io.Reader, stdout io.Writer) (stats *stats.PackfileNegotiation, _ error) {
	h := sha1.New()

	stdin = io.TeeReader(stdin, h)
	stdin, collector := s.runStatsCollector(ctx, stdin)
	defer func() {
		if stats == nil {
			stats = collector.finish()
		}
	}()

	repo := s.localRepoFactory.Build(req.GetRepository())
	if s.bundleURIManager != nil {
		// Bundle generation is an optimization that is transparent to users.
		// If it fails, we log the error but continue with the regular upload-pack
		// operation without the bundle optimization.
		// If successful, a goroutine is spawned to generate the bundle, in which case
		// the bundle generation becomes independent of the RPC request.
		if err := s.bundleURIManager.GenerateWithStrategy(ctx, repo); err != nil {
			s.logger.WithError(err).Error("failed generating bundle")
		}
		gitConfig = append(gitConfig, s.bundleURIManager.UploadPackGitConfig(ctx, req.GetRepository())...)
	} else {
		gitConfig = append(gitConfig, bundleuri.CapabilitiesGitConfig(ctx, false)...)
	}

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return nil, fmt.Errorf("detecting object hash: %w", err)
	}

	commandOpts := []gitcmd.CmdOpt{
		gitcmd.WithStdin(stdin),
		gitcmd.WithSetupStdout(),
		gitcmd.WithGitProtocol(s.logger, req),
		gitcmd.WithConfig(gitConfig...),
		gitcmd.WithPackObjectsHookEnv(objectHash, req.GetRepository(), "http"),
	}

	if s.cfg.Hooks.PackObjectsHookMaxProc > 0 {
		commandOpts = append(commandOpts, gitcmd.WithEnv("GOMAXPROCS="+strconv.Itoa(int(s.cfg.Hooks.PackObjectsHookMaxProc))))
	}

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name:  "upload-pack",
		Flags: []gitcmd.Option{gitcmd.Flag{Name: "--stateless-rpc"}},
		Args:  []string{repoPath},
	}, commandOpts...)
	if err != nil {
		return nil, structerr.NewFailedPrecondition("spawning upload-pack: %w", err)
	}
```
