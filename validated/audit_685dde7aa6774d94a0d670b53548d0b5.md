### Title
Unauthenticated Full-Table Scan DoS via Wallet.getAssetIssueByName/getAssetIssueListByName - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
Multiple unauthenticated HTTP/gRPC query endpoints (`getassetissuebyname`, `getassetissuelistbyname` and their PBFT/Solidity variants) resolve an attacker-supplied token name by loading and iterating **every** asset issue capsule in the `AssetIssueStore`/`AssetIssueV2Store` instead of using an index lookup keyed by name. Because there is no index from name to key, each request forces a full store scan, and the scan cost scales with the number of assets ever issued on the chain, mirroring the parse-server bug class of "unindexed database query executed before validating/rejecting an unauthenticated request."

### Finding Description
`Wallet.getAssetIssueByName` calls `chainBaseManager.getAssetIssueV2Store().getAllAssetIssues()` and then filters the full in-memory list by name whenever `AllowSameTokenName == 1` (the long-standing default on mainnet): [1](#0-0) 

`Wallet.getAssetIssueListByName` is worse: it **unconditionally** (regardless of the `AllowSameTokenName` flag) loads the full asset store via `getAssetIssueStoreFinal(...).getAllAssetIssues()` before filtering by name: [2](#0-1) 

`AssetIssueStore.getAllAssetIssues()` performs a full LevelDB/RocksDB iterator scan and materializes every capsule into a `List`, deserializing each value: [3](#0-2) 

This is reachable without authentication via the HTTP servlets `GetAssetIssueByNameServlet` and `GetAssetIssueListByNameServlet`, which pass an arbitrary attacker-controlled `value` parameter straight into `wallet.getAssetIssueByName`/`getAssetIssueListByName`: [4](#0-3) [5](#0-4) 

and via the equivalent gRPC methods in `RpcApiService`: [6](#0-5) [7](#0-6) 

No caching, index, or short-circuit exists prior to the full scan — the same `getAllAssetIssues()` full-collection materialization runs on every single request, exactly analogous to the parse-server pattern where an unindexed query runs before the request is validated/rejected.

### Impact Explanation
Because every call performs an O(n) full-store deserialization scan where n is the total number of assets ever issued (a number that only grows over the chain's lifetime and that any account can increase cheaply by issuing new tokens via `AssetIssueActuator`), an unauthenticated remote attacker can send a burst of `getassetissuebyname` / `getassetissuelistbyname` (HTTP or gRPC) requests with arbitrary/garbage names. These requests can be trivially parallelized to consume CPU, I/O, and heap on the node repeatedly deserializing the full asset table, degrading or crashing the FullNode/SolidityNode's ability to serve legitimate API traffic — a Denial of Service on the node's public query interface (CWE-400), matching the impact class described in the analog advisory.

### Likelihood Explanation
The endpoints are open, unauthenticated, rate-limited only by the generic `RateLimiterServlet` (which does not account for per-request cost), and require no special crafting beyond supplying any nonexistent asset name string. The attack cost for the requester is trivial (a short HTTP GET/POST or gRPC call) while the server-side cost is proportional to the entire asset table, making this readily and cheaply exploitable at scale.

### Recommendation
Maintain a persisted or in-memory name→key index for assets (populated at issuance time in `AssetIssueActuator`) so that name lookups are O(1)/O(log n) instead of O(n) full-store scans. At minimum, cap and cache `getAllAssetIssues()` results, and add a fast-path rejection when the queried name does not match any cached index entry before touching the underlying store iterator, so that arbitrary/unconfigured names are rejected without a full collection scan.

### Proof of Concept
1. Deploy a FullNode with a non-trivial number of previously issued assets (an attacker can also inflate this number themselves via cheap repeated `AssetIssueContract` transactions).
2. From an unauthenticated client, repeatedly call `http://<node>:8090/wallet/getassetissuelistbyname` (or the gRPC `getAssetIssueListByName`/`getAssetIssueByName` methods) with a random/nonexistent `value` on each request, in parallel across many connections/threads.
3. Observe that each request triggers `AssetIssueStore.getAllAssetIssues()` / `AssetIssueV2Store.getAllAssetIssues()`, fully iterating and deserializing the entire asset store, causing sustained high CPU/I/O usage and increased latency for all other API consumers of the node as the request volume scales.

    List<AssetIssueCapsule> assetIssueCapsuleList =
        getAssetIssueStoreFinal(chainBaseManager.getDynamicPropertiesStore(),
            chainBaseManager.getAssetIssueStore(),
            chainBaseManager.getAssetIssueV2Store()).getAllAssetIssues();

    BandwidthProcessor processor = new BandwidthProcessor(chainBaseManager);
    AssetIssueList.Builder builder = AssetIssueList.newBuilder();
    assetIssueCapsuleList.stream()
        .filter(assetIssueCapsule -> assetIssueCapsule.getName().equals(assetName))
        .forEach(
            issueCapsule -> {
              processor.updateUsage(issueCapsule);
              builder.addAssetIssue(issueCapsule.getInstance());
            });

    return builder.build();
