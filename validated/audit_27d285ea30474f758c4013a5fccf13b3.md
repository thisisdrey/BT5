### Title
Path traversal via crafted `custom_hooks` tar member names in `ExtractHooks` allows arbitrary file write outside temp directory - (File: internal/gitaly/repoutil/custom_hooks.go)

### Finding Description
`ExtractHooks` shells out to the system `tar` binary with `tar -xf - -C path --strip-components N custom_hooks` [1](#0-0) . The trailing `custom_hooks` argument is a member-name filter that matches any archive entry whose path begins with the `custom_hooks/` prefix — it does not validate or canonicalize the remainder of the path. GNU `tar` does not reject `..` path segments in member names by default (only absolute paths trigger a "removing leading '/'" warning), so an entry such as `custom_hooks/../../../../tmp/evil` matches the `custom_hooks` filter and is extracted to a path computed by simple concatenation with `-C path`, letting the OS resolve the `..` components and write outside the destination directory. No `storage.ValidateRelativePath`, symlink check, or member-name sanitization exists in `ExtractHooks` itself; contrast this with `internal/gitaly/service/repository/replicate.go`'s `extractTarToDirectory`, which explicitly validates symlink targets for path escape (`TestExtractTarToDirectory_SymlinkValidation` in `replicate_test.go` [2](#0-1) ), showing the project is aware of this exact class of issue but has not applied equivalent protection to `ExtractHooks`. `SetCustomHooks` then calls `ExtractHooks(ctx, logger, reader, tmpDir.Path(), false)` and later `os.Rename(tempHooksPath, repoHooksPath)` [3](#0-2) [4](#0-3) , but the rename only moves the `custom_hooks` subdirectory — files already escaped outside `tmpDir` during extraction are unaffected by, and not cleaned up by, that step.

`SetCustomHooksRequest`/`RestoreCustomHooksRequest` are streamed directly to `repoutil.SetCustomHooks` with only `locator.ValidateRepository` performed on the repository field [5](#0-4)  — there is no validation of the tar payload's member names before it reaches `ExtractHooks`.

### Impact Explanation
A successful exploit lets the attacker write arbitrary files to any location the Gitaly process's OS user can reach (subject to depth/`..` count needed to escape the temp directory tree), which is a storage-path-confinement violation and can lead to file overwrite / potential code execution depending on what paths are writable (e.g., other repositories' data, or files under Gitaly's runtime directories). This matches "storage-path escape" / "archive extraction escape" impact classes.

### Likelihood Explanation
Exploitability is gated on whether these RPCs are reachable by an unprivileged GitLab user. `SetCustomHooks`/`RestoreCustomHooks` are Gitaly RPCs typically invoked only by GitLab Rails when an instance/group/project owner or admin configures custom server hooks (a privileged, admin-only feature in GitLab), or by internal backup/restore tooling — not by a plain `git push`/fetch. This repository (Gitaly) does not include the GitLab Rails authorization layer, so it cannot be confirmed from this codebase alone that an "unprivileged attacker with no special role" can trigger this RPC on an arbitrary repository. Given the stated threat model explicitly excludes privileged/admin capability, and custom hooks configuration is a privileged operation in the broader GitLab product, this does not clearly meet the "unprivileged attacker" precondition required by the rules.

### Recommendation
Reject archive members whose cleaned relative path contains `..` segments or resolves outside the `custom_hooks` extraction root before invoking `tar`, e.g., by pre-parsing the tar stream with Go's `archive/tar` and validating each header name via `storage.ValidateRelativePath`/`filepath.Clean` + `strings.HasPrefix` boundary check (as already done for symlinks in `replicate.go`'s `extractTarToDirectory`) prior to piping data into the external `tar` command, or by extracting with a memory-safe, traversal-aware Go tar reader that enforces containment instead of shelling out to `tar`.

### Proof of Concept
```go
func TestExtractHooks_PathTraversal(t *testing.T) {
    ctx := testhelper.Context(t)
    tmpDir := t.TempDir()
    outsideDir := t.TempDir() // sibling directory, simulates "outside path"

    var buf bytes.Buffer
    w := tar.NewWriter(&buf)
    // crafted member name escapes the destination via ../
    name := filepath.Join("custom_hooks", "..", "..", filepath.Base(outsideDir), "evil")
    require.NoError(t, w.WriteHeader(&tar.Header{
        Name: name,
        Mode: 0o755,
        Size: int64(len("pwned")),
    }))
    _, err := w.Write([]byte("pwned"))
    require.NoError(t, err)
    require.NoError(t, w.Close())

    err := ExtractHooks(ctx, testhelper.NewLogger(t), &buf, tmpDir, false)
    require.NoError(t, err)

    // Assert file was NOT written outside tmpDir
    _, statErr := os.Stat(filepath.Join(outsideDir, "evil"))
    require.True(t, os.IsNotExist(statErr), "expected no escape, but file was written outside tmpDir")
}
```
Because whether this RPC is reachable by a truly unprivileged user cannot be confirmed from the Gitaly codebase alone (custom hooks configuration is normally a privileged/admin operation gated by GitLab Rails), this finding should be treated as **conditionally valid**, pending confirmation of RPC reachability by an unprivileged actor.
