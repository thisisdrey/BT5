### Title
Resource-weight dilution griefing via instant Freeze/UnfreezeBalanceV2 cycling starves other accounts' bandwidth/energy - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceV2Actuator.java])

### Summary
`TotalNetLimit`/`TotalEnergyCurrentLimit` are shared pools distributed proportionally to accounts based on `TotalNetWeight`/`TotalEnergyWeight` [3](#0-2) . Any account can call `FreezeBalanceV2Contract` to instantly increase this shared total weight [4](#0-3) , and then immediately call `UnfreezeBalanceV2Contract` to reverse the weight contribution with no minimum hold period enforced [5](#0-4) . This mirrors the reported Knox Queue bug class: a user can transiently occupy a shared, capacity-limited resource pool to disadvantage other participants, then reverse the action with no lasting financial cost (only a temporary liquidity lock of the frozen TRX for `unfreezeDelayDays`, not the risk of loss).

### Finding Description
`calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` compute each account's available free bandwidth/energy as `frozenBalance/totalWeight * totalLimit` [6](#0-5) [3](#0-2) . `TotalNetWeight`/`TotalEnergyWeight` are chain-wide dynamic properties updated on every `FreezeBalanceV2Contract`/`UnfreezeBalanceV2Contract` execution [7](#0-6) .

Because `FreezeBalanceV2Actuator.validate()` has no minimum lock-time requirement (unlike legacy V1 freeze which enforces `FROZEN_PERIOD`) [8](#0-7) , and `UnfreezeBalanceV2Actuator.validate()` has no elapsed-time check either [9](#0-8) , an attacker with a large TRX balance can freeze it for BANDWIDTH or ENERGY to spike `TotalNetWeight`/`TotalEnergyWeight` within a block or two, immediately diluting every other account's proportional free-resource share, then unfreeze in a subsequent transaction to reverse their own contribution (the weight is decremented instantly at unfreeze time, per `updateTotalResourceWeight` [5](#0-4) ). The attacker only loses liquidity on the frozen principal for `unfreezeDelayDays` (returned via `WithdrawExpireUnfreezeContract` later) — not the capital itself — analogous to the Queue exploiter withdrawing before epoch end with "no risk."

### Impact Explanation
During the dilution window, other accounts' computed `netLimit`/`energyLimit` drop sharply, which can push their bandwidth/energy usage over the newly-lowered limit in `useAccountNet`/energy consumption checks [10](#0-9) , causing their free-resource-funded transactions to fail or forcing them to burn TRX for bandwidth/energy fees they would not normally pay. Since this can be repeated cheaply and reversed with no capital loss, it is a griefing/DoS vector against ordinary users' resource allowance rather than a fund-theft bug.

### Likelihood Explanation
Reachable by any unprivileged account holding sufficient TRX via two ordinary signed transactions (`FreezeBalanceV2Contract` then `UnfreezeBalanceV2Contract`), requiring no special privilege, and can be automated/repeated across blocks. The severity scales with how large a fraction of `TotalNetWeight`/`TotalEnergyWeight` the attacker's freeze represents.

### Recommendation
Introduce a minimum hold duration between `FreezeBalanceV2Contract` and a matching `UnfreezeBalanceV2Contract` for the same resource type (similar to the legacy `FROZEN_PERIOD` enforced in V1 freeze), or dampen/smooth `TotalNetWeight`/`TotalEnergyWeight` changes (e.g., average over a window, as already done for `TotalEnergyAverageUsage`/`updateAdaptiveTotalEnergyLimit`) so that a single-block freeze/unfreeze cannot instantaneously swing every account's resource share.

### Proof of Concept
1. Attacker account A holds `N` TRX and calls `FreezeBalanceV2Contract{resource=ENERGY, frozenBalance=N}` — `TotalEnergyWeight` jumps by `N/TRX_PRECISION` immediately in the same block [11](#0-10) .
2. Any other account B's `calculateGlobalEnergyLimitV2` is computed against the new inflated `TotalEnergyWeight`, sharply reducing B's free energy limit for the block(s) A stays frozen [12](#0-11) .
3. Attacker A immediately submits `UnfreezeBalanceV2Contract{resource=ENERGY, unfreezeBalance=N}` — no minimum-hold check blocks this [9](#0-8) ; `TotalEnergyWeight` is decremented back immediately [13](#0-12) .
4. A's `N` TRX becomes withdrawable after `unfreezeDelayDays` via `WithdrawExpireUnfreezeContract`, with no principal loss — only temporary illiquidity — while B experienced degraded resource availability during the window.

Note: The precise economic magnitude (how much `N` is needed relative to network-wide `TotalEnergyWeight`/`TotalNetWeight` to cause meaningful impact) depends on live chain parameters not fully inspectable from the indexed code; a background Devin session with full repo/test access could quantify this via `CalculateGlobalLimitHardenTest`-style simulations.

              "ResourceCode error, valid ResourceCode[BANDWIDTH、ENERGY]");
        }

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {

    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  private boolean useAccountNet(AccountCapsule accountCapsule, long bytes, long now) {

    long netUsage = accountCapsule.getNetUsage();
    long latestConsumeTime = accountCapsule.getLatestConsumeTime();
    long netLimit = calculateGlobalNetLimit(accountCapsule);

    long newNetUsage;
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(netUsage, 0, latestConsumeTime, now);
    } else {
      // only participate in the calculation as a temporary variable, without disk flushing
      newNetUsage = recovery(accountCapsule, BANDWIDTH, netUsage, latestConsumeTime, now);
    }


    if (bytes > (netLimit - newNetUsage)) {
      logger.debug("Net usage is running out, now use free net usage."
              + " Bytes: {}, netLimit: {}, newNetUsage: {}.",
          bytes, netLimit, newNetUsage);
      return false;
    }

    long latestOperationTime = chainBaseManager.getHeadBlockTimeStamp();
    if (!dynamicPropertiesStore.supportUnfreezeDelay()) {
      newNetUsage = increase(newNetUsage, bytes, now, now);
    } else {
      // Participate in calculation and flush disk persistence
      newNetUsage = increase(accountCapsule, BANDWIDTH, netUsage, bytes, latestConsumeTime, now);
    }

    accountCapsule.setNetUsage(newNetUsage);
    accountCapsule.setLatestOperationTime(latestOperationTime);
    accountCapsule.setLatestConsumeTime(now);

    chainBaseManager.getAccountStore().put(accountCapsule.createDbKey(), accountCapsule);
    return true;
  }
