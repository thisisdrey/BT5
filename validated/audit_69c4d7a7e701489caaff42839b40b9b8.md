### Title
Positions with debt below `debtFloorInUsd` are permanently unliquidatable, causing protocol bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate` enforces two mutually exclusive constraints: `maxLiquidable` caps each liquidation to a fraction of total debt (initialized to 50%), and `debtFloorInUsd` reverts any repayment that leaves a non-zero remainder below the floor. When a position's total debt is worth less than `debtFloorInUsd`, every possible `amountToRepay_` reverts — partial repayments violate the floor, and full repayment violates `maxLiquidable` — so the liquidation function is permanently disabled for that position.

### Finding Description
In `liquidate`, the ratio check `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts with `AmountGreaterThanMaxLiquidable` for any `amountToRepay_` above 50% of the debt (default `maxLiquidable = 0.5e18`). [1](#0-0)  Separately, if `debtFloorInUsd > 0`, any liquidation leaving `0 < remainingDebtUsd < debtFloorInUsd` reverts with `RemainingDebtIsLowerThanTheFloor`. [2](#0-1) 

`DebtToken._mint` only guarantees debt ≥ floor *at mint time in USD terms*. [3](#0-2)  Because the floor is evaluated via `masterOracle().quoteTokenToUsd(syntheticToken, balance)`, a debt minted exactly at the floor drifts below it whenever the synthetic token's oracle price ticks below its peg — no privileged action or bad oracle required, just normal price movement. `DebtToken.repay` applies the same floor check, so neither users nor third parties can push debt below the floor manually, but interest accrual and collateral price decay can push the position unhealthy while debt-USD sits under the floor. [4](#0-3) 

Once in that state, for any `amountToRepay_`:
- `amountToRepay_ < debt` → remaining debt < floor → `RemainingDebtIsLowerThanTheFloor`
- `amountToRepay_ == debt` → ratio = 1 > `maxLiquidable` (0.5) → `AmountGreaterThanMaxLiquidable`

`quoteLiquidateMax` also cannot produce a usable value, since it caps output at `balance.wadMul(maxLiquidable)`. [5](#0-4)  The unliquidatable debt's locked collateral can never be seized, and the position's collateral stays frozen because `lockedBalanceOf` remains ≥ balance.

### Impact Explanation
Permanent freezing of liquidation: unhealthy under-floor positions become bad debt that can never be cleared while `maxLiquidable < 1e18`. The protocol accumulates unbacked synthetic supply (debt without seizable collateral covering it), and the victim's collateral is permanently locked — `unlockedBalanceOf` stays 0 while the debt is nonzero. This is a liveness/availability break of `Pool.liquidate`, analogous to the CVE's complete-DoS bug class.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` (a live governance parameter; the code path exists precisely because floors are used) and `maxLiquidable < 1e18` (default and only tested config is 50%). An attacker can open a position with debt exactly at the floor; a small downtick in the synthetic's oracle price or in collateral value then makes it simultaneously unhealthy and under-floor. No privileged role, oracle manipulation, or malicious infrastructure is needed — only normal market movement. Impact per position is bounded by the floor value, so severity is medium, matching the CVE's 6.5 rating.

### Recommendation
In `Pool.liquidate`, allow full repayment to bypass `maxLiquidable` when the alternative is an always-reverting position — e.g., skip the `maxLiquidable` check when `amountToRepay_ == _debtTokenBalance`, or when the remaining debt would otherwise be below `debtFloorInUsd` (effectively forcing dust positions to be fully liquidated). Apply the same exemption logic in `quoteLiquidateMax`.

### Proof of Concept
Hardhat-style sketch on a fork/local deploy with `debtFloorInUsd > 0` and `maxLiquidable = 0.5e18`:

```ts
// setup: pool has debtFloorInUsd = $3,000, maxLiquidable = 50%
await pool.updateDebtFloor(parseEther('3000'))

// 1. Attacker deposits collateral and issues debt exactly at the floor.
//    msETH minted so that quoteTokenToUsd(msETH, debt) == 3000 USD.
await metDepositToken.connect(attacker).deposit(collateralAmount)
await msEthDebtToken.connect(attacker).issue(debtAtFloor, attacker.address)

// 2. Collateral price drops (normal oracle update) -> position unhealthy
//    AND debtUsd < floor (or debt already < floor via synth price tick).
await masterOracle.updatePrice(met.address, lowerPrice)
const {_isHealthy} = await pool.debtPositionOf(attacker.address)
expect(_isHealthy).to.be.false

// 3. Every liquidation call reverts.
const debt = await msEthDebtToken.balanceOf(attacker.address)

// partial repayment -> floor revert
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, debt.div(2), msdMET.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// full repayment -> maxLiquidable revert
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, debt, msdMET.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

// position is permanently unliquidatable -> bad debt
```

Uncertainty: whether `debtFloorInUsd` is non-zero on a specific live deployment should be confirmed against on-chain state; the PoC above uses the parameter configuration the code explicitly supports and tests exercise (`updateDebtFloor(parseEther('3000'))` in `test/Pool.test.ts`).
