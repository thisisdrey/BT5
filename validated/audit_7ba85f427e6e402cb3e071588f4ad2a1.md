### Title
Attacker-Chosen `remoteIndexId` Can Shadow/Collide With Existing Hostinfo Entries During Handshake - ([File: handshake_manager.go])

### Summary
The Nayms report describes a class of bug where an entity that controls one side of an ID-space (an off-chain-generated `objectId`) can front-run or collide with a deterministically-derived ID controlled by another, more privileged actor, corrupting shared state and blocking legitimate use. The analogous condition in Nebula is the `localIndexId`/`remoteIndexId` pair used to key handshake and tunnel state in the hostmap: `localIndexId` is generated locally and checked for uniqueness, but `remoteIndexId` is supplied entirely by the remote peer during the handshake and is trusted as-is when inserted into `hm.mainHostMap.RemoteIndexes`, with only a log message on collision rather than any rejection or isolation.

### Finding Description
`HandshakeManager.allocateIndex` generates a `localIndexId` via `generateIndex` and retries until it finds a value that does not collide with anything already in `hm.indexes` or `hm.mainHostMap.Indexes`, guaranteeing local-index uniqueness: [1](#0-0) 

However, `remoteIndexId` is not locally generated — it comes from the handshake result (`result.RemoteIndex`) supplied by the far end of the handshake, and is stored into the hostinfo without any collision-safe allocation: [2](#0-1) 

When this hostinfo is admitted into the main hostmap, `CheckAndComplete` and `Complete` both look up `hm.mainHostMap.RemoteIndexes[hostinfo.remoteIndexId]` and, if an existing (different) hostinfo already owns that key, they merely log an informational message — "New host shadows existing host remoteIndex" — and proceed to overwrite the `RemoteIndexes` map entry: [3](#0-2) [4](#0-3) 

This mirrors the Nayms bug class precisely: one actor (here, any peer that can complete or attempt a handshake) supplies an identifier value (`remoteIndexId`) that indexes into a shared table also used/owned by another party (the existing, already-authenticated tunnel for a different peer), and the system's only defense is a comment/log acknowledging "we can't control the remote ID" — i.e., an explicitly accepted, unmitigated collision, just as the Nayms team "acknowledged" the deterministic-ID front-run as an accepted risk from an uncontrolled off-chain actor.

### Impact Explanation
Because `RemoteIndexes` is used to route inbound relay/data-plane packets to the correct `HostInfo` (see index-keyed lookups in `hostmap.go` and the relay/handshake response paths), a peer that intentionally selects/replays a `remoteIndexId` value already in use by another, unrelated tunnel can shadow that entry in the shared map. This can misdirect packet routing keyed by remote index, or make a legitimate remote's index "invisible" behind a colliding, attacker-influenced hostinfo — a form of remote state poisoning of the hostmap. It does not itself decrypt or forge authenticated payloads, but it degrades the integrity of the index-based routing/session table shared across peers, i.e., a remote state-poisoning impact directly analogous to the accepted-risk finding in the source report.

### Likelihood Explanation
Likelihood is comparable to the Nayms case #5 (any entity admin), since here any handshake participant — not just a Certificate-Authority-anchored, "valid-certificate-holder" peer performing a legitimate handshake — supplies `RemoteIndex` values in the handshake protocol, and the response is only informational logging, never rejection. Combined with `MaxHostInfosPerVpnIp` allowing multiple simultaneous hostinfos per address, repeated handshake attempts with chosen/replayed indices increase the odds of a collision landing on an active, valuable session.

### Recommendation
Do not treat a `RemoteIndexes` collision with an existing, unrelated hostinfo as informational only. At minimum, disambiguate storage so that `RemoteIndexes` lookups are also qualified by the owning `vpnAddrs`/certificate fingerprint (similar to how `Indexes` is checked against `localIndexId`), or reject/isolate handshakes whose `RemoteIndex` collides with a distinct, live hostinfo rather than silently letting `unlockedAddHostInfo`/`Complete` overwrite the map entry. Consider deriving or validating `remoteIndexId` uniqueness within the context of the specific peer relationship rather than trusting an attacker-chosen value in a globally shared table.

### Proof of Concept
1. Peer A establishes a legitimate tunnel with Peer B; the resulting hostinfo is stored with a real `remoteIndexId` (`R`) in `hm.mainHostMap.RemoteIndexes[R]` (see `handshake_manager.go:454-477` for the insertion path).
2. A malicious Peer C initiates or continues a handshake such that its produced `handshake.Result.RemoteIndex` equals `R` (the handshake protocol lets the remote choose this counter/index value on its side of the exchange, as seen in `beginHandshake`, `handshake_manager.go:752-764`).
3. When Peer C's handshake reaches `CheckAndComplete`/`Complete`, the code detects `existingRemoteIndex != nil` for key `R` but only logs "New host shadows existing host remoteIndex" and proceeds to overwrite/associate the entry (`handshake_manager.go:466-473`, `488-495`), corrupting the shared `RemoteIndexes` table entry that previously pointed to Peer B's legitimate session.

func (hm *HandshakeManager) Complete(hostinfo *HostInfo, f *Interface) {
	hm.mainHostMap.Lock()
	defer hm.mainHostMap.Unlock()
	hm.Lock()
	defer hm.Unlock()

	existingRemoteIndex, found := hm.mainHostMap.RemoteIndexes[hostinfo.remoteIndexId]
	if found && existingRemoteIndex != nil {
		// We have a collision, but this can happen since we can't control
		// the remote ID. Just log about the situation as a note.
		hostinfo.logger(hm.l).Info("New host shadows existing host remoteIndex",
			"collision", existingRemoteIndex.vpnAddrs,
		)
	}

	// We need to remove from the pending hostmap first to avoid undoing work when after to the main hostmap.
	hm.unlockedDeleteHostInfo(hostinfo)
	hm.mainHostMap.unlockedAddHostInfo(hostinfo, f)
}

func (hm *HandshakeManager) allocateIndex(hh *HandshakeHostInfo) (uint32, error) {
	hm.mainHostMap.RLock()
	defer hm.mainHostMap.RUnlock()
	hm.Lock()
	defer hm.Unlock()

	for range 32 {
		index, err := generateIndex(hm.l)
		if err != nil {
			return 0, err
		}

		_, inPending := hm.indexes[index]
		_, inMain := hm.mainHostMap.Indexes[index]

		if !inMain && !inPending {
			hh.hostinfo.localIndexId = index
			hm.indexes[index] = hh
			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}
