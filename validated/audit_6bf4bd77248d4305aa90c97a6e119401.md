### Title
Attacker-controlled handshake payload `Time` value permits permanent DoS of tunnel re-establishment for a victim VPN address - (File: handshake_manager.go)

### Summary
Nebula's handshake payload carries a `Time` field (`payload.Time`) that is fully attacker-controlled and copied verbatim into `Result.HandshakeTime` without any bound, freshness, or monotonicity check. This value becomes `hostinfo.lastHandshakeTime`, which `HandshakeManager.CheckAndComplete` uses to decide whether a *newer* handshake is allowed to replace an existing tunnel for a given VPN address. An attacker who possesses a CA-signed certificate for one identity can set this field to `math.MaxUint64` once, permanently blocking that VPN address from ever completing a legitimate rehandshake through the normal ordering path, exactly analogous to the Optimism `l2BlockNumber`/`ANCHOR_STATE_REGISTRY` issue where an unvalidated ordering value fixed at `type(uint256).max` blocks all future updates.

### Finding Description
In `handshake/machine.go`, `processPayload` sets:
```go
m.result.HandshakeTime = payload.Time
``` [1](#0-0) 
This value comes straight from the unmarshalled handshake payload sent by the remote peer, with no range, clock-skew, or monotonic check against previous handshakes.

This `HandshakeTime` is propagated into `HostInfo.lastHandshakeTime` both when a stage-1 handshake is accepted (`beginHandshake`) and when a continuation completes (`continueHandshake`): [2](#0-1) [3](#0-2) 

`CheckAndComplete` then uses this attacker-supplied value as the sole ordering criterion for whether a new handshake for the same VPN address is allowed to displace the existing tunnel:
```go
if existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime && !existingHostInfo.ConnectionState.initiator {
    return existingHostInfo, ErrExistingHostInfo
}
``` [4](#0-3) 

Once a peer completes a handshake with `HandshakeTime = math.MaxUint64`, `existingHostInfo.lastHandshakeTime` is pinned at the maximum uint64 value. Every subsequent legitimate handshake attempt for that VPN address (including from the legitimate certificate holder, after a restart, key rotation, or roam) will have a `HandshakeTime` that cannot exceed the poisoned value, so `CheckAndComplete` will always return `ErrExistingHostInfo` and refuse to replace the tunnel — this exactly mirrors the pattern in the Optimism report where `l2BlockNumber` set to `type(uint256).max` in `ANCHOR_STATE_REGISTRY.anchors` permanently blocks all future `l2BlockNumber() <= rootBlockNumber` comparisons from succeeding.

### Impact Explanation
This poisons the ordering state used to arbitrate "which handshake is newer" for a given VPN address, causing the affected peer's tunnel to become permanently stuck at the attacker's handshake. Since `ErrExistingHostInfo` causes new legitimate handshakes to be rejected in favor of the old (potentially stale/attacker-established) state, this can deny the legitimate certificate holder the ability to re-establish a fresh tunnel through the normal handshake path, a remote, unauthenticated-relative-to-that-specific-check DoS of tunnel replacement/roaming for that VPN address.

### Likelihood Explanation
Any peer that can complete a handshake (i.e., holds *any* valid certificate signed by a CA trusted by the target — not necessarily impersonating the victim's own certificate, since the check only compares `lastHandshakeTime`/`initiator` state per targeted VPN address they can address) can set this field to an extreme value in a single handshake attempt, with no rate limiting or bounds checking preventing it. The condition requires no race or timing precision, just sending `payload.Time = math.MaxUint64` once.

### Recommendation
Validate `payload.Time` against a bounded window of `time.Now()` (as is already done for certificate `NotBefore`/`NotAfter` expiry) before accepting it into `Result.HandshakeTime`, and/or replace `lastHandshakeTime`-based ordering in `CheckAndComplete` with a locally-generated monotonic sequence number that is never derived from remote input.

### Proof of Concept
1. Attacker holds a certificate signed by a CA trusted by the target (`me`).
2. Attacker crafts a handshake payload (`handshake.Payload`) with `Time = math.MaxUint64` and completes a normal IX handshake with `me` for VPN address `victim`.
3. `beginHandshake`/`continueHandshake` store `hostinfo.lastHandshakeTime = math.MaxUint64` for that hostinfo entry (`handshake_manager.go:758`, `handshake_manager.go:883`).
4. Any subsequent legitimate handshake attempt for the same VPN address arrives with a normal `HandshakeTime` (derived from real wall-clock-like values used elsewhere), which is always `< math.MaxUint64`.
5. `CheckAndComplete` evaluates `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` as true and returns `ErrExistingHostInfo`, permanently refusing to replace the tunnel for that VPN address (`handshake_manager.go:447-449`).

Note: I was not able to fully verify from the indexed code whether `payload.Time` is otherwise constrained elsewhere in the wire-format marshal/unmarshal path (e.g., in `handshake.UnmarshalPayload`) or whether there is an additional bound check applied before `Result.HandshakeTime` is set; a full review of `handshake/payload.go` (not returned by the index) would be needed to rule out an existing mitigation. If such a check exists, this finding should be treated as unconfirmed pending that review.
