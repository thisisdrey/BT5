## Title
`WriteRef` RPC bypasses the mandatory access-check / hook pipeline, allowing arbitrary force-update or deletion of any reference - (File: internal/gitaly/service/repository/write_ref.go)

### Summary
Every ref-mutating RPC in `OperationService` (`UserUpdateBranch`, `UserDeleteBranch`, `UserMergeBranch`, `UserCommitFiles`, etc.) is required to route through Rails' `/internal/allowed` access check and the `pre-receive`/`update` custom-hook pipeline before a reference is actually moved. `WriteRef`, exposed on `RepositoryService`, instead calls `updateref.New`/`u.Update`/`u.Commit` directly against the repository's ref store, with no `User` field, no call into `gitlab.Allowed`, and no invocation of `HookManager.PreReceiveHook`. This mirrors the reported CEGA bug class: a function capable of overriding authoritative state (there: price observations; here: any branch/tag ref, including protected branches) that lacks the access-control gate every equivalent, intentionally-gated function in the same service enforces.

### Finding Description
`WriteRef` (`internal/gitaly/service/repository/write_ref.go:19-48`) validates only that the ref name/revision are syntactically well formed (`validateWriteRefRequest`, lines 132-152) and then unconditionally performs the update: [1](#0-0) 
`updateRef` resolves old/new revisions and commits the change via `updateref.New(ctx, repo)` / `u.Update` / `u.Commit`: [2](#0-1) 

Compare this to the sibling `RefService.UpdateReferences` RPC and every `OperationService` RPC (`UserUpdateBranch`, `UserDeleteBranch`, `UserMergeBranch`, `UserCommitFiles`), whose proto contract explicitly states the operation "contacts Rails to verify the user is allowed" and executes `pre-receive`/`update` hooks: [3](#0-2) [4](#0-3) 

The `WriteRef` request message carries no `User` field at all and no `AccessCheckError`/`CustomHookError` structured errors, confirming by design that this RPC was never wired into the access-check/hook flow that `doc/hooks.md` describes as mandatory for any reference update performed "on behalf of a user": [5](#0-4) 

`WriteRef` is also invoked internally by trusted callers such as `create_fork`, `fetch_remote`, and `replicate` for legitimate bootstrap purposes (setting up `HEAD`/initial refs on freshly created repositories). However, it is a general-purpose, unauthenticated (from a Git-permission standpoint) RPC on `RepositoryService`: it accepts an arbitrary `Ref` (any `refs/...` path) and arbitrary `Revision`/`OldRevision` on any repository the caller's gRPC/Praefect token can address, with no verification that the caller is permitted to move that specific ref (e.g., a protected branch) and no quarantine/hook step that would let GitLab's Rails `/allowed` endpoint veto the change.

### Impact Explanation
Any client with access to the Gitaly/Praefect endpoint for a repository (which in GitLab's architecture is reachable indirectly by an ordinary Rails request path, and directly by anyone able to reach Gitaly's gRPC surface, e.g., a compromised Workhorse/Rails component, a misrouted Praefect proxy, or any RPC caller that can supply a `WriteRefRequest`) can force-move or delete **any** reference in the repository — including protected branches or tags used for release/security gating — without the reference-update passing the mandatory GitLab authorization check or executing the administrator's custom `pre-receive`/`update` hooks. This is structurally identical to the reported bug class: a state-mutating entry point that can override an authoritative value (there, price observations feeding payouts; here, ref pointers feeding branch-protection/CI/CD/release logic) while skipping the access-control gate that parallel, intentionally-restricted entry points enforce.

### Likelihood Explanation
`WriteRef` is a first-class, always-registered RPC on `RepositoryService` (not feature-flagged, not internal-only) and is trivially reachable with a well-formed `WriteRefRequest{Repository, Ref, Revision, OldRevision}` — no crafted objects, hooks, or negotiation edge cases are required. The likelihood of reaching this code path is high wherever a client can address a repository through Gitaly/Praefect without being restricted to the higher-level `OperationService` RPCs that Rails/GitLab intends to be the sole ref-mutation surface for its permission model.

### Recommendation
Restrict `WriteRef` so that it cannot be used as a general-purpose, access-check-free ref-mutation primitive: either (a) route ref updates through the same `updateref.UpdaterWithHooks`/access-check pipeline used by `OperationService`, requiring a `User` and invoking `gitlab.Allowed` plus `pre-receive`/`update` hooks before committing, or (b) explicitly scope `WriteRef` to the narrow set of trusted, internal callers (repository creation/replication bootstrap) via a distinct internal-only RPC/service boundary, ensuring it can no longer be invoked to move or delete arbitrary refs (in particular protected branches/tags) on behalf of an unauthenticated or under-authorized caller.

### Proof of Concept
1. As a client capable of issuing `RepositoryService.WriteRef` against a target repository (no `User` field required, unlike every `OperationService` RPC), send:
   ```
   WriteRefRequest{
     Repository: <target repo>,
     Ref:        "refs/heads/protected-branch",
     Revision:   "<attacker-controlled commit sha>",
     OldRevision: "<current head sha>",   // optional
   }
   ```
2. `writeRef` → `updateRef` (`internal/gitaly/service/repository/write_ref.go:36-48,50-130`) resolves the revision and commits the ref update via `git-update-ref` directly, without calling `gitlab.Allowed` or running `pre-receive`/`update` hooks.
3. The protected branch now points to the attacker-supplied commit — equivalent in effect to bypassing an `onlyCegaAdmin`-style gate that the analogous, correctly-gated `OperationService.UserUpdateBranch`/`UserDeleteBranch` RPCs enforce for the same class of mutation.

**File:** doc/hooks.md (L178-220)
```markdown
### Receive-Pack Hooks

These hooks are executed by `git-receive-pack` whenever changes are pushed into
a repository and can be used to:

- Verify whether the changes should be allowed into the repository in the first
  place (`pre-receive` and `update` hooks).
- Show information to the user (`post-update` hook).

While the reference-transaction hook executes on all Gitaly nodes, the
receive-pack style hooks only run on a single Gitaly, which is the primary node.
It can thus happen that receive-pack style hooks reject the update on the
primary node, which is not something the secondary nodes would see. The result
is that secondaries would now hang until the timeout for the RPC call triggers
given that the primary is never going to vote on this transaction.

To fix the hang, transactions support graceful stops: if the primary node fails
the RPC call in code that is only executed on the primary, then it will stop the
transaction and thus tell other Gitaly nodes to stop waiting for quorum.

There are two users of these hooks:

- `PostReceivePack` and `SSHReceivePack` directly invoke `git-receive-pack`,
  which then executes the hooks for us.
- Most RPCs in the `OperationService` that write objects into the repository
  manually invoke these hooks using the `updateref.UpdaterWithHooks` structure.

These hooks perform the following functions:

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old
  and new object ID as well the name of the reference that is to be updated. At
  this point, all objects required to satisfy the update have already been
  received, but they are still in a separate "quarantine directory" and are
  therefore detached from the main repository. This hook first increments a
  reference counter that tracks how many pushes are active at the same time.
  Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint so
  that Rails can determine whether the change is allowed or not. Because objects
  still live in a quarantine directory, Gitaly tells Rails where it can find the
  quarantine directory using the repository's alternative object directory
  fields so that any subsequent RPC calls that check the change can access those
  objects. When the access checks succeed, any existing custom pre-receive hooks
  installed by the administrator are executed.
```
