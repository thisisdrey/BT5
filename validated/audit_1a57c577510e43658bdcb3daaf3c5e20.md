### Title
`gd_post_deploy` aborts on approval-race without refunding `deploy_deposit`, permanently trapping the caller's NEAR deposit - (File: `contracts/global-deployer/src/contract.rs`)

### Summary
`Contract::deploy`/`gd_deploy` schedules `deploy_global_contract_by_account_id(code)` and transfers `deploy_deposit` to the contract *before* the `gd_post_deploy` callback re-validates `self.is_approved(&code_hash)`. If `approved_hash` changes between the promise being scheduled and the callback executing (e.g. the owner calls `gd_approve` in the same or a later block/receipt), `post_deploy` returns `Err(Error::InvalidCodeHash)` before reaching the refund block, so the already-spent/transferred `deploy_deposit` is never returned and no other entrypoint can recover it.

### Finding Description
The binding that must hold is: `deploy_deposit == storage_consumed_by_deploy + refund_sent_to_refund_to_account_id`.

In `contracts/global-deployer/src/contract.rs`:
- `deploy()` (lines 180-207) computes `code_hash = Sha256::digest(&code)`, checks `is_approved(&code_hash)`, then unconditionally chains: (1) `Promise::new(current_account_id()).transfer(attached_deposit())`, (2) `.deploy_global_contract_by_account_id(code)`, (3) `.gd_post_deploy(code_hash, initial_balance, deploy_deposit)` as the callback, all in the *same receipt*. [1](#0-0) 
- `post_deploy()` (lines 209-237) re-checks `self.is_approved(&code_hash)` and returns `Err(Error::InvalidCodeHash)` immediately if it no longer matches — *before* the refund block is ever reached: [2](#0-1) 

By the time this callback executes, the deposit-transfer and `deploy_global_contract_by_account_id` actions have already executed and consumed the deposit for storage staking — these are irreversible NEAR actions within the same receipt chain, not something the callback's early return can undo. The repo's own test `test_post_deploy_fails_when_approval_changed` reproduces exactly this: it batches `gd_deploy(DEPLOYER_WASM)` and `gd_approve(deployer_hash, mt_stub_hash)` in the same transaction, and asserts the `gd_post_deploy` receipt fails while the outer transaction still succeeds: [3](#0-2) 

Because `#[private]` on `gd_post_deploy` prevents any other account from re-invoking it, and there is no `gd_withdraw`/reconciliation entrypoint anywhere in `contracts/global-deployer/src/contract.rs`, the excess balance silently merges into the contract's own NEAR balance forever, unattributed to the original depositor. No existing guard (`is_approved`, `#[private]`, `assert_one_yocto`, etc.) prevents this — they correctly block the *bad deployment*, but do not restore the caller's funds.

### Impact Explanation
The caller of `gd_deploy` (attacker or otherwise) permanently loses the portion of `deploy_deposit` that was consumed for storage on the interrupted deploy, with no code path to reclaim it — this matches the "user funds permanently frozen" Critical category. `State::code_hash` also diverges from the actually-live global contract (the WASM was deployed via `deploy_global_contract_by_account_id`, but `self.0.code_hash` is never updated because the early return skips lines 220-221), so any accounting or off-chain tooling relying on `gd_code_hash()` is inconsistent with the on-chain global contract namespace. This is repeatable for any account running a `GlobalDeployer` instance whenever a `gd_approve` lands between a `gd_deploy` promise and its callback.

### Likelihood Explanation
Triggering the race requires the owner to independently call `gd_approve` while a `gd_deploy` is in flight — the unprivileged attacker cannot force the owner's timing, but the attacker (as the `gd_deploy` caller) can deliberately construct the batch themselves (as the reproducing test does, batching `gd_deploy` + `gd_approve` in one transaction when they happen to also be the owner, or by simply calling `gd_deploy` and racing a natural/legitimate `gd_approve` from the real owner). Since `gd_deploy` is explicitly permissionless and requires only a large deposit (50 NEAR in tests) with no minimum-safety window, and `gd_approve` is a normal, frequently-used owner operation in the documented "Two-Step Deployment" workflow, this is a realistic, low-cost, and directly demonstrable condition — the repository's own sandbox test already exercises it.

### Recommendation
In `post_deploy`, when `is_approved` fails, still issue the refund of `deploy_deposit` (computed the same way as the success path) back to `env::refund_to_account_id()` before returning `Err`, so the deposit is never silently absorbed by the contract's balance regardless of whether the deployment is accepted.

### Proof of Concept
Extend `tests/src/tests/global_deployer/mod.rs::test_post_deploy_fails_when_approval_changed` (already present) with balance assertions:
```rust
let deployer_balance_before = root.balance(controller_instance.contract_id()).await.unwrap().total;
let caller_balance_before = root.balance(root.account_id()).await.unwrap().total;
// ... existing batched gd_deploy + gd_approve call and failure assertions ...
let deployer_balance_after = root.balance(controller_instance.contract_id()).await.unwrap().total;
// Assert the contract's balance grew by (close to) the full deploy_deposit,
// i.e. the deposit was consumed but never refunded to the caller.
assert!(deployer_balance_after.saturating_sub(deployer_balance_before) > NearToken::from_near(45));
// Assert there is no other callable entrypoint (gd_withdraw, etc.) to recover it,
// e.g. by grepping the contract's public methods / ABI.
```
This confirms `deploy_deposit paid != storage consumed + refund sent`, with the difference permanently retained by the contract with no recovery method.

        fn deploy(&self, code: Vec<u8>) -> Result<Promise> {
            let code_hash = Sha256::digest(&code).into();

            if !self.is_approved(&code_hash) {
                return Err(Error::InvalidCodeHash);
            }

            let initial_balance = env::account_balance().saturating_sub(env::attached_deposit());

            Ok(Self::ext_on(
                Promise::new(env::current_account_id())
                    // 0. In case a receipt fails, re-direct the refund to the same
                    // account which was specified as `refund_to` for current receipt.
                    .refund_to(env::refund_to_account_id())
                    // 1. Transfer attached deposit to ourselves, so that it doesn't
                    // affect our balance while in-flight. We could have attached
                    // it to `gd_post_deploy()` below, but this balance is needed
                    // for `deploy_global_contract_by_account_id` to succeed, so
                    // we add a separate transfer action before.
                    .transfer(env::attached_deposit())
                    // 2. Deploy the global contract by our account_id
                    .deploy_global_contract_by_account_id(code),
            )
            .with_static_gas(Self::GD_POST_DEPLOY_MIN_GAS)
            .with_unused_gas_weight(1)
            // 3. Call post-deploy callback **in the same receipt**
            .gd_post_deploy(code_hash.into(), initial_balance, env::attached_deposit()))
        }

```rust
        fn post_deploy(
            &mut self,
            code_hash: [u8; 32],
            initial_balance: NearToken,
            deploy_deposit: NearToken,
        ) -> Result<()> {
            // check that approved hash hasn't changed while in-flight
            if !self.is_approved(&code_hash) {
                return Err(Error::InvalidCodeHash);
            }

            self.0.code_hash = code_hash;
            GdEvent::Deploy { code_hash }.emit();

            // remove just-used approval
            self.approve(State::DEFAULT_HASH, ApprovalReason::Deploy(code_hash));

            let refund = env::account_balance()
                .saturating_sub(initial_balance)
                .min(deploy_deposit);
            if !refund.is_zero() {
                // refund the rest to `refund_to` forwarded here by `gd_deploy()`
                Promise::new(env::refund_to_account_id())
                    .transfer(refund)
                    .detach();
            }

            Ok(())
        }
```
