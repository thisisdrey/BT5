### Title
Unvalidated `Remote` field in `FindRemoteRepository` allows arbitrary Git transport-helper invocation (`ext::`/`fd::`) leading to command execution / SSRF - (File: `internal/gitaly/service/remote/find_remote_repository.go`)

### Summary
`FindRemoteRepository` passes the client-supplied `Remote` string directly as a positional argument to `git-ls-remote(1)` with only an empty-string check. Git itself interprets certain URL schemes (`ext::`, `fd::`, and various `-o`-style SSH options embedded in URLs) as instructions to invoke helper processes. Because Gitaly performs no scheme/format validation on this field before executing `git ls-remote <remote> HEAD`, it is functionally equivalent to the Synapse bridge's unchecked `callData`: an attacker-controlled parameter is forwarded, unvalidated, into a low-level execution primitive that can be repurposed to do something entirely different (and dangerous) than the intended "check whether a remote exists" operation.

### Finding Description
`FindRemoteRepository` only checks that `req.GetRemote()` is non-empty: [1](#0-0) 

It then builds and runs the command via the `gitcmd.Command` API: [2](#0-1) 

The `Args` field of `gitcmd.Command` is documented as unsafe for directly user-controlled values precisely because Gitaly's own argument-validation layer only rejects values that *start with a dash* — it does not validate URL schemes or otherwise vet the content of the string: [3](#0-2) [4](#0-3) 

Git's own remote-URL parser (independent of Gitaly's validation) supports non-network "transport helpers" invoked via `<scheme>::<command>` syntax. `ext::` in particular spawns an arbitrary shell command as the "remote", e.g. `ext::sh -c "id > /tmp/pwn"`, and `fd::` / local-path remotes can be abused to read arbitrary file descriptors or local paths on the Gitaly host. None of `commandDescriptions["ls-remote"]`, `validatePositionalArg`, or the `Command.Args` validation path perform any check that would reject such values (they only reject leading `-`).

This mirrors the Synapse bridge finding conceptually: a parameter meant to encode one narrow kind of "target" (a bridge/transport destination) is passed unfiltered into a generic low-level execution primitive (`call(bytes)` in Solidity / `git-ls-remote(1)` with an unchecked remote string in Gitaly), letting the caller redirect the primitive to perform unrelated, unintended, and dangerous behavior.

### Impact Explanation
A caller able to invoke the `FindRemoteRepository` RPC (this is not a privileged-only RPC — it is reachable by any authenticated Gitaly client, the same trust tier as ordinary repository RPCs) can supply a `Remote` value such as `ext::<command>` to cause the Gitaly server to execute arbitrary commands as the Gitaly process user, or supply crafted URLs to make the server issue requests to internal/attacker-controlled endpoints (SSRF), or read arbitrary local paths via `file://` or bare local-path remotes. This is a full server compromise / SSRF vector, not merely incorrect data as in the original finding — the underlying mechanism (unchecked "target" parameter forwarded into a powerful generic execution primitive) is the same class of bug.

### Likelihood Explanation
Likelihood is high for any environment where `FindRemoteRepository` is reachable to a party that can influence the `Remote` field (e.g., through GitLab features that let users specify a remote/mirror URL, or a compromised/malicious upstream service calling Gitaly directly). No special privilege beyond normal RPC access is required, and no race condition or timing dependency is involved — a single crafted RPC call triggers the behavior.

### Recommendation
- Validate the `Remote` field against an allowlist of safe schemes (e.g., `http://`, `https://`, `git://`, `ssh://`) and reject any value containing `::` transport-helper syntax, `ext::`, `fd::`, or values that don't parse as a well-formed URL.
- Alternatively/additionally, invoke `git-ls-remote(1)` with `-c protocol.ext.allow=never -c protocol.fd.allow=never -c protocol.file.allow=never` (or the global equivalent) so that dangerous transport helpers are disabled at the Git level regardless of application-level validation.
- Apply the same scheme validation everywhere else `Remote`/remote-URL strings are accepted and forwarded to Git subprocesses (e.g. `FetchRemote`), since `fetch_remote.go` follows the same "forward user-supplied remote string to Git" pattern.
- Route such values through `PostSepArgs` only after strict validation, consistent with the existing code comment in `internal/git/gitcmd/command.go` warning that `Args` is unsafe for arbitrary user-controlled input.

### Proof of Concept
1. As any client authorized to call the Gitaly `RemoteService`, send:
   ```
   FindRemoteRepositoryRequest{ remote: "ext::sh -c \"id > /tmp/pwned\"" }
   ```
2. Gitaly executes:
   ```
   git ls-remote 'ext::sh -c "id > /tmp/pwned"' HEAD
   ```
3. Git's `ext::` transport helper spawns `sh -c "id > /tmp/pwned"` on the Gitaly host, demonstrating arbitrary command execution originating from an unvalidated RPC field forwarded into `git-ls-remote(1)`.

(Note: I could not find, within the indexed codebase, any global Gitaly-level `protocol.*.allow` configuration that would already block `ext::`/`fd::` transports for `git-ls-remote(1)` invocations — if such a global mitigation exists elsewhere in configuration not covered by the index, it should be confirmed via a full repository checkout.)

```go
func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
```
