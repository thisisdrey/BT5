## Analysis: `ValidateMultiSign` precompile signature has no domain/replay binding

The reported bug is a **missing domain separation** flaw: a signature meant to authorize a single, specific consumer contract can be replayed against a *different* consumer contract because the signed payload does not bind the signature to the verifying contract's identity. Java-tron ships a TVM precompile with the exact same structural weakness: `ValidateMultiSign` (`0x...0a`).

### Title
Signature verification in the `ValidateMultiSign` precompiled contract lacks domain separation, enabling cross-contract signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x...0a`) computes the digest that off-chain signers sign as `sha256(address || permissionId || data)`, where `address`/`permissionId`/`data` are all attacker-supplied ABI parameters from the calling smart contract. [1](#0-0)  The digest contains no binding to the calling (verifying) contract's address, no chain identifier, and no built-in nonce — exactly the class of missing "domain separator" the external report flags in `CrosschainMerkleDistributor.claimBySignature()`.

### Finding Description
`ValidateMultiSign.execute()` parses `address`, `permissionId`, and `data` straight from calldata, builds `combine = address || permissionId || data`, hashes it, and recovers signer addresses over that hash to check them against the on-chain `Permission` for `address`: [2](#0-1) 

```java
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

The precompile itself performs no differentiation between *which contract* is invoking it, nor does it enforce uniqueness/expiry of `data`. Any responsibility for anti-replay (nonce, expiry, calling-contract identity) is entirely delegated to the calling smart contract's choice of `data` payload — mirroring the exact root cause in the report: `_signed = keccak256(abi.encodePacked(_recipient, _recipientDomain, _beneficiary, _beneficiaryDomain, _total))` never included the verifying contract's address either. [3](#0-2) 

Test fixtures confirm the exact signing scheme dApp developers are expected to replicate off-chain: `merged = address || permissionId || data`, `toSign = sha256(merged)`. [4](#0-3)  Nothing in this scheme differentiates "this signature authorizes action X in Contract A" from "this signature authorizes the semantically identical `data` in Contract B" for the same multisig `address`/`permissionId`. If two independently deployed smart contracts (analogous to `CrosschainContinuousVestingMerkle` / `CrosschainTrancheVestingMerkle` in the report) both call `ValidateMultiSign` for the same shared custody/multisig account and happen to use overlapping `data` encodings (e.g., both encode `(recipient, amount)` the same way without embedding their own contract address or a nonce), a signature collected for one contract's authorization flow will validate identically in the other, permitting replay.

### Impact Explanation
Because signature-based authorization is a common pattern for TRON smart contracts (bridges, custodial vaults, withdrawal-approval systems) built on top of `ValidateMultiSign`, any dApp author who does not manually embed their own contract address/chain-id/nonce into `data` inherits a cross-contract (or cross-deployment/cross-upgrade) replay vulnerability at the protocol-precompile level. This can lead to double-authorization of a privileged action — e.g., duplicate approval of a withdrawal or state change guarded by the same multisig account — resulting in unauthorized account operations or theft of funds when the same multisig identity backs more than one consumer contract.

### Likelihood Explanation
Exploitation requires no privileged access: any contract deployer (a normal, unprivileged actor) can build and deploy a contract that calls `ValidateMultiSign` for a shared multisig account, and any transaction broadcaster can supply the replayed signature/data pair as calldata. The precompile is directly reachable via a `CALL`/`STATICCALL` from any smart contract, gated only by `VMConfig.allowTvmSolidity059()`. [5](#0-4)  Realized impact depends on a downstream dApp reusing the identical `(address, permissionId, data)` domain across two consumer contracts, which is a realistic and previously-seen pattern for off-chain-signed multisig authorization flows in the TRON ecosystem.

### Recommendation
Document and/or enforce that callers must include a verifying-contract identifier and/or a per-use nonce/expiry inside `data` before this precompile is used for financial authorization. Consider extending `ValidateMultiSign`'s digest computation to also absorb `msg.sender` (the calling contract address) automatically, similar to EIP-712's `verifyingContract` domain field, so that a signature produced for one contract can never validate for another contract even if `data` collides.

### Proof of Concept
1. Deploy `ContractA`, which calls `ValidateMultiSign(sharedMultisigAddr, permissionId, data)` to authorize a withdrawal, where `data = abi.encode(recipient, amount)`.
2. Deploy `ContractB`, an independent dApp sharing the same `sharedMultisigAddr`/`permissionId`, that also calls `ValidateMultiSign` with the same `data` encoding for a different purpose (e.g., approving a different withdrawal of the same `recipient`/`amount`).
3. Off-chain signers produce one signature set over `sha256(sharedMultisigAddr || permissionId || data)` intending to authorize the action in `ContractA` only.
4. An attacker submits the same `signatures`/`data` to `ContractB`; `ValidateMultiSign` returns `true` because the digest is identical, letting the attacker trigger `ContractB`'s privileged action without new authorization — reproducing the double-claim/double-authorization pattern from the original report.
