Audit Report

## Title
Redeem path skips live-decimals validation, allowing stale scaling factor to mis-price external-asset payouts - (File: `substrate/frame/psm/src/lib.rs`)

## Summary
`pallet-psm`'s `mint` re-validates the external and internal asset decimals against live `T::Fungibles::decimals(..)` metadata via `Self::ensure_decimals_match(...)` before performing any conversion, erroring with `DecimalsMismatch` on drift [1](#0-0) . `redeem`, by contrast, reads `ext_decimals`/`internal_decimals` straight from the stored `ExternalAssetInfo`/`PsmInfo` registration snapshot and never calls this check before computing `external_out` [2](#0-1) . This asymmetry is real and reproducible from the code, but the pallet's own doc comment discloses it as an intentional design decision rather than an oversight.

## Finding Description
The `redeem` extrinsic's doc comment explicitly states: *"Redemptions use the decimals snapshotted when the PSM/external pair was registered, allowing existing positions to unwind even if live metadata later changes."* [3](#0-2)  This is a deliberate design trade-off documented directly above the `redeem` function, not a silent gap discovered only by code inspection — the pallet authors consciously chose to let `redeem` keep operating on the registration-time snapshot so that users with existing debt positions can still exit even after live decimals metadata for an external asset diverges (e.g., is halted for new `mint`s via `DecimalsMismatch`).

The `mint`/`redeem` doc-string in `prdoc/stable2606/pr_11819.prdoc` states "mint/redeem return DecimalsMismatch if live metadata diverges from the registration snapshot" [4](#0-3) , which does not match the actual `redeem` implementation — this is a documentation/prdoc inaccuracy, not evidence that the code is broken relative to its own in-source contract. The in-source rustdoc directly above `redeem` (which takes precedence as the authoritative description of intended behavior for that function) explicitly documents the snapshot-based, no-live-check behavior as intended.

Whether this asymmetry constitutes an *exploitable* vulnerability hinges on whether asset decimals metadata drift is a normal/expected occurrence that the pallet must defend against on the withdrawal side, or whether it is treated by design as an out-of-band event that only gates new mints while existing debt is intentionally allowed to unwind at the historical rate. Given the pallet's own documentation frames this precisely as intentional dust/positions-unwinding behavior (paralleling the "symmetric" rounding behavior also described in the same docstring and the prdoc's mention of round-trip rounding), the omission of a live-decimals check in `redeem` cannot be characterized as an unintended runtime bug distinct from a disclosed design choice.

## Impact Explanation
No override — the reported mechanism (mis-scaled payout via stale `10^diff` factor) is real, but it operates exactly as the pallet's own documentation says it should: `redeem` intentionally continues to honor the registration-time snapshot so pre-existing debt can be unwound, independent of live-metadata changes that gate new `mint`s. This does not meet the bar of "runtime bug that compromises intended behavior" under the Polkadot SDK impact gate, because the behavior in question is the intended behavior as documented in-source.

## Likelihood Explanation
N/A — rejected on design-intent grounds, not likelihood.

## Recommendation
N/A (informational only, no vulnerability confirmed against documented design intent). If the disclosed intentional behavior is not actually the desired security posture (e.g., if governance truly wants `redeem` to halt on drift, matching the prdoc text), that is a documentation/behavior consistency issue for the pallet maintainers to reconcile, not an externally exploitable security vulnerability under the stated program scope.

## Proof of Concept
N/A — no PoC required since the behavior matches the pallet's documented intent for `redeem` (in-source rustdoc at `substrate/frame/psm/src/lib.rs` lines 781-783).
