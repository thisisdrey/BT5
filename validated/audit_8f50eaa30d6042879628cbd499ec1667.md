# `TrailingOption<T>` Greedily Trusts Unbound Trailing Bytes as Extension Data — Analog to `bps()` Calldata-Injection Bug (File: `polkadot/parachain/src/primitives.rs`)

### Summary
The Sherlock `bps()` bug is fundamentally about a decoder that blindly reads bytes located at a fixed offset relative to the *end* of an untrusted buffer and treats them as a semantically meaningful, security-relevant value (a token address), without any binding to what was actually validated/expected for that call. The polkadot-sdk codebase contains a structurally identical primitive: `TrailingOption<T>` in `polkadot/parachain/src/primitives.rs`, which greedily consumes *all* remaining bytes of a SCALE-encoded buffer and decodes them as `T` (`ValidationParamsExtension`, carrying `relay_parent` / `scheduling_parent` for async-backing V3 candidates) with **no length prefix, no discriminant, and no commitment binding** the trailing bytes to the field they are supposed to represent. [1](#0-0) 

### Finding Description
`TrailingOption<T>::decode` does not check for a `0x00`/`0x01` discriminant like a normal SCALE `Option<T>`. Instead, it inspects `input.remaining_len()`: if any bytes remain, *all* of them are handed to `T::decode`, no matter what those bytes are or where they came from. [2](#0-1) 

The type's own doc comment explicitly documents the exact attacker primitive from the external report — that trailing/injected bytes can be misattributed to a value the decoder was never meant to receive:

> "`TrailingOption` greedily consumes ALL remaining bytes and attempts to decode them as `T`. If your struct is embedded in a larger message, or if you add fields after it, `TrailingOption` will incorrectly steal bytes belonging to those fields." [3](#0-2) 

This is precisely the `bps()` bug class: a value (`ValidationParamsExtension` → `relay_parent`/`scheduling_parent`) is derived from *positional trailing bytes* of a buffer rather than from a value cryptographically bound to (or length-delimited within) the message that was actually verified. The type is used in at least three locations — `polkadot/parachain/src/primitives.rs`, `polkadot/node/core/pvf/execute-worker/src/lib.rs` (9 references), and `cumulus/pallets/parachain-system/src/validate_block/mod.rs` — meaning the "safe usage" invariant ("`ValidationParams` is encoded as a complete standalone message ... PVF receives this as the entire input, no wrapper struct") is an unenforced, purely documentary assumption rather than a type-level guarantee. Nothing in the `Decode` impl, nor in the type signature, prevents a future change (e.g., a new field added after the extension, or embedding `ValidationParams` inside a larger enum/tuple during message construction) from silently causing the `relay_parent`/`scheduling_parent` fields used for async-backing relay-parent validation to be populated from unrelated trailing bytes instead of the intended extension payload — exactly the "computations done on two different, unchecked values" failure mode flagged in the Sherlock report.

### Impact Explanation
`relay_parent` / `scheduling_parent` decoded via this path feed into async-backing execution semantics for V3 parachain candidates. If the byte-boundary assumption is ever violated (a realistic risk given it is enforced only by a code comment, not by the type system, and the pattern is already reused in `execute-worker` and `validate_block`), the PVF/runtime would silently execute validation logic against a relay_parent/scheduling_parent value that does not correspond to any value actually verified against the candidate descriptor or PoV, i.e., "runtime bugs that compromise intended behavior" for validity determination — falling squarely within the in-scope impact category of forged/mis-bound state acceptance in proof/candidate verification.

### Likelihood Explanation
Today's exploitability is uncertain: I could not fully trace, within tool-call limits, how `execute-worker` and `validate_block` currently size/frame the buffer passed to `TrailingOption`, so I cannot confirm a currently-exploitable boundary violation exists in the present call sites — this is an area requiring further code reading. What is concretely established is that (a) the decoder itself has no defense against the exact class of attack described in the report, (b) the maintainers' own comment acknowledges the danger and lists specific ways it can be triggered by legitimate-looking future changes, and (c) the primitive is already reused beyond its originally-safe single call site. This makes it a real, code-evidenced structural weakness rather than a purely theoretical one, but full confirmation of a live, exploitable path requires reviewing the exact call sites in `execute-worker`/`validate_block` for whether any field currently follows/wraps the extension bytes.

### Recommendation
Replace the greedy "consume-everything-remaining" decode strategy with an explicit length-prefixed or discriminant-based encoding for `ValidationParamsExtension`, so its boundary is self-describing and cannot be corrupted by any future field additions or embedding in larger messages — removing the "assume this is always the last field of a top-level message" invariant currently enforced only by documentation.

### Proof of Concept

/// A wrapper that decodes `T` if bytes remain after prior fields, or returns
/// `None` if at EOF. Unlike `Option<T>`, this does NOT expect a 0x00/0x01
/// discriminant byte - it simply checks whether there is remaining input.
///
/// This is used to guarantee no breakage for existing chains with v1/v2
/// descriptors. For v1/v2, no extension bytes are sent at all, and
/// TrailingOption gracefully returns None instead of failing to decode.
///
/// # ⚠️ DANGER - Do Not Use This as a General-Purpose Utility! ⚠️
///
/// **CRITICAL ASSUMPTIONS:**
/// - The type containing `TrailingOption<T>` MUST be the final/top-level struct being decoded
/// - There MUST NOT be any fields after the `TrailingOption<T>` field
/// - There MUST NOT be any legitimate trailing data except `T`
///
/// **Why this is dangerous:**
/// `TrailingOption` greedily consumes ALL remaining bytes and attempts to decode them as `T`.
/// If your struct is embedded in a larger message, or if you add fields after it,
/// `TrailingOption` will incorrectly steal bytes belonging to those fields.
///
/// **Current safe usage:**
/// - `ValidationParams` is encoded as a complete standalone message
/// - `ValidationParamsExtension` is manually appended as trailing bytes
/// - The PVF receives this as the entire input (no wrapper struct)
///
/// If you're considering using this elsewhere, you probably want `Option<T>` instead.
#[derive(Clone)]
#[cfg_attr(feature = "std", derive(Debug))]
pub struct TrailingOption<T>(pub Option<T>);

impl<T: Decode> Decode for TrailingOption<T> {
	fn decode<I: codec::Input>(input: &mut I) -> Result<Self, codec::Error> {
		// Check if input is exhausted - return None instead of failing
		if input.remaining_len()? == Some(0) {
			return Ok(TrailingOption(None));
		}
		// Bytes remain - decode T (the ValidationParamsExtension enum)
		Ok(TrailingOption(Some(T::decode(input)?)))
	}
}
