## Title
`WalletContract` `has_in_flight_tx` lock can be stuck permanently true due to atomic receipt rollback on refund/callback failure - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The near-implicit eth wallet contract uses a boolean flag `has_in_flight_tx` as a re-entrancy lock: it is set to `true` before dispatching a cross-contract promise chain and is supposed to be reset to `false` at the start of every callback. This mirrors the reported DFINITY bug class exactly: a lock is taken before an async multi-hop call, and the code assumes the unlock write will always persist. In nearcore, receipt execution is atomic — if *anything* in the callback receipt fails after the "unlock" instruction has run in WASM, the entire state change (including the flag reset) is rolled back, leaving the lock permanently `true` and the wallet forever unable to process any future `rlp_execute` transaction.

### Finding Description
`WalletContract::rlp_execute` refuses to start a new Ethereum-emulated transaction whenever `has_in_flight_tx` is `true`, and sets it to `true` right before returning a `Promise` chain: [1](#0-0) 

Every callback in the chain (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) resets the flag as its very first statement: [2](#0-1) [3](#0-2) 

Crucially, `rlp_execute_callback`'s failure branch unconditionally attempts to refund the *original* `caller_deposit.yocto_near` amount out of the contract's own current NEAR balance: [4](#0-3) 

But in the ERC-20 emulation path, the contract first spends part of its *own* balance on `storage_deposit` (a fixed `NEP_141_STORAGE_DEPOSIT_AMOUNT`) before chaining to `ft_transfer` and finally to `rlp_execute_callback`: [5](#0-4) 

If the wallet's remaining balance at refund time is smaller than the deposit it must refund (e.g., because `storage_deposit`'s `NEP_141_STORAGE_DEPOSIT_AMOUNT` was already deducted from the account balance, or any other balance movement occurred earlier in the chain), the `env::promise_batch_action_transfer` refund call fails with `BalanceExceeded`, which aborts the whole `rlp_execute_callback` FunctionCall action with an `ActionError`.

Per the runtime's execution model, a failed receipt is rolled back atomically — *all* state changes made during that receipt's execution are discarded, not just the ones related to the failure: [6](#0-5) [7](#0-6) 

This means the `self.has_in_flight_tx = false;` write executed at the top of `rlp_execute_callback` (line 280) is *also* rolled back along with everything else in that failed receipt, exactly like the DFINITY bug where a lock taken before an async hop survives a later panic because the intervening state was already persisted/committed to the wrong point. Once this happens, `rlp_execute` will forever short-circuit with "transaction already in progress" (line 97-105), because there is no other externally-callable method that clears `has_in_flight_tx`.

### Impact Explanation
This permanently freezes the affected eth-implicit wallet account: it can never again execute any `rlp_execute` (Ethereum-emulated) transaction, i.e., it can never move funds or interact with contracts through this wallet contract mechanism again. Since eth-implicit accounts are meant to be operated exclusively through `rlp_execute`, this is a permanent freezing-of-funds condition for that account, matching the accepted impact categories.

### Likelihood Explanation
The relayer/refund gas-subsidy flow is a normal, documented part of the design (`CallerDeposit`, `test_caller_refunds` test at `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:170-229` already demonstrates the refund path is reachable in ordinary operation). Triggering the underflow condition requires only that the wallet's own liquid balance at refund time be less than the deposit that must be refunded — a state reachable through ordinary use of the ERC-20 relayer-subsidized flow (e.g., low wallet balance plus the mandatory `storage_deposit` spend). No privileged or malicious-node capability is required; a normal relayer/caller combination is sufficient.

### Recommendation
- Reset `has_in_flight_tx = false` unconditionally and durably regardless of later failures in the same receipt — e.g., perform the flag reset as a separate, always-succeeding receipt/action (such as via a dedicated cheap self-callback that cannot fail), or restructure refund logic so a failed refund transfer cannot abort the whole callback (catch/`Promise` failures instead of relying on the transfer succeeding synchronously).
- Ensure the refund amount can never exceed the contract's spendable balance by reserving/tracking the caller's deposit separately from funds the contract spends on its own operations (e.g., `storage_deposit`), so a shortfall is detected and handled gracefully (partial refund or explicit error) instead of causing the whole action/receipt to fail.
- Add a recovery mechanism (e.g., an owner-only or time-locked "force unlock" method) so that if `has_in_flight_tx` ever gets stuck, the account is not permanently unusable.

### Proof of Concept
1. Deploy an eth-implicit `WalletContract` with a small NEAR balance beyond storage requirements.
2. Have an external relayer call `rlp_execute` with a validly signed ERC20Transfer Ethereum transaction, attaching a deposit (`caller_deposit`) close to the wallet's total spendable balance, targeting a token that requires `storage_deposit` for the receiver.
3. The chain proceeds: `nep_141_storage_balance_callback`'s `None` branch spends `NEP_141_STORAGE_DEPOSIT_AMOUNT` from the wallet's own balance (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:255-268`), then chains to `ft_transfer` and finally `rlp_execute_callback`.
4. Have the `ft_transfer` promise fail (e.g., invalid/unregistered receiver at the token level after storage_deposit consumed funds), landing in `rlp_execute_callback`'s `PromiseResult::Failed` branch, which attempts to refund the full original `caller_deposit.yocto_near` (`lib.rs:296-311`).
5. Because the wallet's remaining balance is now less than `caller_deposit.yocto_near` (having spent `NEP_141_STORAGE_DEPOSIT_AMOUNT` earlier), `promise_batch_action_transfer` fails with `BalanceExceeded`, aborting the whole `rlp_execute_callback` receipt.
6. The receipt is rolled back per NEAR's atomic-receipt-execution model, discarding the `has_in_flight_tx = false` write executed at the top of `rlp_execute_callback`.
7. Any subsequent call to `rlp_execute` on this account now permanently returns "Error: transaction already in progress, please try again later." — the account is frozen indefinitely.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
