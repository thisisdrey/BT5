## Analysis

The Minio advisory concerns unsanitized Unicode RIGHT-TO-LEFT OVERRIDE (U+202E) characters in user-supplied names being echoed back to a UI, allowing an attacker to visually mask the true content (e.g., make a malicious `.exe` display as `.txt`). The closest reachable analog in java-tron is in the on-chain metadata fields that any account can set via a broadcastable transaction and that are later served back verbatim by public read APIs (`Wallet`, HTTP/gRPC) to wallets and block explorers.

`TransactionUtil` enforces a strict printable-ASCII filter (`0x21`–`0x7E`) for asset names, token abbreviations, and account IDs via `validReadableBytes`, but the asset **description**, asset **url**, and account **name** fields only go through `validBytes`, which checks *length* only and imposes no character-set restriction: [1](#0-0) 

`AssetIssueActuator.validate()` calls `validUrl`/`validAssetDescription` (length-only) for the `url`/`description` fields of `AssetIssueContract`, while calling the strict `validAssetName` for `name`/`abbr`: [2](#0-1) 

Similarly, `UpdateAccountActuator.validate()` only calls `TransactionUtil.validAccountName`, which is length-only (up to 200 bytes, no character filtering), for the `account_name` field of `AccountUpdateContract`: [3](#0-2) 

Because these fields accept arbitrary UTF-8 byte sequences, an attacker can embed U+202E (RTLO) or other Unicode bidi-control characters in a token's `url`/`description` or in an account's `name`. These fields are stored unmodified in `AssetIssueCapsule`/`AccountCapsule` and returned as-is through the public read paths (`Wallet.getAssetIssueList`, `Wallet.getAccount`, and the corresponding HTTP/gRPC/JSON-RPC servlets) to any anonymous client, exactly mirroring the Minio scenario of a name/URL being redisplayed without sanitization.

### Title
Unsanitized RIGHT-TO-LEFT OVERRIDE / bidi Unicode characters permitted in AssetIssue `url`/`description` and Account `name` fields enable display spoofing - (File: `actuator/src/main/java/org/tron/core/utils/TransactionUtil.java`)

### Summary
`TransactionUtil.validUrl`, `validAssetDescription`, and `validAccountName` only enforce a maximum byte length (`validBytes`) and do not restrict the character set, unlike `validAssetName`/`validAccountId` which require printable ASCII via `validReadableBytes`. This allows any transaction broadcaster to embed Unicode RIGHT-TO-LEFT OVERRIDE (U+202E) or other bidirectional-control characters into an `AssetIssueContract.url`/`description` or an `AccountUpdateContract.account_name`, which is then stored on-chain and echoed verbatim by public query APIs.

### Finding Description
`AssetIssueActuator.validate()` validates `url` and `description` with the length-only checks `TransactionUtil.validUrl` / `validAssetDescription`, and `UpdateAccountActuator.validate()` validates `account_name` with the length-only `TransactionUtil.validAccountName`. None of these call `validReadableBytes`, so multi-byte UTF-8 sequences representing bidi-control code points (which fall entirely outside the `0x21`–`0x7E` printable range enforced elsewhere) pass validation unaltered. The values are persisted in the `AssetIssueStore`/`AccountStore` and later returned unmodified by `Wallet` query methods and the corresponding HTTP/gRPC/JSON-RPC endpoints, which any anonymous client can call. A wallet UI, exchange listing page, or block explorer rendering these strings will display attacker-controlled reordered/masked text, e.g. making a malicious URL visually resemble a trusted domain or making a spoofed account name appear identical to a legitimate one.

### Impact Explanation
This is a display-spoofing / information-exposure issue (CWE-200 analog), reachable by any unprivileged asset issuer (`AssetIssueContract`) or account owner (`AccountUpdateContract`). It can be leveraged for phishing: a token's URL field can be crafted so that clients see a fabricated, trustworthy-looking domain while the actual bytes point elsewhere, or an account name can be visually spoofed to impersonate another account/exchange, aiding social-engineering attacks that could lead users to send funds to the wrong destination or visit malicious sites.

### Likelihood Explanation
Likelihood is high for triggering the display anomaly — it only requires issuing an asset (`AssetIssueContract`) or updating an account name (`AccountUpdateContract`), both ordinary, low-cost operations available to any funded account. The exploitation depends on downstream consumers (wallets/explorers) rendering these strings without their own sanitization, which mirrors exactly the precondition in the original Minio console report.

### Recommendation
Apply the same printable-ASCII/readable-byte validation (or an explicit Unicode bidi-control-character blacklist covering U+202A–U+202E, U+2066–U+2069, etc.) to `TransactionUtil.validUrl`, `validAssetDescription`, and `validAccountName`, consistent with the stricter `validReadableBytes` already used for `validAssetName`/`validAccountId`.

### Proof of Concept
1. Broadcast an `AssetIssueContract` with `url` set to bytes containing `U+202E` (e.g., `https://good-domain.com/\u202Egnp.exe`), which passes `AssetIssueActuator.validate()` because `validUrl` only checks length.
2. Query the asset via a public `GetAssetIssueList`/`GetAssetIssueByAccount` API call; the returned `url` bytes contain the unmodified RTLO sequence, causing render-order reversal in any UI that doesn't strip bidi controls, masking the true URL destination.
3. Equivalently, broadcast an `AccountUpdateContract` with `account_name` containing `U+202E` via `UpdateAccountActuator`, then query the account with `Wallet.getAccount`/HTTP `getaccount`; the spoofed name is returned as-is.

  private static boolean validBytes(byte[] bytes, int maxLength, boolean allowEmpty) {
    if (ArrayUtils.isEmpty(bytes)) {
      return allowEmpty;
    }
    return bytes.length <= maxLength;
  }

  private static boolean validReadableBytes(byte[] bytes, int maxLength) {
    if (ArrayUtils.isEmpty(bytes) || bytes.length > maxLength) {
      return false;
    }
    // b must be readable
    for (byte b : bytes) {
      if (b < 0x21) {
        return false; // 0x21 = '!'
      }
      if (b > 0x7E) {
        return false; // 0x7E = '~'
      }
    }
    return true;
  }
