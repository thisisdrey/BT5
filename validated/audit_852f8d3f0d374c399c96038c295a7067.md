### Title
Unbounded blocking read on signer's HTTP event port allows a single slow-drip connection to hang the event receiver forever - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver` binds a `tiny_http::HttpServer` and its single-threaded `main_loop` blocks on `http_server.recv()` with no read/connection timeout configured anywhere in `bind()`. A remote peer that opens a TCP connection to the signer's event-receiver port and never completes sending a valid HTTP request (or drips bytes slowly, as in the OctoRPKI slowloris advisory) causes `recv()` to block indefinitely, hanging the only thread that processes node events (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`).

### Finding Description
`SignerEventReceiver::bind` creates the server with no timeout: [1](#0-0) 

`main_loop` repeatedly calls `next_event()`, which calls `http_server.recv()` and blocks until a full request is available: [2](#0-1) [3](#0-2) 

There is no `recv_timeout()` usage anywhere in `libsigner`, and no socket-level `set_read_timeout` is applied to sockets accepted by the `tiny_http` server (grep confirms `set_read_timeout`/`recv_timeout` only appear in `libsigner/src/runloop.rs`, used for the stop-signal channel, and `libsigner/src/session.rs`, used for the outbound client session — neither applies to the inbound event-receiver socket). This mirrors exactly the OctoRPKI bug class: an HTTP server that accepts a connection and will "wait forever" if the peer keeps the connection open (with or without a slow trickle of bytes) instead of completing/aborting the request within a bounded time.

Because `main_loop` is single-threaded and sequential (`next_event()` → `forward_event()` → loop), a connection that hangs `recv()` blocks the entire signer event pipeline: no further `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` POSTs from the real Stacks node can be processed until the hung connection is closed (only reachable via the `/shutdown` stop signal, which itself must be delivered over the same blocked accept path).

### Impact Explanation
This is a bounded-compute DoS on a read endpoint: a single idle/slow-drip TCP connection (no volumetric traffic required) can stall a signer's event ingestion indefinitely, preventing it from receiving block proposals and burn-block/StackerDB chunk notifications from its node. For a signer, this can translate into missed signing rounds / proposal responses, degrading its participation in consensus signing until the connection is externally terminated (e.g., OS-level TCP timeout, which for a "keep the socket open but drip data" attacker can be avoided entirely).

### Likelihood Explanation
Reaching this requires only that the attacker can open a TCP connection to the signer's configured event-receiver bind address. The signer's own documentation/warning acknowledges it may be exposed beyond localhost in some deployments ("It's important to exercise caution if you are communicating with an external node... this could potentially expose sensitive data or functionalities to security risks"), and no authentication is performed before `http_server.recv()` blocks on the connection. No prior handshake, key, or privileged role is needed — exactly the "few messages / single connection" unauthenticated DoS class.

### Recommendation
Configure a bounded per-connection timeout on the tiny_http server (tiny_http supports `Server::recv_timeout(Duration)` instead of unbounded `recv()`), or set an accept-side read/write timeout, and treat elapsed timeouts as a recoverable error that lets `main_loop` continue polling `is_stopped()` and cycling to the next connection rather than blocking on one peer forever. Ensure the timeout value is bounded well below any external liveness expectations for the signer.

### Proof of Concept
1. Start a signer whose event-receiver bind address is reachable by a network peer (per the code's own external-exposure caveat).
2. From that peer, `TcpStream::connect` to the bind address and either send nothing, or send bytes at a rate below tiny_http's internal buffering needs (e.g., one byte every few seconds), never completing a valid HTTP request/body.
3. Observe that `SignerEventReceiver::next_event` (and therefore `main_loop`) never returns, and legitimate POSTs from the real Stacks node to `/stackerdb_chunks`, `/new_block`, etc. are no longer processed because the single-threaded receive loop is blocked in `http_server.recv()`.

    /// Main loop for the receiver.
    /// Typically, this is started in a separate thread.
    fn main_loop(&mut self) {
        loop {
            if self.is_stopped() {
                info!("Event receiver stopped");
                break;
            }
            let next_event = match self.next_event() {
                Ok(event) => event,
                Err(EventError::UnrecognizedEvent(..)) => {
                    // got an event that we don't care about (not a problem)
                    continue;
                }
                Err(EventError::Terminated) => {
                    // we're done
                    info!("Caught termination signal");
                    break;
                }
                Err(e) => {
                    warn!("Failed to receive next event: {:?}", &e);
                    continue;
                }
            };
            if !self.forward_event(next_event) {
                info!("Failed to forward event");
                break;
            }
        }
        info!("Event receiver main loop exit");
    }
