### Title
Unbounded git-rev-list history walk when an attacker-supplied ListCommits pagination token never matches a real commit - ([File: internal/gitaly/service/commit/list_commits.go])

### Summary
`ListCommits` skips the `--max-count` optimization on `git-rev-list(1)` whenever a pagination `PageToken` is present, trusting that the token corresponds to a real commit close to the requested walk. If the caller supplies an arbitrary/garbage token (a client-controlled RPC field, not a value that is cryptographically bound to the repository state), the in-process skip filter never flips to "seen," and the full, unbounded history of the revision range is walked and streamed through `git-rev-list` → `git-cat-file` batch processing on every single request, with no cap.

### Finding Description
`ListCommits` builds `revlistOptions` for `gitpipe.Revlist` and, when `request.GetPaginationParams().GetPageToken()` is non-empty, adds a `WithSkipRevlistResult` callback that skips every revision result until an OID equal to the decoded token is observed: [1](#0-0) 

The code then explicitly disables the `--max-count` capping optimization specifically because a page token is present, with the max-count logic supposed to be "factored in while commits are being skipped": [2](#0-1) 

The `decodeListCommitsPageToken` function accepts either a JSON-encoded structure or falls back to treating any arbitrary string as a raw legacy commit SHA — there is no validation that the decoded value is an actual object in the repository or reachable from the requested revisions: [3](#0-2) 

Inside `gitpipe.Revlist`, when `cfg.maxCount == 0` (which is what happens whenever a token is supplied), no `--max-count` flag is passed to `git-rev-list(1)` at all, so the full range is walked and every object name is streamed to the caller for skip-filtering in Go: [4](#0-3) 

Each surviving (non-skipped) revision result is then piped into `CatfileObject`, which spawns `git-cat-file --batch` and fully reads/parses the commit object: [5](#0-4) 

Because `WithSkipRevlistResult`'s callback returns `true` for every result until `tokenSeen`, and `tokenSeen` becomes `true` only via an exact OID string match, a token that does not correspond to any commit actually walked by `git-rev-list` (e.g., a valid-looking but non-existent SHA, an OID from an unrelated branch/ref not in the requested revision range, or one that was pruned/never existed) causes the *entire* revision walk to complete without ever finding a match, discarding every result — yet Gitaly still walks and processes the complete history for the given revision(s) before returning an empty result set. This mirrors the reported bug class: the code takes an unbounded/near-full traversal path based on the unvalidated assumption that a caller-supplied "hint" (the previous order's matched state / the page token) narrows or bounds the work, when in fact it does not.

This is directly reachable from an ordinary, unprivileged client: `PaginationParameter.PageToken` is a plain string field on `ListCommitsRequest` fully controlled by the RPC caller, requiring no special privilege beyond read access to the repository.

### Impact Explanation
An unprivileged caller with read access to a repository can force Gitaly to perform an unbounded `git-rev-list` walk plus `git-cat-file` parsing over the entire requested history on every call, simply by supplying a page token that will never match (e.g., a random/garbage or off-branch OID). Repeated calls against a repository with a large history amplify CPU, memory, and I/O usage on the Gitaly node, and because the `--max-count` cap is deliberately skipped in this code path, there is no upper bound on this walk cost tied to the `Limit` the caller requested. This is a resource-exhaustion / DoS vector against a widely used RPC handler.

### Likelihood Explanation
Likelihood is high in terms of reachability (any client that can call `ListCommits` with a `PaginationParameter` can trigger it, and no valid prior page token is required for the request to be accepted), but the severity of impact scales with the size of the repository's history. Small repositories cost little; long-lived repositories with deep/large histories are impacted more severely, and the cost is repeatable per request with no rate/size limiting tied to this specific fallback path.

### Recommendation
- Do not disable the `--max-count` cap purely on the presence of a page token. Instead, always cap `git-rev-list` output (e.g., to `limit + skip-window-bound` or a hard maximum) even when a page token is supplied, and treat "token never found" as a normal empty-page/invalid-token condition rather than an unbounded scan.
- Validate that the decoded page token actually resolves to an object reachable within the requested revision range before starting the walk (e.g., verify existence via `git-cat-file -t` or resolve it as part of the same rev-list invocation using `--ancestry-path`/boundary semantics) rather than relying purely on a linear in-process comparison over an unbounded stream.
- Consider bounding the total number of commits inspected during token-skip mode with a hard ceiling independent of `Limit`, returning an explicit invalid-argument/error once exceeded instead of continuing to scan.

### Proof of Concept
1. Create/use a repository with a large linear or branching history (e.g., tens of thousands of commits).
2. Call `ListCommits` with `Revisions: ["HEAD"]` and `PaginationParams.PageToken` set to a syntactically valid but non-existent commit SHA (40 hex chars not present in the repository), or a real OID that exists in the repo's object database but is not reachable from `HEAD` (so it will never appear in the `git-rev-list HEAD` output).
3. Observe that `ListCommits` still runs `git-rev-list` without `--max-count` (per [6](#0-5) ) and streams every object in the requested revision range through the skip filter, and through `CatfileObject`/`ParseCommit` for objects that pass the filter, before returning an empty commit list — with CPU/time cost proportional to full history size rather than to `Limit`.
4. Repeating this request concurrently amplifies load on the Gitaly node, since the cost of each call is bounded by history size, not by the requested `Limit`.

Note: I was not able to execute this PoC against a live Gitaly instance (no filesystem/terminal access in this session); the analysis is based on static code review of the cited files. A background Devin session with repository/terminal access would be needed to empirically measure the walk cost and confirm the DoS magnitude on a representative large repository.

// decodeListCommitsPageToken decodes a pagination token. It supports both the
// new base64-encoded JSON format and the legacy raw commit SHA format for
// backward compatibility during rolling upgrades.
func decodeListCommitsPageToken(token string) string {
	decodedBytes, err := base64.StdEncoding.DecodeString(token)
	if err != nil {
		// Not valid base64 — treat as a legacy raw commit SHA.
		return token
	}

	var pt listCommitsPageToken
	if err := json.Unmarshal(decodedBytes, &pt); err != nil {
		// Valid base64 but not our JSON struct — treat as legacy.
		return token
	}

	if pt.CommitID == "" {
		// JSON decoded but had no commit_id — treat as legacy.
		return token
	}

	return pt.CommitID
}
