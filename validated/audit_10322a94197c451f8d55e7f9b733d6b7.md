### Title
Unvalidated Negative-Balance Underflow in Default (Non-Hardened) Exchange Trade Calculation - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes new AMM pool reserves for a trade and only validates that the resulting reserves are non-negative when the `hardenedCalc` flag is `true`. That flag is driven by the `AllowHardenExchangeCalculation` dynamic property, which every test in the repo explicitly restores to `0` after use, indicating it is off by default. In the default (legacy) code path, the new reserve values are computed as plain `long` subtraction (`firstTokenBalance - buyTokenQuant` / `secondTokenBalance - buyTokenQuant`) with no post-condition check, so a below-invariant `buyTokenQuant` (over-computed via the legacy floating/BigDecimal `ExchangeProcessor`) can drive a reserve negative without being rejected.

### Finding Description
`ExchangeCapsule.transaction()`: [1](#0-0) 

The invariant check is gated behind `hardenedCalc`: [2](#0-1) 

`ExchangeTransactionActuator` and `ExchangeWithdrawActuator`/`ExchangeInjectActuator` all call `exchangeCapsule.transaction(...)` and then persist the resulting (possibly negative) reserve to the store without any additional sanity check: [3](#0-2) 

The hardened path is exercised only when `AllowHardenExchangeCalculation` is enabled, and tests consistently reset it to `0`, indicating the safe path is opt-in rather than default: [4](#0-3) 

This mirrors the reported bug class conceptually: a subtraction whose result can fall out of the valid domain (negative) is used to update persistent state without a bounds check unless an explicit hardening mode is active — analogous to `wc_XChaCha20Poly1305_Decrypt` computing `cLen - tagLen` without checking `cLen >= tagLen` before using the (potentially underflowed) value.

### Impact Explanation
If the legacy `ExchangeProcessor` (not confirmed to use double/BigDecimal internally in this pass — file could not be located in this exploration, `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java` exists but was not read) can, for any input, return a `buyTokenQuant` that exceeds the actual pool reserve by even 1 unit due to rounding/precision behavior, the resulting negative reserve represents unbacked token supply in the exchange pool: further trades against that pool would compute exchange rates against an invalid (negative) reserve, enabling economic manipulation, or a subsequent withdraw could pay out from a mis-priced pool. This would fall under "unbacked balance" / incorrect accounting.

### Likelihood Explanation
**Not confirmed.** I was unable to read `ExchangeProcessor.java` to verify whether the legacy processor can ever return a quantity that violates the reserve invariant for realistic inputs (the existing tests only show ±1 unit divergence between legacy and hardened results, and don't demonstrate an actual negative-reserve trigger under default settings). Given TRON already ships a "hardened" alternative and extensive regression tests specifically targeting `subtractExact`/negative-balance scenarios, it's plausible this was already identified and mitigated (behind a governance-controlled flag) rather than being a live, exploitable bug today.

### Recommendation
Enforce the non-negative reserve invariant unconditionally in `ExchangeCapsule.transaction()` regardless of `hardenedCalc`, or make the hardened calculation path the unconditional default rather than gating it behind a committee-toggled dynamic property.

Reproducing this requires knowing the precise rounding behavior of `ExchangeProcessor.exchange()` (file not read in this session) to construct sell/buy quantities that push a reserve negative under the default (non-hardened) configuration — this could not be confirmed in the time available.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
