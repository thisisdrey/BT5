### Title
Unbounded central-directory field lengths in `InputZipFile::ProcessCentralDirEntry` cause an out-of-bounds read past the mapped JAR/ZIP buffer - ([File: third_party/ijar/zip.cc])

### Summary
`ijar`/`singlejar`'s ZIP-parsing code trusts attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and the nested extra-field `data_size`) taken directly from a central directory entry to advance a raw pointer through a memory-mapped input file, without checking that the resulting pointer stays within the mapped buffer. This mirrors the LibTIFF CVE-2016-3631 pattern, where `bytecounts[]` values from untrusted file metadata were used to index/advance without validating they stayed inside the actual data, producing an out-of-bounds read.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) reads several 16-bit size fields straight out of the untrusted central directory record and immediately advances the parse cursor `p` by their raw values with no bounds check against the end of the mapped input: [1](#0-0) 

```
p += 16;  // skip to 'compressed size' field
*compressed_size = get_u4le(p);
*uncompressed_size = get_u4le(p);
u2 file_name_length = get_u2le(p);
u2 extra_field_length = get_u2le(p);
u2 file_comment_length = get_u2le(p);
p += 4;  // skip to external file attributes field
*attr = get_u4le(p);
*offset = get_u4le(p);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
p += file_comment_length;
return true;
```

None of `file_name_length`, `extra_field_length`, `file_comment_length`, or the nested extra-field `data_size` are validated against the amount of data actually remaining in the mapped file before `get_u2le`/`get_u4le`/`memcpy` dereference the advanced pointer. Unlike `InputZipFile::ProcessLocalFileEntry`, which calls `EnsureRemaining()` before consuming `file_name_length` and `extra_field_length` (`third_party/ijar/zip.cc:360-370`), the central-directory path performs no equivalent check.

This function is called in a loop from `InputZipFile::ProcessNext` (`third_party/ijar/zip.cc:302-330`), which walks `central_dir_current_` entry-by-entry across the whole central directory. The only global bound enforced earlier is that the aggregate `central_dir_offset + central_dir_size <= in_length` (`third_party/ijar/zip.cc:766-769` in `FindZipCentralDirectory`), which bounds the *total* central directory region but does nothing to stop a single malicious entry's declared `extra_field_length`/`data_size`/`file_comment_length` from making the cursor `p`/`extra_p` walk past the true entry boundary — and, if the entry is near the end of the mapped region, past the end of the mapped file buffer itself. In the extra-field parsing `while` loop, if `data_size` causes `extra_p` to overshoot `p` (rather than landing exactly on it), the loop's `extra_p != p` termination condition never becomes true and the loop's raw `get_u2le(extra_p)` reads continue to consume memory beyond the intended entry, and potentially beyond the mapped buffer, until a chance false match or a crash occurs.

Because this file is `mmap`'d from attacker-suppliable content (an `.aar`/`.jar` produced from a hostile source archive fetched via `http_archive`/`http_jar`, or any dependency artifact singlejar/ijar processes), an attacker who controls the bytes of a build input can trigger reads past the mapped region, matching the CVE-2016-3631 bug class: untrusted size/count fields trusted to walk a buffer without bounds checking.

### Impact Explanation
An out-of-bounds read against a memory-mapped file can crash the Bazel build tool (`ijar`/`singlejar`) with a segmentation fault (denial of service for the build), and in principle could leak adjacent process memory into diagnostic output or misinterpreted parsing state, depending on what lies just past the mapping. This is a memory-safety violation in a component that directly parses attacker-influenced archive content (dependencies, generated jars from untrusted sources) as part of routine `ijar`/`singlejar` post-processing.

### Likelihood Explanation
Reachability is straightforward: any `.jar`/`.aar`/zip-like input consumed by `ijar` (for interface jar generation) or `singlejar` (for combining jars) that is built from untrusted upstream content — e.g., archives fetched from third-party URLs via `http_archive`/`http_jar`/`http_file` and then compiled/repackaged — flows into `InputZipFile::Open`/`ProcessNext`/`ProcessCentralDirEntry`. No credentials, sandbox escape, or local access are required; only the ability to shape a malformed but plausibly-structured ZIP central directory record whose length fields extend past the true buffer.

### Recommendation
Add bounds checks in `ProcessCentralDirEntry` (and the nested extra-field parsing loop) analogous to `EnsureRemaining()` in `ProcessLocalFileEntry`: verify `file_name_length`, `extra_field_length`, `file_comment_length` do not exceed the remaining bytes in the mapped buffer/central directory record before advancing `p`, and make the extra-field loop bail out (rather than looping indefinitely) if `data_size` would cause `extra_p` to exceed `p`/the mapped end.

### Proof of Concept
A reproducible test would construct a malformed ZIP file whose central directory entry declares `extra_field_length` (or a nested extra-field `data_size`) large enough that `extra_p`/`p` walks past the actual mapped end-of-file, then feed it to `ijar`/`singlejar` (e.g., via a `src/test/shell/bazel` shell test similar to `third_party/ijar/test/ijar_test.sh`'s `test_corrupted_end_of_centraldir`, or a new C++ test in the style of `src/tools/singlejar/zip_headers_test.cc`), and run under ASan to confirm a heap/mmap out-of-bounds read is reported. I was not able to execute this PoC myself; only static code review was performed, so exploitability under ASan/valgrind should be confirmed by the engineer implementing the fix. bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
