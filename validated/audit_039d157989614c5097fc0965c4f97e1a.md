## Title
`ExchangeWithdrawActuator` computes and applies the counter-token amount on withdrawal with no user-supplied slippage/minimum-out protection, unlike its swap counterpart - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract` (the "remove liquidity" analog to Balancer's `exitPool`) only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no field allowing the caller to specify a minimum amount of the *other* pooled token they are willing to accept. `ExchangeWithdrawActuator.execute()`/`doValidate()` compute `anotherTokenQuant` purely from the exchange's *current* on-chain reserve ratio at execution time and pay it out unconditionally, exactly the same class of bug as `AuraSpell.closePositionFarm`'s zero-valued `minAmountsOut` passed to Balancer's `exitPool`.

### Finding Description
In `ExchangeWithdrawActuator.doValidate()`, `anotherTokenQuant` is derived solely from `firstTokenBalance`/`secondTokenBalance` read at validation time: [1](#0-0) 

This same unconstrained ratio-based amount is what gets paid out to the withdrawer in `execute()`: [2](#0-1) 

Contrast this with the sibling actuator for swaps, `ExchangeTransactionActuator`, whose contract explicitly carries an `expected` field used as real slippage protection — the transaction reverts if the computed output is below the caller-supplied minimum: [3](#0-2) 

The protobuf definitions confirm the asymmetry: `ExchangeTransactionContract` has an `expected` (minimum output) field while `ExchangeWithdrawContract` has none: [4](#0-3) 

Because `ExchangeWithdrawContract` has no equivalent floor, any actor holding balance/asset can broadcast `ExchangeTransactionContract` transactions immediately before (and after) the target's `ExchangeWithdrawContract` transaction to shift `firstTokenBalance`/`secondTokenBalance` in the exchange pool, sandwiching the withdrawer: the attacker skews the ratio right before withdrawal executes so the withdrawer receives far less of `anotherTokenID` than the pool's fair-value ratio would otherwise yield, then reverses the skew afterward to capture the difference. This is functionally identical to the reported Balancer/Aura issue where `minAmountsOut` is always zero and `exitPool` executes with no floor on returned amounts.

### Impact Explanation
An exchange creator withdrawing their own pooled liquidity via `ExchangeWithdrawContract` can be sandwiched by any unprivileged transaction broadcaster issuing ordinary `ExchangeTransactionContract` swaps around the withdrawal transaction, directly transferring value from the withdrawer to the attacker with no on-chain floor to prevent it. This is a direct, unauthorized value-extraction/theft-of-funds vector reachable purely through the public exchange actuators.

### Likelihood Explanation
Likelihood is high: the attack requires only ordinary signed `ExchangeTransactionContract` transactions (available to any account holding the traded token or TRX) placed adjacent to a known pending `ExchangeWithdrawContract` transaction in the mempool/block — no special privilege, bug in consensus, or contract deployment is needed, only transaction ordering within a block that a broadcaster can influence via timing/fee.

### Recommendation
Add a caller-supplied minimum-amount-out field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting the withdrawal if the computed `anotherTokenQuant` falls below the caller's specified floor.

### Proof of Concept
1. Exchange pool holds `firstTokenBalance` = 100,000,000 TokenA and `secondTokenBalance` = 200,000,000 TokenB.
2. Creator broadcasts `ExchangeWithdrawContract{token_id=TokenA, quant=1,000,000}` expecting ~2,000,000 TokenB back based on the current ratio.
3. Attacker broadcasts an `ExchangeTransactionContract` swap immediately before the creator's transaction is applied, shifting the ratio so `secondTokenBalance` drops sharply relative to `firstTokenBalance`.
4. `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java` lines 77-89), paying the creator far less TokenB than expected, with no `expected`/minimum field to abort the withdrawal.
5. Attacker broadcasts a reversing `ExchangeTransactionContract` swap afterward to restore the ratio and lock in profit, having extracted value from the creator's withdrawal.
