### Title
Attacker can freeze a victim's ability to add new collateral or debt positions by dust-filling their per-account token list to `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol])

### Summary
`Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert once an account holds `MAX_TOKENS_PER_USER` (30) distinct tokens. Because `DepositToken._transfer` registers any token received — including a 1-wei dust transfer sent without consent — an unprivileged attacker can permanently fill a victim's slot count and brick all subsequent first-time deposits, mints, and transfers-in for that account.

### Finding Description
The bug class in CVE-2023-34872 is a crafted input causing a crash/DoS while walking a data structure. The Metronome analog is a crafted state (an attacker-populated per-account token list) causing hard reverts in core flows.

- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30`, and `Pool.sol:143-148` (`onlyIfAdditionWillNotReachMaxTokens`) reverts with `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. [1](#0-0) [2](#0-1) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes 0 → non-zero (`DepositToken.sol:517-520`). `transfer`/`transferFrom` are public and only check the *sender's* unlocked balance (`DepositToken.sol:348-376`). [3](#0-2) 
- The pool has up to 30 deposit tokens (`addDepositToken` caps at `MAX_TOKENS_PER_USER`, `Pool.sol:703`) plus N debt tokens. An attacker acquires dust of each deposit token (or deposits dust themselves) and sends 1 wei of each token to the victim, filling all 30 slots. [4](#0-3) 
- After that: `DepositToken._mint` → `addToDepositTokensOfAccount` reverts, so `deposit()` reverts for any token the victim doesn't already hold (`DepositToken.sol:486-488`); `DebtToken` mint → `addToDebtTokensOfAccount` reverts, blocking issuance of any new synthetic (`Pool.sol:204-208`); any incoming transfer of a new token reverts, which also bricks `Treasury.pull`-style flows and SmartFarmingManager paths that mint/transfer into the account. [5](#0-4) [6](#0-5) 
- The victim cannot self-heal selectively: `removeFromDepositTokensOfAccount` only fires when a balance reaches exactly 0 (`Pool.sol:630-634`, `DepositToken.sol:522-525`), so recovery requires the victim to transfer out every dust token one by one — but a dust *received* balance can be shed (victim transfers the 1 wei onward), making this a temporary rather than permanent freeze. However, during the freeze the victim cannot add new collateral types, which for an underwater-at-risk position blocks the standard rescue path before liquidation.

### Impact Explanation
Temporary freezing of funds / denial of service of a victim's position management: the victim cannot deposit new collateral types, cannot mint new synthetics, and cannot receive new deposit/debt tokens until they manually empty the dusted slots. If the victim's position approaches the liquidation threshold and their unlocked collateral is insufficient to restore health, this can convert into a forced liquidation (collateral seized at a discount). This matches the CVE's medium-severity availability impact.

### Likelihood Explanation
Fully unprivileged: requires only public `transfer` calls with dust amounts of the pool's deposit tokens. Cost is bounded by the value of dust in up to 30 tokens plus gas. No privileged role, oracle manipulation, or trusted-party misbehavior needed. Deployed pools on mainnet/base/optimism have multiple deposit tokens, giving enough distinct tokens to fill the list when combined with debt tokens.

### Recommendation
Decouple list membership from involuntary receipt, e.g.:
- Only add to `depositTokensOfAccount` on `deposit()`/`_mint`, not on `_transfer`, and make `debtPositionOf`/`unlockedBalanceOf` iterate over a balance-checked set — or
- Make `onlyIfAdditionWillNotReachMaxTokens` not revert for unsolicited transfers (let the token be received but excluded from position accounting), or
- Allow an account to opt out / purge entries without requiring a zero balance round-trip, and document that users should consolidate positions via a single token set.

### Proof of Concept
Hardhat test sketch (pool with at least a few deposit tokens; repeat pattern to reach 30 slots):

```ts
// Setup: pool with deposit tokens dtA..dtN and debt token; attacker holds dust of each.
// Victim already holds k deposit/debt tokens (k >= 0).

for (const dt of allDepositTokens) {
  if ((await dt.balanceOf(victim)) === 0) {
    await dt.connect(attacker).transfer(victim, 1); // each fills one slot
    if ((await pool.getDepositTokensOfAccount(victim)).length
        + (await pool.getDebtTokensOfAccount(victim)).length >= 30) break;
  }
}
// Attacker can also do deposit(1, victim) style dust via deposit onBehalfOf_ = victim.

// Victim attempts to deposit a collateral type they don't yet hold:
await expect(
  dtNew.connect(victim).deposit(parseEther("1"), victim.address)
).to.be.revertedWith(UserReachedMaxTokens); // DepositToken._mint -> addToDepositTokensOfAccount

// Victim attempts to mint a new synthetic type:
await expect(
  newDebtToken.connect(victim).issue(...) // via pool mint flow
).to.be.revertedWith(UserReachedMaxTokens);
```

Invariant broken: liveness — a public, permissionless transfer path lets a third party exhaust a per-account bounded-list invariant that gates all first-time mints/deposits, freezing the victim's position-management functions until manual cleanup.
