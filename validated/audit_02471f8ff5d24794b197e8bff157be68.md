## Title
Unbounded index reads in `PrecompiledContracts.extractBytesArray`/`extractSigArray` allow attacker-controlled `DataWord[]` array OOB access from `ValidateMultiSign`/`BatchValidateSign` calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The reported kernel bug is a classic TLV/IE parsing flaw: a loop reads a header field and then a length-derived payload without checking that enough bytes remain in the buffer before dereferencing. The closest reachable analog in java-tron is in the ABI-array extraction helpers used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiles: `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in [1](#0-0) . These functions read an attacker-controlled "array length" word from calldata and then loop that many times, indexing into the `words` array (and the derived `data` byte array) using offsets computed purely from calldata — with no check that the computed indices stay within the bounds of `words` or `data`.

### Finding Description
`extractBytesArray` (and its sibling `extractSigArray`) is called from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, both of which are directly reachable via a TVM `CALL`/`STATICCALL` to the precompile address (`validateMultiSignAddr`/`batchValidateSignAddr`) — i.e., from any smart-contract call that any unprivileged account can trigger, per [2](#0-1)  and [3](#0-2) .

```java
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  if (offset > words.length - 1) {
    return new byte[0][];
  }
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  for (int i = 0; i < len; i++) {
    int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
    int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
    bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen);
  }
  return bytesArray;
}
``` [4](#0-3) 

Only `offset` itself is bounds-checked against `words.length` — a single check performed once, before the loop, exactly analogous to the kernel bug where only the very first IE in a chain gets partial validation while subsequent header/length reads in the loop are unchecked. Inside the loop:
- `words[offset + i + 1]` is read for every `i` up to `len - 1` with no check that `offset + i + 1 < words.length`.
- `bytesOffset` and `bytesLen` are fully attacker-controlled 32-byte words converted via `intValueSafe()`; `words[offset + bytesOffset + 1]` is read with no bound check either.
- `extractBytes(data, ..., bytesLen)` calls `Arrays.copyOfRange(data, offset, offset + len)` at [5](#0-4)  with an attacker-controlled length and start offset, with no verification against `data.length`.

`extractSigArray` has the identical unchecked-loop pattern at [6](#0-5) , and `extractBytes32Array` similarly loops `words[offset + i + 1]` unchecked at [7](#0-6) .

There is a `MAX_SIZE` (16 for `BatchValidateSign`, 5 for `ValidateMultiSign`) check on `signatures.length`/`sigArraySize`, but that check happens only when `VMConfig.allowTvmSelfdestructRestriction()` is active, and even then only bounds `len` itself — it does not validate that `offset + i + 1` or the derived `bytesOffset`/`bytesLen` indices are within the actual `words`/`data` array bounds. See the guard usage in `BatchValidateSign.doExecute`: [8](#0-7) . The pre-loop `isValidAbiEncoding` shape check (`data.length % WORD_SIZE`, header/item word multiples) at [9](#0-8)  validates overall calldata *shape*, but not that the nested dynamic-array offsets embedded in the calldata actually point within the buffer — an attacker can supply a shape-valid buffer whose embedded offset/length words point far outside it.

Because Java array accesses are bounds-checked at the JVM level (unlike the C kernel bug where OOB reads silently read adjacent memory), the practical consequence differs: rather than an information leak, an out-of-range index here throws `ArrayIndexOutOfBoundsException` (from `words[...]`) or `NegativeArraySizeException`/`IndexOutOfBoundsException` (from `new byte[len][]` with negative `len`, or `Arrays.copyOfRange`). This exception is **not caught inside `extractBytesArray`/`extractSigArray`/`ValidateMultiSign.execute`** itself, but the calling paths differ:

- `BatchValidateSign.execute` wraps `doExecute` in a try/catch for `Throwable` at [10](#0-9) , so the exception is swallowed there and converted to a zero result.
- `ValidateMultiSign.execute` has **no such outer try/catch** around the `extractBytesArray`/`extractSigArray` call itself — [11](#0-10)  shows only the inner permission-processing block (after signatures are already extracted) is wrapped in `try { ... } catch (Throwable t)`. Any exception thrown by the unchecked array indexing in `extractBytesArray`/`extractSigArray` before that inner try-block propagates uncaught out of `execute()`.

### Impact Explanation
An uncaught exception thrown out of a `PrecompiledContract.execute()` implementation propagates up into the TVM's `Program`/`callToPrecompiledAddress` call path. Depending on how that exception is or isn't handled further up the call stack (this could not be fully confirmed from the available index; `Program.java` contents were largely inaccessible), this can manifest as either a caught VM exception (contract call reverts, funds-safe) or an unhandled exception during transaction execution that could interrupt block processing on a node — a potential node crash/DoS condition triggerable by any account calling `ValidateMultiSign` (address `0x66...`) with a single crafted call. Given the ambiguity in verified exception containment for `ValidateMultiSign` specifically (unlike `BatchValidateSign`, which is provably contained), this is flagged as Medium-to-High depending on downstream handling, which could not be conclusively verified with the tools available.

### Likelihood Explanation
High: the entry point (`ValidateMultiSign`/`BatchValidateSign` precompile addresses) is reachable from any smart contract via a plain `CALL`/`STATICCALL` with attacker-supplied calldata, requiring no special privileges, no valid signatures, and no prior state setup. Crafting calldata with an oversized `len` word or out-of-range nested offset/length words is trivial.

### Recommendation
Add explicit bounds checks in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` before every array access derived from calldata:
- Validate `len >= 0` and `offset + len + 1 <= words.length` before the loop.
- Validate `offset + bytesOffset + 1 < words.length` before reading `words[offset + bytesOffset + 1]`.
- Validate `bytesLen >= 0` and `(bytesOffset + offset + 2) * WORD_SIZE + bytesLen <= data.length` before calling `extractBytes`.
- Additionally wrap the `extractBytesArray`/`extractSigArray` call in `ValidateMultiSign.execute` in the same defensive try/catch pattern already used in `BatchValidateSign.execute`, so a malformed/oversized nested array can never escape as an uncaught exception from `execute()`.

### Proof of Concept
Craft calldata for `validatemultisign(address,uint256,bytes32,bytes[])`:
1. Fixed head words (`address`, `permissionId`, `hash`, offset to `bytes[]` array) sized so that `isValidAbiEncoding` shape-check passes (aligned to `ABI_HEADER_WORDS`/`ABI_ITEM_WORDS`).
2. At the `bytes[]` array offset, set `len` (the array-length word) to a large value (e.g. `0xFFFFFFFF` truncated via `intValueSafe()`), or leave `len` small but small buffer so that `offset + i + 1` exceeds `words.length` after just a couple of iterations.
3. Alternatively, keep `len` small (e.g. 1) but set the per-item offset word (`words[offset+1]`) to a huge value so `bytesOffset` computed from it, when added to `offset + 2`, produces an index far beyond `words.length`.
4. Invoke this calldata via a `CALL` from a deployed contract to the `ValidateMultiSign` precompile address; observe an `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown from `extractBytesArray`/`extractSigArray` inside `execute()`, uncaught by any surrounding try/catch in `ValidateMultiSign.execute`.

**Note on verification limits:** I was unable to fully retrieve the contents of `Program.java`'s `callToPrecompiledAddress` method through the index (file appeared empty/truncated in results), so I could not conclusively confirm whether an uncaught `RuntimeException` from `ValidateMultiSign.execute()` is caught generically at that call site (which would downgrade impact to a mere reverted transaction) or would propagate further and disrupt block/transaction processing. A Devin session with full repository access would be needed to trace this exactly and confirm the severity of the uncaught-exception path.
