### Title
`allowShieldedTransactionApi` flag can be bypassed by broadcasting `ShieldedTransferContract` directly, since `ShieldedTransferActuator` never checks it - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`allowShieldedTransactionApi` is a node-level flag meant to disable shielded (zk-SNARK) transaction functionality. It is only enforced inside `Wallet.java` (the gRPC/HTTP API layer used to *build* shielded transaction parameters), but the on-chain actuator that actually executes a `ShieldedTransferContract` — `ShieldedTransferActuator` — never checks this flag. A user who constructs the shielded proof/transaction bytes independently (without going through the gated Wallet helper APIs) can broadcast the transaction directly and have it validated and executed normally, exactly as the reported `LMPVault`/`Rewarder` bug describes bypassing a pause flag by calling the lower-level function directly instead of the gated wrapper.

### Finding Description
`Wallet.java` is the only place in the codebase that reads `isAllowShieldedTransactionApi()`: [1](#0-0) 
(single match found; it gates the wallet-side helper RPCs used to build/create shielded transaction inputs, e.g. `createShieldedTransaction`, `getSpendingKey`, etc.)

The actual state-changing logic for shielded transfers lives in `ShieldedTransferActuator.execute()`/`validate()`: [2](#0-1) 

A grep across the entire `actuator` module for `allowShieldedTransactionApi`/`ShieldedTransactionApi` returns zero matches — the actuator only checks the separate, unrelated `allowShieldedTransaction` (whole feature toggle) and `allowShieldedTRC20Transaction` dynamic properties, never the API-only flag. This is corroborated directly by an existing test comment: [3](#0-2) 
which explicitly asserts: "Test that shielded transfer transaction validation works even when `allowShieldedTransactionApi` is disabled... This verifies that the API flag only gates wallet/helper APIs, not the core transaction validation logic."

Because Tron's HTTP/gRPC `broadcastTransaction` entry point accepts any well-formed, correctly-signed `Transaction`, an unprivileged client can independently compute the zk-SNARK proof and note data offline (bypassing `Wallet`'s gated builder methods entirely) and submit a `ShieldedTransferContract` transaction straight into `TransactionsMsgHandler`/`Manager`, where it will be processed by `ShieldedTransferActuator` without any `allowShieldedTransactionApi` check — identical in structure to calling `MainRewarder.getReward` directly instead of the paused `LMPVault.claimRewards`.

### Impact Explanation
`allowShieldedTransactionApi` exists specifically so operators can disable shielded transaction usage at the API layer (e.g., in response to a discovered issue in the shielded pool, to comply with regulatory/exchange requirements, or to mitigate an active exploit) without needing a hard fork of the broader `allowShieldedTransaction` consensus flag. If the actuator itself ignores this flag, the intended kill-switch provides no real protection: attackers/users can continue to move funds into/out of/within the shielded pool via direct broadcast, undermining the operational control the flag is supposed to provide. Given the shielded pool has historically been the target of serious vulnerabilities, an ineffective disable switch is a meaningful medium-severity gap — it can allow continued use of a feature operators believed they had shut off, risking fund safety/compliance guarantees of the disable action.

### Likelihood Explanation
High feasibility: constructing a `ShieldedTransferContract` transaction does not strictly require calling the gated `Wallet` helper RPCs — the ZK proof and note encryption can be produced by any client with access to `librustzcash`/equivalent crypto libraries (which are open source and already vendored in this repo), then packaged into a transaction and submitted via the standard, unauthenticated `broadcastTransaction` API. No privileged access is needed; only knowledge of the protocol and cryptographic build tooling, both of which are already used by ordinary shielded-transaction users.

### Recommendation
Add an explicit check in `ShieldedTransferActuator.validate()` (mirroring the existing `allowShieldedTransaction`/`allowShieldedTRC20Transaction` checks) that rejects the contract with `ContractValidateException` when `CommonParameter.getInstance().isAllowShieldedTransactionApi()` is `false`, so the actuator-level enforcement matches the intended operator-level disable semantics rather than relying solely on the `Wallet` API layer.

### Proof of Concept
1. Node operator sets `allowShieldedTransactionApi=false` in config, believing shielded transfers are disabled.
2. Attacker/user independently builds a valid `ShieldedTransferContract` (spend/receive descriptions, zk proof) offline using the same crypto primitives Tron uses (no dependency on `Wallet`'s gated helper RPCs).
3. Attacker signs and submits the transaction via `broadcastTransaction` (gRPC/HTTP).
4. `TransactionsMsgHandler`/`Manager` routes it to `ShieldedTransferActuator.validate()`/`execute()`, which contains no check of `allowShieldedTransactionApi` (confirmed by code search returning zero references in the actuator module and by the existing test `shieldedTransferValidationWorksWhenApiDisabled` in `ShieldedTransferActuatorTest.java` explicitly demonstrating successful validation with the flag disabled): [4](#0-3) 
5. The transaction executes successfully, proving the API-disable flag can be bypassed by any unprivileged transaction broadcaster.

  @Override
  public boolean execute(Object result)
      throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) result;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    try {
      shieldedTransferContract = any.unpack(ShieldedTransferContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    long fee = calcFee(shieldedTransferContract);
    try {
      if (shieldedTransferContract.getTransparentFromAddress().toByteArray().length > 0) {
        executeTransparentFrom(shieldedTransferContract.getTransparentFromAddress().toByteArray(),
            shieldedTransferContract.getFromAmount(), ret, fee);
      }
      Commons.adjustAssetBalanceV2(accountStore.getBlackhole(),
          CommonParameter.getInstance().getZenTokenId(), fee,
          accountStore, assetIssueStore, dynamicStore);
    } catch (BalanceInsufficientException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(0, code.FAILED);
      ret.setShieldedTransactionFee(fee);
      throw new ContractExeException(e.getMessage());
    }

    executeShielded(shieldedTransferContract.getSpendDescriptionList(),
        shieldedTransferContract.getReceiveDescriptionList(), ret, fee);

    if (shieldedTransferContract.getTransparentToAddress().toByteArray().length > 0) {
      executeTransparentTo(shieldedTransferContract.getTransparentToAddress().toByteArray(),
          shieldedTransferContract.getToAmount(), ret, fee);
    }

    //adjust and verify total shielded pool value
    try {
      Commons.adjustTotalShieldedPoolValue(addExact(subtractExact(
          shieldedTransferContract.getToAmount(),
          shieldedTransferContract.getFromAmount()), fee), dynamicStore);
    } catch (ArithmeticException | BalanceInsufficientException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(0, code.FAILED);
      ret.setShieldedTransactionFee(fee);
      throw new ContractExeException(e.getMessage());
    }

    ret.setStatus(0, code.SUCESS);
    ret.setShieldedTransactionFee(fee);
    return true;
  }

  /**
   * Test that shielded transfer transaction validation works even when
   * allowShieldedTransactionApi is disabled. This verifies that the API flag
   * only gates wallet/helper APIs, not the core transaction validation logic.
   */
  @Test
  public void shieldedTransferValidationWorksWhenApiDisabled() {
    boolean orig = Args.getInstance().isAllowShieldedTransactionApi();
    // Disable the shielded API (this should NOT affect transaction validation)
    Args.getInstance().setAllowShieldedTransactionApi(false);

    dbManager.getDynamicPropertiesStore().saveAllowShieldedTransaction(1);
    dbManager.getDynamicPropertiesStore().saveTotalShieldedPoolValue(AMOUNT);

    try {
      ZenTransactionBuilder builder = new ZenTransactionBuilder(wallet);
      SpendingKey sk = SpendingKey.random();
      ExpandedSpendingKey expsk = sk.expandedSpendingKey();
      PaymentAddress address = sk.defaultAddress();
      Note note = new Note(address, AMOUNT);
      IncrementalMerkleVoucherContainer voucher = createSimpleMerkleVoucherContainer(note.cm());
      byte[] anchor = voucher.root().getContent().toByteArray();
      dbManager.getMerkleContainer()
          .putMerkleTreeIntoStore(anchor, voucher.getVoucherCapsule().getTree());
      builder.addSpend(expsk, note, anchor, voucher);

      addZeroValueOutputNote(builder);

      long fee = dbManager.getDynamicPropertiesStore().getShieldedTransactionCreateAccountFee();
      String addressNotExist =
          Wallet.getAddressPreFixString() + "8ba2aaae540c642e44e3bed5522c63bbc21f0000";

      builder.setTransparentOutput(ByteArray.fromHexString(addressNotExist), AMOUNT - fee);

      TransactionCapsule transactionCap = builder.build();
      Contract contract =
          transactionCap.getInstance().toBuilder().getRawDataBuilder().getContract(0);
      ShieldedTransferActuator actuator = new ShieldedTransferActuator();
      actuator.setChainBaseManager(dbManager.getChainBaseManager()).setContract(contract)
          .setTx(transactionCap);

      // Validation should succeed even when API is disabled
      actuator.validate();
    } catch (ContractValidateException e) {
      Assert.fail("Shielded transfer validation should not throw ContractValidateException: "
          + e.getMessage());
    } catch (Exception e) {
      Assert.fail("Shielded transfer should not throw Exception: " + e.getMessage());
    } finally {
      Args.getInstance().setAllowShieldedTransactionApi(orig);
    }
  }
