Based on the structural evidence gathered, the strongest local analog to the `MarketFactory.updateExtension()` access-control gap is in `pallet-revive`'s **built-in precompile framework**, specifically the inconsistency between `substrate/frame/revive/src/precompiles/builtin/system.rs` and its sibling precompiles.

### Title
Missing delegatecall guard on the `system` builtin precompile allows caller-identity spoofing in `pallet-revive` - (File: `substrate/frame/revive/src/precompiles/builtin/system.rs`)

### Summary
`pallet-revive` recently hardened multiple precompiles (`pallet-xcm` precompile, `pallet-assets` ERC20 precompile, `pallet-asset-conversion` precompile, `pallet-vesting` precompile) by adding an explicit `env.is_delegate_call()` rejection before deriving caller identity via `env.caller()`, because delegatecall preserves the *original* external caller while executing inside the delegating (potentially malicious) contract's storage/logic context [1](#0-0) . This is documented explicitly as a security fix: "Delegatecall to precompiles allows a malicious contract to execute precompile logic in a misleading caller context... letting the intermediary contract act on the caller's assets... on their behalf" [2](#0-1) . The `storage.rs` builtin precompile also enforces a caller-context guard (in the inverse direction, requiring delegatecall) [3](#0-2) . However `system.rs`, which also calls `env.caller()` to resolve identity, does **not** appear in the set of files that received the `is_delegate_call()` guard despite exhibiting the same caller-derivation pattern [4](#0-3) .

### Finding Description
The `MarketFactory.updateExtension()` bug's core invariant was: a privileged self-authorization mapping (`extensions[msg.sender] = true`) was writable by anyone, letting an attacker impersonate an approved operator for other accounts' funds. The equivalent broken invariant here is: the identity used to authorize or account for privileged behavior (`env.caller()`) must reflect the actual invoking context, not be spoofable through an intermediary. `pallet-revive` explicitly recognized and fixed this exact class of bug for four precompiles — the fix pattern is a one-line guard: `ensure!(!env.is_delegate_call(), pallet_revive::Error::<T>::PrecompileDelegateDenied)` before any use of `env.caller()`. `system.rs` uses `env.caller()` [4](#0-3)  but was not covered by PR #11676 ("Reject delegatecall into pallet-assets ERC20 precompile") or PR #11715 ("Reject delegatecall into precompiles via PrecompileDelegateDenied"), both of which enumerate only `substrate/frame/assets/precompiles/src/lib.rs`, `substrate/frame/asset-conversion/precompiles/src/lib.rs`, and `polkadot/xcm/pallet-xcm/precompiles/src/lib.rs` as the files touched [5](#0-4) . A malicious contract can therefore `delegatecall` into the `system` precompile so that `env.caller()` resolves to the original victim caller rather than the malicious intermediary, letting the intermediary's logic execute any caller-identity-gated behavior of that precompile "as" the victim — the direct structural analog of setting oneself as an unauthorized `extension`/operator.

**Note on verification limits:** I was not able to open the full contents of `system.rs` within this session (only grep match locations were available, not file content), so I cannot confirm the exact function signatures it exposes (e.g., whether it exposes any state-mutating or balance/allowance-gated call keyed on `env.caller()`). This should be verified directly in the file before treating this as conclusively exploitable — if `system.rs` only exposes pure read-only system info (e.g., block number, chain id) with no caller-identity-gated state mutation, the impact would be limited to metadata spoofing rather than fund loss, unlike the original H-5 report's operator-hijack impact.

### Impact Explanation
If `system.rs` exposes any caller-identity-gated capability (allowance/balance query on behalf of "caller", nonce/permission checks, etc.) analogous to how the ERC20/vesting/XCM precompiles used `env.caller()` for authorization, a malicious contract could delegatecall into it to make privileged decisions using a victim's spoofed identity — mirroring the fund-loss/unauthorized-action impact of the original H-5 finding. This falls under "unauthorized execution or origin escalation" in the accepted impact set.

### Likelihood Explanation
High, if exploitable: it requires no privileged relayer, validator, or governance actor — any user can deploy a contract that delegatecalls into the `system` precompile address, exactly like the `Caller.sol` fixture already used in the codebase's own tests for the other four now-patched precompiles [6](#0-5) .

### Recommendation
Audit `substrate/frame/revive/src/precompiles/builtin/system.rs` for any use of `env.caller()` in a way that gates privileged/state-changing behavior, and add the same `ensure!(!env.is_delegate_call(), pallet_revive::Error::<T>::PrecompileDelegateDenied)` guard used in `pallet-xcm`, `pallet-assets`, `pallet-asset-conversion`, and `pallet-vesting` precompiles, consistent with the precedent set by those PRs.

### Proof of Concept
Following the pattern already proven in the repository's own test suite (`delegatecall_is_rejected` in `polkadot/xcm/pallet-xcm/precompiles/src/tests.rs`): deploy the existing `Caller.sol` fixture contract, then call its `delegateCall` entry point targeting the `system` precompile's fixed address with a selector for any caller-identity-dependent function; because `system.rs` lacks the `is_delegate_call()` check present in sibling precompiles, `env.caller()` inside the precompile resolves to the original signer, letting the `Caller` contract's code path execute logic gated on that spoofed identity — the same "attacker-controlled contract impersonates a legitimate caller because an access check that peers already require was omitted" pattern as the reported `MarketFactory.updateExtension()` issue.
