### Title
Missing invariant check on legacy (non-hardened) exchange swap allows negative/corrupted pool reserves - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes the counter-token amount for a bancor-style AMM swap using a floating-point/double `Math.pow`-based `ExchangeProcessor` and then unconditionally commits the resulting balances to the `Exchange` protobuf state. The only sanity check that the resulting reserves remain non-negative (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is gated behind `hardenedCalc` (i.e. only runs when the `allowHardenExchangeCalculation` chain parameter is enabled). In the legacy/default path this invariant check is skipped entirely, and `ExchangeTransactionActuator.doValidate()` never verifies that the computed `anotherTokenQuant` does not exceed the pool's actual reserve of that token before `execute()` persists the new (possibly negative) balances. This is the same bug class as the reported issue: an approximate swap-pricing calculation can violate the fundamental pool invariant, and no assertion exists to reject the transaction when that happens.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  computes `buyTokenQuant` via a `Processor` (either the legacy floating-point `ExchangeProcessor` or, only when `hardenedCalc` is true, `SafeExchangeProcessor`) and then updates `newFirstTokenBalance`/`newSecondTokenBalance`. The negativity guard is explicitly conditioned on `hardenedCalc`: [2](#0-1) 
When `hardenedCalc` is false (the historical default, controlled by the `allowHardenExchangeCalculation` dynamic property), this check is never executed, so `this.exchange` is persisted with whatever balances the floating-point bancor formula in `ExchangeProcessor.exchange()` produces [3](#0-2) , including balances that are negative or otherwise violate the pool's value invariant.

`ExchangeTransactionActuator.doValidate()` does not independently bound `anotherTokenQuant` against the pool's real reserve of that token before calling `transaction()` and accepting the trade — it only checks that `anotherTokenQuant >= tokenExpected`: [4](#0-3) 
Contrast this with `ExchangeWithdrawActuator.doValidate()`, which explicitly checks `secondTokenBalance < anotherTokenQuant`/`firstTokenBalance < anotherTokenQuant` before accepting the operation [5](#0-4) . No equivalent reserve-sufficiency assertion exists for `ExchangeTransactionActuator`, and `execute()` commits the mutated `ExchangeCapsule` unconditionally [6](#0-5) .

This is directly analogous to the reported Aftermath Finance bug: an approximate pricing/invariant calculation (there, Newton's method; here, `Math.pow`-based bancor relay math) can, under adversarial input, produce a result that breaks the fundamental pool invariant (reserve cannot go negative / must be internally consistent), and the code path that commits state lacks the assert needed to reject that outcome.

### Impact Explanation
Any unprivileged account holding a TRC-10 asset or TRX can call `ExchangeTransactionContract` (`ExchangeTransactionActuator`) against any existing bancor-style `Exchange` pool. If the legacy (non-hardened) processor is in effect and reserve ratios/quantities are chosen such that the double-precision bancor computation returns a `buyTokenQuant`/`anotherTokenQuant` exceeding the pool's actual reserve, the resulting negative balance is written directly into the persistent `ExchangeStore`/`ExchangeV2Store` state. This corrupts the AMM pool's accounting permanently (an unbacked/negative reserve), and the trader is simultaneously credited the full asset amount in their `AccountCapsule`, effectively minting value out of the pool that is not backed by real reserves — a fund-theft/permanent-freezing-of-funds condition for the pool and its other participants, and can distort all subsequent swaps against that pool.

### Likelihood Explanation
Exploitability depends on the `allowHardenExchangeCalculation` proposal not being active (the hardened path does contain a non-negativity guard) and on finding reserve/quantity combinations where floating-point/bancor rounding produces an output quant that exceeds the pool reserve — feasible for small or heavily skewed pools, similar to how the referenced report demonstrates that extreme, but legitimately-permitted, swap parameters can break the invariant. No special privileges are required; only a signed `ExchangeTransactionContract` transaction from any account holding the sell-side asset.

### Recommendation
Add an unconditional invariant check in `ExchangeCapsule.transaction()` (not gated by `hardenedCalc`) that rejects the swap if `newFirstTokenBalance < 0 || newSecondTokenBalance < 0`, and additionally verify that the pool's value/invariant (e.g., product or bancor-consistent relationship of reserves) does not decrease relative to the pre-swap state, mirroring the recommended fix of asserting `invariant_after >= invariant` before committing state. Also add an explicit reserve-sufficiency check in `ExchangeTransactionActuator.doValidate()` (as already done in `ExchangeWithdrawActuator`) so malformed trades are rejected at validation time rather than corrupting persisted state at execution time.

### Proof of Concept
Conceptual reproduction path (mirrors the referenced Move PoC, adapted to java-tron):
1. Create/target an `Exchange` pool with skewed reserves (e.g., very small `secondTokenBalance` relative to `firstTokenBalance`) while `allowHardenExchangeCalculation` is disabled (legacy path).
2. Submit `ExchangeTransactionContract` selling `firstTokenID` with a `tokenQuant` chosen so that `ExchangeProcessor.exchange()`'s double-precision bancor computation (`exchangeToSupply` → `exchangeFromSupply`) returns a `buyTokenQuant` greater than the pool's actual `secondTokenBalance`.
3. `doValidate()` only checks `anotherTokenQuant >= tokenExpected` [4](#0-3) , so the transaction passes validation.
4. `execute()` calls `exchangeCapsule.transaction(...)` again, and since `hardenedCalc` is false the negativity guard is skipped [2](#0-1) , persisting a negative `secondTokenBalance` while crediting the full `anotherTokenQuant` to the caller's account [7](#0-6) .

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
