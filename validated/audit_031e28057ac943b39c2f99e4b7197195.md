### Title
Non-constant-time comparison of privileged RPC auth tokens enables remote timing side-channel to recover the secret - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
Several privileged Stacks HTTP RPC endpoints (`/v3/block_proposal`, `/v3/blocks/upload` broadcast, `/v3/transactions/simulate`, `/v3/blocks/replay`, `/v3/blocks/simulate`, and `/v3/contracts/fast-call-read`) authenticate callers by comparing the client-supplied `authorization` header against the node-configured secret using ordinary Rust string equality (`!=`), which is not constant-time. This is the same bug class as CVE-2018-1000226 (Cobbler): "improper validation of security tokens" that lets a remote, unauthenticated attacker exploit the validation logic itself rather than the secret being properly protected.

### Finding Description
Each of these handlers implements the identical pattern in `try_parse_request`: [1](#0-0) 

```rust
let Some(password) = &self.auth else {
    return Err(Error::Http(400, "Bad Request.".into()));
};
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```

The same construct appears in [2](#0-1) , [3](#0-2) , and equivalently in `blockreplay.rs` and `blocksimulate.rs` (both matched by `auth_header != password`/`== password` in this repo).

`String`/`&str` `PartialEq` in Rust compares byte-by-byte and returns as soon as a mismatch is found (it is a thin wrapper over slice equality, which itself early-exits). This means the time taken by the comparison is a function of how many leading bytes of the guessed token match the real secret. A remote attacker who can send many HTTP requests to these endpoints and measure response latency can perform a classic byte-at-a-time timing attack to recover the `auth_token` configured via `connection_options.auth_token`, exactly the "improper validation of security tokens" class described in the Cobbler advisory (privilege escalation via API token validation flaws) rather than a flaw in generating or storing the secret itself.

Unlike the volumetric/DDoS carve-out in scope rules, this is not about flooding — it is about the *validation logic itself* leaking a timing side channel that breaks the equality "attacker-supplied token == server secret" in a way that is exploitable byte-by-byte with a bounded, non-volumetric number of requests (one probe set per byte position).

### Impact Explanation
If successfully exploited, an attacker recovers the `auth_token` and gains full unauthorized access to privileged endpoints, most critically `/v3/block_proposal`, which is designed to gate block-validation requests to trusted signers/miners. Recovering this token allows an unauthenticated remote party to submit forged block proposals for validation, invoke `/v3/blocks/upload` broadcast, or drive `fast-call-read`/`txsimulate`/`blocksimulate` — i.e., unauthorized write/compute access to node internals that should require the operator-configured secret. This aligns with the Critical bucket "unauthenticated/unauthorized write to state" and "auth bypass" impact categories, contingent on successful exploitation of the timing channel.

### Likelihood Explanation
Exploitability depends heavily on network jitter and the granularity of measurable timing differences, which is generally difficult over a real network without many repeated samples and statistical averaging, but is a well-documented practical attack (e.g., against HMAC/token comparisons) when enough requests can be sent and averaged. Because these endpoints require an operator to have explicitly configured `auth_token`, only deployments that enable these endpoints are exposed, and the attacker needs sustained network access to the RPC port. This makes exploitation feasible but non-trivial, not a single-packet crash.

### Recommendation
Replace all `auth_header != password` / `auth_header == password` string comparisons in `postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, and `fastcallreadonly.rs` with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or manually XOR-accumulating over fixed-length byte buffers) so that the comparison time is independent of how many leading bytes match. Centralize this check in a single shared helper (e.g., in `httpcore.rs`) to avoid the same defect being reintroduced per-handler.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3cr3tT0ken"` and enable `/v3/block_proposal`.
2. From a remote host, send repeated POST requests to `/v3/block_proposal` with candidate `authorization` header values that share an increasing number of correct leading bytes (e.g., `"A...", "S...", "SA...", "S3...")`, measuring round-trip time for each with many repetitions to average out network noise.
3. Because `if auth_header != password` short-circuits at the first mismatched byte, the average latency should be measurably higher for candidates with a longer correct byte-prefix, since Rust's slice equality proceeds through more comparisons before returning false. Statistically distinguishing these timings step-by-step across all 65 (or so) prefix positions recovers `S3cr3tT0ken` without ever knowing it in advance, bypassing the intended authentication for all endpoints sharing this pattern (`postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, `fastcallreadonly.rs`).
