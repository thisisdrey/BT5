### Title
Permissionless `reclaim_bounty_funds` relies on a debug-only assertion instead of an enforced check for child-bounty funds - (File: `substrate/frame/bounties/src/lib.rs`)

### Summary
The external report's core broken invariant is: a "sweep unrelated tokens" utility fails to protect assets that are actually still owned/managed by the protocol (`want`/`yveCrv`), so the sweep can drain funds it should never touch. The local analog is `pallet_bounties::Pallet::reclaim_bounty_funds`, a **permissionless** extrinsic that sweeps *all* assets out of a closed bounty's sub-account into the treasury. The only guard against sweeping funds that still belong to a live **child bounty** is a `debug_assert!`, which is compiled out entirely in release/production builds.

### Finding Description
`reclaim_bounty_funds` is callable by any signed account and checks only that the parent bounty has been removed from `Bounties::<T, I>` storage: [1](#0-0) 

The single safeguard intended to ensure the bounty account holds no funds still earmarked for outstanding child bounties is:
```rust
debug_assert!(
    T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
    "child bounties should not exist for a closed bounty"
);
```
`debug_assert!` is a no-op in release builds (the build profile used by real Substrate-based chains), so in production this "protection" simply does not execute. The subsequent transfer:
```rust
let transferred = T::TransferAllAssets::force_transfer_all_assets(
    &bounty_account,
    &treasury_account,
)?;
```
sweeps *every* asset configured in `TransferAllAssets` out of `bounty_account` — exactly mirroring the reported pattern where a "sweep leftover tokens" function fails to exclude the assets it is not supposed to touch (there: `want`/`yveCrv`; here: funds still owed to an outstanding child bounty attached to the same account).

### Impact Explanation
If any code path allows a parent bounty to be removed from `Bounties::<T, I>` while child bounties funded from the same `bounty_account` still exist or have unclaimed value (e.g. a future code change, a race between `close_bounty`/removal logic and child-bounty settlement, or a reentrant/ordering bug in `T::ChildBountyManager`), the permissionless `reclaim_bounty_funds` call would irrecoverably redirect those child-bounty funds to the treasury instead of the rightful child-bounty curator/beneficiary. This is a fund-misdirection / permanent-fund-loss primitive callable by any unprivileged account, matching the "duplicate settlement / wrong beneficiary / fund loss" impact class.

### Likelihood Explanation
Exploitability is contingent on whether some other code path in the bounty-closing logic already enforces (via a real `ensure!`) that `child_bounties_count(bounty_id) == 0` before a bounty can be removed from `Bounties::<T, I>`. I could not fully verify from the indexed code whether such an enforced check exists on every removal path (e.g. `close_bounty`, `unassign_curator`, `claim_bounty`). What is confirmed is that `reclaim_bounty_funds` itself does not defend against this condition at its own call site — it only carries a debug-only sanity check with a comment asserting an invariant it does not enforce. Relying on `debug_assert!` for a security-relevant invariant in a permissionless, fund-moving extrinsic is itself the defect, regardless of whether another path currently prevents the precondition from occurring; any future change to bounty/child-bounty removal ordering would silently reintroduce fund loss with no compile-time or runtime signal in production.

### Recommendation
Replace the `debug_assert!` with a real `ensure!(T::ChildBountyManager::child_bounties_count(bounty_id) == 0, Error::<T, I>::...)` in `reclaim_bounty_funds`, or otherwise architecturally guarantee (and unit-test in a way that also runs the check in release builds) that the bounty account can never hold live child-bounty funds when reachable by this permissionless sweep. This ensures the "protected" (still-owed) funds are excluded exactly like `want`/`yveCrv` should have been excluded in the original report's `protectedTokens()`.

### Proof of Concept
Conceptual PoC (pending confirmation that a bounty can be removed from `Bounties::<T,I>` while `child_bounties_count(bounty_id) > 0`):
1. Propose and approve a bounty; propose/accept a curator.
2. Curator creates one or more child bounties funded from the parent `bounty_account`.
3. Trigger whatever path removes the parent bounty from `Bounties::<T, I>` storage while the child bounty is still active/unclaimed (this is the step requiring confirmation — if such a path exists or is later introduced, the following completes the exploit).
4. Any signed account calls `Bounties::reclaim_bounty_funds(origin, bounty_id)`.
5. `force_transfer_all_assets` sweeps the full `bounty_account` balance — including funds still owed to the child bounty — to the treasury, permanently misdirecting the child bounty's funds, with no runtime check preventing it because the only guard (`debug_assert!`) is absent in release builds.
