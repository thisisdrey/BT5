### Title
Servicer can drain USDC from any borrower with a standing allowance via unauthorized address registration - ([File: tare-io__tare-contracts/contracts/Loans.sol])

### Summary
The `Loans` contract relies on a per-caller address book for role validation. Because `LoansAuth.registerAddress` is permissionless and allows any caller to register any address for any role in their own private book, a malicious servicer can register an arbitrary victim as a `Borrower`. They can then use `Loans.updateBorrower` to assign that victim to a loan they service and call `Loans.pay`, which triggers a `safeTransferFrom` to pull USDC from the victim's address into the protocol.

### Finding Description
In the Tare protocol, `LoansAuth` maintains an `addressBook` mapping where each caller manages their own set of approved addresses for various roles: [1](#0-0) 

The `registerAddress` function allows any user to add any address to their book without consent from the target address: [2](#0-1) 

A malicious servicer can exploit this by:
1. Registering a victim address (who has a standing USDC allowance to the `Loans` contract) as a `Roles.Borrower` in the servicer's own address book.
2. Calling `Loans.updateBorrower(loanId, victim)`, where `loanId` is a loan the attacker services. This function only checks if the new borrower is registered in the *servicer's* address book: [3](#0-2) 
3. Calling `Loans.pay(loanId, amount, ...)`. This function pulls tokens from the registered borrower address via `_deposit`: [4](#0-3) [5](#0-4) 

The attacker can then use `applyWaterfall` to allocate these funds to servicing fees and withdraw them via `servicerWithdraw`.

### Impact Explanation
This vulnerability allows a malicious or compromised servicer to steal USDC from any user (investor or borrower) who has granted an ERC20 allowance to the `Loans` contract. Since users are encouraged to provide allowances for legitimate loan activities, this places all such users at risk of total loss of their approved funds. This constitutes an unauthorized state transition and theft of assets from honest users, meeting the Tare Allowed Impact Gate.

### Likelihood Explanation
The likelihood is medium-to-high. While it requires the attacker to be a registered servicer, the `LoansAuth` model allows for decentralized role management. Users often leave "infinite" or large allowances to protocols they interact with frequently, making them easy targets for this "pull-based" theft.

### Recommendation
Strict validation should be added to ensure that an address can only be registered for a role if they have provided a cryptographic signature consenting to that role for a specific address book owner. Alternatively, `updateBorrower` should require a signature from the new borrower.

### Proof of Concept
1. **Setup**: 
   - `Victim` has 10,000 USDC and has called `USDC.approve(Loans, 10,000)`.
   - `Attacker` is the registered servicer for `Loan #123`.
2. **Execution**:
   - `Attacker` calls `LoansAuth.registerAddress(Roles.Borrower, Victim)`.
   - `Attacker` calls `Loans.updateBorrower(123, Victim)`.
   - `Attacker` calls `Loans.pay(123, 10000, timestamp, ref)`.
3. **Result**:
   - `Loans` contract executes `USDC.transferFrom(Victim, Loans, 10000)`.
   - `Loan #123` now has 10,000 USDC in `ACC_BORROWER_PAYMENT_CLEARING`.
   - `Attacker` calls `applyWaterfall` to move funds to `ACC_SERVICER_FEE_PAYABLE` and withdraws via `servicerWithdraw`.
