## Analog Found

### Title
Unvalidated floating-point Bancor relay math lets any account drain an Exchange trading pair's reserve below its real backing - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The BNB Chain report describes an unprivileged actor repeatedly triggering a token's automatic reward-swap logic to siphon a shared liquidity reserve (a PancakeSwap USDT/Pro pair) far below what it should honestly pay out, using nothing but ordinary, permissionless transfer calls. java-tron's built-in on-chain AMM equivalent — the `Exchange`/`ExchangeV2` pair driven by `ExchangeTransactionActuator` — has the same structural weakness: any signed `ExchangeTransactionContract` can invoke the pair's bonding-curve swap, and the invariant that would stop a swap from paying out more of the counter-token than the pair actually holds is only enforced when a governance flag (`ALLOW_HARDEN_EXCHANGE_CALCULATION`, default `0`) is turned on.

### Finding Description
`ExchangeTransactionActuator.execute()` computes the payout for a swap by calling `exchangeCapsule.transaction(tokenID, tokenQuant, ...)` and then unconditionally credits the caller with the returned amount via `accountCapsule.addAssetAmountV2(...)`/`setBalance(...)`, with no check that the exchange pair actually holds that much of the counter-token: [1](#0-0) 

The payout itself is computed by a double-precision "Bancor relay" curve (`Math.pow`/`StrictMath.pow` with an exponent of `2000.0`), a classic source of floating-point rounding/overshoot error at scale: [2](#0-1) 

`ExchangeCapsule.transaction()` is the only place that could reject a payout that exceeds the pair's real reserve (i.e., drives `newFirstTokenBalance`/`newSecondTokenBalance` negative), but that check is gated entirely behind the `hardenedCalc` boolean: [3](#0-2) 

`hardenedCalc` is only `true` when the chain-wide proposal `ALLOW_HARDEN_EXCHANGE_CALCULATION` has been activated: [4](#0-3) 

and that proposal defaults to `0` (disabled) on a fresh/unmigrated chain, per the proposal-validation test that explicitly documents "current value is 0 (default)": [5](#0-4) 

`ExchangeTransactionActuator.doValidate()` also never independently checks `anotherTokenQuant` against the pair's actual `firstTokenBalance`/`secondTokenBalance`; it only checks the caller-supplied slippage floor `tokenExpected`, which an attacker fully controls and can set to `1`: [6](#0-5) 

So, in the default (non-hardened) configuration, nothing in the validate/execute path stops a swap whose computed `buyTokenQuant`/`anotherTokenQuant` (from `exchangeToSupply`/`exchangeFromSupply`'s double arithmetic) exceeds the pair's real counter-token reserve. This is architecturally identical to the Pro Token exploit: an unprivileged, permissionless call into an AMM-style reserve, computed via a formula whose payout is not bounded against the reserve it draws from, allowing the reserve to be pushed underwater/drained by attacker-chosen inputs (repeated or single large `ExchangeTransactionContract` calls), at the expense of the other liquidity participants who deposited real assets via `ExchangeCreateContract`/`ExchangeInjectContract`.

### Impact Explanation
An attacker can extract more of a pair's counter-token than the pair actually backs, creating an unbacked/negative-tracked reserve balance in the `Exchange`/`ExchangeV2` capsule while the attacker's own account is credited real, transferable TRC10/TRX balance via `accountCapsule.addAssetAmountV2`/`setBalance`. Because the accounting isn't checked against the true reserve, this is a theft-of-funds / unbacked-balance condition at the expense of other pool participants (whose deposited principal is diluted or becomes unwithdrawable), reachable purely through a signed `ExchangeTransactionContract` from an ordinary account — no SR/witness/committee privilege required.

### Likelihood Explanation
`ALLOW_HARDEN_EXCHANGE_CALCULATION` defaults to `0`, so the protective invariant check in `ExchangeCapsule.transaction()` is inactive by default. `ExchangeTransactionContract` is a standard, broadcastable transaction type available to any funded account; the only prerequisites are that a pair exists (anyone can create one via `ExchangeCreateContract`) and that the attacker can afford the transaction fee plus whatever token quantity the exploit path requires — both trivially satisfiable by a single unprivileged actor.

### Recommendation
Enforce the reserve-sufficiency invariant (`newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0`, or more strictly `anotherTokenQuant <= availableCounterTokenBalance`) unconditionally inside `ExchangeCapsule.transaction()`/`ExchangeTransactionActuator`, rather than only when `allowHardenExchangeCalculation()` is enabled. Additionally, prefer the `SafeExchangeProcessor` (BigDecimal-based) path unconditionally, or add an explicit reserve-bound check in `doValidate()`/`execute()` independent of the governance toggle so that swap payouts can never exceed the pair's tracked reserve regardless of chain configuration.

### Proof of Concept
1. Create an `Exchange`/`ExchangeV2` pair with `ExchangeCreateContract` (any unprivileged account, e.g. TRX/tokenX with a small `secondTokenBalance`).
2. Do not activate the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal (the default state on any chain since inception).
3. Submit `ExchangeTransactionContract` swaps (via `ExchangeTransactionActuator`) with `tokenQuant`/`tokenExpected` values chosen so that `ExchangeProcessor.exchange()`'s double-precision Bancor relay computation returns a `buyTokenQuant` that is a large fraction of, or exceeds, the pair's actual counter-token reserve (verifiable directly against `ExchangeProcessorTest`/`ExchangeCapsuleTest`, which already show measurable divergence between the double-based and `BigDecimal`-based ("hardened") results for identical inputs, e.g. `testStrictMath` in `framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java`).
4. Because `ExchangeCapsule.transaction()` only checks for a negative post-trade balance when `hardenedCalc` is `true` [7](#0-6) , and `ExchangeTransactionActuator` never separately checks `anotherTokenQuant` against the real reserve, the swap succeeds and credits the attacker's account, leaving the pair's tracked reserve unbacked.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
