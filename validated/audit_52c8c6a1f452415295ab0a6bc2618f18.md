### Title
Unvalidated length field from calldata drives unbounded array allocation in TVM precompiled contracts (BatchValidateSign/ValidateMultiSign) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ModExp`-family and multi-sig precompiled contracts in `PrecompiledContracts.java` decode a "length" word straight out of attacker-supplied TVM calldata and use it, unchecked, to size a Java array before any bound is enforced against the rest of the input. This mirrors the CVE-2017-6349 pattern: a length value taken from untrusted (corrupted) input is fed directly into an allocation routine without validating it against the real size of the surrounding buffer, which can trigger an oversized/negative allocation and a crash.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read `len` from a `DataWord` supplied inside the precompiled-contract call data (`words[offset].intValueSafe()`) and immediately allocate `new byte[len][]`/loop indexing based on it, with no upper bound check against `words.length` or any sane maximum: [1](#0-0) 

`extractSigArray`, used by the multi-signature verification precompile, has the identical pattern — `len` is taken unchecked from calldata and used to allocate `bytesArray` and to index `words[offset + i + 1]`: [2](#0-1) 

The only guard present (`if (offset > words.length - 1)`) validates the *offset* of the length word, not the decoded length value itself, so an attacker can supply a `words[offset]` value up to `Integer.MAX_VALUE` (via `intValueSafe()`), causing `new byte[len][]` to attempt to allocate an object-reference array with billions of entries, or causing the subsequent loop to walk far outside the `words` array bounds.

This is directly analogous to the vim `u_read_undo` bug: a length taken from untrusted/corrupted input is used for allocation sizing without validating it against the real bounds of the source buffer before the allocation happens.

### Impact Explanation
Any account can invoke a smart contract that calls the precompiled contract at the `VALIDATEMULTISIGN`/`BatchValidateSign` address with crafted calldata containing an oversized length word. This forces the TVM executor thread to attempt a huge array allocation (`OutOfMemoryError`) or to walk out of the intended data bounds (`ArrayIndexOutOfBoundsException`). Because this executes inside block/transaction processing on every full node (not just the caller's), an uncaught `OutOfMemoryError`/unexpected exception during precompiled-contract execution can crash the node process or halt transaction processing for that node, i.e., a remotely triggerable denial-of-service against network participants — reachable purely through a normal signed transaction/contract call.

### Likelihood Explanation
Likelihood is high: the precompiled contract is reachable by any unprivileged account through a plain contract call (no special privilege required), and the vulnerable length parsing (`intValueSafe()` without an explicit upper-bound check) is on the direct, unauthenticated call-data parsing path.

### Recommendation
Add an explicit upper bound check on `len` (e.g., cap it to a small constant such as the number of remaining `DataWord` slots, or to a hard maximum count) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating any array, and verify `offset + len` (and any derived indices such as `bytesOffset`) stay within `words.length` before use, mirroring the bounds checks already present elsewhere in the file (e.g., `verifyLength` pattern used in `RLP.java`).

### Proof of Concept
Deploy/call a contract that invokes the VALIDATEMULTISIGN/BatchValidateSign precompiled address with calldata where the length word at the expected offset (e.g., the signature/witness-array count slot consumed by `extractSigArray`/`extractBytesArray`) is set to a very large 256-bit value (e.g., `0x7fffffff`). On execution, `intValueSafe()` returns that large `int`, and `new byte[len][]` attempts to allocate an array of that many byte-array references, exhausting heap and triggering `OutOfMemoryError` inside the TVM execution path on every node that processes the transaction.   private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
