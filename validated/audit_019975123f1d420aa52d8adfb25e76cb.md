### Title
Heap buffer over-read in ijar's central-directory extra-field parser when processing an attacker-supplied JAR/ZIP dependency - (File: third_party/ijar/zip.cc)

### Summary
`java_common.run_ijar` / the Bazel-native `ijar` tool is run over dependency jars (including jars fetched from external registries/mirrors via `http_jar`, `http_file`, or Maven-style rules) to strip them down to interface jars for compilation caching. The bytes of that jar are entirely attacker-controlled if served from a hostile origin, and `ijar` mmaps and parses them directly with raw pointer arithmetic and no checksum/verification step of its own (checksum verification, if any, happens at fetch time in Starlark rules, not inside the ijar C++ parser).

### Finding Description
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses a ZIP/JAR central directory entry directly from the mmap'd input buffer using raw pointer arithmetic (`get_u2le`, `get_u4le`, `get_u8le`) [1](#0-0) . After consuming the fixed-size fields, it reads `file_name_length`, `extra_field_length` and `file_comment_length` directly from the entry, without ever validating these against the remaining size of the mapped file or the declared size of the central directory [2](#0-1) .

The subsequent extra-field loop is the exact analog of `Sass::Prelexer::skip_over_scopes`: it walks a sequence of variable-length "scopes" (extra-field records) bounded only by an internally-declared length, reading a 2-byte tag and a 2-byte size for each record and advancing a raw pointer by `data_size`, with the loop terminating only when the running pointer exactly equals the computed end pointer: [3](#0-2) 
There is no check that `extra_p + 4 <= p` before each `get_u2le` read, and no check that `data_size` does not push `extra_p` past the entry/buffer boundary. If a crafted JAR declares a small `extra_field_length` but the record's `data_size` field is set so that `extra_p += data_size` skips past the true `p` boundary without ever landing exactly on it (or lands beyond the mapped file), the `while (extra_p != p)` loop keeps iterating and calling `get_u2le`/`get_u8le`, which dereference `extra_p` unconditionally — reading past the end of the mmap'd input file. This mirrors the CVE's root cause: a scope-skipping scanner advances a cursor based on attacker-supplied length fields without re-validating against the true buffer end, producing a heap (here, mmap-page) over-read.

Contrast this with the safer `ExtraField::find` helper elsewhere in the codebase, which does perform `start + sizeof(ExtraField) > end` and `start + extra_field->size() > end` checks before dereferencing [4](#0-3)  — showing that the equivalent, safe pattern exists in Bazel's own tooling but is not applied in `ijar`'s central-directory parser.

### Impact Explanation
An out-of-bounds read of adjacent heap/mmap memory can crash the `ijar` worker process (denial of service for that action) or, depending on ASLR/heap layout, leak adjacent memory bytes into decisions that affect stripped output (e.g., corrupted size fields propagate into `*uncompressed_size`/`*compressed_size`/`*offset` when the ZIP64 extra field tag is spuriously matched on garbage memory, potentially corrupting the interface jar). This is a memory-safety violation within a build tool that processes untrusted, network-fetched artifacts.

### Likelihood Explanation
Any project that pulls in Java dependencies from an external HTTP source or registry mirror and applies Bazel's built-in `ijar`/`run_ijar` (used pervasively by `java_library`/`java_import`-style rules to build compile-time interface jars) will run this parser over attacker-controllable bytes. No cooperation from the victim beyond a normal `bazel build` is required, matching the "attacker publishes a malicious dependency artifact" threat model in the report. The only precondition is that the target/registry-served jar reaches an ijar action, which is the default, unconditional code path for compile-jar generation.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry`'s extra-field loop before every dereference: verify `extra_p + 4 <= p` before reading tag/size, verify `extra_p + data_size <= p`, and bound `p` (and the whole central directory entry) against the mapped file's total length before any field is read. Adopt the same pattern already used by `ExtraField::find` in `src/tools/singlejar/zip_headers.h`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test analogous to the ijar-related tests already in `src/tools/singlejar/output_jar_simple_test.cc` [5](#0-4)  can be adapted for `third_party/ijar`: construct a minimal ZIP central directory entry with `extra_field_length` set small (e.g., 4) but embed a fabricated extra-field record inside those 4 bytes whose `payload_size` field causes the computed `next` pointer to overshoot the declared `p` boundary (e.g., `payload_size = 0xfff0`), place this crafted entry at the very end of the mmap'd buffer (so the over-read runs off the mapping), and feed the resulting bytes to the `ijar` binary / `InputZipFile::ProcessNext` via a test harness. Under ASan/valgrind this reproduces a heap-buffer-overflow (read) report originating in the `while (extra_p != p)` loop in `ProcessCentralDirEntry` (third_party/ijar/zip.cc:526-541).

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);

  lh->version(10);
