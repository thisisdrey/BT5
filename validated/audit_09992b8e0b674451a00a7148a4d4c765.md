## Title
Unbounded attacker-controlled `estimated_len` causes integer overflow in `minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` - (File: stackslib/src/net/api/postfeerate.rs)

## Summary
`RPCPostFeeRateRequestHandler::try_parse_request` only validates the HTTP `Content-Length` against `MAX_PAYLOAD_LEN`, not the value of the JSON field `estimated_len`, which is an arbitrary attacker-supplied `u64`. That unvalidated value flows unchanged into `estimate_tx_fee_from_cost_and_length`'s `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` multiplication with no bounds check or checked arithmetic.

## Finding Description
In `try_parse_request` [1](#0-0) , the only length check is on `preamble.get_content_length()` against `MAX_PAYLOAD_LEN` — this bounds the size of the raw HTTP body bytes, not the numeric value the client places inside the JSON `estimated_len` field. The body is then parsed as JSON into `FeeRateEstimateRequestBody { estimated_len: Option<u64>, .. }` [2](#0-1) , and:

```rust
let estimated_len =
    std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64);
``` [3](#0-2) 

takes the max of the attacker-supplied number and the real decoded payload length — so an attacker sending `"estimated_len": 18446744073709551615` (u64::MAX) with a small, valid `transaction_payload` hex string causes `estimated_len` to be `u64::MAX`, well beyond any real transaction size, with no upper-bound clamp against `MAX_PAYLOAD_LEN` or any other cap.

This value is stored on `self.estimated_len` and later passed unchanged to `estimate_tx_fee_from_cost_and_length`:
```rust
let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
``` [4](#0-3) 

This is a plain `*` operator, not `checked_mul`/`saturating_mul`. In a debug build (`overflow-checks` on by default for `dev` profile, which is Rust's default unless explicitly disabled), `u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE` (with `MINIMUM_TX_FEE_RATE_PER_BYTE` > 1) overflows and panics, crashing the thread handling the request. In a release build, the multiplication silently wraps, producing an attacker-steered, meaningless `minimum_fee` value that gets used to override the returned fee estimates in the JSON response.

No authentication is required to hit `/v2/fees/transaction` — this handler serves unauthenticated RPC clients, and the crafted request is a single small HTTP POST.

## Impact Explanation
- Debug/dev builds: a single unauthenticated POST to `/v2/fees/transaction` with an oversized `estimated_len` triggers an arithmetic-overflow panic in the multiplication, crashing the request-handling thread — a remote unauthenticated DoS from one message, repeatable at will.
- Release builds: the multiplication wraps (release builds compile without overflow checks by default), producing a wrapped `minimum_fee`; this corrupts the fee estimate returned to the caller but does not itself corrupt consensus-critical/mempool state (the endpoint is read-only, and no acceptance/relay of transactions occurs here) — this specific effect is lower severity than the debug-build panic.
- Whether this endpoint is compiled in a debug or release configuration in production determines whether the primary impact is a crash (Critical, matching "remote crash/unauthenticated DoS from few messages") or merely a wrapped/incorrect value in an advisory fee-estimate response.

## Likelihood Explanation
No authentication, peer state, or preconditions are required beyond network reachability to a node's RPC port and `POST /v2/fees/transaction` support (fee estimator/cost estimator must be configured on the node, which is a common/default configuration). The attacker cost is a single crafted small JSON body; the check at line 153 only bounds the raw HTTP body length, not the numeric field value, so it does not prevent this. This is trivially repeatable per request.

## Recommendation
Clamp or validate `body.estimated_len` against a sane upper bound (e.g., `MAX_PAYLOAD_LEN` or the node's configured max transaction size) before taking the max with `payload_data.len()`, and use `checked_mul`/`saturating_mul` for `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`, returning an `HttpBadRequest` on overflow rather than panicking or silently wrapping.

## Proof of Concept
```rust
// stackslib/src/net/api/tests/postfeerate.rs (new test)
#[test]
fn test_estimated_len_overflow() {
    let (preamble, contents) = ... // construct minimal valid preamble/body with
    // transaction_payload = "0x00" (valid short hex) and
    // estimated_len: Some(u64::MAX)
    let mut handler = RPCPostFeeRateRequestHandler::new();
    let body_json = serde_json::json!({
        "estimated_len": u64::MAX,
        "transaction_payload": "0x0000000000000000000000000000000000000000"
    });
    let body_bytes = serde_json::to_vec(&body_json).unwrap();
    let result = handler.try_parse_request(&preamble, &captures, None, &body_bytes);
    assert!(result.is_ok()); // parsing succeeds, estimated_len = u64::MAX stored

    // Then, directly call the vulnerable multiplication path:
    let r = std::panic::catch_unwind(|| {
        let _ = u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE; // panics in debug (overflow-checks)
    });
    assert!(r.is_err(), "expected overflow panic in debug build");
}
```
This demonstrates that `try_parse_request` accepts an unbounded `estimated_len` and that the subsequent multiplication in `estimate_tx_fee_from_cost_and_length` at `stackslib/src/net/api/postfeerate.rs:112` panics on overflow in debug builds given no upper-bound guard exists on the parsed value.
