### Title
Unthrottled TVM constant-call execution (`triggerconstantcontract` / `estimateenergy` / `eth_call` / `eth_estimateGas`) allows unauthenticated compute-exhaustion DoS - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
Any anonymous API client can invoke the constant-call family of endpoints (`/wallet/triggerconstantcontract`, `/wallet/estimateenergy`, gRPC `TriggerConstantContract`/`EstimateEnergy`, and JSON-RPC `eth_call`/`eth_estimateGas`) to force the node to run a full TVM execution up to the configured CPU-time budget, without paying any fee or consuming any account resource (energy/bandwidth), because constant calls are execution-only and never broadcast/committed. The only protection is a generic, cost-agnostic QPS/IP rate limiter, not an execution-cost-aware throttle. Flooding these endpoints with maximal-energy, CPU-bound bytecode can exhaust the node's HTTP/RPC worker threads and CPU, denying service to legitimate API/RPC callers — the same bug class as CVE-2019-13967, where an anonymous, computationally expensive "compile" endpoint could be hammered to cause an application outage.

### Finding Description
`Wallet.callConstantContract` runs a `VMActuator` in "constant call" mode for every `triggerconstantcontract`/`estimateenergy` request, executing the full VM without any balance/energy deduction from the caller or bandwidth consumption: [1](#0-0) 

The per-call CPU budget is computed by `VMActuator.calculateCpuLimitInUs`, and for constant calls with the default `constantCallTimeoutMs = 0`, it falls back to `maxCpuTimeOfOneTxMs * cpuLimitInUsRatio`, with `cpuLimitInUsRatio = 1.0` for the `ET_PRE_TYPE` executor type used by constant calls: [2](#0-1) 

Constant calls also get the maximum energy allowance (`maxEnergyLimitForConstant`, default 100,000,000) regardless of the caller's actual account balance or frozen resources: [3](#0-2) [4](#0-3) 

The `estimateEnergy` code path amplifies this further: it performs a binary search over the fee/energy range, re-running the full constant-call VM execution (with internal retries on `OutOfTimeException`) potentially dozens of times per single HTTP/RPC request: [5](#0-4) 

Both `TriggerConstantContractServlet` and `EstimateEnergyServlet` are plain `RateLimiterServlet` subclasses with no dedicated per-endpoint strategy configured by default, so they fall back to the generic default (`QpsRateLimiterAdapter qps=1000`) which is agnostic to the actual CPU cost of the request: [6](#0-5) [7](#0-6) [8](#0-7) 

This mirrors CVE-2019-13967's structure exactly: an expensive server-side operation (there, Solidity/JS compilation; here, full TVM interpretation up to the CPU-time ceiling) reachable via a plain unauthenticated web request, gated only by a generic request-count throttle that has no relationship to the operation's actual resource cost, so "many requests" saturate the worker pool/CPU and produce an application outage.

### Impact Explanation
An attacker who can reach the FullNode's HTTP/gRPC/JSON-RPC surface (no signed transaction, no funded account, no permission needed) can submit concurrent constant-call requests carrying bytecode engineered to spin/loop for the full CPU-time budget on every call. Because:
- each call can consume up to `maxCpuTimeOfOneTx` CPU time,
- `estimateEnergy` multiplies that cost by the binary-search iteration count,
- the default rate limiter only bounds *request count* per IP/globally, not aggregate CPU time,

a moderate volume of concurrent connections can pin all HTTP/RPC worker threads and CPU cores in VM execution, preventing the node from timely servicing legitimate wallet/API/JSON-RPC traffic. This is a node-level denial-of-service against the query surface described in scope ("an API the node can no longer serve"), analogous to the CVE's "application outage."

### Likelihood Explanation
Likelihood is high wherever `supportConstant` is enabled (a common production configuration, since `triggerconstantcontract`/`eth_call` are core read paths used by wallets/dApps): no authentication, signature, funds, or on-chain state is required, and the request cost to the attacker (a small HTTP POST) is far lower than the CPU cost imposed on the node. The `estimateEnergy` variant increases the amplification factor without additional attacker cost, and `estimateEnergy` availability is itself gated by a boolean flag operators must enable for `eth_estimateGas`/`eth_call`-gas-estimation support.

### Recommendation
- Track and cap CPU-time actually consumed by constant-call executions per-IP/per-window (not just request count) so the QPS limiter reflects real cost.
- Apply a stricter, execution-cost-aware default rate limiter (e.g., `IPQPSRateLimiterAdapter` with low QPS, or a semaphore-based `GlobalPreemptibleAdapter`) specifically to `TriggerConstantContractServlet`, `EstimateEnergyServlet`, and their RPC/JSON-RPC equivalents, rather than relying on the generic 1000 QPS default.
- Reduce/bound the number of internal VM re-executions performed per single `estimateEnergy` request, or apply a stricter aggregate deadline across the whole binary search rather than per-iteration.
- Consider running constant-call execution on a bounded, isolated thread pool/queue distinct from block-processing and broadcast-transaction handling so a flood of constant calls cannot starve consensus-critical work.

### Proof of Concept
1. On a FullNode with `vm.supportConstant = true` (a typical production setting), deploy or reuse any contract whose called function executes a CPU-heavy loop (e.g., large iterated hashing/loop opcode sequence) sized to consume close to `maxEnergyLimitForConstant` within `maxCpuTimeOfOneTx`.
2. Fire many concurrent unauthenticated HTTP POSTs to `/wallet/triggerconstantcontract` (or `/wallet/estimateenergy`, or JSON-RPC `eth_call`/`eth_estimateGas`) invoking that function, staying under the default 1000 QPS/IP limiter (`common/src/main/resources/reference.conf` rate.limiter defaults).
3. Observe that concurrent VM executions each occupy a worker thread for up to the configured CPU-time budget (amplified further for `estimateEnergy` by its internal binary-search retries), causing HTTP/RPC latency to spike and legitimate API/RPC calls to time out or be rejected — reproducing an application-outage-style DoS analogous to CVE-2019-13967's `exec.php?...operation=compile` flood.

  public Transaction estimateEnergy(TriggerSmartContract triggerSmartContract,
      TransactionCapsule txCap, TransactionExtention.Builder txExtBuilder,
      Return.Builder txRetBuilder, GrpcAPI.EstimateEnergyMessage.Builder estimateBuilder)
      throws ContractValidateException, ContractExeException, HeaderNotFound, VMIllegalException {

    if (!Args.getInstance().estimateEnergy) {
      throw new ContractValidateException("this node does not support estimate energy");
    }

    if (!Args.getInstance().supportConstant) {
      throw new ContractValidateException("this node does not support constant, "
          + "so estimate energy cannot work");
    }
    int retry = Args.getInstance().estimateEnergyMaxRetry;

    DynamicPropertiesStore dps = chainBaseManager.getDynamicPropertiesStore();
    long high = dps.getMaxFeeLimit();

    Transaction transaction;

    while (true) {
      try {
        transaction = cleanContextAndTriggerConstantContract(
            triggerSmartContract, txCap, txExtBuilder, txRetBuilder, high);
        break;
      } catch (Program.OutOfTimeException e) {
        retry--;
        if (retry < 0) {
          throw e;
        }
      }
    }

    // If failed, return directly.
    if (transaction.getRet(0).getRet().equals(code.FAILED)) {
      txRetBuilder.setCode(response_code.CONTRACT_EXE_ERROR);
      estimateBuilder.setResult(txRetBuilder);
      return transaction;
    }

    long low = dps.getEnergyFee() * txExtBuilder.getEnergyUsed();

    long twoTimes = low * 2;
    if (twoTimes < high) {
      while (true) {
        try {
          transaction = cleanContextAndTriggerConstantContract(
              triggerSmartContract, txCap, txExtBuilder, txRetBuilder, twoTimes);

          if (transaction.getRet(0).getRet().equals(code.FAILED)) {
            low = twoTimes;
          } else {
            high = twoTimes;
          }

          break;
        } catch (Program.OutOfTimeException e) {
          retry--;
          if (retry < 0) {
            throw e;
          }
        }
      }
    }

    while (low + TRX_PRECISION < high) {
      long mid = (low + high) / 2;

      while (true) {
        try {
          transaction = cleanContextAndTriggerConstantContract(
              triggerSmartContract, txCap, txExtBuilder, txRetBuilder, mid);
          break;
        } catch (Program.OutOfTimeException e) {
          retry--;
          if (retry < 0) {
            throw e;
          }
        }
      }

      if (transaction.getRet(0).getRet().equals(code.FAILED)) {
        low = mid;
      } else {
        high = mid;
      }
    }

    // Retry the binary search result
    transaction = cleanContextAndTriggerConstantContract(
        triggerSmartContract, txCap, txExtBuilder, txRetBuilder, high);
    // Setting estimating result
    estimateBuilder.setResult(txRetBuilder);
    if (transaction.getRet(0).getRet().equals(code.SUCESS)) {
      txRetBuilder.setResult(true);
      txRetBuilder.setCode(response_code.SUCCESS);
      estimateBuilder.setEnergyRequired((long) ceil((double) high / dps.getEnergyFee(),
          dps.disableJavaLangMath()));
    }

    return transaction;
  }

  private double getCpuLimitInUsRatio() {

    double cpuLimitRatio;

    if (ExecutorType.ET_NORMAL_TYPE == executorType) {
      // self witness generates block
      if (blockCap != null && blockCap.generatedByMyself
          && !blockCap.hasWitnessSignature()) {
        cpuLimitRatio = 1.0;
      } else {
        // self witness or other witness or fullnode verifies block
        if (trx.getRet(0).getContractRet() == contractResult.OUT_OF_TIME) {
          cpuLimitRatio = CommonParameter.getInstance().getMinTimeRatio();
        } else {
          cpuLimitRatio = CommonParameter.getInstance().getMaxTimeRatio();
        }
      }
    } else {
      // self witness or other witness or fullnode receives tx
      cpuLimitRatio = 1.0;
    }

    return cpuLimitRatio;
  }

  static long calculateCpuLimitInUs(boolean isConstantCall, long maxCpuTimeOfOneTxMs,
      double cpuLimitInUsRatio, long constantCallTimeoutMs) {
    if (isConstantCall && constantCallTimeoutMs > 0L) {
      return constantCallTimeoutMs * VMConstant.ONE_THOUSAND;
    }
    return (long) (maxCpuTimeOfOneTxMs * VMConstant.ONE_THOUSAND * cpuLimitInUsRatio);
  }
