### Title
Unstaked handshake flood exhausts the shared `open_connections` counter and starves staked TPU handshakes - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`ClientConnectionTracker::new` enforces a single global counter (`stats.open_connections`) against `qos.max_concurrent_connections()`, which for `SwQos` is `(max_staked_connections + max_unstaked_connections) * 5 / 4` [1](#0-0) . This admission check runs before any stake-based `try_add_connection` logic and has no per-IP or per-peer-type sub-limit, so an unstaked attacker holding many `Connecting` handshakes open can consume the entire headroom, including the 25% buffer meant for staked overlap, and cause `ClientConnectionTracker::new` to reject legitimate staked handshakes at the same layer.

### Finding Description
`ClientConnectionTracker::new(stats, max_concurrent_connections)` does a single global `fetch_add` on `stats.open_connections` and compares it to `max_concurrent_connections` [2](#0-1) . This counter is incremented as soon as a connection begins its QUIC handshake (before its peer type — staked or unstaked — is known), and is only decremented on `Drop` of the tracker, i.e., once the connection is fully closed/dropped. There is no field distinguishing staked vs unstaked in this check, and no per-source cap enforced at this stage.

`max_concurrent_connections()` for `SwQos` is computed as `(max_staked_connections + max_unstaked_connections) * 5 / 4`, explicitly documented as "Allow 25% more connections than required to allow for handshake" [1](#0-0) . The stake-aware admission control (`SwQos::try_add_connection`, which separates staked vs. unstaked connection tables and applies `max_staked_connections`/`max_unstaked_connections` limits per table) only runs *after* `ClientConnectionTracker::new` has already succeeded [3](#0-2) .

Because `ClientConnectionTracker::new`'s check is peer-type-agnostic and per-source unbounded, an unstaked attacker can open connections (holding them in the `Connecting` state, i.e. before handshake completion, since the tracker is created at connection-accept time prior to peer-type determination) up to `max_concurrent_connections()`. This consumes not just the `max_unstaked_connections` share but also the entire 25% headroom that was intended to accommodate simultaneous staked handshake overlap. Once `stats.open_connections >= max_concurrent_connections()`, any subsequent connection attempt — staked or not — fails at `ClientConnectionTracker::new` and is refused before `SwQos::try_add_connection`'s stake-based admission logic ever executes, meaning stake-weighted QoS cannot rescue a legitimate staked handshake at this stage.

### Impact Explanation
This is a TPU-port handshake-layer denial-of-service: an unstaked attacker with no stake can hold enough concurrent connection attempts open to push `stats.open_connections` to `max_concurrent_connections()`, causing legitimate staked validators/senders' QUIC handshakes to be refused (`ClientConnectionTracker::new` returning `Err(())`) purely due to the shared, peer-type-blind global counter — before the staked/unstaked connection tables and per-peer-type limits in `SwQos::try_add_connection` are consulted. This matches the "QoS evasion" / connection-admission-bypass bounty category: an unprivileged actor can deny leader capacity intended to be reserved (via the 25% headroom) for staked peers, blocking legitimate staked transaction ingress into the TPU pipeline and, transitively, PoH recording.

### Likelihood Explanation
Feasible with a single unstaked IP capable of establishing many simultaneous QUIC connection attempts (bounded only by OS/socket limits, not by any additional per-IP cap enforced prior to `ClientConnectionTracker::new`). The attack requires no stake, no keys, no validator/leader control — purely opening raw QUIC connections to the public TPU port, which is explicitly in the described attacker capability. The condition persists as long as the attacker keeps enough handshakes in flight (not completing them, so `Drop` never fires to decrement the counter), making it easily repeatable and sustainable with modest concurrent connection counts (only `max_concurrent_connections()`, which for defaults is a bounded, computable number).

### Recommendation
Enforce per-source (or per-unstaked-pool) sub-limits before/within `ClientConnectionTracker::new`, e.g., cap the number of concurrently in-flight (pre-handshake-complete) unstaked connections separately from the shared headroom, or reserve a fraction of `max_concurrent_connections()` exclusively for peer-type-unknown/staked-candidate connections so unstaked traffic cannot consume the full 25% buffer. Alternatively, defer the global `stats.open_connections` increment/check until after a lightweight peer-type classification (e.g., TLS client cert / pubkey check) so unstaked and staked headroom can be tracked and limited independently.

### Proof of Concept
Integration test plan (in `streamer/src/nonblocking/quic.rs` or `swqos.rs` test modules):
1. Configure `SwQosConfig` with small `max_staked_connections` and `max_unstaked_connections` (e.g., 2 and 2), so `max_concurrent_connections() == 5`.
2. From a single unstaked test client IP, open 5 concurrent QUIC `Connecting` futures against the test QUIC server without completing the handshake (hold each `connecting.await` pending, or complete transport but delay stream-based classification), asserting all 5 succeed in incrementing `stats.open_connections` via `ClientConnectionTracker::new`.
3. Concurrently attempt one additional connection from a distinct, properly staked client (using `get_connection_stake`-recognized pubkey/stake in `staked_nodes`).
4. Assert that this staked connection attempt fails at `ClientConnectionTracker::new` (i.e., `stats.connection_add_failed` or equivalent refusal counter increments) even though `staked_connection_table.total_size < max_staked_connections`, proving that stake-based admission in `SwQos::try_add_connection` never gets a chance to run because the shared headroom was exhausted purely by unstaked connections.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
