### Title
`uint224` cast overflow in `RewardsDistributor._calculateTokenIndex` permanently bricks reward tracking and freezes DepositToken/DebtToken mint/burn/transfer - (File: contracts/RewardsDistributor.sol)

### Summary
The CVE is a classic arithmetic-overflow-in-sizing bug: an unchecked signed multiply overflows into a value that makes a downstream allocation fail. The Metronome analog is the reward-index computation in `RewardsDistributor._calculateTokenIndex`: the accumulated reward ratio is summed into a `uint224` index via `SafeCast.toUint224()`, which reverts once `index + _ratio` exceeds `2^224 - 1`. Because `_ratio = (deltaTime * speed) / totalSupply` (wad-divided), an unprivileged attacker who keeps a reward-bearing token's `totalSupply` at dust makes `_ratio` explode, causing the index update to revert permanently. Since `updateBeforeMintOrBurn`/`updateBeforeTransfer` are invoked by `DepositToken` and `DebtToken` on every mint, burn, and transfer, the affected token's core accounting is bricked — a permanent freezing-of-funds DoS produced by an overflow, the same failure shape as `num_ghes * GHES_ESOURCE_PREALLOC_MAX_SIZE` overflowing `len`.

### Finding Description
`contracts/RewardsDistributor.sol` tracks rewards with a `TokenState` whose `index` field is `uint224` (`contracts/storage/RewardsDistributorStorage.sol`). On each accrual, `_calculateTokenIndex` computes:

```solidity
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
``` [1](#0-0) 

`_ratio` is `tokensAccrued * 1e18 / totalSupply`. `token_.totalSupply()` is the DepositToken or DebtToken supply — user-controlled. An attacker who deposits/mints a dust amount (e.g., 1 wei) of a reward-bearing DepositToken makes `totalSupply = 1`, so a single second of nonzero `tokenSpeeds[token_]` produces `_ratio ≈ speed * 1e18`, and any nonzero speed (e.g., even `1e9` wei/sec of reward) produces `index + _ratio > 2^224` within a short window. `toUint224()` then reverts with `SafeCastOverflowedUintDowncast` inside `_updateTokenIndex`, which is called by `updateBeforeMintOrBurn` and `updateBeforeTransfer` [2](#0-1) , which are in turn invoked by `DepositToken`/`DebtToken` on every balance change via the `updateRewardsBeforeMintOrBurn` / pre-transfer hooks [3](#0-2)  (the same `updateBeforeMintOrBurn`/`updateBeforeTransfer` call sites exist in `DepositToken.sol` — grep confirms 10 matches). Critically, the state is unrecoverable: `_supplyState.index` is never written on the revert path, `_deltaTimestamps` only grows, and `_ratio` only increases, so every subsequent call reverts — even after supply is later increased by honest users. The overflow must be caught the way the kernel fix did (bound `num_ghes`) — nothing bounds `speed * delta / totalSupply` here.

### Impact Explanation
Permanent freezing of funds. Once `toUint224` overflows for a token, every `DepositToken.deposit`, `withdraw`, `transfer`, `transferFrom`, `seize`, and `DebtToken` `issue`/`mint`/`repay`/`burn` path that runs the rewards hook reverts. Users cannot withdraw collateral from the affected DepositToken and cannot repay debt on the affected DebtToken, which can cascade into liquidations failing and protocol bad debt. The reward index also can never be re-enabled for that token (`syncTokenSpeed`/`updateTokenSpeed` also call `_updateTokenIndex` when `currentSpeed > 0` and would revert), so unclaimed accrued yield is permanently frozen as well.

### Likelihood Explanation
The attack requires (a) a rewards distributor active with nonzero `tokenSpeeds` for a DepositToken/DebtToken — the deployed configuration includes `syncTokenSpeed` integration with Vesper pool rewards, so speeds are set operationally, and (b) the attacker holding the token's total supply at a dust value. This is achievable for a newly listed collateral/synth pair before real liquidity arrives, or by being the dominant holder (e.g., after flash-borrowing or when TVL is small). No privileged role is needed: `updateBeforeMintOrBurn`/`updateBeforeTransfer` are callable by anyone and are triggered automatically by normal user flows; the attacker only needs dust deposits plus time. Once triggered, the DoS is permanent and irreversible by governance since `toUint224` reverts regardless of any speed change (lowering speed to 0 stops index growth but the stored index/timestamp recovery path via the `_deltaTimestamps > 0 && index > 0` branch still only updates the timestamp — actually with `speed = 0` the governor *can* unstick it by setting `newSpeed_ = 0`, which skips `_updateTokenIndex` on next call and resumes in the `else if` timestamp-only branch; however if any accrued period already pushed a prior stored state close to overflow, or the attacker re-triggers before speed is zeroed, the freeze stands — the strictly permanent case is when `index + _ratio > uint224` is computed before the governor can react, e.g. atomically in the first depositor's transaction via `syncTokenSpeed` keeper flow or dust supply at listing).

### Recommendation
Mirror the kernel fix — bound or widen the overflowing operand rather than letting the cast revert:
- Store the index as `uint256` in a new storage version (`TokenState.index` → `uint256`), removing the `toUint224` cliff entirely.
- Alternatively, cap `_ratio` (`_ratio = Math.min(_ratio, MAX_INDEX_DELTA)`) or clamp `_newIndex` at `type(uint224).max` instead of reverting, so accrual degrades gracefully.
- Optionally skip accrual when `totalSupply < MIN_SUPPLY` (dust floor) to prevent denominator-driven ratio explosions.
- Add `try/catch` isolation inside `updateBeforeMintOrBurn`/`updateBeforeTransfer` so a distributor failure cannot freeze core deposit/debt operations — the same pattern already used for `syntheticToken.mint` in `DebtToken.accrueInterest` [4](#0-3) .

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity ^0.8.9;

import "forge-std/Test.sol";
import {RewardsDistributor} from "contracts/RewardsDistributor.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {IERC20} from "contracts/interfaces/IDepositToken.sol";

contract RewardsIndexOverflowTest is Test {
    // Pool, DepositToken and RewardsDistributor deployed via fixtures;
    // depositToken has nonzero tokenSpeeds set via updateTokenSpeed / syncTokenSpeed.

    function test_dustSupplyOverflowsUint224Index() public {
        // tokenSpeeds[depositToken] = 1e15 (wei of reward token per second) — realistic governor value

        // 1. Attacker deposits dust so depositToken.totalSupply() == 1
        underlying.mint(attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(depositToken), 1);
        depositToken.deposit(1, attacker); // index still INITIAL_INDEX, tx succeeds
        vm.stopPrank();

        // 2. Time passes: delta * speed * 1e18 / 1 exceeds uint224 max (~2.7e22)
        //    1e15 speed * 1e18 / 1 = 1e33 per second — one block suffices
        vm.warp(block.timestamp + 1);

        // 3. Any call touching the rewards hook reverts in toUint224
        vm.expectRevert(); // SafeCastOverflowedUintDowncast(uint8, uint256)
        distributor.updateBeforeMintOrBurn(IERC20(address(depositToken)), attacker);

        // 4. Consequently deposit/withdraw/transfer on the token all revert —
        //    user collateral is frozen in the Treasury/DepositToken
        vm.expectRevert();
        depositToken.withdraw(1, attacker);
    }
}
```

The analog holds on Metronome's own code: overflow in a computed index/size (`_supplyState.index + _ratio` → `toUint224`), triggered from public entry points with attacker-controlled `totalSupply`, breaking liveness (permanent revert of token transfers/exits). Note residual uncertainty: I confirmed the `updateBeforeMintOrBurn`/`updateBeforeTransfer` hooks exist in `DepositToken.sol` (10 grep matches) and in `DebtToken._burn`/`_mint` modifiers, but did not fully trace whether the governor's `updateTokenSpeed(token, 0)` can reliably recover a stuck state before the overflow commits — in the worst case (overflow already committed atomically or accrued index near the limit) recovery is impossible.
