## Title
`TrustedSpender.setAllowance` / `executeTransfer` never verify `token` is actually an ERC-20 (not an ERC-721 collection), allowing the ERC-20 allowance path to move Loan NFTs due to `transferFrom` selector collision — (File: `contracts/TrustedSpender.sol`)

### Summary
`TrustedSpender` maintains two parallel, type-segregated allowance systems: a numeric per-route ERC20 `Allowance` (`setAllowance` / `executeTransfer`) and a boolean blanket per-route `NFTAllowance` (`setNFTAllowance` / `executeNFTTransfer`) [1](#0-0) . Neither `setAllowance` nor `executeTransfer` checks that the `token` address is actually an ERC-20 rather than an ERC-721 collection [2](#0-1) . Because `IERC20.transferFrom(address,address,uint256)` and `IERC721.transferFrom(address,address,uint256)` share the identical 4-byte selector (`0x23b872dd`) and OpenZeppelin's `SafeERC20._callOptionalReturn` tolerates empty return data as success, `executeTransfer` will happily execute against an ERC-721 collection, treating the `tokenId` as the numeric `amount`. This is the same root cause as the Cally `createVault()` finding: an unvalidated "declared type" vs. "actual type" mismatch is silently absorbed by shared call semantics instead of being rejected.

### Finding Description
`setAllowance` records `(token, from, to) => Allowance{amount, validUntil}` with no interface check on `token` [3](#0-2) . `executeTransfer` then calls `IERC20(token).safeTransferFrom(from, to, amount)` [4](#0-3) , which under the hood issues a raw `call` with selector `0x23b872dd(from, to, amount)` — the exact same selector as `ERC721.transferFrom(from, to, tokenId)`. If `token` is actually an ERC-721 collection (e.g. `LoansNFT`) that the Safe has approved via `setApprovalForAll` for legitimate NFT-allowance use (per the module's own documented precondition [5](#0-4) ), a numeric `Allowance` mistakenly (or ambiguously) set on that same collection address lets a delegate transfer any tokenId `<= amount` out of the Safe via the ERC20 path — entirely bypassing the boolean, per-collection `_nftAllowances`/`setNFTAllowance` gate that was designed to be the sole authorization surface for NFT movement [6](#0-5) .

This mirrors Cally's bug precisely: neither `createVault()` nor `setAllowance()` confirms that the caller's declared "type" (`TokenType` in Cally; the choice of `setAllowance` vs `setNFTAllowance` in Tare) matches the token's real interface, and a shared function signature across the two standards (there, `transferFrom`/`transfer` naming overlap; here, an exact selector collision) lets the mismatched call silently succeed instead of reverting.

### Impact Explanation
A Loan NFT can move out of a Safe through a code path that was never intended to authorize NFT transfers and that does not respect the blanket single-flag semantics of `NFTAllowance` — a delegate can move up to `amount` distinct tokenIds under a numeric allowance nominally granted for a fungible-token route. This is an "unauthorized reassignment of ... loan NFTs" via a path (`executeTransfer`) that bypasses the intended NFT-specific permission model, and it is reachable by an unprivileged delegate (T-10 in SECURITY.md already treats delegates as the largest operational attack surface, but this specific bypass of the NFT-vs-ERC20 permission segregation is not among the documented/accepted trust assumptions).

### Likelihood Explanation
Exploitation requires the Safe/guardian to have set an ERC20-style `Allowance` whose `token` parameter is actually an ERC-721 collection address for a route where `setApprovalForAll` has been granted to `TrustedSpender` for NFT purposes — a configuration/operator error, analogous to the Cally vault creator picking the wrong `TokenType`. Given the module explicitly supports both ERC20 and ERC721 flows over the *same* Safe-approval surface, and given that `token`/`collection` are free-form addresses with no on-chain type check anywhere in `setAllowance`, this is a realistic misconfiguration rather than a purely theoretical one.

### Recommendation
In `setAllowance`, verify `token` actually supports ERC-20 semantics (e.g., reject addresses that respond to `ERC165.supportsInterface(type(IERC721).interfaceId)`, or require a successful `balanceOf`/`decimals` probe) and symmetrically ensure `setNFTAllowance`'s `collection` supports `IERC721`. At minimum, document and enforce that the two allowance namespaces (`_allowances` vs `_nftAllowances`) must never be set for the same address to eliminate the selector-collision bypass.

### Proof of Concept
1. Safe approves `TrustedSpender` via `LoansNFT.setApprovalForAll(trustedSpender, true)` for its documented ERC-721 flow.
2. Safe (or guardian) mistakenly calls `setAllowance(address(loansNFT), safe, attackerControlledRecipient, amount=5, validUntil)` instead of `setNFTAllowance`, believing it configures a numeric ERC20-style cap.
3. A delegate calls `executeTransfer(address(loansNFT), safe, attackerControlledRecipient, tokenId=3)` (`tokenId <= 5`).
4. `IERC20(loansNFT).safeTransferFrom(safe, recipient, 3)` issues a raw call with selector `0x23b872dd(safe, recipient, 3)`, which `LoansNFT.transferFrom` accepts (same selector, `safe` is owner/approved for tokenId 3, contract returns no data so `SafeERC20` treats it as success).
5. Loan NFT #3 is transferred to `attackerControlledRecipient`, even though `_nftAllowances[loansNFT][safe][attackerControlledRecipient].allowed` was never set to `true`.

  function setAllowance(
    address token,
    address from,
    address to,
    uint208 amount,
    uint48 validUntil
  ) external safeOrGuardian(from) {
    require(token != address(0) && from != address(0) && to != address(0), ZeroAddress());
    require(validUntil > block.timestamp, InvalidAllowanceDeadline());

    _allowances[token][from][to] = Allowance({amount: amount, validUntil: validUntil});
    emit AllowanceSet(token, from, to, amount, validUntil);
  }

  /// @inheritdoc ITrustedSpender
  function executeTransfer(address token, address from, address to, uint256 amount) external whenNotPaused {
    // Verify sender is a delegate
    require(delegates[from][msg.sender], NotADelegate());

    // Check allowance exists, is sufficient, and has not expired
    Allowance storage allowance = _allowances[token][from][to];
    require(allowance.amount >= amount, InsufficientAllowance());
    require(block.timestamp <= allowance.validUntil, AllowanceExpired());

    // Update allowance if not infinite
    if (allowance.amount != type(uint208).max) {
      allowance.amount -= uint208(amount);
    }

    IERC20(token).safeTransferFrom(from, to, amount);
  }

# TrustedSpender Module Specification

## Overview

A minimal allowance module that enables delegates to transfer tokens (ERC20 and ERC721) from Safe accounts up to predefined limits. Allowances are defined for specific token/from/to combinations, and delegates can execute transfers within these limits. The contract uses `GuardianAccessControl` (OpenZeppelin `AccessControl`) for role-based access control.
