### Title
Unbounded numeric-token BigInteger parsing in `JsonFormat.merge` causes quadratic-time CPU DoS on unauthenticated `/wallet/*` transaction-construction endpoints - (File: `framework/src/main/java/org/tron/core/services/http/JsonFormat.java`)

### Summary
Every HTTP servlet that builds a broadcastable transaction/contract from a JSON POST body (e.g. `FreezeBalanceServlet`, `FreezeBalanceV2Servlet`, `CreateAssetIssueServlet`, `DelegateResourceServlet`, `ExchangeCreateServlet`, `CreateWitnessServlet`, and dozens of others) parses the request body with `JsonFormat.merge(...)`, which uses `JsonFormat.Tokenizer` to lex JSON scalar values and `JsonFormat.parseInteger` to convert numeric tokens into protobuf `int64`/`uint64` fields. The tokenizer's numeric-token regex has no length cap, and `parseInteger` falls back to `new BigInteger(numberText, radix)` whenever the token is 16+ characters. `java.math.BigInteger`'s string constructor is quadratic-time in the digit count, exactly the CWE-1333/CWE-407 bug class described in the Gitea advisory (an unbounded attacker string driving a quadratic parser). Since the HTTP body cap is 4 MiB (`HttpService.maxRequestSize`), a single unauthenticated POST containing one oversized numeric literal in an `int64` field can drive multi-megabyte `BigInteger` construction, pinning a CPU core for a very long time per request.

### Finding Description
`JsonFormat.Tokenizer.TOKEN` matches numbers with an unbounded possessive quantifier: [1](#0-0) 

`parseInteger` (invoked by `parseInt64`/`parseUInt64` for any int64/uint64 protobuf field encountered during `merge`) only special-cases short numbers (<16 chars); anything longer goes straight into the JDK's `BigInteger(String, int)` constructor with no upper bound on `numberText.length()`: [2](#0-1) 

This is the same primitive the maintainers already recognized and defensively patched in the JSON-RPC layer — `JsonRpcApiUtil.parseBlockNumber` explicitly caps input length "before BigInteger parsing, whose cost grows quadratically with length": [3](#0-2) 

However, that guard was applied only to the JSON-RPC (`eth_*`) surface. The legacy `/wallet/*` HTTP JSON surface, which parses arbitrary user-supplied JSON directly into protobuf transaction contracts via `JsonFormat.merge`, has no equivalent length guard on numeric tokens. `merge` is called from essentially every contract-construction servlet, e.g.: [4](#0-3) 
(and identically in `CreateAssetIssueServlet`, `DelegateResourceServlet`, `ExchangeCreateServlet`, `CreateWitnessServlet`, `FreezeBalanceV2Servlet`, etc., all of which call `JsonFormat.merge` on the raw request body before building the contract).

The only global guard present is `HttpService.maxRequestSize` (4 MiB) enforced by Jetty's `SizeLimitHandler`, which bounds the *total* request but not any individual field: [5](#0-4) 

So an attacker can place nearly the full 4 MiB budget into a single numeric field (e.g. `frozen_balance`, `amount`, `total_supply`), and the quadratic `BigInteger` constructor runs against ~4×10^6 digits — dramatically more expensive per request than the 1 MiB `Accept-Language` payload in the Gitea PoC (which produced ~2 seconds of CPU burn).

### Impact Explanation
A single unauthenticated (no auth/API key required on the default full-node HTTP API) POST request can pin a CPU core for a substantial period per request; concurrent requests from a handful of clients can saturate all cores of a public full node, denying service to legitimate transaction broadcasters and API consumers — matching the "node crash or halt" / "API the node can no longer serve" acceptance criteria. Because the field is parsed before any signature/business-logic validation, this is reachable by literally any HTTP client, with no funds or authentication required.

### Likelihood Explanation
High. The `/wallet/*` HTTP API is exposed by default on full nodes and typically internet-facing (mirroring the Gitea scenario of "self-hosted installations published to the public internet"). No authentication, valid signature, or funded account is needed — the malicious field is parsed by `JsonFormat.merge` before the transaction is validated or executed, so the attacker only needs a well-formed JSON body with one oversized digit string in an int64/uint64-mapped field.

### Recommendation
Add a length ceiling on the numeric token before it reaches `Long.parseLong`/`new BigInteger(...)` inside `JsonFormat.parseInteger` (e.g., reject tokens longer than ~20-25 characters, mirroring the pattern already used in `JsonRpcApiUtil.parseBlockNumber`/`parseTxIndex`), or bound the `TOKEN` regex's numeric branch length in `JsonFormat.Tokenizer`. This should be applied uniformly to the `JsonFormat` merge path used by all `/wallet/*` HTTP servlets, not only the JSON-RPC layer.

### Proof of Concept
Send a POST request to any contract-construction endpoint that parses JSON via `JsonFormat.merge`, e.g. `/wallet/freezebalance`, with an `int64` field padded to consume most of the 4 MiB body limit:
```
POST /wallet/freezebalance HTTP/1.1
Content-Type: application/json
Content-Length: <~4000000>

{"owner_address":"41abd4b9367799eaa3197fecb144eb71de1e049abc",
 "frozen_balance": <~4,000,000-digit decimal literal>,
 "frozen_duration": 3}
```
This request stays under `HttpService.maxRequestSize` and is accepted by Jetty, but drives `JsonFormat.merge` → `Tokenizer` → `parseInteger` → `new BigInteger(numberText, 10)` on a multi-million-digit string, burning substantial CPU per request before any signature check or business validation occurs.

Note: I was not able to directly execute this PoC or measure exact wall-clock CPU cost in this environment (no code execution available here); the analysis is based on static code inspection of `JsonFormat.java`, `HttpService.java`, and the analogous already-patched guard in `JsonRpcApiUtil.java`. A background Devin session with build/execution access would be needed to empirically confirm the exact CPU-time blowup curve for this specific JDK's `BigInteger` implementation.
