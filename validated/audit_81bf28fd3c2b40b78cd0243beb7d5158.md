### Title
Per-repository concurrency limiter uses unnormalized `RelativePath` as lock key, allowing quota duplication via equivalent path spellings - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
Gitaly's per-repository RPC concurrency limiter (`max_per_repo`) derives its lock/queue key directly from the raw, attacker-supplied `Repository.RelativePath` field of the incoming request, before that path has been canonicalized by the storage locator. Because several different string spellings of a relative path resolve to the identical on-disk repository (e.g. `"repo.git"`, `"repo.git/"`, `"repo.git//"`, `"./repo.git"`, `"a/../repo.git"`), a client can present the same repository under multiple distinct lock keys. Each distinct key gets its own independent `max_per_repo` semaphore/queue, so the effective concurrency limit for a single repository can be multiplied by simply varying how the path is spelled in each request — mirroring the reported bug class where the same underlying voting power was recognized twice because the mechanism keyed on a movable/duplicable representation instead of the canonical identity.

### Finding Description
The concurrency limiter's lock key function is: [1](#0-0) 

`LimitConcurrencyByRepo` returns `info.Repository.GetRelativePath()` verbatim — the value taken from the gRPC request's `Repository` message via `requestinfohandler.Extract`, prior to any of Gitaly's storage-path validation/normalization logic running.

That normalization logic lives in the storage locator and is only invoked later, inside the actual RPC handler when it resolves the repository to a filesystem path: [2](#0-1) 

`ValidateRelativePath` demonstrably treats multiple distinct input strings as the same repository, as shown by its own test table: [3](#0-2) 

For example `"subfolder"`, `"subfolder/"`, and `"subfolder//"` all clean to `"subfolder"`, and `"subfolder/.."` cleans to `"."`. `GetRepoPath` performs this validation and then joins the *raw* `relativePath` (not the cleaned one) onto the storage path: [4](#0-3) 

Because the limiter's `getLockKey` call happens in the gRPC interceptor chain before the RPC handler resolves/validates the path, the limiter never sees the canonicalized identity — it only sees whatever string the client sent in the request. An unprivileged client that has access to run RPCs against a given repository (e.g. via push/fetch/clone or any RPC that carries a `Repository` field) can therefore issue concurrent requests using several equivalent-but-differently-spelled `RelativePath` values (trailing slash, repeated slash, `./` prefix, `subdir/..`) that all resolve to the exact same physical repository, yet are treated as different `limitingKey` values by `ConcurrencyLimiter.Limit`: [5](#0-4) 

Each unique spelling gets its own independent semaphore of size `MaxPerRepo`, so the real number of concurrent in-flight requests against the physical repository can exceed the configured limit by a multiple equal to the number of distinct spellings used — directly analogous to the veNFT bug where the same underlying stake was recognized (and thus double-counted) under two different addresses because the counting mechanism keyed on a mutable representation instead of the canonical underlying resource.

### Impact Explanation
This undermines the backpressure/DoS-protection mechanism documented for Gitaly: [6](#0-5) 

`max_per_repo` and `max_queue_size`/`max_queue_wait` exist specifically to prevent a single repository (e.g. a very large repo, or a "hot" repo under load) from exhausting Gitaly's I/O/CPU resources through excessive concurrent RPCs such as `PostUploadPackWithSidechannel`. If the key derivation can be trivially bypassed by spelling the same relative path differently, an attacker can defeat this safeguard and drive up concurrent resource-heavy operations (clones/fetches/uploads) against one repository well beyond the administrator-configured cap, leading to resource exhaustion / denial of service on the Gitaly node — this falls squarely under the accepted "DoS of a handler" / "RPC-handler resource limits" bug class.

### Likelihood Explanation
Likelihood is high for the following reasons:
- The `Repository.RelativePath` field is attacker-influenceable in essentially every Gitaly RPC that touches a repository (clone, fetch, push-related RPCs, etc.), since it's part of the standard `Repository` protobuf message clients construct.
- No authentication bypass or privileged access is required — any client permitted to call rate-limited RPCs against a repository can vary the path spelling.
- The normalization behavior gap is proven by existing first-party test vectors in `locator_test.go` showing several inputs canonicalize to the same path, confirming the "different key, same repository" precondition holds in this codebase.
- The only uncertainty (not fully confirmed due to tool-call limits) is the exact code path of `requestinfohandler.Extract`, i.e., whether it performs any additional path cleaning before storing `info.Repository`. Based on the middleware ordering (limiter interceptor runs generically over all RPCs before service-specific handler logic that calls `locator.GetRepoPath`/`ValidateRelativePath`), and the fact that `LimitConcurrencyByRepo` calls `GetRelativePath()` directly on the extracted repository without any visible cleaning step, it's likely no normalization occurs at this stage — but this should be verified against `requestinfohandler.go`'s implementation before treating the PoC below as final.

### Recommendation
Normalize (e.g. via `filepath.Clean`, or ideally the same `storage.ValidateRelativePath` logic) the `RelativePath` (and `StorageName`) before using it as the concurrency-limiter lock key in `LimitConcurrencyByRepo`, so that all equivalent spellings of the same repository path collapse to a single canonical key prior to acquiring the per-repo semaphore.

### Proof of Concept
Conceptual PoC (concurrency-limiter bypass):
1. Configure `[[concurrency]] rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel" max_per_repo = 1`.
2. As an ordinary client with access to repository `group/project.git`, issue N concurrent `PostUploadPackWithSidechannel` (or any rate-limited RPC) requests, each with a `Repository.RelativePath` value that resolves to the same on-disk path but is spelled differently, e.g.:
   - `"group/project.git"`
   - `"group/project.git/"`
   - `"group/project.git//"`
   - `"./group/project.git"`
   - `"group/other/../project.git"`
3. Because `LimitConcurrencyByRepo` (`internal/grpc/middleware/limithandler/middleware.go:18-25`) uses each raw string as a distinct `limitingKey`, each spelling gets its own independent semaphore of size 1, allowing N concurrent in-flight requests against the same physical repository instead of the configured 1 — analogous to the referenced report's `X`/`Y` contracts each independently minting/using voting power for the same underlying veNFT by presenting it through a different address.

Note: this PoC is derived from static code review; dynamic confirmation (running the interceptor chain end-to-end with two differently-spelled but path-equivalent `RelativePath` values) was not performed within the available tool budget and is recommended before treating this as fully proven.

// LimitConcurrencyByRepo implements GetLockKey by using the repository path as lock.
func LimitConcurrencyByRepo(ctx context.Context) string {
	if info := requestinfohandler.Extract(ctx); info != nil {
		return info.Repository.GetRelativePath()
	}

	return ""
}

// ValidateRelativePath validates a relative path by joining it with rootDir and verifying the result
// is either rootDir or a path within rootDir. Returns clean relative path from rootDir to relativePath
// or an ErrRelativePathEscapesRoot if the resulting path is not contained within rootDir.
func ValidateRelativePath(rootDir, relativePath string) (string, error) {
	absPath := filepath.Join(rootDir, relativePath)
	if rootDir != absPath && !strings.HasPrefix(absPath, rootDir+string(os.PathSeparator)) {
		return "", ErrRelativePathEscapesRoot
	}

	return filepath.Rel(rootDir, absPath)
}

// GetRepoPath returns the full path of the repository referenced by an RPC Repository message.
// By default, it verifies that the path is an existing git directory. However, if invoked with
// the `GetRepoPathOption` produced by `WithRepositoryVerificationSkipped()`, this validation
// will be skipped. The errors returned are gRPC errors with relevant error codes and should be
// passed back to gRPC without further decoration.
func (l *configLocator) GetRepoPath(ctx context.Context, repo storage.Repository, opts ...storage.GetRepoPathOption) (string, error) {
	var cfg storage.GetRepoPathConfig
	for _, opt := range opts {
		opt(&cfg)
	}

	var validationOptions []storage.ValidateRepositoryOption
	if cfg.SkipRepositoryVerification {
		validationOptions = []storage.ValidateRepositoryOption{
			storage.WithSkipRepositoryExistenceCheck(),
		}
	}

	if err := l.ValidateRepository(ctx, repo, validationOptions...); err != nil {
		return "", err
	}

	storagePath, err := l.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", err
	}
	relativePath := repo.GetRelativePath()

	return filepath.Join(storagePath, relativePath), nil
}

func (c *ConcurrencyLimiter) Limit(ctx context.Context, limitingKey string, f LimitedFunc) (interface{}, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"limiter.ConcurrencyLimiter.Limit",
		[]attribute.KeyValue{
			attribute.String("key", limitingKey),
		},
	)
	defer span.End()

	if c.currentLimit() <= 0 {
		return f()
	}

	sem := c.getConcurrencyLimit(limitingKey)
	defer c.putConcurrencyLimit(limitingKey)
