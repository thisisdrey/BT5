## Title
Heap buffer over-read via missing `attr_count()` bounds check when reading Zip64 extra-field attributes - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`Zip64ExtraField::attr64(int index)` indexes into a variable-length `attr_[]` array using a hardcoded index derived from which 32-bit size/offset fields are `0xFFFFFFFF`, without ever checking that `index < attr_count()` (i.e., that the field's declared `payload_size()` actually contains that many 8-byte slots).

### Finding Description
`ExtraField::find()` [1](#0-0)  only validates that a candidate extra-field record fits within the `[start, end)` window of the `extra_fields` buffer (i.e. `start + sizeof(ExtraField) + payload_size() <= end`). It does not validate that `payload_size()` is large enough for the number of 64-bit attributes the *caller* is about to read.

Callers such as `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and `LH::compressed_file_size()/uncompressed_file_size()` compute a fixed attribute index from the 32-bit fields that read `0xFFFFFFFF` and then call `z64->attr64(index)` directly: [2](#0-1) [3](#0-2) [4](#0-3) .

`attr64()` itself performs no bounds check against `attr_count()`: [5](#0-4) .

So a Central Directory Header or Local Header entry can set `compressed_file_size32 = 0xFFFFFFFF` and `uncompressed_file_size32 = 0xFFFFFFFF` (forcing `attr_no = 1` or higher) while attaching a Zip64 extra field whose `payload_size` is only 8 bytes (one attribute, `attr_count() == 1`). `ExtraField::find()` will accept this record as valid because it only checks that the declared 4+8=12-byte record fits in the extra-fields buffer — it never checks that `index (1) < attr_count() (1)`. The subsequent `attr64(1)` read then dereferences 8 bytes starting immediately after the one valid attribute, which is out of the extra field's own declared bounds and, depending on layout, may run past the end of the memory-mapped/allocated `extra_fields`/central-directory buffer entirely, producing a heap buffer over-read (analogous to the unchecked-continuation-after-partial-validation pattern in the TensorFlow `BandedTriangularSolve` report: a validation function exists and is called, but its result is insufficient to make the follow-on unchecked memory access safe).

This code is compiled into `third_party/ijar` (`zip.cc`) and `src/tools/singlejar` (`output_jar.cc`, `combiners.cc`), both of which parse zip/jar files that are not produced by Bazel itself but can originate from external, attacker-served artifacts (e.g., a `java_import`/`http_archive`/Maven-fetched `.jar` that singlejar merges into a deploy jar, or an `ijar` interface-jar-generation input).

### Impact Explanation
An attacker who can supply a malicious `.jar`/`.zip` file that is consumed by `ijar` or `singlejar` (e.g., a third-party jar dependency fetched via `http_archive`/`http_jar`/a Maven/http rule, where the attacker controls the archive bytes and thus also controls the checksum recorded for it) can craft a Zip64 extra field whose declared payload is smaller than what the fixed-index reads expect. This triggers a heap out-of-bounds read during Bazel's build (in the ijar/singlejar tools), which can crash the build process or leak adjacent heap memory bytes into the process (e.g., into constructed size/offset values that influence subsequent memory operations such as `memcpy`/read lengths), a classic heap buffer over-read of the CVE-2021-29612 bug class.

### Likelihood Explanation
Any consumer of `http_archive`/`http_jar`/Maven-style fetches for `.jar`/`.zip` artifacts that lets an external, untrusted party choose the file content (with the checksum simply pinned to whatever bytes were fetched, which does not stop a hostile origin from serving crafted bytes matching its own advertised hash) can trigger this path merely by having their crafted jar processed by `singlejar`/`ijar` as part of a normal build (deploy-jar assembly, interface jar generation). No special privileges beyond publishing/serving the artifact are required.

### Recommendation
Add an explicit bounds check comparing `attr_count()` (or `payload_size()`) against the required index before calling `attr64()` in every caller (`CDH::compressed_file_size/uncompressed_file_size/local_header_offset`, `LH::compressed_file_size/uncompressed_file_size`), and treat an insufficiently-sized Zip64 extra field as a parse error (analogous to how `ExtraField::find()` already rejects fields that don't fit their declared window) instead of silently returning a possibly out-of-bounds value.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction, extending the existing malformed-extra-field pattern already present in the tests: [6](#0-5)  — craft a Central Directory Header (or Local File Header) with `compressed_file_size32 = uncompressed_file_size32 = 0xFFFFFFFF`, and attach a Zip64 extra field (`tag = 0x0001`) with `payload_size = 8` (only one 8-byte attribute present) instead of the 16 bytes required for both uncompressed and compressed sizes. Feed this zip into `singlejar`/`ijar`'s jar-merging path (e.g., via `output_jar_simple_test.cc`'s `CreateOutput`/`GetEntryContents` helpers or a shell test that builds a `java_binary` depending on such a crafted `.jar` fetched through `http_jar`) and run under ASan; the `attr64(1)` call in `CDH::compressed_file_size()` reads 8 bytes past the declared extra-field payload, which ASan should flag as a heap-buffer-overflow (read).

Note: I was unable to execute the tooling itself (no filesystem/terminal access in this ask-only mode) to confirm the ASan crash empirically; this assessment is based on static analysis of the header logic and the existing test harness's ability to construct malformed extra fields.

  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

  ef2->signature(0xdead);

  size_t cdh_offset = zip_data.size();
