### Title
Exchange (Bancor AMM) settlement uses non-atomic floating-point math and unguarded arithmetic by default, allowing pool balances to go negative / real asset draining beyond backing reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
The Rikkei Finance incident stems from a price/settlement source that could be manipulated to yield incorrect values, letting an attacker extract far more value than the protocol actually held. The closest reachable analog in java-tron is the on-chain TRC10 `Exchange` (Bancor-relay AMM), which functions as the protocol's own price/settlement oracle for `ExchangeTransaction`, `ExchangeInject`, and `ExchangeWithdraw` contracts. By default (`allowHardenExchangeCalculation` off), the settlement math uses unchecked floating point and unchecked `+`/`-` arithmetic instead of the "hardened" strict/overflow-checked path, and the internal pool-balance invariant (`balance >= 0`) is enforced only in the hardened path.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-asset amount using `ExchangeProcessor`, which relies on `double`-based `StrictMath.pow`/`Math.pow` Bancor-relay formulas [1](#0-0)  as the price source for every trade, injection, and withdrawal against a TRC10 liquidity pool.

The balance-update path is gated by a `hardenedCalc` flag that is only true when the dynamic property `allowHardenExchangeCalculation` is enabled: [2](#0-1) 

Critically, the negative-balance sanity check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is only executed `if (hardenedCalc ...)` — in the default (non-hardened) mode, the pool's internal `firstTokenBalance`/`secondTokenBalance` can be pushed negative without any exception being raised, because floating-point rounding in the Bancor relay formula (`exchangeToSupply`/`exchangeFromSupply`) can yield a `buyTokenQuant` larger than what the pool truly holds for extreme or crafted `sellTokenQuant`/balance ratios.

The same "hardened vs not" gating also governs the account-balance bookkeeping performed by the actuators: `AbstractExchangeActuator.addExact`/`subtractExact` silently fall back to raw, unchecked `+`/`-` when `allowHarden()` is false [3](#0-2) , and this is exactly the arithmetic used to credit the counter-asset to the caller's real account in `ExchangeTransactionActuator.execute()` [4](#0-3)  and in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` [5](#0-4) .

The validation step (`doValidate`) only checks that the resulting `anotherTokenQuant` is above the caller-specified `tokenExpected` and that the pool's *nominal* balance stays under `getExchangeBalanceLimit()` [6](#0-5)  — it never re-checks that the counter-asset actually credited to the trader is bounded by what the pool truly has left, when running in the default (non-hardened) math mode.

Because `accountCapsule.addAssetAmountV2()` / `setBalance()` in the actuator credit the trader with the computed `anotherTokenQuant` regardless of whether the internal pool ledger went negative, a sequence of crafted `ExchangeTransaction`/`ExchangeInject`/`ExchangeWithdraw` calls against a pool with skewed, attacker-controlled balances (via prior injects with extreme ratios) can extract real TRX/TRC10 tokens beyond what the exchange actually backs — an "unbacked balance" condition analogous to a manipulated price oracle draining a DeFi protocol's real reserves.

### Impact Explanation
If the default non-hardened path allows the pool ledger to go negative while still crediting the trader with the computed counter-asset, an attacker (any unprivileged transaction broadcaster who can create/inject/withdraw/trade against an Exchange) can repeatedly extract real TRX or TRC10 balances that are not actually backed by the pool's reserves, producing an unbacked balance / direct theft of funds — the same impact class as the Rikkei Finance loss (manipulated settlement value → theft of ~$1.1M). This is High severity because it results in concrete, unauthorized extraction of real network assets.

### Likelihood Explanation
Any account can create an Exchange and repeatedly call `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` — these are ordinary, unprivileged, fee-cheap transactions reachable by any signer. The `allowHardenExchangeCalculation` dynamic property is a committee-controlled toggle, so unless/until it is enabled network-wide, all exchanges run the unguarded floating-point/raw-arithmetic path. Practically triggering the exact rounding condition requires careful selection of pool ratios and quantities (which is feasible for a determined attacker who fully controls a freshly-created exchange's balances via `AssetIssue` + repeated `Inject`), so likelihood is Medium-to-High rather than trivial.

### Recommendation
- Make the negative-balance / overflow checks in `ExchangeCapsule.transaction()` unconditional rather than gated on `hardenedCalc`, so pool balances can never go negative regardless of the `allowHardenExchangeCalculation` setting.
- Enforce the same unconditional check in `AbstractExchangeActuator.addExact`/`subtractExact` (i.e., always use overflow-checked arithmetic, not just when hardened mode is enabled).
- Add an explicit validation in each Exchange actuator's `doValidate()`/`execute()` that the counter-asset amount credited to the caller can never exceed the actual reserve tracked by the pool.
- Consider deprecating/removing the non-hardened legacy math path entirely now that the hardened `SafeExchangeProcessor`/`StrictMathWrapper` implementations exist.

### Proof of Concept
Conceptual reproduction path (exact numeric parameters require live-chain/testnet experimentation to find the rounding edge case, which could not be executed in this static review):
1. Attacker issues a TRC10 asset and creates an `Exchange` pool (`ExchangeCreateContract`) pairing it with TRX, with `allowHardenExchangeCalculation = 0` (default).
2. Attacker performs a sequence of `ExchangeInjectContract` calls with skewed quantities to push `firstTokenBalance`/`secondTokenBalance` into a ratio that maximizes floating-point rounding error in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [1](#0-0) .
3. Attacker calls `ExchangeTransactionContract` with a `tokenQuant` chosen so that the computed `anotherTokenQuant` exceeds the pool's true remaining balance; since the negative-balance guard in `ExchangeCapsule.transaction()` is skipped when `hardenedCalc` is false [7](#0-6) , the trade succeeds and the trader's real account balance is credited via unchecked `addExact` in `ExchangeTransactionActuator.execute()` [8](#0-7) .
4. Repeat step 3 to continue draining, since no subsequent check re-validates that the pool's internal ledger stayed non-negative.

Note: This finding is based on static code analysis of the exchange settlement path; I was unable to execute a live transaction sequence to confirm the exact quantities/ratios that trigger the floating-point rounding beyond the negative-balance boundary, since I do not have access to a running node/test environment. A background Devin session with repo access and a test harness would be needed to construct and confirm the precise numeric PoC.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
