### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract ABI parsing helpers - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a 32-byte "length" word straight out of the precompile call-data and use it directly as the allocation size for a two-dimensional array (`new byte[len][]`), before any bytes have actually been validated to exist for that many elements. This mirrors the reported bug class: an attacker-declared size field (like the tar header `h.Size`) drives a `make`/`new` allocation with no correlation to the real amount of remaining input, letting a small message trigger a huge allocation and an unrecoverable crash.

### Finding Description
`extractBytes32Array`: [1](#0-0) 

and `extractBytesArray` / `extractSigArray`: [2](#0-1) 

In each of these, `len` comes from `words[offset].intValueSafe()`, where `words` is derived from raw precompiled-contract call data supplied by the caller (i.e., attacker-controlled `bytes` passed to a `CALL`/`STATICCALL` targeting one of the precompiled addresses that use these helpers to decode dynamic ABI arrays such as signature lists). `intValueSafe()` returns the literal `intValue()` whenever the 32-byte word occupies at most 4 bytes and is non-negative: [3](#0-2) 

This means a caller can encode a length word such as `0x7FFFFFFF` (2,147,483,647) and the code will immediately attempt `new byte[2147483647][]` (an ~16 GB object-reference array on a 64-bit JVM before any per-element 32/64/192-byte buffers are even allocated) — with **no check** that the call data actually contains that many entries. Unlike the neighboring `extractBytesArray`, which at least bounds-checks `offset` against `words.length` (line 400), none of the three methods bound `len` itself against the remaining data size before allocating.

This is directly analogous to the reported OCI issue: a compact, attacker-supplied header/length value is trusted to size a bulk allocation instead of being validated against the actual amount of available data.

### Impact Explanation
The Java heap-space `OutOfMemoryError` thrown by such an allocation propagates up through TVM precompile execution. Because these precompiled contracts run in-process inside every full node/SR that processes the transaction (there is no separate sandbox/process boundary for precompiles), a single crafted transaction calling the affected precompile with an oversized length word can throw an unrecoverable error during block/transaction execution on every node that validates the block, leading to a cluster-wide node crash/halt (denial of service) rather than a localized, recoverable failure — consistent with "node crash or halt" impact accepted by the validation criteria.

### Likelihood Explanation
Reachability requires only that an unprivileged account deploy or invoke a smart contract that issues a `CALL` to the affected precompiled address with crafted call data containing an inflated length word in the position read by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`. No special permissions, SR/witness status, or non-broadcastable transaction type is needed — a standard `TriggerSmartContract` is sufficient. The bug requires no race condition or timing, just one well-formed but oversized parameter.

### Recommendation
Before allocating `new byte[len][]` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual bounds of `data`/`words` (e.g., verify `len` is non-negative and that `offset + len` does not exceed `words.length`, and/or cap `len` to a sane maximum consistent with the ABI-encoding size checks already used elsewhere via `isValidAbiEncoding`), rejecting the call (returning a failure `Pair`) instead of allocating when the declared length is inconsistent with the supplied data length.

### Proof of Concept
Not independently reproduced in this analysis (no runtime harness available); the vulnerable code path was confirmed by static inspection of `PrecompiledContracts.java:390-426` and `DataWord.intValueSafe()`. Conceptually: craft `TriggerSmartContract` call data to the precompiled address that dispatches to one of these extraction helpers, placing `0x7FFFFFFF` (or any large value fitting in ≤4 bytes) at the length-word offset consumed by `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, while providing a call-data buffer far shorter than implied by that length — the resulting `new byte[len][]` allocation attempt should throw `OutOfMemoryError` during precompile execution.

**Note on completeness**: I was unable to confirm, within the available tool budget, the exact precompiled-contract `execute()` method(s) that invoke these three helpers (the caller sites were not retrieved before the iteration limit was reached), so the specific precompile address/contract name reachable by an end user is not confirmed here — only the vulnerable allocation logic itself and its use of unchecked, attacker-controlled length words. Further static tracing of all `execute()` implementations in `PrecompiledContracts.java` for calls to `extractBytes32Array`/`extractBytesArray`/`extractSigArray` is recommended to fully confirm the end-to-end call path.
