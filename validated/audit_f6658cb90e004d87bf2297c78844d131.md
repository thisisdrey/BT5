### Title
`add_tip` on `snowbridge-pallet-system-v2` credits an attacker-supplied `sender` without any binding to the tip-payer, corrupting `LostTips` accounting - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`pallet_system_v2::Pallet::add_tip` [1](#0-0)  takes `sender: AccountIdOf<T>` as a free-form call argument and, on failure of `InboundQueue::add_tip` / `OutboundQueue::add_tip`, credits the *caller-supplied* `sender` account in `LostTips`, and always emits the `TipProcessed` event with that `sender` — none of it is checked against the actual origin that transacted the message.

### Finding Description
The only authentication performed is `T::FrontendOrigin::ensure_origin(origin)?`, which verifies the message came from the trusted `system-frontend` pallet location on AssetHub [2](#0-1) . It never checks that `sender` matches any principal derived from that origin. On the sending side, `pallet_system_frontend::Pallet::add_tip` does correctly derive `who` from `ensure_signed(origin)` and burns/swaps `who`'s own asset before building the `AddTip { sender: who, ... }` transact call [3](#0-2) . But this coupling between "who paid" and "who is recorded as sender" is only enforced by the frontend pallet's own code path, not by system-v2 — the field is opaque data inside the XCM `Transact` payload, exactly analogous to `_sender` in `addGasFee`, which was also just an unchecked argument rather than `msg.sender`.

Because `sender` is a plain call parameter (not something the `EnsureOrigin` implementation binds to), any dispatch path that can satisfy `FrontendOrigin` (i.e., any XCM `Transact` arriving from the recognized frontend pallet location, regardless of which end-user actually issued it or paid) can embed an arbitrary `sender` value. The `InboundQueue::add_tip` / `OutboundQueue::add_tip` implementations only validate the `nonce`/`amount` [4](#0-3) ; they never see or validate `sender` at all — `sender` is exclusively used for the `LostTips` bookkeeping and the emitted event in `system-v2`.

### Impact Explanation
`LostTips` is documented as the map used to support a future recovery/refund mechanism for tips that could not be applied to a message reward [5](#0-4) . Since the amount credited to `LostTips[sender]` comes from the attacker-controlled `amount`/`sender` pairing without any proof that `sender` actually burned/paid that `amount`, an attacker who can drive an `add_tip` call whose `nonce` is already consumed (trivial — most nonces become consumed quickly) can inflate `LostTips` for an arbitrary victim address, or for themselves, entirely decoupled from any actual asset burn. This is the "duplicate settlement / wrong beneficiary / unbacked accounting" pattern the impact gate targets: once a recovery/claim extrinsic against `LostTips` is added (as the doc comment says is planned), this mislabeled state becomes directly exploitable for theft, mirroring how the Solidity report's `_sender` parameter let an attacker redirect real ERC20 balances to a fake relayer.

### Likelihood Explanation
Reaching `system-v2::add_tip` still requires satisfying `FrontendOrigin`, i.e., arriving as a `Transact` from the frontend pallet's `PalletLocation` after `DescendOrigin` [6](#0-5) . Today the only code path building this call is `system-frontend::add_tip`, which does bind `sender` to the real payer. So under the *current* runtime wiring, direct exploitation requires either another XCM path that can reach the frontend pallet's descended origin with attacker-chosen bytes, or a future extension that consumes `LostTips` for payouts. This keeps likelihood moderate rather than immediately critical, but the root defect — an unauthenticated `sender` field used for financial bookkeeping — is present today and violates the "receipts/payout state must only advance after verified settlement" invariant regardless of whether a consuming payout call exists yet.

### Recommendation
Do not accept `sender` as an unauthenticated call parameter for accounting purposes. Either (a) derive the credited account directly from the verified XCM origin/location passed through `FrontendOrigin` (converting it to an `AccountId` the same way other calls do via `AccountIdConverter`/`location_to_message_origin`), or (b) have `swap_fee_asset_and_burn`/burn step on the frontend pallet return a cryptographic commitment (e.g. hash of `(who, amount, message_id)`) that `system-v2::add_tip` can verify came from the same burn event, rather than trusting a bare `AccountId` argument. At minimum, before any future consumer of `LostTips` performs a payout, it must independently prove the recorded `sender`/`amount` pair corresponds to an actual burned/withdrawn asset, not just accept the stored map value.

### Proof of Concept
1. Attacker (or any actor able to produce a `Transact` XCM that resolves through `T::FrontendOrigin`) crafts an `EthereumSystemCall::AddTip { sender: <victim_or_self>, message_id: Inbound(nonce), amount: <arbitrary> }` where `nonce` is already consumed (guaranteed to fail `AddTip::add_tip`, e.g. `Error::NonceConsumed` in [7](#0-6) ).
2. `system-v2::add_tip` receives it, `T::FrontendOrigin::ensure_origin` succeeds (only checks the pallet's own descended location), `InboundQueue::add_tip` returns `Err(NonceConsumed)`.
3. `LostTips::<T>::mutate(&sender, |lost_tip| *lost_tip = lost_tip.saturating_add(amount))` executes, crediting `sender` with `amount` that was never burned or withdrawn from anyone [8](#0-7) .
4. `TipProcessed { sender, message_id, amount, success: false }` is emitted, misrepresenting that `sender` "deposited the funds" per the event doc comment [9](#0-8) , even though no burn occurred for this fabricated call.

			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error

			// Otherwise add the tip.
