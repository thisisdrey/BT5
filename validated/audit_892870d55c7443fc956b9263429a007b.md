## Analog Identified: Missing Slippage Bound in `pallet-asset-conversion-tx-payment`'s Fee Swap

The external report's core broken invariant is: **a value-transfer operation is settled against a live AMM price with no user-supplied bound, and the settlement happens across a window an unprivileged actor can manipulate by moving the pool price before/after the operation.** The closest real analog in this repository is not in `pallet-asset-conversion` itself (whose `swap_*` extrinsics and `add/remove_liquidity` calls all already enforce `amount_out_min`/`amount_in_max`), but in the `ChargeAssetTxPayment` transaction extension's `SwapAssetAdapter`, which swaps a user's chosen fee-asset against the AMM pool with **no user-specified maximum/minimum bound at all**.

### Title
Unbounded AMM-priced fee swap in `ChargeAssetTxPayment` allows sandwich extraction of asset-based transaction fees — (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`ChargeAssetTxPayment` lets a user pay fees in a non-native asset by having `SwapAssetAdapter` swap that asset for the native fee asset through `pallet-asset-conversion`'s pool. Unlike every public swap/liquidity extrinsic in `pallet-asset-conversion`, this extension carries no user-defined slippage bound (no `max_asset_amount`/`min_refund` field) — it simply quotes the pool at execution time and accepts whatever price results.

### Finding Description
`ChargeAssetTxPayment` only stores `tip` and `asset_id`; there is no slippage/bound field. [1](#0-0) 

In `withdraw_fee`, the amount of the user's asset needed is quoted from the live pool state and immediately withdrawn/swapped with no cap the user could have set: [2](#0-1) 

Symmetrically, at post-dispatch time, `correct_and_deposit_fee` re-quotes the pool to convert any native refund back into the user's asset, again with no bound, silently accepting a worse price (or `Zero::zero()`, i.e. no refund, per the `.unwrap_or(Zero::zero())`): [3](#0-2) 

Because Substrate block extrinsics execute sequentially and an unprivileged account can submit ordinary `pallet-asset-conversion` swaps, an attacker can place a large swap on the same pool immediately before the victim's extrinsic (via tip-based ordering or simply favorable inclusion), causing `withdraw_fee`'s quote to happen at a manipulated price, and place a reversing swap immediately after, causing `correct_and_deposit_fee`'s refund quote to also be manipulated. Every other AMM-facing entrypoint in this pallet family enforces a user bound (`amount_out_min`, `amount_in_max`, `amount1_min`, `amount2_min`) precisely to prevent this — this one does not.

### Impact Explanation
This directly matches "Balances, assets... must conserve value and settle exactly once to the rightful beneficiary and amount." The victim can be forced to pay far more of their chosen asset than the fee should have cost, and/or forfeit a refund that should have been returned, with the difference extracted by the attacker via arbitrage across the pool and any external market — the same value-extraction pattern described in the external report, just applied to the built-in fee-payment AMM swap instead of a mint/burn order.

### Likelihood Explanation
Likelihood is moderate-to-high on any chain that enables `pallet-asset-conversion-tx-payment` with a shallow or thinly-traded pool: the attacker only needs ordinary signed transactions (no validator/collator/relayer privilege), and transaction ordering within a block is influenced by tips, which the attacker fully controls for their own extrinsics.

### Recommendation
Add an optional user-supplied bound to `ChargeAssetTxPayment` (e.g. `max_asset_amount` for `withdraw_fee` and `min_refund_asset_amount` for `correct_and_deposit_fee`), and enforce it via `ensure!` before performing the swap, returning `InvalidTransaction::Payment` (pre-dispatch) or skipping/capping the refund (post-dispatch) when the live quote violates the bound — mirroring the `amount_out_min`/`amount_in_max` pattern already used elsewhere in `pallet-asset-conversion`. Add tests that manipulate the pool between validate/prepare and dispatch/post-dispatch (sandwich simulation) and assert the extension reverts or refuses the swap when bounds would be violated.

### Proof of Concept
1. Attacker and victim both hold `asset_id` and native asset; a shallow `asset_id`/native pool exists.
2. Victim submits an extrinsic with `ChargeAssetTxPayment::from(tip, Some(asset_id))`.
3. Attacker submits (with higher tip, to be ordered first in the block) a large `swap_exact_tokens_for_tokens` moving the pool price so that `asset_id` is temporarily overvalued relative to native.
4. Victim's extrinsic executes: `withdraw_fee` quotes `asset_fee` for the native `fee` at the manipulated price (line 142-146 of `payment.rs`), withdrawing more `asset_id` than a fair-price quote would require — no bound exists to reject this.
5. Attacker submits a reversing swap after (or the victim's own call's ordinary execution restores balance), realizing arbitrage profit equal to the excess `asset_id` extracted from the victim's fee payment.
6. Repeat/scale: since there is no `ensure!` on the quoted `asset_fee`/`refund_asset_amount` against any user-chosen threshold, this is repeatable against every asset-fee-paying transaction touching that pool.
