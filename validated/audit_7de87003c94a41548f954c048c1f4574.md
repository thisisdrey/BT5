### Title
Access-Control Bypass via UpdateReferences RPC Skipping Pre-Receive/Update Hook Enforcement - (File: internal/gitaly/service/ref/update_references.go)

### Summary
The `RefService.UpdateReferences` RPC updates one or more references directly through the low-level `updateref` package without ever invoking Gitaly's `pre-receive`/`update` hook machinery. Every other reference-mutating path in Gitaly (git-receive-pack via `ReceivePack`/`SSHReceivePack`, and the `OperationService` RPCs such as `UserCreateBranch`, `UserCommitFiles`, `UserCreateTag`, etc.) is required to run through `hook.Manager`/`updateref.UpdaterWithHooks`, which performs the mandatory GitLab `/internal/allowed` access check and executes custom `pre-receive`/`update` hooks before a ref is allowed to change. `UpdateReferences` omits this enforcement entirely, exactly mirroring the reported bug class: a permission gate ("isAllowed") is enforced on one mutation path but missing on a second, functionally-equivalent mutation path.

### Finding Description
`doc/hooks.md` explicitly documents the intended, uniform design:

> "There are two users of these hooks: `PostReceivePack` and `SSHReceivePack` directly invoke `git-receive-pack`, which then executes the hooks for us. Most RPCs in the `OperationService` that write objects into the repository manually invoke these hooks using the `updateref.UpdaterWithHooks` structure." [1](#0-0) 

That "allowed" gate is what performs the GitLab authorization check on every reference change, analogous to `isAllowed[collateral.addr]` in the PaprController example — a gate that must be consulted on every mutation path.

However, `RefService.UpdateReferences` constructs a plain `updateref.Updater` with `updateref.New(ctx, repo)` — not `updateref.UpdaterWithHooks` — and never calls into `hook.Manager` at all: [2](#0-1) [3](#0-2) 

Contrast this with the receive-pack code path, which for every reference update explicitly invokes `hookManager.UpdateHook` (custom hook + is-allowed enforcement point) before queuing the update: [4](#0-3) 

The `UpdateReferences` RPC is declared as a `MUTATOR` in the proto definition and accepts a caller-supplied list of arbitrary reference names, old object IDs, and new object IDs, with only reference-name format and object-ID hex validation performed — no user/permission field, no `pre-receive`/`update` custom hook execution, and no call to Rails' `/internal/allowed` endpoint: [5](#0-4) [6](#0-5) 

This is used as a generic building block by internal callers such as backup restore (`internal/backup/repository.go`) and the remote-repository client (`internal/git/remoterepo/repository.go`), and is also the intended sink for reference updates originating from the `proc-receive` hook/WAL flow described in `doc/hooks.md`. Any caller path that routes a ref update — including one derived from user-controlled push/import/fork data — through `UpdateReferences` instead of through `updateref.UpdaterWithHooks` inherits a silent bypass of both the mandatory permission check and any administrator-installed custom hooks (branch protection enforcement, commit signature enforcement, etc. implemented as custom hooks).

### Impact Explanation
Because `UpdateReferences` can force-update or delete arbitrary references (including protected branches/tags) without the GitLab access check or custom hook execution that every other mutation path enforces, any caller able to reach this RPC with a ref update derived from a lower-privileged operation can silently push changes into refs which should have been rejected by branch protection, push rules, or other custom hooks — the same class of impact as the mint-with-disabled-collateral bug (control bypass), but here manifesting as a hook/permission-check bypass rather than a financial-control bypass.

### Likelihood Explanation
The gap is not a corner-case: it is a structural design property visible directly in the source (no `updateref.UpdaterWithHooks`, no `hook.Manager` call) and is even called out in the project's own documentation as a distinction between "most" RPCs (which run hooks) and RPCs like this one, which do not. Exploitability depends only on whether any caller (Rails, WAL/quarantine migration, replication, or another Gitaly-internal component) forwards user-influenced ref-update data to this RPC without independently re-validating permissions — a likely occurrence given the RPC is explicitly built as a generic, hook-free reference-update primitive re-used by multiple higher-level flows (backup restore, remote repository sync).

### Recommendation
Route `RefService.UpdateReferences` through the same `updateref.UpdaterWithHooks`/`hook.Manager` enforcement used by `OperationService` RPCs and `git-receive-pack`, or, if the RPC is intended purely as a trusted internal primitive, explicitly document and enforce (e.g., via caller allow-listing or a dedicated "skip-hooks" flag that must be set only by trusted internal callers) that it must never receive reference names/values derived from unauthenticated or lower-privileged user input without the caller first performing the equivalent of the `/internal/allowed` check and custom hook execution.

### Proof of Concept
1. Obtain a valid Gitaly gRPC connection (as any component that already has access to `RefService`, e.g. through a code path that forwards user-supplied branch/tag data for an update — such as backup/restore or an internal service acting on behalf of a push).
2. Call `UpdateReferences` directly with a request targeting a protected reference, e.g.:
```
stream.Send(&gitalypb.UpdateReferencesRequest{
  Repository: repo,
  Updates: []*gitalypb.UpdateReferencesRequest_Update{{
    Reference:   []byte("refs/heads/protected-branch"),
    OldObjectId: []byte(currentSha),
    NewObjectId: []byte(attackerSha),
  }},
})
```
3. Observe that the update succeeds without any GitLab `/internal/allowed` call and without executing the repository's custom `pre-receive`/`update` hooks, unlike the equivalent update performed via `UserUpdateBranch`/`git push`, which would have been checked and could have been rejected. There are two users of these hooks:

- `PostReceivePack` and `SSHReceivePack` directly invoke `git-receive-pack`,
  which then executes the hooks for us.
- Most RPCs in the `OperationService` that write objects into the repository
  manually invoke these hooks using the `updateref.UpdaterWithHooks` structure.

These hooks perform the following functions:

- `pre-receive`: The pre-receive hook receives all reference updates as a whole
  via standard input, where each change is represented by one line with the old
  and new object ID as well the name of the reference that is to be updated. At
  this point, all objects required to satisfy the update have already been
  received, but they are still in a separate "quarantine directory" and are
  therefore detached from the main repository. This hook first increments a
  reference counter that tracks how many pushes are active at the same time.
  Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint so
  that Rails can determine whether the change is allowed or not. Because objects
  still live in a quarantine directory, Gitaly tells Rails where it can find the
  quarantine directory using the repository's alternative object directory
  fields so that any subsequent RPC calls that check the change can access those
  objects. When the access checks succeed, any existing custom pre-receive hooks
  installed by the administrator are executed.

func (s *server) UpdateReferences(server gitalypb.RefService_UpdateReferencesServer) error {
	ctx := server.Context()

	request, err := server.Recv()
	if err != nil {
		return fmt.Errorf("receiving initial request: %w", err)
	}

	if err := s.locator.ValidateRepository(ctx, request.GetRepository()); err != nil {
		return err
	}
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	// Unset the repository so that we can more easily verify inside of the loop that all incoming requests
	// ain't got a repository set anymore.
	request.Repository = nil

	updater, err := updateref.New(ctx, repo)
	if err != nil {
		return fmt.Errorf("creating updater: %w", err)
	}

	if err := updater.Start(); err != nil {
		return fmt.Errorf("starting updater: %w", err)
	}

					})
			}

			// The old object ID may be empty, in which case we don't care about the current value of the

			oldObjectID := string(update.GetOldObjectId())
			if len(oldObjectID) > 0 {
				if err := objectHash.ValidateHex(oldObjectID); err != nil {
					return structerr.NewInvalidArgument("validating old object ID: %w", err).WithMetadata("old_object_id", oldObjectID)
				}
			}

			newObjectID := string(update.GetNewObjectId())
			if err := objectHash.ValidateHex(newObjectID); err != nil {
				return structerr.NewInvalidArgument("validating new object ID: %w", err).WithMetadata("new_object_id", newObjectID)

			if errors.Is(err, io.EOF) {
				break

		}
	}
