## Analysis: Self-Escalation from Active-Key to Owner-Level Control via `AccountPermissionUpdateActuator`

### Title
Active-Permission Key Can Self-Escalate to Full Owner Control by Overwriting `owner_permission` via `AccountPermissionUpdateContract` - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` is java-tron's self-service "update my account's multi-sig permissions" endpoint — the direct analog of Movary's `PUT /settings/users/{userId}`. Just as Movary's endpoint let a normal user flip a sensitive `isAdmin` field with no extra gate, `AccountPermissionUpdateActuator.validate()`/`execute()` unconditionally rewrites the account's `owner_permission` (the field that grants ultimate control of the account) as long as the transaction is signed with *any* valid permission id whose `operations` bitmask happens to include the `AccountPermissionUpdateContract` bit — it never requires that the caller actually hold Owner-level authority.

### Finding Description
An account's `Permission` model has three tiers: `Owner` (id 0, ultimate authority), `Witness` (id 1), and `Active` (id ≥2, scoped to specific contract types via a 256-bit `operations` bitmask) [1](#0-0) .

Signature verification for a transaction only checks that the signer's `Permission` (looked up by `contract.getPermissionId()`) has the `AccountPermissionUpdateContract` bit set in its `operations`, and that signature weight passes threshold — it does **not** require `permissionId == 0` (Owner) for this specific, highly sensitive contract type: [2](#0-1) 

`AccountPermissionUpdateActuator.execute()` then blindly calls `account.updatePermissions(...)`, replacing `owner_permission` with whatever `Permission` object is in the contract, without checking that the signer (who may only hold an Active permission) is authorized to make that specific change: [3](#0-2) 

`validate()`'s `checkPermission()` further validates operation bitmasks against `dynamicStore.getAvailableContractType()` — the network-wide list of *all* enabled contract types — rather than against the deliberately narrower `getActiveDefaultOperations()` set: [4](#0-3) 

Notably, the codebase's own test suite proves the team explicitly treats `AccountPermissionUpdateContract` as *unsafe to grant by default* to Active keys — it is excluded from `getActiveDefaultOperations()` while it IS included in `getAvailableContractType()`: [5](#0-4) 

This asymmetry means: once an account owner grants any Active permission the `AccountPermissionUpdateContract` operation bit (e.g., intending to allow that key to do narrow key-rotation), that Active key — which only needs to meet its own (possibly low) threshold — can unilaterally submit a new `AccountPermissionUpdateContract` that **replaces the entire `owner_permission`** with keys of its own choosing. There is no check in `validate()`/`execute()` that the new owner permission retains any of the original owner's keys, nor any restriction preventing a non-Owner signer from touching the `owner` field at all. The Active key thus escalates from a narrowly-scoped signer into the sole entity with irrevocable Owner control of the account — structurally identical to Movary's flaw where a self-service PUT endpoint allowed writing a privileged field (`isAdmin`) with no extra authorization check tied to that specific field.

### Impact Explanation
Any account owner who grants an Active permission (common for automation/hot-wallet keys, exchange withdrawal bots, DApp signer keys) the ability to submit `AccountPermissionUpdateContract` transactions — a scope that looks superficially like "allow this key to help manage permissions" — inadvertently hands that key full, permanent takeover capability: it can overwrite `owner_permission` and lock the real owner out, enabling theft of all account funds/assets and irrecoverable account hijacking (CWE-269 Improper Privilege Management). This satisfies the "concrete unauthorized account operation / theft or permanent freezing of funds" bar.

### Likelihood Explanation
Exploitation requires only a single, ordinary signed `AccountPermissionUpdateContract` transaction from an already-authorized Active key whose `operations` bitmask includes that contract type — no special node/witness/committee privilege is needed, and the actuator performs no additional authorization gate beyond the generic signature/weight check shared by every contract type. The scenario (an owner granting broad "management" operations to a delegated Active key, e.g., in custodial/DeFi tooling that provisions active keys for convenience) is a realistic multisig configuration mistake, not a contrived edge case.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`, require that the signer's permission for this contract type be Owner-level (`permission_id == 0`) whenever the `owner` field is present/changed, regardless of what the `operations` bitmask says; alternatively, hard-exclude `AccountPermissionUpdateContract` from ever being settable in an Active permission's `operations` (mirroring the exclusion already applied in `getActiveDefaultOperations()`), by validating against that constant list in `checkPermission()` instead of the full `getAvailableContractType()` list.

### Proof of Concept
1. Account `A` (Owner key `O`) creates an Active permission with `id=2`, threshold=1, containing key `K` (a bot/automation key), and sets its `operations` bitmask bit for `AccountPermissionUpdateContract` (permitted because `checkPermission()` only checks against `getAvailableContractType()`, which includes this type) — done via a legitimate `AccountPermissionUpdateActuator` call signed by `O`.
2. Attacker who controls `K` (or `K` is compromised) crafts a new `AccountPermissionUpdateContract` for account `A`, setting `owner_permission` to a `Permission` containing only the attacker's own key, `permission_id = 2` in the transaction, signs with `K`.
3. `TransactionCapsule.checkPermission()`/`validateSignature()` succeed because permission `2`'s `operations` includes the `AccountPermissionUpdateContract` bit and `K`'s weight meets threshold [6](#0-5) .
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(newOwner, ...)`, overwriting `owner_permission` with the attacker's key [7](#0-6) , permanently transferring Owner control of account `A` to the attacker.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
