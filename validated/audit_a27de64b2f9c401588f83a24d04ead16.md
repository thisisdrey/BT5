### Title
Attacker-controlled `estimated_len` in `POST /v2/fees/transaction` causes integer-overflow panic/wrap in fee calculation - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` takes `body.estimated_len: Option<u64>` directly from the JSON body with no upper bound check, then `estimate_tx_fee_from_cost_and_length` computes `estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` without any overflow guard. A remote, unauthenticated caller can set `estimated_len` to `u64::MAX` to trigger an arithmetic overflow in that multiplication.

### Finding Description
In `try_parse_request`, `estimated_len` is derived as `std::cmp::max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)` [1](#0-0) . `body.estimated_len` is a plain attacker-supplied `Option<u64>` field with no range validation, so it can be set to `u64::MAX` regardless of the actual `payload_data.len()`, since `max()` will simply select the attacker value. This value flows unmodified into `estimate_tx_fee_from_cost_and_length`, where `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` performs an unchecked multiplication [2](#0-1) . Neither `content_len` bound checks (`MAX_PAYLOAD_LEN`) nor any other guard in `try_parse_request` constrain the numeric value of `estimated_len`; those only bound the raw HTTP body byte length, not the JSON-encoded integer field's magnitude [3](#0-2) .

In a standard (non-overflow-checked) release build, `u64::MAX * MINIMUM_TX_FEE_RATE_PER_BYTE` wraps silently, producing a bogus/small `minimum_fee` that is then compared and possibly applied to the client-visible fee estimate (`RPCFeeEstimate.fee`) — this yields an incorrect fee estimate but is not itself a crash. In a debug/overflow-checked build, the same multiplication panics with an arithmetic overflow, and since this handler runs in the RPC server's request-handling context, an unhandled panic in this code path can crash the request-handling thread/task depending on how the top-level dispatcher deals with panics.

### Impact Explanation
- In debug/overflow-checked builds: a single crafted POST to `/v2/fees/transaction` triggers an unhandled panic in `estimate_tx_fee_from_cost_and_length`, which is remotely reachable via the RPC port with no authentication and no special peer role — a repeatable one-shot crash primitive against any node running such a build.
- In standard release builds (the typical production configuration, where Rust performs wrapping arithmetic by default without `overflow-checks`), no panic occurs; the result is a wrapped `minimum_fee` value, causing the API to return an incorrect (but bounded, non-crashing) fee estimate. This does not corrupt any persisted or relayed state and does not affect consensus or mempool admission — `will_admit_mempool_tx` is not on this code path since this is a read-only fee-estimation endpoint, not a transaction broadcast/write endpoint.

### Likelihood Explanation
The endpoint is directly reachable at `POST /v2/fees/transaction` with no authentication, no peer registration, and no privileged role required — any remote party who can connect to the node's RPC port can send the request. The `transaction_payload` field only requires a validly-hex-encoded, consensus-deserializable `TransactionPayload`, which is trivial to construct (e.g., a minimal valid payload). The overall exploitability of a crash is contingent on the node binary being built with `overflow-checks = true` (typically only debug/test builds in this codebase; no `overflow-checks` setting was found configured for release profiles), which limits the DoS-via-panic scenario to non-production build configurations.

### Recommendation
Use `checked_mul` (or `saturating_mul`) when computing `minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length`, returning an `HttpBadRequest` on overflow rather than allowing wrapping or panicking arithmetic. Additionally, clamp/validate `body.estimated_len` in `try_parse_request` against a sane maximum (e.g., `MAX_PAYLOAD_LEN` or a fixed reasonable transaction-length ceiling) before accepting it, rejecting values that are absurdly large as malformed requests.

### Proof of Concept
```rust
// stackslib/src/net/api/tests/postfeerate.rs (illustrative addition)
#[test]
fn test_overflow_estimated_len() {
    let mut handler = RPCPostFeeRateRequestHandler::new();
    let preamble = /* construct valid HttpRequestPreamble with JSON content-type,
                       content-length > 0 and < MAX_PAYLOAD_LEN */;
    let body_json = json!({
        "estimated_len": u64::MAX,
        "transaction_payload": "0x<valid hex-encoded TransactionPayload>"
    });
    let body_bytes = serde_json::to_vec(&body_json).unwrap();

    // try_parse_request should either succeed (storing estimated_len = u64::MAX)
    // or reject the request cleanly; it must not allow the later multiplication
    // to overflow.
    let result = handler.try_parse_request(&preamble, &Captures::default(), None, &body_bytes);
    assert!(result.is_ok());

    // Now call estimate_tx_fee_from_cost_and_length with estimated_len = u64::MAX
    // and MINIMUM_TX_FEE_RATE_PER_BYTE > 1.
    // In a debug/overflow-checked build this line panics:
    //   let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;
    // Assert instead that the handler returns Err(StacksHttpResponse) bounded error.
}
```
Run this test under `cargo test` with `overflow-checks = true` (e.g., default `cargo test` debug profile) to observe the panic at `stackslib/src/net/api/postfeerate.rs:112`.
