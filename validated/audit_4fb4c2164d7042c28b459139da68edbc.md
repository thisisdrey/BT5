### Title
Oversized/arbitrary attachment content bypasses `attachments_max_size` when accepted via `GetAttachmentResponse` download path - (File: stackslib/src/net/atlas/mod.rs, stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs)

### Summary
The custom `Deserialize` for `GetAttachmentResponse` (`stackslib/src/net/atlas/mod.rs:69-77`) hex-decodes a peer-supplied string directly into `Attachment::new(bytes)` with no length check. The attachment-download completion path (`stackslib/src/net/atlas/download.rs:153-169`, via `extend_with_attachments` at `download.rs:530-558`) then calls `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) directly, which also performs no size check — unlike the sibling ingestion path in `posttransaction.rs` which explicitly gates writes with `AtlasDB::should_keep_attachment` (`db.rs:249-266`, checked against `attachments_max_size`).

### Finding Description
The equality the question describes — `decoded_attachment_len <= attachments_max_size` — is not enforced on the peer-download path. Tracing the flow:

1. A remote peer serving `/v2/attachments/:hash` responds with an arbitrary hex payload as the JSON body.
2. `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) parses the JSON via `serde_json::from_value::<GetAttachmentResponse>`, invoking the custom `Deserialize` impl at `mod.rs:69-77`, which does `hex_bytes(&hex_encoded)` then `Attachment::new(bytes)` — no size bound at all.
3. In `AttachmentsBatchStateContext::extend_with_attachments` (`download.rs:530-558`), any successfully decoded response is inserted into `self.attachments` (a `HashSet<Attachment>`) unconditionally — there is also no check that `attachment.hash()` matches the originally-requested `content_hash`.
4. When the state machine reaches `Done`, `AttachmentsDownloader::run` (`download.rs:153-169`) iterates `context.attachments.drain()` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` for every one, unconditionally.
5. `AtlasDB::insert_instantiated_attachment` (`db.rs:576-592`) performs a raw `INSERT OR REPLACE INTO attachments (...) VALUES (?, ?, 1, ?)` with the full `attachment.content` blob and no length comparison against `self.atlas_config.attachments_max_size`.

By contrast, the only place that enforces `attachments_max_size` is `AtlasDB::should_keep_attachment` (`db.rs:249-266`), which is exclusively called from `RPCPostTransactionRequestHandler::try_handle_request` in `stackslib/src/net/api/posttransaction.rs:231-250` for the `insert_uninstantiated_attachment` path (used for locally-POSTed contract-call attachments), not for the download-completion path. `MAX_PAYLOAD_LEN`/HTTP-level body caps bound the individual HTTP response but are much larger than `ATTACHMENTS_MAX_SIZE_MIN` and are not a substitute for the Atlas-specific cap.

### Impact Explanation
A remote peer that the victim node treats as an outbound sync peer for Atlas (reachable simply by being selected in `network.get_outbound_sync_peers()`/serving `data_url`) can respond to a `GetAttachmentResponse` request with content whose length exceeds the configured `attachments_max_size` (minimum 1 MiB, `ATTACHMENTS_MAX_SIZE_MIN`), and this content is written into the node's on-disk `AtlasDB` `attachments` table via `insert_instantiated_attachment` without any size gate. Repeated across many attachment instances/batches, this lets an attacker inflate the victim's Atlas database well beyond the operator-configured cap, i.e., attachment storage exhaustion bypassing the configured size cap — a High-severity finding matching "attachment/BNS mismatch"-class impact on a read/sync endpoint, since the guard exists in one code path but is absent in this one.

### Likelihood Explanation
Preconditions: the attacker needs only to run an ordinary Stacks peer/node that the victim connects to over P2P and to be one of the sources the victim's `AttachmentsDownloader` selects for a needed attachment (driven by advertised inventories, which the attacker also controls). No RPC secret, signer role, or StackerDB slot ownership is required — this is within the declared unprivileged remote-attacker capability. The cost is a single crafted HTTP response per attachment request, fully repeatable for every attachment the victim node needs to fetch.

### Recommendation
Enforce `attachments_max_size` (and ideally hash-matching against the originally requested `content_hash`) in the download-completion path before calling `insert_instantiated_attachment`: e.g., check `attachment.content.len() as u32 <= atlas_config.attachments_max_size` in `extend_with_attachments` (`download.rs:530-558`) or immediately before the loop in `AttachmentsDownloader::run` (`download.rs:153-169`), discarding/penalizing peers that violate it. Additionally, consider adding the same bound directly inside `Attachment::new`/`GetAttachmentResponse::deserialize` (`mod.rs:69-77`) so all callers get the guarantee, and validate `Hash160::from_data(&bytes) == expected_content_hash` before acceptance.

### Proof of Concept
```rust
// stackslib/src/net/atlas/tests.rs (illustrative)
#[test]
fn test_oversized_attachment_bypasses_max_size_on_download_path() {
    let atlas_config = AtlasConfig {
        contracts: HashSet::new(),
        attachments_max_size: 1024, // small cap for the test
        max_uninstantiated_attachments: 10,
        uninstantiated_attachments_expire_after: 10,
        unresolved_attachment_instances_expire_after: 10,
        genesis_attachments: None,
    };
    let mut atlas_db = AtlasDB::connect_memory(atlas_config).unwrap();

    // Craft an oversized attachment (> attachments_max_size) as if decoded
    // from a malicious GetAttachmentResponse JSON body via decode_atlas_get_attachment
    let oversized_content = vec![0x41u8; 4096]; // 4KB > 1024-byte cap
    let attachment = Attachment::new(oversized_content);

    // No should_keep_attachment gate is present on this call path in download.rs;
    // insert_instantiated_attachment performs no size check either.
    atlas_db.insert_instantiated_attachment(&attachment).unwrap();

    let stored = atlas_db.find_attachment(&attachment.hash()).unwrap();
    assert!(stored.is_some());
    // FAILS to reject: content.len() (4096) > attachments_max_size (1024)
    assert!(stored.unwrap().content.len() as u32 <= atlas_db.atlas_config.attachments_max_size,
        "oversized attachment was accepted, bypassing attachments_max_size");
}
```
This demonstrates that `insert_instantiated_attachment` — the exact sink reached by the `GetAttachmentResponse` download-completion path in `download.rs:153-169` — accepts content exceeding `attachments_max_size` with no rejection, whereas `should_keep_attachment` (used only by the unrelated POST-transaction path) would have rejected it.     pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }

impl StacksHttpResponse {
    pub fn decode_atlas_get_attachment(self) -> Result<GetAttachmentResponse, NetError> {
        let contents = self.get_http_payload_ok()?;
        let contents_json: serde_json::Value = contents.try_into()?;
        let resp: GetAttachmentResponse = serde_json::from_value(contents_json)
            .map_err(|_e| NetError::DeserializeError("Failed to load from JSON".to_string()))?;
        Ok(resp)
    }
