### Title
Unprivileged dust deposit/transfer fills a victim's `MAX_TOKENS_PER_USER` account lists, DoS-ing new collateral deposits and debt issuance — (File: contracts/Pool.sol)

### Summary
`Pool` tracks per-account deposit tokens and debt tokens in `MappedEnumerableSet` lists, capped at `MAX_TOKENS_PER_USER = 30`. Both `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined list length reaches 30 [1](#0-0) [2](#0-1) . Entries are added to a *recipient's* list whenever their balance goes from 0 to nonzero — via `DepositToken.deposit(amount_, onBehalfOf_)` or a plain `transfer` of dust msdTokens to the victim [3](#0-2) . An attacker can therefore unilaterally fill a victim's list and cause all subsequent first-touch operations on new tokens to revert.

### Finding Description
The analog of CVE-2020-35668 (unhandled input → crash → availability loss) is a state-driven revert forced on a victim:

1. Attacker acquires 1 wei of several distinct `DepositToken` (msd) tokens — either by depositing dust underlying or buying dust on a DEX.
2. Attacker calls `DepositToken.transfer(victim, 1)` (or `deposit(1 wei underlying, victim)`) for enough distinct tokens so that `depositTokensOfAccount.length(victim)` reaches `MAX_TOKENS_PER_USER` [4](#0-3) .
3. From then on, every path that mints a *new* deposit token or issues a *new* debt token for the victim hits `onlyIfAdditionWillNotReachMaxTokens` and reverts with `UserReachedMaxTokens` [5](#0-4) . This includes `DepositToken.deposit`/`_mint` (which calls `pool.addToDepositTokensOfAccount(account_)` when balance goes 0→nonzero) and `DebtToken.issue`/`_mint`.

The check exists to bound iteration in `debtPositionOf`/`depositOf`/`debtOf` [6](#0-5) , but the revert is enforced at insertion time on the *recipient* — the victim never opted in to receiving the dust. No modifier, health check, or pause flag stops the attacker: `transfer` only requires `_revertIfLocked` on the *sender's* balance [4](#0-3) , and `deposit` only checks `amount_ > 0` and `onBehalfOf_ != 0` [7](#0-6) .

### Impact Explanation
Temporary freezing of funds / griefing:

- The victim cannot deposit any collateral type they don't already hold, and cannot issue any new synthetic debt token, until they manually clear slots.
- Time-critical case: a victim whose position is approaching the liquidation threshold and needs to add a *new* collateral type (the only asset they hold) to restore health is blocked. Their position gets liquidated while the rescue deposit reverts — indirect loss of funds.
- Recovery costs the victim up to 30 transactions of dust transfers, and the attacker can re-grief at dust cost.

Existing balances remain withdrawable (`withdraw`/`transfer` only remove entries), so this is temporary rather than permanent freezing — consistent with an availability-class bug.

### Likelihood Explanation
- Fully unprivileged: any EOA, no privileged role needed; all entry points (`transfer`, `deposit` with `onBehalfOf_`) are public [8](#0-7) .
- Cost is dust amounts of underlying/msdTokens across ≤30 tokens — cheap on L2 deployments (Base, Optimism, etc. exist in `deployments/`).
- Constraint: only as many distinct deposit tokens exist as the pool registers; with fewer than ~30 registered tokens the cap may be unreachable for collateral alone. Pools with many collaterals (e.g., multiple va* tokens via `VesperGateway`) are exposed.

### Recommendation
- Only count a token toward `MAX_TOKENS_PER_USER` when the account itself initiated the position (e.g., add to the recipient list in `deposit`'s `onBehalfOf_` path and in `issue`, but not on inbound `transfer`/`seize`), or
- Keep a separate `enabledCollateral`-style flag per account that is only set by explicit user action, so dust transfers cannot consume slots, or
- Remove tokens from the recipient's list on `transfer` only if they affirmatively added them; alternatively raise/remove the cap by storing per-account iteration offsets.

### Proof of Concept
Foundry fork test sketch (deployed pool on e.g. Base with ≥30 registered deposit tokens, or a test pool configured with 30):

```solidity
function test_fillVictimTokenList() public {
    address victim = address(0xBEEF);
    IDepositToken[] memory tokens = getAllDepositTokens(); // pool.getDepositTokens()

    // Attacker obtains 1 wei of each msdToken and pushes it to the victim
    for (uint i; i < tokens.length && pool.getDepositTokensOfAccount(victim).length < 30; ++i) {
        deal(address(tokens[i]), attacker, 1);
        vm.prank(attacker);
        tokens[i].transfer(victim, 1); // adds tokens[i] to victim's list
    }
    assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

    // Victim tries to deposit a collateral type they never touched — reverts
    IERC20 underlying = tokens[0].underlying(); // a token NOT in victim's list
    deal(address(underlying), victim, 1e18);
    vm.startPrank(victim);
    underlying.approve(address(tokens[0]), 1e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    tokens[0].deposit(1e18, victim);
    vm.stopPrank();
}
```

Expected result: `deposit` reverts in `_mint` → `addToDepositTokensOfAccount` → `onlyIfAdditionWillNotReachMaxTokens`, demonstrating attacker-imposed DoS on the victim's new collateral deposits.
