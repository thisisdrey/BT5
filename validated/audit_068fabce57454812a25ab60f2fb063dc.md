### Title
Cross-StackerDB replay of validly-signed chunks due to missing contract-id binding in `SlotMetadata` signature — ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` (and therefore every signature verification path for StackerDB chunk writes) commits only to `(slot_id, slot_version, data_hash)`. It never binds the signature to the specific StackerDB smart-contract instance the chunk is destined for. Because the Nakamoto signer set publishes multiple sibling StackerDB contracts (`signers-{set}-{message_id}`, one per message type, up to `SIGNER_SLOTS_PER_USER`) that all derive their `(signer -> slot_id)` mapping from the *same* underlying page (`stackerdb-get-signer-slots-page`), the same signer occupies the identical `slot_id` across all of these sibling contracts. A chunk that a signer legitimately signs and pushes to one message-type StackerDB can therefore be captured (StackerDB chunks are gossiped/publicly readable) and replayed verbatim into a different sibling StackerDB contract, where it will pass every server-side check even though it was never intended for that context.

### Finding Description
`SlotMetadata::auth_digest` at [1](#0-0)  hashes only the slot id, slot version, and data hash — the target contract identifier is absent from the signed material. `SlotMetadata::sign`/`verify` [2](#0-1)  operate purely on this digest.

Both storage paths rely solely on this digest for authentication:
- `StackerDBs::try_replace_chunk`, which loads the `slot_validation.signer` *for the given `smart_contract`* and calls `slot_desc.verify(&slot_validation.signer)`, never folding the contract id into the check: [3](#0-2) .
- `PeerNetwork::validate_received_chunk`, used for both StackerDB sync downloads and unsolicited pushes, likewise only checks slot signer + slot metadata verify, with no contract binding: [4](#0-3) .

The `smart_contract`/`contract_id` parameter threaded through these functions is used only to look up *which signer owns which slot in that contract* — it is never mixed into the cryptographic digest that the signer actually signs. This is architecturally identical to the H-29 pattern: a discriminator (`nlrType` there, contract/message-type here) that determines how a signed payload should be interpreted is left out of the signed data, so if two different "types" (here: sibling StackerDB contracts) end up with overlapping/aliasing schemas (here: identical `(signer, slot_id)` assignment), a payload validly signed for one type can be misinterpreted as valid for the other.

The aliasing precondition is realistic, not merely theoretical: the boot contract `signers.clar` stores exactly one signer-slot list per reward-cycle parity (`stackerdb-signer-slots-0/1`), and every `signers-{set}-{message_id}` sibling contract reads the *same* page via `stackerdb-get-signer-slots-page` [5](#0-4)  and [6](#0-5) . The test `signers_db_get_slots` confirms all `signers-{set}-{message_id}` contracts for a given set return the identical, identically-ordered signer/slot list [7](#0-6) . Consequently, for a given reward cycle, signer S is deterministically assigned to the same `slot_id` in every one of the `SIGNER_SLOTS_PER_USER` message-type StackerDB instances.

Given this, an attacker who observes signer S's chunk push to contract `signers-1-0` (slot_id=k, slot_version=v, data=D, sig=Sig) can resubmit the identical tuple `(slot_id=k, slot_version=v, data=D, sig=Sig)` to a node's `signers-1-1` (a different message-type StackerDB) via the POST StackerDB chunk RPC handler [8](#0-7)  or via unsolicited push gossip. Because `try_replace_chunk`/`validate_received_chunk` verify only slot id/version/data-hash against the correct-for-that-contract signer address — and that signer address is the same signer S in both contracts — the replayed chunk is accepted as authentic content for `signers-1-1`, even though S never signed anything intended for that message channel.

### Impact Explanation
This allows unauthenticated/unauthorized cross-context data injection: content meant only for one signer-message channel (e.g., a state-machine-specific signer message) can be forcibly and validly planted into a *different* channel's slot without the signer's cooperation or key, purely by replaying publicly-observed gossip. Depending on how consumers (`stacks-signer`) interpret different message-type channels, this can corrupt the wire-protocol invariant that "a chunk in contract X's slot k was authored by S *for X*," enabling forged-data propagation across the network (any node that syncs the target StackerDB will accept and re-gossip the misattributed chunk) — matching the Critical "network-wide propagation of forged data" / "unauthenticated write to StackerDB" category.

### Likelihood Explanation
High. No secret key or privileged role is needed by the attacker; the attacker only needs to observe/capture one legitimately-signed chunk from any of the sibling per-message StackerDBs (chunks are meant to be replicated/gossiped publicly) and resubmit the exact same `(slot_id, slot_version, sig, data)` bytes to a different sibling contract via the standard POST-chunk RPC or unsolicited push path. The precondition — identical `(signer, slot_id)` mapping across sibling `signers-{set}-{message_id}` contracts — is guaranteed by the current boot-contract design, not an edge case.

### Recommendation
Bind the target StackerDB contract identifier (and ideally the reward-cycle/signer-set discriminator) into the signed digest in `SlotMetadata::auth_digest`, e.g.:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize_to_vec()); // or a stable byte encoding
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
Update `sign`/`verify` call sites (`try_replace_chunk`, `validate_received_chunk`, the RPC handler, `StackerDBSync`) to pass the contract id through so a chunk signed for one StackerDB instance cannot be replayed into another, even when the underlying signer/slot mapping coincidentally overlaps.

### Proof of Concept
1. In a reward cycle where a signer set is active, note that `signers-1-0` and `signers-1-1` (and other `signers-1-{message_id}` contracts) assign signer `S` to the same `slot_id = k` (guaranteed, since both read `stackerdb-get-signer-slots-page` from `.signers`).
2. Signer `S` legitimately signs and pushes chunk `(slot_id=k, slot_version=v, data=D)` to `signers-1-0` — sig `Sig = Sign_S(hash(k || v || hash(D)))`.
3. An attacker observes this chunk via normal StackerDB gossip/replication or a `GET` chunk RPC.
4. The attacker submits `StackerDBChunkData { slot_id: k, slot_version: v, sig: Sig, data: D }` to a node's `signers-1-1` StackerDB via `POST /v2/stackerdb/{signers-1-1}/chunks` (see handler at `stackslib/src/net/api/poststackerdbchunk.rs`), or replays it as an unsolicited `StackerDBPushChunkData` for that contract.
5. `try_replace_chunk` looks up the slot owner for `signers-1-1` at slot `k`, finds it is also `S`, calls `slot_desc.verify(&S)` which succeeds because the digest never included the contract id — the chunk is accepted and stored in `signers-1-1`, even though `S` never signed anything for that contract.

Note: I could not fully trace how `stacks-signer` interprets cross-message-type payload confusion (i.e., whether a `signers-1-0` payload deserialized in a `signers-1-1` consumer would cause further exploitable behavior) since that logic lives in the signer decision logic, which is out of scope per the rules; the finding here is scoped strictly to the StackerDB storage/replication layer's failure to bind signatures to their intended contract.

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
