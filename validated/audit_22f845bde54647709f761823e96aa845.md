### Title
`SmartFarmingManager` swaps have no deadline, allowing stale pending transactions to be sandwich-attacked at outdated slippage - ([File: contracts/SmartFarmingManager.sol])

### Summary
`SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()` route user funds through `ISwapper.swapExactInput()`, whose interface defines no deadline/expiry parameter at all. A pending `leverage`/`flashRepay` transaction can therefore be executed arbitrarily later — when the user's signed slippage bounds are stale — letting a MEV bot sandwich the swap for profit at the user's expense. This is the same bug class as Blueberry H-14 (disabled deadline on DEX interactions), present on Metronome's own code.

### Finding Description
The `ISwapper` interface exposes only `(tokenIn, tokenOut, amountIn, amountOutMin, receiver)` — there is no `deadline` parameter, and `SmartFarmingManager` never passes `block.timestamp` or any expiry to the swapper:

```solidity
// contracts/interfaces/external/ISwapper.sol
function swapExactInput(
    address tokenIn_,
    address tokenOut_,
    uint256 amountIn_,
    uint256 amountOutMin_,
    address receiver_
) external returns (uint256 _amountOut);
```

```solidity
// contracts/SmartFarmingManager.sol:305
swapper_.swapExactInput(address(tokenIn_), address(tokenOut_), amountIn_, amountOutMin_, to_);
```

In `leverage()` (contracts/SmartFarmingManager.sol:155-211), the user-signed slippage protection is a single `depositAmountMin_` checked once at line 198, while the two internal swaps are executed with `amountOutMin_ = 0` (lines 184 and 197). In `flashRepay()` (lines 98-144), the swap at line 125 is executed with `amountOutMin_ = 0` and the only protection is the post-hoc `swapAmountOutMin_` comparison at line 126. Neither function accepts nor enforces a deadline, so the user's slippage tolerance is frozen at signing time while the trade can be mined at any future price.

### Impact Explanation
If a user's `leverage` or `flashRepay` transaction sits pending in the mempool (e.g., underpriced gas) and market prices move, the signed `depositAmountMin_`/`swapAmountOutMin_` becomes an outdated, overly permissive bound. A MEV bot can then sandwich the swap: push the price against the user so the swap fills just above the stale minimum, extracting the difference. The user unknowingly executes a bad trade and loses collateral value — a direct loss of user funds to an unprivileged attacker, exactly the exploitation path described in the reference report. The final `debtPositionOf` health check (lines 140-141, 207-208) does not prevent this; a sandwiched leverage position can remain technically healthy while being worth materially less than intended.

### Likelihood Explanation
Likelihood is moderate: it requires the victim transaction to remain pending while prices move, which occurs whenever gas spikes or network congestion delay inclusion — the canonical scenario for this bug class. No privileged role is needed; any MEV bot observing the public mempool can perform the sandwich. The absence of any deadline field in `ISwapper` means users have no mechanism to protect themselves regardless of the swapper implementation deployed.

### Recommendation
- Add a `deadline` parameter to `leverage()` and `flashRepay()` and revert if `block.timestamp > deadline` before performing swaps.
- Extend `ISwapper.swapExactInput` to accept and forward a `deadline` to the underlying DEX router calls (e.g., Uniswap V2/V3 router deadline), so protection is enforced at the AMM layer, not just the Spell/Manager layer.
- Consider also applying per-swap `amountOutMin` computed from the user's final slippage tolerance instead of passing `0` for intermediate legs.

### Proof of Concept
Reproducible on a mainnet fork (Foundry):

```solidity
// Attacker/bot observes pending tx in mempool:
// victim.leverage(USDC, msUSDDepositToken, msUSD, amountIn, 2e18, depositAmountMin_stale)

// 1. Price of collateral vs msUSD moves against victim while tx is pending.
// 2. Bot front-runs: buys msUSD / sells collateral on the DEX the Swapper routes through,
//    moving price just below victim's stale depositAmountMin_ threshold.
// 3. Victim's leverage() executes: _swap(..., amountOutMin_=0) fills at manipulated price;
//    _depositAmount passes the stale depositAmountMin_ check (line 198);
//    debtPositionOf still reports healthy (line 207).
// 4. Bot back-runs, restoring price and pocketing the spread.
// Result: victim's leveraged position holds less collateral than a same-moment trade
// would have produced; the delta is extracted by the bot.
// A `deadline` param would have let the victim's tx expire before step 3.
```
