### Title
Unbounded Array Allocation in `ValidateMultiSign` Precompile Signature Decoding Leads to Node OOM/Crash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The TensorFlow advisory describes an out-of-bounds read caused by trusting an attacker-supplied length/index value without validating it against the actual buffer size before performing memory operations. The analogous pattern in java-tron is in the `ValidateMultiSign` precompiled contract's legacy signature-array decoder, `extractBytesArray`/`extractBytes32Array`, which reads an attacker-controlled 32-byte "array length" word directly from calldata and uses it, unvalidated, to size a Java array (`new byte[len][]`) before any bound checking against the input size.

### Finding Description
`ValidateMultiSign.execute()` parses the precompile's raw calldata into 32-byte words and derives the signature-array offset/length entirely from attacker-controlled `DataWord`s: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is *not* active, the legacy path `extractBytesArray` is used instead of the newer `extractSigArray`, and it is reached **without** the `sigArraySize > MAX_SIZE` guard that only applies to the `extractSigArray` branch: [2](#0-1) 

Inside `extractBytesArray` (and similarly `extractBytes32Array`), `len` is read straight from calldata via `words[offset].intValueSafe()` and used to allocate `new byte[len][]` with no upper bound and no check that `len` items actually fit within `words.length`: [3](#0-2) 

This is a direct structural analog of the TensorFlow bug class: an externally-controlled "size/index" value (`true_classes` in TF; the ABI-encoded array-length word here) is trusted to drive a memory operation (`byte[len][]` allocation / subsequent array indexing) without validating it against the real backing data size.

The `extractBytesArray` call itself is **not** wrapped in the `try { ... } catch (Throwable t)` block that guards the rest of `ValidateMultiSign.execute()` — that block only wraps the signature-recovery/weight loop, not the array construction: [4](#0-3) 

If `len` is a large positive int (derived from an attacker-crafted 32-byte word), `new byte[len][]` can throw `OutOfMemoryError`. `OutOfMemoryError` is an `Error`, not a `RuntimeException`, so it is **not** caught by the VM's opcode-execution `catch (RuntimeException e)` handler in `VM.java`: [5](#0-4) 

An uncaught `Error` propagating out of contract execution during `Manager` block application can crash or halt the node process handling that transaction/block.

### Impact Explanation
A successful trigger causes an unhandled `OutOfMemoryError`/`NegativeArraySizeException` inside TVM execution on the legacy code path, which is not swallowed by the VM's `RuntimeException` catch block. Depending on the block-application context, this can crash or halt the node processing the block — a Medium/High severity denial-of-service against the node, consistent with the accepted "node crash or halt" impact category.

### Likelihood Explanation
Exploitability is gated by the `allowTvmSelfdestructRestriction` chain parameter: when it is enabled, calls route through `extractSigArray`, which is protected by the `sigArraySize > MAX_SIZE` check performed beforehand, closing this specific path. When the flag is disabled (its default is `false` until enabled by committee proposal, per `VMConfig`/`ConfigLoader`), the legacy unguarded `extractBytesArray`/`extractBytes32Array` path is reachable by any account issuing a plain TVM `CALL`/`STATICCALL` to the `ValidateMultiSign` precompiled contract address with crafted calldata — no special privilege is required. I was unable to confirm from the available code snapshot whether `allowTvmSelfdestructRestriction` is currently active on the target network; this materially affects real-world reachability.

### Recommendation
- Add the same `sigArraySize > MAX_SIZE` (or an equivalent hard cap) validation unconditionally, before calling either `extractSigArray` or the legacy `extractBytesArray`, regardless of the `allowTvmSelfdestructRestriction` flag.
- In `extractBytesArray`/`extractBytes32Array`, validate `len` against a sane upper bound and against the actual `words.length` (i.e., `offset + len + 1 <= words.length`) before allocating `new byte[len][]`, returning a safe error result instead of proceeding.
- Wrap array-construction helpers used by precompiles in the existing `try/catch` so any residual failure degrades gracefully rather than escaping as an uncaught `Error`.

### Proof of Concept
1. Craft calldata for a call to the `ValidateMultiSign` precompiled contract address such that:
   - `words[3]` (the "offset" word) points to a valid in-bounds word.
   - The word at that offset (`words[offset]`, used as the array "length") is set to a very large integer (e.g., close to `Integer.MAX_VALUE`).
2. Deploy/trigger a smart contract that issues a `CALL`/`STATICCALL` to the `ValidateMultiSign` precompile address with this calldata, on a network where `allowTvmSelfdestructRestriction` is not yet activated.
3. `extractBytesArray` executes `new byte[len][]` with the attacker-supplied huge `len`, attempting a massive allocation.
4. The resulting `OutOfMemoryError` is not caught by `VM.java`'s `catch (RuntimeException e)` block, propagating out of TVM execution during transaction/block processing.

Note: I could not verify from the indexed code snapshot the live on-chain activation state of `allowTvmSelfdestructRestriction`; if it is already permanently active on the target deployment, this specific legacy path is dead code and the practical severity is reduced to "latent/legacy code," though the missing bound check in `extractBytes32Array`/`extractBytesArray` themselves remains a code-quality/defense-in-depth issue.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
