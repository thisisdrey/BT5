Audit Report

## Title
Unprotected AMM swap in Snowbridge `system-frontend` lets an attacker sandwich `register_token`/`add_tip` and steal the swapped tip/fee value - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`pallet_snowbridge_system_frontend`'s public extrinsics `register_token` and `add_tip` swap a user-supplied fee/tip asset into Ether via `T::Swap::swap_exact_tokens_for_tokens` with `amount_out_min` hard-coded to `None`, before burning the Ether for teleport to Ethereum. In the production Asset Hub Westend runtime, `type Swap` is bound to the real `pallet_asset_conversion` AMM (`AssetConversion`), making this swap fully exposed to public mempool front-running/sandwiching.

## Finding Description
`Pallet::swap_and_burn` invokes `T::Swap::swap_exact_tokens_for_tokens(..., tip_amount, None, ..., true)` with no minimum output floor. This is reachable from two unprivileged entry points: `add_tip`, callable by any signed account, and `register_token`, whenever the resolved origin is not the root/`Here` location. `pallet_asset_conversion::do_swap_exact_tokens_for_tokens` only checks `amount_out >= amount_out_min` when `amount_out_min` is `Some`; when `None` is passed, the swap accepts any output amount, however degraded by pool-price manipulation. The production wiring in `cumulus/parachains/runtimes/assets/asset-hub-westend/src/bridge_to_ethereum_config.rs` sets `type Swap = AssetConversion`, confirming this is backed by the live constant-product AMM pallet with public, deterministic reserves and pricing. An attacker observing a pending `add_tip`/`register_token` transaction can submit a large trade to skew the pool price, let the victim's zero-floor swap execute at a degraded rate, then trade back to restore the price and capture the difference.

## Impact Explanation
This is a real value-theft primitive against ordinary users: the victim's `ether_gained` (used either as the relayer reward tip forwarded to BridgeHub in `add_tip`, or as the fee funding registration execution in `register_token`) can be driven to near zero by sandwich manipulation of the AMM pool, extracting almost all of the fair-market value of the tip/fee asset the victim paid. This is unbacked value transfer from an unprivileged user to an unprivileged attacker purely through transaction ordering around a public extrinsic with no privileged access, governance, or leaked-key assumption required, matching the "theft of rewards" / underpriced-work impact class.

## Likelihood Explanation
High. `add_tip` and the non-root path of `register_token` are permissionless, publicly documented extrinsics. The exploit requires only ordinary mempool visibility and the ability to submit front-run/back-run transactions against `pallet_asset_conversion`'s own public `swap_exact_tokens_for_tokens` — standard MEV/sandwich tooling, no special privilege. The code explicitly disables the one built-in defense with the comment "No minimum amount required."

## Recommendation
Do not pass `None` for `amount_out_min` in `swap_and_burn`. Compute an expected output via `pallet_asset_conversion`'s quote-price API and pass `Some(min_out)` with a bounded slippage tolerance, or expose an explicit `min_ether_out` parameter on `register_token`/`add_tip` so callers can set their own floor, mirroring `pallet_asset_conversion`'s own dispatchable interface.

## Proof of Concept
1. Attacker observes a pending `add_tip(message_id, asset)` (tip asset X, pool X/Ether) transaction in the mempool.
2. Attacker front-runs with a large `AssetConversion::swap_exact_tokens_for_tokens` trade that skews the X/Ether pool reserves unfavorably for the victim.
3. Victim's `add_tip` executes, calling `swap_and_burn` → `T::Swap::swap_exact_tokens_for_tokens(..., tip_amount, None, ...)`, receiving far less Ether than fair value; `ether_gained` is forwarded to BridgeHub as the tip.
4. Attacker back-runs by reversing the trade, capturing the price difference as profit, restoring the pool.
5. Reproduce as a Rust integration test in the `system-frontend` pallet's mock runtime: create an `AssetConversion` pool for asset X/Ether, seed it with liquidity, call `add_tip` from a victim account, and show that interleaving a large opposing swap immediately before and after the victim's call reduces `ether_gained` (observable via the `EthereumSystemCall::AddTip { amount, .. }` XCM payload) versus the no-manipulation baseline.
