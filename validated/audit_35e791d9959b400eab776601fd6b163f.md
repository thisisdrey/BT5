The `ValidateMultiSign` TVM precompile in java-tron uses exact-signature-byte deduplication (rather than deduplicating strictly by recovered signer) when tallying multisig weight, which is bypassable via ECDSA signature malleability — the same bug class as the Nebula fingerprint blocklist bypass (CWE-347).

### Title
Multisig Weight-Threshold Bypass via ECDSA Signature Malleability in `ValidateMultiSign` Precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (address `0x...a`, reachable from any `TriggerSmartContract` call) deduplicates submitted signatures using the exact byte content of `merge(recoveredAddr, sign)` rather than deduplicating purely by the recovered signer address. Because standard secp256k1 ECDSA signatures are malleable (`(r, s, v)` and `(r, n-s, 1-v)` both verify and recover to the same address), a single private key can produce two syntactically distinct but cryptographically valid signatures over the same hash. Both pass the "already signed" check because the raw signature bytes differ, letting one key's weight be counted multiple times toward a multisig `threshold`.

### Finding Description
`ValidateMultiSign.execute()` computes, for each submitted signature: [1](#0-0) 

The dedup logic only `continue`s (skips adding weight) when **both** the recovered address *and* the exact merged signature bytes are already present in `executedSignList`. If the address is present but the signature bytes differ (as happens with a malleable second signature from the same key), the loop falls through, calls `MUtil.checkCPUTime()`, and then **adds the weight again** via `TransactionCapsule.getWeight(permission, recoveredAddr)` and `totalWeight += weight`.

Signature verification itself does not enforce canonical (low-S) signatures. `ECDSASignature.validateComponents` only range-checks `r`/`s` against the curve order and checks `v ∈ {27,28}` — it does not reject the malleable high-S counterpart: [2](#0-1) 

`toCanonicalised()` exists but is not invoked on the verification/recovery path used by `recoverAddrBySign`: [3](#0-2) 

so both the original signature `(r, s, v)` and its malleable twin `(r, n-s, v^1)` are accepted as independently "valid" signatures that recover to the identical address, exactly mirroring how the Nebula certificate could be re-signed with the opposite chirality to produce a different fingerprint while remaining valid for the same key — except here the effect is bypassing a signer-count/weight check instead of a blocklist fingerprint check.

By contrast, the on-chain transaction-level multisig check `TransactionCapsule.checkWeight` (used for real transaction signature validation) dedups by the resolved **address** (`encode58Check(address)` as map key) rather than by raw signature bytes, and is not vulnerable to this variant: [4](#0-3) 
This shows the precompile's dedup logic is inconsistent with, and weaker than, the transaction-level equivalent.

### Impact Explanation
Any contract that relies on the `ValidateMultiSign` precompile to gate privileged actions (e.g., custom multisig wallets, escrow, or governance contracts built on TRON) based on a `Permission` threshold can be bypassed by an attacker holding only a subset of the required keys. By submitting each held key's signature twice — once in its original form and once in its ECDSA-malleable form — the attacker inflates `totalWeight` and can satisfy `permission.getThreshold()` without collecting the required number/weight of distinct authorized signers. This can lead to unauthorized execution of privileged contract logic (e.g., unauthorized fund transfers or account operations gated by this precompile), i.e., theft or unauthorized account operation.

### Likelihood Explanation
Exploitation requires only a single held private key that is a member of the target `Permission`, plus knowledge of standard secp256k1 malleability math (trivial, well documented). The attacker calls the precompile (`0x...a`) via a normal `TriggerSmartContract` transaction with two crafted signatures over the same hash — no special privileges, node access, or SR/witness collusion needed. This is reachable by any unprivileged contract caller.

### Recommendation
In `ValidateMultiSign.execute()`, deduplicate purely by `recoveredAddr` (skip/continue as soon as the address has already contributed weight), matching the approach in `TransactionCapsule.checkWeight`. Additionally/alternatively, enforce canonical low-S signatures (reject `s > HALF_CURVE_ORDER`) in the signature-recovery path used by `recoverAddrBySign`/`ECRecover`-style verification so that only one canonical signature per key is ever considered valid.

### Proof of Concept
1. Create an account with an `Active` permission requiring `threshold = 2`, containing only `key1` with weight `2` (or two keys where one key's weight alone is insufficient but doubling it reaches the threshold).
2. Compute `hash = sha256(address || permissionId || data)` as done in `ValidateMultiSign.execute`.
3. Sign `hash` with `key1` to get `sig = (r, s, v)`.
4. Derive the malleable twin `sig' = (r, n - s, v XOR 1)` where `n` is the secp256k1 curve order — this remains a valid signature recovering to `key1`'s address (confirmed by `ECDSASignature.validateComponents`, which imposes no canonical-S restriction).
5. Call the `ValidateMultiSign` precompile with `signatures = [sig, sig']`.
6. Observe `recoveredAddr` is identical for both entries, but `merge(recoveredAddr, sig) != merge(recoveredAddr, sig')`, so the second signature is *not* skipped by the `matrixContains` check and its weight is added again — `totalWeight` becomes `4` (or otherwise doubled) even though only one private key participated, satisfying `threshold` and returning `dataOne()` (success) from a single compromised/held key.
