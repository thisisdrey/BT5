### Title
Loss of precision in vote-reward computation due to divide-before-multiply with `double` - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>>)` computes a user's share of a super-representative's cycle reward using floating-point division followed by multiplication, in the same "divide first, then scale" pattern flagged as high severity in the PegOracle report (`(price2 * 10000) / price1` then re-scaled), which truncates precision before the final multiplication is applied.

### Finding Description
For cycles prior to `newRewardAlgorithmEffectiveCycle`, `MortgageService.computeReward` calculates each voter's reward with: [1](#0-0) 
`double voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;`

This divides `userVote` by `totalVote` first (producing a `double` with limited mantissa precision, especially when `totalVote` is large and the ratio is small), and only afterward multiplies by `totalReward`. Just like the PegOracle bug — where `(price2 * 10000) / price1` was computed and then rescaled by `decimals10` before a final `/1000000`, truncating the true ratio before scaling — this ordering discards precision that a `multiply-then-divide` (or BigInteger) approach would have preserved. The same anti-pattern also appears in `IncentiveManager.reward()` (`(double) totalPay / voteSum` then multiplied by `voteCount`) and `MortgageService.payStandbyWitness()` (`(double) totalPay / voteSum` then multiplied by vote count), both used for standby-witness payouts.

By contrast, the newer reward algorithm (`computeReward(long beginCycle, long endCycle, AccountCapsule)`, `VoteRewardUtil.computeReward`, `RewardViCalService`) correctly uses `BigInteger` multiply-then-divide with a fixed-point `DECIMAL_OF_VI_REWARD` scale, avoiding this loss: [2](#0-1) 

This shows the codebase is aware of and has fixed this exact class of bug for the "new algorithm" path, but the legacy `computeReward(long cycle, ...)` path (still reachable for any cycle prior to the algorithm-switch cycle, and for standby witness pay) retains the double-based, divide-before-multiply calculation.

### Impact Explanation
The precision loss causes `reward` to be systematically under- or over-computed for voters relative to their true proportional share of `totalReward`, distributed via `WithdrawBalanceActuator` → `MortgageService.withdrawReward()` → `computeReward()` → `adjustAllowance()`, which directly credits an account's spendable `allowance` (later withdrawn as TRX balance). This is a fund-accounting bug: value can leak from the reward pool (paid to some voters but not correctly reconciled) or be permanently under-paid to voters, since the truncation error is asymmetric per user vote weight and not conserved across all voters of the same SR. Reward math is explicitly in-scope as reachable stake/delegation/reward logic.

### Likelihood Explanation
`WithdrawBalanceActuator` (triggered by any account submitting a `WithdrawBalanceContract` transaction) invokes this exact reward computation for any cycle that predates `newRewardAlgorithmEffectiveCycle`; the standby witness payout path (`payStandbyWitness`) is executed automatically every maintenance cycle. No special privilege is required beyond broadcasting a normal, valid transaction, and legacy cycles remain permanently reachable in reward history for chains that ran under the old algorithm before the switch.

### Recommendation
Replace the `double`-based `voteRate * totalReward` calculation with an integer/BigInteger multiply-then-divide, e.g. `BigInteger.valueOf(totalReward).multiply(BigInteger.valueOf(userVote)).divide(BigInteger.valueOf(totalVote))`, consistent with the fixed-point approach already used in the new reward algorithm (`DECIMAL_OF_VI_REWARD`). Apply the same fix to `IncentiveManager.reward()` and `MortgageService.payStandbyWitness()`, which use the identical divide-then-multiply-with-double pattern.

### Proof of Concept
Given `totalVote = 3` and `userVote = 1` (i.e., exact ratio 1/3) and `totalReward = 10`:
- Current code: `voteRate = (double)1/3 = 0.3333333333333333` (finite binary approximation of a repeating fraction); `reward += 0.3333333333333333 * 10 = 3.333333333333333` → cast/truncated to `long` = 3.
- Correct fixed-point calc: `10 * 1 / 3 = 3` in this trivial example matches, but for large `totalReward` (e.g., `totalReward = 10_000_000_000_000_000L`, near `long` capacity) the `double` intermediate (53-bit mantissa) cannot represent the exact ratio or product, causing off-by-many-units drift compounded across every voter of every SR every cycle — exactly analogous to the PegOracle PoC showing measurable ratio deviation (`990500000000000000` vs `990544616614592905`) once large numerators/denominators exceed floating point precision.   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
