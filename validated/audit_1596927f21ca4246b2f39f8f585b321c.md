Based on the investigation, I found a solid analog to the reported bug class within `marginfi-v2--024`.

### Title
Unprotected `init_global_fee_state` Allows Front-Running to Hijack Protocol Fee Admin and Fee Wallet - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
`initialize_fee_state` (the `init_global_fee_state` instruction) is the "genesis" setup call for the protocol's singleton `FeeState` PDA. Like `ScrollChain::importGenesisBatch`, it is callable by any signer and sets values that are trusted as ground truth for all future security-critical operations — here, the `global_fee_admin` and `global_fee_wallet`. Whoever calls it first wins, permanently.

### Finding Description
The instruction handler takes `admin_key` and `fee_wallet` as raw arguments and writes them directly into the account with no validation that the caller is authorized to set them: [1](#0-0) 

The `Accounts` struct only requires a generic `payer: Signer`, with no admin/upgrade-authority check, and the `fee_state` PDA uses `init` at a fixed seed (`FEE_STATE_SEED`), so it can only ever be created once, by whoever calls first: [2](#0-1) 

This is structurally identical to the `importGenesisBatch` issue: an unprotected one-time initializer that sets a piece of state (`withdrawRoot` there, `global_fee_admin`/`global_fee_wallet` here) that downstream logic implicitly trusts, and which can be raced by an attacker before the legitimate deployer configures it.

Once set, `global_fee_admin` gates all future fee configuration (`edit_global_fee_state` requires the caller to equal `global_fee_admin`), and `global_fee_wallet`/fee rates are copied into every `MarginfiGroup`'s `fee_state_cache` at group creation, which is loaded (not re-validated) from the existing `fee_state` account: [3](#0-2) 

If an attacker calls `init_global_fee_state` first with `admin_key = attacker`, `fee_wallet = attacker`, and inflated `program_fee_rate`/`program_fee_fixed`/`bank_init_flat_sol_fee`/etc., every subsequently created `MarginfiGroup` inherits the attacker-controlled fee wallet and fee parameters into its cache, and the attacker permanently holds `global_fee_admin`, which per the permissions matrix controls editing all global fee state going forward: [4](#0-3) 

### Impact Explanation
This results in unauthorized state change with direct financial consequences: protocol/program fees collected across all banks and all groups would route to an attacker-controlled `global_fee_wallet` instead of the legitimate protocol wallet, and the attacker gains exclusive, permanent control (`global_fee_admin`) over fee configuration, pause-delegate assignment, and other fee-state-gated operations. Recovering from this requires redeploying/migrating to a new `FeeState` PDA, since the seed is fixed and `init` cannot be repeated.

### Likelihood Explanation
Exploitation only requires observing the program deployment (a public, unavoidable on-chain event) and racing a single transaction calling `init_global_fee_state` with attacker-chosen arguments before the deployer's own initialization transaction lands — a standard front-running/MEV pattern on Solana, requiring no special privilege.

### Recommendation
Restrict `init_global_fee_state` (and `init_global_fee_state_v2`) to a known, immutable authority (e.g., require `payer` to equal the program's upgrade authority, or gate it via a dedicated deployer-only signer check), and/or perform the initialization atomically as part of program deployment/migration tooling rather than as a freely callable instruction.

### Proof of Concept
1. Program is deployed/upgraded; `FeeState` PDA at `[FEE_STATE_SEED]` does not yet exist.
2. Attacker submits `init_global_fee_state(admin_key = attacker_pubkey, fee_wallet = attacker_pubkey, ...)` before the legitimate deployer's initialization transaction executes (e.g., by monitoring the mempool/slot and front-running).
3. `fee_state` account is created (`init` succeeds only once) with `global_fee_admin` and `global_fee_wallet` set to attacker-controlled keys, per [5](#0-4) .
4. Every `marginfi_group_initialize` call thereafter copies `fee_state.global_fee_wallet`/fee rates into the new group's cache per [6](#0-5) , permanently routing collected fees to the attacker and leaving `edit_global_fee_state` solely under attacker control.
