## Analysis: Orphaned contract storage rows after SELFDESTRUCT (state/disk bloat)

The CVE describes Nova failing to actually delete an instance's disk resources when deleted during a state transition, letting any authenticated tenant leak disk space. The closest reachable analog in `java-tron--023` is that a contract's persistent storage rows and `ContractState` record are **not deleted** when a contract is destroyed via `SELFDESTRUCT`, even though the account/code/contract-metadata records are removed. Any unprivileged contract deployer can trigger this repeatedly and grow the node's storage-row database (RocksDB `storage-row` CF) without bound.

### Finding Description
`RepositoryImpl.deleteContract()` only removes three of the artifacts associated with a contract: [1](#0-0) 

It never deletes:
- The `ContractStateStore` entry for the address (created via `updateContractState`/`putContractState`), and
- Any rows the contract wrote to `StorageRowStore` during its lifetime.

`Storage.commit()` only issues a `store.delete()` for a row when that specific slot is explicitly overwritten with the zero value; it has no notion of "delete all slots belonging to address X": [2](#0-1) 

When a contract self-destructs (`Program.suicide` / `Program.suicide2`), the flow marks the address as self-destructed and queues it for account/contract/code deletion, but never iterates or clears the contract's storage slots: [3](#0-2) [4](#0-3) 

Since a contract address (derived from creator+nonce for normal `CREATE`) can never be reused, every storage slot the contract ever wrote (e.g. via `SSTORE` to non-zero values) becomes permanently orphaned dead data in the `storage-row` store the moment the contract self-destructs — the data can never be read back (no live contract/account exists to reference it) nor is it ever reclaimed.

### Impact Explanation
Any unprivileged account can:
1. Deploy a contract that writes many non-zero storage slots.
2. Call `SELFDESTRUCT` on it.
3. Repeat with new contracts.

Each iteration permanently grows disk usage on every full node in a way the actuator/VM layer never reclaims, since `deleteContract()` and `Storage.commit()` provide no bulk-cleanup path for a destroyed contract's storage. This mirrors the disk-consumption denial-of-service root cause in CVE-2016-7498 (resource not deleted after the corresponding "delete" operation), and at large scale can contribute to full-node disk exhaustion, which can crash a node or otherwise impair its ability to keep serving RPC/HTTP APIs.

### Likelihood Explanation
The path is reachable by any transaction broadcaster with no special privilege — only the cost of TRX for contract deployment and normal energy fees for `SSTORE`/`SELFDESTRUCT`. This is a nonzero but bounded cost per unit of leaked storage, similar in spirit to the OpenStack case where a normal tenant could trigger the leak.

### Recommendation
When a contract self-destructs, iterate and delete all of its storage rows (or track them via the `Storage`/`ContractState` cache so `commit()` can bulk-delete on self-destruct), and also delete the `ContractStateStore` entry in `RepositoryImpl.deleteContract()`, mirroring what is already done for `codeStore`/`accountStore`/`contractStore`.

### Proof of Concept (conceptual)
1. Deploy contract `C` with a constructor/function that performs many `SSTORE`s of non-zero 32-byte values (bounded by energy limit per tx, repeatable across many contracts/blocks).
2. Call a function on `C` that executes `SELFDESTRUCT`.
3. Observe (via node storage introspection) that the rows written in step 1 remain in the `storage-row` RocksDB column family indefinitely, even though `C`'s account/code/contract entries are gone and `C` is unreachable.
4. Repeat with many contracts to accumulate unbounded disk growth over time.

### Caveat
I was not able to fully trace, within the tool budget, whether any later compaction/pruning pass (e.g., snapshot/pruning mode, `TronStoreWithRevoking` GC) eventually reclaims these orphaned storage rows in non-full-node modes; if such a mechanism exists in a code path I didn't inspect, the severity would be lower than stated (bounded rather than truly unbounded growth) — this should be verified against the full snapshot/pruning implementation before treating this as fully confirmed.   public void put(DataWord key, DataWord value) {
    if (rowCache.containsKey(key)) {
      rowCache.get(key).setValue(value.getData());
    } else {
      byte[] rowKey = compose(key.getData(), addrHash);
      StorageRowCapsule row = new StorageRowCapsule(rowKey, value.getData());
      rowCache.put(key, row);
    }
  }

  public void commit() {
    rowCache.forEach((DataWord rowKey, StorageRowCapsule row) -> {
      if (row.isDirty()) {
        if (new DataWord(row.getValue()).isZero()) {
          this.store.delete(row.getRowKey());
        } else {
          this.store.put(row.getRowKey(), row);
        }
      }
    });
  }

    if (FastByteComparisons.compareTo(owner, 0, ADDRESS_SIZE, obtainer, 0, ADDRESS_SIZE) == 0) {

      getContractState().addBalance(owner, -balance);
      byte[] blackHoleAddress = getContractState().getBlackHoleAddress();
      if (VMConfig.allowTvmTransferTrc10()) {
        getContractState().addBalance(blackHoleAddress, balance);

    if (VMConfig.allowTvmFreeze()) {
      byte[] blackHoleAddress = getContractState().getBlackHoleAddress();
      if (FastByteComparisons.isEqual(owner, obtainer)) {

      if (expireUnfrozenBalance > 0 && internalTx != null) {
