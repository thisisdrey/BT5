Audit Report

## Title
`pallet-oracle`'s aggregated price is served to consumers with no on-read staleness check, allowing stale price data to be treated as current - (File: `substrate/frame/honzon/oracle/src/lib.rs`)

## Summary
`pallet-oracle`'s `DefaultCombineData::combine_data` filters out expired per-operator submissions using `ExpiresIn` only at the moment new data is fed via `do_feed_values`, and the resulting aggregate is written to `Values<T, I>` without any expiry marker. <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/default_combine_data.rs" start="43-52" /> Every downstream read path — `Pallet::get`, the `DataProvider`/`DataProviderExtended` implementations, and the runtime's `OracleApi` — returns this stored `TimestampedValue` verbatim with no comparison of `timestamp` against current time, and `DataProvider::get` even strips the timestamp entirely, denying consumers the ability to self-check freshness. <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/lib.rs" start="395-403" /> <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/lib.rs" start="449-453" /> <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/bin/node/runtime/src/lib.rs" start="3597-3608" />

## Finding Description
The pallet's dual-storage design stores raw per-operator submissions in `RawValues` and the aggregated result in `Values`. <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/lib.rs" start="280-283" /> Freshness filtering (`values.retain(|x| x.timestamp.saturating_add(expires_in) > now)`) runs exclusively inside `DefaultCombineData::combine_data`, which is only invoked from `Pallet::combined`, itself only called from `do_feed_values` when an oracle operator submits new data. <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/lib.rs" start="400-403" /> <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/lib.rs" start="415-429" /> Once `Values<T, I>::insert(key, combined)` runs, that entry persists indefinitely until the next successful feed — there is no expiry sweep or on-read validation anywhere in the pallet. `Pallet::get` (`Self::values(key)`), the `DataProvider` impl, `DataProviderExtended::get_all_values`, and the runtime's `OracleApi::get_value`/`get_all_values` all return the stored value unconditionally. <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/honzon/oracle/src/lib.rs" start="454-460" /> The node runtime concretely wires `pallet_oracle::Config` with `DefaultCombineData<Self, ConstU32<5>, ConstU64<3600>>`, confirming a live `ExpiresIn = 3600` bound is enforced only at write time. <cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/bin/node/runtime/src/lib.rs" start="3152-3165" />

## Impact Explanation
This is a genuine design gap in `pallet-oracle` matching the description exactly, verified against the actual code. However, within this repository, `pallet_oracle` itself is only exercised through the read-only `OracleApi` runtime API (`get_value`/`get_all_values`), which is an off-chain RPC query path, not an on-chain settlement, minting, or liquidation path. No consuming pallet performing minting, redemption, or liquidation logic against `pallet_oracle::Pallet::get`/`DataProvider::get` was found wired into the runtime's `construct_runtime!`/config in this codebase snapshot — the claim's "PSM/stablecoin peg pallet" and "lending/liquidation pallet" scenarios are hypothetical illustrations, not demonstrated in-repo consumers. Without a concrete in-scope consumer whose settlement, payout, or custody logic is shown to trust this stale value, the finding does not, as-is, demonstrate the required "theft or unbacked mint," "duplicate settlement," or "mispriced value transfer" impact against actually-wired production logic — it demonstrates a library/pallet-level staleness gap whose downstream consequence depends on integration choices outside the reviewed code path.

## Likelihood Explanation
The underlying code behavior (freshness filtered only at write, not at read) is real and trivially reproducible by any observer simply waiting past `ExpiresIn` between feeds, as the claim describes. But because no concrete fund-moving consumer of this data was identified as wired into this runtime, the "attacker" capability described (interacting with a consuming pallet to realize mispriced settlement) is unconfirmed in-repo.

## Recommendation
If a consumer pallet or the `OracleApi` RPC is meant to be a live, freshness-sensitive price feed, extend `Pallet::get`/`DataProvider::get`/`OracleApi::get_value` to compare `TimestampedValue::timestamp` against `T::Time::now()` and the configured `ExpiresIn`, returning `None`/an error for stale entries, or expose the raw `TimestampedValue` (including timestamp) to all consumers so they can self-check freshness before use.

## Proof of Concept
Not confirmed as producing a fund-impacting exploit in this repository: the reproduction steps described in the claim (feed at `T0`, let `ExpiresIn` lapse, read at `T1`) correctly demonstrate the pallet-level staleness gap using `Pallet::get`/`DataProvider::get`, but no in-repo test or wired consumer pallet was found that turns this stale read into a duplicate settlement, unbacked mint, or fund loss as required by the impact gate.
