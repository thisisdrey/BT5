## Analysis Summary

I traced the "store not persisting the value that downstream logic depends on" bug-class from the MilkyWay report to the Snowbridge V2 outbound queue delivery-receipt path. Unlike the original bug (write-time truncation to empty bytes), the local analog is a **missing state-gating check**: the receipt's `success` field is decoded from a genuine on-chain event but never inspected before the pallet advances "payout state" (reward + order removal), violating the required invariant that *"payout state must only advance after ... execution ... succeed[s]"*.

### Title
Relayer reward is paid and `PendingOrder` is removed even when the Ethereum delivery receipt reports `success: false` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`DeliveryReceipt` decoded from the `InboundMessageDispatched` Ethereum event includes a `success: bool` field [1](#0-0) , but `Pallet::process_delivery_receipt` never reads or checks this field before crediting the relayer reward and permanently deleting the `PendingOrder`.

### Finding Description
`process_delivery_receipt` verifies the gateway address, computes the `reward_account`, fetches the `PendingOrder` for `receipt.nonce`, unconditionally registers the reward if `order.fee > 0`, and then removes the order — all without referencing `receipt.success`: [2](#0-1) 

The `success` value is part of the decoded, on-chain-verified event data (a legitimate relayer just relays the real Ethereum log through `T::GatewayAddress`/`Verifier` checks) [3](#0-2) , so this does not require a malicious relayer, prover, or governance actor — any correctly-verified receipt for a message whose Ethereum-side dispatch reverted (`success = false`) still flows through the same code path.

This breaks the pivot invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — here the queue advances (order removed, reward paid) even though execution on the Ethereum side explicitly failed.

### Impact Explanation
- Relayers are rewarded for messages that failed to execute on Ethereum, an underpriced/incorrect payout (value paid without the corresponding successful settlement).
- `PendingOrders::remove(nonce)` permanently discards the order once a receipt (success or not) is processed, so there is no path left to retry, refund, or reconcile a failed delivery — a form of state that can no longer reflect the true delivery status, since nothing else tracks failed nonces for correction.
- Given `AfterServiceAccreditationModified`-style flows in the original report caused hard-fork-level remediation on mainnet, an analogous permanent record-loss here (deleted `PendingOrder` for a failed delivery) is similarly unrecoverable outside a governance/storage-migration intervention.

### Likelihood Explanation
This will surface on any legitimate `InboundMessageDispatched` event that Ethereum emits with `success = false` (e.g., a reverting command execution on the Gateway contract) — a normal, expected occurrence in bridge operation, not an adversarial one. Any relayer submitting the (still cryptographically genuine) receipt through `EthereumOutboundQueueV2::submit_delivery_receipt` triggers this code path.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`:
- If `true`, proceed with the existing reward + `PendingOrders::remove` logic.
- If `false`, do not pay the reward from the fee (or route it into failure-handling logic), and either retain/mark the order for retry accounting or emit a distinct `MessageDeliveryFailed` event instead of removing it silently as `MessageDelivered`.

### Proof of Concept
```rust
// In outbound-queue-v2 test harness
let nonce = 1;
let fee: u128 = 1_000_000;
PendingOrders::<Test>::insert(nonce, PendingOrder { nonce, fee, block_number: System::block_number() });

let relayer: AccountId32 = [7u8; 32].into();
let mut receipt = mock_delivery_receipt(); // gateway matches T::GatewayAddress
receipt.nonce = nonce;
receipt.success = false; // Ethereum-side execution reverted

// Reward is paid and order removed despite success == false
assert_ok!(EthereumOutboundQueueV2::process_delivery_receipt(relayer.clone(), receipt));
assert!(PendingOrders::<Test>::get(nonce).is_none()); // order gone, unrecoverable
// relayer balance/reward ledger shows `fee` credited even though delivery failed
```

**Note on scope confidence:** I was unable to fully inspect the `submit_delivery_receipt` extrinsic wrapper source (only located via grep, not fully read) to confirm no upstream check on `success` exists before calling `process_delivery_receipt`; based on the function body itself and its doc/event naming (`MessageDelivered` emitted unconditionally), no such check is present in the reviewed code path.

```rust
impl TryFrom<&Log> for DeliveryReceipt {
	type Error = DeliveryReceiptDecodeError;

	fn try_from(log: &Log) -> Result<Self, Self::Error> {
		let topics: Vec<B256> = log.topics.iter().map(|x| B256::from_slice(x.as_ref())).collect();

		let event = InboundMessageDispatched::decode_raw_log_validate(topics, &log.data)
			.map_err(|_| DeliveryReceiptDecodeError::DecodeLogFailed)?;

			gateway: log.address,
			nonce: event.nonce,
			topic: H256::from_slice(event.topic.as_ref()),
			success: event.success,
			reward_address: event.reward_address.0,
		})
	}
```

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
