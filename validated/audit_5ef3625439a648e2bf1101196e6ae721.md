### Title
Attacker permanently/temporarily DoSes a victim's deposits and position management by filling `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` with dust `DepositToken.transfer`s - (File: contracts/Pool.sol)

### Summary
`DepositToken.transfer` is a public, permissionless entry point that calls `Pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance transitions from 0 to a positive value. `addToDepositTokensOfAccount` enforces `debtTokensOfAccount.length + depositTokensOfAccount.length < MAX_TOKENS_PER_USER (30)` and reverts otherwise. Because adding an entry requires only a dust transfer, an unprivileged attacker can cheaply force entries into a victim's per-account token list, causing subsequent deposits into new collateral types (and seizures received during liquidation) to revert — a resource-exhaustion DoS analogous to the CVE's attacker-triggered resource leak. ### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` on any 0→positive balance transition, with no minimum amount. [4](#0-3) 
- `transfer`/`transferFrom` only check `_revertIfLocked(sender_)`; the recipient's list growth is unconditional. [5](#0-4) 
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts once a user holds 30 distinct deposit+debt tokens. [6](#0-5) 
- Any new deposit into a collateral the victim doesn't already hold goes through `DepositToken._mint`, which calls `addToDepositTokensOfAccount` and reverts when the list is full. [7](#0-6) 
- `seize` uses the same `_transfer`, so a liquidator account already at the cap also cannot receive a new collateral type. [8](#0-7) 

### Impact Explanation
Temporary freezing of funds / denial of service: a victim saturated with dust deposit tokens cannot deposit into any additional collateral type and cannot receive new deposit tokens until they manually zero out an entry. During a falling market, being unable to add new collateral to avoid liquidation converts this into realized losses. The attacker only needs dust amounts of existing deposit tokens, and can front-run the victim's cleanup transactions to re-add the entry, making the freeze effectively persistent while the attacker is active.

### Likelihood Explanation
Requires only an EOA, public `transfer` calls, and negligible token amounts; no privileged roles, oracle manipulation, or reentrancy needed. Cost scales with the number of deposit tokens needed to reach 30 entries. Mitigated only by the victim spending gas to clear entries and racing the attacker's re-dusting.

### Recommendation
Skip the accounting addition for dust amounts (e.g., require a minimum threshold before calling `addToDepositTokensOfAccount`), or allow `deposit`/`seize` paths to opt out of list insertion for victims of unsolicited transfers (e.g., an allowlist/opt-in flag per account per token), or charge the caller for the storage write.

### Proof of Concept
```solidity
// Foundry fork-style test
function test_DustGriefing_FillsTokenList() public {
    // Assume pool has deposit tokens DT[0..n)
    uint256 max = pool.MAX_TOKENS_PER_USER(); // 30

    // 1. Victim already holds (max - 1) tokens
    for (uint256 i = 0; i < max - 1; ++i) {
        depositToken[i].transferFrom(attacker, victim, 1 ether);
    }

    // 2. Attacker dusts victim with a token victim doesn't hold
    depositToken[max - 1].transferFrom(attacker, victim, 1);
    assertEq(pool.getDepositTokensOfAccount(victim).length, max);

    // 3. Victim tries to deposit into a new collateral type -> reverts
    IERC20(newUnderlying).approve(address(newDepositToken), type(uint256).max);
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(100 ether);
}
```
Validated path: `DepositToken.deposit → _mint → pool.addToDepositTokensOfAccount → onlyIfAdditionWillNotReachMaxTokens` reverts once the list is at capacity; entries are added unsolicited via `DepositToken.transfer → _transfer → addToDepositTokensOfAccount`.
