### Title
Equal-version chunk resubmission is accepted by `validate_received_chunk`'s relay-layer check but rejected as stale by `try_replace_chunk`'s storage-layer check, causing inventory/gossip to advertise a chunk version that is never actually stored - ([File: stackslib/src/net/stackerdb/mod.rs] / [File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBSync::validate_received_chunk` uses `data.slot_version < *expected_version` (strict less-than) to reject stale chunks, so a chunk resubmitted at exactly the currently-stored `slot_version` is treated as valid. `StackerDBs::try_replace_chunk` uses `slot_desc.slot_version <= slot_validation.version` (less-than-or-equal), so that same equal-version chunk is rejected by storage as `StaleChunk`. In `handle_unsolicited_StackerDBPushChunk`, the inventory is patched and the message is queued for relay/forwarding based purely on the `validate_received_chunk` result, independent of whether storage will accept it.

### Finding Description
In `validate_received_chunk` (stackslib/src/net/stackerdb/mod.rs:699-706), the staleness check is:
```rust
if data.slot_version < *expected_version {
    ...
    return Ok(false);
}
```
This accepts `data.slot_version == *expected_version` as valid.

In `try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:424-429), the equivalent staleness check is:
```rust
if slot_desc.slot_version <= slot_validation.version {
    return Err(net_error::StaleChunk { ... });
}
```
This rejects `slot_desc.slot_version == slot_validation.version` as stale.

In `handle_unsolicited_StackerDBPushChunk` (stackslib/src/net/stackerdb/mod.rs:742-871), when a `StackerDBChunkInv` reply is constructed, `data.slot_versions` (the expected/current versions, sourced from the local DB via `get_slot_versions`/`make_StackerDBChunksInv_or_Nack`) is passed into `validate_received_chunk` at line 785. If the pushed chunk's `slot_version` equals the locally stored version and it is correctly signed, `validate_received_chunk` returns `Ok(true)`. The code then unconditionally does:
```rust
*slot_version = chunk_data.chunk_data.slot_version;
```
(line 807) advertising in the outgoing `StackerDBChunkInv` reply that this node now has this slot at this version, wakes up the sync state machine, and returns `(false, true)` — i.e., "forward to relayer" — all without storage having actually accepted or persisted the chunk. The chunk is later attempted to be persisted via `try_replace_chunk`, which will reject it as `StaleChunk` because of the `<=` comparison. The relay/inventory-advertisement decision and the storage decision therefore disagree specifically at the equal-version boundary.

### Impact Explanation
An unprivileged remote peer who already legitimately owns/controls a slot (or simply replays an old but correctly-signed chunk at the current version) can cause a node to: (1) advertise via `StackerDBChunkInv` that it possesses a newer/current version of a slot's chunk, (2) forward/relay the chunk data onward to the relayer/other peers, and (3) wake up its sync state machine to propagate this belief — while its actual on-disk storage never updates and continues to reject the identical write as stale. This produces a served-vs-stored mismatch: the node's gossiped inventory diverges from its persisted StackerDB contents, and peers that later request this "version" from this node will not get it, or will get stale data while the inventory claims otherwise. This matches the "network-wide propagation of forged/inconsistent data" Critical category since the mismatch is now gossiped further via the chunk-inv exchange and relay forwarding.

### Likelihood Explanation
The precondition is only that the attacker can send a correctly-signed `StackerDBPushChunkData` for a slot they already legitimately hold, at the exact `slot_version` currently stored by the target node. No secret, no privileged role, and no additional access is required beyond normal P2P reachability and the attacker's own valid slot-signing key — which is squarely within the unprivileged threat model. It is trivially repeatable each time a node is at a given version, since any legitimate signer can just resend their last-known-good chunk to any peer to reproduce the inconsistency.

### Recommendation
Align the two staleness checks to use the same comparison operator so that relay/inventory decisions and storage decisions agree. Either change `validate_received_chunk`'s check to `data.slot_version <= *expected_version` (reject equal-or-less, matching storage), or change `try_replace_chunk`'s check to `slot_desc.slot_version < slot_validation.version` (accept equal, matching relay) — but critically, whichever direction is chosen, `handle_unsolicited_StackerDBPushChunk` should not patch/advertise the inventory version optimistically before the chunk has actually been durably stored.

### Proof of Concept
Rust test plan for `stackslib/src/net/stackerdb/mod.rs` / `db.rs`:
1. Set up a `StackerDBs` instance with one configured contract/slot, with a signer keypair, and insert an initial chunk at `slot_version = 5` via `try_replace_chunk` (should succeed).
2. Construct a `StackerDBChunkData`/`SlotMetadata` for the same slot with `slot_version = 5` (identical version), correctly signed by the same signer key.
3. Call `StackerDBSync::validate_received_chunk(..., expected_versions=[5])` and assert it returns `Ok(true)` (relay layer accepts).
4. Call `StackerDBs::try_replace_chunk(...)` with the same `SlotMetadata`/chunk and assert it returns `Err(net_error::StaleChunk { .. })` (storage layer rejects).
5. Assert the mismatch: `relay_decision == true && storage_decision == Err(StaleChunk)`, demonstrating that `handle_unsolicited_StackerDBPushChunk` would advertise/relay a chunk version its own storage never persists.
