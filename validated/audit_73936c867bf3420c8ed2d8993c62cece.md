### Title
Fixed liquidation fees can make unhealthy positions undercollateralized and create bad debt - ([File: `contracts/Pool.sol`])

### Summary
`Pool.liquidate()` always charges the configured liquidation incentive and protocol fee without checking whether the collateral seized exceeds the value required to improve the position. For an unhealthy position whose collateral ratio is below `1 + liquidatorIncentive + protocolFee`, liquidation reduces the collateral ratio; repeated liquidations can convert an initially overcollateralized position into bad debt. [1](#0-0) 

### Finding Description
`quoteLiquidateOut()` prices `amountToRepay_` in the selected collateral, adds `liquidatorIncentive` to the liquidator payment, adds `protocolFee`, and returns their sum as `_totalToSeize`. [2](#0-1) 

`liquidate()` permits any non-self caller to repay up to `maxLiquidable` of the victim’s debt after verifying only that `debtPositionOf(account_)` is unhealthy. [3](#0-2) 

After quoting the seizure amount, it checks only that the victim owns enough deposit tokens, then burns the liquidator’s synthetic tokens, burns the victim’s debt, and transfers collateral to the liquidator and fee collector. [4](#0-3) 

There is no check that the post-liquidation collateral ratio is greater than the pre-liquidation ratio. If `C` is the collateral value, `D` is the debt value, `x` is the repaid debt value, and `k = 1 + liquidatorIncentive + protocolFee`, the ratio changes from `C / D` to `(C - kx) / (D - x)`, which decreases whenever `C / D < k`. [2](#0-1) 

The default initialization configures a 10% liquidator incentive and 8% protocol fee, giving `k = 1.18`; positions with a collateral ratio below 118% therefore deteriorate when liquidated under that configuration. [5](#0-4) 

The position can simultaneously be overcollateralized and unhealthy because health is based on the collateral-factor-weighted limit rather than a 100% collateral ratio. [6](#0-5) 

For example, the Hemi USDC deposit token is configured with an 85% collateral factor, so a position with a collateral ratio between 100% and approximately 117.65% is both overcollateralized and liquidatable. [7](#0-6) 

`DepositToken.seize()` is callable by the pool and transfers even collateral that is locked for the victim’s ordinary withdrawals or transfers. [8](#0-7) 

### Impact Explanation
An unprivileged liquidator can repeatedly call `Pool.liquidate()` and extract collateral at a premium while leaving progressively less collateral per unit of debt. [9](#0-8) 

With `k = 1.18`, a victim holding `$1,100` of collateral and `$1,000` of debt has a 110% collateral ratio; if the collateral factor is 85%, the position is unhealthy because its `$935` issuable limit is below the `$1,000` debt. [6](#0-5) 

A 50% liquidation repays `$500` of debt but seizes `$590` of collateral, leaving `$510` of collateral against `$500` of debt and reducing the collateral ratio from 110% to 102%. [10](#0-9) 

A second maximum liquidation repays `$250` and seizes `$295`, leaving `$215` of collateral against `$250` of debt, while a third repays `$125` and seizes `$147.50`, leaving only `$67.50` of collateral against `$125` of debt. [4](#0-3) 

This creates protocol bad debt from a position that was initially overcollateralized and gives the liquidator an immediate premium for worsening protocol solvency. [11](#0-10) 

### Likelihood Explanation
The vulnerable region is reachable whenever collateral value falls or debt grows enough for debt to exceed the collateral-factor-adjusted limit while the raw collateral ratio remains below `1 + totalLiquidationFees`. [6](#0-5) 

No privileged role, oracle failure, governance change, or protocol action is needed for liquidation once such a position exists; the attacker needs only enough synthetic tokens to repay and can call the public `liquidate()` function directly. [12](#0-11) 

`maxLiquidable` defaults to 50%, so the attacker can execute the harmful sequence through repeated public calls rather than relying on a single full liquidation. [13](#0-12) 

The deployed implementation’s runtime fee values may have changed after initialization, so the exact vulnerable collateral-ratio boundary is `1 + liquidatorIncentive + protocolFee` rather than necessarily 118%. [14](#0-13) 

### Recommendation
Cap the total collateral seized so every permitted liquidation strictly improves the victim’s collateral ratio. [1](#0-0) 

Before executing the seizure, calculate the victim’s pre- and post-liquidation collateral ratios and revert unless `(C - totalToSeize) / (D - amountToRepay) > C / D`; equivalently, for a fixed-fee design, revert whenever `C / D <= 1 + liquidatorIncentive + protocolFee`. [15](#0-14) 

Alternatively, dynamically reduce the liquidation bonus below `C / D - 1` for low-collateral-ratio positions, while preserving enough incentive for liquidators to repay bad or nearly bad debt. [14](#0-13) 

The check should use USD-valued collateral and debt rather than raw token amounts so it remains correct for multiple collateral and debt assets. [16](#0-15) 

### Proof of Concept
A Foundry fork test can reproduce the sequence by forking a deployment, creating or selecting a position with `$1,100` collateral and `$1,000` debt on an 85% collateral-factor asset, and setting an oracle price state that reflects a legitimate collateral-price decline before making the attacker calls. [7](#0-6) 

```solidity
function testLiquidationWorsensPosition() public {
    // Fork a production deployment and obtain Pool, DebtToken,
    // DepositToken, SyntheticToken, and an unhealthy victim.
    // Assumptions:
    //   collateralFactor = 0.85e18
    //   liquidatorIncentive = 0.10e18
    //   protocolFee = 0.08e18
    //   collateral value = 1_100 USD
    //   debt value = 1_000 USD

    uint256 collateralBefore = 1_100e18;
    uint256 debtBefore = 1_000e18;

    // 110% collateral ratio, but debt is unhealthy:
    // 1_000 > 1_100 * 0.85 = 935.
    assertGt(collateralBefore, debtBefore);

    uint256 repay = debtBefore / 2;
    pool.liquidate(syntheticToken, victim, repay, depositToken);

    // Seized value = 500 * 1.18 = 590.
    // Remaining collateral = 510; remaining debt = 500.
    // Collateral ratio falls from 110% to 102%.

    repay = debtToken.balanceOf(victim) / 2;
    pool.liquidate(syntheticToken, victim, repay, depositToken);

    // Second liquidation leaves collateral value of 215
    // against debt of 250: the account is undercollateralized.
}
```

The numerical result follows directly from `_totalToSeize = repaymentValue + liquidatorIncentive + protocolFee` and the 50% `maxLiquidable` bound. [17](#0-16) 

The oracle adjustment in test setup is not the attacker action; it establishes the state produced by a normal market decline or interest accrual, after which every state-changing call is made by an unprivileged liquidator through the public `liquidate()` entry point. [9](#0-8)
