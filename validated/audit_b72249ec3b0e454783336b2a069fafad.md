### Title
Legacy AMM re-activation via `allowHardenExchangeCalculation` reopens deprecated `ExchangeTransactionContract` swap path with faulty pool-draw logic - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
The `ExchangeTransactionContract` swap path (java-tron's AMM-style "bancor" exchange, analogous to a DEX swap contract) was deprecated and blocked network-wide after fork `VERSION_4_8_0_1` because of known correctness problems in its pool math. A newer `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal/flag was added to "harden" (overflow-check) the same swap math, but the gating function `isExchangeTransaction` was implemented so that turning the harden flag on **completely un-blocks** the legacy swap contract type everywhere it is checked (`pushTransaction`, block generation, and `rejectExchangeTransaction`). This mirrors the SQUID Game root cause: a swap/exchange contract with faulty logic design that is reachable by any ordinary user and can be exploited to drain pooled liquidity/asset balances.

### Finding Description
`Manager.isExchangeTransaction` decides whether a transaction should be treated as (and therefore rejected as) an `ExchangeTransactionContract`: [1](#0-0) 

```java
private boolean isExchangeTransaction(Transaction transaction) {
  if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
    return false;
  }
  ...
}

private void rejectExchangeTransaction(Transaction transaction) throws ContractValidateException {
  if (isExchangeTransaction(transaction) && chainBaseManager.getForkController()
          .pass(Parameter.ForkBlockVersionEnum.VERSION_4_8_0_1)) {
    throw new ContractValidateException("ExchangeTransactionContract is rejected");
  }
}
```

This single boolean short-circuits every enforcement point that was added to retire the legacy swap contract:
- `pushTransaction` refuses to even queue an exchange tx when `isExchangeTransaction` is true [2](#0-1) 
- block generation skips packing exchange transactions when `isExchangeTransaction` is true [3](#0-2) 
- `rejectExchangeTransaction` throws for exchange contracts post-fork.

When any Super Representative proposal or default configuration sets `allowHardenExchangeCalculation` to `1` (this is a normal, non-privileged-attacker-controlled chain parameter toggle intended purely to make the swap math overflow-safe, not to re-legalize the contract type), the deprecated AMM swap becomes fully reachable again by any signed transaction from an ordinary account: `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` all execute normally.

The re-enabled swap math itself, in `ExchangeCapsule.transaction`, still uses the legacy bancor-style continuous formula with floating-point `Math.pow` (non-hardened branch) and, even in the "hardened" branch, relies on lossy `double` conversions inside `SafeExchangeProcessor`: [4](#0-3) 

```java
double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
return SUPPLY.negate().multiply(
    BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
...
double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
BigDecimal exchangeBalance = bdBalance.multiply(
    BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
```

The "hardening" only adds `addExact`/`subtractExact` overflow checks around the pool-balance updates in `ExchangeCapsule.transaction` [5](#0-4) ; it does not fix the underlying floating-point-derived exchange-rate calculation that motivated the outright ban of `ExchangeTransactionContract` after `VERSION_4_8_0_1`. Repeated small swaps that exploit rounding/precision loss in the `double`-based `Maths.pow`/`StrictMathWrapper.pow` conversion (an amplification technique structurally identical to the SQUID Game swap-tax/logic exploit) let an attacker extract more of the counter-token than the pool should yield, draining the exchange pool's TRX/TRC10 balance over many transactions.

### Impact Explanation
This allows an unprivileged transaction broadcaster to perform unauthorized value extraction from any `Exchange`/`ExchangeV2` liquidity pool once `ALLOW_HARDEN_EXCHANGE_CALCULATION` is set to `1` — a state that is explicitly supported and toggled by proposal, not by malicious actors, meaning it is a reachable production configuration. The result is theft of pooled TRX/TRC10 assets from the exchange pool and other participants' claims against it, matching the SQUID Game class of loss (asset drain via a swap contract with faulty logic design).

### Likelihood Explanation
Likelihood is Medium: it requires the `ALLOW_HARDEN_EXCHANGE_CALCULATION` proposal to be active (a legitimate, expected on-chain governance action, not a compromise), after which any ordinary account can call `ExchangeCreateActuator`/`ExchangeTransactionActuator` with no special privilege, exactly as it could before the contract type was banned. No signature/permission bypass is needed — only normal `ExchangeTransactionContract` broadcasting.

### Recommendation
- Decouple the "harden calculation" safety flag from the "is this contract type banned" decision. `isExchangeTransaction`/`rejectExchangeTransaction` should continue to reject `ExchangeTransactionContract` (and related Exchange* contracts) after `VERSION_4_8_0_1` regardless of `allowHardenExchangeCalculation`, unless a separate, explicit "re-enable exchange" governance flag is introduced.
- If legacy Exchange contracts are intentionally being re-enabled, replace the floating-point `Math.pow`/`double` based bancor formula entirely with a fixed-point/BigDecimal implementation verified against known correctness invariants (constant product/invariant checks, slippage bounds), rather than only adding overflow guards around the balance bookkeping.
- Add invariant checks in `ExchangeCapsule.transaction` (e.g., verifying the product/invariant of pool balances does not decrease beyond fees) to detect and reject swaps that would drain the pool disproportionately.

### Proof of Concept
1. A Super Representative proposal sets `ALLOW_HARDEN_EXCHANGE_CALCULATION = 1` (a supported, documented governance action) — see `ProposalService.process` handling of this case [6](#0-5) .
2. `Manager.isExchangeTransaction` now returns `false` for any `ExchangeTransactionContract`, so `pushTransaction` and block packing no longer reject it [7](#0-6) .
3. An attacker creates or uses an existing `Exchange`/`ExchangeV2` pool and repeatedly submits `ExchangeTransactionContract` swaps through `ExchangeTransactionActuator.execute`, exploiting the double-precision rounding in `ExchangeCapsule.transaction`/`SafeExchangeProcessor.exchangeFromSupply` to extract more counter-token than the pool's true invariant should allow, draining the pool over many transactions — directly analogous to the SQUID Game swap-contract exploit that drained ~$87,000 via faulty swap logic.

Note: I was unable to fully verify the precise numeric magnitude of the rounding exploit (i.e., an exact repeatable overflow/underflow sequence) within the available indexed context; a background Devin session with full repo/test access would be needed to construct and validate a concrete numeric PoC against `ExchangeProcessorTest`/`ExchangeTransactionActuatorTest`.

```java
  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
```

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```
