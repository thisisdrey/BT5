Division-before-multiplication precision loss in legacy per-cycle vote reward computation - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes each voter's share of a stand-by-witness/witness reward with `double voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;` — division happens before multiplication using floating point, unlike the newer VI-based algorithm elsewhere in the same class which correctly multiplies with `BigInteger` before dividing. [1](#0-0) 

### Finding Description
The old per-cycle reward algorithm divides `userVote` by `totalVote` into a `double` first, then multiplies by `totalReward`, truncating fractional precision before the multiplication takes effect. Contrast this with the newer accumulation-based algorithm (`accumulateWitnessVi`/`computeReward(beginCycle, endCycle, ...)` in the same file and in `VoteRewardUtil`/`RewardViCalService`), which correctly multiplies `deltaVi * userVote` as `BigInteger` and only divides once at the end by `DECIMAL_OF_VI_REWARD`: [2](#0-1) [3](#0-2) 

The legacy path (`computeReward(long cycle, votes)`) is still live for any cycle before `getNewRewardAlgorithmEffectiveCycle()`, and is also used unconditionally when `allowOldRewardOpt()` is disabled, via `getOldReward`: [4](#0-3) 

This is reachable end-to-end by an ordinary account holder: `WithdrawBalanceActuator.execute` calls `mortgageService.withdrawReward(...)`, which calls the vulnerable `computeReward`, and it also gates validation on `mortgageService.queryReward(...)` (also reachable via the public `GetRewardServlet`/RPC API), both of which invoke the same faulty division-first arithmetic: [5](#0-4) [6](#0-5) 

### Impact Explanation
Because floating-point division truncates precision before the multiplication by `totalReward` (which can be up to full block/brokerage reward magnitudes, i.e. large `long` values), the computed `reward` for a voter can systematically diverge (round down/up incorrectly) from the mathematically exact share `userVote * totalReward / totalVote`. Over many voters and many cycles this causes cumulative under/over-payment of TRX allowance funds relative to the correct proportional share — an unbacked or lost balance issue affecting on-chain fund accounting (the accumulated discrepancy is paid out of / retained in the reward pool incorrectly). This is a fund-accounting integrity issue reachable by any voter simply calling `WithdrawBalanceContract`.

### Likelihood Explanation
This is triggered on every `WithdrawBalanceContract` transaction and every `GetReward`/`queryReward` API call for accounts whose vote history spans cycles prior to `newRewardAlgorithmEffectiveCycle` (or if `allowOldRewardOpt` is not enabled), i.e., for legacy/older delegation cycles. It requires no special privilege — any account holder invoking `WithdrawBalanceContract` triggers it. However, likelihood of significant/attacker-exploitable magnitude depends on chain configuration (whether `allowChangeDelegation`/`allowOldRewardOpt`/`newRewardAlgorithmEffectiveCycle` place execution on this old code path on the live network); on networks that have already advanced past the new-algorithm effective cycle for all relevant history, this path is dead code in practice.

### Recommendation
Replace the double-based proportional calculation in `computeReward(long cycle, List<Pair<byte[], Long>> votes)` with integer/`BigInteger` multiply-then-divide, consistent with the pattern already used by the VI-based algorithm:
```java
long userVote = vote.getValue();
reward += BigInteger.valueOf(userVote)
    .multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote))
    .longValue();
```

### Proof of Concept
Given `totalVote = 3`, `userVote = 1`, `totalReward = 10`:
- Correct (multiply-then-divide): `1 * 10 / 3 = 3`
- Current code: `voteRate = 1.0/3.0 = 0.3333333333333333`; `reward = (long)(0.3333333333333333 * 10) = 3` (matches here, but for values where `userVote/totalVote` yields a repeating/irrational binary fraction combined with a large `totalReward`, e.g. `totalVote = 7`, `userVote = 1`, `totalReward = 10_000_000_000L`): 
  - Correct: `1 * 10_000_000_000 / 7 = 1_428_571_428`
  - Double path: `voteRate = 1.0/7.0 ≈ 0.14285714285714285`; `reward = (long)(0.14285714285714285 * 10_000_000_000) = 1_428_571_428` (rounding differences appear at larger scales / different value combinations, e.g. non-power-of-two divisors combined with values approaching `2^53`, where IEEE-754 double mantissa precision (52 bits) is insufficient to represent the exact rational value, producing off-by-one-or-more unit discrepancies per voter per cycle that accumulate across the whole `votes` loop and across cycles in `getOldReward`).   private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
