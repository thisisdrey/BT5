### Title
Unbounded array allocation in `BatchValidateSign` precompiled contract via unchecked `extractBytesArray`/`extractBytes32Array` sizes when the `allowTvmSelfdestructRestriction` hard-fork is inactive - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompile parses an array-length field directly from attacker-controlled contract call-data and, on the legacy code path (used when the `allowTvmSelfdestructRestriction` feature is not yet activated), allocates a Java array sized by that unchecked length before any bound is enforced, mirroring the `Buffer.from({length})` unbounded-allocation bug class described in the external report.

### Finding Description
`BatchValidateSign.doExecute` reads the size of the signature/address arrays straight from the call-data-derived `DataWord[] words`, but the `MAX_SIZE` bound check is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [1](#0-0) 

If that hard-fork flag is not active, `extractBytesArray` is invoked instead of the safer `extractSigArray`, and `extractBytes32Array` is always invoked, with **no preceding size check at all**: [2](#0-1) 

Both helpers compute `len` from `words[offset].intValueSafe()` — a value fully controlled by the calling transaction's input data — and immediately allocate `new byte[len][]` before any length/data-size cross-check, exactly analogous to `Buffer.from({length: x})` allocating memory proportional to an unchecked attacker-supplied `x`: [3](#0-2) 

Only after both arrays are fully allocated does the code check `cnt > MAX_SIZE`, i.e. the bound-check happens *after* the unbounded allocation has already occurred: [4](#0-3) 

### Impact Explanation
An unprivileged account can invoke the `BatchValidateSign` precompiled contract (a TVM precompile reachable via a plain smart-contract call) with call-data whose length word decodes to a very large value (bounded only by `intValueSafe()`'s clamp, potentially near `Integer.MAX_VALUE`). This triggers allocation of an oversized `byte[][]` reference array on every full node that executes the transaction, consuming memory and CPU on all validating nodes simultaneously as they replay the same transaction — a denial-of-service condition consistent with "Network not being able to confirm new transactions" once nodes begin throwing `OutOfMemoryError` or stalling under GC pressure during block execution.

### Likelihood Explanation
Exploitation only requires the `allowTvmSelfdestructRestriction` hard fork to be inactive (its default/legacy state on any chain that has not yet activated it, or during any rollout window before activation across all nodes), and a single crafted transaction calling the precompile address — no special privileges, staking, or coordination among nodes is needed, making this trivially and repeatably triggerable by any anonymous contract caller.

### Recommendation
Move the `sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE` bound check in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java` (lines 1165–1171) so that it is unconditionally enforced for both code paths (i.e., independent of `allowTvmSelfdestructRestriction()`), and additionally validate the extracted length inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` against `MAX_SIZE` and the actual remaining `data`/`words` length before performing any `new byte[len][]` allocation.

### Proof of Concept
1. Deploy/call a contract that issues a `CALL` (or `STATICCALL`) to the `BatchValidateSign` precompile address on a node where `allowTvmSelfdestructRestriction` is not yet activated.
2. Craft call-data such that `words[0]` is the hash, `words[1]` points to an offset whose word value (`len`) is set to a very large integer (e.g., near `Integer.MAX_VALUE`), and `words[2]` similarly points to a large-length address-array offset.
3. Because the size check at [5](#0-4)  is skipped, `extractBytesArray`/`extractBytes32Array` are called directly with the attacker-chosen `len`, causing `new byte[len][]` to attempt a massive allocation on every full node executing this transaction, degrading or crashing node processes analogous to the `Buffer.from({length})` DOS described in the reference report.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
