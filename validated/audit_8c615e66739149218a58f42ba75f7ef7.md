### Title
Permanent oracle-halt causes protocol-wide denial of service across borrow, withdraw, liquidation and health checks - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`price-resolve` in `v0-4-market.clar` fetches an external Pyth/DIA price and immediately asserts freshness/legality with `unwrap!`/`asserts!`, with no fallback path. If the external price feed becomes unavailable or stale — whether because the Pyth relayer/governance stops publishing, or because a feed is simply not updated for any external reason — every function on the health/collateral path that calls into `price-resolve`/`price-multi-resolve` reverts, freezing user funds.

### Finding Description
`call-pyth` reads the Pyth price via a hard external `contract-call?` and `unwrap!`s the result into `ERR-ORACLE-PYTH` on any failure: [1](#0-0) . `resolve-dia` similarly propagates failure via `try!` with no recovery: [2](#0-1) .

`price-resolve` then combines the resolved price with a hard staleness/legality assertion — `oracle-price-legal` and `oracle-timestamp-fresh` are checked with `asserts! ... ERR-ORACLE-INVARIANT`, which aborts the whole call if the upstream feed is stale (`delta > max-staleness`) or the price is zero: [3](#0-2) . There is no try/catch-equivalent fallback (e.g. last-known-good price, TWAP, or manual override) — any of these failure modes bubbles straight up.

`price-multi-resolve`/`iter-price-multi` batches this same non-recoverable resolution across all assets involved in a single call: [4](#0-3) . Because collateral/debt valuation (`sum-collateral-usd`, `sum-debt-usd`, `get-asset-price`) all route through this same price path, a single unavailable/stale feed for *any* asset used in a position blocks health checks for that entire position: [5](#0-4) .

The underlying Pyth storage contract itself enforces a staleness threshold at write time (`write-batch-entry`), meaning if the off-chain relayer/governance stops submitting price updates (analogous to a Chainlink multisig withholding a feed), the stored price silently ages past `max-staleness` and the mainnet `read`/`get-price` calls used by the market keep returning the last (now stale) entry, which then fails the freshness assertion in `price-resolve` permanently until updates resume: [6](#0-5) .

### Impact Explanation
Since every deposit/borrow/withdraw/liquidate/health-check path that needs to price collateral or debt funnels through `price-resolve`/`price-multi-resolve`, an oracle outage (feed pause, relayer failure, governance-level feed block) causes a hard revert for all of these operations for the affected asset(s). This is a temporary freezing of funds: users cannot withdraw collateral or have positions liquidated/managed while the feed is down, matching the in-scope "temporary freezing of funds" impact class. It does not cause direct fund theft or permanent freezing, since normal operation resumes once the feed is restored.

### Likelihood Explanation
This does not require any bug or compromise in Zest's own code — only an external Pyth (or DIA) feed outage, staleness, or a governance-triggered pause of the price-writer flow, which is a realistic, externally-triggerable condition just as with the original Chainlink-multisig report. Given every price consumer path lacks any try/catch or fallback price mechanism, the likelihood of a full functional DoS window whenever the external oracle infrastructure stalls is high.

### Recommendation
Wrap the external oracle calls (`call-pyth`, `call-dia`, and the staleness/legality assertions in `price-resolve`) so that failures degrade gracefully instead of hard-reverting: e.g., fall back to the last successfully cached price (already tracked via `oracle-last-update`) within a bounded grace window, or provide a permissioned pause/override mechanism that still allows account-safe operations (repay, add collateral) to proceed while blocking only actions that strictly require fresh pricing (borrow, liquidate at the edge). At minimum, expose the staleness/failure state to callers so functions can differentiate "no price available" from "unhealthy position" rather than reverting the whole batch in `iter-price-multi`.

### Proof of Concept
1. Pyth's relayer/governance stops submitting updates for a given feed (e.g. `PYTH-STX`), or governance pauses writes via `pyth-governance-v3`.
2. The stored entry in `pyth-storage-v4` ages past the configured `max-staleness` without violating `write-batch-entry`'s own staleness assert (no new write occurs, so that check never re-triggers) [7](#0-6) .
3. Any Zest user calls a market function that needs to value STX collateral or debt (borrow, withdraw, liquidate, or a health check), which calls `price-multi-resolve` → `price-resolve` for STX.
4. `oracle-timestamp-fresh` computes `delta = stacks-block-time - timestamp > max-staleness` and the `asserts!` fails with `ERR-ORACLE-INVARIANT`, reverting the entire user transaction [8](#0-7) .
5. Every subsequent call touching an STX-priced position fails identically until the feed resumes updating, freezing user funds/operations for the duration of the outage.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))

      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
