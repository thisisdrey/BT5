### Title
Active-permission holder can be granted (or tricked into signing under) `AccountPermissionUpdateContract` rights and use them to overwrite Owner/Witness/other-Active permissions of the account - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateContract` (multi-sig permission management) is treated by the signature/permission layer exactly like any other broadcastable contract type: it is dispatched by `permission_id`, and the only gate applied to a non-owner (`permissionId != 0`) signer is that the signer's `Active` permission (a) has type `Active` and (b) has the corresponding contract-type bit set in its 32-byte `operations` bitmap. There is no additional, contract-specific restriction preventing the `AccountPermissionUpdateContract` bit from being enabled inside an `Active` permission, and the actuator's `execute()` unconditionally overwrites the account's Owner permission, Witness permission and the *entire* Active permission list with whatever the caller supplies — not just the Active slot the caller signed with.

### Finding Description
Signature/permission authorization for any transaction is centralized in `TransactionCapsule.checkPermission()`: [1](#0-0) 
For a non-owner permission (`permissionId != 0`), the only checks are that the permission type is `Active` and that `checkPermissionOperations()` finds the contract-type bit set: [2](#0-1) 

`AccountPermissionUpdateActuator.validate()` never checks *which* permission ID was used to authorize the transaction, nor restricts the new permission structure relative to the signer's own privileges — it only validates internal well-formedness of the submitted `owner`/`witness`/`actives` permissions: [3](#0-2) 

Execution then wholesale replaces the account's Owner permission, (optionally) Witness permission, and clears/rebuilds the entire Active permission list: [4](#0-3) 

So if any of the account's `Active` permissions has the `AccountPermissionUpdateContract` bit enabled in its `operations` bitmap (this is not blocked by `checkPermission` in the actuator, which only rejects bits that are globally unavailable chain contract types, not bits that are contract-management-sensitive), a holder of that single narrowly-scoped `Active` key — who may have been granted authority for only "specific operations" (e.g., what would normally be an unprivileged transfer/vote/share-style key) — can sign an `AccountPermissionUpdateContract` transaction and: set a brand-new Owner permission (potentially replacing all original owner keys with the attacker's own key and threshold), delete or alter the Witness permission, and delete/replace every other Active permission (including higher-privileged ones belonging to other co-signers). This mirrors the reported Nextcloud Deck bug class: a lower-privileged, delegated participant abusing a permission-management surface to rewrite the access rights of other principals on the same shared resource (the multisig account), rather than being confined to modifying only their own delegated scope.

### Impact Explanation
This allows a limited-scope multisig participant to unilaterally seize full control of the account (by installing their own Owner permission and removing all other Active permissions), or to strip/downgrade permissions belonging to other legitimate signers, without their consent. Because Owner permission governs the ability to transfer TRX/TRC10 assets, vote, freeze/unfreeze, and perform virtually any other account contract, this results in unauthorized account takeover and potential theft or permanent loss of the account's funds/resources for the other stakeholders in the multisig scheme — squarely within "unauthorized account operation" / "theft or permanent freezing of funds."

### Likelihood Explanation
Exploitation requires that the account owner (or a prior `AccountPermissionUpdateContract` transaction) has enabled the `AccountPermissionUpdateContract` bit within some `Active` permission's `operations` bitmap and granted a key to a less-trusted co-signer for that Active permission — a configuration that is fully permitted by current validation logic and easy to create inadvertently (e.g., an owner grants "broad" active permissions intending it for convenience, or copies bit-masks between permissions without realizing this specific bit's sensitivity). Given that TRON's default multisig documentation/tests enumerate the full contract-type bitmap (see `checkAvailableContractTypeCorrespondingToCode`) as generally "available," and no code path singles out `AccountPermissionUpdateContract` as requiring Owner-only authorization, the misconfiguration is plausible for real, complex multisig setups (custodians, DAOs, exchange hot-wallet multisig groups) that use tiered Active permissions.

### Recommendation
Add an explicit restriction in `AccountPermissionUpdateActuator.validate()` (and/or `TransactionCapsule.checkPermission()`) requiring that `AccountPermissionUpdateContract` may only be authorized via the account's `Owner` permission (`permissionId == 0`), regardless of whether the bit is set in an `Active` permission's operations bitmap — analogous to how permission-management actions in Deck should be restricted to actual owners rather than delegated "share" rights. Alternatively/additionally, disallow enabling the `AccountPermissionUpdateContract` bit at all when constructing/validating an `Active` permission's `operations` field in `checkPermission()`.

### Proof of Concept
1. Account `A` (Owner key `K0`) creates an `AccountPermissionUpdateContract` (signed with Owner permission) that defines `Active` permission slot 2 with `operations` bitmap having the bit for `AccountPermissionUpdateContract` set, and includes co-signer key `K1` in that Active permission with sufficient weight/threshold to act alone (or with collusion).
2. `K1` constructs a new `AccountPermissionUpdateContract` transaction for account `A`: sets `permission_id = 2` (the compromised Active permission), sets `owner` permission to a new permission containing only `K1`'s key with threshold 1, omits/alters other Active permissions.
3. `K1` signs the transaction with only `K1`'s key.
4. `TransactionCapsule.checkPermission()` at [1](#0-0)  accepts it because `permission.getType() == Active` and `checkPermissionOperations` finds the `AccountPermissionUpdateContract` bit set.
5. `AccountPermissionUpdateActuator.validate()`/`execute()` accepts and applies the update, calling `AccountCapsule.updatePermissions()` at [4](#0-3) , replacing account `A`'s Owner permission with `K1`'s permission and wiping out all previous Active permissions (including the original owner `K0`'s Owner permission being entirely replaced and other co-signers' active permissions being removed).
6. `K1` now solely controls account `A`, locking out `K0` and any other prior co-signers.

  private static void checkPermission(int permissionId, Permission permission, Transaction.Contract contract) throws PermissionException {
    if (permissionId != 0) {
      if (permission.getType() != PermissionType.Active) {
        throw new PermissionException("Permission type is error");
      }
      //check operations
      if (!checkPermissionOperations(permission, contract)) {
        throw new PermissionException("Permission denied");
      }
    }
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

  public boolean validate() throws ContractValidateException {

      throw new ContractValidateException(

    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
