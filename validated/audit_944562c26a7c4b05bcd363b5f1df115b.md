### Title
Permissionless `lending_pool_emissions_deposit` allows zero-duration deposit sandwiching to steal pro-rata emissions from real depositors - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`)

### Summary
The Yieldy finding shows that a discrete, permissionless "rebase" event that revalues all outstanding shares pro-rata can be gamed by a user who deposits immediately before the event and withdraws immediately after, capturing rewards despite having zero economic exposure/time-at-risk. Marginfi's `lending_pool_emissions_deposit` instruction is a direct analog to this rebase mechanism: it is permissionless, instantly re-prices `asset_share_value` for every existing share, and marginfi deposits have no lock-up, warm-up, or vesting period at all (i.e., strictly weaker protection than Yieldy's ineffective `warmUpPeriod`).

### Finding Description
`lending_pool_emissions_deposit` lets anyone permissionlessly transfer same-mint "emissions" tokens into a bank's `liquidity_vault` and then immediately re-price `asset_share_value` for the entire pool: [1](#0-0) 

Key mechanics:
- `total_asset_shares` is left unchanged by this instruction (confirmed by the test assertion `shares_after == shares_before`) [2](#0-1) 
- `asset_share_value` is instantly recomputed as `(total_assets + amount) / total_asset_shares` [3](#0-2) 
- Every unit of `asset_shares` currently outstanding — regardless of how long it has been held — is boosted by the same multiplier.

Marginfi deposits mint shares instantly at the current `asset_share_value` with no warm-up/cooldown, and withdrawals redeem shares instantly at the current `asset_share_value`: [4](#0-3) 

This means an attacker can:
1. Deposit a large amount into the target bank via `lending_account_deposit`, minting fresh `asset_shares` at the pre-emissions `asset_share_value`.
2. Call (or simply race/front-run someone else calling) the permissionless `lending_pool_emissions_deposit`, which raises `asset_share_value` pro-rata across all outstanding shares, including the ones just minted in step 1.
3. Immediately call `lending_account_withdraw` (`withdraw_all`) to redeem the shares at the newly boosted `asset_share_value`, capturing a full pro-rata cut of the emissions deposit despite having provided liquidity for effectively zero time and taken on none of the utilization/borrow risk the emissions were meant to compensate.

This is structurally identical to the Yieldy bug class: a discretely-triggered, permissionless "reward materialization" event (rebase / emissions deposit) that instantly and uniformly re-prices all existing shares, combined with instant, unrestricted entry/exit around that event. Marginfi's docs even describe emissions as meant to be earned "on a pro-rata basis in real time" over the campaign duration [5](#0-4) , but the actual same-bank `lending_pool_emissions_deposit` mechanism has no such time-weighting — it is a single atomic step-function applied to whatever shares exist at call time.

### Impact Explanation
An attacker who deposits immediately before triggering (or observing an imminent) `lending_pool_emissions_deposit` and withdraws immediately after can extract value that should have accrued to genuine, longer-term depositors of that bank. This dilutes real depositors' expected emissions yield and constitutes an unfair/unauthorized reallocation of pool value — a direct value-theft primitive analogous to the referenced report, made worse in marginfi because there is no `warmUpPeriod`-style mitigation attempt at all (deposits/withdraws are instant). Because the instruction is same-mint and directly increases `asset_share_value` in the liquidity vault (not a separate incentive token/claim flow), the attacker's gain is realized immediately and directly in the underlying asset upon withdrawal, without needing any further claim step.

### Likelihood Explanation
`lending_pool_emissions_deposit` is explicitly documented as permissionless [6](#0-5) , so any party (including the attacker or an unrelated funder whose transaction can be observed and front-run/same-block-sandwiched) can trigger it. Since `lending_account_deposit` and `lending_account_withdraw` have no cooldown, an attacker can construct a single sandwiching sequence (deposit → emissions_deposit → withdraw_all), which on Solana can even be composed within one transaction if the attacker is the one funding/calling the emissions deposit, making exploitation straightforward and low-cost (aside from the emissions amount itself, of which the attacker recoups their pro-rata share).

### Recommendation
Do not allow freshly-deposited shares to participate in an emissions re-pricing event that occurs in the same slot/transaction, or within a minimum holding window. Options:
- Track a `last_deposit_timestamp` (or slot) per balance and exclude shares deposited after the last emissions-deposit checkpoint from that particular pro-rata boost (e.g., snapshot eligible share supply prior to running `lending_pool_emissions_deposit`, similar to a checkpoint/snapshot reward model).
- Alternatively, restrict `lending_pool_emissions_deposit` so it cannot be invoked in the same transaction as (or within N slots of) a deposit/withdraw by the same authority, or require it be paired with a time-based vesting schedule rather than an instantaneous share-value bump.
- Consider requiring `lending_pool_emissions_deposit` to be permissioned or rate-limited, since it currently has no protection against being weaponized by anyone with capital to sandwich.

### Proof of Concept
1. Attacker deposits `X` USDC into `bank` via `lending_account_deposit`, minting `shares = X / asset_share_value_before`.
2. Attacker (or any observed pending transaction) calls `lending_pool_emissions_deposit(amount = R)` for the same bank/mint. Per `configure_bank.rs` L138-146, this sets `asset_share_value_after = (total_assets_before + R) / total_asset_shares` — including the attacker's freshly-minted shares from step 1 [3](#0-2) .
3. Attacker immediately calls `lending_account_withdraw(withdraw_all = true)`, redeeming `shares * asset_share_value_after`, which is strictly greater than `X` by the attacker's pro-rata share of `R`, despite zero holding duration.
4. Net effect: the attacker walks away with profit taken directly from the emissions pool intended for genuine depositors, and the existing test suite for this instruction confirms the exact share-value formula that enables this (`emissions_same_bank_deposit_updates_asset_share_value`) [7](#0-6) , but does not test/guard against the deposit-immediately-before/withdraw-immediately-after sandwich scenario.

**Note on verification limits:** I was not able to fully inspect `lending_account_deposit`'s handler body in this session (only located its file path) to double-confirm there is zero minimum holding period or deposit cooldown of any kind; based on `lending_account_withdraw`'s code and all encountered tests/docs, no such restriction appears to exist anywhere in the codebase, but a Devin session with full file access should re-confirm `programs/marginfi/src/instructions/marginfi_account/deposit.rs` before treating this as fully proven.

pub fn lending_pool_emissions_deposit(
    ctx: Context<LendingPoolEmissionsDeposit>,
    amount: u64,
) -> MarginfiResult {
    if amount == 0 {
        return Ok(());
    }

    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    utils::validate_bank_state(&bank, utils::InstructionKind::FailsIfPausedOrReduceState)?;

    // Reject mints with non-zero transfer fees or active transfer hooks.
    let mint_ai = ctx.accounts.mint.to_account_info();
    check!(
        !utils::nonzero_fee(mint_ai.clone(), clock.epoch)?,
        MarginfiError::InvalidTransfer
    );
    check!(
        !utils::has_transfer_hook(mint_ai)?,
        MarginfiError::InvalidTransfer
    );

    let total_asset_shares = I80F48::from(bank.total_asset_shares);
    check!(
        total_asset_shares > I80F48::ZERO,
        MarginfiError::EmissionsUpdateError
    );

    bank.accrue_interest(
        clock.unix_timestamp,
        &group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    transfer_checked(
        CpiContext::new(
            ctx.accounts.token_program.key(),
            TransferChecked {
                from: ctx.accounts.emissions_funding_account.to_account_info(),
                to: ctx.accounts.liquidity_vault.to_account_info(),
                authority: ctx.accounts.depositor.to_account_info(),
                mint: ctx.accounts.mint.to_account_info(),
            },
        ),
        amount,
        ctx.accounts.mint.decimals,
    )?;

    let total_assets = bank.get_asset_amount(total_asset_shares)?;
    let updated_total_assets = total_assets
        .checked_add(I80F48::from_num(amount))
        .ok_or_else(math_error!())?;

    bank.asset_share_value = updated_total_assets
        .checked_div(total_asset_shares)
        .ok_or_else(math_error!())?
        .into();

#[tokio::test]
async fn emissions_same_bank_deposit_updates_asset_share_value() -> anyhow::Result<()> {
    let test_f = TestFixture::new(Some(TestSettings::all_banks_payer_not_admin())).await;

    let usdc_bank = test_f.get_bank(&BankMint::Usdc);

    let emissions_funding = test_f.usdc_mint.create_token_account_and_mint_to(50).await;

    let depositor_a = test_f.create_marginfi_account().await;
    let depositor_b = test_f.create_marginfi_account().await;

    let depositor_a_usdc = test_f.usdc_mint.create_token_account_and_mint_to(40).await;
    let depositor_b_usdc = test_f.usdc_mint.create_token_account_and_mint_to(60).await;

    let depositor_a_amount = 40;
    depositor_a
        .try_bank_deposit(
            depositor_a_usdc.key,
            usdc_bank,
            depositor_a_amount as f64,
            None,
        )
        .await?;

    let depositor_b_amount = 60;
    depositor_b
        .try_bank_deposit(
            depositor_b_usdc.key,
            usdc_bank,
            depositor_b_amount as f64,
            None,
        )
        .await?;

    let bank_before = usdc_bank.load().await;
    let shares_before = I80F48::from(bank_before.total_asset_shares);
    let share_value_before = I80F48::from(bank_before.asset_share_value);

    let liquidity_vault_before =
        TokenAccountFixture::fetch(test_f.context.clone(), bank_before.liquidity_vault)
            .await
            .balance()
            .await;

    let emissions_deposit = 50;
    usdc_bank
        .try_emissions_deposit(native!(emissions_deposit, "USDC"), emissions_funding.key)
        .await?;

    let bank_after = usdc_bank.load().await;
    let shares_after = I80F48::from(bank_after.total_asset_shares);
    let share_value_after = I80F48::from(bank_after.asset_share_value);

    let liquidity_vault_after =
        TokenAccountFixture::fetch(test_f.context.clone(), bank_after.liquidity_vault)
            .await
            .balance()
            .await;

    let asset_shares_value_multiplier =
        1.0 + emissions_deposit as f64 / (depositor_a_amount + depositor_b_amount) as f64;

    assert_eq!(shares_after, shares_before);

    // Should be equal, zero liabilities are present
    assert_eq!(
        share_value_before
            .checked_mul(I80F48::from_num(asset_shares_value_multiplier))
            .unwrap(),
        share_value_after
    );
    assert_eq!(
        liquidity_vault_after - liquidity_vault_before,
        native!(emissions_deposit, "USDC")
    );
    assert_eq!(I80F48::from(bank_after.emissions_remaining), I80F48::ZERO);
