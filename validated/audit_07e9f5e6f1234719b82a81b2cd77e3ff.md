### Title
Unbounded in-memory buffering of `git-fetch` porcelain/verbose output with no server-side timeout enforcement - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`fetchRemoteAtomic` reads the entirety of `git-fetch`'s stdout/stderr into plain `bytes.Buffer` values with no size cap, and the RPC only gets a context deadline if the caller explicitly sets `FetchRemoteRequest.Timeout`. A malicious or hostile remote referenced by `RemoteParams.Url` (e.g. a repository the attacker owns and configures as a pull-mirror/import source) can force `git-fetch --porcelain --verbose` to emit an extremely large number of ref-update lines, causing the buffers to grow without bound, and/or stall the connection to hold the RPC (and its goroutines/buffers) open indefinitely when no timeout is supplied.

### Finding Description
`fetchRemoteAtomic` allocates `var stdout, stderr bytes.Buffer` and passes them directly as `localrepo.FetchOpts.Stdout`/`Stderr`, which are wired straight into the `git fetch` child process's stdout/stderr pipes with no interposed size-limiting writer (unlike `internal/command/stderrbuffer.go`'s `stderrBuffer`, which does cap buffered output but is not used here). [1](#0-0) 
The command is invoked with `Verbose: true` and `Porcelain: true`, which is documented to make `git-fetch(1)` print one line per ref for every reference update/prune it processes. [2](#0-1) 
The remote URL and refspecs (`refs/*:refs/*` by default) are attacker-controlled via `RemoteParams`, and since `Prune: !req.GetNoPrune()` defaults to true, an attacker-owned remote advertising millions of throwaway refs will cause `git-fetch` to emit a correspondingly large porcelain report into the unbounded `stdout` buffer, which is then scanned line-by-line by `gitcmd.NewFetchPorcelainScanner`. [3](#0-2) 
Separately, `FetchRemote` only attaches a context deadline when `req.GetTimeout() > 0`; if the RPC caller does not set `Timeout`, the fetch runs with no Gitaly-imposed upper bound, so a remote that stalls (slowloris-style TCP behavior, or streams data slowly) can hold the RPC, its `git-fetch` subprocess, and its buffers open indefinitely. [4](#0-3) 

However, the practical severity is limited by two factors this audit must account for: (1) `Timeout` is a client-controlled field, not something the end-user attacker sets directly — Gitaly's own Rails/Workhorse caller (mirror scheduling, project import) decides whether/what timeout to pass, so this precondition is only partially within the described "unprivileged user" attacker's control; and (2) generating enough porcelain output lines to exhaust memory requires the attacker's remote to actually advertise and have git process a very large number of real refs, which is also gated by network throughput and git's own ref-advertisement/negotiation cost, not purely by Gitaly's buffer.

### Impact Explanation
If successfully triggered, this causes unbounded process memory growth in the Gitaly process handling the fetch (`bytes.Buffer` grows to hold the full porcelain+verbose transcript), and, absent an explicit `Timeout`, the RPC and its resources can remain held for an extended/indefinite period. Because Gitaly is a shared component serving multiple repositories/tenants on a storage node, sustained memory/goroutine pressure from one abusive fetch can degrade or crash the node, affecting other tenants — matching a DoS-class impact (resource exhaustion of an RPC handler).

### Likelihood Explanation
Exploitability requires: (a) the attacker to control a remote endpoint reachable from Gitaly and configure it as a fetch/mirror/import source for a repository they own — feasible for pull-mirroring or "import project by URL" features aimed at ordinary users; and (b) the RPC being invoked without an effective timeout, which is a decision made by Gitaly's caller (Rails/Sidekiq), not directly controllable by the attacker. Additionally, achieving significant memory exhaustion via porcelain line count requires the attacker's server to actually transmit and have git process a very large number of refs, which is throughput- and time-bound and would likely be noticed/rate-limited by other layers (repository size limits, network timeouts at the transport level) before pure Gitaly buffer exhaustion becomes the dominant failure mode. This lowers likelihood relative to a directly attacker-triggerable, single-request DoS.

### Recommendation
- Wrap `git-fetch`'s stdout/stderr in a size-bounded writer (similar to the existing `internal/command/stderrbuffer.go` `stderrBuffer`) when capturing porcelain/verbose output in `fetchRemoteAtomic`, truncating or erroring out once a configurable cap is exceeded.
- Enforce a mandatory server-side maximum timeout for `FetchRemote` (and similar remote-fetching RPCs) regardless of whether the caller supplies `Timeout`, e.g. clamp `req.GetTimeout()` to a sane default/maximum rather than leaving the context unbounded when it is zero.
- Consider streaming/processing the porcelain output incrementally instead of buffering the full output before scanning, to bound peak memory independent of ref count.

### Proof of Concept
```go
// internal/gitaly/service/repository/fetch_remote_dos_test.go
func TestFetchRemote_UnboundedPorcelainBuffer(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryServiceWithoutRepo(t)

    // Attacker-controlled remote: create a bare repo with a very large number of refs
    // pointing at a single small commit, simulating a hostile mirror source.
    _, remotePath := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{SkipCreationViaService: true})
    commitID := gittest.WriteCommit(t, cfg, remotePath, gittest.WithBranch("main"))
    for i := 0; i < 2_000_000; i++ { // large ref count to amplify porcelain output
        gittest.WriteCommit(t, cfg, remotePath, gittest.WithReference(fmt.Sprintf("refs/heads/spam-%d", i)))
    }

    repo, _ := gittest.CreateRepository(t, ctx, cfg, gittest.CreateRepositoryConfig{})

    req := &gitalypb.FetchRemoteRequest{
        Repository: repo,
        RemoteParams: &gitalypb.RemoteParams{
            Url: "file://" + remotePath, // in a real attack, an attacker-hosted HTTP/SSH remote
        },
        // Timeout intentionally omitted (0) to reproduce the "no server-side deadline" scenario.
    }

    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    before := m.Alloc

    _, err := client.FetchRemote(ctx, req)
    require.NoError(t, err)

    runtime.ReadMemStats(&m)
    after := m.Alloc
    t.Logf("memory delta: %d bytes", after-before) // expect large, unbounded growth proportional to ref count
}
```
Expected observation: process memory grows roughly linearly (unbounded) with the number of refs advertised by the attacker-controlled remote, and no Gitaly-side timeout aborts the call when `Timeout` is left at 0.

func (s *server) FetchRemote(ctx context.Context, req *gitalypb.FetchRemoteRequest) (*gitalypb.FetchRemoteResponse, error) {
	if err := s.validateFetchRemoteRequest(ctx, req); err != nil {
		return nil, err
	}

	if req.GetTimeout() > 0 {
		var cancel context.CancelFunc
		ctx, cancel = context.WithTimeout(ctx, time.Duration(req.GetTimeout())*time.Second)
		defer cancel()
	}
