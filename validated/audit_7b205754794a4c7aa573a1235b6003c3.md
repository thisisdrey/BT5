Based on my investigation, the strongest reachable analog in java-tron to this "all-or-nothing hard cap causes race-condition losses" bug class is the fixed `exchangeBalanceLimit` check in `ExchangeTransactionActuator`, which mirrors the `MINT_CAP` pattern (`current + requested <= CAP`, else revert entirely) from the reported Solidity contract.

### Title
Hard exchange pool balance cap causes front-runnable all-or-nothing transaction failures and unfair fund exposure - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
`ExchangeTransactionActuator.doValidate()` enforces a fixed `exchangeBalanceLimit` on a TRC10/TRX Bancor-style exchange pool. It computes `tokenBalance = addExact(tokenBalance, tokenQuant)` and rejects the entire transaction with `ContractValidateException("token balance must less than " + balanceLimit)` if the resulting pool balance would exceed the limit, rather than allowing the transaction to proceed up to the remaining headroom. [1](#0-0) 

### Finding Description
The pattern is structurally identical to the reported `MINT_CAP` bug: a global scarce-resource cap (`exchangeBalanceLimit` from `DynamicPropertiesStore.getExchangeBalanceLimit()`) is checked via `currentBalance + requestedQuant > cap` and the whole transaction is rejected on overflow instead of admitting the user for the remaining available headroom. [1](#0-0) 

Any unprivileged account can broadcast an `ExchangeTransactionContract` (a TRC10/TRX exchange swap) that is validated purely against the current on-chain pool state read via `Commons.getExchangeStoreFinal(...)`. [2](#0-1)  Because block producers order transactions from the pending pool, when the pool balance is close to `exchangeBalanceLimit`, two competing swap transactions submitted around the same time race for the remaining headroom: whichever is packed first succeeds and consumes the room, the other reverts entirely even though it could have partially succeeded up to the cap. The actuator has no mechanism to clamp `tokenQuant` down to the remaining allowed room; it only performs a strict reject-all check. [1](#0-0) 

### Impact Explanation
A losing user pays transaction bandwidth/energy fees for a transaction that fails purely due to ordering, and — more importantly — loses the deterministic economic opportunity to execute their intended swap at the exchange's current price/ratio (since `ExchangeCapsule.transaction(...)` pricing depends on pool state at execution time). Because the exchange balance limit is a fixed protocol-level constant that many pools can approach under normal usage (unlike a one-time NFT mint), this is a repeatable, systemic griefing/ordering-dependent condition rather than a one-off edge case, matching the "Medium" severity classification of the reported issue (user transaction fails when partial execution was possible, and a racing party can capture the scarce remaining capacity). This does not directly cause unauthorized transfer of funds or protocol insolvency, keeping it at Medium rather than High/Critical.

### Likelihood Explanation
Likelihood is moderate: it requires the pool's `firstTokenBalance`/`secondTokenBalance` to be near `exchangeBalanceLimit` and two independent transactions targeting the same token side to be broadcast close together — a realistic scenario for actively traded TRC10/TRX exchange pairs, and one that can be deliberately triggered by an attacker monitoring `getExchangeBalanceLimit()` headroom via public exchange query APIs and racing a victim's pending transaction.

### Recommendation
When `tokenBalance + tokenQuant > balanceLimit`, instead of unconditionally throwing `ContractValidateException`, either (a) clamp the executed `tokenQuant` to `balanceLimit - tokenBalance` (partial fill up to the cap) and recompute `anotherTokenQuant`/`tokenExpected` checks against the clamped quantity, or (b) keep the hard reject but document/expose the remaining headroom via query APIs so callers can size their requests to avoid needless race losses. This mirrors the Sherlock report's recommendation to allow purchasing "the remaining" capacity instead of failing outright.

### Proof of Concept
1. Pool has `firstTokenBalance = X` where `balanceLimit - X = 100` (only 100 units of headroom remain).
2. Attacker Alice and victim Bob both independently query the exchange (via `getExchangeInfo`/similar wallet APIs) and each broadcast an `ExchangeTransactionContract` requesting `tokenQuant = 80` on the same token side.
3. Alice's transaction is packed first: `tokenBalance = addExact(X, 80)` passes the `<= balanceLimit` check in `ExchangeTransactionActuator.doValidate()` (lines 199-205), her swap executes and updates pool state.
4. Bob's transaction, evaluated next against the now-updated pool balance (`X+80`), fails the same check (`X+80+80 > balanceLimit`) and is entirely rejected — even though up to 20 units of headroom remained that Bob could have legitimately swapped, and Bob still pays the transaction's bandwidth cost for the failed broadcast.
