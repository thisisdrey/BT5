### Title
Missing path validation of `GitAlternateObjectDirectories` allows cross-repository/storage object directory injection - (File: internal/git/alternates/alternates.go)

### Summary
The Solidity report's bug class is "a security-relevant post-check validates one specific piece of state (the executor module) but omits validating the rest of the mutable state (other modules), letting attacker-controlled data slip through unchecked." The Gitaly analog is that `localrepo.Repo.ObjectDirectoryPath()` validates the `GitObjectDirectory` field with `storage.ValidateRelativePath` (rejecting traversal outside the repo/storage), but the sibling field `GitAlternateObjectDirectories` — which is joined directly into `GIT_ALTERNATE_OBJECT_DIRECTORIES` by `alternates.Env()` — receives no equivalent validation at that boundary.

### Finding Description
`localrepo.Repo.ObjectDirectoryPath()` explicitly checks that the relative `GitObjectDirectory` path stays within the repository/storage or matches an expected quarantine prefix: [1](#0-0) 

However, `GitAlternateObjectDirectories` — a repeated string field on the same `Repository` proto — is consumed directly by `alternates.Env()`, which simply does `filepath.Join(repoPath, dir)` for each entry with no call to `storage.ValidateRelativePath` or any root-containment check: [2](#0-1) 

The `Repository` proto documents this field as directly controlling `GIT_ALTERNATE_OBJECT_DIRECTORIES`: [3](#0-2) 

The transaction middleware is aware that these two fields are dangerous and only expects them to be present on repositories that have already been rewritten to a quarantine/snapshot path by legitimate internal flows (e.g., Rails access-check loopback); it explicitly calls out that this invariant can be violated: [4](#0-3) 

Because `GitObjectDirectory` is defended with `ValidateRelativePath` but `GitAlternateObjectDirectories` is not defended anywhere in the `alternates.Env()` code path, a caller able to influence this repeated field (directly via gRPC request, since it is a plain proto field with no separate access-check gate other than the mutator/accessor split above) can point `GIT_ALTERNATE_OBJECT_DIRECTORIES` at an arbitrary path outside the intended repository — including another repository's `objects` directory or any path traversal sequence — enabling cross-repository object database access during Git command execution. This mirrors the reported vulnerability class: one state field (module/hooks path) is checked while a sibling field (other modules/alternate dirs) with equivalent power is left unchecked.

### Impact Explanation
If an attacker (or malfunctioning/compromised intermediate layer) can set `GitAlternateObjectDirectories` on a request that reaches `alternates.Env()` without going through the quarantine/snapshot rewrite guarded by `beginTransactionForRepository`, Git commands would read objects from an arbitrary directory, potentially disclosing objects from other repositories/tenants or escaping storage isolation boundaries — a cross-repository object access issue.

### Likelihood Explanation
Likelihood is constrained by the mutator/accessor gate in `beginTransactionForRepository`, which rejects mutators carrying pre-set object-directory fields and rewrites accessor paths through `restoreSnapshotRelativePath`. Exploitability therefore depends on whether any accessor RPC path, non-transactional code path (e.g., calls not going through this Praefect/storagemgr middleware, or direct localrepo construction with attacker-influenced `GitAlternateObjectDirectories`), or a bug in `restoreSnapshotRelativePath`'s rewriting logic allows an untrusted value to reach `alternates.Env()` unvalidated. I could not fully trace every caller of `alternates.Env()` or confirm whether all entry points funnel through the middleware's rewrite step, so likelihood is assessed as **uncertain/medium** rather than confirmed high.

### Recommendation
Add the same `storage.ValidateRelativePath` (or equivalent root-containment/quarantine-prefix check used in `ObjectDirectoryPath()`) to each entry of `GitAlternateObjectDirectories` before it is joined into `GIT_ALTERNATE_OBJECT_DIRECTORIES` in `alternates.Env()`, or centralize validation of both fields in a single function so no caller can bypass alternate-directory validation while object-directory validation is enforced.

### Proof of Concept
Not independently verified end-to-end (would require confirming a concrete caller that supplies attacker-controlled `GitAlternateObjectDirectories` bypassing `beginTransactionForRepository`'s guard). Conceptually: craft a gRPC request for an accessor RPC whose target `Repository` message sets `git_alternate_object_directories: ["../../other-repo/objects"]`; if the request path does not route through `restoreSnapshotRelativePath`/quarantine rewriting (e.g., a direct/internal call site building a `localrepo.Repo` from raw proto fields), `alternates.Env()` would emit `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repoPath>/../../other-repo/objects`, causing Git to search for objects in another repository's object store.

**Uncertainty note:** Due to the scope of the investigation, I was not able to enumerate every call site that constructs a `Repository` proto with attacker-influenced `GitAlternateObjectDirectories` and passes it directly to `alternates.Env()` outside the storagemgr middleware's guard. A background Devin session with full repo/build access would be needed to confirm a concrete unauthenticated-reachable trigger path.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
