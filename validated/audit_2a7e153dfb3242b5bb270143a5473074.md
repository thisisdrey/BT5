### Title
Non-deterministic floating-point Exchange price calculation can cause consensus divergence across CPU architectures - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The external report warns that a price-oracle whose value computation is not robust across implementations/conditions can silently diverge, be manipulated, or become inconsistent — with severe downstream effects. The closest reachable analog in java-tron is not an external oracle but the protocol's own built-in TRC10/TRX bancor-style Exchange, whose swap output ("price") is computed with unguarded, architecture-dependent floating-point `Math.pow` unless a chain parameter is activated. Any account can trigger this computation with a normal, unprivileged `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two swap-amount computation strategies based on the `useStrictMath` flag pulled from `DynamicPropertiesStore.allowStrictMath()`: [1](#0-0) 

When strict math is not enabled, `ExchangeProcessor` performs the bancor-relay computation with plain `Math.pow` semantics via `Maths.pow(a, b, useStrictMath)`: [2](#0-1) [3](#0-2) 

The non-strict path dispatches to `MathWrapper.pow`, which is implemented **separately per CPU architecture** (`platform/src/main/java/arm/org/tron/common/math/MathWrapper.java` and `platform/src/main/java/x86/org/tron/common/math/MathWrapper.java`), i.e., the exact opposite of `StrictMath`, which guarantees bit-for-bit identical results across platforms. `Math.pow` (non-strictfp) is explicitly permitted by the JLS to use platform-native FPU/vector instructions and can legitimately return different IEEE-754 bit patterns for the same input on x86 vs. ARM.

Both `ExchangeTransactionActuator.execute()`/`doValidate()` and `ExchangeInjectActuator`/`ExchangeWithdrawActuator` call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, meaning the resulting swap amount (`anotherTokenQuant`), which is written into account balances and the `ExchangeCapsule`'s reserve state, is derived straight from this potentially non-deterministic double-precision computation: [4](#0-3) [5](#0-4) 

The project's own unit tests confirm the two math modes produce **different** results for identical inputs, which is the whole point of the hardening effort: [6](#0-5) 

If `allowStrictMath` (and/or `allowHardenExchangeCalculation`) is not active in a given network configuration, an ordinary user submitting an `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` forces every node to independently evaluate `Math.pow` for the swap amount as part of block application in `Manager`. Nodes running on different CPU microarchitectures (x86 vs ARM, or even different x86 generations with different vectorized `libm` implementations) can legitimately compute different `anotherTokenQuant` values, different account balances, and different `ExchangeCapsule` reserve states from the exact same transaction — producing a state root/consensus mismatch.

### Impact Explanation
This is directly analogous to the report's concern that a price computation whose underlying mechanics are not fully controlled/verified can silently diverge and produce inconsistent results depending on conditions (here: CPU architecture) rather than by design. In java-tron this can escalate beyond "wrong price" to a **chain split**: heterogeneous nodes (a mix of x86 and ARM full/witness nodes, which java-tron explicitly ships separate `MathWrapper` builds for) applying the same block would derive different post-state, breaking consensus. This is a concrete Critical/High impact class permitted by the validation rules (chain split / node halt due to divergent state).

### Likelihood Explanation
Triggering the vulnerable code path requires nothing more than a normal signed `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` from any account with a small TRX/TRC10 balance and does not require any special privilege — any anonymous API/transaction broadcaster can invoke it. The likelihood of it actually causing consensus divergence depends on: (a) whether `allowStrictMath`/`allowHardenExchangeCalculation` chain parameters are activated on the target network, and (b) whether the validator/full-node set is mixed-architecture. Given the explicit maintenance of per-architecture `MathWrapper` implementations, mixed-architecture deployments are clearly anticipated by the codebase, and the presence of the strict/hardened math migration path strongly suggests this exact class of non-determinism was a known real risk that is only mitigated when the corresponding dynamic parameters are turned on.

### Recommendation
- Ensure `allowStrictMath` and `allowHardenExchangeCalculation` are activated by default (or hard-code `StrictMath`/`SafeExchangeProcessor` usage) for all Exchange-related actuators so that swap price computation is guaranteed deterministic across all supported architectures before any mixed-architecture node is allowed to sync mainnet blocks.
- Remove or gate out the legacy `MathWrapper`-based (non-strict) exchange path entirely once the hardened path is proven safe, rather than keeping it reachable via a dynamic parameter that could be unset.
- Add cross-architecture (x86 vs ARM) consensus/state-root regression tests specifically for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` to catch any future non-determinism regressions.

### Proof of Concept
1. Deploy two java-tron nodes participating in the same private/test network: one built with `platform/.../x86/.../MathWrapper.java`, another with `platform/.../arm/.../MathWrapper.java`.
2. Ensure the chain parameters controlling `allowStrictMath()`/`allowHardenExchangeCalculation()` in `DynamicPropertiesStore` are left at their default/unactivated (legacy) value.
3. Create a TRC10/TRX Exchange pool via `ExchangeCreateContract`, then broadcast an `ExchangeTransactionContract` (or `ExchangeInjectContract`/`ExchangeWithdrawContract`) with reserve/quantity values chosen so the `Math.pow` intermediate result sits near a rounding boundary (values similar to those exercised in `ExchangeProcessorTest.testStrictMath`, e.g. `{4732214L, 2202692725330L, 29218L}`).
4. Compare the computed `anotherTokenQuant` / final account balances and `ExchangeCapsule` reserves on the x86 node vs. the ARM node for the identical block; a discrepancy demonstrates non-deterministic state derivation from the same transaction, i.e., the consensus-divergence root cause.
