### Validation of the claimed binding

**Claimed binding:** `accounts.get_mut(receiver_id).is_some() == true` immediately after `internal_add_balance`'s `get_or_create(receiver_id)` ran earlier in the same batch/call, and the newly created account must be unlocked.

**Trace:**
- `Accounts::get_or_create` inserts via `self.accounts.entry(account_id).or_insert_with_key(...)`, explicitly constructing `Lock::unlocked(Account::new(...))`, documented as "The created account will be unblocked by default." [1](#0-0) 
- `Accounts::get_mut` is a plain lookup into the same `IterableMap<AccountId, AccountEntry>` backing store used by `get_or_create`. [2](#0-1) 
- `internal_add_balance` calls `get_or_create` (creating the account, unlocked, in-map) before crediting; `internal_sub_balance` calls `get_mut` then `Lock::get_mut` (which only fails if `is_locked()` is true). [3](#0-2) [4](#0-3) 

Within a single NEAR contract execution (one `execute_intents` call), all intent processing happens sequentially against the same in-memory `Contract` state — there is no cross-shard or async gap between processing one intent in a batch and the next. So an account inserted by `get_or_create` earlier in the batch is trivially visible to a later `get_mut` call on the identical `AccountId`, and it is unlocked by construction. **Both sides of the equality match — no divergence exists.**

### Why the attack scenario is not reachable regardless

The scenario requires an intent "signed with a payload whose `signer_id` equals `receiver_id`" later in the same batch — i.e., a valid signature attributable to `receiver_id`. Signature verification is independent of the `self.accounts` map: for an account never registered in the map, `has_public_key`/`iter_public_keys` fall back to treating `receiver_id` as an implicit account and require the corresponding ed25519 private key to produce a valid signature. [5](#0-4)  The prompt itself acknowledges this is "impossible without victim's key." The proposed workaround — using the attacker's own second account as `receiver_id` — is not an attack on a victim at all; it is ordinary same-batch credit-then-withdraw from an account the attacker legitimately controls and can sign for, which is intended, authorized behavior.

    fn internal_add_balance(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_or_create(owner_id)
            // we allow locked accounts to accept deposits and incoming deposits
            .as_inner_unchecked_mut();

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }
            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }

    fn internal_sub_balance(
        &mut self,
        owner_id: &AccountIdRef,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
    ) -> Result<()> {
        let owner = self
            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut()
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        Ok(())
    }
