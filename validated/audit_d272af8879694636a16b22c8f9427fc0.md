Based on my investigation, I found a legitimate analog in gitaly to the MIMO "registry does not guarantee actual state" bug class.

### Title
Cross-repository object pool linking lacks ownership verification, allowing any caller-supplied repository to be linked to any accessible pool - (File: internal/gitaly/service/objectpool/link.go)

### Summary
The MIMO bug was fundamentally about a "registry" component that is trusted to reflect an authoritative relationship (owner ↔ proxy) but which anyone can cause to diverge from reality, plus a factory RPC (`deployFor`) that permits an unrelated caller to create/attach relationships without any check tying the actor to the resource. The `ObjectPoolService.LinkRepositoryToObjectPool` RPC in gitaly exhibits the same structural pattern: the on-disk `alternates` file (the actual "ownership" record of which pool a repo is deduplicated against) can be set by any caller who can name a `repository` and an `object_pool`, with no check that the caller/repository is actually meant to be a member of that pool.

### Finding Description
`LinkRepositoryToObjectPool` only validates that the target repository exists (`s.locator.ValidateRepository`) and that the pool resolves to a valid git directory (`s.poolForRequest`), then unconditionally calls `pool.Link(ctx, repo)`: [1](#0-0) 

The underlying `Link` function in `internal/git/objectpool/link.go` writes the pool's relative object path into the target repository's `objects/info/alternates` file as long as it isn't already linked to a *different* pool: [2](#0-1) 

There is no verification anywhere in this path that the `repository` being linked is actually related to (e.g., forked from, or the documented "origin" of) the `object_pool` in question — the RPC only requires that both the pool and the target repository independently pass existence/validity checks. This mirrors the `deployFor()` pattern in the MIMO report, where any caller can attach an unrelated resource to a relationship record without an ownership/derivation check. The `objectpool.proto` documentation asserts a lifecycle ("pool created from primary member, then linked members get deduplicated") but nothing enforces that only legitimate descendants of the pool's origin can join: [3](#0-2) 

Once linked, alternates give the "member" repository read access to **every object** contained in the pool via git's alternate-object-directory mechanism (as documented in `doc/object_pools.md`): [4](#0-3) 

### Impact Explanation
If an ordinary user can reach `LinkRepositoryToObjectPool` for a repository they control and a pool they don't own (e.g., a private/internal project's pool that they can merely name/guess the storage-relative path or pool disk path for), they can link their own repository to that pool. This gives their repository — and thus their own git client, since objects become reachable through alternates — read access to every object contained in that other pool, i.e., cross-repository object disclosure. This directly matches the "Accept only concrete ... cross-repository object access" criterion. In multi-tenant Gitaly/Praefect deployments where object pool paths are derived deterministically (`DerivePoolPath` from `repositoryID`, or `@pools/<sha256>` for Rails-style pools) rather than secret, an attacker who can compute or enumerate another project's pool path could exfiltrate objects from a pool they were never authorized to join. [5](#0-4) 

### Likelihood Explanation
This RPC is reachable by any client with access to the gRPC API scoped to a repository they control (this is the same trust level used for ordinary pushes/forks) — it does not require special privileges beyond being able to name a target repository and a pool. The only defenses in place are existence/validity checks (`ValidateRepository`, `poolForRequest`) and a "not already linked to a different pool" guard in `linkedToRepository`, none of which verify a legitimate origin/derivation relationship between repo and pool. [6](#0-5)  Whether this is exploitable end-to-end depends on how calling layers (e.g., GitLab Rails, which is the intended caller) restrict which pool a given project may request — that authorization is expected to live in the calling application (Rails), not in Gitaly itself, since Gitaly's RPCs are traditionally an unauthenticated-at-this-layer building block. I could not verify from the indexed gitaly code alone whether any additional authorization is enforced by Praefect/Rails before this RPC is invoked, so likelihood is contingent on that external layer, which is a real gap consistent with the original report's theme (relationships trusted by lower layers but not actually enforced end-to-end).

### Recommendation
Add a check within `LinkRepositoryToObjectPool` (or its Praefect coordinator path) that verifies the target repository is an expected/authorized member of the given pool before writing the alternates link — for example, by consulting the `PoolStore`/pool-metadata registry (`internal/gitaly/storage/relational`) for a recorded relationship, or by requiring that the pool's recorded upstream/origin match the repository's lineage, rather than trusting any caller-supplied `(repository, object_pool)` pair. This closes the same class of gap identified in the MIMO report: a registry/relationship structure that exists but is not actually enforced at the point where privileged linking occurs.

### Proof of Concept
1. Attacker controls repository A on a shared Gitaly/Praefect storage.
2. Attacker learns or computes the pool disk path of victim's private object pool B (e.g., via `DerivePoolPath(repositoryID)` if repository IDs are guessable/sequential, or via a leaked `@pools/<sha256>` path).
3. Attacker calls `LinkRepositoryToObjectPool({repository: A, object_pool: B})`.
4. `internal/gitaly/service/objectpool/link.go` validates only that A exists and B is a valid git repo, then calls `objectpool.Link`, writing B's `objects` path into A's `objects/info/alternates`.
5. Attacker's repository A can now resolve/read any object contained in pool B via git's alternates search path, as documented in `doc/object_pools.md`, exfiltrating objects the attacker was never authorized to access.

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

```go
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

```go
// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
```

```text
// ObjectPoolService is a service that manages the lifetime of object pools.
//
// An object pool is a separate repository that can be linked to from multiple object pool members
// in order to deduplicate common objects between them. This is mostly used in the context of
// repository forks.
//
// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
```

```go
// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.
func DeriveReplicaPath(repositoryID int64) string {
	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}
```
