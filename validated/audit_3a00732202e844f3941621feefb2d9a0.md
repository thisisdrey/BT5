### Title
Equality mismatch between `validate_received_chunk`'s freshness check and `try_replace_chunk`'s staleness check lets an unauthenticated peer force repeated wasted verification/wakeup cycles by replaying an already-current StackerDB chunk - (File: stackslib/src/net/stackerdb/mod.rs)

### Summary
`PeerNetwork::validate_received_chunk` treats a chunk whose `slot_version` equals the currently-stored version as fresh and acceptable (`data.slot_version < *expected_version` is the only rejection condition), while the actual write path, `StackerDBTx::try_replace_chunk`, treats that very same equal-version case as stale and always refuses to store it (`slot_desc.slot_version <= slot_validation.version`). Any peer can replay a chunk it has previously observed (no private key of its own is required beyond re-sending publicly gossiped signed data) at the node's current version and force the validation gate to repeatedly succeed, triggering signature verification, state-machine wakeups, and reply/forward work that can never result in a successful store.

### Finding Description
`validate_received_chunk` is the shared gate used both for unsolicited push-chunk handling and for downloaded chunks: [1](#0-0) 

It only rejects when `data.slot_version < *expected_version`, meaning `data.slot_version == *expected_version` (the exact version currently stored) is treated as valid, "current or newer."

The authoritative persistence layer disagrees. `try_replace_chunk` rejects the exact same equal-version case as `StaleChunk`: [2](#0-1) 

Because these two gates use different boundary operators (`<` vs `<=`) around the same equality point, a chunk at the current version always "passes" the network-facing validator but always fails the storage layer. This is exploited in `handle_unsolicited_StackerDBPushChunk`:

- On the normal `StackerDBChunkInv` branch, a same-version replay passes `validate_received_chunk`, causing the code to patch the local inventory and force-wake the sync state machine, then build and send a P2P reply, and finally forward the message to the relayer: [3](#0-2) 

- On the `FutureView` Nack branch, the same equal-version chunk passes validation and is buffered for later reprocessing, per the repo's own regression test: [4](#0-3) 

Once forwarded to the relayer, the chunk is finally attempted to be stored via `process_stacker_db_chunks` -> `try_replace_chunk`, which always rejects it as `StaleChunk` (logged and dropped): [5](#0-4) 

Because the message that triggers this only needs to contain a *previously valid* `(slot_id, slot_version, data, sig)` tuple that is public (it was broadcast over the P2P StackerDB gossip channel, or is retrievable via the `POST /v2/stackerdb/.../chunks` endpoint's own reflected acks/metadata, or simply the last chunk this node itself stored), no secret key of the real slot owner is required to *replay* it — only to have observed it once.

### Impact Explanation
An unauthenticated remote peer can repeatedly resend an already-current, previously-observed chunk to force each recipient node to: perform ECDSA signature recovery (`SlotMetadata::verify`), query slot-signer/slot-version state from the DB, wake up the StackerDB sync state machine, and construct/send a reply and/or forward the message to the relayer for storage — none of which can ever succeed. This is a bounded per-message compute/DB-read cost that a remote party can trigger repeatedly and cheaply relative to the honest-node cost of processing it, similar in nature to the referenced report's "waste gas" pattern of a boundary-check gap that allows a caller to force downstream work destined to fail.

### Likelihood Explanation
High likelihood of being triggerable: the required inputs (contract ID, slot ID, slot version, data, and signature) are all data that flows over the P2P StackerDB channel in the clear and is not single-use/nonce-protected, so any peer that has seen one broadcast of a chunk at its current version can replay it indefinitely without needing the signer's private key.

### Recommendation
Align `validate_received_chunk`'s freshness check with `try_replace_chunk`'s actual staleness semantics, i.e. change:
```rust
if data.slot_version < *expected_version {
```
to
```rust
if data.slot_version <= *expected_version {
```
in `stackslib/src/net/stackerdb/mod.rs`, so that a chunk that cannot possibly be stored is rejected at the earliest, cheapest gate instead of being accepted, buffered/forwarded, and only failing at the final storage attempt.

### Proof of Concept
1. Observe (via P2P gossip or a normal chunk fetch) a valid signed `StackerDBChunkData` for slot `S` currently at version `V` in some StackerDB replica.
2. Send an unsolicited `StackerDBPushChunk` message containing that exact `(S, V, data, sig)` tuple to a victim node.
3. `handle_unsolicited_StackerDBPushChunk` -> `validate_received_chunk` accepts it (`V < V` is false), causing the node to verify the signature, patch its local inventory / wake the sync state machine, and forward the message onward to be persisted.
4. The eventual `try_replace_chunk` call rejects it as `StaleChunk` since `V <= V`.
5. Repeat step 2 arbitrarily many times; each repetition repeats steps 3–4's wasted work, since nothing in the accepted path consumes or invalidates the replayed tuple.
