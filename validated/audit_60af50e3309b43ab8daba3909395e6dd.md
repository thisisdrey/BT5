### Title
Uncontrolled resource consumption via unbounded, unsanitized PCRE regex passed to `git grep --perl-regexp` in `SearchFilesByContent` - (File: `internal/gitaly/service/repository/search_files.go`)

### Summary
`SearchFilesByContent` forwards the caller-supplied `Query` field directly and without any length or complexity validation into `git-grep(1)` as a PCRE pattern (`--perl-regexp -e <query>`). Unlike the sibling RPC `SearchFilesByName`, which explicitly caps its `Filter` regex at `searchFilesFilterMaxLength` (1000 bytes) before compiling it with Go's linear-time RE2 engine, `SearchFilesByContent` has no such guard, and the pattern is evaluated by `git grep`'s PCRE backend, which — like Python's `re` used in the Django `Truncator` CVE — is a backtracking engine susceptible to catastrophic backtracking on adversarial input.

### Finding Description
In `SearchFilesByContent` ( [1](#0-0) ), `req.GetQuery()` is passed straight into the `-e` value flag alongside `--perl-regexp`: [2](#0-1) 

`validateSearchFilesRequest` only checks that `Query` and `Ref` are non-empty and that `Ref` doesn't start with `-`; it performs no length or pattern complexity validation on `Query`: [3](#0-2) 

Contrast this with `SearchFilesByName`, which explicitly documents and enforces a length cap specifically "to thwart excessive resource usage when filtering": [4](#0-3) [5](#0-4) 

`SearchFilesByName`'s filter is also compiled and evaluated in-process using Go's `regexp` package (RE2 engine, guaranteed linear time, immune to backtracking blowup), whereas `SearchFilesByContent`'s query is handed off to `git grep --perl-regexp`, which uses PCRE — a backtracking engine that is exactly the class of engine vulnerable to CVE-2024-27351-style ReDoS. This asymmetry (length-bounded + safe engine for `SearchFilesByName` vs. unbounded + backtracking engine for `SearchFilesByContent`) indicates the mitigation applied to one code path was not applied to the other.

### Impact Explanation
Any caller able to invoke the `RepositoryService.SearchFilesByContent` RPC against a repository (an ordinary, authenticated GitLab user performing a code search is the typical caller of this RPC) can supply a PCRE pattern crafted for catastrophic backtracking (e.g., a nested-quantifier pattern such as `(a+)+$` matched against a long non-matching line, similar in spirit to the `'<' * 65535` PoC from the report). The spawned `git grep` process will consume excessive CPU for a long time while scanning repository content, tying up the Gitaly worker/goroutine and command-spawning resources handling that RPC. This is a denial-of-service of the RPC handler and, if triggered repeatedly/concurrently, could degrade the whole Gitaly node.

### Likelihood Explanation
The `Query` field is fully attacker-controlled, requires no special privileges beyond the ability to call the search RPC (typical for any project member with read access), and there is no length cap or regex-safety check on the server side before the string reaches a backtracking regex engine. This makes the path easily and repeatedly triggerable.

### Recommendation
Apply the same defensive measures already used for `SearchFilesByName`:
- Enforce a maximum length on `req.GetQuery()` in `validateSearchFilesRequest` (or a `SearchFilesByContent`-specific check) before passing it to `git grep`.
- Consider validating/pre-compiling the pattern (e.g., attempt compilation with Go's RE2-compatible `regexp` package first, or use `git grep --basic-regexp`/fixed-string modes when PCRE features aren't required) to reject patterns likely to cause pathological backtracking.
- Alternatively, apply a bounded execution timeout specific to the `git grep` subprocess so a slow-matching pattern cannot stall the RPC indefinitely.

### Proof of Concept
Call `SearchFilesByContent` with a `Query` engineered for PCRE catastrophic backtracking, e.g.:
```
Query: "(a+)+$"
Ref:   "<branch-with-a-large-non-matching-file>"
```
against a repository containing a large file with long lines of `a` characters not ending in a match (e.g., `strings.Repeat("a", 100000) + "!"`), analogous to the existing test fixtures that already create huge files for this RPC's tests ( [6](#0-5) ). The underlying `git grep --perl-regexp` process will exhibit exponential-time backtracking on such input, stalling the RPC and consuming CPU on the Gitaly host.

func (s *server) SearchFilesByContent(req *gitalypb.SearchFilesByContentRequest, stream gitalypb.RepositoryService_SearchFilesByContentServer) error {
	ctx := stream.Context()

	if err := validateSearchFilesRequest(ctx, s.locator, req); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	repo := s.localRepoFactory.Build(req.GetRepository())

	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name: "grep",
		Flags: []gitcmd.Option{
			gitcmd.Flag{Name: "--ignore-case"},
			gitcmd.Flag{Name: "-I"},
			gitcmd.Flag{Name: "--line-number"},
			gitcmd.Flag{Name: "--null"},
			gitcmd.ValueFlag{Name: "--before-context", Value: surroundContext},
			gitcmd.ValueFlag{Name: "--after-context", Value: surroundContext},
			gitcmd.Flag{Name: "--perl-regexp"},
			gitcmd.ValueFlag{Name: "-e", Value: req.GetQuery()},
		},
		Args: []string{
			string(req.GetRef()),
		},
	}, gitcmd.WithSetupStdout())
	if err != nil {
		return structerr.NewInternal("cmd start failed: %w", err)
	}

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}
