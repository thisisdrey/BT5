### Title
Attacker can permanently DoS a victim's ability to add collateral or receive deposit/debt tokens by filling the 30-slot per-account token list with dust - (contracts/Pool.sol)

### Summary
The bug class is an unauthenticated, unprivileged input causing a persistent denial of service (crafted RDP packet → NULL deref → service stays defunct until reboot). The on-chain analog in Metronome is the `MAX_TOKENS_PER_USER` cap on `Pool`'s per-account `depositTokensOfAccount`/`debtTokensOfAccount` lists: any EOA can, with no privileges and only dust cost, fill all 30 slots of a victim's account so that every subsequent action that would add a new token to the victim's list reverts with `UserReachedMaxTokens()`. The victim's account is "crashed" — they cannot deposit new collateral types, cannot receive deposit tokens, and cannot open new debt positions — and recovery requires them to fully zero out attacker-planted dust balances, which they may be unable to do while the dust is locked by debt.

### Finding Description
`Pool` maintains per-account enumerable sets of deposit and debt tokens, capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). The modifier `onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` (`contracts/Pool.sol:143-148`), and it guards `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-220`).

Entries are added automatically whenever an account receives a token for the first time:

- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` when `balanceOf` goes 0→nonzero (`contracts/DepositToken.sol:486-488`).
- `DepositToken._transfer` does the same for the recipient (`contracts/DepositToken.sol:518-520`).
- `DebtToken._mint` calls `pool.addToDebtTokensOfAccount(account_)` on first issuance (`contracts/DebtToken.sol:597-599`).

Two public, unprivileged entry points let an attacker write into a victim's list:

1. `DepositToken.deposit(amount_, onBehalfOf_)` takes an arbitrary `onBehalfOf_` (`contracts/DepositToken.sol:211-237`). There is no minimum deposit amount — only `amount_ == 0` is rejected (line 215). The attacker deposits 1 wei of each supported underlying with `onBehalfOf_ = victim`, each call minting dust `msdTOKEN` to the victim and inserting that deposit token into `depositTokensOfAccount[victim]`. `Pool.addDepositToken` itself allows up to 30 deposit tokens (`contracts/Pool.sol:703`), so 30 distinct collateral types can exist to fill.
2. `DepositToken.transfer`/`transferFrom` — the attacker deposits dust to themselves and transfers dust `msdTOKEN` to the victim; `_transfer` inserts the token into the victim's list (lines 518-520).

Once the victim's combined list length reaches 30:

- Any `deposit` of a *new* collateral type on their behalf reverts, because `_mint` → `addToDepositTokensOfAccount` hits `UserReachedMaxTokens` (line 486-488 vs Pool line 144).
- Any `transfer`/`transferFrom` sending them a deposit token they don't already hold reverts (lines 518-520 → Pool 144).
- Any `issue`/`mint` of a debt token type they don't already hold reverts (`DebtToken._mint` → `addToDebtTokensOfAccount`, `contracts/DebtToken.sol:598-599`).

Critically, removal from the list only happens when the balance goes fully to zero (`DepositToken.sol:460-462`, `523-525`; `DebtToken.sol:540-542`), and withdrawal/transfer of collateral is gated by `_revertIfLocked` (`contracts/DepositToken.sol:180-181`, 406-411): a victim with outstanding debt has locked collateral and cannot always burn down the attacker-planted dust to free a slot. The attacker can also cheaply re-grief any slot the victim clears.

### Impact Explanation
Temporary freezing of funds / liveness failure for a targeted account, matching the CVE's "service crashes and stays defunct" shape:

- A victim whose position drifts unhealthy cannot deposit a *new* collateral type to restore health (all 30 slots occupied), leaving them exposed to liquidation they could have avoided — indirect loss of collateral via `Pool.liquidate` (`contracts/Pool.sol:537-596`).
- The victim cannot receive deposit tokens (e.g., seized collateral from `seize` → `_transfer`, OTC transfers, airdrops of msdTOKEN) — those transfers revert for everyone sending to them.
- The victim cannot open new debt positions (`DebtToken._mint` → list add reverts).
- Recovery requires the victim to zero out attacker-planted dust across up to 30 tokens, which may be impossible while collateral is locked by debt, and the attacker can re-fill slots at dust cost. This is a persistent, attacker-caused DoS reachable entirely through public entry points (`deposit`, `transfer`), with no privileged role, oracle manipulation, or governance involvement.

### Likelihood Explanation
Likelihood is moderate-to-high: the attack needs only dust amounts of each listed collateral and up to 30 transactions (~1 wei per deposit, or self-deposit + dust `transfer`). No front-running is required — griefing can be done preemptively and maintained. Constraints that lower likelihood: the pool must list enough deposit/debt token types to approach 30 combined slots (the code permits up to 30 deposit tokens, `Pool.sol:703`), and a victim who already holds several distinct positions has fewer free slots (making them *easier* to brick, not harder). Modifiers on `deposit` (`whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`) do not stop the attack. The main mitigation is that the victim can clear slots by fully withdrawing unlocked dust balances, and there is no direct theft — impact is availability, not solvency.

### Recommendation
- Require a minimum deposit amount (e.g., a USD-denominated floor like `debtFloorInUsd`) in `DepositToken.deposit`, or reject `onBehalfOf_ != _msgSender()` deposits below a threshold.
- Alternatively, make list membership opt-in for receipt: only auto-add tokens on `deposit`/`issue` initiated by the account itself, not on `transfer`/`seize`/`deposit(..., onBehalfOf_)` to an arbitrary recipient — e.g., track "position-active" tokens in a separate mapping instead of the enumerable set for received-but-unactioned dust.
- Allow accounts to self-remove entries (a `Pool.removeMyToken(token)` that checks `balanceOf == 0` is already implied by withdrawal, but a sweep-style escape that works even when dust is locked would help), or raise `MAX_TOKENS_PER_USER` / make the cap per-token-type rather than combined.

### Proof of Concept
Hardhat-style sketch (extend `test/Pool.test.ts` fixtures; assume ≥ N deposit tokens are registered so `victim` has <30 total slots remaining):

```ts
import {expect} from 'chai'

it('griefs victim: fills token list, blocks new collateral deposit', async () => {
  // victim starts with 1 deposit token (msdMET) — 29 free slots
  await msdMET.connect(alice).deposit(parseEther('10'), alice.address)

  // attacker deposits 1 wei of every other supported collateral on behalf of alice
  for (const dt of allDepositTokensExcept(msdMET)) {
    const underlying = await dt.underlying()
    await IERC20__factory.connect(underlying, attacker).approve(dt.address, 1)
    await dt.connect(attacker).deposit(1, alice.address) // onBehalfOf = victim
  }

  // also dust-transfer to reach exactly 30 if needed
  // await msdMET.connect(attacker).transfer(alice.address, 1)  // if attacker held any

  expect(await pool.getDepositTokensOfAccount(alice.address)).to.have.lengthOf(30)

  // victim cannot deposit a new collateral type — wait: they can't, all types used.
  // New token attack vector: victim cannot receive ANY token they don't already hold
  await expect(
    msdWETH.connect(bob).transfer(alice.address, 1) // alice holds 0 msdWETH
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // victim cannot open a new debt position either
  await expect(
    msUsdDebtToken.connect(alice).issue(1, alice.address)
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```
