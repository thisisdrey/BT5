### Title
Forged relayer provenance via self-reported `RelayData` entries accepted at face value - ([File: stackslib/src/net/chat.rs])

### Summary
`StacksMessage.relayers` (a `Vec<RelayData>`) is fully attacker-controlled data included inside the signed byte string (`self.relayers.consensus_serialize(&mut message_bits)` in `verify_secp256k1`/`do_sign`), and `verify_secp256k1`/`Preamble::verify` only prove that the sender who owns the signing key produced this exact byte string — they say nothing about who physically relayed the message. On receipt, `ConversationP2P::process_relayers` iterates every entry in `relayers` and unconditionally records it into local reputation/route-selection state via `self.stats.add_relayer(&relayer.peer, ...)`, with no check that any given `RelayData.peer` corresponds to an actual peer the node observed or corresponds to any real forwarding hop.

### Finding Description
`verify_secp256k1` in `stackslib/src/net/codec.rs` (lines 1491-1502) constructs `message_bits` from `self.relayers.consensus_serialize(...)` and `self.payload.consensus_serialize(...)`, then delegates to `Preamble::verify`, which only checks that the byte string (preamble+relayers+payload) was signed by the claimed public key. There is no constraint tying entries of `relayers` to peers that were actually involved in transporting the message — the field is attacker-supplied at message-construction time and merely gets included, along with everything else, under the signature. [1](#0-0) 

On the receiving side, `ConversationP2P::process_relayers` (`stackslib/src/net/chat.rs`, lines 2057-2085) only checks (a) no cycles by public-key hash and (b) that the local peer isn't itself listed, then loops over every relayer entry and calls `self.stats.add_relayer(&relayer.peer, (preamble.payload_len - 1) as u64)` — recording *every* claimed relayer, including any forged third-party `NeighborAddress`, without any correlation to the actual connection this data arrived on. [2](#0-1) 

`process_relayers` is invoked from the push-message validators (`validate_blocks_push`, `validate_microblocks_push`, `validate_transaction_push`, and similarly for microblocks/Nakamoto pushes) — i.e., paths reachable by any connected, unprivileged remote peer sending push-type gossip messages. [3](#0-2) 

The attacker's exact message: craft a `StacksMessage` (e.g. wrapping a `Transaction`/`Blocks`/`Microblocks` push payload) whose `relayers` vector contains one or more `RelayData { peer: <victim's real NeighborAddress>, seq: <anything> }` entries that the attacker itself appended before signing with its own valid key (via `sign_relay`/`do_sign`, or by hand-building the same byte layout). Since the attacker controls the entire byte string prior to signing, and `verify_secp256k1`/`Preamble::verify` validate only the signature over that byte string — not the truthfulness of its contents — the message passes authentication and is accepted.

Note on scope: the question refers to "Handshake" specifically, but `StacksMessage.relayers` and the surrounding `verify_secp256k1`/signature machinery are generic to all `StacksMessage` types (`stackslib/src/net/codec.rs` line 1338-1364), and the concrete downstream consumer of `relayers` (`process_relayers`) is wired to push-type messages (blocks/microblocks/transactions), not to `Handshake` handling itself. I could not confirm within available context that `handle_handshake` calls `process_relayers` on the `Handshake` payload's own `relayers` field before this session ended; however, the identical structural weakness (signed-but-unverified relayer provenance) applies equally to any `StacksMessage`, including a `Handshake`, since the codec/signature logic is shared.

### Impact Explanation
The forged `RelayData.peer` entries are fed directly into `ConversationStatsP2P`/`RelayerStats` (via `add_relayer`, later merged by `merge_relay_stats` and consumed by `get_outbound_relay_rankings`/`get_inbound_relay_rankings` in `stackslib/src/net/relay.rs`), which drive `sample_broadcast_peers` — the node's peer-selection logic for future broadcasts (`stackslib/src/net/p2p.rs` lines 1495-1580). A remote unprivileged attacker can therefore poison a victim node's belief about which third-party peers relay messages, degrading route-selection quality and misattributing traffic to uninvolved nodes. This is a data-integrity/forged-provenance issue affecting local reputation bookkeeping rather than shared/consensus state, and it is repeatable on every message sent (bounded only by `MAX_RELAYERS_LEN`).

### Likelihood Explanation
Any remote peer that can complete a P2P handshake and send push messages (blocks/microblocks/transactions) can trigger this: no privileged role, RPC secret, or third-party key is required, since the attacker only needs its own valid keypair to sign a message it fully controls, including a forged `relayers` list. The attack cost is a single crafted, validly-signed message, and it is trivially repeatable on every subsequent message the attacker sends.

### Recommendation
Do not treat `RelayData` entries in the `relayers` field as authenticated relay provenance. Either (a) have each relaying peer independently attest/re-sign only its own hop (already partially done via `sign_relay`, but the receiving node cannot distinguish a self-appended, unverified hop from a genuinely-forwarding peer's hop), or (b) bind `add_relayer` bookkeeping to the actual authenticated identity of the peer that delivered the message on the wire (`self.ref_public_key()`/`to_neighbor_key()`), not to attacker-controlled `RelayData.peer` values, and only use the `relayers` list for cycle-detection / "don't re-send to sender" purposes rather than for reputation scoring of third parties.

fn test_relay_data_provenance_forgery() {
    // Attacker's own keypair
    let attacker_privkey = Secp256k1PrivateKey::new();
    let attacker_pubkey = StacksPublicKeyBuffer::from_public_key(
        &Secp256k1PublicKey::from_private(&attacker_privkey),
    );

    // Craft a push-type payload (e.g. Transaction) as normal
    let payload = StacksMessageType::Transaction(make_dummy_tx());

    let mut msg = StacksMessage::from_chain_view(
        PEER_VERSION_TESTNET, 0x80000000, &chain_view, payload,
    );

    // Attacker injects a forged RelayData entry naming a real, uninvolved
    // third-party NeighborAddress that never touched this message.
    msg.relayers.push(RelayData {
        peer: victim_third_party_neighbor_address(),
        seq: 1,
    });

    // Attacker signs the message themselves — relayers is part of the
    // signed byte string, so signing succeeds without any relay having occurred.
    msg.preamble.seq = 1;
    msg.do_sign(&attacker_privkey).unwrap();

    // Signature verification succeeds even though relayers is forged.
    assert!(msg.verify_secp256k1(&attacker_pubkey).is_ok());

    pub fn verify_secp256k1(&self, public_key: &StacksPublicKeyBuffer) -> Result<(), net_error> {
        let secp256k1_pubkey = public_key
            .to_public_key()
            .map_err(|e| net_error::DeserializeError(e.into()))?;

        let mut message_bits = vec![];
        self.relayers.consensus_serialize(&mut message_bits)?;
        self.payload.consensus_serialize(&mut message_bits)?;

        let mut p = self.preamble.clone();
        p.verify(&message_bits, &secp256k1_pubkey).map(|_m| ())
    }

        &mut self,
        local_peer: &LocalPeer,
        preamble: &Preamble,
        relayers: &[RelayData],

        if !ConversationP2P::check_relayer_cycles(relayers) {
            warn!(
                "Invalid relayers -- message from {:?} contains a cycle",

            );
            return false;
        }

        if !ConversationP2P::check_relayers_remote(local_peer, relayers) {
            warn!(
                "Invalid relayers -- message originates from us ({})",
                local_peer.to_neighbor_addr()
            );
            return false;
        }

        for relayer in relayers.iter() {
            self.stats
                .add_relayer(&relayer.peer, (preamble.payload_len - 1) as u64);
        }

        return true;
    }
