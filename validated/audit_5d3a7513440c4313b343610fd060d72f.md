### Title
Dust deposit-token transfers permanently occupy per-account slots, blocking victims from issuing debt or receiving new collateral types (`UserReachedMaxTokens`) - (File: contracts/Pool.sol)

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across `depositTokensOfAccount` + `debtTokensOfAccount` [1](#0-0) . `DepositToken._transfer` and `_mint` add the token to the recipient's list whenever the balance moves from 0 to any positive amount, with no minimum [2](#0-1) . An unprivileged attacker can deposit dust into every supported collateral, receive dust `msdTOKEN`s, and `transfer` 1 wei of each to a victim, filling the victim's slots. Every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` for a *new* token reverts, bricking the victim's ability to open positions [3](#0-2) .

### Finding Description
- `DepositToken.deposit(amount_, onBehalfOf_)` only requires `amount_ != 0`, so dust deposits mint dust shares [4](#0-3) .
- `transfer`/`transferFrom`/`seize` all flow through `_transfer`, which calls `pool.addToDepositTokensOfAccount(recipient_)` on any 0→nonzero balance change [5](#0-4) .
- The cap check `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` reverts inside `_mint` and `_transfer`, so a victim at cap cannot: deposit a new collateral type, receive any new `msdTOKEN` (including via liquidation `seize`, which reverts `Pool.liquidate`), or mint a new synthetic debt token (`DebtToken` calls `addToDebtTokensOfAccount` on first mint).

### Impact Explanation
Temporary freezing of position-management functionality and griefing of liquidations. While at cap the victim cannot (a) mint any new synthetic asset, (b) top up health with a different collateral type during a liquidation cascade, and (c) be liquidated via `seize` into a liquidator address holding zero of that token — the `add` inside `seize`'s `_transfer` reverts `UserReachedMaxTokens` only if the *liquidator* is also at cap, but for the victim the `seize` reduces balance and may remove/keep entries correctly; the reliable revert is on the victim's own new-token flows. The victim can self-recover by transferring each dust `msdTOKEN` out (balance → 0 removes the entry via `pool.removeFromDepositTokensOfAccount`), so impact is a temporary liveness/position freeze requiring N cleanup transactions, not permanent loss.

### Likelihood Explanation
Requires the deployed pool to have ≥30 combined deposit/debt tokens for the cap to be reachable purely via deposit-token dust (debt tokens are not transferable, so the attacker can only push deposit-token entries). If fewer than 30 deposit tokens exist, the attack is not reachable on that deployment. Attack cost is only the underlying dust plus gas, but the victim's remediation is equally cheap, and the attacker gains nothing economically — it is pure griefing. That keeps severity at the medium/low boundary.

### Recommendation
Enforce a minimum meaningful balance before registering a token in the per-account lists (e.g., skip `addToDepositTokensOfAccount` below a USD dust floor), or move the cap check out of the transfer/mint path and instead skip set registration without reverting. Alternatively allow anyone to call `removeFromDepositTokensOfAccount` for zero-balance entries.

### Proof of Concept
Hardhat (local/fork):

```ts
// Attacker fills victim's depositTokensOfAccount to MAX_TOKENS_PER_USER
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber() // 30
for (const msd of depositTokens) {                 // each supported DepositToken
  await underlying.connect(attacker).approve(msd.address, 1n)
  await msd.connect(attacker).deposit(1n, attacker.address)   // dust mint
  await msd.connect(attacker).transfer(victim.address, 1n)    // occupies a slot
}
// victim now has `depositTokensOfAccount.length == 30`
// Any new-token action reverts:
await expect(otherMsd.connect(victim).deposit(1n, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// and DebtToken.issue -> addToDebtTokensOfAccount -> same revert
```
