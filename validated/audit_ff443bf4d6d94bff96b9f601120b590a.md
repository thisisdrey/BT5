## Title
Lack of slippage protection in `ExchangeWithdrawContract` (`ExchangeWithdrawActuator`) enables front-run sandwiching of exchange-pool withdrawals - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawContract` lets a Bancor-pool creator withdraw an exact `quant` of one token from an `Exchange`/`ExchangeV2` pool. The amount of the *other* token returned (`anotherTokenQuant`) is derived purely from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio at execution time. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `doValidate()`, `ExchangeWithdrawContract` has no user-supplied minimum/maximum bound on `anotherTokenQuant`. This is the same bug class as RUSH1-4: a withdraw operation whose payout is computed from mutable pool state with no caller-specified slippage protection.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no `expected`/minimum field [1](#0-0)  — whereas `ExchangeTransactionContract` explicitly adds an `expected` field that is validated against the computed swap output [2](#0-1) , and `ExchangeTransactionActuator.doValidate()` enforces `if (anotherTokenQuant < tokenExpected) throw ContractValidateException("token required must greater than expected")` [3](#0-2) .

`ExchangeWithdrawActuator.execute()` has no equivalent check. It computes `anotherTokenQuant` from the live pool ratio at execution time and immediately credits it to the caller with no minimum bound: [4](#0-3) 

The only "protection" in `doValidate()` is a self-consistency precision check (`"Not precise enough"`) comparing the executor's own recomputation against itself, not against any value the caller specified — it does not protect against the ratio moving between transaction construction and block inclusion [5](#0-4) .

Because `firstTokenBalance`/`secondTokenBalance` can be changed by *any* other account submitting `ExchangeTransactionContract` (swap) or `ExchangeInjectContract` transactions against the same `exchange_id`, and Tron's mempool/block-packing order is attacker-influenceable (an unprivileged broadcaster can submit a transaction and have it ordered ahead of a pending withdraw in the same block), a withdrawer's actual `anotherTokenQuant` payout can be manipulated downward with no way for the withdraw transaction to reject an unfavorable outcome.

### Impact Explanation
An attacker who observes a pending `ExchangeWithdrawContract` in the mempool can front-run it with a swap (`ExchangeTransactionContract`) that skews the pool ratio, causing the victim's withdraw to receive far less of the "other token" than intended, then optionally back-run to restore the ratio and pocket the difference (a classic sandwich attack). This is a concrete value-extraction / theft-of-funds vector against any account withdrawing liquidity from a Bancor-style exchange pool — qualifying as unauthorized value extraction, matching the "exchange and market order handling" scope explicitly called out as in-scope.

### Likelihood Explanation
Any unprivileged transaction broadcaster can submit `ExchangeTransactionContract`/`ExchangeInjectContract` transactions; no special privilege, signature authority beyond a normal account, or node/committee compromise is required. The exchange pool ratio is public on-chain state, so front-running/sandwiching opportunities are trivially observable and require only ordinary transaction submission — likelihood is high for actively-used exchange pools.

### Recommendation
Add a caller-specified bound to `ExchangeWithdrawContract` (e.g., `expected`/`min_another_token_quant`, mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the withdrawal if the computed `anotherTokenQuant` falls below the caller's specified minimum, consistent with the existing pattern already implemented for `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from Victim for `exchange_id=X`, `token_id=firstTokenID`, `quant=Q`.
2. Attacker broadcasts an `ExchangeTransactionContract` swap against the same exchange that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably, and pays enough fee/energy to be packed before Victim's withdraw in the same block.
3. Victim's `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` from the now-skewed ratio [6](#0-5) , delivering a lower payout than Victim expected when they signed the transaction, with no on-chain mechanism to reject the unfavorable execution.
4. Attacker submits a reverse swap to restore the pool ratio, capturing the difference extracted from Victim's withdrawal.
