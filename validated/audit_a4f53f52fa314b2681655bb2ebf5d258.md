### Title
`Pool::liquidate` can be front-run DoSed by a dust `DebtToken::repay` - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` reverts with `AmountGreaterThanMaxLiquidable` whenever `amountToRepay_` exceeds the account's current max liquidable amount. Because `DebtToken.repay(onBehalfOf_, amount_)` is permissionless and decreases the target's debt by any amount, anyone (the borrower or a griefer) can front-run a full liquidation with a dust repayment, pushing `maxLiquidable` just below the liquidator's quoted amount and forcing a revert. This is the same bug class as Inverse Finance's `forceReplenish` front-run DoS (M-13).

### Finding Description
`Pool.liquidate` enforces an upper-bound check on `amountToRepay_` against the liquidable amount. The suite confirms the revert path: passing `debt + 1` reverts with `AmountGreaterThanMaxLiquidable`. [1](#0-0) 

The attacker-callable primitive is `DebtToken.repay`, which is `external`, `whenNotShutdown`, `nonReentrant` — no health, lock, or authorization check on the beneficiary `onBehalfOf_`. The caller burns its own synthetic tokens (`_syntheticToken.burn(_msgSender, _repaid)`) to erase `onBehalfOf_`'s debt. [2](#0-1) 

Attack flow:
1. Liquidator observes an unhealthy position and submits `liquidate(synth, victim, amountToRepay, depositToken)` sized at (or near) the full liquidable amount, which is the economically attractive way to liquidate.
2. The borrower (or any griefer, or a bot) front-runs in the same block with `debtToken.repay(victim, dust)` — cost is `dust + fee` worth of synth.
3. The victim's debt drops by dust, so `maxLiquidable` drops correspondingly, and the liquidator's `amountToRepay` is now `> maxLiquidable` → revert `AmountGreaterThanMaxLiquidable`.

An underwater borrower can repeat this each block, keeping its own liquidation failing while only ever paying dust — identical to the sponsor's confirmation scenario in M-13 ("attacker has an underwater loan and keeps front running his own forced replenishments with single digit ... forced replenishments").

### Impact Explanation
Temporary liveness DoS on liquidations: an underwater borrower can repeatedly cause full-size liquidation transactions to revert at dust cost, delaying liquidation of a deteriorating position and increasing the risk of bad debt accruing to the pool. It does not permanently block liquidation — the liquidator can resubmit with `min(debt, maxLiquidable)` quoting or use partial amounts — so impact mirrors the original report (minor/medium griefing, no direct theft).

### Likelihood Explanation
Medium-low. Requires same-block front-running (the victim's `repay` must land before `liquidate` in the same block, or the attacker must over-repay to cover interest accrual between blocks, exactly as in the original report). The attacker's cost is real synth tokens burned, but arbitrarily small. Like M-13, the rational alternative — just front-running the liquidation itself for the bonus — limits practical exploitability, but a borrower defending its own underwater position has a clear motive.

### Recommendation
Inside `Pool.liquidate`, use `amountToRepay = Math.min(amountToRepay_, maxLiquidable)` instead of reverting when `amountToRepay_ > maxLiquidable`, mirroring the upstream fix (`min(deficit, amount)`). This keeps front-running harmless and preserves the intuitive "pass max debt to fully liquidate" UX.

### Proof of Concept
Reproducible in the existing Foundry/Hardhat setup used by `test/Pool.test.ts`:

```ts
// setup: alice has an unhealthy position with msETH debt (as in existing liquidate tests)
const debtBefore = await msEthDebtToken.balanceOf(alice.address);
const amountToRepay = debtBefore; // full liquidation

// attacker/borrower front-runs with dust repay using their own msETH
await msEthDebtToken.connect(griefer).repay(alice.address, 1);

// liquidator's tx reverts
await expect(
  pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');
```

The revert path is already demonstrated by the existing test "should revert if debt amount is < amount to repay". [1](#0-0)

    function repay(
        address onBehalfOf_,
        uint256 amount_
    )
        external
        override
        whenNotShutdown
        nonReentrant
        onlyIfSyntheticTokenExists
        returns (uint256 _repaid, uint256 _fee)
    {
        if (amount_ == 0) revert AmountIsZero();

        accrueInterest();

        address _msgSender = _msgSender();
        IPool _pool = pool;
        ISyntheticToken _syntheticToken = syntheticToken;

        (_repaid, _fee) = quoteRepayOut(amount_);
        if (_fee > 0) {
            _syntheticToken.seize(_msgSender, _pool.feeCollector(), _fee);
        }

        uint256 _debtFloorInUsd = _pool.debtFloorInUsd();
        if (_debtFloorInUsd > 0) {
            uint256 _newDebtInUsd = _pool.masterOracle().quoteTokenToUsd(
                address(_syntheticToken),
                balanceOf(onBehalfOf_) - _repaid
            );
            if (_newDebtInUsd > 0 && _newDebtInUsd < _debtFloorInUsd) {
                revert RemainingDebtIsLowerThanTheFloor();
            }
        }

        _syntheticToken.burn(_msgSender, _repaid);
        _burn(onBehalfOf_, _repaid);

        emit DebtRepaid(_msgSender, onBehalfOf_, amount_, _repaid, _fee);
    }
