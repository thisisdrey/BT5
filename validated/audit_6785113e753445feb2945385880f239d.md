### Title
`AttachmentsBatchStateContext::extend_with_inventories` stores attacker inventory response without verifying `response.block_id == request.index_block_hash` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`extend_with_inventories` decodes a peer's `GetAttachmentsInvResponse` and inserts it into `self.inventories` keyed by `request.key()`, which is derived solely from the *request's* `contract_id`, `pages`, and `index_block_hash`. The response's own `block_id` field is never compared to the request's `index_block_hash` before the response is trusted and stored, so a malicious/misbehaving peer can return inventory bits for an arbitrary block while the caller treats them as valid for the requested tip.

### Finding Description
`AttachmentsInventoryRequest` carries `contract_id`, `pages`, and `index_block_hash` (the block being queried) [1](#0-0) . In `extend_with_inventories`, for each succeeded request/response pair, the raw HTTP response is decoded via `response.decode_atlas_attachments_inv_response()` and, on success, inserted into `self.inventories` under `request.key()` — built purely from request fields — with no check against the decoded `GetAttachmentsInvResponse`'s own `block_id`:

```
if let Ok(response) = response.decode_atlas_attachments_inv_response() {
    let peer_url = request.get_url().clone();
    match self.inventories.entry(request.key()) {
        Entry::Occupied(responses) => { responses.into_mut().insert(peer_url, response); }
        Entry::Vacant(v) => { ... v.insert(responses); }
    };
    report.bump_successful_requests();
}
``` [2](#0-1) 

The `inventories` map type itself is keyed by `(QualifiedContractIdentifier, Vec<u32>, StacksBlockId)` taken from the request, not the response [3](#0-2) . Nowhere in this function (nor visibly upstream in the shown code) is there an equality check `response.block_id == request.index_block_hash`. Consequently, a remote peer answering an `AttachmentsInventoryRequest` can supply a `GetAttachmentsInvResponse` whose `block_id` names a different block than the one requested, and its `AttachmentPage` bitmap will still be filed under the requester's `index_block_hash`.

Downstream, `get_prioritized_attachments_requests` consumes `self.inventories` per the request-derived key, uses the (possibly-forged) `pages`/bit vectors to decide which peer "has" a given attachment, and issues `AttachmentRequest`s accordingly [4](#0-3) . Since the availability decision is driven entirely by the stored (unverified) bitmap, a peer can claim availability that is not tied to the actual requested tip's attachment set.

### Impact Explanation
A remote peer serving Atlas attachment-inventory responses can inject availability bits attributed to a different `index_block_hash` than what was requested, without any signature or hash binding check in this code path. This can steer the downloader into believing attachments are/aren't available for a specific tip based on unrelated block data, which matches the "steering a node off the tip via false inventory / attachment mismatch" High-impact category. The direct consequence is limited to attachment inventory bookkeeping (which attachment-fetch requests get issued to which peers) — it does not by itself corrupt chain state, but it can misdirect subsequent `AttachmentRequest`s and waste bandwidth/compute on content not tied to the queried tip, and is repeatable on every inventory round for any peer the node queries.

### Likelihood Explanation
The attacker only needs to run/control an "outbound sync peer" that the Atlas downloader queries for attachment inventories (a normal, unprivileged network role) and answer with a crafted `GetAttachmentsInvResponse` HTTP body containing a mismatched `block_id` — no secret, signature, or privileged role is required. The request must merely be outstanding (which happens routinely during normal Atlas attachment sync), making this trivially and repeatedly reachable.

### Recommendation
In `extend_with_inventories`, after decoding the response, explicitly verify `response.block_id == request.index_block_hash` (and ideally that `response.pages` correspond to `request.pages`) before inserting into `self.inventories`; treat a mismatch as a failed/faulty response (`report.bump_failed_requests()` and/or mark peer as faulty) rather than silently trusting the decoded payload.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module) plan:
1. Construct an `AttachmentsInventoryRequest` with a fixed `index_block_hash = A`, `contract_id`, `pages`.
2. Build a `BatchedRequestsResult` whose `succeeded` map contains this request paired with a `StacksHttpResponse` whose body decodes (via `decode_atlas_attachments_inv_response`) to a `GetAttachmentsInvResponse` with `block_id = B` (B != A) and an arbitrary `AttachmentPage` bitmap.
3. Call `AttachmentsBatchStateContext::extend_with_inventories` on a context containing the peer in `self.peers`.
4. Assert that `context.inventories` contains a key equal to `(contract_id, pages, A)` (the request's hash) mapping to the response with `block_id == B` — demonstrating the stored inventory is keyed by the request's block hash despite the response actually describing a different block, with no rejection occurring.

    pub fn get_prioritized_attachments_requests(&self) -> BinaryHeap<AttachmentRequest> {
        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }
