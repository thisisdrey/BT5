### Title
Dust `DepositToken` transfers fill a victim's `depositTokensOf` list to `MAX_TOKENS_PER_USER`, blocking all new deposits — (`File: contracts/Pool.sol`)

### Summary
The bug class in the external report is "attacker-craftable dust state that makes a permissionless maintenance/refresh path revert, permanently freezing the account's ability to update." Metronome's analog is the account token-list griefing: `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from 0 to non-zero, and `Pool` enforces `MAX_TOKENS_PER_USER = 30` on that list. An unprivileged attacker can dust-transfer 1 wei of up to 30 different `DepositToken`s to a victim, filling the list. Any subsequent deposit (or transfer) of a *new* deposit token to the victim reverts, freezing their ability to add collateral.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's tracked list on first receipt:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

Removal only happens when the sender's balance reaches exactly zero (`DepositToken.sol:523-525`), and `Pool.sol:79` caps the list at `MAX_TOKENS_PER_USER = 30` via `MappedEnumerableSet.AddressSet` (`contracts/lib/MappedEnumerableSet.sol`, `contracts/storage/PoolStorage.sol`).

Attack steps (unprivileged, direct calls or via `Operator.execute`):
1. Attacker deposits minimal underlying into 30 `DepositToken`s (or receives them via transfers), obtaining ≥1 wei of each.
2. Attacker calls `depositToken.transfer(victim, 1)` for each of the 30 tokens. Each call adds the token to `depositTokensOf[victim]`.
3. `depositTokensOf[victim]` now holds 30 entries of ~1 wei each.
4. Victim's `deposit()` into any deposit token not already in their list reverts on the cap. Minting/debt issuance paths that pull in a new collateral are equally blocked. Liquidations that would credit a new token (e.g., `seize` to the victim as liquidator recipient) also revert.

The victim can only clear slots by `withdraw`-ing the dust. If the victim carries debt, `unlockedBalanceOf`/`_revertIfLocked` can leave the dust locked, making the freeze persist until the victim repays debt first — mirroring the "unpokeable NFT" liveness break of the report.

### Impact Explanation
Temporary-to-persistent freezing of the deposit/collateral-entry path for the victim: they cannot open positions in new collateral types, and in the locked-collateral case cannot clear the dust entries without first repaying debt. This maps to "temporary freezing of funds" — the victim's inbound collateral flow is bricked by an unprivileged attacker for bounded cost (30 dust deposits).

### Likelihood Explanation
High. Cost is 30 token acquisitions/transfers of 1 wei each; no privileged role, oracle, or flash capital is needed. Deposit tokens are permissionlessly transferable by design.

### Recommendation
Track membership idempotently without reverting on cap for transfers (e.g., skip the revert and keep an unbounded set for bookkeeping, cap only health-check iteration), or ignore/remove zero-and-near-zero entries during `addToDepositTokensOfAccount`, or allow `removeFromDepositTokensOfAccount` on `claimRewards`-style recovery calls. At minimum, do not let a permissionless `transfer` permanently consume victim list slots.

### Proof of Concept
```typescript
// Hardhat, metronome-synth-public--019 test env
// victim holds some collateral + debt so lockedBalance > 0
for (const dt of thirtyDepositTokens) {
  // attacker seeded 1 wei of each dt beforehand
  await dt.connect(attacker).transfer(victim.address, 1);
}
expect(await pool.depositTokensOf(victim.address)).to.have.lengthOf(30);
// victim tries to deposit a collateral type not yet in the list
await expect(
  newDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'MaxNumberOfTokensPerUser'); // per MappedEnumerableSet.add
// victim cannot purge dust while locked
await expect(
  thirtyDepositTokens[0].connect(victim).withdraw(1, victim.address)
).to.be.revertedWithCustomError(thirtyDepositTokens[0], 'UnlockedBalanceTooLow');
```

*Caveat:* I confirmed the list-add on first receipt, the `MAX_TOKENS_PER_USER = 30` cap, and the remove-on-zero logic in the indexed code; the exact revert name inside `addToDepositTokensOfAccount`/`MappedEnumerableSet.add` and the deployed count of deposit tokens per pool should be verified when writing the runnable PoC.
