### Title
Permanent, Never-Reconciled Partition Assignment Allows a Single Push/Fork to Wedge a Repository into a Shared Write-Serialized Partition Forever - (File: internal/gitaly/storage/storagemgr/partition_assigner.go)

### Summary
Gitaly's `partitionAssigner` records a `(relative_path -> partition_id)` mapping the first time a repository is touched, and never updates or deletes this mapping afterwards, even when the repository is deleted or its underlying alternate/pool link changes. This is the same bug class as the ThorWallet finding: a single boolean/sticky piece of state ("is linked to X") is set once by an ordinary, low-privilege interaction and then permanently and irreversibly gates all future behavior for the resource, regardless of whether the triggering condition still holds.

### Finding Description
`partitionAssigner.getPartitionID` (`internal/gitaly/storage/storagemgr/partition_assigner.go:156-190`) is invoked from `StorageManager.Begin` (`internal/gitaly/storage/storagemgr/partition_manager.go:344-363`) on every transactional RPC. On first access to a `relativePath`, `assignPartitionID` (lines 290-315) computes the partition either from an existing alternate (`getAlternatePartitionID`) or allocates a brand-new partition, and then calls `partitionAssignmentTable.setPartitionID` (lines 80-91), which is a permanent, unconditional key-value write: [1](#0-0) 

Once set, `getPartitionIDRecursive` (lines 234-288) only ever *reads* the existing assignment for that relative path and returns it — there is no code path that re-evaluates or removes the mapping: [2](#0-1) 

`doc/transactions.md` documents this explicitly as a known limitation: *"The assignment handling is fairly crude at the moment. The assignments are created before the repository is even created, and assignments are not deleted even if the repository is deleted."* [3](#0-2) 

This mirrors the ThorWallet root cause precisely: `isBridgedTokenHolder[_to] = true` is set once on a trivial event and never reset, so all subsequent, unrelated activity for that address is judged by stale state. Here, the "trivial event" is any ordinary repository creation/fork/pool-link operation (`CreateFork`, `CreateObjectPool`, `LinkRepositoryToObjectPool`, or any push that first touches a relative path with an `alternate` hint), which is entirely reachable by an ordinary authenticated user via `RepositoryService`/`ObjectPoolService` RPCs — see the RPC set that mutates alternates and drives partition assignment: `internal/git/objectpool/link.go:21-84`, `proto/objectpool.proto:31-98`.

Because a repository and its object-pool alternate are forced into the **same partition**, and a partition has exactly one serialized writer goroutine (per `doc/transactions.md:72-78`, `TransactionManager.Run()`), an ordinary user's `CreateFork`/`LinkRepositoryToObjectPool` action permanently and irrevocably binds a repository's write path to the partition write-lock of every other repository ever linked into that same object pool — for the entire remaining lifetime of the storage, even after `DisconnectGitAlternates` removes the actual Git-level alternate link, and even after the repository is deleted and its relative path is later reused by an unrelated repository.

### Impact Explanation
- **Cross-repository resource entanglement / stale-state DoS surface**: because assignment is immutable, a repository that once shared a pool remains permanently serialized behind that pool's single-writer partition lock, contradicting the actual (post-disconnect) state of the repository, exactly as the ThorWallet bug left users permanently restricted despite no longer holding "bridged" tokens.
- **Deleted-and-recreated relative paths**: since assignments are not removed on repository deletion, a relative path that is deleted and later recreated (a supported GitLab workflow — project removal/re-creation reuses hashed storage paths) is silently re-attached to the old, potentially unrelated partition and its former pool-mates, without any of the actual Git-level alternates/pool-link checks being re-run for the new repository.
- This falls into the "DoS of a handler" and "cross-repository" categories: legitimate, unprivileged write traffic to one repository can be serialized behind a stale/foreign partition's write-ahead log processing indefinitely, and the mapping can never be corrected short of operator intervention on the underlying key-value store.

### Likelihood Explanation
Reaching the vulnerable code path requires only ordinary, unprivileged actions available to any authenticated Gitaly/GitLab user: creating a fork (`CreateFork`), creating/linking an object pool (`CreateObjectPool`, `LinkRepositoryToObjectPool`), or any push that is routed through `StorageManager.Begin` with an alternate relative path hint. No elevated privileges, leaked tokens, or malicious peers are required — this is a first-class, documented code path (`doc/transactions.md`) hit on every transactional RPC. The likelihood of the *entangling* assignment being created is high; the more severe corollary (relative-path reuse after deletion causing unrelated repos to inherit a stale partition) requires the additional real-world precondition of project deletion + path reuse, which GitLab's hashed-storage / project-recreation flows do support, but I could not directly verify from the indexed code that recreation reuses the exact same relative path in all deployments — this part carries some uncertainty since I did not find the Rails-side project recreation code in this repo.

### Recommendation
- Reconcile the partition assignment at each access instead of treating it as write-once: read the *current* `objects/info/alternates` state before trusting a stored assignment, and if the underlying alternate relationship has changed (removed via `DisconnectGitAlternates`) or the repository doesn't exist, invalidate/migrate the stale assignment.
- Delete the partition assignment entry when a repository is deleted (`Commit{..., DeleteRepository: true}` path in `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`) so a later repository created at the same relative path is assigned fresh rather than inheriting a stale partition.
- Track the *actual current* alternate target as data (analogous to the report's recommendation to track a `bridgedBalances` mapping instead of a boolean) rather than an immutable one-time flag, so a repository that legitimately leaves a pool via `DisconnectGitAlternates` is not permanently stuck serialized behind that pool's other members.

### Proof of Concept
Conceptual sequence based on the read code (I did not execute this against a live cluster, so treat it as a reasoning-level PoC rather than a verified exploit trace):
1. User A calls `CreateObjectPool` from repository `X`, then `LinkRepositoryToObjectPool` to link fork `Y` to that pool. `partitionAssigner.assignPartitionID` runs once for `Y`, discovers the alternate to the pool via `getAlternatePartitionID` (`internal/gitaly/storage/storagemgr/partition_assigner.go:317-359`), and permanently stores `partition_assignment/Y = P` where `P` is the pool's partition.
2. User A later calls `DisconnectGitAlternates` on `Y` (`internal/gitaly/service/objectpool/alternates_test.go:17-55` shows this removes the `objects/info/alternates` file and re-associates objects locally).
3. Despite `Y` no longer being Git-level linked to the pool, every subsequent `StorageManager.Begin(ctx, {RelativePath: Y})` call (`internal/gitaly/storage/storagemgr/partition_manager.go:354`) still resolves to the old partition `P` via `getPartitionIDRecursive`'s cached lookup (`internal/gitaly/storage/storagemgr/partition_assigner.go:236`), because nothing ever calls `setPartitionID` again or clears the old entry.
4. `Y`'s writes remain permanently serialized behind partition `P`'s single writer goroutine together with the pool and any other former/current members, even though `Y` is, by all Git-level metrics, an independent repository again — an unrelated, unprivileged, unbounded coupling that persists for the life of the storage, matching the "sticky boolean, once set never cleared" bug class from the source report.

func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}

func (pa *partitionAssigner) assignPartitionID(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID) (storage.PartitionID, error) {
	// Check if the repository has an alternate. If so, it needs to go into the same
	// partition with it.
	ptnID, err := pa.getAlternatePartitionID(ctx, relativePath, recursiveCall, partitionHint)
	if err != nil {
		if !errors.Is(err, gitstorage.ErrNoAlternate) {
			return 0, fmt.Errorf("get alternate partition ID: %w", err)
		}

		ptnID = partitionHint
		if ptnID == invalidPartitionID {
			// The repository has no alternate. Unpooled repositories go into their own partitions.
			// Allocate a new partition ID for this repository.
			ptnID, err = pa.allocatePartitionID()
			if err != nil {
				return 0, fmt.Errorf("acquire partition id: %w", err)
			}
		}
	}

	if err := pa.partitionAssignmentTable.setPartitionID(relativePath, ptnID); err != nil {
		return 0, fmt.Errorf("set partition: %w", err)
	}

	return ptnID, nil
}
