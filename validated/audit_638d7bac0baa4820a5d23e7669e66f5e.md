### Title
Divergent outcomes between `UpdateTrackedShard` and `ValidateChunkStateWitness` for `FunctionCall` to an account using an undistributed `Global` contract - ([File: runtime/runtime/src/function_call.rs])

### Summary
`execute_function_call` treats a missing contract body (`VMRunnerError::ContractCodeNotPresent`) differently depending on `ApplyState::apply_reason`: for `ValidateChunkStateWitness` it returns a hard `StorageError::MissingTrieValue`, but for any other reason (including `UpdateTrackedShard`) it silently falls through to `Ok(VMOutcome::nop_outcome(CodeDoesNotExist))`, guarded only by a `debug_assert!` that is compiled out in release builds. Because global-contract code is populated on each shard asynchronously via a chained `GlobalContractDistributionReceipt` hop-by-hop (`forward_distribution_next_shard`), an account can legitimately commit to a `Global` contract identifier (via `UseGlobalContract`) before the code has landed in a given shard's trie, causing the two code paths to diverge deterministically for the same receipt/state.

### Finding Description
`execute_function_call` (`runtime/runtime/src/function_call.rs:290-313`) handles `Err(VMRunnerError::ContractCodeNotPresent)` as follows: [1](#0-0) 
When `runtime_ext.account().contract().is_some()` (i.e. the account "commits" to a code hash, which happens for both local and `RuntimeContractIdentifier::Global` contracts resolved by `RuntimeContractIdentifier::resolve`, `runtime/runtime/src/contract_code.rs:36-73`), a genuinely missing code body is only turned into a hard `MissingTrieValue` error when `apply_reason == ValidateChunkStateWitness`. Otherwise (including `UpdateTrackedShard`, which is only guarded by a `debug_assert!` that no-ops in release builds), the call quietly returns a `nop_outcome(CodeDoesNotExist)` — i.e. execution "succeeds" as a no-op failed call rather than aborting with a storage error.

`record_contract_call` (`runtime/runtime/src/function_call.rs:357-395`), which is responsible for recording the accessed global/account-local contract for out-of-band distribution to validators, is a no-op unless `apply_reason == UpdateTrackedShard`, and it silently treats a missing trie entry as "nothing to record" (`.or_else(... MissingTrieValue => Ok(None))`).

Global-contract code is not distributed atomically to all shards. `initiate_distribution`/`forward_distribution_next_shard` (`runtime/runtime/src/global_contracts.rs:142-321`) propagate the code one shard at a time by chaining `GlobalContractDistributionReceipt`s (`already_delivered_shards` tracked incrementally, one `next_shard` per hop), so there is a window, spanning multiple blocks, during which some shards have `TrieKey::GlobalContractCode{identifier}` populated and others do not.

An unprivileged attacker A can `DeployGlobalContract`, and attacker B (any funded account, possibly on a different shard) can immediately issue `UseGlobalContract` (setting `AccountContract` to reference A's just-created identifier) followed by a `FunctionCall`, before the distribution receipt has reached B's shard. On the shard that has not yet received the code, `execute_function_call` genuinely hits `ContractCodeNotPresent` (this is not proof/witness incompleteness — the code truly is absent from that shard's state at that block). A chunk-producing node applying this with `apply_reason == UpdateTrackedShard` proceeds along the `nop_outcome(CodeDoesNotExist)` path and produces a `ChunkExtra`/outgoing-receipts set reflecting a "no-op failed call." A stateless validator re-executing the identical receipt against the recorded partial state with `apply_reason == ValidateChunkStateWitness` takes the other branch and returns `Err(StorageError::MissingTrieValue)`, aborting witness validation entirely (`Error::InvalidChunkStateWitness`) instead of producing a matching outcome.

No existing check (signature, nonce, access-key, gas metering, storage staking, size limits) constrains this, since both the `DeployGlobalContract` and `UseGlobalContract` actions are ordinary, unprivileged, fee-paying actions, and the race window is a function of protocol-level cross-shard distribution timing rather than any input validation gap.

### Impact Explanation
This produces state-root / outcome divergence between chunk producers (who accept the chunk as valid, since `nop_outcome` allows normal chunk production to proceed) and chunk validators (who reject the identical chunk with `Error::InvalidChunkStateWitness`), matching the "Determinism" / consensus-divergence category: chunk validators may be unable to endorse a chunk that its own producer(s) consider valid, which can stall chunk inclusion (repeated endorsement failures) or, if enough honest validators disagree with producers, contribute to a chain split scenario.

### Likelihood Explanation
The precondition is simply timing: a `FunctionCall` (via a fresh `UseGlobalContract`) reaching a shard before the asynchronous, hop-by-hop `GlobalContractDistributionReceipt` chain has delivered the code to that shard. This is entirely achievable by an unprivileged attacker who controls transaction submission timing relative to a just-issued `DeployGlobalContract`, and is reproducible deterministically (not merely probabilistically) any time the distribution lag is exploited, at the cost of ordinary gas/storage fees for `DeployGlobalContract`, `UseGlobalContract`, and `FunctionCall`.

### Recommendation
Make the `ContractCodeNotPresent` handling in `execute_function_call` independent of `ApplyChunkReason`: either always treat a genuinely-missing committed contract code as a real error (not a `nop_outcome`) regardless of `apply_reason`, or explicitly block `UseGlobalContract`/subsequent `FunctionCall` execution until distribution to the shard is confirmed complete (e.g. by having the runtime treat a not-yet-locally-available global contract as a deferred/failed call consistently on both the producer and validator paths), and remove reliance on a `debug_assert!` for what is described in comments as an "inconsistent state" invariant that is in fact reachable via cross-shard distribution timing.

### Proof of Concept
Test-loop integration test, extending the existing `global_contracts_distribution.rs` scaffolding:
1. Set up a multi-shard `TestLoopEnv` with accounts A (deployer) and B (caller) on different shards.
2. A: `DeployGlobalContract` (`GlobalContractDeployMode::CodeHash` or `AccountId`).
3. Immediately, before letting the `GlobalContractDistributionReceipt` chain reach B's shard, submit from B: `UseGlobalContract(identifier)` followed by a `FunctionCall` to B's own account in the same or very next block.
4. Assert that `ValidateChunkStateWitness` (via `validate_chunk_state_witness`) returns `Err`/`Error::InvalidChunkStateWitness` while the chunk-producer's own applied chunk (`UpdateTrackedShard`/apply path) produces `result.result` = `Ok`/no-op failure for the same receipt — i.e. `Runtime::apply` outcome for `UpdateTrackedShard` and `validate_chunk_state_witness` outcome for the identical receipt differ, demonstrating non-determinism between chunk production and stateless validation.
