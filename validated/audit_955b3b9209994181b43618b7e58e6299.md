### Title
Reused account names inherit stale self-authorized `PostponedReceipt`/`PromiseYield` state, allowing a dangling `AddKey` to execute with full permission on a re-created account - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`remove_account` (called from `action_delete_account`) removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never removes `TrieKey::PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, or the yield/data id mappings that are keyed by the account name. `action_create_account` only writes a fresh `TrieKey::Account` and performs no check for or cleanup of these leftover rows. Because the receipt-execution permission check (`check_actor_permissions`) only compares `actor_id == account_id` (both plain `AccountId` strings) with no binding to a specific account "instance", a self-authorized postponed action receipt created before deletion will still pass permission checks and execute against a different, freshly (re)created account of the same name.

### Finding Description
`remove_account` in [1](#0-0)  only removes `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`. It never touches `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId` rows for that `account_id`.

`action_delete_account` in [2](#0-1)  calls `remove_account` and sets `*account = None`, but has no logic to also scrub any of these dangling rows.

`action_create_account` in [3](#0-2)  only validates naming rules and writes a brand-new `Account`; it performs no check for and no cleanup of any pre-existing `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`/`PromiseYieldReceipt` rows keyed to `account_id`.

The permission check that is supposed to guard `AddKey` (and `DeployContract`/`Stake`/`DeleteKey`/`DeleteAccount`) is `check_actor_permissions` in [4](#0-3) , which only requires `actor_id == account_id`. `actor_id` is initialized from `receipt.predecessor_id()` at the start of `apply_action_receipt`: [5](#0-4) . This check is re-evaluated every time a postponed receipt finally executes — including long after the receipt was first postponed — and is not tied to any particular "incarnation" of the account, only to the string equality of `AccountId`s.

The postponed-receipt data-dependency machinery stores/retrieves state purely keyed by `account_id`/`data_id`/`receipt_id`: `process_action_receipt` stores `PostponedReceiptId`, `PendingDataCount`, and the postponed `Receipt` itself ( [6](#0-5) ), and the `Data` branch of `process_receipt` looks these up again purely by `account_id`/`data_id` when a matching `DataReceipt` arrives, and on completion calls `apply_action_receipt` on the recovered postponed receipt ( [7](#0-6) ).

Exploit flow:
1. Attacker (owner of some account, e.g. `victim`) causes their own contract on `victim` to issue an action receipt to itself (`predecessor_id == receiver_id == victim`) with actions `[AddKey(full_access, attacker_pubkey)]` and at least one unresolved `input_data_id` (e.g. a promise `.then()` chained on a cross-contract call). This receipt gets legitimately postponed via `process_action_receipt`, storing `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` under key `victim`.
2. Before the dependency `DataReceipt` resolves, the attacker issues `DeleteAccount(victim)` from `victim` itself (passes `check_actor_permissions` since `actor_id == account_id == victim`). `remove_account` wipes `Account`/keys/code/data, but the postponed-receipt rows for `victim` remain in the trie.
3. A third party creates a brand-new account also named `victim` via `CreateAccount`, funds it with a `Transfer`, and adds their own `AddKey` (full access). `action_create_account` performs no check against, and does not clear, the leftover `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows still present under `victim`.
4. The attacker (who knows the `data_id` they set up in step 1) sends the corresponding `DataReceipt` for that `data_id` to `victim`. `process_receipt`'s `Data` branch finds the still-present `PostponedReceiptId`, decrements `PendingDataCount` to zero, fetches the still-present postponed `Receipt`, and calls `apply_action_receipt` on it.
5. Inside that call, `actor_id` is initialized to the stored `predecessor_id` (`victim`), `account_id` is `victim` (the new account), so `check_actor_permissions` for `AddKey` passes (`actor_id == account_id`), and `action_add_key` installs the attacker's public key as a full-access key on the third party's freshly-funded account.

This bypasses NEAR's intended authorization model, which assumes `AddKey`/`DeployContract`/`Stake`/`DeleteKey`/`DeleteAccount` can only be self-authorized by the actual current owner of the account, because the permission check has no notion of "account identity/incarnation" — it is purely a string comparison against `AccountId`, and the underlying postponed/self-authorized state is never invalidated on account deletion nor checked on account re-creation.

### Impact Explanation
This is theft of funds: an attacker can inject a full-access key onto any account that gets created under a previously attacker-controlled and then attacker-deleted account name, allowing them to drain any balance the new owner deposits. This matches the "authorization escalation across accounts" and "theft of funds" bounty categories, since the attacker executes a self-privileged `AddKey` action against an account they no longer own, using only unprivileged transactions against their own account and a subsequently delivered `DataReceipt`.

### Likelihood Explanation
No validator, node-operator, or special privilege is required — everything is achievable with ordinary signed transactions from a normal funded account (deploying a small contract that issues a chained/awaited self-promise with an `AddKey` action, then deleting the account, then later delivering the pending cross-shard `DataReceipt`). The main precondition is that a third party independently chooses to (re)create an account with the exact same name the attacker previously owned and deleted, and funds it before the attacker triggers the dependency — this is a realistic scenario for account-name squatting/recycling (e.g., short/desirable names, or names an attacker advertises as available). The attack is fully repeatable: the attacker can pre-stage many such booby-trapped account names in advance at low cost.

### Recommendation
Bind postponed/self-authorized receipt state to the account's lifetime: either (a) have `remove_account` also purge all `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, and yield/data id mapping rows for the account being deleted (via prefix iteration similar to how access keys/contract data are already swept), or (b) have `action_create_account` check for and reject/clear any leftover rows of these kinds for the account name being created before allowing account creation. Additionally, consider making `check_actor_permissions`/postponed-receipt validation account-incarnation aware (e.g., reject execution of a postponed receipt if the account was deleted and recreated since the receipt was postponed).

### Proof of Concept
Runtime integration test plan (`runtime/runtime/tests` or `test-loop-tests`):
1. Set up account `victim` with a contract that, via `call_promise`, creates a self-action-receipt (`predecessor_id == receiver_id == victim`) containing `AddKey(attacker_pubkey, FullAccess)` with an `input_data_id` that depends on a cross-contract call to another account (so it becomes a stored `PostponedReceipt` on `victim`), and record the `data_id`.
2. In a later transaction, have `victim` (self-authorized) execute `DeleteAccount(beneficiary_id)`.
3. Assert via direct trie/state inspection that `TrieKey::PostponedReceipt{receiver_id: victim, ..}`, `PostponedReceiptId`, and `PendingDataCount` rows still exist after deletion (demonstrating `remove_account` leaves them).
4. Have a different signer submit `CreateAccount(victim)` + `Transfer(deposit)` + `AddKey(their_own_pubkey, FullAccess)` to recreate `victim`.
5. Deliver the pending `DataReceipt` for the recorded `data_id` to `victim`.
6. Assert that `attacker_pubkey` now exists as a `FullAccess` key on `victim`'s account, and that the attacker can subsequently submit a `Transfer`/withdrawal transaction signed by `attacker_pubkey` draining the funds deposited in step 4.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
