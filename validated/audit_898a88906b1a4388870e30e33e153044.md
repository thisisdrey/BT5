Found a valid analog in `lending_pool_collect_bank_fees`, which unconditionally issues three separate SPL transfers (group fee, insurance fee, program fee) even when the computed amount is `0`, with no `amount != 0` guard, unlike other instructions in the codebase that do skip on `amount == 0`.

### Title
Permissionless `collect_bank_fees` can be permanently DoS'd via unconditional zero-amount transfers on tokens that revert on zero transfers - (File: `programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs`)

### Summary
`lending_pool_collect_bank_fees` computes three fee-transfer amounts (`group_fee_transfer_amount`, `insurance_fee_transfer_amount`, `program_fee_transfer_amount`) and unconditionally calls `bank.withdraw_spl_transfer` for each, even when the computed amount is `0`. [1](#0-0)  This mirrors the OpenQ `TieredPercentageBountyV1` bug class: a contract path that always attempts an SPL transfer regardless of whether the amount is non-zero, which breaks permanently on tokens that revert on zero-value `transfer`/`transfer_checked` calls.

### Finding Description
`bank.withdraw_spl_transfer` performs the CPI transfer directly with no `amount != 0` early-return guard: [2](#0-1)  Every call to `lending_pool_collect_bank_fees` computes `min(outstanding, available_liquidity)` for each of the three fee categories; whenever `outstanding` is `0` for any one category (a very common, not adversary-engineered, steady state — e.g., right after a prior successful collection, or before any interest/program fees have accrued), the code still calls `withdraw_spl_transfer(0, ...)` for that vault leg. [3](#0-2) [4](#0-3) [5](#0-4) 

Notably, other parts of the codebase are explicitly aware of this class of problem and defensively skip the transfer call when `amount == 0`, e.g. `lending_pool_emissions_deposit`, `super_admin_deposit`, `super_admin_withdraw`, and the Drift `cpi_transfer_to_destination` helper all short-circuit with `if amount == 0 { return Ok(...) }` before invoking a transfer. [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8)  This confirms the omission in `collect_bank_fees` (and in `lending_pool_withdraw_fees` / `lending_pool_withdraw_insurance` / `lending_pool_withdraw_fees_permissionless`, which pass caller-supplied `amount` straight to `withdraw_spl_transfer` without a zero check) is an inconsistency in the codebase rather than an intentional design choice.

`lending_pool_collect_bank_fees` is permissionless — its `Accounts` struct only requires the group not be paused, with no admin/signer gating: [10](#0-9)  so any bank using a mint whose token program rejects zero-amount transfers (some SPL-Token-2022 mints with certain extensions, or any custom/Token-2022 mint enforcing non-zero transfer amounts) becomes permanently unable to run this instruction, since one of the three legs will inevitably be `0` in virtually every call (e.g. immediately after any prior successful collection resets that category's outstanding to `0`).

### Impact Explanation
Once bricked, `collect_bank_fees` can never succeed again for that bank, because at least one of the three fee categories is essentially always `0` at some point in the bank's lifecycle (protocol/insurance/group fees don't all accrue simultaneously). This permanently freezes the bank's protocol/insurance/group fee revenue withdrawal path (`lending_pool_withdraw_fees`, `lending_pool_withdraw_insurance`, `lending_pool_withdraw_fees_permissionless` also feed off vaults populated only via `collect_bank_fees`). This is a genuine, permanent freeze of protocol-owned funds accounting in the fee path, matching the "permanent lock/freeze" impact category. It does not directly touch user deposit/withdraw/borrow/repay flows, which remain functional.

### Likelihood Explanation
No adversarial funding/refunding sequence is required (unlike the original OpenQ bug) — the zero-amount condition arises naturally and inevitably during normal operation for any bank using such a mint. The only precondition is that a group admin lists a bank for a mint whose token program reverts on zero-value transfers. Given the codebase's stated intent to support "any" token as a bank mint (as referenced in the guides and in the emissions-deposit mint-hazard checks), and the presence of Token-2022 support throughout, this is a realistic configuration, not a purely theoretical one.

### Recommendation
Add an `amount != 0` guard before each of the three `bank.withdraw_spl_transfer` calls in `lending_pool_collect_bank_fees` (and consider the same defensive check inside `withdraw_spl_transfer`/`deposit_spl_transfer` themselves, or in `lending_pool_withdraw_fees`, `lending_pool_withdraw_insurance`, and `lending_pool_withdraw_fees_permissionless`), consistent with the pattern already used in `lending_pool_emissions_deposit`, `super_admin_deposit`, `super_admin_withdraw`, and the Drift bad-debt claim path.

### Proof of Concept
1. Group admin creates a bank whose mint is a Token-2022 mint configured to reject `transfer`/`transfer_checked` calls with `amount == 0` (or any mint enforcing non-zero transfer amounts).
2. Some interest/fees accrue and `lending_pool_collect_bank_fees` is called once, successfully collecting, e.g., the insurance fee but leaving `collected_group_fees_outstanding == 0` (or vice versa — any one of the three categories at 0 is sufficient).
3. Any subsequent call to `lending_pool_collect_bank_fees` computes `transfer_amount = 0` for that already-drained category and calls `bank.withdraw_spl_transfer(0, ...)`, which reverts inside the token program.
4. `lending_pool_collect_bank_fees` (and hence `lending_pool_withdraw_fees`/`lending_pool_withdraw_insurance`/`lending_pool_withdraw_fees_permissionless`, which depend on funds routed there) is now permanently unusable for that bank.

    #[allow(unused_variables)]
    fn withdraw_spl_transfer<'info>(
        &self,
        amount: u64,
        from: AccountInfo<'info>,
        to: AccountInfo<'info>,
        authority: AccountInfo<'info>,
        maybe_mint: Option<&InterfaceAccount<'info, Mint>>,
        program: AccountInfo<'info>,
        signer_seeds: &[&[&[u8]]],
        remaining_accounts: &[AccountInfo<'info>],
    ) -> MarginfiResult {
        debug!(
            "withdraw_spl_transfer: amount: {} from {} to {}, auth {}",
            amount, from.key, to.key, authority.key
        );

        #[cfg(feature = "client")]
        if let Some(mint) = maybe_mint {
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                Some(mint.to_account_info()),
                to,
                authority,
                Some(mint.decimals),
                remaining_accounts,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                None,
                to,
                authority,
                None,
                remaining_accounts,
                signer_seeds,
            )?;
        }

        #[cfg(not(feature = "client"))]
        if let Some(mint) = maybe_mint {
            spl_token_2022::onchain::invoke_transfer_checked(
                program.key,
                from,
                mint.to_account_info(),
                to,
                authority,
                remaining_accounts,
                amount,
                mint.decimals,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            #[allow(deprecated)]
            transfer(
                CpiContext::new_with_signer(
                    program.key(),
                    Transfer {
                        from,
                        to,
                        authority,
                    },
                    signer_seeds,
                ),
                amount,
            )?;
        }
