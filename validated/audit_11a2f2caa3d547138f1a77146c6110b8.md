### Title
Disk cache no longer verifies content digests on cache hits, allowing shared-disk-cache poisoning to silently corrupt build outputs - (File: CHANGELOG.md, disk cache client)

### Summary
The fee-on-transfer bug class is fundamentally about trusting a *declared* accounting value instead of verifying the *actual* observed value, letting an untrusted party's contribution diverge from what downstream logic assumes. The closest reachable analog in this Bazel snapshot is a documented, concrete behavior change: Bazel's disk cache no longer verifies the digest of a cache entry when serving a cache hit, even though `--remote_verify_downloads` historically covered both remote and disk caches.

### Finding Description
The changelog explicitly states the regression: [1](#0-0) 

This means: on a disk-cache hit, Bazel reads the blob/action-cache entry keyed by content-addressed digest but no longer recomputes/verifies that digest against the actual bytes read from disk before trusting and using them as the action's output content. The historical guarantee, as documented for `--remote_verify_downloads`, was that Bazel "will compute the hash sum of all remote downloads and discard the... cached values if they don't match the expected value" — and this flag was understood by users/docs to control verification for *both* remote and disk caches: [2](#0-1) 

This directly parallels the fee-on-transfer defect pattern: a value is nominally bound to an integrity check (the CAS digest, analogous to a "transfer amount"), but the code path that consumes it (serving a disk-cache hit) skips validating that the actual content matches the expected/declared value, and downstream logic (materializing the output into the build) proceeds as if the check had passed.

Disk caches (`--disk_cache`) are commonly shared across untrusted parties in CI fleets, shared build machines, or NFS-mounted caches used by multiple users/branches. If an unprivileged party who can write into that shared disk-cache directory (e.g., a hostile CI job running on a shared/untrusted branch build that populates the disk cache, or any writer with access to the cache path) places a blob under a digest key that does not match the actual content, a victim build that later gets a "disk cache hit" for that same digest will read back the *attacker-supplied* bytes as the trusted output — without any recomputation of the digest to catch the mismatch.

### Impact Explanation
This breaks the core CAS invariant that "content-addressed" cache entries are self-verifying (the key is supposed to be the hash of the value). Without digest verification on cache hit:
- A victim build can silently receive attacker-controlled/corrupted build outputs from a shared disk cache, without any error, warning, or checksum failure.
- Because action outputs materialized from the disk cache become inputs to further build steps (or final build artifacts), tampered/corrupted content can propagate through the dependency graph undetected — a class of cache poisoning that reaches "another build" per the disk cache being shared across invocations/users.
- This is more severe than a transient miss, because it defeats the exact mechanism (`--remote_verify_downloads` / CAS digest checking) that Bazel document and users rely on to prevent using corrupted/incorrect cache entries.

### Likelihood Explanation
Likelihood is directly tied to two facts: (1) disk caches are frequently configured as a shared directory across CI machines/users for build acceleration, and (2) the changelog confirms this is the *current, intended* (if arguably unintentional relative to the flag's documented scope) behavior in this Bazel snapshot — i.e., it is not a hypothetical, it is a real regression acknowledged in the release notes. Any unprivileged actor capable of writing (or corrupting, e.g. via race, partial write, bitrot, or a hostile process with write access) an entry into the shared disk-cache directory can trigger consumption of unverified content on a subsequent hit by any user of that shared cache.

### Recommendation
Restore digest verification on disk-cache hits (recompute the CAS digest of blobs/action-cache entries read from the disk cache and compare it against the expected digest before using the content), consistent with the documented behavior of `--remote_verify_downloads` for both remote and disk caches. If this trade-off was made deliberately for performance, gate it behind an explicit, off-by-default flag (not the default), and clearly re-scope `--remote_verify_downloads` documentation to reflect the actual verification boundary, so operators sharing disk caches across untrusted principals can opt back into strict verification.

3. Run a second `bazel build` with the same `--disk_cache=$CACHE` that should recompute the action and hit `D` in the disk cache.
