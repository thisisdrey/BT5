Audit Report

## Title
`claim_swap` deletes `PendingSwaps` entry even when the underlying transfer fails, permanently freezing the source's reserved funds - (File: substrate/frame/atomic-swap/src/lib.rs)

## Summary
`claim_swap` unconditionally removes the `PendingSwaps` storage entry after invoking `swap.action.claim(...)`, regardless of whether the underlying reserved-balance transfer actually succeeded. Because `BalanceSwapAction::claim` swallows the `DispatchResult` of `repatriate_reserved` into a discarded `bool`, a failed transfer still results in deletion of the only on-chain record that lets the source recover their reserved funds via `cancel_swap`.

## Finding Description
In `claim_swap`, the code computes `succeeded = swap.action.claim(&swap.source, &target)` and then, irrespective of `succeeded`, calls `PendingSwaps::<T>::remove(target.clone(), hashed_proof)` and returns `Ok(())`: [1](#0-0) 

`BalanceSwapAction::claim` discards the `DispatchResult` from `repatriate_reserved`, converting it into a `bool`: [2](#0-1) 

`repatriate_reserved`'s underlying implementation, `do_transfer_reserved`, is `BestEffort`, so it will not fail merely due to the source having less reserved balance than requested (it just moves less). However it does contain a hard failure path when the beneficiary (`target`) account does not yet exist in storage: `ensure!(!is_new, Error::<T, I>::DeadAccount)`: [3](#0-2) 

If `T::SwapAction`'s underlying `Currency`/`ReservableCurrency` implementation `C` is not the same currency used to pay transaction fees (e.g., a separate `pallet_balances` instance, an asset-wrapper `fungible` adapter, or any currency where the `target` account has no prior existence/balance), the `target` can trivially trigger `DeadAccount` simply by claiming with a still-unfunded account in currency `C`, since nothing requires the `target` to hold any balance in `C` before calling `claim_swap`. This makes `claim` return `false` while `claim_swap` still deletes the `PendingSwaps` entry and returns `Ok(())`.

The only other code path that releases a source's reserved balance is `cancel_swap`, which requires the `PendingSwaps` entry to still exist: [4](#0-3)  Once the entry has been removed by a failed `claim_swap`, `cancel_swap` permanently fails with `Error::NotExist`, and the pallet exposes no other extrinsic capable of unreserving the source's funds. The existing test suite only covers the successful two-party swap path and does not exercise or guard against a failing `claim`: [5](#0-4) 

## Impact Explanation
This is a permanent, unrecoverable freeze of the source's reserved balance, matching the "permanent user-fund ... lock" impact category. It is triggered purely through the unprivileged, public `claim_swap` extrinsic called by the `target`, requiring no governance, validator, or off-chain privilege.

## Likelihood Explanation
The likelihood is concrete rather than purely theoretical: any runtime configuration where `T::SwapAction`'s underlying currency `C` differs from the fee-paying currency (a legitimate and plausible configuration since `SwapAction` is a pluggable, generic trait parameter) allows an ordinary, unprivileged `target` to trigger `DeadAccount` in `do_transfer_reserved` simply by never having held a balance in `C`, which requires no special setup beyond normal account creation. Even under a single shared currency, non-adversarial reductions in the source's actual reserved balance between `create_swap` and `claim_swap` (e.g. via slashing) could similarly desynchronize pallet bookkeeping from actual custody, though the currently proven failure mode is the `DeadAccount` path.

## Recommendation
Change `SwapAction::claim` to return `DispatchResult` instead of a discarded `bool`, and have `claim_swap` only remove the `PendingSwaps` entry (and emit `SwapClaimed { success: true, .. }`) when the claim genuinely succeeds. On failure, either leave the entry intact so `cancel_swap` remains usable after `end_block`, or propagate the error via `?` so the whole extrinsic reverts and the caller can retry.

## Proof of Concept
1. `source` calls `create_swap(target, hashed_proof, BalanceSwapAction::<AccountId, C>::new(value), duration)`, reserving `value` of currency `C` from `source`.
2. `target` (an account with no prior balance in currency `C`, but sufficient balance in the fee-paying currency to sign transactions) calls `claim_swap(proof, action)` with the correct proof and matching action.
3. Inside `swap.action.claim`, `C::repatriate_reserved(source, target, value, BalanceStatus::Free)` invokes `do_transfer_reserved`, which hits `ensure!(!is_new, Error::<T, I>::DeadAccount)` for `target` and returns `Err`, so `claim` returns `false`.
4. `claim_swap` nonetheless executes `PendingSwaps::<T>::remove(target, hashed_proof)` and returns `Ok(())`, emitting `SwapClaimed { success: false }`.
5. `source` later calls `cancel_swap(target, hashed_proof)`; it fails with `Error::NotExist` because the entry no longer exists, and the reserved `value` in currency `C` can never be reclaimed through this pallet.

#[test]
fn two_party_successful_swap() {
	let mut chain1 = new_test_ext();
	let mut chain2 = new_test_ext();

	// A generates a random proof. Keep it secret.
	let proof: [u8; 2] = [4, 2];
	// The hashed proof is the blake2_256 hash of the proof. This is public.
	let hashed_proof = blake2_256(&proof);

	// A creates the swap on chain1.
	chain1.execute_with(|| {
		AtomicSwap::create_swap(
			RuntimeOrigin::signed(A),
			B,
			hashed_proof,
			BalanceSwapAction::new(50),
			1000,
		)
		.unwrap();

		assert_eq!(Balances::free_balance(A), 100 - 50);
		assert_eq!(Balances::free_balance(B), 200);
	});

	// B creates the swap on chain2.
	chain2.execute_with(|| {
		AtomicSwap::create_swap(
			RuntimeOrigin::signed(B),
			A,
			hashed_proof,
			BalanceSwapAction::new(75),
			1000,
		)
		.unwrap();

		assert_eq!(Balances::free_balance(A), 100);
		assert_eq!(Balances::free_balance(B), 200 - 75);
	});

	// A reveals the proof and claims the swap on chain2.
	chain2.execute_with(|| {
		AtomicSwap::claim_swap(
			RuntimeOrigin::signed(A),
			proof.to_vec(),
			BalanceSwapAction::new(75),
		)
		.unwrap();

		assert_eq!(Balances::free_balance(A), 100 + 75);
		assert_eq!(Balances::free_balance(B), 200 - 75);
	});

	// B use the revealed proof to claim the swap on chain1.
	chain1.execute_with(|| {
		AtomicSwap::claim_swap(
			RuntimeOrigin::signed(B),
			proof.to_vec(),
			BalanceSwapAction::new(50),
		)
		.unwrap();

		assert_eq!(Balances::free_balance(A), 100 - 50);
		assert_eq!(Balances::free_balance(B), 200 + 50);
	});
}
