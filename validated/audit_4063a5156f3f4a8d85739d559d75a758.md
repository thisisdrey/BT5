### Title
Unsolicited StackerDB chunk pushes cause the node to advertise (and sign) an inventory claiming a chunk version is stored before it is actually durably committed - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an incoming `StackerDBPushChunkData` message, immediately patches its outgoing `StackerDBChunkInv` reply to claim the pushed slot's version is now held, signs and sends that inventory back to the peer, and only *afterwards* hands the chunk off to the relayer for actual persistence. This breaks the invariant that a signed `StackerDBChunkInv` reply reflects the node's true, committed StackerDB state (served vs. committed mismatch), because the actual write (`StackerDBTx::try_replace_chunk`) happens later, asynchronously, and can still fail (e.g. `StaleChunk`, DB error) after the optimistic inventory has already been dispatched.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`: [1](#0-0) 

The function validates the chunk with `validate_received_chunk` (signature, freshness, size — but *not* actual storage) and then patches `data.slot_versions[slot_id] = chunk_data.chunk_data.slot_version` on the reply payload that is about to be sent back to the peer.

It then signs and transmits this patched inventory immediately: [2](#0-1) 

Crucially, the chunk itself is never written to the StackerDB in this function — it is only forwarded to the relayer (`return Ok((false, true))`), which performs the actual write later, in a separate pass, via `process_stacker_db_chunks`: [3](#0-2) 

That later write calls `try_replace_chunk`, which can still reject the chunk (e.g. as `StaleChunk` if a different, newer version for the same slot commits first) and simply logs and `continue`s, silently dropping the chunk with no correction sent to the peer that already received the "accepted" inventory: [4](#0-3) 

Because `handle_unsolicited_StackerDBPushChunk` explicitly documents that it does not check write frequency or wait for storage ("Note that this can happen *during* a StackerDB sync's execution... The write frequency is not checked for this chunk"), the design intentionally defers persistence, but the peer-facing inventory acknowledgment is not deferred to match: [5](#0-4) .

### Impact Explanation
This lets a remote, unauthenticated (from the node's perspective — any connected P2P neighbor) actor cause the node to broadcast a signed, false `StackerDBChunkInv` claiming possession of chunk data it does not actually hold, by racing two chunk pushes for the same slot (or by exploiting normal concurrent write races) so that the loser is dropped in `try_replace_chunk` after its inventory ack was already sent. Downstream StackerDB sync peers make scheduling decisions (rarest-first, newest-first) based on these inventories; a false inventory steers replication decisions away from nodes that actually hold fresher/complete data ("steering a node off the tip via false inventory" analog), degrading StackerDB replication reliability and potentially causing legitimate chunk data to be under-replicated or lost network-wide if senders trust the ack and stop re-broadcasting.

### Likelihood Explanation
Triggering the race only requires sending ordinary, validly-signed `StackerDBPushChunkData` messages for the same slot in quick succession or racing a slot update concurrently with StackerDB sync's own writes — no special privileges, secret keys, or admin roles are needed beyond having a chunk signed by the actual slot owner (which is normal, expected traffic in the P2P chunk-push protocol; only a single crafted timing/interleaving of otherwise-legitimate pushes is required to expose the served-vs-committed gap).

### Recommendation
Defer generating and sending the `StackerDBChunkInv` reply for a pushed chunk until after the chunk has actually been durably written (or forward the ack only once `process_stacker_db_chunks`/`try_replace_chunk` confirms success), or explicitly re-check/re-send a corrected inventory if the deferred write fails.

### Proof of Concept
1. Establish a P2P connection as a neighbor of a target node replicating a StackerDB.
2. Obtain (or produce, if you are the legitimate slot owner) a validly signed `StackerDBChunkData` for slot `S`, version `V` and another with version `V+1` for the same slot.
3. Send the push for version `V+1` as an unsolicited `StackerDBPushChunk`; the target validates it via `validate_received_chunk`, patches its outbound `StackerDBChunkInv` to advertise version `V+1` as stored, signs, and sends the inventory back — before the chunk is written.
4. Immediately race a second write for the same slot (e.g., via a genuine sync round or another concurrent push already in flight) that commits first through `try_replace_chunk`, causing the deferred write of version `V+1` to fail with `StaleChunk` in `process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2412-2434`), which silently drops it.
5. The target node has already told its peer (step 3) that it holds version `V+1`, but its actual StackerDB slot never reflects that version — demonstrating the served/committed mismatch.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));

        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
