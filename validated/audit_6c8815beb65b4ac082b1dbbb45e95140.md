### Title
Missing minimum-amount-out enforcement when withdrawing underlying from external `VPool` via `VesperGateway.withdraw` - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.withdraw` redeems the user's vault shares (`msdTokens`) for `vTokens`, then calls the external Vesper `VPool.withdraw(_vTokenAmount)` and forwards to the user whatever amount of `underlying` comes back. The function takes no `minAmountOut` parameter and performs no post-check on the actual amount received, so the user has no on-chain slippage protection on the withdrawal leg executed inside an external contract. This is the same bug class as the Olympus `SingleSidedLiquidityVault` finding: the vault (here, the gateway) relies entirely on the external protocol to return a "fair" amount.

### Finding Description
The withdrawal flow in `VesperGateway.sol`:

```solidity
// contracts/VesperGateway.sol L73-93
function withdraw(IPool pool_, IVPool vToken_, uint256 amount_) external override nonReentrant {
    if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();
    address _msgSender = _msgSender();
    IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
    _depositToken.safeTransferFrom(_msgSender, address(this), amount_);
    (uint256 _vTokenAmount, ) = _depositToken.withdraw(amount_, address(this));
    IERC20 _underlying = IERC20(vToken_.token());
    uint256 _balanceBefore = _underlying.balanceOf(address(this));
    vToken_.withdraw(_vTokenAmount);                       // no minOut, no check
    uint256 _underlyingAmount = _underlying.balanceOf(address(this)) - _balanceBefore;
    _underlying.safeTransfer(_msgSender, _underlyingAmount);
}
```

- `amount_` is denominated in `msdTokens`, not in `underlying`, so the user cannot express "I want at least X underlying".
- `vToken_.withdraw(_vTokenAmount)` converts shares to underlying at the `VPool`'s current `pricePerShare` (`totalValue / totalSupply`). Nothing in the gateway bounds the acceptable `pricePerShare` at execution time.
- The `deposit` side has the identical gap: `vToken_.deposit(amount_)` mints however many `vTokens` the pool decides (L57-58), and those are immediately locked as Synth collateral — again with no minimum-shares check.
- `DepositToken.withdraw` itself charges a `withdrawFee` and is oracle-independent, but that fee is predictable; the uncontrolled variable is the external `VPool` conversion, which is exactly the layer the report says the vault should not trust.

Attack path (unprivileged, same-transaction): Vesper `VPool.pricePerShare` is derived from `totalValue()`, which aggregates the pool's `token()` balance plus strategy-reported positions. An attacker can flash-loan a large `underlying` position, deposit and withdraw from the same `VPool` (or trigger strategy rebalances/fee events) so that `totalValue` — or the pool's liquid balance backing the victim's redemption — moves against the victim between mempool observation and execution. The victim's `withdraw` then burns their `msdTokens` (paying the withdraw fee) but receives materially less `underlying` than the `pricePerShare` they saw, with no way to specify a floor. Sandwiching a `deposit` call is symmetric: inflate `pricePerShare` right before the victim deposits so they mint fewer `vTokens` (and hence fewer `msdTokens` of collateral) than expected.

Note the `nonReentrant` guard and `isPoolRegistered` check do not help: the manipulation happens inside the external `VPool`/its strategies, not via reentry into the gateway, and the pool is legitimately registered.

### Impact Explanation
Direct loss of user funds: the user irrevocably burns `msdTokens` (and pays `DepositToken`'s withdraw fee) while the amount of `underlying` returned by `VPool.withdraw` is unbounded below — it can be arbitrarily small if the external pool's share price or liquidity moved adversely. Because `msdTokens` represent collateral positions, the loss is real even though it occurs inside a third-party contract. This matches the report's medium severity: loss depends on market conditions / front-running, not on a guaranteed steal.

### Likelihood Explanation
Medium-low. It requires the targeted `VPool`'s effective conversion rate to be movable within a transaction (large share of pool liquidity, strategy withdrawal fees/losses, or oracle-updated `totalValue`), and a victim using `VesperGateway.withdraw`/`deposit` rather than transacting with `DepositToken` directly. No privileged role is needed by the attacker — only the ability to trade in the external pool, which is permissionless.

### Recommendation
Add a `minUnderlyingOut_` parameter to `VesperGateway.withdraw` and a `minSharesOut_` (or equivalent) parameter to `VesperGateway.deposit`, and revert if the measured balance deltas fall below them:

```solidity
// withdraw
if (_underlyingAmount < minUnderlyingOut_) revert SlippageTooHigh();
// deposit
if (_vTokenAmount < minSharesOut_) revert SlippageTooHigh();
```

Do not rely on the external `VPool` to perform slippage checks on the user's behalf — enforce the bound in the gateway itself.

### Proof of Concept
Foundry fork test (mainnet, real `VPool` such as `vUSDC`):

```solidity
function test_vesperGatewayWithdraw_noMinOut() public {
    // victim holds msdTokens for a vToken collateral
    uint256 msdAmount = depositToken.balanceOf(victim);
    uint256 ppsBefore = vPool.pricePerShare();

    // attacker front-runs: flash-loan underlying, deposit+withdraw huge
    // amount in vPool, forcing strategy withdraw fee / lower totalValue
    attackerManipulateVPool(); // drops effective conversion

    vm.prank(victim);
    depositToken.approve(address(vesperGateway), msdAmount);
    vm.prank(victim);
    vesperGateway.withdraw(pool, vPool, msdAmount); // succeeds, no minOut arg exists

    uint256 received = underlying.balanceOf(victim);
    uint256 expected = (msdValue * ppsBefore) / 1e18;
    assertLt(received, expected); // victim burned collateral, got less than quoted
}
```

The key observation the test demonstrates: `IVesperGateway.withdraw(IPool, IVPool, uint256)` has no parameter to express a minimum acceptable `underlying` amount, and the gateway performs no `>= minOut` assertion on `_underlyingAmount` — the user cannot protect themselves even if they wanted to.
