### Title
Hardcoded, un-updatable `ADDRESS_REGISTRAR_ACCOUNT_ID` in the shared ETH Wallet Contract permanently breaks base-token transfers if misconfigured - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract used by every ETH-implicit account bakes the Address Registrar's account ID into the compiled WASM at build time via `include_str!`, with no runtime validation or update mechanism, closely mirroring the reported pattern of an unvalidated, immutable address parameter breaking core functionality (`deposit`/transfer flows) if wrongly assigned.

### Finding Description
The wallet contract constant is compiled in at build time: [1](#0-0) 

and used, unchecked at construction time, whenever a base-token transfer to another (potentially unregistered) ETH-implicit address requires a registrar lookup: [2](#0-1) 

If the baked-in value is not a valid, parseable `AccountId` (e.g. wrong/empty content in the `ADDRESS_REGISTRAR_ACCOUNT_ID` source file used at compile time, analogous to a zero/garbage address being wired into a constructor), `.parse()` fails and the contract calls `env::panic_str("Invalid address registrar")`, aborting that receipt every single time this code path is hit: [3](#0-2) 

This is structurally identical to the reported bug class: an address that should be validated at "construction" time (here, contract build/deployment time) is instead accepted unchecked, and a downstream "deposit"-equivalent operation (an `EOABaseTokenTransfer` funds transfer) unconditionally depends on it being correct. Unlike an ordinary per-account contract, the ETH Wallet Contract is deployed once as a **Global Contract** referenced by hash and shared by *all* ETH-implicit accounts under the `EthImplicitGlobalContract` protocol feature: [4](#0-3) 

so a bad `ADDRESS_REGISTRAR_ACCOUNT_ID` value would be baked into the one canonical wallet contract hash that the entire network relies on, and cannot be patched without a protocol-level upgrade to the referenced global contract hash.

### Impact Explanation
Any `rlp_execute` call whose decoded Ethereum transaction is classified as `EthEmulationKind::EOABaseTokenTransfer` with `address_check: Some(_)` (i.e., a plain value transfer to another address that is not already known to be a named/registered account) will panic and abort instead of completing the transfer. Since the panic happens before the nonce increment for this branch, every retry of this transaction type will fail identically. This constitutes a permanent freezing of base-token transfer functionality for every ETH-implicit account using this global contract — funds cannot be moved out via this call pattern until governance ships a corrected global contract under a new hash, which is out of scope for the ordinary user. This matches "permanent freezing of funds" for the affected transaction class.

### Likelihood Explanation
Likelihood depends entirely on whether the value baked into `ADDRESS_REGISTRAR_ACCOUNT_ID` at the time the canonical global wallet contract WASM is built/hashed is a syntactically valid, deployed `AccountId`. There is no unit test, protocol-level assertion, or on-chain check that the compiled value is a valid or even-existing account before the resulting hash is adopted as `eth_wallet_global_contract_hash`; the only safeguard is developer/reviewer diligence at build time (the test harness swaps this file in and back out, showing it is treated as a build-time configuration knob rather than a validated on-chain parameter): [5](#0-4) 

### Recommendation
- Validate `ADDRESS_REGISTRAR_ACCOUNT_ID` at build time (e.g., via a `const`-eval or build-script assertion that it parses as a valid `AccountId`) so a bad value cannot make it into a shipped contract hash.
- Consider making the registrar account configurable/upgradable (e.g., stored in contract state and settable through a governed migration action) rather than compiled permanently into a globally-shared, hash-addressed contract, so a misconfiguration does not require a full protocol-level redeploy to fix.
- Add a defensive fallback path (e.g., skip the registrar check and treat the target as unregistered, or return a structured `ExecuteResponse` error instead of `panic_str`) so a bad configuration degrades gracefully rather than deterministically aborting every affected transfer.

### Proof of Concept
1. Assume the `ADDRESS_REGISTRAR_ACCOUNT_ID` file baked into the wallet contract source at compile time contains an invalid or empty string (this is the "wrong address" analog to the `_weth` constructor parameter in the report).
2. This value is compiled into the WASM and the resulting hash is registered as `eth_wallet_global_contract_hash` for all ETH-implicit accounts, per `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:247-261`).
3. A user's ETH-implicit account, via a relayer, submits `rlp_execute` with a base-token transfer (`EOABaseTokenTransfer`) whose `address_check` is `Some(address)` because the target is another not-yet-registered eth-implicit address.
4. `inner_rlp_execute` reaches the branch at `lib.rs:412-424`, attempts `ADDRESS_REGISTRAR_ACCOUNT_ID.trim().parse()`, which fails, and the contract calls `env::panic_str("Invalid address registrar")`.
5. The receipt aborts; because parsing succeeded prior to this branch, the nonce was intentionally *not* incremented (per the comment at `lib.rs:350-365`), so every retry of this same transaction type deterministically re-triggers the same panic — the base-token transfer path is permanently unusable for that class of transactions until the shared global contract itself is redeployed under a new, corrected hash.
