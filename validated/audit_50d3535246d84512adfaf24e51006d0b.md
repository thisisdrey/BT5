### Title
Committee feature-gate for CancelAllUnfreezeV2 / WithdrawExpireUnfreeze / UnDelegateResource is not enforced on the TVM native-contract path - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java)

### Summary
Several stake/unfreeze features are gated behind committee-controlled chain parameters that are checked in the transaction-level `Actuator.validate()` implementations but are silently skipped in the equivalent TVM "native contract" processors that back the Solidity-level precompiled opcodes (`cancelAllUnfreezeBalanceV2()`, `withdrawExpireUnfreeze()`, and `unDelegateResource()`). A smart contract can invoke these opcodes directly, bypassing the committee gate entirely, exactly analogous to the Shopware issue where the `CancelOrderRoute` actuator omitted a check that existed in the UI/controller layer.

### Finding Description
For `CancelAllUnfreezeV2`:
- The externally-facing actuator explicitly rejects the operation unless the committee has enabled it: `if (!dynamicStore.supportAllowCancelAllUnfreezeV2()) { throw new ContractValidateException("Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee"); }` [3](#0-2) .
- The TVM native-contract counterpart, `CancelAllUnfreezeV2Processor.validate()`, performs only address/account existence checks and an invalid-delegated-balance CPU-time check — it never calls `supportAllowCancelAllUnfreezeV2()` [2](#0-1) .
- This processor is invoked directly from `Program.cancelAllUnfreezeV2Action()`, which is the implementation backing the Solidity-callable `cancelAllUnfreezeBalanceV2()` opcode, with no extra gating added at the call site [4](#0-3) .

For `WithdrawExpireUnfreeze`:
- The actuator checks `supportUnfreezeDelay()` before allowing withdrawal [5](#0-4) .
- `WithdrawExpireUnfreezeProcessor.validate()` (used by `Program.withdrawExpireUnfreeze()`) has no equivalent check [6](#0-5) [1](#0-0) .

For `UnDelegateResource`:
- The actuator requires both `supportDR()` and `supportUnfreezeDelay()` [7](#0-6) .
- `UnDelegateResourceProcessor.validate()` checks only `supportDR()`, omitting the `supportUnfreezeDelay()` check [8](#0-7) .

In all three cases the root cause is the same class of bug as the Shopware advisory: a feature flag meant to gate a user-facing action is checked in one code path (the transaction Actuator) but omitted in an equally-reachable alternate code path (the TVM native-contract processor invoked from Solidity contract bytecode).

### Impact Explanation
If the committee has not yet enacted `ALLOW_CANCEL_ALL_UNFREEZE_V2` or `UNFREEZE_DELAY` (i.e., these features are meant to be disabled network-wide), any deployed contract can still invoke `cancelAllUnfreezeBalanceV2()`, `withdrawExpireUnfreeze()`, or `unDelegateResource()` through TVM and have the state changes (balance/resource weight/frozen list mutations) applied, because the processor path performs the mutations regardless of the flag. This bypasses network governance intended to sequence hard-fork feature rollout, and can alter stake/resource/reward accounting in ways the rest of the protocol (bandwidth/energy processors, total weight bookkeeping tied to the fork) is not yet prepared to handle, potentially leading to inconsistent resource accounting or unintended balance changes ahead of the feature's activation.

### Likelihood Explanation
High for any period during which these flags are disabled on-chain: exploitation only requires deploying a trivial contract that calls the corresponding opcode wrapper function (as already exercised in `FreezeV2Test`'s `triggerCancelAllUnfreezeV2`/`triggerWithdrawExpireUnfreeze` test helpers) [9](#0-8) . No special privileges are needed beyond ordinary contract deployment and invocation.

### Recommendation
Add the same committee-flag checks (`supportAllowCancelAllUnfreezeV2()`, `supportUnfreezeDelay()`) at the start of `CancelAllUnfreezeV2Processor.validate()`, `WithdrawExpireUnfreezeProcessor.validate()`, and `UnDelegateResourceProcessor.validate()` that already exist in the corresponding Actuators, so the TVM-reachable code path enforces identical governance gating as the transaction-level path.

### Proof of Concept
1. On a network/fork state where `ALLOW_CANCEL_ALL_UNFREEZE_V2` is not yet enabled (`dynamicStore.getAllowCancelAllUnfreezeV2() == 0`), attempting `CancelAllUnfreezeV2Actuator.validate()` via a normal transaction fails with "Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee" [3](#0-2) .
2. Deploy a contract exposing a function that calls the `cancelAllUnfreezeBalanceV2()` TVM opcode (as done by `FreezeV2Test.triggerCancelAllUnfreezeV2`) [10](#0-9) .
3. Invoke that contract function while the flag is still disabled; `Program.cancelAllUnfreezeV2Action()` → `CancelAllUnfreezeV2Processor.validate()`/`execute()` proceed successfully, cancelling the unfreeze and mutating account/resource state, despite the feature being disabled at the network level [4](#0-3) [2](#0-1) .
