Audit Report

## Title
`process_delivery_receipt` ignores the on-chain `success` flag and always pays the relayer reward and clears the pending order - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
The `DeliveryReceipt` decoded from Ethereum's `InboundMessageDispatched` event contains a `success: bool` field, but `Pallet::process_delivery_receipt` never reads or branches on it. A relayer holding a valid inclusion proof for a log where `success = false` can still trigger unconditional reward payment and permanent removal of the `PendingOrders` entry for that nonce.

## Finding Description
The event is decoded faithfully, including the `success` field, in `DeliveryReceipt::try_from` at [2](#0-1) . The public extrinsic `submit_delivery_receipt` verifies only the log's authenticity/inclusion via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt` at [3](#0-2) . Inside `process_delivery_receipt`, only the gateway address and the existence of a `PendingOrder` for the nonce are checked before paying `order.fee` to the reward account and unconditionally calling `<PendingOrders<T>>::remove(nonce)`, as shown at [4](#0-3) . `receipt.success` is never read anywhere in this function or elsewhere in the pallet — a repository-wide search confirms the field is only referenced once, at its decode site in `delivery_receipt.rs`. The `Verifier::verify` call only attests that the log is authentic and included in a finalized Ethereum block; it has no knowledge of, and does not gate on, the semantic `success` value inside that log.

## Impact Explanation
This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Concretely, the exact corrupted values are: (1) the relayer reward payout via `T::RewardPayment::register_reward` at [5](#0-4) , which is paid even when the receipt states the delivery failed, and (2) the `PendingOrders` map entry, which is deleted via `<PendingOrders<T>>::remove(nonce)` at line 475 regardless of `success`, permanently losing the bookkeeping for that nonce with no retry/failure path. This is an unbacked/incorrect payout (theft of protocol funds relative to actual delivery outcome) and a permanent settlement-state loss for the corresponding bridge message nonce.

## Likelihood Explanation
`submit_delivery_receipt` is a public, unprivileged, signed extrinsic reachable by any account holding a valid Ethereum log inclusion proof, as seen in the `#[pallet::call]` block at [3](#0-2) . `success = false` is a legitimate value the Ethereum Gateway can emit whenever the dispatched inbound command reverts (e.g., insufficient relayer-supplied gas, a reverting downstream call) — this is a normal, reachable condition, not a contrived edge case, and requires no malicious validator, prover, or privileged access.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: if `true`, keep current behavior (pay reward, remove order); if `false`, skip/reduce the reward payment and either retain the order for retry or transition it to an explicit failure state/event (e.g., `Event::MessageDeliveryFailed { nonce }`) rather than emitting `Event::MessageDelivered` and silently finalizing the bookkeeping.

## Proof of Concept
1. `do_process_message` creates a `PendingOrder { nonce, fee, .. }` for an outbound message per [6](#0-5) .
2. The message is relayed to Ethereum's Gateway, and dispatch of the underlying command reverts there, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any relayer obtains a valid inclusion proof for this genuine, finalized log and calls `submit_delivery_receipt(event)`.
4. `T::Verifier::verify` succeeds (log is authentic); `DeliveryReceipt::try_from` decodes `success = false` correctly.
5. `process_delivery_receipt` passes the gateway check, finds the `PendingOrder`, and — because it never checks `receipt.success` — pays `order.fee` to the reward account and removes the order, emitting `Event::MessageDelivered { nonce }` as if delivery had succeeded.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
