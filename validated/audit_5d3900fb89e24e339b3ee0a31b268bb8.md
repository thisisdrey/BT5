### Title
DoS via unbounded `TotalEnergyWeight`/frozen-balance growth causing `ArithmeticException` in hardened energy/bandwidth limit calculation - (File: `chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java`, `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`)

### Summary
The reported DODO GSP bug class is: a fee/state accumulator that grows monotonically from ordinary user transactions, with no cap, and is only ever reduced by an out-of-band privileged action — eventually causing arithmetic failures that DoS core contract functions. The closest reachable analog in java-tron is the `TotalEnergyWeight` / `TotalNetWeight` global counters (and per-account frozen balances that feed them), which grow purely from ordinary `FreezeBalanceV2Actuator`/`DelegateResourceActuator` calls issued by any account, are only reduced by later `UnfreezeBalanceV2Actuator`/`UnDelegateResourceActuator` calls, and are consumed in energy/bandwidth-limit math that — under the "hardened" `longValueExact()` code path — throws `ArithmeticException` on overflow instead of failing gracefully.

### Finding Description
`calculateGlobalLimitV1` in `ResourceProcessor.java` computes a per-account energy/bandwidth limit as: [1](#0-0) 
using `BigInteger... .longValueExact()`, which throws `ArithmeticException` if the intermediate product does not fit back into a `long`. The same hardened pattern is used in `RepositoryImpl.calculateGlobalEnergyLimit`: [2](#0-1) 
and in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2`: [3](#0-2) 

`totalEnergyWeight`/`totalNetWeight` are global accumulators stored in `DynamicPropertiesStore` (`TOTAL_ENERGY_WEIGHT`, `TOTAL_NET_WEIGHT`) that increase whenever any account calls `FreezeBalanceV2Actuator`/`DelegateResourceActuator`, and decrease only when the same or another account explicitly calls `UnfreezeBalanceV2Actuator`/`UnDelegateResourceActuator` — a direct structural parallel to `_MT_FEE_QUOTE_`/`_MT_FEE_BASE_`, which grow on every `sellQuote`/`sellBase`/`flashLoan` call and shrink only via the maintainer's explicit `withdrawMtFeeTotal()`. There is no upper bound enforced on `totalEnergyWeight`/`totalNetWeight` themselves, only unit tests demonstrate that specific combinations of `frozeBalance`/`totalEnergyLimit`/`totalEnergyWeight` reliably trigger the overflow revert: [4](#0-3) [5](#0-4) 

This calculation is invoked from `DelegateResourceActuator.doValidate()`—reachable by any signed `DelegateResourceContract` transaction: [6](#0-5) 
and from `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` used in the TVM native contract execute path: [7](#0-6) 
and from `Wallet.calcCanDelegatedEnergyMaxSize`/`calcCanDelegatedBandWidthMaxSize`, which back the gRPC/HTTP query APIs used by any client: [8](#0-7) 

### Impact Explanation
If an attacker (or organic network growth) drives `TotalEnergyWeight`/`TotalNetWeight` and/or an account's frozen balance high enough that `frozeBalance * totalEnergyLimit` (or the analogous bandwidth product) exceeds `Long.MAX_VALUE` when the hardened calculation path is active, `longValueExact()` throws an uncaught `ArithmeticException`. Since `calculateGlobalEnergyLimit`/`calculateGlobalNetLimit` are invoked unconditionally during resource-delegation validation (`DelegateResourceActuator`, `UnDelegateResourceActuator`), TVM resource accounting, and read-only Wallet/API query paths, this can turn into: (a) validation of otherwise-legitimate `DelegateResourceContract`/`UnDelegateResourceContract` transactions throwing unhandled exceptions instead of clean `ContractValidateException`s, and (b) query APIs such as `calcCanDelegatedEnergyMaxSize`/`calcCanDelegatedBandWidthMaxSize` (surfaced through Wallet/gRPC) becoming permanently unable to serve requests for the affected account — a node-level API DoS with no privileged remediation available (unlike the DODO case, there is no "withdraw" call an ordinary actor can invoke to shrink `TotalEnergyWeight`; it can only decrease as other participants unfreeze).

### Likelihood Explanation
Reaching the overflow requires very large `frozeBalance`/`totalEnergyWeight` values that are unlikely under today's TRX total supply constraints (~10^17 sun scale keeps products well below `Long.MAX_VALUE` in most realistic configurations), and the vulnerable `longValueExact()` path is gated behind the `allowHardenResourceCalculation`/`supportUnfreezeDelay` feature flags, which must be enabled by chain governance. This substantially reduces practical likelihood relative to the DODO analog, where fee accumulation was unconditionally active. Still, the finding is a genuine structural analog of the reported bug class — an unbounded, community-driven accumulator that is never proactively capped and can only shrink via separate voluntary actions, feeding an arithmetic operation that reverts hard rather than degrading gracefully.

### Recommendation
Bound or periodically decay `TotalEnergyWeight`/`TotalNetWeight` growth relative to supply, and replace the `longValueExact()` hard-revert with saturating/clamped arithmetic (or a graceful `ContractValidateException`) in `calculateGlobalLimitV1`/`calculateGlobalLimitV2`/`calculateGlobalEnergyLimit`, so overflow conditions degrade rather than crash validation and query paths.

### Proof of Concept
Existing repo unit tests already demonstrate the crash condition directly: [4](#0-3) 
With `totalEnergyCurrentLimit = Long.MAX_VALUE/2`, `totalEnergyWeight = 1`, and `frozeBalance = Long.MAX_VALUE/4`, `calculateGlobalEnergyLimit` throws `ArithmeticException`. An attacker who can influence total frozen energy weight to a very small value relative to an account's frozen balance (e.g., via a chain restart, migration, or extreme freeze/unfreeze sequencing under `allowHardenResourceCalculation`) could reproduce this condition in `DelegateResourceActuator.doValidate()` for any subsequent `DelegateResourceContract` transaction touching that account, causing repeated transaction failures / API errors rather than clean rejects.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  public long calcCanDelegatedEnergyMaxSize(ByteString ownerAddress) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    AccountCapsule ownerCapsule = accountStore.get(ownerAddress.toByteArray());
    if (ownerCapsule == null) {
      return 0L;
    }

    EnergyProcessor processor = new EnergyProcessor(dynamicStore, accountStore);
    processor.updateUsage(ownerCapsule);

    long energyUsage = (long) (ownerCapsule.getEnergyUsage() * TRX_PRECISION * ((double)
            (dynamicStore.getTotalEnergyWeight()) / dynamicStore.getTotalEnergyCurrentLimit()));

    long v2EnergyUsage = getV2EnergyUsage(ownerCapsule, energyUsage,
        dynamicStore.disableJavaLangMath());

    long maxSize =  ownerCapsule.getFrozenV2BalanceForEnergy() - v2EnergyUsage;
    return max(0, maxSize, dynamicStore.disableJavaLangMath());
  }
