## Title
Unbounded `query` field in `SearchFilesByContent` enables regex/argument-length DoS via `git grep --perl-regexp` - (File: internal/gitaly/service/repository/search_files.go)

### Summary
`SearchFilesByContent` passes the client-supplied `query` string directly into `git grep --perl-regexp` without any length or complexity restriction, unlike its sibling RPC `SearchFilesByName`, which explicitly caps the equivalent `filter` field at 1000 bytes to "thwart excessive resource usage." [1](#0-0)  The `query` used by `SearchFilesByContent` has no such cap.

### Finding Description
`SearchFilesByContent` builds a `git grep` invocation using `req.GetQuery()` as the `-e` value for `--perl-regexp` matching, with only a generic non-empty check performed by `validateSearchFilesRequest`: [2](#0-1) [3](#0-2) 

Compare this to `SearchFilesByName`, where the analogous regex field (`filter`) is explicitly bounded: [4](#0-3) 

The proto documentation for `SearchFilesByName.filter` even states "It has a maximum length of 1000 bytes," confirming that the Gitaly maintainers previously recognized this exact class of risk for this sibling field, but the analogous protection was never added to `SearchFilesByContentRequest.query`: [5](#0-4) 

This is structurally the same bug class as the Hats `uri`/`details`/`imageURI` issue: an unbounded, attacker-controlled string is fed into an expensive per-request operation (there, JSON string concatenation costing gas; here, Perl-compatible regex compilation/execution via `git grep --perl-regexp`, which is vulnerable to catastrophic backtracking and large-argument overhead) with no cap enforced at the point where the value is accepted from an ordinary, unprivileged caller.

### Impact Explanation
An ordinary/unprivileged gRPC client with access to `SearchFilesByContent` (an `ACCESSOR` RPC, reachable by any client authorized to query a given repository, e.g. via GitLab's code search feature) can submit an arbitrarily large or pathologically crafted PCRE pattern as `query`. This can cause the spawned `git grep` process to consume excessive CPU/memory (regex backtracking blowup) or excessive argument/process overhead, degrading or exhausting Gitaly's shared resources (process table, CPU, goroutines) and denying service to other RPCs/tenants on the same Gitaly node — consistent with the "RPC-handler resource limits" DoS category.

### Likelihood Explanation
High likelihood: the RPC is reachable directly from a single unprivileged request (no need for prior write access, no multi-step setup as required in the original Hats report), the `query` field is fully attacker-controlled, and no length/validation guard exists at all in `validateSearchFilesRequest` or `SearchFilesByContent` for this field, whereas the sibling code path explicitly demonstrates the maintainers consider unbounded regex length a resource-usage risk.

### Recommendation
Add a maximum-length check (and/or regex compile timeout/complexity guard) for `req.GetQuery()` in `SearchFilesByContent`, mirroring the `searchFilesFilterMaxLength` check already used in `SearchFilesByName`, e.g. reject queries longer than a fixed threshold (such as 1000 bytes) with `structerr.NewInvalidArgument`.

### Proof of Concept
1. As an ordinary authorized client, call `SearchFilesByContent` with `Repository` set to a valid repo, `Ref` set to a valid branch, and `Query` set to a very large or catastrophically-backtracking PCRE pattern (e.g. a long string of nested quantifiers like `(a+)+$` repeated/padded to tens of thousands of characters).
2. Observe that `validateSearchFilesRequest` performs no length check on `Query` and the request proceeds to spawn `git grep --perl-regexp -e <query>`. [6](#0-5) 
3. The spawned `git grep` process consumes excessive CPU while attempting to match the pathological regex against repository content, tying up Gitaly worker/process resources for the duration, unlike the equivalent `SearchFilesByName` call which would be rejected immediately once `filter` exceeds 1000 bytes. [7](#0-6)

func (s *server) SearchFilesByContent(req *gitalypb.SearchFilesByContentRequest, stream gitalypb.RepositoryService_SearchFilesByContentServer) error {

	if err := validateSearchFilesRequest(ctx, s.locator, req); err != nil {

func validateSearchFilesRequest(ctx context.Context, locator storage.Locator, req searchFilesRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetQuery()) == 0 {
		return errors.New("no query given")
	}

	if len(req.GetRef()) == 0 {
		return errors.New("no ref given")
	}

	if bytes.HasPrefix(req.GetRef(), []byte("-")) {
		return errors.New("invalid ref argument")
	}

	return nil
}

}
