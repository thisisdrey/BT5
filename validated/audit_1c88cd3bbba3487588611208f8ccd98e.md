## Title
Uncontrolled Resource Consumption via Unbounded Array Allocation in `ValidateMultiSign`/`BatchValidateSign` Precompiles Before Size Validation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `@isaacs/brace-expansion` advisory describes a bug class where a library eagerly allocates/expands a data structure sized by attacker-controlled input *before* any bound is enforced, leading to memory/CPU exhaustion. The analogous pattern exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, which are reachable by any contract call (`STATICCALL`/`CALL` from any TVM contract, i.e. any unprivileged transaction sender who deploys or triggers a contract).

### Finding Description
`ValidateMultiSign.execute()` decides which extraction routine to use based on a hardfork flag, `VMConfig.allowTvmSelfdestructRestriction()`: [1](#0-0) 

When the fork flag is active, the array-size check (`sigArraySize > MAX_SIZE`) happens *before* calling `extractSigArray`. But when the flag is **not** active (legacy/pre-fork behavior, still the code path compiled and reachable on any deployment where this specific fork hasn't activated, e.g. private/forked chains, older node versions, or test networks), `extractBytesArray` is invoked **unconditionally**, with no upper bound on the attacker-supplied length, and the `signatures.length > MAX_SIZE` check only runs *after* extraction has already completed: [2](#0-1) 

Inside `extractBytesArray`, `len = words[offset].intValueSafe()` is taken directly from calldata and used to allocate `new byte[len][]` without any validation that `len` is reasonable:
```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
An attacker can craft calldata where this length word is a very large value (e.g. close to `Integer.MAX_VALUE`), causing an immediate attempt to allocate a huge reference array. This allocation happens **outside** any `try/catch(Throwable)` block — the surrounding exception handling in `ValidateMultiSign.execute()` only wraps the *permission-checking loop after* extraction: [3](#0-2) 

The same unguarded-extraction pattern appears in `BatchValidateSign.doExecute()`, which similarly gates the `sigArraySize`/`addrArraySize` bound check behind the same fork flag before calling `extractSigArray`, but falls back to unbounded `extractBytesArray`/`extractBytes32Array` when the flag is off: [4](#0-3) 
`extractBytes32Array` has the identical unbounded-allocation issue: [5](#0-4) 

This mirrors the brace-expansion CWE-1333 pattern precisely: expansion/allocation sized by untrusted input is performed eagerly, before any complexity/size limit is applied, and the resulting `OutOfMemoryError` is an unchecked `Error` (not `Exception`), so it is not caught by the surrounding `catch (Throwable t)` block that only wraps the later loop — it propagates up through `VM.play()` and can destabilize the JVM process (a well-known consequence of near-heap-exhausting `OutOfMemoryError` in Java: other threads fail/allocate-fail unpredictably, potentially crashing the whole node).

### Impact Explanation
Because this precompile is reachable from any smart contract via `CALL`/`STATICCALL` to a fixed known precompile address, any unprivileged account that can broadcast a `TriggerSmartContract` transaction (or deploy a contract that calls the precompile) can attempt this attack at low cost. Successful triggering of `OutOfMemoryError` can crash or destabilize the executing node (denial of service against block-producing or full nodes), which the analog rules explicitly recognize as valid impact ("node crash or halt").

### Likelihood Explanation
Exploitability is conditioned on the legacy code path being reachable — i.e., on networks/deployments where `VMConfig.allowTvmSelfdestructRestriction()` has not been activated (this could include private/consortium chains built from this codebase, older forks, or any deployment lagging the fork activation). Where the fork is active, the bound check happens first and the bug is mitigated for that specific code path. I could not fully confirm from the available index whether this fork is unconditionally active on all currently-supported networks by the time of this codebase snapshot; this should be verified against the live `ForkController`/`ForkBlockVersionEnum` activation status before treating this as universally exploitable on mainnet.

### Recommendation
Move the `sigArraySize`/`addrArraySize` bound checks in `ValidateMultiSign` and `BatchValidateSign` outside the `VMConfig.allowTvmSelfdestructRestriction()` conditional so they always run before any array is allocated, regardless of fork status. Additionally, `extractBytesArray` and `extractBytes32Array` should validate `len` against a sane upper bound (e.g., `MAX_SIZE`) before allocating, rather than relying entirely on a post-hoc check performed by the caller.

### Proof of Concept
Construct calldata for `ValidateMultiSign` (or `BatchValidateSign`) on a network/build where `VMConfig.allowTvmSelfdestructRestriction()` is inactive:
1. Set the ABI header offset word (`words[3]`) to point to an array-length slot.
2. Set that length word to a very large value (e.g. `0x7FFFFFFF`).
3. Invoke the precompile from a deployed contract via `CALL`.
4. `extractBytesArray` executes `new byte[0x7FFFFFFF][]` before any size check, attempting a multi-gigabyte allocation and throwing `OutOfMemoryError`, which is not caught by the local `try/catch(Throwable)` (that block only wraps the post-extraction loop), propagating up through `VM.play()` and destabilizing the node process executing the transaction.     if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();

          bytesLen);
    }

    @Override

        return Pair.of(false, EMPTY_BYTE_ARRAY);
