### Title
Single-user exhaustion of shared per-repository concurrency queue causes DoS for all other users of the same repository - (File: `internal/grpc/middleware/limithandler/middleware.go`, `internal/limiter/concurrency_limiter.go`)

### Summary
The external report describes an attacker manipulating a *shared* action limit (submit/withdraw) through repeated self-triggered cycles, which exhausts the limit and locks the action out for other, unrelated users. Gitaly has an analogous shared, key-based resource limiter: the concurrency-limiting middleware keys its per-RPC queue solely by **repository path**, not by requesting identity. Any single authenticated user with access to a repository can flood that RPC's queue for the shared key and cause the middleware to immediately reject requests from every other legitimate user of the same repository, exactly mirroring the "one actor exhausts a shared limit and disables it for everyone else" bug class.

### Finding Description
Gitaly's backpressure mechanism limits concurrent RPC execution per repository via the `[[concurrency]]` config, as documented in `doc/backpressure.md`. The lock key used to bucket requests is computed purely from the target repository, with no per-user or per-connection component: [1](#0-0) 

This key is used to look up (or lazily create) a `keyedConcurrencyLimiter` shared by *all* callers targeting that repository: [2](#0-1) 

Once the configured `max_queue_size` slots for that repository/RPC pair are occupied, any *additional* caller — regardless of who they are — is rejected immediately with `ErrMaxQueueSize`, without the queue distinguishing between the flooding user and unrelated legitimate users: [3](#0-2) 

The same repo-keyed, identity-agnostic behavior applies to the streaming path used by RPCs such as clone/fetch (`PostUploadPackWithSidechannel`), which is the exact RPC the project's own documentation recommends protecting with `max_per_repo`/`max_queue_size`: [4](#0-3) 

Because the limiter's admission decision depends only on the shared repository key and not on caller identity, a single user with ordinary read/write access to a shared repository (e.g., a project collaborator, or any user on a publicly readable project) can issue `max_per_repo + max_queue_size` concurrent long-running requests (e.g., clones of a large repo) to permanently saturate both the in-flight slots and the queue for that repository. Every other user attempting the same RPC against that repository — clone, fetch, or push depending on which RPC is limited — is then denied service with a `ResourceExhausted`/`LimitError` response until the attacker's requests complete, which the attacker fully controls (e.g., by holding connections open).

### Impact Explanation
This is a direct, unprivileged Denial of Service against all other users of a shared repository for concurrency-limited operations (typically clone/fetch/push paths per the documented `[[concurrency]]` use case). It requires no special privilege beyond ordinary repository access, and defeats the purpose of the backpressure feature by turning a fairness/protection mechanism into an attacker-controlled lockout for collaborators, matching the reported "manipulate shared limit to disable action for others" bug class.

### Likelihood Explanation
Concurrency limiting is an opt-in, admin-configured feature (`[[concurrency]]` in `config.toml`), but it is the officially documented and recommended way to protect Gitaly from resource exhaustion, so production deployments commonly enable it for hot-path RPCs like `PostUploadPackWithSidechannel`. Any authenticated user who can read/clone or push to a repository — which in GitLab includes ordinary project members and, for public projects, any user — can trigger the condition simply by issuing enough concurrent long-running requests against that repository, no elevated privilege or malicious peer/token leak required.

### Recommendation
Incorporate the requesting identity (or connection/session) into the limiter key, or add a secondary per-identity fairness/quota layer on top of the per-repository queue, so that one user's burst of requests cannot consume the entire shared queue budget for a repository. At minimum, reserve a portion of `max_queue_size`/`max_per_repo` capacity per distinct caller, or apply a per-caller token bucket before admission into the shared per-repository queue, as recommended by the report's general mitigation of "redesigning the logic to prevent one actor from locking out the limit for others."

### Proof of Concept
1. Admin configures `[[concurrency]]` for `rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"` with `max_per_repo = 1`, `max_queue_size = 5` (as shown in `doc/backpressure.md`), for a shared repository `R` accessible by multiple collaborators.
2. Attacker (an ordinary collaborator/reader of `R`) opens 1 + 5 = 6 concurrent clone/fetch connections to `R`, deliberately keeping each connection open (e.g., via slow client reads) so the in-flight slot and all 5 queue slots for key `R` remain occupied indefinitely.
3. Any other legitimate user of `R` issuing the same RPC now immediately receives a `gitalypb.LimitError` with `ErrMaxQueueSize`, as produced in `internal/limiter/concurrency_limiter.go` `Limit()`, because the shared `limitsByKey[R]` semaphore is exhausted.
4. The attacker sustains the 6 open connections indefinitely (or repeats the cycle as connections complete), keeping the repository's queue perpetually saturated and denying service to all other users of `R` for that RPC.

func (c *ConcurrencyLimiter) Limit(ctx context.Context, limitingKey string, f LimitedFunc) (interface{}, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"limiter.ConcurrencyLimiter.Limit",
		[]attribute.KeyValue{
			attribute.String("key", limitingKey),
		},
	)
	defer span.End()

	if c.currentLimit() <= 0 {
		return f()
	}

	sem := c.getConcurrencyLimit(limitingKey)
	defer c.putConcurrencyLimit(limitingKey)

	start := time.Now()

	if err := sem.acquire(ctx, limitingKey); err != nil {
		queueTime := time.Since(start)
		switch {
		case errors.Is(err, ErrMaxQueueSize):
			c.monitor.Dropped(ctx, limitingKey, sem.queueLength(), sem.inProgress(), queueTime, "max_size")
			return nil, structerr.NewResourceExhausted("%w", ErrMaxQueueSize).WithDetail(&gitalypb.LimitError{
				ErrorMessage: err.Error(),
				RetryAfter:   durationpb.New(0),
			})

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
