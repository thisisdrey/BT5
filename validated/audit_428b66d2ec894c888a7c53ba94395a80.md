## Title
Native zk-SNARK proving context leaked on every failed shielded TRC-20 parameter build — (File: `framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java`)

## Summary
`ShieldedTRC20ParametersBuilder.build(boolean withAsk)` allocates a native Sapling proving context via `JLibrustzcash.librustzcashSaplingProvingCtxInit()` at the start of the method, then performs a sequence of attacker-influenced operations (path/format validation, proof generation, OVK validation) inside a `try` block whose `catch (Exception e)` branch only rethrows a wrapped `ZksnarkException` and never calls `JLibrustzcash.librustzcashSaplingProvingCtxFree(ctx)`.

## Finding Description
`build()` starts the native context and enters a `try`: [1](#0-0) 

Inside the `try`, multiple attacker-reachable exception paths exist inside `generateSpendProof`/`generateOutputProof` and the caller logic — e.g. a malformed Merkle path throws `ZksnarkException(MERKLE_TREE_PATH_LENGTH_ERROR)`, an invalid/missing `nf`/`cm` throws `"Spend is invalid"`, a bad OVK throws `"ovk is null or invalid..."`, and a native proof failure throws `"Spend proof failed"` / `"Output proof failed"`: [2](#0-1) [3](#0-2) [4](#0-3) 

The catch block at the end of `build()` only wraps and rethrows — it never frees `ctx`: [5](#0-4) 

This is structurally identical to the CVE-2017-5993 bug class: a per-request native rendering/proving context (`vrend_renderer_init_blit_ctx` ↔ `librustzcashSaplingProvingCtxInit`) is allocated, and an error path fails to release it, so each failing invocation leaks host (native/off-heap) memory. Compare with the sibling class `ZenTransactionBuilder.build()`, which correctly uses `try { ... } finally { JLibrustzcash.librustzcashSaplingProvingCtxFree(ctx); }`: [6](#0-5) 

`ShieldedTRC20ParametersBuilder` has no such `finally`, so the fix pattern used elsewhere in the same codebase was not applied here.

## Impact Explanation
`librustzcashSaplingProvingCtxInit`/`Free` manage a native (Rust/C++) proving-context object outside the JVM heap; failing to free it on every error path is a genuine native memory leak, not something the JVM garbage collector can reclaim. Because the majority of realistic attacker inputs to this builder (malformed Merkle paths, invalid `ak`/`nf`, invalid `ovk`, deliberately invalid proof material) are validated only *inside* the `try` block and throw before reaching the intended free point, an external caller of the shielded TRC-20 parameter construction path (mint/transfer/burn) can deterministically trigger the leak on essentially every malformed request. Repeated invocation causes continuous native memory growth on the node, leading to host memory exhaustion and ultimately node crash/denial of service — matching the CVE's "host memory consumption" DoS impact.

## Likelihood Explanation
High reachability: any of the documented failure conditions (bad Merkle path length, empty note commitment/nullifier, invalid `ovk` length, or a rejected proof) is trivial for an external caller to construct deliberately, and each failing call leaks a native context. No privileged role, mining power, or malicious-SR/validator status is required — an ordinary API client building shielded TRC-20 mint/transfer/burn parameters can drive this repeatedly and cheaply.

## Recommendation
Wrap the existing `build()` body in a `try { ... } finally { JLibrustzcash.librustzcashSaplingProvingCtxFree(ctx); }` construct, mirroring `ZenTransactionBuilder.build()`, so the native proving context is released on every exit path (success, `ZksnarkException`, or unexpected `Exception`).

## Proof of Concept
1. Call the shielded TRC-20 parameter construction API (mint/transfer/burn) with a spend whose Merkle `path` array length is not exactly `MERKLE_TREE_PATH_LENGTH` (1024 bytes), or with an invalid/short `ovk`.
2. `build()` calls `librustzcashSaplingProvingCtxInit()`, then `generateSpendProof`/`generateOutputProof` throws `ZksnarkException` (e.g. `"Merkle tree path format is wrong"`, `"ovk is null or invalid..."`, `"Output is invalid"`).
3. The `catch (Exception e)` block wraps and rethrows without calling `librustzcashSaplingProvingCtxFree(ctx)`.
4. Repeat the request; each iteration leaks one native proving context. Sustained repetition grows native memory usage unboundedly, eventually leading to host memory exhaustion and node instability/crash.

        contractBuilder.addSpendDescription(spendDescriptionCapsule.getInstance());
      }

      // Create OutputDescriptions
      for (ReceiveDescriptionInfo receive : receives) {
        ReceiveDescriptionCapsule receiveDescriptionCapsule = generateOutputProof(receive, ctx);
        contractBuilder.addReceiveDescription(receiveDescriptionCapsule.getInstance());

      byte[] dataHashToBeSigned; //256
      transactionCapsule = wallet.createTransactionCapsuleWithoutValidate(
          contractBuilder.build(), ContractType.ShieldedTransferContract, timeout);
