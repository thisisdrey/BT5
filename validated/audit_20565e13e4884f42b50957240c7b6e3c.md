### Title
Unbounded `DelegatedResourceAccountIndexCapsule` list growth with O(n) linear existence checks in `FreezeBalanceActuator` - (File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java)

### Summary
`FreezeBalanceActuator.delegateResource()` maintains per-account `toAccounts`/`fromAccounts` lists in `DelegatedResourceAccountIndexCapsule` to index resource delegations. When adding a new delegation target, the code performs a linear `List.contains()` scan over the entire existing list before appending, and the list itself has no maximum size enforced anywhere in `validate()`. This is structurally identical to the reported `PrimeStrategy.deposit()` bug: an unbounded array combined with an O(n) existence check performed on every write.

### Finding Description
When a `FreezeBalanceContract` transaction specifies a `receiverAddress` (i.e., the sender delegates bandwidth/energy to another account) and the legacy delegate-optimization flag is not enabled, `delegateResource()` is invoked: [1](#0-0) 

For every call, the code fetches (or creates) the `DelegatedResourceAccountIndexCapsule` for both the owner and the receiver, and checks membership via a linear scan of the protobuf-repeated field before appending a new entry:

```
List<ByteString> toAccountsList = ownerIndexCapsule.getToAccountsList();
if (!toAccountsList.contains(ByteString.copyFrom(receiverAddress))) {
  ownerIndexCapsule.addToAccount(ByteString.copyFrom(receiverAddress));
}
```

`addToAccount`/`addFromAccount` simply append to the repeated field with no cap: [2](#0-1) 

An attacker (a single, unprivileged transaction broadcaster) can repeatedly broadcast `FreezeBalanceContract` transactions freezing the minimum allowed balance and delegating to a large number of distinct freshly-generated receiver addresses. Each such transaction:
1. Grows the attacker's own `toAccountsList` by one entry (unbounded — no `MAX` check exists in `FreezeBalanceActuator.validate()`, unlike the analogous, explicitly bounded `MaxFrozenSupplyNumber` check in `AssetIssueActuator`).
2. Performs `.contains()` — an O(n) scan — against that growing list on every single subsequent delegation from the same account.

This is confirmed by the project's own test, which builds a list of 100+ entries via this exact code path without any validation error: [3](#0-2) 

The same unbounded list is also read/rewritten (via `new ArrayList<>(...)`, linear `remove()`, and full serialization) on every corresponding `UnfreezeBalanceActuator` call: [4](#0-3) 

Unlike `AssetIssueActuator`'s `FrozenSupply` list, which is explicitly bounded (`getMaxFrozenSupplyNumber()`, default 10) and validated: [5](#0-4) 
there is no equivalent bound on the number of distinct delegation targets/sources an account can accumulate via the legacy `FreezeBalanceContract` delegate path.

### Impact Explanation
Every write to (and subsequent read/rewrite of) an account's delegation index becomes progressively more expensive as the list grows — both the CPU time consumed within `AbstractActuator.execute()` for that specific account's future freeze/unfreeze/delegate transactions, and the on-disk/serialized size of the `DelegatedResourceAccountIndexCapsule` record (whole-object read-modify-write via protobuf on each mutation). Because this cost is paid inside block-processing/actuator execution (counted against the transaction's execution/CPU-time budget), sufficiently large lists on victim or heavily-targeted accounts degrade their own future freeze/unfreeze/delegate operations and increase per-block processing cost, consistent with a Medium-severity, unbounded-storage/DoS-style analog to the reported class of bug (missing size cap + O(n) existence check reachable from an ordinary user transaction). This does not directly cause fund loss, but produces resource-exhaustion/storage-bloat degradation of a specific account's usability of the freeze/delegate resource system, and increases the marginal validation cost for the chain as this data structure grows without bound.

### Likelihood Explanation
The `FreezeBalanceContract` transaction type is broadcastable by any account with sufficient balance to meet the minimum freeze amount (a low, fixed cost, e.g. 1 TRX per delegation). Generating large numbers of distinct receiver addresses is free (just key generation, no need to create real on-chain accounts). Because delegation only requires the freeze amount plus normal transaction fee/bandwidth — with no additional cost scaling with list size charged to the caller — an attacker can cheaply and repeatedly append entries to their own `toAccounts` (or another account's `fromAccounts`, since the receiver's `fromAccountsList` is also unconditionally appended to by the delegator) index list. Note: this legacy path is only reached when `dynamicPropertiesStore.supportAllowDelegateOptimization()` is false; on networks/forks where the newer delegate-optimization proposal has already been activated, this exact code path is bypassed in favor of `delegateV2`/`unDelegateV2`, which store one entry per (from,to) pair as separate DB keys rather than in a single growing list — reducing but not eliminating exposure to this pattern (each individual delegation is still an unbounded per-account fan-out with no per-account cap enforced anywhere). I was unable to fully verify from the available index whether `supportAllowDelegateOptimization` is enabled by default on current mainnet-equivalent configurations of this codebase snapshot; this affects whether the specific `contains()`-based legacy path is the primary reachable surface today versus the newer key-per-delegation model.

### Recommendation
- Enforce an explicit maximum number of delegation targets/sources per account (analogous to `MaxFrozenSupplyNumber`) in `FreezeBalanceActuator.validate()` and reject transactions that would exceed it.
- Replace the `List.contains()` linear membership check in `delegateResource()` with an O(1) lookup (e.g., a per-(owner,receiver) existence flag/key in the store, similar to how the V2 delegate-optimization path already avoids storing all peers in a single list).
- Consider migrating any remaining legacy (non-`Optimization`) delegation bookkeeping fully onto the key-per-pair (`V2_FROM_PREFIX`/`V2_TO_PREFIX`) model used by `delegateV2`/`unDelegateV2`, which does not require scanning or storing an unbounded in-memory list per account.

### Proof of Concept
1. Ensure the target network has `supportAllowDelegateOptimization()` returning `false` (legacy delegate index path active).
2. Attacker generates N (e.g., 50,000) fresh key pairs (no need to fund or activate them on-chain).
3. Attacker repeatedly broadcasts `FreezeBalanceContract` transactions from their own account, each freezing the minimum allowed balance (e.g., 1 TRX) for `BANDWIDTH` or `ENERGY`, setting `receiverAddress` to a new, distinct generated address each time.
4. Each execution appends one entry to the attacker's `DelegatedResourceAccountIndexCapsule.toAccountsList` (see `FreezeBalanceActuator.delegateResource`, lines 319–345) with no upper bound enforced in `validate()`.
5. As N grows large, every subsequent `FreezeBalanceContract`/`UnfreezeBalanceContract` transaction issued by (or targeting) that account incurs an O(N) `contains()`/list-copy/remove operation (`FreezeBalanceActuator.java:329,342`; `UnfreezeBalanceActuator.java:167-182`), increasing per-transaction CPU time and the serialized size of the index record on every mutation — reproducing the storage-bloat / linear-search DoS pattern described in the source report.

    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .addFromAccounts(fromAccount)
        .build();
  }

  public void removeFromAccount(ByteString fromAccount) {
    if (getFromAccountsList().contains(fromAccount)) {
      List<ByteString> fromList = new ArrayList<>(getFromAccountsList());
      fromList.remove(fromAccount);
      setAllFromAccounts(fromList);
    }
  }

  public List<ByteString> getToAccountsList() {
    return this.delegatedResourceAccountIndex.getToAccountsList();
  }

  public void setAllToAccounts(List<ByteString> toAccounts) {
    this.delegatedResourceAccountIndex = this.delegatedResourceAccountIndex.toBuilder()
        .clearToAccounts()
        .addAllToAccounts(toAccounts)
        .build();
  }
