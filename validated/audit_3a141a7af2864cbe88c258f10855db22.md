### Title
Unvalidated `remote` URL forwarded to `git remote add`/`git fetch` enables git transport-helper command execution - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` accept an attacker-influenceable `remote` string and pass it unmodified as the URL argument to `git remote add origin <remote>` and later `git fetch`, with no scheme allow-listing and, for the bzlmod registry `git_repository` source type, no integrity/checksum pinning at all (unlike the `archive` source type, which requires `integrity`).

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` builds a `_GitRepoInfo` from `ctx.attr.remote` [1](#0-0) , and `_update()` calls `add_origin(ctx, git_repo, ctx.attr.remote)` which executes `git remote add origin <remote>` [2](#0-1) . The `remote` value is passed straight through `_git`/`_execute`, which only prepends `git -c core.fsmonitor=false` and never validates or restricts the URL scheme [3](#0-2) . Git supports the `ext::<command>` remote-helper transport, which runs an arbitrary shell command as the "clone" operation; if `remote` can be set to `ext::sh -c '...'` by anything other than the trusted top-level BUILD/MODULE author, this becomes command execution during repository fetch.

The `remote` attribute is declared as a plain, unvalidated string in `git.bzl` (`attr.string(mandatory = True, doc = "The URI of the remote Git repository")`) [4](#0-3) . Per the bzlmod registry format, a module version's `source.json` can set `"type": "git_repository"` and directly forwards `remote`, `commit`, `tag`, `branch`, etc., to the underlying `git_repository` rule [5](#0-4) . Critically, unlike the default `archive` source type, which requires an `integrity` checksum of the downloaded bytes [6](#0-5) , the `git_repository` source type has **no integrity/checksum field documented at all** — the `remote` string is trusted verbatim from whatever registry served the JSON.

I could not verify (due to tool/time limits) the exact Java class that parses `source.json` for `type=git_repository` and materializes these Starlark attributes (my searches for `RegistryFunction`/`ArchiveRepoSpecBuilder`-style Java code did not surface matching results in this index), so I cannot confirm with certainty whether any additional sanitization is applied between the registry JSON and the `git_repository` rule's `remote` attribute, or whether Bazel's bundled git invocation sets `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow` to restrict transport helpers. Both are necessary to fully confirm exploitability end-to-end.

### Impact Explanation
If exploitable, a hostile/compromised third-party Bazel module registry (added via `--registry`, or a compromised mirror of one) could serve a module version whose `source.json` sets `type: "git_repository"` and `remote: "ext::sh -c '<attacker command>'"`. Because there is no checksum pinning this field (unlike archive sources), any build that resolves this module version would execute the attacker's command on the build machine during repository fetch — full command execution outside any sandbox, analogous to the nodemailer sendmail argument-injection CVE's "attacker-controlled string reaches a privileged subprocess call unsanitized" bug class, except here it is a URL scheme rather than a CLI flag that carries the injection.

### Likelihood Explanation
Likelihood is uncertain given the unverified pieces: it depends on (a) whether Bazel's git invocation restricts `protocol.*.allow` (git defaults typically allow `ext::` for a directly-specified top-level remote, but Bazel-specific hardening could override this — unconfirmed here), and (b) whether the registry-to-attribute path in Java performs any extra validation of `remote` beyond what's visible in the `.bzl` files. Without confirming these two points, this should be treated as a plausible but not fully proven analog.

### Recommendation
- Restrict the `remote` attribute (and any registry-forwarded equivalent) to `http(s)://`, `git://`, `ssh://`, or local file schemes, rejecting `ext::` and other transport-helper schemes.
- When invoking `git`, explicitly set `GIT_ALLOW_PROTOCOL` (or `-c protocol.ext.allow=never` / `-c protocol.allow=never` with an explicit allowlist) in the environment used by `_execute` in `git_worker.bzl`, rather than relying on git's own defaults.
- Require an integrity/checksum-equivalent commitment (e.g., pinned commit hash verification against the fetched HEAD, which Bazel's `git_repository` already computes) to be mandatory for registry-sourced `git_repository` entries, and document/enforce this at the registry-consumption layer.

def _git(ctx, git_repo, command, *args):
    start = [command]
    st = _execute(ctx, git_repo, start + list(args))
    if st.return_code != 0:
        _error(ctx.name, ["git"] + start + list(args), st.stderr)
    return st.stdout

def _git_maybe_shallow(ctx, git_repo, command, *args):
    start = [command]
    args_list = list(args)
    if git_repo.shallow:
        st = _execute(ctx, git_repo, start + [git_repo.shallow] + args_list)
        if st.return_code == 0:
            return st
    return _execute(ctx, git_repo, start + args_list)

def _git_sparse_checkout_config(ctx, git_repo):
    """Configures the repo for a sparse checkout.

    If the Git executable does not support sparse checkout, this function prints a warning and returns False.
    Otherwise, it returns True."""

    git_version = _git_version(ctx)

    # Sparse checkout was added in version 2.25.0.
    if git_version.major < 2 or (git_version.major == 2 and git_version.minor < 25):
        print("WARNING: Git v%s does not support sparse checkout." % (git_version.full_str))
        return False

    # Older versions of Git require this config to be set to the name of the promisor remote.
    config_command = ["config", "extensions.partialClone", "origin"]
    st = _execute(ctx, git_repo, config_command)
    if st.return_code != 0:
        _error(ctx.name, config_command, st.stderr)
    return True

def _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file):
    """Initialize the repo with patterns for a sparse checkout.

    Args:
        ctx: Context of the calling rules.
        git_repo: The Git repository to initialize for sparse checkout.
        sparse_checkout_patterns_or_file: Either a list of patterns or a Label for a sparse-checkout file.
    """

    # Note: `init` is deprecated, but needed for older versions of Git. This command may be removed
    # in future versions.
    init_command = ["sparse-checkout", "init", "--no-cone"]
    st = _execute(ctx, git_repo, init_command)
    if st.return_code != 0:
        _error(ctx.name, init_command, st.stderr)

    if type(sparse_checkout_patterns_or_file) == "list":
        sparse_checkout_patterns = sparse_checkout_patterns_or_file
        set_command = ["sparse-checkout", "set"] + sparse_checkout_patterns
        st = _execute(ctx, git_repo, set_command)
        if st.return_code != 0:
            _error(ctx.name, set_command, st.stderr)
    else:
        sparse_checkout_file = sparse_checkout_patterns_or_file
        link_name = str(git_repo.directory) + "/.git/info/sparse-checkout"
        ctx.delete(link_name)
        ctx.symlink(sparse_checkout_file, link_name)

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
