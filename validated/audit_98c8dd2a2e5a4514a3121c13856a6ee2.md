Audit Report

## Title
Unbounded Ethereum receipts-trie proof in Snowbridge inbound-queue `submit` allows underpriced resource consumption - ([File: bridges/snowbridge/primitives/verification/src/receipt.rs])

## Summary
The `Proof::receipt_proof` field accepted by Snowbridge's inbound-queue `submit` extrinsic is a plain, unbounded `Vec<Vec<u8>>` with no per-node size or overall length limit, unlike the relay-chain's `Proof` type which enforces `MERKLE_PROOF_MAX_DEPTH`/`MERKLE_NODE_MAX_SIZE`. `verify_receipt_proof` walks and RLP-decodes every node in this caller-supplied vector, while the `submit` extrinsic's weight is a single fixed value from benchmarking against one representative fixture, not scaled to the actual proof size, creating a cost/charge mismatch reachable by any signed account.

## Finding Description
`Proof` is defined with an unbounded `receipt_proof: Vec<Vec<u8>>` [6](#0-5) . `verify_receipt_inclusion` forwards this untrusted slice directly into `verify_receipt_proof` [7](#0-6) , which converts every element into a `Bytes` and calls `alloy_trie::proof::verify_proof`, performing trie-node decoding/hashing across all supplied nodes before an RLP decode of the extracted value [2](#0-1) . No bound exists on the number or size of nodes before this walk begins, in contrast to the beacon-chain merkle proofs in the same pallet, which enforce a fixed `branch.len() == depth` check [8](#0-7) , and in contrast to the relay-chain `Proof` type's `Decode` implementation, which explicitly enforces `MERKLE_PROOF_MAX_DEPTH` and per-node `MERKLE_NODE_MAX_SIZE` [9](#0-8) . The `submit` dispatchable's declared weight, `T::WeightInfo::submit()`, is a fixed benchmarked constant produced from a single representative fixture (`T::Helper::initialize_storage()`) rather than any parameter scaled to `receipt_proof` length [3](#0-2) , and the generated weight file confirms this is a flat, non-parameterized value [4](#0-3) .

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. Any signed account calling `submit` [10](#0-9)  can supply a `receipt_proof` with many/large spurious byte-vector nodes, forcing disproportionate trie-decode/hash/RLP-decode CPU work relative to the fixed weight charged, degrading BridgeHub block production.

## Likelihood Explanation
Feasibility is bounded by the runtime's overall block/extrinsic size limits (the whole call must still fit within the parachain's max PoV/extrinsic size), so the attack is not unbounded, but within that ceiling there is no additional constraint keeping `receipt_proof` close to the small number of small nodes a legitimate Ethereum receipts-trie proof requires. No validator, collator, relayer, or governance privilege is needed — only a signed account able to submit an extrinsic, satisfying the unprivileged-attacker bar.

## Recommendation
Bound `Proof::receipt_proof` analogous to the relay-chain `Proof` type — e.g., a `BoundedVec<BoundedVec<u8, MaxNodeSize>, MaxProofDepth>` or a custom `Decode`/`TryFrom` check enforcing realistic Ethereum receipts-trie depth and per-node size limits — and/or scale `submit`'s benchmarked weight by the actual size/length of `receipt_proof` (mirroring how `pallet-bridge-grandpa::submit_finality_proof` scales weight by `precommits.len()`/`votes_ancestries.len()`).

## Proof of Concept
1. Construct a valid `EventProof`/beacon execution proof so `verify_execution_proof` passes (as in `make_inbound_fixture`).
2. Replace `proof.receipt_proof` with a `Vec<Vec<u8>>` containing many large, syntactically-plausible-but-spurious byte strings sized to approach the parachain's extrinsic size limit.
3. Submit via `InboundQueue::submit` from any signed account.
4. Observe `verify_receipt_proof` performs decoding/hashing work across all supplied nodes before failing, while the extrinsic is charged the fixed weight returned by `WeightInfo::submit()`, independent of `receipt_proof` size.

pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
