Based on the investigation, I found a solid local analog. `pallet-revive` itself was already hardened against exactly this bug class (see `prdoc/stable2412/pr_5664.prdoc` — "Calling an address without associated code is a balance transfer" — a call to a plain wallet or contract with no code cannot revert due to missing receive logic). The genuine local analog lives in the Snowbridge reward-payout path.

### Title
Snowbridge relayer rewards are irrecoverably lost when the beneficiary cannot receive the asset on AssetHub, because reward accounting is settled on BridgeHub before remote XCM execution succeeds - ([File: bridges/modules/relayers/src/lib.rs], [File: bridges/snowbridge/primitives/core/src/reward.rs])

### Summary
`pallet-bridge-relayers::do_claim_rewards` removes the relayer's accumulated reward from storage and emits `RewardPaid` as soon as `PaymentProcedure::pay_reward` returns `Ok(())`. For Snowbridge, `pay_reward` is `PayAccountOnLocation::pay_reward`, which only validates, charges fees for, and *delivers* (queues) an XCM to AssetHub — it never confirms that the `DepositAsset` instruction on AssetHub actually succeeds. If the XCM traps on AssetHub (e.g. the destination location cannot receive the asset — insufficient existential deposit for a new foreign-asset account, or any other condition causing `DepositAsset` to fail), the transferred WETH is trapped and the reward is permanently lost, while BridgeHub has already deleted the reward record and reported success.

### Finding Description
`do_claim_rewards` in [1](#0-0)  uses `try_mutate_exists` to `take()` the stored reward and calls `T::PaymentProcedure::pay_reward(...)`. The closure only returns `Err` (rolling back the storage mutation) when `pay_reward` itself returns an `Err`. For the `BridgeReward::Snowbridge` variant, `pay_reward` resolves to `snowbridge_core::reward::PayAccountOnLocation::pay_reward` [2](#0-1) , which builds an XCM containing `ReserveAssetDeposited` + `DepositAsset { beneficiary, ... }`, validates and delivers it via `XcmSender::deliver(ticket)`, then returns `Ok(())`. `deliver` succeeding only means the message was accepted into the outbound transport (UMP/XCMP) queue — it says nothing about whether `DepositAsset` will actually succeed once the message is executed on AssetHub.

Because `Ok(())` from `pay_reward` is treated by `do_claim_rewards` as final settlement (the reward entry is deleted and `RewardPaid` is emitted on BridgeHub), the protocol commits the "money moved" state before the actual value transfer to the beneficiary is confirmed. If the beneficiary location supplied by the relayer cannot accept the deposited asset (e.g. because the account doesn't exist and the reward is below the ED needed to create a new foreign-asset entry, or any other condition under which `DepositAsset` fails), the asset is trapped on AssetHub (an `AssetsTrapped` event is emitted rather than the message failing) and the relayer has no straightforward way to reclaim it, since the XCM's origin used for the trap-claim mechanism is the descended `InboundQueueV2Location`/Ethereum universal origin — not an origin the relayer controls.

This is exactly the invariant break described in the external report: state is advanced/settled optimistically before the terminal, all-or-nothing transfer to the recipient is confirmed to succeed, and the guard that should stop this (an atomic linkage between "reward removed from ledger" and "asset actually deposited to beneficiary") doesn't exist across the two-chain XCM hop. This matches the required pivot: *"Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically."*

Existing tests show `pay_reward` failing synchronously (bad XCM validation, fee-charging failure, delivery failure) correctly preserves the reward entry [3](#0-2) , but there is no equivalent handling for the case where delivery succeeds yet remote execution fails.

### Impact Explanation
A relayer's earned reward (WETH bridged from Ethereum) can be permanently and unrecoverably lost even under entirely honest operation, whenever the chosen/derived AssetHub beneficiary location cannot successfully receive the deposited asset. This is a "permanent user-fund lock/loss" class impact on bridge reward accounting: BridgeHub's local ledger says the reward was paid (`RewardPaid` event, entry deleted), but the value never reaches any usable account and cannot be trivially reclaimed by the relayer.

### Likelihood Explanation
The path is reachable by any registered relayer calling the public, unprivileged extrinsic `claim_rewards_to` [4](#0-3)  with a `BridgeRewardBeneficiaries::AssetHubLocation` beneficiary. No governance, admin, relayer-collusion, or malicious peer assumption is required — only a beneficiary location/asset state on AssetHub that causes `DepositAsset` to fail after the message has already been accepted for delivery (e.g., a fresh account lacking the ED for the WETH foreign asset, which is a very plausible operational condition, not an exotic edge case).

### Recommendation
Do not treat successful XCM `deliver()` as final settlement for reward accounting. Options: (1) use a receipt/ack mechanism so the reward ledger entry is only cleared once AssetHub confirms successful `DepositAsset` execution, or (2) keep the reward pending/re-claimable (rather than deleted) until confirmation, restoring it automatically if a trap/failure signal is observed, or (3) require and validate that beneficiary locations meet minimum-deposit/asset-sufficiency requirements before attempting settlement, rejecting `claim_rewards_to` calls whose target cannot be proven to accept the deposit.

### Proof of Concept
1. Relayer accrues a Snowbridge reward `reward_amount` on BridgeHub via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(beneficiary))` where `beneficiary` resolves to a fresh AccountId32 on AssetHub with `reward_amount` below the WETH foreign-asset sufficient/ED requirement (or any location whose `DepositAsset` handling fails on AssetHub).
3. `PayAccountOnLocation::pay_reward` validates/charges fees for/`deliver`s the XCM successfully, so `pay_reward` returns `Ok(())`.
4. `do_claim_rewards` commits: `RelayerRewards` entry removed, `RewardPaid` event emitted on BridgeHub — as demonstrated by the passing test flow in [5](#0-4) .
5. On AssetHub, the XCM executes; `DepositAsset` fails because the beneficiary account cannot receive/hold the asset. The asset is trapped (`AssetsTrapped`) instead of causing the message to fail — the same "continue processing, drop the value" pattern already demonstrated for a different field in [6](#0-5)  (`invalid_claimer_does_not_fail_the_message`).
6. Result: BridgeHub's ledger shows the reward as paid; the relayer never receives usable funds and has no direct-origin path to `claim_assets` the trapped value.

			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,

			RelayerRewards::<T, I>::try_mutate_exists(

					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;

						&relayer,

							?beneficiary,

					})?;

						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
