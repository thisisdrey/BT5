### Title
`pallet-dap` deactivates arbitrary user-transferred funds as if they were burn/slash proceeds, corrupting `InactiveIssuance` — ([File: substrate/frame/dap/src/lib.rs])

### Summary
`pallet-dap`'s staging account is a plain, deterministically-derived `AccountId` (`Self::staging_account()`), exposed publicly via a view function `staging()`. `on_idle` unconditionally drains **every reducible token** sitting in that account into the buffer account and calls `deactivate_buffer_funds(available)` on the whole amount, treating it as if it were exclusively burn/slash proceeds. Because the account is a normal transferable address, any unprivileged user can send an ordinary balance transfer to it, and that donated balance will be misclassified by the pallet as "burned/inactive" issuance, exactly mirroring the FEI report's core flaw: value that lands in an account "beforehand" via a generic transfer path gets automatically and irreversibly counted as protocol-controlled/collateral-affecting state, without verifying its true origin.

### Finding Description
`pallet-dap` is documented to intercept `OnUnbalanced` burn sources (slashes, fees, dust removal) via `on_nonzero_unbalanced`, which resolves the `Credit` into the staging account: [1](#0-0) 

However, `staging_account()` is just `DAP_PALLET_ID.into_sub_account_truncating(...)`, a normal `AccountId` like any other, and is exposed as a public view function: [2](#0-1) 

Nothing prevents an ordinary account from calling `Balances::transfer_allow_death`/`transfer_keep_alive` to send tokens directly to this address using the standard balances pallet — there is no filter, hold, or provenance tag distinguishing "genuine slash/burn credit" from "user-donated balance."

`on_idle` then reads the account's full reducible balance and, without any check on where the funds came from, transfers the entire amount to the buffer account and deactivates it: [3](#0-2) 

`deactivate_buffer_funds` calls the fungible `Unbalanced::deactivate`, which only mutates the global `InactiveIssuance` counter — it does not verify or track the provenance of the balance being deactivated: [4](#0-3) [5](#0-4) 

This is the direct analog of the FEI report: just as PCVDeposit's `resistantBalanceAndFei` blindly attributed all FEI sitting in the contract to "protocol-controlled" regardless of how it got there (pre-transfer vs. proper deposit flow), `pallet-dap`'s `on_idle` blindly attributes all tokens sitting in the staging account to "burn/slash-derived, now-inactive" issuance regardless of how they got there (legitimate `OnUnbalanced` resolution vs. a plain user transfer).

### Impact Explanation
`InactiveIssuance`/`active_issuance()` (`TotalIssuance - InactiveIssuance`) is a chain-wide accounting primitive that downstream governance and reward logic can rely on to represent circulating/voting-eligible supply. By donating arbitrary amounts of their own tokens to the publicly-known staging address, any unprivileged account can permanently inflate `InactiveIssuance` at will and shrink the reported `active_issuance()` — a runtime-level state-corruption bug that "compromises intended behavior" of a core accounting invariant, without needing any privileged actor, malicious validator, or governance abuse. This falls squarely in the "implementation bugs that compromise intended behavior" and "runtime bugs that compromise intended behavior" categories.

### Likelihood Explanation
Highly likely to be exploitable trivially: any signed account can execute a standard `Balances::transfer_*` to the known/derivable (and publicly exposed via `staging()`) staging account, then simply wait for `on_idle` to run (which happens automatically whenever there's idle weight in a block) to convert the deposit into a permanent `InactiveIssuance` increase. No special permissions, timing, or race conditions are required.

### Recommendation
`pallet-dap` should not treat "whatever balance happens to sit in the staging account" as ground truth for deactivation. Instead:
- Track exactly how much was credited via `on_nonzero_unbalanced` (e.g., accumulate a dedicated storage counter of pending burn-derived amount) and only drain/deactivate that tracked amount in `on_idle`, rather than reading the account's full reducible balance.
- Alternatively, make the staging account inaccessible to ordinary transfers (e.g., by not exposing it as a normal spendable account, or by immediately settling credits without holding a general-purpose balance), so `reducible_balance` can only reflect genuine burn/slash proceeds.

### Proof of Concept
1. Query `Dap::staging()` to obtain the staging account address (a view function, no privilege needed).
2. Submit `Balances::transfer_keep_alive(staging_account, X)` from any funded account.
3. Wait for a block where `on_idle` has spare weight (typical in most blocks); `Pallet::<T>::on_idle` reads `reducible_balance(staging_account)` = `X`, transfers `X` to the buffer account, and calls `deactivate_buffer_funds(X)`.
4. Observe `InactiveIssuance` increased by `X` and `active_issuance()` decreased by `X`, even though `X` originated from a plain user transfer, not a slash/burn/fee credit as the pallet's documented invariant assumes.

		fn on_idle(_block: BlockNumberFor<T>, remaining_weight: Weight) -> Weight {
			let mut meter = WeightMeter::with_limit(remaining_weight);

			// Need at least one read (staging account balance).
			if meter.try_consume(T::DbWeight::get().reads(1)).is_err() {
				return meter.consumed();
			}

			let staging_account = Self::staging_account();
			let available = T::Currency::reducible_balance(
				&staging_account,
				Preservation::Preserve,
				Fortitude::Polite,
			);

			if available.is_zero() {
				return meter.consumed();
			}

			// Need 1 read and 2 writes for the transfer, plus 1 read and 1 write for
			// deactivate (InactiveIssuance) and 1 read for TotalIssuance.
			if meter.try_consume(T::DbWeight::get().reads_writes(3, 3)).is_err() {
				return meter.consumed();
			}

			let buffer = Self::buffer_account();
			if T::Currency::transfer(&staging_account, &buffer, available, Preservation::Preserve)
				.is_err()
			{
				defensive!("DAP: staging account transfer to buffer failed");
				return meter.consumed();
			}

			Self::deactivate_buffer_funds(available);
			Self::deposit_event(Event::StagingDrained { amount: available });

			log::debug!(
				target: LOG_TARGET,
				"DAP: drained {available:?} from staging account to DAP buffer"
			);

			meter.consumed()
		}

impl<T: Config> OnUnbalanced<CreditOf<T>> for Pallet<T> {
	fn on_nonzero_unbalanced(amount: CreditOf<T>) {
		let staging = Self::staging_account();
		let numeric_amount = amount.peek();

		// Funds land in the staging account; `on_idle` will drain them into the buffer and
		// deactivate them there.  Deactivation is intentionally deferred so that active issuance
		// does not flicker down-then-up within the same block.
		let _ = T::Currency::resolve(&staging, amount).inspect_err(|_| {
			defensive!(
				"🚨 Failed to deposit slash to DAP staging account - funds burned, it should never happen!"
			);
		});
