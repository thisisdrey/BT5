### Title
Concurrency-limiter middleware silently disables per-repository admission accounting for RPCs where the target repository cannot be resolved - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
Gitaly's per-repository concurrency limiter derives its lock/admission key from `requestinfohandler`, which extracts the target repository from the RPC request via reflection. When that extraction does not populate a repository (or yields an empty relative path), `LimitConcurrencyByRepo` returns an empty string, and both the unary and stream interceptors treat an empty key as "skip limiting entirely" rather than falling back to a shared/default accounting bucket, exactly mirroring the Zebra flaw where a code path that drops the accounting "source" bypasses the per-source admission cap.

### Finding Description
The concurrency backpressure mechanism documented in `doc/backpressure.md` is implemented by `LimiterMiddleware`. The lock key used to bucket concurrent requests per repository is computed by `LimitConcurrencyByRepo`: [1](#0-0) 

This depends on `requestinfohandler.RequestInfo.Repository`, which is populated only when `mi.TargetRepo(reqMsg)` succeeds for RPCs scoped as `ScopeRepository`: [2](#0-1) 

If the request's repository field cannot be extracted (e.g., method scope mismatch, missing/zero-value repository message, or an empty `relative_path` field on an otherwise well-formed message), `info.Repository` remains `nil`, and `GetRelativePath()` on a nil proto message returns `""` (this is the standard protobuf-generated getter nil-safety behavior). That empty string is then treated specially by both interceptors as "no limiting": [3](#0-2) [4](#0-3) 

In both paths, `if lockKey == "" { return handler(ctx, req) }` (unary) / `return nil` (stream, before acquiring any semaphore) completely bypasses the configured `max_per_repo` / `max_queue_size` / `max_queue_wait` admission control for that RPC invocation — it is not merely bucketed under a shared `""` key (which would still provide *some* fairness bound), it is not limited at all. This is structurally identical to the Zebra advisory's root cause: a code path that fails to carry the accounting "source" (there, the peer address; here, the repository key) causes the per-source/per-repo admission cap check to be skipped, because the enforcement logic is conditioned on the presence of that source (`if let Some(source) = source` in Zebra vs. `if lockKey == ""` in Gitaly).

### Impact Explanation
Unlike Zebra, where the global queue cap (`MAX_INBOUND_CONCURRENCY`) still bounds total in-flight work, Gitaly's concurrency limiting as implemented has no independent global cap — the `[[concurrency]]` config is exclusively keyed by lock key (repository path) per RPC, per `doc/backpressure.md`. Consequently, any code path that causes `lockKey` to be `""` doesn't just lose per-repo fairness, it removes admission control for that RPC entirely, allowing unbounded concurrent in-flight requests of an operator-configured expensive RPC (e.g., `PostUploadPackWithSidechannel`) to build up without ever hitting `max_per_repo`, `max_queue_size`, or `max_queue_wait`, undermining the backpressure mechanism that is documented as Gitaly's primary defense against resource exhaustion.

### Likelihood Explanation
Exploitability depends on the ability of an ordinary caller to trigger the "unresolvable repository" condition on a concurrency-limited RPC while still causing the handler to perform meaningful (expensive) work downstream, since most git RPC handlers independently validate/require the repository path before doing I/O. I was not able to confirm from the indexed code alone whether any operator-configured, concurrency-limited RPC scope/message combination allows `mi.TargetRepo` extraction to fail (or return an empty relative path) while the underlying handler still proceeds to perform substantial work rather than failing fast on repository validation — this would require deeper analysis of `internal/grpc/protoregistry/method_info.go`'s `TargetRepo` implementation and each concurrency-configured RPC's handler-side repository validation order, which I could not fully trace within available tool calls.

### Recommendation
- Distinguish "no lock key available" (should fall back to a safe default limiter, e.g., a global/shared-key limiter or reject the call) from "no concurrency limiting configured for this RPC" in `LimiterMiddleware.UnaryInterceptor`/`wrappedStream.RecvMsg`.
- Ensure `requestinfohandler.extractRequestInfo` surfaces an explicit error/flag when `TargetRepo` extraction fails for a `ScopeRepository` RPC, and have the limithandler treat that as "apply limiter under an explicit sentinel key" rather than silently skipping enforcement.
- Add a regression test asserting that RPCs with a configured `[[concurrency]]` limit cannot bypass the limiter merely by omitting/zeroing the repository field.

### Proof of Concept
Not independently verified end-to-end due to inability to trace whether a concurrency-configured RPC's handler tolerates an empty/unresolvable repository while still doing expensive work; the code-level mechanism is demonstrated by:
1. Configure `[[concurrency]] rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel" max_per_repo = 1`.
2. Send N concurrent requests where the repository message's `relative_path` is empty (or the target-repo field otherwise fails extraction) but the request is otherwise routed to the same expensive handler.
3. Observe via `gitaly_concurrency_limiting_in_progress` Prometheus metric that concurrency exceeds `max_per_repo` because `lockKey == ""` causes `handler(ctx, req)` / `return nil` to be invoked without ever calling `limiter.Limit`.

```go
// LimitConcurrencyByRepo implements GetLockKey by using the repository path as lock.
func LimitConcurrencyByRepo(ctx context.Context) string {
	if info := requestinfohandler.Extract(ctx); info != nil {
		return info.Repository.GetRelativePath()
	}

	return ""
}
```

```go
// UnaryInterceptor returns a Unary Interceptor
func (c *LimiterMiddleware) UnaryInterceptor() grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (interface{}, error) {
		lockKey := c.getLockKey(ctx)
		if lockKey == "" {
			return handler(ctx, req)
		}

		// Check if request is authenticated
		limiter := c.methodLimiters[info.FullMethod]
		unauthLimiter, ok := c.methodLimitersUnauthenticated[info.FullMethod]
		if !auth.IsAuthenticated(ctx) && ok {
			limiter = unauthLimiter
		}

		if limiter == nil {
			// No concurrency limiting
			return handler(ctx, req)
		}
```

```go
func (w *wrappedStream) RecvMsg(m interface{}) error {
	if err := w.ServerStream.RecvMsg(m); err != nil {
		return err
	}

	// Only perform limiting on the first request of a stream
	if !w.initial {
		return nil
	}

	w.initial = false

	ctx := w.Context()

	lockKey := w.limiterMiddleware.getLockKey(ctx)
	if lockKey == "" {
		return nil
```
