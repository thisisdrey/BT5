### Title
64-bit integer overflow in `FindZipCentralDirectory` bypasses zip64 central-directory bounds check, producing a wild pointer dereferenced when Bazel processes an attacker-supplied jar with `ijar` - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (the interface-jar tool bundled with Bazel and invoked during ordinary Java builds to strip a jar down to its ABI) locates the ZIP central directory in `FindZipCentralDirectory`. For zip64 archives, `central_dir_size` and `central_dir_offset` are read as raw, attacker-controlled 64-bit values straight out of the (hostile) zip64 End-Of-Central-Directory record via `get_u8le`, with no independent range validation. The single sanity check `cd.central_dir_offset + cd.central_dir_size > in_length` can be defeated by unsigned 64-bit wraparound, after which `*central_dir = end_of_central_dir - cd.central_dir_size;` computes a wild pointer that is later dereferenced while walking "central directory" entries.

### Finding Description [1](#0-0) 
`EndOfCentralDirectoryRecord.central_dir_size` and `.central_dir_offset` are 64-bit fields, populated in the zip64 path directly from attacker data: [2](#0-1) 
`central_dir_size = get_u8le(current); central_dir_offset = get_u8le(current);` — no upper bound is enforced against `in_length` (the mmap'd file length) at this point.

The only guard is in `FindZipCentralDirectory`: [3](#0-2) 
```
if (cd.central_dir_offset + cd.central_dir_size > in_length) {
    fprintf(stderr, "central directory offset/size is invalid\n");
    return false;
}
*offset = cd.central_dir_offset;
*central_dir = end_of_central_dir - cd.central_dir_size;
```
Because `central_dir_offset` and `central_dir_size` are both fully attacker-controlled `u8` (64-bit unsigned) values, an attacker can choose e.g. `central_dir_size = 0xFFFFFFFFFFFFFFF0` and `central_dir_offset = 0x20`, whose sum wraps modulo 2^64 to `0x10`, which is `<= in_length` and thus passes the check — while `central_dir_size` itself remains astronomically large. The subsequent pointer arithmetic `end_of_central_dir - cd.central_dir_size` then computes a pointer value that is wildly out of the bounds of the memory-mapped input file (undefined behavior in C++, and in practice a garbage address on all common platforms). This pointer is stored as `central_dir_` and used as the starting point for `ProcessCentralDirEntry`/`CalculateOutputLength`/`ProcessNext`, which will dereference it, reading (and copying into the generated interface jar / crashing on) memory well outside the legitimate input buffer.

This function receives its `bytes`/`in_length` straight from `MappedInputFile`, i.e. directly from the bytes of a `.jar`/`.zip` file that `ijar` is asked to strip — such a file is exactly the kind of artifact fetched from an external, attacker-influenced source (e.g., a `java_import`/`http_jar`/Maven dependency served by a hostile registry/mirror). A checksum such as `sha256`/`integrity` on the download only proves the bytes match what the origin published; it does nothing to prevent the origin itself from publishing a maliciously crafted zip64 structure that passes the hash check and then triggers this overflow once `ijar` parses it during the build.

### Impact Explanation
A hostile jar dependency (or hostile mirror serving a jar with a valid, attacker-chosen, declared checksum) can make `ijar` compute and dereference a pointer far outside the mapped input file. At minimum this is a memory-safety violation (out-of-bounds read) inside the `ijar` binary invoked as a build action; depending on the memory layout this can crash the action (build-time DoS) or, more seriously, cause data adjacent to the mapping to be read and copied into central-directory-derived output (interface jar) content, i.e., unrelated process memory potentially leaking into build outputs. This breaks the invariant that "untrusted content stays data" — the crafted numeric fields in the zip64 EOCD record directly control a raw pointer computation, not just data interpretation.

### Likelihood Explanation
Any build that consumes a jar produced or mirrored by an untrusted party (a common scenario for `java_import`, third-party Maven artifacts fetched via `http_jar`/`http_archive`, or a compromised artifact registry) can trigger this: the attacker only needs to craft one zip64 EOCD record with the described offset/size values and publish it (matching whatever checksum they choose to declare, since they are the origin). No sandbox escape, MITM, or credential access is required — only that Bazel's `ijar` action processes the file, which happens automatically as part of standard Java interface-jar generation.

### Recommendation
In `FindZipCentralDirectory` (and in `MaybeReadZip64CentralDirectory`), validate `central_dir_size` and `central_dir_offset` independently against `in_length` *before* performing the addition, and perform the addition using an overflow-checked/widened arithmetic (e.g. compare `central_dir_size > in_length` and `central_dir_offset > in_length - central_dir_size` only after confirming `central_dir_size <= in_length`), rejecting the file if either value alone exceeds the file length or if the subtraction/addition would wrap. Also validate that the resulting `*central_dir` pointer lies within `[bytes, bytes + in_length)` before returning it, rather than trusting pointer arithmetic on unvalidated 64-bit attacker input.
