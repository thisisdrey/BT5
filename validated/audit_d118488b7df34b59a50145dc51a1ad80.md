### Title
Liquidation frontrunning after `open()` prevents debt repayment and causes unfair liquidation - ([File: contracts/utils/Pauseable.sol](contracts/utils/Pauseable.sol))

### Summary
Metronome's `Pauseable` module mirrors the exact Notional vulnerability: when `Pool` (or `PoolRegistry`) is in `everythingStopped` state, `DebtToken.repay`/`repayAll`, `DepositToken.deposit`, and `Pool.liquidate` are all disabled simultaneously. When governance calls `open()`, all functions re-enable in the same block. Any EOA can then call `Pool.liquidate` and frontrun user `repay` transactions, liquidating every position that became unhealthy while the protocol was shut down — with no grace period for users to recapitalize.

### Finding Description
`Pauseable.shutdown()` sets both `_everythingStopped` and `_paused` (Pauseable.sol:113-117). Per `docs/emergency-flags.md`:

- `DebtToken.repay()` / `repayAll()` — disabled if `PoolRegistry.everythingStopped() || Pool.everythingStopped()`
- `DepositToken.deposit()` — disabled if `PoolRegistry.paused() || Pool.paused()` (shutdown implies paused)
- `Pool.liquidate()` — disabled if `PoolRegistry.everythingStopped() || Pool.everythingStopped()`

`open()` (Pauseable.sol:97-100) flips `_everythingStopped = false` atomically. There is no `unpausedAt` timestamp, no grace period, and no per-function re-enable sequencing. While shutdown, oracle prices can move against borrowers; health is publicly readable via `Pool.debtPositionOf`. In the first block after `open()`, a liquidator simply calls `Pool.liquidate(depositToken_, debtToken_, victim_)` — or bundles it ahead of the victim's pending `repay` tx — before the user can act. Users can do nothing during the shutdown to defend themselves (repay and deposit both revert), unlike Compound's design where `repayBorrow` always remains available.

The invariant broken is fair liquidation bounds: users are liquidated while being denied the ability to cure their position, a loss directly attributable to the pause/unpause mechanics rather than market action alone.

### Impact Explanation
Every account that became liquidatable during a shutdown can be liquidated atomically in the same block the protocol reopens, with victims having no window to repay or add collateral. Material loss of user funds; attack cost is one `Pool.liquidate` call. The `onlyGovernor` guard on `open()` does not mitigate this — it merely schedules the attack window; the liquidator needs no privilege.

### Likelihood Explanation
Requires an `everythingStopped` shutdown (governor/guardian action, intended for emergencies) lasting long enough for positions to drift underwater, plus a liquidator frontrunning at reopen — the standard liquidator-bot behavior, not an exotic path. Same class confirmed as a valid Medium by the sponsor in the Notional report. Likelihood is inherently tied to how often shutdowns occur and price volatility during them.

### Recommendation
Add a post-`open()` grace period during which `repay`, `repayAll`, and `deposit` are enabled but `liquidate` remains blocked (e.g., record `unstoppedAt` in `open()` and require `block.timestamp > unstoppedAt + GRACE_PERIOD` in `Pool.liquidate`). Alternatively, allow `repay`/`deposit` during shutdown so users can self-cure without waiting.

### Proof of Concept
Conceptual Foundry fork test:

```solidity
// setup: user has open debt position near liquidation threshold
vm.prank(governor);
pool.shutdown();               // everythingStopped = true, paused = true

// simulate price drift making user liquidatable (mock oracle or real fork over time)

// victim broadcasts repay — blocked while shutdown
vm.expectRevert(IsShutdown.selector);
debtToken.repay(victim, amount);

vm.prank(governor);
pool.open();                   // same block: liquidate re-enabled

// MEV bot frontruns victim's repay in the first block after open()
vm.prank(liquidator);
pool.liquidate(address(depositToken), address(debtToken), victim);

// victim's subsequent repay is too late — position already seized
```

Uncertainty note: I confirmed the flag semantics from `docs/emergency-flags.md` and `Pauseable.sol`; the exact `whenNotShutdown` placement on `Pool.liquidate`/`DebtToken.repay` lines was not line-verified, but the documented disable conditions corroborate the mechanism.
