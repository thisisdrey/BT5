### Title
Unbounded `assets` array in Snowbridge V2 inbound message allows underpriced, disproportionately heavy XCM construction per `submit()` call - ([File: bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs])

### Summary
The Snowbridge inbound queue V2 `submit()` extrinsic charges a fixed weight (`T::WeightInfo::submit()`) regardless of the number of assets encoded in the Ethereum event payload, while the message-to-XCM conversion path iterates over an attacker-controlled, unbounded `Vec<EthereumAsset>` with no length check, directly mirroring the "unbounded loop over externally-supplied list of tokens" bug class from the C4 Sturdy report (`processYield()`/`_getAssetYields()`).

### Finding Description
`Message::try_from(&Log)` decodes an Ethereum log into a `Message` whose `assets: Vec<EthereumAsset>` field is populated by `Message::extract_assets`, which loops over `payload.assets` with no cap: [1](#0-0) 

This message is passed unmodified into `Pallet::process_message`, reachable from the public, permissionless `submit()` extrinsic (callable by any signed relayer after proof verification): [2](#0-1) 

`process_message` hands the message to `T::MessageProcessor::process_message`, which uses `MessageToXcm::convert` → `prepare()`. `prepare()` iterates `message.assets` (again unbounded) to build `AssetTransfer` entries, each requiring a `reanchor` computation and a `MaybeConvert` lookup for `ForeignTokenERC20`: [3](#0-2) 

`convert()` then loops again over `message.assets` to split them into `reserve_deposit_assets`/`reserve_withdraw_assets` before building the final `Xcm<()>`: [4](#0-3) 

None of the three passes (`extract_assets`, `prepare`, `convert`) impose a maximum on `assets.len()`, and I found no `MaxAssets`/`MAX_ASSETS` constant, `BoundedVec`, or `ensure!(assets.len() <= N, ...)` guard anywhere in the `bridges/snowbridge/**` tree for this V2 path (confirmed via repo-wide search for `MaxAssets`/`assets.len()`). Meanwhile, `submit()` is weighed with the flat `T::WeightInfo::submit()` benchmark weight, which does not scale with the number of assets in the decoded log: [5](#0-4) 

This is the direct analog of the Sturdy finding: an externally-supplied list (there, `extraRewards`; here, `assets` inside a relayed Ethereum log) is iterated without a bound check, and the on-chain gas/weight charged for the call does not account for list length, so the actual work done can exceed what was paid for.

### Impact Explanation
Because Ethereum log/event data (including the number of assets in `IGatewayV2::Payload.assets`) is attacker-influenced (an Ethereum-side contract interaction ultimately controls what gets logged and relayed), a submitter can construct a `submit()` call whose event payload contains a very large `assets` array. Each additional asset adds decode work, a `reanchor` computation, and (for `ForeignTokenERC20`) a token-id-to-location lookup, plus additional XCM instruction weight on the destination (AssetHub) side, none of which is reflected in the fixed extrinsic weight charged on BridgeHub. This is exactly the "public underpriced work that degrades block production or stalls bridge processing" impact class called out in the gate: a single permissionless, fee-paying call can consume execution resources disproportionate to its charged weight, and the resulting oversized XCM can also cause downstream execution/weight problems on AssetHub, potentially stalling processing of that channel.

### Likelihood Explanation
The `submit()` extrinsic is fully permissionless (any `ensure_signed` account, after passing proof verification) and does not require any relayer allowlisting, malicious validator, or governance/admin abuse — it only requires producing a valid Ethereum event log with a proof, which is within reach of any relayer/attacker who can interact with the Gateway contract on Ethereum. Because the number of assets is not filtered anywhere in the decode or conversion path, exploitation only requires making the log contain many `EthereumAsset` entries.

### Recommendation
Introduce and enforce an explicit `MaxAssetsPerMessage` bound: reject (or bound-vec truncate with error) messages during `Message::try_from`/`extract_assets` when `payload.assets.len()` exceeds the limit, and factor the actual `assets.len()` (post-decode, pre-execution) into the weight charged for `submit()` (e.g., a linear weight component similar to `pallet-utility`'s `batch`/`batch_all`, which scales weight with `calls.len()` and enforces `batched_calls_limit`, as seen in this same repo) so that the fee paid matches the work performed.

### Proof of Concept
1. On Ethereum, trigger the Gateway contract to emit an `OutboundMessageAccepted` event whose ABI-encoded `payload.assets` array contains a very large number of `EthereumAsset` entries (e.g., thousands of dust `ForeignTokenERC20`/`NativeTokenERC20` entries), while `execution_fee`/`value` are kept minimal.
2. Any relayer submits this event log + proof via `EthereumInboundQueueV2::submit(origin, event)`. Verification only checks the storage proof and gateway address/nonce, not the size of `assets`. [6](#0-5) 
3. `process_message` → `MessageToXcm::prepare()` iterates all assets building `AssetTransfer`s (reanchor + lookup per asset), then `convert()` iterates them again to build the XCM instruction set: [4](#0-3) 
4. The extrinsic is charged only the fixed `T::WeightInfo::submit()` weight, not proportional to `assets.len()`, so the relayer pays a flat fee for work that scales with the (attacker-chosen) asset count — underpriced public work with a chain/bridge-processing impact.

			let who = ensure_signed(origin)?;
			ensure!(!OperatingMode::<T>::get().is_halted(), Error::<T>::Halted);

			// submit message for verification
			T::Verifier::verify(&event.event_log, &event.proof)

			let message =
				Message::try_from(&event.event_log).map_err(|_| Error::<T>::InvalidMessage)?;

			Self::process_message(who, message)
		}
