### Title
`FreezeBalanceV2`/`DelegateResource` TVM opcodes bypass the `supportUnfreezeDelay` governance flag enforced by their external actuators - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/FreezeBalanceV2Processor.java])

### Summary
The external `FreezeBalanceV2Actuator` (and similarly `DelegateResourceActuator`/`UnDelegateResourceActuator`) refuse to execute unless the committee-controlled feature flag `supportUnfreezeDelay()` is enabled, throwing `"Not support FreezeV2 transaction, need to be opened by the committee"`. The equivalent TVM native-contract code paths that a smart contract can trigger via the `freezebalancev2`/`delegateresource`/`undelegateresource` opcodes never check this flag, so a contract can perform FreezeV2/DelegateResource-family state changes even when the feature has not been enabled by the committee for ordinary transactions.

### Finding Description
`FreezeBalanceV2Actuator.validate()` gates the whole FreezeV2 feature behind a committee-controlled dynamic property: [1](#0-0) 

The TVM opcode implementation for the same state transition, `Program.freezeBalanceV2()`, calls `FreezeBalanceV2Processor.validate()`/`execute()` directly, with no check of `supportUnfreezeDelay()`: [2](#0-1) [3](#0-2) 

The same asymmetry exists for `DelegateResourceActuator` (checks `supportDR()` and `supportUnfreezeDelay()`) versus `DelegateResourceProcessor.validate()` (checks only `supportDR()`, no `supportUnfreezeDelay()` check): [4](#0-3) [5](#0-4) 

And for `UnDelegateResourceActuator` vs. `UnDelegateResourceProcessor` (same pattern — the external actuator has a `supportUnfreezeDelay` check per the grep results, while `UnDelegateResourceProcessor.validate()` has none): [6](#0-5) 

This is structurally identical to the JOJO `JUSDBank` bug: a governance/config flag (`isDepositAllowed` ⇔ `supportUnfreezeDelay`) is checked on the "normal"/user-facing entry point (`_deposit` ⇔ `FreezeBalanceV2Actuator`/`DelegateResourceActuator`) but omitted on a parallel, functionally equivalent internal entry point (`_withdraw(isInternal=true)` ⇔ TVM native-contract processors reachable from contract bytecode via opcodes), letting the same effect occur while the feature is nominally disabled.

### Impact Explanation
While `supportUnfreezeDelay`/FreezeV2/DelegateResource are already enabled on current mainnet, the missing gate is a real code-level inconsistency: any account can deploy a contract that calls the `freezebalancev2`, `delegateresource`/`undelegateresource` opcodes, and that path will execute the FreezeV2/Delegate-resource state transitions (mutating `FrozenV2` balances, `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight`, `DelegatedResource` records) regardless of whether the committee proposal enabling this feature has been passed. This breaks the intended governance/rollout control for a resource-accounting feature that affects consensus-relevant bandwidth/energy weight totals, and could let users manipulate global resource weight accounting or delegate resource in states the protocol did not intend to allow yet, ahead of official activation. This maps to "unauthorized account operation" affecting consensus-relevant resource/reward accounting, reachable by any ordinary contract deployer/caller — not a privileged actor.

### Likelihood Explanation
Trivially reachable: any account can deploy a trivial contract that calls `freezebalancev2`/`delegateresource`/`undelegateresource` TVM opcodes via a `TriggerSmartContract` transaction. No special privileges are required. The bug only manifests as a real bypass while `supportUnfreezeDelay` is set to disabled for the network (e.g., prior to activation or if a future committee proposal turns a related flag off), so exploitability is time/window dependent, which is why this is rated Medium rather than High.

### Recommendation
Add the same `supportUnfreezeDelay()` (and, for `DelegateResourceProcessor`, keep `supportDR()` but also add `supportUnfreezeDelay()`) checks inside `FreezeBalanceV2Processor.validate()`, `DelegateResourceProcessor.validate()`, and `UnDelegateResourceProcessor.validate()`, mirroring the checks already present in `FreezeBalanceV2Actuator`, `DelegateResourceActuator`, and `UnDelegateResourceActuator`, so that the TVM opcode paths cannot be used to circumvent the committee-controlled feature toggle.

### Proof of Concept
1. Committee sets `supportUnfreezeDelay()` to `false` (feature not yet enabled) via the dynamic property backing this flag.
2. Attempt a normal `FreezeBalanceV2Contract` transaction via `FreezeBalanceV2Actuator` → fails with `"Not support FreezeV2 transaction, need to be opened by the committee"` (confirms gate works for the ordinary path): [1](#0-0) 
3. Deploy a contract and invoke a function that executes the `freezebalancev2` opcode (`Program.freezeBalanceV2`) with the same owner/resource parameters — this call reaches `FreezeBalanceV2Processor.validate()`/`execute()` directly and succeeds because no `supportUnfreezeDelay()` check exists there: [2](#0-1) 
4. Observe that the contract account's `FrozenV2` balance and the global `TotalNetWeight`/`TotalEnergyWeight` are mutated despite the feature being disabled for regular transactions — demonstrating the bypass.

Note: I was not able to fully audit every other TVM native-contract processor (e.g., `WithdrawExpireUnfreezeActuator`'s TVM analog) for the same pattern within the available iterations; a full sweep of all `nativecontract` processors against their actuator counterparts for `supportUnfreezeDelay`/`supportAllowNewResourceModel`/`supportDR` parity is recommended to confirm whether additional opcodes share this gap.
