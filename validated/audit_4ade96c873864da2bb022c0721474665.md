This is the Go standard library itself, and the code I found demonstrates the opposite of the reported issue: certificate verification is correctly enforced by default. The relevant TLS client handshake code performs full certificate chain and hostname verification unless `InsecureSkipVerify` is explicitly and intentionally set by the caller [1](#0-0) , and the `InsecureSkipVerify` field itself is clearly documented as opt-in and dangerous [2](#0-1) . The one place in the `go` command that disables verification (`impatientInsecureHTTPClient`, used only for `GOINSECURE`) is explicitly gated behind that opt-in environment variable and documented as such [3](#0-2) .

This does not match the reported bug class: the python-scciclient advisory describes a library that fails to verify TLS certificates by default, unconditionally exposing users to MITM. Go's `crypto/tls` does the opposite — verification is on by default, and any bypass is explicit, documented, and requires deliberate configuration by the calling code (either `InsecureSkipVerify: true` or `GOINSECURE`). There is no unauthenticated/default code path in this repository where an unprivileged attacker can perform a MITM attack due to missing certificate validation. No credible, narrowly-matching analog vulnerability exists here.
