## Title
Lottery winner selection uses publicly predictable `RandomnessCollectiveFlip` output, letting an unprivileged actor precompute the winning ticket before the payout block executes - (File: `substrate/frame/lottery/src/lib.rs`)

### Summary
The `pallet-lottery` module in the reference runtime is configured with `type Randomness = RandomnessCollectiveFlip` [1](#0-0) . This "collective flip" randomness source is explicitly documented as **insecure**: its output for any subject is "known far in advance by anyone observing the chain" and manipulable by block producers [2](#0-1) . `pallet_lottery::choose_ticket`/`generate_random_number` feed this predictable value directly into winner selection with no additional entropy binding or freshness enforcement, and the pallet's own source explicitly flags this as an open, unresolved issue ("TODO: deal with randomness freshness") [3](#0-2) . This is the direct structural analog of the VDF report: a security-critical selection mechanism consumes an input that an unprivileged party can precompute/observe before the mechanism "locks in," undermining the unpredictability assumption the payout logic relies on.

### Finding Description
`Lottery::on_initialize` triggers the payout once `payout_block <= n`, calling `Self::choose_account()` → `choose_ticket(TicketsCount)` → `generate_random_number(seed)` → `T::Randomness::random(...)` [4](#0-3) .

`RandomnessCollectiveFlip::random` derives its seed purely from a ring buffer of the last 81 **parent block hashes**, which are all public, already-finalized chain state by the time they're consumed [5](#0-4) . Because `on_initialize` for block `N` first updates `RandomMaterial` with `parent_hash` (i.e., the hash of block `N-1`, which is already public once block `N-1` is imported) and only afterward computes the lottery payout for that same block, the entire seed material that will decide the winner is knowable to *any chain observer* as soon as block `N-1` is gossiped/imported - strictly before block `N` (the payout block) is even authored. `delay` (configured via `start_lottery`, `ManagerOrigin`) is the only mechanism intended to keep some randomness contributions unknown to ticket buyers before the ticket-buying window (`start + length`) closes [6](#0-5) , but nothing in the pallet enforces that `delay` is large enough relative to the 81-block randomness window, nor that ticket purchases stop before the deciding block hashes become public. The pallet code itself acknowledges this is unresolved ("TODO: deal with randomness freshness", referencing upstream issue #8311) [7](#0-6) .

This mirrors the VDF report precisely: the report's concern was that an attacker could precompute the VDF solution for input `x` because `x` wasn't guaranteed fresh/unpredictable; here, any unprivileged observer can precompute the lottery's winning ticket number because the "randomness" input is deterministic public chain data with a known, small lookback window, and the pallet enforces no minimum unpredictability margin between the last usable block hash and ticket-purchase cutoff.

### Impact Explanation
An unprivileged attacker who monitors the chain can determine, before the payout block finalizes, which call/ticket index will win, and adjust which "valid calls" they submit (or hold back ticket purchases and only fire once the outcome is favorable, if the buying window and payout window overlap due to insufficient `delay`) to redirect the pooled lottery funds (`Lottery` pot) to themselves. This is a fund-theft / wrong-beneficiary outcome against pooled user funds, matching the "reward payouts... wrong beneficiary or amount" impact category.

### Likelihood Explanation
Exploitability depends entirely on the `delay` value chosen when `start_lottery` is called and does not require any privileged, validator, relayer, or governance-malice assumption to trigger — the flaw is in the pallet's reliance on an admittedly insecure randomness source with no enforced minimum freshness margin. Any runtime that configures `pallet_lottery` with `RandomnessCollectiveFlip` (as the reference node runtime does) and does not manually pick a sufficiently large `delay` is exposed; the pallet provides no on-chain guard preventing an unsafe `delay`.

### Recommendation
- Do not use `pallet_insecure_randomness_collective_flip` for value-bearing selection; require a VRF-based randomness source (e.g. BABE `AuthorVrfRandomness`) for `pallet_lottery::Config::Randomness`.
- Enforce a minimum `delay` in `start_lottery` (and in `choose_ticket`) that guarantees the randomness material consumed at payout time was not yet public when the last ticket could be purchased.
- Bind the random seed to a value that cannot be known until strictly after the ticket-purchase window closes (e.g., require `delay` > `RANDOM_MATERIAL_LEN` or use future-block VRF).

### Proof of Concept
1. Runtime configures `pallet_lottery::Config::Randomness = RandomnessCollectiveFlip` and a manager calls `start_lottery(price, length, delay, repeat)` with `delay` set too small relative to the ticket-buying deadline [8](#0-7) .
2. As block `start+length-1` (last block where `buy_ticket` succeeds) is imported, its `parent_hash` (block `start+length-2`) is already public and already folded into `RandomMaterial`; since `RANDOM_MATERIAL_LEN = 81` and only a short `delay` separates ticket-buying end from payout, the attacker can compute `RandomnessCollectiveFlip::random(&(PalletId, seed).encode())` themselves off-chain using the public `RandomMaterial` storage as soon as the deciding block hash is public, exactly reproducing `generate_random_number`/`choose_ticket` logic in `substrate/frame/lottery/src/lib.rs` lines 493-522.
3. Knowing which ticket index/number will win, the attacker times/selects their `buy_ticket` calls in the final eligible blocks to occupy the winning ticket slot, guaranteeing they receive the full pot at payout via `on_initialize`'s `Currency::transfer(&Self::account_id(), &winner, lottery_balance, KeepAlive)` [9](#0-8) .

impl<T: Config> Randomness<T::Hash, BlockNumberFor<T>> for Pallet<T> {
	/// This randomness uses a low-influence function, drawing upon the block hashes from the
	/// previous 81 blocks. Its result for any given subject will be known far in advance by anyone
	/// observing the chain. Any block producer has significant influence over their block hashes
	/// bounded only by their computational resources. Our low-influence function reduces the actual
	/// block producer's influence over the randomness, but increases the influence of small
	/// colluding groups of recent block producers.
	///
	/// WARNING: Hashing the result of this function will remove any low-influence properties it has
	/// and mean that all bits of the resulting value are entirely manipulatable by the author of
	/// the parent block, who can determine the value of `parent_hash`.
	fn random(subject: &[u8]) -> (T::Hash, BlockNumberFor<T>) {
		let block_number = frame_system::Pallet::<T>::block_number();
		let index = block_number_to_index::<T>(block_number);

		let hash_series = RandomMaterial::<T>::get();
		let seed = if !hash_series.is_empty() {
			// Always the case after block 1 is initialized.
			hash_series
				.iter()
				.cycle()
				.skip(index)
				.take(RANDOM_MATERIAL_LEN as usize)
				.enumerate()
				.map(|(i, h)| (i as i8, subject, h).using_encoded(T::Hashing::hash))
				.triplet_mix()
		} else {
			T::Hash::default()
		};

		(seed, block_number.saturating_sub(RANDOM_MATERIAL_LEN.into()))
	}

	#[pallet::hooks]
	impl<T: Config> Hooks<BlockNumberFor<T>> for Pallet<T> {
		fn on_initialize(n: BlockNumberFor<T>) -> Weight {
			Lottery::<T>::mutate(|mut lottery| -> Weight {
				if let Some(config) = &mut lottery {
					let payout_block =
						config.start.saturating_add(config.length).saturating_add(config.delay);
					if payout_block <= n {
						let (lottery_account, lottery_balance) = Self::pot();

						let winner = Self::choose_account().unwrap_or(lottery_account);
						// Not much we can do if this fails...
						let res = T::Currency::transfer(
							&Self::account_id(),
							&winner,
							lottery_balance,
							KeepAlive,
						);
						debug_assert!(res.is_ok());

						Self::deposit_event(Event::<T>::Winner { winner, lottery_balance });

						TicketsCount::<T>::kill();

						if config.repeat {
							// If lottery should repeat, increment index by 1.
							LotteryIndex::<T>::mutate(|index| *index = index.saturating_add(1));
							// Set a new start with the current block.
							config.start = n;
							return T::WeightInfo::on_initialize_repeat();
						} else {
							// Else, kill the lottery storage.
							*lottery = None;
							return T::WeightInfo::on_initialize_end();
						}
						// We choose not need to kill Participants and Tickets to avoid a large
						// number of writes at one time. Instead, data persists between lotteries,
						// but is not used if it is not relevant.
					}
				}
				T::DbWeight::get().reads(1)
			})
		}

		/// Start a lottery using the provided configuration.
		///
		/// This extrinsic must be called by the `ManagerOrigin`.
		///
		/// Parameters:
		///
		/// * `price`: The cost of a single ticket.
		/// * `length`: How long the lottery should run for starting at the current block.
		/// * `delay`: How long after the lottery end we should wait before picking a winner.
		/// * `repeat`: If the lottery should repeat when completed.
		#[pallet::call_index(2)]
		#[pallet::weight(T::WeightInfo::start_lottery())]
		pub fn start_lottery(
			origin: OriginFor<T>,
			price: BalanceOf<T>,
			length: BlockNumberFor<T>,
			delay: BlockNumberFor<T>,
			repeat: bool,
		) -> DispatchResult {
			T::ManagerOrigin::ensure_origin(origin)?;
			Lottery::<T>::try_mutate(|lottery| -> DispatchResult {
				ensure!(lottery.is_none(), Error::<T>::InProgress);
				let index = LotteryIndex::<T>::get();
				let new_index = index.checked_add(1).ok_or(ArithmeticError::Overflow)?;
				let start = frame_system::Pallet::<T>::block_number();
				// Use new_index to more easily track everything with the current state.
				*lottery = Some(LotteryConfig { price, start, length, delay, repeat });
				LotteryIndex::<T>::put(new_index);
				Ok(())
			})?;
			// Make sure pot exists.
			let lottery_account = Self::account_id();
			if T::Currency::total_balance(&lottery_account).is_zero() {
				let _ =
					T::Currency::deposit_creating(&lottery_account, T::Currency::minimum_balance());
			}
			Self::deposit_event(Event::<T>::LotteryStarted);
			Ok(())
		}

	/// Generate a random number from a given seed.
	/// Note that there is potential bias introduced by using modulus operator.
	/// You should call this function with different seed values until the random
	/// number lies within `u32::MAX - u32::MAX % n`.
	/// TODO: deal with randomness freshness
	/// https://github.com/paritytech/substrate/issues/8311
	fn generate_random_number(seed: u32) -> u32 {
		let (random_seed, _) = T::Randomness::random(&(T::PalletId::get(), seed).encode());
		let random_number = <u32>::decode(&mut random_seed.as_ref())
			.expect("secure hashes should always be bigger than u32; qed");
		random_number
	}
