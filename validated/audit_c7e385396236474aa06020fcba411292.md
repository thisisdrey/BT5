Audit Report

## Title
`pallet-uniques::transfer_ownership` silently drops undelivered deposit on best-effort `repatriate_reserved`, permanently locking the original owner's reserved funds - (File: substrate/frame/uniques/src/lib.rs)

## Summary
`Pallet::transfer_ownership` in `pallet-uniques` calls `T::Currency::repatriate_reserved(&details.owner, &new_owner, details.total_deposit, Reserved)` and discards the `Ok(remainder)` it can return, then unconditionally updates `details.owner = new_owner`. Since `repatriate_reserved` is documented as best-effort and may move less than the requested value, a partial transfer leaves deposit funds stuck on the disowned original owner while ownership (and all future deposit-refund logic keyed on `details.owner`) moves to the new owner.

## Finding Description
At `substrate/frame/uniques/src/lib.rs` lines 886-897, `transfer_ownership` invokes `repatriate_reserved` and uses `?` only to propagate hard `Err`s; any `Ok(non_zero_remainder)` returned on partial fulfillment is silently ignored. The call then removes `CollectionAccount` for the old owner, inserts it for `new_owner`, and sets `details.owner = new_owner.clone()` regardless of whether the full `total_deposit` was actually moved. `repatriate_reserved`'s contract in `substrate/frame/support/src/traits/tokens/currency/reservable.rs` explicitly states it moves "as much funds up to `value` will be deducted as possible," returning `Ok(non_zero)` remainder on shortfall rather than erroring — so this is a reachable, non-Err code path with no additional guard. The sibling pallet `pallet-assets` had the identical vulnerability and was fixed in `prdoc/pr_12366.prdoc` by capturing the remainder and enforcing `ensure!(remaining.is_zero(), Error::<T, I>::IncompleteDepositTransfer)`, but the equivalent fix was never applied to `pallet-uniques`.

## Impact Explanation
If the old owner's reserved balance under `Reserved` status is less than `total_deposit` at call time, part of the deposit remains reserved on the original (now disowned) account with no remaining permission path to trigger its release, since collection management calls require being `details.owner`. This results in a permanent lock of the original owner's reserved funds, and creates a desync between `Collection::total_deposit` (now attributed to `new_owner`) and the actual reserved balance backing it, affecting any future refund logic (e.g., in `destroy`) that unreserves based on `details.owner`.

## Likelihood Explanation
Reaching the partial-repatriation branch requires the old owner's reserved balance under the `Reserved` status to be less than `total_deposit` at call time (e.g., via other reserve/hold operations consuming the same balance beforehand), which is a normal, unprivileged runtime condition requiring no governance or validator action — only a signed call from the collection owner plus the target having called `set_accept_ownership`.

## Recommendation
Mirror the fix applied to `pallet-assets::transfer_ownership`: capture the `Ok(remainder)` of `repatriate_reserved` in `pallet-uniques::transfer_ownership` and reject the dispatch with a new `IncompleteDepositTransfer`-style error (rolling back all storage writes via `try_mutate`) if the remainder is non-zero.

## Proof of Concept
1. Owner `A` creates a collection with `total_deposit = D` reserved from `A` under `Reserved` status.
2. Reduce `A`'s reserved balance under `Reserved` below `D` (e.g., another reserve-consuming operation partially frees/uses it) before the transfer call.
3. `B` calls `set_accept_ownership(collection)`.
4. `A` calls `Uniques::transfer_ownership(collection, B)`; `repatriate_reserved(A, B, D, Reserved)` moves only `D' < D` and returns `Ok(D - D')`, which is discarded at `substrate/frame/uniques/src/lib.rs` lines 887-892.
5. Assert `Collection::get(collection).owner == B` while `A` still has `D - D'` reserved with no way to reclaim it, and `B` is recorded as backing the full `D` deposit without having received it.
