### Title
Attacker-Seeded Pool Reserves Corrupt First Liquidity Price in `pallet-asset-conversion`'s `do_add_liquidity` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`pallet-asset-conversion` derives a liquidity pool's reserves directly from the **raw on-chain balances** held by a deterministic pool account, rather than from state that is exclusively updated through the pallet's own extrinsics. Because the pool account's address can be computed by anyone before the pool is even created, and `create_pool` is a fully permissionless extrinsic, an attacker can pre-seed the future pool account with a skewed, tiny/huge asset ratio. When the legitimate liquidity provider later creates the pool and calls `add_liquidity`, the pallet treats the attacker-planted balances as genuine reserves and forces the honest deposit to match that corrupted ratio — the exact same "early pair creation with skewed reserves" primitive described in the external report for `BondingCurvePool`/`ZealousSwapFactory`.

### Finding Description
The `Pools` storage doc itself acknowledges the risk this exploits: it "establishes whether a pool has been officially created **rather than people sending tokens directly to a pool's public account**." [1](#0-0) 

`create_pool`/`do_create_pool` is a public, unprivileged, signed extrinsic that only checks `!Pools::contains_key(&pool_id)`; it never checks whether the pool account already holds a balance of either asset before registering the pool: [2](#0-1) 

The pool account address, `T::PoolLocator::address(&pool_id)`, is a pure deterministic function of the two asset identifiers and can be computed by anyone in advance — this is explicitly exercised by the pallet's own `cannot_block_pool_creation` test, where an attacker computes the not-yet-existing pool account and transfers funds to it directly: [3](#0-2) 

`do_add_liquidity` then reads `reserve1`/`reserve2` as the pool account's live balances. If both are non-zero (as they will be after the attacker's pre-seed), it does **not** take the caller's desired amounts as-is; instead it computes an "optimal" amount via `quote()` to match the existing (attacker-controlled) ratio: [4](#0-3) 

Because `amount1_min`/`amount2_min` are the *only* guard, and the pool was believed to be freshly created (reserves "should" be zero), a caller providing loose or even reasonable-looking bounds can be forced into depositing almost all of a valuable asset (e.g. the network's native token) matched against a negligible amount of the other asset — mirroring the report's `kasAmount = (moonTokenAmount * kasReserves) / moonTokenReserves` manipulation exactly. The resulting pool has a hugely disproportionate reserve ratio, which the attacker (already in possession of a large stash of the "cheap" asset) can then drain via `swap_exact_tokens_for_tokens`, since a constant-product AMM with a near-zero-side reserve pays out almost the entire opposite reserve for a modest swap input.

### Impact Explanation
This corrupts the effective spot price of a freshly-created, permissionless AMM pool in `pallet-asset-conversion`, which is used in production Asset Hub runtimes both for ordinary liquidity provision and for XCM fee-asset conversion (`quote_price_*`, `get_reserves`, used by the fees-payment `Trader`). A successfully manipulated pool lets an attacker drain the native/valuable asset contributed by the first honest liquidity provider, and/or corrupts fee-conversion pricing derived from `get_reserves`, both of which are direct value-loss / wrong-beneficiary outcomes on a live chain, without any privileged, validator, or off-chain-relayer access.

### Likelihood Explanation
Likelihood is realistic but conditional: the attacker needs to (a) know/derive the target asset pair's deterministic pool account in advance (trivial, pure computation), (b) hold a small amount of both assets to seed a skewed ratio, and (c) act before the legitimate first `add_liquidity` call is executed. Unlike a mempool front-run against one specific pending transaction, this is a wider timing window — anyone monitoring for asset creation or planned pool bootstraps (a routine, publicly announced action, e.g. enabling a new fee-paying asset) can pre-seed the account well ahead of time. No test in the pallet validates price-integrity of the *first* liquidity add against a pre-seeded (non-zero, skewed) pool account balance — only trivial dust-donation/DoS scenarios (`add_tiny_liquidity_directly_to_pool_address`, `cannot_block_pool_creation`) are covered.

### Recommendation
- Do not use the pool account's raw queried balance as the trusted AMM reserve. Track reserves in dedicated pallet storage that is only mutated by `do_add_liquidity`/`do_remove_liquidity`/swap logic, independent of arbitrary external transfers into the pool account.
- Alternatively, at `do_create_pool` time, assert (and if necessary sweep to treasury/creator) that both assets' balances on the newly derived pool account are exactly zero before registering the pool, so that the invariant "a freshly created pool has zero reserves" actually holds.
- For the very first liquidity provision (`total_supply == 0`), never derive the deposited ratio via `quote()` against a "reserve" that has not been established through the pallet itself; only trust reserves once the pool has an existing LP-token `total_supply > 0`.

### Proof of Concept
1. Attacker computes `pool_account = T::PoolLocator::address(&pool_id)` for `(Native, NewAsset)` before any pool exists (pure/deterministic, no permission needed) — pattern proven feasible by `cannot_block_pool_creation`.
2. Attacker transfers `1` unit of `NewAsset` and `1_000_000_000` units of `Native` directly to `pool_account` via ordinary `Assets::transfer`/`Balances::transfer_allow_death` (no pallet call involved).
3. The legitimate actor later calls `create_pool(Native, NewAsset)` then `add_liquidity(Native, NewAsset, amount1_desired=1_000_000_000_000, amount2_desired=1_000_000_000_000, amount1_min=1, amount2_min=1, ...)`, intending a roughly 1:1 contribution.
4. In `do_add_liquidity`, `reserve1 = 1_000_000_000` (Native), `reserve2 = 1` (NewAsset), both non-zero, so the pallet computes `amount2_optimal = quote(amount1_desired, reserve1, reserve2) = 1_000_000_000_000 * 1 / 1_000_000_000 = 1000`, which is `<= amount2_desired`; consequently `amount1 = amount1_desired` (all `1e12` Native is debited) while `amount2 = 1000` NewAsset (a negligible fraction of the intended `1e12`). Both check against `amount1_min`/`amount2_min = 1`, so the call succeeds despite the drastic ratio distortion.
5. Resulting pool reserves ≈ `(1.000000001e12 Native, 1001 NewAsset)`. Attacker, still holding a large stash of `NewAsset`, calls `swap_exact_tokens_for_tokens` swapping `NewAsset → Native`; because the `NewAsset` reserve is tiny relative to `Native`, the constant-product swap formula pays out nearly the entire `Native` reserve for a moderate `NewAsset` input, draining almost all of the honestly-provided `Native` liquidity — the same outcome as the reported `BondingCurvePool`/`ZealousSwapFactory` exploit.

		pub(crate) fn do_create_pool(
			creator: &T::AccountId,
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			initial_fee: Option<Permill>,
		) -> Result<T::PoolId, DispatchError> {
			ensure!(asset1 != asset2, Error::<T>::InvalidAssetPair);
			if let Some(fee) = initial_fee {
				ensure!(fee <= T::MaxSwapFee::get(), Error::<T>::FeeTooHigh);
			}

			// prepare pool_id
			let pool_id = T::PoolLocator::pool_id(&asset1, &asset2)
				.map_err(|_| Error::<T>::InvalidAssetPair)?;
			ensure!(!Pools::<T>::contains_key(&pool_id), Error::<T>::PoolExists);

			let pool_account =
				T::PoolLocator::address(&pool_id).map_err(|_| Error::<T>::InvalidAssetPair)?;

			// pay the setup fee
			let fee =
				Self::withdraw(T::PoolSetupFeeAsset::get(), creator, T::PoolSetupFee::get(), true)?;
			T::PoolSetupFeeTarget::on_unbalanced(fee);

			if T::Assets::should_touch(asset1.clone(), &pool_account) {
				T::Assets::touch(asset1.clone(), &pool_account, creator)?
			};

			if T::Assets::should_touch(asset2.clone(), &pool_account) {
				T::Assets::touch(asset2.clone(), &pool_account, creator)?
			};

			let lp_token = NextPoolAssetId::<T>::get()
				.or(T::PoolAssetId::initial_value())
				.ok_or(Error::<T>::IncorrectPoolAssetId)?;
			let next_lp_token_id = lp_token.increment().ok_or(Error::<T>::IncorrectPoolAssetId)?;
			NextPoolAssetId::<T>::set(Some(next_lp_token_id));

			T::PoolAssets::create(lp_token.clone(), pool_account.clone(), false, 1u32.into())?;
			if T::PoolAssets::should_touch(lp_token.clone(), &pool_account) {
				T::PoolAssets::touch(lp_token.clone(), &pool_account, creator)?
			};

			let pool_info = PoolInfo { lp_token: lp_token.clone() };
			Pools::<T>::insert(pool_id.clone(), pool_info);
