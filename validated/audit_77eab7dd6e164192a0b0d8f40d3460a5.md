Looking at `ValidateMultiSign.execute()`, when `VMConfig.allowTvmOsaka()` is false (pre-TIP-854 activation), malformed calldata reaches `DataWord.parseArray` / `extractBytesArray` without any validation, and — unlike `BatchValidateSign`, which wraps `doExecute` in a `try { } catch (Throwable t)` — `ValidateMultiSign.execute()` has no outer catch at all. An `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or huge-length `OutOfMemoryError` thrown while parsing `words[3]`/`words[4]` indices propagates directly out of `contract.execute(data)`.

### Title
Unguarded index/length parsing in `ValidateMultiSign` precompile allows an unhandled RuntimeException/OOM to propagate out of a CALL frame - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`ValidateMultiSign.execute()` parses attacker-controlled calldata offsets/lengths (`words[3].intValueSafe()`, `extractBytesArray`/`extractSigArray`) without the bounds validation that `isValidAbiEncoding` provides, and that guard is only invoked `if (VMConfig.allowTvmOsaka())`. When that feature flag is not active, a contract call to the `validateMultiSign` precompile (address `0x...0a`) with truncated or malformed ABI-encoded calldata can throw an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from `DataWord.parseArray` or `extractBytesArray`, since this specific precompile — unlike `BatchValidateSign` — has no `try/catch` wrapping its body. [1](#0-0) 

### Finding Description
`extractBytesArray` computes `len = words[offset].intValueSafe()` and then indexes `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` in a loop with no bounds checks against `words.length`, and can allocate `new byte[len][]` with an attacker-chosen `len`. [2](#0-1) 
`ValidateMultiSign.execute()` calls `words[words[3].intValueSafe() / WORD_SIZE]` and `extractBytesArray(words, ..., rawData)` before any length/format validation is applied, and the `isValidAbiEncoding` guard that would reject malformed input is gated behind `VMConfig.allowTvmOsaka()`. [1](#0-0) 
The project's own regression test explicitly documents that pre-activation this precompile "has no outer catch, so a too-short input raises inside the decoder", contrasting it with `BatchValidateSign`, whose `execute()` wraps everything in `try { return doExecute(data); } catch (Throwable t) { ... }`. [3](#0-2) [4](#0-3) 
In `Program.callToPrecompiledAddress`, `contract.execute(data)` is called directly with no try/catch, so any exception thrown here propagates up through the call stack of `VMActuator`/`Runtime`. [5](#0-4) 

### Impact Explanation
When `VMConfig.allowTvmOsaka()` is not yet active on the network, any account can deploy a trivial contract that issues a `CALL`/`STATICCALL` to precompile address `0x...0a` (`validateMultiSign`) with truncated calldata. This causes an unhandled Java `RuntimeException` (index/array errors) to be thrown from inside `contract.execute()`. Whether this is caught further up (in `VMActuator.execute`'s outer try/catch) determines the practical blast radius: if uncaught there too, this can crash transaction processing or, if reached via `Wallet.callConstantContract` (constant/`eth_call`-style query path), can cause the RPC/API-serving path to throw unexpected errors instead of a graceful revert. At minimum, this is a reachable node/service disruption vector triggerable by any unprivileged transaction broadcaster or constant-call API client, satisfying the "node crash/halt or an API the node can no longer serve" impact bar.

### Likelihood Explanation
High reachability: `validateMultiSign` is a standard TVM precompile reachable from any Solidity contract via a low-level `call`/`staticcall`, requiring only the `allowTvmSolidity059()` feature (already active) and calldata the attacker fully controls. The vulnerable path is condition on `allowTvmOsaka()` being off, i.e. this is a real regression window for any chain/environment that hasn't activated the corresponding TIP-854 proposal yet.

### Recommendation
Wrap `ValidateMultiSign.execute()` in the same `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` pattern already used in `BatchValidateSign.execute()`, independent of the `allowTvmOsaka()` flag, so malformed calldata always fails safely rather than throwing. Additionally, make the `isValidAbiEncoding` bounds check unconditional (not gated behind a governance-activated feature flag) so pre-activation nodes are not exposed to this parsing path at all.

### Proof of Concept
1. Deploy a minimal contract that performs `address(0x000000000000000000000000000000000000000a).call(shortMalformedData)` where `shortMalformedData` is fewer than `(5+1)*32` bytes or has a corrupted offset word (e.g., `words[3]` pointing past `words.length`).
2. On a node where `allowTvmOsaka()` is not activated, execute this transaction; `ValidateMultiSign.execute()` will throw an `ArrayIndexOutOfBoundsException` from `DataWord.parseArray`/`extractBytesArray` with no local catch, exactly mirroring the scenario asserted (and explicitly expected to raise) in `ValidateMultiSignContractTest.testTip854PreActivationNoOp`. [6](#0-5) 

**Note on confidence:** I could not fully verify from the indexed code whether `VMActuator`'s outer exception handling around `program` execution (`actuator/src/main/java/org/tron/core/actuator/VMActuator.java`, lines ~180-280) ultimately catches this specific `RuntimeException` gracefully as a normal transaction failure, or whether it can escape further into block-application code causing a wider crash — the visible catch clauses there target more specific exception types (`JVMStackOverFlowException`, etc.). I also could not confirm the current default/mainnet activation state of `allowTvmOsaka()`/TIP-854 within the indexed snippets.
