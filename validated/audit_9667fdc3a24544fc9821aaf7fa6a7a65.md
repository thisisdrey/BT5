### Title
Pre-funding the hardcoded TIP-2935 `HISTORY_STORAGE_ADDRESS` before activation permanently locks TRX/resources with no recovery path - (`File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 `BlockHashHistory` system contract at a hardcoded, keyless address `HISTORY_STORAGE_ADDRESS`. Any unprivileged account can send TRX (or freeze balance) to this address before the proposal activates. When `deploy()` runs, it detects the pre-existing `Normal` account and, mirroring the CREATE2 address-collision handling pattern, converts it in place to `AccountType.Contract` while deliberately preserving the balance, instead of rejecting or refunding it.

### Finding Description
`deploy()` explicitly branches on a pre-existing account at the canonical address: [1](#0-0) 

and the fixed bytecode installed there is the read-only TIP-2935 getter, which has no payable/withdraw function and no way to move value out: [2](#0-1) 

The test suite confirms this is intended behavior, not an oversight — it explicitly documents "anyone can transfer TRX to `HISTORY_STORAGE_ADDRESS` before the proposal fires" and asserts the balance survives the conversion: [3](#0-2) 

This is analogous to the reported bug class (an address-collision / precomputed-address trust issue), but here the root cause is that the canonical, hardcoded address is publicly known and reachable by a plain `TransferContract`/freeze transaction from any account, well before the corresponding contract logic exists to make use of any deposited value. Unlike a normal CREATE2 collision (where the deployer/attacker chooses the salt and thus can potentially recover value through code they control), here the code at this address is fixed by the protocol itself and offers no mechanism to transfer TRX, frozen resources, or votes out again.

### Impact Explanation
Any TRX transferred, frozen (for bandwidth/energy self-freeze), or delegated to `HISTORY_STORAGE_ADDRESS` prior to `deploy()` running becomes permanently unrecoverable once the address is converted to a contract, since the installed bytecode has no functions to transfer, unfreeze, or otherwise release the account's balance/resources. This is a "permanent freezing of funds" outcome reachable purely by an unprivileged asset holder broadcasting a normal transfer/freeze transaction to a well-known, publicly documented address prior to a scheduled TIP-2935 activation.

### Likelihood Explanation
The precondition (knowledge of `HISTORY_STORAGE_ADDRESS`) is trivially satisfied since the address is a hardcoded constant in the open-source codebase, and the activation trigger (`ProposalService`/committee vote to `saveAllowTvmPrague`) is a scheduled, publicly known chain event. Any account — attacker or unwitting user — could transfer or freeze value to this address at any time before activation without any special privilege, satisfying the "single signed transaction from an unprivileged broadcaster" reachability bar. However, actual funds lost are limited to whatever the sender voluntarily deposits at that address, so it does not enable draining of third-party funds (unlike the referenced Sherlock report, which allowed draining arbitrary approved allowances); it is a self-inflicted-but-protocol-enabled fund-freezing bug rather than a theft primitive.

### Recommendation
Before flipping the account type to `Contract` and completing activation, either (a) refund/return any pre-existing TRX balance, frozen balance, and delegated resources at `HISTORY_STORAGE_ADDRESS` to their original owner(s) or a designated recovery address rather than silently locking them into an unusable system contract, or (b) reject/skip the deployment (similar to the existing foreign-code/foreign-contract skip branches) when a pre-existing account with non-zero balance or resources is found, and surface this condition prominently so operators can decide how to handle it, rather than defaulting to silent permanent freezing.

### Proof of Concept
1. Before the TIP-2935 proposal (`AllowTvmPrague`) is activated on chain, any account `A` sends TRX via a normal `TransferContract` to `HISTORY_STORAGE_ADDRESS` (`410000f90827f1c53a10cb7a02335b175320002935`), creating a `Normal` account with a balance there (or freezes balance for bandwidth/energy targeting that address).
2. The community/committee approves the TIP-2935 proposal; at maintenance time `ProposalService` invokes `HistoryBlockHashUtil.deploy(manager)`.
3. `deploy()` finds the existing account, calls `account.updateAccountType(Protocol.AccountType.Contract)` and `account.clearDelegatedResource()`, but keeps the balance, then installs the fixed `HISTORY_STORAGE_CODE` and `HISTORY_STORAGE_CONTRACT` at that address (as validated by `deployUpgradesPreExistingNormalAccountPreservingBalance` in `HistoryBlockHashIntegrationTest.java`).
4. From this point on, the account is a contract running only the TIP-2935 read-only getter bytecode. There is no transaction that can invoke a transfer, unfreeze, or withdrawal from this bytecode, so `A`'s TRX (and any frozen/delegated resources) are permanently locked.
