## Analysis

The Mycelium incident is a case of **AMM/oracle price divergence being exploited by arbitrage bots to drain a liquidity pool** because the price-feed mechanism had no protection against abnormal spread/price movement.

The closest reachable analog in java-tron is the **TRC10 Bancor-style Exchange** (`ExchangeTransactionContract`), which behaves as an on-chain AMM whose "price" is derived purely from its own reserve ratio — this internal reserve ratio is the equivalent of Mycelium's price oracle. Any unprivileged account can broadcast `ExchangeTransactionContract` transactions that shift this reserve-derived price directly, with the only protection being a client-supplied `expected` minimum output — there is no pool-level defense (no price-impact cap, no per-block trade-size limit, no TWAP) analogous to the missing safeguards that let the Bitfinex spread be arbitraged against Mycelium's MLP pool.

### Title
Unprotected AMM reserve-ratio pricing in TRC10 Exchange enables pool-draining sandwich/arbitrage attacks - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java)

### Summary
The TRC10 `Exchange`/`ExchangeTransactionContract` mechanism computes swap output purely from the exchange's own reserve balances via the Bancor-style formula in `ExchangeCapsule.transaction()` [1](#0-0) , using `ExchangeProcessor`/`SafeExchangeProcessor` to derive an "internal price" from `firstTokenBalance`/`secondTokenBalance` [2](#0-1) . This price is used directly for settlement with no protection beyond a caller-supplied minimum (`tokenExpected`) [3](#0-2) .

### Finding Description
Because the reserve ratio *is* the price oracle for the exchange, any account can submit a large `ExchangeTransactionContract` to move that ratio arbitrarily far in one transaction, execute a second trade at the manipulated price, and revert the ratio with a third trade — a classic sandwich/arbitrage sequence — exactly the failure mode described in the Mycelium report, where a temporarily distorted price feed allowed a robot to repeatedly arbitrage against the pool for ~4-6% of its value. `ExchangeTransactionActuator.doValidate()` only checks that the taker's own output exceeds `tokenExpected` [4](#0-3) ; it enforces no maximum price impact, no minimum reserve depth relative to trade size, and no cooldown/anti-manipulation window at the pool level. `ExchangeInjectActuator`/`ExchangeWithdrawActuator` settle proportionally to whatever the (attacker-manipulated) reserve ratio is at the time of the call [5](#0-4) , so an attacker can also time an injection/withdrawal around a manipulated price to extract value from other liquidity participants.

### Impact Explanation
Any well-capitalized, unprivileged account can extract value from TRC10 Exchange pools (and indirectly from other participants who inject/withdraw liquidity or trade near the manipulated price) by round-tripping large trades within a block or across consecutive blocks, mirroring the ~$300K loss suffered by MLP. This constitutes concrete theft of pooled TRC10/TRX funds without requiring any privileged role — reachable purely via broadcasting standard `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` transactions.

### Likelihood Explanation
The attack requires only a signed transaction and sufficient token/TRX balance to move the reserve ratio meaningfully — no special permissions, no p2p/witness involvement, and no dependency on external oracles. Given java-tron's exchanges are permissionless and pool sizes can be modest, this is economically feasible for anyone able to size a trade relative to a given exchange's reserves, similar to how the Bitfinex feed's wide spread was exploitable by an ordinary arbitrage bot.

### Recommendation
Add pool-level anti-manipulation controls to `ExchangeCapsule.transaction()` / `ExchangeTransactionActuator`, such as: a maximum allowed price-impact percentage per trade relative to current reserves, a minimum reserve-to-trade-size ratio, and/or a time-weighted price check to reject transactions that would move the reserve ratio beyond a safe bound within a short window. Consider requiring `ExchangeInjectActuator`/`ExchangeWithdrawActuator` to also validate against a smoothed/reference ratio rather than the instantaneous one.

### Proof of Concept
1. Attacker calls `ExchangeTransactionContract` with a large `tokenQuant` on Token A against an Exchange with shallow reserves, sharply moving the `firstTokenBalance`/`secondTokenBalance` ratio computed in `ExchangeCapsule.transaction()`.
2. In the same or next block, attacker calls `ExchangeWithdrawContract`/`ExchangeInjectContract` or a second `ExchangeTransactionContract` that settles at the now-distorted ratio, extracting more value than was contributed.
3. Attacker reverses the initial trade to restore the ratio, pocketing the difference — repeatable, with no on-chain check preventing it, since validation only enforces the taker's own `tokenExpected` floor [4](#0-3) .

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
