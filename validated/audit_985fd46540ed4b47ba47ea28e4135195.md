### Title
Bad-debt socialization in `liquidate` aborts the entire liquidation if any chained cross-vault call fails - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`liquidate` mirrors the reported `publicMint` pattern: it chains several mutating external calls together, and a failure in any one of them causes the whole user-initiated transaction to revert. In `liquidate`, once a position's collateral is fully exhausted, the function must "socialize" the borrower's remaining debt across every debt asset the borrower holds. This is done via `fold socialize-debt-asset` over the borrower's debt list, where each iteration performs three sequential cross-contract calls, and any single failure poisons the whole fold and reverts the liquidation.

### Finding Description
`liquidate` at [1](#0-0)  resolves the borrower's position, computes liquidation amounts, and — when `no-collateral-left` is true — calls `fold socialize-debt-asset fresh-debt-list { borrower: borrower, success: true }` and then asserts the fold's `success` flag, reverting the entire `liquidate` call with `ERR-BAD-DEBT-SOCIALIZATION-FAILED` if it is `false`: [2](#0-1) 

Each fold step, `socialize-debt-asset`, performs three chained mutating cross-contract calls for a single debt asset, each wrapped in `unwrap!` that converts any `err` into `{ success: false }` for the accumulator, and — critically — once one asset fails, all later assets are skipped ("Early return if previous socialization failed") but the fold as a whole is still marked failed: [3](#0-2) 

Because the assertion `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` is unconditional, a single failing leg among potentially many debt assets (a borrower can hold debt in up to the number of supported asset vaults) is enough to abort the entire `liquidate` transaction — including the collateral seizure and debt repayment for the *primary* asset that was otherwise fully valid and already computed. This is structurally the same DoS class as `publicMint`: a public entry point stitches together multiple external calls into one atomic operation, and any one of them failing blocks the whole operation for every caller who reaches this code path, rather than isolating the calls or applying a pull/best-effort pattern (which the codebase already does elsewhere, e.g. `liquidate-multi` explicitly notes "Failed liquidations return error codes but don't revert entire batch" by using `map` instead of `try!`/`asserts!`) [4](#0-3) .

### Impact Explanation
If bad-debt socialization for a borrower's position ever fails for any one of the borrower's other debt assets, `liquidate` reverts entirely: the liquidator cannot seize collateral or repay any debt for that borrower in that call, and no state changes are committed. Since the position remains at `no-collateral-left` health status (fully depleted collateral, undercollateralized/insolvent), every subsequent liquidation attempt against that borrower will repeat the same code path and can fail again for the same reason, permanently blocking liquidation of that position. This leaves protocol-recognized bad debt un-socialized, i.e., un-written-off, keeping the vault's/lindex accounting overstating recoverable assets — a form of temporary-to-permanent freezing of the affected vault depositors' funds and a path toward protocol insolvency being masked rather than realized, matching the report's DoS-with-failed-call class.

### Likelihood Explanation
I was unable to fully confirm, within the available exploration, a concrete unprivileged trigger that reliably makes one of the three inner calls (`vault-socialize-debt`, `vault-accrue`, `.market-vault debt-remove-scaled`) fail on demand (e.g., via a zero-amount edge case, a paused vault, or an accrual computation edge case) without invoking DAO-privileged pause actions, which are explicitly out of scope per the rules. The report's own resolution for the analogous `publicMint` issue was "Acknowledged... the chance of a failed call is low," and the same characterization likely applies here: the structural DoS pattern (all-or-nothing chained external calls) exists and is provable from the code, but the probability of naturally or adversarially triggering the failing leg (as opposed to a DAO-caused pause) is not established with certainty from what I could review in this pass.

### Recommendation
Make bad-debt socialization best-effort per asset instead of all-or-nothing: continue processing remaining debt-asset legs even if one fails (do not early-return the whole fold as failed), and do not gate the primary `debt`/`collateral` result of `liquidate` on the success of every socialization leg. Emit a per-asset event for any leg that fails so socialization can be retried/reconciled separately (isolate the external calls, as recommended in the original report), rather than reverting the entire liquidation.

### Proof of Concept
Conceptual PoC (cannot be fully executed/validated without triggering one of the inner calls to fail from an unprivileged path, which I could not conclusively establish):
1. Borrower opens positions with debt in two or more assets (e.g., `USDC` and `USDH`) against a single collateral asset.
2. Collateral price crashes so the position becomes fully insolvent (`no-collateral-left` becomes true after collateral seizure for one debt asset).
3. `liquidate` is called; it seizes all collateral for the primary debt asset, then enters bad-debt socialization for the borrower's *other* debt asset(s) via `fold socialize-debt-asset`.
4. If any single call in `socialize-debt-asset` for one of those other assets returns an `err` (e.g., because that asset's vault is paused, or an edge-case zero-amount `asserts!` fires), `success` becomes `false` for the whole fold.
5. `(asserts! (get success socialization-result) ERR-BAD-DEBT-SOCIALIZATION-FAILED)` reverts the entire `liquidate` call, undoing the collateral seizure/debt repayment that had already been computed for the primary asset, and this repeats on every retry until the failing leg's condition is resolved — potentially indefinitely if the condition is not resolvable by ordinary users.

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
