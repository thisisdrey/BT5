### Title
Stale `PromiseYieldReceipt`/timeout state survives `DeleteAccount`, letting a self-targeted `promise_yield_create` fire a privileged action (e.g. `AddKey`) against a *different* account that later reuses the same `AccountId` - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs:505-575` deletes the `Account`, `ContractCode`, all access/gas keys, and contract data for an account, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the `YieldIdToDataId`/`DataIdToYieldId` mappings. The `PromiseYieldTimeout` queue is shard-global (indexed by `PromiseYieldIndices`, not by account) and is also untouched by account deletion. As a result, a `PromiseYieldReceipt` planted before `DeleteAccount` remains resolvable after the same `AccountId` is recreated.

### Finding Description
An attacker who owns `a.near` calls `promise_yield_create` on `x.a.near` (receiver_id == current_account_id, a self-targeted yield) with a callback action list containing `AddKey`. This is persisted via `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-211`) under `TrieKey::PromiseYieldReceipt{receiver_id: x.a.near, data_id}`, and a corresponding entry is pushed to the shard-global timeout queue via `enqueue_promise_yield_timeout` (`core/store/src/utils/mod.rs:182-198`).

The attacker never resumes the yield and instead issues `DeleteAccount` for `x.a.near`. `remove_account` wipes the `Account`, `ContractCode`, access keys, gas keys, and contract data [1](#0-0)  but has no code path that touches `PromiseYieldReceipt`, `PromiseYieldStatus`, or `YieldIdToDataId`/`DataIdToYieldId` for the account, and the queue entry lives independently under a shard-wide index [2](#0-1) .

`x.a.near` is later recreated (e.g. handed to a victim who deposits funds under the belief it is a fresh account). At `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) walks the timeout queue purely by block height and re-checks `state_update.contains_key(&promise_yield_key)` [3](#0-2) . Since the stale `PromiseYieldReceipt` row still exists under `x.a.near`'s key, the runtime synthesizes a `PromiseResume{data: None}` receipt and forwards it for processing with zero transactions submitted by anyone [4](#0-3) . This resume causes the originally-stored yield actions (including `AddKey`) to execute against whatever account now occupies `x.a.near` — the victim's freshly funded account — with no signature, nonce, or access-key check, because the action originates from an internally-synthesized system receipt rather than a signed transaction.

No existing check in `remove_account`, `DeleteAccount` action validation, or `resolve_promise_yield_timeouts` verifies that an account being deleted has no outstanding `PromiseYieldReceipt`/timeout entries, nor does account recreation clear leftover yield state (consistent with how `CreateAccount` never scrubs prior residual trie entries — that scrubbing is `remove_account`'s job, and it is incomplete for yield-related columns).

### Impact Explanation
This is an authorization-escalation bug: a privileged action (`AddKey`, or any other action embedded in the yield's action list, e.g. `Transfer`, `FunctionCall`, `DeleteKey`) executes against an account with no signed transaction from its current owner, at an attacker-predetermined block height. If the attacker plants `AddKey(attacker_key)`, they regain full access to an account a victim believes is newly created and controls, enabling theft of any funds subsequently deposited — matching the "authorization escalation across accounts" / "theft of funds" bounty categories.

### Likelihood Explanation
Preconditions are attacker-affordable and require only standard signed transactions: own the parent account (`a.near`), create/fund `x.a.near`, call `promise_yield_create` (self-targeted) with an `AddKey` callback, then `DeleteAccount`. All steps use ordinary, unprivileged account/contract actions available to any funded NEAR account. The only external dependency is convincing/arranging for a victim to treat the recreated `x.a.near` as trustworthy and deposit funds into it before the pre-set `expires_at` height — a social/economic precondition, not a protocol permission. The mechanism itself (timeout firing regardless of account history) is fully deterministic and repeatable.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), iterate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, and `YieldIdToDataId`/`DataIdToYieldId` entries scoped to the account being deleted (mirroring the existing access-key/contract-data cleanup loops), or alternatively have `resolve_promise_yield_timeouts` verify the resolving account still corresponds to the account that created the yield (e.g. via a creation-epoch/account-nonce fencing token) before applying the resumed actions.

### Proof of Concept
Test-loop integration test:
1. Create `a.near`, then `x.a.near` as its subaccount, deploy a contract on `x.a.near` that calls `promise_yield_create` targeting itself with a callback action list `[AddKey(attacker_pubkey)]`; capture `expires_at`.
2. Submit `DeleteAccount` for `x.a.near` in a subsequent block; assert `TrieKey::PromiseYieldReceipt` for the corresponding `data_id` still exists in state (unaffected by deletion).
3. Recreate `x.a.near` (fresh `Account`, fresh access key belonging to a "victim" key), and have the victim deposit a balance — no additional transactions related to promise-yield are submitted.
4. Advance the chain to block height `expires_at` with **zero transactions** in that block.
5. Assert that after this block, `x.a.near` has `attacker_pubkey` registered as an access key (via `get_access_key`), demonstrating the `AddKey` action executed with no transaction submitted post-recreation by victim or attacker.

// Enqueues given timeout to the PromiseYield timeout queue
pub fn enqueue_promise_yield_timeout(
    state_update: &mut TrieUpdate,
    promise_yield_indices: &mut PromiseYieldIndices,
    account_id: AccountId,
    data_id: CryptoHash,
    expires_at: BlockHeight,
) {
    set(
        state_update,
        TrieKey::PromiseYieldTimeout { index: promise_yield_indices.next_available_index },
        &PromiseYieldTimeout { account_id, data_id, expires_at },
    );
    promise_yield_indices.next_available_index = promise_yield_indices
        .next_available_index
        .checked_add(1)
        .expect("Next available index for PromiseYield timeout queue exceeded the integer limit");
}

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
