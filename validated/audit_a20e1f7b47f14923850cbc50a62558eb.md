## Title
Unauthorized front-running of `initialize()` allows squatting on vault minimum-liquidity seat, permanently corrupting the DAO's vault bootstrap - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, and equivalents `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Each vault contract exposes a fully permissionless `initialize()` entry point guarded only by a one-time boolean flag, with no DAO/owner authorization check. This mirrors the `createRJLaunchEvent()` bug class: any unprivileged principal can race the protocol's intended setup transaction and claim the single-use initialization slot for a shared resource (the vault), permanently denying the rightful initializer (the DAO) the ability to bootstrap that vault as designed.

### Finding Description
`initialize()` is defined as: [1](#0-0) 

```
(define-public (initialize)
  (begin
    (asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)
    (var-set initialized true)
    (try! (deposit MINIMUM-LIQUIDITY u0 NULL-ADDRESS))
    ...
    (ok true)))
```

Unlike every other state-mutating admin function in the same contract (`set-authorized-contract`, `set-cap-debt`, `set-cap-supply`, `set-fee-flash`, `set-fee-reserve`, `set-default-flashloan-permissions`, `set-flashloan-permissions-many`), which all begin with `(try! (check-dao-auth))` [2](#0-1) [3](#0-2) , `initialize()` has **no** `check-dao-auth` call. The only guard is the `initialized` data-var, set to `false` at deployment [4](#0-3) .

This is the identical bug class described in the external report: a permissionless function that consumes a single-use, globally shared resource slot (`_token` → `RJLaunchEvent` mapping in the report; `initialized` flag → vault bootstrap here), where the only cost of the front-run is holding a small amount of the underlying token (`MINIMUM-LIQUIDITY = u1000` of `UNDERLYING`) [5](#0-4) . Any address holding `MINIMUM-LIQUIDITY` units of the vault's underlying token (e.g., `sbtc-token`) can call `initialize()` directly, before the DAO's `proposal-protocol-init` executes its own call to the same function [6](#0-5) .

Because `initialize()` calls `deposit(MINIMUM-LIQUIDITY, u0, NULL-ADDRESS)` on behalf of `contract-caller`/`tx-sender` (whoever calls it), the attacker becomes the entity whose tokens seed the vault's minimum liquidity floor and whose transaction sets `initialized` to `true`. Since the flag can never be reset, the DAO's subsequent `initialize()` call in its init proposal will unconditionally fail with `ERR-ALREADY-INITIALIZED`, halting the scripted, ordered protocol bootstrap (`proposal-protocol-init.clar` executes vault cap-setting, market authorization, and egroup creation in one atomic transaction after this call) [7](#0-6) .

### Impact Explanation
This lands in the "vault share math and interest accrual" / "temporary freezing of funds" in-scope bucket: an attacker can grief the DAO's atomic protocol-initialization proposal at negligible cost, forcing the entire multi-step `execute()` transaction (vault authorization, cap-setting, egroup creation) to revert or requiring the DAO to redeploy/patch the vault contract before genuine users can supply/borrow against it — a freezing of the protocol's intended launch, not merely of unclaimed yield. Because the attacker's minimal deposit becomes baked into the vault's non-withdrawable `MINIMUM-LIQUIDITY` floor sent to `NULL-ADDRESS`, this state cannot be reversed without a contract upgrade, unlike a simple retry.

### Likelihood Explanation
Likelihood is high in principle: exploiting requires only holding `MINIMUM-LIQUIDITY` (`u1000`, in base units) of the relevant underlying token and calling a fully public function with no other precondition. In practice the impact is bounded to the deploy/init window before the DAO's `proposal-protocol-init` runs — but that is exactly the same "acknowledged, no tokens should be in circulation before init" scenario Trader Joe described for the analogous C4 finding.

### Recommendation
Add a DAO authorization check to `initialize()` in all six vault contracts, matching the pattern used by every other admin-only function in the same file:
```
(define-public (initialize)
  (begin
    (try! (check-dao-auth))
    (asserts! (not (var-get initialized)) ERR-ALREADY-INITIALIZED)
    ...))
```

### Proof of Concept
1. Deploy vault (e.g., `v0-vault-sbtc.clar`) but before the DAO executes `proposal-protocol-init`.
2. Attacker acquires `MINIMUM-LIQUIDITY` (`u1000`) units of the underlying `sbtc-token`.
3. Attacker calls `(contract-call? .v0-vault-sbtc initialize)` directly from their own account — this succeeds because there is no auth check, only the `initialized` flag check [1](#0-0) .
4. `initialized` is now `true` and the attacker's tokens seed the vault.
5. When the DAO later executes `proposal-protocol-init.clar`'s `execute()`, any equivalent direct/embedded `initialize()` call (or a proposal relying on this being the first call) fails with `ERR-ALREADY-INITIALIZED`, disrupting the atomic bootstrap sequence [7](#0-6) .
