Audit Report

## Title
Unbacked XCM asset credit via fee-on-transfer/rebasing ERC20 tokens in `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus` - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` credits `AssetsInHolding` with the full requested `amount` as soon as the underlying `IERC20::transfer` call to the checking account returns `true` (no revert), without verifying that the checking account's actual balance increased by `amount` [4](#0-3) . Combined with `ERC20Matcher`, which treats any local `AccountKey20` address as a valid fungible asset with no registration/allowlist [5](#0-4) , an attacker can permissionlessly deploy a fee-on-transfer/rebasing ERC20 via `pallet_revive` and have the XCM executor mint an `Erc20Credit(amount)` that exceeds what the shared checking account actually received.

## Finding Description
`withdraw_asset_with_surplus` calls `transfer(checking_address, amount)` on the contract at `asset_id` derived from the XCM `Location` via `AccountKey20ToH160` [6](#0-5) . Success is determined purely by `!return_value.did_revert()` and the ABI-decoded boolean return value; if `true`, it unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` using the caller-requested `amount`, not any measured balance change [1](#0-0) . `deposit_asset_with_surplus` has the symmetric issue: it transfers `amount` from the checking account to the beneficiary and again only inspects the revert status and boolean return, not the beneficiary's realized balance delta [7](#0-6) .

`ERC20Matcher` is `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [5](#0-4) , and `IsLocalAccountKey20::contains` accepts any `Location::new(0, [AccountKey20{..}])` with no whitelist check [8](#0-7) . Since deploying an arbitrary contract through `pallet_revive` is unprivileged, any external user can supply a custom ERC20 whose `transfer` deducts a fee or rebases balances downward while still returning `true`. There is no code anywhere in `erc20_transactor.rs` that queries `balanceOf` before/after the transfer to validate the actual amount moved — confirmed by the absence of any such check in the file.

## Impact Explanation
This breaks the "conserve value / settle exactly once" invariant: `AssetsInHolding` can be credited with `amount` of an ERC20 asset while the real balance backing it at the shared `TransfersCheckingAccount` is smaller by the fee/rebase difference. Because all ERC20 assets of a given contract share the same checking account, this creates unbacked internal credit that can later be redeemed via `deposit_asset_with_surplus` for real value never actually deposited — a theft/unbacked-mint condition against the shared checking account and, transitively, against other legitimate holders of the same asset. This matches the "theft or unbacked mint or unlock" category of the accepted impact gate.

## Likelihood Explanation
Deploying a custom fee-on-transfer/rebasing Solidity ERC20 via `pallet_revive` requires no privilege, and `ERC20Matcher`/`AccountKey20ToH160` accept any `AccountKey20` address with no allowlisting or governance-gated registration step, unlike `TrustBackedAssets`/`ForeignAssets`. This is fully reachable through the public `pallet_xcm::execute`/`send` extrinsics with a `WithdrawAsset`/`DepositAsset` program, making the exploit path realistic and repeatable.

## Recommendation
Do not rely solely on the transfer call's return value/revert status. Snapshot the checking account's (for withdraw) or beneficiary's (for deposit) ERC20 balance via `balanceOf` immediately before and after the `transfer` call, and credit/require exactly the observed balance delta instead of the requested `amount`, rejecting the operation if the delta is short of the requested amount. Alternatively, restrict this transactor to an allowlist of vetted, standards-compliant, non-fee-on-transfer ERC20 contracts, closing the permissionless "any `AccountKey20`" matching path in `ERC20Matcher`/`IsLocalAccountKey20`.

## Proof of Concept
1. Deploy a fee-on-transfer ERC20 contract via `pallet_revive` whose `transfer(to, value)` deducts `value` from sender but credits `to` with `value - fee`, while still returning `true`.
2. Submit an XCM program via `pallet_xcm::execute` with `WithdrawAsset` referencing `AccountKey20{key: <fee_token_address>}` for `amount = X` from the attacker's own balance.
3. `withdraw_asset_with_surplus` calls `transfer(checking_address, X)`, which returns `true` (no revert); `Erc20Credit(X)` is placed into holding even though the checking account's real balance only increased by `X - fee`.
4. Follow with `DepositAsset` to a beneficiary for `X`; `deposit_asset_with_surplus` calls `transfer(beneficiary, X)` from the checking account. Repeating withdraw/deposit cycles accumulates a growing gap between the bookkeeping in `Erc20Credit` and the checking account's true on-chain balance, eventually causing later legitimate depositors' transfers to revert for insufficient balance, or allowing an attacker to redeem more than they deposited.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}
