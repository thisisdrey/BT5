### Title
`remove_account` fails to delete `TrieKey::YieldIdToDataId` / `DataIdToYieldId` mappings, permanently freezing a `yield_id` namespace after `DeleteAccount` - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) cleans up the `Account`, `ContractCode`, access keys, gas key nonces, and contract data trie entries for a deleted account, but it never touches `TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` entries created by `set_yield_id_mapping` (core/store/src/utils/mod.rs:281-297). Because `create_promise_yield_receipt_with_id` (runtime/runtime/src/ext.rs:371-382) checks `has_yield_id_mapping` before allowing reuse of a `user_yield_id`, a stale mapping surviving account deletion permanently blocks that `yield_id` for any future owner of the same account name.

### Finding Description
An account owner can call the host function that maps to `create_promise_yield_receipt_with_id` with an attacker-chosen `user_yield_id` `Y`, which invokes `set_yield_id_mapping(trie_update, receiver_id, Y, data_id)` and writes both `TrieKey::YieldIdToDataId { receiver_id: A, yield_id: Y }` and `TrieKey::DataIdToYieldId { receiver_id: A, data_id }` into trie state (core/store/src/utils/mod.rs:286-297). This yielded promise is never resumed, so the mapping is never cleared via `remove_yield_id_mappings` (core/store/src/utils/mod.rs:326-334), which is only invoked on resume/timeout in runtime/runtime/src/lib.rs.

The attacker then submits a `DeleteAccount` action for `A`, which reaches `remove_account` (core/store/src/utils/mod.rs:505-575) through `runtime/runtime/src/actions.rs`. `remove_account` explicitly removes: the `Account` record, `ContractCode`, all access keys/gas key nonces (via iteration over the access-key prefix), and all `ContractData` entries (via iteration over the contract-data prefix). It performs no iteration or removal over the `YieldIdToDataId`/`DataIdToYieldId` key space for the account, so those two trie entries for `Y` persist in state after the account is deleted.

When account `A` is later recreated (via `CreateAccount`) by a new, unrelated owner, and that owner calls the same yield-creating host function with `user_yield_id = Y`, `create_promise_yield_receipt_with_id` calls `has_yield_id_mapping(self.trie_update, &receiver_id, Y)` (runtime/runtime/src/ext.rs:378-382), which still finds the surviving `YieldIdToDataId` row and returns `true`, causing the function to return `Ok(None)` — permanently and unconditionally denying the new owner the ability to ever use `yield_id = Y` on account `A`, regardless of who now controls the account or what its state is.

No existing check (signature, nonce, access key, gas metering, or storage staking) prevents this, because `DeleteAccount` is a fully authorized, standard action for the account's own owner, and the yield-id namespace is scoped only by `(receiver_id, yield_id)`, not by any account "generation" or a nonce that would be reset on account re-creation.

### Impact Explanation
This is a functionality-level, permanent state-hygiene defect: an attacker (any account owner) can salt a namespace of `yield_id` values on their own account before self-destructing it, denying any future owner of that account name the ability to use those specific `yield_id`s forever (or until manual state intervention such as a protocol/state migration). This matches a liveness/DoS-style finding rather than a direct token-theft or consensus-divergence bug. The scoped impact is confined to `promise_yield_create_with_id` calls addressed to a specific `(account_id, yield_id)` pair; it does not affect account balances directly, but could disrupt any application logic that relies on deterministic/expected `yield_id` availability for payment-flow-like coordination (e.g., an escrow or bridge protocol reusing well-known yield ids tied to a recreated account name).

### Likelihood Explanation
- Preconditions: the attacker must control an account `A` (trivial, self-created), deploy or call a contract capable of invoking `promise_yield_create_with_id` with a chosen `user_yield_id`, never resume that yield, and then self-delete via a standard `DeleteAccount` action.
- Cost: normal gas/storage-staking cost of a promise_yield creation plus a `DeleteAccount` action — no privileged access needed.
- Feasibility: fully reachable by an ordinary client submitting standard transactions to a public RPC endpoint; no validator/node/network access required.
- Repeatability: the attacker can repeat this for an arbitrary set of `yield_id` values before deleting the account, salting many/most of the namespace if `YieldId` space is small enough to be exhaustible, or targeting specific known/expected ids used by a re-deployed protocol.

### Recommendation
In `remove_account` (core/store/src/utils/mod.rs), add iteration/removal of the `YieldIdToDataId` and `DataIdToYieldId` trie key ranges for `account_id`, mirroring the existing access-key and contract-data cleanup loops (using an equivalent `trie_key_parsers::get_raw_prefix_for_yield_id_mappings`-style prefix helper), so that both mapping directions are deleted from state when the account is deleted. Alternatively, if pending yielded promises must still resolve (timeout callback) after deletion, ensure the `PromiseYieldTimeout`/timeout handler path also calls `remove_yield_id_mappings` even if the receiver account no longer exists, and confirm that path is exercised for accounts deleted before yield resolution.

### Proof of Concept
Rust unit test in `core/store/src/utils/mod.rs` test module (or a `runtime/runtime` integration/test-loop test):
1. Set up a `TrieUpdate` for a test account `A` with sufficient balance for storage staking.
2. Call `set_yield_id_mapping(&mut trie_update, &A, Y, data_id)` directly (or drive it via `create_promise_yield_receipt_with_id` through the `External` trait) to simulate `promise_yield_create_with_id(A, Y)`.
3. Call `remove_account(&mut trie_update, &A)` to simulate `DeleteAccount(A)`.
4. Assert `has_yield_id_mapping(&trie_update, &A, Y)` — expected `false` after fix, but currently returns `true`, proving the mapping survives deletion.
5. Optionally simulate account re-creation (`set_account(&mut trie_update, A, &new_account)`) and re-invoke `create_promise_yield_receipt_with_id(A, Y)`, asserting it returns `Some(..)` (currently returns `None`), demonstrating the permanent freeze for the new owner.
