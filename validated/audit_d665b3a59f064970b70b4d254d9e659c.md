### Title
Legacy (non-hardened) `ExchangeCapsule.transaction` performs no post-trade solvency check, allowing an unbacked exchange balance / underflow-derived value manipulation - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java)

### Summary
The Sherlock report describes `isHoldAmountAllowed`/`isSubAmountAllowed` in ELFI's `UsdPool.sol`, where a "hold" amount is validated once via addition, but a later, separately-computed subtraction against the same balance is never re-validated for going negative, causing state corruption/DoS. The closest reachable analog in `java-tron` is `ExchangeCapsule.transaction()` [1](#0-0) , which computes a new pool balance via subtraction and only validates the result is non-negative when `hardenedCalc` is `true`; in the default (legacy) path the subtraction result is written to the pool state unconditionally.

### Finding Description
`ExchangeCapsule.transaction()` computes `newFirstTokenBalance`/`newSecondTokenBalance` by adding the sold token amount and subtracting the computed "bought" token amount from the pool reserves: [2](#0-1) 

The invariant check that the resulting balances are `>= 0` is gated behind `hardenedCalc`: [3](#0-2) 

`hardenedCalc` is only `true` when the `allowHarden()` flag (`ALLOW_HARDEN_EXCHANGE_CALCULATION`, controlled by committee proposal, default `0`) is enabled [4](#0-3) . In the default/legacy configuration, `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(...)` and directly persists the resulting balances via `Commons.putExchangeCapsule(...)` with no additional check that `newFirstTokenBalance`/`newSecondTokenBalance` remain non-negative: [5](#0-4) 

`ExchangeTransactionActuator.doValidate()` does bound the request using the anotherTokenQuant computed from a fresh `ExchangeCapsule` copy fetched at validate time and does check `anotherTokenQuant < tokenExpected`, but it does not verify `firstTokenBalance/secondTokenBalance >= tokenQuant`/`anotherTokenQuant` the way `ExchangeWithdrawActuator` does (`firstTokenBalance < tokenQuant || secondTokenBalance < anotherTokenQuant`, see `ExchangeWithdrawActuator` lines 221/248) [6](#0-5) . `ExchangeTransactionActuator` instead relies exclusively on the legacy `ExchangeProcessor` math (a bonding-curve/AMM style computation using floating point `Maths.pow`) to naturally keep `buyTokenQuant` bounded by the buy-side reserve, with no explicit floor at 0 for the legacy path, unlike the hardened `SafeExchangeProcessor` path which tests confirm is bounded (`result <= buyBalance`) [7](#0-6) .

This mirrors the ELFI bug class precisely: an amount is computed and "allowed" via one code path (validate/`isHoldAmountAllowed`-style check), but the actual persisted subtraction in another code path (`execute`/`isSubAmountAllowed`-style) is not re-guarded against producing a negative/underflowed result, because the safety check (`hardenedCalc` branch) is opt-in rather than always enforced.

### Impact Explanation
If the legacy `ExchangeProcessor` (floating point, `double`) computation for `buyTokenQuant` can, due to precision behavior at reserve-depleting quantities, return a value greater than or equal to the buy-side reserve, the exchange's persisted `secondTokenBalance`/`firstTokenBalance` fields would go negative or produce an unbacked/incorrect balance (since these are stored as `long` and neither `subtractExact` nor a `>= 0` check is applied in the legacy path). A negative or corrupted AMM reserve would then be usable as the input to subsequent trades (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`), letting an attacker drain more of a token than the pool actually holds — an unbacked balance / theft-of-funds class impact reachable directly from a single, unprivileged `ExchangeTransactionContract` broadcast.

### Likelihood Explanation
This requires the legacy (non-hardened) exchange calculation path, which is the current default (`allowHardenExchangeCalculation` defaults to `0`), and requires finding sell quantities near the edge of the bonding-curve/floating point precision limits where `buyTokenQuant` computed by `ExchangeProcessor.exchange()` could equal or exceed the buy-side reserve. The repository's own test suite treats the hardened path as the fix for exactly this class of issue (adding `SafeExchangeProcessor`/`hardenedCalc` and associated tests such as `testHardenedTransactionNegativeBalanceThrows`), which suggests the underlying legacy-math risk was recognized, but I was not able to conclusively reproduce a concrete input demonstrating `buyTokenQuant >= buyBalance` from the legacy `ExchangeProcessor` implementation within this investigation. This is a likelihood caveat, not a claim the bug is confirmed exploitable — additional numeric analysis or fuzzing of `ExchangeProcessor.exchange()` against small buy-reserve/large sell-quantity inputs would be needed to prove exploitability.

### Recommendation
Apply the same `>= 0` invariant check (or equivalent `subtractExact`/`BigDecimal` bound) unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, so that legacy-math trades can never persist a negative or reserve-exceeding balance; alternatively, make `hardenedCalc` (and `SafeExchangeProcessor`) mandatory rather than proposal-gated, and add an explicit `firstTokenBalance/secondTokenBalance` sufficiency check in `ExchangeTransactionActuator.doValidate()` mirroring the check already present in `ExchangeWithdrawActuator.doValidate()`.

### Proof of Concept
Not independently reproduced. A PoC would require: (1) creating an exchange pair with a very small buy-side reserve, (2) issuing an `ExchangeTransactionContract` with a `sellTokenQuant` calibrated so that `ExchangeProcessor.exchange()`'s floating-point computation returns a `buyTokenQuant` at or exceeding the buy-side reserve, and (3) confirming the resulting `ExchangeCapsule` balance is persisted as negative or otherwise inconsistent by `ExchangeTransactionActuator.execute()`. This was not executed against the codebase in this analysis; further numerical/fuzz testing of `ExchangeProcessor.exchange()` boundary conditions is required to confirm feasibility.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  @Test
  public void testSafeProcessorNoOvershootForTypicalInputs() {
    // Verify across realistic inputs that hardened result never exceeds buy reserve.
    long[][] data = {
        {100_000_000L, 100_000_000L, 1_000_000L},
        {1_000_000_000L, 1_000_000_000L, 100_000L},
        {1L, 10_140_000_000_000L, 2_897_000_000_000L},
        {903L, 737L, 50L},
    };
    for (long[] row : data) {
      long result = SafeExchangeProcessor.INSTANCE.exchange(row[0], row[1], row[2]);
      Assert.assertTrue("Result must be non-negative", result >= 0);
      Assert.assertTrue("Result must not exceed buy reserve, got " + result + " > " + row[1],
          result <= row[1]);
    }
  }
