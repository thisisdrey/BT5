### Title
Unprivileged dust deposits fill a victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`, blocking the victim from depositing new collateral types and borrowing new synthetic tokens - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a hard cap of 30 combined deposit + debt tokens per account via `onlyIfAdditionWillNotReachMaxTokens`. Any user can call `DepositToken.deposit(amount_, onBehalfOf_)` with an arbitrary `onBehalfOf_`, or `transfer` dust `msdTOKEN` to a victim, and each first-time deposit-token balance unconditionally calls `pool.addToDepositTokensOfAccount(victim)`, which reverts with `UserReachedMaxTokens` once the combined set length reaches 30. An attacker can therefore saturate a victim's set, after which any action that would add a *new* token to the victim's sets — depositing a collateral type the victim doesn't yet hold, receiving deposit tokens, or issuing a new synthetic debt — reverts.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` are gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (30) [1](#0-0) [2](#0-1) 
- `DepositToken.deposit` takes an arbitrary `onBehalfOf_` and calls `_mint`, which calls `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's balance goes 0 → >0 [3](#0-2) [4](#0-3) 
- `DepositToken._transfer` (reachable via public `transfer`/`transferFrom`, and `seize` during liquidation) does the same on the recipient side, so dust transfers also grow the victim's set [5](#0-4) 
- Once the victim's set is full: (a) `deposit` for any deposit token the victim doesn't already hold reverts; (b) `DebtToken.issue`/`mint` for any new synthetic reverts because `Pool.mint` issues debt through the same capped path; (c) any transfer of a deposit token the victim doesn't hold reverts. Existing-token deposits/withdrawals and withdrawals of the dust positions still work, so the victim can self-recover by withdrawing each dust position (which removes it from the set on balance → 0) [6](#0-5) 

### Impact Explanation
Temporary freezing of funds / liveness degradation: while the set is saturated the victim cannot open new collateral types, cannot mint any new synthetic token (all borrows revert via `addToDebtTokensOfAccount`), and cannot receive deposit tokens — including seized collateral flows if a liquidator's own set is saturated. Recovery requires the victim to submit up to ~30 withdrawal transactions (one per dusted deposit token), each costing gas and each revertible again by a persistent attacker re-dusting. This is a per-account denial of service analogous to the availability impact class in the reference report.

### Likelihood Explanation
Cost is one dust deposit or dust `transfer` per victim per slot. Feasibility depends on how many distinct deposit tokens the victim still lacks relative to the cap: the attacker can only add deposit-token entries (debt tokens can't be pushed onto a victim since `Pool.mint` issues debt to the caller). On a deployed pool with few deposit tokens the attacker alone cannot reach 30 for a fresh victim, but for active users already holding several deposit/debt tokens, filling the remainder is cheap. No privileged role, oracle manipulation, or reentrancy is needed — only public `deposit`/`transfer` calls.

### Recommendation
- Cap only per-pool-registered distinct tokens, or replace the hard revert with a graceful skip/queue so new positions don't brick.
- Alternatively, make `addToDepositTokensOfAccount` idempotent-tolerant: on a full set, either allow the position anyway (the set is only an enumeration helper for `debtPositionOf`) or iterate over the pool-global `depositTokens`/`debtTokens` sets instead of per-account sets.
- Consider charging/white-listing `onBehalfOf` deposits so third parties cannot inflate a user's set.

### Proof of Concept
Hardhat fork-style test (against deployed `Pool`, `DepositToken` proxies):

```typescript
// Attacker fills victim's token set with dust deposits
for (const dt of allDepositTokens) {           // registered deposit tokens victim doesn't hold
```
