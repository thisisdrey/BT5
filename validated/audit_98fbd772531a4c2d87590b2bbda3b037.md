### Title
Missing Zero-Address Check in `set_beneficiary_for_operator` Permanently Locks Operator Commission APT — (`delegation_pool.move` / `staking_contract.move`)

### Summary

Both `delegation_pool::set_beneficiary_for_operator` and `staking_contract::set_beneficiary_for_operator` accept a caller-supplied `new_beneficiary: address` with no validation against the zero address (`@0x0`). Setting the beneficiary to `@0x0` causes all future operator commission to be permanently locked (delegation pool) or causes every subsequent distribution call to abort, freezing staker funds as well (staking contract). This is the direct Aptos analog of the Connext `xcall()` bug where missing `recovery != 0` and `agent != 0` checks caused funds to be sent to the zero address or locked forever.

---

### Finding Description

**Root cause — `delegation_pool::set_beneficiary_for_operator`** [1](#0-0) 

The function accepts `new_beneficiary: address` and writes it unconditionally into `BeneficiaryForOperator`. There is no check that `new_beneficiary != @0x0` (nor any `system_addresses::is_reserved_address` guard, which is the pattern used elsewhere in the framework).

When `synchronize_delegation_pool` runs next (callable by anyone), it credits commission shares to the beneficiary: [2](#0-1) 

`buy_in_active_shares(pool, @0x0, commission_active)` succeeds — it is pure share-accounting with no account creation. The pool now records `@0x0` as the owner of those shares. Because `@0x0` (`@vm_reserved`) can never sign a transaction, those shares — and the underlying APT they represent — can never be redeemed. The commission is permanently frozen inside the delegation pool.

**Root cause — `staking_contract::set_beneficiary_for_operator`** [3](#0-2) 

Same missing check. When `distribute_internal` runs, it resolves the operator's recipient to `beneficiary_for_operator(operator)` = `@0x0` and calls: [4](#0-3) 

`aptos_account::deposit_coins(@0x0, ...)` will attempt `account::create_account(@0x0)` if the account does not exist. `@0x0` is `@vm_reserved`, a reserved system address. The framework explicitly guards against this in `vesting::create_vesting_contract`: [5](#0-4) 

No equivalent guard exists in `staking_contract::set_beneficiary_for_operator`. If `create_account(@0x0)` aborts (reserved address), the entire `distribute_internal` call aborts, permanently blocking all distributions — including the staker's own stake withdrawals. If `@0x0` already has an account, the commission coins are deposited there and permanently lost.

---

### Impact Explanation

| Scenario | Affected party | Asset | Outcome |
|---|---|---|---|
| `delegation_pool` — beneficiary set to `@0x0` | Operator | APT commission (staking balance) | Permanently locked in pool; shares owned by `@0x0` can never be redeemed |
| `staking_contract` — beneficiary set to `@0x0`, `create_account(@0x0)` aborts | Staker + Operator | APT stake + commission | `distribute_internal` permanently aborts; staker cannot withdraw |
| `staking_contract` — beneficiary set to `@0x0`, `@0x0` account exists | Operator | APT commission | Coins deposited to `@0x0`, permanently lost |

Both paths satisfy the allowed impact gate: **permanent freezing or burning of APT staking balances** caused by an **unprivileged transaction** (any operator can call `set_beneficiary_for_operator`).

---

### Likelihood Explanation

- Both functions are `public entry`, callable by any operator on mainnet today.
- An operator could trigger this accidentally (e.g., a front-end bug, a calling contract that passes a default-zero address) or deliberately (griefing a staker by freezing distributions).
- No existing guard prevents `@0x0` from being stored as the beneficiary.
- The commission-locking path in `delegation_pool` is deterministic and requires no special conditions beyond calling the function with `@0x0`.

---

### Recommendation

Add a zero-address / reserved-address guard in both functions, mirroring the pattern already used in `vesting::create_vesting_contract`:

```move
// delegation_pool.move  set_beneficiary_for_operator
assert!(
    new_beneficiary != @0x0 && !system_addresses::is_reserved_address(new_beneficiary),
    error::invalid_argument(EINVALID_BENEFICIARY_ADDRESS)
);

// staking_contract.move  set_beneficiary_for_operator
assert!(
    new_beneficiary != @0x0 && !system_addresses::is_reserved_address(new_beneficiary),
    error::invalid_argument(EINVALID_BENEFICIARY_ADDRESS)
);
```

Additionally, consider requiring that `new_beneficiary` has an existing account registered for APT (analogous to the `assert_account_is_registered_for_apt` check in `vesting::set_beneficiary`): [6](#0-5)

### Proof of Concept

**Delegation pool path (commission permanently locked):**

```
1. Operator O controls a delegation pool P with active delegators.
2. O calls: delegation_pool::set_beneficiary_for_operator(O_signer, @0x0)
   → BeneficiaryForOperator { beneficiary_for_operator: @0x0 } stored under O's address.
   → No abort; no validation.

3. Any account calls: delegation_pool::synchronize_delegation_pool(pool_address)
   → calculate_stake_pool_drift computes commission_active > 0.
   → buy_in_active_shares(pool, beneficiary_for_operator(@operator) = @0x0, commission_active)
   → pool.active_shares now records @0x0 as owner of commission_active worth of shares.

4. @0x0 can never sign a transaction.
   → Those shares — and the APT they represent — are permanently frozen in the pool.
   → Every future epoch repeats step 3, compounding the locked amount.
```

**Staking contract path (all distributions blocked):**

```
1. Operator O has a staking contract with staker S.
2. O calls: staking_contract::set_beneficiary_for_operator(O_signer, @0x0)
   → BeneficiaryForOperator { beneficiary_for_operator: @0x0 } stored.

3. Anyone calls: staking_contract::distribute(S_address, O_address)
   → distribute_internal runs.
   → recipient = beneficiary_for_operator(O) = @0x0
   → aptos_account::deposit_coins(@0x0, commission_coins)
     → account::exists_at(@0x0) == false (or true but reserved)
     → create_account(@0x0) aborts (reserved address)
   → distribute_internal aborts entirely.

4. S's stake withdrawal is permanently blocked.
   S cannot recover funds without O changing the beneficiary back —
   but O has no incentive to do so (griefing vector).
```

    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
