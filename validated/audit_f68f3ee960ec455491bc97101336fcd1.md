### Title
Out-of-bounds array read/`ArrayIndexOutOfBoundsException` in `PrecompiledContracts.extractBytes32Array`/`extractBytesArray` due to unvalidated ABI-decoded lengths - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2016-8681 is a class of bug where an attacker-controlled length/index field parsed from a crafted input is used directly to index/iterate an array without validating it against the actual buffer bounds, producing an out-of-bounds read. The analogous pattern in java-tron is `extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java`, which decode ABI-style dynamic array lengths/offsets straight from the `DataWord[] words` array (derived from TVM call/precompile input data) and use them to index into that same array without checking against `words.length`.

### Finding Description
`extractBytes32Array` reads a length word at `words[offset]` and then loops `bytes32Array[i] = words[offset + i + 1].getData()` for `i` in `[0, len)` with no check that `offset + i + 1 < words.length`: [1](#0-0) 

`extractBytesArray` is only slightly more defensive — it checks `offset > words.length - 1` once at the start, but the subsequently computed `bytesOffset`, `bytesLen`, and the per-element loop index `words[offset + i + 1]` are never re-validated against `words.length`, so a crafted `len` (attacker-controlled via `words[offset].intValueSafe()`) or crafted `bytesOffset` can still walk past the end of the `words` array: [2](#0-1) 

These helpers are used by the precompiled-contract implementations (e.g. batch/array-based verify precompiles) that are invoked from within TVM contract execution when a deployed smart contract calls one of these precompiled addresses. The `words` array itself is built by chunking the raw call `data` supplied in the transaction/contract call, so an unprivileged contract deployer/caller fully controls the length field and the total size of `data`, letting them supply a `len` value inconsistent with the actual number of words present.

### Impact Explanation
An out-of-bounds array access here throws an unchecked `ArrayIndexOutOfBoundsException` inside TVM opcode/precompile execution. Depending on how the exception propagates through `VM.play`/`Program`, this is either caught as a generic `RuntimeException` (causing the transaction to fail with energy consumed, which is a normal revert path) or, if it escapes unexpected paths, could produce inconsistent behavior across nodes if the exception isn't uniformly caught in every code path that invokes these helpers. Because TVM execution is part of consensus-critical block application, any code path where such an exception is not deterministically and identically handled across implementations risks a state-divergence / consensus-related class of impact, which is the highest realistic severity here. If the exception is always caught generically as `RuntimeException` and always fails the transaction deterministically (as `VM.play` appears to do), the practical impact is limited to a per-transaction revert (denial of service for that transaction only), not corruption of node state.

### Likelihood Explanation
Reaching this code requires only deploying/calling a contract that invokes the affected precompiled contract with crafted call data — no special privileges are needed, matching the "unprivileged contract deployer/caller" reachability required by the rules. The length/offset values are directly derived from attacker-supplied call data (`words[offset].intValueSafe()`), so triggering an out-of-range index is straightforward.

### Recommendation
In `extractBytes32Array` and `extractBytesArray`, validate that `len` and all derived offsets (`offset + i + 1`, `bytesOffset + offset + 2`, etc.) are within `words.length` (and within the bounds of `data` for `extractBytes`) before use, throwing a well-defined `Program.Exception`/validation error instead of allowing an uncontrolled `ArrayIndexOutOfBoundsException` to propagate. Ensure any such exception is uniformly caught and converted into a deterministic transaction failure across all precompile call sites.

### Proof of Concept
1. Deploy a contract that calls the precompiled contract address whose implementation invokes `extractBytes32Array`/`extractBytesArray` (e.g., a batch-verification precompile that takes a dynamic byte32/bytes array parameter).
2. Craft the calldata so that the length word at the expected `offset` position (`words[offset].intValueSafe()`) is set to a large value (e.g., far exceeding the number of remaining words actually supplied in `data`), while keeping the overall `data` short.
3. Invoke the contract function; the precompile's array-extraction helper will attempt to read `words[offset + i + 1]` past the end of the actual `words` array, producing an out-of-bounds access.

I was not able to fully confirm (due to tool/output truncation in the final iteration) which specific precompiled contract(s) call `extractBytes32Array`/`extractBytesArray`, nor trace the exact exception-handling path from these helpers back through `Program`/`VM.play` to determine with certainty whether the resulting exception is always caught deterministically. If this needs to be verified further, a Devin session with full file access would be needed to enumerate all call sites of these two methods within `PrecompiledContracts.java` and confirm the exception-propagation behavior end-to-end.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
