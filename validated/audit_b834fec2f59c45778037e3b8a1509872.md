### Title
Remote panic (assertion failure) on minimal StacksMessageType::Blocks/Microblocks push - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_blocks_push` and `validate_microblocks_push` assert an invariant about `Preamble.payload_len` that the wire-level preamble parser does not actually guarantee, so a peer that has completed a handshake (no node secret or privileged role required) can send a minimally-sized `Blocks`/`Microblocks` push message that satisfies the parser's own minimum-length check but violates the stricter assumption baked into the handler, triggering a Rust `assert!` panic. This mirrors the TensorFlow class of bug in the report: a downstream code path assumes an implicit non-emptiness/size invariant on attacker-supplied data that the upstream parser does not enforce, and hits an `assert`/precondition failure instead of returning a graceful error.

### Finding Description
`Preamble::consensus_deserialize` only enforces a generic minimum payload length of 5 bytes for *any* message type: [1](#0-0) 
This 5-byte minimum corresponds to a message consisting of nothing but a 1-byte type prefix and a 4-byte zero-length vector — i.e., the smallest possible encoding of an "empty vector" payload such as an empty `BlocksData`/`MicroblocksData`.

Downstream, `handle_data_message` routes any inbound `StacksMessageType::Blocks` or `StacksMessageType::Microblocks` message (after the peer is authenticated via handshake, which requires no secret/privileged key) to `validate_blocks_push` / `validate_microblocks_push`: [2](#0-1) 

Those handlers immediately execute: [3](#0-2) [4](#0-3) 

Both assert `preamble.payload_len > 5`, i.e., they assume the payload must be *strictly greater* than the theoretical empty-vector minimum. But the preamble parser only guarantees `payload_len >= 5` (5 is explicitly allowed), so a peer can send a message whose `Preamble.payload_len` is exactly 5 while `StacksMessageType` is `Blocks`/`Microblocks` with an empty vector — the field-level equality "payload_len must exceed the reserved empty-vector prefix size" is broken at the boundary the assertion checks. When this exact-5 case occurs, the `assert!` fails and panics inside the peer's conversation-processing code path, which is invoked directly off network I/O.

This is the direct in-repo analog of the TensorFlow bug class: the external report describes a parser that accepts "empty" structurally-valid-but-semantically-degenerate input (empty `ret`/`input` fields) that a downstream consumer assumes cannot occur, leading to an assertion failure/crash. Here, the wire-level `Preamble` parser accepts a degenerate (`payload_len == 5`) message that the message-type-specific handler assumes cannot occur, and that mismatch is enforced via a live `assert!` rather than a `Result`-returning check.

### Impact Explanation
An `assert!` panic in this call path is a remote, low-effort denial-of-service: a single small, well-formed (from the perspective of the P2P codec) message from any peer that has merely completed the handshake state machine (no secret key, no elevated privilege, no signer role) will unwind/abort the thread handling that peer's conversation. Depending on how panics propagate in the connection-handling runtime (thread-per-connection or a shared event loop), this can kill the P2P connection-processing thread, potentially taking down the whole node process if the panic is not caught with `catch_unwind` at a higher level (not established in what was reviewed). This falls under "Critical - remote crash/unauthenticated DoS from few messages" in the rules, since the pushing peer needs only to be a network peer that has completed a normal handshake — a bar any anonymous remote actor can clear.

### Likelihood Explanation
Likelihood is high: the trigger requires only crafting an authentic-looking `Preamble` with `payload_len = 5` and a `StacksMessageType::Blocks` or `Microblocks` payload serializing to exactly an empty-vector body (1-byte type tag + 4 zero bytes for vector length), signed with the attacker's own key over their own handshake session (standard P2P protocol signing, not requiring the victim's key). No rate limiting or additional authorization gates this specific boundary check; it is hit on the very first such message.

### Recommendation
Replace the `assert!(preamble.payload_len > 5)` / `assert!(preamble.payload_len > 1)` invariants in `validate_blocks_push`, `validate_microblocks_push`, `validate_transaction_push`, and `validate_stackerdb_push` with graceful `Result`-based validation (e.g., return `Err(net_error::InvalidMessage)` or NACK the peer) instead of panicking, mirroring how other malformed-input paths in this file are handled. Additionally, consider tightening `Preamble::consensus_deserialize`'s minimum-length check per message type (or performing the length check after the message type is known) so that boundary values consistent with "empty vector" payloads for size-sensitive message types are rejected before reaching handler code that assumes a stricter invariant.

### Proof of Concept
1. Complete a normal P2P handshake with the victim node as any remote peer (standard, unauthenticated-by-secret handshake flow).
2. Construct a `StacksMessage` whose `payload` is `StacksMessageType::Blocks(BlocksData { blocks: vec![] })` (or the analogous empty `MicroblocksData`), with an empty `relayers` vector, and sign/serialize it normally so the wire-level `Preamble.payload_len` computes to exactly `5`.
3. Send the message to the victim node's P2P port.
4. On receipt, `ConversationP2P::handle_data_message` dispatches to `validate_blocks_push` (or `validate_microblocks_push`), which executes `assert!(preamble.payload_len > 5)`; because `payload_len == 5`, the assertion fails and the thread panics.

*Note: I was not able to fully verify from the indexed code whether a panic in this specific call stack is caught by an outer `catch_unwind` (which would downgrade the impact to a single dropped connection rather than a process crash); a Devin session with full repo/build access would be needed to trace the P2P thread/panic-handling architecture (e.g., in `stackslib/src/net/p2p.rs` or the node's main event loop) to confirm blast radius.*
