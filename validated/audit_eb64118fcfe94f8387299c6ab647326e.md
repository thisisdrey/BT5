### Title
`Pool.swap` lacks user-controlled slippage tolerance — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.swap(syntheticTokenIn_, syntheticTokenOut_, amountIn_)` burns the caller's synthetic tokens and mints a different synth at an amount computed entirely inside the transaction (`quoteSwapOut` → `masterOracle().quote` → `feeProvider.swapFees`). There is no `amountOutMin_`/slippage parameter, so the caller commits `amountIn_` without any bound on what they receive back.

### Finding Description
In `contracts/Pool.sol:642-671`, `swap()` first burns `syntheticTokenIn_` from `_msgSender`, then computes `_amountOut` and `_fee` via `quoteSwapOut` (`contracts/Pool.sol:508-525`), which prices the trade with `masterOracle().quote(tokenIn, tokenOut, amountIn_)` and deducts the swap fee. The result is minted unconditionally — no check against a user-supplied minimum:

```solidity
syntheticTokenIn_.burn(_msgSender, amountIn_);
(_amountOut, _fee) = quoteSwapOut(syntheticTokenIn_, syntheticTokenOut_, amountIn_);
...
syntheticTokenOut_.mint(_msgSender, _amountOut);
```

The interface (`contracts/interfaces/IPool.sol:100-104`) confirms the signature has no slippage parameter. Other user-facing exchange paths in the same codebase do carry slippage params — `SmartFarmingManager.leverage` takes `depositAmountMin_` and `flashRepay` takes `swapAmountOutMin_` (`contracts/SmartFarmingManager.sol:98-127, 155-162`) — showing the protocol recognizes this protection but omits it on `Pool.swap`. `Pool.liquidate` likewise prices seized collateral purely off `quoteLiquidateOut` with no liquidator-supplied bound (`contracts/Pool.sol:537-596`).

Because `_amountOut` depends on oracle quotes evaluated at execution time, a caller quoting `quoteSwapOut` pre-transaction has no protection if the effective price or fee moves between submission and execution — e.g., an attacker front-running a legitimate oracle update, or moving an oracle-derived rate within the same block so the victim's swap executes at a worse rate than quoted. The user's input tokens are already burned before the output is computed, so the loss is realized in the same transaction.

### Impact Explanation
Direct loss of user funds: a swapper's `syntheticTokenIn_` is burned and they can receive arbitrarily less `syntheticTokenOut_` than the value they observed when submitting. There is no revert path for a worse-than-expected output; the only guards are `whenNotShutdown`, `nonReentrant`, `isSwapActive`, and a balance check — none bound the exchange rate.

### Likelihood Explanation
Exploitation requires the quoted rate to move adversely between the victim's quote/simulation and execution. Feasible vectors for an unprivileged attacker: front-running oracle price updates on chains where the mempool is observable, or manipulating an oracle source that derives prices from on-chain state within the same transaction/block. Severity is bounded by how much the underlying oracle rate can move — this is a Medium-severity user-protection gap rather than a protocol solvency issue, matching the source report's classification.

### Recommendation
Add a user-supplied minimum output parameter, e.g. `swap(syntheticTokenIn_, syntheticTokenOut_, amountIn_, amountOutMin_)`, and revert if `_amountOut < amountOutMin_` after the `quoteSwapOut` call in `Pool.swap`. Apply the same pattern to `Pool.liquidate` (e.g., a `_toLiquidator` minimum / `totalSeized` bound) so liquidators can bound the collateral they receive per unit repaid.

### Proof of Concept
Hardhat outline against the existing `Pool.test.ts` fixture:

```typescript
// 1. Alice holds msETH; quotes swap msETH -> msUSD
const amountIn = parseEther('1');
const { _amountOut: quoted } = await pool.quoteSwapOut(msETH.address, msUSD.address, amountIn);

// 2. Between quote and execution, the ETH/USD oracle rate moves adversely
//    (attacker front-runs an oracle update, or manipulates the oracle source
//    in the same block). Simulate by updating the mocked oracle price down 10%.
await masterOracle.updatePrice(msETH.address, ethPrice.mul(90).div(100));

// 3. Alice's swap still executes — no minOut check — and she receives ~10% less
await msETH.connect(alice).approve(pool.address, MaxUint256);
const tx = await pool.connect(alice).swap(msETH.address, msUSD.address, amountIn);

// 4. Assert received amount < quoted amount; nothing reverts despite the loss
const received = await msUSD.balanceOf(alice.address);
expect(received).lt(quoted); // loss realized, user had no way to bound it
```

Invariant broken: the user's committed input is exchanged at a rate they never consented to, with no revert bound — identical bug class to the Stader report (missing `minOut` on asset-exchange entry points).
