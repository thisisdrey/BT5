### Title
Non-constant-time comparison of privileged API auth tokens enables remote timing side-channel recovery of the secret, leading to authentication bypass - ([File: stackslib/src/net/api/postblock_v3.rs])

### Summary
Several privileged, state-mutating/compute-heavy RPC handlers gate access with a shared-secret `Authorization` header, but compare the received header against the configured secret using a plain, early-exiting byte-wise `!=` string comparison instead of a constant-time comparison. This mirrors the CWE-294-adjacent bug class in the reference advisory (an authentication check that should enforce a strict equality/uniqueness invariant but does not do so robustly), producing an exploitable inequality between "attacker-supplied credential" and "actual stored credential" that can be probed remotely.

### Finding Description
The following handlers all gate privileged behavior behind a single shared secret compared with `auth_header != password`:

- `RPCPostBlockRequestHandler::try_parse_request` — gates whether an unauthenticated POST to `/v2/blocks` may set `broadcast=1` (network-wide block broadcast) [1](#0-0) 
- `RPCBlockProposalRequestHandler::try_parse_request` — gates `/v3/block_proposal`, used by the signer set to validate block proposals [2](#0-1) 
- `RPCFastCallReadOnlyRequestHandler::try_parse_request` — gates `/v3/contracts/fast-call-read/...` [3](#0-2) 
- `RPCTransactionSimulateRequestHandler::try_parse_request` — gates `/v3/transactions/simulate` [4](#0-3) 
- `RPCNakamotoBlockReplayRequestHandler::try_parse_request` — gates `/v3/blocks/replay/:block_id` [5](#0-4) 
- `blocksimulate.rs` contains the same `auth_header` check pattern (confirmed via grep, but exact line range not retrieved due to iteration limits).

In each case, the comparison is:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
Rust's `String`/`&str` `PartialEq` implementation (via `str::eq`) performs a length check followed by a byte-wise comparison that returns as soon as a mismatch is found (this is the standard library behavior backing `==`/`!=` for strings/slices). This means the time taken to reject an incorrect `Authorization` header is a function of how many leading bytes of the guess match the real secret (`self.auth_token` / `connection_options.auth_token`) documented as the shared secret in `docs/rpc/openapi.yaml` [6](#0-5)  and in the config docs [7](#0-6) .

An unauthenticated remote attacker can repeatedly submit guesses (byte-by-byte or via a divide/measure strategy) and use response-timing statistics to recover the `auth_token` without ever needing the node operator's secret. Once the token is recovered, the attacker gains legitimate write access to `/v2/blocks?broadcast=1` (force network-wide broadcast of an attacker-supplied Stacks block, cf. `RPCPostBlockRequestHandler`) and to `/v3/block_proposal` (impersonate the signer-authenticated block-proposal channel), both of which are explicitly described as protected only by this shared secret [7](#0-6) .

This breaks exactly the kind of equality invariant called out in the rules ("authenticated vs. stored") — the check that should robustly assert `attacker_header == stored_secret` leaks information through timing, degrading a binary secret-equality check into an oracle.

### Impact Explanation
If exploitable in practice, this allows a remote, unauthenticated attacker to eventually recover `connection_options.auth_token` and then:
- Force broadcast of an attacker-chosen Stacks block via `/v2/blocks?broadcast=1`, an unauthorized write with network-wide propagation.
- Submit forged block proposals to `/v3/block_proposal`, spoofing the signer-authenticated channel (auth bypass).

This matches the "Critical" bucket in the rules: "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data ... auth bypass."

### Likelihood Explanation
Exploitability is bounded by network jitter, which makes timing side-channels harder to exploit over the open internet but is a well-established, practical attack class against unauthenticated HTTP token comparisons (particularly effective on LANs, in cloud environments with low-jitter paths, or when the attacker can average over many requests). The node operator must have configured `auth_token` for these endpoints to be reachable at all (otherwise the handler returns `400 Bad Request` before ever reaching the comparison, per the `Some(password) = &self.auth` gate). Given that, likelihood is Medium: the vulnerable code path exists on every node that enables the signer/broadcast auth token, and no additional privilege or secret is needed by the attacker.

### Recommendation
Replace all instances of `auth_header != password` (and the analogous check in `blocksimulate.rs`) with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq`, or a manual XOR-accumulate comparison that always processes the full length of both strings regardless of where they diverge. Apply this uniformly across `postblock_v3.rs`, `postblock_proposal.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, `blockreplay.rs`, and `blocksimulate.rs`.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"` and expose `/v3/block_proposal`.
2. From a low-jitter network path, send repeated `POST /v3/block_proposal` requests with `Authorization` headers that are prefixes of increasing correctness (e.g., brute-force byte 0, then byte 1, etc., choosing the guess with the statistically highest average response latency at each position, since a longer common prefix means more comparison iterations before the mismatching byte is hit).
3. Aggregate timing samples per candidate byte to reduce noise; repeat until the full token is recovered.
4. Use the recovered token to POST a forged block to `/v2/blocks?broadcast=1` or a forged proposal to `/v3/block_proposal`.

Note: I was not able to inspect the exact code in `stackslib/src/net/api/blocksimulate.rs` due to tool-call limits in this session, only confirmed via grep that it contains the same `auth_header` comparison pattern as the other five handlers; a follow-up review of that file is recommended to confirm it uses the identical vulnerable pattern.
