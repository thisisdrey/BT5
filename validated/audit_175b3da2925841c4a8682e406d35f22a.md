### Title
Unbounded, attacker-growable witness list is iterated multiple times per maintenance cycle, enabling a consensus-halting DoS - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
`MaintenanceManager.doMaintenance()` is executed by every full node/SR at every maintenance cycle boundary (a fixed, periodic point during block application, not opt-in). Inside it, `consensusDelegate.getAllWitnesses()` — which returns *every* entry ever written to `WitnessStore`, not just the ~27 active/standby witnesses — is iterated several times with per-witness DB reads/writes [3](#0-2) . This mirrors the reported `onlyAllowed()` bug class: a persisted, append-only list with no bound and no removal, exhaustively scanned on a codepath that executes automatically and periodically for every participant of the system.

### Finding Description
Any account can call `WitnessCreateActuator` via a normal `WitnessCreateContract` transaction, paying `dynamicStore.getAccountUpgradeCost()` (a fixed, one-time TRX fee), to add a new entry to `WitnessStore` [4](#0-3) . The only guard in `validate()` is a check that the exact same owner address hasn't already registered as a witness — there is no cap on the total number of witnesses in the store, and there is no contract type or actuator that removes an entry from `WitnessStore` [5](#0-4) .

`WitnessStore.getAllWitnesses()` performs a full iteration over the entire underlying LevelDB/RocksDB column for the store [6](#0-5) . `MaintenanceManager.doMaintenance()`, which runs automatically at every maintenance cycle boundary via `applyBlock()` (part of normal block application in `Manager`), calls `consensusDelegate.getAllWitnesses()` up to four separate times in a single maintenance pass, each followed by a `forEach` that performs additional per-entry store reads and writes (`getWitness`, `saveWitness`, `accumulateWitnessVi`, `setBrokerage`, `setWitnessVote`) [7](#0-6) . Because each of these iterations is O(n) over the full witness count and n can be inflated indefinitely by an unprivileged attacker at a small fixed per-entry cost, the cost of every maintenance cycle for every node in the network grows linearly (and, given the compounded number of loops, effectively worse) with the number of witnesses ever created — with no way to reduce that count afterward.

### Impact Explanation
Maintenance cycles occur automatically and deterministically for every full node and super representative (roughly every 6 hours, or per the configured maintenance interval) as part of ordinary block application — this is not something operators can disable per-node. If an attacker inflates the total witness count sufficiently (each unit of cost being a one-time, fixed TRX fee with no ongoing cost or scarcity), the per-cycle CPU and I/O time in `doMaintenance()` grows without bound, which can cause maintenance processing (and thus block production/synchronization) to fall behind or stall across the network — a chain-wide liveness/availability issue rather than a single node's local resource problem, since the same growable, unremovable state is iterated by all nodes.

### Likelihood Explanation
The precondition (creating a witness) is available to any account with sufficient balance to pay `getAccountUpgradeCost()`, requires no special privilege, election win, or governance action, and is directly reachable via a broadcastable `WitnessCreateContract` transaction. The only friction is the linear cost of the create fee times the number of entries the attacker wants to add; because there is no decay or removal, the cost is one-time and the effect (padding the iterated list) is permanent.

### Recommendation
Bound the resource cost of maintenance processing so it no longer scales with an attacker-controllable, unbounded list:
- Cap the number of registrable witnesses (e.g., enforce a maximum entry count in `WitnessCreateActuator.validate()`), and/or
- Avoid iterating the entire raw `WitnessStore` in `doMaintenance()`/reward and vote-accumulation logic; instead maintain and iterate only the bounded, already-tracked active/standby witness set (as is already done for `getActiveWitnesses()`), or maintain an auxiliary index/limit structure (analogous to the reported `mapping(address => bool)` fix) so per-cycle cost does not grow with total historical witness registrations.
- Consider charging an ongoing (not one-time) cost for remaining registered, or provide/require removal of "abandoned" witnesses with zero votes after some period, to prevent unbounded accumulation.

### Proof of Concept
1. Attacker repeatedly submits `WitnessCreateContract` transactions from N distinct funded accounts, each paying `AccountUpgradeCost`, to create N witness entries in `WitnessStore` (no removal path exists) [8](#0-7) .
2. At the next maintenance cycle boundary, `MaintenanceManager.doMaintenance()` runs automatically as part of `applyBlock()` for every node, performing multiple O(N) scans of `consensusDelegate.getAllWitnesses()` with per-entry store operations [7](#0-6) .
3. As N grows, the wall-clock time each node spends per maintenance cycle grows proportionally (compounded across the ~4 separate full scans), degrading or potentially stalling block production/synchronization network-wide, with no mechanism to reverse the accumulated state.

      dynamicStore.burnTrx(cost);

  public void doMaintenance() {
    VotesStore votesStore = consensusDelegate.getVotesStore();

    tryRemoveThePowerOfTheGr();

    DynamicPropertiesStore dynamicPropertiesStore = consensusDelegate.getDynamicPropertiesStore();
    DelegationStore delegationStore = consensusDelegate.getDelegationStore();
    if (dynamicPropertiesStore.useNewRewardAlgorithm()) {

      consensusDelegate.getAllWitnesses().forEach(witness -> {
        delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount());
      });
    }

    Map<ByteString, Long> countWitness = countVote(votesStore);
    if (!countWitness.isEmpty()) {
      List<ByteString> currentWits = consensusDelegate.getActiveWitnesses();

      List<ByteString> newWitnessAddressList = new ArrayList<>();
      consensusDelegate.getAllWitnesses()
          .forEach(witnessCapsule -> newWitnessAddressList.add(witnessCapsule.getAddress()));

      countWitness.forEach((address, voteCount) -> {
        byte[] witnessAddress = address.toByteArray();
        WitnessCapsule witnessCapsule = consensusDelegate.getWitness(witnessAddress);
        if (witnessCapsule == null) {
          logger.warn("Witness capsule is null. address is {}", Hex.toHexString(witnessAddress));
          return;

        AccountCapsule account = consensusDelegate.getAccount(witnessAddress);
        if (account == null) {
          logger.warn("Witness account is null. address is {}", Hex.toHexString(witnessAddress));
          return;
        }
        witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
        consensusDelegate.saveWitness(witnessCapsule);
        logger.info("address is {} , countVote is {}", witnessCapsule.createReadableString(),
            witnessCapsule.getVoteCount());
      });

      dposService.updateWitness(newWitnessAddressList);

      incentiveManager.reward(newWitnessAddressList);

      List<ByteString> newWits = consensusDelegate.getActiveWitnesses();
      if (!CollectionUtils.isEqualCollection(currentWits, newWits)) {

          WitnessCapsule witnessCapsule = consensusDelegate.getWitness(address.toByteArray());
          witnessCapsule.setIsJobs(true);
