## Title
Protocol fee on `TokenDiff` swaps can be fully bypassed by splitting a fungible `Nep245`/`Imt` trade into unit-sized (`|delta| == 1`) intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee()` waives the protocol fee whenever the traded amount of a `Nep245` (multi-token) or `Imt` (intents-mintable token) `TokenId` is `<= 1`. This exemption is intended for true NFT-style single-unit transfers, but `Nep245`/`Imt` token ids are also used to carry ordinary fungible balances with arbitrary decimals (e.g. `ImtMint`/`ImtBurn` tests move amounts like `1000` of these same token types). Because the fee is evaluated per-`TokenDiff` intent on that intent's own delta, and a signer may bundle/execute an arbitrary number of `TokenDiff` intents (each with `delta == ±1` on the same `Nep245`/`Imt` token) in place of one intent with `delta == N`, the effective protocol fee on such swaps can be reduced to zero regardless of the configured `Pips` fee.

### Finding Description
`TokenDiff::execute_intent` computes the fee for each token leg independently, using only that single intent's delta amount: [1](#0-0) 

The fee-rate lookup explicitly zeroes the fee for `Nep245`/`Imt` (and `Nep171`) token types whenever the absolute delta is `<= 1`: [2](#0-1) 

`Nep245`/`Imt` are not restricted to non-fungible, single-unit semantics — `ImtMint`/`ImtBurn` (and the underlying `Amounts<BTreeMap<TokenId,u128>>` representation) freely move arbitrary integer amounts of these token kinds, e.g. minting/burning `amount = 1000` of an `ImtTokenId`: [3](#0-2) [4](#0-3) 

A single signed `MultiPayload` can contain many `Intent`s (a `DefuseIntents.intents: Vec<Intent>`), and `execute_signed_intents` simply iterates and executes each signed payload's intents under one signature/nonce commit: [5](#0-4) 

Because the fee decision is made per `TokenDiff` intent (not per signer, per batch, or per cumulative token-flow), a trade that would otherwise pay `fee = Pips.fee_ceil(amount)` on a `Nep245`/`Imt` leg of size `amount` can instead be expressed as `amount` separate `TokenDiff` intents each moving `delta = ±1` of that token (paired between the two counterparties, or self-paired by one account controlling both legs). Each of those unit intents hits the `amount <= 1` branch of `token_fee()` and returns `Pips::ZERO`, so `fee_ceil(1) == 0` for every leg, and the sum of collected fees across the whole batch is `0` instead of the fee that would have been collected on the equivalent single `amount`-sized trade.

This breaks the "fees owed versus fees collected" binding: the protocol-configured fee rate (`engine.state.fee()`) is supposed to apply uniformly to negative deltas (token_in) regardless of how the same net economic transfer is chunked into intents.

### Impact Explanation
This falls under the explicitly listed Critical impact category "fees bypassed... or over-collected." Any solver, market maker, or self-trading account can restructure legitimate `Nep245`/`Imt` swaps into unit-sized token diffs to pay zero protocol fee, directly reducing fee-collector revenue for every swap routed through these token kinds. Because `Imt` tokens are explicitly designed to represent arbitrary minted balances (not just NFTs), and `Nep245` covers general multi-token/semi-fungible assets, this is not a narrow edge case restricted to genuine 1-of-1 NFTs — it applies to any fungible-like balance issued under these `TokenId` variants.

### Likelihood Explanation
Exploitation only requires the ability to sign multiple `TokenDiff` intents (which any account holder or solver already can do) and to bundle them into one `execute_intents` call, which is standard usage of the protocol (batches of signed intents from cooperating counterparties, e.g. solver + user, are the normal RFQ pattern demonstrated in the test suite). No privileged role, relayer key, or contract upgrade is required. The number of unit intents needed scales with the traded amount, so it is most attractive for tokens with coarse-grained/low-decimal balances where `amount = 1` still represents meaningful value, but any amount can, in principle, be decomposed into unit legs at the cost of extra signatures/gas.

### Recommendation
- Do not exempt `Nep245`/`Imt` from fees based solely on the per-intent delta magnitude; if the intent is to exempt genuine NFTs, gate the exemption on `TokenIdType::Nep171` only, or on a token-level "is-NFT" flag/registry rather than an amount threshold that fungible-style `Nep245`/`Imt` balances can trivially satisfy by chunking.
- If a `<= 1` exemption must remain for multi-token semantics, compute/aggregate fees over the *net* delta per `(signer, token_id)` across the whole batch of intents in an `execute_intents` call (or across a rolling window), rather than per individual `TokenDiff` intent, so that splitting one large trade into many unit trades cannot evade the fee.

### Proof of Concept
Given a protocol fee `Pips = P > 0` and an `Imt`/`Nep245` token `T` with true intended swap size `amount = N` between a `signer` and a `solver`:

1. Single-intent case (fee correctly charged): `TokenDiff { diff: { T: -N, other_token: +M } }` → `token_fee(T, N, P) = P` (since `N > 1`) → fee charged: `P.fee_ceil(N) > 0`, see [6](#0-5) 

2. Split-intent case (fee bypassed): the same net trade is instead expressed as `N` separate signed `TokenDiff` intents, each `{ diff: { T: -1, other_token: +(M/N) } }` (paired with matching `+1`/`-(M/N)` counter-intents from the solver), bundled into one `execute_intents(signed: Vec<MultiPayload>)` call per [7](#0-6) .
For each of these `N` intents, `token_fee(T, 1, P)` hits the exemption branch and returns `Pips::ZERO`: [2](#0-1) 
so `fees_collected` for token `T` accumulates to `0` across the whole batch, versus `P.fee_ceil(N)` in the single-intent case — a full fee bypass for identical net economic effect.

**Note on verification limits:** I was not able to inspect the exact `Amounts::add`/collision semantics for `fees_collected` batching across multiple intents from different signers in the same `execute_intents` call, nor the full gas cost model for very large `N`, within the available indexed context. A Devin session with full repo/tooling access would be needed to build and run an integration test (in `tests/src/tests/defuse/intents/token_diff.rs`) that concretely measures `fees_collected` for the single-intent vs. split-intent scenarios and confirms the discrepancy end-to-end.

    pub fn execute_signed_intents(
        mut self,
        signed: impl IntoIterator<Item = MultiPayload>,
    ) -> Result<Transfers> {
        for signed in signed {
            self.execute_signed_intent(signed)?;
        }
        self.finalize()
    }

    fn execute_signed_intent(&mut self, signed: MultiPayload) -> Result<()> {
        // verify signed payload and get public key
        let public_key = signed.verify().ok_or(DefuseError::InvalidSignature)?;

        // calculate intent hash
        let hash = signed.hash();

        // extract NEP-413 payload
        let DefusePayload::<DefuseIntents> {
            signer_id,
            verifying_contract,
            deadline,
            nonce,
            message: intents,
        } = signed.extract_defuse_payload()?;

        // check recipient
        if verifying_contract != *self.state.verifying_contract() {
            return Err(DefuseError::WrongVerifyingContract);
        }

        self.inspector.on_deadline(deadline);

        // make sure message is still valid
        if deadline < Timestamp::now() {
            return Err(DefuseError::DeadlineExpired);
        }

        // make sure the account has this public key
        if !self.state.has_public_key(&signer_id, &public_key) {
            return Err(DefuseError::PublicKeyNotExist(signer_id, public_key));
        }

        // commit nonce
        self.verify_intent_nonce(nonce, deadline)?;
        self.state.commit_nonce(signer_id.clone(), nonce)?;

        intents.execute_intent(&signer_id, self, hash)?;
        self.inspector.on_intent_executed(&signer_id, hash, nonce);

        Ok(())
    }
