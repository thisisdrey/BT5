### Title
`AddKey` with `is_limited_allowance=true, allowance=0` silently produces an `Allowance::Unlimited` access key instead of a zero-spend key - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`action_to_promise` builds the `FunctionCall` access-key allowance via `access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)`. Since `near_sdk::Allowance::limited` is backed by `NonZeroU128` and returns `None` for a zero value, an explicitly-declared `Some(0)` allowance collapses through the `.and_then(...).unwrap_or(Allowance::Unlimited)` chain into `Allowance::Unlimited`, silently converting an intended "no spending power" restricted key into an unlimited-allowance key.

### Finding Description
The ABI decodes `AddKey` fields including `is_limited_allowance: bool` and `allowance: u128` [1](#0-0) . When building the near action, `is_limited_allowance` gates whether `allowance` is wrapped in `Some`: `let allowance = if is_limited_allowance { Some(allowance) } else { None };` [2](#0-1) . With `is_limited_allowance=true` and `allowance=0`, this yields `access.allowance = Some(NearToken::from_yoctonear(0))`, a `near_action::FunctionCallPermission` that explicitly states "limited to zero."

That value later reaches `action_to_promise`: [3](#0-2) 
`access.allowance.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)` calls `Allowance::limited(NearToken(0))`. Per `near_sdk`'s `Allowance` type (backed by `NonZeroU128::new`), a zero input yields `None`, and the `.unwrap_or(Allowance::Unlimited)` fallback then substitutes `Allowance::Unlimited`. There is no explicit-zero-vs-unset distinction preserved through this chain: both "caller did not set `is_limited_allowance`" (i.e., truly wants unlimited) and "caller set `is_limited_allowance=true` with `allowance=0`" (i.e., wants zero/no spend) collapse to the same `Allowance::Unlimited` result.

Nothing in `inner_rlp_execute`, `action_to_promise`, or the ABI decoding path in `types.rs`/`internal.rs` rejects `allowance == 0` or treats it specially before this point — there is no validation step that would stop this from reaching `add_access_key_allowance_with_nonce`.

### Impact Explanation
The resulting `Promise::add_access_key_allowance_with_nonce` call grants the newly added `FunctionCall` access key `Allowance::Unlimited` instead of the hard-zero allowance that was explicitly requested via the ABI-encoded action. Since a `FunctionCall`-permissioned access key's allowance funds gas/fee spending from the owning account's NEAR balance, any holder of the resulting public key (e.g., a dApp or automation agent that the account owner intended to restrict to zero spending power) instead receives the ability to drain the account's entire NEAR balance over repeated transactions to the specified `receiver_id`/`method_names`. This is a fund-loss/authorization-escalation bug: the granted `Promise`'s permission scope does not match the caller's declared, signed intent.

### Likelihood Explanation
- No special privileges are required: any relayer can submit the RLP-encoded transaction for the account owner (the owner signs it with their Ethereum-style key as usual); the fields `is_full_access=false`, `is_limited_allowance=true`, `allowance=0` are fully attacker/user-controlled inputs within the ABI-decoded `AddKey` call.
- The bug is deterministic and always triggers for `allowance=0` — no race condition or timing dependency.
- The realistic exploitation scenario is a wallet UI/SDK or third-party integrator that legitimately uses `allowance=0` + `is_limited_allowance=true` to mean "this key can call functions but must never spend NEAR on gas," which is a reasonable and expected use of the ABI, given the ABI explicitly separates `is_limited_allowance` from `allowance` (rather than only using `allowance>0` to imply limited). The bug silently defeats that restriction.

### Recommendation
Do not collapse an explicit zero allowance into `Unlimited`. Either:
1. Reject `is_limited_allowance=true && allowance==0` as a `UserError` (e.g., add a new `UnsupportedAction`/`InvalidAllowance` variant), forcing callers to either omit limiting (unlimited) or use a nonzero limited value; or
2. Preserve the "limited-to-zero" semantics explicitly if the underlying `near_sdk::Allowance`/protocol supports a truly zero-spend key, rather than defaulting to `Allowance::Unlimited` via `unwrap_or`.

The fix belongs in `action_to_promise` in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` (replace the `.and_then(Allowance::limited).unwrap_or(Allowance::Unlimited)` chain with explicit handling of the `Some(0)` case), and/or in `Action::try_into_near_action` in `types.rs` to reject `allowance == 0` when `is_limited_allowance` is `true`.

### Proof of Concept
Unit test in `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs` (or a new test module alongside `tests/`):
```rust
#[test]
fn add_key_zero_allowance_is_not_unlimited() {
    let action = near_action::Action::AddKey(near_action::AddKeyAction {
        public_key: test_public_key(),
        access_key: near_action::AccessKey {
            nonce: 0,
            permission: near_action::AccessKeyPermission::FunctionCall(
                near_action::FunctionCallPermission {
                    allowance: Some(NearToken::from_yoctonear(0)), // is_limited_allowance=true, allowance=0
                    receiver_id: "receiver.near".parse().unwrap(),
                    method_names: vec![],
                },
            ),
        },
    });

    let promise = action_to_promise("target.near".parse().unwrap(), action).unwrap();

    // Inspect the generated promise's AddKey action's allowance
    // (requires exposing the constructed Allowance for assertion, e.g. via
    // a promise-action inspection helper or near-sdk-sim/workspaces receipt check).
    // Expected: allowance must NOT be Allowance::Unlimited.
    assert_ne!(extract_allowance(&promise), Allowance::Unlimited);
}
```
Expected (currently failing) assertion: the produced access key's allowance is `Allowance::Unlimited` even though the caller explicitly requested `is_limited_allowance=true, allowance=0`, confirming the escalation. An integration-test variant can call `rlp_execute` end-to-end and then query `get_access_key` on the resulting account to confirm the on-chain `allowance` field is `None` (unlimited) instead of `Some(0)`.
