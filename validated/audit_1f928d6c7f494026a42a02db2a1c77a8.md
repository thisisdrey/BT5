### Title
Case-insensitive `accountId` index allows permanent, unauthorized blocking of `SetAccountIdContract` submissions - (File: `chainbase/src/main/java/org/tron/core/store/AccountIdIndexStore.java`)

### Summary
`AccountIdIndexStore` normalizes every `accountId` to lowercase before using it as the store key, while the actual `accountId` stored on the `AccountCapsule` (via `SetAccountIdActuator`) preserves the original, case-sensitive bytes. Because `SetAccountIdContract` can only ever be submitted once per account (a second attempt is rejected with "This account id already set"), and the uniqueness check `accountIdIndexStore.has(accountId)` is keyed on the lowercased form, any unprivileged account can permanently "squat" every case-variant of a given identifier string with a single transaction, blocking any other account from ever claiming that identifier in any case. This is directly analogous to the LineaRollup finding: a value that is not actually unique (accountId modulo case) is used as the "cardinality" for a permanent, non-resubmittable operation, causing legitimate submissions to be rejected as duplicates.

### Finding Description
`AccountIdIndexStore.getLowerCaseAccountId` lower-cases the raw `accountId` bytes before every `put`/`get`/`has` operation: [1](#0-0) 

`has`/`get` both route through this normalization: [2](#0-1) 

`SetAccountIdActuator.validate()` uses this case-insensitive `has()` check as the sole uniqueness gate, and rejects the transaction if the (lower-cased) key already exists: [3](#0-2) 

Crucially, once an account successfully sets an `accountId`, it can never be changed again — the validate step permanently blocks any resubmission for that same owner address: [4](#0-3) 

However, `execute()` stores the *original, case-preserved* bytes on the account (not the lowercased form): [5](#0-4) 

This mismatch is confirmed by the project's own test, which shows that `"aABbCcDd_ssd1234"`, its all-lowercase form, and its all-uppercase form are all treated as "already existing" by the index once any one of them is registered: [6](#0-5) 

The bug-class match to the external report: the external report describes a hash/key derived from insufficiently-constrained input data (compressed data omitting nonce/signature, non-strictly-unique timestamps) being used as a permanent cardinality for one-time submission, causing legitimate, distinct inputs to collide and be rejected as duplicates. Here, the "cardinality" is the lowercased `accountId`, which discards case information that `TransactionUtil`'s validation does not otherwise disambiguate, and the operation (`SetAccountIdContract`) is a strictly one-time, non-resubmittable action per account — exactly mirroring the "cannot resubmit under a different, valid representation" failure mode.

### Impact Explanation
Any single signed transaction from an unprivileged account can call `SetAccountIdContract`. By submitting one transaction with a chosen `accountId` string, the attacker permanently occupies every case-variant of that string in the global `AccountIdIndexStore` namespace (a shared, chain-wide resource), because:
1. The index key collapses case, so `"MyBrand"`, `"mybrand"`, `"MYBRAND"`, etc. all map to one entry.
2. `SetAccountIdContract` is immutable per-account once set (no way to release/re-issue), so the block is permanent.
3. `accountId` is a user-facing identifier used by consumers of `GetAccountById`/`getaccountbyid` API to look up accounts, so this also creates confusable/squatting opportunities for identifiers intended to be distinct.

This meets the "permanent freezing" bar in spirit: it permanently denies a specific, otherwise-valid on-chain operation (claiming a legitimate identifier) to any future legitimate account, with no recovery path, triggerable by a single unprivileged transaction at negligible cost (`calcFee()` returns 0). It does not cause fund loss or unbacked balances, so it should be scoped as Medium severity griefing/DoS against a shared namespace resource rather than a fund-theft bug.

### Likelihood Explanation
Trivial to trigger: requires only one signed `SetAccountIdContract` transaction from any existing account, no special privileges, no race condition, and no cost beyond ordinary bandwidth/energy. The identifier collision is deterministic and always reproducible (not a hash-collision search), since it only requires choosing any two accountId strings differing solely in ASCII case.

### Recommendation
Make the uniqueness check consistent with what is actually stored and intended to be unique:
- Either enforce accountId uniqueness case-sensitively end-to-end (store and index the exact bytes, drop `toLowerCase` normalization), or
- If case-insensitive uniqueness is an intentional design choice (to prevent confusable IDs), normalize and store the *same* lowercased form on the `AccountCapsule` as well, so that the stored, queryable, and index-checked values are consistent, and document this restriction (e.g. reject accountIds that only add case-variation of the string used for lookups) so unauthorized parties cannot exploit the store/validate mismatch to block legitimate distinct-cased registrations.

### Proof of Concept
1. Account A calls `SetAccountIdContract` with `accountId = "MyBrand12"` (passes `TransactionUtil.validAccountId` length/charset checks). `SetAccountIdActuator.execute()` stores `accountCapsule.setAccountId("MyBrand12")` and calls `accountIdIndexStore.put(account)`, which persists under the lowercased key `"mybrand12"` (per `AccountIdIndexStore.getLowerCaseAccountId`).
2. Account B (unrelated, unprivileged) later calls `SetAccountIdContract` with `accountId = "myBrand12"` (a different, legitimately distinct case-variant string).
3. `SetAccountIdActuator.validate()` computes `accountIdIndexStore.has("myBrand12".getBytes())`, which lowercases to `"mybrand12"`, finds an existing entry from step 1, and throws `ContractValidateException("This id has existed")` — even though Account B's exact `accountId` bytes were never previously registered.
4. Because `SetAccountIdContract` can only be executed once per account (`account.getAccountId() != null && !isEmpty()` blocks further attempts), Account B (and every other account) is permanently prevented from ever claiming `"myBrand12"` or any other case-variant of that string, confirmed by the existing project test `AccountIdIndexStoreTest.testCaseInsensitive` demonstrating the case-collision behavior.     return ByteString

  @SuppressWarnings("StringCaseLocaleUsage")
  public void testCaseInsensitive() {
    byte[] ACCOUNT_NAME = "aABbCcDd_ssd1234".getBytes();
    byte[] ACCOUNT_ADDRESS = randomBytes(16);

    AccountCapsule accountCapsule = new AccountCapsule(ByteString.copyFrom(ACCOUNT_ADDRESS),
        ByteString.copyFrom(ACCOUNT_NAME), AccountType.Normal);
    accountCapsule.setAccountId(ByteString.copyFrom(ACCOUNT_NAME).toByteArray());
    accountIdIndexStore.put(accountCapsule);

    Boolean result = accountIdIndexStore.has(ACCOUNT_NAME);
    Assert.assertTrue("fail", result);

    byte[] lowerCase = ByteString
        .copyFromUtf8(ByteString.copyFrom(ACCOUNT_NAME).toStringUtf8().toLowerCase())
        .toByteArray();
    result = accountIdIndexStore.has(lowerCase);
    Assert.assertTrue("lowerCase fail", result);

    byte[] upperCase = ByteString
        .copyFromUtf8(ByteString.copyFrom(ACCOUNT_NAME).toStringUtf8().toUpperCase())
        .toByteArray();
    result = accountIdIndexStore.has(upperCase);
    Assert.assertTrue("upperCase fail", result);

    Assert.assertNotNull("getLowerCase fail", accountIdIndexStore.get(upperCase));
