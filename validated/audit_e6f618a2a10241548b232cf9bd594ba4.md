### Title
Unfreeze Balance V2 never decrements the underlying `FrozenV2` stake record, allowing repeated over-unfreezing and unbacked TRX minting - (File: actuator/src/main/java/org/tron/core/actuator/UnfreezeBalanceV2Actuator.java)

### Summary
`UnfreezeBalanceV2Actuator` (and its TVM-reachable counterpart `UnfreezeBalanceV2Processor`) validate an unfreeze request against the amount stored in the account's `FrozenV2` list, but `execute()` never reduces that `FrozenV2` amount afterward. The `FrozenV2` entry is effectively the "receipt" that should be burned/decremented once its balance is unfrozen; because it isn't, the same nominal frozen balance can be unfrozen again and again (up to `UNFREEZE_MAX_TIMES`), and each unfreeze batch is later paid out in real TRX by `WithdrawExpireUnfreezeActuator`/`WithdrawExpireUnfreezeProcessor`, producing TRX far in excess of what was ever actually staked.

### Finding Description
`UnfreezeBalanceV2Actuator` defines `updateAccountFrozenInfo` specifically to decrement the matching `FreezeV2` entry by the unfrozen amount: [1](#0-0) 

However, `execute()` never calls it. Execute only calls `unfreezeExpire` (settles already-expired unfreezes), `addUnfrozenV2List` (adds a new pending unfreeze), `updateTotalResourceWeight` (adjusts the network's total weight counters and a separate `*V2` delegated-weight field), and `updateVote`: [2](#0-1) 

The eligibility check performed in `validate()` relies exclusively on the `FrozenV2` list amount, which is never reduced: [3](#0-2) 

Because `updateAccountFrozenInfo` is dead code, the `FrozenV2.amount` used by `checkUnfreezeBalance`/`checkExistFrozenBalance` stays constant across repeated unfreeze calls for the same resource type. The only limit enforced is the count of currently-pending (non-expired) `UnfrozenV2` entries, capped at `UNFREEZE_MAX_TIMES = 32`: [4](#0-3) [5](#0-4) 

The same missing decrement exists in the TVM-native-contract path used from `Program.unfreezeBalanceV2`-style opcodes, where `UnfreezeBalanceV2Processor.execute()` performs the identical sequence (`unfreezeExpire`, `addUnfrozenV2List`, `updateTotalResourceWeight`, `updateVote`) without ever reducing the `FrozenV2` record: [6](#0-5) 

Consequently, a user who freezes a single amount X for a resource can submit `UnfreezeBalanceV2Contract` for X repeatedly (up to 32 concurrently pending entries), because each subsequent `validate()` call still finds `FrozenV2.amount == X`. Each call appends a new `UnFreezeV2` entry worth X to `unfrozen_v2`: [7](#0-6) 

Once the unfreeze delay elapses, every one of these pending entries is redeemable for real TRX via `WithdrawExpireUnfreezeActuator`/`WithdrawExpireUnfreezeProcessor`, which simply sums all expired `UnFreezeV2` entries and credits the account balance: [8](#0-7) 

This mirrors the reported bug class exactly: the "receipt" (`FrozenV2` stake record) representing the user's locked stake is never invalidated/burned after being redeemed via unfreeze, so it can be reused to claim the underlying value multiple times.

### Impact Explanation
An attacker who freezes X TRX can withdraw up to `UNFREEZE_MAX_TIMES × X` TRX (≈32×) from the network by repeatedly submitting `UnfreezeBalanceV2Contract` (or the equivalent TVM opcode) for the same resource type before any single unfreeze batch is consumed, then collecting all pending entries via `WithdrawExpireUnfreezeContract`. This creates unbacked TRX balance out of thin air — a direct theft/inflation of network funds, reachable from a single unprivileged signed transaction with no special privileges required. This is a Critical-severity, concrete "unbacked balance"/"theft of funds" vulnerability per the validation criteria.

### Likelihood Explanation
Highly likely to be exploitable: `FreezeBalanceV2`, `UnfreezeBalanceV2`, and `WithdrawExpireUnfreeze` are all standard, publicly documented, unprivileged transaction types available to any account (also exposed via HTTP servlets and gRPC, e.g. `WithdrawExpireUnfreezeServlet` and the `UnfreezeBalanceV2`/`WithdrawExpireUnfreeze` RPCs). No special conditions beyond `supportUnfreezeDelay()` being enabled (a standard committee-toggled feature) are required, and the attacker only needs to freeze a small amount once and then loop the unfreeze/withdraw cycle.

### Recommendation
In `UnfreezeBalanceV2Actuator.execute()` (and the equivalent `UnfreezeBalanceV2Processor.execute()`), call `updateAccountFrozenInfo(freezeType, accountCapsule, unfreezeBalance)` to decrement the matching `FrozenV2` entry by `unfreezeBalance` immediately after (or before) adding the new `UnfrozenV2` entry, mirroring how `updateTotalResourceWeight` already reduces the weight-tracking counters. This ensures the `FrozenV2` "receipt" is properly reduced/invalidated so it cannot be reused across multiple unfreeze calls.

### Proof of Concept
1. Account A freezes X sun for `BANDWIDTH` via `FreezeBalanceV2Contract`, populating `FrozenV2{type=BANDWIDTH, amount=X}`.
2. A submits `UnfreezeBalanceV2Contract{resource=BANDWIDTH, unfreeze_balance=X}`. `validate()` passes since `checkUnfreezeBalance` sees `FrozenV2.amount == X`. `execute()` adds `UnFreezeV2{amount=X, expire=now+delay}` to `unfrozen_v2` but leaves `FrozenV2.amount` unchanged at X [9](#0-8) .
3. A repeats step 2 up to 31 more times (bounded only by `UNFREEZE_MAX_TIMES=32` pending entries), each time succeeding validation because `FrozenV2.amount` is still X.
4. After `unfreeze_delay_days` elapses, A submits `WithdrawExpireUnfreezeContract`. All 32 pending `UnFreezeV2` entries (32·X sun total) are summed and credited to A's balance [10](#0-9) , yielding 32× the TRX A ever actually staked — unbacked balance created from a single original freeze of X.

  public boolean checkUnfreezeBalance(AccountCapsule accountCapsule,
                                      final UnfreezeBalanceV2Contract unfreezeBalanceV2Contract,
                                      ResourceCode freezeType) {
    boolean checkOk = false;

    long frozenAmount = 0L;
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (FreezeV2 freezeV2 : freezeV2List) {
      if (freezeV2.getType().equals(freezeType)) {
        frozenAmount = freezeV2.getAmount();
        break;
      }
    }

    if (unfreezeBalanceV2Contract.getUnfreezeBalance() > 0
        && unfreezeBalanceV2Contract.getUnfreezeBalance() <= frozenAmount) {
      checkOk = true;
    }

    return checkOk;
  }

  public void updateAccountFrozenInfo(ResourceCode freezeType, AccountCapsule accountCapsule, long unfreezeBalance) {
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (int i = 0; i < freezeV2List.size(); i++) {
      if (freezeV2List.get(i).getType().equals(freezeType)) {
        FreezeV2 freezeV2 = FreezeV2.newBuilder()
            .setAmount(freezeV2List.get(i).getAmount() - unfreezeBalance)
            .setType(freezeV2List.get(i).getType())
            .build();
        accountCapsule.updateFrozenV2List(i, freezeV2);
        break;
      }
    }
  }

  public long execute(UnfreezeBalanceV2Param param, Repository repo) {
    byte[] ownerAddress = param.getOwnerAddress();
    long unfreezeBalance = param.getUnfreezeBalance();
    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();

    long unfreezeExpireBalance = this.unfreezeExpire(accountCapsule, now);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    long expireTime = this.calcUnfreezeExpireTime(now, repo);
    accountCapsule.addUnfrozenV2List(param.getResourceType(), unfreezeBalance, expireTime);

    this.updateTotalResourceWeight(accountCapsule, param.getResourceType(), unfreezeBalance, repo);
    this.updateVote(accountCapsule, param.getResourceType(), ownerAddress, repo);

    if (repo.getDynamicPropertiesStore().supportAllowNewResourceModel()
        && !accountCapsule.oldTronPowerIsInvalid()) {
      accountCapsule.invalidateOldTronPower();
    }

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return unfreezeExpireBalance;
  }
