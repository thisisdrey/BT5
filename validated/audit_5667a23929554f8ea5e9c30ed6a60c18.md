## Title
Vault `deposit` mints shares and credits `assets` based on the nominal transfer amount instead of the actually-received balance, causing insolvency for fee-on-transfer underlying assets - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`)

### Summary
Every Zest v2 vault's `deposit` entry point computes shares to mint from the caller-supplied `amount` parameter via `convert-to-shares-preview`, and separately increments the internal `assets` accounting variable by that same nominal `amount` — both before/independent of any check on how many underlying tokens the vault actually received. This is the exact bug class from the Sherlock finding: a fee-on-transfer (or otherwise amount-skimming) underlying SIP-010 token causes the vault to believe it holds more assets than it does, over-minting shares and making the vault insolvent for later redeemers.

### Finding Description
In each vault, `deposit` is: [1](#0-0) 

The share amount `inkind` is derived from `convert-to-shares-preview amount` using the raw `amount` argument, and `receive-underlying` is then called with that same nominal `amount`: [2](#0-1) 

`receive-underlying` simply calls `transfer amount account current-contract` on the underlying token and returns `(ok true)` — it never performs a balance-before/balance-after check to determine the *actual* amount the vault received: [3](#0-2) 

After the transfer, `deposit` mints `inkind` shares and unconditionally bumps the `assets` bookkeeping variable by the full nominal `amount`, not by any value derived from `ubalance` (the vault's own on-chain token balance getter, which exists but is unused for this reconciliation): [4](#0-3) 

If the underlying SIP-010 asset skims a fee on transfer (deducts a fee so the vault's actual received balance is `amount - fee`), the vault will:
1. Mint shares (`inkind`) computed as if it received the full `amount`.
2. Increase `assets` by the full `amount`, not `amount - fee`.

Both `total-assets`/`total-assets-preview` (used for share pricing on every subsequent deposit/redeem) are derived from this inflated `assets` variable, not from the real token balance: [5](#0-4) 

This is architecturally identical to the referenced `wfCashERC4626` root cause: minting shares/crediting internal accounting from the pre-transfer-fee amount rather than the post-transfer actual balance received.

### Impact Explanation
Every subsequent depositor's shares are priced against an `assets` figure that is permanently inflated relative to the vault's real token holdings. Since redemption pays out `convert-to-assets-preview` based on the same inflated `total-assets`, the last redeemers cannot be paid in full — the vault becomes unable to honor all outstanding shares 1:1, i.e., protocol insolvency for that vault (Critical impact per the accepted classes: protocol insolvency / permanent freezing of funds for late redeemers).

### Likelihood Explanation
The vault code path itself has no built-in reconciliation against actual received balance — it is a structural flaw present in every vault (`v0-vault-usdc`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-stx`, `v0-vault-usdh`, and their `local-testing` counterparts). It is triggered any time the deposited SIP-010 asset takes a fee on transfer (a class of token that is common enough that Sherlock treats it as a standard integration risk), requiring no privileged action or attacker capital — it is a passive consequence of the vault's accounting design for any qualifying underlying token.

### Recommendation
In `receive-underlying`, measure the vault's underlying token balance before and after the `transfer` call (using the existing `ubalance` helper) and use the actual delta — not the caller-supplied `amount` — as the basis for `convert-to-shares-preview` and for incrementing the `assets` variable in `deposit`.

### Proof of Concept
1. Underlying asset for a vault (e.g., the `usdcx` token referenced in `receive-underlying`) is/becomes a fee-on-transfer SIP-010 token with a 1% transfer fee.
2. User A calls `deposit` with `amount = 1000`. `inkind` (shares) is computed via `convert-to-shares-preview 1000`; `receive-underlying` transfers `1000` but the vault only actually receives `990` due to the fee.
3. `assets` is incremented by `1000`, and `1000`-equivalent shares are minted to A, even though the vault only holds `990` more tokens than before.
4. Repeat across depositors: `assets`/`total-supply` ratio no longer reflects real backing.
5. When later users call `redeem`, `convert-to-assets-preview` pays out based on the inflated `assets`, and the vault runs out of actual underlying tokens before all shares can be redeemed — insolvency.
