### Title
Unbounded microblock count in `MicroblocksData` deserialization enables single-message compute DoS - ([File: stackslib/src/net/codec.rs])

### Summary
`MicroblocksData::consensus_deserialize` bounds the `Vec<StacksMicroblock>` read only by the aggregate byte length `MAX_MESSAGE_LEN`, unlike `BlocksData` which uses `read_next_at_most` with an explicit `BLOCKS_PUSHED_MAX` item-count cap. This lets a remote peer pack a single `MicroblocksData` P2P message with the maximum number of minimally-sized `StacksMicroblock` entries that fit under `MAX_MESSAGE_LEN`, each of which is later individually run through `chainstate.preprocess_streamed_microblock` in `Relayer::preprocess_pushed_microblocks`.

### Finding Description
`BlocksData::consensus_deserialize` explicitly caps the number of items via `read_next_at_most::<_, BlocksDatum>(&mut bound_read, BLOCKS_PUSHED_MAX)` [1](#0-0) . In contrast, `MicroblocksData::consensus_deserialize` reads the `microblocks` vector with plain `read_next(&mut bound_read)`, bounded only by the byte-length `BoundReader::from_reader(fd, MAX_MESSAGE_LEN as u64)`, with no analogous count cap [2](#0-1) .

Because each `StacksMicroblock` entry can be minimally sized (a header plus a small number of transactions, or even zero transactions), an attacker can maximize the *number* of microblock structs that fit within `MAX_MESSAGE_LEN`, unlike `StacksBlock`/`BlocksDatum` entries which are inherently larger and thus naturally self-limit count even without `BLOCKS_PUSHED_MAX`.

Downstream, when this pushed `MicroblocksData` message arrives, `ConversationP2P::validate_microblocks_push` only throttles based on cumulative byte bandwidth (`max_microblocks_push_bandwidth`), not item count [3](#0-2) . The message is then handed to `Relayer::preprocess_pushed_microblocks`, which iterates every microblock in `mblock_data.microblocks` and calls `Relayer::static_check_problematic_relayed_microblock` and `chainstate.preprocess_streamed_microblock` per item [4](#0-3) . `preprocess_streamed_microblock` performs microblock-header validation including signature-recovery-adjacent work per microblock, so an attacker who maximizes the microblock *count* within one message maximizes this per-item CPU work for a fixed message size, well beyond what a byte-length bound alone would suggest.

### Impact Explanation
A single crafted P2P push message causes the receiving node to run per-item validation/signature-adjacent processing thousands of times in one message handling pass, consuming CPU disproportionate to the byte-length throttle that `validate_microblocks_push` enforces. This is a bounded compute DoS delivered via a single message and is repeatable by any connected, unprivileged peer, matching the "High - bounded compute DoS" impact category.

### Likelihood Explanation
The attacker only needs to be an ordinary, already-connected P2P peer capable of sending a `MicroblocksData` push message referencing some `index_anchor_block`; no privileged role, secret, or StackerDB slot is required. Cost to craft the message is trivial (pack minimal `StacksMicroblock` structs up to `MAX_MESSAGE_LEN`), and it can be resent repeatedly, limited only by the existing byte-based bandwidth throttle (`max_microblocks_push_bandwidth`), which does not account for per-item processing cost.

### Recommendation
Add an explicit per-item cap to `MicroblocksData::consensus_deserialize`, analogous to `BLOCKS_PUSHED_MAX`/`NAKAMOTO_BLOCKS_PUSHED_MAX`, e.g. `read_next_at_most::<_, StacksMicroblock>(&mut bound_read, MAX_MICROBLOCKS_COUNT)`, choosing a bound consistent with realistic microblock-stream lengths, and reject/nack messages exceeding it before expensive per-item processing in `Relayer::preprocess_pushed_microblocks`.

### Proof of Concept
Rust test plan (in `stackslib/src/net/codec.rs` tests or a new test module):
1. Construct a minimal `StacksMicroblock` (empty/near-empty tx list, minimal header) and serialize it to determine its minimal encoded byte size `S`.
2. Build a raw `MicroblocksData` payload buffer by hand: write `index_anchor_block` (32 bytes), then a length prefix of `N = MAX_MESSAGE_LEN / S` (or `MAX_PAYLOAD_LEN / S`), followed by `N` copies of the minimal serialized microblock.
3. Call `MicroblocksData::consensus_deserialize` on this buffer and confirm it succeeds and returns `N` microblocks (i.e., no count cap is enforced, unlike `BlocksData::consensus_deserialize` which would reject at `BLOCKS_PUSHED_MAX`).
4. Assert `microblocks.len() > BLOCKS_PUSHED_MAX` (or any sane analogous constant) to demonstrate the absent per-item cap.
5. Optionally, time the downstream call into a stubbed `preprocess_streamed_microblock` loop to show CPU cost scales linearly with `N` for a fixed message byte size, contrasting with the `BlocksData` path.
