### Title
Unchecked user-controlled array length in TVM precompile ABI decoding leads to uncontrolled allocation / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray`, `extractBytes32Array`, and `extractSigArray` decode ABI-encoded dynamic arrays passed as call data to TVM precompiled contracts (used by `ValidateMultiSign`/`BatchValidateSign`-style precompiles). Each helper reads a length word directly from attacker-supplied call data and immediately allocates a Java array sized by that length, with no bound check against the actual size of the decoded `words` buffer, mirroring the CVE-2019-10877 pattern of trusting an attacker-controlled size field to drive an allocation.

and the sibling helpers `extractBytes32Array` and `extractSigArray` follow the same pattern: [2](#0-1) 

`len` is derived from `intValueSafe()` on a `DataWord` taken straight from the ABI header word supplied in the transaction/call data. The only validation performed is `offset > words.length - 1` (whether the *length field itself* is present), not whether `len` is consistent with the actual number of remaining words/bytes in `data`. Consequently a caller can set the length word to an arbitrarily large value (up to `Integer.MAX_VALUE`, since `intValueSafe()` caps rather than rejects) while supplying only a few real bytes of payload. The code then executes `new byte[len][]` (or `new byte[len][]` for `Bytes32Array`) before any bounds validation against the rest of the buffer occurs — this is structurally the same root cause as CMap::Load()'s `width * height` allocation in Teeworlds: an unvalidated, attacker-controlled size value drives a memory allocation.

### Impact Explanation
A single call to a TVM precompiled contract that uses these decoding helpers (e.g. the multi-signature validation precompile family) can force the node to attempt an allocation on the order of billions of array slots. This throws `OutOfMemoryError`, which is a JVM `Error`, not an `Exception`; if it is not specifically caught along the precompile execution path it can propagate past normal `ContractExeException`/`ContractValidateException` handlers and crash or hang the executing node process — an availability impact on any full node/SR that processes the transaction. Because precompiles are executed synchronously as part of ordinary contract-call execution, this is reachable from any signed transaction that invokes the affected contract call, without any special privilege.

### Likelihood Explanation
Likelihood is high for any node that has the corresponding TVM proposal/feature enabled, since the vulnerable helper is reached purely through crafted call data on an ordinary CALL to the precompile address — no special account permissions, staking, or governance role is required, only a validly signed transaction from an unprivileged account.

### Recommendation
Validate `len` against the actual bounds of the `words`/`data` buffers (e.g., require `len <= (words.length - offset - 1)` and reject values that would obviously exceed the size of the supplied call data) before allocating `bytesArray`/`bytes32Array`, mirroring the fix pattern used elsewhere in the codebase (e.g., `RLP.verifyLength`) that rejects a supplied length exceeding the available data length. Additionally, cap the maximum permitted array length to a small sane constant consistent with the maximum number of signatures/entries the precompile is designed to support.

### Proof of Concept
Not independently executed; the analysis is based on static review of `PrecompiledContracts.java`. A concrete PoC would consist of a transaction that calls the `ValidateMultiSign`/`BatchValidateSign` precompile with an ABI header word claiming a very large array length (e.g., `0x7fffffff`) while providing minimal trailing data, then observing whether the node throws `OutOfMemoryError` before any bounds check occurs. I was unable to fully trace, within the available tool budget, whether an outer exception handler in the precompile execution path currently catches `Throwable`/`Error` broadly enough to convert this into a safely reverted transaction rather than a node-level crash — this should be verified directly against `PrecompiledContracts.execute()` and its callers in `Program.java` before treating the crash impact as fully confirmed.
