## Finding

Not a duplicate of the ThorWallet issue itself, but the **root-cause pattern maps onto nearcore's ETH-implicit `WalletContract`**: a single boolean state flag that is supposed to always flip back to a "safe" value, but whose reset only happens inside application logic that can itself fail/panic/run out of gas — leaving the flag permanently stuck and the account permanently unusable, analogous to how `isBridgedTokenHolder` could get stuck `true` and permanently restrict the victim.

### Title
Permanent Denial-of-Service of ETH-Implicit Wallet via Un-resettable `has_in_flight_tx` Flag - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` (the global contract deployed to every ETH-implicit account) tracks whether a transaction is in flight using a single boolean, `has_in_flight_tx`. Once `rlp_execute` sets it to `true`, only the private promise callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) reset it to `false`. Because NEAR reverts *all* state writes of a function-call receipt on panic/out-of-gas, any failure inside those callback bodies (which happens after the flag write in program order, but before/along with other logic) discards the reset along with everything else, leaving `has_in_flight_tx = true` forever, since the flag itself has no other write path.

### Finding Description
The contract's own invariant comment states the intended behavior explicitly: [1](#0-0) 

`rlp_execute` refuses to do anything while the flag is set: [2](#0-1) 

and sets it to `true` before returning a cross-contract promise: [3](#0-2) 

The only code that ever writes `false` again lives inside the `#[private]` callbacks (e.g. `rlp_execute_callback`): [4](#0-3) 

`rlp_execute_callback`'s static gas budget is a fixed constant, independent of the size of the data returned by the cross-contract call it wraps: [5](#0-4) 

On the `PromiseResult::Successful` branch, the callback re-serializes the arbitrary-size `value` returned by the target contract into `ExecuteResponse.success_value` and returns it: [6](#0-5) 

If the target of the `FunctionCall` action (chosen at wallet-execution time from the signed Ethereum tx's `to`/calldata) returns a sufficiently large payload, or if the fixed 5 TGas static allocation for the callback is otherwise insufficient (e.g. underfunded `prepaid_gas` supplied by a relayer, since `validate_tx_relayer_data` only checks a lower bound on relayer-supplied gas, not that the callback receives enough after all upstream deductions), the callback receipt can run out of gas or panic. NEAR rolls back the *entire* receipt's state changes on such failure — including the `self.has_in_flight_tx = false;` write that executed as the very first statement — so the flag remains `true` in the persisted account state.

Because `has_in_flight_tx` has no other reset mechanism (no owner-only "unstick" method, no timeout), the wallet is permanently stuck: `rlp_execute` will forever return `"Error: transaction already in progress, please try again later."` and the account can never again execute any Ethereum-style transaction (transfers, ERC-20 emulation, function calls) through the wallet contract mechanism it was created with.

### Impact Explanation
This is a permanent freezing-of-funds/functionality bug for the affected ETH-implicit account: all $NEAR and NEP-141 balances reachable only via the RLP-executed wallet contract become permanently inaccessible through that mechanism, with no recovery path defined in the contract. A malicious or careless relayer (the untrusted party in this design — the whole point of `validate_tx_relayer_data`/`ban_relayer` is defending against faulty relayers) can trigger this by targeting a contract/method whose return payload is large, or by supplying marginal gas, causing the victim's wallet to become permanently unusable via this design.

### Likelihood Explanation
Reachable by any relayer submitting a `rlp_execute` transaction on behalf of an ETH-implicit account holder — no privileged/validator/node access is required. The static gas budget for the callback is small (5 TGas) and fixed regardless of the size of data returned by the called contract, making it plausible to hit the boundary with an adversarially-chosen target/return value or deliberately tight gas.

### Recommendation
Do not rely on in-body assignment order for a flag that must be reset even on failure. Options:
- Reserve a small always-succeeding "finally" step (a further chained promise/callback with a minimal, size-independent workload) whose sole job is to clear `has_in_flight_tx`, so the reset is not coupled to potentially unbounded work (e.g., serializing an arbitrary `success_value`).
- Bound/truncate `success_value` size before returning it from `rlp_execute_callback`, and ensure the callback's gas is provisioned relative to worst-case payload size rather than a fixed constant.
- Add a recovery/escape hatch (e.g., an owner-signed action, gated by an appropriate timeout) that can force-clear `has_in_flight_tx` if a promise never resolves as expected.

### Proof of Concept
1. Attacker/relayer causes an ETH-implicit account's `rlp_execute` to route a `FunctionCall` action to a contract they control, whose method returns a very large successful result (or attacker submits the NEAR transaction with prepaid gas trimmed so only the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 TGas) remains for the callback).
2. `inner_rlp_execute` sets `has_in_flight_tx = true` and schedules `... .then(ext.rlp_execute_callback(caller_deposit))` (`lib.rs:116-127`, `lib.rs:466-470`).
3. The cross-contract call succeeds and returns the oversized payload; `rlp_execute_callback` begins execution, sets `has_in_flight_tx = false` as its first statement (`lib.rs:280`), then attempts to build/return `ExecuteResponse { success_value: Some(value), .. }` (`lib.rs:313-315`) and runs out of gas serializing/returning it.
4. Because the receipt fails, all its state changes — including the flag reset — are discarded on-chain; `has_in_flight_tx` remains `true` in the persisted account state.
5. Every subsequent call to `rlp_execute` on this account now unconditionally returns the "transaction already in progress" error (`lib.rs:97-105`), permanently locking the wallet with no way to reset the flag.

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
    }
