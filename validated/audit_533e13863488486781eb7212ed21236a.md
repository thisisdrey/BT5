### Title
Quarantine-directory ownership check can be bypassed via a crafted `GitObjectDirectory` path ending in `quarantine` - (File: `internal/git/localrepo/paths.go`)

### Summary
`Repo.ObjectDirectoryPath` is supposed to enforce that a repository's `GitObjectDirectory`/`GitAlternateObjectDirectories` fields either point inside the repository itself, or — if not — point to a quarantine directory that was specifically created for *that* repository (verified via a per-repository hash prefix). A permissive heuristic shortcut added to accommodate nested/transaction quarantines skips that ownership verification entirely whenever the path's last component is literally named `quarantine` (or `.../quarantine/tmp_objdir-*`), regardless of whether the path actually belongs to the repository being operated on.

### Finding Description
`ObjectDirectoryPath` first validates that the object-directory path resolves inside the storage root via `storage.ValidateRelativePath(storagePath, ...)`. That check only proves the path stays within the *storage*, not that it belongs to the specific repository. To restrict scope to the correct repository, the code additionally requires the path to either be a relative subpath of the repo itself, or to match `expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))`, where `QuarantineDirectoryPrefix` is a SHA1-derived, repo-specific prefix [1](#0-0) .

However, this repo-ownership check is entirely skipped when `isTransactionQuarantineDir` is true: [2](#0-1) 

`isTransactionQuarantineDir` is satisfied whenever `baseDir == "quarantine"`, or `parentDir == "quarantine" && baseDir` starts with `tmp_objdir` — a purely name-based heuristic with no cryptographic or identity binding to the requesting repository [3](#0-2) . Any `GitObjectDirectory` value that (a) resolves inside the storage root and (b) has a final path segment literally named `quarantine` (or the two-segment `quarantine/tmp_objdir-*` pattern) short-circuits the strict per-repository prefix check that would otherwise reject it. The existing test suite exercises exactly this shortcut path with directories placed anywhere under the storage root, confirming the check does not tie the accepted directory to the specific repository’s own hash-derived prefix [4](#0-3) .

This mirrors the ERC677 bug class: two overlapping code paths are meant to enforce the same invariant (repository-scoped object directory), but one of them (the loose “transaction quarantine” heuristic) unconditionally satisfies the condition and silently bypasses the other (the strict, repo-bound prefix check), producing an unintended widened effect instead of the intended single, narrow guarantee.

### Impact Explanation
If an attacker can influence the `GitObjectDirectory` field of a `Repository` message processed by Gitaly (e.g., through a crafted RPC field reaching hook/quarantine code paths such as `internal/gitaly/hook/prereceive.go` or `internal/gitaly/hook/custom.go`, which consume `GetGitObjectDirectory()`), they can point Gitaly's object resolution at another repository's or another in-flight transaction's quarantine directory merely by naming the final path segment `quarantine`. Downstream consumers (e.g., `git-cat-file`, `git-receive-pack` environment construction, hook payload environment) would then read or reference objects from a directory that does not belong to the acting repository, resulting in cross-repository/cross-transaction object exposure — objects that are supposed to remain isolated until migrated (or discarded) become visible/usable outside their intended scope.

### Likelihood Explanation
Exploitation requires the attacker to control the `GitObjectDirectory` (or `GitAlternateObjectDirectories`) value on a `Repository` message that reaches `ObjectDirectoryPath`, and for the crafted value to resolve within the storage root while ending in a `quarantine`-named segment. This is a narrower precondition than a fully open path traversal, so likelihood is moderate — it depends on which RPC/internal callers allow client-influenced values in these fields to reach this code path unmodified.

### Recommendation
Remove the special-case bypass, or replace it with a check that still verifies the directory belongs to the calling repository (e.g., always require the `expectedQuarantinePrefix` match, and separately allow the transaction-quarantine naming pattern only after confirming that the transaction's quarantine directory belongs to the same partition/repository context) rather than trusting the literal directory name `quarantine`.

### Proof of Concept
1. Create two repositories `A` and `B` in the same storage.
2. Start a legitimate quarantine or transaction-quarantine flow for repository `B`, creating a directory such as `<storage-tmp>/<tx-id>/quarantine/` (as emulated in `TestRepo_ObjectDirectoryPath`) [5](#0-4) .
3. Craft a `Repository` message for repository `A` with `GitObjectDirectory` set to the relative path (from `A`'s repo path) that resolves to `B`'s `.../quarantine` directory.
4. Call `ObjectDirectoryPath` (or any Gitaly code path that derives the object directory from this field, e.g. hook payload construction) for repository `A`.
5. Because `baseDir == "quarantine"`, `isTransactionQuarantineDir` is `true`, the repo-specific `expectedQuarantinePrefix` check is skipped, and the path is accepted even though it belongs to `B`, not `A` — confirming the bypass [6](#0-5) .

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}

		// a valid path. This may either be a path in the Git repository itself, where it may either
