### Title
Empty-string RPC auth secret causes authentication bypass via empty `Authorization` header - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` compares the configured secret to the request's `authorization` header with a plain `!=` check and never special-cases an empty configured secret. If the node operator sets `self.auth = Some(String::new())`, an unprivileged remote attacker can send `authorization:` with an empty value and satisfy `auth_header != password` (empty == empty), setting `authenticated = true` and passing the `broadcast=1` gate.

### Finding Description
The authentication logic is:
```
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
...
if broadcast && !authenticated {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) 

There is no check that `password` (the configured secret) is non-empty. When `self.auth == Some("".to_string())`, any request that includes an `authorization` header whose value is also the empty string satisfies `auth_header != password` as false (empty == empty), so `authenticated` becomes `true` and the `broadcast=1` gate at line 120-122 passes without the attacker knowing any real secret. Note that *omitting* the header entirely does not trigger this bypass, because the outer `if let Some(auth_header) = ...` is skipped and `authenticated` stays `false`, causing the 401 at the `broadcast && !authenticated` check [2](#0-1) . So the exploitable path specifically requires sending an explicit empty `authorization` header value, not omitting it.

The root cause is that the code conflates "no secret required" (`self.auth == None`) with "secret configured" (`Some(_)`) without validating that the configured secret is non-empty; a degenerate configuration value (`Some("")`) is treated identically to a legitimate, unguessable secret, undermining the authorization gate that protects `broadcast=1` (which triggers relay of the uploaded block to the whole network via `node.set_relay_message` in `try_handle_request`) [3](#0-2) .

### Impact Explanation
If the operator misconfigures the RPC auth secret as an empty string, any remote unprivileged party can force `broadcast=1` to succeed on `/v3/blocks/upload/`, causing the node to accept and relay an attacker-supplied Nakamoto block into the p2p network as if it came from an authenticated source. This is an authentication-bypass primitive gated entirely behind a plausible misconfiguration (empty secret) that the code does nothing to reject or warn about.

### Likelihood Explanation
Exploitation requires the specific precondition that the operator configured the RPC auth secret as the empty string rather than leaving it unset (`None`). This is a misconfiguration scenario, not something exploitable against a node with a properly configured (non-empty) secret or with no secret configured at all (in the `None` case, `broadcast=1` is unconditionally rejected because `authenticated` never becomes `true`). Given this precondition is required and is not the default or typical configuration path, the practical likelihood is low, though the code itself provides no defense-in-depth against it.

### Recommendation
Treat an empty configured secret as equivalent to "no valid secret" for authentication purposes — e.g., when constructing `RPCPostBlockRequestHandler` or in `try_parse_request`, reject/normalize `Some(s) if s.is_empty()` to behave as `None` for the purposes of the `broadcast` check (i.e., never allow `authenticated = true` when the configured password is empty), or fail node startup with a config validation error if the RPC auth token is set to an empty string.
