HTTP request smuggling via unhandled `Transfer-Encoding: chunked` on RPC requests - ([File: stackslib/src/net/http/request.rs])

### Summary
`HttpRequestPreamble::consensus_deserialize`'s header loop only special-cases `host`, `content-type`, `content-length`, `connection`, and `set-cookie`; a `Transfer-Encoding` header is silently absorbed as an opaque, ignored header, leaving `content_length` as `None`. Because `StacksHttp::payload_len`/`get_content_length()` treat a missing `Content-Length` as `0`, a client can send a chunked-encoded POST body that the node never consumes as part of the current request, causing the leftover chunk bytes to be reparsed as the start of the next request on the same keep-alive connection.

### Finding Description
The broken invariant is: *bytes the framing layer treats as this request's body* (`get_content_length()` → `0` when `content_length` is `None`) *must equal bytes the client actually sent as the body* (the full chunked payload). This invariant holds for `HttpResponsePreamble::consensus_deserialize` (`stackslib/src/net/http/response.rs:561-586`), which explicitly recognizes `transfer-encoding: chunked`, rejects the invalid combination of `chunked` + `Content-Length`, and errors when neither is present — but the analogous request-side parser has no such branch at all.

In `HttpRequestPreamble::consensus_deserialize` (`stackslib/src/net/http/request.rs:355-421`), any header not matching `host`/`content-type`/`content-length`/`connection`/`set-cookie` — including `transfer-encoding` — falls into the generic `else` branch (lines 413-421) and is stored verbatim in the `headers` map with no semantic effect. `content_length` therefore stays `None`.

Downstream, `HttpRequestPreamble::get_content_length()` (`stackslib/src/net/http/request.rs:205-207`) returns `self.content_length.unwrap_or(0)`, and `StacksHttp::payload_len` (`stackslib/src/net/httpcore.rs:1550-1554`) uses exactly this value to decide the request's body length, always returning `Some(0)` for requests with no `Content-Length`. `read_payload` (`stackslib/src/net/httpcore.rs:1716-1727`) then slices `buf.get(0..0)` as "the body," consuming zero bytes even though the client's chunked payload bytes remain unread in the stream buffer.

Attack: a remote client on the keep-alive-enabled RPC port sends:
```
POST /v2/... HTTP/1.1\r\nHost: ...\r\nTransfer-Encoding: chunked\r\n\r\n<chunked-body>
```
immediately followed by a second, attacker-chosen request line and headers. The framing state machine parses the first preamble, computes a 0-byte body, and hands the *chunked payload bytes* to the next `read_preamble` call, which then parses them as a brand-new `HttpRequestPreamble` — smuggled and framed entirely by the attacker inside what the node/any intermediary believed was body data of the first request.

Note: `StacksHttp::stream_payload` (`stackslib/src/net/httpcore.rs:1611-1623`) explicitly documents/enforces "HTTP requests can't be chunk-encoded" and returns `NetError::InvalidState` — but this code path is only reached when `payload_len()` returns `None`. Since `payload_len` unconditionally returns `Some(0)` for requests via `get_content_length()`, `stream_payload` is never invoked for requests, so this intended guard against chunked requests is dead code and never fires.

### Impact Explanation
This is a request-smuggling vector on the node's RPC HTTP port: an unprivileged, unauthenticated remote client can inject a request that gets parsed by the node (or any keep-alive-aware proxy/cache in front of it) in a framing context the operator did not intend. Depending on deployment (reverse proxy, logging/rate-limiting keyed on the "outer" request, connection reuse assumptions), this can desync request/response pairing on the connection, poison a fronting proxy's cache, or bypass per-request access controls that assume 1:1 framing between client-sent and node-parsed requests. This matches the "Critical - request smuggling or auth bypass" impact category.

### Likelihood Explanation
- Preconditions: RPC HTTP endpoint reachable, keep-alive enabled (default for HTTP/1.1 per `HttpVersion::Http11` defaulting `keep_alive = true` at `request.rs:346-349`).
- Attacker cost: trivial — a single raw TCP connection sending two crafted HTTP/1.1 requests back-to-back; no secret, no peer key, no StackerDB slot needed.
- Repeatable per connection/request, no rate limiting or volumetric requirement.

### Recommendation
Mirror the response-side handling in `HttpRequestPreamble::consensus_deserialize`: add an explicit `transfer-encoding` branch that (a) rejects `Content-Length` + `Transfer-Encoding: chunked` combinations, and (b) either rejects `Transfer-Encoding: chunked` requests outright (simplest, matching the existing "requests can't be chunked" assumption already coded into `stream_payload`) or properly implements chunked-body decoding for requests before computing `payload_len`/`read_payload`. At minimum, treat an unrecognized/unsupported `Transfer-Encoding` value on a request as a hard parse error rather than silently ignoring it.

### Proof of Concept
Add a test in `stackslib/src/net/tests/httpcore.rs` (mirroring existing chunked-response tests) that:
1. Constructs two pipelined byte buffers: buffer A = `POST /v2/foo HTTP/1.1\r\nHost: 127.0.0.1:20443\r\nTransfer-Encoding: chunked\r\n\r\n3\r\nabc\r\n0\r\n\r\n`, buffer B = a distinct `GET /v2/info HTTP/1.1\r\n...` request.
2. Concatenate A + B and feed into `StacksHttp::read_preamble` / `read_payload` (via the same driver used by `StacksHttp::parse_response`/equivalent request-parsing helper).
3. Assert that `read_preamble` parses the first preamble with `content_length == None`, that `payload_len()` returns `Some(0)`, and that `read_payload` consumes 0 bytes of body — i.e., `total_bytes_consumed == preamble_len` for request A.
4. Assert that the very next `read_preamble` call, operating on the leftover chunk-body bytes (`3\r\nabc\r\n0\r\n\r\n` + buffer B), parses a spurious/garbage or attacker-controlled `HttpRequestPreamble` rather than treating those bytes as the body of request A — demonstrating the smuggling/desync.
