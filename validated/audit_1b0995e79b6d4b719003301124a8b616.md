### Title
StackerDB write-frequency throttle is never enforced on chunk storage/relay, letting a slot owner flood the network with rapid writes - (File: stackslib/src/net/stackerdb/db.rs, stackslib/src/net/stackerdb/mod.rs)

### Summary
This is the closest reachable analog to the reported "prolong distribution" bug class: a cheap, repeatable action by a low-privilege party defeats a rate/pacing control that the rest of the system relies on for smoothing/limiting churn, because the control is only checked on one side of the write path and not on the authoritative storage/acceptance path.

### Finding Description
`StackerDBConfig.write_freq` is meant to bound how often a given slot can be legitimately updated network-wide (it is loaded into `StackerDBSync.write_freq` in `stackslib/src/net/stackerdb/sync.rs:54,266`, and used exclusively in `make_chunk_request_schedule`, `stackslib/src/net/stackerdb/sync.rs:340-352`, to decide whether a *fetch* should be skipped for a chunk that "was written too frequently").

However, the actual write-acceptance paths never check it:
- `StackerDBs::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) only checks chunk size, signer validity (`slot_desc.verify`), staleness (`slot_version <= slot_validation.version`), and `max_writes`. There is no `write_freq`/timing check at all. [1](#0-0) 
- `PeerNetwork::validate_received_chunk`, used both for chunks downloaded via poll and for unsolicited `StackerDBPushChunk` messages (`stackslib/src/net/stackerdb/mod.rs:649-718`), likewise checks size, signer, staleness, and `max_writes`, but never `write_freq`. [2](#0-1) 
- The HTTP `POST /v2/stackerdb/:principal/:contract/chunks` endpoint calls `tx.try_replace_chunk` directly, again with no `write_freq` gate. [3](#0-2) 

The equality being broken is: "what the fetch-side throttle assumes about how often a slot legitimately changes" vs. "what the storage/acceptance side actually permits." A properly-signed slot owner (this still requires holding the private key that owns the slot — StackerDB slots are allocated to known parties such as signers, not arbitrary internet hosts) can push new chunk versions as fast as it likes via HTTP POST or unsolicited P2P `StackerDBPushChunk`, and every honest node will accept, store, and — through `make_chunk_push_schedule` (`stackslib/src/net/stackerdb/sync.rs:434-535`), which has no `write_freq` gate either — relay each new version to its peers as soon as it sees a newer version than its own, exactly like a normal legitimate update. Each write consumes one increment of `max_writes` per slot.

### Impact Explanation
Because `write_freq` is intended to smooth/pace writes across the whole DB replica set (analogous to the 30-day interpolation window in the referenced report), its absence on the storage path lets a slot owner burn through the slot's `max_writes` budget arbitrarily fast and force continuous signature verification, storage churn, and gossip relay across all replicas at a rate far above what the config intends — a bounded-compute, write-triggered load multiplier on every StackerDB replica rather than a genuine unauthenticated write or forged-data issue. This lines up most closely with the "bounded compute DoS" impact tier, though it is weaker than the Critical categories (it needs a valid slot signer key, not an arbitrary unprivileged party, and every action is individually authenticated/authorized — nothing forged or non-canonical is served).

### Likelihood Explanation
Requires only that the attacker already controls a legitimately-provisioned StackerDB slot key (e.g., a signer/miner participant) — no other privilege, node secret, or admin role is needed, and the write is trivially repeatable (any endpoint accepting a chunk works, including the unauthenticated-by-content-signature-only P2P push and the HTTP POST endpoint).

### Recommendation
Enforce `write_freq` in the authoritative write path, not only in the fetch scheduler: check the slot's last `write_time` (already tracked in the `chunks` table, `stackslib/src/net/stackerdb/db.rs:70`, via `get_slot_validation`) inside `StackerDBs::try_replace_chunk` and reject with a new error (e.g., `TooFrequentWrite`) if `now - write_time < write_freq`, and propagate that rejection through `validate_received_chunk` / `handle_unsolicited_StackerDBPushChunk` and the HTTP POST handler's error mapping the same way `TooManySlotWrites` is handled today.

### Proof of Concept
1. Provision a StackerDB slot for principal `P` with `write_freq = 300` (5 minutes) and `max_writes = 100`.
2. As the holder of `P`'s private key, sign and `POST` a 1-byte chunk with `slot_version = 1` to `/v2/stackerdb/P/<contract>/chunks`; observe it is accepted (`try_handle_request`, `stackslib/src/net/api/poststackerdbchunk.rs:197`).
3. Immediately (well under 300s later) sign and POST `slot_version = 2`, `3`, ... up to `100`; each is accepted by `try_replace_chunk` because it never checks elapsed time since the last write — only staleness of version and the `max_writes` ceiling.
4. Observe that every accepted version is subsequently pushed to peers via `make_chunk_push_schedule` (`stackslib/src/net/stackerdb/sync.rs:434`), causing full-speed signature verification and storage churn across the replica set, defeating the pacing that `write_freq` was designed to guarantee.

        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
