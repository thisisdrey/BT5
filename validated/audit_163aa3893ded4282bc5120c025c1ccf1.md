### Title
Unbounded `GetBlobs.revision_paths` Repeated Field Causes RPC-Handler Resource Exhaustion (Field-Duplication-Style DoS) - (File: internal/gitaly/service/blob/get_blobs.go)

### Summary
The `BlobService.GetBlobs` RPC accepts a `GetBlobsRequest` containing a `repeated RevisionPath revision_paths` field with no upper bound on the number of entries and no request-level pagination/limit, unlike its sibling RPC `ListBlobs`, which exposes an explicit `limit` field. This mirrors the "Field Duplication" GraphQL bug class: a client can submit an arbitrarily large repeated collection in a single request, forcing the server to perform one expensive Git object lookup per entry, which can degrade or exhaust Gitaly resources.

### Finding Description
`GetBlobsRequest` is defined with: [1](#0-0) 

Unlike `ListBlobsRequest`, which enforces a `limit` on the number of blobs returned, `GetBlobsRequest` only has a `limit` for bytes-per-blob, not a cap on the number of `revision_paths` entries: [2](#0-1) 

The handler `sendGetBlobsResponse` iterates over every entry in `req.GetRevisionPaths()` unconditionally, performing a `tef.FindByRevisionAndPath` tree lookup (invoking `git-cat-file`/tree traversal machinery) and an `objectInfoReader.Info` call for each entry: [3](#0-2) 

The only validation performed is that the list is non-empty and each revision string is syntactically valid — there is no cap on the number of `RevisionPath` entries: [4](#0-3) 

Because each `RevisionPath` entry triggers a separate object/tree resolution against the repository via `catfile`, a request with a very large number of `revision_paths` (analogous to sending hundreds/thousands of duplicated GraphQL fields) causes the handler to perform a correspondingly large number of Git subprocess/`catfile` operations within a single RPC call, all before any gRPC message-size or count-based safeguard is applied. No global `MaxRecvMsgSize`/`MaxCallRecvMsgSize` limit was found configured for gRPC in this codebase, and the per-RPC concurrency limiter (`[[concurrency]]` config) only throttles concurrent requests per RPC/repository — it does not limit the internal cost of a single already-admitted request. [5](#0-4) 

### Impact Explanation
An authenticated Gitaly client capable of invoking `BlobService.GetBlobs` (e.g., through GitLab Rails/Workhorse acting on behalf of an ordinary user browsing/searching a repository) can submit a single request with an extremely large `revision_paths` array. This drives the server to perform a proportionally large number of expensive tree/blob lookups sequentially in one RPC handler invocation, consuming CPU, catfile-cache/process resources, and increasing response latency — a Denial-of-Service condition affecting the Gitaly node and potentially co-located repositories via `catfile` process contention.

### Likelihood Explanation
The RPC is reachable through the normal blob-retrieval code path with no special privileges beyond ordinary repository read access, and constructing a request with an arbitrarily long `revision_paths` array requires no more effort than crafting a large protobuf message client-side.

### Recommendation
Add an explicit, enforced maximum number of entries permitted in `GetBlobsRequest.revision_paths` (mirroring the `limit` semantics already present on `ListBlobsRequest`), and reject/paginate requests exceeding that bound in `validateGetBlobsRequest`. Alternatively, apply the RPC-level concurrency/queue limiter (`[[concurrency]]`) together with a request-size or item-count guard so a single request cannot trigger unbounded internal work.

### Proof of Concept
1. Establish a gRPC connection with a client authorized to call `BlobService.GetBlobs` on a repository.
2. Construct a `GetBlobsRequest` with `revision_paths` containing many thousands of `RevisionPath` entries (each valid or referencing arbitrary/nonexistent paths), as in: [6](#0-5) 
3. Increase the entry count substantially and observe processing time in `sendGetBlobsResponse` scaling linearly with no rejection, since `validateGetBlobsRequest` only checks for emptiness and per-entry revision syntax, not the total count: [7](#0-6)

// GetBlobsRequest is a request for the GetBlobs RPC.
message GetBlobsRequest {
  // RevisionPath is a combination of revision and path. All objects reachable in the subdirectory of the treeish
  // will be returned.
  message RevisionPath {
    // revision is the revision that identifies the tree-ish. Must not be empty.
    string revision = 1;
    // path is the path relative to the treeish revision that shall be searched for a blob. If the path is empty the
    // root directory of the tree-ish will be searched.
    bytes path = 2;
  }

  // repository is the repository that shall be searched.
  Repository repository = 1[(target_repository)=true];
  // revision_paths identifies the set of revision/path pairs that shall be searched for blobs.
  repeated RevisionPath revision_paths = 2;
  // limit is the maximum number of bytes we want to receive. Use '-1' to get the full blobs no matter how big.
  int64 limit = 3;
}

func sendGetBlobsResponse(
	req *gitalypb.GetBlobsRequest,
	stream gitalypb.BlobService_GetBlobsServer,
	objectReader catfile.ObjectContentReader,
	objectInfoReader catfile.ObjectInfoReader,
) error {
	ctx := stream.Context()

	tef := catfile.NewTreeEntryFinder(objectReader)

	for _, revisionPath := range req.GetRevisionPaths() {
		revision := revisionPath.GetRevision()
		path := revisionPath.GetPath()

		if len(path) > 1 {
			path = bytes.TrimRight(path, "/")
		}

		treeEntry, err := tef.FindByRevisionAndPath(ctx, revision, string(path))
		if err != nil {
			return structerr.NewInternal("find by revision and path: %w", err)
		}

		response := &gitalypb.GetBlobsResponse{Revision: revision, Path: path}

		if treeEntry == nil || len(treeEntry.GetOid()) == 0 {
			if err := stream.Send(response); err != nil {
				return structerr.NewInternal("send: %w", err)
			}

			continue
		}

		response.Mode = treeEntry.GetMode()
		response.Oid = treeEntry.GetOid()

		if treeEntry.GetType() == gitalypb.TreeEntry_COMMIT {
			response.IsSubmodule = true
			response.Type = gitalypb.ObjectType_COMMIT

			if err := stream.Send(response); err != nil {
				return structerr.NewInternal("send: %w", err)
			}

			continue
		}

		objectInfo, err := objectInfoReader.Info(ctx, git.Revision(treeEntry.GetOid()))
		if err != nil {
			return structerr.NewInternal("read object info: %w", err)
		}

		response.Size = objectInfo.Size

		var ok bool
		response.Type, ok = treeEntryToObjectType[treeEntry.GetType()]

		if !ok {
			continue
		}

		if response.GetType() != gitalypb.ObjectType_BLOB {
			if err := stream.Send(response); err != nil {
				return structerr.NewInternal("send: %w", err)
			}
			continue
		}

		if err = sendBlobTreeEntry(response, stream, objectReader, req.GetLimit()); err != nil {
			return err
		}
	}

func validateGetBlobsRequest(ctx context.Context, locator storage.Locator, req *gitalypb.GetBlobsRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetRevisionPaths()) == 0 {
		return errors.New("empty RevisionPaths")
	}

	for _, rp := range req.GetRevisionPaths() {
		if err := git.ValidateRevision([]byte(rp.GetRevision())); err != nil {
			return err
		}
	}

	return nil
}

```markdown
An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
