### Title
StackerDB config-reload failure silently reverts write-rate limits to unbounded (`max_writes`) - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
The Neutron CVE (CVE-2017-7543) is a race condition where, following an update, security enforcement was silently reset to a permissive default (`net.bridge.bridge-nf-call-iptables = 0`), disabling protections that operators believed were in force. `create_or_reconfigure_stackerdbs` in this repo has an analogous fail-open pattern: when a StackerDB's on-chain config fails to load, the in-memory config is silently replaced with `StackerDBConfig::noop()`, which sets `max_writes: u32::MAX`, while the on-disk slot/signer state is deliberately left untouched.

### Finding Description
`StackerDBs::create_or_reconfigure_stackerdbs` reloads each subscribed StackerDB's config once per reward cycle / on refresh triggers: [1](#0-0) 

When `StackerDBConfig::from_smart_contract` fails (e.g., a transient Clarity/DB read error, or the contract temporarily not being queryable), the code falls back to `StackerDBConfig::noop()`: [2](#0-1) 

`StackerDBConfig::noop()` is documented to be a "does nothing" fallback, and its own comment explicitly acknowledges the race: it caps `chunk_size` at `STACKERDB_MAX_CHUNK_SIZE` because "writes can still land on existing slots while `noop()` is active." However, `max_writes` is left at `u32::MAX`: [3](#0-2) 

The reconfigure-skip logic then compounds the problem: reconfiguration of the persisted slot/signer table is explicitly skipped whenever the freshly-fetched config has empty signers (i.e., is the `noop()` fallback), specifically to avoid wiping good on-disk state with a bad fetch — but the *in-memory* map is still overwritten with `noop()` regardless: [4](#0-3) 

The in-memory `stacker_db_configs` map (containing the now-unbounded `noop()` config for that contract) is what gets passed into the write path — `try_replace_chunk`, which enforces the write-count cap using `self.config.max_writes`: [5](#0-4) 

Because `insert_chunk`/`try_replace_chunk` only checks the config object handed to the transaction (`self.config.max_writes`), and that config now reports `u32::MAX`, any already-authorized signer for that contract (still valid, because the signer/slot table was *not* rolled back) can push an unbounded number of chunk versions to their slot for as long as the config reload keeps failing — bypassing the write-frequency ceiling the smart contract's governance intended to enforce (`max-writes`).

### Impact Explanation
This breaks the equality "governance-configured `max-writes` == enforced write cap," causing a state that should be bounded (per the contract's `stackerdb-get-config`) to become effectively unbounded during a config-reload failure window — directly mirroring the Neutron bug where governance-configured firewall state (`security groups`) was silently reset to a permissive default during an update race. It is a bounded/rate-limit fail-open, not a full authentication bypass (a valid slot signature from an already-authorized signer is still required), so it sits at the lower end of the impact scale described in the rules (a rate/quota control failing open rather than an unauthenticated write or forged-data propagation).

### Likelihood Explanation
Triggering requires the on-chain config fetch (`StackerDBConfig::from_smart_contract`) to fail transiently while the local node already has a previously-configured StackerDB with valid signers — this can occur due to normal node/DB hiccups, Clarity call errors, or during a burnchain-tip/reward-cycle refresh, and is not something an external attacker directly controls, only exploits opportunistically once it happens. It requires an existing valid signer, so it's not exploitable by a fully unprivileged remote party.

### Recommendation
Cap `max_writes` in `StackerDBConfig::noop()` to a small/no-write value (or preserve the last-known-good config in-memory instead of falling back to `noop()`) whenever `create_or_reconfigure_stackerdbs` cannot fetch a fresh smart-contract config for an already-initialized StackerDB, analogous to the existing fix already applied to `chunk_size`.

### Proof of Concept
1. Bring up a node that replicates a StackerDB whose smart-contract config was successfully loaded once (real `max_writes` value, e.g. 10).
2. Cause `StackerDBConfig::from_smart_contract` to fail on a subsequent reload (e.g., inject a Clarity read error, or race a burnchain-tip change with a chainstate load failure) so `create_or_reconfigure_stackerdbs` falls back to `StackerDBConfig::noop()` for that contract, while `existing_contract_ids.contains(...)` is true and the fallback's empty `signers` list prevents `reconfigure_stackerdb` from being called (so the on-disk signer table is untouched).
3. As an already-valid signer for a slot in that DB, submit chunk writes with monotonically increasing `slot_version` past the original `max_writes` ceiling (e.g., version 11, 12, 13...).
4. Observe that `try_replace_chunk` accepts these writes because `self.config.max_writes == u32::MAX` from the in-memory `noop()` config, even though the contract's real governance limit was 10. [6](#0-5)

impl StackerDBConfig {
    /// Config that does nothing
    pub fn noop() -> StackerDBConfig {
        StackerDBConfig {
            // Cap the chunk size at the protocol-wide maximum rather than u64::MAX.
            // `noop()` is used as a fallback whenever a replica's real config can't be
            // loaded (see `create_or_reconfigure_stackerdbs`), and it can transiently
            // overwrite a good in-memory config on a failed refresh. Since the DB slots
            // persist independently of the config, writes can still land on existing
            // slots while `noop()` is active, so its chunk-size limit must never be
            // looser than `STACKERDB_MAX_CHUNK_SIZE`.
            chunk_size: STACKERDB_MAX_CHUNK_SIZE as u64,
            write_freq: 0,
            max_writes: u32::MAX,
            hint_replicas: vec![],
            max_neighbors: 8,
            signers: vec![],
        }
    }

        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }

            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
