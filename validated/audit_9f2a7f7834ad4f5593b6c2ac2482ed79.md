## Finding

### Title
Unsynchronized read of `Chainbase.head` / snapshot chain pointers races with `SnapshotManager.refreshOne()` pointer relinking, allowing torn/stale reads or NPE on the query path - (File: `chainbase/src/main/java/org/tron/core/db2/core/Chainbase.java`)

### Summary
This mirrors the CVE-2025-39961 bug class: a writer mutates a small set of related pointer/mode fields under a lock while a reader on a different code path reads the same fields without any synchronization, observing a torn/inconsistent view. In java-tron's `Chainbase`/`SnapshotManager`, the equivalent of AMD IOMMU's `pgtable->root/mode` is the `Chainbase.head` snapshot reference together with the `previous`/`next` pointer chain that forms the "snapshot stack." The write side (`Chainbase.setHead`) is `synchronized`, but the vast majority of read paths that traverse the same structure are not synchronized at all, and a separate maintenance path (`SnapshotManager.refreshOne`) mutates the pointer chain directly on `Chainbase`'s internal `Snapshot` objects without taking `Chainbase`'s monitor.

### Finding Description
`Chainbase` keeps a single mutable field: [1](#0-0) 

Writes to it are guarded by `synchronized`: [2](#0-1) 

But most reads go through the private, unsynchronized `head()` helper or read `head` directly, including the read-facing API used by every state query (`get`, `getUnchecked`, `has`): [3](#0-2) 

and the `prefixQuery` path, which additionally dereferences `head.getRoot()` directly (bypassing even the `head()` accessor) with no synchronization at all: [4](#0-3) 

Meanwhile, `SnapshotManager.refreshOne()` — invoked asynchronously from a per-DB `flushServices` executor thread whenever the revoking stack exceeds `maxSize` (i.e., during ordinary block application, not requiring any malicious input) — reads `db.getHead()`, merges snapshots into the root, and then relinks the snapshot chain and reassigns `head`, all without acquiring `Chainbase`'s monitor: [5](#0-4) 

This is triggered from `buildSession()`, which runs on the block-processing thread as part of ordinary `Manager` transaction/block application: [6](#0-5) 

The `previous`/`next` pointers being relinked live in `AbstractSnapshot`, which stores `next` as a plain `WeakReference` field, with no volatile/atomic semantics: [7](#0-6) 

So exactly as in the kernel bug — writer thread updates `root`/relinks pointers under a lock discipline the reader does not respect — here the flush-service thread relinks `previous`/`next` and reassigns `head` while any concurrent unprivileged HTTP/gRPC/JSON-RPC query thread (going through `Wallet`/`TronJsonRpcImpl` into `AccountStore`, `AssetIssueStore`, etc., all backed by `Chainbase`) can call `get()`/`prefixQuery()`/`getKeysNext()`/`getValuesNext()` and walk `getPrevious()`/`getRoot()` on a chain that is being mutated concurrently, without any shared lock or `volatile` field to establish a happens-before relationship.

### Impact Explanation
A reader can observe a torn view of the snapshot chain during `refreshOne()`'s relinking (`next.getNext().setPrevious(root)` then `root.setNext(next.getNext())` are two separate, non-atomic pointer writes), potentially: returning stale or inconsistent account/balance/asset data to an API caller, throwing an unexpected `NullPointerException`/`ClassCastException` while walking a partially-updated chain (a query-serving thread crash — "an API the node can no longer serve"), or in the worst case silently reading data from the wrong snapshot generation. Because every store the node exposes through `Wallet`/JSON-RPC is backed by `Chainbase`, this affects the whole read-query surface.

### Likelihood Explanation
The race window is small (a handful of pointer assignments during `refreshOne`) and requires the flush to occur (which happens routinely as the revoking stack fills up during normal block production) concurrently with an API/query request touching the exact snapshot being merged. This is not attacker-controlled in the sense of crafting a malicious transaction, but any high-throughput node under sustained query load will regularly hit this window, since flush happens automatically on essentially every block once `maxSize` is reached.

### Recommendation
Make `Chainbase.head` `volatile` (or guard all reads through a single, consistently-acquired lock/read-write lock, similar to the `resetDbLock` pattern already used in `LevelDbDataSourceImpl`/`RocksDbDataSourceImpl`), and ensure `SnapshotManager.refreshOne()` acquires the same lock/monitor on the affected `Chainbase` instance before mutating `previous`/`next`/`head`. Alternatively, adopt a seqlock/copy-on-write style update (analogous to the kernel fix's `seqcount`) so readers can detect and retry on a concurrent update rather than observing a torn pointer chain.

### Proof of Concept
1. Start a node and let the revoking stack (`SnapshotManager.dbs`) exceed `maxSize` during normal block processing so `buildSession()` triggers `flush()` → `refresh()` → `refreshOne()` on a background `flushServices` thread [8](#0-7) .
2. Concurrently issue a burst of read-only HTTP/gRPC/JSON-RPC queries (e.g., `getaccount`, asset/exchange queries) that resolve through `Chainbase.get()`/`prefixQuery()` on the same store being flushed [4](#0-3) .
3. During the window between `next.getNext().setPrevious(root)` and `root.setNext(next.getNext())` in `refreshOne()` [9](#0-8) , a concurrent reader walking `getPrevious()`/`getNext()` (e.g. in `getValuesNext`/`getKeysNext`) can observe an inconsistent chain, producing incorrect query results or an exception that terminates the request-handling thread.

```java
  private void refreshOne(Chainbase db) {
    if (Snapshot.isRoot(db.getHead())) {
      return;
    }

    List<Snapshot> snapshots = new ArrayList<>();

    SnapshotRoot root = (SnapshotRoot) db.getHead().getRoot();
    Snapshot next = root;
    for (int i = 0; i < flushCount; ++i) {
      next = next.getNext();
      snapshots.add(next);
    }

    root.merge(snapshots);

    root.resetSolidity();
    if (db.getHead() == next) {
      db.setHead(root);
    } else {
      next.getNext().setPrevious(root);
      root.setNext(next.getNext());
    }
  }
```
