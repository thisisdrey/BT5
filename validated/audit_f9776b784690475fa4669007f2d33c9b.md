### Title
Account-lifecycle cleanup asymmetry: `remove_account` fails to clear `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId`, letting a stale privileged receipt execute against a re-created account of the same name - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/actions.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` only deletes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` entries keyed by the deleted account's name. If account `A` postpones a self-directed `ActionReceipt` (predecessor_id=A, receiver_id=A) containing an `AddKey(FullAccess)` action while awaiting an unresolved `input_data_id`, then deletes itself via `DeleteAccountAction`, these three trie rows survive. When a third party later creates a brand-new account named `A` and the delayed `DataReceipt` finally arrives, `process_receipt`'s `Data` branch resolves the stale postponed receipt and executes it against the new account, installing the attacker's public key with `FullAccess`.

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-575) enumerates and removes only `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` rows for the account being deleted: [1](#0-0) [2](#0-1) 

`action_delete_account` (runtime/runtime/src/actions.rs:314-390) calls `remove_account` and never checks for or clears any outstanding `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows tied to the account: [3](#0-2) 

These rows are created in `process_action_receipt` (runtime/runtime/src/lib.rs:1593-1658) whenever a self-directed `ActionReceipt` (predecessor_id=A, receiver_id=A) has an unresolved `input_data_id`: the receipt is stored as `PostponedReceipt{receiver_id: A, receipt_id}`, plus `PendingDataCount{receiver_id: A, receipt_id}` and `PostponedReceiptId{receiver_id: A, data_id}`: [4](#0-3) 

Because `check_actor_permissions` (runtime/runtime/src/actions.rs:739-785) only requires `actor_id == account_id` for `Action::AddKey`, and `apply_action_receipt` sets `actor_id = receipt.predecessor_id().clone()` unconditionally from the receipt's own field (runtime/runtime/src/lib.rs:855), a postponed receipt crafted with predecessor_id=A, receiver_id=A trivially satisfies this check with no cryptographic signature re-verification at execution time: [5](#0-4) [6](#0-5) 

When the delayed `DataReceipt` eventually arrives, `process_receipt`'s `VersionedReceiptEnum::Data` branch (runtime/runtime/src/lib.rs:1386-1455) looks up `PostponedReceiptId{receiver_id: account_id, data_id}` purely by the account-name string, finds the stale link, decrements `PendingDataCount` to 0, fetches the stale `PostponedReceipt`, removes it, and executes it via `apply_action_receipt` — against whatever account currently occupies that name: [7](#0-6) 

None of `check_account_existence`, `check_actor_permissions`, nonce checks, or access-key permission checks re-validate that the executing account is the same logical account that created the postponed receipt — trie keys are namespaced only by `AccountId` string, not by an account-creation identity/nonce, so a freshly created account with the same name silently inherits the stale privileged action.

### Impact Explanation
This is an authorization-escalation / account-takeover bug: a victim who creates and funds a brand-new account whose name happens to match a previously deleted account can have an attacker-controlled `FullAccess` key silently installed on it without ever signing a transaction granting that permission, matching the "authorization escalation across accounts or promises" bounty category. The attacker fully controls timing (they choose when to delete A and can arrange for the dangling promise's callee to respond after recreation), and the resulting privilege lets them drain the new account's funds or acquire any assets sent to it.

### Likelihood Explanation
Preconditions: attacker deploys/owns account A and a contract capable of issuing a self-directed promise chain with an unresolved `input_data_id` (e.g., a cross-contract call whose callback embeds `AddKey`), then deletes A via a normal `DeleteAccountAction` — a standard, permission-checked, unprivileged operation requiring no special access. The only external dependency is that a third party later creates an account with the exact same name and that the original dangling `DataReceipt` arrives afterward; both are plausible for short/common account names or names deliberately chosen/squatted by the attacker, and the attack is repeatable at low cost (storage/gas fees only).

### Recommendation
In `action_delete_account`/`remove_account`, before or during account deletion, iterate and remove all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie rows scoped to the account being deleted (mirroring the existing access-key/contract-data iteration pattern in `remove_account`), or reject `DeleteAccountAction` while any postponed receipt is outstanding for that account.

### Proof of Concept
Runtime integration test plan (in the style of `runtime/runtime/src/tests/apply.rs`, using `create_receipt_with_actions`):
1. Set up account `A` (e.g. `alice.near`) and construct an `ActionReceipt` with predecessor_id=A, receiver_id=A, `input_data_ids: [dangling_id]`, and `actions: [AddKey(attacker_pubkey, FullAccess)]`; feed it through `apply` so `process_action_receipt` postpones it, asserting `state_update.get` returns `Some` for `TrieKey::PostponedReceipt{A, receipt_id}`, `TrieKey::PendingDataCount{A, receipt_id}`, and `TrieKey::PostponedReceiptId{A, dangling_id}`.
2. Submit a `DeleteAccountAction` receipt for A (beneficiary attacker-controlled); after applying, assert the three keys above are still `Some` (survive `remove_account`), while `TrieKey::Account{A}` is `None`.
3. Submit a `CreateAccountAction`/`Transfer` receipt from a different predecessor that creates and funds a new account named A.
4. Deliver a `Data` receipt with `receiver_id: A, data_id: dangling_id`; after `apply`, assert the new account A now has an access key equal to `attacker_pubkey` with `AccessKeyPermission::FullAccess`, and that `TrieKey::PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` for A are now `None`.
