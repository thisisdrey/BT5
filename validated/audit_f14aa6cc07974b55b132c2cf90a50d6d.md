## Title
Timing side-channel in HTTP `authorization` header comparison across multiple RPC endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`, `postblock_v3.rs`, `blocksimulate.rs`, `blockreplay.rs`, `fastcallreadonly.rs`, `txsimulate.rs`)

### Summary
Several stacks-node RPC endpoints authenticate remote callers by comparing the `authorization` HTTP header against the configured secret (`auth_token`/`auth`) using Rust's default `!=` (`str`/`String` `PartialEq`), which is a byte-wise, early-exit comparison rather than a constant-time comparison. This is the same bug class as CVE-2016-10535 (csrf-lite): fail-early secret comparison leaks per-byte correctness via timing, letting a remote attacker recover the shared secret without knowing it.

### Finding Description
The RPC handlers gate privileged endpoints with a plaintext shared secret check of the form:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) [2](#0-1) [3](#0-2) 

The same pattern occurs in `blockreplay.rs`, `fastcallreadonly.rs`, and `txsimulate.rs` (all matched by `auth_header != password`). These handlers are wired up in `StacksHttp::register_rpc_methods` with the node's configured `auth_token`, which secures the block-proposal endpoint used for miner↔signer coordination and the authenticated broadcast/simulate endpoints [4](#0-3) . The `auth_token` itself is documented as the exact-match secret shared between node and signer [5](#0-4) .

Rust's `PartialEq` for `str`/`String` compares lengths first, then does a linear/early-exit byte comparison (effectively `memcmp`) — it is documented as *not* constant-time and stops as soon as a mismatch is found. This is architecturally identical to the `csrf-lite` flaw: a plaintext secret is checked with a comparison whose execution time depends on how many leading bytes of the guess match the real secret, instead of a fixed-time comparison (e.g. `subtle::ConstantTimeEq` or a MAC-based check).

### Impact Explanation
An unauthenticated remote attacker who can reach these HTTP endpoints (e.g. `/v3/block_proposal`, `/v3/blocks/replay`, `/v3/blocks/simulate/*`, `/v3/contracts/fast-call-read/*`, `/v3/transactions/simulate`, or `/v2/blocks?broadcast=1` on `postblock_v3`) can measure response latency for varying guesses of the `authorization` header value and use per-character timing differences to reconstruct the `auth_token` secret, bit-by-bit rather than needing to brute force the entire secret space at once. Once the secret is recovered, the attacker gains authenticated access to endpoints intended to be restricted to the paired `stacks-signer`/trusted operator — e.g., submitting block proposals or broadcasting blocks via the now-forged `Authorization` header, i.e. an auth bypass on state-affecting endpoints. This aligns with the "High" impact class described in scope (auth bypass reachable via crafted messages).

### Likelihood Explanation
Exploitability depends on network jitter and the granularity of timing measurable over the wire; classic remote timing attacks against fixed-length secret comparisons have been demonstrated to be practical over LAN and even WAN with enough samples/statistics, especially since these are simple HTTP endpoints that can be probed repeatedly with byte-by-byte extension attacks. No privileged access or the node's private key is required — only network reachability to the RPC port, matching the "remote, unprivileged" bar in scope.

### Recommendation
Replace all `auth_header != password` / `auth_header == password` string comparisons with a constant-time comparison (e.g., `subtle::ConstantTimeEq::ct_eq` on the byte slices, or compare `Sha256(auth_header) == Sha256(password)` digests) in `postblock_proposal.rs`, `postblock_v3.rs`, `blocksimulate.rs`, `blockreplay.rs`, `fastcallreadonly.rs`, and `txsimulate.rs`, so that comparison time does not depend on the position of the first mismatched byte.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. Send repeated POST requests to `/v3/block_proposal` with an `authorization` header guessing the secret byte-by-byte, e.g. starting with correct prefixes of increasing length versus random suffixes.
3. Measure response latency for the 401 rejection path in `try_parse_request` (`stackslib/src/net/api/postblock_proposal.rs:1136-1144`); requests whose header matches a longer correct prefix take marginally longer due to the byte-wise comparison continuing further before mismatching.
4. Statistically aggregate timing samples per candidate byte to iteratively recover `auth_token`, then use the recovered secret to submit authenticated block proposals/broadcasts.
