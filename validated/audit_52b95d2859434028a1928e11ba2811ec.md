### Title
Non-constant-time password comparison enables timing side-channel auth bypass on fast-call-read endpoint - (File: stackslib/src/net/api/fastcallreadonly.rs)

### Summary
`try_parse_request` compares the caller-supplied `Authorization` header against the configured secret using Rust's default `String` `!=` operator, which performs a byte-wise, short-circuiting comparison. Because the comparison time depends on the length of the matching prefix, a remote attacker without the secret can iteratively refine header guesses and, given enough samples per byte, narrow down the password using timing variance.

### Finding Description
At [1](#0-0) , the handler does:
```
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
`String`'s `PartialEq` implementation compares underlying byte slices and returns `false` as soon as a mismatching byte (or differing length) is found, so comparison cost is proportional to the length of the correctly-guessed prefix. This is the classic non-constant-time secret comparison anti-pattern: an attacker who can measure response latency with enough precision and repetition could in principle infer prefix-match length and recover the secret byte-by-byte instead of brute-forcing the full keyspace. No other code path performs a constant-time check before this comparison; the endpoint has no other gating in `try_parse_request`.

### Impact Explanation
If successfully exploited, an attacker recovers the `auth` secret used to gate `/v3/contracts/fast-call-read/...`, granting them the same access as a legitimate holder of that secret — unrestricted access to the fast-call-read-only Clarity execution endpoint, which is otherwise supposed to require this shared secret. This matches the "auth bypass on a gated endpoint" Critical category, since possession of the secret is the only guard on this handler.

### Likelihood Explanation
Precondition: fast-call-read auth must be configured (`self.auth = Some(password)`) and the RPC endpoint must be reachable by the attacker without any other credential — both attacker-favorable conditions per the question's threat model. However, exploiting this in practice requires an extremely high number of samples per byte position to overcome network jitter, since the actual computational time difference for comparing a handful of extra bytes in a `memcmp`-style operation is on the order of nanoseconds, while realistic network round-trip jitter over any real network is on the order of microseconds to milliseconds — several orders of magnitude larger. This makes practical exploitation over a network extremely difficult, though the code pattern itself is a legitimate anti-pattern that should be fixed defensively.

### Recommendation
Replace the direct `!=` comparison with a constant-time comparison, e.g., using `subtle::ConstantTimeEq` on the byte representations of `auth_header` and `password`, or by first hashing both sides (e.g., HMAC) and comparing digests in constant time.

### Proof of Concept
A Rust test in `fastcallreadonly.rs`'s test module could construct an `RPCFastCallReadOnlyRequestHandler` with `auth = Some("A".repeat(64))`, then call `try_parse_request` with headers containing increasingly-correct prefixes (e.g., 0, 16, 32, 48 correct leading bytes followed by incorrect trailing bytes) while measuring wall-clock time via `std::time::Instant` around the call, averaged over many thousands of iterations to reduce noise, and assert whether mean timing increases monotonically with correct-prefix length — demonstrating the underlying non-constant-time comparison, independent of whether it is practically exploitable over a real network.
