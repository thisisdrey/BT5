### Title
Missing Abort Notification in `CrossShardCommitSender` Causes Permanent Deadlock in Dependent Shards — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

### Summary

`TransactionCommitHook` has exactly one method — `on_transaction_committed` — and no `on_execution_aborted` counterpart exists anywhere in the codebase (confirmed by exhaustive grep). When a transaction in shard A aborts, `on_transaction_committed` is never called, so `CrossShardCommitSender` never sends a cross-shard message to shard B. Shard B's `RemoteStateValue` for the dependent key remains permanently in `Waiting` status. `RemoteStateValue::get_value()` uses an unbounded condvar wait with no timeout, so the shard B execution thread blocks forever. Because `execute_block` never returns, the `StopMsg` that would terminate shard B's receiver thread is also never sent. The entire block execution deadlocks.

### Finding Description

**Step 1 — The trait has no abort hook.**

`TransactionCommitHook` declares only one method: [1](#0-0) 

There is no `on_execution_aborted` method. The grep search for `on_execution_aborted` returns zero matches across the entire repository.

**Step 2 — `CrossShardCommitSender` only notifies on commit.**

The `TransactionCommitHook` implementation for `CrossShardCommitSender` calls `send_remote_update_for_success`, which iterates the actual write set and sends each written key to dependent shards: [2](#0-1) 

When a transaction aborts, `on_transaction_committed` is never invoked by the block executor, so no message is ever sent to shard B.

**Step 3 — The hook is only called on the commit path.**

`record_finalized_output` is the sole call site for the hook, and it is only reached for transactions that successfully pass through `materialize_txn_commit`: [3](#0-2) 

Aborted transactions (`ExecutionStatus::Abort`) produce no output and are never queued for commit, so `record_finalized_output` is never called for them.

**Step 4 — Shard B initializes all cross-shard keys in `Waiting` status.**

`create_cross_shard_state_view` inserts every required cross-shard key as `RemoteStateValue::waiting()`: [4](#0-3) 

**Step 5 — `get_value()` blocks indefinitely with no timeout.**

`RemoteStateValue::get_value()` loops on `cvar.wait()` until the status transitions away from `Waiting`. There is no timeout, no cancellation token, and no fallback: [5](#0-4) 

**Step 6 — The `StopMsg` is never sent to shard B.**

In `execute_transactions_with_dependencies`, the `StopMsg` that terminates shard B's `CrossShardCommitReceiver` is sent only after `execute_block` returns: [6](#0-5) 

Because shard B's execution thread is blocked in `get_value()`, `execute_block` never returns, so the `StopMsg` is never sent. Both the execution thread and the receiver thread are permanently stuck.

### Impact Explanation

If the sharded block executor is active, any block containing a transaction that (a) aborts and (b) has at least one registered cross-shard dependent edge will cause the entire block execution to deadlock on every validator running the sharded executor. No block can be committed until the process is restarted. This is a material chain availability failure.

### Likelihood Explanation

The sharded block executor requires explicit configuration to enable and is not the default execution path. Whether it is currently active on mainnet validators cannot be determined from the repository alone. If it is enabled, the trigger condition is straightforward: submit any transaction that aborts (e.g., a Move script with `abort(0)`, a transaction that runs out of gas, or any failed assertion) that the partitioner assigns to a shard with a cross-shard dependent edge. The attacker does not need privileged access — only the ability to submit a transaction.

### Recommendation

1. Add an `on_execution_aborted(txn_idx: TxnIndex)` method to `TransactionCommitHook`.
2. Implement it in `CrossShardCommitSender` to send `RemoteTxnWriteMsg` with `write_op = None` for every key in `dependent_edges[txn_idx]`, mirroring the `None` path already handled by `CrossShardCommitReceiver::start` (`write_op.and_then(|w| w.as_state_value())`).
3. Call the abort hook from the block executor wherever a transaction is finalized as aborted.
4. Alternatively, add a bounded timeout to `RemoteStateValue::get_value()` as a defense-in-depth measure.

### Proof of Concept

```
1. Partition two transactions: T1 (shard A, writes key K, body = abort(0)) and
   T2 (shard B, reads key K, has required cross-shard edge on K from T1).
2. Start sharded block execution.
3. Shard A executes T1 → aborts → on_transaction_committed never called →
   no RemoteTxnWriteMsg sent to shard B.
4. Shard B's execution thread calls get_state_value(K) →
   RemoteStateValue::get_value() → cvar.wait() → blocks forever.
5. execute_block on shard B never returns → StopMsg never sent →
   receiver thread also stuck.
6. Assert (via timeout) that shard B's executor thread does not terminate
   within any finite deadline → deadlock confirmed.
```

        base_view: &'a S,
        transactions: &[TransactionWithDependencies<AnalyzedTransaction>],
    ) -> CrossShardStateView<'a, S> {
        let mut cross_shard_state_key = HashSet::new();
        for txn in transactions {
            for (_, storage_locations) in txn.cross_shard_dependencies.required_edges_iter() {

            }
        }
