### Title
Unbounded array allocation from attacker-controlled length field in TVM precompiled-contract signature array parsing - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2018-18193 is an operator `new[]` failure in `libgig`'s `DLS::File::File`, where an attacker-controlled length field (`pWavePoolTable`) is used directly as an allocation size without validation, causing a crash via an oversized heap allocation. The analogous pattern in java-tron is in the helper functions `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java`, which read an array-length word directly out of calldata and immediately allocate a Java array of that size before any bound is checked against the size of the actual input data.

### Finding Description
The helper methods parse ABI-encoded dynamic arrays out of raw calldata passed into a precompiled contract (used by contracts such as the batch signature validation precompile, `BatchValidateSign`, referenced at [1](#0-0) ). The `len` value is taken directly from an attacker-supplied `DataWord` via `intValueSafe()` and used to size a Java array immediately: [2](#0-1) 

`extractBytes32Array` has no bound check on `len` at all before doing `new byte[len][]`, and `extractBytesArray` only checks that `offset` is within `words.length`, not that `len` (the number of array elements to allocate) is consistent with the amount of calldata actually supplied. `extractSigArray` has the same shape: [3](#0-2) 

Because `len` is decoded from a 256-bit calldata word and truncated to an `int` via `intValueSafe()`, an attacker who calls the corresponding precompiled contract address with crafted calldata can set `len` close to `Integer.MAX_VALUE`. This immediately triggers `new byte[len][]` (an array of ~2.1 billion object references), which the JVM will attempt to allocate before the loop that would actually populate/validate elements ever runs. This mirrors the libgig bug class exactly: an untrusted size field is trusted for a bulk allocation before the corresponding data is verified to exist.

### Impact Explanation
A successful trigger causes the JVM heap allocator to attempt an outsized array allocation, throwing `OutOfMemoryError` inside the TVM execution path. Depending on JVM heap configuration and GC behavior under memory pressure, this can degrade or crash the node process handling the transaction, and because this code runs during contract execution as part of normal block processing, a crafted transaction that is included in a block could cause the same crash on every full node that replays that block, impacting availability/consensus liveness — matching the "node crash/halt" acceptance criterion.

### Likelihood Explanation
The precompiled contract is reachable by any account by invoking a smart contract that calls into the relevant precompile address with attacker-controlled calldata (no special permission, SR, or witness status required) — this is a standard `TriggerSmartContract` broadcast by an unprivileged transaction sender. The only barrier is that the transaction must first be accepted by the TVM's energy accounting for the precompile (`getEnergyForData`), but the array-allocation call happens inside contract-argument parsing, which is not bounded by energy consumed so far when the allocation itself throws.

### Recommendation
Before allocating `new byte[len][]` (or similarly sized arrays) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual remaining size of `data`/`words` (e.g., require `len * elementSize <= data.length - offset`) and reject with an exception if the declared length is inconsistent with the available payload, mirroring the bound checks already used elsewhere (e.g., `verifyLength` in `RLP.java`, or the `subBytes` bound checks in `ContractEventParser.java`).

### Proof of Concept
1. Deploy or call a contract that dispatches calldata to the batch-signature-validation precompiled contract address.
2. Craft the ABI-encoded array-length word (the word at the array offset consumed by `extractBytesArray`/`extractBytes32Array`/`extractSigArray`) to a very large value (e.g., `0x7fffffff`).
3. Broadcast the transaction; when the precompile's `execute` method calls the vulnerable helper, `new byte[len][]` is attempted with an enormous size, triggering `OutOfMemoryError` during TVM execution on any node that processes the transaction.

Note: I was not able to fully trace the exact call site inside `BatchValidateSign.execute()` that invokes these helpers due to tool-call limits; the vulnerable allocation pattern itself, however, is directly visible and unguarded in the cited helper methods.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
