### Title
Unprivileged dust transfers can fill a victim's per-account token list to `MAX_TOKENS_PER_USER`, causing spurious `UserReachedMaxTokens` reverts that block minting new debt positions - (File: contracts/Pool.sol)

### Summary
The bug class in CVE-2021-4454 is a spurious assertion: an invariant that was assumed ("refcount ≥ 2 at deactivate") but is not actually guaranteed under legitimate interleavings, causing a WARN/abort on a path that is otherwise fine. The Metronome analog is the `MAX_TOKENS_PER_USER` account-list cap in `Pool.sol`. The code assumes a user's `debtTokensOfAccount + depositTokensOfAccount` list only grows through the user's own actions, but `DepositToken._transfer` appends the recipient to `depositTokensOfAccount` on *any* inbound transfer with no opt-in. An attacker can push the victim's list to the cap with dust transfers, after which `addToDebtTokensOfAccount`/`addToDepositTokensOfAccount` revert with `UserReachedMaxTokens`/`DepositTokenAlreadyExists`-adjacent errors on otherwise-valid operations — a spurious availability failure analogous to the errant `WARN_ON_ONCE`.

### Finding Description
`Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when a user's combined token list reaches `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:143-148`). The list grows in `addToDepositTokensOfAccount` (`contracts/Pool.sol:216-220`), which is invoked from `DepositToken._transfer` whenever the recipient's balance was zero (`contracts/DepositToken.sol:517-520`). Since `DepositToken.transfer`/`transferFrom` are public and unrestricted for unlocked balances (`contracts/DepositToken.sol:348-376`), any EOA can mint themselves dust of each enabled deposit token (or receive dust) and `transfer` 1 wei of each distinct deposit token to a victim. Each transfer appends a new entry to the victim's `depositTokensOfAccount`.

Once the victim's list is at 30 entries:

- `DebtToken.issue` → `_mint` → `pool.addToDebtTokensOfAccount` reverts `UserReachedMaxTokens` for any debt token the victim does not already hold (`contracts/DebtToken.sol:597-600`), blocking the victim from opening new synthetic-debt positions.
- `DebtToken.mint` via `SmartFarmingManager.leverage` fails identically, breaking the leverage flow.
- `DepositToken.deposit`/`_transfer` to the victim reverts for any deposit token not already in their list (`contracts/DepositToken.sol:485-488`), so the victim cannot receive new collateral types — including `depositToken_.seize` proceeds if they were ever a recipient.

The revert fires even though nothing is wrong with the victim's state — exactly the "WARN fires but the system is fine" pattern: the cap check encodes an assumed bound that untrusted third parties can violate.

### Impact Explanation
Temporary freezing of funds/functionality for the victim: they cannot issue new synthetic asset types, cannot leverage through `SmartFarmingManager`, and cannot receive deposit tokens not already in their list, until they manually transfer out a dust balance to free a slot (`_transfer` removes entries on zero balance, `contracts/DepositToken.sol:522-525`). The attack is cheap: the dust is recoverable by the attacker at any time by transferring it back out. If the victim is unaware, the griefing persists indefinitely and can be timed (front-run) to break a specific `issue`/`leverage` transaction.

### Likelihood Explanation
Feasibility depends on the deployed pool having enough enabled deposit tokens to reach 30 — `addDepositToken` permits up to `MAX_TOKENS_PER_USER` (`contracts/Pool.sol:703`). On pools with few collaterals the cap is unreachable via deposit tokens alone (debt tokens are non-transferable, so the attacker cannot force debt-token entries). On a fully populated pool, the attack is a sequence of ordinary `transfer` calls, entirely unprivileged. No privileged role, oracle manipulation, or flash loan is needed. Mitigation exists (victim can empty a dust balance), so impact is temporary rather than permanent freezing.

### Recommendation
Do not gate per-account list additions on a hard cap that third parties can influence, or make additions idempotent/free for recipients. Options:

- In `_transfer`/`_mint`, let `addToDepositTokensOfAccount` be best-effort for recipients (skip the cap check or the revert when the addition was unsolicited), keeping the cap only for the actor who initiates the action.
- Alternatively, allow removals to always succeed and have reads iterate a bounded view, or raise/remove the cap and bound iteration cost another way, since `debtOf`/`depositOf` already iterate the full lists.

### Proof of Concept
Hardhat-style reproduction (fork of a deployment with ≥30 deposit tokens):

```ts
// setup: pool with 30 active depositTokens dt[0..29], victim has a healthy position
const victim = bob.address
for (let i = 0; i < 30; i++) {
  // attacker self-deposits dust then transfers 1 wei of each deposit token to victim
  await dt[i].connect(alice).deposit(1, alice.address)
  await dt[i].connect(alice).transfer(victim, 1)
}
// victim's depositTokensOfAccount list is now at cap
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30)

// victim tries to issue a synthetic asset type they don't already owe
await expect(
  debtToken.connect(bob).issue(parseEther('1'), bob.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// same for any deposit of a not-yet-held token, and for SmartFarmingManager.leverage
```

Note: I did not verify the current deployments' enabled-token counts; the finding requires a deployment where the number of distinct deposit + debt tokens reachable can reach 30, which `addDepositToken` permits.
