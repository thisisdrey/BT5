### Title
Positions with debt at or below `debtFloorInUsd` can never be liquidated — permanent liquidation deadlock enabling bad-debt insolvency - ([File: contracts/Pool.sol])

### Summary
The external report describes a deadlock where a state transition permanently reverts. The reachable Metronome analog is in `Pool.liquidate`: the interaction between the `maxLiquidable` repay cap (50%) and the `debtFloorInUsd` residual-debt check creates a range of underwater positions for which every possible `amountToRepay_` reverts. Once a position's debt decays to ≤ `debtFloorInUsd`, it is permanently unliquidatable — a liveness deadlock on the liquidation path, directly analogous to an epoch-close deadlock.

### Finding Description
`liquidate` enforces two constraints on `amountToRepay_`:

- `amountToRepay_ / debtBalance <= maxLiquidable` (50%), so partial repayment only.
- The remaining debt must be `0` or `>= debtFloorInUsd`; `0 < remaining < floor` reverts with `RemainingDebtIsLowerThanTheFloor` (`contracts/Pool.sol:571-578`). [1](#0-0) 

For a position whose debt in USD is in the open interval `(floor, 2*floor]`, the only repayments that satisfy the floor check either leave a remainder `< floor` (revert) or require repaying the full debt (which exceeds the 50% `maxLiquidable` cap → `AmountGreaterThanMaxLiquidable`). Repeated partial liquidation converges the debt to exactly `debtFloorInUsd`, at which point any nonzero repayment leaves a remainder below the floor and full repayment breaches the cap — the position is permanently stuck. An unprivileged attacker can manufacture this state deliberately: deposit collateral, `DebtToken.issue` a debt sized just above the floor, and wait for interest accrual or a small adverse oracle move to push it underwater. No privileged action is needed.

### Impact Explanation
Protocol insolvency. The liquidation path — the only mechanism to clear bad debt (seizing `DepositToken` collateral against burned debt) — deadlocks for these positions. As collateral value falls further, the pool retains debt it can never clear, leaving synthetic-token holders/last-exit depositors to absorb the shortfall. This matches the bug class: a required state transition permanently reverts under reachable conditions.

### Likelihood Explanation
Reachable by any unprivileged user whenever `debtFloorInUsd > 0` is configured (the check is only active then). The attacker controls the exact debt size at issuance, so landing in the deadlocked band is fully deterministic; the position only needs to become unhealthy via ordinary price movement or interest accrual. No modifier stops it: `whenNotShutdown`, `nonReentrant`, and the health check all pass normally — the revert is intrinsic to the repayment-bounds logic.

### Recommendation
When `remaining debt < debtFloorInUsd` and `remaining != 0`, either (a) allow the liquidator to repay the full remaining debt (waive `maxLiquidable` when a partial repayment would fall below the floor), or (b) revert at issue/repay time to prevent positions from being created inside the deadlocked band. A typical fix is `if (remaining < floor) amountToRepay_ = debtBalance` before the cap check, or ordering the floor adjustment ahead of `maxLiquidable` enforcement.

### Proof of Concept
Hardhat (against deployed pool on fork or fixture):

```ts
// 1. Alice deposits collateral and issues debt D such that floor < D <= 2*floor (in USD).
await depositToken.connect(alice).deposit(collateral, alice.address);
await debtToken.connect(alice).issue(debtAmount, alice.address); // debt just above floor

// 2. Price drops / interest accrues -> position unhealthy.
await oracle.updatePrice(collateralUnderlying, lowerPrice); // fork/mock price move
expect(await pool.isPositionHealthy(alice.address)).to.be.false;

// 3. Every liquidate call reverts:
//    - partial repay <= 50% leaves 0 < remaining < floor  -> RemainingDebtIsLowerThanTheFloor
//    - full repay > 50% cap                                -> AmountGreaterThanMaxLiquidable
await expect(pool.connect(liq).liquidate(alice.address, synth.address, depositToken.address, partialAmt))
  .to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');
await expect(pool.connect(liq).liquidate(alice.address, synth.address, depositToken.address, fullDebt))
  .to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');
// For debt == floor exactly: any nonzero amountToRepay_ hits one of the two reverts -> permanent deadlock.
```

Note: I verified the liquidation constraint logic in `Pool.sol` directly; I did not re-verify the exact `quoteLiquidateOut` seize math or the deployed `debtFloorInUsd` value on each chain, so the PoC should be run against a fork to confirm the configured floor is nonzero.
