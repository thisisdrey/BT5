### Title
Missing hash verification of downloaded `Attachment` content allows a malicious peer to permanently block resolution of a real attachment - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any decodable `Attachment` payload from a peer without checking that `attachment.hash()` matches the `content_hash` that was actually requested. Because `AttachmentsBatch::resolve_attachment` and `AttachmentsDownloader::run`'s `Done` handling both key off the *received* attachment's own hash rather than the originally requested hash, a peer that lies about having the attachment (via the inventory step) and returns a bogus/empty attachment can make the real attachment's tracking entry stay unresolved indefinitely, while its own reliability score is inflated as if it served a valid response.

### Finding Description
The audit's core equality claim is confirmed: `Attachment::empty().hash() == Hash160::from_data(&[])` is a fixed value, and for essentially any real `content_hash` this will not be equal to the requested hash. Tracing the code:

- `Requestable for AttachmentRequest::make_request_type` builds `GET /v2/attachments/{content_hash}` from the requested hash [1](#0-0) , but nothing ties the response back to that hash.
- `AttachmentsBatchStateContext::extend_with_attachments` decodes the HTTP body via `decode_atlas_get_attachment()` and inserts `response.attachment` into `self.attachments` (a `HashSet<Attachment>`) with **no comparison** of `attachment.hash()` to `request.content_hash`; it also unconditionally calls `report.bump_successful_requests()` for the responding peer [2](#0-1) .
- When the batch reaches `Done`, `AttachmentsDownloader::run` iterates `context.attachments.drain()` and calls `find_all_attachment_instances(&attachment.hash())` and `context.attachments_batch.resolve_attachment(&attachment.hash())` — both use the hash **derived from the attacker-supplied content**, not the original `content_hash` that was requested [3](#0-2) .
- `AttachmentsBatch::resolve_attachment` only removes entries from `attachments_instances` whose tracked `content_hash` equals the passed-in hash [4](#0-3) .

So if an attacker (already selected as a source because it falsely advertised having the attachment in the earlier `/v2/attachments/inv` step, which is also unauthenticated peer data) returns `Attachment::empty()` (or any content whose hash ≠ the real `content_hash`) for a legitimate non-empty attachment request:
1. The response is accepted as "successful" for reliability purposes, artificially raising the attacker's `ReliabilityReport` score (`bump_successful_requests`) — making it more likely to be picked again via `AttachmentRequest::get_most_reliable_source` (`max_by_key` on score) [5](#0-4) .
2. `find_all_attachment_instances(&Hash160::from_data(&[]))` will not match the real instance's tracked hash, so no legitimate pairing occurs for the real request.
3. `resolve_attachment(&Hash160::from_data(&[]))` will not remove the real (non-empty-hash) entry from `attachments_instances`, so `has_fully_succeed()` stays `false` and the batch is re-queued via `bump_retry_count()` [6](#0-5) .
4. Because the attacker's reliability score keeps increasing every round (each bogus response counts as "successful"), it can remain the top-scoring/selected source on subsequent retries, repeating this indefinitely until `retry_count >= max_attachment_retry_count`, at which point the batch — and therefore the real attachment instance — is silently dropped: `"Atlas: dropping batch {:?} retries count exceeded"` [7](#0-6) .

No code path in `stackslib/src/net/atlas/download.rs` compares the received `Attachment`'s content hash to the requested `content_hash` before accepting it as a success or before feeding it into `resolve_attachment`/`find_all_attachment_instances`. This confirms the audit's premise that no such re-validation guard exists.

### Impact Explanation
This is a targeted denial of the Atlas attachment subsystem (which backs BNS zonefiles/subdomain attachments), not a crash or forged canonical state: a single lying peer can (a) permanently prevent a specific, real attachment from ever being resolved by a node (dropped after `max_attachment_retry_count` retries), and (b) pollute that node's `AtlasDB` with attacker-chosen "instantiated" attachment content keyed to `Hash160::from_data(&[])` (harmless in isolation, since that key is also used for legitimate empty/unbind data, but it demonstrates unauthenticated writes influenced entirely by attacker input). The most concrete effect is repeatable resolution failure for legitimate attachments — this matches the "High: attachment/BNS mismatch" category (attachment never resolves / is effectively withheld) rather than "Critical" full network DoS, since it requires the attacker to first win selection as the serving peer for that specific hash (via the inventory step) and does not crash the node or corrupt canonical chain state.

### Likelihood Explanation
- The attacker must be one of the `sources` returned for a given `content_hash` in `get_prioritized_attachments_requests`, i.e., it must have previously claimed (via `/v2/attachments/inv`) to hold that attachment — an unprivileged peer can freely lie about this since inventory responses are unauthenticated. [8](#0-7) 
- Only the single highest-`ReliabilityReport`-scoring source is actually queried per attempt (`get_most_reliable_source`), so the attacker benefits from consistently answering (even with garbage) to keep winning selection over honest peers across retries. [5](#0-4) 
- Attacker cost is a single trivial HTTP 200 response with an empty/garbage `Attachment` body per retry round — cheap and remotely reachable over the node's data-plane HTTP endpoint, no secret or privileged role required.
- Preconditions (needing to win the inventory-and-reliability race) make this narrower than "any peer, any hash, zero effort" as phrased in the audit question, but it is fully reproducible for any attacker willing to run a lying peer and answer every round.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments` and before calling `report.bump_successful_requests()`; treat a hash mismatch as a failed/faulty response (`bump_failed_requests`, and optionally blacklist/deprioritize the peer). This closes the gap that lets the FSM `Done` stage's `resolve_attachment`/`find_all_attachment_instances` calls operate on unverified, attacker-controlled hashes.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/download.rs` tests module (or an integration test using two mocked peers):
1. Construct an `AttachmentsBatchStateContext` with one real `AttachmentInstance` whose `content_hash = H` (non-empty, e.g., hash of `b"real content"`).
2. Register two `sources` for `AttachmentRequest{content_hash: H, ...}`: an "attacker" peer and an "honest" peer, both initially with `ReliabilityReport::empty()`.
3. Drive `BatchedRequestsResult::succeeded` so the attacker's response decodes to `Attachment::empty()` (content = `vec![]`), while assert the honest peer is never actually queried because attacker is selected via `get_most_reliable_source` after gaining score.
4. Call `extend_with_attachments` and then simulate `AttachmentsDownloader::run`'s `Done` branch logic (or call `resolve_attachment(&Attachment::empty().hash())` / `find_all_attachment_instances(&Attachment::empty().hash())` directly) and assert:
   - `attachments_batch.attachments_instances` still contains the entry with `content_hash == H` (i.e., `has_fully_succeed() == false`) — proving the real instance was **not** resolved.
   - `reliability_reports` for the attacker peer shows `total_requests_success` incremented despite serving bogus data.
5. Repeat the round `max_attachment_retry_count` times with the same bogus attacker response each time, and assert the batch is eventually dropped (log message `"Atlas: dropping batch ... retries count exceeded"` / batch removed from `priority_queue`) — demonstrating the real attachment for hash `H` is never delivered to `resolved_attachments`.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }

                missing_attachments.remove(&key);
            }
        }
