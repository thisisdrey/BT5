### Title
Out-of-bounds read when resolving a ZIP Local File Header from an attacker-controlled Central Directory offset - (`src/tools/singlejar/input_jar.h`)

### Summary
`InputJar::LocalHeader()` computes the address of a ZIP entry's Local File Header (`LH`) directly from the `local_header_offset()` field of the corresponding Central Directory Header (`CDH`), which is attacker-controlled data read from the jar file, without ever validating that the resulting pointer lies inside the memory-mapped file. Every caller then immediately dereferences fields of that unchecked `LH*` (`file_name_length()`, `extra_fields_length()`, `size()`, `file_name()`), producing an out-of-bounds read analogous to the ARP-field-used-as-unchecked-offset pattern in CVE-2018-16600.

### Finding Description
`InputJar::NextEntry()` walks Central Directory entries and does bounds-check the pointer advance for the *next* CDH: [1](#0-0) 

But when it resolves the Local Header for the *current* entry, it calls `LocalHeader(current_cdh)`, which performs no such check: [2](#0-1) 

`local_header_offset()` on `CDH` is fully attacker-controlled: it is a 32-bit field from the archive, or — if the 32-bit value is the ZIP64 sentinel `0xFFFFFFFF` — an 8-byte value taken from a Zip64 extra field, also supplied by the archive (`src/tools/singlejar/zip_headers.h` `CDH::local_header_offset()`). `MappedFile::address()` performs raw, unchecked pointer arithmetic: [3](#0-2) 

Note that `mapped()` exists precisely to validate such pointers (and is used for the CDH-chain walk), but it is never called for the LH pointer that `LocalHeader()` returns. The resulting out-of-bounds `LH*` is immediately dereferenced by the caller, `OutputJar::AddJar` (used when merging/combining jars, e.g. via `singlejar`'s deploy-jar and `java_import`/library merging paths), which reads `lh->size()`, `lh->file_name_length()`, `lh->compressed_file_size()`, and ultimately copies `num_bytes` of memory starting at the (possibly wild) `LH` pointer into the output artifact: [4](#0-3) 

Since `lh->file_name_length()` / `lh->extra_fields_length()` / `lh->size()` are also attacker-controlled 16-bit fields read from whatever out-of-bounds memory the pointer lands on, the amount of adjacent process memory read and copied into the output jar is essentially unbounded up to 64KB+, and the copy in `AddJar`'s timestamp-normalization path (`memcpy(lh_new, lh, lh_size)`) will read straight past the mapped file: [5](#0-4) 

Reachability: `singlejar` (and its `third_party/ijar/zip.cc` sibling used by `ijar`/interface jars) processes JAR files that a build ingests as raw file inputs — e.g. jars fetched via `http_jar`/`http_file`/Maven artifacts consumed by `java_library`/`java_binary`/`java_import`, or deploy-jar merging. A hostile origin server or compromised artifact publisher supplies the jar bytes; a declared `sha256`/integrity check on the download only guarantees the bytes are the ones the attacker published — it does not validate that the ZIP structure inside is well-formed, so pinned-checksum verification does not stop this class of bug.

### Impact Explanation
An attacker who controls the content of a jar consumed by a Bazel build (matching its declared checksum) can craft a Central Directory entry whose `local_header_offset` points outside the mapped input file. When Bazel's `singlejar` tool merges/copies that entry, it reads and copies out-of-bounds process memory into the resulting build output (deploy jar / merged jar), leaking adjacent heap/mmap memory contents into an artifact that may be inspected, distributed, or otherwise recoverable by the attacker or downstream consumers — an information-disclosure impact matching the referenced CVE class. In the worst case the wild pointer dereference can also crash the build (segfault) rather than merely leaking memory, since the offset is unbounded.

### Likelihood Explanation
Any repository or `java_*` build target that ingests a jar-shaped file, whether via `http_jar`, `http_archive` + jar contents, `java_import`, or Maven dependencies resolved through standard external-dependency mechanisms, exercises `singlejar`'s Central-Directory/Local-Header parsing at every build that merges jars (e.g., producing a deploy jar). No special build flags are required; this is on by default whenever jars are combined. The only requirement is that an unprivileged content publisher supply a byte-for-byte matching, but structurally malicious jar.

### Recommendation
In `InputJar::LocalHeader()` (and the equivalent logic in `third_party/ijar/zip.cc`), validate that the computed `LH*` pointer (and pointer + `sizeof(LH)` + `file_name_length()` + `extra_fields_length()`) is within `mapped_file_.mapped(...)` bounds before returning it, mirroring the check already performed for CDH chain traversal in `NextEntry()`. Reject/diagnose (`diag_errx`) any entry whose local-header offset, together with declared name/extra-field lengths, would read outside the mapped file.

### Proof of Concept
Add a `TEST(InputJarTest, MaliciousLocalHeaderOffset)` in `src/tools/singlejar/` (alongside `input_jar_random_jars_test.cc`) that:
1. Builds a minimal valid ZIP with one Central Directory entry.
2. Patches that entry's `local_header_offset` field (and/or its Zip64 extra-field `attr64` value) to a huge/out-of-range value (e.g., far past `mapped_file_.size()`).
3. Calls `InputJar::Open()` then `InputJar::NextEntry()`.
4. Asserts (under ASan) that no out-of-bounds read/crash occurs, expecting instead a clean `diag_errx`-style rejection — the test currently fails (ASan heap-buffer-overflow / SEGV) because `LocalHeader()` performs no bounds check.
