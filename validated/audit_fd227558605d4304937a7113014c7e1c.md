### Title
`amoSupply` is never decremented when AMO-minted tokens are burned by Pools/DebtTokens, permanently bricking AMO minting at `maxAmoSupply` - ([File: contracts/SyntheticToken.sol])

### Summary

`SyntheticToken` tracks per-source mint budgets: `totalBridgedIn`/`totalBridgedOut` for the ProxyOFT and `amoSupply` for the AMO, each capped (`maxBridgedInSupply`, `maxAmoSupply`). While the bridge counters use *net* supply (`max(in - out, 0)`), `amoSupply` is only incremented on AMO mints (`_mint`, line 342) and only decremented when the AMO itself calls `burn` on its own balance (`_burn`, lines 278–284). When AMO-minted synths that entered circulation are burned by a registered `Pool` or `DebtToken` — the normal `repay`/`liquidate`/debt-repayment path, callable by any user — `amoSupply` is not decremented. The tracker therefore permanently overstates the outstanding AMO supply, and once it reaches `maxAmoSupply`, every subsequent AMO mint reverts with `SurpassMaxAmoSupply` even though the real circulating AMO supply is far below the cap.

### Finding Description

In `SyntheticToken._mint`:

```solidity
// contracts/SyntheticToken.sol:338-347
if (_isMsgSenderProxyOFT(_msgSender)) {
    totalBridgedIn += amount_;
    if (bridgedInSupply() > maxBridgedInSupply) revert SurpassMaxBridgingSupply();
} else if (_isMsgSenderAmo(_msgSender)) {
    amoSupply += amount_;
    if (amoSupply > maxAmoSupply) revert SurpassMaxAmoSupply();
}
totalSupply += amount_;
if (totalSupply > maxTotalSupply) revert SurpassMaxSynthSupply();
```

In `SyntheticToken._burn`:

```solidity
// contracts/SyntheticToken.sol:275-284
if (_isMsgSenderProxyOFT(_msgSender)) {
    totalBridgedOut += amount_;
    if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
} else if (_isMsgSenderAmo(_msgSender)) {
    if (account_ != _msgSender) revert AmoInvalidAccount();
    amoSupply -= amount_;
}
```

The AMO's purpose is to mint synths into the market (e.g., to defend the peg). Those tokens are fungible and end up held by ordinary users. When a user repays debt or is liquidated, `Pool`/`DebtToken` call `syntheticToken.burn(...)`, where `_msgSender()` is the Pool/DebtToken, not the AMO — so the `else if (_isMsgSenderAmo(_msgSender))` branch is skipped and `amoSupply` stays elevated while `totalSupply` correctly decreases. There is no way to attribute a burn back to AMO-minted inventory, and there is no function to decrease `amoSupply` administratively (`updateMaxAmoSupply` only changes the cap).

An unprivileged attacker can deliberately accelerate this: acquire AMO-minted synths on the open market and burn them via `repay`/`repayAll` on their own position (or via liquidation), permanently consuming AMO mint headroom without the AMO ever burning.

### Impact Explanation

Once `amoSupply` reaches `maxAmoSupply`, `SyntheticToken.mint` reverts with `SurpassMaxAmoSupply` for the AMO on every call, even though the actual AMO-originated circulating supply may be near zero (all burned via debt repayment). This is a liveness failure of a core protocol function: the AMO can no longer perform monetary operations (peg defense, liquidity provision) until governance intervenes to raise `maxAmoSupply` — which itself may be undesirable since the cap exists to bound AMO issuance, and raising it gives the AMO more real issuance headroom than intended. The condition is permanent without governor action and worsens monotonically: every non-AMO burn of AMO-minted tokens ratchets the tracker further away from reality. Funds controlled by the AMO strategy are effectively frozen in terms of the mint operation.

### Likelihood Explanation

Requires an AMO to be configured (`updateAmo`, `updateMaxAmoSupply` by governor) and AMO-minted tokens to circulate — the designed use case. No special attacker privilege is needed; ordinary repay flows and deliberate attacker burns both shrink real supply while the counter stays high. The likelihood that `amoSupply` eventually saturates the cap depends on configured cap sizes and AMO activity, but the accounting drift is guaranteed on every third-party burn of AMO-minted tokens, so cap exhaustion is a matter of cumulative volume, not edge conditions. Reachability is confirmed by `onlyIfCanMint`/`onlyIfCanBurn` (lines 83–106), which explicitly authorize Pool and DebtToken callers whose burns bypass the `amoSupply` decrement.

### Recommendation

Track the AMO supply as a *net* figure the same way bridge supply is handled, or decrement `amoSupply` proportionally on any burn. Because AMO-minted tokens are fungible once in circulation, exact attribution is impossible; the practical mitigations are:

- Clamp on burn: on any burn, `amoSupply = min(amoSupply, totalSupply)` — or treat `amoSupply` as `max(amoMinted - amoBurned - nonAmoBurnedEstimate, 0)`.
- Simpler and safer: compute AMO headroom as `max(amoMintedTotal - totalBurnedSince, 0)` or store `totalAmoMinted`/`totalAmoBurned` counters and check `totalAmoMinted - totalAmoBurned + amount_ <= maxAmoSupply`, where `totalAmoBurned` is incremented by *any* burn while tokens originated from the AMO cannot be distinguished — alternatively accept the conservative bound and decrement `amoSupply` by `min(amount_, amoSupply)` on every burn regardless of caller.
- Alternatively, provide a governor function to reconcile `amoSupply` downward.

Any of these prevents permanent `SurpassMaxAmoSupply` lockups caused by burns the AMO did not perform.

### Proof of Concept

Hardhat test in the existing suite (mirrors `test/SyntheticToken.test.ts` patterns with the existing `poolMock`):

```ts
it('PoC: AMO mint bricked after pool burns AMO-minted tokens', async function () {
  // setup: AMO with a cap
  await msUSD.connect(governor).updateAmo(amo.address)
  const cap = parseEther('1000')
  await msUSD.connect(governor).updateMaxAmoSupply(cap)

  // AMO mints its full budget into circulation
  await msUSD.connect(amo).mint(user.address, cap)
  expect(await msUSD.amoSupply()).eq(cap)

  // AMO-minted tokens are burned via a Pool/DebtToken path (e.g., user repays debt).
  // msg.sender is poolMock -> _isMsgSenderAmo is false -> amoSupply is NOT decremented.
  await msUSD.connect(poolMock.wallet).burn(user.address, cap)

  // totalSupply correctly decreased, but amoSupply stayed at the cap
  expect(await msUSD.totalSupply()).eq(0)
  expect(await msUSD.amoSupply()).eq(cap) // stale

  // AMO can never mint again despite zero circulating AMO supply
  await expect(msUSD.connect(amo).mint(amo.address, 1))
    .revertedWithCustomError(msUSD, 'SurpassMaxAmoSupply')
})
```

This reproduces the bug class: a per-source mint tracker (`amoSupply`) that does not account for burns performed through other authorized paths causes legitimate mints to revert once the counter saturates the cap — the same failure mode as the Pepper `MINT_LIMIT`/`totalSupply` conflation, expressed on the burn side of the accounting.

Limitations: I verified the mint/burn accounting in `contracts/SyntheticToken.sol` (lines 270–350) and confirmed `onlyIfCanMint`/`onlyIfCanBurn` authorize Pool, DebtToken, ProxyOFT and AMO callers, and that `Pool.sol`, `DebtToken.sol`, `AMO.sol`, and `ProxyOFT.sol` contain burn call sites. I did not have remaining iterations to read the exact `repay`/`liquidate` call chain in `Pool.sol`/`DebtToken.sol` line-by-line, but the authorization surface and the asymmetric counter update in `_burn` are sufficient to establish reachability through the standard repay path.
