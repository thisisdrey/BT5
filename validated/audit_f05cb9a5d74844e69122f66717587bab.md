### Title
Unbounded ZIP Central Directory Extra-Field Parsing Causes Heap Buffer Over-Read - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP/JAR reader parses the "extra fields" of a central directory entry with no bounds checking against the mapped file's actual extent, unlike the equivalent parsing code in singlejar's `ExtraField::find` (`src/tools/singlejar/zip_headers.h`), which explicitly validates that each extra-field record stays within the buffer before dereferencing it.

### Finding Description
`ProcessCentralDirEntry` reads a central directory header's `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes, then iterates the extra-field blob: [1](#0-0) 

```
p += 16;  // skip to 'compressed size' field
...
u2 extra_field_length = get_u2le(p);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```

Unlike the local-file-entry path a few lines earlier, which calls `EnsureRemaining()` before reading `file_name` / `extra_field` bytes [2](#0-1) , `ProcessCentralDirEntry` performs no such check for `file_name_length`, `extra_field_length`, or `file_comment_length` against the actual mapped input length. The comment at the top of the function only asserts "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but nothing enforces that assumption against a crafted, oversized `extra_field_length` or a `data_size` field inside an extra-field record that does not evenly divide the declared `extra_field_length`. If `header_id`/`data_size` are crafted so that `extra_p += data_size` overshoots `p` (the declared end of the extra fields), the loop condition `extra_p != p` never becomes true, and `get_u2le` continues to read 2-byte values past the intended boundary — and, since there is no upper bound tied to `input_file_->Length()`, this walk can run past the end of the memory-mapped file entirely, causing an out-of-bounds/heap-adjacent read.

This is the same bug class as CVE-2023-34488 (an unchecked-bounds parser reading past the end of an attacker-supplied buffer while processing a malformed record), but here the surface is Bazel's own ZIP/JAR archive parser, not a network protocol.

Contrast this with the hardened parser in singlejar, which explicitly bounds-checks each extra-field record before touching it: [3](#0-2) 

That defensive pattern is completely absent from `third_party/ijar/zip.cc`.

### Impact Explanation
`ProcessCentralDirEntry` runs whenever ijar processes a `.jar`/`.zip` file — e.g., when Bazel's Java rules generate interface jars from third-party jars (including jars obtained via `http_jar`/`http_archive` or from module registries). The attacker only needs to control the byte content of a `.jar` artifact fetched from a URL/registry that the victim's build then pipes through ijar. A declared `sha256`/`integrity` checksum does not stop this: the attacker crafts the malicious extra-field layout into the exact bytes that hash to the pinned checksum they published, so checksum verification succeeds while the content itself is malformed. The parser then walks past the intended extra-field region into adjacent mapped memory. Depending on layout, this can (a) crash the build (`SIGSEGV`/`SIGBUS` at a page boundary) or (b) read adjacent process/heap-mapped bytes that get interpreted as further `header_id`/`data_size`/ZIP64 override values (`uncompressed_size`, `compressed_size`, `offset` at line ~531-541), which are then used to locate and copy file content elsewhere in the mapped input — a path by which out-of-bounds bytes could influence what data ijar treats as a "file" and copies into the resulting interface jar.

### Likelihood Explanation
Any `.jar`/`.zip` file that reaches ijar via a repository rule download, module registry archive, or checked-in-but-attacker-influenced dependency triggers this code path unconditionally — `ProcessCentralDirEntry` is called for every central directory record during normal jar processing, with no flag needed to enable or disable this parsing. No privileged access is required beyond publishing the archive content that the build fetches, matching the "hostile origin server whose content passes a pinned checksum" threat model.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry` mirroring `EnsureRemaining()`/`ExtraField::find`'s pattern: validate `file_name_length`, `extra_field_length`, and `file_comment_length` against remaining bytes in the mapped file before advancing `p`, and validate each extra-field record's `data_size` against the extra-field blob's declared end before dereferencing or advancing `extra_p`, aborting with an error (as singlejar does with `diag_errx(1, "malformed extra field...")`) instead of looping unboundedly.

### Proof of Concept
Construct a minimal ZIP/JAR with:
1. A valid `LOCAL_FILE_HEADER_SIGNATURE` entry.
2. A `CENTRAL_FILE_HEADER_SIGNATURE` record whose `extra_field_length` is small (e.g. 4 bytes) but whose embedded extra-field record declares `data_size = 0xFFF0` (far exceeding the declared `extra_field_length`), analogous to the existing `CreateZipWithMalformedExtraField` proof-of-concept used against singlejar's output path [4](#0-3) , but fed into ijar's `InputZipFile` (e.g., via `ijar <crafted>.zip <out>.jar`) instead of singlejar's `OutputJar`. Run under ASan/valgrind to observe the heap-buffer-overflow/over-read report when `extra_p` walks past the mapped extent inside the `while (extra_p != p)` loop in `ProcessCentralDirEntry`; a JUnit-equivalent C++ test analogous to `OutputJarSimpleTest.MalformedExtraField` but targeting `ZipExtractor`/`InputZipFile` would assert either a graceful error (`GetError()` non-null) or, currently, a crash/ASan report confirming the unguarded read.
