### Title
Missing StackerDB contract-id domain separation in chunk signatures enables cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` — the digest that is signed and verified for every StackerDB chunk write — commits only to `slot_id`, `slot_version`, and `data_hash`. It does not commit to the target `QualifiedContractIdentifier` (the StackerDB "namespace"/contract). Because multiple distinct StackerDB contracts (e.g. `signers-0-1` for `BlockResponse`, `signers-0-2` for `StateMachineUpdate`, `signers-0-3` for `BlockPreCommit`) assign the *same* slot ordering/slot_id to the *same* signer address within a reward cycle, a signature that a signer legitimately produced for one contract's slot is equally valid for the identically-numbered slot in every other contract. Any unprivileged network peer that observes a validly-signed chunk can therefore replay it into a different StackerDB contract, and the target node's validation logic (`validate_received_chunk` / `try_replace_chunk`) will accept it as an authentic write from that signer, since neither function binds the signature check to the contract being written.

### Finding Description
`SlotMetadata::auth_digest` in [1](#0-0)  computes the signed hash as `SHA512/256(slot_id || slot_version || data_hash)`. This digest is what gets signed in `sign()` and checked in `verify()`: [2](#0-1) . Nothing in this digest identifies *which* StackerDB smart contract the chunk belongs to.

On the receiving side, `StackerDBs::validate_received_chunk` looks up the expected signer for the given `smart_contract_id` and `slot_id` via `get_slot_signer`, then simply calls `slot_metadata.verify(&addr)`: [3](#0-2) . The `smart_contract_id` parameter is used only to resolve *which address* is expected to own that slot — it is never mixed into the signed payload itself. The same is true for the direct chunk-insertion path in `StackerDBTx::try_replace_chunk`, which calls `slot_desc.verify(&slot_validation.signer)` after fetching the validation record for the given `(smart_contract, slot_id)`: [4](#0-3) .

Slot assignment is derived from the shared `.signers` boot contract state (`stackerdb-signer-slots-0`/`stackerdb-signer-slots-1`), which is read identically by every message-type contract within a signer set via `stackerdb-get-signer-slots-page`: [5](#0-4) . All per-message StackerDB contracts for a given signer set/reward cycle (`BlockResponse=1`, `StateMachineUpdate=2`, `BlockPreCommit=3`) are constructed via `NakamotoSigners::make_signers_db_contract_id(reward_cycle, message_id, mainnet)`: [6](#0-5) , and this is confirmed by tests showing the *same* underlying signer slot list is shared across all `signers-{set}-{message_id}` contracts for a given signer set: [7](#0-6) .

Consequently, a given signer's `slot_id` (e.g. index `I`) is identical across the `BlockResponse`, `StateMachineUpdate`, and `BlockPreCommit` contracts of the same signer set. An attacker (any peer relaying/pushing `StackerDBChunkData` over the p2p protocol via `StackerDBPushChunkData`, whose `contract_id` field is attacker-controlled and is *not* covered by the signature) can take a legitimately observed, validly-signed chunk for slot `I` from contract A (e.g. `BlockResponse`), and re-wrap it with `contract_id` = contract B (e.g. `StateMachineUpdate`) while keeping the same `slot_id`, `slot_version`, `sig`, and `data`. Because `get_slot_signer(B, I)` resolves to the same address as `get_slot_signer(A, I)`, and `auth_digest` never included the contract identifier, `slot_metadata.verify(&addr)` succeeds for contract B as well. The chunk is then accepted, stored, and gossiped throughout the network as if it were an authentic write to StackerDB contract B — exactly the class of failure the ChainPort report calls out ("why does the signed message contain an `action`/context field? Without it, a signature ... could be used on [a different] contract ... [for a different purpose]").

### Impact Explanation
This breaks the intended equality "chunk accepted by StackerDB B is authenticated as a genuine B-message from signer S" — the chunk is really an S-authored message *for a different logical channel* that S never intended to publish there. This is an unauthorized/forged write into StackerDB state that is subsequently propagated network-wide via the normal gossip/replication path (`handle_unsolicited_StackerDBPushChunk` and `StackerDBSync`), matching the "network-wide propagation of forged data" / "unauthenticated write to state or StackerDB" Critical-impact category. Any node/application consuming a given StackerDB contract's slot data (miners, signers, monitoring tooling) that does not itself perform an additional structural check tying the payload to the expected message type could be fed cross-context garbage/forged content attributed to a legitimate signer, undermining the non-repudiation and integrity properties StackerDB chunk signatures are meant to provide.

### Likelihood Explanation
The attack requires no privileged key material: the attacker merely needs to observe one legitimately-signed chunk (which is broadcast in the clear over the StackerDB gossip protocol / is queryable from any replicating node) and re-transmit it wrapped in a `StackerDBPushChunkData` naming a different `contract_id` that shares the same signer-slot assignment. All of the validation logic that would need to reject this (`validate_received_chunk`, `try_replace_chunk`) is exactly the logic shown above, and none of it consults the target contract identity when checking the signature. Given that all signer-set message contracts (`BlockResponse`/`StateMachineUpdate`/`BlockPreCommit`) share slot assignment, this is directly and remotely reachable by any unprivileged network peer that can send P2P `StackerDBPushChunk` messages, or by any peer serving as a chunk-fetch target during sync.

### Recommendation
Include a channel/context-binding value — at minimum the StackerDB `QualifiedContractIdentifier` (or equivalently a fixed `message_id`/`action` discriminator plus network identifier) — in `SlotMetadata::auth_digest`, so the signature commits to `(contract_id, slot_id, slot_version, data_hash)` rather than just `(slot_id, slot_version, data_hash)`. This requires a coordinated wire/version change since it alters the signed payload format for `StackerDBChunkData`/`SlotMetadata`. Document explicitly (per the analog report's recommendation) what properties StackerDB chunk signatures are meant to provide and why each field is included, to prevent this domain-separation gap from being reintroduced.

### Proof of Concept
1. Reward cycle `rc`, signer_set = `rc % 2`. Signer `S` with private key `sk` is assigned slot index `I` in the shared `.signers` slot list (`stackerdb-signer-slots-0`/`-1`), used identically by `signers-{set}-1` (BlockResponse), `signers-{set}-2` (StateMachineUpdate), and `signers-{set}-3` (BlockPreCommit) — confirmed by `signers_db_get_slots` test showing identical slot lists returned by `stackerdb-get-signer-slots` for all message-id contracts of a signer set (`stackslib/src/chainstate/stacks/boot/signers_tests.rs:320-341`).
2. `S` legitimately publishes a `StackerDBChunkData { slot_id: I, slot_version: v, sig, data }` to the BlockResponse contract A (`signers-{set}-1`); `sig` is computed by `SlotMetadata::sign` over `auth_digest = H(I || v || H(data))` (`libstackerdb/src/libstackerdb.rs:159-179`).
3. Attacker observes this chunk (via p2p `StackerDBChunkInv`/`StackerDBGetChunk`/gossip, or event stream) and constructs `StackerDBPushChunkData { contract_id: B (signers-{set}-2), rc_consensus_hash: <matching>, chunk_data: { slot_id: I, slot_version: v', sig, data } }`, choosing `v'` ≥ B's currently stored version for slot `I` (independent version state per contract, per `db.rs`), keeping `sig`/`data` unchanged.
4. Attacker sends this to a node via the unsolicited push path. `PeerNetwork::handle_unsolicited_StackerDBPushChunk` looks up config for contract B, calls `validate_received_chunk(B, config_B, chunk_data, ...)`, which calls `get_slot_signer(B, I)` → returns `S`'s address (same as in A), then `slot_metadata.verify(&S_addr)` succeeds because `auth_digest` never referenced contract A or B (`stackslib/src/net/stackerdb/mod.rs:679-697`).
5. The chunk is accepted, stored in B's StackerDB replica, and gossiped further, even though `S` never signed anything intended for contract B (StateMachineUpdate) — the signed digest looks identical between contracts A and B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
