### Title
Single held-open connection with a false `Content-Length` blocks the entire `SignerEventReceiver` main loop indefinitely - (File: libsigner/src/events.rs)

### Summary
`process_event` reads the request body with a plain blocking call, `request.as_reader().read_to_string(&mut body)`, with no read timeout configured anywhere in `SignerEventReceiver::bind`. Because `next_event`/`process_event` run synchronously on the single receiver thread that also drives `main_loop`, a remote peer that opens a TCP connection, sends a `POST /stackerdb_chunks` request with an inflated `Content-Length`, sends fewer bytes than declared, and then goes silent (no further data, no close) causes this blocking read to never return, which halts the *entire* event receiver — not just the one connection's "slot" — for every subsequent event (stackerdb chunks, block-validation responses, burn blocks). No panic occurs on this path.

### Finding Description
`process_event` (`libsigner/src/events.rs:519-542`) does:
```rust
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) {
    ...
}
```
`tiny_http`'s `Request::as_reader()` gives a `Read` that will keep pulling bytes from the underlying `TcpStream` until it has consumed `Content-Length` bytes (or hits EOF/error). If a client declares `Content-Length: 100`, sends 1 byte, and then sends nothing further while keeping the socket open, the inner `TcpStream::read` call blocks — there is no `set_read_timeout` call anywhere in `SignerEventReceiver::bind` (`libsigner/src/events.rs:404-408`) or elsewhere in this file to bound that wait.

Critically, `SignerEventReceiver` has no concurrency: `EventReceiver::main_loop` (`libsigner/src/events.rs:284-312`) calls `next_event()` synchronously, which calls `http_server.recv()` followed directly by `process_event(request)` on the same thread (`libsigner/src/events.rs:413-459`). While that thread is blocked inside `read_to_string`, it cannot call `http_server.recv()` again, so any other already-queued/parsed request from other connections is not serviced, and the `is_stopped()` check at the top of `main_loop` is never reached either. Effectively, a single crafted connection can suspend the entire receiver thread (and therefore prevent delivery of all further stackerdb chunks, `/proposal_response`, `/new_burn_block`, and `/new_block` events to the signer) for as long as the attacker chooses to hold the connection open with no keepalive/timeout enforcement.

No panic path exists in `process_event`'s error branch: `read_to_string`'s `Err` case is handled cleanly (logs, calls `ack_dispatcher`, returns `EventError::MalformedRequest`), and `out_channels` state is untouched by this code path since it's never reached while blocked.

### Impact Explanation
This does not crash or panic the process, and it does not forge or write any data — the guard the question asks about (panic-freedom) holds. However, it is not merely "consumes a slot" because this receiver has no per-connection concurrency: one attacker-controlled TCP connection, requiring no volumetric traffic, is sufficient to stall reception of *all* subsequent node→signer events indefinitely (bounded only by the attacker voluntarily closing the socket, or by OS-level TCP behavior, which by default does not time out an idle-but-open connection). This is a low-cost, repeatable denial of the signer's event intake pipeline, closer to "bounded compute DoS on a read endpoint" than to connection-slot exhaustion, since it requires exactly one connection, not volume.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only network reachability to the signer's event-receiver port (bound via `SignerEventReceiver::bind`) and the ability to open a raw TCP connection and send arbitrary HTTP bytes — no secret, peer key, or admin role is required. The attack is trivially repeatable and costs the attacker one socket held open.

### Recommendation
Set an explicit read timeout on accepted connections/`tiny_http` requests (or on the underlying stream) so that a body read that stalls beyond a bound errors out rather than blocking forever. Additionally, consider processing each accepted connection's request/body read on its own worker thread (or bounding body length with a hard byte cap enforced incrementally, not via `read_to_string`) so one slow/malicious client cannot stall processing of concurrently pending requests from other peers.

```rust
                }
```

```rust
    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(
                    "[{:?}] next_event got request with unexpected url {}, return OK so other side doesn't keep sending this",
                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?
    }
```

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
```
