## Finding: Heap out-of-bounds read in ijar's ZIP central-directory / Zip64 extra-field parser

### Title
Missing length validation in `InputZipFile::ProcessCentralDirEntry` causes heap over-read on crafted ZIP central-directory/extra-field length fields - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar` (invoked by Bazel's Java rules via `run_ijar`/`stamp_jar` on every dependency jar, including jars fetched from external repositories such as `http_jar`/`http_archive`/Maven) parses ZIP central-directory records with attacker-controlled 16-bit length fields and copies/derefs data using those lengths without validating them against the actual remaining bytes of the memory-mapped input file. This mirrors the CVE-2016-6254 bug class: a length field taken directly from untrusted, packet/record-like input is trusted to bound a subsequent read/copy, producing a heap (mmap) buffer over-read.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight from the central directory header and then advances the cursor `p` and copies bytes without any bounds check against the mapped file size: [1](#0-0) 

Unlike the local-file-header path (`ProcessLocalFileEntry`/`SkipFile`), which calls `EnsureRemaining()` before every read, [2](#0-1) , the central-directory path has **no equivalent bounds check at all**. `memcpy(filename, p, len)` at line 520 can read past the end of the mmap'd file if `file_name_length` is crafted to be near the buffer edge.

Worse, the Zip64 extra-field loop compounds the problem: [3](#0-2) 

`get_u2le`/`get_u4le`/`get_u8le` all advance the pointer as a side effect [4](#0-3) . The loop reads a 4-byte sub-header (`header_id`, `data_size`) then advances `extra_p` by the attacker-supplied `data_size` with no check that `data_size >= 8` before `get_u8le(extra)` is called, and no check that `extra_p` stays `<= p` (the declared end of the extra-field region). A crafted `data_size` smaller than 8 makes `get_u8le` read past the sub-field into adjacent memory; a `data_size` that overshoots `p` can make the `while (extra_p != p)` loop skip past its terminating condition and keep iterating over attacker-influenced memory far beyond the intended extra-field bounds.

Contrast this with `singlejar`'s independent ZIP header implementation, which explicitly validates extra-field bounds before touching memory: [5](#0-4) 

That check (`ExtraField::find`) is what's missing from `third_party/ijar/zip.cc`'s hand-rolled Zip64 parsing loop.

### Impact Explanation
`ijar` operates on the raw bytes of jars that are checksum-pinned at fetch time (e.g. via `http_jar`, or transitively through `rules_jvm_external`/Maven coordinates with a `sha256`). A hostile package/jar author can publish a jar whose bytes match the declared, pinned hash exactly, yet contains a corrupted central-directory record or Zip64 extra field with an inconsistent length. Because the checksum only proves byte-for-byte integrity of the *declared* content — not structural well-formedness of the ZIP — this crafted content passes verification and is subsequently handed to `ijar` during ordinary Java compilation (`run_ijar`). The resulting heap/mmap over-read can crash the Bazel build action (denial of service) and, depending on memory layout, leak adjacent heap bytes into subsequently-copied filename/attribute fields that end up embedded in the interface jar output.

### Likelihood Explanation
`ijar` runs automatically and unconditionally as part of standard Java build actions on every dependency jar (`run_ijar`), so any project depending on an external, attacker-controlled jar (a common scenario with Maven/`http_jar` dependencies) will invoke this code path with no additional configuration needed. No special Bazel flags disable this default behavior. The needed length-field manipulation is simple to construct with any ZIP tool.

### Recommendation
Add explicit bounds checks (analogous to `EnsureRemaining`, used in `ProcessLocalFileEntry`) before every central-directory field read and copy in `ProcessCentralDirEntry`, and validate `data_size >= 8` (and that `extra_p + data_size <= p`) before calling `get_u8le` in the Zip64 extra-field loop, mirroring the containment checks already present in `src/tools/singlejar/zip_headers.h`'s `ExtraField::find`.

### Proof of Concept
A JUnit/shell reproduction would construct a minimal ZIP whose central directory declares:
1. `file_name_length` larger than the bytes actually remaining between the current cursor and the end of the mapped file, so `memcpy(filename, p, len)` reads past the mapping, and
2. A Zip64 extra field with `header_id == 0x0001` and `data_size < 8` (e.g. `data_size = 0`) placed at the very end of the extra-field/central-directory region, so `get_u8le(extra)` reads 8 bytes starting right at (or past) the mapped file boundary.

Running `ijar <crafted.zip> out.jar` (as exercised by `third_party/ijar/test/ijar_test.sh`) against such a file should be extended with a case that feeds this crafted archive and asserts the process does not crash/over-read, using ASan/Valgrind to detect the heap-buffer-overflow, matching the pattern already used by existing `ijar` tests such as [6](#0-5) .
