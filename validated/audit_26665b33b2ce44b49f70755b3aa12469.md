### Title
Aliased (non-deep-copied) `AccountCapsule` shared between parent/child `Repository` caches lets reverted TVM calls leak balance mutations - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
CVE-2023-0494 is a use-after-free/dangling-pointer bug caused by `DeepCopyPointerClasses` performing a shallow copy where a deep copy was required, so an object that should have been independent (and later freed/replaced) is instead aliased, letting one code path corrupt state that another path still relies on. `RepositoryImpl`, java-tron's nested cache-of-caches used for every TVM call and native-contract execution, has an analogous "should-have-been-a-copy" aliasing flaw: on a first (cache-miss) read, `getAccount()` caches and returns the *exact same* `AccountCapsule` object instance that the parent repository (or an ancestor further up the chain) also holds, instead of returning/caching a defensive copy. `addBalance()` then mutates that shared instance **in place** via `accountCapsule.setBalance(...)` before deciding whether the surrounding call succeeds or reverts.

### Finding Description
`RepositoryImpl` implements a parent/child "shadow" cache stack: every TVM `CALL`/native-contract execution creates a child `Repository` via `newRepositoryChild()`, mutates state in the child's own `HashMap` caches, and only propagates changes to the parent by explicitly invoking `commit()`. If the child never commits (e.g. the call reverts or throws `ContractValidateException`/`ContractExeException`), the design intends for the parent's state to remain untouched.

The isolation guarantee depends on every cache layer holding **independent copies** of capsules. This holds for cache *hits*: [1](#0-0) 
returns `new AccountCapsule(accountCache.get(key).getValue())` — a fresh wrapper.

But on a cache **miss**, the object obtained from the parent (or the `AccountStore`) is cached and returned **without copying**: [2](#0-1) 

Because the parent's own `getAccount()` follows the exact same miss-path logic, a fresh `AccountCapsule` instance can be shared, by direct object reference, across an entire chain of parent → child → grandchild `Repository` layers that all miss their local cache on the same address in the same call tree (which is exactly the common case for a fresh account touched for the first time in a transaction/internal call).

`addBalance()` then mutates that shared instance directly, rather than working on an independent copy: [3](#0-2) 
`accountCapsule.setBalance(addExact(balance, value, ...))` mutates the object in place; the following `accountCache.put(...)` merely re-tags the *type* of the already-shared reference — it does not isolate the mutation. Since the parent's `accountCache` (and any ancestor's) map entry still points at this same object, the parent instantly observes the balance change even though the child `Repository` has not called `commit()`.

Contrast this with `updateAccount()`, `updateContract()`, etc., which only ever install *new* references coming from actuator/native-contract code — those are safe. The problem is specifically the aliasing introduced by the "get-then-mutate-in-place" pattern in `addBalance()` (and any other method following the same pattern) combined with the non-defensive miss-path caching in `getAccount()`.

This is architecturally the same class of defect as CVE-2023-0494: a structure that is supposed to be deep-copied for isolation between two logical scopes (X server's per-device pointer class list vs. java-tron's per-call `Repository` cache layer) is instead shallow-copied/aliased, so a write performed in one scope silently corrupts state visible to a different scope that should have been isolated from it.

### Impact Explanation
TVM execution and every native-contract invoked through `Program.java` (`CALL`, value-transfer opcodes, `cancelAllUnfreezeV2Action`, `withdrawExpireUnfreezeProcessor`, etc.) creates a child `Repository`, calls a processor's `execute()` (which internally calls `addBalance`/`getAccount`), and only calls `repository.commit()` on success — on `ContractValidateException`/`ContractExeException` the child repository is simply discarded. Because of the aliasing bug, a balance mutation performed inside the discarded child can have already been applied in-place to the shared `AccountCapsule` object that the parent (and potentially the root) repository's cache references, independent of whether `commit()` is ever called. This can result in balances being permanently changed in the persisted account store even though the contract call that produced them was intended to be rolled back — i.e., unbacked/incorrect balance changes, an "unauthorized account operation" affecting fund accounting integrity for any contract call or internal transaction reachable by an unprivileged transaction broadcaster or contract deployer.

### Likelihood Explanation
The vulnerable code path (`getAccount()` cache-miss + `addBalance()`) is exercised on essentially every value transfer and native staking/unfreeze operation performed through the TVM repository layer, and nested child repositories are created for every internal call and several native-contract paths in `Program.java`. Any unprivileged party who can deploy or call a contract that performs a value transfer to a fresh/first-touched account inside a call that is later reverted (e.g. via a failing nested call, `require`/`revert`, or an actuator validation failure inside a native contract wrapper) can reach this path without any special privilege.

### Recommendation
Ensure isolation is maintained by always returning/caching defensive copies of mutable capsules on every cache-miss path in `RepositoryImpl` (mirroring the cache-hit behavior that already does `new AccountCapsule(...)`), and/or have `addBalance()` (and any similar in-place mutator) operate on a copy of the capsule obtained from `getAccount()` before storing it back into the local `accountCache`, so that no `Repository` layer's cache can ever hold a reference shared with another layer.

### Proof of Concept
1. Deploy a contract `A` whose fallback/function performs an internal `CALL` with value to a fresh address `X` that has never been touched before in the transaction, then immediately triggers a revert condition inside the same call (e.g., calls a second contract that reverts, or fails a native-contract validation such as `cancelAllUnfreezeV2Action`/`withdrawExpireUnfreezeProcessor` after the value transfer step).
2. Trace `RepositoryImpl.getAccount(X)`: because `X` is untouched, the miss-path in the root/parent repository caches and returns the *same* `AccountCapsule` instance that the child repository created for the internal call.
3. `addBalance(X, value)` inside the child repository mutates that shared instance's balance field in place before the internal call's failure is detected.
4. The internal call reverts, and the child `Repository.commit()` is never invoked (per the pattern in `Program.java`'s `cancelAllUnfreezeV2Action`-style handlers) — yet because the parent's cache entry pointed at the same mutated `AccountCapsule` object, the balance change persists in the parent when the parent later commits its own (unrelated) state, at the end of the top-level transaction.
5. Result: `X`'s balance is inflated by `value` despite the operation that credited it having logically been rolled back — an unbacked balance change reachable from an ordinary signed transaction/contract call.

  public long addBalance(byte[] address, long value) {
    AccountCapsule accountCapsule = getAccount(address);
    if (accountCapsule == null) {
      accountCapsule = createAccount(address, Protocol.AccountType.Normal);
    }

    long balance = accountCapsule.getBalance();
    if (value == 0) {
      return balance;
    }

    if (value < 0 && balance < -value) {
      throw new RuntimeException(
          StringUtil.createReadableString(accountCapsule.createDbKey())
              + " insufficient balance");
    }
    accountCapsule.setBalance(addExact(balance, value, VMConfig.disableJavaLangMath()));
    Key key = Key.create(address);
    accountCache.put(key, Value.create(accountCapsule,
         accountCache.get(key).getType().addType(Type.DIRTY)));
    return accountCapsule.getBalance();
  }
