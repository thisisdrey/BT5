### Title
Exchange transaction pause can be bypassed via `ALLOW_HARDEN_EXCHANGE_CALCULATION` flag - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`ExchangeTransactionContract` transactions are supposed to be permanently rejected once the network passes fork `VERSION_4_8_0_1` (the exchange feature having been deprecated). This rejection is gated behind a helper, `isExchangeTransaction`, whose result silently flips to `false` — and thus lifts the rejection entirely — whenever the `ALLOW_HARDEN_EXCHANGE_CALCULATION` chain parameter is enabled, with no re-check of the fork/deprecation state.

### Finding Description
`Manager.pushTransaction` calls `isExchangeTransaction(trx.getInstance())` to decide whether to reject a transaction from an unprivileged broadcaster with `"ExchangeTransactionContract is rejected"`: [1](#0-0) 

`isExchangeTransaction` itself is defined as: [2](#0-1) 

Note the very first check: `if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) { return false; }`. This means that as soon as the `ALLOW_HARDEN_EXCHANGE_CALCULATION` committee parameter is turned on (a value/purpose that is documented only as enabling a hardened/fixed *calculation* for exchange math — see `ProposalUtil.java` / `reference.conf` comments), `isExchangeTransaction` unconditionally returns `false` for *every* `ExchangeTransactionContract`, regardless of the fork-version gate that is supposed to determine whether exchange is deprecated/rejected.

There is a second, separate enforcement path, `rejectExchangeTransaction`, which correctly re-checks both `isExchangeTransaction` and the fork version: [3](#0-2) 

However, this method is not invoked anywhere in production code paths (`processTransaction`, block application, etc.) — the only reference found is a reflective unit test that invokes it directly via `Method.setAccessible(true)`: [4](#0-3) 

So the sole real-world gate against exchange transactions is the `isExchangeTransaction` check in `pushTransaction`, and that check is nullified by the same flag that is documented as merely fixing calculation precision. This is directly analogous to the reported bug class: a "pause"-style protection (`pauseRedemptions` blocking `authRedeem`/`autoRedeem`) that is supposed to universally stop an action but has an inconsistent/partial implementation, letting the guarded action execute anyway through a code path the pause doesn't actually cover.

### Impact Explanation
Once `ALLOW_HARDEN_EXCHANGE_CALCULATION` is set to `1` (a governance-controlled but ordinary, non-malicious value change — its stated purpose is fixing exchange math, not re-enabling the deprecated Exchange feature), any unprivileged transaction broadcaster can again submit `ExchangeTransactionContract` transactions that were meant to be permanently blocked. This resurrects the deprecated/legacy TRC10 Exchange trading feature for all users network-wide, defeating the intended protocol-level deprecation and reopening the surface for any exchange-related accounting issues (e.g., stale token balances, calculation edge cases in `ExchangeCapsule.transaction`) that the deprecation was meant to close off. It is an availability/authorization defect of a security control on a broadcastable contract type — matching a "Medium" severity control-bypass class.

### Likelihood Explanation
The condition requires only a single on-chain parameter (`ALLOW_HARDEN_EXCHANGE_CALCULATION`) to be set to `1` via the standard committee proposal mechanism — a routine, expected chain-parameter change, not an attack. After that (entirely normal) governance action, exploitation requires nothing more than any account broadcasting a normal `ExchangeTransactionContract` transaction, which is trivially reachable through `Wallet`/`pushTransaction`. The bug is latent and will trigger automatically the moment the parameter changes, with no attacker privilege needed to trigger the resulting bypass.

### Recommendation
Remove the `allowHardenExchangeCalculation()` short-circuit from `isExchangeTransaction`, or make the exchange-rejection check independent of that flag; the fork-based deprecation check (as implemented in `rejectExchangeTransaction`) should be the single source of truth and should also be wired into `pushTransaction`/`processTransaction` so both entry points are consistently enforced.

### Proof of Concept
1. Committee passes a proposal setting `ALLOW_HARDEN_EXCHANGE_CALCULATION = 1` (a normal calculation-fix proposal, unrelated in intent to exchange availability).
2. Any account (unprivileged) constructs and broadcasts an `ExchangeTransactionContract` transaction via the wallet/gRPC API.
3. `Manager.pushTransaction` calls `isExchangeTransaction(trx.getInstance())`; because `allowHardenExchangeCalculation()` is now `1`, the method returns `false` immediately, skipping the `"ExchangeTransactionContract is rejected"` `ContractValidateException`.
4. The transaction proceeds to `processTransaction` → `ExchangeTransactionActuator.execute`, successfully executing an exchange trade that the protocol intended to have permanently disabled after `VERSION_4_8_0_1`.

  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
  }
