### Title
Unvalidated `NakamotoInv` bitvec length lets a peer's truncated inventory be conflated with "peer confirmed absent" - ([File: stackslib/src/net/inv/nakamoto.rs])

### Summary
`NakamotoTenureInv::merge_tenure_inv` stores a peer-supplied bitvec for a reward cycle without checking that its length matches `self.reward_cycle_len`, and `has_ith_tenure` collapses "index not represented in the bitvec" and "peer explicitly reported absent" into the same `false` return value via `rc_tenures.get(rc_height).unwrap_or(false)`. A malicious peer answering `GetNakamotoInv` can therefore send a short bitvec and have the node treat un-reported sortitions late in the cycle as confirmed-absent tenures.

### Finding Description
`getnakamotoinv_try_finish` takes whatever `BitVec<2100>` the remote peer returns in a `NakamotoInv` reply and passes it straight to `merge_tenure_inv`, which only compares it against a cached value for equality and inserts it unconditionally: [1](#0-0) [2](#0-1) 

There is no check anywhere in this path that `inv_data.tenures.len()` equals `reward_cycle_len` for the reward cycle being answered. Later, `has_ith_tenure` computes `rc_height` from the node's own `self.reward_cycle_len` and looks it up in the stored (possibly truncated) bitvec: [3](#0-2) 

`rc_tenures.get(rc_height).unwrap_or(false)` returns `false` both when the peer's bitvec explicitly recorded "no tenure" for that index and when the bitvec is simply too short to have an entry there at all. These two situations are semantically different ("peer told us no" vs. "peer never told us"), but the API gives the caller no way to distinguish them.

### Impact Explanation
The broken equality means a single crafted `NakamotoInv` reply (fewer bits than `reward_cycle_len`) causes the node's per-peer inventory tracking to silently report "this peer does not have tenure X" for tenures the peer never actually attested to. This is false inventory data injected by an unprivileged peer via a normal, protocol-valid response to a request the node itself initiated. Downstream inventory-availability logic that consumes `has_ith_tenure` (used when computing per-tenure peer availability for the download scheduler) can be steered into believing a canonical tenure is unavailable from that peer, which — if that peer is the last remaining candidate for a given tenure — degrades the node's ability to schedule a download for that tenure until the peer's inventory state is next reset and re-synced. This matches the "steering a node off the tip via false inventory" category (High), since it is forged/false per-index inventory data being accepted and stored without validation.

### Likelihood Explanation
- Attacker cost is minimal: run a normal Stacks P2P peer, respond to the node's own `GetNakamotoInv` request with a truncated bitvec.
- No authentication beyond ordinary peer handshake is required; this is exactly the kind of message an unprivileged peer is expected to send.
- Repeatable every inventory-sync round for any reward cycle the node queries this peer about.
- Actual node-visible impact is bounded by the periodic reset/retry cycle (`try_reset_comms`/`reset_comms`), which will eventually re-query the peer and can correct the record if the peer replies correctly (or is later marked offline/dropped for other reasons) — so the effect is a stall/degradation in tenure availability discovery from this peer rather than a permanent, unrecoverable state corruption.

### Recommendation
In `merge_tenure_inv` (or immediately before calling it in `getnakamotoinv_try_finish`), validate that `tenure_inv.len()` matches the expected length for the reward cycle being reported (accounting for the legitimate truncation allowed only for the current, in-progress reward cycle as noted in `make_tenure_bitvector`'s doc comment). Reject/NACK-equivalent (treat as a hostile reply, e.g. mark the peer as not learned / offline) replies whose bitvec is shorter than expected for a completed reward cycle. Additionally, change `has_ith_tenure` to distinguish "index absent from bitvec" (return `None`/treat as unknown, not usable as negative evidence) from an explicit `false` bit, and update callers (e.g. tenure-availability computation in `stackslib/src/net/download/nakamoto/tenure_downloader_set.rs`) to not treat "unknown" the same as "peer confirmed absent."

### Proof of Concept
1. Construct a `NakamotoTenureInv` with a known `reward_cycle_len` (e.g. 5) via `NakamotoTenureInv::new(...)`.
2. Build a `StacksMessage` with `StacksMessageType::NakamotoInv(NakamotoInvData { tenures: BitVec::try_from(vec![true,true,true]).unwrap(), .. })` (3 bits for a 5-tenure cycle).
3. Call `inv.getnakamotoinv_try_finish(&mut network, msg)` for the reward cycle in question.
4. Call `inv.has_ith_tenure(burn_block_height)` for a `burn_block_height` mapping to `rc_height` 3 or 4 (out of range of the stored bitvec).
5. Assert the call returns `false` (via `unwrap_or(false)`), confirming there is no way to detect that this index was never covered by the peer's reply, and that this "false" is indistinguishable from an explicit negative bit — demonstrating the conflation feeding any consumer (e.g. tenure-availability logic) with forged/false inventory data.

    pub fn has_ith_tenure(&self, burn_block_height: u64) -> bool {
        if burn_block_height < self.first_block_height {
            return false;
        }

        let Some(reward_cycle) = PoxConstants::static_block_height_to_reward_cycle(
            burn_block_height,
            self.first_block_height,
            self.reward_cycle_len,
        ) else {
            return false;
        };

        let Some(rc_tenures) = self.tenures_inv.get(&reward_cycle) else {
            return false;
        };

        let sortition_height = burn_block_height - self.first_block_height;
        let rc_height = u16::try_from(sortition_height % self.reward_cycle_len)
            .expect("FATAL: reward cycle length exceeds u16::MAX");
        rc_tenures.get(rc_height).unwrap_or(false)
    }

    pub fn merge_tenure_inv(&mut self, tenure_inv: BitVec<2100>, reward_cycle: u64) -> bool {
        // populate the tenures bitmap to we can fit this tenures inv
        let learned = self
            .tenures_inv
            .get(&reward_cycle)
            .map(|cur_inv| cur_inv != &tenure_inv)
            .unwrap_or(true);

        self.tenures_inv.insert(reward_cycle, tenure_inv);
        self.last_updated_at = get_epoch_time_secs();
        learned
    }
