### Title
Unauthenticated RecvError packets allow spoofed remote-state reset / tunnel teardown - (File: outside.go)

### Summary
The external report describes an owner-callable function that resets shared profit-share state without meaningful access control, harming trustlessness of the contract. The closest reachable analog in nebula is `handleRecvError` in [1](#0-0)  which processes `header.RecvError` packets — a message type that is handled entirely *before* any decryption/AEAD authentication step in `readOutsidePackets`, at [2](#0-1) .

### Finding Description
`RecvError` is dispatched in the "Unencrypted packets" switch, alongside `Handshake`, before the code ever reaches `hostinfo.ConnectionState.Decrypt` [2](#0-1) . This means an attacker who holds no CA-signed certificate and has never completed a handshake can still cause `handleRecvError` to execute, purely by sending a raw UDP packet with the right header type.

Inside `handleRecvError`, the only checks performed are:
1. A local rate/accept policy `f.acceptRecvErrorConfig.ShouldRecvError(addr)` [3](#0-2) .
2. A lookup of the hostinfo via `f.hostMap.QueryReverseIndex(h.RemoteIndex)` [4](#0-3) .
3. A comparison of the packet's source UDP address against the hostinfo's already-known remote address: `hr := hostinfo.GetRemote(); if hr.IsValid() && hr != addr { ... return }` [5](#0-4) .

If the spoofed source address matches the legitimate remote's address (classic UDP source-address spoofing, since UDP performs no return-routability check), this last check passes trivially. There is no cryptographic authentication of the `RecvError` packet at all — no AEAD tag, no nonce, no session key involvement.

Once these checks pass, the function unconditionally tears down the tunnel state:
```go
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```
`closeTunnel` calls `f.hostMap.DeleteHostInfo(hostInfo)` and, if this was the last hostinfo for the peer, also clears cached lighthouse state via `f.lightHouse.DeleteVpnAddrs` [6](#0-5) . This is the direct analog of "PrepareForProfitShare": a state-resetting operation reachable without proof of legitimate authorization (a valid cert / established session), which unilaterally wipes another party's established state (tunnel, hostmap entries, remote/lighthouse cache).

The only non-trivial requirement for an attacker is knowing (or brute-forcing) the 32-bit `RemoteIndex` value, which is observable on the wire (it appears in plaintext in every packet header of an active tunnel) and does not require holding a valid certificate.

### Impact Explanation
A successful spoofed `RecvError` causes remote state poisoning / forced tunnel teardown: the victim deletes its `HostInfo` and any associated pending handshake state for the peer, forcing a full re-handshake. Repeated injection from an off-path attacker who can spoof the legitimate peer's source IP (or an on-path/adjacent-network attacker) can be used as a persistent denial-of-service primitive against established tunnels, without ever needing a CA-signed certificate.

### Likelihood Explanation
Exploitability depends on (a) knowledge of a live `RemoteIndex` (observable from captured traffic) and (b) the ability to spoof the legitimate peer's UDP source address, which is possible on networks that do not enforce BCP38/source-address validation, or for on-path attackers. This is a lower-effort path than compromising a certificate, since `RecvError` requires no cryptographic material. Rate limiting exists via `ShouldRecvError`/`acceptRecvErrorConfig`, which reduces but does not eliminate exploitability — the underlying authentication gap is structural.

### Recommendation
Do not act on `RecvError` packets to tear down active tunnel/handshake state based solely on a source-address match. Consider requiring some proof tied to session material before honoring a `RecvError` (e.g., only accept it when it can be correlated with a legitimate outbound packet that provoked it, or bind acceptance to a short window immediately following a locally-sent packet and index that has not yet been acknowledged), and tighten or make configurable the default `accept_recv_error` policy so operators are aware of this trust assumption.

### Proof of Concept
1. Establish a legitimate tunnel between `A` and `B`; observe on the wire (or otherwise learn) the `RemoteIndex` value used in `B`'s packets to `A` and `A`'s remote UDP address as known to `B`.
2. From attacker-controlled infrastructure, craft a UDP packet with `header.RecvError` type and `RemoteIndex` set to `A`'s known local index, spoofing the source address to `A`'s real UDP endpoint, and send it to `B`.
3. `B.handleRecvError` passes the `hr == addr` check (since the source is spoofed to match) and calls `closeTunnel`/`DeleteHostInfo`, tearing down `B`'s tunnel state to `A` without any valid certificate or session key from the attacker [1](#0-0) .

**Note on confidence:** I could not fully verify the exact rate-limiting/mitigation logic in `ShouldRecvError`/`acceptRecvErrorConfig` (defined in `interface.go`) within the available index; a background Devin session with full repository access should confirm whether default configuration effectively mitigates spoofed-source exploitation before treating this as a high-severity finding.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
