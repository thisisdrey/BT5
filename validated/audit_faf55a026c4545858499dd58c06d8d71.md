## Title
Systematic Rounding-Down Always Favors the Taker in Market Order Matching, Draining Resting Maker Orders - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder` computes cross-rate exchange amounts using `MarketUtils.multiplyAndDivide`, which performs integer division with `floorDiv` (i.e., always rounds toward zero/down for positive operands) and never corrects the rounding direction. In two of the three match branches, the resting maker's entire remaining sell quantity is consumed exactly, while the amount credited back to the maker is computed via this floor-rounding formula — the same root cause the linked external report describes for a DEX order-matching contract.

### Finding Description
`multiplyAndDivide` always floors the result: [1](#0-0) 

In `matchSingleOrder`, the taker's buyable quantity is first floor-divided from the maker's price: [2](#0-1) 

In the "taker == maker" branch, the taker receives the maker's *entire* remaining sell quantity exactly, but the amount the maker is credited (`makerBuyTokenQuantityReceive`) is a second, independent floor division that is not guaranteed to be the exact inverse of the first: [3](#0-2) 

The same pattern (exact full transfer to taker, floor-rounded credit to maker) recurs in the "taker > maker" branch: [4](#0-3) 

The code even acknowledges rounding can occur, but only special-cases the extreme `makerBuyTokenQuantityReceive == 0` outcome; any nonzero-but-short amount is silently accepted: [5](#0-4) 

Because a maker's full sell-side inventory is debited exactly while the corresponding buy-side credit is floor-rounded, the maker can receive strictly less than the fair proportional amount for the tokens it gave up, and the surplus effectively accrues to the taker (via `takerSellTokenLeft`/`takerOrderCapsule` retaining unspent sell tokens it should have paid). This mirrors the reported bug class: unmitigated division rounding in partial-fill matching that "gives funds to the maker without receiving anything [proportional] in return, or [takes] from the maker without giving anything back" — here manifesting as chronic underpayment of the maker rather than a full zero-payment case, since `MAX_ACTIVE_ORDER_NUM`/price constraints don't bound the ratio precision.

### Impact Explanation
This is reachable by any unprivileged account broadcasting a `MarketSellAssetContract` (a permissionless "order placer" action). Because rounding always floors (never rounds up in the maker's favor), an attacker can act as taker against resting maker orders and systematically extract fractional value on every match, at the maker's expense. Repeated at scale (bots matching against many orders/prices) this becomes a real, sustained value drain from maker funds — theft of funds via unauthorized underpayment. It does not require any privileged role, MEV/witness position, or off-chain state; it is exploitable purely through normal `MarketSellAssetContract` transactions.

### Likelihood Explanation
High likelihood of exploitation for any active market with resting orders: the rounding direction is deterministic and always biased the same way (floor), so an attacker only needs to select maker orders where the price ratio does not divide evenly (common, since sell/buy quantities are integers) and take against them repeatedly. No race condition or special timing is needed — the actuator logic runs deterministically for every matched trade.

### Recommendation
Adopt the same fix pattern as the cited report: round token amounts owed *to* the maker up (ceiling) rather than down, so the taker never underpays. Concretely, in `matchSingleOrder`, when computing `makerBuyTokenQuantityReceive` via `MarketUtils.multiplyAndDivide`, use a ceiling-division variant (`quotient + (remainder != 0 ? 1 : 0)`) instead of `floorDiv`, ensuring the maker is always credited at least the fair proportional amount, with any residual dust rounding cost borne by the taker instead of the maker.

### Proof of Concept
1. Maker posts a sell order via `MarketSellAssetContract` with `sellTokenQuantity`/`buyTokenQuantity` chosen so the exchange ratio does not divide evenly (e.g., sell 10 A for 3 TRX).
2. Attacker (taker) posts a matching buy-side `MarketSellAssetContract` sized to fully consume the maker's remaining quantity (triggering the "taker == maker" or "taker > maker" branch in `matchSingleOrder`).
3. `takerBuyTokenQuantityReceive` is set to the maker's full `getSellTokenQuantityRemain()` (exact), while `makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(...)` which floors the division — the maker receives less TRX than the exact proportional amount for the 10 A given up, while the taker's own leftover sell balance (`takerSellTokenLeft`) is correspondingly inflated, capturing the rounding surplus.
4. Repeating this against many orders/price pairs accumulates a steady value transfer from makers to the taker.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
