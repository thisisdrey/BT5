### Title
Positions with debt below `debtFloorInUsd` can never be liquidated when `maxLiquidable < 100%`, permanently freezing collateral and crystallizing bad debt - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.liquidate()` enforces two bounds on `amountToRepay_` simultaneously: it cannot exceed `maxLiquidable` fraction of the position's debt, and the remaining debt must be either zero or at least `debtFloorInUsd`. When a position's total debt in USD is below `debtFloorInUsd` and `maxLiquidable < 1e18`, no value of `amountToRepay_` can satisfy both constraints — every liquidation call reverts. Unlike `DebtToken.repay`, which is paired with `repayAll` as an escape hatch, `liquidate` has no "repay everything" bypass for the floor.

### Finding Description
In `Pool.liquidate`, any repayment above the `maxLiquidable` share of the debt reverts with `AmountGreaterThanMaxLiquidable`. [1](#0-0) 
Immediately after, any repayment that leaves a non-zero remainder below `debtFloorInUsd` reverts with `RemainingDebtIsLowerThanTheFloor`. [2](#0-1) 

Let `D` be the position's debt in the synthetic token and `F` the floor in the same units (`debtFloorInUsd / synth price`). A valid liquidation amount `x` must satisfy:

- `x ≤ D * maxLiquidable` (partial-close cap)
- `D - x == 0` or `usd(D - x) ≥ debtFloorInUsd` (floor check)

If `usd(D) < debtFloorInUsd` and `maxLiquidable < 1e18`:
- `x = D` (full repay → remainder 0, passes floor check) violates `x ≤ D * maxLiquidable`.
- `x < D` leaves `0 < usd(D - x) < debtFloorInUsd` → floor check reverts.

The position is therefore unliquidatable forever. The same floor logic in `DebtToken.repay` is safe because `repayAll` fully zeroes the debt and bypasses the floor [3](#0-2)  — `Pool.liquidate` has no equivalent path, and self-liquidation is explicitly forbidden (`CanNotLiquidateOwnPosition`) so the account owner cannot resolve it via `liquidate` either. [4](#0-3) 

A position reaches `usd(D) < debtFloorInUsd` through unprivileged paths:

1. If `DebtToken.issue`/`flashIssue` does not enforce a minimum debt ≥ floor (the floor check exists only in `repay`/`repayAll` and `liquidate` — I could not confirm an issue-side floor check within the tool budget; this precondition should be verified against `DebtToken.issue`), an attacker simply issues debt below the floor.
2. Even with an issue-time floor, `debtInUsd` is computed as `amount * synth price` via `masterOracle().quoteTokenToUsd` [5](#0-4) , so a drop in the synthetic's oracle price (or a collateral price crash making the position unhealthy) shrinks `usd(D)` below the floor without any privileged action.

The collateral backing such a position is also permanently locked: `DepositToken.withdraw`/`transfer` revert via `_revertIfLocked` when `unlockedBalanceOf` is zero, which it is for any unhealthy position with debt. [6](#0-5) 

### Impact Explanation
Every unhealthy position whose debt falls below `debtFloorInUsd` becomes permanently unliquidatable. The protocol cannot clear the bad debt (invariant: liquidation bounds / solvency is broken), and the position's collateral is frozen in the `DepositToken` — permanently locked user/protocol funds, a direct analog of the CVE's availability (hang/crash) impact. The attacker can mass-produce such dust positions cheaply to strand collateral and accumulate unresolvable bad debt.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18` on the deployed pool — both are ordinary governance-set parameters (`updateDebtFloor`, `updateMaxLiquidable`) and tests exercise `maxLiquidable = 50%` and `debtFloor = $3,000` as realistic configurations. [7](#0-6)  Creating or reaching a sub-floor unhealthy position needs only public entry points (`deposit` + `issue`, or normal market price movement). No privileged role, oracle malfunction, or external dependency failure is required.

### Recommendation
In `Pool.liquidate`, treat the floor check the same way `repayAll` does — allow the constraint to be satisfied when the repayment is capped by `maxLiquidable` or when it is the maximum the position allows. Concretely: skip `RemainingDebtIsLowerThanTheFloor` when `amountToRepay_` equals `min(D, maxLiquidable-allowed amount)` and the residual debt would be below the floor, or when `D` itself is already below `debtFloorInUsd` (permit full liquidation of sub-floor positions regardless of `maxLiquidable`). Alternatively, enforce `debt ≥ debtFloorInUsd` at `DebtToken.issue`/`flashIssue` time so sub-floor positions can never be created — note this does not save positions that drift below the floor via synth price movement, so the liquidation-side fix is still needed.

### Proof of Concept
Hardhat sketch (mirroring `test/Pool.test.ts` setup):

```ts
// given: pool with debtFloor > 0 and maxLiquidable < 100%
await pool.updateDebtFloor(parseEther('3000'))        // $3,000
await pool.updateMaxLiquidable(parseEther('0.5'))     // 50%

// attacker opens a position with debt worth < $3,000
await met.connect(attacker).approve(msdMET.address, MaxUint256)
await msdMET.connect(attacker).deposit(collateralAmount, attacker.address)
await msEthDebtToken.connect(attacker).issue(smallDebt, attacker.address) // e.g. $1,000 of msEth

// collateral price drops -> position unhealthy, debt still < floor
await masterOracle.updatePrice(met.address, toUSD('0.10'))
expect((await pool.debtPositionOf(attacker.address))._isHealthy).false

// liquidation is impossible:
// 1) partial repay leaves dust < floor
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, smallDebt.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// 2) full repay (rem = 0) violates maxLiquidable
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, smallDebt, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

// attacker's collateral is permanently locked
await expect(
  msdMET.connect(attacker).withdraw(1, attacker.address)
).revertedWithCustomError(msdMET, 'NotEnoughFreeBalance')
```

Caveat: the precondition `maxLiquidable < 1e18` on the target deployment and the absence of a floor check in `DebtToken.issue` should be confirmed on the live config before running the fork PoC; if `issue` enforces the floor, the drift-below-floor path (step via oracle price movement) still applies.
