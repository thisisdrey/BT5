### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2018-15834 bug class is "an untrusted count/length field read from crafted input data is used to allocate/copy memory without validating it against the input's actual bounds." The same root-cause pattern exists in java-tron's `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` helpers used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts: a 32-byte "array length" word taken directly from calldata is used to size a Java array (`new byte[len][]`) before any sanity check is applied in the non-`allowTvmSelfdestructRestriction` code path.

### Finding Description
`extractBytesArray` and `extractSigArray` read a length from the calldata-derived `DataWord[]` and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 
`extractBytes32Array` does the same with no offset-bounds check at all: [3](#0-2) 

In `ValidateMultiSign.execute`, the size guard against `MAX_SIZE` is only applied when the `allowTvmSelfdestructRestriction` hard-fork flag is active; otherwise the code falls straight through to `extractBytesArray` with the raw, unchecked length: [4](#0-3) 
`BatchValidateSign.doExecute` has the identical pattern, and additionally calls `extractBytes32Array` (line 1176-1177) which never receives a `MAX_SIZE`-style guard on its own length word at all, even under the restriction flag: [5](#0-4) 

An attacker only needs to craft a small calldata blob (a handful of 32-byte words) where the header word that `extractBytesArray`/`extractSigArray`/`extractBytes32Array` reads as "array length" is set to a very large value (e.g. `0x7fffffff`). Because the length is read from `DataWord.intValueSafe()` with no upper bound check before the allocation, `new byte[len][]` (or `new byte[len][32]`) attempts to allocate an object-reference array containing hundreds of millions to billions of entries, which throws `OutOfMemoryError` or otherwise exhausts heap.

### Impact Explanation
An unprivileged caller can trigger this from any smart contract that invokes the `ValidateMultiSign` or `BatchValidateSign` precompiled contract addresses via a single signed transaction (a `TriggerSmartContract`). Triggering large/repeated allocations can exhaust JVM heap and crash or destabilize the node process executing/validating the transaction, which — if it happens broadly across SR/witness nodes during block validation — is a Medium-severity node crash/DoS analogous to the crafted-length heap overflow root cause in the CVE.

### Likelihood Explanation
The attack requires no special privileges — any address can broadcast a transaction that calls a contract invoking these precompiles with attacker-chosen calldata. The vulnerable path is reached whenever `allowTvmSelfdestructRestriction()` is not active (e.g., historical block replay/sync, or any network/testnet/private chain that has not activated that hard fork), and unconditionally for the `extractBytes32Array` length in `BatchValidateSign`, since no `MAX_SIZE` guard exists for that call at all.

### Recommendation
Validate the extracted length against a small fixed bound (e.g. `MAX_SIZE`) and against the remaining `words.length` immediately after reading it in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, before performing any allocation — independent of the `allowTvmSelfdestructRestriction` feature flag, so both `ValidateMultiSign` and `BatchValidateSign` are protected in all activation states.

### Proof of Concept
1. Deploy/trigger a contract call that invokes the `BatchValidateSign` precompile address (0x0000...1006 style TVM precompile) with calldata shaped as:
   - word0: `hash` (32 bytes, arbitrary)
   - word1: offset pointing to word4 (e.g. `0x80`)
   - word2: offset pointing to word5 (e.g. `0xa0`)
   - word4: `0x7fffffff` (huge "signatures array length")
   - word5: `0x7fffffff` (huge "addresses array length")
2. On a node/network where `allowTvmSelfdestructRestriction()` is not yet active, `doExecute` skips the `MAX_SIZE` check and calls `extractBytesArray`/`extractBytes32Array` with `len = 0x7fffffff`, attempting `new byte[0x7fffffff][]`, which throws `OutOfMemoryError` and can crash/destabilize the executing node.
