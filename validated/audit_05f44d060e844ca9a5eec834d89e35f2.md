Audit Report

## Title
`fallback_max_weight: None` in Snowbridge V2 inbound `Transact` calls leaves `Transact` weight metering undefined on version downgrade — (File: `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`)

## Summary
`make_create_asset_xcm_for_polkadot` in `bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs` constructs two `Transact` instructions with `fallback_max_weight: None`, for the asset-creation call and the reserve-setting call, unlike the structurally identical `v1.rs::convert_register_token` path which was patched (per `pr_6792`) to set an explicit `Some(Weight::from_parts(400_000_000, 8_000))`. [1](#0-0) [2](#0-1)  Because the XCM v5→v4 downgrade path derives `require_weight_at_most` from `fallback_max_weight.unwrap_or(Weight::MAX)` when the call cannot be locally decoded, this `None` value becomes `Weight::MAX` if the message is ever transported/negotiated to a chain still running XCM v4. [3](#0-2) 

## Finding Description
The XCM v5 `Transact` documentation explicitly flags this risk: `fallback_max_weight` is "used for compatibility with previous versions ... If you don't care about compatibility you can just put `None`. WARNING: If you do, your XCM might not work with older versions." [4](#0-3)  The XCM crate's own regression test documents the concrete failure mode: omitting the fallback on a v5 `Transact` and downgrading it to v4 yields `require_weight_at_most: Weight::MAX`. [5](#0-4)  The v5→v4 `TryFrom` implementation confirms this mechanically: if the call bytes cannot be decoded by the local converter (true here, since `call` is opaque `Encode`d bytes for a remote pallet call index unknown to the generic XCM crate), the weight falls back to `fallback_max_weight.unwrap_or(Weight::MAX)`. [3](#0-2) 

The team already identified and fixed exactly this gap once, in the V1 inbound-queue converter, setting an explicit `Some(Weight::from_parts(400_000_000, 8_000))` fallback for its asset-creation `Transact`. [2](#0-1)  The V2 converter's analogous two `Transact` instructions in `make_create_asset_xcm_for_polkadot`, however, still hard-code `fallback_max_weight: None` for both the `create_call_index` and `set_reserves_call_index` calls. [1](#0-0)  This `Xcm<()>` is built from the `Payload::CreateAsset` variant of an inbound Ethereum message, decoded from `EventProof` data attacker-controlled from Ethereum, inside `MessageToXcm::prepare`/`convert`. [6](#0-5) 

I was unable to fully trace, within the available iterations, the exact downstream transport code (`bridges/snowbridge/primitives/inbound-queue/src/v2/processor.rs` and the pallet's XCM router configuration) that sends this `Xcm<()>` onward to AssetHub, so I cannot conclusively confirm from code alone whether/when XCM version negotiation would force a v5→v4 downgrade of this specific message in the current runtime wiring. That said, the codebase's own documented rationale for `pr_6792`/`pr_6643` — patching the structurally identical `v1.rs` path specifically to cover "the small time window when chains are upgrading" — establishes that this downgrade path is a real, previously-encountered production scenario for Snowbridge inbound XCM, and the V2 converter reproduces the exact same code pattern that was fixed there.

## Impact Explanation
If the generated XCM is downgraded to v4 (staged runtime-upgrade window, or any decode failure of the opaque `call` bytes on the local converter), `require_weight_at_most` becomes `Weight::MAX` instead of a bounded value, per the v5→v4 conversion logic. [3](#0-2)  This falls under the "public underpriced work that degrades block production or stalls bridge processing" impact class, since a receiving chain's weight-limit/barrier checks operating on an unbounded `Weight::MAX` claim can either reject the message (stalling the inbound `CreateAsset` flow) or process it with mis-bound weight accounting for the nested `Transact` dispatch.

## Likelihood Explanation
The trigger — BridgeHub/AssetHub running different XCM versions during a staged runtime-upgrade rollout — is a normal, expected operational condition, not a contrived edge case, as evidenced by the team's own prior fix (`pr_6792`) for the same class of gap in `v1.rs`. The `make_create_asset_xcm_for_polkadot` path is exercised on every inbound Ethereum `CreateAsset` message, which is triggered by attacker-controlled Ethereum senders without any privileged action required.

## Recommendation
Set an explicit, non-`None` `fallback_max_weight` on both `Transact` instructions in `make_create_asset_xcm_for_polkadot` (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`, lines 302-304 and 315-317), mirroring the pattern already used in `v1.rs::convert_register_token`, and add a regression test asserting `fallback_max_weight.is_some()` for all V2-inbound-generated `Transact` instructions.

## Proof of Concept
1. Submit an inbound Ethereum message with `Payload::CreateAsset { token, network: Polkadot }` through `MessageToXcm::convert`. [6](#0-5) 
2. Observe the generated XCM contains two `Transact { fallback_max_weight: None, .. }` instructions. [1](#0-0) 
3. Convert the resulting `Xcm<()>` from v5 to v4 via `TryInto` (as in `polkadot/xcm/src/v5/mod.rs`'s `transact_roundtrip_works` test) while the call bytes remain undecodable to the local converter; observe `require_weight_at_most` becomes `Weight::MAX`. [3](#0-2)
