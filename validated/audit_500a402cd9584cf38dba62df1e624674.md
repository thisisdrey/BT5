### Title
Dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, permanently blocking the victim from adding new collateral types or issuing new debt tokens (DoS / forced liquidation) — (`contracts/Pool.sol` + `contracts/DepositToken.sol`)

### Summary
`Pool` tracks, per account, a bounded enumerable set of deposit/debt tokens (`MappedEnumerableSet`, capped at `MAX_TOKENS_PER_USER`). A `DepositToken._transfer` to an address with a zero balance in that token unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)`, and `Pool` reverts with `UserReachedMaxTokens` once the combined deposit+debt token count reaches the cap [1](#0-0) . An unprivileged attacker can deposit dust of every registered collateral and transfer 1 wei of each `msdToken` to a victim, filling the victim's slots without consent. After that, any `deposit()`/`_mint` of a *new* deposit token and any `issue()`/`_mint` of a *new* debt token for that account reverts, because the mint path calls `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` [2](#0-1) . This mirrors the advisory's bug class: an attacker-triggered state change DoS-ing a victim's ability to use the protocol.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's per-account list whenever the recipient's prior balance was `0` and `amount_ > 0` — there is no opt-in or consent check [3](#0-2) .
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` [4](#0-3) .
- `DebtToken` mints (via `issue`/`flashIssue`) call `addToDebtTokensOfAccount` under the same cap, so once filled, the victim cannot open a debt position in a synthetic token they haven't used before.
- Attack path (all public, unprivileged):
  1. For each registered `DepositToken` i: attacker deposits a dust amount (`DepositToken.deposit(1, attacker)` — allowed since only paused blocks deposits, not shutdown of victim [5](#0-4) ).
  2. Attacker calls `depositToken_i.transfer(victim, 1)`. `_revertIfLocked` only checks the sender's position, which is healthy [6](#0-5) .
  3. Repeat until the victim's combined token count hits `MAX_TOKENS_PER_USER`.
- The victim can free a slot only by burning/transferring out a dust balance (`_balanceAfter == 0` triggers `removeFromDepositTokensOfAccount` [7](#0-6) ), but the attacker can front-run each cleanup with a fresh dust transfer of another token, making the DoS persistent at low cost.

### Impact Explanation
- The victim is blocked from depositing any *new* collateral type and from issuing any *new* synthetic debt. If the victim's position deteriorates toward liquidation and the needed collateral type isn't already in their set, they cannot top up collateral and are force-liquidated — a direct, attacker-controllable loss of funds via `Pool.liquidate`.
- Even when no liquidation occurs, the victim's ability to use the protocol (deposit, borrow, lever up via `SmartFarmingManager`) is DoS-ed for as long as the attacker keeps the slots filled; clearing costs the victim gas and transactions while the attacker refills cheaply.
- Invariant broken: liveness — a user should always be able to add collateral to protect their position.

### Likelihood Explanation
- Cost scales with the number of registered deposit tokens and dust amounts (1 wei each); no privileged role, oracle manipulation, or flash-loan requirement — plain EOA transfers suffice, and `Operator.execute` can batch them atomically [8](#0-7) .
- No existing mitigation: `pause`/`shutdown` are governor-controlled; `nonReentrant` doesn't apply cross-call; `_revertIfLocked` checks only the sender. The `SynthContext` sender resolution does not affect the attack.
- Severity is bounded by the victim's ability to expel dust tokens (transfer out or `withdraw`), so this is temporary freezing/griefing rather than permanent locking — but combined with liquidation timing it enables forced liquidations.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` addition opt-in or exempt unsolicited transfers (e.g., only add on `deposit`/`_mint` where the recipient is the payer, or gate list additions behind a per-account whitelist).
- Alternatively, allow eviction: let an account remove a token from its own list when its balance is below a dust threshold, or raise/segment the cap so gratuitous fills are impractical.
- A minimal fix: in `_transfer`, do not call `pool.addToDepositTokensOfAccount(recipient_)` on plain transfers, or add a `toggleDepositTokenTracking` flag the account controls.

### Proof of Concept
Hardhat sketch (follows existing `test/Pool.test.ts` "should revert when reach max tokens" setup at `test/Pool.test.ts:1386-1416`):

```ts
// victim: alice has an open position in msdMET + msUSD debt
// attacker: mallory

const depositTokens = await pool.getDepositTokens(); // all registered
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await token.underlying());
  // attacker funds dust (or uses existing balance)
  await underlying.connect(mallory).approve(token.address, 1);
  await token.connect(mallory).deposit(1, mallory.address);
  // may need top-up so transfer of 1 wei passes _revertIfLocked
  await token.connect(mallory).transfer(alice.address, 1); // adds slot
}
// combine with existing debt tokens until MAX_TOKENS_PER_USER reached

// victim tries to deposit a new collateral type to avoid liquidation:
await expect(
  newDepositToken.connect(alice).deposit(parseEther('10'), alice.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim tries to issue a new synthetic debt token:
await expect(
  newDebtToken.connect(alice).issue(parseEther('1'), alice.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// attacker re-fills any slot alice frees via front-run transfer(..., 1)
```

Uncertain: the exact value of `MAX_TOKENS_PER_USER` and the number of registered deposit tokens on each deployment (grep returned the constant in `contracts/Pool.sol` but not its literal value); the attack's cost grows if the cap exceeds the number of registered tokens, in which case the attack requires the victim's set to already be near the cap or relies on debt-token entries too.
