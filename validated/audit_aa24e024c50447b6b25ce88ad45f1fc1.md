### Title
Unprivileged attacker can exhaust the global QUIC connection-slot pool via pre-handshake connection churn, evading per-IP rate limiting and starving legitimate TPU ingress - (File: streamer/src/nonblocking/quic.rs)

### Summary
The QUIC accept loop in `run_server` grants a connection slot (`ClientConnectionTracker`) against a single global counter bounded by `qos.max_concurrent_connections()` *before* the QUIC handshake completes, while per-IP registration via `ConnectionRateLimiter::register_connection` only happens *after* a successful handshake in `setup_connection`. An unstaked attacker can therefore repeatedly open connections and abandon them before the handshake finishes, holding slots for up to the 2-second handshake timeout without ever being charged against the per-IP limiter, letting it monopolize the shared connection-slot pool and starve all other (including staked) TPU QUIC ingress.

### Finding Description
In `run_server`, per-IP admission is checked with `rate_limiter.is_allowed(&incoming.remote_address().ip())`, which is a read-only check that returns `true` whenever the IP has no recorded tokens yet [1](#0-0) . The counter is only actually consumed later, inside `setup_connection`, via `rate_limiter.register_connection(&from.ip())`, and this call is reached only once the QUIC handshake has *successfully completed* (`Ok(new_connection)` branch) [2](#0-1) .

Meanwhile, `ClientConnectionTracker::new` is created and increments the shared `stats.open_connections` counter immediately after the per-IP check passes and *before* the handshake even begins, gated only by the single global `qos.max_concurrent_connections()` value shared by every client on the node (staked and unstaked) [3](#0-2) [4](#0-3) . That value is computed globally, not per-IP: [5](#0-4) 

The slot is only released when `ClientConnectionTracker` is dropped, which happens either on successful `try_add_connection`/later removal, or after `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) elapses in `setup_connection`'s `timeout(...)` wrapper [6](#0-5) [7](#0-6) .

Because a single attacker source IP is never checked against a *per-IP* concurrent-connection cap until after a successful handshake (the per-peer cap enforced in `SwQos::try_add_connection`/`prune_unstaked_connections_and_add_new_connection` only runs post-handshake), that IP can keep opening new QUIC connections, never respond to/finish the handshake, and hold up to `max_concurrent_connections()` global slots simultaneously. Once slots free up after the 2-second timeout, the attacker immediately reopens new connections to refill them. Any other client — staked or unstaked — attempting to connect while the pool is saturated is rejected via `incoming.refuse()` with `refused_connections_too_many_open_connections` [4](#0-3) , i.e., legitimate TPU traffic cannot even establish a QUIC connection.

The per-IP rate limiter and the global `overall_connection_rate_limiter` do not prevent this because both are only "charged" post-handshake (`register_connection` and `overall_connection_rate_limiter.consume_tokens(1)` are both inside the `Ok(new_connection)` branch of `setup_connection`) [8](#0-7) , so an attacker who never completes the handshake is invisible to both limiters while still consuming a global connection-table slot.

### Impact Explanation
This is a QoS-evasion/DoS finding: an unstaked, unprivileged attacker can starve the shared connection-slot pool (`max_concurrent_connections`, e.g. `(max_staked_connections + max_unstaked_connections) * 5/4`) using only pre-handshake connection churn from a small number of source IPs, preventing legitimate staked and unstaked validators/clients from establishing new TPU QUIC connections for as long as the churn is sustained. This directly degrades TPU ingress and can meaningfully impair a leader's ability to receive transactions, matching the "unbounded QUIC-endpoint accept-loop resource consumption / QoS evasion starving legitimate TPU ingress" bounty category referenced in the prompt.

### Likelihood Explanation
The attack requires no stake, no special keys, and no cooperation from other validators — only the ability to open QUIC connections to a leader's public TPU port and abandon them before handshake completion, well within reach of a single unprivileged network client with modest concurrency (bounded only by `max_concurrent_connections`, a few thousand by default). It is fully repeatable/sustainable as long as the attacker keeps refilling slots faster than the 2-second timeout releases them, so likelihood is high.

### Recommendation
Enforce a per-IP cap on *in-flight, pre-handshake* connection attempts (not just post-handshake per-peer limits), e.g., track outstanding `ClientConnectionTracker`/`setup_connection` tasks per source IP with a small bound, or require completion of the QUIC Retry/address-validation challenge before allocating a slot from the shared `max_concurrent_connections` pool, so a single IP cannot consume a disproportionate share of the global connection-slot budget.

### Proof of Concept
Integration test plan (extending `streamer/src/nonblocking/quic.rs` test module or `tpu-client-next/tests/connection_workers_scheduler_test.rs`):
1. Configure `SwQosConfig` with small `max_staked_connections`/`max_unstaked_connections` (e.g., 4 total, so `max_concurrent_connections()` = 5) and spin up `setup_quic_server`.
2. From a single attacker `IpAddr`, spawn N (> `max_concurrent_connections()`) parallel `Connecting` futures via a raw `quinn::Endpoint::connect` but immediately `drop` each `Connecting` before it resolves (or don't complete client-side handshake steps), before the 2s `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
3. Concurrently, attempt a legitimate client connection (`make_client_endpoint`) from a different IP.
4. Assert that the legitimate connection is refused/times out while the attacker's churn is ongoing, and that `StreamerStats::refused_connections_too_many_open_connections` increments for the legitimate client, while `StreamerStats::connection_rate_limited_per_ipaddr` for the attacker's IP stays at 0 (proving the per-IP limiter never engaged despite the attacker occupying all slots).

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}
