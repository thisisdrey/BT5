### Title
Bancor-style exchange swap math uses non-deterministic `double`/`Math.pow` floating-point arithmetic instead of exact integer/BigDecimal math, allowing rounding-based value extraction from TRC10 Exchange pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeCapsule.transaction()` computes the output amount of a Bancor-relay-style TRC10 exchange swap by delegating to one of two `Processor` implementations selected by the dynamic property `allowHardenExchangeCalculation()`. Unless that proposal has been activated, the default path is `ExchangeProcessor`, whose `exchangeToSupply`/`exchangeFromSupply` methods perform the Bancor formula entirely with native `double` arithmetic and `Math.pow`, exactly analogous to the reported bug class of "quietly wrong numeric assumptions in a value-determining calculation reachable by an ordinary user." The `SafeExchangeProcessor` (BigDecimal, deterministic rounding) exists precisely because the double-based path is known to be numerically unsound, but it is only used when the hardening flag is enabled.

### Finding Description
`ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and `ExchangeTransactionActuator` are all reachable by any account that signs a corresponding transaction type; `ExchangeTransactionActuator.execute()`/`doValidate()` call `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`. [1](#0-0) 

`ExchangeCapsule.transaction()` chooses the processor based solely on the `hardenedCalc` flag: [2](#0-1) 

When not hardened, `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` use `double` and `Maths.pow`, then truncate to `long` via a raw cast: [3](#0-2) 

Floating-point `pow`/division on `double` is not guaranteed to be bit-identical across JVMs/JIT optimizations and platforms (unlike the fixed-scale `BigDecimal` computation used by `SafeExchangeProcessor`), and repeated truncation (`(long) issuedSupply`, `(long) exchangeBalance`) compounds rounding error into the exchange's `firstTokenBalance`/`secondTokenBalance` state that is persisted directly to the store: [4](#0-3) 

This is the exact bug class from the report: a value-determining computation (asset "price"/exchange rate) relies on an assumption (naive floating point is adequate/consistent) that does not hold in all cases, and the code path that would correct it (`SafeExchangeProcessor`) is gated behind an opt-in flag rather than being the default.

### Impact Explanation
Because `ExchangeProcessor` mutates and persists `firstTokenBalance`/`secondTokenBalance` (the actual TRX/TRC10 reserves backing the exchange) using values derived from `double` math, an attacker who can determine or influence rounding behavior (by choosing quant sizes, executing many small trades, or exploiting divergence between the floating-point result and the true Bancor formula) can extract more of a reserve token than they contributed, or cause the pool's tracked balances to drift from what should be economically consistent — i.e., unbacked balance changes drawn from other liquidity providers' funds in the exchange. Because JVM double/`Math.pow` results can also differ subtly across environments/optimizations for the same inputs, this additionally creates a theoretical determinism risk for consensus if different nodes compute different truncated results (chain-split risk), which is the reason `SafeExchangeProcessor`/`StrictMathWrapper` exist as a hardening mechanism in the first place.

### Likelihood Explanation
Any account with sufficient TRX/TRC10 balance can freely submit `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` transactions against any existing TRC10 exchange pair without special privilege, and the non-hardened `ExchangeProcessor` remains the default calculation path until `ALLOW_HARDEN_EXCHANGE_CALCULATION` is activated via governance proposal. This makes the vulnerable path directly and repeatedly reachable by an ordinary transaction broadcaster at will, over many small trades to accumulate favorable rounding.

### Recommendation
Make the `BigDecimal`-based `SafeExchangeProcessor` calculation the mandatory, non-optional implementation for all exchange balance updates (remove the `double`-based `ExchangeProcessor` code path entirely rather than gating it behind a governance proposal), and add explicit conservation-of-value invariant checks (e.g., constant-product/constant-supply floor checks) after every swap to reject any transaction whose calculated output would violate the pool's algebraic invariant.

### Proof of Concept
1. Create a TRC10 exchange pair with `firstTokenBalance`/`secondTokenBalance` such that Bancor-formula intermediate ratios (`quant/newBalance`, `supplyQuant/SUPPLY`) fall on values where `double`/`Math.pow` truncation systematically rounds in the trader's favor (verifiable by comparing `ExchangeProcessor.exchange()` output against `SafeExchangeProcessor.exchange()` output for the same inputs, as done in `ExchangeProcessorTest`/`ExchangeCapsuleTest`).
2. With `allowHardenExchangeCalculation()` left at its default (disabled), repeatedly submit small `ExchangeTransactionContract` trades via `ExchangeTransactionActuator` in both directions (sell A for B, then B for A) sized to exploit the identified rounding bias.
3. Observe that the account's cumulative received `anotherTokenQuant` (persisted to `AccountCapsule` via `addAssetAmountV2`/`setBalance`) exceeds what a `BigDecimal`-exact Bancor computation would yield, while `exchangeCapsule.setBalance(...)` persists the drifted reserve balances, demonstrating extraction of value not backed by the trader's actual deposits.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
