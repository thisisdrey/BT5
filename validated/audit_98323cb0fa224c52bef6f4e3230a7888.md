**Reasoning**: `postReceivePack` in `internal/gitaly/service/smarthttp/receive_pack.go` does not perform any ref matching itself — it validates the request minimally (`validateReceivePackRequest`) and then pipes the raw pktline stream directly to `git-receive-pack` as stdin via `streamio.NewReader`/`gitcmd.WithStdin`, leaving all negotiation and ref matching to the `git` binary itself. [1](#0-0) 

The only Gitaly-side ref-pattern matching related to negotiation is `pipelineRefPrefixRegex` in `internal/git/stats/packfile_negotiation.go`, used purely for logging/metrics instrumentation of `ls-refs` ref-prefixes, not in `postReceivePack`'s code path at all. [2](#0-1) [3](#0-2) 

That regex is anchored (`^...$`), bounded to 1–19 digits, and — critically — Go's standard `regexp` package is implemented using the RE2 algorithm, which guarantees linear-time matching with no catastrophic backtracking regardless of pattern or input, unlike backtracking engines (PCRE, etc.) where ReDoS is possible. There is no user-controlled, unbounded-complexity regex construction anywhere in this path.

Since (1) `postReceivePack` itself contains no ref-matching logic to exploit, and (2) the only related regex use is a simple, bounded pattern evaluated by Go's inherently linear-time RE2 engine, the premise of "catastrophic CPU in ref matching" does not apply to this codebase.
