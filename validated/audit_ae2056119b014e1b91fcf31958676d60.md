Audit Report

## Title
HOP `hop_submit`/`hop_claim`/`hop_ack` signing payload lacks a chain domain separator, enabling cross-chain signature replay - (File: `substrate/client/hop/src/types.rs`)

## Summary
`signing_payload` and `submit_signing_payload` in `substrate/client/hop/src/types.rs` build the digest a user signs from only a static operation-context prefix and the content hash (plus, for submit, a wall-clock timestamp), never including any chain-identifying value such as genesis hash or spec version. Because `sr25519`/`ed25519`/`ecdsa` `MultiSigner`/`MultiSignature` accounts are chain-agnostic, this makes a signature produced for `hop_submit`/`hop_claim`/`hop_ack` on one HOP-enabled chain byte-identical to what is required on any other HOP-enabled chain, and thus replayable verbatim.

## Finding Description
`signing_payload(context, hash)` computes `blake2_256(context || hash)` <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/types.rs" start="307-315" /> and `submit_signing_payload` computes `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())` <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/types.rs" start="317-329" />. The context constants `HOP_SUBMIT_CONTEXT`, `HOP_CLAIM_CONTEXT`, `HOP_ACK_CONTEXT` are fixed byte strings shared by every deployment of the crate <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/types.rs" start="298-305" />. The RPC handler for `hop_submit` verifies the signature against exactly this construction before inserting into the pool <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/rpc.rs" start="207-214" />, and `find_recipient_idx` uses the same unbound construction for claim/ack <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/pool.rs" start="561-580" />. The `HopRuntimeApi::create_promotion_extrinsic` doc confirms the runtime pallet is expected to re-verify this exact signature on-chain, bounding replay only via a timestamp tolerance window — not any chain-specific value <cite repo="Kohvert/polkadot-sdk--013" path="substrate/primitives/hop/src/lib.rs" start="47-63" />. No genesis hash, spec version, or other chain/instance identifier is folded into any of these payloads at any point in the client crate.

## Impact Explanation
This breaks the invariant that a HOP submit/claim/ack authorization is scoped to a single chain instance. A signature (and its associated `(data, signer, submit_timestamp)` tuple) legitimately produced or publicly observed on one HOP-enabled chain is accepted verbatim by any other HOP-enabled chain where the signer's account is also authorized, because the client-side verification in `rpc.rs` and `pool.rs` and the pallet-level re-verification described by `HopRuntimeApi` never differentiate chains. This is a mis-bound proof/signature acceptance defect: a proof of consent intended for chain A is accepted as valid consent on chain B, letting an attacker cause duplicate promotion of content and consumption of a different chain's per-account `can_account_promote` quota/authorization without any privileged access. This matches the "forged or mis-bound proof or state acceptance" impact class.

## Likelihood Explanation
No malicious node, validator, or leaked keys are required — an attacker only needs to observe a `(data, signer, signature, submit_timestamp)` tuple from a public `hop_submit` RPC call (or the resulting on-chain promotion extrinsic) on one HOP-enabled chain and resubmit it to a second HOP-enabled chain within its timestamp tolerance window. This is deterministic and reproducible whenever two HOP deployments share account space, which is the normal operating condition for sibling parachains or staging/production environments running the same client.

## Recommendation
Fold a chain-specific domain separator (at minimum genesis hash, ideally also spec version) into `signing_payload` and `submit_signing_payload` before hashing, and have the runtime pallet re-derive the identical value during `create_promotion_extrinsic` verification, analogous to `chainId`/`verifyingContract` binding in EIP-712-style domain separation.

## Proof of Concept
1. Account `Alice` on chain A calls `hop_submit(data, recipients, signature_A, signer, ts)` where `signature_A` signs `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || ts.to_le_bytes())` per `submit_signing_payload` <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/types.rs" start="323-329" />.
2. An observer captures `(data, signer, signature_A, ts)` via the public RPC call or the resulting promotion extrinsic.
3. Within the tolerance window, the observer submits the identical tuple to chain B's `hop_submit`, which recomputes the same unbound payload and calls `multi_sig.verify(&submit_payload[..], &account_id)` <cite repo="Kohvert/polkadot-sdk--013" path="substrate/client/hop/src/rpc.rs" start="210-214" />, succeeding and inserting into chain B's pool for eventual promotion despite `Alice` never authorizing this on chain B.
