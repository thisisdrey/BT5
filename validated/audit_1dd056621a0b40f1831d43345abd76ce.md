### Title
Group-level rate limiter can be bypassed via order structuring, allowing net outflow far in excess of the configured cap - ([File: programs/marginfi/src/utils/general.rs])

### Summary
The group-level rate limiter is designed to cap aggregate USD outflow (withdraws/borrows) across an entire `MarginfiGroup`, mirroring the intent of GMX's "virtual price impact" — a protection meant to hold even when individual actions are spread across multiple pools/accounts. Like the GMX bug, the marginfi implementation only compares each individual instruction's flow against a *stale, previously-synced* aggregate counter rather than truly enforcing the limit against all flows that have actually occurred, so a user (or several colluding accounts) can split a large withdrawal/borrow into many smaller calls that are each below the "remaining capacity" snapshot and defeat the aggregate cap entirely before the counter is ever updated.

### Finding Description
`record_withdrawal_outflow` in [1](#0-0)  enforces the group-level limit by reading `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)` and comparing the current instruction's USD value against it — but it never mutates `group.rate_limiter` in the user-facing instruction path itself: [2](#0-1) 

The group account is intentionally left non-writable during user actions; only a `RateLimitFlowEvent` is emitted, and the counter is updated later, out-of-band, by `update_group_rate_limiter` (`delegate_flow_admin`), which the design guide confirms explicitly: [3](#0-2) [4](#0-3) 

This is proven directly by the project's own test, which asserts the group state is **unchanged** after user withdraws/repays and only advances once the admin manually calls the update instruction: [5](#0-4) 

Because every check re-reads the same unmutated `effective_remaining_capacity` baseline, a user can issue N separate withdraw/borrow instructions (across N marginfi accounts, or even within a single transaction across different banks) — each individually under the remaining-capacity threshold — and each one independently passes the read-only check, since none of them decrement the counter that the next check consults. The cumulative outflow can thus vastly exceed the configured hourly/daily group cap, and by the time the off-chain `delegate_flow_admin` aggregates events (documented as happening only "at intervals," e.g. every ~10 minutes) and calls `update_group_rate_limiter`, the funds have already left the protocol. This exactly parallels the GMX finding: the threshold check inspects only the current/marginal flow instead of true cumulative state, so chopping a large flow into smaller ones defeats the aggregate manipulation-resistance mechanism.

### Impact Explanation
The group rate limiter exists specifically as a defense-in-depth control to cap the blast radius of outflows from a group (e.g., in case of a compromised/rogue risk-admin, oracle manipulation, or other exploit chain that would otherwise be checked by the bank-level or group-level caps). Bypassing it via structuring defeats this protection with no on-chain cost beyond transaction fees, allowing outflows unbounded by the configured group limit until the next asynchronous admin settlement, undermining the intended risk-mitigation guarantee of the group rate limiter.

### Likelihood Explanation
Likelihood is high whenever group rate limits are configured and enabled: any unprivileged user with multiple accounts (or simply multiple sequential withdraw/borrow calls before the next admin batch) can trivially structure transactions to stay under the "remaining capacity" snapshot on each call. No special privileges, races, or unusual preconditions are required — only that the attacker act faster than (or during) the interval between admin aggregation calls.

### Recommendation
The group-level check should not rely solely on a stale externally-synced counter for enforcement. Options:
1. Make the group account writable and update `group.rate_limiter` synchronously in the same instruction that performs the check (mirrors how the bank-level limiter is already updated inline), eliminating the read-only staleness window.
2. If avoiding a writable group account per instruction is required for performance, track a per-slot or per-transaction "pending" outflow accumulator (e.g., in a smaller PDA or via a CPI-safe atomic counter) that is consulted and updated within the same or nearby instructions, closing the gap that allows unmutated repeated checks.
3. At minimum, shorten the admin aggregation interval drastically and/or add a hard per-instruction/per-account cap that cannot be trivially structured around, similar to always applying a component of the threshold irrespective of the "would it individually breach" test — analogous to the GMX fix of always applying virtual impact rather than gating it on a single marginal-change check.

### Proof of Concept
1. Admin configures `group_rate_limiter` with `groupHourly = 10` (as in the project's own test) via `configure_group_rate_limits`.
2. Attacker (or several attacker-controlled marginfi accounts) issues repeated `lending_account_borrow`/`lending_account_withdraw` instructions, each with USD value just under the currently cached `effective_remaining_capacity` (e.g., 9 USD each).
3. Because `group.rate_limiter` is never mutated by `record_withdrawal_outflow` in the user path (confirmed by [6](#0-5)  showing the counter unchanged after a user borrow), every subsequent call re-checks against the same baseline and succeeds.
4. Total outflow accumulated (e.g., 9 × 20 = 180 USD) far exceeds the configured 10 USD/hour cap, and is only detected — after the fact, with no ability to claw back the funds — once `update_group_rate_limiter` is eventually called by `delegate_flow_admin` and the aggregated total is found to exceed capacity (at which point the *admin update* fails, but the user's withdrawals have already succeeded and funds already left the protocol).

```rust
pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }
```

```markdown
### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.

Important details:

- Flashloans, liquidations, and deleverages skip the normal rate-limit accounting path.
- `RateLimitFlowEvent` is an indexing aid, not a source of truth. Solana log truncation can drop
  events, so the off-chain worker must reconcile gaps instead of assuming no event means no flow.
```

```typescript
  it("(user 2) group rate limiter is read-only during user instructions", async () => {
    // Configure group hourly limit
    await setRateLimits({
      bankHourly: usdcNative(1_000),
      bankDaily: new BN(0),
      groupHourly: new BN(100),
      groupDaily: new BN(0),

    const groupBefore = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    const outflowBefore =
      groupBefore.rateLimiter.hourly.curWindowOutflow.toNumber();

    // Borrow 5 USDC - this should succeed (within limit) but NOT update group state
    await borrowUsdc(usdcNative(5));

    const groupAfterBorrow = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    // Group rate limiter should NOT have changed (it's read-only during user instructions)
    assertBNEqual(
      groupAfterBorrow.rateLimiter.hourly.curWindowOutflow,
      outflowBefore,
    );

    // Repay 5 USDC - group state should also remain unchanged
    await repayUsdc(usdcNative(5));

    const groupAfterRepay = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(
      groupAfterRepay.rateLimiter.hourly.curWindowOutflow,
      outflowBefore,
    );
  });
```
