### Title
Integer underflow in reftable block parsing leads to out-of-bounds slice access and Gitaly process panic - ([File: internal/git/reftable/reftable.go])

### Summary
`internal/git/reftable/reftable.go` parses git's reftable (`.ref`) files using unsigned (`uint`) arithmetic for block/offset bookkeeping without validating that subtractions cannot underflow, mirroring the reported bug class where `uint(left + (right - left) / 2)` overflows/underflows when operands are attacker-influenced. Because `uint` wraps around on underflow in Go, a corrupted/crafted reftable can cause a computed offset to become an enormous value, which is then used directly to slice a byte buffer, causing an out-of-range panic.

### Finding Description
The `parseRefBlock` function computes the start of the restart table as: [1](#0-0) 

```go
b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)
```

All operands (`blockStart`, `currentBS`, `b.RestartCount`) are derived from file bytes read via `extractBlockLen` and `binary.Read` with no independent validation that `currentBS >= 2 + 3*RestartCount`. Because these are `uint` values, if `currentBS` is small (or zero, or corrupted) while `RestartCount` is large, `blockStart + currentBS - 2 - 3*uint(b.RestartCount)` underflows and wraps to a value near `math.MaxUint`, exactly analogous to the reported `uint(left + (right - left) / 2)` overflow class where an unchecked unsigned computation from untrusted bounds produces a huge value instead of erroring out.

This corrupted `RestartStart` is then used directly as a slice/loop bound in `getRefsFromBlock`: [2](#0-1) 

The loop condition `idx < b.RestartStart` combined with subsequent slicing `src[idx:idx+suffixLength]` will attempt to read far outside the buffer bounds, triggering a Go runtime panic (`slice bounds out of range`) rather than returning a graceful error.

Similar unchecked unsigned arithmetic exists in `getBlockRange` and `extractBlockLen`: [3](#0-2) 

`extractBlockLen` slices `src[blockStart+1 : blockStart+4]` without any check that `blockStart+4 <= len(src)`, so a crafted `footerOffset`/`blockSize` combination can also panic here.

Reftable files under a repository's `reftable/` directory are parsed by Gitaly's own code (`reftable.ParseTable`, `Table.GetReferences`, `Table.PatchUpdateIndexes`) whenever transactions replay or resequence tables, as seen in the partition manager's `reftableRecorder.stageTables`: [4](#0-3) 

Because these `.ref` files live inside the repository's on-disk state, any code path that ingests repository data from outside sources (imports, replication, forks, or a compromised source repository being fetched/mirrored) and materializes it into a snapshot processed by this code could feed corrupted reftable bytes into this parser.

### Impact Explanation
A malformed reftable block header can cause an unrecovered panic inside a Gitaly RPC handler thread. Depending on Go's `recover` middleware coverage for this specific goroutine/code path, this results in denial-of-service of the request or, in the worst case, of the Gitaly process itself if the panic occurs outside a recovering wrapper. This aligns with the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
This code path is exercised during internal transaction/table resequencing rather than being a single field trivially reachable from an ordinary RPC. I could not fully confirm within the indexed code the exact external path (e.g., which import/replication RPC first produces a reftable-backed repository state from potentially attacker-influenced bytes) that feeds corrupted `.ref` content into `ParseTable`/`GetReferences`. This limits confidence in exploitability from a purely unprivileged network client; likelihood should be treated as **uncertain/medium** pending confirmation of the ingestion path (e.g., via repository replication or snapshot restore of a corrupted reftable).

### Recommendation
- Validate `currentBS >= 2 + 3*uint(b.RestartCount)` (and similarly bound-check `blockStart+4 <= len(src)` in `extractBlockLen`, and `offset+size` bounds in `getBlockRange`) before performing subtraction, returning an explicit parse error instead of allowing unsigned wraparound.
- Prefer signed integer arithmetic with explicit bounds checks (as already done in `packfile/index.go`'s `math.MaxInt32` checks) over raw `uint` subtraction when values originate from file content.
- Add fuzz/unit tests feeding truncated or crafted reftable blocks into `Table.GetReferences` and `Table.PatchUpdateIndexes` to ensure malformed input yields errors, not panics.

### Proof of Concept
Not independently reproduced against a live Gitaly instance in this analysis. Conceptually: craft a `.ref` reftable file whose ref-block header encodes `currentBS < 2` (or `currentBS < 2 + 3*RestartCount`) so that `parseRefBlock`'s computation of `b.RestartStart` underflows; when the block is subsequently parsed by `Table.GetReferences` (or during table resequencing via `stageTables`), the resulting huge `RestartStart`/`idx` values drive out-of-bounds slicing in `getRefsFromBlock`, panicking the process. Confirming the exact unprivileged trigger (which RPC/import flow first materializes such a file for parsing) requires further investigation of the housekeeping/transaction code (e.g. `internal/gitaly/storage/storagemgr/partition/transaction_manager_housekeeping.go`), which was not fully explored here.

```go
// parseRefBlock parses a block and if it is a ref block, provides
// all the reference updates.
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
```
