### Title
Fixed-window stream throttling in `ConnectionStreamCounter` allows boundary-straddling bursts to ~2x the intended per-interval stream rate - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`throttle_stream` and `ConnectionStreamCounter::reset_throttling_params_if_needed` implement a fixed (tumbling) window rate limiter keyed on wall-clock `Instant`, not a sliding window or token bucket. An attacker who opens `max_streams_per_throttling_interval` streams just before a window reset and another full batch immediately after the reset can push roughly `2 * max_streams_per_throttling_interval` streams through in a time span much shorter than `STREAM_THROTTLING_INTERVAL_MS`, since the check-then-sleep logic only throttles once the counter for the *current* window is exceeded and only resets the counter lazily on the next call after the interval elapses.

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` (`streamer/src/nonblocking/stream_throttle.rs:213-230`) resets `stream_count` to 0 and records a new `last_throttling_instant` only when `Instant::now() - last_throttling_instant > STREAM_THROTTLING_INTERVAL` at the moment a new stream is opened. `throttle_stream` (`stream_throttle.rs:233-271`) checks the counter, and only sleeps (blocking further stream acceptance) if `streams_read_in_throttle_interval >= max_streams_per_throttling_interval`, i.e., streams `1..=max` in a window pass through with zero delay because the check happens strictly before increment (`on_stream_accepted` in `swqos.rs:445-454` increments the counter after `on_new_stream`/`throttle_stream` runs in `quic.rs:624-627`).

Because the reset is lazy and time-based rather than tied to a fixed schedule, an attacker fully controlling packet/stream timing can:
1. Open `max_streams_per_throttling_interval` streams right before the window boundary (all pass instantly, since count goes 0→max-1 checked, all `< max`).
2. Immediately after crossing the boundary, open another `max_streams_per_throttling_interval` streams; the very next call triggers `reset_throttling_params_if_needed` to zero the counter and start a fresh window, so this second batch again passes with zero delay.

This yields up to `2 * max_streams_per_throttling_interval` streams accepted within a time interval that can be made arbitrarily short (bounded only by RTT/QUIC stream-open latency), rather than the intended `max_streams_per_throttling_interval` per `STREAM_THROTTLING_INTERVAL_MS` (100ms). This is the classic fixed-window-counter boundary flaw versus sliding-window/token-bucket designs (Solana's `SimpleQos`/`TokenBucket` path in `simple_qos.rs` does not have this flaw because it uses continuous token replenishment, but the `SwQos` path used with staked/unstaked stream throttling relies on `ConnectionStreamCounter`, which does).

Neither `qos.on_stream_accepted` nor the concurrent-stream cap (`set_max_concurrent_uni_streams`, `swqos.rs:198-224`) prevents this, because that cap only bounds concurrently-open streams, not the aggregate rate of sequential open/close cycles over time; a client can open and immediately finish many short-lived unidirectional streams (each carrying one transaction) well within the concurrency limit while still exploiting the counter-reset boundary.

### Impact Explanation
This is a QoS/rate-limit evasion: an unstaked (or staked) attacker can obtain up to ~2x their intended per-connection stream/TPS allotment for short bursts by timing stream opens around `STREAM_THROTTLING_INTERVAL_MS` boundaries, without needing privileged access, staking, or protocol violations. Repeated exploitation (straddling every window boundary) could sustain a stream rate close to double the configured `max_streams_per_throttling_interval` indefinitely, which degrades fairness for other senders sharing the leader's TPU ingress capacity (`stats.active_streams`, `stats.total_new_streams`) and can amplify unstaked-vs-staked stream ratio imbalance enforced via `StakedStreamLoadEMA`. This falls under a "QoS evasion" style finding but the effect is bounded to roughly a 2x factor per window and does not cause unbounded resource growth, panics, or consensus-affecting failures.

### Likelihood Explanation
Highly feasible for a remote unstaked/staked attacker: it only requires client-side control over stream-open timing relative to a locally-observable window boundary (or simply issuing streams in tight bursts, since any client sending faster than the leader can accept will naturally straddle boundaries whenever a burst happens to align with a reset). It requires no leader/validator control, no key compromise, and is purely a client-side timing choice against publicly reachable QUIC TPU stream-accept logic (`handle_connection` in `streamer/src/nonblocking/quic.rs:583-639`). It is repeatable every `STREAM_THROTTLING_INTERVAL_MS` (100ms) boundary.

### Recommendation
Replace the fixed/tumbling window in `ConnectionStreamCounter` with a sliding-window or continuous token-bucket algorithm (as already used in `simple_qos.rs`'s `TokenBucket`), so that the rate limit is enforced over any rolling `STREAM_THROTTLING_INTERVAL_MS`-length window rather than resetting the counter for the whole interval to zero. Alternatively, retain a fraction of the previous window's count when computing whether the current burst is allowed (a common sliding-window-counter approximation: `effective_count = current_count + previous_count * (interval_remaining_overlap_fraction)`).

```rust
#[tokio::test]
async fn test_boundary_straddle_doubles_effective_rate() {
    use std::sync::atomic::Ordering;
    let stats = Arc::new(StreamerStats::default());
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 50;
    let remote_addr = "127.0.0.1:1".parse().unwrap();

    let start = tokio::time::Instant::now();

    // Batch 1: fill the window right up to the limit.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, remote_addr, &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    // Wait until just past the window boundary (simulate attacker timing).
    tokio::time::sleep(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Batch 2: another full window's worth, immediately after reset.
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, remote_addr, &counter, max_streams).await;
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }

    let elapsed = start.elapsed();
    let total_streams = 2 * max_streams;
    let observed_streams_per_interval =
        total_streams as f64 * (STREAM_THROTTLING_INTERVAL_MS as f64 / 1000.0) / elapsed.as_secs_f64();

    // Assert the observed rate approaches ~2x max_streams_per_throttling_interval,
    // exceeding the intended single-window budget.
    assert!(
        observed_streams_per_interval > 1.5 * max_streams as f64,
        "expected boundary-straddling to approach 2x rate, got {observed_streams_per_interval}"
    );
}
```

```rust
impl ConnectionStreamCounter {
    pub fn new() -> Self {
        Self {
            stream_count: AtomicU64::default(),
            last_throttling_instant: RwLock::new(tokio::time::Instant::now()),
        }
    }

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
}

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
```
