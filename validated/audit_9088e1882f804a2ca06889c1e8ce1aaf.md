Based on the investigation, I found a genuine analog to CVE-2016-9844 (unvalidated attacker-controlled length field used for buffer/array allocation, causing a crash).

### Title
Unvalidated attacker-controlled length used to allocate array in `PrecompiledContracts` byte-array extraction helpers - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`extractBytes32Array` and `extractBytesArray` in `PrecompiledContracts.java` read a length value directly out of caller-supplied calldata (`DataWord[] words`) and use it, unvalidated, to allocate a Java array via `new byte[len][]`, exactly mirroring the CVE-2016-9844 pattern where an unchecked "compression method"/size field taken from untrusted input is used to size a buffer, leading to a crash.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and immediately allocates `new byte[len][]` with no upper bound or sanity check on `len`, and no bounds check that `offset` is within `words.length`: [1](#0-0) 

`extractBytesArray` performs a similar unchecked allocation (`byte[][] bytesArray = new byte[len][]`) after only checking `offset > words.length - 1`, but not validating `len` itself, nor the derived `bytesOffset`/`bytesLen` used afterwards for `extractBytes`: [2](#0-1) 

These helpers are used by precompiled contracts (e.g. `ValidateMultiSign`/`BatchValidateSign`, referenced by matching test classes `ValidateMultiSignContractTest.java` and `BatchValidateSignContractTest.java`) that decode ABI-style arrays of public keys/signatures from smart-contract call data supplied by any transaction sender invoking the precompile via a CALL opcode. Because `len` comes straight from attacker-controlled `DataWord` calldata and can be as large as `Integer.MAX_VALUE` (via `intValueSafe()`), the allocation `new byte[len][]` attempts to allocate a reference array with up to ~2^31 elements (≈16GB on a 64-bit JVM), which throws `OutOfMemoryError`. Unlike checked `Exception`s that TVM call-frame execution generally catches and converts into reverted transactions, `OutOfMemoryError` is an unchecked `Error`; if it is not specifically caught along the precompile execution path, it can propagate out of the transaction-processing thread, exhausting heap and potentially crashing or destabilizing the whole node process — the same "crash via a large size value with insufficient bounds checking" bug class as CVE-2016-9844.

### Impact Explanation
An unprivileged party who can trigger a smart-contract call into the affected precompile (any account can call a deployed contract that invokes it, or the precompile can be invoked directly via a crafted CALL) can supply an oversized length field in calldata to force a very large array allocation. This is a denial-of-service vector against node availability (node crash/instability due to `OutOfMemoryError`), which matches the "node crash or halt" acceptance criteria.

### Likelihood Explanation
Likelihood is limited by unverified factors: I could not confirm within the available tool budget (1) the exact precompiled contract class/method (`ValidateMultiSign`/`BatchValidateSign` inferred from test file names and grep matches) that calls `extractBytes32Array`/`extractBytesArray` with fully attacker-controlled `len`, and (2) whether an outer catch block in the TVM execution path (e.g., in `Program`/opcode dispatch) already catches `Throwable` broadly enough to prevent an `OutOfMemoryError` from crashing the node versus just failing the transaction. Given `intValueSafe()` likely clamps values to avoid overflow but not to a small sane bound, and given other precompiles in this same file (e.g., `VerifyMintProof`, `VerifyTransferProof`) explicitly wrap their logic in `catch (Throwable any)` to defend against exactly this kind of crash, it's plausible the surrounding precompile method for `extractBytes32Array`/`extractBytesArray` lacks the same defensive `Throwable` catch, but this needs direct confirmation.

### Recommendation
Add explicit upper-bound validation on `len` (and on `offset`/derived `bytesOffset`/`bytesLen`) in `extractBytes32Array` and `extractBytesArray` before allocation — reject/return empty arrays if `len` exceeds a small sane maximum (e.g., bounded by remaining `words.length`) — mirroring the defensive pattern already used elsewhere in this file (`VerifyMintProof`/`VerifyTransferProof`'s `catch (Throwable any)` and count bounds checks like `spendCount > 2`).

### Proof of Concept
Craft a transaction invoking the precompile (e.g., `ValidateMultiSign`) with calldata whose array-length word at the relevant `offset` is set to a large value such as `0x7FFFFFFF`, causing `extractBytes32Array`/`extractBytesArray` to execute `new byte[2147483647][]`, exhausting/triggering `OutOfMemoryError` during transaction execution.   private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
