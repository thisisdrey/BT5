### Title
Missing slippage protection in `ExchangeInjectActuator` / `ExchangeWithdrawActuator` allows front-run liquidity manipulation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The reported bug class is that DEX liquidity-provision/removal and swap functions accept a hardcoded `0` for the minimum-acceptable-amount parameter, leaving them exposed to front-running/slippage. In java-tron's built-in bancor-style TRX Exchange module, the same pattern exists: `ExchangeInjectActuator` (inject liquidity, analogous to `addLiquidity`) and `ExchangeWithdrawActuator` (withdraw liquidity, analogous to `removeLiquidity`) compute the counterpart-token amount from the exchange's *current* pool balances at execution time and pay/receive whatever that yields — there is no caller-supplied minimum/expected bound. This is inconsistent with `ExchangeTransactionActuator` (the trade/swap path), which explicitly carries a `tokenExpected` field and rejects the trade if `anotherTokenQuant < tokenExpected`.

### Finding Description
`ExchangeInjectActuator.execute()`/`doValidate()` reads the current `firstTokenBalance`/`secondTokenBalance` from the `ExchangeCapsule` and derives `anotherTokenQuant` purely from the pool ratio at execution time: [1](#0-0) 

The validate path recomputes the same ratio and only checks that the resulting amount is `> 0` and within the account's balance and the global balance limit — no lower bound supplied by the caller is enforced: [2](#0-1) 

`ExchangeWithdrawActuator` has the identical structure: `anotherTokenQuant` is derived from `firstTokenBalance`/`secondTokenBalance` at the time of execution, with only a `> 0` and “Not precise enough” rounding check, never a caller-provided minimum: [3](#0-2) [4](#0-3) 

By contrast, `ExchangeTransactionActuator` — the trade/swap actuator for the very same exchange pool — takes a `tokenExpected` parameter from the contract and validates `anotherTokenQuant >= tokenExpected` before allowing the transaction to execute, exactly the “minimum acceptable amount” safeguard the external report is about: [5](#0-4) 

Because Tron blocks can contain many transactions and the exchange pool state (`firstTokenBalance`/`secondTokenBalance`) is mutable by any account trading against that pool via `ExchangeTransactionContract`, an attacker (or even honest concurrent traders) can shift the pool ratio between when the creator submits an `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction and when it is actually applied by the `Manager` during block application. Since neither actuator lets the caller specify a minimum acceptable counterpart amount, the creator has no on-chain mechanism to bound the loss from such a ratio shift — the transaction either succeeds with whatever amount the manipulated ratio yields, or fails only on unrelated checks (balance, `>0`, precision rounding).

### Impact Explanation
The exchange creator (the only account authorized to call inject/withdraw, per the `is not creator` check in both actuators) can be forced into economically unfavorable liquidity injections or withdrawals by an attacker who front-runs the pending inject/withdraw transaction with `ExchangeTransactionContract` trades that skew `firstTokenBalance`/`secondTokenBalance`. This can cause the creator to inject more value than intended relative to what they receive back, or withdraw a counterpart-token amount worth far less than expected — a direct, unauthorized value transfer from the creator to the front-runner. This matches the funds-loss criteria (unbacked value extraction from a legitimate account operation) called for by the validation rules.

### Likelihood Explanation
Both `ExchangeInjectContract` and `ExchangeWithdrawContract` are ordinary broadcastable transactions that any account (the exchange creator, itself an unprivileged, non-SR actor who created the exchange via `ExchangeCreateActuator`) can submit; `ExchangeTransactionContract` trades that shift the pool ratio are similarly open to any account. No special privilege, timing assumption beyond ordinary transaction ordering, or SR/witness cooperation is required — a rational attacker only needs to observe the pending inject/withdraw transaction in the mempool and submit a trade with a higher energy price/fee to be included first in the same block or an earlier block, a standard front-running pattern already proven feasible against the sibling `ExchangeTransactionActuator` design (which the codebase itself patched with `tokenExpected`).

### Recommendation
Add a caller-supplied minimum/expected-amount field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction when the computed `anotherTokenQuant` falls below (for inject, above) the caller's tolerance, exactly as `ExchangeTransactionActuator` already does for trades.

### Proof of Concept
1. Attacker monitors the mempool and sees a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from the exchange creator for exchange `exchangeId`, injecting `tokenQuant` of `firstTokenID`.
2. Attacker broadcasts an `ExchangeTransactionContract` trade against the same `exchangeId` with a higher fee/priority so it executes first, materially shifting `firstTokenBalance`/`secondTokenBalance` (see `ExchangeTransactionActuator.execute()`, [6](#0-5) ).
3. The creator's inject transaction then executes against the skewed ratio in `ExchangeInjectActuator.execute()` at [7](#0-6) , computing `anotherTokenQuant` from the manipulated `firstTokenBalance`/`secondTokenBalance`, with no `tokenExpected`-style check to abort if the amount is worse than the creator anticipated when signing the transaction.
4. The creator's assets are debited for both `tokenQuant` and the manipulated `anotherTokenQuant` at [8](#0-7) , realizing a worse-than-expected exchange rate with no on-chain recourse — the analog of the `enter()`/`quit()` zero-minimum-amount vulnerability in the external report.
