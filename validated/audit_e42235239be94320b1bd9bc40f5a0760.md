### Title
Transient state-dependent shielded proof failures are permanently cached as invalid in `ZKProofStore`, causing legitimate `ShieldedTransferContract` transactions to be denied forever — analog of the PowerDNS "wrong negative-caching of a validation result" bug class (CVE-2018-14644) - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
`ShieldedTransferActuator.checkProof()` caches the result of a shielded-transaction proof/state check in `ZKProofStore`, keyed only by the transaction id. If validation fails for a *transient* reason (a state-dependent check, not a cryptographic proof defect), the failure is nonetheless recorded as permanent, and any later re-submission of the exact same transaction bytes is rejected immediately from the cache without ever re-running the real check — even after the underlying state condition that caused the failure has changed.

### Finding Description
In `checkProof`: [1](#0-0) 
the store lookup is keyed only on `tx.getTransactionId()`:
```
if (proofStore.has(tx.getTransactionId().getBytes())) {
  if (proofStore.get(tx.getTransactionId().getBytes())) {
    return;
  } else {
    throw new ZkProofValidateException("record is fail, skip proof", false);
  }
}
```
Inside the same try block that performs the cryptographic zk-proof checks, the code also performs a **state-dependent** check unrelated to proof cryptographic validity: [2](#0-1) 
```
long totalShieldedPoolValue = dynamicStore.getTotalShieldedPoolValue();
...
totalShieldedPoolValue = subtractExact(totalShieldedPoolValue, valueBalance);
...
if (totalShieldedPoolValue < 0) {
  throw new ZkProofValidateException("shieldedPoolValue error", true);
}
```
Any exception thrown inside this block sets `firstValidated=true` on `ZkProofValidateException`. Back in `validate()`: [3](#0-2) 
```
try {
  checkProof(spendDescriptions, receiveDescriptions, fee);
} catch (ZkProofValidateException e) {
  if (e.isFirstValidated()) {
    recordProof(tx.getTransactionId(), false);
  }
  throw e;
}
```
Once `false` is recorded for that transaction id in `ZKProofStore` (a plain persistent key-value store, see `ZKProofStore.put/get`): [4](#0-3) 
every future attempt to validate the identical transaction bytes short-circuits to `"record is fail, skip proof"` and is rejected forever, regardless of whether the transient condition (e.g. `totalShieldedPoolValue` recovering) that originally caused the failure has changed.

The transaction id is derived from the full raw transaction data (which is unique per proof/content), so this does not enable cache-poisoning across different transactions, but it does permanently and irrevocably blacklist any specific signed transaction the first time it happens to be processed at an unfavorable moment (e.g., interleaved with other shielded pool transactions, or during a period of low `totalShieldedPoolValue`). This is directly analogous to the PowerDNS bug class: a state/timing-dependent negative result (there: FORMERR to a meta-type query; here: `totalShieldedPoolValue < 0` at that instant) is durably cached as a definitive failure, causing all subsequent legitimate resubmissions to be answered with a hard failure instead of being re-evaluated.

### Impact Explanation
Any unprivileged transaction broadcaster who creates or rebroadcasts a shielded transfer can be permanently denied service for that specific transaction once it is unlucky enough to be processed while `totalShieldedPoolValue` is momentarily insufficient (which can be engineered/timed by another party broadcasting a competing shielded transaction first, or simply occurs naturally under load). Because signed shielded transactions are expensive to regenerate (fresh zk-SNARK proof, new randomness, new signature), this constitutes a griefing/DoS vector against legitimate users of the shielded pool feature and against the node's ability to correctly (re)serve a resubmitted, otherwise-valid broadcast.

### Likelihood Explanation
Exploitation requires only broadcasting standard `ShieldedTransferContract` transactions (network transaction broadcaster capability, no special privileges) and does not require any cryptographic proof forgery — an attacker only needs to cause the `totalShieldedPoolValue` check to fail once for a targeted or arbitrary shielded transaction, which is a purely state-timing manipulation reachable from ordinary transaction submission.

### Recommendation
Do not cache a negative proof result for failures that are not intrinsic to proof cryptographic validity (e.g., state-dependent shielded pool balance checks, or `ArithmeticException` on amount overflow, which are also marked `firstValidated=true`). Only cache negative results for failures rooted in the cryptographic proof itself (`librustzcashSaplingCheckSpend/CheckOutput/FinalCheck`), and separate the pool-balance/arithmetic checks so they are re-evaluated on every submission instead of being memoized permanently in `ZKProofStore`.

### Proof of Concept
1. Ensure the shielded pool's `totalShieldedPoolValue` is low relative to the intended transfer (e.g., wait for a period of low deposits, or race another shielded transaction first).
2. Broadcast a fully valid, cryptographically correct `ShieldedTransferContract` transaction whose `valueBalance` would momentarily push `totalShieldedPoolValue` below zero given the current store state.
3. `ShieldedTransferActuator.validate()` throws `ZkProofValidateException("shieldedPoolValue error", true)`; `recordProof(tx.getTransactionId(), false)` permanently stores `false` for this exact transaction id in `ZKProofStore`.
4. Wait until `totalShieldedPoolValue` recovers (e.g., other deposits occur) and rebroadcast the identical, still cryptographically valid transaction bytes.
5. Observe that `checkProof` now short-circuits on `proofStore.has(...)` and immediately throws `"record is fail, skip proof"`, permanently rejecting the transaction even though it would otherwise pass all checks.

package org.tron.core.store;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.ApplicationContext;
import org.springframework.stereotype.Component;
import org.tron.core.db.TronDatabase;

@Component
public class ZKProofStore extends TronDatabase<Boolean> {

  @Autowired
  public ZKProofStore(ApplicationContext ctx) {
    super("zkProof");
  }

  @Override
  public void put(byte[] key, Boolean item) {
    byte[] b = {(byte) (item.booleanValue() ? 0x01 : 0x00)};
    dbSource.putData(key, b);
  }

  @Override
  public void delete(byte[] key) {
    dbSource.deleteData(key);
  }

  @Override
  public Boolean get(byte[] key) {
    return dbSource.getData(key)[0] == 0x01;
  }

  @Override
  public boolean has(byte[] key) {
    return dbSource.getData(key) != null;
  }
