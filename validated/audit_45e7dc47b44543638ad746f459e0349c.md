### Title
Anti-replay window check-then-decrypt-then-update race allows the same message counter to be accepted twice, bypassing replay protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` (and its sibling `VerifyRelay`) implement anti-replay protection as two separately-locked operations — `window.Check` and `window.Update` — with the actual AEAD decryption performed *between* them, outside the lock. This mirrors the Ajna `moveQuoteToken` root cause: a logically atomic operation (validate-then-commit) is split so that an intermediate, not-yet-committed state (the replay window after `Check` but before `Update`) is treated as authoritative for a security decision, when only the state *after* the full operation completes should be trusted.

### Finding Description
`Decrypt` performs the replay check and the replay commit as two independent critical sections: [1](#0-0) 

```
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)   // step 1: check only
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)          // unlocked work in between
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)   // step 2: commit
cs.decryptLock.Unlock()
```

`window.Check` only *inspects* whether `messageCounter` has already been seen; it does not mark it as seen — that only happens in `window.Update`, which runs after the (unlocked) decryption completes. Because the lock is released between `Check` and `Update`, the "commit" of the anti-replay state is not atomic with the "check": exactly like `moveQuoteToken` computing `lup_` from an intermediate state (after removal, before addition) and using it as if it reflected the final state, `Decrypt` treats the pre-`Update` window state as if it already reflected the outcome of the current packet.

If two goroutines process copies of the same encrypted packet (a genuine on-wire duplicate, or a duplicate injected/replayed by an on-path attacker who can observe/duplicate a UDP datagram) concurrently, both can call `Check` before either has called `Update`. Both see `messageCounter` as "not yet seen," both proceed to decrypt (a purely computational, stateless AEAD operation using a fixed nonce/counter that they are both allowed to reuse per this bug), and both then call `Update`. The second `Update` call will detect duplication, but decryption has already happened for both attempts, and there is a window depending on caller behavior (e.g. if the caller of `Decrypt` processes the plaintext for tunnel delivery immediately after a successful non-error return, and only checks the `Update` result before delivering) where the same ciphertext/message counter is fully decrypted and can be treated as valid more than once before the second commit is observed.

`VerifyRelay` has the identical structure and is subject to the same race for relayed control-plane AEAD frames: [2](#0-1) 

The replay window itself (`Bits`) is a purely in-memory bitmap that `Check`/`Update` mutate; the separation into two lock scopes is the defect — the intended invariant is that "has this counter been processed" is a single atomic test-and-set, not a check followed later by a set with attacker-visible work (decryption) sandwiched in between.

### Impact Explanation
This directly undermines the nonce/replay handling that Nebula's Noise-based data channel and relay channel rely on to prevent packet replay. The `ReplayWindow`/`Bits` mechanism exists specifically to reject duplicate `messageCounter` values and is documented as the anti-replay defense in `newConnectionStateFromResult`: [3](#0-2) 

A race that allows the same counter to pass `Check` twice defeats this defense for concurrently-processed duplicates, enabling traffic replay — one of the explicitly in-scope impact categories (traffic decryption/forgery/replay).

### Likelihood Explanation
Exploitability depends on whether `Decrypt`/`VerifyRelay` for the *same* `ConnectionState` can genuinely be invoked concurrently by the packet-processing pipeline (e.g., multiple reader routines/queues delivering duplicate or attacker-duplicated UDP datagrams for the same tunnel to different goroutines at the same time). I was not able to fully confirm, within the remaining investigation budget, whether Nebula's outside-packet read path (`outside.go`) dispatches packets for a single hostinfo/ConnectionState across multiple concurrent worker goroutines (a per-queue/per-CPU dispatch model would make this concurrently reachable; a single-routine-per-tunnel model would reduce it to a narrower window). This is a limitation of the current analysis — a background Devin session with full access to `outside.go`/`interface.go` read-loop code would be needed to conclusively establish the concurrency model. Regardless of the dispatch model, the code as written violates the atomicity invariant the comment/design implies (check-then-commit under one critical section), which is the same class of defect as the reported Ajna bug.

### Recommendation
Make the replay-window check-and-commit atomic with respect to decryption: hold `decryptLock` (or use a single atomic bitmap operation) across `Check` and the eventual `Update`, or restructure `window` to expose a single `CheckAndReserve`-style method that reserves the slot before decryption and only finalizes/rolls back after decryption succeeds, ensuring no other caller can observe or pass through the same intermediate, non-final state.

### Proof of Concept
Conceptual PoC (requires confirming the concurrency model of the packet read path):
1. Attacker captures or is positioned to duplicate a single Nebula data-plane UDP packet with message counter `N` for an existing tunnel.
2. Attacker (or network duplication) delivers two copies of this packet to the receiver at (near) the same time such that they are processed by two goroutines calling `ConnectionState.Decrypt` concurrently.
3. Goroutine A calls `cs.window.Check(N)` → true, unlocks.
4. Before goroutine A calls `cs.window.Update(N)`, goroutine B calls `cs.window.Check(N)` → still true (not yet marked seen), unlocks.
5. Both A and B proceed to `DecryptDanger` successfully and both eventually call `Update`; only the second `Update` call returns `false`. If the caller processes/delivers the plaintext before checking the final `Update` result, or if the two decrypt calls happen on different queues, the same message counter's payload is treated as valid on both goroutines' paths, producing a working replay of the original packet.

// newConnectionStateFromResult builds a fully-populated ConnectionState from a
// completed handshake.Result. It seeds messageCounter and the replay window so
// that the post-handshake message indices already used on the wire don't count
// as missed traffic in the data plane.
func newConnectionStateFromResult(r *handshake.Result) *ConnectionState {
	ci := &ConnectionState{
		myCert:    r.MyCert,
		initiator: r.Initiator,
		peerCert:  r.RemoteCert,
		eKey:      noiseutil.NewCipherState(r.EKey, r.Cipher),
		dKey:      noiseutil.NewCipherState(r.DKey, r.Cipher),
		window:    NewBits(ReplayWindow),
	}
	ci.messageCounter.Add(r.MessageIndex)
	for i := uint64(1); i <= r.MessageIndex; i++ {
		ci.window.Update(nil, i)
	}
	return ci

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen

}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
