## Analysis

The report's bug class — a downstream call's return value (success/failure signal) not being checked, causing the caller to silently proceed and record state as if the operation succeeded — maps directly onto bazel's Git repository-rule fetch logic in `tools/build_defs/repo/git_worker.bzl`.

### Title
Unchecked git command exit status in `update_submodules` allows fetch of a hostile git submodule to silently fail while Bazel reports the checkout as complete - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` pin the fetched tree to a specific commit or tag, which is the hermeticity/integrity anchor equivalent to a checksum for this repository-rule class. When submodules are enabled (`init_submodules`/`recursive_init_submodules`), the actual `git submodule update` invocation's exit status is discarded, so a submodule fetch that fails (e.g. because the remote — which is not controlled by the pinning superproject commit contents, but can be an attacker-served/mirrored, unreachable, or protocol-mismatched remote pointed to from `.gitmodules`) leaves the working tree with missing or stale submodule content, yet the repository rule returns normally and the fetched repository is treated as successfully materialized.

### Finding Description
In `git_worker.bzl`, most git subcommands are executed through `_git()`, which explicitly checks `st.return_code` and calls `_error()` (which `fail()`s) on non-zero exit: [1](#0-0) 

`fetch()` for the main repository also checks the return code of `_git_maybe_shallow` and falls back correctly: [2](#0-1) 

However, `update_submodules()` calls `_git_maybe_shallow(...)` for the submodule `git submodule update --init [--recursive] --checkout --force` command but never captures or checks its return value: [3](#0-2) 

`_git_maybe_shallow` itself only checks the return code of the *shallow* attempt to decide whether to retry without the shallow flag; the return code of the final (non-shallow) attempt is returned to the caller but never inspected by `update_submodules`: [4](#0-3) 

`_update()` invokes `update_submodules` unconditionally after `fetch`/`reset`/`clean` succeed, with no post-check: [5](#0-4) 

`git_repo()` then proceeds to record the actual HEAD commit and return a success struct regardless of whether submodule materialization actually succeeded: [6](#0-5) 

As a result, if a submodule remote (declared in `.gitmodules` of the fetched superproject, which is itself untrusted content coming from the network) is unreachable, serves a different/corrupted object graph, requires a protocol Bazel's sandboxed git config disallows, or otherwise causes `git submodule update` to fail, this failure is swallowed. The repository rule's downstream logic (`RepositoryDelegatorFunction.DigestWriter`, per the codebase docs) writes a marker file recording the fetch as complete and successful, and the build proceeds using an incomplete/missing/stale submodule tree instead of failing loudly.

### Impact Explanation
The commit/tag pinned in the repository rule (and the submodule commit hashes recorded in the superproject's tree) function as the integrity anchor for this fetch mechanism — analogous to a checksum in `http_archive`. Silently ignoring the submodule-update exit code breaks that invariant: the on-disk repository content used for the build no longer necessarily matches what the pinned commit specifies, without any error being surfaced. This can result in builds silently consuming stale, incomplete, or attacker-influenced content (e.g., an attacker who controls or can disrupt a submodule's origin server so that fetch partially fails) while Bazel reports a normal, successful build, undermining hermeticity guarantees advertised for `git_repository`.

### Likelihood Explanation
Any repository author using `init_submodules = True` or `recursive_init_submodules = True` is affected. The scenario requires only that a submodule fetch fail (network flake, unreachable/moved submodule host, an attacker serving malformed data for a submodule remote/mirror, or Bazel's sandboxed git config — `protocol.file.allow`, environment stripping — interacting badly with a particular submodule host) — no privileged access to the victim's machine is needed, only control or disruption of content served for a URL the victim's build consumes.

### Recommendation
Capture the return value of every `_git_maybe_shallow` call in `update_submodules()` and check `return_code`, calling `_error()` on failure just as `_git()` and `fetch()` do, e.g.:
```python
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        st = _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        st = _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
    if st.return_code != 0:
        _error(ctx.name, ["git", "submodule", "update", "..."], st.stderr)
```

### Proof of Concept
A `src/test/shell/bazel` integration test can reproduce this: set up a superproject with a `.gitmodules` entry pointing at a submodule remote (e.g. served via a local `python -m http.server`/`git daemon` under test control), then simulate a submodule-fetch failure (stop the submodule's server before checkout, or reference an unreachable path) while the superproject fetch itself succeeds. Assert that `bazel build @repo//...` currently succeeds (`bazel build` exits 0, no `_error()` fail message logged) even though the submodule directory is empty/missing, demonstrating that the failure is swallowed instead of failing the build — contrasted with `test_sha256_incorrect`/`test_integrity_incorrect` in `src/test/shell/bazel/external_integration_test.sh`, which correctly fail loudly on checksum mismatches for `http_archive`. def _update(ctx, git_repo):
```text
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:

        update_submodules(ctx, git_repo)
```

```text
    start = [command]
    st = _execute(ctx, git_repo, start + list(args))

        _error(ctx.name, ["git"] + start + list(args), st.stderr)
```

```text
def _git_maybe_shallow(ctx, git_repo, command, *args):
    start = [command]
    args_list = list(args)
    if git_repo.shallow:
        st = _execute(ctx, git_repo, start + [git_repo.shallow] + args_list)
        if st.return_code == 0:
            return st
    return _execute(ctx, git_repo, start + args_list)
```
