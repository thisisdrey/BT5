### Title
Unbounded per-account TRC10 asset-map growth causes DoS-level resource exhaustion in bandwidth accounting and public account queries - (File: chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java)

### Summary
This is a direct analog of the "looping through `registeredCustodians`" bug class: an unprivileged, cheap transaction lets an attacker unboundedly grow a per-account collection, which is later iterated by a shared/critical code path without any cap or gas-style limit, allowing an attacker to inflate the cost of subsequent, otherwise-cheap operations against a victim account.

### Finding Description
Any account can receive `TransferAssetContract` transfers of arbitrary existing TRC10 tokens without permission from the recipient. Each transfer that targets a new token adds a brand-new entry to the recipient's asset map via `AccountCapsule.addAssetAmountV2`, which unconditionally calls `putAssetV2` on the account's map with no maximum-size check: [1](#0-0) 

Because there is no cap on the number of distinct TRC10 tokens (`assetV2` map entries) an account can accumulate, an attacker can dust a victim address with 1 unit of every existing TRC10 asset (there can be many thousands issued on-chain) at negligible cost, growing the victim's `assetV2Map`/`AccountAssetStore` footprint arbitrarily.

This unbounded per-account map is subsequently iterated, without any bound, inside `BandwidthProcessor.updateUsage`: [2](#0-1) 

`getAssetMapV2()` itself can trigger a full underlying DB prefix scan via `importAllAsset`/`AccountAssetStore.getAllAssets` when asset-storage optimization is enabled: [3](#0-2) [4](#0-3) 

`BandwidthProcessor.updateUsage(AccountCapsule)` is invoked from `Wallet.java` (7 call sites found), which backs the public `GetAccountNet`/`GetAccountResource` query endpoints exposed over gRPC/HTTP/JSON-RPC — endpoints any anonymous API client can call for any address. I was not able to pin down the exact line numbers of these call sites within the remaining tool budget, so this part should be verified directly in `framework/src/main/java/org/tron/core/Wallet.java`.

### Impact Explanation
Unlike the `registeredCustodians` report where the loop blocks `checkpoint` for the whole network, here the unbounded loop/DB-scan is keyed per-account and triggered by any client querying that account's resource info (a routine, unauthenticated read). By dusting a high-value target (e.g., an exchange hot wallet or frequently-queried service account) with thousands of distinct TRC10 tokens, an attacker can make every subsequent `GetAccountResource`/`GetAccountNet` query for that account perform an O(n) map iteration plus a potential full RocksDB prefix scan, degrading response latency and consuming CPU/I/O on full nodes that serve these public query APIs — an availability degradation of a node-served API, and by extension a way to grief specific high-traffic accounts (e.g. exchanges) that are frequently queried by bots/wallets before broadcasting transactions.

### Likelihood Explanation
Likelihood is high: `TransferAssetContract` requires no special permission from the recipient, the fee is fixed/cheap regardless of how many distinct tokens exist, and the number of TRC10 assets already registered on a live network is large enough to make this attack straightforward and repeatable against any target address.

### Recommendation
Introduce a hard cap on the number of distinct TRC10 assets (`assetV2` entries) a single account may hold, similar to the recommendation in the source report for `registeredCustodians`, and validate this cap in `TransferAssetActuator`/`AccountCapsule.addAssetAmountV2` before adding a new asset entry. Additionally, avoid recomputing/iterating the entire per-account asset map inside routinely-invoked read paths (`BandwidthProcessor.updateUsage` as called from `Wallet.java` query methods); consider caching or lazily computing only asset entries relevant to the specific request rather than a full map merge/scan.

### Proof of Concept
1. Attacker enumerates existing TRC10 asset IDs on-chain (public data).
2. Attacker repeatedly broadcasts `TransferAssetContract` transactions sending 1 unit of each distinct asset ID to victim address `V` — each such transfer is cheap (bandwidth/energy fee only) and unconditionally adds a new entry to `V`'s `assetV2` map via `AccountCapsule.addAssetAmountV2` (chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java:733-765), with no cap enforced.
3. Once `V`'s asset map contains many thousands of entries, any client calls the public `GetAccountResource`/`GetAccountNet` API for `V`.
4. This triggers `BandwidthProcessor.updateUsage(accountCapsule)` (chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java:47-79), which builds a merged `HashMap` from `getAssetMapV2()` (potentially triggering a full DB prefix scan via `AccountAssetStore.getAllAssets`, chainbase/src/main/java/org/tron/core/store/AccountAssetStore.java:97-109) and `getAllFreeAssetNetUsageV2()`, then iterates the merged map performing per-entry computation — cost scales linearly with the number of distinct assets the attacker seeded, with no upper bound.

    Map<String, Long> assets = new HashMap<>();
    if (account.getAssetOptimized()) {
      Map<WrappedByteArray, byte[]> map = prefixQuery(account.getAddress().toByteArray());
      map.forEach((k, v) -> {

                account.getAddress().toByteArray().length, k.getBytes().length);
        assets.put(ByteArray.toStr(assetID), Longs.fromByteArray(v));
      });
    }
    account.getAssetV2Map().forEach((k, v) -> assets.put(k, v));
