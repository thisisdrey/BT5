### Title
Underlying tokens sent directly to a vault contract are permanently unaccounted-for and unrecoverable - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
Each Zest vault (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) tracks the underlying assets it holds using an internal data variable `assets`, which is only mutated inside `deposit`, `redeem`, `system-borrow`, `system-repay`, `accrue`, and `socialize-debt`. This mirrors the root cause of the "L2 tokens could get stuck" report: an internal accounting counter (`pendingReward` in the Forta `StakingEscrow`, `assets` here) is the sole gate for moving tokens back out, and any tokens that arrive at the contract by a path that does not update that counter become permanently non-transferable, exactly as FORT tokens sent directly to `StakingEscrow` could not be `release`-d because `pendingReward` was never incremented.

### Finding Description
The vault's underlying-asset accounting is entirely internal-counter-based rather than balance-based: [1](#0-0) 
`total-assets` / `total-assets-preview` compute the vault's asset base purely from `(var-get assets)` plus accrued interest — they never read the underlying token's actual on-chain balance held by the contract.

`get-available-assets`, used by `redeem` to gate withdrawals and by `system-borrow` to gate borrowing, is likewise computed solely from the `assets` variable: [2](#0-1) 

`deposit` is the only public entry point that increments `assets`, and it does so by exactly the `amount` transferred in via `receive-underlying`: [3](#0-2) 

`redeem` burns vault shares (`zft`) and sends out `inkind`, computed from `convert-to-assets-preview`, which is itself derived from `total-assets-preview` (i.e., the `assets` counter), not the real token balance: [4](#0-3) 

The underlying token (e.g., `wstx`/`sbtc`/`usdcx`/`usdh`) is a standard SIP-010 fungible token whose `transfer` function can be called by any ordinary principal to send tokens to any address, including the vault contract's principal, without going through `deposit`: [5](#0-4) 

Because `ubalance` (the private helper that reads the contract's real on-chain token balance) is never consulted by `total-assets-preview`, `get-available-assets`, or any withdrawal path, any tokens transferred directly to the vault's principal (bypassing `deposit`) are never reflected in `assets`. There is no `sweep`, `skim`, `donate`, or `rescue` function in any vault contract that would allow those tokens to be pulled back into accounting or returned to the sender. The tokens sit at the contract's address forever, invisible to `total-assets`, `get-available-assets`, `redeem`, `system-borrow`, and `socialize-debt`, with no code path that can move them.

This is the same root cause as the reference report: an internal ledger variable (`pendingReward` there, `assets` here) is required to authorize outbound transfers, and receiving tokens outside the designated deposit path never updates that ledger, so the tokens become stuck with no recovery mechanism.

### Impact Explanation
Any principal (a user, a bot, a integrator contract) that mistakenly calls the underlying token's `transfer` directly to a vault's principal — a natural mistake, since the vault holds and manages that exact underlying asset — permanently loses those funds. They are not counted toward vault assets, cannot be withdrawn by anyone, do not benefit share price (since `total-assets-preview` ignores real balance), and are not recoverable by DAO governance actions visible in these contracts either (no sweep/rescue entry point exists). This falls under the in-scope impact class of **permanent freezing of funds** (Critical), analogous to the escrowed FORT tokens that could never be `release`-d.

### Likelihood Explanation
Likelihood is moderate: this requires a user or integrating contract to send the underlying SIP-010 token directly to the vault's contract principal instead of calling `deposit`. This is a plausible operational/user error, especially for automations, bridges, or scripts that construct a raw token transfer to "top up" or interact with the vault contract address, exactly the scenario that motivated the original Forta report and its subsequent warning-based fix.

### Recommendation
Add a reconciliation mechanism so that tokens received outside `deposit` are not silently and permanently lost:
- Compare the vault's real on-chain balance (`ubalance`) against `(var-get assets)` on `accrue`/`deposit`/`redeem`, and if `ubalance` exceeds `assets` plus any funds earmarked for outstanding operations, treat the surplus as donated liquidity by incrementing `assets` accordingly (as AAVE-style vaults typically do), or
- Add an explicit DAO-authorized `sweep`/`skim` function that can reconcile stray balance into `assets` (benefiting existing depositors) or return it to a specified recipient, and
- At minimum, clearly document/warn users and integrators that sending the underlying token directly to a vault contract (instead of via `deposit`) will permanently freeze those funds, mirroring the warning approach taken in the referenced Forta fix.

### Proof of Concept
1. A vault, e.g. `v0-vault-stx.clar`, is deployed and active with existing depositors and shares (`zft`) outstanding.
2. An ordinary principal Alice calls `wstx transfer` (or the equivalent SIP-010 `transfer` for `sbtc`/`usdcx`/`usdh`) sending `1000` underlying tokens directly to the vault contract's principal, instead of calling `.v0-vault-stx deposit`.
3. The vault's real token balance (`ubalance`) is now `+1000` relative to `(var-get assets)`, but `(var-get assets)` and hence `total-assets-preview`/`get-available-assets` are unchanged.
4. No shares were minted to Alice, so she has no `zft` balance to `redeem`.
5. Calling `get-total-assets`, `get-available-assets`, or any read-only accessor shows no trace of the extra `1000` tokens; `redeem` by any other holder computes `inkind` strictly from the unaffected `assets`/share-supply ratio, so the surplus tokens are never paid out to anyone.
6. There is no sweep/rescue/skim function in the contract (confirmed absent from `mainnet/contracts/vault/*.clar`), so Alice's `1000` tokens remain permanently locked in the vault contract with no code path to retrieve them — a permanent freezing of funds.
