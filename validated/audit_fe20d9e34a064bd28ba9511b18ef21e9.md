### Title
Incorrect proportional `transferUsage` calculation in `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` mirrors the "wrong initialCapacity" bug class — ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
The Sherlock finding shows that `BondBaseSDA._tune()` incorrectly reconstructs a historical quantity (`initialCapacity`) by multiplying an accumulated counter (`market.purchased`) by the *current* instantaneous price, silently assuming that all prior activity happened at today's rate. java-tron's `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` contains the same root-cause pattern: it reconstructs how much of a receiver's accumulated resource-usage counter (`energyUsage`/`netUsage`) should be transferred back to the delegator by multiplying the receiver's *entire* accumulated usage counter by an instantaneous ratio (`unDelegateBalance / getAllFrozenBalanceForEnergy()`), even though that usage was consumed over time against a resource pool whose composition (self-frozen vs. delegated-from-multiple-sources balances) varied historically.

### Finding Description
In `UnDelegateResourceActuator.execute()`: [1](#0-0) 
the code computes
```
transferUsage = (long) (receiverCapsule.getEnergyUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForEnergy()));
```
and the analogous bandwidth branch: [2](#0-1) 

The same logic is duplicated in the TVM native path, `UnDelegateResourceProcessor.execute()`: [3](#0-2) 

`getAllFrozenBalanceForEnergy()`/`getAllFrozenBalanceForBandwidth()` is the *current* total of the receiver's self-frozen balance plus all delegated-in balances (potentially from several different delegators, frozen/undelegated at different times). `getEnergyUsage()`/`getNetUsage()` is the receiver's single accumulated usage counter, built up over the whole decay window, without regard to which frozen-balance "slice" was consumed against.

By applying `unDelegateBalance / totalFrozenBalanceNow` as a flat ratio to the *entire* accumulated usage counter, the calculation implicitly assumes usage was generated uniformly proportional to the resource pool's current composition — exactly the same "reconstruct history using today's ratio" flaw as the bond `_tune()` bug, where `market.purchased` (accumulated) was multiplied by `price_` (current) instead of the price(s) actually paid at purchase time.

This mismatch is exploitable because both `unDelegateBalance` (chosen by the caller) and the receiver's `getEnergyUsage()`/frozen-balance composition (influenced by prior freeze/delegate/consume actions, potentially by a colluding delegator/receiver pair) are attacker-controlled inputs to the ratio, allowing the transferred usage amount to be pushed far from the usage genuinely attributable to the undelegated balance.

### Impact Explanation
`transferUsage` is subtracted from the receiver's usage and added to the delegator's usage via `BandwidthProcessor.unDelegateIncrease`/`EnergyProcessor.unDelegateIncrease`. Usage counters directly gate how much bandwidth/energy an account can still consume for free before paying TRX. By manipulating the ratio between accumulated usage and current frozen-balance composition (e.g., by delegating/undelegating in specific orders, or having a receiver consume heavily right before an undelegate call from an unrelated small delegation), an attacker-controlled pair of accounts can shift an amount of "used resource" onto a victim account (increasing their effective consumption and future TRX cost) or shed usage onto an account that never actually consumed it, effectively creating free bandwidth/energy for themselves — an unbacked-resource / theft-of-service condition reachable purely through the public `UnDelegateResourceContract` actuator or the `unDelegateResource` TVM opcode, both callable by any account holder.

### Likelihood Explanation
This is reachable by any account: an ordinary user can freeze TRC-10-style resource, delegate it to another (possibly self-controlled) account, drive up or down the receiver's usage counter via ordinary transactions, and then call `UnDelegateResourceContract` (or the `unDelegateResource` precompile from a smart contract) to trigger the miscalculation — no special privileges or validator/witness role required. The calculation is deterministic and consensus-critical (it runs in `execute()`, which all full nodes must replicate identically), so any account can trigger it during normal operation.

### Recommendation
Do not reconstruct historical usage attribution from a single current ratio. Either:
1. Track usage per delegation relationship / per frozen-balance source explicitly (so undelegation only reclaims usage that was actually generated against that specific delegated balance), or
2. Cap/bound the transferred usage using a value derived from data at the time delegation was created (similar to Sherlock's suggested fix of persisting `initialCapacity` at tuning time), rather than deriving it from live, attacker-influenced counters at withdrawal time.

### Proof of Concept
1. Delegator D freezes X TRX for ENERGY and delegates it to Receiver R (`DelegateResourceContract`).
2. R separately freezes/receives additional delegated ENERGY from other sources (or self), and consumes energy heavily via contract calls, driving `R.getEnergyUsage()` very high while `R.getAllFrozenBalanceForEnergy()` stays composed mostly of the other sources' balances.
3. D calls `UnDelegateResourceContract` to undelegate a small `unDelegateBalance` from R.
4. `transferUsage = R.getEnergyUsage() * (unDelegateBalance / R.getAllFrozenBalanceForEnergy())` computes a usage transfer disproportionate to what D's small delegated slice actually contributed, moving usage onto D's account (see `UnDelegateResourceActuator.java` lines 103–115) that D never generated, while R's usage is reduced accordingly — demonstrating the historical-vs-current-ratio mismatch analogous to the reported `_tune()` bug.
