### Title
Cross-StackerDB signature replay due to missing contract-identifier (domain-separation) binding in chunk signing digest - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` (used by both chunk signing and verification) hashes only `slot_id`, `slot_version`, and `data_hash`. It never includes the StackerDB's `QualifiedContractIdentifier`. Consequently, a chunk signature that is valid for slot `N` in one StackerDB contract is *also* a valid signature for slot `N` in any other StackerDB contract owned by the same signer address, as long as the version/staleness checks (which are likewise scoped per-`(contract, slot_id)` and independent of the digest) happen to pass. This lets a legitimate signer's chunk, once produced, be replayed/relayed into a StackerDB instance it was never authorized to write to, and have it accepted and propagated as if it were freshly authorized for that instance.

### Finding Description
`SlotMetadata::auth_digest()`: [1](#0-0) 

only commits to `slot_id`, `slot_version`, and `data_hash`. `SlotMetadata::sign`/`verify` operate purely over this digest: [2](#0-1) 

The storage-layer authorization check, `StackerDBTx::try_replace_chunk`, looks up the expected signer *for this particular `smart_contract` and `slot_id`* and then calls `slot_desc.verify(&slot_validation.signer)`: [3](#0-2) 

Because the signed digest never binds the target contract identifier, `verify()` only checks "was this `(slot_id, slot_version, data_hash)` signed by address X" — it cannot distinguish "signed for StackerDB A" from "signed for StackerDB B." If the same signer address happens to own slot `N` in two different StackerDB contracts (e.g., two different `.signers-<set>-<cycle>` reward-cycle contracts, or any pair of StackerDBs where signer slot assignment coincides), a chunk legitimately signed and stored in DB A can be re-submitted (via `POST /v2/stackerdb/.../chunks` or replayed as a `StackerDBPushChunk`/`StackerDBChunkInv`-triggered download) against DB B's slot `N`. `try_replace_chunk`/`validate_received_chunk` will accept it as long as `slot_version` in the replayed metadata exceeds DB B's current stored version for that slot — a condition trivially satisfiable since versions in each DB are independent per-DB Lamport clocks.

The network-facing validators for both push and pull paths reuse the same unscoped check: [4](#0-3) 

and a store that succeeds is unconditionally re-broadcast to the DB's peer set: [5](#0-4) 

This means data authorized only for context A is stored under context B and then propagated network-wide as valid data for B, breaking the equality "signature authorizes write to *this* StackerDB" vs. "signature merely authorizes writing this `(slot_id, slot_version, data_hash)` tuple somewhere."

### Impact Explanation
This breaks the authorization boundary between distinct StackerDB replicas (e.g., distinct signer-set/reward-cycle message contracts). A signer who is legitimately assigned the same (or an overlapping) `slot_id` across multiple StackerDB contracts they control can cause a chunk meant for one context to be accepted, stored, and network-wide propagated as legitimate data for a different context, without ever needing a signature intended for that context — this is an unauthorized write plus forged-data propagation, matching the Critical-impact criteria of "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data."

### Likelihood Explanation
Exploitation requires only that the attacker be a valid signer with a slot in two different StackerDB instances sharing the same `slot_id` — attainable at will since a stacker/signer controls how/when they register and can often arrange to land on the same relative slot index across cycles or DBs, and no special privilege beyond "signer" is needed. The write and gossip paths are fully remote/unprivileged (HTTP `POST /v2/stackerdb/.../chunks`, and P2P push/pull `StackerDBChunk`/`StackerDBPushChunk` messages).

### Recommendation
Include the StackerDB's `QualifiedContractIdentifier` (and ideally the network/chain identifier) inside `SlotMetadata::auth_digest()` so that chunk signatures are cryptographically bound to the specific StackerDB instance they are submitted to, preventing cross-contract signature reuse. This requires a versioned/compat change to `libstackerdb::SlotMetadata` since it changes the signed message format.

### Proof of Concept
1. Register/operate as a signer such that your signer address owns slot `k` in StackerDB contract `A` and also slot `k` in StackerDB contract `B` (both configured on the target node via `stacker_db_configs`).
2. Produce and sign a `StackerDBChunkData` with `slot_id = k`, `slot_version = v`, `data = D` and successfully `POST` it to `A`'s `/v2/stackerdb/.../chunks` endpoint — it is accepted per `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-423`).
3. Re-submit the identical `(slot_id, slot_version, sig, data)` tuple to `B`'s endpoint (or inject it as an unsolicited `StackerDBPushChunk` for contract `B`). Because `slot_desc.verify(&slot_validation.signer)` in `B`'s context only checks the digest over `(slot_id, slot_version, data_hash)` against the signer address that also owns slot `k` in `B`, and `B`'s stored version for slot `k` is `< v`, the chunk is accepted, stored, and rebroadcast for `B` (`stackslib/src/net/relay.rs:2406-2452`) — even though it was never signed with any reference to `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
