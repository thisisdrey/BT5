### Title
Vault `deposit` mints shares based on the nominal `amount` argument instead of the actual underlying tokens received, corrupting share accounting for fee-on-transfer/deflationary underlying assets - (File: `mainnet/contracts/vault/v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`)

### Summary
Every v0 vault's `deposit` function computes the shares to mint from the caller-supplied `amount` and then unconditionally records `assets` as increased by that same `amount`, without ever checking how many underlying tokens the vault actually received from the `transfer` call. If the underlying SIP-010 token ever deducts a fee on transfer (deflationary/fee-on-transfer behavior), the vault credits itself (and the depositor) with more underlying value than it actually holds, which dilutes every other holder of vault shares (zTokens).

### Finding Description
`deposit` in each vault contract (e.g. `mainnet/contracts/vault/v0-vault-sbtc.clar`) does: [1](#0-0) 

```
(inkind (convert-to-shares-preview amount))
...
(try! (receive-underlying amount account))
(try! (ft-mint? zft inkind recipient))
(var-set assets (+ current-assets amount))
```

`convert-to-shares-preview` computes `inkind` from `amount` and the current `total-assets-preview`/`total-supply`, and `receive-underlying` simply forwards the nominal `amount` to the underlying token's `transfer` call without validating the resulting balance delta: [2](#0-1) 

```
(define-private (receive-underlying (amount uint) (account principal))
  (begin
    (try! (contract-call? 'SM3VDXK3WZZSA84XXFKAFAF15NNZX32CTSG82JFQ4.sbtc-token transfer amount account current-contract none))
    (ok true)))
```

The contracts already implement a `ubalance` helper that queries the vault's real underlying balance [3](#0-2)  but `deposit` never uses it to reconcile the actual amount received versus the nominal `amount` before minting shares or updating the `assets` accounting variable. This is the exact root-cause pattern described in the referenced report (M-15): the protocol assumes `transfer amount` always results in a balance increase of exactly `amount`, and mints/records value on that unchecked assumption. The same pattern repeats identically across all six vaults (`v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`) and their `local-testing` counterparts.

The `market.clar` / `v0-4-market.clar` `supply-collateral-add` entry point reaches this same vulnerable path from an ordinary user call: it transfers the underlying token from the caller and then calls `vault-deposit`, which drives the same `deposit` logic above. [4](#0-3) 

### Impact Explanation
If any current or future whitelisted vault underlying asset applies a transfer fee/deflationary mechanic (a property of the SIP-010 asset contract itself, not something the depositor controls), the depositor is credited shares for the full nominal `amount` while the vault's real token balance only grows by `amount - fee`. Because `assets` (the vault's internal accounting of backing value) is also incremented by the full nominal `amount`, every other zToken holder's claim (`convert-to-assets-preview`) is diluted — the vault now believes it holds more underlying than it truly does, so redemptions by other users become undercollateralized. This is a direct loss of value for existing depositors, i.e., theft/permanent impairment of other users' funds at rest, matching the Critical impact class (protocol insolvency / loss of user funds at rest).

### Likelihood Explanation
Likelihood depends entirely on whether a fee-on-transfer/deflationary SIP-010 token is ever used as vault underlying. Today's six underlying assets (wrapped STX, sBTC, stSTX, USDC, USDH, stSTXbtc) are not known to implement transfer fees, so this is a latent defect rather than an immediately exploitable one under the current asset set. However, the code contains no defensive check (e.g., balance-before/balance-after reconciliation) to protect against this class of asset at all, so any future onboarding of such an underlying token (which is a routine DAO action, not a "DAO compromise") would immediately and silently corrupt vault accounting for every depositor.

### Recommendation
In `receive-underlying` (or in each vault's `deposit`), measure the vault's underlying balance before and after the transfer and use the actual delta received — not the nominal `amount` — both for computing `inkind` shares via `convert-to-shares-preview` and for updating the `assets` state variable.

### Proof of Concept
1. Assume a future onboarded vault underlying token implements a 1% transfer fee (deflationary token), and the DAO whitelists it as a supported asset (a routine registry action, not a compromise).
2. User A calls `deposit` with `amount = 1000`. `receive-underlying` calls `transfer 1000` from User A to the vault, but the vault's real balance only increases by `990` due to the fee.
3. `convert-to-shares-preview 1000` mints shares as if `1000` units were deposited, and `assets` is incremented by `1000` even though only `990` were actually received: [5](#0-4) 
4. Vault's `total-assets-preview`/`assets` now overstates real backing by `10` units per `1000` deposited. Every subsequent `redeem` by other depositors computed via `convert-to-assets-preview` proportionally overpays until the vault runs out of real tokens, leaving the last redeemers unable to withdraw their rightful share — a direct loss of user funds.
