## Analysis

The reported bug class — an admin/system function directly mutating pool-pricing state without validating it against currently-accrued values, letting third parties front-run/back-run the update to shift value away from other stakeholders — has a direct analog in the Zest vault contracts' `socialize-debt` function.

### Title
Non-atomic `socialize-debt()` write-down of `lindex` enables sandwich extraction of LP share value - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and equivalent `v0-vault-*.clar` vaults)

### Summary
Every state-mutating vault entry point (`deposit`, `redeem`, `transfer`, `system-borrow`, `system-repay`) begins by calling `(try! (accrue))` to bring `index`/`lindex` current before computing amounts. `socialize-debt()` is the sole exception: it reads `principal-scaled`, `total-borrowed`, `assets`, and `lindex` directly via `var-get` and writes a new `lindex` based on those stale values, with no preceding accrual step. [1](#0-0) 

Compare to `redeem`/`deposit`, which always accrue first: [2](#0-1) 

### Finding Description
`socialize-debt(scaled-amount)` is invoked from `market.clar`'s `liquidate()` path when a borrower's collateral is fully exhausted but debt remains, via `socialize-debt-asset` → `vault-socialize-debt`: [3](#0-2) 

`liquidate()` is a public, unprivileged market entry point that any liquidator can call once a position is underwater (`current-ltv >= ltv-liq-partial`), so `socialize-debt` is reachable purely from ordinary user action — no DAO involvement required.

Inside the vault, `socialize-debt` computes `debt-reduction` and the proportional write-down of `lindex` using the `idx`/`lindex`/`assets` values as they stood at the start of the call, not the values that would result from first running `accrue()`: [1](#0-0) 

Since `lindex` is a core input to `total-assets`/`convert-to-assets-preview`, which price every LP's shares in `redeem`, any accrued-but-not-yet-applied interest at the moment `socialize-debt` runs is not folded in before the write-down is computed and applied. Because `deposit`/`redeem` explicitly always call `accrue()` at their start, an attacker (or opportunistic MEV actor) monitoring a pending liquidation that will trigger `socialize-debt` can:

1. Call `redeem` (which accrues fully, capturing the latest lindex/interest) immediately before the liquidation transaction, unlocking shares at the fully-accrued rate.
2. Let the liquidation's `socialize-debt` call execute, writing down `lindex` proportionally to the bad debt using state that has now diverged from what remaining LPs actually hold, because the redeemer already extracted value at a rate that didn't yet reflect the loss.
3. The remaining LPs absorb a disproportionate share of the write-down relative to what they would have if `socialize-debt` had accrued first and everyone shared the loss pro rata against a consistent, current index.

This mirrors the report's core defect: a state-mutating function that changes pool-wide pricing inputs (`poolSize`/`lindex`) without first reconciling to the current, fully-accrued state, allowing a sandwich around that atomic write to shift loss/gain unfairly between LPs.

### Impact Explanation
This results in temporary freezing/misallocation of unclaimed yield across remaining LPs of the affected vault (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`): honest depositors who do not front-run the liquidation bear a larger share of the socialized bad debt than they should, while the front-runner extracts their redemption at a rate that hasn't yet reflected the loss. This falls under the in-scope High impact class of "theft of unclaimed yield ... or temporary freezing of funds," since remaining LPs' claimable interest/principal is diluted beyond their fair share.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an underwater position with fully exhausted collateral reaching liquidation (an ordinary, expected market condition), and (b) an actor monitoring the mempool/pending liquidation to redeem just beforehand. Both are realistic MEV-style conditions similar to the original report's scenario, though it depends on bad-debt events actually occurring, which are less frequent than routine pool updates.

### Recommendation
Call `(try! (accrue))` at the start of `socialize-debt`, exactly as `deposit`, `redeem`, `system-borrow`, and `system-repay` do, so `index`/`lindex`/`assets` are brought current before the bad-debt write-down is computed and applied. This ensures the loss is socialized against the same fully-accrued state that ordinary redemptions use, closing the front-run/back-run window.

### Proof of Concept
1. Attacker deposits into `v0-vault-stx`.
2. A borrower's position becomes eligible for full liquidation with no collateral left (per `liquidate()`'s `no-collateral-left` check) — attacker observes this in the mempool.
3. Attacker calls `redeem` in a preceding transaction; this internally calls `accrue()` first, so the attacker's shares are priced at the fully up-to-date `lindex`/`total-assets`.
4. The liquidation transaction executes `liquidate()` → `socialize-debt-asset` → `v0-vault-stx.socialize-debt`, which computes the `lindex` write-down from `var-get lindex`/`assets` directly, without an intervening `accrue()` call.
5. Remaining LPs' shares are repriced against a write-down that was not first reconciled to the same accrued baseline the attacker benefited from, causing them to bear a larger share of the bad debt than a fully-accrued socialization would have assigned. [1](#0-0) [4](#0-3)

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))

(define-private (socialize-debt-asset
                (debt-entry { aid: uint, scaled: uint })
                (acc { borrower: principal, success: bool }))
  ;; Early return if previous socialization failed
  (if (not (get success acc))
      acc
      (let ((borrower (get borrower acc))
            (failed-status { borrower: borrower, success: false })
            (asset-id (get aid debt-entry))
            (scaled-debt (get scaled debt-entry)))

            ;; Socialize in vault - pass scaled directly to avoid rounding
            (unwrap! (vault-socialize-debt asset-id scaled-debt) failed-status)
            ;; Refresh cache with new indexes post-write-down (lindex decreased)
            (map-set index-cache
                     { timestamp: stacks-block-time, aid: asset-id }
                     (unwrap! (vault-accrue asset-id) failed-status))
            ;; Remove from obligation
            (unwrap! (contract-call? .v0-market-vault
                                      debt-remove-scaled
                                      borrower
                                      scaled-debt
                                      asset-id) failed-status)
          acc)
        ))
