### Title
Unbounded length field in TVM precompile ABI array decoding causes out-of-bounds array access / crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` decode ABI-encoded arrays from precompile call data by reading a length word directly from attacker-controlled `DataWord[] words` and then looping `for (int i = 0; i < len; i++)` to index `words[offset + i + 1]` without ever validating `len` (or `offset + len`) against `words.length`. This mirrors the CVE-2017-14939 bug class: a length value taken from untrusted input is used to drive array reads without checking it against the real buffer bounds, producing out-of-bounds access instead of a heap over-read.

### Finding Description
`extractBytes32Array` has no offset/length bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` only check `offset > words.length - 1` (i.e., that the length word itself exists), but never validate that `len`, or `offset + i + 1` for the whole loop, stays within `words.length`: [2](#0-1) 

`len` comes from `words[offset].intValueSafe()`, which is fully attacker-controlled (any 32-byte word from calldata coerced to an int). Two failure modes result:
1. If `len` is large but `words` is small (few DataWord slots derived from short calldata), `words[offset + i + 1]` throws `ArrayIndexOutOfBoundsException` on the very first out-of-range index — directly analogous to the "heap-based buffer over-read" in `decode_line_info`/`read_1_byte`, where a length value is trusted and drives a read past the buffer end.
2. If `len` is very large (up to `Integer.MAX_VALUE`), `new byte[len][]` at line 392/404/419 can trigger `OutOfMemoryError` before any bound is checked, since there is no upper cap on `len` relative to the actual calldata size.

`extractBytes` also performs `Arrays.copyOfRange(data, offset, offset + len)` using offsets/lengths derived the same way, so a crafted `bytesOffset`/`bytesLen` can likewise exceed `data.length`: [3](#0-2) 

`extractBytes32Array` is used to parse public-key/address arrays for the `ValidateMultiSign` precompile, and `extractSigArray`/`extractBytesArray` are used similarly for `BatchValidateSign`, both of which are precompiled contracts reachable from any TVM `CALL`/`STATICCALL` to the fixed precompile address by any contract deployer or caller — i.e., directly reachable from an unprivileged transaction.

### Impact Explanation
An attacker-controlled smart contract can call the `ValidateMultiSign`/`BatchValidateSign` precompiles with a crafted `data` payload whose declared array length does not match the real word-array size. This throws an uncaught `ArrayIndexOutOfBoundsException` (or triggers `OutOfMemoryError` for large lengths) during precompile execution inside the TVM. Depending on how the surrounding `execute()`/`Program` exception handling in the TVM interpreter treats such runtime exceptions versus the expected `Program.Exception` hierarchy, this can escape as an unexpected runtime exception during transaction execution, which is a node-crash/DoS class issue when an unprivileged actor can trigger it deterministically via a single transaction — the same practical impact class flagged for CVE-2017-14939 (crash via malformed/oversized length field in untrusted input).

### Likelihood Explanation
Reaching this code only requires deploying a contract that calls a precompile at a fixed, well-known address with crafted calldata — no special privileges, no consensus role, and no cooperation from other participants are needed. The bug is triggered purely by data length mismatches that are trivial to construct.

### Recommendation
Add explicit bounds checks before allocating and iterating: validate `len >= 0`, `offset + len < words.length` (and similarly for the byte-array `data` used in `extractBytes`) before entering the loop in `extractBytes32Array`, `extractBytesArray`, `extractSigArray`, and clamp/validate `bytesOffset`/`bytesLen` in `extractBytes` against `data.length`. Wrap the whole precompile decoding path in exception handling that safely returns a failure result (as other precompiles in this file already do) rather than allowing `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` to propagate.

### Proof of Concept
Construct calldata for `ValidateMultiSign` (or `BatchValidateSign`) where the header word at the expected array-length offset decodes (via `intValueSafe()`) to a large value, e.g. `0x7FFFFFFF`, while the actual calldata is only a few words long. Calling the precompile with this data causes `extractBytes32Array`/`extractBytesArray`/`extractSigArray` to iterate past the bounds of the internally-built `words` array (or attempt `new byte[0x7FFFFFFF][]`), triggering `ArrayIndexOutOfBoundsException` or `OutOfMemoryError` during precompile execution reached from a normal `CALL` opcode in a deployed contract.

Note: I was not able to fully trace, within the tool budget, how the outer `Program`/`OperationActions` CALL-dispatch layer catches exceptions thrown out of `PrecompiledContract.execute()` (i.e., whether it's uniformly wrapped to a revert or can leak an unchecked runtime exception to the node). Confirming the exact propagation behavior (revert-only vs. potential uncaught exception) would need review of the `CALL`/precompile invocation site in `Program.java`/`OperationActions.java`.
