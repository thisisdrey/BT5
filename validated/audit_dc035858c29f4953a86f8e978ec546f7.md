### Title
Conntrack timer wheel is only advanced on new-connection insert, allowing "stuck" idle entries to leak past their timeout and the conntrack table to grow unbounded - ([File: firewall.go])

### Summary
The reported bug class is "value/state produced during an idle period is never rolled into future accounting because the accrual mechanism only runs on a triggering action (a deposit)." The nebula analog is the `Firewall` conntrack `TimerWheel`: it is only `Advance()`-d when a brand-new five-tuple is inserted via `addConn`, not on every packet that matches an already-tracked flow via `inConns`. If no new distinct connections are created for a period, the wheel's clock never moves, so previously-scheduled entries are never rotated into the `expired` list and never actually evicted, even though wall-clock time has passed and their `Expires` field is stale.

### Finding Description
`Firewall.inConns` is the hot path invoked for every packet that matches an existing conntrack entry. It calls `conntrack.TimerWheel.Purge()` once, but never calls `Advance()`: [1](#0-0) 
Only `addConn`, which runs when a **new** flow is tracked, calls `Advance()` before scheduling the entry: [2](#0-1) 
`TimerWheel.Advance` computes elapsed ticks from `lastTick` and rotates the wheel that many ticks, moving expired slots into the `expired` list; without a call to `Advance`, the `current` pointer and `lastTick` never move forward, so nothing is ever queued for eviction: [3](#0-2) 
`evict()` (called from `inConns` after a successful `Purge()`) is the only place that actually deletes a stale `conn` from the `Conns` map or re-schedules it based on its real `Expires` time: [4](#0-3) 
Because `Purge()`/`evict()` can only act on whatever the wheel rotation has moved into the `expired` list, and rotation is gated entirely behind `addConn`'s `Advance()` call, an attacker (or simply low/no new-connection traffic pattern) that avoids creating new distinct tracked tuples prevents the wheel from ever advancing. Any conntrack entries already present — including ones whose `Expires` has long passed because traffic on that tuple actually stopped — are never purged from the `Conns` map. The file's own `TODO: need conntrack max tracked connections handling` comment confirms there is no independent bound on table size: [5](#0-4) 

### Impact Explanation
This is a remote state-poisoning / resource-exhaustion condition in the firewall's connection-tracking subsystem: the `Conns` map, which is meant to be self-pruning via the timer wheel, can silently accumulate stale entries indefinitely once new-connection creation stalls, because eviction is coupled to insertion rather than to wall-clock progress. This falls squarely into the "firewall enforcement" analog category — the conntrack table is precisely the mechanism the firewall uses to fast-path allow/deny decisions, and its bookkeeping (and thus its accuracy/availability) is corrupted by this coupling. Left unbounded, this is a memory-growth / DoS vector on a live tunnel and undermines the intended time-based expiry guarantee that stale flows won't be trusted forever.

### Likelihood Explanation
Reaching this path only requires an already-established tunnel sending packets that match existing conntrack entries (i.e., any peer able to send traffic through the firewall's fast path), not any special privilege beyond that. It does not require a CA-signed certificate beyond what is already necessary to have a live tunnel, and it is triggerable purely through traffic timing/pattern (keep a few flows alive while not creating new distinct ones), making it a low-effort, high-availability condition to trigger.

### Recommendation
Decouple eviction from insertion: call `conntrack.TimerWheel.Advance(time.Now())` unconditionally inside `inConns` (not only in `addConn`) before calling `Purge()`, so wall-clock time always advances the wheel regardless of whether a new connection was created. Alternatively/additionally, drive `Advance()`/`Purge()` from a periodic background ticker (independent of packet arrival) so idle periods with no new connections still age out stale conntrack state, and enforce the already-noted `TODO` of a maximum tracked-connection bound as defense in depth.

### Proof of Concept
1. Establish a tunnel and create one long-lived flow `fp0` (passes `addConn`, which calls `Advance()` once and schedules `fp0`'s timeout in the wheel).
2. Continue sending traffic that matches `fp0` (keeps hitting `inConns`, which refreshes `c.Expires` but never calls `Advance()`).
3. Do **not** open any new distinct five-tuples for a period exceeding `fp0`'s original wheel slot as well as any other already-scheduled entries' timeouts.
4. Because `Advance()` is never invoked outside of `addConn`, the wheel's `current`/`lastTick` never progress; any other entries that should have expired (their real `Expires` already passed) are never rotated into `expired` and thus never evicted from `Conns`, growing the table and retaining stale state past its intended lifetime — observable via `firewall.conntrack.count` in `EmitStats` not shrinking despite idle/expired flows. // Evict checks if a conntrack entry has expired, if so it is removed, if not it is re-added to the wheel
// Caller must own the connMutex lock!
func (f *Firewall) evict(p firewall.Packet) {
	// Are we still tracking this conn?
	conntrack := f.Conntrack
	t, ok := conntrack.Conns[p]
	if !ok {
		return
	}

	newT := t.Expires.Sub(time.Now())

	// Timeout is in the future, re-add the timer
	if newT > 0 {
		conntrack.TimerWheel.Advance(time.Now())
		conntrack.TimerWheel.Add(p, newT)
		return
	}

	// This conn is done
	delete(conntrack.Conns, p)
}

func (tw *TimerWheel[T]) Advance(now time.Time) {
	if tw.lastTick == nil {
		tw.lastTick = &now
	}

	// We want to round down
	ticks := int(now.Sub(*tw.lastTick) / tw.tickDuration)
	adv := ticks
	if ticks > tw.wheelLen {
		ticks = tw.wheelLen
	}

	for i := 0; i < ticks; i++ {
		tw.current++
		if tw.current >= tw.wheelLen {
			tw.current = 0
		}

		if tw.wheel[tw.current].Head != nil {
			// We need to append the expired items as to not starve evicting the oldest ones
			if tw.expired.Tail == nil {
				tw.expired.Head = tw.wheel[tw.current].Head
				tw.expired.Tail = tw.wheel[tw.current].Tail
			} else {
				tw.expired.Tail.Next = tw.wheel[tw.current].Head
				tw.expired.Tail = tw.wheel[tw.current].Tail
			}

			tw.wheel[tw.current].Head = nil
			tw.wheel[tw.current].Tail = nil
		}
	}

	// Advance the tick based on duration to avoid losing some accuracy
	newTick := tw.lastTick.Add(tw.tickDuration * time.Duration(adv))
	tw.lastTick = &newTick
}
