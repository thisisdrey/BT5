### Title
Keyless Groth16 ZK Proof Verification Executes Before Fee Prologue, Enabling Free Validator CPU Exhaustion — (`aptos-move/aptos-vm/src/aptos_vm.rs`)

---

### Summary

In `validate_signed_transaction`, the expensive Groth16 BN254 proof verification for keyless transactions is performed **before** the Move prologue fee check. When an invalid proof is submitted, the transaction is discarded with `INVALID_SIGNATURE` and no fee is charged. Because the sequence number is also not incremented on discard, an attacker with a single valid keyless account can repeatedly submit transactions with the same sequence number but garbage Groth16 proofs, forcing every validator to perform expensive pairing-based cryptographic computation at zero monetary cost.

---

### Finding Description

**Execution order in `validate_signed_transaction`:**

```
validate_signed_transaction()
  ├─ 1. check_signature()          ← cheap: verifies ephemeral Ed25519 sig only
  ├─ 2. validate_authenticators()  ← EXPENSIVE: Groth16 BN254 proof verification
  │       └─ verify_groth16_proof() (~5–10 ms per call)
  └─ 3. run_prologue_with_payload() ← fee/balance check (never reached on proof failure)
``` [1](#0-0) 

The keyless Groth16 proof verification is invoked at lines 1926–1933, inside `validate_signed_transaction`, **before** `run_prologue_with_payload` is called at lines 2071–2080. [2](#0-1) 

The prologue — which checks the sender's balance and would charge a fee — is only reached if `validate_signed_transaction` succeeds. When the Groth16 proof is invalid, the function returns early with an error, and `unwrap_or_discard!` at line 2131 causes the transaction to be **discarded** with no fee deducted and no sequence number increment. [3](#0-2) 

**The expensive computation path:**

Inside `validate_authenticators`, after cheap checks (expiry, feature flags, JWK lookup), `verify_keyless_signature_without_ephemeral_signature_check` is called, which computes `get_public_inputs_hash` and then calls `zksig.verify_groth16_proof(public_inputs_hash, pvk.unwrap())`: [4](#0-3) 

The actual Groth16 verification is a multi-pairing operation on BN254: [5](#0-4) 

**Why `check_signature()` does not catch this:**

`check_signature()` for keyless transactions only verifies the ephemeral Ed25519 signature over `(TXN || ZKP_bytes)`. The ZKP bytes are included in the signed message but their cryptographic validity is **not** checked at this stage — that is explicitly deferred to the VM: [6](#0-5) 

This means an attacker can:
1. Generate a valid ephemeral key pair.
2. Construct a transaction with a garbage/random Groth16 proof.
3. Sign the transaction (including the garbage proof bytes) with the ephemeral key — this signature is valid.
4. Submit the transaction. `check_signature()` passes; `validate_authenticators` then performs the full Groth16 verification and fails.

**The mempool validation path has the same ordering:**

`validate_transaction` (the mempool/vm-validator entry point) calls `validate_signed_transaction` with the same ordering: [7](#0-6) 

A discarded transaction returns `VMValidatorResult::new(Some(err.status_code()), 0)` — score 0, no fee — and is rejected from mempool. The sequence number is not consumed.

**Training wheels partial mitigation:**

When training wheels are enabled on-chain, the Ed25519 training-wheels signature is checked **before** the Groth16 proof: [8](#0-7) 

This means an attacker cannot trigger the Groth16 verification without a valid training-wheels signature (which only Aptos controls). However, training wheels are a **temporary** measure explicitly designed to be removed; the codebase includes tests for the no-training-wheels path (`test_keyless_no_training_wheels_groth16_verifies`), and the production design assumes they will be disabled. Once disabled, the full attack surface is exposed.

---

### Impact Explanation

- **Validator CPU exhaustion**: Each invalid-proof keyless transaction forces ~5–10 ms of BN254 pairing computation on every validator that processes it.
- **Zero monetary cost after account setup**: The transaction is discarded; no fee is charged and no sequence number is consumed, so the same account can resubmit indefinitely.
- **Amplification**: An attacker with `N` valid keyless accounts (each requiring only a one-time OIDC interaction) can sustain `N` parallel streams of invalid-proof transactions, multiplying the CPU load across all validators simultaneously.
- **Chain availability**: Sustained flooding could saturate validator validation threads, delaying or halting block production — matching the "material chain availability failure caused by crafted transaction" impact category.

---

### Likelihood Explanation

- Requires a valid OIDC account (e.g., Google account) to create a keyless account — a low barrier.
- Ephemeral key generation and signing are trivially cheap.
- The Groth16 proof bytes can be random garbage; no cryptographic knowledge is required.
- The attack is fully exploitable whenever training wheels are disabled on mainnet.
- No privileged access, governance, or admin assumptions are needed.

---

### Recommendation

1. **Move the balance/fee check before proof verification**: Perform a lightweight prologue check (account exists, balance ≥ max_gas_fee) before invoking `validate_authenticators`. This ensures that even if the proof is invalid, the attacker's balance is verified and a fee can be seized.
2. **Charge a minimum fee on discard for keyless transactions**: Analogous to how Aptos charges gas for failed executions that pass prologue, introduce a mechanism to deduct a minimum fee when a keyless proof fails verification.
3. **Rate-limit keyless proof verification per sender address** at the mempool layer, independent of sequence number.

---

### Proof of Concept

```
1. Register a Google (or any OIDC) account and derive a keyless Aptos address.
2. Fund the keyless account with APT (so it exists on-chain).
3. Generate a valid ephemeral Ed25519 key pair (esk, epk).
4. Construct a RawTransaction with sequence_number = current_seq, max_gas_amount = 1000, gas_unit_price = 100.
5. Set ZeroKnowledgeSig.proof = Groth16Proof { a: random_g1_bytes, b: random_g2_bytes, c: random_g1_bytes }.
6. Compute txn_and_zkp = TransactionAndProof { message: raw_txn, proof: Some(garbage_proof) }.
7. Sign txn_and_zkp with esk → ephemeral_signature (valid Ed25519 sig).
8. Submit SignedTransaction to any validator REST endpoint.
9. Observe: transaction is discarded with INVALID_SIGNATURE; account balance unchanged; sequence number unchanged.
10. Repeat step 8 in a tight loop — each iteration forces a full Groth16 BN254 pairing verification on the validator at zero cost to the attacker.
```

    fn verify_keyless_ephemeral_signature<T: Serialize + CryptoHash>(
        message: &T,
        signature: &KeylessSignature,
    ) -> Result<()> {
        // Verifies the ephemeral signature on (TXN [+ ZKP]). The rest of the verification,
        // i.e., [ZKPoK of] OpenID signature verification is done in
        // `AptosVM::run_prologue`.
        //
        // This is because the JWK, under which the [ZKPoK of an] OpenID signature verifies,
        // can only be fetched from on chain inside the `AptosVM`.
        //
        // This deferred verification is what actually ensures the `signature.ephemeral_pubkey`
        // used below is the right pubkey signed by the OIDC provider.

        let mut txn_and_zkp = TransactionAndProof {
            message,
            proof: None,
        };

        // Add the ZK proof into the `txn_and_zkp` struct, if we are in the ZK path
        match &signature.cert {
            EphemeralCertificate::ZeroKnowledgeSig(proof) => txn_and_zkp.proof = Some(proof.proof),
            EphemeralCertificate::OpenIdSig(_) => {},
        }

        signature
            .ephemeral_signature
            .verify(&txn_and_zkp, &signature.ephemeral_pubkey)
    }
