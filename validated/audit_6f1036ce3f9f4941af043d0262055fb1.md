## Title
`ERC20Transactor` credits the XCM holding register with the requested amount instead of the amount actually moved by the ERC20 contract, allowing unbacked value creation from non-standard ERC20 tokens - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs` move ERC20 tokens (deployed via `pallet-revive`) into/out of the XCM holding register by calling `IERC20::transfer` and trusting only its boolean return value [1](#0-0) . Neither function verifies the actual balance delta of the `TransfersCheckingAccount` (on withdraw) or of the beneficiary (on deposit) against the claimed `amount`, which is exactly the flaw described in the Sudoswap report: trusting a token transfer's success signal instead of comparing before/after balances.

### Finding Description
`withdraw_asset_with_surplus` transfers `amount` from the user to `TransfersCheckingAccount` via a raw `IERC20::transferCall`, and on `is_success == true` unconditionally mints an `Erc20Credit(amount)` into the XCM `AssetsInHolding` register: [2](#0-1) 

`deposit_asset_with_surplus` performs the mirrored operation, transferring `amount` from `TransfersCheckingAccount` to the beneficiary and treating a `true` return as full success: [3](#0-2) 

In both cases the code only decodes the boolean return of `transfer()` — it never re-reads `balanceOf` before/after to confirm the checking account (or beneficiary) balance changed by exactly `amount`, unlike the safe pattern the Spearbit report recommends (`balanceOf` diff check as done for the router path in `LSSVMPairERC20._validateTokenInput`). Because `Erc20Credit(amount)` is a self-declared imbalance type with no runtime-level balance enforcement — the struct's own doc says "the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [4](#0-3)  — the XCM executor's holding register can end up crediting more value than what was actually locked in the checking account, or actually delivered to the recipient, whenever the target ERC20 contract does not move exactly `amount` tokens (fee-on-transfer, rebasing, or any other non-standard `transfer()` behavior that still returns `true`).

`ERC20Transactor` is wired into the production `AssetTransactors` tuple for the Asset Hub Westend runtime, alongside the native and `pallet-assets` transactors: [5](#0-4) . The asset id for this transactor is the raw contract address (`H160`), matched via `ERC20Matcher`, meaning any contract deployed through `pallet-revive` (permissionlessly, by any user) whose address happens to be matched by the configured `AccountKey20` location scheme becomes a valid XCM fungible asset for this transactor — there is no allow-listing/registration step analogous to `pallet-assets`' `LocalMint`/`NonZeroIssuance` checks used by the sibling `FungiblesTransactor`/`PoolFungiblesTransactor` configs [6](#0-5) .

### Impact Explanation
An attacker can deploy an arbitrary Solidity/PVM contract implementing `IERC20` with `transfer()` that returns `true` while moving less than the requested `value` (fee-on-transfer/deflationary token), or that mints/moves more elsewhere as a side effect. When this contract's address is used as the XCM asset id in a `withdraw_asset`/`deposit_asset` sequence through `ERC20Transactor`, the executor's holding register will contain `amount` fungible credit for that asset even though the real ERC20 balance movement was different. Because XCM instructions such as `DepositAsset`, teleports, or further routing simply move value that is already inside the holding register, this discrepancy lets an attacker manufacture holding-register value that is not fully backed by tokens actually locked in `TransfersCheckingAccount` — a form of unbacked mint/value creation, matching the "theft or unbacked mint or unlock" impact category. This is a public-entrypoint path (any account can submit an XCM `execute`/message using such a contract as asset) requiring no privileged actor, relayer, or validator collusion.

### Likelihood Explanation
Likelihood is limited by two factors that were not fully confirmed within the available context: (1) exactly how `ERC20Matcher` binds a location to a `H160` contract address (i.e., whether arbitrary user-deployed contracts qualify without any allow-list), and (2) whether `pallet-revive`'s gas/weight accounting or downstream checks (e.g., `WeightLimit`, `defensive_assert!`) incidentally prevent malicious contracts from being used this way in practice. The grep results show `ERC20Matcher` is only referenced in `cumulus/parachains/runtimes/assets/common/src/lib.rs` and the Westend asset-hub `xcm_config.rs`; the matcher's exact matching rules were not retrieved before running out of tool calls, so I cannot fully confirm whether registration/allow-listing constraints exist that would reduce exploitability to only trusted/vetted ERC20 contracts.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf` of the relevant account (checking account or beneficiary) before and after the `transfer()` call and only credit/return the actual observed delta, erroring out (as Spearbit recommended for Sudoswap) if the delta does not equal the requested `amount`. This mirrors the "router" path's balance-diff verification the external report specifically called out as the fix.

### Proof of Concept
Not independently executed against a live runtime due to tool constraints; the logical PoC is:
1. Deploy an ERC20-like contract via `pallet-revive` whose `transfer()` deducts `amount` from the sender but credits the recipient with `amount - fee` (or credits a third account with the difference), while still returning `abi_encode_returns(&true)`.
2. Submit an XCM message that `WithdrawAsset`s this contract's token via `ERC20Transactor::withdraw_asset_with_surplus`, then `DepositAsset`s it elsewhere (or teleports/reserve-transfers it) using the holding register value.
3. Because the transactor credits `Erc20Credit(amount)` regardless of the real balance change in `TransfersCheckingAccount`, the deposit/teleport step propagates the full nominal `amount`, even though the checking account only actually received `amount - fee` — creating value in the destination that is not backed by real locked tokens.

/// A minimal imbalance tracking type that holds an ERC20 token amount.
///
/// This type implements the necessary imbalance accounting traits but does not perform
/// runtime-level balance enforcement. It's used to track ERC20 token amounts within XCM
/// asset holdings, where the actual balance constraints are enforced by the ERC20 smart
/// contract itself rather than the runtime.
struct Erc20Credit(u128);
impl UnsafeConstructorDestructor<u128> for Erc20Credit {
	fn unsafe_clone(&self) -> Box<dyn ImbalanceAccounting<u128>> {
		Box::new(Erc20Credit(self.0))
	}
	fn forget_imbalance(&mut self) -> u128 {
		let amount = self.0;
		self.0 = 0;
		amount
	}
}
