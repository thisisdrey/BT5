### Title
TRC10 Exchange creator can atomically drain/reinject pool liquidity to sandwich and steal from ordinary traders - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java, ExchangeInjectActuator.java, ExchangeTransactionActuator.java)

### Summary
The TRC10 `Exchange` (built-in AMM/bancor-style market) grants the pool's `creatorAddress` unrestricted, timelock-free power to withdraw or inject arbitrary amounts of either token via `ExchangeWithdrawContract`/`ExchangeInjectContract`. Because a trader's expected output from `ExchangeTransactionContract` is fully determined by the current pool ratio at the moment of execution, the creator can manipulate that ratio within the same block/transaction sequence to extract value from any trader interacting with the market, exactly mirroring the "coordinator changes margin ratio with no limit or timelock, then liquidates/harms users" bug class from the Perennial report.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` only checks that the caller equals `exchangeCapsule.getCreatorAddress()` [2](#0-1)  and that resulting balances stay non-negative/precise — there is no minimum-liquidity floor, no rate-of-change limit, and no timelock delaying the effect. Likewise `ExchangeInjectActuator.doValidate()` checks only creator identity [1](#0-0)  and an upper `ExchangeBalanceLimit` bound [3](#0-2) , with no lower/rate limit. `ExchangeTransactionActuator.execute()` computes a trader's received amount purely from the live pool balances via `exchangeCapsule.transaction(...)`, which calls the bancor-style `ExchangeProcessor`/`SafeExchangeProcessor` pricing formula [4](#0-3) [5](#0-4) . Because these three actuators can be freely combined by the creator within a single block (or even a single multi-contract transaction), the creator can: (1) withdraw nearly all of one token to skew the ratio just before a victim's trade lands, (2) let the victim's `ExchangeTransactionContract` execute at the manipulated ratio and receive far less than fair value, (3) reinject liquidity and/or withdraw the other token to capture the difference. This is the direct analog of the coordinator setting extreme margin/maintenance ratios with no limit or notice to make positions liquidatable and then profiting — here the "market parameter" is the AMM pool ratio, and the "coordinator" is the exchange creator, both privileged only over their own market/coordinated-market while harming its unprivileged participants.

### Impact Explanation
Any TRC10 exchange creator can, at will and without any protocol-level safeguard, siphon value from arbitrary counterparties trading through their exchange, since price impact/slippage protection for traders is only a caller-supplied `tokenExpected` minimum-output check [6](#0-5) , which does not protect against the creator manipulating balances in adjacent transactions within the same block ordering the creator controls (e.g., as a block-producing SR or via transaction ordering/front-running). This results in theft of user funds from any unprivileged account issuing an `ExchangeTransactionContract` order, satisfying "concrete unauthorized account operation / theft of funds."

### Likelihood Explanation
Likelihood is high for any malicious exchange creator: creating an exchange (`ExchangeCreateActuator`) is permissionless and cheap, and the withdraw/inject/transact sequence requires no special privilege beyond being the creator of one's own exchange — an attacker can create a market, advertise favorable rates, and drain any counterparties who trade into it.

### Recommendation
Add safeguards analogous to the Perennial mitigation: (1) enforce a timelock/cooldown between creator-initiated `ExchangeInjectContract`/`ExchangeWithdrawContract` operations and subsequent trades, or disallow them within the same block as pending trades; (2) impose a maximum percentage change per withdraw/inject relative to current pool balance; (3) strengthen trader-side slippage protection so that `ExchangeTransactionContract` reverts if pool balances changed since query time beyond an acceptable bound, independent of `tokenExpected`.

### Proof of Concept
1. Attacker creates an exchange with tokens A/B via `ExchangeCreateActuator`, becoming `creatorAddress`.
2. Victim queries the pool and broadcasts `ExchangeTransactionContract` expecting a fair-rate trade of A→B with a `tokenExpected` computed off current ratio.
3. Before victim's transaction is packed (or in the same block as SR/attacker), attacker calls `ExchangeWithdrawContract` to remove most of token B, skewing the ratio sharply in the attacker's favor.
4. Victim's `ExchangeTransactionContract` executes at the skewed ratio via `ExchangeCapsule.transaction()` [5](#0-4) , receiving a much smaller amount of B than fair value (but still passing the `tokenExpected` floor if set loosely, or reverting/being resubmitted at worse terms).
5. Attacker calls `ExchangeInjectContract` to restore/rebalance the pool and withdraws the captured surplus, repeating the cycle against subsequent traders.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
