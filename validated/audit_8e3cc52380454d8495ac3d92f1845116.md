### Title
VesperGateway assumes received amount equals sent amount, breaking deposits of vTokens with fee-on-transfer underlying - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` pulls `amount_` of the vToken's underlying asset from the caller and then approves and calls `vToken_.deposit(amount_)` with the same nominal value, ignoring any fee charged on the inbound transfer. If the underlying ERC20 charges a transfer fee, the gateway receives less than `amount_` and the subsequent Vesper deposit always reverts. Notably, the core `DepositToken.deposit` does measure the actual treasury balance delta, so the gateway path is inconsistent with the protocol's own FoT handling.

### Finding Description
In `VesperGateway.deposit`, the underlying asset is pulled with `_underlying.safeTransferFrom(_msgSender, address(this), amount_)` and the code then calls `vToken_.deposit(amount_)` after approving `amount_` [1](#0-0) . For a fee-on-transfer underlying, the gateway's actual balance is `amount_ - fee`, so `vToken_.deposit(amount_)` fails on `transferFrom` with insufficient balance, reverting the whole transaction. The correct pattern is already used elsewhere: `DepositToken.deposit` snapshots the treasury balance and re-bases `amount_` on `balanceOf(_treasury) - _balanceBefore` [2](#0-1) , and `SmartFarmingManager._safeTransferFrom` returns the received delta [3](#0-2) . The gateway even applies balance-delta correctly for the vToken mint at lines 56–58 and for the underlying in `withdraw` at lines 87–89, but not for the underlying pull in `deposit` [4](#0-3) .

### Impact Explanation
Any vToken listed as collateral whose underlying is a fee-on-transfer ERC20 is permanently unusable through `VesperGateway`: every `deposit` call reverts, so users cannot onboard that collateral via the gateway (the designated entry point for depositing vTokens via underlying). This is a liveness/availability break on a collateral path the protocol intends to support, matching the reported bug class (transfer-amount assumption breaks FoT collateral deposits). No funds are stolen; the impact is a permanently reverting deposit path for that collateral configuration.

### Likelihood Explanation
The bug triggers deterministically with any FoT underlying; no attacker is even required — a normal user calling `VesperGateway.deposit` always reverts. Likelihood is bounded by whether governance lists a vToken whose underlying charges transfer fees. Since `DepositToken.deposit` explicitly supports FoT tokens, such collateral is within intended scope, so the defect is reachable on the deployed configuration whenever such a market exists.

### Recommendation
Measure the actual amount received and deposit that into the vToken:

```solidity
// contracts/VesperGateway.sol, deposit()
IERC20 _underlying = IERC20(vToken_.token());
uint256 _underlyingBefore = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
uint256 _received = _underlying.balanceOf(address(this)) - _underlyingBefore;

_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), _received);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(_received);
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
```

### Proof of Concept
Hardhat (TypeScript), using the repo's `ERC20Mock` fee support (as in `test/DepositToken.test.ts` where `met.updateFee(0.1e18)` models a 10% FoT token):

```ts
// test/VesperGateway.fot.test.ts
import {ethers} from 'hardhat'
import {parseEther} from 'ethers/lib/utils'
import {smock} from '@defi-wonderland/smock'
import {expect} from 'chai'

it('reverts depositing a vToken whose underlying is fee-on-transfer', async () => {
  const [alice] = await ethers.getSigners()

  // underlying with 10% transfer fee (same mechanism as ERC20Mock.updateFee)
  const erc20Factory = await ethers.getContractFactory('ERC20Mock')
  const underlying = await erc20Factory.deploy('FoT', 'FOT', 18)
  await underlying.updateFee(parseEther('0.1')) // 10%
  await underlying.mint(alice.address, parseEther('100'))

  // fake Vesper pool whose token() is the FoT underlying;
  // deposit(amount) does transferFrom(gateway, amount) internally
  const vPool = await smock.fake('contracts/interfaces/external/IVPool.sol:IVPool')
  vPool.token.returns(underlying.address)
  // make vPool.deposit actually pull tokens: use a real consumer, or
  // equivalently assert the gateway's post-transfer balance < amount

  const poolRegistry = await smock.fake('contracts/interfaces/IPoolRegistry.sol:IPoolRegistry')
  poolRegistry.isPoolRegistered.returns(true)

  const pool = await smock.fake('contracts/interfaces/IPool.sol:IPool')

  const gatewayFactory = await ethers.getContractFactory('VesperGateway')
  const gateway = await gatewayFactory.deploy(poolRegistry.address)

  await underlying.connect(alice).approve(gateway.address, parseEther('100'))

  // The gateway receives only 90 FOT but approves/calls vPool.deposit(100)
  // -> the vPool's transferFrom(gateway, 100) reverts on insufficient balance.
  await expect(
    gateway.connect(alice).deposit(pool.address, vPool.address, parseEther('100'))
  ).to.be.reverted
})
```

A Foundry variant is equally simple: deploy a fee-charging mock ERC20, a mock `IVPool` that executes `token.transferFrom(msg.sender, address(this), amount)` in `deposit`, and a mock `IPoolRegistry`/`IPool`; call `gateway.deposit(pool, vPool, 100e18)` and assert `vm.expectRevert()`. The assertion holds because after the 10% fee the gateway holds 90e18 while attempting to transfer 100e18.
