## Title
Missing minimum-liquidity validation in `ExchangeCreateActuator` allows attacker-controlled exchange pool ratios and price manipulation - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java`)

### Summary
The Blueberry `AggregatorOracle` issue is about the owner being able to configure a price source with no sanity checks (no address validation, no minimum number of sources), letting a single, unchecked input dictate the reported price. The closest reachable analog in java-tron is `ExchangeCreateActuator`, which lets **any unprivileged account** create a TRX/TRC10↔TRC10 "Exchange" liquidity pool whose only sanity check is that each side's balance is `> 0` and below an upper `balanceLimit` — there is no minimum liquidity requirement and no check on the ratio between the two declared balances.

### Finding Description
`ExchangeCreateActuator.doValidate()` only enforces:
- both token balances `> 0` [1](#0-0) 
- both balances `<= balanceLimit` (an upper bound only) [2](#0-1) 
- that the caller actually owns/holds that amount of each token [3](#0-2) 

There is no floor on the balances and no constraint on the ratio between `firstTokenBalance` and `secondTokenBalance`. A caller can therefore create an exchange with, e.g., `firstTokenBalance = 1` and `secondTokenBalance = balanceLimit`, establishing an arbitrarily skewed initial "price" for that token pair with a trivial amount of capital — exactly the "no minimum source/no validated input" pattern flagged in the reported bug class.

This initial ratio directly drives the bonding-curve pricing used by `ExchangeCapsule.transaction()`, which is invoked by both `ExchangeTransactionActuator` (swap) and `ExchangeWithdrawActuator` (withdraw) to compute how much of the other token a trader receives: [4](#0-3) 

Critically, the relay-token `supply` constant used by the bancor-style formula is a fixed `1_000_000_000_000_000_000L`, independent of the actual balances the creator committed: [5](#0-4) [6](#0-5) 

`ExchangeTransactionActuator` performs no additional check on pool depth/skew before executing a trade — it only validates that the trader's expected output is met and that resulting balances stay under the same upper `balanceLimit`: [7](#0-6) [8](#0-7) 

### Impact Explanation
Because pool creation has no minimum-liquidity or ratio sanity check, an attacker can seed a pool with an extreme, self-chosen exchange ratio using negligible capital (e.g., `1` unit of a worthless/self-issued TRC10 against a large amount of TRX or another valuable TRC10). Any subsequent unsuspecting trader who calls `ExchangeTransactionContract` against that pool — trusting the on-chain "market price" implied by its balances — can be forced into a heavily mispriced trade, resulting in direct loss of funds (TRX or TRC10 assets) to the pool creator. This is a concrete unauthorized-value-extraction / theft-of-funds path reachable purely by signed transactions (`ExchangeCreateContract` then `ExchangeTransactionContract`), matching the reported bug class of "no address/source validation + no minimum count" enabling price manipulation.

### Likelihood Explanation
Exchange creation is permissionless and requires only holding an arbitrarily small amount of two tokens (including a self-issued TRC10, which is cheap and unrestricted to create), so any anonymous transaction broadcaster can set up a manipulated pool. The only real friction is convincing/attracting a counter-party to trade against the skewed pool (or combining with a follow-up injects/transactions in the same block to force victims through it), which lowers but does not eliminate exploitability relative to a pure oracle-source misconfiguration.

### Recommendation
Add a minimum-liquidity floor for both `firstTokenBalance` and `secondTokenBalance` in `ExchangeCreateActuator.doValidate()` (in addition to the existing `> 0` and `balanceLimit` checks), and/or bound the allowable ratio between the two balances at creation time so that pools cannot be created with economically negligible, easily-manipulated reserves.

### Proof of Concept
1. Issue a throwaway TRC10 token `X` (cheap, self-controlled).
2. Broadcast `ExchangeCreateContract` with `firstTokenId = TRX`, `firstTokenBalance = 1` (sun) and `secondTokenId = X`, `secondTokenBalance = balanceLimit` (or vice versa) — this passes all checks in `ExchangeCreateActuator.doValidate()` since both values are `>0` and `<= balanceLimit`. [9](#0-8) 
3. A victim (or an unsuspecting wallet UI trusting the pool's implied rate) calls `ExchangeTransactionContract` to swap TRX for `X` (or vice versa) against this pool; `ExchangeTransactionActuator` computes the payout via `ExchangeCapsule.transaction()` using the attacker-chosen skewed reserves and fixed supply constant, yielding a payout far from any fair market rate. [10](#0-9) 
4. The attacker then withdraws/extracts the disproportionately received TRX via `ExchangeWithdrawActuator`, realizing profit at the victim's expense.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
