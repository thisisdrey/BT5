### Title
Unclaimed `emissions_outstanding` is silently wiped when a Balance is closed via `close_balance`/`withdraw_all`/`repay_all` — ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
This is a direct analog of the reported Alchemix `VotingEscrow` bug class: burning a position (there, an NFT lock; here, a `Balance` slot) without first settling/claiming the position's accrued rewards. In marginfi-v2, each `Balance` tracks unclaimed reward value in `emissions_outstanding`, but the three code paths that close a `Balance` (`close_balance`, `withdraw_all`, `repay_all`) call `Balance::close()`, which unconditionally resets the entire struct — including `emissions_outstanding` — to zero, with no settlement, payout, or even a check that the value is zero first.

### Finding Description
`Balance` stores unclaimed reward accrual per-position: [1](#0-0) 

`Balance::close()` fully overwrites the struct (including `emissions_outstanding`) with an empty/deactivated value: [2](#0-1) [3](#0-2) 

This `close()` is invoked from all three balance-closing paths without ever reading, settling, or transferring `emissions_outstanding` beforehand:
- `withdraw_all` (used by `lending_account_withdraw` when `withdraw_all=true`): [4](#0-3) 
- `repay_all` (used by `lending_account_repay` when `repay=true`): [5](#0-4) 
- `close_balance` (`lending_account_close_balance` instruction): [6](#0-5) 

Notably, the protocol's own error enum already anticipates this exact defect class — an error variant named specifically for it exists but is never referenced by any of the closing functions above: [7](#0-6) 

A related error (`BankCannotClose`, 6078) confirms the protocol's design intent that positions/banks should not be able to close while "emissions outstanding" exist: [8](#0-7) 

That the `emissions_outstanding` field is not merely legacy/dead is confirmed by production account fixtures showing large non-zero values for it: [9](#0-8) 

This exactly mirrors the reported bug class: the "burn" operation (`Balance::close()`) executes before the "claim" step (settling `emissions_outstanding`) ever happens, and there is no code path anywhere in `close_balance`/`withdraw_all`/`repay_all` that reads or pays out this value — it is simply erased.

### Impact Explanation
Any depositor or borrower who calls `lending_account_withdraw` with `withdraw_all=true`, `lending_account_repay` with `repay=true`, or `lending_account_close_balance` while their `Balance.emissions_outstanding` is non-zero permanently loses that accrued reward value — it is zeroed on-chain with no transfer, no event, and no way to recover it afterward (the `Balance` slot is deactivated/reused). This is a permanent freezing/loss of unclaimed yield for unprivileged end users in a routine, frequently-used account-management path (closing a fully repaid/withdrawn position is the standard way to free up a balance slot), which is explicitly in scope per the rules (margin account / core accounting path, no admin/privileged actors involved).

### Likelihood Explanation
High. `withdraw_all` and `repay_all` are the *only* documented way to close a Balance short of the standalone `close_balance` instruction, and users are actively encouraged to use them to free up balance slots (max 3 temporarily active balances per account). Any bank with a non-zero `emissions_rate`/reward campaign accruing into `emissions_outstanding` puts every affected depositor/borrower at risk of losing rewards the moment they fully withdraw or repay, with no warning, no error, and no special conditions required to trigger it.

### Recommendation
Before invoking `Balance::close()` in `close_balance`, `withdraw_all`, and `repay_all`, require that `emissions_outstanding` be zero (returning the existing, currently-unused `MarginfiError::CannotCloseOutstandingEmissions`), or better, settle/transfer the outstanding emissions to the account's `emissions_destination_account` as part of the close flow before zeroing the `Balance`. This mirrors wiring the already-defined but dormant `CannotCloseOutstandingEmissions` check into the three closing code paths.

### Proof of Concept
1. Admin/oracle sets up a bank with `emissions_rate > 0` for the asset side (as reflected in `Bank.emissions_rate` / `emissions_remaining`, see `bank_pyusd_230822.json` fixture fields).
2. A user deposits into that bank and holds the position long enough to accrue a non-zero `Balance.emissions_outstanding` (confirmed possible per the on-chain fixture in `regression.rs` showing `emissions_outstanding = 26891413.388324654086347`).
3. The user calls `lending_account_withdraw` with `withdraw_all = true` (or `lending_account_repay` with `repay = true`, or `lending_account_close_balance`).
4. `BankAccountWrapper::withdraw_all`/`repay_all`/`close_balance` executes `balance.close()`, which sets `emissions_outstanding` to `I80F48::ZERO` unconditionally (`type-crate/src/types/user_account.rs:347-360`).
5. Post-transaction, the account's `Balance` for that bank is inactive with `emissions_outstanding == 0`, and the previously-accrued reward value is unrecoverable — no instruction exists in the closing flow that reads or transfers it out beforehand.

    pub fn close_balance(&mut self, in_receivership: bool) -> MarginfiResult<()> {
        let balance = &mut self.balance;
        let bank = &mut self.bank;

        let current_liability_amount =
            bank.get_liability_amount(balance.liability_shares.into())?;
        let current_asset_amount = bank.get_asset_amount(balance.asset_shares.into())?;

        check!(
            current_liability_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::IllegalBalanceState,
            "Balance has existing debt"
        );

        check!(
            current_asset_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::IllegalBalanceState,
            "Balance has existing assets"
        );

        let asset_shares: I80F48 = balance.asset_shares.into();
        let liability_shares: I80F48 = balance.liability_shares.into();
        // Counters are incremented in `*_balance_internal` when shares cross
        // `ZERO_AMOUNT_THRESHOLD` upward; match that condition so we don't
        // double-decrement positions that already crossed downward earlier.
        let had_assets = asset_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);
        let had_liabs = liability_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);

        balance.close()?;
