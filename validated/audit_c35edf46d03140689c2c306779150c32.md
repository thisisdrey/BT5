### Title
Unprivileged actor can inflate a victim's gas key balance past `MAX_BALANCE_TO_BURN`, permanently blocking `DeleteKey`/`DeleteAccount` - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`action_transfer_to_gas_key` (runtime/runtime/src/access_keys.rs:257-288) only checks that the target public key exists and is a `GasKey` on `account_id`; it performs no actor/permission check tying the caller (predecessor) to the account owner. Since `TransferToGasKeyAction` is treated like a plain `Transfer` in the actor-permission model, any account can send a `TransferToGasKeyAction` receipt with an attached deposit to any victim account's existing gas key, repeatedly inflating `gas_key_info.balance` past `GasKeyInfo::MAX_BALANCE_TO_BURN`. [1](#0-0) 

### Finding Description
`action_transfer_to_gas_key` looks up the access key by `account_id` + `action.public_key`, confirms it is a gas key, and unconditionally adds `action.deposit` to `gas_key_info.balance`: [2](#0-1) 

There is no check that the predecessor of the receipt is the account itself or any privileged actor — the deposit-based `Transfer`-like actions do not require the caller to own the destination account (this is intentional for ordinary `Transfer`, since anyone can send NEAR to any account). By reusing the same permissive model for `TransferToGasKeyAction`, any unprivileged account can top up someone else's gas key with attacker-supplied deposits, repeated over many small receipts, until `gas_key_info.balance` exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN` (1 NEAR).

Once that threshold is exceeded, `delete_gas_key` (called by `action_delete_key` for `DeleteKeyAction`, and by the account-deletion path for every gas key on the account) rejects the deletion: [3](#0-2) 

The guard exists to prevent burning large balances silently, but it has no bypass or reduction mechanism reachable by the victim other than `action_withdraw_from_gas_key`, which requires knowing/using that specific gas key via a *gas-key transaction* (nonce-indexed) — a normal `DeleteKey`/`DeleteAccount` transaction cannot first withdraw the balance down before deleting in the same atomic action list guaranteed to succeed, and the victim has no way to prevent an attacker from re-inflating the balance again immediately after any withdrawal, creating a race the victim cannot reliably win if the attacker keeps re-funding the key. This effectively can be used to grief a victim's ability to delete that specific key (and, since `action_delete_account` iterates over all gas keys and fails via the same check, potentially block account deletion) as long as the attacker keeps the balance above the threshold.

### Impact Explanation
This is a **freezing of victim funds/state** finding: an attacker can force a target gas key's balance above `MAX_BALANCE_TO_BURN`, causing `ActionErrorKind::GasKeyBalanceTooHigh` on `DeleteKey`, and the same guard is invoked per-key during `action_delete_account`, so an attacker could target every gas key on a victim account to block account deletion as well. This maps to the "permanent freezing of a victim account's ability to delete a key or the account" impact category described in the audit scope.

### Likelihood Explanation
- Precondition: the victim must have an existing gas key (a newer NEAR feature; not all accounts have one).
- Cost to attacker: only the deposit amounts sent (which are refundable in the sense they're the attacker's own funds being deposited into the victim's gas key, not destroyed — though they eventually get burned if the victim is ever able to delete the key, or remain "stuck" on the gas key otherwise). The attacker does not need special permissions, elevated access, or any relationship to the victim account — only enough gas/balance to submit ordinary receipts.
- Repeatable: the attack can be repeated indefinitely since nothing stops re-inflating the balance after a partial `WithdrawFromGasKey` by the victim.
- I was unable to fully verify, due to iteration limits, (a) how `TransferToGasKeyAction` interacts with `check_actor_permissions`/`action_validation.rs` in this codebase to confirm there is truly zero actor restriction (I found references in `actions.rs` and `action_validation.rs` but did not get to read their contents before running out of iterations), and (b) whether there is a maximum receiver-specified action-list ordering that would let the victim atomically withdraw-then-delete in a way immune to attacker front-running within the same block/receipt processing. These are relevant to precisely bounding severity and should be confirmed before treating this as fully proven.

### Recommendation
Require `TransferToGasKeyAction` deposits targeting a given gas key to be capped, rate-limited, or restricted so an unrelated account cannot arbitrarily inflate another account's gas key balance past the burn ceiling; alternatively, decouple the `GasKeyBalanceTooHigh` deletion guard from a hard cap that a third party can trivially trigger — e.g., allow the account owner to force-drain/burn a gas key's balance atomically as part of `DeleteKey`/`DeleteAccount` regardless of the `MAX_BALANCE_TO_BURN` limit (subject to appropriate gas/compute charges), or restrict `TransferToGasKeyAction` to require the predecessor equal the receiver account (self-funding only).

### Proof of Concept
Apply-path unit test (extending the existing test module in `runtime/runtime/src/access_keys.rs`):
1. Set up victim account `alice.near` with a gas key via `add_gas_key_to_account`.
2. From an *unrelated* account context, call `action_transfer_to_gas_key` repeatedly (simulating separate small-deposit receipts from an attacker) with deposits summing to just over `GasKeyInfo::MAX_BALANCE_TO_BURN`.
3. Assert each call succeeds (`result.result.is_ok()`), and that `gas_key_info.balance > GasKeyInfo::MAX_BALANCE_TO_BURN` after the loop.
4. Call `action_delete_key` with a `DeleteKeyAction` for that gas key as the victim.
5. Assert `result.result == Err(ActionErrorKind::GasKeyBalanceTooHigh { .. }.into())`, confirming the key (and, by extension via `test_delete_account`, the account) cannot be deleted while the attacker keeps re-funding it above the threshold.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
