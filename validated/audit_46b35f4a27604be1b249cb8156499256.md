### Title
Slippage checks are enforced post-swap instead of inside the swap call, causing `leverage` and `flashRepay` to revert under normal slippage - (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage` and `SmartFarmingManager.flashRepay` execute swaps through the external `Swapper` with `amountOutMin_ = 0`, then check the returned amount only after the swap has already executed. Because the minimum is not enforced inside the swap call, any pool movement between quote and execution causes the whole transaction to revert. This mirrors the wagmi finding: the AMM-level operation is allowed unlimited slippage while a contradictory post-check reverts when any slippage actually occurs.

### Finding Description
In `flashRepay`, the withdrawn collateral is swapped for the synthetic asset with a hardcoded zero minimum:

```solidity
// contracts/SmartFarmingManager.sol:122-126
(_withdrawn, ) = depositToken_.flashWithdraw(_msgSender, withdrawAmount_);
uint256 _swapAmountOut = _swap(swapper(), _collateralOf(depositToken_), _syntheticToken, _withdrawn, 0);
if (_swapAmountOut < swapAmountOutMin_) revert FlashRepaySlippageTooHigh();
```

In `leverage`, both the optional `tokenIn_ -> collateral` swap and the `synthetic -> collateral` swap are executed with `amountOutMin_ = 0` (the comment even states "slippage will be checked later on"), and the check only happens afterwards:

```solidity
// contracts/SmartFarmingManager.sol:183-198
// Note: `amountOutMin_` is `0` because slippage will be checked later on
amountIn_ = _swap(_swapper, tokenIn_, _collateral, amountIn_, 0);
...
uint256 _depositAmount = amountIn_ + _swap(_swapper, syntheticToken_, _collateral, _issued, 0);
if (_depositAmount < depositAmountMin_) revert LeverageSlippageTooHigh();
```

`_swap` forwards that zero minimum verbatim to the swapper:

```solidity
// contracts/SmartFarmingManager.sol:301-306
if (tokenIn_ != tokenOut_) {
    tokenIn_.safeApprove(address(swapper_), 0);
    tokenIn_.safeApprove(address(swapper_), amountIn_);
    uint256 _tokenOutBefore = tokenOut_.balanceOf(to_);
    swapper_.swapExactInput(address(tokenIn_), address(tokenOut_), amountIn_, amountOutMin_, to_);
```

So the `Swapper` executes against live AMM liquidity with no protection (`amountOutMin_ = 0`), and only afterward does `SmartFarmingManager` revert if the result is below the user's expectation. Since the revert rolls back the whole transaction, the protection works — but at the cost of the entire operation failing whenever the price moves unfavorably, which is common during volatility or when the trade itself moves a thin pool. This is reachable by any unprivileged user via the public `leverage`/`flashRepay` entry points, and any unprivileged attacker can grief by sandwiching/pushing the pool price past the caller's `depositAmountMin_`/`swapAmountOutMin_` to force reverts.

### Impact Explanation
Temporary freezing of funds / liveness failure of core protocol operations. `flashRepay` is the mechanism a leveraged user relies on to deleverage and repay debt; repeated reverts during volatile markets can prevent timely deleveraging, exposing the position to liquidation. `leverage` similarly fails whenever the two chained swaps slip. A malicious actor can also deliberately move the relevant AMM price before the victim's transaction lands, forcing `LeverageSlippageTooHigh`/`FlashRepaySlippageTooHigh` reverts while only paying for a pool trade.

### Likelihood Explanation
High under realistic conditions: the swapper routes through external AMMs where prices move with every trade, and `leverage` performs two sequential swaps whose combined slippage must stay under a single `depositAmountMin_`. The existing test suite itself demonstrates this: setting `swapper.updateRate(0.9e18)` makes `leverage` revert with `LeverageSlippageTooHigh` and `flashRepay` revert with `FlashRepaySlippageTooHigh` even though each call supplied a sensible minimum (test/SmartFarmingManager.test.ts:256-269, 356-370). Modifiers (`whenNotShutdown`, `nonReentrant`, `onlyIfDepositTokenExists`, `onlyIfSyntheticTokenExists`) do not mitigate it, and the final `PositionIsNotHealthy` check adds another revert surface on top of the unprotected swaps.

### Recommendation
Pass the user's slippage tolerance into the swap calls themselves instead of checking after the fact. For `leverage`, split `depositAmountMin_` into per-swap minimums (e.g., a `collateralAmountMin` for the `tokenIn_ -> collateral` leg and enforce the remaining tolerance on the `synthetic -> collateral` leg via `amountOutMin_`), and for `flashRepay` pass `swapAmountOutMin_` directly as `amountOutMin_` to `swapper_.swapExactInput`. This way the swap fails atomically at the AMM level with a meaningful error rather than executing an unprotected trade and reverting afterwards.

### Proof of Concept
Reproducible on a fork/Hardhat using the existing test harness:

```typescript
// test/SmartFarmingManager.test.ts (existing pattern)
// 1. alice calls leverage(vaDAI, msdVaDAI, msUSD, 100e18, 1.5e18, depositAmountMin)
//    expecting ≤5% slippage on the synthetic->collateral leg.
// 2. Before her tx mines, an attacker swaps in the underlying AMM,
//    moving the msUSD/collateral price by >5% (test models this via
//    swapper.updateRate(parseEther('0.9'))).
// 3. alice's tx executes the swap with amountOutMin = 0, receives
//    ~10% less, then reverts with LeverageSlippageTooHigh.
// 4. The same applies to flashRepay: any adverse move makes the
//    deleverage/repay operation revert, leaving the unhealthy position open.
```

The checks `LeverageSlippageTooHigh` (line 198) and `FlashRepaySlippageTooHigh` (line 126) fire precisely because the preceding `_swap(..., 0)` calls at lines 125, 184 and 197 carry no minimum, confirming the mismatch between hardcoded zero slippage at the swap layer and expected slippage at the post-check layer.
