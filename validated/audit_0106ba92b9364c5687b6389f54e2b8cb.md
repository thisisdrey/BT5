### Title
Retroactive interest rate application due to missing accrual checkpoint on bank config updates - ([File: programs/marginfi/src/instructions/marginfi_group/configure_bank.rs])

### Summary
`lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only` mutate `Bank.config.interest_rate_config` directly without first calling `accrue_interest` to checkpoint the bank's `last_update` timestamp. Because `accrue_interest` always charges the *current* rate config over the full `time_delta` since `last_update`, any rate change made by the admin (or delegate curve admin) gets retroactively applied to the entire elapsed period since the last accrual—including the period *before* the rate change took effect. This is the same bug class described in the external report: the contract fails to track historical rate values across the accrual period and instead applies "whatever rate is set at withdraw/accrual time" to the whole span.

### Finding Description
`Bank::accrue_interest` computes `time_delta = current_timestamp - self.last_update` and then calls `calc_interest_rate_accrual_state_changes` using `self.config.interest_rate_config` (via `create_interest_rate_calculator`) for the *entire* `time_delta`: [1](#0-0) 

`last_update` is only advanced when `accrue_interest` actually runs (i.e., on a user deposit/withdraw/borrow/repay/permissionless-accrue), not when the admin changes the interest rate config. Both configuration paths mutate the rate config in place without accruing first: [2](#0-1) [3](#0-2) 

`Bank::configure` (called by `lending_pool_configure_bank`) simply calls `self.config.interest_rate_config.update(ir_config)` with no accrual checkpoint: [4](#0-3) 

Consequently, if a bank goes some period of time without any user interaction (a common occurrence for less-active banks per the project's own documentation), and the admin changes the interest rate curve during that idle window, the *next* accrual (triggered by any ordinary, unprivileged user's deposit/withdraw/borrow/repay) will apply the brand-new rate retroactively across the entire idle period, not just from the moment of the change onward. This directly mirrors the reported bug pattern: `blockCount(T,T+100) * whateverRateIsSetAtWithdrawTime` instead of correctly splitting the period by the rate that was actually in effect during each sub-interval.

### Impact Explanation
This corrupts the core accounting invariant of the protocol: `asset_share_value` and `liability_share_value` (and thus every user's real balance, health, and the fee amounts collected into `collected_insurance_fees_outstanding` / `collected_group_fees_outstanding` / `collected_program_fees_outstanding`) are computed using a rate that was never actually in effect for part of the elapsed period. Depending on the direction of the admin's rate change:
- If the new borrow rate is lower than the old one, borrowers are undercharged for the pre-change period, meaning lenders receive fewer assets than they are entitled to for that span — a shortfall that is not compensated anywhere, effectively insolvency/bad debt for lenders.
- If the new borrow rate is higher, borrowers are retroactively overcharged for time before the change took effect, incorrectly inflating their liabilities and potentially pushing otherwise-healthy unprivileged accounts toward liquidation/bad debt they should not have incurred.

Because share values are shared bank-wide state, this misallocation affects every unprivileged depositor and borrower in the bank, not just an admin-controlled account, and the resulting share-value corruption is permanent (baked into `asset_share_value`/`liability_share_value`, which are never retroactively corrected).

### Likelihood Explanation
Any interest rate config change instruction (`lending_pool_configure_bank`, `lending_pool_configure_bank_interest_only`) can trigger this whenever the bank has gone even a small amount of time without an accrual. The protocol's own documentation acknowledges banks can go long periods without any interaction ("Less popular Banks might compound just a few times per week"), so this is not a rare edge case but a routine operational scenario for any bank whose interest curve is adjusted by the admin/delegate curve admin.

### Recommendation
Force an interest accrual (`accrue_interest`) and cache update immediately before applying any change to `interest_rate_config`, in both `lending_pool_configure_bank` (when `bank_config.interest_rate_config.is_some()`) and `lending_pool_configure_bank_interest_only`. This checkpoints `last_update` and locks in interest under the old rate up to the moment of the change, so that the new rate only applies going forward — analogous to snapshotting the old "rewardPerBlock" before switching to a new one, as recommended in the referenced report.

### Proof of Concept
1. Bank `B` has `last_update = T0`, with `interest_rate_config` R1 (e.g., 10% borrow APR at current utilization).
2. No user interacts with `B` for 30 days (a routine gap, consistent with the project's documented behavior for less-active banks).
3. At `T0 + 30d`, the group admin (or delegate curve admin) calls `lending_pool_configure_bank_interest_only` to change the curve to R2 (e.g., 40% borrow APR). This updates `bank.config.interest_rate_config` in place; `last_update` remains `T0`.
4. At `T0 + 31d`, an ordinary unprivileged user calls `deposit`/`withdraw`/`borrow`/`repay` (or the permissionless `lending_pool_accrue_bank_interest`). `accrue_interest` runs with `time_delta = 31 days` and applies R2 (40% APR) across the *entire* 31-day span, even though R1 (10% APR) was in effect for the first 30 of those days.
5. Result: borrowers are charged 40% APR interest for 30 days they should have been charged only 10% APR, and lenders' `asset_share_value` is inflated to match — an unrecoverable retroactive misstatement of every unprivileged account's balance in the bank, matching the exact bug class in the external report.     /// Calculate the interest rate accrual state changes for a given time period
    ///
    /// Collected protocol and insurance fees are stored in state.
    /// A separate instruction is required to withdraw these fees.
    fn accrue_interest(
        &mut self,
        current_timestamp: i64,
        group: &MarginfiGroup,
        #[cfg(not(feature = "client"))] bank: Pubkey,
    ) -> MarginfiResult<()> {
        #[cfg(all(not(feature = "client"), feature = "debug"))]
        sol_log_compute_units();

        let time_delta: u64 = (current_timestamp - self.last_update).try_into().unwrap();
        if time_delta == 0 {
            return Ok(());
        }

        let total_assets = self.get_asset_amount(self.total_asset_shares.into())?;
        let total_liabilities = self.get_liability_amount(self.total_liability_shares.into())?;

        self.last_update = current_timestamp;

        if (total_assets == I80F48::ZERO) || (total_liabilities == I80F48::ZERO) {
            #[cfg(not(feature = "client"))]
            emit!(LendingPoolBankAccrueInterestEvent {
                header: GroupEventHeader {
                    marginfi_group: self.group,
                    signer: None
                },
                bank,
                mint: self.mint,
                delta: time_delta,
                fees_collected: 0.,
                insurance_collected: 0.,
            });

            return Ok(());
        }
        let ir_calc = self
            .config
            .interest_rate_config
            .create_interest_rate_calculator(group);

        let InterestRateStateChanges {
            new_asset_share_value: asset_share_value,
            new_liability_share_value: liability_share_value,
            insurance_fees_collected,
            group_fees_collected,
            protocol_fees_collected,
        } = calc_interest_rate_accrual_state_changes(
            time_delta,
            total_assets,
            total_liabilities,
            &ir_calc,
            self.asset_share_value.into(),
            self.liability_share_value.into(),
        )?;
