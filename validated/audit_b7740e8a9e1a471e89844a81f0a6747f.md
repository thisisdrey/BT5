### Title
Unvalidated uint16 Offset/Length in Windows Reparse-Point Symlink Parsing Causes Heap Buffer Over-Read - ([File: src/internal/syscall/windows/reparse_windows.go])

### Summary
`SymbolicLinkReparseBuffer.Path()` and `MountPointReparseBuffer.Path()` compute the substitute-name slice bounds directly from attacker-influenced `uint16` `SubstituteNameOffset`/`SubstituteNameLength` fields sourced from raw NTFS reparse-point data, without validating that `SubstituteNameOffset+SubstituteNameLength` stays within the actual `MAXIMUM_REPARSE_DATA_BUFFER_SIZE` buffer returned by the OS. [1](#0-0)  Because the pointer is reinterpreted as a fixed `[0xffff]uint16` array, an offset/length pair that is valid with respect to the `0xffff` cap but exceeds the real 16 KiB allocation causes a read past the end of the actual buffer — the same "offset + size not checked against real length" primitive as the PHP EXIF CVE-2018-14883. [2](#0-1) 

### Finding Description
An unprivileged actor who can place a crafted NTFS reparse point on a filesystem (e.g. a maliciously crafted removable/USB volume, VHD, or a symlink/junction whose raw reparse data is written directly via `FSCTL_SET_REPARSE_POINT` instead of the well-formed `CreateSymbolicLink` API) controls the `ReparseTag`, `SubstituteNameOffset` and `SubstituteNameLength` fields of the on-disk `REPARSE_DATA_BUFFER`. A victim process calling `os.Readlink`, `os.Lstat` on a name surrogate, or walking such a tree reaches `os.readReparseLinkHandle`, which issues `syscall.DeviceIoControl(h, syscall.FSCTL_GET_REPARSE_POINT, ...)` into a fixed `rdbbuf := make([]byte, syscall.MAXIMUM_REPARSE_DATA_BUFFER_SIZE)` buffer and dispatches on `rdb.ReparseTag`. [3](#0-2)  For `IO_REPARSE_TAG_SYMLINK`/`IO_REPARSE_TAG_MOUNT_POINT`, it calls `SymbolicLinkReparseBuffer.Path()`/`MountPointReparseBuffer.Path()`, which compute `n1 := rb.SubstituteNameOffset/2` and `n2 := (rb.SubstituteNameOffset+rb.SubstituteNameLength)/2` and then slice `(*[0xffff]uint16)(unsafe.Pointer(&rb.PathBuffer[0]))[n1:n2:n2]`. [4](#0-3)  There is no check that `n2` (which can be as large as `0x7fff`) fits inside the actual bytes returned by `DeviceIoControl` or inside the real `MAXIMUM_REPARSE_DATA_BUFFER_SIZE` allocation, only that it is `<= 0xffff` (the size of the artificial array overlay). The failed check is therefore the missing bound `SubstituteNameOffset+SubstituteNameLength <= actual buffer/ReparseDataLength`, and the sink is the `unsafe.Pointer` cast plus 3-index slice expression in `Path()`, which reads adjacent heap memory belonging to other allocations when `n2` exceeds the true buffer size.

### Impact Explanation
Reading past the end of `rdbbuf` discloses adjacent heap memory contents as part of the returned "symlink target" string, which can leak sensitive process memory to a log, file listing, or error message a normal user session might display; in the worst case with `n1 > n2` after possible wraparound behavior the slice expression can also trigger a runtime panic (bounds violation), i.e., a crash/DoS on ordinary filesystem traversal of attacker-controlled media. This matches Go's PUBLIC track class of "parser panic / memory disclosure on malicious input" rather than remote code execution.

### Likelihood Explanation
The victim workflow is entirely ordinary: any Go program on Windows that calls `os.Readlink`, `os.Lstat`, `filepath.Walk`/`filepath.WalkDir`, or similar over a directory tree that includes a symlink/junction/reparse point supplied by an unprivileged/attacker-controlled source (an external drive, downloaded archive extracted with low-level reparse creation, or a mounted disk image) will invoke this code path. The attacker's only capability required is the ability to place a file with a crafted reparse buffer that the victim later inspects — a low-privilege capability, consistent with the "ordinary user data consumed by a normal victim workflow" premise.

### Recommendation
In `Path()` (`src/internal/syscall/windows/reparse_windows.go`), validate `n1` and `n2` against the actual reparse buffer size (e.g. `rdb.ReparseDataLength` or the number of bytes returned by `DeviceIoControl`) before constructing the slice, and reject/error out if `SubstituteNameOffset+SubstituteNameLength` exceeds that bound or overflows `uint16`, instead of only bounding by the synthetic `0xffff` array cap.

```go
func TestSymbolicLinkReparseBuffer_PathOOB(t *testing.T) {
    // Simulate a crafted on-disk SymbolicLinkReparseBuffer:
    // SubstituteNameOffset = 0x2000, SubstituteNameLength = 0x2000
    // -> n1 = 4096, n2 = 8192, but the real allocated PathBuffer region
    // inside a 16KiB MAXIMUM_REPARSE_DATA_BUFFER_SIZE buffer is much smaller
    // once the struct header is subtracted.
    buf := make([]byte, 64) // deliberately undersized vs. offset/length claimed
    rb := (*windows.SymbolicLinkReparseBuffer)(unsafe.Pointer(&buf[0]))
    rb.SubstituteNameOffset = 0x2000
    rb.SubstituteNameLength = 0x2000

    // Expected: Path() should return an error / not read beyond len(buf).
    // Actual (vulnerable): Path() casts to (*[0xffff]uint16) and slices
    // [4096:8192:8192], reading far past the 64-byte allocation.
    defer func() {
        r := recover()
        if r == nil {
            t.Fatalf("expected out-of-bounds read or explicit validation error, got neither")
        }
    }()
    _ = rb.Path()
}
```
Expected assertion: `Path()` must reject offset/length combinations that exceed the real buffer size instead of silently reading adjacent heap memory (or panicking with an unguarded slice-bounds violation caused by attacker-controlled `uint16` fields).

```go
type SymbolicLinkReparseBuffer struct {
	// The integer that contains the offset, in bytes,
	// of the substitute name string in the PathBuffer array,
	// computed as an offset from byte 0 of PathBuffer. Note that
	// this offset must be divided by 2 to get the array index.
	SubstituteNameOffset uint16
	// The integer that contains the length, in bytes, of the
	// substitute name string. If this string is null-terminated,
	// SubstituteNameLength does not include the Unicode null character.
	SubstituteNameLength uint16
	// PrintNameOffset is similar to SubstituteNameOffset.
	PrintNameOffset uint16
	// PrintNameLength is similar to SubstituteNameLength.
	PrintNameLength uint16
	// Flags specifies whether the substitute name is a full path name or
	// a path name relative to the directory containing the symbolic link.
	Flags      uint32
	PathBuffer [1]uint16
}

// Path returns path stored in rb.
func (rb *SymbolicLinkReparseBuffer) Path() string {
	n1 := rb.SubstituteNameOffset / 2
	n2 := (rb.SubstituteNameOffset + rb.SubstituteNameLength) / 2
	return syscall.UTF16ToString((*[0xffff]uint16)(unsafe.Pointer(&rb.PathBuffer[0]))[n1:n2:n2])
}
```

```go
func readReparseLinkHandle(h syscall.Handle) (string, error) {
	rdbbuf := make([]byte, syscall.MAXIMUM_REPARSE_DATA_BUFFER_SIZE)
	var bytesReturned uint32
	err := syscall.DeviceIoControl(h, syscall.FSCTL_GET_REPARSE_POINT, nil, 0, &rdbbuf[0], uint32(len(rdbbuf)), &bytesReturned, nil)
	if err != nil {
		return "", err
	}

	rdb := (*windows.REPARSE_DATA_BUFFER)(unsafe.Pointer(&rdbbuf[0]))
	switch rdb.ReparseTag {
	case syscall.IO_REPARSE_TAG_SYMLINK:
		rb := (*windows.SymbolicLinkReparseBuffer)(unsafe.Pointer(&rdb.DUMMYUNIONNAME))
		s := rb.Path()
		if rb.Flags&windows.SYMLINK_FLAG_RELATIVE != 0 {
			return s, nil
		}
		return normaliseLinkPath(s)
	case windows.IO_REPARSE_TAG_MOUNT_POINT:
		return normaliseLinkPath((*windows.MountPointReparseBuffer)(unsafe.Pointer(&rdb.DUMMYUNIONNAME)).Path())
	default:
		// the path is not a symlink or junction but another type of reparse
		// point
		return "", syscall.ENOENT
	}
}
```
