### Title
Attacker can fill `feeCollector`'s 30-slot account token list via dust `DepositToken` transfers, permanently bricking fee-bearing `Pool.liquidate`, `deposit`, and `withdraw` for collateral types the collector does not yet hold — (File: contracts/DepositToken.sol)

### Summary
The referenced kernel bug crashes the suspend path because a resource needed by that path was already torn down by an earlier suspend — i.e., a required dependency is exhausted/disabled before the operation that needs it runs. The Metronome analog lives in the per-account token list bookkeeping: every `DepositToken` balance change calls back into `Pool.addToDepositTokensOfAccount`, which hard-reverts with `UserReachedMaxTokens` once an account tracks `MAX_TOKENS_PER_USER = 30` tokens. Because `DepositToken` is a freely transferable ERC20 and `Pool.liquidate` / `deposit` / `_withdraw` all route protocol fees to `feeCollector` via `_transfer`/`_mint`, an unprivileged attacker can dust-fill the `feeCollector`'s list to 30 entries, after which any fee-bearing operation involving a deposit-token type the collector doesn't already hold reverts unconditionally.

### Finding Description
`Pool.addToDepositTokensOfAccount` enforces a global cap through `onlyIfAdditionWillNotReachMaxTokens`:

```solidity
// contracts/Pool.sol:143-148
modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}
// contracts/Pool.sol:216-220
function addToDepositTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) {
    ...
}
```

`DepositToken._transfer` unconditionally registers the recipient on a zero→nonzero balance transition:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`deposit`, `withdraw`/`flashWithdraw`, and `Pool.liquidate` all deliver fees to `feeCollector`:

- `deposit`: `_mint(_pool.feeCollector(), _fee)` → `addToDepositTokensOfAccount(feeCollector)` (`DepositToken.sol:230-232`, `_mint` at 486-488)
- `liquidate`: `depositToken_.seize(account_, _poolRegistry.feeCollector(), _fee)` → `_transfer` → same registration path (`Pool.sol:591-593`)
- `withdraw`/`flashWithdraw`: `_transfer(account_, _pool.feeCollector(), _fee)` (`DepositToken.sol:546-548`)

Nothing prevents an EOA from transferring dust amounts of each listed `DepositToken` to `feeCollector` (a plain address from `PoolRegistry.feeCollector()`). Once `debtTokensOfAccount + depositTokensOfAccount` for `feeCollector` reaches 30, every subsequent operation that would register a *new* deposit-token type on `feeCollector` reverts in `UserReachedMaxTokens` — and `feeCollector` has no way to remove entries, since removal only happens on balance→0 transitions which the attacker-registered dust keeps non-zero (the attacker can also top-up after any accidental drain).

Like the kernel bug, the operation (`seize`/`_mint` fee leg, analogous to `xhci_suspend` accessing registers) crashes because a resource it needs (a free slot in the recipient's token list, analogous to the gated clock) was consumed by earlier transactions.

### Impact Explanation
- `Pool.liquidate` for any deposit-token collateral where `fee > 0` and `feeCollector` doesn't already hold that token always reverts → liquidations of that collateral are permanently disabled → underwater positions cannot be closed → protocol bad debt / insolvency.
- `deposit` for a new collateral type (fee > 0) reverts → deposits bricked.
- `withdraw`/`flashWithdraw` with `withdrawFee > 0` reverts for token types the collector doesn't hold → temporary/permanent freezing of user collateral in those tokens.
- The same griefing applies to any victim account: filling a user's list blocks their `deposit`/`issue` of new token types, preventing them from adding collateral to rescue a position (forced liquidation).

### Likelihood Explanation
Fully permissionless: the attacker needs only dust balances of the pool's listed `DepositToken`s and calls `deposit` + `transfer(feeCollector, dust)` repeatedly. No privileged role, oracle manipulation, or trusted-remote compromise is required. The constraint is that the pool must have enough distinct deposit/debt token types to reach 30 registrations — on deployments with fewer than 30 listed tokens, the attack surface is proportionally smaller (impact limited to whatever capacity exists). The `MAX_TOKENS_PER_USER` griefing vector is a known-design tradeoff, but targeting `feeCollector` converts a per-user inconvenience into protocol-wide liquidation liveness failure, which is not mitigated anywhere in the code (no exemption for `feeCollector`, no removal path).

### Recommendation
- Exempt `feeCollector` (and optionally `Treasury`/`SmartFarmingManager`) from `onlyIfAdditionWillNotReachMaxTokens`, or track system addresses' collateral separately from the user-facing account lists.
- Alternatively, make fee accrual pull-based: accrue fees in the `DepositToken`/`DebtToken` and let the fee collector claim them, so user-driven transfers can't force registrations on the collector.
- At minimum, let `seize`/`_mint` skip `addToDepositTokensOfAccount` when the recipient is `feeCollector`, since the collector's token list is not used for debt-position accounting.

### Proof of Concept
Hardhat sketch (pool with ≥1 listed deposit token `msdX` with `depositFee`/`withdrawFee`/`liquidationFees.protocolFee > 0`, and enough listed tokens to reach the cap):

```ts
// 1. Attacker fills feeCollector's token list to the cap.
const feeCollector = await poolRegistry.feeCollector();
for (const dt of depositTokens /* enough listed tokens to reach 30 */) {
  await underlying.connect(attacker).approve(dt.address, DUST);
  await dt.connect(attacker).deposit(DUST, attacker.address);   // mint dust
  await dt.connect(attacker).transfer(feeCollector, DUST);      // registers dt on feeCollector
}
// depositTokensOfAccount(feeCollector).length == 30 (plus any debt entries)

// 2. Pick a deposit token `msdY` that feeCollector does NOT yet hold.
// Any fee-bearing op touching msdY now reverts:
await expect(msdY.connect(user).deposit(amount, user.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(msdY.connect(user).withdraw(amount, user.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3. Create an underwater position backed by msdY (e.g., oracle price drop on fork),
//    then liquidation permanently reverts:
await expect(pool.connect(liq).liquidate(msAsset, victim, repayAmt, msdY.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveats: the PoC requires the pool's listed deposit tokens plus the collector's debt-token entries to be able to reach `MAX_TOKENS_PER_USER`; on deployments with very few collateral types the fill may not be achievable. The revert path itself (`_transfer` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`) is unconditional once the cap is hit, and there is no code path for `feeCollector` (or any account) to shrink the list except burning its entire balance of a token, which the attacker can prevent by re-dusting.
