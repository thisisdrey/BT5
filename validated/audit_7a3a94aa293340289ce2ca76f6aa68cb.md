### Title
Unprivileged dust deposit/transfer forces entries into a victim's `depositTokensOfAccount`, permanently griefing their future deposits - ([File: contracts/DepositToken.sol])

### Summary
The Alchemix bug is a missing check that lets an unprivileged user stamp state (`lastVoted`) onto a token they are about to hand off, blocking the receiver. The Metronome analog is stronger: `DepositToken.deposit(amount_, onBehalfOf_)` (and plain `transfer`) lets any unprivileged account add entries to *another* account's `depositTokensOfAccount` list in `Pool`, which is capped by `MAX_TOKENS_PER_USER`. An attacker can dust-fill a victim's list and block the victim from depositing into collateral types they don't already hold — a griefing/liveness break that needs no role and only dust amounts.

### Finding Description
`deposit()` accepts an arbitrary `onBehalfOf_` beneficiary and only validates it is non-zero:

```solidity
// contracts/DepositToken.sol:211-234
function deposit(
    uint256 amount_,
    address onBehalfOf_
) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
    if (amount_ == 0) revert AmountIsZero();
    if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();
    ...
    _mint(onBehalfOf_, _deposited);
```

On mint/transfer, the recipient is appended to the pool's per-account deposit-token list whenever their balance transitions from zero, with no consent or opt-in required:

```solidity
// contracts/DepositToken.sol:485-488 and 517-520
if (_balanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(account_);
}
...
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` on that list (`contracts/Pool.sol`), and both `debtPositionOf`/`depositOf` iterate this list for accounting. The attacker has two dust vectors:

1. `deposit(dust, victim)` on every active `DepositToken` — costs only dust collateral, minted msdTOKENs go to the victim.
2. `transfer(victim, 1 wei)` — even cheaper; the attacker deposits dust to themselves once, then transfers 1 wei of each deposit token to the victim, each `transfer` triggering `addToDepositTokensOfAccount(victim)`.

Once the victim's list is full (attacker front-runs their intended deposit), any subsequent victim deposit into a *new* collateral type reverts when `addToDepositTokensOfAccount` hits the cap. Like the Alchemix `reset` griefing (a seller front-runs the transfer and blocks the buyer's epoch), a seller of an OTC position or an attacker front-running a known depositor can stamp state onto the victim's account with no check that the beneficiary consented.

### Impact Explanation
Griefing / temporary-to-permanent freezing of functionality: the victim cannot deposit collateral types they don't already hold until they fully zero out a dusted position (withdrawing costs withdraw fees and requires the position to be unlocked). If the cap equals the number of registered collateral tokens, the victim is permanently blocked from any *new* collateral added to the pool later. The attacker pays only dust + gas, matching the accepted "temporary freezing of funds" / griefing impact class. No theft, but the liveness invariant "a user can always open a new deposit position" is broken by an unprivileged third party.

### Likelihood Explanation
- Fully unprivileged: `deposit` requires only `whenNotPaused` and that the deposit token exists; `transfer` requires only that the sender has unlocked balance. No governor/keeper/oracle involvement.
- Repeatable: the attacker can dust-fill up to `MAX_TOKENS_PER_USER` entries across all active deposit tokens, and can target any address including contracts that can't easily unwind positions.
- Mitigations don't help: `nonReentrant`, `SynthContext`, and health checks are irrelevant; the lock check `_revertIfLocked` gates the *sender*, and the dusted tokens land unlocked on the victim (no debt), so nothing reverts for the attacker.
- Residual note: the victim can recover by withdrawing/transferring the dusted positions (paying fees), so impact is griefing rather than permanent loss — analogous severity to the Alchemix report.

### Recommendation
Do not let arbitrary callers register tokens on someone else's accounting list, mirroring the suggested `require(poolVote[_tokenId].length > 0)` check:

- In `deposit`, restrict `onBehalfOf_` list registration: only call `addToDepositTokensOfAccount` when `onBehalfOf_ == _msgSender()`, or gate beneficiary deposits behind an opt-in/allowance, or skip list registration for dust amounts below a minimum deposit threshold.
- In `transfer`/`transferFrom`/`_transfer`, either don't register the token for the recipient (recipients can't be liquidated-sensibly without opting in anyway) or require the recipient's balance to cross a meaningful threshold before `addToDepositTokensOfAccount`.
- Alternatively make `addToDepositTokensOfAccount` idempotent-and-unbounded by tracking membership in a mapping so dusting costs the attacker more than it costs the victim.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DustGriefingTest is Test {
    IPool pool;
    DepositToken[] depositTokens; // all active deposit tokens of the pool
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    function test_DustFillBlocksVictimDeposit() public {
        // MAX_TOKENS_PER_USER slots exist; assume victim already holds k of them,
        // leaving free slots the attacker can steal.
        uint256 dust = 1; // 1 wei of underlying per token where fee allows
        for (uint256 i; i < depositTokens.length; ++i) {
            DepositToken dt = depositTokens[i];
            if (dt.balanceOf(victim) > 0) continue; // already counted

            IERC20 underlying = dt.underlying();
            deal(address(underlying), attacker, dust);
            vm.startPrank(attacker);
            underlying.approve(address(dt), dust);
            if (dt.quoteDepositOut(dust) > 0) {
                dt.deposit(dust, victim);      // vector 1: dust deposit on behalf
            } else {
                // vector 2: self-deposit then 1-wei transfer
                dt.deposit(dust + 1, attacker);
                dt.transfer(victim, 1);
            }
            vm.stopPrank();
        }

        // victim's depositTokensOfAccount list is now at MAX_TOKENS_PER_USER.
        // A new collateral type (or one victim didn't hold) can no longer be deposited.
        DepositToken newDt = _newlyAddedDepositToken(); // hypothetical new listing
        IERC20 underlying = newDt.underlying();
        uint256 amount = 100e18;
        deal(address(underlying), victim, amount);
        vm.startPrank(victim);
        underlying.approve(address(newDt), amount);
        vm.expectRevert(); // revert in Pool.addToDepositTokensOfAccount on cap
        newDt.deposit(amount, victim);
        vm.stopPrank();
    }

    function _newlyAddedDepositToken() internal returns (DepositToken) { /* new listing */ }
}
```
