### Title
Missing `transfer.bundleURI=false` hardening in `FetchRemote`/`UpdateRemoteMirror` allows bundle-URI SSRF via attacker-controlled remote - ([File: internal/gitaly/service/repository/fetch_remote.go], [File: internal/gitaly/service/remote/update_remote_mirror.go])

### Summary
`cloneFromURLCommand` explicitly disables `transfer.bundleURI` before cloning from an attacker-supplied URL, with an inline comment stating this is done "since the URI can point to any server, including localhost, this is to prevent attack vectors" [1](#0-0) . `buildCommandOpts` in `fetch_remote.go` and `updateRemoteMirror` in `update_remote_mirror.go` build git config for `git-fetch`/`git-ls-remote`/`git-push` against `RemoteParams.Url`/`Remote.Url`, which is likewise fully attacker-controlled, but neither sets `transfer.bundleURI=false` [2](#0-1) [3](#0-2) .

### Finding Description
`FetchRemote` runs `quarantineRepo.FetchRemote(ctx, "inmemory", opts)` where `opts.CommandOptions` is populated purely from `req.GetRemoteParams()` via `buildCommandOpts`, with the URL set as `remote.inmemory.url` and no `transfer.bundleURI` override [4](#0-3) . Similarly, `UpdateRemoteMirror` calls `repo.GetRemoteReferences` (`git ls-remote`/protocol negotiation) and `repo.Push` against `remoteConfig`, built solely from `Remote.GetUrl()`/`Remote.GetResolvedAddress()`, again without disabling bundle URI [5](#0-4) . In both flows the URL comes directly from the RPC request (`RemoteParams.Url` / `Remote.Url`), which an unprivileged user fully controls when they point Gitaly at a git server they operate (e.g., via a project's "Repository Mirroring" pull configuration or a manual `FetchRemote`/`UpdateRemoteMirror` call against their own project).

The repo's own `internal/bundleuri/git_config.go` comment explicitly acknowledges that "the client [may be] enabled to download bundle URIs on git-fetch(1)" referencing a GitLab-maintained Git fork issue (`gitlab-org/git#271`) [6](#0-5) , confirming that in GitLab's git build this feature is a realistic protocol-v2 negotiation path, not merely a hypothetical opt-in. Because `cloneFromURLCommand` was patched specifically to guard against this for the analogous "attacker supplies clone URL" scenario, the same threat model applies unchanged to `FetchRemote` and `UpdateRemoteMirror`, yet those code paths were left unpatched.

### Impact Explanation
If a malicious remote server (fully controlled by the attacker as the git remote that Gitaly is instructed to fetch from or mirror to) advertises a `bundle.<name>.uri` pointing at an internal address (e.g. `http://169.254.169.254/`) during protocol v2 negotiation, and the Gitaly host's git build has bundle-URI client support active, Gitaly's git-fetch/git-ls-remote invocation would automatically retrieve that internal URL as part of negotiation. This constitutes SSRF from the Gitaly node against internal/cloud-metadata endpoints, matching GitLab's SSRF bounty impact class, without requiring any additional privilege beyond configuring a repository mirror or issuing a `FetchRemote`/`UpdateRemoteMirror` call with an attacker-controlled URL.

### Likelihood Explanation
Preconditions: (1) the attacker operates the remote git server referenced by `RemoteParams.Url`/`Remote.Url` (fully achievable by an unprivileged user configuring a pull/push mirror to their own server), and (2) the Gitaly host's git binary has bundle-URI client fetch support enabled/negotiated (the codebase's own defensive fix and internal comments indicate this is a real concern in GitLab's environment, not purely theoretical, though I could not confirm from this index whether the default upstream git build shipped with Gitaly negotiates bundle-uri without additional config — this remains an assumption inherited directly from the already-accepted `create_repository_from_url.go` fix). Given the fix was already applied to one of three structurally identical URL-fetch code paths, the omission is a straightforward, reproducible gap in the other two, callable directly and repeatably via `FetchRemote`/`UpdateRemoteMirror` RPCs.

### Recommendation
Apply the same defensive `transfer.bundleURI=false` global git config to both:
- `buildCommandOpts` in `internal/gitaly/service/repository/fetch_remote.go`, added to `opts.CommandOptions`.
- `remoteConfig` construction in `internal/gitaly/service/remote/update_remote_mirror.go`, applied to both `GetRemoteReferences` and `Push` calls.

Ideally, centralize this hardening (e.g., a shared helper `gitcmd.DisableBundleURI()` config pair) applied to every git invocation that takes a fully attacker-supplied remote URL, rather than patching each call site ad hoc.

```go
// Pseudocode PoC (Go test) illustrating the missing protection, analogous to how
// create_repository_from_url_test.go would test cloneFromURLCommand's bundleURI flag.

func TestFetchRemote_DoesNotDisableBundleURI(t *testing.T) {
    // Start a malicious git server (e.g., using go-git or a custom smart-HTTP handler)
    // that, during upload-pack negotiation, advertises:
    //   bundle-uri
    // and on a GET to the bundle-uri endpoint, responds with a bundle list containing:
    //   [bundle]
    //     bundle.internal.uri = http://169.254.169.254/latest/meta-data/
    maliciousServerURL := startMaliciousBundleURIServer(t)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: attackerRepo,
        RemoteParams: &gitalypb.Remote{
            Url: maliciousServerURL,
        },
    })
    require.NoError(t, err)

    // Assert: inspect the malicious server's request log and expect NO request
    // was ever made to 169.254.169.254 (or the malicious server's designated
    // "internal" bundle endpoint). Without the transfer.bundleURI=false guard,
    // if the git client honors bundle-uri, such a request would occur.
    require.False(t, maliciousServer.ReceivedBundleFetchRequest())
}
```
Note: exact reproduction depends on the specific git client build's bundle-uri negotiation behavior on the Gitaly host, which I could not directly verify from the indexed source alone (this is a git binary runtime behavior, not something enforced purely in Go code, so full confirmation would require running the built binary against a crafted malicious remote).

```go
func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
}
```
