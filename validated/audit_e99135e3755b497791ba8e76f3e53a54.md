### Title
StackerDB inventory reply advertises a chunk version before it is actually committed to storage - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` patches the outgoing `StackerDBChunkInv` reply to claim the newly-pushed slot version is now present *before* the chunk is actually written to the StackerDB. The actual storage happens later and separately, in the relayer (`Relayer::process_uploaded_stackerdb_chunks` / `Relayer::process_stacker_db_chunks`), which can still reject the chunk (e.g. `StaleChunk`, signer mismatch, DB error). This breaks the equality between "advertised/committed inventory" and "actually stored data," similar in class to the Forta bug where a counter (`totalRewardsDistributed`) was updated optimistically without verifying the underlying state change was valid/unique.

### Finding Description
When an unsolicited `StackerDBPushChunk` arrives, `handle_unsolicited_StackerDBPushChunk` validates the chunk with `validate_received_chunk` (signature, size, staleness, max-writes checks against the *locally cached* `slot_versions`), and then immediately mutates the in-memory inventory copy to reflect acceptance: [1](#0-0) 

This patched inventory is sent straight back to the peer as a signed reply, without waiting for the relayer to actually persist the chunk: [2](#0-1) 

The function's own contract documents that returning `(false, true)` means "forward the message to the relayer, so it can be processed" — i.e., actual storage is deferred: [3](#0-2) 

Actual persistence happens later via the relayer path, which re-validates against the authoritative on-disk state and can still fail (e.g., `StaleChunk` if two versions race, or another `try_replace_chunk` error): [4](#0-3) [5](#0-4) 

Because the `StackerDBChunkInv` sent to the peer at lines 862–870 is built from the *pre-storage* patched vector, and the relayer's `try_replace_chunk` performs a second, independent, authoritative check against the database (`slot_validation.version`), there is a window in which the node tells a remote peer "I now have slot X at version V," while the relayer subsequently fails to store that exact chunk (e.g., a second push for the same slot with a different but valid signature/version arrives first and wins the race, or a transient DB error occurs). The node has now advertised chunk data it does not actually hold — a "served/advertised vs. committed" mismatch.

### Impact Explanation
Any node that receives this optimistic `StackerDBChunkInv` will treat the remote node as authoritative for that slot/version and may attempt to fetch it via `StackerDBGetChunk`. If storage failed, the advertising node cannot supply the promised chunk, causing:
- Wasted round trips and stalled StackerDB sync state machines for honest peers relying on the inventory to prioritize downloads (as described in the crate's own sync design docs).
- Potential propagation of stale/incorrect state, since peers that trust this inventory to decide "rarest-first" download scheduling will make decisions based on non-existent data.

This falls under "High – serving non-canonical state as canonical / steering a node off the correct view via false inventory," since the mismatch is remotely triggerable by any single connected, authenticated (but otherwise unprivileged) peer simply racing two pushes to the same slot, and it affects the view that other honest peers build of this node's StackerDB inventory.

### Likelihood Explanation
The precondition (two competing pushes to the same slot racing between the optimistic inventory patch and the relayer's actual commit) requires no special privilege — any peer capable of pushing `StackerDBPushChunk` messages (which is the normal, unauthenticated write path for StackerDB replicas) can trigger it, e.g., by pushing a chunk, then immediately pushing another one for the same slot from a colluding connection or another signer key, before the relayer commits the first. The comment in the code ("Note that this can happen *during* a StackerDB sync's execution") acknowledges this is a live concurrent path, increasing the plausibility of a genuine race rather than a purely theoretical one.

### Recommendation
Do not patch and send the `StackerDBChunkInv` reply optimistically before the chunk is actually and successfully written to the StackerDB. Either:
1. Defer sending the inventory reply until after the relayer has confirmed the chunk was actually stored (`try_replace_chunk` succeeded), or
2. Re-query the authoritative on-disk slot version (via `get_slot_versions`/`get_slot_metadata`) immediately before constructing/sending the reply, instead of relying on the in-memory patched copy.

### Proof of Concept
1. Node `A` is a StackerDB replica peer connected to node `B`.
2. Attacker controls two valid signer keys `K1` (slot 0, version 1, already stored) and a second push arrives from a colluding/legit second connection targeting the same slot with version 2, signed correctly.
3. `B` sends `StackerDBPushChunk(slot=0, version=2)` to `A`. `A`'s `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which passes (version 2 > cached version 1), patches its local `slot_versions[0] = 2`, and immediately replies to `B` with `StackerDBChunkInv` advertising version 2 for slot 0 (`stackslib/src/net/stackerdb/mod.rs:794-807, 862-870`).
4. Concurrently, an attacker races another `StackerDBPushChunk(slot=0, version=2)` with a *different, also-valid signature* for the same slot from an independent connection into the relayer before the first one's `try_replace_chunk` runs; the relayer's `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) rejects the original as `StaleChunk` because the competing chunk already wrote version 2.
5. `A` has already told `B` (and will tell other neighbors it later gossips its inventory to) that it holds slot 0 version 2 from the first push, but the data actually stored (if any) came from the second, different chunk contents — or in error paths, storage may fail outright, leaving `A` claiming a version it never actually persisted for that specific chunk payload.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
