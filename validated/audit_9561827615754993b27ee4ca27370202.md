### Title
Argument/URL injection into the `git` CLI via unsanitized `remote` value enables command execution through Git's `ext::` transport helper - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` (and the equivalent Bzlmod `git_repository`-type `source.json` entries served by module registries) pass the attacker/registry-controlled `remote` string directly, unsanitized, as a positional argument to the `git` binary via `ProcessBuilder`-style list execution. Because Git treats certain URL forms (in particular the `ext::<command>` and `fd::` transport helpers) as instructions to run an arbitrary local command rather than as a network address, and because Bazel neither validates/allow-lists the URL scheme nor sets `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow=never` in the subprocess environment, a hostile module registry (or `--registry` mirror) can supply a `remote` value that causes the `git` subprocess spawned by Bazel to execute an arbitrary command on the machine running `bazel fetch`/`bazel build`.

### Finding Description
`git_repo()` in [1](#0-0)  builds a `_GitRepoInfo` struct whose `remote` field is taken verbatim from `ctx.attr.remote` (a plain `attr.string`, with no scheme validation). This value is then handed to: [2](#0-1) 

specifically `add_origin(ctx, git_repo, remote)` which calls `_git(ctx, git_repo, "remote", "add", "origin", remote)`. `_git` ultimately calls `_execute`, which builds argv as a list (`["git", "-c", "core.fsmonitor=false"] + args`) and passes it to `ctx.execute(...)`: [3](#0-2) 

No shell is invoked (list-based execution, same as the Camel `ProcessBuilder` case), so classic shell metacharacter injection is not possible — but this is exactly the same weakness class as CVE-2026-40047: an attacker-controlled string is appended to an external tool's *own* argument-parsing surface without validating what the tool itself may do with a value that looks like a flag or a special-purpose URL scheme.

Git supports remote-helper transports invoked as `<scheme>::<command>`, most notably `ext::<shell-command>`, which spawns the given command in place of a network transport. Since `protocol.ext.allow` defaults to `user` for directly-invoked Git commands (only submodule/alternates recursion defaults to deny), a `remote` value such as:
```
ext::sh -c "touch /tmp/pwned; sh 0<&2 1>&2" ext
```
passed to `git remote add origin <remote>` followed by `git fetch origin` (see `fetch()`/`_git_maybe_shallow()` in the same file) causes the locally-invoked `git` process to execute the embedded command, i.e., arbitrary command execution on the machine building the target.

The `_GIT_LOCAL_ENV_VARS` map passed via `environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS` in `_execute` only unsets a fixed list of `GIT_*` internal state variables (`GIT_DIR`, `GIT_CONFIG`, etc.) — [4](#0-3)  — it does **not** set `GIT_ALLOW_PROTOCOL` to an allow-list (e.g. `http:https:git`) nor pass `-c protocol.ext.allow=never`/`-c protocol.file.allow=never` to block the dangerous transports. There is also no validation of `remote`'s scheme anywhere in `git.bzl`/`git_worker.bzl` before it reaches the subprocess argument list.

Crucially, the `remote` attribute is not just settable in a trusted root `MODULE.bazel`/`BUILD` file: a Bzlmod module can be resolved via a `git_repository`-type `source.json` served by any configured `--registry` (including third-party/mirror registries), where the `remote` field is one of the documented fetch parameters: [5](#0-4) 

Unlike the `archive` source type, which is protected by a mandatory `integrity`/`sha256` checksum, the `git_repository` source type has **no** corresponding hash pinning for the `remote` string itself (or for the fetched Git history in general) — the lockfile only records hashes of the registry response files themselves for reproducibility on subsequent runs, and provides no protection on first fetch or when `--lockfile_mode=off`/first population. This is the same "declared checksum should stop it but there isn't one for this field" pattern central to the analog.

### Impact Explanation
An unprivileged attacker who controls (or can get a project to point at) a module registry — e.g., a malicious/compromised third-party `--registry` mirror, or a fork registry referenced in `.bazelrc` — can serve a `source.json` of `type: "git_repository"` whose `remote` field is an `ext::`-style command string. When a victim runs `bazel build`/`bazel fetch` against that module, Bazel's repository-rule machinery will spawn `git remote add origin <remote>` and `git fetch origin ...` with that string as a literal `git` CLI argument, resulting in execution of attacker-chosen commands on the developer's or CI's build machine — full compromise of the build host, not merely a denial of service. This satisfies "write or read outside the repository/exec root/output base" and effectively "credential exfiltration"/arbitrary code execution impact bars required by the rules.

### Likelihood Explanation
Likelihood is limited by the precondition that the project's Bazel configuration references a non-BCR (`--registry`) source that is malicious or compromised, or that BCR itself is compromised/MITM'd for that module — a realistic supply-chain scenario explicitly permitted by the rules ("hostile origin server, mirror or registry"). No special privileges, credentials, or pre-existing local access are required beyond publishing/serving the registry content that the victim's `bazel fetch` consumes, matching the "unprivileged attacker who publishes or serves content a victim's build consumes" threat model.

### Recommendation
- Validate the `remote` attribute (and any registry-supplied `remote` field) against an allow-list of safe schemes (`http://`, `https://`, `git://`, `ssh://`, `file://` with containment checks) before use, rejecting `ext::`, `fd::`, and other transport-helper forms.
- Explicitly set `GIT_ALLOW_PROTOCOL` (or pass `-c protocol.ext.allow=never -c protocol.fd.allow=never`) in the environment/args used by `_execute` in `git_worker.bzl` for every invocation of `git`, regardless of what the resolved value of `remote` is.
- Require the same integrity-pinning discipline for `git_repository`-typed registry entries as for `archive` entries (e.g., pin the resolved commit and validate `remote`'s scheme at registry-ingestion time), and reject registry-supplied `remote`/`commit`/`branch`/`tag` values that resemble CLI flags (leading `-`) or embedded transport-helper syntax.

### Proof of Concept
1. Stand up a hostile index registry (or a malicious mirror listed via `--registry`) serving, for some module `m@1.0`, a `source.json` such as:
```json
{
  "type": "git_repository",
  "remote": "ext::sh -c \"touch /tmp/PWNED\"",
  "commit": "0000000000000000000000000000000000000000"
}
```
2. In a victim workspace, add `bazel_dep(name = "m", version = "1.0")` and configure `--registry=<hostile-registry-url>`.
3. Run `bazel fetch @m//...` (or any build that requires resolving `@m`).
4. Bazel's `git_repo()`/`_update()` path executes `git remote add origin ext::sh -c "touch /tmp/PWNED"` followed by `git fetch origin ...` as literal subprocess arguments (`tools/build_defs/repo/git_worker.bzl`), and `/tmp/PWNED` is created — demonstrating arbitrary command execution on the build host driven purely by registry-served content.

A `BuildIntegrationTestCase`/`src/test/shell/bazel` reproduction would set up a local static-file registry (as done in `src/test/py/bazel/bzlmod/bzlmod_credentials_test.py`) serving a `git_repository`-type `source.json` with an `ext::`-style `remote`, then assert that a sentinel file is created after `bazel fetch`, confirming command execution outside of any sandbox/exec-root boundary.

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )
