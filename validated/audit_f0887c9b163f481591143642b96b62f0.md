### Title
New account initialized with `INITIAL_INDEX` baseline gap grants instant unearned rewards - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` only corrects a missing `accountIndexOf` to `INITIAL_INDEX` when the global `_tokenIndex` is strictly greater than `INITIAL_INDEX`. When an account holds a `DepositToken`/`DebtToken` balance while its stored `accountIndexOf` is `0` and the global index is still exactly `INITIAL_INDEX`, the delta is computed as `balance.wadMul(INITIAL_INDEX)` — i.e. the account instantly accrues reward tokens equal to its full tracked balance with zero elapsed accrual time. An account can hold a balance with `accountIndexOf == 0` because `updateBeforeMintOrBurn`/`updateBeforeTransfer` skip all state writes while `tokenStates[token_].index == 0` (i.e. before any reward speed is set for that token).

### Finding Description
In `contracts/RewardsDistributor.sol:217-231`:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The `> INITIAL_INDEX` comparison is the initialization bug, analogous to the tick `rewardGrowthOutside` initialization flaw in the reference report: a position/account can be "initialized" with a non-zero accrual baseline mismatch.

The window arises from the guard in `updateBeforeMintOrBurn` (line 175-180) and `updateBeforeTransfer` (line 186-192): if `tokenStates[token_].index == 0`, neither the account index nor accrued tokens are touched. So:

1. Attacker deposits collateral into a `DepositToken` before any reward speed exists for it (or while its index slot is still `0`). They hold balance `B` with `accountIndexOf == 0`.
2. Governor later calls `updateTokenSpeed(token, speed)` (or the tokenSpeedKeeper calls `syncTokenSpeed`), which sets `tokenStates[token] = {index: INITIAL_INDEX, timestamp: now}` (`_updateTokenSpeed`, lines 294-299).
3. In the **same block**, `_calculateTokenIndex` produces `_newIndex == INITIAL_INDEX` (`_deltaTimestamps == 0`, or `totalSupply` rounding keeps index at `INITIAL_INDEX`). The attacker back-runs the governance/keeper transaction with `rewardsDistributor.updateBeforeMintOrBurn(token, attacker)` — a permissionless function ("This function also may be called by anyone to update stored indexes", line 173).
4. `_calculateTokenDelta` sees `_accountIndex == 0` but `_tokenIndex == INITIAL_INDEX` (not `>`), so `_accountIndex` stays `0`, `_deltaIndex = 1e18`, and `_tokensDelta = B * 1e18 / 1e18 = B` reward tokens are credited to `tokensAccruedOf[attacker]`.
5. The attacker then calls `claimRewards(attacker, tokens)` and `_transferRewardIfEnoughTokens` (lines 248-256) pays out `B` of `rewardToken`, bounded only by the distributor's reward token balance.

After this write, `accountIndexOf[attacker] = INITIAL_INDEX`, so the exploit is once per account per token per zero-index window, but it can be repeated across tokens and across fresh attacker addresses that pre-positioned balances.

### Impact Explanation
Direct theft of unclaimed yield / reward reserves. A whale-sized balance `B` translates into `B` units of `rewardToken` (e.g. MET) minted as claimable rewards with zero accrual time. `_transferRewardIfEnoughTokens` pays up to the distributor's full `rewardToken` balance, draining rewards owed to legitimate depositors and borrowers.

### Likelihood Explanation
Requirements: (a) the attacker holds a tokenized position before rewards are enabled for that token — trivially achievable, positions commonly exist before reward gauges are added; (b) the attacker's update lands in the same block as (or in a block where the index is still `INITIAL_INDEX`, e.g. while `totalSupply == 0` kept `ratio == 0`) the `updateTokenSpeed`/`syncTokenSpeed` transaction — achievable via public-mempool back-running. No privileged role, malicious oracle, or third-party manipulation is needed; the governor/keeper transaction is benign.

### Recommendation
Initialize the account index unconditionally when `accountIndexOf[token][account] == 0`, to the current global index (or to `INITIAL_INDEX` whenever `_tokenIndex >= INITIAL_INDEX`), matching how Uniswap V4 now initializes below-current tick growth-outside to the global accumulator:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
    // i.e. baseline == current index -> zero delta for never-indexed accounts
}
```

Equivalently, change the condition to `_tokenIndex >= INITIAL_INDEX` and set `_accountIndex = _tokenIndex` (not `INITIAL_INDEX`), so a zero-index account always starts at the current index with `_tokensDelta == 0`.

### Proof of Concept
Hardhat/Foundry fork sketch against deployed mainnet `RewardsDistributor` + a `DepositToken` with no speed set:

```solidity
// Setup (forked state)
IDepositToken msd = IDepositToken(MSD_TOKEN);           // rewards speed == 0, tokenStates.index == 0
RewardsDistributor rd = RewardsDistributor(RD);
IERC20 underlying = msd.underlying();

// 1. Attacker acquires position while index == 0 (hook no-ops, accountIndexOf stays 0)
deal(address(underlying), attacker, 1_000e18);
vm.startPrank(attacker);
underlying.approve(address(msd), type(uint256).max);
msd.deposit(1_000e18, attacker);
assertEq(rd.accountIndexOf(msd, attacker), 0);
assertEq(msd.balanceOf(attacker) > 0, true);
vm.stopPrank();

// 2. Same block: governor enables rewards, attacker back-runs
vm.prank(governor);
rd.updateTokenSpeed(IERC20(address(msd)), 1e18);        // index = INITIAL_INDEX (1e18), ts = now

vm.prank(attacker);
rd.updateBeforeMintOrBurn(IERC20(address(msd)), attacker); // permissionless

// 3. Bug: tokensAccruedOf == balance * INITIAL_INDEX
assertEq(rd.tokensAccruedOf(attacker), msd.balanceOf(attacker));

// 4. Drain rewardToken
vm.prank(attacker);
rd.claimRewards(attacker, toTokens(msd));
assertGt(rewardToken.balanceOf(attacker), 0);
```

Expected on current code: `tokensAccruedOf[attacker] == balanceOf(attacker)` immediately after speed activation, with zero elapsed accrual.
