Audit Report

## Title
Reward-per-token accumulator rounds down to zero for pools with large `total_tokens_staked`, permanently freezing staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` function computes an incremental reward-per-token delta using a fixed-point multiplier `PRECISION_SCALING_FACTOR = 4096` [1](#0-0) . Because integer division via `ensure_div` silently truncates rather than erroring, whenever `pool_info.total_tokens_staked` grows large relative to `reward_rate_per_block * blocks_elapsed * 4096`, the delta computed in `reward_per_token` truncates to zero every update, permanently halting reward accrual for all stakers in the pool [2](#0-1) .

## Finding Description
`reward_per_token` computes `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked` and adds it to the stored accumulator [3](#0-2) . `EnsureDiv::ensure_div` only errors on division by zero or overflow — ordinary truncation to zero passes silently. `total_tokens_staked` is incremented without any upper bound in the public `stake` extrinsic [4](#0-3) , and pool creation itself is gated only by `T::CreatePoolOrigin::ensure_origin(origin)?` inside the public `create_pool` extrinsic [5](#0-4) . In shipped runtime configurations, `CreatePoolOrigin` is set to `EnsureSigned<AccountId>`, making pool creation permissionless for any signed account, confirmed in both `asset-hub-rococo`'s `pallet_asset_rewards::Config` [6](#0-5)  and the reference `node/runtime` [7](#0-6) . Any unprivileged staker can then call `stake` with a large amount of a high-decimal fungible asset, driving `total_tokens_staked` up until the numerator no longer exceeds it, permanently zeroing the per-block delta for every future update regardless of actual reward funding in `pool_info.account`.

## Impact Explanation
This breaks the value-conservation invariant that stakers accrue rewards proportional to their stake and duration. Once `total_tokens_staked` outpaces `reward_rate_per_block * PRECISION_SCALING_FACTOR`, `derive_rewards` — which multiplies by the same accumulator delta and divides again by `PRECISION_SCALING_FACTOR` [8](#0-7)  — yields zero new rewards for all stakers, permanently locking reward-asset funds held in the pool's dedicated account and unclaimable by any legitimate staker, matching the "permanent user-fund... lock" impact category.

## Likelihood Explanation
No privileged actor, governance, or compromised infrastructure is required. Any signed account can permissionlessly create a pool via `create_pool` (`EnsureSigned<AccountId>` in shipped runtimes) and any signed account can call the public `stake` extrinsic with an arbitrary amount of a listed asset. Using an 18-decimal asset staked in large ordinary quantities easily drives `total_tokens_staked` past the truncation threshold given `PRECISION_SCALING_FACTOR` is only `4096`, making this reachable through normal token economics rather than requiring adversarial resources.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point base (e.g., matching `FixedU128`-style 1e18 scaling used elsewhere in the codebase, such as nomination-pools), and/or perform the reward-per-token computation in a wider intermediate type (e.g., `U256`) before dividing, mirroring `point_to_balance` in `substrate/frame/nomination-pools/src/lib.rs`. Consider also bounding `total_tokens_staked` relative to `reward_rate_per_block` or surfacing a defensive event when a non-zero elapsed reward budget produces a zero delta.

## Proof of Concept
1. Call `create_pool` with an 18-decimal `staked_asset_id`, `reward_rate_per_block = 1_000_000_000_000` (1e12), and any `reward_asset_id`.
2. Staker A calls `stake(pool_id, 1_000_000 * 10^18)`, making `total_tokens_staked = 1e24` (via `substrate/frame/asset-rewards/src/lib.rs:469-497`).
3. After 14,400 blocks, `reward_per_token` computes `numerator = 1e12 * 14_400 * 4096 ≈ 5.9e19`, and `5.9e19 / 1e24 = 0` due to integer truncation (`substrate/frame/asset-rewards/src/lib.rs:803-809`).
4. Staker A's harvest/claim path calls `derive_rewards`, which returns 0 new rewards despite the pool having accrued reward tokens in `pool_info.account`.
5. Reward tokens remain permanently stuck and unclaimable as long as `total_tokens_staked` stays large relative to `reward_rate_per_block`.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
