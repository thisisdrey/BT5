### Title
Access-key nonce is not upper-bounded in non-strict nonce mode, allowing replay of an already-executed transaction after DeleteKey+AddKey re-creation of the same public key - (File: `runtime/runtime/src/access_keys.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
`initial_nonce_value(block_height)` reseeds a re-added access key's nonce to `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0)  assuming that no previously-admitted transaction for that public key ever used a nonce that high. In the non-strict nonce path the verifier only checks `tx.nonce > ak.nonce` with no upper bound on the nonce a signer may choose, so an attacker can pick an arbitrarily large `u64` nonce (far beyond any realistic `block_height * 1_000_000`) for a normal signed transaction, have it executed, delete the key, immediately re-add it, and then replay the exact same already-executed transaction because the freshly re-seeded nonce is still smaller than the huge nonce used before.

### Finding Description
`add_regular_key` sets the nonce of a newly (re-)created access key to `initial_nonce_value(block_height)` [2](#0-1) , and the accompanying comment explicitly states the purpose is "to avoid transaction hash collision on access key re-creation," referencing near/nearcore#3779 [3](#0-2) . This scheme implicitly relies on the assumption that no nonce ever admitted for the deleted key exceeded `(new_block_height - 1) * 1_000_000`.

However, the (non-strict) nonce check performed during transaction verification only requires the submitted nonce to be strictly greater than the access key's current stored nonce; no maximum/ceiling check on the nonce value itself was found in `runtime/runtime/src/verifier.rs`. `delete_regular_key`/`action_delete_key` removes the access-key row entirely from the trie [4](#0-3) , discarding the last-admitted nonce. When the same public key is re-added, `add_regular_key` creates a brand new `AccessKey` whose nonce depends only on the current block height, with no memory of the nonce that was in effect right before deletion.

Exploit flow (attacker only needs a funded account and the ability to sign/submit transactions):
1. Attacker signs and submits `Tx1` from account A using access key P, setting `Tx1.nonce = N` for an arbitrarily large `N` (e.g., close to `u64::MAX`), well above what the block-height-derived heuristic assumes. `Tx1` performs a real effect (e.g., a `Transfer` action). Since only `N > ak.nonce_old` is checked, this succeeds, and the access key's on-chain nonce becomes `N`.
2. Attacker issues `DeleteKey(P)` for account A.
3. Attacker issues `AddKey(P, ...)` for account A shortly after (small block-height gap), causing `add_regular_key` to reseed `ak.nonce = initial_nonce_value(H_readd) = (H_readd - 1) * 1_000_000`, which is vastly smaller than `N` for any realistic `H_readd`.
4. Attacker resubmits the identical, previously-executed `Tx1` (same signature/hash). The verifier again only checks `Tx1.nonce (N) > ak.nonce ((H_readd-1)*1_000_000)`, which passes, so `Tx1` executes a second time.

This breaks the intended replay-protection guarantee of nonces: an already-applied transaction can be re-applied by an attacker who fully controls their own key lifecycle, because the reseed heuristic in `initial_nonce_value` is not actually enforced as an invariant anywhere—there is no protocol-level cap tying a signer's usable nonce range to the current block height.

### Impact Explanation
This is a replay/double-spend of the attacker's own previously-executed transaction. Depending on the replayed action, this can cause a double transfer, a double contract call with side effects (e.g., double withdrawal from a bridge/vault contract that trusted "one execution per signed nonce"), or repeated invocation of any privileged action tied to that key, corresponding to the "double-spend/replay" bounty category.

### Likelihood Explanation
Preconditions are minimal and fully within an ordinary attacker's control: own a full-access key, sign one transaction with a very large nonce, then perform `DeleteKey` + `AddKey` for the same public key at a later, nearby block height. All actions are self-directed (delete/re-add own key), cost only standard gas/storage fees, and are trivially repeatable. The main uncertainty is whether `StrictNonce` (which requires `tx.nonce == ak.nonce + 1` exactly, seen in `verifier.rs` tests `test_strict_nonce_exact_next_nonce_succeeds`/`test_strict_nonce_gap_rejected` [5](#0-4) ) is universally enforced for all transaction formats on the current mainnet protocol version; if legacy/non-strict nonce validation remains reachable for any transaction shape, the attack is exploitable exactly as described.

### Recommendation
Do not rely solely on a block-height-derived heuristic for the reseeded nonce. Either (a) persist a tombstone of the highest nonce ever observed for a given `(account_id, public_key)` pair across deletion, and use `max(initial_nonce_value(block_height), last_seen_nonce + 1)` when re-adding the key, or (b) make `StrictNonce` (exact successor) mandatory for all transaction paths so an attacker can never set an arbitrarily large nonce in the first place, removing the underlying assumption gap.

### Proof of Concept
Unit/integration test in `runtime/runtime/src/tests/apply.rs` (or a `test-loop-tests` integration test):
1. Create account A with full-access key P at some low block height.
2. Submit `Tx1` from A using P with `nonce = u64::MAX - 10` and a `Transfer` action; assert it succeeds and `get_access_key(...).nonce == u64::MAX - 10`.
3. Apply `DeleteKey(P)` for A; assert the access key row is gone.
4. Apply `AddKey(P, AccessKey::full_access())` for A at `block_height = H_delete + 1`; assert `get_access_key(...).nonce == initial_nonce_value(H_delete + 1)`, which is `« u64::MAX - 10`.
5. Resubmit the identical `Tx1` bytes/signature; assert it is accepted (`tx.nonce > ak.nonce` holds) and executed a second time, and that the recipient balance reflects two transfers instead of one — demonstrating the invariant `max(admitted nonce before deletion) < initial_nonce_value(block_height_at_readd)` fails and the replayed transaction re-executes.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

pub(crate) fn action_delete_key(
    config: &RuntimeConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_key: &DeleteKeyAction,
) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {
        if let Some(gas_key_info) = access_key.gas_key_info() {
            delete_gas_key(
                config,
                state_update,
                account,
                result,
                account_id,
                &delete_key.public_key,
                &access_key,
                gas_key_info,
            )?;
        } else {
            delete_regular_key(
                &config.fees,
                state_update,
                account,
                account_id,
                &delete_key.public_key,
                &access_key,
            );
        }
    } else {
        result.result = Err(ActionErrorKind::DeleteKeyDoesNotExist {
            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),
        }
        .into());
    }
    Ok(())
}
