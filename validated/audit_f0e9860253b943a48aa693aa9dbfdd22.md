### Title
`RepositoryImpl::calculateGlobalEnergyLimit` divides by `totalEnergyWeight` with only a no-op `assert`, allowing an unguarded divide-by-zero to abort TVM execution - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
The external report shows an admin-controlled fee parameter (`feePerByte`) that, once set to zero, is used as an unguarded divisor/multiplier in a hot path (`getFee`/`sendMessage`), causing the function to revert on every call — a permanent DoS of a core operation. The closest reachable analog in java-tron is `RepositoryImpl.calculateGlobalEnergyLimit`, which divides by `totalEnergyWeight` after only a Java `assert` (a no-op unless `-ea` is enabled in production), unlike the equivalent, properly-guarded implementations elsewhere in the codebase.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's global energy limit by dividing by the dynamic property `totalEnergyWeight`: [1](#0-0) 

Note that it only guards against zero via `assert totalEnergyWeight > 0;`, which is compiled out / disabled unless the JVM is started with `-ea`. In java-tron's production packaging, assertions are not enabled by default, so this check performs no runtime action. If `totalEnergyWeight` is `0`, the harden path (`BigInteger.divide`) throws `ArithmeticException: BigInteger divide by zero`, and the non-hardened path performs a floating point division by zero.

This is inconsistent with the two parallel implementations of the same computation in the codebase, which explicitly guard against a zero divisor and return `0` instead of dividing: [2](#0-1) [3](#0-2) 

`RepositoryImpl.calculateGlobalEnergyLimit` is reachable from `VMActuator`, which is invoked on every smart-contract-triggering transaction (`TriggerSmartContract`/`CreateSmartContract`) through the resource/energy accounting path used during `call()`: [4](#0-3) 

`totalEnergyWeight` is a dynamic property tracking the network-wide sum of frozen balances for energy; it is not directly settable by governance but is derived from aggregate freeze/unfreeze/delegate state. Because `RepositoryImpl`'s copy of this calculation omits the `allowNewReward()`-based zero-guard present in `EnergyProcessor`/`BandwidthProcessor`, any code path that reaches this particular implementation with `totalEnergyWeight == 0` (e.g., very early chain state, or after all energy freezes are withdrawn/undelegated in a network with few participants) throws an unguarded `ArithmeticException` instead of returning `0` as the sibling implementations do.

### Impact Explanation
An unhandled `ArithmeticException` thrown deep inside TVM/energy-accounting logic during transaction execution can cause the transaction-processing path to fail unexpectedly for any/every account attempting to invoke a smart contract while `totalEnergyWeight` is zero, effectively preventing normal contract calls from being processed — a denial-of-service on TVM execution, directly analogous to the reported `sendMessage` always-revert DoS. Depending on where the exception propagates, it can also destabilize the node's transaction-processing/`Manager` block-application flow rather than merely failing the individual transaction.

### Likelihood Explanation
This requires `totalEnergyWeight` to reach `0` while `hardenResourceCalculation()` is enabled and an account is calling into this code path with `frozeBalance >= TRX_PRECISION` (which requires the specific caller to have a nonzero frozen-for-energy balance while the network aggregate is nonetheless zero — an inconsistency that should not occur under normal correct bookkeeping, but the guard's absence here, contrasted with the presence of the guard in the two sibling implementations, indicates it is not treated as impossible by the rest of the codebase). This is a genuine code-inconsistency/defense-in-depth gap rather than a proven, easily-triggerable state in mainnet-like conditions, so likelihood is best characterized as Medium.

### Recommendation
Align `RepositoryImpl.calculateGlobalEnergyLimit` with `EnergyProcessor.calculateGlobalEnergyLimit`/`BandwidthProcessor.calculateGlobalNetLimit`: replace the no-op `assert totalEnergyWeight > 0;` with an explicit runtime check that returns `0` (or otherwise safely short-circuits) when `totalEnergyWeight <= 0`, before performing either the `BigInteger` division or the double division.

### Proof of Concept
Not independently reproduced against a live node in this analysis; the vulnerability is inferred from static comparison of `RepositoryImpl.calculateGlobalEnergyLimit` [1](#0-0)  against the guarded sibling implementations [2](#0-1) , and confirmed to be reachable from the transaction-processing path via `VMActuator` [5](#0-4) . Whether `totalEnergyWeight` can realistically reach `0` while a specific account retains `frozeBalance >= TRX_PRECISION` under the current freeze/unfreeze/delegate bookkeeping was not fully verified within the available tool budget; existing unit tests (`CalculateGlobalLimitHardenTest`, `RepositoryImplHardenTest`) test overflow behavior of this method but do not appear to test the zero-`totalEnergyWeight` case, which is an area worth confirming with a Devin session that can run the test suite and trace freeze/unfreeze accounting end-to-end.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
