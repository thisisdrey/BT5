### Title
StorageDeposit intent permanently burns owner's wNEAR when the external NEP-145 call fails - (File: contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs)

### Summary
The `StorageDeposit` intent is explicitly documented as non-refundable, and the implementation contains no resolver/callback that credits the owner back if the downstream `storage_deposit` cross-contract call to `contract_id` fails. Since the risk is disclosed in-code and the intent is opt-in per signed payload, this is a known/accepted design tradeoff rather than a violated authorization or accounting binding.

### Finding Description
`Contract::storage_deposit` (`contracts/defuse/src/contract/intents/state.rs:265-297`) subtracts `amount` of wNEAR from `owner_id` via `self.withdraw(...)`, then unwraps wNEAR to native NEAR via `ext_wnear::near_withdraw`, chained with `.then(do_storage_deposit(storage_deposit))`, and the whole promise chain is `.detach()`'d at line 294. `do_storage_deposit` (`contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs:14-26`) is `#[private]` and simply forwards the unwrapped NEAR to `ext_storage_management::storage_deposit(contract_id, ...)` — it returns a bare `Promise` with no further `.then(resolve)` attached, unlike the analogous `ft_withdraw` path which chains `ft_resolve_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:98-104, 156-195`) that refunds any unsettled amount back to `sender_id`.

This is deliberate, not an oversight: the doc comment on the `StorageDeposit` intent explicitly states:
```
/// NOTE: the `wNEAR` will not be refunded in any case.
/// WARNING: use this intent only if paying storage deposit is not a prerequisite
/// for other intents to succeed. ...
``` [1](#0-0) 

So the binding "wNEAR debited from owner_id == NEAR delivered as successful storage_deposit at contract_id" is documented as intentionally NOT guaranteed by this intent — the signer is the one choosing to invoke it, with full disclosure of the non-refund behavior, targeting a `contract_id` and `amount` and `deposit_for_account_id` that they themselves supply and sign.

### Impact Explanation
While funds can indeed be lost if `contract_id`'s `storage_deposit` call fails, the owner is the signer of the intent and voluntarily chooses `contract_id`/`amount`/`deposit_for_account_id`. There is no attacker distinct from the signer who can force this loss onto an unwilling victim — a signer can only burn their own funds this way, and only by signing a payload that deliberately or mistakenly targets a bad `contract_id`. This does not fit "tokens moved, credited or withdrawn without the owner's valid signature or authorization" — the owner did authorize exactly this transfer with knowledge (per the doc) that it's not refundable on failure. No unauthorized value leaves the Verifier belonging to a party who didn't sign for it. [2](#0-1) [3](#0-2) 

### Likelihood Explanation
Not applicable as an attack against a third party: the only affected balance is the signer's own, and the signer must sign the payload themselves choosing the bad `contract_id`. This is self-inflicted, matching the documented/accepted risk, and existing tests (`tests/src/tests/defuse/storage/mod.rs`) already cover the success/failure paths of this intent without expecting a refund on external-call failure. [4](#0-3) 

### Recommendation
Not applicable — this is a documented, self-inflicted design choice rather than a security vulnerability with an unauthorized attacker/victim relationship. If desired, the contract could add a refund resolver to `do_storage_deposit` analogous to `ft_resolve_withdraw`, but this is a UX/robustness improvement, not a security fix, since the disclosed risk means users aren't unknowingly exposed to fund loss by a third party.

### Proof of Concept
Not applicable — no distinct attacker/victim relationship to prove; the existing test suite (`storage_deposit_fails_user_has_no_balance_in_intents`, `storage_deposit_success`) already demonstrates the intent's failure/success behavior without any unauthorized loss to a non-signing party.

    fn storage_deposit(
        &mut self,
        owner_id: &AccountIdRef,
        storage_deposit: StorageDeposit,
    ) -> Result<()> {
        self.withdraw(
            owner_id,
            [(
                Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                storage_deposit.amount.as_yoctonear(),
            )],
            Some("withdraw"),
            false,
        )?;

        ext_wnear::ext(self.wnear_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(NEAR_WITHDRAW_GAS)
            // do not distribute remaining gas here
            .with_unused_gas_weight(0)
            .near_withdraw(U128(storage_deposit.amount.as_yoctonear()))
            .then(
                // do_storage_deposit only after unwrapping NEAR
                Self::ext(env::current_account_id())
                    .with_static_gas(Self::DO_STORAGE_DEPOSIT_GAS)
                    // do not distribute remaining gas here
                    .with_unused_gas_weight(0)
                    .do_storage_deposit(storage_deposit),
            )
            .detach();

        Ok(())
    }

    #[private]
    pub fn do_storage_deposit(storage_deposit: StorageDeposit) -> Promise {
        require!(
            promise_result_checked_void(0).is_ok(),
            "near_withdraw failed",
        );

        ext_storage_management::ext(storage_deposit.contract_id)
            .with_attached_deposit(storage_deposit.amount)
            .with_static_gas(STORAGE_DEPOSIT_GAS)
            // do not distribute remaining gas here
            .with_unused_gas_weight(0)
            .storage_deposit(Some(storage_deposit.deposit_for_account_id), None)
    }

#[tokio::test]
async fn storage_deposit_fails_user_has_no_balance_in_intents(#[future(awt)] env: Env) {
    let (user, other_user, ft) =
        futures::join!(env.create_user(), env.create_user(), env.create_token());

    futures::try_join!(
        env.fund_account_with_near(user.account_id(), NearToken::from_near(1000)),
        env.fund_account_with_near(other_user.account_id(), NearToken::from_near(1000))
    )
    .unwrap();
    {
        futures::join!(
            async {
                assert!(
                    ft.storage_balance_of(user.account_id())
                        .await
                        .unwrap()
                        .is_none()
                );
            },
            async {
                assert!(
                    ft.storage_balance_of(other_user.account_id())
                        .await
                        .unwrap()
                        .is_none()
                );
            },
        );
    }

    // For intents contract to have a balance in wnear, we make a storage deposit for it
    futures::try_join!(
        env.wnear
            .storage_deposit(env.defuse.contract_id(), NearToken::from_near(1))
            .into_future(),
        ft.storage_deposit(user.account_id(), NearToken::from_near(1))
            .into_future(),
    )
    .unwrap();

    {
        futures::join!(
            async {
                assert_eq!(
                    ft.storage_balance_of(user.account_id())
                        .await
                        .unwrap()
                        .unwrap()
                        .total,
                    MIN_FT_STORAGE_DEPOSIT_VALUE
                );
            },
            async {
                assert!(
                    ft.storage_balance_of(other_user.account_id())
                        .await
                        .unwrap()
                        .is_none()
                );
            }
        );
    }

    // The user should have enough wnear in his account (in his account in the wnear contract)
    other_user
        .near_deposit(env.wnear.contract_id(), NearToken::from_near(100))
        .await
        .unwrap();

    let signed_intents = [other_user
        .sign_defuse_payload_default(
            &env.defuse,
            [StorageDeposit {
                contract_id: ft.contract_id().clone(),
                deposit_for_account_id: other_user.account_id().clone(),
                amount: MIN_FT_STORAGE_DEPOSIT_VALUE,
            }],
        )
        .await
        .unwrap()];

    // Fails because the user does not own any wNEAR in the intents smart contract. They should first deposit wNEAR.
    env.defuse_simulate_and_execute_intents(env.defuse.contract_id(), signed_intents)
        .await
        .unwrap_err();
