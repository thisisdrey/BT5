### Title
Bunny-style AMM/Bancor curve manipulation via floating-point precision in the built-in Exchange (TRC10↔TRX) module - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The PancakeBunny report is a bug-class hint about draining an AMM-style liquidity pool by exploiting inaccuracies in its pricing curve to extract more value than deposited. java-tron ships its own on-chain AMM equivalent: the `Exchange`/`ExchangeV2` Bancor-relay pools, created permissionlessly by any account via `ExchangeCreateActuator` and traded against by any account via `ExchangeTransactionContract`/`ExchangeTransactionActuator`. The default (legacy) pricing engine, `ExchangeProcessor`, computes swap outputs with Java `double` arithmetic and `Math.pow`, which is not deterministic/precise money math and can round in the trader's favor, letting an attacker who is willing to fund the initial pool bleed real TRX/TRC10 out of it over repeated crafted trades — the same "exploit the pricing curve to steal reserve funds" pattern as PancakeBunny, just applied to java-tron's built-in Bancor exchange rather than an external DEX contract.

### Finding Description
Any unprivileged account can:
1. Create a TRX↔TRC10 exchange pool via `ExchangeCreateContract` handled by `ExchangeCreateActuator` — there is no permission check beyond having enough balance [1](#0-0) .
2. Trade against that pool via `ExchangeTransactionContract`, whose actuator calls `ExchangeCapsule.transaction(...)`, which selects the pricing `Processor` [2](#0-1) .

By default the “hardened” calculation path is gated behind the dynamic property `allowHardenExchangeCalculation`, checked via `AbstractExchangeActuator.allowHarden()` [3](#0-2) . When this flag is not enabled (its state depends on committee proposal activation, which cannot be assumed to be universally on across all deployed networks/forks of this codebase), swaps are routed to the legacy `ExchangeProcessor`, which performs the Bancor relay-token math using `double` and `Math.pow`, then truncates results with a raw `(long)` cast with no overflow/precision safety [4](#0-3) .

The presence of a parallel, purpose-built `SafeExchangeProcessor` using `BigDecimal` with explicit rounding and `StrictMathWrapper` overflow checks [5](#0-4) , feature-flagged behind `allowHardenExchangeCalculation`, is itself evidence that the floating-point legacy processor was recognized as producing imprecise/exploitable results — this mirrors exactly the underlying bug class in the PancakeBunny report: a manipulable, imprecise on-chain price/exchange curve that a funded attacker can repeatedly probe and drain via sequences of `ExchangeInjectContract`/`ExchangeTransactionContract`/`ExchangeWithdrawContract` calls (all reachable by ordinary signed transactions, no privilege required) [6](#0-5) [7](#0-6) .

Unlike the DeFi report's flash-loan, this does not require a flash loan primitive; java-tron has no native flash loans, but an attacker only needs to self-fund a pool (permissionless creation) and can then apply the same “move the curve, extract more than deposited” technique purely through normal signed transactions within/across blocks, since nothing prevents rapid sequential trades by the same account.

### Impact Explanation
If the floating-point legacy processor is reachable (default state, or on any fork/testnet/mainnet configuration where the hardening proposal has not been activated), an attacker can drain real TRX and TRC10 token balances from Exchange pools beyond what accounting invariants should allow, i.e., theft of funds / unbacked balance from the Exchange subsystem. This directly affects on-chain account balances (`AccountStore`) updated by `ExchangeTransactionActuator.execute()` [8](#0-7) , which is a concrete unauthorized transfer of value, matching the accepted impact categories (theft of funds / unbacked balance).

### Likelihood Explanation
Reachability is high: pool creation and trading are permissionless actuators reachable by any signed transaction from any account with modest TRX. The only gating factor is whether `allowHardenExchangeCalculation` is enabled on a given network — since this is a dynamic property controlled by committee proposal (see `ProposalUtil`/`ProposalService` references), its state is not guaranteed across all deployments, and the vulnerable code path (`ExchangeProcessor`) remains present and reachable whenever the flag is off. Actual profitability requires careful crafting of trade sizes to exploit floating-point rounding, which is a research/engineering effort but not privileged access.

### Recommendation
- Force `allowHardenExchangeCalculation` (or an equivalent hard-fork flag) to be permanently on for all networks derived from this codebase, and remove/deprecate the floating-point `ExchangeProcessor` path entirely so it is never selectable.
- Audit `SafeExchangeProcessor` itself for edge cases (e.g., `divide` rounding mode `HALF_UP` still permits value leakage in adversarial trade sequencing) and add invariant checks (e.g., total pool value must not decrease outside of fee assumptions) directly in `ExchangeCapsule.transaction`.

### Proof of Concept
Conceptual sequence (mirroring the PancakeBunny "manipulate curve, then extract manipulated value" pattern), all executable via ordinary signed transactions:
1. Attacker calls `ExchangeCreateContract` to create a TRX/TRC10 pool with a small skewed ratio (permissionless, see `ExchangeCreateActuator.doValidate`).
2. Attacker issues a sequence of `ExchangeTransactionContract` swaps sized to exploit the `double`/`Math.pow` truncation in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (e.g., very small vs. very large trade interleaving, as demonstrated by the differing legacy-vs-hardened results asserted in `ExchangeCapsuleTest.testTransactionLegacyVsHardenedProcessorSelection`, which shows up to a 1-unit-per-trade divergence between the two processors) [9](#0-8) .
3. Repeating such trades across many transactions accumulates rounding-favorable extraction, letting the attacker withdraw more value via `ExchangeWithdrawContract` than was deposited, at the expense of the pool/other participants.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);

  public void testTransactionLegacyVsHardenedProcessorSelection() throws Exception {
    // Same input produces deterministic results in both modes.
    ExchangeCapsule legacy = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 100L, 0L,
        "abc".getBytes(), "def".getBytes());
    legacy.setBalance(100_000_000L, 100_000_000L);
    long legacyResult = legacy.transaction("abc".getBytes(), 1_000_000L, true, false);

    ExchangeCapsule hardened = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());
    hardened.setBalance(100_000_000L, 100_000_000L);
    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);
    Assert.assertTrue("Hardened must not exceed pool",
        hardenedResult <= 100_000_000L);
    // Allow ±1 difference due to BigDecimal vs double precision
    Assert.assertTrue("Results should be within 1 unit",
        StrictMathWrapper.abs(legacyResult - hardenedResult) <= 1);
  }
