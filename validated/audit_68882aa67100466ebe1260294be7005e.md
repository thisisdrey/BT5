Found it: `ExchangeInjectActuator` provides the injection amount `tokenQuant` for a single token, but the corresponding amount of the *other* token (`anotherTokenQuant`) that will be pulled from the caller's balance is computed at execution time from the exchange's live pool ratio (`firstTokenBalance`/`secondTokenBalance`), with **no caller-specified maximum/limit** on that computed `anotherTokenQuant`. This is the same bug class as the reported Notional issue: an amount that must be paid by the caller is derived from mutable, front-runnable state (the AMM pool ratio) with no slippage/limit parameter to bound it, unlike `ExchangeTransactionActuator`, which explicitly has an `expected` field to protect the swapper.

### Title
Missing slippage/maximum-cost control in `ExchangeInjectContract` allows front-run manipulation of the paired-token amount charged to the liquidity injector - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
`ExchangeInjectContract` lets a user inject `quant` of one token into a Bancor-style TRX/TRC10 `Exchange` pool identified by `exchange_id`. The actuator computes how much of the *paired* token must simultaneously be deducted from the same account to preserve the pool ratio, but this paired amount is derived from the pool's live balances at execution time and is never bounded by any value the caller supplies.

### Finding Description
In `ExchangeInjectActuator.doValidate()` and `execute()`, the amount of the paired token that will be deducted from the owner's account, `anotherTokenQuant`, is calculated purely from the current on-chain pool ratio: [1](#0-0) 

and then charged to the caller in `execute()`: [2](#0-1) 

The `ExchangeInjectContract` message only carries `token_id` and `quant` for the token being injected — there is no `expected`/`max` field to cap the paired-token cost, unlike `ExchangeTransactionContract`, which was explicitly designed with an `expected` minimum-output field to protect against exactly this kind of manipulation: [3](#0-2) 

Because `firstTokenBalance`/`secondTokenBalance` (the pool ratio) can be changed by any other account submitting a competing `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` against the same `exchange_id` before the victim's transaction is packed into a block, an attacker (or a block-producing witness reordering transactions) can shift the ratio between the time the victim signs their inject transaction and the time it executes. This directly changes `anotherTokenQuant`, i.e., the amount deducted from the victim account, without the victim having any way to specify an acceptable maximum.

### Impact Explanation
A liquidity injector who submits an `ExchangeInjectContract` can be made to pay substantially more of the paired token (TRX or TRC10 asset) than they intended, because the actuator has no caller-supplied ceiling on `anotherTokenQuant`. This is a concrete, unbounded loss of funds for the transaction sender caused purely by front-running/sandwiching of the pool ratio, matching the "Medium" severity class of the original finding (a broadcastable-transaction author overpaying due to missing slippage control).

### Likelihood Explanation
Any account can observe pending `ExchangeInjectContract` transactions and submit a transaction that shifts the exchange pool ratio (e.g., a large `ExchangeTransactionContract` swap) targeting the same `exchange_id`, then let the victim's inject transaction execute against the new ratio. Exchange IDs and pool balances are public on-chain state, and no special privilege is required — this is reachable by any unprivileged transaction broadcaster.

### Recommendation
Add a `max_another_token_quant` (or similarly named) field to `ExchangeInjectContract`, and in `ExchangeInjectActuator.doValidate()`/`execute()`, reject the transaction if the computed `anotherTokenQuant` exceeds the caller-specified maximum, mirroring the `expected` slippage check already present in `ExchangeTransactionActuator`.

### Proof of Concept
1. Attacker observes a pending `ExchangeInjectContract` from victim for `exchangeId=1`, injecting `tokenQuant` of `firstTokenId`, expecting to also pay roughly `secondTokenBalance * tokenQuant / firstTokenBalance` of `secondTokenId`.
2. Attacker submits and gets included first a large `ExchangeTransactionContract` swap against the same `exchangeId` that sharply changes `firstTokenBalance`/`secondTokenBalance` (e.g., by selling a large amount of `secondTokenId` into the pool), or crafts favorable ordering as a block-producing witness.
3. Victim's `ExchangeInjectContract` then executes with the new, less favorable ratio; `anotherTokenQuant` computed in `ExchangeInjectActuator.execute()` (lines 71-83) is now much larger than what the victim expected when signing the transaction, and this amount is deducted from the victim's balance/asset in lines 85-99, with no check preventing the higher cost.
