## Title
Missing negative-balance / bounds check on the legacy (non-hardened) `ExchangeCapsule.transaction()` path lets bonding-curve exchange balances go negative - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Rubicon report describes two structurally similar `offer()` overloads where a minimum-amount ("dust") safety check exists in one path but is missing from the other, so callers of the unguarded path bypass the protection. `ExchangeCapsule.transaction()` in java-tron has the same class of defect: the sanity check that the post-trade bonding-curve balances (`newFirstTokenBalance`/`newSecondTokenBalance`) cannot become negative is only executed when `hardenedCalc` is `true`, i.e. only when the `allowHardenExchangeCalculation` dynamic property/hard fork is active. The legacy `ExchangeProcessor`-based arithmetic path — which is the default, always-reachable path for `ExchangeTransactionContract` and `ExchangeWithdrawContract` — performs the identical balance math but skips the guard entirely.

### Finding Description
`ExchangeCapsule.transaction()` computes new bonding-curve balances using either the legacy `ExchangeProcessor` (floating point) or, when `hardenedCalc` is true, `SafeExchangeProcessor`/`StrictMathWrapper` arithmetic: [1](#0-0) 

The check that guards against balances going below zero is gated exclusively by `hardenedCalc`:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
```
`hardenedCalc` is derived from `allowHarden()`, which reads `chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation()`: [2](#0-1) 

`ExchangeTransactionActuator.doValidate()` calls `exchangeCapsule.transaction(...)` passing `allowHarden()` as the `hardenedCalc` flag directly, and the same value is used again in `execute()`: [3](#0-2) [4](#0-3) 

None of the other validations performed in `doValidate()` (token-in-exchange check, `tokenQuant > 0`, `tokenExpected > 0`, zero-balance check, `balanceLimit` upper bound) constrain the *lower* bound of the resulting exchange balances when the legacy path is used: [5](#0-4) 

`ExchangeWithdrawActuator` has an analogous issue: its execution path directly subtracts `tokenQuant`/`anotherTokenQuant` from the exchange's on-chain balances using plain `BigInteger` division without ever calling the hardened balance-floor check that `ExchangeCapsule.transaction()` performs: [6](#0-5) 

Since `allowHardenExchangeCalculation` is a dynamic property that defaults to disabled until activated by an on-chain proposal, every `ExchangeTransactionContract` submitted by an ordinary account currently executes through the unguarded legacy branch, exactly analogous to callers reaching the `offer()` overload in RubiconMarket that omits the `_dust` check.

### Impact Explanation
If floating-point rounding in `ExchangeProcessor.exchange()` (which uses `double` arithmetic via `Maths.pow`) ever computes a `buyTokenQuant` that exceeds the counter-token's balance, `newSecondTokenBalance`/`newFirstTokenBalance` becomes negative and is written directly into the `ExchangeCapsule` and persisted via `Commons.putExchangeCapsule`, with no exception thrown to prevent it. A negative on-chain reserve balance is an accounting/state corruption bug in an asset-custody structure (the bancor-style bonding-curve exchange holds real TRX/TRC10 reserves credited to and debited from user accounts in the same transaction), which can be leveraged to extract more of a token than the pool actually backs — an unbacked-balance / permanent-loss-of-funds condition for the exchange's counterparties.

### Likelihood Explanation
Reaching this code path requires only a single, ordinary signed `ExchangeTransactionContract` transaction from an unprivileged account through `ExchangeTransactionActuator`; no special SR/witness privilege or malicious network behavior is needed. The condition depends on triggering a rounding edge case in the legacy double-precision `ExchangeProcessor`, which is the *default* production path since `allowHardenExchangeCalculation` is an opt-in hard-fork flag — this makes the vulnerable branch the normally executing one rather than a rare fallback.

### Recommendation
Move the balance-floor check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) out of the `hardenedCalc`-only branch in `ExchangeCapsule.transaction()` so it is enforced unconditionally, regardless of `allowHardenExchangeCalculation`. Apply the equivalent lower-bound validation in `ExchangeWithdrawActuator`'s balance arithmetic as well, so both call sites reject any trade or withdrawal that would drive the exchange's reserves negative.

### Proof of Concept
1. Ensure `allowHardenExchangeCalculation` is disabled (default state) so `ExchangeTransactionActuator` uses the legacy `ExchangeProcessor` path: [2](#0-1) .
2. Craft an `ExchangeTransactionContract` with `tokenQuant` chosen such that `ExchangeProcessor.exchange()`'s double-precision bancor formula returns a `buyTokenQuant` that rounds to a value at or beyond the counter-token's current `secondTokenBalance`/`firstTokenBalance`.
3. Submit via `ExchangeTransactionActuator.validate()`/`execute()`; observe that `exchangeCapsule.transaction(tokenID, tokenQuant, allowStrictMath, false)` computes `newSecondTokenBalance < 0` but the guard `if (hardenedCalc && ...)` is skipped because `hardenedCalc == false`, so the negative balance is persisted via `Commons.putExchangeCapsule` without error: [7](#0-6) .

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```
