Unclosed RocksDB Iterator on Early Loop Exit in `Wallet.getMarketPairList()` Leaks Native Resources per Anonymous API Call - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`Wallet.getMarketPairList()`, exposed via the unauthenticated HTTP endpoint `GetMarketPairListServlet` and the equivalent gRPC `getMarketPairList` API, obtains a raw `Iterator` from `MarketPairToPriceStore.iterator()` and iterates it in a `while` loop that `break`s early once `MARKET_COUNT_LIMIT_MAX` entries have been counted, without ever closing the iterator, mirroring the "Iterators are not closed" bug class from the referenced Allora report.

### Finding Description
`Wallet.getMarketPairList()` calls:
```java
Iterator<Entry<byte[], BytesCapsule>> iterator = marketPairToPriceStore.iterator();
long count = 0;
while (iterator.hasNext()) {
  Entry<byte[], BytesCapsule> next = iterator.next();
  ...
  count++;
  if (count > MARKET_COUNT_LIMIT_MAX) {
    break;
  }
}
``` [1](#0-0) 

The store's underlying `iterator()` implementation (`RockStoreIterator` for RocksDB, `StoreIterator` for LevelDB) only closes the native handle automatically inside `hasNext()` when the iterator becomes exhausted (`!dbIterator.isValid()`), or when an exception occurs: [2](#0-1) 

Since `getMarketPairList()` exits the loop via `break` once the pair count exceeds `MARKET_COUNT_LIMIT_MAX`, whenever the store contains more entries than the limit, the loop never calls `hasNext()` again to trigger the auto-close path, and the method returns without ever invoking `close()` on the iterator (there is no `try`/`finally` or try-with-resources wrapping it). This leaves the native RocksDB `RocksIterator` and its `ReadOptions` object (or the LevelDB native iterator) permanently open, exactly the resource-leak pattern flagged for `GetStakeRemovalsForBlock`/`GetInferenceScoresUntilBlock` in the Allora report, except here the leaked object is a native (JNI) resource rather than a managed Go object.

Both HTTP and gRPC front ends expose this to any anonymous, unauthenticated caller: [3](#0-2) 

### Impact Explanation
Each invocation of the exchange market-pair-list query that returns more than `MARKET_COUNT_LIMIT_MAX` pairs leaks one native RocksDB iterator handle and its associated `ReadOptions`. Because the API is public and unauthenticated (reachable by any anonymous API client via HTTP or gRPC), repeated calls accumulate un-freed native memory/file handles inside the node process over time. This is a node resource-exhaustion issue that can eventually degrade or crash the API-serving node (an API the node can no longer serve, or general node instability), rather than a fund-theft or consensus issue.

### Likelihood Explanation
Likelihood depends on whether the market-pair store on a given deployment holds more than `MARKET_COUNT_LIMIT_MAX` pairs; if so, every single call to `getMarketPairList` leaks a handle deterministically, and the endpoint can be called repeatedly and freely by any client without authentication or gas cost, making sustained resource exhaustion straightforward to trigger.

### Recommendation
Wrap the iterator usage in `Wallet.getMarketPairList()` in a try-with-resources (or explicit `try/finally { iterator.close(); }`) block, ensuring the iterator is closed on every exit path including the early `break`, consistent with the documented contract on `iterator()`: [4](#0-3) 

### Proof of Concept
1. Populate `MarketPairToPriceStore` with more than `MARKET_COUNT_LIMIT_MAX` distinct trading pairs (via normal `marketSellAsset` transactions creating exchange pairs).
2. As an anonymous client, repeatedly call the public HTTP endpoint `GET /wallet/getmarketpairlist` (served by `GetMarketPairListServlet`) or the equivalent gRPC `getMarketPairList` RPC.
3. Each call triggers `Wallet.getMarketPairList()`, which `break`s out of the loop after `MARKET_COUNT_LIMIT_MAX` entries without closing the iterator, leaking one native RocksDB iterator/`ReadOptions` per call.
4. Repeated calls accumulate leaked native handles, observable via increasing native memory usage / open file descriptors on the node process over time.
