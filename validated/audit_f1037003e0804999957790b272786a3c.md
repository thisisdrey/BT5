### Title
Unbounded read of attacker-declared field lengths in `InputZipFile::ProcessCentralDirEntry` allows out-of-bounds memory read on malicious ZIP/JAR archives - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in the `ijar`/`zipper` ZIP-reading engine parses central-directory entries directly from the mmap'd input file without ever calling the `EnsureRemaining()` bounds check that its sibling function `ProcessLocalFileEntry` uses consistently. An attacker who supplies a crafted ZIP/JAR (e.g. a dependency archive fetched by `http_archive`/`http_jar` and pinned by its own `sha256`) can set `file_name_length`, `extra_field_length`, or `file_comment_length` fields to values that run past the actual end of the mapped file, causing `memcpy` and the `extra_p`-walking loop to read out of bounds of the mapping.

### Finding Description
`InputZipFile::ProcessNext()` calls `ProcessCentralDirEntry` once per central-directory record: [1](#0-0) 

Inside `ProcessCentralDirEntry`, all fields (`compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, `offset`) are read with `get_u4le`/`get_u2le`, which are raw pointer-advancing reads with no bounds checking at all, and then the code does:
```
size_t len = (file_name_length < filename_size) ? file_name_length : (filename_size - 1);
memcpy(reinterpret_cast<void*>(filename), p, len);
...
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  ...
  extra_p += data_size;
  ...
}
p += file_comment_length;
``` [2](#0-1) 

None of `file_name_length`, `extra_field_length`, or the ZIP64 extra-field `data_size` is validated against the remaining bytes of the mmap'd file before being used to `memcpy` or to walk `extra_p`/`p`. Compare this to `ProcessLocalFileEntry`, the local-header parser, which explicitly calls `EnsureRemaining()` before every variable-length read: [3](#0-2)  The `EnsureRemaining` helper itself is defined only to be used defensively where called — it is never invoked from `ProcessCentralDirEntry`: [4](#0-3) 

The class-level comment above `ProcessCentralDirEntry` asserts the parsing is "safe" because "the central directory is always followed by another data structure that has a signature," but this assumption does not hold for a maliciously crafted file where the *declared* `file_name_length`/`extra_field_length` fields simply lie about their true extent relative to the physical file size — the code trusts these attacker-controlled 16-bit length fields unconditionally. [5](#0-4) 

`InputZipFile` backs both the `ijar` interface-jar tool and the `third_party/ijar/zip_main.cc` `zipper` tool, both of which are invoked by Bazel's build machinery on JAR/ZIP files that can originate from external, attacker-influenced sources (e.g., third-party JARs fetched via `http_jar`/`http_archive` and pinned by `sha256`/`integrity`). Because the integrity check only certifies that the downloaded *bytes as a whole* match a hash — a hash that the attacker who first published the artifact effectively chooses — it does nothing to validate that the internal ZIP structure (its central-directory length fields) is well-formed relative to the file's actual size. A hostile origin server can publish a byte-for-byte "legitimate" archive (matching whatever checksum gets pinned) whose central directory entries declare `file_name_length`/`extra_field_length` values that extend past EOF.

### Impact Explanation
Reading with `memcpy` and pointer arithmetic driven by unvalidated, attacker-controlled 16-bit length fields past the end of an `mmap`'d region is a classic out-of-bounds read: at minimum it crashes the build (SIGSEGV/SIGBUS reading past the mapping, or reading adjacent process memory/heap into the extracted `filename` buffer or ZIP64 extra-field values), and in the worst case it can leak adjacent memory contents into fields that influence subsequent decisions (`uncompressed_size`/`compressed_size`/`offset` derived from OOB `get_u8le(extra)` reads), corrupting downstream size/offset computations used for further mmap-relative reads in `ProcessFile`/`SkipFile`/`UncompressFile`. This is directly analogous in class to CVE-2022-34346 (Intel Media SDK out-of-bounds read from untrusted, structured input).

### Likelihood Explanation
Any build that consumes a third-party JAR/ZIP (via `http_jar`, `http_archive`, Maven-resolved artifacts, etc.) exercises `ijar`/`zipper` on that content as part of normal Java compilation or extraction pipelines. Since the sha256/integrity pin only binds to the whole-file digest and is chosen at the time the artifact is first vetted/pinned by the victim (i.e., the attacker who serves the artifact controls its bytes and thus effectively controls what gets pinned), the pinned checksum does not stop a maliciously malformed-but-hash-matching archive from reaching this code path. No special privilege beyond publishing/serving the artifact is required.

### Recommendation
Add `EnsureRemaining()` (or equivalent bounds checks against `input_file_->Length()` / the mapped extent) calls in `ProcessCentralDirEntry` before every variable-length read: after reading `file_name_length`, before the `memcpy`; after computing `extra_field_length`, before walking `extra_p`; and while iterating the ZIP64/extra-field records, verify `data_size` does not exceed the remaining bytes of `extra_field_length`. Apply the same discipline uniformly used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` and `CalculateOutputLength`.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test constructing a ZIP whose central-directory record declares `file_name_length = 0xFFFF` (or `extra_field_length = 0xFFFF`) while the actual remaining bytes in the file after that record are only a few bytes, then invoking `zipper x <malicious.zip>` (or feeding the archive to `ijar`), should reproduce a crash/OOB read: `third_party/ijar/test/zip_test.sh` already contains an analogous structural-attack harness for path traversal (`test_no_path_traversal`) that can be extended with a `test_oob_read_central_directory` case using a truncated/lying central-directory entry, verified via ASan (`-fsanitize=address`) to detect the heap-buffer-overflow/global-buffer-overflow read past the mmap'd region: [6](#0-5) 

Note: I was unable to fully trace, within available tool calls, the exact call chain from a specific Starlark repo rule (e.g. `http_jar`) down into a guaranteed invocation of this native `ijar`/`zipper` C++ code versus a separate Java-based ZIP handling path for `repository_ctx.extract`; this should be verified further (e.g. via a Devin session with build/execution access) before treating this as a fully confirmed, end-to-end reachable production vulnerability.

  u8 compressed, uncompressed;

    return false;

      return false;
    }

  }

  return true;

```text
bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
```
