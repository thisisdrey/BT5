### Title
Attacker can freeze a victim's deposits by dust-transferring a `DepositToken` whose underlying oracle reverts, poisoning `debtPositionOf` - (File: contracts/DepositToken.sol)

### Summary
`DepositToken._transfer` unconditionally registers the token in the recipient's `depositTokensOfAccount` list via `pool.addToDepositTokensOfAccount` whenever the recipient's balance was zero [1](#0-0) . Every subsequent `transfer`, `transferFrom`, or `withdraw` by the victim calls `_revertIfLocked` → `unlockedBalanceOf` → `pool.debtPositionOf(account_)` [2](#0-1) , which iterates all of the account's deposit tokens and calls `masterOracle().quoteTokenToUsd(underlying, ...)` for each [3](#0-2) . If any single underlying's oracle reverts (e.g., a stale pull-oracle feed on Hemi/mainnet that reverts with `price-too-behind`/`invalid-token-price`, or a missing feed), the entire call reverts — the analog of the NULL dereference: a single unrequested "frame" (dust position) crashes every state path that touches the account.

### Finding Description
- An unprivileged attacker deposits a minimal amount of any registered collateral and calls `DepositToken.transfer(victim, dust)`. `_transfer` adds the token to the victim's `depositTokensOfAccount` [4](#0-3) .
- From then on, `debtPositionOf(victim)` iterates `depositTokensOfAccount` and `debtTokensOfAccount` and prices every underlying through `IMasterOracle` [5](#0-4) .
- `unlockedBalanceOf` calls `debtPositionOf` before doing anything else, even when the account has zero debt (`_debtInUsd == 0` early-return still evaluates the oracle loop first) [6](#0-5) .
- `withdraw` and `withdrawFrom` both call `_revertIfLocked`, which reverts via `unlockedBalanceOf` [7](#0-6) .
- Critically, the victim cannot self-heal: removing the poison token requires a `transfer`/`transferFrom` (which reverts in `_revertIfLocked`) or a `withdraw` (same path). There is no way to remove an entry from `depositTokensOfAccount` except zeroing the balance through these now-reverting functions.
- The deployed configuration uses pull oracles (RedStone/Pyth) whose quotes revert when the feed is stale — confirmed by E2E tests where `pool.debtPositionOf` reverts with `invalid-token-price` until the feed is pushed [8](#0-7) . If the dusted collateral's feed is expired (or has no feed at all on a chain where the pool was deployed), all of the victim's positions across all deposit tokens are bricked.

### Impact Explanation
Temporary (or permanent, if the oracle feed is never updated again) freezing of all of the victim's deposited collateral: they cannot transfer, withdraw, or be accurately evaluated for liquidation while the revert persists. This matches the CVE's bug class — an injected, unrequested element reaching a code path that unconditionally dereferences external state, producing a denial of service — and meets the "temporary freezing of funds" acceptance bar. `nonReentrant`, `whenNotPaused`, `whenNotShutdown`, and the `MAX_TOKENS_PER_USER` cap do not mitigate it; the cap only bounds how many poison tokens can be injected.

### Likelihood Explanation
The attacker only needs a dust balance of any registered `DepositToken` whose underlying currently lacks a fresh pull-oracle price. On chains using pull oracles (Hemi/mainnet Pyth/RedStone deployments), feeds go stale by default until someone pays to update them, making the preconditions cheap and common. Cost is limited to acquiring the dust amount plus gas.

### Recommendation
- In `unlockedBalanceOf` / `debtPositionOf`, skip deposit tokens whose underlying oracle reverts (try/catch around `quoteTokenToUsd`), or let `depositOf` tolerate a reverting oracle so the account is not bricked.
- Alternatively, allow users to remove a token from `depositTokensOfAccount` without passing the locked-balance check (e.g., a `Pool.removeFromDepositTokensOfAccount` reachable when `unlockedBalanceOf` would revert), or only add tokens to the list via opt-in (`deposit`) rather than on every inbound `transfer`.

### Proof of Concept
Hardhat fork (reproducible on the repo's fork harness used in `test/E2E.hemi.pullOracle.test.ts`):

```ts
// 1. Attacker deposits 1 wei-equivalent of a collateral whose oracle feed is stale
await collateral.approve(msdToken.address, dust)
await msdToken.deposit(dust, attacker.address)

// 2. Attacker dust-transfers the deposit token to the victim
await msdToken.connect(attacker).transfer(victim.address, dust)
//    -> pool.addToDepositTokensOfAccount(victim) now contains msdToken

// 3. Feed for msdToken.underlying() is expired (default state for pull oracles)
//    Any of these now revert for the victim:
await expect(pool.debtPositionOf(victim.address)).reverted // 'price-too-behind' / 'invalid-token-price'
await expect(msdWETH.connect(victim).withdraw(amount, victim.address)).reverted // via _revertIfLocked -> unlockedBalanceOf -> debtPositionOf
await expect(msdWETH.connect(victim).transfer(bob.address, amount)).reverted

// 4. Victim cannot remove the poison token: transferring it out also reverts
await expect(msdToken.connect(victim).transfer(attacker.address, dust)).reverted
// Victim's funds stay frozen until someone updates the oracle feed (or forever if none exists)
```
