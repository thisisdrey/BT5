### Title
Single stale/unavailable price feed causes protocol-wide DoS of borrow, withdraw, and liquidate via `unwrap-panic` in `get-assets` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`get-assets` resolves prices for every asset in a user's position mask by calling `price-multi-resolve` and then unconditionally unwrapping the result with `unwrap-panic`. If any single asset's price feed is stale or unreadable (a real-world Pyth/DIA scenario, analogous to Chainlink's documented "zero timestamp means round incomplete" case cited in the report), the entire multi-asset price resolution aborts the transaction instead of failing gracefully, blocking every position-health operation (`borrow`, `collateral-remove`, `supply-collateral-add`, `liquidate`) for any account holding that asset.

### Finding Description
`get-assets` gathers the oracle configs for every asset relevant to the user's position mask, resolves all their prices in one pass, then hard-unwraps the result: [1](#0-0) 

`price-multi-resolve` folds over each oracle config via `iter-price-multi`. Individual failures are caught with `unwrap!` and marked `valid: false`, but the aggregate function then reverts with `ERR-ORACLE-MULTI` if *any* single asset failed: [2](#0-1) 

Because `get-assets` calls this with `unwrap-panic` rather than propagating a Response, that `ERR-ORACLE-MULTI` (or any other error) becomes an unconditional abort of the whole calling transaction — there is no fallback/backup oracle path and no localized handling of just the failing asset.

The underlying per-asset resolution chain can genuinely fail in normal operation:
- `resolve-pyth` calls `call-pyth`, which `unwrap!`s the Pyth storage call into `ERR-ORACLE-PYTH`: [3](#0-2) 
- The Pyth storage contract's staleness check itself reverts with `ERR_STALE_PRICE` when the feed hasn't been refreshed within the configured threshold, or `ERR_PRICE_FEED_NOT_FOUND` if the feed was never written: [4](#0-3) 
- `resolve-dia` similarly `unwrap!`s the external DIA oracle call into `ERR-ORACLE-DIA`: [5](#0-4) 

All four functions that need position health depend on `get-assets` for pricing, and all propagate its panic:
- `borrow`: [6](#0-5) 
- `collateral-remove` (has-debt path): [7](#0-6) 
- `liquidate`: [8](#0-7) 

This is a direct analog of the reported bug class: the original report shows `UpdateWeightRunner._getData()` reverting outright when a single oracle among many is not "live," causing DoS across every function needing oracle data. Here, `get-assets`/`price-multi-resolve` exhibits the identical pattern — one bad/stale asset price panics the whole multi-asset resolution used by every position-health-dependent entry point.

### Impact Explanation
Any account whose position includes an asset backed by a temporarily stale or unpublished price feed becomes unable to:
- Withdraw any of its collateral (including unaffected, healthy collateral in the same position), because `collateral-remove`'s has-debt branch also calls `get-assets` on the full position mask.
- Be liquidated, because `liquidate` also depends on `get-assets` for `total-collateral-usd`/`total-debt-usd`. This blocks liquidation of an unhealthy position exactly when the market may need it most, risking bad debt accumulation.
- Borrow further or add collateral via `supply-collateral-add`.

This lands on temporary freezing of funds (a user's own collateral and any positions requiring liquidation become inaccessible/unresolvable until the specific oracle feed recovers), and in the liquidation-blocking case can contribute toward protocol insolvency if the frozen position continues to deteriorate while liquidation is unavailable.

### Likelihood Explanation
Pyth's staleness check (`ERR_STALE_PRICE`) is a normal operating condition, not an attack — a feed simply not being refreshed within the configured window (e.g., due to low volatility, keeper delay, or a paused updater) is common and directly mirrors the Chainlink "zero timestamp" scenario cited in the source report. No privileged action or oracle compromise is required; it triggers under ordinary oracle latency/downtime.

### Recommendation
Do not `unwrap-panic` the aggregate `price-multi-resolve` result in `get-assets`. Either:
1. Change `iter-price-multi`/`price-multi-resolve` to skip/flag only the failing asset (rather than aborting the whole batch) when that asset is not required for the current operation's health check, or
2. Introduce a backup oracle / staleness-tolerant fallback per asset (similar to `UpdateWeightRunner`'s backup-oracle mechanism recommended in the referenced report) so a single feed outage does not block all position operations, and ensure `liquidate` in particular can still execute using last-known-good or backup pricing so unhealthy positions remain liquidatable.

### Proof of Concept
1. User deposits collateral in asset A (Pyth-priced) and asset B (a second Pyth-priced asset).
2. The Pyth price feed for asset B is not refreshed for longer than its configured `max-staleness`/`stale-price-threshold` (a normal, permissionless condition — nobody is obligated to keep pushing updates).
3. User calls `collateral-remove` to withdraw asset A only. `get-assets` is invoked on the full position mask (both A and B), calling `price-multi-resolve`.
4. Resolving B's price triggers `read-price-with-staleness-check` → `ERR_STALE_PRICE` → bubbles through `call-pyth`/`resolve-pyth`/`price-resolve` → `iter-price-multi` marks `valid: false` → `price-multi-resolve` returns `(err ERR-ORACLE-MULTI)` → `get-assets`'s `unwrap-panic` aborts the entire transaction.
5. The user cannot withdraw asset A (a completely unaffected, freshly priced asset) until asset B's feed is refreshed. The same block applies to `borrow`, `supply-collateral-add`, and `liquidate` for this position.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
        ;; resolve price - will use cache for ztokens
        (price (unwrap! (price-resolve oracle-data) (merge acc { valid: false })))
        (next (unwrap-panic (as-max-len? (append (get output acc) price) u64))))
    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
