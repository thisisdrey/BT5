### Title
Dust-transfer spam fills `MAX_TOKENS_PER_USER` and blocks a victim's deposits and mints - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Any user who receives a `DepositToken` balance for the first time has that token appended to their per-account list via `Pool.addToDepositTokensOfAccount`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30). An attacker can acquire dust amounts of every listed `DepositToken` and spam `transfer()`s to a victim, filling all 30 slots. After that, every call path that would add a *new* token to the victim's account — a new collateral deposit, a new synthetic mint, leverage via `SmartFarmingManager`, or receipt of any other `DepositToken` — reverts with `UserReachedMaxTokens`. The victim must spend gas transferring the dust back out (one transaction per spam token) to regain functionality, mirroring the Chainlink incident where unsolicited spam drained node operators' hot-wallet funds.

### Finding Description
`DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance transitions from 0 to nonzero [1](#0-0) . `addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens` [2](#0-1) , which counts both debt and deposit tokens against the shared cap `MAX_TOKENS_PER_USER = 30` [3](#0-2) .

Attack sequence (all public, unprivileged calls):
1. Attacker deposits minimal underlying into each of the pool's active `DepositToken`s (dust is sufficient; only `amount_ > 0` is required to trigger the list add).
2. Attacker calls `depositToken.transfer(victim, 1 wei)` for each distinct token. Each call adds that token to `depositTokensOfAccount[victim]` [4](#0-3) .
3. Once 30 entries are accumulated, any victim action requiring a new list entry reverts:
   - `deposit()` into a collateral token the victim doesn't already hold (`_deposit` → `_transfer` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`).
   - `mint()`/`leverage()` of a synthetic whose `DebtToken` isn't already in the victim's list (`issue` → `addToDebtTokensOfAccount` → same revert) [5](#0-4) .
   - Any inbound `DepositToken` transfer of a new token type (e.g., seized collateral routing, repay-and-transfer flows).

No privileged role is involved; the check triggers purely on the recipient's state, and the `SenderIsNotDepositToken` guard only restricts *which contract* can call, not which account gets filled.

### Impact Explanation
- **Temporary freezing / denial of new positions**: the victim cannot open new collateral types or new debt positions while spammed. A victim trying to add collateral to rescue an underwater position (new token type) before liquidation is blocked — the attacker can time the spam to keep a position liquidatable and prevent self-rescue, converting the DoS into forced liquidation profit.
- **Forced gas expenditure**: clearing the list requires the victim to send one `transfer` per spam token (each transfer zeroes the dust balance and triggers `removeFromDepositTokensOfAccount` [6](#0-5) ), a direct gas-drain analog to the Chainlink hot-wallet drain.
- The attack is cheap: dust costs scale with `amount_ > 0`, and `updateRewardsBeforeTransfer` does not prevent dust transfers.

### Likelihood Explanation
Medium. The attack requires the pool to list enough active `DepositToken`s for the attacker to fill slots the victim hasn't already used; on mature deployments with many collaterals this is feasible with dust capital. The attacker also needs tokens the victim doesn't hold — front-running each of the victim's deposits is possible since transfers are permissionless. The only built-in mitigation is the victim manually clearing entries at their own gas cost.

### Recommendation
- Track the per-account limit on *user-initiated* additions only, or make `addToDepositTokensOfAccount` non-reverting on cap: if the cap is reached, skip the addition instead of reverting (the token is then excluded from `depositOf` accounting — mitigations below address that).
- Safer variant: allow removal-style "sweep" so a user can call `pool.removeFromDepositTokensOfAccountSelf(token)` to purge unwanted entries in one tx, or let `DepositToken` skip the add when the transfer is unsolicited dust below a threshold.
- Alternatively, bound `debtPositionOf`/`depositOf` iteration by iterating a registry of pool tokens filtered by nonzero balance rather than a per-account list, eliminating the griefable list entirely.

### Proof of Concept
The revert path is exercised in the existing suite (`UserReachedMaxTokens` cases) [7](#0-6) . A Hardhat fork PoC:

```ts
// Attacker seeds dust into N active DepositTokens, then:
for (const dt of activeDepositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1); // adds to victim's list
}
// victim's list now at MAX_TOKENS_PER_USER
await expect(
  pool.connect(victim).deposit(newDepositToken.address, amount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  newDebtToken.connect(victim)... // via pool.mint
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// Recovery: victim must transfer each dust token out (one tx each).
```

Note: severity is bounded — existing held tokens still deposit/mint normally, and the victim can clear entries at gas cost, so this is a griefing/temporary-DoS rather than permanent loss of funds.
