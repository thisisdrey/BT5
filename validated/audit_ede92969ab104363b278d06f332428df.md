### Title
`account_not_frozen_for_authority` freeze protection is bypassed for non-authority signers when a frozen account is in receivership or order execution - (File: `programs/marginfi/src/state/marginfi_account.rs`)

### Summary
`lending_account_withdraw` gates the `marginfi_account` on two independent constraints: `account_not_frozen_for_authority` and `is_signer_authorized(..., true, true)` [1](#0-0) . `account_not_frozen_for_authority` only blocks the case where the signer *is* the account's stored `authority` while `ACCOUNT_FROZEN` is set [2](#0-1) , and `is_signer_authorized` short-circuits on receivership/order-execution *before* it ever evaluates the frozen-flag branch [3](#0-2) . Consequently, a frozen account that is simultaneously in `ACCOUNT_IN_RECEIVERSHIP` or `ACCOUNT_IN_ORDER_EXECUTION` can have `lending_account_withdraw` executed by an unprivileged third-party signer (any liquidator/keeper key, not the group admin, not the account authority), completely defeating the admin freeze.

### Finding Description
`freeze.rs`'s `set_account_freeze` sets `ACCOUNT_FROZEN` and documents that "the account authority is blocked from major actions (borrow/deposit/withdraw/repay/transfer/etc.)... The group admin retains access to operate the account while frozen (for remediation/seizure)" [4](#0-3) . This implies the invariant that *only* the group admin should be able to move value while frozen, and everyone else (including the previous authority) should be blocked.

`LendingAccountWithdraw` enforces this with two separate Anchor constraints on `marginfi_account`:
1. `account_not_frozen_for_authority(&a, authority.key())` → `AccountFrozen`
2. `is_signer_authorized(&a, g.admin, authority.key(), true, true)` → `Unauthorized` [1](#0-0) 

`account_not_frozen_for_authority` returns `false` (blocking) **only** when `ACCOUNT_FROZEN` is set *and* `marginfi_account.authority == signer` [2](#0-1) . Any signer whose pubkey differs from the stored `authority` automatically passes this check regardless of the frozen flag.

`is_signer_authorized` is supposed to be the comprehensive check, but its branch order allows receivership/order-execution to short-circuit before the frozen check is reached:
```
if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
    return marginfi_account.authority != signer; // only blocks the original authority
}
if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
    return true; // unconditionally authorized
}
if marginfi_account.get_flag(ACCOUNT_FROZEN) {
    return group_admin == signer;
}
marginfi_account.authority == signer
``` [3](#0-2) 

For `lending_account_withdraw`, `allow_receivership=true` and `allow_order_execution=true` are passed [5](#0-4) . If an account is both `ACCOUNT_FROZEN` and `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION`, `is_signer_authorized` returns `true` for **any** signer that is not the original authority, without ever checking `ACCOUNT_FROZEN`. Combined with `account_not_frozen_for_authority` also passing (because the attacker's key isn't the stored `authority`), both Anchor constraints succeed and `lending_account_withdraw` executes, moving funds from the frozen account.

Exploit sequence (same-slot / adjacent instructions):
1. Admin freezes victim's account (`set_account_freeze(true)`), setting `ACCOUNT_FROZEN`.
2. Victim's account becomes unhealthy (or already has a pending order), so `ACCOUNT_IN_RECEIVERSHIP` (via `start_liquidation`) or `ACCOUNT_IN_ORDER_EXECUTION` gets set on the same/frozen account — these flags are settable through unprivileged, public liquidation/order-execution entrypoints, not admin-gated.
3. An unprivileged liquidator/keeper (attacker) calls `lending_account_withdraw` with `authority = attacker's own signer` (not the victim's authority, not the admin) against the frozen+receivership/order-execution account.
4. `account_not_frozen_for_authority` passes (signer ≠ stored authority).
5. `is_signer_authorized` returns `true` via the receivership/order-execution short-circuit, never checking the frozen flag.
6. Withdrawal executes despite the account being explicitly frozen by the admin for remediation/seizure purposes.

There is no test in the repository that exercises the combination of `ACCOUNT_FROZEN` with `ACCOUNT_IN_RECEIVERSHIP` or `ACCOUNT_IN_ORDER_EXECUTION` (searches for such combined test coverage returned nothing), meaning this interaction is unverified and unguarded by the existing test suite [6](#0-5) .

### Impact Explanation
This breaks the freeze invariant documented at `set_account_freeze`: the admin freezes an account specifically to prevent any value-moving action except by the admin itself (e.g., during an investigation, sanctions/seizure, or exploit remediation) [4](#0-3) . If a frozen account can still be drained through the receivership (liquidation) or order-execution code path by an arbitrary unprivileged signer, an attacker (or a colluding/opportunistic liquidator) can move value out of an account the admin explicitly intended to lock down, undermining the safety-freeze control and causing unauthorized state mutation with financial effect — consistent with the "High: unauthorized state mutation or bypass of safety freeze with financial effect" impact category.

### Likelihood Explanation
- Freezing itself is admin-gated, but entering `ACCOUNT_IN_RECEIVERSHIP` (liquidation) or `ACCOUNT_IN_ORDER_EXECUTION` (order keeper execution) are both public, unprivileged, and reachable at any time an account is unhealthy or has a pending order — independent of the freeze action.
- An admin cannot prevent a frozen account from becoming unhealthy or having pending orders execute; freezing does not itself pause health checks, liquidation eligibility, or pending orders.
- The exploit requires no special privilege beyond being a normal liquidator/keeper, and it is entirely plausible for a frozen account (e.g., one flagged for a suspected exploit or compromised key) to still be liquidatable or have orders pending, which is exactly the "same-slot sequence that freezes and then attempts a value-moving action" scenario described.

### Recommendation
Reorder `is_signer_authorized` so the frozen check takes priority (or is at minimum evaluated) over the receivership/order-execution short-circuits, or explicitly encode the intended policy (e.g., "frozen blocks everyone except admin, regardless of receivership/order-execution state" — or, if third-party liquidation/order-execution during freeze is intentional, document this explicitly and add tests asserting the exact intended matrix of `ACCOUNT_FROZEN` × `ACCOUNT_IN_RECEIVERSHIP` × `ACCOUNT_IN_ORDER_EXECUTION`). At minimum:
```rust
pub fn is_signer_authorized(...) -> bool {
    if marginfi_account.get_flag(ACCOUNT_FROZEN) {
        return group_admin == signer;
    }
    if allow_receivership && marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP) {
        return marginfi_account.authority != signer;
    }
    if allow_order_execution && marginfi_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION) {
        return true;
    }
    marginfi_account.authority == signer
}
```
This ensures freeze semantics take precedence over all other value-moving authorization paths, per the documented invariant.

### Proof of Concept
Integration test plan (Rust, `programs/marginfi/tests`):
1. Create victim marginfi account, deposit collateral, borrow to make it liquidatable (reuse setup similar to `liquidate_receiver_same_authority_withdraw_fails_unauthorized`) [7](#0-6) .
2. As admin, call `set_account_freeze(true)` on the victim account [8](#0-7) ; assert `ACCOUNT_FROZEN` set.
3. Make the account unhealthy and start liquidation via `make_start_liquidation_ix` to set `ACCOUNT_IN_RECEIVERSHIP` (reuse pattern from `liquidate_receiver_same_authority_withdraw_fails_unauthorized`) [9](#0-8) .
4. Have an unrelated keypair (not admin, not victim authority) sign `lending_account_withdraw` (`make_bank_withdraw_ix` with `authority = attacker_keypair`) against the victim's frozen+receivership account.
5. Assert the transaction **succeeds** (currently) instead of returning `MarginfiError::AccountFrozen`/`Unauthorized` — demonstrating the bypass.
6. Repeat with `ACCOUNT_IN_ORDER_EXECUTION` set instead of receivership, using the order-execution flow, and assert the same bypass.
7. Expected fix assertion after patch: both attempts return `MarginfiError::AccountFrozen` (or `Unauthorized`), confirming freeze now takes precedence.

```rust
pub fn set_account_freeze(ctx: Context<SetAccountFreeze>, frozen: bool) -> MarginfiResult {
    let group = ctx.accounts.group.load()?;
    check_eq!(
        group.admin,
        ctx.accounts.admin.key(),
        MarginfiError::Unauthorized
    );
    let mut marginfi_account = ctx.accounts.marginfi_account.load_mut()?;
    if frozen {
        marginfi_account.set_flag(ACCOUNT_FROZEN, true);
    } else {
        marginfi_account.unset_flag(ACCOUNT_FROZEN, true);
    }
    marginfi_account.last_update = Clock::get()?.unix_timestamp as u64;
```
