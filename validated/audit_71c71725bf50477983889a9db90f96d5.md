Audit Report

## Title
`process_delivery_receipt` ignores the on-chain `success` flag from Ethereum and always pays relayer reward - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
The Snowbridge V2 outbound queue pallet decodes a `DeliveryReceipt` from an Ethereum `InboundMessageDispatched` event log that carries an explicit `success: bool` field, but `Pallet::process_delivery_receipt` never inspects this field before paying the relayer reward and clearing the pending order. As a result, a relayer can be paid and the order settled even when the Ethereum-side message execution actually failed.

## Finding Description
`DeliveryReceipt` is decoded via `TryFrom<&Log>` from the Solidity event `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)`, faithfully preserving `success` in the Rust struct [4](#0-3) . The extrinsic `submit_delivery_receipt` verifies the proof and decodes the receipt, then forwards it directly to `process_delivery_receipt` [5](#0-4) . `process_delivery_receipt` checks the gateway address, resolves the reward account and pending order by nonce, and unconditionally pays `T::RewardPayment::register_reward` whenever `order.fee > 0`, then removes the `PendingOrders` entry and emits `MessageDelivered` — at no point is `receipt.success` read or checked [3](#0-2) . The `T::Verifier::verify` step only attests that the event log genuinely exists in a proven Ethereum transaction receipt; it says nothing about the boolean value carried in that log's `success` field, so a message that legitimately failed on the Gateway (e.g., inner command reverted) still produces a provable log with `success = false` that passes verification.

## Impact Explanation
Any relayer holding a valid, provable log for a message with `success = false` still collects the full `order.fee` reward via `T::RewardPayment::register_reward`, and the `PendingOrders[nonce]` entry is permanently removed regardless of the actual outcome. This is an unbacked/incorrect payout condition — reward disbursement independent of whether the message was actually delivered/executed correctly — violating the invariant that bridge payout state must only advance after settlement actually succeeds.

## Likelihood Explanation
High. `submit_delivery_receipt` is a public, unprivileged extrinsic reachable by any signed account with a legitimate Ethereum receipt proof for a nonce still pending in `PendingOrders`. No colluding validators, leaked keys, or privileged actors are required — a message legitimately failing on Ethereum (e.g., a command reverting due to insufficient gas or a bad target call) is a normal, non-adversarial occurrence that triggers this bug path.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `success == true`. When `success == false`, still resolve/clear the `PendingOrders` entry through a distinct failure path (e.g., re-queue, slash, or no-reward settlement) but must not pay the relayer reward. Emit a distinguishable event (e.g., `MessageDelivered { success: bool }` or a separate failure event) so downstream consumers can react appropriately.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce]` with `fee > 0` [6](#0-5) .
2. On Ethereum, the Gateway contract dispatches the message but the inner command execution fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds an `EventProof` for this log and calls `submit_delivery_receipt`; `T::Verifier::verify` succeeds since the log genuinely exists, and `DeliveryReceipt::try_from` decodes `success = false` correctly.
4. `process_delivery_receipt` is invoked; since `receipt.success` is never read, it pays `order.fee` to `reward_account` and removes `PendingOrders[nonce]`, emitting `MessageDelivered { nonce }` exactly as if delivery had succeeded [7](#0-6) .

		pub fn process_delivery_receipt(

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
