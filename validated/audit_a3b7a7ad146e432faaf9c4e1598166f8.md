### Title
Missing `ALLOW_CANCEL_ALL_UNFREEZE_V2` / `UnfreezeDelayDays` committee-gate check in TVM `CANCELALLUNFREEZEV2` opcode path - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/CancelAllUnfreezeV2Processor.java`)

### Summary
The normal-transaction path for cancelling all pending unfreezes, `CancelAllUnfreezeV2Actuator.validate()`, explicitly requires `dynamicStore.supportAllowCancelAllUnfreezeV2()` to be true before allowing the operation [2](#0-1) . `supportAllowCancelAllUnfreezeV2()` requires both the `ALLOW_CANCEL_ALL_UNFREEZE_V2` committee proposal to be enabled *and* `getUnfreezeDelayDays() > 0` [3](#0-2) . However, the equivalent smart-contract-triggerable path, `CancelAllUnfreezeV2Processor.validate()` (invoked from the TVM opcode `CANCELALLUNFREEZEV2` via `Program.cancelAllUnfreezeV2Action()`), performs only address/account-existence checks and never checks `supportAllowCancelAllUnfreezeV2()` or `getUnfreezeDelayDays()` [4](#0-3) .

### Finding Description
This is the same bug class as the report: a "guard" that gates a state-changing balance/resource operation is present on one code path but missing on a sibling path that performs the identical mutation. In the external report, `cancelInv()` lacked `whenNotPaused()` while presumably related order functions had it. Here, `CancelAllUnfreezeV2Processor.execute()` performs the exact same mutation as `CancelAllUnfreezeV2Actuator.execute()` — clearing `unfrozenV2List`, crediting expired amounts back to balance, and re-adding frozen resource weight [5](#0-4)  vs. [6](#0-5)  — but the TVM opcode entry point is gated only by the generic `allowTvmFreezeV2` hard-fork flag at the opcode-table level [1](#0-0) , not by the dedicated `ALLOW_CANCEL_ALL_UNFREEZE_V2` proposal/`UnfreezeDelayDays` feature toggle that governs whether this specific behavior should be reachable at all.

Because `allowTvmFreezeV2` (enabling `FREEZEBALANCEV2`/`UNFREEZEBALANCEV2`/`WITHDRAWEXPIREUNFREEZE`/`CANCELALLUNFREEZEV2` opcodes) can be active on a network/fork stage where the committee has not yet separately enabled `ALLOW_CANCEL_ALL_UNFREEZE_V2` (which per `ProposalUtil` additionally requires `UNFREEZE_DELAY_DAYS` to already be approved) [7](#0-6) , a contract calling the `CANCELALLUNFREEZEV2` opcode can bypass the committee's intended feature rollout gate that the regular transaction actuator enforces.

### Impact Explanation
If `ALLOW_CANCEL_ALL_UNFREEZE_V2`/`UnfreezeDelayDays` is not yet enabled by committee (feature intentionally disabled network-wide), any deployed contract can still invoke the `CANCELALLUNFREEZEV2` opcode (as long as `allowTvmFreezeV2` is on) and force-cancel all pending unfreezes for the calling contract account, immediately crediting expired-unfreeze balances and restoring frozen resource weight. This circumvents the committee-controlled feature-activation mechanism designed to control rollout of this balance/resource-affecting operation, and can produce state divergent from the intended un-freeze-delay lifecycle (e.g., before delayed-unfreeze semantics are fully rolled out), amounting to unauthorized manipulation of an account's frozen/unfrozen balance accounting via a path that should be blocked.

### Likelihood Explanation
Likelihood is moderate: it requires `allowTvmFreezeV2` to be active while `ALLOW_CANCEL_ALL_UNFREEZE_V2`/`UnfreezeDelayDays` is not, which is a specific but plausible transitional/misconfiguration state during network upgrades, since the two flags are toggled independently by separate committee proposals.

### Recommendation
Add the same `supportAllowCancelAllUnfreezeV2()` (i.e., `ALLOW_CANCEL_ALL_UNFREEZE_V2` and `UnfreezeDelayDays > 0`) check to `CancelAllUnfreezeV2Processor.validate()`, mirroring `CancelAllUnfreezeV2Actuator.validate()`, so both entry points enforce the identical committee-controlled feature gate.

### Proof of Concept
1. Configure a node/testnet where `allowTvmFreezeV2` (hard fork gating `FREEZEBALANCEV2`/`CANCELALLUNFREEZEV2` opcodes) is enabled, but the committee has not passed `ALLOW_CANCEL_ALL_UNFREEZE_V2` (i.e., `dynamicStore.getAllowCancelAllUnfreezeV2()` returns 0, or `UnfreezeDelayDays` is 0).
2. Deploy a contract that freezes balance via `FREEZEBALANCEV2`, then unfreezes it via `UNFREEZEBALANCEV2` to populate `unfrozenV2List`.
3. From the contract, invoke the `CANCELALLUNFREEZEV2` opcode (exposed via `Program.cancelAllUnfreezeV2Action()`).
4. Observe that `CancelAllUnfreezeV2Processor.validate()`/`execute()` succeed and mutate the account's frozen/unfrozen state and balance, despite `CancelAllUnfreezeV2Actuator.validate()` rejecting the equivalent normal transaction with `"Not support CancelAllUnfreezeV2 transaction, need to be opened by the committee"` [8](#0-7) , confirming the guard bypass via the TVM opcode path.

  public Map<String, Long> execute(CancelAllUnfreezeV2Param param, Repository repo) throws ContractExeException {
    Map<String, Long> result = new HashMap<>();
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long withdrawExpireBalance = 0L;
    for (Protocol.Account.UnFreezeV2 unFreezeV2: ownerCapsule.getUnfrozenV2List()) {
      if (unFreezeV2.getUnfreezeExpireTime() > now) {
        String resourceName = unFreezeV2.getType().name();
        result.put(resourceName, result.getOrDefault(resourceName, 0L) + unFreezeV2.getUnfreezeAmount());

        updateFrozenInfoAndTotalResourceWeight(ownerCapsule, unFreezeV2, repo);
      } else {
        // withdraw
        withdrawExpireBalance += unFreezeV2.getUnfreezeAmount();
      }
    }
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }
    ownerCapsule.clearUnfrozenV2();

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);

    result.put(VMConstant.WITHDRAW_EXPIRE_BALANCE, withdrawExpireBalance);
    return result;
