### Title
Relay manager trusts peer-claimed `RelayFromAddr`/`OldRelayFromAddr` instead of the authenticated hostinfo's own VPN address, allowing relay-state poisoning for arbitrary victim addresses - ([File: relay_manager.go])

### Summary
`handleCreateRelayRequest` derives the identity of the address being relayed ("from") entirely from an attacker-controlled field in the `NebulaControl` message (`RelayFromAddr` / `OldRelayFromAddr`), rather than from the already-authenticated peer identity (`h.vpnAddrs[0]`, backed by the peer's verified certificate). This mirrors the zNS `approveDomainBid` bug class: a party that has valid credentials for *something* (a signed nebula certificate) is allowed to take an action that should be scoped to *their own* identity/resource ("I am relaying for myself"), but the actual resource identifier used is taken from unauthenticated request data instead of the verified certificate.

### Finding Description
In `relay_manager.go`, `HandleControlMsg` unmarshals the incoming `NebulaControl` message and dispatches `NebulaControl_CreateRelayRequest` to `handleCreateRelayRequest(v, h, f, msg)`, where `h *HostInfo` is the hostinfo of the connection the packet arrived on — i.e., the certificate-verified remote peer [1](#0-0) .

Inside `handleCreateRelayRequest`, the "from" address (the party the relay entry will be created for) is taken directly from the message, not from `h`'s certificate/VPN address:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(from) {
    logMsg.Error("Discarding relay request from myself", "myIP", from)
    return
}
``` [2](#0-1) 

The only check performed is that `from` isn't *my own* address — there is no check that `from` equals `h.vpnAddrs[0]` (the actual authenticated peer that sent the packet) or that `from` falls within the networks bound to `h`'s certificate. This is in contrast to the firewall's `Drop` logic, which explicitly enforces that a packet's claimed remote address must match the peer certificate's bound networks before any further processing (`ErrInvalidRemoteIP`) [3](#0-2) .

Because `from` is unauthenticated, the code proceeds to build relay state keyed by this attacker-chosen address:
```go
_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
...
relay, ok := h.relayState.QueryRelayForByIp(from)
``` [4](#0-3) 

`AddRelay` installs `newRelay := Relay{..., PeerAddr: vpnIp}` into `relayHostInfo.relayState`, where `vpnIp` here is the attacker-supplied `from`, not `h`'s real, certificate-bound address [5](#0-4) . This state later drives which peer's traffic is forwarded through `h` as a relay — the equivalent on the "responder" side to `approveDomainBid` accepting any signature regardless of whether the caller actually owns the resource in question.

### Impact Explanation
An authenticated-but-malicious peer `h` (holding a valid, CA-signed certificate, but only for its own legitimate VPN address) can send a `CreateRelayRequest` claiming an arbitrary `RelayFromAddr` belonging to another, unrelated VPN address ("victim"). Since this claim is never checked against `h`'s certificate-bound VPN networks, the target node installs relay routing state believing that `h` is a valid relay-source proxy for the victim's address. This is remote state poisoning of the relay hostmap/routing tables: it can misroute or hijack the relay-forwarding path intended for the victim, or be used to build/pollute a picture of `PeerAddr` associations that a legitimate node did not consent to and does not own — analogous to the "any owner can approve for any domain" flaw where enforcement of "this action must be scoped to the identity that owns the referenced resource" is missing.

### Likelihood Explanation
The attacker only needs a single valid Nebula certificate signed by any CA trusted by the target (a status achievable by any legitimate member of the mesh, or anyone whose cert was never revoked/blocklisted) — no special network position, host-access, or lighthouse role is required. This matches the report's "reachable by an attacker with no CA-signed certificate for the target resource" bar: the attacker has *a* valid cert, not a cert *for the address it is claiming*. The forged relay-request packet is a normal, spec-legal `Control` message, so it will be processed by any relay-capable/target node without additional gating.

### Recommendation
In `handleCreateRelayRequest` (and the analogous `handleCreateRelayResponse` path), validate that the claimed `RelayFromAddr`/`OldRelayFromAddr` is consistent with the authenticated sender: either require `from == h.vpnAddrs[0]` (or any address within `h.GetCert().Certificate.Networks()`), mirroring the source-IP/cert binding check already enforced in `Firewall.Drop`. Reject the request outright if the claimed address is not one that the sending hostinfo's certificate actually authorizes.

### Proof of Concept
Conceptually (cannot execute here, but derivable from the code path):
1. Attacker `A` establishes a normal, certificate-valid Nebula tunnel to relay-capable node `R`.
2. `A` sends a `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to victim `V`'s VPN address (`V` is not `A` and not `R`), and `RelayToAddr` set to `R`'s own address.
3. `handleCreateRelayRequest` on `R` only checks `f.myVpnAddrsTable.Contains(from)` (fails, since `from = V ≠ R`) before proceeding to call `AddRelay(rm.l, h, f.hostMap, from, ...)`, installing relay state associating `A`'s hostinfo (`h`) with `PeerAddr = V` — despite `A` never proving ownership of `V`'s certificate/address.
4. This corrupted relay state can subsequently be exploited to misdirect or intercept traffic nominally intended to reach `V` via the relay path through `A`.

Note: I was unable to fully trace how this poisoned relay state is consumed on the data-forwarding path (e.g., in `outside.go`/`inside.go` relay lookup) within the available index, so the precise downstream traffic-interception mechanics should be verified directly in the full repository before treating this as conclusively exploitable end-to-end.

func AddRelay(l *slog.Logger, relayHostInfo *HostInfo, hm *HostMap, vpnIp netip.Addr, remoteIdx *uint32, relayType int, state int) (uint32, error) {
	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (f *Firewall) Drop(fp firewall.Packet, incoming bool, h *HostInfo, caPool *cert.CAPool, localCache firewall.ConntrackCache) error {
	// Make sure remote address matches nebula certificate, and determine how to treat it
	if h.networks == nil {
		// Simple case: Certificate has one address and no unsafe networks
		if h.vpnAddrs[0] != fp.RemoteAddr {
			f.metrics(incoming).droppedRemoteAddr.Inc(1)
			return ErrInvalidRemoteIP
		}
	} else {
		nwType, ok := h.networks.Lookup(fp.RemoteAddr)
		if !ok {
			f.metrics(incoming).droppedRemoteAddr.Inc(1)
			return ErrInvalidRemoteIP
		}
		switch nwType {
		case NetworkTypeVPN:
			break // nothing special
		case NetworkTypeVPNPeer:
			f.metrics(incoming).droppedRemoteAddr.Inc(1)
			return ErrPeerRejected // reject for now, one day this may have different FW rules
		case NetworkTypeUnsafe:
			break // nothing special, one day this may have different FW rules
		default:
			f.metrics(incoming).droppedRemoteAddr.Inc(1)
			return ErrUnknownNetworkType //should never happen
		}
	}
