### Title
Cost-Aware Admission bypass lets clients under-report actual RPC resource consumption via `x-gitaly-cost` - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
The `x-gitaly-cost` trailer, which Rails/Workhorse translate into the `X-Score` header for upstream (Cloudflare) rate limiting, is computed from a static per-RPC-type weight plus a dynamic component derived only from gRPC `InPayload`/`OutPayload` byte counts [1](#0-0) . Like the GroupBuy bug where `claim()` assumed the NFT was bought at `minReservePrices[_poolId]` when it could actually be bought cheaper, `computeCost` assumes gRPC payload bytes are a faithful proxy for the real resource cost of the RPC. For the Git smart-HTTP/SSH RPCs that dominate actual server load (`PostUploadPackWithSidechannel`, `PostReceivePack`, `SSHUploadPack`, etc.), the heavy data transfer happens over the sidechannel/raw socket, not as gRPC `InPayload`/`OutPayload` messages, so the dynamic component under-counts the true bytes moved and CPU/IO spent, while these RPCs also get a flat +10 static bonus regardless of how large the actual clone/fetch/push is [2](#0-1) .

### Finding Description
`computeCost` derives the reported cost purely from `static := staticCostForMethod(fullMethod)` and `dynamic := dynamicCostFromContext(ctx)`, and `dynamicCostFromContext` sums `InPayloadBytes + OutPayloadBytes` collected by `grpcstats.PayloadBytes` from the standard gRPC `stats.InPayload`/`stats.OutPayload` events [3](#0-2) . The doc explicitly acknowledges the static score "hides variance (e.g. `PostUploadPackWithSidechannel` is the same cost whether it serves 1 MB or 10 GB)" and states dynamic cost is meant to compensate [4](#0-3) . But the sidechannel-based RPCs stream the actual pack data out-of-band through a side connection, not through the gRPC message stream that `PayloadBytes` instruments — so for exactly the RPC class the doc calls out as variable-cost, the dynamic term stays near zero regardless of how many gigabytes are transferred, leaving the reported cost pinned close to the fixed `staticCostOverrides` value (10). An unprivileged client can therefore drive arbitrarily large clones/fetches/pushes while the `x-gitaly-cost` trailer — and the derived `X-Score` header used by Rails/Workhorse/Cloudflare for complexity-based rate limiting — reports a cost far below the actual load imposed, defeating the very purpose of this signal-export layer described in `doc/load-management-architecture.md`.

### Impact Explanation
This is directly analogous to the GroupBuy accounting bug: a downstream consumer (Rails/Cloudflare's complexity-based rate limiter) trusts a value (`x-gitaly-cost`/`X-Score`) that is supposed to track real consumption but is computed from a proxy that can diverge sharply from the real cost for the most expensive RPC class. The result is a resource-accounting/DoS-relevant flaw: an attacker (any git client performing clones/pushes) can consistently cause Gitaly to under-report its true cost for exactly the workloads (`git-upload-pack`, `git-receive-pack` traffic) that are most expensive, weakening upstream rate limiting/circuit-breaking that is supposed to throttle abusive traffic, in the same spirit as the underlying accounting mismatch in the reported bug class. This affects `RPC-handler resource limits`, an explicitly in-scope category.

### Likelihood Explanation
Every clone, fetch, or push through `PostUploadPackWithSidechannel`, `PostReceivePack`, `SSHUploadPack(WithSidechannel)`, or `SSHReceivePack` triggers this path unconditionally — no special privilege or crafted RPC field is required beyond issuing ordinary Git operations, which is the normal traffic Gitaly serves from arbitrary users. The mismatch is deterministic and reproducible on every such call given the current architecture (sidechannel bytes are outside the gRPC message layer instrumented by `grpcstats.PayloadBytes`).

### Recommendation
Compute the dynamic cost component from actual bytes transferred over the git sidechannel/process pipes (as already tracked elsewhere, e.g. `internal/git/stats` packet/byte counters) rather than solely from gRPC message-layer `InPayload`/`OutPayload`, at least for the RPCs in `staticCostOverrides` that use sidechannels. Alternatively, feed real bytes-transferred counts (already available from BurdenMonitor/`git/stats`) into `dynamicCostFromContext` so `x-gitaly-cost` reflects true payload size for large clones/pushes, restoring the intended correlation between reported cost and actual server load.

### Proof of Concept
1. As an unauthenticated-but-permitted git client, perform `git clone` (or `git push`) of a very large repository (multi-GB) against a Gitaly node, invoking `PostUploadPackWithSidechannel`/`PostReceivePack`.
2. Because the pack data flows over the sidechannel connection rather than as gRPC `InPayload`/`OutPayload`, `grpcstats.PayloadBytes.HandleRPC` records only the small negotiation pkt-lines exchanged over the gRPC stream, not the multi-GB packfile [5](#0-4) .
3. `dynamicCostFromContext` therefore returns a near-zero value even though gigabytes were transferred and significant CPU/IO was consumed [6](#0-5) .
4. The `x-gitaly-cost` trailer returned is `staticCostOverrides["/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"] (=10) + ~0`, identical to what a tiny 1-object clone would report, confirmed by the test comment in `costhandler_test.go` line 61-63 showing cost `10` for an RPC with no stats in context at all [7](#0-6) . Repeating this at scale lets a client generate large repeated resource consumption while consistently reporting low cost to the upstream rate limiter that gates on `X-Score`.

// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}

// HandleRPC implements per-RPC tracing and stats instrumentation.
func (s *PayloadBytes) HandleRPC(ctx context.Context, rs stats.RPCStats) {
	switch st := rs.(type) {
	case *stats.InPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.InPayloadBytes += int64(st.Length)
	case *stats.OutPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.OutPayloadBytes += int64(st.Length)
	}
}
