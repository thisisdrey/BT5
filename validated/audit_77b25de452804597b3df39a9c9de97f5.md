## Title
Stale signer/slot bindings survive StackerDB reconfiguration when the reloaded config has an empty signer set - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`StackerDBs::create_or_reconfigure_stackerdbs` skips calling `reconfigure_stackerdb` whenever the freshly-loaded config has an empty `signers` list, even though the local sqlite replica for that contract still has slots bound to a previously authorized signer. Because the actual slot→signer binding used to authenticate incoming chunks (`get_slot_signer`) is only updated inside `reconfigure_stackerdb`, an already-registered writer keeps write authority over a StackerDB slot after the authoritative on-chain signer set for that slot has been emptied out (via legitimate governance action or a transient/adversarial contract-read failure).

### Finding Description
`create_or_reconfigure_stackerdbs` loads the new config for each subscribed StackerDB contract and decides whether to call `reconfigure_stackerdb`: [1](#0-0) 

The guard `new_config != stackerdb_config && !new_config.signers.is_empty()` means that if the newly loaded config's `signers` vector is empty, the branch is never taken and `reconfigure_stackerdb` (which rewrites the `chunks` table's `signer` column for slots whose owner changed, per `StackerDBTx::reconfigure_stackerdb`) is never invoked: [2](#0-1) 

`signers` becomes empty in two remotely-influenceable situations:
1. The StackerDB contract's `stackerdb-get-signer-slots` legitimately returns an empty list (e.g., governance/contract logic revokes all signer slots).
2. `StackerDBConfig::from_smart_contract` fails to parse/evaluate the contract (any `net_error`, e.g. `InvalidStackerDBContract`), in which case the code falls back to `StackerDBConfig::noop()`, whose `signers` field is also empty: [3](#0-2) [4](#0-3) 

In both cases the persisted `chunks` table for that `stackerdb_id` retains its previous `signer` column values. Chunk authorization for writes and for validating pushed/downloaded data is done purely against this persisted binding via `get_slot_signer`, used in `validate_received_chunk`: [5](#0-4) 

Thus the stale, previously-legitimate signer can continue submitting higher-version chunks that pass `try_replace_chunk`/`validate_received_chunk` (the version/max-writes/size checks reference the *old* config or DB state, not "no signers authorized"), and those chunks are relayed/gossiped by this node's replica to its peers as legitimate StackerDB content — exactly analogous to the reported `_marketWeightsByToken` issue, where removing an authorization record left a stale mapping entry that could still be exercised.

### Impact Explanation
This is an unauthorized write to replicated state and propagation of stale/forged-authority data: a signer whose write authority for a slot has been revoked (signers list emptied) can keep writing to, and have the network keep relaying, chunks for that slot as if still authorized, because the local binding used for authentication was never cleared. This matches the "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data" Critical-impact category.

### Likelihood Explanation
Reaching an empty `signers` config does not require an admin role — it can occur through the ordinary contract-driven config refresh path in `create_or_reconfigure_stackerdbs`/`refresh_stacker_db_configs`, and additionally through the `unwrap_or_else(|e| ... StackerDBConfig::noop())` fallback taken on *any* failure to read/parse the StackerDB config from the smart contract, which is a broader and more easily triggered condition than the original report's "re-added after governance removes it" scenario.

### Recommendation
When the reloaded config's `signers` is empty (or otherwise indicates the DB should be cleared/de-authorized), explicitly clear the persisted slot bindings (e.g. call `clear_stackerdb_slots`/reset all slot signer entries) instead of silently skipping reconfiguration, so no previously-authorized signer retains write ability once the authoritative signer set no longer includes them. At minimum, distinguish "config unchanged" from "config load failed" so a transient read failure can never be treated the same as an intentional retention of the existing binding.

### Proof of Concept
1. Deploy/subscribe to a StackerDB contract `SC` whose `stackerdb-get-signer-slots` initially returns `[(attacker_addr, 1)]`; the node calls `create_stackerdb`, allocating slot 0 to `attacker_addr`.
2. Attacker signs and pushes a chunk to slot 0; it is accepted since `get_slot_signer(SC, 0) == attacker_addr`.
3. The contract (or a transient evaluation failure) causes `stackerdb-get-signer-slots` to now report an empty list — `new_config.signers.is_empty()` is true, so per `stackslib/src/net/stackerdb/mod.rs:414` `reconfigure_stackerdb` is never called; slot 0's stored `signer` column stays `attacker_addr`.
4. Attacker continues to push higher-version chunks for slot 0; `validate_received_chunk`/`try_replace_chunk` still succeed because they check `get_slot_signer`/the DB's persisted `SlotValidation`, not the current authoritative (now-empty) signer set, and those chunks are stored and relayed by the node's replica.

    pub fn noop() -> StackerDBConfig {

            // `noop()` is used as a fallback whenever a replica's real config can't be

            write_freq: 0,
            max_writes: u32::MAX,
            hint_replicas: vec![],
            max_neighbors: 8,
            signers: vec![],
        }
    }

    /// Update a database's storage slots, e.g. from new configuration state in its smart contract.
    /// Chunk data for slots that no longer exist will be dropped.
    /// Newly-created slots will be instantiated with empty data.
    /// If the address for a slot changes, then its data will be dropped.
    pub fn reconfigure_stackerdb(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slots: &[(StacksAddress, u32)],
    ) -> Result<(), net_error> {
        let stackerdb_id = self.get_stackerdb_id(smart_contract)?;
        let mut total_slots_read = 0u32;
        for (principal, slot_count) in slots.iter() {
            total_slots_read =
                total_slots_read
                    .checked_add(*slot_count)
                    .ok_or(net_error::OverflowError(
                        "Slot count exceeeds u32::MAX".to_string(),
                    ))?;
            let slots_before_principal = total_slots_read - slot_count;
            for cur_principal_slot in 0..*slot_count {
                let slot_id = slots_before_principal + cur_principal_slot;
                if let Some(existing_validation) =
                    self.get_slot_validation(smart_contract, slot_id)?
                {
                    // this slot already exists.
                    if existing_validation.signer == *principal {
                        // no change
                        continue;
                    }
                }

                debug!("Reset slot {} of {}", slot_id, smart_contract);

                // new slot, or existing slot with a different signer
                let qry = "INSERT OR REPLACE INTO chunks (stackerdb_id,signer,slot_id,version,write_time,data,data_hash,signature) VALUES (?1,?2,?3,?4,?5,?6,?7,?8)";
                let mut stmt = self.sql_tx.prepare(qry)?;
                let args = params![
                    stackerdb_id,
                    principal.to_string(),
                    slot_id,
                    NO_VERSION,
                    0,
                    vec![],
                    Sha512Trunc256Sum([0u8; 32]),
                    MessageSignature::empty(),
                ];

                stmt.execute(args)?;
            }
        }
        debug!("Shrink {} to {} slots", smart_contract, total_slots_read);
        self.shrink_stackerdb(stackerdb_id, total_slots_read)?;
        Ok(())
    }
