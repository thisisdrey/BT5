### Title
Unbudgeted Pyth oracle fee causes protocol-wide DoS of borrow/withdraw/liquidate operations - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
The `write-feed`/`write-feeds` helpers in `v0-4-market.clar` call the external `pyth-oracle-v4` contract's `verify-and-update-price-feeds` to refresh price data whenever a caller supplies `price-feeds` (used by `supply-collateral-add` and other user-facing entry points). That external contract charges a fee (`stx-transfer? fee-amount tx-sender (get address fee-info)`) that is entirely controlled by Pyth's cross-chain governance (`pyth-governance-v3::update-fee-value`), not by Zest. The market contract does not budget, cap, or verify this fee before calling out, exactly mirroring the reported "ignore external call fee" bug class (Wormhole `publishMessage` fee assumption) — an unpredictable, externally-governed fee on a required external call that the caller code assumes to be zero/negligible.

### Finding Description
`write-feed` in `mainnet/contracts/market/v0-4-market.clar` performs a bare `contract-call?` to the hardcoded mainnet Pyth oracle address, with no STX forwarded and no fee check: [1](#0-0) 

That callee, `pyth-oracle-v4::verify-and-update-price-feeds`, computes a fee from `pyth-governance-v3::get-fee-info` and unconditionally debits it from `tx-sender` (the original transaction signer, which is the same account invoking the Zest market function, since the call is not wrapped in `as-contract`): [2](#0-1) 

The fee value itself is fully governed off-protocol, by Pyth guardians via a VAA processed in `pyth-governance-v3::update-fee-value`, which simply overwrites `fee-value` with whatever mantissa/exponent the VAA specifies — Zest has no control over or cap on this: [3](#0-2) 

If a required price update fails (e.g., insufficient STX balance to cover a suddenly-increased fee, or a post-condition-restricted transaction that didn't anticipate the fee debit), `write-feed` propagates the failure as `ERR-PRICE-FEED-UPDATE-FAILED`, aborting the entire market operation: [4](#0-3) [5](#0-4) 

This directly parallels the external report's root cause: an external, fee-charging call (`wormhole.publishMessage` there, `pyth-oracle-v4.verify-and-update-price-feeds` here) whose fee is set by a third party and can change at any time, while the calling contract assumes it stays at (or near) zero and does not budget for it.

### Impact Explanation
When Pyth's guardians raise `fee-value` beyond what users implicitly budget for (they never explicitly approve this STX transfer amount when constructing borrow/withdraw/liquidate transactions), price-feed refresh calls fail, and any operation in `v0-4-market.clar` that depends on a fresh price (borrow, collateral withdrawal, liquidation via `price-resolve`/`resolve-pyth`) reverts with `ERR-PRICE-FEED-UPDATE-FAILED` once cached prices go stale (`oracle-timestamp-fresh` check). This is a temporary freezing of funds: users cannot borrow, withdraw collateral, or have positions liquidated normally, since the market cannot refresh oracle prices without user-side STX being silently spent on an unbounded, externally-set fee.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires Pyth's guardian network to actually raise the fee value via a valid governance VAA, which is outside Zest's or an attacker's control (this mirrors the original report's own "Likelihood: 1" rating). No malicious on-chain action by an ordinary principal is needed to trigger it — it's a latent design gap that manifests only if the third-party fee changes.

### Recommendation
Have `v0-4-market.clar`'s `write-feed` read `pyth-governance-v3::get-fee-info`/expected fee before calling `verify-and-update-price-feeds`, enforce a maximum acceptable fee (configurable by Zest governance), and/or wrap the STX fee payment in an explicit, bounded transfer from the market/user with clear post-conditions rather than relying on an implicit `tx-sender` debit inside the external contract. Alternatively, cache fee assumptions and fail gracefully (skip feed refresh, fall back to last valid cached price within staleness bounds) rather than reverting the entire user operation.

### Proof of Concept
1. Pyth guardians submit a VAA via `pyth-governance-v3::update-fee-value` raising `fee-value` to a large mantissa/exponent (this contract has no cap on the value it accepts).
2. A user calls `supply-collateral-add` (or any market function accepting `price-feeds`) on `v0-4-market.clar`, supplying a Pyth price update buffer to refresh a stale price, as required by `oracle-timestamp-fresh`.
3. `write-feed` calls `.pyth-oracle-v4 verify-and-update-price-feeds`, which now computes a much larger `fee-amount` and calls `stx-transfer? fee-amount tx-sender fee-recipient`.
4. If `tx-sender` lacks sufficient STX or the transaction's post-conditions don't allow this now-large, previously negligible transfer, the call errors with `ERR_BALANCE_INSUFFICIENT`, `write-feed` returns `ERR-PRICE-FEED-UPDATE-FAILED`, and the entire market transaction reverts — freezing the user's ability to complete borrow/withdraw/liquidate operations that require a fresh oracle price.
