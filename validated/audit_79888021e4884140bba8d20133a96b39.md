Audit Report

## Title
Documented replay-safety invariant ("era shorter than `LockPeriod`") is never enforced on-chain in `pallet-scarcity`'s `AsScarcity` extension - (File: substrate/frame/scarcity/src/extension.rs)

## Summary
`pallet-scarcity`'s docs assert that signers must use mortal transactions with an era shorter than `Config::LockPeriod` so that a failed-and-locked authorization can never be replayed by a third party once the lock expires. `AsScarcity::validate` never inspects `DispatchInfoOf` or any era/mortality information and never compares it to `T::LockPeriod::get()`; it only checks `Locked::<T>::get(&owner)` against `now` and NFT `instance`/`state_nonce` equality, so the documented guarantee is not enforced in code.

## Finding Description
`AsScarcity::validate` takes `_info: &DispatchInfoOf<...>` but discards it (prefixed with `_`), and neither `prepare` nor `post_dispatch_details` reference era or mortality data either. The only replay defenses are: (1) `Locked::<T>::get(&owner)` compared to `now` at validate time, and (2) the `(instance, state_nonce)` match, both of which are keyed on purse *state*, not on the specific signed payload's mortality window. The backoff lock in `failed_dispatch_lock` is computed purely from `T::UnixTime::now()` and `T::LockPeriod::get()`, with no linkage to the actual era length encoded in the extrinsic that triggered it.

Because Substrate mortal extrinsics can specify an arbitrary era length (up to and including immortal, via `frame_system::CheckEra`, a separate extension placed independently in the extension pipeline as shown in `service.rs`), a signer who does not personally choose an era shorter than `LockPeriod` — or a third party who retains a copy of a signed transaction with a long era — can hold a still-valid signed extrinsic that outlives the purse's failure-backoff lock. If that transaction fails once at dispatch (setting `Locked` and restoring the NFT/`state_nonce`), the extrinsic remains valid and gossipable; once the lock naturally expires (independent of the extrinsic's own era), the pool will accept a resubmission because `validate` only checks current `Locked` state and current `instance`/`state_nonce`, not the original signing era relative to `LockPeriod`. This directly contradicts the documented "fresh signing decision" property and confirms the check the docs promise simply does not exist anywhere in the enforced code path.

## Impact Explanation
This is unauthorized execution of a purse-key-authorized action (`transfer`/`burn`) against the signer's later intent: an owner who signed a transaction, saw it fail once, and no longer wants it executed (without moving the NFT to bump `state_nonce`) can have it executed anyway by any third party holding the old signed payload, once the backoff lock naturally expires. Since `AsScarcity`-authorized `transfer`/`burn` are feeless and dispatch-priority-favored public paths, this matches "unauthorized execution" against an origin-bound action with real value (NFT/purse ownership transfer).

## Likelihood Explanation
No privileged actor, governance, validator, or relayer trust is required — only an ordinary signer choosing (or failing to choose) a mortal era shorter than `LockPeriod`, or a third party who observed a broadcast transaction and holds it until the lock naturally expires. Since `validate`/`prepare`/`post_dispatch_details` never check era against `LockPeriod`, this is reachable whenever `LockPeriod` is short relative to allowed mortal eras (up to 65535 blocks) or an immortal transaction is used, both entirely plausible in normal usage since nothing forces short eras.

## Recommendation
Enforce the invariant in code: in `AsScarcity::validate`, inspect the extrinsic's mortality/era (via the checked mortality data made available to the extension, or by requiring the extension to run alongside/consume `frame_system::CheckEra`'s bound) and reject any `AsScarcity`-authorized call whose era is not strictly shorter than `T::LockPeriod::get()`. Alternatively, bind replay protection to the specific extrinsic (e.g., an extrinsic-hash-based one-time-use marker) rather than relying solely on purse `state_nonce`/lock-expiry timing.

## Proof of Concept
1. Configure a runtime with `LockPeriod = 60` seconds.
2. Owner `A` holds NFT `N` at `state_nonce = 5` and signs a mortal `transfer(to: B)` with an era far longer than 60 seconds' worth of blocks (or immortal), authorized via `AsScarcity::AsNft { instance: N, state_nonce: 5 }`.
3. The transaction fails once at dispatch (e.g., a same-block race causes `B`'s purse to become occupied at dispatch time); `post_dispatch_details` restores `N` to `A` at `state_nonce = 5` and sets `Locked::<T>::insert(A, LockInfo { retries: 1, until: now + 60 })` per `failed_dispatch_lock`.
4. `A` no longer wants this transfer and does not move the NFT again, so `state_nonce` remains `5`.
5. After 60 seconds, `Locked::<T>::get(A)` no longer blocks `validate`.
6. A third party who retained the original signed transaction (still within its long/immortal era) resubmits it; `validate` passes (instance/state_nonce still match, lock expired) and the transfer to `B` executes without `A`'s current consent, contradicting the documented "every retry is a fresh signing decision" guarantee. This can be reproduced as a unit test analogous to `failed_scarcity_transfer_is_feeless_and_retryable_after_lock` in `substrate/bin/node/runtime/src/lib.rs`, but using a long-era mortal transaction and asserting the second `dispatch_transaction` (simulating a third-party resubmission after `A`'s state_nonce is unchanged) still passes `validate` after lock expiry.

//!
//! Purse authorization is not account-nonce-based: a signed NFT transaction stays valid for as
//! long as its purse still holds the named instance at the named state nonce. Two rules bound
//! stale intent, exactly as in Coinage:

//!   re-enter a block: every retry after a failure is a fresh signing decision rather than a
