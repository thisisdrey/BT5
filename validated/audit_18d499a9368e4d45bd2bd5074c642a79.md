This gives the confirmed root cause: `AccountPermissionUpdateActuator.execute()` directly overwrites `account.updatePermissions(...)` for owner/witness/active permissions of an account, keyed only by `permissionId`, using authorization from the *Owner* permission (a separate, potentially differently-configured signer set/threshold from the Active permission being modified).

### Title
An Active permission's signing rules (keys, threshold, operations) can be altered by a separate Owner-authorized transaction after signers have begun approving a transaction, changing what an already-collected multi-sig approval authorizes - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
In Tron's multi-signature model, a transaction only references a `Permission_id` [1](#0-0)  — it does not embed the actual permission definition (keys, threshold, `operations` bitmap) that signers relied on when approving it. That definition is looked up dynamically from mutable `AccountCapsule` state via `getPermissionById(id)` both when signers add signatures and again when the transaction is finally validated at broadcast/block-application time. [2](#0-1) 

### Finding Description
When a signer calls `TransactionCapsule.addSign`, the permission used to compute the required `weight` and to run `checkPermissionOperations` is fetched live from the `AccountStore`: [3](#0-2) 

Later, when the transaction is actually applied on-chain, `validateSignature` performs the same live lookup and threshold check again: [4](#0-3) 

The `operations` bitmap that restricts which `ContractType`s a given permission may authorize is checked the same way, against whatever bitmap currently exists for that `permissionId`, via `TransactionUtil.checkPermissionOperations` / `WalletUtil.checkPermissionOperations`: [5](#0-4) [6](#0-5) 

The permission definition itself (keys, threshold, `operations`) is mutable state that can be changed at any time via `AccountPermissionUpdateContract`, processed by `AccountPermissionUpdateActuator.execute()`, which unconditionally overwrites the owner/witness/active permission list for the account: [7](#0-6) 

Critically, this update is itself authorized by the account's **Owner** permission (`permissionId == 0`), which is a distinct key set/threshold from any **Active** permission (`permissionId >= 2`) that other pending, partially- or fully-signed transactions rely on. This is structurally identical to the Llama finding: an "action" (the pending signed transaction) only names a reference (`permissionId`) to authorization semantics, and a *different* action controlled by a *different* signer set (the Owner permission holders submitting `AccountPermissionUpdateContract`) can change what that reference means — after some or all of the intended approvers have already signed — without the original signers being aware or re-consenting.

Concretely, an Active permission's `operations` bitmap or key/threshold set can be widened or altered between the time Active-permission signers begin collecting signatures on a transaction `X` and the time `X` is actually included in a block. Because validation always re-reads the *current* permission from the account store rather than pinning the permission version that existed when the approval process started, the semantics of "what does this collection of signatures actually authorize" can change out from under the signers.

### Impact Explanation
If an account's Owner-permission holders (who may be a small subset of trusted admins, or in an exchange/custody context, a separate ops team) modify an Active permission's `operations` bitmap to include additional sensitive `ContractType`s (e.g. `WitnessUpdateContract`, `ExchangeWithdrawContract`, `AccountPermissionUpdateContract`-adjacent operations, `MarketSellAssetContract`) or change its key set/threshold while Active-permission signers are still in the process of approving other transactions under that same `permissionId`, subsequently-broadcast transactions are checked only against the *new* rules. This can let a transaction pass with fewer/different real-world approvals than the original governance process for that Active permission intended, or unexpectedly authorize a broader class of on-chain operations than the Active signers agreed to when they started collecting signatures — a form of unauthorized account operation / permission-scope confusion.

### Likelihood Explanation
This is reachable by any account owner submitting two ordinary, unprivileged transactions (`AccountPermissionUpdateContract` and any multi-sig transaction referencing the affected `permissionId`) — no privileged node role, malicious SR, or network attack is required. Multi-sig custody workflows commonly have a time gap between "start collecting signatures" (via `getTransactionSignWeight`/`getTransactionApprovedList`) and final broadcast, during which an Owner-authorized permission change can land in an earlier block. [8](#0-7) 

### Recommendation
Bind the semantics a signer approves to at signing time. Options: include a hash/version of the `Permission` (keys, threshold, `operations`) in the data that gets signed (similar to including the permission content in the `transactionId` hash), or store a permission "version" on `AccountCapsule` and reject validation if the current permission version does not match the version referenced by the transaction. At minimum, `TransactionCapsule.validateSignature` and `TransactionUtil.checkPermissionOperations` should not silently re-interpret already-collected signatures against a permission definition that changed after any signature was added.

### Proof of Concept
1. Account `A` has Active permission id `2`: keys `[K1: weight 1, K2: weight 1]`, threshold `2`, `operations` bitmap allowing only `TransferContract`.
2. `K1` and `K2` begin collecting signatures for transaction `X` (a `TransferContract`) using `permissionId=2`, via `TransactionCapsule.addSign` — each call fetches the *current* permission via `account.getPermissionById(2)`.
3. Before `X` is broadcast, `A`'s Owner permission (different key set, e.g. a single admin key) submits `AccountPermissionUpdateContract` changing permission id `2`'s `operations` bitmap to also allow `ExchangeWithdrawContract`/`MarketSellAssetContract`, and/or altering its `keys`/`threshold`. This is processed by `AccountPermissionUpdateActuator.execute()`, which overwrites the permission unconditionally.
4. `K1`/`K2`'s already-collected signatures for `X` remain byte-identical (the transaction body/hash didn't change), but any *new* transaction referencing `permissionId=2` for previously-disallowed contract types now passes `checkPermissionOperations`, and `K1`/`K2` never re-approved under the new rule set — they only ever agreed to the original narrower/older permission definition.
