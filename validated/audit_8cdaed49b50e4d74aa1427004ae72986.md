### Title
`RPCGetAttachmentRequestHandler::try_handle_request` serves `AtlasDB` attachment content without verifying it hashes to the requested `attachment_hash` - ([File: stackslib/src/net/api/getattachment.rs])

### Summary
The GET `/v2/attachments/{attachment_hash}` handler parses the 40-hex-char path capture into a `Hash160` and looks up the corresponding row in `AtlasDB` via `find_attachment`, but it never recomputes `attachment.hash()` and compares it to the requested `attachment_hash` before serializing and returning the `Attachment` content as an HTTP 200 response. If the `AtlasDB` row content does not actually hash to the primary key under which it is stored (a mismatch that must be introduced through some other poisoning path, e.g. a permissive INSERT/UPDATE path), the node will happily serve arbitrary bogus content back to any caller who asks for that hash, breaking the served-versus-requested equality that attachment/BNS consumers rely on.

### Finding Description
In `try_handle_request`, the code does: [1](#0-0) 
which unconditionally wraps whatever `find_attachment(&attachment_hash)` returns into `GetAttachmentResponse { attachment }` and serializes it as the JSON body of a 200 OK response, with no assertion that `attachment.hash() == attachment_hash`. The `attachment_hash` itself is trusted only insofar as it was correctly parsed as a valid Hash160 hex string from the URL path: [2](#0-1) 

This means the endpoint's only integrity guarantee is whatever `AtlasDB` enforces at write time. If `AtlasDB`'s `attachments` table (keyed by `hash TEXT UNIQUE PRIMARY KEY` with a `content BLOB`) can ever end up with a row where `content`'s real hash does not match the `hash` column — through any insertion/update code path that does not itself recompute and check the hash before storing — this handler provides no defense-in-depth: it will retrieve and serve that mismatched content as if it correctly corresponded to the requested hash. Any BNS resolver, wallet, or indexer that queries `/v2/attachments/{hash}` and trusts the returned attachment to correspond to that hash (as the API implies) would then be fed forged/wrong zone-file or name-attachment data.

### Impact Explanation
A client fetching a specific attachment hash (e.g., to resolve a BNS name's zone file) can receive content that does not match the hash it asked for, with no client-observable error, since the response is 200 OK with well-formed JSON. This is "serving non-canonical state as canonical" for a read endpoint — matching the High severity category for attachment/BNS mismatch. It is repeatable for every subsequent GET of the same hash as long as the underlying poisoned row persists in the node's `AtlasDB`.

### Likelihood Explanation
This specific defect (missing post-fetch equality check in `getattachment.rs`) is unconditionally present in the handler and requires no attacker privilege to trigger a mismatch being served — any anonymous remote client can issue the GET request. However, the actual *root cause* of a mismatched row existing in `AtlasDB` in the first place depends on a separate, unverified write path (the "gossip poisoning" precondition referenced in the question) which was not confirmed in this investigation; the `attachments` table's `hash` column is a `UNIQUE PRIMARY KEY`, and whether any insertion code path fails to validate `content`'s hash before insert could not be fully traced with available tool budget. This handler is a necessary link in the exploit chain and independently lacks defense-in-depth, but full end-to-end likelihood is contingent on that unverified write-side gap.

### Recommendation
In `try_handle_request`, after retrieving `attachment` from `find_attachment`, recompute `attachment.hash()` and compare it to the requested `attachment_hash`; if they don't match, treat it as `HttpNotFound`/`HttpServerError` rather than serving the content. This provides defense-in-depth regardless of how `AtlasDB` write paths behave.

### Proof of Concept
Using `TestRPC` (as in other `getattachment` tests):
1. Construct a `TestPeer`/`TestRPC` instance and obtain its `AtlasDB`.
2. Directly execute a SQL `INSERT INTO attachments(hash, content, was_instantiated, created_at) VALUES (?, ?, ...)` where `hash` is `attacker_claimed_hash` (40 hex chars) but `content` hashes to a different value (bypassing normal gossip/write validation, per the question's stated precondition).
3. Build `StacksHttpRequest::new_getattachment(peerhost, attacker_claimed_hash)` and drive it through `TestRPC`'s request/response cycle to `RPCGetAttachmentRequestHandler`.
4. Decode the response via `StacksHttpResponse::decode_atlas_get_attachment`.
5. Assert `response.attachment.hash() != attacker_claimed_hash` and that the HTTP status was 200 (not 404/500), demonstrating the handler served mismatched content without detection.
