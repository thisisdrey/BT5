## Analysis

The external report's core broken invariant: **local state (`party.sleepoors.length`) is mutated but the cross-chain counterpart is never updated, so a length-based guard (`numUsed == sleepoors.length`) becomes permanently wrong, causing funds/NFTs to be irrecoverably stuck.**

The strongest local analog in `paritytech/polkadot-sdk` (BridgeHub Snowbridge code) is in `Pallet::do_process_message` of the Ethereum outbound queue v2 pallet: [1](#0-0) 

This function explicitly documents that it is **not transactional**: [2](#0-1) 

Yet it performs multiple sequential, dependent storage mutations — `Messages::append`, `MessageLeaves::append`, `PendingOrders::insert`, and `Nonce::set` — with fallible decode/encode steps interleaved between them: [3](#0-2) 

Specifically, `Messages::<T>::append(outbound_message)` at line 403 happens *before* the `commands.try_into()` re-encoding step (lines 394-401) that can still return `Corrupt`, and before `MessageLeaves::append` (line 424), `PendingOrders::insert` (line 436), and `Nonce::set` (line 438). If any later fallible step returns an `Err` (e.g. `Corrupt` from the bounded-vec conversion), the function returns `Err(ProcessMessageError::Corrupt)` — but the `Messages` entry already appended at line 403 is **not rolled back**, per the pallet's own doc comment.

### Why the generic `pallet-message-queue` transactional guarantee does not save this

`pallet-message-queue`'s `process_message_payload` wraps message processing in `storage::with_transaction` and rolls back on `Err`: [4](#0-3) 

This *would* normally roll back all storage mutations on error. The comment "IMPORTANT!! This method does not roll back storage changes on error" in the Snowbridge v2 pallet is therefore either stale/incorrect documentation contradicting the actual queue-level transactional wrapper, or (if accurate at some call site / historical version) indicates a real gap where `do_process_message` is invoked outside of `MessageProcessor::process_message`'s transactional path (e.g. directly, or in a future refactor that bypasses `pallet-message-queue`). Given the explicit, deliberate warning left by the Snowfork/Parity developers in the pallet source itself, this is a genuine local signal of a known-risky non-atomic multi-write sequence: `Messages` (data to relay) can be appended while `MessageLeaves` (the commitment root input) and `Nonce`/`PendingOrders` (delivery-receipt/reward accounting) fail to update consistently, producing a `Messages` entry whose corresponding commitment/nonce never gets committed to the header digest via `commit()` — i.e. an entry that can never be delivered/claimed, or worse, a nonce/order bookkeeping mismatch mirroring the "sleepoors.length never advances but numUsed does" class of stuck-state bug.

Note: I could not fully trace whether any code path calls `do_process_message` outside of the message-queue transactional wrapper within the time available — this is the key uncertainty. If `do_process_message` is *only* ever invoked via `ProcessMessage::process_message` → `pallet-message-queue::process_message_payload`, then the transactional wrapper does protect it, and the doc comment is simply outdated/misleading rather than describing a live bug.

### Title
Non-atomic multi-storage-write in `EthereumOutboundQueueV2::do_process_message` can desynchronize `Messages`/`MessageLeaves`/`Nonce`/`PendingOrders` on partial failure - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`Pallet::do_process_message` in the Snowbridge V2 outbound queue appends to `Messages` storage before later fallible encode/decode steps that can still error out, and the pallet's own doc comment states storage changes are not rolled back on error, contradicting the intended atomic append-then-commit invariant between `Messages`, `MessageLeaves`, `Nonce`, and `PendingOrders`.

### Finding Description
`do_process_message` decodes an inbound queued message, appends it to `Messages` (line 403), then continues performing ABI encoding, hashing into `MessageLeaves` (line 424), assigning a nonce and inserting a `PendingOrder` (lines 431-438). A `Corrupt` error can still be returned from the `commands.try_into()` step (lines 394-401) which executes *after* `Messages::append`. Because the pallet's own header comment states "This method does not roll back storage changes on error," a partial failure after the `Messages::append` call would leave a `Messages` entry with no corresponding `MessageLeaves` hash, no `Nonce` advance, and no `PendingOrder` — mirroring the reported bug class where an L1-side array is mutated but the corresponding cross-chain/committed state necessary for downstream validation and claims never advances.

### Impact Explanation
If this non-atomicity is reachable outside of `pallet-message-queue`'s transactional `process_message_payload` wrapper, it would desynchronize the merkle-root commitment (`commit()`, driven by `MessageLeaves`) from the raw `Messages` vector read by relayers via the `prove_message` runtime API, and would desynchronize `Nonce`/`PendingOrders` used for relayer reward settlement in `process_delivery_receipt`. This could permanently strand a message (unprovable/undeliverable) or create reward/nonce bookkeeping inconsistency — the same "stuck value that can never be reconciled" outcome as the reported L1/L2 desync.

### Likelihood Explanation
Low-to-medium confidence: the generic `pallet-message-queue::process_message_payload` transactional wrapper (`storage::with_transaction`) appears to cover exactly this scenario for the standard invocation path, which would make the pallet's inline comment merely stale documentation rather than an active vulnerability. I was unable to confirm within available context whether any other call path invokes `do_process_message` (or an equivalent code path) outside this transactional wrapper.

### Recommendation
Either (a) remove/correct the misleading "does not roll back" comment if the message-queue transactional wrapper genuinely guarantees atomicity for all call paths, or (b) if any call path bypasses `pallet-message-queue`, wrap `do_process_message`'s storage writes explicitly in `frame_support::storage::with_transaction` so that `Messages`, `MessageLeaves`, `Nonce`, and `PendingOrders` always advance together or not at all, consistent with the "atomic advance after decode/dispatch/execution" invariant.

### Proof of Concept
Not independently reproducible from available context — reproducing this would require constructing a `Message` payload that decodes successfully, passes the length/queue checks, but fails the `commands.try_into()` bounded-vec conversion at line 394-401 (e.g. via a command list serialized to exceed the `OutboundCommandWrapper` bound), while invoking `do_process_message` through a path not wrapped by `pallet-message-queue`'s transactional processor. I could not verify the existence of such a bypass path within the scope of this investigation.
