Based on my investigation, I found a valid analog: the Atlas attachment subsystem uses `Hash160` (160-bit, same width as an Ethereum address) as a content-addressing key, and the code that resolves a peer-downloaded `Attachment` against an on-chain-committed `AttachmentInstance.content_hash` does so purely by hash equality — exactly the "pigeonhole/birthday" pattern described in the external report.

### Title
Attachment content is resolved to on-chain commitments by an unauthenticated, birthday-attackable 160-bit hash equality check - (File: stackslib/src/net/atlas/download.rs)

### Summary
The Atlas subsystem binds off-chain "attachment" blobs to on-chain commitments purely via `Hash160` equality (`content_hash == Hash160(content)`), and attachment content is populated into the node's database from **unauthenticated peer downloads**. Because `Hash160` is a 160-bit digest, the same pigeonhole argument in the external report applies: an attacker who can produce/serve attachment content is not proving they authored the *specific* content referenced on-chain — they only need *some* content whose `Hash160` collides with a target `content_hash`.

### Finding Description
`Attachment::hash()` computes `Hash160::from_data(&self.content)` [1](#0-0) . This is the *only* binding between the arbitrary-length attachment bytes downloaded from peers and the 20-byte `content_hash` field that was committed on-chain in an `AttachmentInstance` [2](#0-1) .

When resolving downloaded content, `check_attachment_instances` looks up `atlas_db.find_attachment(&attachment_instance.content_hash)` / `find_uninstantiated_attachment` — a pure SQL `WHERE hash = ?1` lookup — and if any row matches, unconditionally treats it as *the* attachment for that on-chain commitment, inserting it as instantiated and returning it to callers as resolved data: [3](#0-2) . Likewise, in the batch state-machine "Done" path, any freshly-downloaded `Attachment` is matched against `find_all_attachment_instances(&attachment.hash())` and paired with every matching on-chain instance, again by hash equality alone: [4](#0-3) .

Content itself arrives over the wire from arbitrary, unauthenticated remote peers (via the Atlas attachment-inventory/download RPC flow) and is stored keyed by its own `Hash160` in the `attachments` table (`hash TEXT UNIQUE PRIMARY KEY`) [5](#0-4) , and served back out to any requester by hash via `/v2/attachments/{hash}` with no further validation of provenance [6](#0-5) , [7](#0-6) .

This mirrors the CallbackLib pattern exactly: the code trusts that "hash160(X) == committed_content_hash" implies X is *the* legitimate, canonical attachment, rather than verifying provenance (e.g., that X was actually the data referenced by the specific contract-emitted event). Because `Hash160` truncates a stronger digest down to 160 bits, the same `2^80`-birthday-bound applies as in the Panoptic report — an attacker can generate a large corpus of candidate attachment blobs offline and look for a collision against any of the (typically small, low-entropy, often near-empty/near-JSON-string) `content_hash` values that are actually committed on real contract calls, then push the colliding blob into the P2P Atlas network before/instead of the legitimate blob.

### Impact Explanation
If an attacker can push a `Hash160`-colliding blob into the network before (or instead of) the real content, `network.atlasdb.insert_instantiated_attachment` / `find_attachment` will treat this **forged, non-canonical content as canonical** for a legitimate on-chain `AttachmentInstance` (e.g., BNS name-registration zonefiles, or other consumers of Atlas attachments). Downstream consumers (RPC responses via `/v2/attachments/{hash}`, `/v2/attachments/inv`, BNS zonefile resolution, etc.) would then serve the attacker's data as if it were the data referenced by the on-chain event. This matches the "High - serving non-canonical state as canonical, attachment/BNS mismatch" impact category explicitly called out in the rules.

### Likelihood Explanation
This is feasibility-bounded exactly as described in the external report: `Hash160` is a 160-bit truncated digest, so finding *a* collision against a small target set (all currently-outstanding, unresolved `content_hash` values network-wide) costs roughly `2^80` hash operations rather than `2^160`. This remains computationally very expensive today (comparable to the original report's cost analysis), but it is a real, quantifiable weakening versus a full 256-bit binding, and the attack requires no privileged access — only the ability to serve attachment data as any P2P peer, which the Atlas protocol allows by design (any peer can serve/receive attachments for any content hash). No signature, ownership, or on-chain proof ties the raw bytes back to the entity that emitted the `AttachmentInstance` event.

### Recommendation
Do not treat `Hash160(content) == content_hash` as sufficient proof of canonicity/authenticity on its own where consumers assume a 1:1, tamper-proof binding. Concretely:
- Where feasible, widen the content-addressing hash used for Atlas attachments to a full 256-bit digest (e.g., `Sha256`/`Sha512Trunc256Sum`, which is already used elsewhere in this codebase for StackerDB chunks) to push the birthday bound back up to `2^128`.
- Alternatively/additionally, bind attachment resolution to more than just the raw hash — e.g., require the resolving peer's data to be traceable to the specific contract call/txid that emitted the `AttachmentInstance`, rather than accepting any blob whose truncated hash matches.

### Proof of Concept
Conceptual, mirroring the external report's PoC:
1. Network-wide, the set of currently-unresolved `AttachmentInstance.content_hash` values (each 160 bits) is public (queryable via `/v2/attachments/inv` and on-chain events).
2. An attacker precomputes a large corpus of candidate attachment payloads (e.g., valid-looking BNS zonefiles or arbitrary blobs) and their `Hash160` digests offline.
3. Per the birthday bound, after roughly `2^80` computed digests the attacker is likely to find a payload whose `Hash160` collides with some real, outstanding `content_hash`.
4. The attacker serves this colliding payload to the network as a peer (Atlas attachment download protocol has no authentication of the content's provenance) or via `POST`-style ingestion paths that `insert_uninstantiated_attachment`.
5. `check_attachment_instances` (`stackslib/src/net/atlas/download.rs:240-263`) matches the payload to the legitimate `AttachmentInstance` purely by hash and marks it "instantiated"/"resolved," after which it is served to all RPC clients via `/v2/attachments/{hash}` as if it were the original, legitimate content.

**Caveat:** I could not fully trace the ingestion path that populates `attachments`/`attachment_instances` from remote, unauthenticated peers within the available index (e.g., the exact `handle_getattachment`/upload RPC handler code), so the "before the legitimate content arrives" race-condition mechanics and any additional gating (e.g., size caps in `AtlasConfig`) are not fully confirmed from what I could retrieve. A full Devin session with complete repository access would be needed to verify the exact wire-level ingestion handler and any additional provenance checks that may exist there.
