### Title
Missing zero-address (unownable-address) validation in `AccountPermissionUpdateActuator` permits an unprivileged user to permanently lock their own account's owner/active permissions - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any account owner replace their account's `owner`, `witness`, and `active` `Permission` key sets via a self-broadcast `AccountPermissionUpdateContract`. Key addresses are only checked with `DecodeUtil.addressValid`, which validates length/prefix but not that the address is a real, key-controllable address (i.e., it does not reject the zero address).

### Finding Description
`checkPermission()` validates key count, threshold, weight sum, and calls `DecodeUtil.addressValid(key.getAddress().toByteArray())` for each key, but this helper never excludes the degenerate all-zero address: [2](#0-1) [1](#0-0) 

`validate()` requires the `owner` permission to be present and passes it through `checkPermission()`, and likewise for `witness`/`active` permissions: [3](#0-2) 

`execute()` then unconditionally overwrites the account's owner/witness/active permissions with the submitted ones: [4](#0-3) 

An unprivileged transaction broadcaster can craft an `AccountPermissionUpdateContract` where the sole key in the `owner` permission (with `weight >= threshold`) is set to the zero address `0x41 0000000000000000000000000000000000000` (21 bytes, correct prefix, passes `addressValid`), while activity/witness permission keys can remain legitimate or be similarly zeroed. Because `threshold` must be satisfiable and the check only verifies structural validity, once this is applied, the account's owner permission can never be satisfied by any real signature (no private key maps to the zero point), making that permission tier permanently unusable — mirroring the reported `Timelock` root cause where an unchecked "authority" address value renders privileged operations unreachable forever.

### Impact Explanation
This is a permanent, irreversible freezing of the account's owner-permission tier (and potentially active/witness tiers), which the account owner can never fix because updating permissions itself requires satisfying the (now unsatisfiable) owner permission threshold in the general case, or is at minimum a severe self-inflicted DoS on multi-sig governance for that account. This matches the funds/functionality freezing impact class cited in the rules (permanent freezing of funds/functionality via an actuator reachable from a single signed transaction).

### Likelihood Explanation
Reachable directly and trivially by any TRON account holder broadcasting a single `AccountPermissionUpdateContract` transaction — no special privilege, SR/witness status (except for the witness-permission branch), or network condition required. The bug is a straightforward missing input-sanitization gap in a commonly-used actuator.

### Recommendation
In `DecodeUtil.addressValid` (or specifically in `AccountPermissionUpdateActuator.checkPermission`), reject the all-zero address payload (and any other well-known burn/black-hole addresses) as a valid permission key, e.g.:
```java
if (!DecodeUtil.addressValid(key.getAddress().toByteArray())
    || Arrays.equals(key.getAddress().toByteArray(), ZERO_ADDRESS)) {
  throw new ContractValidateException("key is not a valid address");
}
```

### Proof of Concept
1. Attacker (any funded account holder) constructs `AccountPermissionUpdateContract` with:
   - `owner_address` = attacker's own address
   - `owner.keys[0].address` = `0x41` + 20 zero bytes, `weight` = `owner.threshold`
   - valid `active` permission(s) as required by validation rules
2. Broadcasts the transaction; `validate()` passes (`DecodeUtil.addressValid` accepts the zero-payload address, all other structural checks pass) and `execute()` persists the new owner permission via `account.updatePermissions(...)`. [5](#0-4) 
3. The account's owner-permission tier can now never be satisfied by any signature, since no key controls the zero address — any future action requiring owner-permission threshold on that account is permanently blocked.

Note: I could not fully verify from the index whether other actuators (e.g., committee/witness address setters, `UpdateBrokerageActuator`, exchange or market actuators) share exactly this same zero-address gap for privileged/authority-type addresses beyond the ones inspected; a Devin session with full repository access would be needed to exhaustively audit every `addressValid`-only check for this same class of issue.
