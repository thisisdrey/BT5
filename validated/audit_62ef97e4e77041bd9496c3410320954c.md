### Title
Attachments fetched from peers during Atlas sync bypass `attachments_max_size` before being stored and served - ([File: stackslib/src/net/atlas/download.rs])

### Summary
When the Atlas attachment downloader (`AttachmentsBatchStateMachine`) fetches an `Attachment` from a peer in response to a `GET /v2/attachments/:hash` request, it stores the peer-supplied content via `AtlasDB::insert_instantiated_attachment` with no re-check against `AtlasConfig::attachments_max_size`. This differs from the only other ingestion path (`posttransaction.rs`), which explicitly calls `AtlasDB::should_keep_attachment` (which enforces the size limit) before inserting. A malicious peer can therefore get an oversized attachment stored as `was_instantiated = 1`, after which `RPCGetAttachmentRequestHandler` will serve it in full to any RPC client that requests it by hash.

### Finding Description
`AtlasConfig::attachments_max_size` is meant to bound the content length of any attachment the node keeps. The only place this bound is enforced is `AtlasDB::should_keep_attachment` (`stackslib/src/net/atlas/db.rs:249-266`), which is called from `RPCPostTransactionRequestHandler::try_handle_request` (`stackslib/src/net/api/posttransaction.rs:231-250`) before `insert_uninstantiated_attachment`.

However, `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) — the function that actually marks an attachment `was_instantiated = 1` and makes it retrievable via `find_attachment`/the RPC endpoint — is also called directly from the Atlas P2P attachment downloader in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:152-169`):

```rust
AttachmentsBatchStateMachine::Done(ref mut context) => {
    for attachment in context.attachments.drain() {
        ...
        network.atlasdb.insert_instantiated_attachment(&attachment)...
```

`context.attachments` is populated by `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), which simply decodes whatever `GetAttachmentResponse` a queried peer returned and inserts it into the set — with **no call to `should_keep_attachment` and no length check against `attachments_max_size`** at any point in this path:

```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```

The requested peer is chosen from `network.get_outbound_sync_peers()` (any peer this node syncs Atlas data from), i.e., an unprivileged remote peer that a node dials for attachment content. That peer fully controls the `content` bytes returned in the JSON-hex-encoded `GetAttachmentResponse` (`stackslib/src/net/atlas/mod.rs:69-77`). The only generic bound on the response size is the HTTP layer's overall payload/message length cap (much larger than the minimum `attachments_max_size` of 1 MiB, see `ATTACHMENTS_MAX_SIZE_MIN` in `stackslib/src/net/atlas/mod.rs:52`), so a peer can return content larger than the configured/validated `attachments_max_size` while remaining under the generic HTTP cap.

Once inserted via `insert_instantiated_attachment`, the oversized `Attachment` is retrievable by `AtlasDB::find_attachment` (`stackslib/src/net/atlas/db.rs:641-648`), and `RPCGetAttachmentRequestHandler::try_handle_request` (`stackslib/src/net/api/getattachment.rs:93-130`) serves it back in full via `HttpResponseContents::try_from_json(&attachment)` with no re-validation of size against `attachments_max_size`.

### Impact Explanation
A single malicious/misbehaving peer that a victim node syncs Atlas attachments from can cause the victim to store and then repeatedly serve an attachment whose size exceeds the operator-configured `attachments_max_size` (minimum 1 MiB, but can be set much higher). This is a bounded-but-unvalidated compute/memory/storage cost on a read RPC endpoint (`/v2/attachments/:hash`), matching the "bounded compute DoS on a read endpoint" High-severity category. It also breaks the invariant that all bytes served under that endpoint are bounded by the node's configured attachment size policy, independent of it actually corresponding to any legitimately committed on-chain attachment instance (the hash is simply recomputed from whatever content the peer sent; there is no check that the returned content's hash matches an outstanding `AttachmentInstance.content_hash` before storage — it's stored regardless of `find_all_attachment_instances` results).

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be a normal outbound-sync peer that the victim node queries for BNS/Atlas attachment content — no signing key, RPC secret, or admin role is required. The attacker simply responds to a `GET /v2/attachments/:hash` request with attacker-chosen bytes exceeding `attachments_max_size` (but within the general HTTP payload cap). This is repeatable on every Atlas sync round and requires no special timing or on-chain state beyond the victim having an outstanding `AttachmentInstance` batch to resolve (a routine, ongoing condition for any node tracking BNS/Atlas contracts).

### Recommendation
Enforce `AtlasConfig::attachments_max_size` (and ideally that the received content's hash matches the requested `content_hash`) in `AttachmentsBatchStateContext::extend_with_attachments` before adding the attachment to `self.attachments`, and/or add the same check inside `AtlasDB::insert_instantiated_attachment` (or call `should_keep_attachment`-equivalent logic) prior to persisting attachments obtained from the P2P download path in `stackslib/src/net/atlas/download.rs`. As defense in depth, `RPCGetAttachmentRequestHandler::try_handle_request` should also reject/refuse to serve any stored attachment whose `content.len()` exceeds the currently configured `attachments_max_size`.

### Proof of Concept
Rust net test plan (in `stackslib/src/net/atlas/tests.rs` or `stackslib/src/net/api/tests/getattachment.rs`):
1. Configure an `AtlasConfig` with `attachments_max_size = ATTACHMENTS_MAX_SIZE_MIN` (1,048,576 bytes).
2. Simulate `AttachmentsBatchStateContext::extend_with_attachments` (or drive `AttachmentsBatchStateMachine` end-to-end using a mock peer/HTTP server that returns a `GetAttachmentResponse` whose `attachment.content.len() > attachments_max_size`, e.g. 2 MiB).
3. Run the state machine to `Done` and observe that `network.atlasdb.insert_instantiated_attachment(&attachment)` is invoked and succeeds without any size check (assert via `AtlasDB::find_attachment(&attachment.hash())` returning `Some(attachment)` with the oversized content).
4. Then call `RPCGetAttachmentRequestHandler::try_handle_request` for that hash and assert the response is `200 OK` with the full oversized body — demonstrating the endpoint serves unbounded-relative-to-policy content instead of rejecting it (expected/fixed behavior: a 4xx/5xx rejection or truncation consistent with `attachments_max_size`).     pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    fn try_handle_request(
        &mut self,
        preamble: HttpRequestPreamble,
        _contents: HttpRequestContents,
        node: &mut StacksNodeState,
    ) -> Result<(HttpResponsePreamble, HttpResponseContents), NetError> {
        let attachment_hash = self
            .attachment_hash
            .take()
            .ok_or(NetError::SendError("Missing `attachment_hash`".into()))?;

        let attachment_res = node.with_node_state(
            |network, _sortdb, _chainstate, _mempool, _rpc_args| match network
                .get_atlasdb()
                .find_attachment(&attachment_hash)
            {
                Ok(Some(attachment)) => Ok(GetAttachmentResponse { attachment }),
                _ => {
                    let msg = "Unable to find attachment".to_string();
                    warn!("{msg}");
                    Err(StacksHttpResponse::new_error(
                        &preamble,
                        &HttpNotFound::new(msg),
                    ))
                }
            },
        );
        let attachment = match attachment_res {
            Ok(attachment) => attachment,
            Err(response) => {
                return response.try_into_contents().map_err(NetError::from);
            }
        };

        let preamble = HttpResponsePreamble::ok_json(&preamble);
        let body = HttpResponseContents::try_from_json(&attachment)?;
        Ok((preamble, body))
    }
