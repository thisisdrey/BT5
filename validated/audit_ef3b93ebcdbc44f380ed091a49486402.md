### Title
`replace_block` overwrites the live `data` BLOB of an in-flight `NakamotoBlockStream`'s rowid, corrupting `GET /v3/blocks/:block_id` responses mid-stream - ([File: stackslib/src/net/api/getblock_v3.rs])

### Summary
`NakamotoBlockStream::new` resolves `rowid` once via `get_nakamoto_block_rowid`, but `generate_next_chunk` re-opens a fresh blob handle on that `rowid` and reads at `self.offset` on every call, with no lock or snapshot tying the stream to the byte content that existed when it started. Because `NakamotoBlockHeader::block_hash()` deliberately excludes `signer_signature` ("same as sighash -- we don't commit to signatures"), a remote peer can push an alternate copy of the same block (same `consensus_hash`/`block_hash`/`index_block_hash`/rowid) with a different, longer/shorter `signer_signature` vector and higher `signing_weight`; `store_block_if_better`/`replace_block` will then `UPDATE ... SET data = ?1 ... WHERE consensus_hash = ?4 AND block_hash = ?5`, overwriting the same SQLite rowid's blob in place while an unrelated HTTP client is mid-stream reading it.

### Finding Description
`NakamotoBlockStream::new` (getblock_v3.rs:63-86) looks up `rowid` once and stores it. `generate_next_chunk` (getblock_v3.rs:246-284) does not keep a persistent blob handle nor a transaction/snapshot; every invocation calls `self.staging_db_conn.open_nakamoto_block(self.rowid, false)` fresh, seeks to `self.offset`, and reads `hint_chunk_size()` bytes. The equality the design implicitly assumes — "total streamed bytes across all `generate_next_chunk` calls == the single block's byte length validated when the stream started" — depends on the blob content at `rowid` being immutable for the lifetime of the stream.

That assumption is false: the `nakamoto_staging_blocks` table uses `PRIMARY KEY(block_hash, consensus_hash)` with `index_block_hash` as a separate UNIQUE column (staging_blocks.rs:107-143), and `NakamotoBlockHeader::block_hash()` is explicitly computed to exclude `signer_signature` (mod.rs:1058-1065, comment: "same as sighash -- we don't commit to signatures"). `store_block_if_better` → `replace_block` (staging_blocks.rs:642-663, 771-786) performs `UPDATE nakamoto_staging_blocks SET data = ?1, signing_weight = ?2, obtain_method = ?3 WHERE consensus_hash = ?4 AND block_hash = ?5` whenever a new copy of the same sighash arrives with a strictly higher `signing_weight`. Because it's an `UPDATE` (not `DELETE`+`INSERT`) on a table without `INTEGER PRIMARY KEY`, the SQLite `rowid` is preserved while `data` (and its length) changes in place — the test at `stackslib/src/chainstate/nakamoto/tests/mod.rs:1454-1483` explicitly documents "store a sibling with more weight ... This is allowed because we don't commit to signatures."

This path is reachable by an unprivileged remote peer: `Relayer::process_new_nakamoto_block_ext` → `NakamotoChainState::accept_block` (mod.rs:2829-2945) is invoked for p2p-pushed blocks (`net/relay.rs:1696-1704`, `NakamotoBlockObtainMethod::Pushed`) after only `verify_signer_signatures` against the real reward set — which validates that the *attached* signatures are real, valid signer signatures, but does not prevent a different (larger) subset/superset of valid signer signatures being attached later with higher aggregate weight. An attacker who is simply a signer can also achieve the reorder cheaply; alternatively a remote peer can relay any two distinct-but-valid signature sets it has observed for the same block header (this happens naturally as more signers sign over time — no forgery is required, only *timing*).

Exploit flow:
1. Attacker/observer connects a streaming `GET /v3/blocks/:block_id` client; `NakamotoBlockStream::new` resolves `rowid=R` for a block currently in staging with signing_weight W1 and serialized length L1.
2. Between two `generate_next_chunk()` calls, the node's ordinary p2p/relay processing accepts (or the attacker itself pushes) a legitimately-signed alternate copy of the same block with more signer signatures (weight W2 > W1, length L2 ≠ L1), and `replace_block` overwrites the `data` BLOB at rowid `R` in place.
3. The next `generate_next_chunk()` call re-opens the blob at `R`, seeks to the old `self.offset`, and reads bytes from the *new* blob — splicing bytes from serialization L1 with bytes from serialization L2.
4. The client-reassembled response no longer corresponds to a byte-for-byte serialization of either signed block; it is a spliced hybrid that may fail `consensus_deserialize`, or worse, may deserialize into a `NakamotoBlock` whose `header.signer_signature` is a corrupted mix that could pass or fail validation unpredictably downstream in the caller.

Existing guards do not stop this: `try_parse_response`/`decode_nakamoto_block` (getblock_v3.rs:299-310) only performs `consensus_deserialize`, with no post-hoc equality check against `index_block_hash`; no re-verification that reassembled bytes hash to the expected `block_hash`/`index_block_hash` is performed on the client or server side of this streaming endpoint. Nothing locks or pins the row's content for the duration of the HTTP chunked response.

### Impact Explanation
A remote reader of `GET /v3/blocks/:block_id` can be served a corrupted/spliced byte stream that does not correspond to any single serialized `NakamotoBlock`, purely as a side effect of concurrent, entirely legitimate chain/relay activity (or attacker-accelerated via pushing an alternate valid-signature copy). This is a data-integrity break on a read endpoint (serving content that never existed as a single canonical byte sequence), matching the "serving non-canonical state as canonical" / read-endpoint corruption category. It does not by itself corrupt the node's own chainstate (the underlying `data` column always holds one fully valid serialization at rest, either old or new), and does not defeat the block's own header hash checks performed by other code paths (`get_nakamoto_block_header`, `NakamotoChainState::append_block`, etc., which re-open the blob once and hash-check completely). The impact is confined to the streaming HTTP delivery to the specific caller mid-read.

### Likelihood Explanation
Preconditions: an existing streaming HTTP client reading a block whose canonical signature set is still being assembled (i.e., a very recently produced/observed block where signer weight could still be increasing, or an attacker deliberately delays a full-weight copy to synchronize with a victim's stream), and a `replace_block` event landing between two `generate_next_chunk` calls. No secrets, admin roles, or privileged access are needed — the write path is the ordinary p2p block-push/relay path available to any connected peer sending a validly-signed alternate copy. The attack window is narrow (must race a specific stream's `generate_next_chunk` boundary) but is repeatable and does not require volumetric traffic; RPC clients that fetch blocks immediately after they're gossiped are the natural victims.

### Recommendation
Pin the stream to immutable content: either (a) read the entire blob into memory (or capture its length) at `NakamotoBlockStream::new` time inside the same transaction that resolved `rowid`, and serve subsequent chunks from that captured copy rather than re-opening the blob on every `generate_next_chunk` call, or (b) have `generate_next_chunk` verify, on every read, that the blob's current length matches the length recorded at stream-open time (and abort/re-fetch atomically otherwise), or (c) change `replace_block` to insert a new row (allocating a new rowid) instead of mutating `data` in place, so in-flight blob handles/stream state referencing the old rowid keep reading the old content deterministically (open blob handles in SQLICE remain valid against the old data until the row is vacuumed). Additionally, have the streaming path validate final reassembled bytes' hash against `index_block_hash` before considering the response complete, to fail closed rather than silently serving spliced bytes.

### Proof of Concept
Rust test plan in `stackslib::net::api::tests::getblock_v3`:
1. Set up a `StacksChainState` with `nakamoto_staging_blocks` containing block B (consensus_hash CH, header H1 with `signer_signature = [sig_a]`, weight 1), fully serialized as `data1` (length L1).
2. Construct `NakamotoBlockStream::new(chainstate, B.block_id(), CH, parent)`; call `generate_next_chunk()` once to accumulate a partial prefix of `data1` (use `hint_chunk_size()=32` test override to guarantee multiple chunks).
3. Between chunk calls, directly call `staging_tx.store_block_if_better(&block_with_H2, false, 2, NakamotoBlockObtainMethod::Pushed)` where H2 has `signer_signature = [sig_a, sig_b]` (same `signer_signature_hash`/`block_hash`, higher weight, longer serialized length L2) — this exercises `replace_block`'s `UPDATE ... SET data=...` on the same rowid.
4. Continue calling `generate_next_chunk()` until exhausted; concatenate all yielded chunks into `assembled`.
5. Assert failure of the implied equality: `assembled.len() != data1.len()` and `assembled != data1` and `assembled != data2`, and that `NakamotoBlock::consensus_deserialize(&mut &assembled[..])` either errors or produces a `NakamotoBlock` whose `block_id()` fails to equal `B.block_id()` — demonstrating the reassembled stream is neither of the two valid signed serializations and breaks the intended invariant that streamed bytes reconstruct the single block validated at `NakamotoBlockStream::new`.
