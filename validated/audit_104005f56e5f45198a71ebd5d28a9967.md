### Title
Unvalidated bancor-curve preconditions in `ExchangeProcessor` allow silently incorrect swap results - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` implement the TRC10 exchange bancor-style pricing curve using raw `double` arithmetic and mutate an internal `supply` field without validating the same kind of invariants the reported DODO `_GeneralIntegrate` bug flags (that inputs satisfy required orderings/positivity before being used in the formula). Like `_GeneralIntegrate`, which assumes `V0 >= V1 >= V2 > 0` without enforcing it, `ExchangeProcessor` assumes `supply`, `balance`, and `newBalance` remain well-formed (positive, non-degenerate) through the whole exchange call chain, but never checks this inside the math functions themselves.

### Finding Description
`exchangeToSupply` computes `issuedSupply` via `Maths.pow` and adds the truncated result to `supply` with no check that the resulting `supply` stays positive or bounded: [1](#0-0) 

`exchangeFromSupply` then decrements `supply` by the caller-supplied `supplyQuant` *before* using it as a divisor, with no check that `supply` remains positive/non-zero after the subtraction: [2](#0-1) 

This is the exact bug class from the report: a pricing/integration function that "assumes" preconditions on its numeric inputs (here, `supply > supplyQuant`, `balance/newBalance` non-degenerate) without validating them, so if the assumption is violated the function "behaves unexpectedly" — it silently returns an incorrect (or negative-driven, since `1.0 + supplyQuant/supply` can flip sign if `supply` goes non-positive) result instead of reverting.

This code path is reachable by any unprivileged transaction broadcaster: `ExchangeCapsule.transaction` selects this exact `ExchangeProcessor` (non-hardened) implementation by default, and only switches to the checked `SafeExchangeProcessor` when the `AllowHardenExchangeCalculation` proposal is active: [3](#0-2) 

`ExchangeCapsule.transaction` is invoked directly from `ExchangeTransactionActuator.execute`/`doValidate`, which is executed for any signed `ExchangeTransactionContract` transaction submitted by any account: [4](#0-3) [5](#0-4) 

By contrast, the "hardened" replacement, `SafeExchangeProcessor`, still performs the same unchecked arithmetic pattern (subtract-then-divide) using `BigDecimal`, but relies on `ExchangeCapsule.transaction`'s post-hoc balance check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) rather than validating preconditions inside the math functions themselves: [6](#0-5) [7](#0-6) 

### Impact Explanation
If an attacker can drive `supply` (an internal running value seeded from a fixed constant per exchange call, not persisted on-chain but recomputed each call) or the balance ratios into a regime where `1.0 + quant/newBalance` or `1.0 + supplyQuant/supply` is non-positive or extremely large due to floating point behavior, `exchangeToSupply`/`exchangeFromSupply` can return an incorrect `buyTokenQuant` that does not correspond to the intended bancor-curve output. Since this value directly drives `accountCapsule.addAssetAmountV2`/`setBalance` adjustments in `ExchangeTransactionActuator.execute`, an incorrect (e.g., inflated) `anotherTokenQuant` could let a user receive more TRC10 tokens or TRX than the exchange pool should give, while the exchange's own balances (`ExchangeCapsule.setBalance`) are updated based on the same unchecked value — a path to unbacked token minting/theft from the exchange pool.

### Likelihood Explanation
The unchecked `ExchangeProcessor` is the *default* processor for TRC10 exchange operations unless the `AllowHardenExchangeCalculation` proposal has been activated by committee vote; any account can reach it via a plain `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract`. However, exploiting it to actually manufacture an out-of-bounds `supply`/`quant` ratio requires driving the pool into extreme balance states (e.g., very large `quant` relative to `newBalance`), which is constrained by existing `ContractValidateException` checks on `tokenQuant <= 0`, exchange balance limits, and account balance sufficiency in `doValidate`. I could not confirm from the indexed code whether these existing bounds fully prevent all cases where `supply` could become non-positive across repeated calls within a single `exchange()` invocation, since `supply` state is local to the `ExchangeProcessor` instance created per call rather than persisted, limiting practical attacker control across transactions.

### Recommendation
Add explicit precondition checks inside `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (and mirror them in `SafeExchangeProcessor`) that `balance > 0`, `newBalance > 0`, and `supply` remains strictly positive after subtraction before it is used as a divisor, throwing a validation exception (mapped to `ContractValidateException`) rather than silently returning a value derived from an out-of-domain calculation.

### Proof of Concept
Not independently reproduced against a running node; the finding is based on static analysis of `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` [8](#0-7)  and its default selection/usage in `ExchangeCapsule.transaction` [9](#0-8) , reachable from `ExchangeTransactionActuator` [4](#0-3)  for any signed transaction.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
