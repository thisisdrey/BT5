## Title
Heap buffer over-read in `InputZipFile::ProcessCentralDirEntry` when parsing attacker-controlled ZIP/JAR central-directory length fields - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from a ZIP central-directory record and advances the read cursor `p` by those attacker-controlled 16-bit values without ever calling `EnsureRemaining()` to check that the claimed lengths actually fit within the mapped/allocated input buffer. [1](#0-0)  This is unlike the sibling local-file-header parser `ProcessLocalFileEntry`, which explicitly bounds-checks `file_name_length_` and `extra_field_length_` via `EnsureRemaining()` before touching the buffer. [2](#0-1) 

### Finding Description
`ProcessCentralDirEntry` is the parser for each 46-byte-fixed-plus-variable central directory record in a ZIP/JAR file. After reading the fixed fields, it reads three attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and immediately:
- `memcpy`s `p` into a fixed `filename[PATH_MAX]` buffer, clamping only the **destination** write length (`len = min(file_name_length, filename_size-1)`), not validating that the **source** pointer `p` plus `file_name_length` bytes actually remain inside the buffer. [3](#0-2) 
- Advances `p` by the full unchecked `extra_field_length` and then dereferences `extra_p` with `get_u2le`/`get_u8le` while walking the "extra field" TLV records, again with no bound against the buffer end. [4](#0-3) 
- Advances `p` by `file_comment_length` with no check at all. [5](#0-4) 

The only validation performed before entering the central-directory parsing loop is that `central_dir_offset + central_dir_size <= in_length` in `FindZipCentralDirectory`, which bounds the *whole* central directory region but does nothing to prevent an individual record's length fields from claiming values that extend past the end of that region (or the mapped file) once records are read sequentially without accumulation checks. [6](#0-5)  `ProcessCentralDirEntry` is invoked from the main per-entry extraction loop `InputZipFile::ProcessNext()` (used by the `zipper`/ijar extraction tools) and from `CalculateOutputLength()` (used to size ijar's interface-jar output), both of which iterate untrusted, attacker-supplied ZIP/JAR bytes. [7](#0-6) [8](#0-7) 

This class of bug — trusting a length field taken from a parsed record header to index/copy/advance through a buffer without checking it against the buffer's actual remaining size — is the same bug class as the reported LibreDWG CVE-2020-21842, where `read_2004_section_revhistory` used an unchecked length from a parsed section header to drive a heap read/write past the allocated buffer.

### Impact Explanation
An attacker who can get a victim's build to process a crafted `.jar`/`.zip` archive (e.g. a `java_import` target's jar, or any archive run through ijar/zipper as part of normal Bazel processing) can supply a central-directory entry with `file_name_length`, `extra_field_length`, or `file_comment_length` values that exceed the remaining bytes in the mapped input file. This causes out-of-bounds heap/mmap reads: bytes beyond the end of the mapped file are copied into the fixed `filename` buffer or dereferenced as 16/64-bit integers when parsing the "extra field." Depending on platform and allocator layout this can crash the process (denial of service via SIGSEGV) or leak adjacent heap memory contents into the derived interface jar or program output. It does not, on its own, appear to escape the process sandbox or corrupt writes into arbitrary heap locations (there is no over-write here, only over-read/over-advance), so the practical impact is bounded to an information-disclosure/crash primitive rather than remote code execution.

### Likelihood Explanation
The archive is fully attacker-controlled content (an untrusted `.jar`/`.zip` served at a URL or checked into an untrusted branch); the required malformed length fields are simple 16-bit values in a well-documented file format, making creation of a triggering file straightforward. Because Bazel's `sha256`/`integrity` checksum on downloaded archives only pins *which bytes* are used, not that those bytes are well-formed, checksum verification does nothing to stop a malicious-but-pinned archive from containing this malformed central directory record. The main practical friction is that the vulnerable path must actually be reached: this requires the archive to be processed by ijar/zipper (e.g., as a `java_import` jar or through a `zip`-typed `http_archive`/tool invocation) rather than merely fetched, which is a realistic but not universal Bazel workflow.

### Recommendation
In `ProcessCentralDirEntry`, before reading `file_name_length`, `extra_field_length`, and `file_comment_length` bytes (and before walking the extra-field TLV list), validate each length against the number of bytes actually remaining in the input buffer — analogous to the `EnsureRemaining()` checks already used in `ProcessLocalFileEntry`. The function should fail cleanly with an error instead of advancing `p`/`extra_p` past the buffer end.

### Proof of Concept
A reproducible PoC would live alongside the existing ijar zip tests: construct a minimal ZIP file with a valid End-Of-Central-Directory record and a single central directory file header whose `file_name_length` (or `extra_field_length`/`file_comment_length`) field claims a value that extends past the physical end of the file/mapped buffer, then run it through `zipper x`/ijar extraction (mirroring the existing `test_no_path_traversal` pattern in `third_party/ijar/test/zip_test.sh`) and confirm the process crashes or an ASan build reports a heap-buffer-overflow on the `memcpy`/`get_u2le` calls in `ProcessCentralDirEntry`. [9](#0-8) 

**Note on completeness:** I was not able to fully confirm, within the available tooling, all production call paths that feed *externally-fetched, unprivileged-attacker-controlled* jars into `ijar`/`zipper` (e.g., precisely which `java_import`/toolchain actions invoke this code on downloaded artifacts vs. only locally-built jars). Confirming the full attacker-reachable action graph would benefit from a broader repository search than the index could support here.

                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
