### Title
StackerDB inventory falsely advertises a pushed chunk as stored before it is actually written to the replica - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` builds and immediately sends a `StackerDBChunkInv` reply that claims the pushed chunk's new `slot_version` is already present in this node's local replica, but the chunk itself is only *validated* at this point (signature, freshness, size, max-writes) — it is not written to the `StackerDBs` sqlite store here. Storage happens later, asynchronously, when the message is handed off to the relayer. This creates a served-vs-committed mismatch analogous to the reported `Voter.poke()` bug, where a value reflected as "current" is not actually the value that was recomputed/recorded.

### Finding Description
In `stackslib/src/net/stackerdb/mod.rs`, `handle_unsolicited_StackerDBPushChunk`: [1](#0-0) 
builds the reply inventory via `make_StackerDBChunksInv_or_Nack`, which reads the *current* on-disk `slot_versions` from `self.stackerdbs.get_slot_versions(contract_id)`: [2](#0-1) 
It then calls `validate_received_chunk` (a pure validation routine that never touches the DB write path — signature check, staleness check, size check, max-writes check only): [3](#0-2) 
and, if validation passes, directly mutates the outgoing inventory in memory:
```
*slot_version = chunk_data.chunk_data.slot_version;
``` [4](#0-3) 
before signing and sending this patched `StackerDBChunkInv` back to the peer: [5](#0-4) 
and returning `(false, true)`, meaning "don't buffer, forward to relayer" — the actual persistence (`StackerDBs::try_replace_chunk` / `insert_chunk`) happens later, outside this function, when the relayer processes the forwarded message.

This mirrors the `Voter.poke()` defect: the function *claims* a derived/aggregate value (there: the boost baked into `usedWeights`; here: the slot's stored version reflected in the chunk inventory) reflects a freshly-applied update, but the underlying state that value depends on (there: the previous boost; here: the actual chunk bytes on disk) was never actually recomputed/written at the point the claim is made. The equality "advertised inventory version == actually stored chunk version" is broken.

### Impact Explanation
Downstream peers that receive this `StackerDBChunkInv` will believe the sending node already has slot version `N` and will not attempt to fetch/re-push that chunk. If the deferred store (in the relayer) fails or is delayed (e.g., relayer processing is deferred, the node crashes/restarts between accepting the push and the relayer actually calling `try_replace_chunk`, or the message is dropped because it isn't actually forwarded for some intervening reason), the node's replica silently lacks the chunk version it advertised. This can steer StackerDB sync peers into believing stale/absent data is present (an inventory/data mismatch), delaying propagation of signer messages, block-commit related StackerDB writes, or other StackerDB-backed protocol data across the network. This falls under "serving non-canonical state as canonical" / inventory-vs-stored mismatch (High).

### Likelihood Explanation
This code path is on the unsolicited-message handling path (`ConversationP2P` → `handle_unsolicited_StackerDBPushChunk`), reachable by any connected, unauthenticated-or-authenticated peer that sends a `StackerDBPushChunk` with a validly signed chunk (the peer only needs a StackerDB slot signing key that is already registered on-chain for that DB — no special privilege over the receiving node is required). Since the inventory patch happens unconditionally whenever `validate_received_chunk` returns true, the discrepancy window exists on every single accepted push, not just an edge case — the severity/likelihood depends on how reliably and immediately the relayer performs the actual store afterward, which I was not able to fully confirm from the available index (the relay.rs store logic was only partially visible before the tool budget ran out).

### Recommendation
Do not patch/send the `StackerDBChunkInv` claiming the new version until after the chunk has actually been durably written via `StackerDBs::try_replace_chunk`/`insert_chunk`. Either perform the store synchronously in `handle_unsolicited_StackerDBPushChunk` before replying, or defer sending the inventory reply until the relayer confirms the write succeeded.

### Proof of Concept
Not independently reproducible from the index alone — I was unable to fully trace the relayer's exact timing/atomicity guarantees for storing StackerDB push-chunks in `stackslib/src/net/relay.rs` before the tool budget ran out (the grep showed `try_replace_chunk`/`insert_chunk` references there but I could not confirm ordering or failure-handling relative to the inventory reply). This should be verified with a Devin session that traces `relay.rs`'s handling of `StackerDBPushChunkData` end-to-end and constructs a test where the relayer-side store is made to fail/delay after `handle_unsolicited_StackerDBPushChunk` has already replied with the patched inventory, to confirm the advertised-vs-stored mismatch is observable by a third-party peer.

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
