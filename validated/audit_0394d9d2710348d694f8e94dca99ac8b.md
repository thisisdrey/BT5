### Title
`ReliabilityReport::bump_successful_requests()` inflates peer score without verifying returned attachment hash, letting a malicious peer capture `AttachmentRequest::get_most_reliable_source` indefinitely - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` and `extend_with_inventories` call `ReliabilityReport::bump_successful_requests()` whenever an HTTP response merely *decodes* successfully, without checking that the returned `Attachment`'s real content matches the `content_hash` that was actually requested. Because `AttachmentRequest::get_most_reliable_source`/`Requestable::get_url` deterministically picks the peer with the highest `ReliabilityReport::score()` as the *sole* peer queried for a given round, an attacker who always returns well-formed-but-wrong-hash attachments can accumulate an ever-increasing score and get selected exclusively for future, unrelated `content_hash` requests, starving the batch of any chance to reach an honest peer that actually holds the data.

### Finding Description
The claimed equality — "reliability score == verified-correct-responses" — is broken: [1](#0-0) 

In `extend_with_attachments`, the only check performed on a successful HTTP 200 response is that `response.decode_atlas_get_attachment()` parses without error; the decoded `Attachment`'s hash is never compared to `request.content_hash` before calling `report.bump_successful_requests()`. The same pattern exists in `extend_with_inventories` for inventory responses: [2](#0-1) 

`ReliabilityReport::score()` is a pure function of `total_requests_sent`/`total_requests_success`, both of which are bumped unconditionally on decode success: [3](#0-2) 

`get_most_reliable_source` (used by both `Ord for AttachmentRequest` and `Requestable::get_url`) always resolves to a single URL — the peer with the maximal score: [4](#0-3) 

and `BatchedRequestsState::BeginRequests` issues exactly one HTTP request per `AttachmentRequest` via `PeerNetwork::begin_request`, using that single resolved URL: [5](#0-4) 

Exploit flow: an attacker-controlled peer (registered in `network.get_outbound_sync_peers()`/data URL, requiring no privileged role — any peer that establishes an outbound-syncable connection and advertises a data URL) responds to unrelated attachment-inventory or attachment-content requests with syntactically valid but content-mismatched payloads. Each such response bumps its `ReliabilityReport` score without any hash check. Over repeated rounds its score outstrips all honest peers, so for a subsequent distinct `content_hash` request, `get_most_reliable_source` (and therefore `Requestable::get_url`) will pick the attacker again and again, denying honest peers holding the real attachment the chance to be queried.

The only place actual content is validated against a real hash is later, in `AttachmentsDownloader::run`'s `Done` handling, which computes `attachment.hash()` from the bytes actually received and uses that to look up matching pending instances: [6](#0-5) 

This late check prevents the wrong data from being *accepted as resolving* the specific pending `AttachmentInstance`, so no forged content is stored as the canonical attachment for the requested hash. However, it does nothing to stop the score inflation or the resulting peer-selection bias: the batch simply fails to resolve, bumps its retry count, and is retried — during which the same attacker is re-selected as "most reliable" each round, monopolizing the download attempts for the affected batch until `max_attachment_retry_count` is exhausted and the batch is dropped.

### Impact Explanation
Impact is availability/steering, not state-forgery: a single non-privileged remote peer can, at negligible cost, make itself the exclusive queried source for one or more `content_hash` values it does not actually hold, causing legitimate Atlas attachments (BNS zonefiles) referenced by on-chain commitments to never be fetched from the honest peers that hold them, until the batch's retry budget is exhausted and it is silently dropped. This matches the "steering a node off the tip via false inventory / attachment mismatch" bucket at High: the node's peer-selection logic is durably biased toward an unreliable/malicious peer for legitimate content, degrading BNS/Atlas convergence, and is fully repeatable for every batch and every retry round as long as the attacker keeps answering.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be one of `network.get_outbound_sync_peers()` with a resolvable data URL — i.e., an ordinary unprivileged peer connection, no secret, no StackerDB slot, no admin role. The attacker's cost is a handful of well-formed HTTP responses with wrong-hash payloads; there is no cryptographic or state requirement to satisfy. It is trivially repeatable across retry cycles and across different `content_hash` batches, since the score keeps accumulating and is persisted in `AttachmentsDownloader::reliability_reports` across `run()` calls.

### Recommendation
In `extend_with_attachments`, before calling `report.bump_successful_requests()`, verify that the decoded `Attachment::hash()` equals `request.content_hash`; only bump success on a match, and bump failure (or a dedicated "dishonest" penalty) otherwise. Apply an analogous hash/consistency check in `extend_with_inventories` where feasible (e.g., cross-checking inventory claims against later attachment fetch outcomes) so that `ReliabilityReport::score()` reflects verified-correct responses rather than merely well-formed ones.

```rust
#[test]
fn test_reliability_report_should_not_bump_on_mismatched_hash() {
    // Construct an AttachmentRequest for content_hash = H1
    // Simulate extend_with_attachments() receiving a StacksHttpResponse
    // whose decode_atlas_get_attachment() yields Attachment::hash() == H2 (H2 != H1)
    let mut report = ReliabilityReport::empty();
    let score_before = report.score();

    // current buggy behavior: any successful decode bumps score
    report.bump_successful_requests();
    assert!(report.score() > score_before, "score inflated on mismatched-hash response");

    // Desired assertion after fix: score must NOT increase unless
    // decoded attachment hash equals the requested content_hash.
    // i.e. extend_with_attachments should call bump_failed_requests()
    // when Attachment::hash() != request.content_hash.
}
```
A full integration-style reproduction would construct two `AttachmentRequest`s with distinct `content_hash`, drive one through `extend_with_attachments` with a mismatched-hash payload from peer A, observe `context.peers[A].score()` increase, then show that a second request now resolves `get_most_reliable_source()` to peer A over an honest peer B that truthfully has the correct attachment.

```rust
impl AttachmentRequest {
    pub fn get_most_reliable_source(&self) -> (&UrlString, &ReliabilityReport) {
        self.sources
            .iter()
            .max_by_key(|(_, v)| v.score())
            .expect("Atlas: trying to select an Url out of an empty set")
    }
}

impl Hash for AttachmentRequest {
    fn hash<H: Hasher>(&self, state: &mut H) {
        self.content_hash.hash(state)
    }
}

impl Ord for AttachmentRequest {
    fn cmp(&self, other: &AttachmentRequest) -> Ordering {
        other.sources.len().cmp(&self.sources.len()).then_with(|| {
            let (_, report) = self.get_most_reliable_source();
            let (_, other_report) = other.get_most_reliable_source();
            report.cmp(other_report)
        })
    }
}

impl PartialOrd for AttachmentRequest {
    fn partial_cmp(&self, other: &AttachmentRequest) -> Option<Ordering> {
        Some(self.cmp(other))
    }
}

impl Requestable for AttachmentRequest {
    fn get_url(&self) -> &UrlString {
        let (url, _) = self.get_most_reliable_source();
        url
    }

    fn make_request_type(&self, peer_host: PeerHost) -> StacksHttpRequest {
        StacksHttpRequest::new_for_peer(
            peer_host,
            "GET".to_string(),
            format!("/v2/attachments/{}", &self.content_hash),
            HttpRequestContents::new(),
        )
        .expect("FATAL: failed to create an HTTP request for infallible data")
    }
}
```

```rust
pub struct ReliabilityReport {
    pub total_requests_sent: u32,
    pub total_requests_success: u32,
}

impl ReliabilityReport {
    pub fn bump_successful_requests(&mut self) {
        self.total_requests_sent += 1;
        self.total_requests_success += 1;
    }

    pub fn bump_failed_requests(&mut self) {
        self.total_requests_sent += 1;
    }
}

impl ReliabilityReport {
    pub fn new(total_requests_sent: u32, total_requests_success: u32) -> ReliabilityReport {
        ReliabilityReport {
            total_requests_sent,
            total_requests_success,
        }
    }

    pub fn empty() -> ReliabilityReport {
        ReliabilityReport {
            total_requests_sent: 0,
            total_requests_success: 0,
        }
    }

    pub fn score(&self) -> u32 {
        let n = self.total_requests_sent;
        if n == 0 {
            return n;
        }
        self.total_requests_success * 1000 / (n * 1000) + n
    }
}
```
