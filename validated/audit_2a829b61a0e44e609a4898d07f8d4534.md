## Root Cause

`MarketSellAssetActuator.execute()` wraps the whole order-matching flow (including `matchOrder`/`matchSingleOrder`) in a narrow catch clause that only catches `ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, and `ContractValidateException`: [1](#0-0) 

Inside the matching loop, when a taker's order fills against a maker's resting order, the maker's account is credited via `addTrxOrToken`, which mutates the maker's TRX balance or TRC10 asset balance: [2](#0-1) 

Balance/asset credits in java-tron are implemented with overflow-checked arithmetic (`Math.addExact`/`addAssetAmountV2`), which throws an uncaught `ArithmeticException` on overflow — this is the same primitive `TransferActuator` explicitly catches: [3](#0-2) 

Because `MarketSellAssetActuator.execute()`'s catch list omits `ArithmeticException`, an overflow while crediting a maker account during `matchSingleOrder` is not converted into a normal `ContractExeException`; it propagates as an unchecked `RuntimeException` out of actuator execution instead of failing gracefully.

## Analog to the Reported Bug Class

The reported Opyn bug is: a batch/loop settlement process (`netAtPrice`/`withdrawAuction`) can be permanently DOS'd because one specific recipient in the queue is unable to accept a transfer (USDC blacklist), and the code has no way to skip/isolate that failure — it reverts the entire batch.

The java-tron analog is structurally identical: `matchOrder`'s `while` loop iterates over resting maker orders in the order book and, for each match, unconditionally credits the maker's account (`addTrxOrToken`). If any maker account in that price-level queue is in a state where the credit overflows (i.e., its existing balance/asset amount plus the incoming settlement amount exceeds `Long.MAX_VALUE`), the actuator throws an uncaught exception mid-loop instead of a handled `ContractValidateException`, aborting the whole `execute()` call for the taker's `MarketSellAssetContract` — exactly like the USDC-blacklist scenario blocking `netAtPrice`.

An attacker can deliberately engineer this condition because TRC10 asset supply and account balances are attacker-controllable up to `Long.MAX_VALUE` (self-issued token with a very large `totalSupply`, or repeated self-transfers). By pre-loading a maker account's asset balance to just below `Long.MAX_VALUE` and placing a resting sell order at an attractive price for a given trading pair, any taker whose `MarketSellAssetContract` would match against that maker order triggers `addAssetAmountV2` → overflow → uncaught `ArithmeticException`, so **that taker's transaction always reverts unexpectedly** whenever it would match this poisoned maker order — effectively a targeted DOS on order matching for that trading pair, achievable via a single unprivileged `MarketSellAssetContract`/`AssetIssueContract` pair of transactions.

## Assessment

This satisfies the criteria: it's reachable purely by an unprivileged order-placer/asset-issuer submitting `AssetIssueContract` + `MarketSellAssetContract` transactions, it lives in actuator validate/execute logic in scope, and it causes an unhandled exception path (missing `ArithmeticException` handling) that can make legitimate takers' transactions unexpectedly fail — the same "one poisoned participant blocks the shared batch/matching function" bug class as the source report.

### Title
Uncaught `ArithmeticException` in `MarketSellAssetActuator` matching loop allows a crafted maker order to DOS matching taker transactions - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` catches only a fixed set of exceptions (`ItemNotFoundException`, `InvalidProtocolBufferException`, `BalanceInsufficientException`, `ContractValidateException`) around the order-matching loop, but the credit path (`addTrxOrToken` → `addAssetAmountV2`/`addExact`) can throw an uncaught `ArithmeticException` on balance overflow, letting a maliciously-crafted maker order poison matching for any taker.

### Finding Description
`matchOrder`/`matchSingleOrder` iterate resting maker orders and call `addTrxOrToken` to credit the maker account with settled TRX or TRC10 tokens [4](#0-3) . This credit uses overflow-checked arithmetic that throws `ArithmeticException` when the maker's existing balance/asset amount plus the incoming amount exceeds `Long.MAX_VALUE`. The surrounding `execute()` try/catch block does not include `ArithmeticException` in its catch list [1](#0-0) , so the exception is not converted into a normal failed-transaction result; it escapes as an unhandled runtime exception from actuator execution.

An attacker can set up a maker account with a TRC10 asset balance near `Long.MAX_VALUE` (TRC10 `totalSupply` is attacker-chosen at issuance and can be self-held), then place a resting sell order for that asset. Any subsequent taker whose `MarketSellAssetContract` matches this order will trigger the overflow when the maker is credited, causing the taker's own transaction execution to hit the uncaught exception path instead of a clean validation failure.

### Impact Explanation
Order matching is a core, permissionless exchange primitive reachable by any account submitting `MarketSellAssetContract`. An attacker can poison specific price levels in the order book so that unrelated, legitimate takers' matching transactions unexpectedly throw an unhandled exception rather than being cleanly rejected, denying service to the market/order-matching feature for that trading pair and potentially destabilizing transaction processing behavior around actuator execution error handling.

### Likelihood Explanation
Requires only unprivileged transactions: issuing/holding a TRC10 asset with attacker-controlled supply and placing a `MarketSellAssetContract` order — both ordinary, permissionless operations available to any account. No special privileges, timing, or SR/witness cooperation needed.

### Recommendation
Add `ArithmeticException` (or a broader safety-net catch) to the exception handling in `MarketSellAssetActuator.execute()`/`matchOrder`, converting overflow conditions into a proper `ContractValidateException`/`ContractExeException` that fails only the current transaction rather than propagating an unhandled exception. Additionally, consider bounding/validating credited amounts before calling `addAssetAmountV2`/`addExact` so an attacker cannot use self-inflated balances to induce arithmetic overflow against innocent counterparties.

### Proof of Concept
1. Attacker issues a TRC10 token with `totalSupply` close to `Long.MAX_VALUE` and holds virtually all of it in account `M`.
2. Account `M` also accumulates a very large TRX balance (e.g., via repeated legitimate transfers) so that `balance + incoming_settlement` would overflow `Long`.
3. Account `M` places a resting maker sell order (via `MarketSellAssetContract`) offering to sell the TRC10 token for TRX at an attractive price.
4. A victim `V` submits a `MarketSellAssetContract` that matches against `M`'s order.
5. During `matchSingleOrder` → `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)`, crediting `M`'s TRX balance overflows `Long.MAX_VALUE`, throwing `ArithmeticException`.
6. Because `MarketSellAssetActuator.execute()`'s catch block does not include `ArithmeticException`, `V`'s transaction execution exits via an unhandled exception rather than a normal validate/execute failure, as confirmed by the catch clause at [1](#0-0) .

Note: due to index size limits I was not able to view the full body of `AccountCapsule.addAssetAmountV2`/`setBalance` overflow checks or trace precisely how an uncaught `RuntimeException` from `actuator.execute()` is handled further up in `Manager.processTransaction` (e.g., whether it degrades to a per-transaction failure or affects block application) — confirming the exact downstream blast radius would require starting a full Devin session with complete file access.
