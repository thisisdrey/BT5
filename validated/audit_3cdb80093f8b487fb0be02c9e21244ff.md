### Title
Unvalidated attacker-controlled array length causes uncontrolled allocation / crash in BatchValidateSign precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract's `doExecute` method reads array-length fields directly from calldata and only bounds-checks them (`MAX_SIZE`) when the hard-fork flag `VMConfig.allowTvmSelfdestructRestriction()` is enabled. The underlying array-building helpers `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` allocate `byte[][]` arrays sized by an attacker-controlled `len` value taken straight from the calldata words, with no length validation performed inside the helpers themselves.

### Finding Description
`doExecute` parses call data into `DataWord[] words` and only performs a size check conditionally: [1](#0-0) 

The bound check (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is gated behind `if (VMConfig.allowTvmSelfdestructRestriction())`. If that condition is false, execution falls through to `extractBytesArray(...)` and `extractBytes32Array(...)` with no length limit applied at all. Both helpers take the length directly from calldata and immediately allocate an array of that size: [2](#0-1) [3](#0-2) 

`words[offset].intValueSafe()` is fully attacker-controlled via the transaction's contract-call data (a single unprivileged `TriggerSmartContract` call reaching this precompile at the `BatchValidateSign` address). A crafted `len` near `Integer.MAX_VALUE` triggers a huge `new byte[len][]` allocation attempt (heap exhaustion / `OutOfMemoryError`), and a negative-decoding value can throw `NegativeArraySizeException`. This mirrors the GStreamer bug class: an attacker-supplied "count"/length field is used to size a memory allocation without validating it is within safe bounds before use.

### Impact Explanation
If the precompile-invocation code path does not catch `OutOfMemoryError`/`NegativeArraySizeException` gracefully (unlike checked `ContractValidateException`/`ContractExeException` paths elsewhere in the VM), a single crafted transaction could crash the executing thread or destabilize the node process, denying service to all subsequent transaction processing — a Medium/High impact depending on whether the exception propagates past the TVM's normal revert-on-exception handling.

### Likelihood Explanation
Medium. The path is reachable by any unprivileged account able to submit a `TriggerSmartContract` calling the `BatchValidateSign` precompiled contract address with crafted calldata. The exploitability, however, depends on whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network — on current mainnet this hard-fork flag is very likely already enabled (the `MAX_SIZE` check exists specifically to close this gap), which would make the unguarded path unreachable in practice. I was not able to confirm the flag's activation status or find a wrapping try/catch at the precompile-invocation call site within my available tool calls, so exploitability on a live, fully-upgraded mainnet node is uncertain.

### Recommendation
Move the `MAX_SIZE` bound check for `len` inside `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves (unconditional on any hard-fork flag), so that any caller is protected regardless of feature-flag state, and confirm the precompile invocation path wraps `Throwable` (not just checked exceptions) to guarantee a clean revert rather than a process-level crash.

### Proof of Concept
Construct calldata for `BatchValidateSign` where the signature-array-length word (`words[words[1].intValueSafe()/WORD_SIZE]`) is set to a very large value (e.g. `0x7FFFFFFF`) while `VMConfig.allowTvmSelfdestructRestriction()` is not active; submit via `TriggerSmartContract`. Execution reaches `extractBytesArray`/`extractSigArray`, attempting `new byte[0x7FFFFFFF][]`, causing `OutOfMemoryError`.

**Caveat:** I could not verify (a) whether `allowTvmSelfdestructRestriction` is currently active on production networks (which would neutralize this path), or (b) whether an outer exception handler in the Program/VM invocation layer already catches `Throwable` around precompile execution and safely reverts. These are material to whether this is truly exploitable today; a Devin session with full repo/runtime access could confirm both by tracing `VMConfig.allowTvmSelfdestructRestriction` initialization and the precompile call site's exception handling in `Program.java`.
