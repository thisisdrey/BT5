### Title
Single-step, unconfirmed permission/ownership transfer in `AccountPermissionUpdateActuator` can permanently freeze an account - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateContract` lets an account holder unilaterally rewrite its own `Owner`, `Witness`, and `Active` permissions — including the key addresses that control the account — in a single transaction. The actuator only checks that the supplied addresses are *format*-valid; it never confirms that the new key holder is reachable or that the resulting permission set is recoverable. This is the same "no transfer-ownership pattern" weakness described in the report: a one-shot write of a new controlling address with no acceptance step, which can accidentally (or via a malicious dApp / phishing flow) point account control at an address nobody can sign for, permanently disabling every `onlyOwner`-equivalent operation on that account.

### Finding Description
`AccountPermissionUpdateActuator.validate()` only validates address format with `DecodeUtil.addressValid`, not that the new owner/active keys are usable or distinguishable from a mistyped/unreachable address: [1](#0-0) [2](#0-1) 

`execute()` then commits the new `Owner`/`Witness`/`Active` permission sets atomically, in the same transaction, with no staged "nominate then accept" step: [3](#0-2) 

Crucially, only the `Owner` permission (`permission_id == 0`) can authorize an `AccountPermissionUpdateContract` — the `checkPermission` gate in `TransactionCapsule` restricts non-zero `permission_id`s to the `Active` type only for contract-type checks, meaning permission_id 0 is unrestricted and is the sole path that can ever re-issue permissions: [4](#0-3) 

Because both the `Owner` and `Active` permission key sets can be rewritten in the very same `AccountPermissionUpdateContract`, a single transaction can simultaneously replace the address(es) that control day-to-day operations (`Active`, used by `TransferContract`, `TriggerSmartContract`, etc.) and the address(es) that control future permission changes (`Owner`). If the new key(s) are mistyped, correspond to an inactive/uncontrolled address, or an unreachable threshold configuration (e.g., total key weight barely meets threshold but the "wrong" keys were used), there is no second step for the intended new controller to confirm receipt of control, unlike the two-step "nominate + acceptOwnership" pattern recommended in the report.

### Impact Explanation
If the resulting `Owner` and `Active` permission keys are unreachable, the account is permanently locked: it can never again pass `checkWeight`/`validateSignature` for any subsequent `AccountPermissionUpdateContract` (which itself requires the now-broken `Owner` permission), so the account's TRX/TRC10/TRC20 balances, staked resources, and smart-contract-owned assets are frozen with no on-chain remediation path. This matches the "permanent freezing of funds" impact class.

### Likelihood Explanation
The transaction is broadcastable by any account holder with a single signed `AccountPermissionUpdateContract` — no committee, SR, or privileged role is needed. The only friction is that this is (as in the original report) typically a self-inflicted error by the account owner, or induced via a malicious dApp/wallet integration that gets a user to sign a permission update pointing at attacker/uncontrolled keys, exactly mirroring the `Swap.sol` `transferOwnership` scenario the report describes.

### Recommendation
- Require the new `Owner`/`Active` key holder(s) to co-sign or otherwise acknowledge the permission change (a two-step nominate/accept flow) before it becomes effective, particularly when the new `Owner` permission's key set does not overlap with the current one.
- At minimum, warn/require an explicit "self-test" transaction from at least one new key before finalizing a permission set that revokes all previously valid keys, and/or disallow `Owner` and `Active` permission updates that leave no currently-signing key in the new permission set.

### Proof of Concept
1. Account A holds default `Owner` permission (single key = A) and default `Active` permission (single key = A).
2. A signs and broadcasts one `AccountPermissionUpdateContract` (via `permission_id = 0`) setting: `owner` permission's sole key to address `B` (mistyped/unreachable/uncontrolled address that still passes `DecodeUtil.addressValid`), and `actives[0]` permission's sole key also to `B`.
3. `AccountPermissionUpdateActuator.validate()` only checks that `B` is a well-formed address; it succeeds and `execute()` commits both permission changes atomically: [5](#0-4) 
4. From then on, no private key controlled by A (or anyone) can produce a signature that resolves to `B`'s weight in either the new `Owner` or `Active` permission, so `TransactionCapsule.checkWeight`/`validateSignature` can never be satisfied for that account: [6](#0-5) 
5. All TRX/TRC10/TRC20 balances and resources owned by A's account are now permanently frozen — there is no on-chain "acceptOwnership"-style recovery path.

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
