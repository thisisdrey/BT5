### Title
Unprivileged attacker can saturate the bridged-out supply cap and block all bridge-out withdrawals - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
Analogous to the Shibarium incident (user funds stuck inside a bridge with no exit path), Metronome's `ProxyOFT` bridge can be driven into a state where every user bridge-out reverts. `SyntheticToken._burn` enforces `bridgedOutSupply() <= maxBridgedOutSupply`, where `bridgedOutSupply = totalBridgedOut - totalBridgedIn`. Any holder of a synthetic token can call `ProxyOFT.sendFrom` to burn their own tokens, permanently increasing `totalBridgedOut`. Once an attacker pushes the net bridged-out supply to the cap, all subsequent `sendFrom` calls revert with `SurpassMaxBridgingSupply`, freezing other users' ability to exit via the bridge.

### Finding Description
`ProxyOFT._debitFrom` calls `syntheticToken.burn(from_, amount_)` for any sender bridging their own tokens [1](#0-0) . Inside `SyntheticToken._burn`, whenever the caller is the `proxyOFT`, `totalBridgedOut` is incremented and the net out-supply is checked against the governor-set cap: [2](#0-1) 

`bridgedOutSupply()` is `totalBridgedOut - totalBridgedIn` (floored at 0) [3](#0-2) . There is no per-account limit, no rate limit, and no minimum on bridge-outs — anyone holding the synth (obtainable via `DebtToken.issue` with collateral, `Pool.swap`, or the open market) can bridge out arbitrary amounts to themselves on a supported destination chain. The same attack works in reverse: an attacker holding synth on a remote chain can bridge in until `bridgedInSupply() > maxBridgedInSupply` makes `_creditTo` → `_mint` revert [4](#0-3) , sending honest users' inbound transfers into `failedMessages` where they sit until retried after the cap condition clears [5](#0-4) .

### Impact Explanation
Temporary freezing of user funds. Once the cap is saturated, `sendFrom` reverts for every user, so synth holders cannot move funds off the chain — economically equivalent to the Shibarium bridge lock-up. In-flight inbound messages revert during `lzReceive` and are only recoverable via `retryMessage` after net flow reverses or the governor raises the cap. The attacker's funds are not lost (they remain owned on the destination chain) and the attacker can un-block/re-block at will by shuttling their own tokens back and forth, because each bridge-in lowers `bridgedOutSupply` and each bridge-out raises it again.

### Likelihood Explanation
Requires the attacker to control synth liquidity comparable to the configured caps (e.g., `maxBridgedOutSupply` of 40M msUSD or 4500 msETH on mainnet per deploy config). The net-out headroom (`maxBridgedOutSupply - bridgedOutSupply`) determines the true cost; when the bridge is deeply net-in, the attack can require less than the raw cap or may be impractical. No privileged role, oracle manipulation, or governance action is needed — only public `sendFrom` calls and ordinary token ownership. The denial is temporary: it resolves if the governor raises the cap or net bridge-in flow increases, but the attacker alone controls the toggle as long as they keep their tokens parked on the remote chain.

### Recommendation
- Decouple user-facing bridge liveness from the global cap: e.g., revert only the amount exceeding the cap rather than the whole transfer, or queue excess.
- Add per-transaction/per-account bridge-out limits or a time-windowed rate limit so a single actor cannot consume the entire headroom.
- For the inbound direction, consider letting the cap check emit a `MessageFailed`-creditable refund path instead of relying solely on `retryMessage` after cap changes.
- Monitor `bridgedOutSupply`/`bridgedInSupply` against caps so the governor can raise caps before saturation is weaponized.

### Proof of Concept
Hardhat fork outline (mainnet fork, mirroring `test/E2E.mainnet.test.ts` bridge setup):

```ts
// Fork mainnet; use deployed msUSD, msUSDProxyOFT, poolRegistry, msdWETH_1, msUSDDebt_1.
const headroom = (await msUSD.maxBridgedOutSupply()).sub(await msUSD.bridgedOutSupply());

// Attacker obtains `headroom + dust` msUSD via debt.issue() against deposited collateral
// (or via pool.swap / market buy), then bridges it all out to self:
await msUSDProxyOFT['sendFrom(address,uint16,address,uint256)'](
  attacker.address, LZ_OP_CHAIN_ID, attacker.address, headroom.add(1),
  { value: parseEther('0.5') }
);
// bridgedOutSupply() is now at/over maxBridgedOutSupply.

// Victim's ordinary bridge-out now reverts:
await expect(
  msUSDProxyOFT.connect(victim)['sendFrom(address,uint16,address,uint256)'](
    victim.address, LZ_OP_CHAIN_ID, victim.address, parseEther('1'),
    { value: parseEther('0.5') }
  )
).to.be.revertedWithCustomError(msUSD, 'SurpassMaxBridgingSupply');
// Victim's msUSD is frozen on L1 until the attacker bridges back or the cap is raised.
```

    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");

        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
    }
