### Title
`add_public_key`/`remove_public_key`/`disable_auth_by_predecessor_id` not blocked by `#[pause]` unlike all other state-mutating account functions - (File: contracts/defuse/src/contract/accounts/mod.rs)

### Summary
Every other state-mutating entrypoint in the `defuse` contract (`execute_intents`, `simulate_intents`, `mt_withdraw`, `nft_withdraw`, `imt_burn`, `add_relayer_key`, `delete_relayer_key`, `set_fee`, `set_fee_collector`, `deploy_token`, etc.) is annotated with `#[pause]`/`#[pause(name = "...")]` so it reverts once `PauseManager`/`DAO` pauses the contract. The `AccountManager` impl functions `add_public_key`, `remove_public_key`, and `disable_auth_by_predecessor_id` in `contracts/defuse/src/contract/accounts/mod.rs` mutate account credential state but carry no `#[pause]` guard, so they remain callable while the protocol is paused — mirroring the `cooldown()` finding in the referenced report where a state-changing function was left out of the emergency-mode check that protected all sibling functions.

### Finding Description
The contract derives `Pausable` and gates state-changing methods across the codebase with `#[pause]`: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

However `AccountManager for Contract` defines `add_public_key`, `remove_public_key`, and `disable_auth_by_predecessor_id` without any `#[pause]` attribute, unlike the sibling `ForceAccountManager` impl (`force_lock_account`, `force_unlock_account`) which is access-controlled but at least role-gated: [5](#0-4) 

These three functions directly mutate the credential/auth surface used by `execute_signed_intent` to authorize `MultiPayload`s: `has_public_key` checks are what the engine relies on to accept a signature as valid for `signer_id`: [6](#0-5) 

Because they lack `#[pause]`, an account holder can add a new public key, remove an existing one, or toggle `disable_auth_by_predecessor_id` while the contract is paused (e.g., during an incident response where the DAO pauses `intents`/withdrawal families expecting the whole surface to freeze). This breaks the equality the protocol implicitly relies on during a pause: "credentials authorized to move funds" should not change while "funds cannot move" is enforced. An attacker (or a user racing an incident) can pre-stage a new signing key during the pause window, then use it the instant the pause is lifted to execute intents that would not have been possible with the pre-pause key set — analogous to the `cooldown()` bug where a user could set up a future-privileged state during emergency mode to exploit once the emergency ended.

### Impact Explanation
This does not by itself move funds, but it lets an attacker manipulate the authorization set (`public_keys_added`/`removed`, `auth_by_predecessor_id` toggle) during a pause meant to freeze the contract, undermining the incident-response guarantee that "nothing about custody/authorization changes while paused." Combined with `execute_intents` being paused too, the practical exploitation window is at unpause time, but the state change (which keys are valid signers for an account) happens unauthorized-by-policy during the frozen period. This is best classified under authorization-boundary weakening rather than a direct fund-loss primitive, since no `TokenId`/balance/signature-of-record binding is broken in a single atomic step — this weakens confidence in the Critical/High bar the rules require (an intent executed against a locked account, or a wallet executing an unauthorised `Request`). I could not find evidence that a *locked* account can bypass this (locking still blocks `add_public_key`/`remove_public_key` per `internal_add_balance`/`get_or_create` failing with `AccountLocked`, as demonstrated in `tests/src/tests/defuse/accounts/force.rs`), so the exposure is narrower than full fund theft.

### Likelihood Explanation
Requires the DAO/PauseManager to actually invoke `pause("intents")`/global pause during an incident, and requires an attacker to have (or race for) predecessor-ID-based auth control of the target account, which is normally the account owner. This is a self-serve action by an account owner over their own account, so there's no privileged party requirement to exploit it — but it does depend on an emergency pause being active, which is an infrequent event.

### Recommendation
Add `#[pause]` (or a dedicated `#[pause(name = "accounts")]`) to `add_public_key`, `remove_public_key`, and `disable_auth_by_predecessor_id` in `contracts/defuse/src/contract/accounts/mod.rs`, consistent with every other state-mutating entrypoint, so that credential/authorization changes are frozen along with fund movement during an emergency pause.

### Proof of Concept
1. DAO/PauseManager calls `pause(name = "intents")` (or whichever pause names are configured) to halt `execute_intents`, withdrawals, etc. [1](#0-0) 
2. During the pause, an account owner (attacker) calls `add_public_key` on their own account — this succeeds because the function has no `#[pause]` guard: [7](#0-6) 
3. Once the pause is lifted, the attacker signs `MultiPayload`s with the newly added key via `execute_intents`, which validates against `has_public_key` set up during the frozen window: [6](#0-5) 

Note: I was unable to fully confirm from the index whether `#[pause]` was intentionally omitted here for a documented reason (e.g., self-custody key rotation being deliberately excluded from pause scope) — this would need explicit confirmation from the project maintainers or design docs not present in the indexed files.
