### Title
Unbounded blocking HTTP client in `/heartbeat` handler causes unauthenticated DoS of the entire monitoring server - (File: stacks-signer/src/monitoring/server.rs)

### Summary
`MonitoringServer::new` constructs `stacks_node_client` with `reqwest::blocking::Client::new()` and no `.timeout(...)`/`.connect_timeout(...)` configured. `heartbeat()` performs a fully synchronous, unbounded `self.stacks_node_client.get(url).send()` inside the single-threaded `main_loop`, so any remote caller hitting `GET /heartbeat` while the configured Stacks node is unreachable/slow blocks the only server thread indefinitely, denying `/metrics`, `/info`, and `/` to all other callers.

### Finding Description
`MonitoringServer` runs a single-threaded accept loop in `main_loop` ( [1](#0-0) ) that calls `self.http_server.recv()` and then handles the request synchronously before looping back to accept the next one — there is no per-request thread spawn or async dispatch.

The `/heartbeat` route calls `self.heartbeat()` synchronously and only responds after it returns ( [2](#0-1) ). `heartbeat()` issues a blocking GET to the configured `stacks_node_origin` ( [3](#0-2) ).

The `stacks_node_client` used for that GET is built with `reqwest::blocking::Client::new()` and no timeout configuration at all: [4](#0-3) . A search of `stacks-signer/src/monitoring/server.rs` confirms there is no `.timeout(...)` call anywhere in this file, unlike other reqwest client construction sites in the crate. `reqwest::blocking::Client::new()` has no default request timeout, so `send()` can block indefinitely on TCP connect, TLS handshake, or waiting for a response if the target host is down, filtered, or slow to respond.

Because `main_loop` is single-threaded and processes requests strictly sequentially, a single `GET /heartbeat` request that triggers this unbounded blocking call gates every subsequent request on the metrics port (`/metrics`, `/info`, `/`, and any other `/heartbeat`) forever — there is no guard, no read/connect timeout, and no per-request concurrency to bound the exposure.

### Impact Explanation
An unauthenticated remote party able to reach the signer's metrics endpoint can send one `GET /heartbeat` request and, if `stacks_node_origin` is unreachable or slow (a condition that can occur naturally via network partition/misconfiguration, or that the attacker may be able to induce/target if they also control or influence reachability to that origin), permanently stall the monitoring server's single thread. This denies Prometheus scraping (`/metrics`) and `/info`/health checks to all legitimate operators indefinitely, from a single request, matching the "remote crash/unauthenticated DoS from few messages" Critical category applied to this component's availability.

### Likelihood Explanation
Preconditions: the attacker needs network reachability to the configured `metrics_endpoint` (no authentication is required for any of these routes) and the `stacks_node_origin` to be slow/unreachable for the request thread to hang. The attacker needs no privileged role, no secret, and only a single HTTP GET is required; effect is trivially repeatable/permanent once triggered, and the fault is entirely due to the missing timeout in this file's client construction rather than any external network flooding.

### Recommendation
Configure explicit `.timeout(...)` and `.connect_timeout(...)` values on `stacks_node_client` when it is built (`reqwest::blocking::Client::builder().timeout(...).connect_timeout(...).build()`), and/or move heartbeat handling off the single accept-loop thread (e.g., spawn a thread per request or use a thread pool) so a slow upstream cannot stall unrelated endpoints.

### Proof of Concept
1. Start a raw TCP listener on `127.0.0.1:PORT` that accepts connections but never writes any response bytes (simulating an unresponsive `stacks_node_origin`).
2. Construct a `MonitoringServer` with `stacks_node_origin = format!("http://127.0.0.1:{PORT}")` and bind its `http_server` to a test port.
3. In one thread, issue `GET /heartbeat` to the monitoring server.
4. Concurrently, from a second thread, issue `GET /metrics` to the same monitoring server with a bounded deadline (e.g., 5s read timeout on the test's own HTTP client).
5. Assert that the `/metrics` request does not return within the bounded deadline, demonstrating that the hung `heartbeat()` call (blocked in `self.stacks_node_client.get(url).send()` at `stacks-signer/src/monitoring/server.rs:227`) starves `main_loop`'s single request-processing thread and denies service to all other callers.
