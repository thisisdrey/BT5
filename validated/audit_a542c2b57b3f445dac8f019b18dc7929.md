Audit Report

## Title
`pallet-revive` derives contract address and storage `trie_id` from a reapable account nonce, enabling address/trie-id reuse after account dusting - (File: `substrate/frame/revive/src/exec.rs`, `substrate/frame/revive/src/storage.rs`)

## Summary
`pallet-revive`'s CREATE1 address and the contract's storage `trie_id` are both derived from `System::account_nonce(&sender)`, an account-scoped counter that `frame_system` resets to `0` when an account is fully reaped (`providers == 0 && consumers == 0 && sufficients == 0`) [1](#0-0) [2](#0-1) . `pallet-contracts` avoids exactly this failure mode with a dedicated, never-decremented `Nonce<T>` counter, whose doc comment explicitly warns against deriving trie ids from a value that can repeat, precisely because trie deletion is lazy and could collide with stale storage from a prior instantiation at the same trie_id [3](#0-2) .

## Finding Description
`ContractInfo::new` computes `trie_id = hash("bcontract_trie_v1", address, nonce)` from the caller-supplied `nonce` argument [4](#0-3) , and the only caller for user-driven instantiation passes `<System<T>>::account_nonce(&sender)` directly as that nonce, with the CREATE1 address computed from the same nonce (adjusted by one when it was already incremented pre-dispatch) [1](#0-0) . Deletion of a terminated contract's child-trie storage is explicitly lazy: `queue_for_deletion` pushes the trie into `DeletionQueueManager` for later draining by `process_deletion_queue_batch`/`on_idle`, rather than clearing it synchronously at termination time [5](#0-4) .

`ContractInfo::new` guards only against reinstantiating at an address that is *currently* a live contract (`is_contract` check) and against addresses with pending `NativeDepositOf` cleanup rows, but it performs no check against reuse of a `trie_id` value that a *previously terminated* contract used, once that contract's `NativeDepositOf` rows (if any) have been drained and the address is again free [6](#0-5) . Because `frame_system::Account`, including its `nonce` field, is deleted entirely on reaping via `dec_providers`/`dec_sufficients` → `on_killed_account`, and restarts from `0` on refund, this creates a path where `create1(deployer, 0)` and the resulting `trie_id` hash can repeat for the same deployer address across two different, unrelated contract lifetimes.

## Impact Explanation
If exploitable, this would violate the storage-isolation invariant between successive contract instantiations at the same address — a newly instantiated contract could inherit or collide with un-drained child-trie storage from a prior, terminated contract queued in `DeletionQueue`, corrupting the new contract's storage state. This matches the "runtime bug that compromises intended behavior" category in the impact gate, mirroring the exact bug class `pallet-contracts::Nonce<T>`'s doc comment was written to prevent.

However, I was unable to fully verify, within the available tool budget, whether the current `pallet-revive` deletion-queue design has additional safeguards (beyond the `NativeDepositOf`/`PendingDepositCleanup` check already present in `ContractInfo::new`) that specifically block reinstantiation while a trie is still queued for deletion — e.g., whether `DeletionQueueManager`/`is_contract` state, or a similar queued-trie-id check, is consulted before allowing address reuse. The code I reviewed shows a `PendingDepositCleanup` guard tied to `NativeDepositOf` rows, but I could not confirm from the index whether an analogous check exists (or is missing) for the underlying child-trie contents themselves, which is the crux of the claim.

## Likelihood Explanation
The account-nonce-reset mechanism itself is confirmed and reproducible: `frame_system`'s reaping logic deletes `AccountInfo` (nonce included) once `providers/consumers/sufficients` all reach zero [2](#0-1) , and `dust_account_removal_should_work`/`provider_ref_handover_to_self_sufficient_ref_works` confirm `account_nonce` returns to `0` after reaping [7](#0-6) [8](#0-7) . All operations needed (draining an account, refunding it, redeploying without a salt) are ordinary permissionless extrinsics available to any account. What remains unverified is whether the deletion queue's drain timing/ordering and the `PendingDepositCleanup`/`is_contract` checks in `ContractInfo::new` are actually sufficient in the current codebase to prevent the trie-id collision described — I could not locate or confirm a Proof-of-Concept-style regression test analogous to `pallet-contracts`'s `instantiate_unique_trie_id` for `pallet-revive`, nor could I fully trace whether the deletion queue guarantees the old trie's keys are physically gone (or blocked from reuse) before a same-address/same-nonce reinstantiation is permitted.

## Recommendation
Introduce a dedicated, monotonic, never-decremented counter (analogous to `pallet-contracts::Nonce<T>`) for `pallet-revive`'s `trie_id` derivation instead of reusing the reapable `System::account_nonce`, and/or extend the guard in `ContractInfo::new` to reject reinstantiation while any deletion-queue entry for the same trie_id/address is still pending, closing the gap between address/nonce reuse and lazy trie cleanup. Given the incomplete verification above, further investigation (ideally via a background Devin session with full repository and test-execution access) is needed to confirm whether the `DeletionQueueManager` state is actually checked against reinstantiation, before treating this as a confirmed, currently-exploitable bug rather than a design-risk observation.

## Proof of Concept
Not independently verified end-to-end in this review; the claim's proposed reproduction (drain account to reap it, refund it to reset nonce to 0, terminate+redeploy a no-salt contract at the same address/nonce, and check for observable stale storage) is plausible given the confirmed nonce-reset behavior and lazy-deletion-queue design, but requires execution against the live pallet-revive test harness (e.g., an `instantiate_unique_trie_id`-style test as in `pallet-contracts`) to confirm whether existing guards (`is_contract`, `PendingDepositCleanup`) actually prevent the collision.

#[test]
fn provider_ref_handover_to_self_sufficient_ref_works() {
	new_test_ext().execute_with(|| {
		assert_eq!(System::inc_providers(&0), IncRefStatus::Created);
		System::inc_account_nonce(&0);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// a second reference coming and going doesn't change anything.
		assert_eq!(System::inc_sufficients(&0), IncRefStatus::Existed);
		assert_eq!(System::dec_sufficients(&0), DecRefStatus::Exists);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// a provider reference coming and going doesn't change anything.
		assert_eq!(System::inc_providers(&0), IncRefStatus::Existed);
		assert_eq!(System::dec_providers(&0).unwrap(), DecRefStatus::Exists);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// decreasing the providers with a self-sufficient present should not delete the account
		assert_eq!(System::inc_sufficients(&0), IncRefStatus::Existed);
		assert_eq!(System::dec_providers(&0).unwrap(), DecRefStatus::Exists);
		assert_eq!(System::account_nonce(&0), 1u64.into());

		// decreasing the sufficients should delete the account
		assert_eq!(System::dec_sufficients(&0), DecRefStatus::Reaped);
		assert_eq!(System::account_nonce(&0), 0u64.into());
	});
}
