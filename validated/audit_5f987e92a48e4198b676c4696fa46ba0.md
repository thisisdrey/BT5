Audit Report

## Title
`snowbridge-pallet-outbound-queue-v2` trusts an attacker-controlled `fee` field embedded in an unexecuted nested XCM program, allowing unbacked relayer reward payouts - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs, bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs, bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs, polkadot/xcm/xcm-executor/src/lib.rs)

## Summary
`SendMessage::validate`/`deliver` for `snowbridge-pallet-outbound-queue-v2` never verify the `fee` field of a `Message` against any amount actually collected from the sender [1](#0-0) . For the XCM export path, the `fee` is derived by `XcmConverter::extract_remote_fee` purely by pattern-matching `WithdrawAsset`/`PayFees` instructions embedded *inside the nested `xcm` argument* of an `ExportMessage` instruction [2](#0-1) . Critically, the XCM executor's `ExportMessage` handler never executes that nested `xcm` program against the origin's real holding/account — it passes it opaquely to the `MessageExporter`, and only debits the origin using the *exporter-returned* delivery fee via `take_fee` [3](#0-2) , which the v2 `EthereumBlobExporter::validate` hard-codes to `Assets::default()` (i.e., zero) [4](#0-3) . This means the `WithdrawAsset`/`PayFees` values used to compute `fee` are never actually taken from anyone — they are attacker-suppliable literal data, not real fund movement.

## Finding Description
The v2 send pipeline is: `SendMessage::validate` → `SendMessage::deliver` → `do_process_message` builds `PendingOrder{nonce, fee, block_number}` → `submit_delivery_receipt` pays `fee` to the relayer via `RewardPayment` [5](#0-4) . `validate()` only checks payload size and returns the `Message` unchanged as the ticket, performing no fee computation or comparison (unlike v1, which computes fee from `GasMeter`/`PricingParameters` and returns it separately for the caller to charge) [1](#0-0) . `do_process_message` decodes the queued bytes and writes `fee` straight into `PendingOrder` with no cross-check against any escrow [6](#0-5) .

For the XCM producer path, `EthereumBlobExporter::validate` receives the `xcm` argument of an `ExportMessage` instruction and feeds it to `XcmConverter::convert`, which calls `extract_remote_fee` to read a `WithdrawAsset(fee_asset)` followed by `PayFees{asset: fee_asset}` from *within that nested program* and uses `fee_amount` (bounded only by `reserved_fee_amount >= fee_amount`, both taken from the same untouched data) to populate `Message.fee` [2](#0-1) [7](#0-6) .

The decisive fact is how the XCM executor handles `ExportMessage`: it does **not** interpret the nested `xcm` as instructions to execute against the origin's holding register; it passes `xcm` by value into `validate_export::<Config::MessageExporter>`, and the *only* real balance deduction performed against the origin is `self_ref.take_fee(fee, FeeReason::Export{...})`, where `fee` is the second return value of the exporter's own `validate` [3](#0-2) . For v2, `EthereumBlobExporter::validate` returns `Assets::default()` as that delivery fee [4](#0-3) , so `take_fee` is invoked with an empty asset list and is a no-op (its own logic short-circuits with `Ok(())` when `fees.get(0)` is `None`). Consequently, the `WithdrawAsset`/`PayFees` values inside the nested `xcm` that determine `Message.fee` never correspond to any actual balance debit performed by the local XCM executor — they are just literal AST data supplied by whoever constructed the top-level XCM program (e.g., via `pallet_xcm::execute`, subject only to whatever barrier/filter gates top-level XCM execution and the `AllowedAliasOrigin` check on the `AliasOrigin` instruction, which constrains impersonation but not the fee amount).

This confirms and resolves the uncertainty flagged in the original report: it explicitly stated it could not verify "whether that exporter path enforces an equivalent burn/withdraw of exactly `fee`." The executor code shows it does not — the exporter's returned delivery-fee (`Assets::default()`) is unrelated to the `fee` value embedded in the `Message`, and the embedded `WithdrawAsset`/`PayFees` are never executed as real withdrawals.

The only path where `fee` is provably backed by a real burn is `snowbridge_pallet_system_v2::Pallet::send`, invoked with `amount` from `swap_fee_asset_and_burn` (a genuine burn) for `register_token`/`add_tip`, or hardcoded to `0` for `upgrade`/`set_operating_mode` [8](#0-7) [9](#0-8) . The XCM `EthereumBlobExporter` v2 path provides no such guarantee.

## Impact Explanation
`PendingOrder.fee` is paid to the relayer via `RewardPayment: RewardLedger` upon `submit_delivery_receipt` [10](#0-9) . Since the fee embedded via the XCM export path is not backed by any real withdrawal enforced by the executor (confirmed above), an attacker able to submit a top-level XCM program containing an `ExportMessage` instruction whose nested `xcm` declares an inflated `WithdrawAsset`/`PayFees` amount can cause `PendingOrder.fee` to be set to an arbitrary value with zero real cost, producing unbacked relayer payouts — theft/unbacked-mint-style impact against the bridge's reward funds, matching the program's allowed impact categories.

## Likelihood Explanation
Feasibility depends on whether an unprivileged account can submit a top-level XCM program containing `ExportMessage` (e.g., via `pallet_xcm::execute`) that reaches the `EthereumBlobExporter` v2 exporter on the relevant runtime (e.g., asset-hub) without being blocked by barriers/safe-call filters, and whether the `AllowedAliasOrigin` filter (`EverythingBut<Equals<AssetHubLocation>>` in the observed test config) restricts the usable `AliasOrigin`. I was not able to confirm, within the available tool budget, whether production runtime XCM barriers actually permit an ordinary signed account to submit a top-level `ExportMessage` instruction directly through `pallet_xcm::execute`, or whether other constraints (e.g., requiring the message to originate from a sibling parachain's XCMP queue rather than local `execute`) prevent this. The pallet-internal code path itself (`outbound-queue-v2` and the `EthereumBlobExporter`/`ExportMessage` executor logic) is confirmed to provide no defense-in-depth check tying `Message.fee` to a real balance debit.

## Recommendation
Either (a) have `EthereumBlobExporter::validate` return a real delivery-fee `Assets` value (instead of `Assets::default()`) equal to the `fee_amount` extracted from the nested `xcm`, so the XCM executor's `take_fee` genuinely debits the origin for that amount before `deliver` is called, or (b) move fee verification into `snowbridge-pallet-outbound-queue-v2::SendMessage::validate`/`do_process_message`, requiring proof (e.g., an escrow/reserve receipt) that `fee` was actually collected, mirroring the v1 design where `validate` computes and independently returns the fee for the caller to charge.

## Proof of Concept
1. Construct a top-level XCM program (submitted via any mechanism that reaches the AH-to-Ethereum `EthereumBlobExporter` v2 exporter, e.g. `pallet_xcm::execute` if permitted) containing a single `ExportMessage { network: Ethereum, destination: Here, xcm: [WithdrawAsset(Ether, HUGE), PayFees{Ether, HUGE}, AliasOrigin(some_allowed_location), DepositAsset{...}, SetTopic(...)] }`.
2. Observe that the executor's `ExportMessage` handler passes the nested `xcm` to `validate_export::<EthereumBlobExporter>` without executing `WithdrawAsset`/`PayFees` against the origin's holding (see `polkadot/xcm/xcm-executor/src/lib.rs` lines 1672-1712), and that `take_fee` is called with `Assets::default()` returned by the exporter, so no funds are actually taken from the sender.
3. Observe `XcmConverter::extract_remote_fee` sets `Message.fee = HUGE` from the (unexecuted) nested `WithdrawAsset`/`PayFees` data (`bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs` lines 94-117, 312-317).
4. Observe `outbound-queue-v2::do_process_message` stores `PendingOrder{fee: HUGE, ...}` verbatim (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 422-436).
5. After a relayer submits a valid delivery receipt for this message, `RewardPayment::pay` credits `HUGE` to the relayer — an unbacked payout, since no real asset of value `HUGE` was ever withdrawn from the attacker.
A full end-to-end reproduction (unit/integration test) would require confirming the exact runtime configuration that permits an unprivileged account to submit the crafted `ExportMessage` XCM to the exporter; this final confirmation should be done with a Devin session that has full repository/runtime access to trace the barrier/filter configuration for `pallet_xcm::execute` on the target runtime (e.g. asset-hub-westend).

	/// Extract the fee asset item from PayFees(V5)
	fn extract_remote_fee(&mut self) -> Result<u128, XcmConverterError> {
		use XcmConverterError::*;
		let reserved_fee_assets = match_expression!(self.next()?, WithdrawAsset(fee), fee)
			.ok_or(WithdrawAssetExpected)?;
		ensure!(reserved_fee_assets.len() == 1, AssetResolutionFailed);
		let reserved_fee_asset =
			reserved_fee_assets.inner().first().cloned().ok_or(AssetResolutionFailed)?;
		let (reserved_fee_asset_id, reserved_fee_amount) = match reserved_fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		let fee_asset =
			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;
		let (fee_asset_id, fee_amount) = match fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, *amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		// Check the fee asset is Ether (XCM is evaluated in Ethereum context).
		ensure!(fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_amount >= fee_amount, InvalidFeeAsset);
		Ok(fee_amount)
	}

	pub fn convert(&mut self) -> Result<Message, XcmConverterError> {
		// Get fee amount
		let fee_amount = self.extract_remote_fee()?;

		// Get ENA reserve asset from WithdrawAsset.
		let mut enas =
			match_expression!(self.peek(), Ok(WithdrawAsset(reserve_assets)), reserve_assets);
		if enas.is_some() {
			let _ = self.next();
		}

		// Get PNA reserve asset from ReserveAssetDeposited
		let pnas = match_expression!(
			self.peek(),
			Ok(ReserveAssetDeposited(reserve_assets)),
			reserve_assets
		);
		if pnas.is_some() {
			let _ = self.next();
		}

		// Try to get ENA again if it is after PNA
		if enas.is_none() {
			enas =
				match_expression!(self.peek(), Ok(WithdrawAsset(reserve_assets)), reserve_assets);
			if enas.is_some() {
				let _ = self.next();
			}
		}
		// Check AliasOrigin.
		let origin_location = match_expression!(self.next()?, AliasOrigin(origin), origin)
			.ok_or(AliasOriginExpected)?;

		// Validate the AliasOrigin using the configured AllowedAliasOrigin filter.
		// This provides a mechanism for the runtime to restrict which origins
		// are permitted to alias, providing defense-in-depth against
		// unprivileged alias attempts.
		ensure!(AllowedAliasOrigin::contains(origin_location), InvalidOrigin);

		let origin = AgentIdOf::convert_location(origin_location).ok_or(InvalidOrigin)?;

		let (deposit_assets, beneficiary) = match_expression!(
			self.next()?,
			DepositAsset { assets, beneficiary },
			(assets, beneficiary)
		)
		.ok_or(DepositAssetExpected)?;

		// assert that the beneficiary is AccountKey20.
		let recipient = match_expression!(
			beneficiary.unpack(),
			(0, [AccountKey20 { network, key }])
				if self.network_matches(network),
			H160(*key)
		)
		.ok_or(BeneficiaryResolutionFailed)?;

		let mut commands: Vec<Command> = Vec::new();

		// ENA transfer commands
		if let Some(enas) = enas {
			commands.append(&mut self.extract_ethereum_native_assets(
				enas,
				deposit_assets,
				recipient,
			)?);
		}

		// PNA transfer commands
		if let Some(pnas) = pnas {
			commands.append(&mut self.extract_polkadot_native_assets(
				pnas,
				deposit_assets,
				recipient,
			)?);
		}

		// Transact commands
		let transact_call = match_expression!(self.peek(), Ok(Transact { call, .. }), call);
		if let Some(transact_call) = transact_call {
			let _ = self.next();
			let transact =
				ContractCall::decode_all(&mut transact_call.clone().into_encoded().as_slice())
					.map_err(|_| TransactDecodeFailed)?;
			match transact {
				ContractCall::V1 { target, calldata, gas, value } => commands
					.push(Command::CallContract { target: target.into(), calldata, gas, value }),
			}
		}

		ensure!(commands.len() > 0, NoCommands);

		// ensure SetTopic exists
		let topic_id = match_expression!(self.next()?, SetTopic(id), id).ok_or(SetTopicExpected)?;

		let message = Message {
			id: (*topic_id).into(),
			origin,
			fee: fee_amount,
			commands: BoundedVec::try_from(commands).map_err(|_| TooManyCommands)?,
		};

		// All xcm instructions must be consumed before exit.
		if self.next().is_ok() {
			return Err(EndOfXcmMessageExpected);
		}

		Ok(message)
	}
