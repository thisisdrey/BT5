### Title
Re-delegating a small locked resource amount unfairly resets/extends the unlock time of the entire previously-locked balance - ([File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java])

### Summary
`DelegateResourceActuator.delegateResource()` calls `DelegatedResourceCapsule.addFrozenBalanceForBandwidth`/`addFrozenBalanceForEnergy` to accumulate a new locked-delegation amount into any existing locked balance for the same `(owner, receiver)` pair, but it **overwrites** `expireTimeForBandwidth`/`expireTimeForEnergy` with the newly computed `expireTime` for the whole combined balance instead of computing a size-weighted, or at least amount-scoped, unlock time. [1](#0-0) 

### Finding Description
When a user calls `DelegateResourceContract` with `lock=true` against a receiver they have already locked resources with, `delegateResource()` in `DelegateResourceActuator` fetches the existing `DelegatedResourceCapsule` for key `createDbKeyV2(owner, receiver, true)` and calls `addFrozenBalanceForBandwidth(balance, expireTime)` (or the energy equivalent). [2](#0-1) 

That method adds the new `balance` to the existing frozen amount but replaces the stored expire time with the new call's `expireTime`, discarding the previous unlock schedule entirely: [3](#0-2) 

The only guard against shortening the lock is `validRemainTime()`, which merely enforces that the *new* `lockPeriod` must be at least as long as the *remaining* time of the existing lock — it does not prevent a full-length new `lockPeriod` (which is the default when `lockPeriod == 0`, i.e. `DELEGATE_PERIOD / BLOCK_PRODUCED_INTERVAL`) from being applied to the *entire* combined balance, including the portion that was about to unlock. [4](#0-3) [5](#0-4) 

This exactly mirrors the FlatMoney `_setMintUnlockTime` bug class: a large already-vested/near-unlock balance gets its full unlock timer reset because of a small additional deposit, unfairly penalizing users who use the delegate feature more than once for the same receiver. The locked balance cannot be withdrawn early: `UnDelegateResourceActuator.validate()` requires `lockResourceCapsule.getExpireTimeForBandwidth() < now` (or the energy equivalent) before any of the locked amount — including the pre-existing, already near-expiry portion — can be un-delegated. [6](#0-5) 

### Impact Explanation
A user who has, e.g., 1,000,000 TRX locked and about to unlock in 1 second, and then delegates 1 additional TRX with `lock=true` (even using the default/minimum lock period), has the *entire* 1,000,001 TRX locked balance's unlock time pushed out by the full new lock period (default `DELEGATE_PERIOD`). Until that new expire time passes, `UnDelegateResourceActuator` will reject any un-delegation attempt for the locked balance, effectively freezing funds the user reasonably expected to be unlockable. This is an unfair, protocol-enforced temporary freezing of funds triggered by normal use of the delegate-resource feature — reachable by any unprivileged account via a single `DelegateResourceContract` transaction.

### Likelihood Explanation
High likelihood of occurring accidentally (any user who delegates resources to the same receiver more than once while locked balance is still outstanding triggers this), and it can also be exploited maliciously against oneself is not useful, but is a real usability/fairness flaw that a user could be tricked into or stumble into unknowingly — e.g., a wallet/dapp that "tops up" a lock delegation.

### Recommendation
When merging a new locked delegation into an existing `DelegatedResourceCapsule` entry, compute a weighted/blended expire time (or track sub-batches with independent expire times) rather than overwriting the expire time for the entire combined balance. At minimum, only the newly added `balance` portion should be subject to the new lock period, while the already-locked portion should retain its original expire time.

### Proof of Concept
1. User A calls `DelegateResourceContract{owner=A, receiver=B, resource=BANDWIDTH, balance=1_000_000 TRX, lock=true, lockPeriod=0}` at `t=0`. This creates `DelegatedResourceCapsule` key `V2_LOCK_PREFIX|A|B` with `frozenBalanceForBandwidth=1_000_000`, `expireTimeForBandwidth = t0 + DELEGATE_PERIOD` (see `delegateResource`). [7](#0-6) 
2. Just before `expireTimeForBandwidth` is reached (e.g., 1 block before expiry), user A calls the same contract again with `balance=1 TRX, lock=true, lockPeriod=0` targeting the same receiver B. `validRemainTime` passes because the default lock period trivially satisfies `lockPeriod*BLOCK_PRODUCED_INTERVAL >= remainTime` (remainTime is near zero). [5](#0-4) 
3. `addFrozenBalanceForBandwidth(1, newExpireTime)` sets `frozenBalanceForBandwidth = 1_000_001` and `expireTimeForBandwidth = newExpireTime (= now + DELEGATE_PERIOD)`, overwriting the almost-expired timestamp for the whole 1,000,001 TRX balance. [1](#0-0) 
4. User A now cannot un-delegate any part of the 1,000,001 TRX (including the original 1,000,000 TRX that was about to unlock) until the new, much later `expireTimeForBandwidth`, because `UnDelegateResourceActuator.validate()` checks `lockResourceCapsule.getExpireTimeForBandwidth() < now` before allowing withdrawal of the locked portion. [8](#0-7)

  private void validRemainTime(ResourceCode resourceCode, long lockPeriod, long expireTime,
      long now) throws ContractValidateException {
    long remainTime = expireTime - now;
    if (lockPeriod * BLOCK_PRODUCED_INTERVAL < remainTime) {
      throw new ContractValidateException(
          "The lock period for " + resourceCode.name() + " this time cannot be less than the "
              + "remaining time[" + remainTime + "ms] of the last lock period for "
              + resourceCode.name() + "!");
    }
  }
