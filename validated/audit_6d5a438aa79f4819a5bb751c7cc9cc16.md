## Title
Reward accrued for a witness with zero votes in a maintenance cycle is permanently unclaimable / lost - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
`DelegationStore.accumulateWitnessVi` computes the per-cycle reward-per-share value (`Vi`) that all voters use to withdraw their share of a witness's block/transaction-fee rewards. When the witness's total vote count for a cycle is zero, the function silently drops the reward instead of accounting for it, making that reward permanently unclaimable — the same root cause pattern as the reported `updateGlobalExchangeRate`/`totalGlobalShares == 0` bug in the C4 finding.

### Finding Description
Block and transaction-fee rewards for a standby/active witness are accumulated per maintenance cycle via `MortgageService.payReward`, which stores the raw reward amount keyed by `(cycle, witnessAddress)` in `DelegationStore` regardless of whether the witness currently has any voters: [1](#0-0) 

The only mechanism that turns this raw per-cycle reward into something a voter can later claim is the `Vi` (value-per-vote) accumulator, computed in `DelegationStore.accumulateWitnessVi`: [2](#0-1) 

This mirrors the duplicated logic in `RewardViCalService.accumulateWitnessVi`, used for the one-time migration of the new reward algorithm: [3](#0-2) 

In both places, if `voteCount == 0` for the cycle in which the reward was recorded, the code takes the "just forward pre Vi" branch — it does **not** roll the reward forward into a future cycle's `Vi`, and does not refund/redirect it anywhere. The raw reward value written by `addReward` stays keyed to that specific `(cycle, address)` pair and is never read again by any withdrawal path — `MortgageService.computeReward`/`VoteRewardUtil.computeReward` only ever consult `getWitnessVi(cycle, address)` deltas, never `getReward` directly: [4](#0-3) [5](#0-4) 

A witness's per-cycle vote count (`getWitnessVote`) can legitimately become `0` for a cycle while the witness is still standby/active and still receiving block or transaction-fee rewards for that cycle — e.g. all of a witness's voters withdraw their votes/stake through normal, unprivileged user flows such as `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor` or by calling `voteWitness` via the TVM to clear their votes: [6](#0-5) [7](#0-6) 

Because witness election/standby status is determined per maintenance cycle while individual votes can be withdrawn at any time within that cycle window, it is possible for `getWitnessVote(cycle, address)` to be `0` for a cycle in which the witness still produced blocks and accrued reward via `payReward`. This is exactly analogous to the C4 report's scenario where `totalGlobalShares` becomes `0` after unstaking/`disableValidator`, while rewards keep accruing and become permanently locked.

### Impact Explanation
Any reward recorded for a witness in a cycle where its aggregate vote count is `0` is silently and permanently lost — no voter can ever claim it (there is no vote weight to attribute it to), and the protocol has no other path to recover, redistribute, or account for it. This constitutes a permanent loss/freezing of protocol-issued reward funds, matching the "Assets... leak value... with a hypothetical attack path with stated assumptions" Medium-severity classification given by the original judge for the analogous Solidity bug.

### Likelihood Explanation
Reachable purely through unprivileged, everyday actions: voters unstaking/canceling votes (`UnfreezeBalanceV2Actuator`, `UnfreezeBalanceV2Processor`, TVM `voteWitness`) can drop a witness's cycle vote total to zero without any special privilege, while the witness continues to earn block/transaction-fee rewards for blocks produced in that same cycle before the next election takes effect. No malicious SR/witness/committee/peer/node behavior is required — it can occur from ordinary user vote/stake churn.

### Recommendation
When accumulating `Vi` for a cycle where `voteCount == 0` but `reward > 0`, do not silently drop the reward. Instead, carry the un-distributable reward forward to the next cycle's reward bucket for that witness (e.g., add it to `getReward(cycle+1, address)` before that cycle's `Vi` computation) so it eventually gets distributed once the witness regains voters, or otherwise define and implement an explicit recovery/burn path so the value is accounted for rather than silently orphaned.

### Proof of Concept
1. Witness `W` has voters with total `voteCount = V > 0` in cycle `C`.
2. All voters call `UnfreezeBalanceV2Actuator`/`unDelegateResourceAction`/`voteWitness` (clearing votes) before the cycle's maintenance boundary is processed, causing `getWitnessVote(C, W)` to be persisted as `0`.
3. `W` still produces blocks (or otherwise remains eligible) during cycle `C`, so `MortgageService.payReward` calls `delegationStore.addReward(C, W, value)` adding a non-zero reward.
4. When `DelegationStore.accumulateWitnessVi(C, W, 0)` runs, since `voteCount == 0`, the reward is not converted to `Vi` delta — the `reward` stored at `(C, W, "reward")` is never read by any subsequent code path.
5. Result: the reward amount from step 3 is permanently unclaimable by any account, an irrecoverable loss of protocol reward funds. [2](#0-1)

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;

      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);

      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
