Based on the code in `postblock_v3.rs`, the relay side-effect is **not** actually gated by the `broadcast` flag at all — it only depends on whether the block was accepted by chainstate.

### Title
Unauthenticated `broadcast=0` block POST triggers the same network-relay side effect as an authenticated `broadcast=1` request - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` correctly requires authentication only when `broadcast=1` is requested, setting `self.broadcast = Some(false)` for unauthenticated requests. However, `try_handle_request` does not use `self.broadcast` to decide whether to call `node.set_relay_message`; it gates that call solely on `data_resp.accepted`, so any accepted block — including one submitted unauthenticated with `broadcast=0`/omitted — is placed on the relay/broadcast path exactly as if `broadcast=1` had been authenticated.

### Finding Description
In `try_parse_request` [1](#0-0) , `broadcast` defaults to `false` and unauthenticated requests are permitted as long as `broadcast != true`; `self.broadcast` is stored as `Some(false)` in that case [2](#0-1) .

In `try_handle_request`, `self.broadcast.unwrap_or(false)` is passed into `Relayer::process_new_nakamoto_block_ext` as a parameter [3](#0-2) , but the subsequent decision to call `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` — the mechanism that hands the block off to the p2p layer for network-wide gossip — checks only `data_resp.accepted`, with no reference to `self.broadcast` at all: [4](#0-3) .

This breaks the equality the endpoint's own design implies (and that the code comment "should set to relay..." itself hints was uncertain): "broadcast==false must mean the block is processed without being placed on the relay path." Any remote, unauthenticated caller can POST a valid, chain-extending Nakamoto block to `/v3/blocks/upload/` with no `Authorization` header and either omit `broadcast` or set `broadcast=0`; if `chainstate`/`process_new_nakamoto_block_ext` accepts the block (which only requires it be a valid, previously-unseen block that extends known state — not that the submitter be authorized), the handler will still call `node.set_relay_message`, causing the node to gossip the block to its peers over the p2p network.

### Impact Explanation
An unprivileged, unauthenticated remote caller can force a node to relay/broadcast a block into the network without ever supplying the RPC secret. This does not let the attacker forge the block's contents (it must still pass consensus validation via `process_new_nakamoto_block_ext`), but it defeats the intended access-control model of this endpoint, where `broadcast=1` is supposed to be a privileged, authenticated action gating network propagation. Practically, this allows an unauthenticated party to use any Stacks node's RPC port as a public, unauthenticated relay/gossip entry point for valid blocks it has learned out-of-band, bypassing whatever operational policy (e.g., IP allowlisting/auth secret) an operator was relying on to control who can *inject and force-broadcast* blocks through their node.

### Likelihood Explanation
Trivial and fully remote: the attacker only needs network access to a node's RPC port (this is intended to be world-reachable by design, hence "no auth needed for this path"), a syntactically valid, chain-extending Nakamoto block, and to omit `broadcast` or set it to `0`. No secret, peer key, or slot ownership is required. It is repeatable for every new valid block the attacker can obtain or produce.

### Recommendation
Gate the `node.set_relay_message` call on `self.broadcast` (i.e., `self.broadcast == Some(true) && data_resp.accepted`), matching the documented intent that only authenticated `broadcast=1` requests should trigger network propagation, rather than gating solely on acceptance.

### Proof of Concept
Rust test plan for `stackslib/src/net/api/postblock_v3.rs`:
1. Construct an `RPCPostBlockRequestHandler` with `auth = Some("secret".into())`.
2. Call `try_parse_request` with no `Authorization` header and `query = Some("broadcast=0")` (or `query = None`) and a valid serialized `NakamotoBlock` body; assert it succeeds and `handler.broadcast == Some(false)`.
3. Feed the resulting handler into `try_handle_request` against a `StacksNodeState` whose chainstate accepts the block (i.e., a valid block extending the current tip).
4. Assert that `node.set_relay_message` was invoked (e.g., by inspecting the node/network state's pending relay message queue) despite `handler.broadcast == Some(false)`, proving the relay side effect occurred without authentication or `broadcast=1`.
5. Contrast with a second run using `broadcast=1` plus valid auth header, showing identical relay side effect — confirming the two paths are indistinguishable downstream despite differing authentication.
