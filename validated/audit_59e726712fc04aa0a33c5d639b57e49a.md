### Title
Missing Consensus Public Key Uniqueness Enforcement in `rotate_consensus_key` Allows Duplicate BLS Keys Across Validators, Doubling Effective Voting Power — (`File: aptos-move/framework/aptos-framework/sources/stake.move`)

---

### Summary

`stake::rotate_consensus_key` (and `stake::initialize_validator`) validate only that a submitted BLS12-381 public key has a valid proof-of-possession (PoP), but never check whether that key is already registered by another active or pending validator. An operator who controls two validator accounts can register the identical BLS key pair for both. Because BLS multi-signature aggregation is linear, both validators' individual signatures naturally aggregate to a valid aggregate signature under the doubled public key `2·pk`, causing the consensus layer to count the attacker's stake twice. This is the direct Aptos analog of the "duplicate `scriptPubKeyHash`" root cause: a unique identifier is not enforced to be unique across multiple instances of the same registry entry.

---

The same gap exists in `initialize_validator`: [2](#0-1) 

Neither function iterates over `ValidatorSet.active_validators`, `pending_active`, or `pending_inactive` to assert that `new_consensus_pubkey` is not already present. The genesis-time CLI check in `validate_validators` (`crates/aptos/src/genesis/mod.rs`) does enforce uniqueness, but that is an off-chain, pre-genesis-only guard with no on-chain equivalent. [3](#0-2) 

**How the duplicate key reaches consensus:**

`validator_consensus_infos_from_validator_set` assembles the `ValidatorConsensusInfo` vector that is handed to the consensus layer. It copies `vi.config.consensus_pubkey` verbatim for every validator, with no deduplication: [4](#0-3) 

`ValidatorConsensusInfo` carries `(addr, pk_bytes, voting_power)` as independent fields: [5](#0-4) 

The Rust `ValidatorVerifier` indexes validators by address, so two entries with the same `pk_bytes` but different addresses are both admitted: [6](#0-5) 

**BLS arithmetic consequence:**

When the consensus layer aggregates signatures for a quorum certificate, it sums the public keys of all signers in the bitmask. If validators A and B both carry `pk = sk·G`, the aggregate key for a bitmask that includes both is `pk_A + pk_B = 2·pk`. The attacker, who knows `sk`, signs the same message for both validator slots, producing individual signatures `sig = sk·H(msg)`. The natural BLS aggregation of two identical signatures is `sig + sig = 2·sig`. Verification succeeds because `e(2·sig, G₂) = e(H(msg), 2·pk)` holds by bilinearity. No special manipulation is required; the attacker simply runs the same signing key on both validator nodes.

---

### Impact Explanation

An attacker who controls two validator accounts and registers the same BLS key for both effectively doubles their counted voting power in every quorum certificate. If the combined nominal stake of the two pools exceeds one-third of total network stake, the attacker can unilaterally prevent quorum (liveness failure). If it exceeds two-thirds, the attacker can produce valid quorum certificates for conflicting blocks (safety failure / chain split). Staking rewards for the duplicated validator are also inflated because both pools earn rewards independently while sharing a single signing key.

---

### Likelihood Explanation

Low. The attacker must control two separate validator accounts with sufficient combined stake, and must be the operator of both. However, the attack requires only two standard on-chain transactions (`rotate_consensus_key` called twice with the same arguments), is fully unprivileged (no governance access needed), and leaves no on-chain evidence distinguishing it from a legitimate key rotation.

---

### Recommendation

Add a cross-validator uniqueness assertion inside both `rotate_consensus_key` and `initialize_validator`. Before writing `new_consensus_pubkey` into `ValidatorConfig`, iterate over `ValidatorSet.active_validators`, `pending_active`, and `pending_inactive` and abort if any entry already carries the same `consensus_pubkey`. A dedicated `SimpleMap<vector<u8>, address>` (key → pool address) stored alongside `ValidatorSet` would make this O(1) instead of O(n).

---

### Proof of Concept

```
// Attacker controls validator_A (pool_A) and validator_B (pool_B),
// both with operator = attacker_operator.

// Step 1 – generate one BLS key pair off-chain
let (sk, pk) = bls12381::keygen();
let pop = bls12381::sign(sk, pk);   // proof-of-possession

// Step 2 – register pk for validator_A (succeeds: PoP is valid)
stake::rotate_consensus_key(attacker_operator, pool_A, pk_bytes, pop_bytes);

// Step 3 – register the SAME pk for validator_B (also succeeds: no uniqueness check)
stake::rotate_consensus_key(attacker_operator, pool_B, pk_bytes, pop_bytes);

// After the next epoch boundary, both pool_A and pool_B appear in
// ValidatorSet.active_validators with identical consensus_pubkey.
// validator_consensus_infos_from_validator_set emits two ValidatorConsensusInfo
// entries: (pool_A, pk_bytes, vp_A) and (pool_B, pk_bytes, vp_B).

// Step 4 – during consensus, attacker signs every message once with sk.
// The consensus layer aggregates the two identical signatures into 2·sig,
// computes aggregate key 2·pk, and the pairing check passes.
// Both vp_A and vp_B are credited toward quorum.
```
