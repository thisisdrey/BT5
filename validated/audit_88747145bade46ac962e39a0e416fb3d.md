### Title
Unauthenticated write of attacker-chosen bytes into AtlasDB via unchecked attachment hash in `extend_with_attachments` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes an `AttachmentRequest`'s HTTP response into a `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever comparing the returned attachment's content hash to the `content_hash` (`H`) that was actually requested. A malicious peer answering a `GET /v2/attachments/<H>` request can return arbitrary content `C` where `Hash160::from_data(&C) != H`, and that forged attachment is accepted into the batch state and subsequently written to `AtlasDB`.

The `AttachmentRequest` carries the expected `content_hash` field (set when the request was built from `AttachmentsBatch::track_attachment`, `stackslib/src/net/atlas/download.rs:467-472`), but this value, `request.content_hash`, is never compared against `response.attachment.hash()` before insertion. `decode_atlas_get_attachment()` only performs wire-format decoding of the HTTP body into a `GetAttachmentResponse`/`Attachment`; it does not (and structurally cannot, since it has no knowledge of the original request) verify that the returned attachment content actually hashes to the value that was requested.

Downstream, in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-169`), the batch's `attachments` set is drained and, for each attachment, `network.atlasdb.find_all_attachment_instances(&attachment.hash())` is used to look up which pending instances this attachment resolves, and `insert_instantiated_attachment(&attachment)` is called keyed on `attachment.hash()` — i.e., the attacker's own hash of their own forged bytes, not `H`. This means:
- The forged attachment gets written into `AtlasDB` at its own self-consistent hash key (not colliding with `H`), consuming a slot in the attachments table.
- `context.attachments_batch.resolve_attachment(&attachment.hash())` is called with the wrong hash, so the batch's tracked commitment `H` is never properly resolved/cleared by this bogus response — it will eventually retry or time out, but a DB write of attacker-controlled data has already occurred.

No code path between the HTTP response decode and the `self.attachments.insert(...)` performs the equality check `request.content_hash == response.attachment.hash()`. This is a genuine broken invariant: an unprivileged remote peer that is selected as a download source (because they claimed to hold `H` in their `AttachmentsInv` gossip) can serve arbitrary bytes for any hash they claim to have, and those bytes are accepted as legitimate "resolved" attachment data structurally, then stored to disk.

### Impact Explanation
An attacker-controlled peer, once selected in `get_prioritized_attachments_requests` (chosen from peers that advertised `H` in their attachment inventory), can serve arbitrary bytes in response to a `GET /v2/attachments/<H>` request. Those bytes are:
1. Inserted into the batch's in-memory `attachments: HashSet<Attachment>` unconditionally.
2. Persisted into `AtlasDB` via `insert_instantiated_attachment`, consuming space and using resources meant for legitimate data.
3. Not correctly associated with `H`'s pending `AttachmentInstance`, so the legitimate name-operation attachment for `H` is not resolved — potential denial-of-service against BNS/name attachment resolution, and pollution of the attachments store with garbage under the attacker's own (self-consistent) hash.

This matches the "unauthenticated write to state" and "attachment/BNS mismatch" categories in scope (Critical/High), because a remote, unprivileged peer can inject data into a node's persistent Atlas state without ever needing to produce content matching an on-chain commitment.

### Likelihood Explanation
Preconditions are readily attacker-controlled: the attacker needs only to run an ordinary outbound-reachable Stacks peer, gossip an `AttachmentsInv` claiming it holds `H` (any hash they want to answer for), and respond to the resulting attachment GET request with fabricated content. No secret, signature, or privileged role is required — this is a normal RPC endpoint (`/v2/attachments/<hash>`) that any peer serves and any peer can request from. The attack is repeatable per queued attachment instance and costs the attacker nothing beyond running a reachable peer.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; treat a mismatch identically to a failed/faulty response (`report.bump_failed_requests()`, and optionally mark the peer as faulty/blocked). This restores the invariant that only content whose hash matches the requested/committed `content_hash` is ever written into `AtlasDB`.

        let mut queue = BinaryHeap::new();
        let mut enqueued = HashSet::new();
        for ((contract_id, pages, _), peers_responses) in self.inventories.iter() {
            let missing_attachments = match self
                .attachments_batch
                .attachments_instances
                .get(contract_id)
            {
                None => continue,
                Some(missing_attachments) => missing_attachments,
            };
            // Note: we're getting missing_attachments (attachment_id: content_hash)
            for (attachment_index, content_hash) in missing_attachments.iter() {
                let page_index = attachment_index / AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;
                // Since there's a limit in the number of pages that a node can request,
                // we can potentially have multiple inventory request at once.
                if !pages.contains(&page_index) {
                    continue;
                }

                if enqueued.contains(content_hash) {
                    debug!("Atlas: {} already enqueued", content_hash);
                    continue;
                }

                let mut sources = HashMap::new();
                let position_in_page =
                    attachment_index % AttachmentInstance::ATTACHMENTS_INV_PAGE_SIZE;

                for (peer_url, response) in peers_responses.iter() {
                    // Considering the response, look for the page with the index
                    // we're looking for.
                    let search_page = response.pages.iter().find(|page| page.index == page_index);

                    let has_attachment = search_page
                        .and_then(|search_page| {
                            search_page.inventory.get(position_in_page as usize)
                        })
                        .map(|result| *result == 1)
                        .unwrap_or(false);

                    if !has_attachment {
                        debug!(
                            "Atlas: peer does not have attachment ({}, {}) in its inventory {:?}",
                            page_index, position_in_page, response.pages
                        );
                        continue;
                    }

                    let report = self
                        .peers
                        .get(peer_url)
                        .expect("Atlas: unable to retrieve reliability report for peer");
                    sources.insert(peer_url.clone(), report.clone());
                }

                if sources.is_empty() {
                    warn!("Atlas: could not find a peer including attachment in its inventory");
                    continue;
                }

                // Success, we found at least one inventory including the attachment we're looking for.
                let request = AttachmentRequest {
                    sources,
                    content_hash: content_hash.clone(),
                    stacks_block_height: self.attachments_batch.stacks_block_height,
                    canonical_stacks_tip_height: self.attachments_batch.canonical_stacks_tip_height,
                };
                enqueued.insert(content_hash);
                queue.push(request);
            }
        }
        queue
    }

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
