### Title
Signature-malleability weight double-counting in `ValidateMultiSign` precompile bypasses multisig threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompiled contract, reachable by any smart contract via a `CALL` opcode (energy-metered, unprivileged), aggregates signer weights to satisfy an account's `Permission` threshold. Its duplicate-signature detection is keyed on the raw signature bytes rather than on the recovered signer address, so a caller who provides two byte-distinct signatures that both recover to the *same* address (e.g. malleable ECDSA variants `(r, s)` / `(r, n-s)`, or a signature with harmless trailing padding) has that signer's weight counted twice, allowing the threshold check to pass with fewer distinct authorized keys than required.

### Finding Description
`ValidateMultiSign.execute` loops over the supplied signature array and does: [1](#0-0) 

For each signature it recovers the signer address (`recoverAddrBySign`), then merges address+signature bytes into `sign`. If the recovered address was already seen (`executedSignList` contains `recoveredAddr`), it only `continue`s (skips re-adding weight) when the *exact byte-identical* merged value (`sign`) was also already seen. If the address matches but the raw signature bytes differ — which is trivially achievable via ECDSA signature malleability (flipping `s` to `n-s` and the recovery id) or via any other byte-level encoding of a signature that still decodes to the same `(r,s,v)`/address — execution falls through past the `continue`, recomputes `weight = TransactionCapsule.getWeight(permission, recoveredAddr)`, and adds it to `totalWeight` again.

This is the same signature-malleability bug class as the referenced report (accepting alternate but semantically-equivalent encodings of a signature and treating them as independent, when the calling code relies on uniqueness of the signature to bound authorization). Compare this to `TransactionCapsule.checkWeight`, which after fork `VERSION_4_7_1` deliberately keys its dedup map on the *recovered address* (`encode58Check(address)`) instead of the raw signature bytes specifically to prevent this class of double-counting: [2](#0-1) 

`ValidateMultiSign` never received the analogous address-based dedup fix — it still trusts raw-byte identity as the only substitute check.

### Impact Explanation
`ValidateMultiSign` is used by smart contracts (e.g. multisig wallet contracts) to verify that a threshold-weighted set of *distinct* keys authorized an operation. Because the same private key's signature can be malleable-transformed into a second, byte-distinct signature that recovers to the identical address, an attacker controlling a single key with weight `w < threshold` can submit two (or more) malleable variants of their own signature to accumulate `totalWeight >= threshold`, causing the precompile to report the multisig check as satisfied when it should not be. Any on-chain contract relying on this precompile's boolean result to gate a privileged action (fund transfer, permission change, etc.) can be tricked into authorizing an operation with insufficient real signer weight — this constitutes unauthorized account operation / theft of funds for contracts built on this primitive.

### Likelihood Explanation
Reachable directly from a broadcastable smart-contract transaction: any account can deploy or call a contract that invokes the `ValidateMultiSign` precompile with attacker-supplied signature bytes. No special privilege, node compromise, or consensus role is required — only knowledge of one private key with nonzero weight in the target permission and the ability to derive the standard `(r, n-s)` malleable counterpart signature, which is a trivial, well-known operation (`ECKey.ECDSASignature.toCanonicalised` in this same codebase demonstrates the exact transform is native to secp256k1 signatures used here).

### Recommendation
In `ValidateMultiSign.execute`, deduplicate by recovered address alone (not by the raw/merged signature bytes): once `recoveredAddr` has been counted once, skip it unconditionally rather than only skipping identical raw signature bytes. Additionally, canonicalize signatures (reject or normalize `s > HALF_CURVE_ORDER`, as `ECDSASignature.toCanonicalised()` already provides) before deriving `recoveredAddr`/weight, so malleable variants collapse to a single canonical representation before the dedup check runs.

### Proof of Concept
1. Configure an account's `Permission` with one key `K` of weight `w` and `threshold = 2w` (so `K` alone cannot satisfy the permission).
2. Sign the target `hash` with `K` to get signature `sig1 = (r, s, v)`.
3. Derive the malleable counterpart `sig2 = (r, n - s, v')` (standard secp256k1 transform; `n` is the curve order) — this recovers to the same address as `sig1` but differs at the byte level.
4. Call the `ValidateMultiSign` precompile (via a contract) with `signatures = [sig1, sig2]`.
5. In the loop at [3](#0-2) , the second iteration recognizes `recoveredAddr` already in `executedSignList` but the merged `sign` bytes differ from the first iteration's, so it does not `continue`, and it re-adds `weight` for `K` — `totalWeight` reaches `2w >= threshold`, and the precompile returns success even though only one key authorized the operation.

Note: I was unable to retrieve the exact source of `recoverAddrBySign(...)` and the private `merge(...)` helper within `PrecompiledContracts.java` in this session (searches located the call sites but not their bodies before iteration limits were reached), so the precise byte layout of `sign`/`merge` should be double-checked by a follow-up session to confirm there is no additional canonicalization step hidden inside those helper methods that would mitigate this issue.

      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }

    }
