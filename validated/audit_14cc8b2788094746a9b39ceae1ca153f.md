### Title
Replay window Check/Update race in `ConnectionState.Decrypt` allows duplicate packet delivery via multiqueue TUN - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` releases `decryptLock` between `window.Check` and `window.Update`, creating a TOCTOU window. Two goroutines processing duplicate copies of the same encrypted UDP datagram on different multiqueue TUN readers can both pass `Check` before either calls `Update`, resulting in the same ciphertext being decrypted and written to the TUN device twice.

### Finding Description
`Decrypt` in `connection_state.go` performs the replay check and the replay window update as two separate critical sections instead of one atomic operation: [1](#0-0) 

Specifically: `decryptLock.Lock(); result := cs.window.Check(...); decryptLock.Unlock()` — then AEAD decryption happens outside the lock — then `decryptLock.Lock(); cs.window.Update(...); decryptLock.Unlock()`. If an attacker sends two copies of the same encrypted datagram (same `messageCounter`) that get routed to two different underlay socket queues (`q`), both are processed by concurrent `readOutsidePackets` goroutines invoked from `Interface.listenOut`. Both goroutines can call `cs.window.Check` before either calls `cs.window.Update`, since `Check` alone does not mark the counter as seen — only `Update` does. Both `Check` calls succeed, both `DecryptDanger` calls succeed (the AEAD tag/nonce is valid and reused because it's the identical ciphertext, not a forged one), and both goroutines proceed to `f.readers[q].Write(out)` in `outside.go`'s `handleOutsideMessagePacket`, delivering the payload to the TUN device twice.

This is reachable purely from attacker-controlled network input given multiqueue is enabled and packets are dispatched to different underlay queues (e.g., duplicated on the wire or via socket-level fanout), no cryptographic material or handshake bypass is needed — the attacker simply needs to get the same valid ciphertext to two queues nearly simultaneously.

### Impact Explanation
This breaks the stated invariant "each key/nonce used once, replayed packets dropped" for the specific case of near-simultaneous duplicate delivery across multiqueue readers. The scoped impact is duplicate injection of a single decrypted frame into the application layer via the TUN device — a duplicate-packet/replay-adjacent correctness bug in the data plane. It does not enable decryption of new content, forgery, or session compromise; the ciphertext is legitimate and previously observed, but is delivered twice to the OS instead of once.

### Likelihood Explanation
Requires multiqueue TUN to be enabled and requires the attacker to get an already-captured/duplicated valid ciphertext datagram to race across two queues within the narrow window between `Check` and `Update` (a single AEAD decrypt operation's duration). This is a narrow but real race window and is deterministically reproducible in a unit test that directly races two goroutines against the same `ConnectionState.Decrypt` call with the same `messageCounter`.

### Recommendation
Merge the check-and-mark-seen operation into a single atomic critical section, e.g., have `window.Check`+`window.Update` collapsed into one locked "reserve" step performed before decryption (reject immediately if already reserved), and only roll back/allow re-processing on decrypt failure. Concretely, hold `decryptLock` across the entire `Check` + `DecryptDanger` + `Update` sequence, or use a single atomic "claim" primitive in `Bits` that marks the counter seen at Check-time rather than at Update-time.

### Proof of Concept
Unit test in a `_test.go` file alongside `connection_state.go`:
1. Construct a `ConnectionState` via `newConnectionStateFromResult` (or directly populate fields) with a real `window := NewBits(ReplayWindow)`.
2. Spawn N (e.g. 8) goroutines all calling `cs.Decrypt(l, sameMessageCounter, out, samePacket, nb)` concurrently with a `sync.WaitGroup`, using a barrier/synchronization point to force them to enter `Decrypt` at approximately the same time so multiple pass `Check` before any calls `Update`.
3. Count how many goroutines return a non-error result (i.e., how many times decryption "succeeded").
4. Assert exactly 1 success and N-1 `ErrAlreadySeen` results. Currently, due to the lock-release window, more than one goroutine can succeed, demonstrating the race and violating the "replayed packets dropped" invariant.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
