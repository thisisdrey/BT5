### Title
Unbounded contract-type value causes out-of-bounds `ByteString.byteAt` read/crash in permission-operations bitmap check - ([File: actuator/src/main/java/org/tron/core/utils/TransactionUtil.java])

### Summary
`TransactionUtil.checkPermissionOperations()` uses an attacker-controlled contract-type integer, taken directly from the raw protobuf field via `contract.getTypeValue()`, as a bit index into a fixed 32-byte (256-bit) `operations` bitmap without validating that the value lies in `[0, 255]`. This is structurally the same class of bug as the reported kernel issue: a bounded-size array/bitmap (`sdata->link[]` / `operations` bytes) is indexed by a value extracted from attacker-controlled protocol data (`link_id` / `contract type`) without a range check, leading to an out-of-bounds access.

### Finding Description
`Contract.type` is declared as a protobuf3 `enum ContractType` on the wire, but protobuf3 enum fields are backed by a plain `int32` and accept **any** 32-bit value, not just the values declared in the enum. `Transaction.Contract.getTypeValue()` returns this raw, unchecked integer.

`checkPermissionOperations` computes the bit position directly from this raw value: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException("operations size must be 32");
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`operations` is always exactly 32 bytes (256 bits), so valid indices for `contractType / 8` are `0..31`, corresponding to `contractType` in `0..255`. There is no check that `contractType` (obtained from `getTypeValue()`) falls in this range. A transaction whose raw `Contract.type` field is set to a value such as `100000` (or a negative value) produces `contractType / 8` far outside `0..31`, causing `ByteString.byteAt()` to throw an unchecked `IndexOutOfBoundsException` (or, for negative values, a negative index exception) instead of the expected `PermissionException`.

This function is reachable from the transaction signature-validation path exercised on every multisig-permission-checked transaction:
- `TransactionCapsule.checkPermission()` (called from `validateSignature` and `addSign`), which is on the hot path of transaction broadcast/signature validation: [2](#0-1) 
- `Wallet.getTransactionSignWeight` and `Wallet.getTransactionApprovedList`, both directly reachable via gRPC/HTTP API calls that take a raw `Transaction` object from an anonymous client: [3](#0-2) [4](#0-3) 

Any of these paths is triggerable by an unprivileged client: an account owner who has set a non-zero `Permission_id` and an `Active` permission with a 32-byte `operations` bitmap simply needs to submit (via `broadcastTransaction`, `getTransactionSignWeight`, or `getTransactionApprovedList`) a transaction whose contract carries a `permission_id != 0` and whose `Contract.type` raw field value is outside `[0, 255]`.

### Impact Explanation
An uncaught runtime exception thrown deep in the signature/permission-checking logic, instead of the expected `PermissionException`, is not handled by the encompassing `catch` blocks in `TransactionUtil.getTransactionSignWeight` / `Wallet.getTransactionApprovedList` if it doesn't subclass the caught exception types (`SignatureFormatException`, `SignatureException`, `PermissionException`) — but those methods do have a generic `catch (Exception ex)` fallback, so at the API layer the immediate effect may only be an `OTHER_ERROR` response rather than a full crash. However, `TransactionCapsule.validatePubSignature()`/`validateSignature()` is also invoked in transaction processing and block-application code paths in `Manager`/`TransactionCapsule` where such an unchecked exception is not always guaranteed to be caught by a matching handler, since `IndexOutOfBoundsException` is a `RuntimeException`, not one of the checked exceptions (`SignatureException`, `PermissionException`, `SignatureFormatException`) explicitly caught around `validateSignature`. This can propagate as an unhandled runtime exception during transaction processing/broadcast handling, degrading node availability for the affected request path (denial of service against transaction validation service), consistent with the "node crash / API the node can no longer serve" impact bar.

### Likelihood Explanation
High likelihood of reachability: any account with multisig permissions enabled (a normal, self-service feature via `AccountPermissionUpdateContract`) can craft a transaction with an out-of-range `Contract.type` raw integer and a `permission_id != 0`, then submit it through the public `broadcastTransaction`, `getTransactionSignWeight`, or `getTransactionApprovedList` API endpoints — no special privileges, no cooperation from other parties, and no pre-existing malicious state required. Because these are plain protobuf messages, an attacker fully controls the raw `type` field regardless of the enum's declared value range.

### Recommendation
In `TransactionUtil.checkPermissionOperations`, validate that `contractType` (from `contract.getTypeValue()`) is within `[0, 255]` (or more precisely `[0, operations.size()*8-1]`) before using it to index into `operations`, and throw `PermissionException` for out-of-range values instead of allowing an unchecked exception from `ByteString.byteAt()`. Apply the analogous bounds check in `AccountPermissionUpdateActuator.checkPermission` too, if `types1[(i / 8)]` indexing could similarly be affected by user-controlled contract type values elsewhere.

### Proof of Concept
1. Attacker account has multisig enabled with an `Active` permission (id ≥ 2) whose `operations` is a 32-byte bitmap.
2. Attacker constructs a `Transaction` whose `raw_data.contract[0]` has `permission_id` set to that active permission's id, and the low-level `type` field (via manual protobuf field construction, bypassing the Java enum setter, e.g. using `UnknownFieldSet` merge or `setTypeValue(100000)` if using generated builder API which does expose `setTypeValue`) set to an out-of-range integer such as `100000`.
3. Attacker submits this transaction via `broadcastTransaction` / `getTransactionSignWeight` / `getTransactionApprovedList`.
4. During permission/signature validation, `TransactionUtil.checkPermissionOperations` computes `contractType / 8 = 12500`, then calls `operations.byteAt(12500)` on a 32-byte `ByteString`, throwing `IndexOutOfBoundsException` instead of the intended `PermissionException`, which is not among the checked exceptions explicitly handled around the call in `TransactionCapsule.checkPermission`/`validateSignature`.

**Note on verification limits:** I was unable to fully confirm in this session (due to running out of tool iterations) exactly which exception types wrap every call site of `checkPermission`/`validateSignature` up to `Manager`'s transaction-processing entry point, nor whether `Contract.Builder.setTypeValue(int)` is exposed as a public API in the generated protobuf code for this repo version — both would need to be checked in a follow-up session (e.g., a Devin session with full repo/build access) to fully confirm the unhandled-exception propagation path and craft an exact working PoC transaction bytes.
