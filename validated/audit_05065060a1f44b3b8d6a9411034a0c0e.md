### Title
`VerifyTransferProof` precompile ignores its own CPU-timeout signal and blocks on native worker threads instead of failing closed — analogous to Istio's `continue_on_listener_filters_timeout` DoS (CVE-2019-18817) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The Istio advisory describes a class of bug where a filter/verification stage is configured to *continue processing* after its own timeout fires instead of aborting, letting an attacker force the server into an inconsistent, resource-exhausting state. The `VerifyTransferProof` shielded-transfer precompile in java-tron has the same bug class: it computes whether its CPU budget has been exhausted (`withNoTimeout`) but never checks the result before blocking on `Future.get()` for all submitted native-verification tasks.

### Finding Description
`VerifyTransferProof.execute()` submits per-spend/per-output/binding-signature verification jobs (JNI calls into librustzcash) to a small fixed thread pool and waits on a `CountDownLatch` bounded by the remaining CPU time: [1](#0-0) 

`countDownLatch.await(...)` returns `false` when the CPU-time budget (`getCPUTimeLeftInNanoSecond()`) is exhausted before all tasks finish — this is the intended "timeout" signal for this precompile, exactly like the Envoy/Istio `listener_filters_timeout` mechanism. However, the resulting boolean `withNoTimeout` is **never inspected**: execution unconditionally proceeds to call `future.get()` on every submitted task, which blocks the calling thread until each native task actually completes, regardless of whether the CPU deadline has already passed.

This is a direct violation of the pattern used correctly a few hundred lines earlier in the very same file, in `BatchValidateSign.doExecute()`, where the identical `await(...)` result is checked and a hard failure (`Program.Exception.notEnoughTime(...)`) is thrown on timeout: [2](#0-1) 

In `VerifyTransferProof`, the equivalent guard is simply absent, so the "continue past the deadline" behavior is unconditional rather than an edge case — mirroring the Istio misconfiguration where `continue_on_listener_filters_timeout=True` caused processing to proceed after the timeout fired instead of terminating the connection/request.

### Impact Explanation
`VerifyTransferProof` is reached whenever a smart-contract execution (TVM `CALL`/`STATICCALL`) invokes this precompiled contract address — i.e., by any account that can broadcast a `TriggerSmartContract` transaction or deploy a contract that calls it, with attacker-controlled `data` (spend/output counts, proof bytes, signatures). Because the timeout check is dead code:
- A caller can submit input sized to spend up to CPU/energy limits so that native verification legitimately runs long, and the calling VM thread will block in `future.get()` past the point where the VM's own energy/CPU accounting says execution should have already been aborted.
- Both `workersInConstantCall` and `workersInNonConstantCall` are fixed-size pools (5 threads) shared across *all* concurrent shielded-transfer verifications on the node. Multiple concurrent transactions (or repeated calls within a block) that each push execution into this un-bounded wait can occupy every worker thread and stall the shared pool, delaying or blocking all other pending `VerifyTransferProof`/`VerifyMintProof`/shielded verification work — a resource-exhaustion / node-stall condition triggerable by ordinary transaction broadcasters, not requiring any special privilege.
- Because the CPU-time guard is bypassed, energy/CPU accounting invariants that the rest of the VM relies on (bounding execution time per transaction) are violated for this code path, which is the same "processing continues after the filter's own deadline" failure mode as the Istio CVE.

### Likelihood Explanation
The precompile is reachable by any account able to submit a `TriggerSmartContract` transaction that calls the sapling-verify-transfer precompile address with valid-length shielded transfer data (`SIZE = {2080, 2368, 2464, 2752}` bytes) — no special permission or witness/SR role is required. Triggering the missing-timeout path only requires crafting input so that native Rust verification for one of the up to 5 spend/output/binding tasks runs long relative to the remaining CPU budget, which is plausible given the multiple heavy zk-SNARK verification calls (`librustzcashSaplingCheckSpendNew`, `librustzcashSaplingCheckOutputNew`, `librustzcashSaplingCheckBingdingSig`) invoked per call.

### Recommendation
Check the result of `countDownLatch.await(...)` in `VerifyTransferProof.execute()` (and any other precompile with the same pattern) exactly as `BatchValidateSign.doExecute()` does, and fail fast (throw `Program.Exception.notEnoughTime(...)` or otherwise reject the call) instead of calling `future.get()` unconditionally on all futures when `withNoTimeout` is `false`. Additionally audit the rest of `PrecompiledContracts.java` for other `CountDownLatch.await` usages where the boolean result is discarded.

### Proof of Concept
1. Deploy/trigger a contract that calls the sapling `VerifyTransferProof` precompiled address with a data payload sized to one of the accepted lengths (`2080/2368/2464/2752` bytes), containing `spendCount`/`receiveCount` combinations (1–2 each) and proof/signature bytes crafted so the native verification calls take longer than the remaining CPU time returned by `getCPUTimeLeftInNanoSecond()`.
2. Because `withNoTimeout` (line 1589) is never checked, the executing thread proceeds directly to the `for (Future<Boolean> future : futures) { future.get(); ... }` loop (lines 1592–1595) and blocks past the intended CPU deadline waiting on the shared `workersInNonConstantCall` pool (5 threads).
3. Repeat with several concurrent transactions calling the same precompile; because the worker pool is shared and fixed-size, workers become occupied beyond the per-call CPU budget, delaying/stalling other pending shielded-transfer verification work on the node. [3](#0-2) [4](#0-3)
