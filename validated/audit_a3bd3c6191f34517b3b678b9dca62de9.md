### Title
Global bandwidth/energy weight accounting can go negative via TVM-driven freeze/unfreeze/delegate paths, causing network-wide bandwidth/energy DoS - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
The reported HEX Strategy bug is a global accumulator (`currentTotalStakeAmount`/withdraw queue) that can be driven inconsistent by user-triggered stake/unstake ordering, permanently blocking a shared resource and causing an underflow in a subsequent computation used by everyone. java-tron has an analogous shared, global accumulator pattern: `TotalNetWeight` / `TotalEnergyWeight` / `TotalTronPowerWeight`, which are aggregated across all accounts and used to compute every account's bandwidth/energy limits.

### Finding Description
Two independent code paths update these global totals when resources are frozen/unfrozen/delegated:

1. The classic (non-TVM) actuator path uses `DynamicPropertiesStore.addTotalNetWeight` / `addTotalEnergyWeight` / `addTotalTronPowerWeight`, which explicitly clamp the result to a minimum of zero when `allowNewReward()` is enabled: [1](#0-0) [2](#0-1) 

2. The TVM/contract-triggered path — used by `FreezeBalanceV2Processor`, `UnfreezeBalanceProcessor`, `UnfreezeBalanceV2Processor`, `UnDelegateResourceProcessor`, `CancelAllUnfreezeV2Processor`, all invoked from Solidity precompiled "native contracts" reachable by any unprivileged contract-calling transaction — instead uses `RepositoryImpl.addTotalNetWeight` / `addTotalEnergyWeight` / `addTotalTronPowerWeight`, which perform **no clamping whatsoever**: [3](#0-2) 

Both `UnfreezeBalanceProcessor.execute()` and `UnfreezeBalanceV2Processor.updateTotalResourceWeight()` call this unclamped `repo.addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight`: [4](#0-3) [5](#0-4) 

These global totals are then consumed by `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` and `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` to compute the free-bandwidth/energy quota for **every account on the network** (not just the caller): [6](#0-5) [7](#0-6) 

Note that `calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` (the "unfreeze-delay" / V2 formulas, in effect on modern networks) only special-case `totalWeight == 0`; they do **not** guard against a negative `totalWeight`. If `totalNetWeight`/`totalEnergyWeight` becomes negative, the ratio `totalLimit / totalWeight` becomes negative, and every account's computed global net/energy limit becomes negative — this negative limit is then compared against usage in `useAccountNet`/analogous energy-usage checks such as `bytes > (netLimit - newNetUsage)`, which will always fail once `netLimit` is negative, effectively freezing free bandwidth/energy accounting for the whole chain.

The comment `"adjust total resource, used to be a bug here"` in `UnfreezeBalanceProcessor` (line 190) indicates the java-tron team is already aware this bookkeeping is fragile/history-of-bugs, which is exactly the class of issue the external report flags (aggregate accounting drifting inconsistent from per-user actions and not being defensively clamped).

### Impact Explanation
`TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` are global, shared state used to compute the free bandwidth/energy limit for every account, analogous to the shared `currentTotalStakeAmount` in the HEX report. If any TVM-callable native-contract path (freeze/unfreeze/delegate/undelegate/cancel-unfreeze, all directly reachable by ordinary contract-triggering transactions) can drive one of these counters permanently negative through legitimate-looking sequences of operations, the resulting negative or zero-adjacent global weight corrupts bandwidth/energy limit calculations for the entire network — a denial-of-service condition analogous to the "block all future stakes/unstakes" impact described in the report, since free-bandwidth/energy consumption checks would degrade or fail for all users, forcing fallback to paid TRX resource consumption or outright rejecting transactions.

### Likelihood Explanation
Exploitability depends on whether a legitimate transaction sequence (freeze via `FreezeBalanceV2Processor`, unfreeze via `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Processor`, delegate/undelegate) can produce an aggregate total that goes negative given the per-account delta bookkeeping (`newWeight - oldWeight`) is generally self-consistent. I could not conclusively construct or rule out a concrete transaction sequence within the available tool budget that forces the unclamped `RepositoryImpl` accumulator negative purely through valid, validated per-account operations — the divergence between the clamped `DynamicPropertiesStore` path and the unclamped `RepositoryImpl` path is a real code inconsistency, but proving it is triggerable end-to-end (e.g. via race conditions between V1/V2 freeze mixing, self-destruct/inheritance paths in `Program.transferFrozenV2BalanceToInheritor`, or interaction between `UnfreezeBalanceProcessor`'s flat `-unfreezeBalance/TRX_PRECISION` decrement and other paths' delta-based decrements) requires deeper tracing than was possible here.

### Recommendation
Make `RepositoryImpl.addTotalNetWeight`, `addTotalEnergyWeight`, and `addTotalTronPowerWeight` mirror the defensive clamping already present in `DynamicPropertiesStore` (clamp to a minimum of 0), and audit `calculateGlobalNetLimitV2`/`calculateGlobalEnergyLimitV2` to explicitly guard against negative `totalWeight` (not just `== 0`), returning 0 rather than a negative limit in that case.

### Proof of Concept
Not conclusively demonstrated. Given remaining iteration budget, I was unable to trace a complete, validated transaction sequence that drives `RepositoryImpl.addTotalNetWeight`/`addTotalEnergyWeight` negative through legitimate freeze/unfreeze/delegate/undelegate call sequences; further investigation (e.g. via a Devin session with full repo/test access) is recommended to confirm or refute exploitability of this accumulator divergence before treating it as a confirmed vulnerability.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
