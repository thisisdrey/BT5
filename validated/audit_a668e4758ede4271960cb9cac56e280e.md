### Title
ETH-Wallet-Contract ERC-20 emulation permanently loses the caller's attached deposit when the target token lacks NEP-145 storage management - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Wallet Contract's ERC-20 emulation path assumes every token targeted by an emulated `transfer` implements the NEP-145 storage-management standard (i.e. has a working `storage_balance_of` method). When the target contract does not implement this method (a "normal" NEP-141 token without NEP-145 support, analogous to a plain ERC-20 lacking the "universal" interface expected by DODO's `superWithdraw`), the cross-contract call to `storage_balance_of` fails, and unlike every other failure path in this contract, the caller's forwarded deposit is not refunded — it is silently and permanently lost by the wallet contract.

### Finding Description
When `inner_rlp_execute` detects an emulated ERC-20 transfer, it unconditionally schedules a call to `storage_balance_of` on the target token before performing `ft_transfer`, assuming the token supports the NEP-145 storage-management interface: [1](#0-0) 

The result is handled in `nep_141_storage_balance_callback`. On promise failure, or on any unexpected/unparsable response (which occurs whenever the target token doesn't implement `storage_balance_of` as expected), the callback returns an error `ExecuteResponse` **without ever consulting `caller_deposit`**: [2](#0-1) 

This is inconsistent with the general failure-handling callback `rlp_execute_callback`, which is used for every other action type (transfers, plain function calls, add/delete key) and explicitly refunds the `caller_deposit` to the account it came from when the wrapped promise fails: [3](#0-2) 

`caller_deposit` is constructed from the attached deposit forwarded by whoever called `rlp_execute` (see `CallerDeposit::new(&context)` in `inner_rlp_execute`, using `env::attached_deposit()`): [4](#0-3) 

Because the ERC-20 branch is the *only* branch that passes through `nep_141_storage_balance_callback` before reaching `rlp_execute_callback`, and that intermediate callback swallows failures without any refund logic, funds attached by a relayer/caller (`caller_deposit`) that go through this path are unrecoverable whenever the target token contract is not NEP-145 compliant — i.e., whenever it doesn't implement the "universal" storage-management functions the wallet contract assumes all NEP-141 tokens implement.

### Impact Explanation
Any caller attaching a deposit (e.g. a relayer sending an emulated ERC-20 `transfer` call on behalf of a user with attached NEAR to cover fees/refunds) permanently loses that deposit if the target token does not implement `storage_balance_of`. This is a direct, deterministic loss of NEAR funds triggered purely by interacting with a non-conforming (but entirely legitimate) NEP-141 token, with no way to recover the funds afterward — matching the sherlock finding's root cause (assuming a non-standard/extended interface on a "normal" token, resulting in stuck/lost funds).

### Likelihood Explanation
This path is reachable by any ordinary relayer/user performing an ETH-emulated ERC-20 `transfer()` call through an ETH-implicit account's Wallet Contract, targeting a NEP-141 token that has not implemented the NEP-145 storage-management standard (a fully valid, if non-full-featured, NEP-141 token) — a common and unprivileged scenario, not requiring any malicious actor.

### Recommendation
In `nep_141_storage_balance_callback`, on `PromiseResult::Failed` and on JSON-deserialization failure of the `storage_balance_of` response, refund `caller_deposit` in the same manner as `rlp_execute_callback` does, before returning the failure `ExecuteResponse`.

### Proof of Concept
1. Deploy an ETH-implicit account with the Wallet Contract (`wallet_contract`), and a NEP-141 token contract that does **not** implement `storage_balance_of` (i.e., does not follow the NEP-145 storage-management extension — many minimal/legacy NEP-141 implementations omit this).
2. A relayer calls `rlp_execute` targeting that token with an RLP-encoded ERC-20 `transfer()` selector, attaching a NEAR deposit intended as `caller_deposit` (per `CallerDeposit::new`).
3. `inner_rlp_execute` routes to the `ERC20Transfer` branch and schedules `storage_balance_of` followed by `nep_141_storage_balance_callback`, per `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:433-457`.
4. Because the token has no `storage_balance_of` method, the promise fails; `nep_141_storage_balance_callback` hits the `PromiseResult::Failed` branch at lines 204-209 and returns an error response — `caller_deposit` is never referenced or refunded.
5. Compare with any other action type going through `rlp_execute_callback`, where an analogous promise failure at lines 296-311 explicitly refunds `caller_deposit` to its origin account. The discrepancy confirms the loss is specific to the ERC-20/NEP-145 assumption path.
