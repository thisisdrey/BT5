Audit Report

## Title
`refund_on_hold`'s PGAS shortfall settlement is capped by the contract's total PGAS hold rather than the recipient's own contribution - ([File: substrate/frame/revive/src/deposit_payment.rs])

## Summary
`PGasDeposit::refund_on_hold` caps the native portion of a refund by the recipient's `NativeDepositOf` entry, but any shortfall (`pgas_needed`) is settled via `settle_pgas_refund`, which caps only by the contract's *total* PGAS hold, not by anything the specific recipient contributed in PGAS. Because storage-deposit refund amounts are computed pro rata against the contract's aggregate storage/byte/item deposit pool (in `Diff::update_contract`), a recipient whose own contribution was entirely native can receive a refund funded out of PGAS actually paid in by a different, unrelated contributor to the same contract.

## Finding Description
`charge_and_hold` records only native fallback contributions per-payer in `NativeDepositOf[contract][payer]`; PGAS charges via `transfer_and_hold` are never attributed to a specific payer in storage. `refund_on_hold` caps the native refund to `to`'s own `NativeDepositOf` entry, then routes the remainder (`pgas_needed = amount - native_refunded`) through `settle_pgas_refund`, which only checks `Self::pgas_on_hold(reason, from)` — the contract's total PGAS hold — before paying out. Refund `amount` itself is computed pro-rata across the whole contract's aggregate storage deposit (via `Diff::update_contract` in `substrate/frame/contracts/src/storage/meter.rs` / `substrate/frame/revive/src/metering/storage.rs`), not against any specific payer's contribution, so it is not guaranteed to be bounded by what `to` ever contributed. This allows a recipient who paid entirely in native currency to be settled a "PGAS shortfall" out of PGAS that was contributed by a different account. `refund_all` at termination deliberately (and per the code comments, intentionally/acknowledged) bypasses per-contributor caps entirely — that specific full-sweep-at-termination behavior is a documented design tradeoff, not a hidden bug, and the report itself acknowledges this ("the report's original issue was 'Acknowledged'").

## Impact Explanation
Within `refund_on_hold` (the partial-refund path used during ordinary contract-lifetime storage shrink events, not just termination), PGAS contributed by one depositor can be paid out to a different account's refund destination. This is a genuine value-misdirection primitive distinct from the already-acknowledged `refund_all` termination sweep, because it triggers on ordinary partial refunds and is not something the pallet documents as intended.

## Likelihood Explanation
Exploitability requires: (1) a contract where multiple distinct origins independently pay storage deposits on the same contract (some via PGAS, some falling back to native), and (2) a storage-shrink triggering a refund whose pro-rata `amount` exceeds the *native*-only recipient's own contribution, driving `pgas_needed` positive. This is plausible for any shared, multi-tenant contract with a common storage pool (registries, shared mappings, etc.) and does not require any privileged actor — only ordinary contract calls from independent signed origins. However, I was not able to fully trace, within the available tooling and iteration budget, the exact `E::charge`/`FrameMeter` call sites that determine the concrete `to` recipient and `amount` passed into `refund_on_hold` in `exec.rs`/`metering/mod.rs`, so I cannot confirm with full certainty whether real-world refund amounts routinely exceed a native-only payer's own `NativeDepositOf` entry in practice, or whether upstream logic elsewhere constrains `amount` to the calling origin's own prior charges in a way that would make `pgas_needed` always zero for such a payer. This uncertainty affects confidence in the described path but does not affect the analysis of the code shown, which does confirm the absence of any per-payer PGAS attribution mechanism.

## Recommendation
Track PGAS contributions per-payer analogously to `NativeDepositOf` (e.g., a `PGasDepositOf` double map keyed by `(contract, payer)`), and cap `settle_pgas_refund`'s payout to the actual contributor's tracked balance rather than the contract's total PGAS hold. For `refund_all` at termination, since the sweep-to-single-beneficiary behavior is intended design (per the code's own comments and the referenced "Acknowledged" report status), this should remain documented as a known limitation rather than treated as a fix target, unless the maintainers decide to change contract-termination refund semantics to distribute per-contributor.

## Proof of Concept
No new PoC beyond the referenced test (`refund_all_drains_multi_contributor_native_hold` in `substrate/frame/revive/src/tests/deposit_payment.rs`) was available/verifiable within the current investigation; that existing test only demonstrates the acknowledged `refund_all`-at-termination sweep, not the distinct `refund_on_hold` partial-refund cross-contamination path described above. A dedicated test exercising a mixed PGAS/native multi-contributor contract with a mid-lifetime partial storage shrink (rather than termination) would be needed to concretely demonstrate the `refund_on_hold` shortfall-misdirection scenario.
