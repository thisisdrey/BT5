## Title
Permanent, unprivileged-triggerable loss of staking rewards via unconditional "claimed" marking before payout success — (File: `substrate/frame/staking/src/pallet/impls.rs`, also `substrate/frame/staking-async/src/pallet/impls.rs`)

## Summary
This is a local analog of the Caviar M‑14 bug: an arbitrary, unprepared beneficiary causes a value-transfer to fail, but here the state that "settlement happened" is committed **before** the transfer is even attempted and is never rolled back on failure. In `pallet-staking`'s `payout_stakers` (and the newer `staking-async` equivalent), the era/page is marked as claimed unconditionally, and then each staker's payout (`make_payout`/`make_payout_from_provider`) can silently fail and return `None` with no error propagated to the caller and no way to retry. The reward is then permanently lost for that stash, and the extrinsic itself reports success.

## Finding Description
In `payout_stakers`, the page is flagged as claimed immediately, before any payout is executed: [1](#0-0) 

```
if EraInfo::<T>::is_rewards_claimed_with_legacy_fallback(era, &ledger, &stash, page) {
    return Err(Error::<T>::AlreadyClaimed...);
} else {
    EraInfo::<T>::set_rewards_as_claimed(era, &stash, page);
}
```

After this point "no errors allowed" (per the code's own comment), and each individual payout is attempted via `make_payout`, whose result is an `Option`, not a `Result` — any failure is silently swallowed: [2](#0-1) 

`make_payout` itself resolves the arbitrary beneficiary from `RewardDestination::Account(dest_account)` (freely settable by the staker via `set_payee`, i.e. it can be any account, including one that doesn't exist or can't satisfy the Existential Deposit) and uses `mint_into_existing`, which fails (returns `None`) without creating the account or raising an error: [3](#0-2) 

The same pattern exists in the newer transfer-based path, `staking-async`, where `set_rewards_as_claimed` is likewise committed unconditionally before payout: [4](#0-3) 

and `make_payout_from_provider` transfers to the same arbitrary `payout_account`, logging and dropping the reward on any transfer error (e.g. `Preservation::Expendable` transfer failing because the destination account cannot be created/kept alive): [5](#0-4) 

`payout_stakers`/`payout_stakers_by_page` are permissionless — any signed account can call them on behalf of any validator/era/page. This mirrors the M‑14 root cause exactly: the protocol commits an irreversible "paid" state (there, contract logic assuming ether was delivered; here, `set_rewards_as_claimed`) without verifying the transfer/mint to an attacker- or misconfiguration-controlled beneficiary actually succeeded, and provides no retry path once that state is committed.

## Impact Explanation
Once a page is marked as claimed, `EraInfo::<T>::is_rewards_claimed_with_legacy_fallback` (or the `Eras::<T>::is_rewards_claimed` equivalent) will return `true` forever for that era/page, so the payout can never be retried — unlike `pallet-treasury`'s `payout`, which explicitly supports `check_status`/retry via `PaymentState::Failed`. Any stash whose `RewardDestination::Account` target cannot be funded to the Existential Deposit (or otherwise rejects the transfer) permanently and silently forfeits that page's reward, while the dispatch itself returns `Ok`. This is a genuine, chain-visible "permanent user-fund lock" that requires no privileged actor, malicious validator, or off-chain assumption — it is purely a consequence of committing settlement state ahead of, and independent from, actual fund delivery.

## Likelihood Explanation
`payout_stakers` is a public, permissionless, frequently-called extrinsic (anyone can call it for any validator/era/page). The triggering condition — an `Account` reward destination that cannot receive the payout (e.g., balance below ED, account never funded, or simply nonexistent) — is easy to reach: it can occur naturally (a nominator sets a payee account that they haven't funded yet, or that later gets reaped) or be deliberately induced by any third party who knows the destination account state, then calls `payout_stakers` first to "burn" the claim before the victim can fix their payee configuration.

## Recommendation
Do not commit `set_rewards_as_claimed` until after the payout to every beneficiary has been confirmed to have succeeded (or explicitly accounted for), or track per-stash payment status (à la `pallet-treasury`'s `PaymentState`) so failed payouts can be retried rather than permanently lost. At minimum, only mark the page claimed for beneficiaries whose payout actually succeeded, and emit a distinguishable failure event (not just `Rewarded`) so failed portions remain claimable.

## Proof of Concept
1. Nominator `N` calls `set_payee(RewardDestination::Account(X))` where `X` is an account that has never been funded (balance `0`, below existential deposit).
2. Era `E` completes; `N` has nonzero exposure in some validator's page `P`.
3. Anyone (attacker or bystander) calls `payout_stakers(validator, E)` / `payout_stakers_by_page(validator, E, P)`.
4. `EraInfo::<T>::set_rewards_as_claimed(E, &stash, P)` executes unconditionally.
5. `make_payout(&N, reward)` resolves `dest_account = X`, calls `asset::mint_into_existing::<T>(&X, reward)`, which returns `None` because `X` does not exist/would not meet ED — no funds move, no error surfaced.
6. The extrinsic returns `Ok(...)`; `N`'s reward for `(E, P)` is gone permanently — `payout_stakers` for that `(stash, era, page)` will always short-circuit with `Error::<T>::AlreadyClaimed`.
