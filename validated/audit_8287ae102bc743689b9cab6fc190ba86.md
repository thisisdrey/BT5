### Title
Unauthenticated `RecvError` packets allow remote termination of established tunnels without any CA-signed certificate - (File: outside.go)

### Summary
The reported Astaria-GPL bug is a class of "missing authorization on a state-mutating entry point": a function that is supposed to be reachable only through a trusted, internal orchestration path (`PublicVault.redeemFutureEpoch` → `WithdrawProxy.mint`) is instead directly and publicly callable, letting an unauthenticated party manipulate protocol state (share issuance) for their own benefit. The reachable analog in Nebula is `Interface.handleRecvError`, which processes the `header.RecvError` packet type — an unencrypted, unauthenticated, MAC-less message — and uses it to tear down an already-established, mutually-authenticated tunnel between two legitimate certificate holders, without requiring the sender to ever complete a handshake or present a CA-signed certificate.

### Finding Description
`RecvError` packets are dispatched before any certificate/handshake state is required: [1](#0-0) 

`handleRecvError` is invoked directly off this unauthenticated, plaintext header. The only anti-spoofing check performed is a simple equality between the packet's UDP source address and the hostinfo's currently known remote address: [2](#0-1) 

Key problems:
- `h.RemoteIndex` is a 32-bit value transmitted in the cleartext header of every packet on the wire (see `header.Encode` usage for other message types), so it is observable by any network-position attacker without needing to complete a handshake or hold a valid certificate.
- The address check `hr.IsValid() && hr != addr` only rejects the packet if the hostinfo already has a *known, roamed* remote address that differs from the spoofed source. Since UDP carries no cryptographic binding between the IP/port and the packet contents, an attacker who can spoof the victim's UDP source address (or who is simply on-path/NAT-adjacent to it) can satisfy this check trivially.
- Once the check passes, `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` are called unconditionally — completely tearing down and erasing an authenticated Noise tunnel state that took a full certificate-verified handshake to establish.

This mirrors the report's bug class exactly: a state-mutating operation (`WithdrawProxy` share deposit/mint) that should only be reachable via an authenticated/orchestrated internal path is instead exposed to any unauthenticated actor through the base contract's public interface. Here, tunnel-teardown state (which should only be triggerable by a peer that has proven possession of a CA-signed certificate through the Noise handshake) is instead reachable via a cleartext, unauthenticated packet type with only a weak, spoofable heuristic guarding it.

### Impact Explanation
Any network attacker who can observe or guess a 32-bit `RemoteIndex` and spoof (or is positioned to send from) the legitimate peer's UDP source address can force the premature teardown of any active, mutually-authenticated Nebula tunnel — without ever presenting a certificate, without completing a Noise handshake, and without possessing any cryptographic material. This is a remote state-poisoning / denial-of-service primitive against tunnels between fully legitimate, CA-verified peers, degrading availability of the overlay network on demand.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must either spoof the victim's UDP source address (feasible on networks without strict egress/ingress filtering, or from a MITM/NAT-adjacent position) or race an early-handshake window when `hr` is not yet valid, and (2) they must know or guess the target's `RemoteIndex`, which is transmitted in the clear on every packet and is therefore learnable via passive observation of any traffic to/from the target. Combined, this is a realistic pre-authentication attack path against an active tunnel, though it does require either traffic visibility or IP spoofing capability.

### Recommendation
Do not allow `RecvError` (or any other unauthenticated/unencrypted message type) to unilaterally trigger destructive state changes like `closeTunnel`/`DeleteHostInfo` based solely on a UDP source-address string match. Instead:
- Require the `RecvError` response to be authenticated (e.g., include a MAC over the index using a key derived from the existing session, similar to `VerifyRelay`), so only a party that already possesses the tunnel's cryptographic state can trigger teardown.
- At minimum, rate-limit and corroborate `RecvError`-driven teardown with additional signals (e.g., require confirmation via a subsequent handshake attempt) rather than acting on it immediately and unconditionally.

### Proof of Concept
1. Establish a legitimate, CA-authenticated tunnel between hosts A and B.
2. As an unauthenticated attacker C, observe (or brute-force) A's `RemoteIndex` value used in packets addressed to B's UDP endpoint (visible in the cleartext Nebula header of any packet exchanged, since `RemoteIndex` is not encrypted).
3. Craft a `header.RecvError` packet with that `RemoteIndex`, and send it to A while spoofing the source UDP address to match B's known address (or send it from a position where the source address naturally matches, e.g. shared NAT/MITM).
4. A's `handleRecvError` at [3](#0-2)  finds the hostinfo via `QueryReverseIndex`, sees `hr == addr`, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, destroying the authenticated tunnel state — with C never having presented a certificate or completed a handshake.

Note: I was unable to fully trace `HostMap.QueryReverseIndex` and the exact semantics of the `RemoteIndexes` map (start of investigation was cut off before verifying whether this index is the responder's local index or a distinct "reverse" index), so the exact index-guessing difficulty could not be fully confirmed from the indexed code; this should be verified against `hostmap.go` in a follow-up session if precise exploitability bounds are needed.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
