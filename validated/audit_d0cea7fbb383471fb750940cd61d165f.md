### Title
Multi-sig weight double-counting in `ValidateMultiSign` precompile allows a single key to satisfy quorum threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (`PrecompiledContracts.java:1036-1121`) is meant to enforce that a smart-contract-controlled account's permission threshold is met only when enough *distinct* authorized keys sign. The de-duplication logic only skips a signature when the exact same raw signature bytes for an address are repeated; it does not prevent the same recovered address from contributing its weight more than once when two *different* valid signature byte-strings recover to the same address (e.g. via ECDSA signature malleability, or by re-signing the same hash twice with the same key, which yields a different `r/s/v` encoding each time). This lets a single low-weight key satisfy a multi-signature threshold that was designed to require independent approval from multiple keys — the on-chain analog of the Coolify bug, where a single low-privileged actor manages to satisfy a check meant to require higher-privilege / multi-party approval.

### Finding Description
In `execute()`: [1](#0-0) 

For each provided signature, the code:
1. Recovers `recoveredAddr` from the signature.
2. Builds `sign = merge(recoveredAddr, sign)`.
3. If `executedSignList` already contains `recoveredAddr`:
   - if it also contains this exact `sign` byte-string, skip (`continue`).
   - otherwise, only calls `MUtil.checkCPUTime()` (a CPU/time guard) and **falls through** to add the weight again.
4. Weight for `recoveredAddr` is looked up via `TransactionCapsule.getWeight(permission, recoveredAddr)` and unconditionally added to `totalWeight`, and both `sign` and `recoveredAddr` are appended to `executedSignList` again.

Because the duplicate check is keyed on the *raw signature bytes* rather than on the *recovered address* alone, an attacker who controls a single key with weight `w < threshold` can produce two (or more) different valid signatures over the same `hash` (e.g., by exploiting ECDSA signature malleability where `(r, s, v)` and `(r, n-s, v')` are both valid signatures for the same key/message, or simply by calling `ECKey.sign()` twice which can yield different encodings depending on RNG/nonce), both of which recover to the same address. Each such signature is counted as a *separate* satisfied key, and `totalWeight` accumulates `w` multiple times, allowing the check `totalWeight >= permission.getThreshold()` to pass even though only one real key participated.

This directly undermines the account-permission (multi-sig) model of TRON accounts, which is the same primitive validated on-chain by `TransactionCapsule.checkWeight()` (`chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:233-269`), which correctly rejects a second signature from the same address ("has signed twice!"). The precompile's re-implementation of this weight check for TVM/contract-driven flows (e.g. wallet contracts, custody contracts, DAO-style multisig wrappers built on top of `Permission`) does not have this protection. ### Impact Explanation
Any TRON contract account configured with an `Active`/custom `Permission` requiring, e.g., 2-of-3 or M-of-N key weight, and any smart contract that relies on `ValidateMultiSign` (address 0x0...1a, TIP-1) to gate privileged operations (fund transfers, contract upgrades, role changes) can have its threshold bypassed by a single participant supplying two malleated/distinct signatures for the same key. This is a critical broken-access-control bug reachable purely by an unprivileged contract caller who controls only one of the required keys, enabling unauthorized account operations / theft of funds guarded by multisig logic built on this precompile.

### Likelihood Explanation
The precompile is reachable by any `TriggerSmartContract` transaction from any unprivileged account — no special role, mining position, or witness/SR status required. Producing a second differently-encoded valid ECDSA signature for the same key/hash (malleability) or simply re-signing is trivial and requires no protocol-level access. The only mitigation is `MUtil.checkCPUTime()`, which is a resource/time guard, not a correctness check, and does not prevent the weight from being added.

### Recommendation
Change the de-duplication key in `ValidateMultiSign.execute()` from raw signature bytes to the recovered address: once `recoveredAddr` has contributed weight once, skip it entirely regardless of the specific signature bytes presented (mirroring `TransactionCapsule.checkWeight`'s `addMap.containsKey` check that throws "has signed twice!"). I.e., replace the `matrixContains(executedSignList, sign)` inner check with an address-only check that unconditionally `continue`s once an address has already been counted.

### Proof of Concept
1. Deploy/select an account with `Permission` (id=2, `Active`) requiring `threshold = 2`, containing a single key `K` with `weight = 1` and a second unrelated key `K2` with `weight = 1` (so no single key alone should pass).
2. Have holder of `K` produce two distinct valid signatures over the same TIP-1 hash `sha256(address || permissionId || data)`:
   - `sig1 = K.sign(hash)`
   - `sig2` = the malleated counterpart of `sig1` (flip `s` to `n - s` and adjust `v`), which is still a cryptographically valid signature recoverable to `K`'s address.
3. Call the `ValidateMultiSign` precompile (address `0x…1a`) with `signatures = [sig1, sig2]`.
4. In `execute()`, the first pass adds `K`'s weight (1) to `totalWeight`. The second pass sees `recoveredAddr` (K) already in `executedSignList`, but since `sign` (the merged byte string) differs from the stored one, it does not `continue`; it proceeds to add `K`'s weight again, making `totalWeight = 2`.
5. `totalWeight (2) >= threshold (2)` returns `true` (`dataOne()`), even though only one real key (`K`) participated and `K2` never signed — the multisig requirement is bypassed with a single compromised/available key. [3](#0-2)
