### Title
Attacker can permanently grief `feeCollector` (or any account) via dust `DepositToken` transfers, DoS-ing all fee-bearing deposits/withdrawals — ([File: contracts/Pool.sol])

### Summary
Analogous to the Argo CD Gogs webhook crash — where an unauthenticated request reaches a code path that fails on data the handler never validated — any EOA can push unvalidated state into `Pool.depositTokensOfAccount` for an arbitrary account by `transfer()`-ing dust amounts of every whitelisted `DepositToken`. Once the account's combined `debtTokensOfAccount.length + depositTokensOfAccount.length` reaches `MAX_TOKENS_PER_USER`, `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` (Pool.sol:143-148, 216-219), and because `DepositToken._mint`/`_transfer` unconditionally call it for first-time recipients (DepositToken.sol:486-489, 517-520), targeted accounts become unable to receive any *new* deposit-token type.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient previously held a zero balance (DepositToken.sol:517-520). There is no opt-in, allowlist, or minimum amount — anyone can `transfer(victim, 1 wei)` of each whitelisted deposit token.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, reverting `UserReachedMaxTokens` once the account's token list is full (Pool.sol:143-148, 216-219).
- `deposit()` mints fees to `feeCollector` (`_mint(feeCollector, fee)`, DepositToken.sol:231) and `_withdraw` transfers fees to it (DepositToken.sol:547). If the attacker fills `feeCollector`'s list with dust across all deposit tokens, every deposit/withdrawal in any new collateral type added later — and every deposit token the collector doesn't already hold — reverts.
- For a victim user, stuffing `MAX_TOKENS_PER_USER` slots blocks `deposit()` of a collateral type they don't already hold and `DebtToken.issue`/`mint` of a new synth (`addToDebtTokensOfAccount` has the same guard, Pool.sol:204-208). An underwater victim cannot add a *new* collateral type to restore health, while liquidations proceed normally — converting the revert-DoS into liquidation-enabled loss.

### Impact Explanation
- Temporary freezing of funds / liveness break: `deposit`, `withdraw`, `DebtToken.issue`, `seize` to a stuffed recipient all revert at the `addTo*` step until the account sheds tokens.
- Forced liquidation: a stuffed victim at the cap cannot deposit a new collateral type to recover health before being liquidated via `Pool.liquidate` (Pool.sol:537-596).
- `feeCollector` stuffing creates a protocol-wide wedge: any deposit token it doesn't yet hold cannot route its fee, reverting all fee-bearing deposits/withdrawals for that token.

### Likelihood Explanation
- Fully permissionless: requires only holding dust of each whitelisted `DepositToken` (easily bought/deposited) and calling `transfer(victim, dust)`.
- No modifier stops it: `transfer`/`transferFrom` only check the sender's `unlockedBalanceOf` (DepositToken.sol:348-376); the recipient is unvalidated.
- Cost scales with `MAX_TOKENS_PER_USER` dust transfers — cheap; mitigation requires the target to manually burn/transfer out entries, which the feeCollector (a multisig/contract) may not do promptly.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` non-reverting at cap for `seize`/fee transfers, or silently skip list insertion and iterate a bounded alternative.
- Remove per-account list growth from the recipient side of `transfer` (only track via deposit/issue paths), or exempt `feeCollector`/`Treasury` from the cap.
- Allow users to forcibly remove a deposit token they hold dust of (e.g., permissionless `removeFromDepositTokensOfAccount` when balance < threshold).

### Proof of Concept
Hardhat sketch (reproducible against deployed config):

```ts
// feeCollector / victim griefing via dust transfers
const feeCollectorAddr = await poolRegistry.feeCollector()
const depositTokens = await pool.getDepositTokens() // all whitelisted msdTOKENs

// attacker deposits dust into each collateral to obtain msdTOKENs
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('IERC20', await token.underlying())
  await underlying.approve(dt, 1000)
  await token.deposit(1000, attacker.address)
}

// stuff the feeCollector's per-account list to MAX_TOKENS_PER_USER
for (const dt of depositTokens) {
  const token = await ethers.getContractAt('DepositToken', dt)
  await token.transfer(feeCollectorAddr, 1) // adds dt to collector's list
}
// (repeat with a second pool's deposit tokens / remaining slots until at cap)

// now any deposit that mints a fee of a token type the collector doesn't already hold reverts:
await expect(
  msdNewCollateral.connect(user).deposit(amount, user.address) // _mint fee → addToDepositTokensOfAccount(feeCollector)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// victim variant: stuff `victim` to cap, drop price → victim cannot deposit a
// new collateral type to save position; liquidator succeeds.
await expect(
  otherDepositToken.deposit(amount, victim.address)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens')
await pool.connect(liquidator).liquidate(msETH, victim.address, repay, msdMET) // succeeds
```

*Uncertainty note:* I could not read the exact `MAX_TOKENS_PER_USER` constant value or `Pool.sol` storage header in the iterations available, so the cap's numeric size is unverified, but the guard's revert semantics (Pool.sol:143-148) and the unconditional `addTo*` calls in `DepositToken` (DepositToken.sol:486-489, 517-520) are confirmed in code.
