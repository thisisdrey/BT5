### Title
Unvalidated SSRF + Unrestricted Tar Extraction in `CreateRepositoryFromSnapshot` - ([File: internal/gitaly/service/repository/create_repository_from_snapshot.go])

### Summary
`CreateRepositoryFromSnapshot`'s `untar` helper fetches an arbitrary, caller-supplied HTTP URL and pipes the raw response body directly into the system `tar` binary for extraction into the target repository path, with no validation of the destination URL or of the archive contents. The code itself flags this as an unresolved risk.

### Finding Description
The RPC handler builds an HTTP request directly from the attacker-controlled `in.GetHttpUrl()` field and, optionally, forwards a caller-controlled `Authorization` header from `in.GetHttpAuth()`: [1](#0-0) 

The response body is then piped straight into `tar -C path -xvf -` with no inspection of tar entries for path traversal, absolute paths, or symlink escapes, and no restriction on the reachable network destinations (no private/link-local IP block-list beyond the optional caller-supplied `ResolvedAddress` pinning, which itself is attacker-controlled input): [2](#0-1) 

The code comment in `CreateRepositoryFromSnapshot` explicitly acknowledges the danger without mitigating it: [3](#0-2) 

This mirrors the Velodrome bug class in spirit: two conceptually related code paths in the same codebase are assumed to be "close enough" to share a trust model, but one path lacks the protections the other has. Elsewhere in this same repository, tar extraction from untrusted sources (e.g. `extractTarToDirectory` used by `ReplicateRepository`/snapshot replication) has been hardened with explicit checks against path traversal and symlink escapes: [4](#0-3) 

`CreateRepositoryFromSnapshot`'s `untar`, by contrast, has none of these protections and instead delegates entirely to the external `tar` binary with no sandboxing, no allow-listed destination host, and no post-extraction verification — despite handling equally attacker-influenced input (an arbitrary URL and its response body).

### Impact Explanation
An unprivileged or semi-privileged caller able to invoke `CreateRepositoryFromSnapshot` (e.g., via a crafted RPC field during project import/migration flows that plumb a user-supplied URL through to this endpoint) can:
- Cause the Gitaly node to make outbound HTTP requests to arbitrary internal endpoints (SSRF), including internal metadata/services not otherwise reachable, since only an optional pinned `ResolvedAddress` is validated as an IP — the URL itself is not restricted to any allow-list.
- Have the fetched response's tar stream extracted with the full permissions of the Gitaly process into the newly created repository directory, with no protection against malicious tar entries (e.g., absolute paths, symlink-based escapes, or hardlinks) that this same codebase already recognizes as a risk in adjacent extraction code paths.

### Likelihood Explanation
Likelihood depends on how exposed this RPC is to untrusted callers. Gitaly's own code comment states the archive is "trusted *a lot*" and that the RPC "should undergo a lot of hardening" before being pointed at endpoints not under Gitaly's control — indicating the maintainers themselves consider the current access-control assumption fragile. Any caller (or upstream feature) that lets a user influence `HttpUrl` reaches this code path directly, with no additional validation layer inside Gitaly.

### Recommendation
- Validate/allow-list the destination host and enforce private-IP/link-local blocking by default, not only when an explicit `ResolvedAddress` happens to be supplied.
- Replace the shelled-out `tar` extraction with a Go-native, hardened extractor (as already implemented in `extractTarToDirectory`) that rejects absolute paths, `..` traversal, and symlink/hardlink escapes before writing any file.
- Reconsider whether this RPC should remain reachable from any code path where the `HttpUrl`/`HttpAuth` fields can be influenced by an untrusted request originator, and add compensating authorization checks if so.

### Proof of Concept
1. Trigger `CreateRepositoryFromSnapshot` with `HttpUrl` pointing at an internal-only service (e.g., `http://169.254.169.254/...` or an internal Gitaly/GitLab admin endpoint) to demonstrate SSRF.
2. Alternatively, host a tar archive containing an entry with a symlink pointing outside the target directory followed by a regular file entry using that symlink's name, and supply its URL as `HttpUrl`; observe that `tar -xvf -` writes through the symlink outside the intended repository path since no validation is performed before invoking `tar`.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}
