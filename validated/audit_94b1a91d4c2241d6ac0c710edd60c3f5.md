### Title
Deleting an account leaves orphaned PostponedReceiptId/PendingDataCount/PostponedReceipt trie rows, permanently freezing embedded deposits - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` only deletes the `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie entries for an account, but never removes `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` rows that were written for that `account_id` as receiver. Since these rows are never counted toward `account.storage_usage()`, an attacker can create such rows and still pass the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check in `action_delete_account`, permanently orphaning any deposit-carrying receipt.

### Finding Description
When a cross-contract action receipt arrives with unmet `input_data_ids`, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) writes `TrieKey::PostponedReceiptId` for each missing `data_id` [1](#0-0) , a `TrieKey::PendingDataCount` counter, and the receipt itself via `set_postponed_receipt` under `TrieKey::PostponedReceipt` [2](#0-1) . None of these writes touch `account.storage_usage()` — the account's storage-usage counter is left completely unaffected by postponed receipts.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) only guards against large *account* storage usage: it computes `account_storage_usage` from `account.storage_usage()` minus contract code size and checks it against `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE` [3](#0-2) . Because postponed-receipt rows never contribute to `storage_usage()`, this check does not detect or block deletion of an account with pending postponed receipts.

`remove_account` (`core/store/src/utils/mod.rs:505-575`) then removes `Account`, `ContractCode`, access keys/gas-key nonces, and contract-data rows [4](#0-3) , but never iterates or removes `PostponedReceiptId`, `PendingDataCount`, or `PostponedReceipt` keyed by that account, unlike the documented full column set in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` which explicitly lists `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, and `POSTPONED_RECEIPT` as account-scoped columns [5](#0-4) .

Attacker flow: (1) the attacker's own contract issues (to itself) an action receipt with an `input_data_ids` entry that will never be satisfied (e.g. a callback awaiting a promise that is never resolved, or referencing a `data_id` that has no matching output producer) — this is entirely achievable from a single contract call the attacker controls, causing `process_action_receipt` to postpone the receipt for the attacker's own account. (2) Once the postponed rows exist, the attacker submits `DeleteAccountAction` on the same account. Since `storage_usage()` never reflected the postponed rows, the account passes the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check trivially (e.g. with a fresh account whose only usage is the base account/keys). `remove_account` deletes the account but leaves the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows in the trie, permanently orphaned since no account exists anymore to resolve or reference them.

### Impact Explanation
Any deposit (`Transfer`/`FunctionCall` with attached balance) embedded in the postponed action receipt becomes permanently unreachable: the receipt can never execute (no account exists to receive it, and any `Data` receipt satisfying its `input_data_ids` would look up `PostponedReceiptId`/`PendingDataCount` under the same now-nonexistent `account_id`, executing stale state pointing to a deleted account). This is a liveness violation (a receipt that never resolves) and a fund-freezing bug: the deposit amount is locked in the trie forever, not refunded to any party, not reflected in the deleted account's balance, and not part of any beneficiary's balance — this matches "permanent freezing of user funds" and orphaned-state impact categories.

### Likelihood Explanation
The preconditions are fully within reach of an unprivileged attacker: deploy a self-callable contract, issue a cross-contract promise-then-callback to itself where the callback's dependency is never satisfied (trivial via a dangling `input_data_id` produced from a promise that is never resolved, e.g. targeting a receiver/method that will fail before producing the awaited `Data` receipt, or a batch action combining a doomed function call with a callback), then submit a normal `DeleteAccountAction` transaction signed with the account's own full-access key. Cost is limited to gas and the deposit amount the attacker chooses to lock (which could be attacker's own or, more concerning, funds sent to them by a third party expecting a callback). It is fully repeatable with any account and does not require validator or node privileges.

### Recommendation
Update `remove_account` in `core/store/src/utils/mod.rs` to also scan and remove `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceipt` entries for the account being deleted (and ideally `PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldId*` per `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`), or alternatively block `DeleteAccountAction` when any such pending rows exist for the account (similar to the existing storage-usage guard), refunding/canceling the postponed receipt's deposit back to a beneficiary before allowing deletion.

### Proof of Concept
Integration/runtime-test-loop plan:
1. Set up two accounts, `alice` (attacker) and a helper contract account.
2. Have `alice`'s contract issue an action receipt targeting `alice` itself with a `FunctionCall`/`Transfer` action and an `input_data_ids` entry corresponding to a `data_id` that will never be delivered (e.g., construct a receipt directly in the test via `set`/`process_action_receipt`-equivalent test helper, or trigger via a promise chain where the dependency callback never fires).
3. Verify via `get(state_update, &TrieKey::PendingDataCount{...})` and `get_postponed_receipt` that the `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows exist for `alice`, and confirm `get_account(state_update, alice).storage_usage()` is below `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`.
4. Submit a `DeleteAccountAction` transaction from `alice` to itself (or via a receipt) with a valid beneficiary.
5. Assert `action_delete_account` succeeds (`result.result` is `Ok`), `get_account(state_update, alice)` returns `None`.
6. Assert the `PendingDataCount`/`PostponedReceipt`/`PostponedReceiptId` rows still exist in the trie for `alice`'s former `account_id` (proving orphaned state).
7. Assert the deposit balance embedded in the postponed receipt is not present in the beneficiary's balance nor reflected as burnt in `result.tokens_burnt`, demonstrating the funds are unaccounted-for and permanently frozen.
