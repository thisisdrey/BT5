### Title
Attacker fills a victim's per-account collateral list with dust transfers, DoS-ing deposits, transfers and liquidations - (File: contracts/Pool.sol)

### Summary
The external report (CVE-2020-13575) is a denial-of-service triggered by a single crafted request. The closest reachable analog in Metronome is capped-list griefing: `Pool` tracks each account's deposit tokens in a bounded `MappedEnumerableSet` (`depositTokensOfAccount`), and `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token was zero. An unprivileged attacker can send dust amounts of every registered `DepositToken` to any target, filling the victim's list up to `MAX_TOKENS_PER_USER`, after which any operation that adds a new deposit token to the victim's list reverts.

### Finding Description
`DepositToken._transfer` adds the token to the recipient's per-account set whenever `_recipientBalanceBefore == 0 && amount_ > 0` — there is no minimum amount, so a 1-wei transfer permanently occupies a slot until the recipient clears it. [1](#0-0) 
The same add happens on `_mint`, so `deposit(amount_, onBehalfOf_ = victim)` for a new collateral also reverts once the list is full. [2](#0-1) 
The per-account lists are stored in `PoolStorageV1` as `MappedEnumerableSet.AddressSet` and are bounded so that `debtPositionOf`/`depositOf` iterations stay within gas. [3](#0-2) 
`seize` (called by `Pool.liquidate`) routes through the same `_transfer`, so a liquidator whose list is pre-filled cannot receive any collateral token it does not already hold, and the whole `liquidate` call reverts. [4](#0-3) 
Because the attacker only needs public `transfer`/`transferFrom` calls with dust, no privileged role, oracle manipulation, or trusted-remote assumption is required. Note: I could not open `Pool.addToDepositTokensOfAccount`/`MappedEnumerableSet` within the tool-call budget to cite the exact `MAX_TOKENS_PER_USER` revert line; the cap's existence is implied by the bounded-iteration design and the storage layout, but its exact threshold and revert path should be confirmed on the deployed implementation.

### Impact Explanation
- Targeted freeze of new collateral deposits: a victim cannot deposit into any collateral token not already in their list (`deposit(..., onBehalfOf_=victim)` reverts), and no one can transfer a new `DepositToken` to them. If the victim is approaching liquidation and their remaining collateral type is new to them, they cannot add collateral to restore health.
- Liquidation DoS: by dust-filling known liquidator EOAs/bots, every `seize` to that liquidator reverts for unheld tokens, delaying liquidation of underwater positions and increasing bad-debt risk for the pool.
- Recovery exists (victim can transfer/withdraw dust to free slots), so this is temporary freezing/griefing rather than permanent loss, but it is re-appliable at near-zero cost and can be timed against liquidation transactions.

### Likelihood Explanation
Cost is one dust transfer per registered `DepositToken` (a handful of transactions) against any address; no capital, flash loan, or privileged role is needed. It requires that `addToDepositTokensOfAccount` reverts once the cap is reached (bounded-set design indicates it does) and that `whenNotPaused`/health checks do not block dust transfers — transfers of unlocked balances have no health check beyond `_revertIfLocked`, which dust satisfies. [5](#0-4) 

### Recommendation
- In `Pool.addToDepositTokensOfAccount`, skip or silently ignore additions once the cap is reached instead of reverting, or only add tokens for balances above a non-trivial dust threshold (e.g., `>= 1e3` units or a USD-denominated minimum via the master oracle).
- Alternatively, make `seize`/liquidation bypass the per-account set or allow liquidation to a liquidator-specified recipient that already holds the token.

### Proof of Concept
Hardhat sketch (assumes deployed `Pool` with ≥ N registered `DepositToken`s where N = `MAX_TOKENS_PER_USER`):

```ts
// attacker deposits tiny amounts of every collateral to self, then dusts victim
for (const dToken of depositTokens) {
  await dToken.connect(attacker).deposit(1, attacker.address);
  await dToken.connect(attacker).transfer(victim.address, 1); // fills slot
}
// victim's list is now full
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.reverted; // addToDepositTokensOfAccount hits cap

// liquidator's list also filled -> seize inside Pool.liquidate reverts
await expect(pool.connect(liquidator).liquidate(victim.address, ...)).to.be.reverted;
```
