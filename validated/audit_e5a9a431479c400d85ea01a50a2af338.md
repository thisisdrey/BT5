### Title
Sandwich/front-running of `ExchangeInjectContract` and `ExchangeWithdrawContract` allows value extraction from liquidity providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java` and `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Bancor-style TRC10 `Exchange` (AMM-like pool: `ExchangeCreateContract`, `ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) implements the exact recommended fix from the external report for its swap path — `ExchangeTransactionContract` carries an `expected` minimum-output field that is enforced in `ExchangeTransactionActuator.doValidate()`. However, `ExchangeInjectContract` and `ExchangeWithdrawContract` — the analogs of `pool.mint`/`pool.burn` in the report — have **no slippage-protection field at all**. The amount of the "another token" credited/debited on inject/withdraw is computed purely from the pool's instantaneous ratio at execution time, exactly like the unprotected `pool.mint`/`pool.burn` calls flagged in the Hypervisor report.

### Finding Description
`ExchangeInjectContract` (`protocol/src/main/protos/core/Tron.proto`) only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no minimum/maximum bound on the paired token amount. Same for `ExchangeWithdrawContract`.

In `ExchangeInjectActuator.execute()` (and identically in `doValidate()`), the counter-token amount is derived from the live pool balances at execution time: [1](#0-0) 

and in `doValidate()`: [2](#0-1) 

There is no check comparing `anotherTokenQuant` to any user-supplied minimum/maximum bound — only a `> 0` sanity check: [3](#0-2) 

The same pattern exists for `ExchangeWithdrawActuator`: [4](#0-3) 

By contrast, `ExchangeTransactionContract` explicitly carries an `expected` field and `ExchangeTransactionActuator.doValidate()` enforces it: [5](#0-4) [6](#0-5) 

This asymmetry means the swap leg of the AMM is protected against sandwiching (matching the auditor's remediation for `pool.swap`/`pool.mint`/`pool.burn`), but the liquidity provisioning/removal legs (`Inject`/`Withdraw`, the direct analogs of `pool.mint`/`pool.burn`) are not. Since java-tron transactions are broadcast to a public mempool and packed by block-producing witnesses (no pre-committed ordering guarantee for a specific user's transaction relative to others in the same block), an attacker (any unprivileged account) can:
1. Observe a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from a victim in the mempool.
2. Front-run it with an `ExchangeTransactionContract` swap that shifts `firstTokenBalance`/`secondTokenBalance` ratio unfavorably for the victim.
3. Let the victim's inject/withdraw execute at the manipulated ratio, causing them to deposit more value than they intend to receive (inject) or receive less than expected (withdraw).
4. Back-run with a reverse swap to restore the ratio and capture the extracted value, similar to the classic Uniswap V3 sandwich pattern described in the report for `pool.mint`/`pool.burn`.

### Impact Explanation
A victim calling `ExchangeInjectContract` or `ExchangeWithdrawContract` has no way to bound the amount of the paired asset they will contribute or receive. An attacker who can front-run/back-run (any TRX holder capable of broadcasting transactions with sufficient bandwidth/energy, which is a low bar) can extract value from the victim's inject or withdraw operation — this is a direct, unbacked economic loss for the victim (theft of funds via price manipulation), analogous to the Medium-severity impact accepted in the original report for `pool.mint`/`pool.burn`.

### Likelihood Explanation
Likelihood is moderate-to-high for any TRC10 Bancor exchange pair with meaningful liquidity: front-running/sandwiching via public mempool observation and same-block or adjacent-block transaction ordering is a well-known, low-cost, permissionless technique. No special privilege is required — the attacker just needs to submit ordinary `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transactions.

### Recommendation
Add an explicit minimum/maximum bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `expected` in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation, so a liquidity provider can specify the maximum amount of the paired token they are willing to contribute (inject) or the minimum amount they expect to receive (withdraw), rejecting the transaction otherwise.

### Proof of Concept
1. Victim submits `ExchangeInjectContract{exchange_id, token_id=A, quant=Q}` intending to inject token A and expects to also contribute ~`R` of token B based on the pool's current ratio (`firstTokenBalance`/`secondTokenBalance`) as observed off-chain.
2. Attacker observes the pending transaction in the mempool and submits `ExchangeTransactionContract` swapping a large amount of token B into the pool immediately before the victim's transaction lands in the same or an adjacent block, shifting the ratio so that `anotherTokenQuant` computed in `ExchangeInjectActuator.execute()` (line 73-74 or 79-80) is now much larger than `R`.
3. Victim's `ExchangeInjectContract` executes and is forced to contribute the inflated `anotherTokenQuant` of token B (`accountCapsule.reduceAssetAmountV2` at line 98) — since there is no minimum/maximum check, the transaction still validates as long as the victim has sufficient balance.
4. Attacker submits a reverse `ExchangeTransactionContract` to restore the pool ratio, effectively capturing the excess value contributed by the victim, mirroring the sandwich pattern the report identifies for `pool.mint`.

Note: I was unable to load `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java` (the `transaction()`/Bancor price-curve implementation) due to a tool error in the final iteration, so the exact bonding-curve formula used for `ExchangeTransactionContract` swaps could not be fully verified — this does not affect the core finding (absence of slippage bounds in Inject/Withdraw), but a full review of `ExchangeCapsule` would help refine the exact manipulation magnitude achievable per swap.
