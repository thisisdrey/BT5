### Title
Dust-transfer griefing fills victim's `MAX_TOKENS_PER_USER` slots, DoS-ing deposits, mints and collateral top-ups - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` keeps a per-account enumerable set of deposit and debt tokens capped at `MAX_TOKENS_PER_USER = 30`. Every `DepositToken` mint/transfer to a zero-balance recipient calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. An unprivileged attacker can push dust amounts of every supported deposit token to a victim, permanently occupying their slots and making any subsequent receipt of a *new* deposit-token type (including the victim's own deposits of a new collateral) revert.

### Finding Description
- `Pool.addToDepositTokensOfAccount` enforces the cap via `onlyIfAdditionWillNotReachMaxTokens` (`contracts/Pool.sol:143-148`, `216-220`).
- `DepositToken._transfer` invokes `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero (`contracts/DepositToken.sol:517-520`); the same hook fires on `_mint` (`contracts/DepositToken.sol:485-488`).
- `DepositToken.transfer` is a public, unlocked path for any sender with no locked collateral (`contracts/DepositToken.sol:348-354`), so the attacker only needs to hold 1 wei of each deposit token.
- Symmetrically, `DebtToken` issuance calls `addToDebtTokensOfAccount` under the same shared cap, so filling slots also blocks the victim from minting any new synthetic debt type.

Attack flow (all public, unprivileged):
1. Attacker deposits minimal underlying into each of the pool's deposit tokens (pool-level cap is also `MAX_TOKENS_PER_USER`, enforced in `addDepositToken`, `contracts/Pool.sol:703`), obtaining dust `msdToken` balances.
2. Attacker calls `depositToken.transfer(victim, 1)` for each token type the victim doesn't already hold until the victim's combined list reaches 30.
3. From then on, any `DepositToken` transfer/mint of a token type the victim doesn't already hold — including the victim calling `deposit(amount, victim)` on a new collateral — reverts inside `Pool.addToDepositTokensOfAccount`, reverting the whole transaction.

### Impact Explanation
Liveness/availability impact matching the DoS bug class:
- The victim cannot add *new* collateral types. If their position approaches the liquidation threshold, a front-running attacker can dust-fill the remaining slots so the victim's rescue deposit reverts, forcing the position into liquidation (`Pool.liquidate`, `contracts/Pool.sol:541-596`) and causing loss of collateral beyond what a healthy top-up would have cost.
- The victim cannot mint new synthetic debt types either, since `debtTokensOfAccount` shares the same 30-slot budget.
- Any inbound transfer of a not-yet-held deposit token to the victim reverts, breaking integrations that deposit on behalf of users (`deposit(amount_, account_)`, `NativeTokenGateway.deposit`, `VesperGateway`, `SmartFarmingManager` leverage paths).

Mitigation exists: the victim can clear a slot by transferring/withdrawing a dust balance to zero, which triggers `removeFromDepositTokensOfAccount` (`contracts/DepositToken.sol:522-525`). However the attacker can cheaply re-dust the freed slot in the same or next block, so the victim must bundle clear+deposit atomically — a capability not offered by the current single-token `deposit` entry points. No funds are stolen directly; the harm is a repeatable, low-cost freeze of the victim's ability to onboard collateral — temporary freezing of the deposit path, with liquidation loss as a realistic consequence.

### Likelihood Explanation
- Reachable by any EOA holding dust of each deposit token; cost is bounded by minimum deposits across ≤30 collaterals and is largely recoverable (attacker can withdraw their dust afterward).
- Effectiveness scales with the number of pool deposit tokens; on deployments with few collaterals the attacker needs fewer dust types but the victim also has fewer slots to fill with their own holdings, so the attack remains practical whenever the victim's used slots + attacker dust ≥ 30.
- Requires no privileged role, no oracle manipulation, and no reentrancy; only standard `transfer`/`deposit` calls.

### Recommendation
- Do not revert on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the cap is reached; instead skip the list addition and account for untracked tokens in `debtPositionOf`/`depositOf`/`debtOf`, or
- make list membership opt-in (user calls a `trackToken` function) so unsolicited dust cannot consume slots, or
- revert only on the *sender* side of unsolicited transfers (i.e., exempt `deposit`/`mint` paths), so a victim's own deposits are never blocked by attacker-sent dust.

### Proof of Concept
Hardhat (fork or fixture) sketch:

```ts
// pool with N deposit tokens; victim has usedSlots < 30
const victim = alice.address;
const max = (await pool.MAX_TOKENS_PER_USER()).toNumber();

// attacker obtains dust of each deposit token and fills victim's slots
for (const dt of depositTokens) {
  await underlying.connect(attacker).approve(dt.address, dust);
  await dt.connect(attacker).deposit(dust, attacker.address); // mint msd dust
  if (await dt.balanceOf(victim) == 0) {
    await dt.connect(attacker).transfer(victim, 1); // +1 slot each
  }
}
// ...repeat until depositTokensOfAccount(victim) + debtTokensOfAccount(victim) == 30
expect(await pool.getDepositTokensOfAccount(victim))
  .length.to.eq(max - await pool.getDebtTokensOfAccount(victim).length);

// victim's own deposit of a NEW collateral now reverts
await newUnderlying.connect(alice).approve(newDepositToken.address, amount);
await expect(
  newDepositToken.connect(alice).deposit(amount, victim)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// any inbound transfer of a new token type to victim also reverts
await expect(
  newDepositToken.connect(attacker).transfer(victim, 1)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// debt side: victim cannot mint a new synthetic type either
await expect(
  newDebtToken.connect(alice).mint(amount, victim)
).to.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Key call chain per dust fill: `DepositToken.transfer` → `_transfer` → `Pool.addToDepositTokensOfAccount` → `onlyIfAdditionWillNotReachMaxTokens` → `UserReachedMaxTokens`.
