### Title
Missing Slippage Protection in `ExchangeInjectActuator` / `ExchangeWithdrawActuator` Enables Sandwich Attacks Against TRON's Bancor-style Exchange - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The external report describes `LiquidityFundsManage.sol`'s `addLiquidity_P()`/`removeLiquidity_P()` computing proportional swap/liquidity amounts from a manipulable on-chain pool state with no caller-supplied minimum/maximum bound, making them susceptible to sandwich attacks. java-tron's on-chain Bancor-style exchange module has a direct analog: `ExchangeInjectActuator` (add liquidity) and `ExchangeWithdrawActuator` (remove liquidity) compute the counter-token amount from the *live* pool ratio at execution time and accept **no user-specified minimum/maximum bound** on that computed amount, unlike the sibling `ExchangeTransactionActuator` (a trade/swap) which does enforce a caller-supplied `expected` floor.

### Finding Description
`ExchangeInjectActuator.execute()`/`doValidate()` computes `anotherTokenQuant` purely from `firstTokenBalance`/`secondTokenBalance` at execution time: [1](#0-0) 
and in validate: [2](#0-1) 

The `ExchangeInjectContract` fields consumed here are only `exchangeId`, `tokenId`, and `quant` — there is no field equivalent to `ExchangeTransactionContract.expected`, which is the exact bound `ExchangeTransactionActuator` checks: [3](#0-2) 

`ExchangeWithdrawActuator` exhibits the same pattern — `anotherTokenQuant` is derived from the pool ratio at execution time with only an internal precision check (`"Not precise enough"`) against the transaction's own recomputation, not any caller-chosen bound protecting against pool-state manipulation: [4](#0-3) 

Because the pool state (`firstTokenBalance`/`secondTokenBalance`) is mutated by any account's `ExchangeTransactionContract` trade (executed via `ExchangeCapsule.transaction()`): [5](#0-4) 
an attacker who can get a trade transaction ordered immediately before the victim's inject/withdraw transaction — and a reversing trade ordered immediately after — can shift the ratio the inject/withdraw math uses, forcing the exchange creator to deposit disproportionately more of the counter-token (or receive disproportionately less on withdrawal) than the pool's steady-state ratio would imply, exactly mirroring the `addLiquidity_P()`/`removeLiquidity_P()` bug class in the report.

### Impact Explanation
A successful sandwich against `ExchangeInjectContract`/`ExchangeWithdrawContract` transfers real TRX/TRC10 value from the exchange creator to the attacker: the creator overpays the counter-token on inject or receives less than fair value on withdrawal, while the attacker's bracketing trades capture the difference. This is a concrete, unauthorized transfer of value between two unprivileged accounts (theft of funds), reachable purely through ordinary signed transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) — no privileged role or malicious-SR behavior is required, only transaction-ordering advantage that any broadcaster can attempt.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to get transactions ordered around the victim's inject/withdraw transaction within the same or adjacent blocks, and it requires an exchange creator to actually submit inject/withdraw operations (this contract type/API is legacy and less used than TRC20/TVM DEXs today, but is still live and reachable on-chain). Unlike `ExchangeTransactionActuator`, which already mitigated this exact class of issue by adding the `expected` slippage-floor parameter, `ExchangeInjectActuator`/`ExchangeWithdrawActuator` were never given an equivalent protection, so the vulnerability is structurally present whenever these actuators are used.

### Recommendation
Add an explicit slippage-bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `ExchangeTransactionContract.expected`), and validate the computed `anotherTokenQuant` against a caller-supplied minimum (for withdraw) or maximum (for inject) in `doValidate()`, rejecting the transaction if the live pool ratio has moved outside the caller's tolerance — mirroring the fix already applied to `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange creator submits `ExchangeInjectContract` intending to inject `tokenQuant` of token A, expecting `anotherTokenQuant` of token B based on the currently observed pool ratio `firstTokenBalance:secondTokenBalance`.
2. Attacker broadcasts an `ExchangeTransactionContract` trade that shifts the ratio (e.g., sells a large amount of token B into the pool) so that it lands immediately before the creator's inject transaction in block ordering.
3. `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant` from the now-skewed ratio: [6](#0-5) 
forcing the creator to deposit more token B than the pre-attack ratio warranted, with no `expected`/bound check to reject this (contrast with `ExchangeTransactionActuator`'s check at lines 217-221).
4. Attacker submits a reversing `ExchangeTransactionContract` trade afterward, restoring the ratio and extracting the excess value deposited by the creator. [7](#0-6)

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
