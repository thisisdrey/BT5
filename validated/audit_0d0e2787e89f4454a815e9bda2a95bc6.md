### Title
Disabled-API blocklist bypass via path segment mismatch in `HttpApiAccessFilter.isDisabled` - (File: framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java)

### Summary
`reference.conf`'s `disabledApi` list lets an operator disable specific wallet HTTP endpoints (e.g. `getaccount`) for hardening purposes. Enforcement is done in `HttpApiAccessFilter.isDisabled()` [1](#0-0) , which builds `endpoint = contextPath + servletPath`, calls `URI.create(endpoint).normalize()`, and then extracts only `endpoint.split("/")[2]` to match against the (lowercased) blocklist. This is a custom canonicalization that must exactly agree with how the actual Jetty `ServletContextHandler`/`FilterHolder` routing (mapped with `"/*"` and per-service path specs, see `FullNodeHttpApiService.addFilter` and sibling services) resolves the request to a servlet — the same class of bug as the JupyterLab advisory, where a bespoke normalization diverges from the real resolver (pip) used to enforce the block.

### Finding Description
The filter's own regression test already demonstrates a case where the filter's segment-index parsing diverges from a simple traversal-normalized path: `"/wallet/a/b/../getnowblock"` is judged **not** disabled even though `"/wallet/getnowblock"` is [2](#0-1) . That happens because `URI.normalize()` only collapses `"/a/b/.."` into `"/a"`, not into `"getnowblock"` itself, so `split("/")[2]` yields `"a"`, not `"getnowblock"` — while `"/wallet/a/../b/../getnowblock"` does collapse to index `2 == "getnowblock"` and is correctly blocked [3](#0-2) . This confirms the filter's decision is purely a function of segment count/position after a shallow `..`-collapse, not of "which servlet will actually handle this request." Any additional path element the servlet container's routing tolerates or normalizes differently (extra path segments, double slashes, encoded segments, trailing slashes, `;jsessionid`-style matrix params, etc., all handled per-container by Jetty's `PathMap`/`ServletPathSpec` rather than by `URI.normalize()`) can shift which token lands at index `2` while Jetty still dispatches the request to the blocked servlet, exactly mirroring the JupyterLab bug class: the blocklist's own string-canonicalization is weaker/divergent from the canonicalization performed by the actual resolver (there: pip package-name normalization; here: Jetty's servlet path matching).

The filter is wired with wildcard mappings (`"/*"` for FullNode, `"/wallet/*"`/`"/walletsolidity/*"` for Solidity/PBFT nodes) in `FullNodeHttpApiService.addFilter`, `SolidityNodeHttpApiService.addFilter`, and `HttpApiOnPBFTService`/`HttpApiOnSolidityService` [4](#0-3) , so any servlet-path variant that Jetty routes to the target servlet but that the filter's simplistic `split("/")[2]` extraction misclassifies results in the "disabled" API still being served to an anonymous HTTP client.

### Impact Explanation
`disabledApi` is documented as a hardening control ("Disabled API list ... Case insensitive") intended to let operators turn off specific wallet RPCs for their deployment [5](#0-4) . If an unauthenticated/unprivileged HTTP client can construct a request whose servlet path is routed by Jetty to a disabled endpoint's servlet (e.g. `GetAccountServlet`, `GetNowBlockServlet`, or any sensitive query/broadcast endpoint an operator has chosen to disable) while `isDisabled()` computes a different (non-matching) index-2 token, the access-control the operator relies on is silently defeated. This can expose data or functionality the operator explicitly intended to remove from the node's attack surface (e.g. exposing shielded/sensitive query endpoints, or endpoints disabled specifically to reduce DoS/resource exposure), directly undermining node hardening.

### Likelihood Explanation
The bug is not hypothetical string-matching risk only — the shipped unit test already proves the filter is inconsistent for path variants that a servlet container's own normalization treats equivalently to the disabled path (`"/wallet/a/b/../getnowblock"` vs `"/wallet/getnowblock"`). An external attacker only needs an HTTP client and the exact routing behavior of the deployed Jetty version to find additional divergent encodings (double slashes, percent-encoded segments, trailing path info) reachable without authentication.

### Recommendation
Replace the ad-hoc `URI.normalize()` + `split("/")[N]` heuristic with a check that reuses the actual matched servlet name/path (e.g. `HttpServletRequest.getServletPath()`/matched `ServletMapping` from the container after routing, or the concrete servlet class), rather than re-deriving and re-parsing the path independently. At minimum, fully canonicalize the path (collapse all `.`/`..`, decode percent-encoding once, collapse duplicate slashes, strip trailing slashes/matrix params) before segmenting, and add tests asserting parity between what the disabled-API filter blocks and what the container actually dispatches for every servlet mapping registered in `FullNodeHttpApiService`/`SolidityNodeHttpApiService`/`HttpApiOnPBFTService`.

### Proof of Concept
1. Configure `disabledApi = ["getnowblock"]` (or `getaccount`) as in `HttpApiAccessFilterTest` [6](#0-5) .
2. Send `GET /wallet/a/b/../getnowblock` to the FullNode HTTP port (mapped via `"/*"`).
3. `isDisabled()` computes `endpoint.split("/")[2] == "a"`, which is not in the disabled list, so the filter allows the request through the chain.
4. If Jetty's own path routing for the deployed servlet mapping resolves this (or an analogous double-slash/encoded variant) to the `GetNowBlockServlet`/blocked servlet instance, the response is the live API output instead of the expected `{"Error":"this API is unavailable due to config"}`, confirming the blocklist bypass. (Exact confirmation that Jetty dispatches this specific variant to the servlet was not verified against the live Jetty version/config in this analysis — that would require running the full HTTP stack, which is outside the scope of static code review; the existing test at lines 144-150 demonstrates the *classification* divergence that is the root cause.)

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
