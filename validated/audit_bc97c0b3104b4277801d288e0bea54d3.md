### Title
Unprivileged dust-transfer/deposit fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoS-ing their deposits, mints, leverage and collateral top-ups - (File: contracts/Pool.sol)

### Summary
The CVE class is "low-privileged network attacker causes repeatable hang/DoS of a shared service". The Metronome analog: any EOA can force entries into another account's per-account token lists in `Pool`, because `DepositToken._transfer`, `DepositToken._mint` (via `deposit(amount_, onBehalfOf_)`) and `DebtToken` issuance all call `pool.addToDepositTokensOfAccount(account_)` / `addToDebtTokensOfAccount(account_)` for the *recipient*, and both functions enforce `onlyIfAdditionWillNotReachMaxTokens`, reverting with `UserReachedMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER = 30`. By dust-funding a victim (or the `feeCollector`) with 1-wei positions across the pool's deposit tokens, an attacker permanently blocks that account from receiving any *new* deposit or debt token, reverting deposits, mints, leverage, flash-repay and liquidation payouts that would add a new entry.

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`. The check runs on the *account* argument, not the caller.
- `DepositToken._mint` calls `pool.addToDepositTokensOfAccount(account_)` whenever `balanceBefore == 0`, so `deposit(amount_, onBehalfOf_)` lets any user push an entry onto an arbitrary victim's list by depositing 1 wei of underlying on their behalf.
- `DepositToken._transfer` does the same for `recipient_` whenever `recipientBalanceBefore == 0`, so a holder of msdTOKENs can dust-`transfer` to the victim directly (only `unlockedBalanceOf` of the *sender* is checked).
- `DebtToken` issuance adds debt tokens to the borrower's list the same way, and the two lists share the single cap of 30.
- A pool may hold at most `MAX_TOKENS_PER_USER` deposit tokens (`addDepositToken` reverts with `ReachedMaxDepositTokens` at 30), so filling a victim's list costs at most ~29 dust deposits/transfers plus whatever the victim already holds — trivially reachable for an unprivileged attacker.
- No pause flag, health check, reentrancy guard, or `SynthContext` check stops this: the revert is unconditional once the list is full, and entries only leave when the victim's balance of that token returns to zero.

### Impact Explanation
Once the victim's combined list hits 30:
- `deposit()`/`_mint` of any collateral the victim doesn't already hold reverts → the victim cannot top up collateral to defend an unhealthy position, so a forced liquidation becomes guaranteed even though they hold funds elsewhere (temporary freezing of funds / forced loss via liquidation).
- Minting or `SmartFarmingManager.leverage`/`flashRepay` for any new synthetic reverts → the victim is locked out of new borrow/leverage flows.
- Worse, the same attack applies to the protocol's `feeCollector` and to any liquidator address: `DepositToken._mint` sends deposit fees to `feeCollector()` and `seize`/`_transfer` sends liquidation fees there too. Dusting `feeCollector` to 30 entries makes every `deposit`, `withdraw`, and `Pool.liquidate` that would pay a fee in a token not already in the collector's list revert — a protocol-wide liveness/DoS condition matching the CVE's "repeatable crash (complete DOS)" until governance/operator manually drains the dust entries.
- Invariant broken: liveness/availability of core entry points for a targeted account (and potentially fee flows protocol-wide), caused purely by unprivileged calls.

### Likelihood Explanation
- Fully unprivileged: only needs public `deposit`/`transfer` with attacker-chosen `onBehalfOf_`/`to_` and dust amounts; no privileged role, oracle manipulation, or malicious infrastructure required.
- Cost is bounded: at most 30 dust deposits of supported underlyings (or reusing already-held msdTOKENs via `transfer`).
- No economic loss to the attacker (dust amounts only, withdrawable afterward), so the griefing is cheap and repeatable against each new victim or the `feeCollector`.
- Caveat: the victim can recover by fully withdrawing/burning one of the dust tokens to free a slot (each freed slot can be re-griefed), making this a persistent, repeatable DoS rather than permanent freezing — consistent with Medium severity.

### Recommendation
- Remove the cap check from `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` for additions triggered by incoming transfers/mints, or only enforce `onlyIfAdditionWillNotReachMaxTokens` on the *initiating* account (depositor/borrower), not the recipient.
- Alternatively, let `deposit(onBehalfOf_)`/`transfer` skip list insertion (or not revert) when the recipient is at the cap, recording the balance without list membership; or make `debtPositionOf`/`depositOf` iterate `balanceOf` over pool-level token lists instead of per-account lists.
- At minimum, exempt `feeCollector` (and `treasury`) from `onlyIfAdditionWillNotReachMaxTokens`, since griefing that address halts fee-bearing deposits, withdrawals and liquidations for everyone.

### Proof of Concept
Hardhat sketch (fork a deployed pool or use existing fixtures from `test/Pool.test.ts`):

```ts
// Victim holds some collateral and debt; attacker wants to block them.
const victim = alice.address
const depositTokens: DepositToken[] = await getAllPoolDepositTokens(pool) // up to 30

// 1) Fill victim's list: dust-deposit every deposit token on behalf of victim
for (const dToken of depositTokens) {
  const underlying = await dToken.underlying()
  await mintUnderlying(attacker, underlying, 1) // 1 wei
  await IERC20(underlying).connect(attacker).approve(dToken.address, 1)
  await dToken.connect(attacker).deposit(1, victim) // _mint -> addToDepositTokensOfAccount(victim)
}
// Optionally also dust-transfer any msdTOKEN the attacker already holds.

expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30)

// 2) Victim can no longer deposit a collateral type they don't already hold
await expect(
  newDepositToken.connect(alice).deposit(parseEther('1'), victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) Victim cannot mint a new synthetic either (debt-token list shares the cap)
await expect(
  msUSDDebtToken.connect(alice).issue(...) // or synth.mint path that adds debt token
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 4) Same attack against feeCollector bricks fee-bearing ops protocol-wide:
const feeCollector = await poolRegistry.feeCollector()
// ...dust all deposit tokens to feeCollector...
// Now any deposit/withdraw/liquidate paying a fee in a token not yet in
// feeCollector's list reverts inside DepositToken._mint/_transfer.
expect(await pool.getDepositTokensOfAccount(feeCollector)).to.have.length(30)
await expect(dToken.connect(bob).deposit(amount, bob.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```
