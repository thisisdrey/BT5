### Title
Unvalidated `git_object_directory` / `git_alternate_object_directories` fields bypass path-traversal checks in Git command environment construction - ([File: internal/git/gitcmd/command_factory.go])

### Summary
The `Repository` protobuf message exposes `git_object_directory` and `git_alternate_object_directories` fields that are attacker-influenceable on any RPC request carrying a `Repository`. [1](#0-0) . When Gitaly spawns a Git subprocess for that repository, these raw fields are passed straight into `alternates.Env()`, which builds `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` via plain `filepath.Join` with **no traversal or scope validation** [2](#0-1) , and this unvalidated path is what actually gets wired into the executed Git process [3](#0-2) .

This is inconsistent with the rest of the codebase: `localrepo.Repo.ObjectDirectoryPath()` performs strict validation (relative-path escape checks, quarantine-directory prefix checks) before trusting a `GitObjectDirectory` value [4](#0-3) , but that validated helper is **not** the code path used when actually configuring the Git process environment for command execution — `command_factory.go` uses the raw, unchecked getters instead.

### Finding Description
Analogous to the reported bug class (a user-supplied `outputToken` that is never checked to belong to the expected "basket" set, letting the caller point the transfer logic at unrelated assets), Gitaly's `Repository.GitAlternateObjectDirectories` field is a user-suppliable pointer to an object store location that is never checked to belong to the target repository/storage before being used to configure Git's object search path in `ExecCommandFactory.newCommand`:

```go
env = append(alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories()), env...)
``` [5](#0-4) 

`alternates.Env` simply does `filepath.Join(repoPath, dir)` for each entry with no call to `storage.ValidateRelativePath` or any containment check [6](#0-5) , unlike the quarantine/object-pool code paths elsewhere in the repo which explicitly guard against this (`storage.ValidateRelativePath`, `ErrRelativePathEscapesRoot`, `ErrAlternateHasAlternate`, `ErrAlternatePointsToSelf`) [7](#0-6) .

The transaction middleware is aware that request-supplied object-directory fields are meant only for internal Rails-loopback quarantine flows, and explicitly rejects them on **mutator** RPCs (`ErrQuarantineConfiguredOnMutator`), but permits them through unchanged on **accessor** (read) RPCs as long as a snapshot-relative-path metadata header is present — the code comment itself acknowledges this is an unresolved gap: *"This property is violated in tests which manually configure the object directory or the alternate object directory... We'll leave this unaddressed for now."* [8](#0-7) 

### Impact Explanation
A crafted read-only RPC (e.g. `FindCommits`, `CatFile`/blob RPCs) that sets `git_alternate_object_directories` to a `../`-traversal path can redirect Git's object search onto a different repository's object store or an arbitrary directory on the same storage, since the join is purely lexical and not confined to the storage root. This can leak objects (blobs, commits, trees) belonging to a repository the caller is not authorized to access, breaking Gitaly's repository object isolation — analogous to "scooping" resources that don't belong to the caller's own scope.

### Likelihood Explanation
Exploitation requires the ability to set the `Repository.git_object_directory`/`git_alternate_object_directories` fields directly on a gRPC request, which in normal GitLab operation is only exercised by Rails during pre-receive access checks. Directly reaching Gitaly's gRPC surface with a custom `Repository` message generally requires a valid Gitaly auth token, which is normally held by internal components (Rails/Workhorse/gitlab-shell), not an anonymous end user. This somewhat limits likelihood versus a fully "ordinary user" attack surface, but the validation gap itself is real and exists specifically in the code path that executes Git (as opposed to the well-guarded `ObjectDirectoryPath()` helper used elsewhere).

### Recommendation
Route `repo.GetGitObjectDirectory()` and `repo.GetGitAlternateObjectDirectories()` through the same validation used by `localrepo.Repo.ObjectDirectoryPath()` (relative-path containment check plus quarantine-prefix check) before constructing the Git process environment in `alternates.Env`/`ExecCommandFactory.newCommand`, rather than trusting the raw proto fields.

### Proof of Concept
Not independently reproduced against a running Gitaly instance (would require gRPC access with a valid auth token); the finding is based on static code-path analysis showing `alternates.Env` performs no containment validation on `GitAlternateObjectDirectories`/`GitObjectDirectory` before they are joined into the Git process environment at [3](#0-2) , in contrast to the validated `ObjectDirectoryPath()` helper at [4](#0-3) .

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
