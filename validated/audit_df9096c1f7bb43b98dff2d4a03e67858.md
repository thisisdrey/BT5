### Title
`simulate_intents` reports a `Transfer` with `NotifyOnTransfer` as fully succeeding while real `execute_intents` refunds it via `mt_resolve_transfer` when the receiver's `mt_on_transfer` panics - ([File: contracts/defuse/core/src/engine/state/cached.rs])

### Summary
`CachedState::notify_on_transfer` is a documented no-op stub because "simulation ... cannot create promises, as it is a view call" [1](#0-0) , whereas the real `Contract::notify_on_transfer` fires a genuine `mt_on_transfer` cross-contract call chained to `mt_resolve_transfer`, which refunds the transferred balance back to the sender if the receiver rejects/panics [2](#0-1) [3](#0-2) . This produces a documented, test-confirmed divergence between the `simulate_intents` report and the final settled state of `execute_intents` for a `Transfer` with `notification: Some(NotifyOnTransfer{..})` whose receiver panics.

### Finding Description
The equality being claimed is: `simulate_intents(payload).report.logs` (and implied resulting balances) == final balances/events produced by `execute_intents(payload)` after all receipts resolve, for a `Transfer` intent carrying `notification: Some(NotifyOnTransfer{...})`.

Trace:
- `Transfer::execute_intent` unconditionally performs `internal_sub_balance(sender)` / `internal_add_balance(receiver_id)` and, only if `notification` is set, calls `engine.state.notify_on_transfer(...)` afterward [4](#0-3) .
- In real execution, `Contract::notify_on_transfer` schedules `notify_and_resolve_transfer`, which fires `mt_on_transfer` on `receiver_id` and, in the same transaction, chains `mt_resolve_transfer` as a `#[private]` callback [5](#0-4) .
- `mt_resolve_transfer` reads the promise result; if the receiver's `mt_on_transfer` call fails/panics, `promise_result_checked_json_with_len` returns `Err`, causing `refund` to default to the full transferred `amounts` [6](#0-5) , and the function moves that full amount from the receiver's internal balance back to the sender's internal balance [7](#0-6) . This all happens within the receipts of the same `execute_intents` transaction, so by the time the transaction is `Final`, the transfer has been fully reversed.
- In simulation, `CachedState::notify_on_transfer` is a no-op that does nothing and cannot schedule any promise, by explicit design comment [1](#0-0) . Consequently `simulate_intents` only ever reports the immediate `Transfer` event/log from `Transfer::execute_intent` — it never simulates a resolve/refund step, since that step doesn't exist on the cached-state code path at all.
- The repo's own test suite explicitly documents and asserts this exact divergence outcome for `execute_intents`: the `receiver_panics` case in `transfer_intent_with_msg_to_receiver_smc` expects `expected_sender_balance: 1000, expected_receiver_balance: 0` (i.e., a full refund) when the receiver stub panics on `mt_on_transfer` [8](#0-7) . There is no corresponding case validating that `simulate_intents`'s report for the same payload also reflects a refund — and by inspection of `CachedState::notify_on_transfer`, it structurally cannot, since it is a synchronous no-op with no promise machinery. The existing `simulate_transfer_intent` test only checks the simple case without `notification`, asserting `report.logs` equals the intent's own event log [9](#0-8) , which does not exercise the refund path.
- None of the listed guards (`MultiPayload::verify`, `verify_intent_nonce`, `TransferMatcher::finalize`, `assert_one_yocto`, `#[private]`, `#[pause]`, access-control guards, checked arithmetic) address this divergence: they all govern intra-batch consistency and authorization, not the semantic gap between the no-op simulation stub and the real async notify/resolve flow.

### Impact Explanation
No party's tokens are actually moved without authorization within the Verifier's own accounting, and the batch nets to zero in both paths considered independently — this is not a Critical-tier balance-invariant break. It is, however, exactly the enumerated High-tier condition: `simulate_intents` reporting an outcome that `execute_intents` does not produce, for a party that settles on that report. A counterparty who inspects a `simulate_intents` result for a signer's `Transfer` payload (e.g., to verify off-chain that a payment will land at a given receiver before releasing their own side of a trade) can be shown a report indicating the transfer succeeded, while the real `execute_intents` call — because the receiver (which can be a contract the signer controls) panics on `mt_on_transfer` — fully refunds the sender. The signer effectively gets their tokens back after having convinced a relying party that the transfer settled. This is repeatable per signed payload/per receiver contract and is not bounded to a single account or token.

### Likelihood Explanation
Preconditions are minimal and fully within the unprivileged attacker's control: deploy any receiver contract implementing `mt_on_transfer` that panics (or returns manipulated values), sign a `Transfer` intent naming that contract as `receiver_id` with a `notification: Some(NotifyOnTransfer{..})`, and present the `simulate_intents` output to a counterparty who uses it as a settlement precondition. No relayer keys, DAO roles, or victim keys are required. The only dependency is a workflow where some off-chain party actually treats `simulate_intents` as authoritative proof of a specific settlement outcome for `Transfer` intents carrying notifications — this is a realistic but not universal usage pattern (e.g., OTC/solver-style flows that pre-check intents before committing counter-value).

### Recommendation
Either (a) make `CachedState`/`SimulateInspector` explicitly reflect that any `Transfer` carrying a `notification` has an unresolved/uncertain outcome (e.g., emit a warning field or a distinct "pending notification, refund possible" marker in `SimulationOutput`, rather than a full-success log), or (b) document prominently in `SimulationOutput`/`simulate_intents` that `NotifyOnTransfer`-bearing transfers are not simulated end-to-end and must not be used by relying parties as proof of final settlement, since the cross-contract `mt_on_transfer`/`mt_resolve_transfer` refund path is unmodeled by `CachedState::notify_on_transfer` (contracts/defuse/core/src/engine/state/cached.rs:321-330).

```rust
    fn mt_resolve_transfer(
        &mut self,
        previous_owner_ids: Vec<AccountId>,
        receiver_id: AccountId,
        token_ids: Vec<TokenId>,
        #[allow(unused_mut)] mut amounts: Vec<U128>,
        approvals: Option<Vec<Option<Vec<ClearedApproval>>>>,
    ) -> Vec<U128> {
        require!(approvals.is_none(), "approvals are not supported");
        require!(
            !token_ids.is_empty()
                && previous_owner_ids.len() == token_ids.len()
                && amounts.len() == token_ids.len(),
            "invalid args"
        );

        let mut refunds = promise_result_checked_json_with_len::<Vec<U128>>(0, amounts.len())
            .ok()
            .and_then(Result::ok)
            .filter(|refund| refund.len() == amounts.len())
            .unwrap_or_else(|| amounts.clone());

        let sender_id = previous_owner_ids.first().cloned().unwrap();

        for ((token_id, previous_owner_id), (amount, refund)) in token_ids
            .iter()
            .map(|token_id| token_id.parse().unwrap_or_else(|e| panic!("{e}")))
            .zip(previous_owner_ids)
            .zip(amounts.iter_mut().zip(&mut refunds))
        {
            require!(
                sender_id == previous_owner_id,
                "approvals are not supported"
            );

            refund.0 = refund.0.min(amount.0);
            let Some(receiver) = self
                .accounts
                .get_mut(&receiver_id)
                // NOTE: refunds from locked accounts are allowed to prevent
                // senders from loss of funds.
                //
                // Receiver's account might have been locked between
                // `mt_transfer_call()` and `mt_resolve_transfer()`, so that
                // outgoing transfers are no longer allowed for this account.
                // But here we distinguish between regular transfers and
                // refunds, despite it would lead to `mt_transfer` event
                // emitted with `old_owner_id` being the locked account.
                //
                // Locked receivers still won't be able to transfer funds in
                // `<receiver_id>::on_mt_transfer()` implementation.
                .map(Lock::as_inner_unchecked_mut)
            else {
                // receiver doesn't have an account, so nowhere to refund from
                return amounts;
            };
            let receiver_balance = receiver.token_balances.amount_for(&token_id);
            // refund maximum what we can
            refund.0 = refund.0.min(receiver_balance);
            if refund.0 == 0 {
                // noting to refund
                continue;
            }

            // withdraw refund
            receiver
                .token_balances
                .sub(token_id.clone(), refund.0)
                .unwrap();
            // deposit refund
            self.accounts
                .get_or_create(previous_owner_id)
                // refunds are allowed for locked accounts
                .as_inner_unchecked_mut()
                .token_balances
                .add(token_id, refund.0)
                .unwrap();

            // update as used amount in-place
            amount.0 -= refund.0;
        }
```

```rust
    pub(crate) fn notify_and_resolve_transfer(
        sender_id: AccountId,
        receiver_id: AccountId,
        token_ids: Vec<defuse_nep245::TokenId>,
        amounts: Vec<U128>,
        notify: NotifyOnTransfer,
    ) -> PromiseOrValue<Vec<U128>> {
        let previous_owner_ids = vec![sender_id.clone(); token_ids.len()];

        Self::notify_on_transfer(
            sender_id,
            previous_owner_ids.clone(),
            receiver_id.clone(),
            token_ids.clone(),
            amounts.clone(),
            notify,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(Self::mt_resolve_gas(token_ids.len()))
                // do not distribute remaining gas here (so that all that's left goes to `mt_on_transfer`)
                .with_unused_gas_weight(0)
                .mt_resolve_transfer(previous_owner_ids, receiver_id, token_ids, amounts, None),
        )
        .into()
    }
```
