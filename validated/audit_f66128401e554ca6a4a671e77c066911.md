### Title
Path Traversal via Unsanitized MVCC Manifest Hash/Artifact Paths - (File: internal/git/mvcc/cache.go)

### Summary
The external report describes a caching bug class: consumers of a versioned/cached pointer trusting a stale or attacker-influenceable version identifier without validation, leading to use of the wrong (and potentially unsafe) resource. The analog in this codebase is Gitaly's experimental MVCC cache (`internal/git/mvcc`), which resolves a manifest "version" identifier (`hash`) and artifact paths taken from that manifest, and feeds them directly into `filepath.Join` calls that build on-disk cache paths — without ever validating that `hash` or the artifact path components are safe, non-traversing strings.

### Finding Description
`LocalCache.prepare` accepts an externally supplied manifest `hash` (via `PrepareWithManifest`, explicitly documented as being usable "when the RPC already contains a manifest hash in the metadata," e.g. hook-originated requests) and passes it unmodified into `prepareManifestFile`: [1](#0-0) 

```
manifestFilePath := filepath.Join(m.storagePath, m.repositoryID, mvccCacheDir, "manifests", hash)
```

There is no validation that `hash` is a well-formed content hash (e.g. hex-only, fixed length) before it is used as a path component. A value such as `../../../../etc/passwd` or an absolute path would let `filepath.Join` escape the intended `manifests/` directory of the repository's MVCC cache, causing Gitaly to read/write outside the sanctioned cache tree (`fileExist`, `os.Open`, and `createFileAtomic` all operate on this unsanitized path).

The same pattern repeats for artifact paths sourced from the manifest content itself (`manifest.RefPaths()` / `newManifest.Paths`), which are also joined directly into filesystem paths without sanitization: [2](#0-1) [3](#0-2) 

Because manifests are round-tripped through object storage and the manifest's own `Paths` list is used verbatim to build both read (`prepareArtifacts`) and write (`putNewArtifacts`) file paths under `m.storagePath/m.repositoryID/mvccCacheDir/...`, any component able to influence manifest content or the pinned hash (through the "hook" pin path described in `doc/mvcc_rpc_flow.md`, which explicitly forwards a manifest hash coming from a previous RPC/metadata) can direct file reads/writes to arbitrary filesystem locations relative to the storage root.

This mirrors the root cause of the reported bug class: an externally influenceable "version pointer" (there: cached contract address; here: MVCC manifest hash/artifact path) is consumed by security-relevant logic without adequate validation of freshness *or* well-formedness, and here that gap manifests concretely as unsanitized path construction.

### Impact Explanation
If an attacker can influence the manifest hash used by `PrepareWithManifest` (e.g., via the hook-originated pin path documented in `doc/mvcc_rpc_flow.md`, steps "First, if the context has a Pin{} set, we use the manifest from the pin") or can get a crafted path into a manifest's artifact list that later gets committed to object storage, they can cause Gitaly to read or write files outside the intended per-repository MVCC cache directory — a storage escape. Depending on which side (`prepareManifestFile`/`prepareArtifacts` read path, or `putNewArtifacts` write/upload path) is reachable with attacker-controlled input, this could result in local file disclosure, cross-repository object access (crossing storage/repository boundaries within `m.storagePath`), or corruption of unrelated files on the Gitaly storage.

### Likelihood Explanation
This code is explicitly labeled proof-of-concept/"vibe coding" in `doc/mvcc_rpc_flow.md`, and none of the reviewed code paths (`prepare`, `prepareManifestFile`, `prepareArtifacts`, `putNewArtifacts`) perform validation of `hash` or artifact path strings before using them in `filepath.Join`. The MVCC backend is gated behind `Git.S3BackendEnabled`, so likelihood depends on that feature being enabled, but where enabled, the reachable surface (mutator RPCs going through `BeginMVCCWrite` / hook-driven pinned manifests) is part of the normal push/write request flow, not a privileged-only interface.

### Recommendation
Validate `hash` strictly (e.g., enforce it matches the expected content-hash format such as fixed-length hex) before using it in any `filepath.Join` call in `internal/git/mvcc/cache.go`. Similarly validate/normalize every artifact path returned by `Manifest.RefPaths()`/`Manifest.Paths` (reject `..`, absolute paths, and path separators outside the expected shape) before joining them onto `m.storagePath`/`m.repositoryID`. Consider resolving the final path and confirming with `filepath.Clean` + prefix-check that it remains within the expected cache root, consistent with how other Gitaly storage-path resolution code guards against traversal.

### Proof of Concept
Conceptual PoC (concrete exploitation depends on confirming how the pinned manifest hash is threaded from an actual gRPC hook/metadata field into `PrepareWithManifest`, which was not fully traced within the available index):
1. Enable the MVCC/S3 backend (`Git.S3BackendEnabled`).
2. Trigger a write RPC path where the manifest hash is sourced from request-controlled metadata used by the hook "pin" mechanism described in `doc/mvcc_rpc_flow.md`.
3. Supply a hash value such as `../../../../tmp/evil` instead of a legitimate content hash.
4. Observe that `prepareManifestFile` builds `manifestFilePath := filepath.Join(m.storagePath, m.repositoryID, mvccCacheDir, "manifests", hash)` [4](#0-3)  and reads/writes outside the intended `manifests/` directory.

Note: full confirmation of the exact request field/metadata key that populates the pinned manifest hash (and whether it is authenticated/trusted-only) requires reading the pin/interceptor code, which was not located within the indexed portion of the repository during this investigation — this is a gap that should be verified in a full session before treating this as fully proven end-to-end.
