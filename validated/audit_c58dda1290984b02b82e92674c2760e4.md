### Title
Unauthenticated Attachment/BNS Content-Hash Spoofing via Unvalidated `extend_with_attachments` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts any successfully-decoded `Attachment` from a peer's `GET /v2/attachments/{content_hash}` response into `self.attachments` without ever checking that `Attachment::hash()` matches the requested `AttachmentRequest.content_hash`. `decode_atlas_get_attachment` merely deserializes JSON with no hash verification. A malicious peer answering an attachment request can serve arbitrary bytes and have them accepted as the attachment for that hash.

### Finding Description
The claimed equality — `Attachment::hash(response.attachment) == request.content_hash` — is never checked. `decode_atlas_get_attachment` at [3](#0-2)  only parses JSON into a `GetAttachmentResponse`, with no hash comparison performed there or in the caller. In `extend_with_attachments`, the decoded response is inserted directly:
```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
``` [2](#0-1) 

The request itself is built with `content_hash: content_hash.clone()` from the local inventory, and `make_request_type` builds `GET /v2/attachments/{content_hash}` [4](#0-3) , but nothing on the requester side validates the returned bytes against that hash before they're accepted into the batch context's `attachments` set.

An attacker running a peer that legitimately serves attachment inventory (or is asked for a hash it claims to have) can respond to any `AttachmentRequest` with a `GetAttachmentResponse{ attachment: Attachment{ content: <anything> } }` whose hash does not match the requested `content_hash`. That forged `Attachment` is stored in the state-machine's `attachments` set and (per the batch's subsequent lookup/matching logic and `AtlasDB::insert_instantiated_attachment`) can propagate to the local `AtlasDB` and be re-served to other peers under the wrong hash, corrupting the BNS attachment resolution for that content hash across the network.

I was not able to fully trace, within the available context, the exact downstream code that takes `context.attachments` (from `Done(context)`) and correlates entries by `content_hash` before calling `AtlasDB::insert_instantiated_attachment` — it's plausible that a downstream step does a hash re-check (e.g., in `AttachmentsDownloader::run` matching resolved attachments against `AttachmentInstance.content_hash`) that could reject a mismatched hash before DB insertion. This downstream step should be examined before treating the vulnerability as fully proven end-to-end; I could not view that specific matching code within my remaining budget.

### Impact Explanation
If unchecked, a single malicious peer can pollute the batch's resolved-attachment set with content that doesn't match the hash committed to by the BNS name's Stacks transaction, potentially propagating this mismatch to `AtlasDB` and to other nodes that sync attachments from this node — a High-severity "attachment/BNS mismatch" as scoped. However, this hinges on whether the downstream consumer (which I could not fully verify) performs its own hash check on `response.attachment.hash()` vs. the instance's `content_hash` before persisting via `insert_instantiated_attachment`.

### Likelihood Explanation
Low cost to the attacker: run any HTTP peer, appear in another node's peer/inventory list, and answer attachment-content requests with fabricated bytes. No secrets, signatures or privileged roles required — this is a plain unauthenticated GET endpoint. [5](#0-4) 

### Recommendation
In `extend_with_attachments` (or in `decode_atlas_get_attachment`), compute `response.attachment.hash()` and compare it to `request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and do not store the attachment.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/download.rs` (or a new test module) that:
1. Constructs an `AttachmentRequest` with a fixed `content_hash` (e.g., `Hash160::from_data(b"expected")`).
2. Builds a `BatchedRequestsResult` whose `succeeded` map contains that request paired with a crafted `StacksHttpResponse` encoding `GetAttachmentResponse { attachment: Attachment { content: b"malicious".to_vec() } }` (whose `.hash()` differs from `content_hash`).
3. Calls `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
4. Asserts that `context.attachments` contains the malicious `Attachment`, and that `context.attachments.iter().find(|a| a.hash() == content_hash)` is `None` — demonstrating that mismatched content is accepted with no rejection.

Given the uncertainty about whether a downstream hash check exists before `AtlasDB::insert_instantiated_attachment`, I recommend a Devin session trace `AttachmentsDownloader::run`'s handling of `Done(context)` and the resolved-attachments matching logic (`resolved_attachments` in `stackslib/src/net/atlas/download.rs` lines ~93-150) to confirm whether that step re-validates hashes, which would determine whether this is fully exploitable end-to-end or only an internal-state issue mitigated later.
