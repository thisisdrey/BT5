### Title
Unchecked slice length causes out-of-range panic in `AlternateObjectDirectories` - ([File: internal/git/dirs.go])

### Summary
`AlternateObjectDirectories` in `internal/git/dirs.go` blindly slices the result of `ObjectDirectories` with `dirs[1:]` without ever checking that the slice is non-empty. Just like the reported `merkleProof` bug (an externally-influenced array whose length is never validated before it is used), this Gitaly helper can be handed a zero-length slice and will then perform an invalid slice operation, panicking the caller.

### Finding Description
`ObjectDirectories` resolves an object directory (and, recursively, all alternates) starting from `repoPath/objects`: [1](#0-0) 

The recursive helper `altObjectDirs` explicitly returns an **empty slice** (`nil, nil`) whenever the target object directory does not exist on disk: [2](#0-1) 

`AlternateObjectDirectories` then unconditionally executes `dirs[1:]` on whatever `ObjectDirectories` returned, with no `len(dirs) > 0` guard — exactly the missing-length-check pattern described in the report: [3](#0-2) 

In Go, slicing a nil/zero-length slice with `[1:]` panics with `"slice bounds out of range [1:0]"`. Because `objDir` is derived from `filepath.Join(repoPath, "objects")` (`ObjectDirectories`, line 27) and `repoPath` for a `Repository` message can carry an attacker/-caller-influenced `GitObjectDirectory` (e.g. quarantine object directory paths threaded through RPC fields and snapshot/quarantine handling, as documented in `doc/object_quarantine.md`), any situation where that resolved directory is missing from disk (deleted, not-yet-created quarantine dir, stale/incorrect path in a crafted request) causes `ObjectDirectories` to return an empty slice, and `AlternateObjectDirectories` to panic.

The function is consumed by repository snapshotting code (`internal/git/localrepo/snapshot.go` calls `git.AlternateObjectDirectories`), which runs as part of building repository snapshots for transaction/WAL processing — a path reachable from ordinary RPCs that operate on a repository whose object directory has been quarantined or otherwise redirected.

### Impact Explanation
A panic in an RPC-handling goroutine causes that specific request to fail catastrophically (rather than with a clean gRPC error), and depending on whether panic-recovery middleware is present in that particular code path, it can propagate up and destabilize the serving goroutine/connection. At minimum this is an availability bug (DoS of the RPC handler) triggerable by a caller who can arrange for the resolved object directory not to exist on disk (e.g., via inconsistent or racy quarantine/snapshot state, or a malformed `GitObjectDirectory` field), which is a realistic no-privilege-escalation but denial-of-service condition matching "DoS of a handler" in the accepted-impact list.

### Likelihood Explanation
Reaching the empty-slice branch of `altObjectDirs` merely requires the object directory implied by the resolved repository path not to exist on disk at the moment this function is called — a condition that can arise from quarantine directories that are removed/rewritten concurrently, or requests referencing an object directory that has not yet been created. No privileged access or cryptographic bypass is required, only that the disk state and requested repository object directory diverge at the time of the call.

### Recommendation
Add an explicit length check in `AlternateObjectDirectories` before slicing:
```go
if len(dirs) == 0 {
    return nil, nil
}
return dirs[1:], nil
```
This mirrors the report's fix recommendation of validating array/slice length before consuming it, preventing the panic while preserving the existing "no alternates" semantics.

### Proof of Concept
1. Call `git.ObjectDirectories`/`git.AlternateObjectDirectories` (directly, or indirectly via `internal/git/localrepo/snapshot.go`) with a `repoPath` whose `objects` subdirectory does not exist (e.g., a repository reference pointing at a quarantine directory that has already been cleaned up, or any resolved object directory that is momentarily absent from disk).
2. `altObjectDirs` hits `os.IsNotExist(err)` and returns `nil, nil`.
3. `AlternateObjectDirectories` executes `dirs[1:]` on the nil slice, which panics with `runtime error: slice bounds out of range [1:0]`, crashing/aborting the calling goroutine.

Note: I was not able to fully trace every RPC/handler pathway that can supply a not-yet-existing object directory to `AlternateObjectDirectories` at request time (only the single caller in `internal/git/localrepo/snapshot.go` was located in the index), so the exact end-to-end attacker-triggerable request sequence should be confirmed with a live reproduction/test before treating this as fully proven in production.
