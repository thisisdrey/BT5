### Title
Malformed `ft_transfer_call` return causes full refund credit despite completed on-chain transfer - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`ft_resolve_withdraw` treats any non-`U128`-parseable success result from `token.ft_transfer_call` as `used = 0`, issuing a full refund of `amount` back into the withdrawer's Verifier balance even though the `token` contract's own promise executed successfully (`Ok(..)` branch) and may have actually moved the tokens on-chain. Because `token` is a caller-chosen `AccountId` on which the Verifier has no enforced standards-compliance, an attacker who deploys their own `token` contract and withdraws to it can make `ft_transfer_call` genuinely transfer `amount` on-chain while returning a non-`U128` payload, causing the Verifier to credit `amount` back to `sender_id`'s internal `token_balances` without the corresponding custody.

### Finding Description
The broken binding: `used` (the value fed into the refund calculation) must equal the real amount of `token` moved out of the Verifier's on-chain balance by the just-settled `ft_transfer_call` promise. In `ft_resolve_withdraw`: [1](#0-0) 

when `promise_result_checked_json::<U128>(0)` returns `Ok(Err(_deserialize_err))` (i.e., the promise succeeded but its return bytes don't parse as `U128`), `used` is hard-coded to `0`, and the full `amount` is refunded via `self.deposit(sender_id, ..., REFUND_MEMO)`.

The attacker's exact flow:
1. Attacker deploys `token` (their own FT contract) and deposits `amount` of it into the Verifier, then calls `ft_withdraw(token, receiver_id, amount, ...)` as `sender_id` (satisfied by `ensure_auth_predecessor_id()` in `contracts/defuse/src/contract/tokens/nep141/withdraw.rs:36-37`, which only requires the caller to be their own account).
2. `internal_ft_withdraw` first debits `sender_id`'s Verifier balance via `withdraw()`, then schedules `do_ft_withdraw` → `token.ft_transfer_call(receiver_id, amount, ...)` → `ft_resolve_withdraw`.
3. Attacker's `token::ft_transfer_call` implementation genuinely transfers `amount` on-chain to `receiver_id` (which can be attacker-controlled) but returns malformed/non-`U128` JSON as its promise result.
4. `ft_resolve_withdraw` hits `Ok(Err(_deserialize_err)) => 0`, computes `refund = amount`, and calls `self.deposit(sender_id, [(TokenId(token), amount)], REFUND_MEMO)`, restoring `sender_id`'s Verifier balance to its pre-withdrawal value.

Existing guards (`assert_one_yocto`, `#[private]`, `#[pause]`, `auth_by_predecessor_id`) do not prevent this because they only gate who may initiate the withdrawal, not whether `token`'s promise-result payload is trustworthy. The Verifier has no independent means to verify `used` against the real on-chain transfer amount; it fully trusts the byte content of `token`'s callback result.

### Impact Explanation
This produces a Verifier-internal-ledger credit for `token` (a `TokenId(Nep141TokenId(token))`) that is not backed by any Verifier-held custody of `token`, since the real balance was moved out on-chain in step 3. This matches the Critical category "a refund or resolver credit that does not match what failed to settle" / "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." However, because `token` is attacker-deployed and worthless outside the attacker's own control, the only balance affected is the attacker's own `TokenId(token)` entry; no other account's funds are put at risk unless the attacker subsequently uses the phantom balance in a swap with a counterparty who is unaware `token` is non-compliant. This is the same root cause as attacker-controlled token double-crediting (self-deployed token intentionally misreporting `used`), just reached via the deserialize-failure branch rather than the "reported-numeric-zero" branch.

### Likelihood Explanation
Preconditions: attacker must deploy and control `token`, and be `sender_id`/withdrawer of their own funds. No role, relayer key, or victim key is needed. Attacker cost is limited to deploying a contract and depositing/withdrawing their own tokens; it is fully repeatable per attacker-created token but does not by itself extract real value from other users or from the Verifier's custody of any *other* token.

### Recommendation
Treat any non-parseable/malformed successful result from `ft_transfer_call` identically to the "insufficient gas" case (i.e., do not assume `used = 0`) only when it cannot be distinguished from a legitimate partial-transfer response, or alternatively require the resolver to independently verify the token's own balance delta (e.g., via `ft_balance_of` before/after) rather than trusting the returned JSON blob, for any code path that credits back funds.

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
