### Title
CreateRelayRequest/Response `RelayFromAddr` is never checked against the authenticated sender's vpn address, allowing relay-state spoofing - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` build relay state keyed by a peer address (`from`/`RelayFromAddr`) that is taken directly from the attacker-controlled `NebulaControl` message, without ever verifying that it matches the authenticated sender's own VPN address (`h.vpnAddrs`). This is the same bug class as the reported Astaria issue: a value that should be checked against a "registered" identity (there: `s.vaults[c.lienRequest.strategy.vault]`; here: the sender's authenticated `vpnAddrs` on `HostInfo h`) is used unchecked to establish trusted state.

### Finding Description
`handleCreateRelayRequest` receives `h *HostInfo`, the already-authenticated (post-handshake) peer that sent the encrypted Control packet, and `m *NebulaControl`, the message payload itself: [1](#0-0) 

`from` is derived purely from `m.RelayFromAddr`/`m.OldRelayFromAddr`, fields fully controlled by the sender inside the message body: [2](#0-1) 

The only self-referential checks performed are "is `from` == me" and "is `target` == me": [3](#0-2) 

Nowhere is `from` compared against `h.vpnAddrs` (the address(es) actually verified during the handshake for this authenticated tunnel `h`). When the target is this node, the code proceeds to install relay state keyed by the attacker-chosen `from` value on the authenticated hostinfo `h`: [4](#0-3) 

`AddRelay` records `PeerAddr: from` (i.e., the unverified claimed address) tied to `h`'s relay state: [5](#0-4) 

The same unchecked pattern repeats in the "I am asked to forward" branch, where a `ForwardingType` relay is installed keyed by the unverified `from` on a *different* hostinfo (`peer`, the resolved target), again derived from the untrusted message: [6](#0-5) 

Because `from` is only ever validated for the trivial "is it literally my own address" case, a fully-handshaked (but otherwise unprivileged) peer `h` can claim to be *any* other VPN address in the network when requesting a relay. This is functionally identical to the reported pattern: a value that determines which trusted entity subsequent logic acts on/for (`c.lienRequest.strategy.vault` there, `RelayFromAddr`/`from` here) is never checked against the registry of legitimately known identities (`s.vaults` there, `h.vpnAddrs` here) before being used to mutate protected state (`AddRelay`/`relayState`).

### Impact Explanation
An authenticated Nebula peer (any node holding a valid certificate signed by the network's CA — i.e., "no CA-signed certificate" attacker is out of scope, but any legitimate low-privilege node in the mesh qualifies) can spoof `RelayFromAddr` to claim to be an arbitrary victim VPN address when requesting to use another node as a relay. This poisons that relay's `relayState`/`hostMap.Relays` bookkeping under the victim's claimed identity:
- Remote state poisoning: subsequent legitimate relay lookups for the victim's real vpn address (`QueryRelayForByIp`) on this relay host can be captured by the attacker's bogus entry, causing traffic intended for/through the victim's relay path to be associated with the attacker's tunnel instead.
- This can be leveraged for a denial-of-service against the victim's relay-based connectivity (the victim's real relay request will collide with/overwrite or be confused with the attacker's forged entry), and potentially traffic misdirection since the relay's forwarding decisions are keyed on the (spoofable) claimed address rather than the cryptographically verified peer identity.

This does not itself decrypt or forge Nebula-encrypted payloads, but it does allow an authenticated peer to corrupt relay routing/trust state for identities it does not control, which matches the "remote state poisoning" impact bucket.

### Likelihood Explanation
Likelihood is fairly high for any deployment using `relay.am_relay`/`relay.use_relays` (the default is `use_relays: true`), since the attack only requires being one authenticated member of the mesh — no lighthouse/relay compromise or CA key is needed. The attacker only needs to send a crafted `NebulaControl` `CreateRelayRequest` with a `RelayFromAddr` set to a victim's known VPN address.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse` where applicable), verify that the claimed `from` (`RelayFromAddr`/`OldRelayFromAddr`) is contained in `h.vpnAddrs` (the certificate-verified addresses for the authenticated sender `h`) before using it to key any `AddRelay`/`relayState` mutation. If `from` does not match one of `h.vpnAddrs`, drop the message and log it the same way the existing nil-address validation block does in `HandleControlMsg`.

### Proof of Concept
1. Stand up three nodes on the same Nebula CA: `Relay` (with `relay.am_relay: true`), `Victim`, and `Attacker`, where `Attacker` has a normal, validly-signed certificate for `10.0.0.66` and completes a normal handshake with `Relay`.
2. `Attacker` sends `Relay` a `Control` packet (`header.Control`) containing a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: <Victim's real vpn addr>, RelayToAddr: <Relay's own vpn addr>, InitiatorRelayIndex: <attacker-chosen>}`.
3. `handleCreateRelayRequest` sees `target == me`, looks up `h.relayState.QueryRelayForByIp(from)` where `from == Victim`'s address, finds none, and calls `AddRelay(rm.l, h, f.hostMap, Victim, &InitiatorRelayIndex, TerminalType, Established)` — establishing relay state on `Relay` claiming `Attacker`'s tunnel (`h`) is the terminal endpoint for `Victim`'s VPN address, despite `Attacker` never proving control of `Victim`'s identity.
4. Any later legitimate relay traffic that other nodes route to `Relay` intending to reach `Victim` via this relay path is now confused with/collides with the attacker-controlled relay entry, since `h.vpnAddrs` was never checked against `from`.

	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
