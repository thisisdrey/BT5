## Title
Missing domain separation in StackerDB chunk signatures allows cross-contract chunk replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` (and therefore `StackerDBChunkData::sign`/`verify`) only commits to `slot_id`, `slot_version`, and the chunk's `data_hash`. It never binds the signature to the `QualifiedContractIdentifier` (StackerDB contract/lane) the chunk is intended for. This is structurally the same class of bug as the reported EIP-155 issue: the signed payload omits a domain/context identifier (there, `chainId`; here, the contract ID), so a signature valid in one context is also valid in a different context that the signer never intended to authorize. [1](#0-0) 

### Finding Description
`auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 

`SlotMetadata::verify` recovers the public key from this digest and compares its hash against the expected `principal`, again with no contract/lane context: [2](#0-1) 

The actual "which StackerDB / which slot owner" binding is supplied out-of-band by the caller: `validate_received_chunk` (and `try_replace_chunk`) look up the expected signer address via `get_slot_signer(smart_contract_id, data.slot_id)` and then call `slot_metadata.verify(&addr)` — the contract identity is never part of what was actually signed: [3](#0-2) [4](#0-3) 

Because many different StackerDB contracts/lanes exist concurrently for the same reward cycle (e.g. per-message-type "signer" lanes such as block-response, transactions, state-machine-update, distinguished only by `message_id`/slot-index mapping in `get_signers_db_signer_set_message_id`), and because slot ownership (which `StacksAddress`/signer owns slot `N`) is frequently the *same signer set ordering* reused across these lanes, a chunk `(slot_id, slot_version, data_hash, sig)` that a signer legitimately produced and posted to contract A can be replayed verbatim to contract B: if the address that owns `slot_id` in contract B happens to be the same signer, `verify()` will succeed because the digest never encoded which contract it was meant for. The type-byte / `payload_kind` check in `libsigner/src/events.rs` (`try_from` for `StackerDBChunksEvent`) is a post-hoc consumer-side sanity check that filters at the *application decode* layer — it does not prevent the **signature verification and on-disk storage** of the mis-routed chunk by `try_replace_chunk`/`validate_received_chunk`, so a forged/cross-context chunk can still be stored as this slot's canonical data and gossiped further before any consumer parses/rejects it. [5](#0-4) 

The unit tests for `SlotMetadata`/`StackerDBChunkData` sign/verify only assert against `slot_id`, `slot_version`, and `data_hash` mutation — there is no test asserting that a signature bound to one contract is rejected when replayed against a different contract, confirming that contract-binding was never part of the design: [6](#0-5) 

### Impact Explanation
An unprivileged network participant who can observe (via gossip or by direct RPC `GET`) a validly-signed chunk from contract A can repost/relay it as a chunk destined for contract B's `/v2/stackerdb/{contract}/chunks` endpoint or via `StackerDBPushChunk`/`StackerDBChunkInv` gossip, as long as:
1. the target slot in contract B is owned by the same signer address as in contract A (common across the per-message-type signer lanes for a given reward cycle), and
2. the replayed `slot_version` is >= the current version recorded for that slot in contract B.

If successful, this results in **unauthorized data being written into a StackerDB replica the signer never intended to write to**, potentially overwriting/confusing block-response, transaction, or state-machine-update lanes with stale/foreign data, and this forged-but-signature-"valid" chunk will be propagated network-wide through normal StackerDB gossip (`handle_unsolicited_StackerDBPushChunk`), since gossip relay logic trusts `validate_received_chunk`'s signature check as sufficient proof of authenticity. [7](#0-6) 

This matches the "network-wide propagation of forged data" / "unauthenticated write to StackerDB" impact category, though the practical blast radius depends on whether slot ownership actually overlaps across lanes for a given deployment, and whether a stale/replayed message is actually acted upon by downstream consumers (the type-byte filter in `events.rs` mitigates some but not all such confusion, since it only filters at read time, not at write time).

### Likelihood Explanation
Likelihood is **moderate**: it requires (a) knowledge of a validly-signed chunk (trivially obtainable, since chunks are broadcast/queryable by any peer), and (b) the target slot in a different contract being owned by the same signing address, which is plausible given that Nakamoto signer-lane contracts reuse the same signer ordering/index across message types within a reward cycle. No secret key, admin role, or node-specific privilege is required — only the ability to relay an HTTP POST or a gossip StackerDB chunk message to a node, which is explicitly in-scope per the rules (StackerDB chunk stored without contract-bound signature).

### Recommendation
Include the `QualifiedContractIdentifier` (and ideally an epoch/reward-cycle identifier) inside `SlotMetadata::auth_digest()` so that the signed digest binds `(contract_id, slot_id, slot_version, data_hash)` rather than only `(slot_id, slot_version, data_hash)`. Update `sign`/`verify`/`recover_pk` call sites (`StackerDBChunkData`, `try_replace_chunk`, `validate_received_chunk`) to pass the contract ID into the digest computation, and bump the StackerDB chunk wire format/version so old and new signers can be distinguished during a transition.

### Proof of Concept
1. Configure two StackerDB contracts/lanes, A and B, in which the same signer address `S` owns slot `N` in both (realistic for Nakamoto signer message lanes sharing a signer-set ordering across message types within a reward cycle).
2. Signer `S` signs and posts a legitimate chunk `C = (slot_id=N, slot_version=V, data, sig)` to contract A via `put_chunk`, which internally calls `StackerDBChunkData::sign` — the produced digest only covers `(N, V, hash(data))` per `auth_digest()`. [1](#0-0) 
3. An unprivileged network peer captures `C` (via RPC `GET /v2/stackerdb/A/chunks` or gossip) and reposts the identical `(slot_id, slot_version, sig, data)` tuple to contract B's endpoint (`POST /v2/stackerdb/B/chunks`) or as a `StackerDBPushChunk` gossip message tagged with contract B's ID.
4. The receiving node calls `validate_received_chunk`/`try_replace_chunk` for contract B, looks up `get_slot_signer(B, N) == S`, and calls `slot_metadata.verify(&S)`, which succeeds because `auth_digest()` is identical to what `S` signed for contract A. [3](#0-2) 
5. The foreign chunk is accepted and stored into contract B's slot `N`, and is subsequently gossiped onward to other peers as if it were a legitimate chunk for contract B.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

#[test]
fn test_stackerdb_slot_metadata_sign_verify() {
    let pk = StacksPrivateKey::random();
    let addr = StacksAddress::from_public_keys(
        C32_ADDRESS_VERSION_MAINNET_SINGLESIG,
        &AddressHashMode::SerializeP2PKH,
        1,
        &vec![StacksPublicKey::from_private(&pk)],
    )
    .unwrap();
    let bad_addr = StacksAddress::new(0x01, Hash160([0x01; 20])).unwrap();

    let chunk_data = StackerDBChunkData {
        slot_id: 0,
        slot_version: 1,
        sig: MessageSignature::empty(),
        data: vec![0x1; 128],
    };

    let mut slot_metadata = chunk_data.get_slot_metadata();
    slot_metadata.sign(&pk).unwrap();

    assert!(slot_metadata.verify(&addr).unwrap());

    // succeeds with high-S signature (that's not necessarily good, but
    // since this has always worked, it can't just stop)
    slot_metadata.signature = slot_metadata.signature.with_negated_s();
    assert!(slot_metadata.verify(&addr).unwrap());

    // fails with wrong address
    assert!(!slot_metadata.verify(&bad_addr).unwrap());

    // fails with corrupted data
    let mut bad_slot_metadata = chunk_data.get_slot_metadata();
    bad_slot_metadata.sign(&pk).unwrap();
    bad_slot_metadata.slot_id += 1;
    assert!(!bad_slot_metadata.verify(&addr).unwrap());

    let mut bad_slot_metadata = chunk_data.get_slot_metadata();
    bad_slot_metadata.sign(&pk).unwrap();
    bad_slot_metadata.slot_version += 1;
    assert!(!bad_slot_metadata.verify(&addr).unwrap());

    let mut bad_slot_metadata = chunk_data.get_slot_metadata();
    bad_slot_metadata.sign(&pk).unwrap();
    bad_slot_metadata.data_hash = Sha512Trunc256Sum([0x20; 32]);
    assert!(!bad_slot_metadata.verify(&addr).unwrap());
}
