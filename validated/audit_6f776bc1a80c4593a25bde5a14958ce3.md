### Title
QoS stream-throttling bypass via check-then-increment race between `throttle_stream` and `on_stream_accepted` - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` itself is safe: its read-then-upgrade-to-write-lock pattern rechecks the condition under the exclusive write lock, so at most one task per `STREAM_THROTTLING_INTERVAL` can actually reset `stream_count`. The real race is elsewhere: `throttle_stream` reads `stream_count` non-atomically and decides whether to throttle, but the actual increment happens later and separately in `SwQos::on_stream_accepted`, so many concurrently-processed streams on the same connection can all observe a stale, sub-limit count and all pass the throttle check before any of them increments the counter.

### Finding Description
`reset_throttling_params_if_needed` [1](#0-0)  uses a correct double-checked-locking pattern: the write-lock branch recomputes `duration_since(*last_throttling_instant)` against the *current* value after acquiring the exclusive `RwLock` write guard, so a second task that also entered the `if` branch will see the just-updated instant and skip the reset. This means the "more-frequent-than-intended reset" mechanism described in the question does not exist as stated.

However, `throttle_stream` [2](#0-1)  only *reads* `stream_counter.stream_count` with `Ordering::Relaxed` to decide whether to sleep; it never atomically increments it as part of the admission decision. The actual increment happens in `SwQos::on_stream_accepted` [3](#0-2) , which is called from `on_new_stream`'s caller path after `on_new_stream` (which invokes `throttle_stream`) completes [4](#0-3) . Because these are two independent atomic operations on the same `AtomicU64` performed at different points in the per-stream handling flow, and QUIC permits many uni-directional streams to be accepted/processed concurrently per connection (gated only by `max_concurrent_uni_streams`, up to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128` or `QUIC_MAX_STAKED_CONCURRENT_STREAMS = 512`) [5](#0-4) , an attacker who opens a burst of concurrent streams on one connection can have all of them evaluate `throttle_stream` against the same (not-yet-incremented) `stream_count`, all pass the check, and all be admitted in the same throttling window — exceeding `max_streams_per_throttling_interval` by up to the concurrent-stream limit.

### Impact Explanation
This is a QoS-evasion bug: an unstaked/staked attacker can push substantially more streams (i.e., more transaction payloads) into sigverify/scheduling ingestion per `STREAM_THROTTLING_INTERVAL` than the configured `max_streams_per_throttling_interval` allows, by opening bursts of concurrent streams on a single connection instead of pacing them. This increases unthrottled CPU/ingress load beyond the intended QoS cap, but is bounded by the connection's `max_concurrent_uni_streams` cap, not unbounded — so it is a rate-limit-evasion issue rather than an unbounded-memory/crash issue.

### Likelihood Explanation
Fully reachable by an unprivileged remote client: it only requires opening one QUIC connection to the TPU port and issuing many uni-streams in parallel (well within normal QUIC client capability, and within the server's advertised `max_concurrent_uni_streams`). No stake, gossip, or validator control is needed, and the race is trivially reproducible under load because Tokio task scheduling routinely interleaves such reads/increments.

### Recommendation
Make admission atomic: perform the check-and-increment as a single atomic operation (e.g. `fetch_add(1)` first and compare the *previous* value against `max_streams_per_throttling_interval`, refunding/decrementing if over the limit, or use `compare_exchange`/`fetch_update` in a loop) inside `throttle_stream`/`ConnectionStreamCounter`, rather than reading in `throttle_stream` and incrementing later in `on_stream_accepted`.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test)
#[tokio::test]
async fn test_concurrent_streams_can_exceed_cap() {
    use std::sync::atomic::Ordering;
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_per_interval = 10u64;
    let mut handles = vec![];
    // Simulate N concurrent stream-handler tasks racing the same connection.
    for _ in 0..50 {
        let counter = counter.clone();
        handles.push(tokio::spawn(async move {
            // mirror throttle_stream's read-only check
            counter.reset_throttling_params_if_needed();
            let count = counter.stream_count.load(Ordering::Relaxed);
            let admitted = count < max_per_interval;
            // mirror on_stream_accepted's later, separate increment
            tokio::task::yield_now().await;
            counter.stream_count.fetch_add(1, Ordering::Relaxed);
            admitted
        }));
    }
    let mut admitted_count = 0;
    for h in handles {
        if h.await.unwrap() {
            admitted_count += 1;
        }
    }
    // Expected (if throttling worked correctly): admitted_count <= max_per_interval
    assert!(admitted_count > max_per_interval as usize, "race allowed exceeding cap");
}
```
Expected result: `admitted_count` exceeds `max_per_interval`, demonstrating that concurrent stream admission bypasses the intended per-interval cap due to the non-atomic check-then-increment pattern.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }

        }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
