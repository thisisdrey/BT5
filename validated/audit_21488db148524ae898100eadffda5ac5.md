### Title
Unauthenticated `RecvError` packet allows blind off-path teardown of established tunnels - (File: outside.go)

### Summary
The `RecvError` message type is processed entirely outside of any cryptographic authentication: it is dispatched straight from `readOutsidePackets` before hostinfo/certificate lookup or Noise decryption, and its only "authenticity" check is that the observed UDP source address matches the peer's currently known remote address. Since UDP source addresses are trivially spoofable and `RemoteIndex` travels in cleartext in every packet header, an attacker holding no CA-signed certificate can forge a `RecvError` packet that causes Nebula to tear down a legitimate, already-established tunnel — a remote state poisoning / DoS analogous to the reported ETH-transfer DoS, where an unauthenticated, unexpected input (there: leftover ETH balance; here: a forged control packet) triggers an unconditional state-destroying action that a downstream party has no way to reject or verify.

### Finding Description
`readOutsidePackets` parses the header and, for `header.RecvError`, immediately calls `f.handleRecvError(via.UdpAddr, h)` before any hostinfo lookup, certificate validation, or Noise/AEAD decryption is performed: [1](#0-0) 

`handleRecvError` then only performs a config gate and an address-equality check against the currently known remote of the tunnel, then unconditionally tears the tunnel down: [2](#0-1) 

The only "proof" that the sender is the legitimate peer is that the *source IP:port of the received UDP packet* equals `hostinfo.GetRemote()`. This is not a cryptographic authentication check — it relies on the underlying UDP transport's source address, which is not authenticated by Nebula and can be spoofed by any attacker who can inject packets with an arbitrary source address (a classic blind UDP spoofing scenario, especially viable because Nebula never sends a reply that the spoofer would need to receive — `sendRecvError`/`handleRecvError` are pure one-way triggers).

Additionally, the `RemoteIndex` needed to target a specific tunnel is not a secret: it is carried in cleartext in the Nebula packet header (`h.RemoteIndex`) of every packet exchanged between the two peers, including handshake and data packets, and can be observed by anyone who can see the traffic on the wire (or who was previously a peer/relay on the path). This is the same header field validated in `HandleIncoming`/`ProcessPacket` for handshake messages, underscoring that header fields including indices are not secret: [3](#0-2) 

Once a forged `RecvError` packet passes the address check, `handleRecvError` calls `f.closeTunnel(hostinfo)` and deletes the pending hostmap entry, unconditionally destroying legitimate tunnel state: [4](#0-3) 

This mirrors the ETH-DoS bug class: a downstream action (`refundETH`/tunnel teardown) is triggered by conditions an attacker can engineer (residual ETH balance / a spoofed cleartext control packet) without any authorization check tied to the real, cryptographically-verified counterparty, and the victim contract/tunnel has no way to distinguish or reject the unwanted trigger.

### Impact Explanation
A successful forgery causes:
- Immediate teardown of the victim's live tunnel to a peer (`closeTunnel`), forcing renegotiation and interrupting all in-flight traffic on that overlay link.
- Deletion from the pending handshake index map (`hm.handshakeManager.DeleteHostInfo(hostinfo)`), amplifying disruption during reconnection attempts.
- Because the trigger is a single unauthenticated UDP datagram with a guessable/observable index and a spoofed source address, it can be repeated cheaply and continuously, giving an attacker with no valid certificate a low-cost, repeatable DoS primitive against arbitrary Nebula tunnels whose remote index and current remote endpoint they can learn (e.g., by observing traffic, being a former relay, or brute-forcing indices, which are 32-bit and allocated sequentially/pseudo-randomly per session).

This qualifies as remote state poisoning under the accepted impact categories: unauthenticated remote teardown of established security state (tunnel/hostmap entries) without possessing a CA-signed certificate.

### Likelihood Explanation
- The `RemoteIndex` field is unauthenticated cleartext data present in every packet header, making it observable to any network-position attacker (on-path sniffing, prior relay role, or even packet timing/counter-guessing given exposure through `header.Handshake` traffic).
- UDP source-address spoofing is a well-known, widely available capability for off-path attackers, especially since no return packet needs to reach the attacker (`sendRecvError` never expects a reply), which removes the usual barrier (needing to receive spoofed-destination traffic).
- The mitigating factors are configuration-only (`listen.accept_recv_error`/`send_recv_error` style gates in `interface.go`) and a same-address check that does not use any cryptographic proof — meaning any deployment that leaves `RecvError` acceptance enabled (documented in the CHANGELOG as a config option, not a default-deny for spoofing) is exposed.

### Recommendation
- Require the `RecvError` handling path to be based on cryptographically verified state, not solely on observed UDP source address matching. For example, only accept `RecvError` when it can be tied to a value derived from an already-established, authenticated session (e.g., HMAC/MAC the `RecvError` using the negotiated session keys instead of sending/accepting it fully in the clear), similar to how `CloseTunnel` is already routed through the encrypted/authenticated packet path after `Decrypt` succeeds (see the `header.CloseTunnel` handling that occurs only post-decryption).
- If a cleartext fast-path is required for performance reasons, rate-limit and require multiple consistent packets (e.g., across changing ephemeral values) before tearing down state, and default `accept_recv_error` to a conservative bounded value with sender verification.
- Document and, ideally, enforce this in code (not just via optional config) so that an operator cannot inadvertently leave tunnels vulnerable to blind spoofed teardown.

### Proof of Concept
1. Attacker observes (or otherwise learns) a target's active Nebula session `RemoteIndex` value `X` and the peer's current public `UdpAddr` `A:P` — obtainable by sniffing any cleartext Nebula header from the target's traffic (handshake or data packet headers are unencrypted) or through prior relay participation.
2. Attacker crafts a raw UDP packet with header `Type = header.RecvError`, `RemoteIndex = X`, and spoofed source address `A:P`, and sends it to the victim's listening UDP port.
3. On the victim, `readOutsidePackets` dispatches directly to `f.handleRecvError(via.UdpAddr, h)` without any decryption/authentication (see `outside.go:81-83`).
4. `handleRecvError` finds `hostinfo` via `QueryReverseIndex(X)`, sees `hr == addr` (since the source was spoofed to match), and calls `f.closeTunnel(hostinfo)` plus `hm.DeleteHostInfo(hostinfo)`, tearing down the legitimate tunnel without the attacker ever presenting a CA-signed certificate or completing a handshake.
5. Repeating this at will provides a persistent DoS against the victim's tunnel to that peer.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}

func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

	// First message of a new handshake. The wire format requires RemoteIndex
	// to be zero here (the initiator has no responder index to fill in yet),
	// and generateIndex never allocates 0, so any non-zero RemoteIndex on a
	// stage-1 packet is malformed or someone probing for an index collision.
	// Drop without paying the cost of running noise on a pending Machine.
	if h.MessageCounter == 1 {
		if h.RemoteIndex != 0 {
			hm.l.Debug("dropping stage-1 handshake with non-zero RemoteIndex",
				"from", via, "remoteIndex", h.RemoteIndex)
			return
		}
		hm.beginHandshake(via, packet, h)
		return
	}
