### Title
Out-of-bounds read via unchecked Zip64 extra-field attribute index in `LH`/`CDH` size/offset accessors - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar`'s Zip/JAR parser (`LH`, `CDH`) uses `ziph::zfield_has_ext64()` to detect that a 32-bit size/offset field is `0xFFFFFFFF` and must be read from the accompanying Zip64 extra field, then unconditionally calls `Zip64ExtraField::attr64(index)` at a fixed index without ever checking `attr_count()` against that index.

### Finding Description
`Zip64ExtraField::find()` (via `ExtraField::find`) only validates that the extra field's declared `size()` (i.e. `4 + payload_size()`) fits inside the `extra_fields()` buffer bounded by `extra_fields_length()` [1](#0-0) . It does not validate how many 8-byte attributes (`attr_count()`) the field actually contains relative to what the caller intends to read.

`LH::compressed_file_size()`/`uncompressed_file_size()` and `CDH::compressed_file_size()`/`uncompressed_file_size()`/`local_header_offset()` all call `z64->attr64(index)` with a hard-coded or computed index (0 or 1, or up to 2 for `local_header_offset()`) as soon as the 32-bit field equals `0xFFFFFFFF`, with no check that `z64->attr_count()` is large enough to contain that index: [2](#0-1) [3](#0-2) [4](#0-3) 

`attr64(index)` itself performs no bounds check — it directly dereferences `attr_[index]` at `this + 4 + index*8`: [5](#0-4) 

A malicious archive can therefore declare a 32-bit size field as `0xFFFFFFFF` while attaching a Zip64 extra field whose `payload_size` covers only one attribute (`attr_count()==1`) or zero attributes, positioned at the very end of the mapped input file's central directory / local header buffer. When the accessor reads `attr64(1)` (or `attr64(2)` for `local_header_offset`), it reads past the end of the extra field — and potentially past the end of the `mmap`'d input file (`InputJar`/`InputZipFile` map the file directly, per `input_jar.cc` and `third_party/ijar/zip.cc`) — producing an out-of-bounds read that can crash the build tool (SIGSEGV) or leak adjacent memory contents into size/offset computations. This is the same bug class as the referenced GPAC CVE: a parser trusts an attacker-supplied sub-field length/index without confirming the corresponding backing buffer is large enough, leading to an OOB read/segfault while dumping/decoding a field.

Note that a related-but-distinct issue (an oversized `payload_size` on a *generic* extra field exceeding the extra-fields buffer) is already defended against in `OutputJar::AppendToDirectoryBuffer`, which explicitly checks `ef->size()` against `ef_end` and calls `diag_errx("malformed extra field")`, as proven by the existing `MalformedExtraField` death test [6](#0-5) [7](#0-6) . That mitigation, however, only guards the byte-range of the extra field itself; it does not guard the *sub-attribute count* consumed by `attr64()`, so the `Zip64ExtraField` under-population bug described above is not covered by that check.

### Impact Explanation
`singlejar` is Bazel's core JAR-merging tool, invoked on every `java_binary`/`java_library` build to merge/process source and dependency jars — including externally fetched artifacts (e.g., via `java_import`, `maven_install`, `http_jar`) whose byte content is attacker-controlled. A crafted jar with an under-sized Zip64 extra field reaching this code path causes an out-of-bounds memory read, crashing the build (denial of the build step) or potentially leaking adjacent heap/mmap memory bytes into computed size/offset values, which then influence subsequent memory copies (e.g., `AppendToDirectoryBuffer`, `AddJar`), risking further memory-safety issues downstream.

### Likelihood Explanation
Reachability is high: any dependency archive processed by `singlejar` (which every Java build target uses) can trigger this, requiring no privileges beyond controlling the bytes of one input jar. Crafting a valid-looking Zip64 extra field with too few attributes is straightforward and requires no exploitation of compression or other zip machinery.

### Recommendation
In `Zip64ExtraField::attr64()` (or at each call site in `LH`/`CDH`), validate `attr_count()` against the required index before dereferencing, and treat a mismatched attribute count the same way the existing malformed-extra-field check does — abort parsing with a diagnostic (`diag_errx`) rather than reading uninitialized/out-of-bounds memory. Apply this consistently across `LH::compressed_file_size()`, `LH::uncompressed_file_size()`, `CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, and `CDH::local_header_offset()`.

### Proof of Concept
Extend the existing `MalformedExtraField`-style test in `src/tools/singlejar/output_jar_simple_test.cc`: build a minimal zip (as `CreateZipWithMalformedExtraField()` does) where the `CDH`/`LH` for entry `"evil.bin"` sets `compressed_file_size32(0xFFFFFFFF)` and attaches a `Zip64ExtraField` with `payload_size(8)` (i.e. `attr_count()==1`, only the uncompressed-size slot present) placed at the last bytes of the mapped file/central directory buffer. Calling `OutputJar::Doit()` on a `--sources` list containing this crafted jar drives `CDH::compressed_file_size()`/`attr64(1)` to read 8 bytes past the intended field, and if the extra field is placed at the tail of the `mmap`'d region, this manifests as a SIGSEGV (verifiable via `ASSERT_DEATH`), analogous to the GPAC segfault reproduced by an out-of-bounds field read during parsing.
