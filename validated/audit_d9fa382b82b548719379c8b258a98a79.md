### Title
DoS via dust DepositToken transfers filling `depositTokensOfAccount` up to `MAX_TOKENS_PER_USER`, blocking new collateral deposits and debt issuance - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks each account's held collateral and debt in two per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount`) whose combined size is capped at `MAX_TOKENS_PER_USER = 30` by the `onlyIfAdditionWillNotReachMaxTokens` modifier on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (contracts/Pool.sol:143-148, 204-220). Entries are added automatically whenever an account's balance of a `DepositToken` or `DebtToken` goes from 0 to >0 — including on plain ERC20 `transfer`/`transferFrom` of `DepositToken` (contracts/DepositToken.sol:498-526). An unprivileged attacker can therefore deposit dust into every listed deposit token and transfer 1 wei of each to a victim, filling the victim's account list to the cap. Any subsequent `addTo*TokensOfAccount` for that victim reverts with `UserReachedMaxTokens`, reverting the entire parent transaction (a `deposit()` mint or a `DebtToken` issuance), which permanently blocks the victim from adding any *new* collateral type or opening any *new* debt position while the attacker's dust stays.

### Finding Description
The bug class is identical to the OpenQ report: an attacker-controlled, permissionlessly-inflatable token list with a hard cap that, once full, DoSes a legitimate feature.

Concretely:

1. `Pool.addToDepositTokensOfAccount(account_)` and `addToDebtTokensOfAccount` are external and called by the token contracts on every 0→positive balance transition (DepositToken `_mint` at DepositToken.sol:486-488 and `_transfer` at DepositToken.sol:517-520; analogously `DebtToken` issuance).
2. Both are gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` (Pool.sol:143-148).
3. `DepositToken.transfer`/`transferFrom` are public and unrestricted beyond `_revertIfLocked` on the *sender* (DepositToken.sol:348-376). The recipient's consent is never required. A 1-wei transfer to a victim both credits the victim and calls `pool.addToDepositTokensOfAccount(victim)`.
4. Because `addToDepositTokensOfAccount` reverts inside `_mint`, the victim's `deposit()` of any *new* collateral token reverts; because `addToDebtTokensOfAccount` reverts inside issuance, the victim cannot mint any *new* synthetic asset either.
5. Removal normally requires the victim to transfer/withdraw the dust balance to zero. But `transfer` and `withdraw` are gated by `_revertIfLocked`/`unlockedBalanceOf` (DepositToken.sol:383-398): once the victim's `issuableInUsd` is 0 (position at/below water — exactly when topping up new collateral is most urgent), their unlocked balance is 0 and they cannot purge the dust entries themselves. The slots stay occupied and the account is stuck at the cap.

Modifiers that do **not** stop this: `nonReentrant` (single calls), `whenNotShutdown`/`pause` (not set in normal config), `SynthContext._msgSender` (no meta-tx needed), and `_revertIfLocked` only constrains the *sender*'s locked balance, not the recipient.

The attacker's cost is only dust-sized deposits of each existing `DepositToken` (themselves capped at 30 via `addDepositToken`, Pool.sol:703). As pools approach the 30-collateral cap, a single attacker can permanently pin a victim at the limit.

### Impact Explanation
Broken invariant: liveness of account operations. A targeted user is unable to (a) deposit a new collateral type, (b) receive a `DepositToken` they don't already hold (e.g., a rescue transfer from a third party or a liquidation seizure of a new token type — `seize` also calls `_transfer`, DepositToken.sol:343-345), or (c) open a debt position in a synthetic they don't already hold. If the victim is at the liquidation boundary (`issuableInUsd == 0`), they cannot remove the attacker's dust entries because their `unlockedBalanceOf` is 0, so the freeze persists until the position is liquidated or repaid by other means — i.e., temporary freezing of the account's ability to acquire collateral, which can force an avoidable liquidation.

### Likelihood Explanation
Requires only an EOA holding dust of each registered `DepositToken` (attacker deposits minimal underlying themselves). No privileged role, oracle manipulation, or flash loan needed. Effectiveness grows with the number of registered deposit/debt tokens; it is fully effective only when the attacker can bring the victim's combined count to 30, so on deployments with few collateral types the residual capacity may remain — but the same cap also bounds the total pool token set (30), meaning a mature pool makes the attack cheap and total.

### Recommendation
- Do not revert `addTo*TokensOfAccount` at the cap; instead return a boolean/skip so a failed set-add doesn't revert the whole `deposit`/`mint`/`transfer`, or
- Only count tokens added via the account's own actions, or track "forced" additions separately, or
- Remove `transfer`/`transferFrom` from the account-list bookkeeping (add to the recipient's list only on `deposit`/liquidation `seize` initiated in-protocol), so unsolicited dust cannot occupy slots.

// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;               // deployed/initialized pool
    DepositToken[] dTokens;  // the pool's registered deposit tokens
    address victim = address(0xBEEF);
    address attacker = address(0xBAD);

    function test_dustFillBlocksVictimDeposit() public {
        // 1. Attacker deposits dust into each registered DepositToken
        //    and transfers 1 wei of each to the victim.
        for (uint i; i < dTokens.length; ++i) {
            IERC20 underlying = dTokens[i].underlying();
            deal(address(underlying), attacker, 1);
            vm.startPrank(attacker);
            underlying.approve(address(dTokens[i]), 1);
            dTokens[i].deposit(1, attacker);           // mint dust to attacker
            dTokens[i].transfer(victim, 1);            // adds dTokens[i] to victim's list
            vm.stopPrank();
        }

        // combined slots used == number of pool deposit tokens (+ any debt tokens the
        // attacker can route to victim). Repeat with remaining tokens until:
        assertGe(pool.getDepositTokensOfAccount(victim).length
               + pool.getDebtTokensOfAccount(victim).length, 30 /* or available count */);

        // 2. Victim tries to deposit a collateral type they don't yet hold -> reverts
        DepositToken newToken = /* a deposit token the victim doesn't hold */;
        IERC20 newUnderlying = newToken.underlying();
        deal(address(newUnderlying), victim, 100e18);
        vm.startPrank(victim);
        newUnderlying.approve(address(newToken), 100e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        newToken.deposit(100e18, victim);
        vm.stopPrank();

        // 3. If victim is at the liquidation boundary, they cannot purge the dust:
        //    unlockedBalanceOf(victim) == 0  =>  transfer() reverts in _revertIfLocked,
        //    so removeFromDepositTokensOfAccount can never run for them.
    }
}
