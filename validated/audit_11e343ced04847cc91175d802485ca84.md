### Title
Rounding truncation lets `calculate_fee` return a zero remote fee for non-zero, validated pricing parameters, letting relayer-reward delivery costs go unpaid - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`PricingParameters::validate()` in `bridges/snowbridge/primitives/core/src/pricing.rs` only checks that the raw governance-set fields (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) are individually non-zero. It never checks the *derived* value actually charged to a user, which is computed later by `Pallet::calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`. Because of integer truncation while converting the wei-denominated remote cost into local (DOT) decimals, `calculate_fee` can legitimately return `fee.remote == 0` even though all pricing parameters passed `validate()`. This is the exact same "guard checks the wrong thing" bug class as the external report: a value that should be discarded/reverted as invalid (0) is instead accepted and used downstream as if it were legitimate.

### Finding Description
`calculate_fee` computes the remote (Ethereum-side) fee as follows: [1](#0-0) 

1. `calculate_remote_fee` computes `fee_per_gas * gas_used_at_most + reward` in wei (`U256`).
2. The wei value is downcast to `u128` and wrapped in `FixedU128`, multiplied by `multiplier`, divided by `exchange_rate`.
3. `convert_from_ether_decimals` divides by `10^(18 - T::Decimals)` (e.g. `10^8` for a 10-decimal DOT-like currency) using integer `checked_div`, which floors towards zero.

If the resulting wei-scaled numerator is smaller than the decimal-conversion divisor (a completely plausible situation for governance-set `fee_per_gas`/`reward` values that are individually non-zero but small, or for commands with low `gas_used_at_most`), step 3 truncates the result to `0`. This is demonstrated by the pallet's own test: [2](#0-1) 

The test comment itself states: *"Though [a] non[-]zero pricing params the remote fee calculated here is invalid which should be avoided"* — yet no code path prevents it. `PricingParameters::validate()` only guards the raw inputs, not the computed output: [3](#0-2) 

The zero/invalid `fee.remote` then flows unfiltered out of `Pallet::validate` (the public `SendMessage::validate` entry point used by every Polkadot→Ethereum message, including ordinary user-initiated XCM `ExportMessage`s) into the fee that gets charged to the sender: [4](#0-3) 

Meanwhile, `do_process_message` independently sets the *actual* reward promised on the Ethereum side directly from the raw governance `pricing_params.rewards.remote` (in wei), completely decoupled from the truncated `fee.remote` that was (or wasn't) collected from the sender: [5](#0-4) 

So the invariant "the local chain always collects enough DOT-equivalent fee to cover the ETH reward it commits to pay a relayer" can be silently broken: the fee-charging side (`fee.remote`) rounds to zero while the reward-commitment side (`reward` field in the committed `CommittedMessage`) still promises a real, non-zero wei amount to whichever relayer submits the message on Ethereum. This is directly analogous to the external report's core defect: a value that is invalid (0) and should be rejected/discarded is instead treated as valid input to downstream accounting, because the validity guard (`validate()`/`approvedOracles` check in the original; `PricingParameters::validate()` here) checks the wrong thing.

### Impact Explanation
Any unprivileged user calling the public Snowbridge send path (e.g. XCM `ExportMessage`, `pallet_xcm::execute`/`send`) can have their message accepted and enqueued for delivery to Ethereum while paying `fee.total() = fee.local + 0` — i.e., without covering the on-chain-committed relayer reward. This is "public underpriced work" that: (a) allows spamming free/underpriced bridge messages, degrading BridgeHub message-queue throughput and potentially stalling honest bridge traffic, and (b) creates a funding mismatch where the reward promised to Ethereum relayers is not actually backed by fees collected on the Polkadot side, risking depletion of whatever account funds the reward payouts. This matches the required impact category of "public underpriced work that degrades block production or stalls bridge processing," and is not caused by a malicious admin, governance actor, relayer, or node — it is a systemic rounding defect reachable by any ordinary user sending a bridge message under governance-set (but individually valid) pricing parameters.

### Likelihood Explanation
Likelihood depends on the exact `PricingParameters` in force and per-command `gas_used_at_most`. Because `PricingParameters::validate()` allows minimum non-zero values (`1` wei for `fee_per_gas` and `reward`, any non-zero `exchange_rate`/`multiplier`), and because `convert_from_ether_decimals` divides by up to `10^8`, it is straightforward to construct (or organically encounter) parameter/gas combinations where the intermediate value is smaller than the divisor, deterministically producing `fee.remote == 0` for every message sent under those parameters. The pallet's own regression test confirms this is a reachable, already-observed state, not a theoretical edge case — the only open question (which I was unable to fully verify in the remaining time) is whether the currently deployed live `PricingParameters` on production BridgeHub are far enough from this threshold to avoid triggering it, or whether `Fee::total()`/`take_fee()` in the XCM executor path enforces any additional non-zero check I did not locate before running out of iterations.

### Recommendation
Add a validity check on the **computed** fee, not just the raw parameters: after computing `fee.remote` in `calculate_fee`, `ensure!(fee.remote > 0, ...)` (or return a `SendError`) whenever `params.rewards.remote` or `max_dispatch_gas` are non-zero, so messages cannot be enqueued with a promised Ethereum reward that costs the sender nothing. Alternatively, derive the wei `reward` committed in `do_process_message` from the same rounding-consistent conversion used for `fee.remote`, so the two values can never diverge, and add a test asserting `fee.remote > 0` whenever `PricingParameters::validate()` passes and `gas_used_at_most > 0`.

### Proof of Concept
The existing unit test already demonstrates the corrupted value with no code change required: [2](#0-1) 
With `exchange_rate = 1/1`, `fee_per_gas = 1`, `rewards.remote = 1`, `multiplier = 1/1` (all individually non-zero, so `PricingParameters::validate()` passes), `calculate_fee(250000, price_params)` returns `fee.remote == 0` while `fee.local == 698000000`. Any message sent under these parameters would be enqueued via `SendMessage::validate` charging only `fee.local`, while `do_process_message` still records `reward = pricing_params.rewards.remote` (non-zero, in wei) into the `CommittedMessage` sent to Ethereum — a promised payout with zero fee coverage.

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}
