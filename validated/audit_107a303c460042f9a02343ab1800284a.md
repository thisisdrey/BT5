### Title
Out-of-bounds heap read parsing central-directory extra fields in `InputZipFile::ProcessCentralDirEntry` - (File: third_party/ijar/zip.cc)

### Summary
`ijar` (the tool bazel runs to build interface jars from arbitrary input jars, e.g. from `java_import`/prebuilt third-party jars) parses a jar's ZIP central directory in `InputZipFile::ProcessCentralDirEntry` without the same bounds-checking discipline used elsewhere in the file, allowing a hostile jar to drive parsing past the mapped file/central-directory region.

### Finding Description
`third_party/ijar/zip.cc` reads local-file data with explicit bounds checks via `EnsureRemaining()` (e.g. `InputZipFile::ProcessLocalFileEntry` [1](#0-0) , `InputZipFile::SkipFile` [2](#0-1) ). However `InputZipFile::ProcessCentralDirEntry`, which parses each Central Directory Header (CDH) and its extra fields, performs no such check at all: [3](#0-2) 

It reads `file_name_length`, `extra_field_length`, `file_comment_length` directly off attacker-controlled bytes, then walks the extra-field area:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  if (header_id == ZIP64_EXTRA_FIELD_TAG) {
    if (*uncompressed_size == U4_MAX) *uncompressed_size = get_u8le(extra);
    ...
```
There is no verification that:
- `extra_p + 4` stays within the declared `extra_field_length` (or within the mapped file) before the two `get_u2le` calls that read `header_id`/`data_size`, and
- `data_size >= 8` (or that `extra + 8` is in-bounds) before `get_u8le(extra)` is executed for the ZIP64 tag.

The only global guard is in `FindZipCentralDirectory`, which checks `cd.central_dir_offset + cd.central_dir_size <= in_length` [4](#0-3) . That bounds the *aggregate* central directory region against the mmapped file length, but it does not stop a single malicious CDH entry from declaring a `file_name_length`/`extra_field_length`/`comment_length` combination whose extra-field walk (and the raw `get_u2le`/`get_u4le`/`get_u8le` reads it performs) runs past the actual remaining bytes of that record — potentially past the end of the mmapped file itself, into unmapped memory, or misreading adjacent heap/mapped bytes as size/offset fields. This mirrors CVE-2018-8754's root cause: a record-size field (SID size, string size, data size) is trusted and used to drive further reads without validating it against the actual buffer bounds.

This class of bug was actually already fixed for singlejar's independent ZIP-header implementation: `ExtraField::find` in `src/tools/singlejar/zip_headers.h` explicitly checks `byte_ptr(start) + sizeof(ExtraField) > byte_ptr(end)` and `byte_ptr(start) + extra_field->size() > byte_ptr(end)` before touching payload data [5](#0-4) , and `output_jar.cc` calls `diag_errx` on a malformed extra field, which is covered by a dedicated regression test, `OutputJarSimpleTest.MalformedExtraField` [6](#0-5) . `third_party/ijar/zip.cc`'s independent, older ZIP parser (used by `ijar`, a separate code path from singlejar) has no equivalent protection.

### Impact Explanation
`ijar` processes untrusted, externally-supplied jar bytes: it is the tool bazel invokes to reduce prebuilt/third-party jars (e.g. `java_import` inputs, jars fetched from external repositories/registries) to interface jars, as shown by `OpenFilesAndProcessJar` calling `ZipExtractor::Create`/`ProcessAll` directly on the input file [7](#0-6) . A malicious jar (served from an attacker-controlled dependency URL/registry/mirror) with a crafted central-directory extra field can cause `ijar` to read outside the bounds of the record it declared, and in the worst case outside the mmapped input file, producing a crash (segfault) or, more subtly, values pulled from adjacent memory being fed into subsequent size/offset computations — an integrity violation of the assumption that a declared record size bounds the data read for that record.

### Likelihood Explanation
The `ijar` executable's central-directory parser is reached on every jar it processes, and there is no existing bounds check comparable to `EnsureRemaining()` (used elsewhere in the same file) or to singlejar's `ExtraField::find` guarding this specific code path, so a crafted extra field with an oversized `data_size` value, or a CDH whose stated `file_name_length + extra_field_length + comment_length` doesn't match the true remaining bytes, reaches the vulnerable reads unmodified.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc`), before reading `header_id`/`data_size` for each extra-field record, verify `extra_p + 4 <= p` (and that `p` itself does not exceed the mapped file end / declared central directory bounds), and before dereferencing `get_u8le(extra)` for `ZIP64_EXTRA_FIELD_TAG`, verify `data_size >= 8` and `extra + 8 <= extra_field_end`. Mirror the guard pattern already used by `ExtraField::find` in `src/tools/singlejar/zip_headers.h` (lines 99-115) and fail/error out (as `EnsureRemaining` does) rather than reading past the declared extents.

### Proof of Concept
Craft a minimal jar with:
1. One CDH entry whose `extra_field_length` covers a single crafted extra-field record with `header_id = 0x0001` (ZIP64 tag) and `data_size = 0` (or 2), i.e. fewer than 8 bytes of payload, placed at the very end of the mmapped file (immediately followed by the EOCD record with nothing after it).
2. Run `ijar` (or the equivalent `InputZipFile::ProcessCentralDirEntry` call) against this file.

Expected/vulnerable behavior: `get_u8le(extra)` reads 8 bytes starting at `extra`, running past the declared 0/2-byte payload and potentially past the end of the mmapped region, yielding an out-of-bounds read (crash under ASan/valgrind, or silently wrong `uncompressed_size`/`compressed_size`/`offset` values used later). This can be encoded as a `third_party/ijar/zip_test.cc`-style unit test (analogous to the existing `output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField`/`MalformedExtraField` test) that builds the byte sequence above and asserts a bounds-check error is raised (currently it is not) — I was not able to locate an existing C++ unit test file for `third_party/ijar/zip.cc` in the index (only shell-based integration tests under `third_party/ijar/test/`), so a new test target would need to be added to reproduce this deterministically.

std::string CreateZipWithMalformedExtraField() {
  std::string zip_data;
  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
  ecd->cen_offset32(cdh_offset);

  return zip_data;
}
