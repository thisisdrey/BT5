### Title
Unbounded/unvalidated length in `extractBytes32Array` used by the `BatchValidateSign` precompile leads to out-of-bounds array read and unbounded allocation from untrusted transaction data - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The libming CVE is a heap buffer over-read caused by trusting an attacker-controlled length/index field while decoding untrusted binary data without validating it against the buffer's actual bounds. The same bug class exists in java-tron's `BatchValidateSign` precompiled contract, which parses ABI-encoded `data` supplied directly in a `TriggerSmartContract` transaction and calls a helper that reads array-length and per-element offsets from the untrusted input without any bounds check against the parsed word array.

### Finding Description
`PrecompiledContracts.extractBytes32Array` reads a length word and then indexes into the `words` array using that attacker-supplied length with no validation: [1](#0-0) 

Compare this to the sibling helpers `extractBytesArray` and `extractSigArray`, which at least guard against `offset` exceeding `words.length`: [2](#0-1) 

`extractBytes32Array` has no such guard at all — neither on `offset`, nor on `offset + i + 1` staying within `words.length`, nor on `len` being non-negative or reasonably bounded.

In `BatchValidateSign.doExecute`, the `addresses` array is built by calling `extractBytes32Array` on an offset computed from the raw `data`: [3](#0-2) 

The only bound placed on the length (`addrArraySize > MAX_SIZE`) is inside an `if (VMConfig.allowTvmSelfdestructRestriction())` branch, and even when that flag is enabled it only rejects the *signature*-count/`addrArraySize` via a separately-recomputed value — the call to `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)` executes unconditionally beforehand with no bound on `len = words[offset].intValueSafe()`. An attacker fully controls `data` (hence `words`), so:
- `offset` can point outside the array, causing `words[offset]` to throw `ArrayIndexOutOfBoundsException` (out-of-bounds read analogous to the libming over-read), or
- `len` can be a very large positive value (e.g. `Integer.MAX_VALUE`), causing `new byte[len][]` to attempt a huge allocation (memory-exhaustion / `OutOfMemoryError`) before the loop even reaches the out-of-bounds index.

This is invoked from `Program`'s precompile-call path when the TVM executes a `CALL`/`STATICCALL` to the `BatchValidateSign` address, which is unprivileged and reachable by any contract deployer/caller once `VMConfig.allowTvmSolidity059()` is active (a standard mainnet hard-fork flag).

### Impact Explanation
Although `BatchValidateSign.execute` wraps `doExecute` in `catch (Throwable t)` and returns a default failure result for ordinary `RuntimeException`s, an `OutOfMemoryError` triggered by an oversized `new byte[len][]` allocation is a JVM-wide resource-exhaustion event: it can trigger garbage collection storms or genuine memory pressure across the whole node process, not just the executing thread, even though the `Throwable` is nominally caught. Because this precompile can be invoked by any account triggering a smart contract, an attacker can repeatedly send transactions that attempt huge array allocations, degrading or destabilizing full nodes/witness nodes that must execute the same transaction deterministically. This is a resource-exhaustion/DoS analog of the CVE rather than a memory-disclosure bug, but it is the closest reachable analog to "heap buffer over-read causing DoS" within the allowed attack surface (TVM precompiles/opcodes reachable from an unprivileged contract call).

### Likelihood Explanation
High: `BatchValidateSign` is reachable by any address via a normal `TriggerSmartContract`, requires no special privilege, and the vulnerable code path executes before any size-limiting check is applied to the `addresses` array length.

### Recommendation
Add the same defensive checks already present in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`:
- Validate `offset` is within `[0, words.length - 1]` before reading `words[offset]`.
- Validate `len` is non-negative and bounded (e.g., by the same `MAX_SIZE` constant used elsewhere) before allocating `new byte[len][]`.
- Validate `offset + len` does not exceed `words.length` before the loop reads `words[offset + i + 1]`.
Apply the length/offset bound checks unconditionally rather than only inside the `allowTvmSelfdestructRestriction()` branch.

### Proof of Concept
1. Deploy any contract and, with `allowTvmSolidity059` active, craft a `data` payload for a `CALL` to `BatchValidateSign`'s address such that `words[2]` (interpreted as a byte offset divided by 32) points to a word whose value (`len`) is a very large positive integer (e.g., `0x7FFFFFFF`).
2. Trigger the contract; `extractBytes32Array` attempts `new byte[0x7FFFFFFF][]`, causing an `OutOfMemoryError`/large transient allocation during transaction execution.
3. Alternatively, set the offset so that `words[offset + i + 1]` for some `i < len` exceeds `words.length`, causing an `ArrayIndexOutOfBoundsException` read past the parsed buffer, mirroring the libming out-of-bounds read.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
