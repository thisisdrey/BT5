### Title
Cheap dust-transfer stuffing of `MAX_TOKENS_PER_USER` account list blocks victims from depositing new collateral - (File: contracts/Pool.sol)

### Summary
The external report describes a resource-mismatch bug: a block proposal is capped on a scarce dimension (`proposal_byte_limit`) that can be filled while paying only a fraction of the metered dimension (`proposal_gas_limit`), enabling cheap stuffing and defeating the fee-market feedback. The Metronome analog is `Pool.MAX_TOKENS_PER_USER = 30`: every account has a fixed, scarce capacity of 30 combined debt/deposit-token list slots, but an unprivileged attacker can fill a victim's `depositTokensOfAccount` list with dust `DepositToken` transfers at near-zero economic cost (the "calldata zero-bytes" analog — the transfer charges almost nothing while consuming a permanent slot). Once the list is full, `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`, so the victim cannot deposit any new collateral type. The scarce resource (30 list slots) is charged at dust price instead of meaningful value — the same multi-dimensional-underpricing class.

### Finding Description
`Pool` enforces a hard cap on per-account tracked tokens:

```solidity
uint256 public constant MAX_TOKENS_PER_USER = 30;
```

`onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol:143-148) reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. Slots are added by `addToDepositTokensOfAccount` (contracts/Pool.sol:216-220), which is invoked by `DepositToken` whenever an account's deposit-token balance goes 0 → non-zero — including on plain `transfer`/`transferFrom` to an arbitrary recipient (`DepositToken` is a freely transferable ERC-20; it forwards to `Pool.addToDepositTokensOfAccount` in its transfer hook, and `seize` uses the same path for the recipient).

Attack path, all unprivileged:

1. Attacker deposits dust amounts (e.g. 1 wei of underlying) of each listed collateral via `DepositToken.deposit`, receiving dust deposit-token balances for up to 30 distinct collaterals (whichever the victim does not already hold).
2. Attacker calls `depositToken_i.transfer(victim, 1)` for each. Each transfer calls `Pool.addToDepositTokensOfAccount(victim)`, filling the victim's list to 30.
3. Any subsequent victim action that would add a new token to the list reverts with `UserReachedMaxTokens`: depositing a collateral type they do not already hold, receiving deposit tokens via transfer, receiving seized collateral (`DepositToken.seize` → recipient add), or taking on a new debt token via `DebtToken` mint paths.
4. Attacker can refill slots whenever the victim clears them (victim must transfer out the dust balance to zero to trigger `removeFromDepositTokensOfAccount`), sustaining the grief at dust cost.

Modifiers do not stop it: `transfer` on `DepositToken` has no opt-in/opt-out of list registration; `addToDepositTokensOfAccount` only authenticates that the caller is a registered deposit token; pause/shutdown flags are unrelated; `SynthContext._msgSender` checks pass since the call originates from the token contract.

### Impact Explanation
Temporary freezing of funds / forced position degradation:

- A victim holding collateral outside the protocol cannot deposit any new collateral type while their list is stuffed. If their position is drifting toward liquidation, they may be unable to add the new collateral needed to restore health (only an existing-listed collateral can be topped up).
- New debt-token issuance against a not-yet-listed synth also reverts, blocking leverage/refinancing through `SmartFarmingManager.leverage` for new synths.
- The cost asymmetry mirrors the reported bug: the attacker spends dust collateral plus ordinary transfer gas to consume a capped, victim-owned resource, while the victim must actively unwind each slot to recover capacity — and the attacker can re-stuff after every cleanup, making the freeze effectively persistent.

### Likelihood Explanation
High reachability: `DepositToken.transfer`/`transferFrom` are public, permissionless ERC-20 entry points; no governor, keeper, oracle, or malicious endpoint is needed. The only prerequisites are that the pool lists multiple deposit tokens (deployed pools do — `addDepositToken` allows up to `MAX_TOKENS_PER_USER` collaterals) and that the victim does not already hold them. Cost scales linearly (~30 cheap transfers) and can target any address, including known leveraged SmartFarming positions. The one softening factor is that it does not directly steal funds — it blocks the victim's *new-collateral* entry points until they clear slots — which caps severity at a griefing/liveness (temporary freeze) class rather than theft.

### Recommendation
Decouple the scarce per-account capacity from cheap recipient-side registration:

- Only add a deposit token to an account's list on protocol-mediated `deposit`/`seize` flows (or make the victim opt in), rather than on any ERC-20 `transfer` to them.
- Alternatively charge a meaningful minimum (e.g., require `unlockedBalanceOf`-style threshold above dust, or a USD-denominated minimum deposit via `masterOracle().quoteTokenToUsd`) before registering the token in `depositTokensOfAccount` — the analog of raising calldata gas cost so the scarce dimension cannot be stuffed for near-zero payment.
- Consider raising `MAX_TOKENS_PER_USER` or pruning zero-value entries so dust slots do not count against the cap.

### Proof of Concept
Hardhat/foundry sketch (fork at a deployed `Pool` with ≥2 listed deposit tokens; generalizes to filling all 30 slots):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract TokenListStuffingTest is Test {
    Pool pool;
    IDepositToken depositTokenA; // victim already holds none
    IDepositToken depositTokenB; // collateral victim wants to deposit
    IERC20 underlyingA;
    IERC20 underlyingB;

    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    function test_dustTransferStuffsVictimList() public {
        // Setup: deal attacker dust underlying for every listed deposit token
        address[] memory dts = pool.getDepositTokens(); // assume N listed
        deal(address(underlyingA), attacker, 1);
        deal(address(underlyingB), victim, 100e18);

        // Victim's list currently empty
        assertEq(pool.getDepositTokensOfAccount(victim).length, 0);

        // Attacker deposits 1 wei of underlying A and transfers the dust deposit token
        vm.startPrank(attacker);
        underlyingA.approve(address(depositTokenA), 1);
        depositTokenA.deposit(1); // mints deposit-token A to attacker
        // ... repeat for all N collaterals so victim's list reaches 30 ...
        depositTokenA.transfer(victim, 1); // adds A to victim's list
        vm.stopPrank();

        // Inflate victim's list to MAX_TOKENS_PER_USER with remaining dust transfers
        // (loop omitted: for each listed depositToken_i: deposit dust, transfer to victim)
        vm.prank(attacker);
        // ... after loop:
        // assertEq(pool.debtTokensOfAccount.length + pool.depositTokensOfAccount.length, 30)

        // Victim now cannot deposit collateral B (a type not yet in their list)
        vm.startPrank(victim);
        underlyingB.approve(address(depositTokenB), 100e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        depositTokenB.deposit(100e18); // reverts: list is full
        vm.stopPrank();
    }
}
```

Reproduction notes: `DepositToken.deposit` mints shares to the caller and registers the token via `Pool.addToDepositTokensOfAccount`; each `transfer` to `victim` registers it on the *victim's* list. Reaching 30 total slots makes every subsequent registration revert in `onlyIfAdditionWillNotReachMaxTokens` (contracts/Pool.sol:143-148), demonstrating that dust-priced transfers cheaply exhaust the capped resource — the same underpriced-stuffing invariant as the reported calldata bug.

Caveat: I could not re-open `DepositToken.sol` in a follow-up read to quote its exact transfer-hook lines; the registration path is evidenced by the `addToDepositTokensOfAccount` callers in `DepositToken.sol` and the modifier in `Pool.sol`, but the PoC's exact function names (e.g., `deposit(uint256)`) should be confirmed against `IDepositToken` during implementation.
