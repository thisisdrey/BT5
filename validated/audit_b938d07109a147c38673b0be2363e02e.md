### Title
Integer-overflow bypass of chunk-offset bounds check in MVCC manifest parser causes RPC-handler crash - ([File: internal/git/mvcc/manifest.go])

### Summary
`ParseManifest` and its helper `parseChunks` parse an untrusted, attacker-influenceable binary manifest without safely bounding chunk offsets before using them as slice indices. Like the reported concurrent-merkle-tree bug — where an index equal to a boundary value (`1<<MAX_DEPTH`) was accepted as "in range" because the validation logic didn't account for a boundary/overflow edge case — the Gitaly manifest parser validates chunk offsets with a check that can be defeated by integer overflow, letting an out-of-range offset slip through and subsequently panic the process when used to slice the manifest buffer.

### Finding Description
`parseChunks` reads 64-bit chunk offsets straight from manifest bytes and converts them to Go `int`: [1](#0-0) 

`chunkOffsetInFile` and `nextChunkOffsetInFile` are computed via `int(binary.BigEndian.Uint64(...))`. If the attacker-supplied `uint64` value exceeds `math.MaxInt64`, this conversion wraps around to a negative `int`. The subsequent bounds check `chunkOffsetInFile > dataEnd || nextChunkOffsetInFile > dataEnd || nextChunkOffsetInFile < chunkOffsetInFile` does **not** reject negative values — a negative offset is trivially `<= dataEnd`, so the check passes even though the offset is invalid, exactly mirroring the reported bug class where a boundary value that should be rejected is instead treated as valid due to insufficient range checking.

The resulting bogus (negative) `manifestChunk.offset` then flows into `ParseManifest`, where it is used directly as a slice bound: [2](#0-1) [3](#0-2) 

`data[start : start+pw]` or `data[objsChunk.offset : objsChunk.offset+4]` with a negative `start`/`offset` triggers a Go runtime panic (`slice bounds out of range`), crashing the goroutine handling the RPC.

This manifest data is not developer-controlled: it is fetched from object storage and parsed during ordinary RPC handling. `LocalCache.prepare` → `prepareManifestFile` reads the manifest bytes (either from local cache or via `ObjectStorage.ReadManifest`) and calls `ParseManifest` directly: [4](#0-3) 

The manifest hash used to locate the manifest file, and by extension the manifest's `PrepareWithManifest` path, can be supplied via RPC metadata (e.g., from Gitaly hooks / an RPC request), and manifests referenced there are treated as trusted input once fetched — but nothing here cryptographically or structurally guarantees the manifest bytes are well-formed beyond the checksum, and the checksum does not protect against a maliciously-crafted-but-internally-consistent manifest with out-of-range chunk offsets.

### Impact Explanation
A malformed manifest with an oversized (>`math.MaxInt64`) chunk offset causes an unrecoverable panic inside the goroutine parsing the manifest, during preparation of the MVCC cache for an RPC. Because this occurs in a hot path invoked per-RPC (`Prepare`/`PrepareWithManifest` → `prepare` → `prepareManifestFile` → `ParseManifest`), a crafted manifest is a denial-of-service vector against the Gitaly process/RPC handler, consistent with the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
Exploitability depends on how manifests enter the durable object storage and whether attacker-influenced writes (e.g. through the mutator RPC path that later calls `putNewArtifacts`/`ParseManifest` on newly committed manifests, or an actor able to reach `PrepareWithManifest` with an arbitrary hash) can place a crafted binary file at the expected manifest path. The checksum (SHA-256 trailer) only verifies the manifest wasn't altered after creation — it does not validate internal semantic correctness of chunk offsets, so a manifest generator bug or any path that lets Gitaly compute a checksum over attacker-supplied bytes (e.g., during a mutator RPC that writes its own manifest, later read back via `putNewArtifacts`) is sufficient to trigger the crash.

### Recommendation
In `parseChunks` (internal/git/mvcc/manifest.go), validate `chunkOffsetInFile` and `nextChunkOffsetInFile` for non-negativity before comparing them to `dataEnd`, e.g., reject the manifest if either value is `< 0` (post-conversion) or explicitly bound-check the raw `uint64` against `math.MaxInt` before converting. Apply the same defensive check to all offset/size fields derived from external binary input in this file (`objStart`, `objCount`, `pathChunk.offset`, `refsChunk.offset`) to guard against overflow-driven boundary bypasses, matching the referenced remediation pattern of validating both the lower and upper bound of any externally supplied index/offset.

### Proof of Concept
1. Construct a manifest binary with a valid header/magic/version and a TOC entry whose 8-byte big-endian offset field encodes a value greater than `math.MaxInt64` (e.g., `0xFFFFFFFFFFFFFFFF`).
2. Compute and append the correct trailing SHA-256 checksum over the crafted payload so `ParseManifest`'s checksum validation passes.
3. Place this file where `LocalCache.prepareManifestFile` will read it (as the manifest referenced by a hash passed to `Prepare`/`PrepareWithManifest`, or fetched via `ObjectStorage.ReadManifest`).
4. Trigger an RPC that calls `Cache.Prepare`/`PrepareWithManifest`, causing `ParseManifest` to run; the `int(uint64)` conversion wraps to a negative offset, the bounds check in `parseChunks` passes, and the later slice operation on `data` panics, crashing the handling goroutine.

func (m *LocalCache) prepareManifestFile(ctx context.Context, hash string) (manifest *Manifest, err error) {
	// Construct the manifest path
	manifestFilePath := filepath.Join(m.storagePath, m.repositoryID, mvccCacheDir, "manifests", hash)

	// Verify if it already exists on the local filesystem or not
	existLocally, err := fileExist(manifestFilePath)
	if err != nil {
		return nil, fmt.Errorf("check if file exists: %w", err)
	}

	if !existLocally {
		// If it does not exist, read content from ObjectStorage
		manifestReader, err := m.rs.ReadManifest(ctx, m.repositoryID, hash)
		if err != nil {
			return nil, fmt.Errorf("read manifest file: %w", err)
		}

		defer func() {
			closeErr := manifestReader.Close()
			err = errors.Join(err, closeErr)
		}()

		// Create the manifest file on the local file system atomically. This is a protection against
		// potential concurrent requests trying to create the same manifest file.
		if err = createFileAtomic(ctx, manifestFilePath, manifestReader); err != nil {
			return nil, fmt.Errorf("write manifest: %w", err)
		}
	}

	// Now that it exist on disk, let's open the file.
	manifestFile, err := os.Open(manifestFilePath)
	if err != nil {
		return nil, fmt.Errorf("opening manifest %s: %w", manifestFilePath, err)
	}

	// Read the content in memory. These files should not be that large.
	// The Manifest parsing logic needs the whole file at once to parse it.
	manifestContent := bytes.Buffer{}
	_, err = manifestContent.ReadFrom(manifestFile)
	if err != nil {
		return nil, fmt.Errorf("reading manifest: %w", err)
	}

	// Return the parsed manifest
	return ParseManifest(manifestContent.Bytes())
}
