### Title
Front-runnable, permanent account-ID squatting via `SetAccountIdContract` enables account-resolution hijacking - (File: `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
`SetAccountIdActuator` lets any account owner bind an arbitrary, attacker-chosen byte string (`accountId`) to their address exactly once, with global uniqueness enforced only by first-write-wins in `AccountIdIndexStore`. This is structurally identical to the reported `SpokeCommon.createAccount` bug: a user-supplied identifier with no ownership/format binding to the caller, checked for prior existence but not reserved, race-won by whoever lands on-chain first.

### Finding Description
`SetAccountIdActuator.validate()` only checks that the caller's own account has no `accountId` yet and that the requested `accountId` is not already present in `AccountIdIndexStore`: [1](#0-0) 

There is no mechanism tying the `accountId` value to the caller (no hash-of-address-and-nonce, no reservation/commit-reveal). Because pending transactions are visible in the mempool before confirmation, any unprivileged transaction broadcaster can observe a victim's `SetAccountIdContract` and submit their own `SetAccountIdContract` with the identical `accountId` (matching is case-insensitive, see `AccountIdIndexStore.getLowerCaseAccountId`) targeting the attacker's own address, with higher fee/priority to be included first: [2](#0-1) 

Once the attacker's transaction lands, `accountIdIndexStore.put()` binds that `accountId` to the attacker's address permanently. Critically, `SetAccountIdActuator` has no update/unset path — an account may only ever set its `accountId` once ("This account id already set"): [3](#0-2) 

The victim's original transaction then permanently fails with "This id has existed", exactly mirroring the report's scenario where the legitimate transaction is doomed to fail after the attacker's front-run, except here the squatted identifier can never be reclaimed by anyone — it is bound to the attacker forever.

The `accountId` is not a cosmetic label: it is the lookup key for the `GetAccountById` HTTP query API (and equivalent gRPC/JSON-RPC paths), which external systems (e.g., exchanges) use to resolve a user-chosen ID to an on-chain address: [4](#0-3) 

If an off-chain integrator pre-arranges an `accountId` with a user (e.g., to attribute deposits) and the attacker front-runs the `SetAccountIdContract`, any subsequent `GetAccountById` lookup for that ID will resolve to the attacker's address instead of the victim's, permanently — enabling misattribution/redirection of value tied to that identifier resolution, with no recovery path.

### Impact Explanation
- The victim's transaction fails and its bandwidth/energy fee is wasted (griefing), matching the report class.
- Beyond griefing, because the binding is *permanent and irreversible*, the attacker can squat any observed pending `accountId` cheaply, permanently denying that identifier to the legitimate owner and causing any system that resolves accounts by `accountId` (via `GetAccountById`) to be permanently misdirected to the attacker's address — a concrete unauthorized account-identity hijack with no on-chain remediation.
- Attack cost is a single low-fee `SetAccountIdContract` transaction (`calcFee()` returns 0): [5](#0-4) 

### Likelihood Explanation
Likelihood is high for any `accountId` value that becomes predictable/observable before confirmation (mempool visibility, or off-chain pre-agreement of a human-readable ID with a service). Any unprivileged network participant can execute the front-run with a standard signed transaction; no privileged role or witness/SR compromise is required.

### Recommendation
Do not allow the caller to freely choose a globally-unique `accountId` without binding it to the caller's identity. Options:
- Derive/require `accountId` to include or be derived from the owner's address (e.g., hash of address + nonce), preventing pure squatting by unrelated addresses.
- Add a commit-reveal scheme for `accountId` registration so the value is not revealed in plaintext before confirmation.
- Alternatively, allow an account to update/release a previously-set `accountId` under owner permission checks, mitigating the "permanent" aspect of the squat, and reject case-insensitive collisions consistently across both check and index paths.

### Proof of Concept
Conceptual PoC (mirrors the reported bridge PoC), no code execution performed against this repo:
1. Victim broadcasts `SetAccountIdContract{ownerAddress: victim, accountId: "MY-ID"}`.
2. Attacker observes the pending transaction in the mempool (or is told the target ID out-of-band before confirmation) and broadcasts `SetAccountIdContract{ownerAddress: attacker, accountId: "MY-ID"}` with a higher fee/priority.
3. Attacker's transaction is confirmed first; `AccountIdIndexStore.put` binds `"my-id"` → attacker's address.
4. Victim's transaction is applied later, `validate()` throws `"This id has existed"` (`SetAccountIdActuator.java:94-96`) — victim's tx fails permanently, and `accountId` is unrecoverably bound to the attacker.
5. Any caller of `GET /wallet/getaccountbyid?account_id=MY-ID` (`GetAccountByIdServlet.java:21-50`) now resolves to the attacker's account instead of the victim's.

```java
  private static byte[] getLowerCaseAccountId(byte[] bsAccountId) {
    return ByteString
        .copyFromUtf8(ByteString.copyFrom(bsAccountId).toStringUtf8().toLowerCase(Locale.ROOT))
        .toByteArray();
  }

  public void put(AccountCapsule accountCapsule) {
    byte[] lowerCaseAccountId = getLowerCaseAccountId(accountCapsule.getAccountId().toByteArray());
    super.put(lowerCaseAccountId, new BytesCapsule(accountCapsule.getAddress().toByteArray()));
  }
```
