### Title
Front-runnable, unbounded-slippage liquidity injection/withdrawal in the TRC10 Bancor-formula Exchange contracts - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract` and `ExchangeWithdrawContract` (the on-chain AMM liquidity add/remove operations for java-tron's TRC10 "Exchange" market) carry no minimum/maximum bound on the counter-token amount computed at execution time, unlike the sibling `ExchangeTransactionContract` (swap), which explicitly has an `expected` field. A trade transaction (`ExchangeTransactionContract`), which any unprivileged account can freely submit against the same pool, can be used to shift the pool's reserve ratio between the time the exchange creator submits an inject/withdraw transaction and the time it executes, causing the creator to deposit/receive an amount of the counter-token wildly different from what they intended — an unbounded, front-runnable loss identical in class to the reported Multipool "H-4" issue.

### Finding Description
`ExchangeInjectActuator.execute()` computes the second (paired) token amount purely from the exchange's live reserve balances at execution time: [1](#0-0) 

The contract itself provides no way for the caller to bound this derived amount — `ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant`: [2](#0-1) 

Compare this with `ExchangeTransactionContract`, which has an `expected` field, and whose actuator enforces `anotherTokenQuant < tokenExpected` as an explicit slippage guard: [3](#0-2) [4](#0-3) 

No equivalent check exists for `ExchangeInjectActuator` or `ExchangeWithdrawActuator` — their validation only rejects zero/negative results or balance-limit overflow, never an unexpected magnitude: [5](#0-4) 

Crucially, the reserve ratio these actuators rely on can be freely and cheaply manipulated by *any* account, because `ExchangeTransactionActuator` (the swap) has no access restriction (unlike Inject/Withdraw, which require the caller to be the exchange creator) and directly mutates `firstTokenBalance`/`secondTokenBalance` via the bancor-formula processor: [6](#0-5) 

This is structurally the same bug class as the referenced Multipool H-4 finding: a liquidity-provision transaction that only bounds one side of the deposit/withdrawal (here, `quant` of one token) and lets an unbounded amount of the other token be computed from a reserve ratio that an unprivileged actor can move immediately beforehand.

### Impact Explanation
An attacker can sandwich the exchange creator's `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction:
1. Front-run with an `ExchangeTransactionContract` swap that skews `firstTokenBalance`/`secondTokenBalance` in the attacker's favor.
2. The victim's inject transaction then executes against the manipulated ratio, forcing them to contribute (and have deducted via `reduceAssetAmountV2`) far more of the counter-token than intended — or, for withdrawal, receive far less than intended.
3. Back-run to restore the ratio and realize the extracted value.

Because there is no user-specified bound anywhere in the protobuf message, the loss is unbounded (limited only by the victim's account balance / the exchange balance cap), matching the "funds at loss are unbounded" reasoning that got the original Sherlock issue accepted as High.

### Likelihood Explanation
`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` are all ordinary broadcastable transactions reachable by any signed account — no special/SR privilege is required to create an exchange, inject/withdraw as its creator, or trade against it as an attacker. Reordering/front-running within the same block or across adjacent blocks is a standard MEV technique and requires no protocol-level exploit, only submitting a competing transaction with the desired ordering.

### Recommendation
Add a slippage-bound field (e.g., `expected_another_token_min`/`max`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` the same way `tokenExpected` is enforced in `ExchangeTransactionActuator`, so the creator can bound the counter-token amount at submission time and reject execution if the live ratio has moved unfavorably.

### Proof of Concept
1. Alice creates an exchange (`ExchangeCreateContract`) for TRX/TokenA with balanced reserves and becomes its creator.
2. Alice submits `ExchangeInjectContract{exchange_id, token_id=TRX, quant=X}` intending to add liquidity at the current ratio (she expects roughly `Y` TokenA to be deducted).
3. Bob (any unprivileged account) submits an `ExchangeTransactionContract` swap against the same exchange to shift `firstTokenBalance`/`secondTokenBalance`, ordered before Alice's inject transaction (front-run).
4. Alice's inject transaction executes: `ExchangeInjectActuator.execute()` recomputes `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` (see lines 73-80) using the now-skewed balances, deducting a TokenA amount far greater than `Y` from Alice's account via `reduceAssetAmountV2`, with no on-chain check preventing this since `ExchangeInjectContract` has no expected/min field.
5. Bob submits a reverse `ExchangeTransactionContract` swap to restore the ratio, capturing the value effectively extracted from Alice's liquidity injection.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
