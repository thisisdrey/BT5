### Title
Unbounded array allocation from attacker-controlled length word in TVM precompile decoders can trigger `OutOfMemoryError` DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2024-49776 bug class is "an attacker-controlled size/length field is used directly to allocate a buffer, causing a crash." The analogous reachable path in java-tron is the ABI-array decoding helpers used by the `ValidateMultiSign`/`BatchValidateSign` precompiled contracts, which take a length word straight from calldata and use it to size a Java array with no upper-bound check.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` all read a length field from attacker-supplied `DataWord[]` (decoded directly from TVM call `data`) via `intValueSafe()` and immediately allocate an array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

`DataWord.intValueSafe()` only clamps out-of-range values to `Integer.MAX_VALUE`; it never rejects them: [4](#0-3) 

So a crafted calldata word (e.g. `0xFFFFFFFF...` or any value occupying more than 4 bytes) decodes to `len = Integer.MAX_VALUE`, and `new byte[len][]` attempts to allocate an object-reference array of ~2^31 entries (multi-GB), throwing `OutOfMemoryError`. Note also that `extractBytes32Array` is missing the `offset > words.length - 1` guard present in the other two helpers, so it can also throw an unguarded `ArrayIndexOutOfBoundsException` on `words[offset]`.

### Impact Explanation
`OutOfMemoryError` is a JVM `Error`, not an `Exception`. Depending on where it propagates in the TVM's contract-call dispatch, a bare `catch (Throwable)`/`catch (Exception)` around precompile execution may or may not contain it before it corrupts the node's heap state or forces JVM-wide GC thrashing, degrading or crashing node availability for all users on that node — this is reachable by any account issuing a single crafted transaction that calls the `ValidateMultiSign`/`BatchValidateSign` precompiled contract address with a malformed length word, i.e. exactly the "unprivileged transaction broadcaster/contract deployer" threat model in scope.

### Likelihood Explanation
I could not, within the available tool budget, confirm the exact catch/try boundary around `PrecompiledContract.execute()` in the VM dispatch loop (`OperationActions.java` / `Program.java`) to determine definitively whether the resulting `OutOfMemoryError` is swallowed (reverting only the transaction) or propagates to crash the node thread/process. This is a material gap: if the surrounding VM call frame catches `Throwable` broadly, the practical impact is limited to a failed/reverted transaction (energy-exhaustion-only, out of scope per the rules), not a node crash. Given this uncertainty, I cannot confidently assert the "node crash or halt" impact bar is met with certainty from static review alone.

### Recommendation
Add explicit upper bounds and non-negativity validation on all length/offset words decoded from precompile calldata (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) before using them to size arrays — reject values that exceed the maximum plausible element count derivable from `data.length`/`words.length`, similar to the bounds checks already present in `ContractEventParser.subBytes` and `RLP.verifyLength`. Also add the missing `offset > words.length - 1` guard to `extractBytes32Array` for consistency with its sibling methods.

### Proof of Concept
Craft a transaction that calls the `ValidateMultiSign` (or `BatchValidateSign`) precompiled contract address with calldata where the array-length word at the expected `offset` is set to a value whose big-endian byte representation occupies more than 4 significant bytes (e.g. `0x00000000000000000000000000000000000000000000010000000000000000`). `words[offset].intValueSafe()` clamps this to `Integer.MAX_VALUE`, and the subsequent `new byte[Integer.MAX_VALUE][]` in `extractBytes32Array`/`extractBytesArray`/`extractSigArray` attempts a multi-gigabyte allocation, throwing `OutOfMemoryError` during precompile execution triggered by the transaction.

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
