## Title
Admin interest-rate reconfiguration retroactively misapplies the new rate to interest already accrued under the old rate - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`, `programs/marginfi/src/instructions/marginfi_group/configure_bank_lite.rs`)

### Summary
Both `lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only` mutate `bank.config.interest_rate_config` directly, without first calling `accrue_interest` to checkpoint the bank's `asset_share_value`/`liability_share_value` up to the current timestamp. This is the same bug class as the CloneRewarderTime `setRewardPerSecond` report: a rate change is applied without first settling the accumulator ("accToken1PerShare" analog is `asset_share_value`/`liability_share_value`, gated by `last_update`).

### Finding Description
`lending_pool_configure_bank` calls `bank.configure(&bank_config)` directly [1](#0-0) , and `lending_pool_configure_bank_interest_only` calls `bank.config.interest_rate_config.update(...)` directly [2](#0-1) . Neither path calls `Bank::accrue_interest` beforehand.

Compare this to other admin-triggered state mutations in the same file that correctly checkpoint interest first, e.g. `lending_pool_emissions_deposit` explicitly calls `bank.accrue_interest(...)` before mutating share values [3](#0-2) .

`Bank::accrue_interest` computes `time_delta` as `current_timestamp - self.last_update` and applies the *current* `interest_rate_config` curve over that entire delta the next time any user interacts with the bank [4](#0-3) . Because `configure`/`configure` for interest params never advances `last_update` or accrues interest first, any time elapsed between the last accrual and the admin's rate change is silently re-priced using the *new* rate instead of the rate that was actually in effect during that period — exactly analogous to CloneRewarderTime's `setRewardPerSecond` not calling `updatePool` first.

### Impact Explanation
Since `time_delta` spans from `last_update` to whenever the next accrual-triggering instruction runs (deposit/withdraw/borrow/repay/liquidate), and the entire delta is priced with the *post-change* curve, users are exposed to retroactive re-pricing of interest for periods where the old rate should have applied:
- If the admin sets a lower `zero_util_rate`/`hundred_util_rate`/points curve (or effectively zero), depositors lose interest that had already economically accrued at the old rate, matching the "users may lose their pending rewards" impact in the source report.
- If the admin raises the rate, borrowers are retroactively overcharged interest (and protocol/insurance fees, which are derived from the same accrual pass) for time elapsed under the old, lower rate — see fee logic in `accrue_interest` [5](#0-4) .

This affects `asset_share_value`/`liability_share_value` for every depositor and borrower in the bank, i.e. core accounting state, not just an isolated account.

### Likelihood Explanation
This triggers whenever the admin (`admin` or `delegate_curve_admin`) reconfigures a bank's interest rate parameters and any material time has passed since the bank's `last_update` (which happens naturally between transactions, especially for banks with sparse activity, as documented: "Interest accumulates when any transaction that changes funds occurs, so banks without much activity may have stale numbers until someone interacts with them" [6](#0-5) ). No malicious intent is required — this is a routine risk-management/curve-update action that unintentionally mis-prices already-elapsed time. The instructions themselves show no guard requiring an accrual pass first [2](#0-1) .

### Recommendation
In `lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only`, call `bank.accrue_interest(Clock::get()?.unix_timestamp, &group, ...)` (and `update_bank_cache`) before applying the new `interest_rate_config`, so `last_update`/share values are checkpointed under the old curve before the new curve takes effect — mirroring the pattern already used in `lending_pool_emissions_deposit`.

### Proof of Concept
1. Bank has active deposits/borrows; `last_update = T0` with curve C1.
2. Time passes to `T1` with no accrual-triggering transaction (bank is stale).
3. Admin calls `lending_pool_configure_bank_interest_only` at `T1`, setting curve C2 (e.g., much lower rate or `zero_util_rate = 0`). This only mutates `bank.config.interest_rate_config`; `last_update` is still `T0` [7](#0-6) .
4. A user deposits/withdraws at `T2 > T1`, triggering `accrue_interest`, which computes `time_delta = T2 - T0` and applies curve C2 (not C1) over the entire `[T0, T2]` window [8](#0-7) .
5. Depositors/borrowers receive interest/fees computed as if C2 had been in effect for the whole `[T0, T1]` sub-period, even though C1 was actually the governing rate, resulting in incorrect share-value updates for that stale window.

```rust
pub fn lending_pool_configure_bank_interest_only(
    ctx: Context<LendingPoolConfigureBankInterestOnly>,
    interest_rate_config: InterestRateConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    msg!(
        "Configuring bank: {:?} mint: {:?}",
        ctx.accounts.bank.key(),
        bank.mint
    );

    // If settings are frozen, interest rates can't update.
    if bank.get_flag(FREEZE_SETTINGS) {
        msg!("WARN: Bank settings frozen, did nothing.");
    } else {
        bank.config
            .interest_rate_config
            .update(&interest_rate_config);
        bank.config.interest_rate_config.validate()?;
        msg!("Bank configured!");
    }

    Ok(())
}
```

```rust
    fn accrue_interest(
        &mut self,
        current_timestamp: i64,
        group: &MarginfiGroup,
        #[cfg(not(feature = "client"))] bank: Pubkey,
    ) -> MarginfiResult<()> {
        #[cfg(all(not(feature = "client"), feature = "debug"))]
        sol_log_compute_units();

        let time_delta: u64 = (current_timestamp - self.last_update).try_into().unwrap();
        if time_delta == 0 {
            return Ok(());
        }

        let total_assets = self.get_asset_amount(self.total_asset_shares.into())?;
        let total_liabilities = self.get_liability_amount(self.total_liability_shares.into())?;

        self.last_update = current_timestamp;

        if (total_assets == I80F48::ZERO) || (total_liabilities == I80F48::ZERO) {
            #[cfg(not(feature = "client"))]
            emit!(LendingPoolBankAccrueInterestEvent {
                header: GroupEventHeader {
                    marginfi_group: self.group,
                    signer: None
                },
                bank,
                mint: self.mint,
                delta: time_delta,
                fees_collected: 0.,
                insurance_collected: 0.,
            });

            return Ok(());
        }
        let ir_calc = self
            .config
            .interest_rate_config
            .create_interest_rate_calculator(group);

        let InterestRateStateChanges {
            new_asset_share_value: asset_share_value,
            new_liability_share_value: liability_share_value,
            insurance_fees_collected,
            group_fees_collected,
            protocol_fees_collected,
        } = calc_interest_rate_accrual_state_changes(
            time_delta,
            total_assets,
            total_liabilities,
            &ir_calc,
            self.asset_share_value.into(),
            self.liability_share_value.into(),
        )?;
```
