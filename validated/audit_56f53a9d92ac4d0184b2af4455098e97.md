### Title
Unauthenticated API request causes unhandled `IndexOutOfBoundsException` in `ShieldedTRC20ParametersBuilder.mintParamsToHexString` via `Wallet.getTriggerInputForShieldedTRC20Contract` - ([File: framework/src/main/java/org/tron/core/zen/ShieldedTRC20ParametersBuilder.java])

### Summary
`Wallet.getTriggerInputForShieldedTRC20Contract` accepts a fully client-controlled `ShieldedTRC20Parameters` protobuf message (including its `receiveDescription`/`spendDescription` repeated fields) via the gRPC `GetTriggerInputForShieldedTRC20Contract` RPC and the equivalent HTTP servlet, and forwards it to `ShieldedTRC20ParametersBuilder.getTriggerContractInput(...)`, which dispatches by `parameterType` string to `mintParamsToHexString`, `transferParamsToHexString`, or `burnParamsToHexString`.

### Finding Description
`mintParamsToHexString` unconditionally calls `mintParams.getReceiveDescription(0)` [1](#0-0)  without first checking that `getReceiveDescriptionList()` is non-empty, unlike the sibling `burnParamsToHexString`, which does guard on `getReceiveDescriptionList().size() == 0` before calling `getReceiveDescription(0)` [2](#0-1) .

`Wallet.getTriggerInputForShieldedTRC20Contract` takes the `shieldedTRC20Parameters` field straight out of the untrusted `ShieldedTRC20TriggerContractParameters` request and only special-cases and validates fields when `parameterType == BURN` (checking `getSpendDescriptionList().size() != 1`, burn-cipher length, nonce, etc.) [3](#0-2) . For any other declared `parameterType` (e.g. `MINT`), no equivalent validation of `receiveDescription`/`spendDescription` list sizes is performed before the unconditional call to `parametersBuilder.getTriggerContractInput(...)` [4](#0-3) , which for `MINT` type routes to `mintParamsToHexString` [5](#0-4) .

Because the entire `ShieldedTRC20Parameters` object (including its repeated `receive_description`/`spend_description` fields) originates from the RPC/HTTP request body and is deserialized via `JsonFormat.merge`/protobuf parsing with no server-side enforcement of non-empty lists for the MINT path, an attacker can submit `parameterType="MINT"` with an empty `receive_description` list, causing `getReceiveDescription(0)` to throw `IndexOutOfBoundsException` deep inside builder logic.

### Impact Explanation
This directly mirrors the reported bug class (CWE-129, out-of-bounds slice/list access reachable from an unauthenticated/unprivileged API request causing a server-side runtime exception). The endpoint is reachable via the public gRPC `GetTriggerInputForShieldedTRC20Contract` RPC and the HTTP `GetTriggerInputForShieldedTRC20ContractServlet`, requiring only that shielded-transaction APIs be enabled (`checkAllowShieldedTransactionApi()`), not any privileged role. Repeated submission of malformed requests can be used to trigger repeated exceptions/log flooding on this API path, degrading availability of the shielded contract trigger-input endpoint — analogous to the CHF recharge panic described in the report. I was not able to fully confirm from the available index whether the top-level gRPC/HTTP handlers wrap this call in a catch-all that converts the exception into a normal error response (which would reduce impact to a benign 500-style error) or whether it propagates unhandled; the grep results show the RPC and servlet call sites exist but I could not retrieve their full exception-handling bodies within the tool budget.

### Likelihood Explanation
High: it requires a single unauthenticated (or minimally authenticated, subject only to `checkAllowShieldedTransactionApi`) JSON/gRPC request with a crafted `ShieldedTRC20Parameters.parameterType = "MINT"` and empty `receive_description` list — no special privileges, valid signatures, or on-chain state are needed to reach the vulnerable code path.

### Recommendation
Add an explicit size check in `mintParamsToHexString` (and any other `getX(0)`-style accessors on client-supplied repeated fields) mirroring the guard already present in `burnParamsToHexString`, e.g. reject the request with a `ZksnarkException`/`ContractValidateException` if `mintParams.getReceiveDescriptionList().isEmpty()`. More generally, validate `parameterType`-specific list-size invariants for all three types (`MINT`, `TRANSFER`, `BURN`) inside `Wallet.getTriggerInputForShieldedTRC20Contract` before dispatching to `getTriggerContractInput`, not only for `BURN`.

### Proof of Concept
1. Send a gRPC `GetTriggerInputForShieldedTRC20Contract` request (or the equivalent HTTP POST to the trigger-input servlet) with:
   - `shieldedTRC20Parameters.parameterType = "MINT"`
   - `shieldedTRC20Parameters.receiveDescription` = empty (omitted)
   - `amount` set to any valid positive value string
   - `transparentToAddress` empty or omitted
2. The request bypasses the BURN-specific validation block in `Wallet.getTriggerInputForShieldedTRC20Contract` (since `parameterType != BURN`) and proceeds directly to `parametersBuilder.getTriggerContractInput(...)`.
3. `mintParamsToHexString` calls `mintParams.getReceiveDescription(0)` on the empty list, throwing `IndexOutOfBoundsException`.

Note: I could not verify within the available tool budget whether this exception is caught generically at the gRPC/HTTP boundary (in `RpcApiService`/`GetTriggerInputForShieldedTRC20ContractServlet`) and converted into a normal error response, or whether it surfaces as an unhandled server error; this affects whether the concrete impact is "clean error response" vs. "unhandled exception/log flood," but the out-of-bounds root cause itself is confirmed in the source.

  private String mintParamsToHexString(GrpcAPI.ShieldedTRC20Parameters mintParams,
      BigInteger value) {
    if (value.compareTo(BigInteger.ZERO) <= 0) {
      throw new IllegalArgumentException("require the value be positive");
    }

    ShieldContract.ReceiveDescription revDesc = mintParams.getReceiveDescription(0);
    byte[] zeros = new byte[12];
    byte[] mergedBytes = ByteUtil.merge(
        ByteUtil.bigIntegerToBytes(value, 32),
        revDesc.getNoteCommitment().toByteArray(),
        revDesc.getValueCommitment().toByteArray(),
        revDesc.getEpk().toByteArray(),
        revDesc.getZkproof().toByteArray(),
        mintParams.getBindingSignature().toByteArray(),
        revDesc.getCEnc().toByteArray(),
        revDesc.getCOut().toByteArray(),
        zeros
    );
    return Hex.toHexString(mergedBytes);
  }
