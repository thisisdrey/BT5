Audit Report

## Title
`submit_delivery_receipt` pays the full relayer fee regardless of message delivery outcome - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The Snowbridge V2 outbound queue's `process_delivery_receipt` function pays the full relayer fee for any nonce with a valid `PendingOrder`, without ever inspecting the `success` field of the decoded `DeliveryReceipt`. This allows a relayer to be paid in full even when the underlying message execution on Ethereum failed (`success = false`).

## Finding Description
`DeliveryReceipt` decodes the on-chain Ethereum event `InboundMessageDispatched(nonce, topic, success, reward_address)`, explicitly carrying a `success: bool` field [2](#0-1) .

The public, unprivileged extrinsic `submit_delivery_receipt` (`ensure_signed` only) verifies the event log is included in a valid Ethereum receipt via `T::Verifier::verify`, decodes it into a `DeliveryReceipt`, and forwards it directly to `process_delivery_receipt` without ever checking `success` [3](#0-2) .

`process_delivery_receipt` looks up the `PendingOrder` by `nonce`, and if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward` for the full fee before removing the order via `<PendingOrders<T>>::remove(nonce)` — `receipt.success` is never read [4](#0-3) .

The module-level documentation states the intended flow is that reward payment should happen "when the message has been verified **and executed**", implying the reward should be conditioned on successful execution, not merely on proof of an event occurring [5](#0-4) . Existing guards (`T::Verifier::verify`, `GatewayAddress` check, `PendingOrders` lookup) only confirm the event genuinely happened and originated from the correct Gateway contract and a known nonce — none of them are related to the actual delivery outcome encoded in `success`.

This is corroborated by the integration/unit tests in the repository, all of which construct `DeliveryReceipt` with `success: true` and never exercise the `success: false` path, confirming that no code distinguishes the two cases [6](#0-5) .

## Impact Explanation
This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A relayer (or anyone submitting a valid receipt with `reward_address` pointing to themselves) can be paid the full `order.fee` for a message whose execution on Ethereum failed, draining the reward pot funded by users for work that produced no successful delivery, and the `PendingOrder` is permanently removed, precluding retry or reconciliation. This matches the "duplicate settlement or payout" / "theft or unbacked... payout" class of impact under the Polkadot SDK Impact Gate.

## Likelihood Explanation
`submit_delivery_receipt` is a fully public extrinsic requiring only `ensure_signed`, with no relayer allowlist. The only requirement is a genuine, provable `InboundMessageDispatched` event with `success = false`, which is a normal outcome that can occur naturally (e.g., a command execution reverting due to insufficient gas or a failure-prone destination command) and does not require collusion with governance, validators, or the bridge operator — making this readily reachable by any relayer.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` before crediting the reward. On `success == false`, withhold or reduce the reward and/or route the order to a distinct failure-handling path (e.g., re-queue for retry or refund only a base delivery cost), instead of paying the full fee and unconditionally removing the order as if delivery succeeded.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders[nonce] = { fee, block_number }` [7](#0-6) .
2. On Ethereum, the corresponding command execution fails, so the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any account submits `submit_delivery_receipt` with a valid Merkle/receipt proof for this real (but `success=false`) event; `T::Verifier::verify` succeeds because the event genuinely occurred.
4. `DeliveryReceipt::try_from` decodes `success = false`, but `process_delivery_receipt` never inspects it [8](#0-7) .
5. `order.fee > 0` triggers `T::RewardPayment::register_reward(&reward_account, ..., order.fee)` and `<PendingOrders<T>>::remove(nonce)` deletes the order — the relayer is fully paid despite the failed delivery, and this outcome is unrecoverable.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
