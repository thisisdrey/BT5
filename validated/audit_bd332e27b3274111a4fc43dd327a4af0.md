### Title
Dangling `PromiseYieldReceipt`/`PromiseYieldStatus` survive `remove_account`, enabling resurrection of an attacker's yielded receipt (with attacker-embedded actions) on a recreated account - (core/store/src/utils/mod.rs, runtime/runtime/src/ext.rs)

### Summary
`remove_account` deletes an account's `Account`, `ContractCode`, access keys, gas keys, and contract data, but never removes the account's `PromiseYieldReceipt`, `PromiseYieldStatus`, or `YieldIdToDataId`/`DataIdToYieldId` entries. Because these trie keys are namespaced only by the raw `AccountId` string (with no per-account "generation"/creation nonce), a malicious former owner of an account can leave behind a yielded promise whose attached actions execute with the authority of whoever later re-creates that same account name.

### Finding Description
`submit_promise_resume_data` (`runtime/runtime/src/ext.rs:402-426`) authorizes resuming a yield purely by checking `has_promise_yield_receipt(...)` and `has_promise_yield_status(...)` keyed on `self.account_id` (the account currently executing, i.e. the receiver of the yielded promise) and the caller-supplied `data_id`: [1](#0-0) 

Before this can ever return `true`, an attacker must have previously, while they legitimately owned `victim.near`, called `promise_yield_create`, which stores an `ActionReceiptMetadata{ is_promise_yield: true, receiver_id: "victim.near", actions: [...] }` and persists it via `set_promise_yield_receipt`/`set_promise_yield_status`: [2](#0-1) 

Actions can be attached to this pending receipt the same way as any other batched action receipt (`append_action_add_key_with_full_access`, `append_action_transfer`, `append_action_delete_account`, etc.), since `create_promise_yield_receipt` returns a normal `ReceiptIndex`: [3](#0-2) 

The attacker never resolves the yield, then deletes `victim.near` via a `DeleteAccountAction`, recovering its balance. `remove_account` is invoked as part of that deletion, but it only clears the account record, code, keys, and contract data — it never calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or `remove_yield_id_mappings`: [4](#0-3) 

Compare against the removal helpers that do exist for exactly this state but are unused here: [5](#0-4) [6](#0-5) 

Once a new, unrelated owner registers `victim.near` again and deploys a new contract, the stale `PromiseYieldReceipt`/`PromiseYieldStatus` entries are still addressable under that exact `AccountId` key because there is no generation counter distinguishing "old victim.near" from "new victim.near." If the pending yield is ever resumed for the known `data_id` — either because the new owner's contract itself calls `promise_yield_resume(data_id, ...)` with a value that happens to match (e.g., blindly forwarding caller-supplied ids), the resurrected receipt's attacker-authored actions (`AddKey` with full access, `Transfer`, `DeleteAccount` with attacker as beneficiary, etc.) execute against the new account with the same unrestricted authority any self-originated action receipt has (no access-key check, since these are not transactions but already-materialized action receipts). This effectively lets the attacker's dangling receipt hijack or drain the new owner's account.

No existing check in `submit_promise_resume_data`, `remove_account`, or the yield/timeout bookkeeping verifies that the account addressed by `data_id` is the same "generation" of the account that originally created the yield.

### Impact Explanation
This is an authorization-exactness violation across account "generations": privileged actions (e.g., adding a full-access key, transferring funds, or self-deleting with an attacker-controlled beneficiary) planted by a previous, unrelated owner of an account name can execute against the current owner's account and funds — matching NEAR's authorization-escalation / theft-of-funds bounty category.

### Likelihood Explanation
Exploitation requires: (1) the attacker owns the target account name and creates a yielded receipt with malicious attached actions, then deletes the account, cheap and fully within an ordinary user's capability; (2) the account name is later re-registered by a different party; (3) the resume path is triggered for the stale `data_id`. Step 3 is the weak link for the `submit_promise_resume_data` vector specifically — it requires the new owner's own contract to submit resume data using the attacker's `data_id`, which is not attacker-controlled unless the new contract exposes an unguarded `data_id`/`yield_id` parameter to callers. The broader and more directly attacker-triggerable variant (via the timeout-expiration queue, which is populated by account name and is not cleared by `remove_account` either) was identified as a related manifestation of the same root cause but its exact automatic-resolution code path was not fully traced in this session and needs separate confirmation.

### Recommendation
Have `remove_account` also purge promise-yield state for the account: call `remove_promise_yield_receipt`/`remove_promise_yield_status` for any pending yields owned by the account (and remove associated `YieldIdToDataId`/`DataIdToYieldId` mappings), or introduce an account "generation"/creation-nonce component into the `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` trie keys so that state from a prior incarnation of an account cannot be resumed against a later one.

### Proof of Concept
Unit test in `runtime/runtime/src/ext.rs` (or an integration test in `runtime/runtime/src/tests/`):
1. Create `TrieUpdate`, call `create_promise_yield_receipt` for account `"victim.near"`, attach a malicious action (e.g. `AddKey` full access) to the resulting receipt, obtaining `data_id`.
2. Call `remove_account(&mut trie_update, &"victim.near".parse().unwrap())`.
3. Assert `has_promise_yield_status(&trie_update, &"victim.near".parse().unwrap(), data_id)` still returns `true` (demonstrating the bug) instead of `false` (expected/fixed behavior).
4. Extend to a `test-loop` integration test: attacker deletes `victim.near`, a new account is registered under the same name, then either the timeout queue fires or the new contract calls `promise_yield_resume` with the leaked `data_id`; assert the attacker's planted `AddKey`/`Transfer`/`DeleteAccount` action executes against the new account, proving cross-generation privilege escalation.

    fn submit_promise_resume_data(
        &mut self,
        data_id: CryptoHash,
        data: Vec<u8>,
    ) -> Result<bool, VMLogicError> {
        let has_yield_receipt_in_state =
            has_promise_yield_receipt(self.trie_update, self.account_id.clone(), data_id)
                .map_err(wrap_storage_error)?;
        let has_yield_status_in_state =
            has_promise_yield_status(self.trie_update, &self.account_id, data_id)
                .map_err(wrap_storage_error)?;

        if has_yield_receipt_in_state || has_yield_status_in_state {
            self.receipt_manager.create_promise_resume_receipt(data_id, data);
            set_promise_yield_status(
                &mut self.trie_update,
                &self.account_id,
                data_id,
                PromiseYieldStatus::ResumeInitiated,
            );
            return Ok(true);
        }

        Ok(false)
    }

            receiver_id,
            refund_to: None,

            actions: vec![],

        self.promise_yield_receipt_index.insert(input_data_id, new_receipt_index);
        new_receipt_index as ReceiptIndex
    }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
