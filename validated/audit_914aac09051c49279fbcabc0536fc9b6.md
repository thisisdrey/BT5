### Title
Unbounded pre-allocation from attacker-declared array-length words in `PrecompiledContracts.extractBytesArray` / `extractBytes32Array` / `extractSigArray` (legacy pre-`allowTvmSelfdestructRestriction` path) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`BatchValidateSign` (precompile `0x...09`) and `ValidateMultiSign` (precompile `0x...0a`) decode their calldata into a `DataWord[]` and then read an array-length *word* directly from that data to size a Java array with `new byte[len][]`, before any bound is enforced on `len`. The bound check (`MAX_SIZE`) is only applied when the `allowTvmSelfdestructRestriction` hard-fork switch is active; on the legacy code path it is skipped entirely, so `len` (an arbitrary 256-bit attacker value) is used unchecked for allocation. This mirrors the Dulwich flaw: a tiny, attacker-crafted payload declares an oversized "size" field that the ingester uses to allocate memory in proportion to the declared size rather than to the actual bytes received.

### Finding Description
`extractBytes32Array` / `extractBytesArray` / `extractSigArray` read the length purely from calldata: [1](#0-0) 

They are invoked from `ValidateMultiSign.execute` / `BatchValidateSign.doExecute`, where the `MAX_SIZE` (16 for BatchValidateSign, 5 for ValidateMultiSign) sanity check is gated behind `VMConfig.allowTvmSelfdestructRestriction()`: [2](#0-1) [3](#0-2) 

When `allowTvmSelfdestructRestriction()` is `false`, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are called with the length taken from `words[offset].intValueSafe()` with no upper bound at all — `len` can be any value the caller encodes as a 256-bit word (clamped only by `intValueSafe()`'s int range, i.e. up to `Integer.MAX_VALUE`). `new byte[len][]` (an object-reference array) or the subsequent `Arrays.copyOfRange` inside `extractBytes` will attempt to allocate memory sized by that declared value, independent of the actual size of the submitted calldata. The energy charged for the call, `getEnergyForData`, is computed from `data.length` (the actual submitted calldata size), not from the internal declared `len` field: [4](#0-3) 
so a small, cheap calldata payload can encode a huge `len` word and force an allocation attempt vastly out of proportion to the energy actually paid — exactly the "size vs. actual bytes" mismatch at the heart of the referenced CVE.

### Impact Explanation
A single unprivileged `TriggerSmartContract` transaction that calls `batchvalidatesign`/`validatemultisign` with the length word set to a large value (e.g. near `Integer.MAX_VALUE`) can trigger a very large array allocation (`new byte[len][]`, 8 bytes per reference on 64-bit JVM heaps, i.e. potentially multi-GB) inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, executed synchronously inside node/validator TVM execution. This can throw `OutOfMemoryError`, is uncaught by narrow exception handlers in this path, and can crash or destabilize the validating node processing the transaction — a node-crash/DoS condition reachable from a single signed transaction, satisfying CWE-400/CWE-789 resource exhaustion.

### Likelihood Explanation
The precondition (`allowTvmSelfdestructRestriction() == false`) depends on whether that specific hard-fork/committee proposal has been activated on the target network. On networks/chains where this proposal has not yet been switched on (e.g. private/consortium chains freshly deployed from this codebase, or a network at a pre-activation block height), any account able to send a `TriggerSmartContract` transaction calling address `0x...09`/`0x...0a` can trigger the bug with a cheaply-constructed transaction — no special privileges required, only enough TRX to cover the (attacker-controlled, small) declared energy cost.

### Recommendation
Move the array-length bound check (`MAX_SIZE`) out of the `allowTvmSelfdestructRestriction()` conditional and apply it unconditionally before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, and additionally validate declared lengths inside those helper methods against the number of words actually available in `data`/`words` before allocating (`new byte[len][]`), analogous to how git/Dulwich now bounds allocation to actual bytes received rather than the declared size.

### Proof of Concept
1. Ensure/target a java-tron network where `allowTvmSelfdestructRestriction` (see `DynamicPropertiesStore`/`ProposalUtil`) has not been activated.
2. Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign`) where the ABI header offset word for the `bytes[]` array points to a length word containing a very large integer (e.g. `0x7fffffff`) instead of the real element count, while keeping the rest of the calldata minimal.
3. Submit this as a `TriggerSmartContract` transaction calling contract address `0x0000000000000000000000000000000000000009` (BatchValidateSign) via the normal HTTP/gRPC broadcast API.
4. `PrecompiledContracts.BatchValidateSign.doExecute` → `extractBytesArray`/`extractBytes32Array` reads the declared length and executes `new byte[len][]`, attempting a huge allocation disproportionate to the small calldata actually sent and the low energy actually charged, risking `OutOfMemoryError`/node crash during TVM execution of that single transaction.

**Note on verification limits:** I was unable to fully confirm within available tool calls whether `allowTvmSelfdestructRestriction` is unconditionally forced to `true` at genesis/hardcoded for all currently-deployed java-tron networks (which would fully neutralize this path) — this depends on `DynamicPropertiesStore`/`ProposalUtil` default values and per-chain governance state, which I could not fully inspect before running out of iterations. If that flag is guaranteed always-on for the target deployment, this specific analog would be dead code and non-exploitable; a Devin session with full repo access would need to confirm the default/activation status before treating this as immediately exploitable on mainnet.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
