### Title
Permanent lock of eth-implicit Wallet Contract via panicking callback leaving `has_in_flight_tx` stuck `true` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The eth-implicit Wallet Contract (`WalletContract`) serializes all execution through a single boolean flag `has_in_flight_tx`, set to `true` before dispatching any cross-contract promise and reset to `false` only inside the resulting callback. Because NEAR persists state mutations only when a contract call returns without panicking, any code path that lets the callback panic (e.g. gas exhaustion while processing an externally-controlled cross-contract response) discards the in-memory reset and leaves the on-chain flag permanently `true`, exactly mirroring the NFTX bug class where an unprivileged party can permanently lock a shared piece of state that a marketplace-style entry point depends on for every future call.

### Finding Description
`WalletContract::rlp_execute` refuses to start a new operation whenever `has_in_flight_tx` is `true`: [1](#0-0) 

The flag is only cleared inside the `#[private]` callbacks, each of which sets it `false` as their first statement: [2](#0-1) [3](#0-2) 

The intended invariant is documented at the struct definition: [4](#0-3) 

On NEAR, `near-sdk` (`near_bindgen`) only writes the contract's mutated state back to storage if the host call returns normally; if the WASM execution traps for any reason (out-of-gas, unhandled panic, arithmetic overflow, etc.) the entire receipt fails and *all* state changes made during that receipt — including the `has_in_flight_tx = false` assignment that already executed earlier in the same function body — are discarded. The `nep_141_storage_balance_callback` path is reachable whenever the wallet emulates an ERC-20 transfer, and it deserializes and further processes a `StorageBalance` response coming directly from `token_id`, an address fully controlled by whichever contract the wallet is instructed to interact with: [5](#0-4) 

`token_id` can be any NEP-141 contract, including one deployed by an attacker specifically to answer `storage_balance_of` with a payload engineered to make deserialization/processing exceed the statically-attached `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` budget: [6](#0-5) 

Because the flag-reset statement executes before the potentially-panicking work in the same function, but state is only committed on success, an out-of-gas trap anywhere later in `nep_141_storage_balance_callback` rolls back the reset. The on-chain `has_in_flight_tx` value therefore remains whatever it was set to by the prior `rlp_execute` dispatch — `true` — forever, since every future `rlp_execute` call now short-circuits at the very first check and never dispatches a new promise/callback that could ever clear the flag again.

### Impact Explanation
Once `has_in_flight_tx` is stuck `true`, the eth-implicit account's Wallet Contract permanently rejects every subsequent `rlp_execute` call, i.e. every future transaction the account owner tries to sign is refused with "transaction already in progress". Since `rlp_execute` is the *only* entry point through which an eth-implicit account can move funds or otherwise act on NEAR, this permanently freezes the account and any funds held by it — matching the "permanent freezing of funds" impact bar. The griefing does not require any privileged role: it only requires convincing (or tricking) a relayer/owner into routing one ERC-20-emulated transfer through an attacker-deployed token contract, which is a completely ordinary, unprivileged interaction pattern for this contract.

### Likelihood Explanation
The attacker only needs to deploy a standard-looking NEP-141 contract with a malicious `storage_balance_of` responder and get any wallet owner or relayer to route one ERC-20 transfer emulation through it (e.g., via a phishing token/airdrop, a common pattern). No special privileges, races, or validator collusion are required, and the vulnerable code path (`nep_141_storage_balance_callback`) is a normal, frequently-used branch of the wallet's transaction-emulation logic.

### Recommendation
Do not rely on early-in-function assignment plus "hope the rest doesn't panic" to maintain the `has_in_flight_tx` invariant. Options:
- Clear the flag in a way that is robust to failures downstream, e.g. reset it in a dedicated, minimal-gas, panic-free wrapper that runs before any externally-influenced deserialization/processing, and/or use `#[near_bindgen(...)]`'s panic hooks / `Promise` scheduling so a fixed low-gas "unlock" step cannot itself run out of gas.
- Bound the gas cost of processing external cross-contract responses (e.g., cap the size of `StorageBalance`/similar responses before further processing) so it cannot be inflated by a malicious counterparty contract.
- Add a timeout/self-healing mechanism (e.g., an owner-only or anyone-callable "unstick" method gated by a minimum elapsed block height since the flag was set) so a stuck flag cannot cause a truly *permanent* lock.

### Proof of Concept
1. Deploy an eth-implicit account whose code is the shared `Global` Wallet Contract (as done in `test_base_token_transfer_with_relayer_refund`/`test_simultaneous_transactions`, see `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs:121-169`).
2. Deploy a malicious NEP-141 contract whose `storage_balance_of` view method returns a `StorageBalance`-shaped JSON response engineered (e.g., through padding, nested structures, or numeric fields chosen to blow up subsequent arithmetic) to make `nep_141_storage_balance_callback`'s remaining work exceed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`.
3. Have the wallet owner (or a relayer on their behalf) sign and submit one Ethereum-emulated ERC-20 `transfer` call targeting the malicious token contract via `rlp_execute` (as exercised by `test_erc20_transfer_with_relayer_refund` in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/emulation.rs`), triggering `nep_141_storage_balance_callback`.
4. The callback traps with an out-of-gas error after having conceptually cleared `has_in_flight_tx`, but the change is rolled back on receipt failure; `has_in_flight_tx` remains `true` in storage.
5. Any subsequent call to `rlp_execute` (Proof: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:97-105`) is now rejected forever with `"Error: transaction already in progress, please try again later."`, permanently freezing the account.

    #[private]
    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
        let promise = match maybe_storage_balance {
            Some(_) => {
                // receiver_id is registered so we can send the transfer
                // without additional actions. Note: in the standard NEP-141
                // implementation it is impossible to have `Some` storage balance,
                // but have it be insufficient to transact.
                match action_to_promise(token_id, action)
                    .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
                {
                    Ok(p) => p,
                    Err(e) => {
                        return PromiseOrValue::Value(e.into());
                    }
                }
            }
            None => {
                // receiver_id is not registered so we must call `storage_deposit` first.
                let storage_deposit_args =
                    format!(r#"{{"account_id": "{receiver_id}"}}"#).into_bytes();
                let transfer_function_call = match action {
                    near_action::Action::FunctionCall(x) => x,
                    _ => {
                        return PromiseOrValue::Value(ExecuteResponse {
                            success: false,
                            success_value: None,
                            error: Some(
                                "Expected function call action to perform NEP-141 transfer".into(),
                            ),
                        });
                    }
                };
                Promise::new(token_id)
                    .function_call(
                        "storage_deposit".into(),
                        storage_deposit_args,
                        NEP_141_STORAGE_DEPOSIT_AMOUNT,
                        NEP_141_STORAGE_DEPOSIT_GAS,
                    )
                    .function_call(
                        transfer_function_call.method_name,
                        transfer_function_call.args,
                        transfer_function_call.deposit,
                        transfer_function_call.gas,
                    )
                    .then(ext.rlp_execute_callback(caller_deposit))
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
