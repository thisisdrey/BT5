### Title
Out-of-bounds heap read via unvalidated Zip64 extra-field attribute index in `Zip64ExtraField::attr64` - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar`, the Bazel-internal jar packaging tool invoked from build actions such as `java_binary`/`java_library`/deploy-jar assembly, parses `CDH`/`LH` zip headers from input jars, including jars that originate from external dependencies (e.g. fetched via `http_jar`, `http_archive`, or Maven/`http_file` rules) — content an outside attacker fully controls. When a 32-bit size/offset field in a central-directory or local-file header is `0xFFFFFFFF`, the code looks up the "Zip64" extra field and reads a 64-bit value at a computed index without checking that index against the extra field's declared attribute count.

### Finding Description
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()`, and their `LH` counterparts follow this pattern: [1](#0-0) [2](#0-1) 

They call `Zip64ExtraField::attr64(index)`: [3](#0-2) 

`attr_count()` is derived purely from the extra field's own `payload_size()` (attacker-controlled bytes in the zip), but none of the callers (`compressed_file_size`, `uncompressed_file_size`, `local_header_offset`) verify `index < attr_count()` before calling `attr64(index)`. `ExtraField::find()` only validates that the *declared* `payload_size()` fits within the surrounding extra-fields buffer: [4](#0-3) 

So an attacker can craft a CDH/LH entry where:
- `compressed_file_size32_` and/or `uncompressed_file_size32_` and/or `local_header_offset32_` are set to `0xFFFFFFFF` (signaling "value is in Zip64 extra field"), while
- the accompanying Zip64 extra field is present but declares a `payload_size()` smaller than what the combination of 0xFFFFFFFF markers implies (e.g. payload_size = 8, i.e. only one 8-byte attribute, while the code path selects `attr_no = 1` or `attr_no = 2` because two or three of the 32-bit fields are all `0xFFFFFFFF`).

This passes `ExtraField::find`'s bounds check (since the field's own declared small size fits in the buffer) but the mismatched marker/attribute-count relationship causes `attr64(1)` or `attr64(2)` to read 8 bytes at `attr_[1]`/`attr_[2]`, i.e., past the actual (small) payload — an out-of-bounds read of adjacent heap/mmap'd memory relative to what the extra field itself declared, directly analogous to `_XkbReadKeySyms()` trusting one length field while indexing with a value derived from another, unrelated field.

### Impact Explanation
The bug is a boundary-condition OOB read in a class explicitly named as in-scope for this class of finding (`ExtraField`/`Zip64ExtraField` size/parsing logic). The read bytes become the "resolved" `uncompressed_file_size`, `compressed_file_size`, or `local_header_offset`, which are subsequently used to compute buffer offsets, decompression lengths, and memory-copy sizes elsewhere in `singlejar` (`output_jar.cc`, `input_jar.h`'s `LocalHeader()`, `TransientBytes::DecompressEntryContents`, etc.). Depending on where in the mmap'd input file / heap the out-of-bounds bytes land, this can leak adjacent heap contents into a computed size/offset (confidentiality-flavored, matching the CVE's `C:H,I:N,A:N` profile) and can cascade into further wild-pointer reads (e.g., `LocalHeader()` computing `mapped_file_.address(cdh->local_header_offset() + preamble_size_)` from a corrupted 64-bit value) causing a crash or additional out-of-bounds access during the build action.

### Likelihood Explanation
The attacker only needs to control the bytes of a jar/zip file that Bazel's `singlejar` tool processes as an external input — e.g. a malicious third-party `.jar` served from a dependency URL declared in `http_jar`/`http_archive`/Maven coordinates. There is no requirement for MITM, credential access, or local machine access; a hostile origin serving a crafted jar is sufficient, and none of `sha256`/`integrity` checksum verification of the *downloaded archive* protects against internal structural inconsistencies within an otherwise checksum-matching file (the checksum only proves the bytes are the ones the attacker published, not that they are well-formed zip/Zip64 structures). No format-level Zip64 consistency validation exists to reject the mismatched marker/attr-count combination before `attr64()` is called.

### Recommendation
In `Zip64ExtraField::attr64` accessors' call sites (`CDH::compressed_file_size`, `CDH::uncompressed_file_size`, `CDH::local_header_offset`, and the `LH` equivalents), validate `attr_no < attr_count()` before dereferencing, and treat a Zip64 extra field whose `payload_size()` does not match the number of 0xFFFFFFFF-marked 32-bit fields as a corrupt/malformed archive, causing `singlejar` to abort with a diagnostic (as already done elsewhere for other consistency checks in `input_jar.cc`), rather than performing the read.

### Proof of Concept
A concrete JUnit/shell reproduction was not executed in this investigation (no runtime/tool execution available), but the PoC construction mirrors the existing `CreateZipWithMalformedExtraField` pattern already present in the codebase's own test file: [5](#0-4) 

A reproducible test (`src/tools/singlejar/output_jar_simple_test.cc` or `zip_headers_test.cc`) would:
1. Build a CDH with `compressed_file_size32_ = uncompressed_file_size32_ = local_header_offset32_ = 0xFFFFFFFF`.
2. Attach a Zip64 `ExtraField` with `payload_size() = 8` (only one 64-bit attribute) immediately followed in the buffer by other unrelated bytes (e.g., the file name of the next CDH entry, or heap padding).
3. Call `cdh->uncompressed_file_size()` (expects `attr64(0)` — fine) then `cdh->compressed_file_size()` and `cdh->local_header_offset()`, which compute `attr_no` as 1 or 2 respectively — reading 8 bytes past the declared single-attribute payload, i.e., into adjacent buffer memory not sized/owned by this extra field, demonstrating the OOB read via `ASAN`/valgrind detecting a heap-buffer-overflow on read.

*Note: index and boundary details were confirmed by direct code reading; I was not able to execute a build/test to empirically confirm the OOB read is caught by AddressSanitizer in this environment, since no execution tools are available in this session.*

                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }

  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
  auto* ecd = reinterpret_cast<ECD*>(&zip_data[ecd_offset]);
  ecd->signature();
  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
