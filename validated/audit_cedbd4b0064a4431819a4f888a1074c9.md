### Title
Postponed self-receipts survive `DeleteAccount` and resurrect against a re-registered account, granting an attacker-implied `AddKey(FullAccess)` grant the new owner never authorized - ([File: runtime/runtime/src/lib.rs], [File: runtime/runtime/src/actions.rs], [File: core/store/src/utils/mod.rs])

### Summary
`apply_action_receipt` derives `actor_id` from `receipt.predecessor_id()` [1](#0-0) , and for a self-addressed receipt `predecessor_id == receiver_id == account_id` — this is exactly what makes `check_actor_permissions` treat an `AddKey` action as self-authorized regardless of which "owner" currently controls the account name [2](#0-1) . `remove_account`, invoked from `action_delete_account`, only clears `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` [3](#0-2)  — it never clears `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` trie entries, which are keyed purely by the account-id string, not by any per-incarnation identifier. Because postponed-receipt bytes are stored under separate `TrieKey` variants and are not reflected in `Account::storage_usage()`, the `DeleteAccountWithLargeState` gate (`account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE`, `runtime/runtime/src/actions.rs:348`) never sees them and cannot block deletion of an account with a pending postponed receipt.

### Finding Description
1. An attacker's contract at account `A` issues a promise chain (e.g. a cross-shard async call plus a `.then` callback) whose callback receipt targets `A` itself, contains a single `AddKeyAction` with `FullAccess` and zero deposit, and is gated on one `input_data_id`. Because the data hasn't arrived yet, `process_action_receipt` stores it as a postponed receipt: `set_postponed_receipt`, `PendingDataCount{receiver_id: A, receipt_id}`, and `PostponedReceiptId{receiver_id: A, data_id}` [4](#0-3) .
2. Before the input data receipt arrives (attacker can force a delay by making the async leg cross-shard, guaranteeing at least one block of latency), the attacker sends a `DeleteAccount` action for `A`. `action_delete_account` computes `account_storage_usage` from `Account::storage_usage()` only, which never accounted for the postponed-receipt trie entries, so the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` gate passes trivially even though state for `A` still exists in the trie [5](#0-4) . `remove_account` then deletes the `Account`/keys/contract but leaves the `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries untouched [3](#0-2) .
3. Account name `A` becomes available; a new, unrelated user later registers `A`.
4. When the deferred data receipt for the original `data_id` is eventually delivered to `A`, `process_receipt`'s `Data` branch looks up `PostponedReceiptId{receiver_id: A, data_id}`, finds it still present, decrements the pending count to 0, fetches and removes the postponed `ready_receipt`, and calls `apply_action_receipt` on it against whatever account currently lives at `A` (the new owner's account) [6](#0-5) .
5. Inside `apply_action_receipt`, `actor_id` is set to `receipt.predecessor_id().clone()`, which for this self-addressed postponed receipt is `A` itself [7](#0-6) . `apply_action`/`check_actor_permissions` authorizes `AddKey` purely on `actor_id == account_id` [2](#0-1)  — it has no notion of "same actor as when the receipt was originally created," so the check passes even though the account has been fully deleted and recreated by a different key-holder in between. The attacker's chosen `FullAccess` public key is added to the new owner's account.

The existing checks that should prevent this — nonce/signature verification (irrelevant, this isn't a signed tx re-delivery), `DeleteAccountWithLargeState` (bypassed because postponed-receipt storage isn't counted), and `check_actor_permissions` (bypassed because self-addressed semantics don't distinguish account incarnations) — all fail to catch this because none of them tie a postponed receipt's validity to the account's identity/incarnation at delivery time.

### Impact Explanation
This is an authorization-escalation primitive: an attacker who once controlled an account name can plant a dormant `FullAccess` access-key grant that later fires on whichever new party claims that name, without the new owner ever signing for it. Once resurrected, the attacker holds a `FullAccess` key on the victim's account and can drain funds, redeploy contracts, or otherwise fully take over it — this falls under NEAR's "authorization escalation across accounts/promises" and "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: fund one account, submit one `FunctionCall` transaction that creates a self-addressed postponed receipt with a single minimal `AddKeyAction`, wait for the async leg's data receipt to remain outstanding for at least one block (achievable via a cross-shard call), then submit a `DeleteAccount` transaction — no elevated privileges, no timing races beyond ordinary cross-shard latency, and no large payload since the smallest possible postponed receipt (one `AddKeyAction`, zero deposit) is used specifically to keep storage/gas cost negligible and stay under the deletion-size gate. The only additional requirement outside the attacker's control is that the vacated account name gets reused by a third party and that the deferred data receipt eventually gets delivered (which happens automatically once the async leg resolves, since neither side depends on the account still existing) — a realistic, repeatable scenario for name-squatted or recycled account IDs.

### Recommendation
When an account is deleted, clear all outstanding postponed-receipt-related state for that account id (`PostponedReceipt`, `PendingDataCount`, `PostponedReceiptId`, and any pending `ReceivedData`) in `remove_account`/`action_delete_account`, so no postponed receipt can outlive the account incarnation that created it. Alternatively/additionally, count postponed-receipt storage bytes toward `Account::storage_usage()` so `DeleteAccountWithLargeState` cannot be trivially bypassed, and consider binding postponed receipts to an account "incarnation" token (e.g., a monotonically increasing per-account creation counter) so a receipt postponed under one incarnation cannot execute against a later one.

### Proof of Concept
Runtime unit/integration test plan (in `runtime/runtime/src/tests/apply.rs` style, using `create_receipt_with_actions` / raw `Receipt::V0` construction as in existing tests):
1. Create account `attacker.near` with a normal access key.
2. Manually construct (as the test harness, standing in for the promise/pipelining machinery) a self-addressed `ActionReceipt` `R` with `receiver_id = predecessor_id = attacker.near`, `input_data_ids = [data_id]`, `actions = [Action::AddKey(AddKeyAction { public_key: attacker_planted_pk, access_key: AccessKey::full_access() })]`. Apply it via `process_action_receipt`; assert it is stored as postponed (`PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` present, no state change to the account's keys yet).
3. Apply a `DeleteAccount` receipt for `attacker.near` (beneficiary arbitrary). Assert deletion succeeds (`ActionErrorKind::DeleteAccountWithLargeState` NOT returned) and `get_account(state_update, attacker.near)` is `None`, while `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries for `attacker.near` are still present in the trie.
4. Apply a `CreateAccount` (+`AddKey`) receipt that re-registers `attacker.near` with a different, victim-controlled public key `victim_pk`. Assert the account exists with only `victim_pk` as an access key.
5. Deliver a `DataReceipt` with `receiver_id = attacker.near`, `data_id = data_id` (simulating the deferred async result finally arriving). Assert this triggers `apply_action_receipt` on the previously postponed `R` via `process_receipt`.
6. Assert the final state: `attacker.near`'s access key set now contains **both** `victim_pk` and the attacker-planted `FullAccess` key that the victim never signed for — demonstrating unauthorized `AddKey(FullAccess)` escalation across account incarnations.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
