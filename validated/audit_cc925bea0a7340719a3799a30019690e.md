### Title
Sequential floor-division in `calc-liquidity-rate` compounds rounding loss and understates the liquidity index, permanently reducing depositor yield - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent v0-vault-*.clar contracts)

### Summary
The vault contracts' `calc-liquidity-rate` function computes the lenders' interest (liquidity) rate through two chained `mul-bps-down` (multiply-then-divide-by-BPS) operations instead of a single combined multiply-then-divide. Each `mul-bps-down` call floors its own intermediate result before the next multiplication is applied, which is the same "hidden division before multiplication" pattern flagged in the referenced report for `Bonding.sol`'s `liquidity` computation. This compounding of floor divisions understates the resulting liquidity rate (and can round it to zero in edge cases where a single combined calculation would not), which then propagates into `next-liquidity-index` and the `lindex` state variable used for interest accrual bookkeeping.

### Finding Description
`calc-liquidity-rate` is defined as: [1](#0-0) 

```
(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
  (let ((util-applied (mul-bps-down var-borrow-rate util-pct))
        (one-minus-rf (- BPS reserve-factor-bps)))
    (mul-bps-down util-applied one-minus-rf)))
```

where `mul-bps-down` is: [2](#0-1) 

Each `mul-bps-down` call performs `(/ (* x y) BPS)`, flooring the result of the first multiplication (`var-borrow-rate * util-pct / BPS`) before that already-floored value is multiplied again by `one-minus-rf` and divided by `BPS` a second time. This is mathematically equivalent to what the external report calls a "hidden division before a multiplication": the correct single-step calculation would be `var-borrow-rate * util-pct * one-minus-rf / BPS^2`, but the code instead computes `floor(floor(var-borrow-rate * util-pct / BPS) * one-minus-rf / BPS)`, discarding precision at the first division that a combined calculation would have preserved for the second multiplication.

The interest `rate` values fed into this function originate from the interpolated rate table, which is packed/unpacked as 16-bit values (max `MAX-U16 = 65535`), see `pack-u16`/`interpolate-rate`. `util-pct` and `reserve-factor-bps` are basis-point values (0–10000). Because `rate` can be a comparatively small integer relative to `BPS`, the first `mul-bps-down` step can floor a nonzero true value down toward zero (or lose a meaningful fraction of it), and the second `mul-bps-down` amplifies that loss relative to what a single fused-precision calculation would yield — mirroring the report's core finding that separating the multiplication and division steps causes disproportionate loss, up to and including the result becoming zero when it should not be.

The output of `calc-liquidity-rate` is consumed by `next-liquidity-index`: [3](#0-2) 

which computes the multiplier applied to `lindex` via `calc-index-next`, and `lindex` is persisted in the `accrue` public function on every state-changing vault call: [4](#0-3) 

Every accrual cycle that computes `next-liquidity-index` re-derives the (already precision-degraded) liquidity rate from `interest-rate`/`utilization`, so the understatement is not a one-off rounding artifact but a per-accrual, compounding loss to `lindex` growth.

### Impact Explanation
`lindex` represents the accumulated liquidity index tracking interest that should accrue to liquidity providers/depositors, analogous to the `liquidity` variable understatement in the original report. Systematically underestimating the liquidity rate on every accrual means depositors permanently receive less than their entitled yield over time — this is unclaimed-yield loss caused by an on-chain arithmetic bug rather than an oracle or governance issue, landing squarely in the in-scope "theft of unclaimed yield" / "permanent freezing of unclaimed yield" impact category. Because this affects the shared `lindex` state used across all depositors of a given vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`), the impact compounds across every accrual call and every user of the affected reserve, rather than being a one-time isolated rounding error.

### Likelihood Explanation
The bug triggers automatically on every `accrue` invocation (called implicitly by deposit/redeem/borrow/repay flows) whenever utilization, borrow rate, and reserve factor combine such that the two sequential floor divisions lose precision relative to the fused calculation — which, given that `rate` values are drawn from a 16-bit-packed table (max 65535) and can be small relative to `BPS = 10000`, is a routine occurrence rather than a rare edge case. No privileged access or malicious actor is required; it manifests under ordinary protocol usage by any depositor/borrower interacting with the vault.

### Recommendation
Combine the two `mul-bps-down` operations in `calc-liquidity-rate` into a single multiply-then-divide computation to avoid the intermediate floor:
```
(mul-div-down (* var-borrow-rate util-pct) one-minus-rf (* BPS BPS))
```
or equivalently use a higher-precision intermediate (e.g., compute `var-borrow-rate * util-pct * one-minus-rf` in one product before the single division by `BPS * BPS`), consistent with the "prioritize multiplication before division" mitigation recommended in the referenced report. Apply the same fix uniformly across all six vault contracts, since they share identical `calc-liquidity-rate` logic.

### Proof of Concept
Using the same style of reasoning as the referenced report's PoC:

Let `var-borrow-rate = 150`, `util-pct = 99` (0.99%), `reserve-factor-bps = 1000` (10%), `BPS = 10000`.

Current (sequential) implementation:
```
util-applied = floor(150 * 99 / 10000) = floor(14850 / 10000) = 1
one-minus-rf = 10000 - 1000 = 9000
result = floor(1 * 9000 / 10000) = 0
```

Correct (fused) implementation:
```
result = floor(150 * 99 * 9000 / (10000 * 10000))
        = floor(133,650,000 / 100,000,000)
        = 1
```

The current implementation yields `0` where the mathematically correct fused computation yields `1` — an infinite relative error in this instance, and more generally a systematic understatement of the liquidity rate feeding `next-liquidity-index` / `lindex` on every accrual cycle across all vaults sharing this code (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`).
