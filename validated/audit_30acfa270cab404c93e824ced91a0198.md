### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount` set to `MAX_TOKENS_PER_USER`, blocking their deposits and collateral top-ups - ([File: contracts/DepositToken.sol])

### Summary
The MySQL packaging CVE is a denial-of-service class bug: a low-cost action by the attacker breaks availability for other users. The Metronome analog is the per-account deposit-token set. Every first-time receipt of a `DepositToken` (including plain ERC20 `transfer`/`transferFrom`, `seize`, and `deposit(onBehalfOf_)`) calls `Pool.addToDepositTokensOfAccount(recipient)`, which inserts the token into `depositTokensOfAccount[recipient]` capped by `MAX_TOKENS_PER_USER`. An unprivileged attacker can deposit 1 wei of every whitelisted collateral and dust-transfer each `msd*` token to a victim, filling their set to the cap. Afterwards any further deposit-token transfer or deposit to the victim reverts, so the victim cannot add collateral to an at-risk position and is pushed into liquidation.

### Finding Description
`DepositToken._transfer` inserts the token into the recipient's pool-side set whenever the recipient balance was zero:

```solidity
// contracts/DepositToken.sol:517-520
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
```

The same insertion happens on `_mint` (`contracts/DepositToken.sol:485-488`), so `deposit(amount_, onBehalfOf_ = victim)` also grows the victim's set without their consent (`contracts/DepositToken.sol:211-237`). `Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` on the `MappedEnumerableSet` (`contracts/lib/MappedEnumerableSet.sol`), reverting once the cap is reached. Removal only occurs when a balance returns to zero (`_burn`/`_transfer`, lines 459-462, 522-525).

Attack path (all public entry points, unprivileged EOA):
1. For each of the N whitelisted `DepositToken`s, attacker calls `deposit(dust, attacker)` then `transfer(victim, 1)` — or directly `deposit(dust, victim)` — until `depositTokensOfAccount[victim]` holds `MAX_TOKENS_PER_USER` entries.
2. Any subsequent call that would add a new deposit token to the victim's account reverts inside `addToDepositTokensOfAccount`, reverting the whole `deposit`/`transfer`.
3. Victim's existing collateral and withdrawals still work, but they cannot acquire any additional collateral token to restore health.

### Impact Explanation
Temporary freezing of funds / forced liquidation: while the set is saturated, the victim cannot deposit any new collateral type nor receive `msd*` tokens (including collateral topping via `deposit(onBehalfOf_ = victim)` by a helper or zap). If the victim holds an open debt position drifting toward unhealthy, they are denied the standard remediation path and get liquidated by third parties — loss of collateral value beyond the normal liquidation fee. The attacker bears only dust + gas cost, satisfying the DoS-with-cheap-precondition profile of CVE-2019-2536.

### Likelihood Explanation
Requires only a funded EOA; no privileged role, no oracle manipulation, no timing dependence. Cost scales linearly with the number of whitelisted deposit tokens needed to reach `MAX_TOKENS_PER_USER`. Impact is conditional on the victim needing to add a *new* collateral type; if they already hold every relevant token they can still top up, which keeps this at medium severity, matching the CVE's medium CVSS.

### Recommendation
- Do not add to `depositTokensOfAccount` on behalf of recipients in `DepositToken._transfer`/`deposit` for amounts below a meaningful minimum, or require `onBehalfOf_ == _msgSender()` / opt-in for third-party deposits.
- Alternatively, make `addToDepositTokensOfAccount` non-reverting at the cap (return early) and iterate only over tokens with non-zero balance in `debtPositionOf`, or raise/remove the cap since the set is only used for bounded accounting.

### Proof of Concept
```solidity
// Foundry fork test sketch
// Assume pool has >= MAX_TOKENS_PER_USER whitelisted DepositTokens and
// MAX_TOKENS_PER_USER == N.
for (uint i; i < N; ++i) {
    DepositToken dt = depositTokens[i];
    deal(address(dt.underlying()), attacker, 1);
    IERC20(dt.underlying()).approve(address(dt), 1);
    // either path grows victim's set:
    dt.deposit(1, attacker);
    dt.transfer(victim, 1); // triggers addToDepositTokensOfAccount(victim)
}
assertEq(pool.getDepositTokensOfAccount(victim).length, N);

// victim cannot receive or deposit any further collateral token:
vm.expectRevert(); // set cap revert inside addToDepositTokensOfAccount
newDepositToken.deposit(100e18, victim);

// and cannot top up while unhealthy -> liquidator seizes collateral
pool.connect(liquidator).liquidate(msEth, victim, repayAmt, msdMET);
```
Expected: the last deposit reverts and `liquidate` succeeds — demonstrating the frozen-collateral-top-up DoS.
