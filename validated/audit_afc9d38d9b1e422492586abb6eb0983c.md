Confirmed root cause. `DecodeUtil.addressValid()` at [1](#0-0)  only validates address length and prefix byte — it does **not** reject the all-zero address body (e.g. `0x41` followed by 20 zero bytes). This is the exact same class of flaw as the reported `MainToken.set_mint_multisig()` issue: a privileged authority field can be set to an uncontrollable "zero" value with no dedicated check preventing it.

### Title
Permanent account lockout via zero-address key in `AccountPermissionUpdateActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.checkPermission()` validates each permission key's address only with `DecodeUtil.addressValid()`, which merely checks address length and the network prefix byte, never rejecting the all-zero address body. A user can therefore submit an `AccountPermissionUpdateContract` that sets the account's `Owner` permission key(s) to this unusable zero address, an address for which no private key can ever exist or produce a valid signature.

### Finding Description
The validation chain is:
- `AccountPermissionUpdateActuator.validate()` requires an `Owner` permission and calls `checkPermission(owner)` [2](#0-1) .
- `checkPermission()` only checks that each key address is "valid" via `DecodeUtil.addressValid()` and that weights/thresholds are self-consistent; it never checks that the resulting key set can actually satisfy the threshold with keys anyone can control (e.g. rejecting the zero/blackhole address) [3](#0-2) .
- `execute()` then unconditionally applies the new permissions via `account.updatePermissions(...)`, overwriting the account's existing `Owner` permission with the attacker/user-supplied one [4](#0-3) .

Because `Owner` permission changes (including future `AccountPermissionUpdateContract`s) themselves require satisfying the current `Owner` threshold, setting the sole/controlling `Owner` key(s) to the zero address makes the account's owner authority permanently unattainable — no one can ever again produce a signature from the zero address to authorize a new permission update, asset transfer requiring owner approval, or resource management for that account.

### Impact Explanation
This causes permanent loss of control over the account's `Owner` permission (and by extension `Active`/`Witness` permissions that are owner-controlled), analogous to the reported `minting_multisig` bug: an unrecoverable, permanent loss of a privileged authority slot. Any TRX balance, frozen/delegated resources, or votes tied to that account that require owner-authorized actions become permanently frozen since the account can never satisfy its own owner threshold again.

### Likelihood Explanation
Reachable by any account holder broadcasting a single signed `AccountPermissionUpdateContract` transaction; no special privilege is required. The lack of a "usable key" or "non-zero address" check for permission keys makes this trivially triggerable by mistake or via a malicious dApp/wallet crafting the contract on the user's behalf.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly reject the network's zero/blackhole address (and any other well-known unusable address) as a permission key address, in addition to the existing `DecodeUtil.addressValid()` check, particularly for `Owner`-type permissions.

### Proof of Concept
1. Construct an `AccountPermissionUpdateContract` for `OWNER_ADDRESS` with an `Owner` permission whose sole key is `Wallet.getAddressPreFixByte()` followed by 20 zero bytes (a syntactically valid address per `DecodeUtil.addressValid()`), with threshold 1/weight 1.
2. Sign and broadcast with the account's current valid owner key (satisfying the *current* owner threshold).
3. `AccountPermissionUpdateActuator.validate()` passes `checkPermission(owner)` since the zero address passes `DecodeUtil.addressValid()`.
4. `execute()` commits the new `Owner` permission via `account.updatePermissions(...)`.
5. From this point on, no transaction can ever satisfy the account's `Owner` permission threshold (since nobody controls the zero address), permanently freezing the account's owner-level authority.

      return false;
    }

      return false;
    }
    return true;
  }
