### Title
Out-of-bounds read while parsing ZIP central directory entries in ijar - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry()` in ijar's zip reader trusts the `file_name_length`, `extra_field_length`, and `file_comment_length` fields taken directly from an attacker-controlled `.jar`/`.zip` central directory record and advances the read cursor `p` by those amounts — and dereferences memory at the new offsets (`get_u2le`, `get_u4le`, `memcpy`) — with **no bounds check** against the size of the mmap'd input file. This is the same bug class as CVE-2022-24805: a length/index field taken from untrusted input is used to compute an offset/size that is never validated against the buffer's actual extent before being used for a memory access.

### Finding Description
`ProcessCentralDirEntry` reads the fixed 46-byte CDH prefix, then: [1](#0-0) 
reads `file_name_length`, `extra_field_length`, `file_comment_length` and unconditionally does `p += file_name_length; ... p += extra_field_length; ... p += file_comment_length;`, plus a `memcpy` of `file_name_length` bytes from `p` into a fixed 4KB stack buffer, and a loop over "extra field" sub-records advancing by attacker-supplied `data_size` values, all without ever calling the `EnsureRemaining()` bounds helper that the sibling function `ProcessLocalFileEntry` calls before every variable-length field: [2](#0-1) 
`EnsureRemaining` itself is defined and used specifically to prevent reading past the end of the mmap'd file: [3](#0-2) 
but it is never invoked from `ProcessCentralDirEntry`, so a crafted central directory record with an oversized `file_name_length`/`extra_field_length`/`file_comment_length` (or a chain of central-dir entries engineered to walk the cursor past the mapped region) drives `p`, and therefore all subsequent `get_u2le/get_u4le/memcpy` calls, outside the bounds of the memory-mapped input file.

This function is reached whenever Bazel runs `ijar` to build an interface jar, i.e. `java_common.run_ijar`, which operates on jar `File` inputs including prebuilt/third-party jars pulled in as dependencies: [4](#0-3) 
Such a jar is exactly the kind of content an unprivileged attacker controls: a jar served from a dependency's origin server/mirror and referenced e.g. via `http_jar`/`http_file`/a Maven artifact, where `sha256`/`integrity` is optional in Bazel's fetch rules — when omitted (or even when present, since a valid hash simply certifies the attacker's crafted bytes, not that they form a structurally sane ZIP), the malformed-but-hash-matching jar flows unchecked into `ijar`'s native ZIP parser.

### Impact Explanation
The out-of-bounds read can walk the cursor arbitrarily far past the mmap'd input file, causing:
- A crash of the Bazel build action (SIGSEGV when crossing an unmapped page), and
- Disclosure of adjacent process memory into the `filename[PATH_MAX]` buffer and into `attr`/size fields via `memcpy`/`get_u4le`, which are subsequently used to build/label output artifacts.

This is analogous to the net-snmp `INDEX` overflow: a read-side length field from untrusted data is trusted for a memory access, producing an out-of-bounds memory read reachable by a party that merely supplies the (would-be) input data, not by a privileged/local attacker.

### Likelihood Explanation
Any dependency whose jar is fed into `ijar` (virtually every third-party Java dependency, since interface-jar generation is Bazel's default caching optimization for `java_library`/`java_import`) can trigger this by shipping a byte-for-byte crafted central directory entry. No sandbox escape, no credential access, and no local machine access is required — the attacker only needs to control the content of a jar the victim's build fetches and builds against.

### Recommendation
Add `EnsureRemaining()` (or equivalent bounds checks against `input_file_->Length()`) in `ProcessCentralDirEntry` before every advance of `p` by an attacker-supplied length (`file_name_length`, `extra_field_length`, `file_comment_length`, and the "extra field" sub-record `data_size`), mirroring the existing checks in `ProcessLocalFileEntry`. Reject the entry and fail the build with a diagnostic instead of continuing to read past the mapped region.

### Proof of Concept
1. Build a `.jar` whose central directory contains one entry with a plausible signature and a `file_name_length`/`extra_field_length` value large enough that `p + file_name_length` (or `p + extra_field_length`) exceeds `zipdata_in_ + input_file_->Length()`.
2. Run `ijar <that.jar> out-interface.jar` (equivalently trigger `java_common.run_ijar`/interface-jar generation via `java_library` depending on that jar).
3. Observe `ProcessCentralDirEntry` dereferencing memory beyond the mmap'd file bounds (crash under ASan/`SIGSEGV`, or leaked adjacent memory bytes surfacing in the copied `filename` buffer) — this can be encoded as a `googletest`/`cc_test` case in `third_party/ijar/*_test.cc` that opens such a crafted zip through `InputZipFile` and asserts no out-of-bounds access occurs (e.g., via ASan) while today's build lacks any such check.

  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
