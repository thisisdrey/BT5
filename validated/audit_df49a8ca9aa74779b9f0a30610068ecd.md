### Title
Out-of-bounds read when parsing attacker-controlled ZIP central directory entries in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in [1](#0-0)  reads attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) from a ZIP central directory entry and advances the parse cursor `p` by those lengths without ever verifying that the declared lengths actually fit within the bytes still available in the memory-mapped input file, unlike the sibling local-file-header parser which explicitly guards every variable-length field with `EnsureRemaining()`.

### Finding Description
`FindZipCentralDirectory` only validates that the *aggregate* central directory region fits inside the mapped file (`cd.central_dir_offset + cd.central_dir_size > in_length` check) as seen in [2](#0-1) . It never validates that any *individual* entry's declared `file_name_length`/`extra_field_length`/`file_comment_length` stays within that region or within the overall mapped file.

`ProcessCentralDirEntry` then does: [3](#0-2) 
- It reads `file_name_length`, `extra_field_length`, `file_comment_length` directly off the wire with no sanity check.
- It computes `len = min(file_name_length, filename_size-1)` and does `memcpy(filename, p, len)` — the *write* is capped by the local `filename[PATH_MAX]` buffer, but the *read* source `p` is only guaranteed to be a valid pointer, not that `len` bytes remain before the end of the mmap'd file.
- It then unconditionally advances `p += file_name_length;` (line 523) and `p += extra_field_length;` (line 525), and separately walks the "extra field" sub-records with `extra_p += data_size;` (line 530) — again using attacker-supplied 16-bit values with no remaining-bytes check.
- Finally `p += file_comment_length;` (line 543).

This is a direct contrast with `ProcessLocalFileEntry`, which reads the same kind of untrusted length fields for the local header but explicitly bounds-checks them before dereferencing: [4](#0-3) 
and the `EnsureRemaining` helper it relies on: [5](#0-4) 

Because `ProcessCentralDirEntry` omits the equivalent checks, a maliciously crafted (but otherwise well-formed, correctly-hashed) `.jar`/`.zip` file can declare a `file_name_length`, `extra_field_length`, or `file_comment_length` that extends past the end of the memory-mapped input file. Reading (via `memcpy` or the `get_u2le/get_u4le` accessors used in the extra-field loop) past the end of the mapping is a classic out-of-bounds read of the kind described in CVE-2018-6340 (an untrusted length value drives a read past the intended buffer). This is class-equivalent to `ZipDecompressor`/archive-entry parsing bugs called out in the prompt's bug-class list.

### Impact Explanation
This code path (`third_party/ijar`) is bazel's own vendored tool for producing interface jars from `.jar` inputs during Java compilation. Those jar inputs frequently originate from externally fetched dependencies (e.g. via `http_jar`/`http_archive`/Maven rules). A `sha256`/integrity check on the *download* only certifies that the bytes match a known digest — it says nothing about whether the internal ZIP structure is well-formed, so a hostile publisher can craft a byte-for-byte reproducible malicious jar whose advertised hash is legitimately pinned in a lockfile/`BUILD` file yet still contains an out-of-bounds central-directory entry. When `ijar` processes such an artifact, the OOB read can crash the `ijar` process (out-of-bounds page access) or, since the truncated bytes land in the `filename[PATH_MAX]` buffer that is subsequently used for output naming/`processor->Accept()`/error messages, could leak adjacent process memory bytes into build output or error logs.

### Likelihood Explanation
Any unprivileged party that can get bazel to consume a crafted jar file they authored (a dependency archive, a build artifact fetched over HTTP, a file on an untrusted branch/CI) can trigger this: the check that stops most fetch-time tampering (the SHA-256 pin) does not, and cannot, validate internal ZIP semantics. No credentials or access to the victim machine are required; only serving/publishing the bytes.

### Recommendation
Add the same `EnsureRemaining()`-style bounds checks used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before dereferencing/advancing past `file_name_length`, `extra_field_length`, and `file_comment_length`, and validate that each extra-field sub-record's `data_size` does not exceed the remaining bytes of the extra field / mapped file before reading it.

### Proof of Concept
A JUnit/`gtest` proof (analogous to the existing `zip_headers_test.cc`/`output_jar_simple_test.cc` malformed-extra-field tests) should construct a minimal ZIP whose End-Of-Central-Directory record and central-directory-size fields are internally consistent (so `FindZipCentralDirectory`'s aggregate check passes), but whose single central directory entry declares `file_name_length`/`extra_field_length`/`file_comment_length` values that, when added to the entry's start offset, exceed the actual mapped file length. Feeding this file to `ZipExtractor`/`InputZipFile::ProcessNext()` (the public API exercised by `ijar_test`/`output_jar_simple_test.cc`) reproduces the out-of-bounds read (observable via AddressSanitizer as a heap-buffer-overflow/read, or via a crafted length that walks `extra_p` past the mapped region in the extra-field loop at lines 526–541).
