### Title
Time-of-check/time-of-use race in the anti-replay window allows message-counter replay across UDP reader queues - (File: connection_state.go)

### Summary
The bug report requests a general "nonReentrant lock" on every external entry point to prevent reentrancy. Nebula is Go, not Solidity, so there is no EVM call-stack reentrancy, but the analogous class — a state check and the corresponding state commit being non-atomic, so a second "reentrant" invocation can race between them — exists in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`.

### Finding Description
`ConnectionState.Decrypt` implements the anti-replay window as two separate critical sections instead of one atomic check-and-set: [1](#0-0) 

The lock is released after `window.Check` and re-acquired only after the (comparatively expensive) AEAD `DecryptDanger` call finishes, before `window.Update` finally marks the counter as seen. `VerifyRelay` has the identical pattern: [2](#0-1) 

This is exactly the reentrancy bug class from the report translated to Go's concurrency model: the external report warns that a check performed before an external/expensive operation can be invalidated by another call that runs concurrently while the first call is "in flight" and hasn't yet committed its state change. Here, two goroutines processing the same `ConnectionState` (e.g., two copies of the exact same wire packet, or a captured/replayed relay frame) can both pass `window.Check` for the same `messageCounter` before either reaches `window.Update`, because the lock is dropped in between.

Nebula supports multiple concurrent UDP reader routines (`f.routines > 1`), each independently invoking `readOutsidePackets` → `ConnectionState.Decrypt`/`VerifyRelay` for whatever `HostInfo`/`ConnectionState` the inbound packet's `RemoteIndex` resolves to: [3](#0-2) [4](#0-3) [5](#0-4) 

Because queue selection is done by the kernel/socket layer and not pinned to a specific remote index, packets belonging to the same tunnel (including duplicate copies of a single captured packet) can be delivered to different reader goroutines and processed concurrently against the same `ConnectionState`, hitting the Check/Update race window.

An e2e test already demonstrates the real-world consequence for the relay path — a naive re-forward bug that let replays get forwarded because the window wasn't updated at all: [6](#0-5) 

That specific always-fails case is fixed (the code now calls `Update`), but the fix still leaves the Check→(decrypt)→Update sequence non-atomic, so a race between two concurrent deliveries of the same counter is still possible.

### Impact Explanation
An attacker who can capture one legitimate on-wire packet (no CA-signed certificate required — this is a header/nonce-handling issue in the data-plane decrypt/verify path, not a certificate check) can replay it concurrently. If both copies are scheduled onto different reader goroutines and race through `Check` before either calls `Update`, both will attempt to decrypt/verify with the same counter. For `Decrypt` this means a duplicate application-plaintext packet can be delivered twice to the tun device (double delivery of attacker-replayed traffic). For `VerifyRelay`, a relay node could re-forward an already-seen relay frame toward the tunnel target, which is precisely the replay-protection bypass the `TestRelayReplayProtection` test was written to catch. This constitutes a replay-based traffic forgery/duplication impact on the data plane.

### Likelihood Explanation
Exploitation requires: (1) `routines > 1` (multiple UDP reader queues, a supported and documented configuration, not a test-only path), and (2) the ability to send two copies of a captured packet to the listener close enough in time to race the same `ConnectionState`'s lock window. Both conditions are attacker-controlled/network-reachable and don't require holding a valid certificate or being an already-trusted peer, but they do require winning a narrow timing race, which lowers likelihood relative to a deterministic bypass.

### Recommendation
Make the replay-window check-and-commit atomic with respect to a given message counter: hold `decryptLock` across `Check`, `DecryptDanger`, and `Update` for that counter (or use a per-counter claim/reservation step under the lock before doing the expensive decrypt), so no second goroutine can observe the counter as "not yet seen" while the first is still processing it. This mirrors the nonReentrant-lock intent from the report — serialize the full check-effect sequence for a given state (the anti-replay window) rather than only its individual sub-steps.

### Proof of Concept
1. Configure a node with `routines: 2` (or more) so multiple independent UDP reader goroutines run.
2. Capture one legitimate encrypted `Message` (or `MessageRelay`) packet destined to that node.
3. Send two copies of the exact same captured packet to the node's UDP socket at (near-)the same time so the OS/socket layer can dispatch them to two different reader goroutines.
4. If both goroutines' `window.Check` calls execute before either goroutine's `window.Update` call (the window between the two `decryptLock` critical sections in `ConnectionState.Decrypt`/`VerifyRelay`), both copies pass the replay check and are independently decrypted/verified — observed either as a duplicate plaintext packet delivered to tun, or (for relay nodes) as a duplicate forwarded relay frame, as demonstrated by the scenario `TestRelayReplayProtection` in `e2e/tunnels_test.go` guards against.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
