Audit Report

## Title
Unbounded, Fee-less Message Spam in `snowbridge-pallet-outbound-queue-v2` Can Delay/Stall FIFO Bridge Delivery for Legitimate Messages - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, `send_message_impl.rs`)

## Summary
`Pallet::validate()` in the Snowbridge V2 outbound queue enforces only a maximum payload size, never a minimum fee, and the `fee` field derived from the XCM `PayFees` instruction in `XcmConverter::extract_remote_fee` is fully attacker-controlled and can be zero. Combined with strict per-origin FIFO processing and a hard `MaxMessagesPerBlock` cap in `do_process_message`, an attacker can submit a stream of minimal-payload, zero/low-fee messages from a given origin to occupy the entire per-block processing budget for that origin ahead of a legitimate, properly-fee-paying message, delaying its commitment/bridging with no way for anyone to skip ahead to service the specific pending message.

## Finding Description
`send_message_impl.rs::validate` checks only `payload.len() < MaxMessagePayloadSize`, with no minimum-fee assertion. The `fee` carried in `Message` originates from `XcmConverter::extract_remote_fee`, which only verifies that the reserved fee asset covers the declared `PayFees` amount (`reserved_fee_amount >= fee_amount`) — it never enforces `fee_amount > 0`. `do_process_message` in `lib.rs` processes messages strictly in the order the underlying `pallet-message-queue` delivers them for a given `AggregateMessageOrigin`, and yields once `MaxMessagesPerBlock` is reached for the block (via the `current_len >= T::MaxMessagesPerBlock::get()` check), deferring remaining same-origin messages via `MessagePostponed`/`Yield`. `pallet-message-queue::service_queue` enforces strict FIFO within a book/page for an origin — a later message cannot be serviced before an earlier undispatched one, and there is no public function to service a specific pending message out of order. Since `fee` is attacker-supplied and unchecked, and relayer reward is only paid `if order.fee > 0` in `process_delivery_receipt`, cheap zero-fee messages both occupy processing slots ahead of legitimate ones from the same origin and may never be economically relayed, leaving stale `PendingOrders` entries.

## Impact Explanation
This degrades bridge throughput/availability for a specific origin (e.g., a sibling parachain/channel) by delaying commitment of legitimate, fee-paying messages behind cheap spam, and can leave `PendingOrders`/`Nonce` state polluted with unrewarded entries. This fits the "public underpriced work that ... stalls bridge processing" impact category for Snowbridge BridgeHub code.

## Likelihood Explanation
Any account capable of sending an XCM `ExportMessage` toward the Ethereum gateway from the affected origin can repeatedly submit minimal-payload messages with `fee = 0` (or a negligible fee), since neither `validate()`, `extract_remote_fee`, nor `do_process_message()` reject such messages. No privileged role, relayer collusion, or protocol-level manipulation is required — only the ability to construct a valid `WithdrawAsset`/`PayFees`/`AliasOrigin`/`DepositAsset`/`SetTopic` XCM sequence with a zero or near-zero fee amount.

## Recommendation
Enforce a minimum non-zero fee in `Pallet::validate()`/`do_process_message()` or in `XcmConverter::extract_remote_fee` (mirroring `pallet-nis`'s `MinBid` pattern, explicitly documented elsewhere as a defense "to ensure there is no possible storage spam attack or queue-filling attack"), and/or expose a privileged-free mechanism to prioritize/skip to a specific pending order so legitimate, well-funded messages are not held hostage behind cheap same-origin spam.

## Proof of Concept
1. Attacker controls (or transacts from) a parachain origin routed through the V2 exporter.
2. Attacker repeatedly submits `ExportMessage`s converted into `Message { fee: 0, .. }` with minimal `commands` payload, each passing `validate()`'s size-only check and `extract_remote_fee`'s consistency-only check.
3. Each block, `do_process_message` accepts up to `MaxMessagesPerBlock` of these before yielding (`Event::MessagePostponed`), as shown in the existing test `governance_message_not_processed_in_same_block_when_queue_congested_with_low_priority_messages` in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`.
4. A legitimate user then submits a properly fee-paying message from the same origin; because messages are serviced strictly in order and there is no per-message skip mechanism, their message is queued behind all outstanding attacker messages and is only processed once the attacker's backlog is drained across multiple blocks — reproducible directly by extending the referenced test's message count indefinitely.
