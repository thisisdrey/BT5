### Title
Missing bounds checks in `InputZipFile::ProcessCentralDirEntry` allow out-of-bounds read from a malicious ZIP central directory - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the ZIP central directory of a memory-mapped, attacker-controlled archive without ever validating that the fields it reads (or the cursor advances it performs) stay within the bounds of the mapped file. This mirrors the libssh2 `_libssh2_packet_add` class of bug: a length field taken directly from untrusted wire/file data is trusted to advance a read cursor with no remaining-bytes check, leading to out-of-bounds memory access.

### Finding Description
Compare the two parsing paths in `InputZipFile`:

- `ProcessLocalFileEntry` (used when reading the local file header) is careful: every field read or skip is preceded by an `EnsureRemaining(...)` bounds check against `input_file_->Length()`. [1](#0-0) 

- `ProcessCentralDirEntry` (used when reading the central directory) has **no such checks at all**. After validating only the 4-byte signature, it unconditionally advances `p` by 16 bytes, reads `compressed_size`, `uncompressed_size`, `file_name_length`, `extra_field_length`, `file_comment_length`, `attr`, and `offset`, then advances `p` by `file_name_length`, walks an "extra field" chain by `data_size` amounts taken from the file itself, and finally advances by `file_comment_length` - all without ever calling `EnsureRemaining` or comparing `p` to the end of the mapped input: [2](#0-1) 

The comment at line 491-492 asserts "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" - but this is only true for a well-formed archive. `file_name_length`, `extra_field_length`, and `file_comment_length` are attacker-controlled 16-bit fields, and the "extra field" `data_size` values are attacker-controlled as well; a crafted 16-bit value can push `p`/`extra_p` past the end of the `mmap`'d region (`zipdata_in_`), causing reads beyond the mapping. `memcpy(filename, p, len)` at line 520 similarly copies from `p` with a length bounded only by the caller-supplied `filename_size`, not by remaining input length, so a truncated/short archive with a large `file_name_length` field can leak or crash by reading unmapped memory.

This function is reached by the generic `ZipExtractor` interface (`ProcessNext` → `ProcessCentralDirEntry`), which is used, among other callers, in `PartialZipExtractor::UnzipUntil` in the Bazel client launcher's `archive_utils.cc` to extract embedded install data. [3](#0-2) 
It is also the underlying engine for `zip_main.cc`'s `extract()`/`UnzipProcessor`, used for extracting general zip archives. [4](#0-3) 

### Impact Explanation
An attacker who can supply a crafted ZIP archive (e.g., as the contents of an `http_archive`/`repository_ctx.extract`-style artifact processed through this shared `ijar` zip-reading code, or any other Bazel-side consumer of `ZipExtractor`) can trigger reads beyond the bounds of the `mmap`'d input file. Depending on the crafted lengths and how close the mapping is to a page boundary, this can cause a SIGSEGV (crash / denial of availability for the toolchain component doing the read) or leak adjacent heap/mapped memory contents into `filename`/`extra` fields that are subsequently used by calling code (e.g. compared against expected entry names, or copied via `memcpy`). This matches the CWE-125 (out-of-bounds read) class described in the libssh2 analog, reachable purely from attacker-supplied archive bytes with no code execution or trusted-repo access required by the attacker.

### Likelihood Explanation
Any content that this `ZipExtractor`/`InputZipFile` path is used to parse — most notably a hostile archive served from an unprivileged, attacker-controlled URL or mirror and referenced from a build (fetched without integrity being checked by this code path, since this is generic-purpose zip parsing code, not the Java `DownloadManager`/`Checksum` pipeline) — reaches `ProcessCentralDirEntry` directly. Because `ProcessLocalFileEntry` demonstrates the codebase's own idiom (`EnsureRemaining`) is missing specifically in the central-directory path, this is a straightforward, reliably reproducible parsing bug that requires only a truncated or malformed central directory record (e.g., a valid signature immediately followed by end-of-file, or oversized `file_name_length`/`extra_field_length`/`file_comment_length` fields relative to remaining bytes).

### Recommendation
Add the same `EnsureRemaining(...)` bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before each field read and before each pointer advance (the fixed 46-byte central directory header, `file_name_length`, `extra_field_length`, `file_comment_length`, and each iteration of the extra-field walk using `data_size`). Reject/error out on malformed entries instead of trusting length fields taken directly from the archive.

### Proof of Concept
A concrete JUnit/C++ unit test analogous to `zip_headers_test.cc`/`transient_bytes_test.cc` conventions in this repo would:
1. Construct a minimal in-memory (or on-disk, via `MappedInputFile`) buffer containing a valid `CENTRAL_FILE_HEADER_SIGNATURE` (`0x02014b50`) followed by the fixed 42 bytes of header fields, but set `file_name_length` (or `extra_field_length`/`file_comment_length`) to a value (e.g. `0xFFFF`) that is larger than the number of bytes actually remaining in the buffer/mapped file, with no additional bytes appended.
2. Call `InputZipFile::ProcessCentralDirEntry` (via `ZipExtractor::Create`+`ProcessNext`, e.g. as in `tw_test.cc`'s `InMemoryExtractor` harness) on this crafted input.
3. Run under AddressSanitizer or with a tightly-sized mapping (e.g., a heap buffer allocated exactly `sizeof(header)+small_data` bytes, `mmap`'d with a guard page) — the `memcpy(filename, p, len)` at line 520 or the `get_u2le(extra_p)` calls in the extra-field loop at lines 526-530 will read past the end of the buffer, which ASan/the guard page will report as a heap/out-of-bounds read, confirming the vulnerability.

I was not able to fully trace every downstream Bazel Starlark `repository_ctx.extract`/http_archive code path that ultimately invokes this specific C++ `ijar` `zip.cc` reader (as opposed to the Java-side `ZipDecompressor`, which the index did not surface with contents), so the exact set of all attacker-reachable call sites into `ProcessCentralDirEntry` beyond `archive_utils.cc` and `zip_main.cc` could not be exhaustively confirmed from the indexed code alone.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

int extract(char *zipfile, char *exdir, char **files, bool verbose,
            bool extract, bool flatten) {
  std::string cwd = get_cwd();
  if (cwd.empty()) {
    return -1;
  }

  char output_root[PATH_MAX + 1];
  if (exdir != NULL) {
    if (!concat_path(output_root, sizeof(output_root), cwd.c_str(), exdir)) {
      return -1;
    }
  } else if (cwd.length() >= sizeof(output_root)) {
    fprintf(stderr, "current working directory path too long");
    return -1;
  } else {
    memcpy(output_root, cwd.c_str(), cwd.length() + 1);
  }

  UnzipProcessor processor(output_root, files, verbose, extract, flatten);
  std::unique_ptr<ZipExtractor> extractor(ZipExtractor::Create(zipfile,
                                                               &processor));
  if (extractor == NULL) {
    fprintf(stderr, "Unable to open zip file %s: %s.\n", zipfile,
            strerror(errno));
    return -1;
  }

  if (extractor->ProcessAll() < 0) {
    fprintf(stderr, "%s.\n", extractor->GetError());
    return -1;
  }
  return 0;
