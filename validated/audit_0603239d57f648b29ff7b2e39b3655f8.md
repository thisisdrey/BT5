### Title
Pyth confidence-ratio check causes protocol-wide price-resolution revert on stablecoin depeg / volatility, freezing borrow/withdraw/repay operations for unaffected assets ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
Zest's market contract resolves oracle prices through `price-resolve`, which enforces both a freshness check (`oracle-timestamp-fresh`) and — for Pyth-sourced feeds — a confidence-interval bound via `check-confidence` against `max-confidence-ratio` (default 10% of price) [1](#0-0) . This is analogous to Unitas's `_checkPrice` min/max deviation gate: when the confidence interval Pyth reports for a token widens beyond the configured ratio — which is a well-documented Pyth behavior during high volatility or a depeg event — `check-confidence` reverts with `ERR-PRICE-CONFIDENCE-LOW`, exactly mirroring the reported bug class where "if any stable depegs, oracle will fail, disabling swaps."

### Finding Description
`resolve-pyth` fetches `{price, conf, expo, publish-time}` from `pyth-storage-v4` and unconditionally calls `check-confidence`, which reverts if `confidence > price * max-confidence-ratio / BPS` [2](#0-1) . This function is invoked by `resolve-price-feed` → `price-resolve` for every asset whose oracle type is `TYPE-PYTH` [3](#0-2) .

Crucially, `price-resolve` is batched via `price-multi-resolve`/`iter-price-multi`, which folds over the *entire list* of assets a user has as collateral/debt and asserts `valid` is true for the whole batch — if a single asset's price resolution reverts (returns an `err`), the accumulator's `valid` flag flips to `false` and the top-level `asserts!` in `price-multi-resolve` fails with `ERR-ORACLE-MULTI` for the *whole call* [4](#0-3) . This batch is built by `get-assets`, which is used to evaluate a user's full position (collateral + debt) for health/LTV checks used across market operations [5](#0-4) .

As a result, if a *single* stablecoin (e.g. USDC or USDH) in the enabled-collateral set experiences elevated volatility/depeg such that Pyth's published confidence interval exceeds the 10% threshold, `check-confidence` reverts for that one asset, which cascades through `price-multi-resolve`'s all-or-nothing `asserts!` and blocks price resolution — and therefore health checks — for every user whose position touches that asset class, even though their other collateral/debt is unaffected. Liquidations that read disabled-collateral prices on demand via `price-resolve` are similarly exposed [6](#0-5) .

### Impact Explanation
This is a temporary freezing-of-funds condition: when a widely-used collateral/debt asset (e.g., USDC) depegs or becomes volatile enough that Pyth's confidence band exceeds the 10% cap, any operation requiring `get-assets`/`price-multi-resolve` for a position that includes that asset — including withdraw and repay, which users need to *exit* their position — reverts. Users holding otherwise-healthy positions cannot withdraw collateral or repay debt to protect themselves precisely during the market stress event that most requires it, matching the High-severity "temporary freezing of funds" category.

### Likelihood Explanation
Confidence-interval widening during depeg/high-volatility events is a normal, externally-observed Pyth behavior (not attacker-induced), so this triggers under real market conditions rather than requiring an exploit. The all-or-nothing batch design in `iter-price-multi`/`price-multi-resolve` guarantees that a failure on any single asset in a user's enabled set blocks resolution for the entire position, amplifying the blast radius beyond just the affected asset.

### Recommendation
Do not fail the entire batch when a single asset's confidence check fails; instead cache/reuse the last valid price for that specific asset (with an explicit staleness cutoff) or exclude/quarantine only the affected asset from the position evaluation while still allowing withdraw/repay against the healthy remainder. Consider making the confidence-ratio bound configurable per-asset and widening it for known-stable pairs, and ensure `withdraw`/`repay` paths (which reduce risk) are not blocked by the same all-or-nothing oracle gate used for `borrow`.

### Proof of Concept
1. Pyth confidence interval for USDC/USD widens beyond `max-confidence-ratio` (10%) during a real-world depeg/volatility event (e.g., banking-crisis-style USDC de-peg).
2. Any user with USDC/zUSDC enabled as collateral or debt calls `withdraw` or `repay` on an unrelated asset (e.g., STX); the health check path calls `get-assets` → `price-multi-resolve` which includes USDC in the oracle list [5](#0-4) .
3. `price-resolve` for USDC calls `resolve-pyth` → `check-confidence`, which reverts with `ERR-PRICE-CONFIDENCE-LOW` [2](#0-1) .
4. `iter-price-multi` marks the batch invalid; `price-multi-resolve`'s `asserts!` reverts the whole call with `ERR-ORACLE-MULTI` [7](#0-6) .
5. The user's withdraw/repay transaction reverts, even though it does not touch USDC directly — funds are frozen until the depeg resolves or confidence narrows.

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))
