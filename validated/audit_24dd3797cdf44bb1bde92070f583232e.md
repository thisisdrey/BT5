### Title
Missing monotonicity/sanity check on external stSTX ratio used in oracle price resolution - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`resolve-ststx` in the market oracle pipeline fetches an external stSTX/STX exchange ratio via `call-ststx-ratio` and immediately multiplies it into the collateral price with no check that the ratio can only increase (as staking-derived exchange rates should) or is within any sane bound relative to the last known value. This mirrors the ibBTC `pricePerShare` finding: an external, oracle-like value is trusted verbatim to compute the value transferred/valued by the protocol.

### Finding Description
`price-resolve` fetches a base price via `resolve-price-feed`, then applies `resolve-callcode`, which for `CALLCODE-STSTX` (and transitively `CALLCODE-ZSTSTX`) calls `resolve-ststx`: [1](#0-0) 

```
(define-private (resolve-ststx (p uint))
  (let ((ratio (unwrap! (call-ststx-ratio) ERR-ORACLE-CALLCODE)))
    (ok (mul-div-down p ratio STSTX-RATIO-DECIMALS))))
```

The only validation applied downstream is on the *final* price magnitude and the *base* oracle feed's timestamp/staleness, not on the ratio itself: [2](#0-1) 

`oracle-price-legal` only enforces `price > 0`, and `oracle-timestamp-fresh` only checks the freshness of the *underlying* Pyth/DIA feed timestamp — neither compares the newly-read `ratio` against any previously observed value to reject a ratio that decreases (a real staking exchange rate for stSTX should be monotonically non-decreasing over time, exactly like `pricePerShare` in the ibBTC report). This is the same missing invariant as the referenced report: an externally-sourced, monotonic-by-design conversion rate is consumed without a floor/monotonicity check.

Because `resolve-ztoken` (used for zstSTX pricing) also multiplies by the vault's internal liquidity index on top of this ratio, any bad/manipulated `call-ststx-ratio` reading propagates directly into the price used for collateral valuation, health checks, and liquidation calculations for stSTX/zstSTX: [3](#0-2) 

### Impact Explanation
If the external stSTX ratio source is buggy, stale, or exploited to return an inflated ratio, stSTX/zstSTX collateral will be over-valued in the market's health-check/oracle pipeline. Borrowers can then draw down other vaults' real underlying liquidity (USDC, USDH, sBTC, STX) against collateral that is not actually worth that much, resulting in under-collateralized debt and drainage of real assets from the vaults — a direct theft of user/protocol funds and potential protocol insolvency, the same class of impact as draining Curve's wibbtc reserves in the original report.

### Likelihood Explanation
This requires only a bug, misconfiguration, or compromise in the external stSTX ratio provider `call-ststx-ratio` calls into — no privileged Zest role or DAO action is needed to trigger the effect once such a bad reading occurs. Any ordinary principal supplying/borrowing against stSTX/zstSTX collateral would automatically benefit from mispriced collateral, since the market has no independent check to reject an anomalous ratio.

### Recommendation
Track the last-seen stSTX ratio (similar to the `last-update` map used for staleness) and enforce that a new ratio can only increase (or increase within a bounded step) versus the previously accepted value, rejecting the update (or falling back to the last known-good value) otherwise, consistent with the report's recommended mitigation for `pricePerShare`.

### Proof of Concept
1. External ststx staking contract queried by `call-ststx-ratio` returns/experiences a bug that reports a ratio higher than the real STX-per-ststx backing.
2. A user deposits stSTX (or zstSTX) as collateral in the Zest market.
3. `price-resolve` → `resolve-callcode` → `resolve-ststx` computes an inflated collateral price with no check against the previous ratio, since `oracle-price-legal`/`oracle-timestamp-fresh` do not validate the ratio's trend.
4. Using this inflated collateral valuation, the user borrows other assets (e.g., USDC) up to the health-check limit, receiving more real liquidity than their real stSTX backing justifies.
5. The user repays or lets the position go unhealthy after withdrawing the real borrowed assets, leaving the protocol with a bad debt / insolvency exposure sized to the ratio manipulation, mirroring the wibbtc drain from a manipulated `pricePerShare`.

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
