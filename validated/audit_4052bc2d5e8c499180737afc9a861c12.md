### Title
Unbounded reference-count loops in `DeleteRefs` allow single-RPC DoS via unlimited `refnames` iteration - ([File: internal/gitaly/service/ref/delete_refs.go])

### Summary
`DeleteRefs` builds an in-memory slice `refnames` from either the caller-supplied `Refs` field or, when `ExceptWithPrefix` is used, from **all** references currently in the repository, and then performs multiple full, unbounded loops over that slice before ever calling `updater.Prepare()`/`Commit()`. There is no cap on the number of entries the RPC will process in a single call.

### Finding Description
`refsToRemove` returns either the raw `req.GetRefs()` list (fully attacker-controlled length, limited only by gRPC message size) or, for the `ExceptWithPrefix` variant, iterates every existing reference returned by `repo.GetReferences(ctx)` with no truncation: [1](#0-0) 

The resulting `refnames` slice is then walked three separate times in `DeleteRefs` itself — once to validate each ref name, once to queue each `updater.Delete(ref)` call and update a running vote hash, and implicitly again inside the updater/`git update-ref` transaction: [2](#0-1) 

None of these loops, nor the initial validation in `validateDeleteRefRequest`, impose any limit on the size of `req.GetRefs()` or on the number of references discovered via `ExceptWithPrefix`: [3](#0-2) 

This is directly analogous to the reported `_processOrders()` issue: an attacker-influenced, unbounded-length collection is iterated multiple times within a single call before any commit/finalization step, so the cost of the RPC scales linearly (or worse, given the additional `git update-ref --stdin` transaction and voting round-trip) with an attacker-controllable or repository-size-dependent input length, with no pagination, batching, or count limit.

### Impact Explanation
A repository that has accumulated a very large number of references (e.g. via `keep-around`, `merge-requests`, `environments`, or `pipeline` namespaces that GitLab creates over time, or via a client repeatedly calling `UpdateReferences`/`git push` to create many refs) can be targeted with a single `DeleteRefs` call using `ExceptWithPrefix` (or a large `Refs` list) to force Gitaly to build and iterate an enormous in-memory slice and run an oversized `git update-ref` transaction in one RPC. This can consume excessive CPU/memory and block the goroutine/gRPC worker for an extended period, and if it fails partway (e.g. hitting `AlreadyLockedError` on any one of many refs) the whole batch fails, since `DeleteRefs`/`updateref` treat it as one atomic transaction. Because `DeleteRefs` is a `MUTATOR` RPC reachable by any user with push/write access to the repository (no special privilege required), this is a reachable DoS vector against a single repository's Gitaly node, and can be repeated to keep the storage node busy, degrading pushes/fetches for other users of that node.

### Likelihood Explanation
Likelihood is moderate: it requires either (a) the caller to submit a large `Refs` array (bounded mainly by gRPC's default message-size limit, so tens of thousands of short ref names are plausible in one request), or (b) the target repository to have already accumulated a very large number of references, which is a realistic and common situation for long-lived GitLab repositories with many merge requests/environments/keep-around refs. No authentication bypass or special privilege is required beyond normal write access to the repository.

### Recommendation
- Enforce an explicit maximum on `len(req.GetRefs())` and validate it in `validateDeleteRefRequest`, rejecting oversized requests early with `InvalidArgument`.
- For `ExceptWithPrefix`, cap the number of references considered per call or process/delete them in bounded batches (e.g. chunk the transaction and commit incrementally), rather than building one unbounded slice and one unbounded `git update-ref` transaction.
- Consider converting the reference-collection/validation loops to streaming or paginated processing (consistent with how `ListRefs` already implements pagination) so a single call cannot force unbounded in-memory accumulation or an unbounded git transaction.

### Proof of Concept
1. As a user with write access to a repository, create (or let accumulate over time) a very large number of references, e.g. hundreds of thousands of `refs/merge-requests/*` or `refs/keep-around/*` entries — this happens naturally in busy GitLab projects.
2. Call `DeleteRefs` with `ExceptWithPrefix` set to a prefix that excludes only a small subset (e.g. `refs/heads/`), causing `refsToRemove` to collect nearly all references in the repository. [4](#0-3) 
3. Observe the RPC iterating over the full, unbounded reference list three times and issuing a single very large `git update-ref` transaction, consuming disproportionate CPU/memory/time on the Gitaly node and potentially failing atomically due to a single locked reference, causing the whole (expensive) operation to be retried. [5](#0-4)

func (s *server) refsToRemove(ctx context.Context, repo *localrepo.Repo, req *gitalypb.DeleteRefsRequest) ([]git.ReferenceName, error) {
	if len(req.GetRefs()) > 0 {
		refs := make([]git.ReferenceName, len(req.GetRefs()))
		for i, ref := range req.GetRefs() {
			refs[i] = git.ReferenceName(ref)
		}
		return refs, nil
	}

	prefixes := make([]string, len(req.GetExceptWithPrefix()))
	for i, prefix := range req.GetExceptWithPrefix() {
		prefixes[i] = string(prefix)
	}

	existingRefs, err := repo.GetReferences(ctx)
	if err != nil {
		return nil, err
	}

	var refs []git.ReferenceName
	for _, existingRef := range existingRefs {
		if hasAnyPrefix(existingRef.Name.String(), prefixes) {
			continue
		}

		refs = append(refs, existingRef.Name)
	}

	return refs, nil

func validateDeleteRefRequest(ctx context.Context, locator storage.Locator, req *gitalypb.DeleteRefsRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetExceptWithPrefix()) > 0 && len(req.GetRefs()) > 0 {
		return errors.New("ExceptWithPrefix and Refs are mutually exclusive")
	}

	if len(req.GetExceptWithPrefix()) == 0 && len(req.GetRefs()) == 0 { // You can't delete all refs
		return errors.New("empty ExceptWithPrefix and Refs")
	}

	for _, prefix := range req.GetExceptWithPrefix() {
		if len(prefix) == 0 {
			return errors.New("empty prefix for exclusion")
		}
	}

	for _, ref := range req.GetRefs() {
		if len(ref) == 0 {
			return errors.New("empty ref")
		}
	}

	return nil
}
