### Title
Missing null-block-id filter in `TenureStartEnd::from_inventory` allows malicious inventory bits to produce a bogus all-zero tenure-start block ID - (File: stackslib/src/net/download/nakamoto/tenure.rs)

### Summary
`TenureStartEnd::from_inventory` builds `TenureStartEnd` records directly from `wt_start.winning_block_id` and `wt_end.winning_block_id` without ever checking whether these are the null/no-winner sentinel `StacksBlockId([0x00;32])`. Unlike other call sites in the download pipeline (`stackslib/src/net/download/nakamoto/download_state_machine.rs`, which contains the `StacksBlockId([0x00;32])` skip check), `from_inventory` has no such guard, so a peer's inventory bit set on a "missed"/no-winner sortition index can cause `TenureStartEnd.start_block_id` to be populated with an all-zero block ID.

### Finding Description
`WantedTenure.winning_block_id` is derived from the node's own sortition DB and legitimately can be `StacksBlockId([0x00;32])` for a sortition where no block-commit won (a missed sortition) - this is a normal, reachable local chain state, not an attacker-fabricated value. `NakamotoTenureInv.tenures_inv` bit vectors, however, are fully attacker-controlled: a remote peer can set bit `i` to `1` to claim it has tenure data starting at sortition `i`.

In `TenureStartEnd::from_inventory` (`stackslib/src/net/download/nakamoto/tenure.rs`, lines 129-205), the algorithm scans `invbits` for the next set bit (`wt_start_idx`) and unconditionally uses `wanted_tenures[wt_start_idx].winning_block_id` as `start_block_id`: [1](#0-0) 
There is no check comparable to `if ibh == &StacksBlockId([0x00;32]) { continue; }` anywhere in this function - the entire body was inspected and no such filter exists.

If the local sortition history contains a missed sortition at index `wt_start_idx` (i.e., `winning_block_id == [0x00;32]`), a malicious peer only needs to advertise bit `wt_start_idx` as set in its `tenures_inv` to make this function treat the null block ID as a legitimate tenure-start block, producing `TenureStartEnd { start_block_id: StacksBlockId([0x00;32]), .. }`, which is then inserted into `AvailableTenures`.

### Impact Explanation
Downstream, `AvailableTenures` entries are used to construct `NakamotoTenureDownloader` instances scoped to a specific `tenure_start_block_id`. An entry with `start_block_id == [0x00;32]` causes that downloader to issue a fetch for a block that can never exist, wedging that download slot (the state machine cannot make progress on that tenure without external mitigation) - an availability degradation on a single peer/tenure download resource, matching the "High - steering a node off tip / false inventory" category insofar as it corrupts the node's computed available-tenure map from a peer's advertised (and attacker-controlled) inventory bits.

### Likelihood Explanation
Preconditions: the node's own sortition history must contain at least one missed sortition (a naturally-occurring, common on-chain event) within the reward cycle range being synced, and a remote peer must serve a `NakamotoTenureInv` with the corresponding bit set. No secret, signature, or privileged role is required - inventory messages are ordinary P2P gossip content from any connected peer, and an attacker fully controls the bits they advertise. This is cheap and repeatable per download cycle/reward-cycle inventory sync.

### Recommendation
Add an explicit guard in `TenureStartEnd::from_inventory` mirroring the one used in `download_state_machine.rs`: skip/reject any `wt_start`/`wt_end` candidate whose `winning_block_id == StacksBlockId([0x00;32])`, continuing the search for the next valid set bit instead of constructing a `TenureStartEnd` with a null block ID.

### Proof of Concept
Rust unit test in `stackslib/src/net/download/nakamoto/tenure.rs` (or its test module):
1. Construct `wanted_tenures` where index `i` has `winning_block_id = StacksBlockId([0x01;32])` (tenure-start bit) and index `wt_start_idx` (`i+1`) has `winning_block_id = StacksBlockId([0x00;32])` (missed sortition).
2. Build a `NakamotoTenureInv` with bits `i` and `wt_start_idx` both set to `true` for reward cycle `rc`.
3. Call `TenureStartEnd::from_inventory(rc, &wanted_tenures, None, &pox_constants, first_burn_height, &invs)`.
4. Assert the returned `AvailableTenures` map contains an entry whose `start_block_id == StacksBlockId([0x00;32])`, demonstrating the null block ID is never filtered out.
