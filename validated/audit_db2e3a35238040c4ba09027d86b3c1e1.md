## Analysis: Local Analog Found

The Surge Protocol bug is a classic "rate update forced to zero by frequent small calls, but the checkpoint still advances" bug: `change = timeDelta * rateNumerator / recoveryDuration` rounds down to `0` when called too often relative to the denominator, yet the timestamp checkpoint is still advanced, so the missed accrual is permanently lost.

The exact same pattern exists in `pallet-asset-rewards`'s reward-per-token accounting.

### Title
Reward-per-token accrual can be permanently frozen via integer-division rounding griefing - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`Pallet::<T>::reward_per_token` computes the pool's reward accrual as `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`. `update_pool_rewards` then unconditionally advances `last_update_block` to the current block and stores this (possibly zero) increment, regardless of whether the computed increment was non-zero. Any signed account can call `stake`/`unstake`/`harvest_rewards` every block to keep `blocks_elapsed` at `1`, which — whenever `total_tokens_staked` is large relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR` — makes the integer division floor to zero every single block, permanently losing that block's reward accrual for the entire pool.

`stake`, `unstake`, and `harvest_rewards` are all permissionless, `ensure_signed`-gated extrinsics that call `update_pool_and_staker_rewards` (which calls `reward_per_token` then `update_pool_rewards`) before performing their own logic: [3](#0-2) 

There is no minimum-amount check on `stake`, so an attacker can call `stake(pool_id, 0)` (or any negligible amount) once per block, cheaply, for the sole purpose of advancing `last_update_block` to `current_block_number()` while `rewardable_blocks_elapsed` is always `1`. If `reward_rate_per_block * 1 * PRECISION_SCALING_FACTOR (4096) < total_tokens_staked`, the division in `reward_per_token` floors to `0`, so `reward_per_token_stored` never advances even though the checkpoint (`last_update_block`) does. Because the accrual is computed incrementally block-by-block from the moving checkpoint rather than from the pool's genesis, once a block's worth of reward is "rounded to zero" and the checkpoint is moved past it, that reward is unrecoverable — there is no mechanism to retroactively credit skipped, sub-threshold periods.

### Impact Explanation
This breaks the "message queues, bridge markers, receipts, and payout state must only advance after ... settlement succeed atomically" invariant analog: the checkpoint (`last_update_block`) advances even when the actual settlement amount (`reward_per_token` increment) is zero due to rounding. Any griefer — without needing large capital, admin rights, or governance — can permanently stall reward distribution for every staker in a pool that has enough `total_tokens_staked` relative to `reward_rate_per_block`. Reward tokens remain locked/undistributed in the pool account indefinitely, causing loss of expected rewards for depositors while the pool appears active (funds effectively "stuck", matching the "permanent user-fund ... lock" impact class).

### Likelihood Explanation
Likelihood is non-trivial for any pool where `total_tokens_staked` is even moderately large relative to `reward_rate_per_block` (a very plausible/normal configuration, since `PRECISION_SCALING_FACTOR` is only `4096` — a modest multiplier). No special privileges are required; the attacker just submits ordinary `stake`/`unstake` calls, one per block, paying only ordinary transaction fees. Pools with high stake concentration or admins that set `reward_rate_per_block` conservatively low are naturally exposed without any attacker action needed to inflate `total_tokens_staked` further.

### Recommendation
`update_pool_rewards`/`reward_per_token` should not silently advance `last_update_block` when the computed reward increment for the elapsed window rounds to zero purely due to `total_tokens_staked` scale; instead the pallet should either (a) retain fractional/undistributed remainder precision across updates (e.g., track remainder separately, similar to how `TargetedFeeAdjustment` and other pallets avoid "stuck-at-floor" states), or (b) only advance `last_update_block` once accrued (but not yet applied) reward exceeds the rounding threshold, deferring the checkpoint update otherwise so the elapsed window keeps accumulating instead of resetting to `1` block each call.

### Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R` and stakes accumulate such that `total_tokens_staked = S`, where `S > R * 4096`.
2. Attacker (any signed account) calls `stake(pool_id, 0)` (or a negligible amount) in every single block.
3. Each call triggers `update_pool_and_staker_rewards` → `reward_per_token`, computing `R * 1 * 4096 / S = 0` (integer division), then `update_pool_rewards` sets `last_update_block = current_block` and `reward_per_token_stored` unchanged (still incremented by 0).
4. Because `last_update_block` is reset to the current block every time, `rewardable_blocks_elapsed` never exceeds `1` for any subsequent computation, so the division result is `0` forever.
5. Legitimate stakers who call `harvest_rewards` at any later point observe `staker_info.rewards` frozen at whatever it was before the attack began — the pool's reward tokens are never distributed despite `reward_rate_per_block` and elapsed blocks being non-zero. [4](#0-3)

				amount,

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			pool_info: &PoolInfoFor<T>,
