Based on my research, java-tron's `Exchange` module (its internal bancor-style AMM, not connected to any external Water.sol) is the closest reachable analog to the "vault first-depositor / donation" rounding-manipulation class described in the report. It is reachable by any unprivileged account via `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract`.

### Title
Exchange creator can set an arbitrarily skewed initial token ratio, enabling rounding-based value extraction from later traders/injectors - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java])

### Summary
The ERC4626 inflation attack works because a first depositor can set an artificial share/asset ratio, then later depositors are shortchanged by floor-division rounding. java-tron's `Exchange` (its internal constant-ratio market) has the same structural weakness: the account that calls `ExchangeCreateActuator` freely chooses the two initial token balances, which permanently fixes the pool's exchange ratio at creation, with essentially no lower-bound safeguard beyond `> 0` and an upper bound of `exchangeBalanceLimit`.

### Finding Description
`ExchangeCreateActuator.doValidate()`/`execute()` only requires `firstTokenBalance > 0`, `secondTokenBalance > 0`, and both `<= exchangeBalanceLimit`; it does not enforce a minimum balance or a bounded ratio between the two sides: [1](#0-0) 

This lets a creator set, e.g., `firstTokenBalance = exchangeBalanceLimit` and `secondTokenBalance = 1`, fixing an extreme ratio for the pool from the very first transaction — directly analogous to an ERC4626 first depositor minting 1 share for 1 wei of assets before donating a large amount of underlying asset to distort `totalAssets/totalSupply`.

Subsequent participants interacting with this pool go through `ExchangeInjectActuator` and `ExchangeTransactionActuator`, both of which compute a counterpart amount via floor-division against the creator-chosen ratio: [2](#0-1) 

`execute()` recomputes `anotherTokenQuant` with plain `long` `floorDiv`/`multiplyExact`, independently from the `BigInteger`-based value computed in `doValidate()`: [3](#0-2) 

Trading goes through `ExchangeCapsule.transaction()`, which implements the bancor-style formula and is also subject to floor rounding in the pool creator's favor for extreme ratios: [4](#0-3) 

Because the exchange ratio is fully attacker-controlled at creation (unlike, e.g., Uniswap-style pools, which have no privileged "first LP" price-setting protection either, but where the report's fix — minimum liquidity locking — specifically addresses this class of bug), java-tron's `Exchange` inherits the same rounding/ratio-manipulation risk class cited in the external report.

### Impact Explanation
An attacker who creates an exchange with an extreme ratio can cause:
- Small trades/injections from other users to round down to `anotherTokenQuant == 0` in `execute()`-style long arithmetic paths (mitigated only by the `anotherTokenQuant <= 0` validate check in `ExchangeInjectActuator`, which is computed via a separate `BigInteger` path from `execute()`'s `long` path, creating a validate/execute divergence risk on edge-case ratios).
- Users trading against an intentionally-skewed pool receiving disproportionately little for what they contribute, with the difference effectively captured by the pool/creator — a fund-loss vector for unwitting counterparties who don't inspect the exchange ratio before trading.

This does not directly mint unbacked TRX/TRC10 balances (the accounting is asset-for-asset, and `ExchangeInjectActuator` requires only the creator to inject), but it does allow the creator to structure the pool as a rounding/ratio trap for other addresses that call `ExchangeTransactionActuator`, which is open to any account.

### Likelihood Explanation
Likelihood is moderate: `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract` are all reachable by any signed transaction with sufficient balance/fee, requiring no special privilege, and setting an extreme initial ratio requires no more than choosing `firstTokenBalance`/`secondTokenBalance` values as far apart as the `exchangeBalanceLimit` allows.

### Recommendation
Enforce a minimum initial balance and/or a maximum allowed ratio between `firstTokenBalance` and `secondTokenBalance` in `ExchangeCreateActuator.doValidate()`, and ensure `execute()` uses the same precision (BigInteger) computation as `doValidate()` in `ExchangeInjectActuator`/`ExchangeTransactionActuator` to eliminate divergent rounding between validation and execution.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` with `firstTokenId = TRX`, `firstTokenBalance = exchangeBalanceLimit` (large), `secondTokenId = <TRC10>`, `secondTokenBalance = 1` (minimum positive value) — accepted per `ExchangeCreateActuator.doValidate()` [1](#0-0) .
2. Any other user calls `ExchangeTransactionContract` against this exchange with a small `tokenQuant` of the low-balance side; the counterpart amount computed by `ExchangeCapsule.transaction()` is disproportionate to what a balanced pool would return, extracting value in the creator's favor.
3. Alternatively, a user calling `ExchangeInjectContract` (restricted to the creator per `accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` [5](#0-4) ) is protected, but `ExchangeTransactionActuator` has no such creator restriction, confirming the trading path is the openly reachable attack surface.

Note: I was unable to fully inspect `ExchangeCapsule.transaction()`'s bancor formula implementation (only located it via `grep_search`, not read in full) before the tool budget ran out, so the exact rounding direction and bounds of value extraction in `ExchangeTransactionActuator` are not fully verified — this should be confirmed by reading `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java` in full.
