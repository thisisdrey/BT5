### Title
Bank/Group rate limiter can be griefed by front-running to DOS legitimate withdrawals and borrows - (File: `programs/marginfi/src/state/rate_limiter.rs`, `programs/marginfi/src/utils/general.rs`)

### Summary
The Optimism report describes a shared, per-block-resetting resource quota (`MAX_RESOURCE_LIMIT`) that can be cheaply exhausted by an attacker front-running a victim's transaction, causing the victim's transaction to revert and griefing/censoring legitimate usage. marginfi-v2 has a structurally analogous shared, time-windowed capacity primitive — the bank-level and group-level rate limiters — that gate withdrawals and borrows and can similarly be exhausted by any unprivileged user shortly before a victim's withdraw/borrow, causing the victim's transaction to revert.

### Finding Description
When an admin enables rate limiting on a bank, every withdraw/borrow (`lending_account_withdraw`, `lending_account_borrow`, and the Kamino/Drift/Solend/JupLend withdraw variants) consumes capacity from a dual-window (hourly/daily) limiter via `record_withdrawal_outflow`: [1](#0-0) 

The underlying window logic checks `remaining_capacity` and reverts with `BankHourlyRateLimitExceeded` / `BankDailyRateLimitExceeded` (or the group equivalents) if the requested outflow does not fit: [2](#0-1) 

Because the bank's `rate_limiter` field is mutated inline and immediately (unlike the group limiter, which is only checked read-only and settled asynchronously by an off-chain admin), any unprivileged user with a deposited position in the bank can submit a withdraw/borrow that consumes the remainder of the hourly or daily outflow window. A subsequent legitimate user's withdraw/borrow in the same window will then revert with `BankHourlyRateLimitExceeded`/`BankDailyRateLimitExceeded`, exactly mirroring the Optimism pattern of "attacker fills up the shared resource limit → victim's transaction reverts."

Deposits/repays are the only way to *release* capacity (`record_inflow`), and per the project's own documentation, "Deposits/repays release capacity. Withdraws/borrows consume capacity": [3](#0-2) 

This means an attacker can (a) withdraw an amount that saturates the remaining window capacity right before a victim's withdraw/borrow is expected to land, causing the victim's tx to fail, and (b) immediately redeposit the same funds to restore their own position and even release capacity back for their own subsequent use — at a cost limited to transaction/priority fees and possibly a brief, self-controlled forgone-yield period. This is conceptually the same cost asymmetry flagged in the Optimism report: the attacker's cost of "renting" the shared quota is far lower than the cost the victim would need to pay to guarantee non-interference.

### Impact Explanation
A successful attack reverts legitimate users' withdraw/borrow transactions against a specific bank (or, via the group-level check, across an entire group) for the remainder of the hourly/daily window. This is a denial-of-service against unprivileged core accounting paths (withdraw/borrow), degrading availability/UX for depositors and borrowers trying to exit or draw down positions, similar in class to the cited Optimism report's "griefs users who simply want to bridge assets" impact. It does not directly cause theft or insolvency, so the impact is capped at griefing/availability degradation for as long as the attacker is willing to repeat the maneuver each window.

### Likelihood Explanation
Likelihood depends entirely on whether a given bank/group actually has rate limiting configured (windows are disabled when `max_outflow == 0`), which is an admin opt-in mitigation rather than a default-on protocol-wide control. Where enabled, the attack requires only an existing deposited balance in the target bank (no special privilege) and ordinary transaction submission with priority-fee front-running, which is readily achievable on Solana. This makes the likelihood moderate and conditional on rate-limiter usage; it does not affect banks where the admin has left rate limiting disabled.

### Recommendation
- Do not let a single unprivileged actor's outflow be able to fully saturate the remaining window capacity in one shot when other legitimate demand is expected; consider a per-account or per-transaction outflow sub-cap within the window, separate from the aggregate window limit.
- Consider weighting/tracking rate-limiter consumption by account so that an account that withdraws-then-redeposits within the same window cannot repeatedly "reserve and release" capacity to selectively block other users' transactions.
- Document this limitation explicitly for admins configuring `configure_bank_rate_limits` / `configure_group_rate_limits`, since — like the L1→L2 gas market in the cited report — any strict, non-account-scoped shared quota checked at transaction time is inherently frontrunnable.

### Proof of Concept
1. Admin enables a bank-level hourly rate limit of `N` tokens via `lending_pool_configure_bank_rate_limits` (see `programs/marginfi/src/instructions/marginfi_group/configure_rate_limits.rs`, referenced by `BankRateLimiterImpl`/`record_withdrawal_outflow`).
2. Attacker (any user with a deposited balance ≥ `N` in that bank) observes a pending victim withdraw/borrow transaction in the mempool/leader schedule.
3. Attacker submits (front-runs) a withdraw of `N` tokens from the same bank, which succeeds and calls `bank.rate_limiter.try_record_outflow(N, now)`, exhausting the hourly window as shown in: [4](#0-3) 
4. Victim's withdraw/borrow transaction, requesting any nonzero amount, now fails with `BankHourlyRateLimitExceeded` because `remaining_capacity` is 0, as demonstrated in the project's own test: [5](#0-4) 
5. Attacker redeposits the withdrawn `N` tokens, which calls `record_inflow` and restores window capacity for future use, at essentially no lasting capital cost beyond transaction fees — repeatable every window to sustain the denial of service against that bank's withdrawers/borrowers.

            fn try_record_outflow(
                &mut self,
                amount: u64,
                current_timestamp: i64,
            ) -> MarginfiResult<()> {
                // Advance windows before computing remaining capacity to avoid boundary gaps.
                self.hourly.maybe_advance_window(current_timestamp);
                self.daily.maybe_advance_window(current_timestamp);

                // An amount that does not fit in i64 cannot be represented and
                // is treated as exceeding every window.
                let amount_i64 = amount_as_i64(amount);
                let exceeds = |remaining: i64| match amount_i64 {
                    Some(a) => a > remaining,
                    None => true,
                };

                if self.hourly.is_enabled() {
                    let remaining = self.hourly.remaining_capacity(current_timestamp);
                    if exceeds(remaining) {
                        msg!(
                            concat!(
                                $prefix,
                                " hourly rate limit exceeded: amount={}, remaining={}"
                            ),
                            amount,
                            remaining
                        );
                        return err!(MarginfiError::$hourly_err);
                    }
                }

                if self.daily.is_enabled() {
                    let remaining = self.daily.remaining_capacity(current_timestamp);
                    if exceeds(remaining) {
                        msg!(
                            concat!(
                                $prefix,
                                " daily rate limit exceeded: amount={}, remaining={}"
                            ),
                            amount,
                            remaining
                        );
                        return err!(MarginfiError::$daily_err);
                    }
                }

                // Both checks passed, record the outflow.
                if self.hourly.is_enabled() {
                    self.hourly.try_record_outflow(amount, current_timestamp)?;
                }
                if self.daily.is_enabled() {
                    self.daily.try_record_outflow(amount, current_timestamp)?;
                }

                Ok(())
            }
