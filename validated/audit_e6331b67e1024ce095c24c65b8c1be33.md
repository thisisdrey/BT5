### Title
Heap out-of-bounds read parsing ZIP/JAR central directory extra fields with unchecked length fields - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the central directory of a ZIP/JAR file entirely from attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and, inside the extra-field loop, an attacker-controlled `data_size`, without ever calling the bounds-checking helper `EnsureRemaining()` that is used everywhere else in the same file (e.g. in `ProcessLocalFileEntry`, `SkipFile`, `ProcessFile`). This mirrors the ezXML `ezxml_decode()` class of bug: a length-prefixed field in untrusted structured input is trusted to compute a read offset/size, with no validation against the actual buffer bounds, producing a heap out-of-bounds read.

### Finding Description
`ProcessCentralDirEntry` reads the fixed part of a central-directory-file-header record and the variable-length `file_name`, `extra_field`, and `comment` fields purely via pointer arithmetic on the mmap'd input buffer `zipdata_in_`: [1](#0-0) 

Crucially, unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining(file_name_length_, "file_name")` and `EnsureRemaining(extra_field_length_, "extra_field")` before advancing `p`: [2](#0-1) 

`ProcessCentralDirEntry` never validates `file_name_length`, `extra_field_length`, or `file_comment_length` against the remaining bytes in the mapped file before doing `memcpy`, `p += file_name_length`, or `p += extra_field_length`.

The extra-field parsing loop is worse — it uses pointer *equality* rather than a bounded comparison to detect loop termination: [3](#0-2) 

`extra_p` advances by an attacker-controlled `data_size` (`get_u2le`, up to 0xFFFF) read from the file itself. If `data_size` causes `extra_p` to overshoot the expected end pointer `p` (computed from `extra_field_length`), the loop condition `extra_p != p` never becomes true again, so the loop keeps calling `get_u2le(extra_p)` far outside the bounds of the mapped extra-field region — and potentially outside the entire mmap'd input file — reading heap memory that does not belong to the ZIP central directory at all. `get_u4le`/`get_u2le` (from `common.h`) perform raw unaligned byte reads with no bounds checks of their own.

Since the central directory offset (`central_dir_`) and the parsing loop that repeatedly calls `ProcessCentralDirEntry` (see `CalculateOutputLength` / `ProcessNext`) is driven only by the End-Of-Central-Directory record's own length fields — also attacker-controlled — a crafted JAR/ZIP can push parsing arbitrarily far past the true end of the central directory, well beyond what `EnsureRemaining` gating elsewhere in the file is meant to prevent.

### Impact Explanation
This is reachable whenever `ijar` (Bazel's interface-jar-stripping tool, used by `java_library`/`java_import` and other Java rules to build/process interface jars) processes a ZIP/JAR whose bytes come from an external, attacker-influenced source — e.g. a prebuilt jar fetched via `http_jar`/`http_file`, a Maven artifact resolved through an external repository rule, or a jar checked into an untrusted branch that CI builds. A sha256/integrity check on the downloaded archive verifies only that the *bytes* match a fixed digest; it does not validate the internal structural consistency of the ZIP central directory, so a byte-exact, checksum-passing but maliciously malformed jar can still trigger this out-of-bounds read once ijar parses it. The result is a heap buffer over-read that can crash the Bazel build (worker process) or, in principle, leak adjacent heap memory contents into subsequently derived state, matching the impact class of CVE-2022-30045 (heap OOB read from a length-prefixed decode routine on crafted input).

### Likelihood Explanation
Likelihood is moderate-to-high for any project that consumes third-party or externally hosted prebuilt jars through Bazel's Java toolchain (a very common pattern, e.g. `rules_jvm_external`/`maven_install`, `http_jar`). No privileged access is required — only the ability to publish/serve one jar file that a victim's `MODULE.bazel`/`WORKSPACE` references. The bug requires no cooperation from a trusted root-repo `BUILD`/`.bzl` file; it triggers purely from the bytes of the archive during ijar's own parsing, independent of and after any checksum validation succeeds.

### Recommendation
Add the same `EnsureRemaining()` bounds checks used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before reading/advancing over `file_name_length`, `extra_field_length`, and `file_comment_length`. Additionally, change the extra-field loop condition from pointer equality (`extra_p != p`) to a bounded comparison (`extra_p < p`), and validate that each `data_size` does not cause `extra_p` to exceed the extra-field end boundary before reading `header_id`/`data_size`/`extra` data.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction would:
1. Programmatically construct a minimal valid ZIP/JAR whose single central-directory-file-header record declares `extra_field_length = N` but embeds, inside the first N bytes of the extra field, an extra-field entry with `data_size` set to a large value (e.g. `0xFFFF`) that is larger than the remaining bytes of the declared extra field / file.
2. Invoke the `ijar` binary (or the `InputZipFile`/`ZipExtractor` API directly, as done in `third_party/ijar/*_test.cc`) on this crafted jar.
3. Observe (under ASan/heap sanitizer) a heap-buffer-overflow (read) report inside `InputZipFile::ProcessCentralDirEntry`'s extra-field loop, or a SIGSEGV when `extra_p` walks past the mmap'd region, demonstrating the missing bounds validation described above.
