### Title
Fee-on-Transfer / Deflationary NEP-141 Tokens Break Ledger-vs-Reserve Conservation, Enabling Insolvency Theft - ([File: contracts/defuse/src/contract/tokens/mod.rs])

### Summary
`Contract::deposit` credits a depositor's internal ledger (and the global `total_supplies` for that `TokenId`) with the full nominal `amount` reported by the `ft_on_transfer` callback, without ever verifying that this amount matches the actual balance change the intents contract experienced on the underlying NEP-141 token. Because any NEP-141 contract can be deposited permissionlessly (no whitelist gate is visible in the deposit path), a fee-on-transfer/deflationary token breaks the invariant `value credited == value actually received`, letting a depositor mint more internal balance than backing tokens exist, at the expense of other holders of the same `TokenId`.

### Finding Description
`ft_on_transfer` takes the `amount` argument supplied by the calling token contract at face value and forwards it straight into `self.deposit(...)`: [1](#0-0) 

`deposit()` then increments both the owner's `token_balances` and the protocol-wide `total_supplies` for that `TokenId` by that same nominal `amount`, again with no cross-check against the contract's real on-chain balance of the token: [2](#0-1) 

If the deposited NEP-141 token deducts a transfer fee (or rebases downward) so that the intents contract's actual balance increase is smaller than the `amount` argument the token contract passes to `ft_on_transfer`, the internal ledger (`total_supplies` + the depositor's `token_balances` entry) will be overstated relative to the tokens the contract actually custodies for that `TokenId`. This breaks the binding the review rules call out explicitly: "value debited versus value delivered plus refunded." The mismatch is *per-`TokenId`*, so it directly threatens other depositors of the same token, not just the attacker's own funds.

Withdrawal makes the inflated ledger balance spendable: `internal_ft_withdraw`/`withdraw()` subtract the ledger amount and then trigger `ft_transfer`, whose resolver treats the promise as fully successful (crediting `used = amount.0`) whenever the raw NEAR promise doesn't fail, again without any independent balance check: [3](#0-2) 

An attacker can therefore: (1) deposit `X` units of a fee-on-transfer NEP-141 token, receiving `X` internal credit while the contract's real reserve only grows by `X - fee`; (2) immediately withdraw `X`, draining `fee` worth of the same token that belongs to the reserve backing other users' balances of that `TokenId`. Repeated across multiple deposit/withdraw cycles, this can fully drain the reserve for that token, leaving later withdrawers unable to redeem their legitimately-credited balances.

### Impact Explanation
This is a Critical-class issue under the stated criteria — "tokens moved, credited, or withdrawn without valid authorisation" / conservation of a pooled ledger vs actual custody is broken. The attacker profits by withdrawing more raw tokens than they net-deposited, and other holders of the same `TokenId` bear the loss when they later cannot fully withdraw due to the drained reserve.

### Likelihood Explanation
Requires only that the protocol accept (or a solver/user deposit) a real-world NEP-141 token whose `ft_transfer`/`ft_transfer_call` implementation deducts a fee or rebases balances outside of the exact transferred `amount` reported to `ft_on_transfer` — no privileged role, relayer key, or malicious node needed. Given deposits are permissionless for any NEP-141 contract account, likelihood depends only on such a token being listed/used, which the report class explicitly targets ("any ERC-20/NEP-141 is allowed").

### Recommendation
Before crediting `deposit()`, verify the actual balance delta on the token contract (e.g., via a `ft_balance_of` snapshot pre/post-transfer, or restrict deposits to an explicitly vetted token whitelist that excludes fee-on-transfer/rebasing tokens) so that `total_supplies`/`token_balances` credited never exceeds the token amount actually held in custody.

### Proof of Concept
1. Deploy (or use) a NEP-141 token contract that implements a transfer fee, e.g. `ft_transfer_call` internally moves `amount - fee` to the receiver while still invoking `ft_on_transfer(sender_id, amount, msg)` with the pre-fee `amount`.
2. User A deposits `1000` of this token via `ft_transfer_call` to the intents contract. `ft_on_transfer` (contracts/defuse/src/contract/tokens/nep141/deposit.rs:19-43) credits `1000` to A's `token_balances` and `total_supplies`, while the contract's actual on-chain token balance only increased by `950` (5% fee).
3. User B deposits `1000` of the same token normally in the same way, real balance again increases by `950`; ledger now shows `total_supplies = 2000`, real balance `= 1900`.
4. A withdraws `1000` via `FtWithdraw` (contracts/defuse/src/contract/tokens/nep141/withdraw.rs:53-106); the resolver marks the withdrawal fully `used` once the raw NEAR promise for `ft_transfer` succeeds, without checking actual token movement, draining `1000` of the `1900` real reserve.
5. B now cannot withdraw the full `1000` credited to them because only `900` real tokens remain in the contract for that `TokenId` — B's funds are impaired by A's transaction, netting A a profit relative to A's actual deposited value.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        require!(amount.0 > 0, "zero amount");

        let token_id = TokenId::Nep141(Nep141TokenId::new(env::predecessor_account_id()));

        let DepositMessage {
            receiver_id,
            action,
        } = if msg.is_empty() {
            DepositMessage::new(sender_id.clone())
        } else {
            msg.parse().unwrap_or_else(|e| panic!("{e}"))
        };

        self.deposit(
            receiver_id.clone(),
            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )
        .unwrap_or_else(|err| err.panic());

    pub(crate) fn deposit(
        &mut self,
        owner_id: AccountId,
        tokens: impl IntoIterator<Item = (TokenId, u128)>,
        memo: Option<&str>,
    ) -> Result<()> {
        let owner = self
            .storage
            .accounts
            .get_or_create(owner_id.clone())
            // deposits are allowed for locked accounts
            .as_inner_unchecked_mut();

        let mut mint_event = MtMintEvent {
            owner_id: owner_id.into(),
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into),
        };

        for (token_id, amount) in tokens {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            mint_event.token_ids.to_mut().push(token_id.to_string());
            mint_event.amounts.to_mut().push(amount);

            let total_supply = self
                .storage
                .state
                .total_supplies
                .add(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;
            match token_id {
                TokenId::Nep171(ref tid) => {
                    if total_supply > 1 {
                        return Err(DefuseError::NftAlreadyDeposited(tid.clone()));
                    }
                }
                TokenId::Nep141(_) | TokenId::Nep245(_) | TokenId::Imt(_) => {}
            }

            owner
                .token_balances
                .add(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }

        if !mint_event.amounts.is_empty() {
            MtEvent::MtMint([mint_event].as_slice().into())
                .check_refund()?
                .emit();
        }

        Ok(())
    }

                Err(_) => amount.0,

        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };
