## Title
Non-constant-time HTTP `authorization` token comparison enables timing-based auth-token recovery across multiple RPC endpoints - (File: `stackslib/src/net/api/postblock_v3.rs`, `stackslib/src/net/api/postblock_proposal.rs`, and 4 other handlers)

### Summary
Several privileged HTTP RPC endpoints in `stackslib/src/net/api/` authenticate callers by comparing the client-supplied `authorization` header directly against the node's configured secret (`connection_options.auth_token`) using Rust's standard string inequality operator (`!=`). This is a direct analog of CVE-2017-3156: a secret-bearing comparison that is not performed in constant time, allowing a remote, unauthenticated attacker to mount a timing attack to recover the secret token byte-by-byte.

### Finding Description
The block-proposal and other privileged endpoints gate access with a shared-secret HTTP header check: [1](#0-0) 

and [2](#0-1) 

Both compare `auth_header` (attacker controlled, read directly off the wire in `preamble.headers.get("authorization")`) against `password` (the node operator's configured `auth_token`, described in [3](#0-2)  as securing signer↔node communication and the `/v2/blocks?broadcast=1` endpoint) using the default `!=` operator on `String`/`&str`. Rust's standard string/byte-slice equality is not specified or guaranteed to run in constant time — it short-circuits and returns as soon as a byte mismatch (or length mismatch) is found, which is exactly the "non-constant-time MAC/token comparison" class of defect described in the Apache CXF advisory (CVE-2017-3156 / GHSA-qc2p-q7x9-v64p).

The same vulnerable pattern (`auth_header != password` / `auth_header` compared to `self.auth`) is repeated identically in at least four more RPC handlers in the same package: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) 

None of these handlers, nor `net/api/mod.rs`, use any constant-time comparison primitive — a repo-wide search for `constant_time`/`ct_eq` in `stackslib/src/net/api` returns no matches, confirming there is no constant-time equality helper in use anywhere in this authentication path.

### Impact Explanation
`auth_token` is the sole authentication mechanism protecting: (1) `/v3/block_proposal` (`RPCBlockProposalRequestHandler`, which triggers block validation on behalf of a configured signer), and (2) `/v2/blocks?broadcast=1` (`RPCPostBlockRequestHandler`, which allows an authenticated caller to force network broadcast of a submitted block). A remote, unauthenticated attacker who can measure response timing with sufficient precision (a well-established technique against byte-wise, early-exit string comparisons) can incrementally recover the shared secret. Once recovered, the attacker gains authenticated access to these endpoints, which matches the report's "auth bypass" impact category: unauthorized triggering of block-proposal validation and unauthorized block broadcast to the network.

### Likelihood Explanation
The comparison is on the request-handling hot path of a network-facing HTTP endpoint with no rate limiting or constant-time guarantee, so an attacker can send a very large number of requests to build statistical timing signal. Exploitability depends on network jitter and the length of the secret, which raises practical difficulty but does not change the root cause: the code is not resistant to timing side channels by construction, which is precisely the defect class flagged in the report.

### Recommendation
Replace all `auth_header != password` / equivalent comparisons in `stackslib/src/net/api/postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `txsimulate.rs` with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or first hashing both sides with a keyed MAC and comparing digests in constant time) so that the time to reject an incorrect token does not depend on how many leading bytes match.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unauthenticated client, repeatedly send `POST /v3/block_proposal` (or `POST /v2/blocks?broadcast=1`) with `authorization` headers that share progressively more of a guessed prefix.
3. Measure response latency for the `401 Unauthorized` rejection at `stackslib/src/net/api/postblock_proposal.rs:1142` / `postblock_v3.rs:106`. Because the underlying `!=` comparison exits early on the first mismatching byte, correct-prefix guesses will exhibit a measurable (if small) timing differential versus incorrect-prefix guesses, enabling incremental full-token recovery without ever needing the true secret.
