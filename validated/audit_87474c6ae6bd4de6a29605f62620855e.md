Audit Report

## Title
Unchecked `fees`-to-`holding` merge in `RefundSurplus` lets a privileged path bypass `ensure_can_subsume_assets`, silently exceeding `MaxAssetsIntoHolding` - (File: `polkadot/xcm/xcm-executor/src/lib.rs`)

## Summary
The XCM executor enforces `MaxAssetsIntoHolding` on every path that adds assets into the `holding` register via `ensure_can_subsume_assets`, including the trader-weight-refund branch inside `refund_surplus`. Immediately after that guarded branch, the same function merges the leftover `fees` register into `holding` via `self.holding.subsume_assets(leftover_fees)` with no bound check at all, allowing `holding.len()` to exceed the invariant the rest of the codebase (weight benchmarking, `ensure_can_subsume_assets` itself) assumes holds.

## Finding Description
`ensure_can_subsume_assets` is the sole guard protecting the invariant that `holding.len()` never exceeds `2 * holding_limit`. [1](#0-0) 

It is explicitly invoked before the trader-refund is subsumed into `holding`: [2](#0-1) 

But the very next block, which merges the leftover `fees` register into `holding`, calls `subsume_assets` directly with no equivalent check: [3](#0-2) 

`AssetsInHolding::subsume_assets` itself performs no size enforcement — it is a pure merge operation that unconditionally inserts/sums entries into the `fungible`/`non_fungible` maps, with the bound entirely dependent on callers invoking `ensure_can_subsume_assets` beforehand: [4](#0-3) 

The `fees` register can accumulate a distinct `AssetId` via the `take_fee` asset-exchange failure branch, which calls `self.fees.subsume_assets(given_assets)` where `given_assets` (returned by `Config::AssetExchanger::exchange_asset` on failure) can carry a different `AssetId` than the one originally withdrawn: [5](#0-4) 

and via the `PayFees` rollback path, which calls `self_ref.fees.subsume_assets(unspent)`: [6](#0-5) 

Neither of these `fees`-register mutations is bounded by `ensure_can_subsume_assets`, so `self.fees` can accumulate several distinct `AssetId`s across a program. Meanwhile ordinary deposit paths like repeated `WithdrawAsset` are strictly capped, as the existing test demonstrates: 8 distinct assets succeed but a 9th fails with `XcmError::HoldingWouldOverflow`: [7](#0-6) 

When `RefundSurplus` executes, all distinct IDs accumulated in `fees` are merged into `holding` unconditionally, allowing `holding.len()` to exceed `holding_limit * 2` — the exact ceiling that `ensure_can_subsume_assets` is designed to enforce on every other path.

## Impact Explanation
`MaxAssetsIntoHolding` underlies weight-benchmarking assumptions (`worst_case_holding`, `WeighAssets` for wildcard non-fungible filters) that presume `holding` never exceeds this bound. Growing `holding` beyond that ceiling via the unguarded `fees→holding` merge means any subsequent instruction that iterates the full holding (e.g., `DepositAsset(Wild(All))`, `ReportHolding`) performs more work than its benchmarked weight accounts for — public underpriced work that can degrade block production, matching the impact gate's "public underpriced work that degrades block production or stalls bridge processing" category.

## Likelihood Explanation
No privileged actor is required. An unprivileged XCM sender can construct a message using `PayFees` combined with an `AssetExchanger`-dependent fee-swap that fails (a realistic, spec-compliant exchanger behavior returning a different `AssetId` on failure), populating `self.fees` with additional distinct asset entries reachable from ordinary user-originated XCM programs on any chain configured with an `AssetExchanger`.

## Recommendation
Apply `ensure_can_subsume_assets` (or an equivalent length check against `holding_limit`) before merging `self.fees` into `self.holding` inside `refund_surplus`, exactly as already done for the trader-refund branch. If the check fails, drop/trap the excess leftover fee assets instead of merging them.

## Proof of Concept
1. Configure a test runtime with small `MaxAssetsIntoHolding` (e.g. 2) and an `AssetExchanger` whose `exchange_asset` fails and returns `given_assets` of a different `AssetId` than requested.
2. Build an XCM: `WithdrawAsset(AssetA, AssetB)` (filling `holding` to the limit) → `PayFees(AssetA)` → an instruction triggering `take_fee` with a swap to `AssetC` that fails, causing `self.fees.subsume_assets(given_assets)` to add `AssetC` → `RefundSurplus`.
3. Observe `RefundSurplus` succeeds and `self.holding.len()` becomes 3 (`AssetA`, `AssetB`, `AssetC`), exceeding `MaxAssetsIntoHolding = 2`, whereas an equivalent fourth `WithdrawAsset` attempting to add `AssetC` would be rejected with `XcmError::HoldingWouldOverflow` per the existing `max_assets_limit_should_work` test pattern.

	fn ensure_can_subsume_assets(&self, assets_length: usize) -> Result<(), XcmError> {
		// worst-case, holding.len becomes 2 * holding_limit.
		// this guarantees that if holding.len() == holding_limit and you have more than
		// `holding_limit` items (which has a best case outcome of holding.len() == holding_limit),
		// then the operation is guaranteed to succeed.
		let worst_case_holding_len = self.holding.len() + assets_length;
		tracing::trace!(
			target: "xcm::ensure_can_subsume_assets",
			?worst_case_holding_len,
			holding_limit = ?self.holding_limit,
			"Ensuring subsume assets work",
		);
		ensure!(worst_case_holding_len <= self.holding_limit * 2, XcmError::HoldingWouldOverflow);
		Ok(())
	}

	pub fn subsume_assets(&mut self, assets: AssetsInHolding) {
		// for fungibles, find matching fungibles and sum their amounts so we end-up having just
		// single such fungible but with increased amount inside
		for (asset_id, accounting) in assets.fungible.into_iter() {
			match self.fungible.entry(asset_id) {
				btree_map::Entry::Occupied(mut e) => {
					e.get_mut().saturating_subsume(accounting);
				},
				btree_map::Entry::Vacant(e) => {
					e.insert(accounting);
				},
			}
		}
		// for non-fungibles, every entry is unique so there is no notion of amount to sum-up
		// together if there is the same non-fungible in both holdings (same instance_id) these
		// will be collapsed into just single one
		let mut non_fungible = assets.non_fungible;
		self.non_fungible.append(&mut non_fungible);
	}
