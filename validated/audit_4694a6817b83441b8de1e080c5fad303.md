### Title
Unbounded array-index/length reads in `PrecompiledContracts.extractBytes32Array`/`extractBytesArray`/`extractSigArray` allow attacker-crafted TVM calldata to crash the node - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The libming CVE is a heap-buffer overflow caused by trusting an attacker-supplied length/offset field while reading a decoded value (`getString`/DOUBLE handling in `decompile.c`) without validating it against the buffer bounds. The java-tron analog is in the `ValidateMultiSign` / `BatchValidateSign` precompiled contracts, where attacker-controlled length and offset words taken directly from calldata are used to index into the `DataWord[] words` array and the raw `byte[] data` buffer without bounds checking in several helper paths.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:390-430` read a `len`/`bytesOffset`/`bytesLen` value straight from `words[offset].intValueSafe()` (attacker-controlled ABI-decoded calldata) and then loop `words[offset + i + 1]` / call `extractBytes(data, offset*WORD_SIZE, len)` with no validation that the derived index or length lies within the bounds of `words` or `data`: [1](#0-0) 

`extractBytes` itself performs a raw `Arrays.copyOfRange(data, offset, offset + len)` with no bounds validation: [2](#0-1) 

These helpers are reachable from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`, which are precompiled contracts invocable by any TVM `CALL`/`STATICCALL` from a smart contract deployed and executed by any unprivileged account: [3](#0-2) [4](#0-3) 

The codebase does have a partial mitigation: when `VMConfig.allowTvmSelfdestructRestriction()`/`VMConfig.allowTvmOsaka()` is active, `isValidAbiEncoding` and a `sigArraySize > MAX_SIZE` check gate the input shape before calling these helpers (see the `ValidateMultiSignContractTest.testTip854RejectsMalformedCalldata`/`testTip854PreActivationNoOp` tests, which explicitly document that "before activation, malformed calldata reaches the legacy decoder" and can raise an uncaught `RuntimeException`): [5](#0-4) 

Both `extractBytes32Array` and `extractBytesArray`/`extractSigArray` are still called unconditionally when the feature flags (`allowTvmSelfdestructRestriction`, `allowTvmOsaka`) are not active, or even when active but with values that pass the coarse `isValidAbiEncoding`/`MAX_SIZE` gate yet still contain crafted offset words (e.g. `bytesOffset`, or `words[3].intValueSafe()/WORD_SIZE`) that point outside the `words` array bounds, triggering `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException` deep inside array construction (`new byte[len][]`) rather than a graceful validation failure. Because `execute()` in `ValidateMultiSign` has only a narrow `try/catch(Throwable)` scoped around the permission logic (not around the array extraction that happens before it), an exception from `extractBytesArray`/`extractSigArray`/`extractBytes32Array` before that try-block propagates out of `execute()` uncaught.

### Impact Explanation
An uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown while executing a TVM precompiled contract call, if not contained by an outer frame handler, can abort transaction processing for the whole block during block application in `Manager`, denying service or halting the node for all validators processing that transaction — a node crash/halt impact, consistent with the "denial of service" impact class of the CVE analog. The `OperationsTest.testTip854OuterFrameContainment` test suggests some outer containment exists for malformed calldata under the TIP-854 flag, but the pre-activation and pre-array-extraction code paths documented in `testTip854PreActivationNoOp`/`testTip854RejectsMalformedCalldata` show that this containment is not exhaustive for all crafted offset/length combinations that reach `extractBytes32Array`/`extractBytesArray`/`extractSigArray`.

### Likelihood Explanation
Likelihood is Medium: any unprivileged account can deploy a contract and issue a `CALL` to the `ValidateMultiSign` (`0x...0a`) or `BatchValidateSign` (`0x...09`) precompile addresses with crafted calldata containing out-of-range offset/length words. Exploitability depends on exact runtime configuration (`VMConfig.allowTvmSelfdestructRestriction`/`allowTvmOsaka` flags) and on whether the calling frame's exception handling (as partially tested in `OperationsTest`) fully absorbs the resulting exception before it escapes precompile execution — this could not be fully verified from static analysis alone, so the actual current exploitability window is uncertain.

### Recommendation
Add explicit bounds validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before using any attacker-derived `len`, `offset`, or `bytesOffset` value to index into `words` or `data` — mirroring the defensive pattern already used in `ContractEventParser.subBytes` (`actuator`/`framework` code) which validates `start`, `length`, and array bounds before `System.arraycopy`. Additionally, ensure `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` wrap the array-extraction calls in the same broad `try/catch(Throwable)` used for the permission-weight logic so any bounds violation degrades to `Pair.of(true, DATA_FALSE)` rather than propagating an uncaught runtime exception.

### Proof of Concept
Craft ABI-encoded calldata for `validatemultisign(address,uint256,bytes32,bytes[])` where the dynamic `bytes[]` offset word (`words[3]`) points to a length word claiming an array size within `MAX_SIZE`, but whose per-element offset words (`words[offset + i + 1]`) resolve to `bytesOffset` values that, when combined with `offset + bytesOffset + 2`, index past the end of the `words` array (or produce a negative/huge `bytesLen`). Deploy a contract that performs `CALL` to address `0x...0a` with this calldata; when `allowTvmSelfdestructRestriction`/`allowTvmOsaka` is disabled (legacy path, as exercised in `testTip854PreActivationNoOp`) or when the crafted lengths pass the coarse `isValidAbiEncoding`/`MAX_SIZE` check but still overflow `words`, `extractBytesArray`/`extractSigArray`/`extractBytes32Array` throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:390-430`, which is uncaught by the narrow inner `try/catch` in `ValidateMultiSign.execute` (lines 1082-1117) and propagates out of the precompile call.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
