### Title
FetchRemote does not disable `transfer.bundleURI`, allowing SSRF/credential leak via attacker-controlled bundle-URI advertisement - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`validateFetchRemoteRequest` only checks that the repository is valid and that a remote URL is present; it performs no restriction on Git's bundle-URI feature. Unlike `CreateRepositoryFromURL`, which explicitly disables `transfer.bundleURI` before cloning from a user-supplied URL specifically to prevent SSRF, `FetchRemote`'s `buildCommandOpts` never sets `transfer.bundleURI=false`, so a fetch driven by an attacker-controlled remote (e.g., a pull mirror) can have its bundle-URI capability followed by the underlying `git-fetch(1)`/`git-clone(1)` client.

### Finding Description
`fetch_remote.go`'s `validateFetchRemoteRequest` (lines 306-320) validates only the repository and non-empty URL: [1](#0-0) 

`buildCommandOpts`, which builds the git config used for the fetch, sets `remote.inmemory.url`, resolve config, proactive-auth, and `http.<url>.extraHeader` for the `Authorization` header, but never touches `transfer.bundleURI`: [2](#0-1) 

By contrast, `create_repository_from_url.go`'s `cloneFromURLCommand` explicitly disables bundle URIs with a comment that states the exact threat model matching this question — "Since the URI can point to any server, including localhost, this is to prevent attack vectors that could abuse this mechanism": [3](#0-2) 

This mitigation is corroborated by the changelog entry documenting it as a dedicated security fix: "repoFromURL: Disable bundle URIs when cloning from URL to prevent SSRF." Because `FetchRemote` (used for pull mirroring, where the remote URL, `HttpAuthorizationHeader`, SSH key, etc. are attacker-controllable by an unprivileged repository owner configuring a pull mirror to a server they control) does not apply the same `transfer.bundleURI=false` restriction, a malicious remote can advertise a `bundle.<name>.uri` pointing at an internal/attacker-controlled address during the `git-fetch(1)`/`git-upload-pack` handshake. Git's client-side bundle-URI support would then have Gitaly's git process fetch that bundle URI, which is a second HTTP(S) request originating from the Gitaly host. Because Gitaly injects `http.<GetUrl()>.extraHeader` = `Authorization: <header>` scoped to the primary remote URL (not to the bundle URI host), the `Authorization` header should not automatically be replayed to a different bundle host under normal libcurl per-host config scoping — however, the SSRF vector itself (Gitaly's git process making an unvalidated outbound request to a URL fully chosen by the attacker-controlled remote) is not mitigated, since `validateFetchRemoteRequest`/`buildCommandOpts` do nothing to block or opt bundle-URI fetching out.

### Impact Explanation
This matches the GitLab bounty class "SSRF to an internal endpoint": an unprivileged user who can configure a pull mirror (an action available to a project owner with no special role) controls the remote git server response, including any `bundle.<name>.uri` advertised during the Git protocol v2 handshake. If the local Gitaly git client honors that capability during `FetchRemote`, it results in Gitaly making an outbound HTTP(S) request to an address fully chosen by the attacker (e.g., `http://169.254.169.254/`, an internal admin endpoint, etc.), which is the exact SSRF scenario the sibling fix in `create_repository_from_url.go` was written to prevent.

### Likelihood Explanation
Preconditions: the attacker only needs the ability to configure a pull-mirror remote (or otherwise trigger `FetchRemote`) pointing to a git server they control — no special GitLab role is required, matching the stated attacker capability of "an unprivileged GitLab user ... who can push/fetch ... a repository they own." The exploit is deterministic and repeatable: any fetch triggers the handshake in which the malicious remote can advertise the bundle-uri capability. The main uncertainty is whether Git's client-side bundle-uri auto-fetch is enabled by default (`transfer.bundleURI` defaults to `false` in stock Git) and whether Gitaly's global git config elsewhere sets it to true; within this repo's index no code was found that enables `transfer.bundleURI` for FetchRemote, so exploitability hinges on the client-default git behavior/version and possibly on whether GitLab Rails passes a `GitConfigOptions`/`git_config` override enabling it for this RPC path (this could not be confirmed with certainty from the indexed code).

### Recommendation
In `internal/gitaly/service/repository/fetch_remote.go`, mirror the mitigation already applied in `create_repository_from_url.go`: pass `gitcmd.WithGlobalOption(gitcmd.ConfigPair{Key: "transfer.bundleURI", Value: "false"})` (or an equivalent `gitcmd.WithConfig`) into the fetch invocation in `fetchRemoteAtomic`/`buildCommandOpts` for any remote-driven fetch (`FetchRemote`, and any other RPC that fetches from an attacker-influenceable URL), so that Git's bundle-URI capability cannot be leveraged as an SSRF primitive regardless of upstream Git defaults.

### Proof of Concept
```go
// internal/gitaly/service/repository/fetch_remote_bundle_uri_test.go
func TestFetchRemote_BundleURISSRF(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, client := setupRepositoryService(t)

    // internal/attacker-controlled target that should never be reached
    var hitInternal bool
    internalTarget := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        hitInternal = true
    }))
    defer internalTarget.Close()

    // malicious git server advertising bundle-uri pointing at internalTarget
    maliciousRemote := gittest.HTTPServerWithBundleURI(t, ctx, internalTarget.URL)
    defer maliciousRemote.Close()

    repo, _ := gittest.CreateRepository(t, ctx, cfg)

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repo,
        RemoteParams: &gitalypb.Remote{
            Url: maliciousRemote.URL,
        },
    })
    require.NoError(t, err)

    // Expected: hitInternal must remain false because bundle-uri should be disabled;
    // currently this assertion fails, demonstrating the SSRF.
    require.False(t, hitInternal, "Gitaly should not have followed the attacker-supplied bundle-uri")
}
```
Note: a helper like `gittest.HTTPServerWithBundleURI` (advertising `bundle.default.uri=<internalTarget.URL>` in the `git-upload-pack` v2 capability advertisement) would need to be implemented to fully validate this against a live `git-fetch` invocation, since the actual client-side bundle-uri auto-download behavior depends on the Git version bundled with the test environment.

func buildCommandOpts(ctx context.Context, opts *localrepo.FetchOpts, req *gitalypb.FetchRemoteRequest) error {
	remoteURL := req.GetRemoteParams().GetUrl()
	var config []gitcmd.ConfigPair

	for _, refspec := range getRefspecs(req.GetRemoteParams().GetMirrorRefmaps()) {
		config = append(config, gitcmd.ConfigPair{
			Key: "remote.inmemory.fetch", Value: refspec,
		})
	}

	if resolvedAddress := req.GetRemoteParams().GetResolvedAddress(); resolvedAddress != "" {
		modifiedURL, resolveConfig, err := gitcmd.GetURLAndResolveConfig(remoteURL, resolvedAddress)
		if err != nil {
			return fmt.Errorf("couldn't get curloptResolve config: %w", err)
		}

		remoteURL = modifiedURL
		config = append(config, resolveConfig...)
	}

	config = append(config, gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL})

	if featureflag.FetchRemoteProactiveAuth.IsEnabled(ctx) {
		if u, err := url.Parse(remoteURL); err == nil && u.User != nil {
			password, _ := u.User.Password()
			if u.User.Username() != "" && password != "" {
				config = append(config, gitcmd.ConfigPair{
					Key:   "http.proactiveAuth",
					Value: "basic",
				})
			}
		}
	}

	if authHeader := req.GetRemoteParams().GetHttpAuthorizationHeader(); authHeader != "" {
		config = append(config, gitcmd.ConfigPair{
			Key:   fmt.Sprintf("http.%s.extraHeader", req.GetRemoteParams().GetUrl()),
			Value: "Authorization: " + authHeader,
		})
	}

	opts.CommandOptions = append(opts.CommandOptions, gitcmd.WithConfigEnv(config...))

	return nil
}

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
