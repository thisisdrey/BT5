### Title
Uninitialized `accountIndexOf` pays a full `INITIAL_INDEX` delta when the token index still equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The kernel bug treats a prz with `buffer_size == 0` as valid without validating its `start` offset, so a corrupt buffer later crashes the writer. The Metronome analog is in `RewardsDistributor._calculateTokenDelta`: an account that has never accrued (`accountIndexOf == 0`) is only normalized to `INITIAL_INDEX` when the token index is **strictly greater** than `INITIAL_INDEX`. When the stored token index is still exactly `INITIAL_INDEX` (the "empty" state set by `_updateTokenSpeed`), the fallback is skipped, the account's index is left at `0`, and the delta is computed as `1e18 - 0 = 1e18`, crediting the account `balance.wadMul(1e18) = balance` reward tokens for zero elapsed time.

### Finding Description
In `contracts/RewardsDistributor.sol`:

- `_updateTokenSpeed` initializes a newly enabled reward token with `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` where `INITIAL_INDEX = 1e18` (line ~298).
- `_calculateTokenDelta` (lines 217-231) contains:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

Because the guard uses `>` instead of `>=`, when `_tokenIndex == INITIAL_INDEX` exactly, a never-synced account keeps `_accountIndex = 0` and receives `_tokensDelta = balance`.

- Entry points that reach this are permissionless: `claimRewards(...)` (lines 150-168), `updateBeforeMintOrBurn` (lines 175-180), and `updateBeforeTransfer` (lines 186-192) all run while `tokenStates[token_].index > 0`. The stored index stays exactly `INITIAL_INDEX` as long as `_deltaTimestamps == 0`, i.e., within the same block in which `updateTokenSpeed`/`updateTokenSpeeds` enabled the token (`_calculateTokenIndex` returns `_newIndex = 0` when no time has elapsed, so `_updateTokenIndex` writes nothing).
- `_updateTokensAccruedOf` accumulates into `tokensAccruedOf[account_]` (lines 261-265) and `claimRewards` then pays it out via `_transferRewardIfEnoughTokens`, up to the distributor's whole `rewardToken` balance (lines 248-256).

### Impact Explanation
An attacker holding (or flash-acquiring in the same block via `deposit`, `transfer`, or leverage) a large `DepositToken`/`DebtToken` balance can, in the same block that governance enables a reward speed for that token, call `claimRewards(accounts, tokens)` or `updateBeforeMintOrBurn` and accrue reward tokens equal to their token balance — with zero elapsed time and zero legitimate accrual. This directly drains the `RewardsDistributor`'s `rewardToken` balance, i.e., theft of the unclaimed yield owed to all honest users. With a large balance (e.g., millions of `msdVaUSDC`), a single call can claim the distributor's entire reward reserve.

### Likelihood Explanation
- Requires acting in the same block/timestamp as the governor's `updateTokenSpeed` call (once any later block passes and `_updateTokenIndex` runs, the stored index becomes `> INITIAL_INDEX` and the `INITIAL_INDEX` fallback works correctly). On Ethereum mainnet the governor's transaction is visible in the public mempool, so a back-running bundle in the same block is feasible; the attacker can also pre-position a balance before speed is set, since all accrual hooks are no-ops while `index == 0` and leave `accountIndexOf == 0`.
- No privileged access, oracle manipulation, or guard bypass is needed; `claimRewards` and `updateBeforeMintOrBurn` are public and `nonReentrant` only.
- On L2 deployments (Optimism/Base) same-block ordering is harder but not impossible if the governance action is anticipated.

### Recommendation
Treat `accountIndexOf == 0` as uninitialized whenever the token index is at or above the sentinel — mirror the kernel fix of also validating the "start". Change the guard to `>= INITIAL_INDEX`:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Alternatively, initialize `tokenStates[token_]` with `index = INITIAL_INDEX + 1` (or record the account index unconditionally on first sync), so a stored index equal to `INITIAL_INDEX` can never be combined with a zero account index.

### Proof of Concept
Hardhat-style test sketch (repo uses Hardhat + Foundry; mock tokens exist in `test/`):

```ts
// setup: alice deposits collateral, receives msdTOKEN1; no rewards configured yet
await depositToken.connect(alice).deposit(amount, alice.address); // updateBeforeMintOrBurn no-ops (index == 0)

// governor enables rewards for the token
await rewardsDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'));
// tokenStates[msdTOKEN1].index == INITIAL_INDEX (1e18), timestamp == now

// same block / same timestamp: attacker (alice) claims
await network.provider.send('evm_setAutomine', [false]);
const tx = rewardsDistributor.claimRewards(alice.address, [msdTOKEN1.address]);
// claimable rewards credited: tokensAccruedOf[alice] == msdTOKEN1.balanceOf(alice)
// _transferRewardIfEnoughTokens pays out min(accrued, rewardToken.balanceOf(distributor))
```

Expected result: `tokensAccruedOf[alice]` jumps to `balanceOf(alice)` in reward-token units despite zero seconds of accrual, and `claimRewards` transfers up to the full distributor `rewardToken` balance to the attacker.
