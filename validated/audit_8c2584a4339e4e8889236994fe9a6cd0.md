### Title
Missing ownership/relationship validation in `LinkRepositoryToObjectPool` allows linking an arbitrary repository to any object pool, exposing cross-repository objects - (File: internal/gitaly/service/objectpool/link.go, internal/git/objectpool/link.go)

### Summary
The `LinkRepositoryToObjectPoolRequest` handler validates only that the `Repository` and `ObjectPool` fields each individually refer to *some* valid, existing repository on disk. It never verifies that the two are actually related (i.e., that the target repository is a legitimate fork/member intended for that specific pool). This mirrors the `VaultManagerV2::burnDyad` bug class: an operation takes an identifier (here, an object-pool repository) supplied by the caller and acts on it without checking that the caller's own resource (the repository being linked) is authorized to be associated with that identifier.

### Finding Description
`LinkRepositoryToObjectPool` in `internal/gitaly/service/objectpool/link.go:10-28` performs the following checks only:
- `s.locator.ValidateRepository(ctx, repository)` — confirms `repository` exists and is a valid path.
- `s.poolForRequest(ctx, req)` — resolves the `ObjectPool` message to an actual pool repository on disk. [1](#0-0) 

Neither check establishes any relationship between the `repository` and the `object_pool` — there is no verification that the pool was created from (or is otherwise entitled to be linked with) the given repository. The lower-level `Link` function in `internal/git/objectpool/link.go:28-84` similarly only checks whether the repository is *already* linked to *some* alternates target (`linkedToRepository`) and, if not, unconditionally writes the pool's relative object path into the repository's `objects/info/alternates` file: [2](#0-1) [3](#0-2) 

Since Git resolves objects transparently through `objects/info/alternates`, once the alternates file is rewritten to point at an arbitrary pool, every object contained in that pool (including commits/blobs from whatever project originally seeded the pool) becomes directly readable through the linked repository via any read RPC (`GetBlob`, `TreeEntry`, `GetCommit`, clone/fetch, etc.) — this is the "cross-repository object access" analog to the DYAD bug's "operate on another user's ID without ownership check."

### Impact Explanation
An actor able to issue `LinkRepositoryToObjectPoolRequest` with a `Repository` they nominally control and an arbitrary/unrelated `ObjectPool` value effectively grafts a foreign object store onto their own repository. Since `git-cat-file`, `git-log`, and all Gitaly read RPCs transparently traverse alternates, this discloses the full object graph of the object pool — including private data belonging to unrelated repositories/projects that share that pool but never authorized this link — without any content-level access control. It also permanently corrupts the state of the linking repository (its alternates path is no longer scoped to the intended pool), which can only be fixed by `DisconnectGitAlternates`, itself relying on the same unauthenticated relationship trust.

### Likelihood Explanation
The RPC and its underlying git-level `Link` function are reachable by supplying two independently-controlled protobuf fields (`repository`, `object_pool`) in a single mutator call; the tests in `internal/gitaly/service/objectpool/link_test.go` confirm that the only validated preconditions are "repository exists" and "pool exists" (see `TestLink`, `TestLink_noPool`). No test asserts that linking fails when the pool and repository are unrelated forks, confirming the gap is intentional/unaddressed rather than covered by unseen logic elsewhere. [4](#0-3) 

Because the actual authorization decision (whether a given repository is *permitted* to join a given pool) is expected to live entirely in the calling layer (e.g., GitLab Rails), and Gitaly itself performs no relationship check, any caller with access to the `ObjectPoolService` RPC surface with valid but mismatched repository/pool pairs can trigger this.

### Recommendation
Add a relationship check in `LinkRepositoryToObjectPool` (or in `objectpool.Link`) that verifies the target repository is an expected/authorized member of the pool — e.g., by validating that the repository's "pool candidate" lineage (recorded at `CreateFork`/`CreateObjectPool` time) matches the requested pool, or by requiring an explicit, previously-established mapping between repository and pool relative paths before allowing `Link` to rewrite `objects/info/alternates`. Reject the request (analogous to adding the `isDNftOwner` modifier) when the repository has no established relationship to the pool being linked.

### Proof of Concept
Conceptual reproduction (would need to be validated with a live Gitaly instance and appropriate RPC client, which was not available in this analysis):
1. Create object pool `PoolA` seeded from `RepoA` (owned by/associated with victim project) via `CreateObjectPool`.
2. Create an unrelated `RepoB` (attacker-controlled) with no relation to `RepoA`/`PoolA`.
3. Call `LinkRepositoryToObjectPool` with `Repository = RepoB`, `ObjectPool = PoolA`.
4. Observe that the call succeeds (only existence checks in `internal/gitaly/service/objectpool/link.go:10-28` and `internal/git/objectpool/link.go:28-52` are performed) and that `RepoB/objects/info/alternates` now points at `PoolA`'s object directory.
5. Issue read RPCs (e.g., `GetBlob`/`GetCommit`) against `RepoB` for object IDs known only to exist in `PoolA`/`RepoA` and confirm they resolve successfully, demonstrating cross-repository object disclosure.

Note: I was unable to execute this PoC against a live instance or trace the full call chain (`poolForRequest`, `CreateObjectPool`) end-to-end within this session; the analysis is based on the static code paths and existing test coverage shown above. If deeper verification of caller-side authorization (e.g., whether Praefect or Rails enforces the missing relationship check elsewhere) is required, a Devin session with repository access would be needed to trace that fully.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}

func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

func TestLink(t *testing.T) {
	t.Parallel()

	ctx := testhelper.Context(t)

	cfg, repo, _, _, client := setup(t, ctx, testserver.WithDisablePraefect())

	localRepo := localrepo.NewTestRepo(t, cfg, repo)
	poolProto, _, poolPath := createObjectPool(t, ctx, cfg, repo)

	// Mock object in the pool, which should be available to the pool members
	// after linking
	poolCommitID := gittest.WriteCommit(t, cfg, poolPath,
		gittest.WithBranch("pool-test-branch"))

	for _, tc := range []struct {
		desc        string
		request     *gitalypb.LinkRepositoryToObjectPoolRequest
		expectedErr error
	}{
		{
			desc: "unset repository",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: nil,
				ObjectPool: poolProto,
			},
			expectedErr: structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet),
		},
		{
			desc: "unset object pool",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: repo,
				ObjectPool: nil,
			},
			expectedErr: structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet),
		},
		{
			desc: "successful",
			request: &gitalypb.LinkRepositoryToObjectPoolRequest{
				Repository: repo,
				ObjectPool: poolProto,
			},
		},
	} {
		t.Run(tc.desc, func(t *testing.T) {
			_, err := client.LinkRepositoryToObjectPool(ctx, tc.request)
			testhelper.RequireGrpcError(t, tc.expectedErr, err)
			if tc.expectedErr != nil {
				return
			}

			// verify that the commit is present in the pool
			commitClient := gitalypb.NewCommitServiceClient(gittest.DialService(t, ctx, cfg))
			gittest.RequireObjectExistsAPI(t, ctx, commitClient, repo, poolCommitID)

			commit, err := localRepo.ReadCommit(ctx, git.Revision(poolCommitID))
			require.NoError(t, err)
			require.NotNil(t, commit)
			require.Equal(t, poolCommitID.String(), commit.GetId())
		})
	}
