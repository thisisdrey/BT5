### Title
Same-priority eviction is deterministically resolved by insertion-order `TransactionId`, letting an attacker reliably evict a victim's equal-fee transaction - (File: core/src/banking_stage/transaction_scheduler/transaction_state_container.rs)

### Summary
`TransactionPriorityId` orders first by `priority` and then by `TransactionId` [1](#0-0) . `TransactionId` is the slab index handed out in strict insertion order by `insert_map_only`/`get_vacant_map_entry` [2](#0-1) . Because `push_ids_into_queue` evicts via `BTreeSet::pop_first()` when the container is over capacity [3](#0-2) , at equal priority the transaction with the smallest id -- i.e., the one that arrived earliest -- is always evicted first, deterministically and without regard to real arrival fairness or fee proportionality.

### Finding Description
`TransactionStateContainer` uses a `BTreeSet<TransactionPriorityId>` as its priority queue, and `#[derive(PartialOrd, Ord)]` on the tuple `(priority, id)` means ties in `priority` fall through to `id` comparison [4](#0-3) . Every incoming transaction goes through `receive_and_buffer.rs`'s `handle_packet_batch_message`, which calls `container.insert_map_only(state)` (assigning the next slab index in FIFO order) and then `container.push_ids_into_queue(...)` [5](#0-4) . When the container is at capacity, `push_ids_into_queue` pops the smallest `TransactionPriorityId` via `pop_first()` and removes it from both the queue and the map [6](#0-5) . Since slab indices are monotonic per insertion (barring reuse of freed slots), a transaction that arrived earlier has a strictly smaller id than one that arrives later, so among identical-priority transactions the earliest arrival is always the one dropped. An unprivileged attacker who observes (or predicts) a victim's declared `compute_unit_price`/priority can flood the leader's TPU with self-signed transactions carrying the identical priority value after the victim's transaction is buffered; once the container saturates, the victim's transaction — having the smallest id among the tied group — is deterministically evicted ahead of every attacker transaction of equal or lesser id-order, regardless of which arrived "more fairly" or is more likely to actually land. No dedup, rate-limit, or fairness mechanism corrects for this: sigverify, nonce-dedup and fee-payer-unlocked checks only gate validity, not fairness of insertion order, and `push_ids_into_queue`'s only capacity-driven decision criterion is `(priority, id)` ordering.

### Impact Explanation
This falls into the QoS-evasion category: proportionate treatment by declared fee is undermined because, at tie, eviction is decided by arrival order rather than any fee-based or randomized fairness mechanism, and that arrival order is fully attacker-observable/attacker-controllable (the attacker only needs to insert enough same-priority transactions after the victim's is buffered). The scoped impact is a victim's fee-paying transaction being silently dropped from the leader's buffer before it is ever considered for scheduling, at no cost differential to the attacker (declared priority is unchecked against actual balance at insertion time; fees are collected only on execution, not on buffering).

### Likelihood Explanation
Preconditions: the attacker must (a) learn or guess the victim's declared priority (fee) value and (b) be able to submit enough distinct signed transactions with that exact priority to a leader's TPU faster than the buffer drains, while the container is near/at capacity (`TransactionStateContainer::with_capacity` is finite, e.g. `TEST_CONTAINER_CAPACITY`/production capacity). No stake, no peer/gossip control, and no validator config changes are required — matches the “unstaked remote client sending packets to leader’s TPU” attacker model. Feasibility is bounded in practice by existing QUIC/stake-weighted rate limits on unstaked connections and by the cost of generating enough distinct valid transactions, but nothing in the reviewed code path (`push_ids_into_queue`, `TransactionPriorityId`, `handle_packet_batch_message`) breaks the deterministic tie-break once packets are accepted and buffered, so the effect is reliably reproducible in a unit test bypassing network-layer rate limiting.

### Recommendation
Break ties among equal-priority `TransactionPriorityId`s using a criterion that is not attacker-predictable or that favors fairness rather than penalizing earlier arrivals, e.g.:
- Randomize the tie-break (e.g., include a random nonce/salt in the ordering key instead of raw insertion-ordered `TransactionId`), or
- Explicitly reverse the tie preference so newer arrivals are evicted first at equal priority (LIFO-drop for ties) if that is the intended behavior, and document/enforce it consistently, or
- Track per-fee-payer/per-priority-bucket counts and cap flooding of identical-priority transactions from bursts to prevent one priority bucket from being fully attacker-populated.

```rust
#[test]
fn test_equal_priority_tie_break_evicts_earliest_arrival() {
    let mut container = TransactionStateContainer::with_capacity(4);

    // Victim inserts first, with priority P.
    let (victim_tx, max_age, priority, cost) = test_transaction(100);
    container.insert_new_transaction(victim_tx, max_age, priority, cost);
    let victim_id = container.priority_queue.iter().next().unwrap().id;

    // Attacker floods with 10 more transactions at the SAME priority, after the victim.
    for _ in 0..10 {
        let (attacker_tx, max_age, priority, cost) = test_transaction(100); // identical priority
        container.insert_new_transaction(attacker_tx, max_age, priority, cost);
    }

    // Container capacity is 4; victim's tx (smallest id among ties) must have been evicted.
    assert!(
        container.get_mut_transaction_state(victim_id).is_none(),
        "victim's equal-priority transaction was deterministically evicted due to id tie-break, \
         not due to any fee-based fairness mechanism"
    );
}
```
Expected result: the assertion passes, proving that at identical declared priority, the earliest-arriving (victim) transaction is always the one dropped once capacity is exceeded, confirming the tie-break is attacker-exploitable via insertion timing rather than fee-proportionate.

```rust
    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
```
