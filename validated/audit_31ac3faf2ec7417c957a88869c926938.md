Based on the evidence gathered, this is confirmed rather than merely suspected: the repository's own test suite demonstrates the same root cause as the IBC report — a function that is *documented and intended* to operate in a terminal/non-open state is actually blocked by a status guard.

### Title
`refundBorrower` incorrectly enforces an outstanding-loan status, blocking documented post-cancellation/closure refunds - (File: `contracts/Loans.sol`)

### Summary
The `Loans.refundBorrower` function is documented in `specs/loan_permissions.md` as one of the functions **intentionally NOT blocked** on `Cancelled`/`Closed` loans, specifically "to allow post-cancellation recovery/cleanup." [1](#0-0)  However, the actual implementation gates `refundBorrower` with `_onlyOutstandingOrFullyPaid`, which only allows `Active`, `ChargedOff`, and `FullyPaid` — explicitly excluding `Cancelled` and `Closed`. [2](#0-1)  This is confirmed by the test suite, which asserts `InvalidStatus` reverts on both cancelled and closed loans. [3](#0-2) 

### Finding Description
This mirrors the IBC `timeoutPacket`/`timeoutOnClose` bug class exactly: a recovery/cleanup path that is supposed to remain callable when the "channel" (here, the loan) is in a non-open (terminal) state is instead hard-gated to only the "open" states. `Loans.refundBorrower` is meant to let the servicer/admin return over-collected interest, misc fees, or unallocated payment-clearing surplus to the borrower — including after the loan reaches `Cancelled` or `Closed`, per the documented "post-cancellation recovery/cleanup" design in `loan_permissions.md`. [4](#0-3)  The `early_cancellation.md` spec independently documents "Scenario C" where a loan is prematurely flipped to `Cancelled` while `ACC_BORROWER_PRINCIPAL_RECEIVABLE` is still nonzero, noting that `refundBorrower` (along with `pay`, `accrue`, `applyWaterfall`, `returnFunds`) reverts by status guard once `status == Cancelled`, requiring the servicer to first reopen the loan via `updateLoanData` before any refund/cleanup can occur. [5](#0-4)  This directly parallels the IBC finding: a cleanup/exit function incorrectly enforces a "live" state instead of supporting the terminal states it was designed for.

### Impact Explanation
When a loan is moved to `Cancelled` or `Closed` while a borrower still has a refundable surplus in `ACC_BORROWER_INTEREST_PAID`, `ACC_BORROWER_MISC_FEE_PAID`, or `ACC_BORROWER_PAYMENT_CLEARING` (e.g., an over-accrual reversal or overpayment discovered after closure), the servicer/admin cannot call `refundBorrower` to return that cash directly — it reverts with `InvalidStatus`. [3](#0-2)  The only documented workaround is to reopen the loan (`updateLoanData` back to `Active`), perform the refund, and re-close it — an operational side effect (visible status churn in `LoanStatusUpdated` events) that the spec itself flags as something "off-chain consumers must tolerate." [6](#0-5)  If this reopen path is missed or not exercised in a given operational flow, borrower-owed cash held in the loan's `ACC_CASH` becomes stuck in the contract with no other allowed exit for that specific type of borrower-side surplus, since `refundBorrower` is the only production path for these three account types.

### Likelihood Explanation
This requires no adversarial input — it is a deterministic contract-level status gate that contradicts the protocol's own documented behavior and directly affects the correctness of a servicer-only-but-still-operator-facing cleanup flow. Any real-world scenario where a loan is cancelled/closed before all borrower-side overpayment refunds are settled — including the documented "premature `Cancelled`" scenario in `early_cancellation.md` — will hit this bug. [7](#0-6) 

### Recommendation
Change the status gate on `refundBorrower` from `_onlyOutstandingOrFullyPaid` to a broader `_notTerminal`-style check (or explicitly also allow `Cancelled`/`Closed`), matching the documented intent in `loan_permissions.md` that this function is meant to remain callable to allow post-cancellation/closure recovery, without requiring the loan to be reopened first.

### Proof of Concept
1. Create, fund, and disburse a loan; accrue interest, then reverse the over-accrual so `ACC_BORROWER_INTEREST_PAID` holds a refundable surplus (as done in `_assertRefundBorrowerSucceedsAtStatus`). [8](#0-7) 
2. Servicer calls `updateLoanData(loanId, LoanStatus.Cancelled, ...)` to close the loan out.
3. Servicer/admin calls `refundBorrower(loanId, ACC_BORROWER_INTEREST_PAID, refundAmount, ...)`.
4. Call reverts with `InvalidStatus` — confirmed directly by `test_RefundBorrower_RevertsOnCancelledLoan` / `test_RefundBorrower_RevertsOnClosedLoan`. [3](#0-2)

**File:** tare-io__tare-contracts/specs/early_cancellation.md (L99-123)
```markdown
## Scenario C — Status was set to `Cancelled` before borrower repaid

Servicer set `status = Cancelled` via `updateLoanData` while `ACC_BORROWER_PRINCIPAL_RECEIVABLE` was still non-zero.

### Effect of the premature transition

Once `status == Cancelled`, the following calls revert by status guard:

- `pay`, `accrue`, `chargeMiscFee` — `onlyOutstanding`
- `applyWaterfall`, `refundBorrower`, `returnFunds` — `onlyOutstandingOrFullyPaid`
- `updateBorrower`, `updateServicer` — `notTerminal`

`createLedgerEntries`, `updateLoanData`, `originatorWithdraw`, `investorWithdraw`, and `servicerWithdraw` are not status-gated and remain callable.

No funds are lost: cash balances and investor-side payables are untouched by a status flip, and the investor cannot withdraw what was never waterfalled.

### Recovery flow

`updateLoanData` is not guarded by `notTerminal`, so the servicer (or admin) can flip the status back out of `Cancelled`:

1. **Servicer** calls `updateLoanData(loanId, LoanStatus.Active, 0, 0, timestamp)`.
2. Proceed with Scenario A (or Scenario B if interest was accrued).
3. The final `updateLoanData(loanId, LoanStatus.Cancelled, …)` in step 5 returns the loan to terminal state.

The intermediate `Cancelled → Active → Cancelled` transitions are visible in `LoanStatusUpdated` events. Off-chain consumers must tolerate this re-opening pattern.
```
