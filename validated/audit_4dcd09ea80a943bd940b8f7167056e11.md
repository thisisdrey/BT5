### Title
XCM `ERC20Transactor` credits/moves the requested `amount` instead of the actual ERC20 balance delta, allowing fee-on-transfer/deflationary tokens to desynchronize the shared checking-account backing - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor` is the `TransactAsset` implementation that lets XCM move arbitrary `pallet-revive`-deployed ERC20 tokens on Asset Hub. On `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, it calls the token's own `IERC20::transfer` and, upon a `true` boolean return, unconditionally credits the XCM holding register (or considers the deposit complete) with the full `amount` requested by the matcher — never checking the actual balance delta produced by the transfer. [2](#0-1) [3](#0-2) 

### Finding Description
This is the exact bug class from the Sherlock report: an internal bookkeeping system assumes a transferred `amount` param equals the actual balance change caused by the transfer, without validating actual balances before/after. Real ERC20 tokens can implement deflationary or fee-on-transfer behavior (burn-on-transfer, tax-on-transfer, rebasing), where `transfer(to, amount)` moves less than `amount` into the recipient's balance while still returning `true`.

In `withdraw_asset_with_surplus`, the code transfers `amount` from the user (`who`) to a single, **shared** `TransfersCheckingAccount` (a pallet-derived account used for all ERC20 XCM transfers of that instance, configured once in the runtime): [4](#0-3) 

If the ERC20's `transfer` call returns `true`, the code unconditionally builds `Erc20Credit(amount)` — the full requested amount — into the XCM holding register: [5](#0-4) 

It never re-reads `balanceOf(checking_account)` before/after the transfer to confirm the checking account actually received `amount`. For a fee-on-transfer token, the checking account only gains `amount - fee`, but the XCM engine now believes it holds `amount` worth of that asset, which can be forwarded in the same message (e.g. `DepositAsset`, reserve transfer to another parachain, or teleport instruction) as if fully backed.

Symmetrically, `deposit_asset_with_surplus` transfers `amount` out of the same shared checking account to a beneficiary based solely on the XCM holding register value and the boolean transfer result — again with no verification of the actual amount received by the beneficiary: [6](#0-5) 

Because `TransfersCheckingAccount` is a single pooled account shared across all users and all XCM programs that touch a given fee-on-transfer ERC20, a shortfall created by one user's withdraw (checking account under-funded relative to what the XCM holding register believes) is paid for out of the pooled balance contributed by other, unrelated depositors of the same token. This is functionally identical to the Sherlock finding: the pool/vault bookkeeping is keyed off the caller-supplied `amount` parameter rather than the measured balance delta, so an attacker depositing a fee-on-transfer/deflationary token is credited (in XCM holding, and hence in whatever the XCM program subsequently does with that holding — mint LP, forward cross-chain, deposit to any beneficiary) more value than was actually moved into the shared custodial account.

Existing guards do not stop this: `ERC20Matcher`/`IsLocalAccountKey20` only checks that the location is a local `AccountKey20`, with no restriction on the ERC20's transfer semantics being standard/non-deflationary, and `MatchesFungibles::matches_fungibles` only extracts `(asset_id, amount)` from the XCM `Asset` value, never consulting the chain state of the ERC20 contract. [1](#0-0) 

### Impact Explanation
This breaks the "balances/assets held via public wrappers must conserve value and settle exactly once to the rightful beneficiary and amount" invariant for the ERC20↔XCM bridge on Asset Hub. Any account able to deploy a `pallet-revive` contract (an unprivileged, permissionless action) can create a token that returns `true` from `transfer()` while under-delivering the stated `amount`, then drive XCM programs (`WithdrawAsset`/`DepositAsset`, reserve-transfers, or cross-chain sends) that account for the full nominal `amount`. Repeated use inflates the XCM-tracked value backing the shared checking account beyond its real ERC20 balance, letting the attacker (or any user who later withdraws) drain real value contributed by other legitimate users of the same fee-on-transfer token, or successfully complete cross-chain transfers backed by funds that were never actually received.

### Likelihood Explanation
High feasibility: deploying an arbitrary Solidity/PVM contract via `pallet-revive` and registering it as a `ForeignAssets`/XCM-visible ERC20 requires no privileged origin — anyone can deploy a contract at a fresh `AccountKey20` and it is automatically matched by `ERC20Matcher`/`IsLocalAccountKey20`. No governance, admin, relayer, or validator compromise is needed; only a self-authored fee-on-transfer or deflationary ERC20 contract and normal XCM extrinsics (`transfer_assets`, `execute`, etc.) that route through `ERC20Transactor`.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the actual ERC20 balance of the checking account (or recipient) immediately before and after the `IERC20::transfer` call, and use the observed delta — not the requested `amount` — to construct `Erc20Credit`/determine success. If the delta is less than `amount`, either fail the transact (`Err`) or credit only the actual delta, mirroring the "best effort" pattern already used elsewhere in the fungible/fungibles traits (e.g. `Precision::BestEffort` returning the actual transferred amount rather than the requested one, as done in `substrate/frame/support/src/traits/tokens/fungible/regular.rs`).

### Proof of Concept
1. Deploy a PVM/Solidity ERC20 contract via `pallet-revive` whose `transfer(to, amount)` deducts a 5% fee (burns it or sends it elsewhere) but still returns `true`, and register/reference it by its `AccountKey20` location so it is matched by `ERC20Matcher`.
2. Attacker holds 1000 units of this token. Attacker submits an XCM program (e.g. via `pallet-xcm::execute` or `transfer_assets`) that specifies `WithdrawAsset` of `1000` of this token from their own account.
3. `ERC20Transactor::withdraw_asset_with_surplus` calls `transfer(checking_account, 1000)`; the contract moves only 950 to the checking account and burns 50, but returns `true`.
4. The code builds `Erc20Credit(1000)` and inserts it into the XCM holding register — 50 units more than what the checking account actually received.
5. The attacker's XCM program then issues `DepositAsset` of that `1000`-unit holding to a second attacker-controlled account (or forwards it cross-chain). `deposit_asset_with_surplus` executes `transfer(beneficiary, 1000)` from the checking account. Because the checking account is shared and may hold balance contributed by other users' prior deposits of the same token, this transfer can succeed, paying out 1000 real tokens for only 950 actually deposited by the attacker — net theft of 50 tokens (or more, with repetition) from the pooled checking account.
