### Title
StackerDB chunk signature does not commit to the target contract, enabling cross-StackerDB signature replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
The Gatecoin report describes a signature-reuse bug where the request signature does not commit to the payload/parameters, letting an attacker replay a captured signature against a different, more privileged operation. The analogous fault in this repo is in the StackerDB chunk-authentication scheme: `SlotMetadata::auth_digest` signs only `(slot_id, slot_version, data_hash)` and never binds the signature to the specific StackerDB (smart contract) instance it was intended for. Both the write RPC and the p2p push path take the contract identifier out-of-band (from the URL path / message field) rather than from the signed data, so a validly-signed chunk produced for one StackerDB contract can be replayed verbatim against a different StackerDB contract, as long as the same signer key happens to own the same `slot_id` there.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest as: [1](#0-0) 
which hashes only `slot_id`, `slot_version`, and `data_hash` — no contract/DB identifier is included.

`StackerDBChunkData::sign`/`verify`/`recover_pk` derive their digest purely from `get_slot_metadata()`, i.e., the same three fields: [2](#0-1) 

On the write path, the target contract is taken from the URL, not from anything the client signed: [3](#0-2) 

Server-side validation (`validate_received_chunk`) then looks up the expected signer for that externally-supplied `smart_contract_id` and slot, and simply checks that the chunk's signature recovers to that address — the digest itself carries no notion of which contract it was created for: [4](#0-3) 

The same is true on the p2p push path (`StackerDBPushChunkData`), where `contract_id` is a separate, unsigned field alongside the signed `chunk_data`: [5](#0-4) 
`handle_unsolicited_StackerDBPushChunk` validates the chunk using `chunk_data.contract_id` taken from the message, again independent of what the signature commits to: [6](#0-5) 

Because the digest is `(slot_id, slot_version, data_hash)` only, any two StackerDB instances (e.g. `signer-N-0` and `signer-M-0` boot contracts, which commonly preserve the same signer-set ordering across reward cycles) that assign the same `slot_id` to the same signing key will accept an identical signature. An attacker who observes (or a signer who has previously produced) a validly-signed chunk for contract A can resubmit that exact `(slot_id, slot_version, sig, data)` tuple to contract B's endpoint/gossip channel; `SlotMetadata::verify` will succeed because it never checks which contract the signature was made for.

This is the structural equivalent of the Gatecoin bug: the authentication token (signature) fails to bind to all the context that determines its authorization scope (there, the request payload; here, the destination StackerDB/contract), so it can be legitimately verified while being applied somewhere the signer never intended.

### Impact Explanation
If exploited where slot-to-signer assignment overlaps across StackerDB contracts (a realistic scenario for the `signer-XXX-YYY` boot contracts across consecutive reward cycles, which frequently retain the same signer ordering), this allows:
- Unauthorized/forged writes into a StackerDB instance other than the one the signer intended, effectively spoofing a message from that signer in the wrong lane/cycle context.
- Propagation of this cross-contract-replayed chunk to the network via the normal StackerDB gossip/push mechanisms, since the write is not detectably invalid to any receiving node (the signature does check out for the slot owner of the target contract).

This matches the "network-wide propagation of forged data" / "unauthorized write to StackerDB" impact tier, since the write is accepted as authentic for a contract it was never authorized for.

### Likelihood Explanation
Exploitability depends on the attacker being able to observe a validly signed chunk (chunks are broadcast, e.g. via `StackerDBChunkInv`/`StackerDBGetChunkData` sync and the p2p `StackerDBPushChunk` message, so they are not secret) and on slot-id-to-signer mappings coinciding between two live StackerDB contracts. Given that consecutive reward-cycle signer contracts are commonly derived from the same signer set/ordering, this collision condition is plausible in production Nakamoto signer StackerDBs, though it is not guaranteed for every deployment. I was not able to fully verify from the available index whether the node additionally cross-checks the chunk against tenure/burn-view context that would incidentally block cross-contract replay in the `signer-XXX-YYY` case (e.g. `rc_consensus_hash` in `StackerDBPushChunkData` provides some view-binding for the p2p push path, but the direct HTTP POST endpoint in `poststackerdbchunk.rs` has no such binding at all).

### Recommendation
Include the target StackerDB's identity in the signed digest, e.g., have `SlotMetadata::auth_digest` (and thus `sign`/`verify`/`recover_pk`) hash in the `QualifiedContractIdentifier` (or a fixed-length hash/domain-separator derived from it) in addition to `slot_id`, `slot_version`, and `data_hash`. This must be a coordinated protocol/wire change (affecting `libstackerdb`, the StackerDB sync protocol, and all signer/miner clients that produce these signatures), since it changes what bytes are signed.

### Proof of Concept
1. Configure two StackerDB contracts, A and B, where the same private key `sk` is assigned as the owner of `slot_id = 0` in both (e.g. two consecutive `signer-N-0` boot contracts with an unchanged signer set ordering).
2. Sign chunk `data` with `sk` for contract A: `StackerDBChunkData::new(0, v, data).sign(&sk)` — producing `sig`.
3. Submit `(slot_id=0, slot_version=v, sig, data)` to contract B's endpoint: `POST /v2/stackerdb/<B-address>/<B-contract>/chunks` (see `poststackerdbchunk.rs` path regex) or replay it via the p2p `StackerDBPushChunk` message with `contract_id = B`.
4. `validate_received_chunk` for contract B looks up B's slot-0 owner (`sk`'s address), calls `slot_metadata.verify(&addr)`, which succeeds because `auth_digest` never referenced contract A or B — the chunk is accepted and stored/propagated under contract B despite being signed for contract A.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this given chunk data message with the given private key.
    /// Sets self.signature to the signature.
    /// Fails if the underlying signing library fails.
    pub fn sign(&mut self, privk: &StacksPrivateKey) -> Result<(), Error> {
        let mut md = self.get_slot_metadata();
        md.sign(privk)?;
        self.sig = md.signature;
        Ok(())
    }

    pub fn recover_pk(&self) -> Result<StacksPublicKey, Error> {
        let digest = self.get_slot_metadata().auth_digest();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(digest.as_bytes(), &self.sig)
            .map_err(|ve| Error::VerifyingError(ve.to_string()))
    }

    /// Verify that this chunk was signed by the given
    /// public key hash (`addr`).  Only fails if the underlying signing library fails.
    pub fn verify(&self, addr: &StacksAddress) -> Result<bool, Error> {
        let md = self.get_slot_metadata();
        md.verify(addr)
    }
}
