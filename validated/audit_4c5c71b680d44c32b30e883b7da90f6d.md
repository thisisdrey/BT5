### Title
Unvalidated reftable varint lengths allow out-of-bounds slice panics (DoS) - (File: internal/git/reftable/reftable.go)

### Summary
`Table.getRefsFromBlock` and its helper `Table.getVarInt` decode the reftable binary ref-block format using variable-length integers, but the decoded lengths (`prefixLength`, `suffixLength`, `updateIndexDelta`, symref `size`) are never validated against the actual size of the in-memory buffer before being used to slice it. This mirrors the bitcoin-spv defect where a length-prefix value taken from untrusted input was used to drive parsing without being checked against the real bounds of the data, letting a crafted value push the parser out of range.

### Finding Description
`getVarInt` only bounds-checks the *continuation* loop against `blockEnd`/`FullBlockSize`, i.e. it prevents reading past the intended end of the varint's own byte sequence, but it does nothing to validate that the *decoded value* itself is a sane length relative to the remaining buffer: [1](#0-0) 

`getRefsFromBlock` then uses these decoded, unchecked values directly as slice bounds:
- `refname := prefix[:prefixLength] + string(src[idx:idx+suffixLength])` — `prefixLength` can exceed `len(prefix)`, and `suffixLength` can push `idx+suffixLength` past `len(src)`.
- For symrefs, `reference.Target = git.ReferenceName(src[idx : idx+size])` uses a varint-derived `size` with the same lack of validation. [2](#0-1) 

Because Go slicing panics on out-of-range indices, any corrupted or maliciously crafted `.ref` table (the on-disk format for Git's "reftable" ref backend, which Gitaly reads via `ParseTable`/`GetReferences`) can trigger an unrecovered panic while Gitaly parses ref blocks: [3](#0-2) 

This is structurally the same bug class as the external report: a length value taken from a compact/variable encoding is trusted without validating it against the real size of the buffer it indexes into, allowing crafted input to break the parser's invariants.

### Impact Explanation
An out-of-range slice access in Go causes an immediate panic. If this panic occurs on a goroutine handling a gRPC request without a recover wrapper protecting it, it can crash the `gitaly` process or, at minimum, abort in-flight transactions repeatedly, denying service for the affected repository/partition. Because reftable parsing is invoked as part of the storage/WAL housekeeping path (`internal/gitaly/storage/storagemgr/partition/reftable.go` and `transaction_manager.go` consume `reftable.ReadTablesList`/table data), a corrupted table file can repeatedly disrupt partition recovery/application logic each time it is read.

### Likelihood Explanation
Reftable files are ordinarily written by Git itself, so under normal operation the format is well-formed. However, Gitaly's storage layer treats `.ref` table files as data it parses off disk during WAL application/replication rather than re-validating them via `git`, so any path that lets an attacker influence the bytes of a `.ref` file (e.g. corrupted/adversarial repository import, replication from a compromised peer, or a maliciously constructed backup/snapshot that is restored) can reach this parser with attacker-influenced content. I could not fully trace every ingress path that supplies raw reftable bytes to `Table.GetReferences`/`parseRefBlock` from an external, low-privileged actor within the time available, so likelihood is assessed as reachable-but-not-fully-proven from a purely external, unprivileged RPC in this pass.

### Recommendation
In `getVarInt`, `getRefsFromBlock`, and `parseRefBlock`, validate every varint-derived length/offset against `len(src)` (and against the applicable block boundary) before using it to slice, and return a descriptive parse error instead of allowing the slice operation to panic. Additionally, wrap reftable-file parsing entry points (`ParseTable`, `GetReferences`) with panic recovery so that a malformed table converts into a handled error rather than crashing the process, and add fuzz/property tests feeding truncated and inflated varint lengths to `getVarInt`/`getRefsFromBlock`.

### Proof of Concept
Construct a minimal reftable file whose ref block encodes a `suffixLength` varint (after shifting out the 3 `extra` bits) large enough that `idx+suffixLength` exceeds the actual block/file size, e.g. set the raw varint byte(s) to encode `suffixLength=0x7F` while the actual remaining block bytes are only a few bytes long. Feeding this file to `reftable.ParseTable(path)` followed by `table.GetReferences()` reaches `getRefsFromBlock`, where `src[idx : idx+suffixLength]` exceeds `len(src)` and Go panics with `slice bounds out of range`, crashing the parsing goroutine. // getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}

// GetReferences returns all references from the table.
func (t *Table) GetReferences() ([]git.Reference, error) {
	headerOffset := uint(t.footer.Version.HeaderSize())
	offset := uint(0)
	var allRefs []git.Reference

	if _, err := t.src.Seek(0, io.SeekStart); err != nil {
		return nil, fmt.Errorf("seek start: %w", err)
	}

	src, err := io.ReadAll(t.src)
	if err != nil {
		return nil, fmt.Errorf("read all: %w", err)
	}

	for offset < t.footerOffset {
		blockStart, blockEnd := t.getBlockRange(offset, t.blockSize)
		if blockStart == 0 && blockEnd == 0 {
			break
		}

		// If we run out of ref blocks, we can stop the iteration.
		if src[blockStart+headerOffset] != 'r' {
			return allRefs, nil
		}

		references, err := t.parseRefBlock(src, headerOffset, blockStart, blockEnd)
		if err != nil {
			return nil, fmt.Errorf("parsing block: %w", err)
		}

		if len(references) == 0 {
			break
		}

		allRefs = append(allRefs, references...)

		offset = blockEnd
	}

	return allRefs, nil
}
