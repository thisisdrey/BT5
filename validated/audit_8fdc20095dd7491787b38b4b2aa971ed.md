### Title
Self-matching a market order overwrites and permanently destroys the trader's own account-balance update — Storage-overwrite via aliased AccountCapsule copies - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.execute()` keeps a single in-memory `AccountCapsule` for the taker (`accountCapsule`) that is mutated throughout the whole order-matching flow and only persisted to `accountStore` once, at the very end of `execute()`. However, whenever a matched maker order happens to belong to the **same account address** as the taker (i.e. a user self-matches against their own resting order), the maker-side credit is applied to a **separate, freshly re-read copy** of the very same account and written back to the store immediately inside the matching loop. That in-store write is subsequently clobbered by the stale taker-side in-memory copy that gets persisted last in `execute()`, exactly mirroring the Anchor "two accounts are the same" storage-overwrite bug described in the WOOFi report.

### Finding Description
In `execute()`:
```
AccountCapsule accountCapsule = accountStore.get(contract.getOwnerAddress().toByteArray());
...
transferBalanceOrToken(accountCapsule);            // debits sell asset/fee in memory
MarketOrderCapsule orderCapsule = createAndSaveOrder(accountCapsule, contract);
matchOrder(orderCapsule, takerPrice, ret, accountCapsule);   // in-memory copy passed through
...
accountStore.put(accountCapsule.createDbKey(), accountCapsule); // final, single write-back
``` [1](#0-0) 

Inside the matching loop, `matchSingleOrder` credits the **taker** using the in-memory reference that was passed down:
```
addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule);
addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive);
``` [2](#0-1) [3](#0-2) 

The second call (no `AccountCapsule` argument) re-reads the maker's account **fresh from `accountStore`**, credits it, and immediately writes it back:
```
private void addTrxOrToken(MarketOrderCapsule orderCapsule, long num) {
  AccountCapsule accountCapsule = accountStore.get(orderCapsule.getOwnerAddress().toByteArray());
  ...
  accountStore.put(orderCapsule.getOwnerAddress().toByteArray(), accountCapsule);
}
``` [4](#0-3) 

When the maker order's owner address equals the taker's own address (self-trade), this second copy is aliased with the `accountCapsule`/`takerAccountCapsule` object still being carried through the rest of `execute()`. The immediate `accountStore.put(...)` from the maker path is a **stale-relative snapshot** (it does not include the taker-side credit already applied only in memory), and it is unconditionally clobbered by the final `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` at line 148, which itself does not include the maker-side credit. Nothing in `validate()` rejects a taker whose order matches one of their own existing resting orders — there is no owner-address collision check anywhere in `MarketSellAssetActuator.validate()`.

This is structurally identical to the WOOFi Anchor bug: two logical references to the *same* underlying account state are independently mutated and separately written back, so the last write silently discards the other party's update.

### Impact Explanation
When a user's new sell order matches their own previously-placed resting order:
- The asset/TRX that was already deducted from the account when the maker order was originally created (in a prior transaction) is never compensated, because the maker-side credit (`addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)`) is overwritten by the taker's in-memory snapshot.
- The user permanently loses the proceeds of the maker side of the trade — assets are burned from their balance without any corresponding credit, breaking the fundamental token/TRX conservation invariant of `AccountStore`.
- The market order itself is correctly marked `INACTIVE`/removed from the order book (since `orderStore.put` is unaffected), so the loss is silent and undetectable from order-book state — the user believes their trade completed normally while actually losing funds.

This is a genuine, permanent, unbacked-balance loss-of-funds condition reachable by any ordinary account issuing a single `MarketSellAssetContract` transaction, satisfying the "permanent freezing/loss of funds" and "unbacked balance" criteria.

### Likelihood Explanation
Any account can place two orders (e.g. sell TRX for TOKEN_A, then later sell TOKEN_A for TRX at a matching price) that end up crossing against each other. There is no validation-time or execution-time check preventing an order from matching against another order owned by the same address, so this is trivially triggerable by a single user without any special privileges, cooperation, or timing constraints.

### Recommendation
Ensure the maker-side account update in `addTrxOrToken(MarketOrderCapsule, long)` reuses the same in-memory `AccountCapsule` instance as the taker whenever the maker and taker addresses are identical (i.e., detect aliasing and operate on a single shared object, or defer all writes to the store until the very end of `execute()` using a per-address cache keyed by address so repeated reads return the same mutated instance). Alternatively, refactor `matchOrder`/`matchSingleOrder` to accumulate all balance deltas per address in memory and flush them once at the end of `execute()`, eliminating any intermediate `accountStore.put` calls during matching.

### Proof of Concept
1. Account `A` submits `MarketSellAssetContract`: sell 100 TRX, buy 100 `TOKEN_X` → creates and stores a resting maker order (`sellTokenID = "_"`, `buyTokenID = TOKEN_X`), deducting 100 TRX from `A`'s balance via `transferBalanceOrToken` [5](#0-4) .
2. Account `A` (same address) submits a second `MarketSellAssetContract`: sell 100 `TOKEN_X`, buy 100 TRX, at a matching price. This becomes the taker order and matches directly against `A`'s own resting maker order from step 1 inside `matchOrder`/`matchSingleOrder` [6](#0-5) .
3. During `matchSingleOrder`:
   - `addTrxOrToken(takerOrderCapsule, 100, takerAccountCapsule)` credits 100 TRX to the in-memory `accountCapsule` held since `execute()` began.
   - `addTrxOrToken(makerOrderCapsule, 100)` re-reads `A`'s account fresh from `accountStore` (missing the just-applied taker credit and the 100 `TOKEN_X` debit still only in-memory... actually including the correct TOKEN_X debit from DB, but missing the in-memory TRX credit), credits 100 `TOKEN_X`, and writes this snapshot back to `accountStore` immediately.
4. At the end of `execute()`, `accountStore.put(accountCapsule.createDbKey(), accountCapsule)` overwrites the store with the taker-side in-memory copy — which never received the 100 `TOKEN_X` maker credit written in step 3.
5. Final result: `A` has spent 100 TRX (maker) and 100 `TOKEN_X` (taker) but received only the 100 TRX taker-side credit; the 100 `TOKEN_X` maker-side credit is permanently lost, even though the order book shows both orders as fully filled.

  private void matchOrder(MarketOrderCapsule takerCapsule, MarketPrice takerPrice,
      TransactionResultCapsule ret, AccountCapsule takerAccountCapsule)
      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0
          && !orderIdListCapsule.isOrderEmpty()) {
        byte[] orderId = orderIdListCapsule.getHead();
        MarketOrderCapsule makerOrderCapsule = orderStore.get(orderId);

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order
        if (makerOrderCapsule.getSellTokenQuantityRemain() == 0) {
          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
        }
      }

      // the orders of makerPrice have been all consumed
      if (orderIdListCapsule.isOrderEmpty()) {
        pairPriceToOrderStore.delete(pairPriceKey);

        // need to delete marketPair if no more price(priceKeysList is empty after deleting)
        priceKeysList.remove(0);

        // update priceInfo's count
        remainCount = remainCount - 1;
        // if really empty, need to delete token pair from pairToPriceStore
        if (remainCount == 0) {
          pairToPriceStore.delete(makerPair);
          break;
        } else {
          pairToPriceStore.setPriceNum(makerPair, remainCount);
        }
      }
    } // end while
  }
