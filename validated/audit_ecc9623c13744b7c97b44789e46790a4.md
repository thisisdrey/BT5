### Title
Floating-point rounding drift in the legacy Bancor-style TRX/Token Exchange bonding-curve math permits value extraction from the liquidity pool - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The Amnext incident involved an attacker exploiting flawed internal token-accounting math in an AMM-like pool (mass-minting an internal "Ticket" unit and redeeming it for more real value than was deposited, draining the pool through PancakeSwap). Java-tron's built-in `Exchange*` actuators implement an equivalent internal AMM (a relay-supply Bancor formula) for swapping between TRX and TRC10 tokens. The default, non-hardened arithmetic path for this bonding curve is implemented entirely with Java `double` floating-point operations and truncating casts to `long`, and it is reachable by any account broadcasting an `ExchangeTransactionContract`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines depending on the `allowHardenExchangeCalculation` dynamic parameter: [1](#0-0) 

When the hardened flag is not active (the historical/default behavior, gated behind a committee proposal), every trade routes through `ExchangeProcessor`, whose relay-supply math is computed with `double` and `Math.pow`-style operations and then truncated to `long`: [2](#0-1) 

Both `exchangeToSupply` and `exchangeFromSupply` cast the double result down with `(long) issuedSupply` / `(long) exchangeBalance`, which always truncates toward zero. Because a swap is computed as two chained floating-point operations (sell-token → internal relay `supply` → buy-token), the truncation is not symmetric between the two legs, and floating-point results for the same economic operation are not guaranteed consistent across different `balance`/`quant` orderings. This is precisely the "no-loss pool that leaks value due to imprecise internal unit accounting" bug class seen in Amnext: repeated small operations against the internal accounting unit (there, "Ticket"; here, the internal Bancor `supply`) can be used to accumulate a rounding advantage at the pool's expense across many transactions, ultimately extracting more TRX/token from `firstTokenBalance`/`secondTokenBalance` than was contributed.

The actuator wraps outer balance bookkeeping in overflow-checked helpers only when hardening is enabled: [3](#0-2) 
but the core pricing formula itself (`ExchangeProcessor`) has no invariant check that a round-trip or sequence of trades cannot leave the pool net negative relative to real economic value — unlike `SafeExchangeProcessor`, which was added later using `BigDecimal` with explicit rounding modes, implicitly acknowledging the precision problem in the legacy path: [4](#0-3) 

The entry point (`ExchangeTransactionActuator.execute`) is reachable by any unprivileged account with a signed `ExchangeTransactionContract` and applies the computed `anotherTokenQuant` directly to account/pool balances with no post-hoc invariant re-validation: [5](#0-4) 

### Impact Explanation
If a chain has not activated `allowHardenExchangeCalculation` (or during any window where it is disabled), any account can repeatedly submit small `ExchangeTransactionContract` trades against a low-liquidity Exchange pool to exploit the asymmetric floating-point truncation in `ExchangeProcessor`, extracting real TRX/TRC10 balances from the pool over many transactions — a direct theft-of-funds primitive analogous to the Amnext "mass mint internal unit, redeem for more real value" pattern. This can drain both the pool's TRX and token reserves, which are ultimately backed by real user deposits.

### Likelihood Explanation
Likelihood is Medium: the attack requires (a) a chain/network where the hardened exchange calculation proposal has not been enabled, and (b) a pool with low enough liquidity/precision that repeated truncation bias becomes economically significant relative to transaction fees. Both are plausible for legacy or low-fee TRC10 exchange pools, and the transaction path (`ExchangeTransactionContract`) requires no special privilege — only TRX for fees/gas equivalent.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-based, exact-rounding) the mandatory calculation path for all exchange transactions regardless of the `allowHardenExchangeCalculation` flag, or retire the legacy `ExchangeProcessor` entirely.
- Add an explicit pool invariant check after every trade (e.g., the Bancor constant-product/relay-supply invariant must not decrease beyond fees) before committing new `firstTokenBalance`/`secondTokenBalance` values, rejecting the transaction otherwise.
- Add regression tests that perform sequences of many small round-trip trades and assert the pool's total value is monotonically non-decreasing (net of fees) under both math modes.

### Proof of Concept
Conceptual (bounded by inability to run bytecode/simulation in this environment):
1. Attacker creates or locates an `Exchange` pool with small `firstTokenBalance`/`secondTokenBalance` on a network where `allowHardenExchangeCalculation` is disabled (legacy default).
2. Attacker repeatedly broadcasts `ExchangeTransactionContract` transactions alternating the sell direction between `firstTokenId` and `secondTokenId` with small `quant` values, exploiting `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`'s `double`→`long` truncation asymmetry [6](#0-5) .
3. Each round trip nets the attacker a small positive rounding gain in one of the two pool assets (e.g., TRX), paid for by the pool at `ExchangeTransactionActuator.execute` [5](#0-4) .
4. Repeating this over many transactions accumulates a meaningful drain of the pool's TRX/token reserves, mirroring the Amnext pattern of extracting more value than deposited from a flawed internal accounting/pricing mechanism.

Note: I could not execute or numerically simulate the exact floating-point drift magnitude in this environment, so the precise profit-per-transaction and minimum viable pool size for an economically worthwhile attack remain unverified; this would need to be confirmed with a local simulation or unit test harness (e.g., extending `ExchangeProcessorTest`) before treating exploitability as fully proven.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
