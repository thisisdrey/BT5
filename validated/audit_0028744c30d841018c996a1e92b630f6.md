### Title
`PohService::record_or_hash` panics the entire validator on any non-success `PohRecorder::record()` result, unlike the graceful per-item error handling elsewhere in the pipeline - (File: poh/src/poh_service.rs)

### Summary
The Sherlock finding describes a loop that halts (reverts) entirely because a single element in a batch cannot be processed, and no graceful per-item error path exists. The strongest analog reachable in agave without any validator/operator privilege is in the PoH recording path: `PohService::record_or_hash` calls `PohRecorder::record(...)` and, on any `Err` other than the success path, executes `panic!("PohRecorder::record failed: {err:?}")`. This differs sharply from every other batch-processing path found in the codebase (`consumer.rs`, `svm/src/transaction_processor.rs`, `transaction_execution.rs`, `accounts-db/src/account_locks.rs`), all of which represent per-transaction failures as `Result`/`TransactionError` values that are cleanly propagated, retried, or dropped — never as a process panic. A single record call returning an unexpected error (e.g. a stale/mismatched `bank_id`, or `MaxHeightReached` reached via a race between banking-stage senders and slot rotation) crashes the PoH thread and therefore the whole validator process, which is a categorically more severe failure mode than the Sherlock report's reverted transaction.

### Finding Description
`TransactionRecorder::record` and `PohRecorder::record` are designed to return `Result<_, PohRecorderError>` (variants include `MaxHeightReached`), and callers such as `core/src/banking_stage/consumer.rs` and `core/src/banking_stage/vote_worker.rs` explicitly handle these errors without crashing — they convert them into retryable/`not_included_reasons` responses. [1](#0-0) 

However, the low-level PoH tick/record loop that actually drives PoH hashing for the leader — `PohService::tick_producer` / `record_or_hash` — treats a non-`Ok` result from `poh_recorder_l.record(...)` as an unrecoverable condition and panics the thread: [2](#0-1) 

The same panic-on-error pattern also exists in the low-power test/short-lived tick producer's `read_record_receiver_and_process` helper: [3](#0-2) 

Contrast this with the deliberate, per-item error handling seen everywhere else that iterates over multiple items:
- `svm/src/transaction_processor.rs` aborts only the offending sub-range with `TransactionError::CommitCancelled`, never panics: [4](#0-3) 
- `accounts-db/src/account_locks.rs` returns per-transaction `TransactionResult<()>` instead of aborting the whole locking pass: [5](#0-4) 
- `core/src/banking_stage/consume_worker.rs` treats a failed commit as a retry signal, not a panic: [6](#0-5) 

The PoH record loop is the exception: it is fed continuously by banking-stage/leader activity that is driven by ordinary, unprivileged user transaction traffic (any client submitting transactions that get batched and recorded), and any single "record" call hitting an unexpected `Err` branch (any variant besides the handled success path) terminates the whole node via `panic!`.

### Impact Explanation
A panic in the PoH producer thread is fatal to the running validator process (thread panic without `catch_unwind` typically aborts or corrupts the process depending on panic strategy/build config), taking the node offline. Because PoH recording underlies all block production, this is a full node crash/DoS rather than a single reverted call as in the original Sherlock report — an attacker or even ordinary heavy transaction load hitting a race between the record path and bank/slot rotation state could reliably trigger the panic path across all instances running this code, unlike the Sherlock case which only affected a single Sherlock protocol's ability to withdraw/interact.

### Likelihood Explanation
Likelihood depends on whether `PohRecorder::record` can actually return a non-`MaxHeightReached`-handled error, or `MaxHeightReached` itself, while `record_or_hash`/`read_record_receiver_and_process` still hold a `next_record`/queued record that was accepted by `RecordReceiver` before the working bank was rotated/cleared — i.e., a race between the leader's slot boundary handling (which shuts down and drains `record_receiver`) and continued sends from banking-stage. This is plausible under high transaction throughput/backpressure because the record queue and slot-transition logic are asynchronous, but I was not able to fully trace every guard in `PohRecorder::reset`/`clear_bank`/`RecordReceiver::shutdown` in the time available to confirm whether existing shutdown-and-drain sequencing (see `shutdown_and_drain_record_receiver` in `core/src/block_creation_loop.rs`) fully eliminates the race in all code paths, or only in the `block_creation_loop.rs` alpenglow-style leader path versus the classic `tick_producer` path in `poh_service.rs`. This uncertainty should be resolved with further tracing/fuzzing before treating this as confirmed-exploitable.

### Recommendation
Replace the `panic!("PohRecorder::record failed: {err:?}")` branches in `PohService::record_or_hash` and `PohService::read_record_receiver_and_process` with the same graceful pattern used elsewhere in the codebase (`consumer.rs`, `transaction_processor.rs`): treat unexpected `PohRecorderError` results as a signal to abandon/reset the current leader slot (as `abort_working_bank`/`abort_failed_working_bank` already do in `block_creation_loop.rs`) rather than aborting the entire process, and add explicit regression tests that inject a race between record submission and slot/bank rotation to confirm the non-panicking path is exercised.

### Proof of Concept
Not independently reproduced; based on static code-path analysis of `poh/src/poh_service.rs` lines 308-333 and 460-496 versus the graceful error-handling patterns confirmed in `core/src/banking_stage/consumer.rs`, `svm/src/transaction_processor.rs`, and `accounts-db/src/account_locks.rs`. A concrete PoC would require constructing a timing scenario (heavy transaction submission near a slot boundary) that causes `record_receiver`/`working_bank` state to diverge such that `PohRecorder::record` returns an `Err` not otherwise pre-filtered, which could not be fully verified within the scope of this analysis.
