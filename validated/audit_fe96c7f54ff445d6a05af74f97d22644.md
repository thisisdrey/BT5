### Title
Signature-Malleability Double-Counting in `ValidateMultiSign` Precompile Allows a Single Key to Satisfy a Multi-Signature Threshold - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The HashiCorp Vault advisory (CVE-2020-16250) is an authentication-bypass caused by insufficient verification that a presented credential/proof actually corresponds to a unique, intended identity, allowing spoofed identity to be accepted. The closest analogous, reachable java-tron pattern is in the `ValidateMultiSign` TVM precompile at `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java:1036-1121`, where the duplicate-signer detection logic keys deduplication off the *raw signature bytes* concatenated with the recovered address, rather than off the *recovered address alone*. Because ECDSA signatures are malleable (for any valid `(r, s)` there is a second valid signature `(r, n-s)` with a flipped recovery id that recovers to the exact same address), a single private key can produce two different, both-valid signatures over the same message, causing the same signer's weight to be counted twice toward `permission.getThreshold()`.

### Finding Description
`ValidateMultiSign.execute()` iterates over the caller-supplied signature array and, for each signature, recovers a signer address, then decides whether to skip counting it as a duplicate: [1](#0-0) 

```
long totalWeight = 0L;
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
if (totalWeight >= permission.getThreshold()) {
  return Pair.of(true, dataOne());
}
```

The `continue` (skip) branch only triggers when the *exact byte-for-byte signature* (concatenated with the recovered address) has already been seen for that address. If `recoveredAddr` was already used for a *different* signature (e.g., a malleated `(r, n-s)` variant of the same signature, or any of the 4 recovery-id/curve-point variants that still recover to the same address), the code falls through, looks up `getWeight(permission, recoveredAddr)` again, and adds it to `totalWeight` a second time.

This is directly analogous to the CVE's root cause class (CWE-345 Insufficient Verification of Data Authenticity / CWE-290 Authentication Bypass by Spoofing): the contract-facing on-chain multisig verification trusts that each element of the signature array represents an independent authorization from a distinct key, but it fails to bind/deduplicate by the actual cryptographic identity (the recovered address) — only by the literal bytes of the proof. An attacker fully controlling the input to this precompile (any contract call, from any unprivileged EOA/contract) can spoof "multiple independent approvals" using only one private key.

Contrast this with `TransactionCapsule.checkWeight()` used for top-level transaction signature verification, which (post `VERSION_4_7_1` fork) explicitly keys `addMap` by the **recovered address**, not raw signature bytes: [2](#0-1) 

This confirms the team is aware that address-based (not signature-byte-based) deduplication is the correct approach for multisig weight accounting — but the TVM `ValidateMultiSign` precompile was not hardened the same way.

### Impact Explanation
`ValidateMultiSign` is a public, permissionless TVM precompile (address `0x...a`) reachable from any smart contract deployed by any account, and it is specifically designed to let TRC-20/DApp contracts implement multisig-gated logic (e.g., custodial wallets, DAOs, exchange withdrawal contracts) by querying whether a set of signatures meets an account's permission threshold. If a contract relies on this precompile to gate a sensitive operation (fund release, governance action, withdrawal approval) requiring `threshold`-of-`N` independent signers, an attacker who controls only a single key that is one of the `N` authorized signers can submit two malleated signatures from that one key and have the precompile report the threshold satisfied — even though only one real signer authorized the action. This can lead to unauthorized execution of privileged contract logic, theft of funds, or bypass of governance/withdrawal safeguards in any dependent contract, which is a concrete unauthorized-account-operation / theft-of-funds impact as required.

### Likelihood Explanation
Likelihood is high for any contract that uses `ValidateMultiSign` for m-of-n authorization with `m < n` and a signer whose weight alone is insufficient: producing an ECDSA signature malleability variant `(r, n-s)` from an existing valid `(r,s)` signature requires no private key access beyond having one legitimate signature from a legitimate signer, and is a pure, well-known, deterministic elliptic-curve computation (flip `s` to `n-s`, flip recovery id). No special network position, timing, or race condition is required — it is a fully deterministic, offline-computable transformation on data the attacker already legitimately possesses (their own valid signature).

### Recommendation
In `ValidateMultiSign.execute()` (and audit `BatchValidateSign` for the same pattern), deduplicate strictly by `recoveredAddr` rather than by `merge(recoveredAddr, sign)`:
- Once an address has contributed weight, skip it entirely for the remainder of the loop regardless of whether the specific signature bytes differ (i.e., remove the inner `matrixContains(executedSignList, sign)` fallthrough that allows re-counting a re-signed/malleated signature from an already-counted address).
- Alternatively, enforce canonical (low-S) signature form during `recoverAddrBySign`/signature validation so that only one of the two malleable variants is ever considered valid, consistent with how `TransactionCapsule.checkWeight` keys `addMap` by address post-fork.

### Proof of Concept
1. Deploy (or use) an on-chain contract relying on `ValidateMultiSign(address, uint256 permissionId, bytes32 data, bytes[] signatures)` to gate execution of a sensitive function, where the target account's `Active`/custom permission requires `threshold = 2` with two keys `K1` (weight 1) and `K2` (weight 1).
2. As an attacker holding only `K1`'s private key, compute `hash = sha256(address || permissionId || data)` per the precompile's construction (`PrecompiledContracts.java:1062-1064`).
3. Sign `hash` once normally with `K1` to get `sig1 = (r, s, v)`.
4. Derive the malleable counterpart `sig2 = (r, n-s, v')` (flip `s` mod curve order `n`, flip recovery parity) — this is a standard ECDSA malleability transform requiring no private key, only `sig1`.
5. Call `ValidateMultiSign(address, permissionId, data, [sig1, sig2])`.
6. Both `sig1` and `sig2` recover to `K1`'s address. Because `merge(recoveredAddr, sig2) != merge(recoveredAddr, sig1)`, the inner-`continue` guard is skipped, `getWeight` is looked up and added twice, yielding `totalWeight = 2 >= threshold (2)`, and the precompile returns `dataOne()` (success) despite only one real signer (`K1`) having approved. `K2` never signed anything.
