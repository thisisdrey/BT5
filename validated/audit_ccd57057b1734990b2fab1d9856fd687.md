### Title
Attacker can permanently block a victim from adding new collateral or debt positions by dust-filling their per-account token list to `MAX_TOKENS_PER_USER` - ([File: contracts/Pool.sol])

### Summary
The analog to CVE-2017-2635 (a crash/DoS caused by mishandling an empty resource entry) is Metronome's per-account `MappedEnumerableSet` bookkeeping in `Pool`. An unprivileged attacker can, with only dust amounts, force entries into a victim's `depositTokensOfAccount` set until it reaches `MAX_TOKENS_PER_USER` (30). After that, every code path that would add a *new* deposit token or debt token to the victim's account reverts with `UserReachedMaxTokens`, denying the victim the ability to open new collateral positions or issue new synthetic debt — including the deposit they would need to rescue an unhealthy position.

### Finding Description
`Pool` tracks, per account, the set of deposit tokens and debt tokens the account has interacted with, capped by a constant:

- `MAX_TOKENS_PER_USER = 30` at contracts/Pool.sol:79.
- The `onlyIfAdditionWillNotReachMaxTokens` modifier reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` at contracts/Pool.sol:143-148.
- `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` apply that modifier at contracts/Pool.sol:204-220.

Critically, entries are added not only when a user deposits for themselves, but also on plain ERC20-style transfers: `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token moves from zero to positive at contracts/DepositToken.sol:517-520, and `_mint` does the same at contracts/DepositToken.sol:485-488. The recipient has no way to opt out, and a token only leaves the set when the balance returns to exactly zero (contracts/DepositToken.sol:522-525).

Attack path (fully unprivileged):
1. Attacker acquires dust balances in every `DepositToken` listed in the pool (up to 30 collaterals can be registered, contracts/Pool.sol:703).
2. Attacker calls `transfer(victim, 1)` (or deposits dust `onBehalfOf_ = victim`, since `deposit` accepts an arbitrary beneficiary, contracts/DepositToken.sol:211-216) for each deposit token the victim does not yet hold.
3. Each transfer pushes one entry into `depositTokensOfAccount[victim]` via `addToDepositTokensOfAccount`. No consent or minimum amount is required.
4. Once the combined debt + deposit token count hits 30, any subsequent `deposit`, `mint` of a new synthetic asset (`DebtToken._mint` adds to `debtTokensOfAccount`), leverage via `SmartFarmingManager.leverage`, or transfer of a new deposit-token type to the victim reverts with `UserReachedMaxTokens`.

The same griefing applies through `Operator.execute`/`SynthContext`, so it also works when the victim interacts through meta-transactions.

### Impact Explanation
- **Temporary/permanent freezing of position management**: the victim cannot add a new collateral type or a new debt type until they fully exit an existing token balance (transfer/burn to zero). For a victim whose only free path to restore health is depositing a *new* collateral (e.g., their existing collateral token is illiquid for them, or they simply hold a different asset), the inability to deposit can directly cause their position to be liquidated — funds that could have been saved are seized by liquidators.
- The attack costs the attacker only dust amounts (wei-level) of each deposit token's underlying, and no privileged role, oracle manipulation, or governance action is required.
- Even absent liquidation, the victim's ability to receive new deposit tokens, mint new synthetics, or use `SmartFarmingManager` leverage into new collaterals is DoSed, which matches the "temporary freezing of funds" acceptance criterion: exits that require adding a token (e.g., swapping debt into a different synthetic) revert unconditionally.

### Likelihood Explanation
- Requires no privileges: `deposit(onBehalfOf_)` and `transfer` are public and need only dust of whitelisted underlyings.
- Deterministic: there is no check that the recipient consented, no minimum amount, and no way for the victim to remove an entry without zeroing the balance (they can shed entries by transferring dust away, so the DoS is escapable with effort — which keeps severity at temporary-freezing / griefing level rather than permanent theft).
- Caveat (uncertainty): the attack is only impactful if the victim genuinely needs a *new* token entry — e.g., depositing a collateral they don't yet hold to avoid liquidation, or minting a new synthetic. If the victim already holds entries for everything they need, impact is limited. Also note the victim can remove attacker-planted entries by sending the dust to another address, so a sophisticated victim can recover; the attack still reliably traps positions during the window before they do, and passive/contract-based recipients (multisigs, gateways, Operator-mediated flows) may not be able to.

### Recommendation
- Do not add entries to `depositTokensOfAccount` on unsolicited transfers, or allow the recipient to remove an entry without zeroing the balance (e.g., an account-facing `removeMyToken(token)` that only requires balance below a dust threshold, or removal whenever the position is not counted toward issuable limit).
- Alternatively, only enforce `onlyIfAdditionWillNotReachMaxTokens` for actions the account initiates itself (deposit/mint), and let `addToDepositTokensOfAccount` skip (rather than revert) when the cap is reached on the transfer path — the per-account list is an optimization for `depositOf`/`debtOf` iteration, so missing entries can be handled gracefully.
- A minimal fix consistent with current design: in `DepositToken._transfer`, wrap `pool.addToDepositTokensOfAccount(recipient_)` so a `UserReachedMaxTokens` revert does not propagate, or enforce the cap in `deposit`/`mint` only.

### Proof of Concept
Foundry/Hardhat sketch (against the deployed-style pool with ≥2 deposit tokens; scales to 30):

```solidity
// victim has an open position using depositTokenA and debtTokenX.
// Pool lists depositTokenA ... depositTokenN (N up to 30).

// 1. Attacker seeds dust of every deposit token the victim lacks.
for (uint i; i < poolTokens.length; ++i) {
    IDepositToken dt = IDepositToken(poolTokens[i]);
    if (dt.balanceOf(victim) == 0 && attackerHolds(dt)) {
        // deposit dust for self then transfer, or deposit onBehalfOf victim directly:
        dt.underlying().approve(address(dt), 1);
        dt.deposit(1, attacker);            // mint msdTOKEN dust
        dt.transfer(victim, 1);             // adds entry to depositTokensOfAccount[victim]
    }
}

// 2. Assert the victim's combined set length == 30.
assertEq(
    pool.getDepositTokensOfAccount(victim).length
  + pool.getDebtTokensOfAccount(victim).length,
    pool.MAX_TOKENS_PER_USER()
);

// 3. Victim tries to deposit a NEW collateral to rescue an unhealthy position.
vm.startPrank(victim);
newUnderlying.approve(address(newDepositToken), amount);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDepositToken.deposit(amount, victim); // reverts inside addToDepositTokensOfAccount

// 4. Victim cannot mint a new synthetic debt token either.
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
newDebtToken.mint(victim, amount);

// 5. Victim's still-unhealthy position is then liquidated normally.
pool.liquidate(synthX, victim, repayAmount, depositTokenA);
```

Key mechanics verified in code:
- `addToDepositTokensOfAccount` / `onlyIfAdditionWillNotReachMaxTokens`: contracts/Pool.sol:143-148, 216-220.
- Unsolicited entries on `transfer`/`deposit(onBehalfOf)`: contracts/DepositToken.sol:211-216, 485-488, 517-520.
- Removal only at zero balance (attacker's dust keeps the slot occupied until the victim spends gas to clear it): contracts/DepositToken.sol:522-525.
- Revert propagates up through `deposit`, `DebtToken` mint paths, and `SmartFarmingManager.leverage`/`flashRepay` (which call `DepositToken.deposit`/`flashWithdraw` and `DebtToken.mint`, contracts/SmartFarmingManager.sol:155-211).

Not fully verified (index limits): the exact per-account set implementation in `contracts/lib/MappedEnumerableSet.sol` and whether any higher-level entry point strips the revert; the PoC assumes standard `EnumerableSet` semantics consistent with `add`/`remove`/`length` usage in `Pool.sol`.
