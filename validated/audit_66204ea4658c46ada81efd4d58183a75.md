### Title
StackerDB chunk signatures omit the target contract identifier, allowing cross-contract signature replay to write forged chunks - (File: libstackerdb/src/libstackerdb.rs)

### Summary
`SlotMetadata::auth_digest` — the digest that `StackerDBChunkData`/`SlotMetadata` signatures are computed and verified over — binds only to `(slot_id, slot_version, data_hash)` and never to the StackerDB smart-contract identifier the chunk is destined for. Any validly-signed chunk observed on the network (chunks are broadcast in the clear via P2P push/inventory sync and RPC POST) can therefore be replayed verbatim against a *different* StackerDB contract where the same signer address happens to own the same `slot_id`, as long as the target's currently stored version is `<=` the replayed version. This is the same bug class as the referenced report: a signature/authorization token that is valid for one context is silently accepted in an unintended context because the signed payload does not bind to that context.

### Finding Description
`SlotMetadata::auth_digest()` computes: [1](#0-0) 

Note it hashes only `slot_id`, `slot_version`, and `data_hash` — no `smart_contract_id`/`QualifiedContractIdentifier` is ever included. `verify()` recovers the public key from this same digest and only checks the recovered address against the caller-supplied `principal`: [2](#0-1) 

The storage path `StackerDBTx::try_replace_chunk` looks up the expected signer *for the given contract and slot*, then calls `slot_desc.verify(&slot_validation.signer)`: [3](#0-2) 

and the gossip/replication acceptance path `PeerNetwork::validate_received_chunk` does the analogous check by looking up `get_slot_signer(smart_contract_id, data.slot_id)` and then verifying the chunk's `SlotMetadata` against that address, again with no binding of the signature to the contract itself: [4](#0-3) 

Because the contract identity enters the check only via *which local config/table is consulted* (not via anything the signature itself covers), any party — not just the signer — can take a chunk that was legitimately produced and broadcast for contract A and resubmit it (via `POST /v2/stackerdb/.../chunks` or via unsolicited `StackerDBPushChunk`/`StackerDBChunkInv` gossip) as if it were destined for contract B, provided:
- the recovered signer address for that `slot_id` is the same in contract B's slot table (this occurs naturally whenever the same signer is assigned the same `slot_id` across multiple StackerDB instances, e.g. the per-message-id "signer" lanes and per-cycle "miner"/"signers" contracts derived from the same reward-set/signer list), and
- the replayed `slot_version` is not stale relative to contract B's current version for that slot.

This breaks the equality "a signature authenticates data *for the specific StackerDB it was produced for*" — the signature only authenticates `(slot_id, slot_version, hash(data))`, not which contract's slot it was meant to occupy. The `libsigner` `TryFrom<StackerDBChunksEvent>` payload-kind check (`signer_message_payload_matches_lane`) is an application-layer filter for whether the deserialized message parses/matches a lane; it happens after the chunk has already been accepted and durably written into the wrong contract's slot table by `try_replace_chunk`, so it does not prevent the unauthorized write, only the (possible) subsequent misinterpretation: [5](#0-4) 

### Impact Explanation
This is an unauthenticated/unauthorized write to state: a chunk intended and authorized for one StackerDB contract can be forced (replayed) into a different StackerDB contract's slot by any observer of network traffic, without needing the slot owner's key for that specific write. It can be used to overwrite a signer's current, freshly-written slot content in an unrelated StackerDB with stale/garbage data (denial of availability for that slot/contract, since a legitimate later write from the real owner intended for contract B is now competing with version numbers consumed by the replayed chunk), and to inject attacker-controlled/relayed data into contracts the signer never intended to write to. Since chunk writes/propagation are the mechanism `libsigner` and downstream signer/miner logic rely on for out-of-band signer coordination, this can also propagate forged-context data across the network via ordinary `StackerDBChunkInv`/`StackerDBPushChunk` gossip.

### Likelihood Explanation
Exploitability requires only: (1) observing a validly-signed chunk (trivial — StackerDB chunks are broadcast/publicly retrievable), and (2) the same signer address owning the same `slot_id` in a second StackerDB contract with a version that is not yet ahead of the replayed one. Given that Nakamoto signer-set-derived StackerDB contracts (miner/signer message-id lanes, per-cycle contracts) commonly assign slot ids deterministically from the same ordered signer list, this precondition is realistic rather than contrived, making likelihood moderate-to-high for any deployment running multiple StackerDB contracts sharing a signer set.

### Recommendation
Include the target StackerDB's contract identifier (e.g. `smart_contract_id`/`QualifiedContractIdentifier`, serialized canonically) in `SlotMetadata::auth_digest()` so signatures are bound to the specific StackerDB instance they authorize, mirroring how the upstream PoolTogether fix requires binding a signed authorization to its intended single use/context. This requires a coordinated protocol version bump since it changes what `sign`/`verify` compute over.

### Proof of Concept
1. Signer `S` is registered as the owner of `slot_id = k` in StackerDB contract `A` (version currently 0) and also as owner of `slot_id = k` in StackerDB contract `B` (version currently 0), which occurs naturally for shared signer-set-derived contracts.
2. `S` legitimately creates and signs `StackerDBChunkData { slot_id: k, slot_version: 1, data: D, sig }` for contract `A`, and it is broadcast/pushed publicly, e.g. via `handle_unsolicited_StackerDBPushChunk` gossip or served over the `GET .../chunks` endpoint.
3. Attacker `M` observes this chunk (no crypto secrets needed) and submits the *identical* `StackerDBChunkData` (same `slot_id`, `slot_version`, `sig`, `data`) but targeting contract `B`, either via the `POST /v2/stackerdb/{B}/chunks` RPC endpoint or via unsolicited `StackerDBPushChunk` gossip naming contract `B`.
4. `PeerNetwork::validate_received_chunk`/`StackerDBTx::try_replace_chunk` look up `B`'s slot `k` signer (which is also `S`), call `slot_metadata.verify(&S)`, which succeeds because the digest never referenced the contract, and version `1 > 0` passes the staleness check — the chunk is accepted and stored into contract `B`'s slot `k`, even though `S` never signed anything for contract `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
