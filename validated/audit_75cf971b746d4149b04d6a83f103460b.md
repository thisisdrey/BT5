Based on my investigation, I found a strong analog to the escrow-accounting bug in Nebula's `handleRecvError` path: state used to gate a security-relevant action (source-address verification) is treated as absent instead of failing closed, letting an unauthenticated packet tear down a live tunnel — mirroring how the Solidity bug let a stale/absent escrow record produce an unintended, unauthorized state transition.

### Title
Unauthenticated RecvError can tear down a tunnel when the hostinfo's remote address is not yet set - ([File: outside.go])

### Summary
`handleRecvError` looks up a `HostInfo` purely by an attacker-supplied `RemoteIndex` in the plaintext header and only validates the sender's address against `hostinfo.GetRemote()` "if" that remote is already valid. When it is not yet valid (e.g., a fresh/roaming/relayed tunnel where the remote `AddrPort` hasn't been recorded), the address check is skipped entirely and the tunnel is torn down based solely on an unauthenticated, unencrypted control packet.

### Finding Description
`RecvError` packets are sent and processed outside of any AEAD authentication — they consist only of the plaintext Nebula header (`Version, RecvError, 0, index, 0`). `sendRecvError` builds this packet with no encryption: [1](#0-0) 

`handleRecvError` resolves the target `HostInfo` from `h.RemoteIndex` and then performs the spoof check:
```
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    ... reject ...
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
``` [2](#0-1) 

The guard `hr.IsValid() && hr != addr` only rejects a mismatched sender when the hostinfo already has a valid remote recorded. If `hr` is not valid (the zero-value `netip.AddrPort`), the condition short-circuits to false and the address check is skipped — the tunnel is closed and its handshake state deleted for *any* sender that can produce a plausible `RemoteIndex`, without proving they are the actual peer. This is directly analogous to the Dinari bug: a security-relevant record (`hostinfo.remote` / `getOrderEscrow`) that is absent/stale is treated as "no constraint applies" rather than "fail closed," letting an operation (fund transfer / tunnel teardown) proceed that should have been blocked.

`RemoteIndex` values are generated via `generateIndex` and are 32-bit values exchanged in cleartext handshake and data-plane headers, so an on-path or otherwise observing attacker (who needs no CA-signed certificate — they never need to complete a Nebula handshake) can learn or guess a live index and forge a `RecvError` packet whenever the target's remote endpoint has not yet been pinned (this window exists on tunnels that use relays, or by racing right after a handshake before `GetRemote()` is set).

### Impact Explanation
An unauthenticated attacker (no valid certificate, not a party to any tunnel) can force a remote node to close an active or in-progress tunnel and delete the corresponding pending/handshake state (`f.handshakeManager.DeleteHostInfo`), causing a remote denial-of-service / connection disruption that bypasses the certificate/authentication model entirely — the same class of harm as the escrow bug allowing an operation to proceed against invariants that should have blocked it.

### Likelihood Explanation
Exploitability depends on the attacker knowing a valid `RemoteIndex` and reaching a moment where `hostinfo.remote` is still the zero value (unset) — this is plausible for relayed tunnels, tunnels mid-handshake, or freshly roamed tunnels, and `acceptRecvErrorConfig.ShouldRecvError` provides only a rate/config gate, not authentication. This is a real but timing/state-dependent condition rather than a trivially-always-exploitable one, so likelihood is moderate.

### Recommendation
Fail closed when `hostinfo.GetRemote()` is not yet valid: either drop the `RecvError` packet outright when no remote is pinned, or require the packet's source to match the address most recently associated with that index via an authenticated channel before acting on it. At minimum, do not let an absent/zero-value state field silently disable the anti-spoofing check.

### Proof of Concept
1. Attacker observes or infers a victim's live `localIndexId`/`RemoteIndex` (exchanged in cleartext Nebula headers, e.g., during a relayed handshake or shortly after roaming before `GetRemote()` is populated).
2. Attacker crafts a bare header packet: `header.Encode(buf, header.Version, header.RecvError, 0, index, 0)` and sends it to the victim's UDP listener from any arbitrary source address.
3. On the victim, `handleRecvError` resolves the hostinfo via `QueryReverseIndex(h.RemoteIndex)`; since `hostinfo.GetRemote()` has not been set yet (`hr.IsValid()` is false), the `hr != addr` check is skipped.
4. `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` execute, tearing down the tunnel/handshake state without the attacker ever presenting a valid certificate or completing a handshake with the victim.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
