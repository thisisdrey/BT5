### Title
Reserve-balance drift in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` from inconsistent rounding can bias the shared bonding-curve pool used by `ExchangeTransactionActuator` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The Clipper exploit manipulated a single-asset deposit/withdraw path to distort pool reserves used elsewhere for pricing, letting the attacker extract more than deposited. java-tron's TRX/TRC10 Bancor-style `Exchange` feature has an analogous structural pattern: `ExchangeInjectActuator` and `ExchangeWithdrawActuator` mutate `firstTokenBalance`/`secondTokenBalance` using simple linear-ratio integer division [1](#0-0) , while these same two balances are the reserves consumed by the bonding-curve trade formula in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction` used by every other trader [2](#0-1) . The withdraw path additionally gates its precision check on a feature flag (`allowHardenExchangeCalculation`) that switches between an imprecise `double`-based tolerance check and a safer `BigDecimal` one [3](#0-2) .

### Finding Description
`ExchangeInjectActuator.execute` computes the paired-token amount with truncating integer math (`floorDiv(multiplyExact(...), ...)`) [1](#0-0) , meaning the injecting account always pays a rounded-down amount of the paired token relative to the exact proportional ratio.

`ExchangeWithdrawActuator.doValidate` computes the same quantity twice with two different techniques: first with plain `BigInteger` truncating division (matching what `execute` will actually apply) [4](#0-3) , and then re-derives an independent "precision" check using `double` arithmetic when `allowHardenExchangeCalculation` is not enabled [5](#0-4) . The existence of the `allowHarden`/`hardenedPrecisionCheck*` test suite [6](#0-5)  indicates the double-based path was a recognized source of precision error that was subsequently "hardened" behind a dynamic, committee-controlled toggle rather than being fixed unconditionally.

Both actuators are reachable only by the exchange's own creator (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), but any account can permissionlessly become a creator via `ExchangeCreateContract`, and the reserves they mutate (`firstTokenBalance`/`secondTokenBalance`) are the exact inputs consumed by `ExchangeCapsule.transaction()` for every other trader's `ExchangeTransactionContract` [2](#0-1) . This mirrors Clipper's root cause: a deposit/withdraw code path with weaker/rounded arithmetic that diverges from the arithmetic used for pricing/settlement, letting the party controlling deposits/withdrawals bias the shared reserve ratio that other unrelated participants trade against.

### Impact Explanation
If reserve-ratio drift can be repeatedly and cheaply induced (inject/withdraw fee is `0`, see `calcFee()` returning `0` in both actuators [7](#0-6) ), an exchange creator could skew the pool's effective price away from its bonding-curve-implied value and profit at the expense of counterparties trading via `ExchangeTransactionActuator`, or the imprecise (`double`) precision check could admit withdrawal quantities that are less "clean" than the tolerance intends, letting the withdrawer extract more paired-token value than the pool's true backing supports. This would constitute unauthorized value extraction from a shared/trusted liquidity structure, comparable in class (not necessarily in scale) to the Clipper incident.

### Likelihood Explanation
Likelihood is constrained by two factors I could not fully resolve given available context: (1) the practical per-transaction drift is bounded by integer truncation (sub-unit, i.e., less than 1 token unit per call), so a large loss would require many repeated inject/withdraw cycles, which is technically feasible since fees are `0`; and (2) whether `allowHardenExchangeCalculation` is enabled by default on mainnet — if it is already enabled, the weaker `double` check is dead code and this narrows to the plain truncation-based drift only. I was unable to verify the default value of this dynamic property within the available tool budget.

### Recommendation
- Use identical arithmetic (ideally exact `BigDecimal`/`BigInteger` with an explicit, symmetric rounding rule) across `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, and the bonding-curve `exchange()` calculation so no direction of the deposit/withdraw path can systematically bias reserves in the caller's favor.
- Remove or unconditionally enforce the `BigDecimal`/hardened precision path in `ExchangeWithdrawActuator`; do not leave a known-imprecise `double`-based check reachable behind a toggle.
- Consider requiring inject/withdraw to preserve the reserve ratio exactly (reject any operation whose rounding error is nonzero) rather than merely bounding it to a percentage tolerance.

### Proof of Concept
I was not able to construct/verify a concrete end-to-end numeric PoC within the available tool budget (would require confirming the default value of `allowHardenExchangeCalculation`, and simulating a multi-cycle inject/withdraw drift against `ExchangeCapsule.transaction()` to quantify extractable value). The code paths and inconsistency cited above are directly verifiable in the repository; a full quantitative PoC would need to be built and tested in a Devin session with access to run the existing `ExchangeInjectActuatorTest`/`ExchangeWithdrawActuatorTest`/`ExchangeProcessorTest` suites to measure cumulative drift over many cycles.

  /**
   * Hardened mode: BigDecimal precision-loss check passes when input is precise.
   */
  @Test
  public void hardenedPrecisionCheckPassesWhenPrecise() {
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);
    dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    InitExchangeSameTokenNameActive();
    long exchangeId = 1;
    // 100M / 200M pool, withdraw 100M of first token (full ratio, precise)
    String firstTokenId = "123";
    long firstTokenQuant = 100000000L;

    ExchangeWithdrawActuator actuator = new ExchangeWithdrawActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, exchangeId, firstTokenId, firstTokenQuant));
    TransactionResultCapsule ret = new TransactionResultCapsule();
    try {
      actuator.validate();
      actuator.execute(ret);
      Assert.assertEquals(code.SUCESS, ret.getInstance().getRet());
    } catch (Exception e) {
      Assert.fail("Hardened precise withdraw must succeed: " + e.getMessage());
    } finally {
      dbManager.getExchangeStore().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeStore().delete(ByteArray.fromLong(2L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(2L));
      dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    }
  }
