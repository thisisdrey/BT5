### Title
Downloaded attachment bytes are never verified against the requested `content_hash` before being accepted - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) takes the HTTP response body returned by a peer for an `AttachmentRequest`, decodes it via `decode_atlas_get_attachment()`, and inserts the resulting `Attachment` directly into `self.attachments` with no comparison between the requested `content_hash` and `Hash160::hash(&attachment.content)`. The `DownloadingAttachment` branch of `AttachmentsBatchStateMachine::try_proceed` (`download.rs:641-657`) then transitions straight to `Done(context)` with this unfiltered set.

### Finding Description
The broken equality is: for any successfully decoded response, the code assumes `response.attachment` corresponds to the `content_hash` that was requested, but never asserts `Attachment::hash() == request.content_hash`.

Code path:
- `extend_with_attachments` iterates `results.succeeded`, and for each `(request, response)` pair, if `response.decode_atlas_get_attachment()` succeeds it does `self.attachments.insert(response.attachment)` [1](#0-0) , bumping the peer's reliability report as if the request had succeeded, but performing no content-hash check against `request.content_hash`.
- `try_proceed`'s `DownloadingAttachment` arm calls `context.extend_with_attachments(results)` and immediately moves to `AttachmentsBatchStateMachine::Done(context)` [2](#0-1)  — there is no subsequent filtering pass that re-derives each `Attachment`'s hash and drops entries that don't match the originally-requested `AttachmentInstance.content_hash`.

Since `self.attachments` is a `HashSet<Attachment>`, any peer that is queried as one of the `AttachmentRequest.sources` can return arbitrary bytes for the attachment body; those bytes are accepted as the resolved attachment for that request as long as decoding succeeds, regardless of whether their hash matches the `content_hash` committed to by the confirmed `AttachmentInstance`. This lets a malicious source (or colluding sources, though even a single malicious source suffices given the code as shown) substitute wrong content for a legitimate attachment. This exactly matches the concept of "serving non-canonical state as canonical" via a BNS attachment.

### Impact Explanation
A remote, unprivileged peer that is selected as a download source for an attachment request can cause the node to accept and store/serve attachment bytes that do not correspond to the confirmed `content_hash` from the `AttachmentInstance`. Since attachments back BNS name resolution data, this allows serving forged BNS attachment content as canonical to any node/follower that downloads through this attacker-influenced batch — matching the "attachment/BNS mismatch" High-severity category. The attack is repeatable for any attachment request the attacker's URL is selected to serve.

### Likelihood Explanation
Preconditions: the attacker must operate a peer whose URL is included as one of the `sources` for an `AttachmentRequest`/`AttachmentInstance` (achievable by any remote party gossiping attachment instances/inventories that get incorporated into `AttachmentsBatch`), and must be selected by the source-selection logic when the batch downloads the attachment body. No secrets, admin roles, or privileged slots are required — only running an HTTP endpoint that responds to the attachment GET request with attacker-chosen bytes. This is a low-cost, remotely reachable attack.

### Recommendation
In `extend_with_attachments`, after `response.decode_atlas_get_attachment()` succeeds, recompute `Hash160::hash(&response.attachment.content)` (or call `Attachment::hash()`) and compare it against `request.content_hash`. If they differ, treat the peer response as failed (`report.bump_failed_requests()`), skip insertion into `self.attachments`, and optionally penalize/blacklist the offending source instead of crediting it with a successful request.

### Proof of Concept
Add a test in `stackslib::net::atlas::download::tests` that:
1. Constructs an `AttachmentRequest` with a known `content_hash` H.
2. Simulates a `BatchedRequestsResult<AttachmentRequest>::succeeded` map containing a decoded `GetAttachmentResponse` whose `attachment.content` hashes to `H' != H`.
3. Calls `AttachmentsBatchStateContext::extend_with_attachments(results)`.
4. Asserts that the resulting `context.attachments` set contains an `Attachment` whose `.hash() != H`, demonstrating the state machine accepts and would propagate mismatched content through `AttachmentsBatchStateMachine::Done`.
