### Title
Unvalidated negative `Limit`/`Offset` in `FindCommits` bypasses `--max-count` bound, enabling unbounded `git log` output (DoS) - ([File: internal/gitaly/service/commit/find_commits.go])

### Summary
`FindCommitsRequest.Limit` and `.Offset` are `int32` fields taken directly from the RPC caller and used to build `git log` flags without validating that they are non-negative, unlike sibling RPCs in the same package that explicitly reject negative values.

### Finding Description
`validateFindCommitsRequest` only validates the repository and revision, and does not check `Limit`/`Offset`: [1](#0-0) 

The unvalidated `Limit` is then formatted directly into a `--max-count=%d` git flag, and `Offset` into `--skip=%d`: [2](#0-1) 

This is in contrast to other RPCs in the same service that use the analogous pattern of `Limit`/`Offset` and explicitly guard against negative values, e.g. `TreeEntry` and `ListLastCommitsForTree`: [3](#0-2) [4](#0-3) 

Git's `--max-count` and `--skip` semantics treat negative values specially: `git log --max-count=-1` is interpreted by git as "unlimited" (no cap), since git only applies a limit when the value is `>= 0`. Because `FindCommits` does not reject negative `Limit`, a caller can supply `Limit = -1` (or any negative int32) to strip the intended cap entirely, causing `git log` to walk and emit the full history of the referenced revision(s) regardless of the limit the caller nominally requested. This mirrors the reported bug class of "numeric input cast/used directly without validation," where a crafted extreme/out-of-range value (here, a negative limit) changes program behavior in an unintended and resource-exhausting way.

`Offset` is used with `--skip=%d` when `calculateOffsetManually` is false (the common case, i.e. `Follow` unset or `Offset<=0`): [5](#0-4) 
A negative offset would produce `--skip=-N`, whose behavior is not validated/tested here either.

### Impact Explanation
An unauthenticated but otherwise permitted RPC caller (any client able to invoke `FindCommits`, e.g. via GitLab's Gitaly client during normal repository browsing) can request `Limit = -1` against a large repository to force Gitaly to walk and stream the entire commit history and generate/parse every commit object via `catfile`, consuming CPU, memory, and I/O disproportionate to a legitimate bounded request. This is a resource-consumption / DoS vector on the `FindCommits` RPC handler, consistent with "RPC-handler resource limits" abuse in scope.

### Likelihood Explanation
`FindCommits` is a plain accessor RPC that only requires setting an `int32` field to a negative number in the request; no privileged access, malicious peer, or additional preconditions are needed beyond ordinary access to invoke a read-only Gitaly RPC. The fact that sibling RPCs (`TreeEntry`, `ListLastCommitsForTree`) already added explicit negative-value checks after presumably encountering the same concern suggests this is a known/likely-reachable pattern that was simply missed for `FindCommits`.

### Recommendation
- Add validation in `validateFindCommitsRequest` rejecting `req.GetLimit() < 0` and `req.GetOffset() < 0`, mirroring `TreeEntry`'s and `ListLastCommitsForTree`'s validators, returning `structerr.NewInvalidArgument` for such requests.
- More generally, audit all RPC handlers that interpolate signed integer request fields directly into git flags (`--max-count`, `--skip`, `--depth`, etc.) for the same negative-value/format-string injection-of-semantics pattern.

### Proof of Concept
1. Call `FindCommits` with:
   ```
   FindCommitsRequest{
     Repository: <large_repo>,
     Revision:   []byte("main"),
     Limit:      -1,
   }
   ```
2. Because `validateFindCommitsRequest` does not check `Limit`, the request passes validation.
3. `getLogCommandSubCmd` builds `git log --format=%H --max-count=-1 main`.
4. Git treats `--max-count=-1` as unlimited, so `git log` walks and prints the entire reachable history instead of being capped, and Gitaly streams/parses every commit — consuming significantly more CPU/memory/time than the caller's nominal request should allow.

func validateFindCommitsRequest(ctx context.Context, locator storage.Locator, in *gitalypb.FindCommitsRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision(in.GetRevision(), git.AllowEmptyRevision()); err != nil {
		return err
	}
	return nil
}

	//  We will perform the offset in Go because --follow doesn't play well with --skip.
	//  See: https://gitlab.com/gitlab-org/gitlab-ce/issues/3574#note_3040520

		subCmd.Flags = append(subCmd.Flags, gitcmd.Flag{Name: fmt.Sprintf("--skip=%d", req.GetOffset())})
	}
	limit := req.GetLimit()
	if calculateOffsetManually(req) {
		limit += req.GetOffset()
	}
	subCmd.Flags = append(subCmd.Flags, gitcmd.Flag{Name: fmt.Sprintf("--max-count=%d", limit)})

func validateRequest(ctx context.Context, locator storage.Locator, in *gitalypb.TreeEntryRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision(in.GetRevision()); err != nil {
		return err
	}

	if len(in.GetPath()) == 0 {
		return fmt.Errorf("empty Path")
	}

	if in.GetLimit() < 0 {
		return fmt.Errorf("negative Limit")
	}
	if in.GetMaxSize() < 0 {
		return fmt.Errorf("negative MaxSize")
	}

	return nil
}

func validateListLastCommitsForTreeRequest(ctx context.Context, locator storage.Locator, in *gitalypb.ListLastCommitsForTreeRequest) error {
	if err := locator.ValidateRepository(ctx, in.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision([]byte(in.GetRevision())); err != nil {
		return err
	}
	if in.GetOffset() < 0 {
		return fmt.Errorf("offset negative")
	}
	if in.GetLimit() < 0 {
		return fmt.Errorf("limit negative")
	}
	return nil
}
