### Title
Residual account state (assets, votes, frozen resources) is not cleared when an existing address is converted into a contract via CREATE/CREATE2 - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

### Summary
`Program.createContractImpl()` re-uses an account that already exists at the target address (a normal account or a previously self-destructed contract address) when a new contract is deployed there. Only `DelegatedResource` is explicitly cleared before the account is turned into the new contract; other map-like/list-like fields of `AccountCapsule` (TRC10 `assetV2` map, `votes` list, `frozenV2`/`unfrozenV2` lists, tron power) are left intact and are inherited by the freshly-deployed contract. This mirrors the reported bug class: a struct/account holding mapping-style data is "deleted"/repurposed without clearing every nested item, so unexpected state persists after the entity is effectively "re-added."

### Finding Description
When a contract is created (including via `CREATE2`, which lets an attacker or user predict the deployment address in advance), `createContractImpl` looks up any pre-existing account at that address: [1](#0-0) 

If `existingAccount != null` and it is not already recognized as a live contract (`!contractAlreadyExists`), the code only performs:
```
existingAccount.updateAccountType(AccountType.Contract);
existingAccount.clearDelegatedResource();
```
before writing the account back and treating it as the new contract's storage account. It does **not** clear:
- `assetV2` (the TRC10 token balance map on the account — a genuine key/value mapping, analogous to the Solidity mapping in the report),
- `votes` list (witness votes / TRON Power usage),
- `frozenV2`/`unfrozenV2` lists (FreezeV2 balances and pending unfreeze entries),
- old TRON Power flags (`oldTronPower`).

Because a Tron address can receive TRC10 tokens, be the target of `freeze`/`freezeV2`/`vote` operations, or previously host a self-destructed contract before the corresponding `CREATE2` deployment transaction is actually broadcast, all of this state accumulates on the `AccountCapsule` under that address. When the contract is later deployed there, `createContractImpl` treats the account as freshly created except for delegated resources, so the newly deployed contract inherits TRC10 balances, votes, and frozen resource entries it never legitimately received.

This is directly analogous to the reported issue: an entity is "removed"/"re-added" (self-destruct then redeploy at the same address, or first-use of a pre-funded CREATE2 address) but the underlying mapping-like storage (`assetV2`, `votes`, `frozenV2`) is not exhaustively cleared, only one specific field (`DelegatedResource`) is handled, exactly as the original report describes deleting a struct that contains an un-clearable mapping.

The repository's own test suite acknowledges parts of this class of behavior for `DelegatedResource`/frozen-balance transfer around suicide and CREATE2 (see `FreezeTest.testFreezeAndUnfreezeToCreate2Contract`, `testCreate2SuicideToBlackHole`), but the equivalent handling for `assetV2`, `votes`, and `frozenV2`/`unfrozenV2` in `createContractImpl` is missing: [2](#0-1) 

### Impact Explanation
An account can gain state through ordinary, unprivileged operations (`TransferAssetContract`, `FreezeBalanceV2Contract`, `VoteWitnessContract`) directed at a not-yet-deployed CREATE2 address, or through the residue left after a prior contract at that address self-destructs. When a contract is later deployed at that same address, it silently inherits:
- TRC10 token balances it was never transferred through a validated path (potential unbacked/duplicated balance bookkeeping, since the sender's balance was already debited when the tokens were sent to the pre-existing account),
- Non-zero votes / TRON Power usage that can interfere with `canSuicide`/`canSuicide2` checks, reward computation (`VoteRewardUtil`), and vote-count invariants enforced elsewhere,
- Stale `frozenV2`/`unfrozenV2` entries that affect resource-weight accounting (`updateTotalResourceWeight`) without the new contract ever calling freeze.

This can corrupt global bandwidth/energy/TRON Power weight totals and TRC10 balance accounting, and can be leveraged to make a contract appear to hold assets or voting power it never legitimately acquired.

### Likelihood Explanation
Reachable entirely through unprivileged, ordinary transactions: (1) predict a CREATE2 address using `Program.getCreateEnergy`/`generateContractAddress2` logic exposed to any contract, (2) send TRC10 tokens, freeze resources, or vote to that address using standard `TransferAssetContract`/`FreezeBalanceV2Contract`/`VoteWitnessContract`, (3) deploy the contract at that address via CREATE2. No special privileges, SR/witness role, or trusted party is required — an ordinary contract deployer and asset holder can trigger this path.

### Recommendation
In `Program.createContractImpl`, when reusing a pre-existing, non-contract account for a new deployment, fully reset all account fields that resemble maps/collections before converting it into a contract — not just `DelegatedResource`. This should include clearing `assetV2`, `votes`, `frozenV2`, `unfrozenV2`, and resetting `oldTronPower`, mirroring what `withdrawRewardAndCancelVote`/`transferFrozenV2BalanceToInheritor` already do for the `suicide` path, so no residual mapping-style state survives account repurposing.

### Proof of Concept
1. Deploy a factory contract able to compute a CREATE2 address (`predictedAddr`) for a not-yet-deployed contract, as in `Create2Test`/`FreezeTest.getCreate2Addr`.
2. Before deploying at `predictedAddr`:
   - Send TRC10 tokens to `predictedAddr` via `TransferAssetContract`.
   - Freeze bandwidth/energy to `predictedAddr` via `FreezeBalanceV2Contract` (`freezeForOther`).
   - Optionally vote through `predictedAddr` if it is first created as a normal account with TRON Power.
3. Deploy the contract at `predictedAddr` via `CREATE2` (as done in `FreezeTest.testFreezeAndUnfreezeToCreate2Contract`, `deployCreate2Contract`).
4. Inspect the resulting `AccountCapsule` for `predictedAddr`: `assetV2`, `frozenV2`, and `votes` fields still contain the pre-deployment values, only `DelegatedResource` was cleared, confirming the new contract inherited unvetted state. [3](#0-2)
