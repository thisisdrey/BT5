### Title
`redeem()` Lets a User Send Withdrawn Underlying Back to the Vault Itself, Desyncing the `assets` Accounting Variable From the Real Token Balance - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The vault's `redeem` entrypoint accepts an arbitrary `recipient` principal with no restriction preventing `recipient` from being the vault contract's own address (`current-contract`). When a user redeems shares and sets `recipient = current-contract`, `send-underlying` performs a self-transfer of the underlying asset (funds never actually leave the vault), yet `redeem` unconditionally decrements the internal `assets` accounting variable by the redeemed amount. This is the same root-cause pattern as the referenced report: an operation that is supposed to represent liquidity leaving the pool is redirected back into the pool, but the state update still assumes liquidity left, corrupting the accounting used for share pricing and available-liquidity checks.

### Finding Description
In `mainnet/contracts/vault/v0-vault-stx.clar` (identical pattern repeated in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`):

```
(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  ...
  (try! (ft-burn? zft amount account))
  (try! (send-underlying inkind recipient))
  (var-set assets (- current-assets inkind))
  ...
``` [1](#0-0) 

`send-underlying` is implemented as:
```
(define-private (send-underlying (amt uint) (account principal))
  (begin
    (try! (as-contract? ((with-stx amt))
      (try! (contract-call? .wstx transfer amt tx-sender account none))
      true))
    (ok true)))
``` [2](#0-1) 

If `account` (i.e. `recipient`) equals `current-contract`, this is a self-transfer: the underlying token balance held by the vault (`ubalance`) is unchanged because it moves from the vault back to the vault. However, `redeem` still executes `(var-set assets (- current-assets inkind))`, permanently reducing the vault's internally tracked `assets` variable even though the real underlying balance did not decrease.

Notably, the sibling `transfer` function in the same contract explicitly guards against this exact class of self-referential misuse:
```
(asserts! (not (is-eq current-contract to)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
``` [3](#0-2) 

but no equivalent guard exists on `recipient` in `redeem` (or on `recipient` in `deposit`), confirming the omission is the bug — directly analogous to the reported `StakingPool.sol` issue where the `to == address(this)` case was not checked before updating interest-rate/liquidity accounting.

### Impact Explanation
Once `assets` is decremented without a corresponding real outflow, the vault's internal state permanently understates its true underlying balance relative to `ubalance`/deposits already made. This corrupts:
- `total-assets` / `total-assets-preview`, which drive `convert-to-shares-preview` / `convert-to-assets-preview` — future depositors receive shares priced against an artificially lowered asset base, diluting/skewing value for existing shareholders on their eventual redemption (theft of yield/principal value transferred between users due to broken share math).
- `get-available-assets` and the checks `(asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)` / `ERR-INSUFFICIENT-LIQUIDITY` in `redeem`, which will incorrectly block other legitimate users from withdrawing even though the vault actually holds sufficient real tokens — a temporary freezing of funds for unrelated depositors.

This falls squarely within the in-scope "vault share math and interest accrual" category and produces impact matching "temporary freezing of funds" (blocked redemptions from artificially low recorded `assets`) and potential mispricing-driven value transfer between depositors.

### Likelihood Explanation
The `recipient` parameter of `redeem` is fully attacker-controlled and requires no privileged role — any ordinary depositor holding vault shares can call `redeem` with `recipient` set to the vault's own contract principal in a single, ordinary transaction. No special setup (flashloan, DAO action, oracle manipulation) is required, making this trivially and repeatedly triggerable by any user, intentionally or accidentally, unlike the guarded `transfer` path in the same file.

### Recommendation
Add the same guard already present in `transfer` to `redeem` (and `deposit`'s `recipient`/`account` paths where applicable):
```
(asserts! (not (is-eq current-contract recipient)) ERR-TOKENIZED-VAULT-PRECONDITIONS)
```
placed before `send-underlying` is invoked in `redeem`, mirroring the fix pattern from the referenced report (either reject `recipient == current-contract` outright, or, if self-redemption to the vault is intentionally allowed, skip/adjust the `assets` decrement so it reflects the fact that no real outflow occurred).

### Proof of Concept
1. User deposits `X` underlying into `v0-vault-stx`, receiving `zft` shares; `assets` var = `X`.
2. User calls `redeem(amount, min-out, recipient)` with `recipient` set to the vault's own contract address (`'SP...v0-vault-stx`).
3. `ft-burn?` burns the user's shares. `send-underlying` self-transfers the underlying token from the vault to itself — `ubalance` is unchanged.
4. `(var-set assets (- current-assets inkind))` executes, reducing `assets` by `inkind` even though the real token balance held by the vault did not decrease.
5. Repeating this drains the recorded `assets` toward zero while `ubalance` stays at (or above) `X`, causing subsequent legitimate `redeem` calls from other users to revert with `ERR-INSUFFICIENT-ASSETS`/`ERR-INSUFFICIENT-LIQUIDITY` despite real liquidity being present, and skewing share-price calculations (`convert-to-shares-preview`/`convert-to-assets-preview`) for all future deposits/redemptions.
