### Title
Unchecked boolean return of `reduceAssetAmountV2` in `ExchangeInjectActuator`/`ExchangeTransactionActuator` lets a user drain/mint exchange liquidity without deducting their own asset - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java)

### Summary
The external report flags `BasicIssuanceModule.issue()` for ignoring the boolean return value of `transferFrom()`, letting the caller mint `_setToken` even though the underlying asset transfer silently failed. The equivalent pattern in java-tron is `AccountCapsule.reduceAssetAmountV2(...)`, a method that returns `boolean` to signal whether an account had sufficient asset balance to debit. Some actuators (e.g. `TransferAssetActuator`) correctly check this return value and abort the transaction if debiting fails. `ExchangeInjectActuator` and `ExchangeTransactionActuator`, however, invoke `reduceAssetAmountV2` and discard the result, then proceed to credit the exchange pool / counter-party as if the debit had succeeded.

### Finding Description
`TransferAssetActuator.execute()` demonstrates the correct pattern: it checks the boolean result of the debit operation and throws `ContractExeException("reduceAssetAmount failed !")` if it returns `false`, preventing crediting of the destination before confirming the debit succeeded: [1](#0-0) 

By contrast, `ExchangeInjectActuator.execute()` calls `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, ...)` twice and ignores the returned boolean in both places, then unconditionally updates the exchange pool balances (already computed and applied earlier via `exchangeCapsule.setBalance(...)`) and persists the account: [2](#0-1) 

`ExchangeTransactionActuator.execute()` has the same issue — it calls `accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore)` without checking the result, right after `exchangeCapsule.transaction(...)` has already mutated the exchange's internal token balances: [3](#0-2) 

`validate()` in both actuators calls `accountCapsule.assetBalanceEnoughV2(tokenID, tokenQuant, dynamicStore)` before execution to ensure sufficient balance: [4](#0-3) [5](#0-4) 

This means the immediate, single-transaction exploit (calling execute with insufficient balance so `reduceAssetAmountV2` returns `false`) is normally already blocked by `validate()`. However, I was unable to fully verify within the available tool budget whether `reduceAssetAmountV2` can return `false` for reasons other than insufficient balance (e.g., an asset lookup / precision edge case, or a race where account state changes between `validate()` and `execute()` within block processing, such as multiple contracts in the same transaction or block touching the same account). I could not retrieve the full body of `AccountCapsule.reduceAssetAmountV2` before the response cutoff, so I cannot state with certainty all the internal failure conditions of this method, or whether execute()-time state can diverge from validate()-time state for a `TRX_SYMBOL_BYTES`-typed exchange pair versus an asset-typed pair (since TRX path uses direct `setBalance` arithmetic instead of `reduceAssetAmountV2`, while the asset path relies on the unchecked boolean).

### Impact Explanation
If `reduceAssetAmountV2` returns `false` in `execute()` (for any reason not caught by `validate()`), the actuator still: (1) updates the `ExchangeCapsule`'s first/second token balances via `Commons.putExchangeCapsule(...)`, and (2) commits the account without having actually debited the user's asset. This would let a caller inject or trade against an exchange pool while not paying the tokens they claim to be paying — inflating counterparties' credited balances/exchange liquidity relative to what was actually removed from the caller, i.e., unbacked balance creation, analogous to the reported "mint for free" bug.

### Likelihood Explanation
Likelihood is constrained because `validate()` performs an `assetBalanceEnoughV2` check immediately before `execute()` is invoked in the same actuator pipeline, and the two run against the same account state in typical single-contract-per-transaction processing, so the primary trivial trigger (just not having enough tokens) is already gated. Exploitability would depend on finding a state-mutation path between `validate()` and `execute()` for the same account/asset (or on `reduceAssetAmountV2`/`assetBalanceEnoughV2` disagreeing on some edge case, e.g., precision/decimals handling differences), which I could not confirm from the available code snippets.

### Recommendation
In `ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()`, check the boolean return value of `reduceAssetAmountV2` the same way `TransferAssetActuator` does, and throw a `ContractExeException` (aborting the transaction, which will be rolled back by the surrounding repository/session) if the debit fails, instead of silently proceeding to update the exchange pool and persist the account.

### Proof of Concept
Not reproducible with certainty from the available code: a concrete PoC requires confirming a state divergence between `validate()`-time and `execute()`-time `AccountCapsule` asset balances (e.g., via concurrent/batched actuators touching the same account within a block, or a discrepancy between `assetBalanceEnoughV2` and `reduceAssetAmountV2` semantics) — which I could not verify by inspecting the full `AccountCapsule.reduceAssetAmountV2` implementation within this session's tool budget. This should be investigated further (e.g., by reviewing `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java`) before treating this as a confirmed, directly exploitable bug rather than a defensive-coding gap.
