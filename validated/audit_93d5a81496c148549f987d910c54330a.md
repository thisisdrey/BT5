### Title
Unchecked exchange pool balance subtraction leads to negative/unbacked token balances when hardened math is not enabled - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()` computes new bancor-pool balances by subtracting the computed `buyTokenQuant` from the existing pool balance. Unless the chain-wide `allowHardenExchangeCalculation` proposal flag is enabled, this subtraction is performed with plain Java `long` arithmetic (`secondTokenBalance - buyTokenQuant` / `firstTokenBalance - buyTokenQuant`) with **no check that the result stays non-negative**, mirroring the Ethos `ActivePool` bug where a subtraction assumed an invariant (`sharesToAssets >= currentAllocated`) that is not actually guaranteed on all code paths.

### Finding Description
`ExchangeCapsule.transaction()` selects between a hardened processor (`SafeExchangeProcessor`, which does bounds-checked math and validates the result) and the legacy, unchecked path: [1](#0-0) 

When `hardenedCalc` is `false` (the default state until the `allowHardenExchangeCalculation` proposal is activated by the committee), the new balances are computed as raw `long` subtraction/addition with no `if (newBalance < 0) throw` guard — that guard only executes `if (hardenedCalc && ...)`: [2](#0-1) 

The `subtractExact`/`addExact` helpers on `AbstractExchangeActuator` similarly only apply checked math when the feature flag is on; otherwise they silently perform normal overflow/underflow-prone arithmetic: [3](#0-2) 

This is reachable directly from an unprivileged, signed `ExchangeTransactionContract` (any account can call `TransferAssetContract`-style exchange trades) via `ExchangeTransactionActuator.execute()`, which calls `exchangeCapsule.transaction(...)` and persists the resulting (possibly corrupted) balances without any additional sanity check: [4](#0-3) 

Likewise `ExchangeWithdrawActuator.execute()` performs pool-balance subtraction (`subtractExact(firstTokenBalance, tokenQuant)`/`subtractExact(secondTokenBalance, anotherTokenQuant)`) that, absent hardening, is unchecked plain subtraction: [5](#0-4) 

The analog to the reported Ethos issue is structural: the code was written assuming an invariant (pool balance is always sufficient to satisfy the computed trade/withdrawal) which is not enforced by validation for the legacy/default math path, and there is a parallel "hardened" path added later (evidenced by the `allowHardenExchangeCalculation` flag and the dedicated hardened tests in `ExchangeWithdrawActuatorTest`) confirming the developers recognized and only partially/conditionally remediated this exact class of arithmetic-invariant violation.

### Impact Explanation
Unlike the Ethos report (which causes only a revert/DoS), the java-tron default (non-hardened) path performs the subtraction anyway and stores the corrupted balance. Depending on the exact numeric conditions this can silently drive an exchange pool's `firstTokenBalance`/`secondTokenBalance` negative or wrap, producing balances inconsistent with actual backing assets — i.e., an unbacked balance / accounting corruption in a bancor-style AMM pool that other users (via subsequent trades/withdrawals) can exploit to extract more value than the pool actually holds. This is a Medium/High-severity fund-safety issue reachable by any account issuing an `ExchangeTransactionContract` or `ExchangeWithdrawContract`.

### Likelihood Explanation
The hardened path is gated behind the `allowHardenExchangeCalculation` proposal flag, which (like other `AllowXXX` proposal-controlled flags in `DynamicPropertiesStore`) must be explicitly enabled by committee vote; until/unless enabled on a given network, the legacy unchecked path is always executed for every exchange transaction/withdrawal, so the vulnerable code is on the live, default execution path for any unprivileged exchange transaction.

### Recommendation
Make the bounds/invariant check (`newFirstTokenBalance/newSecondTokenBalance >= 0`, and consistency between recorded pool balances and actual token custody) unconditional rather than gated behind `hardenedCalc`, or retire the legacy unchecked path entirely once `allowHardenExchangeCalculation` has been enabled network-wide, so the vulnerable arithmetic can never execute regardless of proposal state.

### Proof of Concept
Not independently reproduced with a live network due to index limitations on some capsule/store initialization code; the vulnerable path is demonstrated structurally: with `allowHardenExchangeCalculation` unset (default), calling `ExchangeCapsule.transaction()` through `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` with parameters chosen so that `buyTokenQuant`/`anotherTokenQuant` exceeds the corresponding pool balance results in `newFirstTokenBalance`/`newSecondTokenBalance` (or `subtractExact` result) going negative without any exception being thrown or validation performed, as shown by the `hardenedCalc`-gated check at `ExchangeCapsule.java:160-162` and the plain `x - y` fallback at `AbstractExchangeActuator.java:17-19`.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }

    return chainBaseManager.getDynamicPropertiesStore().allowHardenExchangeCalculation();

  public long subtractExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.subtractExact(x, y) : x - y;

  public long addExact(long x, long y) {
    return allowHarden() ? StrictMathWrapper.addExact(x, y) : x + y;
