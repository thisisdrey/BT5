### Title
Exchange Withdraw permanently reverts once either token side reaches zero balance, freezing the creator's remaining liquidity - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawActuator` unconditionally rejects any withdraw request from the bancor-style exchange once either side of the pair (`firstTokenBalance` or `secondTokenBalance`) equals zero, treating the pool as permanently "closed." Because ordinary, unprivileged trades executed through `ExchangeTransactionActuator` can drive one side of the pool to exactly zero (via bancor-formula/integer-division truncation), an exchange creator can be left with a non-zero balance of the other token that can never again be withdrawn through any actuator, since `ExchangeWithdrawActuator` is the sole path back to a normal account balance.

### Finding Description
`ExchangeWithdrawActuator.doValidate()` and `execute()` both check: [1](#0-0) 
which throws `"Token balance in exchange is equal with 0, the exchange has been closed"` whenever either side of the pair is zero, and the same check exists in `execute()`'s corresponding validate helper on the transaction (trade) side: [2](#0-1) 

`ExchangeTransactionActuator` is freely callable by any account holding the traded token, and its bancor-curve math (`BigInteger`/`BigDecimal` multiply-then-divide) can legitimately reduce one side of the pool to exactly zero on a sufficiently large trade, especially with small remaining pool balances, due to integer truncation in the constant-product calculation: [3](#0-2) 

Once either `firstTokenBalance` or `secondTokenBalance` becomes zero, both `ExchangeWithdrawActuator` (the creator's only means of pulling funds out of the pool) and `ExchangeTransactionActuator` will revert for that exchange going forward, because both actuators gate on `firstTokenBalance == 0 || secondTokenBalance == 0`. There is no actuator that permits withdrawing from, or otherwise recovering, a pool whose balance has hit zero on one side — `ExchangeInjectActuator`/`ExchangeCreateActuator` only add liquidity, they do not bypass this check for withdrawal.

This is structurally analogous to the reported `dettachFromManagedNFT`/`_poke` issue: a state transition triggered by any third-party transaction (a trade that zeroes one side, analogous to "gauge killed") causes a completely unrelated, legitimate self-service operation (the pool creator's fund withdrawal, analogous to "detach veNFT") to revert, with no code path to recover once the precondition is violated.

### Impact Explanation
Any remaining balance of the non-zero token side becomes permanently stuck in the exchange contract's virtual balance — it is credited to no account and cannot be withdrawn by the creator through `ExchangeWithdrawActuator`, nor traded out through `ExchangeTransactionActuator`, since both check the same zero-balance condition. This is a permanent freezing of funds, reachable purely through public trading activity (an ordinary, unprivileged `ExchangeTransactionContract` transaction) with no admin or special role required.

### Likelihood Explanation
Reaching exactly zero on one side requires a trade sized so that the resulting integer-division amount computed for the pool is 0, which is plausible for exchanges with small remaining balances (e.g., after most liquidity has already been withdrawn/traded, or pools created with minimal initial balances) or via deliberately crafted trade sizes near the tail of the pool. Because `ExchangeTransactionActuator` is a fully public, unprivileged action, an attacker (or even an ordinary trade) can trigger this state without requiring any elevated privileges, making the likelihood non-trivial for smaller/thinning pools.

### Recommendation
Distinguish between "pool fully depleted and should be permanently closed" and "pool has residual balance on the other side that must remain withdrawable." Allow `ExchangeWithdrawActuator` to proceed for the side that is non-zero even if the counter side has reached zero, or add a dedicated closing/reclaim path that lets the creator withdraw any remaining single-sided balance once the pool is degenerate, instead of unconditionally reverting on `firstTokenBalance == 0 || secondTokenBalance == 0`.

### Proof of Concept
1. Exchange creator issues `ExchangeCreateContract` for `(tokenA, tokenB)` with a small remaining balance after prior partial withdrawals/trades (e.g., `firstTokenBalance = X`, `secondTokenBalance = small_Y`).
2. Any user submits an `ExchangeTransactionContract` trade sized such that the bancor calculation (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`) truncates the resulting `anotherTokenQuant`/updated balance to exactly `0` for one side — validated to be `>0` at trade time, but able to zero out the *other* side's balance in `execute()`.
3. `exchangeCapsule.setBalance(...)` in `ExchangeTransactionActuator.execute()` persists `firstTokenBalance = 0` (or `secondTokenBalance = 0`).
4. Creator now calls `ExchangeWithdrawContract` to recover the remaining non-zero token balance.
5. `ExchangeWithdrawActuator.doValidate()` hits `firstTokenBalance == 0 || secondTokenBalance == 0` and throws `ContractValidateException("Token balance in exchange is equal with 0, the exchange has been closed")`, permanently blocking withdrawal of the remaining tokens. [4](#0-3)
