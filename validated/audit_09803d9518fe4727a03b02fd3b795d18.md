### Title
Unauthenticated peer can forge `AttachmentPage.inventory` bits to make an on-chain-committed attachment appear network-wide unavailable - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_inventories` stores each peer's self-reported `GetAttachmentsInvResponse` (`AttachmentPage.inventory`) verbatim, with no cross-check against any committed/verifiable bitset. `get_prioritized_attachments_requests` builds the candidate `sources` for an `AttachmentRequest` purely from these self-reported bits, so a lying peer that falsely reports `inventory[position_in_page] == 0` (or, if it is the only responder, always reports availability but never actually serves the content) can cause the batch to either skip requesting the attachment entirely or exhaust retries against a peer that never delivers it.

### Finding Description
The equality being relied upon is: *peer-reported inventory bit at `position_in_page` == peer's actual local `find_attachment` result for `content_hash`*. This equality is never verified anywhere in the code path.

- `AttachmentPage { index, inventory: Vec<u8> }` is attacker-controlled wire data returned from `GET /v2/attachments/inv` [1](#0-0) .
- `extend_with_inventories` stores the decoded response per peer with no validation beyond successful decoding [2](#0-1) .
- `get_prioritized_attachments_requests` computes `has_attachment` solely from `response.pages...inventory.get(position_in_page)`, and only includes peers as `sources` when this self-reported bit is `1`; if no peer reports `1`, the whole `content_hash` request is skipped for that round (`sources.is_empty() ... continue`) [3](#0-2) .
- If the sole responding peer(s) collude to report `0` (hiding availability) for a `content_hash` they do not want the requester to fetch, the requester never sends an `AttachmentRequest` for it in that round at all, bypassing any fallback because there is no alternate source of truth (e.g., a signed/committed inventory digest) to compare against.
- Conversely, if peer(s) falsely report `1` while unable to actually serve the attachment, `sources` will point only at those peers; the eventual `GET /v2/attachments/<hash>` will fail to decode or return nothing, `extend_with_attachments` calls `report.bump_failed_requests()` [4](#0-3) , and the batch is re-queued via `bump_retry_count` until `max_attachment_retry_count` is exceeded, at which point the batch is dropped entirely [5](#0-4) .
- There is no reconciliation step that re-queries additional peers outside of the already known peer set, and no cryptographic or majority-vote mechanism to detect that a peer's inventory claim disagrees with reality.

### Impact Explanation
A remote, unprivileged peer that is queried during Atlas inventory sync can, by returning a crafted `GetAttachmentsInvResponse` with a falsified `inventory` byte, cause a genuinely on-chain-committed BNS attachment to be treated as unavailable (stalling resolution) or cause futile repeated requests that exhaust the retry budget and get the batch dropped. This does not corrupt state or serve wrong data as canonical—the requester never accepts unverified attachment content, since actual attachment fetches still go through `find_attachment`/hash-based validation. The effect is availability/resolution stalling for the specific attachment (BNS name resolution DoS), scoped to whichever peers the local node happens to be syncing with. This matches the "attachment/BNS mismatch" / false-inventory steering category described as High in the rubric, but the severity is bounded: it requires that the attacker's peer(s) be selected among the node's inventory-request targets, and it doesn't propagate false data network-wide as canonical, only locally withholds/misdirects requests at the querying node.

### Likelihood Explanation
The precondition is that an attacker-controlled node must be one of the outbound sync peers the victim queries for attachment inventories (`network.get_outbound_sync_peers()` in `AttachmentsDownloader::run`), which is achievable for any remote node that peers with the victim—no privileged role or secret needed. Any single non-colluding honest peer in the peer set that reports the truthful bit will supply a valid source and defeat the attack, so the attacker needs to control or collude with all peers currently selected for that content's inventory page, which lowers likelihood somewhat but is plausible in small/sparse peer sets or via Sybil peers. The attack is cheap and repeatable per attachment batch.

### Recommendation
- Do not treat a single peer's inventory report as authoritative; require corroboration or fall back to directly probing `GET /v2/attachments/<hash>` on peers whose inventory reports zero when no peer reports one, at least periodically.
- Track and penalize (via `ReliabilityReport`) peers whose claimed inventory bit disagrees with the outcome of the subsequent attachment fetch (already partly done via `bump_failed_requests`, but consider also decrementing trust for false-positive claims specifically, and excluding chronically-lying peers from future inventory queries).
- Consider periodically re-querying a wider peer set (not just previously known low-reliability peers) rather than dropping the batch after `max_attachment_retry_count`.

### Proof of Concept
Rust test plan (extending `stackslib/src/net/atlas/tests.rs`):
1. Construct an `AttachmentsBatchStateContext` with a single fake peer entry in `self.peers`.
2. Insert into `self.inventories` a `GetAttachmentsInvResponse` for that peer with `pages: vec![AttachmentPage { index: page_index, inventory: vec![0u8; ...] }]` (falsely reporting absence) for a `content_hash` that is present in `attachments_instances`.
3. Call `get_prioritized_attachments_requests()` and assert the resulting `BinaryHeap` does **not** contain a request for that `content_hash` (i.e., `sources.is_empty()` branch was hit at `download.rs:461-464`), demonstrating the attachment is skipped despite being genuinely resolvable.
4. Alternatively, set the bit to falsely report presence (`inventory[position] = 1`), drive `AttachmentsBatchStateMachine` into `DownloadingAttachment`, mock the HTTP layer so the fake peer's `GET /v2/attachments/<hash>` never returns valid content, and assert `report.bump_failed_requests()` is invoked and the batch is retried/eventually dropped via `bump_retry_count` (`download.rs:188-204`) instead of ever succeeding, even though a legitimately-serving peer could exist outside the queried set.

        results: &mut BatchedRequestsResult<AttachmentsInventoryRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_attachments_inv_response() {
                let peer_url = request.get_url().clone();
                match self.inventories.entry(request.key()) {
                    Entry::Occupied(responses) => {
                        responses.into_mut().insert(peer_url, response);
                    }
                    Entry::Vacant(v) => {
                        let mut responses = HashMap::new();
                        responses.insert(peer_url, response);
                        v.insert(responses);
                    }
                };
                report.bump_successful_requests();

                report.bump_failed_requests();
