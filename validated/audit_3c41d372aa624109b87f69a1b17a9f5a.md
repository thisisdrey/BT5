### Title
Insecure permission chmod on path derived from unsanitized zip entry name in self-executing py_binary bootstrap - ([File: tools/python/python_bootstrap_template.txt])

### Summary
The Python zip self-extraction routine `ExtractZip` in `tools/python/python_bootstrap_template.txt` uses Python's `zipfile.ZipFile.extract()` (which internally sanitizes entry names, stripping drive letters, leading slashes, and `..`/`.` path components) to write files safely inside `dest_dir`, but then independently recomputes the file path for a subsequent `os.chmod()` call directly from the raw, unsanitized `info.filename` via `os.path.abspath(os.path.join(dest_dir, info.filename))`. [1](#0-0) 

### Finding Description
`ExtractZip` iterates the zip's `infolist()` and, per entry, calls `zf.extract(info, dest_dir)` — Python's stdlib `zipfile` module sanitizes `info.filename` before writing so that entries cannot escape `dest_dir` via `../` sequences or absolute/drive paths. However, immediately after, the code independently derives `file_path` by joining `dest_dir` with the **raw, unsanitized** `info.filename` and calling `os.chmod(file_path, attrs & 0o7777)`: [2](#0-1) 

Because the write path (sanitized by `zipfile.extract`) and the chmod path (built from the raw, unsanitized name) are computed independently from the same attacker-controlled `info.filename`, an entry name containing `../` sequences causes the two paths to diverge: the *file contents* land safely inside `dest_dir` (at the sanitized location), while the *permission-setting operation* targets an attacker-chosen path outside `dest_dir`. This is the same bug class as the referenced xxl-job CVE-2024-42681 (CWE-276/277/281): a component of untrusted input (the archive-entry "name", analogous to the "Sub-Task ID") is used, without proper validation, to select the target of a privileged/permission-affecting operation, allowing the attacker to set/preserve permissions on a location it should not control.

The runfiles zip consumed here is built by Bazel's Python rules from the target's runfiles/data, which can include files whose original names originate from externally fetched content (e.g. `http_archive`/`ctx.extract` outputs used as `data` of a `py_binary`). If such a name (or one produced via the archive `rename_files`/entry name path) is carried through into the packaged runfiles zip with a `..`-containing path, then at run time — whenever *any* user executes the resulting self-executing `py_binary` zip on a machine where `%is_zipfile%` is true — `ExtractZip` will `chmod` an attacker-influenced path outside the temporary extraction directory to attacker-controlled permission bits (up to `0o7777`, e.g., world-writable `0666`/`0777` or an executable `0755`) on every invocation.

### Impact Explanation
An attacker who can influence a single filename that ends up embedded in a `py_binary`'s self-extracting zip can force every future execution of that binary to `chmod` an arbitrary filesystem path (relative to the fresh `tempfile.mkdtemp()` extraction directory, i.e., anywhere on the filesystem the executing user can reach via `..` traversal) to attacker-chosen permission bits. This can widen permissions on sensitive files/directories (e.g., making them world-writable) that a subsequent attacker step (or another unprivileged actor with local access) can exploit to escalate privileges or achieve code execution, matching the "Improper Preservation of Permissions...remote attacker execute arbitrary code" pattern of the analog CVE.

### Likelihood Explanation
This requires two conditions to line up: (1) the victim's build pipeline packages a `py_binary` in zip mode (`%is_zipfile%` true) whose runfiles/data include a file path containing attacker-influenced `..` sequences, and (2) the resulting zip is executed by a victim. Reaching condition (1) depends on how upstream archive-extraction and runfiles-symlinking steps sanitize entry/path names before they reach the zip packaging step, which I was not able to fully verify within the available search budget — I could not locate the exact zip-packaging code path (e.g., `zip_main.cc`/singlejar equivalent for py_binary runfiles zips) to confirm whether it re-validates/rejects `..`-containing runfile names before writing them as zip entries. This is a real gap in my investigation: without that confirmation, I cannot be certain the malicious entry name actually survives from an attacker-controlled archive into the final runfiles zip unmodified.

### Recommendation
In `ExtractZip`, compute the path used for `os.chmod` from the same sanitized result that `zipfile.extract()` actually wrote to, rather than re-deriving it from the raw `info.filename`. Concretely, capture the return value of `zf.extract(info, dest_dir)` (which returns the actual path written) and use that for the subsequent `chmod`/`abspath` normalization, and additionally verify (e.g., via `os.path.commonpath`) that the resulting path is contained within `dest_dir` before calling `os.chmod`.

### Proof of Concept
I was unable to construct and verify a concrete, runnable JUnit/`BuildIntegrationTestCase`/shell-test proof within the available tool budget, since doing so requires confirming (a) that a runfiles/data file name containing `../` sequences can survive unmodified from an `http_archive` extraction through Bazel's runfiles-to-zip packaging step into `info.filename` in the final py_binary zip, and (b) exercising `ExtractZip` at runtime to observe the chmod divergence. This would need to be validated with actual command/tool execution (building a `py_binary` zip with a crafted data file and inspecting the resulting zip's entry names and the chmod calls at extraction time), which is outside what I can do in this read-only/ask-only investigation.

def ExtractZip(zip_path, dest_dir):
  """Extracts the contents of a zip file, preserving the unix file mode bits.

  These include the permission bits, and in particular, the executable bit.

  Ideally the zipfile module should set these bits, but it doesn't. See:
  https://bugs.python.org/issue15795.

  Args:
      zip_path: The path to the zip file to extract
      dest_dir: The path to the destination directory
  """
  zip_path = GetWindowsPathWithUNCPrefix(zip_path)
  dest_dir = GetWindowsPathWithUNCPrefix(dest_dir)
  with zipfile.ZipFile(zip_path) as zf:
    for info in zf.infolist():
      zf.extract(info, dest_dir)
      # UNC-prefixed paths must be absolute/normalized. See
      # https://docs.microsoft.com/en-us/windows/desktop/fileio/naming-a-file#maximum-path-length-limitation
      file_path = os.path.abspath(os.path.join(dest_dir, info.filename))
      # The Unix st_mode bits (see "man 7 inode") are stored in the upper 16
      # bits of external_attr. Of those, we set the lower 12 bits, which are the
      # file mode bits (since the file type bits can't be set by chmod anyway).
      attrs = info.external_attr >> 16
      if attrs != 0:  # Rumor has it these can be 0 for zips created on Windows.
        os.chmod(file_path, attrs & 0o7777)
