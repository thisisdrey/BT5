### Title
Unvalidated attacker-controlled offset causes Out-Of-Bounds array access in `PrecompiledContracts.ValidateMultiSign`/`BatchValidateSign` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.ValidateMultiSign.execute()` parses the raw calldata of a `CALL` into the `validateMultiSign`/`batchValidateSign` precompile address into a `DataWord[]` array and then indexes into that array using an **offset value taken directly from the calldata itself**, without first checking that the offset (or even the fixed head positions 0-3) is within the bounds of the parsed array. This mirrors the CVE-2025-38599 bug class (an unvalidated index used to access an array, causing OOB access) but here the "index" is derived from fully attacker-controlled TVM calldata.

### Finding Description
In `execute()`: [1](#0-0) 

```java
public Pair<Boolean, byte[]> execute(byte[] rawData) {
  if (VMConfig.allowTvmOsaka()
      && !isValidAbiEncoding(rawData, ABI_HEADER_WORDS, ABI_ITEM_WORDS)) {
    return Pair.of(false, EMPTY_BYTE_ARRAY);
  }
  DataWord[] words = DataWord.parseArray(rawData);
  byte[] address = words[0].toTronAddress();
  int permissionId = words[1].intValueSafe();
  byte[] data = words[2].getData();
  ...
  if (VMConfig.allowTvmSelfdestructRestriction()) {
    int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
    ...
  }
  byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
      extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
      extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```

`words[3]` is a raw 32-byte field fully controlled by the caller's calldata; it is used both directly (as an array index at `words[0..3]`) and as a divisor-scaled offset (`words[3].intValueSafe() / WORD_SIZE`) used to index further into `words[]`. Neither `words.length` nor the derived offset is bounds-checked before the array access. The one guard that exists, `isValidAbiEncoding(...)`, is only applied `if (VMConfig.allowTvmOsaka())` — i.e. it is gated behind a hard-fork feature flag and is skipped entirely when that flag is inactive.

Confirmation that this is a real, previously-observed defect class (not speculative) comes from the regression test explicitly written for the fix: [2](#0-1) 

The test comment states: "a CALL to validateMultiSign or batchValidateSign with malformed calldata must (a) push 0 onto the outer stack, (b) leave the outer frame free of any propagated exception, and (c) allow the outer frame to continue executing afterwards" — confirming that malformed/short calldata previously could throw an exception that propagated out of the precompile call and corrupted/terminated the calling (outer) execution frame. This is functionally the java-tron analog of the OOB `link_id` indexing bug in `mt7996_tx()`.

The narrow try/catch that exists in the method only wraps the signature-recovery loop, starting well after the unguarded array accesses: [3](#0-2) 

So `words[0]`, `words[1]`, `words[2]`, `words[3]`, and the offset-derived `words[words[3].intValueSafe()/WORD_SIZE]` accesses are **not** protected by that catch block at all.

### Impact Explanation
Any TVM contract (deployable by any unprivileged account) can `CALL` into the `ValidateMultiSign`/`BatchValidateSign` precompiled address with calldata shorter than the expected head size, or with a crafted offset word (`words[3]`) pointing past the end of the parsed `words[]` array. When `VMConfig.allowTvmOsaka()` is not yet active on the network, no `isValidAbiEncoding` guard runs, and the resulting `ArrayIndexOutOfBoundsException` is thrown outside of any local try/catch in `execute()`. Depending on how far up the call stack (`Program.callToPrecompiledAddress` / opcode dispatch in `VM.java`) the exception is caught, this can corrupt the calling contract's execution frame, produce incorrect VM/energy accounting, or — in the worst case — propagate up through transaction/block processing, causing a deterministic crash for any node that processes the transaction (since all validating nodes execute the same TVM code on the same input, this is consensus-critical and could cause a chain halt/split if only some nodes have `allowTvmOsaka` active).

### Likelihood Explanation
High reachability: any account can deploy a trivial contract that performs a low-level `CALL`/`staticcall` to the fixed precompile address with attacker-chosen calldata (no special permissions, funds only need to cover minimal energy). The trigger condition (short calldata or an out-of-range offset word) is trivial to construct. The mitigating `isValidAbiEncoding` check is conditioned on the `allowTvmOsaka` hard-fork flag, so exploitability directly depends on whether that flag is active on the target network/height.

### Recommendation
- Validate `words.length` against the number of head words required (`ABI_HEADER_WORDS`/`ABI_ITEM_WORDS`) **unconditionally**, not only when `allowTvmOsaka()` is enabled.
- Bounds-check the derived offset (`words[3].intValueSafe() / WORD_SIZE`) against `words.length` before using it to index into the array, in both the `sigArraySize` computation and in `extractSigArray`/`extractBytesArray`.
- Wrap the entire body of `execute()` (not just the signature-loop) in exception handling that returns `Pair.of(true, DATA_FALSE)` (or equivalent safe failure) for any malformed input, ensuring the outer TVM frame is never able to inherit a propagated runtime exception, matching the intent of the TIP-854 fix but without depending on a feature-flag gate.

### Proof of Concept
1. Deploy a simple contract with a function that performs `staticcall`/`call` to the `ValidateMultiSign` precompiled address (`0x0000000000000000000000000000000000000066` equivalent in TRON's precompile numbering) with calldata shorter than 4 words (128 bytes), or with a well-formed 4th word (`words[3]`) whose value, once divided by `WORD_SIZE`, exceeds `words.length`.
2. Trigger the contract via a normal `TriggerSmartContract` transaction broadcast by any account.
3. On a node where `VMConfig.allowTvmOsaka()` is not active, `DataWord.parseArray(rawData)` returns an array shorter than the index used, and the subsequent `words[...]` access throws `ArrayIndexOutOfBoundsException` outside of any local catch in `execute()`, propagating into the calling TVM frame — reproducing exactly the scenario the `testTip854OuterFrameContainment` regression test was written to prevent.
