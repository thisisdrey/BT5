## Finding

### Title
Shielded-transaction private key material (spending key / ask / nsk) accepted via plain-text HTTP GET query parameters, exposing secrets in logs and browser history - (File: framework/src/main/java/org/tron/core/services/http/GetAkFromAskServlet.java)

### Summary
Several `wallet/get*` HTTP endpoints that back the shielded-transaction ("Zcash-style") API accept raw private key material — spending keys (`sk`), expanded spending key components (`ask`, `nsk`), and viewing key components (`ak`, `nk`) — as plain `GET` query-string parameters, and echo values derived directly from them back in the JSON response.

### Finding Description
`GetAkFromAskServlet.doGet` reads the `ask` (spending authority key) straight from `request.getParameter("value")` and forwards it to `wallet.getAkFromAsk(...)` [1](#0-0) . The same pattern is used by `GetExpandedSpendingKeyServlet.doGet` for the spending key [2](#0-1) , and by `GetIncomingViewingKeyServlet.doGet` for `ak`/`nk` [3](#0-2) . All of these forward into `Wallet` methods such as `getAkFromAsk`, `getExpandedSpendingKey`, and `getNkFromNsk`, which only guard the call with `checkAllowShieldedTransactionApi()` before operating directly on the caller-supplied secret bytes [4](#0-3) .

Because these are `GET` requests, the private key hex strings are placed in the URL query string. URL query parameters are routinely persisted in web-server/proxy access logs, browser history, OS process lists, and can leak to third parties via the `Referer` header if the response is rendered in a browser context — the exact class of exposure described in the reference Jenkins advisory (secret material rendered/transmitted in a way reachable by anyone who can observe the browser's traffic or history). The project's own config file explicitly documents this exact risk for the shielded API ("Some shielded transaction APIs require sending private keys as parameters... may leak your private keys") [5](#0-4) , yet the vulnerable code paths accept the secrets via `GET` (not `POST`-only), which is the worst-case transport for this kind of parameter.

### Impact Explanation
If `node.allowShieldedTransactionApi` is enabled (required for any legitimate wallet usage of shielded transfers) [6](#0-5) , any client (local software, a browser-based wallet UI, or a proxy in front of the node) that calls these `GET` endpoints will have the raw shielded spending/viewing key material embedded in the URL. This is captured by default in access logs, browser history/cache, and can be exposed through `Referer` leakage — disclosure of `ask`/`nsk`/`sk` is equivalent to disclosure of the shielded account's full spending authority, enabling theft of shielded funds by anyone with access to those logs/history.

### Likelihood Explanation
Any unprivileged client that can reach the node's HTTP API and knows the URL scheme (`/wallet/getakfromask`, `/wallet/getexpandedspendingkey`, `/wallet/getincomingviewingkey`, etc., as exercised in `HttpMethed.getAkFromAsk` / `getExpandedSpendingKey` / `getIncomingViewingKey`) can trigger this by supplying secret key bytes as the `value`/`ask`/`nsk` GET parameter [7](#0-6) . No authentication beyond the `allowShieldedTransactionApi` opt-in flag is required, and the vulnerability is triggered simply by the existence of `doGet` handlers that accept secret material as query parameters — this is a design/implementation flaw, not something requiring a privileged attacker.

### Recommendation
Remove or reject the `doGet` handling for all shielded-key-derivation servlets that accept private key material (`GetAkFromAskServlet`, `GetExpandedSpendingKeyServlet`, `GetNkFromNskServlet`, `GetIncomingViewingKeyServlet`, `GetSpendingKeyServlet`'s equivalents, etc.), forcing clients to use `POST` with a request body only, and update `HttpMethed`/client SDKs and documentation accordingly. Additionally, ensure access logs do not record full query strings for the `wallet` HTTP API, or bind these endpoints to loopback-only by default, consistent with the existing warning about `allowShieldedTransactionApi`.

### Proof of Concept
1. Enable `node.allowShieldedTransactionApi = true` on a FullNode.
2. Issue: `GET http://<node>:8090/wallet/getakfromask?value=<64-char-hex-ask>` — the secret `ask` value is now present in the URL and will appear in any HTTP access log, proxy log, or browser history that observes the request [1](#0-0) .
3. Repeat with `GET /wallet/getexpandedspendingkey?value=<64-char-hex-sk>` to leak the full spending key material through the same channel [2](#0-1) .

    checkAllowShieldedTransactionApi();

    byte[] sk = SpendingKey.random().getValue();
    return BytesMessage.newBuilder().setValue(ByteString.copyFrom(sk)).build();
  }

  public ExpandedSpendingKeyMessage getExpandedSpendingKey(ByteString spendingKey)
      throws BadItemException, ZksnarkException {
    checkAllowShieldedTransactionApi();

    if (Objects.isNull(spendingKey)) {
      throw new BadItemException("spendingKey is null");
    }

    if (ByteArray.toHexString(spendingKey.toByteArray()).length() != 64) {
      throw new BadItemException("the length of spendingKey's hexString should be 64");
    }

    ExpandedSpendingKey expandedSpendingKey = null;
    SpendingKey sk = new SpendingKey(spendingKey.toByteArray());
    expandedSpendingKey = sk.expandedSpendingKey();

    ExpandedSpendingKeyMessage.Builder responseBuild = ExpandedSpendingKeyMessage
        .newBuilder();
    responseBuild.setAsk(ByteString.copyFrom(expandedSpendingKey.getAsk()))
        .setNsk(ByteString.copyFrom(expandedSpendingKey.getNsk()))
        .setOvk(ByteString.copyFrom(expandedSpendingKey.getOvk()));

    return responseBuild.build();

  }

  public BytesMessage getAkFromAsk(ByteString ask) throws
      BadItemException, ZksnarkException {
    checkAllowShieldedTransactionApi();

    if (Objects.isNull(ask)) {
      throw new BadItemException("ask is null");
    }

    if (ByteArray.toHexString(ask.toByteArray()).length() != 64) {
      throw new BadItemException("the length of ask's hexString should be 64");
    }

    byte[] ak = ExpandedSpendingKey.getAkFromAsk(ask.toByteArray());
    return BytesMessage.newBuilder().setValue(ByteString.copyFrom(ak)).build();
  }
