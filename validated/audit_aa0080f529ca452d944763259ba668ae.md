### Title
Uncapped Nakamoto block signer-signature recovery lets peer-pushed blocks with a bloated signature vector waste unbounded ECDSA-recovery compute before rejection - ([File: stackslib/src/chainstate/nakamoto/mod.rs])

### Summary
`NakamotoBlockHeader::verify_signer_signatures` iterates over the header's entire `signer_signature: Vec<MessageSignature>` and performs a full secp256k1 public-key recovery (`recover_to_pubkey_without_validating_low_s`) on *every* entry before it ever checks whether the accumulated signing weight meets the acceptance threshold. The number of entries in `signer_signature` is bounded only by the generic wire/message-size limits applied during block deserialization, not by the number of signers actually present in the reward set for that block. A peer can push a block whose signature vector is padded with cheap, unsignable/garbage 65-byte entries, forcing the receiving node to perform a large number of expensive recovery operations before the block is finally rejected — the same "cheap-to-produce, expensive-to-verify, unbounded-by-count-cap" pattern described in the Zcash advisory (uncapped Halo2 proof verification per pushed transaction), just applied to ECDSA recovery on pushed Nakamoto blocks instead of zk-proof verification on pushed transactions.

### Finding Description
`verify_signer_signatures` builds a `signers_by_pk` map from the reward set and then loops over `self.signer_signature.iter()`, calling `Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s` on each signature unconditionally: [1](#0-0) 

Only *after* recovery does the code check whether the recovered public key belongs to a known signer, and only at the very end of the loop is the accumulated weight compared against the threshold: [2](#0-1) 

There is no early exit once the threshold is met, and no cap tying `signer_signature.len()` to the actual size of the reward set (`signers.len()`), so an attacker can pad the vector with any number of syntactically valid but non-recoverable-to-a-real-signer 65-byte blobs, each of which still costs a full EC point recovery before being discarded.

This function is invoked directly on data received from an unauthenticated peer, before the block is otherwise known-good:
- From the P2P push path, on every block in a `NakamotoBlocksData` message pushed by a neighbor: [3](#0-2) 
- From the unsolicited-block-buffering path (`check_nakamoto_block_signer_signature` / `is_nakamoto_block_bufferable`), which runs whenever an unsolicited `NakamotoBlocksData` arrives, before the block is stored or forwarded to the chain-processing pipeline: [4](#0-3) [5](#0-4) 

The only throttle on this path is a byte-per-second bandwidth NACK, which counts raw bytes pushed by a peer, not the number of expensive-to-verify signature slots contained in those bytes: [6](#0-5) 

Because the bandwidth cap operates on wire-byte throughput and the signature-recovery cost is what's actually expensive (not the byte count itself), an attacker can maximize the ratio of "wasted CPU work" to "bytes sent" by filling a block's `signer_signature` field with the maximum number of small, garbage 65-byte entries the wire-size limit allows, exactly mirroring the Zcash finding's root cause: a per-byte/per-message cap that does not track the actual unit of expensive verification work (there, Halo2 proofs; here, ECDSA recoveries).

### Impact Explanation
This is a bounded compute DoS on the P2P block-ingestion path: any connected, unauthenticated peer can push (or repeatedly re-push, subject only to bandwidth throttling) Nakamoto blocks whose signature vectors are stuffed with garbage signatures, forcing the victim node to burn CPU cycles on wasted `secp256k1` recoveries for each such block before rejecting it. Sustained from multiple connections/peers, this degrades the node's ability to process legitimate blocks/relayed data promptly, similar in class to the Zcash "block verification stall" — though the underlying primitive (ECDSA recovery) is much cheaper per-operation than a Halo2 proof, so the practical severity depends on how large a `signer_signature` vector the wire format allows per block.

### Likelihood Explanation
Reachable by any peer with a normal P2P connection; no authentication, special role, or node secret is required — matching the "remote, unprivileged" criterion. The attacker only needs to construct a Nakamoto block payload with a bloated `signer_signature` field; producing garbage 65-byte blobs is essentially free, while the victim pays full EC-recovery cost per entry.

### Recommendation
- Bound `signer_signature.len()` at or before deserialization time to the maximum plausible number of signers (i.e., the reward set size, or a fixed protocol maximum), rejecting oversized vectors before any cryptographic recovery is attempted.
- In `verify_signer_signatures`, short-circuit as soon as `total_weight_signed >= threshold`, and abort recovery early once the number of remaining possible signatures cannot change the outcome.
- Consider charging per-peer cost accounting for expensive verification primitives (ECDSA recoveries per unit time), not just raw push bandwidth, mirroring the ZIP-317-style pre-verification cost gate used to fix the Zcash advisory.

### Proof of Concept
1. Establish a normal P2P connection to a victim node as an unauthenticated peer.
2. Construct a `NakamotoBlocksData` message containing a block whose header has a `signer_signature` vector padded up to the maximum allowed by the wire/message-size limit with distinct, non-recoverable-to-any-real-signer 65-byte `MessageSignature` values (any well-formed recovery-id byte so `recover_to_pubkey_without_validating_low_s` doesn't fail-fast on the encoding itself).
3. Push this block repeatedly, staying under `max_nakamoto_block_push_bandwidth` (bytes/sec) so the byte-based NACK throttle in `validate_nakamoto_block_push` never triggers.
4. Observe the victim node performing a full secp256k1 recovery for every entry in the padded vector on each push (via `check_nakamoto_block_signer_signature` → `verify_signer_signatures`), before finally rejecting the block for insufficient/invalid signer weight, consuming CPU disproportionate to the bytes sent and the attacker's cost to produce them.
