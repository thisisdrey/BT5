### Title
Client-controlled `git_object_directory`/`git_alternate_object_directories` Repository fields bypass storage boundary checks and are joined unvalidated into Git's object-search environment - ([File: internal/git/gitcmd/command_factory.go])

### Summary
The `Repository` proto message exposes two attacker/client-settable fields, `git_object_directory` and `git_alternate_object_directories` [1](#0-0) . Every git command that Gitaly spawns for a repository takes these raw fields and turns them into `GIT_OBJECT_DIRECTORY` / `GIT_ALTERNATE_OBJECT_DIRECTORIES` environment variables via `alternates.Env(repoPath, repo.GetGitObjectDirectory(), repo.GetGitAlternateObjectDirectories())` [2](#0-1) . Unlike the analogous, carefully-guarded `ObjectDirectoryPath` helper that validates the object directory stays within the storage root or a legitimate quarantine directory [3](#0-2) , `alternates.Env` performs **no** boundary validation at all — it simply does `filepath.Join(repoPath, dir)` for each supplied directory [4](#0-3) . This mirrors the Sablier bug class exactly: a value that is supposed to represent a trusted/fixed resource (here, "the repository's own object directory") is instead fully caller-supplied, and downstream code trusts it to behave (stay inside the repo) without verifying that assumption.

### Finding Description
`filepath.Join` does not sanitize `..` segments against a boundary — it only lexically cleans the path. A caller who controls the `Repository` message for a request (this field exists on essentially every RPC that carries a `Repository`) can set `git_alternate_object_directories` to a value such as `"../../other-namespace/other-repo.git/objects"` or any other path reachable from the storage root. `command_factory.newCommand` builds this into `GIT_ALTERNATE_OBJECT_DIRECTORIES` for the spawned `git` process without ever calling `storage.ValidateRelativePath` or `ValidateGitDirectory` — the exact checks Gitaly already uses elsewhere for the very same class of value (compare `ObjectDirectoryPath`'s explicit "Ensure the path points somewhere in the storage" check [5](#0-4)  and the quarantine-boundary logic that follows it). Because git resolves objects by consulting every directory in `GIT_ALTERNATE_OBJECT_DIRECTORIES`, this lets the git process transparently read loose objects/packfiles from any other repository or directory under the storage root (or anywhere reachable via traversal), independent of Gitaly's own repository-scoped access checks.

This is the same root-cause pattern as the report: a parameter that is conceptually meant to be a single trusted value (WETH / "the object directory") is fully attacker-chosen, and the calling code (`_approve`/`createParams.totalAmount` in Sablier; `alternates.Env`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` in Gitaly) assumes the value will behave benignly instead of validating it.

### Impact Explanation
An attacker able to influence the `Repository` message of a request (a "crafted RPC field") can make Gitaly's git subprocess search for objects outside the intended repository's object store. This can result in cross-repository object disclosure — e.g. causing `git cat-file`, `git log`, or similar commands run against the attacker's own (nominally scoped) repository to resolve and return blob/commit content belonging to a different repository that the attacker should not have access to, defeating Gitaly's per-repository storage isolation.

### Likelihood Explanation
The `git_object_directory`/`git_alternate_object_directories` fields are plain string fields on the widely-used `Repository` message with no server-side validation analogous to `storage.ValidateRelativePath`/`ValidateGitDirectory` at the point they are consumed in `command_factory.go`. Any caller capable of setting arbitrary values in these fields on a `Repository` passed to an RPC reaches this unguarded code path, since essentially every git-spawning RPC funnels through `newCommand`.

### Recommendation
Validate `repo.GetGitObjectDirectory()` and each entry of `repo.GetGitAlternateObjectDirectories()` against the storage root before joining them into environment variables, reusing the existing `storage.ValidateRelativePath` (and, where relevant, the quarantine-prefix logic already implemented in `internal/git/localrepo/paths.go`'s `ObjectDirectoryPath`), and reject the request if the resolved path escapes the storage root.

### Proof of Concept
1. Issue any Gitaly RPC that accepts a `Repository` for a legitimate, attacker-owned repository (e.g. `TreeEntry`, `FindCommit`, etc.).
2. Set `git_alternate_object_directories` to a relative path that traverses out of the repository, e.g. `"../../victim-namespace/victim-repo.git/objects"`.
3. Gitaly calls `newCommand`, which builds `GIT_ALTERNATE_OBJECT_DIRECTORIES=<repoPath>/../../victim-namespace/victim-repo.git/objects` via `alternates.Env` with no boundary check [6](#0-5) .
4. The spawned git process can now resolve and return objects that physically reside in the victim repository's object store, disclosing content across repository boundaries.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
