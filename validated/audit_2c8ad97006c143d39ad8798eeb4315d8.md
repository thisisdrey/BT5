### Title
Reward emissions accruing while a tracked token has zero supply are permanently stranded in `RewardsDistributor` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenIndex` advances the emission timestamp even when a tracked `DepositToken`/`DebtToken` has `totalSupply == 0`. During zero-supply periods, `speed * deltaTime` worth of `rewardToken` is conceptually emitted but attributed to nobody, and the contract has no sweep/recovery function, so those reward tokens remain locked in the contract forever — the direct analog of emissions being locked in a "null epoch" vault.

### Finding Description
In `_calculateTokenIndex` (contracts/RewardsDistributor.sol:197-212), when `block.timestamp` has advanced and `tokenSpeeds[token_] > 0`, the code computes `_tokensAccrued = _deltaTimestamps * _speed` but sets `_ratio = 0` when `token_.totalSupply() == 0`. Crucially, `_newTimestamp = block.timestamp` is still stored via `_updateTokenIndex` (lines 271-281), so the elapsed emission period is consumed without any account accruing the corresponding rewards.

Anyone can force this timestamp update through the permissionless `updateBeforeMintOrBurn(IERC20,address)` entry point (lines 175-180), which is also called automatically by `DepositToken`/`DebtToken` on every mint/burn via `updateRewardsBeforeMintOrBurn` (contracts/DepositToken.sol:124-130, contracts/DebtToken.sol:114-120). No holder can ever claim the emissions generated during the zero-supply window: `claimRewards` only pays out `tokensAccruedOf[account_]`, which is only increased via `_calculateTokenDelta` from index deltas (lines 217-231, 261-265), and `_transferRewardIfEnoughTokens` only transfers what has been accrued to a specific account (lines 248-256).

Unlike `DepositToken`/`DebtToken`/`NativeTokenGateway`/`VesperGateway`, which inherit `TokenHolder.sweep` for stuck-token recovery (contracts/utils/TokenHolder.sol:37-45), `RewardsDistributor` inherits only `Manageable` and has no sweep or treasury-return function, so the unallocated reward balance has no legitimate exit path short of a contract upgrade.

The zero-supply-with-nonzero-speed condition is realistic under the deployed configuration: `syncTokenSpeed` (lines 333-348) sets a deposit token's speed as `rewardRate * vPool.balanceOf(treasury) / vPool.totalSupply()`, which depends on the Treasury's Vesper position — not the `DepositToken`'s `totalSupply`. The Treasury keeps earning Vesper rewards even if all Metronome users have withdrawn, so `tokenSpeeds[depositToken]` stays positive while `depositToken.totalSupply() == 0`, and every second streamed is burned into the contract's balance rather than accruing to anyone.

### Impact Explanation
Reward tokens emitted during zero-supply periods are permanently locked in `RewardsDistributor`. The intended recipients (suppliers/borrowers who later hold the tracked token) can never receive them — if a new depositor mints later, `_accountIndex` is initialized at the current `INITIAL_INDEX`-based index and only future deltas accrue (lines 225-230). This is permanent freezing of yield the protocol intended to distribute, matching the referenced "emissionsToken remains in the contract" bug class. The loss equals `speed * (zero-supply duration)` per tracked token, up to the distributor's whole reward balance over time.

### Likelihood Explanation
The condition requires only that a tracked token's `totalSupply` be 0 while `tokenSpeeds[token_] > 0`. This occurs whenever (a) a deposit/debt token is registered with emissions before its first deposit, or (b) the last holder fully withdraws/repays while `syncTokenSpeed` still reports a positive rate due to the Treasury's residual Vesper position. An unprivileged user can force situation (b) simply by being the last withdrawer, and any subsequent public `updateBeforeMintOrBurn` call (or any user activity on the token contracts) commits the loss. No privileged action is needed to trigger the burn; only the initial speed configuration is governor/keeper-set, which is the normal deployed state.

### Recommendation
Do not advance the emission timestamp when `totalSupply == 0`, so emissions are deferred to periods with eligible holders:

```solidity
// contracts/RewardsDistributor.sol, _calculateTokenIndex
if (_deltaTimestamps > 0 && _speed > 0) {
    uint256 _totalSupply = token_.totalSupply();
    if (_totalSupply == 0) {
        // Keep timestamp unchanged so emissions resume when supply returns,
        // or pause accrual without consuming the period.
        return (0, 0);
    }
    uint256 _tokensAccrued = _deltaTimestamps * _speed;
    uint256 _ratio = _tokensAccrued.wadDiv(_totalSupply);
    _newIndex = (_supplyState.index + _ratio).toUint224();
    _newTimestamp = block.timestamp.toUint32();
}
```

Alternatively/additionally, add a governor-only `sweep`-style function (e.g., inherit `TokenHolder` with `_requireCanSweep` restricted to governor) that can return undistributed `rewardToken` balance — i.e., `balanceOf(this) - sum(tokensAccruedOf)` — to treasury when a token's supply is zero.

### Proof of Concept
Hardhat sketch (repo uses Hardhat + smock, see test/RewardDistributor.test.ts):

```ts
it('strands emissions accrued while totalSupply is zero', async () => {
  // Setup: rewardDistributor funded with VSP, depositToken registered,
  // governor sets speed > 0 while depositToken.totalSupply() == 0
  await rewardDistributor.connect(governor).updateTokenSpeed(depositToken.address, parseEther('1'))

  // No deposits exist: depositToken.totalSupply() == 0
  expect(await depositToken.totalSupply()).to.eq(0)

  // Anyone (or a mint/burn hook) advances the index over a zero-supply window
  await increaseTimeOfNextBlock(3600)
  await rewardDistributor.updateBeforeMintOrBurn(depositToken.address, alice.address)

  const { timestamp } = await rewardDistributor.tokenStates(depositToken.address)
  expect(timestamp).to.be.gt(0) // emission period was consumed

  // A depositor arrives later — gets nothing for the elapsed window
  await depositToken.mint(alice.address, parseEther('100')) // via pool deposit
  await increaseTimeOfNextBlock(60)
  const claimable = await rewardDistributor['claimable(address)'](alice.address)
  // claimable only covers ~60s, not the 3600s zero-supply window
  // 3600 * speed worth of rewardToken is permanently stuck:
  // no function can transfer it out of RewardsDistributor
})
```

Note: PoC validation requires executing tests in a session; the logic above follows directly from `_calculateTokenIndex` (lines 201-211), `_updateTokenIndex` (lines 271-281), and the absence of any sweep path in the contract's inheritance (lines 39-48).
