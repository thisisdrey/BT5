## Analog Identified: Blind trust in ERC20 return value without balance verification in `ERC20Transactor`

### Title
Unverified ERC20 transfer amount accounting allows unbacked credit/mint via fee-on-transfer or non-conserving tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
The external report's core broken invariant is: code assumes a token contract behaves like an idealized, fully-conformant token (implements the exact expected interface/semantics) without verifying that assumption, and the escrow contract's accounting proceeds on that unchecked assumption. The local analog is `ERC20Transactor`, the XCM `TransactAsset` implementation used to bridge arbitrary ERC20 contracts (matched via `assets_common::ERC20Matcher`) into the XCM asset model on Asset Hub. It assumes any matched ERC20 contract's `transfer` moves *exactly* `amount` tokens whenever it returns `true`, and credits/debits the XCM `AssetsInHolding` register with that nominal `amount` without ever checking the token's actual `balanceOf` delta.

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the transactor calls `IERC20::transferCall` to move `amount` from the user to `TransfersCheckingAccount`, and as soon as the call doesn't revert and the ABI-decoded return value is `true`, it unconditionally mints an `AssetsInHolding` credit for the full requested `amount`: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` calls `transfer` from the checking account to the beneficiary for `amount` and, again, only inspects the boolean return value: [3](#0-2) 

Nowhere does the transactor read `balanceOf(TransfersCheckingAccount)` before and after the call to confirm that `amount` tokens actually moved. This mirrors exactly the ERC777 report's root cause: the code assumes a token implements standard, value-conserving `transfer` semantics purely because it matches the `IERC20` ABI and returns `true`, when in reality any contract can be registered as an "ERC20" asset via `ERC20Matcher` (matching is by address/interface shape, not by verified conformance) — including fee-on-transfer, deflationary/burn-on-transfer, or rebasing tokens that return `true` while transferring less than `amount`.

Because the checking account's role is to back the credited `amount` 1:1, any gap between "amount nominally credited to XCM holding" and "amount actually held by `TransfersCheckingAccount`" is a real accounting break. That credited `AssetsInHolding` value is not a local artifact — it can be consumed by subsequent XCM instructions in the same program, notably `DepositReserveAsset`/`InitiateReserveWithdraw` to a remote chain (e.g. Asset Hub acting as reserve for this ERC20), which mints a wrapped/foreign-asset representation on the remote chain based on the nominal amount, not the real received balance.

### Impact Explanation
This falls squarely under the "theft or unbacked mint" impact category: an attacker can register or simply use an existing fee-on-transfer/rebasing/deflationary ERC20 contract as a matched XCM asset, `WithdrawAsset` a nominal `amount`, and have the executor credit the full `amount` into holding even though the checking account received strictly less. That credit can then be forwarded via `DepositReserveAsset`/`InitiateReserveWithdraw` to mint a same-valued wrapped asset on a remote chain, permanently unbacking the reserve — real ERC20 balance in `TransfersCheckingAccount` is less than the total nominal liability represented by minted wrapped tokens elsewhere. This is a public-entrypoint (XCM `execute`/message processing), unprivileged-attacker path with no reliance on a malicious validator, relayer, or admin.

### Likelihood Explanation
Likelihood is contingent on such non-conforming ERC20 tokens being matched and usable as an asset by `ERC20Matcher`/`ERC20Transactor` in a live runtime configuration (currently wired into `asset-hub-westend` per `cumulus/parachains/runtimes/assets/asset-hub-westend/src/xcm_config.rs`). Any user can deploy an arbitrary contract satisfying the `IERC20` ABI shape via `pallet-revive`, then use it as the asset in an XCM program — no privileged action is required, matching the "unprivileged attacker" and "public entrypoint" requirements. [4](#0-3) 

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `balanceOf` of the checking/beneficiary account before and after the `transfer` call and credit/debit `AssetsInHolding` based on the observed balance delta rather than the nominal requested `amount`; reject (fail the instruction) if the delta doesn't match `amount` exactly, so fee-on-transfer/rebasing tokens cannot create a mismatch between real token custody and virtual XCM-accounted value.

### Proof of Concept
1. Deploy a `pallet-revive` contract implementing `IERC20` whose `transfer(to, value)` burns 50% of `value` and forwards only 50% to `to`, but still returns `true`.
2. Register/reference this contract's address as the asset id (matched by `ERC20Matcher`) in an XCM program executed via `pallet_xcm::execute` (or a routed message) containing `WithdrawAsset(<this token>, amount)` followed by `DepositReserveAsset`/`InitiateReserveWithdraw` to a remote chain acting as reserve consumer.
3. Observe that `withdraw_asset_with_surplus` credits `AssetsInHolding` with the full `amount` (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs:195-203`) even though `TransfersCheckingAccount`'s real balance only increased by `amount/2`.
4. The remote chain mints a wrapped asset worth `amount`, while only `amount/2` in real tokens back it in `TransfersCheckingAccount` — an unbacked mint of `amount/2`.
