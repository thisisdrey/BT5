Audit Report

## Title
Unbacked reward liabilities in `pallet-bridge-relayers`: `RelayerRewards` can accumulate claims that exceed the balance of the corresponding `PayRewardFromAccount` pot, permanently locking relayer rewards - (File: `bridges/modules/relayers/src/lib.rs`, `bridges/primitives/relayers/src/lib.rs`)

## Summary
`register_relayer_reward` increments a `RelayerRewards` double-map entry purely as bookkeeping, with no check against the balance of the sub-account (`PayRewardFromAccount::rewards_account`) that will later have to pay it out. `pay_reward` performs a full-amount `fungible::Mutate::transfer` from that sub-account and fails outright (reverting the whole extrinsic, including the pending storage removal) if the balance is insufficient, rather than paying a partial amount.

## Finding Description
`register_relayer_reward` only mutates `RelayerRewards<T, I>`, unconditionally accumulating the registered amount without reading or reserving against the balance of the `rewards_account` derived via `PayRewardFromAccount::rewards_account(params)`. [1](#0-0) [2](#0-1) 

This is invoked from `DeliveryConfirmationPaymentsAdapter::pay_reward` / `register_relayers_rewards` for every message-delivery/confirmation transaction, computing `messages * delivery_fee` per relayer with no reference to the current balance of the target `RewardsAccountParams` sub-account. [3](#0-2) 

When claimed, `PayRewardFromAccount::pay_reward` performs a plain `T::transfer` of the *full* registered amount with `Preservation::Expendable`; there is no `min(balance, reward)` fallback, so any shortfall in the sub-account causes the transfer — and therefore the whole `claim_rewards`/`claim_rewards_to` dispatchable — to fail. [4](#0-3) 

The pallet's own unit test confirms exactly this mechanic: minting a fixed balance into `in_lane0_rewards_account`/`out_lane1_rewards_account` and paying out against it, with no aggregate accounting tying registered rewards to the pot's balance. [5](#0-4) 

The Snowbridge-specific reward-registration path (`process_delivery_receipt`) reuses the same `RewardLedger`/`register_reward` mechanism, and the bridge-hub-westend integration test explicitly demonstrates `claim_rewards`/`claim_rewards_to` returning `Error::FailedToPayReward` when the backing account cannot cover the registered reward. [6](#0-5) [7](#0-6) 

No invariant anywhere enforces `sum(RelayerRewards for a reward_kind) <= balance(rewards_account(reward_kind))`; the pot is funded independently (e.g., via delivery-fee crediting, test/benchmark minting, or governance deposits) while the liability side grows purely from permissionless relayer activity.

## Impact Explanation
Relaying (submitting valid message-delivery/confirmation transactions) is a permissionless, unprivileged action available to any external account. If the aggregate registered `RelayerRewards` for a given `RewardsAccountParams` pot exceeds the actual balance sitting in that sub-account — which is plausible given the pot is funded independently of, and asynchronously from, the liability side — some relayers with legitimately accrued rewards will get `FailedToPayReward` on every claim attempt as long as the shortfall persists, i.e., a locked-fund condition matching the "permanent user-fund... lock" impact category.

## Likelihood Explanation
This requires no malicious relayer, validator, or governance action — only enough organic relaying activity that the sum of registered rewards for one pot outpaces the funds actually deposited into that pot's sub-account. No code path caps registration by pot balance, and the failure mode is deterministic once the shortfall condition occurs.

## Recommendation
- Track outstanding liability per `RewardsAccountParams`/`Reward` and refuse/queue new registrations once they would exceed the corresponding `rewards_account` balance, or
- Change `PayRewardFromAccount::pay_reward` to pay `min(pot_balance, reward)` and retain the shortfall as still-owed instead of reverting the full claim, and
- Add a CI/test invariant asserting `sum(RelayerRewards) <= balance(rewards_account)` per pot.

## Proof of Concept
1. Fund a lane's `rewards_account` with a fixed balance (as in `pay_reward_from_account_actually_pays_reward`/`bridge_rewards_works` tests).
2. Have multiple relayers submit valid delivery/confirmation transactions so `register_relayer_reward`/`register_relayers_rewards` accumulate `RelayerRewards` beyond the pot's balance.
3. First relayer calls `claim_rewards`, draining the pot.
4. A second relayer with a non-zero `RelayerRewards` entry calls `claim_rewards`; `PayRewardFromAccount::pay_reward`'s `T::transfer` fails, and `claim_rewards` reverts with `Error::FailedToPayReward`, as reproduced by the existing bridge-hub-westend test at `bridges/modules/relayers/src/payment_adapter.rs` (L179-225) and `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/tests/tests.rs` (L768-795), leaving that relayer's reward permanently stuck until the pot is independently replenished.

```rust
fn register_relayers_rewards<
	T: Config<RI> + pallet_bridge_messages::Config<MI>,
	RI: 'static,
	MI: 'static,
>(
	confirmation_relayer: &T::AccountId,
	relayers_rewards: RelayersRewards<T::AccountId>,
	lane_id: RewardsAccountParams<LaneIdOf<T, MI>>,
	delivery_fee: T::RewardBalance,
) where
	<T as Config<RI>>::Reward: From<RewardsAccountParams<LaneIdOf<T, MI>>>,
{
	// reward every relayer except `confirmation_relayer`
	let mut confirmation_relayer_reward = T::RewardBalance::zero();
	for (relayer, messages) in relayers_rewards {
		// sane runtime configurations guarantee that the number of messages will be below
		// `u32::MAX`
		let relayer_reward =
			T::RewardBalance::saturated_from(messages).saturating_mul(delivery_fee);

		if relayer != *confirmation_relayer {
			Pallet::<T, RI>::register_relayer_reward(lane_id.into(), &relayer, relayer_reward);
		} else {
			confirmation_relayer_reward =
				confirmation_relayer_reward.saturating_add(relayer_reward);
		}
	}

	// finally - pay reward to confirmation relayer
	Pallet::<T, RI>::register_relayer_reward(
		lane_id.into(),
		confirmation_relayer,
		confirmation_relayer_reward,
	);
}
```

**File:** bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs (L445-480)
```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
