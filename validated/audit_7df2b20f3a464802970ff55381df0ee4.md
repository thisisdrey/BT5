Unauthenticated `/shutdown` request to signer event-receiver terminates event ingestion (DoS) - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` handles the `/shutdown` HTTP path by unconditionally setting `stop_signal` to `true` and returning `EventError::Terminated`, with no authentication, secret, or peer-origin check. Any TCP client able to reach the signer's event-receiver listening port can send a raw `POST /shutdown HTTP/1.1` request and permanently halt `SignerEventReceiver::main_loop`, stopping the signer from processing further StackerDB/burn-block/block-validation events.

### Finding Description
The equality assumed by the code is: "any request landing on the `/shutdown` route == a legitimate internal shutdown signal from the node's own `SignerStopSignaler`." This is false — the handler in `next_event` performs no verification of the caller's identity:

```rust
} else if request.url() == "/shutdown" {
    event_receiver.stop_signal.store(true, Ordering::SeqCst);
    Err(EventError::Terminated)
}
``` [1](#0-0) 

This is reached via `next_event`'s dispatch logic in `EventReceiver::next_event` after `http_server.recv()` — no method check beyond generic POST, no `Content-Length`/body validation, no shared secret, no source-IP allowlist: [2](#0-1) 

The only intended caller is `SignerStopSignaler::send`, which connects back to `self.local_addr` and issues exactly this same unauthenticated `POST /shutdown` request: [3](#0-2) 

Since the wire protocol for the legitimate stop signal is indistinguishable from what any outside TCP client could send, any client capable of opening a TCP connection to the bound address/port and writing that HTTP request achieves the same effect. Once `stop_signal` becomes `true`, `is_stopped()` returns `true`, and `main_loop` breaks out and stops processing events permanently: [4](#0-3) [5](#0-4) 

### Impact Explanation
A single crafted TCP message permanently stops the signer's event-receiver main loop, meaning the signer process will no longer ingest `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` events pushed by the node's event observer. This is an unauthenticated, single-message DoS against a signer process — critical because it silences a signer's participation in block validation/signing without requiring any secret, StackerDB slot ownership, or privileged role, and is trivially repeatable against any signer whose event-receiver port is reachable.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only TCP reachability to the signer's event-receiver bind address/port (this is the address the node's event observer is configured to POST to; whether it is bound to a loopback-only or externally reachable interface is an operator/deployment configuration choice, e.g. `endpoint` in the signer config). No RPC secret, peer key, StackerDB slot, or any privileged credential is required — the attacker just opens a raw `TcpStream` and writes one HTTP request. If the port is reachable at all (e.g. bound to `0.0.0.0` in common non-loopback deployment setups), the attack is trivial, cheap, and repeatable.

### Recommendation
Require the caller (the local node's event dispatcher) to be authenticated when hitting `/shutdown` — e.g., restrict the listener to loopback-only regardless of config, and/or require a shared secret/token in the shutdown request that only `SignerStopSignaler`/the node knows, validated before flipping `stop_signal`. Alternatively, use a purely in-process/local IPC mechanism (e.g. a Unix domain socket or an in-memory channel) for the stop signal instead of an unauthenticated HTTP endpoint reachable over the network.
