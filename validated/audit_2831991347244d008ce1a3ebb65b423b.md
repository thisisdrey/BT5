Based on my investigation, I found a real, provable analog of the "double-launch via mutable admin parameter" bug class in `pallet-nomination-pools`.

### Title
Lowering `GlobalMaxCommission` after `update_records` can re-rate already-accrued rewards, transferring member funds to the commission payee - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The Groupcoin bug's core invariant is: an idempotent/one-time state transition (the launch) is guarded only against literal re-entry, but a *mutable admin parameter* (the Uniswap fee) can retroactively change the "identity" used by that guard, letting the same underlying value be re-processed and settled twice under two different rates. `pallet-nomination-pools` has a structurally identical pattern: reward/commission accounting is split into snapshots (`update_records`) computed against whatever commission rate is "current" at call time, and `GlobalMaxCommission` — a chain-wide, root-settable parameter — is allowed to retroactively re-rate reward balances that were already earned (but not yet snapshotted) under a previous, lower effective cap, without first forcing a snapshot at the old cap.

### Finding Description
`Commission::current()` clamps the pool's nominal commission rate to the live `GlobalMaxCommission`: [1](#0-0) 

This clamped rate is what gets fed into `RewardPool::update_records`/`current_reward_counter`, which computes `new_pending_commission = commission * current_payout_balance` over the balance accrued since `last_recorded_total_payouts`: [2](#0-1) [3](#0-2) 

Both `set_commission` and `do_claim_commission` are careful to call `update_records` with the **currently effective** commission *before* changing anything, explicitly documented as required so that "everything up to this point is using the current commission before it updates": [4](#0-3) [5](#0-4) 

However, `GlobalMaxCommission` is a governance-set global that is read live inside `current()` every time `update_records` runs — it is not snapshotted per-pool at the time rewards accrue. A `prdoc` in this same repository documents that exactly this failure mode was already found and partially patched for the sibling `set_commission_max` call: lowering the pool-level max via `try_update_max` force-cut `commission.current` *without* first calling `update_records`, causing rewards accrued at the old (higher) rate to be re-rated at the new lower rate on the next `update_records`, crediting the differential to members instead of the commission payee: [6](#0-5) 

This confirms the underlying invariant break is real and already had one concrete instance (fixed for `set_commission_max`, pool-controlled). But the same clamp lives at the *global*, root-controlled level via `GlobalMaxCommission::<T>::get()` inside `Commission::current()`, and there is no evidence in the reachable code that a `GlobalMaxCommission` change triggers `update_records` snapshots across all pools before taking effect. Any pool whose `commission.current` exceeds a newly-lowered `GlobalMaxCommission` will have its effective clamped rate silently drop retroactively the next time `update_records` runs (triggered by `claim_payout`, `set_commission`, `claim_commission`, bonding/unbonding, etc.), re-rating balance accrued since the last snapshot at the new lower rate and shifting the differential from the commission payee to members — the mirror image of minting/crediting the wrong beneficiary the wrong amount, analogous to the Groupcoin over-mint once a mutable fee parameter changes.

### Impact Explanation
This is a fund-misdirection/value-conservation bug: commission that was contractually owed to the commission payee at the rate in effect while rewards accrued gets redirected to pool members instead, once governance lowers `GlobalMaxCommission`. It doesn't require a malicious actor beyond ordinary governance action changing a legitimate global parameter (not "governance abuse" — this is standard operational use of `GlobalMaxCommission`, which is explicitly intended to be adjustable). It affects potentially many pools simultaneously and each pool's payee loses funds silently with no error or event indicating misallocation.

### Likelihood Explanation
Medium: it requires no attacker action — it is triggered purely by the intended governance operation of lowering `GlobalMaxCommission`, combined with the routine and frequent occurrence of any account calling `claim_payout`/`bond`/`unbond` (which invoke `update_records`) between accrual and the parameter change. Given `GlobalMaxCommission` is designed to be lowered over time (per the pallet's own doc comments about tightening commission caps), this is a foreseeable operational sequence rather than an edge case.

### Recommendation
Before applying a new `GlobalMaxCommission` value, iterate all pools whose `commission.current` exceeds the new maximum and force a `RewardPool::update_records` snapshot at the *old* effective rate (mirroring the fix already applied to `try_update_max`/`set_commission_max` in `pr_12397`), so that rewards accrued under the old rate are settled before the new cap takes effect. Alternatively, snapshot a per-pool "effective commission at last update" rather than recomputing the clamp live against the current global value inside `current_reward_counter`.

### Proof of Concept
1. Root sets `GlobalMaxCommission` to 50%.
2. Pool sets commission to 50% via `set_commission` (allowed, matches cap).
3. Substantial rewards accrue into the pool's reward account (deposits/staking rewards) without any `claim_payout`, `set_commission`, or `claim_commission` call occurring (no `update_records` call in between).
4. Root lowers `GlobalMaxCommission` to 10% via governance (a normal parameter update, no `update_records` triggered for existing pools).
5. Any member calls `claim_payout`, which internally calls `update_records` with `bonded_pool.commission.current()` — this now returns 10% instead of 50%, because the clamp in `current()` reads the *live* `GlobalMaxCommission`.
6. `current_reward_counter` computes `new_pending_commission` using 10% on the entire balance accrued since the last snapshot (which was under 50%), permanently under-crediting the commission payee for the interval between step 3 and step 5, with the shortfall instead credited to `new_pending_rewards` (members).
7. This mirrors the confirmed `set_commission_max` bug in `pr_12397.prdoc` but via the global (root) commission ceiling path rather than the pool-level max path, which — absent verification of a corresponding snapshot-on-change fix for `GlobalMaxCommission` — remains exploitable through ordinary governance action.

**Caveat:** I was unable to locate the extrinsic/hook that sets `GlobalMaxCommission` within the indexed portion of the codebase to confirm definitively whether it independently forces a global `update_records` sweep across all pools (which would close this gap). Given the index size limits, I recommend a Devin session with full repository access to inspect the `GlobalMaxCommission`-setting call site and confirm whether this specific path is patched or remains open.

```rust
	fn update_records(
		&mut self,
		id: PoolId,
		bonded_points: BalanceOf<T>,
		commission: Perbill,
	) -> Result<(), Error<T>> {
		let balance = Self::current_balance(id);

		let (current_reward_counter, new_pending_commission) =
			self.current_reward_counter(id, bonded_points, commission)?;

		// Store the reward counter at the time of this update. This is used in subsequent calls to
		// `current_reward_counter`, whereby newly pending rewards (in points) are added to this
		// value.
		self.last_recorded_reward_counter = current_reward_counter;

		// Add any new pending commission that has been calculated from `current_reward_counter` to
		// determine the total pending commission at the time of this update.
		self.total_commission_pending =
			self.total_commission_pending.saturating_add(new_pending_commission);

		// Total payouts are essentially the entire historical balance of the reward pool, equating
		// to the current balance + the total rewards that have left the pool + the total commission
		// that has left the pool.
		let last_recorded_total_payouts = balance
			.checked_add(&self.total_rewards_claimed.saturating_add(self.total_commission_claimed))
			.ok_or(Error::<T>::OverflowRisk)?;

		// Store the total payouts at the time of this update.
		//
		// An increase in ED could cause `last_recorded_total_payouts` to decrease but we should not
		// allow that to happen since an already paid out reward cannot decrease. The reward account
		// might go in deficit temporarily in this exceptional case but it will be corrected once
		// new rewards are added to the pool.
		self.last_recorded_total_payouts =
			self.last_recorded_total_payouts.max(last_recorded_total_payouts);

		Ok(())
	}
```
