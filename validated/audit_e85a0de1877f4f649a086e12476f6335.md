### Title
JSON Property Injection via Unescaped Exception Messages in `JsonFormat.printErrorMsg` - (File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java)

### Summary
`JsonFormat.printErrorMsg` builds the HTTP API's JSON error body by raw string concatenation of `ex.getMessage()` with no escaping of `"`, `\`, or control characters. Several actuators build `ContractValidateException` messages by concatenating attacker-controlled, unvalidated contract fields (e.g. asset name) directly into the message text. When such a transaction is validated through the Wallet HTTP API, the resulting error JSON can be broken out of and additional sibling JSON keys can be injected into the response body — the same "structured-text-built-by-raw-concatenation" bug class as the Vikunja CalDAV `SUMMARY:` injection.

### Finding Description
`printErrorMsg` at [1](#0-0)  constructs the error JSON like this:
```java
text.append("{");
text.append("\"Error\":");
text.append("\"");
text.append(ex.getMessage());
text.append("\"");
text.append("}");
```
No RFC 8259 escaping is applied to `ex.getMessage()`, unlike the rest of `JsonFormat`, which has a dedicated, thoroughly-tested `escapeText`/`escapeBytesSelfType` path for exactly this class of bug (see the extensive `JsonFormatEscapeTest` suite at [2](#0-1)  and `escapeText` at [3](#0-2) ). That escaping path only protects the transaction-object serialization path (`printTransactionToJSON`/`printToString`); `printErrorMsg` was not brought under the same protection.

Several actuators build `ContractValidateException` messages by directly concatenating attacker-controlled protobuf string/bytes fields with no character-class restriction. For example, `ParticipateAssetIssueActuator.validate()` has the asset-name-format check commented out:
```java
//    if (!TransactionUtil.validAssetName(assetName)) {
//      throw new ContractValidateException("Invalid assetName");
//    }
...
throw new ContractValidateException("No asset named " + ByteArray.toStr(assetName));
``` [4](#0-3) 

`ByteArray.toStr(assetName)` decodes the raw, attacker-supplied bytes of `ParticipateAssetIssueContract.asset_name` as-is — any byte sequence including `"`, `\`, `,`, `{`, `}` is preserved verbatim. Any unprivileged API client can submit a `ParticipateAssetIssueContract` (via `/wallet/createtransaction`-style validate paths, `estimateenergy`, or during actuator validation reached from HTTP servlets that funnel exceptions through `Util.processError` → `JsonFormat.printErrorMsg`, e.g. the many servlets shown at [5](#0-4) ) with an `asset_name` such as:
```
X"},"ret":"SUCCESS","txID":"deadbeef  <-- payload
```
causing the emitted JSON to look like:
```json
{"Error":"No asset named X"},"ret":"SUCCESS","txID":"deadbeef"}
```
This breaks the intended single-key JSON object and injects extra sibling keys into the parsed response, exactly analogous to how the Vikunja CRLF payload in a task title broke out of the `SUMMARY:` iCalendar property and injected sibling `ATTACH:`/`X-INJECTED:` properties.

### Impact Explanation
Automated consumers of the java-tron HTTP API (exchange back-ends, custodial wallets, bridges, monitoring bots) that parse JSON responses for fields like `result`, `code`, `txID`, or `Error` to decide whether to credit a deposit, release a withdrawal, or mark a transaction as confirmed can be fed an attacker-crafted asset name that forges those sibling fields inside what is nominally an error response. A downstream system that naively checks `"result":true`/`"txID":...` without also checking HTTP status or top-level structure could be tricked into treating a failed/invalid asset-participation transaction as successful, leading to unauthorized crediting or release of funds — matching the "unauthorized account operation / theft" impact bar. This is a Medium-severity API-response integrity issue, consistent with the CVSS 3.1 Medium rating of the original CalDAV analog (network-reachable, no privilege required to submit the crafted contract, but requires a vulnerable downstream JSON consumer to realize impact).

### Likelihood Explanation
The `asset_name` validation (`TransactionUtil.validAssetName`) that would normally restrict characters is explicitly commented out in `ParticipateAssetIssueActuator.validate()`, so any anonymous API caller can supply arbitrary bytes in this field with a single crafted transaction — no special privileges, signing key compromise, or multi-step setup required. The only precondition is that the transaction reaches `validate()` and throws with the attacker string embedded, which happens on every "no such asset" validation failure — a trivially reproducible, single-request condition.

### Recommendation
Apply the existing `JsonFormat.escapeText` (or equivalent RFC 8259 escaping) to `ex.getMessage()` inside `printErrorMsg` before embedding it in the JSON literal, exactly like the protection already applied to protobuf `STRING`/`BYTES` fields in `printFieldValue` ( [6](#0-5) ). Additionally, re-enable and enforce `TransactionUtil.validAssetName(assetName)` in `ParticipateAssetIssueActuator.validate()` (and audit other actuators that concatenate raw user-controlled bytes into exception messages, e.g. `TransferAssetActuator`, `UnfreezeAssetActuator`) so unvalidated byte strings never reach message-building code in the first place.

### Proof of Concept
1. Craft a `ParticipateAssetIssueContract` with `asset_name` bytes set to:
   `58 22 7d 2c 22 74 78 49 44 22 3a 22 66 61 6b 65 22 7d` (i.e. the UTF-8 string `X"},"txID":"fake"}`).
2. Submit the contract for validation through any HTTP endpoint that funnels the resulting `ContractValidateException` to `Util.processError`/`JsonFormat.printErrorMsg` (validation fails because the referenced asset does not exist, hitting `ParticipateAssetIssueActuator.java:168`).
3. Observe the HTTP response body:
   ```json
   {"Error":"No asset named X"},"txID":"fake"}
   ```
   The response now contains an injected top-level `"txID"` key that was never produced by the node, which a naively-parsing automated client could misinterpret.

  static String escapeText(String input) {
    StringBuilder builder = new StringBuilder(input.length());
    CharacterIterator iter = new StringCharacterIterator(input);
    for (char c = iter.first(); c != CharacterIterator.DONE; c = iter.next()) {
      switch (c) {
        case '\b':
          builder.append("\\b");
          break;
        case '\f':
          builder.append("\\f");
          break;
        case '\n':
          builder.append("\\n");
          break;
        case '\r':
          builder.append("\\r");
          break;
        case '\t':
          builder.append("\\t");
          break;
        case '\\':
          builder.append("\\\\");
          break;
        case '"':
          builder.append("\\\"");
          break;
        default:
          // Check for other control characters
          if (c >= 0x0000 && c <= 0x001F) {
            appendEscapedUnicode(builder, c);
          } else if (Character.isHighSurrogate(c)) {
            // Encode the surrogate pair using 2 six-character sequence (\\uXXXX\\uXXXX)
            appendEscapedUnicode(builder, c);
            c = iter.next();
            if (c == CharacterIterator.DONE) {
              throw new IllegalArgumentException(
                  "invalid unicode string: unexpected high surrogate pair value "
                      + "without corresponding low value.");
            }
            appendEscapedUnicode(builder, c);
          } else {
            // Anything else can be printed as-is
            builder.append(c);
          }
          break;
      }
    }
    return builder.toString();
  }
