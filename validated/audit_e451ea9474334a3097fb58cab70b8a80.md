### Title
Per-IP connection rate limiter keys on full `IpAddr` with no IPv6 subnet aggregation, allowing trivial evasion via egress address rotation - ([File: streamer/src/nonblocking/connection_rate_limiter.rs])

### Summary
`ConnectionRateLimiter` keys its `KeyedRateLimiter<IpAddr>` token buckets on the raw `IpAddr` returned by `incoming.remote_address().ip()`, with no normalization to an IPv6 /64 (or any) prefix. An attacker who owns a single IPv6 /64 allocation (a standard consumer/cloud allocation) can open one QUIC connection per distinct source address and get a brand-new, full token bucket every time, since `TokenBucket::new(limit_per_minute, max_burst, ...)` is instantiated fresh per key.

### Finding Description
`ConnectionRateLimiter::register_connection`/`is_allowed` operate on `self.limiter.consume_tokens(*ip, 1)` / `self.limiter.current_tokens(ip)` where `ip: &IpAddr` [1](#0-0) . The `KeyedRateLimiter<IpAddr>` creates a new `TokenBucket` on first access to any key it hasn't seen, cloned from the prototype bucket built with `limit_per_minute`/`max_burst` [2](#0-1) , and `KeyedRateLimiter` itself has no concept of IP-prefix grouping — it is generic over any `Hash + Eq` key and stores one bucket per exact key in a `DashMap<K, TokenBucket>` [3](#0-2) . Nowhere in `streamer/src/nonblocking/quic.rs` or `connection_rate_limiter.rs` is the source address truncated/canonicalized to an IPv6 prefix (e.g., /64) before being used as the rate-limiter key — a search of the streamer sources found no `/64`, `Ipv6Addr`, `subnet`, or `prefix` handling in this path.

In `run_server`, the call sequence is: global `overall_connection_rate_limiter.current_tokens()` check → `rate_limiter.is_allowed(&incoming.remote_address().ip())` → QUIC handshake → `rate_limiter.register_connection(&from.ip())` → `overall_connection_rate_limiter.consume_tokens(1)` [4](#0-3) . Because `is_allowed`/`register_connection` are keyed on the exact `IpAddr`, an attacker rotating through unique addresses within one /64 allocation never accumulates state against a shared bucket: each new address starts with a full `max_burst` allowance. The only surviving control is the single shared `overall_connection_rate_limiter` (`TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST`) — a global token bucket shared by every unstaked client — so the attacker's per-IP limiter is fully evaded while the attacker can still consume as much of that shared unstaked budget as their address-churn rate and the global cap allow, at the expense of every other legitimate unstaked sender contending for the same bucket.

### Impact Explanation
This is a QoS/anti-DoS evasion: the per-IP connection rate limit — the mechanism intended to bound a single network identity's share of unstaked connection admission — provides zero protection against an attacker with routine IPv6 subnet access. The attacker can monopolize a disproportionate share of `overall_connection_rate_limiter`'s `TOTAL_CONNECTIONS_PER_SECOND` budget (the last remaining backstop), starving other unstaked senders of connection slots and effectively degrading unstaked transaction ingress/availability for legitimate low-stake or new participants. This matches Agave's "QoS evasion" bounty category rather than any correctness/consensus break.

### Likelihood Explanation
Highly feasible and repeatable: IPv6 /64 delegations (over 10^19 unique addresses) are the default allocation size from virtually every ISP and most cloud/VPS providers, requiring no special privilege, staking, or leaked keys — only a routine consumer/cloud network setup. The attack requires no server-side vulnerability beyond the existing exact-key design; it is a pure identity-churn evasion executable by any unstaked, unauthenticated remote client capable of binding QUIC connections from multiple source addresses in the same /64.

### Recommendation
Rate-limit unstaked/unauthenticated IPv6 connections by network prefix (e.g., /64, matching common allocation granularity) rather than by exact address: derive a canonicalized key (`IpAddr` for IPv4, truncated `Ipv6Addr` prefix for IPv6) before calling `is_allowed`/`register_connection`, so that `KeyedRateLimiter` buckets are shared across all addresses in an attacker-controlled subnet. Alternatively/additionally, tighten and independently track the shared `overall_connection_rate_limiter` contribution per prefix so a single subnet cannot dominate the unstaked-connection budget.

### Proof of Concept
Rust unit test in `streamer/src/nonblocking/connection_rate_limiter.rs` extending the existing `test_connection_rate_limiter` test:

```rust
#[tokio::test]
async fn test_ipv6_subnet_evades_per_ip_limit() {
    // limit_per_minute = 3, max_burst = 3
    let limiter = ConnectionRateLimiter::new(3, 3, 4);
    let base: u128 = 0x2001_0db8_0000_0001_0000_0000_0000_0000; // fixed /64 prefix, varying host bits
    let mut accepted = 0usize;
    for i in 0..10_000u128 {
        let ip = IpAddr::V6(Ipv6Addr::from(base + i)); // same /64, distinct address each time
        if limiter.is_allowed(&ip) {
            assert!(limiter.register_connection(&ip));
            accepted += 1;
        }
    }
    // Expected under a correctly-scoped per-source limiter: accepted should be
    // bounded by max_burst (3) for the whole /64 subnet.
    // Actual observed behavior: accepted == 10_000, because every distinct
    // IpAddr gets a fresh TokenBucket.
    assert_eq!(
        accepted, 10_000,
        "demonstrates that per-address rate limiting is fully evaded by IPv6 address churn within a single /64"
    );
}
```

This test demonstrates that the invariant "per-source connection limits enforced per source and cannot be evaded by spoofed/churned identity" does not hold for `ConnectionRateLimiter` against an attacker who churns addresses within a single IPv6 /64 block.

    /// underlying DashMap. This uses a LazyLRU style eviction policy, so actual memory consumption
    /// will be <= 2 * target_capacity.

    /// shard_amount must be greater than 0 and be a power of two; otherwise this function panics.

    #[allow(clippy::arithmetic_side_effects)]
    pub fn new(target_capacity: usize, prototype_bucket: TokenBucket, shard_amount: usize) -> Self {

            shard_amount > 0 && shard_amount.is_power_of_two(),
            "KeyedRateLimiter shard_amount ({shard_amount}) must be > 0 and a power of two"

        );
        let shrink_interval = target_capacity / 4;
        Self {
            data: DashMap::with_capacity_and_shard_amount(target_capacity * 2, shard_amount),
            target_capacity,
            prototype_bucket,
            countdown_to_shrink: AtomicUsize::new(shrink_interval),
            approx_len: AtomicUsize::new(0),
            shrink_interval,
        }

    packet_sender: Sender<PacketBatch>,
    stats: Arc<StreamerStats>,
    server_params: Arc<QuicStreamerConfig>,
    qos: Arc<Q>,
    tasks: TaskTracker,
) where
    Q: QosController<C> + Send + Sync + 'static,
    C: ConnectionContext + Send + Sync + 'static,
{
    let from = connecting.remote_address();
    let res = timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await;
    stats
        .outstanding_incoming_connection_attempts
        .fetch_sub(1, Ordering::Relaxed);
    if let Ok(connecting_result) = res {
        match connecting_result {
            Ok(new_connection) => {
                debug!("Got a connection {from:?}");
                // now that we have observed the handshake we can be certain
                // that the initiator owns an IP address, we can update rate
                // limiters on the server
                if !rate_limiter.register_connection(&from.ip()) {
