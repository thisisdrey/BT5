### Title
Non-constant-time comparison of the RPC `auth_token` enables timing-based credential recovery - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Every privileged RPC endpoint that gates access behind the node's `connection_options.auth_token` compares the client-supplied `authorization` header to the configured secret using Rust's default `!=` string comparison, which is not constant-time. A remote, unauthenticated attacker can use response-timing differences to incrementally recover the secret token byte-by-byte, then use it to reach admin-only, state-mutating endpoints. This is the direct analog of CVE-2017-12849 (CWE-208/CWE-200): a response-time discrepancy in a credential check that permits enumeration/recovery of a secret via timing.

### Finding Description
Several `HttpRequest::try_parse_request` implementations authenticate privileged requests with the pattern:

```rust
let Some(auth_header) = preamble.headers.get("authorization") else {
    return Err(Error::Http(401, "Unauthorized".into()));
};
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`auth_header` and `password` are plain `String`/`&str` values compared with `PartialEq`, which the Rust standard library implements as a length check followed by a `memcmp`-style comparison that short-circuits on the first differing byte. This means the time taken to reject a bad token is a monotonic function of how many leading bytes match the real secret. No constant-time comparison primitive (e.g. `subtle::ConstantTimeEq`) is used anywhere in this comparison path; a grep across the repo for `ct_eq`/`constant_time` in this context returns nothing tied to these checks.

The `docs/rpc/openapi.yaml` documentation confirms the intended semantic — "Plain-text secret value that must exactly equal the node's configured password" — i.e., this is meant to be a strict equality gate, but the implementation does not protect that equality check against timing side channels. [7](#0-6) 

This breaks the intended equality invariant "attacker-supplied token == stored secret should reveal nothing beyond a boolean" — here it leaks a monotonically-increasing timing signal correlated with matched-prefix length, allowing incremental brute force of the secret over the network (classic byte-at-a-time timing attack), which is exactly the CWE-208 bug class in the reported CVE.

### Impact Explanation
Once an attacker recovers the `auth_token`, they gain access to admin-gated endpoints in this same file family, including `/v3/block_proposal` (used by the signer set to validate block proposals) and the broadcast path of `/v3/blocks` (`postblock_v3.rs`, where `broadcast=1` requires authentication). This grants an unauthorized remote party the ability to submit block proposals / trigger authenticated broadcast paths that are otherwise restricted to trusted signer/operator infrastructure — an unauthenticated-to-authenticated privilege escalation into node write/control paths. This aligns with the "Critical: unauthenticated/unauthorized write to state" impact tier.

### Likelihood Explanation
Exploitation requires a moderate amount of timing measurement (many requests, statistical averaging) — practical byte-at-a-time timing attacks over a network are well documented (e.g. against HMAC/token comparisons) but require the endpoint to be reachable and to have low, stable network jitter or many repeated samples to average out noise. Because the token length and charset are unknown to the attacker in advance, full recovery is non-trivial but has repeatedly been demonstrated to be practical for secrets of this kind over the RPC/API surface, especially against a node reachable with low RTT (e.g., co-located infrastructure, cloud neighbor, or same-datacenter signer/miner topology).

### Recommendation
Replace all instances of `auth_header != password` (and equivalent) in `stackslib/src/net/api/*` with a constant-time comparison, e.g., using the `subtle` crate's `ConstantTimeEq`, or comparing SHA-256/HMAC digests of both values instead of the raw secret. Centralize this into a single `check_auth_token` helper reused by every handler (`postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, `postblock_v3.rs`) so the fix cannot regress independently per endpoint.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"` and expose `/v3/block_proposal`.
2. From a network position with low, stable RTT to the node, send repeated `POST /v3/block_proposal` requests, each time supplying a guessed `authorization` header value that shares an increasing number of correct leading bytes with the real secret (starting from a brute-forced correct first byte, extending one byte at a time).
3. Measure aggregate/averaged response latency for the 401 rejection at `auth_header != password`; because the comparison short-circuits on the first mismatched byte, guesses matching more leading bytes take measurably longer on average.
4. Iteratively extend the correctly-guessed prefix by testing all byte values at the next position and keeping the one with the largest timing delta, until the full token is recovered.
5. Use the recovered token to submit authenticated requests to `/v3/block_proposal` or broadcast-authenticated `POST /v3/blocks?broadcast=1`.
