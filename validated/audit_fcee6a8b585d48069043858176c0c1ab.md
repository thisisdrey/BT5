### Title
Stale PromiseYield receipt/status survives DeleteAccountAction and executes against a recreated account with the same name - (File: core/store/src/utils/mod.rs, runtime/runtime/src/actions.rs, runtime/runtime/src/lib.rs)

### Summary
`remove_account` (called from `action_delete_account`) only clears `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows, but never removes `TrieKey::PromiseYieldReceipt` or `TrieKey::PromiseYieldStatus`. If an account with an outstanding `promise_yield_create` is deleted and a new account is created under the identical `AccountId`, the old yield receipt remains addressable by `(account_id, data_id)` and will be executed by a later `PromiseResume` (including the automatic timeout resume) against the new account's state.

### Finding Description
`set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-212`) stores the yielded `Receipt` under `TrieKey::PromiseYieldReceipt { receiver_id, data_id }`, and `set_promise_yield_status`/timeout enqueue write a parallel `TrieKey::PromiseYieldStatus`/`TrieKey::PromiseYieldTimeout` entry. Both keys are namespaced purely by the string `AccountId`, with no binding to an account "generation" or creation nonce.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) checks storage-usage size and gas-key balance, refunds the balance, then calls `remove_account` (`core/store/src/utils/mod.rs:505-575`) which iterates and removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`. It never touches `col::PROMISE_YIELD_RECEIPT`, `col::PROMISE_YIELD_STATUS`, or `col::PROMISE_YIELD_TIMEOUT`/`YieldIdToDataId`/`DataIdToYieldId` rows for that account.

When a `PromiseResume` receipt later arrives for that `data_id` (either genuinely resumed or the timeout auto-fired via `resolve_promise_yield_timeouts`, `runtime/runtime/src/lib.rs:3009-3105`), the dispatch in `lib.rs:1500-1562` does:
```
get_promise_yield_status(state_update, account_id, data_receipt.data_id)
...
get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)
``` [1](#0-0) 
Both lookups are keyed only by the account-id string and `data_id`, with no check that the account is the same logical account that created the yield. If `victim.near` is deleted and recreated by an attacker, the leftover `PromiseYieldReceipt`/`PromiseYieldStatus` rows are still present at that same key, so `get_promise_yield_receipt` succeeds and the code proceeds to `apply_action_receipt` on the old yield receipt's actions, which execute against the **current** (attacker-controlled) account state: [2](#0-1) 

`remove_account`'s incomplete cleanup is the root cause: [3](#0-2) 

`action_delete_account` itself has no check for outstanding promise-yield state before permitting deletion: [4](#0-3) 

Existing checks that fail to stop this: `DeleteAccountStaking` only checks locked stake, `DeleteAccountWithLargeState` only checks storage usage, `GasKeyBalanceTooHigh` only checks gas-key balances — none inspect promise-yield rows. There is no invariant anywhere that a `PromiseYieldReceipt`/`Status`/`Timeout` blocks account deletion or gets purged with it.

### Impact Explanation
This is an authorization-escalation flaw across accounts: an old contract's callback (whatever actions were embedded in the original `promise_yield_create`'s yield receipt — which can include `FunctionCall`, `Transfer`, etc., since the yield receipt is a normal `ActionReceipt`) executes under a different (attacker-controlled) account after account recreation. Because the callback's actions run with `account_id = victim.near` (now attacker-owned) as receiver, and the receipt's original actions can already contain transfers/function calls determined by the *original* contract logic, exploitation value depends on what the pending yield's actions do (e.g., if the dApp's yield callback transfers funds to `predecessor_id` or writes state based on stale expectations, an attacker who recreates the account and shapes surrounding state can redirect or capture the callback effects). This matches the "authorization escalation across accounts or promises" bounty category, and in scenarios where the callback moves value, it enables theft.

### Likelihood Explanation
Preconditions are attacker-reachable with a normal account:
1. `victim.near` (any account, not necessarily attacker's) has a dApp that calls `promise_yield_create`, creating an outstanding yield keyed by `(victim.near, data_id)`.
2. `victim.near` is deleted via a `DeleteAccountAction` with no locked balance — this requires the account owner (or someone with a full-access key) to delete it; note this requires legitimate control over `victim.near`'s deletion, or the scenario applies when the victim account owner deletes and an attacker front-runs recreation of the exact same name.
3. Attacker recreates `victim.near` (sub-account creation rules apply per `action_create_account`, so this works straightforwardly for sub-accounts, and for top-level accounts only via the registrar or if implicit).
4. The already-scheduled timeout (`PromiseYieldTimeout`) auto-fires via `resolve_promise_yield_timeouts`, requiring no attacker action to forge a resume — it is a guaranteed, protocol-driven event.

Feasibility is moderate: the attacker doesn't need special privileges beyond normal transaction submission, and the timeout resume is automatic, so no forged receipt is needed. The main friction is the requirement that the exact same account name be deleted and recreated before the yield's expiration, which for sub-accounts is straightforward (attacker can create `victim.near` as a sub-account they also fully control, or race a legitimately-deleted account). Repeatable per (account, data_id) pair.

### Recommendation
`remove_account` should also enumerate and remove all `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries scoped to the account being deleted (analogous to how it already sweeps `ContractData` and access keys via prefix iteration). Alternatively/additionally, `action_delete_account` should reject deletion (similar to `DeleteAccountStaking`) if the account has any outstanding `PromiseYieldStatus`/`PromiseYieldReceipt` rows, ensuring account deletion is not permitted while a yield is pending resolution.

### Proof of Concept
Runtime apply-test plan (in `runtime/runtime/src/tests/apply.rs` style, following the pattern already used by `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create `victim.near` and deploy a contract that calls `promise_yield_create` with a callback action list including a state-changing action (e.g., `FunctionCall` to a method that transfers or mutates storage), producing a `PromiseYield` receipt with `input_data_ids = [data_id]`.
2. Apply the receipt so `set_promise_yield_receipt`/`enqueue_promise_yield_timeout` store `TrieKey::PromiseYieldReceipt{receiver_id: victim.near, data_id}` and the timeout entry.
3. Submit a `DeleteAccountAction` receipt for `victim.near` (zero locked balance) and apply it; assert via `get_promise_yield_receipt`/`get_promise_yield_status` that the rows for `data_id` still exist in the trie despite `get_account(victim.near)` returning `None`.
4. Recreate `victim.near` with `CreateAccountAction` + deploy a new/different contract, establishing new state/balance for the attacker-controlled account.
5. Advance `block_height` past `expires_at` and invoke `resolve_promise_yield_timeouts` (or directly construct/apply the `PromiseResume{data_id, data: None}` receipt) targeting `victim.near`.
6. Assert that `apply_action_receipt` executes the *original* stale yield receipt's actions against the newly-recreated `victim.near` account — e.g., assert the callback's `FunctionCall`/`Transfer` action mutates the new account's balance/state, and that `get_promise_yield_receipt`/`get_promise_yield_status` for `data_id` are only cleared at this late point, proving state from the deleted account persisted and executed against the unrelated recreated account.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}
