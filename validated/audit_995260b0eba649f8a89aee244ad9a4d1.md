### Title
Unhandled `ArithmeticException` in `MarketSellAssetActuator` order matching can propagate as an uncaught RuntimeException during block application - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator.matchSingleOrder()` performs overflow-checked arithmetic (`subtractExact`, `addExact`) when settling maker/taker orders, but `execute()` only catches `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException`. If the overflow-checked math throws `ArithmeticException`, it is not caught and converted to a `ContractExeException` the way the analogous `ExchangeTransactionActuator` overflow path is (see `hardenedExecuteOverflowThrowsArithmeticException` test), so it escapes as an unchecked `RuntimeException`.

### Finding Description
`execute()` wraps only specific checked exceptions: [1](#0-0) 

But the order-matching logic invoked from `execute()` uses `subtractExact`/`addExact` on user-controlled quantities during settlement: [2](#0-1) [3](#0-2) 

By contrast, `ExchangeTransactionActuator`/`ExchangeCapsule` explicitly hardened this class of bug: overflow from `addExact`/`subtractExact` in the exchange-pool math is deliberately allowed to surface as `ArithmeticException` and is wrapped into `ContractExeException` by the caller, as demonstrated by the test: [4](#0-3) 

`MarketSellAssetActuator.execute()` has no equivalent catch for `ArithmeticException`, so any such exception raised deep inside `matchOrder`/`matchSingleOrder` is not translated into a checked `ContractExeException`. It instead propagates unchanged through `RuntimeImpl.execute()` (`act.execute(...)` call site with no try/catch around it): [5](#0-4) 

and further up through `Manager.processTransaction()` and `Manager.processBlock()`, whose method signatures only declare specific checked exceptions and whose surrounding `try { ... } finally { ... }` block in `processBlock()` does not catch generic `RuntimeException`: [6](#0-5) 

This is analogous to the Avahi bug class: a state built up by a specific sequence of two attacker-controlled inputs (here: a maker `MarketSellAssetContract` order followed by a matching taker order with quantities crafted so the internal settlement arithmetic overflows `Long`) triggers an internal invariant violation (an unhandled runtime assertion-like exception) instead of a graceful, contained error.

### Impact Explanation
An uncaught `RuntimeException` raised while applying a transaction inside `processBlock()`/`generateBlock()` is not a checked exception the block-processing pipeline is designed to recover from; depending on call context (`pushBlock` vs. transaction packing) this can abort block application/generation with an unexpected exception, which is the "node crash or halt" class explicitly listed as acceptable impact. Because market-sell orders are a broadcastable transaction type available to any account, an anonymous transaction broadcaster can trigger it without needing any special privilege.

### Likelihood Explanation
Likelihood depends on whether `validate()` (not fully inspected here) bounds `sellTokenQuantity`/`buyTokenQuantity` tightly enough to prevent the intermediate `subtractExact`/`addExact` operations in `matchSingleOrder` from ever overflowing `Long.MAX_VALUE`. The `MarketSellAssetContract` quantity fields are protobuf `int64`, so an attacker can supply values up to `Long.MAX_VALUE`; whether real account balances or explicit validate-time checks prevent constructing a maker/taker pair whose settlement math overflows is something I could not fully confirm from the code sections retrieved — this is the main uncertainty in this analog.

### Recommendation
- Audit `MarketSellAssetActuator.validate()` to ensure `sellTokenQuantity`/`buyTokenQuantity` (and any values derived through `MarketUtils.multiplyAndDivide`) are bounded such that all `subtractExact`/`addExact` calls in `matchSingleOrder`/`transferBalanceOrToken`/`addTrxOrToken` cannot overflow.
- Regardless, widen `execute()`'s catch clause (or wrap `matchOrder`/`matchSingleOrder`) to also catch `ArithmeticException` and convert it into `ContractExeException`, mirroring the pattern already used to harden `ExchangeTransactionActuator`/`ExchangeCapsule`.

### Proof of Concept
Not independently reproduced; conceptually: broadcast a `MarketSellAssetContract` maker order and a second matching `MarketSellAssetContract` taker order whose sell/buy quantities are chosen so that `makerOrderCapsule.getSellTokenQuantityRemain() - takerBuyTokenQuantityRemain` (or the corresponding `addExact` in `addTrxOrToken`) exceeds `Long` bounds during `matchSingleOrder`, causing an uncaught `ArithmeticException` to propagate out of `MarketSellAssetActuator.execute()`.
