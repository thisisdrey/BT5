### Title
Multisig weight double-counting in `ValidateMultiSign` precompile allows bypassing permission threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (address `0x0000...09`) is reachable by any contract call (`TriggerSmartContract`) and is meant to let a smart contract verify that a set of signatures from an account's `Permission` key list meets the account's signing threshold. Its de-duplication logic only rejects an *exact* duplicate signature bytes for a signer, not a second, different-but-valid signature from the same signer over the same hash. This lets a single key holder inflate the counted weight and satisfy a multisig threshold that should require multiple independent signers — the on-chain analog of GitLab's CVE-2022-4143, where crafted approvals let unapproved changes be "merged" without the required authorization.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`: [1](#0-0) 

For each supplied signature, the code recovers the signer address, then checks:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
`sign` here is `merge(recoveredAddr, sign)` — the address concatenated with the *raw signature bytes*, so the "already seen" check only fires when the exact same signature bytes repeat. If the same address has already signed (present in `executedSignList`) but is presented with a **different** valid signature over the identical hash (which is trivial to produce — every ECDSA sign with a different nonce k yields a distinct valid `(r,s)` pair for the same key and message, and this VM does not enforce low-S/canonical signatures), the inner `matrixContains(executedSignList, sign)` check fails, so execution does **not** `continue`; it falls straight through to `getWeight(...)` and adds that signer's weight to `totalWeight` a second time.

This differs from the fork-gated fix already applied to the analogous transaction-level check in `TransactionCapsule.checkWeight`, which — after `VERSION_4_7_1` — keys its de-dup map by the recovered **address**, rejecting a second signature from the same signer outright ("has signed twice!"): [2](#0-1) 

The precompile never received the equivalent per-address de-duplication; it only de-duplicates identical signature bytes, per `ByteArray.matrixContains`: [3](#0-2) 

### Impact Explanation
Any Solidity/TVM contract that relies on `ValidateMultiSign` to gate privileged actions (e.g. custodial/multisig wallet contracts, DAO-style approval logic, DeFi vaults) can be tricked into treating a *single* private key as multiple independent approvers. An attacker who controls one key in the permission's key list can produce several distinct valid signatures over the same hash and submit them together, inflating `totalWeight` past `permission.getThreshold()` even though only one real signer participated. This is a concrete unauthorized-operation / permission-bypass vulnerability: contract logic (fund transfers, admin actions, approvals) gated by this precompile can be executed without the intended number of independent approvers, i.e. theft or unauthorized state changes analogous to the GitLab MR-approval bypass.

### Likelihood Explanation
The precompile is directly reachable from any account via a normal `TriggerSmartContract` call to a deployed contract that uses `validateMultiSign`, requiring no special privilege — the attacker only needs to control one key with nonzero weight in the target permission and be able to produce a second valid ECDSA signature over the same hash (trivial, since signing is not required to be deterministic/canonical). No witness, committee, or node compromise is needed.

### Recommendation
Change the de-duplication in `ValidateMultiSign.execute` to key `executedSignList` (or a dedicated set) by the **recovered address only**, mirroring the post-`VERSION_4_7_1` fix in `TransactionCapsule.checkWeight` — reject or skip weight accrual the moment an address that has already contributed weight appears again, regardless of whether the signature bytes differ.

### Proof of Concept
1. Create an account with an `Active` permission containing key `K` (weight `W1`) and key `K2` (weight `W2`), with `threshold = W1 + W2` (i.e., both signers required).
2. Have only holder of `K` sign the same `hash` twice with different nonces, producing two distinct valid signatures `sig1` and `sig2` that both recover to `K`'s address.
3. Call the `validateMultiSign` precompile (via a contract or the existing test harness in `framework/src/test/java/org/tron/common/runtime/vm/ValidateMultiSignContractTest.java`) with `signatures = [sig1, sig2]`.
4. Trace through `execute`: first iteration adds `sig1`'s weight (`W1`), sets `executedSignList = [merge(K,sig1), K]`; second iteration recovers `K` again, `matrixContains(executedSignList, K)` is true but `matrixContains(executedSignList, merge(K,sig2))` is false (different bytes) — so it does not `continue`, and adds `W1` again, giving `totalWeight = 2*W1`.
5. If `2*W1 >= threshold`, the precompile returns `DataWord.ONE()` (success) even though `K2` never signed, bypassing the intended two-signer requirement. [4](#0-3)
