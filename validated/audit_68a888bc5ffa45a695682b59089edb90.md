Based on my investigation, I found a concrete integer/size-overflow analog to the OpenJPEG bug class in the `BatchValidateSign` precompiled contract in java-tron.

### Title
Unbounded attacker-controlled array-length in BatchValidateSign precompile causes OutOfMemoryError DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` precompiled contract parses signature/address array counts directly from attacker-supplied calldata words and immediately allocates Java arrays sized by that count, with the size-bounding check gated behind a feature flag that is not always active.

### Finding Description
In `doExecute`, the signature-array length is read straight from calldata via `words[offset].intValueSafe()`, which can return any value up to `Integer.MAX_VALUE` [1](#0-0) . Bounds validation against `MAX_SIZE` only occurs when the `allowTvmSelfdestructRestriction()` hard-fork flag is enabled: [2](#0-1) 

When that proposal is not active (or on any deployment where it has not yet been switched on by committee vote), the code falls straight into `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, each of which does `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];` with **no upper bound check at all** [3](#0-2) . A crafted 32-byte word describing a length close to `Integer.MAX_VALUE` (e.g. `0x7fffffff`) forces the JVM to attempt allocating an array of ~2.1 billion references, which throws `OutOfMemoryError` — this is the same bug class as the OpenJPEG issue: an attacker-controlled count value drives an allocation/iteration that overflows resource limits and crashes the process, rather than being validated against a sane bound before use.

### Impact Explanation
An `OutOfMemoryError` thrown deep inside VM/precompile execution is a JVM `Error`, not a checked `Exception`; such errors are frequently uncaught by contract-execution exception handlers designed around `ContractValidateException`/`ContractExeException`, so they can propagate and destabilize the executing thread or the node's block-processing pipeline, producing a node crash/halt (availability impact), matching the CVSS vector `C:N/I:N/A:H` of the original report.

### Likelihood Explanation
This precompile is reachable by any unprivileged account: it only requires deploying or calling a contract that issues a `CALL`/`STATICCALL` to the `BatchValidateSign` precompiled address with attacker-chosen calldata — no special permission, SR/witness status, or large network payload is needed, since the malicious "count" is a single 32-byte word inside an otherwise small calldata blob. The only gating factor is whether `allowTvmSelfdestructRestriction()` is active on the chain, which is not guaranteed for all deployments/points in time.

### Recommendation
Move the `MAX_SIZE` bound check unconditionally before calling `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, regardless of the `allowTvmSelfdestructRestriction()` flag, and reject any parsed length that isn't consistent with the actual size of `data`/`words` before allocating arrays.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL` to the `BatchValidateSign` precompiled contract address.
2. Craft calldata where `words[1]` points to an offset whose word value (`sigArraySize`) is set to `0x7fffffff`.
3. On a chain/config where `allowTvmSelfdestructRestriction()` is not enabled, `doExecute` skips the `MAX_SIZE` check [4](#0-3)  and calls `extractBytesArray`, which executes `new byte[len][]` with `len = 0x7fffffff`, throwing `OutOfMemoryError` [5](#0-4) .
