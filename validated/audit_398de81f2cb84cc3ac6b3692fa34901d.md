### Title
Pack-objects concurrency limiter is keyed solely by remote IP, allowing a single unprivileged client to exhaust the shared queue and DoS all other users behind that IP - (File: internal/gitaly/service/hook/pack_objects.go)

### Summary
The external report describes a bug class where a shared/global gating mechanism (a withdrawal queue) can be forcibly triggered by any single actor, degrading service for every other unrelated user of the same system. The analogous mechanism in Gitaly is the `packObjectsLimiter`, a concurrency limiter that gates `git-pack-objects` invocations spawned for every `git fetch`/`git clone` (`upload-pack`) request. Instead of being scoped per repository or per authenticated user as documented, the limiter is keyed **only by the client's remote IP address**, so all fetches from many different repositories and different end-users that happen to share an IP (NAT gateways, corporate proxies, CI runner pools, GitLab.com's own infrastructure egress IPs, etc.) are funneled into one shared concurrency/queue bucket.

### Finding Description
`packObjectsHook` derives the limiting key exclusively from `req.GetRemoteIp()` and passes it into `runPackObjectsLimited`, which calls `s.packObjectsLimiter.Limit(ctx, limitkey, ...)`: [1](#0-0) 

`runPackObjectsLimited` then calls the shared `ConcurrencyLimiter.Limit` using that IP-derived key with no repository or user component: [2](#0-1) 

The `TypePackObjects` limiter's own documentation claims it uses "RemoteIP/Repository/User" as the key, but the actual code that builds the key at the call site uses `ipAddr.String()` alone: [3](#0-2) 

The default configuration further confirms the limiter is "scoped by remote IPs," with a fixed default concurrency (200) and queue size (200) applied per IP, globally across all repositories served by that Gitaly node: [4](#0-3) 

The underlying `ConcurrencyLimiter` enforces both an admission queue (`maxQueueLength`) and a queue-wait timeout per key; once either is exceeded, all *further* requests under that key — including ones from unrelated users/repositories that legitimately share the same key/IP — are rejected with `ResourceExhausted` (`ErrMaxQueueSize`/`ErrMaxQueueTime`): [5](#0-4) [6](#0-5) 

This mirrors the report's bug class precisely: a shared "gate" (queue) intended to protect against pathological load can be forced into its degraded/blocking state by a single unprivileged actor, and because the gate's scope is broader than necessary (global by IP rather than per-repository/per-user), the resulting degradation collaterally punishes every other legitimate request sharing that scope — not just the actor's own requests.

### Impact Explanation
Any unprivileged user issuing ordinary `git fetch`/`git clone` requests against multiple distinct repositories from a shared egress IP (e.g., a large NAT'd office network, a CI/CD runner farm, a corporate VPN gateway, or GitLab.com's own web/proxy infrastructure IP) can saturate the 200-slot concurrency pool and 200-slot queue for that IP. Once saturated, every other user's fetch/clone request that happens to originate from — or is routed through — the same IP will be queued and, upon timeout, will fail with a `ResourceExhausted`/`LimitError` gRPC error, exactly as legitimate large fetches would. This is a handler-level Denial of Service reachable from a completely ordinary, authenticated client action (a git fetch), with no privileged position or malicious peer/MITM assumption required, satisfying the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: shared egress IPs are common (corporate NATs, CI runner pools, cloud load balancers, GitLab-hosted proxy layers), and the mechanism to trigger congestion only requires issuing many ordinary, unprivileged fetch/clone requests against different repositories — the exact write-once-read-many usage pattern of any active Gitaly instance. No authentication bypass, crafted payload, or race condition is needed; simply exceeding 200 concurrent pack-objects invocations from one IP address is sufficient.

### Recommendation
**Short term:** Change the pack-objects concurrency-limiting key to genuinely include a per-repository (and ideally per-user) component in addition to remote IP, as the code comments already claim it should, so that congestion caused by one repository/user cannot exhaust the queue capacity for unrelated repositories/users sharing the same IP. Alternatively, apply a two-level limiter: a generous, purely informational per-IP ceiling plus a strict per-repository/per-user limiter that is the actual gate.

**Long term:** Periodically review the default `PackObjectsLimiting` concurrency/queue-size defaults against real-world IP-sharing patterns (NAT gateways, CI pools, GitLab.com edge infrastructure) to ensure the shared-key design does not let a single tenant behind a popular egress IP degrade service for all others behind that same IP.

### Proof of Concept
1. Deploy Gitaly with default `[pack_objects_limiting]` settings (`concurrency ≈ 200`, `max_queue_size ≈ 200`, scoped by IP as shown in `internal/gitaly/config/config.go`).
2. As an ordinary, authenticated user situated behind a shared IP (e.g., simulate by sending requests that set the same `remote_ip` metadata value, which is populated per-request by the calling proxy layer, e.g. Workhorse/gitlab-shell), issue 200+ concurrent `git fetch`/`git clone` (upload-pack) requests against many distinct repositories on the same Gitaly node.
3. Concurrently, have a second, unrelated legitimate user (different repository, different actual user, same shared IP) attempt a normal `git fetch`.
4. Observe that the legitimate user's `PackObjectsHookWithSidechannel` call is placed into the same IP-keyed queue (`runPackObjectsLimited` / `ConcurrencyLimiter.Limit`) and eventually fails with `codes.ResourceExhausted` / `gitalypb.LimitError` (`ErrMaxQueueSize` or `ErrMaxQueueTime`), as demonstrated by the existing test harness pattern in `pack_objects_test.go` which already exercises this exact queue-exhaustion code path using only `RemoteIp`+ small concurrency values to trigger `ErrMaxQueueTime`/`ErrMaxQueueSize`: [7](#0-6)

```go
// acquire tries to acquire the semaphore. It may fail if the admission queue is full or if the max
// queue-time ticker ticks before acquiring a concurrency token.
func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}
		// We have acquired a queueing token, so we need to release it if acquiring
		// the concurrency token fails. If we succeed to acquire the concurrency
		// token though then we retain the queueing token until the caller signals
		// that the concurrency-limited function has finished. As a consequence the
		// queue token is returned together with the concurrency token.
		//
		// A simpler model would be to just have `maxQueueLength` many queueing
		// tokens. But this would add concurrency-limiting when acquiring the queue
		// token itself, which is not what we want to do. Instead, we want to admit
		// as many callers into the queue as the queue length permits plus the
		// number of available concurrency tokens allows.
		defer func() {
			if returnedErr != nil {
				sem.queueTokens.Release()
			}
		}()
	}

	// We are queued now, so let's tell the monitor. Furthermore, even though we're still
	// holding the queueing token when this function exits successfully we also tell the monitor
	// that we have exited the queue. It is only an implementation detail anyway that we hold on
	// to the token, so the monitor shouldn't care about that.
	sem.monitor.Queued(ctx, limitingKey, sem.queueLength())
	defer sem.monitor.Dequeued(ctx)

	if sem.maxQueueWait != 0 {
		if sem.setWaitTimeoutContext != nil {
			ctx = sem.setWaitTimeoutContext()
		} else {
			var cancel context.CancelFunc
			ctx, cancel = context.WithTimeout(ctx, sem.maxQueueWait)
			defer cancel()
		}
	}

	// Try to acquire the concurrency token now that we're in the queue.
	return sem.concurrencyTokens.Acquire(ctx)
}
```
