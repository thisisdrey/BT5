### Title
Interest accrual pushes `totalSupply_` past `maxTotalSupply` without validation, permanently reverting all new debt issuance - ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
`DebtToken.accrueInterest()` adds accrued interest directly to `totalSupply_` without enforcing the `maxTotalSupply` cap that `_mint()` enforces. Once accrual pushes `totalSupply_` above the cap, every subsequent call to `issue()` and `mint()` (and therefore all leverage through `SmartFarmingManager`) reverts with `SurpassMaxDebtSupply` until enough debt is repaid. This is the same bug class as the reported `LibEntity._updateEntity()` issue: a recomputed/derived value (`newUtilizedCapacity` there, `totalSupply_` + interest here) is written into state without being checked against the configured cap, leaving the contract in a state its own validation logic treats as invalid and denying the core write path.

### Finding Description
In `accrueInterest()` (contracts/DebtToken.sol:156-180):

```solidity
if (_interestAmountAccrued > 0) {
    totalSupply_ += _interestAmountAccrued;
    debtIndex = _debtIndex;
    try syntheticToken.mint(pool.feeCollector(), _interestAmountAccrued + pendingInterestFee) { ... }
}
```

`totalSupply_` is increased by `_interestAmountAccrued` unconditionally. There is no `if (totalSupply_ > maxTotalSupply) revert` here — and there shouldn't necessarily be one for accrual, but the consequence is that the stored state can exceed `maxTotalSupply`.

In `_mint()` (contracts/DebtToken.sol:590-591):

```solidity
totalSupply_ += amount_;
if (totalSupply_ > maxTotalSupply) revert SurpassMaxDebtSupply();
```

Because `accrueInterest()` is invoked at the top of both `issue()` (line 248) and `mint()` (line 340), any accrual that pushes `totalSupply_` over `maxTotalSupply` makes *every* subsequent `issue`/`mint` revert, even for `amount_` small enough that principal debt would fit under the cap if accrued interest were excluded or handled separately.

The asymmetry mirrors the report exactly: the cap check only runs on the "new value added" path (`_mint`), while the recomputed value path (interest added to `totalSupply_`) is never reconciled against the cap — just as `newUtilizedCapacity` was never checked against `maxCapacity`. The result is a persisted state that the protocol's own checks classify as over-capacity, blocking new issuance (the analog of "unable to write new policies").

### Impact Explanation
- **Denial of the core issuance path:** `issue()` is the only way users mint synthetics against collateral, and `mint()` is what `SmartFarmingManager.leverage()`/`flashRepay` flows depend on. Once `totalSupply_ > maxTotalSupply`, both revert unconditionally.
- **Duration:** the DoS persists until repays/liquidations burn enough debt to bring `totalSupply_` back under the cap. Borrowers have weak incentive to repay during this window, and `repay`/`repayAll` still work, so this is a *temporary* freezing/liveness break rather than permanent.
- Interest continues accruing on the over-cap supply, so the gap only widens while issuance stays blocked.

### Likelihood Explanation
- `accrueInterest()` is permissionless; any EOA can trigger the accrual that crosses the cap. The attacker can also deliberately mint debt up to just below `maxTotalSupply` via `issue()` (subject only to their own collateral and `debtFloorInUsd`), maximizing the rate at which interest accumulation exceeds the cap.
- Feasibility depends on `interestRate > 0` and utilization near the cap — both plausible configurations, and the attacker can supply the marginal utilization themselves.
- No privileged role, oracle manipulation, or governance action is required on the attack path itself; the missing check is purely internal.

### Recommendation
- Reconcile accrued interest against `maxTotalSupply` instead of letting `_mint` absorb the inconsistency: either treat the cap as applying to principal (track accrued interest separately from `totalSupply_` for cap purposes) or clamp/short-circuit accrual at the cap.
- At minimum, make the failure mode explicit: document or enforce that `maxTotalSupply` must be set with headroom for interest accrual, or have `_mint` compare `totalSupply_ + amount_` against `maxTotalSupply + accruedInterest` so over-cap interest does not brick all issuance.
- Following the report's second suggestion, consider only folding interest into `totalSupply_` lazily per-account (the `debtIndex`/`principalOf` model already supports this) so the global supply check reflects principal, not accumulated yield.

### Proof of Concept
Hardhat sketch (fork/test against deployed-style fixture):

```ts
// setup: pool with msUSD DebtToken, deposit token with collateralFactor ~0.8e18
const debtToken = msUSDDebt; // DebtToken with interestRate > 0
const cap = await debtToken.maxTotalSupply();

// 1) Attacker deposits collateral and issues debt up to just under the cap
const issuable = cap.sub(await debtToken.totalSupply_()); // principal headroom
await depositToken.deposit(collateralAmount, attacker.address);
await debtToken.issue(issuable, attacker.address); // succeeds, totalSupply_ == cap - epsilon

// 2) Time passes (or attacker calls accrueInterest() after interest accrues)
await ethers.provider.send("evm_increaseTime", [30 * 24 * 3600]);
await ethers.provider.send("evm_mine");
await debtToken.accrueInterest(); // permissionless; totalSupply_ now > maxTotalSupply

// 3) Any new issuance reverts permanently until repays
await expect(
  debtToken.connect(victim).issue(parseEther("1"), victim.address)
).to.be.revertedWithCustomError(debtToken, "SurpassMaxDebtSupply");

// same for SmartFarmingManager path: debtToken.mint(...) -> SurpassMaxDebtSupply
```

The state after step 2 is exactly the reported invalid state: a derived quantity exceeding its configured cap with no check at write time, and the revert in `_mint` then denies the "write new policies" equivalent (`issue`/`mint`) for all users.
