Confirmed. `FullNodeJsonRpcHttpService.addFilter` only registers `HttpInterceptor`, not `HttpApiAccessFilter`, and `JsonRpcServlet.doPost` never consults `CommonParameter.getInstance().getDisabledApiList()`. This matches the exact analog to CVE-2024-9612.

### Title
Node operator's `disabledApi` restriction is silently bypassed via the JSON-RPC endpoint - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/JsonRpcServlet.java`)

### Summary
java-tron exposes a node-operator-controlled `disabledApi` configuration list intended to block access to specific query APIs across all node interfaces. The documentation and code explicitly acknowledge this control does not apply to the JSON-RPC interface, meaning any API disabled by an operator (e.g., to prevent leaking wallet/account/block data) remains fully reachable to any anonymous JSON-RPC client.

### Finding Description
The `node.disabledApi` config is enforced by `HttpApiAccessFilter` for the FullNode/Solidity/PBFT HTTP wallet APIs [1](#0-0)  and by `RpcApiAccessInterceptor` for gRPC [2](#0-1) . Both consult `CommonParameter.getInstance().getDisabledApiList()`.

The JSON-RPC HTTP service, however, wires only `HttpInterceptor` as its filter and never applies `HttpApiAccessFilter` or checks `disabledApiList` anywhere: [3](#0-2) . The request handler `JsonRpcServlet.doPost` dispatches directly into `rpcServer.handle(...)` / `TronJsonRpc` without any disabled-API check [4](#0-3) . This gap is a documented, intentional limitation rather than an oversight — the config comment states: "Disabled API list (works for http, rpc and pbft, not jsonrpc)" [5](#0-4) , and `docs/configuration.md` instructs operators to use `node.disabledApi` to "disable an API endpoint that you do not want to expose publicly" without qualifying that JSON-RPC is exempt [6](#0-5) . `JsonRpcOnSolidityServlet` and `JsonRpcOnPBFTServlet` inherit the same gap (`disabledApiList`/`DisabledApi` is referenced nowhere in any JSON-RPC source file).

### Impact Explanation
An operator who disables sensitive query endpoints (account balances, block/transaction data, delegated-resource info, reward/brokerage info, etc.) via `node.disabledApi` to reduce data exposure on a public-facing node believes those endpoints are unreachable. Any anonymous client can instead retrieve the same information via the equivalent JSON-RPC method (e.g. `eth_getBalance`, `eth_getBlockByNumber`, `eth_call`), completely bypassing the operator's access-control decision. This is an unauthorized information-disclosure/access-control bypass, directly analogous to CVE-2024-9612's backend not enforcing an intended visibility restriction.

### Likelihood Explanation
Trivial to exploit: any anonymous network client that can reach the JSON-RPC HTTP port (enabled via `node.jsonrpc.httpFullNodeEnable`) can send a standard JSON-RPC request; no signature, authentication, or special privilege is required.

### Recommendation
Add a disabled-API check to `JsonRpcServlet` (or a servlet filter registered in `FullNodeJsonRpcHttpService`/`JsonRpcOnSolidityServlet`/`JsonRpcOnPBFTServlet`) that consults `CommonParameter.getInstance().getDisabledApiList()` against the invoked JSON-RPC method name before dispatching to `TronJsonRpc`, mirroring the enforcement already present in `HttpApiAccessFilter` and `RpcApiAccessInterceptor`. Update documentation once fixed.

### Proof of Concept
1. Configure a FullNode with `node.disabledApi = ["getaccount"]` and `node.jsonrpc.httpFullNodeEnable = true`.
2. Confirm `http://<node>:8090/wallet/getaccount` now returns `{"Error":"this API is unavailable due to config"}` (per `HttpApiAccessFilterTest`) [7](#0-6) .
3. Send a JSON-RPC request to `http://<node>:8545/jsonrpc` with `{"jsonrpc":"2.0","method":"eth_getBalance","params":["0x...","latest"],"id":1}` — the equivalent account data is returned successfully, since no disabled-API check exists in `JsonRpcServlet`.

  @Override
  protected void doPost(HttpServletRequest req, HttpServletResponse resp) throws IOException {
    CommonParameter parameter = CommonParameter.getInstance();

    // Transport IOException from readBody propagates as HTTP 500 (genuine IO failure).
    byte[] body = readBody(req.getInputStream());
    JsonNode rootNode;
    try {
      rootNode = MAPPER.readTree(body);
      if (rootNode == null || rootNode.isMissingNode()) {
        writeJsonRpcError(resp, JsonRpcError.PARSE_ERROR, "JSON parse error", null, false);
        return;
      }
    } catch (JsonProcessingException e) {
      if (e instanceof StreamConstraintsException) {
        writeJsonRpcError(resp, JsonRpcError.PARSE_ERROR, e.getMessage(), null, false);
      } else {
        writeJsonRpcError(resp, JsonRpcError.PARSE_ERROR, "JSON parse error", null, false);
      }
      return;
    }

    if (!rootNode.isObject() && !rootNode.isArray()) {
      writeJsonRpcError(resp, JsonRpcError.INVALID_REQUEST, "Invalid Request", null, false);
      return;
    }

    boolean isBatch = rootNode.isArray();
    if (isBatch && rootNode.isEmpty()) {
      writeJsonRpcError(resp, JsonRpcError.INVALID_REQUEST, "Invalid Request", null, false);
      return;
    }
    int batchSize = parameter.getJsonRpcMaxBatchSize();
    if (isBatch && batchSize > 0 && rootNode.size() > batchSize) {
      writeJsonRpcError(resp, JsonRpcError.EXCEED_LIMIT,
          "Batch size " + rootNode.size() + " exceeds the limit of " + batchSize, null, true);
      return;
    }

    int maxResponseSize = parameter.getJsonRpcMaxResponseSize();
    if (isBatch) {
      handleBatch(resp, rootNode, maxResponseSize);
    } else {
      handleSingle(req, resp, rootNode, body, maxResponseSize);
    }
  }
