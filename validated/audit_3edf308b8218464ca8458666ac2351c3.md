This confirms the mechanism. The order is fixed: local → delayed → incoming (`runtime/runtime/src/lib.rs:2681-2715`, `process_receipts`), and `check_proof_size_limit_exceed` is checked at each stage boundary against a single per-chunk `TrieRecorder` (`trie_recording.rs:161-163`). Critically, this recorder is freshly created **every chunk** via `trie.recording_reads_with_proof_size_limit(proof_limit)` in `chain/chain/src/runtime/mod.rs:1268-1269` — it does not persist or accumulate state across chunks. So the premise that the recorder is "shared across whole chunk apply" is true only within a single chunk's apply call; each new chunk starts with `upper_bound_size = 0`.

### Title
Local-receipt storage-proof flooding can perpetually starve delayed-queue and postponed-receipt processing for unrelated accounts - (File: `runtime/runtime/src/lib.rs`, `core/store/src/trie/trie_recording.rs`)

### Summary
`Runtime::process_receipts` processes receipts in the fixed order local → delayed → incoming (`runtime/runtime/src/lib.rs:2681-2715`), checking a single chunk-wide `check_proof_size_limit_exceed()` (`trie_recording.rs:161-163`) before each item. An attacker who repeatedly submits local `FunctionCall` transactions to their own account that read large amounts of trie state (as in `test_storage_proof_size_limit`, `integration-tests/src/tests/features/storage_proof_size_limit.rs:1-147`) can push `upper_bound_size` past `main_storage_proof_size_soft_limit` during `process_local_receipts` alone, causing `process_delayed_receipts` to `break` on its very first iteration (`lib.rs:2486-2490`) every chunk. This blocks the entire delayed-receipt queue — including any Data receipt sitting in it that would otherwise unblock a victim's postponed receipt — indefinitely, so long as the attacker repeats the flooding every chunk.

### Finding Description
`TrieRecorder::check_proof_size_limit_exceed` (`core/store/src/trie/trie_recording.rs:161-163`) compares a monotonically-increasing `upper_bound_size` against `proof_size_limit` for the *whole chunk's* trie recorder, with no per-receipt or per-account partitioning. `process_local_receipts` runs first and unconditionally records every accessed trie node into this recorder (`lib.rs:2407-2416`). If local receipts alone drive `upper_bound_size` above the limit, `process_delayed_receipts`'s very first loop iteration observes `check_proof_size_limit_exceed() == true` and breaks (`lib.rs:2485-2490`) without popping a single delayed receipt.

A victim's Data receipt satisfying a postponed action receipt's last missing `input_data_id` is handled inside `process_receipt`'s `Data` arm (`lib.rs:1386-1473`), which decrements `PendingDataCount` and, when it reaches 0, immediately executes the postponed receipt in the same call. But if that Data receipt is stuck in the delayed queue (having previously been pushed there by an earlier over-budget chunk, or simply queued behind other items), it is never popped for processing while the attacker's local flooding keeps `check_proof_size_limit_exceed()` true at the start of `process_delayed_receipts` every chunk — the postponed receipt, its `PendingDataCount`, and its `PostponedReceipt` trie entries (`lib.rs:1608-1655`, `core/primitives/src/trie_key.rs:204-219`) remain in state unresolved forever.

This is not blocked by any existing check: local receipts are validated only via normal transaction verification (`verify_and_charge_tx_ephemeral`), which does not bound aggregate cross-chunk storage-proof consumption; `main_storage_proof_size_soft_limit` is deliberately a soft limit that defers rather than rejects excess work (`docs/misc/state_witness_size_limits.md:29-32`).

### Impact Explanation
This causes **permanent freezing of a resolvable receipt** for an account unrelated to the attacker — the postponed receipt (and any funds/callback logic gated behind it) never executes as long as the attacker sustains the flood. It also incidentally starves the entire shard's delayed-receipt backlog, not just the one victim, which is a broader liveness failure of receipt processing on the shard. This matches the "permanent freezing of user funds" / liveness-invariant category called out in the prompt.

### Likelihood Explanation
The attacker needs only an ordinary funded account able to deploy a contract and repeatedly submit local (self-addressed) `FunctionCall` transactions that read enough trie/contract state to exceed `main_storage_proof_size_soft_limit` (3,000,000 bytes per `core/parameters/res/runtime_configs/69.yaml:6`) every single chunk — a pattern already demonstrated feasible and cheap in `integration-tests/src/tests/features/storage_proof_size_limit.rs` and `runtime/runtime/src/tests/apply.rs:1444-1517` (`test_main_storage_proof_size_soft_limit`). It requires no validator/node privilege, only sustained gas spend, and is fully repeatable chunk after chunk. However, whether it is a genuine unbounded/permanent freeze (versus merely delaying processing by some bounded number of chunks under gas/economic pressure and existing congestion controls) and whether it is distinguishable from already-accepted soft-limit/congestion trade-offs documented as by-design is not fully verified from static code inspection alone — this needs a concrete test-loop run to confirm the victim's postponed receipt truly never resolves over a long run, rather than merely being delayed.

### Recommendation
Consider bounding delayed-queue starvation, e.g. by reserving a minimum per-chunk storage-proof / compute budget for `process_delayed_receipts` regardless of how much local receipts consumed, or by checking the proof-size limit incrementally per receipt category rather than allowing one category (local) to exhaust the whole chunk's budget before the delayed queue is even attempted.

### Proof of Concept

1. Set up two accounts: `attacker` and `victim`, with `attacker` deploying a contract with a "read N megabytes" method (as in `storage_proof_size_limit.rs`).
2. Set `main_storage_proof_size_soft_limit` low enough to be exceeded by a few megabytes of local reads.
3. Create a victim postponed receipt: send an `ActionReceipt` to `victim` with an unresolved `input_data_id`, then arrange for the resolving `Data` receipt to land in the delayed queue (e.g., by first over-flooding one chunk so it's pushed to `delayed_receipts`).
4. Every subsequent chunk, have `attacker` submit local `FunctionCall` transactions reading enough state to exceed the soft limit before `process_delayed_receipts` runs.

        receipt_sink: &mut ReceiptSink,
    ) -> Result<ProcessReceiptsResult, RuntimeError> {
        let mut validator_proposals = vec![];
        let apply_state = &processing_state.apply_state;

        // TODO(#8859): Introduce a dedicated `compute_limit` for the chunk.
        // For now compute limit always matches the gas limit.
        let compute_limit = apply_state.gas_limit.map(|g| g.as_gas()).unwrap_or(u64::MAX);

        // We first process local receipts. They contain staking, local contract calls, etc.
        self.process_local_receipts(
            processing_state,
            receipt_sink,
            compute_limit,
            &mut validator_proposals,

            processing_state,
            receipt_sink,
            compute_limit,
            &mut validator_proposals,
        )?;

        self.process_incoming_receipts(
            processing_state,
            receipt_sink,
            compute_limit,
            &mut validator_proposals,
        )?;
