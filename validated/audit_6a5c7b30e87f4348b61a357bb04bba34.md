### Title
`AddKey` reseeds nonce purely from `block_height`, contradicting `AccessKey::nonce` doc's "reuse old nonce" guarantee, enabling nonce rollback/replay on same-key recreation - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` and `add_gas_key` in `runtime/runtime/src/access_keys.rs` set the new access key's nonce to `initial_nonce_value(block_height)` unconditionally, never reading the value of any previously-existing access key for that public key (the old key row was already deleted by the preceding `DeleteKey` action, and `action_add_key`'s existence check at line 157 only rejects if a key currently exists). This contradicts the documented invariant on `AccessKey::nonce` ("if the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key... required to avoid replaying old transactions again").

### Finding Description
`initial_nonce_value(block_height)` computes `(block_height - 1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [1](#0-0) . Both `add_regular_key` and `add_gas_key` unconditionally overwrite the `nonce` field with this value when adding a key, without ever looking at a prior nonce: [2](#0-1) [3](#0-2) 

`action_add_key` only checks whether a key *currently* exists (returning `AddKeyAlreadyExists` if so) via `get_access_key` [4](#0-3) ; it does not consult trie history or any deleted key's nonce. Since `DeleteKey` (`delete_regular_key`/`delete_gas_key`) fully removes the access key row from the trie [5](#0-4) , by the time `AddKey` runs there is no "old nonce" left to read even if the code wanted to — the mechanism described in the doc comment (copying old nonce forward) is simply not implemented anywhere in this code path.

Within a single block, `block_height` is constant for every action processed, so `initial_nonce_value(block_height)` is identical for `DeleteKey` and the following `AddKey` for the same public key in the same block. If the previous incarnation of that key had already been used to reach a nonce `N` that is much larger than `initial_nonce_value(block_height)` (which is entirely plausible: nonces just need to be monotonically increasing per key, and legitimate wallets/apps can push nonces arbitrarily high within the `1e6`-per-block-height allocation, or across many prior blocks), then after `DeleteKey; AddKey` in the same block, the key's stored nonce rolls back to `initial_nonce_value(block_height)`, which is *lower* than `N`.

However, whether this is exploitable for actual transaction replay depends on the nonce check semantics in `verifier.rs`, which I was not able to fully confirm before running out of tool budget. In NEAR's protocol, `AddKey`/`DeleteKey` are themselves actions inside a signed transaction using an *existing* access key's nonce for authorization — the new key's nonce only governs *future* transactions signed with that (new) key. For a rollback-based replay to work, an attacker would need to have previously captured a validly-signed-but-executed transaction with nonce `M` such that `initial_nonce_value(block_height_of_recreation) < M <= N` (the old nonce before recreation), and then resubmit that exact old signed transaction after the key is recreated in the same or a later block with a low-enough `initial_nonce_value`. Because `initial_nonce_value` grows with block height and old signed transactions were, by construction, signed with a nonce that was valid (`> nonce_at_signing_time`), for the rollback to expose a replayable window, the new block's `initial_nonce_value(block_height)` must be less than or equal to some already-used nonce `M` from the old key incarnation — this requires the old key's nonce to have been pushed artificially high (via the `1e6 * height` per-recreation jump or via many closely-spaced transactions) relative to the new block height reached at deletion time, which is an edge case that needs a concrete quantitative confirmation against the actual nonce-comparison logic in `verifier.rs` (I was unable to inspect the exact comparison lines before the tool budget was exhausted).

### Impact Explanation
If exploitable, this would allow **replay of an old, already-executed transaction** against the recreated key — a double-spend/replay category impact (e.g., replaying an old `Transfer` or `FunctionCall` action), which matches the "double-spend/replay" bounty category. The severity is bounded by the fact that the attacker needs to control (or be) the account owner performing `DeleteKey`+`AddKey` in the same block, and needs a pre-existing signed transaction with a nonce in the vulnerable window — this is a self-inflicted scenario for a single account, not a cross-account authorization escalation, unless the recreated key is later trusted by a relying party (e.g., a meta-transaction relayer) expecting nonce monotonicity as a security property.

### Likelihood Explanation
Preconditions: attacker (account owner) needs (1) an existing access key already used up to a high nonce `N`, (2) to submit `DeleteKey` + `AddKey` for the same public key within the same block (fully achievable by an ordinary user via a single transaction with a batched action list), and (3) a previously-signed transaction with nonce `M` in the window `(initial_nonce_value(new_block_height), N]`. This is inexpensive and fully attacker-controlled, but the actual replay depends on details of the nonce-check comparator in `verifier.rs` (`>` vs `>=`, and whether nonces are also cross-checked against the delegate/meta-transaction nonce ranges) which I could not fully confirm in this session.

### Recommendation
Confirm the nonce-validation comparator in `runtime/runtime/src/verifier.rs` to determine the exact reachable window. If validated, make `add_regular_key`/`add_gas_key` set the new key's nonce to `max(initial_nonce_value(block_height), <nonce read from a tombstone/prior deletion record>)`, or block `AddKey` for a public key that was deleted earlier in the same block/transaction batch, or simply never allow nonce to decrease relative to any historical maximum for that `(account_id, public_key)` pair (would require persisting a per-key high-water-mark independent of the access key row lifecycle).

### Proof of Concept
Unit test in `runtime/runtime/src/access_keys.rs` tests module:
1. `setup_account` with a `FullAccess` key at `nonce = 0`.
2. Call `action_add_key` is not applicable for existing key (already present) — instead simulate the sequence: set the access key's nonce directly to a large `N` via `set_access_key` (simulating prior transaction usage), then call `action_delete_key` for that public key, then call `action_add_key` for the same public key at the same `block_height`.
3. Read back the access key via `get_access_key` and assert `access_key.nonce == initial_nonce_value(block_height)`, and separately assert this value is `< N`, demonstrating the nonce rollback and contradicting the `AccessKey::nonce` doc-comment guarantee.
4. (To fully confirm exploitability) extend to a `runtime/runtime/src/tests/apply.rs` integration test: submit a `Transaction` with `nonce = M` (where `initial_nonce_value(block_height) < M <= N`) signed by the recreated key, and assert whether it is accepted (would confirm actual replay) or rejected by `verifier.rs`'s nonce check — this final confirmation step was not completed due to tool-call budget exhaustion.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

fn add_gas_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    gas_key_info: &GasKeyInfo,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    // For gas keys, nonce stored on access key is not used and should always be zero
    let mut access_key = access_key.clone();
    access_key.nonce = 0;
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    // Set up nonces for gas key
    let num_nonces = gas_key_info.num_nonces;
    let nonce = initial_nonce_value(block_height);
    for i in 0..num_nonces {
        set_gas_key_nonce(state_update, account_id.clone(), public_key.clone(), i, nonce);
    }

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(gas_key_storage_cost(fee_config, public_key, &access_key, num_nonces))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
