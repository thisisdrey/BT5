### Title
Permanent freeze of ETH-implicit wallet accounts via gas-exhaustion in `WalletContract` callbacks stuck `has_in_flight_tx` lock - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
`WalletContract` (the contract deployed on every ETH-implicit account, cf. `docs/DataStructures/Account.md:121-129`) uses a boolean guard, `has_in_flight_tx`, to serialize execution the same way Uniswap V2's `lock` modifier serializes `swap()` calls in the referenced report. `rlp_execute` refuses to start a new transaction while `has_in_flight_tx == true` [1](#0-0) , and every callback that is supposed to release the lock does so as its very first statement, e.g. `self.has_in_flight_tx = false;` in `rlp_execute_callback`, `address_check_callback`, and `nep_141_storage_balance_callback` [2](#0-1) [3](#0-2) [4](#0-3) . On NEAR, contract state mutations are only committed if the function call finishes without panicking; if execution aborts (e.g. `GasExceeded`) after that line, the entire state diff for that receipt — including the `has_in_flight_tx = false` write — is discarded. The unlock callbacks are budgeted with small, fixed gas constants (`RLP_EXECUTE_CALLBACK_GAS = 5 Tgas`, etc., `lib.rs:34-41`) that do not scale with the size of the cross-contract call's return value, which is directly attacker-controllable when the wallet owner's signed action targets an arbitrary contract.

### Finding Description
1. `rlp_execute` sets `has_in_flight_tx = true` right before returning any promise chain, and treats `has_in_flight_tx == true` as "another tx is already running", rejecting any further calls until the flag is cleared [5](#0-4) .
2. For a normal `FunctionCall`/`Transfer` action to an arbitrary `target` chosen by the signed Ethereum transaction, `inner_rlp_execute`'s default branch attaches `rlp_execute_callback` with a hard-coded budget `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas), independent of the size of data the target contract may return: `action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))` [6](#0-5) .
3. `rlp_execute_callback` unconditionally clears the flag first, then reads `env::promise_result(0)` and, on success, copies the entire returned payload into `ExecuteResponse.success_value` and serializes it for the outer JSON response: `PromiseResult::Successful(value) => ExecuteResponse { success: true, success_value: Some(value), error: None }` [7](#0-6) .
4. Because the target contract is whatever the user's own signed Ethereum-style tx names (which can be a malicious/attacker-deployed contract, exactly as in the reported flash-loan example where an attacker-controlled pool/contract is on the other end of a call), an attacker can make that target return a large payload sized so that copying/serializing it inside the 5-Tgas callback budget causes the host to abort with `GasExceeded` before `self.has_in_flight_tx = false` can be durably committed.
5. Because NEAR only commits state changes for function calls that return successfully (a panicking/aborted call discards all of its state writes for that receipt), the previously-persisted `has_in_flight_tx = true` value survives forever. `rlp_execute` will now permanently return `"Error: transaction already in progress, please try again later."` for every future call, because the wallet contract itself cannot be redeployed, does not support obtaining a full access key, and cannot be deleted (per `docs/DataStructures/Account.md:121`).

This is the direct nearcore analog of the reported bug class: a lock/guard flag mirroring Uniswap V2's reentrancy `lock`, whose interaction with an external call under attacker influence produces an unrecoverable state rather than a simple revert.

### Impact Explanation
Once `has_in_flight_tx` is stuck at `true`, the ETH-implicit account can never again execute `rlp_execute`, which is the *only* entry point capable of moving funds out of, or acting on behalf of, that account (Transfer, FunctionCall, AddKey, DeleteKey all route exclusively through it, per `docs/DataStructures/Account.md:131-136`). Any $NEAR balance or NEP-141 tokens held by that account become permanently frozen — nobody, not even the legitimate owner holding the Secp256k1 private key, can move them again. This satisfies "permanent freezing of funds."

### Likelihood Explanation
The attack requires only that the wallet owner (or a relayer acting for them) sign a `FunctionCall`/generic action whose `target` is an attacker-controlled contract that returns an over-sized payload on success — a realistic scenario for phishing dApps or malicious integrations that eth-wallet users are induced to interact with, mirroring how the original report's victim interacts with an attacker-chosen pool/contract in the same transaction. No special privileges, validator/network access, or race conditions are needed; it is a standard `FunctionCall` executed through the documented `rlp_execute` path. The exact byte threshold at which `GasExceeded` triggers depends on runtime cost parameters (register read + serialization costs) that were not fully inspected within the available tool budget; verifying the precise payload size needed is left as an open item, but the vulnerable pattern (fixed callback gas independent of externally-returned payload size, plus early flag-clear-then-panic ordering) is unambiguous from the code.

### Recommendation
- Persist the "unlock" of `has_in_flight_tx` in a way that survives a subsequent gas-out, e.g. clear the flag in a separate, minimal-gas step performed *before* any gas-variable work (copying/serializing the promise result), or use `env::promise_return`/a fixed-size ack instead of forwarding arbitrary-sized payloads through `ExecuteResponse.success_value`.
- Scale (or cap) the gas forwarded to the caller-supplied action so the reserved callback gas budget (`RLP_EXECUTE_CALLBACK_GAS` and friends) always has enough headroom to safely process the worst-case `promise_result` size, or truncate/reject overly large successful results instead of copying them wholesale.
- Add a self-recovery/timeout mechanism (e.g. an owner-only or nonce-based "force unlock" path) so that even if the flag is stuck, the wallet is not bricked forever.

### Proof of Concept
1. Attacker deploys `EvilContract` with a method `big_return()` that, on success, returns a payload sized so that copying it into `ExecuteResponse.success_value` and JSON-serializing it inside `rlp_execute_callback`'s 5-Tgas budget triggers `GasExceeded` (size can be tuned against `max_length_returned_data`/per-byte gas costs in `core/parameters/src/cost.rs`).
2. Victim (or their relayer) signs an Ethereum-style tx encoding a `FunctionCall` action with `target = EvilContract`, `method_name = "big_return"`, and calls `rlp_execute` on their ETH-implicit `WalletContract`.
3. `rlp_execute` → `inner_rlp_execute` sets `has_in_flight_tx = true`, dispatches `action_to_promise(...).then(ext.rlp_execute_callback(...))` with `RLP_EXECUTE_CALLBACK_GAS` [6](#0-5) .
4. `EvilContract::big_return` succeeds and returns the oversized payload; `rlp_execute_callback` starts, executes `self.has_in_flight_tx = false;`, then attempts to copy/serialize the large `PromiseResult::Successful(value)` and runs out of gas before returning.
5. The callback receipt fails with `GasExceeded`; all its state changes (including the flag reset) are discarded, so the previously committed `has_in_flight_tx = true` remains in storage.
6. Any subsequent call to `rlp_execute` on this account now always hits the early-return branch and returns `"Error: transaction already in progress, please try again later."` [8](#0-7) , permanently freezing the account's funds.

        let predecessor_account_id = env::predecessor_account_id();

            predecessor_account_id,
            target,
            tx_bytes_b64,
            &mut self.nonce,
        );

            Ok(promise) => {
                self.has_in_flight_tx = true;
                PromiseOrValue::Promise(promise)

                PromiseOrValue::Promise(promise)
            }
            Err(e) => PromiseOrValue::Value(e.into()),
        }
    }

    pub fn rlp_execute_callback(
        &mut self,
        caller_deposit: Option<CallerDeposit>,
    ) -> ExecuteResponse {
        self.has_in_flight_tx = false;
        let n = env::promise_results_count();

        if n == 0 {
            // `rlp_execute_callback` is called directly in the case of an emulated self-transfer.
            return ExecuteResponse { success: true, success_value: None, error: None };
        } else if n > 1 {
            return ExecuteResponse {
                success: false,
                success_value: None,
                error: Some(format!(
                    "Invariant violation: this callback comes after a single promise. n={n}"
                )),
            };
        }

        match env::promise_result(0) {
            PromiseResult::Failed => {
                // The cross-contract call failed, refund the caller if needed
                if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit {
                    let refund_promise = env::promise_batch_create(&account_id);
                    env::promise_batch_action_transfer(
                        refund_promise,
                        NearToken::from_yoctonear(yocto_near.into()),
                    );
                }

                ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Failed Near promise".into()),
                }
            }
            PromiseResult::Successful(value) => {
                ExecuteResponse { success: true, success_value: Some(value), error: None }
            }
        }
