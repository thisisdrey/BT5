### Title
Missing array-size validation in `extractBytes32Array` allows unbounded/negative array allocation in the `BatchValidateSign` TVM precompile - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `sized-chunks` advisory concerns constructing a fixed-capacity array-backed structure (`Chunk`) from attacker-influenced length data without checking that the length is within the structure's actual bounds. The analogous pattern in java-tron is `PrecompiledContracts.extractBytes32Array`, which builds a `byte[len][]` array whose `len` is taken directly from attacker-controlled calldata with no upper-bound or non-negativity check, unlike its sibling helpers.

### Finding Description
`extractBytes32Array` reads the array length straight from the ABI-encoded word at `offset` and allocates a new array of that size with no bounds validation at all: [1](#0-0) 

Compare this to the sibling helpers `extractBytesArray` and `extractSigArray`, which at least guard `offset` against `words.length`: [2](#0-1) 

`extractBytes32Array` has neither this `offset` guard nor any check on `len` before `new byte[len][]` is executed.

This helper is invoked by the `BatchValidateSign` precompile (`0x…09`, reachable when `VMConfig.allowTvmSolidity059()` is enabled) to parse the caller-supplied `address[]` parameter, using an offset and length both taken directly from unvalidated calldata: [3](#0-2) 

There is a mitigating check under the `VMConfig.allowTvmSelfdestructRestriction()` feature flag that rejects `addrArraySize > MAX_SIZE` (16) before calling `extractBytes32Array`: [4](#0-3) 

However this guard only rejects values `> MAX_SIZE`; it does not reject negative lengths, so a crafted word whose `intValueSafe()` yields a negative int would pass this check (`-1 > 16` is false) and still reach `extractBytes32Array`, causing `new byte[len][]` to throw `NegativeArraySizeException`. I was unable to confirm within this pass whether `allowTvmSelfdestructRestriction()` is enabled by default on current mainnet (it is a committee-activated hardfork proposal); if it is not yet active for a given chain/testnet, `extractBytes32Array` is reached with a completely unbounded, attacker-chosen `len` (up to `Integer.MAX_VALUE`), which can trigger `new byte[len][]` allocation attempts large enough to exhaust the heap (`OutOfMemoryError`).

### Impact Explanation
`OutOfMemoryError`/large-array allocation attempts and `NegativeArraySizeException` are technically caught by the outer `try/catch (Throwable t)` in `execute()`: [5](#0-4) 
so a `NegativeArraySizeException` alone is low-impact (recovered, returns a zeroed 32-byte result). However, an `OutOfMemoryError` triggered by attempting to allocate a reference array sized by an attacker-controlled `int` up to `Integer.MAX_VALUE` is not reliably "caught and recovered" in a JVM — OOM conditions frequently destabilize concurrent threads/GC state process-wide and can lead to node crash/halt, satisfying the "node crash or halt" impact bar, but only on paths where the `MAX_SIZE` guard is bypassed or inactive.

### Likelihood Explanation
Reachability requires only a single unprivileged TVM contract call to precompile address `0x…09` (`batchValidateSign`), which is enabled via `VMConfig.allowTvmSolidity059()` — no special privilege is needed to invoke a precompile from a smart contract. The likelihood of full exploitation (uncapped huge allocation) hinges entirely on whether `allowTvmSelfdestructRestriction()` is active on the target network; I could not conclusively verify its current default/activation state from the available index, which limits confidence in exploitability on current mainnet. On networks/testnets where that hardfork parameter is still 0, the bug is fully unbounded and trivially reachable.

### Recommendation
Add the same defensive bound checks to `extractBytes32Array` as already exist in `extractBytesArray`/`extractSigArray` (`offset` vs. `words.length`), and additionally reject negative or over-`MAX_SIZE` lengths unconditionally (not only under the `allowTvmSelfdestructRestriction` flag) before allocating `new byte[len][]`.

### Proof of Concept
Craft ABI calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the length word for the `address[]` array (pointed to by the second dynamic offset, `words[2]`) is set to a very large positive value (e.g., `0x7fffffff`) or a value whose low 32 bits form a negative int when the network has `allowTvmSelfdestructRestriction` disabled (or is used against the unconditional path). Invoking this precompile via a `CALL`/`STATICCALL` from any contract triggers `extractBytes32Array` to execute `new byte[len][]` with the attacker-supplied `len`, without any prior bounds check, unlike the sibling `extractBytesArray`/`extractSigArray` helpers.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }
