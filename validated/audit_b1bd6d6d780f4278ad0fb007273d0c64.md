### Title
Praefect repository write-lock TTL expiry allows lock "theft" while the original holder still retains the real on‑disk Git ref lock, defeating write-serialization and causing repeated write failures (DoS) — (File: `internal/praefect/datastore/lock_manager.go`, `internal/praefect/transactions/manager.go`)

### Summary
The external report's bug class is "a resource that should have been invalidated on expiry is still usable, because the consumer only checks whether a *lease* was issued, not whether it is still valid at the time of use." Gitaly's Praefect write-serialization feature has the same shape: a PostgreSQL-backed lock with a hard-coded TTL is used as the *sole* proxy for "is the real Git reference lock still held," but the TTL is not actually coupled to completion of the underlying Git operation, so an in-flight (not crashed) writer can have its lock "stolen" by a second transaction while it is still physically holding the on-disk `*.lock` file for the same refs.

### Finding Description
`internal/praefect/transactions/manager.go`'s `lockRepoForTransaction` acquires the Postgres-backed lock at `PREPARING_PHASE` and renews it at `PREPARED_PHASE`/`COMMITTED_PHASE`: [1](#0-0) 

The renewal cadence is a fixed, hard-coded 20-second TTL, independent of how long the actual Git write takes: [2](#0-1) 

The acquire UPSERT explicitly allows a *different* transaction to take over a row whose `expired_at` has passed, even though the original holder may not have crashed and may still be executing: [3](#0-2) 

Per the documented write flow, by the time a node reaches `PREPARED_PHASE` it has **already taken the real, on-disk Git reference lock** and is only waiting on quorum/network round-trips before voting `Committed`: [4](#0-3) 

If that round-trip (or a slow client, large ref-update set, or a hook) causes the gap between `PREPARED_PHASE` and the next renew/`COMMITTED_PHASE` to exceed the 20s TTL, the Postgres lock is treated as abandoned and can be handed to a second transaction for the *same repository*, even though the first transaction is still physically holding the on-disk ref lock. This exact scenario is reproduced by the test harness itself: [5](#0-4) 

This is precisely the class of bug in the report: the system checks "has the lease/lock formally expired?" instead of "is the underlying resource actually still in use?" — allowing a second claimant in before the first has truly released it.

### Impact Explanation
The entire purpose of `internal/praefect/datastore/lock_manager.go` / the "serialized writes" feature (documented in `doc/serialized_writes.md`) is to prevent two Praefect-coordinated transactions from taking conflicting on-disk Git ref locks concurrently, which is documented as leading to a cross-node deadlock. When the TTL-based "steal" mechanism fires while the original holder is merely slow (not dead), a second, unrelated write from another ordinary user of the same repository is granted the global serialization token and proceeds to instruct its Gitaly nodes to take the very ref locks the first (still-alive) transaction holds. The result is repeated write failures/contention on that repository (an availability/DoS impact on the write-RPC handler), and it reintroduces the class of race the feature exists to eliminate, for any repository experiencing writes slower than the fixed 20s window (e.g., large pushes, slow hooks, or a deliberately slow-rolling client acting as an ordinary user).

### Likelihood Explanation
Reaching this path only requires performing an ordinary write RPC (e.g., a push) through Praefect against a repository — no special privileges are needed. The TTL is a fixed constant unrelated to the actual size/duration of the write, so any repository with pushes/hook executions occasionally exceeding ~20 seconds (or a client that intentionally paces its `VoteTransaction` calls to straddle the TTL boundary) can trigger the steal-while-still-held condition. The project's own test (`TestPraefectWriteSerialization_HangAfterPrepared`) demonstrates the mechanics are real and reachable, not merely theoretical.

### Recommendation
Do not let a Postgres row's `expired_at` alone determine that a lock is safe to steal. Instead, tie lock validity to liveness of the actual holder (e.g., require the holder to actively confirm release/abort before the row is reassigned, or make the renew interval track the real elapsed time of the reference-transaction hook rather than a fixed constant), and/or have `lockRepoForTransaction`'s `PREPARED_PHASE`/`COMMITTED_PHASE` renew failure path actively signal the still-running Git process to abort and release its on-disk lock before another transaction is allowed to proceed, closing the window where two holders can simultaneously believe they own the repository's write lock.

### Proof of Concept
1. Start a write RPC (`VoteTransaction`) for `txn1` through `PREPARING_PHASE` and `PREPARED_PHASE` (as in `TestPraefectWriteSerialization_HangAfterPrepared`), which acquires the lock and simulates the node having taken the real on-disk ref lock. [6](#0-5) 
2. Do not send `COMMITTED_PHASE` for `txn1` (simulating a hung/slow — not crashed — client/hook).
3. Let (or force, by back-dating) `expired_at` pass the TTL. [7](#0-6) 
4. Register `txn2` and call `VoteTransaction` with `PREPARING_PHASE` for the same repository — it succeeds immediately, "stealing" the lock while `txn1` may still resume and complete its write on the still-held on-disk lock. [8](#0-7)

```markdown
### Flow for one write

1. Client calls a write RPC against Praefect.
1. Praefect forwards the RPC to each Gitaly node in the replica set.
1. Each Gitaly node, in `UpdateReference` (or the equivalent write path),
   casts a `Preparing` vote **before** locking refs locally. The hook RPC
   reaches Praefect, which calls `lockRepoForTransaction(PREPARING_PHASE)`:
   `WriteLockManager.Lock` blocks until the per-repository lock is free.
1. Both nodes return from `Preparing` together (quorum reached).
1. Each Gitaly node locks refs on disk and votes `Prepared`. Praefect renews
   the lock.
1. Each Gitaly node writes the update and votes `Committed`. Praefect releases
   the lock.
```

```go
func TestPraefectWriteSerialization_HangAfterPrepared(t *testing.T) {
	t.Parallel()
	db := testdb.New(t)
	ctx := testhelper.Context(t)
	logger := testhelper.SharedLogger(t)
	repoWriteLockMgr := datastore.NewRepoReferenceWriteLockManager(ctx, db, testdb.GetConfig(t, db.Name), logger)

	storageName := "mock"
	relativePath := "hang/after/prepared.git"
	voters := []transactions.Voter{{Name: "primary", Votes: 1}}
	threshold := uint(1)

	cc, txMgr, cleanup := runPraefectServerAndTxMgrAndLockMgr(t, ctx, repoWriteLockMgr)
	defer cleanup()
	client := gitalypb.NewRefTransactionClient(cc)

	// Txn1: PREPARING + PREPARED, then "hang" (no COMMITTED)
	txn1, _, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	hash1 := sha1.Sum([]byte("txn1"))

	for _, phase := range []gitalypb.VoteTransactionRequest_Phase{
		gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE,
	} {
		_, err := client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
			TransactionId:        txn1.ID(),
			Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
			Node:                 voters[0].Name,
			ReferenceUpdatesHash: hash1[:],
			Phase:                phase,
		})
		require.NoError(t, err)
	}
	// Intentionally skip COMMITTED phase to simulate a stuck client.

	// Simulate lock expiry by back-dating the row
	_, err = db.ExecContext(ctx, `
          UPDATE repository_reference_write_locks
          SET expired_at = NOW() - INTERVAL '1 second'
          WHERE lock_id = $1`, storageName+"|"+relativePath)
	require.NoError(t, err)

	// Txn2: PREPARING should succeed (steals the expired lock)
	txn2, cancel2, err := txMgr.RegisterTransaction(ctx, voters, threshold)
	require.NoError(t, err)
	defer func() { require.NoError(t, cancel2()) }()
	hash2 := sha1.Sum([]byte("txn2"))

	_, err = client.VoteTransaction(ctx, &gitalypb.VoteTransactionRequest{
		TransactionId:        txn2.ID(),
		Repository:           &gitalypb.Repository{StorageName: storageName, RelativePath: relativePath},
		Node:                 voters[0].Name,
		ReferenceUpdatesHash: hash2[:],
		Phase:                gitalypb.VoteTransactionRequest_PREPARING_PHASE,
	})
	require.NoError(t, err)
}
```
