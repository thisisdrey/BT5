### Title
Pending Commission Queue Overwrite in `update_commission_percentage` Allows Operator to Bait-and-Switch Delegators — (`File: aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

`delegation_pool::update_commission_percentage` allows a pool owner to queue a new commission rate at any time within the first three-quarters of a lockup cycle, unconditionally overwriting any previously queued `NextCommissionPercentage`. The `MAX_COMMISSION_INCREASE` guard is evaluated against the **current** (already-active) commission, not the pending one. A malicious owner can therefore publicly advertise a low pending commission to attract delegators, then silently replace it with a much higher rate before the lockup cycle ends — an exact structural analog of the Berachef cutting-board queue-invalidation bug.

---

### Finding Description

`update_commission_percentage` stores a deferred commission change in the `NextCommissionPercentage` resource:

```
effective_after_secs = stake::get_lockup_secs(pool_address)   // current lockup expiry
commission_percentage_next_lockup_cycle = new_commission_percentage
``` [1](#0-0) 

The change is activated lazily inside `synchronize_delegation_pool` only when `is_next_commission_percentage_effective` returns true (i.e., `now_seconds >= effective_after_secs`): [2](#0-1) 

`is_next_commission_percentage_effective` is a simple timestamp comparison: [3](#0-2) 

The `MAX_COMMISSION_INCREASE` guard at line 1302 calls `operator_commission_percentage`, which returns the **pending** value only if it is already past `effective_after_secs`, and the **current** value otherwise: [4](#0-3) [5](#0-4) 

Because the guard is evaluated **before** `synchronize_delegation_pool` is called (line 1313), and because `synchronize_delegation_pool` only applies the pending change when the lockup has already expired, the guard never sees the pending lower rate during the same lockup cycle in which it was queued. [6](#0-5) 

**Attack sequence:**

| Step | Action | State |
|------|--------|-------|
| 1 | Owner calls `update_commission_percentage(500)` (5%) | `NextCommissionPercentage { 500, T1 }` |
| 2 | Delegators observe `operator_commission_percentage_next_lockup_cycle` = 5% and add stake | Delegators locked in |
| 3 | Owner calls `update_commission_percentage(2000)` (20%) while `remaining_lockup >= lockup/4` | Guard checks current rate (10%), passes: `1000 + 1000 >= 2000` |
| 4 | `synchronize_delegation_pool` runs but `now < T1`, so pending 5% is **not** applied | |
| 5 | `NextCommissionPercentage` is overwritten: `{ 2000, T1 }` | |
| 6 | Lockup cycle ends at T1 | 20% activates instead of 5% |

The `ETOO_LATE_COMMISSION_CHANGE` guard only blocks changes in the **last quarter** of the lockup cycle; it does not prevent overwriting a pending change in the first three-quarters. [7](#0-6) [8](#0-7) 

---

### Impact Explanation

Delegators who added stake based on the publicly visible `operator_commission_percentage_next_lockup_cycle` view will have their staking rewards silently redirected to the operator at a rate up to `current_commission + MAX_COMMISSION_INCREASE` (up to 10 percentage points higher than the advertised pending rate). This is a direct, material reduction of delegator staking balances — a financial loss proportional to the total active stake in the pool and the commission delta, sustained for the entire next lockup cycle (months on mainnet).

`MAX_COMMISSION_INCREASE` is 1000 basis points (10%): [9](#0-8) 

---

### Likelihood Explanation

- The pool owner is an unprivileged on-chain account; no governance or admin assumption is required.
- The attack requires only two ordinary `update_commission_percentage` entry-function calls within the same lockup cycle.
- The victim action (delegators adding stake) is the normal, expected behavior when a favorable pending commission is advertised.
- The `operator_commission_percentage_next_lockup_cycle` view function is public and indexed by wallets and dashboards, making the bait credible. [10](#0-9) 

---

### Recommendation

Apply the `MAX_COMMISSION_INCREASE` cap against the **pending** commission percentage (i.e., `commission_percentage_next_lockup_cycle` from `NextCommissionPercentage` if it exists and is not yet effective), not the currently active one. Alternatively, mirror the Berachef fix: abort if a `NextCommissionPercentage` already exists and has not yet been applied (i.e., `effective_after_secs` is in the future), preventing any overwrite of a queued-but-not-yet-activated commission change.

Concretely, replace the guard at line 1302 with a check against `operator_commission_percentage_next_lockup_cycle(pool_address)` when a pending change exists and is not yet effective.

---

### Proof of Concept

```move
// Pseudocode — all calls are public entry functions, no privileges required.

// Setup: pool with 10% commission (1000 bps), lockup = 30 days.
initialize_delegation_pool(owner, 1000, seed);
// owner == operator for simplicity

// Step 1: Advertise a low commission for next cycle.
// remaining_lockup = 30 days >= 30/4 = 7.5 days  ✓
update_commission_percentage(owner, 500);  // queue 5%
// NextCommissionPercentage { commission_percentage_next_lockup_cycle: 500,
//                            effective_after_secs: T1 }

// Step 2: Delegators observe operator_commission_percentage_next_lockup_cycle() == 500
//         and add large stake.
add_stake(delegator, pool_address, 1_000_000 * ONE_APT);

// Step 3: 10 days later (20 days remaining > 7.5 day threshold).
timestamp::fast_forward_seconds(10 * 86400);

// Step 4: Owner overwrites the pending 5% with 20%.
// operator_commission_percentage() == 1000 (current, T1 not reached)
// guard: 1000 + 1000 >= 2000  ✓
// synchronize_delegation_pool: now < T1, pending 5% NOT applied
// NextCommissionPercentage overwritten: { 2000, T1 }
update_commission_percentage(owner, 2000);  // overwrite to 20%

// Step 5: Lockup cycle ends.
timestamp::fast_forward_seconds(20 * 86400);
end_aptos_epoch();

// Result: operator_commission_percentage() == 2000 (20%), not 500 (5%).
// Delegators pay 15 percentage points more commission than advertised.
assert!(operator_commission_percentage(pool_address) == 2000, 0);
```

The corrupted on-chain value is `NextCommissionPercentage.commission_percentage_next_lockup_cycle` at the pool's resource account address, overwritten from `500` to `2000` without delegator consent and in violation of the invariant that `MAX_COMMISSION_INCREASE` is measured from the most recently queued rate.     public entry fun update_commission_percentage(
        owner: &signer,
        new_commission_percentage: u64
    ) acquires DelegationPoolOwnership, DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
        assert!(new_commission_percentage <= MAX_FEE, error::invalid_argument(EINVALID_COMMISSION_PERCENTAGE));
        let owner_address = signer::address_of(owner);
        let pool_address = get_owned_pool_address(owner_address);
        assert!(
            operator_commission_percentage(pool_address) + MAX_COMMISSION_INCREASE >= new_commission_percentage,
            error::invalid_argument(ETOO_LARGE_COMMISSION_INCREASE)
        );
        assert!(
            stake::get_remaining_lockup_secs(pool_address) >= min_remaining_secs_for_commission_change(),
            error::invalid_state(ETOO_LATE_COMMISSION_CHANGE)
        );

        // synchronize delegation and stake pools before any user operation. this ensures:
        // (1) the operator is paid its uncommitted commission rewards with the old commission percentage, and
        // (2) any pending commission percentage change is applied before the new commission percentage is set.
        synchronize_delegation_pool(pool_address);

        if (exists<NextCommissionPercentage>(pool_address)) {
            let commission_percentage = borrow_global_mut<NextCommissionPercentage>(pool_address);
            commission_percentage.commission_percentage_next_lockup_cycle = new_commission_percentage;
            commission_percentage.effective_after_secs = stake::get_lockup_secs(pool_address);
        } else {
            let delegation_pool = borrow_global<DelegationPool>(pool_address);
            let pool_signer = account::create_signer_with_capability(&delegation_pool.stake_pool_signer_cap);
            move_to(&pool_signer, NextCommissionPercentage {
                commission_percentage_next_lockup_cycle: new_commission_percentage,
                effective_after_secs: stake::get_lockup_secs(pool_address),
            });
        };

        event::emit(CommissionPercentageChange {
            pool_address,
            owner: owner_address,
            commission_percentage_next_lockup_cycle: new_commission_percentage,
        });
    }
