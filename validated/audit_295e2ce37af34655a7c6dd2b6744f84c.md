### Title
Unchecked long-arithmetic overflow in Exchange pool balance updates enables value extraction via corrupted AMM ratios - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeWithdrawActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator` compute pool balance updates for TRON's bancor-style `Exchange`/`ExchangeV2` AMM using plain, unchecked `long` arithmetic (`x + y` / `x - y`) whenever the chain parameter `ALLOW_HARDEN_EXCHANGE_CALCULATION` is `0`, which is the default/current on-chain value. Only when this SR-governed proposal is explicitly activated does the code switch to overflow-checked `Math.addExact`/`subtractExact` equivalents. Any unprivileged account can create an exchange pool for a self-issued TRC10 asset and drive one side of the pool near `Long.MAX_VALUE` via repeated `ExchangeInjectContract` calls, causing a silent overflow/wraparound of the stored pool balance. Because the withdraw/trade math (`ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) divides by these balances to compute the counter-asset amount, a corrupted (wrapped/negative) balance yields mathematically incorrect payouts, letting the attacker extract disproportionate value from the pool.

### Finding Description
`AbstractExchangeActuator.subtractExact`/`addExact` gate overflow-checking behind the `allowHarden()` flag: [1](#0-0) 

`DynamicPropertiesStore.getAllowHardenExchangeCalculation()` defaults to `0` (`orElse(0L)`) when unset, and `allowHardenExchangeCalculation()` only returns `true` for value `1`: [2](#0-1) 

The unit test `testAllowHardenExchangeCalculationProposal` explicitly documents "current value is 0 (default)" and that it requires an SR committee proposal (gated behind `ForkBlockVersionEnum.VERSION_4_8_2`) to enable: [3](#0-2) 

In `ExchangeWithdrawActuator.execute()`, pool balances are updated via `subtractExact`, which — with hardening disabled — is only `x - y` (no overflow guard), and the withdrawn `anotherTokenQuant` is derived from a ratio of the pool's `firstTokenBalance`/`secondTokenBalance`: [4](#0-3) 

A companion test, `hardenedAddExactOverflowThrows`, demonstrates that the exchange pool balance can be driven to `Long.MAX_VALUE - N` and that an inject operation overflows — but the test only asserts the `ArithmeticException` is thrown when hardening is explicitly turned on, implying the overflow is otherwise silently produced (wraps to a negative/wrong `long`) in the default configuration: [5](#0-4) 

Any address can become an exchange pool "creator" (an unprivileged asset issuer) by issuing a TRC10 token and calling `ExchangeCreateContract`, then repeatedly calling `ExchangeInjectContract` to inflate a chosen token's balance in the pool it controls. Once a pool-side balance overflows/wraps due to unchecked `long` addition, later `ExchangeWithdrawContract`/`ExchangeTransactionContract` operations compute exchange ratios against the corrupted balance, producing incorrect (and exploitable) payout amounts — this is directly analogous to the SwissBorg incident, where flawed backend accounting/validation logic (rather than a private-key compromise) let an attacker extract far more value than legitimately owed from a balance-tracking system.

### Impact Explanation
An attacker fully controlling one side of a self-created liquidity pool can corrupt that pool's tracked balances through unchecked integer arithmetic, then leverage the corrupted ratio to make `ExchangeWithdrawActuator`/`ExchangeTransactionActuator` credit the attacker's account with TRX or TRC10 tokens disproportionate to what was actually deposited into the pool. Because `Commons.putExchangeCapsule` persists whatever (possibly wrapped/negative) values result, this represents creation of unbacked balance / theft of value from the accounting system, meeting the "unbacked balance" bar for Critical/High impact even though it requires the attacker to first fund/inflate their own pool (an unprivileged, permissionless sequence of signed transactions).

### Likelihood Explanation
`ALLOW_HARDEN_EXCHANGE_CALCULATION` is off by default and can only be turned on by an SR committee proposal — meaning the unchecked-arithmetic code path is the currently active behavior on any network that has not passed this proposal. Exploitation requires only standard, unprivileged transactions (`AssetIssueContract`, `ExchangeCreateContract`, repeated `ExchangeInjectContract`, `ExchangeWithdrawContract`/`ExchangeTransactionContract`) available to any funded account — no special permissions, witness/SR status, or off-chain compromise needed.

### Recommendation
Make the overflow-checked arithmetic (`StrictMathWrapper.addExact`/`subtractExact`) unconditional in `AbstractExchangeActuator`, `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator`, rather than gating it behind the `allowHarden()` chain parameter. Additionally, replace the double-precision "Not precise enough" tolerance check in `ExchangeWithdrawActuator.doValidate()` with the `BigDecimal`-based (hardened) computation unconditionally, since floating-point rounding in the tolerance check can itself mask precision-loss abuse.

### Proof of Concept
Not independently executed; based on static analysis of the following sequence, which is reachable purely through signed transactions from an unprivileged account:
1. Issue a TRC10 token with a very large total supply via `AssetIssueContract`.
2. Create an exchange pool pairing this token with TRX via `ExchangeCreateContract` (attacker is the pool `creator`).
3. Repeatedly call `ExchangeInjectContract` to push the custom-token side of the pool balance toward `Long.MAX_VALUE`, causing `addExact`/`addExact`-equivalent unchecked `long` addition to overflow/wrap (confirmed feasible by the `hardenedAddExactOverflowThrows` test setup, which manually sets pool balance to `Long.MAX_VALUE - 10L`).
4. With the pool balance now wrapped to a small/negative value, call `ExchangeWithdrawContract` or `ExchangeTransactionContract`; the ratio-based payout calculation (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`) against the corrupted balance yields an incorrect `anotherTokenQuant`, allowing extraction of TRX/token value disproportionate to genuine deposits.

I was not able to execute this against a live node/test harness to confirm the exact overflow trigger values and final extracted amount; this should be validated with a concrete reproduction (e.g., a JUnit test mirroring `hardenedAddExactOverflowThrows` but asserting the *unhardened* silent-wraparound outcome and the resulting incorrect withdrawal amount) before remediation.
