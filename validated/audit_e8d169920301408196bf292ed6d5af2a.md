## Title
Missing `supportUnfreezeDelay` committee-gate check in TVM native resource-delegation processors bypasses the equivalent check enforced by the transaction-level actuators - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java] / [File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java])

### Summary
The transaction-level `DelegateResourceActuator` and `UnDelegateResourceActuator` both gate execution with two committee-controlled feature checks: `dynamicStore.supportDR()` and `dynamicStore.supportUnfreezeDelay()`. Their TVM-native counterparts, `DelegateResourceProcessor` and `UnDelegateResourceProcessor` (invoked from smart contracts via the DELEGATERESOURCE/UNDELEGATERESOURCE opcodes), only check `supportDR()` and omit the `supportUnfreezeDelay()` check, mirroring the "missing modifier" pattern described in the external report where certain functions omit a pause/feature-gate check that sibling functions enforce.

### Finding Description
`DelegateResourceActuator.validate()` requires both: [1](#0-0) 

`UnDelegateResourceActuator.validate()` mirrors this with the same two checks: [2](#0-1) 

However, `DelegateResourceProcessor.validate()`, which is executed when a smart contract invokes the native "delegate resource" functionality from inside the TVM, only checks `supportDR()`: [3](#0-2) 

Similarly, `UnDelegateResourceProcessor.validate()` also only checks `supportDR()`, without the `supportUnfreezeDelay()` gate: [4](#0-3) 

I was unable to fully confirm within the available tool budget whether the `DELEGATERESOURCE`/`UNDELEGATERESOURCE` TVM opcodes are additionally gated elsewhere (e.g., in `OperationRegistry.java` or `VMConfig`) by a flag that is set only when `UNFREEZE_DELAY_DAYS`/`supportUnfreezeDelay` is enabled, which would make this a non-issue in practice. The grep results show `DelegateResourceProcessor`/`UnDelegateResourceProcessor` are referenced from `Program.java`, `VMActuator.java`, and `OperationRegistry.java`, but I could not verify the opcode-availability gating logic before the iteration budget ran out. This uncertainty must be resolved by reading `Program.java`'s DELEGATERESOURCE/UNDELEGATERESOURCE opcode handlers and `OperationRegistry.java` to confirm whether they independently check `supportUnfreezeDelay`/`VMConfig.allowTvmFreeze()` before invoking these processors.

### Impact Explanation
If the TVM opcode path is not independently gated by an equivalent `supportUnfreezeDelay` check, a smart contract could delegate/undelegate TRX resources (bandwidth/energy) via the native contract path even when the committee has not enabled the "unfreeze delay" feature (`UNFREEZE_DELAY_DAYS` / `supportUnfreezeDelay`), which governs the resource-delegation/lock semantics that the transaction-level actuators depend on for correctness (e.g., correct handling of `lockPeriod`, delegated balance bookkeeping tied to the V2 freeze/unfreeze model). This could allow inconsistent resource-delegation state to be created on-chain via contract calls before the feature is formally activated by governance, potentially leading to inconsistent accounting of delegated frozen balances between actuator-driven and TVM-driven paths.

### Likelihood Explanation
Reachable by any account that can deploy or call a smart contract invoking the DELEGATERESOURCE/UNDELEGATERESOURCE native contract opcode — no special privilege required, only normal contract-call feature energy/fee. The likelihood that this is exploitable depends entirely on whether the opcode dispatch layer (`Program.java`/`OperationRegistry.java`) independently enforces the `supportUnfreezeDelay` gate; this was not conclusively verified.

### Recommendation
Add the same `if (!dynamicStore.supportUnfreezeDelay()) { throw new ContractValidateException(...); }` check to `DelegateResourceProcessor.validate()` and `UnDelegateResourceProcessor.validate()` that already exists in `DelegateResourceActuator.validate()` and `UnDelegateResourceActuator.validate()`, ensuring TVM-triggered resource delegation is gated by the same committee-controlled feature flag as the transaction-level actuators. Alternatively, if the opcode registration itself is already conditioned on `supportUnfreezeDelay`, no code change is needed here — but confirmation via `Program.java`/`OperationRegistry.java` is required before dismissing this.

### Proof of Concept
1. Deploy a smart contract that calls the native TVM opcode responsible for `DELEGATERESOURCE` / `UNDELEGATERESOURCE` (surfaced via `Program.java` opcode dispatch, ultimately invoking `DelegateResourceProcessor`/`UnDelegateResourceProcessor`).
2. On a network/testnet where the committee has enabled `ALLOW_DELEGATE_RESOURCE` (`supportDR()` = true) but has NOT enabled `UNFREEZE_DELAY_DAYS` (`supportUnfreezeDelay()` = false).
3. Call the contract to trigger resource delegation/undelegation.
4. Compare with calling `DelegateResourceContract`/`UnDelegateResourceContract` directly as a normal transaction, which is rejected with `"Not support Delegate resource transaction, need to be opened by the committee"` (see `DelegateResourceActuatorTest.testSupportUnfreezeDelay`): [5](#0-4) 
5. If the TVM-path call in step 3 succeeds (no equivalent rejection), this confirms the missing-gate bypass.
