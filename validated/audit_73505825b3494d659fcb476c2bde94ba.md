Audit Report

## Title
UMP queue capacity check race in elastic-scaling: sibling candidates of the same para bypass `max_upward_queue_count` - (File: `polkadot/runtime/parachains/src/inclusion/mod.rs`)

## Summary
`Inclusion::check_upward_messages` bounds a para's UMP queue by reading the live `MessageQueue::footprint` as the baseline and adding only the current candidate's message count, but this footprint is not updated until a candidate becomes *available* and is enacted via `receive_upward_messages`. Because `process_candidates` iterates all backed candidates for a para (as populated by elastic scaling's multiple cores per `ParaId` in one relay block) in a plain loop without incrementing any running counter between iterations, every sibling candidate is checked against the same stale baseline, allowing their combined UMP message counts to exceed `max_upward_queue_count`/`max_upward_queue_size` once all are later enacted.

## Finding Description
The check reads a live, unmutated snapshot: [1](#0-0) 

`relay_dispatch_queue_size` performs a direct `MessageQueue::footprint` read with no local accumulator: [2](#0-1) 

This check is invoked per-candidate from `verify_backed_candidate`/`check_validation_outputs`, which is itself called inside `process_candidates`'s `for (candidate, core) in para_candidates.iter()` loop — a loop that can process multiple candidates for the *same* `para_id` on multiple cores in the same relay block (elastic scaling), with no footprint mutation between iterations: [3](#0-2) 

The actual enqueue (commit) step only happens later, when a candidate becomes *available* and is enacted: [4](#0-3) 

`receive_upward_messages` is explicitly documented as "infallible" — it assumes admission was already correctly enforced at backing time, which is precisely the check shown above that reuses a stale baseline across sibling candidates. Consequently, N sibling candidates for the same para, each individually satisfying `para_queue_count + additional_msgs <= max_upward_queue_count` against the *same* unmodified `para_queue_count`, can collectively push the enacted queue count/size above the configured caps once each becomes available and is enacted.

## Impact Explanation
This bypasses `config.max_upward_queue_count`/`max_upward_queue_size` in `HostConfiguration`, which exist to bound the cost of servicing a para's UMP queue and protect against message-queue resource exhaustion. Exceeding this bound is the "public underpriced work that degrades block production" class of impact — the queue can grow beyond its intended, fee/weight-accounted size for a given para without any check ever rejecting it, since no single per-candidate check ever observes the sibling contributions.

## Likelihood Explanation
Exploitability only requires an elastic-scaling-enabled para (multiple cores assigned to one `ParaId` in the same relay block, an explicitly supported and tested scheduling pattern) and normal backing of its own chained candidates — no malicious validator, collator, or governance action is required beyond the para operating within its normal, permissionless message-emission rights. This is a straightforward, code-provable admission-control gap rather than a hypothetical or contrived scenario.

## Recommendation
Track a running per-`ParaId` UMP count/size accumulator across the `process_candidates` loop (or across `check_upward_messages` calls within the same block) that starts at the live footprint and is incremented after each sibling candidate is provisionally accepted, so that each subsequent candidate for the same para is checked against the cumulative in-block total rather than the stale, pre-block footprint.

## Proof of Concept
1. Enable elastic scaling for a para with multiple cores assigned in one relay block (as in `include_backed_candidates_elastic_scaling` in `polkadot/runtime/parachains/src/paras_inherent/tests.rs`).
2. Set `max_upward_queue_count = N` with the para's current queue footprint near `N - k`.
3. Produce `m` chained candidates for that para in one block, each individually within `max_upward_message_num_per_candidate` and each passing `check_upward_messages` (since each is checked against the same unadvanced `para_queue_count`), but whose sum exceeds `k`.
4. Submit all `m` backed candidates together; `process_candidates` admits all of them to `PendingAvailability`.
5. As each becomes available in subsequent blocks, `enact_candidate` → `receive_upward_messages` unconditionally enqueues its messages, driving the UMP queue count/size for that para above `max_upward_queue_count`/`max_upward_queue_size`.

	pub(crate) fn receive_upward_messages(para: ParaId, upward_messages: &[Vec<u8>]) {
		let bounded = skip_ump_signals(upward_messages.iter())
			.filter_map(|d| {
				BoundedSlice::try_from(&d[..])
					.inspect_err(|_| {
						defensive!("Accepted candidate contains too long msg, len=", d.len());
					})
					.ok()
			})
			.collect();
		Self::receive_bounded_upward_messages(para, bounded)
	}

	/// Enqueues storage-bounded `upward_messages` from a `para`'s accepted candidate block.
	pub(crate) fn receive_bounded_upward_messages(
		para: ParaId,
		messages: Vec<BoundedSlice<'_, u8, MaxUmpMessageLenOf<T>>>,
	) {
		let count = messages.len() as u32;
		if count == 0 {
			return;
		}

		T::MessageQueue::enqueue_messages(
			messages.into_iter(),
			AggregateMessageOrigin::Ump(UmpQueueId::Para(para)),
		);
		Self::deposit_event(Event::UpwardMessagesReceived { from: para, count });
	}
