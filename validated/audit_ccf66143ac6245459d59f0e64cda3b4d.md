### Title
HTTP request preamble parser ignores `Transfer-Encoding` entirely, enabling CL.TE request smuggling when a Content-Length-only body-framing decision diverges from any front-end proxy that honors `Transfer-Encoding` - (File: `stackslib/src/net/http/request.rs`)

### Summary
The reported GHSA-6jqf-mv7m-3q7p bug class is a framing-equality violation: a server accepts a non-canonical chunk terminator, letting an upstream/downstream pair disagree about where a request body ends, enabling smuggling. This repository's HTTP request preamble parser has the analogous equality break: it computes body length exclusively from `Content-Length` and never inspects or rejects a `Transfer-Encoding` header on requests, unlike its own response-parsing path, which explicitly detects and rejects the conflicting-headers case.

### Finding Description
`HttpRequestPreamble::consensus_deserialize` in `stackslib/src/net/http/request.rs` iterates over all request headers and only recognizes `host`, `content-type`, `content-length`, `connection`, and `set-cookie` as special: [1](#0-0) 
Any `Transfer-Encoding` header supplied on a request simply falls into the generic `headers` bucket and is silently stored/ignored — there is no code path that rejects, or even reads, `transfer-encoding` for requests.

Contrast this with the response-preamble parser in `stackslib/src/net/http/response.rs`, which explicitly recognizes `transfer-encoding: chunked` and rejects the message if both `Content-Length` and chunked `Transfer-Encoding` are present: [2](#0-1) 

The request body length actually consumed by the connection state machine is derived solely from `Content-Length` via `payload_len()`/`get_content_length()`: [3](#0-2) 
and again in `read_payload` for the request arm, which reads exactly `len = http_request_preamble.get_content_length()` bytes as the whole body: [4](#0-3) 

This is the same class of bug as the reported advisory: the node's belief about "where does this HTTP message end" is decided purely by `Content-Length`, while a `Transfer-Encoding: chunked` header — which per RFC 7230 §3.3.3 must take precedence over `Content-Length` and should cause any ambiguous message to be rejected outright — is not consulted at all for requests. If a reverse proxy/load balancer placed in front of a Stacks node (a supported and common deployment topology for its RPC/P2P HTTP surface) chooses to honor `Transfer-Encoding` per spec while this node honors `Content-Length`, the two parties disagree on request boundaries (classic CL.TE desync), letting an attacker prepend/smuggle a second, attacker-chosen request that the backend node will process as if it came from the trusted proxy — an equality break between "bytes the proxy believes it forwarded" and "bytes this node treats as the request".

### Impact Explanation
This maps directly to the "Critical – request smuggling or auth bypass" bucket. A successful smuggling attack lets a remote, unauthenticated attacker desynchronize the proxy/node request stream, causing subsequent legitimate requests (potentially from other clients sharing the same proxy connection pool) to be misrouted, or letting the attacker inject requests that appear to originate from the proxy's trusted IP, bypassing IP-based ACLs typically used to protect internal node RPC endpoints.

### Likelihood Explanation
Exploitability depends on deployment topology: it requires a front-end component (proxy/load balancer) in the same request path that treats `Transfer-Encoding: chunked` as authoritative when it conflicts with `Content-Length`. Many common proxies (older nginx/Envoy/HAProxy configurations) exhibit exactly this behavior when not configured with modern smuggling protections. Given Stacks nodes' HTTP RPC/API surface is frequently placed behind reverse proxies in production and mining infrastructure, this is a realistic remote, unauthenticated precondition, though it is proxy-configuration-dependent rather than purely intrinsic to this node in isolation.

### Recommendation
- In `HttpRequestPreamble::consensus_deserialize`, explicitly detect a `transfer-encoding` header on requests.
- If present, either reject the request outright (safe default, matching the response-side rejection of conflicting `Content-Length`/`Transfer-Encoding`), or implement full chunked-request decoding and forbid simultaneous `Content-Length` + `Transfer-Encoding`, mirroring the check already present in `stackslib/src/net/http/response.rs` lines 575-580.
- Add an explicit test analogous to `test_http_request_type_codec_err` covering a request with both headers set.

### Proof of Concept
1. Deploy a Stacks node's HTTP API behind a reverse proxy that prioritizes `Transfer-Encoding` over `Content-Length` when both are present (default behavior for several proxy versions absent smuggling hardening).
2. Send to the proxy:
```
POST /v2/transactions HTTP/1.1
Host: victim
Content-Length: 6
Transfer-Encoding: chunked

0

SMUGGLED_REQUEST_LINE...
```
3. The proxy, honoring `Transfer-Encoding`, forwards the chunked-terminated (empty) body plus treats "SMUGGLED_REQUEST_LINE..." as the start of a new pipelined request. The Stacks node, however, ignores `Transfer-Encoding` (as shown in `request.rs`) and reads only `Content-Length: 6` bytes — pulling `0\r\n\r\n` as body and treating the remaining smuggled bytes as the next request, which is then processed as if legitimately received on that trusted connection.
