### Title
Self-destructing contract's not-yet-expired unfrozen (locked) TRX is silently deleted instead of transferred to the inheritor - ([File: actuator/src/main/java/org/tron/core/vm/program/Program.java])

### Summary
This is a structural analog of the reported `CollateralPool.merge` bug: when balances/positions are moved from one account/pool to another, a withdrawal-limit/lock state associated with those balances is dropped instead of being carried over. In java-tron, this occurs during TVM contract self-destruct (`SUICIDE`/`SUICIDE2`), where a contract's FreezeV2 state is merged into an inheritor account.

### Finding Description
When a TVM contract self-destructs, `Program.suicide`/`suicide2` invoke `transferFrozenV2BalanceToInheritor` to migrate the owner's FreezeV2 resource state to the inheritor (or the black hole address) [1](#0-0) .

Inside that method, only unfrozen entries whose `unfreezeExpireTime` has already passed (`<= nowTimestamp`) are summed and credited to the inheritor's spendable balance: [2](#0-1) 

Any `UnFreezeV2` entries that are **not yet expired** — i.e., TRX that the owner had already unfrozen but which is still under the `unfreezeDelayDays` withdrawal-lock period — are neither transferred to the inheritor's own `unfrozenV2` list nor credited to any balance. Instead, immediately afterward `clearOwnerFreezeV2(ownerCapsule)` is called, which unconditionally wipes the owner's entire `unfrozenV2` list via `ownerCapsule.clearUnfrozenV2()`: [3](#0-2) 

This is the mirror image of the reported bug: instead of ignoring a withdrawal limit to allow early/unauthorized withdrawal, here the withdrawal-limit state (the pending unfreeze record) is discarded entirely without ever crediting the corresponding value anywhere, causing a permanent loss of those funds. The other FreezeV2 fields (`frozenV2` amounts) are correctly summed into the inheritor via `addFrozenBalanceForBandwidthV2`/`addFrozenBalanceForEnergyV2`/`addFrozenForTronPowerV2`, but this transfer logic was never applied to the still-locked entries in `unfrozenV2List`, which is instead just cleared.

### Impact Explanation
Any account can trigger this by deploying a contract, freezing TRUE for resources with `FreezeBalanceV2`, unfreezing it with `UnfreezeBalanceV2` (which places it into the locked/pending `unfrozenV2` list for `unfreezeDelayDays`), and then executing a self-destruct opcode before the unfreeze delay elapses. The locked TRX amount is permanently deleted from the system — it disappears from both the owner and the inheritor, resulting in an irrecoverable loss of user funds (unbacked total supply reduction), reachable purely through normal smart-contract execution (`SUICIDE`/`SUICIDE2` opcode), no privileged role required.

### Likelihood Explanation
This requires only a standard deployed contract and a standard sequence of `FreezeBalanceV2Contract` → `UnfreezeBalanceV2Contract` → contract self-destruct within the unfreeze-delay window (currently configured to multiple days by `unfreezeDelayDays`), all of which are ordinary, unprivileged operations available to any TVM contract deployer/caller when `allowTvmFreezeV2` is enabled.

### Recommendation
In `transferFrozenV2BalanceToInheritor`, before clearing the owner's `unfrozenV2` list, transfer all not-yet-expired `UnFreezeV2` entries to the inheritor's own `unfrozenV2` list (preserving their `unfreezeExpireTime` and `type`), analogous to how `frozenV2` balances are merged, so the lock/withdrawal-limit semantics are preserved across the account merge instead of being deleted.

### Proof of Concept
1. Deploy a contract `C`, fund it with TRX.
2. From `C`, call `FreezeBalanceV2Contract` to freeze e.g. 1000 TRX for BANDWIDTH.
3. From `C`, call `UnfreezeBalanceV2Contract` for that 1000 TRX — this creates an `UnFreezeV2` entry with `unfreezeExpireTime = now + unfreezeDelayDays * FROZEN_PERIOD` (not yet expired) [4](#0-3) .
4. Immediately (before the delay elapses) have `C` execute `SUICIDE`/`SUICIDE2` to an inheritor address.
5. Observe that `transferFrozenV2BalanceToInheritor` computes `expireUnfrozenBalance = 0` (since the entry hasn't expired) so nothing is credited to the inheritor [2](#0-1) , yet `clearOwnerFreezeV2` clears the owner's `unfrozenV2` list containing that 1000 TRX entry [3](#0-2) .
6. The 1000 TRX is now unrecoverable — it is not on the owner (deleted account), not on the inheritor, and not in any unfrozen/frozen list anywhere.

  public long calcUnfreezeExpireTime(long now) {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    long unfreezeDelayDays = dynamicStore.getUnfreezeDelayDays();

    return now + unfreezeDelayDays * FROZEN_PERIOD;
  }

  public void updateAccountFrozenInfo(ResourceCode freezeType, AccountCapsule accountCapsule, long unfreezeBalance) {
    List<FreezeV2> freezeV2List = accountCapsule.getFrozenV2List();
    for (int i = 0; i < freezeV2List.size(); i++) {
      if (freezeV2List.get(i).getType().equals(freezeType)) {
        FreezeV2 freezeV2 = FreezeV2.newBuilder()
            .setAmount(freezeV2List.get(i).getAmount() - unfreezeBalance)
            .setType(freezeV2List.get(i).getType())
            .build();
        accountCapsule.updateFrozenV2List(i, freezeV2);
        break;
      }
    }
  }
