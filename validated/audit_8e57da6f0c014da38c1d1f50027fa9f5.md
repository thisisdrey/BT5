### Title
DelegateResourceActuator/UnDelegateResourceActuator do not accrue pending vote reward before mutating an account's frozen/delegated balance - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
`UnfreezeBalanceActuator` and `UnfreezeBalanceV2Actuator` both invoke `mortgageService.withdrawReward(ownerAddress)` as the very first step of `execute()` before mutating the account's frozen balance, precisely so that any pending vote reward is settled against the account's *current* (pre-mutation) frozen/vote state. [1](#0-0) [2](#0-1) 

`DelegateResourceActuator` and `UnDelegateResourceActuator`, which also mutate an account's frozen/delegated balance (the quantity that backs voting/TronPower), never call `mortgageService.withdrawReward()` anywhere in their `execute()` or `validate()` methods. [3](#0-2) [4](#0-3) 

### Finding Description
The bug-class pattern from the report is: a state-mutating operation on a value-bearing resource proceeds without first accruing/settling the reward or interest tied to that resource's prior state, so later reward/risk computations use stale data.

`MortgageService.withdrawReward()` settles a pending vote reward into `accountCapsule`'s `allowance` field, using the account's `votesList` and the `beginCycle`/`endCycle` bookkeeping in `DelegationStore`. [5](#0-4) 

Anywhere an account's frozen/tron-power backing balance changes, the protocol pattern (as implemented consistently in `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`/`UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Processor`/`WithdrawRewardProcessor`/`VoteRewardUtil.withdrawReward`) is to call `withdrawReward` first, then adjust balances/votes. [6](#0-5) [7](#0-6) 

`DelegateResourceActuator.execute()` directly mutates `ownerCapsule`'s frozen/delegated balances (`addDelegatedFrozenV2BalanceForBandwidth`, `addFrozenBalanceForBandwidthV2`, etc.) without calling `withdrawReward` beforehand, and `UnDelegateResourceActuator.execute()` does the same in the reverse direction. [8](#0-7) [9](#0-8) 

However, I was **not able to conclusively confirm** (within the remaining tool budget) that this omission produces a materially different reward outcome than the audited codebase intends. Unlike `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Processor`, `DelegateResourceActuator`/`UnDelegateResourceActuator` do not clear the account's `votesList` and do not appear to change the balance actually counted toward TronPower for voting purposes (delegated balance is tracked separately via `DelegatedFrozenV2Balance`/`AcquiredDelegatedFrozenV2Balance` fields, not via `votesList`). I could not verify, given the index/tool limits, whether TronPower/voting-power calculations (`AccountCapsule.getTronPower()`, referenced in `AccountCapsule.java`) treat delegated-out balance identically before and after this operation, which is required to prove that omitting `withdrawReward` here actually causes incorrect reward accrual (as opposed to being intentionally omitted because delegation doesn't change the reward-relevant TronPower snapshot).

### Impact Explanation
If the omission does have downstream effect, its impact would mirror the report: reward computation would use the account's post-delegation vote/frozen state instead of the pre-delegation state for the cycle in which the delegate/undelegate transaction occurs, potentially misallocating vote rewards (`allowance`) between cycles. This would be an "unbacked balance"/incorrect-fund-accounting class issue reachable by any account holder issuing a `DelegateResourceContract`/`UnDelegateResourceContract` transaction. However, without confirming whether TronPower actually changes as a reward-relevant quantity in this path, I cannot assert with confidence that funds are lost, frozen, or misallocated versus the current design being correct-by-construction.

### Likelihood Explanation
Reachable by any unprivileged account via a signed `DelegateResourceContract`/`UnDelegateResourceContract` transaction — no privileged role required. Likelihood of an actual monetary impact depends on unverified internals (whether delegated balance affects the reward-relevant vote/TronPower snapshot), which I could not confirm.

### Recommendation
Given the unresolved uncertainty about actual reward-relevant impact, I cannot issue a confident, concrete finding here. A background engineering review should verify: (1) whether `AccountCapsule.getTronPower()` and the vote-reward computation path in `MortgageService`/`DelegationStore` treat delegated-out/delegated-in balance as reward-affecting; (2) if so, add `mortgageService.withdrawReward(ownerAddress)` (and for the receiver address, if relevant) at the start of `DelegateResourceActuator.execute()` and `UnDelegateResourceActuator.execute()`, consistent with `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`.

### Proof of Concept
Not constructed — the analog's actual exploitability depends on unverified TronPower/reward accounting semantics noted above, which I could not confirm within the available index/tool access. I'm flagging this as a **candidate**, not a confirmed vulnerability, and recommend a Devin session with full repository/test access to trace `AccountCapsule.getTronPower()`, `MortgageService.computeReward()`, and the vote-reward test suite (e.g. `VoteTest.java`) to determine whether delegate/undelegate actually needs the missing `withdrawReward` call.

        logger.debug("Resource Code Error.");
    }

    accountStore.put(ownerCapsule.createDbKey(), ownerCapsule);

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
