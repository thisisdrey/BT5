### Title
Cross-StackerDB Signature Replay Due to Missing Contract-Domain Binding in `SlotMetadata` Signing - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
The digest that a StackerDB signer authenticates does not bind the signature to the specific smart-contract-identified StackerDB instance it authorizes writes for. `SlotMetadata::auth_digest` only commits to `slot_id`, `slot_version`, and `data_hash`, with no domain separator for the target contract. Any remote, unprivileged party who observes a validly-signed chunk for one StackerDB (chunks are broadcast publicly over p2p and readable via the public HTTP StackerDB endpoints) can resubmit that identical `(slot_id, slot_version, sig, data)` tuple against a *different* StackerDB contract. If the signer address occupying that same `slot_id` in the target StackerDB happens to be the same signer (a realistic scenario, since the same signer set commonly occupies the same slot ordering across sibling `.signers-*` StackerDB contracts for different reward cycles), the write is accepted as authentic in the target StackerDB even though it was never authorized for it.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest as: [1](#0-0) 

This digest is the sole input verified in `SlotMetadata::verify`: [2](#0-1) 

The storage path `StackerDBTx::try_replace_chunk` accepts a chunk if the recovered address matches the slot's configured signer for *that DB instance*, but the signature check itself never differentiates which contract/StackerDB the write is destined for: [3](#0-2) 

The same generic verification is used both for chunks arriving via the public, unauthenticated HTTP endpoint `POST /v2/stackerdb/.../chunks`: [4](#0-3) 

and for chunks pushed unsolicited over p2p, which are then broadcast network-wide upon acceptance: [5](#0-4) [6](#0-5) 

Because `contract_identifier` is never part of what is hashed and signed, the equality the system relies on — "a signature verifying under signer `S` for slot `i` means `S` authorized *this* StackerDB's slot `i` to hold this data" — does not hold. It only proves `S` authorized *some* StackerDB's slot `i` version `v` to hold this data. An attacker who is not `S` and holds no private key can still cause the write, purely by replaying bytes that were already legitimately published elsewhere.

### Impact Explanation
This breaks the authenticity guarantee of StackerDB writes: an unauthenticated, unprivileged remote actor can cause node state (StackerDB slot contents) belonging to one smart contract's replica set to be overwritten with data that was authorized only for a different smart contract's replica set. Because a successful store triggers rebroadcast to peers (`process_stacker_db_chunks`), a single replay can propagate forged/misattributed chunk data network-wide, an "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" per the Critical criteria.

### Likelihood Explanation
Exploitability depends on the same signer address occupying identical slot indices across multiple co-existing StackerDB instances with an overlapping/compatible version counter, which is a plausible configuration for consecutive-reward-cycle `.signers-*` StackerDB contracts that reuse similar signer set orderings. The mechanics (observe a broadcasted/publicly-fetchable chunk, resubmit verbatim to a different contract's endpoint) require no cryptographic capability and no privileged role — only network access to the target node's HTTP or p2p StackerDB interfaces.

### Recommendation
Include a domain separator in `SlotMetadata::auth_digest` — e.g., the `QualifiedContractIdentifier` (and ideally a chain/network identifier) of the target StackerDB — so a given signature is cryptographically scoped to exactly one StackerDB instance. This requires a wire/format version bump for `SlotMetadata`/`StackerDBChunkData` signing and coordinated updates to signer client code that produces these signatures.

### Proof of Concept
1. Configure (or observe on-chain) two StackerDB contracts, `A` and `B`, where signer `S` is assigned slot `3` in both (e.g., adjacent `.signers-<cycle>-1` contracts reusing the same signer ordering).
2. Wait for/observe a legitimate chunk broadcast for contract `A`: `StackerDBChunkData { slot_id: 3, slot_version: 5, sig: <S's sig>, data: D }`, obtainable either from the p2p `StackerDBPushChunk` gossip or via `GET /v2/stackerdb/A/3` HTTP RPC.
3. As an unprivileged remote actor, POST the same tuple to `POST /v2/stackerdb/B/chunks` (or push it over p2p) using contract `B`'s identifier while keeping `slot_id=3`, `slot_version` greater than `B`'s current slot-3 version, and the identical `sig`/`data`.
4. `RPCPostStackerDBChunkRequestHandler` calls `try_replace_chunk`, which calls `slot_desc.verify(&slot_validation.signer)` for contract `B`; since the digest never encoded which contract it was for, verification succeeds and the chunk (authored for `A`) is stored and re-broadcast under `B`'s replica set, despite `S` never having authorized this write for `B`.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
