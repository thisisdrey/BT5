### Title
Unauthenticated `RelayFromAddr` in `CreateRelayRequest` allows a peer to poison relay-identity state - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` derives the relay-chain "from" identity directly from an attacker-controlled protobuf field in the `CreateRelayRequest` control message, rather than from the actual authenticated identity of the sender (the cert-bound `vpnAddrs` on the `HostInfo` that terminated the encrypted tunnel). This mirrors the External Report's root cause: attributing a trust-relevant identity to an unverified "claimed sender" value instead of the cryptographically authenticated party.

### Finding Description
In `relay_manager.go`, `handleCreateRelayRequest` reads: [1](#0-0) 

`from` is taken from `m.RelayFromAddr`, a value chosen entirely by the sending peer inside the encrypted control payload — it is never checked against the `h.vpnAddrs` (the actual, certificate-verified identity of the authenticated tunnel `h`). The only self-check performed is that `from` isn't one of *my own* addresses: [2](#0-1) 

When the request's `target` is me, the code immediately establishes relay state keyed by this unverified `from` value: [3](#0-2) 

This is structurally identical to the report's bug class: a value that should represent a verified remote identity (analogous to the "real DAO owner") is instead taken from an attacker/intermediary-supplied field (analogous to `msg.sender` being the LayerZero Deployer rather than the true owner). Here, any authenticated peer `h` (which only needs a valid cert for *some* address, not for `from`) can claim to be relaying "on behalf of" an arbitrary `from` VPN address that it does not own, and the target immediately records that relay-for mapping (`AddRelay(..., TerminalType, Established)`), poisoning the target's relay/hostinfo state with a spoofed identity binding.

### Impact Explanation
This allows a certificate-holding but otherwise arbitrary peer to insert unverified identity claims into another node's relay state (`relayState.relayForByAddr`/`relayForByIdx`), which downstream code (`handleOutsideRelayPacket`, `QueryVpnAddrsRelayFor`) uses to route and forward encrypted relay traffic and to decide relay-relationship state transitions (`Requested`/`Established`/`Disestablished`). Poisoning this state can misdirect or disrupt legitimate relay-based tunnel establishment for the spoofed address and creates persistent bogus relay bookkeeping tied to an address the requester does not control — a remote state-poisoning condition reachable from any certificate holder without needing to control the claimed `from` address.

### Likelihood Explanation
Likelihood is high for any node capable of sending a `CreateRelayRequest` control message (i.e., any peer with a valid cert able to complete a handshake to the target or an intermediary relay) — no special privilege beyond normal PKI membership is required, and the `RelayFromAddr` field is trivially attacker-controlled plaintext-post-decryption input.

### Recommendation
Do not trust `m.RelayFromAddr` as an authoritative identity. Either (a) bind the relay-from identity to `h.vpnAddrs` (the cert-verified address of the authenticated sender) instead of the message-supplied field, or (b) if peers are allowed to request relaying on behalf of a third party, require cryptographic proof (e.g., a cert or signed assertion) that the requester is authorized to represent `from` before calling `AddRelay`.

### Proof of Concept
Conceptual (no external harness available in this analysis):
1. Node `H` establishes a legitimate, cert-authenticated tunnel to victim `V` (target of relay).
2. `H` sends `CreateRelayRequest` with `RelayFromAddr` set to some victim third-party address `X` that `H` does not control. [1](#0-0) 
3. `handleCreateRelayRequest` on `V` only rejects the case where `from == V`'s own address; it does not verify `from` against `H`'s certificate-bound `vpnAddrs`. [2](#0-1) 
4. `V` calls `AddRelay(..., from=X, TerminalType, Established)`, creating relay state that attributes future relay traffic through `H`'s tunnel as being "for" `X`, an address `H` never proved ownership of. [4](#0-3) 

Note: full exploitation impact (e.g., whether this can be leveraged into traffic redirection beyond bookkeeping corruption) would require dynamic testing of `QueryVpnAddrsRelayFor` and `handleOutsideRelayPacket` interactions that could not be fully traced with static search alone in the remaining budget.
