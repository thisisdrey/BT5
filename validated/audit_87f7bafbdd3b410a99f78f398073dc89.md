### Title
Unauthenticated `RecvError` packets allow spoofed teardown of established tunnels (remote state poisoning / DoS) - ([File: outside.go])

### Summary
The SEDA report shows an attacker exploiting a validated-but-untrusted role (the `postBatch` sender address) to poison a piece of authoritative on-chain state (`BatchData.sender`) so that a later, legitimate operation (`postResult`'s fee transfer) is forced to fail, blocking all result submissions for that batch. The nebula analog is `Interface.handleRecvError` in `outside.go`, which lets an attacker who has only observed (not decrypted) plaintext wire traffic poison the authoritative hostmap state (tear down an established `HostInfo`) without ever completing a handshake or holding a CA-signed certificate, blocking the legitimate tunnel the same way the SEDA bug blocks legitimate result submissions.

### Finding Description
`RecvError` is one of the two unencrypted, pre-authentication packet types handled directly in `readOutsidePackets`: [1](#0-0) 

`h.RemoteIndex` — the local index a peer uses to address the tunnel — travels in the cleartext header of *every* nebula packet (handshake, data, test, etc.), so any observer on the path, or anyone who can otherwise learn/guess this 32-bit value, knows it without possessing a certificate, without completing a handshake, and without being a validator/CA member.

`handleRecvError` then does the following, entirely unauthenticated: [2](#0-1) 

The only gate against forgery is a plaintext UDP source-address comparison:
```go
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    f.l.Info("Someone spoofing recv_errors?", ...)
    return
}
f.closeTunnel(hostinfo)
f.handshakeManager.DeleteHostInfo(hostinfo)
```
UDP has no source-address authentication at the transport layer, so `addr` is exactly the value the sender chose to put in the IP/UDP header of the spoofed packet — it is not cryptographically bound to anything. An attacker who can spoof UDP source IP:port (on-path attacker, attacker sharing a NAT'd network, or any network without egress/ingress anti-spoofing) can construct a bare `RecvError` header (`header.Encode(..., header.RecvError, 0, index, 0)`) with:
- `RemoteIndex` = the victim's observed local index (learned by sniffing any packet of the target tunnel), and
- source address spoofed to equal `hostinfo.GetRemote()` (the peer's known/observable UDP endpoint).

This is exactly analogous to the SEDA root cause: a piece of state that should only be mutable by a cryptographically-verified party (`BatchData.sender` / here, `HostMap.RemoteIndexes` -> `HostInfo`) can instead be manipulated by anyone who satisfies a much weaker, attacker-controllable check (any address that passes validator signature checks in SEDA / any packet whose spoofable source address matches in nebula). The result in both cases is the same: authoritative state is poisoned by an unauthenticated party, and this poisoning is used purely to force the legitimate flow (post-batch result payout / active tunnel) to be destroyed.

`QueryReverseIndex` lookups happen against the main hostmap keyed by remote index without checking `ConnectionState` freshness or requiring a decrypted/authenticated packet counter, unlike every other post-handshake packet type which is gated behind `ConnectionState.Decrypt` (AEAD authentication) in the same function just a few lines above: [3](#0-2) 

That gate (AEAD decrypt with replay window) is exactly what protects `Message`, `Test`, `CloseTunnel`, and `Control` packet types from spoofing. `RecvError` and `Handshake` are the two paths that bypass it, and `Handshake` at least requires a full, CA-verified certificate to complete. `RecvError` requires nothing but a guessed/observed index and a spoofed source address.

### Impact Explanation
An attacker with no CA-signed certificate and no completed handshake can tear down any established tunnel between two legitimate nebula nodes by:
1. Observing (or guessing) the target's `LocalIndex`/`RemoteIndex` from the cleartext header of any packet on that tunnel, and
2. Sending a spoofed 1-packet `RecvError` message with a forged source UDP address.

This directly matches the "remote state poisoning" / "remote crash" impact classes: legitimate, encrypted, actively-used tunnels are unilaterally destroyed (`f.closeTunnel` + `hm.DeleteHostInfo`) by an unauthenticated party, causing denial of service that repeats at will (the attacker can keep re-sending the forged packet every time the victims re-handshake, since the new index is again visible in cleartext). This is the direct nebula analog of "Attacker can block result submissions" — here the attacker blocks/repeatedly kills tunnel connectivity, which is the VPN's core guarantee.

### Likelihood Explanation
Feasibility depends on the attacker's ability to spoof UDP source addresses, which is non-trivial across the general internet (ingress/egress filtering, NAT) but realistic for:
- on-path attackers (compromised router, malicious Wi-Fi AP, shared L2 segment),
- attackers behind carrier-grade NAT/symmetric routing weaknesses, or
- environments without BCP38/uRPF filtering.

The `RemoteIndex` value itself requires no decryption and is visible on every packet, so the "hard" part of the attack (spoofing) is the only barrier, and this exact spoofing risk was acknowledged by the project itself as a known, configurable tradeoff (`listen.send_recv_error` / `acceptRecvErrorConfig`), which by default appears to still accept recv-errors in some configurations. I was unable to confirm the exact default value of `acceptRecvErrorConfig` from the available index (it references `recvErrorPrivate`, `recvErrorAlways`, `recvErrorNever`, but the code that sets the actual default from config was not found in the indexed portion of `interface.go`), so the real-world exposure depends on deployment configuration; this should be verified directly in the repo.

### Recommendation
Require `RecvError` handling to be bound to something the attacker cannot forge, e.g.:
- Only accept `RecvError` for an index whose associated tunnel has recently sent a packet toward `addr` from *this* process (a local anti-spoofing echo/nonce check), or
- Require a short authenticated (MAC'd with the session key) proof-of-index instead of a bare unencrypted header, or
- Default `acceptRecvErrorConfig` to a much more conservative mode (e.g., private-address-only or disabled) and clearly document that enabling `RecvError` acceptance re-introduces a source-spoofable tunnel-teardown primitive.

### Proof of Concept
Not executable from static analysis alone; the exploit primitive is:
1. Observe any packet belonging to victim tunnel T (any packet type works) to learn `RemoteIndex = idx` and the peer's `remote` UDP endpoint `E`.
2. Craft `pkt = header.Encode(buf, header.Version, header.RecvError, 0, idx, 0)` (see construction in `sendRecvError`, `outside.go:528-539`).
3. Send `pkt` to the victim's UDP listener with the *source* IP:port spoofed to `E`.
4. Victim's `handleRecvError` (`outside.go:541-575`) finds `hostinfo` via `QueryReverseIndex(idx)`, sees `hr == addr` (spoofed match), and calls `f.closeTunnel(hostinfo)` plus deletes the pending handshake entry — tearing down the legitimate tunnel with zero cryptographic proof of identity.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
