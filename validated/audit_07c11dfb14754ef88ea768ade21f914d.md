Audit Report

## Title
`process_delivery_receipt` ignores the `success` field of the delivery receipt, allowing relayer rewards and order settlement for failed deliveries - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` decodes and validates only the `gateway` address and `nonce` fields of a `DeliveryReceipt`, then unconditionally pays `order.fee` to the reward account and removes the `PendingOrders` entry, without ever inspecting `receipt.success` [1](#0-0) . The `success` field is decoded directly from the Ethereum `InboundMessageDispatched` event and represents whether the message dispatch actually succeeded on the Ethereum side, but this codebase never reads it anywhere in the pallet [2](#0-1) .

## Finding Description
`submit_delivery_receipt` verifies the Merkle/beacon proof for the event log, decodes it into a `DeliveryReceipt` via `DeliveryReceipt::try_from`, and passes it to `process_delivery_receipt` [3](#0-2) . The decode step faithfully copies `event.success` into `DeliveryReceipt.success` [4](#0-3) . `process_delivery_receipt` then only checks `receipt.gateway == T::GatewayAddress::get()` and looks up `PendingOrders` by `receipt.nonce`, before paying `order.fee` via `T::RewardPayment::register_reward` and removing the order [5](#0-4) . There is no `ensure!`, branch, or conditional anywhere referencing `success`, confirmed by the absence of the string `success` anywhere in the pallet's source file. This means any relayer that proves inclusion of a genuine `InboundMessageDispatched(nonce, topic, success=false, reward_address)` event — which is emitted normally by the Gateway contract whenever a dispatched command reverts — can still collect the full `order.fee` reward and cause `PendingOrders` to be permanently cleared for that nonce, exactly as if the message had been executed successfully.

## Impact Explanation
This breaks settlement correctness for the bridge's reward/order lifecycle: pending order state is supposed to advance to "settled" only after successful execution, but it advances identically regardless of `success`, and `order.fee` (a monetary reward) is paid to the reward beneficiary for outcomes that did not actually complete successfully. This matches the "duplicate settlement or payout" / "runtime bugs that compromise intended behavior" category in the impact gate, since fee funds are disbursed and pending-order state is permanently retired without the invariant ("payout state must only advance after decode, dispatch, execution, and settlement succeed atomically") being honored.

## Likelihood Explanation
The only precondition is a legitimate `InboundMessageDispatched` event with `success = false` occurring on Ethereum (e.g., ordinary command execution failure/revert at the Gateway) and any standard relayer submitting a normal Merkle/beacon proof of that event via the public `submit_delivery_receipt` extrinsic. No malicious relayer, prover, validator, or governance action is required — a fully honest relayer following ordinary operating procedure will trigger this path whenever a dispatch fails on Ethereum, which is a normal and expected occurrence, not an edge case requiring adversarial control.

## Recommendation
Add an explicit check on `receipt.success` in `process_delivery_receipt` before calling `T::RewardPayment::register_reward` and/or removing the `PendingOrders` entry. For example, only pay `order.fee` when `receipt.success == true`; for the `success == false` case, define explicit failure-path semantics (e.g., emit a distinct `MessageDeliveryFailed` event, skip or reduce the reward, or otherwise handle stuck orders) rather than silently rewarding and clearing the order identically to the success path.

## Proof of Concept
1. A message is queued via `do_process_message`, creating a `PendingOrders` entry with a nonzero `fee` for `nonce = N` [6](#0-5) .
2. On Ethereum, the Gateway contract processes the message but the dispatched command reverts/fails, emitting `InboundMessageDispatched(nonce=N, topic, success=false, reward_address)`.
3. A relayer obtains a valid Merkle/beacon proof for this event log and calls `submit_delivery_receipt` with it; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success = false` [4](#0-3) .
4. `process_delivery_receipt` passes the `gateway` check and `nonce` lookup, pays `order.fee` to `reward_account`, removes the `PendingOrders` entry for `N`, and emits `MessageDelivered { nonce: N }` — identical behavior to the success case [7](#0-6) .
5. A unit test asserting that `process_delivery_receipt` with `receipt.success = false` results in no reward payment and/or retained/differently-handled order state would fail against current code, confirming the gap.

			<T as frame_system::Config>::AccountId: From<[u8; 32]>,

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward

					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
