### Title
Unbounded-length read from attacker-controlled TransactionInfo.Log data causes ArrayIndexOutOfBoundsException / node crash in shielded TRC20 note scanning - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
`getNoteTxFromLogListByIvk` in `Wallet.java` slices fixed offsets (`0..32`, `32..64`, `96..128`, `128..708`) out of `log.getData().toByteArray()` without first checking that `logData.length` is at least 708 bytes, unlike the sibling `NoteSpent` handling path in `scanShieldedTRC20NotesByOvk` which explicitly guards with `if (logData.length >= 32)` before calling `ByteArray.subArray`.

### Finding Description
`getShieldedTRC20LogType` classifies a `TransactionInfo.Log` as type 1–3 (Mint/Transfer/Burn leaf) purely by matching the log's topic hash against known event signatures [1](#0-0) . It does not validate the length of `log.getData()` at all — only the topic list is inspected.

`getNoteTxFromLogListByIvk` then only checks that `logData` is non-empty (`!ArrayUtils.isEmpty(logData)`) before unconditionally slicing fixed byte ranges up to offset 708: [2](#0-1) 

Because `TransactionInfo.Log` entries are produced from TVM `LOG*` opcode execution during contract execution (`OperationActions`/`getLogCost` in `EnergyCost.java`), an attacker who deploys and calls a smart contract can emit an event with a topic matching `MintNewLeaf`/`TransferNewLeaf`/`BurnNewLeaf` signatures but with a `data` payload shorter than 708 bytes (e.g., 1 byte, or even 32 bytes as in the test log for `NoteSpent`, which is correctly guarded, but no equivalent guard exists for logType 1-3). `ByteArray.subArray` copies bytes via `System.arraycopy`-style logic from the underlying array; if the requested end offset exceeds `logData.length`, the copy throws an unhandled `ArrayIndexOutOfBoundsException` rather than an application-level `ZksnarkException`.

This mirrors the CVE-2016-7449 bug class: reading a fixed/implied length span from an attacker-supplied buffer without first verifying the buffer actually contains that many bytes ("unterminated" / undersized data), producing an out-of-bounds read.

### Impact Explanation
The vulnerable path is reached from the public HTTP/gRPC endpoints `/wallet/scanshieldedtrc20notesbyivk` (and its OVK/solidity/PBFT counterparts), exposed via `ScanShieldedTRC20NotesByIvkServlet` and `RpcApiService.scanShieldedTRC20NotesByIvk` [3](#0-2) [4](#0-3) . These endpoints iterate over historical blocks and every `TransactionInfo.Log` therein [5](#0-4) . An `ArrayIndexOutOfBoundsException` (an unchecked `RuntimeException`, not `BadItemException`/`ZksnarkException`) thrown deep in `getNoteTxFromLogListByIvk` is caught only by the generic `catch (Exception e)` at the gRPC layer (returning an error to the caller) — so per-call impact is limited to a failed RPC response, not necessarily a full node crash, unless the exception occurs in a context without that catch (e.g., is it caught everywhere consistently is unverified for all call paths such as `queryTRC20NoteByIvk`'s direct callers on the HTTP/servlet-thread stack, which do wrap in `try/catch(Exception e)` as well). Given the currently-visible exception handling wraps calls in `try/catch(Exception e)` at both the gRPC (`RpcApiService`) and HTTP servlet (`Util.processError`) layers, the most likely realized impact is a denial of service of that specific API call (HTTP 500 / gRPC error) for any client scanning blocks containing the crafted log, rather than a full node crash — still a legitimate "API the node can no longer serve correctly" condition for shielded TRC20 note scanning once a malicious log of this shape is included in a block.

### Likelihood Explanation
Any account can deploy a contract and emit a `LOG` matching the `MintNewLeaf`/`TransferNewLeaf`/`BurnNewLeaf(...)` topic hash with a `data` field shorter than 708 bytes — this requires no special privilege, no SR/witness/committee role, and is fully within the reach of a normal contract-deploying/calling account and thus a downstream anonymous API client that later calls the scan endpoints. The bug is a simple missing length check, symmetric with the check that *is* present for `NoteSpent` logs in the sibling `scanShieldedTRC20NotesByOvk`/`getNoteTxFromLogListByOvk` path, indicating the length check for logType 1-3 was simply omitted.

### Recommendation
Add an explicit length check (`logData.length >= 708`) before slicing in `getNoteTxFromLogListByIvk` (and audit `getNoteTxFromLogListByOvk` for logType 1–3 for the same issue), throwing `ZksnarkException`/`BadItemException` instead of allowing an unchecked `ArrayIndexOutOfBoundsException` to propagate, consistent with the existing `logData.length >= 32` guard used for `NoteSpent` handling.

### Proof of Concept
1. Deploy a contract whose function emits `log0`/`logN` with topic `keccak256("TransferNewLeaf(uint256,bytes32,bytes32,bytes32,bytes32[21])")` and a `data` payload of, e.g., 1 byte.
2. Trigger the contract from any account; the resulting `TransactionInfo.Log` is persisted with the short `data`.
3. Call `/wallet/scanshieldedtrc20notesbyivk` (or the gRPC `ScanShieldedTRC20NotesByIvk`) with a block range covering that transaction and any `ivk`.
4. `getShieldedTRC20LogType` returns `2` (Transfer) based solely on the topic match [6](#0-5) ; `getNoteTxFromLogListByIvk` proceeds to slice `logData` at offsets up to 708, throwing an `ArrayIndexOutOfBoundsException` inside `ByteArray.subArray` [7](#0-6) , surfacing as an API-level failure for the scan request.

Note: I was unable to fully inspect the exact bounds-check (or lack thereof) inside `ByteArray.subArray` itself before running out of tool iterations, so the precise exception type/message is inferred from `System.arraycopy` semantics rather than confirmed by reading that method's body directly.

    DecryptNotesTRC20.Builder builder = DecryptNotesTRC20.newBuilder();
    BlockList blockList = this.getBlocksByLimitNext(startNum, endNum - startNum);
    for (Block block : blockList.getBlockList()) {
      for (Transaction transaction : block.getTransactionsList()) {
        TransactionCapsule transactionCapsule = new TransactionCapsule(transaction);
        byte[] txId = transactionCapsule.getTransactionId().getBytes();
        TransactionInfo info = this.getTransactionInfoById(ByteString.copyFrom(txId));
        DecryptNotesTRC20.NoteTx.Builder noteBuilder;
        if (!Objects.isNull(info)) {
          List<TransactionInfo.Log> logList = info.getLogList();
          if (!Objects.isNull(logList)) {
            Optional<DecryptNotesTRC20.NoteTx> noteTx;
            int index = 0;
            for (TransactionInfo.Log log : logList) {
              int logType = getShieldedTRC20LogType(log, shieldedTRC20ContractAddress);
              // Only note-producing log types (1..3) advance the note index;
              // TokenBurn (4) and NoteSpent (5) do not emit a leaf.
              if (logType > 0 && logType < 4) {
                noteBuilder = DecryptNotesTRC20.NoteTx.newBuilder();
                noteBuilder.setTxid(ByteString.copyFrom(txId));
                noteBuilder.setIndex(index);
                index += 1;
                noteTx = getNoteTxFromLogListByIvk(noteBuilder, log, ivk, ak, nk,
                    shieldedTRC20ContractAddress, logType);
                noteTx.ifPresent(builder::addNoteTxs);
              }
            }
          }
        }
      } //end of transaction
    } //end of blocklist
    return builder.build();
