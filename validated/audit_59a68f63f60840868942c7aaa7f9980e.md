Found a concrete, unprivileged analog: `CreateRepositoryFromSnapshot` extracts a **completely untrusted, remote-fetched tar archive directly onto the on-disk repository path** without inspecting or restricting its contents, and the extracted files include Git's `objects/info/alternates` file. Because Gitaly's alternates-resolution logic (`internal/git/dirs.go`) only verifies that an alternate path stays *within the storage root* — not that it belongs to the calling repository or to a legitimate object pool — a malicious/crafted snapshot archive can plant an `objects/info/alternates` entry pointing at any other repository's `objects` directory on the same storage, granting the newly created repository read access to that other repository's objects.

### Title
Cross-repository object disclosure via attacker-controlled `objects/info/alternates` in `CreateRepositoryFromSnapshot` archive extraction - (File: internal/gitaly/service/repository/create_repository_from_snapshot.go)

### Summary
`CreateRepositoryFromSnapshot` fetches a tar archive from a caller-supplied HTTP URL and extracts it verbatim onto a brand-new repository's on-disk path via `tar -C path -xvf -`, with an explicit code comment acknowledging the archive is "trusted *a lot*." [1](#0-0)  Nothing filters or validates the archive's file list, meaning it can contain a `objects/info/alternates` file. Git's alternate-object-directory resolution (used throughout Gitaly, e.g. `internal/git/dirs.go`) only rejects alternates that fall **outside the storage root**; it does not verify that an alternate belongs to the caller's own repository or to a repository that has been legitimately linked as an object pool via `LinkRepositoryToObjectPool`. [2](#0-1) 

This mirrors the WETH-drain bug class: just as `withdrawForETH` trusted a caller-supplied contract's self-reported state instead of independently verifying the actual transfer, Gitaly trusts caller-supplied archive content (the alternates pointer) to establish access to another party's assets (Git objects) instead of independently verifying that the alternate target is one the caller is authorized to reference.

### Finding Description
1. The snapshot HTTP source in the request (`HttpUrl`/`ResolvedAddress`) is attacker-influenced input to an ordinary `CreateRepositoryFromSnapshot` RPC call.
2. The response body is piped straight into `tar -C path -xvf -` with no allow-list, no path/entry filtering beyond what `tar` itself does, and no post-extraction sanity check of repository structure. [3](#0-2) 
3. If the archive includes `objects/info/alternates` containing a relative or absolute path such as `../../other-repo/objects`, Gitaly's alternates walker (`altObjectDirs` in `internal/git/dirs.go`) will accept it as long as it resolves under the configured `storageRoot`: [4](#0-3) 
4. That check exists purely to prevent *filesystem* escapes outside the storage — it performs no ownership/authorization check against the target repository, unlike the object-pool `Link`/`linkedToRepository` flow which enforces that alternates match an expected, server-computed relative path derived from an actual `LinkRepositoryToObjectPool` call. [5](#0-4) 
5. As a result, any subsequent Git operation against the newly created repository (clone, cat-file, FindCommit, etc.) will transparently resolve objects from the victim repository's object directory, because alternates function as an implicit search path once resolved within the storage root, as documented in `doc/object_quarantine.md`. [6](#0-5) 

### Impact Explanation
This is a cross-repository object disclosure: an attacker able to invoke `CreateRepositoryFromSnapshot` (e.g., during project import/fork setup workflows that call it) with a crafted or compromised snapshot source can read blobs/commits/trees from arbitrary other repositories in the same Gitaly storage, without ever having read access to them. This is a serious confidentiality breach for a multi-tenant Gitaly storage (private repositories, other users' code) and matches the "cross-repository object access" category called out as in-scope.

### Likelihood Explanation
Likelihood is moderate-to-high wherever `CreateRepositoryFromSnapshot` is reachable with attacker-influenced HTTP source content (self-hosted mirrors, project import from untrusted URL, replicated snapshot sources) — the code's own comment flags that the archive is trusted without hardening, indicating awareness of the general TAR-trust problem but not specifically of the alternates-escape vector. [7](#0-6) 

### Recommendation
- After extraction (or via streaming filter during extraction), reject or strip any `objects/info/alternates` file, `commondir`, or other files that could redirect Git to look outside the freshly created repository's own object directory.
- Alternatively, validate post-extraction via `AlternateObjectDirectories`/`stats.AlternatesInfoForRepository` that no alternates file exists (or that it only points at paths explicitly re-derived via the legitimate object-pool `Link` flow) before the repository is considered created and made available.
- Apply the same allow-list/deny-list treatment used elsewhere in Gitaly for tar extraction (`internal/gitaly/service/repository/replicate.go`'s `extractTarToDirectory` already validates symlink/hardlink targets against path traversal; extend this or the snapshot path to also reject dangerous plain files like `objects/info/alternates`).

### Proof of Concept
1. Attacker controls (or can influence, e.g. via SSRF into an internal snapshot endpoint) the HTTP server referenced by `HttpUrl` in a `CreateRepositoryFromSnapshotRequest`.
2. The served tar archive contains a minimal valid bare-repo skeleton plus `objects/info/alternates` with content `../../<victim-storage-relative-path>/objects`.
3. Gitaly calls `s.untar(...)` which extracts this file verbatim into the new repository's directory. [8](#0-7) 
4. Any subsequent read RPC (e.g., `FindCommit`, `TreeEntry`, `GetBlob`) against the newly created repository transparently resolves objects from the victim repository because the alternates path resolves within the storage root and passes the check in `internal/git/dirs.go`. [9](#0-8) 
5. The attacker now can read arbitrary objects (commits, blobs, trees) from the victim repository despite having no direct authorization to access it.

func (s *server) untar(ctx context.Context, path string, in *gitalypb.CreateRepositoryFromSnapshotRequest) error {
	req, err := http.NewRequestWithContext(ctx, "GET", in.GetHttpUrl(), nil)
	if err != nil {
		return structerr.NewInvalidArgument("Bad HTTP URL: %w", err)
	}

	client := httpClient
	if resolvedAddress := in.GetResolvedAddress(); resolvedAddress != "" {
		client, err = newResolvedHTTPClient(in.GetHttpUrl(), resolvedAddress)
		if err != nil {
			return structerr.NewInvalidArgument("creating resolved HTTP client: %w", err)
		}
	}

	if in.GetHttpAuth() != "" {
		req.Header.Set("Authorization", in.GetHttpAuth())
	}

	rsp, err := client.Do(req)
	if err != nil {
		return structerr.NewInternal("HTTP request failed: %w", err)
	}
	defer rsp.Body.Close()

	if rsp.StatusCode < http.StatusOK || rsp.StatusCode >= http.StatusMultipleChoices {
		return structerr.NewInternal("HTTP server: %s", rsp.Status)
	}

	cmd, err := command.New(ctx, s.logger, []string{"tar", "-C", path, "-xvf", "-"}, command.WithStdin(rsp.Body))
	if err != nil {
		return err
	}

	return cmd.Wait()
}

func altObjectDirs(ctx context.Context, logger log.Logger, storagePrefix, objDir string, depth int) ([]string, error) {
	const maxAlternatesDepth = 5 // Taken from https://github.com/git/git/blob/v2.23.0/sha1-file.c#L575
	if depth > maxAlternatesDepth {
		logger.WithField("objdir", objDir).WarnContext(ctx, "ignoring deeply nested alternate object directory")
		return nil, nil
	}

	fi, err := os.Stat(objDir)
	if os.IsNotExist(err) {
		logger.WithField("objdir", objDir).WarnContext(ctx, "object directory not found")
		return nil, nil
	}
	if err != nil {
		return nil, err
	}
	if !fi.IsDir() {
		return nil, nil
	}

	dirs := []string{objDir}

	alternates, err := os.ReadFile(filepath.Join(objDir, "info", "alternates"))
	if os.IsNotExist(err) {
		return dirs, nil
	}
	if err != nil {
		return nil, err
	}

	for _, newDir := range strings.Split(string(alternates), "\n") {
		if len(newDir) == 0 || newDir[0] == '#' {
			continue
		}

		if !filepath.IsAbs(newDir) {
			newDir = filepath.Join(objDir, newDir)
		}

		if !strings.HasPrefix(newDir, storagePrefix) {
			return nil, alternateOutsideStorageError(newDir)
		}

		nestedDirs, err := altObjectDirs(ctx, logger, storagePrefix, newDir, depth+1)
		if err != nil {
			return nil, err
		}

		dirs = append(dirs, nestedDirs...)
	}

// linkedToRepository tests if a repository is linked to an object pool
func linkedToRepository(ctx context.Context, pool, repo *localrepo.Repo) (bool, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return false, fmt.Errorf("getting repo path: %w", err)
	}

	altInfo, err := stats.AlternatesInfoForRepository(repoPath)
	if err != nil {
		return false, fmt.Errorf("getting alternates info: %w", err)
	}

	if !altInfo.Exists || len(altInfo.ObjectDirectories) == 0 {
		return false, nil
	}

	relPath := altInfo.ObjectDirectories[0]
	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return false, err
	}

	if relPath == expectedRelPath {
		return true, nil
	}

	if filepath.Clean(relPath) != filepath.Join(poolPath, "objects") {
		return false, fmt.Errorf("unexpected alternates content: %q", relPath)
	}

	return false, nil
}
