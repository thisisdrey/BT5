### Title
Unvalidated length field parsed from precompiled-contract call data drives out-of-bounds array reads - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read a 32-byte "count" word directly out of attacker-controlled ABI call data (`words[offset].intValueSafe()`), then use that value as a loop bound to index further into the same `words[]`/`data[]` byte arrays — exactly the bug class described in the Vim CVE: an inline count field taken from untrusted input is used to determine how many fixed-size records follow, with no check that the underlying buffer actually contains that many bytes.

### Finding Description
In `extractBytesArray`: [1](#0-0) 
and in `extractSigArray`: [2](#0-1) 
and `extractBytes32Array`: [3](#0-2) 

Each function reads `len` from a single caller-supplied word (`words[offset].intValueSafe()`) and then loops `i` from `0` to `len`, using `i` to index further into the `words` array (and, in `extractBytesArray`/`extractSigArray`, to compute an `extractBytes(data, offset, len2)` call that does `Arrays.copyOfRange(data, offset, offset + len)`). None of these functions validate that `len` (or the derived `bytesOffset`/`bytesLen`/`offset + len` in `extractBytes`) is within the bounds of the actual `words`/`data` array before using it, only the very first check `offset > words.length - 1` guards the *first* index, not the full range implied by `len`. This mirrors the Vim flaw in `get_text_props()`, where a count value stored inline is used to determine how many fixed-size records to consume without checking the value against the amount of data actually present, leading to reads past the buffer.

Because these helper functions live in `PrecompiledContracts.java`, they are reachable by any contract or wallet call whose input data is routed to a precompiled contract that uses these helpers to decode dynamic arrays out of the raw call-data byte array. A crafted call with `len` far larger than the number of words/bytes actually supplied causes `words[offset + i + 1]` or `Arrays.copyOfRange(data, offset, offset + len)` to run past the end of the array, throwing `ArrayIndexOutOfBoundsException` / `NegativeArraySizeException`.

### Impact Explanation
An uncaught runtime exception thrown deep inside a precompiled contract's `execute()` path, if not caught by the VM/Program exception-handling wrapper, propagates as an unexpected error during transaction execution. If it escapes normal TVM exception handling (which is designed to catch `Program.Exception`/checked reverts, not arbitrary `RuntimeException`/`Error` from precompile helpers), it can crash the block-producing/validating node process while executing an attacker-submitted transaction, i.e., a remotely triggerable node crash/DoS from a single crafted transaction — a concrete "node crash or halt" outcome under the accepted impact categories.

### Likelihood Explanation
Likelihood is Medium: an attacker only needs to invoke the affected precompiled contract with a malformed `len` field in the call data; no privileged role or specific chain state is required, only that the corresponding precompile is enabled and reachable via a normal contract call. Exploitability depends on whether the surrounding TVM/`Program` execution wraps precompile calls in a broad enough catch to convert any `Throwable` into a VM revert rather than letting it crash the node — this could not be fully confirmed within the indexed code available, since the specific precompiled-contract classes that invoke `extractBytesArray`/`extractSigArray` (e.g., a batch/multi-signature validation contract) were not found in the indexed portion of `PrecompiledContracts.java`.

### Recommendation
Add explicit bounds validation in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` (and in `extractBytes`) so that `len`, `bytesOffset`, and `bytesLen` are checked against `words.length` and `data.length` before being used to index or slice, returning a safe/false result (as is already done for the `offset > words.length - 1` guard) instead of allowing out-of-range access. This aligns with the pattern already used defensively elsewhere in `PrecompiledContracts.java` (e.g. `isValidAbiEncoding`) and should be applied consistently to every helper that turns a caller-supplied length word into an array/loop bound.

### Proof of Concept
Conceptual PoC (exact precompile entry point using these helpers was not located in the indexed code, so this describes the reachable primitive, not a fully wired end-to-end transaction):
1. Construct a call to a precompiled contract whose `execute(byte[] data)` calls `extractBytesArray(words, offset, data)` (or `extractSigArray`).
2. Set the word at `offset` (interpreted as `len`) to a large value (e.g., `0xFFFFFFFF` truncated via `intValueSafe()`), while supplying only a few actual words after it.
3. The loop `for (int i = 0; i < len; i++)` then accesses `words[offset + i + 1]` beyond the actual array bounds, throwing an unchecked `ArrayIndexOutOfBoundsException` inside precompile execution — analogous to the Vim `get_text_props()` reading a `uint16` count and iterating past the real end of the line buffer.
