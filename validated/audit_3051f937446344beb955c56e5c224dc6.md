### Title
Unprivileged attacker permanently blocks a victim from opening any new collateral or debt position by dust-filling their account token lists to `MAX_TOKENS_PER_USER` - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2026-19401 (a remote, unauthenticated packet that repeatedly crashes serve children and denies service), Metronome lets any unprivileged EOA remotely force a target account into a state where every new-position entry point reverts. `Pool.MAX_TOKENS_PER_USER = 30` caps the combined length of `debtTokensOfAccount` + `depositTokensOfAccount` per account [1](#0-0) , and `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the cap is hit [2](#0-1) . Because `DepositToken.transfer`/`transferFrom` adds the token to the **recipient's** list whenever their balance goes 0 → >0 [3](#0-2) , an attacker can push dust of every registered deposit token into a victim and permanently fill all 30 slots — no privileged role required.

### Finding Description
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` on a recipient's first receipt [3](#0-2) .
- The per-account list is shared between deposit and debt tokens; `addToDebtTokensOfAccount` enforces the same combined cap [4](#0-3) .
- Any subsequent `_mint` to that account (fresh deposit, smart-farming deposit onBehalf, seized collateral) goes through `pool.addToDepositTokensOfAccount` and reverts [5](#0-4) , and `DebtToken.issue/mint` to a fresh debt token reverts the same way.
- The victim can shed one slot only by fully transferring out a dusted token, but the attacker can re-dust in the same block (front-run/back-run), making the DoS repeatable indefinitely at dust cost — the on-chain analogue of "continuously crashing the serve children".

### Impact Explanation
Temporary freezing of funds / liveness denial: while griefed, the victim cannot deposit any additional collateral type and cannot open any new debt position. If their position drifts toward liquidation, they cannot add a new collateral type to restore health — they are confined to repaying or topping up the one collateral they already hold, and can be force-liquidated while blocked. The attacker sustains the freeze by re-dusting each block; cost is only gas + negligible dust.

### Likelihood Explanation
Fully reachable by any EOA: acquire dust amounts of the pool's registered deposit tokens (or take a flash loan, deposit, receive msdTOKENs, redeem back), then `transfer` 1 wei of each to the victim. No governor, keeper, oracle, or malicious endpoint needed; no supply cap, pause flag, or health check intercepts `transfer`. The only prerequisite is that the pool lists ≥30 distinct deposit+debt tokens reachable by the victim — on deployments with fewer listed tokens the attacker covers all of them and the victim is capped at their existing set.

### Recommendation
- Remove tokens from the recipient list based on opt-in deposits rather than any inbound `transfer`, or
- Track "position" tokens (minted via Pool deposit) separately from passive ERC-20 balances, and skip `addToDepositTokensOfAccount` in `_transfer` for non-pool-initiated transfers, or
- Raise/decouple the cap and charge depositors the marginal gas of list growth.

### Proof of Concept
Foundry fork sketch against a deployed Pool:

```solidity
// contracts/Pool.sol grief test
function test_DustFillBlocksVictim() public {
    address victim = makeAddr("victim");
    IDepositToken[] memory dts = registry.getDepositTokens(); // all listed

    // Attacker: for each deposit token, mint dust for self then transfer to victim
    for (uint i; i < dts.length; i++) {
        IERC20 underlying = dts[i].underlying();
        deal(address(underlying), attacker, 1e18);
        vm.startPrank(attacker);
        underlying.approve(address(dts[i]), 1e18);
        dts[i].deposit(1e18);          // mint msdToken
        dts[i].transfer(victim, 1);    // adds token to victim's list
        vm.stopPrank();
    }
    // victim's combined list == MAX_TOKENS_PER_USER (30)

    // Victim tries a fresh deposit of a listed token -> reverts UserReachedMaxTokens
    vm.startPrank(victim);
    IERC20 underlying = dts[0].underlying();
    deal(address(underlying), victim, 1e18);
    underlying.approve(address(dts[0]), 1e18);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    // any deposit that would add a NEW token to the list fails;
    // keep re-dusting to front-run every removal attempt
    vm.stopPrank();
}
```

Key assertions: `pool.getDepositTokensOfAccount(victim).length == 30`, and every `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` for the victim reverts with `UserReachedMaxTokens` [2](#0-1) .
