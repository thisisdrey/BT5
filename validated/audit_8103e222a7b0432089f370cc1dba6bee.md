## Title
Unbounded out-of-bounds read while parsing ZIP central directory entries in ijar — (File: `third_party/ijar/zip.cc`)

## Summary

### Finding Description
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses each central-directory record of a ZIP/JAR file that has been mmap'd into memory [1](#0-0) . It reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes and then advances the cursor `p` by those lengths with no bounds validation against the mapped file's actual length: `p += file_name_length; ... p += extra_field_length; ... p += file_comment_length;` [2](#0-1) .

This is structurally different from `InputZipFile::ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before consuming `file_name_length` and `extra_field_length` bytes [3](#0-2) . The central-directory parser has no equivalent check. `FindZipCentralDirectory` only validates that the *aggregate* central directory region (`cd.central_dir_offset + cd.central_dir_size`) fits within the file [4](#0-3) , but it never validates that each individual entry's declared `file_name_length`/`extra_field_length`/`file_comment_length` stays within that aggregate region. A crafted entry can declare a name/extra/comment length far larger than the bytes actually remaining in the mapped file, causing `p` (and the inner `extra_p` cursor used to walk extra-field records at lines 524-542) to run past the end of the `mmap`ed input and read (and, via the ZIP64 extra-field branch, dereference `get_u8le`) unmapped or out-of-region memory — the same class of bug as the CGAL `SM_io_parser::read_vertex()`/`set_face()` OOB read: a length-driven cursor read with no remaining-bytes check.

### Impact Explanation
This code path (`ijar`) is invoked by Bazel to build interface jars from `.jar`/`.srcjar` inputs, including outputs of `java_import`, dependencies fetched via `http_archive`/Maven-style repository rules, and other externally-supplied jar files. A hostile origin server or mirror serving a malformed jar (whose sha256/integrity check has not yet been verified, or whose integrity attribute the attacker controls if unset) can trigger an out-of-bounds read in the native `ijar` tool, at minimum a crash (denial of the build) and at worst disclosure of adjacent process memory content into decoded fields (e.g., leaked bytes could theoretically end up copied into the interface-jar filename or extra-field buffers used downstream). This is a memory-safety violation in native code processing untrusted archive bytes, matching the class of the CGAL advisory (OOB read from unchecked length fields during binary parsing) rather than a generic third-party dependency vulnerability.

### Likelihood Explanation
Likelihood is moderate: it requires a hostile/compromised archive-serving mirror (or a case where the downloaded jar's checksum is not yet pinned) to supply a crafted jar/zip with an oversized `file_name_length`/`extra_field_length`/`file_comment_length` in a central directory record. `ijar` is invoked automatically for many Java rule dependencies, so reachability from attacker-controlled remote content is realistic, but exploitation requires the victim's build to consume such a jar before or without checksum verification succeeding.

### Recommendation
Add explicit remaining-bytes validation in `InputZipFile::ProcessCentralDirEntry` (mirroring `EnsureRemaining()` in `ProcessLocalFileEntry`) before consuming `file_name_length`, `extra_field_length`, and `file_comment_length`, and validate that `extra_p` never advances past `p` bounds inside the per-record extra-field loop (lines 526-542) so that a corrupt `data_size` field cannot walk past the end of the mapped central directory region.

### Proof of Concept
A reproducible test would construct a malformed ZIP/JAR whose end-of-central-directory record is well-formed and passes the `FindZipCentralDirectory` aggregate-size check, but whose first central directory header declares `file_name_length = 0xFFFF` (or `extra_field_length`/`file_comment_length` similarly oversized) while the actual remaining bytes in the mmap'd file are much smaller (e.g., the record sits near the end of a short file). Running `ijar` (or any Bazel action invoking `ijar`, e.g. via a `java_library`/`java_import` depending on such a jar) against this file should be verified with ASan/UBSan-instrumented builds of `third_party/ijar:zip` to demonstrate a heap-buffer-overflow read when `ProcessCentralDirEntry` executes the `memcpy`/`get_u4le`/`get_u2le` calls past the mapped region. I was not able to execute or build this PoC in this environment; a background Devin session with build/test tooling would be needed to construct and run the JUnit/shell-based repro (e.g., under `src/test/shell/bazel/` or a new `third_party/ijar` unit test with ASan) and confirm the crash/OOB read empirically.

**Note on completeness:** I could not fully trace whether any higher-level caller (e.g., `singlejar` vs `ijar` proper, or the Bazel client's own archive extraction code in `src/main/cpp/archive_utils.cc`) re-validates or re-parses these fields before use, nor could I confirm from static reading alone whether ASan/fuzzing already covers this path in CI — a live build/fuzz run would be required to conclusively confirm exploitability versus a latent-but-unreachable defect.
