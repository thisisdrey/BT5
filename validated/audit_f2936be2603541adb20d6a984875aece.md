### Title
Praefect serialized-write lock silently no-ops when a transaction has no recorded `PREPARING_PHASE`, letting concurrent writers bypass repo-level serialization - (File: `internal/praefect/transactions/manager.go`)

### Summary

### Finding Description
Praefect's serialized-write feature is meant to guarantee that only one reference-transaction per repository can advance past ref-locking at a time, closing a cross-node deadlock where two transactions each hold a ref lock the other needs [1](#0-0) . The guarantee is implemented purely through a state machine keyed by `transactionID`: `PREPARING_PHASE` acquires a Postgres-backed repo lock, `PREPARED_PHASE`/`COMMITTED_PHASE` renew or release it [2](#0-1) .

The bug is that `lockRepoForTransaction` treats "no lock was recorded for this transaction ID" as an implicit pass rather than a failure: if a transaction reaches `PREPARED_PHASE`/`COMMITTED_PHASE` without ever having registered a `PREPARING_PHASE` lock, the function silently returns `nil` and skips serialization entirely, instead of rejecting the vote or otherwise forcing the transaction to go through the exclusivity check: [3](#0-2) 

This is directly analogous to the reported smart-contract flaw: there is no persisted notion of "the currently active/authoritative operation" that later phases are validated against. A transaction is allowed to reach the commit-equivalent step (`COMMITTED_PHASE`, which drives `unlockRepoForTransaction`'s "release the lock, the write is durable" branch) purely because a boolean/lookup came back empty, exactly as `settleVault` succeeded purely because there was no stored "active proposal id" to check the stale proposal against.

The gap is explicitly acknowledged as by-design tolerance for old Git binaries lacking the `preparing` hook phase (pre `60d8c1e9…`, i.e., before Git v2.54.0) [4](#0-3) , but it is not gated to only the legacy code paths that structurally cannot vote `Preparing` — it is a blanket fallback inside the shared phase handler used by every transaction, including the write paths that were updated to emit `Preparing` (`update_with_hooks.go`, `repoutil/create.go`, `objectpool/fetch.go`, `service/operations/squash.go`, etc.) as well as the paths still calling `git update-ref`/`git fetch` directly and thus never emitting `Preparing` in the first place (`FetchSourceBranch`, `Replicate`, `ResolveConflicts`, `UserCommitFiles`, `UserRevert`, `RebaseToRef`, `MergeToRef`) [5](#0-4) .

### Impact Explanation
Because the fallback is silent (only a debug log line, no error, no metric distinguishing "serialization active" from "serialization dormant"), any ordinary user's push/fetch/RPC that lands on one of the still-unconverted write paths, or on a cluster whose bundled Git predates the `preparing` phase commit, reintroduces exactly the deadlock scenario the feature was built to prevent: two concurrent transactions can each take on-disk ref locks on different nodes for overlapping references and stall each other, since neither goes through the exclusive Postgres lock before locking refs [6](#0-5) . This is a reachable, unprivileged, ordinary-push-triggered DoS of the reference-transaction handling path across a Gitaly Cluster, silently degrading correctness/availability guarantees the feature advertises, with no operator-visible signal that the protection is inactive for a given transaction.

### Likelihood Explanation
Likelihood is moderate-to-high in mixed-fleet or partially-migrated clusters: any RPC using the listed direct `update-ref`/`fetch` write paths permanently skips `PREPARING_PHASE` by design, so every transaction through those paths silently runs with serialization dormant, and a normal user issuing two concurrent conflicting writes (e.g., two pushes updating overlapping refs, or push + `Replicate`) is enough to reach the deadlock precondition without any special privilege, malicious peer, or crafted RPC field — a routine two-writer race is sufficient.

### Recommendation
Do not treat a missing `repoLocks` entry as success. Distinguish structurally-exempt call sites (those that intentionally never call `PREPARING_PHASE`, e.g., `git update-ref`/`git fetch`-driven paths) from ones where the absence indicates an old Git binary or a dropped vote, and:
- For call sites expected to always cast `Preparing`, treat a missing lock at `PREPARED_PHASE`/`COMMITTED_PHASE` as an error and abort the transaction (`ErrTransactionFailed`) rather than silently continuing.
- Track a `transactionID -> requires-preparing` capability (e.g., derived from client Git version negotiation or the RPC being invoked) so the skip path only applies to the paths in the documented Limitations list, not universally.
- Surface a metric/log at `WARN` (not `DebugContext`) whenever serialization is skipped so operators can detect when the protection is dormant in production.

### Proof of Concept
Not independently reproduced against a live Postgres-backed cluster in this analysis; the vulnerable code path is demonstrated statically:
1. `mgr.lockRepoForTransaction` is called at `PREPARED_PHASE`/`COMMITTED_PHASE` for `transactionID` X.
2. `mgr.repoLocks.Load(X)` returns `!ok` — because either (a) the write path never emits `Preparing` (see Limitations list), or (b) the bundled Git build predates `60d8c1e9…`.
3. The function returns `nil` unconditionally at `internal/praefect/transactions/manager.go:298`, allowing transaction X's vote to proceed to commit with no repo-level mutual exclusion, exactly as a second transaction Y for the same repository concurrently does the same, reproducing the ref-lock deadlock described in `doc/serialized_writes.md`'s "Why Serialize Writes" section. ## Why Serialize Writes

The voting protocol relies on Git's `reference-transaction` hook to vote on a
ref update at each phase of the transaction. The phases Git historically
exposed are:

- `prepared` — references have been locked on disk
- `committed` — updates have been persisted
- `aborted` — the transaction was rolled back

Praefect collects votes from all Gitaly nodes participating in the transaction
and only allows the write to proceed when quorum is reached.

The problem is that at the `prepared` phase, **on-disk ref locks have already
been taken**. With two concurrent transactions T1 and T2 updating overlapping
refs A and B:

1. Node 1: T1 locks A, T2 locks B
1. Node 2: T2 locks A, T1 locks B

Each transaction is now waiting for the other to release a lock, and neither
can release until quorum is reached for its own lock. The cluster is
deadlocked.

The fix is to serialize transactions **before** any node has taken an on-disk
ref lock. If only one transaction per repository can advance past this point at
a time, lock acquisition order is globally consistent and the deadlock above
cannot occur.

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
	return nil
}
