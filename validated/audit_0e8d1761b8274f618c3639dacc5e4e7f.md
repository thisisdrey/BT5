### Title
`RewardsDistributor._calculateTokenDelta` treats an unset `accountIndexOf` as 0 instead of `INITIAL_INDEX` when the global index still equals `INITIAL_INDEX`, letting a same-block caller accrue rewards equal to their entire token balance - (File: contracts/RewardsDistributor.sol)

### Summary
The Keras bug is a guard that conflates "unset" (`None`) with "explicitly disabled" (`False`), skipping a deny check. The Metronome analog is in `RewardsDistributor._calculateTokenDelta`: an unset `accountIndexOf[token][account]` (i.e. `0`) is only normalized to `INITIAL_INDEX` when the global `tokenIndex` is *strictly greater* than `INITIAL_INDEX`. When the global index still equals `INITIAL_INDEX` — which is true during the entire block in which a reward token's speed is first set — the unset account index stays `0`, producing a `_deltaIndex` of `1e18` and crediting the account `balance * 1e18 / 1e18 = balance` reward tokens out of thin air.

### Finding Description
`_updateTokenSpeed` initializes a new reward token with `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` the first time its speed is set to non-zero (contracts/RewardsDistributor.sol:294-299). Until `_updateTokenIndex` observes `_deltaTimestamps > 0` with `_speed > 0` and `_totalSupply > 0`, the stored index remains exactly `INITIAL_INDEX` (contracts/RewardsDistributor.sol:197-212).

`_calculateTokenDelta` contains the conflation bug:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```
(contracts/RewardsDistributor.sol:217-231)

An account that has never had its index recorded (`accountIndexOf == 0`) should accrue nothing for the period before it first interacted. The normalization only fires when `_tokenIndex > INITIAL_INDEX`; at `_tokenIndex == INITIAL_INDEX` the missing index is treated as literal `0`, yielding `_deltaIndex == 1e18` and `_tokensDelta == balanceOf(account)` (via `wadMul`).

`updateBeforeMintOrBurn` and `updateBeforeTransfer` are both callable by anyone (the NatSpec on `updateBeforeMintOrBurn` explicitly says so) and invoke this path whenever `tokenStates[token_].index > 0` (contracts/RewardsDistributor.sol:175-192). `claimRewards` then pays out `tokensAccruedOf[account]` from the distributor's `rewardToken` balance with no further checks (contracts/RewardsDistributor.sol:150-168, 248-256).

Attack trace (unprivileged EOA only):
1. Before any speed is set for deposit token `D`, attacker deposits and holds a large `D` balance. All index hooks are no-ops because `tokenStates[D].index == 0`.
2. Governor's `updateTokenSpeed(D, s)` (or keeper's `syncTokenSpeed`) tx lands in block `T`, setting `index = INITIAL_INDEX`.
3. In the same block `T` (same `block.timestamp`, so `_calculateTokenIndex` returns `(0,0)` and the index stays `INITIAL_INDEX`), the attacker calls `updateBeforeMintOrBurn(D, attacker)` — permissionless — which writes `tokensAccruedOf[attacker] += D.balanceOf(attacker)` and `accountIndexOf = INITIAL_INDEX`.
4. Same tx or next: `claimRewards(attacker)` transfers `min(accrued, rewardToken balance of distributor)` to the attacker.

No modifier stops this: `updateBeforeMintOrBurn` is permissionless, `claimRewards` is `nonReentrant` only, and neither pause flags nor SynthContext checks apply.

### Impact Explanation
Direct theft of reward tokens held by the distributor, including yield accrued-but-not-yet-claimed by all other users (`tokensAccruedOf` is paid out of the shared `rewardToken` balance in `_transferRewardIfEnoughTokens`). The payout scales linearly with the attacker's `DepositToken`/`DebtToken` balance, so a whale or a user who has held a large position since before rewards began can drain the distributor in one transaction.

### Likelihood Explanation
The window is the block in which a token's speed transitions from 0 to non-zero while `tokenStates[token_].index == 0`. `updateTokenSpeed`/`updateTokenSpeeds` are governor calls (multisig, publicly visible in the mempool / batch), and `syncTokenSpeed` is callable by the keeper — the attacker only needs to be included in the same block, not to front-run strictly. On mainnet this is achievable with a standard backrun bundle; on L2 deployments the same-timestamp requirement still holds whenever the attacker can land the tx in the same sequencer block. The attacker must hold a meaningful `DepositToken` balance beforehand, which costs only the deposit itself (redeemable afterwards). Reward payouts do not require the distributor to have accrued that value — it pays whatever balance it has.

### Recommendation
Treat "unset" as "at the initial index" unconditionally, mirroring the deny-by-default fix in Keras:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

or equivalently, when `_tokenIndex <= INITIAL_INDEX` and `_accountIndex == 0`, set `_accountIndex = _tokenIndex` so `_deltaIndex` is 0. Add a fork test that deposits, calls `updateTokenSpeed`, then calls `updateBeforeMintOrBurn` + `claimRewards` in the same block and asserts zero payout.

### Proof of Concept
Hardhat fork sketch:

```ts
// Setup: pool, depositToken (D), rewardsDistributor (RD), rewardToken funded in RD.
// 1. Attacker deposits underlying and holds D while speed[D] == 0 (index == 0).
await underlying.approve(depositToken.address, LARGE);
await depositToken.deposit(LARGE, attacker.address);

// 2. Governor enables rewards for D in block T.
await distributor.connect(governor).updateTokenSpeed(depositToken.address, SPEED);
// mine a same-timestamp context: use setNextBlockTimestamp equal or include calls
// via a single block (e.g., automine off, or Operator.execute batch).

// 3. Same block/timestamp: attacker self-updates and claims.
await distributor.connect(attacker).updateBeforeMintOrBurn(depositToken.address, attacker.address);
// tokensAccruedOf[attacker] == depositToken.balanceOf(attacker)
await distributor.connect(attacker).claimRewards(attacker.address);
// rewardToken balance of attacker == min(balanceOf(attacker in D), RD rewardToken balance)
```

Expected: attacker receives `≈ D.balanceOf(attacker)` reward tokens despite rewards having been enabled for zero seconds, draining the distributor.
