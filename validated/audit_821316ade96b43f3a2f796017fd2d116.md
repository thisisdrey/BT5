### Title
Unauthenticated write to the stacks-signer's event-receiver HTTP endpoint allows forging node events (`StackerDBChunksEvent`, `BlockValidateResponse`, `BurnBlockEvent`, `StacksBlockEvent`) - (File: libsigner/src/events.rs)

### Summary
The `ContributionNft::mint` bug is a public write path with no caller authorization, letting an unprivileged party inject attacker-controlled state that downstream logic treats as authentic. The direct analog in this repo is `SignerEventReceiver::next_event` in `libsigner/src/events.rs`, the transport-layer HTTP listener that the stacks-signer binds to receive event pushes from its paired stacks-node. It dispatches on URL path (`/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/new_block`, `/shutdown`, `/status`) and hands the body straight to `process_event`/`TryFrom` without ever checking any authentication header or shared secret on the incoming request.

### Finding Description
`SignerEventReceiver::next_event` [1](#0-0)  reads an HTTP request from the bound socket and, purely based on `request.url()`, routes it to `process_event::<T, StackerDBChunksEvent>`, `process_event::<T, BlockValidateResponse>`, `process_event::<T, BurnBlockEvent>`, or `process_event::<T, StacksBlockEvent>`. There is no call to inspect an `Authorization` header, no comparison against any configured secret, and no peer/IP check anywhere in this function or in `process_event` [2](#0-1) . The only "gate" is the URL string match — any TCP client that can reach the bound port can supply a request with the right path and a JSON body, and it will be deserialized and forwarded to the signer's runloop channel via `forward_event`.

The project's documentation and sample configs describe an `auth_token` (node side, `connection_options.auth_token`) that is meant to match the signer's `auth_password`, and warn explicitly that exposing the signer's endpoint beyond a local/trusted network is dangerous [3](#0-2)  and [4](#0-3) . However, no code in `libsigner/src/events.rs` — the file that actually implements the HTTP receiver bound to that `endpoint` — reads or verifies any authorization header on inbound requests. Grepping the transport code confirms there is no `header(...)`/`headers()` usage in this file at all, i.e., the auth mechanism referenced in the docs is not enforced at this layer.

This breaks the intended equality "request originates from the paired, trusted stacks-node" vs. "any TCP peer that can open a socket to the configured endpoint," analogous to the missing `msg.sender == proposer` check in the reported bug — the gate that should authenticate the writer of state is absent.

Some payload types do carry their own internal signature checks further downstream (e.g., `StackerDBChunkData::recover_pk()` for signer-to-signer message chunks under the `SIGNERS_NAME` contract [5](#0-4) ), but:
- The `MinerMessages` branch deserializes chunk data directly with no signature check at this layer [6](#0-5) .
- `BlockValidateResponse` (`/proposal_response`) and `BurnBlockEvent`/`StacksBlockEvent` (`/new_burn_block`, `/new_block`) have no equivalent signature-based authentication at all in this transport — they are trusted purely because "the node sent them," which is exactly the assumption this endpoint fails to enforce.

### Impact Explanation
Any remote, unprivileged party able to reach the signer's bound listener (default `0.0.0.0`-style bindings appear in sample configs, and the docs themselves warn about exposure risk) can push forged `BlockValidateResponse`, `BurnBlockEvent`, or `StacksBlockEvent` messages directly into the signer's internal event channel, exactly as if the paired node had sent them. This is an unauthenticated write into the signer's runtime state pipeline — the transport-layer equivalent of `ContributionNft::mint`'s missing caller check, and squarely matches the rule's example of "an auth-gate that fails open." Because there is no cryptographic binding tying these HTTP-level "node events" to a legitimate node identity at the point they enter the signer, an attacker on the exposed port can supply arbitrary/forged inputs that the signer will treat as genuine chain/validation events (the actual consequences on the decision loop are downstream signer logic, which is out of scope, but the injection point itself is squarely in-scope transport code and is unauthenticated by design as written).

### Likelihood Explanation
No cryptographic material, node key, or privileged role is required — only network reachability to the configured `endpoint` (a bare TCP `tiny_http` socket, as seen from `HttpServer::http(listener)` in `bind` [7](#0-6) ). Any operator who follows the sample configs without further external firewalling, or any signer reachable over a shared network, is exposed. The vulnerability requires zero preconditions besides connectivity — high likelihood in any deployment where the signer's endpoint is not strictly firewalled to loopback/VPN, which the docs themselves flag as a real-world risk.

### Recommendation
Enforce the documented `auth_token`/`auth_password` (or an equivalent shared-secret/HMAC or mTLS scheme) inside `SignerEventReceiver::next_event`/`process_event` before dispatching any `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` request: reject with 401 if the `Authorization` header is missing or does not match the configured secret, mirroring the pattern already used for the node's own `/v3/block_proposal` RPC endpoint (`postblock_proposal.rs`), which does check an `authorization` header against a configured password [8](#0-7) .

### Proof of Concept
1. Stand up a `SignerEventReceiver` bound to `endpoint` per a sample signer config (e.g., `127.0.0.1:30000` or an externally reachable address per deployment).
2. From an unprivileged remote client with no knowledge of any secret, send:
```
POST /proposal_response HTTP/1.1
Host: <signer-endpoint>
Content-Type: application/json
Content-Length: <n>

{ ...forged BlockValidateResponse JSON... }
```
3. `next_event` matches `request.url() == "/proposal_response"` and calls `process_event::<T, BlockValidateResponse>(request)` with no authentication check [9](#0-8) .
4. `process_event` reads the body, JSON-deserializes it, and converts it into a `SignerEvent`, which is then forwarded to the signer's runloop via `forward_event` [2](#0-1) , indistinguishable from a genuine push by the paired node.

    fn next_event(&mut self) -> Result<SignerEvent<T>, EventError> {
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }
            debug!("Request handling");
            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

            if request.method() != &HttpMethod::Post {
                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));
            }
            debug!("Processing {} event", request.url());
            if request.url() == "/stackerdb_chunks" {
                process_event::<T, StackerDBChunksEvent>(request)
            } else if request.url() == "/proposal_response" {
                process_event::<T, BlockValidateResponse>(request)
            } else if request.url() == "/new_burn_block" {
                process_event::<T, BurnBlockEvent>(request)
            } else if request.url() == "/shutdown" {
                event_receiver.stop_signal.store(true, Ordering::SeqCst);
                Err(EventError::Terminated)
            } else if request.url() == "/new_block" {
                process_event::<T, StacksBlockEvent>(request)
            } else {
                let url = request.url().to_string();
                debug!(
                    "[{:?}] next_event got request with unexpected url {}, return OK so other side doesn't keep sending this",
                    event_receiver.local_addr,
                    url
                );
                ack_dispatcher(request);
                Err(EventError::UnrecognizedEvent(url))
            }
        })?

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
