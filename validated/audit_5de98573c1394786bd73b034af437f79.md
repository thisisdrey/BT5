### Title
Closing a lending account Balance wipes `emissions_outstanding` without settling it, permanently freezing accrued emissions rewards - ([File: programs/marginfi/src/instructions/marginfi_account/close_balance.rs])

### Summary
`lending_account_close_balance` and the internal `repay_all`/`close_balance` paths zero out an account's per-bank `Balance` slot — including `emissions_outstanding`, the field that tracks a user's unclaimed emissions/incentive rewards for that position — without first settling or paying out that reward. This is the same bug class as the reported ALCX issue: a position-closing operation forgets to flush an accrued, separately-tracked reward balance before destroying the state that holds it, permanently freezing those rewards.

### Finding Description
Each `Balance` slot tracks unclaimed protocol emissions independently of asset/liability shares: [1](#0-0) 

`lending_account_close_balance` accrues bank interest and updates the bank cache, then immediately calls `BankAccountWrapper::close_balance`, with no call to any emissions-settlement routine beforehand: [2](#0-1) 

`close_balance` (and the sibling `repay_all` used when fully repaying a liability) only validates that liability/asset amounts are zero, then calls `balance.close()`, which (per `Balance::empty_deactivated()`, the same zeroing template used for a cleared balance) resets every field of the slot — including `emissions_outstanding` — to zero: [3](#0-2) [4](#0-3) 

Notably, the error enum already defines `CannotCloseOutstandingEmissions` ("Cannot close balance because of outstanding emissions"), which strongly implies the protocol was intended to block closing a balance while emissions are still outstanding — but this check is not invoked anywhere in `close_balance.rs`: [5](#0-4) 

By contrast, `transfer_to_new_account`/`transfer_to_new_account_pda` correctly preserve `emissions_outstanding` by copying the entire `lending_account` (all `Balance` slots) to the new account before disabling the old one, showing the protocol is aware that `emissions_outstanding` must be carried forward across account-lifecycle operations: [6](#0-5) 

The `close_balance`/`repay_all` paths do not follow this same discipline — they simply discard the field.

### Impact Explanation
Any user who has accrued protocol emissions on a bank position and then closes that balance (either via `lending_account_close_balance` after their asset/liability shares reach zero, or via `repay_all` when fully repaying a loan) permanently loses whatever emissions had accrued to `emissions_outstanding` for that balance slot. This is a permanent freezing/loss of yield already earned by the user — funds that the protocol/emissions campaign owes them become unclaimable once the balance record that tracked them is zeroed and its slot is reused.

### Likelihood Explanation
This is trivially reachable by any ordinary user with an active emissions campaign on a bank they use: deposit, wait for emissions to accrue on the position (`emissions_outstanding` increases), then repay-in-full or close the balance normally through routine account management. No special privileges, precise timing, or adversarial setup are required — only a bank with an active emissions campaign and a user who closes out a position instead of first claiming emissions.

### Recommendation
Before zeroing a `Balance` slot in `close_balance`/`repay_all`, settle or transfer `emissions_outstanding`: either require it to be zero (mirroring the already-defined but unused `MarginfiError::CannotCloseOutstandingEmissions`, forcing users to claim first) or automatically flush/pay it out (or migrate it to a dust/claimable bucket) as part of the close path, analogous to how dust asset/liability amounts are already routed to `collected_insurance_fees_outstanding` in the same function.

### Proof of Concept
Conceptual reproduction (mirrors the reported ALCX PoC pattern):
1. User deposits into a bank with an active emissions campaign; `Balance.emissions_outstanding` accrues over time.
2. User fully repays any liability / withdraws all assets, then calls `lending_account_close_balance` (or repays in full, triggering `repay_all`, which also calls `balance.close()`).
3. Inspect the account after the call: `balances[i].emissions_outstanding` is now `0`, and the slot is deactivated/reset via `Balance::close()`, matching the zeroing template in `empty_deactivated()`.
4. There is no subsequent path to recover the previously-accrued, non-zero `emissions_outstanding` value that existed prior to step 2 — it has been permanently lost, since no settlement/claim instruction was invoked in `close_balance.rs` before the reset.

Note: I could not fully view the exact body of `Balance::close()` (only its call sites and the near-identical `empty_deactivated()` zeroing constructor) or the emissions-claim instruction logic (`emissions.rs`) within available tool calls; the mechanism by which `emissions_outstanding` is normally paid out and the exact byte-for-byte definition of `close()` should be verified directly in `type-crate/src/types/user_account.rs` and `programs/marginfi/src/instructions/marginfi_account/emissions.rs` to confirm there is no last-chance settlement performed inside `close()` itself.

pub fn lending_account_close_balance(ctx: Context<LendingAccountCloseBalance>) -> MarginfiResult {
    let LendingAccountCloseBalance {
        marginfi_account,
        bank: bank_loader,
        group: marginfi_group_loader,
        ..
    } = ctx.accounts;

    let mut marginfi_account = marginfi_account.load_mut()?;
    let mut bank = bank_loader.load_mut()?;

    check!(
        !marginfi_account.get_flag(ACCOUNT_DISABLED),
        MarginfiError::AccountDisabled
    );

    let group = &*marginfi_group_loader.load()?;
    bank.accrue_interest(
        Clock::get()?.unix_timestamp,
        group,
        #[cfg(not(feature = "client"))]
        bank_loader.key(),
    )?;

    bank.update_bank_cache(group)?;

    let in_receivership = marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP);
    let lending_account: &mut marginfi_type_crate::types::LendingAccount =
        &mut marginfi_account.lending_account;
    let mut bank_account =
        BankAccountWrapper::find(&bank_loader.key(), &mut bank, lending_account)?;

    bank_account.close_balance(in_receivership)?;
    lending_account.sort_balances();
    marginfi_account.sync_indexer_flags();
    marginfi_account.last_update = Clock::get()?.unix_timestamp as u64;

    Ok(())
}

    /// When `in_receivership` is true, clears the bank's liquidation price cache lock
    /// so that banks whose balances are closed mid-liquidation don't stay permanently locked.
    pub fn close_balance(&mut self, in_receivership: bool) -> MarginfiResult<()> {
        let balance = &mut self.balance;
        let bank = &mut self.bank;

        let current_liability_amount =
            bank.get_liability_amount(balance.liability_shares.into())?;
        let current_asset_amount = bank.get_asset_amount(balance.asset_shares.into())?;

        check!(
            current_liability_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::IllegalBalanceState,
            "Balance has existing debt"
        );

        check!(
            current_asset_amount.is_zero_with_tolerance(ZERO_AMOUNT_THRESHOLD),
            MarginfiError::IllegalBalanceState,
            "Balance has existing assets"
        );

        let asset_shares: I80F48 = balance.asset_shares.into();
        let liability_shares: I80F48 = balance.liability_shares.into();

        // `ZERO_AMOUNT_THRESHOLD` upward; match that condition so we don't
        // double-decrement positions that already crossed downward earlier.
        let had_assets = asset_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);
        let had_liabs = liability_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);

        balance.close()?;
