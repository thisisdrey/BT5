### Title
`try_replace_chunk()` never enforces `write_freq`, letting a remote signer bypass the StackerDB's minimum-write-interval control - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`StackerDBConfig::write_freq` is documented as "the minimum wall-clock time between writes to the same slot" [1](#0-0)  and every slot's `write_time` is persisted on each write [2](#0-1) . However, the sole function that actually authorizes and commits a chunk write, `StackerDBTx::try_replace_chunk`, never reads or compares `write_time` against `write_freq`; it only checks chunk size, slot signer, staleness, and `max_writes` before calling `insert_chunk` [3](#0-2) . This is exactly the missing-guard pattern in the analog report: a control (`write_freq`/cooldown) that exists in the schema/config but is not enforced at the actual write gate.

### Finding Description
The write authorization path is `try_replace_chunk` → `insert_chunk`:
- `try_replace_chunk` validates: chunk size vs `config.chunk_size`, slot existence, signature vs `slot_validation.signer`, staleness (`slot_version <= slot_validation.version`), and `slot_version > config.max_writes` [4](#0-3) .
- Nowhere in this function is `slot_validation.write_time` compared against `get_epoch_time_secs()` and `self.config.write_freq`, even though `net_error::TooFrequentSlotWrites(deadline)` exists as a dedicated error variant for this exact case [5](#0-4)  and `SlotValidation` tracks `write_time` for this purpose [2](#0-1) .
- The peer-network's own message-level validator (`validate_received_chunk`) explicitly documents that it "does not check write frequency, since the caller has different ways of doing this" [6](#0-5) , and `handle_unsolicited_StackerDBPushChunk`'s doc comment states the write frequency is deliberately not checked there because bandwidth throttling on the `ConversationP2P` is assumed to cover it [7](#0-6) . Both of these push the responsibility of enforcing `write_freq` downstream onto the DB-write layer (`try_replace_chunk`), on the assumption that it is the final gate. But that final gate never performs the check — the `TooFrequentSlotWrites` error type is defined and displayed in `stackslib/src/net/mod.rs` but is dead code; it is never constructed or returned by `try_replace_chunk`, `insert_chunk`, or anywhere else in `stackslib/src/net/stackerdb/db.rs`.
- Consequently, a remote peer that legitimately owns a StackerDB slot (has the private key for `slot_validation.signer`) can submit as many chunk writes as it wants, back-to-back, bounded only by `max_writes` and normal network throughput — the smart contract's configured minimum write interval (`write-freq`) is never actually enforced on the node accepting the write, regardless of whether the write arrives via direct `POST /stackerdb/chunk` or via P2P push/sync (`process_stacker_db_chunks` in `stackslib/src/net/relay.rs`, which also just calls `tx.try_replace_chunk` [8](#0-7) ).

### Impact Explanation
This breaks an equality the protocol relies on: "chunk write accepted" should imply "at least `write_freq` seconds elapsed since the slot's last write," but the code accepts writes unconditionally with respect to time. Since StackerDB chunks are broadcast to the whole network on successful storage [9](#0-8) , an authorized-but-malicious (or compromised) slot signer can flood every replicating node and the P2P network with an unbounded rate of signed writes/broadcasts for its slot, up to `max_writes`, defeating a rate-limit control that operators and contracts rely on to bound bandwidth/storage churn and gossip volume for a given StackerDB (e.g., signer message DBs, miner DBs). This is a legitimate, signature-valid write path — not a forged-signature bypass — but it defeats an intended anti-spam/anti-flood control that the config schema explicitly exposes (`write-freq`) and that the code's own comments assume is enforced "downstream" at this exact function.

### Likelihood Explanation
High likelihood of triggering: any legitimate slot owner (which could be any signer configured via the `stackerdb-get-config`/`stackerdb-get-signer-slots` contract, not an admin or the node operator) can trivially exploit this by simply submitting rapid, validly-signed, monotonically-increasing-version chunks — no race condition or clock manipulation is needed, since the check is simply absent. It requires only a valid slot-owner private key, which is the intended remote-caller model for StackerDB, and no additional privilege.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `insert_chunk`, fetch the slot's last `write_time` (already returned via `get_slot_validation`) and reject the write with `net_error::TooFrequentSlotWrites(deadline)` if `get_epoch_time_secs() < slot_validation.write_time + self.config.write_freq`. Since `write_freq` currently defaults to `0` in most configs/tests [10](#0-9) , this fix would only change behavior for StackerDB contracts that configure a non-zero `write-freq`, which is precisely the case the guard is meant to protect.

### Proof of Concept
1. Deploy/configure a StackerDB control contract with `write-freq: u3600` (i.e., one write per hour per slot) and a signer key `pk` owning slot 0.
2. As the holder of `pk`, submit `StackerDBChunkData{slot_id: 0, slot_version: 1, ...}` signed with `pk` via `POST /v2/stackerdb/<contract>/chunks` (handled by `poststackerdbchunk.rs`, which calls into `try_replace_chunk`) — succeeds.
3. Immediately submit `slot_version: 2` with the same key, signed correctly, with `slot_version` still `<= max_writes` — per `try_replace_chunk`'s checks (`stackslib/src/net/stackerdb/db.rs:406-436`), this only checks chunk size / signer / staleness / max-writes, and succeeds even though `write_freq=3600` seconds have not elapsed.
4. Repeat as fast as network/API throughput allows, each successful write causing the node to broadcast `StackerDBPushChunk` to the P2P network (`stackslib/src/net/relay.rs:2445-2452`), demonstrating the `write-freq` cooldown is never enforced.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
