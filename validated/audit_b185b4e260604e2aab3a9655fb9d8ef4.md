### Title
Terminal relay forwarding trusts an unauthenticated `RelayFromAddr` field, letting a relay's own peer register/decrypt-into relay state for a victim it never authenticated with - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` derives the “owner” of a relay slot (`from`) entirely from the attacker‑controlled `NebulaControl.RelayFromAddr`/`OldRelayFromAddr` field of an inbound `Control` message, rather than from the sender's authenticated certificate identity (`h.vpnAddrs`). This mirrors the `VestedZeroNFT.split()` bug class: a privileged, state‑mutating operation keys off a caller‑supplied identifier instead of verifying that the identifier actually belongs to the authenticated caller.

### Finding Description
`Interface.readOutsidePackets` decrypts a `header.Control` packet using the already-authenticated `hostinfo` for the sending peer and hands the plaintext to `relayManager.HandleControlMsg(hostinfo, out, f)`: [1](#0-0) 

`HandleControlMsg` unmarshals the message and dispatches to `handleCreateRelayRequest(v, h, f, msg)`, where `h` is the authenticated `HostInfo` of the sender: [2](#0-1) 

Inside `handleCreateRelayRequest`, `from` is taken directly from `m.RelayFromAddr` (or the legacy `OldRelayFromAddr`), a field fully controlled by the sender's plaintext payload, not derived from `h`'s verified certificate identity (`h.vpnAddrs`): [3](#0-2) 

The only sanity check performed is that `from` isn't *my own* address (`f.myVpnAddrsTable.Contains(from)`); there is no check that `from == h.vpnAddrs[0]` (or any address in `h`'s certified networks). Since the sender `h` is only proven to own its own certificate identity, `from` can be forged to any vpn address value the attacker chooses, e.g., a legitimate third peer ("victim") the attacker's node has never even handshaked with. The code then uses this unverified `from` to call `AddRelay`, which installs a `Relay` object into `h.relayState` and into `hm.Relays[index]` keyed by the attacker-chosen `from`: [4](#0-3) 

This is directly analogous to `VestedZeroNFT.split(tokenId, fraction)`, where the function used an attacker‑supplied `tokenId` to mutate/mint state without checking that `msg.sender` actually owned that `tokenId`. Here, `from` plays the role of `tokenId`: the code should require `from` to match `h`'s own certified vpn address (the only identity `h` has proven ownership of via the Noise handshake and certificate verification), but no such check exists.

### Impact Explanation
Once the relay is installed under the forged `from` value, the local node believes it has agreed to relay traffic on behalf of that (spoofed) identity through `h`, and later replies with `CreateRelayResponse` addressed using that same unverified `from`/`RelayFromAddr` value (see `handleCreateRelayResponse`, which similarly trusts `m.RelayFromAddr`/`RelayToAddr` without cross-checking against any certified identity): [5](#0-4) 

This lets an attacker who has any single authenticated tunnel to a relay-capable node poison that node's relay state (`hm.Relays`, `relayState`) with an entry impersonating an arbitrary victim vpn address, without ever proving control of the victim's certificate/private key. Practically this can be used to:
- Register relay state that misattributes a legitimate victim identity to the attacker's tunnel, corrupting relay-index bookkeeping (`hm.Relays[index]`, `relayState.relayForByAddr/relayForByIdx`) — remote state poisoning of the relay subsystem.
- Potentially hijack “forwarding” relay slots intended to reach a target, redirecting traffic that should flow to/through the legitimate victim into the attacker's controlled tunnel instead, since `ForwardingType` relay lookups key off `relay.PeerAddr`, which originates from this unauthenticated `from`/`target` pair (`outside.go` `handleOutsideRelayPacket`, `QueryVpnAddrsRelayFor`).

This does not itself decrypt victim traffic (relayed payloads still pass through `SendVia`/`Decrypt` under the real per-tunnel Noise keys), so the worst confirmed impact is corruption/poisoning of relay routing state and potential denial-of-service/misdirection of relay-based traffic, not outright decryption — impact is bounded by how deeply relay state is trusted downstream (`outside.go:176-248`).

### Likelihood Explanation
Any node that can establish one legitimate, authenticated tunnel to a relay-capable Nebula node (`relay.am_relay = true` on the peer) can send a `Control`/`CreateRelayRequest` message with an arbitrary `RelayFromAddr`. No additional certificate or privilege is required beyond a normal handshake, and the vulnerable code path is reached on every `CreateRelayRequest` processed by a relay node, making this straightforward and reliably reachable for an authenticated-but-untrusted peer in a relay-enabled mesh.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), require that the initiator-supplied `from`/`RelayFromAddr` equal an address actually present in `h.vpnAddrs` (the certificate-verified identity of the immediate sender) before installing or updating any `Relay` state, exactly as `Firewall.Drop` already validates `fp.RemoteAddr` against `h.vpnAddrs`/`h.networks`: [6](#0-5) 
If forwarding relays legitimately need `from` to differ from the immediate sender (multi-hop relay chains), that trust decision must be made explicit and bounded (e.g., only permitted when `h` itself is a certified relay for that address, verified via existing relay state), never accepted unconditionally from message content.

### Proof of Concept
Not independently executable within this repo (no test harness constructed here), but the vulnerable path can be exercised as follows:
1. Attacker node `E` establishes a normal, authenticated tunnel to relay node `R` (`R` has `relay.am_relay=true`).
2. `E` crafts a `NebulaControl{Type: NebulaControl_CreateRelayRequest, RelayFromAddr: <victim's vpn addr>, RelayToAddr: <target>}` and sends it as a `header.Control` message over its legitimate tunnel to `R`.
3. `R`'s `readOutsidePackets` decrypts it under `E`'s real session keys and calls `relayManager.HandleControlMsg(hE, out, f)` → `handleCreateRelayRequest(v, hE, f, msg)`.
4. Inside, `from := protoAddrToNetAddr(m.RelayFromAddr)` becomes the victim's address; `f.myVpnAddrsTable.Contains(from)` is false (it's the victim, not `R`), so the check passes, and `R` installs `hE.relayState`/`hm.Relays[index]` keyed to the victim's identity — despite `hE` never having proven ownership of the victim's certificate. [7](#0-6)

	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}

func (rm *relayManager) handleCreateRelayResponse(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	relayFrom := protoAddrToNetAddr(m.RelayFromAddr)
	relayTo := protoAddrToNetAddr(m.RelayToAddr)
	rm.l.Info("handleCreateRelayResponse",
		"relayFrom", relayFrom,
		"relayTo", relayTo,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"responderRelayIndex", m.ResponderRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	relay, err := rm.EstablishRelay(h, m)
	if err != nil {
		rm.l.Error("Failed to update relay for relayTo", "error", err)
		return
	}
	// Do I need to complete the relays now?
	if relay.Type == TerminalType {
		return
	}
	// I'm the middle man. Let the initiator know that the I've established the relay they requested.
	peerHostInfo := rm.hostmap.QueryVpnAddr(relay.PeerAddr)
	if peerHostInfo == nil {
		rm.l.Error("Can't find a HostInfo for peer", "relayTo", relay.PeerAddr)
		return
	}
	peerRelay, ok := peerHostInfo.relayState.QueryRelayForByIp(relayTo)
	if !ok {
		rm.l.Error("peerRelay does not have Relay state for relayTo", "relayTo", peerHostInfo.vpnAddrs[0])
		return
	}
	switch peerRelay.State {
	case Requested:
		// I initiated the request to this peer, but haven't heard back from the peer yet. I must wait for this peer
		// to respond to complete the connection.
	case PeerRequested, Disestablished, Established:
		peerHostInfo.relayState.UpdateRelayForByIpState(relayTo, Established)
		resp := NebulaControl{
			Type:                NebulaControl_CreateRelayResponse,
			ResponderRelayIndex: peerRelay.LocalIndex,
			InitiatorRelayIndex: peerRelay.RemoteIndex,
		}

		peer := peerHostInfo.vpnAddrs[0]
		if v == cert.Version1 {
			if !peer.Is4() {
				rm.l.Error("Refusing to CreateRelayResponse for a v1 relay with an ipv6 address",
					"relayFrom", peer,
					"relayTo", relayTo,
					"initiatorRelayIndex", resp.InitiatorRelayIndex,
					"responderRelayIndex", resp.ResponderRelayIndex,
					"vpnAddrs", peerHostInfo.vpnAddrs,
				)
				return
			}

			b := peer.As4()
			resp.OldRelayFromAddr = binary.BigEndian.Uint32(b[:])
			b = relayTo.As4()
			resp.OldRelayToAddr = binary.BigEndian.Uint32(b[:])
		} else {
			resp.RelayFromAddr = netAddrToProtoAddr(peer)
			resp.RelayToAddr = m.RelayToAddr
		}

		msg, err := resp.Marshal()
		if err != nil {
			rm.l.Error("relayManager Failed to marshal Control CreateRelayResponse message to create relay", "error", err)
			return
		}
		f.SendMessageToHostInfo(header.Control, 0, peerHostInfo, msg, make([]byte, 12), make([]byte, mtu))
		rm.l.Info("send CreateRelayResponse",
			"relayFrom", peer,
			"relayTo", relayTo,
			"initiatorRelayIndex", resp.InitiatorRelayIndex,
			"responderRelayIndex", resp.ResponderRelayIndex,
			"vpnAddrs", peerHostInfo.vpnAddrs,
		)
	}
}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}
