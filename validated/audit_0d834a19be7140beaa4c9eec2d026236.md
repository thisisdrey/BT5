### Title
Uninitialized `accountIndexOf` treated as 0 instead of `INITIAL_INDEX` lets a first-time account instantly accrue `balance × 1` reward tokens - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` uses `accountIndexOf[token][account]` as the account's baseline reward index. A value of `0` means "never accrued" and is supposed to be normalized to `INITIAL_INDEX` (1e18). The normalization only runs when the token index is **strictly greater** than `INITIAL_INDEX`. When the token index equals `INITIAL_INDEX` exactly — the entire window between a token being added via `_updateTokenSpeed` (which stores `TokenState({index: INITIAL_INDEX, ...})`) and the first index accrual that produces a nonzero `wadDiv` ratio — a first-time account's index stays `0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account) * 1`. This is the same bug class as CVE-2025-40214: an uninitialized index field is misjudged as a real value, so the account is grouped/credited incorrectly.

### Finding Description
In `contracts/RewardsDistributor.sol`:

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
``` [1](#0-0) 

When `_tokenIndex == INITIAL_INDEX` (i.e., `tokenStates[token_].index` is still exactly the seed value set at line 298 when speed was first configured), `_accountIndex` remains `0`, so `_deltaIndex = 1e18` and the account is credited `wadMul(balance, 1e18) = balance` reward tokens with zero elapsed accrual.

The index stays at `INITIAL_INDEX` whenever `_calculateTokenIndex` yields no increase: `_deltaTimestamps == 0` (same block the speed was set) or `_tokensAccrued.wadDiv(totalSupply)` rounds to `0` (speed × elapsed < totalSupply), which can persist for many blocks with low speeds or large supplies — `_newIndex` then equals `_supplyState.index` unchanged [2](#0-1) .

The entry point is unprivileged: `updateBeforeMintOrBurn(token_, account_)` is explicitly "callable by anyone" and only requires `tokenStates[token_].index > 0` [3](#0-2) . `claimRewards(accounts_, tokens_)` likewise calls `_updateTokensAccruedOf` then `_transferRewardIfEnoughTokens`, paying out `tokensAccruedOf[account]` up to the contract's `rewardToken` balance [4](#0-3) .

### Impact Explanation
Theft of unclaimed yield / direct reward-token theft. An attacker holding any `DepositToken`/`DebtToken` balance calls `updateBeforeMintOrBurn` (or `claimRewards`) while the token's global index is still `INITIAL_INDEX`, and instantly records `tokensAccruedOf[attacker] = balanceOf(attacker)` reward tokens that were never emitted over time. Because the bug triggers once per fresh account (`accountIndexOf == 0`), the attacker can repeat it across multiple accounts by transferring deposit tokens between them while the index remains pinned at `INITIAL_INDEX`, draining the entire `rewardToken` balance of the distributor — rewards owed to all legitimate stakers.

### Likelihood Explanation
- Requires a reward token whose `tokenStates[token].index == INITIAL_INDEX`. This is guaranteed in the same block the token is added (governor/keeper calls `updateTokenSpeed`, a routine config operation), and persists indefinitely whenever `speed * elapsed < totalSupply` so `wadDiv` rounds to zero.
- Attacker needs only an EOA holding (or flash-obtaining via deposit) a nonzero token balance; deposit via `Pool.deposit`/`NativeTokenGateway` is public.
- No modifier stops it: `updateBeforeMintOrBurn` has no `onlyPool` restriction and no pause check; `claimRewards` is `nonReentrant` only.
- Payout is bounded by `rewardToken.balanceOf(distributor)`, so impact is capped but directly extractable.

### Recommendation
Normalize the zero sentinel unconditionally for a token that has been initialized: when `tokenStates[token_].index >= INITIAL_INDEX` (or `tokenSpeeds[token_] > 0`), treat `accountIndexOf == 0` as `INITIAL_INDEX`. Equivalently, change the guard at line 225 to `if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX)`, or store `INITIAL_INDEX` as the account index when the account first interacts, mirroring the fix pattern of assigning a fresh monotonically-unique value rather than leaving the default.

### Proof of Concept
Hardhat sketch (mirroring `test/RewardDistributor.test.ts` setup):

```ts
// Governor configures speed for a deposit token -> index seeded at INITIAL_INDEX
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))

// Attacker holds 100 msdTOKEN1 (e.g., just deposited); token index still == 1e18
// because _deltaTimestamps == 0 or the accrual ratio rounds to 0
msdTOKEN1.totalSupply.returns(parseEther('1000000')) // large supply so ratio == 0
msdTOKEN1.balanceOf.whenCalledWith(attacker.address).returns(parseEther('100'))

// Public entry point: accountIndexOf[attacker] == 0, tokenIndex == INITIAL_INDEX
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, attacker.address)

// Bug: tokensDelta = 100e18 * wadMul(1e18) = 100 reward tokens accrued instantly
expect(await rewardDistributor.tokensAccruedOf(attacker.address)).to.eq(parseEther('100'))

// Drain rewards
await vsp.mint(rewardDistributor.address, parseEther('100'))
await rewardDistributor['claimRewards(address)'](attacker.address)
expect(await vsp.balanceOf(attacker.address)).to.eq(parseEther('100'))
```

Expected (correct) behavior: `tokensAccruedOf` remains `0` because no time-weighted accrual occurred; actual: attacker accrues `balance` reward tokens. Repeating with fresh funded accounts extracts up to the distributor's full `rewardToken` balance.
