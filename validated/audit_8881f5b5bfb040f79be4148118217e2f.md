### Title
Gitaly's `LinkRepositoryToObjectPool` RPC performs cross-repository object pooling without validating that the requester is authorized to expose the target repository's objects to the pool - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` accepts two independently-controlled repository identifiers — the `object_pool` and the `repository` to be linked — and unconditionally wires them together via Git alternates, exactly analogous to the Centrifuge router which performed a privileged action (`requestDeposit`/`requestRedeem`) using caller-supplied identifiers (`controller`, `owner`) without checking that the caller was actually authorized to act on that pairing. In both cases, a mechanism that is *supposed* to only be invoked for a legitimately-related pair of actors (endorsed operator + real owner; fork + its source repository) instead trusts the RPC-supplied identifiers at face value, with the authorization decision assumed to live entirely outside the component performing the sensitive action.

### Finding Description
The `ObjectPoolService.LinkRepositoryToObjectPool` RPC takes a `repository` (target) and an `object_pool` (additional repository) purely as caller-supplied protobuf fields, and the handler does nothing to verify that `repository` is actually derived from / entitled to access `object_pool`: [1](#0-0) 

The only checks performed are that the `repository` field is a syntactically/structurally valid, existing repository (`s.locator.ValidateRepository`) and that the pool itself is a valid pool (`s.poolForRequest`): [2](#0-1) 

Once these superficial checks pass, `pool.Link(ctx, repo)` proceeds to write the `objects/info/alternates` file for `repository`, pointing it at the pool's object directory — with no verification that `repository` was ever forked from, or has any legitimate relationship to, the origin project that seeded `object_pool`: [3](#0-2) 

The proto definitions confirm both fields are simple caller-controlled repository references, with `object_pool` merely marked `additional_repository` and `repository` marked `target_repository` — there is no cross-checked "ownership" or "origin" attribute enforced at the Gitaly layer: [4](#0-3) 

Documentation of the object pool lifecycle likewise confirms that Gitaly's contract places *no* internal safety check on this relationship — the RPC's own comment set for `DeleteObjectPool`/`LinkRepositoryToObjectPool` explicitly states "there are no safety checks in place" and that it is "the responsibility of the caller" to get this right, i.e., the authorization boundary is assumed to be entirely external (Rails), not enforced by Gitaly itself: [5](#0-4) 

This mirrors the root cause of the Centrifuge bug precisely: a privileged operation (linking/exposing shared object storage between two repositories, analogous to allowing an operator to move funds on behalf of an owner) is executed by validating only the *shape* of the caller-supplied identifiers (that `repository` is a valid repo, that `object_pool` is a valid pool) rather than the *relationship* between them (that `repository` is legitimately entitled to see `object_pool`'s objects). Because alternates make **all** objects in the pool transparently readable from any linked member repository (this is the entire point of the alternates mechanism, as documented in `doc/object_pools.md`), any component able to reach this RPC with an arbitrary `(repository, object_pool)` pair can splice a repository it doesn't legitimately own into a pool containing another project's objects, or splice a pool containing sensitive/private data into a repository the caller can read from.

### Impact Explanation
If this RPC is reachable with a caller-controlled `(repository, object_pool)` pairing that hasn't been pre-validated by the layer that is supposed to enforce project-level authorization (e.g., a bug or race in the Rails-side fork/authorization flow, or any other path that can construct and forward this gRPC call with attacker-influenced parameters), the result is direct cross-repository object disclosure: an attacker's repository becomes able to read every object contained in an arbitrary other repository's object pool via ordinary Git operations (`git cat-file`, `git fetch`, clone) once linked, because Git's alternates mechanism has no fine-grained access control — it exposes the entire object database of the pool.

### Likelihood Explanation
Exploitability depends entirely on whether an ordinary/less-privileged actor can influence the `repository` or `object_pool` identifiers passed into this RPC without an intervening authorization check (e.g., via GitLab Rails' fork-creation flow, import flow, or any code path that derives these repository references from user-supplied project/namespace parameters). Gitaly itself performs no defense-in-depth check here, so any authorization gap upstream translates directly into a cross-repository read primitive at the Gitaly layer, with no additional barrier.

### Recommendation
Add a defense-in-depth check inside `LinkRepositoryToObjectPool` (and ideally `FetchIntoObjectPool`) that verifies the `repository` being linked is legitimately associated with the `object_pool`'s origin — e.g., by recording and checking the object pool's originating repository (already tracked via `ObjectPoolStateManager`/`PoolStore`, see `internal/gitaly/storage/relational/state_manager.go`) rather than relying solely on the calling layer (Rails) to have validated the fork relationship before invoking the RPC. At minimum, document explicitly (beyond the existing "no safety checks... responsibility of the caller" comment) that this RPC must never be exposed to a code path where the `repository`/`object_pool` pairing can be influenced by an unprivileged, unauthenticated-relative-to-that-pairing actor.

### Proof of Concept
1. Attacker controls (or can cause the creation of) `repoA` in `storage1`, which has no legitimate forking relationship to `repoB`.
2. `repoB` has been pooled into `objectPoolB` (via `CreateObjectPool` from `repoB`), containing private/sensitive objects.
3. Attacker (or a component acting on attacker's behalf without proper authorization validation) calls:
   ```
   LinkRepositoryToObjectPool(object_pool: objectPoolB, repository: repoA)
   ```
   as shown in [6](#0-5) .
4. Gitaly performs the link with no check that `repoA` is a legitimate member/fork of `repoB`'s lineage, per [1](#0-0) .
5. Attacker now fetches/reads from `repoA` and can retrieve any object that exists in `objectPoolB` (i.e., objects originally only present in `repoB`), because the alternates mechanism transparently serves pooled objects to all linked members, as described in `doc/object_pools.md` lines 10-12 and demonstrated by the `TestDisconnectGitAlternates`/`TestLink` test flows.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}
```
