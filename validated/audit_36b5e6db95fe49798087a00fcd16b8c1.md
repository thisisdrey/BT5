### Title
Attacker-controlled `RelayFromAddr`/`RelayToAddr` fields are used unverified against the sender's authenticated identity in relay control-message handling - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` and `handleCreateRelayResponse` in `relay_manager.go` install relay routing state (`AddRelay`, `InsertRelay`, `relayState` updates) keyed on `from`/`target` addresses taken directly from the peer-supplied `NebulaControl` message fields (`m.RelayFromAddr` / `m.RelayToAddr`), rather than binding those addresses to the sender's certificate-verified `vpnAddrs`. This is the same bug class as the ERC20 report: a security-relevant identity check uses a caller/peer-supplied parameter instead of the entity that is actually authenticated (there, `to` instead of `address(this)`; here, `m.RelayFromAddr` instead of `h.vpnAddrs[0]`).

### Finding Description
`HandleControlMsg` [1](#0-0)  only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`/`handleCreateRelayResponse`. It never confirms that `RelayFromAddr` corresponds to `h.vpnAddrs[0]` (the address bound to `h`'s already-verified, handshake-authenticated certificate).

In `handleCreateRelayRequest`, `from` is derived purely from the message field and is then used to add relay state associating the authenticated `HostInfo h` with an arbitrary claimed `from` address: [2](#0-1) 

The only identity checks performed are "is `from` me" and "is `target` me" (`f.myVpnAddrsTable.Contains(...)`), never "does `from` actually belong to `h`'s certificate/vpnAddrs": [3](#0-2) 

The relay-state bookkeeping (`AddRelay`, `relayState.InsertRelay`) binds the caller-supplied `from`/`target` values to the `HostInfo` object of the actual authenticated sender: [4](#0-3) [5](#0-4) 

This mirrors the C4 finding exactly: the code assumes the peer-supplied address parameter equals the verified identity of the message sender, but never enforces that equivalence. In the ERC20 case `to` (attacker/caller-influenced) was substituted for `address(this)` (the verified spender identity). Here, `m.RelayFromAddr` (fully attacker-controlled protobuf field) is substituted for `h.vpnAddrs[0]` (the cert-verified identity of the connection that delivered the control message).

### Impact Explanation
Any already-authenticated Nebula peer (one with a valid, CA-signed certificate that has completed a normal handshake — i.e., no forged certificate needed) can send a `CreateRelayRequest`/`CreateRelayResponse` control message claiming an arbitrary `RelayFromAddr`/`RelayToAddr` that does not belong to it. Because the code never validates that the claimed address matches the sender's own certificate networks, this lets an authenticated-but-malicious peer:
- Poison this node's relay-routing state (`hostmap.Relays`, `relayState`) by causing it to believe traffic destined for a third-party VPN address should be relayed through the malicious peer, diverting/black-holing traffic intended for that address (remote state poisoning / traffic redirection).
- Trigger spurious `CreateRelayResponse` messages and relay-state churn toward unrelated third parties, since `handleCreateRelayRequest`'s "am I the target" branch installs `Established` relay state keyed by an unverified `from`.

This does not bypass the Noise handshake's cryptographic peer authentication and does not decrypt other tunnels' traffic directly, but it does allow a legitimate, certificate-holding peer to corrupt/misdirect the relay topology for hosts it does not represent, which is a concrete remote state-poisoning impact within relay/lighthouse address-trust handling.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to be a valid member of the mesh (holding a CA-signed cert, as any Nebula node does) and to control the `am_relay`-capable path or be a party in a relay handshake — this is squarely within nebula's normal peer capabilities, not requiring a stolen private key or forged certificate. Any node participating in relay negotiation can freely set these protobuf fields since they are not covered by any signature (they ride inside the encrypted `Control` message payload, so no cross-peer signature ties them to the sender's cert).

### Recommendation
In `HandleControlMsg` / `handleCreateRelayRequest` / `handleCreateRelayResponse`, validate that the `from` (`RelayFromAddr`) address is actually one of `h.vpnAddrs` (the cert-verified addresses of the peer that sent the control message) before creating or updating any relay state referencing it. Reject the message (log and drop) if `from` is not contained in `h`'s certificate networks, mirroring the existing self-address checks (`f.myVpnAddrsTable.Contains(from)`) but checking against the sender's own identity instead.

### Proof of Concept
Conceptual PoC (cannot be executed without lab access, described for a Devin agent to build as an e2e test similar to existing relay tests):
1. Stand up three legitimate nebula nodes with valid certs signed by the same CA: `me`, `attacker`, `victim`, plus a relay-capable node `relay` (`am_relay: true`).
2. Have `attacker` (a normal authenticated peer, no forged cert needed) send a `CreateRelayRequest` to `relay` with `RelayFromAddr` set to `victim`'s VPN address instead of `attacker`'s own address.
3. Observe that `relay.handleCreateRelayRequest` (in `relay_manager.go`) accepts the message, calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` with `h` = `attacker`'s `HostInfo` but `from` = `victim`'s address, and responds with `CreateRelayResponse`, installing relay state that associates `attacker`'s tunnel with routing for `victim`'s address — without ever checking that `victim`'s address is present in `attacker`'s certificate networks.
4. This corrupted relay state can then be leveraged to redirect subsequent relay-routed traffic intended for `victim` through `attacker`'s established tunnel to `relay`.

	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return

					// We got a brand new Relay request, because its index is different than what we saw before.

					return
