### Title
Missing storage-equality check in `LinkRepositoryToObjectPool` allows cross-storage alternates linking - ([File: internal/gitaly/service/objectpool/link.go](https://github.com/ThankGodontt/gitaly--012/blob/main/internal/gitaly/service/objectpool/link.go))

### Summary
`LinkRepositoryToObjectPool` validates the `Repository` field on its own [1](#0-0)  and validates the pool repository exists as a valid Git repository via `poolForRequest`/`objectpool.FromProto` [2](#0-1) , but at no point does it check that `repository.GetStorageName()` equals `objectPool.GetRepository().GetStorageName()`. This is exactly analogous to the reported `addLender` bug: two related resources (`want` token of strategy vs. lender; here, the storage of the repo vs. the storage of the pool) are combined without a matching-identity check.

### Finding Description
`Link` in `internal/git/objectpool/link.go` computes the relative alternates path purely with `filepath.Rel`, with no verification that `pool` and `repo` live under the same storage root: [3](#0-2) . Because `filepath.Rel` works across unrelated absolute paths (producing a `../../..` style path even when the two directories share no common ancestor other than `/`), if `pool.Path()` and `repo.Path()` resolve to different storages, the resulting relative path in the alternates file will still be syntactically valid but will point outside the repository's own storage root.

By contrast, the sibling RPC `FetchIntoObjectPool` explicitly guards against this class of mismatch with a dedicated storage equality check: [4](#0-3) . `LinkRepositoryToObjectPool` has no equivalent check — `objectpool.FromProto` only validates that the pool relative path is a legitimate pool directory or an in-progress temp directory [5](#0-4) , and `Link` never cross-checks the repo's storage name against the pool's storage name before writing the alternates file [6](#0-5) .

### Impact Explanation
If a caller of `LinkRepositoryToObjectPool` (this RPC is invoked as part of the ordinary fork-creation flow, see `TestCompleteForkCreationFlow` [7](#0-6) ) can supply a `Repository` and `ObjectPool.Repository` with different `storage_name` values (e.g., in a multi-storage Gitaly/Praefect deployment), the write path in `Link` will still succeed and configure the repository's Git alternates to point at objects located on a different storage. This is a cross-repository/cross-storage object-access primitive: once linked, `git fsck`/`git cat-file`/clone operations on the "member" repository would be able to read objects from a pool repository the caller does not otherwise have access to, undermining storage-level isolation guarantees that other Gitaly paths (e.g. `FetchIntoObjectPool`, `ObjectDirectoryPath`'s quarantine-prefix check [8](#0-7) ) are careful to enforce.

### Likelihood Explanation
Moderate. The Repository and ObjectPool.Repository fields of the `LinkRepositoryToObjectPoolRequest` are attacker-influenceable RPC fields; in deployments with multiple storages, a crafted request that pairs a repository on storage A with a pool on storage B would reach this code path unhindered by any existing check, since `s.locator.ValidateRepository` in `LinkRepositoryToObjectPool` only validates the `Repository` field in isolation [1](#0-0)  and never compares it against the pool's storage.

### Recommendation
Add an explicit check in `LinkRepositoryToObjectPool` (or in `objectpool.Link`) that `repository.GetStorageName() == poolRepository.GetStorageName()` before proceeding, mirroring the existing guard in `validateFetchIntoObjectPoolRequest` [4](#0-3) , and return an `InvalidArgument`/`FailedPrecondition` error on mismatch instead of silently computing a cross-storage relative path.

### Proof of Concept
1. Configure a Gitaly node with two storages, `storage-a` and `storage-b`.
2. Create/seed a repository `repo` on `storage-a` and a valid pool repository `pool` on `storage-b` (both reachable via the same Gitaly server config).
3. Call `LinkRepositoryToObjectPool` with `Repository={storage_name: "storage-a", relative_path: "repo.git"}` and `ObjectPool.Repository={storage_name: "storage-b", relative_path: "@pools/.../pool.git"}`.
4. Observe the request succeeds (no storage-mismatch error is raised, unlike `FetchIntoObjectPool` with mismatched storages), and inspect `repo.git/objects/info/alternates` — it will contain a path traversing out of `storage-a` into `storage-b`'s pool object directory, confirming the missing check allows cross-storage alternate linkage.

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

func getRelativeObjectPath(ctx context.Context, pool, repo *localrepo.Repo) (string, error) {
	poolPath, err := pool.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting object pool path: %w", err)
	}

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", fmt.Errorf("getting repository path: %w", err)
	}

	relPath, err := filepath.Rel(filepath.Join(repoPath, "objects"), poolPath)
	if err != nil {
		return "", err
	}

	return filepath.Join(relPath, "objects"), nil
}

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {

		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

		return errors.New("origin has different storage than object pool")
	}

	return nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}
