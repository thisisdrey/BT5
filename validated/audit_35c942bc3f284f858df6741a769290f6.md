### Title
StackerDB chunk signatures do not bind to the target StackerDB contract, allowing cross-contract chunk replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
Analogous to the Argo CD flaw where a JWT's signature was verified but its `aud` (audience) claim was never checked — letting a token minted for one service be replayed against another — the `SlotMetadata`/`StackerDBChunkData` signing scheme in this repo signs only `(slot_id, slot_version, data_hash)` and never binds the signature to the specific StackerDB contract ("audience") it is meant for. The server-side verifier likewise never checks this, so a legitimately-signed chunk from one StackerDB replica can be replayed as valid input to a different StackerDB replica.

### Finding Description
`SlotMetadata::auth_digest()` builds the signed digest from only the slot id, slot version, and data hash: [1](#0-0) 

`SlotMetadata::verify()` recovers the public key from this digest and the supplied signature and compares its hash to the expected `StacksAddress` — again with no notion of *which contract* this signature was supposed to authorize: [2](#0-1) 

On the server side, `StackerDBs::validate_received_chunk` looks up the expected signer address for `smart_contract_id`/`slot_id` and then calls `slot_metadata.verify(&addr)` — but since the digest never includes `smart_contract_id`, this check only proves "some address recovered from this signature equals the configured owner of slot `slot_id` in contract `smart_contract_id`," not "this signer intended this signature for this contract": [3](#0-2) 

The same unbound `verify()` is used at the HTTP POST-chunk RPC endpoint (`BadSigner` check) and at the unsolicited `StackerDBPushChunk` p2p path: [4](#0-3) 

Multiple StackerDB contracts are provisioned per reward cycle, one per "signer set" / "message id" lane (e.g. block-responses, transactions), following the naming convention `signer-<signer_set>-<message_id>` decoded by `get_signers_db_signer_set_message_id`: [5](#0-4) 

Because slot allocation for these sibling contracts is derived from the same underlying reward-cycle signer set, a given signer typically occupies the *same* `slot_id` across multiple sibling contracts in that reward cycle. Since the auth digest binds neither `smart_contract_id` nor any per-contract nonce, a `StackerDBChunkData` (slot_id, slot_version, sig, data) that a signer legitimately produced and published to contract A is a byte-for-byte valid, verifiable chunk for contract B as well, provided the signer also owns that `slot_id` in B and the freshness/size checks (`slot_version >= expected_version`, `data.len() <= chunk_size`) pass.

### Impact Explanation
This breaks the equality the system is supposed to enforce: "chunk accepted into StackerDB X ⇒ chunk was authored/signed for StackerDB X by its owner." Because the signature is not scoped to the target contract, an unprivileged network observer (who need not possess any private key) can capture a legitimately-published chunk for one StackerDB instance and replay it as a `POST /v2/stackerdb/<contractB>/chunks` request or via unsolicited `StackerDBPushChunk` gossip against a different StackerDB instance. If accepted, this is an unauthorized write of attacker-selected legitimate signer data into a StackerDB replica the signer never intended to write to, and the node will then propagate ("forged" for that lane) this chunk to its peers via its normal StackerDB broadcast/anti-entropy schedule — network-wide propagation of misattributed/forged data under a signer's identity for a context they did not intend, matching the Critical bucket ("unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data").

### Likelihood Explanation
The write path is reachable by any peer able to reach the node's HTTP RPC or p2p StackerDB endpoints — no signer key or admin role is required, only capture/observation of a chunk that was already broadcast on the (public) StackerDB gossip network, which is itself designed to be widely replicated. The main precondition — that the same signer occupies the same `slot_id` across sibling per-reward-cycle contracts — could not be fully confirmed within the available search budget (the exact slot-allocation code path in `stackslib/src/chainstate/nakamoto/signer_set.rs` was not fully traced), but the shared "signer_set" component of the `signer-<signer_set>-<message_id>` contract-naming scheme strongly suggests slot ordering is derived once per reward cycle and reused across message-id lanes, which is the deterministic default the naming/allocation model implies.

### Recommendation
Include the target `smart_contract_id` (and ideally a network/chain identifier) inside `SlotMetadata::auth_digest()` so that a chunk signature is only valid for the specific StackerDB instance it was produced for, mirroring how OIDC/JWT audience-restriction is fixed by explicitly hashing/checking the `aud` claim. This requires a coordinated protocol version bump: update `auth_digest`, `sign`, and `verify` in `libstackerdb/src/libstackerdb.rs` to take the contract id as an additional input, and update all callers (`stackslib/src/net/stackerdb/mod.rs::validate_received_chunk`, `stackslib/src/net/api/poststackerdbchunk.rs`, `libsigner/src/events.rs`) accordingly.

### Proof of Concept
1. Observe (as any unprivileged peer, e.g. via the public StackerDB HTTP GET-chunk endpoint or p2p gossip) a legitimately signed `StackerDBChunkData { slot_id, slot_version, sig, data }` that signer `S` published to StackerDB contract A (e.g. `signer-<rc>-<message_id_A>`), where `S` also owns `slot_id` in sibling contract B (`signer-<rc>-<message_id_B>`).
2. Construct an HTTP POST to `/v2/stackerdb/<contract_B_address>/<contract_B_name>/chunks` (per `stackerdb_post_chunk_path`) reusing the exact same `slot_id`, `slot_version`, `sig`, and `data` bytes captured from contract A.
3. The receiving node calls `StackerDBs::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649`), which fetches `addr = get_slot_signer(contract_B, slot_id)` (= `S`'s address, since `S` owns that slot in B too) and calls `slot_metadata.verify(&addr)`.
4. Because `auth_digest()` only hashes `slot_id`, `slot_version`, and `data_hash` (`libstackerdb/src/libstackerdb.rs:159-166`), the same signature recovers to `S`'s public key regardless of contract, so `verify()` returns `true` and the chunk is accepted into contract B — even though `S` never signed anything for contract B.
5. The node subsequently gossips/broadcasts this chunk as legitimate data for contract B, propagating the misattributed/forged-context chunk across the network.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

    /// The chunk exceeds the replica's configured chunk size.
    ChunkTooBig,
    /// The chunk's slot version exceeds the replica's configured maximum writes.
    TooManySlotWrites,
}

impl StackerDBErrorCodes {
    pub fn code(&self) -> u32 {
        match self {
            Self::DataAlreadyExists => 0,
            Self::NoSuchSlot => 1,

            Self::ChunkTooBig => 3,
            Self::TooManySlotWrites => 4,
