### Title
Client-supplied `GitConfigOptions` can override the internally pinned `core.hooksPath`, allowing hook bypass/hijack on push - ([File: internal/gitaly/service/ssh/receive_pack.go])

### Summary
The reported bug class is "trusted key gets overwritten by attacker-controlled data because trusted and untrusted values are merged into the same ordered structure, with the untrusted one placed/applied last." In Gitaly's `receive-pack`/`upload-pack` RPC handlers, the same pattern exists: an internally computed, security-critical Git config entry (`core.hooksPath`, pointing at Gitaly's own hooks directory) is placed into the same ordered `cc.globals` slice as the caller-supplied `GitConfigOptions`, and the caller-supplied entries are appended *after* it.

### Finding Description
`WithReceivePackHooks` → `configureHooks` appends `ConfigPair{Key: "core.hooksPath", Value: gitCmdFactory.HooksPath(ctx)}` to `cc.globals`: [1](#0-0) 

In both `sshReceivePack` and `postReceivePack`, the CmdOpt order passed to `repo.Exec` is: `WithReceivePackHooks(...)` (which sets `core.hooksPath`) followed later by `WithConfig(config...)`, where `config` is built directly from the RPC request's `GitConfigOptions` field via `gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())`: [2](#0-1) [3](#0-2) 

`WithConfig` simply appends to the same `cc.globals` slice used by `configureHooks`: [4](#0-3) 

Because `cc.globals` preserves call order and is turned into `-c key=value` flags in that same order in `combineArgs`, and because Git applies repeated `-c` entries for the same key with "last one wins" semantics (as explicitly exercised in the test suite, `override.me`/`from.option` cases): [5](#0-4) [6](#0-5) 

a caller-supplied `GitConfigOptions` entry with key `core.hooksPath` is applied strictly after the internally computed one and therefore wins, redirecting `git-receive-pack`'s hook execution to a path of the caller's choosing. `ConvertConfigOptions` performs only syntactic `key=value` splitting with no key allowlist/denylist: [7](#0-6) 
and `GitConfig.Validate()`/`GlobalArgs()` only enforce that the key looks like a valid dotted Git config key (no dots at start/end, contains "=" check, regex match) — it does not block sensitive keys such as `core.hooksPath`, `uploadpack.packObjectsHook`, or `core.alternateRefsCommand`: [8](#0-7) 

This is architecturally the same flaw class as the reported issue: a trusted/fixed key (`channel` in the report; `core.hooksPath` here) is unpacked/merged into the same container as attacker-influenced data without isolating it in a way that prevents the untrusted side from clobbering it by using the same key name.

### Impact Explanation
`core.hooksPath` controls where Git looks for `pre-receive`, `update`, and `post-receive` executables when running `git-receive-pack`. Gitaly relies on this setting to point Git at its own controlled hooks directory, which is what invokes `gitaly-hooks` to perform the GitLab-side authorization checks (permission checks, protected branch checks, etc.) and quota/transaction accounting. If a caller can redirect `core.hooksPath` to an arbitrary directory:
- The GitLab-mandated `pre-receive`/`update` authorization hooks can be skipped entirely (hook bypass), allowing pushes that should have been rejected (e.g., to protected branches, or lacking permission) to succeed.
- If the attacker can also place executable files at the redirected path (e.g., via a writable location on the same host, or if the value can point at a path they control within storage), this becomes arbitrary code execution as the Gitaly process user, since Git will exec whatever is found there as the hook.

This is a legitimate storage/argument-injection-class analog: crafted RPC field (`GitConfigOptions`) leads to config injection that undermines hook/quarantine gating.

### Likelihood Explanation
`GitConfigOptions` is a field on `SSHReceivePackRequest`, `PostReceivePackRequest`, and the upload-pack equivalents, and is converted with no allowlist. Whatever intermediate trust boundary exists between an end user and this RPC field (e.g., gitlab-shell/Workhorse) is outside of Gitaly's code and cannot be verified from this repository alone — Gitaly's own handler code performs no filtering of dangerous keys before merging user data with internally pinned safety-critical config in the same ordered list, which is the root cause regardless of what upstream systems intend to allow. Because the "later entry wins" semantics of `-c` are exercised and expected behavior in Gitaly's own tests (`command_options_test.go`), and because `WithConfig(config...)` for request-supplied options is invoked strictly after hook configuration in both the SSH and Smart HTTP receive-pack code paths, the override is deterministic and reproducible, not a race condition.

### Recommendation
- Add an explicit denylist/allowlist in `gitcmd.ConvertConfigOptions` (or a dedicated validation step in the RPC handlers) that rejects caller-supplied Git config keys corresponding to internally security-critical settings, at minimum: `core.hooksPath`, `uploadpack.packObjectsHook`, `core.alternateRefsCommand`, `receive.procReceiveRefs`, and any other config keys Gitaly itself sets for enforcement purposes.
- Alternatively/additionally, apply internally pinned configuration (`core.hooksPath`, etc.) *after* any caller-supplied config in the `cc.globals`/`combineArgs` ordering, mirroring the existing pattern used for `cf.cfg.Git.Config` (admin config), which is intentionally appended last so it always wins: [9](#0-8) 
- Consider passing internally required config exclusively via `WithConfigEnv`/`GIT_CONFIG_KEY_N`/`GIT_CONFIG_VALUE_N` with a mechanism (e.g., `GIT_CONFIG_COUNT` fixed and applied by Gitaly's own trusted process, not mergeable with `-c` arguments controlled elsewhere) so caller-supplied `-c` flags structurally cannot collide with Gitaly-internal keys.

### Proof of Concept
Conceptual reproduction using the existing test scaffolding pattern (`TestServer_PostUploadPackSidechannel_gitConfigOptions`/analogous receive-pack test) shows the mechanism is already validated for benign keys like `uploadpack.hideRefs`: [10](#0-9) 

The same mechanism, applied to `SSHReceivePackRequest`/`PostReceivePackRequest` with:
```
GitConfigOptions: []string{"core.hooksPath=/tmp/attacker-controlled-hooks"}
```
would, per the code paths cited above, cause `git-receive-pack` to be invoked with `-c core.hooksPath=<gitaly-real-hooks-path> ... -c core.hooksPath=/tmp/attacker-controlled-hooks`, and Git uses the last occurrence, bypassing Gitaly's real hook directory. Full end-to-end exploitation (confirming whether an external, unprivileged client can actually populate `GitConfigOptions` before it reaches Gitaly's gRPC handlers) would require verifying the gitlab-shell/Workhorse trust boundary, which is outside the scope of this repository and could not be confirmed from the indexed code alone.

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}

// WithConfig adds git configuration entries to the command.
func WithConfig(configPairs ...ConfigPair) CmdOpt {
	return func(_ context.Context, _ config.Cfg, _ CommandFactory, c *cmdCfg) error {
		for _, configPair := range configPairs {
			c.globals = append(c.globals, configPair)
		}
		return nil
	}
}

// Validate validates that the Git configuration conforms to a format that Git understands.
func (cfg GitConfig) Validate() error {
	// Even though redundant, this block checks for a few things up front to give better error
	// messages to the administrator in case any of the keys fails validation.
	if cfg.Key == "" {
		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}
	if strings.Contains(cfg.Key, "=") {
		return cfgerror.NewValidationError(
			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}
	if !strings.Contains(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must not start or end with a dot", cfg.Key),
			"key",
		)
	}

	if !configKeyRegex.MatchString(cfg.Key) {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q failed regexp validation", cfg.Key),
			"key",
		)
	}

	return nil
}

// GlobalArgs generates a git `-c <key>=<value>` flag. Returns an error if `Validate()` fails to
// validate the config key.
func (cfg GitConfig) GlobalArgs() ([]string, error) {
	if err := cfg.Validate(); err != nil {
		return nil, fmt.Errorf("invalid configuration key %q: %w", cfg.Key, err)
	}

	return []string{"-c", fmt.Sprintf("%s=%s", cfg.Key, cfg.Value)}, nil
}
