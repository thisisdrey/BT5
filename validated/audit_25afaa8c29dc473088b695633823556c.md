### Title
Deterministic priority-tie eviction lets an attacker evict a targeted equal-priority victim transaction from the scheduler buffer without paying a higher fee - ([File: core/src/banking_stage/transaction_scheduler/transaction_state_container.rs])

### Summary
`TransactionStateContainer::push_ids_into_queue` evicts the transaction with the smallest `TransactionPriorityId` from a `BTreeSet`, and `TransactionPriorityId`'s `Ord` impl breaks priority ties by comparing the internal `TransactionId` (the slab index assigned at insertion time). Because slab indices are assigned sequentially at insertion, on a priority tie the *older* (already-queued) transaction always has the smaller id and is therefore evicted first, while a flood of newer equal-priority transactions is protected — letting an unprivileged remote attacker reliably evict a specific victim transaction merely by matching its priority and sending enough follow-up transactions to overflow the container.

### Finding Description
`TransactionPriorityId` derives `Ord` over `(priority, id)` [1](#0-0) , and its own test explicitly documents that on equal priority the entry is ordered "then compare by id" [2](#0-1) .

`push_ids_into_queue` inserts new ids into the `priority_queue: BTreeSet<TransactionPriorityId>` and, if capacity is exceeded, repeatedly calls `self.priority_queue.pop_first()` to select victims for removal [3](#0-2) . `pop_first` always removes the minimum `(priority, id)` pair in the set.

`id` here is a `TransactionId` obtained from `Slab::vacant_entry()` at insertion time via `insert_map_only` [4](#0-3) , so under normal, non-removal-heavy load, ids increase monotonically with arrival order — an earlier-arriving transaction gets a smaller id than a later one.

Consequence: when many transactions share identical priority (e.g., zero additional priority fee, which is extremely common for plain transfers), the tie-break rule guarantees that **the oldest of the tied transactions is evicted first**, while newer, attacker-submitted, equal-priority transactions are preserved. An attacker who can observe or predict a victim's priority value (e.g., default/zero priority, a common and public value) can:
1. Wait for the victim's transaction to be queued.
2. Flood the leader's TPU with enough transactions at the exact same priority to push `id_to_transaction_state.len()` above `capacity`.
3. `push_ids_into_queue` will then repeatedly `pop_first()`, and because the victim's transaction has the smallest id among the tied-priority group, it will be evicted before any of the attacker's newer flood transactions, deterministically.

This is reachable purely from unstaked/unauthenticated ingress: transactions are inserted into the container from the standard packet receive path (`receive_and_buffer.rs`, `container.push_ids_into_queue(...)`) with no additional gate against equal-priority flooding beyond total container capacity [5](#0-4) . Sigverify/dedup/QoS checks validate that a transaction is well-formed and fee-payer funded, but do nothing to prevent an attacker from choosing a priority value that exactly collides with a known victim's, nor do they randomize or protect-oldest on ties.

### Impact Explanation
This is a QoS evasion / targeted censorship primitive: an attacker with no stake and no fee premium over the victim can deterministically cause a specific, already-accepted transaction to be dropped from the banking-stage buffer before being scheduled for execution, purely by flooding equal-priority transactions after it. This undermines the fee-market fairness assumption that only strictly higher-paying transactions can preempt a queued transaction, and it can be used to censor targeted low/zero-priority-fee transactions (which are the common case for ordinary transfers) at negligible cost to the attacker (matching priority is trivial for the very common priority=0 case).

### Likelihood Explanation
Feasible and repeatable with only unprivileged connections to the leader's public TPU: send/observe a target's transaction, submit a flood of arbitrary transfers with the identical priority value, and rely on the deterministic `BTreeSet` ordering / `pop_first` tie-break. No staked/gossip/config access is required; only enough transaction volume to overflow container capacity, which is a normal congestion condition.

### Recommendation
Do not use the monotonically-assigned internal `TransactionId` as an implicit tie-breaker that biases eviction toward "oldest first." Either:
- Use a tie-break that favors keeping earlier-arrived transactions (i.e., prefer evicting the newest on ties) so that first-come, first-served ordering is preserved among equal-priority transactions, or
- Add a randomized/salted secondary key (not derived from arrival order) to `TransactionPriorityId` so ties are resolved unpredictably to attackers, preventing deterministic targeting.

### Proof of Concept
```rust
// core/src/banking_stage/transaction_scheduler/transaction_state_container.rs (test module)
#[test]
fn test_equal_priority_tiebreak_evicts_oldest_first() {
    // Container holds only 2 transactions.
    let mut container = TransactionStateContainer::with_capacity(2);

    // Victim's transaction arrives first, priority = 0 (typical default priority).
    let (victim_tx, max_age, priority, cost) = test_transaction(0);
    container.insert_new_transaction(victim_tx, max_age, priority, cost);
    let victim_id = container.priority_queue.iter().next().unwrap().id;

    // Attacker floods with equal priority (0) after the victim, exceeding capacity.
    for _ in 0..5 {
        let (attacker_tx, max_age, priority, cost) = test_transaction(0);
        container.insert_new_transaction(attacker_tx, max_age, priority, cost);
    }

    // Victim's transaction (oldest, smallest id) must have been evicted first,
    // even though it never paid a lower priority than any attacker transaction.
    assert!(
        container.get_transaction(victim_id).is_none(),
        "victim transaction was deterministically evicted on priority tie by newer attacker flood"
    );
    assert_eq!(container.queue_size(), 2); // only newest attacker txs remain
}
```
Expected result: the assertion passes, demonstrating that an attacker submitting only equal-priority (never higher-priority) transactions after a victim's transaction can deterministically force the victim's transaction out of the buffer via the `pop_first`/`id`-based tie-break in `push_ids_into_queue`.

```rust
    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }
```
