Audit Report

## Title
Non-atomic ERC20 return-value validation in `ERC20Transactor` allows real token transfer to execute while XCM asset accounting is rolled back, enabling permanent fund lock or duplicate settlement via asset trap/claim - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call `pallet_revive::Pallet::bare_call` to execute a real, state-mutating ERC20 `transfer()` *before* the returned boolean is validated via `IERC20::transferCall::abi_decode_returns_validate`. Because the physical token movement (mutating `pallet_revive` contract storage) happens unconditionally and is decoupled from the subsequent decode/validate step, a token contract whose `transfer()` mutates balances but returns malformed or `false` data can cause the XCM-level accounting (`AssetsInHolding`) to diverge from the real on-chain ERC20 balances — either permanently locking the withdrawn amount (withdraw path) or leaving the un-rolled-back credit trappable and reclaimable via `ClaimAsset` after the real transfer already happened (deposit path).

## Finding Description
In `withdraw_asset_with_surplus`, `bare_call` transfers real ERC20 balance from `who` to the checking account (lines 172-183 of `erc20_transactor.rs`). Only after this on-chain mutation does the code check `did_revert()` and then `abi_decode_returns_validate` (lines 188-207). If decode fails or the value is `false` despite the real balance having moved, the function returns `Err(XcmError::FailedToTransactAsset(..))` with **no compensating `AssetsInHolding` credit created** — the tokens sit in the checking account backing no XCM-visible value. [1](#0-0) 

In `deposit_asset_with_surplus`, the same pattern occurs: `bare_call` moves real balance from the checking account to the beneficiary's mapped address (lines 253-266) before `abi_decode_returns_validate` runs (lines 273-298). On decode failure, the function returns `Err((what, XcmError::FailedToTransactAsset(..)))`, handing the original `AssetsInHolding` value back to the executor even though the real transfer already succeeded on-chain. [2](#0-1) 

The test `smart_contract_does_not_return_bool_fails` confirms this exact scenario is reachable using `MyTokenFake`, a contract whose `transfer()` performs the real balance mutation but returns a non-boolean value: [3](#0-2) [4](#0-3)  The test only asserts the overall XCM execution errors; it does not assert on-chain ERC20 state reversion or absence of double accounting.

I was **not able to fully verify within the available tool budget** whether the returned `what` in the deposit-failure path actually reaches `Config::AssetTrap::drop_assets` for later `ClaimAsset` recovery, versus being dropped/discarded by the calling instruction logic in `xcm-executor`'s instruction-processing code (`polkadot/xcm/xcm-executor/src/lib.rs`), which I could not fully inspect before running out of iterations. The trap/claim mechanism itself is real and generic — anything left in the holding register at `post_process` is trapped and later claimable — but I could not confirm the exact intermediate step of whether a `DepositAsset` instruction failure re-inserts `what` into the holding register versus terminating the XCM program with that value discarded. [5](#0-4) [6](#0-5) 

What is confirmed and unambiguous regardless of that unresolved detail: the **withdraw-side fund lock** is real and provable — `withdraw_asset_with_surplus` unconditionally executes the real transfer via `bare_call` and only creates the compensating `AssetsInHolding` credit *after* validation succeeds; on validation failure, the moved tokens have no corresponding credit anywhere in the XCM program, and the whole program aborts, permanently stranding value in `TransfersCheckingAccount` with no way for the XCM layer to reference or recover it. [1](#0-0) 

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category from the gate: on the withdraw path, an unprivileged party interacting with a registered ERC20-backed asset whose contract returns non-standard data can cause real funds to move into `TransfersCheckingAccount` while no `AssetsInHolding` credit is ever created for that value, and the aborted XCM program provides no mechanism to reference or reclaim it. The deposit-path double-credit scenario described in the original claim (theft/duplicate settlement via `ClaimAsset`) is plausible given the generic trap/claim design, but I could not confirm the precise instruction-processing step that determines whether the returned `what` from a failed `deposit_asset_with_surplus` call is retained in the holding register (and thus later trapped) or discarded outright — this materially affects whether the "duplicate settlement" impact holds, versus only the "fund lock" impact being provable.

## Likelihood Explanation
Reachability depends on whether an attacker-controlled or arbitrary ERC20 contract can be registered as the backing contract for an asset matched by `ERC20Transactor`'s `Matcher`. The original report itself flags this as unresolved — registration of a foreign/ERC20 asset for XCM accounting typically requires a governance or privileged registration step in `asset-hub` runtimes, which was not confirmed or denied within the available tool budget. If registration requires privileged action, the practical likelihood is significantly reduced, since an unprivileged attacker could not unilaterally get a malicious contract recognized as backing for XCM value.

## Recommendation
Ensure the real `bare_call` state mutation and the return-value validation occur within a single atomic/transactional boundary (e.g., wrap the call in a `with_transaction` savepoint as done elsewhere for `pallet_revive`), so that any decode/validation failure rolls back the underlying ERC20 storage mutation together with the `AssetsInHolding` accounting failure. Alternatively, validate the expected outcome via a dry-run before committing the real transfer, and audit the exact `DepositAsset`/`WithdrawAsset` instruction-processing code in `xcm-executor` to confirm and, if necessary, fix the handling of returned `what` on transactor failure so unspent value cannot be both physically transferred and left claimable.

## Proof of Concept
1. Deploy `MyTokenFake` (or an equivalent contract that mutates balances in `transfer()` but returns non-bool/`false`) via `pallet_revive`.
2. Register/match it as an asset consumed by `ERC20Transactor` (registration privilege requirement unconfirmed — see Likelihood).
3. Execute an XCM program performing `WithdrawAsset` on this asset, following `smart_contract_does_not_return_bool_fails` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` (lines 2019-2073).
4. Observe the real ERC20 balance move (verifiable via `balanceOf`) into `TransfersCheckingAccount`, while the overall XCM program errors with no compensating `AssetsInHolding` credit ever created — demonstrating the fund-lock. Confirming the deposit-side double-credit/claim scenario requires additional tracing of `xcm-executor`'s `DepositAsset` instruction handling that was not completed.

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
		Self::deposit_event(Event::AssetsClaimed {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		Some(claimed)
	}

	/// This includes refunding surplus weight, trapping extra holding funds, and returning any
	/// errors during execution.
	pub fn post_process(mut self, xcm_weight: Weight) -> Outcome {
		// We silently drop any error from our attempt to refund the surplus as it's a charitable
		// thing so best-effort is all we will do.
		let _ = self.refund_surplus();
		drop(self.trader);

		let mut weight_used = xcm_weight.saturating_sub(self.total_surplus);

		if !self.holding.is_empty() {
			tracing::trace!(
				target: "xcm::post_process",
				holding_register = ?self.holding,
				context = ?self.context,
				original_origin = ?self.original_origin,
				"Trapping assets in holding register",
			);
			let claimer = self
				.asset_claimer
				.as_ref()
				.or(self.context.origin.as_ref())
				.unwrap_or(&self.original_origin);
			let trap_weight = Config::AssetTrap::drop_assets(claimer, self.holding, &self.context);
			weight_used.saturating_accrue(trap_weight);
		};
