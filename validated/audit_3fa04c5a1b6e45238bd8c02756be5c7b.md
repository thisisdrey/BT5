### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign` precompile enables RAM exhaustion / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract (address `0x66`) parses a caller-supplied `signatures` array length directly from call data and uses it to allocate a Java array (`new byte[len][]`) without validating it against a maximum bound, unless the `allowTvmSelfdestructRestriction` hard-fork flag is active. This mirrors the pypdf FlateDecode issue: an attacker-controlled size parameter drives allocation size with no upper bound, causing RAM exhaustion (CWE-789).

### Finding Description
`ValidateMultiSign.execute()` extracts the signature-array offset and, depending on `VMConfig.allowTvmSelfdestructRestriction()`, either validates the declared array length against `MAX_SIZE` (5) before calling `extractSigArray`, or calls `extractBytesArray` directly with no size validation: [1](#0-0) 

`extractBytesArray` takes `len` straight from an attacker-supplied word in the call data and immediately allocates a two-dimensional array of that size: [2](#0-1) 

`extractSigArray` has the same unbounded allocation pattern and is only reached in the "fixed" branch, but it too allocates `new byte[len][]` before any bound check inside itself — the actual bound check (`sigArraySize > MAX_SIZE`) happens in the caller, and only when the hard-fork flag is enabled: [3](#0-2) 

Energy for this precompile is computed purely from `data.length` (the size of the raw call-data buffer), not from the declared array length embedded inside the buffer: [4](#0-3) 

This means an attacker can submit a small, cheap `data` payload whose embedded 32-byte "length" word (at the array-length slot referenced by `words[3]`) contains an arbitrarily large integer value (bounded only by `DataWord.intValueSafe()`'s clamp to `Integer.MAX_VALUE`). When the legacy (non-hard-fork) code path is taken, this value is used directly as the size of a newly allocated Java array with no validation, no energy charge proportional to it, and no correlation to the actual (small) call-data size.

### Impact Explanation
Allocating an array sized near `Integer.MAX_VALUE` of object references (8 bytes each on a 64-bit JVM) attempts to allocate on the order of tens of gigabytes, which will throw `OutOfMemoryError` or exhaust available heap, potentially crashing the node process or the JVM, or degrading it enough to halt block/transaction processing. Because this is reachable from a single crafted transaction that invokes the precompile via `STATICCALL`/`CALL` from any contract, any unprivileged transaction broadcaster can trigger this if the `allowTvmSelfdestructRestriction` feature is not active. This satisfies the "node crash or halt" impact bar.

### Likelihood Explanation
Likelihood depends on whether the `allowTvmSelfdestructRestriction` chain parameter/hard-fork has been activated on the target network. If it has been activated (as is presumably the case on TRON mainnet today), the vulnerable `extractBytesArray` branch is dead code and the bug is not exploitable there; on any network/private chain/testnet where this feature is not yet enabled, the vulnerable branch remains live and directly reachable by any account able to broadcast a transaction that calls the precompile. I was not able to fully confirm the current default/activation state of `allowTvmSelfdestructRestriction` across all deployments from the available context — this should be checked against `ProposalUtil.java`/`DynamicPropertiesStore.java` to determine exposure on a specific running network.

### Recommendation
Move the `sigArraySize > MAX_SIZE` bound check so it always applies before allocating any array in both `extractBytesArray` and `extractSigArray`, regardless of the `allowTvmSelfdestructRestriction` flag, and additionally clamp/validate `len` inside `extractBytes32Array`/`extractBytesArray`/`extractSigArray` themselves (defense in depth) so a hostile length word can never drive allocation size directly.

### Proof of Concept
1. Craft a contract call to the `ValidateMultiSign` precompile address (`0x0000...0066`) with `rawData` containing:
   - `words[0]` = target address, `words[1]` = permissionId, `words[2]` = data pointer/value, `words[3]` = an offset value chosen so `words[3]/WORD_SIZE` points to another word within the (small) buffer.
   - The word at that computed offset ("array length") set to a very large value (e.g., `0x7FFFFFFF`).
2. Keep the rest of `rawData` minimal so `getEnergyForData` (based on `data.length`) charges very little energy.
3. On a chain/network where `VMConfig.allowTvmSelfdestructRestriction()` is `false`, `execute()` calls `extractBytesArray(words, offset, rawData)` which executes `new byte[0x7FFFFFFF][]`, attempting a multi-gigabyte allocation and triggering `OutOfMemoryError` in the node's TVM execution thread, potentially destabilizing the node.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
