## Title
Self-beneficiary `DeleteAccount` permanently burns the account's balance instead of transferring it - (File: `runtime/runtime/src/actions.rs`)

### Summary
This is a direct nearcore analog of the Unlock "transfer to self destroys the token" bug class: an unprivileged signer can submit a `DeleteAccount` action whose `beneficiary_id` equals the account being deleted itself. Because no validation rejects this self-referential input, the balance-refund receipt is addressed to an account that no longer exists by the time it executes, the refund fails, and — per the protocol's refund-failure rule — the entire remaining balance is permanently burned rather than refunded to anyone.

### Finding Description
`action_delete_account` computes the account's balance and unconditionally queues a refund receipt to `delete_account.beneficiary_id`, then deletes the account: [1](#0-0) [2](#0-1) 

The only stateless validation performed on the `DeleteAccount` action is that `beneficiary_id` is a syntactically valid account id — there is no check that `beneficiary_id != account_id`: [3](#0-2) 

When `beneficiary_id == account_id`, the generated `Receipt::new_balance_refund` (a `system`-predecessor / refund receipt, single `Transfer` action) is later delivered to the same account, which has already been removed (`*account = None`) by the delete action that spawned it. Refund receipts are explicitly documented and coded to *not* trigger implicit account (re)creation: [4](#0-3) 

Since the action is a refund (`predecessor_id().is_system()` is true), `implicit_account_creation_eligible` is `false`, so `check_account_existence` rejects the `Transfer` with `AccountDoesNotExist` even for a would-be implicit account, and certainly for a named account: [5](#0-4) 

Because this refund receipt then fails, the runtime applies its refund-failure rule: refund receipts are free (no further refund is generated) and any failed refund's deposit is burnt into `other_burnt_amount`: [6](#0-5) 

So the entire account balance that should have gone to the "beneficiary" is instead permanently destroyed (burnt), exactly mirroring the Unlock report's pattern where a self-referential parameter (`_from == _recipient` there, `beneficiary_id == account_id` here) causes value destruction instead of the expected transfer, with no explicit guard preventing it.

### Impact Explanation
Any account holder (or anyone with a full-access key / meta-transaction relayer acting on their behalf) who deletes their own account with `beneficiary_id` set to their own account id loses their entire remaining NEAR balance — it is burned from total supply rather than transferred anywhere. This is a genuine, permanent loss of user funds triggered purely by ordinary transaction input, requiring no privileged role, malicious node, or network-level behavior.

### Likelihood Explanation
This requires user/wallet-integration error (e.g., a wallet or SDK default that sets `beneficiary_id` to the caller's own account id, or a user manually specifying self as beneficiary), similar to the "requires user error" caveat noted in the Unlock report. However, given that `beneficiary_id` is a free-form parameter of the action and there is zero validation preventing this case (unlike e.g. Unlock's `_from != 0x0` checks that at least show some input hygiene exists elsewhere), an accidental self-beneficiary deletion is plausible, especially through third-party tooling or scripts that pass the signer's own id as a placeholder beneficiary.

### Recommendation
Add an explicit validation check in `validate_delete_action` (`runtime/runtime/src/action_validation.rs`) or in `action_delete_account` (`runtime/runtime/src/actions.rs`) rejecting `DeleteAccount` actions where `beneficiary_id == receiver_id`/`account_id`, returning a clear `ActionErrorKind` (e.g. `DeleteAccountBeneficiaryIsSelf`) instead of silently burning the balance.

### Proof of Concept
1. Account `alice.near` holds a non-zero balance.
2. `alice.near` signs and submits a transaction to itself containing a single `DeleteAccount { beneficiary_id: "alice.near" }` action (self-delete, self-beneficiary) — this passes `validate_delete_action` since `"alice.near"` is a syntactically valid account id.
3. `action_delete_account` executes: it reads `account_balance = account.amount()`, pushes `Receipt::new_balance_refund("alice.near", account_balance)` into `new_receipts`, then sets `*account = None`, deleting `alice.near`.
4. The queued refund receipt (predecessor `"system"`, single `Transfer` action, receiver `alice.near`) is later processed. `apply_action` calls `check_account_existence`; since `account` is now `None` and `implicit_account_creation_eligible` is `false` (refund receipts are excluded), it returns `ActionErrorKind::AccountDoesNotExist`.
5. Back in `apply_action_receipt`, because `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the code adds the full `account_balance` to `stats.balance.other_burnt_amount` — i.e., it is burned, never reaching any account (`runtime/runtime/src/lib.rs:993-1000`).
6. Net effect: `alice.near`'s entire balance is irrecoverably destroyed instead of being paid out, purely as a consequence of `beneficiary_id == account_id`.
