### Title
Missing bounds check in `extractBytes32Array` allows an unhandled `ArrayIndexOutOfBoundsException`/`OutOfMemoryError` from attacker-controlled precompile calldata - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE-2020-23322 bug class is a parser that assumes a specific token/state without validating it, so malformed attacker input reaches an `assert()` and aborts the process. The java-tron analog is `PrecompiledContracts.extractBytes32Array`, which decodes an ABI-encoded `bytes32[]` parameter for a precompiled contract but, unlike its two sibling helpers, contains no bounds check on the attacker-supplied `offset`/`len` values before indexing and allocating.

### Finding Description
`extractBytes32Array` reads the array length directly from calldata and then indexes the `words` array without validating that `offset` is inside bounds and without clamping `len`: [1](#0-0) 

Compare this to the two neighboring helpers that decode similarly-shaped ABI arrays and explicitly guard against an out-of-range offset before indexing: [2](#0-1) 

`extractBytesArray` and `extractSigArray` both begin with `if (offset > words.length - 1) { return new byte[0][]; }`, but `extractBytes32Array` has no equivalent check. If a caller supplies an ABI offset word that decodes to a value `>= words.length`, `words[offset]` throws `ArrayIndexOutOfBoundsException`. If the length word decodes to a very large positive integer (via `DataWord.intValueSafe()`), `new byte[len][]` can throw `OutOfMemoryError` — which, being an `Error` rather than a `RuntimeException`, is not caught by the generic `catch (RuntimeException e)` blocks used throughout the VM interpreter loop and `Program`. This mirrors the JerryScript root cause: a structural assumption about position/well-formedness of attacker data is not validated before the code acts on it, and the resulting fault is not gracefully handled — it is a raw JVM exception/error escaping the expected control-flow (an “assertion-style” crash instead of a validated revert).

### Impact Explanation
- `ArrayIndexOutOfBoundsException` is a `RuntimeException`, so it is caught by the generic `catch (RuntimeException e)` in `VM.play`, which spends all energy and reverts the call — this path alone is low severity (failed transaction only).
- The more serious path is `OutOfMemoryError` from an oversized `len`. `Error` types are not caught by the `RuntimeException` handlers in `VM.play`/`Program`, so this can propagate out of the VM interpreter loop, out of `VMActuator`/`RuntimeImpl.execute`, and into block application in `Manager`. Depending on where it surfaces, this can crash the executing thread or, if the JVM heap is sufficiently exhausted, destabilize the node process — a DoS against a node processing a crafted transaction, which matches the "node crash or halt" impact bar.

### Likelihood Explanation
Reachability requires only a single signed transaction (`TriggerSmartContract`) calling the precompiled contract address that invokes `extractBytes32Array` with attacker-controlled calldata (the function is used to decode ABI `bytes32[]` parameters passed to a precompile, in the vicinity of `BatchValidateSign`/similar precompiles per the surrounding code and `SIG_LENGTH` constant used by the neighboring `extractSigArray`). No special privilege, signature forgery, or governance action is needed — any unprivileged contract caller can construct calldata whose length/offset words are crafted to trigger the out-of-bounds/oversized-allocation path. I could not fully confirm from the available index snippets which specific precompiled contract's `execute()` invokes `extractBytes32Array` (the exact call site was not retrievable within the tool budget); this should be verified directly in the file before treating this as fully confirmed.

### Recommendation
Add the same defensive bounds/length validation used in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`:
- Reject if `offset > words.length - 1` (or more strictly, if `offset + 1 > words.length`).
- Clamp/validate `len` against `words.length - offset - 1` before allocating `new byte[len][]`, so a malicious length cannot trigger an oversized allocation or read past the decoded words array.
- Ensure the precompile execution path uniformly converts any resulting `RuntimeException`/`Error` from ABI decoding into a graceful revert (`Pair<Boolean, byte[]>` failure) rather than letting an `Error` escape uncaught.
