## Analysis

I found a strong analog to CVE-2024-57822 in `third_party/ijar/zip.cc`. The Raptor CVE is a heap-based buffer over-read in a term-length-prefixed parser (nquads triples) that lacks a bounds check before reading a field of attacker-controlled length. The equivalent class in bazel's own code is `InputZipFile::ProcessCentralDirEntry`, which parses ZIP central directory entries.

### Finding

`InputZipFile::ProcessLocalFileEntry` (the local-file-header parser) always guards every field read with `EnsureRemaining(n, "state")` before advancing the cursor `p`, e.g.: [1](#0-0) [2](#0-1) 

By contrast, `InputZipFile::ProcessCentralDirEntry` — which reads `file_name_length`, `extra_field_length`, `file_comment_length`, and then walks the extra-field records — performs **no** `EnsureRemaining` checks at all before dereferencing memory at `p`, `extra_p`, or `extra` (`get_u4le`, `get_u2le`, `get_u8le`, `memcpy`): [3](#0-2) 

Specifically:
- `file_name_length`, `extra_field_length`, `file_comment_length` are read directly from attacker-controlled bytes with no validation against the actual remaining central-directory buffer size.
- The `memcpy(filename, p, len)` at line 520 and the `p += file_name_length` / `p += file_comment_length` advances can walk `p` past the end of the mapped input file.
- The inner extra-field loop (`while (extra_p != p)`) reads `header_id`/`data_size` via `get_u2le` and, for a `ZIP64_EXTRA_FIELD_TAG`, an 8-byte value via `get_u8le(extra)` — again with no check that `extra + 8` stays within the mapped region or within `extra_field_length`.

This function is called from `InputZipFile::ProcessNext` and `InputZipFile::CalculateOutputLength`, which are the entry points used when `ijar`/`zipper`-style logic reads any input `.jar`/`.zip` (e.g., interface-jar generation from a fetched Maven artifact, `java_import`/`aar_import` processing) — i.e. content whose *bytes* originate from an untrusted origin server or archive, matching the attacker model of "an outsider who publishes … bytes at a dependency URL, an archive."

### Why this is a real (if bounded) over-read

`FindZipCentralDirectory` locates the EOCD and hands `central_dir` (and file length) forward, but the length/offset fields inside individual central-directory-header records (as opposed to the container as a whole) are never cross-checked against the actual mapped file length in `ProcessCentralDirEntry`. `MappedInputFile` mmaps the file directly, so `p` walking past `zipdata_in_ + input_file_->Length()` reads past the end of the mapping (heap/mmap buffer over-read), directly analogous to `raptor_ntriples_parse_term_internal()` reading past the end of an nquads token buffer.

### Uncertainty

I was unable to fully trace `MappedInputFile`'s allocation strategy (whether it pads/rounds mmap length to a page boundary, which could make small over-reads land within the same mapped page in practice, reducing observable impact to "usually benign" rather than a guaranteed crash) or definitively confirm which bazel-invoked code paths (e.g. `singlejar`, ijar-based interface jar generation for downloaded jars) call this exact `InputZipFile` central-directory reader versus the alternate `output_jar.cc`/`zip_headers.h` path (which *does* have explicit `ziph::byte_ptr(ef) + ef->size() > ziph::byte_ptr(ef_end)` bounds checks, per `output_jar.cc:781-785` and `:936-940`). Given index size limits, I could not read the full `zip.cc`/`zip.h` file end-to-end or the `MappedInputFile` implementation to build a fully reproducible PoC; a Devin session with full repo/build access would be needed to compile a minimal crafted `.jar` and run it through the `ijar` binary (or a targeted `BuildIntegrationTestCase`) under ASan to confirm the heap-over-read empirically.

### Title
Heap-based buffer over-read in ZIP central directory parsing due to missing bounds checks - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in bazel's `ijar` ZIP reader parses central-directory-header length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and extra-field sub-records from attacker-controlled archive bytes without any `EnsureRemaining`-style bounds validation, unlike the sibling local-file-header parser `ProcessLocalFileEntry` in the same file, which validates every field read.

### Finding Description
`ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) advances a raw pointer `p` over the mmap'd input file using length fields taken directly from the archive without checking them against the remaining buffer size, and separately walks an "extra fields" region (`extra_p`) reading 2-byte and 8-byte little-endian values with no per-record bounds check against `extra_field_length` or the mapped file end. [3](#0-2) 
Compare this to `ProcessLocalFileEntry`, where every read is preceded by `EnsureRemaining`: [2](#0-1) 

### Impact Explanation
A hostile origin server or mirror serving a malformed `.jar`/`.zip` (e.g. behind an `http_jar`/Maven dependency fetch, or committed to an untrusted branch that CI builds) whose central directory declares oversized `file_name_length`/`extra_field_length`/`file_comment_length` or a malformed extra-field chain can cause `ijar` (used for interface-jar generation of external Java dependencies) to read past the end of the mmap'd input buffer — a heap/mmap-based buffer over-read, matching CVE-2024-57822's class. This does not corrupt writes or escape the sandbox, but it can crash the build process (info leak into `filename[PATH_MAX]` copy is bounded, but the `extra_p` walk is not) and represents undefined behavior on attacker-supplied bytes that a hash/sha256 on the archive as a whole would not prevent (Bazel typically only verifies a checksum of the whole downloaded archive, not internal structural validity of every embedded jar processed later by ijar).

### Likelihood Explanation
Medium: reaching this code requires the archive to actually be routed through `ijar` (interface jar generation), which is a common path for Java external dependencies, but does not apply to all fetched content generically.

### Recommendation
Add `EnsureRemaining`-equivalent bounds checks in `InputZipFile::ProcessCentralDirEntry` before every pointer advance/read (`file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field record's `header_id`/`data_size`/payload), mirroring the checks already present in `ProcessLocalFileEntry`, and validating `extra_p + 4 <= p` and `extra_p + data_size <= p` before dereferencing, as `output_jar.cc` already does for its own extra-field walks (`output_jar.cc:781-785`, `:936-940`).

### Proof of Concept
Not independently verified/compiled due to tool limitations (no filesystem/build access in this session). A concrete PoC would need to: 1) construct a minimal ZIP with a central directory header whose `extra_field_length` exceeds the actual remaining space before EOCD, or whose extra-field payload declares `data_size` extending past the true extra-field region; 2) run it through the `ijar` binary or an equivalent `BuildIntegrationTestCase`/`zip_test` harness under AddressSanitizer to confirm the over-read. This should be done in a follow-up Devin session with full repo and build/test access.
