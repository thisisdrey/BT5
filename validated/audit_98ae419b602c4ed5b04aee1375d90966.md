Index generation is cryptographically random (`crypto/rand`) via `generateIndex` in `handshake_manager.go:624-643`, so the index isn't guessable — but it is passively observable, since `RemoteIndex` is sent in plaintext in every handshake and message header. Combined with the fact that `RecvError` handling occurs entirely pre-authentication (before certificate verification / Noise decryption), this produces a valid, reachable, no-cert analog to the report's "unauthenticated function that forces a state change for attacker gain."

### Title
Unauthenticated `RecvError` packets allow index-and-address-based remote tunnel teardown (state poisoning) - ([File: outside.go])

### Summary
`RecvError` packets are processed before any Noise handshake or certificate verification, and the only anti-spoofing check is that the UDP source address must equal the currently-known remote address of the targeted tunnel. Both the `RemoteIndex` and the current remote `UdpAddr` are observable/learnable by a passive on-path or off-path attacker (they travel in plaintext in every packet header and are also distributed via LightHouse), letting an attacker with no CA-signed certificate force `closeTunnel` and pending-handshake deletion on a victim, similar in spirit to the report's concern about an unauthenticated function that can force state changes for gain.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches `header.RecvError` packets to `f.handleRecvError` immediately after header parsing, with no cert/Noise verification: [1](#0-0) 

`handleRecvError` then looks up the hostinfo purely by `h.RemoteIndex` and checks only that the packet's source `addr` matches `hostinfo.GetRemote()`; if so it unconditionally tears down the tunnel and removes it from the pending handshake map: [2](#0-1) 

This spoof check is inherently weak against an off-path/on-path attacker who can forge the UDP source address (UDP has no source-address authentication) as long as they know (a) the tunnel's `RemoteIndex` and (b) the peer's currently known UDP remote address. Both values are exposed in plaintext: `RemoteIndex` appears in every packet's unencrypted header, and the endpoint address is either the packet's visible source/destination or discoverable via LightHouse `HostQueryReply`/`HostUpdateNotification` traffic. No certificate, PSK, or handshake completion is required to send this packet — it is processed prior to `hostinfo.ConnectionState.Decrypt`.

### Impact Explanation
This allows an unauthenticated, no-cert attacker to remotely force `f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)`, poisoning both nodes' tunnel state and forcing a re-handshake at a time of the attacker's choosing. This is a remote state-poisoning / denial-of-service primitive: an attacker can repeatedly and predictably force re-handshakes between victims, which (similar to the "forced predictable update" pattern in the source report) creates a race window the attacker can exploit — e.g., to win address-registration races with a lighthouse, to inject an attacker-controlled remote address before the legitimate peer re-establishes (see `TestWrongResponderHandshake` in `e2e/handshakes_test.go` for how a bad lighthouse-supplied remote can otherwise be exploited), or simply to persistently disrupt connectivity.

### Likelihood Explanation
The `RemoteIndex` is a random 32-bit value (not guessable via brute force at scale), which limits blind attackers; however, any attacker who can observe traffic (passive on-path, e.g., shared network segment, ISP-level observer, or a previous/former peer) or who has ever been legitimately connected can trivially harvest a valid `(RemoteIndex, current remote addr)` pair from unencrypted headers/LightHouse traffic and later spoof it from anywhere, since UDP source addresses are not otherwise authenticated at this stage. The CHANGELOG shows this general class of message has already been a source of security hardening (`recv_error` disabled outside allowable counter window, #1459; `send_recv_error`/`accept_recv_error` config added to limit exposure), which corroborates that this is a recognized, previously-partially-mitigated risk area rather than a purely theoretical one: [3](#0-2) 

### Recommendation
Do not act on `RecvError` for tunnels whose Noise session is otherwise healthy without cryptographic evidence. Consider: (1) requiring `RecvError` to be authenticated (e.g., MAC'd with the session key or replaced with an encrypted control message once a tunnel is established, rather than accepted in cleartext before decrypt), (2) rate-limiting/deduplicating `RecvError`-triggered teardowns per remote index, and (3) treating a source-address match alone as insufficient trust, since UDP source addresses are attacker-controllable off-path.

### Proof of Concept
1. Attacker passively observes (or has previously participated in) a Nebula UDP flow between victim A and victim B, recording A's currently valid `RemoteIndex` for its tunnel to B and B's UDP `AddrPort` (both are visible in plaintext packet headers, or learnable via a LightHouse `HostQueryReply`).
2. Attacker crafts a bare `header.H{Type: header.RecvError, RemoteIndex: <observed index>}` packet (as constructed in `f.sendRecvError`, `outside.go:528-539`) and sends it to A, spoofing the UDP source address to equal B's known address.
3. `readOutsidePackets` routes it to `handleRecvError` before any decryption/authentication; since `addr == hostinfo.GetRemote()`, the check passes and A's tunnel to B is torn down (`closeTunnel` + `DeleteHostInfo`), with no cryptographic proof the packet came from B. [4](#0-3) 

**Uncertainty note:** I could not verify from the available index whether the `send_recv_error`/`accept_recv_error` config (`recvErrorConfig`, `interface.go:124-143`) is enabled by default or defaults to a more restrictive mode (e.g., `recvErrorPrivate`/`recvErrorNever`), which materially affects real-world exploitability; a Devin session with full repo access would be needed to check `config.yml`/default wiring to confirm the default posture.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
