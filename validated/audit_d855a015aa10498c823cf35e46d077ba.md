Audit Report

## Title
`process_delivery_receipt` pays relayer reward without checking `DeliveryReceipt.success` - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Pallet::process_delivery_receipt` decodes an Ethereum `InboundMessageDispatched` event into a `DeliveryReceipt` struct that carries a `success: bool` field, but the function never reads or checks `receipt.success` before paying out the relayer reward. It only validates the gateway address and the existence of a `PendingOrder`, then unconditionally calls `T::RewardPayment::register_reward` whenever `order.fee > 0` and removes the order.

## Finding Description
The `DeliveryReceipt` primitive decodes the Solidity `InboundMessageDispatched` event, preserving `success` from the event: <cite repo="Kohvert/polkadot-sdk--037" path="bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs" start="10-12" end="14-27" /> and [1](#0-0) .

The extrinsic `submit_delivery_receipt` verifies the log via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt` without ever inspecting `success`: [2](#0-1) .

`process_delivery_receipt` checks only the gateway address and that a `PendingOrder` exists for the nonce, then unconditionally pays the fee and removes the order — `receipt.success` is decoded onto `receipt` but is never read anywhere in this function: [3](#0-2) .

The module doc comment describes the intended flow as simply "pay reward with fee attached in the order" after verifying the delivery proof, with no mention of a success-dependent branch: [4](#0-3) . Existing tests and benchmarks (`submit_delivery_receipt_succeeds_after_unhalt`, the `submit_delivery_receipt` benchmark, and the emulated integration test) all construct receipts with `success: true` and never exercise the `success: false` path, confirming there is no logic anywhere gating on this field: [5](#0-4) [6](#0-5) .

The only existing guard on this payout path is the bridge-halt check inside `Verifier::verify` (added in a recent PR to block payouts while governance has halted the light client): [7](#0-6) . This halt check is orthogonal to `success` — it only blocks proof verification entirely during an emergency stop, it does nothing to distinguish a genuinely verified-but-failed dispatch (`success = false`) from a successful one during normal operation. So under normal, non-halted operation, the reward is paid regardless of whether the dispatched command actually succeeded on Ethereum.

## Impact Explanation
Any relayer holding a valid proof for a real `InboundMessageDispatched` event with `success = false` (i.e., the dispatched command reverted on Ethereum) can submit `submit_delivery_receipt` and still receive the full `order.fee` reward via `T::RewardPayment::register_reward`, while the `PendingOrder` is removed as if delivery had succeeded. This is a payout ( `order.fee` ) settled to the relayer/`reward_account` beneficiary despite the underlying bridge action not completing successfully — a duplicate/unbacked settlement relative to actual service delivered, matching the "duplicate settlement or payout" impact criterion for Snowbridge BridgeHub code.

## Likelihood Explanation
`submit_delivery_receipt` is a public, permissionless, signed extrinsic reachable by any account once a message is queued (`PendingOrders` populated) and the corresponding Ethereum event is included and finalized. `success = false` naturally arises whenever the dispatched command reverts on the Ethereum side (e.g., insufficient gas, downstream revert). No proof forgery, relayer collusion, or privileged access is required — only submission of a legitimate but failed-dispatch event log with a valid inclusion proof, which is a normal, repeatable occurrence in bridge operation.

## Recommendation
Add an explicit branch on `receipt.success` in `process_delivery_receipt` before registering the reward: only invoke `T::RewardPayment::register_reward` when `receipt.success == true`; when `false`, still remove the stale `PendingOrder` to avoid leaving it dangling, but skip or reduce the reward and emit a distinct event (e.g. `MessageDeliveryFailed`) to make failed dispatches observable and unpaid.

## Proof of Concept
1. A message is queued via `do_process_message`, creating `PendingOrder { nonce, fee, .. }` with `fee > 0`: [8](#0-7) .
2. The message is relayed to Ethereum but the dispatched command reverts, so the Gateway emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account calls `submit_delivery_receipt` with a valid inclusion proof of this event; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` checks only `gateway` and `PendingOrders` existence, both pass, then calls `T::RewardPayment::register_reward(&reward_account, .., order.fee)` unconditionally and removes the order: [9](#0-8) .
5. A unit test analogous to `submit_delivery_receipt_succeeds_after_unhalt` but constructing the event log with `success: false` would demonstrate `MessageDelivered` is still emitted and the reward is still registered, with no differing behavior from the `success: true` case.

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
