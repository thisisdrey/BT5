Audit Report

## Title
Non-standard ERC20 tokens (no/void `bool` return, e.g. USDT/BNB-style) cause `ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` to report failure after the on-chain transfer already succeeded, permanently stranding user funds - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` dispatches a real `pallet_revive::bare_call` executing `IERC20::transferCall` that moves the user's ERC20 balance to `TransfersCheckingAccount` before any success/failure determination is made. It then requires the call's return data to strictly ABI-decode as a `bool` via `IERC20::transferCall::abi_decode_returns_validate`; any ERC20 that returns no data on success (USDT/BNB-style non-standard tokens) causes this decode to fail even though `did_revert()` is `false` and the balance already moved, producing `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))` with no `AssetsInHolding` credit ever created. [1](#0-0)  The symmetric issue exists in `deposit_asset_with_surplus`, which transfers from `TransfersCheckingAccount` to the beneficiary and applies the same strict-decode-or-fail logic after the transfer is committed. [2](#0-1) 

## Finding Description
In `withdraw_asset_with_surplus`, the code builds `IERC20::transferCall { to: checking_address, value: ... }.abi_encode()` and dispatches it via `pallet_revive::Pallet::<T>::bare_call` from the withdrawing user's own account, which is the actual state-mutating operation that moves the on-chain ERC20 balance. [3](#0-2)  After the call, if `return_value.did_revert()` is false, the code still requires `IERC20::transferCall::abi_decode_returns_validate(&return_value.data)` to yield a `bool`; if this fails to decode (e.g., empty return data from a non-standard token), the `map_err` branch converts it to `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))` — even though the transfer already succeeded on-chain. [4](#0-3)  Because the function returns `Err` before reaching the `Ok((AssetsInHolding::new_from_fungible_credit(...), surplus))` branch, no imbalance is ever recorded in `AssetsInHolding`, so the XCM executor treats the withdrawal as never having happened, while the tokens are already sitting in `TransfersCheckingAccount`. [5](#0-4)  The bundled reference OpenZeppelin contract used for testing always returns `true`/`false` from `transfer`, masking the bug in the repo's own test fixtures, but real-world tokens like USDT/BNB return no data on success, which is exactly the class this fixture cannot represent. There is no reconciliation mechanism exposed for `TransfersCheckingAccount` in this transactor.

## Impact Explanation
This falls within the "Balances, assets ... must conserve value and settle exactly once to the rightful beneficiary" and "permanent user-fund ... lock" impact categories. `ERC20Transactor` is wired as a real transactor in `AssetHubWestend`'s XCM configuration [6](#0-5) , and any ERC20 registered for use through the configured `Matcher` that isn't a strictly bool-returning implementation will have real balance movement to/from `TransfersCheckingAccount` with no corresponding XCM-level accounting, permanently stranding those funds since no sweep/reconciliation extrinsic is exposed for that account in this code path.

## Likelihood Explanation
Likelihood depends entirely on whether such a non-standard token (no bool return on `transfer`) is actually configured as a supported asset for `ERC20Transactor`'s `Matcher` — this is an operational/governance decision, not something an attacker controls. Given that decision is made, every ordinary user withdrawal/deposit for that asset is affected deterministically and requires no privileged actor, matching the "public underpriced work" / unprivileged-user-triggered class described.

## Recommendation
Adopt SafeERC20-equivalent semantics for the `bare_call`-mediated ERC20 transfers in `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`: treat a non-reverted call with empty return data as success rather than failing on ABI-decode, and only fail when the call actually reverts or explicitly returns `false`. Add tests using a mock ERC20 that returns no data on `transfer` (mimicking USDT/BNB) to confirm funds aren't stranded in `TransfersCheckingAccount`, and consider a governance-gated reconciliation extrinsic for that account as defense-in-depth.

## Proof of Concept
1. Register (via the configured `Matcher`) a minimal ERC20 contract whose `transfer(address,uint256)` updates balances/emits `Transfer` but declares no `returns (bool)`, replicating USDT/BNB semantics.
2. As an ordinary user, trigger an XCM operation causing `ERC20Transactor::withdraw_asset_with_surplus` to execute for this asset on `AssetHubWestend`.
3. `pallet_revive::bare_call` executes `IERC20::transferCall`; the contract's internal balances update (user decreases, `TransfersCheckingAccount` increases) and `did_revert()` returns `false`.
4. `return_value.data` is empty, so `IERC20::transferCall::abi_decode_returns_validate` returns `Err`, and the function returns `Err(XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode"))`.
5. Query `balanceOf(who)` (decreased) and `balanceOf(TransfersCheckingAccount)` (increased) to confirm funds moved with no corresponding `AssetsInHolding` credit — funds are stranded with no exposed recovery path in this transactor.

				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(

					))

				}
			}
