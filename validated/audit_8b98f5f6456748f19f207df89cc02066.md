### Title
Dust deposit-token transfers fill `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, bricking deposits, transfers and seize flows for the victim - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The reference bug (CVE-2022-46770) is a resource-exhaustion DoS: a single crafted input forces the system into unbounded work and halts liveness. The Metronome analog is account-list griefing: `Pool` tracks each account's deposit/debt tokens in `MappedEnumerableSet` and reverts any addition once `debtTokensOfAccount + depositTokensOfAccount >= MAX_TOKENS_PER_USER` (30). Any `DepositToken` transfer that takes a recipient from a zero to a non-zero balance calls `addToDepositTokensOfAccount`, which enforces that cap. An attacker can dust-transfer small amounts of every listed deposit token to a victim, permanently saturating their list. From then on, every code path that would add a new token to the victim's list reverts — blocking them from depositing a new collateral type, receiving deposit tokens, or receiving seized collateral — until the victim clears entries one by one.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` when the combined per-account lists reach `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`).
- `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are called by `DepositToken`/`DebtToken` on any 0→positive balance transition, i.e., on deposit, `transfer`/`transferFrom`, `seize`, and mint/issue (`contracts/Pool.sol:204-220`).
- `addDepositToken` also caps the pool-wide list at `MAX_TOKENS_PER_USER` (`contracts/Pool.sol:703`), so the number of distinct deposit tokens an attacker needs for dust is bounded (~30 or fewer) and each costs only a dust amount plus gas.
- Once the victim's list is full:
  - `DepositToken.deposit` into any collateral they don't already hold reverts → they cannot add a *new* collateral type to rescue an unhealthy position.
  - `DepositToken.transfer`/`transferFrom` to them reverts → they cannot receive deposit tokens.
  - `Pool.liquidate` calls `depositToken_.seize(account_, _msgSender, _toLiquidator)` (`contracts/Pool.sol:589`); if the liquidator's list is dust-filled the same way, `seize` reverts, blocking liquidations targeting that liquidator.
- No modifier prevents this: there is no opt-in, no minimum-transfer threshold, and `SynthContext`/pause/reentrancy checks don't apply to the accounting path.

### Impact Explanation
Temporary freezing of funds and liveness loss for a targeted account. A victim whose position is falling toward liquidation and who only holds an unlisted collateral (e.g., newly acquired WETH deposit token they never deposited, or a collateral type they haven't used) cannot deposit it to restore health — `addToDepositTokensOfAccount` reverts. The same attack against active liquidation bots/EOAs prevents them from receiving seized collateral, degrading liquidation liveness, which is the direct analog of "loss of forwarding" in the CVE. The victim can recover by transferring out the dust entries (each removal frees a slot), so the freeze is temporary rather than permanent.

### Likelihood Explanation
The attack is cheap (≤ ~30 dust transfers of already-existing deposit tokens, no privileged role, no flash loan required) and permissionless — `DepositToken.transfer` is a public ERC-20-style entry point. It requires the victim to not already hold the needed collateral tokens, which is common for new accounts. Cost to the victim to unblock is symmetric (transfer dust back out), which bounds severity.

### Recommendation
- Remove the `onlyIfAdditionWillNotReachMaxTokens` check from the add path and instead bound iteration cost where it matters (`debtOf`/`depositOf` loops), or raise the cap — the pool itself can't list more deposit tokens than `addDepositToken` allows anyway.
- Alternatively, make `seize` and liquidation-critical paths exempt from the cap (e.g., allow addition during `seize` to the fee collector/liquidator), and/or treat dust balances below a threshold as not occupying a slot.
- A simpler mitigation is to track only tokens with balance above a minimum dust threshold, or let any account remove foreign tokens from its own list via a `sweep` function.

### Proof of Concept
Hardhat fork sketch (assumes a live Pool with ≥2 listed deposit tokens `dA`, `dB`, …, and attacker holding or flash-borrowing dust of each underlying):

```ts
// 1. Attacker deposits a dust amount of each underlying via DepositToken.deposit(underlying, dust)
//    so attacker holds a tiny balance of every listed depositToken.
for (const dt of listedDepositTokens) {
  await dt.connect(attacker).deposit(DUST); // or underlying.approve + deposit via pool flow
}

// 2. Attacker transfers 1 wei of each deposit token to victim.
//    Each transfer flips victim's balance 0 -> >0 and calls
//    Pool.addToDepositTokensOfAccount(victim), filling the list to 30.
for (const dt of listedDepositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1);
}

// 3. Any subsequent operation that would add a NEW token to victim's list reverts.
const newCollateral = anotherListedDepositTokenNotYetUsedByVictim; // or a newly added one
await expect(
  newCollateral.connect(victim).deposit(amount)
).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

await expect(
  listedDepositTokens[0].connect(attacker).transfer(victim.address, 1)
).to.not.be.reverted; // already-listed token still works; new ones don't

// 4. Liquidation liveness: dust-fill a liquidator bot, then
//    Pool.liquidate(...) -> depositToken.seize -> addToDepositTokensOfAccount(liquidator)
//    reverts with UserReachedMaxTokens once liquidator's list is full.
```

Note: I verified the cap check and the add/remove entry points in `contracts/Pool.sol`, but did not read `DepositToken.transfer`/`seize` line-by-line in this pass to confirm the exact call site of `addToDepositTokensOfAccount` on every transfer path; the doc comments on `Pool.sol:200-219` state the contract calls it on any 0→positive balance change, which the PoC relies on. The attack is reversible by the victim (temporary freeze), so severity is bounded accordingly.
