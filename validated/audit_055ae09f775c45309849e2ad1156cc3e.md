### Title
Signature-malleability weight double-counting in `ValidateMultiSign` precompile allows multisig-threshold bypass with a single key - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompile (address invoked by any smart contract to check on-chain multisig permissions) accumulates `weight` for each signature it recovers a valid address from, but its de-duplication check only skips accumulation when the exact same signature byte sequence for an already-seen address is repeated. Because ECDSA signatures over secp256k1 are malleable (a given `(r,s)` and `(r, n-s)` both recover to the same address for the same message hash), a caller controlling a single private key can submit two syntactically-different but validly-recovering signatures for that one key and have `ValidateMultiSign` count the key's `weight` twice, inflating `totalWeight` past the configured `permission.getThreshold()`.

### Finding Description
`ValidateMultiSign.execute()` parses an address, `permissionId`, message `data`, and an array of `signatures` from the precompile call, then for each signature recovers the signer address and looks up its configured weight in the target account's `Permission`: [1](#0-0) 

The de-duplication logic is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
This only `continue`s (skips weight addition) when the *exact same signature bytes* for an address were already seen. If the same address appears again with a *different* signature (e.g., produced via ECDSA `s`-malleability, `s' = n - s`, still valid and still recovering to the same address for the identical `hash`), the code falls through and adds `weight` for that address a second time. Because Tron's signature verification does not appear to enforce canonical low-`s` values in this precompile path (only `Rsv`/length checks are visible in transaction-level signature parsing, not in this precompile), an attacker holding a single active key with assigned `weight` can trivially craft a second malleable signature over the same `hash` and submit both in the `signatures` array. `totalWeight` then becomes `2 * weight (or more, bounded only by MAX_SIZE=5)` for that single key, letting an attacker satisfy `permission.getThreshold()` (e.g., a 2-of-2 or higher multisig) without possessing any of the other required keys.

This precompile is directly reachable by any contract deployer/caller: any smart contract can invoke `ValidateMultiSign` (mapped precompiled contract address) with attacker-controlled `data` in a normal transaction, with no special privilege needed — matching the "TVM opcodes, precompiles and energy metering" and "signature and permission verification" in-scope categories.

### Impact Explanation
Any Tron account, wallet contract, or DApp that relies on `ValidateMultiSign` to enforce an on-chain active-permission multisig threshold (a common pattern for smart-contract wallets and custody/escrow contracts that gate withdrawal or execution on TVM-level multisig checks) can have its authorization bypassed by a single colluding or compromised key. This is a concrete "unauthorized account operation" vulnerability — it can be used to unlock or execute privileged operations (e.g., release of escrowed/custodied funds) protected by multisig logic implemented via this precompile, without the required number of distinct approving keys, resulting in theft or unauthorized transfer of funds.

### Likelihood Explanation
High. ECDSA signature malleability is well-known and trivial to compute (flip `s` to `n - s`) once a single valid `(r, s)` signature exists; no additional cryptographic capability is required beyond holding one private key with assigned weight. The precompile is callable by any account via ordinary contract calls, so exploitation requires only crafting the calldata array with two malleable signatures for the same key rather than obtaining additional keys.

### Recommendation
- Enforce canonical (low-`s`) signature form before/during recovery in `ValidateMultiSign.execute()` (reject signatures with `s > secp256k1n/2`), matching standard non-malleable signature handling used elsewhere in Ethereum/TVM ecosystems.
- Change the de-duplication logic to key strictly on `recoveredAddr` (skip/`continue` whenever the recovered address has already contributed weight), rather than allowing a second contribution when only the raw signature bytes differ.

### Proof of Concept
1. Deploy or call an existing contract that invokes the `ValidateMultiSign` precompile against a target account `A` whose active `Permission` has threshold `T` requiring keys `K1` (weight `w`) and `K2` (weight `w`), with `w < T <= 2w`.
2. Attacker holds only `K1`. Compute `hash = sha256(address || permissionId || data)` per the precompile's construction.
3. Sign `hash` with `K1` to get `(r, s)`. Compute the malleable counterpart `(r, n-s)` (same recovered address, valid ECDSA signature).
4. Submit `signatures = [sig1_bytes, sig2_bytes]` (the two byte-distinct encodings) to the precompile call.
5. In `execute()`, iteration 1 adds `weight` for `K1`'s address; iteration 2 finds `recoveredAddr` already in `executedSignList` but `sign` (different bytes) not in list, so it does **not** `continue` and adds `weight` again, reaching `totalWeight = 2w >= T`, returning `dataOne()` (success) despite only one real signer.
