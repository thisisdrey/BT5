### Title
Stale PromiseYieldReceipt survives account deletion and can overwrite a recreated account's contract via `DeployContract` on timeout resume - (File: `runtime/runtime/src/lib.rs`, `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (used by `action_delete_account`) removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData`, but never cleans up `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the pending `TrieKey::PromiseYieldTimeout` queue entry for that account. If a contract yields a promise (`promise_yield_create`) that batches a `DeployContract` action onto itself and then the account is deleted before the yield resumes or times out, the stale yield receipt remains in state keyed only by `(receiver_id, data_id)`. When a new, unrelated owner later recreates an account with the same `account_id` and deploys their own contract, the original timeout will still fire and `resolve_promise_yield_timeouts` will deliver a `PromiseResume` to that account name, executing the old, attacker-chosen `DeployContract` action against the new incarnation of the account.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`) to purge account state. `remove_account` removes `Account`, `ContractCode`, all `AccessKey`/`GasKeyNonce` entries, and `ContractData`, but has **no code path that touches `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, or `PromiseYieldIndices`** [1](#0-0) .

A contract can create a self-targeted pending promise via `promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660-3718`), whose receiver is always `self.context.current_account_id` [2](#0-1) . The returned promise index is a normal promise index that can be extended with further `promise_batch_action_*` calls, including `promise_batch_action_deploy_contract`, appending a `DeployContract` action with attacker-chosen bytecode to the same pending receipt (batched actions to a promise index are a standard NEAR Promise API feature, confirmed present via `promise_batch_action_deploy_contract` usages across the VM logic and test contracts).

The yield is persisted with `set_promise_yield_receipt` under `TrieKey::PromiseYieldReceipt { receiver_id, data_id }` [3](#0-2) , and a matching timeout entry is enqueued under `TrieKey::PromiseYieldTimeout { index }` (`core/store/src/utils/mod.rs:181-198`) [4](#0-3) , keyed purely by `account_id`/`data_id` strings, with no binding to the specific "incarnation" of the account (no account nonce/creation-height binding).

If the attacker (the original account owner) never resumes and instead deletes the account (`DeleteAccountAction`), `remove_account` leaves the `PromiseYieldReceipt`, `PromiseYieldStatus`, and the `PromiseYieldTimeout` queue entry intact in state.

Once `apply_state.block_height` reaches `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) checks only `state_update.contains_key(&promise_yield_key)` where `promise_yield_key = TrieKey::PromiseYieldReceipt { receiver_id: queue_entry.account_id, data_id: queue_entry.data_id }` [5](#0-4)  — it does not check whether the account still exists or whether it is the same account that created the yield. It creates and forwards a `PromiseResume` receipt targeting `queue_entry.account_id` with `data: None` [6](#0-5) .

When that `PromiseResume` is later processed (`runtime/runtime/src/lib.rs:1500-1568`), the code checks `get_promise_yield_status(state_update, account_id, data_id)` for `ResumeInitiated` (not found here, since it was never resumed), then fetches `get_promise_yield_receipt(state_update, account_id, data_id)` — finds the stale receipt — and unconditionally executes it via `apply_action_receipt` [7](#0-6) . This executes the embedded `DeployContract` action (`action_deploy_contract`, `runtime/runtime/src/actions.rs:274-312`) against whatever account currently exists under that `account_id` — the new owner's freshly recreated account — silently overwriting `AccountContract::Local` with the attacker's old bytecode [8](#0-7) .

The authorization/actor check for actions inside a receipt only verifies that the *receiver account id string* matches (and the predecessor is "self", since the receipt was self-yielded) — it has no notion of account identity persisting across a delete/recreate cycle, so the exactness invariant (only the current owner's actions may mutate the current account state) is violated.

### Impact Explanation
This is a contract-code hijack of a recreated account: the new legitimate owner deploys and believes their own contract is live, but a leftover receipt from the deleted prior owner silently replaces it with attacker-controlled bytecode. Any subsequent deposits, function calls, or funds sent to the account under the assumption the new code is running are instead handled by the attacker's chosen logic, enabling theft of any value sent to the account post-hijack (funds/assets can be drained by attacker-controlled code). This matches the NEAR bounty category of "authorization escalation across accounts/promises" leading to "theft of user funds."

### Likelihood Explanation
- Fully reachable by an unprivileged actor: only requires deploying/calling one's own contract that calls `promise_yield_create` + `promise_batch_action_deploy_contract`, then submitting a `DeleteAccountAction`.
- No validator, node-operator, or privileged access needed.
- The account-name collision requires the new owner to reuse the exact same account name after deletion, which is a normal occurrence for sub-accounts (e.g., factory-created sub-accounts, "rented" names) and is entirely within the attacker's control if they pre-select which name to squat/relinquish.
- Cost to the attacker is minimal: standard gas/storage fees for a yield-create + deploy-contract-batch + delete-account sequence, plus waiting for the timeout window (`yield_timeout_length_in_blocks`, a `RuntimeConfig` parameter — exact stable value not confirmed in this session, but it's a bounded, known number of blocks).
- Fully repeatable against any target account name the attacker controls before deletion.

### Recommendation
`remove_account` should also purge any pending `PromiseYieldReceipt`/`PromiseYieldStatus` entries (and, ideally, invalidate/skip the corresponding `PromiseYieldTimeout` queue entries) for the account being deleted, e.g., by iterating and removing all `TrieKey::PromiseYieldReceipt`/`TrieKey::PromiseYieldStatus`/`TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` keys with that `receiver_id` prefix, mirroring the existing access-key/contract-data cleanup loops. Alternatively/additionally, `resolve_promise_yield_timeouts` and the `PromiseResume` handler should verify that the account was not deleted/recreated since the yield was created (e.g., by binding the yield's validity to an account "epoch"/creation marker) before executing the stashed receipt.

### Proof of Concept
Integration/test-loop plan (in the style of `test-loop-tests/src/tests/yield_resume.rs`):
1. Deploy a test contract (extend `near-test-contracts/test-contract-rs`) exposing a method `call_yield_create_then_deploy(code: Vec<u8>)` that calls `promise_yield_create` to get a promise index, then calls `promise_batch_action_deploy_contract(promise_idx, code)` to append a `DeployContract` action to the same yielded receipt, and returns the `data_id` (do not resume).
2. On account `victim.test0`, call `call_yield_create_then_deploy(old_malicious_wasm)`; assert the yield is persisted (`get_yield_data_ids_in_latest_state`).
3. Submit `DeleteAccountAction { beneficiary_id: "test0" }` for `victim.test0`; commit the apply result; assert the account no longer exists via `get_account`.
4. Recreate `victim.test0` via `CreateAccount` + `Transfer` from `test0`, then deploy a new legitimate contract (`new_good_wasm`) via `DeployContractAction`; commit.
5. Advance blocks until `apply_state.block_height >= expires_at` for the original yield's timeout entry so `resolve_promise_yield_timeouts` fires and forwards the `PromiseResume(data: None)` receipt to `victim.test0`.
6. Process that receipt; then read `victim.test0`'s account record (`get_account`) and assert its `AccountContract::Local` hash equals `hash(old_malicious_wasm)` rather than `hash(new_good_wasm)` — demonstrating the silent overwrite of the new owner's contract.
7. Assert this occurs without any transaction signed by the new owner authorizing the deploy, confirming the authorization-exactness violation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_deploy_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    deploy_contract: &DeployContractAction,
    config: Arc<VmConfig>,
    next_config: Option<Arc<VmConfig>>,
    cache: Option<&dyn ContractRuntimeCache>,
) -> Result<(), StorageError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_contract").entered();
    clear_account_contract_storage_usage(state_update, account_id, account)?;

    let code = ContractCode::new(deploy_contract.code.clone(), None);
    account.set_storage_usage(
        account.storage_usage().checked_add(code.code().len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(AccountContract::Local(*code.hash())).or_inconsistent_state(account_id)?;
    // Legacy: populate the mapping from `AccountId => sha256(code)` thus making contracts part of
    // The State. For the time being we are also relying on the `TrieUpdate` to actually write the
    // contracts into the storage as part of the commit routine, however no code should be relying
    // that the contracts are written to The State.
    state_update.set_code(account_id.clone(), &code);
    // Precompile the contract under the current `wasm_config`. If a protocol upgrade with a
    // different `wasm_config` is scheduled for the next epoch, also schedule a fire-and-forget
    // warming compile under the new config so the on-disk cache is hot at the boundary.
    // Note: contract compilation costs are already accounted in deploy cost using special logic
    // in estimator (see get_runtime_config() function).
    precompile_contract_with_warming(&code, config, next_config, cache);
    // Inform the `store::contract::Storage` about the new deploy (so that the `get` method can
    // return the contract before the contract is written out to the underlying storage as part of
    // the `TrieUpdate` commit.)
    state_update.record_contract_deploy(code);
    Ok(())
}
