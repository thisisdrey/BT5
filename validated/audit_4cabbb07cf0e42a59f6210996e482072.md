### Title
Uncontrolled memory allocation from attacker-declared array length in `BatchValidateSign`/`ValidateMultiSign` precompiles - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` (precompile `0x...09`) and `ValidateMultiSign` (precompile `0x...0a`) TVM precompiled contracts decode a signature/address array length directly from an attacker-controlled calldata word and immediately allocate a Java array of that declared size — before any bound check and before the energy charged reflects the declared size. This mirrors the dompdf bug class: a "declared dimension" (here, an ABI array length embedded anywhere in the calldata) drives a native/JVM allocation while the metering (there: `memory_limit`; here: TVM energy) is computed from the unrelated actual payload size, not the declared value.

### Finding Description
`extractBytesArray` and `extractBytes32Array` trust a length word taken from arbitrary calldata content and allocate accordingly with no upper bound: [1](#0-0) 

```
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
}
private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
  ...
  int len = words[offset].intValueSafe();
  byte[][] bytesArray = new byte[len][];
  ...
}
```

Both `BatchValidateSign.doExecute` and `ValidateMultiSign.execute` call these helpers using a length index whose position (`offset`) and whose *content* (`len`) are both taken from raw calldata words, fully attacker-controlled: [2](#0-1) 

The energy charged for these calls, however, is computed only from the **physical byte length of the calldata**, not from the declared `len` value that drives the allocation: [3](#0-2) 
```
public long getEnergyForData(byte[] data) {
  long cnt = (data.length / WORD_SIZE - 5) / 6;
  return cnt * ENGERYPERSIGN;
}
```

Because `len` is decoded from one specific 32-byte word inside `data`, an attacker can submit a small calldata (e.g. ~6-7 words) whose `getEnergyForData` result is near zero, while embedding an arbitrary 32-bit value (up to `Integer.MAX_VALUE`, ≈2.1 billion) at the length-word position. `new byte[len][]` is executed **before** the subsequent `cnt > MAX_SIZE` bound checks that exist further down in the method: [4](#0-3) 

The `MAX_SIZE` guard only protects the "TIP-854" hardened path (`VMConfig.allowTvmSelfdestructRestriction()`), which pre-checks `sigArraySize`/`addrArraySize` before calling `extractSigArray`. When that flag is disabled (legacy path, still reachable), `extractBytesArray`/`extractBytes32Array` are called unconditionally with no pre-check at all — allocation happens first, validation happens after the array already exists.

Reachability is verified via `Program.callToPrecompiledAddress`, which computes required energy from `contract.getEnergyForData(data)` and only skips execution if that (attacker-minimizable) value exceeds the call's energy budget: [5](#0-4) 

Both precompiles are reachable from any smart-contract `CALL`/`STATICCALL` to address `0x...09` or `0x...0a`, which in turn is reachable from an ordinary `TriggerSmartContract` transaction or an unauthenticated `wallet/triggerconstantcontract` API call (constant call, no broadcast, no fee needed beyond minimal energy for a call op).

### Impact Explanation
A single cheap call (constant call or a low-fee `TriggerSmartContract`) can force the node to attempt allocating an array of up to ~2^31 references (multiple GB depending on JVM pointer compression) with a near-zero energy charge. Repeated concurrent requests can exhaust JVM heap, trigger severe GC pauses, or crash node/FullNode/SolidityNode processes handling `triggerconstantcontract`/`triggersmartcontract`, denying service to legitimate API clients and block-processing workers — the same "uncontrolled resource consumption" (CWE-400) class as the dompdf advisory, but reachable in java-tron via TVM precompiles instead of image decoding.

### Likelihood Explanation
High. No special privileges, no funds, and no cooperation from validators/witnesses are required — any address can trigger `BatchValidateSign`/`ValidateMultiSign` via a trivial contract call or the public `triggerconstantcontract` HTTP/gRPC API, which does not require a broadcast transaction or fee. The malformed-calldata construction only requires placing an arbitrary 32-byte word at a computed offset, well within normal ABI encoding capability.

### Recommendation
- In `extractBytesArray` and `extractBytes32Array`, validate the decoded `len` against a strict upper bound (e.g., the existing `MAX_SIZE` constants) *before* allocating any array, independent of the `allowTvmSelfdestructRestriction` feature flag.
- Ensure `getEnergyForData` energy costs (or an additional pre-execution size check) account for attacker-controlled declared lengths, not merely the physical calldata size, so the two cannot diverge.
- Apply the same declared-length bound check uniformly regardless of hard-fork/feature-flag state, so the legacy (`allowTvmSelfdestructRestriction()==false`) code path is not left exploitable.

### Proof of Concept
Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign`) with the minimum number of words required to make `getEnergyForData` return 0 (few real signature bytes), but set the array-length word (`words[offset]`) to `0x7FFFFFFF`:

```
word0: hash (32 bytes)
word1: offset to signatures array (points to word4)
word2: offset to addresses array (points to some other small word)
word3..: padding
word4: 0x000000000000000000000000000000000000000000000000000000007FFFFFFF  // declared len
```
Send this as calldata in a `TriggerConstantContract` (or `TriggerSmartContract`) call to precompile address `0x...09`. `getEnergyForData` computes `cnt = (data.length/32 - 5)/6 ≈ 0`, so the call proceeds with negligible energy, but `extractBytesArray`/`extractBytes32Array` immediately executes `new byte[2147483647][]`, attempting a multi-gigabyte allocation before any `MAX_SIZE` check is applied.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
