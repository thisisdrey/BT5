### Title
Permissionless dust deposits on behalf of a victim fill `MAX_TOKENS_PER_USER`, permanently DoS-ing their deposits, transfers, and liquidation seizes - (File: contracts/DepositToken.sol)

### Summary
`DepositToken.deposit(amount_, onBehalfOf_)` lets anyone mint deposit-token shares to an arbitrary `onBehalfOf_` account. On first mint, `_mint` registers that token in the victim's per-account list via `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once `debtTokensOfAccount + depositTokensOfAccount >= 30`. An attacker can grief any account (EOA or contract such as a SmartFarming position holder) by depositing 1 wei of each listed collateral on the victim's behalf, permanently bricking every code path that would add a token to their list — deposits, `transfer`/`transferFrom` receipts, and liquidation `seize` calls.

### Finding Description
In `DepositToken.sol`, `deposit` is an unauthenticated external function that mints shares to `onBehalfOf_` without requiring `onBehalfOf_ == _msgSender()`:

- `deposit(...)` → `_mint(onBehalfOf_, _deposited)` (DepositToken.sol:211-234)
- `_mint` → `if (_balanceBefore == 0 && amount_ > 0) pool.addToDepositTokensOfAccount(account_)` (DepositToken.sol:486-488)
- `Pool.addToDepositTokensOfAccount` is gated only by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when the account already has 30 registered tokens (Pool.sol:143-148, 216-220).

The same "add on zero-balance transition" logic runs in `_transfer` (DepositToken.sol:518-520), so any token sent to a full-list victim reverts. `seize` (DepositToken.sol:343-345) is just `_transfer` under `onlyIfCanSeize`, so `Pool.liquidate` calls that seize collateral into a liquidator/victim with a full list also revert. The list is shared across debt and deposit tokens, so only ~30 entries total are needed; on a pool with ≥15 deposit tokens the attacker fills it with dust deposits alone, and `DebtToken.issue`/`flashIssue` style flows (which similarly call `addToDebtTokensOfAccount` when minting debt to a recipient) can fill the rest — I could not fully re-verify the `issue` signature due to search limits, but the deposit-token side alone is sufficient on deployments with enough collaterals (e.g., the deployed mainnet/optimism pools list many `msdToken`s).

No modifier stops this: `deposit` is `whenNotPaused nonReentrant onlyIfDepositTokenExists` — none restrict `onBehalfOf_`. The griefing is also effectively permanent: the victim cannot remove entries because removal only happens when their balance returns to zero, and they can't transfer the dust out if it is locked against debt — and even if they can clear it, the attacker can re-fill in the same or a subsequent transaction (front-running).

### Impact Explanation
Liveness break: the victim cannot receive any new deposit token, cannot accept transfers, cannot open new collateral positions, and — critically — `Pool.liquidate` transactions that would `seize` collateral to them (or that add a token to their list) revert. If the victim is a position holder, liquidators cannot seize new collateral types owed to them, and any integration contract (leveraged positions, gateways, multisigs) whose tokens-list is filled becomes unable to interact. This maps to the Wireshark bug class: crafted input (attacker-chosen `onBehalfOf_` + dust amount) crashes/aborts protocol operations for the targeted account, i.e., temporary-to-permanent freezing of funds.

### Likelihood Explanation
The attacker needs only dust amounts of each listed underlying (the tokens are transferred to the Treasury, so the cost is the underlying dust + fees + gas — no privileged role). Anyone can do it at any time against any address, including contracts that cannot themselves clear the list. It is mitigated only if a pool has few collateral types (<30 combined debt+deposit tokens), which bounds the window in which the list can be fully clogged by deposits alone.

### Recommendation
Restrict `onBehalfOf_` registration: either (a) only call `addToDepositTokensOfAccount` when `account_ == _msgSender()` (track positions only for the depositor), or (b) allow `addToDepositTokensOfAccount` to silently no-op (or let the token-list entry be a soft cap) instead of reverting once at max, and/or add a public `removeFromDepositTokensOfAccount`-style escape where a user can forcibly deregister a token with a zero/dust balance via `transfer(0)`-equivalent cleanup. Alternatively, enforce a minimum first-deposit amount.

### Proof of Concept
Hardhat sketch (assumes deployed-like pool with ≥ `MAX_TOKENS_PER_USER` deposit tokens, or use a mix with debt tokens):

```ts
// contracts/DepositToken.sol / contracts/Pool.sol
it('griefs victim token list via dust onBehalfOf deposits', async () => {
  const victim = alice.address
  const depositTokens = await pool.getDepositTokens() // all listed collaterals

  // Attacker deposits 1 wei of each collateral on behalf of victim
  for (const dt of depositTokens.slice(0, 30)) {
    const deposit = await ethers.getContractAt('DepositToken', dt)
    const underlying = await ethers.getContractAt('ERC20Mock', await deposit.underlying())
    await underlying.mint(bob.address, 1)
    await underlying.connect(bob).approve(deposit.address, 1)
    await deposit.connect(bob).deposit(1, victim) // fills victim's list
  }

  expect((await pool.getDepositTokensOfAccount(victim)).length +
         (await pool.getDebtTokensOfAccount(victim)).length).to.eq(30)

  // Victim can no longer receive a new deposit token
  const newDeposit = await ethers.getContractAt('DepositToken', depositTokens[30])
  await expect(newDeposit.connect(carol).deposit(100, victim))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // Liquidation seize to victim also reverts (seize -> _transfer -> addToDepositTokensOfAccount)
  await expect(pool.liquidate(synthetic.address, victim, victim /*liq to full-list acct*/, amount))
    .revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

Caveat: if the deployed pool has fewer than 30 combined deposit+debt tokens reachable by an unprivileged attacker (i.e., `DebtToken.issue`'s `to_` parameter cannot be arbitrary), the list cannot be fully filled and the impact degrades to blocking only the marginal tokens. The deposit-side vector is confirmed in `DepositToken.sol:211-234` and `486-488`, and the cap check in `Pool.sol:143-148` and `216-220`.
