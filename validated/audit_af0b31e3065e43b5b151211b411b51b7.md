### Title
Unchecked boolean return of `reduceAssetAmountV2`/`addAssetAmountV2` in `ExchangeTransactionActuator.execute` allows silent asset-balance corruption - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionActuator.execute()` calls `AccountCapsule.reduceAssetAmountV2` and `AccountCapsule.addAssetAmountV2` to move TRC10 asset balances between the account and the exchange pool, but it never checks the boolean result these methods return, exactly the same "unchecked success/fail return value" pattern flagged in the external report for ERC20 `transferFrom`. `TransferAssetActuator`, by contrast, explicitly checks the return of `reduceAssetAmountV2` and throws `ContractExeException` on failure, showing the codebase's own convention that this check is required for a debit to be trusted. [1](#0-0) [2](#0-1) 

### Finding Description
In `execute()`, the debit/credit legs of an exchange trade are performed as:
```
accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
...
accountCapsule.addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
```
Neither call's boolean return value is checked or propagated. `AccountCapsule` methods such as this return `false` when the operation logically fails (e.g., insufficient asset amount, or item not present in the internal asset map) rather than throwing, mirroring exactly the non-reverting ERC20 pattern in the external report where `transferFrom` returning `false` on failure is silently ignored by the caller. Since `validate()` performs a similar `assetBalanceEnoughV2` pre-check, in the normal path the failure condition should not trigger — but any discrepancy between the state checked at validate time and the state mutated at execute time (e.g., due to a stale snapshot, a race in how `assetMap`/`assetV2Map` entries are keyed under `AllowSameTokenName` transitions, or future changes to `reduceAssetAmountV2` that add new failure branches) will cause the debit to silently no-op while the trade is still marked `SUCESS` and the exchange pool and counter-party leg are updated as if funds were moved. This causes accounting to diverge from actual balances, unlike `TransferAssetActuator` which fails loudly by checking the return value and throwing `ContractExeException`.

### Impact Explanation
If the reduce operation silently fails while the transaction is still marked as `SUCESS`, the exchange pool balances and the received-token credit are updated with no matching debit, producing an unbacked/inflated balance for the trading account (medium/high impact: incorrect exchange pool accounting and free minting of asset value from the exchange's perspective) without any exception being thrown or transaction rejection occurring. This is a state-integrity impact class explicitly in scope (unbacked balance / permanent freezing or theft of exchange funds).

### Likelihood Explanation
Likelihood is lower than a directly exploitable bug because `doValidate()` currently gates the same condition via `assetBalanceEnoughV2`, and both checks are backed by the same store data at the time of the transaction. However, the missing check removes an important defense-in-depth guard that the codebase itself applies inconsistently (present in `TransferAssetActuator`, absent in `ExchangeTransactionActuator`), and any divergence between validate-time and execute-time state — including future modifications to `reduceAssetAmountV2`/`addAssetAmountV2` semantics, or any of the several call sites that already ignore these returns (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `MarketSellAssetActuator` per the grep results) — would let this silently corrupt account/exchange asset accounting with no error surfaced. This is a systemic code-quality gap rather than a single-transaction proven exploit, so it is assessed as valid but with moderate confidence in immediate exploitability.

### Recommendation
Check the boolean return of `reduceAssetAmountV2` and `addAssetAmountV2` in `ExchangeTransactionActuator.execute()` (and the other actuators identified via the same call pattern: `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `MarketSellAssetActuator`) and throw `ContractExeException` on failure, consistent with the pattern already used in `TransferAssetActuator`, so a trade can never be marked successful while an asset leg silently failed to move.

### Proof of Concept
Conceptual PoC (root cause, not a runnable exploit given current validate() gating):
1. Submit an `ExchangeTransactionContract` transaction that passes `doValidate()`'s `assetBalanceEnoughV2` check.
2. In `execute()`, if `reduceAssetAmountV2` internally returns `false` for any reason not covered by `assetBalanceEnoughV2` (e.g., an edge case in asset map key handling under `AllowSameTokenName` semantics), the debit silently does not occur.
3. `addAssetAmountV2` for the counter-asset still executes and the exchange pool is updated, and `ret.setStatus(fee, code.SUCESS)` is set — the transaction is committed as successful with an unbacked credit and no debit, corrupting the account's/exchange's token balances. [3](#0-2)
