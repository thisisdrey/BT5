### Title
Multisig authorization checks bind to a mutable `permission_id` reference, not the signed `Permission` configuration - ([File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java])

### Summary
TRON's multisig transactions commit only to an integer `permission_id` inside the signed `raw` transaction data, not to the actual `Permission` (its `threshold`, `keys`, and `operations` bitmap) that co-signers intended to authorize under. The real `Permission` object is looked up fresh from the `AccountStore` at validation/execution time. Because `AccountPermissionUpdateContract` lets the account owner freely rewrite any permission's keys/threshold/operations while keeping the same `permission_id`, previously collected ECDSA signatures on a raw transaction remain "valid" but get evaluated against whatever permission definition exists at broadcast/apply time — not the one signers believed they were agreeing to. This is the same bug class as the Atlas report: an identifier (`DAppControl` address / `permission_id`) is committed to the hash, but the mutable configuration behind that identifier (`CallConfig` / `Permission.threshold|keys|operations`) is not.

### Finding Description
`TransactionCapsule.validateSignature` resolves the authorizing `Permission` dynamically by `permissionId` from the current account state, then checks weight/operations against it: [1](#0-0) 

The signature itself is computed purely over the transaction's raw-data hash (`getTransactionId()`), independent of the `Permission` content: [2](#0-1) 

`checkWeight` and `checkPermissionOperations` both operate on whatever `Permission` object is passed in — they have no way to verify it matches what the signer originally saw: [3](#0-2) [4](#0-3) 

Critically, `AccountPermissionUpdateActuator.execute` lets the account owner overwrite the owner/witness/active `Permission` definitions (keys, weights, threshold, operations bitmap) at any time, while `permission_id` values for actives are reassigned sequentially and typically stay stable (e.g. the first active permission keeps id `2`): [5](#0-4)  Validation of the *new* permission's own shape (`checkPermission`) only constrains keys/threshold/operations bit consistency — it has no dependency on outstanding pre-signed transactions: [6](#0-5) 

As a result, exactly like the Atlas finding, the security-relevant "configuration" (`CallConfig` ↔ `Permission.threshold/keys/operations`) that a co-signer relies on when producing a signature is not part of what gets hashed and signed — only the stable `permission_id` reference is. `Wallet.broadcastTransaction`/`getTransactionApprovedList` and the actuator's `TransactionUtil.getTransactionSignWeight` path all re-fetch the *live* permission object the same way, confirming this is the general on-chain execution behavior, not just a display quirk: [7](#0-6) 

### Impact Explanation
In multi-party custody scenarios (exchanges, DAOs, shared treasuries) using TRON's active-permission multisig, co-signers sign a raw transaction expecting it to be authorized under a specific `Permission` (specific key set, threshold, and allowed `ContractType` operations bitmap) that was in effect at signing time. If the account owner updates that same `permission_id`'s definition (lowering the threshold, changing the key set, or widening the `operations` bitmap) before the transaction is broadcast or included in a block, the already-collected signatures — which never depended on the permission's content — are checked against the new configuration instead. This can let a transaction execute with fewer/different authorized signers than co-signers believed necessary, or let a transaction that should have been scoped to a narrow set of contract types (e.g., only `TransferContract`) suddenly qualify under a widened operations bitmap for other sensitive contract types (e.g., `WithdrawBalanceContract`, `FreezeBalanceV2Contract`), resulting in unauthorized account operations that bypass the multisig protection the co-signers thought they were relying on.

### Likelihood Explanation
Exploitation requires the account owner (or whoever currently controls the owner permission) to submit an `AccountPermissionUpdateContract` for the same `permission_id` between the time co-signers produce their signatures off-chain and the time the pre-signed transaction is actually broadcast/applied. This is a realistic window in custodial/exchange multisig workflows where withdrawal batches are pre-signed and queued, and permission updates (rotating keys, adjusting thresholds) are a normal, unprivileged-from-the-protocol's-perspective operation reachable by any account owner via a standard signed transaction — no special node or SR privilege is needed.

### Recommendation
Bind the signed transaction to a snapshot of the authorizing permission's security-relevant fields (e.g., include a hash or version/generation counter of `Permission.threshold`, `keys`, and `operations` in the signed payload, or increment a per-permission version number on every `AccountPermissionUpdateContract` and require transactions to reference the version they were signed against) so that `TransactionCapsule.validateSignature`/`checkWeight`/`checkPermissionOperations` can reject a transaction whose signatures were collected under a since-changed permission configuration, analogous to including the expected `CallConfig` in the Atlas structs.

### Proof of Concept
1. Account `A` sets active permission `id=2` with keys `[K1, K2, K3]`, each weight 1, `threshold=2`, `operations` bitmap allowing only `TransferContract`.
2. A withdrawal-processing service collects signatures from `K1` and `K2` on a `TransferContract` transaction under `permission_id=2` (satisfies threshold 2), queued but not yet broadcast.
3. The account owner submits an `AccountPermissionUpdateContract` (`AccountPermissionUpdateActuator.execute`) that redefines permission `id=2` to `keys=[K1]`, `threshold=1`, and an `operations` bitmap that also allows `WithdrawBalanceContract`/other sensitive types.
4. The originally collected `K1`+`K2` signatures are still bytewise valid (they sign the immutable raw-data hash), and when the queued transaction is finally broadcast, `TransactionCapsule.validateSignature` re-fetches the *new* permission `id=2` and evaluates the old signatures against it — satisfying the new (weaker or differently-scoped) requirements even though co-signer `K2` never agreed to authorize anything under that new configuration.

  private boolean checkPermission(Permission permission) throws ContractValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (permission.getKeysCount() > dynamicStore.getTotalSignNum()) {
      throw new ContractValidateException("number of keys in permission should not be greater "
          + "than " + dynamicStore.getTotalSignNum());
    }
    if (permission.getKeysCount() == 0) {
      throw new ContractValidateException("key's count should be greater than 0");
    }
    if (permission.getType() == PermissionType.Witness && permission.getKeysCount() != 1) {
      throw new ContractValidateException("Witness permission's key count should be 1");
    }
    if (permission.getThreshold() <= 0) {
      throw new ContractValidateException("permission's threshold should be greater than 0");
    }
    String name = permission.getPermissionName();
    if (!StringUtils.isEmpty(name) && name.length() > 32) {
      throw new ContractValidateException("permission's name is too long");
    }
    //check owner name ?
    if (permission.getParentId() != 0) {
      throw new ContractValidateException("permission's parent should be owner");
    }

    long weightSum = 0;
    List<ByteString> addressList = permission.getKeysList()
        .stream()
        .map(x -> x.getAddress())
        .distinct()
        .collect(toList());
    if (addressList.size() != permission.getKeysList().size()) {
      throw new ContractValidateException(
          "address should be distinct in permission " + permission.getType());
    }
    for (Key key : permission.getKeysList()) {
      if (!DecodeUtil.addressValid(key.getAddress().toByteArray())) {
        throw new ContractValidateException("key is not a validate address");
      }
      if (key.getWeight() <= 0) {
        throw new ContractValidateException("key's weight should be greater than 0");
      }
      try {
        weightSum = addExact(weightSum, key.getWeight());
      } catch (ArithmeticException e) {
        throw new ContractValidateException(e.getMessage());
      }
    }
    if (weightSum < permission.getThreshold()) {
      throw new ContractValidateException(
          "sum of all key's weight should not be less than threshold in permission " + permission
              .getType());
    }

    ByteString operations = permission.getOperations();
    if (permission.getType() != PermissionType.Active) {
      if (!operations.isEmpty()) {
        throw new ContractValidateException(
            permission.getType() + " permission needn't operations");
      }
      return true;
    }
    //check operations
    if (operations.isEmpty() || operations.size() != 32) {
      throw new ContractValidateException("operations size must 32");
    }

    byte[] types1 = dynamicStore.getAvailableContractType();
    for (int i = 0; i < 256; i++) {
      boolean b = (operations.byteAt(i / 8) & (1 << (i % 8))) != 0;
      boolean t = ((types1[(i / 8)] & 0xff) & (1 << (i % 8))) != 0;
      if (b && !t) {
        throw new ContractValidateException(i + " isn't a validate ContractType");
      }
    }
    return true;
  }
