## Confirmed: negative-control claim is **false** — the delayed/buffered queue delivery path is not immune

### Title
`remove_account` fails to purge account-scoped survivor rows (`ReceivedData`/`PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt`), and this bug is reachable through the delayed-receipt and outgoing-receipt-buffer delivery paths, not just direct incoming receipts - (File: `core/store/src/utils/mod.rs::remove_account`)

### Summary
`TrieKey::DelayedReceipt{index}` and `TrieKey::BufferedReceipt{index, receiving_shard}` are confirmed to be non-account-scoped (`get_account_id` returns `None` for both), so the FIFO queue position of a receipt is unaffected by account deletion. However, once such a receipt is popped from either queue, its *delivery* is dispatched through the exact same `process_receipt`/`process_action_receipt` code used for ordinary incoming/local receipts, which reads and writes the account-scoped `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, and `PostponedReceipt` rows keyed by `receiver_id`. `remove_account` never clears these rows, so they survive account deletion and are consulted again once the account is recreated - meaning the delayed/buffered queues do **not** serve as a negative control; they are simply another entry point into the same vulnerable, receiver-keyed state.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData` for the deleted account: [1](#0-0) 

It never touches `TrieKey::ReceivedData`, `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId`, even though `TrieKey::get_account_id` reports all of these as account-scoped: [2](#0-1) 

By contrast, `TrieKey::DelayedReceiptIndices`/`DelayedReceipt` and `TrieKey::BufferedReceiptIndices`/`BufferedReceipt` correctly return `None` from `get_account_id`, confirmed both by the enum match and by the dedicated test: [3](#0-2) [4](#0-3) 

So the queue *slot* of a receipt addressed to a deleted-and-recreated account A is indeed untouched by `remove_account` - this part of the scoping boundary is correct.

The critical point is what happens on **delivery**. `DelayedReceiptQueue::pop`/`OutgoingReceiptBuffer::pop` return a plain `Receipt`, which is fed into the same dispatcher used for every other receipt kind: [5](#0-4) [6](#0-5) 

`process_receipt`/`process_action_receipt` compute `account_id = receipt.receiver_id()` and, regardless of whether the receipt came from the delayed queue, the outgoing buffer, or a fresh incoming receipt, they check `has_received_data` and read/write `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, `TrieKey::PostponedReceipt` keyed by that `account_id`: [7](#0-6) [8](#0-7) 

These are exactly the survivor rows `remove_account` leaves behind. Consequently:
1. An attacker's contract creates an action receipt R1 to their own account A carrying `input_data_ids=[d1]`, causing `PostponedReceiptId{A,d1}→R1`, `PendingDataCount{A,R1}=1`, and `PostponedReceipt{A,R1}=R1` to be written (`lib.rs:1608-1655`).
2. Before `d1` is delivered, the attacker deletes A (`action_delete_account` → `remove_account`), which leaves those three rows (and any stale `ReceivedData`) intact, then recreates A with a `CreateAccount` action.
3. The eventual `Data` receipt satisfying `d1` - or, in the delayed/buffered-queue variant, a *new*, unrelated action receipt addressed to A that happens to declare `d1` as one of its own `input_data_ids` - is processed through the identical `process_receipt` path whether it arrives directly, via the delayed queue, or via the outgoing receipt buffer of another shard.
4. Because `has_received_data`/`PostponedReceiptId` lookups are keyed only by `(account_id, data_id)`/`(account_id, receipt_id)` with no epoch/incarnation tag, the stale rows are consulted as if they still belonged to the current incarnation of A, either short-circuiting `pending_data_count` to zero prematurely or resurrecting/executing the old postponed receipt `R1` against the new account.

This confirms that the delayed-receipt and outgoing-buffer paths are **not** a negative control: the queue-key non-account-scoping only protects the FIFO position, not the delivery-time state lookups, which are shared, unmodified code with the vulnerable direct-incoming path.

### Impact Explanation
This extends the scope of the underlying `remove_account` survivor-row bug from "postponed/yield receiver-keyed rows only" to "any receipt delivery path, including the congestion-control delayed and outgoing-buffer queues." The concrete impact is authorization/determinism violation: actions intended for a prior incarnation of an account (with its own access keys/contract) can execute against, or prematurely release execution for, the recreated account, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Reachable entirely with unprivileged, ordinary transactions: an account controls the timing of its own postponed cross-contract calls, its own deletion, and its own recreation, and can also arrange for chunk congestion to push a receipt through the delayed queue or trigger cross-shard forwarding to exercise the outgoing buffer. No validator, node-operator, or privileged access is required - only careful sequencing of the attacker's own transactions.

### Recommendation
Extend `remove_account` (`core/store/src/utils/mod.rs`) to also iterate and delete all `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows scoped to the deleted `account_id`, mirroring the access-key/contract-data cleanup already performed, so that no account-scoped survivor state persists across a delete/recreate cycle regardless of which receipt path (direct, delayed, or buffered) eventually reads it.

### Proof of Concept
Integration-test plan (runtime apply-loop style, similar to `runtime/runtime/src/tests/apply.rs`):
1. Create account A; from another account, send an action receipt R1 to A with `input_data_ids=[d1]` (unmet), causing `PostponedReceiptId{A,d1}`, `PendingDataCount{A,R1}=1`, `PostponedReceipt{A,R1}` to be set.
2. In a subsequent chunk, delete account A (`DeleteAccountAction`) and immediately recreate it (`CreateAccountAction`) with a different set of access keys/contract.
3. Fill the chunk's gas/compute limit so that a *new*, benign action receipt R2 addressed to A gets queued via `DelayedReceiptQueue::push` (or, for the buffered variant, force cross-shard congestion so R2 lands in `ShardsOutgoingReceiptBuffer`).
4. Deliver the `Data` receipt for `d1`. Assert that `PostponedReceiptId{A,d1}`, `PendingDataCount{A,R1}`, and `PostponedReceipt{A,R1}` are still present pre-delivery (confirming survivor rows), and that R1 executes against the *new* account A's state/access keys once `d1` arrives - demonstrating cross-incarnation execution.
5. Additionally process R2 out of the delayed/buffered queue and confirm `process_action_receipt` consults the same `TrieKey::PendingDataCount`/`PostponedReceiptId` namespace for A, proving the queue path funnels into the identical vulnerable lookup code as step 4.
