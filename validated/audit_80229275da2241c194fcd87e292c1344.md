Based on my research, I found a strong analog to the reported "signature replay across chains/contracts" bug class in Gitaly's commit-signing/verification logic.

### Title
System-signed commit signatures lack repository binding, enabling cross-repository signature replay - (File: internal/gitaly/service/commit/get_commit_signatures.go)

### Summary
Gitaly can sign commits with a server-wide GPG/SSH key (`cfg.Git.SigningKey`) to mark them as authored by Gitaly/GitLab itself (`SIGNER_SYSTEM`), and it verifies signatures purely by checking whether the signature is valid over the commit payload — with no binding to the repository, storage, or any other domain-separating identifier. This mirrors the reported bug class: a signature that authenticates a message but omits a "chain id"/"contract address" equivalent can be replayed wherever the same signing code/key applies.

### Finding Description
`GetCommitSignatures` loads the server's global signing keys and validates a commit's signature purely against its `SignatureData.Payload`: [1](#0-0) 

The verification is delegated to `SigningKeys.Verify`, which simply checks the raw signature against the raw signed bytes with no additional context: [2](#0-1) 

Because:
1. The signing key (`cfg.Git.SigningKey`) is a single, server-wide configuration value, not scoped per repository, and
2. The verified payload is only the standard Git commit content (tree, parent, author, committer, message) with no repository identifier, storage name, or Gitaly instance identity baked in,

any commit object that is byte-identical to one previously signed by Gitaly (`SIGNER_SYSTEM`) will verify as `SIGNER_SYSTEM` in *any* other repository served by the same Gitaly/GitLab instance (or any instance sharing the same signing key, e.g. in a fleet configuration). This is the direct analog of the `Airdrop.sol` issue: the "signature" (Gitaly's system signature) doesn't bind to the "contract" (specific repository), so it can be replayed across different repositories with the same underlying commit content.

An attacker who has read access to a repository containing a Gitaly-signed commit (e.g. a squash/merge commit auto-generated when GitLab performs commit signing on the user's behalf) can extract the raw commit object and its signature via `GetCommitSignatures`, then construct/push an object graph with an identical commit (and requisite tree/parent objects) into a different repository they control. Querying `GetCommitSignatures` on that repository will then report `Signer: SIGNER_SYSTEM` for a commit the attacker fabricated by replay, not one Gitaly actually signed in that repository's context.

### Impact Explanation
This is a medium-severity trust/spoofing issue: `Signer: SIGNER_SYSTEM` is surfaced to GitLab Rails and used to indicate that a commit was verified as signed by the platform itself (analogous to a "Verified" badge). Replaying a valid Gitaly system signature into an unrelated repository lets a user misrepresent commit provenance, misleading reviewers/auditors relying on the signed/verified status — without ever compromising the private signing key itself. It doesn't grant an attacker arbitrary forged content (the payload must be replayed verbatim, not freely chosen), but it does allow misattribution of authenticity across repository boundaries, the same limited-but-real impact called out in the original report.

### Likelihood Explanation
The likelihood is constrained by the need for a byte-identical commit object (including its full ancestry chain of tree/blob objects) to be reproducible in the victim repository, and by the requirement that a Gitaly system-signed commit exist somewhere accessible to the attacker. Given that GitLab does sign auto-generated commits (squashes, web-UI-created commits, etc.) with `cfg.Git.SigningKey`, and `GetCommitSignatures` is an unprivileged, read-only RPC exposing the raw payload/signature pair, an ordinary user with read access to one repo and write/push access to another can realistically construct this replay via low-level Git plumbing and a crafted push.

### Recommendation
Bind the domain to the signature the same way the report recommends binding `chainid`/`address(this)`: include a repository-identifying value (e.g., the repository's relative path or Gitaly storage name) as part of what's verified when determining `SIGNER_SYSTEM`, or otherwise record/verify provenance (e.g., store which repository the signing operation was performed for and compare it against the requested repository) rather than relying solely on cryptographic validity of the Git-native signature payload.

### Proof of Concept
1. As a user with read access to Repo A, call `GetCommitSignatures` for a commit known to be Gitaly-system-signed (e.g., a GitLab-generated squash commit) and capture `Signature` and `SignedText`. [3](#0-2) 
2. Reconstruct the exact same commit object (same tree OID, parent OID(s), author/committer lines, message) using `git hash-object -t commit --stdin --literally` against objects present (or supplied) in Repo B, which the attacker controls.
3. Push/store this identical commit object into Repo B (e.g., via a crafted `git push` supplying the necessary object graph, or via internal RPCs that accept raw objects).
4. Call `GetCommitSignatures` against Repo B for the new commit ID; because verification (`SigningKeys.Verify`) only checks the signature against the payload with no repository binding, the response will report `Signer: SIGNER_SYSTEM`, falsely indicating that this commit was produced/signed by Gitaly in the context of Repo B.

func sendResponse(
	signature []byte,
	commit *catfile.Commit,
	signer gitalypb.GetCommitSignaturesResponse_Signer,
	stream gitalypb.CommitService_GetCommitSignaturesServer,
) error {
	if len(signature) <= 0 {
		return nil
	}

	err := stream.Send(&gitalypb.GetCommitSignaturesResponse{
		CommitId:  commit.Id,
		Signature: signature,
		Signer:    signer,
		Author:    commit.Author,
		Committer: commit.Committer,
	})
	if err != nil {
		return err
	}

	streamWriter := streamio.NewWriter(func(p []byte) error {
		return stream.Send(&gitalypb.GetCommitSignaturesResponse{SignedText: p})
	})

	msgReader := bytes.NewReader(commit.SignatureData.Payload)

	_, err = io.Copy(streamWriter, msgReader)
	if err != nil {
		return fmt.Errorf("failed to send response: %w", err)
	}

	return nil
}

// Verify iterates over all signing keys and returns nil if any
// verification was successful. Otherwise, the last error is returned.
// Note: when Golang 1.19 is no longer supported, can be refactored using errors.Join
func (s *SigningKeys) Verify(signature, signedText []byte) error {
	var err error
	for _, signingKey := range append([]SigningKey{s.primaryKey}, s.secondaryKeys...) {
		err = signingKey.Verify(signature, signedText)
		if err == nil {
			return nil
		}
	}
	return err
}
