### Verdict
No vulnerability found for this question.

### Reasoning

The premise of the question — that `internal_apply_deltas` mutations made before `finalize()` runs could survive on persistent storage even though `finalize()` later returns `Err(InvariantViolated::...)` — does not hold for the actual execution path used by `execute_intents`.

**1. `execute_intents` does not use `CachedState` at all.**

`execute_intents` constructs the engine directly against the live contract object: [1](#0-0) 

`Engine::new(self, ExecuteInspector::default())` passes `self: &mut Contract` (the actual contract struct held in near-sdk's in-memory representation for the duration of this host function call), not a `CachedState<W>` wrapper. `CachedState` (in `contracts/defuse/core/src/engine/state/cached.rs`) is only used by `simulate_intents`, which is a `view` call and therefore can never write to storage in the first place: [2](#0-1) 

So the specific "CachedState in-memory delta buffer only committed later" mechanism the question describes is not on the path that can actually persist state — it's exclusively used in the read-only simulation path.

**2. In `execute_intents`, `Deltas<S>::internal_add_balance`/`internal_sub_balance` mutate `self.state` (the real `Contract`) synchronously, in the same in-memory NEAR contract object that near-sdk will only serialize back to storage at the very end of the host function call, and only if the call returns without panicking.** [3](#0-2) 

`Engine::execute_signed_intents` runs every signed payload's intents, accumulating both real balance mutations (via `Deltas` delegating into `S: State`, i.e. `Contract`) and `TransferMatcher` deltas, then calls `self.finalize()`: [4](#0-3) [5](#0-4) 

**3. If `finalize()` returns `Err(InvariantViolated::...)`, `execute_intents` calls `.unwrap_or_else(|e| e.panic())`.** [6](#0-5) 

`panic()` invokes NEAR's abort mechanism (`env::panic_str`/equivalent), which terminates the host function call for that receipt. Per the NEAR runtime's transactional execution model (guaranteed by the platform, not by this repo's code), a panicking contract call causes the *entire* transaction/receipt to be rejected: no state changes made during that call — regardless of whether they were mutations to `self.token_balances`, `self.accounts`, or any other field of the in-memory `Contract` struct — are ever written back to persistent storage. The `#[near]`/contract-state serialization step that flushes the in-memory contract struct to storage only executes on a normal (non-panicking) return path. This is standard, unconditional NEAR contract semantics: a panic anywhere in a function call rolls back the whole call atomically, there is no partial-commit mechanism, and no code exists in this repo (nor could exist) to intentionally persist a partial write before a later panic.

**4. Consequence for the attacker's scenario.**

An attacker can indeed construct a batch of `TokenDiff` intents across sock-puppet signers such that per-token unmatched deltas trip `InvariantViolated::UnmatchedDeltas` (line 277-280) or `Overflow` (line 274) in `TransferMatcher::finalize`. But regardless of whether this happens on the first intent or the Nth, the *entire* `execute_intents` call panics via `e.panic()`, and the NEAR runtime discards every state mutation performed during that call, including all the `internal_apply_deltas`/`internal_add_balance`/`internal_sub_balance` writes that happened earlier in the same batch. There is no window where a partial write becomes "irreversible" before `finalize()` runs, because nothing is written to real persistent storage until the call returns successfully — the in-memory `Contract` object mutated during the call is not "real storage" until the runtime commits it at the end, and a panic prevents that commit entirely.

The residual-cancellation attempt (crafting N>2 legs so `deltas.is_empty()` becomes true) is the *only* way to make `finalize()` return `Ok(transfers)`, and in that case the sum of deltas is by construction zero — which is exactly the invariant `TransferMatcher::finalize` is designed to enforce via `TokenTransferMatcher::finalize_into` matching deposits against withdrawals. There's no divergence between what's asserted and what's persisted.

### Conclusion

The atomic-revert-on-panic property of the NEAR runtime (not something this repo needs to implement, since it's inherent in how contract function calls execute) is exactly the guard that prevents the divergence hypothesized in the question. `finalize()`'s `InvariantViolated` error path, when it results in `e.panic()` in `execute_intents`, always aborts before any mutation is persisted; `simulate_intents`, which does use a mutation buffer (`CachedState`) that could theoretically diverge, is a view call and cannot write to storage regardless of its outcome. No path exists for an unprivileged attacker to leave partial internal balance mutations committed to real `Contract` storage while `finalize()` reports failure.
