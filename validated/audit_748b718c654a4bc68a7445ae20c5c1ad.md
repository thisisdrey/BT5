### Title
Missing bounds check in `PrecompiledContracts.extractBytes32Array` causes OOB array read reachable from TVM precompiled contract calls - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array(DataWord[] words, int offset)` reads a length word `words[offset]` and then loops reading `words[offset + i + 1]` for `i` in `[0, len)`, with **no validation** that `offset` or `offset + len` is within the bounds of the `words` array. [1](#0-0) 

This is exactly the same bug class as the reported BACnet issue: a length/offset value is decoded from attacker-controlled input and then used directly to index a buffer without checking it against the buffer's actual size, producing an out-of-bounds read.

### Finding Description
Two sibling helper functions in the same file, `extractBytesArray` and `extractSigArray`, both explicitly guard against the offset exceeding the array bounds before indexing: [2](#0-1) [3](#0-2) 

`extractBytes32Array`, however, omits this check entirely: [1](#0-0) 

`words` is derived from ABI-decoded precompile call `data`, whose contents (including the "length" word at `offset`) are fully controlled by the caller of the precompiled contract (e.g., the `BatchValidateSign` / `ValidateMultiSign` precompiles registered at addresses `0x9`/`0xa`, reachable via `VMConfig.allowTvmSolidity059()`). By supplying a crafted `len` value at `words[offset]` (via `intValueSafe()`, which can return a large positive value), the loop indexes `words[offset + i + 1]` past the end of the array, throwing an `ArrayIndexOutOfBoundsException`.

### Impact Explanation
Any account that broadcasts a transaction invoking a smart contract that calls the `BatchValidateSign`/`ValidateMultiSign` precompile (addresses `0x...09` / `0x...0a`) with crafted call data can trigger this unhandled runtime exception during TVM execution. Depending on how deeply this exception propagates and whether it is caught by a generic exception handler higher in the `Program`/`Runtime` execution stack, this results at minimum in unpredictable transaction execution behavior (uncontrolled abort) triggered from untrusted, attacker-supplied contract input — the same "index blindly trusts attacker-controlled length" root cause as the BACnet advisory. Because only reads occur (no memory corruption), this maps to a denial-of-service class issue rather than RCE, consistent with the original CVE's own characterization.

### Likelihood Explanation
Likelihood is high: `extractBytes32Array` is invoked with attacker-fully-controlled precompile call data, and the missing bounds check contrasts directly with the equivalent guarded functions (`extractBytesArray`, `extractSigArray`) in the same file, showing the safe pattern exists elsewhere but was omitted here. No special privileges are required — a normal account can call any contract that internally calls the affected precompile with malicious static call data.

### Recommendation
Add the same defensive bounds check used in `extractBytesArray`/`extractSigArray` to `extractBytes32Array`: validate `offset >= 0 && offset <= words.length - 1` before reading `words[offset]`, and validate that `offset + len` does not exceed `words.length` before entering the loop, returning an empty/error result (or explicitly reverting via the precompile's returned `Pair.of(false, ...)`) instead of allowing an unchecked `ArrayIndexOutOfBoundsException` to propagate.

### Proof of Concept
1. Deploy or call an existing contract that invokes the `BatchValidateSign` or `ValidateMultiSign` precompiled contract (address `0x...09` / `0x...0a`).
2. Craft the call `data` such that at the byte offset consumed as the "array offset" parameter passed into `extractBytes32Array`, the decoded `DataWord` at that position (`words[offset].intValueSafe()`) is a large value (e.g., close to `Integer.MAX_VALUE` or simply larger than `words.length - offset - 1`).
3. Submit the transaction; during precompile execution, the loop `bytes32Array[i] = words[offset + i + 1].getData();` in `extractBytes32Array` [4](#0-3)  indexes beyond `words.length`, throwing `ArrayIndexOutOfBoundsException` instead of gracefully failing like the sibling `extractBytesArray`/`extractSigArray` functions do.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
