Based on my investigation, I found a genuine analog to the Django `FilteredRelation` bug class in the ETH-implicit wallet contract, where user-controlled data is interpolated into a JSON string via `format!` without escaping — the same "unescaped identifier/value interpolated into a structured mini-language" root cause as the SQLi report.

### Title
Unescaped memo bytes interpolated into `ft_transfer` JSON args in Wallet Contract ERC-20 emulation - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/eth_emulation.rs])

### Summary
The eth-implicit Wallet Contract's ERC-20 `transfer` emulation path builds the JSON `args` for the downstream `ft_transfer` cross-contract call using raw string interpolation (`format!`) rather than a JSON serializer, mirroring the Django class of bug where a user-controlled value is spliced into a structured query/document without escaping.

### Finding Description
`try_emulation` in [1](#0-0)  constructs the `ft_transfer` call arguments by directly formatting values into a JSON string template:
```
let memo = if tx.data.len() > 68 {
    Some(format!(r#""0x{}""#, hex::encode(&tx.data[68..])))
} else { None };
let args = format!(
    r#"{{"receiver_id": "{}", "amount": "{}", "memo": {}}}"#,
    receiver_id.as_str(), value, memo.as_deref().unwrap_or("null"),
);
```
`memo` is derived from arbitrary attacker-controlled bytes in the Ethereum-style transaction's calldata (`tx.data[68..]`), and `receiver_id` is a Near account ID derived from an ABI-decoded 20-byte `Address` plus the current account's suffix. In the current implementation the memo bytes are hex-encoded first (limiting the character set to `[0-9a-f]`), and `receiver_id`/`value` are similarly constrained (hex address + validated account-id suffix, decimal `u128`). Because of this, no raw quote or brace characters can currently reach the JSON template, so this specific call site is not exploitable today — but it is structurally the same anti-pattern as the reported Django bug: constructing a structured payload (JSON args to be parsed by the receiving `ft_transfer` contract) via string formatting instead of a proper serializer, relying entirely on incidental encoding of individual fields to prevent injection. If any developer later adds a field for which the "safety by construction" property doesn't hold (e.g., forwarding a raw string from calldata without hex-encoding, or increasing account-id charset, or reusing this pattern for a new emulated method with a string parameter), this exploitable channel would allow an attacker to inject additional JSON keys (e.g., override `receiver_id` or add fields interpreted by the token contract) executing on behalf of the wallet's account.

### Impact Explanation
As implemented today, the fields are safety-constrained (hex-encoded memo, validated `receiver_id`/decimal `amount`), so I could not construct a working PoC that breaks out of the JSON structure with the current call sites. I am not able to confirm concrete, currently-reachable theft or fund loss from this exact code path — the impact is contingent on future or adjacent uses of this format-string pattern rather than a proven exploit against the current logic.

### Likelihood Explanation
Low as it stands, because the interpolated values are currently restricted to safe character sets by construction (hex encoding, decimal formatting, account-id validation). This is a code-quality/defense-in-depth concern rather than a demonstrated exploitable vulnerability in the current build.

### Recommendation
Replace the manual `format!(r#"{{...}}"#, ...)` JSON construction in `try_emulation` (and the analogous pattern in `internal.rs`/`lib.rs` for `rlp_execute` args, and in `wallet_contract.rs` test helper) with a proper JSON serializer (e.g., `serde_json::json!` / `serde_json::to_vec`) so that any future change to what data is embedded (memo contents, method names, string fields) cannot reintroduce a JSON-injection primitive analogous to the reported SQL injection class.

### Proof of Concept
Not reproducible against the current code: I traced `tx.data[68..]` (memo) through `hex::encode` before interpolation, and `receiver_id`/`amount` through hex-address and `AccountId`/decimal formatting respectively, all of which exclude the `"` and `{`/`}` characters needed to break out of the JSON template. I could not construct calldata that survives these encodings to inject additional JSON keys, so I cannot provide a working exploit; this is reported as a structural analog/hardening recommendation rather than a proven live vulnerability.
