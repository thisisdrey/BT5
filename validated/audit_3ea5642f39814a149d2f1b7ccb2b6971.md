### Title
Fee-on-transfer / non-conforming NEP-141 tokens cause silent value loss in `ft_resolve_withdraw` (and NEP-245 equivalent) - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`ft_resolve_withdraw` determines how much of a withdrawal was "used" (and therefore how much to refund back to the user's internal balance) purely from the *promise outcome* of the outbound `ft_transfer`/`ft_transfer_call` call, not from any measurement of what the receiver actually received. For a non-call `ft_transfer`, any successful promise (`promise_result_checked_void(0).is_ok()`) is treated as proof that the *full* requested `amount.0` was delivered, and zero refund is issued. If the underlying NEP-141 token implements a transfer fee or deflationary/rebasing mechanic (which is exactly the bug class in the referenced report), the receiver gets less than `amount.0`, but Defuse has already burned the full `amount.0` from the withdrawing user's internal ledger and issues no refund, permanently losing the fee delta with no accounting trail. The analogous NEP-245 path (`mt_resolve_withdraw`) has the same assumption.

### Finding Description
`internal_ft_withdraw` first debits the owner's internal balance by the full withdrawal `amount` via `self.withdraw(...)` [1](#0-0) , then fires the outbound `ft_transfer`/`ft_transfer_call` in `do_ft_withdraw` [2](#0-1) , and finally calls `ft_resolve_withdraw` to decide what portion was "used" versus what should be refunded back to the sender's internal balance:

```
} else {
    // `ft_transfer` returns empty result on success
    if promise_result_checked_void(0).is_ok() {
        amount.0
    } else {
        0
    }
};
``` [3](#0-2) 

This treats "the promise did not fail" as equivalent to "the full `amount.0` reached `receiver_id`." NEP-141's `ft_transfer` returns void on success by protocol design — it carries no information about how much value actually landed in the receiver's balance. A token contract that deducts a fee (or applies deflation/rebasing) before crediting the receiver can legitimately return success while delivering less than `amount.0`. In that case:
- Internal ledger: `_balances`-equivalent (`owner.token_balances`) was debited by the full `amount.0` in `Contract::withdraw` [4](#0-3) .
- External reality: receiver got `amount.0 - fee`.
- Refund logic: `refund = amount.0.saturating_sub(used)` computes `0` because `used = amount.0` [5](#0-4) .

The equality that should hold — *value debited == value delivered + value refunded* — is broken: `amount.0 != (amount.0 - fee) + 0`. The missing `fee` amount is neither delivered to the receiver, refunded to the sender, nor accounted for in `total_supplies`, causing a permanent, silent discrepancy between Defuse's internal accounting and the actual token balances it custodies.

The identical pattern exists for NEP-245 batch withdrawals in `mt_resolve_withdraw`, where the non-call branch also assumes success implies the requested `amounts` were fully delivered [6](#0-5) .

The corresponding deposit-side (`ft_on_transfer`) has a symmetric issue: the deposited amount credited to the internal ledger is taken directly from the caller-supplied `amount` parameter of `ft_on_transfer`, not from any observed balance delta [7](#0-6) , but since NEP-141 deposits are a single atomic call rather than a two-step pull (unlike ERC-20's `approve`/`transferFrom`), the withdraw-side resolver mismatch is the clearer break of the conservation invariant.

### Impact Explanation
This falls under the Critical category "a mismatched resolver refund": Defuse's ledger is debited for the full requested amount, while the actual value delivered to the receiver can be less for tokens with transfer fees/deflationary mechanics, and the difference is never refunded or otherwise accounted for — a silent, permanent loss of custodied value with no attacker interaction required beyond depositing/withdrawing such a token.

### Likelihood Explanation
Likelihood depends entirely on which NEP-141/NEP-245 tokens are listed/whitelisted for deposit into Defuse; if any listed token can apply a fee or deflationary adjustment on transfer (even a future upgrade to an existing token), every withdrawal of that token silently leaks the fee amount from the protocol's accounting.

### Recommendation
Do not infer "amount delivered" from promise success alone for `ft_transfer`/`mt_batch_transfer` (which return no information). Either: (1) restrict withdrawals to tokens verified not to apply any fee/rebase on transfer as part of listing policy, or (2) measure `ft_balance_of`/`mt_balance_of` of `receiver_id` before and after the transfer promise resolves and use the observed delta as `used`, refunding the sender for any shortfall rather than assuming `used == amount.0` whenever the promise succeeds.

### Proof of Concept
1. List a NEP-141 token `FEE_FT` on Defuse that deducts, e.g., a 1% fee on `ft_transfer` (kept by the token contract or a designated fee collector), while still returning void/success as required by NEP-141.
2. User deposits `1000 FEE_FT` into Defuse; internal balance becomes `1000`.
3. User calls `ft_withdraw` for `1000 FEE_FT` with `msg = None` (so the non-call branch of `ft_resolve_withdraw` is used) — `Contract::withdraw` debits the user's internal balance by `1000` immediately [8](#0-7) .
4. `do_ft_withdraw` issues `ft_transfer(receiver_id, 1000)` on `FEE_FT`; the token transfers `990` to `receiver_id` (keeping `10` as fee) and returns successfully (void).
5. `ft_resolve_withdraw` sees `promise_result_checked_void(0).is_ok() == true`, sets `used = 1000`, computes `refund = 0` [9](#0-8) .
6. Result: Defuse's internal ledger and total supply were reduced by `1000`, but the receiver only got `990`, and `10 FEE_FT` is unaccounted for — permanently lost from the protocol's internal bookkeeping with no refund and no record.

    pub fn do_ft_withdraw(withdraw: FtWithdraw) -> Promise {
        let min_gas = withdraw.min_gas();
        let p = if let Some(storage_deposit) = withdraw.storage_deposit {
            require!(
                promise_result_checked_void(0).is_ok(),
                "near_withdraw failed",
            );

            ext_storage_management::ext(withdraw.token)
                .with_attached_deposit(storage_deposit)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .storage_deposit(Some(withdraw.receiver_id.clone()), None)
        } else {
            Promise::new(withdraw.token)
        };

        let p = ext_ft_core::ext_on(p)
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(min_gas)
            // distribute remaining gas here
            .with_unused_gas_weight(1);
        if let Some(msg) = withdraw.msg {
            p.ft_transfer_call(
                withdraw.receiver_id,
                withdraw.amount.into(),
                withdraw.memo,
                msg,
            )
        } else {
            p.ft_transfer(withdraw.receiver_id, withdraw.amount.into(), withdraw.memo)

        token_amounts: impl IntoIterator<Item = (TokenId, u128)>,

        force: bool,

        let owner = self

            .accounts
            .get_mut(owner_id)
            .ok_or_else(|| DefuseError::AccountNotFound(owner_id.to_owned()))?
            .get_mut_maybe_forced(force)
            .ok_or_else(|| DefuseError::AccountLocked(owner_id.to_owned()))?;

        let mut burn_event = MtBurnEvent {
            owner_id: Cow::Owned(owner_id.to_owned()),
            authorized_id: None,
            token_ids: Vec::new().into(),
            amounts: Vec::new().into(),
            memo: memo.map(Into::into).map(Into::into),
        };

        for (token_id, amount) in token_amounts {
            if amount == 0 {
                return Err(DefuseError::InvalidIntent);
            }

            burn_event.token_ids.to_mut().push(token_id.to_string());
            burn_event.amounts.to_mut().push(amount);

            owner
                .token_balances
                .sub(token_id.clone(), amount)
                .ok_or(DefuseError::BalanceOverflow)?;

            self.storage
                .state
                .total_supplies
                .sub(token_id, amount)
                .ok_or(DefuseError::BalanceOverflow)?;
        }
