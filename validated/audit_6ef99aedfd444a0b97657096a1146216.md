### Title
Multi-Signature Weight Double-Counting via ECDSA Signature Malleability Allows Multisig Threshold Bypass - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` TVM precompile's signature-weight accumulation loop treats each distinct raw signature byte-string as a new approval, even when it recovers to an address that has already been counted. Because ECDSA signatures are trivially malleable (flipping `s` to `n-s` yields a second, equally valid signature for the same hash from the same key, requiring no secret material), a caller holding a single valid signature from one permission key can submit both the original and its malleated twin to have that one key's weight counted twice, letting an unprivileged caller reach or exceed a multisig `threshold` that was designed to require multiple independent signers.

### Finding Description
`PrecompiledContracts.ValidateMultiSign.execute()` recovers the signer address for each supplied signature and accumulates weight per address, guarding only against exact re-use of the *same signature bytes*: [1](#0-0) 

Specifically:
- `recoveredAddr` is computed from each signature.
- `sign = merge(recoveredAddr, sign)` forms a per-signature key.
- If `recoveredAddr` was already seen but the *exact byte sequence* `sign` was not, the code does **not** `continue` — it only performs a CPU-time bookkeeping check (`MUtil.checkCPUTime()`) and then falls through to add the address's weight again via `totalWeight += weight` and re-adds it to `executedSignList`.

This means the loop only deduplicates identical signature bytes, not identical signers. ECDSA signatures are malleable: for any valid `(r, s)` signature, `(r, n-s mod n)` is also a valid signature recovering to the same address, and this transformation requires only public information (the original signature), not the private key. An attacker who legitimately possesses one valid signature from a key with `Permission` weight `W` can compute the malleated counterpart and submit both as two entries in the `signatures` array passed to the precompile. Both entries recover to the same address but are byte-distinct, so the loop counts the weight twice (`2W`) instead of once, letting `totalWeight` reach `permission.getThreshold()` with only one real approver.

This is directly reachable by any unprivileged contract caller: `ValidateMultiSign` is invoked from Solidity via `TriggerSmartContract`/constant calls, with the caller fully controlling the `signatures` array content, and is the exact "TVM opcodes, precompiles and energy metering" surface explicitly in scope.

### Impact Explanation
This is an authorization-forgery bug: on-chain contracts that use `ValidateMultiSign` to gate privileged logic (e.g., custody contracts, multisig wallets, escrow releases keyed to TRON account permissions) can be tricked into believing a 2-of-N (or M-of-N) threshold has been met when only 1 real signer actually approved. This is a direct analog of the OFBiz bug class — a caller manufactures a second "valid credential" from a single legitimate one to impersonate multiple approvers and bypass an authorization check — resulting in unauthorized approval/execution of privileged contract logic and, depending on the consuming contract, unauthorized asset movement.

### Likelihood Explanation
Exploitation requires only:
1. A `Permission` with `threshold > weight of a single key`.
2. One legitimate signature from any key in that permission over the relevant hash (attacker either owns that key or otherwise obtains one signature, e.g. from a legitimate co-signer's partial approval flow).
3. A trivial, well-known public-key-only transformation (`s -> n - s mod n`) with no cryptographic secret needed.

No special privileges, node access, or additional key compromise are required beyond having one genuine signature, making this straightforward for any dApp/contract relying on the precompile for threshold logic.

### Recommendation
In `ValidateMultiSign.execute()`, deduplicate strictly by `recoveredAddr` (not by the raw `sign` bytes): once an address has contributed weight, skip any further signature recovering to that same address, regardless of whether the byte-level signature differs. Additionally, enforce canonical (low-`s`) signature form before recovery/weight accounting to reject malleated duplicates outright.

### Proof of Concept
1. Create an on-chain account with an `Active` permission: two keys `K1`, `K2`, each weight `1`, `threshold = 2`.
2. Attacker controls `K1` only. Compute `hash = sha256(merge(address, permissionId, data))` as required by the precompile ABI.
3. Sign `hash` with `K1` to get valid signature `sig1 = (r, s)`.
4. Compute the malleated signature `sig2 = (r, n - s mod n)` — no private key needed, `n` is the public curve order.
5. Call `validateMultiSign(address, permissionId, data, [sig1, sig2])` (as exercised by the existing test harness at [2](#0-1) ).
6. Both `sig1` and `sig2` recover to `K1`'s address. The loop in `PrecompiledContracts.java` (lines 1088-1106) counts weight `1` twice, yielding `totalWeight = 2 >= threshold(2)`, returning `DataWord.ONE()` (success) despite only one real signer having participated.
