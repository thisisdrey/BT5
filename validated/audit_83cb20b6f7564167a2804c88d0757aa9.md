Based on the investigation, the strongest local analog to the Buffer Finance issue is in the `sc-hop` crate (Hand-Off Protocol), where the sender's cryptographic authorization is bound to the wrong data — mirroring the core flaw in the external report: a critical outcome-determining value is left outside the signed commitment, so it can be supplied or substituted independently of the party who is supposed to control it.

### Title
HOP submit signature does not commit to the recipient list, letting a replayed signature redirect hand-off data to attacker-chosen recipients - (File: substrate/client/hop/src/rpc.rs)

### Summary
`hop_submit` requires a `MultiSignature` from the sender, but that signature is only computed over `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp)` — it never covers the `recipients` list. [1](#0-0) 
The `recipients` field is decoded and stored independently of signature verification. [2](#0-1) [3](#0-2) 

### Finding Description
The sender's signature authorizes "this data, at this timestamp," analogous to how Buffer's `verifyMarketDirection` only authorized a trade's existence but let the outcome-critical `direction` be supplied later by the same untrusted party without being bound into an earlier commitment. In HOP, the outcome-critical value is *who receives the data* (`recipients: Vec<Bytes>` → `RecipientVec`), and it is never part of the signed payload verified in `submit`: [4](#0-3) 

Because content is deduplicated by `blake2_256(data)`, a `(data, signer, signature, submit_timestamp)` tuple is a fixed, replayable artifact once it has been observed (e.g. from a prior successful `hop_submit` call, from node logs, or from a third-party HOP-enabled collator's RPC surface — this is a public, unauthenticated JSON-RPC method, so no privileged access is needed). After the original entry is removed (either fully ack'd via `hop_ack` or expired) — both of which are normal, attacker-triggerable end states — [5](#0-4) 
the same signed tuple remains valid (the signature check only re-verifies `data`+`submit_timestamp`, and the runtime tolerance window for `submit_timestamp` is explicitly documented as "a few hours"): [6](#0-5) 

An attacker can resubmit that exact `(data, signer, signature, submit_timestamp)` with an entirely new `recipients` list of keys they control. `submit()` re-derives the same content hash, passes signature verification (since recipients aren't part of what's signed), and inserts a new pool entry whose `Recipient` set is attacker-chosen: [7](#0-6) [8](#0-7) 

This is functionally identical to the Buffer bug's root cause: a value that determines who ultimately benefits from an already-authorized action (direction → payout winner; recipients → data recipient) is decoupled from the cryptographic commitment that was supposed to fix it, allowing a party other than the original committer to unilaterally set that value after the fact.

### Impact Explanation
The sender's one-time consent (their signature) is reusable by an unrelated third party to redirect private hand-off data — which per the crate's own design is meant to reach only recipients whose ephemeral private keys the sender shared out-of-band — to attacker-controlled keys instead. Because the same `signer`/`signature`/`submit_timestamp` is also what gets carried into the on-chain promotion extrinsic (`create_promotion_extrinsic`) as "proof of consent to promote," [9](#0-8) 
an attacker-controlled resubmission with attacker recipients can subsequently be promoted on-chain under the appearance of the original sender's authorization, permanently storing content the original sender no longer controls the distribution of.

### Likelihood Explanation
`hop_submit` is a public, unauthenticated JSON-RPC method on any HOP-enabled node; exploitation only requires observing one prior valid submission (which is not confidential — it travels in cleartext RPC calls/responses) and waiting for or forcing the original entry to be removed (trivial: recipients themselves normally ack it, or it simply expires per `--hop-retention-secs`, default 24h). No validator, collator, relayer, or admin compromise is needed — only a normal unprivileged RPC caller.

### Recommendation
Include a commitment to the `recipients` list inside the signed submit payload, e.g. `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || blake2_256(recipients.encode()) || submit_timestamp)`, so the sender's signature binds both *what* is being handed off and *to whom*, preventing any party other than the original sender from altering the recipient set for a given signed submission.

### Proof of Concept
1. Alice calls `hop_submit(data, [Bob_pubkey], sig_over(hash(data)+ts), Alice_signer, ts)`. Entry is stored with `recipients = [Bob]`. [4](#0-3) 
2. Bob claims and acks the data; the pool entry is deleted once all recipients ack. [5](#0-4) 
3. Mallory, who observed Alice's original `hop_submit` RPC call/response (e.g., from node logs or another public HOP node), calls `hop_submit(data, [Mallory_pubkey], sig_over(hash(data)+ts), Alice_signer, ts)` — reusing the exact same signature bytes.
4. `submit()` re-verifies the signature purely against `blake2_256(data) || ts`, which is still valid, and inserts a new entry whose sole recipient is Mallory's key. [7](#0-6) 
5. Mallory calls `hop_claim`/`hop_ack` with her own ephemeral key and receives data that was never intended for her, under cover of Alice's unrelated authorization.

```markdown
### `hop_submit(data, recipients, signature, signer, submit_timestamp) -> SubmitResult`

Store a blob for the given list of recipients.

- `data`: raw bytes, must be ≤ `HopRuntimeApi::max_promotion_size()` (the runtime
  cap is authoritative — no separate node-side ceiling).
- `recipients`: up to **256** SCALE-encoded `MultiSigner` values (ed25519,
  sr25519, or ecdsa ephemeral public keys).
- `signature`: SCALE-encoded `MultiSignature` over
  `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
- `signer`: SCALE-encoded `MultiSigner` of the submitting account.
- `submit_timestamp`: wall-clock submit time in milliseconds since the Unix
  epoch. Bound into the signed payload; the runtime rejects promotions whose
  timestamp drifts too far from on-chain time, so the same `(data, signer,
  signature)` cannot be replayed indefinitely.
```

```rust
	fn submit(
		&self,
		data: Bytes,
		recipients: Vec<Bytes>,
		signature: Bytes,
		signer: Bytes,
		submit_timestamp: u64,
	) -> RpcResult<SubmitResult> {
		let recipient_keys: RecipientVec = recipients
			.into_iter()
			.map(|r| {
				MultiSigner::decode(&mut &r.0[..])
					.map(|signer| Recipient { signer, claimed: false })
					.map_err(|_| HopError::InvalidRecipientKey)
			})
			.collect::<Result<Vec<_>, _>>()?
			.try_into()
			.map_err(|v: Vec<Recipient>| HopError::TooManyRecipients {
				provided: v.len(),
				limit: MAX_RECIPIENTS as usize,
			})?;

		let signer =
			MultiSigner::decode(&mut &signer.0[..]).map_err(|_| HopError::InvalidSigner)?;
		let multi_sig = MultiSignature::decode(&mut &signature.0[..])
			.map_err(|_| HopError::InvalidSignature)?;

		let chain_info = self.client.info();
		let best_hash = chain_info.best_hash;

		let data_len = data.0.len();

		// Reject oversized payloads before the per-account authorization lookup so
		// a flood of too-big submits cannot force runtime state reads. The cap is
		// the runtime-declared `max_promotion_size`; the runtime is authoritative.
		let runtime_max = runtime_api::max_promotion_size::<Block, _>(&*self.client, best_hash)
			.map_err(HopError::from)?;
		if data_len > runtime_max as usize {
			return Err(HopError::DataTooLarge(data_len, runtime_max).into());
		}

		// Check authorization before verifying the signature: a flood of unauthorized
		// requests must not force a signature verification per submit.
		// `can_account_promote` returns false for any reason the runtime rejects:
		// unauthorized account or exhausted per-account quota.
		let account_id: AccountId32 = signer.clone().into_account();
		let authorized = runtime_api::can_account_promote::<Block, _>(
			&*self.client,
			best_hash,
			account_id.clone(),
			data_len as u32,
		)
		.map_err(HopError::from)?;
		if !authorized {
			return Err(HopError::NotAuthorized.into());
		}

		// Domain-separated payload so a submit signature cannot be replayed as claim/ack,
		// and bound to `submit_timestamp` so an old signature can't be replayed long
		// after the fact (the runtime enforces a tolerance window on the timestamp).
		let hash = H256(blake2_256(&data.0));
		let submit_payload = submit_signing_payload(&hash, submit_timestamp);
		if !multi_sig.verify(&submit_payload[..], &account_id) {
			return Err(HopError::InvalidSignature.into());
		}

		let sender_id: [u8; 32] = account_id.into();
		self.pool
			.insert(data.0, recipient_keys, sender_id, signer, multi_sig, submit_timestamp)?;
		Ok(SubmitResult { pool_status: self.pool.status() })
```

```rust
/// One intended recipient of a HOP entry: the ephemeral public key the sender
/// generated for this handoff, paired with the `claimed` flag that tracks whether
/// this recipient has acked. Fusing the two into a single struct (and a single
/// `BoundedVec<Recipient, ...>`) makes it impossible — by construction and on
/// disk — for the key list and the ack state to drift out of sync.
#[derive(Debug, Clone, Encode, Decode)]
pub struct Recipient {
	/// Ephemeral public key (MultiSigner: ed25519, sr25519, or ecdsa).
	pub signer: MultiSigner,
	/// Whether this recipient has acked receipt.
	pub claimed: bool,
}
```
