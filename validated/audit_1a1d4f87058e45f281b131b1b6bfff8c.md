### Title
HookService RPCs meant only for the internal gitaly-hooks entrypoint are also served on the external, client-facing listener - (File: internal/gitaly/service/hook/pre_receive.go)

### Summary
Gitaly's `HookService` (`PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, `PackObjectsHookWithSidechannel`) is designed to be invoked exclusively by the `gitaly-hooks` binary over Gitaly's *internal* Unix socket, using a `HooksPayload` that is minted by Gitaly itself as part of executing a legitimate Git operation. Analogous to the reported `fallback()` bug — where a handler meant to be reached only through a trusted entrypoint (the ERC-4337 EntryPoint) can instead be invoked directly by anyone — `HookService` is registered on the same gRPC server that also serves the public, external API, so any client that can reach Gitaly's external listener with a valid auth token can call these hook RPCs directly, bypassing the intended call path (`git` invoking `gitaly-hooks`, which is only spawned during operations Gitaly itself has already authorized).

### Finding Description
`HookService` is registered via the shared `setup.RegisterAll` used for every server (both internal and external listeners): [1](#0-0) 
and the client-facing entrypoint `gitaly-hooks` normally dials the *internal* socket using a token embedded in the `HooksPayload`: [2](#0-1) 

The payload carrying `InternalSocket`/`InternalSocketToken` is only ever generated by Gitaly server-side when it configures a Git command to run hooks: [3](#0-2) 

However, the `HookService` gRPC methods themselves perform no check that the caller is actually the internal `gitaly-hooks` process or that the request originated from the internal socket — they only validate the target repository: [4](#0-3) [5](#0-4) 

This is explicitly acknowledged as a known architectural weakness in the test suite itself: [6](#0-5) 
"we should stop serving HookService on the external socket given it is a service intended only to be used internally by Gitaly for hook callbacks."

Because these RPCs are also exposed on the external, client-reachable gRPC server, any caller holding a valid Gitaly auth token (the same token used for ordinary RepositoryService/OperationService calls — not a special internal-only secret) can invoke `PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, or `PackObjectsHookWithSidechannel` directly with attacker-crafted `Repository`, `EnvironmentVariables`, and `stdin`/ref-update fields, without going through an actual `git-receive-pack`/`git-update-ref` invocation. This mirrors the fallback() issue: the handler trusts that it is only reached via the legitimate "entrypoint" path but has no authorization control of its own to enforce that.

### Impact Explanation
An attacker who possesses ordinary Gitaly credentials (the same credential class used for standard push/fetch RPCs — e.g., a compromised or misconfigured client, or any principal with network access to Gitaly's external listener) can call `PreReceiveHook`/`PostReceiveHook`/`UpdateHook`/`ReferenceTransactionHook` out of band from any real Git operation. Depending on hook logic (custom hooks execution, GitLab `/internal/allowed` calls, transaction voting, reference-transaction hashing used for Praefect quorum decisions), this can be used to: trigger custom hook script execution with attacker-controlled `stdin`/environment variables against a target repository, spoof reference-transaction votes that Praefect relies on for write-ahead log/consistency decisions, or invoke `PackObjectsHookWithSidechannel` to run `git-pack-objects` with attacker-influenced arguments outside the context of an authorized fetch. The severity depends on what a given hook implementation trusts about the caller (similar to how the Nexus report rated it Medium because the practical exploitability depends on what the fallback handler does with `msg.sender`), but it represents a broken trust boundary between "internal only" and "external" RPC surfaces.

### Likelihood Explanation
Likelihood is moderate: exploitation requires possessing valid Gitaly authentication (a bearer token), which is the same bar as any other Gitaly RPC — there is no extra secret protecting the internal-only nature of `HookService`. Any actor who already has legitimate but limited access to Gitaly (e.g., a service account meant only for read/fetch operations, or a compromised client credential) could call these hook RPCs directly. This is explicitly called out by Gitaly's own test comments and referenced issue as a known gap (gitlab-org/gitaly#3746), indicating the exposure is real and currently unresolved rather than purely theoretical.

### Recommendation
Do not register `HookService` on the external, client-facing gRPC listener; only register it on the internal socket that `gitaly-hooks` uses, and additionally verify that requests to `HookService` methods carry proof of originating from the internal socket/token (analogous to `onlyEntrypoint()` in the Solidity report). If `HookService` must remain reachable externally for some deployments, add explicit authorization checks in each RPC handler (e.g., validate `InternalSocketToken`/an internal-only credential distinct from the general auth token, or check the connection's local peer/socket) rather than relying solely on generic repository validation.

### Proof of Concept
Conceptual PoC (cannot be executed without a running cluster, but demonstrates the reachable path):
1. Obtain a valid Gitaly auth token (same one used for normal external RPCs).
2. Using `grpcurl` against Gitaly's external `listen_addr`/socket (as documented in `doc/invoking_grpc_endpoints_locally.md`), call `gitaly.HookService/PreReceiveHook` (or `UpdateHook`, `ReferenceTransactionHook`, `PackObjectsHookWithSidechannel`) directly, supplying a target `Repository` and crafted `environment_variables`/`stdin`, without having triggered any actual `git-receive-pack` operation.
3. Observe that the hook logic executes (e.g., custom hook script runs, transaction vote is cast) even though no legitimate push/fetch ever occurred — confirming the RPC is reachable outside its intended internal-only entrypoint, matching the reference-transaction test file's built-in workaround for calling `HookService` "through the external API" at `internal/gitaly/service/hook/pre_receive_test.go` lines 182-193.

func dialGitaly(ctx context.Context, payload gitcmd.HooksPayload) (*grpc.ClientConn, error) {
	var dialOpts []grpc.DialOption
	if payload.InternalSocketToken != "" {
		dialOpts = append(dialOpts, grpc.WithPerRPCCredentials(gitalyauth.RPCCredentialsV2(payload.InternalSocketToken)))
	}

	// Propagate correlation ID
	unaryInterceptors := []grpc.UnaryClientInterceptor{
		labkitcorrelation.UnaryClientCorrelationInterceptor(
			labkitcorrelation.WithClientName("gitaly-hooks"),
		),
	}
	streamInterceptors := []grpc.StreamClientInterceptor{
		labkitcorrelation.StreamClientCorrelationInterceptor(
			labkitcorrelation.WithClientName("gitaly-hooks"),
		),
	}

	if spanContext, err := tracing.PropagateFromEnv(os.Environ()); err == nil {
		unaryInterceptors = append(unaryInterceptors, tracing.UnaryPassthroughInterceptor(spanContext))
		streamInterceptors = append(streamInterceptors, tracing.StreamPassthroughInterceptor(spanContext))
	}

	dialOpts = append(dialOpts,
		grpc.WithChainUnaryInterceptor(unaryInterceptors...),
		grpc.WithChainStreamInterceptor(streamInterceptors...),
	)
	conn, err := client.New(ctx, "unix://"+payload.InternalSocket, client.WithGrpcOptions(dialOpts))
	if err != nil {
		return nil, fmt.Errorf("error when dialing: %w", err)
	}

	return conn, nil
}
