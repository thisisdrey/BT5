### Title
Missing Cross-Oracle Timestamp Validation Between Pyth Price and stSTX Ratio in `resolve-ststx` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`resolve-ststx` combines a Pyth-sourced STX/USD price (which carries its own `timestamp`) with a live-fetched `stSTX` conversion ratio from `call-ststx-ratio` (which carries no timestamp at all) to derive the price used for `stSTX`/`zstSTX`/`zstSTXbtc` collateral valuation. The protocol's only freshness/staleness check, `oracle-timestamp-fresh`, is applied solely to the Pyth price's timestamp; the ratio value that is multiplied into the final price is never validated against that same timestamp window. This is the same bug class as the referenced Ion Protocol report: two independently-sourced values are combined into a single collateral price without ensuring they represent the same point in time.

### Finding Description
In `resolve-ststx`, the base STX price `p` (already resolved via `resolve-pyth`, carrying a `timestamp` field) is multiplied by a ratio obtained from `call-ststx-ratio`: [1](#0-0) 

This ratio call returns only a numeric ratio, with no associated timestamp, and is not routed through `oracle-timestamp-fresh` at all: [2](#0-1) 

The overall resolution path, `price-resolve`, only checks freshness of the outer `resolution` timestamp (the Pyth/DIA feed's `timestamp`), *after* `resolve-callcode` (which invokes `resolve-ststx`) has already blended in the un-timestamped ratio: [3](#0-2) 

So the STX/USD leg of the price is guaranteed fresh (bounded by per-asset `max-staleness`), but the stSTX-ratio leg is not reconciled to any timestamp window — it is whatever `call-ststx-ratio` returns at call time from the external `ststx-token` contract, with no cross-check that it reflects market conditions from the same period as the Pyth price. During a period where STX/USD price is volatile (e.g. dropping sharply) but the stSTX conversion ratio has not yet been updated to reflect that volatility (or vice versa), `resolve-ststx` produces a blended price that misrepresents the true value of stSTX in USD terms — the exact "timestamp discrepancy between two price sources" pattern described in the report. This same unchecked-ratio composition also feeds `CALLCODE-ZSTSTX` (via `resolve-ztoken (try! (resolve-ststx p)) stSTX`), so the derived `zstSTX`/`zstSTXbtc` vault-token prices inherit the same flaw: [4](#0-3) 

Unlike the Ion Protocol case — where the manipulated/misaligned spot price is explicitly upper-bounded by a separate "reserve oracle" exchange rate — Zest has no analogous secondary bound here: the ratio from `call-ststx-ratio` *is* the only exchange-rate-like reference used, so there is no independent cap limiting how far the combined price can diverge from the "true" value during the timestamp-misaligned window.

### Impact Explanation
This collateral price feeds directly into the market's LTV/health accounting used when issuing debt against `stSTX`, `zstSTX`, or `zstSTXbtc` collateral. If the STX/USD leg and the ststx-ratio leg diverge during volatility (one stale relative to the other), a borrower can be issued debt against an over-valued collateral price with no secondary cap to limit the divergence, unlike Ion's exchange-rate-bounded design. This can allow borrowing beyond the intended LTV against real collateral value, which upon later correction (price/ratio re-alignment) can leave the position under-collateralized — risking protocol insolvency/bad debt exposure if positions cannot be liquidated for the full misrepresented amount. This lands in the Critical impact category (protocol insolvency risk via over-issuance of debt against transiently mispriced collateral).

### Likelihood Explanation
This requires no privileged access or DAO compromise — it is triggered purely by ordinary market volatility causing natural timing/reporting lag between the Pyth STX/USD feed and the `ststx-token` ratio update cadence, then an ordinary user borrowing against `stSTX`/`zstSTX`/`zstSTXbtc` collateral during that window. Likelihood is moderate: it depends on real-world timing misalignment between two independently-updated external data sources, similar to the acknowledged (but unresolved) Ion Protocol issue.

### Recommendation
Track and return a timestamp from `call-ststx-ratio` (if the underlying `ststx-token` contract exposes one, e.g. last update block/time) and validate it via `oracle-timestamp-fresh` (or a dedicated ratio-staleness check) before combining it with the Pyth price in `resolve-ststx`. At minimum, bound the combined derived price so it cannot diverge from a reference/reserve value beyond a safety margin, similar to the exchange-rate cap in Ion Protocol's design.

### Proof of Concept
1. STX/USD price drops sharply on Pyth; the new lower price is published with a fresh `timestamp` and passes `oracle-timestamp-fresh`.
2. `call-ststx-ratio` still returns the previous (higher) ratio value because the underlying `ststx-token` contract has not yet updated its ratio for the current market conditions — no timestamp check exists to reject this stale ratio.
3. `resolve-ststx` multiplies the fresh (lower) STX price by the stale (higher) ratio, producing an inflated `stSTX`/USD price that does not reflect true market value at that moment.
4. A borrower opens/increases a position using `stSTX`/`zstSTX` collateral valued at this inflated price, extracting more debt than the true collateral value should permit, with no exchange-rate-style cap to limit the overvaluation as in Ion Protocol's design.

Note: I was unable to fully retrieve the implementation of `call-ststx-ratio` itself (its exact contract call target and whether the external `ststx-token` contract exposes any timestamp) within the available search iterations; this analysis is based on how its return value is consumed and gated (or not gated) for freshness within `market.clar`/`v0-4-market.clar`. Confirming the external contract's timestamp semantics would strengthen this finding further.

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
