### Title
Unbounded iteration over attacker-growable `unfrozenV2` list in `CancelAllUnfreezeV2Actuator`/`WithdrawExpireUnfreezeActuator` - (File: actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java)

### Summary
The `UNFREEZE_MAX_TIMES = 32` cap enforced by `UnfreezeBalanceV2Actuator.validate()` only counts *unexpired* entries (`getUnfreezeExpireTime() > now`), via `AccountCapsule.getUnfreezingV2Count`. Entries whose expire time has already passed are excluded from the cap check, so an attacker can keep submitting `UnfreezeBalanceV2Contract` transactions across many blocks (each one adding one `UnFreezeV2` entry) without ever triggering the 32-item ceiling, as long as they periodically let some entries "expire" without withdrawing them. Because the account's own balance/frozen state gates whether a transaction is accepted, and unfreezing an arbitrarily small amount is cheap and repeatable, the `unfrozenV2` list on the account can be grown to an effectively unbounded size over time.

### Finding Description
- `UnfreezeBalanceV2Actuator.validate()` throws only if the *current unexpired* unfreezing count reaches 32: [1](#0-0) 
- `AccountCapsule.getUnfreezingV2Count` walks the entire `unfrozenV2` list and only counts non-expired entries: [2](#0-1) 
- The account never garbage-collects expired-but-unwithdrawn entries automatically — they persist until a `WithdrawExpireUnfreezeContract` or `CancelAllUnfreezeV2Contract` transaction is submitted by the account owner (or, for TVM contract accounts, via `cancelAllUnfreezeV2Action`/`withdrawExpireUnfreeze` opcodes).
- `CancelAllUnfreezeV2Actuator.execute()` then iterates the *entire* `unfrozenV2List` unconditionally: [3](#0-2) 
- `WithdrawExpireUnfreezeActuator`/`WithdrawExpireUnfreezeProcessor` similarly stream over the full list on every call: [4](#0-3) 
- Unlike other list-bearing actuators in the codebase (e.g. `VoteWitnessActuator`/`VoteWitnessProcessor` capping votes at `MAX_VOTE_NUMBER`, `AssetIssueActuator` capping `FrozenSupply` list length, `MarketSellAssetActuator` capping match iterations at `MAX_MATCH_NUM`), there is no cap on the total size the `unfrozenV2` protobuf field can reach on an account, since the only enforced limit tracks unexpired items.
- This mirrors the cosign root cause exactly: an actor-controlled, growable collection is fully iterated in a hot path (`execute()`), without an independent hard cap on total collection size, only a cap on "active" subset size.

### Impact Explanation
Once an account accumulates a very large `unfrozenV2` list (built up over many blocks/transactions at negligible cost — each unfreeze can be as small as 1 unit), any subsequent `CancelAllUnfreezeV2` or `WithdrawExpireUnfreeze` transaction from that account (or invoked via TVM opcode from a contract) forces the node to iterate the full list during block validation/application inside `Manager`. This increases CPU time spent processing a single transaction disproportionately to its declared fee/energy, and because this executes during block application for every node validating the chain, a sufficiently large list can cause processing delays across the network for that block, degrading availability for other users' transactions in the same block window. This is a resource-exhaustion class issue analogous to the reported cosign DoS (unbounded loop driven by attacker-influenced input length).

### Likelihood Explanation
Any unprivileged account holder can build up the oversized list purely through their own repeated freeze/unfreeze transactions over time (bounded only by transaction fees and time, not by any protocol-level total-size check), making this reachable by a single actor without special privileges, and triggerable by that same actor at will by finally issuing the `CancelAllUnfreezeV2` or `WithdrawExpireUnfreeze` transaction.

### Recommendation
Enforce a hard cap on the total size of the `unfrozenV2` repeated field regardless of expiry status — e.g., extend the `UNFREEZE_MAX_TIMES` check in `UnfreezeBalanceV2Actuator.validate()` (and the TVM `UnfreezeBalanceV2Processor.validate()`) to count *all* entries in `getUnfrozenV2List()`, not just unexpired ones, or add an explicit total-size ceiling check before allowing new entries via `AccountCapsule.addUnfrozenV2List`.

### Proof of Concept
1. Attacker freezes a small balance for BANDWIDTH via `FreezeBalanceV2Contract`.
2. Attacker repeatedly submits `UnfreezeBalanceV2Contract` transactions unfreezing 1 drop at a time, each adding one entry to `unfrozenV2` with a short expire delay (`unfreezeDelayDays`).
3. Because `getUnfreezingV2Count(now)` only counts entries with `getUnfreezeExpireTime() > now`, once earlier entries' expire time passes, the count resets, allowing the attacker to keep adding more entries across many blocks, growing `unfrozenV2List` far beyond 32 total entries.
4. Attacker then submits a `CancelAllUnfreezeV2Contract` transaction; `CancelAllUnfreezeV2Actuator.execute()` at [5](#0-4)  iterates the entire oversized list within the transaction's execution during block application, consuming disproportionate CPU relative to a single transaction's cost.
