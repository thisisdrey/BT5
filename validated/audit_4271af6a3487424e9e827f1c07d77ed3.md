### Title
Uninitialized `accountIndexOf` is read as a valid index, inflating first-claim rewards at token registration - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta()` reads `accountIndexOf[token_][account_]` and treats the uninitialized value `0` as a real index unless the current token index is strictly greater than `INITIAL_INDEX`. At the moment a token is registered (`tokenStates[token_].index == INITIAL_INDEX`, no time elapsed), the fallback is skipped, so `_deltaIndex = INITIAL_INDEX - 0 = 1e18` and the account is credited `balance * 1.0` reward tokens. An unprivileged user with an existing `DepositToken`/`DebtToken` balance can call the public `claimRewards` in the same block the governor registers the token speed and drain the distributor.

### Finding Description
The vulnerability is in `contracts/RewardsDistributor.sol`, `_calculateTokenDelta` (lines 217-231):

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

The boundary condition is `> INITIAL_INDEX` instead of `>=`. When `updateTokenSpeed`/`_updateTokenSpeed` first registers a token, it writes `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (lines 296-299). From then on, `claimRewards(accounts_, tokens_)` (lines 150-168) sees `tokenStates[_token].index > 0` and calls `_updateTokensAccruedOf` → `_calculateTokenDelta` for every account passed in.

For any account holding the token whose `accountIndexOf` was never written (e.g., it deposited before the reward token was registered — `updateBeforeMintOrBurn` at lines 175-180 does nothing while `index == 0`), `_accountIndex == 0` but `_tokenIndex == INITIAL_INDEX`, so the fallback does not apply. `_deltaIndex = 1e18`, and `_tokensDelta = balance.wadMul(1e18) = balance` is added to `tokensAccruedOf[account_]`. `_transferRewardIfEnoughTokens` (lines 248-256) then pays out `min(accrued, distributor balance)` — up to the entire reward-token balance.

Concrete attacker call sequence (all public entry points):
1. Attacker holds a large `DepositToken` balance (deposited via `DepositToken.deposit` before the reward token has a non-zero speed). Their `accountIndexOf[depositToken][attacker]` remains `0`.
2. Governor calls `updateTokenSpeed(depositToken, speed)` (routine, non-malicious governance action), setting `index = INITIAL_INDEX`.
3. In the same block (same `block.timestamp`, so `_updateTokenIndex` cannot advance the index past `INITIAL_INDEX`), attacker calls `claimRewards(attacker)` or `claimRewards(attacker, depositToken)`.
4. `_calculateTokenDelta` computes `_tokensDelta = attackerDepositBalance`, and the distributor transfers its whole `rewardToken` balance (or `attackerDepositBalance` if smaller) to the attacker.

The analogous invariant break to the reported class: uninitialized per-account index storage is accessed as if initialized, producing a corrupted accrual delta.

### Impact Explanation
Direct theft of unclaimed yield: the attacker receives reward tokens proportional to their deposit-token balance rather than to elapsed time × speed. A single claim can extract the distributor's entire `rewardToken` balance, stealing rewards owed to all other users. Because `tokensAccruedOf` is also inflated, even if the distributor is refilled later the attacker may claim again unless `accountIndexOf` was corrected (it is set to `_tokenIndex`, so the inflated amount persists in `tokensAccruedOf` until paid).

### Likelihood Explanation
Requires only that (a) the attacker holds a deposit/debt token balance before the reward token's speed is first set, and (b) the claim executes in the same block/timestamp as the speed registration so the index is still exactly `INITIAL_INDEX`. The attacker can pre-position a balance cheaply (deposits are permissionless) and monitor the mempool for `updateTokenSpeed`/`updateTokenSpeeds` transactions, back-running within the same block. If the distributor also rewards `DebtToken` holders, the attacker can mint synthetic debt to hold a large tracked balance with modest collateral. No privileged role, oracle manipulation, or malicious bridge component is needed; the triggering governance action is a normal configuration call.

### Recommendation
Change the fallback condition so an uninitialized account index is always pinned to the index at which the account is first observed:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

or more simply, treat `accountIndex == 0` as `_tokenIndex` when `_tokenIndex <= INITIAL_INDEX`, so the delta is 0 at registration. Additionally, consider emitting/initializing `accountIndexOf` for existing holders at registration time, and add a regression test asserting that `claimable`/`claimRewards` returns 0 for all accounts in the same block that `updateTokenSpeed` registers a token.

### Proof of Concept
Hardhat-style sketch against the existing fixture (`smartFarmingManager`/`pool`/`rewardsDistributor` deployments):

```ts
// setup: alice deposits collateral before any reward speed is set
await depositToken.connect(alice).deposit(amount, alice.address) // accountIndexOf[depositToken][alice] == 0

// governor registers reward speed for the deposit token
await rewardsDistributor.updateTokenSpeed(depositToken.address, speed)
expect(await rewardsDistributor.claimable(alice.address)).to.eq(0) // FAILS: returns `amount`

// attacker claims in the same block -> receives min(amount, rewardToken balance)
await rewardsDistributor.connect(anyone).claimRewards(alice.address)
// rewardToken balance of alice == drained distributor balance (up to `amount`)
```

Expected: `claimable` and the payout should be 0 because zero time has elapsed since the index was initialized at `INITIAL_INDEX`. Actual: `_deltaIndex = 1e18` yields `tokensDelta == depositToken.balanceOf(alice)`.
