### Title
Pull-based oracle accepts any within-staleness-window price (not necessarily the latest), enabling attacker-timed self-liquidation that extracts collateral above true market value - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`price-resolve` and its helper `oracle-timestamp-fresh` accept any Pyth price whose publish timestamp is `>= prev` (the market's own last-seen timestamp) and within `max-staleness` of `stacks-block-time`, rather than requiring the current/latest price. Since `liquidate()` is permissionless and does not prevent `borrower == liquidator`, and only blocks liquidation in the *exact same block* as the last borrow, an attacker can borrow, wait a block, and self-liquidate while the market is still accepting a stale (but within-window) unfavorable collateral price and/or a fresher favorable debt price, collecting the liquidator bonus on their own position and shifting the loss (potential bad debt) to the protocol/LPs.

### Finding Description
Price freshness in the market is enforced by: [1](#0-0) 

which only checks `delta <= max-staleness` and `ts >= prev` — it does not require the price to be the most recently published one. `max-staleness` is per-asset and documented as up to 300 seconds for stable assets: [2](#0-1) 

`liquidate()` accepts an optional `price-feeds` list that is written before resolving position health, but the write is optional and callers can simply omit it and rely on whatever price is currently on-chain within the staleness window: [3](#0-2) 

The only front-running/self-liquidation guard present is a *same-block* check tied to `last-borrow-block`: [4](#0-3) 

This only prevents liquidation in the identical block as the borrow — it does not prevent liquidation in the next block (or any later block within the staleness window), and it does not prevent `borrower` and `liquidator` (`contract-caller`) from being the same principal; no such check exists anywhere in `liquidate`.

Collateral seized during liquidation is computed by dividing a USD amount by `coll-price` (the resolved oracle price for that asset), so a lower `coll-price` yields more collateral tokens for the same USD-denominated debt repayment and bonus: [5](#0-4) 

Because `oracle-timestamp-fresh` tolerates any timestamp within the staleness window (not strictly the latest), a borrower can wait for a moment where the on-chain collateral price is at the stale low end of that window (or otherwise unfavorable relative to the "true" current market price) while the debt-asset price used is comparatively higher/fresh, then call `liquidate(borrower=self, ...)` themselves to extract collateral valued at the stale price plus the liquidation bonus.

### Impact Explanation
This lands on **Critical — protocol insolvency / theft of funds at rest**. By self-liquidating using a stale-but-valid price leg, the attacker extracts collateral valued above what the true current market price would justify, plus the liquidation bonus (`liq-penalty`, up to `LIQ-PENALTY-MAX`). If the borrower's remaining collateral is insufficient to cover the true debt value after this extraction, the shortfall becomes bad debt that is socialized to lenders/vault depositors via `vault-socialize-debt`, i.e., protocol insolvency funded by other users' deposited funds.

### Likelihood Explanation
Likelihood is moderate: it requires (a) at least one asset pair with a `max-staleness` window wide enough to contain a materially different valid price (documented as up to 300s for "stable" assets, but any nonzero `max-staleness` creates the window), and (b) enough natural price movement of the underlying feeds within that window for the mismatch to be profitable net of the same-block guard, opening fees, and liquidation bonus economics. Because `liquidate` allows `borrower == contract-caller` with no dedicated check, and the only anti-self-liquidation control is the single-block guard, the attack is straightforward to execute mechanically once a favorable price window is observed — it is a timing/statistical opportunity rather than a guaranteed exploit on every block, matching the report's characterization of a "statistical risk" that grows with the number of correlated collateral/debt pairs supported.

### Recommendation
- Require price resolution in `liquidate` (and ideally in `borrow`) to use the most recently written price for each feed rather than any timestamp merely satisfying `>= prev` and `<= max-staleness`; e.g., track and require equality with the latest on-chain Pyth `publish-time` for that feed at call time, or force a mandatory feed refresh (`price-feeds` non-optional) immediately before evaluating liquidation health.
- Extend the existing front-running guard beyond same-block: prevent `borrower == contract-caller` (or `borrower == tx-sender`) from calling `liquidate` on their own position, or require a minimum elapsed time/blocks since the last collateral/debt price update used for the position's own borrow, tightly bounded to the confidence interval of the oracle.
- Reduce `max-staleness` values and/or introduce a price-confidence/deviation buffer as described in the report's mitigation (research realized historical volatility per collateral/debt pair, add a buffer, and adjust `LTV-LIQ-PARTIAL`/`MICR`-equivalent thresholds accordingly) so that legitimate staleness windows cannot be weaponized between correlated or volatile asset pairs.

### Proof of Concept
1. Attacker deposits collateral C of asset A (egroup with `max-staleness` for A/debt asset B set to e.g. 120–300s, per `docs/oracle.md`).
2. Attacker calls `borrow` to take out debt near `LTV-BORROW` in asset B (see `mainnet/contracts/market/v0-4-market.clar:1238-1314`), recording `last-borrow-block`.
3. Attacker waits at least one block (satisfying the `same-block-check` at `mainnet/contracts/market/v0-4-market.clar:1428-1431`) and monitors the on-chain Pyth prices for asset A and B; because `oracle-timestamp-fresh` (`mainnet/contracts/market/v0-4-market.clar:365-371`) accepts any price within `max-staleness` (not necessarily the freshest), the attacker picks the moment where the currently-resolvable price for A is at its most unfavorable point in the window relative to B.
4. Attacker calls `liquidate(borrower=self, collateral-ft=A, debt-ft=B, ...)` (`mainnet/contracts/market/v0-4-market.clar:1382-1493`) — no check prevents `borrower == contract-caller`. `current-ltv` computed from the stale/favorable price combination crosses `LTV-LIQ-PARTIAL`, allowing self-liquidation.
5. `coll-actual`/`coll-final` are computed by dividing the USD debt-repay amount (plus bonus) by the resolved `coll-price` (`mainnet/contracts/market/v0-4-market.clar:1453-1486`); using the unfavorable stale price yields more collateral tokens back to the attacker than the true market price would justify.
6. If the remaining collateral cannot cover the true debt, `vault-socialize-debt` absorbs the shortfall into the vault (lender funds), completing the wealth transfer from the protocol to the attacker.

;; -- Oracle: price resolution -----------------------------------------------

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

**Per-Asset Configuration:**
- Each asset defines its own `max-staleness` during registration
- Volatile assets can have shorter staleness (e.g., 60 seconds)
- Stable assets can have longer staleness (e.g., 300 seconds)
- `max-staleness > 0` required during asset registration

**Purpose:** Prevents using stale price data that could enable exploits, with flexibility per asset type.

**Note:** Uses `stacks-block-time` (Clarity 4 feature) for accurate timestamp-based validation, eliminating the need for block-height approximations.
