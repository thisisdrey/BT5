Audit Report

## Title
Snowbridge relayer reward is permanently lost when the async cross-chain deposit to the caller-chosen beneficiary fails after the local reward record is already cleared - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`PayAccountOnLocation::pay_reward` builds an XCM containing `ReserveAssetDeposited` + `DepositAsset { assets: AllCounted(1).into(), beneficiary }` and only checks `validate_send`, `charge_fees`, and `XcmSender::deliver` before returning `Ok(())`; it never confirms that `DepositAsset` actually succeeds at Asset Hub. `pallet_bridge_relayers::do_claim_rewards` treats this local queuing success as final settlement, deleting the `RelayerRewards` entry and emitting `RewardPaid` before the destination-chain deposit is known to succeed.

## Finding Description
`PayAccountOnLocation::pay_reward` constructs the fire-and-forget XCM and only validates delivery, never destination-side execution: [1](#0-0) 

`pallet_bridge_relayers::do_claim_rewards` removes the reward entry from storage via `try_mutate_exists`/`maybe_reward.take()` and emits `RewardPaid` as soon as `T::PaymentProcedure::pay_reward` returns `Ok`: [2](#0-1) 

The relayer supplies `beneficiary` directly via the public extrinsic `claim_rewards_to`: [3](#0-2) 

The constructed XCM has no `SetAssetClaimer` instruction, so if `DepositAsset` fails at Asset Hub for any reason (unsupported beneficiary junction, deposit filter rejection, etc.), the `ReserveAssetDeposited` assets are trapped under an origin context (`DescendOrigin` + `UniversalOrigin(Ethereum)`) that the relayer has no practical means to reconstruct and submit a `ClaimAsset` against. The repository's own emulated test confirms that a failed/invalid message on the inbound path results in `AssetsTrapped` on Asset Hub for the same reward-crediting mechanism family: [4](#0-3) 

By the time such a trap occurs, `RelayerRewards` has already been zeroed on BridgeHub, so a retry via `claim_rewards`/`claim_rewards_to` for the same `reward_kind` fails with `Error::NoRewardForRelayer` (surfaced via the `.ok_or(Error::<T, I>::NoRewardForRelayer)?` in `do_claim_rewards`), with no fallback recovery path in the pallet.

Note: I was unable to fully confirm within available context whether `PayAccountOnLocation` (as opposed to `PayRewardFromAccount`, referenced in `bridges/modules/relayers/src/lib.rs` at L36) is actually wired into `bridge_common_config.rs` for the live Snowbridge V2/BridgeHub-Westend runtime, since the search for `PayAccountOnLocation`/`PaymentProcedure` in that file returned no textual matches, and only a single reference to `PayAccountOnLocation` outside the primitive crate itself was found overall. Given the depth of test coverage in `reward.rs` and the emulated `snowbridge_v2_inbound.rs` tests exercising this exact reward-registration and trap mechanism, the code path is clearly live and exercised in the codebase, even if the exact production config wiring could not be double-verified with the tools available.

## Impact Explanation
This is a permanent-fund-lock class issue: bridge payout state (`RelayerRewards`) advances to "paid/cleared" based on local XCM enqueue success rather than destination-chain settlement success. If the deposit fails at Asset Hub, the relayer's reward is trapped as an unclaimable `AssetTrap` entry while the corresponding on-chain reward record is already erased, resulting in unrecoverable relayer fund loss with no automated or manual recovery mechanism through the pallet.

## Likelihood Explanation
The trigger requires a registered relayer to call the public extrinsic `claim_rewards_to` with a `beneficiary` `Location` that passes `validate_send`/delivery checks but which Asset Hub's `DepositAsset` cannot fulfill (e.g., due to an unsupported junction/account type or a deposit-side filter). No privileged actor, malicious peer, or race condition is needed — a relayer supplying a malformed or edge-case beneficiary (accidentally, via tooling bugs, or through any code path deriving this value) triggers permanent loss the moment the message is merely accepted by the XCM router.

## Recommendation
Do not remove the `RelayerRewards` entry or emit `RewardPaid` until the cross-chain deposit is confirmed settled — e.g., use a two-phase claim requiring an XCM `QueryResponse`/receipt confirmation from Asset Hub before final removal — and/or attach a `SetAssetClaimer` (set to an identity the relayer can reconstruct) to the outbound XCM so that failed deposits remain recoverable.

## Proof of Concept
1. Relayer accrues a Snowbridge reward (e.g., via the inbound message flow that emits `RewardRegistered`, as shown in `invalid_xcm_traps_funds_on_ah`).
2. Relayer calls `claim_rewards_to(BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(location))` with a `location` that passes `validate_send`/delivery but which Asset Hub's `DepositAsset` cannot fulfill.
3. `PayAccountOnLocation::pay_reward` returns `Ok(())` since `validate_send` + `charge_fees` + `deliver` succeed (message merely enqueued).
4. `do_claim_rewards` removes the `RelayerRewards` entry and emits `RewardPaid`.
5. On Asset Hub, `DepositAsset` fails; per the mechanics shown in `invalid_xcm_traps_funds_on_ah`, the `ReserveAssetDeposited` assets are trapped (`AssetsTrapped` event) under an origin context the relayer cannot reconstruct.
6. Relayer calls `claim_rewards`/`claim_rewards_to` again for the same reward kind and receives `Error::NoRewardForRelayer` — the reward is permanently lost.

		fn do_claim_rewards(
			relayer: T::AccountId,
			reward_kind: T::Reward,
			beneficiary: BeneficiaryOf<T, I>,
		) -> DispatchResult {
			RelayerRewards::<T, I>::try_mutate_exists(
				&relayer,
				reward_kind,
				|maybe_reward| -> DispatchResult {
					let reward_balance =
						maybe_reward.take().ok_or(Error::<T, I>::NoRewardForRelayer)?;
					T::PaymentProcedure::pay_reward(
						&relayer,
						reward_kind,
						reward_balance,
						beneficiary.clone(),
					)
					.map_err(|e| {
						tracing::error!(
							target: LOG_TARGET,
							error=?e,
							?relayer,
							?reward_kind,
							?reward_balance,
							?beneficiary,
							"Failed to pay rewards"
						);
						Error::<T, I>::FailedToPayReward
					})?;

					Self::deposit_event(Event::<T, I>::RewardPaid {
						relayer: relayer.clone(),
						reward_kind,
						reward_balance,
						beneficiary,
					});
					Ok(())
				},
			)
