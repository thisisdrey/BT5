### Title
Pool.swap executes oracle-priced synthetic swaps with no user-controlled slippage bound - (File: contracts/Pool.sol)

### Summary
`Pool.swap()` burns a user's `syntheticTokenIn_` and mints `syntheticTokenOut_` at a price derived entirely from `masterOracle().quote()`, yet exposes no `amountOutMin_` parameter. The same pattern affects `quoteSwapOut`/`quoteSwapIn` callers and the liquidation path `liquidate()`/`quoteLiquidateOut()`, where the amount of collateral seized is computed purely from the oracle quote with no bound supplied by either party. If the oracle's output deviates from the fair price at execution time — including same-transaction manipulation of a spot-derived oracle source — the swapper receives less synth out (and the liquidated account loses more collateral) than expected, with no way to reject the fill.

### Finding Description [1](#0-0) 

`swap()` takes only `(syntheticTokenIn_, syntheticTokenOut_, amountIn_)`. The output amount is computed by `quoteSwapOut`, which calls `_poolRegistry.masterOracle().quote(...)` and subtracts the fee: [2](#0-1) 

There is no `amountOutMin_` anywhere in the swap path — the user cannot express "revert if I get less than X". Compare with `SmartFarmingManager.flashRepay`, which correctly enforces `swapAmountOutMin_` after the external swap (`if (_swapAmountOut < swapAmountOutMin_) revert FlashRepaySlippageTooHigh()`), and `leverage`, which enforces `depositAmountMin_` — the codebase clearly acknowledges the need for slippage bounds, but the direct `Pool.swap` entry point lacks one entirely. [3](#0-2) 

Similarly, `liquidate()` computes `_totalSeized` via `quoteLiquidateOut` → `masterOracle().quote(synthetic → collateral underlying, amountToRepay)` with no upper bound on seized collateral: [4](#0-3) [5](#0-4) 

The `MasterOracle` is an external aggregator (`IMasterOracle.quote/quoteTokenToUsd/quoteUsdToToken`) that also prices vault-share collateral (`VesperGateway` / `IVPool` assets). If any leg of the pricing path is derived from a manipulable on-chain source (vault share price, AMM spot), an unprivileged attacker can shift the quote within the same transaction and extract value.

### Impact Explanation
- For `swap`: user burns `amountIn_` of a synth and receives `oracleQuote - fee` of the other. If the attacker pushes the quote down (or the input synth's oracle price up) — e.g., by manipulating the oracle's spot source in the same tx, front-running via `Operator.execute`/gateways, or trading on the source pool — the user receives materially less synth out. Direct loss of user funds equal to the pricing deviation.
- For `liquidate`: the seized amount scales inversely with the collateral's oracle price. An attacker liquidator that deflates the collateral quote (donation/manipulation of the underlying vault price source) seizes more of the victim's collateral for the same `amountToRepay_`. `AmountIsTooHigh` only checks `_totalSeized <= balanceOf(account_)`, not fairness — so an inflated seize within the user's balance succeeds.

### Likelihood Explanation
The guards present (`whenNotShutdown`, `nonReentrant`, `onlyIfSyntheticTokenExists`, `onlyIfDepositTokenExists`, `isSwapActive`, `maxLiquidable`, health checks) do not bound the price used. The only check on seized collateral is a balance cap. Exploitation requires the `MasterOracle`'s quote for at least one asset to be influenceable in-transaction; Metronome quotes vault-share collaterals (Vesper `IVPool` tokens) whose share price can be moved by deposits/withdrawals, and any DEX-derived feed is manipulable by definition. If the deployed oracle is purely Chainlink push feeds, the residual risk is stale/lagged prices between user quote estimation and execution — still uncompensated because no min-out exists. Likelihood is therefore conditional on oracle composition, but the missing protection is unconditional.

### Recommendation
- Add `amountOutMin_` to `Pool.swap()` (and propagate through `NativeTokenGateway`/`Operator` call paths), reverting when the oracle-priced output is below it.
- For `liquidate()`, let the liquidator pass `maxToSeize_` (or require `_totalSeized <= expected * (1 + maxDeviation)`), and consider a two-source/sanity bound on the collateral quote before seizing.
- Alternatively make `MasterOracle` quote both spot and a bounded TWAP and revert on deviation beyond a threshold.

### Proof of Concept
Foundry fork test sketch (run against a chain deployment where `MasterOracle` resolves a manipulable source, e.g., a Vesper vault share price):

```solidity
// 1. Victim holds msUSD, intends swap to msETH at fair quote q0.
uint256 fairOut = pool.quoteSwapOut(msUSD, msETH, amountIn); // e.g. ~amountIn * pxUSD/pxETH

// 2. Attacker same-tx (or front-runs victim's Operator.execute batch):
//    manipulates the oracle source so quote(msUSD -> msETH) drops X%.
//    e.g., dump the DEX pool / deposit-withdraw the vault underlying
//    that MasterOracle reads, moving the quote used by swap().

// 3. Victim's swap executes — no amountOutMin exists to revert:
pool.swap(msUSD, msETH, amountIn);   // burns msUSD, mints manipulated-low msETH
assert(msETH.balanceOf(victim) < fairOut); // loss realized

// Liquidation variant:
//    Attacker deflates collateral underlying oracle quote, then:
pool.liquidate(msUSD, victim, amountToRepay, depositToken);
// quoteLiquidateOut returns inflated _totalSeized; only check is
// _totalSeized <= depositToken.balanceOf(victim) -> passes, victim over-seized.
```

Note: whether a concrete fork PoC succeeds depends on the deployed `MasterOracle` implementation (not fully in this repo's `contracts/` — only the `IMasterOracle` interface and `MasterOracleMock` are in-scope). The missing-slippage defect itself is unconditional and verifiable from `Pool.sol` alone.
