## Analysis

The Dopex finding's core broken invariant: a public, permissionless entry point (`bond()`) internally and atomically triggers an AMM operation (`reLP()` → remove/swap/add liquidity) whose economics are quoted against *live, attacker-influenced* pool reserves, with only self-consistent slippage bounds that don't defend against manipulation performed by the caller's own preceding action in the same transaction.

The closest local analog is `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`, which wires an AMM pool (`pallet-asset-conversion`) into ordinary transaction-fee payment. Any signed extrinsic can select a non-native `asset_id` fee asset via `ChargeAssetTxPayment`, causing the same pool to be swapped against automatically at two different points straddling the user's own dispatched call.

### Title
Fee-asset refund swap in `ChargeAssetTxPayment`/`SwapAssetAdapter` prices against post-call, user-manipulated pool reserves, enabling mempool-free value extraction from AMM liquidity providers - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter::withdraw_fee` quotes and swaps the fee asset for the native fee **before** the extrinsic's own call executes, while `SwapAssetAdapter::correct_and_deposit_fee` quotes and swaps the unspent-fee refund **after** the call executes [1](#0-0) , [2](#0-1) . Both swaps hit the exact same `pallet-asset-conversion` pool used by `T::OnChargeAssetTransaction`/`S: SwapCredit`. If the extrinsic's own `call` is itself a swap in that pool (e.g. `pallet_asset_conversion::swap_exact_tokens_for_tokens` on the same asset pair), a single signed account can shift the pool reserves between the pre-dispatch fee withdrawal and the post-dispatch refund, all inside one atomic transaction, with no mempool positioning and no flash loan needed.

### Finding Description
The extension lifecycle is: `validate` → `prepare` (calls `withdraw_fee`) → **dispatch the wrapped call** → `post_dispatch_details` (calls `correct_and_deposit_fee`) [3](#0-2) , [4](#0-3) .

- `withdraw_fee` quotes `asset_fee` via `quote_price_tokens_for_exact_tokens(asset_id, A, fee, true)` against the pool's reserves *before* the wrapped call runs, withdraws that exact amount from the payer, and swaps it into native `fee` with `S::swap_tokens_for_exact_tokens` [5](#0-4) .
- The wrapped call is then dispatched normally by the runtime's call-execution logic — nothing prevents that call from itself being `pallet_asset_conversion::swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` on the very same `(asset_id, A)` pool, moving the reserves substantially in the direction the payer chooses.
- `correct_and_deposit_fee` then computes `refund_amount` and quotes `refund_asset_amount = quote_price_exact_tokens_for_tokens(A, asset_id, refund_amount, true)` against the pool's **now-manipulated** reserves, and swaps the refund back with `S::swap_exact_tokens_for_tokens(vec![A, asset_id], refund, Some(refund_asset_amount))` [6](#0-5) .

The `Some(refund_asset_amount)` "minimum" passed into the refund swap is not an independent slippage guard — it is derived from the same manipulated quote the swap will execute against, so it can never reject the swap; it only guarantees internal accounting consistency, not fair pricing. There is no snapshot of reserves taken at `validate`/`prepare` time that is enforced at `correct_and_deposit_fee` time, and no check that the wrapped call did not itself trade against the fee-payment pool.

### Impact Explanation
A payer who chooses `asset_id = X` for fee payment and whose wrapped call is a large `swap_*` trading `X` into the `X/native` pool can:
1. Pay the (small) fee in `X` at the pre-trade price via `withdraw_fee`.
2. Execute their own large swap that dumps `X` into the pool and pulls native `A` out, depressing `X`'s pool price relative to `A`.
3. Receive the unspent-fee refund back in `X` via `correct_and_deposit_fee`, priced at the post-trade (depressed) `X` price — i.e. get more `X` per unit of refunded native `A` than the pool's fair pre-trade rate implied.

This drains value from the AMM pool's liquidity providers (fee-asset holders funding the pool) into the attacker's account, entirely within one atomic, unprivileged, signed extrinsic — no mempool front-running, no validator/collator collusion, and no flash loan required, matching the "public underpriced work" / "conserve value, settle exactly once" pivots for this program.

### Likelihood Explanation
Likelihood is moderate-to-high wherever a runtime enables `pallet-asset-conversion-tx-payment` with `SwapAssetAdapter` and permits fee payment in an asset that also has an active liquidity pool a user can swap against with a normal dispatchable in the same transaction (e.g. Asset Hub-style runtimes using `AssetConversion` both for tx-fee swaps and for user swaps) — this is exactly the configuration exercised in the repository's own integration tests [7](#0-6) . The attacker needs only enough capital to move the pool and pay the extrinsic's own weight/length fee — no special privileges, no governance/admin action, and no timing dependence on other transactions.

### Recommendation
- In `SwapAssetAdapter::correct_and_deposit_fee`, do not re-quote against live post-call reserves; instead reuse (or bound against) the pool state captured at `withdraw_fee` time, or apply an independent, caller-supplied maximum-slippage bound for the refund leg rather than deriving the "minimum" from the same just-computed quote.
- Alternatively, disallow/flag combinations where the wrapped call trades in the same asset pair used for fee payment within the same extrinsic, or perform the refund swap using a TWAP/oracle-anchored price rather than instantaneous spot reserves.
- Add integration tests that dispatch a call which swaps in the fee-payment pool and assert the refund cannot be priced more favorably than the pre-dispatch quote.

### Proof of Concept
1. Runtime configures `pallet-asset-conversion-tx-payment` with `SwapAssetAdapter<Native, Assets, AssetConversion, OU>`, and a live `X/Native` pool exists via `pallet-asset-conversion`.
2. Attacker submits one signed extrinsic:
   - `ChargeAssetTxPayment { asset_id: Some(X), tip: 0 }` extension.
   - `call = AssetConversion::swap_exact_tokens_for_tokens(path: [X, Native], amount_in: <large>, amount_out_min: 0, send_to: attacker, keep_alive: false)`.
3. `prepare` → `withdraw_fee`: quotes small `asset_fee` of `X` at pre-trade reserves, swaps it for exact native `fee` [5](#0-4) .
4. Runtime dispatches the wrapped call: attacker's large `X → Native` swap executes, sharply moving the `X/Native` pool reserves.
5. `post_dispatch_details` → `correct_and_deposit_fee`: computes `refund_amount` (unspent weight fee) and quotes/swaps it back into `X` using the now-skewed reserves via `quote_price_exact_tokens_for_tokens`/`swap_exact_tokens_for_tokens` [6](#0-5) , returning more `X` to the attacker than the pre-trade rate would have allowed.
6. Net effect: attacker's own atomic transaction extracts pool value through the refund leg, at the expense of the pool's other liquidity providers, with no mempool interaction.

			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
