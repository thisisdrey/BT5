### Title
Dust-transfer griefing fills a victim's `depositTokensOfAccount` list to `MAX_TOKENS_PER_USER`, permanently blocking new collateral deposits and forcing liquidation - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined length of an account's deposit-token and debt-token lists, reverting with `UserReachedMaxTokens` inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` [1](#0-0) [2](#0-1) . Any registered `DepositToken` (a permissionless, transferable ERC-20-style share token) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance goes from 0 to >0 [3](#0-2) . An unprivileged attacker can therefore deposit dust of each listed collateral, transfer 1 wei of each `msd*` token to a victim, and fill all 30 slots, permanently DoS-ing the victim's ability to onboard new collateral types — the analog of the CVE's "unprivileged user enables denial of service."

### Finding Description
Attack trace (all public entry points, no privileged role):

1. Attacker calls `DepositToken.deposit(dust, attacker)` for each of the pool's ~N registered deposit tokens to obtain dust `msd*` balances [4](#0-3) .
2. Attacker calls `DepositToken.transfer(victim, 1)` for each token. Each transfer where the victim's prior balance is 0 invokes `pool.addToDepositTokensOfAccount(victim)` [5](#0-4) , which appends to `depositTokensOfAccount[victim]` via `MappedEnumerableSet` [6](#0-5) .
3. Once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`, every subsequent first-time receipt reverts in `onlyIfAdditionWillNotReachMaxTokens` [7](#0-6) .

Consequences once the list is saturated:
- `Pool.deposit`/`DepositToken._mint` for any *new* collateral type reverts (`UserReachedMaxTokens`), because `_mint` calls `addToDepositTokensOfAccount` when the balance was zero [8](#0-7) .
- `DebtToken` issuance of any new synth reverts the same way via `addToDebtTokensOfAccount` [9](#0-8) .
- Any `transfer`/`transferFrom` of a token the victim doesn't already hold reverts, since `_transfer` propagates the pool revert — even funds legitimately sent to the victim bounce.
- Cleanup is often impossible: entries are only removed when a balance reaches 0 (`removeFromDepositTokensOfAccount`) [10](#0-9) , but `transfer` enforces `unlockedBalanceOf`/`_revertIfLocked`, so a victim whose collateral is locked against debt cannot move the dust out. Even an unlocked victim must spend one transaction per dusted token.

### Impact Explanation
Temporary-to-permanent freezing of the victim's position-management capability and forced liquidation, meeting the "denial of service / freezing" impact bar. After saturation, if the market moves against the victim's existing collateral, they cannot deposit a *different* collateral type to restore health; `debtPositionOf` deteriorates and any liquidator executes `Pool.liquidate` [11](#0-10) , seizing collateral plus `liquidatorIncentive` — a direct, externally caused loss the victim was blocked from preventing. Even absent a crash, the victim is locked out of new collateral/debt positions and cannot receive new deposit tokens until they individually clear each dusted slot.

### Likelihood Explanation
Low-to-medium attacker cost, fully unprivileged: depositing dust of each listed `DepositToken` and transferring 1 wei to the victim. Feasibility depends on the pool having enough listed deposit tokens to approach the cap of 30 combined with the victim's debt tokens; on deployments with many collaterals (or where the victim already holds several debt tokens), the gap is small. No oracle manipulation, privileged role, or timing assumption is needed; the attack is front-runnable against a pending deposit and works on any victim address at any time.

### Recommendation
- Make first-time receipt non-reverting under the cap: in `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount`, skip (or cap) insertion instead of reverting with `UserReachedMaxTokens`, or treat forced dust receipts differently so a third party cannot consume the victim's slots.
- Alternatively, require a minimum amount (e.g., `MIN_BALANCE` dust threshold) before a token is tracked in `depositTokensOfAccount`, or store per-account tracking off the critical deposit path.
- Allow victims to opt out: add a `Pool.sweepFromAccountList(token)` escape hatch that lets an account remove an unwanted tracked token and burn/redirect the dust balance even when locked.

### Proof of Concept
Reproducible in the existing Hardhat suite (`test/Pool.test.ts` already demonstrates `UserReachedMaxTokens` on saturation [12](#0-11) ):

```ts
// hardhat fork test sketch
const victim = alice.address;
const depositTokens = await pool.getDepositTokens();
for (const dt of depositTokens.slice(0, 30)) {
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('ERC20', await token.underlying());
  await underlying.connect(attacker).approve(token.address, 1);
  await token.connect(attacker).deposit(1, attacker.address);
  await token.connect(attacker).transfer(victim, 1); // adds slot for victim
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.length(30);
// victim can no longer deposit a new collateral type:
await expect(newDepositToken.connect(alice).deposit(1, victim))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```
