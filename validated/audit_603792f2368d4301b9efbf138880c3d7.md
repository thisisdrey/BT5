### Title
Per-IP and global QUIC connection rate limiters use a check-then-act (peek-then-consume) pattern, allowing burst evasion of `max_connections_per_ipaddr_per_min` - (File: streamer/src/nonblocking/quic.rs)

### Finding Description
In `run_server`, incoming QUIC connections are gated by two "peek" checks performed *before* the handshake even begins:
- `overall_connection_rate_limiter.current_tokens() == 0` (global) [1](#0-0) 
- `rate_limiter.is_allowed(&incoming.remote_address().ip())` (per-IP) [2](#0-1) 

`ConnectionRateLimiter::is_allowed` is explicitly documented and implemented as read-only — it never mutates the token bucket, it only checks `current_tokens(ip) > 0`: [3](#0-2) 

Actual token consumption only happens later, inside the spawned `setup_connection` task, *after* the QUIC handshake completes (bounded by `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` = 2s): both `rate_limiter.register_connection(&from.ip())` and `overall_connection_rate_limiter.consume_tokens(1)` are called only once `connecting.await` resolves `Ok`: [4](#0-3) 

Because the check (`is_allowed`/`current_tokens`) and the mutation (`register_connection`/`consume_tokens`) are separated by an unbounded number of concurrently in-flight handshakes, a single IP can open many connection attempts in a tight burst; each new attempt performs the peek independently against a bucket that has not yet been decremented by any of the still-in-flight siblings. All of them observe `is_allowed() == true` and are admitted into `incoming.accept()` / `setup_connection`, receiving an `ClientConnectionTracker` slot and incrementing `stats.outstanding_incoming_connection_attempts`, before any of them actually spends a token. Only once a given handshake finishes does the real per-IP/global decrement occur — too late to prevent the burst from being admitted.

The comment at lines 332-340 acknowledges the intended defense-in-depth design ("cap total connections per-peer/ip") but the implementation defers the actual charge to post-handshake completion, creating exactly the TOCTOU gap the question describes.

### Impact Explanation
This is a genuine QoS-evasion bug: it lets a single unstaked/unprivileged IP consume a disproportionate share of the shared, global `max_concurrent_connections` budget (via `ClientConnectionTracker::new`, checked against `qos.max_concurrent_connections()`) and drive `outstanding_incoming_connection_attempts` and handshake CPU well above what `max_connections_per_ipaddr_per_min` is supposed to permit, during each ~2-second handshake-timeout window. This can starve legitimate (including staked) connection attempts from being admitted, since the shared `stats.open_connections` counter and connection-table capacity are limited resources [5](#0-4) . That said, growth is not literally unbounded: it is still capped by `qos.max_concurrent_connections()` (global) and by the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, so this is a rate-limit/QoS-evasion issue rather than a panic/deadlock/OOM primitive.

### Likelihood Explanation
Feasible for a single unprivileged attacker with only its own IP: it merely needs to open many parallel QUIC connection attempts in a tight burst (well within the ~2s handshake timeout window) rather than sequentially waiting for prior attempts to resolve. No stake, keys, or special network position are required — just the ability to complete (or attempt) many concurrent handshakes quickly, which matches the question's threat model exactly.

### Recommendation
Make the per-IP and global admission checks atomic with the reservation: consume/reserve a token (or a placeholder slot) at `incoming.accept()` time (before spawning `setup_connection`), and release it back if the handshake fails, rather than deferring `register_connection`/`consume_tokens` until after handshake success. Alternatively, use a reservation pattern (e.g., "try-consume-then-refund-on-failure") so that concurrent in-flight attempts are charged against the bucket as soon as they are admitted, closing the check-then-act window between `is_allowed` and `register_connection`.

### Proof of Concept
Integration test plan for `streamer/src/nonblocking/quic.rs`:
1. Configure `run_server` (or a test harness reusing `spawn_server`) with a small `max_connections_per_ipaddr_per_min` (e.g., 3/min) and a generous `max_concurrent_connections`/`overall_connection_rate_limiter` burst allowance.
2. From a single test client IP, launch N (e.g., 20) QUIC connection attempts concurrently (all dialed within the same tokio task-spawn tick, before any completes its handshake).
3. Assert that despite `max_connections_per_ipaddr_per_min` = 3, more than 3 connections are simultaneously admitted into `setup_connection` (observable via `stats.outstanding_incoming_connection_attempts` peak, or via `stats.total_new_connections` after all resolve) — i.e., `stats.connection_rate_limited_per_ipaddr` does not bound the number of concurrently admitted handshakes to the configured per-minute rate when attempts are bursted rather than serialized.
4. Compare against a control run where the N attempts are serialized (each waited on before the next starts) — in that case, the limiter should correctly reject connections beyond the configured limit, showing the discrepancy is caused specifically by concurrency/timing rather than the limiter's basic correctness.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
}

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
