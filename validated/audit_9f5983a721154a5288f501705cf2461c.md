### Title
Anti-replay window check-then-update race allows concurrent replay of captured packets - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` (and its relay counterpart `VerifyRelay`) validates a packet's `messageCounter` against the replay window (`window.Check`), releases the lock, performs the actual AEAD decryption *unlocked*, and only re-acquires the lock afterwards to mark the counter as seen (`window.Update`). This mirrors the DYAD pattern of computing a value from live/incoming state in one step and committing/reconciling that state in a separate, later step: any packet processed concurrently with the same counter can pass the "not yet seen" check before either commits, defeating the purpose of the replay window.

### Finding Description
`Decrypt` is implemented as: [1](#0-0) 

The sequence is: lock → `window.Check(messageCounter)` → unlock → `dKey.DecryptDanger(...)` (unlocked) → lock → `window.Update(messageCounter)` → unlock. The commit (`Update`, which actually marks the bit as seen) is decoupled from the read (`Check`) by an unprotected interval during which the expensive decrypt operation runs. `VerifyRelay` has the identical structure: [2](#0-1) 

If two packets carrying the same `messageCounter` (e.g., an original packet and a bit-for-bit copy captured off the wire and re-injected by a network attacker) are handed to two different goroutines that reach `Decrypt` at roughly the same time, both can execute `window.Check` before either executes `window.Update`, because the lock is released between the two calls. Both `Check` calls observe the bit as unset and both return `true`, so both packets proceed to be decrypted and accepted as valid, non-replayed traffic. Only after both have already decrypted does either call `Update`, and by then the replay has already been let through.

This is structurally the same class of bug as the reported issue: state used for validation (the "current" replay window state read via `Check`) is allowed to diverge from state used for final settlement (`Update`) because the two are not executed atomically with respect to the operation they are meant to gate, and an attacker can win the race by supplying the input (the duplicated ciphertext) that lands on two parallel processing paths.

Nebula explicitly supports multiple parallel packet-processing routines (`listen.routines`, batched `recvmmsg`), and hostinfo lookup for the data plane keys off the header's index rather than strictly off the UDP source `ip:port` (to support roaming). An attacker who captures a legitimate ciphertext packet and re-transmits it from a different source port can cause it to be scheduled on a different worker/queue than the original, giving a realistic opportunity for concurrent `Decrypt` calls on the same `ConnectionState` for the same counter.

### Impact Explanation
This breaks the confidentiality/integrity guarantee that the replay window is supposed to provide: an attacker who can capture and replay ciphertext (no valid certificate or key material required) can, under a race, get a duplicate/old packet re-accepted and delivered to the tun device or forwarded, defeating anti-replay protection for the affected packet(s). This falls squarely in the "nonce/replay handling" category identified as reachable-and-impactful.

### Likelihood Explanation
Exploitation requires winning a race between two goroutines processing the same counter, which depends on packet scheduling/timing and on the deployment running with multiple listener routines. It is not deterministically exploitable on every attempt, but the CHANGELOG for this exact repository already documents multiple related, previously-shipped bugs in this area — "Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them" and "Lock replay window updates so concurrent readers can't corrupt it" — showing this is a recurring, real weak point rather than a theoretical one. [3](#0-2) 

### Recommendation
Hold `decryptLock` across the entire check-decrypt-update sequence in `Decrypt` and `VerifyRelay` (or otherwise make check-and-set atomic, e.g. via a single `CheckAndUpdate` that speculatively marks the counter before decrypting and rolls back on decryption failure), so that no second caller can observe the "unseen" state for a counter that is already in flight.

### Proof of Concept
Conceptual race (not a full harness):
1. Two goroutines `A` and `B` both call `cs.Decrypt(l, N, ...)` for the same `ConnectionState` and the same `messageCounter = N` (e.g., `B`'s packet is a captured duplicate of the packet `A` is processing, re-injected from a different source port so it is scheduled on a different worker).
2. `A` acquires `decryptLock`, calls `window.Check(N)` → `true`, releases lock.
3. Before `A` calls `window.Update(N)`, `B` acquires `decryptLock`, calls `window.Check(N)` → also `true` (bit for `N` still unset), releases lock.
4. Both `A` and `B` proceed to `dKey.DecryptDanger(...)` unlocked and both succeed, then both call `window.Update(N)`.
5. Result: the duplicate/replayed packet `B` is accepted and processed as legitimate traffic even though `N` had already been "seen" by `A`, defeating the replay window.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
