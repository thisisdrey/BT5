### Title
Unbounded/unchecked array-length field in TVM precompile ABI decoding can trigger OutOfMemoryError / crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
CVE-2016-4489 is a libiberty integer-overflow where an attacker-controlled length field from a crafted binary is used to size an allocation with no bounds checking, producing an unrecoverable crash. The same bug class exists in `PrecompiledContracts.extractBytes32Array`, which reads an untrusted length word straight from precompile call data and uses it to size a Java array with no upper bound and no offset validation, unlike the sibling helpers in the same file.

### Finding Description
`extractBytes32Array` reads the array length directly from attacker-supplied call data and allocates a two-dimensional array of that size without any validation: [1](#0-0) 

Compare this to the two other extraction helpers in the same file, `extractBytesArray` and `extractSigArray`, which both guard against `offset` running past the end of `words` before reading the length: [2](#0-1) 

`extractBytes32Array` has no such `offset > words.length - 1` guard, and — more importantly for this analog — none of the three helpers cap `len` to any sane maximum. `len` comes from `words[offset].intValueSafe()`, i.e. an attacker-chosen 256-bit ABI word coerced into an `int`. A malicious contract caller can set this length field to a very large positive value (up to `Integer.MAX_VALUE`), causing `new byte[len][]` (or `new byte[len]` variants) to attempt an allocation of gigabytes of object-array header memory, exactly analogous to `gnu_special`'s crafted length field driving an oversized/negative allocation that crashes the process.

### Impact Explanation
An `OutOfMemoryError` is a JVM `Error`, not a checked `RuntimeException`; VM opcode/precompile dispatch code in the TVM interpreter that catches `Exception` (as is typical throughout `PrecompiledContracts`/`Program`) will not catch it, so the exception propagates out of the transaction-processing path. Because block/transaction execution happens on the node's core processing thread inside `Manager`'s block application flow, an uncaught `Error` here can crash or hang the node process serving that thread, denying service to the whole node — matching the "node crash or halt" impact bar in the validation criteria.

### Likelihood Explanation
This is reachable by any unprivileged account: any address can send a `TriggerSmartContract` transaction (or make a constant call) whose EVM bytecode issues a `CALL`/`STATICCALL` to the precompiled-contract address that uses `extractBytes32Array`, supplying call data with an oversized length word at the relevant offset. No special permission, stake, or witness/SR role is required — only the ability to broadcast a transaction or make an API call that triggers contract execution, which is exactly the "contract deployer / order placer / anonymous API client" reach specified in scope.

### Recommendation
Add the same bounds checks that already exist in `extractBytesArray`/`extractSigArray` to `extractBytes32Array` (validate `offset` against `words.length`), and additionally clamp/validate `len` in all three helpers against the actual remaining size of `data`/`words` (i.e., `len` must not imply reading past `data.length`) before allocating the destination arrays. Reject with a normal execution failure (return `Pair.of(false, ...)`) instead of allowing an unbounded allocation to reach the JVM.

### Proof of Concept
Deploy/trigger any smart contract whose bytecode `CALL`s the precompiled-contract address that dispatches to a precompile using `extractBytes32Array`, with call data encoding a very large value (e.g., `0x7FFFFFFF`) in the 32-byte word at the `offset` used as the array-length field, and enough trailing zero-padding to pass initial parsing. This forces `new byte[0x7FFFFFFF][]` to execute, which will attempt to allocate on the order of many gigabytes for the array's object header, producing an `OutOfMemoryError` during transaction execution.

**Note on verification limits:** I was not able to fully trace, within the remaining tool budget, exactly which precompiled contract (address) dispatches into `extractBytes32Array` at runtime (the call sites are in `PrecompiledContracts.java` but the exact `execute()` method invoking it was not retrieved before the iteration limit). The vulnerable helper method, its missing bounds check relative to its siblings, and the reachability of precompile execution from ordinary `TriggerSmartContract` transactions are confirmed by the cited code; the specific precompile name/address using this exact helper should be confirmed by grepping for `extractBytes32Array(` call sites in `PrecompiledContracts.java` in a follow-up session.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
