### Title
ValidateMultiSign TVM precompile authorizes with any permission (Owner/Witness/Active) by weight/threshold only, bypassing the Active-permission-type restriction enforced on the normal transaction path - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` precompiled contract lets any smart contract ask "does this set of ECDSA signatures satisfy account X's permission #Y?" and returns true purely based on `weight >= threshold`. Unlike every other place in java-tron that authorizes an action using an account's `Permission` (permission id ≠ 0), this precompile never checks that the referenced permission is of type `Active`, i.e. it skips the same class of trust-boundary check that the SeaweedFS bug skipped (validating the credential/signature but not the role's scope/trust policy).

### Finding Description
Every "official" TRON authorization path that resolves a `Permission` by id and then checks signature weight also enforces that non-owner permissions (`permissionId != 0`) are `PermissionType.Active` before trusting the weight calculation:

- `TransactionCapsule.checkPermission()` (used by both `validateSignature()` and `addSign()`) throws `PermissionException` if `permission.getType() != PermissionType.Active` when `permissionId != 0`, and additionally checks `checkPermissionOperations()`. [1](#0-0) 
- `TransactionUtil.getTransactionSignWeight()` (Wallet gRPC query) performs the identical `PermissionType.Active` + operations check. [2](#0-1) 
- `Wallet.getTransactionApprovedList()` performs the same check again. [3](#0-2) 

In contrast, `PrecompiledContracts.ValidateMultiSign.execute()` — reachable by any contract deployer/caller through the TVM opcode/precompile interface — takes an arbitrary `permissionId` supplied in the call data, fetches `account.getPermissionById(permissionId)`, and authorizes solely by summing `TransactionCapsule.getWeight(permission, recoveredAddr)` against `permission.getThreshold()`. It never checks `permission.getType()`: [4](#0-3) 

This means `permissionId = 1` (the account's `Witness` permission, intended solely to gate SR/witness-specific operations and typically held by separate, more operationally-exposed infrastructure) or `permissionId = 0` (the `Owner` permission) will satisfy `ValidateMultiSign` exactly like a properly scoped `Active` permission would, with no verification that the permission was ever meant to authorize the class of action the calling contract is gating. This is structurally the same bug class as the OIDC report: a "bearer" verification path (raw signature + permission id) authenticates against a role's raw key material and threshold without enforcing the scope/type restriction ("trust policy") that the canonical authorization path enforces.

### Impact Explanation
Any smart contract that relies on `ValidateMultiSign` (a documented TRON precompile used by wallets/custody/multisig DApps to verify off-chain approvals) to gate value-moving or privileged operations can be tricked into accepting authorization from an account's `Witness` permission slot, which is operationally meant only for witness/SR block-signing duties and is often configured with weaker, differently-scoped keys or delegated to different operators than the account's intended `Active` transactional keys. Because the precompile treats any resolvable `permissionId` identically, an attacker who compromises or otherwise obtains signatures valid under the account's Witness (or a narrowly-scoped Active) permission can force `ValidateMultiSign` to return `true` for authorization checks the DApp intended to restrict to a specific, properly-scoped Active permission — enabling unauthorized fund transfers or privileged actions gated by that check. This satisfies the "unauthorized account operation / theft of funds" bar since it directly affects any contract-mediated authorization built on this precompile.

### Likelihood Explanation
Reachable by a single, ordinary transaction: any account can deploy or call a contract that invokes the `ValidateMultiSign` precompile with an attacker-controlled `permissionId`, and the check silently succeeds for any permission type as long as key-weight/threshold is met — no special privilege, mining power, or trusted-role compromise is needed beyond obtaining signatures valid under *some* configured permission of the target account (which multisig/custody accounts commonly expose via delegated Witness or narrowly-scoped Active permissions).

### Recommendation
In `PrecompiledContracts.ValidateMultiSign.execute()`, mirror the checks already performed in `TransactionCapsule.checkPermission()` / `TransactionUtil.getTransactionSignWeight()`: reject (or explicitly require the caller to opt into) any `permissionId` whose resolved `Permission.getType() != PermissionType.Active` (except where `permissionId == 0`, i.e., Owner, is intentionally allowed), so the precompile enforces the same scope guarantees as the canonical transaction-signing path.

### Proof of Concept
1. Configure an account with an `Active` permission (id 2) intended to authorize only low-value operations, and a `Witness` permission (id 1) held by a separately-trusted operator.
2. Deploy a DApp/contract that calls `ValidateMultiSign(address, permissionId, dataHash, signatures)` expecting `permissionId=2` (the scoped Active permission) to gate a sensitive action.
3. An attacker who can produce signatures valid under permission id `1` (Witness) submits `permissionId=1` with valid Witness-key signatures meeting that permission's threshold. [4](#0-3) 
4. `ValidateMultiSign` returns `true` (no `PermissionType.Active` check performed), bypassing the scope restriction the DApp relied on, whereas the equivalent transaction-signature path (`TransactionCapsule.checkPermission`) would have rejected this exact scenario. [1](#0-0)
