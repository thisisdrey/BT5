### Title
Handshake re-key path accepts a new peer identity without verifying the claimed public key signed the message - (File: `stackslib/src/net/chat.rs`)

### Summary
`ConversationP2P::validate_handshake` only performs a signature check (`message.verify_secp256k1`) when the connection does **not yet** have a known public key for the peer. Once a public key is already on file for the connection, the function skips signature verification entirely and only checks that the self-reported address matches (and only for outbound connections). The subsequent call to `update_from_handshake_data` then unconditionally trusts and installs `handshake_data.node_public_key` as the peer's new identity — even though nothing proved the sender controls the private key for that new public key. This mirrors the analog bug class: a mapping (`neighbor connection -> trusted public key`) that is already bound is silently reassigned to a new value without verifying the party performing the reassignment is authorized to make that claim.

### Finding Description
`validate_handshake` in [1](#0-0)  branches on whether `self.connection.get_public_key()` is `None` or `Some`:

- `None` branch: calls `message.verify_secp256k1(&handshake_data.node_public_key)`, i.e. it cryptographically proves the sender controls the private key matching the claimed `node_public_key`.
- `Some(_)` branch: performs **no signature verification at all** — it only checks, for outbound connections, that the reported `addrbytes`/`port` match the socket address. For inbound connections, or when the reported address is `is_anynet()`, there is no check whatsoever. [2](#0-1) 

After `validate_handshake` returns `Ok`, `handle_handshake` calls `update_from_handshake_data`, which compares the new `pubk` to the currently stored key, sets `updated = true` if they differ, and unconditionally calls `self.connection.set_public_key(Some(pubk))` — regardless of whether the message was actually signed by that new key: [3](#0-2) 

If the re-keyed connection is outbound, the fabricated identity is also persisted to the on-disk `PeerDB` via `Neighbor::load_and_update` / `neighbor.save_update`: [4](#0-3) 

The doc-comment on `handle_handshake` claims "A handshake will only be accepted if we do not yet know the public key of this remote peer, or if it is signed by the current public key" [5](#0-4) , but the code does not actually enforce "signed by the current public key" — it enforces nothing at all once a key is already known.

Practical exploitation path: an attacker opens a connection and completes a first, honest handshake with key `A` (so `self.connection.get_public_key() == Some(A)`), then sends a second `Handshake` message on the same connection claiming `node_public_key = B` (an arbitrary key, e.g. belonging to a real, trusted neighbor) with an arbitrary/invalid signature. Since a key is already known, the message routes as unauthenticated (it doesn't match `A`) into `handle_unauthenticated_control_message` → `handle_handshake(authenticated=false)`, and `validate_handshake` takes the `Some(_)` branch which never checks the signature against `B` (or against `A`). The node accepts the claim and re-labels the connection's trusted identity as `B`, corrupting local trust state and, for outbound sessions, the persisted `PeerDB` record.

### Impact Explanation
This breaks the authentication invariant that a neighbor's recorded public key is always backed by a valid signature from that key. The corrupted binding is used for:
- Deciding whether future messages on the connection are "authenticated" (comparing against the now-attacker-controlled key), enabling the attacker to subsequently impersonate the claimed identity on that connection using their own signing key.
- Populating `NeighborAddress`/`Neighbor` records (`pubkey_hash`) that are gossiped through neighbor-walk handshake responses and inventory exchange, letting a forged identity binding propagate to other peers that later resolve `NeighborAddress` entries.
- Triggering `PeerDB::update_peer` / `insert_or_replace_peer` logic that drops StackerDB associations on key change [6](#0-5) , disrupting legitimate StackerDB replication state for that neighbor slot.

This falls into "unauthorized write to state" / "network-wide propagation of forged data" territory (an auth-gate that fails open on re-key), reachable by any unprivileged remote peer with a normal inbound TCP connection.

### Likelihood Explanation
Likelihood is moderate-to-high: it requires only two ordinary `Handshake` messages on a single connection, no cryptographic material belonging to the victim, and no special privileges — any peer that can open a p2p connection to a node can attempt it. The main precondition is that `disable_inbound_handshakes` is not set (default) and that a first handshake has already succeeded, both trivially satisfiable by the attacker.

### Recommendation
In the `Some(_)` branch of `validate_handshake`, require the incoming message to be verified against the **new** claimed `node_public_key` (proving possession of that key) before accepting a re-key, and/or require it be signed by the **currently known** public key to authorize a key rotation, matching the doc-comment's stated intent. Reject (or treat as a fresh, address-scoped) handshake attempts that fail this check rather than silently overwriting the trusted key.

### Proof of Concept
1. Attacker connects inbound to a target node and completes a normal `Handshake`/`HandshakeAccept` exchange using key `A`, so `self.connection.get_public_key() == Some(A)` on the target's `ConversationP2P` for this socket.
2. Attacker sends a second `Handshake` message on the same TCP connection with `handshake_data.node_public_key = B` (any key, e.g. copied from a known validator/signer's public key) and an arbitrary signature (not produced by `B`'s or `A`'s private key).
3. On the target, `validate_handshake` takes the `Some(_)` branch (`stackslib/src/net/chat.rs:1072-1091`), performs no signature check, and returns `Ok(())`.
4. `handle_handshake` calls `update_from_handshake_data`, detects `pubk (B) != cur_pubk (A)`, sets `updated = true`, and calls `self.connection.set_public_key(Some(B))` — the target now believes this connection/neighbor's identity is `B`, without any proof the attacker controls `B`'s private key.

    /// Validate a handshake request.
    /// Return Err(...) if the handshake request was invalid.
    fn validate_handshake(
        &mut self,
        local_peer: &LocalPeer,
        chain_view: &BurnchainView,
        message: &mut StacksMessage,
    ) -> Result<(), net_error> {
        let handshake_data = match message.payload {
            StacksMessageType::Handshake(ref mut data) => data.clone(),
            _ => panic!("Message is not a handshake"),
        };

        match self.connection.get_public_key() {
            None => {
                // if we don't yet have a public key for this node, verify the message.
                // if it's improperly signed, it's probably a poorly-timed re-key request (but either way the message should be rejected)
                message
                    .verify_secp256k1(&handshake_data.node_public_key)
                    .map_err(|_e| {
                        debug!(
                            "{:?}: invalid handshake: not signed with given public key",
                            &self
                        );
                        net_error::InvalidMessage
                    })?;
            }
            Some(_) => {
                // for outbound connections, the self-reported address must match socket address if we already have a public key.
                // (not the case for inbound connections, since the peer socket address we see may
                // not be the same as the address the remote peer thinks it has).
                // The only exception to this is if the remote peer does not yet know its own
                // public IP address, in which case, its handshake addrbytes will be the
                // any-network bind address (0.0.0.0 or ::)
                if self.stats.outbound
                    && (!handshake_data.addrbytes.is_anynet()
                        && (self.peer_addrbytes != handshake_data.addrbytes
                            || self.peer_port != handshake_data.port))
                {
                    // wrong peer address
                    debug!(
                        "{:?}: invalid handshake -- wrong addr/port ({:?}:{:?})",
                        &self, &handshake_data.addrbytes, handshake_data.port
                    );
                    return Err(net_error::InvalidHandshake);
                }
            }
        };
