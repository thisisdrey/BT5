## Analysis

The OpenVM bug's core pattern: a control flag (`is_buffer_start`) is decoded/available in the witness but never constrained to be checked before the chip performs a state-mutating action (a memory write). The prover is free to omit the check and the write proceeds unconditionally.

The closest local analog is in the Snowbridge outbound queue v2 delivery-receipt handling. The `DeliveryReceipt` decoded from a *verified* Ethereum event log carries a `success` field (and a `topic` field) that indicate whether the corresponding message actually executed successfully on Ethereum, but `Pallet::process_delivery_receipt` never inspects `receipt.success` (or `receipt.topic`) before paying out the relayer reward and clearing the `PendingOrder`. ### Title
Reward payout in `process_delivery_receipt` ignores the decoded `success` flag, settling relayer rewards for failed message deliveries - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`DeliveryReceipt::try_from` decodes the real `InboundMessageDispatched` event emitted by the Ethereum Gateway, which includes a `success: bool` field describing whether the message execution on Ethereum actually succeeded. `Pallet::process_delivery_receipt` only checks `receipt.gateway` and looks up the `PendingOrder` by `receipt.nonce`; it never reads or enforces `receipt.success` (or binds `receipt.topic`) before paying the reward and removing the order.

### Finding Description
`submit_delivery_receipt` verifies the event log/proof via `T::Verifier::verify`, decodes it into a `DeliveryReceipt` (which includes `success`), and forwards it to `process_delivery_receipt`: [3](#0-2) 

`process_delivery_receipt` then only validates the gateway address and resolves the reward account/order by nonce:
```rust
ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
...
let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
if order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
<PendingOrders<T>>::remove(nonce);
``` [4](#0-3) 

Nowhere is `receipt.success` read. `PendingOrder` stores only `nonce`, `fee`, `block_number` — it never captures the message `topic`, so `receipt.topic` is also decoded but discarded: [5](#0-4) 

This is directly analogous to the report's broken invariant: a field that exists precisely to gate an important state transition (`is_buffer_start` gating the memory write / `success` gating the reward settlement) is present in the decoded record but is never enforced by the code path that performs the state mutation. The required pivot text states message queues, bridge markers, receipts, and payout state must only advance "after decode, dispatch, execution, and settlement succeed atomically" — here settlement (reward payment + order removal) proceeds regardless of whether execution (dispatch on Ethereum) succeeded.

### Impact Explanation
Any relayer can submit a legitimately-proved `InboundMessageDispatched` event where `success == false` (i.e., the Ethereum-side execution of the outbound command reverted/failed) and still receive full payment of `order.fee`, and the `PendingOrder` is deleted as if delivery had fully succeeded. This decouples the reward economics from actual message execution outcome, letting relayers collect fees for messages that never took effect on Ethereum, silently violating the intended "settle exactly once … after execution … succeed" invariant for bridge reward payout state.

### Likelihood Explanation
This requires only an ordinary relayer (unprivileged, no admin/governance/validator role, no proof forgery) submitting a real, correctly proved event log where the emitted `success` field happens to be `false` (a normal outcome achievable by crafting an outbound command that reverts on the Ethereum Gateway, e.g. via insufficient gas/target revert) and calling the already-public `submit_delivery_receipt` extrinsic. No malicious peer, prover, or privileged actor is needed.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success` is `true`; for `success == false`, still remove/resolve the `PendingOrder` (to avoid replay) but skip payment, or route to a distinct penalty/no-reward path. Additionally consider binding `receipt.topic` to the message's committed topic stored in (or derivable from) the `PendingOrder`/`Messages` record, so a receipt cannot be matched to an unrelated nonce's order purely by numeric nonce collision across the field it decodes but never checks.

### Proof of Concept
1. A message is enqueued and processed by `do_process_message`, creating `PendingOrders[nonce] = { nonce, fee>0, block_number }`.
2. The command dispatched to Ethereum reverts on execution (e.g., recipient contract rejects the token/XCM payload), so the real Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer obtains a valid Merkle/receipt proof for this genuine event and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds (proof is real), `DeliveryReceipt::try_from` decodes `success=false` but `process_delivery_receipt` never inspects it: `order.fee > 0` still triggers `register_reward`, and `PendingOrders::remove(nonce)` fires `Event::MessageDelivered`.
5. Relayer is paid identically to a genuinely successful delivery despite `success == false`, confirmed by the existing test pattern in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` where only `gateway`/`nonce` are asserted and `success` is never varied to prove reward is gated on it.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
