### Title
Anyone can permanently destroy reward accrual by spamming `RewardsDistributor` index updates with small `dt`, truncating `_ratio` to zero while the timestamp still advances - (contracts/RewardsDistributor.sol)

### Summary
The external report describes Curve's `LiquidityGauge._checkpoint`, where the reward integral `rate * last_weight * dt / _working_supply` truncates to zero for small `dt`, so frequent calls permanently prevent accrual. Metronome's `RewardsDistributor` implements the identical accounting pattern with the same truncation: the token index increment `_ratio = _tokensAccrued.wadDiv(_totalSupply)` rounds to zero when `dt * speed` is small relative to `totalSupply`, yet `tokenStates[token_].timestamp` is unconditionally advanced to `block.timestamp`, permanently forfeiting the rewards accrued during that interval. Anyone can trigger this via the permissionless `updateBeforeMintOrBurn`/`updateBeforeTransfer`/`claimRewards` entry points (or via ordinary `DepositToken`/`DebtToken` mint, burn, and transfer hooks).

### Finding Description
`RewardsDistributor._calculateTokenIndex` computes the index delta:

```solidity
// contracts/RewardsDistributor.sol:201-212
uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
if (_deltaTimestamps > 0 && _speed > 0) {
    uint256 _totalSupply = token_.totalSupply();
    uint256 _tokensAccrued = _deltaTimestamps * _speed;
    uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
    _newIndex = (_supplyState.index + _ratio).toUint224();
    _newTimestamp = block.timestamp.toUint32();
}
```

`_updateTokenIndex` then stores both `_newIndex` and `_newTimestamp`. When `wadDiv` truncates `_ratio` to zero (i.e., `_tokensAccrued * 1e18 < _totalSupply`, or `< _totalSupply / 2` under half-up rounding), the index stays constant but the timestamp still moves forward — the rewards that should have accrued over `dt` are irrecoverably lost, exactly like the LiquidityGauge bug.

`updateBeforeMintOrBurn` is explicitly permissionless ("This function also may be called by anyone to update stored indexes", `contracts/RewardsDistributor.sol:173-180`), with no caller validation, no minimum-interval check, and no `onlyIfTokenExists` guard on the call path — only `tokenStates[token_].index > 0` is required. An attacker calls it every block with any `account_` argument (e.g., `address(0)` or themselves). Because each call resets `timestamp`, `dt` never exceeds one block time (2s on Optimism/Base), so `_ratio` stays zero whenever `speed * dt * 1e18 < totalSupply`. Since deposit/debt token supplies are large (e.g., millions of wei-18 units) and `speed` values per token are modest, this condition is realistic on deployed configuration. Additionally, every legitimate user mint/burn/transfer that happens to land on a small `dt` silently destroys the intervening accrual even without an attacker.

No modifier stops this: `nonReentrant` only covers `claimRewards`, `updateBeforeMintOrBurn`/`updateBeforeTransfer` have no reentrancy or access guard, and pause/shutdown flags do not gate the distributor.

### Impact Explanation
Permanent theft/freezing of unclaimed yield. Rewards emitted at `tokenSpeeds[token_]` per second are designed to accrue into `tokenStates[token_].index`; by keeping `dt` at one block, the attacker forces `_tokensAccrued` to truncate to zero while the timestamp checkpoint moves forward, so the reward budget for those seconds is never credited to anyone's index and effectively vanishes. DepositToken suppliers and DebtToken holders across every reward-bearing pool earn nothing while the attack runs — identical impact to the referenced Curve finding ("users will not earn interest").

### Likelihood Explanation
The attacker needs only an EOA and per-block gas; on the deployed L2 targets (Optimism, Base, Hemi, Swell per `deployments/*`) gas is cheap and blocks are ~2s, minimizing `dt`. No privileged role, oracle, or governance parameter manipulation is required. The condition `speed * 2 * 1e18 < totalSupply` holds whenever a token's emission rate is small relative to its supply, which is the normal configuration — reward speeds of ~0.001–0.1 tokens/sec against multi-thousand-token supplies truncate at single-block resolution even without half-up rounding. This is a medium/high likelihood griefing vector: the attacker gains nothing directly but destroys all stakers' yield at gas cost only, and a block builder can do it for free — the same "malicious miner" exploit scenario as the original report.

### Recommendation
- Accumulate unapplied accrual instead of discarding it: if `_ratio` truncates to zero, do not advance `tokenStates[token_].timestamp` (or carry the fractional remainder), so rewards accrue once `dt` is large enough.
- Alternatively, enforce a minimum accrual interval or compute index deltas on a coarser granularity than block timestamps.
- Restrict `updateBeforeMintOrBurn`/`updateBeforeTransfer` to registered pool tokens (they are already only invoked by `DepositToken`/`DebtToken`), removing the public spam surface.
- Bound `tokenSpeeds`/`totalSupply` configurations so `speed * minBlockTime * 1e18 > totalSupply`, per the original report's short-term recommendation.

### Proof of Concept
Hardhat-style sketch against a live `RewardsDistributor` (matching `test/RewardDistributor.test.ts` setup):

```ts
// Setup: rewardToken funded, governor set speed on msdToken (real DepositToken)
await rewardDistributor.updateTokenSpeed(msdToken.address, speed) // speed such that speed*1e18 < totalSupply
await depositToken.deposit(amount, alice.address) // initializes tokenStates index=INITIAL_INDEX

// Attack: Eve spams updateBeforeMintOrBurn every block
for (let i = 0; i < N; i++) {
  await rewardDistributor.updateBeforeMintOrBurn(msdToken.address, eve.address)
  await mine() // ~2s dt
}

// Assert: index never advanced despite N*2s elapsed
const {index, timestamp} = await rewardDistributor.tokenStates(msdToken.address)
expect(index).eq(INITIAL_INDEX)               // no accrual
expect(timestamp).eq(latestBlockTimestamp)    // checkpoint moved anyway

// Even after waiting, elapsed rewards for the spam window are lost permanently
await increaseTimeOfNextBlock(3600)
await rewardDistributor.updateBeforeMintOrBurn(msdToken.address, alice.address)
// alice's claimable only reflects the final 3600s — the N*2s window is gone
```

Expected: `index` remains `INITIAL_INDEX` throughout the spam loop while `timestamp` advances, demonstrating that `speed * dt` intervals below the truncation threshold are permanently forfeited — the direct analog of the LiquidityGauge integral griefing bug.
