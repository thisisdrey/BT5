### Title
Missing slippage protection in `ExchangeInjectContract`/`ExchangeWithdrawContract` allows front-run-induced fund loss for exchange liquidity providers - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
TRON's Bancor-style `Exchange` feature lets any account create a token-pair pool (`ExchangeCreateContract`) and inject/withdraw liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `ExchangeTransactionActuator`/`ExchangeCapsule.transaction()` to bound trade slippage, the inject/withdraw contracts carry no equivalent bound on the counterparty token amount that is computed dynamically from the current pool ratio at execution time.

### Finding Description
`ExchangeInjectActuator.execute`/`doValidate` computes `anotherTokenQuant` purely from the pool's live `firstTokenBalance`/`secondTokenBalance` ratio at the moment the transaction is applied: [1](#0-0)  and the validation path recomputes the same ratio-derived amount without any caller-supplied bound: [2](#0-1) . Symmetrically, `ExchangeWithdrawActuator` computes the amount of the paired token to be returned from the live ratio with no minimum-received bound: [3](#0-2)  and [4](#0-3) .

The protobuf definitions confirm neither contract carries a bound field, while `ExchangeTransactionContract` explicitly does: [5](#0-4) . This is the same root cause the external report describes for `HifiPool`: `addLiquidity`/`removeLiquidity`-equivalent operations compute the paired amount from the pool's current reserve ratio, and any pending trade that changes that ratio before the inject/withdraw transaction lands changes the outcome unfavorably for the liquidity-side transaction, with no on-chain parameter to reject an unfavorable execution.

### Impact Explanation
An exchange creator (the only account authorized to inject/withdraw, per the creator check at [6](#0-5) ) who submits an `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction has no on-chain guarantee about the resulting exchange of value. An unprivileged order placer can observe the pending transaction and submit an `ExchangeTransactionContract` trade (open to any account, `ExchangeCreateContract`/pools are permissionless) ahead of it to shift `firstTokenBalance`/`secondTokenBalance`, forcing the liquidity operation to execute at a materially worse ratio. This is a concrete mechanism for extracting value from the exchange creator without their consent — a theft-of-funds class impact — the same class of harm the external report attributes to `HifiPool`.

### Likelihood Explanation
Any account can create an exchange pool and become its creator, so this affects a broad set of potential victims, not a privileged role. The attack only requires ordinary permissionless capabilities: observing a pending transaction and submitting a competing `ExchangeTransactionContract` trade, both of which are standard, always-available actuator paths (`ExchangeTransactionActuator`). No special network position beyond ordinary transaction broadcasting/front-running is required, making this practically reachable whenever exchange pool balances are non-trivial and price-sensitive.

### Recommendation
Add caller-specified bound fields to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `ExchangeTransactionContract.expected`), e.g. `expected` / `min_another_token_quant` for inject and `min_receive` for withdraw, and enforce them in `ExchangeInjectActuator.execute`/`doValidate` and `ExchangeWithdrawActuator.execute`/`doValidate` by rejecting execution when the ratio-derived `anotherTokenQuant` falls outside the caller's specified bound, mirroring the existing `expected` check pattern used by `ExchangeTransactionActuator`.

### Proof of Concept
1. Account A creates an exchange pool via `ExchangeCreateContract` with balances `X:Y` and later becomes the sole creator authorized for inject/withdraw operations.
2. Account A broadcasts `ExchangeInjectContract` intending to inject token `X` in the expectation of receiving/pairing roughly `Y * quant / X` of the other token, based on the ratio at broadcast time.
3. Before A's transaction is applied, Account B (any address, no special privilege) broadcasts `ExchangeTransactionContract` trades against the same pool, shifting `firstTokenBalance`/`secondTokenBalance` significantly.
4. When A's `ExchangeInjectContract` executes, `ExchangeInjectActuator` recomputes `anotherTokenQuant` from the now-shifted ratio (`actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java:71-83`), causing A to inject a disadvantageous, unbounded amount of the paired token with no on-chain check to abort the operation — resulting in an unwanted, unrecoverable loss of value for A.
