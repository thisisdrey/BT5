This confirms the vulnerability claim. `BitMap256::cleanup_by_prefix` at [1](#0-0)  simply does `self.0.remove(&prefix)`, deleting the **entire** storage entry for that `word_pos` — all 256 bits (representing 256 distinct nonces sharing that prefix) at once, regardless of whether individual nonces within that word are still within their valid deadline.

The `cleanup_nonces` entrypoint only validates the *specific* nonce passed by the caller via `is_nonce_cleanable`, checking only that one nonce's `deadline`/`salt`: [2](#0-1) 

It then calls `cleanup_nonce_by_prefix` with only the 31-byte prefix (dropping the last byte / `bit_pos`), which wipes the whole word — including any other nonce (different `bit_pos`, same `word_pos`) that may still be valid and unused-but-committed, or even worse, **committed but not yet consumed**, clearing its "used" bit and making it usable again: [3](#0-2) [4](#0-3) [5](#0-4) 

This traces exactly the attack described: attacker commits N1 (word W, bit b1, short deadline) and N2 (word W, bit b2, long deadline) — both under the same salt/prefix. `MaybeLegacyNonces::commit` at [6](#0-5)  only checks legacy usage and delegates to `Nonces::commit`/`BitMap256::set_bit`, which sets individual bits within the 32-byte word — there's no protection preventing two nonces sharing a `word_pos` from being independently committed. Once N1 expires and a GarbageCollector calls `cleanup_nonces([N1])`, the entire word is deleted, clearing N2's still-committed bit even though N2's deadline hasn't passed. The attacker can then resubmit their original signed `MultiPayload` for N2 — since `commit_nonce` ( [7](#0-6)  checks `is_nonce_used` which is now `false` for N2 — it succeeds again, re-executing N2's intents (e.g., a transfer) a second time.

The existing tests confirm the semantics: `cleanup_multiple_nonces` in `tests/src/tests/defuse/accounts/nonces.rs` groups several nonces created with random `bit_pos` values and cleans them together, and `legacy_nonces_cant_be_cleared` confirms only legacy nonces are protected from cleanup — there is no protection against this word-sharing collision for regular (non-legacy) nonces. ### Title
Nonce cleanup by prefix deletes entire 256-bit word, allowing replay of still-valid nonces sharing the same prefix - ([File: contracts/defuse/core/src/engine/state/cached.rs], [crates/bitmap/src/b256.rs], [contracts/defuse/src/contract/garbage_collector.rs])

### Summary
`cleanup_nonces` validates only the single nonce's deadline/salt via `is_nonce_cleanable`, but the underlying `cleanup_nonce_by_prefix` -> `BitMap256::cleanup_by_prefix` removes the whole 31-byte-prefix storage word (256 bits) at once. Any other nonce that happens to share the same `word_pos` (same first 31 bytes, differing only in last byte `bit_pos`) — even one that is still within its valid deadline — has its "used" bit wiped, allowing the signer's still-valid `MultiPayload` to be replayed and its intents executed a second time.

### Finding Description
The broken binding: REPLAY_COUNT(N2) == 1 for all time, independent of GC activity on a different nonce N1 sharing N2's `word_pos`. This is violated because:

- `Nonces::commit`/`is_used` operate per-bit on a 256-bit word keyed by `word_pos` (`Nonce`'s top 31 bytes): [9](#0-8) .
- `cleanup_nonces` in `contracts/defuse/src/contract/garbage_collector.rs` checks cleanability of only the passed-in nonce (`deadline < now || invalid salt`), then strips the last byte and calls `State::cleanup_nonce_by_prefix(self, &account_id, prefix)`: [10](#0-9) .
- `CachedState::cleanup_nonce_by_prefix` forwards to `CachedAccount::cleanup_nonce_by_prefix` -> `Nonces::cleanup_by_prefix` -> `BitMap256::cleanup_by_prefix`, which does `self.0.remove(&prefix)`, unconditionally deleting the entire 32-byte bitmap word for that prefix: [1](#0-0) .
- Nothing checks whether other bits in that word are still "live" (committed with a valid, non-expired deadline) before deleting the word.

Attacker exploit: attacker signs and commits N1 = `word_pos || b1` with a short deadline, and N2 = `word_pos || b2` with a far-future deadline, both under the same currently-valid salt, in two separate `execute_intents` calls. After N1 expires, any GarbageCollector role holder (unprivileged from the attacker's perspective — background maintenance) legitimately calls `cleanup_nonces` targeting only N1. This wipes the entire `word_pos` entry, clearing N2's bit as a side effect. The attacker then resubmits their original signed payload for N2 (same signature, same still-valid deadline and salt) to `execute_intents`. `commit_nonce` sees `is_nonce_used == false` for N2 and succeeds, and N2's intents (e.g., a transfer) execute a second time.

None of the existing guards prevent this: `MaybeLegacyNonces::commit` only guards against legacy-map collisions, not intra-word collisions [6](#0-5) ; `is_nonce_cleanable` only checks the single passed nonce's own deadline/salt, never the other 255 bits sharing its word [11](#0-10) .

### Impact Explanation
A signer's already-executed, still-not-expired intent (e.g., a token transfer out of their Verifier balance) can be re-executed a second time using the exact same signature, moving funds twice from one signature — this matches the Critical category "one signed payload settling more than once." The blast radius affects any account/nonce pair where the attacker (or anyone controlling nonce generation client-side) chooses two nonces with colliding `word_pos` but different `bit_pos` and different deadlines, which is trivially achievable since nonces are attacker-chosen 32-byte values. Repeatable per account, once per GC cleanup event targeting a sibling nonce in the same word.

### Likelihood Explanation
The attacker needs no special privileges: they choose their own nonces (any 32-byte value under the currently valid salt), so they can trivially force two nonces to share a `word_pos`. They just need a GarbageCollector-role account (a normal, expected background maintenance actor) to run `cleanup_nonces` on the expired nonce — this is routine legitimate operation, not attacker-controlled, but the attacker can also wait for/encourage this to happen, or in principle hold the GC role's cleanup call as guaranteed maintenance behavior since expired nonces are supposed to be cleaned. This makes it fully feasible with low cost: two signed payloads plus waiting for routine cleanup.

### Recommendation
Do not delete the entire word on cleanup. Either: (1) clear only the individual bit for the specific nonce being cleaned (`clear_bit` instead of `remove`), losing the storage-reclamation benefit but preserving correctness; or (2) before removing the word, verify that all other bits in the word correspond to nonces that are also expired/invalid (requires tracking per-bit deadlines, which isn't currently stored, so this is not straightforward); or (3) redesign the nonce/prefix scheme so that cleanup can't affect unrelated live nonces, e.g., only allow full-word cleanup once all 256 bits are confirmed unused/expired via an explicit `all_bits_cleanable` check, or store deadlines in a way that lets a single word removal be gated on the max deadline across all committed bits in that word.

### Proof of Concept
`cargo test` in `near-workspaces` sandbox (in `tests/src/tests/defuse/accounts/nonces.rs`):
1. Create `user`, fetch `current_salt`.
2. Construct N1 = 31-byte `word_pos` (arbitrary/random) || `bit_pos = 0`, wrapped as a `SaltedNonce`/`ExpirableNonce` with `deadline = now + 3s`.
3. Construct N2 = same `word_pos` || `bit_pos = 1`, with `deadline = now + 1 hour`.
4. Sign and `execute_intents` for N1 (empty intents ok) and separately sign and execute a real transfer intent under N2 (e.g., ft_transfer moving balance to a recipient), assert recipient balance increases by `X`.
5. Assert `is_nonce_used(N1) == true` and `is_nonce_used(N2) == true`.
6. `sleep(3s)`; grant `Role::GarbageCollector` to some account; call `defuse_cleanup_nonces` with only `[(user, [N1])]`.
7. Assert `is_nonce_used(N1) == false` (expected) AND assert `is_nonce_used(N2) == false` (the bug — N2's bit was wiped even though its deadline is still far in the future).
8. Resubmit the *same original signed payload* for N2 to `execute_intents` again; assert it succeeds (no `NonceUsed` error).
9. Assert recipient's balance increased by `X` a second time (total `2X`), violating conservation/replay==1.

async fn cleanup_multiple_nonces(
    #[with(Env::builder().deployer_as_super_admin())]
    #[future(awt)]

    #[values(1, 10, 100)] nonce_count: usize,

    use futures::StreamExt;

    const CHUNK_SIZE: usize = 10;
    const WAITING_TIME: Duration = Duration::from_secs(3);
    let mut nonces = Vec::with_capacity(nonce_count);
    let (user, current_salt) = futures::try_join!(
        env.create_user().map(Ok),
        env.defuse.current_salt().into_future()
    )
    .unwrap();

    env.acl_grant_role(
        env.defuse.contract_id(),
        Role::GarbageCollector,
        user.account_id(),
    )
    .await
    .expect("failed to grant role");

    for start in (0..nonce_count).step_by(CHUNK_SIZE) {
        let end = (start + CHUNK_SIZE).min(nonce_count);

        let intents = join_all((start..end).map(|_| {
            // commit expirable nonce
            let deadline = current_timestamp + WAITING_TIME;
            let expirable_nonce = create_random_salted_nonce(current_salt, deadline, &mut rng);

            user.sign_defuse_message(
                env.defuse.contract_id(),
                expirable_nonce,
                deadline,
                DefuseIntents { intents: [].into() },
            )
        }))
        .await;

        env.defuse_simulate_and_execute_intents(env.defuse.contract_id(), intents)
            .await
            .unwrap();
    }

    sleep(WAITING_TIME).await;

    user.defuse_cleanup_nonces(

    .unwrap();

                            account_id: &user_id,
                            nonce: &n,
                        })
                        .await
                        .unwrap()
                }
            })
            .await
    );
}
