## Title
Unbounded per-address delegation index enables energy-exhaustion / node-DoS via `DelegatedResourceAccountIndexStore` prefix scan - (File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java)

### Summary
The reported Y2K bug class is "an attacker-controlled array grows without bound and a later function that iterates the full array can exceed the block gas limit." The closest reachable analog in java-tron is the `DelegatedResourceAccountIndexStore`/`DelegatedResourceAccountIndexCapsule` structure that tracks TRX delegation relationships (`FreezeBalanceActuator`/`DelegateResourceActuator`). Unlike the sibling structures that were hardened with explicit caps (`UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES = 32` [1](#0-0) , and `VoteWitnessProcessor`'s `MAX_VOTE_NUMBER` check [2](#0-1) ), there is **no limit** on the number of distinct addresses one account can delegate resources to/from.

### Finding Description
When an account delegates bandwidth/energy to a new receiver, `DelegateResourceActuator`/`FreezeBalanceActuator` call `DelegatedResourceAccountIndexStore.delegate()` (or the legacy `addToAccount`/`addFromAccount` list append) with no cap on distinct counterparties: [3](#0-2) 

The store persists each `(from,to)` pair as a separate key under `FROM_PREFIX`/`TO_PREFIX` (or `V2_FROM_PREFIX`/`V2_TO_PREFIX`): [4](#0-3) 

To reconstruct the index for a single address, `getIndex`/`getV2Index` perform a full `prefixQuery` over that address's namespace, load **every** matching entry into memory, deserialize it, sort it, and rebuild the full to/from lists: [5](#0-4) 

This method is invoked directly from unauthenticated wallet query surfaces reachable over HTTP/gRPC: `Wallet.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` [6](#0-5) , exposed via `RpcApiService.getDelegatedResourceAccountIndex`/`getDelegatedResourceAccountIndexV2` [7](#0-6)  and the HTTP servlet `GetDelegatedResourceAccountIndexServlet` [8](#0-7) .

Because the number of distinct delegation counterparties for a single address is not bounded (no analog to `UNFREEZE_MAX_TIMES`/`MAX_VOTE_NUMBER`), an attacker can cheaply generate thousands of fresh receiver addresses and issue many low-cost `DelegateResourceContract`/`FreezeBalanceContract` transactions from one account, each creating a new `(from,to)` key-pair entry. Each transaction only costs ordinary bandwidth/energy fees and a small amount of delegated balance — it does not require destroying value.

### Impact Explanation
Once the attacker has created a large number of distinct delegation relationships for one address, any client (including automated services, exchanges, or the attacker themselves) calling `getDelegatedResourceAccountIndex`/`V2` for that address forces the node to execute an unbounded `prefixQuery`, deserialize potentially many thousands of protobuf records, sort them, and serialize a large response — all synchronously inside the gRPC/HTTP handler thread. Repeated invocation of this query (which is free and requires no special permission) against one or more "poisoned" addresses can be used to exhaust node CPU/memory resources, degrading or halting the query service for legitimate clients (an availability impact on "an API the node can no longer serve"). This differs from the original Y2K report (which broke an actuator that changes state) in that here the affected operation is a read-only wallet API rather than a mutating actuator/consensus path — the underlying `delegate`/`unDelegate` writes themselves remain O(1), but the unbounded aggregation happens purely on the read/query side.

### Likelihood Explanation
Medium likelihood: creating many delegation entries costs only ordinary transaction fees (no large TRX lock required, since delegated resource amounts can be minimal) and can be automated at scale by any account holder; the query API is unauthenticated and can be hit as frequently as the node's rate limiter allows, and `RateLimiterServlet` on the HTTP path provides only general throttling, not a cap tied to result size.

### Recommendation
Impose a maximum number of distinct delegation counterparties per account (mirroring `UnfreezeBalanceV2Actuator.UNFREEZE_MAX_TIMES` and `VoteWitnessProcessor`'s `MAX_VOTE_NUMBER`) enforced in `DelegateResourceActuator`/`FreezeBalanceActuator` validation, and/or cap the number of entries returned/scanned by `getWithPrefix` (e.g., pagination or a hard result-count ceiling) so a single query cannot force an unbounded prefix scan.

### Proof of Concept
Not independently executed; based on static code review of:
- `FreezeBalanceActuator.delegateResource` [3](#0-2) 
- `DelegatedResourceAccountIndexStore.delegate`/`getWithPrefix` [9](#0-8) 
- `Wallet.getDelegatedResourceAccountIndexV2` exposed via gRPC/HTTP [10](#0-9) 

Conceptual PoC: (1) from address A, generate N (e.g., 50,000) fresh receiver addresses; (2) submit N `DelegateResourceContract` transactions from A delegating a minimal amount of bandwidth/energy to each; (3) repeatedly call `getDelegatedResourceAccountIndexV2(A)` via gRPC/HTTP and observe growing latency/CPU/memory as N increases, with no cap preventing arbitrarily large N. This was not verified by running the code in this session; confirmation would require deploying a local node and measuring resource consumption at scale.

  public void delegate(byte[] from, byte[] to, long time) {
    byte[] fromKey = Bytes.concat(FROM_PREFIX, from, to);
    DelegatedResourceAccountIndexCapsule toIndexCapsule =

  }

  public DelegatedResourceAccountIndexCapsule getIndex(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = get(address);
    if (indexCapsule != null) {
      return indexCapsule;
    }
    return getWithPrefix(FROM_PREFIX, TO_PREFIX, address);
  }

  public DelegatedResourceAccountIndexCapsule getV2Index(byte[] address) {
    return getWithPrefix(V2_FROM_PREFIX, V2_TO_PREFIX, address);
  }

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }
