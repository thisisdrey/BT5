## Title
Disabled-API access control bypass via extra path slash in `HttpApiAccessFilter` - (File: `framework/src/main/java/org/tron/core/services/filter/HttpApiAccessFilter.java`)

### Summary
The reported bug class is a path-normalization bypass: an extra `/` in the request URL defeats a security check that assumed a clean/normalized path. Java-tron's HTTP layer has a structurally analogous check: `HttpApiAccessFilter.isDisabled()` is the gatekeeper that enforces an operator-configured `disabledApiList` (blocking sensitive/expensive wallet HTTP endpoints such as `getaccount`, `triggerconstantcontract`, `estimateenergy`, etc. across `/wallet`, `/walletsolidity`, `/walletpbft`). It builds `endpoint = contextPath + getServletPath()`, calls `URI.create(endpoint).normalize()`, then extracts the API name with `endpoint.split("/")[2]` to compare against the disabled list. [1](#0-0) 

### Finding Description
`java.net.URI#normalize()` only resolves `.`/`..` segments; it does **not** collapse repeated `/` characters. If a client requests a path containing a doubled slash (e.g. `/wallet//getnowblock`), the resulting `endpoint` string after normalization is still `/wallet//getnowblock`. Splitting this string on `/` yields `["", "wallet", "", "getnowblock"]`, so `split("/")[2]` returns an empty string instead of `"getnowblock"`. The disabled-API name lookup therefore silently fails and `isDisabled()` returns `false` even though the request still targets the same logical endpoint. [2](#0-1) 

Notably, the existing test suite only validates the `..`-segment normalization path (which the code correctly handles via `URI.normalize()`), but never exercises the doubled-slash case — the same class of bypass documented in the external report (`http://host//../../etc/passwd`, and generically `http://host//<blocked-path>`). [3](#0-2) 

The remaining open question — and the reason I cannot fully validate exploitability — is whether the embedded Jetty server's URI/path-matching for the underlying `ServletHolder` mappings (which use exact string patterns like `/wallet/getnowblock`) will itself normalize/collapse the doubled slash before or after `HttpApiAccessFilter` runs. If Jetty's own path resolution collapses `//` prior to servlet dispatch, then `getServletPath()` would already return the canonical single-slash path and the filter's bug would be masked. If Jetty preserves the doubled slash through dispatch (which many servlet containers historically do, especially with lenient `UriCompliance`/`HttpCompliance` settings), the request reaches the intended servlet (`GetNowBlockServlet`, `GetAccountServlet`, `TriggerConstantContractServlet`, etc.) while `isDisabled()` returns `false`, fully bypassing the operator's block. I was not able to confirm the exact Jetty version's default `UriCompliance` behavior for this project from the code I could inspect, so this must be verified empirically (or via a Devin session with full repo/build access) before treating it as a confirmed exploit.

### Impact Explanation
`disabledApiList` is an operator-facing safety control used to turn off HTTP endpoints that are resource-intensive (`triggerconstantcontract`, `estimateenergy`), privacy-sensitive (shielded-note scanning endpoints), or otherwise undesired on a given node (e.g. solidity/PBFT read nodes disabling costly `wallet` calls). A confirmed bypass would let an anonymous HTTP client re-enable access to endpoints an operator explicitly disabled, undermining defense-in-depth on public-facing full/solidity/PBFT nodes, potentially exposing endpoints intended to be turned off for DoS-mitigation or policy reasons. This does not itself amount to fund theft or consensus compromise, so, assuming the bypass is confirmed reachable through Jetty, the severity would sit at Medium rather than High/Critical.

### Likelihood Explanation
Any unauthenticated HTTP client can craft the request with a doubled `/`; no privileged access or special conditions are required. Likelihood of the code-level flaw existing is high (confirmed by reading the `split("/")[2]` logic), but real-world exploitability additionally depends on Jetty's request-path handling not collapsing the doubled slash before dispatch — this part is unverified.

### Recommendation
- In `HttpApiAccessFilter.isDisabled()`, collapse consecutive slashes (e.g. `endpoint.replaceAll("/+", "/")`) before/after `URI.normalize()`, or better, split on `/+` (`endpoint.split("/+")`) instead of `/` so that any number of repeated slashes cannot produce empty segments that shift the array index.
- Alternatively, compare against `disabledApiList` using the last non-empty path segment (`request.getServletPath()` lower-cased, stripped of any leading/trailing slashes) rather than a fixed-index `split` result.
- Add a regression test mirroring `testIsDisabled` in `HttpApiAccessFilterTest.java` that specifically covers double/triple-slash inputs (`/wallet//getnowblock`, `//wallet/getnowblock`) to prevent regression. [1](#0-0) 

### Proof of Concept
1. Configure a node with `disabledApiList = ["getnowblock"]` (as done in `HttpApiAccessFilterTest`). [4](#0-3) 
2. Send `GET /wallet/getnowblock` → correctly blocked with `{"Error":"this API is unavailable due to config"}`.
3. Send `GET /wallet//getnowblock` (double slash) → if Jetty preserves the doubled slash through servlet dispatch, `getServletPath()` returns a value containing `//`, causing `isDisabled()`'s `split("/")[2]` to evaluate to `""` instead of `"getnowblock"`, so the filter allows the request through to `GetNowBlockServlet`.
4. Repro of the internal logic can be verified directly by unit-testing `isDisabled("/wallet//getnowblock")` the same way `testIsDisabled` already tests `"/wallet/a/../b/../getnowblock"`. [3](#0-2) 

**Caveat:** I could not confirm within this analysis whether Jetty's servlet dispatch in this project preserves the double slash all the way to `getServletPath()` (this depends on the embedded Jetty version's default `UriCompliance` settings, which I could not fully verify from the indexed code). This should be confirmed with a live test (e.g., via a Devin session that can run the actual server) before treating this as a fully proven, end-to-end exploitable vulnerability rather than a latent logic flaw in the filter's string-parsing.

        String endpoint = contextPath + ((HttpServletRequest) request).getServletPath();

  private boolean isDisabled(String endpoint) {
    boolean disabled = false;

    try {
      endpoint = URI.create(endpoint).normalize().toString();
      List<String> disabledApiList = CommonParameter.getInstance().getDisabledApiList();
      if (!disabledApiList.isEmpty()) {
        disabled = disabledApiList.contains(endpoint.split("/")[2].toLowerCase(Locale.ROOT));
      }
    } catch (Exception e) {
      logger.warn("check isDisabled except, endpoint={}, {}", endpoint, e.getMessage());
    }

    return disabled;
  }
