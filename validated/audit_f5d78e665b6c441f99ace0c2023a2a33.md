### Title
Relay control messages trust attacker-supplied `RelayFromAddr` without verifying it matches the authenticated sender - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` derive the relay's claimed VPN identity (`from`, `relayFrom`) directly from attacker-controlled fields inside a `NebulaControl` message (`m.RelayFromAddr`/`m.OldRelayFromAddr`), but never check that this claimed address actually equals `h.vpnAddrs[0]`, the VPN address of the tunnel peer that cryptographically sent the message. This is the same bug class as the `SecuritizeSwap::buy` finding: the code validates that a claimed identity is well-formed/known, but never validates that the authenticated caller (`msg.sender` / the Noise-tunnel peer `h`) is actually that identity.

### Finding Description
`HandleControlMsg` is called with `h *HostInfo`, which is the already-authenticated peer whose established, encrypted tunnel delivered the control message [1](#0-0) . The message body itself carries `RelayFromAddr`/`RelayToAddr` (or the v1 equivalents `OldRelayFromAddr`/`OldRelayToAddr`), which are simply unmarshalled and converted with `protoAddrToNetAddr`/binary decoding — fields fully controlled by whoever sent the packet [2](#0-1) .

In `handleCreateRelayRequest`, `from := protoAddrToNetAddr(m.RelayFromAddr)` is used as the identity "on behalf of" which relay state is created, checked only against the *local* node's own addresses (self-check) and the target check — never against `h.vpnAddrs[0]` (the actual sender) [3](#0-2) . Because `from` is never required to equal `h.vpnAddrs[0]`, an authenticated but malicious peer `h` can send a `CreateRelayRequest` claiming `RelayFromAddr` = some *other*, legitimate victim host's VPN address. The receiving node will then call `AddRelay(...)` and build relay state (`Established`/`Requested`) for that victim address and reply with a `CreateRelayResponse` addressed as if that victim had actually asked for a relay [4](#0-3) .

Similarly, `handleCreateRelayResponse` calls `rm.EstablishRelay(h, m)`, matching purely by `InitiatorRelayIndex`/`ResponderRelayIndex` from the message and then using `relayFrom`/`relayTo` (again derived from message fields) to notify a third peer, without re-verifying those addresses against `h`'s authenticated identity [5](#0-4) .

This mirrors the `SecuritizeSwap::buy` pattern exactly: the contract checked `isInvestor(_senderInvestorId)` (is the ID valid/known) but never checked that `msg.sender` corresponds to `_senderInvestorId`. Here, nebula checks that `from`/`target` are syntactically valid addresses and applies self/target-ownership checks, but never checks that the claimed `from` equals the cryptographically verified sender `h.vpnAddrs[0]`.

### Impact Explanation
An authenticated-but-malicious mesh peer (one with a valid, CA-signed cert of its own — no special privilege required beyond normal mesh membership) can forge relay-establishment control messages that misattribute relay ownership to arbitrary other VPN addresses. This can pollute a relay's `relayState`/`HostMap.Relays` bookkeeping for hosts that never requested a relay, potentially causing legitimate relay traffic for the victim to be redirected, disrupted, or associated with attacker-controlled relay indices — a remote state-poisoning condition in the relay subsystem, reachable purely from the encrypted control channel without needing to compromise the victim's certificate.

### Likelihood Explanation
Any node holding a valid cert signed by the same CA pool can reach this code path simply by establishing a normal tunnel and sending a `Control`-type `NebulaControl_CreateRelayRequest`/`Response` message with a forged `RelayFromAddr`. No malicious lighthouse, no privileged relay role, and no valid-certificate-holder impersonation of the victim's cert is required — only crafting the message body, which is attacker-controlled plaintext protobuf content inside the (attacker's own) encrypted tunnel.

### Recommendation
In `handleCreateRelayRequest` and `handleCreateRelayResponse`, require that the claimed `from`/`relayFrom` address in the message equals `h.vpnAddrs[0]` (the cryptographically authenticated VPN address of the sending peer) whenever the peer is acting as the terminal/initiator of the relay, rejecting/logging mismatches instead of trusting the message-supplied address.

### Proof of Concept
Not independently executed against a live instance in this analysis; the vulnerability is demonstrated structurally by code inspection: `handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl)` uses `from := protoAddrToNetAddr(m.RelayFromAddr)` and never asserts `from == h.vpnAddrs[0]` before calling `AddRelay` [3](#0-2) , so a peer `h` with VPN address `A` can send a request with `RelayFromAddr = B` (a third host's address) and the target will build relay state as if `B` requested it.

**Uncertainty note:** I could not fully trace, within this session, every call site that feeds decrypted control-message bytes into `HandleControlMsg` (e.g. the exact dispatch in `outside.go`/`inside.go` that decrypts and derives `h`) to double-check whether some upstream code already enforces the `from == h.vpnAddrs[0]` invariant elsewhere before reaching `relay_manager.go`. Given the index/size limits on visible file contents, I recommend a Devin session with full repo access to confirm there is no such check upstream before treating this as fully verified.

func (rm *relayManager) handleCreateRelayResponse(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	relayFrom := protoAddrToNetAddr(m.RelayFromAddr)
	relayTo := protoAddrToNetAddr(m.RelayToAddr)
	rm.l.Info("handleCreateRelayResponse",
		"relayFrom", relayFrom,
		"relayTo", relayTo,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"responderRelayIndex", m.ResponderRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	relay, err := rm.EstablishRelay(h, m)
	if err != nil {
		rm.l.Error("Failed to update relay for relayTo", "error", err)
		return
	}
	// Do I need to complete the relays now?
	if relay.Type == TerminalType {
		return
	}
	// I'm the middle man. Let the initiator know that the I've established the relay they requested.
	peerHostInfo := rm.hostmap.QueryVpnAddr(relay.PeerAddr)
	if peerHostInfo == nil {
		rm.l.Error("Can't find a HostInfo for peer", "relayTo", relay.PeerAddr)
		return
	}
	peerRelay, ok := peerHostInfo.relayState.QueryRelayForByIp(relayTo)
	if !ok {
		rm.l.Error("peerRelay does not have Relay state for relayTo", "relayTo", peerHostInfo.vpnAddrs[0])
		return
	}
	switch peerRelay.State {
	case Requested:
		// I initiated the request to this peer, but haven't heard back from the peer yet. I must wait for this peer
		// to respond to complete the connection.
	case PeerRequested, Disestablished, Established:
		peerHostInfo.relayState.UpdateRelayForByIpState(relayTo, Established)
		resp := NebulaControl{
			Type:                NebulaControl_CreateRelayResponse,
			ResponderRelayIndex: peerRelay.LocalIndex,
			InitiatorRelayIndex: peerRelay.RemoteIndex,
		}

		peer := peerHostInfo.vpnAddrs[0]
		if v == cert.Version1 {
			if !peer.Is4() {
				rm.l.Error("Refusing to CreateRelayResponse for a v1 relay with an ipv6 address",
					"relayFrom", peer,
					"relayTo", relayTo,
					"initiatorRelayIndex", resp.InitiatorRelayIndex,
					"responderRelayIndex", resp.ResponderRelayIndex,
					"vpnAddrs", peerHostInfo.vpnAddrs,
				)
				return
			}

			b := peer.As4()
			resp.OldRelayFromAddr = binary.BigEndian.Uint32(b[:])
			b = relayTo.As4()
			resp.OldRelayToAddr = binary.BigEndian.Uint32(b[:])
		} else {
			resp.RelayFromAddr = netAddrToProtoAddr(peer)
			resp.RelayToAddr = m.RelayToAddr
		}

		msg, err := resp.Marshal()
		if err != nil {
			rm.l.Error("relayManager Failed to marshal Control CreateRelayResponse message to create relay", "error", err)
			return
		}
		f.SendMessageToHostInfo(header.Control, 0, peerHostInfo, msg, make([]byte, 12), make([]byte, mtu))
		rm.l.Info("send CreateRelayResponse",
			"relayFrom", peer,
			"relayTo", relayTo,
			"initiatorRelayIndex", resp.InitiatorRelayIndex,
			"responderRelayIndex", resp.ResponderRelayIndex,
			"vpnAddrs", peerHostInfo.vpnAddrs,
		)
	}
}

func (rm *relayManager) handleCreateRelayRequest(v cert.Version, h *HostInfo, f *Interface, m *NebulaControl) {
	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
			case Disestablished:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.
					logMsg.Error("Existing relay mismatch with CreateRelayRequest",
						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
				}
				// Mark the relay as 'Established' because it's safe to use again
				h.relayState.UpdateRelayForByIpState(from, Established)
			case PeerRequested:
				// I should never be in this state, because I am terminal, not forwarding.
				logMsg.Error("Unexpected Relay State found",
					"existingRemoteIndex", existingRelay.RemoteIndex,
					"state", existingRelay.State)
			}
		} else {
			_, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
			if err != nil {
				logMsg.Error("Failed to add relay", "error", err)
				return
			}
		}

		relay, ok := h.relayState.QueryRelayForByIp(from)
		if !ok {
			logMsg.Error("Relay State not found", "from", from)
			return
		}

		resp := NebulaControl{
			Type:                NebulaControl_CreateRelayResponse,
			ResponderRelayIndex: relay.LocalIndex,
			InitiatorRelayIndex: relay.RemoteIndex,
		}

		if v == cert.Version1 {
			b := from.As4()
			resp.OldRelayFromAddr = binary.BigEndian.Uint32(b[:])
			b = target.As4()
			resp.OldRelayToAddr = binary.BigEndian.Uint32(b[:])
		} else {
			resp.RelayFromAddr = netAddrToProtoAddr(from)
			resp.RelayToAddr = netAddrToProtoAddr(target)
		}

		msg, err := resp.Marshal()
		if err != nil {
			logMsg.Error("relayManager Failed to marshal Control CreateRelayResponse message to create relay", "error", err)
		} else {
			f.SendMessageToHostInfo(header.Control, 0, h, msg, make([]byte, 12), make([]byte, mtu))
			rm.l.Info("send CreateRelayResponse",
				"relayFrom", from,
				"relayTo", target,
				"initiatorRelayIndex", resp.InitiatorRelayIndex,
				"responderRelayIndex", resp.ResponderRelayIndex,
				"vpnAddrs", h.vpnAddrs,
			)
		}
		return
