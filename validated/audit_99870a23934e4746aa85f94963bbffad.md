### Title
Missing slippage protection in `Pool.swap` lets oracle-priced swaps execute at stale/moved prices - ([File: contracts/Pool.sol])

### Summary
`Pool.swap()` values both synthetic tokens via the external `MasterOracle` at execution time, but exposes only `(syntheticTokenIn_, syntheticTokenOut_, amountIn_)` — there is no `minAmountOut`/`maxAmountIn`/deadline parameter. A user who signs a swap transaction therefore has no bound on the output amount: if the oracle price of either token moves between signing and mining (normal market drift, oracle update rounds, or same-transaction price manipulation where the oracle reads manipulable inputs), the victim receives fewer synthetic tokens than quoted, with no revert.

### Finding Description
`Pool.swap` burns `amountIn_` of `syntheticTokenIn_` and mints `syntheticTokenOut_` at whatever rate `quoteSwapOut` returns in that same block:

```solidity
// contracts/Pool.sol:642-671
function swap(
    ISyntheticToken syntheticTokenIn_,
    ISyntheticToken syntheticTokenOut_,
    uint256 amountIn_
) external override whenNotShutdown nonReentrant ... {
    ...
    syntheticTokenIn_.burn(_msgSender, amountIn_);
    (_amountOut, _fee) = quoteSwapOut(syntheticTokenIn_, syntheticTokenOut_, amountIn_);
    if (_fee > 0) {
        syntheticTokenOut_.mint(_poolRegistry.feeCollector(), _fee);
    }
    syntheticTokenOut_.mint(_msgSender, _amountOut);
}
```

`quoteSwapOut` calls `masterOracle().quote(assetIn, assetOut, amountIn)` [1](#0-0) , and `IMasterOracle` is a free-standing external oracle (`quoteTokenToUsd`/`quoteUsdToToken`/`quote`) [2](#0-1) . There is no freshness bound, no caller-supplied expected rate, and no revert path on unfavorable prices. Contrast with the rest of the codebase, which consistently treats oracle-priced/AMM-priced operations as requiring slippage params: `SmartFarmingManager._swap` takes `amountOutMin_` [3](#0-2) , and the cross-chain leverage/flash-repay flows expose `swapAmountOutMin_`, `depositAmountMin_`, `bridgeTokenAmountMin_`, `repayAmountMin_` [4](#0-3) . Only the direct `Pool.swap` path lacks this protection (the same applies in principle to `liquidate`, which has no min-seize bound, though a liquidator can compute the quote in the same tx more easily).

Since swaps mint/burn synths, the exchange rate directly determines how much debt-relevant asset the user holds; an unfavorable execution is a straight loss of user funds and can be forced by an attacker whenever the underlying oracle input is movable within the transaction (e.g., a vault-share-priced feed or any spot-priced component used by the deployed `MasterOracle`).

### Impact Explanation
A victim swapper's `syntheticTokenIn_` is burned unconditionally at line 660 before the output is computed, and `_amountOut` is minted at whatever the oracle returns in that block. If the price of `syntheticTokenOut_` rose (or `syntheticTokenIn_` fell) after the victim signed, they receive materially less synth than quoted — a direct, unbounded loss proportional to the price movement, with no user-side protection. Where oracle inputs are manipulable same-tx, an attacker can front-run the swap to worsen the rate and capture the difference by swapping in the opposite direction.

### Likelihood Explanation
`swap` is a public entry point (guarded only by `whenNotShutdown`, `nonReentrant`, token existence checks, and `isSwapActive`) [5](#0-4) . Any mempool delay or oracle price update between signing and inclusion triggers the issue organically; if the deployed `MasterOracle` reads a manipulable feed, extraction is actively exploitable. Severity is Medium, matching the referenced bug class (loss limited to price drift, not arbitrary theft).

### Recommendation
Add caller-controlled bounds to `IPool.swap`, e.g. `swap(syntheticTokenIn_, syntheticTokenOut_, amountIn_, amountOutMin_)` (and/or a deadline), reverting with a dedicated error when `_amountOut < amountOutMin_` — mirroring the `amountOutMin_` pattern already used in `SmartFarmingManager._swap`.

### Proof of Concept
```solidity
// Foundry fork-style sketch (targets deployed Pool + MasterOracle)
function test_swapNoSlippage() external {
    // victim holds msUSD, wants msETH at current oracle rate
    uint256 amountIn = 100_000e18;
    deal(address(msUSD), victim, amountIn);

    // expected output at signing time
    (uint256 quotedOut,) = pool.quoteSwapOut(msUSD, msETH, amountIn);

    // --- price of msETH oracle feed moves up ~5% before victim tx mines ---
    // (e.g., oracle round update, or same-tx manipulation of a
    //  manipulable feed component used by MasterOracle)
    masterOracle.movePriceUp(address(msETH)); // model: feed now returns +5%

    vm.prank(victim);
    (uint256 amountOut,) = pool.swap(msUSD, msETH, amountIn);

    // victim's msUSD is burned; he receives ~5% less than quoted,
    // and the tx does not revert because there is no minOut check
    assertLt(amountOut, quotedOut * 95 / 100);
}
```
The PoC demonstrates that `swap` executes at whatever rate the oracle returns at mining time with no bound, reproducing the "oracle-priced deposit/swap without slippage" bug class on Metronome's `Pool.swap`.
