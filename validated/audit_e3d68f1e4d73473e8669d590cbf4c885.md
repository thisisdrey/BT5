### Title
Dust transfer griefing fills victim's per-account token list to `MAX_TOKENS_PER_USER`, blocking new collateral deposits and borrows - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Analogous to the Avahi bug where `CLIENTS_MAX` bookkeeping existed but `server_work()` appended clients unconditionally, Metronome's per-account token list is a bounded resource that an unprivileged attacker can fill on behalf of any victim. `DepositToken._transfer()` appends the deposit token to the *recipient's* `depositTokensOfAccount` list whenever the recipient's prior balance is zero, and `Pool.addToDepositTokensOfAccount()` enforces `MAX_TOKENS_PER_USER = 30` by reverting once the combined deposit + debt token count hits the cap. Because any EOA can `transfer()` dust amounts of every listed `DepositToken` to an arbitrary victim, the attacker can permanently occupy all 30 slots with worthless dust positions, causing every subsequent `deposit` of a new collateral type and every `issue`/`mint` of a new debt token for that victim to revert with `UserReachedMaxTokens`.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER = 30` caps `debtTokensOfAccount.length + depositTokensOfAccount.length` per account (`contracts/Pool.sol:79`, `contracts/Pool.sol:143-148`).
- `DepositToken._transfer()` calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's balance transitions `0 → >0` (`contracts/DepositToken.sol:518-520`), with no opt-in and no minimum amount.
- `DepositToken._mint`/`deposit` do the same on the `0 → >0` transition (`contracts/DepositToken.sol:486-488`), so a victim cannot deposit a *new* collateral type once the cap is reached — `addToDepositTokensOfAccount` reverts.
- `DebtToken` mint paths similarly call `addToDebtTokensOfAccount`, so borrowing a new synthetic also reverts.
- Removal only happens when a balance returns to exactly zero (`contracts/DepositToken.sol:523-525`, `removeFromDebtTokensOfAccount` on repay-all). The attacker controls the triggering deposits; the victim must spend gas per dust token to push balances to zero, and the attacker can re-fill slots by front-running the victim's next deposit with fresh dust transfers, keeping the victim permanently capped at dust positions.

Attack steps:
1. Attacker deposits a minimal amount of each of the pool's ~N listed collaterals to acquire dust balances of each `DepositToken`.
2. For each `DepositToken dt_i`, call `dt_i.transfer(victim, 1 wei)` (or the smallest non-zero amount). Each call executes `addToDepositTokensOfAccount(victim)` and consumes one slot, no victim consent needed.
3. Repeat with any available deposit tokens (and, where the attacker can push debt — e.g., via dust positions — debt-token slots) until `debtTokensOfAccount.length + depositTokensOfAccount.length == 30`.
4. Any subsequent `pool`-driven `depositToken.deposit(victim, ...)` of a *new* collateral, `debtToken.issue`/`mint` of a *new* synthetic, or incoming `transfer` of a new deposit token to the victim reverts with `UserReachedMaxTokens`.

### Impact Explanation
- A victim with an open unhealthy-or-borderline position cannot add a new collateral type to restore health; their position becomes liquidatable and liquidators seize collateral — indirect but direct-attributable loss of user funds.
- New entrants can be blocked from depositing any collateral or borrowing at all (temporary freezing of protocol usage for that account), and existing users can be blocked from diversifying collateral or opening new debt positions indefinitely, since the attacker can re-grief after each victim cleanup.
- The `MAX_TOKENS_PER_USER` guard exists, but — exactly like the ignored `CLIENTS_MAX` in the report — nothing stops an unprivileged third party from exhausting the per-account quota on the victim's behalf.

### Likelihood Explanation
- Fully unprivileged: only requires ERC-20-style `transfer` calls on already-whitelisted `DepositToken`s; cost is dust collateral plus gas.
- Persistence: grief can be renewed indefinitely by monitoring the victim's list and re-filling freed slots, making remediation via self-cleanup unreliable under adversarial mempool conditions (attacker can front-run the victim's deposit transaction).
- Constrained by the number of listed deposit/debt tokens in a pool (cap is 30 combined), so effectiveness depends on pools having enough listed tokens for the attacker to occupy; on pools with many collaterals this is cheap.

### Recommendation
- Do not add entries to a recipient's `depositTokensOfAccount` on inbound `transfer`/`transferFrom` unless the recipient has opted in, or require a minimum transfer amount that makes dust griefing economically infeasible.
- Alternatively, decouple the accounting list from transfers (e.g., only track tokens the account explicitly deposited via `deposit()`), or allow a permissionless "sweep dust / force-remove" path on the `Pool` so a victim can evict unsolicited entries without transferring tokens.
- Consider skipping the `add` call (and the cap revert) for transfers below a configurable dust threshold.

### Proof of Concept
Hardhat (TypeScript, against the existing test setup in `test/Pool.test.ts`):

```ts
// Assumes `pool` is deployed with >=2 listed DepositTokens (dt0..dt29) and attacker holds dust of each.
// Victim starts with 0 entries.
const victim = bob.address;

// 1. Attacker fills victim's list with dust transfers
for (const dt of allDepositTokens.slice(0, 30)) {
  await dt.connect(attacker).transfer(victim, 1); // 1 wei each
}
expect(await pool.getDepositTokensOfAccount(victim)).to.have.lengthOf(30);

// 2. Victim tries to deposit a NEW collateral type -> reverts
const newCollateral = await deployDepositToken(...); // listed, victim balance 0
await pool.connect(governor).addDepositToken(newCollateral.address);
await underlying.connect(victim).approve(newCollateral.address, amount);
await expect(newCollateral.connect(victim).deposit(amount))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3. Even an inbound transfer of any new deposit token reverts
const dt31 = allDepositTokens[30];
await expect(dt31.connect(attacker).transfer(victim, 1))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

A Foundry fork variant: deploy `Pool` via the existing fixture, impersonate each `DepositToken`'s holder or mint dust via `deal`, execute step 1 against a mainnet pool on a fork (`forge test --fork-url`), then assert `deposit`/`issue` revert with `UserReachedMaxTokens()`.
