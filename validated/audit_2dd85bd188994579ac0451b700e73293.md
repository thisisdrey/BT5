### Title
Reentrancy in `redeem` via post-transfer accounting update allows `assets` state to be inflated and drained beyond backing - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
`redeem` (and its identical twins in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`) burns the caller's shares and transfers the underlying asset to `recipient` *before* updating the `assets` accounting variable, i.e. `(try! (send-underlying inkind recipient))` happens before `(var-set assets (- current-assets inkind))`. This mirrors the `collectFees` reentrancy defect in the report: state that gates further withdrawals is only committed after an external, potentially-controllable transfer call, so a reentrant call sees stale accounting.

### Finding Description
`redeem` in `mainnet/contracts/vault/v0-vault-usdc.clar` (and sibling vaults) is: [1](#0-0) 

The sequence is:
1. Capture `current-assets` and `available-assets` (both derived from `var-get assets`) at the top of the call.
2. `ft-burn?` the caller's shares (state update for supply happens here).
3. `send-underlying inkind recipient` — this performs `(contract-call? .usdc transfer inkind current-contract account none)`: [2](#0-1) 
4. Only *after* the transfer returns does the vault do `(var-set assets (- current-assets inkind))`.

Because `send-underlying` invokes an external SIP-010 `transfer` on the configured underlying-asset contract, and because in Clarity `contract-call?` fully executes the callee before returning (the callee can itself call back into this vault, e.g. `redeem` again, before step 4 runs), a reentrant call into `redeem` observes the *pre-decrement* `assets` variable. `total-assets-preview`/`convert-to-assets-preview` (used to compute `inkind`) and `get-available-assets` are all derived from this same `assets` var: [3](#0-2) 

While `ft-burn?` does correctly reduce the caller's share balance before the external call (limiting how many times the *same* shares can be redeemed), the `assets` bookkeeping variable — which represents the vault's backing and is used to compute `available-assets` / `ERR-INSUFFICIENT-LIQUIDITY` and exchange-rate previews for every other user's deposits/redeems — remains unchanged during the reentrant window. A caller who controls (or has a whitelisted callback hook on) the underlying token, or who can arrange for the `recipient` to be a contract that receives a transfer callback, can re-enter `redeem` (or `deposit`/other vault ops gated on the same `assets` var) while `assets` still reflects un-decremented backing, allowing liquidity/accounting checks (`ERR-INSUFFICIENT-LIQUIDITY`, exchange-rate previews) to pass using assets that have already been logically committed to the outer call's payout. This is a direct check-effects-interaction violation of the same class as the reported `collectFees` bug: the accounting mutation that should occur before the external call is deferred to after it.

Unlike the mainnet SIP-010 tokens listed (`usdc`, `usdh`, `sbtc`, `ststx`, `stx`) which today are simple fungible-token wrappers without callback hooks, the vulnerability is latent in the contract logic itself: the CEI ordering is wrong regardless of the specific token used, and the vaults are deliberately built as generic wrappers around `<ft-trait>`-typed calls, so any future or DAO-onboarded underlying asset with transfer hooks (a legitimate, foreseeable configuration change, not a DAO compromise) reactivates this exact class of drain.

### Impact Explanation
If exploited, an attacker can manipulate the vault's `assets` state during reentrancy to redeem against liquidity that has not actually been accounted for as spent, undermining `ERR-INSUFFICIENT-LIQUIDITY` protections and the share-to-asset exchange rate used by `convert-to-assets-preview`/`convert-to-shares-preview` for every other depositor. This can result in the vault paying out more underlying assets than its true backing supports, directly harming other depositors' principal — a direct theft of user funds at rest / protocol insolvency, matching the Critical impact bucket.

### Likelihood Explanation
Exploitability today depends on the underlying token contract's `transfer` function being able to invoke attacker-controlled code back into the vault (a callback/hook), which the currently wired mainnet tokens (`usdc`, `usdh`, `sbtc`, `ststx`, `wstx`) do not appear to provide based on visible code. However, the vault contracts are generically written against a `<ft-trait>` and reused across six near-identical deployments, so the CEI-ordering defect is systemic and only requires one of the accepted underlying assets (present or future) to support a transfer-time callback for the drain to become directly exploitable by an ordinary unprivileged principal — no DAO compromise needed.

### Recommendation
Update `redeem` (and audit `deposit`, `system-borrow`, `system-repay`, and `flashloan` for the same pattern) so that all internal accounting state (`var-set assets ...`) is committed *before* the external `send-underlying`/`receive-underlying` call, following check-effects-interaction. Additionally, add an explicit reentrancy guard (mirroring the existing `in-flashloan` flag) around `redeem`/`deposit` to prevent any nested vault entry during an outstanding external asset transfer.

### Proof of Concept
1. DAO onboards (or an existing asset is upgraded/wrapped to) a SIP-010 token whose `transfer` function calls back into the recipient contract (a realistic possibility for any non-`stx`/legacy token added later, or via a wrapping contract).
2. Attacker deposits and acquires `2 * amount` in vault shares.
3. Attacker calls `redeem(amount, min-out, attacker)`. Execution reaches `send-underlying inkind attacker`, which triggers the token's callback into the attacker's contract before the outer call's `(var-set assets (- current-assets inkind))` executes.
4. From the callback, attacker calls `redeem(amount, min-out, attacker)` again. This nested call reads `(var-get assets)` still at its pre-decrement value, so `available-assets`/`ERR-INSUFFICIENT-LIQUIDITY` and the `convert-to-assets-preview` exchange rate compute as if the first `inkind` had never been paid out, letting the attacker extract asset value beyond what the vault's true remaining backing supports.
5. Both calls complete, shares are fully burned (correctly), but the vault has paid out assets valued against a stale (higher) backing figure, leaving remaining depositors under-collateralized. [1](#0-0) [2](#0-1)
