Audit Report

## Title
Hardcoded ERC20 Transfer Gas Limit Permanently Traps XCM-Bridged Tokens for Non-Standard ERC20 Contracts - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::deposit_asset_with_surplus` and `withdraw_asset_with_surplus` invoke `pallet_revive::Pallet::<T>::bare_call` with a fixed `WeightLimit::get()` gas budget (instantiated as `ERC20TransferGasLimit`, sized for a "standard" ERC20 transfer) regardless of the actual gas needs of the target contract's `transfer` function. When a beneficiary-side ERC20 transfer exceeds this fixed budget, `deposit_asset_with_surplus` fails, the XCM executor traps the leftover holding, and because `ERC20Transactor` has no `mint_asset` override, subsequent `claim_assets` attempts cannot recover the funds — resulting in a permanent, deterministic user-fund lock.

## Finding Description
Both transactor functions hardcode the gas budget passed to `bare_call`: [1](#0-0) [1](#0-0) 

The value is a fixed constant sized only for a "standard" transfer: [2](#0-1) 

The implementation's own comment acknowledges the limitation is unfixable by the user at the XCM level: [3](#0-2) 

This is not hypothetical — the runtime's own test suite reproduces the exact failure with a contract fixture (`MyTokenExpensive`) that performs extra storage writes during `transfer`, causing `PolkadotXcm::execute` to fail.

When `deposit_asset_with_surplus` fails during a `DepositAsset`/reserve-transfer flow, `deposit_assets_with_retry` retries once and then propagates the error: [4](#0-3) 

The un-deposited holding — which for the ERC20 case is the `Erc20Credit` representing tokens already moved out of the sender's balance into `TransfersCheckingAccount` (a real ERC20 balance change already committed by `withdraw_asset_with_surplus`) — is then trapped by `post_process` via `Config::AssetTrap::drop_assets`: [5](#0-4) 

Recovery is nominally offered through `pallet_xcm::claim_assets`, which calls `AssetTransactor::mint_asset`. Critically, `ERC20Transactor` implements only `can_check_in`, `check_in`, `can_check_out`, `check_out`, `withdraw_asset_with_surplus`, and `deposit_asset_with_surplus` — it never overrides `mint_asset`, confirmed by reading the complete file (no `mint_asset` function is present). It therefore falls back to the default trait implementation, which unconditionally returns `Err(XcmError::Unimplemented)`: [6](#0-5) 

Because `AssetTransactors` is a tuple `(FungibleTransactor, FungiblesTransactor, ForeignFungiblesTransactor, UniquesTransactor, ERC20Transactor)`, the tuple-composed `mint_asset` tries each member in order and moves to the next only on `Err(AssetNotFound)`/`Err(Unimplemented)`: [7](#0-6) 

None of the other transactors' matchers recognize an `AccountKey20`-keyed ERC20 asset, so the chain falls through to `ERC20Transactor`, which returns the default `Err(XcmError::Unimplemented)`. The tuple then returns `Err(XcmError::AssetNotFound)` overall, and `pallet_xcm::claim_assets` logs the failure and drops the asset without minting anything back: [8](#0-7) 

Thus, once the deposit-side gas limit is exceeded, the credit is trapped and cannot be un-trapped: there is no code path that mints it back to any account, and re-attempting the deposit via any other route would hit the identical fixed-gas `bare_call` and fail identically.

## Impact Explanation
This matches the "permanent user-fund... lock" impact class in the Polkadot SDK Impact Gate. An ordinary, unprivileged user moving an ERC20 token via XCM whose `transfer` legitimately requires more gas than the hardcoded `ERC20TransferGasLimit` (rebasing tokens, fee-on-transfer tokens, blacklist/compliance-checking tokens, proxy-forwarded ERC20s, etc.) will have their tokens withdrawn from the sender into `TransfersCheckingAccount` successfully, but the deposit to the beneficiary will deterministically fail and the credit becomes permanently unrecoverable since `ERC20Transactor` has no `mint_asset` implementation to service a claim. The repository's own `expensive_erc20_runs_out_of_gas` test demonstrates this exact failure condition against a real contract fixture.

## Likelihood Explanation
Likelihood is high: no malicious actor, governance action, or privileged capability is required. Any user who bridges/transfers a non-"standard" ERC20 token (a common real-world category) via XCM `DepositAsset`/`InitiateTransfer` triggers this deterministically and repeatably, since the gas requirement of the destination-side `transfer` call is entirely a property of the token contract, not something the user or the XCM program can adjust.

## Recommendation
- Replace the single hardcoded `WeightLimit` with a per-asset configurable gas limit for `deposit_asset_with_surplus`/`withdraw_asset_with_surplus`, or dry-run/estimate gas for the specific token contract before locking in a fixed budget (as Snowbridge did when raising its `TransferToken` gas limit from 100k to 200k for tokens like LDO).
- Implement a dedicated `mint_asset` for `ERC20Transactor` using an escalated or configurable weight limit specifically for the claim/recovery path, so assets trapped due to gas exhaustion are actually recoverable via `pallet_xcm::claim_assets`.
- Consider rejecting/quarantining known "expensive" ERC20 contracts at the XCM matcher level before funds leave the sender's balance, rather than trapping them post-withdrawal.

## Proof of Concept
The repository's existing test directly demonstrates the failure mode: [9](#0-8) 

To confirm the permanent-lock aspect, extend this test to split the single XCM into two separate programs mirroring a real bridge flow: first execute a `withdraw_asset_with_surplus`-only XCM (succeeds, moving ERC20 balance into `ERC20TransfersCheckingAccount`), then execute a `deposit_asset_with_surplus`-only XCM to the beneficiary (fails identically due to the fixed gas limit, trapping the holding). Then call `PolkadotXcm::claim_assets` for the trapped `Erc20Credit` and assert it returns no minted assets (matches `Err(XcmError::AssetNotFound)`/`Unimplemented` fall-through) while the ERC20 contract balance of `ERC20TransfersCheckingAccount` remains unchanged and non-zero across repeated claim attempts.

#[test]
fn expensive_erc20_runs_out_of_gas() {
	let sender: AccountId = ALICE.into();
	let beneficiary: AccountId = BOB.into();
	let revive_account = pallet_revive::Pallet::<Runtime>::account_id();
	let checking_account =
		asset_hub_westend_runtime::xcm_config::ERC20TransfersCheckingAccount::get();
	let initial_wnd_amount = 10_000_000_000_000u128;

	ExtBuilder::<Runtime>::default().build().execute_with(|| {
		// Bring the revive account to life.
		assert_ok!(Balances::mint_into(&revive_account, initial_wnd_amount));

		// Fund all accounts involved.
		assert_ok!(Balances::mint_into(&sender, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&beneficiary, initial_wnd_amount));
		assert_ok!(Balances::mint_into(&checking_account, initial_wnd_amount));

		// This contract does a lot more storage writes in `transfer`.
		let code = compile_module_with_type("MyTokenExpensive", FixtureType::Resolc)
			.expect("compile ERC20")
			.0;

		let initial_amount_u256 = U256::from(1_000_000_000_000u128);
		let constructor_data = sol_data::Uint::<256>::abi_encode(&initial_amount_u256);
		let Contract { addr: non_erc20_address, .. } = bare_instantiate(&sender, code)
			.transaction_limits(TransactionLimits::WeightAndDeposit {
				weight_limit: Weight::from_parts(500_000_000_000, 10 * 1024 * 1024),
				deposit_limit: Balance::MAX,
			})
			.data(constructor_data)
			.build_and_unwrap_contract();

		let wnd_amount_for_fees = 1_000_000_000_000u128;
		let erc20_transfer_amount = 100u128;
		let message = Xcm::<RuntimeCall>::builder()
			.withdraw_asset((Parent, wnd_amount_for_fees))
			.pay_fees((Parent, wnd_amount_for_fees))
			.withdraw_asset((
				AccountKey20 { key: non_erc20_address.into(), network: None },
				erc20_transfer_amount,
			))
			.deposit_asset(AllCounted(1), beneficiary.clone())
			.build();
		// Execution fails but doesn't panic.
		assert!(PolkadotXcm::execute(
			RuntimeOrigin::signed(sender.clone()),
			Box::new(VersionedXcm::V5(message)),
			Weight::from_parts(2_500_000_000, 120_000),
		)
		.is_err());
	});
