### Title
Out-of-Bounds Read in ZIP Central Directory Parsing — (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the central directory of a `.jar`/`.zip` file without any bounds checking, unlike its sibling `ProcessLocalFileEntry`, which validates every read via `EnsureRemaining()`. An attacker-controlled jar (e.g., a jar fetched via `http_jar`/`http_archive`/`maven_install` that a victim's build consumes and then runs through `ijar` to produce an interface jar, or that `singlejar`/related tooling processes) can supply central-directory length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and offset values that cause the parser to read and `memcpy` memory past the end of the memory-mapped input file.

### Finding Description
`ProcessLocalFileEntry` calls `EnsureRemaining()` before reading every variable-length field: [1](#0-0) 

`ProcessCentralDirEntry`, however, performs no equivalent checks. It reads fixed and variable-length fields directly off the mapped buffer: [2](#0-1) 

and then walks an "extra fields" region purely based on attacker-supplied `extra_field_length`/`data_size`, again with no bound validation: [3](#0-2) 

This function is invoked in a tight loop over the whole central directory with no check that the cursor stays inside the mapped file, both in `ProcessNext()`: [4](#0-3) 

and in `CalculateOutputLength()`: [5](#0-4) 

If the jar's declared `file_name_length`/`extra_field_length`/`file_comment_length` fields (or the central-directory-driven `offset`/entry count) are crafted so the cursor `p`/`extra_p` advances past the actual mapped extent of the input file, the subsequent `get_u2le`/`get_u4le`/`get_u8le` calls and the `memcpy(filename, p, len)` (line 520) read memory outside the file's mapping. Because the file is `mmap`'d (see `MappedInputFile` in `third_party/ijar/mapped_file_unix.cc`/`mapped_file_windows.cc`), an out-of-bounds cursor can cross into unmapped pages (crash) or into adjacent process memory (potential leak of arbitrary heap contents into the `filename` buffer, which is later passed to `processor->Accept()`/used to construct output jar entries).

### Impact Explanation
This is analogous to `exif_scan_thumbnail`'s bug class: an untrusted binary container format with self-declared length fields is trusted to bound subsequent reads without independently verifying those lengths against the true size of the backing buffer. The consequence here is the same — out-of-bounds memory read leading to information disclosure (heap bytes leaked via the filename buffer into build-visible artifacts/errors) or process crash (denial of the `ijar`/related tool invocation) when Bazel's own C++ tooling parses an attacker-published jar.

### Likelihood Explanation
Any workflow where Bazel processes a jar file whose bytes are supplied by an untrusted party (e.g., an external HTTP jar dependency, a Maven artifact, or a jar bundled in a fetched archive that later gets passed through `ijar`) reaches this code path. A pinned `sha256`/integrity check on the outer archive does not mitigate this: the attacker controls both the malicious byte content and its checksum, so the checksum simply confirms the malicious bytes were faithfully downloaded — it does nothing to validate the internal ZIP structural invariants that `ProcessCentralDirEntry` fails to enforce.

### Recommendation
Add `EnsureRemaining()`-style bounds checks in `ProcessCentralDirEntry` (and in the `extra_field` walking loop) mirroring what `ProcessLocalFileEntry` already does, verifying that each fixed-size read and each variable-length advance (`file_name_length`, `extra_field_length`, `file_comment_length`, and per-extra-field `data_size`) stays within `zipdata_in_ + input_file_->Length()` before dereferencing.

### Proof of Concept
Construct a minimal ZIP/JAR whose central directory contains a single entry where `file_name_length` (or `extra_field_length`) is set to a large value (e.g., `0xFFFE`) such that `p + file_name_length` and the subsequent `extra_p` walk exceed the actual mapped file length, while keeping the overall file just large enough to satisfy `FindZipCentralDirectory`'s EOCD-locator scan. Feed this file to the `ijar` binary (`third_party/ijar/ijar.cc` entry point, which drives `InputZipFile::ProcessNext`/`CalculateOutputLength`). Running under ASan (or observing a SIGSEGV/heap-read failure) demonstrates the read past the mmap'd region in `ProcessCentralDirEntry`'s `memcpy`/`get_u*le` calls, matching the pattern that would be codified as a `src/test/shell/bazel` or JUnit reproduction feeding a crafted jar through the ijar action.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;

  u8 offset;
  char filename[PATH_MAX];

    u8 file_compressed, file_uncompressed;

                                &file_compressed, &file_uncompressed,

      break;

      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }
