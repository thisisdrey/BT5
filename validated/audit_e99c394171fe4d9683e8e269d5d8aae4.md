Confirmed: `redeem` explicitly guards against a zero-value conversion (`ERR-OUTPUT-ZERO`), but `deposit` does not have the analogous guard on its `inkind` (shares-minted) value. This is the exact WUSDA rounding bug reproduced in Zest's tokenized vault contracts.

### Title
Missing zero-shares check in vault `deposit` allows silent loss of depositor funds via share-rounding to zero - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and all sibling vaults)

### Summary
`convert-to-shares-preview` computes `mul-div-down amount ts ta`, which floors to `u0` when `amount` is small relative to `total-assets` (`ta`). `deposit` uses this value as `inkind` (shares to mint) but only checks `(>= inkind min-out)` for slippage and never asserts `inkind > u0`, unlike `redeem`, which explicitly enforces `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)`.

### Finding Description
In `deposit`: [1](#0-0) 
`inkind` is derived from `convert-to-shares-preview`: [2](#0-1) 
which floors via `mul-div-down amount ts ta`. If a caller's default `min-out` argument is `u0` (a normal, non-malicious default for a "no slippage protection" call, or simply because they didn't anticipate rounding), the check `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes trivially even when `inkind` is `u0`. The deposit then proceeds: `receive-underlying` pulls the user's full `amount` of underlying into the vault, `assets` is incremented by the full `amount`, but `ft-mint?` mints `u0` shares to the depositor. [3](#0-2) 

Contrast this with `redeem`, which has the missing safeguard: [4](#0-3) 

This asymmetry is the same root cause as the WUSDA finding: `_usdaToWUSDA`-style floor division producing `0` for small deposits relative to a large "total-assets"/"total-supply" ratio, with no revert-on-zero guard on the deposit path.

An attacker (or even benign market conditions) can inflate `total-assets` relative to `total-supply` (e.g., via `accrue` interest accumulation increasing `ta` without proportional `ts` growth, or a large deposit inflating `ta` right before a smaller victim deposit lands in the same or a subsequent block) so that a victim's `amount * ts / ta` rounds to zero. The victim's underlying tokens are absorbed into `assets` and permanently accrue to all existing shareholders pro-rata, while the depositor receives zero vault shares in return — an irrecoverable, direct loss of their principal. This is reachable by any ordinary principal calling `deposit` on any of the tokenized vaults (`v0-vault-stx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`), which all share the identical `convert-to-shares-preview`/`deposit` logic. [5](#0-4) [6](#0-5) 

### Impact Explanation
This is direct theft/loss of user funds at rest: the depositor's underlying asset is transferred into the vault and irretrievably credited to other shareholders (their share of `total-assets` increases without corresponding dilution), while the depositor is left holding zero shares and no way to reclaim the deposited amount. This matches the Critical impact class ("direct theft of user funds at rest or in motion").

### Likelihood Explanation
Likelihood depends on the ratio of a given deposit `amount` to the vault's `total-assets`/`total-supply` ratio; it is most exploitable in vaults that grow large (e.g., through `accrue` interest or big deposits) relative to the granularity of a later small deposit. A user (or attacker deliberately inflating `ta` beforehand, e.g. via a large legitimate deposit or by waiting for organic interest accrual) can trigger this without needing any privileged access or DAO compromise — only ordinary `deposit` calls are required. `min-out` defaulting to `u0` (no slippage protection specified) is a realistic default for many front-end/integration flows, making the zero-share outcome silently acceptable per the current code.

### Recommendation
Add the same zero-output guard used in `redeem` to `deposit`:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
placed alongside the existing `deposit` asserts in each vault contract (`v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`), so that a deposit reverts instead of silently minting zero shares while consuming the depositor's underlying assets.

### Proof of Concept
1. Vault has `total-assets` (`ta`) = 1,000,000,000 (1e9) micro-units and `total-supply` (`ts`) = 10,000 shares (a ratio that can arise organically after sufficient `accrue` interest growth relative to share issuance, since `total-assets` grows via interest while `total-supply` only grows on new deposits).
2. Victim calls `deposit` with `amount` = 90,000 (a modest, realistic deposit) and `min-out` = `u0` (default/no explicit slippage bound).
3. `convert-to-shares-preview` computes `inkind = mul-div-down(90000, 10000, 1000000000) = 0` (floors to zero since `90000*10000 = 9e8 < 1e9`).
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` → `(>= 0 0)` passes.
5. `receive-underlying` pulls 90,000 units from the victim into the vault; `assets` is incremented by 90,000; `ft-mint? zft 0 recipient` mints zero shares.
6. The victim has lost 90,000 units of underlying with zero vault shares to redeem it back; all existing shareholders' claims on `total-assets` increase proportionally at the victim's expense.

(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      (states (var-get pause-states))
      (u (try! (accrue)))
      (account contract-caller)
      (CAP-SUPPLY (var-get cap-supply))
      (current-assets (var-get assets))
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
    (var-set assets (+ current-assets amount))
```
