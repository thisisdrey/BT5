### Title
Checked-math overflow in resource-usage-to-TRX conversion can crash `GetAccountResource`/`GetAccountNet` query path and TVM `unDelegateResource` execution - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.usageToBalance()` mirrors the reported bug class: a multiply-then-divide computation on user-influenced values that, in its "hardened" mode, uses `BigInteger...longValueExact()` instead of saturating/clamped math. Just like the Solidity `getVestedAmount()` case, an out-of-range intermediate product causes an uncaught `ArithmeticException` instead of a graceful result, bricking the calling query/transaction path.

### Finding Description
`usageToBalance()` computes `usage * totalWeight * TRX_PRECISION / totalLimit` and, when `hardenResourceCalculation()` is enabled, does this with `BigInteger` and calls `.longValueExact()`: [1](#0-0) 

Unlike `Math.multiplyExact`/`longValueExact()` usages elsewhere that are wrapped in `try { ... } catch (ArithmeticException e)` (e.g. `ExchangeInjectActuator.execute()` and `.validate()`), this call has no surrounding exception handling: [2](#0-1) 

`usageToBalance()` is invoked from `getAccountEnergyUsageBalanceAndRestoreSeconds()` / `getAccountNetUsageBalanceAndRestoreSeconds()`, which compute available bandwidth/energy balance from `usage`, `totalWeight` (`getTotalEnergyWeight()`/`getTotalNetWeight()`), and `totalLimit`: [3](#0-2) 

The analogous unchecked `.longValueExact()` pattern also appears in `ResourceProcessor.calculateGlobalLimitV2()`, used to compute frozen-balance-to-resource-limit conversions during freeze/delegate/undelegate resource native contract execution: [4](#0-3) 
and in `ResourceProcessor.unDelegateIncreaseV2()`'s window-size computation, which multiplies `ownerUsage`/`transferUsage` against window sizes with `BigInteger` and `divideCeilExact`: [5](#0-4) 

These "hardened" BigInteger paths were introduced specifically to prevent silent overflow of the legacy `double`-based computation, but by switching to exact/checked arithmetic without bounding the inputs or catching the resulting `ArithmeticException`, they reintroduce the exact overflow-DoS bug class described in the report: an out-of-range multiplication result throws instead of failing safely.

### Impact Explanation
If `usage`, `totalWeight`, or the accumulated `ownerUsage`/`windowSize` values combine to produce a product outside `Long` range, `.longValueExact()` throws an unhandled `ArithmeticException`. Because these methods are reached via read-only account-resource query paths in `Wallet`/gRPC/HTTP (`GetAccountNet`, `GetAccountResource`) as well as from native-contract execution during `UnDelegateResourceContract`/`FreezeBalanceV2`/`UnfreezeBalanceV2` processing (both invokable by any signed transaction from an unprivileged account), an uncaught exception on this path can turn into a denial-of-service: the specific account's resource query/transaction execution consistently fails until the underlying state (usage/weight ratios) changes, matching the "DoS bricks a user's ability to query/claim" scenario in the original report.

### Likelihood Explanation
Exploitability depends on whether `hardenResourceCalculation()`/`hardenCalculation()` are enabled on the target network and whether an attacker can, through repeated freeze/delegate/undelegate operations, drive `usage`, `totalWeight`, and `windowSize` values into a combination whose product overflows `Long.MAX_VALUE` before division. This requires manipulating global/one's-own resource accounting over many transactions rather than a single crafted input, so likelihood is lower than the original single-Merkle-leaf scenario, but the same missing-bound / uncaught-exception root cause is present and unmitigated in code, in contrast to the exchange actuators where the same pattern is deliberately wrapped in `try/catch (ArithmeticException e)`.

### Recommendation
- Wrap the `.longValueExact()`/`divideCeilExact()` calls in `usageToBalance()`, `calculateGlobalLimitV2()`, and `unDelegateIncreaseV2()` in `try/catch (ArithmeticException e)` and fall back to a safe clamped value (mirroring the pattern already used in `ExchangeInjectActuator`/`ExchangeWithdrawActuator`).
- Alternatively, bound `usage`, `totalWeight`, and `windowSize` inputs to values that cannot produce an overflowing product, or use a saturating multiply/divide helper instead of exact-checked BigInteger conversion back to `long`.

### Proof of Concept
Not independently reproducible from static analysis alone — confirming actual overflow requires driving `usage * totalWeight * TRX_PRECISION` (or the `unDelegateIncreaseV2` window-size product) past `Long.MAX_VALUE` through a sequence of freeze/delegate/undelegate transactions while `hardenResourceCalculation()`/`hardenCalculation()` is active, and then invoking `getAccountResource`/`getAccountNet` (or triggering the corresponding native contract) to observe the uncaught `ArithmeticException`. This would need to be validated in a running/test node (e.g., via `RepositoryImplHardenTest`, which already exercises the hardened `usageToBalance`/`calculateGlobalLimitV2` code paths) — code-index access alone cannot confirm concrete numeric feasibility of the overflow under current chain parameters.   private long usageToBalance(long usage, long totalWeight, long totalLimit) {
    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(usage)
          .multiply(BigInteger.valueOf(totalWeight))
          .multiply(BigInteger.valueOf(TRX_PRECISION))
          .divide(BigInteger.valueOf(totalLimit))
          .longValueExact();
    }
    return (long) ((double) usage * totalWeight / totalLimit * TRX_PRECISION);
  }
