The `pallet-dap` (Dynamic Allocation Pool) budget-distribution loop mirrors the `vestingDeposits` issue exactly: it iterates over a list of recipients and mints per-entry with no runtime-enforced duplicate check, relying only on a debug-only assertion that never runs during actual block production.

### Title
Duplicate `BudgetRecipient` key in `pallet-dap` causes silent unbacked over-minting on every issuance drip - ([File: substrate/frame/dap/src/lib.rs])

### Summary
`pallet-dap::mint_and_distribute` iterates the recipient list returned by `T::BudgetRecipients::recipients()` and mints `perbill.mul_floor(issuance)` into each entry's account independently, using the shared `BudgetKey` to look up the percentage. If two entries in that list carry the same `BudgetKey` (whether mapped to the same or different accounts), the loop mints that key's allocated share twice per drip. The only protection against duplicate keys is a `debug_assert!` inside `BudgetRecipientList` and an `integrity_test()` hook — neither of which executes during normal block production on a release-built node, so the duplication silently persists and compounds every drip cycle.

### Finding Description
`mint_and_distribute` at [1](#0-0)  loops over `recipients` and for each `(key, account)` pair does `budget.get(key)` then `T::Currency::mint_into(account, amount)`, accumulating `total_minted`. There is no `BTreeSet`/sort-and-check step in this function to reject or dedupe repeated keys before minting.

The intended invariant — "each `BudgetKey` corresponds to exactly one recipient" — is only checked in two places:
1. `BudgetRecipientList`'s blanket tuple impl, which wraps the check in `debug_assert!` at [2](#0-1)  — `debug_assert!` is compiled out entirely in release builds (the default for production Substrate nodes), so this check never fires on a live chain.
2. `Pallet::integrity_test()` at [3](#0-2)  — this hook is only exercised by the `construct_runtime!`-generated `#[test]` and by explicit `try-runtime` invocations; it is not called by `frame_executive` during `on_initialize`/block execution, so it provides no protection for a running chain.

`T::BudgetRecipients` is a runtime-composed tuple (e.g. `(Dap, StakerRewardRecipient, ValidatorIncentiveRecipient)` as documented at [4](#0-3) ). Because it aggregates independently-authored `BudgetRecipient` implementations from multiple pallets/modules, it is entirely plausible for two implementations to end up returning the same `budget_key()` (e.g. copy-paste error, shared constant reused across two sub-modules, or a later added recipient accidentally reusing an existing key string) without any compile-time uniqueness guarantee — `BudgetKey` is just a `BoundedVec<u8, ...>` string, not a type-level discriminant.

This is the same broken invariant as the reported `PortalToken.vestingDeposits` bug: a list processed item-by-item, where a repeated identifier (address in the external report, `BudgetKey` here) causes the corresponding allocation to be paid out more than once, while the acceptance path enforcing "no duplicates" is not actually active on the enforced path (constructor/deployment script there, actual runtime block execution here).

### Impact Explanation
Every drip (`on_initialize` → `drip_issuance` → `mint_and_distribute`) mints new currency directly via `T::Currency::mint_into`, which increases `TotalIssuance`. If a duplicate key exists, the amount minted for that key's `Perbill` share is minted twice (once per duplicate entry), so `total_minted` exceeds the value computed by `T::IssuanceCurve::issue(total_issuance, elapsed)` for that period. This is an unbacked mint: new tokens enter circulation that were never intended by the issuance curve, permanently and silently inflating supply on every subsequent drip, for the lifetime of the chain, until someone notices and redeploys a corrected runtime via governance/forkless upgrade. This directly matches the "theft or unbacked mint" and "duplicate settlement or payout" impact categories.

### Likelihood Explanation
This does not require any malicious actor, governance abuse, or privileged access — it is a pure implementation gap: the only safety net (`debug_assert!`/`integrity_test`) is inert on any production (release-mode) node. Any runtime that composes `BudgetRecipients` from more than one source (which the pallet explicitly documents as the intended usage pattern) is one accidental key collision away from continuously over-minting, with zero warning in logs or on-chain events (the `IssuanceMinted` event just reports whatever `total_minted` accumulated, with no indication that the underlying accounting double-counted a category).

### Recommendation
In `mint_and_distribute`, deduplicate `recipients` by `BudgetKey` before minting (e.g., collect into a `BTreeMap<BudgetKey, AccountId>` and error/skip on collision, or return early with a `defensive!` and abort the drip). Additionally, replace the `debug_assert!` in `BudgetRecipientList`'s tuple impl with a real `assert!`/hard error path that panics regardless of build profile, and consider actively invoking `integrity_test`-style validation from `on_runtime_upgrade` so that any future duplicate introduced via a runtime upgrade is caught at upgrade time rather than silently accepted.

### Proof of Concept
1. Configure a runtime's `BudgetRecipients` as `(RecipientA, RecipientB)` where `RecipientA::budget_key()` and `RecipientB::budget_key()` both return the same `BudgetKey` (e.g., `b"alpha"`) but `pot_account()` differs (`AccountX` vs `AccountY`) — as demonstrated by the test fixtures `RecipientA`/`RecipientDuplicate` at [5](#0-4) , which only panics under `#[should_panic]` test conditions (debug assertions enabled), not in a release build.
2. Set `BudgetAllocation` via `set_budget_allocation` so that `alpha -> 50%` (and other keys sum the remainder to 100%) — this call only validates against `registered` keys, not for duplicates among registrants, per [6](#0-5) .
3. Build the node in release mode (standard for any production chain) and let a block trigger `drip_issuance`. `mint_and_distribute`'s loop at [7](#0-6)  will process both `(alpha, AccountX)` and `(alpha, AccountY)`, minting `50% * issuance` into each — 100% of `issuance` for a single 50%-weighted category, i.e., the total minted that drip is 150% of the intended issuance, with no error, event anomaly, or panic raised.
4. Observe `TotalIssuance` growth over subsequent drips consistently exceeds `IssuanceCurve::issue()`'s intended output, confirming persistent unbacked over-minting.
