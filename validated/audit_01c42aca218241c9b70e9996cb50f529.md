### Title
Floating-point reward-share computation in `MortgageService.computeReward(long, List)` produces systematically incorrect (and unrecoverable) voter reward amounts - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The old-algorithm per-cycle voter reward calculation in `MortgageService` (and its TVM twin `VoteRewardUtil`) derives each voter's share of a witness's reward pool using double-precision floating point division and multiplication instead of exact integer/BigInteger arithmetic. This mirrors the reported `TickLogic.getAdjustedAmount` bug class: a derived, per-account value is computed from an inexact arithmetic operation (division followed by multiplication) rather than being tracked directly, so the individually computed shares do not necessarily reconcile with the total reward pool that was actually paid into the cycle.

### Finding Description
In `payReward`, a witness's per-cycle reward pool is stored as an exact integer (`delegationStore.addReward(cycle, witnessAddress, value)`), after brokerage is deducted using floating point (`double brokerageRate = (double) brokerage / 100; long brokerageAmount = (long) (brokerageRate * value);`). [1](#0-0) 

When a voter withdraws/queries reward for cycles prior to `newRewardAlgorithmEffectiveCycle`, the protocol falls back to the legacy per-cycle computation:
```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  ...
  long userVote = vote.getValue();
  double voteRate = (double) userVote / totalVote;
  reward += voteRate * totalReward;
}
``` [2](#0-1) 

This is exactly the same bug class as the reported `getAdjustedAmount`: a proportional/derived amount (`voteRate * totalReward`) is recomputed independently per account instead of being derived from an exact, order-independent invariant (as the newer BigInteger `Vi`-accumulator algorithm does at lines 215-227 of the same file, which is not used for cycles before `newRewardAlgorithmEffectiveCycle`). [3](#0-2) 

Because `voteRate` is a `double`, and each voter's `long userVote / long totalVote` ratio is rounded to floating-point precision before being multiplied back by `totalReward` and truncated to `long`, the sum of rewards computed independently for all voters of a witness in a given cycle is not guaranteed to equal `totalReward`. Depending on rounding direction this can either:
1. Systematically under-pay voters — funds that were already deducted from the reward pool (`delegationStore.addReward`) as belonging to voters are never claimed by anyone and become permanently stranded, exactly analogous to Bob earning less interest in the report, or
2. Over-pay (when floating point rounds several voters' shares upward), which mints allowance (`adjustAllowance`, ultimately convertible to real TRX balance via `WithdrawBalanceContract`/`WithdrawRewardProcessor`) that was never actually backed by the recorded per-cycle `totalReward`. [4](#0-3) [5](#0-4) 

The same pattern is duplicated for the TVM voting path in `VoteRewardUtil`, but it already uses the BigInteger `Vi`-delta method there for reward computation, so the vulnerable path is specifically the legacy `MortgageService.computeReward(long cycle, ...)` reachable for any account with votes cast in cycles before the new reward algorithm became effective, or for chains/testnets where `allowOldRewardOpt`/`newRewardAlgorithmEffectiveCycle` configuration still routes through this method.

### Impact Explanation
This directly maps to "unbacked balance" or "permanent freezing of funds" categories: a voter's allowance balance (ultimately withdrawable as real TRX) is computed from an imprecise per-account proportional calculation instead of an exact, reconciled value, so the total TRX paid out across all voters for a witness's cycle reward can diverge from the actual reward pool recorded for that cycle — either permanently starving some voters of legitimately earned rewards or allowing more TRX to be withdrawn in aggregate than was ever deposited into that cycle's reward pool.

### Likelihood Explanation
This code path executes automatically whenever any account calls `WithdrawBalanceContract`, `VoteWitnessContract`, or the TVM `withdrawReward`/`vote` precompiled paths and has un-withdrawn votes/reward from a cycle prior to the new reward algorithm's effective cycle — a completely unprivileged, single signed transaction. No special role or timing manipulation is required; the discrepancy accumulates naturally from ordinary voting/reward flow over many witnesses/voters/cycles.

### Recommendation
- **Short term:** Replace the double-based `voteRate = (double) userVote / totalVote; reward += voteRate * totalReward;` computation in `MortgageService.computeReward(long, List)` with exact integer/BigInteger arithmetic (`reward += totalReward * userVote / totalVote` using `BigInteger` or `Math.multiplyHigh`/`LongMath` to avoid overflow), matching the precision approach already used in the newer `Vi`-based algorithm.
- **Long term:** Deprecate/migrate all historical cycles still relying on the legacy `computeReward(long cycle, ...)` path to the BigInteger `Vi`-accumulator algorithm, and add invariant tests asserting that the sum of individually computed voter rewards for a witness's cycle never exceeds (and, ideally, exactly reconciles with) `delegationStore.getReward(cycle, srAddress)`.

### Proof of Concept
1. Set up two voters A and B who both vote for witness W with `userVoteA = 1` and `userVoteB = 2` out of `totalVote = 3` in cycle `c`, prior to `newRewardAlgorithmEffectiveCycle`.
2. Trigger `payReward`/`payBlockReward` so `delegationStore.getReward(c, W)` is set to a value such as `10` (a value not evenly divisible by 3), e.g. `totalReward = 10`.
3. Call `withdrawReward`/`WithdrawBalanceContract` for A: `voteRate = 1.0/3.0 ≈ 0.333333333333`, `reward = (long)(0.333333333333 * 10) = 3`.
4. Call `withdrawReward`/`WithdrawBalanceContract` for B: `voteRate = 2.0/3.0 ≈ 0.666666666667`, `reward = (long)(0.666666666667 * 10) = 6`.
5. Total distributed = `3 + 6 = 9`, one unit of the `totalReward = 10` recorded for this cycle is permanently unclaimable by anyone — analogous to Bob's lost interest in the reported exploit. With different vote ratios and larger `totalReward` magnitudes (and multiple witnesses/voters), the accumulated floating-point rounding can instead cause the opposite effect (sum of individually-computed rewards exceeding `totalReward`), producing TRX withdrawable via `WithdrawBalanceActuator`/`WithdrawRewardProcessor` that was never actually backed by the recorded reward pool.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
