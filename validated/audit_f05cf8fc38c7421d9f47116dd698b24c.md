### Title
Unbounded array index reads in `PrecompiledContracts` word-array parsers cause uncaught `ArrayIndexOutOfBoundsException` on attacker-controlled TVM calldata - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The iccDEV report describes an OOB read caused by using an attacker-influenced index into an array without validating it against the array's real bounds (`IccCmm.cpp` reading through an index during profile processing). The same bug class — indexing an array with a value derived from untrusted, attacker-supplied data without first checking it is within the array's length — is present in java-tron's precompiled-contract calldata parsers used by the TVM `CALL` opcode path.

### Finding Description
`PrecompiledContracts.extractBytes32Array` reads `words[offset]` and then loops reading `words[offset + i + 1]` for `i` up to the attacker-controlled `len`, with **no bounds check at all** against `words.length`: [1](#0-0) 

This is inconsistent with the sibling helpers `extractBytesArray` and `extractSigArray`, which at least guard `offset > words.length - 1` before reading `words[offset]` (though they still don't bound the inner loop against `words.length`, only against `data` via `extractBytes`): [2](#0-1) 

More critically, `ValidateMultiSign.execute` indexes `words[0]`, `words[1]`, `words[2]`, and later `words[3]` (used both directly and as an offset into `words` at line 1067) **before any length check** on the `words` array produced by `DataWord.parseArray(rawData)`: [3](#0-2) 

`DataWord.parseArray` simply divides `data.length` by 32 and builds an array of that size — it performs no minimum-size enforcement: [4](#0-3) 

The `isValidAbiEncoding` gate at the top of `execute` only applies `if (VMConfig.allowTvmOsaka())` — on chains/configurations where that feature flag is not enabled, there is no minimum-length enforcement at all, so a caller can supply calldata shorter than 4 words (or with `words[3]` decoded to point far outside the array) and trigger an `ArrayIndexOutOfBoundsException` directly inside `execute()`, outside of any local `try/catch` (the `try` block only starts at line 1082, after the offending array accesses at lines 1058-1074).

Similarly, `BatchValidateSign.doExecute` calls `extractBytes32Array(words, words[2].intValueSafe() / WORD_SIZE)` with an attacker-chosen offset and no bound check inside that helper, so `words[offset]` and the subsequent loop can throw `ArrayIndexOutOfBoundsException` for crafted offsets/lengths: [5](#0-4) 

That call is wrapped by an outer `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }` in `BatchValidateSign.execute`, so the exception is absorbed there. However, `ValidateMultiSign.execute` has **no such outer guard** around the initial `words[...]` accesses (lines 1058-1074) — only the account/permission logic below is wrapped in try/catch.

### Impact Explanation
`ValidateMultiSign` and `BatchValidateSign` are TVM precompiled contracts reachable by any contract via a `CALL`-family opcode from a single, unprivileged, attacker-crafted transaction (contract deployment + trigger, or a call from an already-deployed contract). If the `ArrayIndexOutOfBoundsException` thrown from `ValidateMultiSign.execute` before the local `try` block is not caught by a broader handler in the VM/`Program` call chain, it would propagate as an uncaught `RuntimeException` during opcode execution, which in `VM.play` is caught generically and turned into a halted execution (`program.stop()`, energy spent, exception surfaces as contract execution failure) — this generic RuntimeException handling in `VM.play` (`actuator/src/main/java/org/tron/core/vm/VM.java:93-101`) likely absorbs it as a normal VM exception rather than crashing the node process. I was unable to fully confirm, from the available index, whether `Program.callToPrecompiledAddress` has additional exception handling around precompiled-contract invocation that would convert this into a clean revert versus an unhandled exception that escapes transaction processing (the file's exact content around that method could not be retrieved within the tool budget). Given Java's memory safety, this bug class cannot produce a C++-style memory-disclosure/segfault; the realistic worst case is a denial-of-service via unhandled exception during transaction/block application if the exception is not caught by an enclosing handler, which would be High severity per the rules (node crash/halt) — but this is unverified.

### Likelihood Explanation
High, if the crash path is real: any account can broadcast a `TriggerSmartContract` transaction that calls `ValidateMultiSign` (address configured under `VMConfig.allowTvmSelfdestructRestriction`) with calldata shorter than 4 words, requiring no special privilege, asset, or SR/witness role — fully within scope as "unprivileged transaction broadcaster / contract deployer" reachable code.

### Recommendation
Add explicit length checks before any indexing into `words` in `ValidateMultiSign.execute` (verify `words.length` is large enough for the fixed header, and that `words[3].intValueSafe() / WORD_SIZE` is within `[0, words.length)`), and fix `extractBytes32Array` to include the same `offset > words.length - 1` guard used by `extractBytesArray`/`extractSigArray`, plus bound the inner loop (`offset + i + 1 < words.length`) in all three extractors. Ensure `isValidAbiEncoding` (or an equivalent check) is enforced unconditionally, not gated behind `VMConfig.allowTvmOsaka()`.

### Proof of Concept
1. Deploy any contract, or use an existing one, that issues a low-level `call` to the `ValidateMultiSign` precompile address with calldata shorter than `128` bytes (4 words), e.g. only `64` bytes.
2. `DataWord.parseArray` returns a `words` array of length `2`.
3. `ValidateMultiSign.execute` executes `words[2].getData()` (line 1060) or, if `VMConfig.allowTvmSelfdestructRestriction()` is enabled, `words[3].intValueSafe()` (line 1067) against a 2-element array, throwing `ArrayIndexOutOfBoundsException` outside of the local `try/catch` block that only starts at line 1082.
4. Observe whether the exception is silently swallowed by the VM's generic runtime-exception handling in `VM.play`/`Program`, or propagates further — this final step could not be fully verified from the retrieved code and would need to be confirmed by running the actual call path in the node.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }

      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          SIG_LENGTH);
    }
    return bytesArray;
  }

  public static DataWord[] parseArray(byte[] data) {
    int len = data.length / WORD_SIZE;
    DataWord[] words = new DataWord[len];
    for (int i = 0; i < len; i++) {
      byte[] bytes = Arrays.copyOfRange(data, i * WORD_SIZE, (i + 1) * WORD_SIZE);
      words[i] = new DataWord(bytes);
    }
    return words;
  }
