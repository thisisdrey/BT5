### Title
Malicious peer response bypasses per-request content-hash validation, causing legitimate attachments to be permanently marked unresolved - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` accepts any `Attachment` a peer returns for a `GetAttachment` request without checking that its hash matches the `content_hash` that was actually requested. In the `Done` branch of `AttachmentsDownloader::run`, the pending batch entry is cleared using `attachment.hash()` (the hash of whatever bytes the peer sent) instead of the originally requested hash, so a peer that always answers with mismatched-hash junk can prevent a specific, genuinely on-chain-committed attachment from ever being marked resolved for this node.

### Finding Description
`AttachmentRequest` carries a specific `content_hash` that the downloader expects for a given attachment instance [1](#0-0) . When the HTTP response for that request comes back, `extend_with_attachments` decodes it and inserts the returned `Attachment` into `self.attachments` with **no comparison** between `response.attachment.hash()` and `request.content_hash`: [2](#0-1) 

Later, in `AttachmentsDownloader::run`'s `Done` branch, for every attachment collected this way, the code looks up matching instances and clears the pending entry using the *returned* hash, not the originally requested one: [3](#0-2) 

If a malicious peer receives a `GetAttachment` request for real hash `H` and responds with junk `J` where `hash(J) != H`:
- `find_all_attachment_instances(&attachment.hash())` looks up instances keyed by `hash(J)`, which will not match the instance(s) actually pending on `H`, so nothing gets added to `resolved_attachments` for that instance (no forged data is propagated as resolved — the DB-lookup gate does prevent that specific worse outcome).
- `context.attachments_batch.resolve_attachment(&attachment.hash())` is called with `hash(J)`, so the pending entry for `H` is **never** cleared.
- `context.attachments_batch.has_fully_succeed()` remains false, the batch is re-queued via `bump_retry_count()`, and once `retry_count >= max_attachment_retry_count`, the batch is dropped entirely: [4](#0-3) 

Because `AttachmentRequest.sources` is populated from whichever peers advertised having the attachment in their `AttachmentsInv` response, an attacker peer that (a) advertises having the attachment and (b) always answers with mismatched-hash junk for it, can keep this specific `content_hash` unresolved across retries until the batch is dropped, particularly if it ends up as the peer chosen to answer that request in each retry round.

### Impact Explanation
The affected node permanently treats a validly, on-chain-committed attachment/BNS record as unresolved/unavailable after retries are exhausted, even though the data is legitimately committed and could be obtained from a well-behaved peer. This matches the "attachment/BNS mismatch" High-severity category: the node serves/records "attachment absent" for data that was actually committed on-chain, degrading BNS name resolution correctness for that node without any privileged access, using only unauthenticated P2P/HTTP responses from a single hostile peer that the victim happens to talk to.

### Likelihood Explanation
The attacker only needs to run a normal peer node that the victim's Atlas downloader queries (no secret, no signing key, no StackerDB slot needed) and needs the victim to end up depending on it as a/the source for the targeted `content_hash` (e.g., by advertising the item in its `AttachmentsInv` responses). The cost is trivial — one crafted HTTP response with wrong bytes per retry round, repeatable indefinitely for any attachment the attacker chooses to target, bounded only by the victim's `max_attachment_retry_count` before it drops the batch.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if it doesn't match, treat the peer's response as failed (`report.bump_failed_requests()`), and do not add the mismatched attachment. This ensures `resolve_attachment` in `run`'s `Done` branch is always invoked with the actually-requested hash, and a hash-mismatching peer response is correctly counted as a failure that triggers retry with a *different* peer or attempt, rather than silently poisoning resolution of `H`.

### Proof of Concept
1. In `stackslib::net::atlas::tests`, construct an `AttachmentsBatch` with one pending instance whose `content_hash = H` for a real, on-chain-committed attachment.
2. Set up a mock peer/server that, for any `GetAttachment` request, always returns a well-formed `GetAttachmentResponse` whose `attachment` bytes hash to `J != H`.
3. Drive `AttachmentsBatchStateMachine::try_proceed` through `Initialized -> DNSLookup -> DownloadingAttachmentsInv -> DownloadingAttachment -> Done` using `AttachmentsDownloader::run`, repeating until `connection_options.max_attachment_retry_count` retries are exhausted.
4. Assert that: (a) `resolve_attachment(&H)` is never observed to clear the pending entry for `H` (inspect `attachments_batch.attachments_instances` / `has_fully_succeed()` before drop), and (b) after the final retry the batch is dropped (log path at `download.rs:200-204`) with `H` still unresolved, confirming the on-chain-committed attachment is permanently marked unavailable for this node.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
