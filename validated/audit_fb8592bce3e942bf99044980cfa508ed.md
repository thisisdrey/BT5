## Title
Legacy (non-hardened) TRC10 Exchange swap path allows draining an exchange pool beyond its actual reserve - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Sherlock report describes `BlueBerryBank.borrow()` computing a borrowed amount and transferring it out without ever checking that the bank's `totalDebt`/reserve actually contains that many tokens. The direct java-tron analog is the TRC10 bonding-curve exchange swap path (`ExchangeTransactionContract` / `ExchangeWithdrawContract`), which computes an output amount from a floating-point bonding-curve formula and pays it out of the pool's `firstTokenBalance`/`secondTokenBalance` without validating that the resulting balances stay non‑negative, unless the "hardened" calculation path is active.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-token amount (`buyTokenQuant`) using a `Processor` and then unconditionally updates the pool balances: [1](#0-0) 

Two processor implementations exist:
- The legacy `ExchangeProcessor`, which performs the bonding-curve math with `double`/`Math.pow` floating-point arithmetic: [2](#0-1) 
- The newer `SafeExchangeProcessor`, using `BigDecimal` with explicit rounding: [3](#0-2) 

Crucially, the post-transaction balance sanity check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` → revert) is only performed **when `hardenedCalc` is true**: [4](#0-3) 

When `hardenedCalc` is false (legacy math path, selected by `allowHarden()` not yet being active via chain proposal), the non-strict branch computes `newSecondTokenBalance = secondTokenBalance - buyTokenQuant` (or the symmetric case) with **plain `long` subtraction and no lower-bound check at all**. If the floating-point `ExchangeProcessor.exchange()` computation (via `Math.pow` on doubles) returns a `buyTokenQuant` that exceeds the actual `buyTokenBalance` for certain input ratios/precision edge cases, the resulting pool balance silently goes negative (or wraps), while the actuator still pays out the full `anotherTokenQuant` to the caller's account: [5](#0-4) 

This exactly mirrors the reported bug class: an amount computed from a formula/state is paid out to the caller without validating it against the actual reserve held by the pool.

### Impact Explanation
If the legacy (non-hardened) exchange math path is reachable (i.e., the hardening proposal is not enabled on a given network/branch), a caller submitting `ExchangeTransactionContract` (or `ExchangeWithdrawContract`, which shares the same `transaction()`-adjacent balance logic without the guard) could receive more of the counter-token than the exchange pool actually holds, and/or drive the pool's tracked reserve negative. This creates an unbacked balance / accounting mismatch, letting other participants who withdraw afterward find the pool's `AssetIssueStore`-backed balances exhausted — a direct theft-of-funds / unbacked-balance condition reachable by any unprivileged account able to submit an `ExchangeTransactionContract`.

### Likelihood Explanation
Reachable by any anonymous account holding a TRC10 token or TRX involved in an existing exchange pair — no special privileges required, only a signed `ExchangeTransactionContract`/`ExchangeWithdrawContract`. The likelihood depends on whether the network still exercises the legacy (`hardenedCalc = false`) path, i.e. whether `allowHarden()` is active; if the corresponding hardening proposal has already been activated network-wide, this path is dead code for exchange contracts and the bug is not exploitable there, but the un-hardened `ExchangeProcessor` code and the unguarded branch in `ExchangeCapsule.transaction()` remain present and reachable if that flag is ever off (e.g. private/legacy chains, or during any rollback/transition window).

### Recommendation
Perform the same non-negative balance check (and preferably migrate fully to `SafeExchangeProcessor`'s `BigDecimal` math) unconditionally in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`, so that no output can ever exceed the token actually held in `firstTokenBalance`/`secondTokenBalance`.

### Proof of Concept
1. Deploy/observe an exchange pair on a chain/branch where `allowHarden()` returns `false` (hardening proposal not activated) so `ExchangeCapsule.transaction()` uses the legacy `ExchangeProcessor` (`hardenedCalc = false`), skipping the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` guard [6](#0-5) .
2. Craft a `ExchangeTransactionContract` with `sellTokenQuant` chosen at extreme ratios relative to the pool's small `buyTokenBalance` such that `ExchangeProcessor.exchange()`'s floating point `Math.pow` computation (in `exchangeToSupply`/`exchangeFromSupply`) returns a `buyTokenQuant` larger than `buyTokenBalance` [7](#0-6) .
3. Submit the transaction; `ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction()`, receives the oversized `anotherTokenQuant`, credits it to the caller via `addAssetAmountV2`/`setBalance`, and persists the pool capsule with a negative or nonsensical reserve balance [5](#0-4) .
4. Subsequent legitimate withdrawals from the same pool fail or under-deliver because the tracked reserve no longer matches actual backing, confirming fund loss/unbacked balance.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
