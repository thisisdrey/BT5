The `ALLOW_HARDEN_EXCHANGE_CALCULATION` feature flag, which is supposed to *harden* (i.e. make safer) the bonding-curve math used by `ExchangeTransactionContract`, actually disables the node's global rejection of that same contract type once turned on.

### Title
Enabling `ALLOW_HARDEN_EXCHANGE_CALCULATION` re-activates the deprecated, unsafe `ExchangeTransactionContract` code path that was globally disabled - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
`Manager.isExchangeTransaction()` is used in two safety-critical places: to reject `ExchangeTransactionContract` transactions in `pushTransaction()` and to skip them when packing a block in `generateBlock()`. Its very first line short-circuits to `false` whenever `allowHardenExchangeCalculation()` is enabled, meaning the "hardening" flag paradoxically turns the exchange feature back on network-wide instead of only hardening its math.

### Finding Description
`pushTransaction()` explicitly guards against `ExchangeTransactionContract` being broadcast at all: [1](#0-0) 
and block generation skips any exchange transaction sitting in the pending pool: [2](#0-1) 

Both checks funnel through the same private helper: [3](#0-2) 

The helper's *first* condition is `if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) { return false; }` — i.e., if the "harden exchange calculation" dynamic parameter is `1`, `isExchangeTransaction()` unconditionally returns `false` for every transaction, regardless of its actual contract type. This means:

- `pushTransaction()`'s `ExchangeTransactionContract is rejected` guard is bypassed, so exchange transactions are accepted into the pending queue again.
- `generateBlock()` no longer skips them, so witnesses will pack and execute `ExchangeTransactionActuator` for these transactions.

This is confirmed directly by the repo's own test, which documents the bypass as intended behavior rather than a bug: [4](#0-3) 

The naming and stated intent of `ALLOW_HARDEN_EXCHANGE_CALCULATION` (per `ProposalUtil` and `AbstractExchangeActuator.allowHarden()`) is only to switch the arithmetic backend of `ExchangeCapsule.transaction()` to `SafeExchangeProcessor`, a safer/overflow-checked implementation of the constant-product/bancor formula: [5](#0-4) [6](#0-5) 

Nowhere does the SR-proposal validation for this parameter (`ProposalUtil.java`, case `ALLOW_HARDEN_EXCHANGE_CALCULATION`) mention or intend re-enabling the previously-rejected `ExchangeTransactionContract` feature; a fork block gate (`VERSION_4_8_0_1`) was specifically added elsewhere (`rejectExchangeTransaction`) to permanently retire this legacy exchange feature: [7](#0-6) 
but that separate rejection path is never invoked from `pushTransaction()`/`generateBlock()` — only the flawed `isExchangeTransaction()` gate is used there, and it is trivially defeated by the harden flag.

This mirrors the audit's root cause pattern: a safety check (leverage bound / feature-disable gate) that is computed/consulted under one condition set but silently invalidated by an unrelated, seemingly protective parameter, letting a supposedly-retired and riskier code path execute in production without the intended restriction being enforced.

### Impact Explanation
Once a single active proposal sets `ALLOW_HARDEN_EXCHANGE_CALCULATION = 1` (any SR/committee-approved chain parameter change, which is normal operational governance, not a "malicious SR" attack), any unprivileged account can once again submit `ExchangeTransactionContract` transactions that will be accepted into the mempool and packed into blocks — even though the network intended to have fully retired this legacy bonding-curve exchange feature (evidenced by the dedicated `VERSION_4_8_0_1` fork-gated rejection elsewhere in the same file). This re-exposes the entire legacy `Exchange`/`ExchangeV2` transaction surface (`ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) to live user funds and complex bonding-curve/overflow arithmetic that the project evidently wanted gated off, resulting in unauthorized account balance/asset transfers occurring through a code path operators believed was disabled.

### Likelihood Explanation
Likelihood is high given normal chain operation: the flag is a standard dynamic-parameter proposal (`ProposalService`/`ProposalUtil`) gated only behind a fork version, not behind any exotic or malicious precondition. Any committee vote to enable exchange-math hardening — a change that sounds purely defensive — silently and unintentionally reopens the whole legacy exchange feature for all users.

### Recommendation
Decouple the "harden calculation" flag from the "is this an exchange transaction" gate. `isExchangeTransaction()` should identify the contract type purely by `ContractType.ExchangeTransactionContract`, independent of `allowHardenExchangeCalculation()`. If exchange transactions should remain rejected post-fork, that rejection must not depend on, or be revocable by, the hardening flag.

### Proof of Concept
1. Chain is past `VERSION_4_8_0_1` so `ExchangeTransactionContract` is normally rejected via `isExchangeTransaction()` returning `true` in `pushTransaction()`.
2. Committee/SR passes a proposal setting `ALLOW_HARDEN_EXCHANGE_CALCULATION = 1` (a legitimate, unrelated proposal meant only to improve arithmetic safety).
3. `DynamicPropertiesStore.allowHardenExchangeCalculation()` now returns `true`.
4. Any user broadcasts an `ExchangeTransactionContract` transaction. `Manager.pushTransaction()` calls `isExchangeTransaction(trx.getInstance())`, which now returns `false` (per line 1810-1812), so the `"ExchangeTransactionContract is rejected"` guard is skipped and the transaction enters the pending pool.
5. During block generation, `generateBlock()`'s `isExchangeTransaction(transaction)` check also returns `false`, so the transaction is not skipped and is executed via `ExchangeTransactionActuator`, moving TRX/TRC10 balances through the legacy exchange pools.
6. This is directly reproduced by the existing repo test `isExchangeTransactionBypassedWhenHardenedEnabled`, which asserts the bypass occurs when the harden flag is set: [8](#0-7)

  private boolean isExchangeTransaction(Transaction transaction) {
    if (getDynamicPropertiesStore().allowHardenExchangeCalculation()) {
      return false;
    }
    Contract contract = transaction.getRawData().getContract(0);
    switch (contract.getType()) {
      case ExchangeTransactionContract: {
        return true;
      }
      default:
        return false;
    }
  }
