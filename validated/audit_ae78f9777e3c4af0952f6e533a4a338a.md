### Title
Attacker can permanently block a victim from depositing new collateral types by dust-filling their `depositTokensOfAccount` list up to `MAX_TOKENS_PER_USER` - (File: contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
`DepositToken._transfer` unconditionally registers the token in the recipient's per-account deposit-token list via `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero (DepositToken.sol L517-520). `Pool` enforces a `MAX_TOKENS_PER_USER` cap on that list. An unprivileged attacker who holds any balance of the pool's deposit tokens can `transfer` (or `transferFrom` with self-allowance) 1 wei of each deposit token to a victim, filling the victim's list to the cap. Once full, every subsequent operation that would add a new deposit-token entry for the victim reverts — most importantly `DepositToken.deposit(..., onBehalfOf_=victim)` into any collateral type the victim does not already hold (DepositToken.sol L486-488 reverts inside `_mint`). This is the same bug class as the reference report: missing validation of attacker-controlled input lets a third party poison a per-account registry, after which honest usage reverts and the affected functionality halts.

### Finding Description
- `DepositToken.transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked`, L348-376). There is no check that the *recipient* consents to or has capacity for a new token entry.
- `_transfer` then calls `pool.addToDepositTokensOfAccount(recipient_)` on any first-time receipt of a dust amount (L517-520). `Pool.addToDepositTokensOfAccount` pushes into `depositTokensOfAccount` which is bounded by `MAX_TOKENS_PER_USER` (contracts/Pool.sol). Once the set reaches the cap, adding a further distinct token reverts.
- `DepositToken.deposit` mints via `_mint`, which calls `pool.addToDepositTokensOfAccount(account_)` for first-time holders (L486-488). For a victim whose list was filled by the attacker, `deposit` into any new collateral token reverts inside `_mint`, after the underlying `safeTransferFrom` — the whole transaction rolls back.
- Unlike the beacon-chain case, removal paths still work: `_burn`/`_transfer` to zero removes entries (L460-462, L523-525), so the victim can still withdraw or transfer out existing holdings. However, a victim who needs to *add* a different collateral type — e.g., to restore health factor and avoid liquidation — is blocked, because the new token can never be registered.
- No modifier stops this: `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists` all pass for normal transfers; `SynthContext` sender resolution doesn't restrict recipients; no signature/consent check exists on the recipient side.

### Impact Explanation
Temporary freezing / liveness failure of funds: the victim cannot deposit any collateral type not already in their list, and cannot receive transfers of new deposit tokens. If the victim's position drifts toward the liquidation threshold, they cannot top up with a new collateral type (e.g., a stablecoin deposit token) to avoid `Pool.liquidate` — a forced-loss path that would otherwise be preventable. The griefing also propagates to liquidation: `DepositToken.seize` (L343-345) routes through the same `_transfer`, so a liquidator whose own list is capped cannot receive a new seized token, degrading liquidation liveness for that token.

### Likelihood Explanation
Fully permissionless: the attacker needs only dust balances of the pool's deposit tokens (obtainable by depositing 1 wei of each underlying themselves) and gas. Cost scales linearly with `MAX_TOKENS_PER_USER` and the number of registered `DepositToken`s; on deployments with many collaterals (mainnet/base pools have numerous deposit tokens) filling the cap is cheap. No privileged role, oracle manipulation, or timing dependence is required. The attack must be repeated per victim but can be front-run against any account attempting to onboard new collateral.

### Recommendation
Mirror the beacon-spec fix ("validate before accepting") on the recipient side: either
1. Do not auto-register on transfers — only register in `_mint` (deposit/seize paths where the protocol itself credits the account), keeping `MAX_TOKENS_PER_USER` as a deposit-time check, or
2. Allow the recipient list to exceed the cap via inbound transfers but enforce the cap only at deposit time, or
3. Make registration opt-in/removable so a victim can prune attacker-inserted dust entries (a `removeDepositTokenOfAccount(account, token)` escape callable by the account when its balance is the dust amount).

Option 1 is simplest: a transferred msdTOKEN position doesn't need list membership for withdrawal (the sender's own entry handles burn), and `debtPositionOf`/`depositOf` aggregation should skip zero-value entries.

### Proof of Concept
Hardhat (existing test harness `test/Pool.test.ts` deploys Pool + multiple DepositTokens):

```ts
// attacker holds dust of every DepositToken
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1); // registers each token
}
const list = await pool.getDepositTokensOfAccount(victim.address);
// assert list.length === MAX_TOKENS_PER_USER

// victim tries to deposit into a collateral not in their list
await underlying.connect(victim).approve(newDepositToken.address, amount);
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.reverted; // addToDepositTokensOfAccount hits the cap inside _mint
```

Note: I verified the unconditional `addToDepositTokensOfAccount` call in `DepositToken._transfer`/`_mint` and the presence of `MAX_TOKENS_PER_USER` in `Pool.sol`, but index limits prevented me from reading the exact revert branch in `Pool.addToDepositTokensOfAccount`; the PoC assumes (consistent with the deployed bytecode constants in `deployments/*/Pool.json`) the cap reverts on overflow rather than silently dropping. If the cap silently no-ops instead, severity degrades to accounting inaccuracy only.
