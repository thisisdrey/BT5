Audit Report

## Title
Outbound Queue V2 pays relayer reward and clears the pending order regardless of Ethereum-side execution `success` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`Pallet::process_delivery_receipt` in the Snowbridge Outbound Queue V2 pallet registers the relayer reward and permanently removes the `PendingOrders` entry for a nonce based solely on the gateway address matching and the order existing — it never inspects `receipt.success`, even though that field is decoded directly from the Ethereum `InboundMessageDispatched(nonce, topic, success, reward_address)` event specifically to signal whether execution actually succeeded. A codebase-wide search confirms `receipt.success` (or `.success` on the `DeliveryReceipt`) is read nowhere outside its own struct decode.

## Finding Description
`DeliveryReceipt::try_from` decodes `success` from the Ethereum event log at [1](#0-0) , populating the field defined at [2](#0-1) .

`submit_delivery_receipt`, callable by any signed account, verifies only that the log/proof is authentic and decodes it, then forwards the result directly to `process_delivery_receipt` without touching `success`: [3](#0-2) .

`process_delivery_receipt` checks only `T::GatewayAddress::get() == receipt.gateway` and that a `PendingOrder` exists for `receipt.nonce`, then unconditionally pays `order.fee` via `T::RewardPayment::register_reward` and removes the `PendingOrders` entry, emitting `MessageDelivered`: [4](#0-3) . The `success` field is never referenced in this function or anywhere else in the pallet.

The pallet's own doc comment describes the intended flow as gating step 10 on the message having "been verified **and executed**", confirming `success` was meant to be checked before paying the reward and clearing the order: [5](#0-4) . Since `<PendingOrders<T>>::remove(nonce)` executes unconditionally, once any valid receipt (successful or not) is submitted for a nonce, there is no path to retry or resend the message — this is a permanent state transition decoupled from actual execution outcome.

## Impact Explanation
If Ethereum-side execution of a message's commands fails (e.g., insufficient gas budget from `T::GasMeter::maximum_dispatch_gas_used_at_most`, or any command revert), `InboundMessageDispatched` is emitted with `success = false`, yet a relayer submitting this receipt is still paid `order.fee` in full and the `PendingOrders` entry is deleted, permanently foreclosing retry of the failed cross-chain action. This is a duplicate/wrongful settlement (reward paid without correct outcome) combined with a permanent bridge-state lock on the affected nonce, both within scope of the accepted impact categories.

## Likelihood Explanation
`submit_delivery_receipt` is a public, unprivileged extrinsic callable by any signed account acting as relayer; no governance or validator collusion is needed. A `success=false` event is a normal, reachable outcome of the existing gas-metering design (`T::GasMeter::maximum_dispatch_gas_used_at_most`), so the exploit path requires no protocol violation, only submission of a legitimately proof-verified receipt for a message whose real Ethereum execution failed.

## Recommendation
Check `receipt.success` in `process_delivery_receipt` before paying the reward. On `success == false`, withhold or reduce the reward, retain the `PendingOrders` entry (or move it to a distinct failed/retry state) instead of unconditionally removing it, and emit a distinct failure event (e.g., `MessageDeliveryFailed`) rather than `MessageDelivered`.

## Proof of Concept
1. A message with a command whose real Ethereum execution cost exceeds the gas committed via `OutboundCommandWrapper.gas` is queued, creating a `PendingOrder` with non-zero `fee` (see `do_process_message`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs` lines 426-436).
2. The relayer submits the message to the Ethereum Gateway with exactly the committed gas, sufficient for the transaction to complete and emit the event, but insufficient for the command to fully execute, resulting in `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. The relayer calls `submit_delivery_receipt` with a valid proof of that log; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success=false`.
4. `process_delivery_receipt` checks only `gateway` and nonce existence, pays `order.fee` to `reward_account`, and removes the `PendingOrders` entry — despite `success == false` and the intended recipient never receiving the unlock/mint/agent-call effect, with no path left to retry the nonce.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
