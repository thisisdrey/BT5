### Title
Market order funds can be permanently frozen when MARKET_CANCEL_FEE is raised above a user's remaining balance - ([File: actuator/src/main/java/org/tron/core/actuator/MarketCancelOrderActuator.java])

### Summary
`MarketSellAssetActuator` locks a user's TRX/TRC10 tokens into an on-chain order book entry when a `MarketSellAssetContract` is broadcast, and the only way to reclaim any unmatched remainder is `MarketCancelOrderContract`, executed by `MarketCancelOrderActuator`. Both the sell action and the cancel action are gated by independent, committee-controlled dynamic fees (`MARKET_SELL_FEE` and `MARKET_CANCEL_FEE`), which can be changed at any time via a governance proposal, exactly analogous to the reported `counterpartyFee`/`finalizationFee` mismatch. If `MARKET_CANCEL_FEE` is raised (via `ProposalService`) to a value greater than a user's post-lock spendable TRX balance while they have an active, unmatched (or partially matched) order, the user's cancel transaction will permanently revert, and there is no other code path to return the escrowed sell-side funds.

### Finding Description
`MarketSellAssetActuator.execute` moves the seller's TRX/token into escrow (`transferBalanceOrToken`) and creates a `MarketOrderCapsule` stored in the order book (`createAndSaveOrder`/`saveRemainOrder`) if it isn't fully matched immediately: [1](#0-0) 

The remaining sell-side funds sit in escrow until either (a) a future taker matches the order (`matchOrder`), which is entirely dependent on external counterparties and market conditions, or (b) the owner cancels via `MarketCancelOrderContract`.

`MarketCancelOrderActuator.validate` requires the owner's spendable balance to cover `calcFee()`, which reads the *current* value of `MARKET_CANCEL_FEE` from `DynamicPropertiesStore`, not the value that existed when the order was placed: [2](#0-1) [3](#0-2) 

`MARKET_CANCEL_FEE` is a committee-adjustable chain parameter, processed unconditionally and immediately whenever a proposal is approved: [4](#0-3) 

and its documented valid range extends up to 10,000 TRX: [5](#0-4) 

Because a user who places a sell order commonly spends most of their liquid TRX into the escrowed order (particularly when selling TRX itself, via `transferBalanceOrToken`), their remaining spendable balance can easily fall below a newly raised `MARKET_CANCEL_FEE`. When that happens, `validate()` throws `"No enough balance !"` on every future cancel attempt, and since `execute()` is the only code path that calls `MarketUtils.returnSellTokenRemain` to release escrowed funds outside of a match, the user's remaining sell-side balance becomes permanently unreachable — identical in structure to the reported `counterpartyFee`/`finalizationFee` deadlock, where one leg of a two-step, fee-gated flow becomes unexecutable after an independent fee parameter is updated mid-flight, with no rescue mechanism.

### Impact Explanation
A user's escrowed TRX or TRC10 tokens from an unmatched or partially matched sell order can become permanently frozen with no path to recovery: the order cannot be canceled (insufficient balance to pay the now-higher `MARKET_CANCEL_FEE`) and there is no guarantee the order will ever fully match. This is a direct, unrecoverable loss of user funds triggered purely by a routine governance parameter update combined with normal user activity — no malicious actor is required, only an ordinary committee proposal execution racing an ordinary user transaction.

### Likelihood Explanation
`ALLOW_MARKET_TRANSACTION`/market fee proposals are ordinary committee governance actions that are processed without any check against outstanding open orders (`ProposalService.process`, case `MARKET_CANCEL_FEE`). Any user with an active order at the moment a `MARKET_CANCEL_FEE` increase takes effect, and whose free balance doesn't happen to exceed the new fee, is affected. Given orders can remain open indefinitely (there is no expiry), the window of exposure for any given order is effectively unbounded, making this a realistically reachable condition rather than a purely theoretical one.

### Recommendation
- Snapshot the applicable cancel fee (and/or the fee cap) into the `MarketOrderCapsule` at order-creation time, and use that stored fee when validating cancellation, rather than reading the live `MARKET_CANCEL_FEE`.
- Alternatively, allow cancellation to succeed even when the balance is insufficient to cover the full fee by capping the charged fee to the available balance (analogous to a rescue/force-cancel path), ensuring escrowed funds can always be returned to their owner regardless of subsequent fee changes.
- Add a safeguard so that increases to `MARKET_CANCEL_FEE` cannot exceed what unmatched sellers can be reasonably expected to still hold, or provide a governance-independent rescue/cancel function.

### Proof of Concept
1. User calls `MarketSellAssetContract` selling TRX (`sellTokenId = "_"`), moving most of their balance into escrow via `transferBalanceOrToken`, and paying `MARKET_SELL_FEE` at that time — see execution flow in `MarketSellAssetActuator.execute`: [6](#0-5) 
2. Order does not fully match and remains active in the order book (`saveRemainOrder`).
3. Committee approves a proposal raising `MARKET_CANCEL_FEE` above the user's remaining spendable balance; `ProposalService.process` applies it immediately: [4](#0-3) 
4. User broadcasts `MarketCancelOrderContract` to cancel and reclaim escrowed TRX; `validate()` throws `ContractValidateException("No enough balance !")` because `ownerAccount.getBalance() < calcFee()`: [7](#0-6) 
5. Every subsequent cancel attempt fails identically. The escrowed TRX remains locked in `MarketOrderCapsule` state with `sellTokenQuantityRemain > 0`, unreachable except by an external match that may never occur.
