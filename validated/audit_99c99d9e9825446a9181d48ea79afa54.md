### Title
Oracle pallet's `get`/`get_value` return aggregated values with no read-time staleness check, unlike the write-time expiry check in `combine_data` - (File: `substrate/frame/honzon/oracle/src/lib.rs`)

### Summary
The core invariant broken in the source report is: a function that can return a value together with a "this value is invalid/expired" indicator is consumed in one place with the indicator checked (`KangarooVault.getTokenPrice`), and in another place without checking it (`LiquidityPool.getTokenPrice`/`_getTotalMargin`), letting stale/invalid data silently drive fund-moving logic. The same class of bug exists in `pallet_oracle`: freshness (`expires_in`) is enforced only inside `DefaultCombineData::combine_data`, which runs solely on the write path (`feed_values`/`feed_value`). The read path (`Pallet::get`, `Pallet::get_value`, and the `DataProvider`/`DataProviderExtended` trait implementations that external pallets are meant to consume) never re-checks freshness and simply returns whatever is sitting in the `Values` storage map, however old it is.

### Finding Description
`DefaultCombineData::combine_data` filters out stale raw feeds using `ExpiresIn` before computing the median, but this filtering is only invoked as a side effect of a *new* feed arriving: [1](#0-0) 

```
fn combine_data(...) -> Option<TimestampedValueOf<T, I>> {
    let expires_in = ExpiresIn::get();
    let now = T::Time::now();
    values.retain(|x| x.timestamp.saturating_add(expires_in) > now);
    ...
}
```
This is called from `do_feed_values`, which only runs when `feed_values`/`feed_value` is dispatched: [2](#0-1) 

If oracle members stop feeding (go offline, get removed from membership, or simply no one calls `feed_values` again), the previously aggregated entry in `Values` storage is never revisited, expired, or cleared. The read-side API — `Pallet::get`, the `#[pallet::view_functions]` `get_value`, and the `DataProvider`/`DataProviderExtended` trait implementations that other pallets are explicitly meant to use for price consumption — simply return the stored value verbatim with no freshness check at all: [3](#0-2) [4](#0-3) [5](#0-4) 

`TimestampedValue` does carry a `timestamp` field, so the pallet itself has all the information needed to detect staleness on read (exactly analogous to `isInvalid` in the source report), but no consumer-facing function checks `timestamp.saturating_add(ExpiresIn) > now` before handing the value out. This is the same asymmetry as the report: one code path (write/`combine_data`) enforces the validity condition, the other (read/`get`, `get_value`, `DataProvider::get`) silently trusts the value.

The pallet is wired into the live node runtime: [6](#0-5) 
with `CombineData = DefaultCombineData<..., ConstU64<3600>>`, i.e. a 3600ms/expiry window is configured but that guarantee only holds for the value at the moment it was last aggregated — it is never re-validated afterward.

### Impact Explanation
`pallet_oracle` is a generic price/data-feed primitive designed (per its own module docs) to let other pallets — CDP/collateral engines, PSM-like stablecoin modules, DEX pallets — consume trusted, "fresh" data via `DataProvider`/`DataProviderExtended`. Because the freshness guarantee silently disappears the moment feeding stops (e.g., all oracle members are removed via `change_members_sorted`, or members simply go offline/get slashed/rotated out without any new push), any downstream pallet built against this primitive's `get`/`get_value`/`DataProvider::get` will use an arbitrarily stale value indefinitely, with no error, no revert, and no on-chain signal that the data is stale. This mirrors exactly the reported impact class: valuation/margin computations built on unchecked, potentially invalid external data — which can misprice collateral, mis-value assets, or allow deposits/withdrawals/liquidations at incorrect terms in any consumer pallet, i.e. a runtime bug that compromises intended behavior of value-bearing logic built on top of this primitive.

### Likelihood Explanation
No privileged or malicious actor is required. The condition (feeders stop submitting, or oracle membership empties/rotates without immediate re-feed) is an entirely ordinary operational scenario, not an attack requiring a malicious node, relayer, or governance actor. Any pallet author who trusts `DataProvider::get`/`get_value` at face value — following the pallet's own advertised freshness guarantee — inherits this silent gap by default; the vulnerable condition triggers passively over time rather than needing any exploit primitive.

### Recommendation
Make freshness a property enforced at read time, not only at write/aggregation time:
- Add an `is_valid`/`is_outdated` check to `Pallet::get`, `get_value`, and the `DataProvider`/`DataProviderExtended` implementations, comparing the stored `TimestampedValue.timestamp` against `ExpiresIn`/`T::Time::now()` and returning `None` (or an explicit invalid indicator) when stale, exactly as `combine_data` already does for raw values.
- Alternatively, expose the timestamp explicitly in the `DataProvider` trait contract (or a new `DataProviderExtended` variant) so that every consumer is forced to check freshness itself, rather than relying on an implicit and easily-bypassed write-time-only guarantee.

### Proof of Concept
1. Configure `pallet_oracle` with `ExpiresIn = 3600` (as in the node runtime) and a small set of oracle members.
2. Members feed a price for key `K` three times so `combine_data` produces `Values[K] = TimestampedValue { value: P, timestamp: T0 }`.
3. Remove all oracle members via governance/membership rotation (`change_members_sorted`), or simply have them stop calling `feed_values` — no new feed ever arrives.
4. Advance the chain far beyond `T0 + ExpiresIn` (e.g., simulate `Timestamp::set_timestamp` far in the future, as already done in `should_combined_data`/`get_all_values_should_work` tests which show `Values` persisting across large timestamp jumps): [7](#0-6) 
5. Call `Pallet::get(&K)` / `get_value(K)` / any consumer using `DataProvider::get(&K)`. It still returns `Some(TimestampedValue { value: P, timestamp: T0 })` even though `T0` is far past `ExpiresIn` — no staleness error is raised, exactly mirroring `LiquidityPool.getTokenPrice`'s failure to reject an invalid/stale margin value that `KangarooVault.getTokenPrice` correctly rejects.

	fn do_feed_values(who: T::AccountId, values: Vec<(T::OracleKey, T::OracleValue)>) {
		let now = T::Time::now();
		for (key, value) in &values {
			let timestamped = TimestampedValue { value: value.clone(), timestamp: now };
			RawValues::<T, I>::insert(&who, key, timestamped);

			// Update `Values` storage if `combined` yielded result.

				<Values<T, I>>::insert(key, combined);
			}

			T::OnNewData::on_new_data(&who, key, value);
		}
		Self::deposit_event(Event::NewFeedData { sender: who, values });
	}
