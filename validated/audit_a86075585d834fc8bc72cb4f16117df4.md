### Title
StackerDB chunk push is broadcast to the network before the storing transaction is committed - ([File: stackslib/src/net/relay.rs])

### Summary
`PeerNetwork::process_stacker_db_chunks` accepts new StackerDB chunks from a sync peer, writes them into an open (uncommitted) SQL transaction, and immediately re-broadcasts a `StackerDBPushChunk` gossip message to the rest of the network for each accepted chunk — all *before* the transaction that actually persists the chunk is committed. This mirrors the class of bug in the referenced report: authoritative external state ("we have stored version N") is announced based on data that is not yet durably/finally committed, and can end up disagreeing with what actually lands in the store.

### Finding Description
In `process_stacker_db_chunks`, chunks for a given StackerDB contract are all validated and written using one `tx = self.stacker_dbs.tx_begin(config.clone())?` transaction: [1](#0-0) 

For each chunk that `tx.try_replace_chunk` accepts, the node immediately relays the chunk to the rest of its peers via `self.p2p.broadcast_message(...)`: [2](#0-1) 

Only after *all* chunks for that contract across *all* sync results have been processed and broadcast does the code call `tx.commit()?`: [3](#0-2) 

Because `tx.commit()` can fail (it returns a `Result` and is propagated with `?`), or the node process can terminate/crash in the window between a chunk's `try_replace_chunk` success and the eventual `tx.commit()`, the SQLite transaction will be rolled back (on `Drop` without commit, per normal transaction semantics) while the corresponding `StackerDBPushChunk` message has already been irrevocably sent to the network. This breaks the intended equality: *"a chunk this node gossips as stored is a chunk this node has durably stored."* After the rollback, the node's own StackerDB slot reverts to its prior (older) version, yet its peers now believe (and may propagate further, via chunk-inventory gossip) that a newer version exists and is available from this node. Any peer that later fetches that slot from this node will observe a mismatch between the previously-announced version and the actually-served (older) canonical data.

### Impact Explanation
This is reachable purely through the normal, unauthenticated StackerDB sync/relay path (`process_stacker_db_chunks` is called by `PeerNetwork` while relaying pushed/synced StackerDB chunks). The consequence is a network being told about StackerDB slot state that the originating node does not durably possess, i.e. non-canonical state served/announced as canonical — matching the "steering a node off the tip via false inventory"/"serving non-canonical state as canonical" impact class described for High severity, applied here to StackerDB chunk inventories rather than the Stacks chain tip.

### Likelihood Explanation
The window in which this matters requires either (a) a `tx.commit()` failure (a DB error) after one or more chunks in the batch have already been broadcast, or (b) a process crash/restart between broadcasting and commit. Both are transient/operational conditions rather than something a remote attacker can trigger with a single crafted message, so likelihood is comparatively low. However, no attacker privilege or secret key is needed — any StackerDB sync activity can hit this code path, and multi-chunk batches per contract widen the exposed window (only the final chunk's broadcast is close to the commit; earlier chunks in the same batch have an extended exposure period).

### Recommendation
Move the `self.p2p.broadcast_message(...)` calls to occur only after `tx.commit()` succeeds for the whole batch (e.g., collect chunks-to-broadcast during the loop, call `tx.commit()?`, and only then iterate and broadcast), mirroring the referenced fix pattern of finalizing state before using it to drive external announcements/rebases.

### Proof of Concept
1. A peer's StackerDB sync path produces one or more valid `chunks_to_store` for a contract that this node also configures.
2. In `process_stacker_db_chunks`, the first chunk is written via `tx.try_replace_chunk` (uncommitted) and then immediately broadcast via `p2p.broadcast_message`, notifying the rest of the network.
3. Before `tx.commit()` runs (e.g., due to a subsequent DB error on a later chunk in the same batch, or a process crash/restart), the transaction is rolled back.
4. The node's persisted StackerDB slot reverts to its previous version, but peers that received the broadcast in step 2 now hold/propagate stale inventory information claiming this node has the newer chunk, which subsequent fetches from this node will contradict. [4](#0-3)
