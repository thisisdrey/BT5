The reported CVE describes a Perl XS bug where `Sodium.xs` casts a `STRLEN` (`size_t`) to `unsigned long long` before passing a length pointer into libsodium, causing a width mismatch on 32-bit systems (the C callee writes 8 bytes into a location the caller only reserved 4 bytes for). I searched the Go standard library's cgo-based cryptographic bindings (`crypto/internal/boring`) for an analogous pattern — a Go-side integer type passed to a C function's `size_t*` output parameter using a mismatched fixed-width type.

In `src/crypto/internal/boring/aes.go`, `src/crypto/internal/boring/rsa.go`, and `src/crypto/internal/boring/ecdh.go`, all length values passed across the cgo boundary are consistently converted with `C.size_t(len(...))`, and output-length pointers are declared as `C.size_t` (e.g. `var outLen C.size_t` in `DecryptRSAPKCS1`/`SignRSAPSS` at [1](#0-0) ), matching the underlying BoringSSL C prototypes exactly (`size_t*` in `goboringcrypto.h`, e.g. [2](#0-1) ). There is no place where a `size_t`-typed length/pointer is cast to a wider fixed type like `unsigned long long`/`uint64_t` before being handed to a C callee expecting `size_t*`, so the specific width-mismatch primitive from the CVE does not reproduce in this codebase. The cgo documentation and generated glue code (`src/cmd/cgo/doc.go`, `src/cmd/cgo/out.go`) also show cgo generates C type declarations (`GoUint64`, `size_t`, etc.) consistently matched to their Go counterparts rather than being manually re-cast by binding authors, which is the root cause class in the reported CVE.
