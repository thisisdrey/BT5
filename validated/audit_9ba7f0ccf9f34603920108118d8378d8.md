### Title
Proposal approval threshold uses live active-witness set instead of a snapshot, allowing the SR quorum denominator/eligible-approver set to shift after votes are cast - (File: `framework/src/main/java/org/tron/core/consensus/ProposalController.java`)

### Summary
This is a structural analog of the reported "un-snapshotted `totalVotingPower`" bug class. In java-tron, on-chain governance proposals (`ProposalCreateContract` / `ProposalApproveContract`) are approved by committee/witness "yes" votes, and the pass/fail threshold is computed as `activeWitnesses.size() * 7 / 10` where `activeWitnesses` is read live from `WitnessScheduleStore` at the moment the proposal is finally processed — not a snapshot taken when the proposal was created. Because the active-witness set is re-elected and rewritten every maintenance cycle, both the quorum denominator and the set of "valid" approvers can change multiple times between proposal creation and proposal expiration/processing, exactly mirroring the Party-protocol bug where `totalVotingPower` drifted between proposal creation and tallying.

### Finding Description
`ProposalCapsule.hasMostApprovals` filters previously-collected approvals against the *current* active witness list and computes the quorum against the *current* size of that list: [1](#0-0) 

This is invoked from `ProposalController.processProposal`, which is only run when the proposal has expired (i.e., at the end of its voting window), and always re-reads the witness set fresh from the store: [2](#0-1) 

Individual approvals are cast asynchronously via `ProposalApproveActuator`, which only validates that the caller is *currently* a registered witness at the time of the vote — it does not check whether the voter was part of the active-witness set that will ultimately be used for the quorum calculation, nor does it snapshot that set: [3](#0-2) 

The active-witness list itself is rewritten every maintenance cycle (roughly every 6 hours by default) as part of `MaintenanceManager.doMaintenance`, which recomputes vote tallies and calls `dposService.updateWitness(...)`, changing membership of the active set stored in `WitnessScheduleStore`: [4](#0-3) 

Since a `ProposalCapsule`'s `expirationTime` is typically several maintenance cycles away (governance proposals live for multiple maintenance periods), the active-witness list backing both the approver-eligibility filter and the quorum denominator in `hasMostApprovals` can be re-elected several times between when individual approvals are cast and when the proposal is finally tallied — unlike the Party bug where a single "total voting power" scalar drifts, here both the accepted-approver membership *and* the quorum size are live values rather than values pinned to proposal-creation time.

### Impact Explanation
* If the active-witness count/composition shrinks between votes being cast and proposal expiration, the effective quorum (70% of the *current*, possibly smaller, set) can be met even though it would not have met the 70% threshold of the *original* set at proposal-creation time — this can let a chain governance parameter change (fees, energy price, TVM feature flags, etc., processed in `ProposalService.process`) pass with less real support than the protocol intends.
* Conversely, if the active-witness set grows or is reshuffled, previously-cast approvals from witnesses who fell out of the active set are silently discarded (`hasMostApprovals` filters by current active membership), which can cause a proposal that should have passed to fail, or force it into limbo requiring re-approval from an entirely different witness cohort.
* Because chain governance proposals control critical dynamic parameters (fees, energy pricing, feature toggles such as `ALLOW_MARKET_TRANSACTION`, `ALLOW_TVM_ISTANBUL`, etc. — see `ProposalService.process`), a manipulated or accidental quorum shift can result in unauthorized parameter changes affecting the whole network, which is a chain-consensus-parameter integrity issue.

### Likelihood Explanation
This does not require any malicious behavior — it is a deterministic consequence of normal witness re-election happening on every maintenance cycle while proposals remain pending across multiple such cycles. Any witness (a role reachable by any account that stakes/gets elected, not a privileged pre-set party) casting an ordinary `ProposalApproveContract` transaction can trigger the drift; no privileged, malicious-SR, or p2p behavior is required — it manifests from routine `MaintenanceManager.doMaintenance()` witness reshuffles combined with the multi-cycle lifetime of proposals.

### Recommendation
Snapshot the active-witness set (or at minimum its size and membership) at proposal-creation time in `ProposalCapsule`, and use that snapshot — rather than the live `WitnessScheduleStore.getActiveWitnesses()` — both to validate which witnesses' approvals are eligible and to compute the quorum denominator in `hasMostApprovals`/`ProposalController.processProposal`.

### Proof of Concept
1. At time T0, active witness set is `W0` with `|W0| = 27`. A proposal `P` is created with `proposedTime = T0`, expiring several maintenance cycles later.
2. Witnesses in `W0` cast approvals via `ProposalApproveContract`, reaching e.g. 18/27 (~66.7%, just under 70%).
3. At a subsequent maintenance cycle (`MaintenanceManager.doMaintenance`), witness re-election changes the active set to `W1`, where some approving witnesses from `W0` are voted out and `|W1| < |W0|` (e.g. 24 due to fewer eligible candidates).
4. When `P` expires, `ProposalController.processProposal` calls `hasMostApprovals(W1)`. The approvals list is filtered against `W1` (losing votes from ousted witnesses), and the required threshold is now `24 * 7 / 10 ≈ 16` instead of the original `27 * 7 / 10 ≈ 18`. Depending on how many approving witnesses remained in `W1`, the proposal's pass/fail outcome flips compared to what it would have been judged against the `W0` snapshot at proposal-creation time — demonstrating the same "denominator drift" bug class as the Party `totalVotingPower` finding.

  public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    if (count != this.proposal.getApprovalsCount()) {
      List<ByteString> InvalidApprovalList = this.proposal.getApprovalsList().stream()
          .filter(witness -> !activeWitnesses.contains(witness)).collect(Collectors.toList());
      logger.info("InvalidApprovalList:" + getAddressStringList(InvalidApprovalList));
    }
    if (activeWitnesses.size() != MAX_ACTIVE_WITNESS_NUM) {
      logger.info("activeWitnesses size = {}", activeWitnesses.size());
    }
    return count >= activeWitnesses.size() * 7 / 10;

  public void processProposal(ProposalCapsule proposalCapsule) {

    List<ByteString> activeWitnesses = this.manager.getWitnessScheduleStore().getActiveWitnesses();
    if (proposalCapsule.hasMostApprovals(activeWitnesses)) {
      logger.info(
          "Processing proposal,id:{},it has received most approvals, "
              + "begin to set dynamic parameter:{}, "
              + "and set proposal state as APPROVED",
          proposalCapsule.getID(), proposalCapsule.getParameters());
      setDynamicParameters(proposalCapsule);
      proposalCapsule.setState(State.APPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);
    } else {
      logger.info(
          "Processing proposal,id:{}, "
              + "it has not received enough approvals, set proposal state as DISAPPROVED",
          proposalCapsule.getID());
      proposalCapsule.setState(State.DISAPPROVED);
      manager.getProposalStore().put(proposalCapsule.createDbKey(), proposalCapsule);
    }

  }
