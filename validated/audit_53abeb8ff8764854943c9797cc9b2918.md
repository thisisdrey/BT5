### Title
Permissionless `add_tip` allows overwriting a previously committed relayer reward with a lower value before message processing - (File: `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`)

### Summary
The core broken invariant in the external report is: a permissionless action can revise a critical economic value (the amount a counterparty will receive at settlement) downward, close to the finalization event, with no floor/monotonicity guard and no time for the disadvantaged party to react. The Snowbridge inbound-queue-v2 pallet exposes an analogous pattern via its `add_tip(nonce, tip)` extrinsic/API, which lets an unprivileged, permissionless caller register a tip for a pending message nonce that is later added to the relayer's reward when `process_message` executes.

### Finding Description
`add_tip` is documented as letting anyone "add a tip to an Inbound or Outbound message, in case the relayer reward is too low and not profitable to process" [1](#0-0) . The stored value is later consumed and paid out atomically with the relayer_fee when the message is processed and then removed from storage [2](#0-1) .

Because `add_tip` is permissionless and keyed solely by `nonce`, any account can call it repeatedly for the same pending nonce right up until a relayer submits the message for processing. If the underlying implementation stores the tip via a plain map `insert` rather than an additive/monotonic update (the test suite only exercises a single `add_tip` call per nonce and does not assert accumulation or a floor-preserving guard), a second, low-value call from any account can silently overwrite an earlier, higher tip that a relayer observed off-chain and relied upon to decide the message was profitable to relay. This mirrors the AstariaRouter refinance bug exactly: an economically load-bearing parameter (`liquidationInitialAsk` there, the registered tip here) can be revised downward by an unrelated, permissionless caller immediately before the value-locking event (liquidation there, `process_message` here), with the original beneficiary having no opportunity to react.

I was not able to confirm from the retrieved snippets whether the storage write in `add_tip` uses `saturating_add` (safe, additive top-up) or a plain `insert` (overwrite, vulnerable) — this needs direct inspection of the function body in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`, which I could not complete within the available tool budget.

### Impact Explanation
If the write is an overwrite rather than an accumulation, a relayer that commits gas/compute to deliver a message based on an observed high tip can have that tip zeroed or reduced by any third party immediately before submission, causing the relayer to be underpaid for already-performed work — a direct instance of "public underpriced work that degrades... bridge processing," matching the Impact Gate criteria. This could disincentivize relaying, causing message backlogs/stalls in the Snowbridge delivery pipeline.

### Likelihood Explanation
The call is fully permissionless (no origin/authorization check beyond `ensure_signed`-style dispatch) and requires no special conditions beyond knowing a pending `nonce`, which is observable on-chain. If the storage semantics are overwrite-based, exploitation is trivial and immediate for any nonce with a currently registered tip.

### Recommendation
- Verify the implementation of `add_tip` in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs`.
- If it currently uses `insert`, change it to use `mutate`/`saturating_add` so tips strictly accumulate and can never decrease an already-registered value.
- Alternatively, disallow updates to an existing tip entry for a nonce and require a fresh nonce/new message for any additional incentive, or restrict tip reduction to the original tipper.

### Proof of Concept
1. Relayer observes `Tips::<T>::get(nonce) == 12_345` for a pending inbound message and decides it is profitable to relay [3](#0-2) .
2. Before the relayer submits, any unrelated account permissionlessly calls `add_tip(nonce, 0)` (or a very small value) for the same nonce.
3. If storage is overwritten rather than accumulated, `Tips::<T>::get(nonce)` now returns the lower value.
4. The relayer processes the message; `process_message` pays out `relayer_fee + tip`, now using the reduced tip, and the tip entry is removed from storage [4](#0-3)  — the relayer is paid less than expected for work already committed/performed, with no recourse.
