### Title
Postponed receipts survive `DeleteAccount`/`CreateAccount`, allowing a stale self-targeted `AddKey(FullAccess)` to hijack a re-created account - ([File: runtime/runtime/src/lib.rs], [File: core/store/src/utils/mod.rs -> remove_account])

### Summary
`remove_account` only clears `TrieKey::Account`, `ContractCode`, `AccessKey`/gas-key nonces, and `ContractData` for a deleted account [1](#0-0) ; it never touches `TrieKey::PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` entries keyed by that account's `receiver_id`. `action_create_account` likewise creates a fresh empty `Account` without checking for or purging any leftover postponed-receipt state under the same account id [2](#0-1) . When the pending data dependency later resolves, `process_receipt` fetches and executes the stale postponed receipt exactly as if nothing happened [3](#0-2) , and `check_actor_permissions` for `AddKey` only checks `actor_id == account_id` (a "self-call" predecessor check), with no notion of account incarnation/generation [4](#0-3) .

### Finding Description
1. An account `A` (controlled by its then-owner) issues a self-targeted callback receipt with `receiver_id == A`, `predecessor_id == A`, and a non-empty `input_data_ids` list, whose actions include `Action::AddKey(FullAccess, pubkey_X)`. Because it has an unmet input data dependency, `process_action_receipt` stores it via `set_postponed_receipt` under `TrieKey::PostponedReceipt { receiver_id: A, receipt_id }`, plus `PostponedReceiptId`/`PendingDataCount` bookkeeping entries, all keyed only by `account_id`/`receiver_id` — not by any account generation or state root snapshot.
2. Before the dependency resolves, `A`'s owner submits `Action::DeleteAccount`. `action_delete_account` calls `remove_account(state_update, account_id)`, which removes `Account`, `ContractCode`, access/gas keys, and `ContractData`, but never removes the `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` trie entries for `A` [5](#0-4) . This is the same prefix (`trie_key_parsers::get_raw_prefix_for_access_keys`) scoped strictly to column `ACCESS_KEY`, so it cannot and does not reach column `POSTPONED_RECEIPT` (col 6) or `POSTPONED_RECEIPT_ID` (col 4).
3. Any party then calls `Action::CreateAccount` for the same account id `A`. `action_create_account` performs only naming/permission checks and installs a brand-new empty `Account` — it never checks for or clears residual postponed-receipt state tied to `A` [2](#0-1) .
4. When the outstanding data dependency eventually resolves (a `Data` receipt for the recorded `data_id` arrives — something the original schedulers of the callback control the timing of), `process_receipt` looks up `PostponedReceiptId`/`PendingDataCount` for `A`, finds the count reaches zero, fetches the still-present postponed receipt, and calls `apply_action_receipt` on it exactly as if the account were untouched [6](#0-5) .
5. Inside that execution, `check_actor_permissions` for `Action::AddKey` only checks `actor_id == account_id` [4](#0-3) ; since the receipt's `predecessor_id` is `A` (a self-call) and `account_id` is still `A`, the check passes trivially even though the underlying account has been deleted and re-created by an unrelated party in the interim. `action_add_key` then installs the full-access key for `pubkey_X` on the brand-new `A` [7](#0-6) , giving the party that authored the stale receipt full control of the new account without the new owner's consent.

This is not blocked by any existing check: `remove_account`'s scope, `action_create_account`'s lack of state cleanup/validation, and `check_actor_permissions`'s purely name-based self-call authorization all fail to account for account "incarnations." NEAR account ids have no generation counter, so a receipt authorized under the old incarnation is indistinguishable from one authorized under the new incarnation.

### Impact Explanation
This is an authorization-escalation bug: a party that had legitimate self-call permission on an account's *previous* incarnation can gain a full-access key — and therefore complete control — over a *newly created, unrelated* account occupying the same account id, without any action or consent from the new owner. This maps to NEAR's "authorization escalation across accounts or promises" bounty category and can lead to outright theft of the new account's funds/contract control once the attacker adds their key.

### Likelihood Explanation
Exploitability requires a fairly specific but fully unprivileged sequence: (1) the account id must actually be deleted and then re-created by a different, unsuspecting party before the pending data dependency resolves — a scenario most plausible with squatted/valuable short or freed account names where re-registration happens quickly after deletion; (2) the attacker (or a party who once had access) must have deliberately staged a self-targeted, data-dependent `AddKey(FullAccess)` callback before losing/relinquishing the account, and must be able to trigger resolution of the outstanding data dependency at the desired time (fully attacker-controlled, since the dependency is authored and can be satisfied by the attacker's own cross-contract call chain). No validator, node, or leaked-key access is needed — only ordinary transaction submission (`CreateAccount`, `DeleteAccount`, cross-contract calls with `input_data_ids`, `AddKey`). The attack is repeatable against any account name subject to delete+recreate churn.

### Recommendation
Purge all account-scoped receipt-dependency state (`PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, and ideally `ReceivedData`) for `account_id` inside `remove_account` (or in `action_delete_account` immediately around the `remove_account` call), using the corresponding trie key prefixes for those columns, mirroring how access keys and contract data are already swept. Alternatively/additionally, have `action_create_account` refuse to create (or explicitly wipe) an account id that still has unresolved postponed receipts pending in state, and/or bind postponed receipts to an account "generation" so `apply_action_receipt` can detect and reject execution against a different incarnation of the receiver.

### Proof of Concept
Integration/apply-path test (in `runtime/runtime/src/tests/apply.rs`, following the pattern of `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create account `A` owned by signer `S1`, with a full-access key `pk_S1`.
2. Build and apply an action receipt with `receiver_id = A`, `predecessor_id = A`, `input_data_ids = [data_id]`, actions `[AddKey(FullAccess, pk_attacker)]`. Confirm it is stored as a postponed receipt (state has `TrieKey::PostponedReceipt{receiver_id: A, ..}` and no access key `pk_attacker` yet).
3. Apply a `DeleteAccount` receipt for `A` (predecessor `A`, beneficiary some other account) — confirm `A`'s `Account`/`AccessKey` records are gone.
4. Apply a `CreateAccount` receipt creating `A` again, this time as a sub-account of a different predecessor/signer `S2` (simulating a different owner), followed by adding `S2`'s own key.
5. Apply the `Data` receipt satisfying `data_id`, resolving the postponed receipt.
6. Assert: the new `A`'s access-key set now unexpectedly contains `pk_attacker` with `FullAccess` permission — demonstrating the escalation. Expected (fixed) behavior: `pk_attacker` must NOT be present, either because the postponed receipt was purged on delete or because execution was rejected due to incarnation mismatch.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn action_create_account(
    fee_config: &RuntimeFeesConfig,
    account_creation_config: &AccountCreationConfig,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    account_id: &AccountId,
    predecessor_id: &AccountId,
    result: &mut ActionResult,
) {
    if account_id.is_top_level() {
        if account_id.len() < account_creation_config.min_allowed_top_level_account_length as usize
            && predecessor_id != &account_creation_config.registrar_account_id
        {
            // A short top-level account ID can only be created registrar account.
            result.result = Err(ActionErrorKind::CreateAccountOnlyByRegistrar {
                account_id: account_id.clone(),
                registrar_account_id: account_creation_config.registrar_account_id.clone(),
                predecessor_id: predecessor_id.clone(),
            }
            .into());
            return;
        } else {
            // OK: Valid top-level Account ID
        }
    } else if !account_id.is_sub_account_of(predecessor_id) {
        // The sub-account can only be created by its root account. E.g. `alice.near` only by `near`
        result.result = Err(ActionErrorKind::CreateAccountNotAllowed {
            account_id: account_id.clone(),
            predecessor_id: predecessor_id.clone(),
        }
        .into());
        return;
    } else {
        // OK: Valid sub-account ID by proper predecessor.
    }

    *actor_id = account_id.clone();
    *account = Some(Account::new(
        Balance::ZERO,
        Balance::ZERO,
        AccountContract::None,
        fee_config.storage_usage_config.num_bytes_account,
    ));
}

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}
