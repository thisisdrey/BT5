### Title
Unbounded `VotesStore` iteration in `Wallet.countVote()`/`MaintenanceManager.doMaintenance()` allows cheap-vote spam to DOS the `getPaginatedNowWitnessList` query API and block maintenance processing - ([File: framework/src/main/java/org/tron/core/Wallet.java])

### Summary
`GetPaginatedNowWitnessListServlet` (an unauthenticated HTTP/gRPC endpoint reachable by any anonymous client) calls `Wallet.getPaginatedNowWitnessList()`, which internally calls `Wallet.countVote(VotesStore)`. This method iterates over *every* entry currently stored in `VotesStore` with no limit, cap, or pagination — the only bound applied (`WITNESS_COUNT_LIMIT_MAX`) is on the *output* witness page, not on the number of `VotesCapsule` records scanned. [1](#0-0) [2](#0-1) 

`VotesStore` is populated by any account that issues a `VoteWitnessContract` transaction (`VoteWitnessActuator.countVoteAccount`), and every unique voting address adds/updates one entry that persists until the next maintenance cycle clears it. `MaintenanceManager.doMaintenance()` (invoked automatically from `applyBlock` during block processing in the `Manager`/consensus flow) performs the same unbounded, single-pass iteration over the entire `VotesStore` every maintenance period. [3](#0-2) [4](#0-3) 

### Finding Description
The report's bug class is: a permissionless action lets an attacker cheaply enqueue an unbounded number of items into a store; a later batch-processing step (triggered periodically or on every call) then loops over the entire unbounded set with no cap, causing an Out-of-Gas/latency blowup that DOSes downstream processing.

The java-tron analog is structurally identical:
1. Any funded account can send a `VoteWitnessContract` transaction. `VoteWitnessActuator.validate()` caps the number of *votes per transaction* to `MAX_VOTE_NUMBER` (30), but does **not** cap the number of distinct *voting accounts* that can each add one entry into `VotesStore`. [5](#0-4) 
2. Each successful vote transaction persists a `VotesCapsule` keyed by the voter's address via `votesStore.put(ownerAddress, votesCapsule)`. These entries accumulate in `VotesStore` and are only cleared once, at the next `doMaintenance()` call. [6](#0-5) 
3. `Wallet.countVote(VotesStore)` — invoked on **every single call** to `getPaginatedNowWitnessList` (an anonymous, unauthenticated HTTP/JSON-RPC/gRPC query endpoint) — does a full linear scan (`Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator()`) over the entire store with no limit, plus nested `forEach` over each capsule's old/new vote lists. [7](#0-6) 
4. The same unbounded scan (`countVote(votesStore)` in `MaintenanceManager`) executes automatically as part of block application every maintenance cycle, mirroring the `RootManager.propagate()`/`dequeueVerified` pattern from the original report (periodic batch draining of an attacker-inflatable queue). [8](#0-7) 

Because `VotesStore` is a LevelDB/RocksDB-backed store (not an in-memory bounded structure), the number of records is limited only by the number of distinct addresses that vote during an epoch — an amount fully controllable by an attacker who registers/funds many accounts and casts a minimal vote from each.

### Impact Explanation
- The `getPaginatedNowWitnessList` query path performs unbounded, request-triggered work proportional to attacker-inflated store size. A sufficiently large `VotesStore` turns each API call into an expensive full-store scan, degrading or denying this API to all clients (query-serving DOS), and since it is invoked per-request rather than once per epoch, the amplification is repeatable on demand by any anonymous caller.
- The same unbounded `countVote()` logic runs inside `MaintenanceManager.doMaintenance()`, which executes as part of normal block application (`applyBlock`). If the scan becomes large/slow enough it can delay or stall maintenance-period block processing across the network, since every node performs the identical unbounded work deterministically.
- Unlike the original RootManager report (free, permissionless spam), voting here requires the attacker to fund accounts with tron power (via freeze), so the cost is non-zero — this reduces (but does not eliminate) the practical severity relative to the original finding.

### Likelihood Explanation
Moderate. An attacker needs capital to freeze balance across many accounts to generate large numbers of `VotesStore` entries, and the cost scales with the desired size of the DOS. However, no additional privilege is required beyond normal account funding and transaction issuance, and the query-endpoint code path is reachable by any anonymous HTTP/gRPC client without funding requirements once the store is inflated, making repeated exploitation of the read path cheap after the initial setup cost.

### Recommendation
1. Bound or paginate the scan in `Wallet.countVote()`/`MaintenanceManager.countVote()` — e.g., maintain running vote-count aggregates incrementally (update witness vote deltas at vote time) instead of recomputing them by scanning the entire `VotesStore` on every read or maintenance cycle.
2. Enforce an economic or count-based cap on the number of *distinct* voter entries processed per maintenance cycle, and process any excess in batches across multiple cycles/blocks, analogous to the recommended `MAX_MATCH_NUM`-style bounding already used elsewhere in the codebase (e.g., `MarketSellAssetActuator`'s `MAX_MATCH_NUM` bound on order matching).
3. For the HTTP/gRPC query path, add a rate limit or a maximum store-scan budget per request, or serve a precomputed/cached tally in constant time instead of a live full scan.

### Proof of Concept
1. Attacker creates and funds N accounts, freezing a minimal TRX amount for tron power (e.g., 1 TRX bandwidth freeze) in each.
2. Attacker submits one `VoteWitnessContract` transaction per account (each valid, ≤`MAX_VOTE_NUMBER` votes), causing N distinct `VotesCapsule` entries to accumulate in `VotesStore` before the next maintenance boundary. [3](#0-2) 
3. Any anonymous client calls `HTTP GET /wallet/getpaginatednowwitnesslist?offset=0&limit=1` (served by `GetPaginatedNowWitnessListServlet`), which internally triggers `Wallet.getPaginatedNowWitnessList` → `countVote(votesStore)`, forcing an O(N) full scan of `VotesStore` for every such call. [9](#0-8) 
4. Separately, when the maintenance boundary is reached, `MaintenanceManager.doMaintenance()` performs the same O(N) scan as part of ordinary block application, delaying maintenance-period processing for the whole network. [10](#0-9) 

Note: I was unable to fully verify runtime timing/gas-limit behavior for the HTTP servlet path (there is no on-chain gas metering for this off-chain query, so the impact is availability/latency degradation on the API and node rather than a transaction revert) — this differs from the on-chain OOG-revert mechanic in the original report and should be validated empirically (e.g., benchmarking scan time vs. `VotesStore` size) before assigning a final severity.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    // Initialize a result map to store vote changes for each witness
    Map<ByteString, Long> countWitness = Maps.newHashMap();

    // VotesStore is a key-value store, where the key is the address of the voter
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();

    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();

      /**
       * VotesCapsule contains two lists:
       * - Old votes: Last votes from the previous epoch, updated in maintenance period
       * - New votes: Latest votes in current epoch, updated after each vote transaction
       */
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) - voteCount);
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        countWitness.put(voteAddress,
            countWitness.getOrDefault(voteAddress, 0L) + voteCount);
      });
    }
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }

  public void doMaintenance() {

      });
    }

    if (!countWitness.isEmpty()) {
      List<ByteString> currentWits = consensusDelegate.getActiveWitnesses();

      List<ByteString> newWitnessAddressList = new ArrayList<>();
      consensusDelegate.getAllWitnesses()

        consensusDelegate.saveWitness(witnessCapsule);
        logger.info("address is {} , countVote is {}", witnessCapsule.createReadableString(),
            witnessCapsule.getVoteCount());
      });

      dposService.updateWitness(newWitnessAddressList);

      incentiveManager.reward(newWitnessAddressList);

      List<ByteString> newWits = consensusDelegate.getActiveWitnesses();
      if (!CollectionUtils.isEqualCollection(currentWits, newWits)) {

          witnessCapsule.setIsJobs(false);

          witnessCapsule.setIsJobs(true);

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }
