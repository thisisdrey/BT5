### Title
Front-running of `SetAccountIdContract` permanently squats a victim's chosen unique account ID - (`actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`)

### Summary
`SetAccountIdActuator` lets any account permanently bind a human-readable, globally-unique `account_id` to its address, exactly analogous to Lens Protocol's `createProfile` handle-claim. Because the transaction is broadcast in plaintext to the mempool before inclusion, an observer can front-run it with the identical `account_id`, permanently and irreversibly claiming the identifier for themselves and locking the original submitter out forever.

### Finding Description
`SetAccountIdActuator.validate()` only checks that the requesting account has no ID yet and that the requested `accountId` is not already indexed: [1](#0-0) 

If the check passes, `execute()` writes the ID into both `AccountStore` and the global `AccountIdIndexStore`: [2](#0-1) 

The protocol comment itself states the intended uniqueness semantics: "Set account id if the account has no id. Account id is unique and case insensitive," confirming this is meant to behave like a scarce, first-come-first-served namespace: [3](#0-2) .

Critically, once an account's ID is set it can never be changed again — `account.getAccountId() != null && !isEmpty()` unconditionally rejects any further `SetAccountIdContract` for that address, with no governance flag to reverse this (unlike `AccountUpdateContract`'s `AllowUpdateAccountName`). This is demonstrated in the test suite, where a second attempt with a different name for the same owner is permanently rejected ("This account id already set") and a duplicate ID for a different owner is rejected ("This id has existed"): [4](#0-3) 

Since all pending transactions (and their `account_id` field) are visible in the node's mempool/API before being packed into a block, any third party can observe a victim's `SetAccountIdContract`, copy the `account_id`, and submit their own transaction with a higher energy/bandwidth priority or better network position to get it mined first. `AccountIdIndexStore.has(accountId)` will then cause the victim's original transaction to fail deterministically with "This id has existed," and because `account_id` can only ever be set once, the victim's address is permanently and irrecoverably barred from ever obtaining that identifier — a stronger and more permanent version of the Lens handle-squatting bug, since Lens allows a fresh (different) handle retry while a java-tron account can never call `SetAccountIdContract` again at all.

### Impact Explanation
This is directly analogous to the referenced Lens `createProfile` frontrunning finding: an attacker observing the mempool can seize a unique, permanent, user-facing identifier intended for another account, permanently denying that account the resource and enabling extortion/ransom scenarios exactly as in the original report. Because `account_id` binding is a one-shot, irreversible operation (`This account id already set`), the griefing is permanent rather than merely inconvenient, arguably a stronger impact than the original Lens finding.

### Likelihood Explanation
No privileged role is required — any account holder can submit `SetAccountIdContract`, and mempool transactions are broadcast before confirmation, making front-running trivially observable by any network participant (a simple public API/broadcast client), matching the "unprivileged transaction broadcaster" reachability in scope. The only requirement is that the attacker wants (or is paid/incentivized to want) a specific human-readable ID that another user is also trying to claim, which mirrors real-world handle-squatting/extortion incentives seen in the original bug report.

### Recommendation
Adopt the same mitigation class recommended in the original report: implement a commit-reveal scheme for `SetAccountIdContract` (commit a hash of `accountId + salt`, then reveal after a delay) so the desired ID is not visible in plaintext in the mempool before inclusion, removing the front-running window.

### Proof of Concept
1. Victim broadcasts `SetAccountIdContract{owner_address: V, account_id: "alice"}`.
2. Attacker observes this transaction in the mempool via any public API/broadcast endpoint before it is packed into a block.
3. Attacker immediately broadcasts `SetAccountIdContract{owner_address: A, account_id: "alice"}` with equal/better propagation, which is validated per `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java` lines 87-96 and gets included first (as `AccountIdIndexStore` did not yet contain "alice").
4. Victim's original transaction is then processed, `accountIdIndexStore.has("alice")` returns true, and validation throws `"This id has existed"`, as reproduced by the existing test `nameAlreadyUsed` in `framework/src/test/java/org/tron/core/actuator/SetAccountIdActuatorTest.java` lines 173-217.
5. Because `account.getAccountId() != null` check permanently blocks any future call for address V, the victim can never obtain any `account_id` binding claim it attempted to race — the identifier is permanently lost to the attacker, who may now demand ransom.

  @Test
  public void twiceUpdateAccount() {
    TransactionResultCapsule ret = new TransactionResultCapsule();
    SetAccountIdActuator actuator = new SetAccountIdActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager())
        .setAny(getContract(ACCOUNT_NAME, OWNER_ADDRESS));
    SetAccountIdActuator actuator1 = new SetAccountIdActuator();
    actuator1.setChainBaseManager(dbManager.getChainBaseManager())
        .setAny(getContract(ACCOUNT_NAME_1, OWNER_ADDRESS));
    try {
      actuator.validate();
      actuator.execute(ret);
      Assert.assertEquals(ret.getInstance().getRet(), code.SUCESS);
      AccountCapsule accountCapsule = dbManager.getAccountStore()
          .get(ByteArray.fromHexString(OWNER_ADDRESS));
      Assert.assertEquals(ACCOUNT_NAME, accountCapsule.getAccountId().toStringUtf8());
      Assert.assertTrue(true);
    } catch (ContractValidateException e) {
      Assert.assertFalse(e instanceof ContractValidateException);
    } catch (ContractExeException e) {
      Assert.assertFalse(e instanceof ContractExeException);
    }

    try {
      actuator1.validate();
      actuator1.execute(ret);
      Assert.assertFalse(true);
    } catch (ContractValidateException e) {
      Assert.assertTrue(e instanceof ContractValidateException);
      Assert.assertEquals("This account id already set", e.getMessage());

      Assert.assertFalse(e instanceof ContractExeException);
    }

  @Test
  public void nameAlreadyUsed() {

      actuator.validate();

      Assert.assertFalse(e instanceof ContractExeException);

        new AccountCapsule(
