### Title
Truncating division in `MarketUtils.multiplyAndDivide` lets a taker systematically underpay makers on TRC10 exchange order fills - (File: chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java)

### Summary
`MarketUtils.multiplyAndDivide(a, b, c)` computes `floor(a*b/c)` with no option to round up. `MarketSellAssetActuator.matchSingleOrder()` uses it to derive `makerBuyTokenQuantityReceive` — the amount the resting (maker) order owner is paid — from the maker's own price ratio when the taker's order fully consumes the maker's remaining quantity [1](#0-0) . Because the division always truncates downward, the payout owed to the maker is rounded in favor of the taker on every partial/edge fill, exactly analogous to the Tapioca `_repay` bug where `shares→amount` conversion should round up in favor of the protocol/counterparty but instead always rounds down.

### Finding Description
`multiplyAndDivide` is implemented as a plain floor division: `floorDiv(multiplyExact(a, b), c)` [2](#0-1) . It is invoked from `matchSingleOrder` to compute `makerBuyTokenQuantityReceive` (what the maker gets paid in the taker's sell-side asset) whenever the maker's order is fully drained by the taker in one match ("taker == maker" and "taker > maker" branches) [1](#0-0) [3](#0-2) . The taker's `sellTokenQuantityRemain` is reduced by this same truncated amount, while the maker's remaining sell quantity is set to exactly `0` (fully consumed) regardless of the truncation. The result is that the taker's payment to the maker for the maker's full remaining sell quantity is always rounded down, so the maker gets systematically underpaid a small fraction of a token unit on each fill, and the difference is effectively pocketed by the taker (via less TRX/asset debited than the true proportional price).

### Impact Explanation
Every trade fill that hits `matchSingleOrder`'s "==" or ">" branches loses a `floor`-rounding remainder to the maker's favor... actually the loss falls on the maker since payment is rounded down while the maker's order is fully closed as if paid in full. This value leakage is systemic — it affects the exchange's/maker's expected payout on **every** order match, not just an edge case, and a taker (or colluding accounts) can structure trades to exploit the fractional loss repeatedly to accumulate value at makers' expense, mirroring the "protocol pays out very little amount many times" dynamic in the Tapioca report.

### Likelihood Explanation
Any unprivileged account can broadcast `MarketSellAssetContract` transactions to create/fill TRC10 exchange orders; no special permission is required. The rounding triggers deterministically whenever a maker order's remaining quantity is fully consumed with a non-exact `multiply/divide` ratio, which is common with arbitrary user-chosen sell/buy quantities.

### Recommendation
Round the maker's receive amount up (ceiling division) when the maker's full remaining quantity is consumed, or otherwise ensure the taker pays no less than the exact proportional amount for the sell quantity being extinguished — analogous to always rounding in favor of the party whose "shares"/order is being fully settled, as recommended in the referenced Tapioca fix.

### Proof of Concept
1. Attacker (taker) submits a `MarketSellAssetContract` selling asset A for asset B, matching against a maker order with `makerSellQuantity`/`makerBuyQuantity` ratio such that `makerSellRemainQuantity * makerBuyQuantity` is not evenly divisible by `makerSellQuantity` (e.g. maker order 3 sell : 7 buy, remaining sell = 5).
2. Taker's order exactly matches or exceeds the maker's remaining sell quantity, driving `matchSingleOrder` into the "taker == maker" or "taker > maker" branch [1](#0-0) .
3. `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` truncates the true fractional amount owed to the maker (e.g. `5*7/3 = 11.67` truncates to `11` instead of rounding up to `12`), while `makerOrderCapsule.setSellTokenQuantityRemain(0)` closes the maker's order as fully filled [4](#0-3) .
4. Repeating this against many maker orders (or the same maker's many resting orders) lets the taker accumulate the truncated remainder across trades at the makers' expense, with the taker's own debited sell-side balance also computed by the same truncating formula, compounding the leakage.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
