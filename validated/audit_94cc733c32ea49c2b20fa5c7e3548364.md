### Title
Attacker can fill a victim's token list to `MAX_TOKENS_PER_USER` via dust `DepositToken` transfers, DoS-ing new deposits/borrows (contracts/DepositToken.sol)

### Summary
`Pool` enforces a hard cap of 30 total deposit+debt tokens per account. Anyone can add entries to *another* account's list simply by transferring dust amounts of `DepositToken` to them. Once the victim's combined list reaches 30, every subsequent `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, which reverts the whole `deposit`, `transfer`, `issue`/`mint` (debt), `seize` (liquidation payout to a fresh collateral), and SmartFarming leverage flows for that account.

### Finding Description
- `DepositToken._transfer` adds the recipient to `depositTokensOfAccount` whenever the recipient's prior balance is 0 (DepositToken.sol, `_transfer` lines ~517-520). `transfer`/`transferFrom` are public and only check the *sender's* unlocked balance via `_revertIfLocked(_msgSender, amount_)`.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol, lines 143-148, 204-220).
- The same cap applies to debt tokens: `DebtToken` issue/mint calls `pool.addToDebtTokensOfAccount`, so a victim at the cap cannot open debt in any new synthetic either.
- Attack path: attacker deposits a small amount of each pool-listed deposit token to themselves (or receives dust), then calls `depositTokenX.transfer(victim, 1 wei)` for each token X. Each call invokes `pool.addToDepositTokensOfAccount(victim)`, consuming one slot per distinct token. No victim action or approval is required.
- Consequence: the victim's own `deposit(amount, onBehalfOf=victim)` on any *new* collateral reverts inside `_mint → addToDepositTokensOfAccount`; issuing a new synthetic debt reverts the same way; liquidation `seize` to the victim is unaffected, but the victim cannot top-up a deteriorating position with a collateral type they don't already hold. If the pool's listed deposit tokens plus the victim's existing debt tokens total ≥ 30, the victim can be pushed to the cap in a single attacker transaction burst.

### Impact Explanation
Temporary freezing of funds / forced-liquidation griefing. During the griefed window the victim cannot add a new collateral type or open new debt; if their position is or becomes unhealthy they cannot rescue it with a new collateral and can be liquidated (`Pool.liquidate` → `DepositToken.seize`) while remediation is blocked. The victim can eventually recover by withdrawing each dust balance to zero (which triggers `removeFromDepositTokensOfAccount`), paying gas per token — so it is temporary, not permanent, consistent with Medium severity.

### Likelihood Explanation
Requires only an unprivileged EOA and ordinary `transfer` calls on already-listed deposit tokens — no privileged role, no oracle manipulation, no fake contracts. Cost scales with the number of distinct deposit tokens the pool lists (gas + dust for each). The attack is only fully blocking if (#pool deposit tokens + victim's existing debt tokens) ≥ 30; on deployments where a pool lists close to 30 collaterals this is directly reachable. Partial filling still forces the victim to burn gas cleaning slots before onboarding additional collateral.

### Recommendation
- Only register a deposit/debt token in the per-account list on user-initiated actions (`deposit`, `issue`), not on inbound `transfer`/`seize`/`transferFrom` credits; or
- Skip `addToDepositTokensOfAccount` when the credit is a transfer to an account that did not initiate it (e.g., only add when `recipient_ == _msgSender()` semantics via a dedicated flag), and/or
- Bound or drop the `MAX_TOKENS_PER_USER` revert so that excess tokens are tracked but do not brick `deposit`/`issue` — e.g., cap only the looped health-check set while allowing balance holding.

### Proof of Concept
```solidity
// Foundry fork-style PoC (Hardhat equivalent applies)
function test_dustFillGriefing() public {
    // victim already holds k debt tokens; pool lists n deposit tokens with k + n >= 30
    for (uint i; i < depositTokens.length; ++i) {
        DepositToken dt = depositTokens[i];
        // attacker gets a dust balance (deposit 1 wei of underlying onBehalf self)
        underlying[i].approve(address(dt), 1);
        dt.deposit(1, attacker);
        // grief: credit victim with dust -> consumes one slot
        vm.prank(attacker);
        dt.transfer(victim, 1);
    }

    // victim's list is now at MAX_TOKENS_PER_USER
    assertEq(
        pool.getDepositTokensOfAccount(victim).length
      + pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // victim tries to deposit a collateral type they don't already hold -> reverts
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    vm.prank(victim);
    newDepositToken.deposit(1e18, victim);

    // victim also cannot issue a new synthetic debt token (addToDebtTokensOfAccount reverts)
}
```
Cleanup cost for the victim is one `withdraw` per dust token; until then deposits, borrows, and leverage routes on any new token are DoS'd, and an unhealthy position cannot be topped up with a new collateral.
