### Title
Guardian can drain user-owed assets via `rescueERC20Tokens` due to lack of liability accounting - ([File: tare-io__tare-contracts/contracts/misc/Rescuable.sol])

### Summary
The `Rescuable` contract provides a `rescueERC20Tokens` function intended to recover tokens accidentally sent to protocol contracts. However, the implementation does not prevent the rescue of the protocol's primary underlying assets (`currency` in `Loans.sol` or `assetToken` in `PortfolioVault.sol`). Because `rescueERC20Tokens` calculates the rescueable amount based on the raw `balanceOf(address(this))` without subtracting the contract's internal accounting liabilities (user ledger balances or pending withdrawal/redemption reserves), a Guardian can withdraw funds that are legally owed to users, causing protocol insolvency.

### Finding Description
The `Rescuable.rescueERC20Tokens` function is designed to allow a Guardian to recover tokens. It determines the maximum rescueable amount by checking the contract's current balance: [1](#0-0) 

When inherited by `Loans.sol` or `PortfolioVault.sol`, this function can be called on the primary protocol token (e.g., USDC). These contracts maintain internal ledgers and state variables that track how much of their `balanceOf` is actually owed to users:
*   In `Loans.sol`, the `accountBalances` mapping tracks `ACC_CASH` and various payable accounts for investors, servicers, and originators.
*   In `PortfolioVault.sol`, `totalPendingDepositAssets` and `totalClaimableRedeemAssets` track assets that are reserved for specific users.

The `rescueERC20Tokens` function does not subtract these liabilities from the `balance`. Consequently, it treats the entire contract balance as "excess" or "accidentally sent." This mirrors the bug-class in the seed report, where the failure to exclude specific protocol-owned amounts (fees) from the "excess" calculation allowed unauthorized withdrawal of those funds. In Tare, the oversight is broader, as it fails to exclude *all* protocol-accounted liabilities.

The protocol documentation explicitly acknowledges this risk as a violation of the Solvency invariant: [2](#0-1) 

### Impact Explanation
If a Guardian calls `rescueERC20Tokens` on the protocol's primary asset, they can divert funds belonging to honest users (Investors, Shareholders, or Borrowers) to the `recoveryAddress`. 
1.  **Insolvency**: The contract's `balanceOf` will fall below the sum of its internal ledger liabilities.
2.  **Fund Loss**: Users attempting to call `investorWithdraw` in `Loans.sol` or `redeem`/`withdraw` in `PortfolioVault.sol` will experience transaction reverts due to `InsufficientCashBalance` or `InsufficientLiquidity`, effectively locking their claimable assets or resulting in permanent loss if the funds are not returned.
3.  **Unauthorized Reassignment**: Funds are moved from the shared protocol state to a `recoveryAddress` without following the defined waterfall or redemption logic.

### Likelihood Explanation
While the `GUARDIAN_ROLE` is a trusted role (typically a `TimelockController`), the protocol's security model relies on smart contracts enforcing invariants to prevent even privileged roles from causing material corruption of ledger balances or theft of assets. The current implementation provides a direct, un-gated path to break the core Solvency invariant.

### Recommendation
Modify `Rescuable.sol` to allow concrete implementations to define a "protected" balance that cannot be rescued. In `Loans.sol` and `PortfolioVault.sol`, this should be the sum of all internal liabilities. Alternatively, prevent `rescueERC20Tokens` from being called on the contract's primary asset token.

```solidity
// In Rescuable.sol
function rescueERC20Tokens(address token, uint256 amount) external virtual ...

// In Loans.sol
function rescueERC20Tokens(address token, uint256 amount) external override ... {
    require(token != address(currency), "Cannot rescue primary currency");
    return super.rescueERC20Tokens(token, amount);
}
```

### Proof of Concept
1.  Users deposit `1,000,000 USDC` into `PortfolioVault.sol`.
2.  The vault's `assetToken.balanceOf(address(this))` is `1,000,000`.
3.  The Guardian (Timelock) calls `rescueERC20Tokens(USDC, 500,000)`.
4.  The function sees the balance is `1,000,000`, calculates `rescued = 500,000`, and transfers `500,000 USDC` to the `recoveryAddress`.
5.  The vault now only has `500,000 USDC` but still has `1,000,000 USDC` worth of shares/claims recorded in its state.
6.  Users attempt to redeem their shares. The first `500,000 USDC` worth of redemptions succeed, but subsequent users' transactions revert, and they lose their funds. [3](#0-2) [4](#0-3)

    rescued = amount >= balance ? balance : amount;
    if (rescued > 0) {
      IERC20(token).safeTransfer(recoveryAddress, rescued);
      emit ERC20TokensRescued(token, rescued, recoveryAddress);
