## Title
Out-of-bounds read on crafted Zip64 extra fields via unchecked `attr64` index in `CDH`/`LH` size/offset accessors - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`CDH::compressed_file_size()`, `CDH::uncompressed_file_size()`, `CDH::local_header_offset()` (and the analogous `LH` accessors) read a 64-bit value from a `Zip64ExtraField` at an index that is *derived from context* (which of the sibling 32-bit fields are `0xFFFFFFFF`) rather than validated against the field's own declared `attr_count()`. This mirrors CVE-2017-5845's root cause: a sub-record ("ncdt" sub-tag / here, the Zip64 attr entry) is trusted to extend as far as an outer computation implies, without checking that the sub-record itself actually contains that much data — allowing the parser to read past the boundary the sub-record legitimately covers.

### Finding Description
`ExtraField::find()` at [1](#0-0)  correctly bounds-checks that the *declared* size of an extra field (`sizeof(ExtraField) + payload_size()`) does not exceed the `extra_fields` buffer end. That gives a valid but attacker-controlled `payload_size()`, and thus `attr_count() = payload_size() / 8` at [2](#0-1) .

The callers, however, never consult `attr_count()`. Instead they compute the index to read purely from the surrounding 32-bit fields' sentinel state: [3](#0-2) [4](#0-3) 

For example, `CDH::local_header_offset()` computes `attr_no` by checking whether `uncompressed_file_size32()` and `compressed_file_size32()` are `0xFFFFFFFF`, then calls `z64->attr64(attr_no)` unconditionally — with no check that `attr_no < z64->attr_count()`. An attacker who controls the raw bytes of a ZIP/JAR (e.g. a file fetched via `http_archive`/`http_jar`, or any jar merged by `singlejar`'s `OutputJar::AddJar`) can set:
- `local_header_offset32 == 0xFFFFFFFF` (forcing the ext64 path),
- `compressed_file_size32`/`uncompressed_file_size32` to normal 32-bit values (so the code believes only `local_header_offset` needs the extension, `attr_no = 0`),
- but supply a Zip64 extra field with `payload_size() == 0` (`attr_count() == 0`) or otherwise smaller than required.

`z64->attr64(0)` then reads 8 bytes from `attr_[0]`, which is memory immediately following the (empty/short) extra field record — i.e., data beyond the region `ExtraField::find` validated as belonging to this extra field. Because the whole file is memory-mapped (`MappedFile`, `mapped_start_`/`mapped_end_`, see `src/tools/singlejar/mapped_file.h`), this read stays inside the mapping only by chance (adjacent header bytes, comment bytes, or the next central-directory record); a sufficiently small/truncated extra field near the end of the mapped region can push the read outside `mapped_end_`, and `mapped()` is never invoked to verify it. `MappedFile::address()` also performs no bounds check.

The corrupted "size"/"offset" value produced by this bad read then flows into `InputJar::LocalHeader()` (`mapped_file_.address(cdh->local_header_offset() + preamble_size_)`) and into copy-length computations in `OutputJar::AddJar` (`num_bytes`, `copy_from`), so a single OOB 8-byte read can also poison subsequent length/offset arithmetic used for further reads — directly analogous to how the GStreamer ncdt bug used one out-of-bounds tag to corrupt subsequent parsing state, causing invalid reads/crashes.

### Impact Explanation
This is a memory-safety violation (heap/mapping out-of-bounds read) triggerable purely by the bytes of an untrusted jar/zip that Bazel's `singlejar` tool processes (e.g., merging deploy jars whose inputs include externally fetched `.jar`/`.aar`/`.war` archives via `http_archive`/`http_jar`, or `AddJar` in the packaging pipeline). At minimum this causes incorrect size/offset values to be used, potentially crashing the build (SIGSEGV if the read crosses the mapping) or corrupting downstream `memcpy`/copy-length computations in `OutputJar::AddJar`, matching the CVE-2017-5845 class (invalid memory read / crash) rather than a memory-corruption write.

### Likelihood Explanation
Any attacker who can supply a ZIP/JAR file consumed by the build (a hostile release asset, a compromised mirror, or a malicious dependency version) can trivially craft a Zip64 extra field with `payload_size()` smaller than the sibling-32-bit-field logic expects. No cryptographic or checksum verification of internal file structure (only whole-file `sha256`/`integrity` on the archive as a unit) protects against this, since it's a structural parsing bug internal to a file that otherwise matches its outer checksum.

### Recommendation
Add an explicit check in `Zip64ExtraField`/`CDH`/`LH` before every `attr64(index)` call that `index < attr_count()`, and treat an out-of-range index the same as the "no Zip64 extra field" case (return an error/`0xFFFFFFFF` sentinel and fail the parse) rather than reading unchecked memory. Alternatively, validate at `ExtraField::find(1, ...)` call sites that the found Zip64 field's `payload_size()` matches the exact combination of sentinel 32-bit fields observed in the enclosing header before trusting any `attr64()` reads.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction would:
1. Construct a minimal ZIP with one central-directory entry where `local_header_offset32 = 0xFFFFFFFF`, `compressed_file_size32`/`uncompressed_file_size32` set to ordinary small values, and an attached Zip64 extra field (tag `0x0001`) with `payload_size = 0` (i.e., zero `attr64` entries), placed at (or near) the very end of the mapped/central-directory region so `attr_[0]` falls outside `mapped_end_`.
2. Feed this file to `InputJar::Open`/`NextEntry` (or `OutputJar::AddJar`) as in the existing `singlejar` tests (`src/tools/singlejar/input_jar_scan_entries_test.h`, which already exercises Zip64 handling via `TestZip64`).
3. Observe the out-of-bounds/undefined read in `CDH::local_header_offset()` when computing `z64->attr64(attr_no)`, e.g. via an AddressSanitizer build producing a heap-buffer-overflow report, confirming the read crosses the extra field's validated boundary.

I was not able to fully trace every call path from a specific Starlark repository rule (`http_jar`/`http_archive`) down into `OutputJar::AddJar` within the available search budget, so the exact end-to-end trigger from a `bazel build` invocation (vs. direct `singlejar` invocation) would need to be confirmed by a background agent with build/test access.

```text
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
```
