## Title
Unbounded ZIP64 extra-field walk in `InputZipFile::ProcessCentralDirEntry` allows out-of-bounds reads from a malicious jar/zip archive - (File: `third_party/ijar/zip.cc`)

## Summary
`ijar` (used by Bazel's header-jar generation and `zip`/`unzip` tooling) parses the central directory of a ZIP/JAR file that can originate from an untrusted, attacker-published archive (e.g. a `.jar` fetched via `http_jar`/`http_archive`, or any dependency artifact consumed at build time). While walking the "extra fields" attached to a central directory entry to find the ZIP64 sizes, the code trusts an attacker-controlled 16-bit `data_size` field with no bound check against the actual extra-field region, closely mirroring the "attacker-supplied length field consumed without validation, leading to a read past the intended buffer" bug class in the OpenSSL X.509 name-constraint report.

## Finding Description
In `InputZipFile::ProcessCentralDirEntry` (`third_party/ijar/zip.cc`, ~lines 524-542):

```cpp
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
}
``` [1](#0-0) 

Two invariants that should hold for untrusted input are broken here:

1. **`data_size` is never validated against the remaining bytes in the extra-field region (`p`) or the mapped file.** An attacker can set `data_size` to a value that makes `extra_p` overshoot `p`. Because the loop condition is a strict `extra_p != p` (not `extra_p < p`), an overshoot means the loop never terminates by hitting the boundary and continues consuming attacker-controlled bytes from far beyond the intended extra-field slice — walking arbitrarily deep into (and past) the memory-mapped input file.
2. **`get_u8le(extra)` reads 8 bytes unconditionally when `header_id == ZIP64_EXTRA_FIELD_TAG`,** without checking that `data_size >= 24` (the minimum size for the up-to-three 8-byte ZIP64 attributes) or that `extra + 24` stays inside the mapped region. A crafted extra field with `header_id = 0x0001` and a `data_size` of 0 or 1 still causes three `get_u8le` reads (24 bytes) from `extra`, which is a straightforward out-of-bounds/adjacent-memory read within (or past) the mmap'd file — reading uncompressed size, compressed size, and offset values from unrelated file bytes or, near the end of the mapping, past the mapped region entirely.

This function is called for **every entry in the central directory** by `InputZipFile::ProcessNext()` and `InputZipFile::CalculateOutputLength()` [2](#0-1) [3](#0-2) , both of which are reachable purely by feeding `ijar`/`zipper` (and consequently Bazel's jar-processing machinery) an attacker-controlled archive — no code execution or credential access needed, and no checksum verification happens on the *contents* of the central directory prior to this parse (checksum verification, where present via `sha256`, only covers the whole archive blob before extraction begins in `http_archive`/`http_jar`, not the internal structural fields consumed here byte by byte).

By contrast, the sibling ZIP parser used by `singlejar` (`ExtraField::find` in `src/tools/singlejar/zip_headers.h`) does perform bounds checks (`ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)` and `... + extra_field->size() > ... end`) [4](#0-3) , confirming that the `ijar` code path lacks the equivalent containment check that exists elsewhere in the codebase for the same data structure.

## Impact Explanation
A hostile origin serving a crafted `.jar`/`.zip` (e.g. a dependency downloaded via `http_jar`/`http_archive`, or any archive processed by the `ijar`/`zipper` binaries during a build) can trigger out-of-bounds reads of adjacent process memory during central-directory parsing. Depending on layout, this can crash the build process (denial of availability for that build step) or cause corrupted size/offset values to be used downstream, leading to further misparsing of the archive (e.g., wrong `uncompressed_size`/`offset` feeding into subsequent local-file-header processing and `EnsureRemaining` bound calculations). This is a genuine "integrity of parsed length fields" bypass — the attacker controls a length that is trusted without containment checking, letting them read past the buffer boundary, functionally analogous to the OpenSSL X.509 read-buffer-overflow triggered by name-constraint length fields.

## Likelihood Explanation
Any project consuming a third-party JAR/ZIP (via `http_jar`, `http_archive` unpacked and then re-processed by `ijar` for header-jar generation, or direct use of the `zipper`/`unzip_bin` tool) will run this code path on attacker-influenced bytes. Since central-directory entries are iterated for every file in the archive, and there is no field-level validation, the attack requires only serving/publishing one malformed archive — well within the "unprivileged, publishes content the victim's build consumes" threat model.

## Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry`'s extra-field loop:
- Ensure `extra_p + 4 <= p` before reading `header_id`/`data_size`.
- Ensure `extra_p + data_size <= p` before advancing `extra_p`, and abort/return an error if it does not hold (rather than looping on `extra_p != p`, use `extra_p < p` combined with an explicit equality check for termination, and error out on overshoot).
- For the ZIP64 tag, verify `data_size >= 24` before calling `get_u8le` three times.
- Mirror the containment checks already implemented in `ExtraField::find` in `src/tools/singlejar/zip_headers.h`.

## Proof of Concept
A JUnit/`src/test/shell` proof would construct a minimal ZIP archive (mirroring the pattern already used in `src/tools/singlejar/output_jar_simple_test.cc`'s `CreateZipWithMalformedExtraField` helper [5](#0-4) , but targeted at `third_party/ijar`) containing:
1. A single central directory entry with `compressed_size32`/`uncompressed_size32` set to `0xFFFFFFFF` (forcing ZIP64 lookup).
2. An extra field with `header_id = 0x0001` (ZIP64 tag) and `data_size = 1` (too small to hold the 24 bytes the code will read).
3. Invoke `InputZipFile::ProcessCentralDirEntry` (via `ijar`'s public entry point, e.g. through the `zip_main`/`ijar` binary or a direct unit test linking `third_party/ijar/zip.cc`) on this archive and observe (with AddressSanitizer) a heap-buffer-overflow read report when `get_u8le(extra)` reads past the declared `data_size`/extra-field boundary, or an out-of-bounds walk when `data_size` is set to cause `extra_p` to overshoot `p`.

*Note: I was unable to fully trace whether an outer size check exists between `Open()`/`central_dir_` initialization and `ProcessCentralDirEntry` that might already clamp the central directory to the mapped file length; the index did not surface `InputZipFile::Open()`'s full body. This should be verified in a full checkout before finalizing severity, since a whole-file length clamp on `central_dir_` would still not prevent the internal `data_size` overshoot described above, but could bound how far past the file the read can go.*

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}

  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);

  ecd->this_disk_entries16(1);
  ecd->total_entries16(1);
  ecd->cen_size32(cdh_size);
