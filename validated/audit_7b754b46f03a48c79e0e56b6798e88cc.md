## Title
StackerDB chunk signatures are not scoped to a specific contract, enabling cross-context chunk replay across StackerDB instances sharing the same signer/slot assignment - (File: libstackerdb/src/libstackerdb.rs)

### Summary
The signature that authenticates a StackerDB chunk write (`SlotMetadata::auth_digest`) only commits to `slot_id`, `slot_version`, and `data_hash` — it never commits to the identity of the StackerDB smart contract the chunk is destined for. Multiple StackerDB instances (e.g. the `.signers-{0|1}-{1,2,3}` contracts used for `BlockResponse`, `StateMachineUpdate`, and `BlockPreCommit`) are deliberately configured to share the *identical* signer→slot-id assignment for a given reward-cycle parity. Because the on-chain slot assignment is identical across these sibling contracts and the signature never binds the contract, a chunk that a signer legitimately authored and signed for one StackerDB contract can be relayed by any unprivileged network peer into a *different* sibling contract's identically-indexed slot and will pass all server-side checks (`slot_desc.verify(&slot_validation.signer)`), even though the signer never authorized that write for that resource.

### Finding Description
`SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) . `sign()`/`verify()` operate purely on this digest and a target `StacksAddress`, with no notion of *which contract* the chunk is being written to: [2](#0-1) .

Both write paths — the local sync/relay path `StackerDBTx::try_replace_chunk` and the unsolicited-push validation path `PeerNetwork::validate_received_chunk` — authenticate a chunk purely by recovering the signer for the target contract's `slot_id` and calling `slot_desc.verify(&slot_validation.signer)` / `slot_metadata.verify(&addr)`: [3](#0-2) [4](#0-3) 

Neither check verifies that the signature was produced *for this specific contract*. This is the "custody != collateral_custody but neither is checked against the intended asset" pattern from the report, restated for StackerDB: the code checks "is this signature valid for *some* slot owned by the recovered signer at this slot_id" but never checks "was this signature scoped to *this* StackerDB contract".

Crucially, the boot contract deliberately shares slot assignment across sibling `.signers-X-Y` contracts. `stackerdb-set-signer-slots` stores one shared list per cycle-parity (`stackerdb-signer-slots-0`/`-1`), and every `.signers-{parity}-{message_id}` contract reads from that same shared list via `stackerdb-get-signer-slots-page`: [5](#0-4) [6](#0-5) . This is confirmed by the test showing the same expected slot list applies identically across all `message_id` values (0..`SIGNER_SLOTS_PER_USER`) for a given signer set: [7](#0-6) . The distinct contracts per `message_id` (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) are constructed via `NakamotoSigners::make_signers_db_contract_id`: [8](#0-7) , [9](#0-8) .

Consequently, for any given reward-cycle parity, a signer's `StacksAddress` owns the *same* `slot_id` in `.signers-0-1` (BlockResponse), `.signers-0-2` (StateMachineUpdate), and `.signers-0-3` (BlockPreCommit) simultaneously. Since `auth_digest()` never includes the contract identifier, a signature that a signer produced to authenticate a chunk for one of these contracts is equally valid for the identically-indexed slot in the other sibling contracts.

### Impact Explanation
An unprivileged network peer that observes a legitimately signed `StackerDBPushChunk`/`StackerDBChunk` for one signers contract (e.g. `BlockResponse`) can re-wrap the same `StackerDBChunkData` (slot_id, slot_version, data, signature unchanged) inside a `StackerDBPushChunkData`/HTTP POST targeted at a sibling contract (e.g. `BlockPreCommit`) that shares the same signer/slot mapping. `validate_received_chunk` / `try_replace_chunk` will accept and store it, since the recovered signer address for that slot_id in the target contract matches the address the signature actually resolves to — even though the signer never intended or authorized writing that payload into that contract. Successful storage causes the node to further broadcast the (mis-attributed) chunk to its neighbors via `process_stacker_db_chunks`, propagating this cross-context data network-wide: [10](#0-9) . This is an unauthorized write into a StackerDB replica (the signer authorized the bytes for a different resource) that is then propagated network-wide — matching the Critical category "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data."

### Likelihood Explanation
Exploitation only requires observing one legitimately broadcast chunk (chunks/messages are gossiped in plaintext over the p2p network to all replicating peers) and re-submitting it, either via the P2P `StackerDBPushChunk` message or the public `/v2/stackerdb/.../chunks` HTTP endpoint, with no special privileges, keys, or node roles required. The only precondition is that the version-freshness check (`slot_version` must exceed the target contract's stored version for that slot) is satisfiable, which is trivially true for the first replay of a newer chunk into a sibling contract, or achievable by waiting for a version gap between sibling DBs.

### Recommendation
Bind the signed digest to the specific StackerDB contract (and, ideally, the expected consumer/message-type), not merely `(slot_id, slot_version, data_hash)`. Modify `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` to also hash the `QualifiedContractIdentifier` of the target StackerDB, and thread the contract identifier through `sign()`/`verify()`, `try_replace_chunk()`, and `validate_received_chunk()` so a signature produced for one contract cannot be replayed as valid for another.

### Proof of Concept
1. During a reward cycle, a signer with address `S` owns `slot_id = k` in both `.signers-0-1` (BlockResponse) and `.signers-0-3` (BlockPreCommit), per the shared `stackerdb-signer-slots-0` list.
2. The signer legitimately signs and pushes a `StackerDBChunkData{slot_id: k, slot_version: v, data: D}` to `.signers-0-1`; this propagates over the p2p network as a `StackerDBPushChunk`.
3. An attacker observes this message, and constructs a new `StackerDBPushChunkData{contract_id: <.signers-0-3 id>, chunk_data: StackerDBChunkData{slot_id: k, slot_version: v, sig: <unchanged>, data: D}}` (or POSTs the same body to `/v2/stackerdb/.../signers-0-3/chunks`).
4. `validate_received_chunk`/`try_replace_chunk` for `.signers-0-3` recover signer `S` for slot `k` — identical to the actual signer of `D` — so `slot_metadata.verify(&S)` succeeds, and the chunk (originally a BlockResponse payload) is stored and re-broadcast as slot `k` content of the BlockPreCommit StackerDB, without the signer ever authorizing that specific write.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
