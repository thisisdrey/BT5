Audit Report

## Title
Relayer reward paid in full and unconditionally regardless of Ethereum execution success or actual gas used, with no sender refund - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

## Summary
`Pallet::process_delivery_receipt` pays the full pre-committed `PendingOrder.fee` to the relayer's `reward_account` as soon as a `DeliveryReceipt` passes cryptographic log verification, without inspecting the `success` field of the decoded `InboundMessageDispatched` event, and with no mechanism to refund any unused portion of the fee (which was sized from a worst-case gas bound) to the original sender. [1](#0-0) 

## Finding Description
The fee is fixed at enqueue time in `do_process_message`, taken from `Message.fee` (originally derived on the source side from `GasMeter::maximum_dispatch_gas_used_at_most`, a worst-case gas estimate) and stored unconditionally in `PendingOrder.fee`. [2](#0-1) 

`DeliveryReceipt::try_from` decodes the Ethereum `InboundMessageDispatched(nonce, topic, bool success, reward_address)` event and explicitly carries a `success: bool` field. [3](#0-2) 

However, `submit_delivery_receipt` only verifies the log's cryptographic authenticity via `T::Verifier::verify`, decodes the receipt, and hands it to `process_delivery_receipt`, which checks only `T::GatewayAddress::get() == receipt.gateway` and `order.fee > 0` before unconditionally calling `T::RewardPayment::register_reward` for the full `order.fee`, then removes the pending order. `receipt.success` is never read anywhere in this function. [4](#0-3) [5](#0-4) 

Existing guards (`T::Verifier::verify`, `InvalidGateway`, `InvalidPendingNonce`) validate only proof authenticity, gateway origin, and nonce existence — none of them inspect or gate on the semantic delivery outcome (`success`) carried inside the verified log, and no code path exists anywhere in the pallet to compute actual gas used or refund the sender for the difference between the quoted worst-case fee and actual cost.

## Impact Explanation
This is a runtime bug that compromises intended fee/reward-settlement behavior: the reward payout is decoupled from the actual delivery outcome and actual execution cost, meaning relayers are rewarded the full quoted fee even for failed message deliveries, and senders are permanently overcharged for the difference between worst-case quoted fee and real cost with no refund mechanism. This falls under the allowed "duplicate settlement or payout" / value-conservation impact class in the Polkadot SDK impact gate, since the fee is settled in full to the relayer without validating that delivery actually succeeded or that the amount matches actual cost incurred.

## Likelihood Explanation
High. `submit_delivery_receipt` is a public, permissionless extrinsic guarded only by `ensure_signed(origin)?`; any account holding a valid Ethereum log proof (including the legitimate relayer flow) can trigger full payout regardless of the `success` value embedded in the very same log. [6](#0-5)  No governance or privileged action is required — this occurs on every normal invocation of the intended relayer-reward flow whenever the underlying delivery fails or costs less than the worst-case quote.

## Recommendation
- In `process_delivery_receipt`, branch on `receipt.success`: only pay the full `order.fee` when `success == true`.
- On `success == false`, withhold or reduce the relayer reward and route the unused/full fee back to the original message sender/origin recorded at enqueue time.
- If/when actual gas-used data becomes available in the event, refund the sender the delta between quoted `fee` and actual cost, analogous to the `targetChainRefundPerUnitGasUnused` pattern, before treating `PendingOrders::remove(nonce)` as final settlement.

## Proof of Concept
1. Sender submits a message via the outbound queue v2 pipeline; the message is enqueued with `fee` derived from `GasMeter::maximum_dispatch_gas_used_at_most` and stored as `PendingOrder { nonce, fee, .. }`. [2](#0-1) 
2. On Ethereum, the gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`, e.g. because the inner dispatched call reverted while the outer log emission still succeeds.
3. A relayer calls `submit_delivery_receipt` with the valid log/proof; `T::Verifier::verify` succeeds since the log is authentic, and `DeliveryReceipt::try_from` decodes `success: false` into the receipt. [7](#0-6) 
4. `process_delivery_receipt` ignores `receipt.success`, pays `order.fee` in full to `reward_account`, and removes the pending order. [8](#0-7) 
5. Result: relayer is fully rewarded for a failed delivery, and the sender has no path to recover any portion of the overpaid worst-case fee.

		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,

			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });
