## Finding

### Title
Stale signature re-verification window for account permission updates in `Manager.getVerifyTxs` - (File: framework/src/main/java/org/tron/core/db/Manager.java)

### Summary
The Sherlock report describes a "revoke approval" bug class: an authority (router) is replaced, but privileges granted to the old authority (token approval) are not revoked, so the stale authority retains capability it should have lost. The closest reachable analog in java-tron is in block/transaction re-verification logic in `Manager`: when an account's multisig `Permission` set is changed via `AccountPermissionUpdateContract`, previously pending/cached transactions signed under the *old* permission set can be treated as already-verified ("approved") unless the node explicitly re-checks them against the new permission after the update. This is effectively the same class of bug — permission/approval state changes without properly invalidating prior grants tied to the old state.

### Finding Description
`AccountPermissionUpdateActuator.execute()` calls `AccountCapsule.updatePermissions()` which fully overwrites `ownerPermission`, `witnessPermission`, and `activePermission` in the account, replacing the previous permission keys/thresholds/operations bitmap: [1](#0-0) [2](#0-1) 

Separately, `Manager.getVerifyTxs` (invoked during block application) decides which transactions in a candidate block still need full signature/permission re-verification versus which can be treated as already verified because they match an entry already sitting in `pendingTransactions`. The unit tests demonstrate that the node specifically special-cases `AccountPermissionUpdateContract`: once such a contract for an owner address has been seen/consumed, subsequent transactions from that same owner must be forced back into the re-verify list rather than trusted via a stale `isVerified=true` flag, precisely because their prior verification could have been performed against an obsolete permission set: [3](#0-2) [4](#0-3) 

The signature/weight check itself (`TransactionCapsule.checkWeight` / `TransactionUtil.getTransactionSignWeight`) always re-derives the `Permission` object live from the current `AccountCapsule` via `account.getPermissionById(permissionId)`, so a correctly-implemented re-verification path is safe: [5](#0-4) [6](#0-5) 

The exposure is the caching/short-circuit logic that decides *whether* to re-run that check at all. If a transaction's `isVerified` flag is trusted based on identity with a pending-pool entry without accounting for an intervening `AccountPermissionUpdateContract` for the same owner, a transaction that was validly signed and cached under the *old* permission (analogous to the old router's stale approval) would be accepted into a block without being checked against the *new* permission — i.e. the old approval was never "revoked" for already-verified/cached transactions.

### Impact Explanation
If the re-verify skip logic fails to force re-checking after a permission change (the exact scenario the added regression test `getVerifyTxsSkipsBlockWhenPermissionTxAlreadyConsumed` guards against), an attacker or a legitimate co-signer whose active-key was removed/rebalanced in a multisig update could still get a previously-signed, cached transaction included and treated as authorized, even though their weight/threshold no longer qualifies under the new permission. This is an unauthorized-account-operation class of impact (equivalent to the old router being able to move tokens after `setUniswapRouter` changed the active router): a party whose signing authority was supposed to be revoked can still push through an operation.

### Likelihood Explanation
This path is only reachable through the ordinary block-application pipeline (`pushBlock` → `getVerifyTxs`), which processes every incoming block's transactions, including transactions broadcast by any unprivileged account (via `TransactionCapsule` + `AccountPermissionUpdateContract`, both broadcastable by any signer). Exploitation requires: (1) an account using multisig (`AccountPermissionUpdateContract`), (2) a co-signed transaction already pending/cached with `isVerified=true`, and (3) the owner updating permissions to remove/reduce that signer's weight before the block is finalized. This is a narrow timing window but requires no special privilege — a normal multisig account holder triggers it. The presence of the dedicated regression test in the codebase indicates this was previously an actual defect that was patched; the current committed test asserts the fix (`getVerifyTxs` must place the transaction into the re-verify list). I was unable to retrieve the full body of `Manager.getVerifyTxs` in this pass (only 2 references were located and the method source itself did not load), so I cannot confirm with certainty whether the fix is complete for all code paths (e.g., different signature/contract counts, multiple contracts per transaction, or transactions targeting `witness`/`owner` permission tiers rather than `active`).

### Recommendation
- Confirm `Manager.getVerifyTxs` unconditionally forces re-verification (bypassing the pending-pool cache) for **every** transaction whose owner address had *any* `AccountPermissionUpdateContract` processed within the same candidate block or still resident in `ownerAddressSet`, not only for the literal contract instance itself.
- Ensure the invalidation also covers cases where the permission change originates from a different transaction within the same block that precedes the transaction being verified, and covers all permission tiers (owner/witness/active), not just active permissions used for `operations` bitmap checks.
- Add/extend regression coverage (the existing `getVerifyTxsSkipsBlockWhenPermissionTxAlreadyConsumed` test is a good template) for multi-contract transactions and for witness/owner permission tier changes.

### Proof of Concept
Conceptual PoC mirrored on the existing regression test:
1. Account X has 2-of-2 active-permission multisig with keys A and B.
2. X co-signs (with A and B) a sensitive transfer transaction `T1`; it enters `pendingTransactions` with `isVerified=true` after passing weight/threshold checks under the *current* permission.
3. Before `T1` is included in a block, X broadcasts `AccountPermissionUpdateContract` `T0` that removes key B's authority (e.g., new 2-of-2 permission with keys A and C).
4. A block is proposed containing `T0` and `T1` (in that order, or `T0` already applied).
5. If `getVerifyTxs` treats `T1` as already verified (matching cached pending entry) instead of re-checking it against the new permission, `T1` executes despite B's authority having been revoked — analogous to the old router retaining spend approval after `setUniswapRouter` rotated the router.   public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }

  @Test
  public void getVerifyTxsSkipsBlockWhenPermissionTxAlreadyConsumed() throws Exception {
    // Scenario: a permission-change tx (A) for owner X has been processed and consumed,
    // so it is no longer in pendingTransactions but ownerAddressSet still contains X.
    // A later transfer tx (B) from X with the old signature enters pending with
    // isVerified=true. A malicious SR produces a block containing only B (no A).
    // getVerifyTxs must place B into the re-verify list rather than calling
    // setVerified(true) just because B matches the pending entry.
    TransferContract bContract = TransferContract.newBuilder()
        .setOwnerAddress(ByteString.copyFrom("f1".getBytes()))
        .setAmount(7).build();
    TransactionCapsule bTx = new TransactionCapsule(bContract, ContractType.TransferContract);
    String hexOwner = ByteArray.toHexString("f1".getBytes());

    dbManager.getPendingTransactions().clear();
    dbManager.getPendingTransactions().add(bTx);

    Field field = Manager.class.getDeclaredField("ownerAddressSet");
    field.setAccessible(true);
    @SuppressWarnings("unchecked")
    Set<String> ownerAddressSet = (Set<String>) field.get(dbManager);
    Set<String> backup = new HashSet<>(ownerAddressSet);
    ownerAddressSet.clear();
    ownerAddressSet.add(hexOwner);

    try {
      List<Transaction> blockTxs = new ArrayList<>();
      blockTxs.add(bTx.getInstance());
      BlockCapsule capsule = new BlockCapsule(0, ByteString.EMPTY, 0, blockTxs);

      List<TransactionCapsule> txs = dbManager.getVerifyTxs(capsule);

      Assert.assertEquals(1, txs.size());
      Assert.assertEquals(bTx.getTransactionId(), txs.get(0).getTransactionId());
    } finally {
      ownerAddressSet.clear();
      ownerAddressSet.addAll(backup);
      dbManager.getPendingTransactions().clear();
    }
  }

  public void addSign(byte[] privateKey, AccountStore accountStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = this.transaction.getRawData().getContract(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwnerAddress();
    AccountCapsule account = accountStore.get(owner);
    if (account == null) {
      throw new PermissionException("Account is not exist!");
    }
    Permission permission = account.getPermissionById(permissionId);
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    List<ByteString> approveList = new ArrayList<>();
    SignInterface cryptoEngine = SignUtils
        .fromPrivate(privateKey, CommonParameter.getInstance().isECKeyCryptoEngine());
    byte[] address = cryptoEngine.getAddress();
    if (this.transaction.getSignatureCount() > 0) {
      checkWeight(permission, this.transaction.getSignatureList(),
          this.getTransactionId().getBytes(),
          approveList);
      if (approveList.contains(ByteString.copyFrom(address))) {
        throw new PermissionException(encode58Check(address) + " had signed!");
      }
    }

    long weight = getWeight(permission, address);
    if (weight == 0) {
      throw new PermissionException(
          ByteArray.toHexString(privateKey) + "'s address is " + encode58Check(address)
              + " but it is not contained of permission.");
    }
    ByteString sig = ByteString.copyFrom(cryptoEngine.Base64toBytes(cryptoEngine
        .signHash(getTransactionId().getBytes())));
    this.transaction = this.transaction.toBuilder().addSignature(sig).build();
  }
