### Title
Newly added reward token with `index == INITIAL_INDEX` credits a user's full token balance as accrued rewards — ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenDelta` computes an account's claimable delta as `balanceOf(account).wadMul(index - accountIndex)`. The `accountIndex == 0` fallback only normalizes the baseline when `index > INITIAL_INDEX`. When the token's stored index is exactly `INITIAL_INDEX` (1e18) — i.e., right after `updateTokenSpeed`/`syncTokenSpeed` initializes the `TokenState` and before any timestamp delta accrues — an account that already holds a `DepositToken`/`DebtToken` balance but has `accountIndexOf == 0` gets `_deltaIndex == 1e18`, so `tokensDelta == balanceOf(account)`. The stored accounting variable `tokensAccruedOf[account]` is thereby inflated to the full token balance — the same class as `userBoosts.amount` being written with two different scales depending on the update path.

### Finding Description
- `RewardsDistributor._updateTokenSpeed` initializes a new tracked token with `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` at `contracts/RewardsDistributor.sol:298`.
- `RewardsDistributor._calculateTokenIndex` returns `(0, 0)` when `block.timestamp - tokenState.timestamp == 0`, so within the same block the stored index stays exactly `1e18` (`contracts/RewardsDistributor.sol:200-212`). The index also stays `1e18` if `speed == 0` or `totalSupply == 0` each time it is recomputed.
- `RewardsDistributor._calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`):
  ```
  if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
      _accountIndex = INITIAL_INDEX;
  }
  uint256 _deltaIndex = _tokenIndex - _accountIndex;
  _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
  ```
  When `_tokenIndex == INITIAL_INDEX`, the guard `> INITIAL_INDEX` fails, `_accountIndex` remains `0`, `_deltaIndex == 1e18`, and `wadMul(1e18)` returns the raw balance — i.e., the user is credited `1x` their entire token balance as "accrued" rewards.
- `_updateTokensAccruedOf` then writes `tokensAccruedOf[account_] += _tokensDelta` and stamps `accountIndexOf = 1e18` (`contracts/RewardsDistributor.sol:261-266`), and `claimRewards` pays out `tokensAccruedOf` up to the distributor's reward-token balance via `_transferRewardIfEnoughTokens` (`contracts/RewardsDistributor.sol:248-256`).

Two paths converge on the same storage (`tokensAccruedOf`/`accountIndexOf`) with inconsistent baseline scales — exactly the reported bug shape.

### Impact Explanation
Theft of unclaimed yield / direct theft of reward funds: an attacker can mint `tokensAccruedOf` equal to their full `DepositToken`/`DebtToken` balance and drain the distributor's `rewardToken` balance (capped by `IERC20(rewardToken).balanceOf(distributor)`). With a large deposit (or debt position), the stolen amount equals the attacker's balance denominated in reward tokens, paid for only by temporarily holding collateral — no protocol accounting backs this credit.

### Likelihood Explanation
Requirements:
- Attacker holds a `depositToken`/`debtToken` balance acquired **before** the token is added to the distributor (so `accountIndexOf == 0`). Balances acquired via `DepositToken.deposit`/`DebtToken.issue` before `updateTokenSpeed` leave `accountIndexOf` untouched because `updateBeforeMintOrBurn` skips when `tokenStates[token].index == 0` (`contracts/RewardsDistributor.sol:176`).
- Attacker calls `claimRewards(accounts, [token])` — a permissionless `nonReentrant` public function callable for any account — in the **same block** as the governor/keeper transaction that first sets `speed > 0` (`updateTokenSpeed`, `updateTokenSpeeds`, or `syncTokenSpeed`). These are mempool-observable on L1 deployments, enabling same-block back-running; `onlyIfDistributorExists`/`onlyIfTokenExists` are satisfied for a legitimately added token.
- No health check, pause flag, reentrancy issue, or `SynthContext` check interferes; `claimRewards` deliberately allows claiming on behalf of arbitrary `accounts_`.

### Recommendation
In `_calculateTokenDelta`, apply the `INITIAL_INDEX` baseline whenever the account has no recorded index and the token is tracked, i.e. change the guard to `_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX` (or set `accountIndexOf = INITIAL_INDEX` when the token state is initialized via a first-touch hook). Equivalently, when `TokenState` is created in `_updateTokenSpeed`, existing holders' deltas should be computed against `INITIAL_INDEX` regardless of whether the index has since grown.

### Proof of Concept
Foundry test sketch (deploy `Pool`/`DepositToken`/`RewardsDistributor` per repo fixtures):

```solidity
function testInflatedAccrualSameBlock() public {
    // 1. Attacker deposits collateral BEFORE the deposit token is added to rewards
    depositToken.deposit(1000e18, attacker);   // tokenStates[depositToken].index == 0 -> hook no-ops

    // 2. In the SAME block, governor enables rewards for the deposit token
    vm.prank(governor);
    rewardsDistributor.updateTokenSpeed(depositToken, speed); // index = 1e18, timestamp = now
    // no time passes -> _calculateTokenIndex returns (0,0); stored index stays 1e18

    // 3. Attacker (or anyone) triggers accrual in the same block
    IERC20[] memory toks = new IERC20[](1);
    toks[0] = IERC20(address(depositToken));
    address[] memory accts = new address[](1);
    accts[0] = attacker;
    rewardsDistributor.claimRewards(accts, toks);

    // _deltaIndex = 1e18 - 0 -> tokensDelta = 1000e18 * 1 = 1000e18
    // attacker receives ~1000e18 rewardToken for a zero accrual period
    assertGt(rewardToken.balanceOf(attacker), 0);
}
```

Caveat: exploitability hinges on executing in the same `block.timestamp` as the speed-initialization transaction (or on a token whose index remains `INITIAL_INDEX` because `totalSupply`/`speed` conditions never produced accrual while an account held a balance). I verified the arithmetic and hook coverage directly; I did not exhaustively check `ProxyOFT`/gateway paths for alternative ways to hold a balance while `accountIndexOf == 0`, but `claimRewards`'s permissionless multi-account form already provides a sufficient trigger.
