## Title
Out-of-bounds read when parsing ZIP "extra field" records in ijar's central directory parser — (`third_party/ijar/zip.cc`)

## Summary
`InputZipFile::ProcessCentralDirEntry()` in ijar (Bazel's interface-JAR / `zipper`/`singlejar`-adjacent ZIP reader used to process JAR files that can originate from attacker-controlled `http_jar`/`http_archive` downloads) reads the 2-byte `extra_field_length` from a Central Directory Header and then walks the "extra fields" region reading 2-byte `header_id`/`data_size` pairs with `get_u2le()`, without checking that at least 4 bytes remain before each read or that `data_size` fits inside the declared extra-field region. This is structurally the same bug class as the OpenEXR `IDManifest::init()` issue: a length-prefixed sub-record is decoded by unconditionally reading a fixed number of header bytes from attacker-supplied data without first verifying that many bytes are actually available.

The loop condition is only `extra_p != p` (i.e., `extra_p < extra_p_start + extra_field_length`), but `get_u2le(extra_p)` unconditionally reads 2 bytes for `header_id` and another 2 bytes for `data_size` before checking that 4 bytes remain in the declared extra-field window. If `extra_field_length` is odd, or a trailing sub-record's declared `data_size` runs past the parent's `extra_field_length`, the code advances `extra_p` past `p` and continues issuing `get_u2le`/`get_u8le` reads (for `ZIP64_EXTRA_FIELD_TAG`) beyond the region that was validated as belonging to this entry — this can walk into the file-comment bytes, into the next Central Directory Header, or, near the boundary of a crafted mmap'd file, past the mapped region entirely, causing an out-of-bounds read.

This is the same defect pattern as the reported OpenEXR bug: a length-prefixed byte stream is decoded by reading fixed-size header fields (there, the 2-byte prefix length; here, the 4-byte `header_id`+`data_size` pair) without first confirming that many bytes remain in the current record, relying instead on an implicit "the data must be well-formed" assumption. The code comment explicitly documents this assumption ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") but that only bounds the *entry* boundary via a signature scan on the next iteration of the outer loop — it does not bound the *inner* extra-field sub-record walk, which is exactly where the OOB read can occur.

## Impact Explanation
ijar processes JAR/ZIP files that are frequently pulled in via `http_jar`/`http_archive`/`java_import` from third-party URLs. A malicious origin server (or a compromised mirror serving bytes matching a pinned `sha256`, since the checksum verifies byte content but says nothing about ZIP-structural well-formedness) can craft a Central Directory Header with a manipulated `extra_field_length`/nested `data_size` that causes `ProcessCentralDirEntry` to read past the boundary of the declared extra-field region. Depending on layout this can read adjacent heap/mmap memory (comment bytes, next header, or, at an unlucky page boundary, unmapped memory), producing an out-of-bounds read that can crash the build (`ijar`/interface-jar generation) or leak adjacent memory bytes into computed offsets that influence subsequent parsing decisions.

## Likelihood Explanation
Reaching this code only requires supplying a JAR whose Central Directory Header contains a crafted `extra_field_length` and a trailing/oversized extra-field sub-record — no privileged access is required, only control over the bytes served for a `http_jar`/`http_archive`/downloaded `.jar` dependency that is fed through ijar (e.g., interface jar generation for `java_import` / `java_library` deps). The `sha256`/`integrity` check on the download only pins *which* bytes are fetched; it does not validate ZIP-internal structural invariants, so a checksum-pinned malicious jar can still trigger this path. I could not fully verify from static reading alone whether typical mmap page-alignment/guard behavior makes an actual segfault difficult to trigger in practice (vs. only being detectable via ASan/valgrind as a heap-buffer-overflow read); this affects exploitability but not the presence of the missing bounds check itself.

## Recommendation
In `third_party/ijar/zip.cc`'s `ProcessCentralDirEntry`, before reading each extra-field sub-record header, verify that at least 4 bytes remain between `extra_p` and the extra-field region end (`p`), and verify that `data_size` does not extend `extra_p` past that end, mirroring the bounds checks already implemented in `ExtraField::find()` in `src/tools/singlejar/zip_headers.h`. Reject (return `false`/error) malformed entries instead of continuing to walk past the declared boundary.

## Proof of Concept
Construct a minimal ZIP whose Central Directory Header sets `extra_field_length = 3` (an odd value smaller than one full `header_id`+`data_size` pair boundary alignment) or, more directly, sets a single extra-field entry with `data_size` larger than the remaining bytes in the declared `extra_field_length` window, followed immediately by only a few bytes before EOF (no further valid Central Directory Header). Feed this via a new test in `third_party/ijar` (e.g., extending `zip_test.cc`/adding a `zip_test` case akin to `ZipHeadersTest.CentralDirectoryHeader` in `src/tools/singlejar/zip_headers_test.cc`) that calls `InputZipFile::ProcessCentralDirEntry` on the crafted buffer under AddressSanitizer, and confirm the read now walks past the declared extra-field/file boundary, which ASan reports as a heap-buffer-overflow read. I was not able to execute this PoC in this environment; it should be run as a background verification step. [4](#0-3)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
