### Title
Aggregate position notional evaluation aborts entirely when any single held asset's oracle malfunctions, freezing unrelated healthy collateral - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`get-assets` builds the list of a user's held assets (all debt-side assets, unfiltered by the admin-enabled bitmap) and resolves a price for every one of them via `price-multi-resolve`. If price resolution fails for even one asset (e.g. a stale/reverting Pyth/DIA feed, a broken `callcode` transform, or a confidence/staleness violation), the whole call fails, which is then wrapped in `unwrap-panic` inside `get-assets`, aborting the entire transaction. Because `collateral-remove` (when the user has debt) and `borrow` both depend on `get-assets`/`get-notional-evaluation` to compute collateral/debt USD values for the health check, a single malfunctioning oracle for ANY asset the user holds debt in blocks the user from withdrawing or adding collateral for every other, unaffected asset in their position - directly analogous to the SafEth `[H-03]` pattern where one broken derivative DOS'd the shared `unstake` loop.

### Finding Description
`get-assets` at `mainnet/contracts/market/v0-4-market.clar:482-492` computes `safe-mask` via `user-safe-mask`, which only filters the *collateral* bits by the admin-enabled bitmap - the *debt* bits pass through unfiltered: [1](#0-0) 

It then resolves prices for every asset in that combined list in one shot: [2](#0-1) 

`price-multi-resolve`/`iter-price-multi` propagate any single failed `price-resolve` call as `valid: false`, and the caller `asserts!`s on that, then `get-assets` calls `unwrap-panic` on the whole result: [3](#0-2) 

`price-resolve` itself can fail for a variety of reasons that are outside a normal user's or the admin's immediate control once triggered: a stale/regressed oracle timestamp, a zero/invalid price, or a broken `callcode` transform (`resolve-ststx`/`resolve-ztoken`, which itself depends on `call-ststx-ratio` or the liquidity-index cache): [4](#0-3) 

Both `collateral-remove` (debt path) and `borrow` call `get-assets`/`get-notional-evaluation` before doing anything else, meaning a broken oracle for ANY one asset in the user's mask reverts the whole call, even for collateral unrelated to the broken asset: [5](#0-4) [6](#0-5) 

By contrast, `repay` deliberately avoids all price resolution, computing repayable amounts purely from the scaled debt and borrow index: [7](#0-6) 

This means the only escape route from the freeze is for the user to fully repay the debt in the asset whose oracle is broken (removing that bit from their mask) - but this requires them to source that specific token, which the exploit's cause may or may not permit, and is not something the admin's "disable this asset" governance action helps with, since disabling only affects the admin-enabled bitmap used for *collateral* filtering, not the debt-side bits that reach `get-assets`.

### Impact Explanation
This lands in the **High - temporary freezing of funds** category (and can approach permanent freezing if the user cannot source the specific debt asset to repay it). A user with healthy, unrelated collateral (e.g. STX) and a small debt in an asset whose oracle malfunctions (stale feed, `callcode` failure, zero price) is blocked from calling `collateral-remove` or `borrow` for any asset in their position until either the oracle recovers or they fully repay the affected debt. This mirrors the SafEth report's core defect: aggregate, all-or-nothing processing over a set of assets/derivatives with no way to exclude a single malfunctioning member from the loop that determines whether an unrelated operation can proceed.

### Likelihood Explanation
Likelihood is moderate: it requires an oracle malfunction (staleness, feed failure, confidence breach, or a `callcode`-dependent computation like `call-ststx-ratio` failing) for an asset that a user has actually borrowed. Since oracle feeds (Pyth/DIA) and `callcode` dependent contracts (e.g. stSTX ratio) are external, out-of-protocol-control failure modes, this is a realistic operational risk rather than a contrived edge case, and it affects every user who has debt in the malfunctioning asset simultaneously.

### Recommendation
Decouple the health-check aggregation from all-or-nothing price resolution: either (1) allow `get-assets`/`price-multi-resolve` to continue evaluating other assets and only fail the specific health check that needs the broken asset's price (e.g. skip zero-balance/zero-scaled-debt legs, or use a last-good cached price with an explicit staleness-tolerant fallback for read paths that don't strictly require a fresh price), or (2) filter the debt-side mask the same way collateral is filtered against an admin "asset enabled" flag and let the admin force a specific stuck debt asset out of the aggregate evaluation (with an explicit socialize/quarantine path), analogous to the mitigation Asymmetry shipped for SafEth (enable/disable per-asset processing) but extended to cover the debt side of the mask, not just collateral.

### Proof of Concept
1. User A deposits STX as collateral and borrows a small amount of Asset X (whose oracle uses `callcode` `CALLCODE-ZSTSTX`/`CALLCODE-STSTX` or a Pyth/DIA feed).
2. The oracle backing Asset X becomes stale beyond `max-staleness`, or the `call-ststx-ratio` contract call underlying `resolve-ststx` starts failing, or the feed returns a `0` price.
3. User A calls `collateral-remove` to withdraw some of their unrelated, perfectly healthy STX collateral. `collateral-remove` → `get-assets` → `price-multi-resolve` → `price-resolve` on Asset X fails `oracle-timestamp-fresh`/`oracle-price-legal`/`resolve-callcode`, causing `ERR-ORACLE-INVARIANT`/`ERR-ORACLE-CALLCODE`, propagated as `valid: false`, and `get-assets`'s `unwrap-panic` aborts the entire transaction.
4. `borrow` fails the same way. User A's healthy STX collateral is now stuck until either the oracle for Asset X recovers or User A can source and fully repay their Asset X debt via `repay` (the only call that avoids `get-assets`).

(define-public (repay (ft <ft-trait>) (amount uint) (on-behalf-of (optional principal)))
  (let ((address (contract-of ft))
        (asset (try! (get-asset address)))
        (asset-id (get id asset))
        ;; defaults to payer (contract-caller) if not specified
        (account (match on-behalf-of behalf behalf contract-caller))
        
        ;; Step 1: Get position WITHOUT resolving prices
        (position (try! (get-position account)))
        (mask (get mask position))
        
        ;; Step 2: Accrue user's positions (populates cache for ztokens)
        (u-debt (accrue-user-debts (get debt position)))
        
        (borrow-index (get index (unwrap-panic (get-cached-indexes asset-id))))
        
        ;; Step 3: Get account debt FIRST to enable safe amount capping
        (account-scaled-debt (get-account-scaled-debt account asset-id))
        
        ;; Step 4: Calculate max repayable amount (actual debt in token), mul-div-up for safe upper bound
        (max-repay-tokens (mul-div-up account-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Step 5: Cap input amount at actual debt - prevents overflow in scaled calculation
        (safe-amount (min amount max-repay-tokens))
        
        ;; Step 6: Convert to scaled debt (amount is bounded)
        (scaled-debt-repayment (mul-div-down safe-amount INDEX-PRECISION borrow-index))

        (repaid-scaled-debt (min account-scaled-debt scaled-debt-repayment))
        (amount-to-repay (mul-div-up repaid-scaled-debt borrow-index INDEX-PRECISION))
        
        ;; Check if repaying ALL debt for this asset
        (repaying-all (is-eq repaid-scaled-debt account-scaled-debt)))
