### Title
Unsynchronized firewall pointer swap during `reloadFirewall` allows stale/inconsistent rule enforcement on in-flight packets - (File: interface.go)

### Summary
The Sherlock report describes a class of bug where an invariant-enforcing check (`MAXIMUM_NUMBER_OF_DEPOSITS_PER_ROUND`) can be violated because a state-mutating admin action (pause/unpause) races with an asynchronous callback (`fulfillRandomWords`), leaving a window where the enforced invariant is checked against stale state. The reachable analog in nebula is the firewall-ruleset hot-swap performed by `reloadFirewall`, which replaces the `Interface.firewall` pointer with no synchronization against the concurrent packet-processing goroutines that read that same field to make Drop/allow decisions.

### Finding Description
`Interface.firewall` is declared as a plain, unsynchronized pointer field: [1](#0-0) 

`reloadFirewall` is invoked asynchronously (as a config reload callback, e.g. on SIGHUP) and swaps this pointer with a plain assignment, guarded only by the `Conntrack` mutex (which protects the conntrack map, not the `firewall` field itself, nor the read side): [2](#0-1) 

Meanwhile, every packet-processing goroutine (`listenIn`/`listenOut`, one per configured `tun.routines`/`listen.routines`) reads `f.firewall` directly and unsynchronized on the hot path to decide whether to allow, reject, or conntrack a packet: [3](#0-2) [4](#0-3) 

Because there is no atomic pointer (`atomic.Pointer[Firewall]`) or lock protecting reads of `f.firewall`, and no `sync/atomic` load/store pairing between the writer (`reloadFirewall`) and the many concurrent readers, the Go memory model gives no guarantee about when (or whether) a given reader goroutine observes the new firewall object after a config-driven reload. This mirrors the root cause of the report: an invariant-affecting state transition (rule replacement) happens concurrently with the exact code path that is supposed to enforce the invariant (`Drop()`), and the enforcement path can keep evaluating against the pre-reload (now-stale) rule set for an indeterminate/unbounded window, instead of atomically switching over.

This is distinct from — and not remediated by — the `rulesVersion`/conntrack-revalidation mechanism in `firewall.go`, which only re-validates *existing* conntrack entries once a goroutine actually observes the new `Firewall` object; it does nothing to guarantee *when* that observation happens.

### Impact Explanation
If an operator narrows the firewall policy at runtime (e.g., removing an "allow" rule for a host/subnet in response to an incident) via a config reload, packet-processing goroutines that have not yet observed the pointer swap will continue to evaluate inbound/outbound traffic against the old, more permissive ruleset. This is a concrete firewall-bypass condition: attacker traffic that should be dropped under the newly-installed policy can continue to be allowed through the tunnel for an unbounded amount of time, undermining the security-group based access control that is nebula's core network security mechanism (as described in the README).

### Likelihood Explanation
Reachability requires an operator-triggered firewall reload (SIGHUP/config change) — this is a normal, expected operational event, not a rare emergency action, making the window more likely to be hit than the "protocol paused" scenario in the original report (which the LooksRare judges themselves argued was low-likelihood). Any already-established, attacker-controlled peer whose traffic should be dropped under the new rules can continue sending packets during the race window on multi-routine configurations (`tun.routines`/`listen.routines` > 1, a supported and common configuration for performance).

### Recommendation
Use an atomic pointer for the firewall reference (`atomic.Pointer[Firewall]`) with `Store`/`Load` on both the writer side (`reloadFirewall`) and every reader site (`inside.go`, `outside.go`), so that the swap is published with proper memory-model guarantees and all future reads by any goroutine observe the new ruleset promptly and consistently, rather than relying on incidental pointer-write visibility.

### Proof of Concept
Not applicable in the traditional sense — this is a data race requiring the Go race detector or a targeted stress test (e.g., run nebula with `tun.routines: 4`, continuously inject inbound packets on all reader goroutines while concurrently calling `reloadFirewall` with a stricter ruleset from a separate goroutine, and run with `go test -race`) to demonstrate that `f.firewall` reads/writes are unsynchronized and that reader goroutines can retain the old `*Firewall` object past the point the new one has been installed.
