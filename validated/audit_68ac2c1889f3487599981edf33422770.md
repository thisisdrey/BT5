Audit Report

## Title
Snowbridge V2 `process_delivery_receipt` pays and settles relayer reward without checking Ethereum execution `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
The `DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries an explicit `success: bool` field indicating whether the dispatched command actually executed successfully on Ethereum. `Pallet::process_delivery_receipt` verifies the event proof, decodes the receipt, and then unconditionally pays out the full `PendingOrder.fee` reward and removes the order — it never inspects `receipt.success`.

## Finding Description
`submit_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:298-317`) requires only a signed origin plus a valid proof from `T::Verifier::verify`, which attests only that the log was genuinely emitted by the Gateway contract — not that the dispatched command succeeded. The decoded `DeliveryReceipt` struct explicitly carries `success: bool` sourced from the `InboundMessageDispatched` Solidity event (`bridges/snowbridge/primitives/outbound-queue/src/v2/delivery_receipt.rs:10-27`). In `process_delivery_receipt` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:445-480`), the function checks `receipt.gateway`, looks up `PendingOrders` by `receipt.nonce`, pays `order.fee` via `T::RewardPayment::register_reward`, and removes the order — `receipt.success` is never read anywhere in this path. This means a message whose command reverted on Ethereum (e.g., out-of-gas `Transact`, or command-level revert) still emits the event with `success=false`, and any relayer submitting that valid proof receives the full reward exactly as if delivery had succeeded, while the `PendingOrder` is permanently removed with no retry mechanism.

## Impact Explanation
This breaks the required invariant that payout state must only advance after execution actually succeeds. An unprivileged relayer is paid the full fee for deliveries that did not actually execute on Ethereum, and the corresponding `PendingOrder` (identified by its `nonce`) is irrevocably cleared, eliminating any path to retry or correctly re-attribute the reward. This is a fund-payout correctness bug in the bridge's economic/reward settlement logic — wrong settlement condition (proof-of-log-emission) substituting for the required condition (proof-of-successful-execution).

## Likelihood Explanation
Any relayer running the standard, permissionless `submit_delivery_receipt` flow can trigger this whenever a dispatched command fails on the Ethereum side — a realistic and recurring scenario for complex or underpriced commands — with no governance, validator, or malicious-peer assumption required.

## Recommendation
In `Pallet::process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`; for `success == false`, withhold or refund the fee (or route to a distinct failure-settlement path), while still removing/marking the `PendingOrder` to prevent replay.

## Proof of Concept
1. A message is queued via `do_process_message`, inserting `PendingOrders[nonce] = { fee, ... }` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:426-436`).
2. On Ethereum, the dispatched command reverts, but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof for this log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` decodes `success: false` successfully, and `process_delivery_receipt` proceeds to `register_reward(&reward_account, ..., order.fee)` and removes the `PendingOrder` — identical to the `success: true` path (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:445-480`), since `receipt.success` is never read.
