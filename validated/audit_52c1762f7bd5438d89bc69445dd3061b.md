### Title
Expensive multi-signature verification performed before bandwidth/energy is charged, enabling free-CPU DoS - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
The Arbitrum report identifies that WASM activation performs expensive decompression before gas is charged, so a crafted input that fails decompression lets an attacker consume node CPU for free. The analogous root cause exists in java-tron's transaction admission path: `TransactionCapsule.validateSignature()` (which can perform ECDSA public-key recovery for every signature in a multi-signature transaction) runs before any bandwidth/energy is deducted from the sender.

### Finding Description
In `Manager.pushTransaction` an incoming transaction is signature-validated immediately: [1](#0-0) 
and again in `Manager.processTransaction`, `validateSignature` is invoked at line 1542 — well before `consumeBandwidth(trxCap, trace)` at line 1555, which is the point where the account's bandwidth/energy is actually charged: [2](#0-1) 

`validateSignature` → `validatePubSignature` performs the actual cryptographic work: it checks the signature count against `dynamicPropertiesStore.getTotalSignNum()` (a chain-configurable, potentially large ceiling) and then does the CPU-expensive ECDSA hash/recovery inside `validateSignature(...)`, guarded only by a timer that *logs* slow verification after the fact rather than charging for it: [3](#0-2) 

If the signature is invalid (garbage bytes, wrong recovery id, etc.), a `ValidateSignatureException` is thrown immediately after the CPU-expensive verification, and the transaction is discarded from `pushTransactionQueue` — `consumeBandwidth`/`consumeMultiSignFee` are never reached, so **no resource is ever charged for the CPU work already performed**: [4](#0-3) 

This is structurally identical to the WASM bug: an expensive, user-triggerable operation (bytecode decompression / signature recovery) executes prior to the point where the caller's resources are debited, and a crafted failure path (corrupted compressed bytes / malformed signature) guarantees the operation is done "for free."

### Impact Explanation
An anonymous JSON-RPC/gRPC client (via `Wallet.broadcastTransaction` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction`) can submit a stream of transactions carrying the maximum allowed signature count (`getTotalSignNum()`) filled with syntactically valid-length but cryptographically invalid signature bytes. Each such transaction forces the node to perform multiple ECDSA signature-recovery operations before the transaction is rejected and before any bandwidth/energy fee is imposed on the (potentially non-existent or attacker-controlled) sending account. Because it costs the attacker nothing (no valid account balance/bandwidth required to reach the crypto step) this is a computational resource-exhaustion vector against block producers and full nodes that validate incoming transactions and gossip signatures in parallel (`preValidateTransactionSign`), potentially degrading transaction throughput or causing missed block production — a network-DoS class impact reachable purely via unauthenticated transaction broadcast.

### Likelihood Explanation
The path is reachable directly from `Wallet.broadcastTransaction` with a single, unsigned/malformed transaction — no privileged access, valid account, or prior transaction history is required. The signature-count ceiling (`getTotalSignNum`) can be set to multiple signatures per transaction, multiplying the CPU cost per submitted transaction while the rejection happens deterministically before charging, making the attack trivially repeatable and cheap to script.

### Recommendation
- **Short term:** Reorder transaction admission so that a preliminary, cheap sanity/format check (length, count bounds, structural correctness) happens first, and ensure any account-chargeable cost (bandwidth/energy) is deducted, or the sender is otherwise penalized/rate-limited, before performing the expensive per-signature ECDSA recovery — mirroring the recommendation to charge gas as early as possible in WASM activation. At minimum, apply a strict per-IP/per-account rate limit on `pushTransaction` requests that fail `validateSignature` so unpriced expensive verification cannot be repeated without bound.
- **Long term:** Audit all other computationally expensive, user-triggerable pre-charge operations in the transaction/block admission pipeline (e.g., `preValidateTransactionSign`, zk-SNARK proof checks for `ShieldedTransferContract`, `ValidateMultiSign` precompile signature loops) to ensure CPU cost is either charged up front or strictly bounded/rate-limited before expensive cryptography executes.

### Proof of Concept
1. Construct a `Transaction` with a `raw_data` containing any contract and attach `getTotalSignNum()` (chain parameter, e.g. 5) signatures, each a random 65-byte blob with a valid `v` byte range so it passes format checks but fails EC point recovery/matching against any real account permission.
2. Submit repeatedly via the gRPC/HTTP `broadcastTransaction` endpoint (`Wallet.broadcastTransaction`).
3. Each call flows into `Manager.pushTransaction` → `trx.validateSignature(...)` → `validatePubSignature` → per-signature ECDSA recovery, all executed prior to `consumeBandwidth`/`consumeMultiSignFee`; the call then throws `ValidateSignatureException` and the transaction is discarded without any resource debit, at file/lines: `framework/src/main/java/org/tron/core/db/Manager.java:904-909`, `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:650-680`.
4. Repeating this at scale demonstrates unpriced CPU consumption on the node with zero cost to the attacker, consistent with the reported bug class.

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
