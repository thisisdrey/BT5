### Title
Unbounded array allocation from attacker-controlled length field in `PrecompiledContracts.extractBytesArray` causes node-crashing memory exhaustion - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2017-12804 bug class is "attacker-controlled length field used to allocate a buffer without an upper bound, causing memory exhaustion." The same pattern exists in the `ValidateMultiSign` precompiled contract's legacy signature-array extraction path, where a length taken directly from calldata is used to allocate a Java array with no upper-bound check before the allocation occurs.

### Finding Description
`extractBytesArray` reads an unchecked, caller-supplied length word and immediately allocates an array of that size: [1](#0-0) 

`ValidateMultiSign.execute` calls this helper in the legacy (`!allowTvmSelfdestructRestriction()`) code path *before* any size check is applied — the `MAX_SIZE` bound is only checked on the already-allocated array's `.length` result, and only unconditionally for the `extractSigArray`/newer path is the size validated pre-allocation: [2](#0-1) 

`words[offset].intValueSafe()` clamps only to `Integer.MAX_VALUE` (not to any sane protocol limit), so `len` in `extractBytesArray` can be up to `2^31-1`, making `new byte[len][]` request several GB of heap for the object-reference array alone. This call sits outside the `try { ... } catch (Throwable t)` block that wraps the rest of the method (that block starts only at line 1082, after the array has already been allocated), so a resulting `java.lang.OutOfMemoryError` is not contained by this actuator and propagates out of the precompiled-contract dispatch.

### Impact Explanation
An `OutOfMemoryError` thrown mid-execution inside the TVM can destabilize or crash the node's JVM process depending on how far up the call stack it is caught, since it is a `java.lang.Error`, not a checked/application exception, and is raised before the contract's own `Throwable` guard is reached. Any unprivileged account can trigger this by calling the `ValidateMultiSign` precompile through a smart contract with a single crafted call, without spending significant energy since the cost model in `getEnergyForData` is computed from `data.length`, not from the value of the length field embedded in the data. This matches the "node crash or halt" acceptance bar.

### Likelihood Explanation
Reachable by any address that can send a transaction invoking a contract that calls the `ValidateMultiSign` precompile — no special privileges required, and the trigger is a single calldata field. The only gating factor is that this specific vulnerable branch is guarded by `VMConfig.allowTvmSelfdestructRestriction()` being `false`; whether that hard-fork flag is active on a given production network determines whether this exact branch is currently reachable, which I could not fully confirm from the indexed files.

### Recommendation
Validate the extracted length against a strict upper bound (e.g., `MAX_SIZE`) inside `extractBytesArray`/`extractBytes32Array` themselves, before allocating any array, rather than only after the fact in the caller. Wrap the entire `ValidateMultiSign.execute`/`BatchValidateSign.doExecute` bodies (including array extraction) in the existing `Throwable` guard so any allocation failure degrades to a revert instead of an uncaught `Error`.

### Proof of Concept
Craft calldata to `ValidateMultiSign` (or `BatchValidateSign` in its pre-check state) where the word at the signature-array offset (`words[3]` referenced offset) encodes a huge count (e.g., close to `Integer.MAX_VALUE / WORD_SIZE`). Invoke via a contract `CALL` from any account; `extractBytesArray` executes `new byte[len][]` before any bound check, attempting a multi-gigabyte allocation and risking `OutOfMemoryError` propagation.   private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
