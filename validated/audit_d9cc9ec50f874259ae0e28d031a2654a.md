### Title
Account-creation charge invariant enforced only by `debug_assert!`, silently violated in release builds - (File: `runtime/runtime/src/lib.rs`)

### Summary
`Runtime::refund_unspent_gas_and_deposits` charges an account-creation fee (`account_creation_charge`, mainnet `0.007 N`) out of the refund owed to the payer of a receipt that created a new account [1](#0-0) . The logic explicitly documents and depends on the invariant "purchasing gas at `min_gas_purchase_price` should be enough to cover the cost of creating an account," i.e. `min_gas_purchase_price * create_account_gas_cost >= account_creation_charge` [2](#0-1) . This is the same shape as the Mochi bug: two economically related parameters (a "floor price" and a "charge" derived from it) must maintain a specific ordering/buffer, or the system's accounting breaks down.

### Finding Description
The invariant is checked only with `debug_assert!`, which is compiled out in release builds [3](#0-2) [4](#0-3) . The two governing parameters, `min_gas_purchase_price` and `account_creation_charge`, are both ordinary versioned `RuntimeConfig`/`RuntimeConfigStore` parameters loaded from YAML diffs (e.g. both introduced together in `85.yaml`) [5](#0-4) , with no cross-field validation performed when the config store is built (`RuntimeConfig::try_from` assembles fields independently; `ParameterTable::apply_diff` only checks that a diff's declared `old` value matches, not any cross-parameter relationship) — this was confirmed by inspecting the config assembly/validation code path, which contains no comparison between these two fields. The `RuntimeConfig::free()` constructor even documents that it relies on the same untested invariant, only guaranteeing it "holds trivially" by zeroing both fields, again evidencing there is no structural enforcement [6](#0-5) .

If a future protocol-version config diff (or a non-mainnet/testnet chain, e.g. a permissioned or custom nearcore-based chain, which is an ordinary in-scope deployment of this code) sets `account_creation_charge` too high relative to `min_gas_purchase_price` (for example by only bumping `account_creation_charge` without correspondingly raising `min_gas_purchase_price`, or by lowering `min_gas_purchase_price` in a later diff without checking downstream consumers), the code takes the safe path via `std::cmp::min(amount_to_charge, burned_gas_refund)` [7](#0-6)  — so no panic or fund-loss occurs from this clamp alone in the currently release build. However, the invariant is treated as load-bearing elsewhere in the design ("as long as the purchase price is high enough, there should always be enough refund balance to cover the cost"), and the guard against violation exists purely as a `debug_assert!`, meaning any code path relying on this guarantee without the `min()` clamp would silently produce incorrect (uncharged or under-charged) account-creation economics in a release binary, and the violation would go completely undetected in production since `debug_assert!` never fires there.

### Impact Explanation
This is a latent misconfiguration/logic-invariant bug rather than a directly exploitable one in the current values (mainnet's `min_gas_purchase_price=1e9 yN`, `account_creation_charge=0.007N`, `create_account` exec gas `7.2 Tgas` satisfy the inequality). The impact is that the safety invariant protecting the account-creation charge economics is unverified in production, so any future protocol upgrade that changes either parameter independently (a routine governance action, analogous to Mochi's team independently tuning CF/LF per asset class) can silently break the intended cost recovery for account creation, without any error or metric signaling the violation, potentially causing under-collection of the account-creation fee (a mild "value leak" from the fee mechanism, not a shard-halting or theft-of-funds bug in the current release).

### Likelihood Explanation
Low-to-moderate: the bug does not manifest under the current release's shipped values, so no active user-triggerable exploit exists today. It requires a future config-diff change to one of these two parameters without updating the other — exactly the kind of independent, ordinary-looking parameter tuning that caused the original Mochi CF/LF bug — combined with the complete absence of a release-mode check.

### Recommendation
Replace the `debug_assert!` at `runtime/runtime/src/lib.rs:1327-1331` and `:1335-1336` with either (a) a build-time/config-load-time validation in `RuntimeConfigStore`/`RuntimeConfig::try_from` that rejects a `RuntimeConfig` whose `min_gas_purchase_price * create_account_gas_cost < account_creation_charge`, or (b) a runtime `checked`/saturating computation path that does not rely on the invariant holding, so that a future misconfiguration cannot silently under-charge account creation.

### Proof of Concept
No standalone transaction-based PoC is available: the current mainnet/testnet parameter values satisfy the invariant, so no on-chain exploit exists today. The vulnerability is a structural gap — analogous to Mochi's CF/LF mismatch — verified by direct code inspection: the invariant is only asserted via `debug_assert!` [8](#0-7)  and there is no corresponding check in `RuntimeConfig`/`RuntimeConfigStore`/`ParameterTable::apply_diff` that enforces `min_gas_purchase_price * create_account_gas_cost >= account_creation_charge` when parameters are loaded from a config diff (e.g. `core/parameters/res/runtime_configs/85.yaml`, which introduces both values in the same diff without any cross-check) [5](#0-4) .
