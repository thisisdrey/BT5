### Title
StackerDB chunk signatures omit the StackerDB contract identity from the signed digest, enabling cross-database signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the message that a StackerDB slot owner signs as `SHA512/256(slot_id || slot_version || data_hash)` only. It never binds the signature to the specific StackerDB instance (`smart_contract_id`) that the chunk is being written to. This is the exact analog of the reported EIP-712 bug class: the signed payload is missing a domain/type identifier that scopes the signature to its intended context, so a signature that is valid in one context can be replayed, unmodified, into a different context where the verifier only checks the fields that *are* covered.

### Finding Description
The digest committed to by a StackerDB slot signature is built here: [1](#0-0) 

```rust
fn auth_digest(&self) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```

`sign()`/`verify()` operate purely on this digest: [2](#0-1) 

Verification of an incoming chunk (whether pulled via sync or unsolicited-pushed) resolves the expected signer address *per StackerDB contract*, then checks the signature against that address, but the contract identity never enters the digest that was actually signed: [3](#0-2) 

The wire message that carries a pushed chunk explicitly carries a separate `contract_id` field alongside the `chunk_data`, but that `contract_id` is not part of what is hashed/signed — it is only used to select which config/signer-address table to check against: [4](#0-3) 

Because `slot_id`, `slot_version`, and `data_hash` are the *only* things bound into the signature, if the same signer address holds a slot with the same `slot_id` in two different StackerDB smart contracts (which is a normal, expected configuration for the Stacks signer set — the same signer set is replicated across multiple StackerDB contracts, e.g. per-cycle `.signers-*` or block-proposal DBs, typically with matching slot index ordering), then a chunk that the signer legitimately authored and broadcast for StackerDB A is a **valid** signature for the corresponding slot in StackerDB B as well, even though the signer never intended or authorized writing that data to B. This exactly mirrors the reported bug's root cause: the missing "typeHash"/domain component means data that is unambiguously scoped by the application (contract identity) is not actually bound by the cryptographic commitment, so the same bytes+signature satisfy verification in more than one intended context.

### Impact Explanation
This breaks the equality "signed for StackerDB contract X" vs. "signed for any StackerDB context accepting this slot_id/version/data". An unprivileged remote peer that observes a legitimately-gossiped, validly-signed `StackerDBChunkData` for one contract can resubmit/relay that exact same `(slot_id, slot_version, sig, data)` tuple to a different StackerDB contract's endpoint or push-gossip path. If that contract's slot-signer table maps the same `slot_id` to the same signer address (a realistic configuration for co-deployed signer-set StackerDBs), the replica will accept and store the chunk as authentic (`validate_received_chunk` / `try_replace_chunk` succeed), and the node will further gossip it network-wide via the relay path (`RelayPayload for StackerDBPushChunkData`, keyed only on `data_hash`) — i.e., an unauthorized write to state and forged-context data propagation, without needing the signer's private key or any admin role.

### Likelihood Explanation
The prerequisite (same signer address assigned to matching slot IDs across sibling StackerDB contracts) is a plausible, common deployment pattern for the Stacks signer-set StackerDBs, not a contrived edge case. The attacker only needs to observe one legitimately-signed, publicly-gossiped chunk and resend it — no secret key, no privileged role, and no more than ordinary peer-to-peer message volume is required.

### Recommendation
Include a domain/context identifier — at minimum the `smart_contract_id` (and ideally a StackerDB-specific typeHash/version constant) — inside `SlotMetadata::auth_digest()` before hashing `slot_id`, `slot_version`, and `data_hash`, so that a signature is cryptographically bound to the specific StackerDB instance it was produced for, mirroring EIP-712's requirement to hash in a domain separator and typeHash rather than only the "loose" application fields.

### Proof of Concept
1. Configure two StackerDB contracts A and B such that address `S` (controlled by signer key `sk`) is the assigned signer for `slot_id = 0` in both A and B (a normal signer-set replication scenario).
2. Signer legitimately creates and signs `StackerDBChunkData { slot_id: 0, slot_version: 1, data: D }` with `sk` for contract A, and it propagates via `PeerNetwork::handle_unsolicited_StackerDBPushChunk`.
3. Attacker (any peer) captures this message, then submits `StackerDBPushChunkData { contract_id: B, chunk_data: <same chunk> }` (or POSTs to `/v2/stackerdb/{B}/{name}/chunks`) to any node replicating B.
4. `validate_received_chunk` resolves the signer address for B/slot 0 to `S`, calls `SlotMetadata::verify(&S)`, which succeeds because `auth_digest()` never included the contract identity — the chunk is accepted and stored for B and relayed onward, even though it was never authorized for B.

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
