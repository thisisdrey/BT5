### Title
Relay identity spoofing via unauthenticated `RelayFromAddr` in `CreateRelayRequest` — (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` accepts a `RelayFromAddr` value taken directly from the incoming `NebulaControl` message body and uses it, unchecked, as the identity for which relay state is created on behalf of the sending peer `h`. Nothing ties the claimed `from` address to `h`'s actual certificate identity (`h.vpnAddrs` / `h.GetCert()`). This is the same bug class as the Ajna `Pool.transferLPs` finding: a privileged/state-changing action ("act on behalf of address X") is performed based purely on caller-supplied data instead of verifying that the caller is actually authorized to represent that identity.

### Finding Description
When a node receives a `header.Control` packet, it is routed to `relayManager.HandleControlMsg`, which only verifies that `RelayFromAddr`/`RelayToAddr` are non-nil [1](#0-0) , then dispatches to `handleCreateRelayRequest`:

```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(target) {
    ...
    _, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
``` [2](#0-1) 

`h` is the already-authenticated `HostInfo` of the sender (its identity comes from a verified certificate at handshake time — see `hm.validatePeerCert` and `certVerifier` [3](#0-2) ). However, `from` (the `RelayFromAddr`/`RelayToAddr` claimed relay peer) is **not** cross-checked against `h`'s certificate networks (`h.GetCert().Certificate.Networks()`), nor against `h.vpnAddrs`. The code only verifies "am I the target," never "is `h` allowed to claim it is relaying for `from`."

`AddRelay` then unconditionally records `relayHostInfo.relayState` keyed by the attacker-chosen `from` address [4](#0-3) , and the local node marks this as an `Established` terminal relay association, replying with a `CreateRelayResponse` confirming it. Any authenticated peer `h` (a legitimate certificate holder for its own identity, but not for `from`) can therefore cause the target node to install relay/routing state that maps an arbitrary victim VPN address to `h`'s own tunnel.

This differs from a "malicious peer/valid cert holder" exclusion in that the actual vulnerability is not simply that a certified peer sent a control message (expected), but that the message's *claimed relay identity* field is trusted with no binding to the sender's own certificate-verified identity — directly analogous to `transferLPs` trusting the caller argument instead of verifying the caller is the approved party.

### Impact Explanation
An attacker holding any valid Nebula certificate for the mesh can register itself as the relay/terminal endpoint for an arbitrary victim vpn address (`from`) at any node it can reach directly. Traffic routed toward that victim address which transits through relay logic can be redirected/associated with the attacker's hostinfo instead of the legitimate victim, poisoning relay/hostmap state (`hm.Relays`, `relayForByAddr`) for that address. This falls under remote state poisoning of hostmap/relay address trust, which is explicitly in scope.

### Likelihood Explanation
Likelihood is high for any deployment that enables relaying (`am_relay`/`use_relays`), since the only precondition is possessing a valid certificate in the mesh (the normal, expected attacker capability for this class of finding) and sending a crafted `header.Control` / `NebulaControl_CreateRelayRequest` message with an arbitrary `RelayFromAddr`. No additional secrets, timing races, or privilege escalation steps are required.

### Recommendation
In `handleCreateRelayRequest` (and the corresponding response-handling path), validate that the claimed `from` (RelayFromAddr) is actually authorized: e.g., relay establishment should only be accepted from `h` on behalf of an identity previously introduced via a valid handshake-relay flow tied to `h`'s certificate networks, or require that `from` be present in `h.GetCert().Certificate.Networks()`/`UnsafeNetworks()` when `h` is asserting it can act on behalf of that address as a forwarding relay. At minimum, reject `CreateRelayRequest`s where the sending hostinfo `h` has no legitimate basis (existing pending handshake state, cert authorization) to claim `from`.

### Proof of Concept
1. Attacker `A` obtains a valid certificate in the mesh for identity `A` and establishes a normal handshake/tunnel with target node `T` (which has `am_relay`/relay support enabled).
2. `A` sends `T` a `header.Control` packet containing a `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to `V`'s VPN address (an arbitrary victim, not `A`) and `RelayToAddr` set to `T`'s own address, with an arbitrary `InitiatorRelayIndex`.
3. `T`'s `relayManager.HandleControlMsg` → `handleCreateRelayRequest` sees `target == T` (itself), finds no existing relay for `from=V` on `A`'s hostinfo, and calls `AddRelay(rm.l, h=A's hostinfo, f.hostMap, from=V, ..., TerminalType, Established)`, installing relay state mapping `V` to `A`'s tunnel, and replies with `CreateRelayResponse` confirming success — without ever verifying `A`'s certificate covers `V`.
4. `T` now believes it can relay traffic addressed to `V` through `A`, which `A` did not legitimately own or represent. [2](#0-1) [5](#0-4) [4](#0-3)

	hm.Lock()
	defer hm.Unlock()
	for range 32 {
		index, err := generateIndex(l)
		if err != nil {
			return 0, err
		}

		_, inRelays := hm.Relays[index]
		if !inRelays {
			// Avoid standing up a relay that can't be used since only the primary hostinfo
			// will be pointed to by the relay logic
			//TODO: if there was an existing primary and it had relay state, should we merge?
			if !hm.unlockedMakePrimary(relayHostInfo) {
				// The tunnel was torn down after the caller grabbed relayHostInfo. A relay standing
				// on an unlinked hostinfo would never carry traffic, and its Relays entry could
				// never be reclaimed since the delete-time cleanup has already run.
				return 0, errors.New("relay hostinfo is no longer in the hostmap")
			}

			hm.Relays[index] = relayHostInfo
			newRelay := Relay{
				Type:       relayType,
				State:      state,
				LocalIndex: index,
				PeerAddr:   vpnIp,
			}

			if remoteIdx != nil {
				newRelay.RemoteIndex = *remoteIdx
			}
			relayHostInfo.relayState.InsertRelay(vpnIp, index, &newRelay)

			return index, nil
		}
	}

	return 0, errors.New("failed to generate unique localIndexId")
}

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}
