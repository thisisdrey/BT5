### Title
Legacy (non-hardened) Bancor exchange calculation in `ExchangeCapsule.transaction()` skips the post-trade non-negative balance check, allowing pool balances to go negative - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` computes the new pool balances (`newFirstTokenBalance`/`newSecondTokenBalance`) after a bancor-style trade, but only validates that these values are non-negative when `hardenedCalc == true`. When `hardenedCalc == false` (the legacy code path, selected when `allowHarden()` is not enabled), the exact same arithmetic is performed but the safety check is skipped entirely, mirroring the reported Index Protocol bug where a bid/quote quantity is accepted without verifying it does not exceed the actual available balance of the pool/send token.

### Finding Description
`ExchangeCapsule.transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath, boolean hardenedCalc)` computes `buyTokenQuant` via either the legacy `ExchangeProcessor` (double-based bancor formula) or the `SafeExchangeProcessor` (BigDecimal-based), then computes `newFirstTokenBalance`/`newSecondTokenBalance` for the pool: [1](#0-0) 

Critically, the guard that prevents a resulting negative pool balance is gated behind `hardenedCalc`:
```java
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
``` [2](#0-1) 

This is called directly from `ExchangeTransactionActuator.execute()`/`doValidate()` with `hardenedCalc` supplied by `allowHarden()`: [3](#0-2) [4](#0-3) 

When `allowHarden()` is false (i.e., the hardening feature has not been activated by the committee, which is the historical/default behavior of this legacy exchange market), the legacy `ExchangeProcessor` path is used and no bound check on the resulting pool balances is performed, exactly the same class of bug described in the external report: no check that the requested trade amount does not exceed what the pool can actually deliver, before mutating balances. Because the legacy `ExchangeProcessor.exchange()` uses floating point `double` bancor math (via `Maths.pow`), extreme or edge-case inputs (very large `sellTokenQuant` relative to pool balance, or repeated trades draining a thin pool) can drive `exchangeFromSupply()`'s output to exceed the actual `buyTokenBalance`, producing a negative `newSecondTokenBalance`/`newFirstTokenBalance` that is accepted and persisted without any validation: [5](#0-4) 

The negative balance is then written back into the exchange capsule and persisted by the actuator: [6](#0-5) 

The account's own asset/TRX transfer legs are separately checked against the trader's balance (`assetBalanceEnoughV2`/`getBalance()` checks in `doValidate()`), but that only protects the trader's own funds - it does nothing to ensure the *exchange pool* itself has sufficient balance to pay out `anotherTokenQuant`, which is precisely the missing check class from the reported issue (`_quoteQuantityLimit` vs `preBidTokenSentBalance`).

### Impact Explanation
If a caller can drive the legacy (non-hardened) bancor calculation to compute a `buyTokenQuant` larger than the exchange pool's actual balance of that token, `ExchangeCapsule.setBalance()` will store a negative balance for one side of the pool. This corrupts the AMM-like Exchange/Bancor accounting: the "unbacked" negative balance means future trades against the pool compute against an incorrect (negative) reserve, and the trader who triggered the exploit receives real, correctly-added TRX/TRC10 asset amount from `addAssetAmountV2`/`setBalance` on their own account, i.e., an unbacked value is credited to the trader while the pool's ledger becomes inconsistent - a fund-accounting integrity break reachable via a single ordinary `ExchangeTransactionContract` transaction from any account holding an exchange-eligible asset.

### Likelihood Explanation
Exploitation requires only submitting an ordinary `ExchangeTransactionContract` (a standard, unprivileged transaction type available to any account with a balance) against an existing TRX/TRC10 Bancor exchange pair, provided `allowHarden()` is not active. `doValidate()` only bounds-checks the trader's own balance and confirms `anotherTokenQuant >= tokenExpected` - it performs no upper bound on `anotherTokenQuant` relative to the counter-side pool reserve. Achieving an actual negative output specifically requires driving the floating point bancor formula (`exchangeToSupply`/`exchangeFromSupply` in `ExchangeProcessor`) into a regime where the computed payout exceeds the pool reserve, which is more plausible for thin/low-liquidity pools or via crafted sequences of trades exploiting `double` precision behavior; this needs concrete confirmation via testing/fuzzing of `ExchangeProcessor.exchange()` against small reserves, which was not verified here.

### Recommendation
Move the non-negative balance check for `newFirstTokenBalance`/`newSecondTokenBalance` outside of the `hardenedCalc` conditional so it always applies, e.g.:
```java
if (newFirstTokenBalance < 0 || newSecondTokenBalance < 0) {
  throw new ContractValidateException("Exchange balance must be >=0 after transaction");
}
```
Additionally, add an explicit upper-bound validation in `ExchangeTransactionActuator.doValidate()` that `anotherTokenQuant` (the amount to be paid out from the pool) does not exceed the current `firstTokenBalance`/`secondTokenBalance` of the exchange, independent of `hardenedCalc`/`allowHarden()` feature flags, so validation is consistent regardless of the calculation mode selected.

### Proof of Concept
1. Create (or use) a `ExchangeTransactionContract`-eligible exchange pair with a small reserve on one side (e.g., first token balance very small relative to second token balance), while `allowHarden()` remains disabled (default/legacy mode).
2. Submit an `ExchangeTransactionContract` selling the large-reserve token in a quantity chosen so that the legacy `ExchangeProcessor.exchange()` bancor formula computes a `buyTokenQuant` (paid from the small-reserve side) that is greater than that side's current balance.
3. Because `hardenedCalc` is `false`, the guard at `ExchangeCapsule.java` lines 160-162 is skipped; `exchangeCapsule.transaction()` returns the oversized `buyTokenQuant`, `ExchangeTransactionActuator.execute()` credits the trader with `addAssetAmountV2`/`setBalance` for that amount, and persists the exchange capsule with a negative balance on the depleted side via `Commons.putExchangeCapsule(...)`.
4. Observe the exchange's stored `firstTokenBalance`/`secondTokenBalance` is negative, and the trader received tokens/TRX not actually backed by the pool's remaining reserve — matching the "bid/trade beyond available balance leads to loss of backing funds" bug class from the external report.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
