## Analog Found

### Title
Exchange Inject/Withdraw always floor-round the matching token quantity, giving the depositor a systematic discount while giving the withdrawer a systematic haircut - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
The reported bug is a class of issue where the *same* rounding direction is applied to two economically opposite scenarios, so the rounding helps the protocol in one case and unintentionally helps the counter-party in the other. `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the proportional "matching" token quantity (`anotherTokenQuant`) with the exact same floor-rounding formula, even though the direction of the token flow (into vs out of the pool) is opposite, producing the same asymmetric-safety-margin problem described in the report.

### Finding Description
When a user injects liquidity via `ExchangeInjectActuator`, `anotherTokenQuant` is the amount of the *other* token that is **deducted from the user** to keep the pool ratio constant: [1](#0-0) 
It is computed with `floorDiv(multiplyExact(secondTokenBalance, tokenQuant), firstTokenBalance)` (an integer floor division), and the same floor semantics are echoed in `doValidate()` via plain `BigInteger.divide()`: [2](#0-1) 

When a user withdraws liquidity via `ExchangeWithdrawActuator`, `anotherTokenQuant` is the amount of the *other* token that is **credited to the user**, computed with the exact same floor-rounding formula (`BigInteger.divide()` / `BigDecimal.divideToIntegralValue()`, both truncate toward zero for positive operands): [3](#0-2) [4](#0-3) 

Because `anotherTokenQuant` sits on **opposite sides of the ledger** in these two operations (a cost to the caller when injecting, a payout to the caller when withdrawing), using the same rounding-down direction has opposite safety implications, exactly mirroring the report's CALL/PUT issue:
- **Inject**: rounding down under-charges the depositor for the matching token, letting them add liquidity for less than the exact proportional amount — this dilutes/skews the pool's `firstTokenBalance`/`secondTokenBalance` ratio in the depositor's favor, analogous to the PUT case where rounding erodes the intended safety buffer.
- **Withdraw**: rounding down under-pays the withdrawer — analogous to the CALL case where rounding favors the protocol.

Both `ExchangeInjectContract` and `ExchangeWithdrawContract` are ordinary broadcastable transactions restricted only to the exchange's creator account (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), i.e., any account that created an on-chain exchange pair can reach this path with a signed transaction — no privileged role is required beyond having created the exchange, which itself is an action any account can perform.

### Impact Explanation
Because the pool's reserve ratio (`firstTokenBalance`/`secondTokenBalance`) directly drives the bonding-curve pricing used by `ExchangeCapsule.transaction()` (via `ExchangeProcessor`/`SafeExchangeProcessor`), repeatedly performing Inject operations lets the creator skew the ratio in their favor at sub-unit granularity each time, while Withdraw always shaves off value in the protocol's favor. The asymmetric rounding direction relative to the direction of value flow means the intended proportional invariant of the pool is not preserved consistently, which can be exploited via repeated small Inject/Withdraw cycles to extract or distort reserve value over time — a "reduced safety margin" class issue consistent with Medium severity in the source report.

### Likelihood Explanation
Any account that has created an Exchange pair can call `ExchangeInjectContract`/`ExchangeWithdrawContract` directly and repeatedly; the discrepancy is deterministic (not dependent on race conditions) and triggers on ordinary integer division truncation whenever `secondTokenBalance * tokenQuant` (or `firstTokenBalance * tokenQuant`) is not exactly divisible by the balance — a very common case, making the condition trivially and repeatedly reachable.

### Recommendation
Round the matching-token quantity in the direction that always protects the pool, mirroring the report's recommendation of asymmetric rounding for opposite risk directions:
- For `ExchangeInjectActuator` (token flowing **into** the pool from the user), round `anotherTokenQuant` **up** (ceiling), so the depositor never contributes less than the exact proportional share.
- For `ExchangeWithdrawActuator` (token flowing **out** of the pool to the user), continue rounding **down** (floor), so the pool never pays out more than the exact proportional share.
Apply the same corrected rounding consistently in both `execute()` and the `doValidate()` precision checks so the enforced/validated amounts match what's actually applied to balances.

### Proof of Concept
1. Attacker creates an Exchange pair (`firstToken`, `secondToken`) with initial balances `firstTokenBalance = 3`, `secondTokenBalance = 10` (ratio 10/3 ≈ 3.333).
2. Attacker calls `ExchangeInjectContract` with `tokenID = firstToken`, `tokenQuant = 1`. The exact proportional `secondToken` contribution should be `10*1/3 = 3.33...`; `floorDiv` truncates to `3`, so the attacker only pays `3` `secondToken` instead of the "fair" `3.33...`, silently diluting the pool ratio in their favor (0.33 secondToken of value effectively not collected relative to the pre-injection price).
3. Repeating step 2 many times (or scaling `tokenQuant`) accumulates the discount, provably showing the pool's reserve ratio — and thus future swap pricing via `ExchangeCapsule.transaction()` — drifts from the mathematically fair value with every injection, purely due to rounding direction, exactly the "reduced safety margin" effect described in the source report but manifesting as reserve-ratio drift instead of an options strike price.
