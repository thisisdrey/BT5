### Title
Tokens sent directly to a vault contract (outside `deposit`) are permanently unrecoverable - ([File: mainnet/contracts/vault/v0-vault-stx.clar], and identical pattern in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
Each Zest vault contract tracks its underlying holdings in an internal accounting variable `assets` [1](#0-0)  rather than by reading the token contract's real balance. `deposit` only increments `assets` by the exact amount transferred in via `receive-underlying`, and `redeem`/borrow flows only ever move funds up to the tracked `assets` value [2](#0-1) [3](#0-2) . Any underlying/zToken sent to the vault contract's address by a normal user through a bare `transfer` call (mistaken address, wrong amount, wrong flow) increases the real token balance held by the contract but never updates `assets`, so it is not reflected in `total-assets`/`convert-to-shares`, cannot be withdrawn via `redeem`, and there is no sweep/rescue/skim function anywhere in the codebase to recover it.

### Finding Description
The vault's helper `ubalance` reads the contract's actual on-chain token balance [4](#0-3) , but this real balance is never reconciled with the `assets` data-var that drives all share-price and withdrawal logic (`total-assets`, `total-assets-preview`, `convert-to-shares-preview`, `convert-to-assets-preview`) [5](#0-4) . `deposit` explicitly sets `assets` to `(+ current-assets amount)` for only the amount passed as the transfer argument [6](#0-5) ; a stray/mistaken plain `transfer` call made by any ordinary principal directly to the vault's `current-contract` address (calling the underlying token's `transfer` function, not the vault's `deposit`) bypasses this bookkeeping entirely. Because `redeem` gates the payout by `current-assets`/`inkind` derived strictly from the `assets` var (not from `ubalance`) [7](#0-6) , the excess tokens sitting in the contract's real balance are permanently inaccessible to anyone — the depositor cannot reclaim them, and no other user's `redeem` call can reach them either since the accounting cap never rises to include them. There is no `sweep`, `rescue`, `skim`, or `donate`-style function in the repository that would let the DAO or the mistaken sender retrieve these tokens.

This is the direct analog of the reported nounsDAO `Stream.cancel()` issue: after `remainingBalance = 0` is set, `token_` sent to the stream contract by mistake becomes permanently stuck with no recovery path. In Zest, the analogous "zeroed accounting vs. real balance mismatch" occurs continuously via the `assets` var vs. real token balance gap in every vault, and there is likewise no recovery mechanism.

### Impact Explanation
Any principal, sBTC/STX/USDC/USDH/stSTX/stSTXbtc holder, or an ordinary user's own deployed contract that sends tokens directly to a Zest vault contract address by mistake (e.g., miscalling the underlying token's `transfer` instead of the vault's `deposit`, or an off-by-one amount error compared to what was approved/intended) permanently loses those funds. This falls under permanent freezing of funds, since the tokens are locked in the vault contract forever with no code path — public or admin — to move them back out.

### Likelihood Explanation
Likelihood is driven purely by ordinary user error (wrong function target, UI/integration mistake, or an integrating contract accidentally transferring to the vault address instead of calling `deposit`), which is a common real-world occurrence for ERC20/SIP-010-style vault contracts and requires no privileged access or DAO involvement to trigger.

### Recommendation
Add a permissioned (DAO-gated) sweep function that transfers out any surplus underlying balance (`ubalance` minus tracked `assets`) to a designated recipient, mirroring the fix recommended for the original nounsDAO `Stream` finding — allow rescue of tokens that were sent to the contract outside the normal accounted flow.

### Proof of Concept
1. User intends to deposit 100 STX into `v0-vault-stx` via `deposit`, but instead mistakenly calls `.wstx transfer` directly with the vault contract as recipient.
2. The vault's real token balance (`ubalance`) increases by 100, but `assets` (the accounting var used by `total-assets`, `convert-to-shares-preview`, `redeem`) is unchanged [1](#0-0) .
3. No shares (`zft`) were minted to represent these tokens, since `ft-mint?` only occurs inside `deposit` [8](#0-7) .
4. The user calls `redeem` — it is capped by `current-assets` (unchanged accounting var) and requires burning `zft` shares the user does not have for the mistaken amount, so the 100 STX cannot be withdrawn [3](#0-2) .
5. No sweep/rescue function exists in the contract or elsewhere in the repo to move the stranded 100 STX out, so it is permanently locked.
