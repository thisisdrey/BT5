### Title
Attachment hash-mismatch responses are not recorded as faulty and do not exclude the serving peer from future `sources` selection - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`BatchedRequestsResult::faulty_peers` (download.rs:963) is only populated when a peer's HTTP response has status code 404, at the point where `AttachmentRequest`/`AttachmentsInventoryRequest` polling completes (download.rs:900-910). Any 200-status response — including one whose body content fails the Hash160 content-hash check against the requested attachment's `content_hash` — is unconditionally inserted into `state.succeeded` (download.rs:909), never into `faulty_peers`. Separately, `get_prioritized_attachments_requests` (download.rs:404-478) builds the `sources` map for a new `AttachmentRequest` purely from each peer's presence in the relevant inventory page (download.rs:434-458) and never consults `faulty_peers` or any hash-mismatch history to exclude a peer.

### Finding Description
The claimed equality — "trusted-peer-count == peers-that-have-not-served-invalid-content" — does not hold. Tracing the path:

1. A remote peer answers a `GET /v2/attachments/<hash>` request (`AttachmentRequest::make_request_type`, download.rs:1110-1118) with an HTTP 200 and attacker-controlled body that does not match the expected `content_hash`.
2. In the polling state machine, only `status_code == 404` causes `state.faulty_peers.insert(event_id, peer_url)` (download.rs:901-903); any other status (including 200 with a bad body) falls through to `state.succeeded.insert(request, Some(response))` (download.rs:909) with no content validation at this stage.
3. When `get_prioritized_attachments_requests` later rebuilds `sources` for the same `content_hash`/attachment (download.rs:430-458), it iterates `peers_responses` from `self.inventories` and inserts every peer whose inventory page shows the attachment (`has_attachment`) into `sources`, using `self.peers.get(peer_url)` for the `ReliabilityReport` (download.rs:454-458). There is no check against `faulty_peers`, and no state field records "this peer previously served hash-mismatched content."
4. `AttachmentRequest::get_most_reliable_source` (download.rs:1074-1079) then selects the peer with the highest `ReliabilityReport::score()` from `sources` — since a hash-mismatching peer's report is never penalized for that specific failure mode (only inventory/DNS/connection-level accounting is visible in the traced code), the same malicious peer can be re-selected on a subsequent retry.

Root cause: the fault-tracking mechanism (`faulty_peers`) is scoped only to transport/HTTP-status-level failures (404), while application-level content integrity failures (hash mismatch) are handled, if at all, downstream of the succeeded/faulty split and do not feed back into peer exclusion for `sources` selection.

### Impact Explanation
A single non-privileged peer that a node has selected as an outbound Atlas sync peer can repeatedly serve attachment content that fails the Hash160 integrity check without ever being excluded from `sources` or demoted via `faulty_peers`. This matches the "attachment/BNS mismatch" High-impact category: the node will keep re-requesting from, and potentially re-processing responses from, a peer that has already proven it serves non-canonical/invalid attachment data, wasting request/verification cycles and potentially delaying resolution of legitimate BNS attachment data indefinitely if that peer is the top-ranked/only source in `sources`.

### Likelihood Explanation
Preconditions: the attacker must be an outbound sync peer the node already talks to for Atlas attachments (achievable by any P2P peer, no privileged role or secret required) and must be listed in the relevant attachment's inventory page so it appears as a candidate source. Attacker cost is minimal — running a node/peer and returning any HTTP 200 body with a valid-looking `GetAttachmentsInvResponse`/attachment endpoint. The behavior is repeatable indefinitely since nothing in the traced code path (download.rs:404-478, 900-910) removes or downgrades a peer for content-hash failures specifically.

### Recommendation
When processing a downloaded attachment whose computed hash does not match `AttachmentRequest.content_hash`, explicitly insert the serving peer's URL/event id into `faulty_peers` (or an equivalent persistent penalty on that peer's `ReliabilityReport`), and have `get_prioritized_attachments_requests` filter `sources` to exclude peers present in `faulty_peers` / with a hash-mismatch penalty, mirroring the existing 404 handling.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/download.rs` or `tests.rs`):
1. Construct an `AttachmentsBatchStateContext` with a single peer `P` present in `self.peers` and in an inventory response indicating it has the target attachment.
2. Simulate a completed `BatchedRequestsResult<AttachmentRequest>` where `P`'s response for `content_hash` H returns HTTP 200 with a body whose hash != H; verify `state.faulty_peers` is empty and `state.succeeded` contains the entry for `P` (asserting the 404-only gate at download.rs:901-903).
3. Call `get_prioritized_attachments_requests()` again for the same missing attachment and assert `P`'s URL is still present in the resulting `AttachmentRequest.sources`, and that `get_most_reliable_source()` can still return `P`, demonstrating the peer was never excluded despite having served invalid content.
