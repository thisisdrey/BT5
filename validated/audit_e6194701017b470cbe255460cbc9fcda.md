### Title
Unbounded array allocation before length validation in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract extracts a caller-controlled dynamic array length from call data and immediately allocates a Java array of that size *before* validating it against the intended maximum, when the `allowTvmSelfdestructRestriction` hard-fork flag is not active. This lets any account calling this precompile force the node to allocate an outsized array, causing memory exhaustion — the same bug class as CVE-2018-17437 (crafted length field consumed for allocation before bounds-checking, causing memory-consumption DoS).

### Finding Description
`ValidateMultiSign.execute()` parses the raw call data into `DataWord[]` and then extracts the signature array: [1](#0-0) 

When `VMConfig.allowTvmSelfdestructRestriction()` is `false` (the legacy/pre-activation code path, still reachable on any network/branch where this feature flag has not yet been turned on), the size-bound check on `sigArraySize` (`if (sigArraySize > MAX_SIZE) return ...`) is skipped entirely, and `extractBytesArray` is invoked directly on attacker-supplied offsets: [2](#0-1) 

Inside `extractBytesArray`, `len` is read straight from the caller's ABI-encoded data via `words[offset].intValueSafe()` and used to allocate `new byte[len][]` with no upper bound check:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
Only *after* this allocation does the caller check `signatures.length == 0 || signatures.length > MAX_SIZE` and reject — but by then the (potentially huge) array has already been allocated: [3](#0-2) 

`DataWord.intValueSafe()` converts an arbitrary 256-bit word supplied in the call data into a safe `int` value (up to `Integer.MAX_VALUE`), so a crafted length word in the ABI payload can drive `len` close to `Integer.MAX_VALUE`, forcing allocation of an array with billions of reference slots.

### Impact Explanation
Any account can reach this precompile from a `TriggerSmartContract` transaction via a `CALL`/`STATICCALL` to the fixed `ValidateMultiSign` precompile address, or from any deployed contract that calls it. A single crafted transaction can force the executing full node to attempt an allocation on the order of gigabytes, throwing `OutOfMemoryError` and destabilizing/crashing the node process or degrading availability for all transactions being processed by that node — a concrete denial-of-service against the chain's transaction-processing path, matching the "node crash or halt" acceptance criterion.

### Likelihood Explanation
The vulnerable branch is taken whenever `VMConfig.allowTvmSelfdestructRestriction()` is false, i.e., before/without that specific hard-fork proposal being active — a normal, low-privilege configuration state, not a "malicious SR/witness" scenario. Triggering it requires only crafting the ABI-encoded array-length word in the call data of a public-facing precompile call, something any unprivileged transaction sender or contract deployer can do without any special permission.

### Recommendation
Move the `sigArraySize > MAX_SIZE` bound check so it runs unconditionally, before `extractBytesArray`/`extractSigArray` allocate any array — i.e., validate `len` against `MAX_SIZE` inside `extractBytesArray` (and `extractBytes32Array`) themselves rather than only in the caller and only under the feature flag. Reject with `Pair.of(true, DATA_FALSE)` (or equivalent) if the declared length exceeds `MAX_SIZE` or is negative/inconsistent with remaining `words` length, regardless of `allowTvmSelfdestructRestriction()`.

### Proof of Concept
1. Craft ABI-encoded call data for `validateMultiSign(address,bytes32,bytes32,bytes[])` where the dynamic array length word at the byte-array-offset location is set to a large value (e.g. `0x7FFFFFFF`).
2. Submit a `TriggerSmartContract` transaction (or deploy a trivial contract that forwards the call) invoking the `ValidateMultiSign` precompile with this payload on a node/network where `allowTvmSelfdestructRestriction` is not yet activated.
3. `ValidateMultiSign.execute()` takes the `else` branch and calls `extractBytesArray(words, offset, rawData)`, which executes `new byte[0x7FFFFFFF][]`, forcing a massive allocation attempt and triggering `OutOfMemoryError` in the node's TVM execution thread before any length-bound rejection occurs.
