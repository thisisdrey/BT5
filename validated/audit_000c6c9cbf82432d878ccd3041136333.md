## Analysis

The OpenClaw bug class is: a write-scoped entry point internally reused the exact same mutation logic as an admin-only entry point, and the scope check was only enforced at the outer method — not on the shared mutation path itself. The closest reachable analog in java-tron is in the account permission (multi-sig) subsystem, where an `Active`-tier permission key that is merely granted the ability to *sign* an `AccountPermissionUpdateContract` transaction can use that same transaction to unconditionally overwrite the account's `Owner` permission, effectively performing an admin-level mutation that the signer's tier was never meant to reach unchecked.

### Title
Active-permission signer can overwrite Owner permission via `AccountPermissionUpdateActuator`, enabling full account takeover - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateContract` transactions are authorized the same way as any other transaction: the signer's permission (`Owner` or an `Active` permission with the matching operation bit set) is checked with `checkPermission`/`checkWeight`, and if the threshold is met the transaction is accepted. The actuator's `execute()` then unconditionally rewrites the account's `Owner`, `Witness`, and all `Active` permissions with whatever the transaction contains — with no check that the signer's own tier is `Owner`.

### Finding Description
Signature/permission verification for any transaction (including `AccountPermissionUpdateContract`) is done generically in `TransactionCapsule.checkPermission`, which only verifies that, for a non-zero `permissionId`, the permission is of type `Active` and its 32-byte `operations` bitmap has the bit set for the contract type being executed: [1](#0-0) 

This same generic path is reused for `AccountPermissionUpdateContract` exactly as for any other write-style transaction (e.g. transfers). `AccountPermissionUpdateActuator.validate()` checks the internal consistency of the new permission structure (key counts, thresholds, operation bit validity) but never checks which permission tier the *signer* used to authorize the update: [2](#0-1) 

`execute()` then unconditionally replaces the Owner permission, Witness permission, and all Active permissions with the contents of the contract, regardless of whether the transaction was authorized by the Owner permission or by a lower-tier Active permission that merely had the `AccountPermissionUpdateContract` bit enabled in its operations bitmap: [3](#0-2) 

The `operations` bitmap on an `Active` permission is a per-contract-type allow-list (see `checkActiveDefaultOperations`/`checkAvailableContractTypeCorrespondingToCode` tests enumerating which contract types can be granted to Active keys) — its purpose is to scope what an Active key can *do* (e.g. transfer, freeze, vote), not to grant it full administrative control over the account's permission hierarchy itself: [4](#0-3) 

Because the mutation path (`updatePermissions`) does not distinguish "who is allowed to redefine Owner" from "who is allowed to sign this contract type," any Active key holding the `AccountPermissionUpdateContract` bit — a scope an account owner might grant intending only limited co-management — can reach the same full-account-control mutation that should be Owner-exclusive, mirroring the OpenClaw pattern where a write-scoped caller reached admin-only reset logic through a shared internal path.

### Impact Explanation
An Active permission holder with the `AccountPermissionUpdateContract` operation bit set can submit a transaction that replaces the account's `Owner` permission entirely (e.g., setting themselves as the sole Owner key with threshold 1), permanently locking out the legitimate owner and any other co-signers, and gaining unrestricted future control over the account's funds and all other permission tiers. This constitutes unauthorized account takeover and potential permanent freezing/theft of funds for the original owner.

### Likelihood Explanation
Exploitation requires that the account owner has previously granted an Active permission the `AccountPermissionUpdateContract` operation bit (this bit is excluded from default Active permissions, so it must be explicitly configured). This is a realistic configuration for multi-sig setups that intend to allow a co-signer or automated key to perform routine permission maintenance (e.g., rotating a compromised key) without granting full Owner rights — the actuator's lack of tier separation means that intended "limited" grant is equivalent to full Owner control.

### Recommendation
`AccountPermissionUpdateActuator.validate()`/`execute()` should require that any change to the `Owner` permission (or to the `Witness` permission) be authorized specifically by the current `Owner` permission (`permissionId == 0`), rather than accepting any `Active` permission whose operations bitmap merely includes the `AccountPermissionUpdateContract` type. Alternatively, restrict what an Active-permission-authorized `AccountPermissionUpdateContract` transaction is allowed to modify (e.g., disallow altering the Owner permission unless signed by Owner).

### Proof of Concept
1. Owner account `X` configures an `Active` permission (id=2, threshold=1) for co-signer key `K`, with the `operations` bitmap bit for `ContractType.AccountPermissionUpdateContract` set (a legitimate-looking grant intended for "permission maintenance").
2. Attacker controlling `K` crafts an `AccountPermissionUpdateContract` transaction for owner `X` with `permissionId = 2`, setting a brand-new `Owner` permission containing only `K`'s key with threshold 1, and setting `Active` permissions of the attacker's choosing.
3. The transaction passes `TransactionCapsule.checkPermission`/`checkWeight` (Active permission id=2 has the required bit and enough weight) and `AccountPermissionUpdateActuator.validate()` (internal consistency only).
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, overwriting `X`'s Owner permission with attacker-controlled key/threshold — `K` now solely and permanently controls account `X`, including its full balance, with no further need for the original Owner key.
