I have sufficient evidence to produce a finding analogous to the reported bug class: a predictable deployment address combined with a strict "no pre-existing balance/account" guard that any unprivileged actor can trigger to block deployment.

### Title
Any account can permanently block a pending `CreateSmartContract` deployment by front-running the predictable contract address with a funding transaction - ([File: actuator/src/main/java/org/tron/core/actuator/VMActuator.java])

### Summary
`VMActuator.create()` computes the new contract's address deterministically via `WalletUtil.generateContractAddress(trx)` and then rejects the deployment outright if any account already exists at that address, rather than only guarding against an already-deployed *contract*. Because the address is derivable from public transaction data (owner address + transaction hash) once a `CreateSmartContract` transaction is signed/broadcast, any third party who observes it in the mempool can race a plain TRX transfer to that address, permanently causing the legitimate deployment transaction to fail — the exact "predictable address + brittle balance/existence guard" bug class described in the external report.

### Finding Description
The contract address for a top-level deployment is computed as `sha3omit12(txRawDataHash || ownerAddress)`: [1](#0-0) 

`VMActuator.create()` then enforces:
```
byte[] contractAddress = WalletUtil.generateContractAddress(trx);
// insure the new contract address haven't exist
if (rootRepository.getAccount(contractAddress) != null) {
  throw new ContractValidateException(
      "Trying to create a contract with existing contract address: " ...);
}
``` [2](#0-1) 

This check fails on *any* pre-existing account at that address — not just an already-deployed contract. An account is created in the store the moment it receives any TRX or TRC10 transfer. Since `txRawDataHash` (the transaction ID) is fully determined once the deployer signs the `CreateSmartContract` transaction, and the owner address is public, the resulting `contractAddress` is knowable by anyone who sees the pending signed transaction (e.g., in the P2P mempool prior to block inclusion, or via any broadcast API). An attacker can then submit a trivial `TransferContract` sending 1 sun to that address and get it confirmed first. Because the transaction ID (and thus `contractAddress`) is fixed by the deployer's own signed raw data, the deployer's original transaction can never succeed once broadcast — the attack is a persistent denial-of-service specific to that transaction, forcing the victim to discard it and resubmit a brand-new transaction (with a different `ref_block`/`expiration`/etc. to get a new hash).

This directly mirrors the reported bug class: a contract deployed to a deterministically predictable address, guarded by a strict balance/existence check that any unprivileged token holder can violate by pre-funding the address, causing deployment to revert.

By contrast, internal `CREATE`/`CREATE2` (via `Program.createContractImpl`) correctly tolerates a pre-funded, non-contract account and only rejects when the address is *already a contract*: [3](#0-2) 
showing the top-level path in `VMActuator.create()` is the outlier that uses the overly strict guard.

### Impact Explanation
Any unprivileged transaction broadcaster can grief a targeted `CreateSmartContract` transaction from any other user, causing that specific deployment attempt to permanently fail with `ContractValidateException`. This is a denial-of-service against contract deployment reachable purely by an anonymous actor observing pending transactions and issuing a low-cost TRX/TRC10 transfer — no privileged role, no consensus compromise required. It does not cause fund loss or unbacked balances (the transfer just lands as a normal balance on that address, later inherited by the contract once eventually deployed under a different transaction hash), but it is a concrete node-observable griefing/DoS vector against a core actuator's validate/execute path.

### Likelihood Explanation
The `contractAddress` depends only on public data (`ownerAddress`, transaction raw-data hash) available to anyone who can see the signed pending transaction (e.g., via the network's transaction relay before block confirmation), and the counter-transaction (a plain TRX transfer) is cheap and trivially raceable. No special access or timing precision beyond ordinary transaction-relay racing is needed, making this readily exploitable by any network participant against a chosen victim's pending deployment.

### Recommendation
In `VMActuator.create()`, do not reject solely because `rootRepository.getAccount(contractAddress) != null`. Instead, mirror the internal-CREATE semantics in `Program.createContractImpl`: allow deployment onto an address that merely holds a balance/plain account, and only reject when that address already hosts a deployed smart contract (e.g., check `rootRepository.getContract(contractAddress) != null` / `isContractExist`), migrating any existing balance into the new contract account as `Program.createContractImpl` already does for the legacy path.

### Proof of Concept
1. Victim signs and broadcasts a `CreateSmartContract` transaction; its future contract address `A = sha3omit12(txId || ownerAddress)` is now computable by any observer via `WalletUtil.generateContractAddress`.
2. Attacker, monitoring the mempool, immediately broadcasts a `TransferContract` sending 1 sun to `A` with a higher/competing priority so it is included in an earlier or same block.
3. Once the transfer lands, `A` exists in `AccountStore`.
4. When the victim's `CreateSmartContract` transaction executes, `VMActuator.create()` hits
`rootRepository.getAccount(contractAddress) != null` at [4](#0-3)  and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`, permanently failing that specific deployment transaction.

  public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
```
