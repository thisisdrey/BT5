### Title
Rebase surplus on stSTX/stSTXbtc underlying is permanently unreachable because `assets` bookkeeping is never reconciled with `ubalance()` - ([File: mainnet/contracts/vault/v0-vault-ststx.clar], [File: mainnet/contracts/vault/v0-vault-ststxbtc.clar])

### Summary
`v0-vault-ststx.clar` and `v0-vault-ststxbtc.clar` track vault holdings solely through the book-keeping variable `assets`, which is only mutated by `deposit`, `redeem`, `system-borrow`/repay-style flows. The private helper `ubalance` queries the real, rebasing token balance held by the contract but is never used to true-up `assets`, `total-assets-preview`, or `convert-to-assets-preview`, so any upward rebase of the underlying stSTX/stSTXbtc token accrues to the contract's real balance but is invisible to all vault accounting and thus unclaimable through `redeem`.

### Finding Description
`redeem` computes the payout via `convert-to-assets-preview`, which is driven by `total-assets-preview`, itself derived purely from `(var-get assets)` plus internal interest accrual — never from `ubalance()`: [1](#0-0) [2](#0-1) [3](#0-2) 

The liquidity gate in `redeem` (`get-available-assets`) is also purely book-based, derived from `(var-get assets)` minus `(var-get total-borrowed)`, not from the real token balance: [4](#0-3) 

The `redeem` function itself: [5](#0-4) 

`deposit` only increments `assets` by the exact `amount` transferred in via `receive-underlying`, never by any observed real-balance delta: [6](#0-5) 

No function in either vault contract calls `ubalance()` to reconcile the book `assets` variable with the actual on-chain token balance held by the contract. I searched the full file for call sites of `ubalance` beyond its own definition and found no usage feeding into `assets`, `total-assets`, `total-assets-preview`, `convert-to-shares-preview`, `convert-to-assets-preview`, or `get-available-assets`. Consequently, once the underlying stSTX/stSTXbtc token rebases upward (a normal external property of that token, granted as precondition), the vault's real balance (`ubalance()`) permanently exceeds `(var-get assets)`, and every share continues to redeem only at the book-based ratio. The delta `(- (ubalance) (var-get assets))` is structurally unreachable by any supplier through the normal `deposit`/`redeem` lifecycle, and no admin/DAO function was found that sweeps or syncs this surplus into `assets` either (no `sync`, `skim`, `sweep`, or `donate` function exists in these contracts).

This is not a caller-side exploit that lets an attacker steal the surplus — the attacker's own `inkind` payout on `redeem` is capped at the book ratio just like everyone else's — but it does permanently strand the rebase yield for all suppliers, since the accounting invariant "book assets tracks real assets" is never enforced or reconciled.

### Impact Explanation
This matches the in-scope **High** impact category: "permanent freezing of unclaimed yield." The rebase surplus accruing on the real stSTX/stSTXbtc balance held by the vault is yield that legitimately belongs to LP suppliers (analogous to protocol/user yield), but it can never be distributed through `redeem`, `deposit`, or `accrue` because none of those functions read `ubalance()` to true up `(var-get assets)`. The yield is not stolen by a single attacker; it becomes permanently inaccessible to the whole supplier base.

### Likelihood Explanation
This requires no attacker skill or capital beyond a routine deposit — it manifests as a natural side effect of holding a rebasing/appreciating underlying token over any window during which the vault holds a nonzero stSTX/stSTXbtc balance, i.e., it is guaranteed to occur under normal operation (not merely triggerable by an attacker). It is fully reproducible and repeats every time the underlying token rebases.

### Recommendation
Add an explicit reconciliation step (e.g., invoked inside `accrue`, `deposit`, or `redeem`) that reads `ubalance()` and, if it exceeds `(var-get assets)` plus any assets currently lent out (`total-borrowed` accounting), credits the surplus into `assets` (optionally minting treasury/LP-fee shares as is already done for interest in `accrue`) so that the rebase yield becomes part of `total-assets-preview` and is distributable to shareholders through the standard `convert-to-assets-preview` ratio.

### Proof of Concept
Clarinet/vitest simnet plan (local fork):
1. Deploy `v0-vault-ststx.clar` with a mock `ststx-token` contract implementing `ft-mint?`/`get-balance`/`transfer`.
2. Attacker calls `deposit(amount, 0, attacker)` — assert `(var-get assets)` == amount, `ubalance()` == amount.
3. Simulate an external rebase: call `ft-mint?` on the mock stSTX token directly to the vault's `current-contract` address (or otherwise increase its raw balance) to simulate the vault's real balance growing without any vault-mediated deposit — assert `ubalance()` > `(var-get assets)`.
4. Call `redeem(all-shares, 0, attacker)` — assert the returned `inkind` equals `convert-to-assets-preview(all-shares)`, computed strictly from `(var-get assets)`, and is strictly less than `ubalance()` prior to the call.
5. After redeem, assert `(var-get assets)` == 0 (or minimal residual) while `ubalance()` still shows a stranded positive residual balance in the vault contract equal to the rebase surplus.
6. Assert no available public/DAO function call sequence reduces this residual `ubalance()` surplus to zero via normal vault operations, confirming the surplus is permanently frozen.
