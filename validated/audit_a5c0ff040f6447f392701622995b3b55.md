### Title
Unguarded `assert totalEnergyWeight > 0` in `RepositoryImpl.calculateGlobalEnergyLimit` allows division-by-zero to crash TVM contract-call/creation processing - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's global energy limit by dividing by `totalEnergyWeight`, guarding the zero-denominator case only with a Java `assert`. Since Java assertions are disabled by default in production JVMs (no `-ea` flag), this guard is a no-op at runtime, and the following unconditional `BigInteger.divide(BigInteger.valueOf(totalEnergyWeight))` will throw `ArithmeticException: / by zero` if `totalEnergyWeight` is ever `0` while an account still has energy frozen. This mirrors the OUSD bug class: a critical rate/denominator value used pervasively is not validated to be non-zero, and reachable inputs can drive it to zero, breaking an invariant relied upon by ordinary balance/limit calculations.

### Finding Description
`calculateGlobalEnergyLimit` in `RepositoryImpl` is:
```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
``` [1](#0-0) 

Unlike this path, the equivalent guards in `EnergyProcessor` and `BandwidthProcessor` explicitly check `totalEnergyWeight <= 0` / `totalNetWeight == 0` and `return 0` before ever dividing: [2](#0-1) [3](#0-2) 

`RepositoryImpl.calculateGlobalEnergyLimit` has no such explicit check — only the disabled `assert`. This method is reached from `VMActuator.getAccountEnergyLimitWithFloatRatio`, which is invoked whenever `getEnergyLimitHardFork()` is not active and an account calling or creating a contract has `totalBalanceForEnergyFreeze != 0`:
```java
long totalEnergyFromFreeze = rootRepository.calculateGlobalEnergyLimit(account);
``` [4](#0-3) 

This is called both from `create()` (contract creation, wrapped in a broad `try/catch(Exception e)` that re-throws as `ContractValidateException`) and from `call()` (contract invocation via `getTotalEnergyLimit` → `getTotalEnergyLimitWithFloatRatio`), where I could not confirm an enclosing try/catch around the `call()` energy-limit computation in the code inspected — this path appears unguarded at the call site level, meaning an `ArithmeticException` there would propagate up through `VMActuator.validate()`/`execute()` into transaction processing rather than being converted into a validation failure. [5](#0-4) 

The hardened `BigInteger` division path is gated by `hardenResourceCalculation()` (`VMConfig.allowHardenResourceCalculation()`), a chain parameter; test files confirm this flag is exercised and that overflow/zero-denominator scenarios throw `ArithmeticException` under hardening: [6](#0-5) 

### Impact Explanation
If `totalEnergyWeight` reaches `0` (e.g., transiently during accounting of unfreeze/freeze operations, or via edge-case sequences of freeze/unfreeze/delegate operations that zero out the global weight while an individual account still reports nonzero frozen-for-energy balance) and hardened resource calculation is active, any ordinary user's `TriggerSmartContract` or `CreateSmartContract` transaction that reaches `getAccountEnergyLimitWithFloatRatio`/`getTotalEnergyLimitWithFloatRatio` will throw an uncaught `ArithmeticException`. Because this computation happens during ordinary transaction/energy-limit determination (not exception-safe validation), this can disrupt processing of TVM transactions network-wide once `totalEnergyWeight` hits zero, denying the ability to execute or create smart contracts — a denial-of-service on a core, unprivileged, transaction-broadcaster-reachable code path.

### Likelihood Explanation
Reaching `totalEnergyWeight == 0` requires a specific state of the global energy-weight accounting (all energy freezes fully withdrawn network-wide) combined with hardened resource calculation being enabled and at least one account retaining a nonzero `getAllFrozenBalanceForEnergy()` (a state achievable through the freeze/unfreeze/delegate lifecycle, which is fully reachable by unprivileged accounts). This is a narrower trigger condition than the OUSD case (which required only a single privileged call), so likelihood is lower, but it is not privileged: any user's freeze/unfreeze sequence can influence `totalEnergyWeight`, and any user's subsequent contract call/creation can trigger the division. I was not able to fully verify from the available files whether an enclosing exception handler exists specifically around the `call()` path's `getTotalEnergyLimit` invocation, so the exact blast radius (uncaught vs. caught-and-failed-transaction) is not fully confirmed.

### Recommendation
- Short term: Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check (`if (totalEnergyWeight <= 0) { return 0; }`), matching the pattern already used in `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` and `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2`.
- Long term: Audit all other `assert x > 0`-style guards preceding a division in resource/weight calculation code (`RepositoryImpl`, `VMActuator`, `EnergyProcessor`, `BandwidthProcessor`) and replace with explicit, non-optional validation, since `assert` is disabled by default in production and provides no real protection.

### Proof of Concept
1. Configure the chain with `allowHardenResourceCalculation = 1` (as tested in `CalculateGlobalLimitHardenTest`/`RepositoryImplHardenTest`).
2. Drive `dynamicPropertiesStore.getTotalEnergyWeight()` to `0` through a sequence of freeze/unfreeze operations (e.g., all frozen-for-energy balances network-wide are unfrozen so the global weight becomes exactly zero) while at least one account retains `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (e.g., due to a not-yet-reconciled delegated balance).
3. Submit a `TriggerSmartContract` or `CreateSmartContract` transaction from that account with `StorageUtils.getEnergyLimitHardFork() == false`, causing `VMActuator.getAccountEnergyLimitWithFloatRatio` → `RepositoryImpl.calculateGlobalEnergyLimit` to execute `BigInteger.valueOf(energyWeight).multiply(...).divide(BigInteger.valueOf(0))`, which throws `ArithmeticException: / by zero`, as directly reproduced by the existing hardened-path tests using a zero/near-zero weight denominator: [6](#0-5)

  private long getTotalEnergyLimitWithFloatRatio(AccountCapsule creator, AccountCapsule caller,
      TriggerSmartContract contract, long feeLimit, long callValue) {

    long callerEnergyLimit = getAccountEnergyLimitWithFloatRatio(caller, feeLimit, callValue);
    if (Arrays.equals(creator.getAddress().toByteArray(), caller.getAddress().toByteArray())) {
      return callerEnergyLimit;
    }

    // creatorEnergyFromFreeze
    long creatorEnergyLimit = rootRepository.getAccountLeftEnergyFromFreeze(creator);

    ContractCapsule contractCapsule = rootRepository
        .getContract(contract.getContractAddress().toByteArray());
    long consumeUserResourcePercent = contractCapsule.getConsumeUserResourcePercent(
        VMConfig.disableJavaLangMath());

    if (creatorEnergyLimit * consumeUserResourcePercent
        > (VMConstant.ONE_HUNDRED - consumeUserResourcePercent) * callerEnergyLimit) {
      return floorDiv(
          callerEnergyLimit * VMConstant.ONE_HUNDRED, consumeUserResourcePercent,
          VMConfig.disableJavaLangMath());
    } else {
      return addExact(callerEnergyLimit, creatorEnergyLimit,
          VMConfig.disableJavaLangMath());
    }
  }
