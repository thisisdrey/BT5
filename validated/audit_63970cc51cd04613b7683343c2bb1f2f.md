### Title
Attacker can permanently fill a victim's `depositTokensOfAccount` list via dust deposits, DoS-ing new collateral deposits and rescue-top-ups - (File: contracts/Pool.sol)

### Summary
`DepositToken.deposit(amount_, to_)` credits the minted deposit tokens to an arbitrary `to_` address (used by `VesperGateway.deposit` at `contracts/VesperGateway.sol:64` to deposit on behalf of users). Every mint to an account with a zero balance triggers `Pool.addToDepositTokensOfAccount(account)`, which enforces `MAX_TOKENS_PER_USER = 30` across the combined debt+deposit token list (`contracts/Pool.sol:79,143-148,216-220`). An unprivileged attacker can call `deposit` on each registered `DepositToken` with a dust amount and `to_ = victim`, filling all 30 slots of the victim's per-account set without the victim's consent.

### Finding Description
- `DepositToken._mint` adds the deposit token to the recipient's `depositTokensOfAccount` set whenever their balance moves from 0 to >0 (`contracts/DepositToken.sol:469-480` and the `addToDepositTokensOfAccount` hook it calls).
- `Pool.addToDepositTokensOfAccount` is gated only by `onlyIfAdditionWillNotReachMaxTokens`; it does not check that the addition was initiated by the victim (`contracts/Pool.sol:216-220`).
- `deposit(amount_, to_)` pulls the underlying collateral from the *caller* (`_msgSender`) but mints the deposit-token position to `to_`. The attacker therefore pays only dust amounts of each collateral asset.
- Once the victim's combined `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`, any subsequent deposit of a *new* deposit token type reverts with `UserReachedMaxTokens`, and the minted-dust tokens cannot be removed by the victim faster than the attacker re-adds them (attacker can re-dust after the victim withdraws the dust; also, since removal only happens when balance hits exactly 0 via `_burn`, the attacker can front-run removal transactions with fresh dust deposits).
- No modifier stops this: `deposit` has no `onlyPool`-style restriction on `to_`, the supply-cap check only bounds `totalSupply`, and `SynthContext`/`nonReentrant`/pause flags are irrelevant to the attack.

### Impact Explanation
Denial of service on collateral management, matching the DoS half of the reference class: a victim holding an unhealthy or near-unhealthy position cannot deposit a new collateral type to restore health, enabling forced liquidation of their position (loss via liquidation penalty / seizure). Even for healthy users, all deposits of new deposit-token types revert until slots free up — and the attacker can keep slots occupied indefinitely by re-dusting. This is a liveness break on core user operations reachable by any EOA.

### Likelihood Explanation
Requires the pool to have enough registered deposit tokens to fill the remaining slots (pools with many collaterals, e.g. multiple Vesper vTokens, are vulnerable; pools with <30 total tokens limit the attack to blocking new debt/deposit types proportionally). Cost is dust amounts of each underlying plus gas. No privileged role, oracle manipulation, or timing dependency is needed. The mechanism relies on `deposit(amount_, to_)` accepting an arbitrary beneficiary, which is confirmed by `VesperGateway.deposit` calling `_depositToken.deposit(_vTokenAmount, _msgSender)` — I did not fully re-verify the `DepositToken.deposit` signature and its exact revert paths in the current source within the available search, so the precise argument order should be confirmed when writing the PoC.

### Recommendation
Restrict mint-to-arbitrary-account: either remove the `to_` parameter from `DepositToken.deposit` (have gateways mint to themselves then transfer), or track "deposited-by-self" positions and only add to `depositTokensOfAccount` when `to_ == _msgSender()` — alternatively, keep the max-token check but make `addToDepositTokensOfAccount` a soft failure (skip the add) for non-self deposits, since the per-account list is only used for health computation which must reflect balances anyway. A cleaner fix: require `to_` deposits above a governor-set dust threshold, or let the recipient opt in.

### Proof of Concept
Hardhat sketch (fork of a deployed pool with N registered deposit tokens):

```ts
// attacker: EOA with dust balances of each collateral
for (const dt of await pool.getDepositTokens()) {
  const depositToken = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('IERC20', await depositToken.underlying())
  await underlying.connect(attacker).approve(dt, MAX)
  // deposit 1 wei of underlying credited to victim
  await depositToken.connect(attacker).deposit(1, victim.address)
}
// victim's list is now full
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30)
// victim cannot deposit a new collateral type
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
// victim also cannot top-up a different new collateral to escape liquidation;
// withdrawing the dust frees a slot, but attacker re-dusts in the same block
```

Key assertion: `pool.debtPositionOf` / `deposit` paths revert for the victim while the attacker spent only ~30 dust transfers.
