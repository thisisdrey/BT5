This confirms the analysis. `calculate_is_link_allowed` (scheduler.rs:506-544) gates links purely on receiver/sender chunk-missing status and congestion status — not on whether the attacker has recently sent traffic on that link. `grant_base_bandwidth` (scheduler.rs:340-345) is applied unconditionally to every allowed link every height regardless of any request or recent activity, so the premise that an attacker must "keep links warm" with periodic traffic to receive base bandwidth is incorrect: idle, never-used links receive the same base bandwidth as busy ones, as documented explicitly in the module doc [1](#0-0) .

The "allowance banking" behavior described is the intended token-bucket fairness mechanism, explicitly documented: allowance accrues at a fixed fair rate per link every height via `increase_allowance`, capped at `max_allowance` [2](#0-1) , and higher-allowance links are prioritized in `process_bandwidth_requests`, with allowance decreasing by the granted amount afterward [3](#0-2) . This burst-after-idle pattern is the literal purpose of a token bucket and is called out in the doc comment as intentional design to let occasional large senders get their fair share without starving others [4](#0-3) . Regardless of allowance ordering, total bandwidth granted on any link remains bounded every height by `sender_budget`/`receiver_budget` capped at `max_shard_bandwidth`, enforced in `try_grant_bandwidth` [5](#0-4) , so no attacker can exceed the shard-wide byte budget; at most they shift the *order* in which competing requests within the same height are served, which is a QoS/fairness nuance, not a resource-exhaustion or correctness bug.

Critically, the scoped impact claimed — "denied fair bandwidth share, delaying cross-shard receipts" — is a temporary liveness/QoS degradation, not a permanent freeze of funds, theft, inflation, double-spend, authorization escalation, state-root divergence, or shard halt as required by the rubric. Delayed receipt forwarding due to token-bucket prioritization is bounded, self-correcting (the honest link's allowance also grows every height it isn't fully served), and does not stop any receipt from eventually being delivered. Since the required concrete impact categories are not met, and the underlying "exploit" is simply intended token-bucket burst behavior with unconditional base-bandwidth already provided to idle links, this does not constitute a valid vulnerability under the given scope.

    fn try_grant_bandwidth(&mut self, link: &ShardLink, bandwidth: Bandwidth) -> TryGrantOutcome {
        if !self.is_link_allowed(link) {
            // Not allowed to send anything on this link. Receiver is too congested or had a missing chunk.
            return TryGrantOutcome::NotGranted;
        }

        let sender_budget = self.sender_budget.get(&link.sender).copied().unwrap_or(0);
        let receiver_budget = self.receiver_budget.get(&link.receiver).copied().unwrap_or(0);

        if sender_budget < bandwidth || receiver_budget < bandwidth {
            // Sender or receiver can't send this much as they would go over the per-shard budget.
            return TryGrantOutcome::NotGranted;
        }

        // Ok, grant the bandwidth
        self.sender_budget.insert(link.sender, sender_budget - bandwidth);
        self.receiver_budget.insert(link.receiver, receiver_budget - bandwidth);
        self.decrease_allowance(link, bandwidth);
        self.grant_more_bandwidth(link, bandwidth);

        TryGrantOutcome::Granted
    }
