### Title
Unbounded offset parsing in `VerifyTransferProof` precompile allows attacker-controlled `ArrayIndexOutOfBoundsException` / heap-thrash via crafted call data - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Zcash-Sapling `VerifyTransferProof` TVM precompiled contract parses transaction-shielding proof data supplied directly by an unprivileged caller (any contract or EOA invoking the precompile address via `STATICCALL`/`CALL`). Several offsets (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) are read from the raw input and used to index into the `data` array via `System.arraycopy` calls with only a bound check on the derived *counts* (`spendCount`, `receiveCount`), not on the offsets themselves or on the final computed indices against `data.length`.

### Finding Description
`VerifyTransferProof.execute()` reads three 32-byte-word integers straight from attacker-supplied `data` as byte offsets into the same buffer: [1](#0-0) 

It then validates only that `spendCount == spendAuthSigCount`, `1 <= spendCount <= 2`, and `1 <= receiveCount <= 2` — it never validates that `spendOffset`, `spendAuthSigOffset`, or `receiveOffset` are within `[0, data.length)`, nor that `spendOffset + 320*spendCount`, `spendAuthSigOffset + 64*spendCount`, or `receiveOffset + 288*receiveCount` stay inside the bounds of `data`. The code then performs multiple `System.arraycopy` calls indexed by these unchecked offsets: [2](#0-1) 

Because `parseInt`/offsets are attacker-controlled 32-bit values (potentially negative or arbitrarily large after `intValueSafe`-style parsing), the `System.arraycopy` calls can be given negative or wildly out-of-range source indices, which throws an unchecked `ArrayIndexOutOfBoundsException` (or `NegativeArraySizeException`) deep inside precompile execution. This exactly mirrors the CVE-2026-20053 root cause: "improper range checking" on attacker-controlled, offset-driven data copy that leads to an out-of-bounds memory access — in java-tron's case the equivalent of a heap read/crash primitive instead of a native heap overflow.

This is directly reachable from an unprivileged transaction: any account can deploy or call a contract that issues a `CALL`/`STATICCALL` to the Sapling verify-transfer precompile address with arbitrary calldata, since precompiles are invoked from `OperationActions.exeCall` without contract-specific ACLs: [3](#0-2) 

### Impact Explanation
An `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` thrown mid-precompile is a Java runtime exception; whether it aborts only the current transaction (revert) or propagates uncaught up through the TVM executor and crashes/halts node threads depends on the surrounding call stack's exception handling, which I could not fully verify within the available tool budget (the outer try/catch scope around the `execute()` body was visible but its catch clause and how the caller (`Program.callToPrecompiledAddress`) handles arbitrary `RuntimeException` types was not confirmed). If the exception is only caught as `ContractExeException`/`ContractValidateException` further up and an unchecked `RuntimeException` slips through, this could crash the TVM execution thread for every node validating the transaction, resulting in a DoS condition consistent with the CVE's Snort 3 "Detection Engine crash" analog. If it is fully caught and reverted, impact is limited to wasted energy per call (Low/no qualifying impact under the given scope rules).

### Likelihood Explanation
Trivial to trigger: the attacker only needs to submit a single transaction that performs a `CALL` to the `verifytransferproof` precompile address with a calldata blob whose `spendOffset`/`spendAuthSigOffset`/`receiveOffset` fields point outside the buffer (e.g., a huge value or a negative-appearing 32-bit int). No special privileges, no waiting on chain state, purely single-transaction, unauthenticated exploitation.

### Recommendation
Add explicit bounds validation immediately after parsing `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and their derived post-increment values) in `VerifyTransferProof.execute()`, rejecting the call (returning `Pair.of(true, DataWord.ZERO().getData())`, consistent with existing validation style) whenever any offset, or any of the subsequent `System.arraycopy` ranges (`offset + fieldSize*count`), would exceed `data.length` or is negative — mirroring the pattern already used in `RLP.verifyLength()` elsewhere in the codebase. Wrap the parsing/copy block so any unexpected `IndexOutOfBoundsException` is caught and converted into a normal "verification failed" precompile result rather than propagating as an uncaught runtime exception.

### Proof of Concept
1. Craft `data` for a `CALL` to the Sapling `VerifyTransferProof` precompile address where the first three 32-byte words (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) are set to out-of-range values, e.g. `spendOffset = 0x7FFFFFFF` (or a negative-looking word like `0xFFFFFFFF`), while `spendCount` embedded at that (fabricated) offset location cannot even be read without first triggering an out-of-bounds `System.arraycopy`/array index read in the `parseInt(data, spendOffset)` step.
2. Submit this as calldata in a `TriggerSmartContract` transaction that performs `staticcall(gas(), <VerifyTransferProof precompile address>, data, len, 0, 0)` from a simple forwarding contract.
3. Observe whether the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` is caught and converted to a normal contract revert, or propagates further — the latter is required to fully confirm node-crash impact, which I was unable to verify with certainty given the tool-call budget exhausted before inspecting `Program.callToPrecompiledAddress`'s exception-handling and the full outer `try { ... } catch (...)` block enclosing lines 1472–1591.

  public static void exeCall(Program program, DataWord adjustedCallEnergy,
      DataWord codeAddress, DataWord value, DataWord tokenId, boolean isTokenTransferMsg) {

    DataWord inDataOffs = program.stackPop();
    DataWord inDataSize = program.stackPop();

    DataWord outDataOffs = program.stackPop();
    DataWord outDataSize = program.stackPop();

    program.memoryExpand(outDataOffs, outDataSize);
    int op = program.getCurrentOpIntValue();
    MessageCall msg = new MessageCall(
        op, adjustedCallEnergy, codeAddress, value, inDataOffs, inDataSize,
        outDataOffs, outDataSize, tokenId, isTokenTransferMsg);

    PrecompiledContracts.PrecompiledContract contract =
        PrecompiledContracts.getContractForAddress(codeAddress);
    if (contract != null) {
      if (program.isConstantCall()) {
        contract =  PrecompiledContracts.getOptimizedContractForConstant(contract);
      }
      program.callToPrecompiledAddress(msg, contract);
    } else {
      program.callToAddress(msg);
    }
    program.step();
  }
