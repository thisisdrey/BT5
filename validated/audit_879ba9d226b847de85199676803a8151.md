Audit Report

## Title
Child-bounty sub-accounts have no fallback/reclaim path for stray or residual funds - (File: substrate/frame/child-bounties/src/lib.rs)

## Summary
`pallet-child-bounties` computes a deterministic sub-account per child bounty via `child_bounty_account_id(parent_bounty_id, child_bounty_id)` [1](#0-0) , which anyone can pre-compute and send value to. Both terminal paths, `claim_child_bounty` [2](#0-1)  and `impl_close_child_bounty` [3](#0-2) , sweep only the native `T::Currency` free balance and then delete the storage entry, permanently orphaning the address for any non-native assets or funds sent after closure. The sibling pallet `pallet-bounties` was patched with a dedicated `reclaim_bounty_funds` extrinsic to fix precisely this class of stranded-funds issue (tracked as GitHub issue #10996) [4](#0-3) , but no equivalent exists for child-bounty accounts.

## Finding Description
`child_bounty_account_id` is a pure function of two public indices (`PalletId::into_sub_account_truncating(("cb", parent_bounty_id, child_bounty_id))`), making the resulting `AccountId` computable and reachable by any external party before, during, or after the child bounty's lifecycle [1](#0-0) .

`claim_child_bounty` moves only `T::Currency::free_balance(&child_bounty_account)`, split between `curator_fee` and `payout`, via native `Currency::transfer` calls [5](#0-4) . This does sweep the *entire* native balance present at claim time (including any extra native top-ups), so native funds sent before claim are not stuck. However, non-native assets (e.g. `pallet-assets` tokens) sent to the account are never referenced, and any native or non-native funds sent *after* the account is claimed or closed are unreachable, because `ChildBountyDescriptionsV1` and the `ChildBounties` storage entry are removed at the end of both `claim_child_bounty` and `impl_close_child_bounty` [3](#0-2) , and no other pallet extrinsic references that account afterward.

Parity's own fix for the structurally identical parent `pallet-bounties` account confirms this is a recognized bug class: `reclaim_bounty_funds` was added specifically to sweep both native and `TransferAllAssets`-configured assets from closed bounty accounts back to the treasury, explicitly to resolve issue #10996 concerning stranded funds [6](#0-5) . No such call, or `TransferAllAssets`-style abstraction, exists in `pallet-child-bounties`. Additionally, the newer `pallet-multi-asset-bounties` (used only on Asset Hub Westend, not on the Rococo relay chain) does not supersede `pallet-child-bounties`, which remains compiled into and wired into the live Rococo relay-chain runtime with its own weights file.

## Impact Explanation
Non-native assets, or native/non-native funds sent to a child-bounty sub-account after it has been claimed or closed, become permanently irrecoverable — no dispatchable call in `pallet-child-bounties` references the account once its storage entry is removed. This matches the accepted "permanent user-fund lock" impact category, requiring no privileged actor, leaked key, or malicious validator/collator — only a standard asset or balance transfer to a publicly computable address.

## Likelihood Explanation
Likelihood is moderate: reaching the affected states (post-claim/post-close) is a routine part of the child-bounty lifecycle, and computing `child_bounty_account_id` and sending assets to it requires only standard, permissionless extrinsics available to any account. The condition is trivially and repeatably reproducible, and Parity's independent identification and remediation of the same issue in the sibling `pallet-bounties` corroborates that this is a genuine, previously-unaddressed gap rather than a benign design choice.

## Recommendation
Add a permissionless `reclaim_child_bounty_funds` extrinsic mirroring `pallet_bounties::reclaim_bounty_funds`, gated on the `(parent_bounty_id, child_bounty_id)` pair no longer existing in `ChildBounties` storage, that sweeps any residual native balance and `TransferAllAssets`-configured assets from the deterministic child-bounty account back to the parent bounty or treasury account.

## Proof of Concept
1. Create a parent bounty and add a child bounty via `add_child_bounty`; compute `A = child_bounty_account_id(parent_bounty_id, child_bounty_id)`.
2. Complete the lifecycle: `propose_curator` → `accept_curator` → `award_child_bounty` → `claim_child_bounty`, removing the `ChildBounties` storage entry.
3. After step 2, transfer a `pallet-assets` token, or a native balance, to `A`.
4. Observe that no extrinsic in `pallet-child-bounties` can move funds out of `A`; the balance is permanently stranded.

		/// Reclaim funds stranded in a closed bounty's account back to the treasury.
		///
		/// Permissionless. Moves all remaining assets from a closed bounty's account back to the
		/// treasury in a single call. Which assets are swept depends on the `TransferAllAssets`
		/// configuration.
		///
		/// The call is free if funds were reclaimed and paid otherwise, so no-op calls cannot be
		/// used to grief the network. Emits `BountyFundsReclaimed` on success.
		///
		/// ## Complexity
		/// - O(A) where A is the number of relevant assets configured in `TransferAllAssets`.
		#[pallet::call_index(11)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::reclaim_bounty_funds())]
		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

			// Free only if something moved, otherwise paid to prevent griefing.
			if !transferred {
				return Ok(Pays::Yes.into());
			}

			Self::deposit_event(Event::<T, I>::BountyFundsReclaimed { bounty_id });

			Ok(Pays::No.into())
		}
