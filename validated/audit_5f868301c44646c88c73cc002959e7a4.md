### Title
`ProxyOFT._creditTo()` lacks the `isBridgingActive` check that `_debitFrom()` enforces — inbound cross-chain mints bypass the bridging emergency pause - (File: contracts/ProxyOFT.sol)

### Summary
`ProxyOFT` enforces `IPoolRegistry.isBridgingActive()` on the outbound (debit) path of the LayerZero bridge, but the inbound (credit) path mints synthetic tokens unconditionally. The result is an asymmetric circuit breaker: once the governor pauses bridging (the emergency control intended to stop value transfer during an incident), users cannot bridge out, yet anyone with an in-flight or retryable inbound message can still force a mint on the destination chain. This is the same bug class as the referenced report — a state-gating check applied on one side of an operation is missing from its counterpart, so the pause flag does not actually protect the affected surface.

### Finding Description
In `contracts/ProxyOFT.sol`, `_debitFrom` reads the pool registry and reverts when bridging is paused or the destination chain is unsupported: [1](#0-0) 

The counterpart `_creditTo` performs no such validation — it calls `syntheticToken.mint` directly: [2](#0-1) 

`SyntheticToken.mint` only requires the caller to be an authorized minter (the proxyOFT qualifies via `onlyIfCanMint`), so nothing else blocks the mint while bridging is paused: [3](#0-2) [4](#0-3) 

Additionally, the inherited `NonblockingLzAppUpgradeable` retry functions (`retryOFTReceived`/`retryMessage`) are public, so a previously stored failed payload can be re-executed by anyone — including after a pause — and it will flow into `_creditTo` with no pause check.

### Impact Explanation
- Emergency pause is ineffective inbound: during a bridge incident (e.g., supply inflation or a compromised peer contract on a remote chain), the governor sets `isBridgingActive = false`, expecting value flow to stop. Any `sendFrom` message already committed on the remote chain before the pause is still delivered by the LayerZero endpoint and mints on the destination chain.
- An attacker can time this deliberately: initiate `sendFrom` on the source chain just before/as an incident is detected, wait for the destination-side pause, and still receive minted synthetics, then swap or redeem them in the destination pool — draining healthy-chain liquidity with devalued remote supply.
- Failed deliveries are equally affected: a message that failed on first delivery is stored by the non-blocking app, and any unprivileged account can call the public retry to trigger the mint post-pause.
- Net effect: protocol insolvency on the healthy chain (minted synthetics not backed by real burned value) and circumvention of the intended liveness control — both within the accepted impact categories.

### Likelihood Explanation
Likelihood is moderate. It requires either (a) a legitimately in-flight cross-chain message at the moment bridging is paused — common whenever a pause is triggered reactively — or (b) a stored failed message that anyone can permissionlessly retry. The attacker does not need any privileged role, forged oracle data, or a malicious endpoint; they only need to have sent (or find) a real message. The scenario is most damaging when combined with a remote-chain incident, which is precisely when `isBridgingActive` would be toggled.

### Recommendation
Mirror the debit-side checks in `_creditTo`:

```solidity
function _creditTo(
    uint16 /*srcChainId_*/,
    address toAddress_,
    uint amount_
) internal override returns (uint256 _received) {
    IPoolRegistry _poolRegistry = syntheticToken.poolRegistry();
    if (!_poolRegistry.isBridgingActive()) revert BridgingIsPaused();
    syntheticToken.mint(toAddress_, amount_);
    return amount_;
}
```

If the intent is to let in-flight messages land during a pause, document that explicitly and instead gate only the emergency-scenario path (e.g., a separate kill switch), since the current asymmetry silently defeats `isBridgingActive` for inbound value.

### Proof of Concept
Foundry fork sketch (destination chain):

```solidity
// Setup: fork the chain where ProxyOFT + SyntheticToken are deployed
// 1. Attacker calls proxyOFT.sendFrom(...) on the SOURCE chain before pause
//    (cross-chain part simulated by invoking the endpoint path directly on dst).

// 2. Governor pauses bridging on destination:
vm.prank(governor);
poolRegistry.toggleBridgingIsActive(); // isBridgingActive() == false

// 3a. Direct path: endpoint delivers the in-flight payload:
vm.prank(address(lzEndpoint));
proxyOFT.lzReceive(srcChainId, trustedRemote, nonce,
                   abi.encodePacked(attacker, amount));
// -> _creditTo -> syntheticToken.mint(attacker, amount) succeeds,
//    even though _debitFrom would revert with BridgingIsPaused.

// 3b. Alternative: a previously failed delivery stored in the app:
proxyOFT.retryOFTReceived(srcChainId, trustedRemote, nonce,
                          storedPayload); // callable by anyone
// -> mint succeeds post-pause.

// 4. Attacker swaps/redeems minted synthetics in Pool.swap, draining liquidity.
```

Key invariant demonstrated: `syntheticToken.balanceOf(attacker)` increases while `poolRegistry.isBridgingActive() == false`, proving the pause flag does not cover the mint path.

Caveat I could not fully verify within available context: whether the deployment intends inbound credit to remain open during a bridging pause (i.e., whether this asymmetry is deliberate). The code gives no such indication — `BridgingIsPaused` exists and is enforced on debit — so the inconsistency stands on its own.
