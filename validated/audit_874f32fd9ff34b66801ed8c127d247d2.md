### Title
`LinkRepositoryToObjectPool` allows a repository to be linked to *any* object pool without verifying pool membership authorization - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The `LinkRepositoryToObjectPool` RPC lets a caller attach an arbitrary repository to an arbitrary, pre-existing object pool by supplying both `Repository` and `ObjectPool` fields in the request. The handler only validates that the two repository references are well-formed and that the pool actually exists on disk — it never checks whether the target repository is actually entitled to be a member of that specific pool (e.g. that it's a fork of the pool's origin repository). This mirrors the `buyLoan()` flaw: a state-changing operation (attaching to a pool / moving a loan into a pool) is exposed through a secondary path that omits the authorization/consistency check (`maxLoanRatio` / pool-membership) that is enforced elsewhere in the system (e.g., via GitLab's Rails `ObjectPoolMembers` authorization API used only for administrative pool scanning, not for the linking RPC itself).

### Finding Description
`LinkRepositoryToObjectPool` in [1](#0-0)  only performs:
1. `s.locator.ValidateRepository(ctx, repository)` — confirms the target repository path is syntactically valid and exists.
2. `s.poolForRequest(ctx, req)` — resolves the `ObjectPool` message to an actual `ObjectPool` instance, again just validating it is a legitimate repository/pool on disk.
3. `pool.Link(ctx, repo)` — performs the actual link.

The core `Link` function, [2](#0-1) , writes the pool's object directory into the target repository's `objects/info/alternates` file as long as the repository isn't already linked to a *different* pool. There is no check anywhere in this call chain confirming that the calling context is authorized to add this specific repository as a member of this specific pool (e.g. verifying the source/fork relationship that GitLab Rails tracks). That kind of authorization is only implemented as a separate, out-of-band mechanism used for pool bookkeeping/scanning — the Rails `ObjectPoolMembers` API surfaced through `internal/gitaly/service/internalgitaly/list_pool_upstreams.go` [3](#0-2)  and the `gitlab.Client.ObjectPoolMembers` interface [4](#0-3)  — but this check is never invoked from the `LinkRepositoryToObjectPool` handler itself.

Because `objects/info/alternates` grants full read access to every object in the pool's object database (this is exactly how Gitaly implements object deduplication for forks, per `doc/object_quarantine.md`/pool docs), any caller who can invoke `LinkRepositoryToObjectPool` with a repository they control and the relative path of an existing (potentially unrelated) object pool can make their own repository read every object — commits, blobs, trees — stored in that pool, including objects that originated from other users' private/upstream repositories that were pooled there.

### Impact Explanation
This is a cross-repository object access vulnerability: a repository owner can link their own repository to an object pool belonging to an unrelated project (if they can determine or guess its relative path, e.g. `@pools/xx/yy/<hash>.git`), thereby exfiltrating all objects contained in that pool via normal Git object access (`git cat-file`, clone, etc.) against their own linked repository — without ever having legitimate access to the source project. This can expose source code, commit history, and other repository content of private/upstream repositories that happen to share the pool.

### Likelihood Explanation
`LinkRepositoryToObjectPool` is a standard mutator RPC in `ObjectPoolService` [5](#0-4) , reachable by any client with valid Gitaly gRPC credentials (the same credentials used for ordinary fork/push/fetch operations). Nothing in the RPC handler itself restricts which pools a given repository may join — that authorization is assumed to live entirely in the calling layer (Rails), and Gitaly performs no independent enforcement, analogous to `buyLoan()` trusting no invariant beyond "the pool exists and has balance."

### Recommendation
Add an authorization check inside `LinkRepositoryToObjectPool` (or `Link`) verifying that the target repository is a recognized/allowed member of the given object pool — e.g., by consulting the same relationship metadata used by `ObjectPoolMembers`/pool-membership tracking — before writing the alternates file, rather than relying solely on callers (Rails) to have gated the call.

### Proof of Concept
1. Repository A (attacker-controlled) and Object Pool P (containing private repository B's objects, created via `CreateObjectPool`/fork flow) both exist on the same Gitaly storage.
2. Attacker calls `LinkRepositoryToObjectPool` directly against Gitaly with:
   ```
   LinkRepositoryToObjectPoolRequest{
     Repository: <Repository A>,
     ObjectPool: <ObjectPool P>,
   }
   ```
3. Gitaly performs only `ValidateRepository` and `poolForRequest` checks (both pass since P and A are legitimate on-disk repos), then calls `pool.Link(ctx, repoA)`.
4. `objects/info/alternates` in repository A now points at pool P's object directory.
5. Attacker fetches/reads objects from repository A and can retrieve any object ID that exists in pool P (originally contributed by repository B), even without ever having access to B.

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
```

```go
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

```go
// ListPoolUpstreams queries the Rails ObjectPoolMembers API in batches for the given pool disk
// paths and returns a mapping of pool disk path to upstream repository relative path.
func (s *server) ListPoolUpstreams(stream gitalypb.InternalGitaly_ListPoolUpstreamsServer) error {
	ctx := stream.Context()

	req, err := stream.Recv()
	if err != nil {
		return structerr.NewInvalidArgument("receive request: %w", err)
	}
	storageName := req.GetStorageName()
	if storageName == "" {
		return structerr.NewInvalidArgument("storage name is required")
	}

	// Collect all pool disk paths from the streaming request.
	poolDiskPaths := req.GetPoolDiskPaths()
	for {
		msg, err := stream.Recv()
		if errors.Is(err, io.EOF) {
			break
		}
		if err != nil {
			return structerr.NewInvalidArgument("receive pool disk paths: %w", err)
		}
		poolDiskPaths = append(poolDiskPaths, msg.GetPoolDiskPaths()...)
	}
```
