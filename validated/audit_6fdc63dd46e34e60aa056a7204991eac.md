## Analog Finding

### Title
Single-step, unvalidated authority transfer in `transfer_to_new_account`/`transfer_to_new_account_pda` can permanently lock a user's funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The Clober report flags a design flaw where role transfer (contract ownership / market host) is a single irreversible step with no validation that the new role-holder is reachable, allowing accidental or malicious bricking. Marginfi has the same bug-class pattern in its unprivileged, user-facing account-migration instructions: `transfer_to_new_account` and `transfer_to_new_account_pda` let any account authority move all its collateral/debt positions to a brand-new `MarginfiAccount` under an arbitrary `new_authority`, with no acknowledgment/claim step and no validation of the new authority at all.

### Finding Description
`TransferToNewAccount`/`TransferToNewAccountPda` accept a `new_authority: UncheckedAccount<'info>` explicitly documented as "New authority is completely unchecked": [1](#0-0) [2](#0-1) 

The instruction handler immediately: (1) disables the old account permanently by setting `ACCOUNT_DISABLED` and zeroing its `lending_account`, and (2) initializes a new account whose sole controlling key is whatever `new_authority` was supplied — with no signature, no second confirmation step, and no on-chain check that the value is a legitimate/reachable key: [3](#0-2) [4](#0-3) 

Crucially, migration is a one-time, irreversible action: `AccountAlreadyMigrated` blocks any further transfer from the old account, and the old account's `lending_account` (all balances) is zeroed out immediately, with funds now solely owned by the new account under the (unchecked) `new_authority`: [5](#0-4) 

This is functionally identical to Clober's "lack of two-step role transfer": there is no `pending_authority` + `claim` pattern requiring the recipient to prove control of the new key before the transfer finalizes. Compare with `marginfi_account_update_emissions_destination_account`, which similarly writes an unchecked destination pubkey but does not move any funds or disable anything — so the blast radius there is limited to misdirected emissions, not loss of principal: [6](#0-5) 

The p0-cli client only guards against the trivial zero-pubkey typo, not against any other unreachable/incorrect key: [7](#0-6) 

### Impact Explanation
If a user (or a front-end/integrator bug) supplies an incorrect `new_authority` (typo, wrong keypair, an address they don't actually control, or a PDA seed mismatch for `transfer_to_new_account_pda`), all of that account's deposited and borrowed positions are irreversibly migrated to a new `MarginfiAccount` that nobody can sign for. Because `migrated_to` is checked (`AccountAlreadyMigrated`) the old account can never be used to retry the migration, and the old account's balances are already zeroed, so the funds are permanently locked/frozen with no recovery path. This matches the "permanent lock/freeze" impact category from the validation criteria.

### Likelihood Explanation
This is reachable by any unprivileged account authority with a single self-authorized instruction call (`authority: Signer<'info>`), no admin gating required. Likelihood of an accidental trigger is realistic given that `new_authority` is a raw `UncheckedAccount` with zero validation beyond non-default-pubkey checking in the off-chain client (which itself is optional/bypassable since anyone can construct the instruction directly), and the PDA variant additionally requires exact seed reproduction (`account_index`, `third_party_id`) that is easy to mis-supply.

### Recommendation
Introduce a two-step migration/claim flow: the initiating authority proposes the `new_authority`/new account, and finalization requires a subsequent transaction signed by `new_authority` (or requires the new account's own authority signer in the same/second instruction) before the old account is disabled and balances are moved. Alternatively, require `new_authority` to co-sign the migration transaction, or add an explicit acknowledgment instruction executed by `new_authority` prior to irreversibly zeroing the old account.

### Proof of Concept
1. User has a `MarginfiAccount` with deposits/borrows.
2. User calls `transfer_to_new_account` (or `transfer_to_new_account_pda`) supplying a `new_authority` pubkey that is mistyped or for which they do not hold the private key (e.g., copy-paste error, wrong derivation).
3. Transaction succeeds: old account's `lending_account` is zeroed and `ACCOUNT_DISABLED` is set [8](#0-7) ; the new account is initialized with `authority = new_authority` holding all the migrated balances [9](#0-8) .
4. Any subsequent attempt to re-migrate the old account fails with `AccountAlreadyMigrated` [10](#0-9) , and the new account cannot be operated on because nobody controls `new_authority`'s private key — funds are permanently inaccessible.

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
