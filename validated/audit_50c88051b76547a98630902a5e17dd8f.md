### Title
Missing bounds check on witness-slot index in fork-version downgrade tracking causes `ArrayIndexOutOfBoundsException` during block application - (File: `chainbase/src/main/java/org/tron/common/utils/ForkController.java`)

### Summary
`ForkController` tracks per-hard-fork "which SR has seen this version" state as a `byte[]` sized to the current active-witness-list length. `update()` recomputes that size safely for the *target* version, but `downgrade()` — called from the same code path to clear stale votes on *other, higher* fork versions — indexes into a possibly differently-sized, previously-persisted `byte[]` with no bounds check. When the active-witness count changes between maintenance cycles (a normal consequence of stake-weighted voting, not a malicious act), a newly-added witness's slot index can exceed the length of a `stats` array that was allocated for a smaller witness set, throwing an unhandled `ArrayIndexOutOfBoundsException` while every full node applies the block.

### Finding Description
`ForkController.update()` computes the caller's slot as its position in the *current* active-witness list: [1](#0-0) 

It then calls `downgrade(version, slot)` *before* resizing/creating the `stats` array for the current `version`: [2](#0-1) 

`downgrade()` fetches the persisted `stats` byte array for every *higher* fork version that hasn't passed yet, and writes to `stats[slot]` with no length check at all: [3](#0-2) 

That `stats` array for the higher version was originally allocated by `upgrade()`, sized to `slotSize` (i.e., `witnesses.size()` at the time it was first created): [4](#0-3) 

By contrast, `update()` itself is careful to re-create the array whenever the witness-set size no longer matches: [5](#0-4) 

`downgrade()` has no equivalent guard. The active-witness-list size is not a constant — it is recomputed every maintenance cycle in `MaintenanceManager.doMaintenance()` / `DposService.updateWitness()` based on stake-weighted vote totals (any account can vote via `VoteWitnessContract`), and can range from 1 up to `MAX_ACTIVE_WITNESS_NUM`: [6](#0-5) [7](#0-6) 

This is exactly the stale-size/stale-index pattern described in the libde265 CVE: a cached array (the persisted `stats` byte array for a not-yet-passed higher fork version) is sized for a "config" (witness-set size) that later changes, and a later write path (`downgrade`) reuses an index computed against the *new* configuration without re-validating the array's length, leading to an out-of-bounds write.

### Impact Explanation
`ForkController.update()` runs inside per-block consensus/version-tracking logic invoked during block application in `Manager` for every produced block (confirmed by a single call site in `Manager.java`). An uncaught `ArrayIndexOutOfBoundsException` thrown here during block application is not caught by any surrounding try/catch specific to this path, so it propagates and aborts block processing. Because every full node, solidity node, and SR executes the identical deterministic logic against the identical on-chain state (persisted `stats` arrays and witness-schedule store), the exception fires deterministically on all nodes simultaneously at the block that triggers it — resulting in a full network halt (all nodes crash/stop processing new blocks) rather than an isolated node crash. This matches the "node crash or halt" / "chain split" acceptance criteria.

### Likelihood Explanation
Triggering requires a specific but organically reachable state combination:
1. At least one hard-fork version's `stats` array already exists (was created via `upgrade()`) sized to an earlier, smaller active-witness count.
2. A subsequent maintenance cycle changes the active-witness set to include a witness whose new index (`slot`) is `>= that stored array's length`.
3. A block is produced whose `version` is lower than that pending higher fork version (so `downgrade()` is reached and clears the stale vote), and the new/reindexed witness produces (or otherwise appears at a shifted slot in) that block.

This is plausible under normal operation on any network where the active SR set size fluctuates across epochs (e.g., private/test chains with fewer than `MAX_ACTIVE_WITNESS_NUM` candidates, or during SR churn on mainnet), and can be reliably reproduced/engineered by any set of accounts coordinating votes to shrink and then grow the active witness set around a hard-fork activation window. No special privilege beyond normal `VoteWitnessContract` broadcasting is required, and no witness needs to act maliciously — the bug is purely in `ForkController`'s bookkeeping. I could not fully trace every call site of `ForkController.update()`/`reset()` inside `Manager.java` (only located it via `grep`, not a full read), so I cannot state with certainty how many independent fork-version "generations" typically coexist in the store at once in production configurations; this affects exact reproduction timing but not the root-cause validity.

### Recommendation
In `downgrade()`, mirror the same defensive check `update()` already performs: before indexing, verify `slot < stats.length` (and treat a stale/mismatched-length array the same way `update()` does — recreate/resize it, or skip the downgrade write for that version) rather than writing directly into a persisted array whose length was fixed at a previous, potentially different witness-set size.

### Proof of Concept
Conceptual reproduction (exact trigger requires orchestrating maintenance-cycle witness churn against pending fork versions, which needs a running node/testnet — not verifiable purely from static code reading):
1. Start a chain configured with `MAX_ACTIVE_WITNESS_NUM = N` but fewer than `N` witness candidates receiving votes, so the active-witness list has size `k < N`.
2. Get a higher, not-yet-active `ForkBlockVersionEnum` version's `stats` array created via `upgrade()` while the active list size is `k` (array length `k`).
3. Have additional accounts vote to bring new witnesses into the active set, growing it to size `m > k`, such that a newly admitted witness lands at index `slot >= k`.
4. That witness produces a block whose `version` is below the pending higher fork version, causing `ForkController.update()` → `downgrade(version, slot)` to execute `stats[slot] = VERSION_DOWNGRADE` against the length-`k` array with `slot >= k`.
5. `ArrayIndexOutOfBoundsException` is thrown inside block application in `Manager`, uncaught, aborting block processing on every node that reaches this state deterministically. [8](#0-7)

  private void downgrade(int version, int slot) {
    for (ForkBlockVersionEnum versionEnum : ForkBlockVersionEnum.values()) {
      int versionValue = versionEnum.getValue();
      if (versionValue > version && !pass(versionValue)) {
        byte[] stats = manager.getDynamicPropertiesStore().statsByVersion(versionValue);
        if (Objects.nonNull(stats)) {
          stats[slot] = VERSION_DOWNGRADE;
          manager.getDynamicPropertiesStore().statsByVersion(versionValue, stats);
        }
      }
    }
  }

  private void upgrade(int version, int slotSize) {
    for (ForkBlockVersionEnum versionEnum : ForkBlockVersionEnum.values()) {
      int versionValue = versionEnum.getValue();
      if (versionValue < version && !pass(versionValue)) {
        byte[] stats = manager.getDynamicPropertiesStore().statsByVersion(versionValue);
        if (stats == null || stats.length == 0) {
          stats = new byte[slotSize];
        }
        Arrays.fill(stats, VERSION_UPGRADE);
        manager.getDynamicPropertiesStore().statsByVersion(versionValue, stats);
      }
    }
  }

  public synchronized void update(BlockCapsule blockCapsule) {
    List<ByteString> witnesses = manager.getWitnessScheduleStore().getActiveWitnesses();
    ByteString witness = blockCapsule.getWitnessAddress();
    int slot = witnesses.indexOf(witness);
    if (slot < 0) {
      return;
    }

    int version = blockCapsule.getInstance().getBlockHeader().getRawData().getVersion();
    if (version < ForkBlockVersionConsts.ENERGY_LIMIT) {
      return;
    }

    if (manager.getDynamicPropertiesStore().getLatestVersion() >= version) {
      return;
    }

    downgrade(version, slot);

    byte[] stats = manager.getDynamicPropertiesStore().statsByVersion(version);
    if (Objects.isNull(stats) || stats.length != witnesses.size()) {
      stats = new byte[witnesses.size()];
    }

    if (pass(version)) {
      upgrade(version, stats.length);
      manager.getDynamicPropertiesStore().saveLatestVersion(version);
      return;
    }

    stats[slot] = VERSION_UPGRADE;
    manager.getDynamicPropertiesStore().statsByVersion(version, stats);
    logger.info(
        "Update hard fork: {}, witness size: {}, solt: {}, witness: {}, version: {}.",
        Streams.zip(witnesses.stream(), Stream.of(ArrayUtils.toObject(stats)), Maps::immutableEntry)
            .map(e -> Maps
                .immutableEntry(encode58Check(e.getKey().toByteArray()), e.getValue()))
            .map(e -> Maps
                .immutableEntry(StringUtils.substring(e.getKey(), e.getKey().length() - 4),
                    e.getValue()))
            .collect(Collectors.toList()),
        witnesses.size(),
        slot,
        encode58Check(witness.toByteArray()),
        version);
  }
