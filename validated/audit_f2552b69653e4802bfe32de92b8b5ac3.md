### Title
StackerDB chunk signatures are not bound to the smart contract (StackerDB instance) that authorized them, enabling cross-database chunk replay - (File: libstackerdb/src/libstackerdb.rs)

### Summary
The OAuth advisory's root cause is that a check value (state/nonce/PKCE verifier) is verified without being cryptographically bound to the identity of the context (provider) that minted it, letting a value from one context satisfy validation in a different context. The same class of fault exists in `SlotMetadata::auth_digest`, which computes the signed digest for a StackerDB chunk from only `slot_id`, `slot_version`, and `data_hash` — it does not include the `smart_contract_id` (the StackerDB "provider") that the chunk belongs to.

### Finding Description
`SlotMetadata::auth_digest` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) . `sign`/`verify` operate purely over this digest, with no reference to which StackerDB (smart contract) the slot belongs to: [2](#0-1) .

Verification of an incoming chunk resolves the expected signer strictly by `(smart_contract_id, slot_id)` via `get_slot_signer`/`get_slot_validation`, then calls `slot_desc.verify(&slot_validation.signer)` — a check that only confirms the signature recovers to the correct address for *that slot number*, not that the signature was minted for *that specific contract*: [3](#0-2) . The same pattern appears in the p2p sync validation path, `validate_received_chunk`, which likewise looks up the signer only by `(smart_contract_id, slot_id)` before calling `slot_metadata.verify(&addr)`: [4](#0-3) .

Because the signed digest carries no contract/provider identity, a signature that is valid for slot `X`/version `V`/data `D` in StackerDB contract `A` is *also* a valid signature for slot `X`/version `V`/data `D` in any other StackerDB contract `B` for which the same signer address happens to own slot `X` — the signature is fungible across "providers," exactly analogous to the OAuth state/nonce/PKCE cookie being consumable by a different provider's callback.

### Impact Explanation
If any signer key is configured (by contract-set stacking/signer configuration) to own the same slot index in two different StackerDB instances — which is plausible since slot signer sets are independently defined per contract and can overlap (e.g., the same node operator/signer participating in multiple StackerDB-backed protocols) — an attacker who observes a legitimately signed, broadcast chunk for contract `A` (StackerDB chunks are gossiped/public, not secret) can replay that exact `(slot_id, slot_version, sig, data)` tuple to contract `B`'s `POST /v2/stackerdb/:principal/:contract/chunks` endpoint [5](#0-4)  or push it as `StackerDBPushChunkData` over the p2p unsolicited path. If `B`'s freshness/version and max-writes checks happen to be satisfiable, the forged-context chunk is accepted and stored/propagated as if it were validly written to `B`, and further gossiped network-wide via the store-and-forward StackerDB sync protocol. This is an unauthorized write of data into a StackerDB replica under a mismatched trust context and forged-data propagation across the network — impact consistent with "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data."

### Likelihood Explanation
Exploitability is conditional and requires overlap between two independently-operated StackerDB contracts' signer sets at the same slot index, plus an observable valid chunk from contract `A` and a matching acceptable version/data at contract `B`. This is a real and reachable analog of the reported bug class (missing provider binding in a check value) but the practical trigger (slot-index/signer overlap across contracts) is speculative without inspecting concrete production StackerDB contract configurations, which are outside what the indexed code shows.

### Recommendation
Bind the signed digest to the StackerDB's identity by including the `smart_contract_id` (or a serialized contract identifier) as part of `SlotMetadata::auth_digest`, so a chunk signature minted for one StackerDB instance cannot be replayed and accepted by a different StackerDB instance, mirroring the fix direction used for the OAuth check-cookie issue (binding checks to the exact context that created them).

### Proof of Concept
1. Configure two StackerDB smart contracts `A` and `B` such that slot `0` in both is owned by the same signer address `S` (a plausible operational overlap, e.g. the same node running signer duties for two boot contracts).
2. Node `A`'s legitimate operator signs and stores/broadcasts chunk `(slot_id=0, slot_version=5, data=D)` for contract `A` using `S`'s key: `SlotMetadata::sign` in [6](#0-5) ; this chunk is publicly observable via StackerDB replication/gossip.
3. Attacker (no private key required) submits the exact same `(slot_id=0, slot_version, sig, data=D)` tuple to contract `B`'s `POST /v2/stackerdb/.../B/chunks` endpoint.
4. `try_replace_chunk` looks up `B`'s slot-0 signer (also `S`), and `slot_desc.verify(&slot_validation.signer)` succeeds because `auth_digest` never included the contract id, so the signature recovers to `S` regardless of which contract it was minted for: [7](#0-6) .
5. If `B`'s version/max-writes checks are satisfied, the chunk minted for `A` is now accepted and stored as valid data in `B`, and propagated to `B`'s replica set.

    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
