### Title
Multipart form temp-file cleanup fails silently on Windows when uploaded file stream is left open - ([File: src/mime/multipart/formdata.go])

### Summary
`(*Form).RemoveAll` in `src/mime/multipart/formdata.go` deletes on-disk multipart temp files via `os.Remove(fh.tmpfile)`. If application code opens an uploaded file via `FileHeader.Open()` (used by `Request.FormFile`) and does not close the returned `*os.File` before the server calls `RemoveAll`, `os.Remove` on Windows fails with a sharing violation because Windows disallows deleting a file that still has an open handle, unlike POSIX unlink-while-open semantics. This is the same primitive as CVE-2023-42794: cleanup of an uploaded-file temp file is contingent on the consumer closing its stream, and on Windows that omission causes the temp file to remain on disk permanently, enabling disk-exhaustion DoS.

### Finding Description
Attacker input: a normal multipart/form-data HTTP upload → Go entry point `Request.ParseMultipartForm` (`src/net/http/request.go:1389`) → `mr.ReadForm` (`src/mime/multipart/formdata.go:41`) which writes large file parts to disk with `os.CreateTemp` and records the path in `fh.tmpfile` (`src/mime/multipart/formdata.go:177-195`). A handler retrieves the file with `Request.FormFile` → `FileHeader.Open()` (`src/mime/multipart/formdata.go:268-281`), which returns an `*os.File` opened on `fh.tmpfile`. Cleanup is later performed by `Form.RemoveAll` (`src/mime/multipart/formdata.go:240-253`), which does `os.Remove(fh.tmpfile)` and, notably, only surfaces the first non-`ErrNotExist` error while continuing to loop over the rest — the failed check is that `os.Remove` failure on Windows (because the caller's handle to the file is still open) is not retried and the temp file is left in place. `net/http`'s `server.go` invokes this cleanup path (`.RemoveAll()` referenced in `src/net/http/server.go`) once, with no retry loop, so a handler that forgets (or, under attacker-influenced control flow, is tricked into forgetting, e.g. via panics/early returns bypassing a `defer file.Close()`) to close the `multipart.File` leaves the sink — the temp file on disk — undeleted.

### Impact Explanation
Each unclosed multipart file handle results in one uninstantiated `os.Remove` on Windows, permanently leaking a temp file per affected request. Repeated over many requests (a normal, unprivileged HTTP upload workflow, no special attacker capability needed beyond triggering the handler code path that leaves the stream open), this accumulates disk usage until the volume is exhausted — a genuine denial of service, matching the Tomcat advisory's own characterization. This would be a Go PUBLIC-track report class (availability/DoS via resource accumulation tied to a real code-path bug in the standard library's cleanup contract, not a hypothetical), though the root trigger requires a specific Windows-only OS/filesystem locking policy plus an unclosed reader, so its severity is Windows-platform-scoped and lower than the memory-safety/crypto classes typically escalated as PRIVATE/URGENT.

### Likelihood Explanation
The victim workflow is very ordinary: any Go HTTP server that calls `ParseMultipartForm`/`FormFile` on Windows and has any code path where the returned `multipart.File` is not always closed (e.g., an early `return` before a `defer`, or a panic recovered elsewhere) is affected. No attacker privilege beyond making normal HTTP uploads is required; the attacker doesn't even need to control the leak directly — it's latent in ordinary large-file uploads on Windows.

### Recommendation
Make `Form.RemoveAll` (and/or the server's cleanup invocation) robust to files with lingering open handles on Windows: e.g. open temp files with `FILE_SHARE_DELETE` sharing mode (or `syscall.FILE_FLAG_DELETE_ON_CLOSE`) at creation time in `readForm`'s `os.CreateTemp` call so deletion succeeds even if a reader handle is still open, matching the fix approach ultimately used for the Tomcat/Commons FileUpload issue.

### Proof of Concept
```go
// formdata_windows_leak_test.go
//go:build windows

package multipart

import (
	"bytes"
	"os"
	"strings"
	"testing"
)

func TestRemoveAllFailsWhenFileStillOpenOnWindows(t *testing.T) {
	body := "--X\r\n" +
		`Content-Disposition: form-data; name="file"; filename="a.txt"` + "\r\n" +
		"Content-Type: text/plain\r\n\r\n" +
		strings.Repeat("A", 1<<20) + // force disk-backed temp file
		"\r\n--X--\r\n"

	r := NewReader(bytes.NewReader([]byte(body)), "X")
	form, err := r.ReadForm(1) // tiny maxMemory forces disk storage
	if err != nil {
		t.Fatal(err)
	}

	fh := form.File["file"][0]
	f, err := fh.Open() // opens *os.File on fh.tmpfile, caller "forgets" to Close()
	if err != nil {
		t.Fatal(err)
	}
	// NOTE: intentionally not calling f.Close() here, simulating the
	// unclosed-stream scenario from CVE-2023-42794.

	tmpPath := fh.tmpfile
	if err := form.RemoveAll(); err == nil {
		t.Fatalf("expected RemoveAll to fail while file handle is open on Windows")
	}
	if _, statErr := os.Stat(tmpPath); statErr == nil {
		t.Fatalf("temp file %s still exists on disk after RemoveAll: leaked", tmpPath)
	}
	f.Close()
	os.Remove(tmpPath) // cleanup for test hygiene
}
```
Expected assertion: on Windows, `form.RemoveAll()` returns a non-nil error and `os.Stat(tmpPath)` succeeds (file still present), demonstrating the leaked temp file; on POSIX platforms the same sequence succeeds because `unlink` on an open file is permitted, showing the platform-specific gap. // RemoveAll removes any temporary files associated with a [Form].
func (f *Form) RemoveAll() error {
	var err error
	for _, fhs := range f.File {
		for _, fh := range fhs {
			if fh.tmpfile != "" {
				e := os.Remove(fh.tmpfile)
				if e != nil && !errors.Is(e, os.ErrNotExist) && err == nil {
					err = e
				}
			}
		}
	}
	return err
}
