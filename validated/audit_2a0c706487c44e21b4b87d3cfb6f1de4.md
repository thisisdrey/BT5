I found a genuine unbounded-loop DoS candidate: `getDelegatedResourceAccountIndex` / `getDelegatedResourceAccountIndexV2`, reachable from anonymous gRPC/HTTP API clients, whose backing `getWithPrefix` in `DelegatedResourceAccountIndexStore` performs a `prefixQuery` and loads/sorts an entirely unbounded list of delegation records, with no pagination or count cap — unlike the `MARKET_COUNT_LIMIT_MAX`/`WITNESS_COUNT_LIMIT_MAX` bounds enforced on the sibling market/witness/asset list APIs.

### Title
Unbounded delegation-index query allows API-triggered node hang/DoS via unlimited resource delegation fan-out - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix` (invoked by `getIndex`/`getV2Index`) performs a `prefixQuery` over all `from`/`to` delegation records for a given address and materializes, sorts, and streams the entire unbounded result set into a `DelegatedResourceAccountIndexCapsule`. This is exposed directly to unauthenticated API callers via `Wallet.getDelegatedResourceAccountIndex(V2)` [1](#0-0) , which is wired to gRPC `GetDelegatedResourceAccountIndex(V2)` in `RpcApiService`/`RpcApiServiceOnSolidity` and to the `GetDelegatedResourceAccountIndexServlet`/`V2Servlet` HTTP endpoints [2](#0-1) .

### Finding Description
The store method builds the full list with no size limit: [3](#0-2) 

Any account can cheaply grow this list by repeatedly issuing `FreezeBalance`/`DelegateResource` transactions with tiny amounts to many distinct receiver addresses controlled by the attacker — each delegation just adds one `from`/`to` key-value pair via `delegate`/`delegateV2` [4](#0-3) . Unlike the analogous list-returning wallet APIs — `getMarketPairList`, `getMarketPriceByPair`, `getPaginatedNowWitnessList`, `getAssetIssueList(offset,limit)` — which all cap iteration with `MARKET_COUNT_LIMIT_MAX` or `WITNESS_COUNT_LIMIT_MAX` [5](#0-4) , there is no equivalent cap here. A single unauthenticated query against a heavily fanned-out address forces the node to load, sort, and serialize the entire unbounded record set in one synchronous call, on the same request-handling threads used by every other RPC/HTTP client.

This is directly analogous to CVE-2020-14868: an authorized-but-unprivileged actor (any transaction sender) can, through ordinary application-level operations (delegation transactions) followed by a normal read-only query, drive the node into unbounded/expensive computation that degrades or hangs request-serving threads — a repeatable, low-cost availability impact rather than any consensus-breaking bug.

### Impact Explanation
Because HTTP/gRPC handling threads are shared and there is no per-request bound on the number of delegation entries scanned/sorted/serialized, a single crafted address with a very large delegation fan-out can cause disproportionately expensive processing (large `prefixQuery` scan, `List.sort`, and full protobuf/JSON serialization) on every query. Repeated or concurrent queries against such an address can exhaust worker threads/CPU and degrade or deny the query API for legitimate users — matching the CVE's "hang or frequently repeatable crash (complete DOS)" impact class, scoped to the query-serving path rather than consensus.

### Likelihood Explanation
Likelihood is high: creating many delegation records only requires ordinary `FreezeBalance`/`DelegateResource`-type transactions (which are cheap, standard, and unprivileged), and the query endpoints (`/wallet/getdelegatedresourceaccountindex`, `/wallet/getdelegatedresourceaccountindexv2`, and their gRPC/Solidity/PBFT equivalents) are unauthenticated and rate-limited only generically (`RateLimiterServlet`), not by response-size/work bound.

### Recommendation
Add pagination/limits to `DelegatedResourceAccountIndexStore.getWithPrefix` (and corresponding `Wallet`/API methods), analogous to `MARKET_COUNT_LIMIT_MAX`/`WITNESS_COUNT_LIMIT_MAX`, so a single query cannot force unbounded prefix scans, sorts, or serialization; consider deprecating the unbounded variants in favor of offset/limit-based endpoints.

### Proof of Concept
1. From an attacker-controlled account, repeatedly submit `FreezeBalanceContract`/`FreezeBalanceV2Contract` transactions delegating small bandwidth/energy amounts to N (e.g., tens of thousands of) distinct receiver addresses, so `DelegatedResourceAccountIndexStore` accumulates N `FROM_PREFIX`/`TO_PREFIX` (or V2) entries for the attacker address (see `delegate`/`delegateV2` [4](#0-3) ).
2. Call `GET /wallet/getdelegatedresourceaccountindex?value=<attacker_address_hex>` (or the gRPC `GetDelegatedResourceAccountIndex`) repeatedly/concurrently.
3. Observe that each call triggers `getWithPrefix`'s full unbounded `prefixQuery` + sort + list materialization [3](#0-2) , consuming disproportionate CPU/memory per request and degrading the node's ability to serve concurrent API requests.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
