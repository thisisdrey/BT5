### Title
`CancelAllUnfreezeV2Actuator` skips the mandatory reward-settlement checkpoint that all other stake-mutating actions perform - (File: `actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java`)

### Summary
Every account action in java-tron that changes an account's frozen/voting-eligible balance (`FreezeBalanceV2`, `UnfreezeBalanceV2`, `UnfreezeBalance`, `VoteWitness`) first calls `mortgageService.withdrawReward(ownerAddress)` (or the TVM-side `VoteRewardUtil.withdrawReward`) to settle/close the reward accounting cycle before mutating state. `CancelAllUnfreezeV2Actuator` — and its TVM counterpart `CancelAllUnfreezeV2Processor` — restore the previously-unfrozen balance back into `FrozenV2`/total resource weight without ever calling this settlement checkpoint, exactly the "recalculate/settle on cancel" gap described in the external report.

### Finding Description
`UnfreezeBalanceV2Actuator.execute()` calls `mortgageService.withdrawReward(ownerAddress)` before moving balance out of `FrozenV2` into the pending `UnfrozenV2` list and adjusting total resource weight/votes. [1](#0-0) 

The same settlement call is present in the legacy `UnfreezeBalanceActuator`. [2](#0-1) 

By contrast, `CancelAllUnfreezeV2Actuator.execute()` iterates the pending `UnfrozenV2` list and re-adds any not-yet-expired entries directly back into `FrozenV2`/total resource weight via `updateFrozenInfoAndTotalResourceWeight`, with no `mortgageService.withdrawReward` call anywhere in the method. [3](#0-2) 

The TVM native-contract analog (`cancelAllUnfreezeBalanceV2()` opcode) shows the identical omission. [4](#0-3) 

`MortgageService.withdrawReward` is the checkpoint that closes the current reward cycle window (`beginCycle`/`endCycle` in `DelegationStore`) and snapshots the account's vote list for reward computation; skipping it means the account's `FrozenV2`/resource-weight state can be freely round-tripped (unfreeze → wait → cancel → unfreeze → cancel …) without ever forcing the cycle-closing bookkeeping that every other action performs. [5](#0-4) 

### Impact Explanation
This is directly analogous to the reported bug class: the "cancel" path for a pending state-change (here, a pending unfreeze) does not recompute/settle the value that depends on point-in-time state (here, the reward-cycle snapshot), while the "create" path (`UnfreezeBalanceV2Actuator`) does. Because settlement is asymmetric, an account can manipulate when the reward-cycle boundary is closed relative to its resource-weight/vote state by strategically unfreezing and cancelling, instead of ever triggering the settlement that a genuine unfreeze forces. This can bias reward-cycle accounting in `DelegationStore` (`beginCycle`/`endCycle`) in the attacker's favor without the loss of resource weight that an honest, uncancelled unfreeze imposes on other participants — mirroring the vault "fee/yield abuse via repeated cancel" pattern in the original report, but expressed through TRON's stake/vote-reward bookkeeping rather than a share-price mechanism.

### Likelihood Explanation
Reachable directly by any account holder via a single signed `CancelAllUnfreezeV2Contract` transaction (or the TVM `cancelAllUnfreezeBalanceV2()` opcode reachable from any contract call), requiring only `AllowCancelAllUnfreezeV2` to be enabled by committee (a mainnet-enabled feature flag), no special privilege beyond normal account transaction broadcasting. [6](#0-5) 

### Recommendation
Insert a `mortgageService.withdrawReward(ownerAddress)` (and the equivalent `VoteRewardUtil.withdrawReward` call in `CancelAllUnfreezeV2Processor`) at the start of `CancelAllUnfreezeV2Actuator.execute()`/`CancelAllUnfreezeV2Processor.execute()`, before any `UnfreezeV2` entries are moved back into `FrozenV2`, so the reward/cycle settlement checkpoint is consistently enforced on every action that mutates frozen balance/resource weight — matching the pattern already used by `UnfreezeBalanceV2Actuator` and `UnfreezeBalanceActuator`.

### Proof of Concept
1. Account A freezes TRX and votes for SR witnesses, accruing reward-cycle exposure tracked via `DelegationStore.beginCycle/endCycle` (never settled while votes are held).
2. Near a reward-cycle boundary, A calls `UnfreezeBalanceV2` for a partial amount — this correctly triggers `mortgageService.withdrawReward`, closing/settling the cycle window as of that block.
3. Before the unfreeze's delay period would normally finalize/lock the state change, A calls `CancelAllUnfreezeV2` to restore the frozen balance/resource weight. This path never calls `withdrawReward`, so it neither re-triggers settlement nor is symmetric with step 2.
4. A repeats steps 2–3 across cycle boundaries, using the create/cancel asymmetry to control exactly when reward-cycle settlement fires relative to A's frozen/voting state, unlike honest participants whose unfreeze is not cancelled and who bear the settlement consistently.

This confirms the structural asymmetry exists in the current code (verified directly in `CancelAllUnfreezeV2Actuator.java`, `CancelAllUnfreezeV2Processor.java`, `UnfreezeBalanceV2Actuator.java`, and `MortgageService.java`); I was not able to fully trace, within the available tool budget, the exact numeric magnitude of reward gain obtainable per cycle-boundary manipulation, since that depends on `RewardViCalService`/`DelegationStore` cycle-Vi computation details not fully reviewed here — this should be validated with a live/testnet reproduction before treating the magnitude as confirmed.

  public Map<String, Long> execute(CancelAllUnfreezeV2Param param, Repository repo) throws ContractExeException {
    Map<String, Long> result = new HashMap<>();
    byte[] ownerAddress = param.getOwnerAddress();
    AccountCapsule ownerCapsule = repo.getAccount(ownerAddress);
    long now = repo.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    long withdrawExpireBalance = 0L;
    for (Protocol.Account.UnFreezeV2 unFreezeV2: ownerCapsule.getUnfrozenV2List()) {
      if (unFreezeV2.getUnfreezeExpireTime() > now) {
        String resourceName = unFreezeV2.getType().name();
        result.put(resourceName, result.getOrDefault(resourceName, 0L) + unFreezeV2.getUnfreezeAmount());

        updateFrozenInfoAndTotalResourceWeight(ownerCapsule, unFreezeV2, repo);
      } else {
        // withdraw
        withdrawExpireBalance += unFreezeV2.getUnfreezeAmount();
      }
    }
    if (withdrawExpireBalance > 0) {
      ownerCapsule.setBalance(ownerCapsule.getBalance() + withdrawExpireBalance);
    }
    ownerCapsule.clearUnfrozenV2();

    repo.updateAccount(ownerCapsule.createDbKey(), ownerCapsule);

    result.put(VMConstant.WITHDRAW_EXPIRE_BALANCE, withdrawExpireBalance);
    return result;
  }

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
