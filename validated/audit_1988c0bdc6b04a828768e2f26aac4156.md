Audit Report

## Title
Snowbridge outbound-queue `calculate_fee` misuses `FixedU128::from_inner` and truncating integer division, allowing the Ethereum-side relayer fee to round to zero for valid, non-zero pricing parameters - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`Pallet::<T>::calculate_fee` computes the wei-denominated remote relayer fee and converts it to the native (DOT) currency by calling `FixedU128::from_inner(fee)`, which incorrectly reinterprets the raw wei integer as an already-scaled fixed-point value (dividing by `10^18` prematurely), then further truncates via `checked_div` in `convert_from_ether_decimals`. For pricing parameters that individually satisfy `PricingParameters::validate()` (all fields non-zero) but are numerically small relative to `gas_used_at_most` and the chain's decimal precision, the computed `fee.remote` rounds down to exactly `0`, as demonstrated by the pallet's own test. This lets a message be queued and committed for Ethereum relay without paying any remote/relayer-side fee component.

## Finding Description
`calculate_fee` at [1](#0-0)  computes `calculate_remote_fee` in raw wei, downcasts to `u128`, and then does:
```rust
let fee = FixedU128::from_inner(fee)
    .saturating_mul(params.multiplier)
    .checked_div(&params.exchange_rate)
    .expect("exchange rate is not zero; qed")
    .into_inner();
let fee = Self::convert_from_ether_decimals(fee);
```
`FixedU128::from_inner` treats the passed integer as already representing `value * 10^-18`, so a genuine wei value (which is itself an 18-decimal-scaled quantity) gets divided by `10^18` before the multiplier/exchange-rate adjustment is even applied. `convert_from_ether_decimals` then performs an additional integer `checked_div` by `10^(18 - Decimals)` (e.g., `10^6` for a 12-decimal chain, per `bridge_to_ethereum_config.rs`), silently floor-truncating any fractional remainder to `0` [2](#0-1) .

`PricingParameters::validate()` only rejects exactly-zero fields and does not check the resulting fee magnitude against expected gas usage or decimal scaling [3](#0-2) . The pallet's own regression test confirms the exact zero-fee outcome for `exchange_rate=1`, `fee_per_gas=1`, `reward=1`, `gas_used=250000`: `fee.remote == 0` [4](#0-3) .

This computed fee flows directly into `SendMessage::validate`, which is the sole gate before a message is accepted into the outbound queue and later committed to the merkle root for Ethereum relay [5](#0-4) . There is no downstream re-check of fee magnitude in `do_process_message` or `commit`.

However, the currently deployed production pricing parameters for BridgeHub Rococo are far from the pathological magnitudes shown in the test: `exchange_rate = 1/400`, `fee_per_gas = 20 gwei`, `rewards.remote = meth(1)` (i.e., `10^15` wei), `multiplier = 1`, with `Decimals = 12` [6](#0-5) . Under these realistic values, `calculate_remote_fee` produces a wei amount many orders of magnitude above the point where truncation would zero out the result, so the zero-fee condition does not manifest under the actual configured parameters — it requires governance to set pricing parameters at magnitudes far below realistic ETH gas-cost/reward levels (as in the test fixture) for the bug to actually produce `fee.remote == 0`.

## Impact Explanation
The arithmetic flaw is real and independently verifiable: `calculate_fee` can produce `fee.remote == 0` for pricing parameters that pass `PricingParameters::validate()`, which would allow a message to be queued and relayed to Ethereum without the relayer reward/gas-refund component being charged — matching the "public underpriced work that degrades block production or stalls bridge processing" impact category in principle. However, triggering the zero-fee condition in practice requires governance/admin-configured `PricingParameters` to be set at magnitudes far smaller than the deployed values (`exchange_rate=1/400`, `fee_per_gas=20 gwei`, `reward=1e15` wei), which are already large enough to avoid the truncation. An unprivileged external attacker calling the public send-message path cannot themselves cause the underpricing; it depends entirely on the specific pricing parameters governance chooses, making this fundamentally a parameter-magnitude-dependent latent defect rather than an attacker-triggerable bug against currently deployed configuration.

## Likelihood Explanation
Low under the currently deployed configuration, since the production `Parameters` in `bridge_to_ethereum_config.rs` are far from the values needed to trigger `fee.remote == 0`. The bug would only become live if governance later sets significantly smaller pricing-parameter magnitudes (as in the pallet's own test fixture), at which point it is trivially reproducible by any user sending a message. It is not exploitable by an unprivileged actor against the current live configuration alone.

## Recommendation
Fix the unit conversion in `calculate_fee` to use explicit, non-ambiguous scaling (avoid `FixedU128::from_inner` on a raw wei integer) and replace the silent-truncating `checked_div` in `convert_from_ether_decimals` with logic that rounds up or rejects sub-minimum fees. Extend `PricingParameters::validate()` to reject parameter combinations that would compute a zero DOT-denominated remote fee for expected message gas usage, rather than only checking individual fields for non-zero-ness.

## Proof of Concept
The pallet's existing test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` [4](#0-3)  demonstrates the arithmetic defect directly, but reproducing it against the live BridgeHub Rococo deployment would additionally require governance to first replace the configured `Parameters` [7](#0-6)  with magnitudes similar to the test fixture, which is outside attacker control.

		// which should be avoided
		assert_eq!(fee.remote, 0);
