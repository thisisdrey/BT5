Based on my investigation, I found a strong analog to the kernel `wwan_rtnl_policy` bug (an unvalidated/oversized index used to read into a fixed-size buffer) in java-tron's permission-operation bitmap check.

### Title
Out-of-bounds `ByteString.byteAt()` access in permission operation-bitmap check via unvalidated `Contract.type` value - ([File: actuator/src/main/java/org/tron/core/utils/TransactionUtil.java])

### Summary
`TransactionUtil.checkPermissionOperations()` and its duplicate `WalletUtil.checkPermissionOperations()` compute a bit index into a fixed 32-byte `operations` bitmap using the *raw* protobuf enum value of the contract type (`contract.getTypeValue()`), without validating that this value is within the expected `ContractType` range (0–59, fits in the 32-byte/256-bit bitmap). [1](#0-0) [2](#0-1) 

### Finding Description
`ContractType` is a protobuf enum field on `Transaction.Contract.type`. Per standard protobuf3 semantics, an enum field received over the wire with a value outside the declared enum set is preserved as its raw `int32` (via `getTypeValue()`), while `getType()` would report `UNRECOGNIZED`. This is exactly the same bug class as the kernel report: the kernel used `wwan_rtnl_link_ops`'s declared "bigger" `maxtype` value as an index/bound for a smaller policy array, causing an out-of-bounds read when parsing netlink attributes with an unvalidated field. Here, java-tron uses an attacker-controlled/unvalidated `contractType` integer (which is not restricted to the 0–255 range that fits the 32-byte permission bitmap) directly as `operations.byteAt(contractType / 8)`, an index into a fixed 32-byte `ByteString`. [1](#0-0) 

If `contractType` is crafted (via raw protobuf encoding of the `Contract.type` varint field to an arbitrary int32, e.g., a large positive value or a negative value), `contractType / 8` can exceed 31 or be negative, causing `ByteString.byteAt()` to throw an unchecked `IndexOutOfBoundsException`/`ArrayIndexOutOfBoundsException`.

### Impact Explanation
This check is reached whenever a transaction is signed/executed under a non-owner (multisig) permission (`permission_id != 0`), a condition entirely controlled by the transaction sender who sets up their own account's active permission. The unchecked exception is a `RuntimeException`, not declared by the method signature (`throws PermissionException`), so it is not guaranteed to be caught by all callers along the transaction-processing/signature-validation path (e.g., `TransactionCapsule` signature validation, `Wallet` sign-weight computation). An uncaught runtime exception in these paths can disrupt transaction/block processing, representing a node crash/DoS vector triggerable from a single attacker-controlled transaction — matching the "node crash or halt" impact bar. [3](#0-2) 

### Likelihood Explanation
Exploitation requires only: (1) an account with a defined active permission and a 32-byte `operations` bitmap (satisfiable by any user via `AccountPermissionUpdate`), and (2) submission of a raw transaction whose `Contract.type` field is set to an out-of-range varint value that is not a legitimate `ContractType` enum constant. Constructing such a raw transaction bypasses normal SDK-level enum constraints since protobuf allows arbitrary int32 values on the wire for enum fields.

### Recommendation
Validate `contract.getType() != ContractType.UNRECOGNIZED` (or bound-check `contractType` to `[0, 255]`) before using it as a bitmap index in both `TransactionUtil.checkPermissionOperations()` and `WalletUtil.checkPermissionOperations()`, rejecting the transaction/permission check with a `PermissionException` if it fails.

### Proof of Concept
1. Craft a raw `Transaction` protobuf where `raw_data.contract[0].type` is manually serialized as a varint field with value e.g. `100000` (out of the enum's real range) instead of any declared `ContractType` constant.
2. Ensure the transaction's owner account has an active permission with `permission_id != 0` set and a valid 32-byte `operations` field (via a prior `AccountPermissionUpdateContract`).
3. Sign and submit this transaction, or call the sign-weight/permission-check RPC path with it.
4. `checkPermissionOperations()` computes `contractType / 8 = 12500`, calling `operations.byteAt(12500)` on a 32-byte `ByteString`, throwing an unchecked `IndexOutOfBoundsException`.

**Uncertainty note:** I was unable to fully trace whether every call site (particularly `TransactionCapsule.validateSignature()` in `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`) wraps this call in a catch-all exception handler before propagating to `Manager`/block application, since my tool budget was exhausted before confirming that method body. This determines whether the impact is a fully unhandled node crash or merely a rejected transaction with graceful error handling — I could not fully verify which, so treat the crash/DoS severity as provisional pending confirmation of that call site's exception handling.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException("operations size must be 32");
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
