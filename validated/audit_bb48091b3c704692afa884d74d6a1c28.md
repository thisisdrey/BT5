### Title
Anti-replay window `Check`-then-`Update` race lets a duplicated/replayed data packet be decrypted and delivered twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` validates the message counter against the sliding anti-replay window, releases the lock, performs the (comparatively expensive) AEAD decryption, and only then re-acquires the lock to mark the counter as seen. Because the "check" and the "commit" are split across two separate lock/unlock sections with the decryption operation happening outside the lock, two goroutines processing the same message counter concurrently can both pass the `Check` before either has called `Update`, mirroring the report's TOCTOU class of bug (a quoted/validated value being consumed after the state it was validated against has already changed).

### Finding Description
`Decrypt` in [1](#0-0)  implements the pattern:

1. Lock, `window.Check(messageCounter)`, unlock.
2. Perform `dKey.DecryptDanger(...)` (AEAD open) with no lock held.
3. Lock, `window.Update(messageCounter)`, unlock — only this step actually marks the counter as seen in the bitmap (`bits.go` `Check`/`Update`) [2](#0-1) .

This mirrors exactly the report's root cause: a value (`quote`/minimum-output) is computed and validated at one point in time, but the actual state-changing operation (`swap`) happens afterward, and nothing prevents the world from changing between "check" and "act." Here, the "world" that can change is the replay-window bitmap itself: `Check` only reads state, and `Update` is the only call that writes it. Anything that causes two decrypt operations for the *same* counter to interleave between `Check` and `Update` defeats the anti-replay guarantee that `ReplayWindow`/`Bits` is supposed to provide, exactly as `getSwapOutput`-then-`swap` in the report defeats the intended slippage protection.

An attacker positioned to observe/relay UDP traffic (no CA-signed certificate needed — this is purely a network-level replay, not a handshake or authentication bypass) can capture one already-authenticated data packet for a live tunnel and rapidly re-inject (replay) it multiple times at the victim. If those replays are processed concurrently, each concurrent `Decrypt` call sees `window.Check(messageCounter)` return `true` (since the previous decrypt for the same counter has not yet reached its `Update` call), successfully decrypts, and delivers the plaintext to the overlay device — multiple times for what should be a single, once-only counter value.

### Impact Explanation
Successful exploitation causes remote state poisoning / traffic-replay: an application-layer packet an authenticated peer sent exactly once can be delivered to the TUN device more than once. Depending on the encapsulated protocol this can duplicate side-effecting operations (e.g., a UDP datagram carrying a command, DNS query, or any idempotency-sensitive traffic), and it undermines the core guarantee `ReplayWindow`/`Bits` (`bits.go`) exists to provide — Nebula's anti-replay protection for the Noise-derived transport keys. This falls squarely within the allowed "nonce/replay handling" / "traffic replay" analog category.

### Likelihood Explanation
Likelihood is limited by the narrow race window: the attacker needs the two replayed copies of the packet to be dispatched to concurrent goroutines and both reach `window.Check` before either reaches `window.Update`, i.e., before the (relatively fast) AEAD decrypt of the first copy completes and the lock is reacquired. This is feasible under multiple-reader/multiple-listener configurations or under load, but requires precise timing, making it a race condition rather than a deterministic bypass — comparable to the report's "Medium" likelihood given typical volatility/timing assumptions.

### Recommendation
Perform the replay-window check and commit atomically under a single critical section that also serializes with (or precedes) the decrypt call for the same message counter, e.g., hold `decryptLock` across `Check` through `Update`, or use a compare-and-set primitive that atomically reserves the counter slot before decryption begins and only finalizes/rolls back after decryption succeeds or fails. This removes the check/act gap analogous to fixing the swap's minimum-output enforcement by validating and consuming atomically rather than trusting a value computed earlier under different state.

### Proof of Concept
Not executed against a live binary; the race is inferred from the code structure:
1. Two goroutines both process an outside UDP packet carrying the same `messageCounter` for the same `ConnectionState` (e.g., attacker replays a captured packet to two listener sockets/readers, or the OS delivers duplicates fast enough for concurrent handling).
2. Goroutine A: `decryptLock.Lock(); window.Check(mc) -> true; decryptLock.Unlock()`.
3. Before goroutine A calls `window.Update`, goroutine B runs the same sequence: `decryptLock.Lock(); window.Check(mc) -> true (bit not yet set); decryptLock.Unlock()`.
4. Both A and B independently run `dKey.DecryptDanger` successfully (same valid ciphertext) and both return decrypted plaintext to their callers, each of which forwards it to the TUN/overlay device — the packet is processed twice despite the anti-replay window being designed to guarantee single delivery per counter. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
