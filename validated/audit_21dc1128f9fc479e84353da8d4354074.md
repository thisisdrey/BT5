### Title
Unbounded attacker-controlled length field drives an unbounded array allocation in TVM precompiles `BatchValidateSign`/`ValidateMultiSign` before the `allowTvmSelfdestructRestriction` guard is active - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `batchvalidatesign`/`validatemultisign` precompiled contracts parse an attacker-supplied 256-bit calldata word into a Java `int` length (`intValueSafe()`) and use it directly to size a `byte[][]` allocation, exactly the same bug class as the reported openssl_encrypt CVE (unvalidated size field from untrusted input drives an allocation). The size-limiting check (`MAX_SIZE`) is only performed when the feature flag `VMConfig.allowTvmSelfdestructRestriction()` is enabled; when it is not, the array-building helpers `extractBytesArray`/`extractBytes32Array` run unconditionally with the raw, unchecked count.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read a count directly from calldata and allocate an array of that size without any upper bound: [1](#0-0) 

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. The size check that would reject an oversized count (`sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE`) is gated behind `VMConfig.allowTvmSelfdestructRestriction()`; when that flag is false, the unconditional call to `extractBytesArray`/`extractBytes32Array` still executes with the fully attacker-controlled length: [2](#0-1) [3](#0-2) 

`words[offset].intValueSafe()` converts an arbitrary 256-bit calldata word to an `int`, and nothing in `extractBytes32Array`/`extractBytesArray` bounds it against the actual size of the supplied `data` (only later array-index reads on `words` would fail, but the initial `new byte[len][]` allocation happens first). A crafted 5-word (or slightly larger) calldata blob can therefore declare a length field near `Integer.MAX_VALUE`, triggering an attempt to allocate a multi-gigabyte `Object[]` reference array before any other bound is enforced — the same root cause pattern as the FLAC `STREAMINFO.total_samples` issue in the referenced CVE: a tiny crafted input declares an enormous count that is used to size memory before validation.

### Impact Explanation
Any account or contract can invoke the `batchvalidatesign`/`validatemultisign` precompiles via a `CALL`/`STATICCALL` from a TVM contract with a single crafted transaction. On execution paths where `allowTvmSelfdestructRestriction()` is not active (e.g., private/enterprise java-tron based chains, sidechains, or any deployment that has not activated this specific TIP proposal), the oversized allocation throws an `OutOfMemoryError` inside the node's JVM. Because this happens inside transaction execution (including possibly during block re-application by other full nodes validating the block), it can crash or destabilize the whole node process, not just fail the single transaction — a node crash/halt as required by the report's acceptance criteria.

### Likelihood Explanation
Likelihood is moderate to high on any chain/environment where `allowTvmSelfdestructRestriction` has not been enabled via governance proposal, since triggering the precompile requires only a normal `CALL` transaction from an unprivileged account, no special permissions, and a small calldata payload (a handful of 32-byte words). On networks (e.g. current TRON mainnet) where the proposal is already active, this specific path is blocked by the `MAX_SIZE` check, limiting exploitability to chains where the flag is off by default or not yet voted in — this is a genuine limitation on likelihood that could not be fully confirmed from the index (the on-chain/default activation status of `allowTvmSelfdestructRestriction` on the primary production network was not directly verifiable here).

### Recommendation
Move the `MAX_SIZE` (and any length sanity/consistency-with-`data.length`) checks so they are unconditionally enforced before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, independent of `VMConfig.allowTvmSelfdestructRestriction()`. Additionally, harden `extractBytesArray`/`extractBytes32Array` themselves to reject a `len` that is negative or inconsistent with the actual `words.length`/`data.length` before allocating, so the fix does not depend on any future feature flag being active.

### Proof of Concept
1. Construct calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign`) with the standard ABI head words, but set the offset word for the `address[]` (or `bytes[]`) parameter to point at a word whose value is a huge count, e.g. `0x7FFFFFFF`.
2. Deploy a minimal contract that performs a low-level `call` to the precompile address (`0x100...09` / the batchValidateSign address) with this crafted calldata, or call it directly via `triggercontract`.
3. Send the transaction to a java-tron node where `allowTvmSelfdestructRestriction` is not active (default/pre-activation state, e.g. private chain deployment).
4. Observe that `PrecompiledContracts.extractBytes32Array`/`extractBytesArray` attempts `new byte[0x7FFFFFFF][]`, exhausting/attempting to exceed the JVM heap and raising `OutOfMemoryError`, potentially destabilizing the node process executing/validating the transaction.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
