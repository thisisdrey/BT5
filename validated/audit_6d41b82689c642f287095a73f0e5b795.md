### Title
Wallet Contract Relayer-Fee Replay: Unconditional Fee Payout Combined With Deferred Nonce Increment on Address-Registrar Failure Enables Unlimited Fund Draining - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The Wallet Contract's `rlp_execute` entry point relies on a hard-coded external contract account, `ADDRESS_REGISTRAR_ACCOUNT_ID` (embedded from `runtime/near-wallet-contract/implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID`, currently `address-map.near`), to resolve whether an ETH-implicit `target` collides with a named account. [1](#0-0) [2](#0-1)  This is architecturally the same class of risk flagged in the external report: a critical safety check depends on a single hard-coded registry-contract reference that, if it becomes stale, unreachable, or otherwise fails, breaks the intended fail-safe behavior. Here, when that registrar call fails, the contract's fee-payout and nonce-increment logic interact in a way that allows the exact same signed relayer transaction to be replayed indefinitely, draining the wallet's relayer-fee balance on every replay.

### Finding Description
In `inner_rlp_execute`, for an `EOABaseTokenTransfer` whose target requires an address check (`address_check: Some(_)`), the nonce increment is deliberately **deferred** until the address-registrar lookup resolves in `address_check_callback`: [3](#0-2) 

Independently, and unconditionally, if the transaction carries a non-zero relayer `fee`, a **separate, non-chained** promise transferring that fee to the predecessor (relayer) is created immediately, regardless of whether the downstream address-check/registrar call ultimately succeeds: [4](#0-3) 

The actual registrar lookup is dispatched via the hard-coded `ADDRESS_REGISTRAR_ACCOUNT_ID`: [5](#0-4) 

If that cross-contract call to the registrar fails (e.g., because the hard-coded registrar account is stale/unreachable/misconfigured — the exact bug class described in the external report, just for an on-chain NEAR account reference instead of an Ethereum contract address), `address_check_callback` returns early **without incrementing the nonce**: [6](#0-5) 

Because `rlp_execute` is a public, unprivileged method — any NEAR account may call it as predecessor with a previously-observed `tx_bytes_b64` (no possession of the wallet's private key is required to *replay* an already-signed transaction, only to have originally produced it) — and because `has_in_flight_tx` only blocks *concurrent* in-flight transactions (it is reset to `false` at the top of every callback, including the failure path), the same signed transaction with nonce `N` can be resubmitted an unbounded number of times as long as the registrar call keeps failing. Each resubmission re-triggers the unconditional fee-transfer promise, resulting in repeated payouts to the calling relayer while the underlying user-intended action never executes and the nonce never advances.

### Impact Explanation
This results in concrete, repeatable theft of funds from the wallet's own balance: an attacker acting as "relayer" can drain the fee amount from the ETH-implicit account's wallet balance on every call, with no cap, as long as the address-registrar dependency remains broken/unreachable (the exact failure mode the external report warns about for hard-coded registry references). Because the address-check flow is only reachable for transfers whose `to` matches another eth-implicit account (`EOABaseTokenTransfer` with `address_check: Some(_)`), this is a real, unprivileged-signer-reachable path through the wallet contract that every NEAR client can hit by simply resubmitting a captured signed Ethereum transaction.

### Likelihood Explanation
Triggering requires: (1) a user signs an Ethereum-style transaction with `to` equal to another eth-implicit address and a non-zero relayer fee, and (2) the hard-coded `ADDRESS_REGISTRAR_ACCOUNT_ID` registrar call fails persistently (deleted/undeployed/misconfigured account, insufficient gas provisioned for the lookup, or any other durable failure). Once condition (2) holds, exploitation is trivial and requires no special privilege — any account can resubmit the publicly-visible signed transaction bytes repeatedly. The dependency on a single hard-coded external account for a security-relevant check is precisely the anti-pattern called out by the external ERC820 report, ported to this codebase's `ADDRESS_REGISTRAR_ACCOUNT_ID` mechanism.

### Recommendation
- Do not send the relayer-fee transfer as an unconditional, separate promise when the action still depends on an unresolved registrar lookup; chain the fee payment after the registrar call succeeds/fails is known, or scope it strictly to nonce-incrementing paths.
- On registrar-lookup failure, still increment the nonce (or otherwise render the specific signed transaction non-replayable) so a persistently failing/misconfigured registrar cannot be leveraged for unbounded replay.
- Avoid relying on a single hard-coded account for a security-critical address-collision check; consider validating/pinning the registrar account via governance-controlled, upgradeable configuration rather than a compile-time `include_str!` constant, and add monitoring/alerting so a broken registrar reference is caught before it can be exploited.

### Proof of Concept
1. User Alice owns eth-implicit account `0xAAA...` (Wallet Contract) with balance `B`.
2. Alice signs an Ethereum-style transaction: `to = 0xBBB...` (another, currently-unnamed eth-implicit address), value/action = anything, `fee = F > 0`, `nonce = N`.
3. Attacker Mallory (any NEAR account, no special permission) submits this `tx_bytes_b64` via `rlp_execute(target="0xBBB...", tx_bytes_b64)` to Alice's wallet contract.
4. `inner_rlp_execute` classifies this as `EOABaseTokenTransfer{ address_check: Some(addr_bbb), fee: F }`; nonce increment is deferred (`lib.rs:358-365`), and the fee-transfer promise to Mallory is scheduled immediately and unconditionally (`lib.rs:374-385`).
5. The registrar lookup against `ADDRESS_REGISTRAR_ACCOUNT_ID` fails (registrar account stale/unreachable/misconfigured).
6. `address_check_callback` hits `PromiseResult::Failed`, returns an error, and does not touch `self.nonce` (`lib.rs:140-159`); `has_in_flight_tx` is reset to `false`.
7. Mallory receives fee `F`, but Alice's transaction never executed and her nonce is still `N`.
8. Mallory resubmits the identical `tx_bytes_b64` in step 3 again — steps 4-7 repeat, and Mallory collects fee `F` again. This can be repeated until Alice's wallet balance is exhausted.
