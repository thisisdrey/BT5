### Title
JupLend Deposits Below the Rounding Threshold Permanently Burn User Funds With Zero Shares Minted - (File: programs/marginfi/src/instructions/juplend/deposit.rs)

### Summary
`juplend_deposit` computes the expected fToken shares for a deposit using floor-division against JupLend's `liquidity_exchange_price` / `token_exchange_price`, then transfers the user's underlying tokens and CPIs into JupLend *before* checking whether any shares were actually minted. When the deposited `amount` is small relative to the current exchange prices, the floor division can yield `0` expected/minted shares while the (non-zero) underlying tokens have already been irreversibly transferred out of the user's wallet and deposited into JupLend. The instruction still succeeds because `require_eq!(minted_shares, expected_shares, ...)` passes when both sides are `0`, silently crediting the depositor `0` marginfi asset shares for real, non-zero tokens spent.

### Finding Description
`juplend_deposit` follows this flow: [1](#0-0) 

1. `expected_shares` is computed via `expected_shares_for_deposit_from_rates`, which performs the same floor-division math as JupLend's liquidity layer: `raw = floor(assets*1e12/liquidity_exchange_price)`, `norm = floor(raw*liquidity_exchange_price/1e12)`, `shares = floor(norm*1e12/token_exchange_price)` [2](#0-1) .
2. The user's underlying tokens are transferred to the bank's liquidity vault and then CPI-deposited into JupLend *unconditionally*, regardless of whether `expected_shares` is `0`: [3](#0-2) 
3. Only after the transfer/CPI does the code assert `minted_shares == expected_shares`; when both are `0` this check trivially passes, and the code proceeds to credit the marginfi account `0` asset shares via `bank_account.deposit_no_repay(I80F48::from_num(0))`.

The repository's own unit tests confirm that floor-to-zero is a reachable, expected outcome once `token_exchange_price`/`liquidity_exchange_price` drift away from the `1e12` baseline (which happens naturally as yield accrues, since JupLend's `token_exchange_price` "starts at 1:1, only increases with yield"): [4](#0-3)  and [5](#0-4) . The fuzz-invariant harness for this instruction (`assert_juplend_deposit_success`) also only asserts `f_token_vault_after > f_token_vault_before` for `amount > 0`, without any lower bound that would catch a full-value floor-to-zero mint [6](#0-5) .

This is the direct structural analog of the Teleporter bug: a source-side actor (marginfi's JupLend deposit path, analogous to `TeleporterTokenSource`) transfers real value across a "bridge" (the JupLend CPI, analogous to the cross-chain message) to a destination denomination (fToken shares) that has its own rounding/decimals; when the transferred amount is below that destination's effective minimum denomination, the conversion rounds to zero and the value is unrecoverably absorbed by the destination side (JupLend's pool), while the depositor is credited nothing.

### Impact Explanation
Any depositor who submits `juplend_deposit` with an `amount` that floors to `0` shares under the bank's current `token_exchange_price`/`liquidity_exchange_price` permanently loses those tokens: the SPL transfer and CPI deposit into JupLend both execute and cannot be reversed, but the marginfi account is credited `0` asset shares, so the user has no claim on the deposited value (it accrues instead to the pool/other depositors). This is a genuine "permanent lock/loss of funds" for the affected user, matching one of the accepted impact categories (permanent lock/freeze of funds).

### Likelihood Explanation
`token_exchange_price` monotonically increases above `1e12` as JupLend yield accrues (per the code's own invariant assumptions), so over time there necessarily exists a "dust" deposit size below which the floor division yields zero shares — this is not a contrived edge case but a mathematically guaranteed steady-state condition, as the codebase's own tests explicitly construct and assert (`shares_for_deposit_tiny_amount_can_floor_to_zero`, `round_trip_near_zero_amounts`). Any unprivileged user (accidentally or via a scripted/looped attack pattern) can trigger this by depositing a sufficiently small `amount` once prices have drifted from `1e12`; no privileged role or special preconditions are required.

### Recommendation
Add an explicit guard in `juplend_deposit` that rejects the instruction (before transferring any tokens) when `expected_shares == 0`, e.g. `require!(expected_shares > 0, MarginfiError::JuplendDepositFailed)` (or a dedicated `MinimumDepositNotMet` error), mirroring the way Drift already rejects zero-value deposits. This prevents any underlying tokens from leaving the user's account when the resulting share credit would be zero, closing the loss vector without needing a destination-side registration redesign (unlike the more invasive fix used in the Teleporter bridge report).

### Proof of Concept
Given a JupLend-wrapped bank where `token_exchange_price = 1_500_000_000_000` and `liquidity_exchange_price = 1_200_000_000_000` (i.e., yield has accrued so both prices exceed `1e12`), a user calls `juplend_deposit(amount = 1)`:

1. `expected_shares_for_deposit_from_rates(1, 1_200_000_000_000, 1_500_000_000_000)` computes `raw = floor(1e12/1.2e12) = 0`, then `norm = 0`, then `shares = 0`, matching the codebase's own proven test case [7](#0-6) .
2. `cpi_transfer_user_to_liquidity_vault(1)` moves 1 native token unit out of the user's wallet into the bank vault, and `cpi_juplend_deposit(1, ...)` deposits it into JupLend, both of which succeed since Solana SPL transfers of amount `1` are valid.
3. `minted_shares = post_f_token_balance - pre_f_token_balance = 0` (matching JupLend's own floor-division deposit math, per the mock's documented formula), so `require_eq!(minted_shares, expected_shares, ...)` (`0 == 0`) passes.
4. `bank_account.deposit_no_repay(I80F48::from_num(0))` credits the user `0` asset shares.
5. Net effect: the user's wallet balance decreased by 1 unit, the JupLend pool's underlying liquidity increased by 1 unit, and the marginfi account's tracked position is unchanged — the depositor's 1 token unit is permanently and unrecoverably lost.

    ///
    /// Mirrors JupLend's actual deposit flow: **round down** via the liquidity layer.
    ///
    /// The deposit goes through a two-step conversion in the liquidity layer before
    /// computing shares. The intermediate floor divisions can cause up to 1 unit of

    ///
    /// Formula (1e12 precision):
    /// ```text
    /// raw   = floor(assets * 1e12 / liquidity_exchange_price)

    fn shares_for_deposit_matches_computed_values() {
        // Baseline: both prices at 1e12 -> assets == shares (no rounding)
        let l = lending_state(1_000_000_000_000, 1_000_000_000_000);
        assert_eq!(
            l.expected_shares_for_deposit(100_000_000).unwrap(),
            100_000_000
        );

        // Different prices: liq=1.2e12, token=1.5e12
        //   raw    = floor(100_000_000 * 1e12 / 1.2e12) = 83_333_333
        //   norm   = floor(83_333_333 * 1.2e12 / 1e12)  = 99_999_999
        //   shares = floor(99_999_999 * 1e12 / 1.5e12)  = 66_666_666
        let l = lending_state(1_200_000_000_000, 1_500_000_000_000);
        assert_eq!(
            l.expected_shares_for_deposit(100_000_000).unwrap(),
            66_666_666
        );

        let l = lending_state(1_000_000_000_000, 2_000_000_000_000);
        let shares = l.expected_shares_for_deposit(100_000_000).unwrap();
        assert_eq!(shares, 50_000_000);
        assert!(shares < 100_000_000, "protocol must not overmint");

        // Tiny deposit: floor divisions can eat the entire value
        let l = lending_state(1_200_000_000_000, 1_500_000_000_000);
        assert_eq!(l.expected_shares_for_deposit(1).unwrap(), 0);
    }
