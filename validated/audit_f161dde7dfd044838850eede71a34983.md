### Title
StackerDB unsolicited push-chunk handler advertises chunk acceptance in `StackerDBChunkInv` before the chunk is actually committed to storage - ([File: stackslib/src/net/stackerdb/mod.rs])

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` validates an incoming pushed chunk and immediately replies to the sender with a `StackerDBChunkInv` claiming the new `slot_version` is now held locally, but the actual database write is deferred to the relayer (`process_stacker_db_chunks` → `StackerDBTx::try_replace_chunk`). Because the acceptance advertisement and the actual persistence are two separate, non-atomic steps operating on the same "is this version now stored" fact, a legitimate-looking (but not necessarily attacker-forged) chunk can be acknowledged as stored to peers while the deferred write is later dropped, breaking the equality between "advertised inventory" and "actually stored data" — the same class of bug as the BakerFi report, where a value used to represent post-write state is computed/committed before the actual write takes effect.

### Finding Description
In [1](#0-0)  the handler:
1. Builds a `StackerDBChunkInv` reply payload from the node's current on-disk inventory.
2. Runs `validate_received_chunk` (signature, size, staleness, max-writes checks) against that snapshot — [2](#0-1) .
3. On success, **patches the in-memory inventory vector** (`*slot_version = chunk_data.chunk_data.slot_version;`) and sends this patched `StackerDBChunkInv` back to the peer immediately, claiming the chunk is now stored.
4. Returns `(false, true)`, meaning "do not buffer, forward to relayer" — i.e., the actual persistence has **not yet happened** at the point the acceptance reply is sent.

The real write only happens later and asynchronously, in [3](#0-2) , which independently re-validates and calls `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`). If that later write fails for any reason that isn't a hard, immediately-detectable rejection at push time (e.g., a race where a different, higher-versioned chunk for the same slot is committed by a concurrently-processed message before the relayer catches up, exceeding `max_writes`, or any transient DB-tx error), the failure is only logged with `warn!`/`debug!` and silently dropped — the peer that already received the "accepted" `StackerDBChunkInv` is never corrected.

This breaks the "advertised vs. actually stored" equality: the node's gossiped chunk inventory can claim it possesses a slot version it never actually persisted, exactly analogous to the Vault fee bug where a fee amount is computed against `totalSupply()`/`_totalAssets()` before the state-changing mint that the calculation is supposed to reflect actually occurs.

### Impact Explanation
StackerDB chunk inventories are used by neighbors for rarest-first/newest-first download scheduling (`stackslib/src/net/stackerdb/mod.rs:85-96`). A node advertising a version it doesn't actually have can cause neighbors relying on this inventory to treat unreplicated/uncommitted data as already propagated, and can be leveraged to steer peers' StackerDB sync decisions away from the true canonical state — matching the "steering a node off canonical state via false inventory" High-impact category. It does not require the node's private key or the signer's key: an attacker only needs to be an ordinary authenticated p2p peer relaying validly-signed chunks (which are routinely broadcast) in a timing pattern that causes the deferred write to fail after the optimistic ack has already gone out.

### Likelihood Explanation
Exploitability requires winning a race between two or more pushed/relayed chunks for the same slot such that the chunk whose acceptance was already advertised is the one dropped by `try_replace_chunk`'s strict version-ordering check in the deferred relayer path. This is plausible under normal gossip/broadcast conditions (the same push is often relayed via multiple neighbors near-simultaneously), making it a real but timing-dependent condition rather than a guaranteed single-message trigger.

### Recommendation
Do not send the `StackerDBChunkInv` acceptance reply (or patch the advertised inventory) until the chunk has actually been committed via `try_replace_chunk`/`tx.commit()`. Alternatively, perform the actual storage synchronously within `handle_unsolicited_StackerDBPushChunk` (or gate the reply on a confirmation callback from the relayer) so that the version advertised to peers always reflects a genuinely persisted slot version.

### Proof of Concept
1. Attacker (or two independent honest relays) sends two `StackerDBPushChunk` messages for the same `slot_id` in the same StackerDB contract to the victim node over two different connections, both carrying validly-signed chunks for versions `N+1` and `N+2` respectively (both signed with the legitimate slot owner's key, obtained by observing normal StackerDB gossip).
2. Both arrive at the victim in a window where each independently passes `validate_received_chunk` against the not-yet-updated on-disk `expected_versions` (`stackslib/src/net/stackerdb/mod.rs:785-792`), so both get their inventories patched and an "accepted" `StackerDBChunkInv` sent back (lines 794-807).
3. Both are forwarded to the relayer as `(false, true)`. In `process_stacker_db_chunks` (`stackslib/src/net/relay.rs:2406-2455`), `try_replace_chunk` is applied sequentially: whichever chunk is processed second, if its version is not strictly newer than what the first one just stored (e.g., due to interleaving, or because `N+1` gets processed after `N+2` and is then a `StaleChunk`), it is silently dropped with only a debug log (line 2416-2423).
4. The peer that received the "accepted" ack for the dropped version now believes the victim node holds that slot version, when the victim's actual on-disk state reflects a different version — a concrete break of the advertised-vs-stored equality.

    pub fn validate_received_chunk(
        &self,
        smart_contract_id: &QualifiedContractIdentifier,
        config: &StackerDBConfig,
        data: &StackerDBChunkData,
        expected_versions: &[u32],
    ) -> Result<bool, net_error> {
        // validate -- must not exceed this replica's configured chunk size.
        if (data.data.len() as u64) > config.chunk_size {
            info!(
                "Received StackerDBChunk for {} ID {}, which is oversized: {} bytes (max {} bytes)",
                smart_contract_id,
                data.slot_id,
                data.data.len(),
                config.chunk_size
            );
            return Ok(false);
        }

        // validate -- must be a valid chunk
        let Some(expected_version) = expected_versions.get(data.slot_id as usize) else {
            info!(
                "Received StackerDBChunk for {} ID {}, which is too big ({})",
                smart_contract_id,
                data.slot_id,
                expected_versions.len()
            );
            return Ok(false);
        };

        // validate -- must be signed by the expected author
        let addr = match self
            .stackerdbs
            .get_slot_signer(smart_contract_id, data.slot_id)?
        {
            Some(addr) => addr,
            None => {
                return Ok(false);
            }
        };

        let slot_metadata = data.get_slot_metadata();
        if !slot_metadata.verify(&addr)? {
            info!(
                "StackerDBChunk for {} ID {} is not signed by {}",
                smart_contract_id, data.slot_id, &addr
            );
            return Ok(false);
        }

        // validate -- must be the current or newer version
        if data.slot_version < *expected_version {
            info!(
                "Received StackerDBChunk for {} ID {} version {}, which is stale (expected {})",
                smart_contract_id, data.slot_id, data.slot_version, *expected_version
            );
            return Ok(false);
        }

        // validate -- must not exceed max writes
        if data.slot_version > config.max_writes {
            info!(
                "Write count exceeded for StackerDBChunk for {} ID {} version {} (max is {})",
                smart_contract_id, data.slot_id, data.slot_version, config.max_writes
            );
            return Ok(false);
        }

        Ok(true)
    }
