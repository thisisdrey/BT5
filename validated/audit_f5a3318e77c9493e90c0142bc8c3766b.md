### Title
Deposit path mints zero vault shares for real underlying funds after `socialize-debt` zeroes `assets`, permanently freezing/burning depositor funds - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
The external report's bug class is: contracts that fall back to a value-derived-from-state computation when a supply/balance denominator is zero, and fail to specially guard the "supply nonzero but balance zero" case (post-liquidation), causing depositors to receive an unfair (here: zero) amount of minted tokens. The Zest v2 vault contracts (`v0-vault-stx.clar` and its sibling vaults `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) contain the exact analog: `convert-to-shares-preview` silently returns `u0` when `total-assets` is `0` but `total-supply` is non-zero, and the `deposit` function — unlike `redeem` — has no `ERR-OUTPUT-ZERO` guard to reject that condition.

### Finding Description
`convert-to-shares-preview` is the share-pricing function used by `deposit`: [1](#0-0) 

```
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```

When `ts` (total zft supply) is non-zero but `ta` (total-assets) is `0`, the function returns `u0` unconditionally, regardless of `amount`. This is the same "balance is zero but supply exists" edge case the original report flags as dangerous, and which the protocol says it patched (in the ThetaVault/VolatilityToken case) by never letting a full-value mint happen against a zeroed balance.

`ta == 0` while `ts > 0` is reachable through an ordinary, non-privileged path: `socialize-debt`, which any authorized caller in the liquidation flow of `v0-4-market.clar` can trigger when a position's debt exceeds recoverable collateral. `socialize-debt` can drive `assets` to `u0` and `lindex` to `u0` while the vault's `zft` supply held by other depositors remains non-zero: [2](#0-1) 

After such an event, `deposit` is called: [3](#0-2) 

```
(define-public (deposit (amount uint) (min-out uint) (recipient principal))
    (let (
      ...
      (inkind (convert-to-shares-preview amount)))

    (asserts! (not (get deposit states)) ERR-PAUSED)
    (asserts! (var-get initialized) ERR-INIT)
    (asserts! (not (var-get in-flashloan)) ERR-REENTRANCY)
    (asserts! (> amount u0) ERR-AMOUNT-ZERO)
    (asserts! (>= inkind min-out) ERR-SLIPPAGE)
    (asserts! (<= (+ current-assets amount) CAP-SUPPLY) ERR-SUPPLY-CAP-EXCEEDED)

    (try! (receive-underlying amount account))
    (try! (ft-mint? zft inkind recipient))
```

There is no `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` in `deposit`. Contrast with `redeem`, which explicitly guards against this exact degenerate case: [4](#0-3) 

```
(define-public (redeem (amount uint) (min-out uint) (recipient principal))
  ...
  (asserts! (>= current-assets inkind) ERR-INSUFFICIENT-ASSETS)
  (asserts! (not (get redeem states)) ERR-PAUSED)
  (asserts! (> amount u0) ERR-AMOUNT-ZERO)
  (asserts! (> inkind u0) ERR-OUTPUT-ZERO)
  (asserts! (>= inkind min-out) ERR-SLIPPAGE)
```

So a depositor who calls `deposit` with `amount > 0` and `min-out = 0` (the honest, unaware default — nothing in the interface signals that "0" is a dangerous value to pass) will: transfer real underlying tokens into the vault (`receive-underlying`), have `assets` incremented by their deposit, but be minted `u0` zft shares. Their principal is absorbed into the vault's `assets` and effectively redistributed pro-rata to all pre-existing zft holders on the next accrual/withdrawal, while the depositor is left holding nothing.

This is the same root cause class as the ThetaVault/VolatilityToken report: a token-minting function derives an amount from a state ratio that is undefined/degenerate when the underlying balance has been fully drained (there via liquidation of a vol-token position; here via `socialize-debt`), and the contract fails to specially treat that case for new mints, instead of rejecting or clamping it as `redeem`'s sibling code path already does.

### Impact Explanation
This is a Critical-severity direct theft of user funds: a depositor's real underlying tokens are absorbed into vault `assets` and distributed to other zft holders, while the depositor receives zero shares and no way to recover the deposited value. This can happen to any unprivileged depositor without their knowledge (they need only omit or under-set `min-out`), any time the vault's `assets` has been fully socialized while supply remains — a state reachable through the standard liquidation/`socialize-debt` flow, not requiring DAO compromise.

### Likelihood Explanation
Likelihood is a function of `socialize-debt` occurring (a bad-debt/liquidation event that fully wipes a vault's tracked `assets`, e.g., very small vault utilization/edge scenario or a sizeable under-collateralized position) and a depositor subsequently calling `deposit` without a protective `min-out`. Given `min-out` is a caller-supplied parameter with no explicit "reject-zero-output" default and no dedicated UX warning at the contract level, and given `socialize-debt` is part of normal liquidation machinery (not privileged/DAO-only), this is plausible under stressed-market conditions, and the affected vault code is duplicated identically across `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, and `v0-vault-ststxbtc.clar`, multiplying exposure.

### Recommendation
Add the same `(asserts! (> inkind u0) ERR-OUTPUT-ZERO)` guard to `deposit` that already exists in `redeem`, across all six vault contracts. Additionally, mirror the fix pattern described in the referenced report: when `total-assets` is `0` while `total-supply` is non-zero (post-`socialize-debt`), do not allow a full-ratio mint at all — either revert the deposit entirely until the vault is re-seeded through a controlled/limited-size recovery mint, or apply a fixed conservative ratio with a capped maximum deposit amount for the first deposit(s) after such an event, consistent with how `socialize-debt` is meant to be handled operationally.

### Proof of Concept
1. An unprivileged liquidator triggers a liquidation via `v0-4-market.clar` on an undercollateralized position such that the shortfall is socialized through `v0-vault-stx.clar`'s `socialize-debt`, driving `(var-get assets)` (and possibly `lindex`) to `u0` while `zft` total supply remains `> 0` (other depositors still hold shares) — see `socialize-debt` at [2](#0-1) .
2. A new depositor calls `deposit(amount=1000_000000, min-out=0, recipient=self)`.
3. Inside `deposit`, `convert-to-shares-preview` computes `ta = 0`, `ts > 0`, returning `inkind = u0` (per [1](#0-0) ).
4. `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes since `0 >= 0`.
5. `receive-underlying` pulls the depositor's real 1000 tokens into the vault; `(var-set assets (+ current-assets amount))` credits the vault; `(ft-mint? zft inkind recipient)` mints `0` shares to the depositor.
6. The depositor has irreversibly lost their 1000 tokens' worth of value, which now backs the existing `zft` supply held by other, unrelated accounts.

(define-public (socialize-debt (scaled-amount uint))
  (let ((scaled-principal (var-get principal-scaled))
        (borrowed (var-get total-borrowed))
        (idx (var-get index))
        (current-assets (var-get assets))
        (current-lindex (var-get lindex))
        (old-total-assets (total-assets))
        (debt-reduction (mul-div-down scaled-amount idx INDEX-PRECISION))
        (principal-reduction (if (> scaled-principal u0)
                                (mul-div-down scaled-amount borrowed scaled-principal)
                                u0))
        ;; Write down lindex proportionally to loss in total-assets
        (new-lindex (if (and (> old-total-assets u0) (> old-total-assets debt-reduction))
                       (mul-div-down current-lindex (- old-total-assets debt-reduction) old-total-assets)
                       u0)))

    (try! (check-caller-auth))
    (asserts! (> scaled-amount u0) ERR-AMOUNT-ZERO)

    (var-set lindex new-lindex)
    (var-set principal-scaled (if (> scaled-principal scaled-amount) (- scaled-principal scaled-amount) u0))
    (var-set total-borrowed (if (> borrowed principal-reduction) (- borrowed principal-reduction) u0))
    (var-set assets (if (> current-assets principal-reduction) (- current-assets principal-reduction) u0))
