## Finding: Winning miner's StackerDB slot can be permanently bound to an unowned null address

### Title
Attacker-controlled `LeaderKeyRegisterOp.memo` can force the `.miners` StackerDB slot owner to the null Hash160, permanently denying legitimate writes to that slot - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoChainState::make_miners_stackerdb_config` derives the two `.miners` StackerDB slot owners from each sortition-winning miner's registered VRF key. When the leader key's `memo` field cannot be interpreted as a 20-byte Hash160, the code silently falls back to the "null" address `Hash160([0x00; 20])` instead of rejecting the configuration. Because the `memo` field is fully attacker-controlled burnchain-transaction data, any miner can win a sortition with a malformed/short memo and force every node on the network to configure that miner's StackerDB slot as owned by an address nobody can sign for.

### Finding Description
`LeaderKeyRegisterOp::interpret_nakamoto_signing_key` reads the first 20 bytes of the operation's `memo` field, which is populated from raw, attacker-supplied Bitcoin transaction data during `parse_data`/`parse_from_tx`: [1](#0-0) [2](#0-1) 

The comment at `parse_data` even notes "memo can be empty" — nothing in `LeaderKeyRegisterOp::check` or the burnchain-transaction parser enforces a minimum memo length, so `interpret_nakamoto_signing_key()` legitimately returns `None` for a maliciously crafted registration.

In `NakamotoChainState::make_miners_stackerdb_config`, this `None` case is treated defensively rather than being rejected — it substitutes the null Hash160 as the slot's signer address: [3](#0-2) 

This function is invoked by every node to (re)build the `.miners` StackerDB replica configuration whenever the burnchain tip advances: [4](#0-3) 

Note that this reconfiguration is keyed off `get_last_snapshot_with_sortition` (i.e., burnchain-level sortition winner selection), not off whether the corresponding Nakamoto block has passed `validate_normal_nakamoto_block_burnchain`, which *does* reject blocks whose leader key lacks a valid signing-key hash: [5](#0-4) 

That later, stricter check only guards actual block acceptance — it does not prevent the StackerDB config code from running first and installing the null address as the slot owner for every node in the network, since sortition winner determination happens independently of Nakamoto block validation.

Once installed, `StackerDBConfig.signers` contains `(StacksAddress::new(1, Hash160([0x00;20])), MINER_SLOT_COUNT)` for that slot. Every subsequent chunk-write validation against this slot goes through `verify()`/`validate_received_chunk`, which requires an ECDSA signature that recovers to this null pubkey-hash — something nobody (including the legitimate miner) can produce: [6](#0-5) [7](#0-6) 

This is the direct structural analog of the reported bug class: an initialization path accepts/derives a "zero/null" identity value instead of validating and rejecting it, and that null identity is later used as the authoritative owner in an authorization check — breaking the equality between "authenticated signer" and "actually controllable signer."

### Impact Explanation
The `.miners` StackerDB contract is the channel miners use to broadcast block proposals to signers in Nakamoto. Forcing a slot's owner to an unownable null address makes that slot permanently un-writable by anyone until the next sortition rotates it out (two sortitions later, per the slot-preservation logic in the same function). Because the misconfiguration is computed identically by every node from public burnchain data, this is a network-wide effect, not limited to the attacker's own node: all replicas reject legitimate chunk writes to that slot, disrupting miner→signer block-proposal propagation for that tenure window.

### Likelihood Explanation
Triggering this requires only: (1) submitting a `LeaderKeyRegisterOp` burnchain transaction with a memo shorter than 20 bytes (explicitly permitted per the parser's own comment), and (2) that operation's corresponding block-commit winning a sortition. Winning a sortition requires burn/commit resources proportional to normal mining, but no privileged access, secret keys, or admin role — it is the same unprivileged capability any participant already has to become a miner. No other node cooperation or bug is needed; the null-address fallback fires deterministically once the malformed key is referenced by a winning commit.

### Recommendation
In `NakamotoChainState::make_miners_stackerdb_config`, do not substitute a null/default Hash160 when `interpret_nakamoto_signing_key()` returns `None`. Instead, propagate an error (as `validate_normal_nakamoto_block_burnchain` already does) so that the `.miners` StackerDB config generation fails closed (e.g., falls back to `StackerDBConfig::noop()` for that reconfiguration attempt, as is already done elsewhere in `create_or_reconfigure_stackerdbs` when config loading errors), rather than assigning slot ownership to an unrecoverable placeholder address.

### Proof of Concept
1. Attacker crafts a Bitcoin transaction encoding a `LeaderKeyRegisterOp` whose payload after the VRF public key (bytes 52+) is empty or less than 20 bytes, so `memo.len() < 20`.
2. Attacker submits a `LeaderBlockCommitOp` referencing this leader key and wins the sortition for that burn block (via normal burn-commitment competition).
3. On every node, `create_or_reconfigure_stackerdbs` → `make_miners_stackerdb_config` runs, calls `interpret_nakamoto_signing_key()` on the malformed leader key, gets `None`, and falls back to `Hash160([0x00; 20])` as the slot's signer for that miner's index.
4. All nodes now enforce that only a signature recovering to `Hash160([0x00; 20])` may write that slot; no party can produce such a signature, so the slot is permanently unwritable until slot rotation.

    fn parse_data(data: &[u8]) -> Option<ParsedData> {
        /*
            Wire format:

            0      2  3              23                       55                      75        80
            |------|--|---------------|-----------------------|-----------------------|---------|
             magic  op consensus hash   proving public key      block-signing hash160    memo
                       (ignored)                                                       (ignored)

             Note that `data` is missing the first 3 bytes -- the magic and op have been stripped.
             `block-signing hash160` is new to Nakamoto.
        */
        // memo can be empty, and magic + op are omitted
        if data.len() < 52 {
            // too short to have a consensus hash and proving public key
            warn!(
                "LEADER_KEY_REGISTER payload is malformed ({} bytes)",
                data.len()
            );
            return None;
        }

        let consensus_hash = ConsensusHash::from_bytes(data.get(0..20)?)
            .expect("FATAL: invalid byte slice for consensus hash");
        let pubkey = match VRFPublicKey::from_bytes(data.get(20..52)?) {
            Some(pubk) => pubk,
            None => {
                warn!("Invalid VRF public key");
                return None;
            }
        };

        let memo = data.get(52..)?;

        Some(ParsedData {
            consensus_hash,
            public_key: pubkey,
            memo: memo.to_vec(),
        })

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
