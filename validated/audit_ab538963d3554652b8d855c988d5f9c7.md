### Title
DAO Treasury reserve-fee interest is permanently lost to floor-division precision loss in `accrue()` - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every Zest vault's public `accrue()` function computes the protocol's reserve-factor cut of newly accrued interest (`reserve-inc`) and mints it to `dao-treasury` as vault shares. Both the interest delta and the reserve cut are computed with floor-rounding (`mul-div-down`). Because `accrue()` is a callable-by-anyone `define-public` function with no auth check, and because it always advances `idx`/`last-update` regardless of whether any treasury shares were minted, an unprivileged caller can repeatedly call `accrue()` with short time deltas so that `debt-delta`/`reserve-inc` continually floors to `0`, permanently and irrecoverably erasing the protocol's yield for those periods — the same "reward rounds to zero due to precision loss" bug class as Derby's `storePriceAndRewards()`.

### Finding Description
In `accrue()` (present identically in `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`): [1](#0-0) 

```clarity
(define-public (accrue)
  (let ((states (var-get pause-states))
        (idx (var-get index))
        (lidx (var-get lindex)))
      (if (get accrue states)
          (ok { index: idx, lindex: lidx })
          (let ((next (next-index))
                (nliq (next-liquidity-index))
                (scaled-principal (var-get principal-scaled))
                (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
                (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
                (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
                (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
                (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
            (if (not (is-eq idx next)) (var-set index next) false)
            (if (not (is-eq lidx nliq)) (var-set lindex nliq) false)
            (if (> treasury-lp u0) (try! (ft-mint? zft treasury-lp .dao-treasury)) false)
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)
            (ok { index: next, lindex: nliq })))))
```

`debt-delta` and `reserve-inc` are both computed via `mul-div-down`, i.e. floor division: [2](#0-1) 

```clarity
(define-private (mul-div-down (x uint) (y uint) (z uint))
  (/ (* x y) z))
```

`debt-delta` is expressed in underlying-asset units (6 decimals for USDC/USDH), while the interest multiplier applied to the borrow index only grows by a tiny amount over a short `time-delta`. When `time-delta` is small (e.g. `accrue()` is called shortly after the previous accrual — which is trivial since `accrue()` has no caller restriction, unlike `system-borrow`/`system-repay`/`socialize-debt` which all call `(try! (check-caller-auth))`), `debt-delta` for moderate `principal-scaled` sizes rounds to a value whose 10% (or configured) reserve fee (`reserve-inc`) rounds down to `0`. Crucially, even when `reserve-inc` (and thus `treasury-lp`) is `0`, the code still unconditionally sets `index` to `next` and `last-update` to the current block time: [3](#0-2) 

```clarity
            (if (not (is-eq idx next)) (var-set index next) false)
            ...
            (if (or (not (is-eq idx next)) (not (is-eq lidx nliq))) (var-set last-update stacks-block-time) false)
            (ok { index: next, lindex: nliq })))))
```

This means the interest attributable to that accrual window is baked into `idx`/`lindex` (so suppliers still benefit) but the protocol's reserve-factor share of it is discarded forever — there is no accumulator that carries the fractional, rounded-away `reserve-inc` remainder into the next accrual. Because any principal can call `accrue()` at will (it's `define-public` with no `check-caller-auth`), an attacker/griefer can call it every block (or even every transaction) to keep `time-delta` tiny, guaranteeing `debt-delta`/`reserve-inc` floors to `0` on essentially every call, indefinitely suppressing DAO treasury minting while regular interest still accrues to lenders/borrowers as usual.

This is the identical bug class flagged as valid High in the referenced Derby report: a legitimate, non-zero yield/reward that should be captured by the protocol is silently zeroed out by floor-division when the numerator (a small, low-decimal delta) is divided by a large denominator (BPS/INDEX-PRECISION scaling), and the loss is not carried forward, making it permanent.

### Impact Explanation
The DAO treasury's reserve-factor yield (the protocol's fee income on all vaults) can be permanently and repeatedly zeroed out via a callable, unprivileged entry point. This is a form of permanent freezing/theft of unclaimed yield belonging to the protocol treasury — it satisfies the in-scope High impact class "theft of unclaimed yield ... or permanent freezing of unclaimed yield."

### Likelihood Explanation
`accrue()` is public and unauthenticated, and is also invoked as the first step of every deposit/redeem/borrow/repay/socialize-debt call, so its `last-update` is already touched frequently by ordinary usage. An attacker only needs to submit `accrue()` transactions (or trigger any vault interaction) at a high enough cadence relative to the vault's `principal-scaled`/interest rate that each incremental `debt-delta` floors its reserve cut to zero — a condition that is easily reachable, especially on vaults with modest borrowed amounts (mirroring the Derby PoC's "$30k / 1mln tokens" scenario) or with normal, frequent transaction activity, and it is repeatable indefinitely, making cumulative loss significant over time.

### Recommendation
Track an accumulator for the fractional, rounded-away reserve amount (e.g. `reserve-inc-remainder`) across `accrue()` calls, similar to a "carry" in AAVE-style reserve logic, so unminted reserve dust is not lost but rolled into the next accrual's `reserve-inc` computation. Alternatively, use a higher-precision intermediate (scale `debt-delta`/`reserve-inc` up before dividing, analogous to the `BASE_SCALE` fix suggested in the referenced Derby report) so treasury share computation does not floor to zero for realistic vault sizes.

### Proof of Concept
1. Vault (e.g. `v0-vault-usdc`) has some outstanding `principal-scaled`/debt and a configured `fee-reserve` (e.g. 1000 bps).
2. Attacker calls `accrue()` (public, no auth) immediately after a previous accrual, so `time-delta` is minimal.
3. `next-index` computed via `calc-multiplier-delta` yields only a marginal increase over `INDEX-PRECISION`; `debt-delta = new-debt - old-debt` is a very small integer in 6-decimal USDC units.
4. `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` floors to `0` because `debt-delta * fee-reserve < BPS`.
5. `treasury-lp` is `0`, so no shares are minted to `.dao-treasury`, yet `index`/`lindex`/`last-update` are advanced as if the period were fully processed.
6. Attacker repeats step 2–5 every block/transaction, permanently preventing the reserve factor from ever accumulating enough per-call `debt-delta` to round up, while lenders/borrowers still see the underlying index move — the treasury's fee income for that vault is durably suppressed.
