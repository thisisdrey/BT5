### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Signature Replay in `offer_signer_capability` - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`offer_signer_capability` verifies a signature over `SignerCapabilityOfferProofChallengeV2`, but that struct omits `chain_id`. The analogous `RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to V2 specifically to add `chain_id` and prevent cross-chain replay. The signer-capability challenge was not given the same treatment, leaving a cross-chain replay window that allows an attacker to reuse a valid signature from one Aptos network (e.g., devnet/testnet) on mainnet to gain unauthorized signer capability over a victim's account.

---

### Finding Description

`RotationCapabilityOfferProofChallengeV2` is documented as:

> "This V2 struct adds the `chain_id` and `source_address` to the challenge message, which prevents replaying the challenge message." [1](#0-0) 

Its definition:

```move
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,          // ← present
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

`SignerCapabilityOfferProofChallengeV2`, however, omits `chain_id`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,
    source_address: address,   // ← chain_id missing
    recipient_address: address,
}
``` [2](#0-1) 

`offer_signer_capability` constructs and verifies a signature over this chain-id-free struct:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(
    source_address, account_scheme, account_public_key_bytes,
    signer_capability_sig_bytes, proof_challenge);
``` [3](#0-2) 

Because the signed message does not bind to a chain, a signature produced on any Aptos network (testnet, devnet, a fork) is cryptographically valid on every other Aptos network where the same `(source_address, sequence_number, recipient_address)` triple holds.

---

### Impact Explanation

A successful replay grants the attacker's address a `SignerCapabilityOffer` over the victim's account:

```move
account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
``` [4](#0-3) 

The recipient can then call `create_authorized_signer` to obtain a full `signer` for the victim's account and execute arbitrary transactions — transferring APT, fungible assets, or any other resource — without the victim's mainnet consent. This constitutes **unauthorized transaction execution and direct theft of user-controlled on-chain assets**.

---

### Likelihood Explanation

The preconditions are realistic:

1. **Same address on multiple networks**: Aptos account addresses are deterministic from public keys, so any account that exists on testnet with the same key pair also exists (or can be created) on mainnet at the same address.
2. **Same sequence number**: Freshly created accounts start at sequence number 0 on every network. A victim who signs a `offer_signer_capability` on testnet at sequence number 0 produces a signature that is immediately replayable on mainnet if their mainnet account is also at sequence number 0.
3. **Signature exposure**: The signature is submitted as a public transaction argument on testnet, visible to any observer.
4. **No additional secret required**: The attacker only needs to observe the testnet transaction and resubmit it on mainnet with the same arguments.

---

### Recommendation

Add `chain_id` to `SignerCapabilityOfferProofChallengeV2`, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,              // add this field
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

And populate it in `offer_signer_capability`:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

This is a breaking change to the signed message format; existing off-chain signers must be updated. A struct version bump (V3) may be preferable to avoid silent incompatibility.

---

### Proof of Concept

**Setup**: Alice has the same Ed25519 key pair on both testnet and mainnet. Both accounts are at sequence number 0. Attacker (Bob) wants to gain signer capability over Alice's mainnet account.

**Step 1 – Observe testnet**: Alice legitimately calls `offer_signer_capability` on testnet, granting Charlie signer capability. The transaction is public; Bob records `signer_capability_sig_bytes`, `account_public_key_bytes`, and `recipient_address` (Charlie's address, or Bob substitutes his own if he can trick Alice into signing for him).

**Step 2 – Replay on mainnet**: Bob submits an identical `offer_signer_capability` transaction on mainnet:

```
account::offer_signer_capability(
    alice_signer,                  // Alice's mainnet signer (Bob submits as Alice)
    signer_capability_sig_bytes,   // copied verbatim from testnet tx
    0,                             // ED25519_SCHEME
    alice_public_key_bytes,        // same key, same address
    bob_address                    // Bob designates himself as recipient
)
```

**Step 3 – Verification passes**: `verify_signed_message` reconstructs `SignerCapabilityOfferProofChallengeV2 { sequence_number: 0, source_address: alice_addr, recipient_address: bob_addr }`. Because `chain_id` is absent, the BCS-serialized bytes are identical to the testnet-signed message. The signature verifies. [5](#0-4) 

**Step 4 – Capability granted**: `account_resource.signer_capability_offer.for` is set to Bob's address on mainnet. Bob calls `create_authorized_signer(&bob, alice_addr)` and obtains a signer for Alice's mainnet account, enabling full asset theft.

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
