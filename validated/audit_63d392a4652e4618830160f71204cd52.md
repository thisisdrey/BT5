### Title
Unauthorized NAV Manipulation via Mid-Cycle Calculator Configuration Update - ([File: tare-io__tare-contracts/contracts/NavCalculator.sol])

### Summary
The `NavCalculator` allows the `CALCULATING_AGENT` to update valuation factors (discount factors and portfolio factors) while a `PortfolioVault` NAV computation is in progress. Although the vault restarts its computation if it detects a configuration change between batches, it does not prevent the agent from changing factors multiple times or timing updates to bias the final `lastNav`. Because `approveDeposit` and `approveRedemption` rely on the `lastNav` finalized at the end of a cycle, an attacker (or malicious agent) can manipulate the share price by shifting factors between the start and end of a paginated NAV update.

### Finding Description
The `PortfolioVault` computes NAV by paginating through its loan portfolio using `updateNav`. At the start of a cycle, it snapshots the `calculator.configurationVersion()` [1](#0-0) . If the version changes mid-cycle, the vault restarts the computation [2](#0-1) . 

However, the `NavCalculator` functions `setDiscountFactor` and `setPortfolioFactor` do not check if a vault NAV computation is currently idle [3](#0-2) . A `CALCULATING_AGENT` can:
1. Wait for the vault manager to start `updateNav`.
2. Update factors to a "high" value.
3. Allow the vault to finish several batches.
4. Update factors to a "low" value just before finalization.

Because the vault only checks for version consistency at the *start* of each `updateNav` call [4](#0-3) , if the agent updates the factor and the manager calls `updateNav` again, the cycle restarts. But if the agent updates factors *after* the final batch is processed but *before* the finalization logic in the same transaction (or if the agent is the one calling `updateNav`), they can ensure the `pendingNav` (sum of individual loans) is calculated with one set of factors while the `applyPortfolioAdjustment` (final multiplier) uses a different, newly updated factor.

More critically, since `applyPortfolioAdjustment` is a `view` call used during finalization [5](#0-4) , and it reads the *current* `portfolioFactor` [6](#0-5) , any update to the factor immediately affects the finalization of an in-progress cycle if that update happens in the same block or just before the final batch call.

### Impact Explanation
This leads to material corruption of the vault's NAV. An unprivileged or malicious actor with `CALCULATING_AGENT` permissions (or a compromised agent key) can artificially inflate or deflate the share price. This results in unfair minting (cheaper shares for depositors) or unfair redemptions (inflated value for redeemers), directly extracting value from honest shareholders or the protocol's shared state.

### Likelihood Explanation
The protocol relies on a "single entity assumption" and trusted roles, but the `CALCULATING_AGENT` is a distinct role from the `PORTFOLIO_MANAGER`. The lack of a "lock" or "idle-check" on the calculator side allows for race conditions or intentional timing attacks during the multi-block `updateNav` process.

### Recommendation
Add a check in `NavCalculator` to ensure that no vault is currently in the middle of a NAV computation before allowing factor updates. Alternatively, the `PortfolioVault` should pass the snapshotted `configurationVersion` to the calculator, and the calculator should revert if the version has changed.

### Proof of Concept
1. `PortfolioVault` has 100 loans. Manager calls `updateNav(50)`. `navStart` is set, `lastCalculatorConfigurationVersion` is snapshotted as `1`.
2. `CALCULATING_AGENT` calls `setPortfolioFactor(2e18)` (2x multiplier). `configurationVersion` becomes `2`.
3. Manager calls `updateNav(50)`. The vault detects `currentConfigurationVersion (2) != lastCalculatorConfigurationVersion (1)`, restarts the cycle, and snapshots version `2`.
4. Manager calls `updateNav(50)` (first 50 loans). `pendingNav` accumulates values using `discountFactors` at version `2`.
5. `CALCULATING_AGENT` calls `setPortfolioFactor(1e18)` (1x multiplier) in the same block as the final `updateNav` or just before it.
6. Manager calls `updateNav(50)` (last 50 loans). The loop finishes. The vault calls `calculator.applyPortfolioAdjustment(pendingNav)`. 
7. Even though the individual loans were valued while the agent intended a 2x adjustment, the final adjustment uses the new 1x factor, or vice versa, leading to a mismatched and corrupted `lastNav`.

  function setMaxPortfolioFactor(uint256 newMax) external onlyRole(GUARDIAN_ROLE) {
    maxPortfolioFactor = newMax;
    emit MaxPortfolioFactorUpdated(newMax);

    // Clamp current portfolio factor if it now exceeds the new cap.
    if (portfolioFactor > newMax) {
      portfolioFactor = newMax;
