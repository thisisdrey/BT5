## Analog Found: Maximum Concurrent QUIC Stream Cap Bypassed via RTT Scaling

### Title
Stake-Weighted QUIC Stream Cap Bypassed by Client-Influenced RTT Scaling - (`streamer/src/nonblocking/swqos.rs`)

### Summary
`compute_max_allowed_uni_streams_with_rtt()` computes a per-connection maximum for concurrent unidirectional QUIC streams. It first derives a stake-scaled `streams` value and explicitly `.clamp()`s it to the documented hard caps `QUIC_MAX_STAKED_CONCURRENT_STREAMS` (512) or `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` (128). It then multiplies that already-capped value by an RTT-derived scaling ratio that can exceed 1, and returns the result without re-clamping — allowing the effective concurrent-stream limit set on the connection to exceed the intended maximum by up to 7x.

### Finding Description
The function is defined as: [1](#0-0) 

The `streams` value is bounded via `.clamp(QUIC_MIN_STAKED_CONCURRENT_STREAMS, QUIC_MAX_STAKED_CONCURRENT_STREAMS)` for staked peers, or fixed to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` for unstaked peers — these constants are documented as the enforced maximum ("Set the maximum concurrent stream numbers to avoid excessive streams") [2](#0-1) .

However, the final line then scales this already-capped value by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS`, where `REFERENCE_RTT_MS = 50` and `MAX_RTT_MS = 350` [3](#0-2) . When `rtt_millis` exceeds 50ms, this ratio exceeds 1 (up to 7x at the 350ms clamp), so the returned value can be as large as `512 * 7 = 3584` for staked peers or `128 * 7 = 896` for unstaked peers — far beyond the caps that were just enforced two lines earlier.

The project's own test explicitly documents this behavior as intended: "Max streams should scale with BDP in high-RTT connections" [4](#0-3) , confirming the constants named `QUIC_MAX_*_CONCURRENT_STREAMS` are not actually enforced as a hard cap on the returned/applied value — mirroring the reported bug class where `getMaxBorrowRate()` declares a cap that `calculateInterestRates()` can exceed via a multiplicative factor greater than 1.

The returned value is passed directly into `connection.set_max_concurrent_uni_streams(max_uni_streams)`, which configures the QUIC transport parameter controlling how many concurrent unidirectional streams the remote peer is allowed to open on that connection: [5](#0-4)  RTT is derived from `connection.rtt()`, an unprivileged, client-influenceable QUIC-level measurement, clamped only at the call site to `MAX_RTT_MS`: [6](#0-5) 

### Impact Explanation
Any unprivileged client establishing a QUIC/TPU connection (staked or unstaked) that appears to have an elevated round-trip time — whether via genuine network distance or by artificially delaying its own handshake/ack responses — can cause the server to grant substantially more concurrent unidirectional streams than the constants `QUIC_MAX_STAKED_CONCURRENT_STREAMS`/`QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` are meant to permit. Since stream count directly bounds per-connection concurrency in the packet-receiving pipeline (validator TPU/QUIC streamer), this represents a QoS-limit evasion: a client can consume up to ~7x more concurrent stream resources than the validator's designed cap allows, increasing exposure to resource exhaustion from a single peer in the packet ingestion path.

### Likelihood Explanation
Any client connecting to the TPU QUIC endpoint controls this path — no special stake or validator role is required (both staked and unstaked peer branches are affected). Inflating perceived RTT toward the network-observed maximum is a low-effort action for a remote client and does not require malicious packet crafting, satisfying the "unprivileged-user reachable" and "QoS evasion" criteria.

### Recommendation
Re-clamp the RTT-scaled result to the same `QUIC_MIN_STAKED_CONCURRENT_STREAMS`/`QUIC_MAX_STAKED_CONCURRENT_STREAMS` (or `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`) bounds after applying the RTT multiplier, so the documented maximum is actually the maximum returned by `compute_max_allowed_uni_streams_with_rtt()`. Alternatively, clarify whether BDP-scaling is intended to override the stated caps and rename/document the constants accordingly (mirroring the report's recommendation to either enforce the cap or remove it).

### Proof of Concept
1. A client (staked or unstaked) opens a QUIC connection to the TPU streamer.
2. The client delays its handshake responses (or is naturally distant) such that `connection.rtt()` reports a value near `MAX_RTT_MS` (350ms).
3. `setup_connection` → `cache_new_connection` computes `rtt_millis = min(observed_rtt, 350)` and calls `compute_max_allowed_uni_streams_with_rtt(350, peer_type, total_stake)`.
4. For an unstaked peer: `streams = QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS (128)`; final result = `128 * 350 / 50 = 896`, applied via `connection.set_max_concurrent_uni_streams(896)` — 7x the documented max of 128. [5](#0-4)

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
