## Finding: Missing length validation before array-index cast in `ValidateMultiSign` precompile

### Title
Unvalidated buffer length before `DataWord[]` cast/indexing in TVM `ValidateMultiSign` precompile causes uncaught exception - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`ValidateMultiSign.execute()` casts the raw calldata buffer into a `DataWord[]` via `DataWord.parseArray(rawData)` and then unconditionally indexes `words[0]`, `words[1]`, `words[2]`, `words[3]` before any length check or try/catch guard, mirroring the `tb_xdp_handle_request()` pattern in the report: a buffer is type-cast/indexed against an assumed minimum size that is never actually verified.

### Finding Description
`DataWord.parseArray` simply slices the input into `data.length / WORD_SIZE` words with no minimum-size enforcement: [1](#0-0) 

`ValidateMultiSign.execute()` calls this on the raw calldata and, only *if* `VMConfig.allowTvmOsaka()` is active, runs `isValidAbiEncoding` to size-check the buffer beforehand: [2](#0-1) 

When that fork flag is not active (or on any deployment/testnet where it hasn't been enabled), the guard is skipped entirely and `words[0]` through `words[3]` are dereferenced with no bound check. Any calldata shorter than 4 words (128 bytes) makes `words.length < 4`, so accessing `words[3]` (line 1067) throws `ArrayIndexOutOfBoundsException`. Critically, this indexing happens **outside** the `try { ... } catch (Throwable t)` block that only wraps the later permission/weight logic (lines 1082-1117) — so the exception is not caught by the contract's own defensive code at all.

This is a direct structural analog of the CVE: a peer/caller-controlled buffer is cast to a fixed-size structure (`DataWord[]`) and indexed at offsets implying a minimum size, without validating that the buffer actually contains enough data, causing an out-of-bounds access.

Notably, the sibling function `BatchValidateSign.execute()` — which has the identical `words[0..2]` indexing pattern — was hardened with an explicit `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }` wrapper: [3](#0-2) 

`ValidateMultiSign` was never given the same defensive wrapper, indicating the class of bug was known/fixed in one precompile but left open in the other.

### Impact Explanation
`ValidateMultiSign` is a fixed-address TVM precompiled contract reachable by any smart contract (and therefore by any unprivileged transaction broadcaster deploying/calling a contract) that performs a `CALL`/`STATICCALL` to it with attacker-chosen calldata. A single crafted call with calldata shorter than 128 bytes triggers an uncaught `ArrayIndexOutOfBoundsException` inside precompile execution, which is not handled by the contract's own logic. Because I could not fully verify (tool budget exhausted) exactly how the outer TVM/`Program` call-dispatch layer treats a raw uncaught `RuntimeException` thrown from a precompiled contract's `execute()`, I cannot confirm with certainty whether this propagates all the way to abort block application (node halt) versus being caught generically by the VM's top-level exception handling and only reverting the single call frame. If it is caught generically (as is typical for most EVM/TVM implementations wrapping opcode execution in try/catch around `Program.Exception`/`Throwable`), the practical impact is bounded to a deterministic, gas-consuming revert for that transaction — a much lower severity than the CVE's OOB read. If any code path in block application does not fully guard against arbitrary `RuntimeException` from a precompile (unlike `BatchValidateSign`, which had to be defensively patched), this becomes a chain-wide DoS vector triggerable by a single transaction from an anonymous caller.

### Likelihood Explanation
High reachability: no privileged role is required, only the ability to broadcast a transaction that calls the `ValidateMultiSign` precompile with short calldata. The condition is trivial to trigger and is gated only by the `allowTvmOsaka` config/fork flag, which may not be enabled on all networks/branches.

### Recommendation
Add an explicit minimum-length check on `rawData` (e.g., `rawData.length < ABI_HEADER_WORDS * WORD_SIZE` or `words.length < 4`) before any `words[i]` access in `ValidateMultiSign.execute()`, independent of the `allowTvmOsaka` flag, and wrap the whole method body in the same defensive `try/catch(Throwable)` pattern used in `BatchValidateSign.execute()` so any parsing failure degrades to `Pair.of(true, DATA_FALSE)` rather than propagating an uncaught exception.

### Proof of Concept
1. Deploy/call a contract that issues a low-level `staticcall`/`call` to the `ValidateMultiSign` precompile address with calldata shorter than 128 bytes (e.g., 32 bytes, only encoding an address word).
2. On a chain/branch where `allowTvmOsaka` is not active, execution reaches `DataWord.parseArray(rawData)` producing `words.length == 1`.
3. `words[1].intValueSafe()` (line 1059) or `words[3].intValueSafe()` (line 1067) throws `ArrayIndexOutOfBoundsException`, outside the method's own `try/catch`, before any signature/permission logic executes. [4](#0-3)

  public static DataWord[] parseArray(byte[] data) {
    int len = data.length / WORD_SIZE;
    DataWord[] words = new DataWord[len];
    for (int i = 0; i < len; i++) {
      byte[] bytes = Arrays.copyOfRange(data, i * WORD_SIZE, (i + 1) * WORD_SIZE);
      words[i] = new DataWord(bytes);
    }
    return words;
  }
