### Title
Cross-StackerDB-contract chunk replay due to missing contract/message-type binding in `SlotMetadata::auth_digest` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the value a signer signs as `H(slot_id || slot_version || data_hash)`, omitting any binding to the specific StackerDB smart contract (or message type) the chunk is destined for. [3](#0-2)  Because the Nakamoto signer set assigns the *same* slot_id → signer-address mapping to every `MessageSlotID` contract within a reward-cycle parity (`BlockResponse`, `StateMachineUpdate`, `BlockPreCommit` all read from the same `stackerdb-get-signer-slots-page`), a chunk validly signed by a signer for one message-type contract remains a validly-signed chunk for any other message-type contract at the same slot_id/version. [2](#0-1) [4](#0-3) 

### Finding Description
`validate_received_chunk()` (used both for downloaded chunks and for unsolicited pushed chunks) resolves the expected signer strictly from `smart_contract_id` + `slot_id` via `get_slot_signer`, then calls `slot_metadata.verify(&addr)`, which only checks that the signature recovers to `addr` over `auth_digest() = H(slot_id, slot_version, data_hash)`. [5](#0-4)  The digest itself never incorporates `smart_contract_id`, so the same `(sig, slot_id, slot_version, data)` tuple, honestly produced by a signer for e.g. the `BlockResponse` contract, is *also* a valid, correctly-signed chunk for the `StateMachineUpdate` or `BlockPreCommit` contract of the same reward-cycle parity, since those contracts share the identical slot_id→signer mapping. `StackerDBChunkData::verify`/`SlotMetadata::verify` do not take the contract id into account at all. [6](#0-5) 

This is the exact same class of bug as the reported issue: an authorization primitive (leaf hash / signed digest) omits the “domain”/identity value (hook address ↔ StackerDB contract id/message type) that is supposed to scope what the credential is valid for, allowing a valid credential produced for one domain to be replayed into a semantically different one.

An unprivileged network peer that observes any legitimately-broadcast, validly-signed StackerDB chunk (all StackerDB chunk traffic is unauthenticated-to-read and gossiped/pushable by any peer) can take that `(slot_id, slot_version, sig, data)` tuple and push/POST it as a chunk for a *different* message-type contract of the same reward-cycle parity, either via `handle_unsolicited_StackerDBPushChunk` P2P path or via the `POST /v2/stackerdb/.../chunks` RPC endpoint, both of which ultimately call the same signature-verification logic. [7](#0-6) [8](#0-7)  As long as the target contract's current slot version is lower than the replayed version (or write-count rules otherwise permit it), the write is accepted, and the wrong-message-type payload (e.g. serialized `BlockResponse` bytes) gets stored as though it were canonical content of the target contract's slot (e.g. `StateMachineUpdate`), because insertion is authenticated per-slot using `get_slot_signer`/`insert_chunk` without any check that the signature was actually produced for this contract. [9](#0-8) 

### Impact Explanation
This lets a remote, unprivileged peer replicate/replay authentic-but-wrong-context data into a StackerDB contract that consumers treat as canonical for a specific message type (e.g. signer `StateMachineUpdate` state, consumed by `InitialChunksLoader`/`StackerDBListener` to seed miner-side signer state). [10](#0-9)  Depending on how downstream consumers parse the stored bytes (`SignerMessage` deserialization by `msg_id`), this can serve non-canonical/forged-context data as canonical in a slot that other nodes and the miner poll and trust, satisfying the "serving non-canonical state as canonical" / "forged-data propagation" bar for High severity. It does not itself forge new signer content (the attacker cannot alter the bytes without breaking the signature/hash), but it can confuse or poison per-message-type application state across contracts sharing a signer set, and can be used to overwrite/version-bump slots in unintended contracts using replayed traffic the attacker merely observed.

### Likelihood Explanation
High likelihood: the required inputs (a validly signed chunk for any message-type StackerDB contract in the current reward cycle) are broadcast in the clear over the p2p StackerDB gossip/push and are also fetchable via the public read RPC endpoints; no private key or elevated privilege is needed by the attacker, only re-submission of already-observed, correctly-signed data to a different contract path.

### Recommendation
Bind the `smart_contract_id` (or at minimum the reward-cycle + message-type index) into the value that is signed, analogous to including `hookAddress` in the leaf hash in the original report. Concretely, change `SlotMetadata::auth_digest()` to hash in the target smart-contract identifier (e.g. `hasher.update(smart_contract_id.serialize_to_vec())`) in addition to `slot_id`, `slot_version`, and `data_hash`, and thread the contract id through `sign()`/`verify()`/`auth_digest()`. This requires updating `StackerDBChunkData`, `SlotMetadata`, and all call sites (`stackslib/src/net/stackerdb/mod.rs`, `stackslib/src/net/stackerdb/db.rs`, `libstackerdb/src/libstackerdb.rs`, signer client code in `stacks-signer/`) to pass the contract id, and is a wire-format-affecting/consensus-affecting change requiring coordinated versioning.

### Proof of Concept
1. Observe (via P2P StackerDB push, sync, or the public `GET /v2/stackerdb/<contract>/<slot>/<version>` RPC) a validly signed chunk `(slot_id=S, slot_version=V, sig, data)` written by signer key `K` into `signers-0-1` (`BlockResponse`) for reward cycle `R`.
2. Because `signers-0-1`, `signers-0-2`, and `signers-0-3` all derive their slot list from the same `.signers` contract page for parity `R % 2`, signer `K` also owns slot `S` in `signers-0-2` (`StateMachineUpdate`).
3. Submit the same `(slot_id=S, slot_version=V', sig, data)` (with `V'` ≥ current version in `signers-0-2`) to `signers-0-2` via `POST /v2/stackerdb/<signers-0-2 contract>/chunks` or via an unsolicited `StackerDBPushChunk` P2P message.
4. `validate_received_chunk`/RPC handler resolves signer for `(signers-0-2, S)` = `K`, calls `slot_metadata.verify(&addr)`, which succeeds because `auth_digest()` never referenced `signers-0-1`; the chunk (raw `BlockResponse` bytes) is accepted and stored under `signers-0-2`'s slot `S`, even though it was never signed for that contract.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
