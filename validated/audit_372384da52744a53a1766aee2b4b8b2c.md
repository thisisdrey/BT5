### Title
Disabling `ALLOW_SHIELDED_TRANSACTION` via committee proposal permanently locks TRX already deposited in the shielded pool - ([File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java])

### Summary
`ShieldedTransferActuator` is the single actuator used for **every** shielded-pool operation: depositing transparent TRX into the pool, transferring value between shielded notes, and withdrawing (unshielding) value back to a transparent address. Its `validate()` method gates all of these operations behind one global committee-controlled switch, `dynamicStore.supportShieldedTransaction()`. Because deposit and withdrawal share the exact same actuator and the exact same gating flag, disabling the flag after users have deposited funds makes it impossible for them to ever withdraw those funds again — the same bug class as the reported UXDController issue, where a single whitelist check governs both entry (mint) and exit (redeem) of value.

### Finding Description
`ShieldedTransferActuator.validate()` unconditionally requires the flag to be enabled before allowing the transaction to proceed, regardless of transaction direction: [1](#0-0) 

The same `ShieldedTransferContract` message type (and hence the same actuator/validate path) is used to move value in either direction — from a transparent address into the shielded pool, and from the shielded pool back out to a transparent address — as seen in `executeTransparentFrom`/`executeTransparentTo` and the total pool value accounting: [2](#0-1) 

The switch `ALLOW_SHIELDED_TRANSACTION` is set via a normal governance proposal processed in `ProposalService`, and `DynamicPropertiesStore.saveAllowShieldedTransaction`/`supportShieldedTransaction()` simply stores/reads this flag with no distinction between "new deposits" and "withdrawal of already-shielded funds." A test confirms that once the flag is `0`, any `ShieldedTransferContract` transaction (including what would be a withdrawal) fails identically with "Not support Shielded Transaction, need to be opened by the committee": [3](#0-2) 

Because zk-SNARK shielded notes are unlinkable and the pool total is tracked only in aggregate (`getTotalShieldedPoolValue`), there is no alternate path to redeem or spend the notes once `ALLOW_SHIELDED_TRANSACTION` is turned off — every spend must go through this same actuator and the same check.

### Impact Explanation
If the witness committee (via `UpdateBrokerageActuator`/`ProposalApproveActuator`/`ProposalCreateActuator` governance flow feeding into `ProposalService`) ever disables shielded transactions — for example, in response to a vulnerability in the zk-SNARK circuit, a compliance/regulatory requirement, or a discovered exploit — any TRX that users have already deposited into the shielded pool becomes permanently unspendable. This is a genuine, permanent freezing-of-funds condition: legitimate users lose access to their TRX with no on-chain recovery mechanism, since the same flag and same actuator path gate both the deposit and withdrawal legs of the shielded pool.

### Likelihood Explanation
This requires only a standard committee proposal to flip `ALLOW_SHIELDED_TRANSACTION` back to `0` (a plausible administrative action, e.g., in emergency response), combined with any user having previously and legitimately deposited TRX into the shielded pool while the feature was enabled — an ordinary sequence of events, not an attack requiring malicious SRs or privileged compromise beyond routine governance.

### Recommendation
Do not gate withdrawal/spend operations on `ALLOW_SHIELDED_TRANSACTION`. Split the check so that only deposits (transparent → shielded) are blocked when the switch is off, while spends/withdrawals that consume existing shielded notes and reduce `TotalShieldedPoolValue` remain permitted regardless of the switch state — mirroring the recommended fix in the source report of only gating the "mint" side and never the "redeem" side of the same whitelist/switch.

### Proof of Concept
1. Committee approves `ALLOW_SHIELDED_TRANSACTION = 1`.
2. User A broadcasts a `ShieldedTransferContract` depositing TRX from a transparent address into a shielded note (`executeTransparentFrom`, increasing `TotalShieldedPoolValue`).
3. Committee approves a new proposal setting `ALLOW_SHIELDED_TRANSACTION = 0`.
4. User A now attempts to spend that shielded note back to a transparent address via a new `ShieldedTransferContract`; `ShieldedTransferActuator.validate()` immediately throws `"Not support Shielded Transaction, need to be opened by the committee"` as shown in `testCreateBeforeAllowZksnark`/`testBroadcastBeforeAllowZksnark`, permanently blocking withdrawal of the already-deposited TRX.
