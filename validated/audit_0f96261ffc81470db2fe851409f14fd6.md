I have enough evidence to write up this finding now. This confirms the vulnerability I identified: `handleCreateRelayRequest` in `relay_manager.go` never validates that the attacker-supplied `RelayFromAddr` field in the `NebulaControl` message matches the authenticated `vpnAddrs` of the `HostInfo` (`h`) that the message actually arrived over. It only checks that `from` is not one of *my own* addresses, and never checks it against `h.vpnAddrs`, the cryptographically-verified peer identity established during the handshake.

### Title
Relay registration trusts unauthenticated `RelayFromAddr` field instead of the handshake-verified peer identity - (File: relay_manager.go)

### Summary
`handleCreateRelayRequest` builds relay state (`TerminalType` on the target side, `ForwardingType`/`PeerRequested` on the middle-hop side) keyed by the `RelayFromAddr` value taken directly out of the incoming `NebulaControl` message, without ever checking that this value matches the vpn address(es) of the `HostInfo h` the message was decrypted from. `h.vpnAddrs` is the only value whose identity is backed by the Noise handshake and certificate verification (`validatePeerCert`); `RelayFromAddr` is attacker-controlled plaintext-of-intent inside an otherwise-authenticated control message, analogous to trusting a user-supplied address parameter over the verified caller identity, as in the referenced Solidity bug where `msg.sender` (verified) should have been used instead of blindly trusting an unrelated field.

### Finding Description
In `relayManager.HandleControlMsg` ( [1](#0-0) ), a `NebulaControl` message decoded from `d` is only checked for non-nil `RelayFromAddr`/`RelayToAddr`, then dispatched to `handleCreateRelayRequest(v, h, f, msg)`. The `h *HostInfo` parameter is the tunnel the packet was decrypted on — its `vpnAddrs` field is the caller's cryptographically verified identity, set only after a successful Noise handshake and `validatePeerCert` check ( [2](#0-1) , [3](#0-2) ).

In `handleCreateRelayRequest` ( [4](#0-3) ), `from` is decoded straight from the message body:
```go
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(from) {
    logMsg.Error("Discarding relay request from myself", "myIP", from)
    return
}
```
The only guard is that `from` isn't one of *my own* addresses. There is no check that `from` is one of `h.vpnAddrs` — i.e., that the peer claiming to be `from` is actually the authenticated peer that opened tunnel `h`. Every legitimate call site that emits `RelayFromAddr` always sets it to the sender's own certified address ( [5](#0-4) , [6](#0-5) ), confirming `RelayFromAddr` is *intended* to always equal the authenticated sender's identity — but the receiver never enforces this invariant.

As a result, when `f.myVpnAddrsTable.Contains(target)` is true (I am the relay's terminal endpoint), the code installs relay state keyed by the attacker-chosen `from` value ( [7](#0-6) ) — `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)` and `h.relayState.QueryRelayForByIp(from)` — even though the packet actually arrived from the authenticated peer `h`, whose real identity is `h.vpnAddrs`, not necessarily `from`. Likewise, in the "I am a forwarding relay" branch, `AddRelay(rm.l, peer, f.hostMap, from, ...)` ( [8](#0-7) ) stores `from` as the `PeerAddr` used later by `handleOutsideRelayPacket`'s `ForwardingType` case to decide where to forward relayed traffic ( [9](#0-8) ).

### Impact Explanation
A peer with a valid, authenticated tunnel `h` (any legitimate Nebula node) can impersonate a different vpn address in `RelayFromAddr` when requesting relay service. This lets an authenticated-but-malicious peer register itself as the terminal/forwarding endpoint for a `from` address it does not own, poisoning the relay's `relayForByAddr`/`relayForByIdx` state (remote state poisoning) for a victim address it never established a tunnel for. Depending on downstream routing via `QueryVpnAddrsRelayFor`/`handleOutsideRelayPacket`, this can misdirect or intercept relayed traffic nominally addressed to/from the impersonated `vpnAddr`, undermining the intended one-relay-per-authenticated-identity invariant that the relay protocol relies on.

### Likelihood Explanation
Likelihood is medium: it requires the attacker to already hold a valid certificate and complete a normal handshake as any peer (no special privilege), then simply send a `CreateRelayRequest` with a `RelayFromAddr` different from its own certified address to a node acting as relay (`am_relay: true`) or as the terminal target. This is a single crafted control message on an already-established, authenticated tunnel — no certificate forgery or lighthouse manipulation is needed.

### Recommendation
In `handleCreateRelayRequest`, validate that `from` is contained in `h.vpnAddrs` (the authenticated identity of the sender) before using it to install or update relay state; reject the request (as is already done for `f.myVpnAddrsTable.Contains(from)`) if `from` does not match one of `h.vpnAddrs`.

### Proof of Concept
1. Node A and Node B complete a normal Nebula handshake so that Node A holds a `HostInfo h` for Node B with `h.vpnAddrs = [B_addr]`.
2. Node B (or a node impersonating B on this authenticated tunnel) sends `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: V_addr, RelayToAddr: A_addr}` where `V_addr` is some third victim node's certified vpn address, unrelated to `h.vpnAddrs`.
3. `HandleControlMsg` decodes the message and calls `handleCreateRelayRequest(v, h, f, msg)`; since `f.myVpnAddrsTable.Contains(target)` is true and `from = V_addr` is not `f`'s own address, the code proceeds to call `AddRelay(rm.l, h, f.hostMap, V_addr, &m.InitiatorRelayIndex, TerminalType, Established)`, registering relay state on `h` keyed by `V_addr` even though the packet actually came from `B`, not `V`.
4. Node A now believes it has a valid, `Established` relay entry for `V_addr` reachable via tunnel `h`, despite never having verified that `B` is authorized to speak on behalf of `V`.

	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		v = cert.Version2
	}

			}

				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
