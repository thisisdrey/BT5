### Title
Dust-transfer griefing of `depositTokensOfAccount`/`debtTokensOfAccount` blocks a victim from adding new collateral or debt positions - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` maintains two per-account enumerable sets — `depositTokensOfAccount` and `debtTokensOfAccount` (PoolStorageV1, contracts/storage/PoolStorage.sol) — whose combined length is capped at `MAX_TOKENS_PER_USER = 30`. Entries are added through `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`, which are callable only by registered token contracts but accept an arbitrary `account_` parameter. When a `DepositToken` (or `DebtToken`) moves an account's balance from zero to positive — including via an unsolicited `transfer` of dust — it calls `addToDepositTokensOfAccount(victim)`, and `onlyIfAdditionWillNotReachMaxTokens` reverts with `UserReachedMaxTokens` once the combined count hits 30. An unprivileged attacker can therefore fill a victim's list by sending them dust amounts of every registered deposit token, after which any further token-addition for that account reverts.

### Finding Description
- `MAX_TOKENS_PER_USER` is a hard cap of 30 shared across debt + deposit tokens (`contracts/Pool.sol:79`, `:143-148`).
- `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` verify only that `msg.sender` is a registered token; the `account_` argument is attacker-controllable via a plain ERC20 `transfer` to the victim (`contracts/Pool.sol:204-220`).
- `addDepositToken` itself caps the pool at `MAX_TOKENS_PER_USER` deposit tokens (`contracts/Pool.sol:703`), so on a pool with enough listed collaterals the attacker can fill most or all of the cap using worthless dust.
- Once the victim's set is full, the modifier causes a revert on: (a) `DepositToken` mint/transfer paths that would register a *new* collateral type for the victim (blocking deposits of collateral types not already held), and (b) `DebtToken.issue`/`mint` for any synthetic the victim doesn't already hold (blocking new borrowing), since issuance calls `addToDebtTokensOfAccount`.
- The situation mirrors the whitelist-queue DoS: a bounded, append-only list writable via public token transfers, with no fee and no slashing, where eviction (the victim transferring dust out to zero the balance) can be re-griefed by the attacker re-dusting in the same or next block.

### Impact Explanation
Temporary freezing of funds / liveness: the victim cannot open positions in any collateral or synthetic type not already in their set while the attacker's dust persists. Existing positions remain liquidatable and withdrawable for already-listed tokens, so the impact is a temporary, per-victim DoS rather than theft or insolvency. It is most damaging when combined with liquidation timing (e.g., blocking a victim from depositing a different collateral type to restore health), though existing collateral can still be topped up.

### Likelihood Explanation
Requires only an unprivileged EOA holding dust of each registered `DepositToken` (obtainable by depositing minimal underlying). Cost is gas only; no quorum, privilege, or oracle manipulation is needed. Effectiveness depends on the number of listed deposit+debt tokens approaching 30; note `addDepositToken` caps deposit tokens at 30, so whether the attacker alone can fully saturate the combined cap depends on how many deposit tokens exist on the deployed configuration — with fewer listed tokens the victim's headroom may not be exhaustible by transfers alone. This dependency limits severity on pools with few listings.

### Recommendation
- Do not register tokens for an account on inbound `transfer`; only add on explicit `deposit`/`mint` initiated by the account, or make registration opt-in.
- Alternatively, drop the `MAX_TOKENS_PER_USER` cap by iterating lazily (e.g., computing `debtPositionOf`/`depositOf` over the global token lists filtered by nonzero balance) or raising/removing the shared cap so dust griefing cannot saturate it.

### Proof of Concept
A Foundry/Hardhat fork test: (1) enumerate `pool.getDepositTokens()`; (2) attacker deposits 1 wei of underlying into each `DepositToken` to obtain dust shares; (3) attacker calls `depositToken.transfer(victim, 1)` for each token until `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`; (4) victim attempts `deposit` into a not-yet-held collateral or `DebtToken.issue` of a new synthetic — the inner `addTo*TokensOfAccount` call reverts with `UserReachedMaxTokens`. Victim's only recovery is transferring dust out (triggering `removeFromDepositTokensOfAccount`), which the attacker can front-run with fresh dust.
