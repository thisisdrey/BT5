### Title
Replay-window check/update race in `ConnectionState.Decrypt`/`VerifyRelay` allows duplicate packet acceptance under concurrent delivery - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both call `cs.window.Check()` and, after decrypting, `cs.window.Update()` as two *separate* locked critical sections rather than a single atomic check-and-set. Between the `Check` and the `Update`, the lock is released while the (comparatively expensive) AEAD decrypt runs. This is structurally the same bug pattern as the Gondi finding: two logically-coupled checks over one piece of mutable state (there: `_loan.startTime+_loan.duration` vs. `block.timestamp`; here: `Bits.current`/bitmap state at `Check`-time vs. `Update`-time) are evaluated non-atomically, so an attacker who can trigger two decrypt calls for the same message counter concurrently can slip both through the `Check` before either `Update` commits the counter as seen.

### Finding Description
`cs.window` is a `*Bits` anti-replay sliding-window tracker (`bits.go`). `Decrypt` does:
```go
cs.decryptLock.Lock()
result := cs.window.Check(l, messageCounter)
cs.decryptLock.Unlock()
...
out, err = cs.dKey.DecryptDanger(...)
...
cs.decryptLock.Lock()
result = cs.window.Update(l, messageCounter)
cs.decryptLock.Unlock()
``` [1](#0-0) 

`VerifyRelay` follows the identical pattern. [2](#0-1) 

`Check` and `Update` are individually locked, but the pair is not atomic: the lock is dropped in between so the AEAD `DecryptDanger` call runs outside the lock. `Bits.Check` only reads state (`bits.go` lines 135-150) and `Bits.Update`/`updateSlow` is the only place that mutates the bitmap and marks a counter as "seen" (`bits.go` lines 152-263). [3](#0-2) [4](#0-3) 

If two packets carrying the *same* `messageCounter` (e.g., a duplicated/retransmitted or attacker-replayed UDP datagram, which is trivially producible without any CA-signed certificate — the attacker only needs to capture and resend a ciphertext observed on the wire) are processed by two goroutines calling `readOutsidePackets` → `Decrypt` concurrently, both can execute `Check(messageCounter)` before either has executed `Update(messageCounter)`. Both `Check` calls read the bitmap as "not yet seen" and return `true`, so both proceed to decrypt and both later call `Update`. This is directly analogous to the Gondi bug: the "is this state already consumed" check and the "consume/commit this state" check are split across two separately-guarded steps with attacker-triggerable work (decryption) sandwiched in between, exactly the pattern that let `_baseLoanChecks` and `_liquidateLoan`'s expiry test disagree at the boundary and be exploited by an interleaved second transaction (`addNewTranche`) before the first (`liquidateLoan`) settled.

### Impact Explanation
Successful exploitation causes the anti-replay window to accept and decrypt/process the same message counter twice, defeating the nonce/replay protection that the `Bits` window exists to enforce. Depending on what payload is replayed, this can result in duplicate application of a data-plane packet (double delivery) inside the tunnel, and more importantly demonstrates that the core replay-defense invariant ("a message counter is processed at most once") is not actually enforced atomically, which is the same category of defect ("Remote traffic replay") explicitly called out as acceptable impact in scope.

### Likelihood Explanation
This requires being able to deliver two UDP datagrams carrying the same header/ciphertext to the same peer roughly concurrently (network duplication, attacker replay of a captured packet racing the original, or an on-path attacker duplicating the datagram) and for the receiving process to actually schedule two goroutines/threads to service them concurrently through `readOutsidePackets`. No CA-signed certificate is required to trigger it — the attacker simply needs to observe/capture and resend an already-encrypted UDP packet destined to a nebula node; the vulnerable code path itself doesn't perform any pre-authentication of the sender. Winning the race window (the gap between `Check` and `Update`, spanning one AEAD decrypt) is timing-dependent, so likelihood is moderate rather than trivial, but is architecturally always present, unlike the Gondi bug which required a specific timestamp equality.

### Recommendation
Merge `Check` and `Update` into a single atomic "check-and-mark" operation performed under one continuous lock hold, e.g. add a `Bits.CheckAndUpdate` (or make `Decrypt`/`VerifyRelay` hold `decryptLock` across both the check and the post-decrypt update, deferring the mark until decrypt succeeds but never releasing the lock to another decrypt of the same counter in between), so no other goroutine can observe the "not yet seen" state for the same counter while a decrypt using that counter is in flight.

### Proof of Concept
1. Establish a tunnel between two nebula nodes so `ConnectionState` with an active `window *Bits` exists.
2. Capture one legitimate encrypted data-plane UDP packet with header counter `N`.
3. Send two copies of this exact packet to the receiving node's UDP listener at (near-)the same time from two sockets, so `readOutsidePackets` is invoked concurrently for both, each calling `hostinfo.ConnectionState.Decrypt(f.l, N, ...)` (`outside.go` lines 126-132). [5](#0-4) 
4. Because `Check` and `Update` are separately locked (`connection_state.go` lines 61-82), both goroutines can pass `Check(N)` before either calls `Update(N)`, so both successfully decrypt and process counter `N`, demonstrating the replay window failed to reject the duplicate.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]

	}

	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}

// updateSlow handles jumps, in-window backfill, dupes, and out-of-window.
func (b *Bits) updateSlow(l *slog.Logger, i uint64) bool {
	// If i is a jump, adjust the window, record lost, update current, and return true
	if i > b.current {
		end := i
		if end > b.current+b.length {
			end = b.current + b.length
		}
		count := end - b.current
		startPos := (b.current + 1) & b.lengthMask

		var lost int64
		if b.current >= b.length {
			// Steady state: every cleared slot is past warmup, so any unset
			// bit we evict is a lost packet from the previous cycle.
			wasSet := b.clearRange(startPos, count)
			lost = int64(count) - int64(wasSet)
		} else {
			// Warmup (the very first window). Some cleared slots represent
			// packets <= length where eviction is not "lost" in the usual
			// sense. This branch is taken at most once per connection so we
			// don't bother optimizing it.
			for n := b.current + 1; n <= end; n++ {
				if !b.get(n) && n > b.length {
					lost++
				}
			}
			b.clearRange(startPos, count)
		}

		// Anything past the new window can never be backfilled, so it's lost.
		if i > b.current+b.length {
			lost += int64(i - b.current - b.length)
		}
		b.lostCounter.Inc(lost)

		b.set(i)
		b.current = i
		return true
	}

	// If i is within the current window but below the current counter, check to see if it's a duplicate
	if b.strictlyWithinWindow(i) {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if b.current == i || w&mask != 0 {
			if l.Enabled(context.Background(), slog.LevelDebug) {
				l.Debug("Receive window",
					"accepted", false,
					"currentCounter", b.current,
					"incomingCounter", i,
					"reason", "duplicate",
				)
			}
			b.dupeCounter.Inc(1)
			return false
		}

		b.bits[word] = w | mask
		return true
	}

	// In all other cases, fail and don't change current.
	b.outOfWindowCounter.Inc(1)
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("Receive window",
			"accepted", false,
			"currentCounter", b.current,
			"incomingCounter", i,
			"reason", "nonsense",
		)
	}
	return false
}
