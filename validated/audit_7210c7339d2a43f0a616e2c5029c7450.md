### Title
Single-step Owner Permission Update Can Cause Permanent, Unrecoverable Account Lockout - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` lets an account holder replace its `Owner`, `Witness`, and `Active` permissions in a single transaction with no two-step confirmation. If the new `Owner` permission's keys are mistyped, point to an address the sender does not actually control, or otherwise cannot produce a valid signature, the account's owner rights are irreversibly transferred/lost in one step, exactly the "single-step role transfer" hazard described in the reference report.

### Finding Description
`AccountPermissionUpdateActuator.execute` unconditionally overwrites the account's permissions via `AccountCapsule.updatePermissions` as soon as `validate()` passes: [1](#0-0) 

`validate()` and the `checkPermission` helper only check structural correctness of the new permission (address format via `DecodeUtil.addressValid`, key count, threshold, weight sums) — never that the new owner keys are reachable/controllable by the submitter or any confirming second transaction from the new owner: [2](#0-1) 

`AccountCapsule.updatePermissions` then directly replaces the stored `OwnerPermission` (and Active/Witness permissions) with the submitted values in the same transaction, with no pending/staged state and no acceptance step from the designated keys: [3](#0-2) 

This is the same anti-pattern flagged in the reference report: a rights/role transfer (here, the account's `Owner` permission, which governs control of the whole account including future permission changes and asset movement) is applied atomically and irreversibly based on attacker/user-supplied data, with no verification that the new holder can actually exercise the granted authority.

### Impact Explanation
If the `Owner` permission's key set is set to an address whose private key is unavailable (typo, wrong checksum-passing but uncontrolled address, or an address under threshold that can never collect enough weight), the account permanently loses the ability to ever change its `Owner`, `Active`, or `Witness` permissions again, and depending on the `Active` permission overwrite, can also lose the ability to transfer funds or interact with contracts. This is a full, unrecoverable loss of account control — matching "High" impact ("important protocol functionality would become unusable") from the reference report.

### Likelihood Explanation
Low — it requires the account owner to submit an `AccountPermissionUpdateContract` with an incorrect/unreachable key, i.e., an operator error rather than an externally triggerable exploit. This mirrors the Low likelihood rated in the original report for the analogous `AccountRegistry`/`transferAccount` issue.

### Recommendation
Introduce a two-step confirmation for owner-permission changes: stage the proposed `Owner`/`Active`/`Witness` permission set and require a follow-up transaction signed by (enough weight of) the new key set to confirm and activate it, mirroring the `NodeRegistry` two-step pattern referenced in the original report. At minimum, add an explicit acceptance/acknowledgement step before `AccountCapsule.updatePermissions` commits the new `Owner` permission.

### Proof of Concept
1. Account `A` (controlled by key `K1`) submits an `AccountPermissionUpdateContract` via `AccountPermissionUpdateActuator`, setting `Owner` permission keys to address `X`, where `X` is a validly-formatted address but no one holds the private key for it (e.g., a typo of the intended address).
2. `validate()` passes because `DecodeUtil.addressValid(X)` only checks format/checksum, not key ownership.
3. `execute()` calls `account.updatePermissions(...)`, overwriting the `OwnerPermission` immediately.
4. Account `A` can no longer produce a transaction with sufficient `Owner`-permission signature weight, permanently freezing its ability to update permissions (and, if `Active` was similarly misconfigured, to transfer funds).

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
