### Title
Unauthenticated forged `NewBurnBlock` event injected into signer runloop via `SignerEventReceiver`'s `/new_burn_block` HTTP endpoint - ([File: libsigner/src/events.rs])

### Summary
`SignerEventReceiver::next_event` routes any POST to `/new_burn_block` straight into `process_event::<T, BurnBlockEvent>`, which only JSON-deserializes the body and calls `TryFrom<BurnBlockEvent> for SignerEvent<T>` with no signature, secret, or peer-identity check. Any TCP client that can reach the bound address can therefore inject an attacker-chosen `SignerEvent::NewBurnBlock` into the signer's decision-input channel.

### Finding Description
`SignerEventReceiver::bind()` opens a plain `tiny_http` HTTP server on the configured address with no auth mechanism (`libsigner/src/events.rs:404-408`). `next_event()` dispatches purely on URL path and HTTP method — `/new_burn_block` → `process_event::<T, BurnBlockEvent>(request)` — with no check on the connecting peer, no shared-secret header, and no request signature verification (`libsigner/src/events.rs:437-457`). `process_event` reads the raw body, deserializes it as `BurnBlockEvent` via `serde_json::from_slice`, and converts it via `TryInto<SignerEvent<T>>`, acking the dispatcher regardless (`libsigner/src/events.rs:519-542`). `TryFrom<BurnBlockEvent> for SignerEvent<T>` copies every attacker-supplied field (`burn_block_height`, `burn_block_hash`, `consensus_hash`, `parent_burn_block_hash`) verbatim into `SignerEvent::NewBurnBlock` with no validation against any node-observed state (`libsigner/src/events.rs:637-649`). The event is then unconditionally forwarded to the runloop channel via `forward_event()` (`libsigner/src/events.rs:469-490`), and consumed by `stacks-signer/src/v0/signer.rs` where it is written directly into `signer_db.insert_burn_block(...)` and drives `local_state_machine.bitcoin_block_arrival(...)`, feeding the miner-view/tenure state machine (`stacks-signer/src/v0/signer.rs:629-673`). No field of the HTTP request (source IP, header, body signature) is ever checked against the configured stacks-node's identity, so the claimed identity equality — "every `SignerEvent` delivered to the runloop equals an event the node actually observed" — does not hold anywhere in this path.

### Impact Explanation
An attacker who can open a TCP connection to the signer's event-receiver port can inject an arbitrary, persistent `NewBurnBlock` record into `SignerDB` and drive the signer's `bitcoin_block_arrival`/miner-state-machine logic with forged height/hash/consensus-hash/parent-hash values, repeatable on every connection. This corrupts the signer's local view of the burnchain tip that other consensus checks (sortition, tenure, conflict resolution) rely on, matching "unauthenticated/unauthorized write to state" severity.

### Likelihood Explanation
This is not a defect introduced by a specific logic bug but reflects the general, long-standing design of the Stacks event-observer/webhook pattern (used identically for the node's own event-observer HTTP callbacks): the receiving HTTP server is designed to be reachable only by the specific node it's paired with via config, and operators are expected to keep this port private/firewalled (bound to localhost or an internal network) rather than exposed to arbitrary remote parties. The question's threat model, however, explicitly grants the attacker only the ability to "open a TCP connection to the address `SignerEventReceiver::bind()` listens on" — it does not establish that this address is, or must be, remotely/publicly reachable by an untrusted party in the deployed topology this repo assumes. I could not fully verify from the available index whether `stacks-signer`'s config/documentation restricts this bind address to loopback/trusted-network only by default (config.rs event-server binding code was not retrievable in full within available searches), so I cannot confirm this port is treated as a remotely-reachable, unprivileged-facing surface in this codebase's threat model rather than a trusted-network-only sidecar channel.

### Recommendation
N/A — see uncertainty above; if this endpoint is intended to be reachable across an untrusted network boundary, add a shared-secret/HMAC header check or mTLS between the node and the signer's event receiver before processing `/new_burn_block`, `/new_block`, `/stackerdb_chunks`, and `/proposal_response`.
