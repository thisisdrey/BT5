### Title
Unbounded per-item processing loop over `GetBlobsRequest.revision_paths` allows DoS - (File: internal/gitaly/service/blob/get_blobs.go)

### Summary
`BlobService.GetBlobs` accepts a single, non-streaming request containing a `repeated RevisionPath revision_paths` field with no upper bound on the number of entries, and processes every entry in a single unbroken loop, each iteration performing one or more expensive Git object-database operations (tree walks, object-info lookups, and blob reads). This mirrors the reported bug class: an attacker-controlled repeated collection drives an unbounded loop of costly per-item work inside a single RPC invocation, which can be used to exhaust CPU/time on the handling Gitaly node.

### Finding Description
`GetBlobs` validates only that `revision_paths` is non-empty and that each revision string is well-formed; it never checks (nor could it, from a single message) how many entries are present: [1](#0-0) 

The handler then iterates over `req.GetRevisionPaths()` in `sendGetBlobsResponse`, and for **every** entry calls `tef.FindByRevisionAndPath`, which performs a `git cat-file` tree lookup (`TreeEntries`) for each distinct revision/directory pair not already cached, followed by `objectInfoReader.Info` and (for blobs) a full `sendBlobTreeEntry` object read: [2](#0-1) [3](#0-2) 

`FindByRevisionAndPath` caches per-directory tree listings but performs a fresh `objectReader.Object` call (spawning/using the catfile batch process) whenever a new `revision`+directory combination is seen, and always does a linear scan of the returned entries: [4](#0-3) 

Because `revision_paths` is a single field on a unary (non-streaming input) request, an attacker can pack tens of thousands of `{revision, path}` pairs — each pointing at a distinct revision or a distinct deep path — into one gRPC message (bounded only by the general gRPC message-size limit, not by any per-request item cap), forcing thousands of sequential catfile round-trips, tree-walks, and object reads within a single RPC call, all before any response streaming back-pressure can intervene. There is no cap analogous to `limit`/`blobsLimit` used elsewhere in this package (e.g., `ListBlobs`) to bound the amount of work per request.

### Impact Explanation
An unprivileged caller with read access to a repository (any client permitted to invoke `BlobService.GetBlobs`, e.g., via Gitaly's gRPC or Workhorse/GitLab-Shell proxy paths) can submit a single crafted request whose `revision_paths` list is very large, causing the serving Gitaly node to spend a large, attacker-controlled amount of CPU time and catfile-process I/O processing one RPC. This is a resource-exhaustion / availability risk against the Gitaly process handling the request — consistent with the reported bug class of "unbounded loop over a user-controlled collection performing expensive per-item work," though the concrete blast radius here is a single gRPC handler's goroutine/catfile session rather than a chain-wide liquidation DoS.

### Likelihood Explanation
Likelihood is moderate: the RPC is reachable by any client authorized to call read-only `BlobService` RPCs (no special privilege beyond normal repository read access), the request shape (a `repeated` field in one message) is trivial to construct, and no server-side cap on the number of `revision_paths` entries exists in the validation path shown above. The main mitigating factor is the overall gRPC message-size limit, which caps how many entries fit in one request, and the fact that context cancellation (client disconnect) can stop the loop early — but a still-connected client can keep the loop running for its full size.

### Recommendation
- Add an explicit upper bound on `len(req.GetRevisionPaths())` in `validateGetBlobsRequest` (e.g., reject requests exceeding a configurable maximum count), analogous to the `limit`/`blobsLimit` bounds already used for byte/blob counts elsewhere in the blob service.
- Consider converting `GetBlobs` semantics to encourage batching via the client (smaller repeated requests) or steering callers toward `ListBlobs`, which already does graph-walk based enumeration with its own limits, as hinted by the existing proto comment recommending `ListBlobs` over `GetBlobs`.
- Periodically check `ctx.Err()` inside the loop in `sendGetBlobsResponse` so that client cancellation is honored promptly rather than only relying on the stream `Send` failing.

### Proof of Concept
Conceptual PoC (not executed): construct a single `GetBlobsRequest` with `revision_paths` containing e.g. 100,000 entries, each pointing at a distinct valid revision (or many distinct deep paths under one revision) in a repository the attacker can read, then invoke `GetBlobs`. Each entry forces a `TreeEntries`/`objectReader.Object` catfile round trip (cache keyed only on `revision`+directory, so varying `revision` per entry defeats caching), driving up wall-clock/CPU time for the single RPC call in `sendGetBlobsResponse`. This exercises the exact code path cited above (`internal/gitaly/service/blob/get_blobs.go:33-94` and `internal/git/catfile/tree_entries.go:36-69`).

func sendGetBlobsResponse(
	req *gitalypb.GetBlobsRequest,
	stream gitalypb.BlobService_GetBlobsServer,
	objectReader catfile.ObjectContentReader,
	objectInfoReader catfile.ObjectInfoReader,
) error {
	ctx := stream.Context()

	tef := catfile.NewTreeEntryFinder(objectReader)

	for _, revisionPath := range req.GetRevisionPaths() {
		revision := revisionPath.GetRevision()
		path := revisionPath.GetPath()

		if len(path) > 1 {
			path = bytes.TrimRight(path, "/")
		}

		treeEntry, err := tef.FindByRevisionAndPath(ctx, revision, string(path))
		if err != nil {
			return structerr.NewInternal("find by revision and path: %w", err)
		}

		response := &gitalypb.GetBlobsResponse{Revision: revision, Path: path}

		if treeEntry == nil || len(treeEntry.GetOid()) == 0 {
			if err := stream.Send(response); err != nil {
				return structerr.NewInternal("send: %w", err)
			}

			continue
		}

		response.Mode = treeEntry.GetMode()
		response.Oid = treeEntry.GetOid()

		if treeEntry.GetType() == gitalypb.TreeEntry_COMMIT {
			response.IsSubmodule = true
			response.Type = gitalypb.ObjectType_COMMIT

			if err := stream.Send(response); err != nil {
				return structerr.NewInternal("send: %w", err)
			}

			continue
		}

		objectInfo, err := objectInfoReader.Info(ctx, git.Revision(treeEntry.GetOid()))
		if err != nil {
			return structerr.NewInternal("read object info: %w", err)
		}

		response.Size = objectInfo.Size

		var ok bool
		response.Type, ok = treeEntryToObjectType[treeEntry.GetType()]

		if !ok {
			continue
		}

		if response.GetType() != gitalypb.ObjectType_BLOB {
			if err := stream.Send(response); err != nil {
				return structerr.NewInternal("send: %w", err)
			}
			continue
		}

		if err = sendBlobTreeEntry(response, stream, objectReader, req.GetLimit()); err != nil {
			return err
		}
	}

func sendBlobTreeEntry(
	response *gitalypb.GetBlobsResponse,
	stream gitalypb.BlobService_GetBlobsServer,
	objectReader catfile.ObjectContentReader,
	limit int64,
) (returnedErr error) {
	ctx := stream.Context()

	var readLimit int64
	if limit < 0 || limit > response.GetSize() {
		readLimit = response.GetSize()
	} else {
		readLimit = limit
	}

	// For correctness, it does not matter, but for performance, the order is
	// important: first check if readlimit == 0, if not, only then create
	// blobObj.
	if readLimit == 0 {
		if err := stream.Send(response); err != nil {
			return structerr.NewInternal("send: %w", err)
		}
		return nil
	}

	blobObj, err := objectReader.Object(ctx, git.Revision(response.GetOid()))
	if err != nil {
		return structerr.NewInternal("read object: %w", err)
	}
	defer func() {
		if _, err := io.Copy(io.Discard, blobObj); err != nil && returnedErr == nil {
			returnedErr = structerr.NewInternal("discarding data: %w", err)
		}
	}()
	if blobObj.Type != "blob" {
		return structerr.NewInternal("blob got unexpected type %q", blobObj.Type)
	}

	sw := streamio.NewWriter(func(p []byte) error {
		msg := &gitalypb.GetBlobsResponse{}
		if response != nil {
			msg = response
			response = nil
		}

		msg.Data = p

		return stream.Send(msg)
	})

	_, err = io.CopyN(sw, blobObj, readLimit)
	if err != nil {
		return structerr.NewInternal("send: %w", err)
	}

	return nil
}

func validateGetBlobsRequest(ctx context.Context, locator storage.Locator, req *gitalypb.GetBlobsRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}

	if len(req.GetRevisionPaths()) == 0 {
		return errors.New("empty RevisionPaths")
	}

	for _, rp := range req.GetRevisionPaths() {
		if err := git.ValidateRevision([]byte(rp.GetRevision())); err != nil {
			return err
		}
	}

	return nil
}

// FindByRevisionAndPath returns a TreeEntry struct for the object present at the revision/path pair.
func (tef *TreeEntryFinder) FindByRevisionAndPath(ctx context.Context, revision, path string) (*gitalypb.TreeEntry, error) {
	span, ctx := tracing.StartSpanIfHasParent(
		ctx,
		"catfile.FindByRevisionAndPatch",
		[]attribute.KeyValue{
			attribute.String("revision", revision),
			attribute.String("path", path),
		},
	)
	defer span.End()

	dir := pathPkg.Dir(path)
	cacheKey := revisionPath{revision: revision, path: dir}
	entries, ok := tef.treeCache[cacheKey]

	if !ok {
		var err error
		entries, err = TreeEntries(ctx, tef.objectReader, revision, dir)
		if err != nil {
			return nil, err
		}

		tef.treeCache[cacheKey] = entries
	}

	for _, entry := range entries {
		if string(entry.GetPath()) == path {
			return entry, nil
		}
	}

	return nil, nil
}
