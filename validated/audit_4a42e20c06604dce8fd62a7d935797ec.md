### Title
Attacker can fill `feeCollector`'s deposit-token list to `MAX_TOKENS_PER_USER`, DoS-ing all fee-bearing deposits and liquidations - ([File: contracts/DepositToken.sol])

### Summary
`Pool.addToDepositTokensOfAccount` enforces `MAX_TOKENS_PER_USER` on any account receiving a deposit token for the first time. Because `DepositToken.transfer`/`deposit(amount_, onBehalfOf_)` allow an unprivileged caller to credit dust `msdToken` balances to *any* address, an attacker can saturate the `feeCollector`'s per-account token list. Once saturated, every `DepositToken.deposit` that mints a nonzero fee (`_mint(_pool.feeCollector(), _fee)`) and every `Pool.liquidate` fee seizure (`depositToken_.seize(account_, feeCollector, _fee)`) reverts for any deposit token the collector does not already hold — a protocol-wide DoS on deposits and liquidations analogous to the malformed-input crash in CVE-2021-36802.

### Finding Description
- `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` [1](#0-0) .
- `DepositToken._transfer` adds the token to the recipient's list whenever the recipient's prior balance is zero — for any `recipient_` chosen by the caller [2](#0-1) .
- `DepositToken.transfer` only checks the *sender's* unlocked balance; nothing prevents sending 1-wei dust to `feeCollector` [3](#0-2) . `deposit(amount_, onBehalfOf_)` offers the same primitive with any `onBehalfOf_` [4](#0-3) .
- `deposit` mints the deposit fee to `feeCollector` whenever `feeProvider.depositFee() > 0` [5](#0-4) ; `Pool.liquidate` seizes `_fee` to `feeCollector` on each liquidation [6](#0-5) .

Attack trace: attacker deposits into each registered deposit token, then `transfer(feeCollector, 1)` on each until `depositTokensOfAccount[feeCollector]` hits `MAX_TOKENS_PER_USER`. Any subsequent deposit into a token the collector does not already hold mints a fee → `addToDepositTokensOfAccount(feeCollector)` → `UserReachedMaxTokens` revert. Same revert blocks `Pool.liquidate` whenever `protocolLiquidationFee > 0` and the seized token is new to the collector.

### Impact Explanation
Temporary freezing of funds and blocked liquidations: while `depositFee`/`protocolLiquidationFee` are nonzero, deposits for the griefed token(s) are bricked for all users, and liquidations of positions whose collateral token is missing from the collector's list revert — undercollateralized positions cannot be closed, risking protocol insolvency during volatile markets. Recovery requires the `feeCollector` to manually transfer out dust tokens to free slots, which is only possible if the collector is an operable address; if it is a non-transacting address (e.g., burn/multisig without arbitrary call), the DoS is permanent.

### Likelihood Explanation
Fully unprivileged and cheap: any EOA with minimal collateral executes it in one transaction batch (or via `Operator.execute` multicall). Preconditions are the deployed config having `depositFee > 0` / `protocolLiquidationFee > 0` and fewer registered deposit tokens needed than `MAX_TOKENS_PER_USER` cost being trivially affordable (1 wei each). No privileged role, oracle manipulation, or malicious infrastructure is required.

### Recommendation
- Whitelist `feeCollector` (and possibly `treasury`) from the `MAX_TOKENS_PER_USER` check in `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount`.
- Alternatively, make fee accounting not depend on token-list membership: accumulate fees internally or skip the per-account list for the fee collector.
- Consider restricting first-time-list-addition to opt-in paths (deposit/self-transfer) or tracking lists only for positions with collateral relevance.

### Proof of Concept
Hardhat sketch (based on repo test setup):

```ts
// feeCollector = await poolRegistry.feeCollector()
// Fill feeCollector's deposit token list with 1-wei dust
for (const dt of depositTokens) {
  await underlying.approve(dt.address, 1)
  await dt.deposit(1, attacker.address)           // attacker gets dust
  await dt.connect(attacker).transfer(feeCollector, 1) // feeCollector list += 1
}
// repeat until depositTokensOfAccount.length(feeCollector) == MAX_TOKENS_PER_USER
// (e.g., cycle a new deposit token through add/remove, or use debt tokens too)

// Now: any deposit in a token feeCollector lacks reverts
await expect(msdX.deposit(amount, alice.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')

// And liquidations revert on the fee seize for such tokens
await expect(pool.connect(liq).liquidate(msEth.address, victim, repay, msdX.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Caveat: I could not confirm the exact `MAX_TOKENS_PER_USER` value or the deployed `depositFee`/`protocolLiquidationFee` config within available iterations; the mechanics hold whenever fees are nonzero and the token count is reachable, which a fork test can verify directly.
