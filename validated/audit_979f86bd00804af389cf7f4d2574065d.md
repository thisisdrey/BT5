Based on the code traced, `StackerDBSession` in `libsigner/src/session.rs` connects to the node's own RPC host configured in the signer's config (typically the operator's trusted stacks-node), not an arbitrary attacker-controlled endpoint reachable without privilege. That said, the underlying code-level fault the question describes is real and independent of who the "host" happens to be: `run_http_request` unconditionally does an unbounded read before any cap is applied.

### Title
Unbounded `sock.read_to_end` in `run_http_request` buffers entire HTTP response before `MAX_MESSAGE_LEN` is enforced - (File: libsigner/src/http.rs)

### Summary
`run_http_request` (`libsigner/src/http.rs:221-262`) calls `sock.read_to_end(&mut buf)` at line 251 with no size limit whatsoever, before `decode_http_response`/`decode_http_body` are invoked and before `HttpChunkedTransferReader`'s `MAX_MESSAGE_LEN` cap comes into play. Any HTTP peer that `StackerDBSession::rpc_request` connects to can stream an arbitrarily large response (chunked or not) and the client will buffer it entirely in memory prior to any length check.

### Finding Description
The claimed fault holds exactly as stated: `decode_http_body` at `libsigner/src/http.rs:197-217` and `HttpChunkedTransferReader` (`stacks-common/src/util/chunked_encoding.rs:185-226`) do correctly enforce `MAX_MESSAGE_LEN` — `read_chunk_bytes` checks `self.total_size >= self.max_size` and returns `ChunkedError::OverflowError` — but this enforcement only happens for the chunked *decode* step, which is called on `buf[body_offset..]`, i.e. on a buffer that is *already fully read into memory* by `sock.read_to_end(&mut buf)` on `libsigner/src/http.rs:251`. That call has no cap: `std::io::Read::read_to_end` keeps reallocating and growing the `Vec<u8>` until the peer closes the connection or reading fails, regardless of `Content-Length` or chunk sizes. A malicious/misbehaving peer can simply keep the connection open and stream data (chunked-encoded or not — the same unbounded read happens either way) far beyond `MAX_MESSAGE_LEN`, and the client will attempt to hold all of it in RAM before `decode_http_response`/`decode_http_body` ever get a chance to reject it. ### Impact Explanation
This is a memory-exhaustion vector on the process that calls `run_http_request` — i.e. any `StackerDBSession` client (signer) — for an unbounded amount of data per connection, until either the process OOMs or the connection's read timeout fires. It does **not** affect the signer's inbound `tiny_http` server, since `run_http_request`/`decode_http_body` are only used on the *client* (outbound-request) side of `libsigner`; no evidence was found that the signer's own HTTP server reuses this unbounded-read path for incoming request bodies. [3](#0-2) 

### Likelihood Explanation
The reachability of this bug depends on who controls the remote endpoint that `StackerDBSession` connects to. `StackerDBSession.host` is set via `connect()`/`StackerDBSession::new()` from configuration supplied by the signer operator (pointed at their own or a designated stacks-node's RPC endpoint), not derived from untrusted, attacker-supplied gossip data discoverable in this repo. I was not able to fully trace, within the available tool budget, whether any code path lets an unprivileged remote party influence which host a `StackerDBSession` connects to (e.g. via a StackerDB-advertised peer list); if such a path exists, this bug becomes remotely triggerable by an unprivileged attacker per the rules' threat model. Without that confirmation, the precondition "attacker controls the remote HTTP peer" is not clearly satisfied by an unprivileged party — it more plausibly requires the operator to have configured (or been redirected to) a malicious/compromised node, which is a config/trust precondition, not a pure code defect exploitable purely from network position. [4](#0-3) 

### Recommendation
Impose a hard cap (e.g. `MAX_MESSAGE_LEN`) on `sock.read_to_end` in `run_http_request`, e.g. by wrapping `sock` in a size-limited reader (`std::io::Read::take(MAX_MESSAGE_LEN as u64)`) before calling `read_to_end`, so the unbounded buffering never happens regardless of `Transfer-Encoding` or `Content-Length`.

    fn read_chunk_bytes<R: Read>(&mut self, fd: &mut R, buf: &mut [u8]) -> io::Result<usize> {
        assert_eq!(self.parse_step, HttpChunkedTransferParseMode::Chunk);

        if self.total_size >= self.max_size && self.chunk_size > 0 {
            return Err(io::Error::other(ChunkedError::OverflowError(
                "HTTP body exceeds maximum expected length".to_string(),
            )));
        }

        let remaining = if self.chunk_size - self.chunk_read <= (self.max_size - self.total_size) {
            self.chunk_size - self.chunk_read
        } else {
            self.max_size - self.total_size
        };

    /// connect or reconnect to the node
    fn connect_or_reconnect(&mut self) -> Result<(), RPCError> {
        debug!("connect to {}", &self.host);
        let sock = TcpStream::connect(&self.host)?;
        // Make sure we don't hang forever if for some reason our node does not
        // respond as expected such as failing to properly close the connection
        sock.set_read_timeout(Some(self.socket_timeout))?;
        sock.set_write_timeout(Some(self.socket_timeout))?;
        self.sock = Some(sock);
        Ok(())
    }
