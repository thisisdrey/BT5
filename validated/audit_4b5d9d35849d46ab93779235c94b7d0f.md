### Title
Order execution reads `order_execution_max_fee` live from `FeeState` instead of the value in effect at order placement, letting the global fee admin change how much of a Take-Profit order's equity the executor may claim - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
`marginfi_account_place_order` creates an `Order` PDA that only stores the user-supplied thresholds and slippage; it does not snapshot the currently configured `order_execution_max_fee`. Later, potentially long after placement, a keeper calls `start_execute_order`/`end_execute_order` to trigger the order, and `end_execute_order` re-reads `fee_state.order_execution_max_fee` at that moment to compute the maximum amount the executor may keep. This is the same bug class as the `Flip.sol` finding: a percentage-based fee used to determine a payout/limit is recomputed with the *current* config at completion time instead of being fixed at the time the position/commitment was created.

### Finding Description
In `place_order` (lines 38-137), the `Order` account is initialized with `stop_loss`/`take_profit`/`max_slippage` only [1](#0-0) ; `fee_state.order_execution_max_fee` is not copied anywhere into the `Order` or any other per-order record - the `Order` struct itself has no fee field [2](#0-1) .

When the keeper later executes the order, `end_execute_order` loads `FeeState` fresh and uses its *current* `order_execution_max_fee` to derive `max_fee_frac`, which gates how much of the account's equity the keeper is allowed to consume for a Take-Profit trigger: [3](#0-2) [4](#0-3) 

`allowed_diff = start_health * (1 - max_fee)`, and the check only requires `net >= allowed_diff`. If the global fee admin raises `order_execution_max_fee` (via `edit_global_fee_state`) between the time a user places a Take-Profit order and the time a keeper executes it, `max_fee_frac` shrinks, `allowed_diff` shrinks, and the keeper is permitted to withdraw a larger fraction of the account's equity as "fee" than was permitted (and than the user implicitly agreed to) at order placement time. The user has no way to know or consent to this because the fee actually applied is determined entirely at execution time, not at order-creation time. This exactly mirrors the `Flip.sol` root cause: `netPayout`/fee limits are recalculated with the *live* fee configuration at completion instead of the value locked in at the start of the operation, allowing a fee change made after the user commits funds to change the economic outcome of that commitment.

### Impact Explanation
A user who places a Take-Profit order effectively agrees to a maximum extraction percentage bounded by `ORDER_EXECUTION_MAX_FEE`/`order_execution_max_fee` in force at that time. If the fee state is later increased by the global fee admin (a normal, permissionless-timing operation on FeeState that is not synchronized with any individual order), every pending order in the system is silently subject to the new, larger allowed keeper profit at execution, without the order owner's knowledge or ability to cancel/adjust in time (keepers execute permissionlessly once trigger + oracle conditions align). This can result in the account's owner receiving a smaller net equity, i.e., unauthorized-by-design divergence from what they signed up for, an unintended state change to their account's balances beyond the originally configured bound.

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the global fee admin to change `order_execution_max_fee` while orders are outstanding, which can happen for legitimate reasons (fee schedule updates) rather than only via malicious admin behavior, and orders can persist for extended periods waiting on price triggers. Unlike the `Flip.sol` case (short single-block game), marginfi orders are explicitly a two-step, time-displaced flow (`place_order` now, `end_execute_order` whenever the trigger fires), which increases exposure to this exact class of bug relative to same-block operations.

### Recommendation
Snapshot the applicable `order_execution_max_fee` (and any other fee-dependent parameters used at settlement) into the `Order` account (or into `ExecuteOrderRecord`, e.g., at `StartExecuteOrder`) at the time the order is placed, and use that stored value in `end_execute_order` instead of re-reading the live `FeeState`. If protocol-wide changes should apply to future orders only, this guarantees existing orders honor the fee terms in effect when the user committed to the order.

### Proof of Concept
1. User calls `marginfi_account_place_order` with `OrderTriggerType::TakeProfit`, when `FeeState.order_execution_max_fee` = 5% (`ORDER_EXECUTION_MAX_FEE`) [5](#0-4) .
2. Before the order's take-profit threshold is reached, the global fee admin calls `edit_global_fee_state` and raises `order_execution_max_fee` to, e.g., 50% [6](#0-5) .
3. Once price crosses the take-profit threshold, a keeper runs `marginfi_account_start_execute_order` then `marginfi_account_end_execute_order`. `end_execute_order` loads the now-50% `order_execution_max_fee` from `FeeState`, computes `allowed_diff = start_health * 0.5` instead of `start_health * 0.95`, and permits the keeper's withdraw/repay sequence to leave much less equity for the user than would have been allowed under the 5% fee that was in force when the user placed the order [7](#0-6) .
4. The user ends up with a materially worse outcome than what they agreed to at order placement, with no on-chain record tying the order to the fee terms at creation time.

Note: I was unable to fully inspect `SECURITY.md` or the `start_execute_order`/`ExecuteOrderRecord` initialization code (tool calls failed on the final iteration), so I cannot confirm whether this exact issue is explicitly listed as a known/out-of-scope item; based on everything retrieved, no such exclusion was found in the fee/order guides reviewed.
