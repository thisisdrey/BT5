Based on my research, I found a strong analog to this bug class in java-tron's governance proposal processing pipeline.

### Title
Single malformed on-chain proposal can permanently halt block processing chain-wide - (File: framework/src/main/java/org/tron/core/consensus/ProposalController.java)

### Summary
`ProposalController.processProposals()` iterates over all pending governance proposals during every maintenance cycle and, for each expired proposal, calls `processProposal()` → `setDynamicParameters()` → `ProposalService.process()` to apply its parameters directly to `DynamicPropertiesStore`. Only the DB read (`manager.getProposalStore().get(...)`) is wrapped in a try/catch; the actual parameter-application call is not. This mirrors the `FundsAllocator` bug class exactly: a loop over multiple externally-influenced items where a single bad item can throw and there is no per-item fault isolation, causing the whole batch operation (and everything downstream) to fail deterministically on every node.

### Finding Description
`processProposals()` loops while `proposalNum > 0`: [1](#0-0) 

Note that fetching the capsule is guarded (`try { ... } catch (Exception ex) { ...; continue; }`), but the call `processProposal(proposalCapsule)` on line 63 is **not** guarded. `processProposal` calls `setDynamicParameters(proposalCapsule)`, which delegates to `ProposalService.process(manager, proposalCapsule)`: [2](#0-1) 

`ProposalService.process` blindly applies each parameter value from the proposal to `DynamicPropertiesStore` via a large switch statement, and several branches perform unchecked arithmetic on the raw proposal value, e.g.: [3](#0-2) 

If `entry.getValue()` for `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` is `0` (or any value producing `ratio == 0`), `getTotalEnergyLimit() / ratio` throws an unchecked `ArithmeticException`. Because this call happens outside any try/catch in `processProposals()`, the exception propagates up through `MaintenanceManager.doMaintenance()` → `DposService.applyBlock()` → `Manager.processBlock()`, which itself does not catch it around the `consensus.applyBlock(block)` call: [4](#0-3) 

Since block/maintenance processing is deterministic, every node applying the same block containing (or preceding) the toxic proposal will throw the identical exception at the identical point, and the proposal will never be marked processed — the same failure will recur on every subsequent maintenance cycle attempt to reprocess it, permanently halting block application/consensus chain-wide.

I was not able to fully confirm within the available tool budget whether `ProposalUtil.validator()` (invoked at proposal-creation time via `ProposalCreateContract`) rejects a value of `0` for `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` specifically — this is the key open question determining whether *this exact* parameter is exploitable by an unprivileged proposal creator today. Regardless of that specific case, the structural defect is real and unambiguous: `processProposals()` provides fault isolation for the DB-read step but not for the parameter-application step, so **any** future or currently-unvalidated proposal parameter whose application can throw (division by zero, overflow, null dereference, etc.) creates a permanent chain-halting DOS with no ability to skip/remove the offending proposal, exactly analogous to FundsAllocator's inability to bypass a single failing adapter.

### Impact Explanation
If exploitable, this is a **chain halt** — a Critical-severity condition. Every full node/witness would throw during `processBlock` at the same point deterministically, since consensus is applied identically everywhere, and the proposal remains unprocessed indefinitely (state is never advanced past it), causing a total, permanent denial of service for the entire network with no fix short of a hard fork/patch.

### Likelihood Explanation
Exploitability hinges entirely on whether `ProposalUtil.validator()` fully constrains every numeric parameter used in unchecked arithmetic within `ProposalService.process`. Any active committee-member-approved proposal (or any parameter whose validation is incomplete) reaching this un-guarded code path would trigger it deterministically the moment the proposal expires and is processed during maintenance — this requires committee approval (governance action) rather than an arbitrary unprivileged transaction, which somewhat limits likelihood, but the underlying architectural gap (no exception isolation in the proposal-processing loop) remains a design flaw independent of any single parameter's current validation status.

### Recommendation
Wrap the `processProposal(proposalCapsule)` call inside `processProposals()`'s loop in the same defensive try/catch pattern already used for `manager.getProposalStore().get(...)`, logging and skipping (marking disapproved/cancelled) any proposal whose application throws, rather than letting the exception propagate and halt block processing. Additionally, audit `ProposalService.process` for any arithmetic (divisions, shifts) on untrusted proposal values not fully constrained by `ProposalUtil.validator()`.

### Proof of Concept
Conceptual PoC (contingent on validator gaps, not independently confirmed):
1. A committee member/witness collective approves a proposal setting `ADAPTIVE_RESOURCE_LIMIT_TARGET_RATIO` (or another parameter reachable in `ProposalService.process` with unchecked arithmetic) to a value that produces a zero/overflowing divisor.
2. At the proposal's expiration time, the next maintenance cycle's `MaintenanceManager.doMaintenance()` → `ProposalController.processProposals()` reaches this proposal and calls `processProposal()` → `ProposalService.process()`.
3. The arithmetic operation throws (e.g., `ArithmeticException: / by zero`), uncaught by `processProposals()`, propagating through `Manager.processBlock()`.
4. Every node applying this block/maintenance cycle throws identically, and block application/consensus fails permanently since the proposal is never marked processed and will be re-attempted (and re-fail) every subsequent maintenance window. [5](#0-4) [3](#0-2)
