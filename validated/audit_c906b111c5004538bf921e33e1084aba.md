### Title
Unbounded per-account delegation index list enables unmetered O(n) iteration DoS - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
The legacy (pre-optimization) resource-delegation index model stores, for every account, a single `DelegatedResourceAccountIndexCapsule` containing a `toAccountsList` / `fromAccountsList` of every distinct receiver/sender it has ever delegated resources to/from. `FreezeBalanceActuator.delegateResource()` appends a new entry to these lists with no size cap whenever a new, previously-unseen receiver address is used, so a single account can grow these lists to arbitrary size at negligible cost (1 TRX minimum bandwidth/energy freeze per unique receiver). When the network later enables `AllowDelegateOptimization`, the very next delegate/undelegate/freeze/unfreeze transaction from that account triggers `DelegatedResourceAccountIndexStore.convert()`, which performs a full, unmetered linear iteration over the entire legacy list to migrate every entry to the new index format.

### Finding Description
`FreezeBalanceActuator.delegateResource()` unconditionally appends to the index lists without any bound: [1](#0-0) 

These lists are stored as a single serialized capsule value per account (`DelegatedResourceAccountIndexCapsule`), so they can be inflated to thousands or millions of entries by an unprivileged account simply issuing many low-cost `FreezeBalanceContract`/`DelegateResourceContract` transactions to distinct throwaway receiver addresses — this only requires the network minimum (≈1 TRX) per unique receiver and default parameters (`supportAllowDelegateOptimization()` disabled, which is the pre-upgrade/default state).

Once the chain enables the optimization flag, `convert()` performs an *unmetered*, fully in-memory linear scan and per-entry write for every item in the attacker-inflated list: [2](#0-1) 

This `convert()` call is invoked from inside the delegate/freeze/unfreeze actuator execution paths (e.g. `FreezeBalanceActuator.delegateResource()` and `UnfreezeBalanceActuator.execute()`), all of which have `calcFee()` returning `0` and no energy/bandwidth cost scaling with the size of this list: [3](#0-2) [4](#0-3) 

This is structurally the same bug class as the reported issue: an unprivileged actor grows an unbounded, attacker-controlled list under default parameters, and a later single transaction forces the node to perform unmetered linear iteration proportional to that attacker-controlled size, inside block-application logic (`Manager`/actuator `execute()`), with no gas/fee cost scaling.

### Impact Explanation
A malicious but unprivileged account can pre-inflate its `DelegatedResourceAccountIndexCapsule` to an arbitrarily large size at low, linear cost. When the network flips `AllowDelegateOptimization` on (a normal upgrade path, analogous to "reset to default params" in the original report), the attacker's very next (or any node syncing/replaying that block) delegate/undelegate/freeze/unfreeze transaction forces every validating node to perform a full O(n) migration walk and n additional store writes synchronously inside block processing, with no accompanying resource charge. With a sufficiently large n this can materially slow or stall block processing across the network — a shared, permissionless chain-halt/DoS vector.

### Likelihood Explanation
Low/Medium: `supportAllowDelegateOptimization()` is presumably already enabled on the current network (matching the original report's note that the “system has moved off default params”), so the migration codepath (`convert()`) is likely dormant in production today. However, the vulnerable list-growth code in `FreezeBalanceActuator.delegateResource()` remains reachable and unbounded, and any future reset of this flag, a new sidechain/private-chain deployment starting from defaults, or forked networks that haven't yet toggled the flag would reintroduce full exploitability. This mirrors the original report's own "Low" likelihood characterization.

### Recommendation
1. Cap the number of distinct `toAccountsList`/`fromAccountsList` entries an account can accumulate in the legacy `DelegatedResourceAccountIndexCapsule` (reject further unique delegations beyond the cap, or force use of the new indexing model once the list reaches a threshold).
2. Alternatively, charge fee/energy proportional to the current list size in `FreezeBalanceActuator`/`DelegateResourceActuator` when appending new entries, and/or perform `convert()` incrementally (paginated/lazy migration) rather than as a single unmetered pass.
3. Audit other `TronStoreWithRevoking` capsules that store per-account growable lists (e.g., `getFrozenList()`/`Frozen` list, delegated resource lists) for similar unbounded-growth-then-unmetered-iteration patterns.

### Proof of Concept
1. On a network still running with `AllowDelegateOptimization` disabled (default/legacy state), have an attacker-controlled account repeatedly broadcast `FreezeBalanceContract` transactions with `receiverAddress` set to a fresh, previously-unused address each time (minimum 1 TRX bandwidth/energy delegation each), causing `ownerIndexCapsule.addToAccount(...)` to grow the `toAccountsList` without bound.
2. Repeat until the list contains a very large number (e.g., hundreds of thousands) of entries; this is bounded only by attacker capital (1 TRX per entry) and transaction throughput, not by any protocol-level cap.
3. Once the network committee enables `AllowDelegateOptimization`, submit any further `DelegateResourceContract`/`FreezeBalanceContract`/`UnfreezeBalanceContract` transaction from the attacker account, or wait for the attacker's account to naturally exercise this path.
4. Observe that `DelegatedResourceAccountIndexStore.convert()` performs a full linear scan/write over the inflated list inside block application, consuming disproportionate CPU/time on every full node processing that block, with no fee charged for the work — demonstrating the unmetered iteration DoS.

  public void convert(byte[] address) {
    DelegatedResourceAccountIndexCapsule indexCapsule = this.get(address);
    if (indexCapsule == null) {
      // convert complete or have no delegate
      return;
    }
    // convert old data
    List<ByteString> toList = indexCapsule.getToAccountsList();
    for (int i = 0; i < toList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(address, toList.get(i).toByteArray(), i + 1L);
    }

    List<ByteString> fromList = indexCapsule.getFromAccountsList();
    for (int i = 0; i < fromList.size(); i++) {
      // use index as the timestamp, just to keep index in order
      this.delegate(fromList.get(i).toByteArray(), address, i + 1L);
    }
    this.delete(address);
  }
