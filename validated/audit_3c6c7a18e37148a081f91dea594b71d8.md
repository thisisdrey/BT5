The same signer address is registered across **multiple StackerDB contracts simultaneously** (`signers-0-{message_id}` and `signers-1-{message_id}` for `message_id` in `0..SIGNER_SLOTS_PER_USER`, per reward-cycle parity), [1](#0-0) [2](#0-1)  and the per-slot signature does not bind to the contract/DB identity at all.

### Title
StackerDB chunk signature omits the DB identity, enabling cross-contract signature replay - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` (and thus every chunk signature) is computed only over `slot_id`, `slot_version`, and `data_hash` — it never includes the StackerDB's `smart_contract_id`. Because the same signer key legitimately owns slot `N` in many distinct StackerDB instances (each `.signers-{0|1}-{message_id}` contract, one per message type per reward-cycle parity), a validly-signed chunk chunk that is public (broadcast, stored, and downloadable by anyone) from one StackerDB can be replayed verbatim into a different StackerDB contract that the node also replicates, and it will pass signature verification there too.

### Finding Description
`SlotMetadata::auth_digest` hashes only `slot_id`, `slot_version`, and `data_hash`: [3](#0-2)  This digest is what gets signed in `SlotMetadata::sign` and checked in `SlotMetadata::verify` — the verification recovers the public key from this same restricted digest and compares only against `principal` (the configured slot owner for the DB being written to), never checking which `smart_contract_id`/StackerDB the digest was originally produced for. [4](#0-3) 

The node-side acceptance path, `PeerNetwork::validate_received_chunk`, looks up the expected signer address for `(smart_contract_id, slot_id)` and calls `slot_metadata.verify(&addr)` — but `addr` is derived purely from `(smart_contract_id, slot_id)` config, and the digest itself carries no `smart_contract_id` binding: [5](#0-4) 

Each signer's key is configured as the owner of slot `N` across *many* StackerDB contracts simultaneously: one `.signers-0-{message_id}` and `.signers-1-{message_id}` contract per message type, with the same relative slot index derived from the same underlying `get-signers`/`stackerdb-get-signer-slots-page` state [6](#0-5) , and these DB contracts are boot-installed identically per message id: [7](#0-6) . Consequently the same address `addr` frequently owns slot `N` in more than one live StackerDB.

Since the signed digest never commits to which `smart_contract_id` it was produced for, an attacker who has observed a validly-signed `StackerDBChunkData` (slot_id, slot_version, sig, data) published on StackerDB A can resubmit that exact same tuple as a push to StackerDB B (a different `smart_contract_id`) where the same signer address owns the same `slot_id`, as long as B's current expected version for that slot is `<= slot_version`. `validate_received_chunk` will successfully verify the signature (since `slot_metadata.verify(&addr)` only checks `slot_id`/`slot_version`/`data_hash` against the recovered key, not the target contract) and the forged/foreign chunk will be accepted and stored/relayed by the node as legitimate content for StackerDB B: [8](#0-7) 

This is the structural analog of the reported issue: just as the LooksRareExchange domain separator failed to bind signatures to a specific chain instance (allowing cross-fork replay), the StackerDB `auth_digest` fails to bind signatures to a specific StackerDB contract instance (allowing cross-contract replay), breaking the equality "signed-for-DB-A chunk == acceptable-in-DB-A-only."

### Impact Explanation
This allows an unauthenticated/unprivileged network peer to write forged (foreign but validly-signed) data into a StackerDB other than the one it was intended for, as long as the two DBs share a signer/slot pairing — this is an unauthorized write to StackerDB state via forged/misdirected data propagation, matching the "unauthenticated/unauthorized write to state or StackerDB" and "network-wide propagation of forged data" Critical impact categories. Because StackerDB content (e.g. signer block-response messages, in `stacks-signer`) is consumed and interpreted by downstream consumers keyed by contract/message-type semantics, a chunk crafted for one message type/DB replayed into another can corrupt or desynchronize that consumer's view of state.

### Likelihood Explanation
Likelihood is moderate: exploitation does not require the signer's private key — only a previously-published, validly-signed chunk (which is itself broadcast/publicly downloadable StackerDB content) and knowledge of which other DB contracts assign the same signer to the same slot index. Given the deterministic `signers-{0,1}-{message_id}` structure and identical slot ordering derived from the same reward-cycle signer set, an attacker can enumerate candidate cross-DB targets without any privileged access.

### Recommendation
Include the StackerDB's identity (e.g. `smart_contract_id`, or a fixed, unique network/DB-name constant) in `SlotMetadata::auth_digest` so a chunk signature is only valid for the specific StackerDB it was intended for, e.g. `hasher.update(smart_contract_id.serialize())` before hashing `slot_id`, `slot_version`, and `data_hash`. This requires a corresponding signing-side change in all producers (`stacks-signer` StackerDB client) and is only safely deployable via a coordinated protocol/version bump, since it changes the wire-signed digest format.

### Proof of Concept
1. Reward cycle `R` assigns signer `S` (private key `sk`) to relative slot index `2` in both `signers-1-0` (block-response messages) and `signers-1-3` (another message type), because both contracts derive the same ordering from `stackerdb-get-signer-slots-page` for the same reward-cycle parity. [6](#0-5) 
2. `S` legitimately signs and publishes chunk `C = (slot_id=2, slot_version=5, sig, data=D)` to `signers-1-0` via `StackerDBChunkData::sign` / normal push flow.
3. Attacker observes `C` (StackerDB content is public, served via chunk-download/push-gossip) and re-submits the identical `(slot_id=2, slot_version=5, sig, data=D)` as a push targeting `signers-1-3` instead, where slot 2's current expected version is `< 5`.
4. On the receiving node, `PeerNetwork::validate_received_chunk` for `smart_contract_id = signers-1-3` fetches `addr = S` for slot 2, computes `slot_metadata.verify(&addr)` — which recovers `S` correctly since the digest never referenced `signers-1-0` — and accepts the chunk as valid for `signers-1-3`, even though `S` never signed anything intended for that DB. [5](#0-4)
