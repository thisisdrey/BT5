Audit Report

## Title
`claim_child_bounty` ignores transfer failure via `debug_assert!`, permanently trapping bounty funds - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`claim_child_bounty` performs two `T::Currency::transfer(..., AllowDeath)` calls to pay the curator fee and beneficiary payout out of the child-bounty sub-account, but only validates the results with `debug_assert!`, which compiles to a no-op in release builds. If either transfer fails (e.g., destination account doesn't exist and amount is below the Existential Deposit), the pallet still emits `Event::Claimed`, decrements `ParentChildBounties`, removes `ChildBountyDescriptionsV1`, and sets the child-bounty record to `None` — permanently orphaning the undelivered funds in `child_bounty_account` with no remaining state to support a retry.

## Finding Description
The relevant code is in `claim_child_bounty` at `substrate/frame/child-bounties/src/lib.rs` lines 726-763: after computing `curator_fee` and `payout` from the child-bounty sub-account balance, it calls `T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath)` and `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)`, checking each result only via `debug_assert!(...is_ok())` [1](#0-0) . Since `debug_assert!` is gated by `cfg(debug_assertions)` and disabled in release/production runtime builds, a failed transfer is silently ignored and execution proceeds unconditionally to emit `Event::Claimed`, decrement `ParentChildBounties`, remove `ChildBountyDescriptionsV1`, and set `*maybe_child_bounty = None` [2](#0-1) .

`Currency::transfer` with `ExistenceRequirement::AllowDeath` can fail with `TokenError::BelowMinimum`/`ExistentialDeposit` errors when transferring to a not-yet-existing account with an amount below `ExistentialDeposit`, as confirmed by the balances pallet logic (`deposit_creating` enforces `value >= ed || !is_new`) and test `default_indexing_on_new_accounts_should_not_work2` which asserts `TokenError::BelowMinimum` for exactly this scenario [3](#0-2) [4](#0-3) . The curator fee is set via `propose_curator`/`accept_curator` with no enforced minimum tying it to ED, and both `curator` and `beneficiary` are attacker-influenceable, non-existent-account-capable addresses, so this failure condition is reachable by ordinary unprivileged actors.

The exact same unguarded pattern also exists in the sibling `claim_bounty` in `substrate/frame/bounties/src/lib.rs` (lines 821-826) and in `impl_close_child_bounty`'s fund-return transfer (line 940-946), confirming this is a structural, repeated anti-pattern rather than an isolated typo [5](#0-4) [6](#0-5) .

## Impact Explanation
This matches the "permanent user-fund lock" and "settle exactly once to the rightful beneficiary and amount" impact categories. When a transfer silently fails, the pallet's bookkeeping (`ParentChildBounties`, `ChildBountyDescriptionsV1`, the `ChildBounties` map entry itself) is destroyed while the actual balance remains stuck in `child_bounty_account`, with `Event::Claimed` falsely reporting success. Since the child-bounty record backing any retry logic is wiped via `*maybe_child_bounty = None`, there is no remaining extrinsic path to recover or redistribute the trapped balance in `child_bounty_account`.

## Likelihood Explanation
Triggering this requires only unprivileged actions available to any bounty curator/proposer and claimer: setting a child-bounty `fee` below `ExistentialDeposit` during `propose_curator`, having a `curator` (or `beneficiary`) account with zero prior balance/no existing entry in `System::Account`, and then anyone calling `claim_child_bounty` after `unlock_at`. No malicious validator, relayer, collator, or governance action is needed.

## Recommendation
Replace the `debug_assert!` checks with proper error propagation, e.g. use `?` on both `T::Currency::transfer` calls so a failed transfer aborts the `try_mutate_exists` closure (preserving the child-bounty state for retry) rather than silently continuing to remove state and emit a false `Claimed` event. Alternatively, verify destination accounts meet ED before committing to state removal, or route sub-ED remainders to a safe sink prior to deleting bookkeeping.

## Proof of Concept
1. Create a parent bounty and a child bounty with `fee` set below `ExistentialDeposit` (e.g., `fee = 1` on a chain with `ED = 1_000_000_000_000`).
2. Have a brand-new `curator` account (zero balance, not yet existing in `System::Account`) accept the curator role via `accept_curator`.
3. After `unlock_at`, call `claim_child_bounty(parent_bounty_id, child_bounty_id)`.
4. In a release build, `T::Currency::transfer(&child_bounty_account, curator, 1, AllowDeath)` fails (`TokenError::BelowMinimum`), but `debug_assert!(fee_transfer_result.is_ok())` is compiled out and the failure is ignored.
5. `Event::Claimed` is emitted, `ParentChildBounties` decremented, `ChildBountyDescriptionsV1` removed, `*maybe_child_bounty = None` — with the balance still sitting untouched in `child_bounty_account`, now permanently unreachable via any extrinsic.
