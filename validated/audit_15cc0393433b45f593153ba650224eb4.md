### Title
Reward-per-token JIT accounting in `pallet-asset-rewards` lets a staker "flash-stake" to snipe a disproportionate share of accrued rewards from existing stakers - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` computes rewards just-in-time via `reward_per_token`, dividing the reward accrued since the last update (`reward_rate_per_block * elapsed_blocks`) by whatever `total_tokens_staked` happens to be at the moment the update is triggered [1](#0-0) . Because any account can permissionlessly `stake` a large amount immediately before this update fires and withdraw again immediately after, the same core invariant broken in the Based Loans finding (an unprivileged actor transiently inflates the denominator/numerator input to a persisted rate calculation, then reverses the position) is reproducible here: a large holder can capture a share of the pool's already-committed reward budget without having contributed staking duration, diluting/stealing yield that should have accrued to genuine long-term stakers.

### Finding Description
`reward_per_token` accrues reward proportionally to `rewardable_blocks_elapsed` and divides by `pool_info.total_tokens_staked` read at call time [2](#0-1) . `update_pool_and_staker_rewards` — explicitly documented as having "no side-effects... should be called prior to any operation involving a staker" — is invoked on every `stake`/`unstake`/harvest-style call, and it snapshots `reward_per_token_paid` for the staker to the freshly computed `reward_per_token_stored` [3](#0-2) .

The reward computed for a period is fixed once at `reward_rate_per_block * elapsed_blocks` (independent of who is staked), but the pallet only tracks *shares* of that accrued reward via `total_tokens_staked` at the instant `reward_per_token` is invoked, not a time-weighted average. This is exactly analogous to Compound's `Comptroller.refreshCompSpeeds`, which recomputes a persisted rate using `totalBorrows` read at call time rather than a TWAP. An account can:
1. `stake` a very large amount of the staking asset in block N (this itself calls `update_pool_and_staker_rewards`, so `reward_per_token_paid` is set to the current `reward_per_token_stored`, meaning the attacker owes/earns nothing for prior periods).
2. Wait until block N+1 (or the next block in which any staker-affecting call is made), then call an operation that re-triggers `update_pool_and_staker_rewards` (e.g. `unstake`), which computes `reward_per_token` using `total_tokens_staked` now inflated by the attacker's huge deposit.
3. Because the attacker holds a large fraction of `total_tokens_staked` at this instant, `derive_rewards` (`staker_info.amount * (reward_per_token - reward_per_token_paid) / PRECISION_SCALING_FACTOR`) credits the attacker a proportionally large slice of the reward accrued during that interval [4](#0-3) , despite having been staked for only the shortest possible window.
4. The attacker then withdraws (`unstake`), returning `total_tokens_staked` to its prior level, having paid nothing but transaction fees for a slice of the reward pot that would otherwise have gone entirely to the pre-existing stakers.

This mirrors the reported bug-class precisely: no admin, governance, validator, or malicious-peer assumption is required; the attack primitive is transient, single-account manipulation of a value (`total_tokens_staked`) that feeds a persisted/committed rate calculation (`reward_per_token_stored`), executed by an ordinary unprivileged EOA in back-to-back blocks, siphoning value legitimately owed to other participants — the "reward rate manipulation via flash borrow/deposit" pattern.

### Impact Explanation
This directly violates the required invariant that "Balances, assets, NFTs, staking, pools, treasury spends, bridge rewards, and contract-held value must conserve value and settle exactly once to the rightful beneficiary and amount." Reward tokens meant for long-term stakers of a given `asset-rewards` pool are redirected to a short-term, capital-rich attacker who only needs to hold the staking asset across a very short window (as small as one block), repeatable indefinitely to continuously skim the reward budget of any pool with predictable/periodic reward accrual triggers.

### Likelihood Explanation
Likelihood is high wherever `pallet-asset-rewards` is deployed with a permissionless staking asset and non-trivial `reward_rate_per_block`: the pallet's own doc explicitly notes "future iterations of this pallet may allow permissionless creation and management of pools" [5](#0-4) , and `stake`/`unstake` are ordinary signed extrinsics with no minimum staking duration, cooldown, or time-weighted accounting to prevent this. Any account with capital sufficient to temporarily dominate `total_tokens_staked` for a single pool can execute the attack with only gas cost.

### Recommendation
Use a time-weighted average of `total_tokens_staked` (or checkpoint stake changes with a minimum bonding/cooldown period) rather than an instantaneous snapshot when computing `reward_per_token`, or require a minimum staking duration before a staker's `reward_per_token_paid` can be updated to capture newly accrued rewards, similar to the fix pattern recommended for the referenced Based Loans issue (TWAP-style state instead of instantaneous readings for values feeding persisted reward-rate math).

### Proof of Concept
1. Pool P has `total_tokens_staked = S`, `reward_rate_per_block = R`, and small legitimate stakers holding `S`.
2. At block N, attacker calls `stake(P, amount = K)` with `K >> S`. This calls `update_pool_and_staker_rewards`; since `rewardable_blocks_elapsed` since the previous update is small/zero, `reward_per_token_stored` barely changes, and the attacker's `reward_per_token_paid` is set to the current stored value (start of tracking).
3. At block N+1, any state-affecting call (attacker's own `unstake`, or another staker's action) triggers `update_pool_and_staker_rewards`, computing `reward_per_token` increment as `R * 1 / (S + K)` — but the attacker's owed reward is `K * (reward_per_token - reward_per_token_paid)`, which because `K` dominates `(S+K)`, gives the attacker roughly `R` (the entire block's reward budget) despite existing stakers having been staked the whole time [4](#0-3) .
4. Attacker calls `unstake` to withdraw `K`, keeping the harvested reward share, having paid only two transactions' worth of gas.

Note: I could not fully retrieve the bodies of the `stake`/`unstake`/`harvest_rewards` extrinsics in this session (only their signatures and the underlying `update_pool_and_staker_rewards`/`reward_per_token`/`derive_rewards` helper logic were available), so exact call-index/line numbers for those three extrinsics are not cited here; a Devin session with full file access should confirm whether any minimum-stake-duration guard exists in those call bodies before treating this as fully verified.

			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {

			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}

		/// Derives the amount of rewards earned by a staker.
		///
		/// This is a helper function for `update_pool_rewards` and should not be called directly.
		fn derive_rewards(
			staker_info: &PoolStakerInfo<T::Balance>,
			reward_per_token: &T::Balance,
		) -> Result<T::Balance, DispatchError> {
			Ok(staker_info
				.amount
				.ensure_mul(reward_per_token.ensure_sub(staker_info.reward_per_token_paid)?)?
				.ensure_div(PRECISION_SCALING_FACTOR.into())?
				.ensure_add(staker_info.rewards)?)
		}
