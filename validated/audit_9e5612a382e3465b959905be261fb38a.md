### Title
Missing anti-DoS rate limiting on unauthenticated handshake processing enables remote resource-exhaustion DoS - (File: handshake_manager.go)

### Summary
The external report flags Morpho's failure to replicate Compound's protective threshold checks (`borrowCaps`, `borrowGuardianPaused`) before permitting an action — checks the underlying protocol designed in specifically to prevent runaway/unsafe usage, which Morpho silently omits. The Nebula analog is structurally identical: the handshake wire protocol explicitly reserved a `Cookie` field for "an anti-DoS mechanism," but that protection was **never implemented**, and `HandshakeManager.beginHandshake` performs full asymmetric Noise-protocol crypto and certificate processing for every unauthenticated stage-1 packet with no rate limit, no per-source cap, and no cost-reducing cookie/puzzle challenge.

### Finding Description
The wire-format comment is explicit about the missing protection: [1](#0-0) 

which documents `Cookie` as "reserved for an anti-DoS mechanism that was never implemented. No released version of nebula has ever populated it."

`HandshakeManager.HandleIncoming` dispatches any stage-1 packet (`MessageCounter == 1`, `RemoteIndex == 0`) straight to `beginHandshake` after only a subtype check and an optional remote-allow-list check: [2](#0-1) 

`beginHandshake` then unconditionally allocates a new Noise `Machine` and performs a full Diffie-Hellman handshake step (`machine.ProcessPacket` → `m.hs.ReadMessage`) for every such packet, *before* any certificate/CA verification has succeeded: [3](#0-2) 

Certificate/identity validation (`hm.validatePeerCert`) only happens *after* this expensive cryptographic work has already completed: [4](#0-3) 

There is no per-source-IP or global rate limit gating entry into `beginHandshake`, no handshake-cookie/stateless-retry mechanism (despite the protocol reserving a field for exactly this), and no cap analogous to Compound's `borrowCaps` that would bound the number of concurrent/attempted handshakes an unauthenticated remote can trigger. This mirrors the report's core complaint: the underlying protocol design anticipated a safety threshold (the `Cookie` anti-DoS field, akin to Compound's `borrowCaps`) but the implementing layer (`HandshakeManager`) never enforces it, and no equivalent guardrail was substituted.

The optional `lighthouse.remote_allow_list` check (`AllowUnknownVpnAddr`) is an operator-configured allow/deny list, not a rate limiter — by default it does not throttle handshake volume, so it does not substitute for the missing anti-DoS mechanism, similar to how Morpho's operator-controlled pausing is acknowledged by Morpho itself as an insufficient substitute for hard caps ("no amount of checks will be sufficient... Operator should be proactive").

### Impact Explanation
An attacker with no valid CA-signed certificate can send an unlimited stream of spoofed UDP stage-1 handshake packets (arbitrary source `via`/`RemoteIndex=0`) to a node's listening port. Each packet forces the responder to instantiate a new Noise `Machine` and execute a full elliptic-curve Diffie-Hellman handshake computation plus payload/cert parsing before the peer's identity is verified and the packet can be discarded. This is classic asymmetric-cost amplification: cheap for the attacker (a crafted UDP packet), expensive for the victim (EC crypto + allocation). Sustained flooding can exhaust CPU and memory on the target Nebula node, degrading or crashing the daemon and denying legitimate handshakes/tunnels — a remote crash/DoS impact reachable without any certificate.

### Likelihood Explanation
The attack requires only network reachability to the node's UDP port; no certificate, prior handshake state, or trust relationship is needed, since the vulnerable code path is the very first-contact handshake stage before authentication. `MessageCounter==1` / `RemoteIndex==0` is trivially satisfied by any attacker. The only mitigating factor is `remote_allow_list`, which is opt-in operator configuration, not a default protection, and — even when configured — is an allow/deny filter rather than a rate limiter, so it does not prevent flooding by any single already-allowed (or unconfigured/default-open) source.

### Recommendation
Implement the anti-DoS mechanism the protocol already reserves a field for (or an equivalent lightweight stateless cookie/proof-of-work challenge) so that expensive Noise/cert processing is only performed after a cheap, spoof-resistant round trip validates the sender's address. Additionally, add a configurable rate limit / cap on the number of pending or per-second stage-1 handshakes accepted per source address (and/or globally), analogous to Compound's `borrowCaps`, and document clearly if this protection is intentionally deferred to network-layer (firewall) mitigations.

### Proof of Concept
1. Stand up a Nebula node with default configuration (no `remote_allow_list` restricting unknown addresses).
2. From an attacker host with no CA-issued Nebula certificate, craft repeated stage-1 handshake UDP packets: `header.H{Type: header.Handshake, Subtype: header.HandshakeIXPSK0, RemoteIndex: 0, MessageCounter: 1}` with varying spoofed source ports/addresses and arbitrary payload bytes (as done in `e2e/handshake_manager_test.go`'s `InjectUDPPacket` helper, but sent in a tight loop rather than singly).
3. Observe that each packet reaches `HandshakeManager.beginHandshake` (verified by the existing test `TestHandleIncomingDispatch` in `handshake_manager_test.go:184-237`, which shows only subtype/RemoteIndex==0 gating before dispatch — no volumetric limiting) and triggers a fresh `handshake.NewMachine` + `machine.ProcessPacket` (full Noise DH step) before any cert check occurs.
4. At sufficient packet rate, CPU consumption from repeated DH operations and per-packet allocations (new `Machine`, new `HostInfo`, maps) rises linearly with attacker-controlled packet volume, with no code path to throttle or reject cheaply — demonstrating the resource-exhaustion primitive.

func (hm *HandshakeManager) HandleIncoming(via ViaSender, packet []byte, h *header.H) {
	// Gate on known handshake subtypes. Unknown subtypes (or future ones we
	// don't yet support) are dropped here rather than silently routed through
	// the IX path. Add a case when introducing a new pattern.
	switch h.Subtype {
	case header.HandshakeIXPSK0:
		// supported
	default:
		hm.l.Debug("dropping handshake with unsupported subtype",
			"from", via, "subtype", h.Subtype)
		return
	}

	// First remote allow list check before we know the vpnIp
	if !via.IsRelayed {
		if !hm.lightHouse.GetRemoteAllowList().AllowUnknownVpnAddr(via.UdpAddr.Addr()) {
			hm.l.Debug("lighthouse.remote_allow_list denied incoming handshake", "from", via)
			return
		}
	}

	// First message of a new handshake. The wire format requires RemoteIndex
	// to be zero here (the initiator has no responder index to fill in yet),
	// and generateIndex never allocates 0, so any non-zero RemoteIndex on a
	// stage-1 packet is malformed or someone probing for an index collision.
	// Drop without paying the cost of running noise on a pending Machine.
	if h.MessageCounter == 1 {
		if h.RemoteIndex != 0 {
			hm.l.Debug("dropping stage-1 handshake with non-zero RemoteIndex",
				"from", via, "remoteIndex", h.RemoteIndex)
			return
		}
		hm.beginHandshake(via, packet, h)
		return
	}

func (hm *HandshakeManager) beginHandshake(via ViaSender, packet []byte, h *header.H) {
	f := hm.f
	cs := f.pki.getCertState()

	v := cs.DefaultVersion()
	if cs.GetCredential(v) == nil {
		f.l.Error("Unable to handshake with host because no certificate is available",
			"from", via, "certVersion", v)
		return
	}

	machine, err := handshake.NewMachine(
		v, cs.GetCredential,
		hm.certVerifier(), func() (uint32, error) { return generateIndex(f.l) },
		false, header.HandshakeIXPSK0,
	)
	if err != nil {
		f.l.Error("Failed to create handshake machine", "from", via, "error", err)
		return
	}

	response, result, err := machine.ProcessPacket(nil, packet)
	if err != nil {
		f.l.Error("Failed to process handshake packet", "from", via, "error", err)
		return
	}
