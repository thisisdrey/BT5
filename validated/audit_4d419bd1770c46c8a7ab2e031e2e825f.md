## Title
Missing zero-payment check in `matchSingleOrder`'s "taker == maker" branch allows a maker's TRC10 order to be drained for free - (File: `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetActuator.matchSingleOrder()` computes the amount a maker receives from a trade via integer (floor) division, and in one of its three branches this computed amount is never checked for zero before the trade is finalized. This mirrors exactly the reported bug class: an amount is rounded (here, down instead of up) while a corresponding whole quantity is transferred unconditionally, letting a counterparty obtain tokens without paying for them.

### Finding Description
`matchSingleOrder` handles three cases depending on how the taker's desired buy amount compares to the maker's remaining sell amount [1](#0-0) :

- **taker == maker** (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`): `makerBuyTokenQuantityReceive` is computed via `MarketUtils.multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...)` (a floor division), the taker unconditionally receives the maker's entire `getSellTokenQuantityRemain()`, and the maker's remaining quantity is unconditionally zeroed out — **with no check that `makerBuyTokenQuantityReceive > 0`** [2](#0-1) .
- **taker > maker**: the analogous computation *is* explicitly guarded — `if (makerBuyTokenQuantityReceive == 0) { ... return sellToken to maker; return; }` — precisely to prevent the maker from losing tokens for zero payment [3](#0-2) .
- **taker < maker**: the taker's own receive amount is checked for zero earlier in the method (`if (takerBuyTokenQuantityRemain == 0) { ...return; }`) [4](#0-3) .

The "taker == maker" branch is the only one of the three symmetric cases missing this safeguard. If `makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity` (using `MarketUtils.multiplyAndDivide`, which is a floor division [5](#0-4) ) rounds down to `0`, the trade still proceeds: the taker is credited the maker's full `sellTokenQuantityRemain` via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)`, while the maker is credited `0` via `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` [6](#0-5) .

This condition is reachable whenever a taker's `MarketSellAssetContract` sell/buy quantities are crafted (or coincide with) an existing maker order's remaining quantity such that `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()` and the reverse-price division underflows to zero — e.g. a maker order with a very small remaining quantity relative to its own sell/buy ratio (which regularly occurs after partial fills, as shown by the project's own "Accuracy problem" test comments) [7](#0-6) .

### Impact Explanation
Any unprivileged account can place `MarketSellAssetContract` transactions to become a taker against an existing maker order. By choosing a sell/buy quantity pair that exactly matches a maker order's depleted remaining quantity in a ratio that rounds the maker's payout to zero, the taker drains the maker's entire remaining TRC10/TRX balance held in that order while paying nothing in return — a direct theft of the maker's locked assets. This is a concrete unauthorized transfer of funds reachable purely through the public `MarketSellAssetContract` actuator path.

### Likelihood Explanation
The bug requires no special privilege — any account can place sell/buy market orders and match against existing ones. The exact-equality branch (`takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()`) is a normal, frequently-hit code path (it is exercised, without the zero-value edge case, in the project's own tests, e.g. `matchAll2SamePriceBuyOrders1`) [8](#0-7) . An attacker can deliberately engineer the maker-side remainder (by partially filling their own or a colluding maker order first) to land in the zero-rounding regime, then submit a single taker transaction to drain it.

### Recommendation
Add the same zero-check used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens to the maker (mark inactive) instead of zeroing out `sellTokenQuantityRemain` and transferring it to the taker for free, e.g.:
```java
makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(...);
if (makerBuyTokenQuantityReceive == 0) {
    makerOrderCapsule.setSellTokenQuantityReturn();
    returnSellTokenRemain(makerOrderCapsule);
    return;
}
```

### Proof of Concept
1. Attacker (or colluding account) creates/maintains a maker order (sell token A for token B) via `MarketSellAssetContract` such that after prior partial fills its `getSellTokenQuantityRemain()` is a small value `R` relative to its `sellTokenQuantity`/`buyTokenQuantity` ratio.
2. Attacker submits a new `MarketSellAssetContract` (selling B, buying A) with `sellTokenQuantity`/`buyTokenQuantity` chosen so that `takerBuyTokenQuantityRemain` computed by `MarketUtils.multiplyAndDivide` in `matchSingleOrder` equals exactly `R`.
3. Execution enters the "taker == maker" branch in `matchSingleOrder`; `makerBuyTokenQuantityReceive = multiplyAndDivide(R, makerBuyQuantity, makerSellQuantity, ...)` floors to `0` because `R * makerBuyQuantity < makerSellQuantity`.
4. `takerBuyTokenQuantityReceive` is set to `R` (the maker's full remainder) and credited to the attacker via `addTrxOrToken`; `makerOrderCapsule.setSellTokenQuantityRemain(0)` zeroes the maker's order, while `addTrxOrToken(makerOrderCapsule, 0)` credits the maker nothing.
5. Result: attacker receives `R` units of token A for zero payment of token B, at the maker's expense.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
