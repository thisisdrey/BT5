### Title
Dust-transfer griefing fills `MAX_TOKENS_PER_USER` account list, permanently blocking a victim from accepting new deposit/debt tokens - ([File: contracts/Pool.sol])

### Summary
`Pool` maintains per-account enumerable sets (`depositTokensOfAccount`, `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can transfer 1-wei dust of `DepositToken` (msdTOKEN) shares to a victim for every listed collateral, filling the victim's combined token list to the cap. From then on, `onlyIfAdditionWillNotReachMaxTokens` makes every operation that would register a *new* token for that account revert — the account "stops accepting new connections", mirroring CVE-2021-41585's improper-input-validation → accept-queue saturation.

### Finding Description
- `DepositToken.transfer`/`transferFrom`/`deposit(onBehalfOf)` mint or move msdTOKEN; whenever a recipient's balance goes `0 → >0`, the token calls `Pool.addToDepositTokensOfAccount`, which inserts `_msgSender()` into `depositTokensOfAccount` after checking `onlyIfAdditionWillNotReachMaxTokens` at `contracts/Pool.sol:143-148` and `contracts/Pool.sol:216-220`.
- `DebtToken.issue`/`mint` similarly registers via `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`).
- The check uses the **combined** length: `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` reverts `UserReachedMaxTokens` (`contracts/Pool.sol:79,143-146`).
- Nothing prevents sending dust to an arbitrary address: `DepositToken` is a plain transferable ERC20; `deposit(amount, onBehalfOf_)` only rejects `onBehalfOf_ == address(0)` and the treasury, so the attacker can also push tokens directly via `deposit(1, victim)` (`contracts/DepositToken.sol:211-237`).
- Once saturated, the victim's `DepositToken.deposit`/`transfer` into any not-yet-held collateral and `DebtToken.issue` of any not-yet-held synthetic all revert inside the token's `addTo*TokensOfAccount` call — no modifier, health check, or cap stops the fill-up because each individual dust transfer is legitimate input that is never validated as "unsolicited".

### Impact Explanation
Permanent (until victim acts) denial of service of position opening: the victim cannot deposit a new collateral type, cannot receive msdTOKEN transfers, and cannot issue a new synthetic asset — any call reverts `UserReachedMaxTokens`. This is a liveness break of the "accept new positions" invariant, matching the CVE's "server stops accepting new connections". Recovery requires the victim to spend gas transferring out each dusted token so `removeFromDepositTokensOfAccount` fires; positions in already-registered tokens keep working, so funds are not directly stolen but new interactions are bricked.

### Likelihood Explanation
Requires the pool to list enough tokens that the combined cap (30) is reachable — `addDepositToken` itself allows up to `MAX_TOKENS_PER_USER` deposit tokens (`contracts/Pool.sol:703`), and the attacker's own entries don't count against the victim. Cost is only dust deposits/transfers per collateral; no privileged role, oracle manipulation, or flash loan needed. Effectiveness is reduced on pools with few listed tokens, and the victim can self-heal by clearing entries, so severity is bounded — but the validation gap (unvetted registration on inbound transfers) is real.

### Recommendation
- Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` opt-in or ignore dust below a per-token minimum, or decouple set membership from ERC20 transfers (e.g., register on `deposit`/`issue` only, and make `transfer` of deposit tokens opt-in).
- Alternatively, allow automatic removal when a dust balance is received and never used, or exempt transfers initiated by token contracts from triggering registration for unsolicited inbound amounts.

### Proof of Concept
Hardhat fork (existing suite in `test/Pool.test.ts` provides fixture):

```ts
// attacker fills victim's account list with dust of every listed deposit token
const depositTokens = await pool.getDepositTokens(); // up to 30 entries
for (const dtAddr of depositTokens) {
  const dt = await ethers.getContractAt('DepositToken', dtAddr);
  const underlying = await ethers.getContractAt('ERC20', await dt.underlying());
  // attacker deposits 1 wei of underlying to victim via onBehalfOf,
  // or deposits to self then dt.transfer(victim, 1)
  await underlying.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1, victim.address); // adds dt to victim's list
}
// victim already held a few tokens; combined length hits 30

// now any NEW token interaction for victim reverts:
await expect(
  someNewDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  someNewDebtToken.connect(victim).issue(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note: reproducibility depends on the deployed pool listing enough deposit/debt tokens to reach the combined cap of 30; if the live deployment lists fewer, the PoC instead saturates all available slots and blocks only token types the victim doesn't already hold.
