### Title
Front-running `SetAccountIdContract` permanently squats a global human-readable account ID before the intended owner can claim it - ([File: actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java])

### Summary
`SetAccountIdActuator` lets any account bind an arbitrary, user-chosen `accountId` to itself exactly once, with global uniqueness enforced through `AccountIdIndexStore`. Because the ID is user-supplied, unbound to the sender's identity beforehand, and the binding is irrevocable, an attacker who observes a pending `SetAccountIdContract` transaction in the mempool can front-run it with the same `accountId` value and permanently deny the intended owner that identifier — closely mirroring the reported `createOffer` front-running/ID-squatting bug class.

### Finding Description
`validate()` in `SetAccountIdActuator` only checks:
1. That the account hasn't already set an ID (`account.getAccountId()` empty), and
2. That the `accountId` is not already registered in the global `AccountIdIndexStore` [1](#0-0) 

There is no binding between the chosen `accountId` and the sender prior to submission (no reservation/commit-reveal, no signature tying the ID to a specific address). `AccountIdIndexStore.put`/`has` normalize the ID to lower case and index it globally, meaning the namespace is shared across all accounts on the chain [2](#0-1) .

Once an account's ID is set, it can never be changed again — the second `execute()` call for that account fails validation with `"This account id already set"` [3](#0-2) , and attempting to set an ID that is already taken by any account fails with `"This id has existed"` [4](#0-3) .

This produces exactly the front-running pattern described in the report: a victim broadcasts a `SetAccountIdContract` transaction with a desired `accountId` (e.g., a recognizable brand/company/user name); an attacker sees it in the mempool, submits their own `SetAccountIdContract` with the identical `accountId` bytes with higher fee/priority, and gets it included first. The victim's transaction then reverts with `"This id has existed"`, and — critically — because the mapping is permanent and cannot ever be overwritten or reassigned, the victim can *never* obtain that identifier for any of their accounts, unlike the reported Solidity bug where the offer ID collision is merely a one-time nuisance per attempt. This ID is not cosmetic: it is queryable via the public API (`GetAccountByIdServlet`, `getAccountById` RPC/HTTP endpoints referenced throughout `framework/src/main/java/org/tron/core/services/...`), so it functions as a public-facing account handle that third parties (exchanges, dApps) may rely on to resolve an address.

### Impact Explanation
This is a griefing/denial-of-service vector rather than a direct fund-theft vector, matching the "Medium" severity classification used in the original report: it doesn't directly steal funds, but it permanently and irrecoverably blocks a legitimate account from claiming a human-readable identifier that may be depended upon by third-party integrations or branding, and it is trivially and cheaply repeatable against any target visible in the mempool.

### Likelihood Explanation
Any unprivileged account can construct and observe pending `SetAccountIdContract` transactions in the mempool (accountId and ownerAddress are both plaintext in the contract), and the fee for `SetAccountIdActuator` is zero (`calcFee()` returns `0`) [5](#0-4) , so the attack is essentially free and requires only front-running via gas/priority, which is straightforward on any account with minimal TRX for bandwidth/energy.

### Recommendation
Bind the `accountId` claim to the sender at submission time so a third party cannot intercept it — e.g., require a commit-reveal scheme, or require the `accountId` to incorporate/hash the `ownerAddress`, or otherwise verify some proof that ties the requested ID to the actual submitting account before allowing the irreversible, global uniqueness check in `SetAccountIdActuator.validate()`.

### Proof of Concept
1. Victim broadcasts `SetAccountIdContract{ownerAddress = victim, accountId = "brandname"}`.
2. Attacker observes this transaction in the mempool, and broadcasts `SetAccountIdContract{ownerAddress = attacker, accountId = "brandname"}` with a competitive fee/priority so it is packed first.
3. Attacker's transaction executes: `accountIdIndexStore.put(attackerAccount)` registers `"brandname"` -> attacker's address [6](#0-5) .
4. Victim's transaction is then processed and fails validation with `"This id has existed"` [4](#0-3) .
5. Victim can never retry with `"brandname"` on any account since the mapping is global and permanent, and `accountId` on the victim's own account (once actually set to anything) also cannot be changed per `"This account id already set"`.

  private static byte[] getLowerCaseAccountId(byte[] bsAccountId) {
    return ByteString
        .copyFromUtf8(ByteString.copyFrom(bsAccountId).toStringUtf8().toLowerCase(Locale.ROOT))
        .toByteArray();
  }

  public void put(AccountCapsule accountCapsule) {
    byte[] lowerCaseAccountId = getLowerCaseAccountId(accountCapsule.getAccountId().toByteArray());
    super.put(lowerCaseAccountId, new BytesCapsule(accountCapsule.getAddress().toByteArray()));
  }

  public byte[] get(ByteString name) {
    BytesCapsule bytesCapsule = get(name.toByteArray());
    if (Objects.nonNull(bytesCapsule)) {
      return bytesCapsule.getData();
    }
    return null;
  }

  @Override
  public BytesCapsule get(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    if (ArrayUtils.isEmpty(value)) {
      return null;
    }
    return new BytesCapsule(value);
  }

  @Override
  public boolean has(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    return !ArrayUtils.isEmpty(value);
  }
