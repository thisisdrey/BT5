## Title
Unescaped comma-delimiter injection in `split_method_names` lets an attacker inject extra allowed methods into a `FunctionCall`/`GasKeyFunctionCall` access key created via host functions - (File: `runtime/near-vm-runner/src/logic/utils.rs`)

### Summary
The reported Ruby CGI bug is a classic "structured value built by string concatenation with an unescaped delimiter" flaw: caller-supplied data containing the header/record separator (`\r\n`) is passed straight into a value the library later splits/interprets as multiple fields (Set-Cookie, Status, body), letting one untrusted string masquerade as several distinct protocol fields. The nearcore host-function surface for building `FunctionCall`/`GasKeyFunctionCall` access-key permissions has the same shape: `method_names` is passed to the host as a single opaque byte buffer, and the host silently treats the `,` byte as a field separator with no escaping mechanism, expanding one logical value into an arbitrary number of allowed method names.

### Finding Description
`promise_batch_action_add_key_with_function_call` and `promise_batch_action_add_gas_key_with_function_call` read a single guest-memory buffer for `method_names` and hand it to `split_method_names`, which splits purely on the `,` byte with no escaping/quoting support: [1](#0-0) 

Both host functions use this helper directly on raw contract-supplied bytes before constructing the `AddKey` action: [2](#0-1) [3](#0-2) 

The documentation itself confirms the design: "`method_names` is a `utf-8` string with `,` used as a separator. The vm will split the given string into a vector of strings," with no mention of any escaping for a literal comma inside an intended method name: [4](#0-3) 

Contrast this with the "properly typed" path a user reaches directly via a signed transaction, where `FunctionCallPermission.method_names` is an explicit `Vec<String>` with no delimiter ambiguity at all: [5](#0-4) 

Because the host-function surface (reachable from any deployed, attacker-controlled contract) re-encodes that same structured `Vec<String>` as a single delimited byte string with no escape mechanism, any contract that builds this buffer by concatenating a caller-supplied method name with its own additional method name(s) - e.g. `format!("{},required_method", user_supplied_method)` - is vulnerable: an attacker who controls `user_supplied_method` can embed a `,` followed by an arbitrary extra method name (or even the contract's most privileged method) and have the host silently add it as an additional entry in the resulting `FunctionCallPermission.method_names` / `GasKeyFunctionCall` permission, exactly as the original PoC injected an extra `Set-Cookie`/`Status` header by embedding `\r\n` in a single string field. Downstream verification (`verify_function_call_permission` / delegate-action checks) trusts the resulting `method_names` list unconditionally as authorization boundary: [6](#0-5) 

### Impact Explanation
This is an authorization-escalation primitive: a restricted-permission access key (or gas key) can end up permitting calls to methods the issuing contract never intended to authorize, because the host API silently splits one caller-influenced field into several allowed methods on an unescaped delimiter. Any relayer/marketplace/vault contract pattern that builds a single method name from partially user-controlled input and joins it with its own required method name via `,` is exposed to privilege injection on the resulting access key, matching the "authorization escalation across accounts or promises" impact category.

### Likelihood Explanation
Reaching the vulnerable API requires only deploying an ordinary WASM contract and calling `promise_batch_action_add_key_with_function_call`/`promise_batch_action_add_gas_key_with_function_call` with a `method_names` buffer built from partially untrusted input - a common pattern for contracts issuing scoped access/gas keys to users. No privileged role, validator, or node compromise is needed; the trigger is purely a normal cross-contract call from a signer-controlled contract.

### Recommendation
Provide the host function with a length-prefixed or otherwise unambiguous encoding for `method_names` (mirroring the `Vec<String>` used by the direct-transaction path) instead of a bare comma-joined string, or reject/escape any embedded delimiter byte within an individual name before splitting, so a single logical method name can never be expanded into multiple permission entries by caller-controlled bytes.

### Proof of Concept
1. Deploy a contract that issues a scoped `FunctionCall` access key for callers, constructing the method list as `format!("{},safe_view_method", caller_supplied_name)` and passing it to `promise_batch_action_add_key_with_function_call` (semantics reproduced by the existing test at [7](#0-6)  where `method_names = b"foo,bar"` is split into two independent method names `foo` and `bar`).
2. Have the caller supply `caller_supplied_name = "transfer,withdraw_all"`.
3. The resulting `AddKey` action ends up with `method_names = ["transfer", "withdraw_all", "safe_view_method"]` instead of the single intended entry, granting the access key permission to call `withdraw_all` even though the issuing contract only ever intended to authorize the caller-chosen name plus `safe_view_method`.

/// Uses `,` separator to split `method_names` into a vector of method names.
/// Returns an empty vec if the empty slice is given.
/// Throws `HostError::EmptyMethodName` in case there is an empty method name inside.
pub(crate) fn split_method_names(method_names: &[u8]) -> Result<Vec<Vec<u8>>, HostError> {
    if method_names.is_empty() {
        Ok(vec![])
    } else {
        method_names
            .split(|c| *c == b',')
            .map(|v| if v.is_empty() { Err(HostError::EmptyMethodName) } else { Ok(v.to_vec()) })
            .collect()
    }
}
