## Analysis: TRC10 Bancor-Exchange pool can be driven into an unbacked deficit via floating-point precision overshoot (no post-trade invariant check on the legacy path)

### Title
Unbacked/negative token balance in TRC10 `Exchange` pool due to floating-point overshoot in legacy `ExchangeProcessor` with no invariant enforcement - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The DefiTuna report describes an attacker exploiting a lending-pool accounting flaw to create a matching deficit and drain funds. The closest reachable analog in java-tron is the built-in TRC10 Bancor-style AMM (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract`/`ExchangeTransactionContract`), reachable by any unprivileged transaction broadcaster. The pricing math for `ExchangeTransactionContract` is computed with `double`-based power functions in the legacy `ExchangeProcessor`, and unlike the newer "hardened" processor, the legacy execution path in `ExchangeCapsule.transaction` never checks that resulting pool balances stay non-negative.

### Finding Description
`ExchangeCapsule.transaction()` selects between the legacy floating-point `ExchangeProcessor` and the `SafeExchangeProcessor`/hardened path based on the `hardenedCalc` flag: [1](#0-0) 

The invariant check that a trade cannot push a pool balance below zero is gated exclusively behind `hardenedCalc`: [2](#0-1) 

When `hardenedCalc` is false (the legacy/default path, used unless the `allowHardenExchangeCalculation` committee-controlled dynamic property is enabled), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` arithmetic on top of a `double`-based Bancor relay calculation and stored unconditionally, with no check against going negative.

The legacy pricing math itself relies on `double` and `Math.pow`, which is a floating-point approximation, not an exact fixed-point computation: [3](#0-2) 

`ExchangeTransactionActuator.execute()` calls this legacy/hardened selector directly and, on success, unconditionally credits the caller with `anotherTokenQuant` and persists the (possibly negative) new pool balance via `Commons.putExchangeCapsule`: [4](#0-3) 

`ExchangeTransactionActuator.doValidate()` only checks that the *pre-trade* balances are non-zero and within the configured `balanceLimit`; it does not re-derive `buyTokenQuant` from the double-based Bancor formula to bound the payout, so it cannot catch an overshoot from the floating-point calculation before `execute()` applies it: [5](#0-4) 

By contrast, developers were clearly aware precision issues exist here: a parallel `SafeExchangeProcessor` (BigDecimal-based) and a hardened invariant check were added specifically to catch overshoot/negative-balance scenarios, but only take effect once the `allowHardenExchangeCalculation` proposal is activated: [6](#0-5) 

This mirrors the DefiTuna bug class: an unchecked pricing/accounting computation lets a user extract more value than the pool's backing allows, leaving the pool (and thus other participants who later try to withdraw/inject/trade against it) with a "matching deficit" — here manifested as a negative or otherwise unbacked `firstTokenBalance`/`secondTokenBalance` in the persisted `ExchangeCapsule`/`ExchangeV2Store` entry.

### Impact Explanation
If the legacy `double`-based Bancor computation ever overshoots (e.g., for extreme ratios of `supplyQuant/supply` approaching the `pow(x, 2000)` exponent, or for balances near the edges of `long` precision converted through `double`), `exchangeFromSupply` can return a `buyTokenQuant` greater than the true available `buyTokenBalance`. Since the non-hardened path applies this result without any post-condition check, the pool's stored balance for that token can go negative — an unbacked liability recorded on-chain. Any TRC10 asset or TRX held in that exchange pool is now impossible to fully back for other holders/participants of that exchange pair, and repeated trades against the corrupted pool compound the deficit, directly analogous to the "matching deficit" drained from DefiTuna's lending pool. This is a concrete theft/unbacked-balance condition reachable by any account with the TRC10 asset(s) needed to trade against the pool.

### Likelihood Explanation
Reachability is trivial: any account holding one side of an existing TRC10 exchange pair can broadcast `ExchangeTransactionContract` transactions repeatedly. Exploitability, however, depends on finding balance/quant combinations where the `double`-based `Math.pow` computations in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` diverge enough from the exact fixed-point result to overshoot the buy-side reserve; the codebase's own tests show measurable divergence between the legacy and hardened/strict computations (`testStrictMath`, `testTransactionLegacyVsHardenedProcessorSelection` assert non-trivial differences), confirming precision drift exists in production math, though I could not execute code to construct a concrete overshoot input within this review — the specific numeric trigger (extreme ratio, near-limit balances) would need to be found by fuzzing/exhaustive testing of `ExchangeProcessor.exchange` against `SafeExchangeProcessor.exchange` for divergence causing `result > buyTokenBalance`.

### Recommendation
1. Move the non-negative pool-balance invariant check in `ExchangeCapsule.transaction()` (currently gated on `hardenedCalc`) to apply unconditionally, regardless of which processor computed the trade. [2](#0-1) 
2. Enable `allowHardenExchangeCalculation` (or make the `SafeExchangeProcessor` the sole/default processor) so the BigDecimal-based, exact computation is always used instead of `double`/`Math.pow`. [7](#0-6) 
3. Add a validate()-time cross-check in `ExchangeTransactionActuator` bounding `anotherTokenQuant` against the current buy-side reserve before allowing execution, mirroring the "Not precise enough"/balance-sufficiency checks already present in `ExchangeWithdrawActuator`. [8](#0-7) 

### Proof of Concept
Not fully constructible without live execution/fuzzing access. The theoretical PoC path is:
1. Create or use an existing TRC10 `Exchange` pool (`ExchangeCreateContract`) with `allowHardenExchangeCalculation` disabled (default/legacy path active).
2. Identify a `(firstTokenBalance, secondTokenBalance, sellTokenQuant)` triple where `ExchangeProcessor.exchange()`'s double-precision `Math.pow` computation returns a `buyTokenQuant` that exceeds the true available `buyTokenBalance` (codebase tests such as `ExchangeProcessorTest.testStrictMath` already demonstrate measurable divergence between legacy-double and BigDecimal-exact results for various balance/quant combinations, confirming the underlying precision drift exists).
3. Broadcast `ExchangeTransactionContract` with that triple; `ExchangeTransactionActuator.execute()` credits the attacker with the inflated `anotherTokenQuant` and persists a negative `secondTokenBalance`/`firstTokenBalance` in `ExchangeV2Store` since no invariant check runs on the non-hardened path.
4. Repeat to compound the deficit, or withdraw/inject to interact with the now-corrupted pool, propagating the unbacked balance into legitimate participants' realized withdrawals.

    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
