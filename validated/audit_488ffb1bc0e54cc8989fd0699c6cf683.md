## Title
Rounding-down of protocol interest-fee share in `accrue` lets any caller permanently reduce/eliminate `dao-treasury` yield via repeated frequent calls - ([File: mainnet/contracts/vault/v0-vault-sbtc.clar])

### Summary
The Zest vault contracts (`v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) compute the protocol's interest-fee share (`reserve-inc`, minted to `.dao-treasury` as `treasury-lp`) using `mul-div-down` at every step, instead of rounding up. Because `accrue()` is a public, permissionless, no-fee function that anyone can call at any time, an attacker can call it repeatedly with tiny time deltas so that the rounded-down fee share is truncated to zero on (almost) every call, permanently destroying protocol yield that would otherwise have accrued from a normal, less-frequent accrual cadence. This mirrors the DeliHook `_beforeSwap` bug where rounding down a per-call fee allowed an attacker to split actions into many small calls to avoid paying/collecting fees.

### Finding Description
`accrue()` recomputes the debt delta and the protocol's fee-reserve cut entirely with `mul-div-down`: [1](#0-0) 

```
(let ((next (next-index))
      (nliq (next-liquidity-index))
      (scaled-principal (var-get principal-scaled))
      (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
      (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
      (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
      (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
      (treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0)))
```

Note the inconsistency with the vault's own borrower-facing debt accounting, which explicitly rounds up in the borrower's favor to protect the protocol: [2](#0-1) 

`calc-cumulative-debt` uses `mul-div-up` so borrowers never under-pay debt. But the same debt growth, when recomputed inside `accrue()` purely to size the treasury's fee cut, uses `mul-div-down` twice in a row (`old-debt`, `new-debt`) and again for `reserve-inc` and `treasury-lp`. Three consecutive rounding-down operations compound the truncation.

`accrue()` itself is a `define-public` function with no caller authorization and no pause bypass beyond the `accrue` pause flag, and no minimum time-delta enforcement — any principal can call it directly at will: [3](#0-2) 

The index update itself uses `calc-multiplier-delta` with `round-up=true` for the borrow index (so total debt still fully accrues over time regardless of call frequency): [4](#0-3) 

This means over many tiny-interval calls, borrower debt (`total-borrowed`/`index`) still grows correctly (rounds up), but the treasury's proportional cut (`reserve-inc`/`treasury-lp`), computed independently with `mul-div-down`, can be truncated to zero on every single call if the per-call `debt-delta` is small enough relative to `INDEX-PRECISION` and `fee-reserve`/`BPS`. The exact analog of the reported issue: splitting one large accrual into many small ones changes the rounding outcome from "some fee collected" to "no fee collected," because `floor(a)+floor(b)+...+floor(n) <= floor(a+b+...+n)`.

### Impact Explanation
The protocol's reserve fee (`fee-reserve`) is the DAO treasury's yield share on all interest paid by borrowers, minted as `zft` shares (`treasury-lp`) to `.dao-treasury`. By calling `accrue()` in a tight loop (or interleaving it with every other transaction touching the vault, since deposit/withdraw/borrow/repay likely also call `accrue`), an attacker can keep the per-call `debt-delta`/`reserve-inc` below the rounding threshold indefinitely, causing the treasury to permanently lose interest-fee yield it would have collected under normal, less frequent accrual. This is a permanent loss of unclaimed protocol yield, which falls under the in-scope High-severity impact class: "theft of unclaimed yield or royalties, permanent freezing of unclaimed yield or royalties."

### Likelihood Explanation
`accrue()` requires no permission, no fee, and no minimum call interval, and is present identically across all six vault contracts (`v0-vault-sbtc`, `v0-vault-stx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststx`, `v0-vault-ststxbtc`). An attacker only needs enough transactions to keep triggering sub-rounding-threshold accruals, which — as in the original report — becomes economically attractive when gas costs are low relative to the fee amounts being denied, especially for higher-value/higher-precision underlyings (e.g. sBTC) where `INDEX-PRECISION` (1e12) and `fee-reserve` (in BPS) combine to make rounding-to-zero achievable at realistic time deltas.

### Recommendation
Round up (not down) when computing `old-debt`/`new-debt`/`reserve-inc` in `accrue()` and `calc-treasury-lp-preview` (using `mul-div-up` consistently, matching `calc-cumulative-debt`), or accumulate fractional remainders across calls instead of discarding them, so that splitting accrual calls into many small time deltas cannot reduce the treasury's total collected fee versus a single larger accrual.

### Proof of Concept
1. Attacker observes a vault (e.g. `v0-vault-sbtc`) with nonzero `fee-reserve` and `index`/`total-borrowed` > 0.
2. Attacker repeatedly calls the public `accrue()` function at short intervals (every block or as fast as tx throughput allows) instead of letting time pass between calls.
3. Each call computes `debt-delta = mul-div-down(new-debt, ...) - mul-div-down(old-debt, ...)`, `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)`; for sufficiently short intervals, `reserve-inc` truncates to `u0` on each call: [5](#0-4) 
4. `treasury-lp` stays `u0` and no `ft-mint?` to `.dao-treasury` occurs, even though the borrow index (and thus real borrower interest) has genuinely progressed: [6](#0-5) 
5. Compare against a single accrual call after the same elapsed time without attacker interference: the treasury would have received a nonzero `treasury-lp` mint. The difference is the yield permanently lost to the protocol.
