Audit Report

## Title
`EthereumOutboundQueueV2::process_delivery_receipt` pays relayer reward and settles the order regardless of the Ethereum-side dispatch `success` flag - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field indicating whether the message dispatch on Ethereum actually succeeded, but `Pallet::process_delivery_receipt` never inspects this field before paying the relayer/reward account and removing the corresponding `PendingOrder`. This allows relayers to collect the full fee for messages that failed to execute on Ethereum, misallocating bridge reward funds.

## Finding Description
`DeliveryReceipt` is decoded from the Ethereum log's `InboundMessageDispatched` event, explicitly including `success: bool`: [1](#0-0) 

`process_delivery_receipt` verifies the gateway address, resolves the reward account, looks up the `PendingOrder` by `nonce`, and unconditionally pays `order.fee` to the reward account before removing the order and emitting `MessageDelivered` — at no point does it read or branch on `receipt.success`: [2](#0-1) 

A targeted search across the `bridges/snowbridge/` tree for any reference to `.success` on the receipt confirmed no logic branch consumes `receipt.success` in the pallet call path — only its decode-time definition and test/benchmark usages appear, none of which gate the reward/removal logic. The pallet accepts any validly-proven `InboundMessageDispatched` event as sufficient grounds for the same settlement path, regardless of whether the underlying dispatch succeeded on Ethereum.

## Impact Explanation
This breaks the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." Because `T::RewardPayment::register_reward` is invoked and `PendingOrders::remove(nonce)` executes whenever `order.fee > 0` and the receipt is validly proven — irrespective of `receipt.success` — a relayer is paid the full fee for message deliveries that failed on the Ethereum side. The order is irreversibly removed, permanently losing the ability to re-process or re-reward that message, and misallocating funds from the relayer reward pot to a payout not tied to a correct outcome.

## Likelihood Explanation
Any unprivileged relayer who observes a genuine `InboundMessageDispatched(success=false)` event (a normal, expected occurrence — that's why the field exists) can submit the corresponding valid proof through `submit_delivery_receipt` and receive full payment as though the message succeeded. No privileged actor, compromised validator, or off-chain trust assumption beyond standard proof verification is required.

## Recommendation
Branch on `receipt.success` in `process_delivery_receipt`: only pay `order.fee` to the reward account when `receipt.success == true`. When `false`, withhold or reduce the reward and/or retain the pending order state for a later successful delivery attempt or explicit failure-handling path, rather than unconditionally paying and removing it.

## Proof of Concept
1. An `OutboundMessage` with nonce `N` and fee `F > 0` is committed via `do_process_message`, creating `PendingOrders[N] = { nonce: N, fee: F, .. }` [3](#0-2) .
2. The message dispatch fails on Ethereum; the Gateway contract emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address=R)`.
3. A relayer submits a valid proof of this event via `submit_delivery_receipt`, which decodes it into `DeliveryReceipt { success: false, .. }` via `TryFrom<&Log>` [4](#0-3) , and calls `process_delivery_receipt`.
4. `process_delivery_receipt` finds `order.fee = F > 0`, calls `T::RewardPayment::register_reward(&reward_account, .., F)`, and removes the order via `PendingOrders::remove(nonce)` — identical to the success path, since `receipt.success` is never checked [5](#0-4) .
5. The relayer/reward account is paid `F` despite the message never executing correctly on Ethereum, and `Event::MessageDelivered { nonce }` is emitted misleadingly.

```rust
		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
