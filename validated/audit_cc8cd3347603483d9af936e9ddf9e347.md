### Title
Anyone can reset a victim's deposit lock timer by dust-depositing `onBehalfOf` them, permanently blocking `withdraw`/`transfer`/`transferFrom` — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The GMX finding's bug class is: *a deposit performed by anyone refreshes a timestamp-based lock that blocks withdrawals, so a cheap, unprivileged "keep-alive" deposit can freeze funds indefinitely.* Metronome's `DepositToken` has the same structure, but worse: the lock is per-account and `deposit(amount_, onBehalfOf_)` lets any caller set the beneficiary to an arbitrary address. `lastDepositOf[account]` "stores the timestamp of the last deposit event of each account" and is "used combined with `minDepositTime`" to gate transfers/withdrawals via `_revertIfLocked`. Because `deposit` mints to `onBehalfOf_` without that account's consent, an attacker can deposit a dust amount of underlying to any victim and continuously refresh their lock, blocking `withdraw`, `withdrawFrom`/`flashWithdraw`, `transfer`, and `transferFrom`.

### Finding Description
- `deposit(uint256 amount_, address onBehalfOf_)` is `external`, `whenNotPaused`, `nonReentrant` — callable by any EOA. It pulls `underlying` only from `_msgSender` and mints msdTOKEN to `onBehalfOf_` with no opt-in from the recipient. `contracts/DepositToken.sol:211-237`
- `lastDepositOf` is a per-account timestamp "used combined with `minDepositTime`"; the mint path records the deposit timestamp for the beneficiary account. `contracts/storage/DepositTokenStorage.sol` (mapping + devdoc)
- `_revertIfLocked(account, amount)` is enforced on every exit path:
  - `withdraw`: `_revertIfLocked(_msgSender, amount_)` — `contracts/DepositToken.sol:406-411`
  - `withdrawFrom` (SmartFarmingManager path): `contracts/DepositToken.sol:420-427`
  - `transfer`: `contracts/DepositToken.sol:348-354`
  - `transferFrom`: `contracts/DepositToken.sol:357-376`
  - (`flashWithdraw`/`_withdraw` itself doesn't re-check the lock but is only reachable via the SmartFarmingManager, which routes through user positions — `contracts/DepositToken.sol:245-250`.)
- Nothing in `deposit` restricts `onBehalfOf_` to `msg.sender` or requires a signature/allowance from the beneficiary. A deposit of the smallest non-zero `amount_` suffices to update `lastDepositOf[victim]`.

So the exact analog holds: an unprivileged caller's *deposit* action extends the window in which a target's *redemption/withdrawal* reverts — the same liveness invariant broken in the GMX `cooldownDuration` report.

### Impact Explanation
Temporary freezing of user funds (qualifies per the impact rules). While `block.timestamp < lastDepositOf[victim] + minDepositTime`, the victim cannot withdraw collateral from the Treasury, transfer msdTOKEN, or have it moved via `transferFrom`. An attacker can repeat the dust deposit once per `minDepositTime` window at a cost of one transfer's gas plus a dust amount of underlying (the dust is minted to the victim, not lost — the attacker only spends gas and optionally the deposit fee). There is no upper bound on repetitions, so the freeze is effectively indefinite for as long as the attacker keeps paying gas. It also griefs integrations that hold msdTOKEN positions (e.g., SmartFarmingManager positions that go through `withdrawFrom`, which calls `_revertIfLocked(from_, ...)`).

### Likelihood Explanation
- No privilege required: `deposit` is a public entry point; the attacker uses their own underlying.
- Cost per refresh ≈ one `safeTransferFrom` + mint (gas only, plus `depositFee` on the dust amount if configured — near zero for dust).
- Trigger conditions: any active `DepositToken` with a nonzero `minDepositTime`. Note: whether a nonzero `minDepositTime` is actually set in the deployed configuration is a governance parameter; if it is `0` on all deployed pools the attack is inert on those chains (the `lastDepositOf`/`minDepositTime` machinery exists in deployed artifacts such as `deployments/bsc/DepositToken.json`, which document the mechanism).
- I could not fully verify the body of `_revertIfLocked` and the `_mint` hook that writes `lastDepositOf` within the search budget; the deployed-ABI devdocs and the call sites establish the mechanism, but the exact revert condition (full balance lock vs. partial) should be confirmed in `DepositToken.sol`'s `_revertIfLocked`/`_mint` implementations.

### Recommendation
Do not let a permissionless deposit refresh an account's withdrawal lock for an arbitrary beneficiary. Options:
- Record `lastDepositOf` only for `_msgSender` (i.e., lock only newly minted tokens attributable to the caller), or lock only the *incremental* deposited amount rather than timestamping the whole account.
- Alternatively, make the lock amount-based: track `lockedUntil` per deposit receipt, or have `unlockedBalanceOf` subtract only deposits made within `minDepositTime` (rolling window per tranche) instead of a single timestamp that any deposit resets.
- If per-account timestamp is retained, require `onBehalfOf_ == _msgSender` or a recipient opt-in/allowance before updating `lastDepositOf[onBehalfOf_]`.

### Proof of Concept
Hardhat sketch (assumes deployed `DepositToken` for underlying `MET`, nonzero `minDepositTime`):

```ts
// victim already holds msdMET and minDepositTime has nearly elapsed
const metDepositToken = await ethers.getContractAt('DepositToken', MSD_MET)

// attacker approves 1 wei of underlying once
await met.connect(attacker).approve(metDepositToken.address, MaxUint256)

// grief: keep victim locked forever
await metDepositToken.connect(attacker).deposit(1, victim.address) // resets lastDepositOf[victim]

await expect(
  metDepositToken.connect(victim).withdraw(victimBalance, victim.address)
).to.be.reverted // locked: _revertIfLocked(victim, ...) fails

await time.increase(minDepositTime - 1)
await metDepositToken.connect(attacker).deposit(1, victim.address) // refresh again
await expect(
  metDepositToken.connect(victim).withdraw(victimBalance, victim.address)
).to.be.reverted // still locked — repeatable indefinitely
```

On a fork test, query `minDepositTime`/`lastDepositOf` and `unlockedBalanceOf(victim)` before/after the dust `deposit` to show the lock extension. Confirm the revert originates from `_revertIfLocked` in `withdraw`/`transfer`/`transferFrom`.
