### Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus` survive account deletion, allowing a deferred `AddKey` action to hijack a recreated account - (`core/store/src/utils/mod.rs`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` purges the `Account`, `ContractCode`, access/gas keys, and contract data trie entries, but never removes `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId` keyed by that account. An attacker can plant a self-targeted `PromiseYield` receipt whose action list includes `AddKey(FullAccess)`, delete the account, have the name recreated by an unrelated party, and let the automatic timeout mechanism deliver a `PromiseResume` that resurrects and executes the stale `AddKey` against the new owner's account.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:504-575`) removes `Account`, `ContractCode`, access keys/gas-key nonces, and contract data, but has no logic to enumerate or remove `PromiseYieldReceipt { receiver_id, data_id }` or `PromiseYieldStatus { receiver_id, data_id }` entries for the account being deleted (nor the corresponding `PromiseYieldTimeout` queue entry, which is only removed when the timeout is later processed).

Exploit flow:
1. Attacker controls a subaccount (e.g. `temp.attacker.near`) and deploys a contract there.
2. From that contract the attacker calls `promise_yield_create(receiver_id = "temp.attacker.near")` (`runtime/near-vm-runner/.../logic.rs:3959` / `runtime/runtime/src/ext.rs:353`), obtaining a promise index for a receipt whose `predecessor_id` and `receiver_id` are both `temp.attacker.near` (set in `function_call.rs:187-194`), and a queued `PromiseYieldTimeout` (`function_call.rs:160-169`).
3. Using the same promise index, the attacker calls `promise_batch_action_add_key_with_full_access` (`runtime/near-vm-runner/.../logic.rs:3447`), which appends `Action::AddKey(FullAccess)` to the **same** pending receipt via `receipt_manager::append_action_add_key_with_full_access` (`runtime/runtime/src/receipt_manager.rs:544-557`). The stored receipt's action list is now `[FunctionCall, AddKey(attacker_backdoor_key)]`.
4. Attacker submits `DeleteAccount` on `temp.attacker.near`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account`, which deletes the account/keys but leaves the `PromiseYieldReceipt`, `PromiseYieldStatus`, and the still-queued `PromiseYieldTimeout` entry untouched.
5. `temp.attacker.near` is recreated (e.g. by the parent account `attacker.near`, which is the only entity allowed to create that subaccount per `action_create_account`, `runtime/runtime/src/actions.rs:167-210`) and handed to an unrelated new owner via `CreateAccount` + `AddKey(new_owner_key)`.
6. When the block height reaches the queued `expires_at`, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3104`) checks only `state_update.contains_key(&promise_yield_key, ...)` — true, since it was never removed — and automatically synthesizes and forwards a `PromiseResume { data: None }` receipt to `temp.attacker.near`. No signature or authorization is required; this happens purely as part of normal chunk processing.
7. `PromiseResume` handling (`runtime/runtime/src/lib.rs:1500-1562`) finds `get_promise_yield_receipt` returns `Some(yield_receipt)` and executes it via `apply_action_receipt`. For the `AddKey` action, `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) only checks `actor_id != account_id`; since `actor_id` derives from the stored `predecessor_id` of the yield receipt (which is the same account-id *string* as `receiver_id`, both fixed at creation time under the original owner), the check trivially passes even though the account is now controlled by a completely different owner. The attacker's backdoor `AddKey(FullAccess)` executes against the new owner's account.

The root cause is that `remove_account` does not treat pending `PromiseYield` state as part of "everything belonging to the account" that must be purged on deletion, and the `AddKey` authorization check (`check_actor_permissions`) validates only account-id string equality rather than re-verifying that the actor is still authorized against the account's *current* state.

### Impact Explanation
This is an authorization-escalation bug: an unrelated new owner of a recreated account name has a full-access key silently injected by a receipt created before they owned the name, without their signature, key, or consent. This falls into NEAR's "authorization escalation across accounts or promises" bounty category and can lead to complete compromise/theft of any account whose name is reused after deletion, provided an attacker previously controlled that name and planted a yield.

### Likelihood Explanation
- No special privilege is required: any unprivileged account can deploy a contract, call `promise_yield_create`/`promise_batch_action_add_key_with_full_access`, and self-delete via `DeleteAccount`.
- The only precondition is that the account name gets reused. This is realistic for subaccounts (attacker controls naming as the parent account and can hand out/resell/regift the same subaccount name to third parties, e.g. faucet-style flows), and it is fully automatic once the timeout fires — no cooperation from the new owner or anyone else is needed.
- Cost to attacker is minimal: one yield-create call, one batch add-key call, one delete-account call, and waiting `yield_timeout_length_in_blocks` blocks.
- Fully repeatable for any number of recycled account names.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), when deleting an account, also enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` trie entries keyed by that `account_id` (mirroring the existing access-key/contract-data enumeration pattern). Additionally/alternatively, the pending `PromiseYieldTimeout` queue entries referencing the deleted account should be invalidated so they cannot resurrect actions against a differently-owned account, and/or `check_actor_permissions` for privileged actions delivered via `PromiseResume` should be re-validated against a receipt "epoch"/creation-time binding rather than pure account-id string equality.

### Proof of Concept
Integration/runtime test-loop plan:
1. Deploy a contract on subaccount `temp.attacker.near` (child of an attacker-controlled `attacker.near`).
2. Call a method that: (a) invokes `promise_yield_create` with `receiver_id = "temp.attacker.near"`, and (b) using the returned promise index, calls `promise_batch_action_add_key_with_full_access` with a backdoor public key. Assert `get_promise_yield_receipt(state_update, &"temp.attacker.near".parse().unwrap(), data_id)` returns `Some(..)` and the receipt's actions include `AddKey`.
3. Submit `DeleteAccount` on `temp.attacker.near`. After applying, assert `get_promise_yield_receipt` still returns `Some(..)` (bug proof) even though `get_account` returns `None`.
4. Submit `CreateAccount` + `AddKey(new_owner_key)` for `temp.attacker.near` from `attacker.near`, giving control to a "new owner" key unrelated to the attacker's backdoor key.
5. Advance the chain past `yield_timeout_length_in_blocks` blocks without any resume call.
6. Assert a `PromiseResume` receipt is auto-generated and applied, and that afterward `get_access_key(state_update, "temp.attacker.near", backdoor_public_key)` returns `Some(AccessKey { permission: FullAccess, .. })`, proving the attacker's key was injected into the new owner's account.
