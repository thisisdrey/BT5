### Title
Legacy floating-point Bancor-style exchange calculation in `ExchangeCapsule.transaction()` allows rounding-drift extraction via repeated small trades - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
`ExchangeTransactionActuator` and `ExchangeWithdrawActuator`, both reachable by any unprivileged account via a signed `ExchangeTransactionContract`/`ExchangeWithdrawContract`, compute swap/withdraw amounts using `ExchangeCapsule.transaction()`. Unless the `AllowHardenExchangeCalculation` proposal has been activated by the committee, this path uses the legacy `ExchangeProcessor`, which performs the Bancor relay-supply calculation in native `double` arithmetic rather than exact decimal math.

### Finding Description
`ExchangeCapsule.transaction()` selects between the hardened `SafeExchangeProcessor` (BigDecimal-based) and the legacy `ExchangeProcessor` (double-based) depending on `hardenedCalc`, which is derived from `allowHarden()` / `dynamicStore.allowHardenExchangeCalculation()`: [1](#0-0) 

The legacy processor computes both legs of the trade using floating point `pow`/division: [2](#0-1) 

`allowHarden()` is gated purely by a dynamic-store flag toggled through a committee proposal (`AllowHardenExchangeCalculation`), i.e., a privileged/administrative switch, not something an ordinary transaction sender controls: [3](#0-2) 

Both `ExchangeTransactionActuator.execute()` and `ExchangeWithdrawActuator.execute()` are directly invoked from a signed `ExchangeTransactionContract`/`ExchangeWithdrawContract` broadcast by any account, with `tokenQuant` fully attacker-controlled: [4](#0-3) 

The test suite itself documents that legacy (non-hardened) and hardened/strict paths produce *different* results for identical inputs (`Assert.assertNotEquals(anotherTokenQuant, result)`), confirming the legacy `double` path is not the exact/precise one: [5](#0-4) 

This mirrors the reported ATM bug class: a value-transfer mechanism with an embedded automatic conversion/skim step whose internal math is imprecise, allowing an attacker to repeatedly trigger the conversion path to accumulate drift in their favor and drain the pool, rather than a single-shot logic flaw.

### Impact Explanation
An attacker can submit a sequence of `ExchangeTransactionContract` (or `ExchangeWithdrawContract`) transactions against any TRC10/TRX exchange pool. Because the default calculation path relies on IEEE-754 `double` `pow`/division rather than exact decimal arithmetic, small but consistent rounding bias can be accumulated over many repeated trades, extracting value from the pool's `firstTokenBalance`/`secondTokenBalance` beyond what an exact bonding-curve calculation would allow — i.e., unbacked token issuance/permanent loss of funds in the exchange pool, funded by other liquidity participants. This is a concrete "theft or permanent freezing of funds" impact.

### Likelihood Explanation
Medium: the bug requires no special privilege — any account holding TRX/TRC10 and able to broadcast an `ExchangeTransactionContract` can attempt the drain; the pattern (many repeated small trades) is exactly the "repeatedly triggered" pattern in the source incident. However, exploitability depends on the magnitude of accumulated floating-point drift being large enough to be profitable net of transaction fees/bandwidth cost, and on whether `AllowHardenExchangeCalculation` has already been activated on the live network (in which case the vulnerable legacy branch would no longer be reachable). I could not verify from the indexed code whether this proposal is currently active on mainnet.

### Recommendation
Make `SafeExchangeProcessor` (BigDecimal, exact rounding) the unconditional path for both `ExchangeTransactionActuator` and `ExchangeWithdrawActuator`, removing the legacy `ExchangeProcessor` double-math branch entirely rather than gating exactness behind an optional committee proposal. If backward compatibility must be preserved, add invariant checks on cumulative pool balance to detect/limit favorable-drift extraction across sequential trades within a block or account.

### Proof of Concept
1. Create/observe an exchange pool with `firstTokenBalance`/`secondTokenBalance`.
2. Repeatedly submit small `ExchangeTransactionContract` trades alternating direction, computed via `ExchangeCapsule.transaction(tokenID, tokenQuant, useStrictMath, allowHarden())` while `allowHardenExchangeCalculation()` is false (default/unactivated state) — see the actuator call site: [6](#0-5) 
3. Compare final pool balances against the amount computed using `SafeExchangeProcessor` for the same sequence of trades (as done in `ExchangeProcessorTest.testStrictMath`, which shows legacy vs. exact results diverge): [7](#0-6) 
4. The divergence, repeated across many trades, represents value extracted from/added to the pool beyond the exact bonding-curve amount.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
