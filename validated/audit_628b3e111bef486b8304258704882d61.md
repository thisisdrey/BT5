### Title
Liquidation deadlock: interaction of `maxLiquidable` cap and `debtFloorInUsd` makes unhealthy positions unliquidatable - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate()` enforces two mutually exclusive constraints on `amountToRepay_`: it cannot exceed `maxLiquidable` fraction of the account's debt, and the post-liquidation debt must be either `0` or `>= debtFloorInUsd`. When `maxLiquidable < 1e18` (partial-liquidation cap, e.g. 50%) and `debtFloorInUsd > 0`, any account whose debt satisfies `0 < debtUsd * (1 - maxLiquidable) < debtFloorInUsd` can never be liquidated: repaying the maximum allowed leaves residual debt below the floor (reverts `RemainingDebtIsLowerThanTheFloor`), and repaying down to zero reverts `AmountGreaterThanMaxLiquidable`. This is the same deadlock class as Notional H-10 (`minBorrowSize` vs. max deposit cap).

### Finding Description
In `Pool.liquidate()`: [1](#0-0) 

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` → `AmountGreaterThanMaxLiquidable`. A full repayment is only possible if `maxLiquidable == 1e18`.
2. If `debtFloorInUsd > 0`, the remaining debt `_debtTokenBalance - amountToRepay_` quoted to USD must be `0` or `>= debtFloorInUsd`, else `RemainingDebtIsLowerThanTheFloor`.

The minimum residual debt after any successful liquidation is `debt * (1 - maxLiquidable)`. If that minimum residual is non-zero and below the floor, no valid `amountToRepay_` exists:

- Let `debtUsd = $4,000`, `maxLiquidable = 0.5e18`, `debtFloorInUsd = $3,000`.
- Max repay = `$2,000` → residual `$2,000`, which is `> 0` and `< $3,000` → `RemainingDebtIsLowerThanTheFloor`.
- Any repay `< $2,000` leaves an even larger residual below the floor; any repay `> $2,000` (up to full `$4,000`) hits `AmountGreaterThanMaxLiquidable`.

`quoteLiquidateMax()` returns the same capped value (`debtToken.balanceOf(account_).wadMul(maxLiquidable)`), so even the protocol's own "max liquidatable" quote produces a transaction that always reverts. Additionally, if the position is underwater (`_totalSeized > depositToken_.balanceOf(account_)` → `AmountIsTooHigh`), the collateral-balance bound further shrinks the feasible repay range, widening the dead zone.

### Impact Explanation
Positions inside the dead zone are permanently unliquidatable while the collateral price keeps falling, so the pool accrues bad debt that msAsset holders/treasury must absorb — protocol insolvency risk identical in nature to the Notional finding. The condition is reachable by ordinary borrowers: an account mints debt in the range `(debtFloorInUsd/(1-maxLiquidable) lower bound)`, then becomes unhealthy via price movement. No privileged action is needed to create the victim position.

### Likelihood Explanation
Requires `maxLiquidable < 1e18` and `debtFloorInUsd > 0` simultaneously. Both are governor-set parameters; `updateMaxLiquidable` explicitly permits any value `<= 1e18` and the debt floor exists precisely to keep liquidations economically meaningful, so deployments commonly set it non-zero (the test suite exercises the floor path and historically Metronome Synth deployed with a fractional `maxLiquidable` and a positive USD debt floor). I could not confirm current on-chain storage values from the repo — the `deployments/*/Pool.json` files contain ABI/address artifacts only, not parameter state — so likelihood hinges on the live configuration; the code path itself is unconditionally present. Note this is not purely a "governance parameter choice" issue: the floor check's intent is to prevent dust debt, but its interaction with the cap creates an unbounded dead zone rather than merely requiring full liquidation, and the fix (allow repay-to-exactly-floor or relax the cap when the residual would dust) is a logic change.

### Recommendation
In `Pool.liquidate()`, permit the liquidation when the maximum allowed repayment would leave dust debt — i.e., either:
- treat `remaining < debtFloorInUsd` as valid when `amountToRepay_` equals the maximum permitted (`debt * maxLiquidable`) or wipes the debt, or
- allow repaying up to the amount that leaves residual `== debtFloorInUsd` even if that nominally exceeds `maxLiquidable`, or
- cap the effective `amountToRepay_` server-side like `quoteLiquidateMax` does and exempt full-balance seizures from the floor check.

Update `quoteLiquidateMax`/`quoteLiquidateIn` to return only amounts that will not revert.

### Proof of Concept
Hardhat, extending `test/Pool.test.ts` (fixture already deploys pool, msETH debt token, msdMET collateral, oracle at `ethPrice`):

```ts
it('deadlock: no amountToRepay satisfies both maxLiquidable and debtFloor', async function () {
  // Config: 50% liquidation cap, $3,000 debt floor
  await pool.updateMaxLiquidable(parseEther('0.5'));
  await pool.updateDebtFloor(parseEther('3000'));

  // alice debt is 1 msETH; set oracle so debt = $4,000 (already $4,000 in fixture).
  // Make position unhealthy by dropping collateral price (fixture uses newMetPrice).
  const debt = await msEthDebtToken.balanceOf(alice.address); // 1 msETH = $4,000

  // 1) Repay the maximum allowed (50% => residual $2,000 < floor) -> reverts
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address)
  ).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

  // 2) Repay more to leave residual >= floor or zero -> exceeds cap -> reverts
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, debt.div(2).add(1), msdMET.address)
  ).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

  // 3) Protocol's own max quote also reverts
  const maxRepay = await pool.quoteLiquidateMax(msEth.address, alice.address, msdMET.address);
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, maxRepay, msdMET.address)
  ).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');
});
```

Every branch reverts: the position cannot be liquidated at any `amountToRepay_`, so bad debt accrues until governance changes `maxLiquidable` or `debtFloorInUsd`.
