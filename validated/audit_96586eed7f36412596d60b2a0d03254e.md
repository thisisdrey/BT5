### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount` to `MAX_TOKENS_PER_USER` and blocks their deposits — ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
Any unprivileged account can force arbitrary addresses to accumulate entries in `depositTokensOfAccount` by transferring dust amounts of `msdTOKEN`s to them. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance of that token transitions from zero, and `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`. Once the victim's combined deposit+debt token list reaches `MAX_TOKENS_PER_USER`, every subsequent deposit or first-time mint of a token they do not already hold reverts with `UserReachedMaxTokens`, denying the victim use of the pool.

### Finding Description
- `DepositToken._transfer` credits the recipient and, when `_recipientBalanceBefore == 0 && amount_ > 0`, calls `pool.addToDepositTokensOfAccount(recipient_)` — no opt-in, no minimum amount.
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)`, which reverts `UserReachedMaxTokens` once `depositTokensOfAccount.length + debtTokensOfAccount.length >= MAX_TOKENS_PER_USER` (confirmed by the "should revert when reach max tokens" tests in `test/Pool.test.ts:1386` and `1491`).
- `DepositToken._mint` applies the same addition on first receipt (`_balanceBefore == 0 && amount_ > 0`), so `deposit(amount_, onBehalfOf_)` for a token the victim does not yet hold reverts inside `_mint` after the underlying has already been pulled — the whole transaction rolls back.
- Attack path: attacker deposits dust into each registered `DepositToken` (or acquires msdTOKENs any way), then calls `transfer(victim, 1)` for each token. Each transfer appends one entry to the victim's list. With enough registered deposit tokens the victim is at the cap.
- Result: `deposit(..., onBehalfOf_ = victim)` for any new collateral type reverts, and even the victim's own `deposit` for a new token reverts, until the victim manually transfers the dust away to shrink the list. Same applies to `DebtToken` issuance paths that add to `debtTokensOfAccount` (`Pool.addToDebtTokensOfAccount` has identical gating), so minting a new synthetic also reverts.
- Cost to attacker is bounded by dust balances times number of registered tokens; the tokens are not lost (transferring them out removes the entry), so the attack is cheap and repeatable against any address, including contracts (e.g., a SmartFarmingManager-position contract or multisig) that cannot easily shuffle ERC20 balances to clean the list.

### Impact Explanation
Temporary freezing of funds / liveness denial: the victim cannot deposit new collateral types or open new debt positions — both state-changing entry points revert inside `_mint`/list-add before any effect. For contract victims that cannot sign arbitrary `transfer` calls to clear dust entries (e.g., contracts integrating msdTOKENs without a sweep function), the freeze can be permanent. For EOAs it is temporary but requires the victim to discover and clean each dust entry, and the attacker can re-grief at negligible cost.

### Likelihood Explanation
Reachable by any EOA with dust collateral; no privileged role, oracle manipulation, or governance action needed. Requires enough registered deposit tokens to reach the shared cap, and the victim recovers by transferring dust out — which bounds impact to temporary freezing for EOAs rather than permanent loss. Severity is moderate: it is a real griefing/DoS surface mirroring the crafted-input DoS class (unauthenticated input causes repeated failure of the target's operations), but it neither steals funds nor breaks solvency, and self-recovery is possible.

### Recommendation
- Skip the `addToDepositTokensOfAccount` call in `DepositToken._transfer` for permissionless transfers and only track tokens added through `deposit`/`_mint`/`seize`, or add a dust threshold (`amount_ > MIN_TRACKED_AMOUNT`).
- Alternatively, let `addToDepositTokensOfAccount` silently skip (rather than revert) when the cap is reached for token additions caused by third-party transfers, so deposits of new tokens cannot be blocked by unsolicited dust.
- At minimum, provide a victim-callable removal path (e.g., `removeFromDepositTokensOfAccount` callable by the account when its balance is zero/dust) so contracts that cannot transfer tokens can unblock themselves.

### Proof of Concept
Hardhat sketch against a deployed pool (mainnet fork):

```ts
// victim has never held msdA, msdB, ...
const depositTokens = await pool.getDepositTokens() // or enumerate DepositTokenAdded events
for (const dt of depositTokens.slice(0, MAX)) {
  const token = await ethers.getContractAt('DepositToken', dt)
  // attacker deposits dust of each underlying, then:
  await underlying.approve(dt, DUST)
  await token.deposit(DUST, attacker.address)
  await token.transfer(victim.address, 1) // adds dt to victim's list
}
// victim's list is now at MAX_TOKENS_PER_USER
const newCollateral = /* a deposit token victim doesn't hold, or a newly added one */
await expect(newDepositToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Note: I verified the add-on-transfer logic (`DepositToken.sol:517-520`), the mint-side addition (`DepositToken.sol:485-488`), and the cap enforcement via `onlyIfAdditionWillNotReachMaxTokens` on `Pool.addToDepositTokensOfAccount` (`Pool.sol:204-208`), plus the reverting behavior in `test/Pool.test.ts`. I did not execute a fork PoC, and the exact value of `MAX_TOKENS_PER_USER` / count of registered deposit tokens on each chain should be confirmed from deployments to confirm the cap is practically reachable.
