### Title
Receivership liquidation's `ignore_healthy` branch bypasses the `max_fee` bound and, via asset/liability weight asymmetry, lets a liquidator extract equity value far beyond the intended premium on sub-threshold ("dust") accounts - (File: `programs/marginfi/src/instructions/marginfi_account/liquidate_end.rs`)

### Summary
`end_liquidation` skips the `seized <= repaid * max_fee` check whenever the account's snapshotted equity at `start_liquidation` was below `LIQUIDATION_CLOSEOUT_DOLLAR_THRESHOLD` ($5) [1](#0-0) . The only remaining guard in that path is the maintenance-weighted "health must not get worse" check in `end_receivership`, which operates on weighted (maintenance) values while `seized`/`repaid` are computed in unweighted equity terms [2](#0-1) . Because asset maintenance weights are typically <1 and liability weights are typically ≥1, a liquidator can withdraw the full equity value of collateral while repaying only a fraction of the weighted-equivalent debt and still satisfy `post_health >= pre_health`, extracting far more than the 10% max premium the design intends.

### Finding Description
`end_liquidation` reads the equity snapshot taken in `start_liquidation` (`liq_record.cache.asset_value_equity`), and if it is below `LIQUIDATION_CLOSEOUT_DOLLAR_THRESHOLD` (a constant $5), sets `ignore_healthy = true` and skips the `check!(seized <= repaid * max_fee, ...)` bound entirely [3](#0-2) [4](#0-3) .

The only remaining constraint is enforced unconditionally inside `end_receivership`: `pre_health` and `post_health` are computed as maintenance-weighted `assets - liabilities`, and the instruction fails only if `pre_health > post_health` (i.e., health got strictly worse) [5](#0-4) . `seized` and `repaid`, however, are computed separately from *equity*-mode values (unweighted, `RequirementType::Equity`), not from the maintenance-weighted values used in the health check [6](#0-5) .

Because asset maintenance weights are generally less than 1 (e.g., SOL at 0.4 in the repo's own test fixture) and liability maintenance weights are generally ≥1, a liquidator can:
1. Trigger `start_liquidation` on an account whose asset-equity snapshot is under $5 (any small/dust account, which the docs and tests confirm is a normal/reachable state — see `liquidate_receiver_closes_out_low_value_acc`) [7](#0-6) .
2. Withdraw the entire equity value of the collateral (full seizure), which reduces post-assets-maint to 0.
3. Repay only enough of the liability so that `post_liabs_maint <= pre_liabs_maint - pre_assets_maint` (i.e., just enough to keep maintenance health from decreasing), rather than repaying an equity-equivalent amount bounded by `max_fee`.
4. Because liability weight > asset weight, the dollar (equity) amount required to satisfy that maintenance constraint is smaller than the dollar value of assets seized, so `seized - repaid` (net value extracted) is not bounded by 10% as the design intends — it is bounded instead by the weight asymmetry, which can be much larger.

This defeats the purpose of `max_fee`: the intended cap is that the liquidator profits at most `LIQUIDATION_BONUS_FEE_MINIMUM`/`FeeState.liquidation_max_fee` (documented ~10%) over the repaid amount [8](#0-7) , but for any account snapshotted under the $5 threshold this cap simply does not apply, and the health-only guard does not enforce an equivalent equity-based bound.

Documentation states the intent for sub-threshold accounts is that "all remaining collateral … will be seized and all debt repaid, closing out the account" [9](#0-8) , implying the liquidator is expected to fully close the position (seize all, repay all). However, nothing in `end_receivership`/`end_liquidation` enforces that debt be fully repaid — only that weighted health does not worsen [10](#0-9) . A liquidator is free to leave residual (weighted-negative) debt on the account and withdraw disproportionately more equity than repaid.

### Impact Explanation
On any individual dust account the absolute dollar amount at risk is small (bounded by the ~$5 threshold), but the exploit is repeatable at zero incremental cost against every account whose snapshotted equity falls under the threshold (which can itself be induced/timed by an attacker manipulating their own dust positions, or simply targeting any naturally-occurring dust account). Aggregated across many such accounts, this becomes a systematic value-extraction vector that bypasses the protocol's own fee/premium invariant, leaving affected accounts under-collateralized/with stranded bad debt beyond the intended liquidation discount. This is a real violation of the intended SOLVENCY/fee-bound invariant, not merely a "known accepted" close-out behavior, because full debt repayment is not actually enforced.

### Likelihood Explanation
- Precondition (equity snapshot < $5) is trivial to reach: any small account, or an attacker's own multiply-created dust accounts, or third-party dust accounts that exist organically.
- The call sequence (`start_liquidation` → `lending_account_withdraw`/`lending_account_liquidate` → `end_liquidation`) is fully permissionless and reachable by any liquidator, as documented in `RECEIVERSHIP_LIQUIDATION.md`.
- No admin/governance privilege is required; only standard liquidator flow.
- Exploitability depends on the specific weight configuration of the two assets involved (needs asset maint weight < liability maint weight, which is the common/default case for most collateral/borrow pairs, e.g. SOL at 0.4 asset weight vs. USDC borrow near 1.0 weight, as seen directly in the repo's own test fixture).

### Recommendation
When `ignore_healthy` is true, still enforce an equity-based bound on net value extracted, e.g. require `seized <= repaid * max_fee` OR require that the account is fully closed out (`post_assets_equity == 0 && post_liabilities_equity == 0`) before allowing the fee check to be skipped. Alternatively, compute the health-improvement check in equity terms (not maintenance-weighted terms) so that `seized - repaid` is bounded consistently regardless of the `ignore_healthy` path, closing the loophole created by weight asymmetry between asset and liability maintenance weights.

### Proof of Concept
Rust integration test plan (extending `programs/marginfi/tests/user_actions/liquidate_receiver.rs`):
1. Set up a bank pair with asset maint weight 0.4 (SOL) and liability maint weight 1.0 (USDC), matching the existing `liquidate_receiver_closes_out_low_value_acc` fixture [11](#0-10) .
2. Create a liquidatee with deposit 0.4 SOL (~$4 equity, $1.6 maint) and borrow ~2 USDC (~$2 equity/maint), so pre-liquidation equity snapshot < $5 (threshold) and pre_health = 1.6 - 2 = -0.4.
3. Call `start_liquidation`.
4. Have the liquidator: withdraw all 0.4 SOL (full asset seizure, ~$4 equity), then repay only enough USDC (~$0.4-$1.6 equity) such that post_liabs_maint ≤ pre_liabs_maint - pre_assets_maint (i.e., post_health ≥ pre_health, satisfying the only remaining check).
5. Call `end_liquidation`.
6. Assert the transaction succeeds (no `LiquidationPremiumTooHigh` error) despite `seized` (~$4) far exceeding `repaid * max_fee` (~$1.6 * 1.1 ≈ $1.76), proving the fee bound was bypassed.
7. Assert `seized - repaid` (net liquidator profit) exceeds `repaid * LIQUIDATION_BONUS_FEE_MINIMUM`, demonstrating value extraction beyond the intended premium.
8. Repeat across a set of independently generated dust accounts in an invariant/fuzz harness (using `trident-tests/fuzz_0`) and assert the sum of `(seized - repaid)` deltas does not exceed the sum of `repaid * max_fee` across all closes — expect this invariant to fail, confirming systemic leak potential.

```markdown
Maximum profits are higher with receivership liquidation, up to 10% as of November 2025, where
classic only nets a 2.5% profit. The maximum profit is defined as:

```
Seized <= Repaid * (1 + max_fee)
```

Where Seized is the equity value withdrawn, in \$, Repaid is the equity value repaid, in \$, and max
fee is the maximum allowed profit currently configured at 10%. Note that equity value is the price
of the token without any weights applied, but inclusive of oracle confidence interval adjustments.
```
