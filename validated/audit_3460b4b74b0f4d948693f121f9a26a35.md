### Title
Firewall `ca_name` rules trust a certificate's human-readable CA name instead of its cryptographic identity, letting a certificate from an unintended (but pool-trusted) CA satisfy rules meant to scope access to a specific CA - ([File: firewall.go])

### Summary
The Vault bug is a scoping failure: an approval intended for one relationship (Bob ↔ Alice's LendingPair) is checked in a way that lets an unrelated, unintended party (Eve's LendingPair) satisfy it and gain the same access. `Vault._transfer`/`allowed` only checks that *some* approved contract initiated the call, never that it is the specific contract the funds were meant for.

`firewall.go`'s `ca_name` rule matching has the same shape of defect: it authorizes traffic based on a mutable, admin-chosen `Name()` string belonging to the CA that happens to have signed the peer's certificate, rather than the CA's cryptographic identity (fingerprint/SHA). Any certificate that resolves (via `caPool.GetCAForCert`) to a CA cert whose `Name()` field matches the rule's `ca_name` will satisfy the rule - even if that CA is a completely different, unrelated CA object than the operator intended when writing `ca_name: "root01"`.

### Finding Description
`FirewallCA.match` implements the "the request is authorized for firewall purposes" decision: [1](#0-0) 

```
func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	...
	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}
	return fc.CANames[s.Certificate.Name()].match(p, c)
}
```

`GetCAForCert` cryptographically resolves the signing CA only by issuer fingerprint (a map lookup keyed by fingerprint), and it performs *no* signature validation itself (its doc comment says so explicitly): [2](#0-1) 

The rule then indexes into `fc.CANames` using `s.Certificate.Name()` - a free-text field the CA operator chose when generating the CA cert (`nebula-cert ca -name ...`), not a value that is unique or bound to the CA's key material. `AddCA` never enforces name uniqueness across the pool: [3](#0-2) 

Because `ncp.CAs` is keyed by fingerprint (SHA), a `CAPool` can legitimately (and often does, in multi-org/multi-CA deployments, cert rotation, or CA `ca.pem` bundles from different vendors) contain multiple distinct CA certificates. If any two of these share the same `Name()` string - by coincidence, by convention (e.g., both named "root", "prod-ca", or a name copied from a template), or by an attacker crafting a self-signed CA cert with an attacker-chosen name and getting an operator to add it to the trusted `ca.pem` bundle (a documented, supported multi-CA workflow) - a firewall rule intended to scope access to CA "root01" specifically will also authorize any host whose certificate chains to the *other* CA that merely shares that name string.

This directly parallels the Vault report: the "approval" (`ca_name` rule) is checked against the wrong scope of trust (a display name shared across CAs) instead of the intended unique target (a specific CA's fingerprint), letting an unrelated trust root's cert holders ("Eve's pool") satisfy access meant only for the intended CA's cert holders ("Alice's pool").

By contrast, `ca_sha` rules are bound to `c.Certificate.Issuer()` (the actual signer fingerprint) and are not subject to this ambiguity: [4](#0-3) 

The existing test suite even documents that `ca_name`/`ca_sha` are treated as independent, both-considered inputs without asserting any name-uniqueness invariant: [5](#0-4) 

### Impact Explanation
If exploited, a certificate signed by an operator-trusted-but-unintended CA (one added to the CA pool for a separate purpose, and which happens to share a `Name()` with another CA in the same pool) can satisfy `ca_name`-scoped firewall rules, granting inbound/outbound network access that the rule author believed was restricted to a specific, distinct trust root. This is a **firewall enforcement bypass**: traffic that should be dropped (`ErrNoMatchingRule`) is instead allowed because the wrong CA-identity check (name instead of fingerprint) succeeded. The severity depends entirely on deployment: single-CA networks are unaffected, but any environment using `ca_name` rules with a multi-CA trust pool (a supported and documented Nebula feature) is exposed.

### Likelihood Explanation
Likelihood is moderate and configuration-dependent: it requires (a) the operator to use `ca_name` (rather than the stronger `ca_sha`) in a firewall rule, and (b) the CA pool to contain more than one CA certificate where two share a `Name()` value - either through operational coincidence (templated CA names, merged `ca.pem` bundles from different teams) or through deliberate abuse if an attacker can get their own self-signed CA added to the trust bundle under a colliding name. No CA-signed certificate from the "intended" CA is required by the attacker - only a certificate from *any* CA already present in the operator's trust pool, mirroring how Eve in the Vault report needs no relationship with Alice's pool at all.

### Recommendation
- **Short term:** Document that `ca_name` firewall rules provide only a weak, non-cryptographic binding and recommend operators use `ca_sha` (fingerprint-based) rules whenever precise CA scoping is required, especially in multi-CA deployments.
- **Long term:** Consider deprecating raw `ca_name` matching in `FirewallCA.match`, or hardening it by requiring an explicit uniqueness check across the `CAPool` at load time (reject/warn when two trusted CAs share a `Name()`), or by internally resolving `ca_name` rules to the corresponding fingerprint(s) at config-load time so that matching is always fingerprint-based under the hood.

### Proof of Concept
Not independently executed against a live binary; the following is a code-path walkthrough demonstrating the reachable defect using the repo's own test helpers as a basis:
1. Build a `cert.CAPool` containing two distinct self-signed CA certificates, CA-A and CA-B, both created with `Name() == "root01"` but different keys/fingerprints (supported since `AddCA` only keys by fingerprint, per `cert/ca_pool.go:101-132`).
2. Configure a firewall rule: `{"proto":"any","port":"any","group":"trusted","ca_name":"root01"}`, intending to scope access to hosts whose certs are signed by CA-A only.
3. Issue a host certificate signed by CA-B (the "unintended" CA), with group `"trusted"`.
4. On `fw.Drop`, `FirewallCA.match` calls `caPool.GetCAForCert(cert)` (`cert/ca_pool.go:254-266`), which resolves CA-B via `Issuer()` fingerprint lookup, then indexes `fc.CANames["root01"]` (`firewall.go:761-766`) - which matches the rule intended for CA-A, since `fc.CANames` is keyed by name, not fingerprint.
5. Traffic from the CA-B-signed host is allowed, even though the firewall author only trusted CA-A's cert holders for that rule - directly analogous to Eve's unrelated LendingPair pool satisfying Bob's broad Vault approval meant only for Alice's pool.

This proof-of-concept path is derived from static code reading only (`firewall.go` and `cert/ca_pool.go`); it was not run/tested in this session, so runtime confirmation (e.g., via `firewall_test.go`'s existing `TestFirewall_Drop` harness extended with a two-CA, same-name pool) is recommended before treating this as fully validated.

func (fc *FirewallCA) match(p firewall.Packet, c *cert.CachedCertificate, caPool *cert.CAPool) bool {
	if fc == nil {
		return false
	}

	if fc.Any.match(p, c) {
		return true
	}

	if t, ok := fc.CAShas[c.Certificate.Issuer()]; ok {
		if t.match(p, c) {
			return true
		}
	}

	s, err := caPool.GetCAForCert(c.Certificate)
	if err != nil {
		return false
	}

	return fc.CANames[s.Certificate.Name()].match(p, c)
}

// AddCA verifies a Nebula CA certificate and adds it to the pool.
func (ncp *CAPool) AddCA(c Certificate) error {
	if !c.IsCA() {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotCA)
	}

	if !c.CheckSignature(c.PublicKey()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrNotSelfSigned)
	}

	sum, err := c.Fingerprint()
	if err != nil {
		return fmt.Errorf("could not calculate fingerprint for provided CA; error: %w; %s", err, c.Name())
	}

	cc := &CachedCertificate{
		Certificate:    c,
		Fingerprint:    sum,
		InvertedGroups: make(map[string]struct{}),
	}

	for _, g := range c.Groups() {
		cc.InvertedGroups[g] = struct{}{}
	}

	ncp.CAs[sum] = cc

	if c.Expired(time.Now()) {
		return fmt.Errorf("%s: %w", c.Name(), ErrExpired)
	}

	return nil
}

// GetCAForCert attempts to return the signing certificate for the provided certificate.
// No signature validation is performed
func (ncp *CAPool) GetCAForCert(c Certificate) (*CachedCertificate, error) {
	issuer := c.Issuer()
	if issuer == "" {
		return nil, fmt.Errorf("no issuer in certificate")
	}

	signer, ok := ncp.CAs[issuer]
	if ok {
		return signer, nil
	}

	return nil, ErrCaNotFound
}
