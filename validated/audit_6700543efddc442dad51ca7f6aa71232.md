## Title
Unbounded Array Length from Untrusted Precompile Input Causes Unbounded Memory Allocation / Effectively Infinite Loop in TVM Precompiled Contracts - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE-2024-42358 root cause is that pdfio's TTF parser reads an attacker-controlled length field (`nGroups`) directly from file data and uses it, unbounded, as a loop bound/array-allocation size, letting a hostile input drive the parser into effectively unbounded iteration and memory exhaustion. The equivalent pattern exists in java-tron's TVM precompiled-contract helpers, where an attacker-controlled 256-bit word taken directly from contract call data is coerced into an `int` length and used to size and iterate over Java arrays without any upper-bound check against a sane maximum (such as the expected number of proof/signature elements).

### Finding Description
`PrecompiledContracts.extractBytes32Array` and `extractBytesArray` read a length value straight out of the caller-supplied `data`/`words` array and use it unchecked to allocate and iterate over arrays: [1](#0-0) 

Specifically, `len = words[offset].intValueSafe()` is taken from attacker-controlled call data and used as-is to size `new byte[len][]` and to drive a `for (int i = 0; i < len; i++)` loop that performs further out-of-bounds-prone reads (`words[offset + i + 1]`, `words[offset + bytesOffset + 1]`). `intValueSafe()` only guards against values that don't fit in an `int` (returning `Integer.MAX_VALUE` in that case); it does **not** enforce any semantic upper bound tied to the actual expected number of elements: [2](#0-1) 

This is structurally identical to the pdfio bug: a single untrusted length field (`nGroups` there, `words[offset].intValueSafe()` here) is used unbounded to drive allocation size and loop iteration count, with no cap tied to the real protocol/data shape. A crafted call with `len` set to a very large value (up to `Integer.MAX_VALUE`) will cause the JVM to attempt to allocate an array of that many `byte[]` references, and then loop that many times performing further array reads — this can exhaust heap/CPU resources on the node executing the transaction.

By contrast, the Zcash-shielding precompile at the same file explicitly bounds analogous counts (`spendCount`, `receiveCount`, `leafCount`) with sanity checks (`spendCount > 2`, `leafCount >= TREE_WIDTH - 1`, etc.) before using them to size arrays and loop: [3](#0-2) 

`extractBytes32Array`/`extractBytesArray`/`extractSigArray` lack any equivalent bound, showing the difference between a hardened parser and an unhardened one within the same file.

### Impact Explanation
If a precompiled contract path that calls `extractBytes32Array`/`extractBytesArray`/`extractSigArray` is reachable from a TVM `CALL` to a precompile address (as with the other length-driven precompiles like the shielded-transfer verifier in the same class), an attacker can submit a transaction whose call data encodes a huge unchecked length word. This drives the node to attempt an outsized array allocation and loop, which can manifest as `OutOfMemoryError`/excessive CPU consumption on the node processing/validating the transaction — a denial-of-service condition matching the "utilize 100% memory / effectively infinite loop" characterization of the original CVE. Because block-producing/validating nodes must execute the same TVM call to reach consensus, a DoS here can affect availability of the node (and potentially cascade if many nodes process the same malicious transaction).

### Likelihood Explanation
Likelihood is bounded by whether the specific precompiled-contract entry points that call these unbounded-length helpers are reachable directly from ordinary transaction call data without prior sanitization elsewhere in the calling precompile's `execute()` method. Given the demonstrated pattern (unbounded `intValueSafe()`-derived length feeding array allocation and loop count) exists in the same class where sibling precompiles explicitly add bound checks, this is a plausible but not fully confirmed reachable DoS — a full determination requires tracing every precompile `execute()` method that calls `extractBytes32Array`/`extractBytesArray`/`extractSigArray` to confirm the length word is attacker-controlled end-to-end without an earlier length cap.

### Recommendation
Add an explicit upper bound check on any length value derived from `DataWord.intValueSafe()` (and `longValueSafe()`) before using it to size arrays or drive loops in `PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` — mirroring the sanity checks already used for `spendCount`/`receiveCount`/`leafCount` in the shielded-transfer precompile. Reject (return `Pair.of(false, ...)` or throw) when the decoded length exceeds the maximum number of elements the calldata could actually encode given `data.length`, rather than trusting the raw attacker-supplied word.

### Proof of Concept
1. Identify a precompiled contract whose `execute(byte[] data)` invokes `extractBytes32Array` or `extractBytesArray`/`extractSigArray` with an `offset` pointing at attacker-controlled call data.
2. Craft `data` such that the 32-byte word at that `offset` decodes (via `intValueSafe()`) to a very large value (e.g., close to `Integer.MAX_VALUE`), while the remainder of `data` is arbitrary/minimal.
3. Submit a `TriggerSmartContract` transaction that calls into this precompile with the crafted `data`.
4. Observe the node attempting to allocate `new byte[len][]` and iterate `len` times inside `extractBytes32Array`/`extractBytesArray`, leading to excessive memory allocation and/or CPU consumption during transaction execution/validation.

    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();

    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
