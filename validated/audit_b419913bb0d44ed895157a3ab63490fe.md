### Title
Reward not marked-to-market before TVM-triggered `unfreezeBalance()` clears votes, unlike the transaction-level actuator - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnfreezeBalanceProcessor.java])

### Summary
This is the java-tron analog of the Velodrome `Gauge.withdrawToken()` bug: a balance/state-changing operation is reachable through two different entry points, but only one of them calls the reward-accrual routine before mutating the state that reward accounting depends on.

### Finding Description
In the ordinary (transaction-level) unfreeze path, `UnfreezeBalanceActuator.execute()` unconditionally calls `mortgageService.withdrawReward(ownerAddress)` **before** touching the account's frozen balance / votes: [1](#0-0) 

The same pattern (reward flush strictly before the balance/vote-affecting mutation) is consistently followed by `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, `VoteWitnessProcessor` and `WithdrawRewardProcessor`: [2](#0-1) [3](#0-2) [4](#0-3) 

However, the TVM-native equivalent of unfreeze, `UnfreezeBalanceProcessor.execute()` — reachable from any smart contract via the `unfreezeBalance` native/precompiled opcode exposed through `Program.java` — does **not** call `VoteRewardUtil.withdrawReward()` at the top of `execute()`. It only calls it deep inside a conditional branch, and only when the account's remaining tron power falls below the votes already cast: [5](#0-4) [6](#0-5) 

`VoteRewardUtil.withdrawReward()` snapshots the account's current `votesList` together with `beginCycle`/`endCycle` bookkeeping, and computes reward strictly for the interval `[beginCycle, endCycle)` based on that snapshot: [7](#0-6) 

Because `UnfreezeBalanceProcessor.execute()` mutates the account's frozen balance and total resource weight (`repo.updateAccount`) *before* any reward flush, and only conditionally clears votes (and only then calls `withdrawReward`) if `tronPower < usedTronPower`, a caller can unfreeze balance through a smart contract in a way that changes `TronPower`/weight totals used elsewhere in reward math without first crystallizing rewards owed under the pre-unfreeze state — exactly the same class of bug as the Velodrome report: a public/reachable state-changing entry point (`withdrawToken` / here the TVM `unfreezeBalance`) that omits the “update rewards before balance change” call that its sibling entry point (`withdraw` / here `UnfreezeBalanceActuator`) performs unconditionally.

### Impact Explanation
Reward math in `MortgageService`/`VoteRewardUtil` is duration- and vote-weight-sensitive (`computeReward` uses per-cycle Vi deltas multiplied by the voter's vote count captured at `withdrawReward` time). If the reward flush is skipped or deferred relative to the underlying balance/weight mutation, subsequent reward computations for `beginCycle..endCycle` can be computed against a state that no longer matches what was actually staked/voted for that interval, causing a user's accrued voting rewards to be miscalculated — either lost or (in specific interleavings) inflated. Given that unfreeze can be triggered from arbitrary smart contracts, an attacker-controlled or benign contract calling `unfreezeBalance()` in a specific order relative to freeze/vote operations within the same transaction can manipulate its own reward accounting, producing unbacked reward balance (medium/high impact per the report's own severity class).

### Likelihood Explanation
Reaching this code requires only a signed transaction that triggers a smart contract calling the native `unfreezeBalance` capability — no special privilege needed, matching the "unprivileged transaction broadcaster" reachability requirement. The condition to trigger the divergent behavior (having active votes but not immediately dropping below `usedTronPower`) is a normal usage pattern for participants who both vote and freeze/unfreeze resources via contracts, so likelihood is moderate.

### Recommendation
Move the `VoteRewardUtil.withdrawReward(ownerAddress, repo)` call to the very beginning of `UnfreezeBalanceProcessor.execute()`, unconditionally, matching the ordering used in `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, and `VoteWitnessProcessor`, so that rewards are always flushed against the pre-mutation state before frozen balance, total weight, or votes are altered.

### Proof of Concept
1. Deploy a contract that freezes balance, votes for a witness, and lets rewards accrue for one or more cycles (as in `VoteTest.testRewardAlgorithmNo3`, which exercises the same TVM-level freeze/vote/reward flow) — see the test harness pattern: [8](#0-7) 
2. From the contract, call the TVM `unfreezeBalance` opcode (routed to `UnfreezeBalanceProcessor.execute`) while `accountCapsule.getTronPower() >= usedTronPower * TRX_PRECISION` (i.e., partially unfreeze so votes are *not* cleared) — this skips the `VoteRewardUtil.withdrawReward` call entirely for that operation: [9](#0-8) 
3. Subsequently call `withdrawReward`/`queryReward` (via `WithdrawRewardProcessor`) and compare against the reward the account would have accrued had `withdrawReward` been invoked immediately before the unfreeze-induced weight change, analogous to the `checkRewardAndWithdraw` helper used elsewhere in the test suite: [10](#0-9) 
4. The discrepancy demonstrates that the reward snapshot boundary no longer lines up with the actual state transition, exactly mirroring the root cause described in the Velodrome report.

  public static void withdrawReward(byte[] address, Repository repository) {
    if (!VMConfig.allowTvmVote()) {
      return;
    }
    AccountCapsule accountCapsule = repository.getAccount(address);
    long beginCycle = repository.getBeginCycle(address);
    long endCycle = repository.getEndCycle(address);
    long currentCycle = repository.getDynamicPropertiesStore().getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = repository.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account, repository);
        adjustAllowance(address, reward, repository);
        reward = 0;
      }
      beginCycle += 1;
    }
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      repository.updateBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule, repository);
      adjustAllowance(address, reward, repository);
    }
    repository.updateBeginCycle(address, endCycle);
    repository.updateEndCycle(address, endCycle + 1);
    repository.updateAccountVote(address, endCycle, accountCapsule);
  }

  private void checkRewardAndWithdraw(byte[] contract, boolean isZero) throws Exception {
    long rewardBySystem = mortgageService.queryReward(contract);
    long beginCycle = dbManager.getDelegationStore().getBeginCycle(contract);
    long currentCycle = dbManager.getDynamicPropertiesStore().getCurrentCycleNumber();
    long passedCycle = max(0, currentCycle - beginCycle,
        dbManager.getDynamicPropertiesStore().disableJavaLangMath());
    Assert.assertTrue(isZero ? rewardBySystem == 0 : rewardBySystem > 0);
    triggerContract(contract, SUCCESS,
        getConsumer(">=", rewardBySystem)
            .andThen(getConsumer("<=", rewardBySystem + passedCycle)),
        queryRewardBalanceMethod);
