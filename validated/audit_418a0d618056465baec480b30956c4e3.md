### Title
Old account authority can pre-plant an unhealthy/liquidatable position at a victim's deterministic PDA account via `transfer_to_new_account_pda` - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The external report describes an NFT position handoff where the old position owner leaves a pending/near-liquidation GMX position for a new owner who has no way to inspect it before acquiring the NFT, causing the new owner to lose funds. In marginfi, the analogous primitive is `transfer_to_new_account_pda`, which lets any account authority unilaterally migrate their entire `lending_account` (including any existing debt/leverage) into a brand-new `MarginfiAccount` PDA whose owner (`new_authority`) is completely unchecked and unconsented, and whose address is fully deterministic from `(group, new_authority, account_index, third_party_id)`.

### Finding Description
`transfer_to_new_account_pda` copies `old_account.lending_account` (i.e., all deposit/borrow balances) into a freshly-initialized PDA account keyed by `new_authority`, `account_index`, and `third_party_id`: [1](#0-0) 

The `new_authority` account is explicitly documented as unchecked and requires no signature or consent from the intended recipient: [2](#0-1) 

The PDA seeds are fully deterministic and identical to the seeds a legitimate user would derive for their own first/default account (e.g., `account_index = 0`, `third_party_id = None`): [3](#0-2) [4](#0-3) 

The only guardrails before allowing the transfer are unrelated to account health: not in flashloan, not in receivership, not in order execution, `active_orders == 0`, and not already migrated. There is no check that the account being transferred is solvent, healthy, or free of near-liquidation risk: [5](#0-4) 

Because the seeds only depend on the *authority's public key* (which is public, known information for any target wallet), an attacker can: (1) create their own account, build a leveraged position deliberately close to liquidation, and (2) call `transfer_to_new_account_pda` targeting a victim's known wallet as `new_authority` with `account_index = 0` — the address a victim's wallet/dApp would naturally derive and use as their "first" account. This silently plants a debt-laden, near-liquidatable `MarginfiAccount` at the exact PDA the victim is likely to interact with next, without the victim ever signing or being aware of it.

### Impact Explanation
If the victim later deposits collateral into what they believe is a fresh account at that PDA (as most integrations derive `account_index = 0` by default), their new collateral becomes part of the health calculation of an account that already carries pre-existing debt engineered to be near liquidation. A subsequent liquidation (which can be triggered immediately or shortly after by anyone, including the attacker) seizes the victim's freshly deposited collateral to cover debt the victim never intentionally took on — a direct, unauthorized loss of funds for the victim, mirroring the "new NFT owner damaged by old owner's pending position" pattern in the source report. This is also an unauthorized state change: an account controlled by the victim's authority is created and populated with liabilities the victim never consented to.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker gains no direct benefit unless the victim actually deposits into (or otherwise interacts trustingly with) the pre-seeded PDA, and by the flat SOL fee (`ACCOUNT_TRANSFER_FEE`) the attacker must pay to execute the transfer. However, no signature or opt-in from the victim is required to create the state, and the deterministic, guessable nature of the default `account_index = 0` PDA (used pervasively across the test/client tooling as the default first account) makes targeted griefing against a known wallet address straightforward once an attacker has engineered an unhealthy position.

### Recommendation
Require the `new_authority` to co-sign (or otherwise explicitly consent to, e.g., via a pending-transfer/accept pattern) `transfer_to_new_account` / `transfer_to_new_account_pda`, especially when the resulting account is a PDA that a legitimate user could derive and later assume is uninitialized. Alternatively, disallow transferring an account whose health factor is below a safe threshold, and/or require the transferred account to be empty/healthy before migration, similar to the recommendation in the referenced report to disable transfer of positions with pending risk.

### Proof of Concept
1. Attacker creates `old_marginfi_account` with their own authority, deposits collateral, and borrows up to near the liquidation threshold.
2. Attacker computes victim's PDA at `account_index = 0`, `third_party_id = None` using `MarginfiAccount::derive_pda(group, victim_pubkey, 0, None, program_id)` — this is public information requiring no cooperation from the victim. [3](#0-2) 
3. Attacker calls `transfer_to_new_account_pda(account_index=0, third_party_id=None)` with `new_authority = victim_pubkey`, paying the flat fee; no signature from the victim is required by the accounts context. [2](#0-1) 
4. The victim's default PDA account now exists on-chain, owned by the victim's real authority, but pre-loaded with the attacker's near-liquidation debt/collateral position, set via `initialize_migrated_account`. [6](#0-5) 
5. Victim later uses this same PDA (assuming it is their normal first account) and deposits additional collateral, unaware of the embedded debt; a subsequent liquidation seizes the victim's collateral to cover the attacker-engineered debt.

```rust
pub fn transfer_to_new_account_pda(
    ctx: Context<TransferToNewAccountPda>,
    account_index: u16,
    third_party_id: Option<u16>,
) -> MarginfiResult {
    // Validate the global fee wallet and claim a nominal fee
    let group = ctx.accounts.group.load()?;
    check_eq!(
        ctx.accounts.global_fee_wallet.key(),
        group.fee_state_cache.global_fee_wallet,
        MarginfiError::InvalidFeeAta
    );
    anchor_lang::system_program::transfer(ctx.accounts.transfer_fee(), ACCOUNT_TRANSFER_FEE)?;

    let mut old_account = ctx.accounts.old_marginfi_account.load_mut()?;

    check!(
        !old_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_RECEIVERSHIP),
        MarginfiError::ForbiddenIx
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION),
        MarginfiError::ForbiddenIx
    );

    check!(
        old_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before transfer"
    );

    // Prevent multiple migrations from the same account
    check_eq!(
        old_account.migrated_to,
        Pubkey::default(),
        MarginfiError::AccountAlreadyMigrated
    );

    // Validate third-party id restriction if provided
    if let Some(id) = third_party_id {
        if !is_allowed_cpi_for_third_party_id(&ctx.accounts.instructions_sysvar, id)? {
            return err!(MarginfiError::Unauthorized);
        }
    }

    let mut new_account = ctx.accounts.new_marginfi_account.load_init()?;
    let current_timestamp = Clock::get()?.unix_timestamp as u64;
    initialize_migrated_account(
        &mut new_account,
        &old_account,
        ctx.accounts.new_authority.key(),
        current_timestamp,
        ctx.accounts.old_marginfi_account.key(),
    );
    new_account.account_index = account_index;
    new_account.third_party_index = third_party_id.unwrap_or(0);
    new_account.bump = ctx.bumps.new_marginfi_account;
```
