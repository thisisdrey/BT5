## Title
Non-owner Active permission can be granted authority over `AccountPermissionUpdateContract`, letting a lesser-privileged (delegated) key retain persistent owner-level control after a legitimate key rotation - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
The reported OpenC3 bug is a case of two credentials with different trust levels (password vs. session token) being treated as interchangeable for a sensitive credential-reset operation, so a lower-trust credential that survives a password change lets the attacker keep resetting the "real" credential. java-tron's account permission model has the same class of flaw: the `Owner` permission (root credential) and `Active` permissions (delegated/limited credentials, analogous to session tokens) are supposed to be different trust tiers, but an `Active` permission can be granted the `AccountPermissionUpdateContract` operation bit, which lets that lesser key rewrite the account's `Owner` permission itself.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's `Owner`, `Witness`, and `Active` permissions with whatever is supplied in the `AccountPermissionUpdateContract`, with no restriction tying this to the transaction's `permissionId`: [1](#0-0) 

Whether a given signer is authorized to submit this contract is decided purely by `TransactionCapsule.checkPermission`/`checkWeight`, based on the `permissionId` embedded in the contract and the *current* permission fetched from the account: [2](#0-1) [3](#0-2) 

For `permissionId != 0` (i.e., a non-owner `Active` permission), the only extra gate is `checkPermissionOperations`, which just checks whether the bit for the contract's `ContractType` is set in that `Active` permission's 32-byte `operations` bitmap: [4](#0-3) 

Crucially, `AccountPermissionUpdateActuator.checkPermission()` validates that any operations bitmap bit set on an `Active` permission is merely a *valid* `ContractType` — `AccountPermissionUpdateContract` itself is a valid bit that can be set on an `Active` permission (only `ClearABIContract`/`UpdateBrokerageContract` are excluded from the general "valid type" check, as shown by the test enumerating available contract types): [5](#0-4) 

By contrast, the *default* active-permission operations bitmap deliberately excludes `AccountPermissionUpdateContract`: [6](#0-5) 

This asymmetry means the system distinguishes "default/safe" active permissions (no self-modifying power) from ones an owner can explicitly (or be tricked into) empower with the ability to rewrite the account's own `Owner` permission — i.e., an `Active` key (a delegated, lower-trust credential comparable to a "session token") can be made functionally equal to the `Owner` key for the specific purpose of resetting the account's credentials. Once such an `Active` permission exists, holding that single active private key is sufficient to repeatedly issue `AccountPermissionUpdateContract` transactions and overwrite `Owner`/`Active`/`Witness` permissions — exactly analogous to how a still-valid OpenC3 session token could be used to repeatedly overwrite the account password even after the legitimate user "changed their password."

If a legitimate owner, upon suspecting a leaked/hijacked active key, only rotates the `Owner` permission's keys (the natural mental model of "changing my password") without realizing that the compromised key still sits inside an `Active` permission carrying the `AccountPermissionUpdateContract` bit, the attacker's key remains just as powerful as before: they can still sign a fresh `AccountPermissionUpdateContract` (using `permissionId` pointing at their still-valid `Active` permission) and overwrite the `Owner` permission again, re-seizing the account and locking the legitimate owner out — the same "persistence despite password reset" impact described in the advisory.

### Impact Explanation
An attacker who has ever obtained a private key placed in an `Active` permission with the `AccountPermissionUpdateContract` operation bit set retains full account-takeover capability indefinitely, independent of subsequent `Owner`-key rotations, as long as that specific `Active` permission entry (with that bit and that key) is not itself explicitly stripped in every future update. This can result in permanent loss of account control for the legitimate user/asset owner and is directly reachable by any holder of a signed transaction with the appropriate `permissionId` — no special node privilege or consensus role required.

### Likelihood Explanation
Exploitation requires that some `Active` permission on the target account has been configured (by the owner, by tooling, or by social engineering) with the `AccountPermissionUpdateContract` operation bit and that an attacker has obtained (or still controls) one of the keys in that permission with sufficient weight. This is a realistic multisig/delegation misconfiguration scenario (e.g., an exchange or DAO granting broad "ops" permissions to automate account management), and, once set up, the takeover/persistence technique itself requires only a single signed, broadcastable transaction — well within reach of an ordinary transaction broadcaster.

### Recommendation
Restrict the set of "valid" `ContractType` bits that can be set in an `Active` permission's `operations` to explicitly forbid `AccountPermissionUpdateContract` (in `AccountPermissionUpdateActuator.checkPermission`), mirroring the existing exclusion of `ClearABIContract`/`UpdateBrokerageContract`, so that only the `Owner` permission (`permissionId == 0`) can ever authorize rewriting an account's permissions. Alternatively, require `permissionId == 0` unconditionally inside `AccountPermissionUpdateActuator.validate()`/`execute()` regardless of what the `operations` bitmap says.

### Proof of Concept
1. Owner account `A` configures an `Active` permission (id=2) whose `operations` bitmap includes the bit for `ContractType.AccountPermissionUpdateContract`, and includes attacker's key `K_attacker` with sufficient weight to meet that permission's threshold (via `AccountPermissionUpdateActuator`, as validated/allowed by `checkPermission()`).
2. Attacker, holding `K_attacker`, signs and broadcasts an `AccountPermissionUpdateContract` with `permissionId = 2`, rewriting the `Owner` permission to contain only attacker-controlled keys. `TransactionCapsule.checkPermission`/`checkWeight` accept it because the Active permission's `operations` bit for this contract type is set; `AccountPermissionUpdateActuator.execute()` calls `AccountCapsule.updatePermissions(...)`, overwriting `Owner` unconditionally.
3. The legitimate owner, realizing the compromise, submits a new `AccountPermissionUpdateContract` signed with a fresh `Owner` key, but leaves the pre-existing `Active` permission id=2 (still containing `K_attacker` and the `AccountPermissionUpdateContract` bit) unchanged, believing the "password" (owner key) reset is sufficient.
4. Attacker signs another `AccountPermissionUpdateContract` with `permissionId = 2` using the still-valid `K_attacker`, again rewriting the `Owner` permission to attacker-controlled keys, regaining exclusive control of the account and locking out the legitimate owner — reproducing the "persistence after password reset" impact of the OpenC3 advisory.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
