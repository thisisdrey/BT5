### Title
Rewards emitted while a tracked token has zero supply are permanently skipped and remain stranded in `RewardsDistributor` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor` distributes `rewardToken` via a Compound-style supply index driven by a per-second `tokenSpeeds[token_]`. In `_calculateTokenIndex`, when `token_.totalSupply() == 0`, the accrual ratio is set to `0` so no one can earn the emission — yet `_newTimestamp` is still advanced to `block.timestamp` (lines 204–208). The `deltaTimestamps * speed` emission for every zero-supply window is therefore silently discarded. Once speeds are later set to `0`, the reward tokens funded into the contract for those windows can never be accrued or claimed by anyone, and the contract exposes no sweep/recovery function. This is the same bug class as the reference report (rewards accruing during a no-deposit period are never distributed and stay stuck).

### Finding Description
Relevant logic in `contracts/RewardsDistributor.sol`:

```solidity
function _calculateTokenIndex(TokenState memory _supplyState, IERC20 token_)
    private view returns (uint224 _newIndex, uint32 _newTimestamp)
{
    uint256 _speed = tokenSpeeds[token_];
    uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
    if (_deltaTimestamps > 0 && _speed > 0) {
        uint256 _totalSupply = token_.totalSupply();
        uint256 _tokensAccrued = _deltaTimestamps * _speed;
        uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
        _newIndex = (_supplyState.index + _ratio).toUint224();
        _newTimestamp = block.timestamp.toUint32();   // timestamp still advances
    }
    ...
}
```

- `_ratio = 0` when `totalSupply == 0`, but `_newTimestamp` still moves forward, permanently consuming the emission budget for that window. `_updateTokenIndex` persists this (lines 274–281).
- The code only guards the "speed re-enabled after being 0" case by resetting `timestamp` in `_updateTokenSpeed` (lines 300–303). There is no equivalent handling for `totalSupply == 0` while `speed > 0`.
- `_updateTokenSpeed` even allows the governor/keeper to set a non-zero speed for a token that has no deposits yet (`onlyIfTokenExists` only requires the token to be registered on the pool, lines 91–97).
- Claims are capped by accrued accounting: `_transferRewardIfEnoughTokens` only pays `tokensAccruedOf[account_]` and never sweeps the residual (lines 248–255). There is no `recover`/`sweep` function anywhere in the contract.

Reachable zero-supply windows include: (a) a `DepositToken` whose speed is set before the first `Pool.deposit`, (b) a deposit token fully withdrawn, and (c) a `DebtToken` when all debt is repaid — `DebtToken`/`DepositToken` call `updateBeforeMintOrBurn`/`updateBeforeTransfer` on every mint/burn/transfer, which is exactly what advances the timestamp (`DepositToken._mint`/`_burn` carry `updateRewardsBeforeMintOrBurn`, `contracts/DepositToken.sol:444,472`).

### Impact Explanation
The `deltaTimestamps * speed` emission for zero-supply periods never maps to any `tokensAccruedOf` balance. While emission continues the tokens are effectively still distributable to later accrual (accounting is index-based, not balance-based), but once the campaign ends (`updateTokenSpeed(token, 0)`), the surplus `rewardToken` balance — equal to all emissions during zero-supply windows — is frozen in the contract forever with no recovery path. This is permanent freezing of unclaimed yield, analogous to the referenced finding.

### Likelihood Explanation
The condition requires no attacker action: any period where a registered `DepositToken` or `DebtToken` has a non-zero `tokenSpeed` while its `totalSupply` is `0` permanently burns emission. This occurs naturally for newly incentivized tokens before first deposit, pools that get fully withdrawn, or debt tokens during full repayment. Note the leftover tokens are only recoverable indirectly (by future accruals while the campaign is still running), so the frozen amount materializes at the end of the emission program — matching the referenced Medium severity.

### Recommendation
Do not advance `tokenStates[token_].timestamp` when `totalSupply == 0` (freeze the accrual window until supply returns), or track undistributed emission and credit it when supply resumes. Additionally, consider adding a governor-gated `sweep` of the undistributed `rewardToken` surplus so leftover emissions are not permanently stranded.

### Proof of Concept
Hardhat-style PoC (same pattern as `test/RewardDistributor.test.ts`, which already mocks `msdTOKEN1`):

```ts
// Setup: rewardDistributor initialized with rewardToken (VSP),
// governor calls updateTokenSpeed(msdTOKEN1, 1e18) while msdTOKEN1.totalSupply() == 0.
// Fund distributor: vsp.mint(rewardDistributor.address, parseEther('1000'))

await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'));
msdTOKEN1.totalSupply.returns(0);
msdTOKEN1.balanceOf.returns(0);

// 40 seconds pass with zero supply
await increaseTimeOfNextBlock(40);
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address);

// Observation 1: index unchanged (still INITIAL_INDEX) but timestamp advanced 40s
const { index, timestamp } = await rewardDistributor.tokenStates(msdTOKEN1.address);
expect(index).to.eq(INITIAL_INDEX);            // no accrual recorded
// 40 * 1e18 reward tokens' worth of emission is permanently skipped

// Alice deposits later (supply now > 0) and accrues from the NEW timestamp only
msdTOKEN1.totalSupply.returns(parseEther('100'));
msdTOKEN1.balanceOf.whenCalledWith(alice.address).returns(parseEther('100'));
await increaseTimeOfNextBlock(10);
const claimable = await rewardDistributor['claimable(address)'](alice.address);
expect(claimable).to.eq(parseEther('10')); // only 10s of emission, not 50s

// Campaign ends; the 40-token surplus can never be claimed
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, 0);
// claimRewards drains only accrued amounts; ~40 rewardToken remain in the
// contract forever — RewardsDistributor has no sweep/recovery function.
```

Expected outcome: `index` stays at `INITIAL_INDEX` while `timestamp` advances, the zero-supply emission is never accrued by anyone, and the corresponding `rewardToken` balance is stranded in `RewardsDistributor` once speeds are zeroed.
