### Title
Unbounded per-endpoint Codahale metric leak via `HttpInterceptor` lets any HTTP client crash the node with OOM - (File: framework/src/main/java/org/tron/core/services/filter/HttpInterceptor.java)

### Summary
`HttpInterceptor`, a servlet `Filter` mapped to `/*` on every HTTP API context (`FullNodeHttpApiService`, solidity/PBFT node services), builds a metrics key by concatenating a request-derived `endpoint` string to a fixed prefix and calls `MetricsUtil.meterMark(...)`, which lazily creates and permanently stores a new Codahale `Meter`/`Counter`/`Histogram` object in a static, unbounded `MetricRegistry` for every distinct key it has never seen before.

### Finding Description
`HttpInterceptor.doFilter` computes `endpoint = contextPath + request.getServletPath()` and uses it, unsanitized and unbounded, as part of the metric key passed to `MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_QPS + endpoint, ...)` and `MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_OUT_TRAFFIC + endpoint, ...)`: [1](#0-0) 

`MetricsUtil` backs these calls with a single static `com.codahale.metrics.MetricRegistry` that has no eviction policy: `metricRegistry.meter(key)` (used inside `meterMark`) creates and permanently registers a new `Meter` object the first time a given `key` string is seen, and simply returns the existing one thereafter — entries are never removed: [2](#0-1) [3](#0-2) 

Because this filter is registered with path pattern `/*` and `DispatcherType.REQUEST` on every servlet handler, `Filter.doFilter` runs for every incoming HTTP request the node accepts, including requests to paths that don't match any registered servlet: [4](#0-3) 

`HttpServletRequest.getServletPath()` reflects Jetty's path matching, and for URLs that don't hit a mapped servlet, distinct request paths yield distinct `getServletPath()`/`getPathInfo()` values that flow straight into the metric key with no normalization, truncation, or whitelist. This is functionally the same bug class as ALPINE-CVE-2021-20210: a status/monitoring code path (Prometheus/Codahale metrics registry backing `MetricsServlet`'s `/monitor/getstatsinfo` and `NetMetricManager`) accumulates unbounded state as a side effect of ordinary, unauthenticated request handling, and the accumulation is never reclaimed — an attacker doesn't need any privileged action, just distinct URLs.

### Impact Explanation
Each unique path sent by a remote, unauthenticated client permanently registers new `Meter`/`Counter` objects in the JVM heap that are never freed for the lifetime of the process. An attacker can trivially generate unlimited unique paths (e.g. `/aaaa`, `/aaab`, `/aaac`, ...) against any exposed HTTP API port, growing the `MetricRegistry` without bound until the node exhausts heap memory and crashes (OutOfMemoryError) or becomes unresponsive due to GC pressure — a full node/witness DoS reachable by any anonymous HTTP client, matching the "node crash or halt" / "API the node can no longer serve" acceptance criteria.

### Likelihood Explanation
High. No authentication, no special contract or transaction is required — a simple HTTP GET loop against the exposed JSON-RPC/HTTP API port (default enabled on full nodes) with randomized paths is sufficient. The filter and vulnerable metric path are always active whenever `Args.getInstance().isNodeMetricsEnable()` returns true (the guard inside `meterMark`), which is a commonly enabled operational setting, not a rare or malicious-operator-only configuration.

### Recommendation
Do not derive metric registry keys directly from unbounded/unauthenticated request-controlled strings. Either: (1) map `endpoint` through the same fixed servlet-name/allow-list used elsewhere (e.g., `RateLimiterServlet` already uses `getClass().getSimpleName()` for its own per-endpoint keys) instead of raw `getServletPath()`, or (2) fall back to `MetricLabels.UNDEFINED` whenever the resolved endpoint does not match one of the explicitly registered servlet paths, or (3) cap the number of distinct dynamic metric keys `MetricsUtil` will create and reuse a bounded "other" bucket beyond that cap.

### Proof of Concept
1. Start a full node with `node.metrics.enable = true` (or equivalent config enabling `CommonParameter.isNodeMetricsEnable()`), exposing the HTTP API (default port 8090).
2. From any unauthenticated client, issue a large number of GET requests to distinct, non-existent paths under the API context, e.g. `curl http://<node>:8090/<random-32-char-string>` repeated with a fresh random suffix each time, at high rate and in parallel.
3. Observe (via `jconsole`/heap dump or `/monitor/getstatsinfo`) that the JVM's Codahale `MetricRegistry` backing `MetricsUtil` grows unboundedly with one new `Meter`/`Counter` entry per unique path, and that heap usage climbs monotonically and never decreases.
4. Continue the flood; the node eventually throws `OutOfMemoryError` or becomes unresponsive under GC pressure, halting API service (and potentially the whole JVM) — reproducing the "no filter files configured → unbounded memory growth → crash" pattern of ALPINE-CVE-2021-20210 in the java-tron HTTP status/metrics path. import javax.servlet.Filter;
import javax.servlet.FilterChain;
import javax.servlet.FilterConfig;
import javax.servlet.ServletRequest;
import javax.servlet.ServletResponse;
import javax.servlet.http.HttpServletRequest;
import javax.servlet.http.HttpServletResponse;
import lombok.extern.slf4j.Slf4j;
import org.eclipse.jetty.http.BadMessageException;
import org.eclipse.jetty.http.HttpStatus;
import org.tron.common.prometheus.MetricKeys;
import org.tron.common.prometheus.MetricLabels;
import org.tron.common.prometheus.Metrics;
import org.tron.core.metrics.MetricsKey;
import org.tron.core.metrics.MetricsUtil;

@Slf4j(topic = "httpInterceptor")
public class HttpInterceptor implements Filter {

  private final int HTTP_SUCCESS = 200;
  private final int HTTP_BAD_REQUEST = 400;
  private final int HTTP_NOT_ACCEPTABLE = 406;

  @Override
  public void init(FilterConfig filterConfig) {
  }

  @Override
  public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    String endpoint = MetricLabels.UNDEFINED;
    try {
      if (!(request instanceof HttpServletRequest)) {
        chain.doFilter(request, response);
        return;
      }
      String contextPath = ((HttpServletRequest) request).getContextPath();
      endpoint = contextPath + ((HttpServletRequest) request).getServletPath();
      CharResponseWrapper responseWrapper = new CharResponseWrapper(
              (HttpServletResponse) response);
      chain.doFilter(request, responseWrapper);
      HttpServletResponse resp = (HttpServletResponse) response;
      int size = responseWrapper.getByteSize();
      MetricsUtil.meterMark(MetricsKey.NET_API_OUT_TRAFFIC, size);
      MetricsUtil.meterMark(MetricsKey.NET_API_QPS);
      if (resp.getStatus() >= HTTP_BAD_REQUEST && resp.getStatus() <= HTTP_NOT_ACCEPTABLE) {
        MetricsUtil.meterMark(MetricsKey.NET_API_FAIL_QPS);
        Metrics.histogramObserve(MetricKeys.Histogram.HTTP_BYTES,
                size, MetricLabels.UNDEFINED, String.valueOf(responseWrapper.getStatus()));
        return;
      }
      if (resp.getStatus() == HTTP_SUCCESS) {
        MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_QPS + endpoint);
      } else {
        MetricsUtil.meterMark(MetricsKey.NET_API_FAIL_QPS);
        MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_FAIL_QPS + endpoint);
      }
      MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_OUT_TRAFFIC + endpoint, size);
      Metrics.histogramObserve(MetricKeys.Histogram.HTTP_BYTES,
              size, endpoint, String.valueOf(responseWrapper.getStatus()));
    } catch (Exception e) {
      String key = MetricsKey.NET_API_DETAIL_QPS + endpoint;
      if (MetricsUtil.getMeters(MetricsKey.NET_API_DETAIL_QPS).containsKey(key)) {
        MetricsUtil.meterMark(key, 1);
        MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_FAIL_QPS + endpoint, 1);
      }
      MetricsUtil.meterMark(MetricsKey.NET_API_QPS, 1);
      MetricsUtil.meterMark(MetricsKey.NET_API_FAIL_QPS, 1);
      if (e instanceof BadMessageException
          && ((BadMessageException) e).getCode() == HttpStatus.PAYLOAD_TOO_LARGE_413) {
        throw (BadMessageException) e;
      }
    }
  }

  @Override
  public void destroy() {
  }
}
