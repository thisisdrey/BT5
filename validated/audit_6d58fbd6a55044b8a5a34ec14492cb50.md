The claimed entrypoint doesn't exist: `execute_intents` (reached via `ft_on_transfer`'s `msg` field or otherwise) never calls nonce cleanup at all. Tracing `Engine::execute_signed_intent`, the only nonce-related state mutation is `commit_nonce`, which sets a single bit via `Nonces::commit` → `BitMap256::set_bit`, and never touches `cleanup_by_prefix`. [1](#0-0) 

The only place that invokes `cleanup_nonce_by_prefix`/`BitMap256::cleanup_by_prefix` (which does remove the *entire* 256-bit word for a given 31-byte prefix regardless of whether other bits in that word are still live) is the dedicated `GarbageCollector::cleanup_nonces` method. [2](#0-1) [3](#0-2) 

That method is gated with `#[access_control_any(roles(Role::DAO, Role::GarbageCollector))]` plus `assert_one_yocto()`, meaning only a `DAO` or `GarbageCollector` role holder can trigger the word-wide removal. [4](#0-3) 

Per the rules, the attacker is explicitly "not... any `Role` holder (`UnrestrictedWithdrawer`, `SaltManager`, `GarbageCollector`, ...)". Since there is no unprivileged path (via `ft_on_transfer`'s `msg` executing `execute_intents`, or any other `MultiPayload` submission) that reaches `cleanup_nonce_by_prefix`, the scenario described — an unprivileged attacker planting expired nonces to force cleanup of a victim's live nonce word — is not reachable. The only actor who can invoke word-wide cleanup is a privileged `GarbageCollector`/`DAO` role holder, which is out of scope by the rules of this audit.
