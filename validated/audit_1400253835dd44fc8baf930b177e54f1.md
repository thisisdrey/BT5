Audit Report

## Title
Unchecked payout transfer results in `claim_child_bounty`/`claim_bounty` lead to permanent fund lock on silent transfer failure - (File: `substrate/frame/child-bounties/src/lib.rs`, `substrate/frame/bounties/src/lib.rs`)

## Summary
`claim_child_bounty` and `claim_bounty` execute the curator-fee and beneficiary payouts via `T::Currency::transfer(..., AllowDeath)` and only validate the `Result` with `debug_assert!(...)`, which compiles to a no-op in release builds used by production chains. If the destination account (curator or beneficiary) does not yet exist and the transferred amount is below `ExistentialDeposit`, the transfer returns `Err` silently, yet the code unconditionally proceeds to remove the bounty/child-bounty storage entry and emit the `Claimed`/`BountyClaimed` event, permanently stranding the funds in the bounty account with no remaining reference to reclaim them. [1](#0-0) [2](#0-1) 

## Finding Description
In `claim_child_bounty`, `curator_fee = child_bounty.fee.min(balance)` and `payout = balance.saturating_sub(curator_fee)` are transferred out of `child_bounty_account` with `AllowDeath`, and both results are only checked via `debug_assert!`, which is stripped in release builds. [3](#0-2)  Immediately after, the code emits `Event::Claimed`, decrements `ParentChildBounties`, removes `ChildBountyDescriptionsV1`, and sets `*maybe_child_bounty = None`, deleting the only on-chain reference to `child_bounty_account_id(parent_bounty_id, child_bounty_id)`. [4](#0-3)  The identical pattern exists in `claim_bounty` in the parent pallet. [5](#0-4) 

Substrate's balance-transfer semantics require a newly-created destination account to meet the existential deposit; a transfer of a sub-ED amount to a not-yet-existing account fails regardless of the sender's `AllowDeath`/`Preservation` setting. Because `debug_assert!` does not execute in a release-profile runtime — the configuration all production Substrate/Polkadot-SDK chains use — this failure path is never actually detected or acted upon, so the pallet has no functioning guard against it despite the "should not fail" comments indicating an assumed, but unenforced, invariant.

The precondition (`curator_fee` or `payout` below ED, and the corresponding curator/beneficiary account not yet existing) is reachable through the normal call sequence: `propose_curator` sets `child_bounty.fee` (only constrained to `fee < child_bounty.value`), and `accept_curator` is called by the signer designated as curator. [6](#0-5) [7](#0-6)  Setting the fee is thus performed by the (parent bounty's) curator role, and `claim_child_bounty`/`claim_bounty` itself can then be triggered by any signed account. [8](#0-7) 

However, triggering the actual failure condition requires the party proposing/accepting the curator role (and choosing the beneficiary at award time) to deliberately or accidentally select a dust-sized fee/payout combined with a brand-new, unfunded destination account. This is not achievable by a fully unprivileged, uninvolved third party without cooperation from whoever controls curator/beneficiary selection for that specific bounty — it requires the bounty's own curator-assignment flow to produce the dust condition, which sits at the boundary between "ordinary user error" and a role that already has some standing (curator) within that specific bounty's lifecycle, rather than an arbitrary external attacker acting purely through public extrinsics against funds/state they have no legitimate role in.

## Impact Explanation
If triggered, the impact matches the "permanent user-fund lock" category in the impact gate: bounty-treasury-derived funds in `child_bounty_account_id(...)` (or `bounty_account_id(...)`) become stranded because the storage entry that is the only handle to reference or reclaim that account is deleted unconditionally in the same call as the failed transfer. This is a real code-level correctness gap: settlement (the transfer) can fail while payout state (removal + event) advances anyway, violating the invariant that payout state should only advance after settlement succeeds.

## Likelihood Explanation
The exploit requires a specific, engineered combination: a dust-sized `curator_fee`/`payout` and a corresponding curator/beneficiary account that has never held a balance. Setting the fee is done through `propose_curator` by the parent bounty's curator (a role with some pre-existing standing over that bounty, not an arbitrary anonymous caller), and the beneficiary is chosen at `award_child_bounty` time. While `claim_child_bounty` itself can be called by any signed account, actually causing the failure condition depends on the bounty's own curator/proposer selecting these dust parameters — this is a narrower and less clearly "unprivileged attacker via public extrinsics only" scenario than the claim frames it, since it depends on cooperation or misconfiguration by a role with legitimate authority over that specific bounty's fee/beneficiary parameters, rather than a party with no standing at all.

## Recommendation
Replace `debug_assert!(transfer_result.is_ok())` with proper error propagation (`?`) in both `claim_child_bounty` and `claim_bounty` so a failed transfer aborts the `try_mutate_exists`/`try_mutate` closure and rolls back the event emission, counter updates, and storage removal. Alternatively, ensure destination accounts are topped up to ED before the transfer, or use currency primitives that guarantee success for the amounts involved, and only finalize/remove bounty storage after confirming successful settlement.

## Proof of Concept
1. Propose and approve a parent bounty; assign a child-bounty curator via `propose_curator` with `fee` set to a dust value (e.g., 1 unit) via `propose_curator`. [6](#0-5) 
2. Have the designated curator (a brand-new, never-funded account) call `accept_curator`. [7](#0-6) 
3. Award the child bounty to a beneficiary and progress it to `PendingPayout`, waiting past `unlock_at`.
4. Call `claim_child_bounty` in a release-built runtime; `T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath)` returns `Err` because the destination cannot be created below ED, but `debug_assert!` is compiled out. [9](#0-8) 
5. Observe `Event::Claimed` fires and the `ChildBounties` entry is removed despite the failed transfer, leaving funds permanently stranded in `child_bounty_account_id(parent_bounty_id, child_bounty_id)`. [4](#0-3)

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.take().ok_or(Error::<T, I>::InvalidIndex)?;
				if let BountyStatus::PendingPayout { curator, beneficiary, unlock_at } =
					bounty.status
				{
					ensure!(Self::treasury_block_number() >= unlock_at, Error::<T, I>::Premature);
					let bounty_account = Self::bounty_account_id(bounty_id);
					let balance = T::Currency::free_balance(&bounty_account);
					let fee = bounty.fee.min(balance); // just to be safe
					let payout = balance.saturating_sub(fee);
					let err_amount = T::Currency::unreserve(&curator, bounty.curator_deposit);
					debug_assert!(err_amount.is_zero());

					// Get total child bounties curator fees, and subtract it from the parent
					// curator fee (the fee in present referenced bounty, `self`).
					let children_fee = T::ChildBountyManager::children_curator_fees(bounty_id);
					debug_assert!(children_fee <= fee);

					let final_fee = fee.saturating_sub(children_fee);
					let res =
						T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
					debug_assert!(res.is_ok());
					let res =
						T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
					debug_assert!(res.is_ok());

					*maybe_bounty = None;

					BountyDescriptions::<T, I>::remove(bounty_id);
					T::ChildBountyManager::bounty_removed(bounty_id);

					Self::deposit_event(Event::<T, I>::BountyClaimed {
						index: bounty_id,
						payout,
						beneficiary,
					});
					Ok(())
