### Title
Unbounded per-receipt subsidized_amount accumulation via repeated 1-yoctoNEAR promise_batch_action_function_call_weight calls on zero-balance accounts - (File: runtime/near-vm-runner/src/logic/logic.rs)

### Summary
`promise_batch_action_function_call_weight` grants a "skip deduct" subsidy of 1 yoctoNEAR whenever `amount == 1` and `current_account_balance.is_zero()`, intending to cap the subsidy once per zero-balance account. Because the subsidy path never actually mutates `current_account_balance` (only `subsidized_amount` is incremented), every subsequent call within the same `FunctionCall` receipt still observes a zero balance and re-triggers the subsidy, letting a single receipt accumulate `K` yoctoNEAR of subsidized value for `K` calls instead of the documented single-yoctoNEAR cap.

### Finding Description
In `runtime/near-vm-runner/src/logic/logic.rs` (`promise_batch_action_function_call_weight`, ~lines 3097-3112): [1](#0-0) 

```rust
let skip_deduct = amount == Balance::from_yoctonear(1)
    && self.config.one_yocto_on_promise
    && self.result_state.current_account_balance.is_zero();
if skip_deduct {
    self.result_state.subsidized_amount = self
        .result_state
        .subsidized_amount
        .checked_add(amount)
        .expect("subsidized_amount overflow");
} else {
    self.result_state.deduct_balance(amount)?;
}
```

The `skip_deduct` branch intentionally bypasses `deduct_balance`, which is the only code path that would otherwise decrement `current_account_balance`. As a result, `current_account_balance` is left unchanged (still zero) after every subsidized call. Because the check re-evaluates `current_account_balance.is_zero()` fresh on every invocation within the same host-function execution, an attacker-controlled contract can call `promise_batch_action_function_call_weight` (or the related `promise_batch_action_function_call` wrapper, and potentially `promise_yield_create_with_id`) `K` times in a single `FunctionCall`, each time passing `amount = 1`. Each call independently satisfies `skip_deduct` and adds 1 yoctoNEAR to `subsidized_amount`, producing `subsidized_amount == K` for a single receipt/account with genuinely zero balance throughout.

This directly contradicts the intended "capped at 1 yoctoNEAR per call" semantics implied by the comment ("Allow attaching exactly 1 yoctoNEAR to a promise function call when the contract has zero balance") — the cap is per zero-balance-check evaluation, not per account or per receipt, so it multiplies with the number of promise actions issued.

No existing check (access-key permission, gas metering, or storage staking) prevents this, since the attacker only needs a funded account able to deploy a contract and issue ordinary `FunctionCall` actions containing many promise batch actions; gas costs for issuing more promise actions are paid normally and do not police the subsidized value logic.

### Impact Explanation
This is a token-inflation bug: it lets an attacker mint `K` yoctoNEAR of value per receipt "for free" via `subsidized_amount`, where `K` is bounded only by how many `promise_batch_action_function_call_weight` calls fit within gas/receipt-size limits of one `FunctionCall`. While the per-call value is at yoctoNEAR-scale, this violates the value-conservation invariant meant to be enforced end-to-end against `total_balance_burnt`/total supply reconciliation (referenced in `chain/chain/src/runtime/mod.rs` and `runtime/runtime/src/lib.rs` `subsidized_amount` accounting). Repeated across many receipts/blocks this could scale to a systemic, reproducible violation of NEAR's value-conservation invariant, which maps to the "token inflation" bounty category even though the marginal amount per call is minimal.

### Likelihood Explanation
Preconditions are trivially met by an unprivileged attacker: fund an ordinary account, deploy a contract that in a single `FunctionCall` execution calls `promise_batch_action_function_call_weight` with `amount = 1` many times (bounded by gas/prepaid gas and receipt size limits, but easily tens or more per call). No special permissions, validator access, or leaked keys are required. The exploit is fully repeatable across any number of receipts/blocks.

### Recommendation
Track whether the zero-balance subsidy has already been granted within the current receipt/execution context (e.g., a boolean flag or count limit in `result_state`) rather than re-checking `current_account_balance.is_zero()` on every call, since that check is invariant across calls in the `skip_deduct` path. Alternatively, cap `subsidized_amount` to a maximum of 1 yoctoNEAR per receipt/account explicitly, independent of how many qualifying promise actions are issued.

### Proof of Concept
Add a runtime apply-path integration test (e.g., in `runtime/runtime/src/tests/apply.rs`) that:
1. Creates a funded account and deploys a test contract exposing a method that internally invokes the promise-batch-action host function (`promise_batch_action_function_call_weight`) `K = 50` times with `amount = 1` on a zero-balance deterministic/target account within a single `FunctionCall`.
2. Applies the resulting receipt via the runtime apply path and inspects `ExecutionResultState`/`apply_result.stats.balance.subsidized_amount`.
3. Assert that `subsidized_amount == 50` (demonstrating the multiplication) rather than the documented cap of `1`, while confirming `current_account_balance` remained zero across all `K` calls (proving `skip_deduct` never triggered `deduct_balance`).
4. Cross-check `total_balance_burnt` accounting in `chain/chain/src/runtime/mod.rs` to show the extra 49 yoctoNEAR is not accounted for as burnt/deducted anywhere, breaking supply conservation for that receipt.
