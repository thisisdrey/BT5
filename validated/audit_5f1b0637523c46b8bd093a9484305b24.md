## Title
`ERC20Transactor::withdraw_asset_with_surplus` / `deposit_asset_with_surplus` let a malicious ERC20 contract DoS XCM asset transfers by reverting or returning oversized returndata - ([File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs])

### Summary
`ERC20Transactor` is a `TransactAsset` implementation used to move XCM-held ERC20 assets by calling the arbitrary `pallet-revive` (EVM/PVM) contract that represents the asset, exactly the low-level, unmetered-consequence "external call inside a value-moving path" pattern described in the external report. The contract invoked is user/attacker-controlled (any address registered as an ERC20 asset kind matched by `Matcher`), and its `transfer` call is made via `pallet_revive::Pallet::<T>::bare_call`. A malicious or buggy ERC20 implementation can unconditionally revert or return malformed/oversized data, causing `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` to return `Err(XcmError::FailedToTransactAsset(..))` every single time, for every account, permanently.

### Finding Description
`withdraw_asset_with_surplus` ( [1](#0-0) ) and `deposit_asset_with_surplus` ( [2](#0-1) ) both:

1. Encode an `IERC20::transferCall` and invoke `pallet_revive::Pallet::<T>::bare_call` on the asset's contract address (`asset_id`/`asset_contract_id`), which is fully attacker-chosen at asset-registration time — this is functionally the same "low-level call to an operator/attacker-controlled contract in the middle of a fund-moving flow" primitive as the report's `ConsensusLayerFeeDispatcher`.
2. Treat *any* revert (`return_value.did_revert()`), ABI-decode failure, or `false` boolean return as a hard `Err(XcmError::FailedToTransactAsset(...))` ( [3](#0-2) , [4](#0-3) ).
3. Propagate the error to the XCM executor. In the XCM engine, a failing `TransactAsset::withdraw_asset`/`deposit_asset` call for one instruction aborts and traps the currently-held assets (or fails the whole message, depending on the calling instruction) — there is no per-asset isolation, no circuit breaker, and no fallback path if the contract that backs a given "ERC20 asset kind" is malicious or simply buggy (e.g., a contract whose `transfer` always returns `false`, always reverts, or returns oversized/garbage return-data that fails ABI decoding).

Unlike native `pallet-assets`/`pallet-balances` transfers, which are entirely runtime-controlled and cannot arbitrarily fail based on external code, this transactor delegates the fund-movement decision to attacker-supplied bytecode running inside `pallet-revive`. Once an asset is registered with a malicious contract as its backing address, **every future XCM deposit/withdraw for that asset id will deterministically fail**, and any assets already placed in the XCM holding register for that instruction get trapped (`AssetsTrapped`) rather than delivered, matching the "permanent user-fund or bridge-state lock" and "public underpriced work that... stalls bridge processing" impact categories.

Existing guards do not stop this: `WeightLimit`/`StorageDepositLimit` only bound resource consumption of the call, not its *semantic* outcome; there is no allow-list, sanity check, or retry/quarantine mechanism around the contract's return value, and the whole transactor design intentionally "enforces balance constraints [...] by the ERC20 smart contract itself rather than the runtime" (per the code's own comment at [5](#0-4) ), i.e., the runtime fully trusts an externally-controlled contract to not weaponize its own call outcome.

### Impact Explanation
Any XCM message that attempts to move (withdraw or deposit) a maliciously-backed "ERC20 asset kind" through this transactor will permanently fail: assets already withdrawn into XCM holding for that instruction can be trapped on the local chain (`AssetsTrapped`), while the deposit side to the intended beneficiary never happens. Because the failure is deterministic and depends solely on adversarial contract code chosen once at asset registration, this is a durable underpriced-work / fund-lock vector rather than a one-off revert: every subsequent transfer attempt for that asset consumes weight/deposit and fails identically, degrading bridge/XCM processing for that asset class and permanently locking value routed through it.

### Likelihood Explanation
Likelihood depends on how "ERC20 asset kind" contracts get registered for use with `ERC20Transactor`/`Matcher`; if that registration path is permissioned to trusted governance, exploitation requires a privileged/governance actor (out of scope per the impact gate). However, if `Matcher: MatchesFungibles<H160, u128>` can match arbitrary user-supplied contract addresses (e.g., a generic "any revive contract implementing IERC20" matcher used for permissionless foreign-asset bridging), an unprivileged attacker can deploy a hostile `IERC20` contract and register/route XCM traffic to it, triggering the DoS/lock without any admin, relayer, validator, or key compromise. The exact registration/matcher configuration used in production runtimes was not available with the tools used here, so likelihood cannot be fully confirmed to be unprivileged-attacker-reachable in the currently deployed asset-hub configuration; this should be verified against the concrete `Matcher` implementation wired into whichever runtime enables `ERC20Transactor`.

### Recommendation
- Do not let a single misbehaving/malicious asset-backing contract deterministically DoS the whole transfer path: bound the returndata size read from the call (mirroring the report's "restrict `returndata` to a couple of bytes" advice) before ABI-decoding.
- On contract revert/failure, avoid propagating a hard, permanently-repeating `XcmError` without a way to quarantine or blacklist the offending asset id; consider emitting a diagnostic event and returning a specific, distinguishable error that governance/asset-registration logic can act on (e.g., auto-deregister an asset whose backing contract consistently fails).
- Ensure whatever `Matcher` is used in production only allows registering ERC20 asset kinds through a vetted/permissioned process, and document/verify this invariant, since the transactor design inherently trusts the backing contract's return value for fund-movement semantics.

### Proof of Concept
1. Deploy (via `pallet-revive`) a minimal "ERC20" contract whose `transfer(address,uint256)` function always executes `revert()` (or always returns `false`, or writes an oversized/garbage return buffer that fails `IERC20::transferCall::abi_decode_returns_validate`).
2. Register this contract's address as an ERC20 asset kind matched by the runtime's `Matcher: MatchesFungibles<H160, u128>` configuration used with `ERC20Transactor`.
3. Submit any XCM program that performs `WithdrawAsset`/`DepositAsset` for that asset id (e.g., a reserve transfer or teleport routed through this transactor).
4. Observe that `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` return `Err(XcmError::FailedToTransactAsset(...))` deterministically every time ( [3](#0-2) ), causing assets to be trapped/locked and the transfer to never complete, for every future attempt involving this asset id.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}
