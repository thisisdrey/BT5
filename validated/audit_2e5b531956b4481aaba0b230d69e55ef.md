### Title
ValidateMultiSign Precompile Double-Counts Multi-Sig Weight via ECDSA Signature Malleability - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (accessible from any smart contract via the `validatemultisign` opcode call) recovers a signer address from each supplied signature and accumulates permission weight. Because java-tron's ECDSA signature validation never enforces canonical/low-`S` values, an attacker can derive a second, distinct-looking, but still valid signature `(r, N-s, v')` for the exact same message hash from a single legitimately obtained signature — the classic ECDSA malleability transform. `ValidateMultiSign`'s duplicate-detection logic only skips an entry when the *exact byte-for-byte* signature repeats; it does not dedupe by recovered address alone, so two malleated variants of the same signer's signature are counted as two independent approvals, inflating `totalWeight` and potentially reaching the permission threshold with only one real signer.

### Finding Description
Signature component validation in both crypto engines omits the canonical-`S` (or equivalent) check that would reject the malleated companion signature: [1](#0-0) 
The class does provide a `toCanonicalised()` helper, but it is never invoked on the verification/recovery path used by `ValidateMultiSign`: [2](#0-1) 
Because verification (and the SM2 variant, which has the identical gap) is recovery-based — `signatureToAddress`/`recoverPubBytesFromSignature` — an attacker who has *any* valid signature `(r, s, v)` from a real key holder for message hash `h` can compute `s' = N - s` and flip the recovery id `v' = v XOR 1`; the pair `(r, s', v')` recovers to the exact same public key/address for the same `h`, with no knowledge of the private key required: [3](#0-2) 

`ValidateMultiSign` then merges the recovered address with the raw signature bytes to build its dedupe key and only skips counting when this *combined* byte string was already seen — if only the address matches but the signature bytes differ (as with a malleated variant), it proceeds to add the weight again instead of skipping: [4](#0-3) 

This lets a single signer's one signature be expanded into up to `MAX_SIZE` (5) distinct valid signatures for the same hash, each contributing that signer's full weight toward `permission.getThreshold()`.

### Impact Explanation
Any smart contract that gates privileged actions (fund transfers, admin operations, on-chain permission checks) behind `validatemultisign` can be tricked into believing a multi-signature threshold was met when in fact only a single (or fewer than required) distinct signers actually approved — a concrete unauthorized-operation / theft-of-funds vector reachable purely from a contract call using a single legitimately signed message. Because weight/threshold logic (`TransactionCapsule.getWeight`, `Permission.getThreshold`) is the same primitive used elsewhere for TRON account multisig authorization, the underlying malleability also means the recovered-address based verification model tolerates multiple distinct signature encodings per signer/message pair, which is unsafe wherever code assumes signature bytes (not just recovered address) are unique per approval.

### Likelihood Explanation
Exploitation requires only: (1) obtaining one valid signature over the exact `(address, permissionId, data)` hash the contract will check (e.g., the attacker is one of the legitimate co-signers, or a signature leaks/is reused), and (2) simple modular arithmetic (`s' = N - s`, flip recovery bit) — no cryptographic breaking, no private key needed. The precompile is directly callable from any TVM contract, and inputs (`sigArraySize` up to `MAX_SIZE`) are attacker-controlled at call time.

### Recommendation
In `ValidateMultiSign.execute`, deduplicate strictly by `recoveredAddr` (not by the address+signature-bytes composite) so any second signature recovering to an address already counted is always skipped, regardless of its `(r,s,v)` encoding. Additionally, enforce canonical signature form (reject non-low-`S` signatures, e.g., by calling `ECDSASignature.toCanonicalised()`/an equivalent SM2 check and rejecting mismatches) inside `ECDSASignature.validateComponents`/`SM2Signature.validateComponents` so malleated signatures are rejected at the earliest validation point across all consumers (`ECRecover` precompile, `TransactionCapsule.checkWeight`, `ValidateMultiSign`).

### Proof of Concept
1. Signer A holds private key `d` and produces one valid signature `sigA = (r, s, v)` over `hash = SHA256/SM3(address || permissionId || data)` for a multisig-protected contract call with threshold requiring weight from 2 keys (or weight 2 from key A alone counted twice).
2. Attacker computes `s' = SECP256K1N.subtract(s)` and `v' = (v == 27) ? 28 : 27`, forming `sigA2 = (r, s', v')`. Both `sigA` and `sigA2` pass `ECDSASignature.validateComponents` (no low-S check) and both recover to A's address via `recoverPubBytesFromSignature`.
3. Attacker calls the `validatemultisign` precompile (`ValidateMultiSign.execute`) with `signatures = [sigA, sigA2, ...]`. For the second entry, `recoveredAddr` equals A's address (already in `executedSignList`), but the merged `sign` bytes differ from the first entry's merged bytes, so the `continue` (skip) branch is not taken; `TransactionCapsule.getWeight` is called again and A's weight is added a second time.
4. `totalWeight` reaches `permission.getThreshold()` using only signer A's single real signature, and the precompile returns success (`dataOne()`), authorizing an action that should have required additional independent signers.

  @Nullable
  public static byte[] recoverPubBytesFromSignature(int recId,
      ECDSASignature sig, byte[] messageHash) {
    check(recId >= 0, "recId must be positive");
    check(sig.r.signum() >= 0, "r must be positive");
    check(sig.s.signum() >= 0, "s must be positive");
    check(messageHash != null, "messageHash must not be null");
    // 1.0 For j from 0 to h   (h == recId here and the loop is outside
    // this function)
    //   1.1 Let x = r + jn
    BigInteger n = CURVE.getN();  // Curve order.
    BigInteger i = BigInteger.valueOf((long) recId / 2);
    BigInteger x = sig.r.add(i.multiply(n));
    //   1.2. Convert the integer x to an octet string X of length mlen
    // using the conversion routine
    //        specified in Section 2.3.7, where mlen = ⌈(log2 p)/8⌉ or
    // mlen = ⌈m/8⌉.
    //   1.3. Convert the octet string (16 set binary digits)||X to an
    // elliptic curve point R using the
    //        conversion routine specified in Section 2.3.4. If this
    // conversion routine outputs “invalid”, then
    //        do another iteration of Step 1.
    //
    // More concisely, what these points mean is to use X as a compressed
    // public key.
    ECCurve.Fp curve = (ECCurve.Fp) CURVE.getCurve();
    BigInteger prime = curve.getQ();  // Bouncy Castle is not consistent
    // about the letter it uses for the prime.
    if (x.compareTo(prime) >= 0) {
      // Cannot have point co-ordinates larger than this as everything
      // takes place modulo Q.
      return null;
    }
    // Compressed allKeys require you to know an extra bit of data about the
    // y-coord as there are two possibilities.
    // So it's encoded in the recId.
    ECPoint R = decompressKey(x, (recId & 1) == 1);
    //   1.4. If nR != point at infinity, then do another iteration of
    // Step 1 (callers responsibility).
    if (!R.multiply(n).isInfinity()) {
      return null;
    }
    //   1.5. Compute e from M using Steps 2 and 3 of ECDSA signature
    // verification.
    BigInteger e = new BigInteger(1, messageHash);
    //   1.6. For k from 1 to 2 do the following.   (loop is outside this
    // function via iterating recId)
    //   1.6.1. Compute a candidate public key as:
    //               Q = mi(r) * (sR - eG)
    //
    // Where mi(x) is the modular multiplicative inverse. We transform
    // this into the following:
    //               Q = (mi(r) * s ** R) + (mi(r) * -e ** G)
    // Where -e is the modular additive inverse of e, that is z such that
    // z + e = 0 (mod n). In the above equation
    // ** is point multiplication and + is point addition (the EC group
    // operator).
    //
    // We can find the additive inverse by subtracting e from zero then
    // taking the mod. For example the additive
    // inverse of 3 modulo 11 is 8 because 3 + 8 mod 11 = 0, and -3 mod
    // 11 = 8.
    BigInteger eInv = BigInteger.ZERO.subtract(e).mod(n);
    BigInteger rInv = sig.r.modInverse(n);
    BigInteger srInv = rInv.multiply(sig.s).mod(n);
    BigInteger eInvrInv = rInv.multiply(eInv).mod(n);
    ECPoint.Fp q = (ECPoint.Fp) ECAlgorithms.sumOfTwoMultiplies(CURVE
        .getG(), eInvrInv, R, srInv);
    return q.getEncoded(/* compressed */ false);
  }
