### Title
Forged `RelayData` entries in P2P messages let a remote peer inject bogus relay-stat credits for arbitrary neighbors - (File: stackslib/src/net/chat.rs)

### Summary
`ConversationP2P::process_relayers` (chat.rs:2057-2085) only checks the `relayers` vector for cycles and for self-references before crediting every listed `RelayData.peer` in `self.stats.add_relayer(...)`. There is no cryptographic binding between a `RelayData` entry and any action performed by the referenced peer, so a single malicious sender can attribute relay credit to any `NeighborAddress` it chooses.

### Finding Description
The claimed equality "relayer stat credited == peer that cryptographically relayed this message" is broken. `process_relayers` performs exactly two checks:
- `check_relayer_cycles` (chat.rs:2030-2039): dedups by `public_key_hash` within the same list.
- `check_relayers_remote` (chat.rs:2042-2050): rejects if the local node's own address appears in the list.

Neither check verifies that the peer named by `relayer.peer` (a `NeighborAddress`, i.e. IP/port/public-key-hash chosen entirely by the sending peer) ever handled, signed, or forwarded the message. The loop at chat.rs:2079-2082 unconditionally calls `self.stats.add_relayer(&relayer.peer, (preamble.payload_len - 1) as u64)` for every entry in the wire-supplied vector. Since `RelayData` carries no signature over "I actually relayed this," an attacker directly connected to the victim node can construct a message (e.g. a `GetMicroblocksUnconfirmed`/blocks-push/relay-bearing message) whose `relayers` field lists any `NeighborAddress` values it likes, including ones for peers it does not control and that never touched the message.

### Impact Explanation
The forged credits accumulate in the victim's own `NeighborStats`/relay-stats table for that conversation, which is later read by `get_inbound_relay_rankings`/`get_outbound_relay_rankings` in `stackslib/src/net/relay.rs` and used by `sample_broadcast_peers` in `stackslib/src/net/p2p.rs` to decide which peers to prioritize when relaying/gossiping data. By repeatedly sending messages with forged relayer lists, an attacker can inflate or deflate the perceived relay reputation of arbitrary peers, steering the victim's broadcast-peer selection toward attacker-chosen (possibly attacker-controlled or Sybil) neighbors and away from legitimate ones. This is a local (per-victim-node) poisoning of internal peer-selection state, not a globally stored/served canonical artifact — it does not forge blocks, transactions, or StackerDB state, and it does not crash the node or grant unauthorized writes to consensus-relevant state.

### Likelihood Explanation
The attacker only needs an established P2P conversation with the victim (no privileged role, no secret) and the ability to send any message type that carries a `relayers: Vec<RelayData>` field (blocks push, microblocks push, etc.). Cost is a single crafted message, and the attack is fully repeatable/automatable since there's no rate limiting tied to relayer-list content itself.

### Recommendation
Do not attribute cryptographic trust to unauthenticated `RelayData.peer` entries. Either drop the relay-stats-based prioritization mechanism entirely, or bind relayer credit to information verified at the transport/handshake layer (i.e., only credit the actual, handshake-authenticated `NeighborKey` of the conversation partner that sent the bytes, not arbitrary entries the sender claims were involved). At minimum, cap the influence of unauthenticated relayer-list content on `sample_broadcast_peers` selection so a single peer cannot arbitrarily inflate/deflate another peer's ranking.

### Proof of Concept
Rust unit test in `stackslib/src/net/chat.rs` test module:
1. Construct a `ConversationP2P` for a test peer as in existing tests (see `stackslib/src/net/tests/relay/epoch2x.rs` for stats-related test scaffolding).
2. Build a `Preamble` with a valid `payload_len`, and a `relayers: Vec<RelayData>` containing one `RelayData` whose `peer: NeighborAddress` is a "victim" address the test peer never sent traffic through.
3. Call `conversation.process_relayers(&local_peer, &preamble, &relayers)` directly.
4. Assert it returns `true` and that `conversation.stats` now contains a relay-count entry for the victim's `NeighborAddress` equal to `(preamble.payload_len - 1) as u64`, despite the victim peer never having participated in the connection — demonstrating the forged credit is recorded with no cryptographic verification.
