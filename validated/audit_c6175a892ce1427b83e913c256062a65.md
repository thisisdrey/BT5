### Title
Unauthenticated nonce-address dedup allows fee-fee attacker to evict a victim's already-buffered durable-nonce transaction - (File: core/src/banking_stage/transaction_scheduler/transaction_state_container.rs)

### Summary
The `TransactionStateContainer` keeps a `nonces_in_use: HashMap<Pubkey, TransactionPriorityId>` that maps a durable-nonce account address to the single highest-priority buffered transaction referencing it, and exposes `get_nonce_transaction_priority_id`/`set_nonce_transaction_priority_id` for the scheduler to enforce a one-transaction-per-nonce-address policy. The dedup key is purely the nonce account address extracted structurally from the transaction's instructions; it is never checked against the transaction's actual signers/authority. An attacker who merely knows the victim's public nonce account address (which is not secret) can submit their own validly self-signed transaction that structurally references that nonce address with a higher priority fee, causing the scheduler to call `remove_by_id` on the victim's legitimately buffered nonce transaction and evict it from `id_to_transaction_state`, even though the attacker's transaction is not authorized to advance that nonce and will fail at execution time.

### Finding Description
`TransactionStateContainer::set_nonce_transaction_priority_id` (core/src/banking_stage/transaction_scheduler/transaction_state_container.rs, lines 251-262) unconditionally inserts a `(nonce_address, priority_id)` pair into `nonces_in_use`, overwriting whatever entry previously existed for that address: [1](#0-0) 

`get_nonce_transaction_priority_id` (lines 244-249) is the lookup used by the caller (in `receive_and_buffer.rs`) to detect a conflicting existing entry for the same nonce address: [2](#0-1) 

Eviction of the previous holder is performed through the generic `remove_by_id` (lines 207-212), which unconditionally deletes the referenced `TransactionId` from both the priority queue and the `id_to_transaction_state` slab: [3](#0-2) 

Nothing in this container-level API validates that the new transaction claiming the nonce address is signed by the nonce account's authority, or by the same signer as the transaction being evicted. The key used for the whole dedup/eviction decision is only the `Pubkey` of the nonce account — a value that is public on-chain (any client can read the nonce account or observe it in prior transactions) and requires no special privilege to reference. A transaction can structurally reference an `AdvanceNonceAccount`-style nonce account as its "nonce transaction" indicator without actually being a validly authorized nonce advance (the authority signature requirement for a real `AdvanceNonceAccount` CPI is enforced only later, during program execution in the runtime — not at the point where the scheduler assigns/dedups the nonce address in `TransactionStateContainer`). Because sigverify only checks that supplied signatures match the signers declared in the message (not that a particular pubkey is the correct nonce authority for a particular account), an attacker's self-signed transaction passes sigverify and reaches the container logic, where it is treated identically to a legitimately-authorized nonce transaction purely based on address equality.

### Impact Explanation
This falls under the ingress/dedup fairness bounty category described in the prompt ("svm/src/account_loader.rs -> Scope: High... an unprivileged attacker can craft transaction batches that permanently strand or silently drop other users' fee-paying transactions through lock conflicts, priority handling, or buffer eviction"). A victim's correctly-formed, fee-paying, properly-authorized nonce transaction can be silently and permanently dropped from `id_to_transaction_state` (tracked by `num_evicted_on_nonce_dedup` in `scheduler_metrics.rs`) without the victim being notified, purely because an unrelated attacker who does not control the nonce authority submitted a marginally higher-priority transaction that merely references the same public nonce address. The victim's transaction never executes and the attacker's replacement transaction is very likely to fail at execution (missing authority signature), so the net effect is denial of service against the victim with no benefit to the network, degrading fairness/availability guarantees of the buffering layer.

### Likelihood Explanation
Exploitation only requires: (1) knowledge of the victim's nonce account address, which is either publicly queryable on-chain or observable from any prior transaction the victim broadcasts, and (2) the ability to craft and sign an ordinary self-funded transaction whose instruction set is structurally recognized by the scheduler as referencing that nonce account, with a compute-unit price marginally above the victim's. Both preconditions are trivially satisfiable by any unstaked remote client with a QUIC/UDP connection to the leader's TPU, requiring no validator/operator privileges, no leaked keys, and no more than ordinary transaction submission. This is fully repeatable for any victim nonce account and any number of times.

### Recommendation
Bind the nonce-dedup key to more than just the nonce account address — e.g., verify (or record alongside the entry) the actual authorized nonce authority/signer for the currently-buffered transaction, and only allow a new transaction to preempt/evict the existing entry if it is signed by the same authority, or defer priority-based nonce eviction decisions until after a cheap authority-ownership check against the nonce account state. At minimum, do not let `remove_by_id` be invoked purely on `Pubkey` address collision without confirming the incoming transaction is capable of legitimately advancing that nonce.

### Proof of Concept
Integration test in `transaction_state_container.rs`/`receive_and_buffer.rs` test module:
1. Construct `victim_tx`: an `AdvanceNonceAccount` transaction properly signed by `victim_authority`, referencing `nonce_pubkey`, with priority fee `P`.
2. Insert `victim_tx` into `TransactionViewStateContainer` via the normal buffering path (`insert_new_transaction`/`set_nonce_transaction_priority_id`), and confirm `get_nonce_transaction_priority_id(&nonce_pubkey)` returns the victim's `TransactionPriorityId` and `id_to_transaction_state` contains the victim's `TransactionId`.
3. Construct `attacker_tx`: a transaction signed only by `attacker_keypair` (not `victim_authority`) that structurally references `nonce_pubkey` as its nonce address (e.g., via an `AdvanceNonceAccount`-shaped instruction naming `nonce_pubkey` and an authority pubkey the attacker doesn't control), with priority fee `P + 1`.
4. Feed `attacker_tx` through the same buffering path used by `handle_packet_batch_message`, triggering the "existing nonce priority id" check and `remove_by_id(existing_nonce_priority_id.id)`.
5. Assert: `id_to_transaction_state` no longer contains the victim's `TransactionId` (`get_transaction(victim_id).is_none()`), `nonces_in_use[nonce_pubkey]` now points to the attacker's id, and `num_evicted_on_nonce_dedup` metric incremented — demonstrating the victim's valid, properly-authorized, higher-effort transaction was silently dropped by an unauthorized third party.

        &mut self,

        if let Some(state) = self.id_to_transaction_state.get_mut(priority_id.id) {
