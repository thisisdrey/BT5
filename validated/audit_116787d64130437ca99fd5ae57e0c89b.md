### Title
Attacker claims rewards equal to full token balance when claiming in the same block a reward token is added — `accountIndexOf` zero-value treated as zero delta instead of `INITIAL_INDEX` - (contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` only substitutes `INITIAL_INDEX` for a missing per-account index when the global token index is strictly greater than `INITIAL_INDEX`. During the same block in which a token is registered via `_updateTokenSpeed` (index stored as `INITIAL_INDEX` = 1e18), any account's unset `accountIndexOf[token][account]` remains `0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account) * 1`. A public `claimRewards(accounts_, tokens_)` call in that block lets an attacker with a large DepositToken/DebtToken balance drain `rewardToken` from the distributor.

### Finding Description
The bug class of the reference report is an index/bounds error that corrupts accounting. The analog lives in the reward-index math:

- `_updateTokenSpeed` initializes a newly tracked token with `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` [1](#0-0) 
- In `claimRewards`, `_updateTokenIndex` computes `_deltaTimestamps = block.timestamp - _supplyState.timestamp`. In the same block this is `0`, so the index stays exactly `INITIAL_INDEX` [2](#0-1) 
- `_calculateTokenDelta` then evaluates `_accountIndex == 0 && _tokenIndex > INITIAL_INDEX`. Since `_tokenIndex == INITIAL_INDEX`, the fallback does not apply and `_accountIndex` stays `0`, giving `_deltaIndex = 1e18` and `_tokensDelta = token_.balanceOf(account_).wadMul(1e18) = balanceOf(account_)` [3](#0-2) 
- `_updateTokensAccruedOf` adds that delta into `tokensAccruedOf[account_]` and `claimRewards` pays it out via `_transferRewardIfEnoughTokens`, which transfers up to the distributor's full `rewardToken` balance [4](#0-3) 
- `claimRewards(address[] accounts_, IERC20[] tokens_)` is permissionless and takes attacker-chosen token and account arrays [5](#0-4) 

The correct check should be `_accountIndex == 0` → use `INITIAL_INDEX` whenever `_tokenIndex >= INITIAL_INDEX` (or initialize the account index at first touch), since a fresh account must accrue zero delta against the initial index, not `1e18`.

### Impact Explanation
Direct theft of reward funds. The attacker deposits a large amount of underlying (or mints debt, since DebtToken `balanceOf` counts too) to maximize `token_.balanceOf(attacker)`, then calls `claimRewards` in the same block the governor adds the token. `tokensAccruedOf[attacker]` is credited with an amount equal to their DepositToken/DebtToken balance — denominated in `rewardToken` — and paid out up to the distributor's entire balance. The deposit can be withdrawn immediately after. All unclaimed yield held by the distributor is stolen.

### Likelihood Explanation
Requires the claim to land in the same block (same `block.timestamp`) as the governor's `updateTokenSpeed`/`updateTokenSpeeds`/`syncTokenSpeed` call that first registers a token. Reward token additions are public, scheduled events (reward program launches on each chain deployment), and same-block backrunning via bundles/Flashbots or simply observing the mempool is feasible on the deployed chains (mainnet, Optimism, Base, Hemi, Swell). The attacker needs capital only for the duration of one block (deposit → claim → withdraw), which flash liquidity can provide. No privileged role is needed; the attacker only front-runs/backruns a routine governance operation.

### Recommendation
In `_calculateTokenDelta`, treat an unset account index as `INITIAL_INDEX` whenever the stored index is non-zero:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

or more conservatively initialize `accountIndexOf[token_][account_] = INITIAL_INDEX` on first accrual. Additionally, set a fresh token's `timestamp` such that index accrual begins correctly, and consider requiring `token_.totalSupply() > 0` / a one-block delay before a newly added token is claimable.

### Proof of Concept
Hardhat fork test sketch (pool, deposit token `msdX`, and `RewardsDistributor` deployed and registered):

```typescript
// 1. Attacker deposits underlying to get a large deposit-token balance
await underlying.mint(attacker.address, ATTACK_AMOUNT);
await underlying.connect(attacker).approve(msdX.address, ATTACK_AMOUNT);
await msdX.connect(attacker).deposit(ATTACK_AMOUNT); // balanceOf(attacker) = ATTACK_AMOUNT

// 2. In the SAME block as governor registers the reward token:
await ethers.provider.send("evm_setAutomine", [false]);
await distributor.connect(governor).updateTokenSpeed(msdX.address, speed);
await distributor.connect(attacker).claimRewards(attacker.address, [msdX.address]);
await ethers.provider.send("evm_mine");
await ethers.provider.send("evm_setAutomine", [true]);

// 3. Assert theft
// _deltaIndex = INITIAL_INDEX - 0 = 1e18  =>  _tokensDelta = ATTACK_AMOUNT
expect(await rewardToken.balanceOf(attacker.address)).to.eq(
  BigNumber.from(ATTACK_AMOUNT) // capped by distributor's rewardToken balance
);
```

The same-block constraint is what makes `block.timestamp - tokenStates[msdX].timestamp == 0`, which keeps `index == INITIAL_INDEX` and skips the `_accountIndex = INITIAL_INDEX` fallback.
