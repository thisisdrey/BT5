### Title
Unbounded tar entry count / size / depth in `extractTarToDirectory` allows resource-exhaustion DoS on target Gitaly node during `ReplicateRepository` - ([File: internal/gitaly/service/repository/replicate.go])

### Summary
`extractTarToDirectory` (used by `ReplicateRepository` → `createFromSnapshot` → `extractSnapshot`) iterates over an attacker-influenceable tar stream (produced by `GetSnapshot` on a source repository the attacker owns) without any cap on the number of tar entries, total decompressed bytes, or path depth. Each `TypeDir`/`TypeReg` entry results in a syscall (`os.MkdirAll`, file create/write), so a source repository engineered to contain a very large number of files/refs or deeply nested ref paths can force the receiving node to perform proportionally unbounded I/O work.

### Finding Description
`extractSnapshot` (internal/gitaly/service/repository/replicate.go:264-312) calls `GetSnapshot` against the source storage and pipes the returned tar stream straight into `extractTarToDirectory` (replicate.go:314-406). That function loops `tarReader.Next()` with only a context-cancellation check per iteration [1](#0-0) , calling `os.MkdirAll`/`extractFile` for every entry with no limit on entry count, cumulative bytes, or path depth beyond a prefix check that only guards against path traversal, not resource exhaustion.

The tar content itself comes from `CreateSnapshot`, which walks the real `.git` directory of the source repository (objects, refs, hooks, config) [2](#0-1) . Since GitLab allows ref names with arbitrary slash-separated path segments, an attacker who owns the source repository can create many refs (`refs/heads/<many segments>`) or a very large number of distinct refs, each of which becomes a real loose-ref file/directory on disk and therefore a real tar entry in the snapshot — this is not injected tar metadata but actual repository content the attacker controls through ordinary push operations.

### Impact Explanation
If successfully triggered, extraction of a snapshot with an extremely large number of entries or deeply nested directories would consume disk inodes, file descriptors, and CPU time on the target Gitaly node during `ReplicateRepository`, potentially degrading or denying service for other repositories co-located on that node (matches a resource-exhaustion / DoS impact class).

### Likelihood Explanation
Exploitability is constrained by factors not fully addressed by this code path alone: git/OS enforce per-component and total path length limits on ref names (bounding nesting depth to well under "thousands of levels"), and reaching millions of entries requires creating a correspondingly large number of real refs/objects, which is bounded by push size/rate limits and repository size quotas typically enforced elsewhere in GitLab/Gitaly before extraction is ever reached. `ReplicateRepository` is also an internal Gitaly-to-Gitaly RPC normally invoked by the replication/Praefect layer in response to repository mutations rather than directly callable by an end user, so the attacker only indirectly triggers this path by mutating a repo they own. Because of these bounding factors, the practical severity is lower than a "cheap" DoS, but the underlying code gap (no explicit cap on entry count/total size/depth in `extractTarToDirectory`) is real and should be hardened regardless of how large an attack currently needs to be to be effective.

### Recommendation
Add explicit bounds in `extractTarToDirectory`: a maximum number of tar entries, a maximum cumulative decompressed size (checked incrementally against `header.Size` and actual bytes written), and a maximum path depth/component-length check, aborting extraction with an error once any limit is exceeded. Consider also bounding it via a size/entry-count value derived from the source repository's known object/ref count so legitimate large repositories are not adversely affected while runaway archives are rejected early.

### Proof of Concept
```go
// internal/gitaly/service/repository/replicate_test.go (illustrative)
func TestExtractTarToDirectory_NoResourceLimits(t *testing.T) {
    var buf bytes.Buffer
    tw := tar.NewWriter(&buf)
    for i := 0; i < 200000; i++ { // simulate very large ref/object count
        hdr := &tar.Header{Name: fmt.Sprintf("refs/heads/branch-%d", i), Typeflag: tar.TypeReg, Size: 0, Mode: 0644}
        require.NoError(t, tw.WriteHeader(hdr))
    }
    require.NoError(t, tw.Close())

    dir := testhelper.TempDir(t)
    s := &server{logger: testhelper.NewLogger(t)}
    start := time.Now()
    err := s.extractTarToDirectory(context.Background(), &buf, dir)
    require.NoError(t, err)
    t.Logf("extraction of 200k entries took %s", time.Since(start)) // no cap enforced, scales linearly/superlinearly with entry count
}
```
Expected assertion in a hardened implementation: extraction should fail fast once a configured maximum entry count / total size / depth is exceeded, rather than proceeding to create hundreds of thousands of files with no limit.

		return structerr.NewInvalidArgument("%w", err)

		return err
	}
