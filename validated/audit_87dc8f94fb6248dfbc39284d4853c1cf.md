### Title
`ExchangeWithdrawActuator` computes and pays out the paired-token amount with no user-specified minimum, exposing exchange creators to front-run/sandwich value extraction - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The `ExchangeWithdrawContract` handler lets the creator of a Bancor-style TRX/TRC10 `Exchange` pair burn one side of the pool balance and receive a computed amount of the other token (`anotherTokenQuant`), but the contract provides no field for the caller to specify a minimum acceptable `anotherTokenQuant`. This mirrors the `withdraw_liquidity` slippage-protection gap in the external report, and is directly comparable to the sibling `ExchangeTransactionActuator`, which *does* implement this protection via its `expected` field.

### Finding Description
In `ExchangeWithdrawActuator.execute()`, `anotherTokenQuant` is derived purely from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio at execution time: [1](#0-0) 

The computed `anotherTokenQuant` is then unconditionally credited to the withdrawer with no lower-bound check: [2](#0-1) 

`doValidate()` only checks that `tokenQuant > 0`, `anotherTokenQuant > 0`, and a precision-drift bound - it never compares `anotherTokenQuant` against any value supplied by the transaction owner: [3](#0-2) 

Contrast this with `ExchangeTransactionActuator`, which supports exactly the missing protection: callers supply `contract.getExpected()`, and validation rejects the transaction if the computed output is below that expectation: [4](#0-3) 

`ExchangeWithdrawContract` (the protobuf message backing `ExchangeWithdrawActuator`) has no analogous `expected`/`min` field, so there is no way for a caller to protect a withdrawal the way a trade is protected.

Because a single `ExchangeTransactionContract` (buy/sell against the same exchange pool) can shift `firstTokenBalance`/`secondTokenBalance` arbitrarily within `dynamicStore.getExchangeBalanceLimit()`, and both trade and withdraw transactions are ordinary unprivileged transactions competing for block inclusion, an attacker who observes a pending `ExchangeWithdrawContract` in the mempool can:
1. Broadcast a large trade against the same `exchangeId` that shifts the pool ratio unfavorably for the withdrawer, timed to land immediately before the withdraw transaction.
2. Let the withdraw execute at the manipulated ratio, causing the creator to receive far less of `anotherTokenID` than the pre-attack ratio implied.
3. Reverse the trade afterward to restore the ratio and recapture the value extracted from the withdrawer, net of the small `calcFee()`.

### Impact Explanation
This allows a party who can influence transaction ordering (e.g., another user racing transactions, or a block producer, both of whom only need the ability to broadcast an ordinary signed `ExchangeTransactionContract`) to extract value from the exchange creator's withdrawal in a manner not covered by any existing precision/limit check. This is a concrete theft-of-funds vector against an unprivileged, valid contract flow (`ExchangeWithdrawContract` execution), analogous in root cause and impact to the original `withdraw_liquidity` slippage issue in the AMM pool manager.

### Likelihood Explanation
Reachable via two ordinary, unprivileged, already-permitted transaction types (`ExchangeTransactionContract` and `ExchangeWithdrawContract`) targeting the same `exchangeId`; no special privilege, malicious SR/witness role, or off-chain component is required — only normal transaction broadcasting and favorable ordering, which is realistic given java-tron's transaction ordering is not otherwise constrained for this pair of actuators.

### Recommendation
Add an `expected`/`min_received` field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`), and in `ExchangeWithdrawActuator.doValidate()`/`execute()` reject the transaction when the computed `anotherTokenQuant` is below the caller-supplied minimum, exactly as already done for `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange creator `A` broadcasts `ExchangeWithdrawContract` for `exchangeId=X`, `tokenId=firstTokenID`, `quant=Q`.
2. Attacker `B` observes the pending tx and broadcasts `ExchangeTransactionContract` against `exchangeId=X` selling a large amount of `secondTokenID` for `firstTokenID`, shifting `firstTokenBalance`/`secondTokenBalance` so that the ratio used in `ExchangeWithdrawActuator.execute()` (lines 77-89) yields a much smaller `anotherTokenQuant` for `A`.
3. `B`'s trade transaction is ordered before `A`'s withdraw (transaction ordering is not restricted for these actuators).
4. `A`'s withdraw executes at the manipulated ratio (`ExchangeWithdrawActuator.execute()` lines 91-104), crediting far less `anotherTokenID` than expected, with no validate-time check to prevent it (`doValidate()` lines 205-227 has no minimum-output check).
5. `B` reverses the trade with a second `ExchangeTransactionContract`, restoring the pool ratio and net-capturing the value forfeited by `A`, confirmed by comparing `ret.getExchangeWithdrawAnotherAmount()` before/after the sandwich as exercised in `ExchangeWithdrawActuatorTest` (e.g. `SameTokenNameCloseSuccessExchangeWithdraw`).
