### Title
Relayer fee is paid out before the wallet-contract action promise is confirmed constructible, letting a relayer collect the fee without executing the user's transaction - (File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs)

### Summary
The nearcore analog of the Crate.sol "decrement debt before the fallible operation, no rollback on catch" bug is in the eth-implicit **Wallet Contract**'s `inner_rlp_execute` (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:330-472`). For emulated `EOABaseTokenTransfer`/`ERC20Transfer` Ethereum transactions carrying a relayer `fee`, the contract unconditionally schedules a `Transfer` promise paying the fee to the predecessor (the relayer) **before** it has confirmed that the user's actual intended action can even be turned into a promise via `action_to_promise(target, action)?` [1](#0-0) . If that later fallible step returns `Err`, `inner_rlp_execute` propagates the error and `rlp_execute` converts it into a normal (non-panicking) `ExecuteResponse` value rather than aborting execution [2](#0-1) . Because the function does not panic, all promises/receipts already scheduled via host calls (including the fee transfer) are still emitted, exactly mirroring the Solidity bug where `liquidityPool.debt` was decremented before the fallible `swapVirtualToAsset` call and never rolled back when the try/catch caught a failure.

### Finding Description
In `inner_rlp_execute`:
1. The eth tx is parsed and `nonce` is incremented immediately for most cases [3](#0-2) .
2. For `EOABaseTokenTransfer`/`ERC20Transfer` transaction kinds with a non-zero `fee`, a `Transfer` promise crediting the predecessor (relayer) with the fee is created and scheduled right away via `env::promise_batch_create` + `env::promise_batch_action_transfer`, unconditionally on whether the actual user action ever gets executed [4](#0-3) .
3. Only afterward does the code attempt to build the promise for the user's real action:
```
_ => {
    let ext = WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
    action_to_promise(target, action)?.then(ext.rlp_execute_callback(caller_deposit))
}
``` [5](#0-4) 
If `action_to_promise` returns `Err`, the `?` operator makes `inner_rlp_execute` return `Err` too, and the public entry point simply converts that into a graceful `ExecuteResponse` error value:
```
Err(e) => PromiseOrValue::Value(e.into()),
``` [6](#0-5) 
Since the contract call completes without panicking, the already-issued fee `Transfer` receipt (step 2) is still emitted and executed - the relayer is paid even though the user's underlying action never ran. This is functionally identical to the reported Solidity pattern: an accounting-affecting operation (debt decrement / here, a value transfer) is committed before the fallible step it logically depends on, and the "catch" path (graceful `Err`→response conversion) does not undo it.

This is distinct from the intended, unconditional "relayer compensation" design noted in the code comments, which is meant to apply when the relayer honestly submits a transaction that *fails only at the intended-action execution stage* (handled later, safely, inside `rlp_execute_callback`'s `PromiseResult::Failed` branch, which itself refunds only the *caller's deposit*, not the fee). The bug is specifically that the fee-payment promise is issued **before** `action_to_promise` is even attempted, so a promise-construction failure (a purely local, pre-flight error, not a cross-shard execution failure) still results in fee payment.

### Impact Explanation
A relayer can craft or select a call where `target`/`action` causes `action_to_promise` to fail deterministically (e.g., an action-conversion error unrelated to the eth signature/fee validity) while `fee` is non-zero, collecting the user-authorized relayer fee in $NEAR from the wallet's balance without ever attempting the user's intended transfer/contract call. This is a fund-theft vector: value leaves the user's eth-implicit account to the relayer with no corresponding service rendered, and the loss is not refunded by any subsequent step (the only refund path in `rlp_execute_callback` covers the caller's attached deposit for cross-shard promise failures, not this pre-flight fee).

### Likelihood Explanation
Reachable by any unprivileged relayer submitting an `rlp_execute` call, which is the standard/only way to interact with eth-implicit accounts through the Wallet Contract. Exploitation requires knowing or engineering an `action`/`target` combination that fails specifically at the `action_to_promise` construction step (not at cross-shard execution), which is plausible for malformed but nonce-valid, fee-bearing Ethereum-emulated transactions; the exact conditions under which `action_to_promise` errors could not be fully enumerated within available context (the definition of `action_to_promise` and the full `Error` enum from `error.rs` were not retrievable in this session), so likelihood should be validated by inspecting `action_to_promise`'s error conditions and the `Error`/`RelayerError`/`UserError` variants directly in the repository.

### Recommendation
Move the relayer fee-payment promise creation so it is only scheduled after `action_to_promise(target, action)` (or the equivalent promise-construction step for each `TransactionKind` branch) has succeeded, mirroring the ASTRO-13 remediation of moving the debt decrement inside the `try` block. Concretely, compute/validate the action promise first, and only then create and chain the fee-transfer promise (or attach it to the same promise batch conditioned on success), so a pre-flight construction failure cannot trigger fee payment.

### Proof of Concept
Conceptual (cannot be fully executed without the `action_to_promise`/`Error` definitions, which were not retrievable in this session):
1. Relayer submits `rlp_execute(target, tx_bytes_b64)` with a validly-signed Ethereum tx recognized as `TransactionKind::EthEmulation(EthEmulationKind::ERC20Transfer { fee, .. })` where `fee > 0` and `predecessor_account_id != current_account_id`.
2. Craft `target`/`action` (e.g., referencing an action variant/parameters that `action_to_promise` rejects, such as an unsupported or malformed `near_action::Action`) so that `action_to_promise(target, action)` returns `Err` after the fee-refund promise has already been scheduled at [7](#0-6) .
3. `inner_rlp_execute` returns `Err(e)`; `rlp_execute` converts this to `PromiseOrValue::Value(e.into())` without panicking [6](#0-5) .
4. The already-created `Transfer` promise to the relayer for `fee` is still executed as a receipt, paying the relayer, while the user's intended action never runs and no refund of the fee occurs.
