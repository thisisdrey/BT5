## Analog Analysis: CVE-2017-6319 → java-tron

CVE-2017-6319 is an unchecked, attacker-controlled length field being used to index/copy from a buffer in radare2's DEX debug-info parser, causing an out-of-bounds crash. The closest reachable analog in java-tron is the ABI-array extraction helper used by the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts, which parse attacker-supplied calldata into a `DataWord[]` and then index into it using length/offset fields taken directly from that same calldata, with no bound check against the actual array size.

### Title
Unbounded, attacker-controlled array index in TVM precompile ABI decoding causes uncaught out-of-bounds exception - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `extractBytesArray` / `extractBytes32Array` helpers used by the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts read a length value directly from caller-controlled calldata and then loop over `words[offset + i + 1]` without verifying that this index stays within the bounds of the `words` array that was actually parsed from the input data.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` parse the raw calldata into a `DataWord[]` via `DataWord.parseArray(data)` and then compute an array offset from an attacker-supplied word: [1](#0-0) 

`extractBytesArray` only guards the initial `offset`, not the subsequent index used inside its loop: [2](#0-1) 

`len` (the number of items to iterate) is read from `words[offset]` and fully attacker-controlled; nothing forces `offset + i + 1 < words.length`, so a crafted calldata layout where `len` is larger than what the parsed `words` array actually contains causes `words[offset + i + 1]` to throw `ArrayIndexOutOfBoundsException`. A negative or overflowed `len` also reaches `new byte[len][]`, which throws `NegativeArraySizeException`. This is the same bug class as the CVE: a length value taken from untrusted structured input is used to drive array/pointer arithmetic without validating it against the real buffer size, resulting in an out-of-bounds access/crash instead of a controlled error path. `extractBytes32Array` has the identical unguarded pattern: [3](#0-2) 

Both precompiles are reached by calling their fixed contract addresses from any deployed smart contract via a normal `CALL`/`STATICCALL` opcode, i.e. from an unprivileged contract deployer or caller — no special privilege is required.

### Impact Explanation
`ValidateMultiSign.execute` does not wrap the `extractBytesArray`/`extractSigArray` call in a try/catch: [4](#0-3) 

An uncaught `RuntimeException` thrown here propagates out of the precompiled-contract dispatch path invoked during transaction execution inside the TVM. Depending on how far up the exception is caught (I was not able to fully trace the exception-handling boundary in `Program`/`ProgramInvoke` within the remaining investigation budget), the practical impact ranges from a single transaction/contract call failing unexpectedly (denial of service for that call, not itself catastrophic) up to a broader failure if this exception occurs during block application and is not caught by the transaction-execution wrapper, which would affect node availability. I could not conclusively confirm which of these outcomes occurs without further tracing of the calling context, so I flag this as the main uncertainty in this finding.

### Likelihood Explanation
High: the trigger only requires crafting calldata to a known, fixed precompiled-contract address with an out-of-range offset/length word — no special account, permission, or state precondition is needed, and it can be done via a single transaction/contract call from any account.

### Recommendation
Add explicit bounds checks in `extractBytesArray` and `extractBytes32Array` so that `offset + i + 1` (and the nested `bytesOffset` index) are validated against `words.length` before use, and reject (rather than propagate an unchecked exception for) negative or oversized `len` values, mirroring the defensive checks already present in `RLP.verifyLength` and `ContractEventParser.subBytes` elsewhere in the codebase (e.g. [5](#0-4) ). Ensure `ValidateMultiSign.execute` treats any parsing failure as `Pair.of(true, DATA_FALSE)` rather than letting an unchecked exception escape.

### Proof of Concept
Deploy a contract that performs a `STATICCALL`/`CALL` to the `ValidateMultiSign` precompiled-contract address with calldata where:
- word[3] (the offset-selector word) points to a position such that `words[offset]` (the declared array length) is set to a value like `1000`, while the actual calldata only contains a `words` array of, e.g., 10 elements.

This causes `extractBytesArray`'s loop to read `words[offset + i + 1]` past the bounds of the array parsed by `DataWord.parseArray(data)`, throwing `ArrayIndexOutOfBoundsException` uncaught by `ValidateMultiSign.execute`, confirmed by inspecting the unguarded loop at [2](#0-1)  and the missing surrounding try/catch at [4](#0-3) .

  protected static byte[] subBytes(byte[] src, int start, int length) {
    if (ArrayUtils.isEmpty(src)) {
      throw new OutputLengthException("source data is empty");
    }
    if (start < 0 || start >= src.length || length < 0 || length > src.length - start) {
      throw new OutputLengthException(
          "data start:" + start + ", length:" + length + ", src.length:" + src.length);
    }
    byte[] dst = new byte[length];
    System.arraycopy(src, start, dst, 0, length);
    return dst;
