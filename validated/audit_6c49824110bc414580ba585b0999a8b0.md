### Title
Exchange (bancor TRC10 pair) permanently freezes the remaining token balance once either side reaches zero, with no recovery function - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeCapsule` maintains a purely virtual accounting pool of `firstTokenBalance`/`secondTokenBalance` for a TRX↔TRC10 or TRC10↔TRC10 trading pair created by `ExchangeCreateActuator`, funded by `ExchangeInjectActuator`, traded against by `ExchangeTransactionActuator`, and only withdrawable via `ExchangeWithdrawActuator`. Just like wstETH tracks "shares" that only change through `wrap()`/`unwrap()`, the Exchange pool tracks these two virtual balances that can only change through the four dedicated actuators. Both `ExchangeTransactionActuator.doValidate()` (via `AbstractExchangeActuator`) and `ExchangeWithdrawActuator.doValidate()` unconditionally reject any operation once **either** side of the pool balance is `0`: [1](#0-0) 

There is no owner/creator function, no emergency-withdraw, and no sweep path once this state is reached: `ExchangeWithdrawActuator` is the only way to recover funds, and it self-locks. This is structurally analogous to the reported wstETH bug: an internal “shares/virtual balance” ledger that becomes permanently unreachable because the only withdrawal path is a specific function gated on invariants that can be driven to a stuck state, and no recovery function exists.

### Finding Description
`ExchangeTransactionActuator` allows any account to repeatedly trade against a pool using the bancor-relay formula implemented in `ExchangeProcessor`/`SafeExchangeProcessor`: [2](#0-1) 

The formula's floating-point/BigDecimal `pow()` computations round the returned `buyTokenQuant` **down**, but nothing bounds `buyTokenQuant` strictly below `buyTokenBalance`; repeated small trades that each round in the taker's favor (or a sequence of large `ExchangeInjectActuator`/`ExchangeTransactionActuator` calls that skew the ratio to extreme values) can drive one side of `exchangeCapsule`'s balance down to exactly `0` (or the taker can simply keep buying until the pool balance for one token empties out, since `exchange()` never explicitly forbids draining a side to zero — it is only checked as a **precondition**, `firstTokenBalance == 0 || secondTokenBalance == 0`, not as a **postcondition** guard preventing the trade that produces it): [3](#0-2) 

Once either `firstTokenBalance` or `secondTokenBalance` becomes `0`, **all** subsequent `ExchangeTransactionContract` and `ExchangeWithdrawContract` calls on that exchange fail validation with "the exchange has been closed": [1](#0-0) [4](#0-3) 

At that point the remaining non-zero side's balance — which represents real TRX/TRC10 that account holders subtracted from their own balances via `reduceAssetAmountV2`/`setBalance` in `ExchangeCreateActuator`/`ExchangeInjectActuator` — is permanently trapped inside the `ExchangeCapsule` record in `ExchangeStore`/`ExchangeV2Store`. There is no actuator, precompile, or governance path that lets the creator sweep the frozen remainder; `ExchangeWithdrawActuator` is the sole recovery mechanism and it is blocked by the same zero-balance guard that caused the freeze.

### Impact Explanation
This causes a permanent, unrecoverable freezing of real economic value (TRX and/or TRC10 assets) that were legitimately deposited into the exchange pool by the creator/injector, exactly the "permanent freezing of funds" impact category. Any unprivileged account can trigger the freeze by simply issuing `ExchangeTransactionContract` transactions against a pool until one side reaches zero (this requires no special privilege — any signed transaction sender who can afford the trade amounts can do it, including trading against their own created exchange, or an attacker deliberately draining a victim's pool to grief them).

### Likelihood Explanation
Draining one side of a bancor-style constant-product-like relay pool to exactly zero via repeated/rounded trades is a well-known DeFi failure mode, and here it is not defended against — the check exists only as a validation gate for *future* operations, not as an invariant enforced *during* the trade that could reach zero. Any TRC10 exchange with a small enough remaining balance (which can be engineered by successive trades reducing the balance toward the rounding floor, or simply achieved on any exchange with low liquidity) is at risk.

### Recommendation
Add an actuator/path that allows the exchange creator to withdraw/close the pool without the `firstTokenBalance == 0 || secondTokenBalance == 0` guard blocking recovery of the non-zero remainder (e.g., a dedicated "close exchange" operation that returns whatever balances remain regardless of whether one side already hit zero), and/or explicitly prevent trades that would drive either side to `0` in `ExchangeCapsule.transaction()`/`ExchangeProcessor.exchange()` before rather than only validating the precondition in `ExchangeWithdrawActuator.doValidate()`.

### Proof of Concept
1. Account A calls `ExchangeCreateContract` to create a TRX/TRC10 “abc” pool with `firstTokenBalance=X` TRX, `secondTokenBalance=Y` "abc" — `ExchangeCreateActuator.execute()` deducts X TRX and Y "abc" from A's account into `ExchangeCapsule`.
2. Account B repeatedly calls `ExchangeTransactionContract` selling TRX for "abc" (or vice versa), each time driven by `ExchangeCapsule.transaction()` → `ExchangeProcessor.exchange()`, until the returned `secondTokenBalance` (or `firstTokenBalance`) reaches `0` — no code path rejects the trade that produces this exact-zero outcome.
3. Account A now attempts `ExchangeWithdrawContract` to recover the remaining non-zero side's balance; `ExchangeWithdrawActuator.doValidate()` throws `ContractValidateException("Token balance in exchange is equal with 0, the exchange has been closed")` at line 209-212, permanently blocking recovery of the remaining funds since no other actuator exists to withdraw from this `ExchangeCapsule`.
