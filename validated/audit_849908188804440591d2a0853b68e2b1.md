### Title
Stale `TrieKey::PostponedReceipt`/`PendingDataCount` survive `DeleteAccount`, letting a postponed self-authorized receipt execute privileged actions against an unrelated recreated account - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` only clears `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData`; it never removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` rows keyed by the deleted account's name. `action_delete_account` performs no check for outstanding postponed receipts before calling `remove_account`. If the deleted account's name is later reused by `CreateAccount`, the stale postponed receipt (created by the original owner as a self-call, `predecessor_id == receiver_id == account_name`) will still fire once its final input data arrives, and `check_actor_permissions` only compares `actor_id == account_id` by name — with no notion of "account generation" — so its stored actions (e.g. `AddKey(FullAccess)`, `DeployContract`, `Transfer`) execute with self-actor privilege against the new, unrelated account.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only `Account`, `ContractCode`, access/gas keys, and `ContractData`: [1](#0-0) 
It leaves `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` rows for the account untouched.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) checks storage-usage size cap, gas-key balance, and zero locked stake, but has no check for pending/postponed receipts targeting the account before calling `remove_account`: [2](#0-1) 

When the account created a promise with two `input_data_ids`, one of which resolves before the account self-deletes, the pending state (`PendingDataCount`, `PostponedReceiptId`, `PostponedReceipt`) is written by `process_action_receipt`/`process_receipt` keyed purely by `receiver_id` (the account name), independent of account existence: [3](#0-2) [4](#0-3) 

Once the last input data arrives, the runtime blindly fetches and executes the postponed receipt via `apply_action_receipt`, which re-reads the account fresh by name (`get_account(state_update, account_id)`) and sets `actor_id = receipt.predecessor_id().clone()`: [5](#0-4) 

`check_actor_permissions` for privileged actions (`DeployContract`, `AddKey`, `DeleteKey`, `WithdrawFromGasKey`, etc.) only requires `actor_id == account_id` (string/name equality), with no check that the account is the "same" logical account that authorized the receipt originally: [6](#0-5) 

Because the postponed receipt's `predecessor_id` equals `receiver_id` (a self-call, which only the account's own contract logic can produce), `actor_id == account_id` trivially holds regardless of whether `account_id` now refers to a brand-new account created by an unrelated party. The stale receipt's actions therefore run with full self-authorization against the new account.

Note this is distinct from the existing same-chunk delete/recreate fix covered by `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` (`runtime/runtime/src/tests/apply.rs:4877`), which only ensures a `FunctionCall` resolves against fresh code/account state — it does not address privileged actions carried in a *postponed* receipt surviving deletion+recreation via the uncleaned `PostponedReceipt`/`PendingDataCount` trie rows.

### Impact Explanation
This is an authorization-escalation bug: actions such as `AddKey(FullAccess)`, `DeployContract`, or `Transfer` stored in a stale postponed receipt execute against a newly created, unrelated account without any signature or consent from that new account's actual owner. An attacker who controls the original `victim.near` account can pre-plant a self-callback (e.g., "add my key as FullAccess") in a promise with an outstanding input data dependency, delete the account, and then — once the name is re-registered by any third party (or even the same attacker acting as a name squatter) — deliver the final data receipt at will (since the attacker's own contracts control the promise chain) to trigger privileged execution against the new owner's account. This maps to theft of funds / authorization escalation across accounts.

### Likelihood Explanation
The attacker fully controls the timing of the exploit because both legs of the promise chain (the initiating call and the final data-producing callback) are typically the attacker's own contracts, so they can choose exactly when the second input data item is delivered — including after the account name has been recreated. The main externally-dependent precondition is that the vacated account name gets reused (e.g., via a public account-name registrar/linkdrop or the attacker itself re-registering it under a different flow to bait a victim into taking over the "clean-looking" account). Preconditions (zero locked stake, storage usage ≤ `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, gas-key balance ≤ 1 NEAR) are all attacker-controllable at account setup. No validator or node privilege is required, only ordinary contract deployment and transaction submission — repeatable per victim account name.

### Recommendation
`remove_account` should also purge all `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` (and ideally `PromiseYieldReceipt`/`PromiseYieldTimeout`/`PromiseYieldStatus`/`YieldIdToDataId`/`DataIdToYieldId`) entries keyed by the account being deleted, mirroring the iteration-and-remove pattern already used for access keys and contract data. Alternatively/additionally, `action_delete_account` should reject deletion (or force resolution/failure of pending receipts) while any `PendingDataCount`/`PostponedReceipt` exists for the account, ensuring an account cannot vanish while it still has an outstanding promise obligation that would later execute self-authorized actions against a differently-owned account of the same name.

### Proof of Concept
Runtime/test-loop integration test plan:
1. Create `victim.near` and have its contract issue an `ActionReceipt` to itself (`predecessor_id == receiver_id == "victim.near"`) with `input_data_ids = [d1, d2]` and `actions = [AddKey(attacker_pubkey, FullAccess)]`.
2. Deliver a `DataReceipt` for `d1` only (leaving `PendingDataCount == 1`); assert `TrieKey::PostponedReceipt{receiver_id: "victim.near", receipt_id}` exists in state.
3. Submit `DeleteAccount` from `victim.near` (zero locked stake) and commit; assert `TrieKey::Account{"victim.near"}` is gone but `TrieKey::PostponedReceipt`/`PendingDataCount` for it still exist in the trie.
4. Submit `CreateAccount` for `"victim.near"` by an unrelated account (simulating re-registration), fund it, commit.
5. Deliver the final `DataReceipt` for `d2`; let the runtime resolve and execute the postponed receipt.
6. Assert the new `"victim.near"` account now has `attacker_pubkey` as a `FullAccess` key — i.e., `get_access_key` returns `FullAccess` for a key the new account's owner never authorized — demonstrating authorization escalation across account identities without the new owner's signature.
