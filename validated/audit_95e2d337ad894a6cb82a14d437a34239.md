### Title
Unstaked RTT-based BDP stream-window scaling lets an attacker inflate concurrent QUIC stream capacity beyond fair share - (File: streamer/src/nonblocking/swqos.rs)

### Finding Description
`compute_max_allowed_uni_streams_with_rtt` first selects a base stream count per `ConnectionPeerType` and then, regardless of peer type (staked or unstaked), scales that base value linearly by the measured `rtt_millis` clamped to `[REFERENCE_RTT_MS, MAX_RTT_MS]` (`50`–`350`ms): [1](#0-0) 

For `ConnectionPeerType::Unstaked`, the base is the fixed constant `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128`, chosen empirically to bound TPS impact from unstaked clients: [2](#0-1) 

But the final RTT-scaling line applies universally to `streams` (both staked and unstaked branches), so an unstaked peer's granted `max_uni_streams` is not RTT-invariant: it scales up to `128 * (350/50) = 896` for an RTT at or above `MAX_RTT_MS`. This is confirmed by the existing unit test itself, which explicitly asserts unstaked streams scale with RTT: [3](#0-2) 

The RTT value used is `connection.rtt()` from `quinn`, read once at connection-accept time in `cache_new_connection` before `set_max_concurrent_uni_streams` is applied: [4](#0-3) 

`quinn`'s RTT estimate is derived from real observed ACK round-trip timing on the wire. A client fully controls when/how it acknowledges server-sent packets (e.g., during the QUIC handshake and subsequent 1-RTT exchanges), so it can genuinely inflate the server-observed RTT for its own connection (e.g., by delaying ACKs, routing through a high-latency relay, or throttling its own send/receive pacing) without needing any protocol violation or spoofing. Because this RTT sample directly and unconditionally multiplies the unstaked `max_uni_streams` cap, an unstaked attacker can obtain up to ~7x the concurrent-uni-stream allowance of an honest, low-latency unstaked peer, while the per-IP/per-peer connection limits (`max_connections_per_unstaked_peer`) and the separate rate-based `throttle_stream`/`StakedStreamLoadEMA` mechanism do not compensate for this — they gate stream *rate*, not the concurrently-open-stream *window*, so a larger window still lets one peer hold open disproportionately more simultaneous streams (and associated per-stream QUIC/receive-buffer resources) than peers with honest RTT.

### Impact Explanation
This is a QoS-evasion / unfair-capacity-capture issue matching the described bounty scope ("connection, stream, or per-IP QoS limits" bypass). An unstaked attacker who inflates its own measured RTT captures a disproportionately large window of concurrently open unidirectional streams relative to other unstaked peers sharing the same `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` fairness envelope, allowing it to occupy more per-connection stream/resource slots on the leader's TPU and starve honest low-RTT unstaked senders of stream capacity.

### Likelihood Explanation
Preconditions are trivial for an unprivileged, unstaked remote client: it only needs to connect to the TPU QUIC port and induce a higher round-trip time as perceived by the server, which requires no more than normal client-side network behavior (e.g., relaying through a distant proxy or deliberately delaying its own ACKs), well within `[REFERENCE_RTT_MS, MAX_RTT_MS]`. This is fully repeatable per-connection since `compute_max_allowed_uni_streams_with_rtt` is invoked and applied deterministically for every new connection at accept time.

### Recommendation
Remove RTT-based scaling for `ConnectionPeerType::Unstaked` (keep it fixed at `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`, matching the intent stated in the comment on the constant), applying BDP scaling only to the staked branch where the peer's identity/stake is already authenticated and cannot be freely multiplied across many unstaked identities/IPs.

### Proof of Concept
Extend the existing test module in `streamer/src/nonblocking/swqos.rs` with a differential assertion:
```rust
#[test]
fn test_unstaked_streams_are_rtt_invariant() {
    let low_rtt = compute_max_allowed_uni_streams_with_rtt(
        REFERENCE_RTT_MS, ConnectionPeerType::Unstaked, 10000);
    let high_rtt = compute_max_allowed_uni_streams_with_rtt(
        MAX_RTT_MS, ConnectionPeerType::Unstaked, 10000);
    // Expected (desired) invariant: unstaked stream cap must not scale with RTT.
    assert_eq!(low_rtt, high_rtt, "unstaked max_uni_streams must be RTT-invariant");
}
```
Running this against current code fails because `low_rtt == 128` while `high_rtt == 896`, demonstrating the attacker-controllable capacity capture; the existing `test_max_allowed_uni_streams_with_rtt` test already documents this scaling behavior for the unstaked class.

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
