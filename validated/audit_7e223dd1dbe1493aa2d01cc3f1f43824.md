### Title
StackerDB chunk signatures are not bound to the target contract/message-lane, enabling cross-lane chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` computes the signed digest solely from `slot_id`, `slot_version`, and `data_hash`. It never includes the StackerDB's `smart_contract_id` (i.e., which `.signers-{set}-{message_id}` contract or `.miners` contract the chunk belongs to). Because each reward cycle's `.signers` boot contract assigns the *same* signer address to the *same* `slot_id` across every `signers-{set}-{message_id}` "lane" contract (per `signers.clar`'s single `stackerdb-get-signer-slots-page` source of truth and `stackslib/src/chainstate/stacks/boot/signers_tests.rs:277-343`), a chunk that is validly signed by a signer for one message lane is *also* a validly-signed chunk for the same slot in every other message lane of that signer set. This is directly analogous to the reported TPM issue: authentication data (the signature) is bound to the signer's identity but not to the full context ("PCR state" ≈ which contract/lane the chunk is destined for), letting an attacker splice authenticated data from one context into another.

### Finding Description
- `SlotMetadata::auth_digest()` (`libstackerdb/src/libstackerdb.rs:160-166`) hashes only `slot_id`, `slot_version`, and `data_hash`.
- `SlotMetadata::verify()` / `StackerDBChunkData::verify()` (`libstackerdb/src/libstackerdb.rs:181-193`, `233-244`) only check that the recovered public key hash matches the expected slot owner for *that* contract — they never check which contract the signature was originally produced for.
- Chunk validation on receipt, `StackerDBs::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs:649-717`), looks up the slot owner via `get_slot_signer(smart_contract_id, slot_id)` and then calls `slot_metadata.verify(&addr)`. Since the digest doesn't encode `smart_contract_id`, this check succeeds for *any* contract in which `addr` happens to own that `slot_id` — including a different message-lane contract than the one the chunk was originally produced/broadcast for.
- The per-lane signer-slot assignment comes from a single shared source, `stackerdb-get-signer-slots-page` in `stackslib/src/chainstate/stacks/boot/signers.clar:40-43`, which is reused verbatim by every `signers-{set}-{message_id}` contract for a given signer set. This is confirmed by `signers_db_get_slots` in `stackslib/src/chainstate/stacks/boot/signers_tests.rs:277-343`, which shows the identical stackerdb-slots list applies across all `SIGNER_SLOTS_PER_USER` message-id lanes.
- The payload-type filtering that would normally reject a message replayed into the wrong lane (`signer_message_payload_matches_lane` in `libsigner/src/events.rs:568-596`) is enforced only in the downstream `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` conversion inside the signer's event-processing client — it is *not* enforced by the network/storage layer (`validate_received_chunk`, `try_replace_chunk`, or the HTTP `POST /v2/stackerdb/.../chunks` handler in `stackslib/src/net/api/poststackerdbchunk.rs`). Consequently, the chunk is accepted and *stored* into the wrong lane's StackerDB replica, and will be gossiped/broadcast further (`handle_unsolicited_StackerDBPushChunk`, `stackslib/src/net/stackerdb/mod.rs:767-861`) to other nodes, propagating the misplaced data network-wide, even though libsigner's own downstream interpretation might later discard mismatched payload types.

### Impact Explanation
An unprivileged remote attacker who can observe a legitimately signed StackerDB chunk (chunks are public — retrievable over HTTP or via p2p gossip) can resubmit the exact same signed bytes to a *different* message-lane contract for the same reward cycle where the signer occupies the same `slot_id`. Because the signature only commits to `(slot_id, slot_version, data_hash)`, it verifies successfully against the wrong contract's slot owner, letting the attacker cause the node to store and further propagate signer-authored data under the wrong lane/contract without ever possessing any signer's private key. This is an unauthenticated write of otherwise-valid signed data into the wrong StackerDB state and network-wide propagation of that misplaced data — matching the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact bar.

### Likelihood Explanation
High likelihood of reachability: StackerDB chunks are inherently public (readable via HTTP GET and gossiped over p2p), the lane-sharing of slot assignment is a designed, permanent property of the `.signers` boot contract (not a transient bug), and no private key or special privilege is required — only observation of one publicly broadcast chunk and a single POST/gossip to a different contract endpoint. The wrong-lane check exists only in the signer's higher-level event dispatch code, not the underlying network/storage layer that stores and re-propagates chunks.

### Recommendation
Bind the signed digest to the full authentication context, not just the slot. Include the `smart_contract_id` (and ideally an epoch/reward-cycle-scoping value) in `SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs`, and correspondingly update all signing/verification call sites (`StackerDBChunkData::sign`/`verify`, `recover_pk`) and the on-wire message schema so that a signature produced for one contract instance cannot be replayed as valid for another. Since this changes the wire format, plan for a versioned protocol upgrade.

### Proof of Concept
1. Attacker observes (via `GET /v2/stackerdb/{contract1}/chunks/{slot}/{version}` or via p2p gossip) a validly-signed `StackerDBChunkData` for `signers-0-1` slot 3, signed by signer address `A` (owner of slot 3 in every `signers-0-*` lane per `signers.clar`).
2. Attacker submits the identical `slot_id=3, slot_version, sig, data` via `POST /v2/stackerdb/signers-0-2/chunks` (a different message lane, same signer set).
3. The node's `validate_received_chunk`/`try_replace_chunk` path looks up `A` as the owner of slot 3 in `signers-0-2` and calls `slot_metadata.verify(&A)`, which succeeds because the digest never referenced the contract id — the chunk is accepted and stored under `signers-0-2`, then broadcast to peers.     /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
