Audit Report

## Title
ERC20Transactor XCM asset transactor trusts requested amount instead of actual ERC20 balance delta, breaking reserve backing for fee‑on‑transfer / non‑standard ERC20 tokens - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` construct/redeem the `Erc20Credit(amount)` XCM holding-register imbalance using the caller-supplied `amount` rather than the real balance delta observed on the ERC20 contract, trusting only the boolean return value of `IERC20::transfer`/`transferFrom`. This is wired into AssetHub Westend's `AssetTransactors` via `assets_common::ERC20Matcher`, which accepts any local `AccountKey20` location (i.e., any pallet-revive-deployed contract address) with no allow-list, so an unprivileged attacker can deploy a fee-on-transfer contract and use it through this transactor.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall` from the user to `checking_address` and, if the decoded boolean return is `true`, unconditionally credits `Erc20Credit(amount)` into the XCM holding register without checking `TransfersCheckingAccount`'s real balance delta: [1](#0-0) . `deposit_asset_with_surplus` mirrors this by transferring the ledgered `amount` from `TransfersCheckingAccount` to the beneficiary, again trusting only the boolean return: [2](#0-1) . The `Erc20Credit` type is explicitly documented as not runtime-enforced, deferring real balance enforcement to "the ERC20 smart contract itself": [3](#0-2) .

Crucially, the `Matcher` wired into AssetHub Westend's `ERC20Transactor` is `assets_common::ERC20Matcher`, defined as `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>` [4](#0-3) , and `IsLocalAccountKey20` matches *any* location of the shape `(0, [AccountKey20 { .. }])` with no allow-list or registration check [5](#0-4) . This matcher is used directly in `AssetTransactors` alongside the other transactors on AssetHub Westend: [6](#0-5) . Because contract deployment via `pallet-revive` is unprivileged, any attacker can deploy a fee-on-transfer/deflationary ERC20 contract at an `AccountKey20` address and immediately have it accepted by this transactor for XCM `WithdrawAsset`/`DepositAsset` operations — no governance curation or registration gate exists in this path.

## Impact Explanation
Since `TransfersCheckingAccount` is a single shared escrow account for all users of a given ERC20 asset routed through this transactor, a fee-on-transfer or otherwise non-standard contract that returns `true` while moving less than `amount` causes the ledgered `Erc20Credit` amount in the XCM holding register to exceed the real balance held by `TransfersCheckingAccount`. This breaks the custody/settlement invariant that the checking account's real balance must equal outstanding credits, and can cause a subsequent legitimate depositor's `deposit_asset_with_surplus` to fail/trap funds, or allow accounting to diverge such that value is not conserved across all holders of the asset.

## Likelihood Explanation
Likelihood is significant given the unrestricted `ERC20Matcher`: any unprivileged user can deploy a trivial fee-on-transfer Solidity contract via `pallet-revive` and route it through XCM `WithdrawAsset`/`DepositAsset` on AssetHub Westend without any governance approval, since the matcher accepts every local `AccountKey20` address. The transactor performs no pre/post balance introspection at either leg, only decoding the boolean return of `transfer`.

## Recommendation
After each `IERC20::transferCall` in `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read the actual pre/post ERC20 balance of `TransfersCheckingAccount` (or the relevant party) via `IERC20::balanceOfCall` and construct/redeem `Erc20Credit` from the observed delta rather than the caller-supplied `amount`. Alternatively, restrict `ERC20Matcher`/the `Matcher` type parameter to a governance-curated allow-list of vetted, non-fee-on-transfer, non-rebasing ERC20 contracts, and add an invariant check (e.g., `defensive_assert!`) ensuring `TransfersCheckingAccount`'s balance tracks the sum of outstanding `Erc20Credit`.

## Proof of Concept
1. Deploy an unprivileged ERC20 contract via `pallet-revive` whose `transfer`/`transferFrom` burns 5% of `value` before crediting the recipient while still returning `true`.
2. Since `ERC20Matcher`/`IsLocalAccountKey20` matches any local `AccountKey20` address with no allow-list [7](#0-6) , this contract is immediately usable as a reserve asset via AssetHub Westend's `ERC20Transactor`.
3. User A executes an XCM `WithdrawAsset` for `amount = 1000`; `withdraw_asset_with_surplus` calls `transfer(checking, 1000)`, the contract returns `true` but only credits `checking` with 950, while the holding register records `Erc20Credit(1000)` [8](#0-7) .
4. Repeat across multiple users into the same shared `TransfersCheckingAccount`, accumulating a shortfall between real balance and ledgered credits.
5. A later legitimate `deposit_asset_with_surplus` for outstanding `Erc20Credit(N)` attempts `transfer(beneficiary, N)` from `TransfersCheckingAccount`, which now holds less than `N`, causing that transfer to revert/trap funds for that user [9](#0-8) .

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
