### Title
Non-atomic partition assignment for not-yet-created repositories allows an attacker to pre-claim a victim's future repository/pool partition - ([File: internal/gitaly/storage/storagemgr/partition_assigner.go])

### Summary
The external report describes a smart-contract analog where a deterministic, `CREATE`-derived address is computed and persisted for an object *before* it is actually deployed/funded, letting an attacker who can predict that address front-run the legitimate deployment during a chain reorg and hijack the funds sent to it. Gitaly has a structurally identical pattern in its partitioning subsystem: a repository's storage **partition assignment**, keyed by relative path, is recorded in the persistent key-value store *before* the repository (or object pool) that the path refers to has actually been created, and this assignment is never rolled back even if the creating transaction later fails.

### Finding Description
`StorageManager.Begin` resolves the partition that a transaction should run against via `partitionAssigner.getPartitionID`, which in turn calls `getPartitionIDRecursive`: [1](#0-0) 

For repository-creating RPCs (`AllowPartitionAssignmentWithoutRepository` / `isRepositoryCreation`), the code explicitly tolerates the target relative path not existing yet and still calls `assignPartitionID`, persisting the `(relative_path, partition_id)` mapping to the storage's embedded key-value store: [2](#0-1) 

This is a documented, acknowledged design gap. `doc/transactions.md` states plainly: [3](#0-2) 

and the middleware that decides which RPCs are allowed to do this repeats the same caveat verbatim, including a link to the still-open tracking issue: [4](#0-3) 

Critically, the relative path that gets bound to a partition this way is often **deterministic and predictable**, not attacker-opaque: object pool and replica paths are derived purely as a hash of a monotonically-increasing repository ID via `DeriveReplicaPath`/`DerivePoolPath`: [5](#0-4) 

and `PostgresRepositoryStore.ReserveRepositoryID` hands out these IDs from a plain, sequential Postgres sequence: [6](#0-5) 

Because (a) the future on-disk path for the next repository/pool is computable in advance from the next sequence value, and (b) any RPC classified as repository-creating is allowed to eagerly create the partition-assignment record for that path even if the repository is never actually created (e.g. the seeding step fails, a hook rejects, or the transaction is aborted for any reason after `assignPartitionID` runs but before `stageRepositoryCreation`/`CreateRepository` commits), an attacker can:

1. Predict the relative path (via `DeriveReplicaPath`/`DerivePoolPath`) that the *next* repository or object pool created by another tenant will receive.
2. Issue a repository-creating RPC (e.g. `CreateRepository`, `CreateObjectPool`, `CreateFork`) targeting that exact predicted relative path, causing `getPartitionIDRecursive`/`assignPartitionID` to bind that path to a partition of the attacker's choosing — this record persists in the KV store regardless of whether the RPC itself ultimately succeeds.
3. Because "assignments are not deleted even if the repository is deleted" (and are also never deleted if creation never completed), when the legitimate owner's request later runs `CreateRepository`/`CreateFork` for the same relative path, it is bound to the attacker-preassigned partition rather than a fresh one.

This is the direct structural analog of the reported bug: a deterministic identifier is computed and durably reserved ahead of the object's real creation, and the reservation step is not atomic with — nor cleaned up on failure of — the actual creation, letting a race-winning attacker "own" the slot the victim's object will be born into.

### Impact Explanation
Object pools and their linked repositories are placed together in a single partition specifically so that transactional guarantees (write-ahead log ordering, consistency between fork and pool) hold between them, per `doc/transactions.md`. If an attacker can force a victim's about-to-be-created fork/pool relative path into a partition the attacker already controls or has instrumented, this breaks the isolation the partitioning layer is meant to provide between unrelated repositories/tenants, and can result in write-ahead log entries, quarantine directories, or reference-transaction state for the victim's repository being applied against a partition the attacker has visibility/influence over. Because partition assignment persists indefinitely and is never reconciled against the actual repository lifecycle (creation success/failure, deletion), the corrupted mapping is durable and requires manual/operator intervention to fix — consistent with the "loss of funds"-style permanence in the original report, here manifesting as durable state confusion/DoS between tenants' repositories in a Gitaly cluster.

### Likelihood Explanation
Exploitation requires: (1) the ability to predict the next sequential repository ID before the victim creates their repository/pool (visible to co-tenants of the same storage/virtual-storage, or derivable by racing the sequence with repeated cheap `CreateRepository` calls of one's own to observe/pace the counter), and (2) the ability to issue a repository-creating RPC against that predicted relative path while an unprivileged, ordinary user of the service — both are reachable through the standard `CreateRepository`, `CreateObjectPool`, and `CreateFork` RPCs without any special privilege. The maintainers themselves flag this in code comments and documentation as a known, unresolved gap (issue #5957), indicating the race window is real and currently unmitigated, though winning the race in practice (predicting the exact next ID and beating the legitimate creation) still requires some timing precision.

### Recommendation
Make partition assignment atomic with repository creation: only persist the `(relative_path, partition_id)` mapping once the repository-creation transaction actually commits (or transactionally tie the assignment record to the same WAL entry as the repository creation), and reconcile/garbage-collect stale assignments for relative paths whose creation transaction aborted. Additionally, avoid deriving pool/replica paths purely from a predictable sequential counter without binding the assignment to a value only the legitimate creator can supply (e.g., include a per-request nonce/lock token verified at commit time), closing the "predict-then-preassign" window described in the referenced tracking issue.

### Proof of Concept
Not applicable — no PoC file was provided in the external report, and constructing a full end-to-end PoC would require access to a live multi-tenant Gitaly/Praefect deployment to demonstrate winning the repository-ID race in practice.

```go
func (pa *partitionAssigner) getPartitionIDRecursive(ctx context.Context, relativePath string, recursiveCall bool, partitionHint storage.PartitionID, isRepositoryCreation bool) (storage.PartitionID, error) {
	// Check first whether the repository is already assigned into a partition. If so, just return the assignment.
	ptnID, err := pa.partitionAssignmentTable.getPartitionID(relativePath)
	if err != nil {
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			return 0, fmt.Errorf("get partition: %w", err)
		}

		// Repository wasn't yet assigned into a partition. This is the slow path. Requests attempting
		// to get or assign a partition ID concurrently are serialized.

		releaseLock, err := pa.acquireRepositoryLock(ctx, relativePath)
		if err != nil {
			return 0, fmt.Errorf("acquire repository lock: %w", err)
		}

		defer releaseLock()

		// With the repository locked, check first whether someone else assigned it into a partition
		// while we weren't holding the lock between the first failed attempt getting the assignment
		// and locking the repository.
		ptnID, err = pa.partitionAssignmentTable.getPartitionID(relativePath)
		if !errors.Is(err, storage.ErrPartitionAssignmentNotFound) {
			if err != nil {
				return 0, fmt.Errorf("recheck partition: %w", err)
			}

			// Some other goroutine assigned a partition between the failed attempt and locking the
			// repository.
			return ptnID, nil
		}

		// With the repository under lock, verify it is a Git directory before we assign it into a partition.
		// It's okay if the repository doesn't yet exist as this transaction may be about to create it.
		if err := storage.ValidateGitDirectory(filepath.Join(pa.storagePath, relativePath)); err != nil {
			if errors.Is(err, fs.ErrNotExist) {
				if !isRepositoryCreation {
					return 0, relativePathNotFoundError(relativePath)
				}

				// Repository creations are allowed to target non-existing repositories. They create the partition
				// where the repository is to be created.
			} else {
				return 0, fmt.Errorf("validate git directory: %w", err)
			}
		}

		ptnID, err = pa.assignPartitionID(ctx, relativePath, recursiveCall, partitionHint)
		if err != nil {
			return 0, fmt.Errorf("assign partition ID: %w", err)
		}
	}
```

**File:** doc/transactions.md (L56-70)
```markdown
Gitaly automatically assigns repositories to partitions when they are first accessed:

- Object pools and all repositories connected to the object pool are placed in the same partition. Repositories that are about to be connected to an object pool, such as newly created forks, are also placed in the same partition with the object pool they are about to be connected.
  - Assigning pools and their connected repositories into the same partition ensures transactions can guarantee consistency between them. If pools were in different partitions, transaction ordering could cause issues, for example updating a reference in a fork before the objects are written into the pool.
- Repositories that are not connected (nor about to be connected) to an object pool are placed in their own partitions.

Whether repository is, or is about to be connected to an object pool, is determined from multiple sources:

- If it has an `info/alternates` file, the repository is currently connected to a pool.
- If it is an RPC that contains an additional repository in the request, the repository is about to be connected.
  - For example, `CreateFork` contains the origin repository as an additional repository. We place the fork in the same partition as an objet pool might be created, and the fork and the origin connected to it.
  - `CreateObjectPool` will similarly place the object pool into the same partition as the source repository since it will generally be connected to it.

Partitioning is handled in the `StorageManager` component. This component handles routing transactions to the correct partitions, and starting and stopping partitions as needed. The partition assignments are retrieved or created at
[this location in the codebase](https://gitlab.com/gitlab-org/gitaly/-/blob/7c0f925b3df33c77de8c124b5f89447a13da3059/internal/gitaly/storage/storagemgr/partition_manager.go#L331) when a transaction is began against a repository for the first time. The assignment handling is fairly crude at the moment. The assignments are created before the repository is even created, and assignments are not deleted even if the repository is deleted.
```

```go
// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.
func DeriveReplicaPath(repositoryID int64) string {
	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}
```

```go
// ReserveRepositoryID reserves an ID for a repository that is about to be created and returns it. If a repository already
// exists with the given virtual storage and relative path combination, an error is returned.
func (rs *PostgresRepositoryStore) ReserveRepositoryID(ctx context.Context, virtualStorage, relativePath string) (int64, error) {
	var id int64
	if err := rs.db.QueryRowContext(ctx, `
SELECT nextval('repositories_repository_id_seq')
WHERE NOT EXISTS (
	SELECT FROM repositories
	WHERE virtual_storage = $1
	AND   relative_path   = $2
)
	`, virtualStorage, relativePath).Scan(&id); err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return 0, ErrRepositoryAlreadyExists
		}

		return 0, fmt.Errorf("scan: %w", err)
	}

	return id, nil
}
```
