### Title
Missing chain-id binding in `ValidateMultiSign`/`BatchValidateSign` TVM precompiled signature schema enables cross-chain replay of permission-approval signatures - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts recover signer addresses and check them against an account's on-chain `Permission` without ever binding the signed hash to a chain identifier. Any smart contract on the network can use these precompiles as a generic "verify this permission-holder signed this message" primitive, but the message schema itself has no chain-id/domain separator, so a signature approving an action is valid on every java-tron-based network that shares the same account address and permission configuration.

### Finding Description
`ValidateMultiSign.execute()` builds the hash to check as:
```
combine = address || permissionId || data
hash = SHA256(combine)
``` [1](#0-0) 

and then recovers each supplied signature against that hash and sums the weights of the recovered signers from the account's `Permission`: [2](#0-1) 

`BatchValidateSign.doExecute()` is even more permissive — it takes an arbitrary caller-supplied `hash` word directly (no address/permission binding at all) and simply verifies which of the given signatures recover to the given addresses: [3](#0-2) 

Neither precompile mixes in a chain identifier (or any other value unique to the deployed network) into the hash that gets signed and checked. This mirrors exactly the bug class from the report: a fixed signature schema (`Order(bidId, trader, quantity, price, ...)` in CrabNetting) that omits `chainid`, so a valid signature produced for one network can be replayed verbatim on another network where the same address/private key and account permission setup exist. In java-tron's case, both TRON mainnet and its sibling/derivative TVM networks (testnets such as Nile/Shasta, and other java-tron-based chains such as BTTC) share identical ECDSA key/address derivation, so a key holder's address and any `Permission` structure they set up (via `AccountPermissionUpdateContract`, itself with no chain binding either — see `AccountPermissionUpdateActuator.validate()` [4](#0-3) ) can trivially be replicated cross-chain.

Since `ValidateMultiSign`/`BatchValidateSign` are reachable from any TVM contract via a plain `STATICCALL`/`CALL` to precompile addresses `0x9`/`0xa` — i.e. reachable by any unprivileged account that can trigger a smart contract call — any DApp that relies on these precompiles to gate a privileged action (e.g., a multisig-style withdrawal approval, an off-chain "order" or "permit" authorized by a set of permission keys) inherits the missing chain-id binding, because the precompile itself provides no chain-specific salt for the caller to rely on being unique.

### Impact Explanation
A signature produced (intentionally or via phishing a signing request) by a permission key holder to authorize an action on one java-tron network can be replayed by an unauthorized third party against a contract using the same precompile-based verification scheme on another java-tron-based network where the victim's account/permission state has been mirrored, causing unauthorized execution of privileged multisig-gated operations (e.g., asset transfers/approvals gated by `ValidateMultiSign`). This is a concrete "unauthorized account operation" vector matching the accepted impact categories.

### Likelihood Explanation
Exploitation requires that the victim's account address exist with an equivalent `Permission` configuration on more than one java-tron-derived network (a realistic scenario given cross-deployment of the same DApp/contract code and address-reuse across TRON mainnet, testnets, and TVM sidechains such as BTTC), and that an attacker obtain a signature intended for one such network (e.g., by observing a broadcast transaction/calldata, or via a mempool/relay). Given the precompiles are public, permissionless entry points with no chain binding whatsoever, likelihood is moderate wherever DApps reuse the same signing flow across environments.

### Recommendation
Include a chain identifier (and ideally the precompile/verifying-contract address) in the hash constructed by `ValidateMultiSign` and require callers of `BatchValidateSign` to include chain id in the hash they pass in, e.g.:
```
combine = chainId || address || permissionId || data
```
Document that `BatchValidateSign`'s caller-supplied hash must itself be chain-bound, and update TVM documentation/guidance to mandate chain-id inclusion for any signature scheme built on top of these precompiles.

### Proof of Concept
1. Deploy the same DApp contract (using `ValidateMultiSign` at precompile address `0x...a` to gate a withdrawal) on TRON mainnet and on a java-tron-based testnet/sidechain.
2. Configure identical account address `A` with an `Active` `Permission` (threshold/keys) on both networks (trivial since address derivation from the private key is chain-independent, and `AccountPermissionUpdateContract` has no chain binding — see `AccountPermissionUpdateActuator.validate()`).
3. Key holder signs `hash = SHA256(A || permissionId || data)` to authorize a withdrawal on network 1.
4. Attacker captures this signature (e.g., from the broadcast transaction calldata) and submits it unchanged as the multisig proof to the equivalent DApp contract on network 2, where `ValidateMultiSign` recomputes the identical `hash` and recovers the identical signer — the check passes and the unauthorized withdrawal executes on network 2.
