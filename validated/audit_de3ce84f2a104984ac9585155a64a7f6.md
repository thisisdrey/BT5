Audit Report

## Title
Relayer reward and order settlement ignore the `DeliveryReceipt.success` field, allowing rewards to be paid for failed message dispatch - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`process_delivery_receipt` pays the pending relayer fee and removes the `PendingOrder` based solely on a valid, verified event log matching the message's nonce, without ever inspecting whether the decoded `receipt.success` field is `true` or `false`. This allows a relayer to collect the full reward for a message whose dispatch on Ethereum actually failed/reverted.

## Finding Description
The `DeliveryReceipt` struct decoded from the Ethereum Gateway's `InboundMessageDispatched` log carries an explicit `success: bool` field, correctly populated from the on-chain event during `TryFrom<&Log>` decoding. `process_delivery_receipt` verifies only the gateway address (`T::GatewayAddress::get() == receipt.gateway`) and looks up the `PendingOrder` by `receipt.nonce`; it then unconditionally calls `T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee)` whenever `order.fee > 0`, and removes the order — the `success` field is never read or branched on. The pallet's own documentation frames the receipt as confirming the message "has been verified and executed" prior to paying the reward, showing the intended gate is dispatch success, not nonce presence alone. The existing check (`T::Verifier::verify`, invoked upstream in `submit_delivery_receipt`) only attests to authenticity of the log, not to the dispatch outcome encoded within it, so a fully authentic receipt reporting `success: false` passes every current guard.

## Impact Explanation
Any relayer eligible for the reward (default is the submitting relayer when `reward_address == [0u8; 32]`) can be paid the full `order.fee` for a message that failed to execute on Ethereum, because the sole determinant of payout is nonce lookup, not outcome. This violates the bridge-reward invariant that payout must settle exactly once to the rightful beneficiary and amount only after execution actually succeeds. It is an unbacked/incorrect payout for work not actually completed, and the `PendingOrder` is irrevocably removed, precluding any further reconciliation of the failed dispatch.

## Likelihood Explanation
No privileged actor or compromised relayer is required — an ordinary, honest relayer who submits a proof for a legitimately failed (reverted) dispatch on the Ethereum side (which can occur for many benign reasons, e.g. a reverted command) will trigger this path during normal operation. `T::Verifier::verify` only validates log authenticity, not the `success` outcome, so this is trivially and repeatably reachable via the public `submit_delivery_receipt` extrinsic.

## Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only invoke `T::RewardPayment::register_reward` when `receipt.success == true`. When `receipt.success == false`, still resolve/remove the order (or otherwise handle per intended incident-response design) but withhold the fee, ensuring reward issuance is tied to actual dispatch success rather than mere presence of a verified log.

## Proof of Concept
1. A message is enqueued via `do_process_message`, creating a `PendingOrder { nonce, fee: F, .. }` in storage.
2. On Ethereum, the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` because the dispatched command reverted.
3. A relayer calls `submit_delivery_receipt` with a valid proof of this event log. `T::Verifier::verify` succeeds (log is authentic), and `DeliveryReceipt::try_from` correctly decodes `success: false`.
4. `process_delivery_receipt` executes: `order.fee > 0` is true, so `T::RewardPayment::register_reward` pays the relayer despite `success == false`, and `PendingOrders::remove(nonce)` clears the order — no code path distinguishes this from a successful delivery.
