### Title
Attacker can permanently fill a victim's token slots via dust deposits/transfers, blocking them from opening new positions - ([File: contracts/Pool.sol](https://github.com/Loderfordw/metronome-synth-public--019/blob/main/contracts/Pool.sol))

### Summary
`Pool` tracks every `DepositToken`/`DebtToken` an account holds in `depositTokensOfAccount` / `debtTokensOfAccount` (`MappedEnumerableSet`) and reverts with `UserReachedMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER = 30` (`Pool.sol:79`, `Pool.sol:143-148`). An unprivileged attacker can add entries to a victim's set without consent — via `DepositToken.deposit(amount_, onBehalfOf_ = victim)` with dust amounts, or by `transfer`ing dust msdTOKEN to the victim — causing every subsequent `deposit`, `mint`/`issue`, `seize`, or `transfer` that would register a *new* token for the victim to revert.

### Finding Description
- `deposit()` mints msdTOKEN to `onBehalfOf_`, and minting/transferring registers the token in the recipient's per-account set via `pool.addToDepositTokensOfAccount`, which enforces `onlyIfAdditionWillNotReachMaxTokens` and reverts when the count is `>= 30` (`DepositToken.sol:234`, `Pool.sol:143-148`).
- Nothing prevents a third party from crediting an arbitrary account with a dust balance of a deposit token: `deposit(amount_, onBehalfOf_)` has no `onBehalfOf_ == msg.sender` check, and ERC20 `transfer`/`seize` push the recipient into the set (`DepositToken.sol:348-354`, `DepositToken.sol:343-345`).
- The attacker therefore iterates over the pool's registered `depositTokens` (a pool with ≥30 deposit/debt tokens, or a mix) and performs 30 dust deposits (e.g., `deposit(1 wei, victim)` after approving the underlying) or sends 30 dust transfers, filling the victim's set to the cap.
- After that, any victim action requiring a *new* set entry reverts: depositing into a collateral type they don't already hold, issuing a new synthetic debt (`DebtToken.issue` registers debt tokens into `debtTokensOfAccount` under the same cap), receiving seized collateral in liquidation as a liquidator, or receiving a deposit token they don't already hold.
- The analogous DoS-to-liveness mapping of CVE-2023-21976 (high-privileged MySQL DOS) translates here to an unprivileged attacker degrading a specific victim's available protocol operations.
- Mitigating factors: the victim can self-unblock by withdrawing or transferring away one of the dust balances (removing the entry when the balance hits 0 via `removeFromDepositTokensOfAccount`), so the freeze is temporary and costs the victim gas to remediate; existing funds remain withdrawable. The attack costs the attacker gas and negligibly-priced collateral dust per slot.

### Impact Explanation
Targeted temporary denial of service: the victim cannot open positions in new collateral types, cannot mint new synthetic assets, and cannot be a liquidator receiving a new collateral type, until they spend gas to clear dust entries. On an L1 with high gas costs, remediation may be non-trivial; if the attacker repeatedly refills slots (griefing), they can keep the victim blocked as long as they are willing to spend gas, potentially blocking timely deposits needed to restore health — in extreme cases contributing to liquidation losses.

### Likelihood Explanation
Requires a pool exposing ~30 deposit/debt tokens (deployed Metronome pools support many Vesper collateral types) and an attacker willing to fund 30 dust deposits/transfers. No privileged role, oracle manipulation, or timing advantage is needed; the attack is fully reproducible through public entry points. Impact is bounded (per-victim, reversible), consistent with medium/low severity.

### Recommendation
- Skip adding entries for zero-valued or below-dust-threshold balances, or require `onBehalfOf_ == _msgSender()` / whitelisted gateways in `deposit` and add a minimum deposit amount.
- Track positions by positive meaningful balances only, or switch to a per-token deposit accounting that does not need a bounded enumerable set.
- Provide a `rescue`/self-remove path so a user can forcibly remove tokens from their set regardless of balance.

### Proof of Concept
```solidity
// Hardhat/Foundry fork PoC (sketch)
// Preconditions: pool has >= 30 registered deposit tokens (or mix of deposit+debt tokens).
for (uint i; i < 30; ++i) {
    IDepositToken dt = pool.depositTokensAt(i);
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 1);
    underlying.approve(address(dt), 1);
    dt.deposit(1, victim); // adds dt to victim's depositTokensOfAccount
}
vm.expectRevert(UserReachedMaxTokens.selector);
newDepositToken.deposit(1 ether, victim); // blocked
vm.expectRevert(UserReachedMaxTokens.selector);
debtToken.issue(1e18, victim);            // new debt token also blocked
// victim still holds dust in 30 tokens; must transfer/withdraw each to clear slots
```
