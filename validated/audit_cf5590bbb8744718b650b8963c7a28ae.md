Based on the investigation, the strongest reachable analog in marginfi-v2 to the ClaggSyncAdapter "migration can't be reverted / no empty option" bug class is the `transfer_to_new_account` / `transfer_to_new_account_pda` flow, which permanently migrates a user's marginfi account without on-chain validation of the destination authority.

### Title
Unprivileged account migration accepts an unchecked `new_authority`, permanently bricking the account and its liquidity - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let any account authority migrate their `MarginfiAccount` (and all its balances) to a freshly initialized account under a caller-supplied `new_authority`. The `new_authority` field is explicitly documented as "completely unchecked" [1](#0-0) , and no on-chain check rejects `Pubkey::default()` or any other value the caller cannot ever sign for. Once migration executes, the old account is irreversibly disabled and its balances zeroed, and re-migration is permanently blocked.

### Finding Description
`finalize_migrated_old_account` sets `migrated_to`, wipes `lending_account` to `LendingAccount::zeroed()`, and permanently sets `ACCOUNT_DISABLED` on the old account: [2](#0-1) . `transfer_to_new_account` then initializes the new account under `ctx.accounts.new_authority.key()` with no validation of that key: [3](#0-2) . The account struct marks `new_authority` as an `UncheckedAccount` with an explicit "WARN" comment that it is unchecked: [4](#0-3) . The same unchecked pattern exists in `transfer_to_new_account_pda`, which additionally derives the new account as a PDA seeded on `new_authority`: [5](#0-4) [6](#0-5) .

Crucially, migration is a one-way door: `AccountAlreadyMigrated` blocks any further calls once `migrated_to != Pubkey::default()` [7](#0-6) . There is no complementary "undo"/"re-migrate" instruction analogous to the missing "disable staking" path in ClaggSyncAdapter — once the migration target is wrong, it can never be corrected.

Notably, marginfi's own off-chain tooling (`p0-cli`) recognizes this exact hazard and defends against it client-side: `marginfi_account_transfer` explicitly bails if `new_authority == Pubkey::default()` [8](#0-7) . This confirms the zero-address case is a known-dangerous input, yet the on-chain program itself performs no equivalent check, so any other caller (a different front-end, a malicious dApp, a scripting/integration bug, or a user manually constructing the transaction) can submit this unsafe value directly to the program.

### Impact Explanation
If `new_authority` is set to `Pubkey::default()` (or any other pubkey the user does not control/cannot sign for), the entire process is irreversible:
- The old account's balances are already zeroed and its `ACCOUNT_DISABLED` flag set, so it can no longer be used [9](#0-8) .
- The new account is initialized with `authority = Pubkey::default()`, a key with no known private key, meaning nobody can ever sign for it to withdraw the migrated liquidity.
- Because `migrated_to`/`migrated_from` are permanently fixed once set, there is no possible remediation instruction to retry or redirect the migration.

This results in a permanent lock/freeze of the user's entire lending/borrowing position, matching the accepted impact category (permanent lock/freeze of user funds), directly analogous to the ClaggSyncAdapter case where a migration path lacking a "disable"/fallback option permanently locked liquidity.

### Likelihood Explanation
The instruction is fully permissionless from the perspective of the account authority — no admin approval is required to trigger migration [10](#0-9) . The unchecked nature of `new_authority` combined with p0-cli's separate client-side guard demonstrates the marginfi team is aware this value is unsafe if left unchecked, but this protection is bypassable by any caller not going through that specific CLI path (e.g., a compromised/buggy front-end integration, a third-party wallet building the instruction directly, or a malicious dApp exploiting `transfer_to_new_account_pda`'s optional `third_party_id`). This is a realistic, unprivileged-user-triggerable condition, not merely theoretical.

### Recommendation
Add on-chain validation in both `transfer_to_new_account` and `transfer_to_new_account_pda` to reject `new_authority == Pubkey::default()` (and any other unsignable/degenerate values, if any exist), mirroring the guard already present in `p0-cli`. Consider also requiring the new account to be verified as controllable, e.g., by having the transaction be co-signed or by exposing an explicit rollback/re-migration path if the destination is later proven unusable, so a single bad input cannot permanently strand user liquidity.

### Proof of Concept
1. User (or a front-end acting on their behalf) calls `transfer_to_new_account` with a legitimate `old_marginfi_account` they control, but sets `new_authority = Pubkey::default()`.
2. The instruction succeeds: `finalize_migrated_old_account` disables the old account and zeroes its lending_account [2](#0-1) ; `initialize_migrated_account` creates the new account with `authority = Pubkey::default()`.
3. Because `Pubkey::default()` has no corresponding private key, no transaction can ever be signed as that authority, so the migrated balances in the new account can never be withdrawn.
4. Any subsequent attempt to migrate the old account again fails with `AccountAlreadyMigrated` [7](#0-6) , confirming there is no recovery path — the funds are permanently locked.

```rust
fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,

    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
```

```rust
pub fn transfer_to_new_account_pda(
    ctx: Context<TransferToNewAccountPda>,
    account_index: u16,
    third_party_id: Option<u16>,
) -> MarginfiResult {
    // Validate the global fee wallet and claim a nominal fee
    let group = ctx.accounts.group.load()?;
    check_eq!(
        ctx.accounts.global_fee_wallet.key(),
        group.fee_state_cache.global_fee_wallet,
        MarginfiError::InvalidFeeAta
    );
    anchor_lang::system_program::transfer(ctx.accounts.transfer_fee(), ACCOUNT_TRANSFER_FEE)?;

    let mut old_account = ctx.accounts.old_marginfi_account.load_mut()?;

    check!(
        !old_account.get_flag(ACCOUNT_IN_FLASHLOAN),
        MarginfiError::AccountInFlashloan
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_RECEIVERSHIP),
        MarginfiError::ForbiddenIx
    );

    check!(
        !old_account.get_flag(ACCOUNT_IN_ORDER_EXECUTION),
        MarginfiError::ForbiddenIx
    );

    check!(
        old_account.active_orders == 0,
        MarginfiError::IllegalAction,
        "Close all active orders before transfer"
    );

    // Prevent multiple migrations from the same account
    check_eq!(
        old_account.migrated_to,
        Pubkey::default(),
        MarginfiError::AccountAlreadyMigrated
    );

    // Validate third-party id restriction if provided
    if let Some(id) = third_party_id {
        if !is_allowed_cpi_for_third_party_id(&ctx.accounts.instructions_sysvar, id)? {
            return err!(MarginfiError::Unauthorized);
        }
    }

    let mut new_account = ctx.accounts.new_marginfi_account.load_init()?;
    let current_timestamp = Clock::get()?.unix_timestamp as u64;
    initialize_migrated_account(
        &mut new_account,
        &old_account,
        ctx.accounts.new_authority.key(),
        current_timestamp,
        ctx.accounts.old_marginfi_account.key(),
    );
    new_account.account_index = account_index;
    new_account.third_party_index = third_party_id.unwrap_or(0);
    new_account.bump = ctx.bumps.new_marginfi_account;
```
