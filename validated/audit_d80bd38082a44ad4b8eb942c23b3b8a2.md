Audit Report

## Title
Reward-per-token accrual in `pallet-asset-rewards` can permanently round to zero, freezing staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`reward_per_token` computes the pool's global reward accumulator increment as `reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, where `PRECISION_SCALING_FACTOR` is a fixed `u16` constant of `4096` [1](#0-0) . When `total_tokens_staked` is large relative to `reward_rate_per_block * rewardable_blocks_elapsed * 4096`, integer division floors this increment to zero, and because `update_pool_rewards` unconditionally advances `last_update_block` to the current block on every call regardless of whether the computed increment was nonzero, the elapsed-block window resets each time the pool is touched, allowing the increment to be repeatedly re-floored to zero.

## Finding Description
`reward_per_token` performs the division shown at [2](#0-1) , and its result is passed straight into `update_pool_rewards`, which sets `new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number()` unconditionally, with no check on whether `reward_per_token` actually advanced [3](#0-2) . This is invoked by `update_pool_and_staker_rewards`, which every public pool-touching extrinsic calls first: `stake` [4](#0-3) , `unstake` [5](#0-4) , and `harvest_rewards` [6](#0-5) . None of these extrinsics contain any minimum-elapsed-blocks guard, cooldown, or dust-accumulation mechanism — I confirmed this by reading their full bodies, and there is no additional check beyond origin/amount validation before `update_pool_and_staker_rewards` is called. Consequently, any account can call `harvest_rewards` (self-targeted, no minimum amount required) or `stake`/`unstake` with a trivial amount every block, each time resetting `last_update_block` to the current block, so `rewardable_blocks_elapsed` stays small (as low as 1) and the division in `reward_per_token` floors to zero indefinitely for realistic asset-decimal/rate combinations (e.g., an 18-decimal staked asset with large total supply and a 6-decimal reward asset with a modest per-block rate).

## Impact Explanation
This causes `reward_per_token_stored` to remain stuck, so every staker's accrued rewards computed via `derive_rewards` [7](#0-6)  never increase, even though the pool's configured `reward_rate_per_block` implies rewards should be accruing and the pool account may be funded with reward tokens via `deposit_reward_tokens`. This matches the "permanent user-fund lock" impact category — reward-asset funds intended for distribution to stakers remain stuck/undistributed in the pool account indefinitely.

## Likelihood Explanation
No privileged origin, governance action, or off-chain component is required. Any unprivileged, unsigned-fee-paying account can trigger the stall via ordinary, publicly callable extrinsics (`harvest_rewards` targeting themselves, or `stake`/`unstake` with a minimal amount) on any pool where `total_tokens_staked` (in the staked asset's raw units) is large relative to `reward_rate_per_block * PRECISION_SCALING_FACTOR` — a plausible and easily reachable configuration given `PRECISION_SCALING_FACTOR` is fixed at only `4096`. The griefing is cheap, repeatable every block, and requires no cooperation from the pool admin.

## Recommendation
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to a much wider fixed-point scale, using a type wide enough to avoid overflow in the multiplication) so realistic reward-rate/stake-size ratios do not floor to zero.
- Avoid unconditionally resetting `last_update_block` when the computed reward increment is zero; instead retain the unadvanced block number (or track/accumulate remainder) so elapsed-block windows can grow until the division yields a nonzero increment.
- Add regression tests exercising high-decimal staked assets against low-rate/low-decimal reward assets combined with repeated same/adjacent-block touches to ensure the accumulator still advances over a bounded number of blocks.

## Proof of Concept
1. Create a pool via `create_pool` with an 18-decimal staked asset with `total_tokens_staked` ≈ `10^24`, and a 6-decimal reward asset with `reward_rate_per_block = 10^6` (1 token/block).
2. Per the arithmetic in `reward_per_token` [8](#0-7) : `10^6 * 1 * 4096 / 10^24 = 0`, flooring to zero.
3. Any account repeatedly calls `harvest_rewards` (or `stake`/`unstake` with a trivial amount) once per block; each call runs `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`, which advances `last_update_block` to the current block regardless of the zero increment [9](#0-8) .
4. `reward_per_token_stored` never increases across any number of blocks, and all stakers' derived rewards remain zero indefinitely despite the pool being funded and configured with a nonzero reward rate.

		pub fn update_pool_and_staker_rewards(
			pool_info: &PoolInfoFor<T>,
			staker_info: &PoolStakerInfo<T::Balance>,
		) -> Result<(PoolInfoFor<T>, PoolStakerInfo<T::Balance>), DispatchError> {
			let reward_per_token = Self::reward_per_token(&pool_info)?;
			let pool_info = Self::update_pool_rewards(pool_info, reward_per_token)?;

			let mut new_staker_info = staker_info.clone();
			new_staker_info.rewards = Self::derive_rewards(&staker_info, &reward_per_token)?;
			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}

		/// Computes update pool reward state.
		///
		/// Should be called every time the pool is adjusted, and a staker is not involved.
		///
		/// Returns the updated pool and staker info.
		///
		/// NOTE: this function has no side-effects. Side-effects such as storage modifications are
		/// the responsibility of the caller.
		pub fn update_pool_rewards(
			pool_info: &PoolInfoFor<T>,
			reward_per_token: T::Balance,
		) -> Result<PoolInfoFor<T>, DispatchError> {
			let mut new_pool_info = pool_info.clone();
			new_pool_info.last_update_block = T::BlockNumberProvider::current_block_number();
			new_pool_info.reward_per_token_stored = reward_per_token;

			Ok(new_pool_info)
		}
