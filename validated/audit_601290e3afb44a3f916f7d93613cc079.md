### Title
Chunk signatures omit the StackerDB contract identifier, allowing cross-contract replay of validly-signed chunks - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the digest that `StackerDBChunkData::sign`/`verify`/`recover_pk` operate over — commits only to `slot_id`, `slot_version`, and `data_hash`. It never commits to the target smart-contract (`QualifiedContractIdentifier`) that the chunk is destined for. All downstream verification (`StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, `PeerNetwork::validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`, and the HTTP `poststackerdbchunk` handler) look up the expected signer *per contract* via `get_slot_validation`/`get_slot_signer`, but the signature they check carries no binding to that contract. This mirrors the reported Oracle bug pattern exactly: a value/identifier (`endRoundId` ↔ here, the "target contract/lane") that should scope an authenticated action is not included in what's actually authenticated, so an action authenticated in one context can be replayed as valid in a different context.

### Finding Description
`auth_digest()`: [1](#0-0) 

is used by both `sign()` and `verify()`: [2](#0-1) 

Note the digest never includes `smart_contract` / `contract_id`. The actual authorization check that gates a write, `try_replace_chunk`, resolves "who is allowed to write this slot" *per contract* and then calls `slot_desc.verify(&slot_validation.signer)`: [3](#0-2) 

Because the signed digest is contract-agnostic, if the *same address* is registered as the writer of `slot_id` N in two different StackerDB replicas (which is the normal, by-design situation for the Nakamoto signer StackerDB contracts — multiple `signers-<signer_set>-<message_id>` boot contracts share the same underlying signer-set ordering for a given reward cycle, see `get_signers_db_signer_set_message_id` and the shared `stackerdb-get-signer-slots` list built once per reward cycle in `update_signers`): [4](#0-3) 

then a chunk that this address legitimately signs and stores for contract A also verifies successfully against contract B's stored `slot_validation.signer` for the same `slot_id`, provided `slot_version`/`data_hash` line up for B's replica state. The same missing binding applies to the p2p-side gate `PeerNetwork::validate_received_chunk`, which checks the recovered signer address per `smart_contract_id` but again only over the contract-agnostic digest: [5](#0-4) 

and the unauthenticated write surfaces — both the HTTP `POST /v2/stackerdb/.../chunks` handler (`RPCPostStackerDBChunkRequestHandler::try_handle_request`, which calls `try_replace_chunk` directly): [6](#0-5) 

and the p2p `StackerDBPushChunk` unsolicited-message handler, which after `validate_received_chunk` succeeds forwards the chunk to be stored and re-broadcast to the network: [7](#0-6) [8](#0-7) 

— will happily accept and then **rebroadcast network-wide** a chunk that was cryptographically authenticated for a different contract/lane than the one it is being stored into. The equality that should hold — "a signature is only valid for the specific (contract, slot_id, slot_version, data) tuple it was created for" — is broken: it is actually valid for "(any contract where this address owns this slot_id, slot_version, data)".

Any application-layer segregation (e.g. `signer_message_payload_matches_lane` in `libsigner/src/events.rs`, which filters by payload-type prefix) happens only when a specific consumer (`SignerEvent::try_from`) later interprets the chunk; it is not enforced at the point where the chunk is authenticated and durably stored/propagated by the StackerDB/network layer.

### Impact Explanation
This is a High-severity finding under the given impact categories: it is "network-wide propagation of forged data" — data authenticated for one StackerDB replica context is stored and rebroadcast as authentic for a different replica/lane, without the replica layer ever verifying that the signature was meant for it. A signer (an unprivileged-relative-to-admin, ordinary network role that legitimately holds only its own key) can move an old or out-of-context, but validly-signed, message from one lane's StackerDB into another lane's StackerDB slot it also happens to own, corrupting that lane's chunk contents and forcing the P2P layer to propagate it to all replicating peers as legitimate data for that lane. Downstream consumers that don't independently re-derive/re-check the intended contract context (only checking payload-type compatibility, not contract origin) can be made to process data that was never actually signed for that context.

### Likelihood Explanation
Exploitability requires only that the attacker be a registered signer/writer for a slot in at least one contract, and that the same address occupy the identical `slot_id` in another StackerDB contract — which is the normal condition for the multiple `signers-<set>-<message_id>` boot-contract lanes sharing one reward-cycle's signer ordering. No admin role, no other party's key, and no complex race window is needed — it can be exploited at will via either the public HTTP `poststackerdbchunk` endpoint or an unsolicited p2p `StackerDBPushChunk` message.

### Recommendation
Bind the `auth_digest()` to the full write context, not just `(slot_id, slot_version, data_hash)`. Include the `QualifiedContractIdentifier` (and ideally the `rc_consensus_hash`/reward-cycle epoch) inside the signed digest in `SlotMetadata::auth_digest()`, and update both `sign()`/`verify()` call sites (`libstackerdb/src/libstackerdb.rs`) and all verification paths (`try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, `validate_received_chunk` in `stackslib/src/net/stackerdb/mod.rs`) to pass in and check the contract identifier as part of the authenticated payload, so a signature produced for one StackerDB contract cannot verify against another.

### Proof of Concept
1. Node maintains two StackerDB replicas, `signers-0-1` and `signers-0-2`, for the same reward cycle; both were configured with the same `stackerdb-get-signer-slots` ordering, so address `S` owns `slot_id = 3` in both.
2. `S` builds `chunk = StackerDBChunkData::new(3, 5, payload_A)` and signs it with its private key: `chunk.sign(priv_S)`. This is submitted (e.g., via `RPCPostStackerDBChunkRequestHandler`) and accepted into `signers-0-1` because `slot_desc.verify(&slot_validation.signer)` succeeds against `signers-0-1`'s recorded signer for slot 3 (`stackslib/src/net/stackerdb/db.rs:418`).
3. The identical `chunk` bytes (same `slot_id`, `slot_version`, `sig`, `data`) are POSTed instead against `signers-0-2`'s contract endpoint (or pushed via `StackerDBPushChunk` naming `signers-0-2` as `contract_id`). Because `auth_digest()` never references the contract, `slot_desc.verify(&slot_validation.signer)` for `signers-0-2` also succeeds (same address owns slot 3 there, and `data_hash`/`slot_id`/`slot_version` match), so `try_replace_chunk` stores it and `Relayer::process_stacker_db_chunks`/`process_uploaded_stackerdb_chunks` rebroadcasts a `StackerDBPushChunk` for `signers-0-2` network-wide, even though `payload_A` was authenticated only for `signers-0-1`.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
