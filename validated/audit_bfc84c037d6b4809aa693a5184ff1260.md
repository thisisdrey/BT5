Confirmed: `RPCPostStackerDBChunkRequestHandler::try_handle_request` accepts any `contract_identifier` from the URL path and any `StackerDBChunkData` from the POST body, and simply calls `tx.try_replace_chunk(&contract_identifier, ...)` with no binding between the submitted signature and the target contract other than the per-contract slot-owner lookup.### Title
Cross-contract StackerDB chunk signature replay due to missing contract-binding in the signed digest - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` (the data actually signed/verified for every StackerDB chunk write) commits only to `(slot_id, slot_version, data_hash)`. It never includes the target StackerDB's `QualifiedContractIdentifier` (or any other domain separator such as network/chain id). Because a single signer's key/address commonly owns the same `slot_id` across multiple different StackerDB contracts (e.g. the `.signers-{0|1}-{message_id}` boot contracts for `message_id in 0..SIGNER_SLOTS_PER_USER`, and the same parity contract is reused across every other reward cycle since the contract name is only `reward_cycle % 2`), a validly-signed chunk observed for one contract/slot can be replayed into a different contract/slot owned by the same signer.

### Finding Description
`SlotMetadata::auth_digest()` computes: [1](#0-0) 
This hash is what gets signed in `sign()` and what is checked in `verify()`: [2](#0-1) 

The verification path used by both direct HTTP writes and StackerDB gossip, `validate_received_chunk`, looks up the *expected signer address for that specific contract* and then calls `slot_metadata.verify(&addr)`: [3](#0-2) 

Crucially, the signature itself never encodes *which* contract it was made for — only the address lookup is contract-scoped, while the digest that is actually authenticated (`slot_id`, `slot_version`, `data_hash`) is contract-agnostic. If the same signer address is a registered slot owner in two different StackerDB contracts (which happens by design in this codebase — every `.signers-{parity}-{message_id}` contract for `message_id` in `0..SIGNER_SLOTS_PER_USER` uses the identical signer set/slot assignment for a given parity, and the parity contract is reused every other reward cycle via `make_signers_db_name`): [4](#0-3) 

then a chunk `(slot_id, slot_version, sig, data)` that was legitimately signed and stored for contract A can be POSTed verbatim to contract B's endpoint. The HTTP handler takes the `contract_identifier` from the URL and the raw chunk from the body with no cross-check to the chunk's origin contract, and writes it directly via `try_replace_chunk`: [5](#0-4) 

As long as the target contract's expected `slot_version` and `data_hash` conditions are satisfiable (attacker fully controls which historical/observed chunk to replay and to which contract), the write is accepted as if freshly authorized for that contract, and the node will even re-broadcast it as a `StackerDBPushChunk` to the rest of the network: [6](#0-5) 

The same missing binding applies on the p2p gossip path, `handle_unsolicited_StackerDBPushChunk`, which relies on the identical `validate_received_chunk`/`SlotMetadata::verify` machinery.

### Impact Explanation
This breaks the intended equality "signed-for-contract-A == authenticated-for-contract-B" — the signature does not bind to the StackerDB replica it was intended for. A remote, unauthenticated third party (anyone who observed a legitimately-signed chunk on one `.signers-*` contract) can inject that same signer's chunk data into a *different* `.signers-{parity}-{message_id}` lane (or a future reward cycle reusing the same parity contract name) that they were never given, causing an unauthorized/forged write into that StackerDB replica and propagation of that forged-for-this-context data to the rest of the network via the automatic relay in `try_handle_request`. This matches the in-scope Critical class "unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data."

Downstream application-level checks (e.g. `signer_message_payload_matches_lane` in `libsigner/src/events.rs`, or block-specific hashes embedded inside `SignerMessage` payloads) provide partial mitigation for the miner/signer message-consumption logic, but the StackerDB storage layer itself has no such protection — the chunk is accepted and stored/relayed as valid for the target contract regardless of which contract it was actually authorized for.

### Likelihood Explanation
The attack requires no privileged access: any peer that can observe StackerDB chunk gossip or make an authenticated-looking POST to the `/v2/stackerdb/:principal/:contract/chunks` RPC endpoint can attempt the replay. It does require satisfying the target contract's freshness gates (`slot_version` must not be stale, `data_hash` bound to the observed payload bytes), which limits it to replaying *specific already-observed* payloads rather than arbitrary forged content, but this is still a concrete cross-context replay that violates the intended per-contract signing guarantee. Likelihood is Medium-High given how routinely the same signer key/slot assignment is reused across the numerous per-message-id `.signers-*` contracts and across alternating-parity reward cycles.

### Recommendation
Include the target `QualifiedContractIdentifier` (and ideally the network/chain id) as part of `SlotMetadata::auth_digest()`, e.g.:
```rust
fn auth_digest(&self, contract_id: &QualifiedContractIdentifier) -> Sha512Trunc256Sum {
    let mut hasher = Sha512_256::new();
    hasher.update(contract_id.serialize_to_vec()); // or a versioned domain tag
    hasher.update(self.slot_id.to_be_bytes());
    hasher.update(self.slot_version.to_be_bytes());
    hasher.update(self.data_hash.0);
    Sha512Trunc256Sum::from_hasher(hasher)
}
```
and thread the contract id through `sign()`/`verify()`/`recover_pk()` call sites in `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/mod.rs`, and `stackslib/src/net/api/poststackerdbchunk.rs`, so a chunk signature can never be validated against a contract other than the one it was created for.

### Proof of Concept
1. Attacker (or a passive relay observer) monitors StackerDB gossip/RPC and captures a valid `StackerDBChunkData { slot_id: S, slot_version: V, sig, data }` legitimately written by signer `K` into contract `A = .signers-0-1`.
2. Signer `K` also owns `slot_id = S` in contract `B = .signers-0-2` (same parity, different `message_id` — a normal configuration per `make_signers_db_name`/the per-`message_id` slot layout).
3. Attacker submits `POST /v2/stackerdb/<addr>/signers-0-2/chunks` with the identical `slot_id`, `slot_version`, `sig`, and `data` captured from contract `A`.
4. `RPCPostStackerDBChunkRequestHandler::try_handle_request` calls `tx.try_replace_chunk(&contract_B_id, ...)`, which resolves `K`'s address as the slot-B owner and calls `slot_metadata.verify(&addr)`; since `auth_digest()` never included the contract id, the signature verifies successfully against contract `B`, and the (contract-A-originated) chunk is written to contract `B` and relayed network-wide as an authentic `StackerDBPushChunk` for `B`.
