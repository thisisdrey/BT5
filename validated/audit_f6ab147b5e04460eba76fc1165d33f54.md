## Finding

### Title
Uncaught `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile breaks TIP‑854 outer‑frame containment - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The kernel CVE rejects a dma-buf bind whose size/SG length is not validated to be a multiple of `PAGE_SIZE` before it is used to compute array indices, causing an out-of-bounds `tx_vec` access. The same bug class — an attacker-controlled offset that is divided by a fixed unit and used to index a fixed-size array without bounds checking — exists in java-tron's `ValidateMultiSign` precompiled contract, and unlike its sibling `BatchValidateSign`, it is not defensively wrapped, so the resulting Java `RuntimeException` is not contained to the failing call.

### Finding Description
`ValidateMultiSign.execute()` parses calldata into a `DataWord[]` and then, before any bounds validation, computes an offset from attacker-controlled word `words[3]` and indexes directly into the array: [1](#0-0) 

The only gating check, `isValidAbiEncoding`, merely verifies that the total calldata length is word-aligned and that `(length - headerWords*32)` is a positive multiple of `itemWords*32`; it never validates that the offset word `words[3]` actually points within the bounds of `words`: [2](#0-1) 

This check is also only active when `VMConfig.allowTvmOsaka()` is enabled; pre‑Osaka there is no structural check at all: [3](#0-2) 

An attacker can therefore craft calldata that passes `isValidAbiEncoding` (correct total length/word alignment) but sets `words[3]` to a large value, so `words[3].intValueSafe() / WORD_SIZE` produces an index far beyond `words.length`, throwing an uncaught `ArrayIndexOutOfBoundsException` inside `execute()`. Unlike `BatchValidateSign`, whose `execute()` wraps `doExecute()` in a `try { ... } catch (Throwable t) { return Pair.of(true, new byte[WORD_SIZE]); }` guard: [4](#0-3) 

`ValidateMultiSign.execute()` has no such outer guard — its only `try/catch` starts after the vulnerable array access, at line 1082: [5](#0-4) 

The repository even contains a regression test explicitly named for this containment property, `testTip854OuterFrameContainment`, asserting that a CALL into `ValidateMultiSign`/`BatchValidateSign` with malformed calldata must not propagate an exception to the calling frame: [6](#0-5) 

However, that test only exercises the trivial `data.length == 0` case, which is rejected early by `isValidAbiEncoding` before reaching the unguarded array index — it does not cover a well-formed-length payload with an out-of-range offset word, which is exactly the case left unguarded in `ValidateMultiSign`.

When the exception fires from a nested `CALL` (via `Program.callToPrecompiledAddress`, which invokes `contract.execute(data)` with no surrounding try/catch): [7](#0-6) 

it propagates as a `RuntimeException` out of the `CALL` opcode's execution and is caught by the per-opcode handler in `VM.play()`, which stops the whole VM and rethrows rather than just pushing `0` for the failed inner call: [8](#0-7) 

### Impact Explanation
This violates standard EVM call semantics (a failed low-level `CALL` should only zero out the caller's return value and let outer execution continue) and specifically the containment guarantee TIP-854 was meant to establish for these two precompiles. Any contract that performs a low-level `CALL` (or `staticcall`/`delegatecall`) into `ValidateMultiSign` with attacker-influenced calldata — e.g., a multisig/permission-check helper contract — can be forced to have its *entire* outer transaction abort instead of merely failing the inner call, defeating error-handling/fallback logic that depends on graceful failure. Because `VMActuator` ultimately catches the resulting `Throwable` and reverts the whole transaction, this manifests as a reliable, attacker-triggered denial of the intended call-containment behavior for any dApp relying on it, and is inconsistent with the hardening already applied to `BatchValidateSign`.

### Likelihood Explanation
The precompile is reachable by any account through ordinary smart-contract execution (any `CALL`-family opcode targeting the `ValidateMultiSign` precompile address), requiring only a single crafted transaction with a permission ID and an out-of-range signature-array offset word. No special privileges are required.

### Recommendation
Wrap `ValidateMultiSign.execute()` the same way `BatchValidateSign.execute()` is wrapped — move the body into a `doExecute()` and catch `Throwable` at the `execute()` boundary, returning a safe `Pair.of(true/false, ...)` result instead of letting exceptions escape. Additionally, validate that offset words (e.g. `words[3]`) resolve to an index within `words.length` before using them in `extractSigArray`/`extractBytesArray`, mirroring the fix pattern in the referenced kernel commit of validating derived sizes/offsets before using them for indexing.

### Proof of Concept
1. Enable `allowTvmOsaka` (or use pre-Osaka network where no `isValidAbiEncoding` guard exists at all).
2. Deploy a contract that performs `address(VALIDATE_MULTISIGN_PRECOMPILE).call(payload)`.
3. Craft `payload` as 10 words (320 bytes, satisfying `isValidAbiEncoding(rawData, 5, 5)`), where `words[3]` (the sig-array offset word) is set to a large value such as `0x00000000000000000000000000000000000000000000000000000000989680` (10,000,000), so `words[3].intValueSafe() / WORD_SIZE` (~312,500) far exceeds `words.length` (10).
4. Send a transaction invoking this contract. `ValidateMultiSign.execute()` throws `ArrayIndexOutOfBoundsException` at `words[words[3].intValueSafe() / WORD_SIZE]`, which is uncaught, propagates through `Program.callToPrecompiledAddress` and `VM.play()`'s opcode handler, and forces the entire outer transaction to fail/revert instead of the inner `CALL` merely returning failure.
