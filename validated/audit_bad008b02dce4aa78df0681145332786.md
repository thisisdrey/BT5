### Title
Credential leak via unsanitized error logs for FindRemoteRootRef (and any RPC not in the URL-sanitizer allowlist) - ([File: internal/log/url_sanitizer.go])

### Summary
`URLSanitizerHook.Fire` only redacts URL credentials for gRPC methods explicitly registered via `AddPossibleGrpcMethod`, and only `CreateRepositoryFromURL`, `FetchRemote`, and `UpdateRemoteMirror` are registered. `FindRemoteRootRef` accepts a caller-controlled `RemoteUrl` field, embeds it into the git command/config and into error messages, but is not in the allowlist, so any embedded `user:pass@host` credentials would appear in cleartext log entries.

### Finding Description
`FindRemoteRootRef` takes `request.GetRemoteUrl()` directly from the RPC request and passes it into `git remote show` via `gitcmd.ConfigPair{Key: "remote.inmemory.url", Value: remoteURL}` [1](#0-0) . If the git command fails (e.g., due to DNS/connection failure, or authentication failure against a malicious/unreachable host with `user:pass@` embedded in the URL), the underlying error — which can contain the raw URL — propagates up through `findRemoteRootRef`/`FindRemoteRootRef` and gets wrapped with `structerr.NewInternal` [2](#0-1) .

The `URLSanitizerHook.Fire` function only sanitizes log entries when `entry.Data["grpc.method"]` matches an entry in `hook.possibleGrpcMethods`, a map populated solely by `AddPossibleGrpcMethod` calls in `serve.go` [3](#0-2) . That call site only registers three methods [4](#0-3) . `FindRemoteRootRef` is absent, confirmed both by the allowlist itself and by the existing unit test case `"with gRPC method not added to the list"`, which asserts (using `UserDeleteTag` as an example) that unsanitized methods pass raw credential strings straight through to the log output unmodified [5](#0-4) .

This is a genuine gap in an opt-in allowlist design: any current or future RPC that accepts a URL (spawns git commands or logs errors containing that URL) but is not added to `possibleGrpcMethods` will leak embedded credentials into Gitaly's logs. `FindRemoteRootRef` is a concrete, currently-reachable, unprivileged (repo owner can trigger fetch/mirror-configuration RPCs) example of this gap, independent of the three RPCs the sanitizer's authors already anticipated.

### Impact Explanation
If the standard gRPC access-log / error-log path attaches the returned error (or spawned command args) with `grpc.method: "FindRemoteRootRef"` to a logrus entry, and that error message contains the raw `RemoteUrl` (as git error strings for auth/connect failures typically do, matching the exact same pattern the sanitizer targets for `FetchRemote`/`UpdateRemoteMirror`), the embedded username/password would be written to Gitaly's log files in cleartext. This matches a credential-disclosure impact class: secrets intended to remain internal (transient RPC-supplied remote credentials) become persisted in log storage, accessible to anyone with log read access — a broader exposure surface than the gRPC response alone.

### Likelihood Explanation
The attack requires only an unprivileged GitLab user capable of triggering `FindRemoteRootRef` with an attacker-chosen `RemoteUrl` (e.g., via a repository mirror/import configuration flow that ultimately invokes this RPC) and causing the underlying git command to fail (trivially done by pointing to a non-resolving or refusing host). No elevated privileges, config changes, or peer compromise are needed. The mechanism directly parallels the already-acknowledged pattern for `FetchRemote`, which was deliberately added to the allowlist for exactly this reason.

### Recommendation
Add `"FindRemoteRootRef"` (and any other RPC that accepts a raw remote URL, e.g., check for `HttpAuthorizationHeader`/`RemoteUrl` fields across the proto surface) to the `AddPossibleGrpcMethod` allowlist in `configure()`/`serve.go`. More robustly, replace the opt-in allowlist model with either (a) automatic sanitization applied to all log entries regardless of `grpc.method`, or (b) a proto-level annotation/field option marking URL-bearing fields, so newly added or renamed RPCs are sanitized by default rather than requiring manual allowlisting.

### Proof of Concept
```go
// internal/log/url_sanitizer_test.go style PoC demonstrating the gap
func TestURLSanitizer_FindRemoteRootRefNotSanitized(t *testing.T) {
    outBuf := &bytes.Buffer{}
    urlSanitizer := NewURLSanitizerHook()
    urlSanitizer.AddPossibleGrpcMethod("CreateRepositoryFromURL", "FetchRemote", "UpdateRemoteMirror")

    logger := newLogger()
    logger.Out = outBuf
    logger.Hooks.Add(urlSanitizer)

    logger.WithFields(Fields{
        "grpc.method": "FindRemoteRootRef",
        "error": fmt.Errorf("fatal: unable to access 'https://foo_the_user:hUntEr1@attacker.invalid/foo/bar/': Could not resolve host"),
    }).Error("ERROR")

    // Credential is NOT filtered because FindRemoteRootRef is absent from possibleGrpcMethods
    require.Contains(t, outBuf.String(), "foo_the_user:hUntEr1@attacker.invalid")
}
```
At the RPC level: an unprivileged user configures a repository mirror/import job (or otherwise triggers `FindRemoteRootRef`) with `RemoteUrl: "https://user:pass@nonexistent.invalid/x"`. The git subprocess fails DNS resolution, the error string containing the credentials propagates through `structerr.NewInternal` in `FindRemoteRootRef`, and — if the access-log middleware records `error` with `grpc.method=FindRemoteRootRef` — the credential is persisted in cleartext in Gitaly's stdout/log files.

func (hook *URLSanitizerHook) Fire(entry *logrus.Entry) error {
	mth, ok := entry.Data["grpc.method"]
	if !ok {
		return nil
	}

	mthStr, ok := mth.(string)
	if !ok || !hook.possibleGrpcMethods[mthStr] {
		return nil
	}

	if _, ok := entry.Data["args"]; ok {
		sanitizeSpawnLog(entry)
	} else if _, ok := entry.Data["error"]; ok {
		sanitizeErrorLog(entry)
	} else {
		entry.Message = sanitizeString(entry.Message)
	}

	return nil
}
