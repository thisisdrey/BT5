### Title
CancelAllUnfreezeV2Actuator increases TronPower / resource weight without settling vote rewards first - ([File: actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java])

### Summary
The external report's bug class is: a state-changing operation reads/mutates an account's accrual-bearing balance (frozen/vote power) without first "closing the books" (calling the settle/collect routine) on the prior accrual period, letting the accrual computation silently use stale bounds. In java-tron, TronPower/voting-power changes are supposed to be preceded by `MortgageService.withdrawReward()` (the on-chain equivalent of `collect()`) so that `DelegationStore`'s `beginCycle`/`endCycle`/`accountVote` snapshot is settled against the *old* power/votes before the power changes. `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, `VoteWitnessActuator`, and `WithdrawBalanceActuator` all call `mortgageService.withdrawReward(ownerAddress)` before mutating frozen balance or votes. `CancelAllUnfreezeV2Actuator.execute()` does not.

### Finding Description
`CancelAllUnfreezeV2Actuator.execute()` re-freezes (restores) balances from `UnfreezeV2` entries back into `FrozenV2`/`TronPower`, increasing `TotalNetWeight`/`TotalEnergyWeight`/`TotalTronPowerWeight` and the owner's `TronPower` via `updateFrozenInfoAndTotalResourceWeight()`, directly mutating `AccountCapsule` fields that feed into `AccountCapsule.getTronPower()`. [1](#0-0) [2](#0-1) 

Unlike its siblings that change frozen/tron-power balances, it never calls `mortgageService.withdrawReward(ownerAddress)` before mutating state. Compare with `UnfreezeBalanceActuator`/`UnfreezeBalanceV2Actuator`, which explicitly call `mortgageService.withdrawReward(ownerAddress)` first and comment that this "pulls" (settles) reward before the frozen/vote state is touched: [3](#0-2) [4](#0-3) 

`MortgageService.withdrawReward()` (the java-tron analog of `Divider.collect()`) computes and pays out reward for the `[beginCycle, endCycle)` window using the account's *current* votes list, then advances `beginCycle`/`endCycle` and snapshots the votes for the new cycle boundary: [5](#0-4) 

Because `CancelAllUnfreezeV2Actuator` changes the account's TronPower (and thus voting weight for existing votes) between the previous `withdrawReward` snapshot cycle and the next one, without first calling `withdrawReward` to close out the accrual period at the old TronPower, the next `withdrawReward` invocation (triggered by any later vote/freeze/unfreeze/withdraw action) will compute the reward for the entire elapsed multi-cycle window using the *new*, restored TronPower value rather than the value that actually existed during those cycles — exactly the "backfill uses stale/unsettled accrual state" pattern described in the report (`join()` pulling backfill amounts based on unsettled `collect()` state).

### Impact Explanation
`VoteRewardUtil`/`MortgageService.computeReward()` reward math is a function of the account's vote weight, which is bounded by TronPower. `CancelAllUnfreezeV2Actuator` restores frozen balance (and TronPower) into the account without settling the vote-reward accrual for the interval where TronPower was smaller. Depending on how `computeReward` uses the account snapshot vs. current TronPower, this can cause under- or over-crediting of SR voting rewards for the affected account across the unsettled cycles — i.e., unbacked/incorrect reward balances credited from `DelegationStore`'s shared reward pool, which is a shared, protocol-level asset. This is a fund-accounting correctness bug reachable by any account holder via a signed `CancelAllUnfreezeV2Contract` transaction.

### Likelihood Explanation
Reachable by any unprivileged account: freeze balance → unfreeze (creates `UnfreezeV2` entries) → vote for a witness → wait one or more maintenance cycles without triggering any reward-settling action → call `CancelAllUnfreezeV2` (`CancelAllUnfreezeV2Contract`) to restore the frozen balance and TronPower → subsequently withdraw/vote/unfreeze to trigger `withdrawReward` and observe reward computed against a TronPower value that didn't exist during the elapsed cycles. Requires `dynamicStore.supportAllowCancelAllUnfreezeV2()` to be enabled (committee-controlled feature flag) and a non-empty `unfrozenV2List`, both of which are ordinary preconditions, not privileged operations.

### Recommendation
Call `mortgageService.withdrawReward(ownerAddress)` at the start of `CancelAllUnfreezeV2Actuator.execute()`, before any change to `FrozenV2`/`TronPower`-affecting fields, mirroring the pattern already used in `UnfreezeBalanceActuator`, `UnfreezeBalanceV2Actuator`, and `VoteWitnessActuator`. This settles the reward accrual against the account's pre-change TronPower before the resource-weight/TronPower is mutated.

### Proof of Concept
Not independently executed; based on static code analysis of the actuator/service classes cited above. A concrete PoC would need to: (1) freeze balance, (2) vote for a witness, (3) unfreeze (build `UnfreezeV2` entries and reduce TronPower), (4) let several maintenance cycles pass without any action that calls `mortgageService.withdrawReward`, (5) call `CancelAllUnfreezeV2Contract` to restore TronPower, then (6) trigger `withdrawReward` (e.g. via `WithdrawBalanceActuator` or another vote action) and compare the paid reward against the reward that should have accrued using the actual historical TronPower per cycle — this last verification step was not run and should be validated in a test harness such as `framework/src/test/java/org/tron/core/actuator/CancelAllUnfreezeV2ActuatorTest.java`.

  public void withdrawReward(byte[] address) {
    if (!dynamicPropertiesStore.allowChangeDelegation()) {
      return;
    }
    AccountCapsule accountCapsule = accountStore.get(address);
    long beginCycle = delegationStore.getBeginCycle(address);
    long endCycle = delegationStore.getEndCycle(address);
    long currentCycle = dynamicPropertiesStore.getCurrentCycleNumber();
    long reward = 0;
    if (beginCycle > currentCycle || accountCapsule == null) {
      return;
    }
    if (beginCycle == currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        return;
      }
    }
    //withdraw the latest cycle reward
    if (beginCycle + 1 == endCycle && beginCycle < currentCycle) {
      AccountCapsule account = delegationStore.getAccountVote(beginCycle, address);
      if (account != null) {
        reward = computeReward(beginCycle, endCycle, account);
        adjustAllowance(address, reward);
        reward = 0;
        logger.info("Latest cycle reward {}, {}.", beginCycle, account.getVotesList());
      }
      beginCycle += 1;
    }
    //
    endCycle = currentCycle;
    if (CollectionUtils.isEmpty(accountCapsule.getVotesList())) {
      delegationStore.setBeginCycle(address, endCycle + 1);
      return;
    }
    if (beginCycle < endCycle) {
      reward += computeReward(beginCycle, endCycle, accountCapsule);
      adjustAllowance(address, reward);
    }
    delegationStore.setBeginCycle(address, endCycle);
    delegationStore.setEndCycle(address, endCycle + 1);
    delegationStore.setAccountVote(endCycle, address, accountCapsule);
    logger.info("Adjust {} allowance {}, now currentCycle {}, beginCycle {}, endCycle {}, "
            + "account vote {}.", Hex.toHexString(address), reward, currentCycle,
        beginCycle, endCycle, accountCapsule.getVotesList());
  }
