### Title
Stale per-routine conntrack cache bypasses firewall rule revalidation after reload - (File: firewall.go, firewall/cache.go)

### Summary
The Cally report describes a class of bug where a cached/stored value is trusted for later state-changing operations without being kept in sync with the actual, current underlying state — causing incorrect outcomes to persist. In Nebula's firewall enforcement path, the same root cause pattern occurs: the per-routine local conntrack cache (`firewall.ConntrackCache`) is consulted as an authoritative "already allowed" signal without ever being cross-checked against the firewall's current `rulesVersion`, unlike the authoritative shared conntrack table which does perform this check.

### Finding Description
`Firewall.inConns` first checks the caller-supplied `localCache` and, if the packet tuple is present, immediately returns `true` (allow) with no further validation: [1](#0-0) 

Only if the tuple is *not* found in `localCache` does the code fall through to the authoritative conntrack table, which explicitly re-validates old entries against the current firewall ruleset whenever `f.rulesVersion` has changed since the connection was tracked: [2](#0-1) 

After a successful lookup/creation in the authoritative table, the packet tuple is written into `localCache` for the remainder of the local cache "tick": [3](#0-2) 

The `ConntrackCache`/`ConntrackCacheTicker` type stores no `rulesVersion` field at all — its only invalidation mechanism is a periodic ticker that clears the whole map, independent of firewall reloads: [4](#0-3) [5](#0-4) 

Because the local cache entry carries no rule-version metadata, once a flow is admitted into `localCache` it will continue to be allowed by `Drop`/`inConns` for the remainder of the cache interval — bypassing the rule-version re-validation logic in the shared conntrack table — even if a `SIGHUP`/config reload immediately afterward removes or narrows the rule that originally permitted this flow. This mirrors the reported "stale stored value drives future decisions instead of the live/current value" defect class, here manifesting in a security enforcement path (the firewall) rather than an accounting path.

### Impact Explanation
This allows already-established flows to continue passing through the firewall for up to one local-cache tick (governed by `firewall.conntrack.routine_cache_timeout`, defaulting to `1s` when multiple worker routines are configured) after an administrator has tightened or removed the rule that permitted them via a config reload. This is a firewall bypass: traffic that should be dropped under the new ruleset is instead admitted solely because it was cached locally under the old ruleset, directly undermining the freshly-applied security policy during the propagation window.

### Likelihood Explanation
This is reachable by any peer that already has an established (allowed) flow at the moment a firewall reload occurs — no CA-signed certificate compromise or malicious peer behavior is required, only ordinary traffic continuing across a legitimate rule change. The condition is deterministic given the code path (no revalidation of `localCache` hits against `rulesVersion`), so likelihood of triggering the stale-allow window is high whenever `routine_cache_timeout` is nonzero (which is the default when `routines > 1`), though the impact window is bounded by the tick duration.

### Recommendation
Store the `rulesVersion` (or a monotonic firewall config generation counter) alongside each `ConntrackCache` entry, and have `inConns` compare it against the firewall's current `rulesVersion` before trusting a local-cache hit — falling through to the authoritative conntrack table's revalidation logic (as already done for the shared `conntrack.Conns` map) whenever the versions differ. Alternatively, force an immediate reset of all per-routine `ConntrackCacheTicker` instances whenever the firewall is reloaded, rather than relying solely on the independent time-based tick.

### Proof of Concept
1. Configure Nebula with `routines > 1` (enabling the routine-local conntrack cache with its default `1s` tick) and a firewall rule permitting inbound traffic from group `A` on port `443`.
2. Peer in group `A` opens a TCP connection; the flow is admitted via `Firewall.Drop` → `inConns`, added to the shared `conntrack.Conns` table, and cached in the calling goroutine's `localCache`.
3. Operator issues a `SIGHUP` reload that removes the rule permitting group `A`, incrementing `f.rulesVersion`.
4. Within the current local-cache tick window, the same goroutine processes another packet for the same flow tuple: `inConns` sees the entry present in `localCache` and returns `true` immediately at firewall.go:505-510 — the `rulesVersion` check at firewall.go:527 is never reached, so the flow keeps passing despite no longer matching any rule.
5. Traffic continues to be allowed until the local cache tick advances and clears the map, at which point the flow would finally be re-evaluated (and dropped) via the authoritative table.

```go
// ConntrackCache is used as a local routine cache to know if a given flow
// has been seen in the conntrack table.
type ConntrackCache map[Packet]struct{}

type ConntrackCacheTicker struct {
	cacheV    uint64
	cacheTick atomic.Uint64

	l     *slog.Logger
	cache ConntrackCache
}
```

**File:** firewall/cache.go (L50-67)
```go
// Get checks if the cache ticker has moved to the next version before returning
// the map. If it has moved, we reset the map.
func (c *ConntrackCacheTicker) Get() ConntrackCache {
	if c == nil {
		return nil
	}
	if tick := c.cacheTick.Load(); tick != c.cacheV {
		c.cacheV = tick
		if ll := len(c.cache); ll > 0 {
			if c.l.Enabled(context.Background(), slog.LevelDebug) {
				c.l.Debug("resetting conntrack cache", "len", ll)
			}
			c.cache = make(ConntrackCache, ll)
		}
	}

	return c.cache
}
```
