### Title
Node-wide DoS via a single expensive smart-contract transaction serializing block application on the shared `Manager` lock - (File: `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
`Manager.pushTransaction()` and `Manager.pushBlock()` both synchronize on the same monitor — the `Manager` instance itself (`synchronized (this)`). Any unprivileged, signed transaction broadcast to the network is admitted into the pending pool via `pushTransaction()`, which executes the transaction's actuator/VM logic (`processTransaction`) *while holding this global lock*. Because `pushBlock()` — the method that applies newly received or self-produced blocks — needs the very same lock, a stream of maximally-expensive `TriggerSmartContract`/`CreateSmartContract` transactions from a single unprivileged account can repeatedly hold that lock for a bounded-but-large fraction of the CPU-time budget, delaying block application/broadcast propagation across the network, similar in spirit to the reported Discourse issue where one tenant's job blocks the shared "defer queue" for everyone else.

### Finding Description
`pushTransaction()` first busy-waits until no block is being applied (`isBlockWaitingLock()`), then enters `synchronized (this)` and calls `processTransaction(trx, null)` for the incoming transaction before releasing the lock: [1](#0-0) 

`pushBlock()` uses `setBlockWaitLock(true)` (an `AtomicInteger` flag checked by `pushTransaction`) and then also takes `synchronized (this)` to apply the block: [2](#0-1) 

Both code paths lock the exact same object monitor (the `Manager` bean, `this`). `setBlockWaitLock`/`isBlockWaitingLock` only prevents a *new* `pushTransaction` from starting once a block push has begun signaling; it does **not** prevent a `pushTransaction` that is already inside its `synchronized (this)` block (executing a smart-contract VM call) from continuing to hold the monitor while a new block arrives and tries to enter `pushBlock`'s own `synchronized (this)`: [3](#0-2) 

The execution time an attacker can force inside that critical section is governed by the VM's per-transaction CPU deadline, computed in `VMActuator` from `getMaxCpuTimeOfOneTx()` and `maxTimeRatio` (default `5.0`), and enforced opcode-by-opcode in `Program.checkCPUTimeLimit()`: [4](#0-3) [5](#0-4) 

The endless-loop VM test confirms that a crafted contract will consume the full CPU-time budget before being aborted with `OutOfTimeException`/`OutOfEnergyException`: [6](#0-5) 

An attacker only needs a funded account and enough `feeLimit`/bandwidth to keep submitting such transactions through the normal broadcast path (`TransactionsMsgHandler.handleTransaction` → `TronNetDelegate.pushTransaction` → `Manager.pushTransaction`), each one re-acquiring `synchronized (this)` and running close to the CPU deadline before being processed/rejected: [7](#0-6) 

### Impact Explanation
By continuously feeding worst-case-CPU smart-contract transactions into the mempool, an unprivileged broadcaster forces every full node that receives and processes those transactions to spend the maximum allowed VM time inside the same monitor `pushBlock()` must acquire to apply new blocks. This delays block application, propagation, and downstream consensus/liveness signaling on affected nodes, and stacks with `netMaxTrxPerSecond`/`maxTrxCacheSize` limits being consumed by the flood. This is a genuine node/service-level denial-of-service analog to the reported "defer queue" starvation bug — one actor's cheap-to-submit, expensive-to-execute work item can repeatedly stall shared queue/lock resources that other participants (block processing) depend on.

### Likelihood Explanation
Likelihood is Medium: the attack requires only a normally signed transaction (no special privilege) crafted to spend near-maximum energy/CPU per call, and it can be repeated at the rate allowed by bandwidth/energy economics and `netMaxTrxPerSecond`. The per-transaction lock-hold time is bounded by the VM CPU-time deadline (not unbounded), so this is a throughput/latency degradation rather than a permanent hang; sustained impact requires sustained submission (and funds/energy to pay for it), which somewhat limits severity relative to a true unbounded lock.

### Recommendation
Decouple `pushTransaction`'s VM/actuator execution from the block-application lock: execute transaction validation/VM under a narrower lock (or a per-transaction lock) and only take the `Manager`-wide monitor for the minimal state mutation needed to enqueue into `pendingTransactions`, so `pushBlock` never has to wait behind a transaction's VM execution. Alternatively, have `pushTransaction` check `isBlockWaitingLock()`/yield periodically during long VM execution, or move `processTransaction` invocation outside of `synchronized(this)` with a fine-grained lock protecting only the pending-queue and session state.

### Proof of Concept
1. Deploy (or reuse) a contract whose entry function contains a tight, energy-cheap-but-CPU-heavy loop (as in `EnergyWhenTimeoutStyleTest.endlessLoopTest`), sized so VM execution runs until `Program.checkCPUTimeLimit` trips near the max CPU-time deadline.
2. From an unprivileged account with sufficient bandwidth/energy, repeatedly broadcast `TriggerSmartContract` transactions calling that function, at a rate close to `netMaxTrxPerSecond`.
3. Each transaction reaching `Manager.pushTransaction()` executes `processTransaction()` inside `synchronized (this)` for up to the configured CPU-time budget (`maxCpuTimeOfOneTx * maxTimeRatio`) before failing with `OutOfTimeException`.
4. Concurrently observe that new blocks arriving at the node via `TronNetDelegate.processBlock()` → `Manager.pushBlock()` are delayed because they must acquire the same `Manager` monitor, increasing `tron:block_push_latency_seconds` / `tron:lock_acquire_latency_seconds` and delaying block propagation/production readiness on the affected node.
