## Title
Democracy referendum approval threshold uses `total_issuance()` snapshotted at bake-time instead of at referendum launch, letting issuance drift during the voting period silently alter Adaptive Quorum Biasing outcomes — (`substrate/frame/democracy/src/lib.rs`)

### Summary
`pallet-democracy`'s `bake_referendum` compares the referendum's tally against `T::Currency::total_issuance()` fetched live at maturation time, rather than a value pinned to when the referendum was launched via `inject_referendum`. This is the same broken-invariant class described in the external report: a threshold's denominator ("electorate"/"totalVotingPower") is allowed to drift between snapshot-time votes and decision-time evaluation, silently making referenda harder or easier to pass than intended when the vote was proposed.

### Finding Description
When a referendum is created (`launch_external`/`launch_public` → `inject_referendum`), only `end`, `proposal`, `threshold`, `delay`, and an empty `tally` are stored: [1](#0-0) 

No snapshot of `total_issuance` is taken at this point. Voters accumulate `status.tally` (ayes/nays/turnout, weighted by locked balance and conviction) over the entire `VotingPeriod` via `vote`/`try_vote`. At the end of the voting period, `begin_block` calls `bake_referendum`, which decides pass/fail using the **current** issuance: [2](#0-1) 

This value is fed into `VoteThreshold::approved`, which uses `electorate` as the denominator for Adaptive Quorum Biasing (`SuperMajorityApprove`/`SuperMajorityAgainst`) via `compare_rationals` against `sqrt_electorate`: [3](#0-2) 

The votes composing `status.tally` were cast against a balance/electorate baseline that existed throughout the `VotingPeriod` (which can span many days), but the pass/fail decision is made against whatever `total_issuance` happens to be at the exact block the referendum matures — a value that has moved due to ongoing protocol issuance (e.g., staking era payouts mint new tokens every era) unrelated to any vote. This is structurally identical to the reported bug: the tally is bound to one point in time while the threshold denominator is evaluated at another, uncontrolled point in time, so the same tally can resolve to pass or fail depending purely on unrelated issuance drift.

### Impact Explanation
Because `VoteThreshold::SuperMajorityApprove`/`SuperMajorityAgainst` are the exact mechanism gating whether a referendum enacts a call with `RawOrigin::Root` (see `bake_referendum`'s `Scheduler::schedule_named(... RawOrigin::Root ...)`), a mismatched electorate denominator can cause:
- A referendum that *should* pass under its intended Adaptive Quorum Biasing threshold to be rejected (issuance grew during the voting window, raising `sqrt_electorate`), or
- A referendum that *should not* pass to be approved (issuance effectively lower relative to what voters assumed), enacting root-level runtime changes.

This directly compromises the intended behavior of the governance consensus mechanism that ultimately controls privileged/root dispatch on the chain, matching the "runtime bugs that compromise intended behavior" and "false state acceptance" impact categories.

### Likelihood Explanation
`VotingPeriod` is long by design (days), and total issuance is not static — it continuously increases via staking inflation/era payouts and other minting paths that occur regardless of any single referendum. Every ongoing referendum is therefore exposed to this drift with no attacker action required; it is a deterministic consequence of the existing code path, not a hypothetical edge case, making likelihood high for long-running or borderline (near-threshold) referenda.

### Recommendation
Snapshot `total_issuance` (or an equivalent frozen "electorate" value) at `inject_referendum` time and store it in `ReferendumStatus`, then use that stored snapshot in `bake_referendum`'s `status.threshold.approved(status.tally, snapshot_issuance)` call instead of re-reading `T::Currency::total_issuance()` at bake time — mirroring the fix pattern recommended in the external report (snapshot the value used as denominator at the same time the tally begins accumulating, and use the snapshot consistently wherever the threshold is evaluated).

### Proof of Concept
1. Referendum R is launched at block `N` with `total_issuance = I0`; `VotingPeriod` runs until block `N + P`.
2. Voters cast votes over `[N, N+P]`; `status.tally` accumulates ayes/nays/turnout based on their locked balances — this behavior is fixed and doesn't change.
3. Between `N` and `N+P`, staking era payouts mint new tokens, increasing issuance to `I1 > I0` (a normal, expected occurrence over a multi-day voting period, not requiring any admin/attacker action).
4. At block `N+P`, `begin_block` → `bake_referendum` reads `total_issuance = I1` (not `I0`) and calls `status.threshold.approved(status.tally, I1)`.
5. For a referendum whose tally would have passed `SuperMajorityApprove` against `I0` but fails against the larger `sqrt(I1)` denominator (or vice-versa for a decrease scenario), the pass/fail outcome differs from what voters intended when the referendum was proposed and voted on — directly reproducing the reported invariant break (`electorate`/`totalVotingPower` must be evaluated at the same snapshot time as the votes it's compared against).

	}

	fn approved(&self, tally: Tally<Balance>, electorate: Balance) -> bool {
		let sqrt_voters = tally.turnout.integer_sqrt();
		let sqrt_electorate = electorate.integer_sqrt();
		if sqrt_voters.is_zero() {
			return false;
		}
		match *self {
			VoteThreshold::SuperMajorityApprove => {
				compare_rationals(tally.nays, sqrt_voters, tally.ayes, sqrt_electorate)
			},
			VoteThreshold::SuperMajorityAgainst => {
				compare_rationals(tally.nays, sqrt_electorate, tally.ayes, sqrt_voters)
			},
			VoteThreshold::SimpleMajority => tally.ayes > tally.nays,
		}
	}
