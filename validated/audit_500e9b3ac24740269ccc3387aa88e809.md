### Title
Unguarded `(- ta-preview reserve-inc)` in treasury-LP minting can underflow and revert every vault action - ([File: mainnet/contracts/vault/v0-vault-stx.clar])

### Summary
`accrue` and its preview counterpart `calc-treasury-lp-preview` compute the DAO treasury's LP mint amount as `reserve-inc * total-supply / (ta-preview - reserve-inc)`. Unlike every sibling subtraction in the same file (`debt-delta`, `interest` in `total-assets`/`total-assets-preview`, `get-available-assets`), this particular subtraction is performed with no `if (> a b) (- a b) u0` / `>=` guard. If `reserve-inc` (the reserve-factor cut of this period's interest) is ever `>= ta-preview` (total assets preview), the subtraction underflows a `uint`, triggering a Clarity runtime panic and reverting the entire call — this is the same "unordered subtraction leading to underflow revert / DoS" bug class as the reported `getMaxDailyBuy` issue.

### Finding Description
`accrue` is invoked from essentially every state-changing entry point of each vault (`deposit`, `redeem`, `system-borrow`, `system-repay`, `socialize-debt`, `flashloan`), and transitively from every `market.clar` action that touches a position (`borrow`, `repay`, `collateral-add/remove`, `liquidate`) because the market always accrues before touching vault state. Every other subtraction of two dynamically-derived `uint`s in this file is defensively ordered/guarded, e.g.:
- `debt-delta` is guarded: `(if (> new-debt old-debt) (- new-debt old-debt) u0)` [4](#0-3) 
- `interest` inside `total-assets`/`total-assets-preview` is guarded the same way [5](#0-4) 
- `get-available-assets` is guarded with `(if (>= current-assets borrowed) (- current-assets borrowed) u0)` [6](#0-5) 

but `(- ta-preview reserve-inc)` / `(- (total-assets-preview) reserve-inc)` has no such guard at all — it only checks `reserve-inc > u0` before computing the division, not whether `ta-preview >= reserve-inc`. `reserve-inc` is not intrinsically bounded to be smaller than `ta-preview`: it is derived from `debt-delta` (change in `principal-scaled * index`) scaled by the DAO-set `fee-reserve` factor, while `ta-preview` is derived independently from `current-assets` (the vault's on-hand token balance, which can be driven to zero via `system-borrow`) plus `interest` computed from a *different* pair of quantities (`debt-preview` vs. `total-borrowed`, not vs. `old-debt`). Because `debt-delta` and `interest` are not defined against the same baseline, there is no algebraic guarantee that `reserve-inc <= ta-preview` in all reachable states (e.g., after `total-borrowed` has been reduced disproportionately by `socialize-debt`, which adjusts `principal-scaled` exactly but `total-borrowed` only proportionally, or in low-liquidity/high-scaled-principal states shortly after large borrows). This is the same class of bug the external report describes: performing subtraction between two derived quantities without validating their relative ordering before the operation, guarded correctly elsewhere in the same contract but not here.

This affects all six vault contracts (`v0-vault-stx`, `v0-vault-usdc`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-ststxbtc`, `v0-vault-usdh`) since they share identical `accrue`/`calc-treasury-lp-preview` logic.

### Impact Explanation
If the underflow condition is hit, `accrue` panics and reverts, and because `accrue` gates every deposit, withdrawal, borrow, repay and liquidation on the affected vault, the vault becomes permanently unusable until a DAO-privileged fix is deployed — this is a temporary/permanent freezing of user funds (deposits, collateral, and unclaimed yield) sitting in that vault, matching the in-scope "temporary freezing of funds" / "permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
Reaching the specific numeric relationship where `reserve-inc >= ta-preview` requires a combination of low `current-assets` (heavily borrowed vault) and either an unusually large per-period interest delta or index/principal skew introduced by `socialize-debt` write-downs, so it is not trivially triggerable on every call. However, it requires no privileged action and no DAO compromise — an ordinary borrower/liquidator sequence (large borrow draining `current-assets`, followed by a bad-debt liquidation invoking `socialize-debt`, followed by normal `accrue` on the next interaction) can plausibly drive the vault into this state, making it a realistic, unprivileged-triggerable DoS.

### Recommendation
Guard the subtraction the same way every sibling computation in the file is guarded, e.g.:
```
(if (> ta-preview reserve-inc)
    (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
    u0)
```
applied both in `calc-treasury-lp-preview` (line 360) and in `accrue` (line 850), across all six vault contracts.

### Proof of Concept
Conceptually:
1. Attacker (or any borrower) borrows heavily against collateral via `market.clar` `borrow`, driving a vault's `assets` (on-hand liquidity) close to zero via `system-borrow`.
2. A subsequent bad-debt event (uncollateralized position, e.g. from an oracle price drop) triggers `liquidate` → `socialize-debt`, which reduces `total-borrowed` proportionally but `principal-scaled` by the exact scaled amount, decoupling the ratio the borrow `index` tracks from `total-borrowed`.
3. On the next call that triggers `accrue` (any deposit/borrow/repay), `debt-delta` (computed from `principal-scaled`/`index`) and `interest` (computed from `debt-preview`/`total-borrowed`) can diverge such that `reserve-inc > total-assets-preview`.
4. `(- ta-preview reserve-inc)` underflows, `accrue` panics, and the transaction — and all subsequent transactions touching that vault — revert, freezing the vault.

Note: I was not able to fully enumerate all numeric preconditions required to force `reserve-inc >= ta-preview` from first principles within the available exploration; a background Devin session with test-execution access would be needed to construct a concrete numeric trace (specific borrow/socialize-debt/time-delta sequence) that reproduces the panic, since the index-cache and DAO-configurable `fee-reserve`/`cap-debt` parameters materially affect the exact threshold.
