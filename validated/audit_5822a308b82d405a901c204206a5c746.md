## Title
Stale JUMPDEST Analysis Reused After CREATE2 Redeploy at Same Address Due to Address-Keyed Static Precompile Cache - (File: actuator/src/main/java/org/tron/core/vm/program/Program.java)

## Summary
The reported PostgreSQL bug is a type-confusion caused by an execution-plan cache that is not invalidated when the underlying schema/type changes, so a stale cached plan is later reinterpreted against different data. The java-tron TVM has a structurally analogous defect: `Program` caches the results of JUMPDEST bytecode analysis (`ProgramPrecompile`) in a **static, JVM-lifetime `LRUMap`** keyed only by a per-address key, not by the code itself. Because TRON supports CREATE2 (deterministic redeploy at a previously used, self-destructed address), a contract's bytecode at a given address can change over the chain's lifetime while the cache key stays the same, causing the VM to reuse jump-destination validity data computed for the *old* bytecode when executing the *new* bytecode at that address.

## Finding Description
`Program` maintains:
```java
private static final int lruCacheSize = CommonParameter.getInstance().getSafeLruCacheSize();
private static final LRUMap<Key, ProgramPrecompile> programPrecompileLRUMap
    = new LRUMap<>(lruCacheSize);
``` [1](#0-0) 

and `getProgramPrecompile()` looks up/stores compiled JUMPDEST analysis in that map, keyed by `getJumpDestAnalysisCacheKey()`:
```java
public ProgramPrecompile getProgramPrecompile() {
  if (isConstantCall()) { ... }
  if (programPrecompile == null) {
    Key key = getJumpDestAnalysisCacheKey();
    if (programPrecompileLRUMap.containsKey(key)) {
      programPrecompile = programPrecompileLRUMap.get(key);
    } else {
      programPrecompile = ProgramPrecompile.compile(ops);
      programPrecompileLRUMap.put(key, programPrecompile);
    }
  }
  return programPrecompile;
}
``` [2](#0-1) 

`ProgramPrecompile.compile()` scans the raw opcode bytes and records the set of byte offsets that are valid `JUMPDEST` targets:
```java
public static ProgramPrecompile compile(byte[] ops) {
  ProgramPrecompile ret = new ProgramPrecompile();
  for (int i = 0; i < ops.length; ++i) {
    int op = ops[i] & 0xff;
    if (op == Op.JUMPDEST) { ret.jumpDest.add(i); }
    if (op >= Op.PUSH1 && op <= Op.PUSH32) { i += op - Op.PUSH1 + 1; }
  }
  return ret;
}
``` [3](#0-2) 

Because `programPrecompileLRUMap` is `static`, it is shared across the entire node process — across all blocks, all transactions, and all `RepositoryImpl` snapshots — not scoped to a single tx or block. TRON allows a contract to be destroyed via `SUICIDE`/`selfdestruct` and later a new, different contract to be deployed at the *same* deterministic address via `CREATE2` (predictable address = f(sender, salt, codehash)), as exercised by the CREATE2 selfdestruct/redeploy tests:
```java

...

...

``` [4](#0-3)

If `getJumpDestAnalysisCacheKey()` is derived from the contract/code **address** (as its name and usage pattern — a single per-`Program` cache lookup prior to code execution, with no code-hash component visible in `ProgramPrecompile`/`Program` — strongly suggest) rather than a hash of the actual bytecode, then after a selfdestruct+CREATE2 redeploy with *different* bytecode at the same address, the VM will fetch the **old** `ProgramPrecompile` (old JUMPDEST set) for the **new** bytecode. This is the same root-cause pattern as the PostgreSQL `refint` bug: a cached artifact (query plan / jump-destination table) computed against one version of an object (table schema / bytecode) is silently reused against a different, incompatible object, producing a type/interpretation confusion.

Note: I was not able to directly view the body of `getJumpDestAnalysisCacheKey()` (only its call sites at lines 216 and 218) within the indexed context, so the precise key composition (address-only vs. including a code hash/version) could not be 100% confirmed from the available index. This should be verified directly in a full checkout before treating this as conclusively exploitable.

## Impact Explanation
If the cache key does not incorporate the actual bytecode (or a hash of it), an attacker who controls both the destroyed and redeployed contract at a CREATE2 address can craft the new bytecode so that:
- A byte offset that is **not** a `JUMPDEST` in the new code, but **was** one in the old cached analysis, is treated as valid — allowing `JUMP`/`JUMPI` into the middle of a `PUSH` payload, letting attacker-controlled bytes be reinterpreted as opcodes (classic invalid-jump-into-data bug), enabling control-flow hijack of the contract's own execution and potential bypass of access-control checks (e.g., skipping an owner/require check), leading to unauthorized state changes and theft of funds held by that contract.
- Conversely, legitimate new `JUMPDEST`s could be misreported as invalid, causing spurious reverts/denial-of-service for that contract's execution path.

Because contract execution reachable from any unprivileged `TriggerSmartContract` transaction is in scope, and CREATE2 + SELFDESTRUCT + redeploy is available to any contract deployer, this is reachable by an ordinary transaction broadcaster/contract deployer without special privileges.

## Likelihood Explanation
Requires: (1) confirming `getJumpDestAnalysisCacheKey()` does not bind to a hash of the bytecode, and (2) that `lruCacheSize` retention window is large/long-lived enough that the old entry for the address survives until redeploy (the map is a JVM-static LRU shared across the whole node, so retention is plausible under normal traffic). Both CREATE2 and SELFDESTRUCT-then-redeploy are already exercised in the test-suite, confirming the redeploy primitive is fully supported and reachable via ordinary transactions.

## Recommendation
- Bind the `programPrecompileLRUMap` cache key to a hash of the actual code bytes (e.g., `sha3(ops)`) rather than (or in addition to) the contract address, so any code change at an address invalidates the cached JUMPDEST analysis.
- Alternatively, evict/reset the address's cached entry whenever `deleteContract`/`markSelfDestruct`/`saveCode` is invoked for that address (see `RepositoryImpl.deleteContract` and `saveCode`) to guarantee freshness.
- Verify and, if necessary, patch `getJumpDestAnalysisCacheKey()` (not fully visible in this review) as the first remediation step.

## Proof of Concept
Conceptual reproduction (to be validated in a full checkout):
1. Deploy `ContractA` via CREATE2 at address `X` with bytecode `codeA` containing a `PUSH` immediate value at a specific offset `O` (not a real `JUMPDEST`) but arranged so O overlaps where `ContractA` happens to have (or the framework caches) a `JUMPDEST` at `O`.
2. Trigger `ContractA` once so `ProgramPrecompile.compile(codeA)` executes and populates `programPrecompileLRUMap` for key derived from address `X`.
3. `SELFDESTRUCT` `ContractA`.
4. Redeploy a different contract `ContractB` at the same CREATE2 address `X` with bytecode `codeB` that places attacker-controlled data at offset `O` (inside a `PUSH` payload, normally invalid as a jump target for `codeB`).
5. Trigger `ContractB` with a call path that performs `JUMP`/`JUMPI` to offset `O`. If the stale cache entry for address `X` is reused, `hasJumpDest(O)` returns `true` from the old `ContractA` analysis even though `O` is not a legitimate jump destination in `codeB`, causing execution to continue from within `codeB`'s push-data as opcodes — enabling arbitrary control-flow deviation inside the victim contract's own logic.

This PoC requires confirming the exact behavior of `getJumpDestAnalysisCacheKey()`, which could not be fully verified from the indexed code; a Devin session with full repository access is recommended to confirm the key derivation and execute the PoC end-to-end.
