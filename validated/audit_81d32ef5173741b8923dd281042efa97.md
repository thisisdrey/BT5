### Title
Attacker-controlled `relayers` field lets a remote peer force a node to sever its connection to an innocent third-party relaying peer - ([File: stackslib/src/net/chat.rs])

### Summary
The `relayers: Vec<RelayData>` field embedded in `Transaction`/`Blocks`/`Microblocks`/`StackerDBChunk`/Nakamoto-block push messages is fully attacker-controlled wire data with no cryptographic binding to actual relay history. An attacker can plant the victim's own peer identity in this list before the message is ever forwarded by an honest intermediate peer, so when that intermediate peer legitimately relays the (otherwise valid) message to the victim, `process_relayers`/`check_relayers_remote` on the victim's side incorrectly concludes "this message originates from us" and returns `Err(net_error::InvalidMessage)`, causing the victim to tear down its conversation with the innocent relaying peer.

### Finding Description
`ConversationP2P::process_relayers` (stackslib/src/net/chat.rs:2057-2085) performs two anti-loop checks on the `relayers` list carried inside the message payload: `check_relayer_cycles` (chat.rs:2030-2039) and `check_relayers_remote` (chat.rs:2042-2050). The latter simply scans the relayer list for an entry whose `public_key_hash` equals the local peer's own address hash: [1](#0-0) 

This list is not authenticated relay-history: it is just a `Vec<RelayData>` decoded from the message payload that the *originating* sender constructs. Nothing ties an entry in this vector to an actual hop the message traversed. An attacker `A`, connected only to an honest peer `B`, can therefore craft a `Transaction` (or `Blocks`/`Microblocks`/`StackerDBChunk`) push whose `relayers` vector already contains victim `C`'s own `public_key_hash`/address, even though `C` has never touched the message.

`B` validates the message on its own `ConversationP2P` (the A↔B conversation): `process_relayers` runs with `local_peer = B`, finds no cycle and no entry matching `B`'s own address, so it passes. `B` treats the transaction as legitimately relayed and forwards/gossips it onward to its neighbors, including `C`, over the separate B↔C conversation. When `C` receives it, `validate_transaction_push` (chat.rs:2166-2199, and analogously `validate_blocks_push` chat.rs:2089-2124, `validate_microblocks_push` chat.rs:2129-2162, `validate_stackerdb_push` chat.rs:2204-2238, `validate_nakamoto_block_push` chat.rs:2243-2277) calls `self.process_relayers(local_peer, preamble, &relayers)` where `self` is the B↔C `ConversationP2P` and `local_peer = C`. Because the attacker-forged entry for `C` is still present in the (unmodified/forwarded) relayer list, `check_relayers_remote` returns `false`, and the validate function returns `Err(net_error::InvalidMessage)`: [2](#0-1) 

Per the question's cited call site (`validate_inbound_message`, chat.rs:2501-2514), this `InvalidMessage` error is treated as fatal for the conversation on which the message was received — i.e., the B↔C conversation is dropped — even though `B` did nothing wrong: it faithfully relayed a message whose fault (the forged relayer entry) was injected entirely by `A`, a party `B` (and `C`) have no reason to distrust for this specific field. `C` is misled into disconnecting from a legitimate peer `B` based on payload content that only the original attacker `A` controlled.

No guard in this path (payload length caps, mempool admission checks, bandwidth throttling) validates that entries in `relayers` correspond to peers that actually touched the message; the check is purely a self-consistency heuristic that trusts attacker-supplied data.

### Impact Explanation
A remote, unprivileged attacker who has any peer (even indirectly, by getting a message relayed through one hop) can cause a targeted node to unilaterally sever ties with an arbitrary, uninvolved third-party peer connection using a single crafted, otherwise valid application message (a mempool transaction push, a block/microblock push, or a StackerDB chunk push). This is a bounded, repeatable DoS: the attacker can repeat this against any conversation slot the target victim maintains, degrading the target's connectivity/mesh health and potentially partitioning it from honest peers, without needing any privileged role, secret, or high message volume.

### Likelihood Explanation
Preconditions are minimal: the attacker needs a P2P connection to some honest peer `B` that in turn peers with the target victim `C` (a common topology in a gossip network), and needs only to craft one message whose `relayers` vector contains `C`'s public key hash. No signature over the relayer list, no special permissions, and no volumetric flooding are required — this is a single-message, deterministic condition, fully within the "few messages" DoS category and remotely reachable via the standard P2P push handlers.

### Recommendation
Do not treat a self-referential entry in the attacker/sender-supplied `relayers` list as a reason to terminate the *receiving* conversation. At minimum:
- Drop/ignore the specific message (e.g., respond as if malformed/ignored) instead of returning an error that tears down the conversation on which it arrived.
- Only apply the "originates from us" and cycle checks to influence gossip/rebroadcast decisions (don't re-relay it further), not to sanction the immediate peer that delivered it, since that peer cannot be assumed at fault for payload content it did not originate.
- Consider bounding trust in `relayers` entries by requiring that each entry be attributable to the direct sender's own signed relay step, rather than accepting an arbitrary, attacker-supplied vector, and cap penalization to lightweight NACK/score decrement rather than connection teardown.

Build a `StacksTransaction` push `Preamble` + payload where `relayers: Vec<RelayData>` contains a single `RelayData` whose `peer.public_key_hash` equals `C`'s own `local_peer.to_neighbor_addr().public_key_hash` (simulating the forged entry injected upstream by attacker `A` and forwarded unmodified by honest `B`).
3. Call `conversation.validate_transaction_push(&network, &preamble, relayers)` directly (or drive it through `validate_inbound_message`/`chat_neighbors_check` if exposed in tests).
4. Assert the call returns `Err(net_error::InvalidMessage)`, and assert/trace that this return value is what causes the caller (per `validate_inbound_message`, chat.rs:2501-2514) to mark the B↔C conversation as failed/to be dropped — even though the constructed scenario represents `B` (an innocent relayer) simply forwarding attacker `A`'s crafted message.

    /// Verify that we aren't in this relayers list
    fn check_relayers_remote(local_peer: &LocalPeer, relayers: &[RelayData]) -> bool {
        let addr = local_peer.to_neighbor_addr();
        for r in relayers.iter() {
            if r.peer.public_key_hash == addr.public_key_hash {
                return false;
            }
        }
        return true;
    }
