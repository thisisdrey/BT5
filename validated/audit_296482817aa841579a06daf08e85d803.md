Based on my review, the claim's core technical premise is accurate: `disable_transfer` (used by `do_lock_nft`) does not modify NFT ownership, and `fractionalize()` performs an ownership check via `T::Nfts::owner` without checking whether `NftToAsset` already contains an entry for the `(nft_collection_id, nft_id)` key before unconditionally overwriting it with `NftToAsset::<T>::insert`.

Audit Report

## Title
Re-fractionalizing an already-locked NFT overwrites `NftToAsset` and permanently orphans/locks the first depositor's deposit and asset holders' claim - ([File: substrate/frame/nft-fractionalization/src/lib.rs])

## Summary
`pallet-nft-fractionalization::fractionalize()` only verifies that the caller is the NFT's owner via `T::Nfts::owner`, but `do_lock_nft` calls `disable_transfer`, which does not change NFT ownership. As a result, the same owner can call `fractionalize()` a second time on an already-fractionalized NFT, silently overwriting the `NftToAsset` entry and permanently orphaning the first deposit and the first fractional-asset holders' redemption rights.

## Finding Description
`fractionalize()` [1](#0-0)  checks `nft_owner == who` using `T::Nfts::owner(&nft_collection_id, &nft_id)`, then calls `Self::do_lock_nft`, which only invokes `T::Nfts::disable_transfer` [2](#0-1) . The `owner` accessor reads the `Item` storage's `owner` field directly [3](#0-2) , and `disable_transfer` does not alter that field — it only affects transferability, so `nft_owner == who` continues to hold true for the original owner after the first fractionalization.

Critically, `fractionalize()` never checks `NftToAsset::<T>::get((nft_collection_id, nft_id))` for an existing entry before unconditionally overwriting it via `NftToAsset::<T>::insert(...)` [4](#0-3) . This allows the same owner to call `fractionalize()` a second time, taking a second deposit hold via `T::Currency::hold(&HoldReason::Fractionalized.into(), ...)` [5](#0-4)  and minting a second, independent asset, while silently discarding the first `Details` record that pointed to the first asset and first deposit.

`unify()` relies exclusively on the current `NftToAsset` record: `NftToAsset::<T>::try_mutate_exists(...).ok_or(Error::<T>::NftNotFractionalized)?` followed by `ensure!(details.asset == asset_id, Error::<T>::IncorrectAssetId)` [6](#0-5) . Once overwritten, holders of the first asset can never satisfy this equality check, and the first deposit — released only inside `unify()` — can never be released.

## Impact Explanation
This matches the "permanent user-fund or bridge-state lock" impact category: the first depositor's held `Deposit` (under `HoldReason::Fractionalized`) becomes permanently unreleasable, and holders of the first minted fractional asset permanently lose their ability to redeem the underlying NFT, since `unify()` can only ever satisfy the surviving (second) `Details` record. No privileged actor is required — the NFT's registered owner alone, whose ownership status is untouched by `disable_transfer`, can trigger this sequence through two ordinary signed `fractionalize()` calls.

## Likelihood Explanation
High. The exploit requires no race condition, no privilege escalation, and no interaction with any other party besides the pallet itself. Since `disable_transfer` does not alter the `owner` field checked by `fractionalize()`, the same account that completed the first fractionalization can trivially invoke `fractionalize()` again on the identical `(nft_collection_id, nft_id)` pair in a subsequent block/extrinsic.

## Recommendation
Add a guard in `fractionalize()` before locking the NFT and inserting into `NftToAsset`:
```rust
ensure!(!NftToAsset::<T>::contains_key((nft_collection_id, nft_id)), Error::<T>::AlreadyFractionalized);
```
Introduce a corresponding `AlreadyFractionalized` variant in `Error<T>` so that a resource that already carries an active fractionalization claim cannot be re-claimed by a second `fractionalize()` call.

## Proof of Concept
1. Alice owns NFT `(collection=1, item=1)` and calls `fractionalize(1, 1, asset_id=100, beneficiary=Bob, fractions=1000)`. This inserts `NftToAsset[(1,1)] = Details { asset: 100, ... }`, holds deposit `D1` from Alice, and mints 1000 units of asset `100` to Bob. `T::Nfts::owner(1,1)` remains `Alice` since `do_lock_nft` only calls `disable_transfer`.
2. Alice calls `fractionalize(1, 1, asset_id=200, beneficiary=Carol, fractions=500)` again. The `nft_owner == who` check passes (owner is still Alice); a second deposit `D2` is held; `NftToAsset[(1,1)]` is overwritten with `Details { asset: 200, ... }`.
3. Bob calls `unify(1, 1, asset_id=100, beneficiary=Bob)`. `try_mutate_exists` returns the current record with `asset: 200`; `ensure!(details.asset == asset_id, Error::<T>::IncorrectAssetId)` fails. Bob's 1000 units of asset `100` are now permanently unredeemable, and deposit `D1` is never released.

		pub fn fractionalize(
			origin: OriginFor<T>,
			nft_collection_id: T::NftCollectionId,
			nft_id: T::NftId,
			asset_id: AssetIdOf<T>,
			beneficiary: AccountIdLookupOf<T>,
			fractions: AssetBalanceOf<T>,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let beneficiary = T::Lookup::lookup(beneficiary)?;

			let nft_owner =
				T::Nfts::owner(&nft_collection_id, &nft_id).ok_or(Error::<T>::NftNotFound)?;
			ensure!(nft_owner == who, Error::<T>::NoPermission);

			let pallet_account = Self::get_pallet_account();
			let deposit = T::Deposit::get();
			T::Currency::hold(&HoldReason::Fractionalized.into(), &nft_owner, deposit)?;
			Self::do_lock_nft(nft_collection_id, nft_id)?;
			Self::do_create_asset(asset_id.clone(), pallet_account.clone())?;
			Self::do_mint_asset(asset_id.clone(), &beneficiary, fractions)?;
			Self::do_set_metadata(
				asset_id.clone(),
				&who,
				&pallet_account,
				&nft_collection_id,
				&nft_id,
			)?;

			NftToAsset::<T>::insert(
				(nft_collection_id, nft_id),
				Details { asset: asset_id.clone(), fractions, asset_creator: nft_owner, deposit },
			);

			Self::deposit_event(Event::NftFractionalized {
				nft_collection: nft_collection_id,
				nft: nft_id,
				fractions,
				asset: asset_id,
				beneficiary,
			});

			Ok(())
		}
