### Title
Unbounded per-item loops over attacker-controlled repeated fields in `GetCommitSignatures`/`ListCommitsByOid`/`ListCommitsByRefName` allow CPU/handler-resource exhaustion - ([File: internal/gitaly/service/commit/get_commit_signatures.go])

### Summary
`GetCommitSignatures` (and, analogously, `ListCommitsByOid` and `ListCommitsByRefName`) iterate over a fully client-controlled `repeated` field with no upper bound on its length and no way to page/batch the work, performing non-trivial per-item work (catfile object lookup, commit parsing, and — when server-side commit-signing is configured — cryptographic signature verification) inside a single unary/streaming RPC call. This mirrors the reported bug class: an accessor RPC whose total work is `O(N)` (here without even the mitigating small bounding factors `P`/`F` from the original report) driven entirely by an untrusted, unbounded list, with no batching mechanism, which can be used to make a single handler invocation run for a very long time / consume a lot of CPU.

### Finding Description
`GetCommitSignatures` validates only that each supplied `commit_id` is a well-formed hex string; it does **not** cap `len(request.GetCommitIds())`: [1](#0-0) 

The handler then loops over every supplied commit ID, performing a catfile object lookup, a commit parse, and — if `s.cfg.Git.SigningKey` is configured — a cryptographic `Verify` call per commit, streaming output progressively: [2](#0-1) 

The same unbounded-loop-over-repeated-field pattern (no length validation at all) exists in:
- `ListCommitsByOid`, iterating `in.GetOid()` and calling `catfile.GetCommit` per entry: [3](#0-2) 
- `ListCommitsByRefName`, iterating `in.GetRefNames()` and calling `catfile.GetCommit` per entry: [4](#0-3) 

None of these RPCs enforce a maximum collection size, and there is no repository-wide `MaxRecvMsgSize`/per-field limit found in the codebase that would cap the number of entries a client can submit in a single request (searches for `MaxRecvMsgSize`/`MaxMsgSize` and for length checks on `CommitIds`/`Oid`/`RefNames` returned nothing). This is the direct analog of the reported issue: an accessor path whose total work scales linearly (or worse) with an attacker-supplied, unbounded collection, with "no functionality to skip"/batch the work, forcing the full list to be processed in one call.

By contrast, RPCs like `ListCommits`/`ListAllCommits`/`ListRefs` in the same services do implement pagination (`PaginationParameter`, `WithMaxCount`) that caps the amount of work per call: [5](#0-4)  — showing the codebase is aware of this class of risk for some RPCs, but not for the `*ByOid`/`*ByRefName`/`GetCommitSignatures` family.

### Impact Explanation
Any client authorized to call these read-only (`ACCESSOR`) `CommitService` RPCs (an ordinary user with repository read access) can submit a request with a very large `commit_ids`/`oid`/`ref_names` list (bounded only by gRPC's default message size, which allows tens of thousands of 40/64-character hex strings in a single message). Each entry triggers real, non-negligible work — object reads via the catfile pipe, commit parsing, and (when repository/Gitaly-wide commit signing is enabled) GPG/SSH signature verification per commit — inside a single request-handling goroutine with no cooperative yielding to allow the server to cap or reject the excess work. This can tie up a Gitaly worker/goroutine and its catfile connection for an extended period, degrading availability for other tenants/repositories served by the same Gitaly node (a resource-exhaustion / DoS of the RPC handler), especially in a multi-tenant GitLab.com-style deployment where storage nodes are shared.

### Likelihood Explanation
High from a reachability standpoint: these are unauthenticated-at-the-Gitaly-layer, unprivileged, read-only RPCs reachable by any client with repository read access (no special repository state, hook execution, or admin privilege required), and the request shape (a plain repeated string/bytes field) is trivial for a client to construct with an arbitrarily large size. The severity of the resulting resource consumption is moderated by gRPC's default message-size ceiling and by the fact that catfile reads (not new process spawns) are used per item, so it is less severe than the `O(P*F*E)` triple-nested blowup in the original finding, but the missing size validation is a clear, concrete gap that the codebase itself fixes elsewhere (`ListCommits`, `ListAllCommits`, `ListRefs` all support pagination/limits).

### Recommendation
- Add an explicit maximum-length validation for `commit_ids` in `GetCommitSignatures`, `oid` in `ListCommitsByOid`, and `ref_names` in `ListCommitsByRefName` (mirroring the `MAX_ITEMS_LIMIT`-style guard suggested in the source report), rejecting oversized requests with `InvalidArgument` before doing any work.
- Alternatively/additionally, convert these RPCs to accept pagination parameters (as already done for `ListCommits`/`ListAllCommits`/`ListRefs`) so clients must request results in bounded batches.
- Consider making expensive per-item operations (especially signature verification) cancellable/interruptible against the request context, and account for per-RPC concurrency/queueing limits (`[[concurrency]]` config) for these RPCs to bound aggregate resource usage.

### Proof of Concept
1. As an ordinary user with read access to a repository (no elevated privileges required), open a `GetCommitSignatures` request against `CommitService`.
2. Populate `commit_ids` with the maximum number of valid-looking (or a mix of valid/invalid but correctly-hex-length) commit OIDs that fit under the gRPC message-size limit (tens of thousands of entries).
3. Send the request. Repeat concurrently from multiple sessions.
4. Observe the handler looping once per commit ID, performing catfile reads/parses (and signature verification if the server has `Git.SigningKey` configured) synchronously in the request goroutine, with no server-side cap rejecting the request up front — consuming CPU/catfile-connection time proportional to the attacker-chosen list size, and degrading throughput for other requests served by the same Gitaly process/storage.

*Note: I was unable to fully verify at runtime whether an operator-level Praefect/Gitaly `[[concurrency]]` limit or an external gRPC message-size cap is uniformly configured in production deployments to blunt this; the code-level analysis shows no in-handler size validation, which is the concrete, reproducible gap.*

func validateGetCommitSignaturesRequest(objectHash git.ObjectHash, request *gitalypb.GetCommitSignaturesRequest) error {
	if len(request.GetCommitIds()) == 0 {
		return errors.New("empty CommitIds")
	}

	// Do not support shorthand or invalid commit SHAs
	for _, commitID := range request.GetCommitIds() {
		if err := objectHash.ValidateHex(commitID); err != nil {
			return err
		}
	}

	return nil
}

func (s *server) ListCommitsByOid(in *gitalypb.ListCommitsByOidRequest, stream gitalypb.CommitService_ListCommitsByOidServer) error {
	ctx := stream.Context()
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return err
	}
	defer cancel()

	sender := chunk.New(&commitsByOidSender{stream: stream})
	listCommitsbyOidHistogram.Observe(float64(len(in.GetOid())))

	for _, oid := range in.GetOid() {
		commit, err := catfile.GetCommit(ctx, objectReader, git.Revision(oid))
		if errors.As(err, &catfile.NotFoundError{}) {
			continue
		}
		if err != nil {
			return err
		}

		if err := sender.Send(commit.GitCommit); err != nil {
			return err
		}
	}

	return sender.Flush()

func (s *server) ListCommitsByRefName(in *gitalypb.ListCommitsByRefNameRequest, stream gitalypb.CommitService_ListCommitsByRefNameServer) error {
	ctx := stream.Context()
	repository := in.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}
	repo := s.localRepoFactory.Build(repository)

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return structerr.NewInternal("%w", err)
	}
	defer cancel()

	sender := chunk.New(&commitsByRefNameSender{stream: stream})

	for _, refName := range in.GetRefNames() {
		commit, err := catfile.GetCommit(ctx, objectReader, git.Revision(refName))
		if errors.As(err, &catfile.NotFoundError{}) {
			continue
		}
		if err != nil {
			return structerr.NewInternal("%w", err)
		}

		commitByRef := &gitalypb.ListCommitsByRefNameResponse_CommitForRef{
			Commit: commit.GitCommit, RefName: refName,
		}

		if err := sender.Send(commitByRef); err != nil {
			return structerr.NewInternal("%w", err)
		}
	}

	return sender.Flush()
}
