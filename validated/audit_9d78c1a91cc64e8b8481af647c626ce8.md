### Title
Accessor RPCs bypass WAL transaction/snapshot isolation via client-controlled `git_object_directory`/`git_alternate_object_repositories` fields - ([File: internal/gitaly/storage/storagemgr/middleware.go])

### Summary
`beginTransactionForRepository()` decides whether an incoming repository-scoped RPC should be wrapped in a WAL transaction (with its associated snapshot isolation, quorum voting, and consistent-state guarantees) purely by inspecting whether the request's `Repository.GitObjectDirectory` / `Repository.GitAlternateObjectDirectories` fields are non-empty. These fields are ordinary, client-settable proto fields on every `*gitalypb.Repository` message, not internal, unforgeable state. An ordinary caller of any accessor RPC can set either field to any non-empty value and Gitaly will skip transaction creation entirely, running the handler directly against the live, un-snapshotted repository.

The code's own comment admits the precondition ("should only be configured on a repository coming from a request that was already configured with a quarantine directory... looped back to Gitaly from Rails' authorization checks") is not enforced and is "violated" whenever `GitObjectDirectory`/`GitAlternateObjectDirectories` are set directly by a caller — "This allows for circumventing the transaction management by configuring either of the object directories. We'll leave this unaddressed for now."

This is structurally the same bug class as the referenced report: a privileged/expected-only code path (Rails' internal quarantine loop-back, analogous to the "current campaign owner" who is supposed to pay fees) is gated on mutable, attacker-controlled data (the object-directory fields, analogous to the transferable `owner` address) rather than on an unforgeable, server-verified property. Just as the campaign owner could reassign ownership to dodge the fee check that only fires for the original creator, an ordinary Gitaly client can set an object-directory field to dodge the transaction-management gate that is only meant to fire for legitimate Rails-looped-back requests.

For any accessor RPC (`OpAccessor`), setting `GitObjectDirectory` (even to a bogus but non-empty string) causes `nonTransactionalRequest` to be returned, and the RPC handler executes without ever calling `storageHandle.Begin`, meaning no snapshot is taken and no WAL transaction wraps the read.

### Impact Explanation
Read-only/accessor RPCs are the ones normally protected by transactional snapshot isolation to guarantee consistent reads while concurrent writers mutate the repository via the WAL-based `TransactionManager`. By supplying a harmless-looking `git_object_directory` value on the `Repository` message of any accessor call, a normal user can force Gitaly to execute that RPC non-transactionally, directly against the mutable on-disk state. This defeats the consistency guarantees the transaction manager is designed to provide (the same class of guarantee the reference-transaction/quarantine hooks and WAL machinery exist to enforce), and it can lead to TOCTOU races and inconsistent reads/reference states versus what a properly snapshotted request would see, effectively letting a client selectively "opt itself out" of a resource/consistency-management gate the same way the Metrom bug let an owner opt itself out of the fee gate.

### Likelihood Explanation
The trigger is trivial: it only requires setting a non-empty value in `Repository.GitObjectDirectory` (or `GitAlternateObjectDirectories`) on any accessor request field that Gitaly's public gRPC API accepts from ordinary clients — no special privileges, tokens, or internal knowledge of Rails' loop-back protocol are required. The condition is checked purely on the wire-level request the client controls.

### Recommendation
Do not use client-supplied `GitObjectDirectory`/`GitAlternateObjectDirectories` values as the sole signal to skip transaction management. Instead, gate the quarantine-loop-back bypass on server-verified, unforgeable state — e.g. require and validate the accompanying `MetadataKeySnapshotRelativePath` header against an active transaction/quarantine prefix recorded server-side (as `QuarantineDirectoryPrefix` already does for path validation in `ObjectDirectoryPath`), or require an internally-issued transaction/quarantine token, rather than trusting the mere presence of an object-directory string supplied by the caller.

### Proof of Concept
1. As an ordinary Gitaly client, call any repository-scoped accessor RPC (e.g. `TreeEntry`, `ListRefs`, `FindCommit`) with `Repository.GitObjectDirectory` set to any non-empty string (e.g. `"objects"`).
2. `beginTransactionForRepository` sees `targetRepo.GetGitObjectDirectory() != ""`, treats the request as an accessor loop-back, and returns `nonTransactionalRequest` (`internal/gitaly/storage/storagemgr/middleware.go:271-296`), skipping `storageHandle.Begin` entirely.
3. The RPC executes directly against the live repository outside of any WAL snapshot, even though no genuine Rails-issued quarantine/transaction context exists — the caller has removed itself from transactional isolation using only a request field it fully controls.

	targetRepo, err := methodInfo.TargetRepo(req)
	if err != nil {
		if errors.Is(err, protoregistry.ErrRepositoryFieldNotFound) {
			// The above error is returned when the repository field is not set in the request.
			// Return instead the error many tests are asserting to be returned from the handlers.

		return transactionalizedRequest{}, fmt.Errorf("extract target repository: %w", err)
