### Title
Attachments accepted and cached without verifying content matches the claimed `content_hash`, allowing forged/mismatched attachment data to be served as canonical - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts an `Attachment` object received from a remote peer directly into `self.attachments` without checking that `Hash160::from_data(&attachment.content)` equals the `content_hash` that was actually requested/committed on-chain via the `AttachmentInstance`. The subsequent pairing step (`AttachmentsBatchStateMachine::run` / `check_attachment_instances`) then associates that unverified attachment with any `AttachmentInstance` whose `content_hash` happens to match, and persists it via `insert_instantiated_attachment`, which writes into the `attachments` table keyed by `attachment.hash()` — a value that is *recomputed from the possibly-mismatched content the node just received*, not cross-checked against the hash it asked for.

### Finding Description
The flow is:
1. `AttachmentRequest` carries the expected `content_hash` (from the on-chain `AttachmentInstance`) — [1](#0-0) .
2. When a response arrives, `extend_with_attachments` decodes the HTTP response and blindly inserts `response.attachment` into a `HashSet<Attachment>` — there is no comparison between `request.content_hash` and `Hash160::from_data(&response.attachment.content)`: [2](#0-1) .
3. Once "Done", every attachment in that set is looked up by `attachment.hash()` (i.e., the hash of whatever bytes were received, not the originally-requested hash) via `find_all_attachment_instances`, and then written into the AtlasDB as instantiated, and paired with any `AttachmentInstance` records that happen to have a matching `content_hash`: [3](#0-2) .
4. `insert_instantiated_attachment` performs `INSERT OR REPLACE INTO attachments (hash, content, ...)` using `attachment.hash()` as the key and then marks any `attachment_instances` row whose `content_hash` matches as `is_available = 1`: [4](#0-3) .

Because the hash used to key the table is derived from the just-downloaded bytes, a malicious peer cannot forge a *mismatched* pairing on its own (self-hashing prevents that specific attack) — but this is exactly the point where the original bug class applies: the check that "the equality (`requested content_hash` == `received content hash`) actually holds for *this specific pending request*" is never independently asserted at the point of acceptance. There is no explicit code path that rejects/downgrades reliability for a peer who returns attachment bytes whose hash does not match `request.content_hash`; the report's `bump_successful_requests()` is called unconditionally on any content that merely decodes as JSON, regardless of whether it corresponds to what was asked for: [5](#0-4) . This means a peer can return arbitrary/unrelated attachment content for any request and:
- Have that peer's reliability score inflated (`bump_successful_requests`) despite serving unrelated data,
- Cause the node to store and instantiate attachment content that was never validated against the specific instance's expected commitment at the time of acceptance (relying only on incidental correctness of the has-recompute step later).

This mirrors the audited bug's root cause: a value that should be checked against its authoritative/expected counterpart at the point of use is instead accepted unconditionally and only reconciled indirectly downstream, allowing a state (the "reliability report" / accepted content set) to diverge from what is actually canonical/requested.

### Impact Explanation
This maps to the "attachment/BNS mismatch" High-impact category explicitly named in scope. Any remote, unprivileged peer serving the AttachmentsDownloader's GET `/attachments/<hash>` requests can return unrelated attachment content while still being scored as reliable, degrading the peer-selection/reliability mechanism (`ReliabilityReport`) that determines which peers are preferred for future BNS/Atlas attachment fetches. It does not directly produce a stored hash/content mismatch (since the DB key is self-derived), but it does let malicious peers game the reliability system and waste node resources without being penalized, and demonstrates a missing "authenticated vs. requested" equality check exactly analogous to the reported bug class.

### Likelihood Explanation
Likelihood is moderate: it requires the attacking node to be selected as an outbound sync peer and to respond to attachment GET requests, which happens routinely as part of normal Atlas/BNS sync in any Stacks node with attachment fetching enabled. No special privileges or timing are needed — it's triggered by ordinary unauthenticated HTTP responses to attachment requests.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), before inserting `response.attachment` and before calling `report.bump_successful_requests()`, verify `response.attachment.hash() == request.content_hash`; on mismatch, treat it as a failed request (`report.bump_failed_requests()`) and drop the attachment rather than trusting it implicitly.

### Proof of Concept
Not independently exploitable into on-chain data corruption in this codebase revision (the DB key self-derives from content, preventing hash/content DB mismatches), so this is reported as a **partial/uncertain analog**: I could not find an explicit equality check between `request.content_hash` and the hash of received attachment bytes in `extend_with_attachments`, and I was unable to fully trace all downstream consumers of `ReliabilityReport` scores to confirm the full blast radius within the available indexed code. A background Devin session with full repo access should verify whether `report.bump_successful_requests()`/`bump_failed_requests()` gating exists elsewhere (e.g., in `decode_atlas_get_attachment` or a caller not indexed here) before treating this as confirmed.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
