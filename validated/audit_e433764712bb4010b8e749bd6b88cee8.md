### Title
Stale postponed `DeployContract` action receipt survives `DeleteAccount` and re-executes against a recreated account of the same name, overwriting the new owner's contract - ([File: runtime/runtime/src/actions.rs])

### Summary
NEAR postpones an `ActionReceipt` whose `input_data_ids` are not yet satisfied by storing it under `TrieKey::PostponedReceipt{receiver_id, receipt_id}` completely independent of the `Account` trie entry for that `receiver_id`. `action_delete_account` (runtime/runtime/src/actions.rs) never touches `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` state, and neither `check_account_existence` nor `check_actor_permissions` verify that the account currently occupying `receiver_id` is the "same" account that originally created the postponed receipt. An attacker can self-postpone a `DeployContract(evil.wasm)` receipt, delete their account, wait for a third party to recreate the same `account_id` and deploy a legitimate contract, then release the missing `DataReceipt` at will to silently overwrite the victim's contract code.

### Finding Description
- `process_action_receipt` ( [1](#0-0) ) stores an action receipt as a `PostponedReceipt` keyed only by `(receiver_id, receipt_id)` when any `input_data_id` is missing, with no binding to the account's identity/generation/creation height.
- `process_receipt`'s `Data` branch ( [2](#0-1) ) fetches and executes the postponed receipt purely by `receiver_id`/`receipt_id` lookup as soon as the matching `DataReceipt` arrives, with no check on what account currently exists at that `receiver_id`.
- `action_delete_account` lives entirely in `actions.rs`, and that file contains **no references** to `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` (confirmed by search), so deleting an account never purges any postponed receipts still addressed to it.
- `check_account_existence` for `DeployContract` only requires `account.is_some()` ( [3](#0-2) ) — it doesn't care whether this is the "original" account or a freshly recreated one.
- `check_actor_permissions` for `DeployContract` only requires `actor_id == account_id` ( [4](#0-3) ). Because the attacker's postponed receipt is a **self-receipt** (`predecessor_id == receiver_id == account_id`), `actor_id` is trivially equal to `account_id` at receipt-creation time — this is a string-equality check with no reference to keys, block height, or any "generation" of the account.
- `action_deploy_contract` ( [5](#0-4) ) unconditionally overwrites `account.contract` and calls `state_update.set_code`/`record_contract_deploy` once dispatched — it has no way to know the account was deleted and recreated by someone else in between.

**Exploit flow:**
1. Attacker controls `victim.acct` (any name, e.g. one they intend to abandon). They submit a receipt to themselves (`predecessor_id == receiver_id == victim.acct`) containing `DeployContract(evil.wasm)` and an `input_data_ids: [D]` that will never be satisfied unless the attacker chooses to satisfy it (e.g., a promise chain the attacker controls, or simply never fulfilling `D` until they want to). This receipt is stored as a `PostponedReceipt`.
2. Attacker sends `DeleteAccount` on `victim.acct` (self-authorized, passes `actor_id == account_id`, and the account has no locked stake). The account entry disappears, but the postponed receipt and its `PendingDataCount`/`PostponedReceiptId` bookkeeping remain in state, untouched.
3. A third party creates `victim.acct` again (`CreateAccount`), adds their own key, deploys `legit.wasm`, and later receives a deposit.
4. The attacker (who still fully controls when/if the `DataReceipt` for `data_id = D` is emitted) releases it. `process_receipt`'s Data branch finds the still-present `PostponedReceiptId`, decrements `PendingDataCount` to 0, fetches the stale receipt, and executes it via `apply_action_receipt` against the account that now exists at `victim.acct` — silently deploying `evil.wasm` over `legit.wasm`, with no signature or authorization check tied to the new owner at all.

This breaks the audit's stated invariant that "post-state should reflect only actions the new owner authorized" — the new owner never authorized `evil.wasm`.

### Impact Explanation
Contract-code substitution on the recreated account lets the attacker's `evil.wasm` intercept calls and drain any funds subsequently sent to `victim.acct` (e.g., funds deposited by the new owner or by users interacting with what they believe is the legitimate contract) — a direct theft-of-funds scenario, matching the "theft of funds" NEAR bounty category via authorization-escalation/state-divergence from unauthorized code execution.

### Likelihood Explanation
- Fully reachable by an ordinary, unprivileged account: self-sent action receipt + `DeleteAccount`, both are standard transactions any client can submit.
- The attacker fully controls the timing of releasing the dependent `DataReceipt` (it can be held indefinitely across blocks/epochs via a promise chain they control), so they can wait for the account-name to be reused and funded before firing the malicious deploy.
- The only precondition outside attacker control is that a third party reuses the exact deleted account name — a real-world risk (auction/marketplace-style account name reuse, or attacker deliberately advertising/selling the "available" name) but not something the attacker needs cooperation to trigger technically; the attack is purely mechanical once the name is reused.
- Repeatable for any account name the attacker is willing to give up.

### Recommendation
Bind postponed-receipt execution to the identity/generation of the account, e.g.:
- On `DeleteAccount`, either purge all `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`/`ReceivedData` entries keyed to that `account_id`, or
- Disallow deleting an account while it has outstanding postponed receipts (mirroring the existing `!account.locked().is_zero()` staking guard in `check_actor_permissions`'s `DeleteAccount` arm), requiring a maintained per-account "pending receipt count" that must be zero before deletion, or
- Add an account "generation"/incarnation counter that is captured when a receipt is postponed and re-checked (must match the live account's generation) before executing a released postponed receipt in `process_receipt`.

### Proof of Concept
Integration test (apply-path, following the style of `runtime/runtime/src/tests/apply.rs`):
1. Setup `alice` with a signer key and balance.
2. Apply a receipt `R1` = self-receipt (`predecessor_id = receiver_id = alice`) with `input_data_ids: [D]` and `actions: [DeployContract(evil_wasm)]`. Assert `get_postponed_receipt(state, alice, R1).is_some()`.
3. Apply a `DeleteAccount(alice, beneficiary)` self-receipt. Assert `get_account(state, alice) == None` **and** `get_postponed_receipt(state, alice, R1)` is still `Some(...)` (proves no cleanup).
4. Apply `CreateAccount` + `AddKey(new_owner_key)` + `DeployContract(legit_wasm)` receipt from `charlie` recreating `alice`. Assert `get_account(state, alice).contract()` hash equals `legit_wasm` hash.
5. Apply a `DataReceipt{receiver_id: alice, data_id: D, data: Some(vec![])}`. Assert this triggers execution of `R1` (check outcome for `R1`'s receipt id).
6. Assert `get_account(state, alice).contract()` hash now equals `evil_wasm` hash, **not** `legit_wasm` — proving contract substitution with no authorization from `charlie`/new owner.

pub(crate) fn action_deploy_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    deploy_contract: &DeployContractAction,
    config: Arc<VmConfig>,
    next_config: Option<Arc<VmConfig>>,
    cache: Option<&dyn ContractRuntimeCache>,
) -> Result<(), StorageError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_contract").entered();
    clear_account_contract_storage_usage(state_update, account_id, account)?;

    let code = ContractCode::new(deploy_contract.code.clone(), None);
    account.set_storage_usage(
        account.storage_usage().checked_add(code.code().len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(AccountContract::Local(*code.hash())).or_inconsistent_state(account_id)?;
    // Legacy: populate the mapping from `AccountId => sha256(code)` thus making contracts part of
    // The State. For the time being we are also relying on the `TrieUpdate` to actually write the
    // contracts into the storage as part of the commit routine, however no code should be relying
    // that the contracts are written to The State.
    state_update.set_code(account_id.clone(), &code);
    // Precompile the contract under the current `wasm_config`. If a protocol upgrade with a
    // different `wasm_config` is scheduled for the next epoch, also schedule a fire-and-forget
    // warming compile under the new config so the on-disk cache is hot at the boundary.
    // Note: contract compilation costs are already accounted in deploy cost using special logic
    // in estimator (see get_runtime_config() function).
    precompile_contract_with_warming(&code, config, next_config, cache);
    // Inform the `store::contract::Storage` about the new deploy (so that the `get` method can
    // return the contract before the contract is written out to the underlying storage as part of
    // the `TrieUpdate` commit.)
    state_update.record_contract_deploy(code);
    Ok(())
