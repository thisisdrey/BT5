Found the analogous vulnerability. The `ValidateMultiSign` TVM precompile is the java-tron equivalent of the OAuth `client_credentials` scope-ignoring bug: it verifies a permission's signature threshold but never checks that the requested operation (here, the calling smart contract's `validatemultisign` invocation context) matches the permission's `operations` scope bitmap the way every other signature-verification path in the codebase does.

### Title
Scope/Operations Check Bypassed in `ValidateMultiSign` TVM Precompile Allows Restricted Active Permission to Authorize Unrestricted Actions - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Every other permission-verification path in java-tron (`TransactionCapsule.validateSignature`/`checkPermission`, `WalletUtil.checkPermissionOperations`, `TransactionUtil.getTransactionSignWeight`) enforces two things for a non-owner (`permissionId != 0`) permission: (1) the permission type must be `Active`, and (2) the permission's 32-byte `operations` bitmap must have the bit for the specific `ContractType` set, via `checkPermissionOperations`. [1](#0-0) [2](#0-1) 

The `ValidateMultiSign` precompile, however, looks up an account's permission by `permissionId` and validates only the signature weight against `permission.getThreshold()` — it never calls `checkPermissionOperations` and never enforces `permission.getType() == PermissionType.Active`: [3](#0-2) 

### Finding Description
`ValidateMultiSign.execute` recovers signer addresses, sums `TransactionCapsule.getWeight(permission, recoveredAddr)` for each signature, and returns "true" (`dataOne()`) once `totalWeight >= permission.getThreshold()`. It resolves `permission` purely via `account.getPermissionById(permissionId)` with no type check and no operations-scope check: [4](#0-3) 

Contrast this with the canonical pattern used everywhere else that a `permissionId != 0` (i.e., a restricted Active permission, as opposed to the full-power Owner permission with id 0) is consumed for authorization — `TransactionCapsule.checkPermission`, `WalletUtil`/`TransactionUtil`'s `checkPermissionOperations`, and `AccountPermissionUpdateActuator.checkPermission` all gate the permission on its declared `operations` scope bitmap, exactly analogous to how hexpm's OAuth flow is supposed to gate a token on the key's `resource: "read"` qualifier before granting a JWT scope: [5](#0-4) 

Because the precompile's "meaning" of a successful multisig validation is meant to be consumed by arbitrary smart-contract logic (e.g. contracts that gate withdrawals, ownership transfers, or approvals on `validatemultisign` returning `true`), any caller can pass an `address` and a restricted `permissionId` (e.g., an Active permission scoped only to `TransferContract` in its `operations` bitmap, analogous to hexpm's "read-only" key) and the precompile will authorize the check as long as signature weight is met — regardless of what operation the calling contract logic is actually gating. This mirrors the CVE precisely: a narrowly scoped permission ("api:read"/limited `operations` bitmap) gets treated by the consuming logic as if it had the broad "api" scope, because the scope/resource qualifier is silently dropped in this one validation path while it is correctly enforced in all sibling paths.

### Impact Explanation
Any smart contract on TRON that relies on `validatemultisign(address,permissionId,hash,signatures)` to gate a sensitive action (contract upgrades, fund releases, admin operations restricted to specific TRON contract types via `operations`) can be tricked into accepting authorization from a permission that the account owner intended to restrict to a narrow set of operations. An attacker who controls signers meeting only a *limited-scope* Active permission's threshold can produce a valid `true` result from this precompile and use it to unlock functionality the account owner never intended that permission to authorize — an unauthorized account operation enabled by TVM logic that trusts this precompile's scope semantics.

### Likelihood Explanation
Reachable by any unprivileged contract deployer/caller: the precompile is invoked purely via TVM `STATICCALL`/`CALL` to the fixed precompile address with attacker-supplied `address`, `permissionId`, `hash`, and `signatures[]`, requiring no special privilege beyond deploying/calling a contract, and needs only signatures from keys meeting the target permission's threshold (which, per the CVE analog, is treated as "known/obtainable" in the equivalent scenario — the point is the missing scope gate itself, not the signature acquisition difficulty).

### Recommendation
Add the same scope enforcement used in `TransactionCapsule.checkPermission`/`WalletUtil.checkPermissionOperations` to `ValidateMultiSign.execute`: reject non-owner (`permissionId != 0`) permissions whose type is not `Active`, and require the caller to also supply/derive the target `ContractType` so the precompile can verify the relevant `operations` bit is set before returning `dataOne()`. At minimum, document and enforce that `permissionId`s with restricted `operations` cannot be used to satisfy checks equivalent to broader/owner-level authorization, mirroring the fix in `71c127afebb7ed7cc637eb231b98feb802d62999` that made hexpm honor the resource qualifier during scope derivation.

### Proof of Concept
1. Account `A` sets up an Active permission (id=2) with `operations` bitmap restricted to only `TransferContract` (analogous to hexpm's read-only API key), signed by keys `k1`,`k2` with threshold 2, as shown in the existing test fixture: [6](#0-5) 
2. A separate consumer smart contract (deployed by anyone) calls the `validatemultisign` precompile with account `A`'s address, `permissionId=2`, an application-specific `hash`, and signatures from `k1`/`k2` meeting the threshold, intending to gate some unrelated privileged action (e.g., "admin approve") on this call succeeding.
3. `ValidateMultiSign.execute` returns `dataOne()` (`true`) purely based on `totalWeight >= permission.getThreshold()`, exactly as shown in the passing case of `testDifferentCase`: [7](#0-6) 
4. No check is performed that the permission's `operations` bitmap actually authorizes "admin approve"-type actions — the precompile has no notion of the caller's intended operation/contract type at all, unlike `checkPermissionOperations` used elsewhere, so a permission scoped to `TransferContract` alone is treated as authorization for anything the consuming contract chooses to gate on it.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
