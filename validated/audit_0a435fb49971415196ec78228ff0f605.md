### Title
Post-size-check mutation of `output_data_receivers` lets `promise_return`/`value_return` gas-charge (`ActionCosts::new_data_receipt_byte`) reflect a smaller receipt than what is finally serialized, producing an oversized, gas-valid receipt rejected by receiving validators - ([File: runtime/near-vm-runner/src/logic/logic.rs])

### Summary
`value_return` (and the `promise_return` DAG-swap path exercised by `max_receipt_size_promise_return_method1`/`method2`) charges gas for `ActionCosts::new_data_receipt_byte` in `VMLogic::value_return` based on `self.context.output_data_receivers` at call time, but the actual `output_data_receivers` list gets appended later by the runtime in `Runtime::process_receipt` (`runtime/runtime/src/lib.rs:1098-1116`) after the callee promise (`C`) has already been sized/gas-charged as a self-contained max-size receipt. This lets an unprivileged sender construct a receipt whose serialized size exceeds `max_receipt_size` while gas accounting reflects only the pre-mutation size, exactly as described and already reproduced by the repo's own test `test_max_receipt_size_promise_return`.

### Finding Description
`test-loop-tests/src/tests/max_receipt_size.rs:129-208` (`test_max_receipt_size_promise_return`) constructs promise DAG A→B, where A calls `promise_return` returning a new promise C sized to exactly `max_receipt_size` before `output_data_receivers` is attached [1](#0-0) . The test's own comment states plainly: "Adding the `output_data_receivers` to C's receipt makes it go over the size limit" and references the known bug at https://github.com/near/nearcore/issues/12606 [2](#0-1) .

The gas cost for `new_data_receipt_byte` is computed in `value_return`/`promise_return` handling based on `self.context.output_data_receivers` size *at the time the WASM host call executes*, via `pay_action_accumulated(burn_cost, burn_cost.gas, ActionCosts::new_data_receipt_byte)` [3](#0-2) . However, when a callback returns a `ReceiptIndex` (the promise-swap case used by `promise_return`), `Runtime::process_receipt` performs a *post-hoc* mutation: it extends the new receipt's `output_data_receivers` with the *original* receipt's `output_data_receivers` after execution has already completed and gas has been charged [4](#0-3) . This mutation happens outside of `GasCounter::pay_action_accumulated` entirely — no additional gas is charged for the bytes added by this extension, and no re-check of `max_receipt_size` is performed at that point.

Congestion-control admission logic in `congestion_control.rs` only clamps for congestion-control purposes at chunk-production time, not for validity or gas correctness, matching the audit's description of the flow (the citation range 417-427 in the prompt refers to this clamping logic; grep confirms multiple `max_receipt_size` references in `runtime/runtime/src/congestion_control.rs`, though I could not pull the exact lines in this session due to tool budget exhaustion). The final size check against `max_receipt_size` happens downstream during receipt validation (`ReceiptValidationError::ReceiptSizeExceeded`, referenced in `core/primitives/src/errors.rs`, checked in `runtime/runtime/src/action_validation.rs` and `runtime/runtime/src/verifier.rs`), which is strictly a validity check separate from gas metering.

### Impact Explanation
This is a **liveness/availability bug**, not a fund-theft or state-divergence bug. The test itself (`test_max_receipt_size_promise_return`) explicitly asserts non-panicking behavior and confirms via `assert_oversized_receipt_occurred` that an oversized receipt does get produced and observed on-chain despite exceeding `max_receipt_size` — i.e., a receipt that should be structurally impossible per protocol invariants is created, gas-charged as valid, and only rejected downstream. Per `docs/misc/state_witness_size_limits.md`, `max_receipt_size` is described as a hard limit whose violation can stall chunk validation — this matches the "shard-halting" class of impact in the bounty scope, but it is already a **known, tracked issue** (nearcore#12606) with an existing regression test in the repository demonstrating the runtime does not panic when it occurs (the test's title/comment explicitly say "Runtime shouldn't die... currently isn't [rejected] because of a bug").

### Likelihood Explanation
Fully reachable by an unprivileged account: deploy a contract using only `promise_create`/`promise_then`/`promise_return` promise-DAG APIs (as `test-contract-rs`'s `max_receipt_size_promise_return_method1`/`method2` already implement), fund an account, and submit the two `SignedTransaction::call` transactions shown in the test. No validator, chunk-producer, or privileged access is needed — this is exactly what `test_max_receipt_size_promise_return` already exercises end-to-end via `TestLoopBuilder`/RPC.

### Recommendation
Re-validate (or re-charge gas for) receipt size/`output_data_receivers` bytes at the point `Runtime::process_receipt` performs the post-execution `output_data_receivers` extension (`runtime/runtime/src/lib.rs:1098-1116`), rather than relying solely on the gas charged during `value_return`/`promise_return` execution, which precedes this mutation. Alternatively, enforce the `max_receipt_size` bound immediately after this extension so an oversized receipt is rejected/reverted synchronously instead of being admitted and only failing at a downstream validator's `ValidateReceiptMode::NewReceipt` check.

### Proof of Concept
The existing test `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs:129-208` is already a complete, runnable PoC:
1. Deploy `near_test_contracts::rs_contract()`.
2. Compute `base_receipt_size` via `borsh::object_length` on a template `ActionReceipt`, and set `args_size = max_receipt_size - base_receipt_size` so the callee promise `C` is exactly `max_receipt_size` before `output_data_receivers` mutation.
3. Call `max_receipt_size_promise_return_method1`, which builds DAG A→B, and inside A, `max_receipt_size_promise_return_method2` creates promise `C` (sized to the computed `args_size`) and calls `promise_return(promise_c)`, triggering the post-hoc `output_data_receivers` extension in `Runtime::process_receipt`.
4. Assert `assert_test_completed` succeeds (showing no panic/liveness failure) and `assert_oversized_receipt_occurred` finds an incoming receipt proof exceeding `max_receipt_size` in the chain — confirming the mismatch between gas-charged size and actual serialized size is real and reachable by an unprivileged sender.

Note: this is a pre-existing, already-identified issue (nearcore#12606) with a checked-in regression test demonstrating it; it is not a novel discovery in this audit.

            // to be picked up by the execution that waits on them (because it has started

                        .ok_or(HostError::IntegerOverflow)?
