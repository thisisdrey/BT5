I found a concrete analog: `CancelAllUnfreezeV2Actuator` increases an account's TRON Power (via `addFrozenForTronPowerV2`) without withdrawing pending vote rewards first or re-syncing votes, which is exactly the pattern in the LoopFi report — a privileged "reset/restore" style operation that mutates the balance state used by the cached reward-accounting snapshot, without going through the code path that keeps the reward snapshot consistent.

### Title
Increasing TRON Power via `CancelAllUnfreezeV2Actuator` without withdrawing reward first can corrupt/desync the cached vote-reward snapshot - (File: `actuator/src/main/java/org/tron/core/actuator/CancelAllUnfreezeV2Actuator.java`)

### Summary
The reported LoopFi bug is caused by a privileged "reset" function (`manualStopEmissionsFor`) that mutates a user's tracked balance directly, bypassing the normal balance-update path that keeps a cached eligibility/reward-tracking flag (`lastEligibleStatus`) consistent with the real balances across all vaults. In java-tron's TVM vote/reward accounting, the equivalent cached-state invariant is maintained by `MortgageService`/`VoteRewardUtil`: every code path that changes an account's effective TRON Power or votes is expected to call `withdrawReward`/`VoteRewardUtil.withdrawReward` *before* changing power/votes, so the `beginCycle`/`endCycle`/`AccountVote` snapshot in `DelegationStore` correctly reflects the vote weights that were in effect for each cycle.

### Finding Description
`VoteRewardUtil.withdrawReward` (and its TVM-independent counterpart `MortgageService.withdrawReward`) rely on a strict invariant: whenever an account's votes or usable TRON Power changes, `withdrawReward` must be called first so that the reward accrued under the *old* vote/power configuration is settled and a fresh snapshot (`beginCycle`, `endCycle`, `AccountVote`) is recorded before any new state is written. This is enforced consistently by `VoteWitnessActuator.countVoteAccount` [1](#0-0) , `UnfreezeBalanceActuator.execute` [2](#0-1) , and `UnfreezeBalanceV2Actuator.execute` [3](#0-2) , all of which call `mortgageService.withdrawReward(ownerAddress)` before modifying frozen balances or votes.

However, `CancelAllUnfreezeV2Actuator.execute`, which restores TRON Power/energy/bandwidth from the account's pending `unfrozenV2` (cancel-unfreeze) list back into active frozen balance, does **not** call `mortgageService.withdrawReward` at all before calling `updateFrozenInfoAndTotalResourceWeight`, which directly increases `TronPowerFrozenV2Balance` via `accountCapsule.addFrozenForTronPowerV2(...)` [4](#0-3) [5](#0-4) . This mirrors the LoopFi flaw precisely: a privileged/valid user-initiated action mutates the resource weight (analogous to vault balance) that the reward system assumes is frozen between `withdrawReward` calls, but it skips the settlement step. As a result, `DelegationStore`'s stored `AccountVote` snapshot and `beginCycle`/`endCycle` bookkeeping become stale relative to the account's actual TRON Power for the remainder of the current cycle — the reward computation logic in `MortgageService.computeReward`/`VoteRewardUtil` (`chainbase/src/main/java/org/tron/core/service/MortgageService.java:171-230`) will use vote records that no longer correspond to the TRON Power actually backing them once cancel-unfreeze restores power mid-cycle.

### Impact Explanation
Because `withdrawReward` is skipped, the reward that should have accrued under the account's TRON Power/vote configuration prior to the cancel-unfreeze is not properly checkpointed, and the vote records used for later reward computation in the current cycle may not correspond to the actual TRON Power held. This causes either loss of legitimately earned voting rewards for the account (the user's `allowance` under-accrues) or, in edge cases where TRON Power was already exceeded by existing votes, permits a mismatch between voted TRON Power and actual TRON Power without the corrective `clearVotes` logic (as seen in `UnfreezeBalanceProcessor`/`UnfreezeBalanceV2Actuator.updateVote`) ever being triggered, since that corrective logic only runs when `withdrawReward` and the vote-adjustment routine are actually invoked, which they are not here. This is a fund-accounting correctness bug in the DPoS reward system.

### Likelihood Explanation
`CancelAllUnfreezeV2Contract` is a normal, unprivileged user transaction (any account with a pending cancelable unfreeze can call it) once the chain parameter `AllowCancelAllUnfreezeV2` is enabled, so the vulnerable path is directly reachable from any user without special permissions. Any account that has previously unfrozen TRON Power, voted for witnesses, and has a pending cancel-unfreeze entry can trigger this by simply calling cancel-all-unfreeze.

### Recommendation
Add a call to `mortgageService.withdrawReward(ownerAddress)` at the start of `CancelAllUnfreezeV2Actuator.execute`, before `updateAndCalculate`/`updateFrozenInfoAndTotalResourceWeight` modify the account's frozen TRON Power, energy, or bandwidth balances — mirroring the pattern already used in `UnfreezeBalanceActuator` and `UnfreezeBalanceV2Actuator`. This ensures the `DelegationStore` vote/reward snapshot is settled against the TRON Power in effect prior to the restoration, keeping the invariant intact.

### Proof of Concept
1. Account `A` freezes TRON Power and votes for witness `W` with the resulting voting power.
2. Account `A` calls `UnfreezeBalanceV2` (`TRON_POWER`) mid-cycle, which correctly calls `withdrawReward` first, settles reward, and proportionally reduces `A`'s votes via `updateVote`.
3. Before the unfreeze cooldown expires, account `A` calls `CancelAllUnfreezeV2`, restoring the TRON Power back into `frozenV2` via `addFrozenForTronPowerV2` — this executes without any `withdrawReward` call, and without re-adjusting/re-validating votes against the restored TRON Power.
4. The `DelegationStore`'s `beginCycle`/`AccountVote` snapshot recorded at step 2 remains keyed to the reduced TRON Power/vote state, while `A`'s account now has restored TRON Power that was never reconciled with the votes list or reward snapshot for the remainder of the cycle — leading to reward miscalculation (`MortgageService.computeReward`) for that cycle. Concrete quantification of the exact monetary loss requires running the `RewardViCalService`/`MortgageService` cycle logic against this sequence in an integration test, which was not performed here due to the scope of this analog scan.
