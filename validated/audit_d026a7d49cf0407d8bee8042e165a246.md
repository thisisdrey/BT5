### Title
Liquidation permanently reverts when oracle confidence interval widens beyond `oracle_max_confidence`, blocking bad-debt cleanup during high volatility - (File: `programs/marginfi/src/state/price.rs`)

### Summary
Marginfi's `liquidate` instruction fetches asset/liability prices through `PriceAdapter::get_price_of_type`, which internally calls `get_confidence_interval`. If the oracle-reported confidence interval exceeds the bank's configured `oracle_max_confidence` (default 10% if unset), the price-fetch function unconditionally errors out with `OracleMaxConfidenceExceeded` rather than clamping the price and continuing. Because liquidation cannot proceed without a valid price for both the asset and liability bank, any account whose collateral or debt is denominated in a bank hitting this condition becomes permanently un-liquidatable for as long as the oracle confidence stays wide — which is exactly the market condition (high volatility/rapid drawdowns) under which timely liquidation matters most.

### Finding Description
In `programs/marginfi/src/state/price.rs`, both `SwitchboardPullPriceFeed::get_confidence_interval` and `PythPushOraclePriceFeed::get_confidence_interval` implement the same pattern: [1](#0-0)  and [2](#0-1) . If `conf_interval > max_conf` (where `max_conf` is derived from `bank.config.oracle_max_confidence`, defaulting to 10%), the function returns `err!(MarginfiError::OracleMaxConfidenceExceeded)` instead of clamping to a safe maximum and continuing.

This check is invoked unconditionally from `get_price_of_type` whenever a `PriceBias` is supplied, which is exactly how the liquidation path fetches prices: `fetch_asset_price_for_bank_low_bias` (used for the asset bank) and the inline liability-price fetch in `liquidate.rs` both pass `Some(PriceBias::...)` and `bank.config.oracle_max_confidence`: [3](#0-2) . There is a bypass function `get_price_of_type_ignore_conf` that passes `u32::MAX` to skip the check [4](#0-3) , but this is not used anywhere in the liquidation flow.

During a genuine, correctly-reported market crash or volatility spike, Pyth/Switchboard confidence intervals widen (this is legitimate, non-manipulated oracle behavior reflecting real market uncertainty). Once the reported confidence exceeds `oracle_max_confidence`, every attempt to compute `asset_price` or `liab_price` for that bank in `liquidate.rs` reverts with `OracleMaxConfidenceExceeded`, and the transaction fails entirely — no liquidation of that position can occur. This mirrors the OpenLeverage anti-flashloan finding: a price-sanity check intended to reject anomalous/manipulated inputs instead blocks legitimate liquidations during the exact market conditions (fast drawdowns) that make timely liquidation critical, allowing under-collateralized positions to persist and accumulate bad debt.

### Impact Explanation
While confidence remains above the threshold, liquidators cannot close out under-collateralized positions in the affected bank via the normal `liquidate` instruction. If the market continues trending in the borrower's unfavorable direction while confidence stays wide (a plausible multi-block/multi-minute condition during a crash), the position's debt can exceed its collateral value, resulting in bad debt to lenders/depositors — an insolvency condition. This is a protocol-wide accounting risk, not merely a UX inconvenience, since it directly prevents the core mechanism (liquidation) that keeps the lending pool solvent.

### Likelihood Explanation
This triggers under real, non-adversarial market conditions (high volatility) without requiring any privileged action or governance change — any bank using Pyth or Switchboard with a non-permissive `oracle_max_confidence` is exposed whenever the oracle's legitimately reported confidence interval widens past the configured threshold, which is a realistic and recurring market event for volatile collateral types.

### Recommendation
Do not hard-revert when confidence exceeds `oracle_max_confidence` specifically for liquidation-critical price fetches. Instead, either (a) clamp the price/confidence to the configured maximum and proceed (as is already done for the unconditional 5% cap via `MAX_CONF_INTERVAL`), or (b) provide a liquidation-specific fallback (e.g., using TWAP/EMA price or a receivership-style path) so that positions remain liquidatable even when spot confidence is temporarily wide, while still protecting non-liquidation operations (borrow/withdraw) with the stricter check.

### Proof of Concept
1. Bank `X` has `oracle_max_confidence` unset (defaults to 10%, per `U32_MAX_DIV_10` in `get_confidence_interval`).
2. Market volatility spikes; the Pyth/Switchboard feed for `X` legitimately reports a confidence interval > 10% of price.
3. Borrower's position in bank `X` becomes under-collateralized (maint health < 0) as price continues to fall.
4. Liquidator calls `liquidate` with `asset_bank`/`liab_bank` = `X`; inside the accounting block, `fetch_asset_price_for_bank_low_bias` (or the liability-price fetch) calls `get_price_of_type` → `get_confidence_interval`, which returns `err!(MarginfiError::OracleMaxConfidenceExceeded)` per [5](#0-4) .
5. The entire `liquidate` transaction reverts; the position remains open and under-collateralized until confidence narrows, during which further price decline can push the account into bad debt.

    fn get_confidence_interval(&self, oracle_max_confidence: u32) -> MarginfiResult<I80F48> {
        let conf_interval: I80F48 = I80F48::from_num(self.feed.result.std_dev)
            .checked_div(EXP_10_I80F48[switchboard_on_demand::PRECISION as usize])
            .ok_or_else(math_error!())?
            .checked_mul(STD_DEV_MULTIPLE)
            .ok_or_else(math_error!())?;

        let price = self.get_price()?;

        // Fail the price fetch if confidence > price * oracle_max_confidence
        let oracle_max_confidence = if oracle_max_confidence > 0 {
            I80F48::from_num(oracle_max_confidence)
        } else {
            // The default max confidence is 10%
            U32_MAX_DIV_10
        };
        let max_conf = price
            .checked_mul(oracle_max_confidence)
            .ok_or_else(math_error!())?
            .checked_div(U32_MAX)
            .ok_or_else(math_error!())?;
        if conf_interval > max_conf {
            let conf_interval = conf_interval.to_num::<f64>();
            let max_conf = max_conf.to_num::<f64>();
            msg!("conf was {:?}, but max is {:?}", conf_interval, max_conf);
            return err!(MarginfiError::OracleMaxConfidenceExceeded);
        }
