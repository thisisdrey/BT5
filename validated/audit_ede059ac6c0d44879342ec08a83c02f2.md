### Title
Unbounded attacker-controlled offsets in Sapling `VerifyTransferProof` precompile cause out-of-bounds/mis-sized buffer copies - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `VerifyTransferProof` precompiled contract, reachable by any account or contract that performs a `CALL`/`STATICCALL` to the corresponding TVM precompile address with Shielded TRC20 verify-transfer calldata, only validates the *total* length of its `data` argument against a small fixed set of allowed sizes. It then reads three offset fields (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) directly out of attacker-supplied `data` and uses them, unvalidated, as `System.arraycopy` source offsets for subsequent field extraction, similar to how ClamAV's `.tar` parser trusted an internal length/checksum field without confirming it stayed within the buffer, causing an over-read.

### Finding Description
`VerifyTransferProof.execute` in `PrecompiledContracts.java` checks only that `data.length` matches one of the four permitted total sizes (`SIZE = {2080, 2368, 2464, 2752}`): [1](#0-0) 

It then parses three offset values straight from attacker-controlled bytes and immediately uses them as array indices/`arraycopy` source positions without checking they are within `[0, data.length]`, nor that the derived ranges (`spendOffset + 320*i + 128`, etc.) stay inside the buffer: [2](#0-1) 

The counts derived from these offsets (`spendCount`, `spendAuthSigCount`, `receiveCount`) are bounded to 1–2, but that check happens only *after* `parseInt(data, spendOffset)` etc. has already read from the attacker-chosen offset, and the offset itself is never range-checked against `data.length`. Because `spendOffset`/`spendAuthSigOffset`/`receiveOffset` are fully attacker-controlled 32-bit values taken from the first 96 bytes of `data`, a caller can set them to any value (including negative-after-cast or larger-than-buffer values), producing an `ArrayIndexOutOfBoundsException` deep inside `System.arraycopy`, or in the best case walking far outside the intended fields to copy unrelated adjacent memory content of the `data` array into the fields subsequently fed to the native Sapling verification routines (`librustzcashSaplingCheckSpend`/`CheckOutput`/`FinalCheck`) invoked through `JLibrustzcash`. This mirrors the ClamAV analog: an internally-declared length/offset value is trusted to index into a buffer without bounds validation, leading to an over-read condition.

The comparable `VerifyMintProof.execute` in the same file enforces `data.length != SIZE` for an *exact* fixed length, so all its `arraycopy` offsets are compile-time constants and safe: [3](#0-2) 
`VerifyTransferProof` is the outlier because it supports 4 possible sizes and therefore needs *variable* offsets, which introduces the unchecked dynamic indexing.

### Impact Explanation
An unauthenticated/unprivileged transaction sender who can invoke this precompile from a smart contract (e.g. through a Solidity `staticcall`/`call` to the Sapling-transfer-verify precompile address used by Shielded TRC20 support) can supply malformed offset fields to trigger an unhandled `ArrayIndexOutOfBoundsException`. All exceptions in `execute()` are caught by a generic `catch (Throwable any)` in similar sibling methods, but here there is no such catch around the parsing block before the `try` that wraps the JNI calls — the offset parsing and `arraycopy` calls occur inside the method body's `try` block that only ends at line ~1600, so `ArrayIndexOutOfBoundsException` would propagate up through TVM execution. If not properly absorbed by the VM's opcode-level exception handling, this could crash energy accounting / transaction execution for the node processing the block, representing a potential node-crash / DoS vector triggered by a single crafted transaction reaching a public precompile — the class of impact explicitly in scope (node crash / halt).

### Likelihood Explanation
Reaching this code only requires deploying or calling a contract that issues a `CALL`/`STATICCALL` to the Sapling verify-transfer precompile address with 2080/2368/2464/2752-byte calldata containing attacker-chosen offset words — this is directly reachable by any unprivileged contract deployer/caller with no special permissions, matching the CVE's "any file sent to the scanner" trigger model.

### Recommendation
Before using `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and before every subsequent `parseInt`/`arraycopy` that depends on them), validate that each offset is non-negative and that the offset plus its maximum required read length (including per-iteration terms `320*spendCount`, `64*spendCount`, `288*receiveCount`, etc.) does not exceed `data.length`, returning the default `(true, DataWord.ZERO().getData())` failure result instead of allowing an unchecked `arraycopy`/`parseInt` to run. Adding an explicit bounds check mirrors the fix ClamAV applied for CVE-2017-12378 (validating declared length before use).

### Proof of Concept
1. Construct calldata of exactly `SIZE[0] = 2080` bytes (one of the accepted sizes).
2. Set the first 32-byte word (`spendOffset`) to an arbitrary large value, e.g. `0x00000000000000000000000000000000000000000000000000000000000FFF` (4095), which is larger than `data.length` (2080).
3. Deploy a simple contract that performs `staticcall`/`call` to the Sapling verify-transfer precompile address with this calldata.
4. Broadcast a transaction invoking that contract function; `parseInt(data, spendOffset)` (or the subsequent `System.arraycopy(data, spendOffset + 320*i, ...)`) reads/writes past `data.length`, throwing `ArrayIndexOutOfBoundsException` inside `VerifyTransferProof.execute`, uncaught before the method's own `try`/exception-swallowing boundaries at the top of the parsing block.
