## Title
Active-Permission Delegation of `AccountPermissionUpdateContract` Enables Full Account Takeover via a Single Low-Privilege Key - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
TRON's multi-sig permission model allows an account owner to delegate the ability to broadcast `AccountPermissionUpdateContract` to a low-privilege "Active" permission via its operations bitmap. Because `AccountPermissionUpdateActuator.execute()` blindly overwrites the account's Owner, Witness, and Active permissions with whatever is supplied in the contract — with no additional check tying this sensitive rewrite capability to the highest-privilege (Owner, `permissionId == 0`) key — any signer who satisfies the threshold of that delegated Active permission can unilaterally seize full control of the account, exactly mirroring the `Trust.sol` "blanket authority" flaw described in the external report: a single compromised lower-privilege trusted key can lock out all legitimate owners.

### Finding Description
The permission model is defined by `Permission` protobuf messages with `PermissionType` `Owner`, `Witness`, and `Active`. Sensitive contracts (including `AccountPermissionUpdateContract` itself) can be enabled for an Active permission through its 32-byte `operations` bitmap, validated in `checkPermission`: [1](#0-0) 

Signature/permission enforcement for a broadcast transaction only checks that the permission referenced by `contract.getPermissionId()` is of type `Active` and that the target contract type's bit is set in that permission's `operations` — it performs no special-casing for `AccountPermissionUpdateContract` requiring the Owner permission: [2](#0-1) 

Once threshold weight is met for that (potentially low-weight, single-key) Active permission, `AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's Owner, Witness, and Active permission set with the caller-supplied values: [3](#0-2) 

`validate()` only checks structural validity of the new permission set (weights, thresholds, address distinctness, operations bitmap) — it never verifies that the *signer* holds the account's Owner permission before permitting this account-wide takeover: [4](#0-3) 

This is the direct on-chain analog of the `Trust.sol` issue: instead of a flat "any trusted account has root" model, TRON's design still allows an operator to grant a day-to-day, lower-privilege signing key ("Active") the same god-mode capability as the account's Owner key — rewriting all permissions including Owner itself — with no additional friction. If that Active key is compromised (the same EOA-compromise scenario the report highlights for `deployer`/`Dev`-style operational keys), the attacker can replace the Owner permission with an attacker-controlled key/threshold, permanently locking out the legitimate owner and all other Active/Witness key holders in a single transaction.

### Impact Explanation
Successful exploitation results in permanent, unrecoverable account takeover: the attacker becomes the sole Owner of the account, and the legitimate owner (and any co-signers) are locked out with no recourse (no "recovery" path exists outside submitting a further `AccountPermissionUpdateContract` signed by the new attacker-controlled Owner permission). Depending on the compromised account (e.g., an exchange hot-wallet operational key, a contract deployer's operational key, or a DAO-style multisig configured this way), this can lead to theft of funds and total loss of control of the account, matching the "unauthorized account operation" and "theft/permanent freezing of funds" impact classes.

### Likelihood Explanation
Exploitation requires that the victim account's owner previously delegated `AccountPermissionUpdateContract` into an Active permission's operations bitmap — a configuration choice, not a default. However, this is precisely the pattern the original report warns against: operational/low-privilege keys (EOAs) being trusted with capabilities that should be reserved for a secure multisig root. Wallets, exchanges, or protocols that set up "broad" or "all-operations" Active permissions for convenience (a common multisig UX pattern) are directly exposed. Given TRON's own documentation/tooling exposes this bitmap as a general-purpose feature without warning against including `AccountPermissionUpdateContract`, and that it is reachable purely via a single signed transaction from an already-obtained Active key, likelihood is realistic for any deployment following the exact operational pattern the bug report is concerned about.

### Recommendation
Treat `AccountPermissionUpdateContract` as an Owner-only operation at the protocol level: reject the contract type bit for `AccountPermissionUpdateContract` when validating an Active permission's `operations` bitmap in `checkPermission` (and correspondingly in `getAvailableContractType`), or explicitly require `permissionId == 0` (Owner) in `AccountPermissionUpdateActuator.validate()`/`TransactionCapsule.checkPermission` regardless of what the Active permission's operations allow. This closes the ability for any delegated Active key to silently escalate to full account control.

### Proof of Concept
1. Account owner configures an Active permission (e.g., `id=2`, `threshold=1`, single key `K`) with an `operations` bitmap that includes the bit for `AccountPermissionUpdateContract` (allowed today because `checkPermission`/`getAvailableContractType` place no special restriction on this type — see lines 137–144 cited above).
2. Attacker compromises key `K` (the same low-privilege EOA-compromise scenario cited in the report).
3. Attacker crafts a `Transaction` whose `Contract.permission_id = 2`, containing an `AccountPermissionUpdateContract` that sets:
   - `owner` = a brand-new Owner permission containing only the attacker's key with `threshold=1`
   - `actives` = a new Active permission set containing only attacker keys
4. Attacker signs with `K` (satisfies the Active permission's threshold of 1) and broadcasts.
5. `TransactionCapsule.checkPermission`/`AccountPermissionUpdateActuator.validate()` pass because `permission.getType() == Active` and the operations bit is set; `execute()` then overwrites the account's Owner/Active permissions per `AccountCapsule.updatePermissions`, permanently locking out the original owner and all other keys.

  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
