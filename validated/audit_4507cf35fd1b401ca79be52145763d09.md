### Title
Unprivileged attacker can DoS any account's deposits/borrows/claims by filling `MAX_TOKENS_PER_USER` slot list via dust `DepositToken.transfer` - (File: contracts/Pool.sol)

### Summary
`Pool` tracks a per-account set of deposit and debt tokens and enforces a hard cap of `MAX_TOKENS_PER_USER = 30`. Any first-time positive `DepositToken` balance unconditionally calls `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined deposit+debt token count reaches the cap. Because `DepositToken.transfer`/`seize` are callable by anyone on their own unlocked balance, an unprivileged attacker can dust-transfer one wei of every supported deposit token into a victim, filling the victim's list. Afterwards the victim's `deposit()` into any new collateral, `DebtToken` `_mint` (i.e. `issue`) of a new synthetic, and any receipt of new deposit tokens all revert, temporarily freezing their ability to open positions — the Metronome analog of the InnoDB hang/crash DoS in CVE-2025-21559.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (30) and is applied to both `addToDebtTokensOfAccount` (Pool.sol:143-148, 204) and `addToDepositTokensOfAccount` (Pool.sol:216).
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was zero and `amount_ > 0` (DepositToken.sol:517-520). `transfer` only requires the sender's balance to be unlocked via `_revertIfLocked` (DepositToken.sol:348-353), so the attacker needs no permission from the victim.
- The same revert propagates into `DepositToken._mint` (DepositToken.sol:486-488) — blocking `deposit()` on a new collateral — and into `DebtToken._mint` → `pool.addToDebtTokensOfAccount` (DebtToken.sol:597-600) — blocking `issue`/`mint` of any synthetic the victim doesn't already hold.
- Attack cost: attacker makes one minimal `deposit()` per collateral type (up to 30 tokens across the deployed registries, e.g. msdMET, msdETH, msdBTC, etc.) and calls `transfer(victim, 1)` on each `DepositToken`. No health check, approval, or minimum amount stops this; the transfer path is `nonReentrant` only on `transferFrom` and the revert occurs after state changes anyway.
- Recovery exists (victim can transfer each dust balance out to zero their balance, triggering `removeFromDepositTokensOfAccount`), so impact is temporary freezing of position-management functions rather than permanent loss — matching the accepted "temporary freezing of funds" impact class and the CVE's DoS (crash/hang) semantics.

### Impact Explanation
While the victim's list is saturated:
- `deposit()` into any collateral they don't already hold reverts (`UserReachedMaxTokens`), so they cannot add collateral to improve health — if their position is near liquidation, they are denied the ability to rescue it and will be liquidated.
- `DebtToken._mint` reverts for any synthetic they don't already hold, blocking all new borrows/`issue`, `SmartFarmingManager.leverage` for new debt tokens, and any liquidator/`seize` path that would add a new token to them.
- Rewards distribution hooks (`updateBeforeMintOrBurn`/`updateBeforeTransfer`) still run, but claims tied to mint/burn of new tokens are unreachable.

The invariant broken is liveness of account-level token additions: the cap intended as a gas bound becomes an externally fillable resource, letting a third party dictate which operations a victim may perform.

### Likelihood Explanation
Requires only an unprivileged EOA holding dust amounts of each whitelisted underlying. No privileged role, oracle manipulation, or cross-chain component is needed. The only mitigation is that the set of deposit tokens is governor-whitelisted, so cost scales with the number of listed collaterals; on pools with ≥30 listed tokens combined it is trivially reachable, and even fewer suffice if the victim already holds tokens. Dust amounts make the collateral cost negligible.

### Recommendation
- Do not revert user-facing actions on the cap; instead silently skip adding low-value/dust entries, or make `addTo*TokensOfAccount` return a bool and let `_mint`/`_transfer` proceed.
- Alternatively track deposit/debt membership lazily (compute on the fly from global token lists) or enforce a minimum balance threshold for list membership.
- Optionally allow `removeFrom*TokensOfAccount` to be callable by the account itself so victims have a single-transaction recovery.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Fork test: fill victim's depositTokensOfAccount to MAX_TOKENS_PER_USER
// using dust transfers, then show victim's deposit/issue on a new token reverts.

import "forge-std/Test.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IDebtToken} from "../contracts/interfaces/IDebtToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefTest is Test {
    IPool pool = IPool(POOL_ADDR);          // deployed Pool proxy
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    function test_dustFillBlocksVictim() public {
        address[] memory depTokens = pool.getDepositTokens();
        uint256 n = depTokens.length;

        // 1) Attacker deposits minimum and dust-transfers 1 wei of every
        //    deposit token to the victim until the combined list hits 30.
        vm.startPrank(attacker);
        uint256 filled;
        for (uint256 i; i < n && filled < 30; ++i) {
            IDepositToken dToken = IDepositToken(depTokens[i]);
            IERC20 underlying = dToken.underlying();
            deal(address(underlying), attacker, 1); // dust
            underlying.approve(address(dToken), 1);
            try dToken.deposit(1, attacker) returns (uint256 minted) {
                if (minted > 0) {
                    dToken.transfer(victim, minted); // adds entry for victim
                    ++filled;
                }
            } catch {}
        }
        vm.stopPrank();

        assertEq(pool.getDepositTokensOfAccount(victim).length, filled);

        // 2) Victim cannot deposit into any NEW collateral type:
        //    _mint -> addToDepositTokensOfAccount -> UserReachedMaxTokens
        //    (assuming victim held no tokens before; combined count == 30).
        address newCollateral = depTokens[0]; // any token victim has 0 of
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        IDepositToken(newCollateral).deposit(1, victim);

        // 3) Victim cannot issue a synthetic they don't already have debt in:
        //    DebtToken._mint -> addToDebtTokensOfAccount -> UserReachedMaxTokens
        address[] memory debtTokens = pool.getDebtTokens();
        vm.prank(victim);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        IDebtToken(debtTokens[0]).issue(1, victim);
    }
}
```

Steps: attacker `deposit(1)` + `transfer(victim, minted)` per whitelisted `DepositToken`; victim's `deposit`/`issue` on any new token then revert in `Pool.onlyIfAdditionWillNotReachMaxTokens` (Pool.sol:143-148), demonstrating the repeatable, unprivileged temporary freeze.
