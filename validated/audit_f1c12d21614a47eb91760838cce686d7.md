### Title
Unpaginated Asset-Issue query APIs allow anonymous API DoS - (File: framework/src/main/java/org/tron/core/Wallet.java)

### Summary
The GitLab advisory describes a DOS from an unpaginated dependencies API that lets an attacker force the server to build and serialize an unbounded result set. java-tron has an analogous unbounded query pattern: `Wallet.getAssetIssueList()`, `Wallet.getAssetIssueListByName()`, and `Wallet.getAssetIssueByAccount()` load **every** asset-issue record from the store (`getAllAssetIssues()`) into memory and serialize the entire list into the response, with no offset/limit and no cap, even though a paginated sibling API (`getAssetIssueList(offset, limit)`/`GetPaginatedAssetIssueList`) already exists in the same codebase for the exact same data.

### Finding Description
`Wallet.getAssetIssueList()` [1](#0-0)  calls `AssetIssueStore.getAllAssetIssues()` [2](#0-1) , which iterates the full asset-issue column family and returns every entry with no size limit. The same unbounded pattern is used by `getAssetIssueByAccount` [3](#0-2)  and `getAssetIssueListByName` [4](#0-3) , all of which stream `getAllAssetIssues()` and then filter/annotate every result in-process, i.e., the O(n) cost is paid regardless of the filter, before any subset is returned.

These are reachable by any anonymous API client through:
- gRPC `Wallet.GetAssetIssueList` (and `GetAssetIssueByAccount`, `GetAssetIssueListByName`) exposed in `RpcApiService`, confirmed to call `wallet.getAssetIssueList()`/`getAssetIssueByAccount` directly (3 call sites in `RpcApiService.java`).
- HTTP `/wallet/getassetissuelist` via `GetAssetIssueListServlet` and `/wallet/getassetissuebyaccount` via `GetAssetIssueByAccountServlet`, both of which call the unpaginated wallet methods.
- `/wallet/getassetissuelistbyname` via `GetAssetIssueListByNameServlet` [5](#0-4) .

By contrast, the codebase clearly demonstrates the correct, bounded pattern elsewhere: `AssetIssueStore.getAssetIssuesPaginated()` caps `limit` at `ASSET_ISSUE_COUNT_LIMIT_MAX` [6](#0-5) , and block-range APIs enforce a hard `BLOCK_LIMIT_NUM` cap (`GetBlockByLimitNext`) [7](#0-6) , and `getPaginatedProposalList` caps result size at `PROPOSAL_COUNT_LIMIT_MAX` [8](#0-7) . The three asset-issue endpoints above were never updated to use this same bound, leaving an unpaginated, unauthenticated read path that scales linearly with the total number of assets ever issued on the network (a value that only grows over time and cannot shrink).

### Impact Explanation
Any anonymous client can repeatedly call these endpoints (HTTP or gRPC, on any full node, solidity node, or PBFT node since the solidity/PBFT variants delegate to the same store logic) to force full-store scans, object construction, and JSON/protobuf serialization of the complete asset-issue set on every request. As the number of issued TRC10 assets on mainnet grows, the cost per request grows unboundedly, allowing a low-cost, repeated-request DOS against node CPU/memory/bandwidth — degrading or crashing the API service and, if resource exhaustion affects the shared node process, potentially the whole node (matching the "API the node can no longer serve" acceptance criterion).

### Likelihood Explanation
High likelihood: these endpoints are unauthenticated, require no special role or fee, and are part of the standard public Wallet HTTP/gRPC API that java-tron documents for developers. No signed transaction or stake is needed — a single unauthenticated GET/POST/gRPC call triggers the full scan, and it can be trivially automated/parallelized.

### Recommendation
Apply the same bounding already used elsewhere in the codebase:
- Route `getAssetIssueList()`, `getAssetIssueByAccount()`, and `getAssetIssueListByName()` through `AssetIssueStore.getAssetIssuesPaginated()` (or add offset/limit parameters, capped at `ASSET_ISSUE_COUNT_LIMIT_MAX`), analogous to `getPaginatedAssetIssueList`.
- Deprecate/rate-limit the unbounded variants, or enforce a hard cap on results returned/entries scanned per call.
- Add per-IP/per-key rate limiting on these read-only wallet endpoints if not already enforced by `RateLimiterServlet` at a level sufficient to prevent abuse of expensive full-scan queries.

### Proof of Concept
1. Deploy or connect to a full node exposing the default Wallet HTTP API (port 8090).
2. As an anonymous client, repeatedly send:
   `curl -X POST http://<node>:8090/wallet/getassetissuelist`
   or the gRPC `Wallet/GetAssetIssueList` call with an `EmptyMessage`.
3. Each call triggers `AssetIssueStore.getAllAssetIssues()` scanning the entire asset-issue store and serializing every record with no offset/limit — observe CPU/memory/latency degradation proportional to the total number of assets ever issued, and demonstrate degraded responsiveness under repeated concurrent requests.

  private List<AssetIssueCapsule> getAssetIssuesPaginated(List<AssetIssueCapsule> assetIssueList,
      long offset, long limit) {
    if (limit < 0 || offset < 0) {
      return null;
    }

    if (assetIssueList.size() <= offset) {
      return null;
    }
    assetIssueList.sort((o1, o2) -> {
      if (o1.getName() != o2.getName()) {
        return o1.getName().toStringUtf8().compareTo(o2.getName().toStringUtf8());
      }
      return Long.compare(o1.getOrder(), o2.getOrder());
    });
    limit = limit > ASSET_ISSUE_COUNT_LIMIT_MAX ? ASSET_ISSUE_COUNT_LIMIT_MAX : limit;
    long end = offset + limit;
    end = end > assetIssueList.size() ? assetIssueList.size() : end;
    return assetIssueList.subList((int) offset, (int) end);
  }
