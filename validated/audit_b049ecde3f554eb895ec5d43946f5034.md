### Title
Attacker can fill a victim's per-account token list with dust deposits/transfers, permanently hitting `MAX_TOKENS_PER_USER` and DoS-ing new collateral deposits and debt issuance - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a hard cap of `MAX_TOKENS_PER_USER = 30` on the combined `depositTokensOfAccount` + `debtTokensOfAccount` sets [1](#0-0) . Entries are added automatically whenever an account's balance of a listed `DepositToken` goes from 0 to positive — via `_mint` during `deposit`, via `_transfer` on `transfer`/`transferFrom`, and via `seize` during liquidation [2](#0-1) . Because `deposit(amount_, onBehalfOf_)` lets anyone mint `msdTOKEN` to an arbitrary `onBehalfOf_` address [3](#0-2) , an unprivileged attacker can force entries into a victim's list until `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` [4](#0-3) .

### Finding Description
The bug class of CVE-2016-9823 is "crafted input causes a crash/DoS". The on-chain analog: crafted dust inputs (1-wei deposits/transfers of every whitelisted deposit token) force `addToDepositTokensOfAccount(victim)` calls that fill the victim's enumerable set to the 30-token cap. Thereafter:

- `DepositToken._mint` → `pool.addToDepositTokensOfAccount(victim)` reverts `UserReachedMaxTokens`, so the victim cannot deposit any *new* collateral type (including to restore health before liquidation).
- `DebtToken.issue`/`mint` paths that call `addToDebtTokensOfAccount(victim)` revert, so the victim cannot mint any synth whose debt token they don't already hold.
- `DepositToken.seize` during `Pool.liquidate` calls `_transfer(account_, liquidator, ...)` which calls `addToDepositTokensOfAccount(liquidator)` [5](#0-4)  — a liquidator whose own list is full cannot seize a collateral type they don't already hold, so `liquidate` reverts and the position cannot be liquidated through that collateral.

Removal only happens when a balance returns to exactly 0 (`removeFromDepositTokensOfAccount`) [6](#0-5) . The victim can only eject the dust by transferring it out, which requires `unlockedBalanceOf > 0`; when the victim's position is unhealthy (`_issuableInUsd == 0`), `unlockedBalanceOf` returns 0 [7](#0-6) , so the dust is locked and the victim cannot clear a slot precisely when they most need to deposit a new collateral type.

### Impact Explanation
Denial of service of core protocol functions for a targeted account: deposits of new collateral types, issuance of new synth debt, and seizure of non-held collateral types during liquidation all revert unconditionally. An attacker can dust-fill an account that is drifting toward unhealthy, blocking the victim's only self-help path (adding collateral), forcing liquidation and the associated liquidation-incentive loss. This maps to the accepted impact of temporary freezing of funds / liveness failure caused by crafted input.

### Likelihood Explanation
Fully permissionless: `deposit(amount_, onBehalfOf_)` has no beneficiary opt-in or minimum amount, and `transfer` of msdTokens requires no approval from the recipient. Cost is bounded by acquiring dust amounts (or even zero-cost fee-on-transfer-style minting when `depositFee == 0`) across the whitelisted deposit tokens of one pool — a finite, one-time set (pools have a limited number of deposit tokens; 30 total slots counting both lists). No privileged role, oracle manipulation, or governance action is required.

### Recommendation
- Add a beneficiary opt-in (or `onlyIfSmartFarmingManager`/self-only restriction) to `deposit(..., onBehalfOf_)` for tokens the account doesn't already hold, or let accounts pull-claim instead of push-mint.
- Alternatively, make the cap per-list rather than combined, and/or ignore dust entries below a minimum meaningful balance when enforcing `MAX_TOKENS_PER_USER`.
- Allow an account to forcibly remove a deposit-token entry (e.g., `sweep`/`removeFromDepositTokensOfAccount` callable by the account itself when balance is below a dust threshold).

### Proof of Concept
Hardhat fork sketch (pattern mirrors `test/Pool.test.ts:1386-1416`):

```ts
// attacker fills victim's account token list to MAX_TOKENS_PER_USER
const depositTokens = await pool.getDepositTokens(); // all whitelisted msdTOKENs
for (const dt of depositTokens.slice(0, 30)) {
  const token = await ethers.getContractAt('DepositToken', dt);
  const underlying = await ethers.getContractAt('IERC20', await token.underlying());
  await underlying.connect(attacker).approve(token.address, ethers.constants.MaxUint256);
  // mint 1 wei of msdTOKEN to the victim — no opt-in required
  await token.connect(attacker).deposit(1, victim.address); // adds dt to depositTokensOfAccount[victim]
}

// victim now cannot deposit a collateral type it doesn't already hold
const newToken = await ethers.getContractAt('DepositToken', depositTokens[30]);
await expect(
  newToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// if victim is unhealthy (issuableInUsd == 0), dust cannot be transferred out:
// unlockedBalanceOf(victim) == 0 -> NotEnoughFreeBalance, so the block persists
// until debt is repaid or the account is liquidated.
```

The revert propagates through `DepositToken._mint` → `pool.addToDepositTokensOfAccount` at `contracts/Pool.sol:216-220` and `contracts/DepositToken.sol:486-488`, and identically blocks `DebtToken` issuance via `addToDebtTokensOfAccount` at `contracts/Pool.sol:204-208`.
