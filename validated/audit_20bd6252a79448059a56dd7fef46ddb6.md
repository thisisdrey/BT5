### Title
Bridged-in supply accounting is not decreased when bridged synths are burned via Pool/DebtToken paths, permanently consuming the bridge-in cap and freezing inbound transfers - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
`SyntheticToken._burn` only updates the `totalBridgedOut` counter when the caller is the `ProxyOFT` bridge. When bridged-in tokens are burned through any other authorized path — debt repayment (`DebtToken.repay`/`repayAll`), liquidations, or `Pool.swap` — the tokens leave circulation but `totalBridgedIn` is never decremented. `bridgedInSupply()` therefore overstates the circulating bridged supply, permanently consuming `maxBridgedInSupply` headroom. An attacker can deliberately burn bridged-in synths to exhaust the cap, causing all subsequent inbound bridge transfers to revert with `SurpassMaxBridgingSupply` and freezing users' bridged funds in the LayerZero message store.

### Finding Description
In `SyntheticToken._burn`, the bridged-supply counters are updated solely based on `msg.sender` identity:

```solidity
// contracts/SyntheticToken.sol
function _burn(address account_, uint256 amount_) private {
    ...
    if (_isMsgSenderProxyOFT(_msgSender)) {
        totalBridgedOut += amount_;
        if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
    } else if (_isMsgSenderAmo(_msgSender)) {
        amoSupply -= amount_;
    }
    ...
    totalSupply -= amount_;
}
```

Mirroring this, `_mint` increments `totalBridgedIn` only when the caller is `ProxyOFT`. However, tokens minted via `ProxyOFT._creditTo` (which calls `syntheticToken.mint`, incrementing `totalBridgedIn`) are plain synths that can later be burned by other whitelisted callers: `onlyIfCanBurn` also permits any registered Pool and DebtToken. When a user repays debt with bridged-in tokens, `DebtToken.repay` calls `syntheticToken.burn(_msgSender, _repaid)` where `msg.sender` is the DebtToken, so neither counter is adjusted while `totalSupply` decreases.

The invariant `totalBridgedIn - totalBridgedOut == net bridged tokens circulating on this chain` breaks: `bridgedInSupply()` permanently overstates it. Each bridged-in token that is repaid/swapped/liquidated locally consumes `maxBridgedInSupply` cap forever. Once `bridgedInSupply() > maxBridgedInSupply`, `ProxyOFT._creditTo` → `syntheticToken.mint` reverts for every inbound LayerZero message.

### Impact Explanation
Permanent accounting inflation of `bridgedInSupply` leads to denial of inbound bridging: legitimate users who burn synths on a source chain have their destination-chain mint revert, leaving their funds stuck as failed LayerZero messages. Recovery requires either the governor raising `maxBridgedInSupply` or someone bridging out to inflate `totalBridgedOut` — i.e., temporary freezing of user funds and persistent degradation of bridge capacity. This mirrors the reported bug class: a tracked balance (`bucket.collateral` / `totalBridgedIn`) is not decreased on withdrawal/burn, corrupting all downstream cap/price accounting.

### Likelihood Explanation
Fully reachable by an unprivileged attacker on deployed configuration:
1. Bridge X synths into the chain via `ProxyOFT.sendFrom` (or obtain bridged-in tokens on the market — the attacker only needs tokens whose mint incremented `totalBridgedIn`).
2. Deposit any collateral, issue debt, and call `DebtToken.repay` (or `Pool.swap` burning the synth) so the bridged-in tokens are burned with `msg.sender = DebtToken/Pool` — `totalBridgedIn` is not reduced.
3. Repeat (or use flash-issued leverage via `SmartFarmingManager`) to push `bridgedInSupply()` above `maxBridgedInSupply`.

No privileged actor is needed; `revert SurpassMaxBridgingSupply()` then blocks every subsequent inbound bridge message. Note the symmetric path exists on the out side in principle, but the exploitable direction is the inbound cap since `totalBridgedIn` is the counter inflated.

### Recommendation
Decrement `totalBridgedIn` (saturating at 0) whenever tokens are burned by non-ProxyOFT burners while `bridgedInSupply() > 0`, or track bridged supply by origin rather than by caller — e.g., in `_burn`, do `totalBridgedIn = totalBridgedIn > amount_ ? totalBridgedIn - amount_ : 0` for Pool/DebtToken burns, capped so it cannot underflow `totalBridgedOut` semantics. Alternatively, reconcile counters via `bridgedInSupply`/`bridgedOutSupply` netting inside `_burn`.

### Proof of Concept
Hardhat/Foundry sketch (deployment uses the real `Pool`, `DebtToken`, `SyntheticToken`, `ProxyOFT` stack):

```solidity
// Assume maxBridgedInSupply = 1_000e18, attacker already holds 600e18 bridged-in msUSD
// (minted to them by ProxyOFT._creditTo, so totalBridgedIn = 600e18)

// 1. Deposit collateral, issue debt
depositToken.deposit(collateralAmount, attacker);
debtToken.issue(600e18, attacker);            // attacker holds msUSD + debt

// 2. Repay using the bridged-in tokens — burn via DebtToken path
debtToken.repay(attacker, 600e18);
// totalSupply decreased, but totalBridgedIn still 600e18  <-- BUG

// 3. Repeat bridge-in + repay until bridgedInSupply() == maxBridgedInSupply

// 4. Victim bridges 100e18 from another chain; lzReceive -> _creditTo -> mint
vm.prank(lzEndpoint);
proxyOFT.retryOFTReceived(srcChainId, srcAddress, nonce, payload);
// reverts with SurpassMaxBridgingSupply — victim funds stuck in failed-message store
```

Assert: `syntheticToken.bridgedInSupply()` unchanged after `repay` while `totalSupply` dropped, and subsequent `_creditTo` reverts once `bridgedInSupply() > maxBridgedInSupply`.

*Caveat: I was unable to fully verify `Pool.swap`'s burn path and deployed `maxBridgedInSupply` values within the available iterations; the core accounting flaw in `SyntheticToken._burn` is confirmed directly from source.*
