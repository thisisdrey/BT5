### Title
Legacy (non-hardened) Exchange Pool Math Allows Unbacked Token Debt With No Solvency Check or Repayment Mechanism - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
This is analogous to the Insure-DAO finding: when a market/pool becomes insolvent (pays out more than it holds), the protocol has no mechanism to guarantee the resulting shortfall is ever backed or repaid — it just silently persists as a bad debt state. In java-tron's Bancor-style TRX/TRC10 `Exchange` pools, the legacy (`hardenedCalc == false`) code path computes swap output using floating-point double math and writes the new pool balances with **no invariant check that the balances remain non-negative or that outflow ≤ reserve**. The solvency check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) only runs when `hardenedCalc` is `true`, and that mode is gated behind the `allowHardenExchangeCalculation()` proposal flag, so on any deployment where that committee proposal hasn't been activated, every `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` call uses the unchecked legacy path.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on `hardenedCalc`: [1](#0-0) 

The negative-balance guard is only enforced for the hardened path:
```
if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
  throw new ContractValidateException(...);
}
```
For the default legacy path, `ExchangeProcessor.exchangeFromSupply()`/`exchangeToSupply()` use `double` arithmetic and `Maths.pow`, casting the result to `long`: [2](#0-1) 

Whether hardened math is used at all is controlled by a dynamic property that must be enabled through governance: [3](#0-2) 

`ExchangeTransactionActuator` and `ExchangeWithdrawActuator` both pass this flag straight into `exchangeCapsule.transaction(...)`, and persist the resulting (unchecked) balances back to the store without any post-hoc solvency verification: [4](#0-3) 

Exactly like the Insure-DAO report — where `PoolTemplate.resume()` computes a shortfall (`_shortage`) and simply calls `vault.transferDebt(_shortage)` with no guaranteed backing mechanism — java-tron's legacy exchange path can produce a `buyTokenQuant` that (due to floating-point rounding/precision loss on the two chained double-power operations) exceeds the actual buy-side reserve. Because the check that would catch `newSecondTokenBalance < 0` (or `newFirstTokenBalance < 0`) is bypassed whenever `hardenedCalc` is false, the pool's on-chain reserve counters (`firstTokenBalance`/`secondTokenBalance` in the `Exchange` capsule) can be driven negative or below the sum of tokens that other users are entitled to withdraw. There is no debt-tracking, no compensation mechanism, and no `resume()`-style repayment path anywhere in the exchange subsystem to make the pool whole again — the insolvency is simply persisted as corrupted state in the `ExchangeStore`/`ExchangeV2Store`.

### Impact Explanation
If the legacy math ever produces an output larger than the actual reserve (a realistic risk given chained double-precision `pow` operations with exponents 0.0005 and 2000.0, which amplify floating-point error), the pool's tracked balances become unbacked: subsequent `ExchangeWithdrawActuator` or `ExchangeTransactionActuator` calls will pay out tokens that don't actually exist in the pool, effectively creating counterfeit TRX/TRC10 balance for whichever user trades first, at the expense of later participants who cannot fully redeem their share. This is a fund-theft/insolvency vector reachable by any unprivileged account issuing an `ExchangeTransactionContract`.

### Likelihood Explanation
Likelihood depends on whether `allowHardenExchangeCalculation()` has been activated network-wide via committee proposal. If it has not been activated (or on any private/test network where it is off by default), every exchange trade uses the unguarded legacy path, making the missing solvency check always reachable. I could not fully verify from the indexed code whether this proposal is active by default on mainnet at the current block height — that would need to be confirmed via `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`'s default value and `ProposalUtil.java`'s allowed proposal ranges, which I was only able to partially inspect through grep results, not full file contents.

### Recommendation
Enforce the non-negative/reserve-sufficiency invariant unconditionally in `ExchangeCapsule.transaction()`, independent of `hardenedCalc`, so that the legacy floating-point path cannot silently create unbacked pool debt. Alternatively, deprecate the legacy `ExchangeProcessor` path entirely and make `SafeExchangeProcessor` (BigDecimal-based, with an explicit check) the only supported code path.

### Proof of Concept
1. Create an `Exchange` pool with small reserves that make floating-point rounding error proportionally significant relative to the queried token balances (e.g., very small `buyTokenBalance`).
2. Repeatedly issue `ExchangeTransactionContract` trades using the legacy path (`allowHardenExchangeCalculation()` disabled/not yet activated), each computing `buyTokenQuant` via `ExchangeProcessor.exchange()`.
3. Because `hardenedCalc` is `false`, `ExchangeCapsule.transaction()` skips the `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` check and commits the new balances unconditionally.
4. Over repeated trades near the reserve boundary, floating-point drift can cause `newSecondTokenBalance` (or `newFirstTokenBalance`) to go negative or below what other depositors are owed, while the actuator still marks the transaction `SUCESS` and transfers the (now unbacked) tokens to the trader's account, as seen in the unconditional `accountCapsule.addAssetAmountV2`/`setBalance` calls in `ExchangeTransactionActuator.execute()`.

I was unable to fully confirm from indexed content the exact default activation state of `allowHardenExchangeCalculation()` on the current live chain — this should be verified directly against `DynamicPropertiesStore`'s default value before treating likelihood as certain.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
