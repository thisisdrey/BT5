### Title
Missing "internal-only" guard on `HookService` allows cross-transaction hook-pairing bypass via forged `GITALY_HOOKS_PAYLOAD` - (File: `internal/git/gitcmd/hooks_payload.go`, `internal/gitaly/hook/prereceive.go`, `internal/gitaly/hook/postreceive.go`, `internal/gitaly/hook/referencetransaction.go`)

### Summary
Gitaly's `HookService` (`PreReceiveHook`, `PostReceiveHook`, `UpdateHook`, `ReferenceTransactionHook`, `ProcReceiveHook`) is designed to be invoked *only* internally by the `gitaly-hooks` binary as part of a single git-receive-pack/OperationService flow, mirroring the "PreSwap must be paired with PostSwap in the same call" invariant from the reported bug class. However, the service is also reachable on Gitaly's external, authenticated gRPC listener, as explicitly acknowledged in the codebase itself: [1](#0-0)  Because all pairing/state information (`TransactionID`, `Transaction`, `Repository`, `UserDetails`) is carried in a plain base64/JSON `GITALY_HOOKS_PAYLOAD` environment variable with no cryptographic binding to the actual internal call chain, an attacker holding a valid Gitaly auth token can synthesize this payload and invoke these RPCs directly and out of order.

### Finding Description
`HooksPayloadFromEnv` simply base64-decodes and JSON-unmarshals the caller-supplied `environment_variables` field of the hook RPC request — it performs no signature check, no correlation to an actual in-flight internal invocation, and no verification that the caller is `gitaly-hooks` itself: [2](#0-1)  The payload fully controls the `TransactionID`, which `PreReceiveHook`, `PostReceiveHook`, and `ReferenceTransactionHook` use to look up a live `storage.Transaction` from the process-global `TransactionRegistry`: [3](#0-2) [4](#0-3) [5](#0-4) 

This is architecturally identical to the reported CPI-guard bug: two operations (`PreReceiveHook`↔`PostReceiveHook`, or `ReferenceTransactionHook(prepared)`↔`ReferenceTransactionHook(committed)`) are supposed to be paired within a single internally-orchestrated push, correlated only by an attacker-controllable index/ID (`TransactionID` here, `pre_or_post_idx`/`current_index` there). Nothing enforces that the RPC was reached via the legitimate internal chain (the CPI-guard analog) rather than a direct external call. A holder of any valid Gitaly token can:
- Guess/observe a live `TransactionID` belonging to a concurrent legitimate push and call `PostReceiveHook`, `ReferenceTransactionHook(committed)`, or `SignalPostReceiveReady` against it out-of-band, decoupling `Rails`'s reference-counter accounting from `preReceiveHook`'s: [6](#0-5) 
- Invoke `PreReceiveHook`/`PostReceiveHook`/`UpdateHook` with `isPrimary(payload)` forged and a self-chosen `Repository` (including quarantine object-directory fields), causing Rails's `/internal/allowed` access-check flow and reference-counter increments/decrements to run against arbitrary attacker-chosen data. [7](#0-6) 

### Impact Explanation
An attacker who possesses Gitaly's shared external auth token (any regular authenticated client, not a privileged operator) can desynchronize the pre-receive/post-receive/reference-transaction pairing that GitLab access-control and Praefect-quorum logic rely on. This can decrement/increment the per-repository push reference counter without a matching real push, spoof `ReferenceTransactionHook(committed)` votes against another concurrent transaction, or trigger `PostReceiveHook`'s Rails notification for a push that never completed its access checks — undermining the access-control and vote-integrity guarantees the hook chain exists to provide.

### Likelihood Explanation
Exploitation only requires: (1) a valid Gitaly auth token — the same credential used for any ordinary RPC — and (2) knowledge or observation of a `TransactionID` value, which is a small monotonically-increasing integer assigned by `TransactionRegistry.register` and thus easy to guess/race against a concurrent push: [8](#0-7)  No specialized access or insider position is required beyond what an ordinary Gitaly client already has, and the flaw is explicitly reachable over the external listener today.

### Recommendation
Enforce a genuine "internal-only" guard on `HookService`: stop serving it on the external socket (as the code comment itself recommends), or require the `InternalSocketToken`/a per-call HMAC over the whole payload — bound to the specific request context that generated it — before trusting `TransactionID`, `Repository`, and `UserDetails` from `GITALY_HOOKS_PAYLOAD`. This closes the gap analogous to the missing CPI check in the report: reject any hook RPC that did not originate from the paired internal call chain.

### Proof of Concept
1. Obtain a valid Gitaly gRPC auth token (identical to what any client uses for other RPCs).
2. Start a legitimate push (e.g. via `git push`) and observe/guess the assigned `TransactionID` (small sequential integer from `TransactionRegistry`).
3. Independently connect to Gitaly's external listener and call `HookServiceClient.PostReceiveHook` (or `ReferenceTransactionHook` with `state=committed`), supplying a self-crafted `GITALY_HOOKS_PAYLOAD` env var containing that `TransactionID` and an attacker-chosen `Repository`/`UserDetails`, as done in `internal/gitaly/service/hook/pre_receive_test.go` lines 182-197 (which itself demonstrates calling `HookService` "through the external API"). [9](#0-8) 
4. Observe that the forged call is processed against the live transaction/registry entry without any check that it originated from the paired internal `gitaly-hooks` invocation, decoupling `pre-receive`/`post-receive`/reference-transaction accounting from the actual push, analogous to the reported PreSwap/PostSwap CPI-guard bypass.

// HooksPayloadFromEnv extracts the HooksPayload from the given environment
// variables. If no HooksPayload exists, it returns a ErrPayloadNotFound
// error.
func HooksPayloadFromEnv(envs []string) (HooksPayload, error) {
	encoded, ok := lookupEnv(envs, EnvHooksPayload)
	if !ok {
		return HooksPayload{}, ErrPayloadNotFound
	}

	decoded, err := base64.StdEncoding.DecodeString(encoded)
	if err != nil {
		return HooksPayload{}, err
	}

	var jsonPayload jsonHooksPayload
	if err := json.Unmarshal(decoded, &jsonPayload); err != nil {
		return HooksPayload{}, err
	}

	var repo gitalypb.Repository
	err = protojson.Unmarshal([]byte(jsonPayload.Repo), &repo)
	if err != nil {
		return HooksPayload{}, err
	}

	payload := jsonPayload.HooksPayload
	payload.Repo = &repo

	// If no RequestedHooks are passed down to us, then we need to assume
	// that the caller of this hook isn't aware of this field and thus just
	// pretend that he wants to execute all hooks.
	if payload.RequestedHooks == 0 {
		payload.RequestedHooks = AllHooks
	}

	return payload, nil
}

	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return structerr.NewInternal("extracting hooks payload: %w", err)
	}

	// When transactions are enabled, new writes to the repository are only available for readers (other than the
	// transaction itself) after the transaction is committed. Commit usually happens in middleware after the gRPC
	// request handler returns. Because the post-receive hook is invoked within the request handler, the transaction
	// will still be in flight, and the new writes will not be available to other transactions yet. Rails sends
	// further requests from its post-receive handler. Each of these requests are handled in their own transactions.
	//
	// To address this, explicitly commit the transaction here. We then begin a new transaction to provide the hook
	// with read-only access to the repository and its newly written changes. A new transaction is needed because
	// the previous transaction's snapshot would've been discarded by the commit. As the changes have been committed,
	// the subsequent requests sent from Rails' post-receive handler will have access to the new changes.
	//
	// We perform this dance here instead of the transaction middleware as the post-receive hook may need to write
	// messages directly to the client.
	if payload.TransactionID > 0 {
		tx, err := m.txRegistry.Get(payload.TransactionID)
		if err != nil {
			return fmt.Errorf("get transaction: %w", err)
		}

		originalRepo := tx.OriginalRepository(repo)

		// The transaction may already be committed if the RPC invokes git-receive-pack(1) with the
		// proc-receive hook enabled. Ignore the error indicating that here.
		if commitLSN, err := tx.Commit(ctx); err != nil {
			if !errors.Is(err, storage.ErrTransactionAlreadyCommitted) {
				return fmt.Errorf("commit transaction: %w", err)
			}

			// If the transaction was already committed, we don't log the line below.
		} else {
			storage.LogTransactionCommit(ctx, m.logger.WithFields(payload.LogFields), commitLSN, "post-receive")

// PreReceiveHook will try to authenticate the changes against the GitLab API.
// If successful, it will execute custom hooks with the given parameters, push
// options and environment.
func (m *GitLabHookManager) PreReceiveHook(ctx context.Context, repo *gitalypb.Repository, pushOptions, env []string, stdin io.Reader, stdout, stderr io.Writer) error {
	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return structerr.NewInternal("extracting hooks payload: %w", err)
	}

	changes, err := io.ReadAll(stdin)
	if err != nil {
		return structerr.NewInternal("reading stdin from request: %w", err)
	}

	// Only the primary should execute hooks and increment reference counters.
	if isPrimary(payload) {
		if err := m.preReceiveHook(ctx, payload, repo, pushOptions, env, changes, stdout, stderr); err != nil {
			m.logger.WithError(err).WarnContext(ctx, "stopping transaction because pre-receive hook failed")

			// If the pre-receive hook declines the push, then we need to stop any
			// secondaries voting on the transaction.
			if err := m.stopTransaction(ctx, payload); err != nil {
				m.logger.WithError(err).ErrorContext(ctx, "failed stopping transaction in pre-receive hook")
			}

			return err
		}
	}

	if err := m.synchronizeHookExecution(ctx, payload, "pre-receive"); err != nil {
		return fmt.Errorf("synchronizing pre-receive hook: %w", err)
	}

	return nil
