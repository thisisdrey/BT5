## Title
Unbounded array-size allocation in TVM precompiled contracts `BatchValidateSign`/`ValidateMultiSign` allows small calldata to trigger huge memory allocation - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` helper methods used by the `BatchValidateSign` (address `0x...09`) and `ValidateMultiSign` (address `0x...0a`) TVM precompiles read an attacker-controlled 32-byte word as an array length and immediately allocate a Java array of that size, without validating it against the actual size of the supplied calldata. This mirrors the CVE-2019-3553 pattern in Facebook Thrift, where a declared container size larger than the actual payload is used to drive a memory allocation before the payload is checked.

### Finding Description
`extractBytes32Array` reads the length word and allocates directly: [1](#0-0) 

`extractBytesArray` and `extractSigArray` bound-check only the *offset* into the parsed word array, not the declared `len` itself, before allocating `new byte[len][]`: [2](#0-1) 

These are reached from `BatchValidateSign.doExecute`, where `words[2]`/`words[1]` are attacker-supplied offsets pointing at attacker-supplied words used as `len`: [3](#0-2) 

A `MAX_SIZE` (16) bound on the declared sizes is applied only when `VMConfig.allowTvmSelfdestructRestriction()` is active: [4](#0-3) 

The identical pattern (guard gated by the same feature flag) exists in `ValidateMultiSign.execute`: [5](#0-4) 

When that feature flag is not active on a given network (or before its activation height), `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are invoked with a fully attacker-controlled `len` derived from `DataWord.intValueSafe()`, with no relation to the actual number of bytes present in the calldata. The energy cost charged by `getEnergyForData` is computed purely from `data.length` (the real calldata size), not from the declared `len`: [6](#0-5) 

So a caller can submit a small, cheaply-metered calldata (a few hundred bytes) that encodes a length field near `Integer.MAX_VALUE`, causing the precompile to attempt `new byte[2147483647][]` — an allocation of many gigabytes of array-reference memory — before any bounds/energy check reflects the real cost. This is functionally the same root cause as CVE-2019-3553: trusting a declared container size instead of validating it against the actual payload before allocating memory.

### Impact Explanation
A successful call triggers a large heap allocation (multi-GB reference array) inside the JVM executing the node, which can throw `OutOfMemoryError`/exhaust available heap, stall or crash the node's execution thread, and potentially disrupt block processing for other transactions/threads sharing the JVM. This satisfies the "node crash or halt" impact bar. The precompile is reachable from any contract call (CALL opcode to address `0x9`/`0xa`), i.e., by any unprivileged contract deployer or caller once `VMConfig.allowTvmSolidity059()` is enabled (a long-activated TVM feature), making it broadly reachable.

### Likelihood Explanation
Exploitability depends on whether `VMConfig.allowTvmSelfdestructRestriction()` is active on the target network. Where inactive (e.g., newly bootstrapped private/consortium chains, or any deployment that has not yet passed that proposal's activation height), the vulnerable path is trivially reachable with a single crafted transaction. Where active, the `MAX_SIZE` check mitigates this specific precompile, but the underlying helper functions (`extractBytesArray`, `extractSigArray`, `extractBytes32Array`) still have no internal bound on `len`, so any future precompile or code change reusing them without the external gate reintroduces the flaw.

### Recommendation
Add an intrinsic upper bound on `len` inside `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` themselves (e.g., validate `len` against `words.length` or a hard maximum) rather than relying solely on the feature-flag-gated caller-side check, so the protection is unconditional and does not depend on hard-fork activation state.

### Proof of Concept
Construct calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the ABI offset word for the `address[]` (or `bytes[]`) parameter points at a word whose value is `0x7FFFFFFF` (2147483647) instead of a realistic array count, while keeping the rest of the calldata minimal (a few hundred bytes total). Submit this as calldata in a contract call to precompile address `0x...09` (or `0x...0a` for `validatemultisign`) via a normal signed transaction. On a node where `allowTvmSelfdestructRestriction()` is not active, `doExecute`/`execute` will call `extractBytes32Array`/`extractBytesArray` with `len = 2147483647`, attempting `new byte[2147483647][]`, exhausting JVM heap.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
