**`TransactionCommitHook` trait** — only one method, no abort hook: [1](#0-0) 

**`CrossShardCommitSender` implementation** — `on_transaction_committed` only fires `send_remote_update_for_success`, which iterates the write set of the committed output: [2](#0-1) 

**`send_remote_update_for_success`** — only sends a `RemoteTxnWriteMsg` for keys that actually appear in the write set: [3](#0-2) 

**`RemoteStateValue::get_value()`** — unconditional, timeout-free `Condvar::wait` loop: [4](#0-3) 

**`CrossShardStateView::get_state_value()`** — calls `get_value()` (blocking) for every registered cross-shard key: [5](#0-4) 

**`RemoteTxnWrite`** — the struct explicitly documents a `None` write_op for the abort case, and the receiver handles it correctly (`write_op.and_then(|w| w.as_state_value())`), but the sender never produces it: [6](#0-5) [7](#0-6) 

---

**The deadlock path is real and complete:**

1. Block partitioner assigns transaction A (shard 1, writes key K) and transaction B (shard 2, reads key K) with a cross-shard dependency edge.
2. `CrossShardStateView` pre-registers K as `RemoteStateValue::waiting()` in shard 2.
3. A executes and hits a Move abort — its `TransactionOutput` has an empty write set (no K).
4. `on_transaction_committed` is called for A. `send_remote_update_for_success` iterates A's write set — K is absent — no `RemoteTxnWriteMsg` is sent to shard 2.
5. Shard 2's executor thread calls `get_state_value(&K)` → `get_value()` → blocks forever on the `Condvar`.
6. `execute_block` in shard 2 never returns → `StopMsg` is never sent → `CrossShardCommitReceiver` also never exits → the entire `rayon::scope` deadlocks.

The design clearly intended to handle this: `RemoteTxnWrite.write_op` is `Option<WriteOp>` with the comment "None if the transaction is aborted," and the receiver correctly resolves the `Condvar` with `None`. The sender simply never calls that path.

### Title
Cross-shard dependency deadlock: aborted producing transaction never notifies dependent shard, blocking `RemoteStateValue::get_value()` indefinitely — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

### Summary
`CrossShardCommitSender` implements `TransactionCommitHook` but the trait has no `on_transaction_aborted` method. When a producing transaction aborts (Move abort, empty write set), `send_remote_update_for_success` sends nothing for the cross-shard key. The dependent shard's `RemoteStateValue::get_value()` blocks forever on a `Condvar` with no timeout, deadlocking the entire block execution.

### Finding Description
`TransactionCommitHook` exposes only `on_transaction_committed`. [1](#0-0) 

`CrossShardCommitSender::on_transaction_committed` calls `send_remote_update_for_success`, which only sends `RemoteTxnWriteMsg` for keys present in the committed output's write set. [3](#0-2) 

A Move-aborted transaction produces a `TransactionOutput` with an empty (or gas-only) write set. The cross-shard key K is absent, so no message is sent. The dependent shard's `RemoteStateValue` stays in `Waiting` state permanently. [4](#0-3) 

The `CrossShardCommitReceiver` loop only exits on `StopMsg`, which is sent only after `execute_block` returns. `execute_block` cannot return while any executor thread is blocked in `get_value()`. This is a mutual deadlock with no escape. [8](#0-7) 

The design clearly intended to handle aborts: `RemoteTxnWrite.write_op` is `Option<WriteOp>` ("None if the transaction is aborted") and the receiver resolves the condvar correctly for `None`. The sender path is simply never triggered. [9](#0-8) 

### Impact Explanation
Any block containing a cross-shard dependency where the producing transaction aborts will deadlock the sharded block executor permanently. No subsequent blocks can be processed on the affected shard. This is a material chain availability failure reachable from an unprivileged transaction.

### Likelihood Explanation
Move aborts are a normal, expected outcome of any transaction that fails a precondition check (`assert!`, resource not found, arithmetic overflow, etc.). The block partitioner creates cross-shard dependency edges based on static read/write set analysis — an attacker can craft a transaction that declares a write to a contested key (causing the partitioner to create a dependency edge) and then aborts at runtime. Even without a deliberate attacker, any organic transaction abort in a sharded block with cross-shard dependencies triggers this.

### Recommendation
Add `on_transaction_aborted` to `TransactionCommitHook` and implement it in `CrossShardCommitSender` to send `RemoteTxnWriteMsg(RemoteTxnWrite::new(state_key, None))` for every key in `dependent_edges[txn_idx]`. The receiver already handles `None` correctly. Alternatively, add a timeout to `RemoteStateValue::get_value()` and propagate an error to the block executor.
