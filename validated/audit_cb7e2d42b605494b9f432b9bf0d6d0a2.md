#### Title
Attacker-fabricated `contract_id` in `StackerDBChunksEvent` spoofs boot signer contract identity in `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` - (File: libsigner/src/events.rs)

#### Summary
`SignerEventReceiver`'s HTTP endpoint (`/stackerdb_chunks`) accepts and deserializes a raw JSON `StackerDBChunksEvent` with no authentication check anywhere in `libsigner`, and the `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` conversion trusts the attacker-supplied `contract_id` field purely as data, with no binding to the node's actual StackerDB configuration or chain state. Setting `contract_id.issuer` to the real boot address and `contract_id.name` to `"signers-0-3"` makes `event.contract_id.is_boot()` and `get_signers_db_signer_set_message_id` both succeed, producing a `SignerEvent::SignerMessages{signer_set: 0, ...}` built entirely from attacker JSON.

#### Finding Description
The broken equality: `contract_id accepted as a boot signer contract` should imply the chunk was genuinely fetched/stored from that boot StackerDB contract on-chain, but in `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` (`libsigner/src/events.rs:544-625`) the check is purely syntactic:

```

    let Some((signer_set, message_id)) =
        get_signers_db_signer_set_message_id(event.contract_id.name.as_str())
``` [1](#0-0) 

`QualifiedContractIdentifier` (`issuer`, `name`) is just deserialized JSON data (`StackerDBChunksEvent` derives `Deserialize`) with no signature or chain-state check at this layer: [2](#0-1) 

The entry point is `SignerEventReceiver::next_event`, which routes `POST /stackerdb_chunks` straight to `process_event::<T, StackerDBChunksEvent>(request)`, which reads the body, JSON-decodes it, and calls `.try_into()` — with no auth check anywhere in this file or module: [3](#0-2) [4](#0-3) 

A grep across `libsigner/**` for `auth_password`/`auth_token`/`Authorization` found no matches, confirming this HTTP listener performs no credential check despite the documentation (`docs/signing.md`) describing an `auth_password`/`auth_token` pairing intended for the node→signer channel. That mechanism is not implemented in this code path.

Once inside the accepted branch, per-message trust is also weak: `chunk.recover_pk()` only recovers *whatever* public key signed the chunk's `sig` field — it does not check that key against the real signer set for that contract: [5](#0-4) 

So the attacker can self-sign chunks with their own throwaway key and have them pass `recover_pk`. The only remaining gate — `signer_message_payload_matches_lane` — is a fixed, local table keyed off `message_id` extracted from the same attacker-controlled `contract_id.name`; it enforces a payload-type/lane pairing consistency but does not verify contract authenticity.

**Attacker's exact message**: a JSON body of `StackerDBChunksEvent { contract_id: {issuer: <real boot address>, name: "signers-0-3"}, modified_slots: [<self-signed chunk with a valid v0 SignerMessage type byte>] }` POSTed to `http://<signer-endpoint>/stackerdb_chunks`.

**Exploit flow**: attacker connects directly to the signer's bound HTTP port (e.g., `0.0.0.0:30000` per `sample/conf/mainnet-signer.toml`) → sends the fabricated request → `process_event` parses it → `TryFrom` accepts it as a genuine boot-contract `signers-0-3` message → `SignerEvent::SignerMessages{signer_set: 0, messages: [(slot_id, attacker_pk, message)]}` is forwarded into the signer's runloop as if it came from the real node/StackerDB.

**Why existing guards fail**: there is no signature/MAC over the HTTP body tying it to the real node, no comparison of `contract_id` against a locally configured allow-list of real StackerDB contract IDs, and no verification that `recover_pk()`'s result belongs to the actual signer set for that reward cycle at this layer.

#### Impact Explanation
The attacker fully spoofs the identity of the `signers-0-3` (or any `signers-X-Y`, or `.miners`) boot-contract message lane inside the signer process, injecting an arbitrary `SignerEvent::SignerMessages` with an attacker-chosen `signer_set` and a message payload of the attacker's choosing (bounded only by `signer_message_payload_matches_lane`'s type-byte constraint). This is repeatable per TCP connection to the exposed port. Whether this materializes into an actionable consensus-affecting write depends on downstream consumers (e.g., `SignerRunLoop`/signer-state processing) validating the recovered public key against the real signer set before acting — that check is out of scope per the rules (signer decision logic is excluded), but the finding itself — unauthenticated write of a fully-attributed, boot-contract-labeled `SignerEvent` into the signer's event stream — matches "unauthenticated/unauthorized write to state" at the event-ingestion layer.

#### Likelihood Explanation
Preconditions: the attacker only needs network reachability to the signer's bound HTTP port (commonly `0.0.0.0:30000`, i.e., not loopback-restricted per sample config), and no secret, key, or slot ownership is required to construct or send the message. Cost is a single crafted HTTP POST; fully repeatable and remotely reachable per the stated threat model.

#### Recommendation
Add authentication to the `SignerEventReceiver` HTTP endpoint (verify a shared secret/HMAC over the request, e.g., using the documented `auth_password`, which is currently unenforced in `libsigner`), and additionally validate the `contract_id` in `StackerDBChunksEvent` against a locally known set of legitimate boot contract IDs (and, for signer messages, verify `chunk.recover_pk()`'s result against the actual signer entries for the derived `signer_set`) before constructing `SignerEvent::SignerMessages`.

fn test_fabricated_contract_id_spoofs_signer_set() {

        fabricated_event.try_into().expect("should not succeed if contract_id were validated");

    match signer_event {
        SignerEvent::SignerMessages { signer_set, .. } => {
            assert_eq!(signer_set, 0); // attacker-controlled signer_set accepted
        }
        _ => panic!("expected SignerMessages"),
    }
}

fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
