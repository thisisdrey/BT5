### Title
Attached deposit on `rlp_execute` is silently absorbed with no refund when the underlying wallet action succeeds - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The Wallet Contract's `rlp_execute` entry point is marked `#[payable]` and accepts any attached NEAR deposit from its caller, but that deposit is unrelated to the value actually encoded in the user's signed Ethereum transaction (`tx.value`). The contract only tracks the caller's deposit (`CallerDeposit`) in order to refund it if the resulting cross-contract promise chain *fails*; if the action succeeds, the attached deposit is neither forwarded to the intended action nor refunded to the caller - it is permanently absorbed into the eth-implicit account's own balance.

### Finding Description
`rlp_execute` accepts an arbitrary attached deposit via `#[payable]`: [1](#0-0) 

Inside `inner_rlp_execute`, the attached deposit is wrapped into `CallerDeposit`, whose only purpose is documented as enabling a refund "if the cross-contract call fails": [2](#0-1) [3](#0-2) 

Critically, the value actually forwarded to the target action (`additional_value`) is derived exclusively from the signed Ethereum transaction's `value` field, not from `context.attached_deposit`: [4](#0-3) 

The only place `caller_deposit` is consulted again is in `rlp_execute_callback`, and only in the `PromiseResult::Failed` branch - a refund is issued only on failure: [5](#0-4) 

There is no corresponding branch in the `PromiseResult::Successful` case, nor anywhere else in `address_check_callback` or `nep_141_storage_balance_callback`, that forwards or refunds `caller_deposit` when the action succeeds. This mirrors the reported bug class: a payable entry point accepts tokens it does not use, with no validation/reversion of a non-zero, unused amount - except here the funds are not simply "lost" to a burn address, they are silently retained by the eth-implicit account contract itself (i.e., transferred to a party - the account owner - that the caller did not intend to fund), and are unrecoverable by the original caller once the action succeeds.

### Impact Explanation
Any relayer (or any caller with a function-call access key allowing `rlp_execute`, or the account owner themselves acting through a compromised/careless relayer flow) who mistakenly attaches a NEAR deposit to `rlp_execute` - for example intending it to cover the value of the relayed transaction, or by simple user error analogous to the Tezos report - permanently loses that deposit to the wallet's own account balance whenever the underlying action succeeds. This is a genuine, unrecoverable transfer of funds away from the caller with no reversion path, matching the "trapped funds" bug class from the report. Because `rlp_execute` is the sole entry point used by every relayer for every Ethereum-compatible transaction routed through NEAR's eth-implicit account mechanism, the blast radius is every relayer interacting with every eth-implicit (Wallet Contract) account.

### Likelihood Explanation
Likelihood is moderate: the deposit misuse requires a caller (typically a relayer service) to attach a NEAR deposit to `rlp_execute` that is not equal to zero and not intended to be absorbed by the account. Since relayers are expected to pay gas but not necessarily attach deposits, this may be a rare operational mistake rather than an actively exploited path, and it does not enable an attacker to steal a third party's funds directly - it only causes accidental loss by the depositor. There is also no explicit documentation/enforcement in the code base requiring `rlp_execute` callers to attach zero deposit, so the risk is generic misuse rather than a deliberate exploit against victims.

### Recommendation
- Short term: Reject `rlp_execute` calls where `env::attached_deposit()` is non-zero and not needed for the parsed action, following the same "revert if amount not used" pattern recommended in the original report, or explicitly refund the attached deposit at the top-level (before any promise dispatch) whenever the value is not consumed by the resulting action.
- Alternatively, if attaching a deposit to `rlp_execute` is an intended feature (e.g., to let a relayer fund the actual on-chain value transfer), then also refund `caller_deposit` on the `PromiseResult::Successful` branch of `rlp_execute_callback` (and equivalent branches in `address_check_callback`/`nep_141_storage_balance_callback`) whenever the deposit was not actually consumed by the dispatched action, or explicitly forward it as part of the action's value with clear documentation of that semantics.
- Long term: Audit all `#[payable]` methods across `near-wallet-contract` and `address-registrar` for the same unused-deposit pattern, and add unit/integration tests asserting deposit-in equals deposit-out (via forward or refund) on every code path.

### Proof of Concept
1. Deploy the Wallet Contract on an eth-implicit account `0xabc...`.
2. As a relayer, call `rlp_execute(target, tx_bytes_b64)` with a valid, RLP-encoded, correctly signed `AddKey` or `DeleteKey` Ethereum transaction (a `SelfNearNativeAction`, whose `Action::value()` is defined as zero), and attach `1 NEAR` as the NEAR deposit on the transaction/call.
3. `inner_rlp_execute` computes `caller_deposit = CallerDeposit::new(&context)` (`Some`, since predecessor != current account and deposit is non-zero).
4. The dispatched `AddKey`/`DeleteKey` promise succeeds; `rlp_execute_callback` receives `PromiseResult::Successful` and returns success without ever inspecting/refunding `caller_deposit`.
5. Query the balance of the eth-implicit account before and after: it will show the attached 1 NEAR retained as part of the account's balance, with no transfer back to the relayer and no relation to the actual (zero-value) action that was executed.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
