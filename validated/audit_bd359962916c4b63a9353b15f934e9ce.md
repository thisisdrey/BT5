### Title
RewardsDistributor credits `balance`-sized instant rewards to any account touched while the token index still equals `INITIAL_INDEX` - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
Same class as the ath11k bug: a state record is (re)initialized with a default value that a validity check fails to treat as "unset". The ath11k fix re-initialized `peer_id` to `HAL_INVALID_PEERID` after a `memset` because `0` slipped past the `== HAL_INVALID_PEERID` check. Here, `tokenStates[token_]` is initialized to `TokenState{index: INITIAL_INDEX, timestamp: now}` (i.e. `index = 1e18`, not `0`), and `_calculateTokenDelta`'s "account has no index yet" fallback only fires when `_accountIndex == 0 && _tokenIndex > INITIAL_INDEX`. The equality case `_tokenIndex == INITIAL_INDEX` slips through, leaving `_accountIndex = 0`, producing `_deltaIndex = 1e18` and `tokensDelta = balanceOf(account)` in `wadMul` units — an instant reward credit equal to the account's token balance.

### Finding Description [1](#0-0) 
`_updateTokenSpeed` sets a fresh token's state to `{index: INITIAL_INDEX, timestamp: block.timestamp}` the first time a non-zero speed is configured. [2](#0-1) 
In `_calculateTokenDelta`, the uninitialized-account branch is:

```solidity
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

While `tokenState.index == INITIAL_INDEX` (strict `>` fails), a first-time account gets `_deltaIndex = 1e18` and `_tokensDelta = balance`, instead of the intended `_deltaIndex = 0`.

`index` stays exactly `INITIAL_INDEX` whenever:
- the same block/timestamp as the speed update (`_deltaTimestamps == 0` → `_calculateTokenIndex` returns nothing), or
- the speed is later set back to `0` while `index == INITIAL_INDEX` (e.g. `syncTokenSpeed` after `periodFinish` in the same block); afterwards `_updateTokenIndex` only bumps the timestamp and the index remains pinned at `INITIAL_INDEX` indefinitely.

Every public balance-changing entry point triggers the flawed accrual: `DepositToken`/`DebtToken` mint/burn/transfer hooks call `updateBeforeMintOrBurn`/`updateBeforeTransfer`, and `claimRewards` itself calls `_updateTokensAccruedOf` — all gated only by `tokenStates[token_].index > 0`, which `1e18` satisfies. [3](#0-2) [4](#0-3) 

### Impact Explanation
Direct theft of reward tokens held by the distributor (theft of other users' unclaimed yield). Each affected account's first touch of the token yields `tokensAccruedOf += balance`, i.e. a claim equal to its deposit/debt balance in reward-token units. `_transferRewardIfEnoughTokens` pays out the full accrued amount whenever the distributor's reward balance covers it; if it doesn't, the inflated `tokensAccruedOf` persists and drains future reward funding first, ahead of legitimate accruals. An attacker deposits/mints (or claims via `claimRewards(account, tokens)`) inside the window and withdraws reward tokens they never earned.

### Likelihood Explanation
The window is deterministic, not just same-block: if a token's speed transitions to `0` while `index == INITIAL_INDEX` (same-block `syncTokenSpeed` after Vesper's `periodFinish`, or a governor speed update and a user action in one transaction via multicall/`Operator.execute`), the index is frozen at `INITIAL_INDEX` for every subsequent block, so all later first-time accounts hit the bug permanently. Even without that, the same-block window after any `updateTokenSpeed` is open to any unprivileged depositor. No privileged or malicious-oracle assumptions are needed for the trigger.

### Recommendation
Initialize accounts correctly regardless of index equality: in `_calculateTokenDelta`, treat `_accountIndex == 0` as "use the greater of `INITIAL_INDEX` and `_tokenIndex`" — e.g. `if (_accountIndex == 0) { _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX; }` or simply `if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX)`. Equivalently, initialize the account index whenever a token becomes reward-active so `_deltaIndex` can never be `INITIAL_INDEX` for a fresh account. Add a regression test: set token speed, in the same block have a user deposit/mint, assert `claimable == 0`.

### Proof of Concept
Hardhat (existing fixture style in `test/`):

```ts
// fixture: pool, msdDAI DepositToken, rewardsDistributor registered on pool,
// rewardToken funded to rewardsDistributor
await rewardsDistributor.updateTokenSpeed(msdDAI.address, parseEther('1')) // governor

// Same block (automine off or via Operator.execute batch):
await dai.connect(alice).approve(treasury.address, amount)
await pool.connect(alice).deposit(msdDAI.address, amount) // -> DepositToken._mint
//  -> updateBeforeMintOrBurn -> _updateTokensAccruedOf:
//     tokenIndex == INITIAL_INDEX (1e18), accountIndex == 0
//     -> deltaIndex = 1e18 -> tokensDelta = alice msdDAI balance

expect(await rewardsDistributor.claimable(alice.address)).to.eq(amount) // BUG: expected 0

await rewardsDistributor.claimRewards(alice.address)
// drains `amount` rewardToken from the distributor to alice
```

Uncertainty note: I could not re-verify `DepositToken`'s exact hook invocation line-by-line in this pass, but `updateBeforeMintOrBurn`/`updateBeforeTransfer` are the documented pre-balance-change hooks called by `DepositToken` and `DebtToken` (comments at `contracts/RewardsDistributor.sol:172-184`), and `claimRewards` alone is sufficient to trigger the accrual for any account that already holds tokens before the index window.
