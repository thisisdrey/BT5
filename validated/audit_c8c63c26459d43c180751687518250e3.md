### Title
Heap buffer over-read via unbounded ZIP central-directory extra-field pointer walk - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` walks a central-directory entry's "extra field" region using an attacker-controlled 16-bit `data_size` taken directly from the archive, without validating that the cursor stays within the declared extra-field length or the mapped file bounds. This is structurally the same bug class as CVE-2018-7436 (FreeXL `parse_SST`): a length field read from untrusted content is trusted to advance a pointer used for further dereferences, with no bounds check tying it back to the buffer/region size.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` from the CDH, then processes the extra-field bytes: [1](#0-0) [2](#0-1) 

The extra-field loop is:
```cpp
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
`extra_p` is advanced by an attacker-controlled `data_size` (0–65535) read straight from the archive, and the loop termination condition is `extra_p != p` — an exact-equality check, not a `<` bound check. If a crafted `data_size` value causes `extra_p` to overshoot `p` (the declared end of the extra-field region) rather than land exactly on it, the loop does not terminate: it keeps calling `get_u2le(extra_p)` (which dereferences `extra_p[0]`/`extra_p[1]` unconditionally) and keeps advancing `extra_p` by further attacker-controlled amounts, walking past the extra-field region, past the whole central-directory record, and past the end of the memory-mapped archive file (`zipdata_in_` / `mapped_file_`), which is a fixed-size mapping with no guard against reads beyond its length. There is no `EnsureRemaining`-style check (unlike `ProcessLocalFileEntry`, which does call `EnsureRemaining` before reading `file_name`/`extra_field`) protecting this specific loop. `get_u2le` unconditionally dereferences two bytes: [3](#0-2) 

This is a pointer-dereference-after-unchecked-length-field pattern, analogous to `parse_SST`'s heap over-read: an attacker-supplied length steers a read cursor beyond the buffer it was carved out of, and the code dereferences memory at that location without re-validating it against the true buffer bounds.

This ijar/singlejar zip-parsing code is reached by Bazel's build-time zip/jar processing (e.g., `zip_main.cc`'s `extract`/`ProcessAll` and singlejar's jar-merging path used for `java_binary`/`java_import`/`http_jar`-style targets), which consumes zip/jar files that can originate from untrusted external sources (e.g., a `http_jar`/`http_archive` fetch, or a jar embedded in an untrusted branch's build inputs).

### Impact Explanation
A crafted zip/jar central directory can drive the parser to read arbitrary amounts of memory past the mapped file, potentially crashing the Bazel build process (denial of service) or, depending on heap/mmap layout, leaking adjacent memory content into observable behavior (e.g., via `filename` truncation/memcpy from the over-read region, or via the Zip64 attribute values later used to size other allocations/copies). This matches the high-severity heap over-read class of the reference CVE, though the concrete exploitation depth (info leak vs. crash) depends on platform memory layout, similar to the original FreeXL bug.

### Likelihood Explanation
Reaching this path only requires supplying a zip/jar file with a central directory entry whose extra field contains an oversized/malformed length; no privileged access is required — this is achievable by anyone who can supply a zip/jar to a build (e.g., a malicious release archive, a `http_jar`, or a crafted `.jar`/`.zip` build input). A declared sha256 in `http_archive`/`http_jar`, if computed over the same malicious bytes by the person who introduces the dependency, does not prevent this: checksum verification only certifies that the fetched bytes match a pinned value, it does not validate that the internal zip structure is well-formed, so it does not stop a structurally malicious archive whose hash was pinned against that same malicious content, nor does it help when integrity is not enforced at all for locally-produced/vendored zips consumed directly by ijar/singlejar.

### Recommendation
In `InputZipFile::ProcessCentralDirEntry` (and the analogous logic in `output_jar.cc`/`zip_headers.h`'s `ExtraField::find`, which already does bound-check `start < end` correctly), change the extra-field walking loop to use a strict `<` bound comparison against `p` (the declared end) instead of `!=`, and additionally validate `extra_p + 4 <= p` before reading `header_id`/`data_size`, and `extra_p + data_size <= p` before advancing, erroring out via the existing `error(...)` path (as is already done in `EnsureRemaining` for other fields) rather than silently continuing when the field would overrun the region.

### Proof of Concept
A `BuildIntegrationTestCase`/unit test analogous to `src/tools/singlejar/zip_headers_test.cc` should construct a crafted zip file whose central directory entry declares `extra_field_length = 4` but whose first (and only) extra field entry declares `data_size = 0xFFFF` (i.e., header bytes `01 00 FF FF`), so that `extra_p` after one iteration overshoots `p` instead of equaling it. Feeding this file to `ZipExtractor::Create(...)->ProcessAll()` (as done in `third_party/ijar/zip_main.cc`'s `extract` function) is expected to run past the intended extra-field bounds; under AddressSanitizer/heap-checking, this should manifest as a heap-buffer-overflow (read) report when `get_u2le` dereferences memory beyond the mapped file region, confirming the analog to CVE-2018-7436.
