<title>Unbounded RevisionPaths Array in GetBlobs Enables Per-Request DoS via Repeated Catfile Lookups</title>

### Summary
`BlobService.GetBlobs` accepts a single `GetBlobsRequest` containing a `repeated RevisionPath revision_paths` field [1](#0-0) . The handler only rejects an *empty* list and never caps the number of entries, then iterates the entire list synchronously, issuing a tree-entry lookup and an object-info round-trip against the `git cat-file` process for every element [2](#0-1) [3](#0-2) .

### Finding Description
`validateGetBlobsRequest` only checks `len(req.GetRevisionPaths()) == 0`; there is no upper bound on the number of `RevisionPath` entries a caller may submit [4](#0-3) . `sendGetBlobsResponse` then loops over every entry, calling `tef.FindByRevisionAndPath` (a tree walk through catfile) and, for blob entries, `objectInfoReader.Info` — each a synchronous IPC round-trip to the long-lived `git cat-file` helper process — before finally streaming a response for that entry [5](#0-4) .

This mirrors the reported bug class: an externally reachable handler iterates an attacker-supplied array with no size limit, and per-iteration work (here, git object/tree resolution rather than a value-accumulation loop) is proportional to array length. Unlike other blob-listing RPCs in the same service (`ListBlobs`, `ListAllBlobs`), which explicitly define a `limit`/`blobs_limit` field enforced in `processBlobs` to bound iteration [6](#0-5) , `GetBlobsRequest` has no such limit field for `revision_paths` at all [1](#0-0) , and the repository-wide gRPC server is not configured with any `MaxRecvMsgSize` override (no matches for `MaxRecvMsgSize`/`MaxMsgSize` in the codebase), so the only cap on array size is grpc-go's default 4 MiB message size — large enough to encode tens of thousands of short revision/path pairs in one request.

### Impact Explanation
A single crafted `GetBlobsRequest` can force the Gitaly worker handling the RPC to perform tens of thousands of sequential tree-walk and object-info lookups against the repository's catfile process before the RPC completes or fails. Because the loop is fully synchronous within one request/goroutine, this ties up that goroutine and the shared catfile session for the request's duration, degrading throughput for other RPCs against the same repository/catfile cache entry and consuming CPU proportional to the attacker-chosen array size — a DoS impact consistent with the reported bug class of unbounded-array iteration in an externally reachable handler. Impact is bounded by the default gRPC 4 MiB message cap, which limits (but does not eliminate) the achievable amplification, so this is a resource-exhaustion/availability-degradation issue rather than an unbounded crash.

### Likelihood Explanation
Any client authorized to call `GetBlobs` against a repository (this is a standard `ACCESSOR` RPC used by GitLab/Workhorse, and reachable to anyone with API access to trigger blob retrieval, e.g., via diff/tree browsing endpoints) can trigger this by supplying a large `revision_paths` array in a single request — no privileged position, leaked token, or malicious peer/MITM is required beyond ordinary authorized RPC access.

### Recommendation
Add an explicit maximum bound on `len(req.GetRevisionPaths())` in `validateGetBlobsRequest` (returning `structerr.NewInvalidArgument` when exceeded), mirroring the `limit`/`blobs_limit` pattern already used by `ListBlobs`/`ListAllBlobs`, and/or convert `GetBlobsRequest` to a client-streaming or paginated RPC so unbounded revision/path sets cannot be submitted in a single message.

### Proof of Concept
1. Build a `GetBlobsRequest` for an accessible repository whose `revision_paths` contains as many `RevisionPath{Revision: "<valid-oid>", Path: "<short-path>"}` entries as fit under the ~4 MiB default gRPC message limit (tens of thousands of entries with short strings).
2. Call `BlobService.GetBlobs` with this request.
3. Observe that `sendGetBlobsResponse` sequentially performs a `FindByRevisionAndPath` and `objectInfoReader.Info` catfile round-trip for every entry [3](#0-2) , causing the request to consume CPU/time proportional to the array size while no size validation in `validateGetBlobsRequest` rejects the oversized array [4](#0-3) .

// GetBlobsRequest is a request for the GetBlobs RPC.
message GetBlobsRequest {
  // RevisionPath is a combination of revision and path. All objects reachable in the subdirectory of the treeish
  // will be returned.
  message RevisionPath {
    // revision is the revision that identifies the tree-ish. Must not be empty.
    string revision = 1;
    // path is the path relative to the treeish revision that shall be searched for a blob. If the path is empty the
    // root directory of the tree-ish will be searched.
    bytes path = 2;
  }

  // repository is the repository that shall be searched.
  Repository repository = 1[(target_repository)=true];
  // revision_paths identifies the set of revision/path pairs that shall be searched for blobs.
  repeated RevisionPath revision_paths = 2;
  // limit is the maximum number of bytes we want to receive. Use '-1' to get the full blobs no matter how big.
  int64 limit = 3;
}
