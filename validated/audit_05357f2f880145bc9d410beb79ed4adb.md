### Title
Unbounded per-witness/per-voter iteration in `MaintenanceManager.doMaintenance()` executed on every maintenance block can slow or stall block application - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` is invoked unconditionally from `MaintenanceManager.applyBlock()` [1](#0-0)  every time a maintenance-cycle block is applied — the DPoS analog of `EndBlocker`. It performs multiple full, unbounded scans: (1) `consensusDelegate.getAllWitnesses().forEach(...)` over the entire witness-candidate set [2](#0-1) , (2) `countVote(votesStore)` which iterates every entry ever written to `VotesStore` since the last maintenance [3](#0-2) , and (3) a second full `getAllWitnesses()` scan when `allowChangeDelegation()` is set [4](#0-3) . None of these loops have any page limit, cap, or bound analogous to the `topicPageLimit`/`maxTopicPages` used (even if imperfectly) in the Allora report.

### Finding Description
Both inputs to these unbounded loops are directly and cheaply grown by unprivileged, anonymous transactions:
- Any funded account can call `WitnessCreateContract` to register as a witness candidate for a fixed TRX cost, with no cap on the total number of witness candidates in `WitnessStore` [5](#0-4) .
- Any account can call `VoteWitnessContract` to write/update an entry in `VotesStore` every epoch, with the only limits being per-transaction vote-count validation (`MAX_VOTE_NUMBER`, TRON power) — there is no limit on the number of distinct voting accounts that can add entries to `VotesStore` [6](#0-5) .

Because `doMaintenance()` scans the full `VotesStore` iterator and the full witness list on every maintenance block (which recurs periodically, e.g. every 6 hours by default), the per-maintenance-block cost grows linearly (and with nested per-witness/per-account lambda work, effectively worse) with the number of witness candidates and active voters — both of which any address can inflate at will by paying account/witness-creation and freeze/vote fees. This directly mirrors the reported bug class: an ABCI/end-of-block handler whose computational cost scales with unbounded, attacker-influenced application state rather than being paginated/bounded.

### Impact Explanation
As the witness-candidate set and voter set grow, `doMaintenance()` execution time increases per maintenance block, which is executed synchronously as part of `applyBlock()` for every node validating/producing blocks. If this processing exceeds the block interval, it can delay block production/validation across all nodes at maintenance boundaries, risking node stalls or, in the worst case, missed block production windows and chain liveness degradation — consistent with the "node crash or halt" / "chain split" impact bar.

### Likelihood Explanation
The attack requires only ordinary TRX and standard, unprivileged transactions (`WitnessCreateContract`, `FreezeBalance` + `VoteWitnessContract`) that any address can broadcast; no special role (SR/witness authority), no chain-halting privilege, and no external protocol dependency are required beyond funding the account-upgrade cost and vote fees. Cost scales roughly linearly with the attacker's spend, making this a moderate-cost but fully reachable, deterministic degradation vector triggered every maintenance cycle until candidates/votes are cleaned up (votes are cleared each cycle in `countVote`, but witness candidates persist indefinitely in `WitnessStore`, so witness-list growth is permanent and cumulative).

### Recommendation
Bound the per-maintenance work: cap or paginate the witness-candidate scan (e.g. only process the currently eligible/active-voting subset, not literally `getAllWitnesses()`), and process `VotesStore` in bounded batches across multiple maintenance cycles or amortize the cost, similar to (but correctly bounding, unlike) the flagged Allora pattern. Consider requiring witness candidates to periodically re-stake/renew to bound the live candidate set, and/or move to an incrementally-maintained vote-tally structure instead of a full-store rescan each epoch.

### Proof of Concept
1. From N distinct funded accounts, broadcast `WitnessCreateContract` transactions to register N witness candidates (cost: `AccountUpgradeCost` each) — grows `WitnessStore` permanently and unboundedly [7](#0-6) .
2. From M distinct funded accounts, freeze balance and broadcast `VoteWitnessContract` transactions each maintenance epoch — grows `VotesStore` entries scanned by `countVote` every cycle [8](#0-7) .
3. As N and M grow, measure `doMaintenance()` wall-clock time at each maintenance boundary (invoked from `applyBlock`) — it grows linearly with N and M with no cap, unlike bounded/paginated ABCI handlers, demonstrating the unbounded-cost end-of-block computation.

  private Map<ByteString, Long> countVote(VotesStore votesStore) {
    final Map<ByteString, Long> countWitness = Maps.newHashMap();
    Iterator<Entry<byte[], VotesCapsule>> dbIterator = votesStore.iterator();
    long sizeCount = 0;
    while (dbIterator.hasNext()) {
      Entry<byte[], VotesCapsule> next = dbIterator.next();
      VotesCapsule votes = next.getValue();
      votes.getOldVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) - voteCount);
        } else {
          countWitness.put(voteAddress, -voteCount);
        }
      });
      votes.getNewVotes().forEach(vote -> {
        ByteString voteAddress = vote.getVoteAddress();
        long voteCount = vote.getVoteCount();
        if (countWitness.containsKey(voteAddress)) {
          countWitness.put(voteAddress, countWitness.get(voteAddress) + voteCount);
        } else {
          countWitness.put(voteAddress, voteCount);
        }
      });
      sizeCount++;
      votesStore.delete(next.getKey());
    }
    logger.info("There is {} new votes in this epoch", sizeCount);
    return countWitness;
  }

  private void countVoteAccount(VoteWitnessContract voteContract) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    VotesStore votesStore = chainBaseManager.getVotesStore();
    MortgageService mortgageService = chainBaseManager.getMortgageService();
    byte[] ownerAddress = voteContract.getOwnerAddress().toByteArray();

    VotesCapsule votesCapsule;

    //
    mortgageService.withdrawReward(ownerAddress);

    AccountCapsule accountCapsule = accountStore.get(ownerAddress);

    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    if (dynamicStore.supportAllowNewResourceModel()
        && accountCapsule.oldTronPowerIsNotInitialized()) {
      accountCapsule.initializeOldTronPower();
    }

    if (!votesStore.has(ownerAddress)) {
      votesCapsule = new VotesCapsule(voteContract.getOwnerAddress(),
          accountCapsule.getVotesList());
    } else {
      votesCapsule = votesStore.get(ownerAddress);
    }

    accountCapsule.clearVotes();
    votesCapsule.clearNewVotes();

    voteContract.getVotesList().forEach(vote -> {
      logger.debug("countVoteAccount, address[{}]",
          ByteArray.toHexString(vote.getVoteAddress().toByteArray()));

      votesCapsule.addNewVotes(vote.getVoteAddress(), vote.getVoteCount());
      accountCapsule.addVotes(vote.getVoteAddress(), vote.getVoteCount());
    });

    accountStore.put(accountCapsule.createDbKey(), accountCapsule);
    votesStore.put(ownerAddress, votesCapsule);
  }
