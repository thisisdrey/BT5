### Title
Uninitialized `accountIndexOf` credits users `balance * INITIAL_INDEX` rewards when token index still equals `INITIAL_INDEX` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` treats a missing per-account index (`accountIndexOf == 0`) as "started at `INITIAL_INDEX`", but only when the token index has already grown past `INITIAL_INDEX`. While `tokenStates[token].index == INITIAL_INDEX` (i.e., during the same `block.timestamp` in which the governor first set a nonzero speed via `updateTokenSpeed`/`updateTokenSpeeds`/`syncTokenSpeed`), the fallback does not apply, so `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, and any existing balance holder is credited `balance.wadMul(1e18) = balance` reward tokens — without having earned anything.

### Finding Description
In `_calculateTokenDelta` (contracts/RewardsDistributor.sol:217-231):

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a token is first activated in `_updateTokenSpeed` (lines 296-299), `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})`. Until `_updateTokenIndex` runs at a later timestamp with `_speed > 0` (lines 203-208), `index` remains exactly `INITIAL_INDEX`. For any account that already holds `DepositToken`/`DebtToken` balance but has no recorded `accountIndexOf` (everyone, the first time), `_accountIndex` stays `0`, producing `_deltaIndex = 1e18` and `_tokensDelta = balanceOf(account_)`.

This uninitialized-value is reachable from permissionless paths:
- `claimRewards(accounts_, tokens_)` (line 150): iterates tokens, calls `_updateTokenIndex` (no-op at same timestamp since `_deltaTimestamps == 0`), then `_updateTokensAccruedOf`, then pays out via `_transferRewardIfEnoughTokens`.
- `updateBeforeMintOrBurn` / `updateBeforeTransfer` (lines 175, 186), invoked by `DebtToken`/`DepositToken` on every mint/burn/transfer.
- `claimable` (line 114) shows the inflated amount read-only.

### Impact Explanation
An attacker holding a DepositToken balance (e.g., deposited collateral, or a leveraged position via `SmartFarmingManager.leverage`) before the reward token's speed is set can, in the same block as the governor's `updateTokenSpeed` transaction (same `block.timestamp`, index still `INITIAL_INDEX`), call `claimRewards(attacker, [depositToken])`. `tokensAccruedOf[attacker]` is set to `depositToken.balanceOf(attacker)` — a 1:1 grant of `rewardToken` per unit of deposit-token balance — and `_transferRewardIfEnoughTokens` (line 248) pays it out up to the distributor's whole `rewardToken` balance. This is direct theft of unclaimed yield owed to all other users; afterwards `tokensAccruedOf` is reset to 0 but `accountIndexOf` is correctly stored as `INITIAL_INDEX`, so the attack is a one-shot drain bounded by the reward balance and the attacker's balance size (inflatable via leverage within the same transaction since `updateBeforeMintOrBurn` on the mint would store `accountIndexOf` before crediting — the attacker instead claims on a pre-existing balance, then can repeat across multiple accounts they control).

### Likelihood Explanation
The exploit window is narrow: `tokenStates[token].index == INITIAL_INDEX` only between the speed-setting transaction and the next `_updateTokenIndex` at a later timestamp. In practice this means the claim must land in the same block as the governor/keeper transaction setting speed (feasible via public-mempool observation and same-block ordering on L2s), or when a token's speed was set to a nonzero value and index was initialized but no time has passed. No privileged role is needed for `claimRewards`. Requires the attacker to already hold a deposit/debt token balance, which any public depositor can arrange beforehand.

### Recommendation
In `_calculateTokenDelta`, treat any unset account index as "no accrual" regardless of token index value: set `_accountIndex = _tokenIndex` (or `INITIAL_INDEX`) whenever `_accountIndex == 0`, i.e.:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;
    // equivalently: skip accrual entirely
}
```

or simply return `_tokensDelta = 0` and persist `_tokenIndex` when `_accountIndex == 0 && _tokenIndex <= INITIAL_INDEX`. Alternatively, initialize `tokenStates` index to `INITIAL_INDEX` at distributor `initialize` time is insufficient — the per-account guard must not depend on the strict `>` comparison.

### Proof of Concept
Foundry-style fork test (Hardhat equivalent):

```solidity
// Assume: pool with DepositToken `dToken`, RewardsDistributor `rd`
// funded with `rewardToken`, attacker already holds dToken balance.

function test_UninitializedAccountIndexDrainsRewards() public {
    // 1. Attacker deposits collateral BEFORE reward speed is set
    vm.prank(attacker);
    dToken.deposit(1_000e18); // attacker balance = ~1_000e18 (minus fee)

    // 2. Same block: governor enables rewards for dToken
    vm.prank(governor);
    rd.updateTokenSpeed(IERC20(address(dToken)), 1e18); // index = INITIAL_INDEX (1e18)

    // 3. Same timestamp: attacker claims — index is still INITIAL_INDEX
    //    _accountIndex == 0, _tokenIndex == INITIAL_INDEX (not >), so
    //    _deltaIndex = 1e18, _tokensDelta = balance(attacker)
    uint256 rewardBalBefore = rewardToken.balanceOf(attacker);
    vm.prank(attacker);
    rd.claimRewards(attacker, toArray(IERC20(address(dToken))));

    // 4. Attacker receives ~balance(attacker) rewardToken for zero accrual time
    assertApproxEqAbs(
        rewardToken.balanceOf(attacker) - rewardBalBefore,
        dToken.balanceOf(attacker),
        1
    );
}
```

Key assertion: `tokensAccruedOf[attacker] == dToken.balanceOf(attacker)` immediately after the speed is set, before any reward time has elapsed — demonstrating the uninitialized index was treated as 0 rather than `INITIAL_INDEX`.
