### Title
Unbounded growth of `DelegatedResourceAccountIndex` lists via legacy `FreezeBalanceContract` delegation - ([File: actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java])

### Summary
The Category Labs/Spearbit report describes a peer-list DoS where an attacker can force unbounded growth of a list keyed by attacker-controlled identities with no size cap. The same bug class exists on-chain in `FreezeBalanceActuator`'s legacy resource-delegation path: any account can cheaply force unbounded growth of the `DelegatedResourceAccountIndex.toAccounts` / `fromAccounts` protobuf lists stored under its own address, with no maximum size enforced anywhere in `validate()` or `execute()`.

### Finding Description
When a `FreezeBalanceContract` specifies a non-empty `receiverAddress` and `dynamicStore.supportDR()` is true, execution takes the delegation branch in `FreezeBalanceActuator.execute()`: [1](#0-0) 

This calls the private `delegateResource(...)` helper, which — when `supportAllowDelegateOptimization()` is false (the legacy/non-optimized storage model) — unconditionally appends the new receiver to the owner's index and the owner to the receiver's index: [2](#0-1) 

Critically, the only guard on repeated freezing is `frozenCount` (must be 0 or 1), checked in `validate()`: [3](#0-2) 

`frozenCount` only tracks the owner's own (non-delegated) `Frozen` entries; it does not limit how many distinct `receiverAddress` values the owner can delegate to, and delegation to a new receiver never touches the owner's own frozen-balance state that `frozenCount` inspects. As a result, an attacker can issue many `FreezeBalanceContract` transactions from a single account, each freezing the minimum `1 TRX` (`TRX_PRECISION`, enforced at line 191-193) to a freshly generated, never-before-seen receiver address. Each such transaction appends one more entry to `DelegatedResourceAccountIndexCapsule.toAccountsList` on the owner's key, and one more entry to a brand-new `fromAccountsList` on each receiver's key — with **no upper bound** anywhere in `DelegatedResourceAccountIndexCapsule` or `DelegatedResourceAccountIndexStore`: [4](#0-3) 

Each `get`/`put` on this store loads and re-serializes the entire (unbounded) protobuf list on every subsequent freeze/unfreeze/query touching that address: [5](#0-4) 

This is functionally the same bug class as the reported peer-list issue: an actor can cheaply and repeatedly force growth of a list with no cap, degrading storage and read/write cost for that account's index entry, and for any wallet/API query that must deserialize it (e.g. `Wallet.getDelegatedResourceAccountIndex`).

### Impact Explanation
Each additional entry costs the attacker only 1 TRX (refundable after the freeze duration) plus a fresh keypair (free), while it permanently grows a protobuf list stored under a single DB key with no cap or pruning path besides an exact-match unfreeze per receiver. Because the whole list is deserialized/reserialized on every read and write to the entry, this can be leveraged to bloat a specific account's index entry over time, increasing serialization cost/storage on the node and degrading the API path that serves `getDelegatedResourceAccountIndex` for that account. This maps to a resource-exhaustion class issue reachable purely via a normal signed transaction, without any special privilege — comparable in kind (unbounded list growth from cheap attacker-controlled operations) to the referenced report, though the achievable blast radius is scoped to a chosen account's index record rather than to global peer/consensus state.

### Likelihood Explanation
High from a "trivial to trigger" standpoint (only requires ordinary transactions and minimal TRX), but the affected legacy delegation path (`!dynamicStore.supportAllowDelegateOptimization()`) is only active on chains/at times where the delegate-optimization hard fork has not been enabled; once `AllowDelegateOptimization` is active, new delegations use the newer `delegateV2`/prefix-key storage model in `DelegateResourceActuator`, which does not maintain an in-place growing list. The exposure window is therefore tied to that dynamic parameter's state on the target network.

### Recommendation
- Enforce a maximum size on `DelegatedResourceAccountIndexCapsule.toAccountsList` / `fromAccountsList` in the legacy (non-optimized) delegation path within `FreezeBalanceActuator.delegateResource()`, rejecting further delegation to new, distinct receivers beyond the cap (mirroring the pattern already used for `MAX_ACTIVE_ORDER_NUM` in `MarketSellAssetActuator` and `getMaxFrozenSupplyNumber()` in `AssetIssueActuator`).
- Alternatively/additionally, ensure the optimized (`delegateV2`, per-pair-key) storage model is unconditionally used going forward so the legacy unbounded-list code path is fully retired.

### Proof of Concept
1. Attacker controls `OWNER_ADDRESS` with balance ≥ `1 TRX * N`.
2. On a chain where `AllowDelegateOptimization` is not yet enabled, attacker generates `N` fresh keypairs `R_1..R_N`.
3. For each `R_i`, attacker submits a `FreezeBalanceContract` from `OWNER_ADDRESS` with `frozenBalance = 1 TRX`, `resource = BANDWIDTH`, `receiverAddress = R_i`.
4. Each transaction passes `validate()` (frozenCount check is irrelevant to delegation) and executes `delegateResource()`, appending `R_i` to `OWNER_ADDRESS`'s `DelegatedResourceAccountIndexCapsule.toAccountsList` per `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java:328-332`, and creating a new one-entry index record for each `R_i`.
5. Repeating this for large `N` grows `OWNER_ADDRESS`'s index record without bound, confirmed reachable and unrestricted by the existing test `testMultiFreezeDelegatedBalanceForBandwidth` demonstrating repeated appends to the same list: [6](#0-5) .
