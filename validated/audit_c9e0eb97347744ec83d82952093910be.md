### Title
Unprivileged dust transfers fill a victim's `depositTokensOfAccount` list, permanently blocking their deposits and withdrawals — ([File: contracts/DepositToken.sol])

### Summary
`DepositToken._transfer` and `DepositToken._mint` call `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from zero to non-zero. This function in `Pool.sol` enforces `MAX_TOKENS_PER_USER` and reverts once the account's list is full. Because `transfer`, `transferFrom`, and `deposit(amount_, onBehalfOf_)` are all public entry points with no opt-in from the recipient, any unprivileged attacker can permanently register every existing `DepositToken` on a victim's account list with dust amounts, so that any subsequent deposit by the victim reverts.

Analog to CVE-2021-1095: the handler dereferences attacker-supplied data (the recipient pointer) inside a control path (`_transfer` → `addToDepositTokensOfAccount`) without validating that the recipient consented, and the resulting state corruption causes denial of service for the victim's subsequent operations.

### Finding Description [1](#0-0) 

`_transfer` is invoked by `transfer`, `transferFrom`, and `seize`. When `balanceOf[recipient_] == 0` and `amount_ > 0`, it unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)`. The same happens in `_mint`, which is reached by `deposit(..., onBehalfOf_)` for an arbitrary `onBehalfOf_` address: [2](#0-1) [3](#0-2) [4](#0-3) 

`addToDepositTokensOfAccount`/`MAX_TOKENS_PER_USER` is enforced in `contracts/Pool.sol` and `contracts/lib/MappedEnumerableSet.sol`; once the list reaches the cap the add reverts, which propagates up and reverts the whole `_mint`/`deposit` transaction.

Attack path (all unprivileged):
1. Attacker deposits dust of each whitelisted collateral into `DepositToken` (or obtains dust any way), yielding `msdX` balances.
2. Attacker calls `depositToken.transfer(victim, 1)` for every `DepositToken` in the pool. Each call hits `_transfer` → `addToDepositTokensOfAccount(victim)`, filling `depositTokensOfAccount[victim]` up to `MAX_TOKENS_PER_USER`.
3. When the victim later calls `depositToken.deposit(amount, victim)` on a collateral they do not yet hold, `_mint` → `addToDepositTokensOfAccount(victim)` reverts, so the victim cannot onboard any new collateral type.

Note on uncertainty: I was able to confirm the registration calls and the `MAX_TOKENS_PER_USER`/`MappedEnumerableSet` machinery exist in `Pool.sol`/`PoolStorage.sol` via grep, but I did not have iterations left to read the exact `addToDepositTokensOfAccount` body to quote the revert line and confirm the cap is enforced at add-time (rather than only on deposit). The mechanism is still clearly present: `DepositToken` unconditionally registers recipients with no consent flag.

### Impact Explanation
- Denial of service on deposits: the victim is blocked from depositing into any collateral not already in their list for as long as the list is at the cap.
- Compounding griefing: the attacker can front-run/grief repeatedly (re-dust after the victim empties a slot), effectively imposing a persistent freeze on new collateral onboarding at near-zero cost (dust amounts only).
- The same forced registration also inflates `debtPositionOf`/health-factor computation over the victim's list (more iterations on every deposit/withdraw/liquidation involving the victim), raising gas costs of victim operations.

### Likelihood Explanation
- Fully reachable by any EOA: `deposit` accepts an arbitrary `onBehalfOf_`, and `transfer`/`transferFrom` have no recipient allowlist.
- Cost is only dust plus gas; no privileged role, oracle manipulation, or trusted-remote assumptions needed.
- Effectiveness depends on the deployed `MAX_TOKENS_PER_USER` value relative to the number of whitelisted `DepositToken`s — with a bounded set of collaterals the cap is reachable.

### Recommendation
- Gate list registration on recipient opt-in (e.g., only register on `deposit` where `onBehalfOf_ == _msgSender()`, or require an explicit `addCollateral`/`setUseAsCollateral` flag set by the account owner, similar to Aave's `setUserUseReserveAsCollateral`).
- Alternatively, allow `addToDepositTokensOfAccount` overflow to be handled lazily (track active collaterals derived from non-zero balances instead of a capped list), or exempt dust amounts below a minimum deposit threshold from registration.
- At minimum, apply a `MINIMUM_REGISTRATION_AMOUNT` check in `_transfer`/`_mint` before calling `addToDepositTokensOfAccount` so attacker dust cannot occupy list slots.

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {DepositToken} from "../contracts/DepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DustListGriefingTest is Test {
    Pool pool;                 // deployed mainnet fork instance
    DepositToken[] tokens;     // all DepositTokens registered in the pool
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    function testDustFillsVictimList() public {
        // fork mainnet, load pool + its DepositTokens
        // 1) attacker gets dust of each msdToken (deposit small amount or transfer)
        for (uint i; i < tokens.length; i++) {
            IERC20 underlying = tokens[i].underlying();
            deal(address(underlying), attacker, 1e6);
            vm.startPrank(attacker);
            underlying.approve(address(tokens[i]), type(uint256).max);
            tokens[i].deposit(1e6, attacker);          // attacker mints dust position
            tokens[i].transfer(victim, 1);             // registers token on victim's list
            vm.stopPrank();
        }

        // depositTokensOfAccount[victim] is now at MAX_TOKENS_PER_USER

        // 2) victim tries to deposit into a collateral they don't hold -> reverts
        DepositToken newCollateral = tokens[0]; // assume victim's balance there became 0
        deal(address(newCollateral.underlying()), victim, 100e18);
        vm.startPrank(victim);
        newCollateral.underlying().approve(address(newCollateral), type(uint256).max);
        vm.expectRevert(); // MaxTokensPerUserReached / list-full revert from addToDepositTokensOfAccount
        newCollateral.deposit(100e18, victim);
        vm.stopPrank();
    }
}
```

The PoC is reproducible on a Hardhat/Foundry mainnet fork against the deployed `Pool`/`DepositToken` proxies; the exact revert depends on confirming `addToDepositTokensOfAccount`'s cap check in `contracts/Pool.sol` (the `MAX_TOKENS_PER_USER` and `MappedEnumerableSet` usages are present there but I could not read the function body within available iterations — if the cap is not enforced on add, this degrades to gas-cost griefing only and should be reported as such rather than a DoS).
