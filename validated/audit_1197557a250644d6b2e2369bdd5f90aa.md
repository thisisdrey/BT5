### Title
Unauthenticated POST to `/v3/blocks/upload/` triggers unconditional network-wide block relay - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_handle_request` calls `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))` solely based on whether the block was locally accepted (`data_resp.accepted`), with no check on `self.broadcast` or the `authenticated` flag computed during request parsing. This lets any unauthenticated remote caller who successfully POSTs a valid block cause the node to gossip that block to the whole network, even though the operator's `broadcast=1` + auth-token gate was never satisfied.

### Finding Description
In `try_parse_request` (stackslib/src/net/api/postblock_v3.rs:99-122), the code computes `authenticated` from the `authorization` header vs the configured secret, and `broadcast` from the `broadcast=1` query arg, enforcing `if broadcast && !authenticated { return Err(401) }`. This only prevents an *unauthenticated caller from setting broadcast=1*; it does not prevent an unauthenticated caller from POSTing at all (the endpoint has no blanket auth requirement — `self.auth` is only checked if the header is present) [1](#0-0) .

The resulting `self.broadcast = Some(broadcast)` (which will be `Some(false)` for a bare unauthenticated request) is passed into `Relayer::process_new_nakamoto_block_ext(..., self.broadcast.unwrap_or(false))` in `try_handle_request` [2](#0-1) . That `broadcast` bool controls internal behavior of block processing/storage, but it is **not** consulted again afterward. Instead, the relay decision is made purely on `data_resp.accepted`:

```
if data_resp.accepted {
    node.set_relay_message(StacksMessageType::NakamotoBlocks(NakamotoBlocksData {
        blocks: vec![block],
    }));
}
``` [3](#0-2) 

So the equality the operator expects — "requests that trigger network relay == requests carrying the configured auth_token/broadcast=1" — is broken: any request (authenticated or not, broadcast=1 or not) that results in the block being accepted by chainstate validation will unconditionally queue it for relay to peers via `node.set_relay_message`.

An attacker's exploit message is simply: a well-formed `NakamotoBlock` (consensus-deserializable, under `MAX_PAYLOAD_LEN`) POSTed to `/v3/blocks/upload/` with `Content-Type: application/octet-stream`, no `authorization` header, and no `broadcast` query parameter. As long as the block passes chainstate acceptance criteria (e.g., a legitimately-produced block the attacker relays from elsewhere, or one it can otherwise get accepted), `data_resp.accepted` is true and the relay fires regardless of the auth/broadcast gate.

### Impact Explanation
This allows an unauthenticated remote party to force the node to gossip network-wide any block it can get chainstate to accept, bypassing the operator's intended broadcast authorization control (`auth` + `broadcast=1`). This matches "network-wide propagation of forged/unauthorized data" — the node is instructed to relay content its operator never approved for broadcast, from an unauthenticated write path. The relay path is per-message and repeatable for any subsequent accepted block upload.

### Likelihood Explanation
- Precondition: the node's RPC endpoint is reachable (default RPC posture), and the endpoint accepts anonymous POSTs unless an `authorization` header happens to be present — no secret is required to reach this code path at all.
- Attacker cost: trivial — construct a valid `NakamotoBlock` payload and issue one HTTP POST; no signature/secret bypass is needed because the check that would need bypassing (`broadcast && !authenticated`) is simply never triggered since the attacker never sets `broadcast=1`.
- Repeatable per accepted block; scales with how many valid blocks the attacker can supply.

### Recommendation
Gate the `node.set_relay_message(...)` call on the `broadcast` flag (and by extension the authentication that already governs it), e.g. `if data_resp.accepted && self.broadcast.unwrap_or(false) { ... }`, so that relay only happens when the caller was authenticated to request broadcast, restoring the intended equality between authorized broadcast requests and actual network relay.

### Proof of Concept
Rust test plan in `stackslib::net::api::tests::postblock_v3`:
1. Construct a `StacksHttpRequest` to `PATH` (`/v3/blocks/upload/`) with a valid serialized `NakamotoBlock` body, `Content-Type: application/octet-stream`, no `authorization` header, and no `broadcast` query arg.
2. Feed it through `RPCPostBlockRequestHandler::try_parse_request`; assert `handler.broadcast == Some(false)`.
3. Call `try_handle_request` with a `StacksNodeState` set up so `Relayer::process_new_nakamoto_block_ext` returns an "accepted" result (e.g., stub/mock chainstate acceptance or use a valid tenure-start block scenario from existing test helpers).
4. Assert that `StacksNodeState`'s relay message queue (`network.pending_messages` / whatever `set_relay_message` populates, per `stackslib/src/net/mod.rs`) now contains a `StacksMessageType::NakamotoBlocks` entry for the block — demonstrating relay fired despite `authenticated == false` and `broadcast == false`.
