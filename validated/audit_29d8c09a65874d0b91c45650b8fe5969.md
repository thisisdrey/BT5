## Title
Accumulate-and-Forward pallet permanently loses pooled protocol revenue on destination-side XCM rejection, with no `onDropMessage`-style recovery path - (File: `polkadot/xcm/xcm-builder/src/forwarder.rs`)

### Summary
`pallet_accumulate_and_forward` (deployed on Westend relay chain, Collectives, Coretime, People and Bridge-Hub system chains) periodically teleports pooled transaction-fee/coretime/dust revenue to a destination chain via `TeleportForwarderForAccountId32::forward`. The adapter itself documents the exact failure class from the external report: local success only guarantees the message was *enqueued*, not that the remote `DepositAsset` succeeds; on remote rejection the funds are trapped with **"no automatic recovery path"** — analogous to Scroll's missing `onDropMessage` hook that stranded ETH when the router bypassed the gateway. [1](#0-0) 

### Finding Description
`on_idle` triggers `T::Forwarder::forward(accumulation_account, available_funds)`, which builds an XCM: `WithdrawAsset → InitiateTransfer{Teleport, preserve_origin: true, remote_xcm=[DepositAsset]}` and executes it locally with `XcmExecutor::prepare_and_execute`. [2](#0-1) [3](#0-2) 

Only `Outcome::Complete` (i.e. local acceptance/queuing of the outbound message) is treated as success (`ForwardSucceeded`) and commits the withdrawal. There is no receipt, callback, or `onDropMessage`-equivalent hook that verifies the *remote* `DepositAsset` into `StagingLocation`/`AccumulateAccount` actually completed. If the destination executes `AliasOrigin(source) → UnpaidExecution → DepositAsset` and that `DepositAsset` fails (e.g. destination account below ED, `MaxAssetsIntoHolding` reached, filtered by destination barrier, or the destination staging account is not pre-funded/misconfigured after a runtime upgrade), the XCM executor's `post_process` traps the assets via `Config::AssetTrap::drop_assets`, using `AliasOrigin(source)` — the sending chain's `accumulation_account` reanchored — as the trap origin. [4](#0-3) [5](#0-4) 

The only recovery mechanism, `ClaimAssets::claim_assets`, requires an XCM sent *as that exact origin* on the destination chain. [6](#0-5) 

But `accumulation_account` is a `PalletId`-derived sovereign account (`into_account_truncating`) with no private key — it has no signing origin, and unlike a parachain sovereign account it cannot originate a native XCM message ("nobody" controls it) unless a system parachain/relay privileged route happens to alias into it. This mirrors the Scroll bug precisely: the routing optimization (teleport straight from `L1GatewayRouter`/here, the accumulation pallet, instead of via an intermediary gateway/receipt-bearing pallet) removed the entity that could execute the drop/refund callback, so once the "message" (teleport) is accepted locally but rejected on the far side, the funds are permanently stuck — this time as pooled protocol revenue (fees, coretime revenue, dust) rather than a single user's ETH.

### Impact Explanation
This falls under "permanent user-fund or bridge-state lock" and "theft or unbacked mint or unlock" style asset-accounting failures called out in the Required Impacts. Funds accumulated in `AccumulateAccount` are burnt locally on `forward()` success (per the pallet's own doc: "Accumulated funds are burnt upon forwarding … and the same funds are minted at the destination when the sent message is received") [7](#0-6) 

If the destination-side mint/deposit fails, the minted teleport value is trapped under an unreachable origin, meaning it is neither returned to the source chain, nor recoverable at the destination without a privileged/governance intervention to author an XCM as that alias (which is not guaranteed to exist, and even where it exists is a workaround, not a designed recovery path). This is systemic pooled treasury/fee revenue, recurring every `TransferPeriod`, not a one-off user error.

### Likelihood Explanation
The pallet is wired into live Westend system-chain runtimes (relay chain, Collectives, Coretime, People, Bridge-Hub) as the `OnUnbalanced` handler for fees/dust/coretime revenue, and `on_idle` runs unconditionally and permissionlessly (no attacker action needed — it is an automatic periodic internal process). No admin/governance/malicious-relayer action is required to trigger the failure mode; any transient destination-side condition (barrier rejection, ED underflow at the staging account, holding-limit overflow, XCM version mismatch, or a runtime-upgrade that leaves `StagingLocation` unfunded even briefly) silently and permanently traps the batch with only a debug-level `ForwardFailed`/trap event, no funds returned. This matches "public underpriced work that … stalls bridge processing" / accounting-invariant class explicitly in scope, and does not require a malicious peer/validator/admin, satisfying the pivot's guard.

### Recommendation
Implement an explicit remote-delivery acknowledgement (e.g. `ReportTransactStatus`/`QueryResponse`-based confirmation of the far-end `DepositAsset`) before treating the funds as forwarded, or make `remote_xcm` include a `SetAppendix`/`ClaimAsset`-friendly fallback whose failure path deposits back to a location the source chain can practically claim from (e.g. `RefundSurplus` + `DepositAsset` to a location matching an origin the runtime can reconstruct via governance-free means), and add integration tests asserting that a destination-side `DepositAsset` failure does not result in an unrecoverable trap for the `accumulation_account` origin, mirroring how Scroll's fix rolled back to routing calls through the gateway that could execute `onDropMessage`.

### Proof of Concept
Not independently executable within the current investigation (would require running the `pallet_accumulate_and_forward`/`xcm-builder` test harness with a destination barrier/`AssetTrap` mock forcing `DepositAsset` failure). The existing unit tests already validate the "happy path" and local-rollback-on-local-failure path but do not cover the destination-side-rejection-after-local-success scenario: [8](#0-7) 
A concrete reproduction would extend the `xcm-executor`/`xcm-builder` forwarder test suite (`polkadot/xcm/xcm-builder/src/tests/forwarder.rs`) to simulate remote rejection and assert that `AssetTraps` records an entry under `AliasOrigin(accumulation_account)` with no subsequent path to reclaim it without a privileged/governance-authored XCM.

	fn forward(source: AccountId, amount: Balance) -> Result<(), ()> {
		let dest = Dest::get();
		let asset = Asset { id: AssetId(NativeAsset::get()), fun: Fungible(amount.into()) };
		let beneficiary: Location = StagingLocation::get().into_location();

		let remote_xcm = Xcm(vec![DepositAsset { assets: Wild(AllCounted(1)), beneficiary }]);

		// The XCM flow: `ReceiveTeleportedAsset → AliasOrigin(source) → UnpaidExecution →
		// DepositAsset`. `preserve_origin: true` causes `InitiateTransfer` to prepend
		// `AliasOrigin(source_location)` to the remote XCM.
		let xcm: Xcm<XcmConfig::RuntimeCall> = Xcm(vec![
			UnpaidExecution { weight_limit: WeightLimit::Unlimited, check_origin: None },
			DescendOrigin(Junction::AccountId32 { network: None, id: source.into() }.into()),
			WithdrawAsset(asset.into()),
			InitiateTransfer {
				destination: dest,
				remote_fees: None,
				preserve_origin: true,
				assets: BoundedVec::truncate_from(alloc::vec![AssetTransferFilter::Teleport(
					Wild(AllCounted(1))
				),]),
				remote_xcm,
			},
		]);

		with_transaction(|| -> TransactionOutcome<Result<(), DispatchError>> {
			let outcome = XcmExecutor::<XcmConfig>::prepare_and_execute(
				Location::here(),
				xcm,
				&mut [0u8; 32],
				Weight::MAX,
				Weight::MAX,
			);

			match outcome {
				Outcome::Complete { .. } => TransactionOutcome::Commit(Ok(())),
				exec_error => {
					tracing::debug!(
						target: LOG_TARGET,
						?exec_error,
						"accumulate-forward: XCM execution failed"
					);

					TransactionOutcome::Rollback(Err(DispatchError::Other("XCM execution failed")))
				},
			}
		})
		.map_err(|_| ())

impl<T: Config> DropAssets for Pallet<T> {
	fn drop_assets(origin: &Location, holding: AssetsInHolding, _context: &XcmContext) -> Weight {
		if holding.is_empty() {
			return Weight::zero();
		}
		let assets: Vec<Asset> = holding.assets_iter().collect();
		// SAFETY: "forget" about any fungible imbalances so that they are not dropped/resolved
		// here. The mirrored asset claiming operation will "recover" the imbalances by minting
		// back into holding, effectively duplicating the imbalance and only then dropping the
		// duplicate. As a result, total issuance doesn't change.
		holding.fungible.into_iter().for_each(|(_, mut accounting)| {
			accounting.forget_imbalance();
		});
		let versioned = VersionedAssets::from(Assets::from(assets));
		let hash = BlakeTwo256::hash_of(&(&origin, &versioned));
		AssetTraps::<T>::mutate(hash, |n| *n += 1);
		Self::deposit_event(Event::AssetsTrapped {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		// TODO #3735: Put the real weight in there.
		Weight::zero()
	}

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}

/// A single sub-ED deposit fails, the instruction is aborted, and the leftover holding is
/// trapped by `post_process` — funds are not lost.
#[test]
fn failed_deposit_aborts_instruction_and_post_process_traps_holding() {
	add_asset(SENDER, (Here, 1u128)); // 1 < ExistentialDeposit (=2 in mock)

	let xcm = Xcm::<TestCall>::builder_unsafe()
		.withdraw_asset((Here, 1u128))
		.deposit_asset(All, RECIPIENT)
		.build();

	let (mut vm, weight) = instantiate_executor(SENDER, xcm.clone());

	// `bench_process` returns `Err` because the retry-pass deposit failure now bubbles up.
	let result = vm.bench_process(xcm);
	let err = result.expect_err("retry-pass deposit failure must bubble up");

	// Mirror what `XcmExecutor::execute` does between `process` and `post_process`: register
	// the instruction error so `post_process` produces `Outcome::Incomplete`.
	vm.set_error(Some((err.index, err.xcm_error)));

	let outcome = vm.bench_post_process(weight);
	assert!(
		matches!(outcome, Outcome::Incomplete { .. }),
		"expected Outcome::Incomplete, got {outcome:?}"
	);

	// Recipient never received anything.
	assert!(asset_list(RECIPIENT).is_empty());

	// `post_process` trapped the holding (which `transactional_process` had restored after
	// the failed `DepositAsset`). The mock `TestAssetTrap` accumulates everything under
	// `TRAPPED_ASSETS`.
	assert_eq!(
		asset_list(TRAPPED_ASSETS),
		vec![(Here, 1u128).into()],
		"undeposited assets must be trapped, not silently lost"
	);
}
