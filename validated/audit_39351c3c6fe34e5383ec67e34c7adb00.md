Based on my analysis, I found a valid analog in java-tron's precompiled contract handling that mirrors the `ReverseSequence` root cause: **an attacker-controlled length/offset field is used directly to size an array allocation without validation**, unless a feature flag is enabled to add the missing bound.

### Title
Unvalidated attacker-controlled array-length field in `ValidateMultiSign`/`BatchValidateSign` precompiles allows unbounded array allocation (`OutOfMemoryError` DoS) - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts decode caller-supplied call data into `DataWord[]` and use an attacker-controlled word as an *array length* to allocate `byte[][]` buffers in `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, without validating that the length is within a sane bound unless the `allowTvmSelfdestructRestriction` hard-fork flag is active.

### Finding Description
In `extractBytes32Array`, the length used for allocation comes straight from decoded call data with no bound and no index bound check at all: [1](#0-0) 

`extractBytesArray` and `extractSigArray` at least guard `offset` against `words.length`, but the `len` they use to size `byte[][] bytesArray = new byte[len][];` is taken from `words[offset].intValueSafe()`, which can return values up to `Integer.MAX_VALUE`: [2](#0-1) 

`intValueSafe()` deliberately clamps overflow/negative values to `Integer.MAX_VALUE` rather than rejecting them — this is the DataWord equivalent of TensorFlow's unchecked `seq_dim`/`batch_dim`: [3](#0-2) 

The size cap (`MAX_SIZE`) is only enforced when the `allowTvmSelfdestructRestriction` hard fork is active, and it's checked on a *pre-fetched* index word (`words[words[1]... ]`) rather than inside the extraction helpers themselves: [4](#0-3) [5](#0-4) 

`BatchValidateSign.execute()` wraps the whole `doExecute` in `catch (Throwable t)`, so an `OutOfMemoryError` there is swallowed and converted into a graceful failure: [6](#0-5) 

`ValidateMultiSign.execute()`, however, calls `extractSigArray`/`extractBytesArray` (line 1072-1074) **outside** any local try/catch — the only try/catch in that method starts later, wrapping only the signature-recovery/weight logic: [7](#0-6) 

An `OutOfMemoryError` thrown here propagates uncaught through `Program.callToPrecompiledAddress` and `VM.play()` — whose exception handling only catches `RuntimeException`/`StackOverflowError`/`JVMStackOverFlowException`/`OutOfTimeException`, not general `Error`/`OutOfMemoryError`: [8](#0-7) 

It is ultimately only caught much further up the call stack, at `VMActuator`'s generic `catch (Throwable e)`: [9](#0-8) 

### Impact Explanation
Any account can broadcast a `TriggerSmartContract` (or `TriggerConstantContract`) transaction that `CALL`s the `ValidateMultiSign` precompiled address with crafted ABI data setting the signature-array-length word (referenced via `words[3]`) to a very large value (e.g., `0x7FFFFFFF`). Because `extractSigArray`/`extractBytesArray` attempt `new byte[len][]` before any size cap applies (the cap only exists conditionally on `allowTvmSelfdestructRestriction` and is computed redundantly, not enforced inside the helper), this can trigger a multi-gigabyte allocation attempt and an `OutOfMemoryError`. While this specific error is eventually caught by `VMActuator`'s `Throwable` handler and converted into a failed transaction, the act of attempting a huge heap allocation stresses the whole node's JVM heap and GC, and can be repeated cheaply across many concurrent transactions/threads, degrading or crashing the node process — a memory-exhaustion denial-of-service analogous to the "stack overflow and/or CHECK-fail based denial of service" described in the TensorFlow advisory, where an unvalidated dimension/length argument from untrusted input directly drives an unsafe operation.

### Likelihood Explanation
Likelihood is high for triggering the underlying condition: the precompile is invoked via a normal signed transaction with no special privilege, and the vulnerable length field is fully attacker-controlled ABI-encoded call data. The severity of the ultimate impact (node-wide OOM vs. a merely failed transaction) depends on JVM heap headroom at the time and whether `allowTvmSelfdestructRestriction` has been activated on the running network, since that hard fork gate is the only thing standing between this and a hard crash/instability event.

### Recommendation
Enforce the `MAX_SIZE` bound unconditionally, inside `extractBytesArray`/`extractSigArray`/`extractBytes32Array` themselves (validate `len` against `MAX_SIZE` and against remaining `words.length` before allocating), regardless of `allowTvmSelfdestructRestriction`, and wrap `ValidateMultiSign.execute()` in the same top-level `catch (Throwable t)` pattern already used by `BatchValidateSign.execute()` so any unexpected `Error` degrades gracefully instead of propagating.

### Proof of Concept
1. Deploy any contract, or use `TriggerConstantContract`, calling the `ValidateMultiSign` precompiled contract address.
2. Craft the ABI call data such that the word normally read as `words[3]` (used as `offset = words[3].intValueSafe() / WORD_SIZE`) points at a word set to `0xFFFFFFFF...` (interpreted via `intValueSafe()` as `Integer.MAX_VALUE`) as the array-length field consumed by `extractSigArray`/`extractBytesArray`.
3. Send the transaction against a node where `allowTvmSelfdestructRestriction` has not been activated (or craft an offset combination the redundant pre-check doesn't cover).
4. Observe the node attempt `new byte[Integer.MAX_VALUE][]`, causing an `OutOfMemoryError` during precompile execution, exercisable repeatedly and cheaply from any account.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
