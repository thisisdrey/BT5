### Title
`ft_resolve_withdraw` double-credits a token whose custom FT contract returns non-empty data on a successful `ft_transfer`, refunding an amount that already left the Verifier - (File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs)

### Summary
`ft_resolve_withdraw`'s non-`is_call` branch collapses "promise failed" and "promise succeeded but returned non-empty bytes" into a single `Err` case from `promise_result_checked_void`, treating both as a total failure and refunding the full withdrawn amount internally. An attacker who deploys and controls the `token` FT contract can implement `ft_transfer` to perform the real balance-affecting transfer while returning non-empty output, causing the Verifier to both lose the real tokens externally and re-credit the same amount internally.

### Finding Description
The broken binding: `token_balances_debited(token, owner) == real_tokens_transferred_out(token) + refund_recredited(token, owner)` must hold as `amount == amount + 0`. The bug makes it `amount == amount + amount`.

Path: `ft_withdraw` → `internal_ft_withdraw` (debits `amount` from `owner_id`'s internal balance via `self.withdraw`) → `Self::do_ft_withdraw` schedules `ext_ft_core::ft_transfer(receiver_id, amount, memo)` on the attacker-controlled `token` contract [1](#0-0)  → callback `ft_resolve_withdraw` inspects the promise result: [2](#0-1) 

`promise_result_checked_void` is defined as: [3](#0-2) 

`env::promise_result_checked(result_idx, 0)` enforces that the returned buffer length is `<= max_len` (here `0`). If the promise executed successfully (status `Successful`, i.e. the real `ft_transfer` logic already ran and moved tokens) but the callee returns any non-empty bytes (even one byte), `env::promise_result_checked` returns an `Err`, which is indistinguishable in `ft_resolve_withdraw` from an actual transfer failure. `debug_assert!(data.is_empty())` is compiled out in release builds and cannot catch this case anyway since `Ok` is only reached when data is already empty.

Because the attacker fully controls the `token` account (deploy/upgrade rights, per the allowed attacker profile), they can write a raw exported `ft_transfer` that performs the real internal transfer bookkeeping of their own FT contract (so the external call is genuinely "successful" and real tokens leave that contract to `receiver_id`) and then calls `env::value_return` with non-empty bytes. `ft_resolve_withdraw` then sees `promise_result_checked_void(0).is_ok() == false`, sets `used = 0`, `refund = amount.0`, and calls `self.deposit(sender_id, [(token, amount)], ...)`, re-crediting the owner's internal balance by the full amount that was already transferred out for real.

No existing guard prevents this: `#[private]` only restricts external callers of `ft_resolve_withdraw`, not the logic bug itself; there is no distinction in the void-check path between "failed" and "succeeded with unexpected non-empty output."

### Impact Explanation
The Verifier's internal `token_balances` ledger for the exploited `TokenId` is inflated by `amount` relative to the actual FT balance the Verifier custodies for that token, matching the Critical category "a refund or resolver credit that does not match what failed to settle." The attacker can repeat this for every withdraw call against their own FT contract, accumulating internal balance for that `TokenId` without ever losing it, while genuinely draining whatever real reserve of that token the Verifier holds (including reserves contributed by other users who deposited the same FT contract's token believing it behaved as a standard NEP-141 token). If other users hold real balances of that same `TokenId`, their eventual withdrawals can fail or the Verifier becomes insolvent for that asset.

### Likelihood Explanation
The attacker needs only to: (1) deploy their own FT contract with a custom `ft_transfer` that performs a real transfer but returns non-empty bytes, (2) deposit and hold a Verifier balance for that `TokenId`, and (3) call `ft_withdraw` with `msg=None`. All of this is within the stated attacker capabilities (deploy/control own FT contracts, hold own Verifier balances, sign own transactions), requires no privileged role, and is fully repeatable per token/account.

### Recommendation
Distinguish a genuinely failed promise from a successful promise with unexpected non-empty output in `promise_result_checked_void`/`ft_resolve_withdraw`: only treat the outcome as "used = 0" when the promise status itself indicates failure (`PromiseResult::Failed`), not when the length check on an otherwise-successful result trips. Alternatively, check `env::promise_result(idx)` status directly instead of relying on a length-bounded `Err` to signal failure, and separately reject/ignore unexpected non-empty payloads without treating them as a transfer failure eligible for full refund.

### Proof of Concept
`near-workspaces` sandbox test plan:
1. Deploy a stub FT contract at `evil_token` whose `ft_transfer` decrements the caller's real internal ledger for `receiver_id`/sender (simulating a genuine transfer) then calls `env::value_return(&[0u8; 100])` before returning.
2. Deposit `amount` of `evil_token` into the Verifier for `owner_id` (real transfer in, `token_balances[evil_token][owner_id] += amount`).
3. Call `ft_withdraw(token=evil_token, receiver_id=owner_id_alt, amount, memo=None, msg=None)`.
4. Assert:
   - The real balance moved out of `evil_token` contract's custody (external state changed by `amount`).
   - Post-call, `token_balances[evil_token][owner_id] == amount` again (refunded), i.e. `self.deposit` was invoked with `refund = amount.0`.
   - Assert the equality `internal_ledger_amount(evil_token) > real_verifier_held_balance(evil_token)`, demonstrating the double count/drain described.

/// Returns `Ok(())` if the promise at `result_idx` succeeded with an empty result.
/// This is the expected outcome for void-returning cross-contract calls
/// (e.g. `ft_transfer`, `nft_transfer`, `mt_batch_transfer`).
#[inline]
pub fn promise_result_checked_void(result_idx: u64) -> PromiseResult<()> {
    let data = env::promise_result_checked(result_idx, 0)?;
    debug_assert!(data.is_empty());
    Ok(())
}
