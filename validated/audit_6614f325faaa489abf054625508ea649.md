### Title
Remote panic via crafted shadow-flagged `NakamotoBlock` failing burnchain validation - (File: `stackslib/src/chainstate/nakamoto/mod.rs`, `stackslib/src/chainstate/nakamoto/shadow.rs`)

### Summary
`NakamotoChainState::accept_block` treats any block whose header version has the high bit set (`NakamotoBlockHeader::is_shadow_block()`) as a "shadow block" and routes it into `validate_shadow_nakamoto_block_burnchain`, unwrapping the result with a `panic!("Unacceptable shadow Nakamoto block")` on failure. Shadow blocks are only supposed to be created by offline admin tooling (`process_shadow_block`/`add_shadow_block`) and never travel over the network, but the version-bit check that dispatches into this code path is purely a header-field check with no authentication, so a remote peer can trigger the failure branch with an ordinary crafted block.

### Finding Description
`NakamotoBlockHeader::is_shadow_block()` simply checks `self.version & 0x80 != 0` [1](#0-0) , a wire-controlled field with no cryptographic binding to any admin/SIP process. `validate_shadow_nakamoto_block_burnchain` first requires the block to already be present in the staging DB with `obtain_method = Shadow` via `has_shadow_nakamoto_block_with_index_hash` [2](#0-1) ; that flag is only ever set by `NakamotoStagingBlocksTx::add_shadow_block`, called exclusively from the offline, explicitly-marked "DO NOT RUN ON A RUNNING NODE" function `process_shadow_block` [3](#0-2) . The normal P2P/HTTP block-relay path (`net/relay.rs`) never sets `obtain_method = Shadow`, so any block arriving with the shadow version bit set via the network is guaranteed to fail this "must already be stored" check and return `Err(ChainstateError::InvalidStacksBlock("Shadow block must already be stored"))`, or, if that somehow passed, fail later burnchain linkage checks in `validate_shadow_against_burnchain`/`validate_nakamoto_tenure_snapshot`. Per the audit target, `accept_block` calls `Self::validate_shadow_nakamoto_block_burnchain(...).unwrap_or_else(|e| { ...; panic!("Unacceptable shadow Nakamoto block") })` — confirmed by the literal string appearing twice in `stackslib/src/chainstate/nakamoto/mod.rs` — so any `Err` returned from this validator (including the trivially-triggerable "not already stored" error) results in an unconditional process panic. Because `is_shadow_block()` requires only a single header bit, and this header travels unauthenticated through `NakamotoBlocksData` P2P messages and HTTP block uploads to `Relayer::process_new_nakamoto_block_ext` → `NakamotoChainState::accept_block`, an attacker with no privileged role can reach this panic with one crafted block.

### Impact Explanation
A single crafted `NakamotoBlock` with the version high bit set and mismatched/absent burnchain linkage crashes any node that accepts and processes it, matching the "Critical — remote crash/unauthenticated DoS from few messages" category. The crash is deterministic and repeatable against any reachable Nakamoto-epoch node (P2P or HTTP block-upload endpoints), and can be broadcast to affect multiple nodes simultaneously via gossip relay.

### Likelihood Explanation
Preconditions are minimal: the target node must be running in the Nakamoto epoch and reachable on P2P or the block-upload HTTP endpoint — no secret, peer key, or StackerDB slot ownership is required. The attacker only needs to flip one bit in a `NakamotoBlockHeader.version` field and submit an otherwise-plausible block; no proof-of-work, signer signature, or burnchain state needs to be forged to *reach* the panic, since the "not already stored" check fails immediately and deterministically for any externally-submitted block.

### Recommendation
Do not dispatch network-received blocks into shadow-block validation/panic logic at all. `accept_block` should treat `is_shadow_block()==true` blocks arriving from `process_new_nakamoto_block`/relay paths as invalid input to be rejected with an `Err` (e.g., `InvalidStacksBlock("Shadow blocks are not accepted over the network")`) before ever calling `validate_shadow_nakamoto_block_burnchain`, reserving the panicking assertion only for the internal/offline shadow-block insertion tooling path where invariants are guaranteed by construction, not by attacker-controlled header bits.

### Proof of Concept
Rust test in `stackslib::chainstate::nakamoto` (or `net::relay` tests):
1. Build a well-formed `NakamotoBlock` (satisfying `is_wellformed_tenure_start_block`) with valid signatures/merkle root but with `header.version |= 0x80` so `is_shadow_block()` returns `true`.
2. Do **not** call `process_shadow_block`/`add_shadow_block` (simulating that it never touched the offline shadow tooling), so `has_shadow_nakamoto_block_with_index_hash` is `false`.
3. Feed the block through `Relayer::process_new_nakamoto_block_ext` (or directly call `NakamotoChainState::accept_block`) as if received via `NakamotoBlocksData`.
4. Observe/assert: instead of returning `Err(ChainstateError::InvalidStacksBlock(..))`, the call panics with `"Unacceptable shadow Nakamoto block"`, crashing the test process — demonstrating the reachable remote-crash condition. The fix should make this assertion instead check for a clean `Err` return.
