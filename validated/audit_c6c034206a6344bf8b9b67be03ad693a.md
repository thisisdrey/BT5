## Title
Unconditional relayer fee payout in the eth-implicit wallet contract before target/relayer validation completes, combined with no nonce advance on that failure path, allows unlimited fee-draining replay — (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

## Summary
`WalletContract::rlp_execute` performs a two-part operation on every emulated Ethereum base-token / ERC-20 transfer: (1) an unconditional NEAR transfer of the user-specified `fee` to whoever called `rlp_execute` (the "relayer"), and (2) the actual action execution, which for `EOABaseTokenTransfer` targets going through the address registrar is deferred behind an async cross-contract validation (`address_check_callback`). Leg (1) has no dependency on leg (2) succeeding, and leg (2)'s failure path (a "faulty relayer" target) intentionally skips incrementing the nonce, so the exact same signed transaction can be resubmitted indefinitely by any caller, extracting `fee` every time without the intended action ever executing.

## Finding Description
`inner_rlp_execute` unconditionally schedules the fee payment to the caller (`predecessor_account_id`) as soon as parsing succeeds, independent of the outcome of the actual action: [1](#0-0) 

This fee-transfer promise batch is queued regardless of which `TransactionKind` follows. For `EOABaseTokenTransfer { address_check: Some(address), .. }`, the nonce is deliberately *not* incremented at this point: [2](#0-1) 

The actual action is gated behind an async call to the address registrar to determine whether the relayer used a "raw address" `target` when a real named account is actually registered for that address (i.e., relayer misbehavior): [3](#0-2) 

In `address_check_callback`, if the address turns out to be registered (an "invalid target" from a faulty relayer) and the caller is not using the wallet's own access key, the call simply returns an error **without ever incrementing the nonce**: [4](#0-3) 

Because `rlp_execute` is a public, unauthenticated method — any NEAR account can call it with any `target`/`tx_bytes_b64` pair, this being the explicit design so that "any relayer" can permissionlessly submit a user's signed transaction: [5](#0-4) 

An attacker who has observed a user's signed Ethereum-style transaction (which, by design, is meant to be shareable with arbitrary relayers) can repeatedly call `rlp_execute(target, tx_bytes_b64)` with `target` set to the raw eth-implicit address form of an account that is *also* registered in the address registrar. Each call:
1. Passes `validate_tx_relayer_data`'s target check (`is_valid_target`) because `target` legitimately matches the address form: [6](#0-5) 
2. Immediately fires the fee transfer to the attacker (the caller/predecessor).
3. Resolves in `address_check_callback` to "Invalid target" (since the address is registered), which does not increment the nonce and never executes the underlying user action.

Because the nonce is unchanged, step 1–3 can be repeated indefinitely with the exact same `tx_bytes_b64`/`target` pair, draining the wallet's NEAR balance one `fee` payment at a time, with the intended action never being performed.

## Impact Explanation
This is a concrete theft-of-funds vulnerability: the wallet contract's own NEAR balance is transferred out to an unprivileged caller via a self-contained, repeatable exploit that requires no special permission, access key, or the cooperation of an honest relayer — only knowledge of a validly signed transaction that (per the protocol's own design intent) is meant to be shared with arbitrary relayers. The drain is bounded only by the wallet's balance and the `fee` value set in the transaction, and can be executed to zero out the account.

## Likelihood Explanation
The precondition (a signed Ethereum transaction whose `to` address is also independently registered in the address registrar) is realistic: address-registrar registration and eth-wallet usage are both first-class, user-driven behaviors, so it is plausible for a transaction's target to satisfy both forms. The exploit requires no validator/relayer collusion, no privileged role, and no race condition — it is a straightforward sequential replay enabled purely by the nonce-skip design combined with the unconditional up-front fee payment.

## Recommendation
- Do not send the relayer `fee` refund until after the action (and, where applicable, the address-check validation) has succeeded — i.e., move the fee-payment promise into the success branch of `rlp_execute_callback`/`address_check_callback`, or make it part of the same promise batch/callback chain that also performs the real action, so it can never be dispatched independently of a successful (or at least attempted) execution.
- Alternatively, if the fee must be paid up front for UX reasons (to bootstrap relayers), ensure the nonce is always incremented once the fee has been paid, closing the replay window regardless of whether the relayer's target turns out to be invalid.

## Proof of Concept
1. User signs an Ethereum-style transaction with `to = 0xAAAA...` (their own eth-implicit-style address form), a non-zero `max_fee_per_gas`/`gas_limit` (hence non-zero `fee`), and gives the base64 blob to a relayer for submission — this is the normal, documented relaying flow.
2. `0xAAAA...` corresponds to an account that is *also* registered under a named account (e.g., `alice.near`) in the `AddressRegistrar` contract, see `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`.
3. Attacker (any NEAR account, no access key needed) calls `rlp_execute(target = "0xaaaa...", tx_bytes_b64)` on the wallet contract, where `target` is the eth-implicit form rather than `alice.near`.
4. `validate_tx_relayer_data` accepts this target (matches the address form). The fee-refund promise to the attacker's account fires immediately.
5. `address_check_callback` finds `alice.near` is registered for that address, and since `env::signer_account_id() != current_account_id`, it returns an `ExecuteResponse::error` without incrementing `self.nonce`.
6. Attacker repeats step 3 with the identical `target`/`tx_bytes_b64` any number of times, collecting `fee` each time, draining the wallet's NEAR balance, while the user's intended action is never executed.
