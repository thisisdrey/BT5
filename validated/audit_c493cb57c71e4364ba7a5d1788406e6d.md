### Title
Quarantined objects are packed into the repository via `git-pack-objects` without object validity verification, allowing malformed/invalid objects to be committed to the permanent object store on every write transaction - ([File: internal/gitaly/storage/storagemgr/partition/transaction_manager.go])

### Summary
`TransactionManager.packObjects` walks every reference-reachable object that a client wrote into its per-transaction quarantine directory (populated by an ordinary user's push, fetch, `UserCommitFiles`, `UserMergeBranch`, etc.) and re-packs it straight into the WAL entry that will be applied to the repository's real object database. The code that does this explicitly documents, in its own comment, that the packed objects are never checked for validity before being trusted and merged into the repository.

### Finding Description
`packObjects` is the code path that turns everything a client places in the quarantine directory into a `git-index-pack`'d, WAL-committed pack file: [1](#0-0) 

The comment on the function states in-repo:

> "The packed objects are not yet checked for validity. See the following issue for more details on this: https://gitlab.com/gitlab-org/gitaly/-/issues/5779"

The walk itself is done with `git rev-list --objects --missing=print --stdin`: [2](#0-1) 

`rev-list --objects` only walks the object *graph* (parsing trees/commits/tags to discover child OIDs); it does not perform `git-fsck`-style structural/content validation of blob or tree data, nor does it verify that object types match what a tree/commit claims they are. Objects found in the quarantine directory are then fed straight to `pack-objects`/`index-pack` and written into the WAL, and ultimately migrated into the repository's real object store on commit: [3](#0-2) [4](#0-3) 

This is directly analogous to the WildCredit bug class: a value/trust-bearing operation (`packObjects` committing objects permanently, analogous to `uniClaimDeposit` minting shares) is performed on unverified/unsettled input (raw quarantined bytes, analogous to un-collected "parked" liquidity) before any validity check equivalent to "accrue" is applied. In `git-receive-pack`'s traditional flow this gap is normally covered by `receive.fsckObjects`/connectivity checks run by native Git; here Gitaly's own transaction manager re-implements object packing on top of `rev-list`/`pack-objects` without an equivalent fsck step, and the maintainers' own comment confirms the check is missing.

### Impact Explanation
Because the object walk/pack step has no fsck-equivalent validation, a malicious or buggy client (an ordinary authenticated pusher, e.g. through `SSHReceivePack`/`ReceivePack`, `UserCommitFiles`, or any RPC that stages objects in a quarantine directory and then updates references) can smuggle malformed Git objects into the permanent, WAL-committed object database of a repository:
- Corrupted or type-confused objects (e.g. a "tree" object with malformed entries, or a commit/tag with malformed headers) that would normally be rejected by `git fsck`/`--strict` checks during `unpack-objects`/`index-pack` in stock Git receive-pack.
- Because these objects become part of the permanently packed, WAL-durable state, later readers (browsing, archive export, `git gc`, replication) can encounter corrupted or unexpected object graphs, potentially causing crashes, undefined behavior in downstream Git tooling, or repository corruption that is difficult to repair since it's now baked into a committed WAL entry.
- This is a DoS/data-integrity issue in a `RPC-handler resource limit`/`storage` sense: an unprivileged pushing user can degrade or corrupt the repository state of a partition (or, if the partition is shared with an object pool, other pool members that share the object directory via alternates), which the maintainers themselves acknowledge is unresolved (tracked in gitlab-org/gitaly#5779).

### Likelihood Explanation
High likelihood of reachability: `packObjects` runs on essentially every write transaction that includes reference updates with quarantined packs (ordinary pushes, `UserCommitFiles`, merges, etc.), which is the primary, most-used code path in Gitaly's transaction manager. The lack of validation is not a hypothetical edge case — it is called out explicitly in the source comment as a known, unresolved gap, and the surrounding test-suite (`transaction_manager_test.go`) exercises normal object flows but does not appear to assert fsck-style rejection of malformed object content, only missing-dependency detection.

### Recommendation
Add an explicit object validity check (equivalent to `git index-pack --strict` / `git fsck --no-dangling` connectivity+content checks, or Git's `receive.fsckObjects`) over the objects discovered by `WalkObjects`/gathered by `ListObjects` before they are packed and staged into the WAL entry in `packObjects`. Reject the transaction if any object fails structural/type validation, mirroring the protection that native `git-receive-pack` provides via `fsckObjects`, so that unverified client-supplied bytes cannot become part of the permanently committed object store.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation depends on constructing a Git object (blob/tree/commit/tag) that is byte-valid enough to satisfy `rev-list --objects`'s graph traversal (i.e., parses enough to be included, with correct type headers and hashes) but is either (a) rejected by `git fsck --strict`, or (b) semantically malformed in a way current Git tooling mishandles. The exact conditions and impact would require experimentation with `git hash-object`/`git mktree`/`git commit-tree` to hand-craft such an object and pushing it through `git-receive-pack` against a transaction-enabled Gitaly instance, then confirming it is persisted into the packed WAL/repository state and that no `packObjects`/`index-pack` failure occurs. This step could not be executed in this read-only analysis; a background engineering session with test-harness access would be needed to confirm the precise blast radius (e.g., whether `git index-pack` performs enough of its own checks to already block malformed objects, narrowing this to a documented-but-non-exploitable gap).

			if !update.IsRegularUpdate() {
				// We don't have to worry about symrefs here.
				continue

			if update.NewOID == objectHash.ZeroOID {
				// Reference deletions can't introduce new objects so ignore them.
				continue

// WalkObjects walks the object graph starting from heads and writes to the output the objects it
// sees. Objects that are encountered during the walk and exist in the object database are written
// out as `<oid> <path>\n` with the `<path>` being sometimes present if applicable. Objects that
// were encountered during the walk but do not exist in the object database are written out
// as `?<oid>\n`.
func (repo *Repo) WalkObjects(ctx context.Context, heads io.Reader, output io.Writer) error {
	var stderr bytes.Buffer
	if err := repo.ExecAndWait(ctx,
		gitcmd.Command{
			Name: "rev-list",
			Flags: []gitcmd.Option{
				gitcmd.Flag{Name: "--objects"},
				gitcmd.Flag{Name: "--missing=print"},
				gitcmd.Flag{Name: "--stdin"},
			},
		},
		gitcmd.WithStdin(heads),
		gitcmd.WithStdout(output),
		gitcmd.WithStderr(&stderr),
	); err != nil {
		return structerr.New("rev-list: %w", err).WithMetadata("stderr", stderr.String())
	}

	return nil
}
