### Title
`remove_account` fails to purge account-scoped receipt-resolution state (PostponedReceipt/PendingDataCount/ReceivedData/PromiseYield*/Yield↔Data mappings), allowing orphaned receipts to resurrect and execute against a re-created account - (File: core/store/src/utils/mod.rs)

### Summary
`TrieKey` defines eight variants that are explicitly account-scoped (`PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`), as enumerated in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`. `remove_account` only removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows, leaving the other six/eight receipt-bookkeeping key types behind in the trie under the deleted account's prefix.

### Finding Description
`core/primitives/src/trie_key.rs` lists `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, `DATA_ID_TO_YIELD_ID` inside `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` [1](#0-0) , confirming these trie keys are keyed by `account_id` and thus live physically under the account's storage prefix in the trie.

`remove_account` in `core/store/src/utils/mod.rs` is the single routine invoked by `DeleteAccountAction` handling to purge an account's trie footprint. It calls `state_update.remove` only for `TrieKey::Account`, `TrieKey::ContractCode`, and iterates/removes `TrieKey::AccessKey`/`TrieKey::GasKeyNonce` via `get_raw_prefix_for_access_keys`, then iterates/removes `TrieKey::ContractData` via `get_raw_prefix_for_contract_data` [2](#0-1) . None of the eight account-scoped receipt-resolution key types are enumerated, iterated, or removed anywhere in this function.

Because a self-targeted `promise_then` `FunctionCall` with an unmet `input_data_id` causes `process_action_receipt` to persist a `PostponedReceipt` and a `PendingDataCount` entry keyed by the receiving account (`victim.near`), deleting `victim.near` via `DeleteAccountAction` does not clear these rows. If any signer later submits `CreateAccountAction` to re-create `victim.near`, the orphaned trie rows remain associated with the new account. Once the attacker (who still controls/knows the pending `data_id`) supplies the missing `DataReceipt`, the receipt-processing logic resolves the pending count and dispatches the previously postponed receipt for execution against the newly created account, running actions the new account owner never authorized.

### Impact Explanation
This is an authorization-escalation bug: actions queued under a deleted account's identity execute against a distinct, newly created account that has different ownership/keys, violating the invariant that state is scoped exclusively to the account instance that authorized it. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are fully within reach of an unprivileged actor: the attacker only needs to own `victim.near`, submit a self-targeted `FunctionCall` receipt with a promise dependency (`promise_then`) that is never resolved, then delete their own account. The final trigger (recreation of `victim.near`) requires a third party (any signer) to submit an ordinary `CreateAccountAction`, and the account-name-reuse pattern (delete then recreate) is a normal, permitted operation with no additional protocol restriction preventing it. No validator/node privilege is required.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also iterate and remove all account-scoped receipt-resolution trie keys — `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` — for the given `account_id`, using the same raw-prefix iteration pattern already used for access keys and contract data, before allowing `CreateAccountAction` to reuse the account name; alternatively, forbid account deletion while any postponed/yielded receipts remain pending for that account.

### Proof of Concept
1. Integration test in `core/store` (or a new test module) that: creates an account, writes one instance of each of the 8 account-scoped `TrieKey` variants plus `Account`/`ContractCode`/`AccessKey`/`ContractData` for `victim.near`, calls `remove_account`, then iterates `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` prefixes for `victim.near` and asserts the resulting set is empty — expect it to fail, showing the 8 keys remain.
2. `runtime/runtime` apply-test (`runtime/runtime/src/tests` or `runtime/runtime/src/lib.rs` test module): submit a `FunctionCall` promise_then receipt from `victim.near` with an unmet `input_data_id` (triggering `set_postponed_receipt`/`PendingDataCount`), then a `DeleteAccountAction` for `victim.near`, then a `CreateAccountAction` recreating `victim.near`, then deliver the missing `DataReceipt`; assert that the previously postponed receipt still executes against the recreated account (demonstrating the bug) versus the expected behavior of the postponed receipt being absent/discarded after deletion.

```rust
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
```
