### Title
Unhardened bancor-style pricing in TRX/TRC10 Exchange uses lossy double-precision math, allowing value extraction from Exchange pools - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The external report describes a fixed/unchecked exchange-rate flaw in a mint function that let an attacker convert ETH into a BTC-pegged asset at an incorrect rate, extracting far more value than deposited. The closest reachable analog in java-tron is the `ExchangeTransactionActuator` → `ExchangeCapsule.transaction()` → `ExchangeProcessor.exchange()` path, which by default computes the bancor-relay exchange rate using `double`/`Math.pow` arithmetic instead of exact `BigDecimal` math. This is directly reachable by any unprivileged account broadcasting an `ExchangeTransactionContract`.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [1](#0-0) , which selects between two `Processor` implementations depending on the `allowHardenExchangeCalculation` dynamic property: `SafeExchangeProcessor` (exact `BigDecimal` math) when hardened, or the legacy `ExchangeProcessor` (floating-point `double` math) otherwise [2](#0-1) .

The legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the bancor-formula relay/output amounts using `double` arithmetic and `Math.pow`, then truncate to `long` [3](#0-2) . The project's own test suite explicitly demonstrates that this legacy path produces *different* results from the exact `BigDecimal`-based `SafeExchangeProcessor` for the same inputs (`Assert.assertNotEquals(anotherTokenQuant, result)` when comparing the unhardened vs. hardened/strict results) [4](#0-3) , confirming the double-precision path is a lossy approximation of the intended exact formula. The introduction of `SafeExchangeProcessor`, `StrictMathWrapper`, and the `ALLOW_HARDEN_EXCHANGE_CALCULATION` governance proposal (activated only via committee proposal after fork `VERSION_4_8_2`) indicates this floating-point precision defect in bancor pricing was a recognized problem requiring a hardening mechanism [5](#0-4) . Until this proposal is actively enabled on a given chain, every `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` execution against a legacy (`ExchangeStore`) or `ExchangeV2Store` pool is priced using this imprecise double-based path, allowing an attacker who structures trade sizes/pool states to obtain a systematically favorable `buyTokenQuant` versus what the true bancor formula would yield — extracting more of the counter-asset from the pool than economically justified, directly analogous to the Bedrock `mint()` bug where a broken/approximate pricing formula let ETH be exchanged 1:1 for a much more valuable BTC-pegged asset.

### Impact Explanation
Any account can call `exchangetransaction`/`exchangeinject`/`exchangewithdraw` against any existing token exchange pool. If the double-precision pricing diverges favorably for a chosen trade size (as the test suite proves it can diverge from the exact formula), a caller can repeatedly extract disproportionate quantities of the paired token from the pool, i.e., theft of funds from other exchange participants/liquidity, without any privileged access — a direct funds-theft impact reachable via a single signed transaction.

### Likelihood Explanation
The vulnerable code path (`ExchangeProcessor`, unhardened) is the *default* unless the `ALLOW_HARDEN_EXCHANGE_CALCULATION` committee proposal has been activated on the network, and the actuator is reachable by any funded account without special permissions via `wallet/exchangetransaction`. However, exploitability depends on identifying specific pool-balance/trade-size combinations where the double-precision drift is large enough to be profitable after fees, which requires precise computation but is not preventable by protocol-level access control.

### Recommendation
Ensure `ALLOW_HARDEN_EXCHANGE_CALCULATION` (i.e., routing through `SafeExchangeProcessor`'s `BigDecimal`-based math) is unconditionally enforced for all exchange arithmetic rather than gated behind an opt-in governance proposal, or replace the legacy `ExchangeProcessor` double-based implementation entirely so no chain configuration can leave the lossy floating-point pricing path active. Audit historical exchange pool states for evidence of value extraction attributable to the floating-point pricing divergence.

### Proof of Concept
Not independently reproducible from the index alone — reproduction requires deriving a concrete `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` triple where `ExchangeProcessor.exchange()` yields a materially larger output than `SafeExchangeProcessor.exchange()` for the same inputs (the test file already demonstrates that such divergences exist, e.g. via `testStrictMath`'s dataset, but does not quantify the profitable magnitude) [6](#0-5) . A background Devin session with code execution would be needed to brute-force pool parameters and confirm an economically exploitable divergence and craft the corresponding `ExchangeTransactionContract` sequence.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private void testAllowHardenExchangeCalculationProposal() {
    long code = ProposalType.ALLOW_HARDEN_EXCHANGE_CALCULATION.getCode();
    ThrowingRunnable proposeZero = () -> ProposalUtil.validator(dynamicPropertiesStore, forkUtils,
        code, 0);
    ThrowingRunnable proposeOne = () -> ProposalUtil.validator(dynamicPropertiesStore, forkUtils,
        code, 1);
    ThrowingRunnable proposeTwo = () -> ProposalUtil.validator(dynamicPropertiesStore, forkUtils,
        code, 2);

    byte[] stats = new byte[27];
    forkUtils.getManager().getDynamicPropertiesStore()
        .statsByVersion(ForkBlockVersionEnum.VERSION_4_8_1.getValue(), stats);
    long maintenanceTimeInterval = forkUtils.getManager().getDynamicPropertiesStore()
        .getMaintenanceTimeInterval();
    long hardForkTime =
        ((ForkBlockVersionEnum.VERSION_4_8_2.getHardForkTime() - 1) / maintenanceTimeInterval + 1)
            * maintenanceTimeInterval;
    forkUtils.getManager().getDynamicPropertiesStore()
        .saveLatestBlockHeaderTimestamp(hardForkTime - 1);

    // 1) before fork 4.8.2 -> rejected
    ContractValidateException thrown = assertThrows(ContractValidateException.class, proposeOne);
    assertEquals("Bad chain parameter id [ALLOW_HARDEN_EXCHANGE_CALCULATION]",
        thrown.getMessage());

    forkUtils.getManager().getDynamicPropertiesStore()
        .saveLatestBlockHeaderTimestamp(hardForkTime + 1);
    Arrays.fill(stats, (byte) 1);
    forkUtils.getManager().getDynamicPropertiesStore()
        .statsByVersion(ForkBlockVersionEnum.VERSION_4_8_2.getValue(), stats);

    // 2) value not in {0, 1} -> rejected
    thrown = assertThrows(ContractValidateException.class, proposeTwo);
    assertEquals("This value[ALLOW_HARDEN_EXCHANGE_CALCULATION] is only allowed to be 0 or 1",
        thrown.getMessage());

    // 3) current value is 0 (default), proposing 0 again -> rejected
    thrown = assertThrows(ContractValidateException.class, proposeZero);
    assertEquals("[ALLOW_HARDEN_EXCHANGE_CALCULATION] has been set to 0, no need to propose again",
        thrown.getMessage());
