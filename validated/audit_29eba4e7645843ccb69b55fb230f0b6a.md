### Title
First-touch of a newly activated reward token accrues `balance * INITIAL_INDEX` reward to pre-existing holders - ([File: contracts/RewardsDistributor.sol])

### Summary
`RewardsDistributor._calculateTokenDelta` treats a missing per-account index (`accountIndexOf[token][account] == 0`) as "index zero" instead of the initial index whenever the token's global index is still exactly `INITIAL_INDEX` (1e18). The existing fallback only corrects this when `_tokenIndex > INITIAL_INDEX`, so any account holding a `DepositToken`/`DebtToken` balance at the moment the governor activates a reward speed can claim a delta equal to their full token balance before a single second of accrual has passed. This is an index/offset accounting error of the same class as the CVE-2019-7310 signedness bug: a boundary value is interpreted with the wrong semantics, producing an out-of-range result.

### Finding Description
In `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`):

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When the governor calls `updateTokenSpeed`/`updateTokenSpeeds` (or the keeper calls `syncTokenSpeed`) for a token for the first time, `_updateTokenSpeed` initializes `tokenStates[token_] = TokenState({index: INITIAL_INDEX, ...})` (`contracts/RewardsDistributor.sol:296-299`). At that moment `_tokenIndex == INITIAL_INDEX`, so the `> INITIAL_INDEX` fallback is skipped. For any account that already holds the token but has never been index-updated (`accountIndexOf == 0`), `_deltaIndex = 1e18 - 0 = 1e18`, and `wadMul(balance, 1e18) = balance`. The account's `tokensAccruedOf` is credited one reward-token unit per deposit/debt-token unit held, with zero elapsed accrual time.

### Impact Explanation
The first state-changing touch of the victim token by (or on behalf of) such an account — `claimRewards(accounts, tokens)` (public, `accounts_` is caller-chosen), `updateBeforeMintOrBurn`, or `updateBeforeTransfer` (callable by anyone per the natspec on `contracts/RewardsDistributor.sol:173-180`) — credits the inflated delta, and `claimRewards` pays it out via `_transferRewardIfEnoughTokens` up to the distributor's reward-token balance (`contracts/RewardsDistributor.sol:248-256`). An attacker can:

1. Deposit/mint `DepositToken` (or borrow to hold `DebtToken`) before the reward speed is activated — depositing does not set `accountIndexOf` while `tokenStates.index == 0` (the `index > 0` guard at `contracts/RewardsDistributor.sol:176` skips updates).
2. Wait for the governor/keeper to activate the speed (a routine, public observable action).
3. Call `claimRewards(attacker, [token])` in the same or next block and drain the distributor's reward balance up to `balanceOf(attacker)` reward tokens.

This is direct theft of reward funds that belong to the pool of all holders' accrued yield (theft of unclaimed yield), and it front-runs legitimate accrual. Any holder touched first gains the windfall; rewards for others are drained proportionally.

### Likelihood Explanation
- No privileged role is needed for exploitation; `claimRewards`, `updateBeforeMintOrBurn`, and `updateBeforeTransfer` are all permissionless.
- The only precondition is that the distributor's `rewardToken` balance is nonzero and a speed is activated — a normal, expected operation (the contract exists precisely to distribute rewards, and `syncTokenSpeed` exists to continuously re-activate speeds for Vesper-backed tokens).
- The attacker must hold a token balance at activation time; `DebtToken` balances can be obtained via a borrow with collateral, and `DepositToken` via an ordinary deposit, both unprivileged. Cost is limited to temporarily locking collateral.
- The window is one transaction after speed activation, but nothing prevents the attacker from being the first to call `claimRewards` in the same block (it can even be triggered for the attacker's address by any call path that touches the token first; the attacker controls their own touch).
- Mitigation note: if the distributor's reward balance is lower than the attacker's claim, payout is capped; if it is zero, nothing is stolen — but reward distributions imply a funded distributor.

### Recommendation
Change the fallback condition to `>=` so a zero account index is always normalized before computing the delta:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = _tokenIndex; // or INITIAL_INDEX; both prevent the 1e18 phantom delta
}
```

Setting `_accountIndex = _tokenIndex` is safest: it treats untouched accounts as "joined now," consistent with how `accountIndexOf` is written to the current token index on every update. Additionally, consider initializing `accountIndexOf` eagerly in `updateBeforeMintOrBurn`/`updateBeforeTransfer` even when `tokenStates.index == 0`, so no account can carry a zero index into an activated period.

### Proof of Concept
Hardhat fork-style scenario (against deployed `RewardsDistributor` + `Pool`):

```ts
// 1. Attacker deposits collateral and holds DepositToken before rewards are on.
await depositToken.connect(attacker).mint(attacker.address); // via pool deposit
// accountIndexOf[dToken][attacker] == 0; tokenStates[dToken].index == 0

// 2. Governor (or keeper via syncTokenSpeed) activates the reward speed.
await distributor.connect(governor).updateTokenSpeed(dToken.address, speed);
// tokenStates[dToken].index == INITIAL_INDEX (1e18)

// 3. Attacker claims immediately — no time elapsed.
const bal = await dToken.balanceOf(attacker.address);
await distributor.claimRewards(attacker.address, [dToken.address]);
// _deltaIndex = 1e18 - 0 => _tokensDelta = wadMul(bal, 1e18) = bal
// tokensAccruedOf[attacker] += bal; transferred MET up to distributor balance
```

Expected: `claimable(attacker)` returns ~0 right after activation.
Actual: `claimable(attacker)` returns `balanceOf(attacker)` reward-token units, paid from the distributor's balance on `claimRewards`.
