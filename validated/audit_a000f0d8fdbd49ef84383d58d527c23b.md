### Title
Griefing DoS of `CreateObjectPool` via pre-created target path at a deterministic pool location - ([File: internal/gitaly/repoutil/create.go], [File: internal/git/objectpool/create.go])

### Summary
`CreateObjectPool` (like the reported `swapOutRewardToken`) is guarded by a "target must not already exist" pre-condition. Because object-pool relative paths are deterministically derived (from a sequential/guessable repository ID), an ordinary user who can trigger repository creation can pre-occupy the future pool's path, permanently blocking legitimate pool creation for a repository/fork network with no self-healing recovery path.

### Finding Description
`ObjectPoolService.CreateObjectPool` delegates to `repoutil.Create`, passing the pool's `Repository` message (with `RelativePath` computed from the target project's ID) as the entity to create: [1](#0-0) 

`repoutil.Create` explicitly requires that nothing already exists at the target path before it will proceed, both before and after acquiring the repository lock: [2](#0-1) [3](#0-2) 

The lower-level `objectpool.Create` performs the same style of check on the pool path itself, and the codebase's own test comment acknowledges this is a known weak point: [4](#0-3) [5](#0-4) 

Crucially, object pool relative paths are not random/unpredictable — they are deterministically derived from the (sequential, easily observable/incrementable) repository ID: [6](#0-5) [7](#0-6) 

and `IsPoolRepository`/`IsRailsPoolRepository`/`IsPraefectPoolRepository` only validate that a path *matches the pool naming pattern* — they do not prevent an ordinary repository-creation flow from writing into a path that happens to collide with a not-yet-created pool's future path: [8](#0-7) 

Because object pools are created lazily — the documented lifecycle is "An object pool is created via CreateObjectPool from its primary pool member. Typically this would be the repository that gets forked" — there is a window between a repository/project being provisioned (its ID becoming known/predictable) and the pool actually being created (typically triggered by the first fork): [9](#0-8) 

An attacker who can cause repository creation at an attacker-chosen or predicted relative path (e.g., via project creation flows that ultimately call `CreateRepository`, which performs the identical existence check) can pre-populate the exact relative path that will later be computed for a target project's object pool. When the legitimate fork/pool-creation flow later calls `CreateObjectPool`, it fails permanently with a `FailedPrecondition`/`AlreadyExists` error — exactly mirroring the reported bug class where an admin's "swap in a new resource" operation is permanently blocked because an unprivileged party pre-created state at the location the legitimate operation needed to be empty.

### Impact Explanation
This is a griefing/DoS: the attacker gains no direct benefit, but the fork-pool creation for the targeted repository (and thus deduplication of objects across all its forks) is permanently prevented until an operator manually inspects and removes the colliding directory on disk — there is no automatic recovery path exposed via the gRPC API. This can degrade storage efficiency and functionality of the fork network at scale, and is a legitimate handler-level DoS consistent with the "DoS of a handler" acceptance criteria.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to (a) have some means to trigger repository creation at an arbitrary or predictable relative path, and (b) correctly predict/target the specific relative path that will later be derived for a specific project's object pool (repository IDs are sequential and often inferable). This is more constrained than the original report's trivial "call a public function with 1 wei," since gitaly repository creation is normally only reachable through GitLab's application layer rather than directly by arbitrary end-users, but the underlying check-then-act precondition in `repoutil.Create`/`objectpool.Create` is the same unguarded class of bug.

### Recommendation
- Avoid failing permanently on a pre-existing but foreign/empty directory at the computed pool path; instead, validate that any pre-existing path is actually a valid, related repository before treating it as a hard conflict, or reject only if it collides with a *known, legitimately allocated* repository ID.
- Reserve/allocate pool relative paths transactionally at project/pool-member creation time (not lazily at first fork), closing the window during which the path is guessable-but-unclaimed.
- Provide an idempotent/self-healing path for `CreateObjectPool` (e.g., detect and reconcile an empty, non-repository directory at the target path) so that a spurious pre-existing directory does not require manual operator intervention.

### Proof of Concept
Conceptual reproduction (cannot be executed here, but derivable directly from code paths cited above):
1. Observe/predict the sequential repository ID `N` that will be assigned to a target project that is expected to be forked (and thus have an object pool created for it), using `DerivePoolPath(N)` logic: `@cluster/pools/<hash[0]>/<hash[1]>/<N>` (or the Rails equivalent `@pools/xx/yy/<sha256>.git`).
2. Before the legitimate pool-creation flow runs, invoke repository creation (via the same `repoutil.Create` precondition path used by `CreateRepository`) targeting that exact relative path, creating an arbitrary (even empty) directory/repository there.
3. When the legitimate flow later calls `CreateObjectPool` with `ObjectPool.Repository.RelativePath` computed to be the same path, `repoutil.Create`'s pre-check at [10](#0-9)  (or `objectpool.Create`'s check at [4](#0-3) ) returns `AlreadyExists`/`FailedPrecondition`, and the pool can never be created for that repository without manual disk cleanup — mirroring the existing test's own acknowledgment of this behavior at [11](#0-10) .

var (
	// PraefectRootPathPrefix is the root directory for all git repositories.
	PraefectRootPathPrefix = "@cluster"
	// praefectPoolPathPrefix is the prefix directory where Praefect places object pools.
	praefectPoolPathPrefix = filepath.Join(PraefectRootPathPrefix, "pools")
	// praefectRepositoryPathPrefix is the prefix directory where Praefect places repositories.
	praefectRepositoryPathPrefix = filepath.Join(PraefectRootPathPrefix, "repositories")
	// prafectPoolDirRegexp is used to validate object pool directory structure and name as generated by Praefect.
	praefectPoolDirRegexp = regexp.MustCompile(praefectPoolPathPrefix + `/[0-9a-f]{2}/[0-9a-f]{2}/[0-9]+$`)
	// railsPoolDirRegexp is used to validate object pool directory structure and name as generated by Rails.
	railsPoolDirRegexp = regexp.MustCompile(`@pools/([0-9a-f]{2})/([0-9a-f]{2})/([0-9a-f]{64})\.git$`)
)

// IsRailsPoolRepository returns whether the repository is a pool repository generated by Rails.
func IsRailsPoolRepository(repo Repository) bool {
	matches := railsPoolDirRegexp.FindStringSubmatch(repo.GetRelativePath())
	if matches == nil || !strings.HasPrefix(matches[3], matches[1]+matches[2]) {
		return false
	}

	return true
}

// IsPraefectPoolRepository returns whether the repository is a Praefect generated object pool repository.
func IsPraefectPoolRepository(repo Repository) bool {
	return praefectPoolDirRegexp.MatchString(repo.GetRelativePath())
}

// IsPoolRepository returns whether the repository is an object pool.
func IsPoolRepository(repo Repository) bool {
	return IsRailsPoolRepository(repo) || IsPraefectPoolRepository(repo)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to

// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository

func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}

```go
func deriveDiskPath(prefixDir string, repositoryID int64) string {
	hasher := sha256.New()
	// String representation of the ID is used to make it easier to derive the replica paths with
	// external tools. The error is ignored as the hash.Hash interface is documented to never return
	// an error.
	hasher.Write([]byte(strconv.FormatInt(repositoryID, 10)))
	hash := hasher.Sum(nil)
	return filepath.Join(prefixDir, fmt.Sprintf("%x/%x/%d", hash[0:1], hash[1:2], repositoryID))
```

// ObjectPoolService is a service that manages the lifetime of object pools.
//
// An object pool is a separate repository that can be linked to from multiple object pool members
// in order to deduplicate common objects between them. This is mostly used in the context of
// repository forks.
//
// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
