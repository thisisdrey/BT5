### Title
Dust deposit griefing fills victim's `MAX_TOKENS_PER_USER` slots, DoS-ing deposits and issuance - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks per-account deposit/debt tokens in `depositTokensOfAccount`/`debtTokensOfAccount` and caps them at `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens`. `DepositToken._mint` and `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(account_)` whenever a recipient's balance goes from 0 to >0. Because `deposit(amount_, onBehalfOf_)` lets anyone mint a position to an arbitrary `onBehalfOf_` address, an unprivileged attacker can permissionlessly fill a victim's token list with dust positions across all listed deposit tokens. Once the list is full, every attempt by the victim to deposit a new collateral type, receive deposit tokens, or issue a new debt token (which calls `addToDebtTokensOfAccount`) reverts — a repeatable availability failure analogous to the CVE's hang/crash class.

### Finding Description
- `Pool.sol:79` sets `MAX_TOKENS_PER_USER = 30`; the modifier at `Pool.sol:143-148` reverts `UserReachedMaxTokens` when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`.
- `Pool.addToDepositTokensOfAccount` (`Pool.sol:216-220`) and `addToDebtTokensOfAccount` (`Pool.sol:204-208`) enforce this cap on every 0→nonzero balance transition.
- `DepositToken._mint` (`DepositToken.sol:486-488`) and `_transfer` (`DepositToken.sol:518-520`) call `addToDepositTokensOfAccount` on first balance — triggered by `deposit(amount_, onBehalfOf_)`, `transfer`, `transferFrom`, and `seize`.
- `deposit` (`DepositToken.sol:211-237`) accepts an arbitrary `onBehalfOf_` with no opt-in, so the attacker can add entries to the victim's list without victim consent, at only the dust cost of each collateral.
- Symmetrically, `DebtToken`'s issuance path adds to `debtTokensOfAccount`; once the combined count hits 30, `DebtToken.issue`/`mint` for a new synthetic also reverts for the victim.

### Impact Explanation
Temporary freezing of funds / protocol functionality for the targeted account: while the victim's list is saturated, all transactions that would add a new token entry revert — depositing additional collateral types (`DepositToken.deposit` → `_mint` → revert), receiving any deposit token (`transfer`/`transferFrom`/`seize` → revert), and issuing new debt tokens (`issue`/`mint` → `addToDebtTokensOfAccount` → revert). This also blocks liquidations that would credit a *new* collateral token to a saturated liquidator, and blocks smart-farming leverage flows for saturated users (`SmartFarmingManager` mints/withdrawals through the same paths). The victim can recover only by fully withdrawing dust positions to pop entries (costing withdraw fees and gas), and the attacker can re-saturate, making the DoS repeatable.

### Likelihood Explanation
Fully permissionless: the attacker needs only enough underlying to make dust deposits (`deposit` supports `onBehalfOf_` freely) or dust msdTOKEN balances to transfer. No privileged role, oracle manipulation, or malformed input is required — the check fires on a normal code path. Cost is bounded by the dust amounts across the pool's listed deposit tokens (each requiring `maxTotalSupply` headroom, i.e. `isActive` tokens only, so realistically fewer than 30 unique tokens per pool; debt tokens count too, so partial saturation still reduces the victim's usable slots).

### Recommendation
Make per-account token tracking opt-in or non-reverting for recipients: e.g., only add to `depositTokensOfAccount` on `deposit`/`issue` actions initiated by the account (or via an explicit whitelist flag), and treat unsolicited `transfer`/`seize` receipts differently; alternatively, iterate positions differently (store a per-account flag instead of enumerating for health checks) or drop the recipient-side revert by allowing balance lists to grow without a hard cap for forced receipts.

### Proof of Concept
Hardhat (TypeScript, forked or fixture deployment):

```ts
// test/poc/maxTokensGriefing.test.ts
import {expect} from 'chai'
import {ethers} from 'hardhat'
import {parseEther} from 'ethers/lib/utils'

describe('PoC: dust deposit fills MAX_TOKENS_PER_USER and DoS-es victim', function () {
  it('victim cannot deposit a new collateral or receive new deposit tokens', async function () {
    // pool, depositTokens[], underlying[], victim, attacker from fixture
    const max = (await pool.MAX_TOKENS_PER_USER()).toNumber() // 30

    // Attacker deposits 1 wei of every listed collateral on behalf of the victim
    for (let i = 0; i < depositTokens.length && i < max; i++) {
      const underlying = await ethers.getContractAt('IERC20', await depositTokens[i].underlying())
      await underlying.connect(attacker).approve(depositTokens[i].address, 1)
      // _mint(victim, dust) -> pool.addToDepositTokensOfAccount(victim)
      await depositTokens[i].connect(attacker).deposit(1, victim.address)
    }

    // Sanity: victim's account lists are saturated
    const count =
      (await pool.getDepositTokensOfAccount(victim.address)).length +
      (await pool.getDebtTokensOfAccount(victim.address)).length
    expect(count).to.be.gte(max)

    // 1) Victim's own deposit of a NOT-yet-held collateral reverts
    const newDepositToken = depositTokens[depositTokens.length - 1] // victim holds 0 of it
    const newUnderlying = await ethers.getContractAt('IERC20', await newDepositToken.underlying())
    await newUnderlying.connect(victim).approve(newDepositToken.address, parseEther('10'))
    await expect(
      newDepositToken.connect(victim).deposit(parseEther('10'), victim.address)
    ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

    // 2) Issuing a new synthetic (DebtToken._mint -> addToDebtTokensOfAccount) reverts
    await expect(
      debtToken.connect(victim).issue(parseEther('1'), victim.address)
    ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')

    // 3) Even a plain transfer of a new deposit token to the victim reverts
    await expect(
      depositTokens[0].connect(attacker).transfer(victim.address, 1)
    ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens')
  })
})
```

Note: entries are only added on 0→nonzero transitions (`DepositToken.sol:486`, `DepositToken.sol:518`), so the attacker should pick deposit tokens the victim does not yet hold; existing balances do not free slots, and the victim can only recover by fully zeroing dust positions via `withdraw`, which the attacker can cheaply re-grief.
