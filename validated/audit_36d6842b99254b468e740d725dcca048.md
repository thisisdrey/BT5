### Title
Unchecked SIP-010 transfer boolean return in vault deposit/redeem and market token transfer paths allows silent no-op transfers to be treated as success - (File: mainnet/contracts/vault/v0-vault-usdc.clar, mainnet/contracts/market/v0-market-vault.clar, mainnet/contracts/market/v0-4-market.clar)

### Summary
Every vault's `receive-underlying`/`send-underlying` helper, and `v0-market-vault`'s `receive-tokens`/`send-tokens`, invoke `contract-call? ... transfer ...` and only apply `try!` to the outer `(response bool uint)`. `try!` only distinguishes `ok` vs `err` — it never inspects the inner `bool`. If the underlying SIP-010 token returns `(ok false)` instead of an `err` on a failed transfer (a behavior the `ft-trait` interface explicitly permits since `transfer` returns `(response bool uint)`, not `(response bool bool)`), the code proceeds as if the token movement succeeded, mints/burns zTokens and updates internal `assets` accounting regardless. This is the direct Clarity analog of the Notional/Sherlock finding: the protocol "assumes all money markets/tokens will revert if [the transfer] has an error," but does not verify the actual success signal returned.

### Finding Description
In every vault contract, `deposit` calls `receive-underlying` before minting shares, and `redeem` calls `send-underlying` after burning shares: [2](#0-1) [3](#0-2) 

```
(define-private (receive-underlying (amount uint) (account principal))
  (begin
    (try! (contract-call? 'SP120SBRBQJ00MCWS7TM5R8WJNTTKD5K0HFRC2CNE.usdcx transfer amount account current-contract none))
    (ok true)))
```

`try!` on a `(response bool uint)` only aborts when the call returns `(err ...)`; it discards the wrapped boolean and always treats `(ok true)` and `(ok false)` identically, unwrapping to the boolean value without asserting it is `true`. The same discard pattern repeats in every vault (`v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-stx.clar`, `v0-vault-usdh.clar`) for both `receive-underlying` and `send-underlying`, and in the market layer's `receive-tokens`/`send-tokens` used for direct token supply/repay flows: [4](#0-3) 

The `ft-trait` itself defines `transfer` to return `(response bool uint)`, i.e., it is a documented possibility (per the SIP-010 interface as implemented here) for a compliant contract to signal failure via `(ok false)` rather than by raising an `err` — exactly the ambiguity flagged in the Notional report ("the successful response returned from various money markets might be different... some protocols return 1 on success while others use zero"). The vaults' `deposit`/`redeem` entry points and `v0-4-market.clar`'s `supply-collateral-add`/`repay`-style transfer at line 1209 are reachable directly by any ordinary principal: [5](#0-4) 

### Impact Explanation
If any of the underlying tokens (`usdcx`, `sbtc-token`, `ststx-token`, `usdh-token-v1`, `wstx`) ever returns `(ok false)` on a failed transfer — whether due to an edge case in that external token's own logic (e.g., paused state, blacklist, fee-on-transfer shortfall, or a future upgrade) rather than reverting — the vault will still mint zTokens (`ft-mint? zft inkind recipient`) and increment `assets` in `deposit`, or decrement `assets` and physically believe funds were sent in `redeem`, without the underlying value having actually moved. This directly leads to insolvency of the vault (zToken supply not backed by real underlying) and, on the redeem side, exactly the scenario the original report calls out: "assets sent to the users even though the redemption fails" is inverted here — shares/debt reduced while underlying is not actually delivered/received, corrupting the total-assets accounting used by all other users' collateral valuation, LTV checks, and liquidation math. This lands in the in-scope Critical impact class: protocol insolvency / permanent freezing or loss of user funds at rest, since the `assets` variable underpins share pricing (`convert-to-assets-preview`/`convert-to-shares-preview`) for every depositor.

### Likelihood Explanation
Likelihood depends entirely on whether any of the five underlying tokens (`usdcx`, `sbtc-token`, `ststx-token`, `usdh-token-v1`) can, under any code path, return `(ok false)` instead of erring for a failed `transfer`. This is a property of third-party tokens outside this repo, so it cannot be fully confirmed here — however, the report's core point stands regardless: the vault code contains **no defensive check** (`asserts! (is-eq result true) ...`) on the boolean, so the contract is unconditionally trusting any future or edge-case behavior of these external tokens to always err instead of returning false. This is a reachable, no-privilege-required code path (ordinary `deposit`/`redeem`/`supply-collateral-add`), differing from the "OUT OF SCOPE" categories (no flashloan, no DAO compromise, no privileged address needed).

### Recommendation
After every `contract-call? ... transfer ...`, explicitly assert the returned boolean is `true` (e.g., `(asserts! (unwrap! (contract-call? ... transfer ...) ERR-TRANSFER-FAILED) ERR-TRANSFER-FAILED)`) rather than relying solely on `try!`/`err` propagation, in `receive-underlying`/`send-underlying` in all vault contracts and in `receive-tokens`/`send-tokens` in `v0-market-vault.clar`.

### Proof of Concept
1. Assume (or a future upgrade introduces) a scenario where one of the hardcoded underlying token contracts (e.g., `usdcx`) returns `(ok false)` for `transfer` under some internal condition instead of raising an `err` (permitted by the `(response bool uint)` trait signature).
2. A user calls `deposit` on `v0-vault-usdc.clar` with `amount` while triggering that token's `(ok false)` condition.
3. `receive-underlying` calls `(try! (contract-call? ... transfer amount account current-contract none))`; since the call returns `(ok false)`, `try!` does not abort — it unwraps to `false` and the `begin` block still returns `(ok true)`.
4. `deposit` proceeds to `(try! (ft-mint? zft inkind recipient))` and `(var-set assets (+ current-assets amount))`, crediting the user with zTokens/shares backed by underlying that was never actually transferred in.
5. The user can later `redeem` those shares for real underlying from other depositors' funds, resulting in insolvency of the vault. [3](#0-2)
