### Title
Unbounded Array Allocation from Untrusted Precompiled-Contract Input Length - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
Several helper routines used by TVM precompiled contracts (`BatchValidateSign`/`ValidateMultiSign`, reachable via a normal contract `CALL`/`STATICCALL`) read an array-length word directly from attacker-controlled call data and use it to size a Java array with no upper bound check, mirroring the PX4 Zenoh bug class where an unvalidated length field from untrusted input drives an unbounded allocation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each take a `DataWord[] words` array that is the raw ABI-decoded call data passed into a precompiled contract, and immediately size a Java array from an attacker-supplied word without validating it against any sane maximum or against the actual remaining `words.length`: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three methods, `len = words[offset].intValueSafe()` is attacker-controlled (it comes straight from the transaction's call data to the precompiled contract), and is used directly as `new byte[len][]` (or similarly sized array) before any bounds/sanity check is performed. There is no cap comparing `len` to a reasonable maximum such as the actual number of remaining `words`, nor any check that `len` is non-negative and small. A crafted call with a very large `len` (e.g., close to `Integer.MAX_VALUE`) causes the JVM to attempt to allocate a reference array of that size, which either throws `OutOfMemoryError` or causes severe GC pressure — the heap-array analog of the PX4 bug's stack VLA allocated straight from an unvalidated incoming length.

### Impact Explanation
These extraction helpers are invoked by precompiled-contract implementations (`BatchValidateSign`/`ValidateMultiSign`) that are reachable from any account via a normal `TriggerSmartContract` transaction calling the precompile address from a deployed contract's bytecode — no special privilege is required. A single malicious call can force an oversized allocation attempt inside the VM execution thread, producing an `OutOfMemoryError`. Depending on JVM heap pressure at the time, this can crash or destabilize the node process handling the transaction, denying service to legitimate users (matches the "node crash or halt" acceptable-impact criterion in the validation rules).

### Likelihood Explanation
Likelihood is high for triggering the code path: constructing call data with an oversized length word requires no special permissions, only a standard smart-contract deployment and call, which is fully within reach of "an unprivileged transaction broadcaster, contract deployer, ... or order placer" per the scope. The severity of impact (partial OOM vs full node crash) depends on runtime heap conditions I could not fully verify from the index (e.g., whether other guards elsewhere clamp `len` before reaching these helpers, or whether the surrounding VM code wraps `OutOfMemoryError` safely) — this residual uncertainty should be validated with a live JVM heap-pressure test.

### Recommendation
Add an explicit upper bound / consistency check before allocation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, e.g., validate `len >= 0` and `len <= words.length - offset - 1` (or another small application-defined maximum) prior to `new byte[len][]`, mirroring the bound-checking pattern already used elsewhere in the codebase (e.g., `RLP.verifyLength`, `ContractEventParser.subBytes`) that reject oversized/malformed lengths instead of allocating from them.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL`/`CALL` to the `BatchValidateSign` or `ValidateMultiSign` precompiled-contract address.
2. Encode the call data so that the ABI word at the offset consumed by `extractSigArray`/`extractBytesArray`/`extractBytes32Array` (the "array length" word) is set to a very large value (e.g. `0x7FFFFFFF`).
3. Broadcast a `TriggerSmartContract` transaction invoking that contract.
4. During execution, `PrecompiledContracts.extractSigArray`/`extractBytesArray`/`extractBytes32Array` attempts `new byte[len][]` with the attacker-chosen `len`, triggering excessive allocation / `OutOfMemoryError` in the node's VM execution thread.

Note: I was unable to fully trace, within the available index, the exact address-dispatch mapping in `getContractForAddress` and any proposal/hardfork gating that enables `BatchValidateSign`/`ValidateMultiSign`, nor whether a higher-level `Throwable` catch elsewhere in the execution pipeline mitigates the `OutOfMemoryError` before it destabilizes the whole node process. Confirming these two points would require deeper inspection of `PrecompiledContracts.getContractForAddress` and the VM's top-level exception handling, which is recommended before treating this as fully confirmed critical-impact.
