Let me verify the key details about `migrate_coin_store_to_fungible_store` and `set_frozen_flag_internal`.

### Title
Unprivileged Caller Can Unfreeze a Frozen Primary FungibleStore via `migrate_coin_store_to_fungible_store` — (`aptos-move/framework/aptos-framework/sources/coin.move`)

---

### Summary

`migrate_coin_store_to_fungible_store` accepts an arbitrary `vector<address>` with no signer requirement for the listed accounts. When a victim holds an unfrozen `CoinStore` (with non-zero balance) alongside a frozen primary `FungibleStore`, any unprivileged caller can trigger migration on the victim's address and cause `maybe_convert_to_fungible_store` to overwrite the FA store's `frozen` field to `false` via `set_frozen_flag_internal`, bypassing the invariant that only the `TransferRef` holder may unfreeze a store.

---

### Finding Description

`migrate_coin_store_to_fungible_store` is a `public entry fun` that takes only a `vector<address>` — no signer for the target accounts is required: [1](#0-0) 

Inside `maybe_convert_to_fungible_store`, when `coin.value > 0`, the code synchronises the frozen flag between the `CoinStore` and the primary FA store unconditionally in both directions: [2](#0-1) 

The developer comment at lines 707–711 only describes the intended direction (frozen CoinStore → freeze an unfrozen FA store). The reverse direction — an unfrozen CoinStore overwriting a frozen FA store — is unintended and constitutes the bug. [3](#0-2) 

`set_frozen_flag_internal` is `public(friend)` and writes directly to `FungibleStore.frozen` without any `TransferRef` check: [4](#0-3) 

The only legitimate path to unfreeze a store is through `set_frozen_flag`, which requires a `TransferRef`: [5](#0-4) 

---

### Impact Explanation

Any module or protocol that freezes a user's primary FA store via `TransferRef` (e.g., compliance enforcement, locked vesting, staking escrow) can have that freeze silently removed by an unprivileged third party. Once unfrozen, the victim can freely transfer assets that were supposed to be immobilised, breaking the protocol invariant and potentially enabling theft or circumvention of regulatory/protocol-level controls on fungible assets including APT.

---

### Likelihood Explanation

The preconditions are realistic and common during the ongoing coin-to-FA migration period:

1. Victim has a legacy `CoinStore<CoinType>` with `frozen=false` and `coin.value > 0` — the default state for most accounts that have not yet migrated.
2. Victim's primary FA store has `frozen=true` — set by any module holding a `TransferRef` (e.g., a DeFi protocol, a compliance layer, or the framework itself for APT).
3. Attacker submits a single transaction calling `migrate_coin_store_to_fungible_store<CoinType>([victim_addr])` — zero privilege required.

The attack is a single, cheap, permissionless transaction.

---

### Recommendation

The frozen-flag synchronisation in `maybe_convert_to_fungible_store` should only ever **freeze** an FA store to match a frozen CoinStore, never **unfreeze** one. Replace the bidirectional sync with a one-directional guard:

```move
// Only propagate a freeze; never silently unfreeze an already-frozen FA store.
if (frozen && !fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, true);
};
```

This preserves the intended semantic (a frozen CoinStore freezes the FA store on migration) while preventing an unfrozen CoinStore from overriding a freeze that was legitimately set by a `TransferRef` holder.

        store: Object<T>, frozen: bool
    ) acquires FungibleStore {
