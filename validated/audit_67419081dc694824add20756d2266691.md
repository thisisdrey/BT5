### Title
Dust-transfer/deposit griefing fills victim's `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, DoS-ing deposits and debt mints - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` tracks a per-account set of deposit and debt tokens capped at `MAX_TOKENS_PER_USER = 30`, and reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`. Any unprivileged user can forcibly add entries to a victim's set — either by depositing dust `onBehalfOf_` the victim via `DepositToken.deposit(amount_, onBehalfOf_)`, or by `transfer`/`transferFrom`-ing 1 wei of each DepositToken share to the victim — since `_mint`/`_transfer` unconditionally call `pool.addToDepositTokensOfAccount` whenever the recipient's balance was zero. Once the victim's set is full, every subsequent first-time deposit (`DepositToken.deposit` → `_mint` → `addToDepositTokensOfAccount`) and every first-time borrow (`DebtToken.issue/mint` → `addToDebtTokensOfAccount`) reverts, matching the report's hang/DoS bug class.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` enforces the combined 30-slot cap on both `addToDepositTokensOfAccount` and `addToDebtTokensOfAccount`. [1](#0-0) [2](#0-1) 
- `addToDepositTokensOfAccount` is callable only by a registered DepositToken (`_revertIfSenderIsNotDepositToken`), but the DepositToken itself calls it on behalf of *any* recipient address with no opt-in: in `_mint` (line 486-488) and `_transfer` (line 517-520), `pool.addToDepositTokensOfAccount(account_)` runs whenever `balanceBefore == 0 && amount > 0`. [3](#0-2) 
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` address, so the attacker doesn't even need prior shares — depositing dust directly adds a slot to the victim. [4](#0-3) 
- `transfer` only checks `_revertIfLocked(msg.sender, amount)` on the sender, so dust transfers of unlocked balances are unrestricted. [5](#0-4) 

Attack trace (all public, unprivileged):
1. For each deposit token registered in the pool, attacker calls `depositToken.deposit(1 wei, victim)` — or deposits once to themselves and calls `transfer(victim, 1)`.
2. Victim's `depositTokensOfAccount.length` grows to 30 (or 30 minus existing debt tokens).
3. Any `deposit`/`issue`/`leverage`/`NativeTokenGateway.deposit` call that would add a new token to the victim's set now reverts in `onlyIfAdditionWillNotReachMaxTokens`.

### Impact Explanation
Liveness denial of core protocol functions for the targeted account (the analog of CVE-2020-14773's complete DoS):
- The victim cannot deposit a collateral type they don't already hold a balance of, so they cannot add collateral to rescue an under-collateralized position — making them liquidatable when they otherwise would not be, i.e., indirect theft via forced liquidation.
- The victim cannot mint a new synthetic/debt token type (`addToDebtTokensOfAccount` shares the same 30-slot budget).
- Recovery requires the victim to transfer out/withdraw each dusted token to zero to trigger `removeFromDepositTokensOfAccount`, and the attacker can re-fill slots in the same or next block (front-running), extending the freeze. This qualifies as temporary freezing of funds / blocked exits under the acceptance criteria.

### Likelihood Explanation
Cost is bounded and trivial: one dust deposit or 1-wei transfer per pool deposit token (pools typically have a handful of collaterals, far fewer than 30 slots needed to combine with the victim's own tokens). No privileged role, oracle manipulation, or flash capital is required — `_revertIfLocked` doesn't apply since the attacker uses their own unlocked balance, `nonReentrant` doesn't block cross-call patterns, and `whenNotPaused` doesn't help. The main constraint is that the total number of deposit tokens registered in the pool limits how many slots an attacker can fill alone; if pool collateral count is small, the victim must already hold many token types for the cap to bind. Still, any victim already near the cap (e.g., leveraged SmartFarming positions holding several collaterals plus several debt tokens) can be pushed over it cheaply.

### Recommendation
- Do not auto-register tokens on behalf of recipients on `transfer`/`transferFrom`/`deposit(onBehalfOf_)` without consent; e.g., only add to `depositTokensOfAccount` when `account_ == _msgSender()` or require the recipient to opt in.
- Alternatively, only add to the set when the received amount exceeds a meaningful threshold, or make the cap per-list rather than forcing reverts on `add` — e.g., skip registration instead of reverting when full (though that changes `depositOf` accounting, so the opt-in approach is safer).
- At minimum, allow a removal-only escape path that doesn't revert at the cap (already true via `removeFromDepositTokensOfAccount`), and document the griefing vector.

### Proof of Concept
Hardhat (typescript, modeled on `test/Pool.test.ts` deposit-token tests):

```ts
it('fills victim token list via dust deposits/transfers', async () => {
  // pool has depositTokens d0..dk (registered via addDepositToken by governor in fixture)
  const victim = alice.address
  const attacker = bob

  // Victim already holds some debt tokens / deposit tokens, leaving `free` slots
  const free = (await pool.MAX_TOKENS_PER_USER()).toNumber() -
    (await pool.getDepositTokensOfAccount(victim)).length -
    (await pool.getDebtTokensOfAccount(victim)).length

  // Attacker dusts victim: either deposit onBehalfOf or transfer 1 wei
  for (let i = 0; i < free; ++i) {
    await underlyingTokens[i].connect(attacker).approve(depositTokens[i].address, 1)
    await depositTokens[i].connect(attacker).deposit(1, victim) // adds slot to victim
  }

  expect((await pool.getDepositTokensOfAccount(victim)).length +
         (await pool.getDebtTokensOfAccount(victim)).length
  ).to.eq(await pool.MAX_TOKENS_PER_USER())

  // Victim can no longer deposit a new collateral type
  const newDepositToken = depositTokens[free] // not yet in victim's set
  await underlyingTokens[free].connect(alice).approve(newDepositToken.address, parseEther('10'))
  await expect(
    newDepositToken.connect(alice).deposit(parseEther('10'), victim)
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')

  // Nor mint a new synthetic debt type
  await expect(
    newDebtToken.connect(alice).issue(parseEther('1'))
  ).revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```
