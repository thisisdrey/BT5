### Title
Unbounded array allocation in TVM precompile helper methods enables cheap-energy memory-exhaustion DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` (address `0x...09`) and `ValidateMultiSign` (address `0x...0a`) precompiled contracts, reachable by any TVM contract call from an unprivileged, signed transaction, decode their calldata via helper methods that allocate arrays sized directly from an attacker-controlled length word, with no upper bound or correlation to the actual size of the supplied calldata (and hence no correlation to the energy charged).

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each read a length value straight out of the ABI-decoded words and immediately allocate an array of that size: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three cases, `len` comes from `words[offset].intValueSafe()`, a value fully controlled by the calling contract's ABI-encoded calldata word — it is not bounded by the actual number of words present in `data`/`words`, nor clamped to any sane maximum before the `new byte[len][]` allocation. `intValueSafe()` is designed to avoid throwing on overflow, meaning an attacker can set this length field to a very large 32-bit value (e.g., near `Integer.MAX_VALUE`) using only a handful of encoded words, i.e., a small calldata payload. Allocating a reference array of that size (`new byte[Integer.MAX_VALUE][]`) requires on the order of many gigabytes of heap (4–8 bytes per reference slot before any element data is populated), which can trigger `OutOfMemoryError` in the node process handling the call.

This is structurally the same bug class as the GitLab CVE-2022-3759 hint: a small, cheaply-crafted input (there, a CI artifact zip; here, a short ABI-encoded calldata blob) causes the receiving worker (there, Sidekiq; here, the TVM executing the precompile within `Program`/`Runtime`) to allocate a disproportionately large amount of memory relative to the input size, producing denial of service.

### Impact Explanation
If reachable without a compensating bounds check upstream (in `BatchValidateSign.execute()` / `ValidateMultiSign.execute()`, which call these helpers — not directly inspected due to tool budget), an attacker could submit a cheap, small transaction that calls a contract invoking these precompiles, causing the executing full node/SR to attempt a multi-gigabyte allocation. This can crash the JVM (`OutOfMemoryError`) or severely degrade node availability — a node crash/halt impact, which is in-scope per the validation rules.

### Likelihood Explanation
The precompiles are reachable from any Solidity contract via a `STATICCALL`/`CALL` to a fixed low-numbered address, requiring no special privilege — any address that can deploy a contract and issue a transaction can trigger this path. The likelihood hinges on whether `getEnergyForData` for these two contracts charges energy proportional to the *declared* array length (from the length word) rather than just `data.length`; I was not able to view the full `BatchValidateSign`/`ValidateMultiSign` class bodies before running out of tool budget, so I cannot confirm whether energy metering already indirectly bounds `len` (e.g., by requiring `data.length` to be at least `len * elementSize`, which would make the allocation‑to‑cost ratio bounded) or whether it is unmetered relative to `len`. This is the key open question for confirming exploitability at Medium/High severity.

### Recommendation
Add an explicit bounds check on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocation — e.g., reject if `len` exceeds a small sane maximum (matching the realistic max number of signatures/keys a validator would need) or if `len` is inconsistent with the remaining `words.length` / `data.length`, similar to the existing `offset > words.length - 1` guard already present in `extractBytesArray`/`extractSigArray`. Confirm and, if necessary, correct energy accounting in `BatchValidateSign.getEnergyForData` and `ValidateMultiSign.getEnergyForData` so that energy cost scales with the declared array length, not just the raw `data.length`.

### Proof of Concept
Conceptual PoC (exact byte layout depends on `BatchValidateSign`/`ValidateMultiSign` ABI, not fully verified here):
1. Deploy a minimal contract that performs a `STATICCALL` to precompile address `0x...09` (`BatchValidateSign`) or `0x...0a` (`ValidateMultiSign`).
2. Craft the calldata so the ABI word at the offset consumed by `extractBytesArray`/`extractSigArray`/`extractBytes32Array` encodes a very large length (e.g., `0x7fffffff`), while keeping the overall calldata short.
3. Broadcast a transaction invoking this contract call; on execution, the node attempts `new byte[len][]`, causing a large-heap allocation attempt and potential `OutOfMemoryError`/node instability.

**Caveat:** I could not fully inspect the `BatchValidateSign`/`ValidateMultiSign` `execute()`/`getEnergyForData()` implementations within the available tool budget to confirm whether an existing bound elsewhere (e.g., a max signature-count check before calling these helpers) already mitigates this. This finding should be validated against those two classes' full source before treating it as confirmed/exploitable.
