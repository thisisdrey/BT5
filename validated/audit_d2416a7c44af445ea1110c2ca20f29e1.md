## Title
Heap-based buffer over-read in `LH::compressed_file_size()` from an unvalidated Zip64 extra-field index - (File: `src/tools/singlejar/zip_headers.h`)

## Summary
`singlejar`/`ijar` parse ZIP/JAR archives that are frequently built from third-party artifacts (e.g., `http_jar`/`http_archive`-fetched dependencies merged into a deploy jar). When a Local File Header (`LH`) declares a 32-bit compressed size of `0xFFFFFFFF` (Zip64 sentinel), `LH::compressed_file_size()` unconditionally reads `attr64(1)` from the Zip64 extra field, assuming that index 1 always holds the compressed size. This assumption is only valid if the archive strictly obeys the "MUST have both sizes present" rule; a crafted/corrupted extra field can supply a `Zip64ExtraField` payload with fewer than two 64-bit attributes (e.g., `payload_size == 8`), causing `attr64(1)` to read 8 bytes past the actual field payload into adjacent heap memory (the mmap'd archive buffer).

## Finding Description
`LH::compressed_file_size()` in [1](#0-0)  is:
```
size_t compressed_file_size() const {
  size_t size32 = compressed_file_size32();
  if (ziph::zfield_has_ext64(size32)) {
    const Zip64ExtraField* z64 = zip64_extra_field();
    return z64 == nullptr ? 0xFFFFFFFF : z64->attr64(1);
  }
  return size32;
}
```
This hard-codes index `1` for the compressed-size attribute. Contrast this with the equivalent `CDH::compressed_file_size()` at [2](#0-1) , which correctly derives the index from whether the *uncompressed* size also needs the 64-bit extension:
```
return z64 == nullptr ? 0xFFFFFFFF
                      : z64->attr64(ziph::zfield_has_ext64(
                            uncompressed_file_size32()));
```
The `LH` variant relies on the ZIP64 spec comment that "the Zip64 extra field of the Local Header MUST have both uncompressed and compressed sizes present" (see comment at [3](#0-2) ) — but this is merely a spec convention, not something enforced by the parser. `Zip64ExtraField::attr64(int index)` performs no bounds check against `attr_count()`/`payload_size()`:
```
uint64_t attr64(int index) const { return le64toh(attr_[index]); }
``` [4](#0-3) 

`Zip64ExtraField::find` only validates that the *whole* extra-field record (header + declared `payload_size`) fits within `[start, end)` [5](#0-4) ; it does not verify `payload_size >= 16` (two 8-byte attrs) before `LH::compressed_file_size()` blindly indexes into `attr_[1]`.

This function is reached during normal JAR-merging in `OutputJar::AddJar`, which memory-maps the input jar read-only and calls `lh->compressed_file_size()` to compute `num_bytes` for the raw byte copy of an entry [6](#0-5) . Because the archive is `mmap`'d read-only, a heap/mapped-memory over-read of 8 bytes just reads adjacent process memory (potentially bytes from a different section of the mapped file, or padding past it) — this is the same bug class as CVE-2018-11433 (`mobi_get_kf8boundary_seqnumber` reading a fixed-offset field from a variable-length/attacker-controlled structure without validating the actual declared length).

## Impact Explanation
An attacker who controls the content of a `.jar`/`.zip` file that a victim's build consumes (e.g., a maven/http-fetched dependency, or any archive path that flows into `singlejar`) can construct a Local File Header whose `compressed_file_size32` is `0xFFFFFFFF` but whose accompanying Zip64 extra field payload is only 8 bytes (one attribute) rather than the expected 16 bytes. `LH::compressed_file_size()` will then read `attr_[1]`, which is out-of-bounds relative to the declared payload. The returned (garbage/adjacent-memory) value is subsequently used as `num_bytes` to compute an over-large or nonsensical byte count in `OutputJar::AddJar`, which is then used to size a `WriteBytes` copy from the mapped input file [7](#0-6) . This can leak adjacent heap/mapped memory bytes into the build's output artifact (information disclosure), matching the "heap-based buffer over-read" impact class of the reported CVE.

## Likelihood Explanation
Note on scope: standard `http_archive`/`http_jar` integrity checks (sha256/integrity) verify the *whole downloaded file* before it is used, so if a checksum is pinned, the file bytes (including this malformed structure) are exactly what was checked — the integrity check does not, and cannot, validate internal semantic consistency of the ZIP64 extra field. This is analogous to the original CVE: it is a parsing bug independent of whether the outer file's checksum matches. Any workflow where `singlejar` merges third-party/externally-produced jars (a common Bazel Java build step) is a plausible trigger path, requiring no privilege beyond publishing content that a build consumes.

## Recommendation
Fix `LH::compressed_file_size()` to mirror `CDH::compressed_file_size()`'s approach: compute the correct attribute index based on which 32-bit fields report the ext64 sentinel, and additionally validate `z64->attr_count()` against the required index before calling `attr64()`, returning an error/sentinel value if the payload is too short.

## Proof of Concept
Not fully reproducible from static analysis alone: constructing a JUnit/`zip_headers_test.cc` case exercising this requires building an `LH` whose `compressed_file_size32_` is `0xFFFFFFFF` and whose Zip64 extra field has `payload_size == 8` (only one attribute), then calling `lh->compressed_file_size()` and observing that `attr64(1)` reads bytes beyond the field's declared payload (verifiable with an ASan/valgrind-instrumented allocation matching the `kPoison`-fill pattern already used in `zip_headers_test.cc`, e.g. extending the existing `TEST(ZipHeadersTest, LocalHeader)` test at [8](#0-7) ). I was not able to trace a complete concrete exploit chain from an attacker-controlled URL/archive all the way through the real `singlejar` binary invocation in this analysis; this would need to be validated with an instrumented build (ASan) to confirm the out-of-bounds read is observable at runtime rather than only in a static reasoning about the missing bounds check.
