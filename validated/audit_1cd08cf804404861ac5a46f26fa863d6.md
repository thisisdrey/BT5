<br>Based on my investigation, I found a concrete analog in the codebase. Here's the finding:

### Title
Stale, reward-cycle-scoped StackerDB chunk data can be silently reused as canonical current-cycle data due to unbound (non-domain-separated) chunk signatures - (File: `stackslib/src/net/stackerdb/db.rs`, `stackslib/src/chainstate/stacks/boot/signers.clar`)

### Summary
The Curve report's core lesson is that a signature/authorization scheme which does not bind the *context* in which it is used (only the raw callback parameters) lets a validly-authorized action for one context be reused/interpreted as authorized for a different, unintended context. The Stacks `.signers` StackerDB scheme has the same class of flaw: chunk signatures (`SlotMetadata::auth_digest`) commit only to `slot_id`, `slot_version`, and `data_hash` — never to the StackerDB contract/reward cycle — while the physical `.signers-{0,1}-{message_id}` contracts are recycled every 2 reward cycles (`reward_cycle % 2`), and slot data is *not* cleared when the same signer address keeps the same slot index across cycles.

### Finding Description
`SlotMetadata::auth_digest()` only hashes `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) . It never incorporates the target contract ID or reward cycle, so a signature is portable across any StackerDB instance where the signer happens to own the same slot ID.

The `.signers` boot contracts intentionally reuse only two physical StackerDB contracts across all reward cycles, keyed by `reward_cycle % 2`: [2](#0-1)  and the Rust-side contract-name derivation confirms the same pairing: [3](#0-2) .

When the reward cycle rolls over, `reconfigure_stackerdb` is used to re-apply the new signer→slot assignment. Critically, if a signer keeps the **same slot_id** it had two cycles prior (a common and expected occurrence, since slot indices are typically derived from a stable sort/ranking of stackers), the code takes a "no change" branch that leaves the existing stored version and chunk data completely untouched — it does not reset the version counter, clear the data, or invalidate the signature: [4](#0-3) 

Only when `existing_validation.signer != principal` does the slot get reset to `NO_VERSION` with an empty signature (lines 332–346 of the same file). This means a chunk that was signed and legitimately stored two reward cycles earlier — with a `SlotMetadata` signature that never mentioned the reward cycle or contract context at all — remains addressable and verifiable "as-is" in the recycled `.signers-{same_parity}-{message_id}` contract for the brand-new reward cycle, with no way for the verification logic (`try_replace_chunk`'s `slot_desc.verify(&slot_validation.signer)`, [5](#0-4) ) to distinguish "signed for cycle N" from "signed for cycle N+2."

Consumers such as `InitialChunksLoader::load_chunks`, used by `StackerDBListener::new` to seed a miner/signer's initial global state at the start of a cycle, read whatever is currently stored in the slot without any reward-cycle binding check in the payload itself: [6](#0-5)  and [7](#0-6) . If the slot wasn't reset (same signer, same slot id, mod-2 collision), the loader will feed a stale, previous-cycle vote/state-machine-update message into the current cycle's `GlobalStateEvaluator` as if it were fresh, because the on-wire signature format gives it no way to tell the two apart.

### Impact Explanation
This breaks the "authenticated for context X" vs. "served/consumed as canonical for context Y" equality: a `StackerDBChunkData` cryptographically valid for reward cycle N is silently reusable/servable as canonical for reward cycle N+2 (same slot occupant), because neither `SlotMetadata::auth_digest` nor `try_replace_chunk`/`reconfigure_stackerdb` bind the signature or storage reset to the reward cycle. This falls under "serving non-canonical state as canonical," which per the scoping rules is a High-severity class — a node/signer's initial view of coordination state for a new cycle can be seeded with 2-cycles-stale data without anyone forging a signature or needing privileged access; any peer who already observed the old (legitimately broadcast, hence public) chunk can also re-propagate it into the recycled contract via ordinary StackerDB push/replication paths once slot occupancy again matches, without needing the signer's private key.

### Likelihood Explanation
This does not require compromising any private key — the old, validly-signed chunk was already publicly broadcast to the whole network when originally posted (`process_stacker_db_chunks` broadcasts every accepted chunk: [8](#0-7) ). The precondition (the same signer address is assigned to the same slot index two cycles apart) is not adversarially controllable but is a routine occurrence given how slot assignment is derived from a stable ordering of registered signers; large/stable signers are especially likely to retain their slot index across reward cycles.

### Recommendation
Include the target contract identifier (or at minimum the reward cycle number) in `SlotMetadata::auth_digest()`'s signed payload so a signature is cryptographically scoped to one specific StackerDB replica/cycle, mirroring the external report's recommendation to use a callback-specific signature. Additionally, `reconfigure_stackerdb`'s "no change" branch should still reset `version`/`data` (or otherwise mark the previous cycle's chunk as expired) whenever the reward cycle boundary is crossed, even if the same signer retains the same slot index.

### Proof of Concept
1. Reward cycle N (parity 0): signer A is assigned slot 3 in `.signers-0-{message_id}`; A posts and signs `StackerDBChunkData{slot_id:3, slot_version:7, data:D_N}`. This is broadcast network-wide and stored.
2. Reward cycle N+1 (parity 1): a different contract `.signers-1-{message_id}` is used; `.signers-0-{message_id}` is untouched.
3. Reward cycle N+2 (parity 0 again): `reconfigure_stackerdb` runs against `.signers-0-{message_id}` for the new signer set. Because signer A still occupies slot 3 (`existing_validation.signer == principal`), the code takes the "no change" branch in [9](#0-8)  — version 7 / `D_N` / A's old signature remain stored verbatim.
4. Any node/miner that queries `.signers-0-{message_id}` slot 3 at the start of cycle N+2 (e.g. via `InitialChunksLoader::load_chunks`) retrieves `D_N` — data cryptographically signed and intended for cycle N — and treats it as this cycle's state, because the signature format carries no cycle/context binding to reject it.
