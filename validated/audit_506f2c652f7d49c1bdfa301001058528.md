### Title
Attacker can fill a victim's per-account token list with dust deposits/transfers, blocking new collateral deposits and debt issuance - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
Metronome tracks each account's deposit and debt tokens in bounded per-account sets (`depositTokensOfAccount`, `debtTokensOfAccount`) capped by `MAX_TOKENS_PER_USER = 30`. Any nonzero receipt of a whitelisted `DepositToken` (via `deposit(amount, onBehalfOf_)` or a plain ERC20 `transfer` of msdTokens) adds that token to the recipient's list via `Pool.addToDepositTokensOfAccount`, which reverts with `UserReachedMaxTokens` once the combined list reaches 30. There is no minimum amount, so an attacker can push dust (1 wei) of every supported deposit token to a victim and permanently occupy all slots until the victim manually cleans them out.

### Finding Description
`DepositToken._transfer` / `DepositToken._mint` add the token to the recipient's account list whenever the recipient's prior balance is zero: [1](#0-0) [2](#0-1) 

`Pool.addToDepositTokensOfAccount` enforces the cap on the *recipient*, with no minimum value: [3](#0-2) [4](#0-3) 

The cap is shared across deposit and debt tokens: [5](#0-4) 

`DebtToken.issue` mints debt to `_msgSender()` (collateral-checked), so the attacker cannot add debt tokens to the victim's list directly — but the deposit-token side alone can consume all 30 slots: [6](#0-5) 

Once the list is full, every `deposit` of a collateral the victim doesn't already hold reverts inside `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`, and `issue` of a synthetic the victim doesn't already owe reverts the same way.

### Impact Explanation
- The victim cannot deposit any *new* collateral type and cannot issue any *new* synthetic debt type while the list is full — a liveness break on the two core position-management entry points.
- Timed against a falling market, this can prevent a victim from topping up with a different collateral to avoid liquidation, converting a griefing attack into indirect loss of funds (forced liquidation / seizure via `Pool.liquidate`).
- The victim can recover by withdrawing/transferring the dust positions (each withdraw to zero calls `removeFromDepositTokensOfAccount`), but only after noticing the attack and paying gas per token — mirroring the Debita report's dust-fragmentation griefing where cleanup cost is imposed on the victim.

### Likelihood Explanation
The attack is permissionless and cheap: the attacker deposits a dust amount of each supported underlying (or deposits once and `transfer`s 1 wei of each msdToken) to the victim. No privileged role, oracle manipulation, or flash capital is needed. Constraints: the number of distinct deposit tokens per pool is limited by `ReachedMaxDepositTokens`, and the victim retains a self-service cleanup path, so the freeze is temporary rather than permanent — consistent with a medium-severity griefing finding.

### Recommendation
Enforce a minimum amount on `deposit`/`transfer` before calling `addToDepositTokensOfAccount` (e.g., a USD floor via `masterOracle`), or gate list insertion on a minimum balance so dust cannot occupy a slot. Alternatively, allow `removeFromDepositTokensOfAccount` cleanup by anyone for dust balances below the floor.

### Proof of Concept
Hardhat outline (against deployed pool on a fork):

```ts
// victim = alice, attacker = bob
// For each registered deposit token d_i (i = 1..N where N = 30 - victimSlotsUsed):
//   1. bob deposits 1 wei of underlying_i on behalf of alice:
await depositToken_i.connect(bob).deposit(1, alice.address);
//    OR bob holds msdToken_i and dust-transfers:
await depositToken_i.connect(bob).transfer(alice.address, 1);

// After the loop:
expect(await pool.getDepositTokensOfAccount(alice.address)).to.have.length(N);

// Victim tries to deposit a collateral type not yet in their list:
await underlying.connect(alice).approve(newDepositToken.address, amount);
await expect(
  newDepositToken.connect(alice).deposit(amount, alice.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens');

// Likewise, issuing a synthetic whose debt token isn't in the list reverts:
await expect(
  newDebtToken.connect(alice).issue(amount, alice.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Existing tests confirm the revert path and that a single dust `transfer` triggers exactly one `addToDepositTokensOfAccount` call: [7](#0-6) [8](#0-7)
