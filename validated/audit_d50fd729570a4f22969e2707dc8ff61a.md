### Title
Pending transaction queue misattributes deploy-exclusivity/P_MAX bookkeeping for DelegateAction meta-transactions to the relayer instead of the delegating sender - (File: chain/client/src/pending_transaction_queue.rs)

### Summary
`add_chunk_transactions` keys all per-account bookkeeping (`deploy_tx_count`, `access_key_tx_count`, `paid_from_balance`) by the outer `SignedTransaction`'s `signer_id`, even though `is_deploy_like_action` correctly recurses into `Action::Delegate`/`Action::DelegateV2` to detect a wrapped `DeployContract`. For a meta-transaction, the outer signer is the relayer, not the delegating account whose contract is actually deployed, so the NEP-611 deploy-exclusivity/P_MAX enforcement is applied to the wrong account's bucket.

### Finding Description
In `add_chunk_transactions` [1](#0-0) , the signer used for the `pending_accounts`/`chunk_data.accounts` map key is `tx.signer_id()` (the outer transaction's signer). `has_deploy_action` / `is_deploy_like_action` correctly recurse into `Action::Delegate`/`Action::DelegateV2` payloads to detect a `DeployContract` nested inside a delegate action [2](#0-1) , so `chunk_account.deploy_tx_count` is incremented — but for the wrong account, since `chunk_account` is `chunk_data.accounts.entry(signer_id.clone())` where `signer_id` is the relayer, not `delegate_action.sender_id` (the delegator).

This is a real, reachable pattern: `DeployContract` is explicitly a supported action inside a `DelegateAction`, executed against the delegating sender's own account with the relayer paying gas, as shown by the `meta_tx_deploy` test [3](#0-2)  and the `meta_tx_from_actions` helper that builds exactly such a transaction (`SignedTransaction::from_actions(relayer_nonce, relayer, sender, &relayer_signer, vec![Action::Delegate(...)], ...)`) [4](#0-3) . Action validation (`validate_delegate_action`) permits `DeployContract` as a delegated action and only restricts nested `Delegate`-in-`Delegate` and delete-must-be-final ordering [5](#0-4) , so nothing in transaction/action validation blocks this.

Consequently:
- `query_pending_state`/`check_pending` (used by `PendingTxSession` for chunk-production admission and by `get_pending_constraints` for RPC-side validation) looks up state keyed by `signer_id` [6](#0-5)  and [7](#0-6) , which for the delegator D is never populated by a meta-transaction deploy, since it was recorded under R.
- The deploy-exclusivity check (`total_deploy_count > 0` skip, `tx_has_deploy && total_access_key_count > 0` skip) and the P_MAX cap (`total_access_key_count >= P_MAX`) at lines 495-507 are evaluated against D's own (empty) bucket for any subsequent transaction D submits directly, meaning D's pending deploy is invisible to D's own future transactions.

### Impact Explanation
This module exists specifically to bound double-spend exposure for uncertified (Spice) chunks per NEP-611: the deploy-exclusivity rule prevents a contract-deploying account from having other concurrently-pending access-key transactions execute against speculative, not-yet-certified state, and P_MAX bounds the number of pending access-key transactions for contract accounts [8](#0-7) . By wrapping a `DeployContract` in a `DelegateAction` and having it relayed (even by a second account the same attacker controls), the delegator's own bucket in `pending_accounts` never reflects the pending deploy or resulting exclusivity/P_MAX pressure, so the delegator can submit further access-key transactions (which will be admitted/prepared) unconstrained by the deploy-exclusivity or P_MAX limits this queue is meant to enforce for that account, undermining the intended double-spend-exposure bound during the uncertified window.

This bug is scoped to the SPICE protocol feature, gated behind `spice_pending_transaction_queue_enabled` (disabled by default) [9](#0-8) , so it only matters on networks/configurations where this feature is active.

### Likelihood Explanation
Low cost and fully within an ordinary user's capability: fund two accounts (or use any willing relayer), sign a `DelegateAction` containing `DeployContract` targeting one's own account as receiver, and have it relayed as an outer `SignedTransaction`. No special privileges, no validator/node access, and no bypass of signature/nonce/action-limit checks is required — the flaw is purely in the accounting key used by the pending queue, not in signature or action validation. The attack is trivially repeatable since it only requires standard meta-transaction construction, which is a documented, tested feature (`meta_tx_deploy`).

### Recommendation
When building the per-tx accounting key(s) in `add_chunk_transactions`, iterate `tx.actions()` and, for `Action::Delegate`/`Action::DelegateV2`, attribute the corresponding deploy/access-key/balance effects to `signed_delegate.delegate_action.sender_id` rather than (or in addition to) the outer `tx.signer_id()`. The `paid_from_balance`/gas-payer bookkeeping should remain attributed to the relayer (who pays gas), but `deploy_tx_count`/`access_key_tx_count` used for P_MAX/deploy-exclusivity must be tracked per the actual mutated account (the delegate sender), mirroring how `check_actor_permissions` and actual execution attribute the mutation to the delegate's `sender_id`, not the relayer.

### Proof of Concept
Integration/test-loop test plan (extending `test-loop-tests/src/tests/pending_transaction_queue.rs` patterns):
1. Enable `spice_pending_transaction_queue_enabled`.
2. Create delegator account D (already having a deployed contract, to trigger P_MAX/exclusivity paths) and relayer account R.
3. Construct `DelegateAction{ sender_id: D, actions: [DeployContract(...)] }`, sign it with D's key, wrap into `SignedTransaction{ signer_id: R, actions: [Action::Delegate(signed_delegate)] }` signed by R (mirroring `meta_tx_from_actions`).
4. Submit this meta-tx and get it included (but not certified).
5. Assert `pending_transaction_queue.pending_accounts` has an entry for R with `deploy_tx_count == 1` but has no entry (or `deploy_tx_count == 0`) for D.
6. From D directly, submit an ordinary access-key transaction (e.g., transfer) and assert it is admitted (`PendingTxCheckResult::Admit`) instead of being `Skip`ped by deploy-exclusivity, demonstrating that D's own pending deploy is invisible to the constraint check that should block it.

fn is_deploy_like_action(action: &Action) -> bool {
    match action {
        Action::DeployContract(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::DeterministicStateInit(_) => true,
        Action::Delegate(signed_delegate) => {
            signed_delegate.delegate_action.get_actions().iter().any(is_deploy_like_action)
        }
        Action::DelegateV2(signed_delegate) => {
            signed_delegate.delegate_action.get_actions().iter().any(is_deploy_like_action)
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeleteAccount(_)
        | Action::TransferToGasKey(_)
        | Action::WithdrawFromGasKey(_) => false,
    }
}

/// Returns true if any action in the list is deploy-like.
fn has_deploy_action(actions: &[Action]) -> bool {

    fn query_pending_state(
        &self,
        signer_id: &AccountId,
        public_key: &PublicKey,
        nonce_index: Option<NonceIndex>,
    ) -> PendingStateSnapshot {
        let pending_account = self.pending_accounts.get(signer_id);
        let access_key_tx_count = pending_account.map(|a| a.access_key_tx_count).unwrap_or(0);
        let deploy_tx_count = pending_account.map(|a| a.deploy_tx_count).unwrap_or(0);
        let paid_from_balance =
            pending_account.map(|a| a.paid_from_balance).unwrap_or(Balance::ZERO);

        let gas_key = (signer_id.clone(), public_key.clone());
        let pending_gas_key_cost =
            self.pending_gas_key_costs.get(&gas_key).copied().unwrap_or(Balance::ZERO);

        let nonce_key = (gas_key.0, gas_key.1, nonce_index);
        let max_nonce = self.pending_nonces.get(&nonce_key).map(|n| n.max_nonce()).unwrap_or(0);

        PendingStateSnapshot {
            access_key_tx_count,
            deploy_tx_count,
            paid_from_balance,
            max_nonce,
            pending_gas_key_cost,
        }
    }

fn validate_delegate_action(
    limit_config: &LimitConfig,
    delegate_action: VersionedDelegateActionRef<'_>,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ActionsValidationError> {
    // Check the count before `get_actions()` clones the list, so a huge
    // nested-action list can't force the allocation before being rejected.
    // Consensus-neutral: same `TotalNumberOfActionsExceeded` as the check in
    // `validate_actions_with_mode` below.
    let num_actions = delegate_action.actions().len() as u64;
    if num_actions > limit_config.max_actions_per_receipt {
        return Err(ActionsValidationError::TotalNumberOfActionsExceeded {
            total_number_of_actions: num_actions,
            limit: limit_config.max_actions_per_receipt,
        });
    }
    let actions = delegate_action.get_actions();
    let inner_receiver =
        if ProtocolFeature::FixDelegatedDeterministicStateInit.enabled(current_protocol_version) {
            // This is the correct receiver id to use for the check.
            delegate_action.receiver_id()
        } else {
            // This is a bug fixed with `FixDelegatedDeterministicStateInit` that
            // validated against the wrong id. This makes it impossible to
            // initialize deterministic accounts from meta transactions.
            // The bug cannot be abused, if someone crafts a state init that passes
            // validation here, it will fail when it is checked as incoming receipt.
            receiver
        };
    validate_actions_with_mode(
        limit_config,
        &actions,
        inner_receiver,
        current_protocol_version,
        mode,
    )?;
    Ok(())
}
