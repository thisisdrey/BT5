### Title
Missing slippage/minimum-ratio protection in `ExchangeInjectActuator` allows sandwich-attack theft of value from TRC10 AMM liquidity providers - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
Java-tron's built-in bancor-style TRC10 token exchange (`Exchange`) supports three broadcastable operations: `ExchangeInjectContract` (add liquidity), `ExchangeWithdrawContract` (remove liquidity), and `ExchangeTransactionContract` (swap). The swap contract includes an `expected` field so a caller can bound the minimum output they will accept, giving slippage protection [1](#0-0) . The liquidity-injection contract has no equivalent field at all — `ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant`, with no user-supplied minimum/maximum bound on the paired token amount [2](#0-1) . This is the direct analog of the reported Uniswap `addLiquidity(..., amountAMin=0, amountBMin=0, ...)` slippage-protection gap: a liquidity-provision operation that commits a fixed input amount but lets the pool ratio at execution time freely determine the paired amount, with no way for the caller to guard against ratio movement between signing and packing.

### Finding Description
`ExchangeInjectActuator.execute` computes the paired ("another") token amount purely from the exchange's current on-chain balances at execution time using the constant-ratio formula, and applies it without any bound supplied by the transaction itself: [3](#0-2) 

`doValidate` for the inject only rejects a zero/negative computed amount and enforces balance limits — it never compares the computed `anotherTokenQuant` against anything the caller specified, unlike the swap actuator which enforces `anotherTokenQuant < tokenExpected`: [4](#0-3) 

Contrast with `ExchangeTransactionActuator.doValidate`, which does have an `expected` bound check: [5](#0-4) 

The pool ratio (`firstTokenBalance`/`secondTokenBalance`) used by inject is mutated by every prior `ExchangeTransactionContract` (swap) or `ExchangeInjectContract`/`ExchangeWithdrawContract` processed earlier in the same block, per `ExchangeCapsule.transaction`: [6](#0-5) . Because block producers (or any observer of the mempool) control transaction ordering within a block, an attacker can front-run a victim's `ExchangeInjectContract` with a large swap that skews the ratio, force the victim to deposit their fixed `quant` at the manipulated ratio (receiving a debited paired-token amount computed from the skewed pool), and then back-run with a reverse swap to restore the ratio and extract the difference — a classic sandwich attack. The victim has no on-chain field to express "do not inject if the implied paired amount deviates from what I expected," so they cannot protect themselves at the protocol level.

### Impact Explanation
This directly causes theft of user funds: liquidity providers using `ExchangeInjectContract` can be forced to inject assets at an attacker-manipulated ratio, transferring value to the attacker who reverses the price move afterward. Because `ExchangeInject`/`ExchangeTransaction`/`ExchangeWithdraw` are all standard signed transactions reachable by any account, this is exploitable by an unprivileged transaction broadcaster with no special permissions, satisfying "unauthorized... theft of funds" impact.

### Likelihood Explanation
Likelihood is high for active TRC10 exchange pairs: the attacker only needs to observe a pending `ExchangeInjectContract` in the mempool (or control ordering as a witness) and submit two ordinary `ExchangeTransactionContract` swaps around it. No special privileges, race conditions beyond standard MEV/front-running, or protocol bugs are needed — only the absence of any caller-specified bound in `ExchangeInjectContract`.

### Recommendation
Add a caller-specified minimum (and optionally maximum) acceptable paired-token amount to `ExchangeInjectContract` (mirroring the `expected` field already present in `ExchangeTransactionContract`), and enforce it in `ExchangeInjectActuator.doValidate`/`execute` by rejecting the injection if the computed `anotherTokenQuant` falls outside the caller's specified bound. The same protection should be considered for `ExchangeWithdrawContract`/`ExchangeWithdrawActuator`, which appears to have the same gap.

### Proof of Concept
1. Victim broadcasts `ExchangeInjectContract{exchange_id=X, token_id=A, quant=Q}` intending to inject at the current observed ratio `firstTokenBalance:secondTokenBalance`.
2. Attacker observes this transaction pending and submits `ExchangeTransactionContract` swapping a large amount of token B for token A on exchange X, shifting the pool ratio unfavorably for anyone injecting token A, and ensures it is ordered before the victim's transaction (e.g., via higher-priority ordering or same-block placement before the witness packs it).
3. Victim's `ExchangeInjectActuator.execute` computes `anotherTokenQuant` from the now-skewed balances at [7](#0-6) , debiting the victim's token B (or TRX) at the manipulated ratio with no minimum check to reject it.
4. Attacker submits a reverse `ExchangeTransactionContract` swap immediately after, restoring the ratio and extracting the spread — net profit taken from the victim's injected liquidity, with zero on-chain mechanism available to the victim to have prevented it.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
