Audit Report

## Title
Reentrant `CREATE2`-style instantiation collision in `pallet-contracts` bypasses the duplicate-contract guard (unlike the patched `pallet-revive`) - (File: `substrate/frame/contracts/src/exec.rs`)

## Summary
`pallet-contracts::ContractInfo::new` rejects a duplicate contract address only via `<ContractInfoOf<T>>::contains_key(account)` [1](#0-0) , but `push_frame` only writes contract info to `ContractInfoOf` for `Call` frames, explicitly skipping constructor frames [2](#0-1) . This means a re-entrant instantiate targeting the same deterministic address as an in-flight constructor is not detected, unlike `pallet-revive`, which added an explicit live-frame-stack check for exactly this case.

## Finding Description
`new_frame` computes the deterministic contract address via `Contracts::<T>::contract_address` and calls `ContractInfo::new(&account_id, nonce, code_hash)` as the sole collision guard [3](#0-2) . Because `push_frame` persists the top frame's `ContractInfo` to storage only when it is a `Call` frame ("We do not store on instantiate because we do not allow to call into a contract from its own constructor") [2](#0-1) , an address whose constructor is still executing is absent from `ContractInfoOf`, so `contains_key` cannot see it. `pallet-revive`'s `push_frame` was patched to close this exact gap by checking the live frame stack for an existing `Constructor` frame with the same `account_id` before pushing a new constructor frame [4](#0-3) , documented in `prdoc/pr_12645.prdoc` as fixing issue #12639. `pallet-contracts` has no analogous check anywhere in its `push_frame` or `ContractInfo::new` logic.

## Impact Explanation
A successful collision permits two constructor executions against a single account/trie, corrupting code reference-counting and storage-deposit accounting invariants, and can lead to orphaned/permanently locked storage deposits and inconsistent contract/child-trie state — a runtime bug compromising the intended behavior of the public `instantiate`/`instantiate_with_code` extrinsics, reachable by any unprivileged account.

## Likelihood Explanation
The exploit path requires only a self-deployed, attacker-controlled factory contract whose constructor re-enters the same call context to instantiate another contract with a fixed, attacker-chosen `salt` and `code_hash`, matching the deterministic address formula in `DefaultAddressGenerator::contract_address` [5](#0-4) . This is self-inflicted and deterministic within a single transaction via call-stack re-entrancy alone, as demonstrated by `pallet-revive`'s regression test `reentrant_instantiate_at_same_address_is_rejected` [6](#0-5) , which has no equivalent in `pallet-contracts`.

## Recommendation
Port the `pallet-revive` fix to `pallet-contracts::push_frame`: before pushing a new `Constructor` frame, walk the existing frame stack for any frame with `entry_point == ExportedFunction::Constructor` and the same `account_id`, and return `Error::<T>::DuplicateContract` if found, mirroring `substrate/frame/revive/src/exec.rs:1238-1246`.

## Proof of Concept
1. Deploy factory contract `F` in `pallet-contracts`.
2. `F`'s constructor, when invoked via `instantiate_with_code`/`instantiate` at computed address `X` (fixed `sender=F`, `code_hash=C`, `salt=S`), re-enters `F`'s own call/message-handling path (e.g., via a nested `seal_instantiate` host call) to instantiate the same `code_hash=C` with the same `salt=S` again from the same `sender=F` before the first constructor returns.
3. `Contracts::<T>::contract_address(&F, &C, input, S)` yields the same address `X` both times, per the deterministic formula [5](#0-4) .
4. Because `ContractInfoOf::<T>` for `X` was never inserted for a `Constructor` frame (only for `Call` frames) [2](#0-1) , `ContractInfo::new`'s `contains_key(X)` check passes a second time, and a second constructor frame executes against `X` — mirroring the scenario `pallet-revive`'s test `reentrant_instantiate_at_same_address_is_rejected` reproduces and rejects, which `pallet-contracts` has no equivalent guard against.
