### Title
Attacker-Controlled `HandshakeTime` in Peer Payload Enables Handshake-Freshness Bypass / Tunnel Takeover - (File: `handshake_manager.go`)

### Summary
`HandshakeManager.CheckAndComplete` decides whether a newly-arriving handshake should replace an existing, established `HostInfo` for the same VPN address by comparing `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime`. `lastHandshakeTime` is populated directly from the `Time` field of the handshake payload (`processPayload` → `m.result.HandshakeTime = payload.Time`), a value the remote peer places on the wire itself, not a value nebula derives from its own trusted local clock or a monotonically-tracked internal counter. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The comment on the field itself states the intent: "This is used to avoid an attack where a handshake packet is replayed after some time." That is, `lastHandshakeTime` is supposed to act as a freshness/anti-replay marker analogous to Yearn's `totalIdle` — an authoritative, tamper-resistant tracked value. Instead, exactly like `_yTotalAssets()` reading a spoofable `balanceOf` instead of the tracked `totalIdle`, nebula reads this "freshness" value straight out of attacker-supplied wire data (`payload.Time`, decoded in `handshake/payload.go` as a raw varint field with no bound to real time) and stores it verbatim as `hostinfo.lastHandshakeTime`. [4](#0-3) 

Because `CheckAndComplete` only rejects a new handshake as stale when `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime`, an attacker who can complete a valid noise handshake (which does require possession of a certificate signed by a trusted CA — see the constraint below) can simply set `payload.Time` to a very large value on every handshake attempt, guaranteeing it is always treated as "newer" and is always allowed to evict/replace the existing hostinfo for that vpnAddr, regardless of true handshake ordering.

### Impact Explanation
If any two hosts trusted by the same CA are compromised or a malicious insider is present, this logic allows deliberate manipulation of which handshake "wins" the race for a given VPN address's `HostInfo` slot, undermining the freshness/anti-replay guarantee the field is designed to provide and potentially enabling forced tunnel resets/renegotiation (a form of remote state poisoning of the hostmap) at a time of the attacker's choosing, bypassing the intended ordering protection. This is a lower-severity issue than a full authentication bypass since a valid CA-signed cert is still required to complete the handshake in the first place, but it is a genuine "trust an attacker-manipulable value instead of an authoritative tracked one" defect of the same class as the Yearn finding.

### Likelihood Explanation
Any peer that can complete a handshake (i.e., holds a valid nebula certificate for the mesh) can trivially set this field to any value; no special conditions or race are needed beyond normal handshake participation.

### Recommendation
Do not trust a peer-supplied timestamp for freshness/ordering decisions. Use the receiving node's own local monotonic clock at the time it processes and locally records the handshake (i.e., a value tracked internally, not read from the wire) to determine which handshake is authoritative, mirroring the fix of preferring `totalIdle` (self-tracked) over `balanceOf` (externally observable/manipulable).

### Proof of Concept
1. Attacker holds a valid cert signed by the network's CA (a legitimate but potentially compromised/malicious peer).
2. Attacker completes a handshake with a target and observes that `payload.Time` is echoed back into `hostinfo.lastHandshakeTime` unmodified: [5](#0-4) .
3. On the next handshake attempt (or a replayed/staged one), attacker sets `Time` to `math.MaxUint64` in the outgoing handshake payload.
4. In `CheckAndComplete`, `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` evaluates false because the new value is maximal, so the check at [6](#0-5)  never triggers `ErrExistingHostInfo`, and the new (attacker-timed) handshake always displaces the existing one — regardless of actual chronological order of the underlying noise handshake completion.
