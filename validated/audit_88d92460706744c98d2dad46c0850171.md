The sample configs even show `endpoint = "0.0.0.0:30000"` for the signer's `SignerEventReceiver` bind address [1](#0-0) , and `SpawnedSigner::new` binds directly to this operator-configured `endpoint` with no additional access control layer [2](#0-1) . The `/shutdown` route match is purely on URL path string equality with no secret, token, or peer-identity check [3](#0-2) , whereas the code's own comment states the design intent is that only the paired node process (via `SignerStopSignaler::send`) should trigger this [4](#0-3) . ### Title
Unauthenticated remote shutdown of signer's `SignerEventReceiver` via `/shutdown` HTTP path - (File: libsigner/src/events.rs)

### Summary
The `SignerEventReceiver`'s HTTP listener treats any POST to `/shutdown` as an authoritative stop signal, regardless of sender identity, with no secret, token, or IP check. Any remote party that can reach the bound event-receiver port can permanently kill the signer's event-processing loop with a single crafted request.

### Finding Description
`SignerEventReceiver::bind` opens a plain `tiny_http` HTTP server on the operator-configured `endpoint` [6](#0-5) . Sample production configs explicitly bind this to `0.0.0.0:30000`, i.e., all interfaces, not loopback-only [1](#0-0) . Inside `next_event`, requests are dispatched purely by matching `request.url()` against fixed strings; there is no check of source address, no shared secret, no signature, nothing analogous to the node's `auth_token`/`auth_password` pairing used for the node→signer event POSTs described in `docs/signing.md` [7](#0-6) . When `request.url() == "/shutdown"`, the handler unconditionally sets `stop_signal` to `true` via `Ordering::SeqCst` and returns `EventError::Terminated` [3](#0-2) . `main_loop` treats `EventError::Terminated` as a clean exit condition and breaks the loop for good [5](#0-4) , and there is no restart logic in `Signer::spawn` [8](#0-7) . The intended caller of this shutdown path is the node itself via `SignerStopSignaler::send`, which builds the exact same POST but is only reachable by the local stacks-node process holding the loopback socket in typical deployments; nothing in the code enforces that restriction [9](#0-8) . Any TCP client that can complete an HTTP/1.1 request to this port can therefore trigger the same effect.

### Impact Explanation
A single unauthenticated POST permanently halts the `SignerEventReceiver::main_loop`, so the signer process stops receiving `stackerdb_chunks`, `proposal_response`, `new_burn_block`, and `new_block` events from its node, and its `forward_event` channel goes silent — effectively taking that signer out of block-validation/signing participation until manually restarted. This matches the "Critical - remote crash/unauthenticated DoS from few messages" category since it is a full functional crash of the signer's event pipeline from one request.

### Likelihood Explanation
Exploitability depends entirely on whether the signer's `endpoint` is reachable from the attacker's network position. Reference/sample configs bind it to `0.0.0.0`, and `docs/signing.md` warns that the endpoint is meant to be reached only by the paired node [10](#0-9) , but nothing in the code enforces this; if an operator's firewall/network does not restrict access to that port (which the code gives no assistance in doing), any remote party can send the request. `SpawnedSigner::new` itself warns operators about exactly this class of risk when the signer talks to a non-local node, but the mitigation is left entirely to operator-side network hardening, not to the code [11](#0-10) . Given only network reachability is required (no secret, no privileged role), likelihood is high wherever the port is exposed.

### Recommendation
Require the same authentication mechanism used elsewhere (e.g., a shared secret/token checked against a header, or restrict `/shutdown` handling to connections originating from the configured node's loopback/allow-listed address) before honoring `/shutdown`. At minimum, bind the event receiver to `127.0.0.1` by default and document/enforce that `0.0.0.0` bindings require an additional auth check on the `/shutdown` (and other) routes.
