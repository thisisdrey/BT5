Audit Report

## Title
Single griefing contributor can permanently block `Crowdloan::refund` for all other contributors and prevent fund dissolution - ([File: polkadot/runtime/common/src/crowdloan/mod.rs])

## Summary
`Pallet::refund` iterates all contributors of an ended crowdloan and pushes a `CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?` for each one inside the loop; because the entire dispatchable is wrapped in `with_storage_layer` (an implicit `frame_support::storage::with_transaction`), any single failed transfer propagated by `?` rolls back the whole call — including refunds already applied to earlier, honest contributors in that same call. Since `dissolve` requires `fund.raised.is_zero()`, one attacker whose refund destination cannot accept the transfer can permanently block refunds and fund dissolution for every other contributor and the depositor's `SubmissionDeposit`.

## Finding Description
The loop is confirmed exactly as cited: [1](#0-0) . Every pallet call, including `refund`, is compiled to run inside `frame_support::storage::with_storage_layer`, which uses `with_transaction` under the hood, so any `Err` returned anywhere in the call rolls back all storage mutations performed during that call: [2](#0-1)  and [3](#0-2) .

Balances confirms that a transfer to a non-existing account for an amount below `ExistentialDeposit` fails deterministically regardless of the `ExistenceRequirement` used for the sender: [4](#0-3)  and the underlying `deposit_creating`/`can_deposit` logic enforces `ensure!(value >= ed || !is_new, Error::<T,I>::ExistentialDeposit)`: [5](#0-4) .

`MinContribution` is documented only as a recommendation ("Should almost certainly be at least `ExistentialDeposit`") and is not enforced anywhere in `do_contribute` or `create`: [6](#0-5) , [7](#0-6) . There is no code-level guard preventing a runtime/parachain-specific config from setting `MinContribution` below `ExistentialDeposit`. `contribution_iterator` always begins iterating the child trie from the same starting prefix on every call, so a poisoned entry is hit again on every future `refund` attempt: [8](#0-7) . `dissolve` requires `fund.raised.is_zero()`, which can never be reached while the poisoned contribution remains: [9](#0-8) .

Existing guards reviewed and shown insufficient: `ensure_crowdloan_ended` only checks the block number/lease period and that `fund_account` free balance covers `fund.raised` — it does nothing to validate that every individual contribution can still be paid back to its specific destination account: [10](#0-9) . Nothing in `refund` isolates or skips a failed per-contributor transfer.

## Impact Explanation
This is a config-contingent but real "permanent user-fund lock": once a contributor's refundable balance is below `ExistentialDeposit` and their account has been reaped, `refund` deterministically fails at that entry on every call, blocking refunds to all other contributors sharing that fund and preventing `dissolve` from ever succeeding, locking both the remaining pot and the depositor's `SubmissionDeposit`. This matches the "permanent user-fund lock" category in the impact gate. [11](#0-10) 

## Likelihood Explanation
The exploit requires `MinContribution` (the amount the attacker contributes, which is what gets refunded) to be smaller than `ExistentialDeposit` at refund time — a condition the code does not prevent, but which is only met if the crowdloan's configured `MinContribution` is set at or below `ExistentialDeposit`. Checked production values in this repo (e.g. Westend's `MinContribution: Balance = 100 * CENTS` versus the recommended relationship to `ExistentialDeposit`) suggest current relay-chain crowdloan configs intentionally keep `MinContribution` well above `ExistentialDeposit`, precisely to avoid this scenario, per the doc comment guidance. I was not able to fully confirm the exact numeric `ExistentialDeposit` constant for Westend/Polkadot in this session, so I cannot state with certainty whether any live configuration currently violates this relationship; the attack is only reachable if a deployer/parachain sets `MinContribution` below `ExistentialDeposit`, which is a configuration choice not enforced by code, making exploitability config-dependent rather than universally live on all currently observed runtime parameters.

## Recommendation
Enforce `MinContribution >= ExistentialDeposit` at `create`/`do_contribute` time (defensive assertion or `ensure!`), and independently harden `refund` to not let one failed transfer abort the whole batch — e.g., catch the transfer error per contributor, log/emit a defensive event, and skip/quarantine that entry (or route it to a separate claim mechanism) while continuing to refund the rest.

## Proof of Concept
1. Deploy/parametrize a runtime where `Crowdloan::Config::MinContribution` is at or below `ExistentialDeposit` (not prevented by any code-level check).
2. Attacker contributes exactly `MinContribution` via `Crowdloan::contribute`.
3. Attacker transfers away the remainder of their balance so their account is reaped (loses all providers, balance goes to zero).
4. After `fund.end`, call `Crowdloan::refund`; the loop reaches the attacker's entry, `CurrencyOf::<T>::transfer(&fund_account, &attacker, balance, AllowDeath)` fails with `Error::ExistentialDeposit`/`TokenError::BelowMinimum`, `?` propagates the error, and `with_storage_layer` rolls back the whole call, including refunds already applied to earlier contributors.
5. Every subsequent call to `refund` hits the same entry first (fixed iteration start) and fails identically; `dissolve` can never succeed since `fund.raised` never reaches zero.

		/// Due to weight restrictions, this function may need to be called multiple
		/// times to fully refund all users. We will refund `RemoveKeysLimit` users at a time.
		///
		/// Origin must be signed, but can come from anyone.
		#[pallet::call_index(3)]
		#[pallet::weight(T::WeightInfo::refund(T::RemoveKeysLimit::get()))]
		pub fn refund(
			origin: OriginFor<T>,
			#[pallet::compact] index: ParaId,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			let mut fund = Funds::<T>::get(index).ok_or(Error::<T>::InvalidParaId)?;
			let now = frame_system::Pallet::<T>::block_number();
			let fund_account = Self::fund_account_id(fund.fund_index);
			Self::ensure_crowdloan_ended(now, &fund_account, &fund)?;

			let mut refund_count = 0u32;
			// Try killing the crowdloan child trie
			let contributions = Self::contribution_iterator(fund.fund_index);
			// Assume everyone will be refunded.
			let mut all_refunded = true;
			for (who, (balance, _)) in contributions {
				if refund_count >= T::RemoveKeysLimit::get() {
					// Not everyone was able to be refunded this time around.
					all_refunded = false;
					break;
				}
				CurrencyOf::<T>::transfer(&fund_account, &who, balance, AllowDeath)?;
				CurrencyOf::<T>::reactivate(balance);
				Self::contribution_kill(fund.fund_index, &who);
				fund.raised = fund.raised.saturating_sub(balance);
				refund_count += 1;
			}

			// Save the changes.
			Funds::<T>::insert(index, &fund);

			if all_refunded {
				Self::deposit_event(Event::<T>::AllRefunded { para_id: index });
				// Refund for unused refund count.
				Ok(Some(T::WeightInfo::refund(refund_count)).into())
			} else {
				Self::deposit_event(Event::<T>::PartiallyRefunded { para_id: index });
				// No weight to refund since we did not finish the loop.
				Ok(().into())
			}
		}

	fn ensure_crowdloan_ended(
		now: BlockNumberFor<T>,
		fund_account: &T::AccountId,
		fund: &FundInfo<T::AccountId, BalanceOf<T>, BlockNumberFor<T>, LeasePeriodOf<T>>,
	) -> sp_runtime::DispatchResult {
		// `fund.end` can represent the end of a failed crowdloan or the beginning of retirement
		// If the current lease period is past the first period they are trying to bid for, then
		// it is already too late to win the bid.
		let (current_lease_period, _) =
			T::Auctioneer::lease_period_index(now).ok_or(Error::<T>::NoLeasePeriod)?;
		ensure!(
			now >= fund.end || current_lease_period > fund.first_period,
			Error::<T>::FundNotEnded
		);
		// free balance must greater than or equal amount raised, otherwise funds are being used
		// and a bid or lease must be active.
		ensure!(
			CurrencyOf::<T>::free_balance(&fund_account) >= fund.raised,
			Error::<T>::BidOrLeaseActive
		);

		Ok(())
	}

pub fn with_transaction<T, E, F>(f: F) -> Result<T, E>
where
	E: From<DispatchError>,
	F: FnOnce() -> TransactionOutcome<Result<T, E>>,
{
	// This needs to happen before `start_transaction` below.
	// Otherwise we may rollback the increase, then decrease as the guard goes out of scope
	// and then end in some bad state.
	let _guard = inc_transaction_level().map_err(|()| TransactionalError::LimitReached.into())?;

	start_transaction();

	match f() {
		TransactionOutcome::Commit(res) => {
			commit_transaction();
			res
		},
		TransactionOutcome::Rollback(res) => {
			rollback_transaction();
			res
		},
	}
}
