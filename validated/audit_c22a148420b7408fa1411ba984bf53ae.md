## Local Analog Found

Root cause of the Cap Finance bug: a per-call rate/reward accumulator advances its "last update" checkpoint to `now` unconditionally, while the accrued amount is computed via integer division over `elapsed`. An unprivileged actor who forces `elapsed` to stay at its minimum value (by calling the update path every block) drives the division numerator below the denominator, causing perpetual truncation to zero and permanently starving the accrual — even though a naturally-spaced call sequence would have produced a non-zero, correctly compounding result.

This exact pattern exists in `pallet-asset-rewards`.

### Title
Reward-per-token accrual can be permanently frozen by forcing single-block updates - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet_asset_rewards::Pallet::reward_per_token` computes accrued rewards as `rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR / total_tokens_staked`, and `update_pool_rewards` always resets `last_update_block` to the current block regardless of whether `reward_per_token_stored` actually changed. Because `PRECISION_SCALING_FACTOR` is only `4096` [1](#0-0) , any pool where `total_tokens_staked` exceeds `reward_rate_per_block * 4096` will floor-divide to `0` when `blocks_elapsed == 1`. Any unprivileged account can force `blocks_elapsed` to always equal `1` by invoking a public extrinsic (`stake`, `unstake`, or `harvest_rewards`) once per block, which permanently prevents `reward_per_token_stored` from ever increasing.

### Finding Description
`reward_per_token` computes rewardable blocks as `now - last_update_block`, then accrues: [2](#0-1) 

`update_pool_rewards` is the only place `last_update_block` is written, and it is set unconditionally to the current block every time it is invoked, independent of whether `reward_per_token` actually advanced: [3](#0-2) 

`update_pool_and_staker_rewards` (which calls the above) is invoked at the start of `stake`, `unstake`, and `harvest_rewards` — all plain, permissionless, signed extrinsics with no cooldown or minimum-elapsed-blocks guard: [4](#0-3) [5](#0-4) 

Because the arithmetic performs `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR` before dividing by `total_tokens_staked` — exactly the same order-of-operations pattern as the vulnerable `VaultAdapter.sol` calculation — an attacker who calls `stake` (even with a `0`/dust amount, since there is no minimum-amount check on `stake`) once per block keeps `blocks_elapsed` pinned at `1` on every subsequent call. If `reward_rate_per_block * 4096 < total_tokens_staked`, the numerator is smaller than the denominator on every single call, so the division always floors to `0`, and `last_update_block` is advanced to `now` each time — permanently discarding the "1 block worth" of reward instead of ever letting `blocks_elapsed` grow large enough for the division to round up to a non-zero value. Existing guards (`ensure_signed`, the `expiry_block`-based `BadOrigin` check in `unstake`/`harvest_rewards`) do not prevent this because the attacker is calling as themselves (or as any staker) with a normal, permitted extrinsic — no privileged or malicious-node assumption is required.

### Impact Explanation
All stakers of the affected pool are permanently denied reward accrual: `reward_per_token_stored` never increases while the attack is sustained, so `derive_rewards` (`staker_info.amount * (reward_per_token - reward_per_token_paid) / PRECISION_SCALING_FACTOR`) always yields `0` new reward for every staker regardless of stake size or real elapsed time [6](#0-5) . The reward tokens already deposited into the pool's pot account remain effectively locked/undistributed for as long as the attacker griefs the pool, which only costs one low-amount extrinsic per block. This matches the "permanent user-fund lock" / broken payout-settlement impact class.

### Likelihood Explanation
High: no privileged origin, governance, validator, or off-chain assumption is needed. The attacker only needs to be able to submit a signed extrinsic once per block (any staker of the pool, or anyone who can call `stake` with a small amount) and pay the ordinary transaction fee. Whether the bug triggers depends on the ratio of `reward_rate_per_block * 4096` to `total_tokens_staked`, which is realistic for pools with large stake and modest reward rates — a configuration entirely plausible for production reward pools.

### Recommendation
Do not update `last_update_block` unconditionally. Either (a) only advance `last_update_block` when `reward_per_token` actually changes (leaving unaccounted elapsed blocks pending so they can accumulate into a later, non-truncating computation), or (b) perform the division with round-up/carry semantics (e.g., track a remainder or use higher precision) so repeated small-window calls cannot systematically lose precision compared to a single larger-window call, matching the same fix approach recommended for `VaultAdapter.sol` (avoid pre-dividing per-call before multiplying by the accumulated variable).

### Proof of Concept
1. Admin creates a pool with `reward_rate_per_block = R` and lets `total_tokens_staked` grow (via legitimate staking) such that `R * 4096 < total_tokens_staked`.
2. Attacker calls `stake(pool_id, 0_or_dust)` (or any staker calls `harvest_rewards`) once in block `N`. This triggers `reward_per_token` with `blocks_elapsed = N - last_update_block` computed normally, then `update_pool_rewards` sets `last_update_block = N`.
3. Attacker repeats the same call in block `N+1`, `N+2`, ... every single block. Each time `blocks_elapsed = 1`, so `R * 1 * 4096 / total_tokens_staked` floors to `0` (since `R*4096 < total_tokens_staked`), and `reward_per_token_stored` never changes while `last_update_block` keeps advancing.
4. Any legitimate staker calling `harvest_rewards` at any point receives `0` in `staker_info.rewards`, despite real block time having elapsed and the pool having accumulated a non-zero reward budget if computed over the full unattacked window.

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
