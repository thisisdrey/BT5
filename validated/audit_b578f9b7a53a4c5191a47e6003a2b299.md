### Title
Anti-replay window Check/Update split allows two concurrent packets with the same message counter to both decrypt before the window is marked as seen - ([File: connection_state.go])

### Summary
The Beedle report describes a classic **Checks-Effects-Interactions** violation: a re-entrant call is possible in the window between an external interaction and the state update that is supposed to prevent it from being reused. The closest reachable analog in Nebula, exploitable by an unauthenticated remote UDP peer without a CA-signed certificate needing to be valid (this happens on already-established connections, but is driven purely by attacker-controlled packet counters that are not re-verified between the two locking sections), is in `ConnectionState.Decrypt` (and identically in `VerifyRelay`), where the anti-replay window "Check" and "Update" are two *separate* critical sections with unlocked, expensive work (AEAD decryption) happening in between.

### Finding Description
`ConnectionState.Decrypt` in `connection_state.go` performs the CEI-relevant sequence:
1. Lock, `cs.window.Check(l, messageCounter)`, unlock — checks if `messageCounter` was already seen.
2. `cs.dKey.DecryptDanger(...)` — performs the actual AEAD decryption, **without holding the lock**.
3. Lock, `cs.window.Update(l, messageCounter)`, unlock — marks `messageCounter` as seen (the actual state mutation). [1](#0-0) 

Because `Check` and `Update` are not atomic with respect to each other, two UDP packets carrying the identical `messageCounter` that arrive concurrently (trivial for a network attacker to craft/duplicate/replay at the UDP layer before the CA/cert boundary even matters, since this fires on the data-plane path for any already-negotiated tunnel index) can both pass `Check` before either calls `Update`. Both then proceed to call `DecryptDanger` and both succeed, and only afterward is `Update` invoked — by which time the "effect" (state mutation marking the counter consumed) happens strictly after the "interaction" (decrypting attacker payload and, in `readOutsidePackets`, running the full downstream side effects: `f.handleHostRoaming`, `f.connectionManager.In`, and dispatch to message/lighthouse/control handlers) has already occurred for both packets.

`VerifyRelay` has the identical pattern for relay-verified frames. [2](#0-1) 

This is invoked from the outside packet path exactly once per packet, with the lock releases sitting exactly at the CEI-violating positions: [3](#0-2) 

Note that the project's own changelog explicitly acknowledges a related but distinct issue — corruption of the window state under concurrent access — was fixed by adding locking around `Update` itself (`Lock replay window updates so concurrent readers can't corrupt it`, #1802) and around relay replay advancement (#1751). [4](#0-3)  That fix only serializes each individual `Check` or `Update` call; it does not make the `Check`→decrypt→`Update` sequence atomic as a whole, which is the root cause of the residual TOCTOU race analogous to the reported Lender `refinance` reentrancy (external/expensive interaction sandwiched between a check and the corresponding state commit).

### Impact Explanation
An attacker who can duplicate or race two copies of the same encrypted data packet at the UDP layer (no valid certificate required — this operates purely on ciphertext/counter fields of an already-established tunnel index) can cause the anti-replay window to accept and fully process a duplicated message twice: both invocations decrypt successfully and both are handed to `readOutsidePackets`'s post-decrypt side effects (roaming update, connection-manager liveness tracking, and message dispatch to the TUN device / lighthouse / control-message handlers). This directly undermines the anti-replay guarantee Nebula's `ConnectionState` is supposed to provide, allowing limited packet replay/duplication of otherwise legitimate traffic within a race window, which is the network-protocol analog of draining state via a reentrant transfer in the original report.

### Likelihood Explanation
Requires only two UDP datagrams (a genuine packet plus its attacker-forged/replayed duplicate) delivered close enough in time to both reach the unlocked decrypt call before the first `Update` commits — no cryptographic material or certificate forgery is needed, only network-level duplication/race timing, which is readily achievable by a network attacker or a malicious/duplicating on-path relay. This is a genuine, currently-present race in the reachable data-plane decrypt path, not merely a theoretical concern, though the practical window is narrow (bounded by AEAD decrypt time).

### Recommendation
Hold `decryptLock` across the entire Check → Decrypt → Update sequence in both `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`, so the anti-replay window check and its corresponding update are atomic with respect to the decrypt operation, eliminating the TOCTOU race — i.e., apply the CEI pattern by moving the "effect" (window update) to happen atomically with the "check," not after the "interaction" (decrypt).

### Proof of Concept
Conceptual PoC (race, not exploit code since no terminal access is available here):
1. Attacker captures or forges a valid ciphertext packet `P` for an established tunnel with `messageCounter = N`.
2. Attacker sends `P` twice back-to-back (or via two sockets) to the target's UDP listener so both copies are read by concurrent `readOutsidePackets` goroutines/threads.
3. Goroutine A calls `Decrypt`: `window.Check(N)` succeeds, lock released.
4. Before goroutine A calls `window.Update(N)`, goroutine B (processing the duplicate) also calls `window.Check(N)`, which also succeeds because `Update` has not yet run.
5. Both goroutines successfully `DecryptDanger` the same ciphertext and proceed into `readOutsidePackets`'s post-decrypt handling (roaming, connection-manager `In`, message dispatch) before either calls `Update`.
6. Result: the same on-wire message counter is accepted and processed twice, defeating the anti-replay window despite the per-call locking added in commit history (#1802). [1](#0-0)

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
