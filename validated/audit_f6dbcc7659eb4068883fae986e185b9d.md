## Title
Unsanitized `remote_patches` filenames/URLs allow shell-command injection in `patch()` when falling back to external patch tool - (File: `tools/build_defs/repo/utils.bzl`)

## Summary
The reported Django bug is a class of "attacker-controlled string is concatenated unescaped into a structurally-interpreted command (SQL query)." The closest reachable analog in Bazel is the `patch()` helper in `tools/build_defs/repo/utils.bzl`, which builds a shell command by string interpolation and hands it to `bash -c` / `powershell /c` without quoting the patch file path, while the *set* of patch files/URLs (`remote_patches`, keyed by filename) can originate from content that an unprivileged actor controls (a registry's `source.json`, or archive-provided patch names via bzlmod module resolution).

## Finding Description
`patch()` is the common implementation used by `http_archive`, `git_repository`, and bzlmod's internal repo-spec builders to apply patches after fetching a repository: [1](#0-0) 

For each entry in `patches`, when falling back to a non-native patch tool (triggered automatically whenever `patch_tool` is set or `patch_args` contains anything other than `-p`), the code builds: [2](#0-1) 

```
command = "{patchtool} {patch_args} < {patchfile}".format(
    patchtool = patch_tool,
    patchfile = ctx.path(patchfile),
    patch_args = " ".join(["'%s'" % arg for arg in patch_args]),
)
st = ctx.execute([bash_exe, "-c", command], working_directory = patch_directory or "")
```

Only `patch_args` elements are quoted (with single quotes, which is itself insufficient if an arg contains a `'`). The `patchfile` path is interpolated **completely unquoted** into a string that is then executed as `bash -c "<command>"` (or PowerShell for `patch_cmds_win`, similarly unquoted for `cmd` entries). Any shell metacharacter in the resolved path — spaces, `;`, `$( )`, backticks, `>` — is interpreted by the shell rather than treated as literal path data, exactly analogous to how the JSONField `KeyTransform` bug let a raw string reach the SQL parser as syntax instead of as data.

The remote patch set is populated from `remote_patches`, a `string_dict` whose **keys are the download URLs/paths of patch files and whose names ultimately determine on-disk filenames** used later as `patchfile` in the same `patch()` function: [3](#0-2) 

These remote patches are typically populated for Bazel modules resolved through bzlmod from a registry's `source.json` `"patches"` map (patch filename → integrity hash), as documented: [4](#0-3) 

The registry's `bazel_registry.json`/`source.json` content is exactly the kind of unprivileged, attacker-served input covered by this analysis: a hostile or compromised registry mirror controls the **patch filename string** (the map key), while only the patch **file contents** are integrity-checked via the recorded checksum. Bazel's checksum verification binds the byte content of the patch archive/file to a hash, but it does not constrain or sanitize the filename/key used to name that file on disk or to build the shell command in `patch()`. If a registry serves a patch entry whose key contains shell metacharacters (e.g. `"a.patch; touch pwned"` or `"a.patch $(id)"`), that string is used to name the downloaded artifact and subsequently interpolated unquoted into the `bash -c` command string when the module (or any `http_archive`/`git_repository` using `patch_tool`) falls back to the external patch tool.

## Impact Explanation
If reachable with attacker-controlled key content, this results in **arbitrary command execution during repository fetch**, i.e., a checksum/integrity mechanism that verifies the wrong artifact (patch bytes) while leaving a structurally significant string (the filename used to build a shell command) completely unverified and unsanitized — the same "verified content, unverified structure" class as the SQL injection report. This would allow a malicious registry or MITM'd mirror (backed by no sha/integrity binding on the *name*) to execute code on the build machine outside the sandbox, during the loading/fetch phase, which runs with the invoking user's privileges.

## Likelihood Explanation
Moderate-to-low confidence rather than fully confirmed: the sandboxed index in this snapshot does not expose the Java-side `IndexRegistry`/`RegistryFunction`/`ArchiveRepoSpecBuilder` classes that construct the `remote_patches` dict from `source.json`, so I could not directly confirm whether the registry-provided patch filename/key is used verbatim as the `patches`/`remote_patches` map key without any sanitization or whitelist of characters before reaching `ctx.path(patchfile)` in `patch()`. The Starlark-level code (`tools/build_defs/repo/utils.bzl`) itself unambiguously performs unquoted string interpolation of `patchfile` into a shell command whenever a non-native patch tool is used, which is the vulnerable sink; the missing piece is full confirmation of the untrusted-source-to-sink data flow for the filename component specifically (as opposed to the well-known checksum-verified byte content).

## Recommendation
- Quote `patchfile` (and every `patch_args` entry) properly for shell execution, or avoid `bash -c`/string interpolation entirely by passing arguments as a list to `ctx.execute()` (which already supports argument lists) instead of building a single command string.
- Reject/sanitize registry- or archive-supplied patch filenames that contain characters outside a safe allow-list (e.g., `[A-Za-z0-9._-]`) before using them to name on-disk files or interpolate them into any command string.
- Audit all other locations in `tools/build_defs/repo/utils.bzl` and bzlmod's repo-spec builders where filenames derived from `source.json`/registry data are used to construct commands or paths, to ensure containment and lack of shell metacharacter interpretation.

## Proof of Concept
Not fully reproducible from the available index — a concrete JUnit/`src/test/shell/bazel` PoC would need to demonstrate a `source.json`/`remote_patches` entry with a filename such as `foo.patch; touch /tmp/pwned` reaching `patch()`'s `patchtool ... < {patchfile}` command construction with `patch_tool` set (forcing the non-native code path), and observing shell-command execution. This requires confirming, in the Java-side registry/module-resolution code (not present in this index snapshot), that the `source.json` `"patches"` map key is passed through unsanitized as the `remote_patches` dict key/filename. A Devin session with full repository access would be needed to trace `IndexRegistry`/`ArchiveRepoSpecBuilder` and construct/execute this PoC.
