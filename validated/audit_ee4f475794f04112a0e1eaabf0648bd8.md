### Title
Precompiled contract input length fields used for unchecked array allocation - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array` and `extractBytesArray` read a 32-byte "length" word directly out of attacker-supplied precompile call data and immediately use it to size a Java array (`new byte[len][]`), with no upper bound check against the actual size of the supplied `data`/`words` before allocation. [1](#0-0) 

### Finding Description
`extractBytes32Array(DataWord[] words, int offset)` takes `len = words[offset].intValueSafe()` and allocates `new byte[len][]` without validating that `len` corresponds to the actual number of words available in `words`, then loops `for (i = 0; i < len; i++)` reading `words[offset + i + 1]`.
`extractBytesArray(DataWord[] words, int offset, byte[] data)` similarly derives `len` from an attacker-controlled word and allocates `byte[len][]` before any per-element bounds are checked. [1](#0-0) 

This is structurally the same bug class as CVE-2025-8885: a length value taken from untrusted input is used to size a memory allocation before any validation that the claimed length is consistent with the actual available data, allowing an attacker to force excessive allocation (CWE-770) with a small, cheap input. In Bouncy Castle's case it was an OID length field driving allocation in `ASN1ObjectIdentifier`; here it is a calldata "array length" word driving a `new byte[len][]` allocation inside a TVM precompiled-contract call path.

### Impact Explanation
Any account or contract that can invoke one of the precompiled contracts consuming these helpers (batch signature/array-based precompiles) can pass a very large 32-byte length word (up to `Integer.MAX_VALUE`-ish via `intValueSafe()`), causing the node to attempt to allocate an oversized object-reference array. This can throw `OutOfMemoryError`, and depending on where the error propagates in the execution/validation path, it can destabilize the executing thread or the whole node process, i.e. a resource-exhaustion / crash condition reachable purely from a broadcast transaction that calls a smart contract. This is a memory-exhaustion node crash/DoS analog to the reported Bouncy Castle issue.

### Likelihood Explanation
Reaching this code only requires deploying/calling a contract that invokes the relevant precompiled contract (e.g., a batch-verification precompile) with a single crafted calldata word — no special privileges, no consensus role, and no cooperation from other nodes are required, matching the "unprivileged contract caller" threat model in scope.

### Recommendation
Before allocating `new byte[len][]` (or any array sized from an untrusted `DataWord`), bound `len` against the actual remaining `words`/`data` length (e.g., `len <= (words.length - offset - 1)`), and reject the call (consuming energy / reverting) if the claimed length is inconsistent with the supplied calldata size, mirroring the `verifyLength` bounds checks already used elsewhere in the RLP decoder (`framework/src/main/java/org/tron/core/capsule/utils/RLP.java`, `verifyLength`) for the same class of attacker-controlled length fields. [2](#0-1) 

### Proof of Concept
1. Deploy a contract that calls the precompiled contract path which uses `extractBytesArray`/`extractBytes32Array` (e.g. a batch-signature-verification style precompile) with calldata whose word at the "array length" offset is set to a very large value (e.g. `0x7fffffff`).
2. Invoke the contract via a normal signed `TriggerSmartContract` transaction.
3. During execution, `extractBytesArray`/`extractBytes32Array` computes `len` from that word and executes `new byte[len][]`, forcing an oversized allocation attempt that throws `OutOfMemoryError` inside the node's transaction execution path. [3](#0-2) 

Note: I was unable to fully trace, within the remaining tool budget, which specific precompiled-contract `execute()` methods call `extractBytesArray`/`extractBytes32Array` and whether energy metering charges for the claimed `len` before or after the allocation occurs; confirming the exact call sites and any pre-existing energy-based size caps would require further reading of `PrecompiledContracts.java` (e.g. the `BatchValidateSign` inner class) to fully validate exploitability end-to-end.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
