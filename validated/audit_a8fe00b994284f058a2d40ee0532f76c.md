Audit Report

## Title
Ignored transfer failures in `claim_child_bounty` permanently lock funds in the child-bounty sub-account - (File: `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`Pallet::claim_child_bounty` transfers the curator fee and beneficiary payout out of the per-child-bounty sub-account via `T::Currency::transfer(..., AllowDeath)`, but checks the results only with `debug_assert!`, a macro compiled to a no-op in release builds. [1](#0-0)  If either transfer fails (e.g., destination below the Existential Deposit for a non-existent account), execution continues unconditionally to delete the child-bounty record and decrement bookkeeping, permanently orphaning the funds still held in the child-bounty account.

## Finding Description
`claim_child_bounty` computes `curator_fee` and `payout` from the child-bounty account's free balance and unconditionally transfers them with `AllowDeath`. [2](#0-1)  Both `fee_transfer_result` and `payout_transfer_result` are checked only via `debug_assert!`, which is a no-op in `--release` builds, so a genuine transfer failure is silently ignored. [1](#0-0)  Regardless of transfer outcome, the code proceeds to fire `Event::Claimed`, decrement `ParentChildBounties`, remove `ChildBountyDescriptionsV1`, and set `*maybe_child_bounty = None`, deleting the only state that referenced these funds. [3](#0-2) 

The `beneficiary` account is fully attacker-controlled: `award_child_bounty` accepts any `beneficiary` address from the curator without any existence or minimum-balance check before transitioning the child bounty to `PendingPayout`. [4](#0-3)  Because `payout = balance.saturating_sub(curator_fee)` has no floor relative to the runtime's Existential Deposit, a curator (who is an ordinary, unprivileged participant in the bounty workflow, not requiring governance) can set up a child bounty whose residual `payout` is below ED and award it to a zero-balance beneficiary, guaranteeing the beneficiary transfer fails under `AllowDeath` semantics.

Comparing to the sibling pallet, `pallet-bounties` was given a `reclaim_bounty_funds` extrinsic specifically to sweep dust/stranded balance out of a bounty account after such issues, confirmed present in `substrate/frame/bounties/src/lib.rs`, its weights, benchmarking, and tests. [5](#0-4)  No equivalent recovery call exists anywhere in `substrate/frame/child-bounties/src/lib.rs` — a search for `reclaim_bounty_funds` in the codebase returns matches only under `pallet-bounties`, never `pallet-child-bounties`, confirming there is no path to recover funds stranded in a child-bounty sub-account once its record is erased.

## Impact Explanation
This matches the "permanent user-fund lock" impact category in the required impact gate. The child-bounty sub-account retains real funds (the un-transferred `payout` or `curator_fee`), but the `ChildBounties` storage entry that would allow re-processing is deleted, and `pallet-child-bounties` provides no reclaim/sweep mechanism analogous to `pallet-bounties::reclaim_bounty_funds`. The funds become permanently inaccessible through any dispatchable in this pallet.

## Likelihood Explanation
The path is reachable entirely through public, unprivileged dispatchables in the ordinary bounty workflow: a curator (assigned through normal, non-privileged flow) calls `award_child_bounty` with a `beneficiary` of their choosing and a `fee`/`value` combination such that `payout` falls below the runtime's Existential Deposit, then anyone calls `claim_child_bounty` after the delay. [4](#0-3)  No malicious peer, validator, governance action, or off-chain compromise is required, and the condition (small residual payout vs. ED, non-existent beneficiary account) is trivially satisfiable by the curator.

## Recommendation
Replace the `debug_assert!` checks on `fee_transfer_result` and `payout_transfer_result` with `?`/`ensure!`-based propagation so a failed transfer aborts the extrinsic before the child-bounty record and counters are mutated. Additionally, introduce a `reclaim_child_bounty_funds`-style extrinsic mirroring `pallet-bounties::reclaim_bounty_funds` to sweep any residual/stranded balance from a child-bounty account back to the parent bounty or treasury after the fact.

## Proof of Concept
1. Propose and fund a parent bounty; assign and accept a child-bounty curator via the normal workflow.
2. Add a child bounty with `value`/`fee` chosen such that `payout = value - fee` is below the runtime's `ExistentialDeposit`.
3. Call `award_child_bounty` with `beneficiary` set to an account holding zero balance (nonexistent in `System::Account`). [4](#0-3) 
4. After `unlock_at`, call `claim_child_bounty`. In a release build, `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` returns `Err` because the destination cannot be created below ED, but the surrounding `debug_assert!` is compiled out. [6](#0-5) 
5. Observe `Event::Claimed` is emitted, `ParentChildBounties` is decremented, `ChildBountyDescriptionsV1` is removed, and `*maybe_child_bounty` is set to `None`, while `Balances::free_balance(child_bounty_account)` still holds the un-transferred `payout` amount with no dispatchable in `pallet-child-bounties` available to recover it. [3](#0-2)

			let beneficiary = T::Lookup::lookup(beneficiary)?;

			// Ensure parent bounty exists, and is active.
			let (parent_curator, _) = Self::ensure_bounty_active(parent_bounty_id)?;

			ChildBounties::<T>::try_mutate_exists(

				child_bounty_id,
				|maybe_child_bounty| -> DispatchResult {
					let child_bounty =
						maybe_child_bounty.as_mut().ok_or(BountiesError::<T>::InvalidIndex)?;

					// Ensure child-bounty is in active state.
					if let ChildBountyStatus::Active { ref curator } = child_bounty.status {

						);

						};
						Ok(())
					} else {
						Err(BountiesError::<T>::UnexpectedStatus.into())
					}
				},
			)?;

#[test]
fn reclaim_bounty_funds_works_after_accidental_refund() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Full lifecycle: propose → approve → fund → curator → award → claim
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		let fee = 4;
		Balances::make_free_balance_be(&4, 10);
		assert_ok!(Bounties::propose_curator(RuntimeOrigin::root(), 0, 4, fee));
		assert_ok!(Bounties::accept_curator(RuntimeOrigin::signed(4), 0));
		assert_ok!(Bounties::award_bounty(RuntimeOrigin::signed(4), 0, 3));
		go_to_block(5);
		assert_ok!(Bounties::claim_bounty(RuntimeOrigin::signed(1), 0));

		// Bounty is now fully closed; verify it is gone from storage.
		assert!(pallet_bounties::Bounties::<Test>::get(0).is_none());

		let bounty_account = Bounties::bounty_account_id(0);
		// Account should already be empty after claim.
		assert_eq!(Balances::free_balance(&bounty_account), 0);

		// Simulate someone accidentally sending funds to the closed bounty account.
		Balances::make_free_balance_be(&bounty_account, 25);
		assert_eq!(Balances::free_balance(&bounty_account), 25);

		let treasury_before = Treasury::pot();

		// Dust the account.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(99), 0));
		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		assert_eq!(Balances::free_balance(&bounty_account), 0);
		assert!(Treasury::pot() > treasury_before);
	});
}
