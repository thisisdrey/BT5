### Title
Unbounded array allocation from attacker-controlled length in `PrecompiledContracts.extractBytesArray`/`extractBytes32Array` can trigger unhandled `OutOfMemoryError` during TVM execution - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`extractBytesArray`, `extractBytes32Array`, and `extractSigArray` in `PrecompiledContracts.java` decode ABI-encoded array arguments passed to the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts. Each reads an attacker-controlled 32-byte word as an array length and immediately allocates a Java array of that size (`new byte[len][]`) without validating it against the actual size of the calldata, before any per-element bounds check occurs.

### Finding Description
`extractBytes32Array` reads `len = words[offset].intValueSafe()` and allocates `new byte[len][]` with no upper bound check at all. [1](#0-0) 

`extractBytesArray` and `extractSigArray` have the same pattern; they only guard against `offset` being out of range, not against `len` being attacker-controlled and huge, before allocating `new byte[len][]`. [2](#0-1) 

This mirrors the CVE-2020-10811 bug class: a length field taken from untrusted, attacker-supplied input is used to size/traverse a buffer without first validating it against the bounds of the actual data, similar to `H5O__layout_decode()` trusting an encoded dimensionality/length value.

In `ValidateMultiSign.execute()`, the `MAX_SIZE`/`sigArraySize` guard is only applied when `VMConfig.allowTvmSelfdestructRestriction()` is enabled and only for the `extractSigArray` path; the legacy `extractBytesArray` path used when that flag is disabled has no such pre-check, and the calls occur **outside** the `try { ... } catch (Throwable t)` block that wraps the rest of the method, so any resulting `Error` (not `RuntimeException`) is not swallowed there. [3](#0-2) 

`BatchValidateSign.execute()` wraps its `doExecute` call in `catch (Throwable t)`, so an `OutOfMemoryError` there would be swallowed and converted into `Pair.of(true, new byte[WORD_SIZE])`. [4](#0-3) 

However, `ValidateMultiSign.execute()` has no such `Throwable` guard around the `extractBytesArray`/`extractSigArray` call site, so an `OutOfMemoryError` there propagates out of `execute()`. In the interpreter loop, `VM.play()` only catches `RuntimeException`, not `Error`/`OutOfMemoryError`: [5](#0-4) 

An uncaught `OutOfMemoryError` thrown mid-transaction-execution can leave the JVM heap in a degraded state and, depending on JVM/GC behavior, can affect concurrently executing threads in the same node process (block application, other pending transactions), which is a shared-fate DoS risk rather than a memory-safety violation (Java arrays cannot be over-read past their bounds the way a C buffer can, so the literal "heap-based buffer over-read" primitive from the HDF5 CVE does not exist as such in java-tron's managed-memory code).

### Impact Explanation
If reachable with a length value large enough to force a very large allocation attempt (e.g. close to `Integer.MAX_VALUE`), the JVM can throw `OutOfMemoryError` while allocating `new byte[len][]`. Because `ValidateMultiSign.execute()` does not catch `Throwable`, this error is not contained to the single transaction/precompile call and propagates through `VM.play()`, which only catches `RuntimeException`. This could destabilize the transaction-processing thread and, depending on downstream exception handling, potentially crash or degrade the node process — a resource-exhaustion / denial-of-service class of impact analogous to the referenced CVE's DoS effect, though the underlying mechanism differs (Java memory-safety vs. C heap over-read).

### Likelihood Explanation
Reaching `ValidateMultiSign` and `BatchValidateSign` only requires any account to deploy a contract that issues a `CALL`/`STATICCALL` to their fixed precompile addresses with crafted calldata — no special privileges are needed, and no signature validity is required to reach the array-length parsing step (the length is read before any signature is verified). However, exploitation depends on whether `words[offset].intValueSafe()` and downstream JVM allocation limits actually allow a length value that is large enough to trigger `OutOfMemoryError` before hitting an `ArrayIndexOutOfBoundsException` from the very next line (`words[offset + i + 1]`), which for most attacker-controlled `words` arrays (whose real size is bounded by the transaction's calldata, itself capped by transaction size limits) is likely to throw the cheaper, already-caught `RuntimeException` first rather than succeed in allocating a very large array. I was unable to fully confirm the exact numeric threshold or JVM behavior (e.g., whether array-of-references allocation of `Integer.MAX_VALUE` length actually throws `OutOfMemoryError` versus `NegativeArraySizeException`/other bounded failure) due to remaining tool-call budget, so this should be treated as a plausible but not fully proven DoS path.

### Recommendation
- In `extractBytesArray`, `extractBytes32Array`, and `extractSigArray`, validate the decoded `len` against a sane upper bound (e.g., `MAX_SIZE`, consistent with the check already applied when `allowTvmSelfdestructRestriction()` is enabled) and against the remaining `words.length` before allocating `new byte[len][]`, for all code paths (not just when the feature flag is enabled).
- Wrap the array-extraction and signature-recovery logic in `ValidateMultiSign.execute()` with the same `try { ... } catch (Throwable t)` pattern already used in `BatchValidateSign.execute()`, so any unexpected `Error` from precompile input parsing is safely converted into a rejection (`DATA_FALSE`) rather than propagating uncaught.

### Proof of Concept
1. Deploy a trivial contract that performs a raw `CALL` to the `ValidateMultiSign` precompile address (with `VMConfig.allowTvmSelfdestructRestriction()` disabled, i.e. the legacy `extractBytesArray` path active).
2. Craft calldata where the fourth word (`words[3]`) points to an offset word whose value is an extremely large integer (close to `Integer.MAX_VALUE`), forcing `extractBytesArray`'s `int len = words[offset].intValueSafe();` followed by `new byte[len][]` to request a very large array.
3. Observe whether the JVM throws `OutOfMemoryError` instead of the immediately-following bounds check failing first, and confirm it is not caught by `ValidateMultiSign.execute()` or by `VM.play()`'s `catch (RuntimeException e)`. [6](#0-5) [7](#0-6) [5](#0-4)

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
