Audit Report

## Title
Snowbridge relayer reward is marked paid and cleared before the cross-chain `DepositAsset` mint is confirmed to succeed - (File: `bridges/snowbridge/primitives/core/src/reward.rs`)

## Summary
`PayAccountOnLocation::pay_reward` returns `Ok(())` as soon as the reward-minting XCM is handed to `XcmSender::deliver`, without any confirmation that the remote `DepositAsset` instruction on AssetHub actually succeeds. Because `pallet-bridge-relayers`'s `claim_rewards_to` extrinsic treats this `Ok(())` as final settlement and irrevocably clears the relayer's reward entry on BridgeHub, a relayer's reward can be trapped on AssetHub (bad beneficiary, ED/asset-registration issues) while BridgeHub's bookkeeping shows it as paid.

## Finding Description
`PayAccountOnLocation::pay_reward` builds an XCM ending in `DepositAsset { assets: AllCounted(1), beneficiary }`, calls `validate_send`, `XcmExecutor::charge_fees`, and `XcmSender::deliver`, then returns `Ok(())` unconditionally on successful local delivery [1](#0-0) . There is no callback, receipt, or `check_status`-style mechanism anywhere in this code path to confirm that the remote `DepositAsset` on AssetHub executed without error. This procedure is wired into `BridgeRewardPayer::pay_reward` in the BridgeHub Westend runtime config for `BridgeReward::Snowbridge` [2](#0-1) , which is invoked from `pallet-bridge-relayers`'s reward-claiming logic. The pallet's own integration tests demonstrate that `DepositAsset`/`ReserveAssetDeposited` XCM instructions can trap assets on AssetHub under adverse conditions, and that recovery via `pallet_xcm::claim_assets` only works when the encoded claimer matches the account that signs the claim [3](#0-2) , confirming that the "fire-and-forget" trust assumption in `pay_reward` is not accompanied by a guaranteed recovery path for a relayer-chosen beneficiary at claim time.

## Impact Explanation
This breaks the invariant that bridge markers, receipts, and payout state must only advance after execution and settlement succeed atomically. A relayer's registered reward can become permanently unreachable (asset trapped on AssetHub, no reliable recovery for a beneficiary not anchored to a matching claimer) while BridgeHub records the reward as fully paid and emits `RewardPaid`. This falls under the "duplicate settlement / permanent user-fund lock" impact category in the required impact gate, since the corrupted value is the relayer's cleared `RelayerRewards` entry co-existing with a failed/uncertain remote settlement.

## Likelihood Explanation
The path is reachable by any relayer calling the permissionless `claim_rewards_to` extrinsic with an `AssetHubLocation` beneficiary of their choosing, under normal-but-unfavorable destination-chain conditions (unfunded/ED-insufficient beneficiary, asset-registration edge cases) — no privileged actor or malicious peer is required. However, the exact interaction between `pay_reward`'s return value and the point at which `RelayerRewards` is cleared inside `claim_rewards_to`/its internal claim logic in `bridges/modules/relayers/src/lib.rs` could not be fully confirmed within the available investigation; grep results located the relevant identifiers in that file but the exact function bodies and their sequencing were not fully read before the investigation budget ran out. This is a data/state-dependent condition rather than always exploitable, and the precise clearing order should be verified directly in that file before treating this as fully confirmed.

## Recommendation
Do not treat `XcmSender::deliver` success as final settlement in `PayAccountOnLocation::pay_reward`. Either require confirmed-execution feedback from AssetHub before clearing the reward record on BridgeHub, or adopt an async two-phase payout (e.g., mark as pending/attempted on send, finalize only after confirmed `DepositAsset` success), analogous to `PayoutAttempted`-style state machines used elsewhere in the codebase. Ensure relayers have a reliable, self-served recovery path for trapped rewards independent of whether they can craft a matching claimer.

## Proof of Concept
1. Relayer accrues a Snowbridge reward and calls `claim_rewards_to` with `BridgeRewardBeneficiaries::AssetHubLocation` pointing to an unfunded/unregistered-for-asset account.
2. `BridgeRewardPayer::pay_reward` routes to `PayAccountOnLocation::pay_reward`, which validates, charges fees, and calls `XcmSender::deliver`, returning `Ok(())` purely on local queuing (`bridges/snowbridge/primitives/core/src/reward.rs:127-151`).
3. On AssetHub, `DepositAsset` fails due to beneficiary/ED/registration conditions and the asset is trapped, as reproduced in `cumulus/parachains/integration-tests/emulated/tests/bridges/bridge-hub-westend/src/tests/snowbridge_v2_inbound.rs:1158-1182`.
4. On BridgeHub the reward is already recorded as paid (via the cleared `RelayerRewards` entry and `RewardPaid` event), leaving the relayer with no recorded claimable balance and no guaranteed recovery path for the trapped asset.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
