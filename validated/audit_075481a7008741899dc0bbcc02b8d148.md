### Title
`amoSupply` accounting leak in `SyntheticToken._burn` permanently exhausts AMO minting capacity - (File: contracts/SyntheticToken.sol)

### Summary
The analog of the refcount leak (a counter incremented on acquisition but never decremented on release) is `amoSupply` in `SyntheticToken`. It is incremented on every AMO mint, but decremented only inside the `else if (_isMsgSenderAmo(...))` branch of `_burn`, which additionally requires `account_ == amo`. Tokens that were minted by the AMO but have since left the AMO's balance are burned through other authorized paths (`proxyOFT` bridge-out, `pool`/`debtToken` repay/seize) without decrementing `amoSupply`. The counter therefore leaks: it monotonically accumulates until `amoSupply > maxAmoSupply` reverts, permanently freezing AMO minting despite the AMO-attributable circulating supply being far below the cap. [1](#0-0) [2](#0-1) 

### Finding Description
`_mint` adds `amount_` to `amoSupply` whenever `_isMsgSenderAmo(_msgSender)` and enforces `amoSupply <= maxAmoSupply` [3](#0-2) . `_burn` subtracts from `amoSupply` only in the AMO-self-burn branch (`account_ != _msgSender` reverts with `AmoInvalidAccount`) [4](#0-3) . Every other authorized burner — `proxyOFT` (`_debitFrom` → `syntheticToken.burn`), `pool`, and `debtToken` — skips the decrement entirely [5](#0-4) . Since AMO-minted synths are distributed to users (e.g., via an AMM), the tokens are overwhelmingly burned by non-AMO callers: bridge-outs via `ProxyOFT.sendFrom`, debt repayments via `DebtToken`, and pool `seize`. Each such burn leaves `amoSupply` unchanged while the actual AMO-minted outstanding supply decreases. This mirrors CVE-2022-49715: a resource acquired (refcount/`amoSupply` increment) is not released (`of_node_put`/decrement) on a valid release path.

### Impact Explanation
`amoSupply` is a leaked, monotonically-growing counter. Once leaked increments push it to `maxAmoSupply`, every subsequent AMO `mint` reverts with `SurpassMaxAmoSupply` even though the AMO holds zero of its attributed supply. The AMO minting facility is frozen until governance manually raises `maxAmoSupply` — temporary freezing of a funded minting allocation, recoverable only by privileged intervention. Any unprivileged user holding AMO-minted synths can trigger the leak by bridging out (`ProxyOFT.sendFrom` → `_debitFrom` → `burn` with `msg.sender = proxyOFT`) [6](#0-5)  or repaying debt; no privileged action is required once AMO tokens are in circulation.

### Likelihood Explanation
AMO-minted supply is designed to circulate; every bridge-out, repay, or liquidation-seize involving those tokens leaks the counter. Because `amoSupply` never shrinks except via AMO self-burn (which AMO cannot perform on tokens it no longer holds), the cap is reached through ordinary protocol usage and attacker-accelerated looping (buy AMO-originated synths → bridge out → repeat). No modifier prevents it: `onlyIfCanBurn` admits `proxyOFT`, `pool`, and `debtToken`, and none of those paths touch `amoSupply` [7](#0-6) .

### Recommendation
Decrement `amoSupply` on any burn of AMO-attributed supply, or redefine accounting: track AMO headroom as a balance-scoped allowance and decrement `amoSupply` whenever `totalSupply` attributable to AMO issuance decreases (e.g., decrement on any burn up to the leaked amount), or have burns by `proxyOFT`/pools reduce `amoSupply` by `min(amount_, amoSupply)` when the underlying tokens originated from AMO. Alternatively, periodically reconcile via a governor function that resets `amoSupply` to `balanceOf[amo]`-attributed outstanding supply.

### Proof of Concept
Hardhat/Foundry fork sketch:

```solidity
// 1. Governor sets amo and maxAmoSupply = 100e18
synth.updateAmo(amo);
synth.updateMaxAmoSupply(100e18);

// 2. AMO mints up to cap and distributes to alice (e.g., via AMM sale)
vm.prank(amo);
synth.mint(amo, 100e18);          // amoSupply = 100e18
vm.prank(amo);
synth.transfer(alice, 100e18);    // AMO balance now 0

// 3. Alice bridges out — burn executed by proxyOFT path, no amoSupply decrement
vm.prank(alice);
proxyOFT.sendFrom{value: fee}(alice, dstChainId, alice, 100e18);
// totalSupply decreases by 100e18, but amoSupply still == 100e18  ← leaked refcount

// 4. AMO attempts to mint again — reverts despite zero outstanding AMO supply
vm.prank(amo);
vm.expectRevert(SurpassMaxAmoSupply.selector);
synth.mint(amo, 1);
```

Same leak is reachable via `DebtToken.repay`/`Pool.seize` burns instead of `sendFrom`. After step 3, `amoSupply == maxAmoSupply` while `balanceOf[amo] == 0`, demonstrating the un-released reference.

Note: severity is bounded — it freezes AMO minting capacity (governance-recoverable via `updateMaxAmoSupply`) rather than user funds directly, consistent with the Medium/DoS character of the source advisory.

```text
    function _burn(address account_, uint256 amount_) private {
        if (account_ == address(0)) revert BurnFromTheZeroAddress();

        address _msgSender = _msgSender();

        if (_isMsgSenderProxyOFT(_msgSender)) {
            totalBridgedOut += amount_;
            if (bridgedOutSupply() > maxBridgedOutSupply) revert SurpassMaxBridgingSupply();
        } else if (_isMsgSenderAmo(_msgSender)) {
            // AMO can only burn from self address.
            // account_ should be AMO and in this case it is same as _msgSender()
            if (account_ != _msgSender) revert AmoInvalidAccount();

            amoSupply -= amount_;
        }

        uint256 _currentBalance = balanceOf[account_];
        if (_currentBalance < amount_) revert BurnAmountExceedsBalance();
        unchecked {
            balanceOf[account_] = _currentBalance - amount_;
            totalSupply -= amount_;
        }

        emit Transfer(account_, address(0), amount_);
    }
```
