Audit Report

## Title
`add_tip` missing halted-mode check allows fund burn while Snowbridge export is paused - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
The `snowbridge-pallet-system-frontend` pallet exposes an `ExportOperatingMode` halt switch intended to freeze all fund-moving export operations toward Ethereum. `register_token` correctly guards its call to `swap_fee_asset_and_burn` with `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)`, but `add_tip`, which invokes the identical fund-burning helper, omits this check entirely, allowing any signed user to keep swapping and irreversibly burning assets during a declared halt.

## Finding Description
Both `register_token` (bridges/snowbridge/pallets/system-frontend/src/lib.rs L225-252) and `add_tip` (L254-273) call `Self::swap_fee_asset_and_burn`, which swaps the caller's asset for Ether via `T::Swap::swap_exact_tokens_for_tokens` and then calls `burn_for_teleport::<T::AssetTransactor>` (L372-404), an irreversible operation that removes value from the caller's account. `register_token` gates this behind `ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted)` at L231. `add_tip` has no such check: it proceeds from `ensure_signed(origin)?` (L265) directly to `Self::swap_fee_asset_and_burn(...)` (L267), with no reference to `Self::export_operating_mode()`. The `ExportOperatingMode` storage is surfaced pallet-wide via `ExportPausedQuery::is_paused()` (L426-430), which is consumed elsewhere (e.g., `PausableExporter` in bridges/snowbridge/primitives/outbound-queue/src/v2/exporter.rs) as the authoritative signal that export/bridge processing should stop — confirming the halt is meant to apply uniformly to fund-burning export operations, not selectively to `register_token`.

## Impact Explanation
This is a runtime bug that compromises the intended behavior of the pause/halt control: an operator invoking `set_operating_mode(Halted)` to freeze Snowbridge export operations (e.g., during an incident on the Ethereum side, a compromised relay, or an active exploit) cannot actually stop users from burning tip assets through `add_tip`. Because the burn (`burn_for_teleport`) executes unconditionally regardless of halted state, and only the subsequent `send_transact_call`/XCM dispatch may or may not be blocked depending on downstream wiring, this can produce burned-but-unprocessed value — funds are irreversibly destroyed locally while the corresponding reward/tip allocation on the BridgeHub/Ethereum side may never be realized. This matches the in-scope impact class of "permanent user-fund lock" / degraded bridge processing during an emergency halt.

## Likelihood Explanation
High likelihood and fully unprivileged: any signed account can call `add_tip` with an arbitrary `message_id`/`asset` at any time, including immediately after a halt is declared, with no special conditions, keys, or governance access required. The vulnerability is a simple, mechanical asymmetry between two public extrinsics sharing a common fund-burning helper, confirmed directly by reading the source.

## Recommendation
Add the same halted-mode guard used in `register_token` to `add_tip`:
```rust
pub fn add_tip(origin: OriginFor<T>, message_id: MessageId, asset: Asset) -> DispatchResult {
    let who = ensure_signed(origin)?;
    ensure!(!Self::export_operating_mode().is_halted(), Error::<T>::Halted);
    let ether_gained = Self::swap_fee_asset_and_burn(who.clone().into(), asset)?;
    ...
}
```
Better yet, move the halted check inside `swap_fee_asset_and_burn` itself so future callers of this shared fund-burning helper cannot omit the guard.
