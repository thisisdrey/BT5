### Title
Fresh accounts accrue `balance × 1` reward tokens when token index still equals `INITIAL_INDEX` — (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` handles the "never-accrued account" case by substituting `INITIAL_INDEX` (1e18) only when the token index is strictly greater than `INITIAL_INDEX`. While a token's index is still exactly `INITIAL_INDEX` — i.e. in the same `block.timestamp` in which the reward speed was set — an account that has never been accrued computes `_deltaIndex = INITIAL_INDEX - 0 = 1e18`, so `_tokensDelta = balanceOf(account).wadMul(1e18) = balanceOf(account)`. The attacker instantly accrues reward tokens equal to their full DepositToken/DebtToken balance and can claim them via `claimRewards`, draining the distributor's `rewardToken` balance.

### Finding Description
In `contracts/RewardsDistributor.sol`:

```solidity
// _calculateTokenDelta (lines 221-231)
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a reward token is registered, `_updateTokenSpeed` sets `tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (line 298). Until at least one second elapses with `speed > 0` and `totalSupply > 0`, `_updateTokenIndex` leaves `index == INITIAL_INDEX` (`_deltaTimestamps == 0`, or `_ratio == 0` when supply is 0 — lines 202-208).

During that window, `updateBeforeMintOrBurn` / `updateBeforeTransfer` — explicitly callable by anyone (devdoc: "This function also may be called by anyone") — take the `index > 0` branch (line 176) and call `_updateTokensAccruedOf`, which for any account with `accountIndexOf == 0` records `tokensAccruedOf[account] += balanceOf(account)` (line 264). `claimRewards(account_)` then pays `tokensAccruedOf[account_]` out in `rewardToken` via `_transferRewardIfEnoughTokens` (lines 248-255).

Attack sequence, all unprivileged:
1. Attacker deposits collateral and holds `DepositToken` balance (or mints debt via `DebtToken.issue`) *before* the reward-speed transaction.
2. Attacker sees the governor's `updateTokenSpeed(token, speed)` tx in the mempool, and in the **same block** (same `block.timestamp`) calls `RewardsDistributor.updateBeforeMintOrBurn(token, attacker)` after it. `_updateTokenIndex` no-ops (`_deltaTimestamps == 0`), so index stays `1e18`.
3. `_calculateTokenDelta` yields `tokensDelta = attackerBalance` (wadMul by 1e18). `accountIndexOf` is set to `1e18`, so it is a one-shot, not repeatable — but it credits the *entire balance* once, instantly.
4. Attacker calls `claimRewards(attacker)` and receives `rewardToken` up to the distributor's full balance.

The boundary condition `_tokenIndex > INITIAL_INDEX` should be `>=` (or `_accountIndex` should be set to `_tokenIndex`/`INITIAL_INDEX` unconditionally for first-time accounts); with strict `>`, a zero account index collides with the legitimate initial index, letting "uninitialized" state leak value — the analog of the Xen grant-page disclosure where an unzeroed/shared region exposes unrelated data.

### Impact Explanation
Direct theft of reward tokens (unclaimed yield) held by the `RewardsDistributor`. The attacker receives `min(attackerDepositTokenBalance, rewardToken.balanceOf(distributor))` in a single transaction with no time-weighted accrual. Because deposit/debt balances are attacker-controlled (can be maximized with a whale deposit or borrowed liquidity beforehand), the entire `rewardToken` inventory can be drained.

### Likelihood Explanation
Requires only that the attacker's first accrual happens while `tokenStates[token].index == INITIAL_INDEX`. The primary window is the same `block.timestamp` as the `updateTokenSpeed` registration/update — routine governor transactions are publicly observable and same-block front-/back-running is within the stated attacker model (no malicious governor needed; the governor action is a normal, scheduled operation). A secondary window exists whenever a registered token has `totalSupply == 0` (`_ratio = 0` keeps the index pinned at 1e18). No pause flag, reentrancy guard, or `SynthContext` check restricts `updateBeforeMintOrBurn`/`claimRewards`, and `nonReentrant` on `claimRewards` does not help.

### Recommendation
In `_calculateTokenDelta`, treat a never-accrued account as starting at the current index rather than the constant: when `_accountIndex == 0`, set `_accountIndex = _tokenIndex` (equivalently, change the guard to `_tokenIndex >= INITIAL_INDEX` *and* clamp so that a zero delta results when index equals `INITIAL_INDEX`). Alternatively initialize `accountIndexOf[token][account] = tokenStates[token].index` on first touch.

### Proof of Concept
Hardhat-style fork/unit PoC outline:

```ts
// setup: pool with DepositToken `msdTOKEN`, RewardsDistributor initialized,
// distributor funded with rewardToken. Attacker holds balance B of msdTOKEN.
await depositToken.mint(attacker, B);               // attacker deposit before speed set

// governor registers reward speed (index = INITIAL_INDEX, timestamp = now)
await rewardsDistributor.connect(governor).updateTokenSpeed(msdTOKEN.address, speed);

// same block/timestamp: attacker triggers public accrual
await rewardsDistributor.updateBeforeMintOrBurn(msdTOKEN.address, attacker.address);

expect(await rewardsDistributor.tokensAccruedOf(attacker.address)).to.eq(B); // B, not ~0

// drain rewards
const balBefore = await rewardToken.balanceOf(attacker.address);
await rewardsDistributor.claimRewards(attacker.address);
expect(await rewardToken.balanceOf(attacker.address)).to.eq(balBefore.add(B));
```

Key assertions: `tokenStates(msdTOKEN).index == 1e18` at the call, `_deltaTimestamps == 0`, `accountIndexOf == 0` → `_deltaIndex == 1e18` → `tokensDelta == B`.
