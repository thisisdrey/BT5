Based on my investigation, this confirms a genuine analog to the reported ERC4626 override-inconsistency bug class in java-tron: the reward calculation logic exists in two independently maintained implementations that have diverged in their handling of the old/new reward algorithm cutover, exactly the same failure mode as "custom logic defined in one place without propagating it to all dependent call sites."

### Title
Reward Computation Diverges Between MortgageService and TVM VoteRewardUtil Around the New-Reward-Algorithm Cutover Cycle - (File: actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java)

### Summary
`MortgageService.computeReward` (used by the wallet-level `WithdrawBalanceActuator`/`UnfreezeBalanceV2Actuator` path) contains explicit branching logic to combine the legacy per-cycle reward algorithm with the newer Vi-based (delegation index) algorithm around `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE`. `VoteRewardUtil.computeReward` — the parallel implementation used by the TVM `WITHDRAWREWARD`/`REWARDBALANCE` native contract path, reachable from any deployed smart contract — never re-implements that branching and always applies the Vi-only formula for the whole `[beginCycle, endCycle)` range.

### Finding Description
`MortgageService.computeReward(long beginCycle, long endCycle, AccountCapsule)` explicitly special-cases cycles before the new algorithm became effective: [1](#0-0) 

It computes `getOldReward` for any part of the range before `newAlgorithmCycle`, and only uses the Vi-delta method for cycles at or after that boundary.

The TVM-facing implementation, `VoteRewardUtil.computeReward`, used by `VoteRewardUtil.withdrawReward`/`queryReward` (invoked from `Program.withdrawReward()`, reachable by any contract via the `WITHDRAWREWARD` opcode), has no such branch — it unconditionally applies the Vi-delta formula across the entire cycle range: [2](#0-1) 

`DelegationStore.getWitnessVi` returns `BigInteger.ZERO` for any cycle that has no stored Vi value: [3](#0-2) 

Because Vi values are only populated starting from `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` (backfilled once by `RewardViCalService.accumulateWitnessReward`, and incrementally by `DelegationStore.accumulateWitnessVi` going forward), any `beginCycle` earlier than that boundary will read `beginVi = 0` from `DelegationStore.getWitnessVi(beginCycle - 1, ...)` in the TVM path, while `endVi` reflects the full accumulated index. This yields `deltaVi = endVi - 0`, i.e., the entire historical Vi accumulation from cycle 1 onward, rather than only the delta owed for `[beginCycle, endCycle)`. This is structurally the same bug class as the ERC4626 report: `convertToShares`/`convertToAssets`-equivalent logic (the "correct" reward formula in `MortgageService`) was updated with cutover-aware branching, but the parallel/duplicate implementation that other code paths depend on (`VoteRewardUtil`, feeding the TVM opcode) was never updated to match, so it silently produces different, larger results for the same account state.

### Impact Explanation
If exploitable, a TVM contract account whose `beginCycle` predates `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` and that calls `withdrawReward()`/reward-balance opcodes could receive a reward computed from the full historical Vi accumulation instead of the correct bounded delta, resulting in an inflated, unbacked TRX credit to `accountCapsule.allowance`/balance — a direct theft-of-funds / unbacked-balance issue, matching the "unauthorized account operation, theft, or unbacked balance" impact bar.

### Likelihood Explanation
Likelihood is uncertain and I could not fully verify exploitability with the tools available. The relevant TVM voting/reward feature is gated by `VMConfig.allowTvmVote()`, and whether any account can currently have `beginCycle < NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` while also using the TVM `WITHDRAWREWARD` path depends on the chronological order in which `allowTvmVote` and the new-reward-algorithm hard forks were activated on a given network. On networks where the new-reward-algorithm cutover happened before TVM voting was enabled, no account could have a pre-cutover `beginCycle`, making the divergent branch unreachable in practice. I was not able to confirm the activation ordering/timeline from the code alone, so this should be treated as a real code-level divergence whose practical exploitability needs confirmation against the specific chain's fork-activation history.

### Recommendation
Refactor `VoteRewardUtil.computeReward` (and `queryReward`) to delegate to the same cutover-aware logic as `MortgageService.computeReward`/`getOldReward`, rather than maintaining a second, independently-evolving copy of the reward formula. Alternatively, extract the branching logic into a single shared utility consumed by both `MortgageService` and `VoteRewardUtil` so future changes to the reward algorithm cannot diverge between the wallet/actuator path and the TVM native-contract path.

### Proof of Concept
Not independently reproducible without live chain state/fork-activation history: it requires an account with `beginCycle` set before the network's `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` that also exercises the `WITHDRAWREWARD` TVM opcode via `Program.withdrawReward()` → `VoteRewardUtil.withdrawReward()` → `VoteRewardUtil.computeReward()`, and comparing the resulting allowance credit against the amount `MortgageService.computeReward` would have produced for the same cycle range. I could not execute or set up such a scenario with the available tools; a background Devin session with test/db access would be needed to confirm the divergence with a concrete before/after reward-amount reproduction (similar to the existing `framework/src/test/java/org/tron/core/services/ComputeRewardTest.java` test harness, which already exercises `MortgageService.computeReward` and could be extended to compare against `VoteRewardUtil.computeReward`).

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }

  private static long computeReward(long beginCycle, long endCycle,
                                    AccountCapsule accountCapsule, Repository repository) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    for (Protocol.Vote vote : accountCapsule.getVotesList()) {
      byte[] srAddress = vote.getVoteAddress().toByteArray();
      BigInteger beginVi = repository.getDelegationStore().getWitnessVi(beginCycle - 1, srAddress);
      BigInteger endVi = repository.getDelegationStore().getWitnessVi(endCycle - 1, srAddress);
      BigInteger deltaVi = endVi.subtract(beginVi);
      if (deltaVi.signum() <= 0) {
        continue;
      }
      long userVote = vote.getVoteCount();
      reward += deltaVi.multiply(BigInteger.valueOf(userVote))
          .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
    }
    return reward;
  }
