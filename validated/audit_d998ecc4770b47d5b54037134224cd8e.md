### Title
Malicious NEP-141 token contract can permanently brick the eth-implicit Wallet Contract via gas-exhaustion panic in `nep_141_storage_balance_callback`, freezing wallet funds - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The Notional report describes a class of bug where a single failing/misbehaving external protocol interaction (during a batch of external calls) can revert or otherwise permanently derail the caller's process, freezing funds. The NEAR analog is the `WalletContract` (eth-implicit account contract), which serializes all of a user's Ethereum-emulated transactions through a single `has_in_flight_tx` flag and depends on cross-contract calls to an arbitrary, attacker-influenced NEP-141 token contract (`target`) as part of ERC-20 transfer emulation. If that external contract's response causes the wallet's callback to fail (e.g., run out of gas), NEAR's atomic receipt-rollback semantics restore `has_in_flight_tx` to its prior (`true`) value, and the flag can never be cleared again — permanently DOS-ing the wallet contract and freezing any funds/authority tied to it.

### Finding Description
`WalletContract::rlp_execute` enforces single-flight execution using an in-contract flag: [1](#0-0) 

For ERC-20 transfer emulation, the wallet contract makes a cross-contract call to `target` (an arbitrary NEP-141 token account, effectively chosen based on the "to" field of the user's signed Ethereum-style transaction) to check `storage_balance_of`, before chaining into `nep_141_storage_balance_callback`: [2](#0-1) 

The callback clears the in-flight flag as its very first statement, then deserializes the external contract's arbitrary response with `serde_json::from_slice`, and only re-sets the flag to `true` if it successfully builds and returns a new promise: [3](#0-2) 

The static gas budget allocated to this callback is fixed and small (15 Tgas total): [4](#0-3) 

Because `target`/the NEP-141 token is an external, unprivileged, and attacker-controllable contract (the wallet contract source itself acknowledges this risk class, e.g. hardcoding the storage deposit amount specifically "to prevent malicious token contracts ... from taking lots of $NEAR from eth-wallet-contract users", see comment at lines 28-32), a malicious/compromised token contract can return an oversized or adversarially-structured JSON payload from `storage_balance_of`. Parsing such a payload inside the 15 Tgas-limited callback can exceed the prepaid/allocated gas, causing the WASM execution to panic with a gas-exhaustion error.

NEAR's runtime treats such a failed receipt atomically: any in-memory state mutation performed during that failed execution — including the `self.has_in_flight_tx = false` write made at the top of `nep_141_storage_balance_callback` — is discarded via `state_update.rollback()`, and only the previously-committed value of `has_in_flight_tx` (`true`, set by the prior successful receipt) persists: [5](#0-4) 

Since `rlp_execute` unconditionally refuses to proceed whenever `has_in_flight_tx == true`, and there is no other code path or timeout mechanism that can reset this flag once it is stuck, the wallet contract becomes permanently unusable.

### Impact Explanation
Once bricked, the wallet-contract account can never process another `rlp_execute` call: every future call — including legitimate transfers, key management, or attempts to move funds out — is rejected immediately with "transaction already in progress." This permanently freezes any NEAR balance held by the wallet-contract account and any authority it represents (its associated Ethereum-style address is effectively disabled forever), a permanent freezing-of-funds outcome. Unlike the underlying Notional bug (temporary DOS of a discretionary rebalance), this NEAR analog can permanently lock an ordinary end user's account with no recovery path, since the flag can only be legitimately cleared by a callback receipt that must itself succeed against the same (compromised/malicious) external dependency.

### Likelihood Explanation
The `target` NEP-141 contract used in ERC-20 transfer emulation is not vetted, hardcoded, or size-limited by the Wallet Contract; it is effectively derived from the Ethereum-transaction's `to` address, so a user (or anyone tricking a user into interacting with a malicious token) can point at an adversarial or buggy token contract. Crafting a `storage_balance_of` view response large/complex enough to exceed a 15 Tgas JSON-deserialization budget is a standard, well-understood gas-griefing technique and does not require any privileged access — it only requires deploying an ordinary (if malicious) NEP-141-like contract and inducing a transfer to it through the wallet.

### Recommendation
- Bound the size of external call results consumed inside gas-limited callbacks (e.g., reject/short-circuit if `env::promise_result` payload exceeds a small, sane size before attempting to deserialize it), or perform deserialization with an explicit gas/size guard.
- Ensure `has_in_flight_tx` cannot get stuck due to a failed/panicking callback receipt — e.g., use a callback-independent mechanism (such as a timeout, or clearing the flag in a step that is guaranteed to commit even when the inner logic fails) rather than relying on a flag write that is only committed if the entire callback function returns without panicking.
- Increase/parameterize the static gas allotted to `nep_141_storage_balance_callback` and add defensive limits so an external token contract cannot control whether the wallet's own bookkeeping state commits.

### Proof of Concept
1. Deploy a NEP-141-style contract `evil.near` whose `storage_balance_of` view method returns a very large/deeply-structured JSON value (e.g., megabytes of data or deeply nested arrays) instead of a normal `StorageBalance`/`null`.
2. As the wallet owner, sign an Ethereum-style transaction emulating an ERC-20 transfer with `to` = the address corresponding to `evil.near`, and submit it via `rlp_execute(target = "evil.near", tx_bytes_b64 = ...)`. This sets `has_in_flight_tx = true` and schedules a call chain ending in `nep_141_storage_balance_callback`.
3. `evil.near::storage_balance_of` returns the oversized payload; `nep_141_storage_balance_callback` sets `self.has_in_flight_tx = false` in memory, then calls `serde_json::from_slice::<Option<StorageBalance>>(&value)`, which consumes gas well beyond the fixed `NEP_141_STORAGE_BALANCE_CALLBACK_GAS` (15 Tgas), causing the receipt to fail with "Exceeded the prepaid gas."
4. Per NEAR's failed-receipt atomicity (`runtime/runtime/src/lib.rs` rollback path), the entire state mutation of this receipt — including the `has_in_flight_tx = false` write — is discarded; the account's persisted `has_in_flight_tx` remains `true` from step 2.
5. Any subsequent call to `rlp_execute` on this account immediately returns `"Error: transaction already in progress, please try again later."` indefinitely, with no way to reset the flag — permanently freezing the wallet contract and its funds.

    pub fn nep_141_storage_balance_callback(
        &mut self,
        token_id: AccountId,
        receiver_id: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_storage_balance: Option<StorageBalance> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some(format!("Call to NEP-141 {token_id}::storage_balance_of failed")),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from NEP-141 storage_balance_of".into()),
                    });
                }
            },
        };
