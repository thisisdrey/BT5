### Title
Unbounded ZIP central-directory field parsing causes out-of-bounds read on crafted archives - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in ijar's ZIP reader parses central-directory-header fields and their "extra fields" directly from a memory-mapped input file without any bounds checking against the mapped file length, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every field read.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` guards every read with `EnsureRemaining(n, "state")`, which compares the requested read size against `input_file_->Length() - in_offset` and aborts with an error if a read would run past the end of the mapped file: [1](#0-0) .

`ProcessCentralDirEntry`, in contrast, unconditionally reads the signature, sizes, name/extra/comment lengths, attributes and offset fields, and then walks the "extra fields" sub-records with no equivalent check: [2](#0-1) .

The extra-field walking loop is particularly unsafe:
```
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
``` [3](#0-2) 

This loop assumes each sub-record's declared `data_size` exactly tiles the `extra_field_length` span. A crafted central directory entry can set a `data_size` that does not evenly divide the extra-field region (or is arbitrarily large), causing `extra_p` to overshoot the intended boundary `p`. Because the loop condition is `extra_p != p` (not a `<=`/`<` bound check), an overshoot means the pointer never re-equals `p` and the loop keeps calling `get_u2le`/`get_u8le` on `extra_p`, walking arbitrarily far past the end of the extra-field region — and potentially past the end of the entire memory-mapped file — reading whatever bytes happen to reside beyond the mapping (an out-of-bounds heap/mmap read, directly analogous to the OpenEXR `rleUncompress` OOB read triggered by malformed run-length-encoded length fields).

There is no caller-side validation that bounds `central_dir_` traversal to the mapped file's extent before this function is invoked — `ProcessNext()` and `CalculateOutputLength()` simply loop calling `ProcessCentralDirEntry` until it returns `false`, and `false` is only returned when a signature check fails, not when the cursor has already read out of bounds: [4](#0-3) [5](#0-4) .

### Impact Explanation
`ijar`/`zip.cc` is Bazel's interface-JAR extraction tool, used to process `.jar`/`.zip`-format archives that Bazel treats as build inputs (e.g. class jars from `java_import`, precompiled jars pulled in via `http_archive`/`http_jar`, or jars extracted from Maven-style dependencies). An attacker who controls the bytes of such an archive (a hostile origin server or a malicious release artifact) can craft a central directory entry whose extra-field length/size values are inconsistent, causing the ijar reader to read out of process-mapped memory. The immediate consequence is process crash (SIGSEGV) or leaking adjacent mapped memory contents into decisions made from the read bytes (e.g., misinterpreted size/offset fields feeding into subsequent parsing), i.e., an out-of-bounds read impacting availability and integrity of the parse, matching the CVSS profile of the analog (`C:N/I:N/A:H`).

### Likelihood Explanation
Reaching this code path requires only that an attacker-controlled ZIP/JAR file be supplied as a build input and processed by ijar — a routine, unprivileged action (publishing a crafted jar at a URL a build fetches, or checking one into an untrusted branch). No credentials, sandbox escape, or local machine access are needed. The malformed extra-field structure is a small, easily crafted byte sequence within an otherwise valid-looking ZIP central directory, making this a low-complexity trigger once the target function is confirmed reachable from an untrusted archive.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` (mirroring `EnsureRemaining` in `ProcessLocalFileEntry`) before reading each fixed field and the central directory header pointer itself, and validate that `extra_field_length` sub-records (`header_id`/`data_size` pairs) never cause `extra_p` to exceed `p`; treat any `data_size` that would overshoot the declared `extra_field_length` boundary as a parse error rather than continuing the loop. Additionally validate `p` (and `central_dir_current_`) against `zipdata_in_ + input_file_->Length()` before every dereference inside this function.

### Proof of Concept
I was not able to construct or run an executable JUnit/`BuildIntegrationTestCase`/shell reproduction within this session — I could only confirm the missing-bounds-check pattern via static code reading (`EnsureRemaining` present in `ProcessLocalFileEntry` at lines 332-336/360-369 vs. entirely absent in `ProcessCentralDirEntry` at lines 493-545, plus the unguarded extra-field walk at lines 524-542). Constructing a concrete crafted ZIP (central directory entry with a truncated/mismatched extra-field `data_size`) and verifying the resulting crash/OOB read under ASan would require running `third_party/ijar/zip_test.cc` or a new test against `InputZipFile::ProcessCentralDirEntry`/`CalculateOutputLength`, which I could not execute in this read-only investigation. This should be validated with an ASan-instrumented unit test before treating the finding as fully confirmed.
