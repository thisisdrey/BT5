The bound check in `BatchValidateSign.doExecute()` is guarded by a feature flag, and even when active it only checks the array-size headers used for signature/address extraction — not the general `extractBytesArray`/`extractBytes32Array` helpers used elsewhere in `PrecompiledContracts.java`, which allocate arrays directly from an attacker-controlled length word.

### Title
Unbounded heap allocation in TVM `BatchValidateSign` precompile via attacker-controlled array-length word - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array()` and `extractBytesArray()` read an array length directly from calldata (`words[offset].intValueSafe()`) and immediately allocate `new byte[len][]` with no upper bound before the length is validated against any energy/size limit. `BatchValidateSign.doExecute()` calls these helpers to parse the signatures and addresses arrays supplied by the caller of the `batchvalidatesign` precompiled contract, and the size check (`MAX_SIZE = 16`) that would prevent an oversized allocation is applied only inside an `if (VMConfig.allowTvmSelfdestructRestriction())` branch, mirroring the libheif bug where the bound check is applied on one parsing path but not consistently on all paths feeding the same allocation sink.

### Finding Description
`extractBytes32Array` computes `int len = words[offset].intValueSafe();` and then does `new byte[len][]` with no maximum, and `extractBytesArray` does the same for the non-fixed-size path: [1](#0-0) 

`BatchValidateSign.doExecute()` parses the calldata into `DataWord[] words`, and only when `VMConfig.allowTvmSelfdestructRestriction()` is enabled does it pre-check the size fields (`sigArraySize`/`addrArraySize`) against `MAX_SIZE` before calling the extraction helpers: [2](#0-1) 

`intValueSafe()` clamps a 256-bit `DataWord` into a Java `int`, so an attacker can craft calldata whose offset word (`words[1]`/`words[2]`) points to a slot containing an arbitrarily large 32-bit value (up to `Integer.MAX_VALUE`, i.e. ~2^31). If that length reaches `extractBytesArray`/`extractBytes32Array` before the `MAX_SIZE` gate is enforced — e.g., on chains/configurations where `allowTvmSelfdestructRestriction()` is not yet active, or via the unguarded `extractBytesArray` call when the sig-array-size check is bypassed by pointing `words[1]` at a different index than the one used for the actual extraction offset — the code executes `new byte[len][]`, attempting to allocate a huge object array (2^31 references ≈ 16 GB on 64-bit JVM) in a single call. Energy accounting (`getEnergyForData`) is computed from `data.length`, not from the parsed array length, so the calldata itself can be tiny while the derived length word is enormous, meaning the caller pays negligible energy for triggering a massive allocation attempt.

### Impact Explanation
Any account can invoke the `batchvalidatesign` precompile (address `0x66` équivalent) via a smart-contract call or trigger, supplying crafted calldata. A single transaction can force the full node to attempt an outsized array allocation, throwing `OutOfMemoryError` or causing prolonged GC pressure/stalls across the JVM, which can crash or hang the node process (denial of service for the reachable HTTP/gRPC query paths and transaction processing) — a High severity, unauthenticated-DoS analog of the libheif issue (unbounded allocation from a numeric field with inconsistent bound enforcement across code paths).

### Likelihood Explanation
The precompile is reachable from any deployed contract via `CALL`/`STATICCALL` with attacker-controlled calldata, requiring no special privileges, matching the "unprivileged contract caller" reachability criterion. The vulnerable helper methods have no bound check of their own; safety currently depends entirely on the caller performing an explicit pre-check, and that pre-check is version-gated (`allowTvmSelfdestructRestriction`) and only covers the `sigArraySize`/`addrArraySize` computed from `words[1]`/`words[2]`, not a length embedded elsewhere that the extraction functions could also read (e.g., a crafted `words[1]` value pointing the size-check to a small value while the actual bytes-array parsing offset resolves elsewhere). This makes reliable exploitation configuration/version-dependent, which is why full confirmation (whether current default configs are unaffected) would require confirming `allowTvmSelfdestructRestriction`'s activation status.

### Recommendation
Add a hard upper bound (`MAX_SIZE` or a fixed sane cap) inside `extractBytes32Array` and `extractBytesArray` themselves — not only in the calling `BatchValidateSign` code — so the length is validated before `new byte[len][]` is executed, regardless of feature-flag state or which caller path is exercised. Additionally validate that the derived length is consistent with `data.length` (as is already partly done via `isValidAbiEncoding`) to reject sizes that cannot be backed by the actual calldata.

### Proof of Concept
Craft calldata for the `batchvalidatesign` precompile where:
1. `words[0]` = arbitrary hash.
2. `words[1]` = an offset (in bytes) pointing to a word slot within calldata.
3. That word slot's value is a very large integer (e.g., `0x7FFFFFFF`), used as `len` in `extractBytesArray`.
4. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is not yet enabled (or craft it so the `sigArraySize`/`addrArraySize` guard is bypassed), causing `extractBytesArray(words, offset, data)` to execute `new byte[2^31-1][]` and trigger `OutOfMemoryError`/node stall, all funded by the small `data.length`-based energy cost.

    int len = words[offset].intValueSafe();

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();

    }

  }
