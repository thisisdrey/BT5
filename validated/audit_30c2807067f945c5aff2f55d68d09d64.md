### Title
Unprivileged dust-transfer griefing fills a victim's `MAX_TOKENS_PER_USER` list, DoS-ing deposits, mints, liquidations and rewards for that account - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks every deposit/debt token an account touches in two `MappedEnumerableSet` lists and hard-reverts any insertion that would push the combined count to `MAX_TOKENS_PER_USER = 30`. Because `DepositToken._transfer` is a public, permissionless ERC-20 path that unconditionally registers the *recipient* in `depositTokensOfAccount`, anyone can dust-transfer all of a pool's deposit tokens to a victim and fill their quota. Every subsequent operation that would add a new token to the victim's lists reverts with `UserReachedMaxTokens`.

### Finding Description
The relevant mechanics:

- `Pool.MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`) enforced by `onlyIfAdditionWillNotReachMaxTokens`, which sums `debtTokensOfAccount.length + depositTokensOfAccount.length` (`contracts/Pool.sol:143-148`).
- `addToDepositTokensOfAccount(account_)` reverts via that modifier before inserting (`contracts/Pool.sol:216-220`).
- `DepositToken._transfer` — reachable by any holder via `transfer`/`transferFrom` — calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero, with no opt-out or lock check (`contracts/DepositToken.sol:517-520`).
- The same cap gates `addToDebtTokensOfAccount` (`contracts/Pool.sol:204-208`), which `DebtToken.issue`/`mint` invoke on a first mint.

Attack path:
1. Attacker deposits a dust amount of every deposit token registered in the pool (or buys dust positions on each).
2. Attacker calls `depositToken.transfer(victim, 1)` for each deposit token until `depositTokensOfAccount.length(victim) + debtTokensOfAccount.length(victim) == 30`.
3. The victim can now no longer:
   - deposit into any collateral type they don't already hold (`Pool.deposit` → `DepositToken._mint` → `addToDepositTokensOfAccount` reverts);
   - mint a new synthetic asset / receive debt in a new `DebtToken`;
   - be topped up by `deposit(amount_, onBehalfOf_ = victim)` from a keeper, gateway (`NativeTokenGateway`, `VesperGateway`), or `SmartFarmingManager.leverage` callback — each of these funnels into the same revert, so the whole transaction fails.

### Impact Explanation
- If the victim holds an open debt position approaching the collateral-factor threshold, they cannot add a *new* collateral type to restore health. Any `deposit`/`leverage`/`flashRepay` that introduces a new token reverts, so the position is pushed to liquidation when an otherwise-valid rescue deposit would have saved it — direct, attacker-controlled denial of a liveness-critical path and forced loss via liquidation fees.
- Victims are blocked from opening any position requiring a token not already in their lists, and airdrop/deposit-on-behalf flows targeting them revert. Impact class: temporary freezing of funds / blocked protocol liveness for the targeted account (the victim can recover slots only by spending gas to transfer out each dusted token — itself griefable since the attacker can re-dust).

### Likelihood Explanation
Requires no privileged role, no oracle manipulation, and no governance action — only dust amounts of the pool's whitelisted deposit tokens (attacker funds are recoverable afterward). Feasibility depends on the deployed pool offering enough tokens (deposit + debt) to reach 30 combined; where the offering is smaller, the same attack still caps the victim at the pool's token count and blocks all *new* token types. The `updateRewardsBeforeTransfer` hook and `nonReentrant` guards do not stop it — `transfer` is the intended public entry point.

### Recommendation
Let recipients opt out of list registration on plain transfers: e.g., skip `addToDepositTokensOfAccount` inside `_transfer` (transfers don't confer collateral benefit unless tokens are locked/supplied via `deposit`), or only register on `deposit`/`mint` paths while treating a received-but-unregistered balance as non-collateral. Alternatively, drop the `MAX_TOKENS_PER_USER` revert in favor of bounded iteration elsewhere, or allow `removeFromDepositTokensOfAccount` semantics to be triggered permissionlessly for zero-balance entries so slots self-clean.

### Proof of Concept
```solidity
// Foundry-style test against a deployed-pool fork
function test_Grief_MaxTokensPerUser() public {
    // victim already holds 1 deposit token and some debt
    vm.startPrank(attacker);
    for (uint i; i < depositTokens.length; ++i) {
        // attacker holds or acquires dust of each whitelisted deposit token
        IDepositToken(depositTokens[i]).transfer(victim, 1); // registers each token
    }
    vm.stopPrank();

    assertEq(
        pool.getDepositTokensOfAccount(victim).length
      + pool.getDebtTokensOfAccount(victim).length,
        pool.MAX_TOKENS_PER_USER()
    );

    // victim's rescue deposit into a collateral type they don't yet hold reverts
    vm.startPrank(victim);
    underlying.approve(address(newDepositToken), type(uint256).max);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newDepositToken.deposit(1e18, victim); // via Pool.deposit -> _mint -> addToDepositTokensOfAccount
}
```
Any Hardhat/Foundry fork test that dust-transfers each listed `DepositToken` to a victim and then calls `pool.deposit`/`debtToken.issue` for a token the victim doesn't hold reproduces the revert.
