### Title
Floating-point AMM pricing in the default `Exchange` bonding-curve path enables pool-draining arithmetic manipulation - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
The Impermax report describes a flash-loan attack that manipulated an AMM's internal pricing math to drain its V3 liquidity pools. Java-tron ships its own on-chain AMM primitive — the `Exchange`/`ExchangeV2` Bancor-style relay pools, reachable by any unprivileged account through `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract` and `ExchangeTransactionContract`. The default (non-hardened) pricing engine, `ExchangeProcessor`, computes the bonding-curve swap output using IEEE-754 `double` arithmetic and `Math.pow`, then truncates to `long`, instead of using exact/BigDecimal math.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the dynamic property `allowHardenExchangeCalculation`: [1](#0-0) 

When hardening is not enabled, it falls back to `ExchangeProcessor`, whose `exchangeToSupply`/`exchangeFromSupply` methods use `double` and `Maths.pow`, a floating-point operation with rounding/precision error that does not match the mathematically exact Bancor formula: [2](#0-1) 

The existence of a separate, purpose-built `SafeExchangeProcessor` that reimplements the same formula with `BigDecimal`/`RoundingMode.HALF_UP` and explicit overflow-checked (`StrictMathWrapper`) arithmetic confirms this was recognized internally as an arithmetic-integrity gap in the original implementation: [3](#0-2) 

`ExchangeTransactionActuator.execute()` is reachable by any signed transaction from any account and directly invokes `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())`, applying whatever quantity the caller supplies to the pool balances and crediting the computed “another token” amount back to the caller's account: [4](#0-3) 

Because `allowHardenExchangeCalculation` is a committee-controlled dynamic property (introduced later as a hardening switch) rather than the default execution path, any deployment where the committee has not proposed/activated it continues to run the floating-point calculation for every trade, inject, and withdraw against every `Exchange` pool. An attacker who can chain multiple trade/inject/withdraw transactions in sequence against a lightly-capitalized pool can exploit the accumulated floating-point truncation error in `exchangeToSupply`/`exchangeFromSupply` to extract more of the counter-asset than the pool should mathematically yield, incrementally draining the pool balance recorded in `ExchangeCapsule` — conceptually the same “price/accounting math exploited within a short transaction sequence” bug class as the Impermax V3 pool drain, adapted to TRON's built-in AMM instead of an EVM contract.

### Impact Explanation
A successful drain empties the `firstTokenBalance`/`secondTokenBalance` of an `Exchange` pool capsule, transferring TRX/TRC-10 asset balance to the attacker beyond what the invariant permits — a direct theft-of-funds condition for any account that has injected liquidity into that exchange pool, matching the "unauthorized... theft... of funds" acceptance bar.

### Likelihood Explanation
The attack path requires only standard, unprivileged `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions — no special privilege, SR/witness role, or off-chain component — and is gated purely by whether the `allowHardenExchangeCalculation` committee proposal has been activated on a given network. On networks/testnets where it has not been enabled, the vulnerable floating-point path is the live default for every `Exchange` pool.

### Recommendation
Force the hardened, exact-arithmetic path (`SafeExchangeProcessor`) unconditionally for all exchange operations rather than gating it behind an opt-in dynamic property, and add invariant checks (e.g., constant-product/relay-supply monotonicity assertions) after every trade/inject/withdraw in `ExchangeCapsule.transaction()` to reject any calculation result that would violate the pool's economic invariants regardless of which `Processor` is used.

### Proof of Concept
Not independently reproduced with a live network; based on static analysis of `ExchangeProcessor`'s floating-point formula versus `SafeExchangeProcessor`'s exact formula and the actuator paths above. I was unable to confirm the on-chain default value of `allowHardenExchangeCalculation` in `DynamicPropertiesStore.java` (grep did not surface an explicit default), so whether a specific mainnet deployment is currently affected versus already hardened is uncertain and would need to be verified against that store's initialization code and the chain's proposal history.

    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

  }

  private long exchangeFromSupply(long balance, long supplyQuant) {

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
