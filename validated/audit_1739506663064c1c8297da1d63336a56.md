### Title
Unprivileged slot signer can bypass `write-freq` throttle via `POST /v2/stackerdb/:principal/:contract/chunks` to force network-wide chunk re-broadcast - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
Any legitimate StackerDB slot signer (a role assigned by the smart contract, not a node admin) can submit an unlimited number of validly-signed, monotonically-versioned chunks to their own slot in rapid succession, because the write-acceptance path never enforces the contract-configured `write_freq` (wall-clock write throttle). Each accepted write is relayed to the whole network, producing a repeated, remotely-triggerable propagation/storage cost analogous to the Solvent "repeated unstake" DoS: an unprivileged, otherwise-legitimate action is abused at high frequency to make the system repeatedly do costly work.

### Finding Description
`StackerDBTx::try_replace_chunk` is the sole gate used by the HTTP chunk-write endpoint. It checks chunk size, slot existence, signer/signature validity, staleness, and `max_writes`, but never checks `write_time`/`write_freq`: [1](#0-0) 

`insert_chunk`, which actually performs the write, also does not consult `write_freq`; its own doc comment says the lamport-clock/authentication checks "will not be checked" here (they're the caller's job) — and the caller (`try_replace_chunk`) indeed skips `write_freq`: [2](#0-1) 

The HTTP handler for `POST /v2/stackerdb/:principal/:contract/chunks` calls `try_replace_chunk` directly and, on success, unconditionally relays the accepted chunk to the whole network via `node.set_relay_message(StacksMessageType::StackerDBPushChunk(...))`: [3](#0-2) [4](#0-3) 

The only place `write_freq` is consulted at all is on the *read/fetch-scheduling* side of sync, to decide whether a stale-looking peer's chunk is worth re-fetching — not to reject or throttle incoming writes: [5](#0-4) 

`validate_received_chunk`, used both for downloaded chunks and for unsolicited pushed chunks (`handle_unsolicited_StackerDBPushChunk`), explicitly documents that it does not check write frequency, "since the caller has different ways of doing this": [6](#0-5) 

But tracing the actual callers (the HTTP write endpoint above, and the store path used by sync) shows `write_freq` is never enforced anywhere on the write-acceptance side — it is used purely as a hint for scheduling fetches, not as an admission-control check. This breaks the intended equality "chunk accepted only if `now >= write_time + write_freq`" — the contract-declared throttle exists in config but has no enforcement point.

### Impact Explanation
A signer only needs their own valid slot-signing key (a normal, contract-assigned, non-admin role — e.g. a miner/stacker/signer participant, exactly analogous to an ordinary NFT staker in the Solvent report) to submit as many strictly-increasing-version, correctly-signed chunks as desired, with no wall-clock spacing. Each accepted write causes:
- a local DB write,
- a network-wide relay broadcast (`StacksMessageType::StackerDBPushChunk`) to peers,
- every receiving replica to validate the signature, store the chunk, and potentially re-broadcast further via its own sync round.

This lets a single legitimate signer force continual re-validation/re-storage/re-broadcast cycles across the network, undermining the intended cadence that `write_freq` was meant to enforce (analogous to how Solvent's unstake spam denied staking rewards to the whole system) — a state-mutation DoS vector reachable by any unprivileged signer, not just an admin.

### Likelihood Explanation
High for any account already holding a StackerDB slot-signing key (a routine, non-privileged, contract-granted role) — no special access, secrets, or admin keys are needed, and the exploit requires only repeatedly calling a public RPC endpoint with a valid, self-signed, version-incrementing chunk. `max_writes` bounds the total number of writes per slot lifetime but not their rate, so the attack is not blocked by that check.

### Recommendation
Enforce `write_freq` at the same point `max_writes` and staleness are enforced — i.e., inside `StackerDBTx::try_replace_chunk` (and/or `insert_chunk`) — by comparing `get_epoch_time_secs()` against the slot's stored `write_time` plus `config.write_freq`, returning a `net_error::TooFrequentSlotWrites` (which already exists as an error variant) before accepting the write, rather than relying on downstream fetch-scheduling logic that only advises other peers when to re-fetch.

### Proof of Concept
1. Obtain a valid private key for a slot already assigned in a StackerDB's signer set (a normal, non-admin, contract-designated role).
2. Repeatedly call `POST /v2/stackerdb/:principal/:contract/chunks` with `StackerDBChunkData` at `slot_id`, incrementing `slot_version` by 1 each time and signing correctly, with no delay between calls (well under the contract's configured `write-freq`).
3. Observe that `try_replace_chunk` (stackslib/src/net/stackerdb/db.rs:400) accepts every request as long as `slot_version` increases and stays within `max_writes`, since `write_freq`/`write_time` is never checked in this path.
4. Each accepted chunk is relayed via `StacksMessageType::StackerDBPushChunk` to the network (stackslib/src/net/api/poststackerdbchunk.rs:315-324), forcing every peer replicating that StackerDB to repeatedly validate and store the churned chunk far more often than the contract's `write-freq` was intended to permit.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
