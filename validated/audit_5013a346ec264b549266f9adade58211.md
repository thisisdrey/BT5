Confirmed: `f.routines > 1` spins up multiple concurrent UDP-reader goroutines (`listenOut`, one per queue) that all funnel into `readOutsidePackets` and ultimately `ConnectionState.Decrypt` / `VerifyRelay` for the *same* `hostinfo.ConnectionState` object concurrently.

### Title
Replay-window check/update race in `ConnectionState.Decrypt`/`VerifyRelay` allows a captured packet to be processed twice under multi-queue (`routines > 1`) - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check into two separately-locked steps: `window.Check` (gate) then, after the AEAD operation completes outside any lock, `window.Update` (mark-seen). Because `f.routines > 1` runs multiple independent reader goroutines (`Interface.listenOut`, one per UDP queue, see `interface.go:275-286` and `interface.go:309-337`) that can call `readOutsidePackets` concurrently for the same `hostinfo`, two goroutines can both pass `Check` for the same `messageCounter` before either calls `Update`. This is structurally the same bug class as the ZetaChain report: a "pending" state (decrypt in flight, not yet marked as seen) is treated as if it were still "available" by a second concurrent check, because the code checks a data structure for "already recorded" rather than atomically claiming the slot before doing the expensive/side-effecting work.

### Finding Description
`connection_state.go`:
```go
func (cs *ConnectionState) Decrypt(...) ([]byte, error) {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)   // gate
	cs.decryptLock.Unlock()
	if !result { return nil, ErrAlreadySeen }

	out, err = cs.dKey.DecryptDanger(...)          // no lock held here
	...
	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)   // mark seen, after the fact
	cs.decryptLock.Unlock()
	...
}
``` [1](#0-0) 

`VerifyRelay` has the identical Check-then-(unlocked work)-then-Update pattern: [2](#0-1) 

The replay window itself (`Bits.Check` / `Bits.Update`) is correctly implemented to reject true duplicates when called serially: [3](#0-2) 

But because `Check` and `Update` are two independently-locked calls rather than one atomic "claim-then-process" operation, an attacker who captures one legitimate ciphertext packet and replays it can have both copies reach the `Check` step (on different reader goroutines pinned to different UDP queues) before either has advanced `window.current`/set the bit via `Update`. Both goroutines then proceed to `DecryptDanger` with the same `messageCounter`/nonce (harmless per AEAD, since it's the identical ciphertext) and both dispatch the decrypted payload into `handleOutsideMessagePacket` / `handleOutsideRelayPacket`, i.e. the packet is processed and delivered twice instead of the second copy being dropped as a replay.

Nebula explicitly runs multiple concurrent reader queues when `routines > 1` is configured: [4](#0-3) [5](#0-4) 

This is exactly the report's bug class: a function meant to gate on "not yet completed / in-flight" state (`Check`) is consulted and trusted as proof of "not a duplicate," while the actual completion marker (`Update`) that would make the state accurate lags behind the real work, letting concurrently in-flight items slip through the same window twice.

### Impact Explanation
This weakens (does not fully defeat) the anti-replay guarantee on the data plane and on relay frames for deployments running with `routines > 1` (multi-queue UDP, a documented and encouraged performance configuration). A network-path attacker who can capture a single legitimate ciphertext packet (no CA-signed certificate needed — this is a post-handshake data-plane/relay frame, reachable purely from observing traffic on the wire) can attempt to get it delivered twice to the tun interface or forwarded twice through a relay, by racing delivery across queues. The changelog's own fix for `#1751`/`#1802` ("Advance the replay window on relayed packets..." / "Lock replay window updates so concurrent readers can't corrupt it") shows this exact class of concurrency bug has already bitten this codebase once; the Check/Update split here reintroduces a narrower version of the same race at the "two lock acquisitions instead of one" level.

### Likelihood Explanation
Requires: (1) `routines > 1` configured (multi-queue enabled, common for performance), (2) attacker able to capture and replay a valid ciphertext packet on the underlay network (no cert needed, matches "reachable without CA-signed certificate"), and (3) winning a narrow race between two reader goroutines. This is a genuine but narrow timing window (a handful of instructions between the two lock acquisitions), so it is lower likelihood than a deterministic bypass, but it is deterministically exploitable given repeated replay attempts and true concurrency across queues.

### Recommendation
Collapse `Check` and `Update` into a single atomically-locked "claim" operation performed before the AEAD operation, e.g. hold `decryptLock` across a combined `Check-and-provisionally-mark` step, only reverting the mark if `DecryptDanger` fails. This removes the check/complete split entirely rather than trying to reconcile two independent snapshots of window state, mirroring the eventual ZetaChain-style fix of not trusting an intermediate "attempted" state as proof of "settled/deduplicated."

### Proof of Concept
1. Start two nebula nodes with `routines: 2` (or more) so `Interface.run()` launches multiple `listenOut` goroutines sharing the same `hostMap`/`ConnectionState` (`interface.go:273-287`).
2. Establish a tunnel between A and B.
3. Capture one legitimate encrypted data packet (or relay frame) sent from A to B, e.g. via a MITM tap on the underlay UDP socket.
4. Rapidly re-inject two copies of the identical captured packet at B, targeting different UDP source ports/sockets or timed to land on separate `SO_REUSEPORT` queues so they are picked up by different `listenOut(i)` goroutines almost simultaneously.
5. Observe (with logging/instrumentation on `Bits.Check`/`Bits.Update`) whether both copies pass `window.Check` before either calls `window.Update`, and whether `handleOutsideMessagePacket` (or `SendVia` for relay) is invoked twice for the same `messageCounter`, indicating the duplicate was delivered rather than dropped.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.

	return false
}

func (f *Interface) listenOut(i int) {
	var li udp.Conn
	if i > 0 {
		li = f.writers[i]
	} else {
		li = f.outside
	}

	ctCache := firewall.NewConntrackCacheTicker(f.ctx, f.l, f.conntrackCacheTimeout)
	lhh := f.lightHouse.NewRequestHandler()
	plaintext := make([]byte, udp.MTU)
	h := &header.H{}
	fwPacket := &firewall.Packet{}
	nb := make([]byte, 12, 12)

	err := li.ListenOut(func(fromUdpAddr netip.AddrPort, payload []byte) {
		f.readOutsidePackets(ViaSender{UdpAddr: fromUdpAddr}, plaintext[:0], payload, h, fwPacket, lhh, nb, i, ctCache.Get())
	})

	// An error after teardown began is shutdown noise, the closed flag covers resources
	// Close releases itself and the cancelled ctx covers ones torn down by their owners
	// reacting to it, like the user device pipes
	if err != nil && !f.closed.Load() && f.ctx.Err() == nil {
		f.l.Error("Error while reading inbound packet, closing", "error", err)
		f.onFatal(err)
	}

	f.l.Debug("underlay reader is done", "reader", i)
}
