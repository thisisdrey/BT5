### Title
Unstaked QUIC connections can inflate `max_uni_streams` up to 7x `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` via RTT/BDP scaling - ([File: streamer/src/nonblocking/swqos.rs])

### Summary
`compute_max_allowed_uni_streams_with_rtt` applies BDP-based RTT scaling uniformly to both staked and unstaked peer types, but the unstaked base value (`QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS = 128`) is not clamped to that constant after scaling. Because an unstaked, unprivileged client fully controls the path/timing characteristics observed by the QUIC RTT estimator, it can inflate its observed RTT toward `MAX_RTT_MS` (350ms) to obtain up to ~7x more concurrent uni-streams than the named policy maximum permits.

### Finding Description
`cache_new_connection` computes the per-connection concurrent-uni-stream limit from the connection's measured RTT and applies it directly to the QUIC transport parameter: [1](#0-0) 

The scaling function is: [2](#0-1) 

For `ConnectionPeerType::Unstaked`, `streams` is set to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` (128), but this base value is then multiplied by `rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS) / REFERENCE_RTT_MS` with **no subsequent clamp** back to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS`, unlike the staked path which is explicitly `.clamp(QUIC_MIN_STAKED_CONCURRENT_STREAMS, QUIC_MAX_STAKED_CONCURRENT_STREAMS)`-bounded *before* RTT scaling is applied on top of it. The repo's own unit test demonstrates the unbounded growth for high RTT: [3](#0-2) 

At `REFERENCE_RTT_MS = 50` and `MAX_RTT_MS = 350`, the maximum unstaked scaling factor is `350/50 = 7`, so `max_uni_streams` can reach `128 * 7 = 896`, i.e. 7x the constant that is documented and named as the "max" for unstaked connections.

The RTT value fed into this computation, `connection.rtt()`, is derived from quinn's QUIC RTT estimator, which is driven by ACK timing between the two QUIC endpoints. An unstaked remote client fully controls its own send/ACK timing and network path to the leader's TPU QUIC port (per the stated threat model), so it can deliberately introduce or declare added latency (e.g., routing through a high-latency path, or delaying its own ACK transmissions) to drive the server-observed RTT toward `MAX_RTT_MS` without needing any staked/privileged capability.

This inflates the QUIC transport-level `max_concurrent_uni_streams` value advertised to the peer via `connection.set_max_concurrent_uni_streams(max_uni_streams)`, which governs how many uni-directional streams the client is allowed to have open concurrently at the QUIC protocol layer — independent of the separate application-level `throttle_stream` rate limiter in `stream_throttle.rs`, which only limits the *rate* of new streams accepted per 100ms window, not the concurrent count permitted by the QUIC transport itself.

### Impact Explanation
This is a QoS/policy-evasion bug: an unstaked, unprivileged attacker can obtain up to ~7x more concurrently open QUIC uni-streams than the `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` policy value intends, increasing per-connection resource consumption (stream state, buffers) allocated by the validator's QUIC streamer for unstaked, low-priority traffic. This falls under QoS evasion / disproportionate resource allocation to unstaked peers, undermining the stake-weighted QoS design that is supposed to prioritize staked traffic and cap unstaked connection resource usage.

### Likelihood Explanation
Fully feasible with only network-path/timing control, matching the stated attacker capability exactly (no staked/gossip/config access required). The scaling behavior is deterministic and directly reproducible from the existing unit test in the same file, which already demonstrates values exceeding `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` for RTT above `REFERENCE_RTT_MS`.

### Recommendation
Clamp the final `max_uni_streams` result for `ConnectionPeerType::Unstaked` to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` after RTT scaling (mirroring the `.clamp(...)` already applied on the staked branch), so BDP scaling cannot push unstaked connections' concurrent-stream allowance above the documented policy maximum.

### Proof of Concept
Extend the existing test module in `streamer/src/nonblocking/swqos.rs`:

```rust
#[test]
fn test_unstaked_max_uni_streams_never_exceeds_policy_cap() {
    for rtt in 0..=MAX_RTT_MS {
        let max_streams = compute_max_allowed_uni_streams_with_rtt(
            rtt,
            ConnectionPeerType::Unstaked,
            10_000,
        );
        assert!(
            max_streams <= QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
            "rtt={rtt} produced max_uni_streams={max_streams}, exceeding policy cap {QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS}"
        );
    }
}
```
This fuzz-style loop over all RTT values up to `MAX_RTT_MS` fails against current code (e.g., at `rtt=350`, `max_streams=896 > 128`), confirming the bypass; it should pass once the unstaked branch is clamped.

fn compute_max_allowed_uni_streams_with_rtt(
    rtt_millis: u32,
    peer_type: ConnectionPeerType,
    total_stake: u64,
) -> u32 {
    let streams = match peer_type {
        ConnectionPeerType::Staked(peer_stake) => {
            // No checked math for f64 type. So let's explicitly check for 0 here
            if total_stake == 0 || peer_stake > total_stake {
                warn!(
                    "Invalid stake values: peer_stake: {peer_stake:?}, total_stake: \
                     {total_stake:?}"
                );

                QUIC_MIN_STAKED_CONCURRENT_STREAMS
            } else {
                let delta = (QUIC_TOTAL_STAKED_CONCURRENT_STREAMS
                    - QUIC_MIN_STAKED_CONCURRENT_STREAMS) as f64;

                (((peer_stake as f64 / total_stake as f64) * delta) as u32
                    + QUIC_MIN_STAKED_CONCURRENT_STREAMS)
                    .clamp(
                        QUIC_MIN_STAKED_CONCURRENT_STREAMS,
                        QUIC_MAX_STAKED_CONCURRENT_STREAMS,
                    )
            }
        }
        ConnectionPeerType::Unstaked => QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS,
    };
    // scale amount of streams based on RTT if RTT is larger than REFERENCE_RTT_MS
    // multiply first then divide to avoid rounding errors.
    (streams.saturating_mul(rtt_millis.clamp(REFERENCE_RTT_MS, MAX_RTT_MS))) / REFERENCE_RTT_MS
}
