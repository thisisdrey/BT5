## Finding

### Title
Missing Precision-Loss Validation in `ExchangeInjectActuator` Allows Ratio Manipulation of TRC10 Exchange Pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` are mirror-image actuators that both compute a proportional `anotherTokenQuant` for a bancor-style exchange pool using integer/BigInteger division that truncates any fractional remainder. `ExchangeWithdrawActuator.doValidate()` guards against the resulting rounding drift with an explicit "Not precise enough" check, but the structurally identical `ExchangeInjectActuator.doValidate()` has no equivalent check, letting the pool ratio be skewed by injections that round in the injector's favor.

### Finding Description
Both actuators compute the counterpart token amount from the pool ratio:

`ExchangeInjectActuator` (execute/validate) truncates via `BigInteger.divide()`/`floorDiv`: [1](#0-0) 

`ExchangeWithdrawActuator.doValidate()` performs the same truncating division but then explicitly checks the relative rounding error and rejects the transaction if it exceeds `0.0001` (0.01%), both in "hardened" (`BigDecimal`, `RoundingMode.HALF_UP`) and legacy `double` modes: [2](#0-1) 

`ExchangeInjectActuator.doValidate()` has no analogous check — after computing `anotherTokenQuant` it only verifies `anotherTokenQuant > 0` and that the resulting balances stay under `getExchangeBalanceLimit()`; it never verifies that the truncated amount is close to the exact proportional value: [3](#0-2) 

Because `firstTokenBalance`/`secondTokenBalance` can be small (e.g., low-decimal TRC10 tokens) and `tokenQuant` is fully attacker-chosen, the exchange creator can craft an inject transaction where the exact proportional `anotherTokenQuant` has a large fractional part; truncation then produces an `anotherTokenQuant` far below the value required to preserve the pool's price ratio. Since `execute()` unconditionally applies the same truncated value to `exchangeCapsule.setBalance(...)`, the on-chain pool ratio is shifted by an amount `ExchangeWithdrawActuator` would have rejected for the reverse operation.

### Impact Explanation
The exchange's price for all subsequent swaps (`ExchangeTransactionActuator`, reachable by any unprivileged trader) is derived directly from `firstTokenBalance`/`secondTokenBalance` maintained here. By repeatedly injecting amounts engineered to maximize rounding-favorable truncation, the pool's creator can move the exchange price away from its fair value without providing proportional counterpart liquidity, then profit by trading against unsuspecting counterparties at the skewed price (or by having victims trade against the manipulated pool). This is a concrete unauthorized value-extraction vector reachable from a single signed `ExchangeInjectContract` transaction, matching the class of "inconsistent validation between mirror deposit/withdraw functions" from the referenced report.

### Likelihood Explanation
Only the exchange's creator can call `ExchangeInjectContract`/`ExchangeWithdrawContract` for a given exchange (enforced by the creator check), so this is not open to arbitrary third parties, but it is fully reachable by any address that creates its own exchange pool via a normal, unprivileged `ExchangeCreateContract` transaction and other users who trade against it are exposed to the resulting price manipulation. No special permissions beyond normal account/asset ownership are required.

### Recommendation
Add the same relative-precision check used in `ExchangeWithdrawActuator.doValidate()` (hardened `BigDecimal` remainder check, gated by `allowHarden()`/`getAllowHardenExchangeCalculation`) to `ExchangeInjectActuator.doValidate()`, rejecting injections whose truncated `anotherTokenQuant` deviates from the exact proportional value beyond the same tolerance, so both mirror operations enforce identical ratio-preservation guarantees.

### Proof of Concept
1. Attacker creates an exchange pool (`ExchangeCreateContract`) with `firstTokenBalance` and `secondTokenBalance` chosen so that a small `tokenQuant` produces a large truncation remainder in `anotherTokenQuant = bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`.
2. Attacker (as creator) submits `ExchangeInjectContract` with that `tokenQuant`; `ExchangeInjectActuator.doValidate()` accepts it because it only checks `anotherTokenQuant > 0` and the balance limit — no precision check exists, unlike in `ExchangeWithdrawActuator`.
3. `execute()` applies the truncated `anotherTokenQuant` to `exchangeCapsule.setBalance(...)`, shifting the pool ratio in the attacker's favor.
4. Any subsequent trader calling `ExchangeTransactionActuator` swaps at the now-skewed price, allowing the attacker to extract value by trading back against the manipulated pool.
