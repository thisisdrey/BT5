### Title
Lighthouse relay-address cache accepts unvalidated attacker-supplied relay addresses via `unlockedSetRelay`, bypassing the `remote_allow_list`/self-network checks enforced on `V4`/`V6` addresses - (File: `lighthouse.go`, `remote_list.go`)

### Summary
`LightHouseHandler.handleHostUpdateNotification` and `LightHouseHandler.handleHostQueryReply` both process attacker-reachable lighthouse metadata messages and write the reported addresses into a peer's `RemoteList`. For `V4AddrPorts`/`V6AddrPorts` they call `RemoteList.unlockedSetV4`/`unlockedSetV6` and explicitly pass `lhh.lh.unlockedShouldAddV4`/`unlockedShouldAddV6` as a validation callback, which enforces `lighthouse.remote_allow_list` and rejects addresses inside our own VPN network. For the relay list, however, both handlers call `RemoteList.unlockedSetRelay(fromVpnAddrs[0], relays)` with no validation callback at all, so attacker-controlled relay VPN addresses are accepted and cached unconditionally.

### Finding Description
`unlockedSetV4`/`unlockedSetV6` are always invoked together with a `checkFunc` (`unlockedShouldAddV4`/`unlockedShouldAddV6`), which re-implements the same allow/deny logic as `LightHouse.shouldAdd`: [1](#0-0) [2](#0-1) 

That callback denies any candidate address that is blocked by `lighthouse.remote_allow_list` or that falls inside our own VPN networks: [3](#0-2) 

In contrast, the relay list update on the very same code paths passes no callback and performs no equivalent check: [4](#0-3) [5](#0-4) 

This is the same bug class as the reported issue: one code path (`unlockedSetV4`/`unlockedSetV6`) enforces the safety invariant (address must pass `remote_allow_list` and must not be a self address), while a second, equally reachable path (`unlockedSetRelay`, invoked from `handleHostUpdateNotification`/`handleHostQueryReply`) writes attacker-supplied data to the same trust structure (`RemoteList`) without going through that validation. Any peer that can complete a handshake with a lighthouse (or with any node that processes a `HostQueryReply`) can therefore inject arbitrary "relay" VPN addresses into another host's relay cache — including addresses that `remote_allow_list` was configured to block.

I could not directly view the body of `RemoteList.unlockedSetRelay` in `remote_list.go` (only its call sites and signature were confirmed via the tool output before the tool budget ran out), so I cannot 100% confirm there is no internal filtering inside that function itself; the call-site asymmetry (no `checkFunc` argument passed, unlike the V4/V6 calls) is strong but not fully conclusive evidence, and this should be verified by reading `remote_list.go`'s `unlockedSetRelay` definition directly.

### Impact Explanation
Cached relay entries are later consumed by `relayManager.StartRelays`, which iterates `hostinfo.remotes.relays` and, for each entry, either initiates a handshake to that address (`f.Handshake(relay)`) or sends a `CreateRelayRequest` control message asking a peer to relay traffic to/through the injected address: [6](#0-5) 

If relay addresses bypass `remote_allow_list` filtering, an attacker who is otherwise restricted from being used as a relay/remote (via `remote_allow_list`) can still get itself (or an arbitrary third-party address) recorded as a candidate relay for other hosts' tunnels, and have those hosts attempt to establish relayed tunnel/handshake traffic through it — a remote state-poisoning condition affecting hostmap/lighthouse trust that can facilitate traffic redirection through an attacker-chosen relay.

### Likelihood Explanation
Both `handleHostUpdateNotification` (reachable by any peer that has completed a handshake to a lighthouse) and `handleHostQueryReply` (reachable from any node acting as/behind a lighthouse reply) are on the normal, unauthenticated (beyond possessing a valid mesh certificate) lighthouse protocol path, so the missing validation is trivially reachable without a CA-signed relationship to the target beyond normal mesh membership.

### Recommendation
Pass the same allow-list validation used for `V4AddrPorts`/`V6AddrPorts` (`unlockedShouldAddV4`/`V6`-equivalent) into `RemoteList.unlockedSetRelay`/`unlockedSetRelay` call sites, filtering each reported relay address against `lighthouse.remote_allow_list` and the "not in my own vpn network" check before it is cached, mirroring the fix pattern used for `MixinParams.setParams` (enforce the same invariant at every mutation path, not only the "primary" one).

### Proof of Concept
Full exploitation would require running the e2e harness (e.g., extending `TestLighthouse_Memory`/`handleHostUpdateNotification` unit tests) to show that a peer blocked by `lighthouse.remote_allow_list` for direct addressing can still have its address accepted into another host's `RemoteList.relays` via a crafted `HostUpdateNotification`/`HostQueryReply` `NebulaMeta.Details.Relays` field — this was not runnable in this environment; verification of `unlockedSetRelay`'s internals in `remote_list.go` is recommended to confirm absence of filtering before treating this as fully proven.

func (lh *LightHouse) unlockedShouldAddV4(vpnAddr netip.Addr, to *V4AddrPort) bool {

	allow := lh.GetRemoteAllowList().Allow(vpnAddr, udpAddr.Addr())

		lh.l.Log(context.Background(), logging.LevelTrace, "remoteAllowList.Allow",
			"vpnAddr", vpnAddr,
			"udpAddr", udpAddr,
			"allow", allow,
		)
	}

	if !allow {
		return false
	}

	if lh.myVpnNetworksTable.Contains(udpAddr.Addr()) {
		return false
	}

	return true
}
