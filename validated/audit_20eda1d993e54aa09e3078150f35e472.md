### Title
`ValidateMultiSign`/`BatchValidateSign` precompiles build the signing hash without a domain separator or type tag, enabling cross-contract signature replay - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external report shows that omitting a `typeHash`/domain separator from an EIP‑712 style digest lets a signature crafted for one purpose be reinterpreted or replayed in another context. The analogous construction in java-tron is the `ValidateMultiSign` TVM precompile, which builds its signing hash purely from `(address, permissionId, data)` with no tag identifying the calling contract, function, or protocol purpose, and no hashing of the variable-length `data` field to bind it to a specific usage context.

### Finding Description
`ValidateMultiSign.execute()` builds the hash to be verified as: [1](#0-0) 

```java
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

This is a raw concatenation-and-hash scheme with **no domain separator** (no chain id, no calling/`verifyingContract` address, no “ValidateMultiSign” type tag) and **no structured/dynamic-type encoding** of `data` — exactly the two elements the external report identifies as missing from the vulnerable EIP‑712 `digest`. Any smart contract on TRON can invoke this precompile with an arbitrary, attacker-supplied `data` blob; the resulting hash depends only on the literal bytes of `address ‖ permissionId ‖ data`, never on which contract or which application logic is asking for the check.

Because the hash carries no binding to the invoking contract (the equivalent of EIP‑712’s `verifyingContract` in the domain separator) or to a specific message “type” (the equivalent of EIP‑712’s `typeHash`), a single ECDSA signature over `sha256(address ‖ permissionId ‖ data)` is valid input to **any** contract that calls `ValidateMultiSign` with that same triple, regardless of what business meaning that contract assigns to `data`. Contracts using this precompile as an authorization/permission-proof primitive (a documented use case of `ValidateMultiSign`, mirrored in `checkWeight`) can therefore be tricked into accepting a signature that the user believed was scoped to one dApp/action as proof of authorization for a completely different dApp/action, as long as the second contract is engineered (or coincidentally happens) to reconstruct the identical `(address, permissionId, data)` bytes, e.g. by echoing the public `data` payload that the first dApp already exposed on-chain or in its UI.

For comparison, real TRON transactions signed via `TransactionCapsule.sign`/`checkWeight` at least bind the signature to the fully unique `raw` transaction bytes (ref block, expiration, unique contract fields): [2](#0-1) 

`ValidateMultiSign`, by contrast, exposes this generic "sign an opaque blob for an address+permissionId" primitive directly to Solidity/TVM callers with no such context binding, which is the same class of gap the report calls out for the missing `typeHash`/`hashStruct(data)`.

### Impact Explanation
Any smart contract that relies on `ValidateMultiSign` as an on-chain authorization/permission proof (e.g., meta-transaction relayers, escrow/order contracts, delegated approval systems) can be fooled into treating a signature intended for a different application/context as valid authorization, resulting in unauthorized account/contract operations executed under an account's identity without genuine informed consent for that specific action. This matches "concrete unauthorized account operation" impact.

### Likelihood Explanation
`ValidateMultiSign` is a public precompile reachable from any deployed TVM contract via a plain `staticcall`/`call`, i.e., by any unprivileged transaction broadcaster or contract deployer, with fully attacker-controlled `data`. No special privilege, SR/witness role, or node compromise is required — only that a second, unrelated contract also uses this precompile and can be induced to reconstruct the same `(address, permissionId, data)` triple that was previously signed and made public by a legitimate dApp.

### Recommendation
Include a domain separator that binds the hash to the calling context — at minimum the calling contract address (`msg.sender`/`CALLER`), a chain identifier, and a purpose/type tag analogous to EIP-712's `typeHash` — before hashing `address`, `permissionId`, and `data` in `ValidateMultiSign.execute()`. Additionally, hash the dynamic `data` field on its own (e.g., `sha256(data)`) before combining it with the fixed-length fields, so its encoding cannot be conflated across different callers/purposes, mirroring the `hashStruct`/dynamic-type encoding required by EIP‑712.

### Proof of Concept
1. DApp A asks a user to sign `hash = sha256(userAddress ‖ permissionId ‖ data)` (e.g., as an off-chain "approve withdrawal of 10 TRX" proof) and later calls `ValidateMultiSign(userAddress, permissionId, data, [sig])` on-chain; `data` and the resulting call are publicly visible on-chain.
2. A malicious DApp B, unrelated to DApp A, is written to call the same precompile with the identical `(userAddress, permissionId, data)` triple it copies from DApp A's public transaction, but DApp B's own logic interprets a successful `ValidateMultiSign` result as authorization for a different, higher-value action (e.g., granting admin rights or approving a larger transfer) tied to that `permissionId`.
3. Because `ValidateMultiSign` only checks `recoverAddrBySign(sig, sha256(address‖permissionId‖data))` against the account's permission — see [3](#0-2)  — with no context distinguishing "signed for DApp A" from "signed for DApp B", the same signature the user gave to DApp A is accepted by DApp B, letting it execute unauthorized logic under the guise of a validated multisig approval.
