### Title
Unvalidated attachment content accepted without matching requested `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts a peer-supplied `Attachment` into `self.attachments` purely based on successful JSON decoding, never checking that `Attachment::hash()` equals the `content_hash` that was originally requested via `AttachmentRequest`. A malicious peer serving arbitrary garbage bytes at `GET /v2/attachments/{H}` gets accepted as long as the HTTP status is 200 and the body decodes as valid JSON.

### Finding Description
The broken equality: the code never asserts `response.attachment.hash() == request.content_hash`. In `AttachmentsBatchStateContext::extend_with_attachments` [1](#0-0) , for each `(request, response)` pair in `results.succeeded`, the code calls `response.decode_atlas_get_attachment()` and on success does `self.attachments.insert(response.attachment)` — `request.content_hash` is available (it's the key used to build `AttachmentRequest` in `get_prioritized_attachments_requests` [2](#0-1) ) but is discarded and never compared.

The HTTP decode path itself performs no hash check either: `StacksHttpResponse::decode_atlas_get_attachment` just JSON-parses the body into `GetAttachmentResponse` [3](#0-2) , and `GetAttachmentResponse`'s custom `Deserialize` impl simply hex-decodes whatever bytes are given into `Attachment::new(bytes)` with no validation against any expected hash [4](#0-3) .

Downstream, `AttachmentsDownloader::run` drains `context.attachments` and, for each attachment, looks up `find_all_attachment_instances(&attachment.hash())` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)`, keyed by the attacker-controlled content's own self-consistent hash — not by the `content_hash` that was originally committed on-chain via the BNS/Atlas contract event [5](#0-4) .

Exploit flow: attacker runs a peer, advertises (or is selected via existing inventory logic) as a source for `content_hash = H` in `get_prioritized_attachments_requests`, and when queried on `GET /v2/attachments/{H}`, replies with a 200 response containing arbitrary hex content `C` where `Hash160::from_data(C) != H`. The state machine's `BatchedRequestsState::PollRequests` only checks `status_code == 404` to mark faulty [6](#0-5) ; any 200 response is accepted into `succeeded` regardless of content correctness, and `extend_with_attachments` never rejects the mismatch.

### Impact Explanation
An attacker can get a node to store attacker-chosen content in the AtlasDB, keyed by that content's own hash (which was never actually requested/committed by any legitimate BNS/Atlas contract event for that instance). This is a High-severity "attachment/BNS mismatch" — the node serves and persists non-canonical/uncommitted data via `insert_instantiated_attachment`, and it will be served back to any RPC client hitting `GET /v2/attachments/{attacker_hash}`, and paired with `find_all_attachment_instances` only for instances that happen to track that same attacker-chosen hash (limiting blast radius to attachments that legitimately reference that hash — but the core defect remains that the fetched content is never validated against the specific `content_hash` it was fetched to satisfy).

### Likelihood Explanation
Requires: a queued `AttachmentInstance` with `content_hash == H` (created from any confirmed BNS/Atlas contract call), and the attacker's peer being selected as a source in `get_prioritized_attachments_requests` (which only requires the peer to advertise `H` as present in its inventory response — no privileged role, no secret, purely an outbound sync peer connection any remote node can establish). Attacker cost is a single crafted HTTP response per request; fully repeatable for every attachment fetch the node performs.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; treat a mismatch as a failed request (`report.bump_failed_requests()` and optionally mark the peer faulty), analogous to the existing 404 handling in `BatchedRequestsState::PollRequests`.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that:
1. Constructs an `AttachmentsBatchStateContext` with a single peer and an `AttachmentRequest { content_hash: H, .. }` where `H = Hash160([0x11; 20])`.
2. Builds a `BatchedRequestsResult` whose `succeeded` map has that request paired with a crafted `StacksHttpResponse` (via `StacksHttpResponse::new_error`/manual construction, or reusing `test_rpc` helpers from `stackslib/src/net/api/tests/getattachment.rs`) that decodes via `decode_atlas_get_attachment()` into `GetAttachmentResponse { attachment: Attachment::new(b"garbage".to_vec()) }`, where `Hash160::from_data(b"garbage") != H`.
3. Calls `context.extend_with_attachments(&mut results)`.
4. Asserts that `context.attachments` does NOT contain an attachment whose hash differs from `H` — currently this assertion fails, demonstrating that `self.attachments.insert(response.attachment)` at `stackslib/src/net/atlas/download.rs:548` accepts content regardless of hash mismatch with `request.content_hash`.
