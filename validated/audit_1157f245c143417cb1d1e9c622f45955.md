### Title
Unbounded in-memory read of attacker-controlled commit message causes memory-exhaustion DoS - (File: internal/git/catfile/commit.go)

### Summary
`GetCommitMessage` in `internal/git/catfile/commit.go` reads an entire commit object into memory via `io.ReadAll` with no size cap, unlike the sibling function `ParseCommit` which explicitly truncates message bodies to `helper.MaxCommitOrTagMessageSize`. This function backs the `GetCommitMessages` RPC, so a client can force Gitaly to buffer an attacker-sized commit message fully in memory, exactly mirroring the external report's bug class: an "external call" (here, invoking `git cat-file` and reading its output) can return far more data than the caller expects/budgets for, and that data is unconditionally copied into memory before any size check is applied.

### Finding Description
`GetCommit`/`ParseCommit` (`internal/git/catfile/parse_commit.go:198-233`) truncate the commit body to `helper.MaxCommitOrTagMessageSize` (10 KiB) before storing it: [1](#0-0) .

However `GetCommitMessage`, used specifically to fetch full/untruncated commit messages, calls `splitRawCommit`, which does an unconditional `io.ReadAll(object)` over the whole object stream with no upper bound: [2](#0-1) .

This function is invoked directly by the `GetCommitMessages` RPC handler for each commit ID supplied by the client, and the resulting message is streamed back to the client only after being fully read into memory: [3](#0-2) .

Since Git places no server-side hard limit on commit message size, and Gitaly accepts pushes/imports that create such commits, an ordinary user can create a repository containing one or more commits with extremely large commit messages (git itself allows messages many megabytes/gigabytes in size) and then invoke `GetCommitMessages` against that repository/commit ID. Gitaly will spawn `git cat-file`, read the *entire* object into a `[]byte` via `io.ReadAll`, and only after that completes begin streaming/chunking the response back to the caller. There is no size ceiling comparable to `MaxCommitOrTagMessageSize` applied here, so the "external call" (the `cat-file` subprocess and its returned object stream) can force gitaly to allocate memory proportional to attacker-chosen data, unconstrained by the deliberate truncation mechanism that exists elsewhere in the same package for exactly this class of value.

### Impact Explanation
Because `GetCommitMessage` deliberately opts out of the message-size cap that protects `GetCommit`/`ParseCommit`, repeated or concurrent calls to `GetCommitMessages` against commits with maliciously oversized messages can drive Gitaly process memory usage up sharply, degrading or crashing the `gitaly` process (and thus disrupting service to other repositories/tenants sharing the same node) — a resource-exhaustion/DoS impact reachable purely from RPC calls a normal authenticated Gitaly client can make (no privileged actor, no malicious peer, no leaked token required).

### Likelihood Explanation
Likelihood is moderate-to-high: creating a commit with a very large message requires only normal `git commit`/push access to a repository, and `GetCommitMessages` accepts an arbitrary list of `CommitIds`, allowing a single request to target multiple oversized messages or the same message repeatedly (bounded mainly by request size and Gitaly's general RPC limits, not by any commit-message-specific guard).

### Recommendation
Apply the same defensive bound used in `ParseCommit`: either enforce `helper.MaxCommitOrTagMessageSize` (or a documented "full message" limit) inside `splitRawCommit`/`GetCommitMessage` before allocating the result, or switch `GetCommitMessages` to stream the object body directly from the `cat-file` reader to the gRPC stream (chunk-by-chunk) rather than buffering the whole message with `io.ReadAll` first, avoiding the unnecessary full in-memory copy analogous to using a bounded/streaming pattern instead of the unrestrained `.call`/`ReadAll`-style full-copy.

### Proof of Concept
1. Create a repository and commit a message far larger than `helper.MaxCommitOrTagMessageSize` (e.g., tens/hundreds of MB), which git accepts without complaint.
2. Call the `GetCommitMessages` RPC with that commit's ID.
3. Observe that `GetCommitMessage` → `splitRawCommit` performs `io.ReadAll(object)` over the full object before any chunking/streaming occurs, causing a memory spike proportional to the attacker-chosen message size — repeat with many commit IDs or concurrent requests to amplify the effect and induce OOM/service degradation.

// GetCommitMessage looks up a commit message and returns it in its entirety.
func GetCommitMessage(ctx context.Context, objectReader ObjectContentReader, repo storage.Repository, revision git.Revision) ([]byte, error) {
	obj, err := objectReader.Object(ctx, revision+"^{commit}")
	if err != nil {
		return nil, err
	}

	_, body, err := splitRawCommit(obj)
	if err != nil {
		return nil, err
	}
	return body, nil
}

func splitRawCommit(object git.Object) ([]byte, []byte, error) {
	raw, err := io.ReadAll(object)
	if err != nil {
		return nil, nil, err
	}

	header, body, _ := bytes.Cut(raw, []byte("\n\n"))

	return header, body, nil
}

func (s *server) getAndStreamCommitMessages(request *gitalypb.GetCommitMessagesRequest, stream gitalypb.CommitService_GetCommitMessagesServer) error {
	ctx := stream.Context()
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectReader, cancel, err := s.catfileCache.ObjectReader(ctx, repo)
	if err != nil {
		return err
	}
	defer cancel()

	for _, commitID := range request.GetCommitIds() {
		msg, err := catfile.GetCommitMessage(ctx, objectReader, repo, git.Revision(commitID))
		if err != nil {
			return fmt.Errorf("failed to get commit message: %w", err)
		}
		msgReader := bytes.NewReader(msg)

		if err := stream.Send(&gitalypb.GetCommitMessagesResponse{CommitId: commitID}); err != nil {
			return err
		}
		sw := streamio.NewWriter(func(p []byte) error {
			return stream.Send(&gitalypb.GetCommitMessagesResponse{Message: p})
		})
		_, err = io.Copy(sw, msgReader)
		if err != nil {
			return fmt.Errorf("failed to send response: %w", err)
		}
	}
	return nil
}
