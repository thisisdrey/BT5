### Title
Postponed action receipts are never counted in `CongestionInfo.receipt_bytes`, hiding real state backlog from congestion signaling - ([File: runtime/runtime/src/lib.rs, congestion_control.rs])

### Summary
`Runtime::process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an action receipt as a postponed receipt (`PendingDataCount`, `PostponedReceiptId`, `set_postponed_receipt`) whenever any `input_data_ids` are unresolved, but never calls `CongestionInfo::add_receipt_bytes` for it, unlike the delayed queue (`DelayedReceiptQueueWrapper::push`, `congestion_control.rs:838-865`) and buffered receipts (`ReceiptSinkV2::buffer_receipt`, `congestion_control.rs:466-501`) which do. [1](#0-0) [2](#0-1) [3](#0-2)  This is a documented, intentional MVP limitation, not an accidental bug.

### Finding Description
`compute_receipt_congestion_gas` explicitly states the congestion-control MVP does not account for data receipts or postponed receipts because "looking that up would require reading the postponed receipt from the trie" [4](#0-3) . Correspondingly, `bootstrap_congestion_info`, which recomputes `receipt_bytes` from scratch, only iterates the `DelayedReceiptQueue` and `ShardsOutgoingReceiptBuffer` — it never scans `PostponedReceiptId`/`PendingDataCount`/postponed-receipt trie entries [5](#0-4) . An attacker's contract can call `promise_and` to create an action receipt with several `input_data_ids` that point to data receipts that will never (or very slowly) arrive, causing `process_action_receipt` to persist the receipt as postponed state (`lib.rs:1642-1655`) with zero contribution to `receipt_bytes`, `delayed_receipts_gas`, or `buffered_receipts_gas`. This can be repeated at volume to accumulate arbitrarily large borsh-serialized postponed-receipt payloads in the shard's trie while `CongestionInfo.memory_congestion` (and the other three congestion fractions) remain unaffected by this backlog, since none of the four congestion dimensions defined by `CongestionControl::congestion_level` (`core/primitives/src/congestion_info.rs:44`) look at postponed receipts.

However, the practical exploitability is bounded by other mechanisms not covered by this finding directly: postponed receipts are only created after the *sender's* receipt has already passed the normal delayed-queue/incoming admission checks and storage-staking is already charged to the receiving account for any state kept there (postponed receipts consume the receiver account's `storage_usage`, which requires the receiver to have sufficient balance locked for storage, per NEAR's standard storage staking model applied to `TrieKey::PostponedReceiptId`/`PendingDataCount`/postponed receipt entries). This means growth of postponed-receipt state is gated by ordinary account storage-staking economics rather than being genuinely free — an attacker must pay (or force the receiver to pay/be unable to pay, in which case account operations would fail) for the storage they occupy on the receiver account, same as any other trie state under that account. The described mechanism is a real gap in congestion-signal completeness by design, but it does not by itself demonstrate unbounded free storage growth, since the receiver's storage-staking balance requirement still limits how much postponed-receipt data can accumulate per account without failing due to insufficient locked balance.

### Impact Explanation
This is a **resource-accounting/signal-completeness gap** in NEP-539 congestion control, not a fund-loss, consensus-divergence, double-spend, authorization-escalation, or shard-halt bug. It matches, at most, a low-severity "congestion control incompleteness" / DoS-adjacent finding: the four congestion dimensions (incoming/outgoing/memory/missed-chunks) can under-report actual shard state growth from postponed receipts, but this growth is still constrained by the receiver account's storage-staking balance requirements, which is the standard NEAR mechanism that already limits unbounded state growth per account. It does not cause theft/freezing of funds, inflation, double-spend, escalation, state-root divergence, or a shard halt — it is a known, documented MVP scoping decision in `compute_receipt_congestion_gas` [4](#0-3) .

### Likelihood Explanation
An unprivileged attacker can trivially create postponed receipts via `promise_and` with never-resolving dependencies, at low cost (the cost of the cross-contract calls and storage staking on the receiving account). However, because the receiver's account storage-staking balance requirement still bounds how much postponed-receipt state can exist per account, the "unbounded" framing in the question is not fully substantiated by the code; the bound is per-account economic, not a congestion-control safety mechanism.

### Recommendation
No plan is warranted since this reflects a documented, intentional design limitation (comment at `congestion_control.rs:685-695`) rather than a security vulnerability. If desired, protocol authors could extend congestion accounting to include postponed/promise-yield receipt bytes (would require a protocol version bump given `CongestionInfoV1`'s consensus-critical semantics), but this is a protocol design/roadmap item, not a discrete exploitable bug fix.

### Proof of Concept
Not applicable as a security PoC — the behavior is reachable and reproducible (submit postponed receipts via `promise_and` and observe `own_congestion_info.receipt_bytes()` unaffected while `PostponedReceiptId`/`PendingDataCount` trie entries grow, similar in spirit to `test_congestion_delayed_receipts_accounting` in `runtime/runtime/src/tests/apply.rs:3287-3327` but for postponed receipts instead of delayed ones), but it does not demonstrate a concrete loss/freezing of funds, consensus divergence, or shard halt required by the validation rules, and growth is still gated by receiver-side storage staking.

pub fn bootstrap_congestion_info(
    trie: &dyn near_store::TrieAccess,
    config: &RuntimeConfig,
    shard_id: ShardId,
) -> Result<CongestionInfo, StorageError> {
    let mut receipt_bytes: u64 = 0;
    let mut delayed_receipts_gas: u128 = 0;
    let mut buffered_receipts_gas: u128 = 0;

    let delayed_receipt_queue = &DelayedReceiptQueue::load(trie)?;
    for receipt_result in delayed_receipt_queue.iter(trie, true) {
        let receipt = receipt_result?;
        let gas =
            receipt_congestion_gas(&receipt, config).map_err(int_overflow_to_storage_err)?.as_gas();
        delayed_receipts_gas = safe_add_gas_to_u128(delayed_receipts_gas, Gas::from_gas(gas))
            .map_err(int_overflow_to_storage_err)?;

        let memory = receipt_size(&receipt).map_err(int_overflow_to_storage_err)? as u64;
        receipt_bytes = receipt_bytes.checked_add(memory).ok_or_else(overflow_storage_err)?;
    }

    let mut outgoing_buffers = ShardsOutgoingReceiptBuffer::load(trie)?;
    for shard in outgoing_buffers.shards() {
        for receipt_result in outgoing_buffers.to_shard(shard).iter(trie, true) {
            let receipt = receipt_result?;
            let gas = receipt_congestion_gas(&receipt, config)
                .map_err(int_overflow_to_storage_err)?
                .as_gas();
            buffered_receipts_gas = safe_add_gas_to_u128(buffered_receipts_gas, Gas::from_gas(gas))
                .map_err(int_overflow_to_storage_err)?;
            let memory = receipt_size(&receipt).map_err(int_overflow_to_storage_err)? as u64;
            receipt_bytes = receipt_bytes.checked_add(memory).ok_or_else(overflow_storage_err)?;
        }
    }

    Ok(CongestionInfo::V1(CongestionInfoV1 {
        delayed_receipts_gas: delayed_receipts_gas as u128,
        buffered_receipts_gas: buffered_receipts_gas as u128,
        receipt_bytes,
        // For the first chunk, set this to the own id.
        // This allows bootstrapping without knowing all other shards.
        // It is also irrelevant, since the bootstrapped value is only used at
        // the start of applying a chunk on this shard. Other shards will only
        // see and act on the first congestion info after that.
        allowed_shard: shard_id.into(),
    }))
}
