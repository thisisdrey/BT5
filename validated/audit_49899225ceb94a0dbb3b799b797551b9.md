### Title
Global buffer over-read in `InputZipFile::ProcessCentralDirEntry` while parsing attacker-supplied ZIP/JAR central directory - (File: third_party/ijar/zip.cc)

### Summary
`ijar`'s ZIP central-directory parser trusts length fields taken directly from the input file (`file_name_length`, `extra_field_length`, `file_comment_length`, and per-extra-field `data_size`) and uses them to `memcpy` and advance the read cursor without ever checking them against the size of the mapped input buffer, unlike the sibling local-file-header parser in the same file which does call `EnsureRemaining()`.

### Finding Description
`InputZipFile::ProcessCentralDirEntry` reads the four size fields straight out of the mmap'd central directory record and immediately uses them: [1](#0-0) 

- `file_name_length` is used to `memcpy` bytes starting at `p` into a fixed `filename[PATH_MAX]` buffer (bounded on the destination side, but the *source* read via `memcpy(filename, p, len)` is never checked against how many bytes actually remain in the mapped input file).
- `p += file_name_length`, `p += extra_field_length`, and later `p += file_comment_length` can walk `p` arbitrarily far past the end of the mapped region.
- The subsequent extra-field loop reads `header_id`/`data_size` from `extra_p` and, for a `ZIP64_EXTRA_FIELD_TAG`, unconditionally calls `get_u8le(extra)` — reading 8 bytes from `extra` even when the field's own declared `data_size` is smaller — with no check that 8 bytes are actually available before the boundary of the extra-field block or the file itself: [2](#0-1) 

By contrast, `ProcessLocalFileEntry` in the very same file validates every variable-length read with `EnsureRemaining()` before touching the data: [3](#0-2) [4](#0-3) 

`ProcessCentralDirEntry` has no equivalent call anywhere in its body. The function is invoked both from `InputZipFile::ProcessNext()` (used by singlejar/ijar's main extraction loop) and from `CalculateOutputLength()` while walking the whole central directory: [5](#0-4) [6](#0-5) 

Since `ijar` operates on a `mmap`'d file (`MappedInputFile`), reading past the end of that mapping is a genuine out-of-bounds/global-buffer-overflow style read (can hit an unmapped page and crash, or read adjacent heap/mapping memory into `filename`/decoded sizes) — the same bug class as the reported libelfin `dwarf::line_table::line_table` issue: a length field taken from untrusted, attacker-controlled binary data is used to index/copy without validating it against the buffer's actual bounds.

### Impact Explanation
`ijar` is invoked by Bazel's Java toolchain to build interface jars, and singlejar-family tools built on the same header definitions process third-party JARs that arrive as build dependencies (e.g., via `http_jar`/`http_archive`/`java_import`). An attacker who controls the contents of such a JAR (which is exactly the "hostile origin server publishes a jar the victim's build consumes" scenario) can craft a central directory entry with an oversized `file_name_length`, `extra_field_length`, or a truncated ZIP64 extra field to make `ProcessCentralDirEntry` read past the end of the mapped file. Because the checksum/`sha256`/`integrity` attribute on `http_jar`/`http_archive` only verifies that the downloaded bytes match what the attacker published — it does nothing to validate internal structural invariants of the ZIP format — a fully "integrity-verified" malicious jar still reaches this vulnerable parser unchanged. The result is a crash (denial of service of the build) or, in the worst case, disclosure of adjacent memory into build-visible metadata (filenames/sizes used further downstream). No arbitrary code execution vector was found.

### Likelihood Explanation
Likelihood is moderate. Any build that consumes a third-party or CI-served JAR through `ijar`/interface-jar generation exercises this code path automatically, with no special flags required and no interaction from the victim beyond a normal `bazel build`. The attacker only needs to control (or compromise) one dependency's binary artifact — no MITM or credential compromise is required, since `ijar` will happily process a validly-hashed, structurally-malformed ZIP.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the number of bytes actually remaining in the mapped file before advancing `p`/`memcpy`-ing, and validate each extra-field's `data_size` (and the 8-byte ZIP64 payload read) against the bounds of the extra-field block before dereferencing.

### Proof of Concept
Not fully verified/reproduced in this pass — I traced the missing-bounds-check logic statically (comparing `ProcessCentralDirEntry` against the bounds-checked `ProcessLocalFileEntry` and `EnsureRemaining`) but did not have the ability to execute a JUnit/`src/test/shell/bazel` test to confirm an actual out-of-bounds read/crash at runtime in this session. A concrete PoC would build a minimal ZIP file whose central directory record declares `file_name_length`/`extra_field_length`/`file_comment_length` (or a ZIP64 extra field `data_size`) larger than the bytes remaining in the file, feed it to `ijar` (or a unit test directly instantiating `InputZipFile` and calling `ProcessCentralDirEntry`/`ProcessNext`), and run under ASan to confirm a heap-buffer-overflow/out-of-bounds read is reported — analogous to the existing `CreateZipWithMalformedExtraField` regression test in `src/tools/singlejar/output_jar_simple_test.cc` [7](#0-6) , which shows the singlejar code path was hardened against malformed extra fields but the equivalent hardening was not confirmed present in `third_party/ijar/zip.cc`'s `ProcessCentralDirEntry`.

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
