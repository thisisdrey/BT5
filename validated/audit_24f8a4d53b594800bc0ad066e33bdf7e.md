### Title
Missing staleness/deviation check on the stSTX liquid-staking ratio used in oracle price resolution enables collateral mispricing - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
The `resolve-ststx` callcode transform, which converts the STX price into a stSTX (Liquid Staking Token) price by multiplying it by an external exchange ratio, fetches that ratio with no staleness check and no deviation/sanity check, unlike every other price input in the same oracle pipeline.

### Finding Description
`stSTX` is a Liquid Staking Token that accrues value relative to STX over time and is not pegged 1:1 — the same class of asset discussed in the referenced report (wstETH vs. ETH). Its price is computed as `STX price * stSTX/STX ratio`, where the ratio is fetched from an external contract via `call-ststx-ratio` and applied in `resolve-ststx`: [1](#0-0) 

This ratio feeds directly into `resolve-callcode` (used for both the `stSTX` collateral price and the `zstSTX` vault-share price via the nested `CALLCODE-ZSTSTX` branch): [2](#0-1) 

Compare this to how the base Pyth/DIA feeds are treated in `price-resolve`: those go through an explicit legality check and a per-asset `max-staleness`/monotonicity check (`oracle-price-legal`, `oracle-timestamp-fresh`) before being trusted, and Pyth additionally enforces a confidence-interval bound (`check-confidence`): [3](#0-2) [4](#0-3) 

The `resolve-ststx` output, however, bypasses all of this — the ratio is applied as a raw multiplier with no timestamp attached, no staleness threshold, and no bound on how far it can move between blocks. There is also no cross-check against an independent market price for stSTX (analogous to "Solution 1" in the report) and no bound on the expected annual growth rate of the ratio (analogous to "Solution 2"/AAVE's `maxRatio` approach). The same unguarded pattern appears identically in `local-testing/contracts/market/market.clar` and is consumed for collateral/debt USD valuation in `mainnet/contracts/utility/v0-1-data.clar`'s `get-asset-price`: [5](#0-4) [6](#0-5) 

If the ratio oracle (`block-info-nakamoto-ststx-ratio-v2`) lags behind the true, on-chain-observable value of stSTX relative to STX — e.g., after a stacking-rewards/slashing-style event or any update delay in that external contract — the on-chain price used by the market for health checks, borrowing, and liquidation will diverge from reality with no automatic circuit breaker. An ordinary principal can, in a single transaction/block, exploit the stale ratio: deposit stSTX/zstSTX collateral (or repay/redeem) while the ratio is artificially high relative to true value, borrow the maximum allowed against it, and walk away with more value than the collateral is actually worth, leaving the protocol with under-collateralized debt.

### Impact Explanation
This lands squarely on the Critical impact class: it enables an ordinary user to extract more assets from the market than their real collateral value backs, directly draining other users'/the protocol's funds and creating protocol insolvency/bad debt, exactly mirroring the loss-of-assets scenario in the reference report.

### Likelihood Explanation
Exploitation requires a real divergence between the external ratio oracle's reported stSTX/STX ratio and the "true"/expected value (e.g., due to update latency, a stacking event, or a bug/lag in the ratio-provider contract) — this is an external pre-condition outside the attacker's control, similar to the Lido reporting-delay scenario in the source report. However, once such a divergence exists, exploitation is a simple, permissionless, single-transaction borrow/redeem — there is no on-chain mechanism (deviation cap, staleness check, or pause) to stop it, unlike the protection already applied to the raw Pyth/DIA feeds.

### Recommendation
Apply the same defense-in-depth already used for Pyth/DIA feeds to the stSTX ratio: (1) require the ratio provider to return a timestamp and enforce a staleness bound via `oracle-timestamp-fresh`-style logic before use in `resolve-ststx`; and (2) bound the ratio's per-block/per-period growth (e.g., cap it against an expected annual staking-yield growth rate, analogous to AAVE's `maxRatio` pattern) or cross-check it against an independent market price feed for stSTX, reverting/capping when the deviation exceeds a configured threshold.

### Proof of Concept
Not executable from static review — an on-chain PoC would require reproducing a real lag between `block-info-nakamoto-ststx-ratio-v2`'s reported ratio and the true stSTX/STX value, then calling the market's deposit/borrow entrypoints (which invoke `resolve-ststx`/`resolve-callcode` via `price-resolve`) to demonstrate over-borrowing against the stale price. Given the current index does not include the external ratio provider contract's implementation, actual divergence behavior of that dependency could not be independently confirmed in this review.

(define-private (oracle-price-legal (p uint))
  (> p u0))

(define-private (oracle-timestamp-fresh (ts uint) (prev uint) (max-staleness uint))
  (let ((delta (if (> ts stacks-block-time)
                   u0
                   (- stacks-block-time ts))))
    (and
      (<= delta max-staleness)
      (>= ts prev))))

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data

    (if (> timestamp last-update-time)
