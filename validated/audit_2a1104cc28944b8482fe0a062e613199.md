### Title
`write-freq` StackerDB rate-limit is never enforced on the chunk-write path, allowing unauthenticated write-frequency-limit bypass - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
The `write-freq` field returned by a StackerDB's controlling smart contract (`stackerdb-get-config`) is documented and consumed as a wall-clock rate limit governing how often a slot owner may write a chunk. In practice this limit is enforced only as a client-side heuristic used to decide whether to *fetch* a chunk during sync, and is never checked on the write-acceptance path (`try_replace_chunk` / `insert_chunk`), which is reachable directly and unauthenticated-except-for-signature via the public `POST /v2/stackerdb/{principal}/{contract_name}/chunks` RPC endpoint. This is directly analogous to the reported `block.timestamp`-as-deadline bug: a protective time-based check exists conceptually, but the actual enforcement point does not perform it, so the "protection" is illusory and can be trivially bypassed by any legitimate slot owner.

### Finding Description
`StackerDBConfig::write_freq` is loaded from the contract and is meant to bound how frequently a given slot can be rewritten (`stackslib/src/net/stackerdb/config.rs:422-437`, `496-503`).

The only place this value is checked is in the *sync scheduler*, which uses it purely to decide whether the local node should bother requesting a chunk from a peer: [1](#0-0) 

The comment in `validate_received_chunk` explicitly states the write-frequency is not checked there either, "since the caller has different ways of doing this": [2](#0-1) 

The actual chunk-acceptance path — `StackerDBTx::try_replace_chunk`, which is called directly by the HTTP write handler — validates chunk size, signer, staleness (`slot_version <= stored version`), and `max_writes`, but performs **no `write_freq`/wall-clock check at all**: [3](#0-2) 

`insert_chunk` merely records the current time in `write_time` for bookkeeping — it does not gate the write on it: [4](#0-3) 

The public HTTP endpoint that ultimately drives this insert path is `RPCPostStackerDBChunkRequestHandler::try_handle_request`, which calls `tx.try_replace_chunk(...)` directly with no additional frequency check, and on success immediately relays the chunk to the whole network via `set_relay_message(StacksMessageType::StackerDBPushChunk(...))`: [5](#0-4) [6](#0-5) 

So any principal that legitimately owns one or more slots in a StackerDB (e.g. a signer set contract with `write-freq` intentionally configured to throttle writes, such as once per reward cycle) can submit a new, validly-signed chunk with an incremented `slot_version` as fast as the network will accept HTTP requests, up to `max_writes`. The `write-freq` control that the contract author configured to bound this behavior is never enforced at the node's write-acceptance boundary — it only affects whether *other* nodes eagerly re-fetch it during their own sync scheduling, which does not stop the writer or the automatic push-relay from happening for every accepted write.

### Impact Explanation
This breaks the equality "configured write-freq limit == enforced limit," the same class of bug as the reported swap-deadline issue (a declared time-based protection that is not actually checked at the enforcement point). Concretely, a legitimate slot owner can:
1. Write and push a new chunk on every allowed `slot_version` increment as fast as HTTP round trips allow, ignoring `write-freq` entirely, up to `max_writes` for the slot.
2. Each accepted write is relayed via `StackerDBPushChunk` to the entire peer network (`poststackerdbchunk.rs:315-324`), producing repeated compute/DB work (`sql_tx` chunk replace, hash/signature verification, JSON encode/decode) and repeated inbound message load on every peer that replicates this contract.

This is a bounded-per-write but repeatable compute/bandwidth amplification vector driven by a small trust boundary (owning any slot in a StackerDB whose creator intended a throttling policy), which matches "High – bounded compute DoS on a read/write endpoint" in the rules. It is not a full unauthenticated write (a valid slot signature is still required), but it defeats a specific declared protection mechanism (`write-freq`) that operators/contract authors rely on to bound StackerDB write/relay volume.

### Likelihood Explanation
High for any StackerDB contract that sets a nonzero `write-freq` expecting it to be enforced by the node. No special network position or timing manipulation (unlike PoS block-withholding in the original report) is required — a slot owner simply issues repeated signed POST requests. The only prerequisite is holding a valid slot-signer private key, which is the normal, expected capability of a StackerDB participant (e.g., a signer in the signer-set contract), not a privileged/admin credential.

### Recommendation
Enforce `write_freq` inside `StackerDBTx::try_replace_chunk` (or `insert_chunk`) by comparing the stored `write_time` for the slot against `get_epoch_time_secs()` and rejecting the write (returning the existing `Error::TooFrequentSlotWrites` variant, which is currently defined but never constructed/used outside of `mod.rs`'s `Display` impl) before performing the update. This ensures the configured rate limit is enforced at the actual write-acceptance boundary rather than only being advisory to sync-scheduling logic on other nodes.

### Proof of Concept
1. Deploy or use a StackerDB contract with `write-freq` set to a large value (e.g., one reward cycle) and `max-writes` set high enough to allow many increments.
2. As a valid slot signer, repeatedly call `POST /v2/stackerdb/{principal}/{contract_name}/chunks` with `slot_version` incremented and a fresh valid signature on each call, back-to-back with no delay.
3. Observe that `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs:400-438`) accepts every write immediately (no `TooFrequentSlotWrites` error is ever returned) as long as `slot_version` increases and stays `<= max_writes`, and that each accepted write triggers a `StackerDBPushChunk` relay (`stackslib/src/net/api/poststackerdbchunk.rs:315-324`) to the network, despite the contract's configured `write-freq` intending to throttle this to one write per interval.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
}
