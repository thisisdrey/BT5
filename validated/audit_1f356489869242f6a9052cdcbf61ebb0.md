### Title
Legacy floating-point Bancor-style exchange math permanently corrupts TRC10 exchange pool reserves - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The default (non-hardened) TRC10 Exchange arithmetic path in `ExchangeProcessor` uses IEEE-754 `double` math and truncating `(long)` casts to compute a Bancor-formula token swap, exactly the class of rounding/precision bug that caused the YAM rebase incident (an internal accounting value drifting from truth via imprecise math, with no correction before the drifted value is committed to persistent state). Any unprivileged account that submits `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transactions drives this code path and permanently mutates the on-chain pool reserves (`firstTokenBalance`/`secondTokenBalance`) stored in `ExchangeCapsule`.

### Finding Description
`ExchangeCapsule.transaction()` selects between two arithmetic engines based on the `allowHardenExchangeCalculation` dynamic property: the hardened `SafeExchangeProcessor` (BigDecimal-based) or the legacy `ExchangeProcessor` (double-based): [1](#0-0) 

The legacy `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` perform the AMM relay-supply computation entirely in `double` precision, then truncate to `long` via a bare cast (which is not equivalent to floor/round and silently discards fractional precision), and accumulate the result back into the mutable `supply` field across the two-leg computation: [2](#0-1) 

This is structurally the same bug class as the YAM incident: an internal supply/accounting value (`supply`, and by extension `firstTokenBalance`/`secondTokenBalance`) is derived from an imprecise calculation, and the erroneous value is written directly into the persisted `ExchangeCapsule`/store without any independent correctness check in the legacy path (unlike the hardened path, which cross-checks results against a BigDecimal-computed remainder in `ExchangeWithdrawActuator.doValidate()`): [3](#0-2) 

In the legacy/default path, no equivalent precision check exists for `ExchangeTransactionActuator` or `ExchangeInjectActuator`, so a caller can freely trigger transactions whose double-precision rounding error is written straight into `newFirstTokenBalance`/`newSecondTokenBalance` and persisted via `Commons.putExchangeCapsule`: [4](#0-3) 

Because every subsequent trade recomputes its result from whatever `firstTokenBalance`/`secondTokenBalance` currently sit in the store, repeated small/adversarially-chosen trades (analogous to repeated "rebase" calls in YAM) compound the double-precision drift into the persisted reserve balances over time, and — just like YAM's `totalSupply` mistake becoming irreparable once the next rebase executes — each subsequent legacy-path trade builds directly on top of the already-corrupted reserve values with no mechanism to detect or roll back the accumulated error.

### Impact Explanation
An attacker who repeatedly calls `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` against a TRC10 Bancor-style exchange pool while `allowHardenExchangeCalculation` is not enabled can, over many transactions, skew the pool's `firstTokenBalance`/`secondTokenBalance` away from the values a precise implementation would produce. Because these balances back real TRX/TRC10 asset custody for other users' liquidity, sustained exploitation can result in unbacked balances or an extractable value gap between what the pool believes it holds and what it can actually pay out — a direct funds-theft/permanent-corruption impact analogous to YAM's frozen $750K in governance/Curve tokens.

### Likelihood Explanation
The vulnerable path is the *default* arithmetic engine — the hardened, precision-checked path only activates when the `allowHardenExchangeCalculation` committee proposal parameter is turned on (a chain-governance toggle, not something end users control), so absent that specific flag being active, every exchange transaction from any account runs through the double-precision `ExchangeProcessor`. No special privilege is needed to submit these contracts, only a small trade fee, making this reachable by any transaction broadcaster.

### Recommendation
Ensure the BigDecimal/`SafeExchangeProcessor` hardened path is the mandatory arithmetic engine for all exchange contract types (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) rather than a governance-gated opt-in, or add the same precision/remainder verification used in `ExchangeWithdrawActuator.doValidate()` to `ExchangeTransactionActuator` and `ExchangeInjectActuator` so any double-precision-derived result that deviates from the exact BigDecimal expectation is rejected before being persisted.

### Proof of Concept
1. On a chain where `allowHardenExchangeCalculation == 0` (default legacy path, confirmed by `ManagerTest.isExchangeTransactionBypassedWhenHardenedEnabled` which shows hardened mode must be explicitly enabled), create/participate in a TRC10 Exchange pool via `ExchangeCreateActuator`.
2. Submit repeated `ExchangeTransactionContract` broadcasts with quant values chosen to maximize double-precision rounding error in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` (e.g., ratios producing non-terminating binary fractions).
3. After each transaction, `ExchangeCapsule.transaction()` persists `newFirstTokenBalance`/`newSecondTokenBalance` computed from the drifted `double` result with no BigDecimal cross-check, as seen in the executor path. [5](#0-4) 
4. Repeat over many transactions/blocks; observe the pool's persisted reserve ratio diverge from the exact BigDecimal-computed ratio (as already demonstrated by the test comment "Allow ±1 difference due to BigDecimal vs double precision" per-transaction, which compounds over N transactions), permanently corrupting the exchange's backing reserves.   private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }
