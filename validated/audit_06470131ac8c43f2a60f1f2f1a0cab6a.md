The premise underlying this question misunderstands NEAR's execution model, and the code does not exhibit the claimed vulnerability.

**Binding to verify:** sum of `token_balances` deltas for token X across all receipts stemming from one deposit == deposited amount, exactly once.

**What actually happens:** `ft_on_transfer` (contracts/defuse/src/contract/tokens/nep141/deposit.rs:19-78) calls `self.deposit(...)` synchronously, then if `DepositAction::Execute{refund_if_fails: true}` is present, calls `self.execute_intents(execute.execute_intents)` [1](#0-0) . This is a **plain synchronous Rust function call on `&mut self`**, not a new NEAR receipt, not a cross-contract call, and not a promise. `execute_intents` itself constructs `Engine::new(self, ExecuteInspector::default())`, runs `execute_signed_intents`, and calls `.unwrap_or_else(|e| e.panic())` — all within the same function-call stack, same receipt, same WASM execution [2](#0-1) . Control does not return to the NEAR runtime and no other receipt can execute until this entire call chain (including the nested engine's `finalize` and nonce commit) completes and the outer `ft_on_transfer` function itself returns.

The exploit's core assumption — "any code path allows a third, concurrent NEAR receipt to also call `execute_intents` referencing X in the window between deposit and nested engine's nonce commit" — is not possible. NEAR contract execution is single-threaded per contract: receipts to the same contract are processed strictly sequentially, never interleaved. There is no "window" during the execution of one receipt (or one function call within that receipt) in which another receipt's `execute_intents` call can read or write intermediate/uncommitted state of `self`. The nested `self.execute_intents` call is fully synchronous Rust code — it is not asynchronous, not re-entrant in the NEAR promise/callback sense, and there is no yield point at which the runtime could schedule another receipt.

Because both the outer `deposit()` and the nested `execute_intents()` mutate the *same* in-memory `self` sequentially within one atomic execution, and because no other receipt can interleave with this execution, the deposited balance for token X is credited exactly once (by `self.deposit`) and then consumed at most according to whatever the nested `MultiPayload` actually authorizes against that already-updated balance — same as any ordinary two-step balance update within a single function. There is no double-authorization of the same delta.

No vulnerability found for this question.

        if let Some(event) = Engine::new(self, ExecuteInspector::default())
            .execute_signed_intents(signed)
            .unwrap_or_else(|e| e.panic())
            .as_mt_event()
        {
            // NOTE: Not all `mt_transfer` events are refundable, but it's safe to check them
            // all at once since non-refundable transfers only increase the potential refund
            // log size without affecting correctness. This can actually prevent resolve transfer
            // from failing due to too long event log !!!
            event
                .check_refund()
                .unwrap_or_else(|err| err.panic())
                .emit();
        }
    }
