## Title
Pre-funded pool account lets an attacker DoS/skew first `add_liquidity` in `pallet-asset-conversion` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`do_add_liquidity` computes the pool's "reserves" directly from the live asset balances of the deterministic pool account (`Self::get_balance`) rather than from any pool-tracked reserve/price state, exactly mirroring the pattern in the external report where `sqrtPriceX96`/expected LP mint is derived from the contract's raw token balance instead of a canonical pool price. Because the pool account address is a pure hash of the asset pair (`AccountIdConverter`/`AccountIdConverterNoSeed`, computable by anyone before the pool even exists), an unprivileged attacker can pre-fund that address with a small, disproportionate amount of one or both assets before the real liquidity provider's first `add_liquidity` call. This skews the reserve ratio used to compute `amount2_optimal`/`amount1_optimal`, causing the legitimate provider's call to revert (`AssetTwoDepositDidNotMeetMinimum`/`OptimalAmountLessThanDesired`/`AssetOneDepositDidNotMeetMinimum`) even though `total_supply` of LP tokens is still zero (i.e., no genuine liquidity has been provided yet). ### Finding Description
`do_add_liquidity` reads `reserve1`/`reserve2` via `Self::get_balance(&pool_account, asset)`, which is simply `T::Assets::balance(asset, owner)` — the pool account's raw balance, not a value tracked and updated exclusively through pallet extrinsics: [3](#0-2) [4](#0-3) 

The `pool_account` address is fully deterministic and predictable before the pool is created — it is `blake2_256(pallet_id, pool_id)` decoded into an `AccountId`, with no dependency on whether `Pools::<T>` actually contains the pool: [5](#0-4) 

`do_create_pool` only touches the account for `asset1`/`asset2` (to allow it to hold balances) — it never checks or resets any pre-existing balance at that address: [6](#0-5) 

Consequently, an attacker can transfer a small amount of `asset1` and/or `asset2` directly to the (soon-to-be) pool account — either before `create_pool` is even called, or after creation but before the intended first `add_liquidity` — using ordinary `Assets::transfer`/`Balances::transfer`. When the legitimate first liquidity provider then calls `add_liquidity`, `do_add_liquidity` sees `reserve1`/`reserve2` as non-zero (because of the attacker's donation) even though `PoolAssets::total_issuance(lp_token)` is still zero (no LP tokens minted). The code branches into the "existing pool" path (`Self::quote`) instead of the "empty pool" path, computing an `amount2_optimal`/`amount1_optimal` skewed by the attacker's donated ratio: [7](#0-6) 

If the attacker donates an extreme ratio (e.g., 1 unit of asset1 alongside a large amount of asset2, or vice versa — analogous to the 2-wei WETH swap in the report), the computed optimal amount for the counter-asset will fall far outside the caller's `amount1_min`/`amount2_min`/`amount1_desired`/`amount2_desired` bounds, causing the transaction to revert with `AssetTwoDepositDidNotMeetMinimum`, `OptimalAmountLessThanDesired`, or `AssetOneDepositDidNotMeetMinimum`. Since the LP-token total supply is still zero and no `Pools`/`total_supply`-derived guard distinguishes "genuinely funded pool" from "pool account merely holding donated dust", the invariant that the *first* liquidity provider gets to set the initial price 1:1 with their own desired amounts (as intended by the `if reserve1.is_zero() || reserve2.is_zero()` branch) is broken by an attacker with no privileged position, no need to run a node/validator/relayer, and no admin/governance action — a pure unprivileged donation.

### Impact Explanation
This is a public, permissionless griefing/DoS vector against pool bootstrapping in `pallet-asset-conversion`, which is deployed on Asset Hub / system parachains for token swaps. An attacker can repeatedly block the legitimate creation of a healthy-ratio pool for any asset pair by pre-donating dust to the deterministic pool account, forcing subsequent `add_liquidity` calls to fail their min-amount checks, or forcing them to accept an attacker-skewed ratio if the caller's slippage tolerance (`amount1_min`/`amount2_min`) happens to be loose. This does not steal funds outright, but degrades the availability/intended behavior of a runtime pallet's public dispatchable, aligning with the "runtime bugs that compromise intended behavior" and "public underpriced work that degrades... processing" categories, at Medium impact consistent with the source report.

### Likelihood Explanation
Likelihood is Medium: the attack requires only a permissionless asset transfer to a computable address (no special asset creation restrictions if the assets are already `sufficient` or the attacker holds them), and it can be executed proactively (front-running is not even required if it's done before the pool exists at all). It is cheap (dust amounts, similar to the 2-wei PoC) and repeatable for any new pool, though its blast radius is limited to pools not yet meaningfully funded (`total_supply == 0`), which somewhat limits ongoing/established pools from being affected.

### Recommendation
Do not derive first-liquidity/reserve-ratio decisions from raw pool-account balances that can be pre-funded by third parties. Instead:
- Track pool reserves explicitly in pallet storage (updated only through `do_add_liquidity`/`do_remove_liquidity`/swap paths) rather than reading `T::Assets::balance` directly, or
- Gate the "empty pool" branch on `total_supply == 0` (LP-token issuance) rather than on `reserve.is_zero()`, and when `total_supply == 0`, ignore any pre-existing dust balance by crediting it to the first minter (sweep the excess into the new LP position) instead of using it to compute misleading `quote()` ratios.
- Alternatively, reject/sweep unexpected balances found in the pool account during `do_create_pool`/the first `add_liquidity` call so they cannot influence quoting decisions before genuine liquidity is provided.

### Proof of Concept
1. Attacker computes the pool account for `(asset1, asset2)` using the same `AccountIdConverter`/`AccountIdConverterNoSeed` logic used by the pallet (public, deterministic) before `create_pool` is even called. [5](#0-4) 
2. Attacker transfers a tiny, disproportionate amount of `asset1` (or `asset2`) directly to that address via `Assets::transfer`/`Balances::transfer_keep_alive` (works even pre-`create_pool`, or immediately after `create_pool` but before the legitimate `add_liquidity`).
3. Legitimate user calls `create_pool` (if not already done) then `add_liquidity(asset1, asset2, amount1_desired, amount2_desired, amount1_min, amount2_min, mint_to)` with a fair market ratio.
4. Inside `do_add_liquidity`, `reserve1`/`reserve2` reflect the attacker's donated dust, so the branch at [8](#0-7) 
computes `amount2_optimal`/`amount1_optimal` skewed to the attacker's chosen ratio, which fails the `amount2_min`/`amount1_min`/`amount1_desired` checks and the extrinsic reverts with `Error::AssetTwoDepositDidNotMeetMinimum` (or the analogous error), even though no real liquidity (`total_supply == 0`) has ever been added — reproducing the report's "attacker spends dust to DoS pool initialization" primitive locally.

pub struct AccountIdConverter<Seed, PoolId>(PhantomData<(Seed, PoolId)>);
impl<Seed, PoolId, AccountId> TryConvert<&PoolId, AccountId> for AccountIdConverter<Seed, PoolId>
where
	PoolId: Encode,
	AccountId: Decode,
	Seed: Get<PalletId>,
{
	fn try_convert(id: &PoolId) -> Result<AccountId, &PoolId> {
		sp_io::hashing::blake2_256(&Encode::encode(&(Seed::get(), id))[..])
			.using_encoded(|e| Decode::decode(&mut TrailingZeroInput::new(e)).map_err(|_| id))
	}
}
