## Title
Underpriced ModExp precompile energy cost enables CPU-time DoS via crafted base/exponent/modulus (pre-Osaka fork) - (`actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
Java-tron's `ModExp` precompiled contract (TVM address `0x05`) computes energy cost using the same EIP-198-style `getMultComplexity`/`getAdjustedExponentLength` formula that Besu used when EL-2022-15 was reported, and only recently gained a stricter cost model (TIP-7883) and hard length cap (`UPPER_BOUND = 1024`), both gated behind `VMConfig.allowTvmOsaka()`. [1](#0-0)  Until that hard fork is active on a given chain/network, the legacy formula is used unmodified, reproducing the exact underpricing bug class described in EL-2022-15: specific large base/exponent/modulus combinations make `BigInteger.modPow` take far more wall-clock time than the energy charged accounts for. [2](#0-1) 

### Finding Description
`ModExp.execute` parses `base`, `exp`, `mod` from calldata and calls `base.modPow(exp, mod)` directly, exactly as Besu's `BigIntegerModularExponentiationPrecompiledContract` did. [3](#0-2)  The corresponding energy cost (`getEnergyForData`) uses `getMultComplexity(max(baseLen, modLen))` combined with `getAdjustedExponentLength`, which is the same big-O approximation formula whose mismatch with actual `modPow` cost for specific numeric shapes (as demonstrated in EL-2022-15's PoC) allows charging orders of magnitude less energy than the real CPU time consumed. [4](#0-3) 

The only existing mitigation, `MUtil.checkCPUTimeForModExp()`, is extremely narrow: it only triggers when `baseLen == 0 && modLen == 0 && expLen > UPPER_BOUND`, and even then only after `ForkBlockVersionEnum.VERSION_4_8_1_1` is activated. [5](#0-4) [6](#0-5)  The EL-2022-15 PoC calldata is the opposite shape — non-zero, sizeable `base` and `modulus` with a small `exp` — so this guard does not apply to it at all. The general 1024-byte input cap and the corrected TIP-7883 pricing formula (`getEnergyTIP7883`/`getMultComplexityTIP7883`/`getIterationCountTIP7883`) only apply when `VMConfig.allowTvmOsaka()` returns true, i.e., after that specific hard fork is enabled on the network. [7](#0-6) [8](#0-7)  Before that activation point, an attacker's contract can invoke the `0x05` precompile (directly or via `STATICCALL`/`CALL` in a loop) with calldata shaped like the EL-2022-15 PoC, and repeat the call as many times as the transaction's energy limit allows, since each call is priced far below its actual CPU cost.

### Impact Explanation
Any unprivileged account can deploy a contract and submit a single signed transaction that repeatedly calls the ModExp precompile with pathological, underpriced inputs, consuming disproportionate CPU time on every full node and SR that must re-execute the transaction (during broadcast validation, block application in `Manager`, and re-verification by other nodes). This is a computation-based denial-of-service vector against block production/validation, matching the "no impact" exclusion boundary only if unreachable — here it is directly reachable from an ordinary contract call, which the scan rules explicitly permit ("TVM opcodes, precompiles and energy metering").

### Likelihood Explanation
Likelihood depends entirely on whether the `allowTvmOsaka` hard fork (which introduces `UPPER_BOUND` and TIP-7883 repricing) has been activated on the target network. Prior to that activation, the vulnerable legacy formula (`getMultComplexity`/`getAdjustedExponentLength`) is fully live and unrestricted in input size, making the attack straightforward to reproduce by directly porting the EL-2022-15 calldata into a TVM contract call to `0x05`.

### Recommendation
- Backport/decouple the `UPPER_BOUND` length cap and TIP-7883-style pricing correction so they are not solely gated behind `allowTvmOsaka`, or accelerate activation of that fork on all networks.
- Broaden `checkCPUTimeForModExp` (or a similar wall-clock/CPU-time guard) to cover all ModExp invocations, not only the `baseLen == 0 && modLen == 0` degenerate case.
- Independently benchmark/re-derive the energy formula against real `BigInteger.modPow` costs for adversarial inputs (as done for EIP-7883) rather than relying solely on the historical EIP-198 approximation.

### Proof of Concept
Deploy a contract whose fallback loops `STATICCALL(gas, 0x05, ...)` with calldata identical in shape to the EL-2022-15 PoC (large `base`/`modulus`, small `exp`, `baseLen`/`modLen` well under any then-unenforced cap), and submit one transaction with the maximum permitted `fee_limit`/energy. Each call bills the cheap `getMultComplexity`-derived energy while executing a comparably slow `BigInteger.modPow`, so the total number of iterations affordable under the energy limit yields a proportionally larger wall-clock delay than intended by the energy model — reproducing the 5.4s-for-5555-calls disparity reported against Besu, scaled to java-tron's per-transaction energy limit.

    private long getMultComplexity(long x) {

      long x2 = x * x;

      if (x <= 64) {
        return x2;
      }
      if (x <= 1024) {
        return x2 / 4 + 96 * x - 3072;
      }

      return x2 / 16 + 480 * x - 199680;
    }

    private long getAdjustedExponentLength(byte[] expHighBytes, long expLen) {

      int leadingZeros = numberOfLeadingZeros(expHighBytes);
      int highestBit = 8 * expHighBytes.length - leadingZeros;

      // set index basement to zero
      if (highestBit > 0) {
        highestBit--;
      }

      if (expLen <= 32) {
        return highestBit;
      } else {
        return 8 * (expLen - 32) + highestBit;
      }
    }

    private long getEnergyTIP7883(int baseLen, int modLen,
                                  byte[] expHighBytes, int expLen) {
      long multComplexity = getMultComplexityTIP7883(baseLen, modLen);
      long iterCount = getIterationCountTIP7883(expHighBytes, expLen);

      // use big numbers to stay safe in case of overflow
      BigInteger energy = BigInteger.valueOf(multComplexity)
          .multiply(BigInteger.valueOf(iterCount));

      if (isLessThan(energy, MIN_ENERGY_TIP7883_BI)) {
        return MIN_ENERGY_TIP7883;
      }

      return isLessThan(energy, BigInteger.valueOf(Long.MAX_VALUE)) ? energy.longValueExact()
          : Long.MAX_VALUE;
    }

    /**
     * TIP-7883: New multiplication complexity formula.
     * Minimal complexity of 16; doubled complexity for base/modulus > 32 bytes.
     */
    private long getMultComplexityTIP7883(int baseLen, int modLen) {
      long maxLength = StrictMathWrapper.max(baseLen, modLen);
      if (maxLength <= 32) {
        return 16;
      }
      // ceil(maxLength / 8)
      long words = StrictMathWrapper.floorDiv(StrictMathWrapper.addExact(maxLength, 7L), 8L);
      return StrictMathWrapper.multiplyExact(2L, StrictMathWrapper.multiplyExact(words, words));
    }

    /**
     * TIP-7883: New iteration count formula.
     * Multiplier for exponents > 32 bytes increased from 8 to 16.
     */
    private long getIterationCountTIP7883(byte[] expHighBytes, long expLen) {
      int leadingZeros = numberOfLeadingZeros(expHighBytes);
      long highestBit = StrictMathWrapper.subtractExact(
          StrictMathWrapper.multiplyExact(8L, expHighBytes.length), leadingZeros);

      if (highestBit > 0) {
        highestBit = StrictMathWrapper.subtractExact(highestBit, 1L);
      }

      long iterCount;
      if (expLen <= 32) {
        iterCount = highestBit;
      } else {
        iterCount = StrictMathWrapper.addExact(
            StrictMathWrapper.multiplyExact(16L, StrictMathWrapper.subtractExact(expLen, 32L)),
            highestBit);
      }

      return StrictMathWrapper.max(iterCount, 1L);
    }
