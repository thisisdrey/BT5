## Analog Found

### Title
Duplicate-signature bypass in `ValidateMultiSign` precompile allows a single validator's key to be counted multiple times toward the multisig weight threshold - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile, which is directly reachable by any contract-calling transaction via `TriggerSmartContractContract`, is supposed to enforce a weighted-threshold multisig check similar in spirit to `SettlementSignatureVerifier::verifyECDSA` from the external report. Its de-duplication logic keys on the raw signature bytes rather than on the recovered signer's identity, so an attacker who controls a single valid signature over the message hash can derive an ECDSA-malleable variant of it and submit both, causing the same signer's weight to be counted twice.

### Finding Description
`ValidateMultiSign.execute` loops over the caller-supplied `signatures` array, recovers the signer address for each entry, and is meant to skip signatures already counted: [1](#0-0) 

```
List<byte[]> executedSignList = new ArrayList<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  sign = merge(recoveredAddr, sign);
  if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
    if (ByteArray.matrixContains(executedSignList, sign)) {
      continue;
    }
    MUtil.checkCPUTime();
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
  executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
}
```

The `continue` (skip) is only taken when the *exact byte encoding* of `merge(recoveredAddr, sign)` has already been seen. If `recoveredAddr` was already counted but the raw signature bytes differ — which is trivially achievable for ECDSA via signature malleability (the pair `(r, s)` and `(r, n-s)` with the corresponding flipped recovery id both recover to the same public key/address) — execution falls through and adds `weight` again for the very same signer. This is the same root cause pattern described in the external report: the checker verifies "is this a valid signer" but never verifies "has this signer already been counted," so a single controlled key can be replayed (in a malleated form) to inflate the apparent number of distinct signers.

By contrast, the sibling path `TransactionCapsule.checkWeight` (used for on-chain transaction multisig validation) mitigates this precisely by keying de-duplication on the recovered **address** (post fork `VERSION_4_7_1`), not on the raw signature bytes: [2](#0-1) 

The `ValidateMultiSign` precompile never received the equivalent hardening.

### Impact Explanation
Any contract using `ValidateMultiSign` (address `0x66`-class precompile) as its authorization gate for multisig-protected operations (e.g., custom TRC20 bridges, vaults, or DAOs built on TVM that rely on this precompile for weighted multisig, as documented/tested in `ValidateMultiSignContractTest`) can be tricked into believing a threshold of *distinct* validators/co-signers has been reached when in fact only one signer (with a malleated duplicate of their own signature) participated. This is a direct authorization bypass on funds or privileged operations gated by TVM-level multisig, matching the "single valid signature satisfies a multi-party threshold" impact class from the external report.

### Likelihood Explanation
The precompile is reachable from any transaction that triggers a smart contract calling it — no special privilege is required. Constructing a malleated but still cryptographically valid signature for a known `(r,s)` pair is a standard, well-understood operation (flip `s` to `n-s` and the corresponding `v`), requiring no private key access beyond already possessing one valid signature over the hash. The only precondition is that the permission's threshold can be met by double-counting one signer's weight (e.g., an active permission where the attacker's key weight, doubled, meets or exceeds `required_validators`/threshold) — a configuration entirely under the control of whoever sets up the permission being (mis)relied upon by the calling contract.

### Recommendation
De-duplicate by recovered signer identity (`recoveredAddr`), not by the raw signature bytes, mirroring the fix already applied in `TransactionCapsule.checkWeight`:
```diff
- if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
-   if (ByteArray.matrixContains(executedSignList, sign)) {
-     continue;
-   }
-   MUtil.checkCPUTime();
- }
+ if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
+   continue;
+ }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  ...
  totalWeight += weight;
- executedSignList.add(sign);
  executedSignList.add(recoveredAddr);
```
Additionally, enforce canonical (low-`s`) signature form during recovery (as already done for signing via `ECDSASignature.toCanonicalised()`) so malleated signature encodings are rejected outright.

### Proof of Concept
1. Deploy/permission an active account with `required_validators`/`threshold` such that a single key's weight, if counted twice, meets the threshold (e.g., weight 2 with threshold 2, only one real signer with weight 2 but attacker submits it as "two slots").
2. Attacker signs `hash` once with their key, obtaining `(r, s, v)`.
3. Attacker derives the malleable counterpart `(r, n-s, v')` — still a cryptographically valid signature recovering to the same address.
4. Attacker calls the contract that invokes `ValidateMultiSign` with `signatures = [sig1, sig1_malleated]`.
5. In the loop: iteration 1 adds `weight` for `recoveredAddr` and records `merge(addr, sig1)`. Iteration 2 recovers the same `recoveredAddr`, but `merge(addr, sig1_malleated)` was never recorded, so the `continue` is skipped and `weight` is added a second time, satisfying `totalWeight >= permission.getThreshold()` with only one real signer.
