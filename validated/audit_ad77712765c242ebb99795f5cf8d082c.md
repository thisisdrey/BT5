### Title
`remove_account` fails to purge `PostponedReceipt`/`PostponedReceiptId` trie rows, allowing an attacker to plant a self-privileged action that fires against a re-created account - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) only removes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for a deleted account. It never iterates or removes `TrieKey::PostponedReceipt{receiver_id, receipt_id}` or `TrieKey::PostponedReceiptId` rows, meaning any receipt that was postponed against that account (waiting on unresolved `input_data_ids`) survives account deletion untouched in the trie.

### Finding Description
`remove_account` explicitly enumerates and deletes only three categories of state for `account_id`: [1](#0-0) 
- `TrieKey::Account` and `TrieKey::ContractCode` [2](#0-1) 
- Access keys / gas-key nonces, found via `get_raw_prefix_for_access_keys` [3](#0-2) 
- Contract data, found via `get_raw_prefix_for_contract_data` [4](#0-3) 

There is no prefix scan or removal for `TrieKey::PostponedReceipt` or `TrieKey::PostponedReceiptId`, both of which are keyed by `receiver_id` (per `core/primitives/src/trie_key.rs`). A postponed receipt is created whenever an `ActionReceipt` arrives at its receiver before all of its `input_data_ids` have been delivered; `set_postponed_receipt`/`get_postponed_receipt` in `runtime/runtime/src/lib.rs` persist and later retrieve these rows purely by `(receiver_id, receipt_id)`, independent of whether the `Account` row for that `receiver_id` still exists.

Because account deletion does not clear these rows, an attacker can:
1. From account `X`, issue a `FunctionCall` that creates a promise/receipt targeting `X` itself (`predecessor_id == receiver_id == X`) containing an `AddKey(FullAccess, attacker_pubkey)` action, and make that receipt depend on two `input_data_ids` that are never resolved immediately — this causes the runtime to persist the `ActionReceipt` via the postponed-receipt path under key `(X, receipt_id)`.
2. Submit `DeleteAccount(X)`, removing the `Account`/keys/contract state for `X` but leaving the postponed `ActionReceipt` row intact in the trie.
3. Have some other party (or the attacker via a different path) subsequently execute `CreateAccount` for the same `account_id` `X` (account-id reuse after deletion is otherwise permitted by the protocol).
4. Deliver the outstanding `DataReceipt`s for the two `input_data_ids`. The runtime's Data-receipt handling path fetches the row via `get_postponed_receipt(state_update, receiver_id, receipt_id)` and, once all dependencies are satisfied, executes the stored `ActionReceipt` against whatever account currently occupies `receiver_id` — the freshly re-created `X` — running `AddKey` with `check_actor_permissions` seeing `predecessor_id == receiver_id` (self-privileged) and installing the attacker's `FullAccess` key on an account the attacker no longer legitimately controls (and which may now belong to an unrelated party).

Existing checks (nonce, nonce/access-key, gas metering, size limits) validate the original transaction that created the postponed receipt, but none of them are re-evaluated at resolution time against the *current* state of the account, and `remove_account` provides no invalidation of stale postponed work tied to a deleted-and-recreated account id.

### Impact Explanation
This is an authorization-escalation bug across account lifecycle boundaries (NEAR bounty category: authorization escalation across accounts/promises). An attacker can implant a dormant, self-authorizing action (`AddKey` granting themselves `FullAccess`, but the same mechanism generalizes to any actor-authorized action such as `DeleteKey`, `Stake`, or `DeployContract`) that lies latent in the trie after the account is deleted, and detonate it once the account id is reused, potentially by an unrelated new owner. The scoped impact is gaining unauthorized full control of a re-created account.

### Likelihood Explanation
Preconditions are attacker-controlled and inexpensive: the attacker only needs to (a) deploy/call a contract capable of issuing a self-receipt with unresolved `input_data_ids`, (b) delete their own account, and (c) later supply the corresponding `DataReceipt`s. The step requiring the account id to be *re-created* by a third party is the main external dependency and constrains real-world likelihood — this is most exploitable for cases where the attacker also controls or influences re-creation (e.g., short-lived/named subaccounts, or the attacker itself triggers recreation), and less directly powerful against arbitrary victims who happen to reuse the exact deleted account id. I was not able to fully verify in this pass (i) whether `DeleteAccount` has any precondition today that blocks deletion while postponed receipts exist for the account, or (ii) the precise wording of `check_actor_permissions` for `AddKey`, so these should be confirmed with the referenced files (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`) before treating this as fully proven.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also iterate and delete all `TrieKey::PostponedReceipt{receiver_id, ..}` and `TrieKey::PostponedReceiptId{receiver_id, ..}` rows for `account_id`, using an analogous prefix-scan-and-remove pattern to the existing access-key/contract-data loops, so that no dangling postponed work can survive account deletion and later fire against a re-created account with the same id.

### Proof of Concept
1. Integration/unit test in `runtime/runtime/src/tests/apply.rs` (or a test-loop test similar to `test-loop-tests/src/tests/create_delete_account.rs`):
   - Create account `X` with a contract that, on call, creates an `ActionReceipt` to itself containing `AddKey(FullAccess, attacker_pk)` and depends on two unresolved `input_data_ids`.
   - Assert via `get_postponed_receipt` that the receipt is stored under `(X, receipt_id)`.
   - Submit `DeleteAccount(X)` and confirm `Account`/access-key state is gone but the postponed receipt row still resolves via `get_postponed_receipt`.
   - Submit `CreateAccount(X)` to recreate the account.
   - Deliver the two missing `DataReceipt`s and process them through the Data-receipt arm in `runtime/runtime/src/lib.rs`.
   - Assert the `AddKey` action executes successfully (permission check passes) and that `attacker_pk` now has `FullAccess` on the recreated `X`, despite the attacker not owning `X` at the time of recreation.
