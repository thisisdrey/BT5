### Title
Silent partial fetch on non-fatal `git-fetch` errors leads to incomplete/inconsistent reference updates - ([File: internal/gitaly/service/repository/fetch_remote.go])

### Summary
`fetchRemoteAtomic` (called from the `FetchRemote` RPC) attempts to distinguish "benign" `git-fetch` failures (some refs rejected) from genuine fetch failures purely by string-matching the wrapped Go error against the literal string `"exit status 1"` and checking whether `stderr` is empty. If both conditions hold — remote-controlled behavior, since `git-fetch` is invoked against the caller-supplied remote URL/SSH command — the function treats the failure as a harmless partial ref-update failure and silently continues to apply whatever fetch-porcelain lines happened to be captured in `stdout`, then commits those to the repository. [1](#0-0) 

### Finding Description
`FetchRemote` builds fetch options with `DryRun: true` and `Porcelain: true`, then executes the fetch against the (potentially remote-controlled) `inmemory` remote inside a quarantine directory. [2](#0-1)  When `quarantineRepo.FetchRemote` returns an error, the code does not check the git exit status via `command.ExitStatus` or any structured signal — it only checks whether `stderr` is non-empty and whether `err.Error()` is exactly the string `"exit status 1"`: [1](#0-0) 

This is unreliable because:
- `exec.ExitError.Error()` always renders as `"exit status N"` regardless of *why* the process exited 1 — e.g., a truncated/aborted connection, an interrupted SSH transport, a corrupted pack stream, or a hostile remote that intentionally emits nothing to stderr while returning exit code 1 (trivially achievable by a remote that redirects `receive.denyCurrentBranch`-style output, closes the connection at a specific point, or is a Gitaly-driven mirror pointing to an attacker-controlled server since `RemoteParams.Url`/SSH parameters are attacker-influenced input for mirror-pull configurations).
- The subsequent code then proceeds unconditionally to scan whatever partial `stdout` porcelain lines were produced and to `Prepare()`/`Commit()` those reference updates via `prunedUpdater`/`refUpdater`. [3](#0-2) 
- No validation exists to confirm that the fetch actually completed a full negotiation/transfer before those partial results are treated as authoritative. Since `DryRun: true` is used specifically so that `git-fetch` reports intended reference changes without applying them, an aborted fetch can still emit a subset of porcelain lines describing refs whose objects were only partially received, yet those lines get applied to the real repository through `git-update-ref` after quarantine migration.

The comment in the code candidly documents the intended (but fragile) assumption: *"the error message is not 'exit status 1', it is determined that the error is unrelated to failed reference updates... Otherwise, it is assumed the error is from a failed reference update and the operation proceeds to update references."* This assumption conflates all `exit status 1` + empty-stderr failures with "some individual ref updates were rejected," which is not something Git guarantees.

### Impact Explanation
Because `FetchRemote` is a mutator RPC that participates in Gitaly's Praefect voting/replication protocol, an inconsistent or partial application of reference updates on one replica — driven by a remote server that can trigger this ambiguous exit condition — can propagate through the reference-transaction vote as if the fetch had legitimately succeeded, since the returned error is swallowed. This causes:
- Silent write of an incomplete/inconsistent set of refs to the repository despite the underlying fetch not fully succeeding.
- Divergent state versus other nodes/replicas that either received the same ambiguous failure differently or that a legitimate retry would have avoided, undermining the "atomic" fetch design that the surrounding code and comments explicitly aim to guarantee.
- Because this happens transparently to the RPC caller (no error is surfaced when the ambiguous condition is hit), any caller (e.g., GitLab's mirror-pull workers) will believe the fetch fully succeeded when in fact it may have applied a subset of updates against a partially/never-negotiated fetch.

This maps to the bug class described in the source report (unchecked/misinterpreted operation result leading to state inconsistency across execution boundaries): here the "chains" are Gitaly replicas/repository state versus the actual remote's guaranteed outcome, rather than blockchains, but the causal mechanism (proceeding on an operation whose success was not actually verified) is the same.

### Likelihood Explanation
Reaching this code path requires only invoking `FetchRemote` (or a mirror/pull-mirror workflow that calls it) with a `RemoteParams.Url`/SSH configuration pointing at a remote under attacker influence or subject to network conditions that can produce a bare `exit status 1` (e.g., truncated connection, remote closing stdout early, or misbehaving/malicious server). This is a normal, unprivileged operation available to any caller permitted to invoke repository mutator RPCs (e.g., configuring or triggering a pull mirror), and does not require compromising Gitaly itself — only control or interference with the remote endpoint. Producing exit code 1 with empty stderr is a low-effort condition for a hostile git server to engineer deliberately.

### Recommendation
Replace the string-based error classification with the actual git exit status and, more importantly, with structured signals from the fetch output rather than assuming any `exit status 1` with empty stderr implies "only some individual ref updates failed":
- Use `command.ExitStatus(err)` to check the process exit code robustly instead of comparing `err.Error()` to a literal string.
- Do not treat an ambiguous exit-1/empty-stderr case as automatically safe to continue. Instead, positively confirm that the failure is exactly a `"the following refs failed to update"`-style git-fetch outcome (or otherwise use `--porcelain` markers that unambiguously indicate partial-rejection versus transport failure) before proceeding to apply partial reference updates.
- When the classification cannot be made with confidence, fail closed (return the error) rather than silently continuing to commit whatever partial porcelain output was captured.

### Proof of Concept
Not directly demonstrable without live access to a Gitaly test environment and a controllable git remote/SSH endpoint. Conceptually: run `FetchRemote` against a remote (or fake git server) that responds to the fetch negotiation, sends a subset of `git fetch --porcelain --dry-run` status lines to stdout, then aborts the connection so that `git-fetch` exits with status 1 and writes nothing to stderr (e.g., closing the socket immediately after sending partial ref advertisement/porcelain output, or using a custom `git-upload-pack` wrapper that exits 1 silently after partially responding). Observe that `fetchRemoteAtomic` proceeds to `Prepare()`/`Commit()` the partial reference set instead of surfacing an error, verifiable by asserting the RPC returns success (`FetchRemoteResponse`) while the local repository reflects only a subset of the intended updates.

		Stdout:  &stdout,
		Stderr:  &stderr,
		Force:   req.GetForce(),
		Prune:   !req.GetNoPrune(),
		Tags:    localrepo.FetchOptsTagsAll,
		Verbose: true,

		// Since references are not updated during a `git-fetch(1)` dry-run, the reference

	scanner := gitcmd.NewFetchPorcelainScanner(&stdout, objectHash)
	for scanner.Scan() {
		status := scanner.StatusLine()

		switch status.Type {
		// Failed and unchanged reference updates do not need to be applied.
		case gitcmd.RefUpdateTypeUpdateFailed, gitcmd.RefUpdateTypeUnchanged:
		// Queue pruned references in a separate transaction to avoid F/D conflicts.
		case gitcmd.RefUpdateTypePruned:
			if err := prunedUpdater.Delete(git.ReferenceName(status.Reference)); err != nil {
				return false, false, fmt.Errorf("queueing pruned ref for deletion: %w", err)
			}
			referencesUpdated = true
		// Queue all other reference updates in the same transaction.
		default:
			if err := refUpdater.Update(git.ReferenceName(status.Reference), status.NewOID, status.OldOID); err != nil {
				return false, false, fmt.Errorf("queueing ref to be updated: %w", err)
			}
			referencesUpdated = true

			// While scanning reference updates, check if any tags changed.
			if wereTagsChanged(status) {
				tagsChanged = true
			}

			// While scanning reference updates, check if repo was changed.
			if changeTypes[status.Type] {
				repoChanged = true
			}
		}
	}
	if scanner.Err() != nil {
		return false, false, fmt.Errorf("scanning fetch output: %w", scanner.Err())
	}

	// Prepare pruned references in separate transaction to avoid F/D conflicts.
	if err := prunedUpdater.Prepare(); err != nil {
		return false, false, fmt.Errorf("preparing reference prune: %w", err)
	}

	// Commit pruned references to complete transaction and apply changes.
	if err := prunedUpdater.Commit(); err != nil {
		return false, false, fmt.Errorf("committing reference prune: %w", err)
	}

	// Prepare the remaining queued reference updates.
	if err := refUpdater.Prepare(); err != nil {
		return false, false, fmt.Errorf("preparing reference update: %w", err)
	}

	// Before committing the remaining reference updates, fetched objects must be migrated out of
	// the quarantine directory.
	if err := quarantineDir.Migrate(ctx); err != nil {
		return false, false, fmt.Errorf("migrating quarantined objects: %w", err)
	}

	// Commit the remaining queued reference updates so the changes get applied.
	if err := refUpdater.Commit(); err != nil {
		return false, false, fmt.Errorf("committing reference update: %w", err)
	}
