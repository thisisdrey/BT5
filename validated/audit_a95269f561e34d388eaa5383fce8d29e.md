### Title
`DeleteAccountAction.beneficiary_id` is only format-validated, not existence-checked, causing account balance to be permanently burnt if the beneficiary account does not exist - (File: runtime/runtime/src/actions.rs)

### Summary
`DeleteAccountAction` lets the account owner send the deleted account's entire balance to `beneficiary_id`. The action validator only checks that `beneficiary_id` is a syntactically valid `AccountId`; it never checks that the account actually exists on-chain. When it doesn't exist, the resulting balance-transfer receipt is treated like a refund and, since refunds that fail to execute are burnt rather than bounced back, the funds are irrecoverably destroyed — a direct analog of the escrow-pool-not-set bug: a value that is not properly validated at write time silently discards funds at spend time.

### Finding Description
`action_delete_account` computes the account's balance and unconditionally enqueues a system-originated transfer receipt to `beneficiary_id`, without checking that this account exists: [1](#0-0) 

The only validation performed on `beneficiary_id` anywhere in the transaction/receipt pipeline is a format check: [2](#0-1) 

This uses `validate_action_account_id`, which only validates that the string is a well-formed `AccountId` (per the docs, `InvalidAccountId` is the only validation-time error for `beneficiary_id`) — there is no existence check possible at validation time since validation happens before receipts execute and cannot know the recipient's future account state: [3](#0-2) 

`Receipt::new_balance_refund` constructs a system-predecessor `Transfer` action receipt — the same construct used for "deposit refunds": [4](#0-3) 

When this receipt is applied and the receiving account does not exist, `check_account_existence` fails for the `Transfer` action against a non-existent named account (matching the documented behavior for `send_money` to a non-existent account, which fails with `AccountDoesNotExist`): [5](#0-4) 

Critically, because this receipt has `predecessor_id == "system"` (a refund), the runtime's documented and implemented behavior is: *"If the execution of a refund fails, the refund amount is burnt."* [6](#0-5) 

This is implemented directly in the receipt-processing loop: when `receipt.predecessor_id().is_system()` and `result.result.is_err()`, the deposit amount is added to `stats.balance.other_burnt_amount` instead of being refunded/returned anywhere: [7](#0-6) 

So an account owner who deletes their account with a `beneficiary_id` that is a syntactically valid but non-existent (or not-yet-created) account permanently loses their entire remaining balance — exactly the escrow-bug pattern: a destination field is accepted without existence/liveness validation, and funds routed to it are silently destroyed rather than delivered or returned to the sender.

### Impact Explanation
This causes permanent, unrecoverable loss of the deleting account's full balance (potentially the account's entire net worth) with no way to retrieve it — a real "loss of funds" impact matching the Medium-severity escrow report. Any ordinary user issuing a normal `DeleteAccount` transaction with a mistyped, not-yet-created, or otherwise nonexistent beneficiary account triggers this loss; no special privileges are required to construct the transaction.

### Likelihood Explanation
Likelihood is high in the sense that any user error (typo in beneficiary account name, deleting the beneficiary account beforehand, or targeting an implicit/derived account that was never funded/created) triggers this path deterministically and silently — the transaction still succeeds (the `DeleteAccountAction` itself completes), giving no on-chain error signaling that funds were lost, since the failure occurs in a separate, later-processed refund-style receipt.

### Recommendation
Either (a) do not use the "refund" (system-predecessor) receipt semantics for the beneficiary payout — instead treat the failure of this transfer the same as an ordinary failed `Transfer` action (which typically bounces the deposit back to the predecessor) rather than silently burning it, or (b) require verification that `beneficiary_id` corresponds to an existing account before allowing `DeleteAccountAction` to execute (fail the whole delete if the beneficiary account doesn't exist), analogous to validating the escrow pool address before allowing a non-zero escrow portion.

### Proof of Concept
1. Account `alice.near` holds balance `B`.
2. `alice.near` submits `DeleteAccountAction { beneficiary_id: "nonexistent.near" }` where `nonexistent.near` has never been created.
3. `action_delete_account` passes `beneficiary_id` through only `validate_action_account_id` (format check) — no existence check — and enqueues `Receipt::new_balance_refund(&"nonexistent.near", B)`.
4. When this receipt executes, `check_account_existence` fails with `AccountDoesNotExist` for `nonexistent.near`, and because the receipt's `predecessor_id` is `"system"`, the runtime burns `B` into `stats.balance.other_burnt_amount` instead of returning it to `alice.near` or leaving `alice.near`'s account intact.
5. `alice.near`'s balance `B` is permanently lost — total supply is reduced, and no account regains the funds.
