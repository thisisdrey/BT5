### Title
Postponed self-Stake receipt survives DeleteAccount and locks a re-created account's funds to an attacker-controlled validator key - (File: runtime/runtime/src/actions.rs, core/store/src/utils/mod.rs)

### Summary
`remove_account` only deletes the `Account`, `ContractCode`, access/gas keys, and `ContractData` trie entries; it never touches `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` entries keyed by the account's `receiver_id`. `check_actor_permissions` for `Stake` only checks `actor_id == account_id` (i.e. the receipt is self-directed), never re-validating that the account's *current* owner authorized the action. An attacker can postpone a self-`Stake` action receipt (via a data dependency they fully control, e.g. `promise_yield`), delete their account while `locked == 0`, wait for a victim to recreate the same `account_id` and fund it, then resolve the pending data to force the postponed `Stake` to execute against the victim's funds.

### Finding Description
1. Attacker's contract at account `A` issues a promise whose callback is a self-receipt `{predecessor_id: A, receiver_id: A, actions: [Stake(attacker_pubkey, stake)]}` with a non-empty `input_data_ids` (e.g., via `promise_yield_create`, giving the attacker full timing control over when the dependency resolves, up to the yield timeout window).
2. Since `pending_data_count > 0`, `process_action_receipt` stores this as a postponed receipt: `set_postponed_receipt` under `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}`, plus `TrieKey::PendingDataCount{receiver_id: A, receipt_id}` and `TrieKey::PostponedReceiptId{receiver_id: A, data_id}`. [1](#0-0) 
3. Attacker submits `DeleteAccount` on `A` (locked is still `0` because the `Stake` action hasn't executed yet). `check_actor_permissions` allows this since `actor_id == account_id` and `account.locked().is_zero()`. [2](#0-1) 
4. `action_delete_account` calls `remove_account`, which removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData` — it never removes `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` for `receiver_id = A`. [3](#0-2) [4](#0-3) 
5. A victim (unaware of the dangling postponed receipt) creates account `A` again via `CreateAccount` + `Transfer(deposit)`, funding it.
6. The attacker resolves the pending `DataReceipt` (e.g., calls `promise_yield_resume`) at the time of their choosing. `process_receipt` finds the matching `PostponedReceiptId{A, data_id}`, decrements `PendingDataCount` to zero, fetches the postponed receipt, and calls `apply_action_receipt` on it unconditionally. [5](#0-4) 
7. Inside `apply_action`, `check_account_existence` passes because `A` now exists again, and `check_actor_permissions` passes trivially because `actor_id (A) == account_id (A)` — there is no check that the current account state/owner matches whoever authorized the original `Stake`. `action_stake` then executes, moving `min(stake, account.amount())` from `amount` to `locked` and pushing a `ValidatorStake` proposal for the attacker's public key. [6](#0-5) [7](#0-6) 

The root cause is that authorization for administrative actions (`Stake`, `AddKey`, `DeleteKey`, etc.) is enforced only via the "predecessor==receiver" self-call check at receipt-execution time, relying on the assumption that the receipt was legitimately authorized when originally converted from a signed transaction. Postponed receipts break this assumption because their execution can be arbitrarily delayed past an intervening `DeleteAccount`/`CreateAccount` cycle on the same `account_id`, and `remove_account` does not invalidate/purge receiver-keyed postponed-receipt bookkeeping.

### Impact Explanation
This allows an unprivileged attacker to force a victim's freshly-created account to stake its balance to a validator public key the attacker controls, without the victim ever submitting a `Stake` action. This is a direct freezing/theft of user funds (the victim's balance moves from `amount` to `locked`, is unstakeable by the victim, and the resulting `ValidatorStake` proposal benefits the attacker's chosen key) — matching the "theft or permanent freezing of user funds" and "authorization escalation across accounts" bounty categories.

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privileged access:
- Attacker only needs to own account `A`, deploy a contract, and use a normal data-dependency mechanism (cross-contract callback or `promise_yield_create`/`promise_yield_resume`) to create a postponed self-`Stake` receipt, then submit an ordinary `DeleteAccount` transaction (locked=0 satisfies `DeleteAccountStaking`).
- The remaining trigger — needing a third party to later `CreateAccount`+fund the exact same `account_id` — is the main practical constraint. This is most exploitable for well-known/likely-to-be-reused sub-account names or in combination with social engineering/typo-squatting account names, or when the attacker itself controls when the funding happens (e.g., the attacker recreates their own account and funds it, if the goal is self-griefing/lockup demonstration, or if the "victim" is an unsuspecting party who is induced to create a specific named sub-account, e.g., a marketplace escrow or vanity subaccount workflow). Cost to the attacker is minimal (one contract deployment + a few transactions); the exploit is fully repeatable.

### Recommendation
`remove_account` (or `action_delete_account`) must purge all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` entries keyed by the deleted account's `receiver_id` before/while deleting the account, refunding/erroring out those pending receipts instead of leaving them dangling. Alternatively, `apply_action_receipt`/`check_actor_permissions` for postponed administrative actions should re-validate that the account has not been deleted-and-recreated since the receipt was postponed (e.g., by tracking an account "incarnation" counter compared at postponement time vs. execution time).

### Proof of Concept
Integration/unit test plan (runtime apply-level, similar in structure to `test_promise_input_size_limit_exceeded_fails_and_cleans_up` and `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` in `runtime/runtime/src/tests/apply.rs`):
1. Set up account `A` with `locked = 0`.
2. Apply a manually constructed `ActionReceipt` targeting `A` with `actions = [Stake(attacker_pubkey, stake_amount)]` and `input_data_ids = [data_id]` (unsatisfied) — assert it is stored as a postponed receipt (`get_postponed_receipt` returns `Some`).
3. Apply a `DeleteAccount` receipt for `A` (predecessor=`A`, beneficiary=attacker) — assert it succeeds and `get_account(A)` is `None`.
4. Apply `CreateAccount` + `Transfer(deposit)` receipts for `A` from a different predecessor (the "victim") — assert `A` exists with `amount = deposit`, `locked = 0`.
5. Apply the `DataReceipt{receiver_id: A, data_id}` that resolves the pending dependency.
6. Assert: `get_account(A).locked() > 0` (equal to `min(stake_amount, deposit)`), and that a `ValidatorStake` proposal for `attacker_pubkey` was emitted — despite the victim never signing or submitting any `Stake` action. This is the concrete PoC demonstrating unauthorized fund-locking.

pub(crate) fn action_stake(
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    stake: &StakeAction,
    last_block_hash: &CryptoHash,
    epoch_info_provider: &dyn EpochInfoProvider,
) -> Result<(), RuntimeError> {
    let increment = stake.stake.saturating_sub(account.locked());

    if let Some(new_balance) = account.amount().checked_sub(increment) {
        if account.locked().is_zero() && stake.stake.is_zero() {
            // if the account hasn't staked, it cannot unstake
            result.result =
                Err(ActionErrorKind::TriesToUnstake { account_id: account_id.clone() }.into());
            return Ok(());
        }

        if stake.stake > Balance::ZERO {
            let minimum_stake = epoch_info_provider.minimum_stake(last_block_hash)?;
            if stake.stake < minimum_stake {
                result.result = Err(ActionErrorKind::InsufficientStake {
                    account_id: account_id.clone(),
                    stake: stake.stake,
                    minimum_stake,
                }
                .into());
                return Ok(());
            }
        }

        result.validator_proposals.push(ValidatorStake::new(
            account_id.clone(),
            stake.public_key.clone(),
            stake.stake,
        ));
        if stake.stake > account.locked() {
            // We've checked above `account.amount >= increment`
            account.set_amount(new_balance);
            account.set_locked(stake.stake).or_inconsistent_state(account_id)?;
        }
    } else {
        result.result = Err(ActionErrorKind::TriesToStake {
            account_id: account_id.clone(),
            stake: stake.stake,
            locked: account.locked(),
            balance: account.amount(),
        }
        .into());
    }
    Ok(())
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
