### Title
Unprivileged low-cost transactions can permanently exhaust the per-account cost limit and censor a specific victim account's transactions each slot - ([File: cost-model/src/cost_tracker.rs])

### Summary
The Paraspace report describes an attacker cheaply filling a *per-entity, hard-capped* resource (the 30-NFT `balanceLimit`) belonging to a victim so that the victim's legitimate follow-up action (adding collateral) is permanently rejected, creating a window for a profitable follow-on attack (liquidation). Agave has a structurally identical bug class in `CostTracker`: a hard per-writable-account compute-unit budget (`MAX_WRITABLE_ACCOUNT_UNITS`) that any unprivileged fee-payer can fill with cheap, low-CU transactions that write-lock a chosen victim account, causing `WouldExceedMaxAccountCostLimit`/`AccountInUse`-style rejection of every other transaction touching that account for the remainder of the slot — regardless of the victim's own fee/priority.

### Finding Description
`CostTracker::would_fit` enforces, per writable account, a hard cap of `self.limits.account_cost` (`MAX_WRITABLE_ACCOUNT_UNITS = 24_000_000` CU) accumulated in `cost_by_writable_accounts`, independent of the requesting fee payer's identity or priority fee: [1](#0-0) 

The default limits wire this account cap directly from the constant: [2](#0-1) [3](#0-2) 

Once an account's accumulated cost reaches this cap within a slot, `try_add` rejects *any* subsequent transaction writing to that account with `CostTrackerError::WouldExceedAccountMaxLimit`, mapped to `TransactionError::WouldExceedMaxAccountCostLimit`: [4](#0-3) [5](#0-4) 

Because the check is purely a compute-unit accounting bound on the account key — not a priority-ordered auction — an attacker does not need to outbid the victim. The attacker only needs to be scheduled first (which unprivileged users freely can be, since scheduling by the `GreedyScheduler`/banking stage only orders by priority among *currently buffered* transactions, and the attacker can pre-stuff many low-CU, low-fee transactions writing to the victim account at the very start of every slot). Filling `24,000,000` CU worth of budget with minimum-CU transfer-style transactions (a few thousand CU each) requires only thousands of cheap, base-fee transactions per slot — far cheaper than the value the attacker can extract by delaying the victim's transaction (e.g., a liquidation-sensitive account update, an oracle-consuming program, or any time-critical write to that account).

This mirrors the Paraspace pattern exactly:
- Both rely on a fixed, per-entity resource ceiling (`balanceLimit` vs. `account_cost` limit) enforced during normal, permissionless "mint"/"transaction" flows.
- Both allow a third party with no special privilege to consume that ceiling on someone else's behalf, using only transaction fees as cost (cheap on both a Uniswap-mint/liquidity-removal loop and on a minimal-CU Solana transaction).
- Both create a window in which the victim's legitimate, higher-value transaction is rejected purely due to hitting the shared limit, enabling a profitable follow-on action by the attacker (liquidation in Paraspace; front-running/censorship-driven MEV in Agave).

### Impact Explanation
A victim's time-sensitive transaction touching a specific hot account (their own account, a lending-protocol state account, an AMM pool account, etc.) can be reliably excluded from a leader's block for an entire slot (and can be repeated slot after slot) at very low cost to the attacker, since the attacker only pays base fees for minimal-CU transactions and does not need to win any priority auction. This is a real censorship/DoS primitive against a chosen account that degrades the fairness and availability guarantees the cost model is meant to provide (it was designed to bound per-account contention, not to be weaponizable against a specific account by a third party). It can be leveraged to delay liquidations, oracle updates, or any account-specific critical path, giving the attacker a timing/MEV advantage — directly analogous to the "front-run and lock out collateral, then liquidate" scenario in the source report.

### Likelihood Explanation
High reachability: any unprivileged client can submit ordinary transactions writing to a public/hot account; no special role or vulnerable configuration is required. The cost is bounded by `MAX_WRITABLE_ACCOUNT_UNITS` (24M CU) divided by the minimal per-transaction CU cost (a few thousand CU for signature + write-lock + minimal instruction), meaning a moderate number of cheap transactions per slot suffices. This is a per-slot repeatable griefing pattern requiring only sustained low-value spend, not a one-off exploit, and does not require validator/peer roles, mocking, or theoretical-only conditions.

### Recommendation
Consider making the per-account cost limit resistant to third-party griefing, for example by:
- Weighting or prioritizing the per-account budget by the fee/priority of competing transactions rather than plain FIFO/first-scheduled consumption, so a victim's higher-priority transaction can displace low-fee filler transactions within the same account bucket.
- Introducing a minimum fee-per-CU floor for consuming a meaningful fraction of the per-account budget, to raise the cost of griefing an account.
- Allowing the fee payer/signer of the contended write-locked account to retain a reserved fraction of the per-account CU budget, similar to how the Paraspace mitigation intends to add cost/friction to filling shared limits on behalf of others.

### Proof of Concept
Conceptual PoC (mirrors the Paraspace `_uniswapv3_position_control.spec.ts` pattern):
1. Identify a victim account `V` that a legitimate, time-critical transaction (e.g., liquidation call) will need to write-lock in an upcoming slot.
2. At the start of every slot, submit as many minimal-CU transactions as needed (via `system_transaction::transfer`-style transactions or minimal custom instructions) that write-lock `V`, until `cost_by_writable_accounts[V]` reaches `MAX_WRITABLE_ACCOUNT_UNITS` (24,000,000 CU), exercising the same accounting path validated in the existing tests: [6](#0-5) 
3. Submit the victim's legitimate high-priority-fee transaction touching `V` in the same slot; it fails with `WouldExceedMaxAccountCostLimit` regardless of fee, exactly as exercised by: [7](#0-6) 
4. Repeat every slot at negligible cost to keep `V` effectively censored while the attacker executes the profitable follow-on action.

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

    #[test]
    fn test_cost_tracker_try_add_is_atomic() {
        let acct1 = Pubkey::new_unique();
        let acct2 = Pubkey::new_unique();
        let acct3 = Pubkey::new_unique();
        let cost = 100;
        let account_max = cost * 2;
        let block_max = account_max * 3; // for three accts

        let mut testee = CostTracker::new(account_max, block_max);

        // case 1: a tx writes to 3 accounts, should success, we will have:
        // | acct1 | $cost |
        // | acct2 | $cost |
        // | acct3 | $cost |
        // and block_cost = $cost
        {
            let transaction = WritableKeysTransaction::new(vec![acct1, acct2, acct3]);
            let tx_cost = simple_transaction_cost(&transaction, cost);
            assert!(testee.try_add(&tx_cost).is_ok());
            let (_costliest_account, costliest_account_cost) = testee.find_costliest_account();
            assert_eq!(cost, testee.block_cost());
            assert_eq!(3, testee.cost_by_writable_accounts.len());
            assert_eq!(cost, costliest_account_cost);
        }

        // case 2: add tx writes to acct2 with $cost, should succeed, result to
        // | acct1 | $cost |
        // | acct2 | $cost * 2 |
        // | acct3 | $cost |
        // and block_cost = $cost * 2
        {
            let transaction = WritableKeysTransaction::new(vec![acct2]);
            let tx_cost = simple_transaction_cost(&transaction, cost);
            assert!(testee.try_add(&tx_cost).is_ok());
            let (costliest_account, costliest_account_cost) = testee.find_costliest_account();
            assert_eq!(cost * 2, testee.block_cost());
            assert_eq!(3, testee.cost_by_writable_accounts.len());
            assert_eq!(cost * 2, costliest_account_cost);
            assert_eq!(acct2, costliest_account);
        }

        // case 3: add tx writes to [acct1, acct2], acct2 exceeds limit, should failed atomically,
        // we should still have:
        // | acct1 | $cost |
        // | acct2 | $cost * 2 |
        // | acct3 | $cost |
        // and block_cost = $cost * 2
        {
            let transaction = WritableKeysTransaction::new(vec![acct1, acct2]);
            let tx_cost = simple_transaction_cost(&transaction, cost);
            assert!(testee.try_add(&tx_cost).is_err());
            let (costliest_account, costliest_account_cost) = testee.find_costliest_account();
            assert_eq!(cost * 2, testee.block_cost());
            assert_eq!(3, testee.cost_by_writable_accounts.len());
            assert_eq!(cost * 2, costliest_account_cost);
            assert_eq!(acct2, costliest_account);
        }
