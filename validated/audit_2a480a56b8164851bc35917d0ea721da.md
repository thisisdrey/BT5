### Title
Missing server-side enforcement of `write-freq` allows unauthorized-write throughput abuse on StackerDB HTTP write path - (File: stackslib/src/net/stackerdb/db.rs)

### Summary
The external report describes a missing economic/rate limit (transaction fee) on a privileged write path, letting an unprivileged caller exhaust a shared resource controlled by the intended limit. The closest reachable analog in this repo is `StackerDBTx::try_replace_chunk`, which enforces `chunk_size`, slot ownership (signature), monotonic `slot_version`, and `max_writes`, but never checks `StackerDBConfig::write_freq` (the smart-contract-declared minimum wall-clock interval between writes to a slot) [1](#0-0) . This function is invoked directly, with no additional throttling, from the unauthenticated HTTP write endpoint `RPCPostStackerDBChunkRequestHandler::try_handle_request` (`POST /v2/stackerdb/:principal/:contract/chunks`) [2](#0-1) .

### Finding Description
`StackerDBConfig.write_freq` is a value read from the controlling smart contract, documented as the minimum wall-clock interval a slot owner must wait between successive writes (`stackerdb-get-config`'s `write-freq` field) [3](#0-2) . It is loaded into `StackerDBConfig` and stored per-replica [4](#0-3) , and `SlotValidation` even tracks a `write_time` per slot in the database that could support this check [5](#0-4) .

However, `try_replace_chunk` — the single authoritative write path used both by the P2P sync/relay logic and by the HTTP `POST .../chunks` handler — only validates chunk size, slot existence, signature ownership, version freshness, and `max_writes`; it never compares `get_epoch_time_secs()` against the slot's last `write_time` plus `config.write_freq` [6](#0-5) . The peer-to-peer validation function `validate_received_chunk` explicitly documents this gap: "NOTE: does not check write frequency, since the caller has different ways of doing this" [7](#0-6)  — but the HTTP handler is not one of those "other ways"; it calls `try_replace_chunk` unconditionally once signature/version checks pass [8](#0-7) .

This mirrors the reported bug class exactly: a protocol-level economic/rate control (`BurnFee`/`write-freq`) that governs how fast a privileged operation can be repeated is declared and read, but the actual write-executing code path silently omits enforcing it, so any caller who can produce a validly-signed chunk (i.e., the legitimate slot owner, or anyone who has ever observed one of that owner's signed chunks and can replay/increment its version) can write as fast as the network allows, unconstrained by the contract-declared throttle.

### Impact Explanation
`max_writes` bounds total lifetime writes to a slot but does not bound rate; without `write_freq` enforcement, a slot owner (or anyone able to construct valid signed chunks, which requires the slot's private key) can spam the HTTP write endpoint or P2P push messages at wire speed, causing:
- Repeated `sqlite` `UPDATE` writes and disk I/O well beyond what the smart-contract-encoded rate limit intended.
- Rapid re-broadcast of new chunk versions to all replicating peers via `process_stacker_db_chunks`, amplifying the write into network-wide `StackerDBPushChunk` gossip traffic [9](#0-8) , consuming bandwidth/CPU on every replicating node in the network.
- Effective negation of the smart contract's write-frequency policy meant to bound the cost of maintaining a fresh, valid replica set.

This is a bounded compute/bandwidth DoS reachable from a small number of privileged-but-rate-limited writers turning into an unbounded-rate writer, consistent with the "bounded compute DoS on a read/write endpoint" and "network-wide propagation" impact classes.

### Likelihood Explanation
Any actor holding a slot's private key (a legitimate but supposedly-throttled StackerDB writer) can trivially exploit this: the check is simply absent from the code path, requiring no timing tricks, only signing increasing `slot_version` chunks as fast as possible and POSTing them to `/v2/stackerdb/.../chunks`, or pushing them via P2P `StackerDBPushChunk`. No race condition or edge case is needed — this is not conditional on any other defense failing.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `insert_chunk`, load the existing `SlotValidation.write_time` for the slot and reject the write with a new error (e.g., `net_error::TooFrequentWrite`) if `get_epoch_time_secs() < write_time + config.write_freq`. Apply the same check consistently to the P2P ingestion path (`validate_received_chunk` / `process_stacker_db_chunks`) so both write surfaces enforce the same contract-declared rate limit. Add negative tests asserting that rapid resubmission within `write_freq` is rejected via both the HTTP and P2P paths.

### Proof of Concept
1. Deploy/observe a StackerDB contract with `write-freq` set to, e.g., 600 (10 minutes) and `max-writes` set high.
2. Obtain (or be) the owner of slot `N` with private key `pk`.
3. Sign chunk version 1 with `pk`, POST to `/v2/stackerdb/<addr>/<contract>/chunks` — accepted per `test_request_ok` flow [10](#0-9) .
4. Immediately sign chunk version 2 with `pk` (no delay) and POST again.
5. Because `try_replace_chunk` never checks `write_time`/`write_freq`, only `slot_version > slot_validation.version`, the second write succeeds instantly despite violating the intended 600-second interval, and is re-broadcast to the network via `process_stacker_db_chunks` [9](#0-8) . This can be repeated as fast as version numbers and signatures can be generated, up to `max_writes`.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
