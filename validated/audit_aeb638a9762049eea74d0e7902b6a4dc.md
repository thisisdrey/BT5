## Analysis

The report describes an unbounded-loop DoS: a user-controlled list (`shareholders`) with no maximum size causes a fee-distribution function to iterate without bound, exhausting resources and blocking critical operations (`withdraw()`, `destroy()`).

The closest analog in Gitaly is the **proc-receive hook's non-atomic reference-update processing path**, which parses and then serially processes a fully user-controlled, unbounded list of reference updates supplied over the wire during an ordinary `git push`.

### Title
Unbounded reference-update list in the proc-receive hook causes per-reference subprocess/hook fan-out DoS - (File: internal/gitaly/hook/receivepack/receive_pack.go, internal/gitaly/hook/procreceive_handler.go)

### Summary
`NewProcReceiveHandler` reads an attacker/client-controlled number of reference updates from the proc-receive protocol stream in an unbounded loop, and `procReceiveHook`'s non-atomic branch then invokes a full update cycle (spawn `git update-ref`, invoke the update hook, invoke the HTTP-based custom hook) once **per reference**, with no cap on the number of references that can be pushed in one request.

### Finding Description
`NewProcReceiveHandler` reads reference updates off the client-controlled `stdin` stream in a `for scanner.Scan()` loop with no limit on the number of iterations, appending every parsed update to `updates`: [1](#0-0) 

That unbounded slice is later exposed via `ReferenceUpdates()`: [2](#0-1) 

`procReceiveHook` then branches on whether the push was atomic. For the (default) non-atomic case, it iterates over every single reference update and, for each one individually, calls `receivePackReferenceUpdates`: [3](#0-2) 

`receivePackReferenceUpdates` spawns a brand-new `git update-ref` process (`updateref.New`) and invokes `hookManager.UpdateHook` (which round-trips to the GitLab Rails internal API per `doc/object_quarantine.md`) — all per single reference, then commits: [4](#0-3) 

There is no maximum-reference-count check anywhere in this flow before the loop begins iterating, unlike other RPCs in the codebase which explicitly cap unbounded lists via a `limit` field (e.g. `ListBlobsRequest.limit`, `FindRefsByOIDRequest.limit`) or via `[[concurrency]]` request-level backpressure described in `doc/backpressure.md`: [5](#0-4) 

Because a `git push` can specify an arbitrarily large number of reference updates (proc-receive is negotiated on ordinary pushes when the corresponding hook is configured), a single push with a very large number of references causes Gitaly to spawn a proportionally large number of `git update-ref` subprocesses and make a proportional number of hook invocations (including Rails API calls) sequentially within the RPC handling goroutine.

### Impact Explanation
An ordinary user performing a single push with a very large number of reference updates can force the Gitaly node handling `PostReceivePack`/`SSHReceivePack` to spawn a very large number of Git subprocesses and issue a correspondingly large number of custom-hook/Rails calls in serial. This consumes CPU, memory, file descriptors, and goroutines on the Gitaly node for the duration of the request, and — because it happens within a single RPC's processing — can starve other concurrent RPCs on the same node/repository of Git-spawning resources, similar in effect to the referenced fee-splitter DoS where an unbounded loop blocks other critical operations.

### Likelihood Explanation
Reachable from an ordinary, unprivileged `git push` by any user permitted to push to a repository where proc-receive is exercised; no special privileges, no malicious peer/MITM assumptions, and no dependency on leaked tokens are required. The number of reference updates in the pktline stream is fully controlled by the pushing client and is not validated against any maximum before the per-reference processing loop runs.

### Recommendation
Enforce a sane maximum number of reference updates accepted by `NewProcReceiveHandler` (rejecting/erroring the push if exceeded), and/or batch the non-atomic update path so that `git update-ref`/hook invocations are not spawned individually per reference, mirroring the batching/limit patterns already used elsewhere in Gitaly's proto surface (e.g. `limit` fields, streaming with chunking, and the `[[concurrency]]` backpressure mechanism).

### Proof of Concept
1. Configure a repository with a proc-receive hook registered (per `internal/gitaly/hook/procreceive_registry.go`) and transactions enabled so `RegisterProcReceiveHook` is invoked.
2. As an ordinary user with push access, perform `git push` with a very large number (e.g. hundreds of thousands) of distinct branch ref updates in a single non-atomic proc-receive negotiation.
3. Observe that `NewProcReceiveHandler` accepts and buffers the entire unbounded list of updates [1](#0-0) , and `procReceiveHook`'s non-atomic loop subsequently spawns one `git update-ref` process and one update-hook invocation per reference [3](#0-2) , consuming Gitaly node resources proportionally to the number of references pushed, with no upper bound enforced.

func receivePackReferenceUpdates(
	ctx context.Context,
	cfg config.Cfg,
	req gitcmd.ReceivePackRequest,
	repo *localrepo.Repo,
	hookManager hook.Manager,
	updates []hook.ReferenceUpdate,
	stdout, stderr io.Writer,
) (returnedErr error) {
	hooksPayload, err := setupHooksPayloadEnv(ctx, cfg, req, repo, gitcmd.UpdateHook)
	if err != nil {
		return fmt.Errorf("creating hooks payload: %w", err)
	}

	updater, err := updateref.New(ctx, repo, updateref.WithNoDeref())
	if err != nil {
		return fmt.Errorf("spawning ref updater: %w", err)
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel ref updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	for _, update := range updates {
		if err := hookManager.UpdateHook(
			ctx,
			req.GetRepository(),
			update.Ref.String(),
			update.OldOID.String(),
			update.NewOID.String(),
			[]string{hooksPayload},
			stdout, stderr,
		); err != nil {
			return fmt.Errorf("running update hook: %w", err)
		}

		if err := updater.Update(update.Ref, update.NewOID, update.OldOID); err != nil {
			return fmt.Errorf("queueing ref to be updated: %w", err)
		}
	}

	if err := updater.Commit(); err != nil {
		return updateError{error: err}
	}

	return nil
}
