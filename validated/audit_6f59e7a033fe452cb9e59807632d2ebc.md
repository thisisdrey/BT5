### Title
Unprivileged `SetAccountIdContract` broadcaster can permanently hijack a legacy account's `AccountId → address` mapping during the one-time Turkish-locale migration - (File: `chainbase/src/main/java/org/tron/core/store/AccountIdIndexStore.java`, `actuator/src/main/java/org/tron/core/actuator/SetAccountIdActuator.java`, `framework/src/main/java/org/tron/core/db/api/MigrateTurkishKeyHelper.java`)

### Summary
`AccountIdIndexStore` normalizes all `accountId` lookups to `Locale.ROOT` lowercase, but legacy entries written under a Turkish/Azerbaijani JVM locale were stored under a different (dotless-ı) byte key. A one-time `MigrateTurkishKeyHelper.doWork()` migration reconciles these legacy keys into the ROOT-normalized key space, but only writes the ROOT key **if it is currently absent**. Any unprivileged account holder can call the permissionless `SetAccountIdContract` actuator to pre-register the ROOT-normalized `accountId` for a legacy Turkish-key account before the migration runs, causing the migration to skip overwriting that slot and instead permanently delete the legitimate legacy entry — effectively hijacking the `accountId → address` mapping for that account.

### Finding Description
`AccountIdIndexStore.has()`/`get()` always normalize the queried key to `Locale.ROOT` before checking the store: [1](#0-0) 

Because of this, `has()` cannot see a legacy record that was written under a Turkish-locale lowercase form (containing dotless-ı, U+0131) — it only matches ROOT-normalized keys. `SetAccountIdActuator.validate()` relies exclusively on `accountIdIndexStore.has(accountId)` to reject collisions: [2](#0-1) 

Any account owner can therefore submit a `SetAccountIdContract` transaction for an `accountId` string whose ROOT-lowercase form is the same as an existing, not-yet-migrated legacy (Turkish-locale) `accountId`, and it will pass validation and `execute()` will write straight into that ROOT key via `AccountIdIndexStore.put()`: [3](#0-2) 

When the one-time `MigrateTurkishKeyHelper.doWork()` migration subsequently runs (triggered once from `Manager` init/upgrade, guarded by the `DynamicPropertiesStore` "Turkish key migration done" flag), it only writes the ROOT-equivalent key **if it is empty**, and unconditionally deletes the original legacy key regardless of whether the write happened: [4](#0-3) 

This is architecturally identical to the reported Lens bug: a permissionless/whitelisted actor can perform an ordinary, individually-valid operation (`mintHandle` / `SetAccountIdContract`) that collides with pre-existing, not-yet-migrated legacy state, and the one-time migration logic (`batchMigrateProfiles` / `MigrateTurkishKeyHelper.doWork`) is not aware of and cannot recover from that collision — it silently drops/loses the legacy record instead of failing safely.

### Impact Explanation
After the migration runs, any resolver of `accountId` (e.g. `GetAccountByIdServlet`, `getAccountById` gRPC/HTTP API in `Wallet.java`) will permanently return the attacker's address instead of the legitimate legacy account's address for that `accountId`, since the legitimate record is deleted and the ROOT slot now holds the attacker's mapping. Any external system, wallet, or exchange that resolves an account by its human-readable `accountId` (rather than the raw address) to route a payment or verify identity will end up interacting with the attacker's address instead of the legitimate one — enabling misdirected funds/phishing and a permanent, unrecoverable corruption of the account-id index for the victim account (denial of correct resolution). This satisfies the "unauthorized account operation" / "permanent freezing/loss" bar since the legacy mapping cannot be restored (the original key is deleted).

### Likelihood Explanation
The attack requires only a single, ordinary signed transaction (`SetAccountIdContract`) from any account — no special privilege is required, unlike the Lens bug which required a whitelisted profile creator. The attacker needs knowledge of which legacy `accountId` strings exist under the Turkish-locale key form and must front-run the one-time migration (win the race before `MigrateTurkishKeyHelper.doWork()` executes, e.g., immediately following the hard-fork/version upgrade that introduces the migration but before the flag is set). This is a narrow timing window but fully attacker-triggerable and requires no compromise of any node, key, or consensus participant.

### Recommendation
Make `AccountIdIndexStore.has()` also check for legacy (non-ROOT-normalized) collisions before allowing `SetAccountIdActuator` to write a new mapping, or run the Turkish-key migration synchronously/atomically before the `SetAccountIdContract` actuator becomes reachable (e.g., gate `SetAccountIdActuator.execute()` behind the `isTurkishKeyMigrationDone` flag, or have the migration also scan and refuse to skip on conflicts, instead merging/rejecting such transactions until the legacy state is confirmed migrated).

### Proof of Concept
1. On a node/database containing a legacy `AccountIdIndexStore` entry written under a Turkish-locale key for `accountId = "JustDoIt"` (as exercised in `AccountIdIndexStoreTest.testKeysMigration`) [5](#0-4) , before `MigrateTurkishKeyHelper.doWork()` has executed:
2. Attacker submits a `SetAccountIdContract` transaction from their own account with `accountId = "JustDoIt"`. `SetAccountIdActuator.validate()` calls `accountIdIndexStore.has("JustDoIt")`, which normalizes to ROOT lowercase and finds no match (the legacy key is stored under the Turkish dotless-ı form), so validation passes. [6](#0-5) 
3. `execute()` writes the attacker's address under the ROOT-normalized key for `"justdoit"`. [7](#0-6) 
4. When the network later runs `MigrateTurkishKeyHelper.doWork()`, Phase 2 finds the legacy Turkish key for the same accountId, checks the ROOT key, sees it is non-empty (attacker's entry), skips writing over it, and deletes the legacy key anyway. [8](#0-7) 
5. The legitimate account's `accountId → address` mapping is now permanently lost; any subsequent lookup of `accountId = "JustDoIt"` resolves to the attacker's address.

    return ByteString

        .toByteArray();

  public void put(AccountCapsule accountCapsule) {
    byte[] lowerCaseAccountId = getLowerCaseAccountId(accountCapsule.getAccountId().toByteArray());
    super.put(lowerCaseAccountId, new BytesCapsule(accountCapsule.getAddress().toByteArray()));
  }

  public byte[] get(ByteString name) {
    BytesCapsule bytesCapsule = get(name.toByteArray());
    if (Objects.nonNull(bytesCapsule)) {
      return bytesCapsule.getData();
    }
    return null;
  }

  @Override
  public BytesCapsule get(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    if (ArrayUtils.isEmpty(value)) {
      return null;
    }
    return new BytesCapsule(value);
  }

  @Override
  public boolean has(byte[] key) {
    byte[] lowerCaseKey = getLowerCaseAccountId(key);
    byte[] value = revokingDB.getUnchecked(lowerCaseKey);
    return !ArrayUtils.isEmpty(value);
  }
