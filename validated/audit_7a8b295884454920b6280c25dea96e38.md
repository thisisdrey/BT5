### Title
Fixed-window stream throttling in `throttle_stream` allows boundary-straddling bursts of up to ~2x `max_streams_per_throttling_interval` - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`throttle_stream` enforces stream-rate limits using a fixed, non-overlapping window counter (`ConnectionStreamCounter`) that resets to zero once `STREAM_THROTTLING_INTERVAL` (100 ms) has elapsed since the last reset. Because the window boundary is anchored to when it was last reset rather than being a true sliding window, a client can open `max_streams_per_throttling_interval` streams right before a reset and another full batch immediately after, admitting close to double the configured budget within a short span straddling the boundary.

### Finding Description
`ConnectionStreamCounter::reset_throttling_params_if_needed` [1](#0-0)  only resets `stream_count` to 0 when `now - last_throttling_instant > STREAM_THROTTLING_INTERVAL`. `throttle_stream` then compares the (possibly stale) `stream_count` against `max_streams_per_throttling_interval` and only sleeps/throttles once that count is met or exceeded [2](#0-1) .

This is a classic fixed-window counter: it tracks "streams admitted since the last reset instant," not "streams admitted in the last `STREAM_THROTTLING_INTERVAL_MS`." Consequently, if an unstaked (or staked) client opens exactly `max_streams_per_throttling_interval` streams at time `t = window_end - ε` (just before the current window resets), none of them are throttled because the check only fires once the count is *reached*, and the count hasn't yet reset. Immediately after the window flips at `t = window_end`, `reset_throttling_params_if_needed` zeroes the counter, and the same client can immediately open another full batch of `max_streams_per_throttling_interval` streams before the window's throttling counter would again hit the cap. In a 2ε-wide slice of wall-clock time (which can be made arbitrarily small relative to `STREAM_THROTTLING_INTERVAL_MS`), the client is permitted to open close to `2 * max_streams_per_throttling_interval` streams, i.e., roughly double the intended per-window budget in any sliding window centered on the boundary.

The reset is per-`ConnectionStreamCounter`, meaning it's scoped per connection rather than tracking a true rolling admission count, so no mechanism in this function (or its caller) checks the admitted-stream count over an arbitrary sliding window—only over the fixed window defined by `last_throttling_instant`.

### Impact Explanation
This lets an unstaked (or even staked) attacker double their effective stream throughput for short bursts by timing new streams to straddle throttling-interval boundaries, letting them consume disproportionate TPU stream-processing capacity relative to the configured `max_streams_per_throttling_interval` / EMA-derived staked-vs-unstaked capacity split computed in `available_load_capacity_in_throttling_duration` [3](#0-2) . This falls under QoS/rate-limit evasion: the invariant that a peer cannot exceed the throttling budget via timing is violated, though the effect is bounded (at most ~2x for a single boundary crossing, not unbounded) and self-resolves once outside the boundary window.

### Likelihood Explanation
This requires no special privileges—any unstaked remote client opening a QUIC connection to the TPU port can time its stream opens relative to wall-clock boundaries of `STREAM_THROTTLING_INTERVAL_MS` (100 ms), which is a fixed, publicly known constant [4](#0-3) . Because `last_throttling_instant` is deterministic (relative to when the connection was created/last throttled) and the interval is fixed and public, an attacker can straightforwardly predict window boundaries and script bursts around them, making this readily reproducible.

### Recommendation
Replace the fixed-window reset logic in `ConnectionStreamCounter`/`throttle_stream` with a sliding-window or token-bucket algorithm (e.g., track timestamps of recent admissions and only count those within the last `STREAM_THROTTLING_INTERVAL_MS`, or use a leaky/token bucket that refills continuously) so that the admitted-stream count over any rolling `STREAM_THROTTLING_INTERVAL_MS` window—not just the fixed window since last reset—stays within `max_streams_per_throttling_interval`.

### Proof of Concept
Add an integration/fuzz test in `streamer/src/nonblocking/stream_throttle.rs` under `#[cfg(test)]`:

```rust
#[tokio::test]
async fn test_boundary_burst_exceeds_budget_in_sliding_window() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams = 10u64;
    let remote_addr = "127.0.0.1:1234".parse().unwrap();

    // Simulate max_streams admissions right before window reset.
    for _ in 0..max_streams {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
    }
    // Force the window to look like it's about to expire.
    {
        let mut instant = counter.last_throttling_instant.write().unwrap();
        *instant = tokio::time::Instant::now() - STREAM_THROTTLING_INTERVAL + Duration::from_millis(1);
    }

    // Sleep past the boundary by a tiny amount, triggering reset.
    tokio::time::sleep(Duration::from_millis(2)).await;

    let mut admitted_in_sliding_window = max_streams; // already admitted before boundary
    for _ in 0..max_streams {
        throttle_stream(&stats, ConnectionPeerType::Unstaked, remote_addr, &counter, max_streams).await;
        admitted_in_sliding_window += 1;
    }

    // Assert: total admitted within ~STREAM_THROTTLING_INTERVAL_MS window should not
    // exceed max_streams, but the fixed-window implementation allows ~2x.
    assert!(
        admitted_in_sliding_window <= max_streams,
        "admitted {admitted_in_sliding_window} streams in one throttling interval, expected <= {max_streams}"
    );
}
```

Expected result with the current implementation: the assertion fails, admitting up to `2 * max_streams` within a window narrower than `STREAM_THROTTLING_INTERVAL_MS`, confirming the boundary-burst evasion.

```rust
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }
```

```rust
pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
```
