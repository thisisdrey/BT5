### Title
StackerDB chunk signatures are not bound to the StackerDB contract or a reconfiguration epoch, enabling replay of stale signed chunks after a slot signer change-and-return - (File: `libstackerdb/src/libstackerdb.rs`, `stackslib/src/net/stackerdb/db.rs`)

### Summary
`SlotMetadata`/`StackerDBChunkData` signatures only commit to `(slot_id, slot_version, data_hash)` — never to the StackerDB's smart-contract identifier or any epoch/cycle-scoped nonce. The only thing that prevents replay of an old, validly-signed chunk is the monotonically increasing per-slot `version` counter tracked in the local `chunks` table. That counter is reset to `0` whenever `reconfigure_stackerdb` observes that a slot's signer address has changed — but if the same signer address is later reassigned to the same `slot_id` (e.g., across reward-cycle StackerDB reconfigurations), the version resets to 0 again for that "return." At that point, any previously valid signed chunk from that signer for that slot ID — captured off the wire earlier — satisfies `version > 0` and passes signature verification, so it is accepted and re-broadcast as if it were fresh data. This mirrors the Ambire bug class: state that gates replay (`scheduledRecoveries` / here, per-slot `version`) gets cleared by an unrelated administrative event (cancellation / here, signer reassignment), while the signed payload that drove the original state transition remains eternally replayable because the signature carries no binding to the specific context (nonce / contract ID) that should have invalidated it.

This digest — and therefore the signature produced by `sign()` and checked by `verify()` — only covers `slot_id`, `slot_version`, and `data_hash`. It never includes the `QualifiedContractIdentifier` of the StackerDB, nor any value tied to a particular reconfiguration/reward-cycle epoch: [2](#0-1) 

The only anti-replay control is the locally-tracked, per-slot `version` (a lamport clock), enforced in `try_replace_chunk`: [3](#0-2) 
and in the P2P path's `validate_received_chunk`, which checks the same freshness invariant against `expected_versions`: [4](#0-3) 

Crucially, `reconfigure_stackerdb` resets a slot's version back to `NO_VERSION` (0) whenever the signer assigned to that `slot_id` differs from the slot's previous signer — but leaves it untouched (`continue`) when the signer is unchanged: [5](#0-4) 

This "unchanged signer → don't reset" logic is precisely what normally prevents replay across reconfigurations (the version keeps climbing so old signed chunks remain stale forever). But it also means the *reset* path is a state-clearing event, structurally identical to Ambire's cancellation clearing `scheduledRecoveries`: any signer who is reassigned away from a slot and then reassigned back to that same `slot_id` in a later reconfiguration will find their slot's version reset to 0 twice, and at that second reset, an attacker (or the signer's own old cached message, or anyone who observed the original broadcast/chunk on the wire) can resubmit the old `(slot_id, slot_version, sig, data)` tuple. Since the signature is valid forever (no contract/epoch binding) and `slot_version > 0` now again satisfies the freshness check, the stale chunk is accepted and re-broadcast via `process_stacker_db_chunks`: [6](#0-5) 

### Impact Explanation
This allows an unauthenticated party (anyone who saved a previously broadcast, validly-signed StackerDB chunk) to reinject stale signer data into a StackerDB replica after the affected slot's version has been reset by an unrelated signer-set change, causing the node to accept and network-wide propagate forged/stale data as if it were fresh (`accepted: true` ack, followed by `broadcast_message`). For signer-message StackerDBs (e.g., `.signers-*` contracts used for Nakamoto block responses), this can present a stale `BlockResponse`/signature-share message as canonical current signer state, matching the "network-wide propagation of forged data" / "serving non-canonical state as canonical" impact tier.

### Likelihood Explanation
Exploitation requires: (1) capturing a signer's previously valid signed chunk from an earlier assignment to a given `slot_id`, and (2) that same signer address being reassigned away and then back to the identical `slot_id` in a later StackerDB reconfiguration (plausible given deterministic/sorted slot allocation across reward cycles, especially for smaller signer sets or during cycle-boundary churn). This is a remote, unprivileged replay requiring no secret key material — only a stored copy of an old signed chunk and normal chunk-submission access (HTTP `POST /v2/stackerdb/.../chunks` or P2P `StackerDBPushChunk`).

### Recommendation
Bind the `SlotMetadata`/`StackerDBChunkData` signature to the StackerDB's contract identifier (and ideally an epoch/reconfiguration nonce) in `auth_digest()`, so a chunk signed for one StackerDB/epoch cannot be replayed into another. Alternatively, persist a monotonically-increasing per-slot "epoch counter" that is incremented (never reset to a previously-used value) on every `reconfigure_stackerdb` signer reassignment, and require signed chunks to also commit to that epoch value.

### Proof of Concept
1. Signer `S` is assigned `slot_id=5` in StackerDB contract `C` for reward cycle `N`; `S` signs and submits chunk `(slot_id=5, version=1, data=D)`, which is accepted and broadcast (captured by an observer/attacker off the wire).
2. At the next reconfiguration, `reconfigure_stackerdb` reassigns `slot_id=5` to a different signer `S2` (`existing_validation.signer != S2` branch), resetting the slot's version to `NO_VERSION` per [5](#0-4) .
3. At a subsequent reconfiguration, `S` is reassigned back to `slot_id=5` (again `existing_validation.signer != S` at that point, since it currently belongs to `S2`), resetting the version to `NO_VERSION` again.
4. The attacker replays the originally captured chunk `(slot_id=5, version=1, sig, data=D)` via `POST /v2/stackerdb/.../chunks` or a P2P `StackerDBPushChunk`. `slot_desc.verify(&slot_validation.signer)` succeeds (signature only binds slot_id/version/data_hash, still recovers to `S`), and `slot_desc.slot_version (1) > slot_validation.version (0)` passes the staleness check in `try_replace_chunk`, so the stale chunk is stored and re-broadcast to the network as fresh data.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
