### Title
Unauthenticated attachment content is bound to attacker-chosen hash due to missing `attachment.hash() == AttachmentRequest.content_hash` check in `extend_with_attachments` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When the Atlas downloader processes a `GetAttachment` HTTP response, `AttachmentsBatchStateContext::extend_with_attachments` decodes the response and inserts the returned `Attachment` into `self.attachments` without ever comparing `attachment.hash()` to the `content_hash` that was actually requested (`AttachmentRequest.content_hash`). The attachment is later stored in `AtlasDB` keyed by its self-reported hash, allowing a malicious/compromised peer picked from `get_prioritized_attachments_requests` to bind arbitrary bytes to any BNS-committed hash it chooses.

### Finding Description
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest{ sources, content_hash, ... }` for a specific `content_hash` that the node is looking for, based on peers whose gossiped inventory bit claims to have it [1](#0-0) . The state machine's `DownloadingAttachment` state dispatches the HTTP request and, on success, calls `context.extend_with_attachments(results)` [2](#0-1) .

Inside `extend_with_attachments`, the code iterates `(request, response)` pairs, decodes the response via `decode_atlas_get_attachment()`, and inserts `response.attachment` into `self.attachments` — the original `request.content_hash` (the value that was actually asked for) is never read or compared to `response.attachment.hash()`: [3](#0-2) 

Subsequently, in `AttachmentsDownloader::run`, the accepted `Attachment` objects are drained and persisted using their own self-reported hash (`attachment.hash()`), not the original request's `content_hash`: [4](#0-3) 

Because `attachment.hash()` is derived purely from attacker-supplied `content` bytes (`Attachment::hash = Hash160::from_data(content)`), and no code anywhere in this path checks `attachment.hash() == request.content_hash`, a malicious peer can respond to a `GetAttachment` request for hash `H_real` with arbitrary `content` bytes producing a different hash `H_forged`. The forged attachment gets inserted into `AtlasDB` under `H_forged` via `insert_instantiated_attachment`, and if any legitimate `AttachmentInstance` later resolves against `H_forged` (or if the peer's inventory falsely claims to have `H_real` and the requester keys its lookup only by that response), the mismatch bypasses the intended commitment binding entirely. The core issue is architectural: the request's target hash is discarded after use and never re-validated against the actually-returned content before it's treated as a trusted keyed record.

### Impact Explanation
An attacker running a normal outbound-reachable peer node can serve arbitrary attachment bytes in response to `GetAttachment` requests. Since the returned `Attachment` is stored keyed by its own hash rather than validated against the requested hash, this allows unauthenticated writes of attacker-chosen data into a node's `AtlasDB`, and later this same node will serve that stored content to every future requester of that (now falsely populated) hash via `RPCGetAttachmentRequestHandler`/`find_attachment`. This can propagate forged content across the network as it is re-gossiped/served to other peers, matching "Critical: unauthenticated write to state + network-wide propagation of forged data."

### Likelihood Explanation
Any remote unprivileged peer that a node connects to for Atlas sync (an outbound sync peer, obtainable simply by running a Stacks node and being selected via `get_outbound_sync_peers`) can serve this response. The attacker needs no secret, no signature, and no elevated role — just to answer an HTTP `GetAttachment` request with a 200 status and arbitrary bytes. This is trivially repeatable per attachment request cycle.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (stackslib/src/net/atlas/download.rs), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; on mismatch, treat it as a failed/faulty response (bump `report.bump_failed_requests()`, and consider registering the peer as faulty) rather than silently discarding the check.

### Proof of Concept
Rust test in `stackslib::net::atlas::download` (or a new test module):
1. Construct an `AttachmentRequest` with `content_hash = Hash160::from_data(b"real")` and a mock peer URL.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains this request paired with a `StacksHttpResponse` decoding (via a stub of `decode_atlas_get_attachment`) to `GetAttachmentResponse { attachment: Attachment { content: b"forged".to_vec() } }`.
3. Call `AttachmentsBatchStateContext::extend_with_attachments(context, &mut results)`.
4. Drain `context.attachments` and call `atlasdb.insert_instantiated_attachment(&attachment)` as done in `AttachmentsDownloader::run` (stackslib/src/net/atlas/download.rs lines 153-169).
5. Assert `atlasdb.find_attachment(&Hash160::from_data(b"forged")).unwrap() == Some(attachment)` while `atlasdb.find_attachment(&Hash160::from_data(b"real"))` returns `None` — proving the originally requested hash `content_hash` was never checked against the delivered content, and forged data was accepted and stored.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
