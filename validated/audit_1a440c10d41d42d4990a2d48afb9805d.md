### Title
Unsafe floating-point Bancor-formula math in TRC10 Exchange enables value-extraction via precision drift - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The TRC10 Bancor-style Exchange (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) reachable by any unprivileged account, computes swap/inject/withdraw amounts using the default `ExchangeProcessor`, which relies on IEEE-754 `double` arithmetic (`Math.pow`, division) rather than exact integer/`BigDecimal` math. This is the same bug class as the xToken/xSNX incident referenced in the report: an accounting/valuation routine for a pooled asset that is vulnerable to precision loss/rounding that a caller can repeatedly exploit to extract value disproportionate to what was deposited, because the "hardened", overflow/precision-safe path (`SafeExchangeProcessor`, `BigDecimal`-based `ExchangeWithdrawActuator` checks) is gated behind the `allowHardenExchangeCalculation` dynamic property and is not the default execution path.

### Finding Description
`ExchangeCapsule.transaction()` [1](#0-0)  selects between two `Processor` implementations depending on the `hardenedCalc` flag: the legacy `ExchangeProcessor` (floating-point) or `SafeExchangeProcessor` (BigDecimal). `AbstractExchangeActuator.allowHarden()` reads this flag straight from `DynamicPropertiesStore.allowHardenExchangeCalculation()` [2](#0-1) , meaning the safer math path is only used when SRs vote it on via a proposal (`ProposalUtil`/`ProposalService`), while the default production path uses `ExchangeProcessor`.

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the constant-virtual-supply Bancor curve entirely with `double` and `Math.pow` [3](#0-2) . Any account can call `ExchangeTransactionActuator` repeatedly (buy/sell in tiny or crafted quantities) to interact with this floating-point curve; because IEEE-754 doubles lose precision as the ratio `quant/newBalance` becomes very small or very large, and because the result is truncated via a lossy `(long) issuedSupply` cast rather than a mathematically exact `BigDecimal` rounding rule, rounding is not guaranteed to be conservative in the pool's favor on every call. This is structurally the same defect class flagged in the xToken/xSNX report: value/exchange-rate accounting for a pooled asset that is derived from an approximate/manipulable calculation rather than an exact one, exploitable purely by an ordinary market participant issuing transactions against the pool — no privileged role is required.

### Impact Explanation
Exploiting accumulated rounding/precision drift in the double-based curve lets an attacker drain TRX/TRC10 balances from the Exchange pool (held in escrow by the exchange's creator/committer) over repeated `ExchangeTransactionContract` calls, or obtain an `anotherTokenQuant` more favorable than the exact Bancor formula would allow, directly causing theft of pooled funds — a concrete, unauthorized transfer of value out of the exchange pool, which the accepted-impact criteria call out ("unauthorized account operation, theft ... of funds, unbacked balance").

### Likelihood Explanation
Any TRON account can hold TRX/TRC10 tokens and submit `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions with attacker-chosen `quant`/`expected` values via the standard broadcast path — no special permission, node operator role, or witness/SR privilege is needed, matching the "unprivileged transaction broadcaster" reachability requirement. The vulnerable path (`ExchangeProcessor`, floating-point) is the *default* unless SRs have activated `allowHardenExchangeCalculation`, so exploitability depends on the live value of that dynamic property on a given deployment.

### Recommendation
Make the `SafeExchangeProcessor` (BigDecimal-based, exact rounding) the unconditional processor for all Exchange calculations instead of an opt-in behind `allowHardenExchangeCalculation`, or retroactively force the flag on for all pools by chain hard-fork, and add invariant checks (e.g., k = firstTokenBalance * secondTokenBalance must never decrease after any swap net of fees) inside `ExchangeCapsule.transaction()` to reject any calculation whose result would leave the pool in an inconsistent state regardless of which `Processor` computed it.

### Proof of Concept
Not executable without a live database/test harness; the mechanism (floating-point Bancor formula truncation being the default path unless a governance proposal activates the safe/BigDecimal path) is demonstrated in the existing test `hardenedSuccessExchangeTransaction` / `hardenedExecuteOverflowThrowsArithmeticException` in `ExchangeTransactionActuatorTest.java` [4](#0-3) , which shows the two code paths (`ExchangeProcessor` vs `SafeExchangeProcessor`) yield different overflow/precision behavior and that the safe path is only exercised when `saveAllowHardenExchangeCalculation(1)` is explicitly set.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  /**
   * Hardened mode: ExchangeTransaction succeeds and routes through SafeExchangeProcessor.

  @Test
  public void hardenedSuccessExchangeTransaction() {
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);
    dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    InitExchangeSameTokenNameActive();
    long exchangeId = 1;
    String tokenId = "_";
    long quant = 100_000_000L;

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_SECOND);
    AccountCapsule before = dbManager.getAccountStore().get(ownerAddress);
    long initialBalance = before.getBalance();

    ExchangeTransactionActuator actuator = new ExchangeTransactionActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_SECOND, exchangeId, tokenId, quant, 1));

    TransactionResultCapsule ret = new TransactionResultCapsule();
    try {
      actuator.validate();
      actuator.execute(ret);
      Assert.assertEquals(code.SUCESS, ret.getInstance().getRet());
      AccountCapsule after = dbManager.getAccountStore().get(ownerAddress);
      Assert.assertEquals(initialBalance - quant, after.getBalance());
      Assert.assertTrue("Hardened tx must produce positive received amount",
          ret.getExchangeReceivedAmount() > 0);
    } catch (Exception e) {
      Assert.fail("Hardened transaction must succeed: " + e.getMessage());
    } finally {
      dbManager.getExchangeStore().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeStore().delete(ByteArray.fromLong(2L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(2L));
      dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    }
  }
