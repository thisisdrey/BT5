### Title
Unauthenticated Relay Address Confusion in `handleCreateRelayRequest` Allows Remote Relay-State Poisoning - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` (in `relay_manager.go`) trusts the `RelayFromAddr`/`RelayToAddr` fields carried inside an attacker-reachable `NebulaControl` message body without verifying that the claimed "from" address actually corresponds to the authenticated identity (`h.vpnAddrs`, derived from the peer's certificate during the handshake) of the host that sent the message. This mirrors the `TeaVaultAmbient.executeSwap` bug class: a caller-supplied address/parameter is accepted and acted upon without validating it against a trusted, authoritative source, letting a privileged-but-untrustworthy actor manipulate protocol state using an arbitrary value it was never authorized to assert.

### Finding Description
`HandleControlMsg` unmarshals the incoming `NebulaControl` message and only checks that `RelayFromAddr`/`RelayToAddr` are non-nil before dispatching to `handleCreateRelayRequest`: [1](#0-0) 

Inside `handleCreateRelayRequest`, `from` and `target` are decoded directly from the attacker-controlled message fields: [2](#0-1) 

The only identity check performed is that `from` is not one of *my* own addresses (`f.myVpnAddrsTable.Contains(from)`); there is no check that `from` matches `h.vpnAddrs` — the VPN address(es) that were actually cryptographically bound to `h` during the handshake (see `validatePeerCert` in `handshake_manager.go`, which is the only place that ties an authenticated identity to a `HostInfo`) [3](#0-2) . Because of this gap, the terminal-relay branch installs relay state keyed by the caller-asserted `from` value rather than the authenticated sender: [4](#0-3) 

`AddRelay` then stores this attacker-chosen address as `Relay.PeerAddr`, which subsequently drives real data-plane forwarding decisions in `handleOutsideRelayPacket` (`f.hostMap.QueryVpnAddrsRelayFor(hostinfo.vpnAddrs, relay.PeerAddr)`), i.e. the relay/forwarding routing table is populated from a value nobody has attested to via a certificate: [5](#0-4) 

This is directly analogous to the report's core flaw: an address parameter supplied by a party that holds some legitimate protocol privilege (the pool manager / here, any already-handshaked peer that can send a `Control` message) is accepted and used to drive high-impact state (fund transfer / relay routing) without validating it against the actual, cryptographically-authenticated principal.

### Impact Explanation
An already-connected (but otherwise unprivileged/malicious) peer can send a `CreateRelayRequest` claiming an arbitrary `RelayFromAddr` that does not belong to its own certificate identity. This poisons the relay-routing state (`RelayState.relayForByAddr` / `hostMap.Relays`) on the receiving/relay node, associating the attacker's tunnel session with an address it does not own. Depending on how relay lookups are subsequently consumed (`QueryVpnAddrsRelayFor`, `SendVia`), this can misdirect or intercept relayed traffic intended for a legitimate third-party VPN address, constituting remote relay/routing state poisoning — one of the accepted impact classes (remote state poisoning).

### Likelihood Explanation
Any node that can complete a handshake with the target (which, per Nebula's trust model, only requires a CA-signed certificate for its *own* identity, not for the address it claims in `RelayFromAddr`) can send this control message. No additional privilege beyond an established tunnel is required, making this reachable by any authenticated-but-otherwise-unprivileged peer — consistent with "no CA-signed certificate for the target address" reachability required by the rules.

### Recommendation
In `handleCreateRelayRequest` (and `handleCreateRelayResponse`), validate that the `from` (initiator) address asserted in the `NebulaControl` message is actually contained in `h.vpnAddrs` — the addresses bound to `h`'s certificate at handshake time — before creating or updating any `RelayState`/`hostMap.Relays` entry. Reject the message if the claimed address is not among the sender's authenticated VPN addresses, the same way `handleHostUpdateNotification` already checks `detailsVpnAddr` against `fromVpnAddrs` [6](#0-5) .

### Proof of Concept
1. Node `M` (malicious) completes a normal handshake with relay node `R`, obtaining a valid `HostInfo` `h` with `h.vpnAddrs = [M_addr]`.
2. `M` sends a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: V_addr (victim, not M), RelayToAddr: R_addr}` over its authenticated tunnel to `R`.
3. `R.handleCreateRelayRequest` decodes `from = V_addr`, `target = R_addr`; since `target == R`'s own address and `from != R`'s own address, it proceeds to `AddRelay(..., h, hostMap, from=V_addr, ..., TerminalType, Established)`, installing `h`'s relay state as if `M` were relaying on behalf of `V_addr`, despite `M` never proving it controls `V_addr`.
4. This state can now influence relay-based forwarding/routing decisions attributed to `V_addr` on `R`, without `V_addr`'s certificate ever being presented to `R` for this purpose.

Note: I could not fully trace every downstream consumer of `Relay.PeerAddr`/`RelayState` in this session (e.g., whether an additional cert check exists later in the forwarding path that would fully neutralize the poisoning) — the index may not contain every code path, so a full-repository review via a Devin session is recommended to confirm the exact blast radius before treating this as fully validated.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
