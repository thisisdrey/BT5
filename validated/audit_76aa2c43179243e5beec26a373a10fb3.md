### Title
Leftover `YieldIdToDataId`/`DataIdToYieldId` trie entries are not cleared on account deletion, allowing state poisoning across account recreation - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` (core/store/src/utils/mod.rs:505-575) clears `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and contract data for a deleted account, but does not clear the promise-yield bookkeeping keys `TrieKey::YieldIdToDataId` / `TrieKey::DataIdToYieldId` that `create_promise_yield_receipt_with_id` (runtime/runtime/src/ext.rs:371-400) writes via `set_yield_id_mapping`. Because these keys are namespaced only by `account_id` + caller-chosen `yield_id`, they survive `DeleteAccount` and become visible again if the same account name is later recreated via `CreateAccount`.

### Finding Description
`create_promise_yield_receipt_with_id` first checks `has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)` (runtime/runtime/src/ext.rs:378) and, if it finds an existing mapping, returns `Ok(None)` without creating a new receipt [1](#0-0) . If no mapping exists, it writes a bidirectional mapping via `set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id)` keyed only by the account id and the caller-supplied `yield_id`.

`remove_account`, invoked when an account is deleted, removes the `Account`, `ContractCode`, access keys/gas keys, and contract data trie entries, but never touches the `YieldIdToDataId`/`DataIdToYieldId` columns [2](#0-1) . Since the trie key encodes only the account name (not a per-incarnation nonce), the mapping persists in the trie state after `DeleteAccount` and is still present under that account name if a new account is later created with the identical name via `CreateAccount`.

Attack flow:
1. Account `victim.near` calls its own deployed contract, which invokes `promise_yield_create_with_id` with a fixed `yield_id` (a value the attacker controls). This writes `YieldIdToDataId`/`DataIdToYieldId` entries for `victim.near`.
2. `victim.near` submits `DeleteAccountAction`, removing the account but leaving the yield-id mapping keys in the trie.
3. Some other party (whoever is authorized to create `victim.near`, e.g. a parent/registrar account) submits `CreateAccount` to recreate `victim.near`.
4. The new owner's contract calls `promise_yield_create_with_id` with the same `yield_id` value. `has_yield_id_mapping` finds the stale entry still in state and the call silently returns `None`, blocking creation of that particular yield for the new (unrelated) account owner.

This is a violation of the expected invariant that a freshly created account starts with clean state - no code path re-initializes or purges promise-yield mappings on account creation, and `remove_account` is the only cleanup point for account-scoped keys but misses this pair of columns.

### Impact Explanation
The impact is scoped exactly as described in the question: a Denial-of-Service / state-corruption effect limited to a specific `yield_id` value inherited across an account-name recreation. It does not cause fund loss, double-spend, or consensus divergence, because `yield_id` values are chosen by the calling contract and colliding on a specific value requires the new owner's contract to independently reuse the exact same `yield_id` the previous owner used (most plausible when the same or similar contract code is redeployed to the recreated account, e.g. in account-migration or account-name-reuse scenarios common on NEAR). This maps to a narrow "availability / state-hygiene" bug rather than a funds-impacting bounty category.

### Likelihood Explanation
Preconditions: the attacker must control (or be) the account being deleted and must know/choose the specific `yield_id` that will later collide with the recreated account's usage; recreation of the exact same account name is only possible by whoever is authorized to submit `CreateAccount` for that name (e.g., the parent account for subaccounts, or the registrar for top-level names) - this is not always available to an arbitrary attacker for a top-level name like `victim.near`, but it is easily attacker-controlled for subaccounts under the attacker's own namespace, and it is entirely self-inflicted here (the "victim" is whoever reuses the account name later, not the deleting party). Cost to the attacker is a normal function call, storage staking cost, and a `DeleteAccount` transaction - all cheap and repeatable. The scenario is deterministic and fully reproducible in a unit/integration test.

### Recommendation
Extend `remove_account` in core/store/src/utils/mod.rs to also enumerate and remove all `TrieKey::YieldIdToDataId`, `TrieKey::DataIdToYieldId`, `TrieKey::PromiseYieldIndices`, `TrieKey::PromiseYieldTimeout`, and `TrieKey::PromiseYieldStatus` entries scoped to the account being deleted (via prefix iteration similar to the existing access-key/contract-data cleanup loops), ensuring account deletion fully purges promise-yield state before the account name can be reused.

### Proof of Concept
Integration test plan (test-loop or runtime `apply.rs` style):
1. Create account `victim.near`, fund it, deploy a test contract.
2. Have `victim.near` call `promise_yield_create_with_id` with a fixed `yield_id = X`, commit the block, and assert `has_yield_id_mapping(trie, "victim.near", X) == true`.
3. Submit `DeleteAccountAction` for `victim.near` (beneficiary any other account), commit.
4. Assert `has_yield_id_mapping(trie, "victim.near", X)` is still `true` immediately after deletion (demonstrating the leak) even though `get_account(trie, "victim.near")` returns `None`.
5. Submit `CreateAccountAction` to recreate `victim.near` from an authorized parent/registrar account, commit.
6. Assert `has_yield_id_mapping(trie, "victim.near", X) == true` before the new owner ever calls `promise_yield_create_with_id`, proving the poisoned state was inherited.
7. Have the new `victim.near` contract call `promise_yield_create_with_id` with the same `yield_id = X` and assert it returns `None`/blocked, confirming the DoS.

```rust
    fn create_promise_yield_receipt_with_id(
        &mut self,
        receiver_id: AccountId,
        user_yield_id: YieldId,
    ) -> Result<Option<(ReceiptIndex, CryptoHash)>, VMLogicError> {
        // Check for duplicate yield_id in trie. TrieUpdate also reflects writes from earlier
        // calls within the same function call, so this also catches in-transaction duplicates.
        if has_yield_id_mapping(self.trie_update, &receiver_id, user_yield_id)
            .map_err(wrap_storage_error)?
        {
            return Ok(None);
        }

        let input_data_id = self.generate_data_id();

        // Store bidirectional yield_id <-> data_id mappings
        set_yield_id_mapping(&mut self.trie_update, &receiver_id, user_yield_id, input_data_id);

        let receipt_index =
            self.receipt_manager.create_promise_yield_receipt(input_data_id, receiver_id.clone());

        set_promise_yield_status(
            &mut self.trie_update,
            &receiver_id,
            input_data_id,
            PromiseYieldStatus::Yielded,
        );

        Ok(Some((receipt_index, input_data_id)))
    }
```

```rust
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
```
