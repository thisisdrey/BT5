### Title
Raw git stderr (containing embedded remote-URL credentials) is returned unsanitized in the FetchRemote gRPC error, bypassing all URL-credential filtering - (File: internal/gitaly/service/repository/fetch_remote.go)

### Summary
`fetchRemoteAtomic` in `internal/gitaly/service/repository/fetch_remote.go` embeds the raw `git-fetch` stderr directly into the gRPC error returned to the caller via `structerr.NewInternal("fetch remote: %q: %w", errMsg, err)`, without ever passing it through any URL-credential sanitizer. The `hostPattern` regex bypass concerns raised for `internal/log/url_sanitizer.go` and `internal/helper/security.go` are moot for this path because neither sanitizer is even invoked here - the credential leak does not depend on a regex edge case at all.

### Finding Description
An attacker who owns a project can call `FetchRemote` with `RemoteParams.Url` pointing at a server they control (or a URL containing credentials belonging to another party, e.g. a stored/shared mirror credential). When `git fetch` fails, `git` frequently writes the full URL - including embedded userinfo (`user:password@`) - into its stderr, for example in "unable to access 'https://user:password@host/repo.git/'" style fatal messages.

The relevant code path: [1](#0-0) 

This is the only sanitization-relevant point in the flow, and it performs none. Compare this to `internal/command/command.go`'s `logProcessComplete`, which does route the corresponding `args`/`error` log fields through `logrus`, where `URLSanitizerHook.Fire` in `internal/log/url_sanitizer.go` scrubs matching credentials from **log output**: [2](#0-1) 

Critically, that hook only fires on `logrus.Entry` objects consumed by Gitaly's own logger — it has no relationship to the `error` value returned by the RPC handler to the gRPC caller. The value built by `structerr.NewInternal` in `fetch_remote.go` is returned straight up the call stack to `FetchRemote`'s response and becomes the gRPC status message the caller receives, completely independent of the logging pipeline and its sanitizer. `internal/helper/security.go`'s `SanitizeString`/`SanitizeError` (which do have a stricter, scheme-mandatory `hostPattern`) are also never called anywhere in this code path.

So regardless of whether `hostPattern` can be evaded via percent-encoding tricks, IPv6 brackets, or a missing `scheme://` prefix, the returned RPC error is not filtered by any sanitizer in the first place — the described regex-bypass mechanism is a secondary/irrelevant concern compared to the outright absence of sanitization on the returned error value.

### Impact Explanation
An attacker triggering `FetchRemote` (or via `CreateRepositoryFromURL`/`UpdateRemoteMirror`, which follow the analogous "spawn git against attacker-supplied URL, propagate stderr into structerr" pattern) can force a fetch failure and receive the raw git stderr — potentially containing credentials embedded in the remote URL — directly in the gRPC error message returned to their own client. This matches the "Credential disclosure" bounty impact class: secrets that should never reach a requester (e.g., mirror credentials configured by a more privileged user/group, or a resolved-address/authorization-header value) can be read back by the low-privileged caller who triggered the RPC.

### Likelihood Explanation
The precondition is simply project ownership (to invoke `FetchRemote`/mirroring RPCs) and control of, or knowledge of, a URL whose failure mode causes `git` to echo the full URL to stderr — a very common and easily reproducible git behavior for HTTP(S) authentication failures. No admin privileges, MITM, or configuration change is required; this is reachable through the default, unmodified RPC surface every time a fetch against a URL with embedded credentials fails.

### Recommendation
Sanitize `errMsg`/`err` in `fetch_remote.go` (and the equivalent locations in `create_repository_from_url.go`, `update_remote_mirror`-related code) with `helper.SanitizeError`/`helper.SanitizeString` before embedding them into `structerr.NewInternal`, e.g.:
```go
if errMsg != "" {
    return false, false, structerr.NewInternal("fetch remote: %q: %w", helper.SanitizeString(errMsg), err)
}
```
Additionally, fix `internal/helper/security.go`'s `hostPattern` to make the scheme optional (matching `internal/log/url_sanitizer.go`'s pattern) so that scheme-less URLs are also redacted, and audit all other RPC handlers that embed subprocess stderr directly into returned errors for the same gap.

### Proof of Concept
```go
func TestFetchRemote_CredentialLeakInError(t *testing.T) {
    ctx := testhelper.Context(t)
    cfg, repoProto, _ := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg, cfg.SocketPath)

    // URL pointing to a host that will reject/fail auth and echo the URL in stderr.
    maliciousURL := "https://attacker:s3cr3t-p4ss@127.0.0.1:1/nonexistent.git"

    _, err := client.FetchRemote(ctx, &gitalypb.FetchRemoteRequest{
        Repository: repoProto,
        RemoteParams: &gitalypb.RemoteParams{
            Url: maliciousURL,
        },
    })
    require.Error(t, err)
    // Assert the credential is NOT present in the returned gRPC status message.
    require.NotContains(t, err.Error(), "s3cr3t-p4ss")
}
```
This test currently fails because the raw stderr (potentially containing `s3cr3t-p4ss`) is embedded unsanitized by `structerr.NewInternal` in `fetchRemoteAtomic`.

	mth, ok := entry.Data["grpc.method"]
	if !ok {
		return nil
	}

	mthStr, ok := mth.(string)
	if !ok || !hook.possibleGrpcMethods[mthStr] {
		return nil
	}

	if _, ok := entry.Data["args"]; ok {
		sanitizeSpawnLog(entry)
	} else if _, ok := entry.Data["error"]; ok {
		sanitizeErrorLog(entry)

		entry.Message = sanitizeString(entry.Message)
	}

	return nil
