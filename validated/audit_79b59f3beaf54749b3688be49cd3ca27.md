## Analysis Result

### Title
Zero-Share Deposit Due to Insufficient Share-Price Precision Permanently Freezes Depositor Funds - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
Every Zest vault (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`) computes shares to mint on `deposit` via `convert-to-shares-preview`, which performs an unchecked `mul-div-down`. Unlike `redeem`, the `deposit` function never asserts that the resulting share amount (`inkind`) is greater than zero, so a depositor whose `amount` rounds down to `0` shares still has their underlying tokens pulled into the vault while receiving nothing in return.

### Finding Description
`convert-to-shares-preview` rounds down when converting an underlying `amount` into vault shares: [1](#0-0) 

This is the same class of bug as the referenced report: the smallest amount representable in the output unit (shares here, `pricePerUnit` there) is bounded by an integer-division floor. When `total-assets-preview` (`ta`) has grown large relative to `total-supply-preview` (`ts`) — which happens naturally as a vault accrues interest and mints treasury LP over time — the "price" of one share in underlying-asset terms increases. Any deposit `amount` smaller than `ta/ts` computes `inkind = 0`.

Crucially, `deposit` lacks the same zero-output guard `redeem` has (`ERR-OUTPUT-ZERO`): [2](#0-1) 

The only checks are `(> amount u0)` and `(>= inkind min-out)`. If the caller passes `min-out u0` (a perfectly normal, non-malicious default for a "small deposit"), the slippage check `(>= 0 0)` trivially passes. The vault then executes:
- `(receive-underlying amount account)` — pulls the depositor's tokens into the vault.
- `(ft-mint? zft inkind recipient)` — mints `0` shares to the depositor.
- `(var-set assets (+ current-assets amount))` — increases the vault's tracked assets.

The depositor's underlying tokens permanently become part of the vault's asset base with no corresponding share claim, silently transferring their value to all existing shareholders. This mirrors the reported bug's root cause exactly: a value below the smallest representable unit of the target denomination (shares, in this case) cannot be expressed, and unlike the marketplace's `pricePerUnit > 0` check, Zest's `deposit` function has no equivalent `inkind > 0` check to reject the transaction.

### Impact Explanation
This is theft of user funds at rest: the depositor's tokens are absorbed into the vault (`assets` increases) while they receive zero shares (`zft` balance unaffected), with no way to reclaim the deposited amount. As the vault's share price appreciates over time via `calc-treasury-lp-preview`/`accrue` interest accrual (a growing, expected state, not an edge case), the amount required to trigger a zero-share mint grows, widening the window during which ordinary small deposits are silently confiscated. This falls into the Critical impact category: direct theft of user funds at rest.

### Likelihood Explanation
Likelihood is high given normal user behavior: many wallets/dApps default `min-out` to `0` for simple deposits, and any user depositing a small amount of a high-share-price vault (e.g., late in a long-running vault's life, or into a vault backed by a high-value asset like sBTC) can trigger this without malicious intent. No privileged access or unusual configuration is required — only an ordinary `deposit` call from any principal.

### Recommendation
Add an explicit zero-output guard in every vault's `deposit` function, mirroring the existing `redeem` check:
```clarity
(asserts! (> inkind u0) ERR-OUTPUT-ZERO)
```
This should be added immediately alongside the other `asserts!` in `deposit` across `v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, and `v0-vault-ststxbtc.clar` (and their `local-testing` counterparts), so that a deposit computing `0` shares reverts instead of silently consuming the depositor's funds.

### Proof of Concept
1. Allow a vault (e.g. `v0-vault-usdc`) to accrue significant interest over time via repeated `accrue` calls / borrow-repay cycles, so that `total-assets-preview` grows much larger than `total-supply-preview`, raising the effective share price (`ta/ts`) above `1`.
2. An ordinary user calls `deposit` with an `amount` smaller than the current `ta/ts` ratio and `min-out = 0` (the typical default when a caller isn't defending against this specific rounding case).
3. Inside `deposit`: `inkind = (convert-to-shares-preview amount)` evaluates to `(mul-div-down amount ts ta)`, which rounds down to `0`.
4. The check `(asserts! (>= inkind min-out) ERR-SLIPPAGE)` passes because `0 >= 0`.
5. `(receive-underlying amount account)` transfers the user's tokens into the vault; `(ft-mint? zft inkind recipient)` mints `0` shares; `(var-set assets (+ current-assets amount))` credits the vault with the extra assets.
6. The depositor now holds no shares representing the deposited `amount`, which is permanently distributed as extra backing to all existing shareholders — funds theft with no recovery path.

```text
(define-private (convert-to-shares-preview (amount uint))
  (let ((ta (total-assets-preview))
        (ts (total-supply-preview)))
    (if (is-eq ts u0)
        amount
        (if (is-eq ta u0)
            u0
            (mul-div-down amount ts ta)))))
```
