Based on my analysis, the write path for StackerDB chunks does not enforce the `write_freq` rate-limit that the smart contract configures, even though the P2P sync/download path does respect it.

### Title
StackerDB HTTP chunk-write endpoint never enforces the contract-specified `write_freq` throttle - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`StackerDBTx::try_replace_chunk` [1](#0-0)  is the sole gate for accepting a new chunk into a slot, whether the chunk arrives via the `POST /v2/stackerdb/.../chunks` RPC endpoint [2](#0-1)  or via internal P2P push/store. It checks chunk size, slot signer, stale version, and max-writes, but never compares the elapsed wall-clock time since the slot's last write against `self.config.write_freq`.

### Finding Description
`StackerDBConfig.write_freq` is documented as the "minimum wall-clock time between writes to the same slot" [3](#0-2)  and is derived from the StackerDB's controlling smart contract via `eval_config` [4](#0-3) . The `net::Error` enum even defines a dedicated `TooFrequentSlotWrites(u64)` variant with its own `Display` message [5](#0-4) [6](#0-5) , signalling that the codebase intends to enforce this throttle on writes.

However, grepping the whole `stackslib/src/net/**` tree for `TooFrequentSlotWrites` shows it is declared but never constructed anywhere in `stackslib/src/net/mod.rs` — it is dead code. The only place `write_freq` is actually read is in `StackerDBSync::make_chunk_request_schedule`, where it is used purely to decide whether a *sync client* should bother requesting a chunk that was written too recently [7](#0-6) . `StackerDBSync::validate_downloaded_chunk` explicitly notes "no need to validate the timestamp, because we already skipped requesting it if it was written too recently" [8](#0-7)  — this reasoning only holds for the pull-based sync path, not for the HTTP write path.

The write path itself, `try_replace_chunk`, only performs:
1. Chunk size vs `config.chunk_size` check.
2. Signer verification against `slot_validation.signer`.
3. Stale-version check (`slot_version <= slot_validation.version`).
4. Max-writes check (`slot_version > config.max_writes`).

There is no check of `slot_validation.write_time` against `config.write_freq` before calling `self.insert_chunk(...)` [9](#0-8) . Any remote, unprivileged client (or the slot's legitimate signer, or anyone able to relay a validly-signed chunk if the signer's key is otherwise available) can therefore submit a strictly-increasing-version chunk to a slot as fast as they want via `POST /v2/stackerdb/:principal/:contract/chunks`, bypassing the wall-clock throttle the controlling smart contract declared. `validate_received_chunk`, used to sanity-check pushed/received chunks in `handle_unsolicited_StackerDBPushChunk`, also has no write-frequency check and explicitly documents that it doesn't: "NOTE: does not check write frequency, since the caller has different ways of doing this" [10](#0-9)  — but the caller (the HTTP endpoint) has no other way of doing this either.

This is directly analogous to the reported Chainlink bug: a protocol-level invariant (freshness/rate limit) is declared in configuration/state but the code path that actually accepts and commits new data skips validating it, letting stale-throttling be silently bypassed.

### Impact Explanation
This does not itself cause a crash or memory disclosure, but it is an unauthorized-write/protocol-invariant-bypass: signer-throttling that application contracts rely on (e.g., signer message cadence limits, anti-spam/anti-flood assumptions baked into `write-freq`) can be defeated by any party capable of producing validly-signed, monotonically-versioned chunks (which for legitimate slot owners is trivial — they already sign their own state updates). This lets a slot owner (or one holding the slot's key) flood the StackerDB with new chunks far faster than the smart contract permits, forcing continuous re-broadcast/relay to every replicating peer network-wide (since accepted writes are turned into `StackerDBPushChunk` relay messages) and defeating the DB-level rate-limiting the config author intended, i.e. "propagation of allowed-but-then-relayed-too-fast writes" to the whole peer network. Impact is bounded by max-writes/versioning, so it is not unauthenticated write to state (need signer's key), but it is a rate-limit-bypass exposing the network-wide propagation of chunk writes outside of the declared invariant, best mapped to the High tier ("bounded compute DoS/relay flooding stemming from a declared invariant not being enforced on the write path").

### Likelihood Explanation
Any actor that already knows a slot's private key (the normal, expected way of submitting a chunk to that slot) can immediately exploit this — no additional privilege beyond what's required for legitimate writes. Given `TooFrequentSlotWrites` is dead code and `write_freq` enforcement is fully absent from `try_replace_chunk`/`validate_received_chunk`, this is a certain gap, not a race condition or timing corner case.

### Recommendation
In `StackerDBTx::try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `insert_chunk`, load the slot's last `write_time` (already tracked, as seen in `get_slot_write_timestamps`/`slot_validation.write_time`) and reject the write with `net_error::TooFrequentSlotWrites(deadline)` if `now < write_time + config.write_freq`, mirroring the existing read-side throttle in `StackerDBSync::make_chunk_request_schedule`. Also add the corresponding rejection path to `validate_received_chunk` for pushed/unsolicited chunks, and surface a dedicated `StackerDBErrorCodes` variant (e.g. `TooFrequent`) in `poststackerdbchunk.rs` so HTTP clients get a proper ack rather than acceptance.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u3600` (once per hour) and a signer slot owned by key `K`.
2. Using `K`, sign and `POST` a chunk at slot `0`, version `1` to `/v2/stackerdb/:principal/:contract/chunks` — accepted (per `try_handle_request` in `poststackerdbchunk.rs`).
3. Immediately (same second) sign and `POST` another chunk at slot `0`, version `2` with the same key — `try_replace_chunk` only checks `slot_version <= slot_validation.version` (which is false, `2 > 1`) and `slot_version > config.max_writes` (false); the write succeeds and is relayed via `StackerDBPushChunk`, despite the contract's `write-freq: u3600` supposedly permitting only one write per hour.
4. Repeat step 3 as fast as the network round-trip allows to observe unrestricted write throughput to the slot, in violation of the configured `write_freq`.
