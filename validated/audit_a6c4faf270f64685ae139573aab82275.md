### Title
Floating-point precision manipulation of the TRC10 Bancor-relay Exchange pool enables draining of paired-asset liquidity from low-liquidity pairs - (File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java)

### Summary
java-tron's built-in TRC10 `Exchange` module implements a Bancor-relay AMM (`ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`) that any unprivileged account can invoke. Pool creation is permissionless and unbounded in ratio, liquidity injection is open to any account, and — critically — the price/quantity calculation used by default is performed with IEEE-754 `double` arithmetic (`Math.pow`) rather than exact integer/BigDecimal math. This mirrors the root cause of the Moonwell incident: an attacker can create or find a very shallow (“low-liquidity”) token pool, then use a sequence of trades/injections to move the pool's internal price ratio and exploit rounding behavior of the floating-point relay formula to extract more of the paired real asset (TRX or another TRC10 token) than was deposited, at the expense of the pool's other holdings.

### Finding Description
The exchange price/quantity math lives in `ExchangeCapsule.transaction()` which, unless the chain-parameter `AllowHardenExchangeCalculation` proposal has been activated, instantiates the legacy `ExchangeProcessor` that performs the Bancor relay computation with `double` and `Math.pow`: [1](#0-0) [2](#0-1) 

The safer `SafeExchangeProcessor` (BigDecimal-based) exists but is only used when `hardenedCalc` is true, gated by the `allowHardenExchangeCalculation()` dynamic-property flag checked in `AbstractExchangeActuator.allowHarden()`: [3](#0-2) 

`ExchangeCapsule.transaction()` selects the processor and mutates pool balances based on whichever math path is active: [4](#0-3) 

Any account can permissionlessly create a pool pairing an arbitrary, self-issued TRC10 token against TRX or another real asset, with no minimum-liquidity floor beyond `balance > 0` and an upper `ExchangeBalanceLimit`: [5](#0-4) 

Any account (not just the creator) can subsequently inject additional liquidity into an existing pool at the pool's current ratio via `ExchangeInjectActuator`, and any account can trade against the pool via `ExchangeTransactionActuator`, which recomputes the trade using the same `exchangeCapsule.transaction()` path both during `validate()` (to check the caller-supplied `expected` slippage bound) and again during `execute()`: [6](#0-5) [7](#0-6) 

Because the default math path uses floating point, and there is no protocol-level minimum liquidity, price-impact cap, or oracle cross-check, an attacker who creates or targets a shallow pool can perform a sequence of small `ExchangeInject`/`ExchangeTransaction` calls engineered so that floating-point truncation (`(long) issuedSupply`, `(long) exchangeBalance`) systematically favors the attacker across repeated operations, allowing them to withdraw more of the paired real asset than they contributed — directly analogous to Moonwell's attacker inflating the price of a low-liquidity token (MAMO) and extracting real assets (cbBTC/USDC) against it.

### Impact Explanation
A successful sequence drains real TRX/TRC10 value from an Exchange pool that other honest accounts may have deposited into via `ExchangeInject` (injection is not restricted to the pool creator), resulting in concrete unauthorized transfer/theft of funds from the pool participants — a direct on-chain financial loss reachable purely by broadcasting signed `ExchangeCreateContract`, `ExchangeInjectContract`, and `ExchangeTransactionContract` transactions, satisfying the High-severity "theft of funds" bar.

### Likelihood Explanation
- Asset issuance (to mint the low-liquidity token) and Exchange contract creation/trading are fully permissionless operations reachable by any funded account.
- The vulnerable floating-point path (`ExchangeProcessor`) is the *default*; the safer `SafeExchangeProcessor` requires the `AllowHardenExchangeCalculation` chain parameter to be activated via SR/committee proposal, so unless that proposal has been passed on a given network, every Exchange pool on it uses the unsafe math.
- No minimum-liquidity requirement or price-impact/oracle safeguard exists to block creation of an artificially shallow pool or large single-block price swings.

### Recommendation
- Make `SafeExchangeProcessor` (or an equivalent fixed-point/BigDecimal implementation) the mandatory, non-optional calculation path for all Exchange actuators, removing the floating-point `ExchangeProcessor` from production use.
- Enforce a protocol-level minimum liquidity/minimum balance for both sides of an Exchange pool at creation and after withdraw/inject, and reject transactions that would move the pool ratio beyond a bounded per-transaction price-impact threshold.
- Consider restricting `ExchangeInjectActuator`/`ExchangeWithdrawActuator` to the pool creator or adding pool-level access controls, and add slippage/deadline protections enforced at the protocol level rather than only via caller-supplied `expected` values.

### Proof of Concept
1. Attacker issues a new TRC10 token `EVIL` (permissionless `AssetIssueContract`).
2. Attacker broadcasts `ExchangeCreateContract` pairing `EVIL` with TRX using a very small TRX balance (e.g., 1 TRX) and a large `EVIL` balance, creating a low-liquidity pool — allowed because validation only requires `balance > 0` and `< ExchangeBalanceLimit` (`ExchangeCreateActuator.doValidate`, lines 201-208).
3. Attacker (or an accomplice acting as a "liquidity provider") calls `ExchangeInjectContract` multiple times, each recalculated from the current pool ratio (`ExchangeInjectActuator.execute`, lines 71-83), progressively pushing the reserve ratio to a state where `ExchangeProcessor`'s double-precision Bancor formula (`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`) yields a favorable truncation for large trades.
4. Attacker calls `ExchangeTransactionContract` to sell `EVIL` into the pool, receiving TRX out via `ExchangeCapsule.transaction()` (`ExchangeCapsule.java`, lines 124-169) using the unsafe path (since `allowHardenExchangeCalculation()` defaults unset), extracting more TRX than the economic value of `EVIL` deposited, at the expense of any real TRX/TRC10 liquidity present in the pool.
5. Repeat across pools/other participants' injected liquidity to compound losses, mirroring the "inflate a low-liquidity token, use it to extract real assets" pattern from the Moonwell incident.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
