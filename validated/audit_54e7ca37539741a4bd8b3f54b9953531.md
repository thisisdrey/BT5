Confirmed: `preamble.headers.get("authorization")` returns a `String`, compared via `auth_header != password` (standard `String`/`&String` `PartialEq`), which is a byte-wise comparison implemented via slice equality — not a constant-time comparison primitive (e.g., `subtle::ConstantTimeEq` or `ring::constant_time::verify_slices_are_equal`). This pattern is duplicated identically across six RPC endpoint handlers in `stackslib/src/net/api/`.

### Title
Timing side-channel in `auth_token` comparison enables secret recovery and auth bypass on privileged `/v3` RPC endpoints - (File: `stackslib/src/net/api/postblock_proposal.rs`, `postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`)

### Summary
Six RPC request handlers gate privileged/expensive endpoints behind a shared secret (`connection_options.auth_token`) supplied via the `authorization` HTTP header. Each handler validates the header with a plain, non-constant-time `String` equality check: `if auth_header != password { return Err(... 401 ...) }`. This is the same bug class as CVE-2019-25025/GHSA-cvw2-xj8r-mjf7 (timing attack on secret-equality checks), applied here to a network-facing authentication token rather than a session ID.

### Finding Description
The affected sites are:
- `stackslib/src/net/api/postblock_proposal.rs:1139-1144` (`/v3/block_proposal`)
- `stackslib/src/net/api/postblock_v3.rs` (`/v2/blocks` / `/v3` broadcast=1 path), same pattern
- `stackslib/src/net/api/blockreplay.rs:578-583` (`/v3/blocks/replay/:block_id`)
- `stackslib/src/net/api/blocksimulate.rs:156-161` (`/v3/blocks/simulate/:block_id`)
- `stackslib/src/net/api/fastcallreadonly.rs:105-110` (`/v3/contracts/fast-call-read/...`)
- `stackslib/src/net/api/txsimulate.rs:355-360` (`/v3/transactions/simulate`)

In every case the code is:
```rust
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password { return Err(Error::Http(401, "Unauthorized".into())); }
```
`preamble.headers.get(...)` returns an owned `String`; the `!=` operator uses `String`'s derived `PartialEq`, which delegates to slice/byte comparison that returns as soon as a length mismatch or the first differing byte is found. This creates a measurable timing difference correlated with the number of matching leading bytes between the attacker-supplied header value and the real, configured `auth_token`. A remote, unauthenticated attacker can issue repeated requests to any of these endpoints, incrementally guessing the token byte-by-byte (or via statistical timing analysis across many trials), and eventually recover the full secret without needing any prior credential. ### Impact Explanation
`auth_token` is documented as the single shared secret securing the node-to-signer channel and gating `/v3/block_proposal` (accepts block proposals from the configured signer) and the `broadcast=1` path of block posting. [5](#0-4) 
If an attacker recovers this token via timing analysis, they gain the ability to POST forged/attacker-controlled block proposals to `/v3/block_proposal` and to authenticate broadcast requests — i.e., unauthorized write / auth bypass into node-signer coordination, matching the "Critical: unauthenticated/unauthorized write to state... auth bypass" category. It also unlocks `fast-call-read` and `transactions/simulate`/`blocks/simulate` compute endpoints for unauthenticated use, enabling bounded compute DoS.

### Likelihood Explanation
Exploitation requires only network access to the RPC port and a statistically significant number of timed requests per guessed byte — no credentials, no privileged position, and no protocol violation. Modern network jitter makes exact byte-by-byte recovery non-trivial but not infeasible, especially on low-latency/local networks (this is precisely the risk class the referenced advisory targeted); Rust's default string/slice equality gives no constant-time guarantee, so the timing signal genuinely exists and is not mitigated anywhere in this code path.

### Recommendation
Replace all six comparisons with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq` (`ct_eq`) or `ring::constant_time::verify_slices_are_equal`, comparing the header bytes and secret bytes:
```rust
use subtle::ConstantTimeEq;
if !bool::from(auth_header.as_bytes().ct_eq(password.as_bytes())) {
    return Err(Error::Http(401, "Unauthorized".into()));
}
```
Centralize this into a single shared helper (e.g., in `stackslib/src/net/http/request.rs`) so all six handlers use one audited constant-time check instead of six independent copies of `!=`.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3cr3tToken1234"`.
2. Send repeated POST requests to `/v3/block_proposal` (or `/v3/transactions/simulate`) with `authorization` header values that share an increasing number of correct leading bytes with the real token, each followed by a fixed suffix.
3. Measure response latency for each guess with many repetitions to average out jitter; requests whose prefix matches more bytes of the real secret will, on average, spend marginally more time in the `!=` comparison before returning 401.
4. Use the latency signal to iteratively determine each byte of `auth_token`, then use the recovered token to submit a forged block proposal or broadcast-authenticated block post.
