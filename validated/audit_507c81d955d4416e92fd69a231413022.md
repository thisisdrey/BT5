### Title
Unchecked `Currency::transfer` results in `claim_bounty` / `claim_child_bounty` allow permanent fund loss on award payout - ([File: substrate/frame/bounties/src/lib.rs] / [File: substrate/frame/child-bounties/src/lib.rs])

### Summary
`accept_curator` reserves the curator's deposit via `T::Currency::reserve(curator, deposit)?` [1](#0-0) , which only guarantees the curator account holds at least the `curator_deposit` amount — it does not guarantee the free/transferable balance stays above `ExistentialDeposit` after later operations, nor does it guarantee the beneficiary account (chosen freely by the curator in `award_bounty`) exists or is above ED. In both `claim_bounty` and `claim_child_bounty`, the final payout `Currency::transfer` calls are only checked with `debug_assert!`, which compiles to a no-op in release builds, while the bounty/child-bounty storage entry is unconditionally deleted and a "claimed" event is emitted regardless of transfer outcome.

### Finding Description
In `pallet-bounties::claim_bounty`:
```rust
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;
...
Self::deposit_event(Event::<T, I>::BountyClaimed { index: bounty_id, payout, beneficiary });
``` [2](#0-1) 

The same pattern exists in `pallet-child-bounties::claim_child_bounty`:
```rust
let fee_transfer_result = T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath);
debug_assert!(fee_transfer_result.is_ok());

let payout_transfer_result = T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath);
debug_assert!(payout_transfer_result.is_ok());
...
*maybe_child_bounty = None;
``` [3](#0-2) 

`debug_assert!` is stripped out of release/production builds (`debug-assertions = false`), so the check does nothing in a live chain build. The transfer to the beneficiary is `AllowDeath` and can fail with `Error::ExistentialDeposit` if `payout` (or `final_fee`/`curator_fee`) is below `ExistentialDeposit` and the destination account does not already exist with a provider reference. This is entirely plausible:
- The curator sets an arbitrary `fee` when proposed (bounded only by `<= value`), and `final_fee = fee.saturating_sub(children_fee)` can legitimately be smaller than `ExistentialDeposit`.
- The beneficiary is chosen freely by the curator in `award_bounty` [4](#0-3)  and can be a brand-new, never-funded account; if the computed `payout` for that account is below ED, the transfer fails to create the account.
- `accept_curator` only reserves the curator deposit [5](#0-4) , which does not guarantee anything about the free balance of an arbitrary beneficiary chosen later.

Once the transfer fails, the code does not roll back, retry, or preserve the funds path: `*maybe_bounty = None` (or `*maybe_child_bounty = None`) removes the only storage record tracking that sub-account's earmarked funds, and the `Claimed`/`BountyClaimed` event is emitted as if payment succeeded. The plancks remain stranded in the bounty/child-bounty derived sub-account with no remaining code path referencing them (the bounty index is gone, so no retry, cancel, or re-award is possible).

### Impact Explanation
This is a direct analog of the reported "unchecked transfer" bug class: the code assumes `transfer` "should not fail" and only guards it with a debug-only assertion, then irreversibly advances settlement state (deletes the bounty record, emits a paid event) regardless of the real transfer outcome. The result is a public, unprivileged-triggerable permanent loss/lock of treasury-derived funds — money that was allocated to a beneficiary/curator never reaches them and can never be recovered because the tracking storage that references the sub-account is deleted. This matches the "permanent user-fund lock" and "duplicate/incorrect settlement" impact categories in the gate.

### Likelihood Explanation
Likelihood is real but not universal: it requires that the beneficiary (freely chosen by the curator) is a fresh, unfunded account and that the computed payout/fee for that leg is below `ExistentialDeposit`. This is a normal, permissionless situation — curators routinely set small fees, and any account address (including one that has never been funded) can be nominated as beneficiary in `award_bounty`. No malicious peer, validator, governance actor, or leaked key is required — only an ordinary curator/claimant executing the standard bounty lifecycle with realistic parameter choices.

### Recommendation
- Replace the `debug_assert!` checks in `claim_bounty` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs`) with proper `?`/`ensure!`-based error propagation so that a failed transfer aborts the claim (leaving the bounty storage intact) instead of silently deleting the bounty record.
- Alternatively, use existential-deposit-safe deposit patterns (e.g., `deposit_creating`/`resolve_creating` semantics or explicitly checking/ topping up ED) before finalizing removal of bounty state, and only clear storage after all transfers are confirmed `Ok`.
- Add regression tests exercising a beneficiary/curator account that does not exist and whose computed payout is below `ExistentialDeposit`, verifying that the claim fails atomically and the bounty remains claimable.

### Proof of Concept
1. Governance approves a bounty with `value` funded into the bounty sub-account; a curator is proposed with a small `fee` (e.g., `fee = ExistentialDeposit - 1`).
2. Curator calls `accept_curator`, reserving only `curator_deposit` from their own balance — this does not fund any other account.
3. Curator calls `award_bounty` with `beneficiary` set to a brand-new AccountId that has never received funds (no existing provider reference), and structures the bounty such that `payout = balance.saturating_sub(fee)` (or, for child bounties, `payout`/`curator_fee`) ends up below `ExistentialDeposit` for that fresh beneficiary.
4. After `unlock_at`, anyone calls `claim_bounty` (or `claim_child_bounty`).
5. In a release build, `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(Error::ExistentialDeposit)` because it would create a new account below ED; `debug_assert!(res.is_ok())` is compiled out and does nothing.
6. Execution continues: `*maybe_bounty = None;` deletes the bounty, `BountyDescriptions` is removed, and `Event::BountyClaimed` is emitted with the `payout` amount — even though the beneficiary never received any funds.
7. The plancks remain stuck in the (now-orphaned) bounty sub-account, with no bounty index left to retry, cancel, or reclaim them — a permanent fund lock triggered entirely through the pallet's normal, permissionless public API.

			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
			beneficiary: AccountIdLookupOf<T>,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;
			let beneficiary = T::Lookup::lookup(beneficiary)?;

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.as_mut().ok_or(Error::<T, I>::InvalidIndex)?;

				// Ensure no active child bounties before processing the call.
				ensure!(
					T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
					Error::<T, I>::HasActiveChildBounty
				);

				match &bounty.status {
					BountyStatus::Active { curator, .. } => {
						ensure!(signer == *curator, Error::<T, I>::RequireCurator);
					},
					_ => return Err(Error::<T, I>::UnexpectedStatus.into()),
				}
				bounty.status = BountyStatus::PendingPayout {
					curator: signer,
					beneficiary: beneficiary.clone(),
					unlock_at: Self::treasury_block_number() + T::BountyDepositPayoutDelay::get(),
				};

				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::BountyAwarded { index: bounty_id, beneficiary });
			Ok(())
