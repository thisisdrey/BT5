## Analog Found: Stale Postponed Receipts Survive `DeleteAccount` and Later Execute Against a Recreated Account

### Title
Postponed action receipts and received-data callbacks are not purged on account deletion, allowing a stale receipt to execute against a later-recreated account with the same id - (File: `runtime/runtime/src/actions.rs`)

### Summary
This is the same bug class as the GMX report: state is left "floating" in a keyed store after the thing it depended on (a position / an account) has gone away, and it is not cancelled — only to later fire unexpectedly against a *new* instance that reuses the same key (a new position / a recreated account).

### Finding Description
NEAR's cross-contract-call mechanism persists three separate trie entries keyed by `receiver_id` while a callback action receipt waits for its input data:

- `TrieKey::PostponedReceiptId { receiver_id, data_id }`
- `TrieKey::PendingDataCount { receiver_id, receipt_id }`
- `TrieKey::PostponedReceipt { receiver_id, receipt_id }` [1](#0-0) 

These are set by `process_action_receipt`/`apply_action_receipt` when a receipt's `input_data_ids` are not yet satisfied [2](#0-1) , and are only ever consumed (matched and removed) when the corresponding `Data` receipt finally arrives, in `process_receipt`: [3](#0-2) .

`action_delete_account` (the handler for `Action::DeleteAccount`) removes the `Account`/key state via `remove_account`, refunds the balance to the beneficiary, and clears `actor_id`/`account`, but it never touches `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, or `ReceivedData` entries keyed on the deleted `account_id`: [4](#0-3) 

There is no call to `remove_postponed_receipt` or any `state_update.remove(TrieKey::PostponedReceiptId{..})`/`PendingDataCount`/`ReceivedData` anywhere in the delete-account path — the only places these keys are read/written/removed are the receipt-matching logic in `lib.rs` itself [5](#0-4) . Because NEAR account ids can be reused after deletion (a NEAR-implicit account "acts as a regular account until it's deleted" and can be recreated by a subsequent `Transfer`, and a named sub-account id can likewise be recreated by `CreateAccount` once its parent authorizes it) [6](#0-5) [7](#0-6) , any dangling `PostponedReceipt`/`ReceivedData`/`PendingDataCount` rows survive the deletion and remain addressable under the same `receiver_id` for the freshly created account.

If the still-outstanding `Data` receipt (the callback's return value) eventually arrives after the account has been deleted and recreated, `process_receipt` will still find the `PostponedReceiptId` link, decrement `PendingDataCount`, and — if it hits zero — fetch and execute the old `PostponedReceipt` via `apply_action_receipt` against the *new* account's state [8](#0-7) . This is functionally identical to GMX's phantom decrease order firing against User A's newly opened position.

### Impact Explanation
Whether this is exploitable for concrete impact hinges on the contents of the stale `PostponedReceipt`. Because `apply_action_receipt` seeds `actor_id` from `receipt.predecessor_id()` and self-calls (`predecessor_id == receiver_id == account_id`) are granted full actor permission in `check_actor_permissions` [9](#0-8) , a stale self-addressed postponed receipt (a very common pattern: a contract calling itself as a promise callback) would replay with full authority over the *new* occupant of that account id — e.g. re-running an `AddKey`/`DeployContract`/`Transfer`/`Stake` action nobody currently controlling the account authorized. That is authorization escalation across account "generations" sharing an id, and can manifest as unauthorized fund transfers or key/contract takeover of the freshly (re)created account.

### Likelihood Explanation
I could not fully verify the body of `remove_account` in `core/store/src/utils/mod.rs` in this pass (tool budget exhausted before reading it), so I cannot rule out that it separately walks and clears postponed-receipt/received-data columns for the account outside of `action_delete_account`. All direct evidence I gathered (trie key removal call sites, the delete-account handler itself, and the architecture docs) points to these keys being untouched by account deletion, but this residual uncertainty should be resolved by inspecting `remove_account`'s full implementation before treating this as confirmed. Triggering the scenario also requires: (a) a pending cross-contract callback whose data receipt is delayed past the same-block deletion+recreation window (plausible under congestion/cross-shard latency, similar to GMX's "same block" race), and (b) the account being deletable and re-creatable with a matching `receiver_id`, both of which are ordinary, permissionless operations available to any signer.

### Recommendation
On `Action::DeleteAccount`, also purge any `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, and `ReceivedData` entries associated with the account being deleted (or, failing that, refuse deletion while any such entries remain outstanding for that account, mirroring the report's "cancel on failure" recommendation) so a dangling receipt/data-dependency cannot later resolve against a different account occupying the same id.

### Proof of Concept
Conceptual reproduction (not executed — would need a `test-loop-tests`/`runtime/runtime/src/tests` harness):
1. Account `A` issues a `FunctionCall` to itself that creates a cross-contract call with a callback (`input_data_ids=[d]`), producing a postponed receipt `R` stored under `(receiver_id=A, receipt_id=R)`, plus `PostponedReceiptId{A,d}=R` and `PendingDataCount{A,R}=1`.
2. Before the `Data` receipt carrying `d` is delivered, `A` self-deletes via `DeleteAccountAction` (refunding to a beneficiary). `action_delete_account` clears the `Account`/keys but leaves the three postponed-receipt trie entries intact [10](#0-9) .
3. A new account with id `A` is created (e.g. `A` is a NEAR-implicit id and gets funded again via `Transfer`, recreating it fresh) [7](#0-6) .
4. The delayed `Data` receipt for `d` finally arrives and is processed: `process_receipt` matches `PostponedReceiptId{A,d}`, decrements `PendingDataCount` to 0, fetches `PostponedReceipt{A,R}` (the old receipt), and executes it via `apply_action_receipt` against the newly created account `A` [11](#0-10) , running the original (now unauthorized) actions with self-call actor permission on the new account's state.

pub(crate) fn action_delete_account(
    state_update: &mut TrieUpdate,
    account: &mut Option<Account>,
    actor_id: &mut AccountId,
    receipt: &Receipt,
    result: &mut ActionResult,
    account_id: &AccountId,
    delete_account: &DeleteAccountAction,
    config: &RuntimeConfig,
    current_protocol_version: ProtocolVersion,
) -> Result<(), StorageError> {
    let account_ref = account.as_ref().unwrap();
    let account_storage_usage = if ProtocolFeature::FixDeleteAccountGlobalContractStorageUsage
        .enabled(current_protocol_version)
    {
        let contract_storage = get_contract_storage_usage(state_update, account_id, account_ref)?;
        account_ref.storage_usage().saturating_sub(contract_storage)
    } else {
        // Legacy behavior: only subtracts local contract code, misses the
        // global contract identifier overhead.
        let account_storage_usage = account_ref.storage_usage();
        let code_len = get_code_len_or_default(
            state_update,
            account_id.clone(),
            account_ref.local_contract_hash().unwrap_or_default(),
        )?;
        debug_assert!(
            code_len == 0 || account_storage_usage > code_len,
            "account storage usage should be larger than code size. storage usage: {}, code size: {}",
            account_storage_usage,
            code_len
        );
        account_storage_usage.saturating_sub(code_len)
    };
    if account_storage_usage > Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE {
        result.result =
            Err(ActionErrorKind::DeleteAccountWithLargeState { account_id: account_id.clone() }
                .into());
        return Ok(());
    }
    let gas_key_balance_to_burn = compute_gas_key_balance_sum(state_update, account_id)?;
    if gas_key_balance_to_burn > GasKeyInfo::MAX_BALANCE_TO_BURN {
        result.result = Err(ActionErrorKind::GasKeyBalanceTooHigh {
            account_id: account_id.clone(),
            public_key: None,
            balance: gas_key_balance_to_burn,
        }
        .into());
        return Ok(());
    }
    // We use current amount as a pay out to beneficiary.
    let account_balance = account_ref.amount();
    if account_balance > Balance::ZERO {
        result
            .new_receipts
            .push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));
    }
    let remove_result = remove_account(state_update, account_id)?;
    result.tokens_burnt =
        result.tokens_burnt.checked_add(gas_key_balance_to_burn).ok_or_else(|| {
            StorageError::StorageInconsistentState("tokens_burnt overflow".to_string())
        })?;
    if remove_result.gas_key_nonce_count > 0 {
        let compute = storage_removes_compute(
            &config.wasm_config.ext_costs,
            remove_result.gas_key_nonce_count,
            remove_result.gas_key_nonce_total_key_bytes,
            AccessKey::NONCE_VALUE_LEN * remove_result.gas_key_nonce_count,
        );
        result.compute_usage = safe_add_compute(result.compute_usage, compute).map_err(|_| {
            StorageError::StorageInconsistentState("compute_usage overflow".to_string())
        })?;
    }
    *actor_id = receipt.predecessor_id().clone();
    *account = None;
    Ok(())
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}

pub fn set_postponed_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    assert!(matches!(receipt.versioned_receipt(), VersionedReceiptEnum::Action(_)));
    let key = TrieKey::PostponedReceipt {
        receiver_id: receipt.receiver_id().clone(),
        receipt_id: *receipt.receipt_id(),

    set(state_update, key, receipt);
}

pub fn remove_postponed_receipt(
    state_update: &mut TrieUpdate,
    receiver_id: &AccountId,

) {

}

### Implicit account creation

An account with implicit account ID can only be created by sending a transaction/receipt with a single `Transfer` action to the implicit account ID receiver:

- The account will be created with the account ID.
- The account balance will have a transfer balance deposited to it.
- If this is NEAR-implicit account, it will have a new full access key with the ED25519-curve public key of `decode_hex(account_id)` and nonce `(block_height - 1) * MULTIPLIER` (to address an issues discussed [here](https://gov.near.org/t/issue-with-access-key-nonce/749)).
- If this is ETH-implicit account, it will have the [Wallet Contract](#wallet-contract) deployed, which can only be used by the owner of the Secp256K1 private key where `'0x' + keccak256(public_key)[12:32].hex()` matches the account ID.

Implicit account can not be created using `CreateAccount` action to avoid being able to hijack the account without having the corresponding private key.

Once a NEAR-implicit account is created it acts as a regular account until it's deleted.
