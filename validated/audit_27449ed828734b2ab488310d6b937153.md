### Title
Unbounded, unverified attachment content is written into AtlasDB from remote peer responses - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts an `Attachment` decoded from a remote peer's `GetAttachmentResponse` into `context.attachments` with no size check, and `GetAttachmentResponse::deserialize` (`stackslib/src/net/atlas/mod.rs:69-77`) hex-decodes the body with no length cap. When the batch reaches the `Done` state, `AttachmentsDownloader::run` unconditionally calls `atlasdb.insert_instantiated_attachment(&attachment)` for every entry in `context.attachments`, regardless of whether `attachment.hash()` matches any tracked `attachment_instance.content_hash`, and with no comparison against `AtlasConfig.attachments_max_size`.

### Finding Description
The claimed equality/fault holds: bytes accepted per attachment equals an attacker-controlled, unbounded value at the point of insertion.

- `GetAttachmentResponse::deserialize` at `stackslib/src/net/atlas/mod.rs:69-77` decodes an arbitrary-length hex string into `Attachment::new(bytes)` with no size cap: [1](#0-0) 
- `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) inserts the decoded `response.attachment` straight into `self.attachments: HashSet<Attachment>` after only checking `decode_atlas_get_attachment()` succeeded — no length/size validation against `AtlasConfig.attachments_max_size` occurs here: [2](#0-1) 
- The consuming loop when the state machine reaches `Done` (`stackslib/src/net/atlas/download.rs:153-169`) drains `context.attachments` and calls `network.atlasdb.insert_instantiated_attachment(&attachment)` **unconditionally**, before even checking whether `find_all_attachment_instances(&attachment.hash())` returned any matching instance: [3](#0-2) 

This means a malicious outbound sync peer that is asked for a given `content_hash` (via `AttachmentRequest`) can return a `GetAttachmentResponse` body containing arbitrary, many-megabyte content that does not even need to hash to the requested `content_hash`. That content will still be written to the SQLite-backed `AtlasDB` via `insert_instantiated_attachment`, with no size bound enforced at this call site and no requirement that it correspond to any real on-chain attachment commitment.

The `attachments_max_size` field of `AtlasConfig` does exist and is validated for configuration sanity (`stackslib/src/net/atlas/mod.rs:116-121`), and is used elsewhere (e.g., for on-chain-sourced `queue_attachment_instance`/`should_keep_attachment` logic), but it is not enforced on this remote-response ingestion path (`extend_with_attachments` → `insert_instantiated_attachment`).

### Impact Explanation
An unprivileged remote peer, once selected as an outbound Atlas sync peer, can cause the victim node to write attacker-supplied, unbounded-size blobs into its local `AtlasDB` for every `AttachmentRequest` it answers, with no verification that the content matches the requested hash or any legitimate on-chain attachment commitment. This is repeatable across the full space of `content_hash` values enumerated from `attachments_batch`, allowing sustained disk/storage exhaustion and pollution of node state with unauthenticated data — matching the "Critical: unauthenticated write to node state" category.

### Likelihood Explanation
Preconditions: the attacker must be selected among `network.get_outbound_sync_peers()` for Atlas sync and answer `AttachmentRequest`s that the victim issues, which requires no special privilege, secret, or role — any peer providing a P2P/RPC-reachable `/v2/attachments/<hash>` endpoint that participates in normal Atlas gossip can qualify. The attacker cost is minimal: a single malformed or oversized response per request. This is fully repeatable across many attachment instances tracked by the victim's Atlas subsystem.

### Recommendation
In `extend_with_attachments` (or in the `Done`-state consumption loop in `AttachmentsDownloader::run`), reject `Attachment`s whose content length exceeds `AtlasConfig.attachments_max_size` before inserting into `context.attachments`, and verify `attachment.hash()` matches the specific requested `content_hash` before calling `insert_instantiated_attachment`, discarding/penalizing the peer otherwise.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AttachmentsBatchStateContext` with a tracked `AttachmentInstance` for content hash `H`.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains a `GetAttachmentResponse` with `attachment.content` set to several megabytes of arbitrary bytes that do NOT hash to `H`.
3. Call `context.extend_with_attachments(&mut results)` and assert `context.attachments.len() == 1` with the oversized content present, showing no `attachments_max_size` check ran.
4. Drive the state machine to `Done` and observe (via a mock/instrumented `AtlasDB`) that `insert_instantiated_attachment` is invoked for the mismatched, oversized attachment even though `find_all_attachment_instances(&attachment.hash())` returns empty — confirming the unconditional, unbounded write.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }
