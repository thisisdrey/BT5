Audit Report

## Title
Ignored/`debug_assert!`-only transfer results in `claim_child_bounty` allow silent payout failure while bounty state is still finalized - (File: substrate/frame/child-bounties/src/lib.rs)

## Summary
In `pallet-child-bounties`'s `claim_child_bounty` extrinsic, both the curator-fee transfer and the beneficiary payout transfer results are checked only via `debug_assert!(...is_ok())`, which is compiled out entirely in release builds. Regardless of whether either `T::Currency::transfer` call succeeds, the code unconditionally proceeds to delete the `ChildBounty` storage entry, decrement `ParentChildBounties`, remove the description, and emit `Event::Claimed`, finalizing settlement state without verifying the underlying value transfer actually occurred.

## Finding Description
The code path in `claim_child_bounty` is: [1](#0-0) 

After computing `curator_fee = child_bounty.fee.min(balance)` and `payout = balance.saturating_sub(curator_fee)`, both amounts are transferred out of `child_bounty_account` with `AllowDeath`. Each result is bound to a local variable and passed to `debug_assert!`, which is a no-op in `--release` builds — the standard build profile for production Substrate runtimes/nodes. No `?` propagation or `map_err` exists for either transfer.

Following these transfers, execution unconditionally continues to finalize settlement: [2](#0-1) 

This means the `Event::Claimed` emission, `ParentChildBounties` decrement, description removal, and `ChildBounty` record deletion (`*maybe_child_bounty = None`) all occur even if `fee_transfer_result` or `payout_transfer_result` returned `Err`. Because `ChildBounty` is removed from storage, the pallet has no remaining code path to retry the payout for a beneficiary/curator who never actually received funds, while the funds remain stranded in `child_bounty_account`.

A concrete failure trigger exists: if `payout` (or `curator_fee`) is smaller than `T::Currency::minimum_balance()` and the destination account does not already exist, `pallet_balances`'s transfer logic will refuse to create an account below the existential deposit, returning an error that is silently discarded here. This is a genuinely reachable condition for public, unprivileged callers of `claim_child_bounty` (any signed origin can call it once `PendingPayout` state's `unlock_at` has elapsed), so existing guards (`ensure!` on `unlock_at`, the `PendingPayout` status match) do nothing to prevent finalizing state on a failed transfer.

## Impact Explanation
This matches the Impact Gate's "duplicate settlement or payout" and "permanent user-fund lock" categories: the `ChildBounty` storage entry — the only pallet-level handle enabling a retriable payout — is deleted regardless of transfer outcome, so funds left in `child_bounty_account` after a failed transfer become unreachable through any subsequent call (both `claim_child_bounty` and `close_child_bounty` require an existing/appropriately-staged `ChildBounty` record). Simultaneously, a `Claimed` event is emitted attesting to a payout that did not occur, corrupting the pallet's off-chain-observable settlement record (`payout`, `beneficiary` fields in the event) and the on-chain `ParentChildBounties` count.

## Likelihood Explanation
Triggering requires no privileged access — any signed account can call the public `claim_child_bounty` extrinsic once the associated child bounty is `PendingPayout` and `unlock_at` has passed. The exact-balance transfer amounts (`curator_fee <= balance`, `payout = balance - curator_fee`) make outright `FundsUnavailable` unlikely, but the missing existential-deposit floor check on the destination side is a real, unguarded edge case: a `payout` or `curator_fee` value below `ExistentialDeposit` paid to a not-yet-existing account will be rejected by `pallet_balances`, and that rejection is discarded by the `debug_assert!`-only check. The absence of any explicit error handling means this is a defense-in-depth failure independent of how rare the triggering conditions are today.

## Recommendation
Replace the `debug_assert!(...is_ok())` calls with `?` propagation (or explicit `map_err`) so a failed transfer aborts the extrinsic before any storage mutation or event emission occurs:
```rust
T::Currency::transfer(&child_bounty_account, curator, curator_fee, AllowDeath)?;
T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)?;
```
If partial success needs to be tolerated, wrap the transfers and subsequent storage changes so that state is only finalized once both transfers are confirmed to succeed.

## Proof of Concept
1. Configure a runtime/test where `payout` (post curator-fee) is smaller than `T::Currency::minimum_balance()` and the `beneficiary` account does not yet exist (zero balance, never funded).
2. Move the child bounty into `PendingPayout` state via `award_child_bounty`, and advance the block number past `unlock_at`.
3. Call `claim_child_bounty(parent_bounty_id, child_bounty_id)` from any signed account.
4. `T::Currency::transfer(&child_bounty_account, beneficiary, payout, AllowDeath)` returns `Err` due to the destination balance being below the existential deposit; this is only checked via `debug_assert!`, a no-op in release builds.
5. Observe that `ChildBounty` storage is nonetheless removed, `ParentChildBounties` is decremented, and `Event::Claimed { payout, beneficiary, .. }` is emitted, while the funds remain stuck in `child_bounty_account` with no remaining pallet call able to retrieve them.
