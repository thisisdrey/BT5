### Title
Stale held-transaction `TransactionPriorityId` re-queued after nonce-dedup eviction recycles its Slab `TransactionId`, causing a single id to be double-queued with mismatched priority - (File: core/src/banking_stage/transaction_scheduler/transaction_state_container.rs)

### Summary
`TransactionStateContainer::hold_transaction` stores a `TransactionPriorityId` snapshot in `held_transactions` for a transaction that is currently *not* in `priority_queue` but still occupies its `id_to_transaction_state` (Slab) slot. If that same `TransactionId` slot is freed via `remove_by_id` (e.g. nonce-dedup eviction in `receive_and_buffer.rs`) while the stale reference is still sitting in `held_transactions`, the Slab can hand that numeric id to a brand-new, unrelated transaction. When `flush_held_transactions`/`push_ids_into_queue` later replays the stale entry, it inserts a second `BTreeSet` key `(old_priority, id)` for an id that is already queued as `(new_priority, id)`, producing two queue entries referencing the same `TransactionId`.

### Finding Description
`TransactionStateContainer` keeps two loosely-coupled views of the same `TransactionId`: the `priority_queue: BTreeSet<TransactionPriorityId>` and `id_to_transaction_state: Slab<TransactionState<Tx>>` [1](#0-0) . `hold_transaction` pushes a `TransactionPriorityId` into a side `held_transactions: Vec` without touching the map or queue [2](#0-1) . This is invoked from `retry_transaction` when `immediately_retryable == false`, leaving the transaction's slab slot occupied but its `TransactionPriorityId` neither in the queue nor removable through `recheck_iter` (which only walks `priority_queue`) [3](#0-2) .

Independently, the nonce-dedup path in `receive_and_buffer.rs` looks up `nonces_in_use` by nonce address and, on a match, unconditionally calls `container.remove_by_id(existing_nonce_priority_id.id)` before inserting the new transaction under a (potentially reused) Slab id [4](#0-3) . `nonces_in_use` is set once, at initial validation via `set_nonce_transaction_priority_id`, and is never refreshed by `retry_transaction`/`hold_transaction`, so it can still point at a transaction that has since been popped for scheduling, marked retryable, and re-held. `remove_by_id` calls `remove_state`, which frees the Slab slot via `id_to_transaction_state.remove(id)` and best-effort clears the nonce map entry, then attempts `priority_queue.remove(&priority_id)` — a silent no-op since the held id was never in the queue [5](#0-4) [6](#0-5) . Crucially, `held_transactions` is never scrubbed of the now-dangling entry.

Slab's free-list reuses the just-vacated key on the very next `vacant_entry()` call [7](#0-6) , and `receive_and_buffer.rs` immediately calls `insert_map_only` for the incoming (attacker-controlled) transaction and pushes it into the queue with its own priority [8](#0-7) . `TransactionPriorityId`'s `Ord`/`Eq` is derived over `(priority, id)`, so two entries with the same `id` but different `priority` are distinct `BTreeSet` keys, not deduplicated [9](#0-8) . When the scheduler later calls `flush_held_transactions` at the slot boundary, it replays the stale `(old_priority, id)` pair through `push_ids_into_queue`, inserting a second, independent queue entry that happens to alias the live transaction's `TransactionId` [10](#0-9) [11](#0-10) .

The `TransactionStateContainer` doc comment explicitly asserts the invariant this breaks: "The entry in the map should exist before insertion into the queue, and be removed only after the id is removed from the queue" [12](#0-11)  — here the map entry is removed (and reallocated to a different transaction) while a stale queue-eligible reference to the old id still exists outside the queue.

### Impact Explanation
Once both `(old_priority, id)` and `(new_priority, id)` are in `priority_queue`, the scheduler will pop `id` twice. `TransactionState::take_transaction_for_scheduling` explicitly panics on the second call ("transaction not already pending") [13](#0-12) , so the second pop of the aliased id crashes the banking-stage scheduler thread — a remotely triggerable validator panic/DoS. Alternatively, depending on timing relative to in-flight account locks, this can silently double-schedule/double-count a single live transaction, corrupting scheduler bookkeeping (`buffer_size`/`queue_size` counters, in-flight tracking) — an internal consistency violation of the container's core invariant.

### Likelihood Explanation
Requires: (1) attacker submits a durable-nonce transaction that gets fully validated and buffered (attacker must control/fund a real nonce account on-chain, which is achievable by any unstaked funded client, not requiring leader/validator privilege); (2) that transaction gets scheduled, sent to a `ConsumeWorker`, and returns retryable with `immediately_retryable == false` (held, not requeued); (3) before `flush_held_transactions` runs, the attacker sends a second transaction using the same nonce address, triggering nonce-dedup eviction of the still-held id; (4) the freed Slab slot is reused by the new transaction before flush. Steps 1–3 are attacker-controlled via ordinary packet submission; step 4 depends on Slab's free-list reuse behavior and container occupancy timing, which is plausible under sustained high packet churn but not guaranteed on every attempt — it is a timing-dependent, repeatable race rather than a deterministic single-shot exploit. The `immediately_retryable=false` condition in `consumer.rs`/`consume_worker.rs` could not be fully enumerated in this investigation; this affects exact reproduction preconditions and should be verified.

### Recommendation
When evicting a transaction via `remove_by_id`/`remove_state`, also invalidate any matching entry in `held_transactions` (e.g., store held ids in a way that can be checked/removed, or filter `held_transactions` against currently-valid Slab occupancy immediately before `flush_held_transactions` re-pushes them). Alternatively, have `flush_held_transactions` verify that `id_to_transaction_state` still logically owns that `(priority, id)` pair (e.g., by storing a generation counter alongside each Slab entry and validating it) before reinserting into `priority_queue`.

### Proof of Concept
```rust
// core/src/banking_stage/transaction_scheduler/transaction_state_container.rs (test module)
#[test]
fn test_held_transaction_stale_after_slab_id_reuse() {
    let mut container = TransactionStateContainer::with_capacity(4);

    // 1. Insert & pop transaction A (id=0), simulate scheduling.
    let (tx_a, max_age, prio_a, cost) = test_transaction(10);
    container.insert_new_transaction(tx_a, max_age, prio_a, cost);
    let popped = container.pop().unwrap(); // id=0, priority=10
    let _ = container
        .get_mut_transaction_state(popped.id)
        .unwrap()
        .take_transaction_for_scheduling();

    // 2. Transaction A comes back retryable but not immediately retryable -> held.
    let (tx_a_retry, ..) = test_transaction(10);
    container.retry_transaction(popped.id, tx_a_retry, /*immediately_retryable=*/ false);
    assert!(!container.is_queued(&popped)); // held, not queued
    assert_eq!(container.buffer_size(), 1);

    // 3. External eviction frees id=0's slab slot while it's still "held".
    container.remove_by_id(popped.id);
    assert_eq!(container.buffer_size(), 0);

    // 4. A brand-new transaction B reuses the freed slab slot (id=0) with a different priority.
    let (tx_b, max_age_b, prio_b, cost_b) = test_transaction(99);
    let id_b = container.insert_map_only(TransactionState::new(tx_b, max_age_b, prio_b, cost_b));
    assert_eq!(id_b, popped.id, "slab must reuse the freed key");
    let priority_id_b = TransactionPriorityId::new(prio_b, id_b);
    container.push_ids_into_queue(std::iter::once(priority_id_b));
    assert!(container.is_queued(&priority_id_b));

    // 5. Flush held transactions: stale entry for old priority (10) + reused id gets re-queued.
    container.flush_held_transactions();

    // BUG: both the stale (priority=10, id=0) and the live (priority=99, id=0)
    // now coexist in priority_queue, aliasing the same TransactionId.
    assert_eq!(
        container.queue_size(),
        1,
        "expected single logical entry per id, found duplicate queue entries for id {}",
        id_b
    );

    // Popping twice for the same id demonstrates the double-schedule / panic path:
    let first = container.pop().unwrap();
    let second = container.pop();
    assert!(
        second.is_none() || second.unwrap().id != first.id,
        "same TransactionId popped twice from priority_queue"
    );
}
```
Expected (pre-fix) result: the assertion on `queue_size()` fails (queue contains 2 entries for the same `id`), and/or the subsequent `pop()`/`take_transaction_for_scheduling()` sequence panics with `"transaction not already pending"`, demonstrating the corrupted, double-queued state described above.

    fn push_ids_into_queue(
        &mut self,
        priority_ids: impl Iterator<Item = TransactionPriorityId>,
    ) -> usize {
        for id in priority_ids {
            self.priority_queue.insert(id);
        }

        // The number of items in the `id_to_transaction_state` map is
        // greater than or equal to the number of elements in the queue.
        // To avoid the map going over capacity, we use the length of the
        // map here instead of the queue.
        let num_dropped = self
            .id_to_transaction_state
            .len()
            .saturating_sub(self.capacity);

        for _ in 0..num_dropped {
            let priority_id = self.priority_queue.pop_first().expect("queue is not empty");
            self.remove_state(priority_id.id);
        }

        num_dropped
    }

    fn remove_state(&mut self, id: TransactionId) -> TransactionPriorityId {
        let state = self.id_to_transaction_state.remove(id);
        let priority_id = TransactionPriorityId::new(state.priority(), id);

        if let Some(nonce_address) = state.nonce_address()
            && let Entry::Occupied(entry) = self.nonces_in_use.entry(*nonce_address)
            && *entry.get() == priority_id
        {
            entry.remove();
        }

        priority_id
    }
