### Title
Missing URL Scheme/Protocol Allowlisting on User-Supplied Remote URLs Enables RCE via `ext::`/`file://` Transport - (File: internal/gitaly/service/repository/create_repository_from_url.go)

### Summary
`CreateRepositoryFromURL` and `FetchRemote` accept a user-controlled `url` field and pass it directly to `git-clone(1)`/`git-fetch(1)` without validating or restricting the URL's protocol scheme. Neither RPC constrains git's allowed transports (e.g. via `protocol.allow`/`GIT_ALLOW_PROTOCOL`), so an ordinary caller of these RPCs can supply a `ext::<command>` or `file://` URL, letting git itself execute an arbitrary external command or read arbitrary local files on the Gitaly host.

### Finding Description
`cloneFromURLCommand` parses the caller-supplied `req.GetUrl()` with `url.Parse` and only inspects it to extract userinfo for HTTP auth headers; it performs no scheme validation before building the `git clone` argument list: [1](#0-0) 

The only URL-related check performed anywhere in the RPC is that the field is non-empty: [2](#0-1) 

`git clone`/`git fetch` support a `ext::<command>` transport helper that runs `<command>` as a subprocess and pipes git's protocol over it, effectively giving arbitrary command execution, and a `file://` transport that reads any local path readable by the Gitaly process. Modern git versions disable `ext`, `file`, and other risky protocols by default only when the environment variable `GIT_ALLOW_PROTOCOL` or config `protocol.allow`/`protocol.<name>.allow` is explicitly set to a restrictive value; absent such a restriction, these transports remain usable. A search of the codebase found no `GIT_ALLOW_PROTOCOL`, `protocol.allow`, or scheme allowlist anywhere in the git command construction path (`internal/git/gitcmd`, `internal/git/localrepo`, or the repository/remote services), and the `FetchRemote` validation function similarly only checks that the URL is non-empty: [3](#0-2) 

The one defensive measure present is scoped narrowly to bundle URIs, not to the primary clone/fetch URL itself: [4](#0-3) 

This is the same bug class as the reported issue — accepting an attacker-influenced URL and handing it to a mechanism (`bypassSecurityTrustResourceUrl` in the AngularJS case, `git clone`'s URL argument here) that performs privileged/unsafe operations based on scheme, without first restricting that scheme to a safe allowlist (`http://`/`https://`/`git://`/`ssh://`).

### Impact Explanation
An ordinary/unprivileged user who can invoke `CreateRepositoryFromURL` or `FetchRemote` (both reachable via normal GitLab import/mirror/fetch flows that proxy to Gitaly) can supply `ext::sh -c "<arbitrary command>"` as the URL, resulting in remote code execution on the Gitaly node under the Gitaly service account. Alternatively, `file:///etc/...` or `file://<internal path>` can be used to exfiltrate arbitrary local files into the newly created "cloned" repository, resulting in local file disclosure/storage escape. This is a severe, unprivileged-actor-reachable RCE/file-disclosure primitive.

### Likelihood Explanation
Both RPCs are part of Gitaly's public gRPC surface designed specifically to clone/fetch from an externally supplied URL, and the `url`/`RemoteParams.Url` field is fully attacker-controlled input from a normal repository-import or mirror-fetch action — no special privilege is required beyond what's needed to trigger an import or mirror update. Because there is no scheme check anywhere in the call path before the value reaches `git clone`/`git fetch`, exploitation only requires supplying a crafted URL string, making this highly likely to be exploitable if git's ext/file protocols aren't disabled at the git binary/config level elsewhere (no such restriction was found in this repository).

### Recommendation
Before constructing the clone/fetch command, validate `req.GetUrl()`/`RemoteParams.GetUrl()` against an explicit allowlist of schemes (`http://`, `https://`, and if required `git://`/`ssh://`), rejecting all others (in particular `ext::`, `file://`, `fd::`, and any URL without a recognized `://` prefix that could be interpreted as scp-style local paths in unintended ways). Additionally, set `GIT_ALLOW_PROTOCOL`/`protocol.allow=never` with an explicit allowlist for `http`/`https`/`git`/`ssh` on every git invocation that consumes a user-supplied remote URL, as defense in depth, mirroring the existing narrow mitigation already applied to `transfer.bundleURI`.

### Proof of Concept
1. Call `CreateRepositoryFromURL` with:
   ```
   Url: "ext::sh -c 'id > /tmp/pwned; git upload-pack .'"
   ```
2. `cloneFromURLCommand` parses this successfully with `url.Parse` (scheme `ext`) and passes it unmodified as the clone source argument to `git clone --bare "<url>" <targetPath>` [5](#0-4) .
3. Git's `ext` transport helper executes the embedded shell command on the Gitaly host as part of servicing the clone, achieving command execution outside of any git repository sandbox.

func validateCreateRepositoryFromURLRequest(ctx context.Context, locator storage.Locator, req *gitalypb.CreateRepositoryFromURLRequest) error {

func (s *server) validateFetchRemoteRequest(ctx context.Context, req *gitalypb.FetchRemoteRequest) error {
	if err := s.locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return structerr.NewInvalidArgument("%w", err)
	}

	if req.GetRemoteParams() == nil {
		return structerr.NewInvalidArgument("missing remote params")
	}

	if req.GetRemoteParams().GetUrl() == "" {
		return structerr.NewInvalidArgument("blank or empty remote URL")
	}

	return nil
}
