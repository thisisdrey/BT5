### Title
`DeleteAccountAction.beneficiary_id` is only syntax-validated, not existence-validated, so funds are permanently burnt if the beneficiary account is nonexistent - ([File: runtime/runtime/src/action_validation.rs])

### Summary
`DeleteAccountAction` carries a `beneficiary_id` that receives the account's entire remaining balance on deletion, functionally identical to the "beneficiary address" in the referenced report. The only validation performed on it is a syntactic `AccountId` format check; there is no check that the account actually exists. If the beneficiary account does not exist (e.g., a typo, a never-created account, or one that has since been deleted), the resulting balance-refund receipt fails and the funds are permanently burnt.

### Finding Description
`DeleteAccountAction` is defined with a single field, `beneficiary_id: AccountId` [1](#0-0) . Action validation for it is:

```rust
fn validate_delete_action(action: &DeleteAccountAction) -> Result<(), ActionsValidationError> {
    validate_action_account_id(&action.beneficiary_id)?;
    Ok(())
}
``` [2](#0-1) 

This only checks the string is a well-formed `AccountId`; it does not check that the account exists on chain.

When the delete executes, the account's remaining balance is used to build a `Transfer` refund receipt addressed to `beneficiary_id` unconditionally: `result.new_receipts.push(Receipt::new_balance_refund(&delete_account.beneficiary_id, account_balance));` [3](#0-2) , using `Receipt::new_balance_refund` which builds a `predecessor_id: "system"` `ActionReceipt` with a single `Transfer` action [4](#0-3) .

When this refund receipt is later processed against the (possibly nonexistent) beneficiary account, `check_account_existence` for `Transfer` actions on a missing account defers to `check_transfer_to_nonexisting_account`, which only allows implicit-account auto-creation and explicitly documents that refunds never auto-create accounts:

```rust
// - Refunds don't automatically create accounts, because refunds are free and
// we don't want some type of abuse.
// - Account deletion with beneficiary creates a refund, so it'll not create a
// new account.
Ok(())
} else {
    Err(ActionErrorKind::AccountDoesNotExist { account_id: account_id.clone() }.into())
}
``` [5](#0-4) 

So if `beneficiary_id` is a plain (non-implicit) account that does not exist, the refund receipt execution fails with `AccountDoesNotExist`. Per the protocol's refund semantics: "If the execution of a refund fails, the refund amount is burnt." [6](#0-5)  This is implemented at the runtime level: for system-predecessor (refund) receipts, on failure the deposit is added to `other_burnt_amount` rather than returned anywhere: 
```rust
let gas_refund_result = if receipt.predecessor_id().is_system() {
    // If the refund fails tokens are burned.
    if result.result.is_err() {
        stats.balance.other_burnt_amount = safe_add_balance(...)?
    }
``` [7](#0-6) 

This mirrors the report's core defect: an unvalidated, high-value "beneficiary" recipient field whose misconfiguration causes an unrecoverable loss of funds, with no mechanism to correct it after the fact (the account is already deleted).

### Impact Explanation
Any account owner (unprivileged signer) who submits a `DeleteAccount` action with an incorrect, mistyped, or already-nonexistent `beneficiary_id` (a valid-format but non-existent named `AccountId`) will have their entire remaining account balance permanently burnt instead of transferred, since the account is deleted in the same execution and cannot be recovered. This is a concrete, irreversible loss-of-funds condition reachable directly from an ordinary transaction, with no privileged access required.

### Likelihood Explanation
Likelihood is moderate to high: this requires only a mistake (typo, stale/copy-pasted account id, or targeting an account that gets deleted between construction and submission of the transaction) by an ordinary user issuing a `DeleteAccount` action — a common, everyday, unprivileged operation. No validation step ever confirms the beneficiary account is live before the irreversible account deletion + balance-burn occurs.

### Recommendation
Add an existence check for `beneficiary_id` before executing account deletion (e.g., in `action_delete_account`, look up the beneficiary account in `state_update` and reject the action, e.g. with a new `ActionErrorKind` such as `BeneficiaryAccountDoesNotExist`, if it isn't present and isn't a valid implicit account eligible for creation), rather than relying on the format-only check in `validate_delete_action` at [2](#0-1) .

### Proof of Concept
1. Account `alice.near` calls `DeleteAccount { beneficiary_id: "nonexistent.near" }`, where `nonexistent.near` is a syntactically valid but never-created account.
2. Action validation passes because `validate_action_account_id` only checks the string format [2](#0-1) .
3. `action_delete_account` deletes `alice.near` and enqueues a `Receipt::new_balance_refund(&"nonexistent.near", account_balance)` [3](#0-2) .
4. When that refund receipt is processed, `check_account_existence`/`check_transfer_to_nonexisting_account` rejects it with `AccountDoesNotExist` since it's a refund and not eligible for implicit creation [5](#0-4) .
5. The failed refund's deposit is added to `other_burnt_amount`, permanently destroying `alice.near`'s former balance [7](#0-6) , matching the documented "refund fails, amount is burnt" rule [6](#0-5) .
