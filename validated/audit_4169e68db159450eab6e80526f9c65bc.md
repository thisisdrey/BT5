### Title
No vulnerability found - gas exhaustion in the Wallet Contract promise chain cannot cause an apply-path panic or chunk halt

### Summary
The premise assumes that running out of gas mid-way through the `rlp_execute` promise chain (`storage_balance_of` → `storage_deposit`+`transfer` → `rlp_execute_callback`) could cause an "Out-Of-Gas apply-path panic" that halts chunk processing. This is not how NEAR's gas accounting works: every gas-exhaustion path documented in the codebase resolves to a graceful `FunctionCallError::HostError(HostError::GasExceeded)` / `"Exceeded the prepaid gas."` `ActionError`, which is a normal, on-chain-committed execution outcome, not a panic.

### Finding Description
`validate_tx_relayer_data` only guarantees `env::prepaid_gas().as_gas() >= tx.gas_limit * GAS_MULTIPLIER` [1](#0-0) , and the eth-emulation ERC-20 transfer arm always allocates a fixed `2 * FIVE_TERA_GAS` for the inner `ft_transfer` action regardless of `tx.gas_limit` [2](#0-1) . If an attacker crafts `tx.gas_limit` to just clear this check while under-provisioning gas for the downstream chain (`storage_balance_of` → conditionally `storage_deposit`+`transfer` → `nep_141_storage_balance_callback`/`rlp_execute_callback`, per `inner_rlp_execute` and `nep_141_storage_balance_callback` in `lib.rs` [3](#0-2) [4](#0-3) ), the outcome is that the wasm host function running out of gas returns `HostError::GasExceeded`, which the runtime converts into `VMOutcome::abort` → `FunctionCallError::HostError(HostError::GasExceeded)` → `ActionErrorKind::FunctionCallError` — a normal `ActionError`, not a panic [5](#0-4) . This is corroborated by `GasCounter::process_gas_limit`, whose comments explicitly describe how a prior version of this exact logic *could* have led to a node-crashing `assert`, and how that was deliberately replaced with saturating arithmetic so that an attacker "achieves... throwing some of their gas away," never a crash [6](#0-5) . The existing wallet-contract test `test_insufficient_gas` demonstrates precisely this scenario (insufficient gas attached to `rlp_execute`) resolving to `"Exceeded the prepaid gas."` with the contract remaining fully usable afterward, no panic, no halt [7](#0-6) . If gas runs out mid-promise-chain (e.g., at `storage_deposit`), the promise creation host calls simply fail with `GasExceeded` inside that receipt's execution, producing `PromiseResult::Failed` for dependent receipts, which is exactly the graceful failure mode the question incorrectly claims is bypassed — this is the intended and only outcome path in NEAR's gas model, not an OOG "apply-path panic."

### Impact Explanation
None. There is no code path that converts gas exhaustion into a process panic or chunk-halting fault; the runtime's gas accounting was specifically hardened (see the historical fix referenced in `gas_counter.rs`) to avoid exactly this class of issue, replacing an `assert`-based approach with saturating arithmetic that always yields a normal `ActionError`.

### Likelihood Explanation
Not applicable — the described failure mode does not exist in the current runtime.

### Recommendation
No fix needed for this scenario. If gas budgeting for the ERC-20 transfer promise chain is a concern, standard hardening would be to make `NEP_141_STORAGE_DEPOSIT_GAS`, `NEP_141_STORAGE_BALANCE_OF_GAS`, and the callback gas constants scale with (or be validated against) `tx.gas_limit` so that under-resourced multi-hop chains fail fast with a graceful `ExecuteResponse` error rather than a `PromiseResult::Failed` deep in the chain — but this is a UX/liveness-of-response concern, not a chunk-halting or fund-loss vulnerability.

### Proof of Concept
Not required — no vulnerability exists in the audited scope. `runtime/near-wallet-contract/implementation/wallet-contract/src/tests/sanity.rs::test_insufficient_gas` already demonstrates that under-provisioned gas resolves gracefully via `ActionError`/`ExecuteResponse` and the contract remains usable, which is the pattern that would also govern the multi-hop ERC-20 case described in the question.

    pub(crate) fn process_gas_limit(&mut self, new_burnt_gas: Gas, new_used_gas: Gas) -> HostError {
        use std::cmp::min;
        // Never burn more gas than what was paid for.
        let hard_burnt_limit = min(self.prepaid_gas, self.max_gas_burnt);
        self.fast_counter.burnt_gas = min(new_burnt_gas.as_gas(), hard_burnt_limit.as_gas());
        debug_assert!(hard_burnt_limit.as_gas() >= self.fast_counter.burnt_gas);

        // Technically we shall do `self.promises_gas = 0;` or error paths, as in this case
        // no promises will be kept, but that would mean protocol change.
        // See https://github.com/near/nearcore/issues/5148.
        // TODO: consider making this change!
        let used_gas_limit = min(self.prepaid_gas, new_used_gas);
        // [CONTINUATION OF THE PREVIOUS COMMENT]
        //
        // Now, there are two distinct ways an attacker can attempt to exploit this code given
        // their full control of the `new_used_gas` value.
        //
        // 1. `self.prepaid_gas < new_used_gas` This is perfectly fine and would be the happy path,
        //    were the computations performed with arbitrary precision integers all the time.
        // 2. `new_used_gas < new_burnt_gas` means that the `new_used_gas` computation wrapped
        //    and `used_gas_limit` is now set to a lower value than it otherwise should be. In the
        //    past this would have triggered an unconditional assert leading to nodes crashing and
        //    network getting stuck/going down. We don’t actually need to assert, though. By
        //    replacing the wrapping subtraction with a saturating one we make sure that the
        //    resulting value of `self.promises_gas` is well behaved (becomes 0.) All a potential
        //    attacker has achieved in this case is throwing some of their gas away.
        self.promises_gas =
            used_gas_limit.saturating_sub(Gas::from_gas(self.fast_counter.burnt_gas));

        // If we crossed both limits prefer reporting GasLimitExceeded.
        // Alternative would be to prefer reporting limit that is lower (or
        // perhaps even some other heuristic) but old code preferred
        // GasLimitExceeded and we’re keeping compatibility with that.
        if new_burnt_gas > self.max_gas_burnt {
            HostError::GasLimitExceeded
        } else {
            HostError::GasExceeded
        }

#[tokio::test]
async fn test_insufficient_gas() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, .. } = TestContext::new().await?;

    // If not enough gas is attached to the `rlp_execute` call then the action fails.
    let target = "some.account.near".to_string();
    let action = Action::FunctionCall {
        receiver_id: target.clone(),
        method_name: "greet".into(),
        args: br#"{"name": "Aurora"}"#.to_vec(),
        gas: 5_000_000_000_000,
        yocto_near: 0,
    };
    let signed_transaction = utils::create_signed_transaction(
        0,
        &target.parse().unwrap(),
        Wei::zero(),
        action,
        &wallet_sk,
    );

    let error = wallet_contract
        .inner
        .call(crate::tests::RLP_EXECUTE)
        .args_json(serde_json::json!({
            "target": target,
            "tx_bytes_b64": codec::encode_b64(&codec::rlp_encode(&signed_transaction))
        }))
        .gas(near_gas::NearGas::from_tgas(7))
        .transact()
        .await
        .unwrap()
        .raw_bytes()
        .unwrap_err();

    assert!(
        error.to_string().contains("Exceeded the prepaid gas."),
        "Error should be that there was not enough gas"
    );

    // But the contract is still usable afterwards.
    utils::deploy_and_call_hello(&worker, &wallet_contract, &wallet_sk, 0).await?;

    Ok(())
}
