### Title
Intra-batch account-lock conflicts are not detected by `AccountLocks::try_lock_transaction_batch`, allowing two conflicting transactions in the same batch to both acquire the same account lock - ([File: accounts-db/src/account_locks.rs])

### Summary
`AccountLocks::try_lock_transaction_batch` performs conflict checking (`can_lock_accounts`) for every transaction in the batch in a first pass that only reads `self`, and only afterwards performs the actual locking (`lock_accounts`) in a second pass. Because the check pass never mutates lock state, it cannot see locks that would be produced by earlier transactions *within the same batch*, so two (or more) transactions in one batch that conflict on the same account (e.g. both write-lock account `A`, or one writes and another reads `A`) will both be marked `Ok` in the check pass and both will be unconditionally locked in the apply pass.

### Finding Description
`try_lock_transaction_batch` is implemented as two separate passes: [1](#0-0) 

The first pass calls `self.can_lock_accounts(keys.clone())` for every transaction using an immutable borrow of `self`, so it never applies any locks — it only checks against the lock state that existed *before this batch call began* (locks left over from previously-processed batches): [2](#0-1) 

The second pass then unconditionally calls `self.lock_accounts(keys)` for every transaction marked `Ok` in the first pass, in order. `lock_accounts` / `lock_write` / `lock_readonly` do not re-check for conflicts — they simply increment counters: [3](#0-2) 

Consequence: if transaction `i` and transaction `i+1` in the *same batch* both touch account `A` with a conflicting access pattern (write/write or write/read), the check for transaction `i+1` is evaluated against the pre-batch lock state — which does not yet reflect transaction `i`'s (not-yet-applied) lock — so both are found lock-able. In the second pass both transactions are then actually locked, leaving `write_locks[A]` incremented to 2 (an internally inconsistent state that should never occur under correct write-exclusivity), or a simultaneous write-lock and read-lock on `A`. This directly violates the function's own documented contract ("Lock accounts for all transactions in a batch which don't conflict with existing locks") and the mutual-exclusion invariant that `AccountLocks` exists to enforce for the parallel/concurrent transaction execution pipeline that consumes these results to decide which transactions may run concurrently.

### Impact Explanation
Downstream consumers (e.g. batch/bank transaction execution scheduling that gates concurrent execution on these lock results) rely on `try_lock_transaction_batch`'s per-transaction `Ok`/`Err(AccountInUse)` results to guarantee that two transactions touching the same account are never run concurrently. Because the bug lets conflicting transactions within one batch both receive `Ok`, an unprivileged attacker who gets two of their own transactions (write/write or write/read on the same account) into a single processing batch can cause the execution layer to believe both are safe to execute concurrently, corrupting the mutual-exclusion guarantee. This is an "invalid recorded block / account-lock correctness" class issue affecting transaction execution correctness on the leader, not merely a metrics/logging cosmetic defect.

### Likelihood Explanation
This is deterministic and requires only a single call to `try_lock_transaction_batch` with a batch containing two transactions that share a conflicting account access — no staked/privileged access, no races with other validators, and no special timing is needed. The only precondition is that both transactions land in the same processing batch, which an attacker can trivially arrange by submitting both transactions in the same message/packet or within the batching window used by the ingesting stage.

### Recommendation
Merge the check and lock passes into a single sequential loop so that each transaction's lock check is evaluated against the lock state *as mutated by all previously-processed transactions in the same batch* (i.e., call `can_lock_accounts` immediately followed by `lock_accounts` for each transaction in order, rather than splitting into two independent passes over the whole batch).

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (test module)
#[test]
fn test_try_lock_transaction_batch_intra_batch_conflict_bug() {
    let pubkey_a = Pubkey::new_unique();
    let mut locks = AccountLocks::default();

    // Two transactions in ONE batch call, both write-locking the same account.
    let tx0_keys = vec![(&pubkey_a, true)].into_iter();
    let tx1_keys = vec![(&pubkey_a, true)].into_iter();

    let batch: Vec<TransactionResult<_>> = vec![Ok(tx0_keys), Ok(tx1_keys)];

    let results = locks.try_lock_transaction_batch(batch);

    // Correct behavior: the second write-lock on the same account within
    // the same batch must be rejected with AccountInUse.
    assert_eq!(results[0], Ok(()));
    assert_eq!(
        results[1],
        Err(TransactionError::AccountInUse),
        "BUG: both conflicting write-locks on the same account within one \
         batch were granted, violating mutual exclusion"
    );
}
```
Expected/actual: the assertion on `results[1]` fails — the current implementation returns `Ok(())` for both transactions, demonstrating that account `A` is simultaneously write-locked twice within a single batch call.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    fn lock_readonly(&mut self, key: &Pubkey) {
        *self.readonly_locks.entry(*key).or_default() += 1;
    }

    fn lock_write(&mut self, key: &Pubkey) {
        *self.write_locks.entry(*key).or_default() += 1;
    }
