## Non-constant-time comparison of the RPC `authorization` bearer token allows timing-based token recovery - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Every HTTP RPC handler that gates a privileged endpoint behind `connection_options.auth_token` compares the client-supplied `authorization` header to the configured secret using Rust's built-in `String`/`&str` `!=` operator, which is not constant-time. This is the same bug class flagged in the Etherpad advisory (CWE-208/209, non-constant-time password compare with no failure delay), reproduced across several stacks-node HTTP endpoints.

### Finding Description
The `auth_token` is a shared secret used to authenticate `stacks-signer` communication with the node and to authorize `/v2/blocks?broadcast=1`/`/v3/block_proposal` writes: [1](#0-0) 

Multiple request handlers implement the check as a plain `!=` comparison between the header value and the stored password:

- `RPCBlockProposalRequestHandler::try_parse_request`: [2](#0-1) 
- `RPCNakamotoBlockReplayRequestHandler::try_parse_request`: [3](#0-2) 
- `RPCTransactionSimulateRequestHandler::try_parse_request`: [4](#0-3) 
- `RPCPostBlockRequestHandler::try_parse_request` (used for `/v3/blocks?broadcast=1`): [5](#0-4) 

Rust's `String`/`&str` equality (`PartialEq`) is implemented as a byte-wise comparison that short-circuits at the first mismatching byte; it provides no constant-time guarantee (unlike `subtle::ConstantTimeEq` or `crypto.timingSafeEqual` used in the Etherpad fix). Because the response path also differs based on how far the comparison proceeded (more matching prefix bytes ⇒ marginally more CPU work before the 401 is returned), an attacker who can send many requests can, in principle, use timing measurements to infer the auth token byte-by-byte instead of brute-forcing the whole secret space at once. There is no failure delay, throttling, or timing-safe compare on any of these code paths.

### Impact Explanation
If exploitable, this constitutes an authentication-bypass primitive against `connection_options.auth_token`, which gates:
- unauthenticated write of blocks into the node via `/v3/blocks?broadcast=1` and `/v3/block_proposal` (block proposal validation), and
- the signer↔node communication channel.

Successfully recovering the token would let a remote, unauthenticated attacker inject block proposals or broadcast requests as if it were the trusted signer/miner, i.e., an auth bypass leading to unauthorized write to node state — which maps to the "Critical" impact bucket (unauthenticated/unauthorized write to state, auth bypass).

### Likelihood Explanation
Likelihood is low in practice. Extracting a secret via network timing side-channels requires an extremely large number of statistically-averaged requests to overcome network jitter, load-dependent scheduling noise, and TLS/TCP overhead, and the signal here (a few extra byte comparisons in a `memcmp`-style loop) is minute compared to full request/response round-trip variance. This is the classic "theoretical timing side-channel over network" scenario — it is real as a code-quality/hardening gap (exactly what the Etherpad advisory hardened), but is not a practically demonstrated, low-effort remote exploit like the other categories in scope (forged StackerDB chunk, unchecked wire length, etc.).

### Recommendation
Replace all direct `!=`/`==` string comparisons of `auth_header` against the configured `auth_token`/password with a constant-time comparison (e.g., via the `subtle` crate's `ConstantTimeEq`, or by hashing both sides with a keyed MAC before comparing), across `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, and `postblock_v3.rs`. Consider consolidating the check into a single shared helper to avoid future drift, and optionally add a small uniform delay on authentication failure.

### Proof of Concept
Not applicable as a concrete, demonstrable remote exploit — this is a hardening gap rather than a proven practical attack, given the network-timing-noise caveat discussed above.
