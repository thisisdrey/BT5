### Title
Replay-window check/update race (TOCTOU) allows a captured packet to be processed twice before the anti-replay window commits - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` implement the Dahlia bug class exactly: a state-dependent security check (`window.Check`) is performed, the state is used to gate an expensive/consequential operation (AEAD decrypt), and only *afterward* is the authoritative state update (`window.Update`) applied and its own result checked. Because the check, the decrypt, and the update are three separate lock-scoped critical sections rather than one atomic operation, two concurrent deliveries of the same captured ciphertext can both pass the stale `Check` before either has recorded itself via `Update`.

### Finding Description
`Decrypt` reads the replay window inside its own lock, releases the lock, decrypts, and only then re-acquires the lock to mark the counter as seen: [1](#0-0) 

`VerifyRelay` (used to authenticate and forward relayed frames through a relay node) has the identical structure: [2](#0-1) 

`Bits.Check` is a pure read (no mutation) and `Bits.Update` is the only call that actually marks a counter as consumed: [3](#0-2) 

Because `Check` and `Update` are invoked as two independent, separately-locked operations instead of a single atomic "check-and-set", a second copy of the exact same captured UDP datagram delivered concurrently (before the first copy's `Update` call executes) will see `Check` return `true` against the still-stale window, just like `BorrowImpl.internalBorrow` in the referenced report consuming `borrowedShares`/`maxBorrowAssets` computed from state that had not yet accrued interest. In both cases a decision is made against data that is authoritative-looking but not yet updated to reflect the in-flight operation, permitting the same "unit of work" (borrow / packet) to be admitted more than once.

### Impact Explanation
This is directly reachable by a network-level attacker who never holds a CA-signed certificate: they only need to capture one legitimate ciphertext frame on the wire and re-inject it (UDP duplication/replay requires no cryptographic capability). If duplicate/racing delivery causes the second copy to also pass `Check` before `Update` commits, the anti-replay guarantee that Nebula's data plane and relay path rely on to prevent duplicate processing is defeated for that window. For `VerifyRelay` specifically this maps to a relay re-forwarding a replayed frame, which is exactly the class of issue previously flagged and partially fixed in this codebase's changelog ("Advance the replay window on relayed packets so a relay drops replayed frames instead of re-forwarding them", "Lock replay window updates so concurrent readers can't corrupt it"). Those fixes addressed data-structure corruption and forwarding-without-updating, but the check→decrypt→update ordering itself is still split across three separately-locked sections, so the logical TOCTOU window on the check remains.

### Likelihood Explanation
Exploitation only requires the ability to duplicate/replay a captured UDP datagram to the target (or relay) faster than the first delivery's processing pipeline completes its `Update` call — a purely network-timing condition, not requiring any credential, valid certificate, or privileged position beyond basic packet capture/replay capability. This is a narrow race window (the gap between `Check` and `Update`, which includes an AEAD decrypt), so success is probabilistic and requires closely-timed duplicate delivery (e.g., via multiple listener routines or UDP GSO/batch reads), which is plausible on multi-threaded listener configurations (`tun.routines`/`listen.batch` > 1) that this codebase explicitly supports.

### Recommendation
Make the replay-window check-and-mark atomic with respect to the AEAD authentication result: hold a single lock (or use a single `CheckAndReserve`-style call) across the check, and only release/finalize the window slot after decryption success, so no second caller can observe the pre-update window state. Concretely, refactor `Bits` to expose a combined `Reserve(i) (ok bool, commit func(), abort func())` (or perform the check immediately before commit under one held lock spanning the decrypt) instead of independent `Check`/`Update` calls guarded by separate lock acquisitions in `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Establish a tunnel (or relayed tunnel) between two Nebula nodes.
2. Capture a single legitimate encrypted data-plane (or `MessageRelay`) frame off the wire.
3. Re-inject two copies of that exact frame back-to-back into the receiving/relaying node's UDP listener, ideally via two listener routines (`tun.routines`/`listen.batch` > 1) so they are processed concurrently by separate goroutines calling `ConnectionState.Decrypt` / `VerifyRelay`.
4. If both goroutines execute `cs.window.Check` before either executes `cs.window.Update`, both will decrypt/authenticate successfully; the losing goroutine's own `Update` call will report `ErrAlreadySeen`, but its `DecryptDanger`/authentication step already ran, and for the relay path this can result in a duplicate forward of the frame before the second `Update` result is checked — reproducing the same "duplicate replay accepted" outcome the existing `TestRelayReplayProtection` regression test targets, but via a timing race rather than a strictly sequential replay.

Note: I could not execute this PoC in the current environment (no code execution/terminal access) — the analysis above is based on static review of `connection_state.go` and `bits.go`; confirming the exact race window and its practical exploitability under real scheduler timing would require running the reproduction in a live/test environment.

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

// Update has three branches:
//   - i == b.current+1: fast path; advance the cursor by one and lose-count
//     the slot we just stomped (only past warmup; see the i > b.length guard
//     below).
//   - i  >  b.current+1: jump path; clear all slots between current and i
//     (or up to a full window's worth, whichever is smaller) via clearRange,
//     then mark i. Two arms here: a warmup arm that handles the very first
//     window before the cursor has slid, and a steady-state arm that treats
//     every cleared empty slot as a lost packet.
//   - i  <= b.current: in-window check for duplicates; out-of-window otherwise.
//
// NewBits seeds bits[0]=1 so counter 0 looks "received" — Update never
// clears that marker during warmup (clearRange skips position 0 when
// startPos=1), and once b.current >= b.length the marker is no longer
// consulted. The marker prevents a fictitious "lost" hit on the first real
// counter.
func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
