### Title
StackerDB write-frequency rate limit (`write_freq`) is never enforced at the chunk write path - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBConfig::write_freq` is documented as "the minimum wall-clock time between writes to the same slot" [1](#0-0) , and a dedicated `net_error::TooFrequentSlotWrites` variant exists specifically to reject writes that violate it [2](#0-1) . However, the only function that actually persists a chunk to the on-disk StackerDB, `StackerDBTx::try_replace_chunk`, never checks `write_freq` or the stored `write_time` before writing — it only checks chunk size, signature, staleness, and `max_writes` [3](#0-2) .

### Finding Description
The intended invariant is: `now - slot_validation.write_time >= config.write_freq` before a slot may be overwritten. This equality/bound is never evaluated anywhere in the write path:
- `try_replace_chunk` retrieves `slot_validation` (which contains `write_time`) only to check the signer and `slot_version`, never comparing `write_time` against `config.write_freq` [4](#0-3) .
- The HTTP `POST /stackerdb chunk` handler calls `tx.try_replace_chunk(...)` directly, with no additional frequency gate before or after [5](#0-4) .
- The gossip/network validation function `validate_received_chunk` explicitly documents that it "does not check write frequency, since the caller has different ways of doing this" [6](#0-5) , and `handle_unsolicited_StackerDBPushChunk` likewise states "The write frequency is not checked for this chunk" [7](#0-6) , deferring the responsibility elsewhere.
- Searching the actual storage/enforcement code (`stackslib/src/net/stackerdb/db.rs`) turns up no reference to `write_freq` or `TooFrequentSlotWrites` at all; those symbols only appear in `sync.rs` (client-side heuristics about which slots to bother re-fetching), `config.rs` (parsing/bounds of the config value), and tests.

This mirrors the reported bug class: a protocol parameter meant to bound the rate/timing of a state-changing operation (`write_freq`, analogous to `decreaseStakeLockupDuration`) exists in configuration and is referenced in comments/errors, but the code path that actually performs the write never enforces it, so the "protection window" is unconditionally bypassed rather than merely misconfigurable.

### Impact Explanation
Because `try_replace_chunk` is the single authoritative gate for committing a chunk (used by both the authenticated HTTP write endpoint and internally for accepted P2P pushes), the missing `write_freq` check means any party holding a valid slot-signing key can write to their slot at unbounded frequency, up to `max_writes` versions, with no wall-clock throttling. Every accepted write is broadcast/replicated to StackerDB peers (`log_stored_stackerdb_chunk`) [8](#0-7) , so a signer can force much higher network-wide chunk-propagation volume and version churn than the protocol design intends, and always win any freshness/version race against honest peers who are wall-clock-throttled by convention rather than by enforcement. This is a bounded, remotely triggerable compute/bandwidth amplification against the read/replication path (StackerDB chunk propagation), falling under the "bounded compute DoS" / rate-limit-bypass impact class.

### Likelihood Explanation
High likelihood for any actor who is a legitimate slot signer (a normal, permitted StackerDB participant, e.g., a Nakamoto signer) — no special privilege beyond a normal signing key is required, and the check is unconditionally absent rather than merely misconfigured, so it triggers on every single write, not only under specific config values.

### Recommendation
Enforce `config.write_freq` inside `StackerDBTx::try_replace_chunk` (or immediately before calling it) by comparing `get_epoch_time_secs() - slot_validation.write_time` against `self.config.write_freq`, returning `net_error::TooFrequentSlotWrites` when violated, consistent with how `max_writes` and staleness are already enforced in the same function.

### Proof of Concept
1. Configure a StackerDB contract with a non-zero `write-freq` (e.g., 120 seconds) for a slot owned by key `sk`.
2. Sign and POST a chunk to `/v2/stackerdb/.../chunks` for that slot at version 1; it is accepted.
3. Immediately (no wait) sign and POST a chunk at version 2, then version 3, etc., in rapid succession from the same key.
4. Because `try_replace_chunk` only checks `slot_version > slot_validation.version` and `slot_version <= config.max_writes` (never `write_time`), every rapid-fire write succeeds and is re-broadcast to the network, up to `max_writes`, with no rate limiting — despite the configured `write_freq` implying such writes should be rejected as `TooFrequentSlotWrites` [9](#0-8) .

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
