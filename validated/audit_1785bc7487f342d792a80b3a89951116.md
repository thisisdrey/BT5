Based on my research, I found a strong analog for this CVE class in Bazel's own C++ ZIP-parsing code used by `singlejar`/`ijar`—the tools that build and merge JAR files (including externally-fetched jars) as part of every `java_binary`/`java_library` build.

### Title
Out-of-bounds read when parsing a crafted Zip64 extra field's attribute array in Bazel's JAR/ZIP header parser - (File: `src/tools/singlejar/zip_headers.h`)

### Summary
`singlejar` (used to assemble/merge deploy jars) and `ijar` both parse Central Directory Headers (`CDH`) and Local Headers (`LH`) from ZIP/JAR files that can come from attacker-controlled inputs (e.g. a jar file consumed as a build input). When a 32-bit size/offset field equals `0xFFFFFFFF` (the "value is stored in Zip64 extra field" sentinel), Bazel looks up the companion `Zip64ExtraField` and reads a 64-bit value at a computed array index — without validating that the extra field actually contains that many attributes.

### Finding Description
The `Zip64ExtraField` class exposes: [1](#0-0) 

`attr64(int index)` directly indexes into the flexible array `attr_[]` based on the field's declared `payload_size()` divided by 8 (`attr_count()`), but callers never check `index < attr_count()` before calling `attr64(index)`.

Callers compute the index purely from the *32-bit* fields' sentinel values, not from the actual extra-field payload size, e.g. in `CDH::compressed_file_size()`: [2](#0-1) 

and in `CDH::local_header_offset()`: [3](#0-2) 

The lookup itself, `Zip64ExtraField::find`, only validates that the extra-field header lies within the declared `extra_fields_length()` window; it does not validate the *content length* against the number of attributes a caller intends to read: [4](#0-3) [5](#0-4) 

This is structurally identical to the vim CVE: a persisted structure (Zip64 extra field) stores a size/count, and a *separate* piece of untrusted data (the 32-bit size sentinels) is used to compute an offset/index into that structure's payload — without cross-validating that the payload is actually large enough. If an attacker crafts a CDH/LH where `compressed_file_size32`/`uncompressed_file_size32`/`local_header_offset32` are `0xFFFFFFFF` but the accompanying Zip64 extra field's `payload_size` is smaller than required (e.g. 0 or 8 bytes when 24 are implied), `attr64()` reads 8 bytes past the declared/allocated attribute array — an out-of-bounds read within (or past the end of) the memory-mapped input file.

### Impact Explanation
The archive is memory-mapped (`mapped_file_.MapExisting`, see `InputJar::Open`), so an out-of-bounds `attr64()` read can pull adjacent heap/mapped-file bytes into a size or file offset that `singlejar`/`ijar` then use to determine how many bytes of the entry to copy into the output jar (`OutputJar::AddJar`, `TransientBytes::DecompressEntryContents`). This can leak adjacent process memory into the produced deploy/output jar (confidentiality impact, matching the original CVSS `C:L`), or crash the tool by dereferencing a wildly out-of-range pointer/length derived from garbage data (matching CVSS `A:H`).

### Likelihood Explanation
`singlejar` is invoked on every Java build to merge jar inputs, some of which may be externally supplied (e.g., prebuilt/third-party jars declared as inputs to `singlejar`/`ijar` actions). An attacker who controls the bytes of one such jar (matching its own declared/pinned checksum) can trivially construct a CDH/LH with mismatched Zip64 extra-field lengths, satisfying "AC:L, PR:N, UI:R" from the origin advisory — the victim's build simply needs to consume the crafted archive.

### Recommendation
Bound-check `Zip64ExtraField::attr64()`'s index against `attr_count()` (derived from the actual `payload_size()`) before indexing, and have every caller (`CDH`/`LH` size/offset accessors) treat an out-of-range index as a corrupt-archive error instead of reading past the field's declared payload.

### Proof of Concept
A JUnit/`gtest` proof (in the style of `src/tools/singlejar/zip_headers_test.cc`) would:
1. Build a `CDH` with `compressed_file_size32 = uncompressed_file_size32 = local_header_offset32 = 0xFFFFFFFF`.
2. Attach a `Zip64ExtraField` extra field with `payload_size = 0` (i.e., zero stored 64-bit attributes).
3. Call `cdh->compressed_file_size()` / `cdh->local_header_offset()` and observe (under ASan) an out-of-bounds heap read past the extra-field buffer, since `attr64(0)`/`attr64(2)` is invoked despite `attr_count() == 0`. [6](#0-5)

class ExtraField {
 public:
  static const ExtraField* find(uint16_t tag, const uint8_t* start,
                                const uint8_t* end) {
    while (start < end) {
      if (ziph::byte_ptr(start) + sizeof(ExtraField) > ziph::byte_ptr(end)) {
        break;
      }
      auto extra_field = reinterpret_cast<const ExtraField*>(start);
      if (ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)) {
        break;
      }
      if (extra_field->is(tag)) {
        return extra_field;
      }
      start = ziph::byte_ptr(start) + extra_field->size();
    }
    return nullptr;
  }
