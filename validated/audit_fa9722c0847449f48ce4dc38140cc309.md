### Title
Shielded-API endpoints accept spend-authorizing key material (`ask`) via unauthenticated HTTP GET query parameters, exposing them in plaintext logs/history - (File: framework/src/main/java/org/tron/core/services/http/GetAkFromAskServlet.java)

### Summary
Several FullNode HTTP endpoints under `/wallet/*` that operate on Sapling shielded-pool secret key material (`ask`, spending key, expanded spending key) accept these secrets as `doGet` query-string parameters in addition to POST body, mirroring the CWE-319 pattern in the Jenkins advisory where sensitive credentials were transmitted/rendered in a way that exposed them in plaintext (form fields → here, GET query strings, access logs, browser/proxy history).

### Finding Description
`GetAkFromAskServlet.doGet` reads the raw spend-authorizing key `ask` straight from `request.getParameter("value")` and forwards it to `wallet.getAkFromAsk(...)`: [1](#0-0) 

The sibling servlet `GetExpandedSpendingKeyServlet.doGet` does the same for a full expanded spending key: [2](#0-1) 

Because these are `GET` handlers, the secret is placed in the URL query string. Query strings are routinely captured in web-server/reverse-proxy access logs, browser history, HTTP Referer headers to third parties, and any intermediary caches/monitoring — the exact "plaintext exposure via a transport/storage path not intended for secrets" bug class flagged by CVE-2019-10391 (plaintext password shown/transmitted via a form mechanism not designed to protect it). Here the "password" analog is Sapling key material (`ask`, expanded spending key) that directly gates control of shielded funds.

The project's own configuration documentation acknowledges this risk class for the shielded API family generally, recommending it only be invoked locally and gated behind `allowShieldedTransactionApi`: [3](#0-2) 

However, that warning/gate is written with `getSpendingKey`/`createShieldedTransaction`-type flows in mind; `GetAkFromAskServlet` and `GetExpandedSpendingKeyServlet` derive/echo secret-dependent material and still expose a `doGet` code path that takes the secret straight from the query string, regardless of caller intent to keep it out of logs.

### Impact Explanation
If an operator (even one who deliberately enables the shielded API only for local trusted use) or any client library uses the documented `GET /wallet/getakfromask?value=<ask>` or `GET /wallet/getexpandedspendingkey?value=<sk>` form, the secret ends up in:
- web server / reverse proxy access logs,
- shell history if invoked via curl,
- browser history if invoked via browser,
- any HTTP debugging/monitoring proxy in the path.

Disclosure of `ask` or the expanded spending key allows an attacker who gains access to any of these logs to derive spend authority over the corresponding shielded note, i.e., unauthorized shielded-fund control — a concrete key-disclosure/theft-of-funds impact, consistent with the Medium severity of the analog advisory.

### Likelihood Explanation
Likelihood is bounded by the same opt-in requirement documented in `reference.conf` (`allowShieldedTransactionApi`), so a default-configuration FullNode does not expose this surface. Where an operator or wallet-integration explicitly enables the shielded API (as the config comments anticipate for "development and testing", but which does happen in practice), the `doGet` variant is reachable by any client using standard HTTP GET semantics without any additional authentication, and secret leakage into logs is nearly automatic on any node with default access logging enabled.

### Recommendation
Remove or reject the `doGet` handlers for endpoints that accept spend-authorizing/spending key material (`GetAkFromAskServlet`, `GetExpandedSpendingKeyServlet`, and any other shielded-key-accepting GET endpoint such as `GetNkFromNskServlet`), forcing POST-body-only submission, and ensure these routes are never written to access logs (or disable access logging for the `/wallet/getakfromask`, `/wallet/getexpandedspendingkey` paths specifically). Update documentation to explicitly warn that GET usage of these endpoints leaks key material into logs even when `allowShieldedTransactionApi` is enabled for local development.

### Proof of Concept
1. Enable the shielded API (`node.allowShieldedTransactionApi = true`) as documented in `reference.conf`.
2. Issue: `curl "http://<fullnode>:8090/wallet/getakfromask?value=<ask_hex>"` (or `getexpandedspendingkey?value=<sk_hex>`).
3. Observe that `<ask_hex>`/`<sk_hex>` now appears verbatim in the node's HTTP access log, any intermediary proxy log, and the invoking client's shell history — all locations outside the trust boundary the operator intended when restricting the API "to invoke them locally."

Note: I could not verify from the index whether `GetAkFromAskServlet`/`GetExpandedSpendingKeyServlet` perform an explicit `allowShieldedTransactionApi` gate check themselves (the check appears centrally in `Wallet.java`, whose exact logic I was unable to fully inspect within the given tool budget) — a Devin session with full file access would be needed to confirm the precise gating logic before treating this as fully unauthenticated by default.
