### Title
Replay-window check-then-commit race allows a captured ciphertext to be decrypted and delivered twice - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split replay-window enforcement into three non-atomic steps: peek (`window.Check`), decrypt (`dKey.DecryptDanger`), then commit (`window.Update`). The lock protecting the window is released between the peek and the commit, and Nebula's multi-queue UDP listener architecture (`f.routines` reader goroutines) can genuinely deliver the same captured packet to two different reader goroutines concurrently. Both can pass `Check` before either calls `Update`, so a replayed packet is authenticated and handed to the application/relay path twice, mirroring the referral-withdraw bug class: an irreversible/observable action (successful AEAD decrypt + delivery) is taken before the commit point (`window.Update`) that is supposed to make the operation exactly-once.

### Finding Description
`Decrypt` (and the analogous `VerifyRelay` used for relay frames) is implemented as:

```go
// connection_state.go:61-82
func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}
``` [1](#0-0) 

`window.Check` only reads whether the bit for `messageCounter` is already set; it does not mark it. The bit is only marked in `window.Update`, called after the (comparatively expensive) `DecryptDanger` AEAD call. The mutex `cs.decryptLock` is unlocked between these two calls, so the "reservation" of a counter is not atomic with the peek.

The interface intentionally runs `f.routines` independent reader goroutines over the same UDP socket set:

```go
// interface.go:273-279
func (f *Interface) run() {
	for i := 0; i < f.routines; i++ {
		f.wg.Go(func() {
			f.listenOut(i)
		})
	}
	...
}
``` [2](#0-1) 

and each `listenOut(i)` independently calls into `readOutsidePackets` → `hostinfo.ConnectionState.Decrypt` for whatever packet its queue receives:

```go
// outside.go:126-132
out, err = hostinfo.ConnectionState.Decrypt(f.l, h.MessageCounter, out, packet, nb)
``` [3](#0-2) 

There is no per-hostinfo affinity guaranteeing a given peer's traffic always lands on the same reader queue; OS-level UDP load balancing (e.g. multiple sockets/`SupportsMultipleReaders`) can steer two copies of the exact same wire packet — one legitimate, one attacker-replayed and injected at the same underlay moment — to two different queues. Both goroutines then race through `Decrypt`:

1. Goroutine A calls `Check(messageCounter)` → bit unset → returns true.
2. Goroutine B calls `Check(messageCounter)` → bit still unset (A hasn't reached `Update` yet) → returns true.
3. Both A and B successfully `DecryptDanger` the identical ciphertext (AEAD decrypt of the same valid ciphertext succeeds both times).
4. Both A and B call `Update`; only one of them will find the bit still unset and return true from `Update`'s perspective (the CHANGELOG entry "Lock replay window updates so concurrent readers can't corrupt it. (#1802)" only fixes corruption of the bitset structure under concurrent access, not the semantic double-acceptance), but **both goroutines have already produced a decrypted plaintext output at step 3** and, on the `Decrypt` success path, that plaintext is dispatched to `handleOutsideMessagePacket`/relay forwarding before either `Update` call runs.

This is analogous to the report's core defect: the state that gates "already processed" (`referral_commissions.status` / here, the replay-window bit) is only committed *after* the consequential, externally observable action (USDC transfer / here, AEAD-authenticated decrypt-and-deliver) has already happened, and the gap between the two is not atomic.

### Impact Explanation
An attacker who can capture a single ciphertext packet on the wire (no valid certificate required — this is pure packet capture/replay, matching the "nonce/replay handling" analog class) and re-inject it at the moment the legitimate copy is also in flight can cause the same encrypted payload to be decrypted and delivered twice to the tun device or, in the relay case, forwarded twice by a relay node (`VerifyRelay`, used in `handleOutsideRelayPacket`). This is a traffic-replay/duplication impact: idempotency guarantees the replay window is meant to provide are broken under concurrency, enabling double delivery of application traffic through the tunnel. The CHANGELOG shows the project has already fixed adjacent replay-window bugs (`#1751`, `#1802`), indicating the replay window is considered a security-relevant control, but the Check/Decrypt/Update non-atomicity itself remains.

### Likelihood Explanation
Exploitation requires `f.routines > 1` (multi-queue enabled, the documented/recommended configuration on multi-core hosts) and requires winning a narrow race window between two reader goroutines processing the same wire packet before the AEAD decrypt of the second copy completes. This is harder to trigger reliably than a simple flood, but is deterministically reachable by an attacker with packet-capture/injection capability on the underlay network, without needing any peer credential — it is a genuine, if timing-sensitive, remote replay-window bypass.

### Recommendation
Make the reservation atomic with the check: hold `decryptLock` (or a per-counter reservation) across a tentative `Update`-style claim *before* calling `DecryptDanger`, and only finalize/roll back the claim based on decrypt success, e.g.:
```go
cs.decryptLock.Lock()
if !cs.window.Reserve(l, messageCounter) { // atomically checks-and-marks
    cs.decryptLock.Unlock()
    return nil, ErrAlreadySeen
}
cs.decryptLock.Unlock()

out, err = cs.dKey.DecryptDanger(...)
if err != nil {
    // decrypt failed; the counter slot stays consumed, which is fine —
    // a failed AEAD tag for that counter should never be retried anyway.
    return nil, err
}
return out, nil
```
This removes the window where two concurrent readers can both observe the counter as "not yet seen" and both complete a successful decrypt/deliver for the same message.

### Proof of Concept
1. Configure a nebula node with `listen.routines` (or `tun.routines`) set greater than 1 so multiple UDP reader queues run concurrently (`f.routines > 1` in `interface.go`).
2. As a network-level attacker, capture one valid data-plane packet in flight (any ciphertext addressed to that host).
3. Re-inject an exact duplicate of that packet onto the underlay at (or very near) the same time the original arrives, such that OS UDP load balancing delivers the original and the duplicate to two different reader queues/goroutines.
4. Both goroutines call `ConnectionState.Decrypt` for the same `messageCounter`; both pass `window.Check` before either reaches `window.Update`, both successfully `DecryptDanger` the identical ciphertext, and both proceed to deliver the plaintext to the tun device (or forward it, for `VerifyRelay`/relay frames), resulting in double delivery of a single wire message despite the replay window.
