### Title
Front-runnable, unauthenticated global singleton initializer allows an attacker to seize protocol-wide fee-admin privileges - (File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs)

### Summary
The external report's bug class is "an uninitialized template/singleton contract can be initialized by an attacker, who then supplies their own address as the privileged owner." The closest reachable analog in marginfi-v2 is `init_global_fee_state` (and its `v2` counterpart), which creates the single, program-wide `FeeState` PDA and sets `global_fee_admin` from a caller-supplied argument, gated only by "does the PDA already exist" rather than by any check that the caller is the legitimate protocol deployer.

### Finding Description
`InitFeeState` derives a canonical, single PDA from a fixed seed (`FEE_STATE_SEED`) with no group- or caller-specific component, so exactly one `FeeState` account can ever exist for the whole program: [1](#0-0) 

The handler itself does not check that `ctx.accounts.payer` is any particular privileged key (e.g. the program's upgrade authority, a hardcoded multisig, etc.) — it simply writes whatever `admin_key` / `fee_wallet` arguments were passed by the caller into the newly-created account: [2](#0-1) 

The only entry point in `lib.rs` is likewise unauthenticated beyond requiring a signer to pay rent, and is documented as something that is only expected to "run once per program": [3](#0-2) 

Because Anchor's `init` constraint only fails if the PDA is *already* initialized (i.e., it protects against double-initialization, not against *who* performs the first initialization), this is structurally identical to the reported bug class: a privileged singleton (analogous to `pairTokenBase`/`poolBase`) is deployed/derivable on-chain but is not initialized atomically with deployment, and whoever calls the "runs once" initializer first becomes the permanent owner (`global_fee_admin`), exactly as an attacker becomes `owner` by calling `PoolToken.initialize()`/`LeveragedPool.initialize()` first in the original report.

All subsequent admin-gated fee/pause instructions (`config_group_fee`, `edit_global_fee.rs::EditFeeState`, etc.) trust `fee_state.global_fee_admin` via `has_one = global_fee_admin`, so whoever wins the initialization race becomes the sole party who can modify protocol fees, the fee wallet, and pause-related fee-state fields for the entire deployed program: [4](#0-3) [5](#0-4) 

### Impact Explanation
If an attacker observes/anticipates the `init_global_fee_state` (or `init_global_fee_state_v2`) transaction before the legitimate deployer's call lands (e.g., via mempool/validator visibility, or simply because deployment and initialization are not bundled atomically), they can submit their own `InitFeeState` transaction first, permanently becoming `global_fee_admin` on the sole `FeeState` PDA for the program. From there they control the protocol-wide fee wallet (`global_fee_wallet`), fee rates (`program_fee_fixed`, `program_fee_rate`), liquidation/order fee parameters, and pause delegate — a permanent, protocol-wide unauthorized privilege escalation with no recovery path short of a program upgrade, matching the report's required impact category of "unauthorized state change" / persistent illegitimate ownership.

### Likelihood Explanation
This requires winning a very narrow race window immediately after (or even before, if the PDA can be pre-derived and pre-funded) program deployment/upgrade, before the legitimate admin's own initialization transaction is confirmed. In practice, deployment tooling can mitigate this by bundling deploy + init in the same atomic operation or same block, and mainnet program upgrades of an already-initialized `FeeState` would not re-expose this window (the PDA would already exist, so recreation is blocked by `init`). Because the on-chain gating logic itself provides no authentication of "who is allowed to run this the first time," the vulnerability is real and directly analogous to the reported class, but its practical exploitability is limited to the initial-deployment/initialization window, so likelihood is low-to-moderate rather than continuously exploitable.

### Recommendation
Gate `init_global_fee_state` / `init_global_fee_state_v2` so that only the program's upgrade authority (verified via the `ProgramData` account) or another verifiably privileged deployer key can call it, rather than accepting an arbitrary signer plus an arbitrary `admin_key` argument. Alternatively, hardcode the expected first-admin key in the program and require `ctx.accounts.payer.key() == HARDCODED_KEY`, or bundle deployment and initialization into a single atomic transaction so no external caller can front-run it.

### Proof of Concept
1. Deploy (or upgrade to) a marginfi program version where `FeeState` at PDA `[FEE_STATE_SEED]` does not yet exist.
2. Before the legitimate operator sends their `init_global_fee_state` transaction, an attacker submits their own transaction calling `init_global_fee_state` (or `init_global_fee_state_v2`) with `admin: attacker_pubkey`, `fee_wallet: attacker_wallet`, using the `InitFeeState` accounts shown at [1](#0-0) .
3. Because the instruction has no signer/authority check beyond "pay rent" and the PDA is derived only from the fixed seed, the attacker's transaction succeeds and creates the sole `FeeState` account with `global_fee_admin = attacker_pubkey`.
4. Any subsequent call to `edit_global_fee`/`config_group_fee` by the legitimate team fails `has_one = global_fee_admin` checks, while the attacker can freely call these instructions to redirect protocol fees to their own wallet, matching the report's "attacker sets themselves as owner via calling initialize() first" pattern.

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
