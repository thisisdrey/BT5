### Title
Dust `DepositToken` transfers fill a victim's `depositTokensOfAccount` list up to `MAX_TOKENS_PER_USER`, permanently reverting the victim's first deposits into any new collateral and blocking position top-ups/liquidations - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
The Nouveau CVE is a remote, unprivileged denial-of-service triggered by a crafted input. The Metronome analog is a state-poisoning DoS: any EOA can dust-`transfer` every whitelisted `DepositToken` to a victim. Each dust transfer is a first-time receipt for that token, so `_transfer` calls `Pool.addToDepositTokensOfAccount(recipient_)`. Once the per-account enumerable set reaches `MAX_TOKENS_PER_USER`, `addToDepositTokensOfAccount` reverts, which makes any subsequent `_mint`/`_transfer` of a collateral the victim does not already hold revert — including the victim's own `deposit()` and a liquidator's `seize()` path when it would register a new token.

### Finding Description
`DepositToken._transfer` registers the token on the recipient's account list whenever the recipient previously had a zero balance, with no minimum amount and no opt-out: [1](#0-0) 

The same registration happens in `_mint` on deposit: [2](#0-1) 

`transfer`/`transferFrom` only check the *sender's* unlocked balance (`_revertIfLocked(sender_, amount_)`, lines 348-373), so an attacker holding tiny unlocked balances of each `DepositToken` (obtainable by depositing dust themselves) can push them to any victim. `Pool.addToDepositTokensOfAccount` (contracts/Pool.sol) enforces `MAX_TOKENS_PER_USER` via the `MappedEnumerableSet` in `PoolStorage` and reverts when the cap is reached — note: I was unable to re-read the exact revert line in `Pool.sol` in this pass, but the cap and the revert-on-full behavior are the documented purpose of the bounded set.

### Impact Explanation
Once the victim's list is saturated:
- `deposit()` of any collateral type not already in the victim's list reverts inside `_mint → addToDepositTokensOfAccount`, so the victim cannot add new collateral to heal an unhealthy position.
- A liquidator calling `Pool.liquidate` specifying a `depositToken_` the victim holds works, but `seize` to a liquidator whose own list is full reverts; more importantly the victim is pushed toward liquidation with no way to deposit fresh collateral.
- `withdraw`/`issue`/`repay` that route through `debtPositionOf` still work, so this is a targeted freeze of the deposit path and of incoming transfers of new token types — a temporary freezing of funds / forced-liquidation primitive, matching "permanent or material temporary freezing of funds or blocked withdrawals" in scope.

Invariant broken: an unprivileged third party can change the feasibility of a victim's `deposit()` — an operation that requires no victim interaction to be griefed (unlike approvals-based attacks).

### Likelihood Explanation
- Fully unprivileged: `transfer` is a public ERC20 entry point; dust amounts suffice (`amount_ > 0` check at line 518).
- Cost is minimal — attacker deposits a dust amount of each collateral once and splits it across many victims.
- Not stopped by `nonReentrant`, `whenNotPaused`, SynthContext sender checks, or supply caps; the only prerequisite is the pool having ≥ `MAX_TOKENS_PER_USER` registered deposit tokens, which holds on production deployments with many collaterals.
- Caveat: if the revert lives only in `addToDepositTokensOfAccount` and the victim already holds at least one token, the impact is limited to blocking *new* collateral types — still sufficient to prevent health recovery via a different asset and to block first-time users entirely.

### Recommendation
- Only call `addToDepositTokensOfAccount` for genuine deposits (`_mint` path), not for arbitrary ERC20 `transfer`s — e.g., track "registered" tokens separately from transfer-received balances, or restrict `transfer`/`transferFrom` to tokens already in the recipient's list.
- Alternatively, make `debtPositionOf` iterate a whitelist determined at `deposit` time, and treat unsolicited transfers as non-collateral (ignored for locking) so dust cannot consume list slots.
- Add a regression test: dust-transfer all deposit tokens to a victim, then assert their `deposit` of a new collateral and `liquidate` behavior.

### Proof of Concept

```ts
// attacker deposits dust in every DepositToken of the pool
for (const dt of allDepositTokens) {
  await underlying(dt).connect(attacker).approve(dt.address, dust);
  await dt.connect(attacker).deposit(dust, attacker.address);
  // sends dust to victim -> adds token to victim's depositTokensOfAccount
  await dt.connect(attacker).transfer(victim.address, 1n);
}
// victim's list is now at MAX_TOKENS_PER_USER
expect(await pool.depositTokensOfAccount(victim.address)).to.have.length(MAX);

// victim tries to deposit a collateral type they never held -> reverts
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.reverted; // MaxNumberOfTokensReached inside addToDepositTokensOfAccount
```
