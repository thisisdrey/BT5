## Title
Time-bound `validUntil` baked into the CREATE2 salt permanently strands prefunded Safe addresses when `deploySmartAccount` expires - (File: `tare-io__tare-contracts/contracts/SmartAccountFactory.sol`)

### Summary
`SmartAccountFactory` exposes `predictSmartAccountAddress()` so callers can compute a Safe's CREATE2 address before it is deployed [1](#0-0) . The salt used for both prediction and deployment is derived from the full `Safe.setup` initializer, which embeds the `validUntil` parameter [2](#0-1) . `deploySmartAccount()` unconditionally reverts if `validUntil <= block.timestamp` at call time [3](#0-2) . Because `validUntil` is a fixed absolute timestamp folded into the salt, any deployment delay past that timestamp makes the original address permanently undeployable, exactly mirroring the Sablier `createMerkleLT()` CREATE2 issue where changing constructor inputs to satisfy a revert condition also changes (and thus abandons) the precomputed address.

### Finding Description
`predictSmartAccountAddress` and `deploySmartAccount` both compute the initializer/salt from identical inputs, including `validUntil`:

```solidity
bytes32 salt = keccak256(abi.encodePacked(keccak256(initializer), saltNonce));
``` [4](#0-3) 

`initializer` is built via `_buildInitializer`, which encodes `validUntil` inside the delegatecall data to `configureSmartAccount` that is itself part of the `Safe.setup` calldata: [5](#0-4) 

At actual deployment time, `deploySmartAccount` enforces:
```solidity
require(validUntil > block.timestamp, InvalidAllowanceDeadline());
``` [3](#0-2) 

Since `validUntil` is a static value chosen at prediction time and is compared against `block.timestamp` at deployment time, the exact set of parameters that produced a valid predicted address at time T0 will deterministically fail on-chain if the deployment transaction lands after `validUntil` has elapsed — with zero need for any malicious input, purely due to time passing (multisig owner-signature collection delay, gas-price waiting, sequencer congestion, etc.). The only way to make the call succeed again is to pick a new, later `validUntil`, but that changes the initializer hash and therefore the CREATE2 `salt` and the resulting Safe address — exactly the "changing inputs to satisfy validation also changes the deterministic address" root cause identified in the Sablier report.

Because `predictSmartAccountAddress` is a public, purpose-built prediction function, it signals an intended counterfactual-funding workflow (deposit USDC/ERC20/NFTs to the not-yet-deployed Safe address, then finalize deployment later) — the same usage pattern the original report calls out ("used for counterfactual deployment where funds are sent to the contract's off-chain computed address").

### Impact Explanation
Any assets (USDC, other approved currencies, or NFTs slated for `nftCollections`) sent to a predicted-but-undeployed Safe address become permanently unrecoverable once `block.timestamp` passes the `validUntil` used in the prediction: `deploySmartAccount` can never succeed at that exact address again (any new `validUntil` yields a different salt/address), and there is no other way to deploy a contract to that specific CREATE2 address. This is a permanent, unrecoverable loss of funds caused entirely by an unprivileged, ordinary usage path (any deployer/user predicting then later deploying their own Safe), matching the "Permanent or practically unrecoverable lock of USDC... caused by an unprivileged path" allowed impact.

### Likelihood Explanation
Likelihood is driven purely by elapsed time between prediction and deployment, not by any adversarial input:
- Multi-owner Safes (`owners`/`threshold`) commonly require collecting several signatures before the deployment transaction is actually broadcast, which can introduce arbitrary delay.
- `validUntil` is also reused as the TrustedSpender allowance expiry, so an operator has an incentive to pick a near-term value rather than `type(uint48).max`, increasing the chance it expires before deployment executes.
- No warning or guard prevents callers from funding a predicted address ahead of deployment, since `predictSmartAccountAddress` exists specifically to support that pattern.

### Recommendation
- Exclude `validUntil` (and any other time-sensitive/mutable field) from the CREATE2 salt/initializer hash, or decouple `predictSmartAccountAddress`'s deterministic identity from parameters that can expire.
- Alternatively, do not hard-revert `deploySmartAccount` on `validUntil <= block.timestamp`; instead deploy the Safe regardless and apply a safe default/refreshed `validUntil` for the allowance-setting step only, so the CREATE2 address is never blocked from being realized.
- Document and/or block on-chain prefunding of undeployed predicted addresses, or provide a rescue path (e.g., allow any deployer-chosen `validUntil` at deployment time without affecting the salt) so previously funded addresses remain deployable.

### Proof of Concept
1. `deployer` calls `predictSmartAccountAddress(deployer, 0, ..., validUntil = T0 + 1 hour, owners, threshold)` and obtains address `SA`.
2. `deployer` (or a third party funding the Safe) sends USDC to `SA` in anticipation of finishing multisig owner coordination.
3. Owner-signature collection or transaction submission takes longer than expected; `block.timestamp` now exceeds `T0 + 1 hour`.
4. `deployer` calls `deploySmartAccount` with the same parameters; it reverts with `InvalidAllowanceDeadline` per [3](#0-2) .
5. `deployer` retries with a new `validUntil = block.timestamp + 1 hour` to pass the check; per [2](#0-1)  this produces a different `salt`/deployed address `SA' != SA`.
6. USDC previously sent to `SA` is now unreachable: no contract can ever be deployed at `SA` with the original `validUntil`, and there is no privileged recovery path exposed by the factory.
