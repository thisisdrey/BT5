Confirmed: `extend_with_attachments` inserts `response.attachment` into `self.attachments` immediately after `decode_atlas_get_attachment()` succeeds, with **no check** that `response.attachment.hash() == request.content_hash`.

### Title
Missing hash verification of downloaded attachment content allows attacker-controlled BNS attachment data - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` decodes a peer's `GetAttachmentResponse` and inserts `response.attachment` into `self.attachments` without ever comparing `attachment.hash()` to the `AttachmentRequest.content_hash` that was actually requested. This lets any peer selected via `AttachmentRequest::get_most_reliable_source` (which only requires being in `network.get_outbound_sync_peers()` and reporting the content hash present in its inventory) serve arbitrary bytes that get accepted, stored, and bound to the on-chain-committed hash.

### Finding Description
The download flow is: `AttachmentsBatchStateMachine::DownloadingAttachment` → `BatchedRequestsState::try_proceed` (stores raw `StacksHttpResponse` on HTTP 200, `stackslib/src/net/atlas/download.rs:899-910`) → `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), which does:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
}
```
`decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) only JSON-parses the response body into `GetAttachmentResponse { attachment }` — it performs no hash check against the requested `content_hash`. The `request` value (which holds `content_hash`, the committed hash) is discarded via `results.succeeded.drain()` without ever being compared to `response.attachment.hash()`.

Downstream, `AttachmentsDownloader::run`'s `Done` branch (`stackslib/src/net/atlas/download.rs:153-169`) iterates `context.attachments.drain()` and calls:
```rust
network.atlasdb.insert_instantiated_attachment(&attachment)?;
...
context.attachments_batch.resolve_attachment(&attachment.hash())
```
It uses `attachment.hash()` (recomputed from the attacker-served bytes) as the key for both the DB row and for resolving/matching against `attachments_batch.attachments_instances` (which was populated from the on-chain `content_hash` — see `AttachmentsBatch::track_attachment`, `download.rs:1150-1181`, and `resolve_attachment`, `download.rs:1227-1239`). Because `resolve_attachment` matches by comparing `hash == content_hash` where `hash` is now `attachment.hash()` (not the original committed `content_hash` from the request), a malicious response's mismatched content only fails to resolve the *specific* instance whose content_hash it was fetched for — it does not fail to be **stored** in the AtlasDB via `insert_instantiated_attachment`. The attacker's bytes end up in `AtlasDB` under `attacment.hash()` regardless of whether they match the originally requested `content_hash`.

The root cause is that `extend_with_attachments` never checks `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`, and the request object carrying `content_hash` is dropped at that point.

### Impact Explanation
A malicious outbound-sync peer chosen as the "most reliable source" for an attachment request can return arbitrary content in the `GetAttachmentResponse.attachment.content` field. That content is unconditionally accepted, stored into `AtlasDB` (`insert_instantiated_attachment`), and becomes queryable by any client hitting `GET /v2/attachments/<hash-of-attacker-content>`. Combined with BNS zonefile resolution built on Atlas attachments, this allows a node to serve/store attacker-chosen bytes under a hash that does not match what a confirmed on-chain name operation actually committed to — matching the "attachment/BNS mismatch" High severity category. This is repeatable for every attachment request routed to the malicious peer.

### Likelihood Explanation
Preconditions are modest: the attacker just needs to be a normal outbound-sync peer of the victim node (no privileged role, no RPC secret) and be selected as a source, which happens automatically whenever it reports (truthfully or falsely) having the requested content hash in its `/v2/attachments/inv` inventory response. No signature or additional authentication protects the `/v2/attachments/<hash>` response, and `decode_atlas_get_attachment` performs no cross-check against the request. The attack is fully remote and repeatable.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530`), after decoding the response, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; if it doesn't match, treat it as a failed request (`report.bump_failed_requests()`) and optionally mark the peer as faulty/blocklist it.

### Proof of Concept
Add a unit test in `stackslib/src/net/atlas/tests.rs`:
1. Construct an `AttachmentRequest` with `content_hash = Hash160::from_data(b"expected")`.
2. Build a `StacksHttpResponse` whose JSON body is `GetAttachmentResponse { attachment: Attachment { content: b"malicious".to_vec() } }` (note `Hash160::from_data(b"malicious") != content_hash`).
3. Put this into `BatchedRequestsResult { succeeded: {request -> Some(response)}, .. }` and call `AttachmentsBatchStateContext::extend_with_attachments`.
4. Assert that `context.attachments` contains the malicious `Attachment` (i.e., `context.attachments.iter().next().unwrap().hash() != content_hash`), demonstrating that `extend_with_attachments` accepts it despite the hash mismatch — and that a subsequent call to `network.atlasdb.insert_instantiated_attachment(&attachment)` in `AttachmentsDownloader::run` would store it without ever checking `attachment.hash() == content_hash`.     pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }
            }
            for key in keys {
                missing_attachments.remove(&key);
            }
        }
    }
