I have enough context now to write the analog finding.### Title
Unprivileged user can grief batched `UpdateReferences` restore/backup operations, causing entire atomic ref-update RPC to abort - ([File: internal/gitaly/service/ref/update_references.go])

### Summary
`RefService.UpdateReferences` is a client-streaming RPC that batches many independent reference updates from a single caller into one all-or-nothing (`updater.Commit()`) transaction. If the actual value of just one of the many references no longer matches its client-supplied `old_object_id`, `updater.Commit()` returns a `MismatchingStateError` and the RPC aborts the *entire* batch, discarding all of the other unrelated reference updates.

### Finding Description
The handler collects every `Update` from potentially many streamed requests into a single `updateref.Updater`, then calls `updater.Commit()` once at the end: [1](#0-0) 

If the actual current value of any single reference in that batch diverges from the `old_object_id` supplied for it, the whole commit fails atomically and is surfaced as a single `ReferenceStateMismatch` error, aborting updates to all the other — unrelated — references in the same call: [2](#0-1) 

This all-or-nothing coupling of unrelated references in one batch is exactly the class of bug in the reported `pokeTokens()` case: batching independent items (there, distinct veALCX tokens; here, distinct git references) behind a single atomic precondition check lets whoever controls just one of the items invalidate the precondition for their own item and thereby revert processing of every other, unrelated item in the batch. The existing test suite documents this failure mode explicitly: [3](#0-2) 

`UpdateReferences` is explicitly designed for batching many independent reference creations/deletions/updates "in a raceless way" via optimistic `old_object_id` locking: [4](#0-3) [5](#0-4) 

Any actor with ordinary push/write access to the repository (an "ordinary user") can update, delete, or create one of the references contained in such a batch (e.g., their own branch or an MR/pipeline-managed ref that they control) between the moment the caller (e.g. GitLab Rails performing a bulk housekeeping/sync operation, migration, or restore) reads the expected old OIDs and the moment `UpdateReferences` actually commits. Because the whole call is atomic, this single, cheap, self-owned write invalidates the entire batch and reverts updates that were meant to apply to many unrelated references, at the cost of wasted git-object-database writes/locks for the whole batch on the server side.

A concrete internal caller of this exact all-or-nothing multi-reference commit is the backup/restore path, which builds up `UpdateReferencesRequest_Update` lists spanning the entire set of references in a repository and sends them in one raceless `UpdateReferences` call/stream: [6](#0-5) [7](#0-6) 

Because the restore/reset flow reads `existingRefs` first, then computes update/delete sets, then sends them all as one atomic `UpdateReferences` transaction, any push into the repository between the ref listing and the commit (which an ordinary contributor to that repository can trigger) will change the actual OID of at least one reference in the batch, causing `MismatchingStateError`/`ReferenceStateMismatch` and reverting the entire restore-time reference reset for that repository — not just the one changed reference.

### Impact Explanation
- Wasted server-side resources: building the updater, staging potentially thousands of reference updates, and running `git update-ref`/reftable transaction machinery, only to have it all discarded because of one benign concurrent write to an unrelated reference.
- Denial of service for administrative/maintenance batch operations: backup restore, bulk reference synchronization, or any other internal caller relying on `UpdateReferences` batching many refs in one atomic call can be repeatedly and cheaply blocked by an ordinary repository contributor who simply keeps pushing/updating one of their own branches during the window between state-read and commit.
- Delay of legitimate administrative processes (e.g. restore operations, ref-cleanup jobs) analogous to the delay of gauge-vote resets in the original report — the operation must be retried, and a persistent griefer can keep re-triggering the failure.
- This is a griefing/DoS impact with no direct data corruption, matching the "Griefing" impact class of the original report and the required "DoS of a handler" category from validation rules.

### Likelihood Explanation
Any user with ordinary write access to the repository (the minimum privilege needed to push a branch) can trigger this: they only need to update/create/delete a reference that will be included in a batched `UpdateReferences` call before that call commits. For large repositories or busy caller loops (e.g., backup restore across many refs, or GitLab's bulk internal-ref maintenance flows), the window for a race is non-trivial, and the griefer does not need any special timing precision beyond "keep pushing." The condition is deterministic and 100% reproducible once the race is won, mirroring the reliability demonstrated in the original PoC.

### Recommendation
- Avoid coupling unrelated references' fates in a single atomic commit when the caller's intent is "best-effort batched processing of independent items," not "all logically related and must succeed/fail together." For callers such as the backup/restore reference reset path, either:
  - Split unrelated reference updates into individually-committed sub-batches (mirroring the existing `optimistic` mode already used for deletes vs. updates in `internal/backup/repository.go`, but extended so update failures for one reference do not block committed changes for other, unrelated references), or
  - Retry only the specific mismatching references reported in `ReferenceStateMismatchError` rather than re-attempting/abandoning the whole batch.
- For internal/administrative callers that intentionally use `UpdateReferences`' raceless atomicity, document and enforce that the RPC should only be used for updates that are genuinely correlated (e.g., updates that must be all-or-nothing for correctness), and use chunked, independently-committed calls for logically independent references (per-branch/per-MR/etc.) to bound the blast radius of any single concurrent write.
- Consider adding a partial-success mode to `UpdateReferences` (or documenting a narrower "advisory" batching guideline for Rails/other Gitaly clients) so a single unrelated conflicting reference cannot revert an entire large batch.

### Proof of Concept
Conceptual reproduction based on the existing test harness pattern: [3](#0-2) 

1. Caller (e.g., backup restore, per `internal/backup/repository.go` `ResetRefs`) lists existing references and computes a batch of `N` `UpdateReferencesRequest_Update` entries, each carrying an `old_object_id` captured at read time.
2. Before the caller's `UpdateReferences` stream is closed and committed, an ordinary user with push access updates (or force-pushes) just one of the `N` references included in the batch to a different OID.
3. When the caller's stream is closed, `updater.Commit()` fails with `updateref.MismatchingStateError` for that one reference (as reproduced by the "subset of references fails" test), and the RPC returns `Aborted`/`ReferenceStateMismatch`, discarding updates to all `N-1` other unrelated references in the batch.
4. The caller must retry the entire batch from scratch, and the griefer can repeat step 2 indefinitely against the retried batch.

// UpdateReferencesRequest is a request for the UpdateReferences RPC.
message UpdateReferencesRequest {
  // Update represents a reference update.
  message Update {
    // reference is the fully-qualified reference name that should be updated.
    bytes reference = 1;

    // old_object_id is the object ID the reference should be pointing to in order to be updated.
    // This has the intent to avoid time-of-check-time-of-use-style races when the object ID
    // has changed.
    //
    // If empty, the reference will be force-updated without any such checks. If set to the
    // all-zeroes object ID, this will verify that the branch did not exist previously.
    bytes old_object_id = 2;

    // new_object_id is the object ID the reference should be updated to. If set to the all-zeroes
    // object ID the branch will be deleted.
    bytes new_object_id = 3;
  };

  // repository is the repository where references shall be updated in.
  Repository repository = 1 [(target_repository)=true];
  // updates is the set of reference updates that shall be performed.
  repeated Update updates = 2;
}

func (rr *remoteRepository) ResetRefs(ctx context.Context, refs []git.Reference, optimistic bool) error {
	if len(refs) == 0 {
		return errors.New("empty refs list")
	}

	existingRefs := []git.Reference{}
	iterator, err := rr.ListRefs(ctx)
	if err != nil {
		return fmt.Errorf("list refs: %w", err)
	}
	for iterator.Next() {
		ref := iterator.Ref()
		existingRefs = append(existingRefs, ref)
	}
	if err := iterator.Err(); err != nil && !errors.Is(err, io.EOF) {
		return fmt.Errorf("list refs: %w", err)
	}

	objectHash, err := rr.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("object hash: %w", err)
	}

	refClient := rr.newRefClient()

	// Add updates to delete existing refs not in the new set
	refsToKeep := make(map[git.ReferenceName]struct{}, len(refs))
	for _, ref := range refs {
		refsToKeep[ref.Name] = struct{}{}
	}
	removeUpdates := make([]*gitalypb.UpdateReferencesRequest_Update, 0, len(existingRefs))
	for _, existingRef := range existingRefs {
		if shouldRemoveRef(refsToKeep, existingRef.Name) {
			removeUpdates = append(removeUpdates, &gitalypb.UpdateReferencesRequest_Update{
				Reference:   []byte(existingRef.Name),
				NewObjectId: []byte(objectHash.ZeroOID),
			})
		}
	}

	// Add updates to create or modify refs in the new set
	existingRefTargets := make(map[git.ReferenceName]string, len(existingRefs))
	for _, ref := range existingRefs {
		existingRefTargets[ref.Name] = ref.Target
	}
	updates := make([]*gitalypb.UpdateReferencesRequest_Update, 0, len(refs))
	for _, newRef := range refs {
		if shouldUpdateRef(existingRefTargets, newRef) {
			updates = append(updates, &gitalypb.UpdateReferencesRequest_Update{
				Reference:   []byte(newRef.Name),
				NewObjectId: []byte(newRef.Target),
			})
		}
	}

	if optimistic {
		// Separate delete and update operations to handle edge cases in incremental backups:
		// 1. Lightweight tags may exist in .refs but not in bundles (they reference existing objects)
		// 2. .refs and .bundle creation is not atomic - refs file is created first, so an object
		//    might be deleted between .refs creation and bundle generation
		// 3. By deleting refs first, we ensure repository state matches the backup even if some
		//    refs can't be updated due to missing objects in the bundle
		//
		// This approach replaces recreateRepo() while avoiding reftable transaction conflicts.
		// Regular update operations are allowed to fail to maintain backward compatibility -
		// previously we only fetched bundles without updating refs afterward, so failed updates
		// don't create a regression. Delete operations must succeed to ensure refs not in the
		// backup are removed (matching recreateRepo's behavior).
		//
		// TODO: Once our minimum Git version supports the --batch-update flag for git-update-ref,
		// we can combine these operations and let Git handle partial failures appropriately.
		if err := rr.sendRefUpdates(ctx, refClient, removeUpdates); err != nil {
			return fmt.Errorf("remove refs: %w", err)
		}
		_ = rr.sendRefUpdates(ctx, refClient, updates)

		return nil
	}

	allUpdates := make([]*gitalypb.UpdateReferencesRequest_Update, 0, len(removeUpdates)+len(updates))
	allUpdates = append(allUpdates, removeUpdates...)
	allUpdates = append(allUpdates, updates...)
	if err := rr.sendRefUpdates(ctx, refClient, allUpdates); err != nil {
		return fmt.Errorf("update refs: %w", err)
	}

	return nil
}

// sendRefUpdates sends a batch of ref updates to the remote repository.
func (rr *remoteRepository) sendRefUpdates(ctx context.Context, refClient gitalypb.RefServiceClient, updates []*gitalypb.UpdateReferencesRequest_Update) error {
	if len(updates) == 0 {
		return nil
	}

	stream, err := refClient.UpdateReferences(ctx)
	if err != nil {
		return fmt.Errorf("open stream: %w", err)
	}

	// We need to send the first update without the chunker, because the RPC expects the `Repository` field to be
	// empty in subsequent messages. We also need to send the first reference because the RPC expects at least one
	// update.
	if err := stream.Send(&gitalypb.UpdateReferencesRequest{
		Repository: rr.repo,
		Updates: []*gitalypb.UpdateReferencesRequest_Update{
			updates[0],
		},
	}); err != nil {
		return fmt.Errorf("send initial request: %w", err)
	}

	chunker := chunk.New(&updateRefsSender{stream: stream})

	for _, update := range updates[1:] {
		if err := chunker.Send(update); err != nil {
			return fmt.Errorf("send ref update: %w", err)
		}
	}

	if err := chunker.Flush(); err != nil {
		return fmt.Errorf("flush ref update chunker: %w", err)
	}

	if _, err := stream.CloseAndRecv(); err != nil {
		return fmt.Errorf("close stream: %w", err)
	}

	return nil
}
