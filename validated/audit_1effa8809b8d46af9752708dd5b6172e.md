### Title
Signed Integer Wraparound in MVCC Manifest Chunk-Table Parsing Causes Out-of-Bounds Slice Panic / DoS - ([File: internal/git/mvcc/manifest.go])

### Summary
`ParseManifest` in `internal/git/mvcc/manifest.go` parses the chunk table-of-contents (TOC) of a binary MVCC manifest by reading raw `uint64` offsets from attacker/content-controlled bytes and converting them directly to Go `int` without range-checking against `math.MaxInt64`, mirroring the Solidity `uint24` cast underflow described in the reference report (unchecked narrowing/sign conversion of an attacker-influenced integer that bypasses a subsequent range check).

### Finding Description
In `parseChunks`, each TOC entry's file offset is decoded as: [1](#0-0) 

```go
chunkOffsetInFile := int(binary.BigEndian.Uint64(data[chunkOffset+4 : chunkOffset+tocChunkSize]))
...
nextChunkOffsetInFile := int(binary.BigEndian.Uint64(data[nextChunkStart+4 : nextChunkStart+tocChunkSize]))

if chunkOffsetInFile > dataEnd || nextChunkOffsetInFile > dataEnd || nextChunkOffsetInFile < chunkOffsetInFile {
    return nil, fmt.Errorf("chunk %d has out-of-bounds offsets [%d, %d)", i, chunkOffsetInFile, nextChunkOffsetInFile)
}
chunkSize := nextChunkOffsetInFile - chunkOffsetInFile
``` [1](#0-0) 

`binary.BigEndian.Uint64` returns an unsigned 64-bit value fully controlled by the manifest bytes. Casting it directly to Go's signed `int` (64-bit on all Gitaly-supported platforms) reproduces exactly the same class of bug as the Solidity `uint24(tick/tickSpacing)` cast: a large unsigned value (e.g. `0x8000000000000001`) wraps to a large *negative* signed integer. Because the guard only checks `chunkOffsetInFile > dataEnd` (never `< 0`), a negative `chunkOffsetInFile` trivially passes the "too large" check, and by choosing `nextChunkOffsetInFile` to be any small value ≥ that negative number, the `nextChunkOffsetInFile < chunkOffsetInFile` guard is also satisfied. The resulting `chunkSize := nextChunkOffsetInFile - chunkOffsetInFile` becomes an enormous *positive* number (subtracting a huge negative), just as in the report where the underflowed value propagated into a downstream size/range computation.

This corrupted `manifestChunk{offset, size}` is then used directly to slice the buffer without further bounds validation in the PATH/OBJS/REFS chunk consumers: [2](#0-1) 

```go
numPath := pathChunk.size / pw
m.Paths = make([]string, numPath)
for i := range numPath {
    start := pathChunk.offset + i*pw
    record := data[start : start+pw]
    ...
``` [2](#0-1) 

A negative `pathChunk.offset` (or a `numPath` derived from an inflated `chunkSize` far larger than `len(data)`) causes `data[start:start+pw]` to be sliced with an out-of-range/negative index, which panics at runtime (`slice bounds out of range`), or `make([]string, numPath)` to attempt an enormous allocation, causing memory exhaustion — both are unrecoverable-by-design DoS conditions in the request-handling goroutine.

### Impact Explanation
`ParseManifest` is reached from `LocalCache.prepareManifestFile` and `LocalCache.putNewArtifacts` in `internal/git/mvcc/cache.go`, which are invoked on every RPC using the MVCC backend (`gitaly--013` MVCC reference-backend feature) via `LocalCache.Prepare`/`Commit`, both driven per the write/read path documented in `doc/mvcc_rpc_flow.md`. Manifest bytes are fetched from the shared object-storage bucket keyed by content hash and written to the local per-repository cache directory, then parsed on every subsequent Gitaly node that reads that manifest (e.g., during replication/multi-node MVCC snapshot hydration). A manifest body that is corrupted or crafted with an out-of-range TOC entry (while still passing the trailing SHA-256 self-check, since the attacker who can write the object-storage blob controls its full content and therefore also its trailer) will panic or exhaust memory on every Gitaly node that subsequently loads it, constituting a resource-limit/DoS condition in the RPC handler path rather than a benign parse-error return.

### Likelihood Explanation
Reaching this code requires the ability to place an arbitrarily crafted manifest blob into the MVCC object store that a node will fetch by content-addressed hash (e.g. via a compromised/misbehaving storage write path, a replicated write from another node, or a corrupted upload). It is not exploitable purely from a normal Git push/fetch since normal manifest bodies are produced deterministically by Gitaly/Git itself; genuine exploitation requires control over manifest bytes that later get fetched and parsed, which is a narrower trust boundary than "any RPC field from an ordinary user." Given the "Reject ... malicious-peer/node ... no-impact analogs" instruction and that this MVCC storage backend is explicitly documented as being at a POC stage (`doc/mvcc_rpc_flow.md`), likelihood of a truly ordinary-user-triggerable path is uncertain and not conclusively demonstrated from the available code alone.

### Recommendation
Reject any TOC offset value greater than `math.MaxInt64` conversion hazards by validating the raw `uint64` against `len(data)` **before** casting to `int` (e.g., `if raw > uint64(len(data)) { return error }`), and additionally assert `chunkOffsetInFile >= 0` and `nextChunkOffsetInFile >= 0` explicitly after conversion, mirroring the fix pattern used for the reported Solidity issue (validate before/after the unchecked arithmetic rather than relying solely on a post-hoc magnitude comparison that can be bypassed by sign wraparound).

### Proof of Concept
Not executed against a live Gitaly instance (index-only analysis); the code path was reconstructed from `internal/git/mvcc/manifest.go`, `internal/git/mvcc/cache.go`, and the test file `internal/git/mvcc/manifest_test.go`, which validates only the "too large" and "next < current" cases but does not include a test case with an offset whose top bit is set (i.e., a `uint64` value that overflows Go's signed `int` on cast), so this specific wraparound scenario appears unverified by the existing test suite.
