Audit Report

## Title
`EthereumSystem::add_tip` on BridgeHub trusts an unauthenticated `sender` field bound only to a static, replayable pallet-location origin, not the real caller - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`system-v2::add_tip` on BridgeHub authenticates the call solely via `T::FrontendOrigin::ensure_origin(origin)?`, and `FrontendOrigin` is configured as `EnsureXcm<AllowFromEthereumFrontend>`, which only checks that the XCM origin equals the static location `(1, [Parachain(ASSET_HUB_ID), PalletInstance(FRONTEND_PALLET_INDEX)])`, independent of which AssetHub account actually triggered it. [1](#0-0) [2](#0-1)  The `sender: AccountIdOf<T>` parameter, `message_id`, and `amount` are all caller-supplied and used verbatim — crediting `LostTips` and forwarding `amount` to `InboundQueue`/`OutboundQueue::add_tip` — without verifying that they correspond to the account that actually performed the swap-and-burn on AssetHub via `system-frontend::add_tip`. [3](#0-2) 

## Finding Description
On AssetHub, the legitimate entrypoint `system-frontend::add_tip` requires a signed caller, burns the tip asset for ether, and constructs a `Transact` call embedding `sender = who` before sending it via `DescendOrigin(T::PalletLocation::get())`: [4](#0-3) [5](#0-4) 

On BridgeHub, `EthereumSystem::add_tip` re-authenticates only via `T::FrontendOrigin::ensure_origin(origin)`, whose `Success` is a bare `Location`, and then trusts `sender`, `message_id`, and `amount` exactly as given in the call, using `sender` to route `LostTips` bookkeeping: [6](#0-5) 

The runtime wiring confirms `FrontendOrigin = EnsureXcm<AllowFromEthereumFrontend>`, and `AllowFromEthereumFrontend::contains` only checks `(1, [Parachain(para_id), PalletInstance(index)])` equals `(ASSET_HUB_ID, FRONTEND_PALLET_INDEX)` — it performs no check that ties the origin to a specific AssetHub account or to the specific `sender`/`amount` values supplied in the call: [2](#0-1) 

This confirms the architectural claim in the report: the resulting origin after `DescendOrigin(T::PalletLocation::get())` is identical regardless of which AssetHub account triggered it, and BridgeHub's `add_tip` conflates "message came from the correct pallet-class location" with "the embedded `sender`/`amount` fields are trustworthy."

However, validating exploitability requires confirming that an unprivileged AssetHub account can actually cause a message to be delivered to BridgeHub carrying an attacker-chosen `DescendOrigin(SystemFrontendPalletLocation)` + `Transact{origin_kind: OriginKind::Xcm, call: AddTip{...}}` program. This depends on whether `pallet_xcm::send`/`execute` (or any other generic XCM-sending surface) on AssetHub is reachable by ordinary signed accounts with an arbitrary, attacker-crafted `Xcm<()>` program, and whether XCM barriers on BridgeHub restrict which senders/programs are allowed to reach `AllowFromEthereumFrontend`-gated calls. I was unable to fully verify this within the available exploration: locating and confirming `SendXcmOrigin`/`XcmExecuteFilter` configuration for `asset-hub-westend`'s `pallet_xcm::Config`, and confirming whether BridgeHub's XCM `Barrier` config restricts arbitrary `Transact` + `DescendOrigin` combinations from sibling chains, would be required to establish that this is actually reachable by an unprivileged external attacker rather than merely a theoretical parameter-trust weakness gated by XCM-level access controls elsewhere in the stack.

## Impact Explanation
If reachable, the impact matches the report's description: `sender` is used unauthenticated to attribute `LostTips::<T>` storage increments [7](#0-6) , and `amount` is credited to `InboundQueue`/`OutboundQueue::add_tip` without a corresponding on-chain burn [8](#0-7) . If this tip subsequently affects relayer reward payout, this constitutes unbacked reward inflation, aligning with the "theft or unbacked mint or unlock" / "duplicate settlement or payout" impact categories.

## Likelihood Explanation
Likelihood hinges entirely on whether an unprivileged AssetHub account can construct and deliver the exact forged XCM program (`DescendOrigin(PalletLocation)` + `Transact{origin_kind: Xcm, call: AddTip{...}}`) to BridgeHub through a public, permissionless surface (e.g., `pallet_xcm::send`/`execute`). This is the crux of the claim and could not be conclusively confirmed or refuted from the code inspected: the `AllowFromEthereumFrontend` check on BridgeHub is confirmed to be a static-location-only check with no account binding, but whether AssetHub's runtime configuration and BridgeHub's XCM barriers permit an arbitrary account to actually deliver such a crafted program to that exact origin remains unverified.

## Recommendation
Given the confirmed weakness that `T::FrontendOrigin`'s `Success` type carries only a `Location` with no per-account binding, and that `add_tip` trusts the caller-supplied `sender`/`amount` without cross-checking against the verified origin, the fix should bind the tipping identity to the verified origin (e.g., by encoding the account into the XCM interior location before `DescendOrigin`, mirroring the account-aware `RegisterTokenOrigin` pattern) and derive `sender` server-side rather than trusting it as a call parameter, as proposed in the report.

## Proof of Concept
Not independently reproduced in this review. The report's PoC (crafting `Xcm(vec![DescendOrigin(PalletLocation), UnpaidExecution, Transact{origin_kind: OriginKind::Xcm, call: EthereumSystemCall::AddTip{...}}])` via `pallet_xcm::execute`/`send` targeting BridgeHub) is plausible given the confirmed static-location-only `AllowFromEthereumFrontend` check, but confirming end-to-end reachability requires verifying AssetHub's `pallet_xcm` send/execute origin filters and BridgeHub's XCM `Barrier` configuration, which were not conclusively established in this review.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
