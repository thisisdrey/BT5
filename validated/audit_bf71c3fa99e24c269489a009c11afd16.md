### Title
Lack of slippage control on Bancor-style exchange liquidity inject/withdraw - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java], [File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
`ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-token amount (`anotherTokenQuant`) required/received for a liquidity inject/withdraw using the exchange's current on-chain token balances at execution time, with no user-supplied minimum/maximum bound. This mirrors the reported bug class: the amount of "restaking tokens" received is computed from a live, mutable exchange-rate source with no slippage parameter, so the actor has no control over deviation between the value expected at signing time and the value actually received at execution time.

### Finding Description
`ExchangeTransactionContract` (used for actual swaps) includes an explicit `expected` field, and `ExchangeTransactionActuator.doValidate()` enforces `anotherTokenQuant >= tokenExpected` [1](#0-0) . In contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` carry no equivalent bound. In `ExchangeInjectActuator`, `anotherTokenQuant` is derived purely from the exchange's current `firstTokenBalance`/`secondTokenBalance` ratio at validate/execute time and pulled from the caller's balance with no minimum/maximum check [2](#0-1) . Likewise, `ExchangeWithdrawActuator` computes `anotherTokenQuant` from the live pool ratio and pays it out to the caller without any user-specified minimum-acceptable-amount check; the only sanity check present ("Not precise enough") is a rounding-tolerance check, not a slippage/price-protection mechanism [3](#0-2) .

Because both `validate()` and `execute()` re-derive the ratio from the store state at the moment the transaction is actually processed inside a block (not at signing time), and other transactions targeting the same exchange (trades via `ExchangeTransactionContract`, or other inject/withdraw calls) can be included earlier in the same block and shift `firstTokenBalance`/`secondTokenBalance`, the amount ultimately paid to/charged from the caller can differ arbitrarily from what was expected when the transaction was signed and broadcast.

### Impact Explanation
An exchange creator submitting `ExchangeWithdrawContract` to pull liquidity can receive fewer counter-tokens than intended if the pool ratio shifts (due to intervening trades in the same block) between signing and execution — a direct, unbounded value loss with no recourse, since there is no minimum-amount check to cause the transaction to safely revert. Symmetrically, `ExchangeInjectContract` can force the creator to supply more of the counter-token than intended for the same nominal injected quantity. This is a concrete "theft of funds via unfavorable execution" class issue reachable by any account that created an exchange (creation is not admin-gated) and submits transactions through the normal Wallet/gRPC transaction broadcast path.

### Likelihood Explanation
Likelihood is limited by the precondition that the actor must be the specific exchange's `creatorAddress` [4](#0-3)  — but exchange creation itself is open to any account (no privileged role), so this remains reachable by an ordinary, unprivileged transaction broadcaster who created their own exchange. The rate can be moved by other unprivileged users' trade transactions (`ExchangeTransactionContract`) landing in the same block ahead of the inject/withdraw transaction, which is entirely feasible under normal TRON block processing.

### Recommendation
Add a slippage-bound field (e.g., `expected`/`minAnotherTokenQuant` for withdraw, `maxAnotherTokenQuant` for inject) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` analogous to the existing check in `ExchangeTransactionActuator` (`anotherTokenQuant < tokenExpected`).

### Proof of Concept
1. Account A creates an exchange for TokenX/TRX and becomes `creatorAddress`.
2. Account A signs and broadcasts an `ExchangeWithdrawContract` intending to withdraw based on the currently observed ratio, expecting to receive N TRX for Q TokenX.
3. Before A's transaction is packed into a block, other unprivileged users broadcast `ExchangeTransactionContract` trades against the same exchange, shifting `firstTokenBalance`/`secondTokenBalance` significantly.
4. When A's withdraw transaction executes, `ExchangeWithdrawActuator.execute()` recomputes `anotherTokenQuant` from the now-shifted balances [5](#0-4) , paying A a materially different (lower) amount than expected, with no mechanism to abort the transaction based on a minimum acceptable amount.
