### Title
Unauthenticated remote peers can force the node to issue arbitrary DNS lookups via the `Handshake.data_url` field - ([File: stackslib/src/net/chat.rs])

### Summary
Any remote peer, even before completing peer authentication, can send a `Handshake` message whose `data_url` field contains an attacker-chosen DNS domain name. This value is stored verbatim on the conversation and later fed directly into the node's DNS resolver, causing the node to perform a live DNS lookup against whatever hostname the attacker supplied. This mirrors the Apache Wicket `X-Forwarded-For`-driven DNS issue: an untrusted, attacker-supplied string is used verbatim as an input to a network-triggering DNS resolution.

### Finding Description
`HandshakeData` is a p2p wire message field with no host allow-list, defined at `stackslib/src/net/mod.rs:1041-1048`, and it round-trips through the wire codec basically unrestricted other than a coarse URL syntax/length check (`stackslib/src/util_lib/strings.rs:30-41,59-107,113-151`), which only enforces http(s) scheme, no userinfo, no query/fragment — but the host itself can be *any* domain name.

Handling an inbound `Handshake` does not require the peer to be authenticated first: `handle_unauthenticated_control_message` dispatches `StacksMessageType::Handshake(_)` straight to `self.handle_handshake(network, msg, false, ibd)` [1](#0-0) . `handle_handshake` only blocks this if `disable_inbound_handshakes` is set; otherwise it calls `validate_handshake` and then unconditionally stores the peer-supplied URL: `update_from_handshake_data` does `self.data_url = handshake_data.data_url.clone();` [2](#0-1) .

Each time the conversation "chats" (i.e. on every processed message batch), `try_resolve_data_url_host` is invoked (`stackslib/src/net/chat.rs:3020`), and if the URL host is a DNS name (as opposed to a literal IPv4/IPv6 address), it queues a real DNS lookup:
```
Some(url::Host::Domain(domain)) => {
    let deadline = get_epoch_time_ms().saturating_add(dns_timeout);
    if let Err(e) = dns_client.queue_lookup(domain, port, deadline) { ... }
    self.dns_request = Some(DNSRequest::new(domain.to_string(), port, 0));
    ...
}
``` [3](#0-2) 

The actual resolution is performed by the `DNSResolver`, which just calls `to_socket_addrs()` on the attacker-controlled hostname string in a background thread: `stackslib/src/net/dns.rs:125-151`. There is no allow-list of expected/known peer hostnames, and no restriction correlating the claimed `data_url` host with the peer's actual TCP source address — an attacker can point it at an arbitrary internal or external hostname of their choosing.

This precisely matches the CWE-20/Wicket bug class: attacker-controlled string field → uncontrolled DNS resolution.

### Impact Explanation
Every inbound connection an attacker opens (each can present a fresh identity/handshake) can specify a distinct or repeated attacker-chosen hostname, causing the node to issue DNS lookups on the attacker's behalf. This can be used to:
- Force the victim node's resolver/upstream DNS infrastructure to perform lookups against attacker-chosen authoritative name servers (a DNS proxy effect), enabling reconnaissance, cache pollution attempts, or amplification against a third party's DNS infrastructure.
- Slow down the node's own DNS resolver thread and connection-processing loop, since resolution is a blocking call performed serially per request (subject to `max_inflight`), degrading connectivity/health tracking for legitimate peers.

This aligns with the "High" bucket in the rules ("bounded compute DoS on a read endpoint" / non-volumetric abuse of a control-plane feature), since it does not require raw traffic volume — a single crafted handshake per connection is sufficient to trigger a DNS lookup, and the attacker fully controls the target hostname.

### Likelihood Explanation
High likelihood: no authentication or special privilege is required to send a `Handshake` (this is explicitly the *unauthenticated* control-message path), the `data_url` field is fully attacker-controlled at the wire-format level, and the resolution path (`try_resolve_data_url_host` → `DNSClient::queue_lookup` → `DNSResolver::resolve`) is unconditionally reached whenever the host parses as `url::Host::Domain`. The only constraints are URL syntax (regex `URL_STRING_REGEX`) and max string length (`CLARITY_MAX_STRING_LENGTH`), both trivially satisfiable with a valid-looking `http://<attacker-domain>/` string.

### Recommendation
- Do not perform DNS resolution against a hostname supplied by a peer's handshake `data_url` unless it corresponds to a peer whose identity/address the node has already validated (e.g., only resolve if the host is a known/allow-listed neighbor domain or matches an expected configuration).
- Consider disallowing or rate-limiting DNS-name data URLs from unauthenticated/unsolicited handshakes, and cap the number of *distinct* hostnames that can be queued for lookup per remote IP/time window.
- Ensure the DNS resolver thread pool/`max_inflight` limits are conservative enough that a burst of unique inbound connections cannot appreciably serialize/block resolution of legitimate lookups (defense in depth; already partially present in `stackslib/src/net/dns.rs` via `max_inflight`, but this only bounds concurrency, not distinct-hostname abuse).

### Proof of Concept
1. Attacker opens a TCP connection to the victim Stacks node's p2p port.
2. Attacker sends a `Handshake` StacksMessage with `HandshakeData.data_url = "http://attacker-chosen-name.example/"` (any syntactically valid host).
3. Victim node's `handle_unauthenticated_control_message` → `handle_handshake` → `update_from_handshake_data` stores this URL as `self.data_url` on the conversation, with no verification that this hostname is expected or matches the peer's actual address.
4. On the next `chat()` cycle, `try_resolve_data_url_host` detects a `url::Host::Domain` and calls `dns_client.queue_lookup("attacker-chosen-name.example", port, deadline)`, causing the node's `DNSResolver` background thread to perform a live `to_socket_addrs()` DNS lookup for the attacker-chosen hostname (`stackslib/src/net/dns.rs:133`).
5. Repeating with many connections and many distinct hostnames causes the node to issue many DNS lookups on attacker's behalf. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

        if let Some(addrs) = self.hardcoded.get(&(req.host.clone(), req.port)) {

        }

        // TODO: this is a blocking operation, but there's not really a good solution here other

        let addrs: Vec<SocketAddr> = match (req.host.as_str(), req.port).to_socket_addrs() {
            Ok(iter) => {
                let mut list = vec![];
                for addr in iter {
                    list.push(addr);
                }
                list
            }
            Err(ioe) => {
                return DNSResponse::error(req, format!("DNS resolve error: {:?}", &ioe));
            }
        };

        if addrs.is_empty() {
            return DNSResponse::error(req, "DNS resolve error: got zero addresses".to_string());
        }
        test_debug!("{}:{} resolved to {:?}", &req.host, req.port, &addrs);
        DNSResponse::new(req, Ok(addrs))
    }

    pub fn parse_to_block_url(&self) -> Result<url::Url, codec_error> {
        // even though this code uses from_utf8_unchecked() internally, we've already verified that
        // the bytes in this string are all ASCII.
        let url = url::Url::parse(&self.to_string())
            .map_err(|e| codec_error::DeserializeError(format!("Invalid URL: {:?}", &e)))?;

        if url.scheme() != "http" && url.scheme() != "https" {
            return Err(codec_error::DeserializeError(format!(
                "Invalid URL: invalid scheme '{}'",
                url.scheme()
            )));
        }

        if !url.username().is_empty() || url.password().is_some() {
            return Err(codec_error::DeserializeError(
                "Invalid URL: must not contain a username/password".to_string(),
            ));
        }

        if url.host_str().is_none() {
            return Err(codec_error::DeserializeError(
                "Invalid URL: no host string".to_string(),
            ));
        }

        if url.query().is_some() {
            return Err(codec_error::DeserializeError(
                "Invalid URL: query strings not supported for block URLs".to_string(),
            ));
        }

        if url.fragment().is_some() {
            return Err(codec_error::DeserializeError(
                "Invalid URL: fragments are not supported for block URLs".to_string(),
            ));
        }

        Ok(url)
    }
