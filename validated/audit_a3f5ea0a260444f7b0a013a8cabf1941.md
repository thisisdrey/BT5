### Title
Central-directory ZIP64 extra-field parsing buffer over-read in ijar's zip reader - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in bazel's ijar library parses the "extra fields" of each ZIP central-directory entry without any bounds validation, mirroring the ALPINE-CVE-2022-23537 class of bug: an attacker-controlled, length-prefixed "attribute" (there, a STUN attribute; here, a ZIP extra-field record) is trusted to actually contain the number of bytes its handler expects, and the parser reads past the declared/available bytes when it doesn't.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the central directory bytes of an untrusted `.zip`/`.jar` file and then walks the extra-field region with no bound checks: [1](#0-0) 

Inside the loop, for each sub-field it reads a 2-byte `header_id` and a 2-byte `data_size`, and if `header_id == ZIP64_EXTRA_FIELD_TAG` it unconditionally calls `get_u8le(extra)` up to three times (24 bytes) starting at `extra`, the start of that sub-field: [2](#0-1) 

There is no check that `data_size >= 24` (the size actually needed for the up to three 8-byte ZIP64 values), no check that `extra + 24` stays within `extra_p + extra_field_length` (the declared extra-field region), and no check against the end of the memory-mapped input file at all. Contrast this with `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading variable-length fields such as `file_name` and `extra_field`: [3](#0-2) 
`ProcessCentralDirEntry` has no equivalent `EnsureRemaining` calls anywhere, and the comment above it explicitly (incorrectly) assumes safety merely because "the central directory is always followed by another data structure that has a signature": [4](#0-3) 
That assumption does not protect against reads that occur *within* a single entry's extra-field region, nor at the very end of the mapped file, where an attacker can place a tiny (e.g. 0-byte) ZIP64 extra field as the last bytes of the archive.

`get_u4le`/`get_u2le`/`get_u8le` (declared in `third_party/ijar/common.h`) are simple little-endian byte readers that perform no bounds checking themselves, so any missing caller-side check translates directly into an out-of-bounds read of the memory-mapped file buffer.

This code is reachable from real bazel build actions: ijar is invoked whenever bazel processes a `.jar` (e.g., generating interface jars for `java_library`/`java_import`, or via `singlejar`/related tooling built on the same `InputZipFile` reading path), and the jar file content can originate from an externally-fetched, attacker-controlled artifact (e.g., a malicious `http_jar`/`http_file`/`maven_install` dependency, or any `.jar` on an untrusted branch that CI builds), i.e., "bytes at a dependency URL" consumed later by ijar without any checksum-gated parsing boundary protecting internal extra-field reads.

### Impact Explanation
A maliciously crafted `.jar`/`.zip` with a central-directory entry containing a ZIP64 extra field whose declared `data_size` is smaller than 24 bytes (or a `header_id`/`data_size` combination placed at the very tail of the mapped file) causes `get_u8le` to read up to 24 bytes past the intended sub-field boundary and potentially past the end of the mmap'd input file. This is a classic out-of-bounds/buffer over-read: it can leak adjacent process memory contents into computed `uncompressed_size`/`compressed_size`/`offset` values (which influence subsequent size/allocation decisions), or crash the build (SIGSEGV) if the read crosses an unmapped page boundary at the end of the file mapping. This matches the "Buffer overread ... when parsing a specially crafted [message] with unknown attribute" bug class of the reference CVE, mapped onto bazel's own ZIP/JAR extra-field parser instead of PJSIP's STUN parser.

### Likelihood Explanation
Any repository or root-level target that consumes a jar file supplied by an unprivileged, external party (a hostile mirror, a malicious release artifact fetched by `http_jar`/`http_archive`, a compromised Maven artifact, or files on an untrusted branch that CI builds and then processes with `java_library`/ijar or `singlejar`) can trigger this path merely by including one crafted ZIP64 extra field in the central directory of an otherwise valid-looking jar. No output-base or credential access, no MITM, and no root-repo Starlark trust is required — only that ijar/`InputZipFile` be invoked to read the file's central directory, which happens automatically as part of normal Java build actions.

### Recommendation
Add explicit bounds checks in `InputZipFile::ProcessCentralDirEntry`'s extra-field loop before reading:
- Verify `extra_p + 4 <= p` before reading `header_id`/`data_size`.
- Verify `extra_p + data_size <= p` (does not overrun the declared extra-field region) before advancing `extra_p`.
- Verify `data_size >= 24` (or the actual number of ZIP64 sub-values needed) before invoking `get_u8le` three times on `extra`.
- Additionally bound all of these against `zipdata_in_ + input_file_->Length()` (the actual end of the mapped file), analogous to the existing `EnsureRemaining()` used in `ProcessLocalFileEntry`.
On any violation, treat the archive as malformed and abort parsing with an error, rather than reading past the sub-field/file boundary.

### Proof of Concept
A `BuildIntegrationTestCase`/`src/test/shell/bazel` style reproduction:
1. Programmatically craft a minimal ZIP archive whose single central-directory entry has `uncompressed_size32`/`compressed_size32` fields set to `0xFFFFFFFF` (forcing ZIP64 lookup) and an extra field with `header_id = 0x0001` (ZIP64 tag) but `data_size = 0`, placed as the very last bytes of the file (immediately followed by the End Of Central Directory record so no other data exists past it).
2. Feed this archive to ijar (e.g., via `singlejar`/an ijar-based `java_library` build, or a unit test directly instantiating `InputZipFile`/calling `ProcessCentralDirEntry`).
3. Run under AddressSanitizer/Valgrind: `get_u8le(extra)` in the ZIP64 branch reads 8–24 bytes starting at `extra` (a 0-length declared field) which extends past the mapped extra field and, in this crafted layout, past the end of the mmap'd file, producing a heap/mmap buffer-overflow-read report (or a SIGSEGV without ASan, depending on page alignment).

Note: I was not able to execute this PoC or fully trace every downstream consumer of `InputZipFile` (e.g., whether `singlejar`'s reader shares this exact code path or has independent bounds checks) within the scope of static code search; a background Devin session with sandbox/build access would be needed to build and run the ASan-instrumented reproduction to confirm the crash/over-read empirically.
