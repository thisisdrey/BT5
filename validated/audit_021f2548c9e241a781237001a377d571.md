### Title
Gitaly-signed commit signatures are not bound to a repository, enabling cross-repository signature replay - (File: internal/gitaly/service/commit/get_commit_signatures.go)

### Summary
`GetCommitSignatures` reports a commit as `SIGNER_SYSTEM` (i.e., "signed by Gitaly") whenever `SigningKeys.Verify` succeeds against the commit's raw payload. That payload never includes any per-repository or per-installation identifier, so any user who can obtain a Gitaly system-signed commit (e.g., via GitLab's squash/rebase/cherry-pick web operations, which set `Sign: true` in `WriteCommitConfig`) can replay the identical raw commit object plus its signature into a completely different repository they control and have it reported as Gitaly-verified there too.

### Finding Description
- `internal/git/localrepo/commit.go` `WriteCommit` invokes `git commit-tree --gpg-sign=<key>` when `cfg.Sign` is set, producing a commit object whose signed content is exactly the commit's `tree`/`parent`/`author`/`committer`/`message` fields [1](#0-0) .
- `internal/signature/gpg.go` `CreateSignature`/`Verify` operate purely on `contentToSign`/`signedText` byte slices with no repository context mixed in [2](#0-1) .
- `internal/gitaly/service/commit/get_commit_signatures.go` `GetCommitSignatures` calls `signingKeys.Verify(signature, commit.SignatureData.Payload)` and marks the commit `SIGNER_SYSTEM` on success, again with no check that the commit actually originated in the queried repository under a Gitaly-issued transaction [3](#0-2) .
- Signatures are deterministic for identical content and signing key, as demonstrated by `TestGPGSignatureDeterministic` [4](#0-3) .

Because Git commit objects are content-addressed, an attacker with write access to any repository can construct a commit whose `tree`/`parent`/`author`/`committer`/`message` bytes exactly match a commit that was legitimately signed by Gitaly elsewhere (e.g., copied from a public repository, a merge/rebase/squash commit produced via GitLab's Web IDE against a repo on the same Gitaly node), then `git push` (or write the loose object directly) that identical object plus the captured signature into a target repository. Calling `GetCommitSignatures` against the target repository will then report `Signer: SIGNER_SYSTEM`, misrepresenting the commit as Gitaly-verified even though Gitaly never signed it in that repository's context.

### Impact Explanation
This is a signature-replay/spoofing issue analogous to the reported bug class: a signature intended to attest to one context (one repository/transaction) can be validly presented in a different context (a different repository) because the signed payload lacks a scope-binding identifier (the "chainId" equivalent here would be repository/storage identity). Any downstream feature that trusts `GetCommitSignaturesResponse.Signer == SIGNER_SYSTEM` as proof of a GitLab-server-generated commit (e.g., "Verified" badges, provenance/audit checks, or policy gates that special-case system-authored commits) can be spoofed by an ordinary user with push access to any repository on the same Gitaly deployment.

### Likelihood Explanation
Likelihood is moderate: the attacker needs (a) push/write access to some target repository, and (b) a previously observed Gitaly-system-signed commit with reusable raw bytes (achievable since many GitLab operations — squash merge, rebase, cherry-pick, revert via the API/UI — set `Sign: true`, and commit content such as empty trees or common messages is easy to align, or the attacker can directly obtain the exact object from a repository they can read). No secret leakage, MITM, or privileged access is required — this is reachable purely through ordinary `git push` plus a standard RPC call (`GetCommitSignatures`).

### Recommendation
Bind the signed content to repository/installation context, e.g., include the storage name/relative path (or `GlRepository`) in the data passed to `CreateSignature`/`Verify`, or otherwise require an out-of-band, repository-scoped attestation rather than relying solely on the raw commit bytes to determine `SIGNER_SYSTEM` status. Alternatively, treat `SIGNER_SYSTEM` purely as "this content was signed with our GPG/SSH key" without implying it was created in the current repository, and update any consumer that treats it as repository-scoped provenance.

### Proof of Concept
1. On Repository A (any repo where a GitLab web operation triggers a signed system commit, e.g. squash-merge), obtain the resulting commit's raw object via `git cat-file commit <oid>` and its GPG/SSH signature via the `GetCommitSignatures` RPC (`internal/gitaly/service/commit/get_commit_signatures.go`).
2. Recreate an identical tree/parent/author/committer/message combination in Repository B, controlled by the attacker but hosted on the same Gitaly deployment (same signing key), such that `git hash-object -t commit` produces the same commit ID as in Repository A. In the simplest case, replay the exact same commit object (same tree, same parents, same author/committer lines and dates, same message) if the underlying blobs/trees already exist or can be reproduced, e.g. via an empty tree with no parents.
3. Write this commit object (with the embedded `gpgsig`/SSH signature header copied byte-for-byte from step 1) into Repository B's object store via `git push` or direct loose-object write, and point a ref at it.
4. Call `GetCommitSignatures` against Repository B for this commit ID; the response returns `Signer: SIGNER_SYSTEM`, exactly like the legitimate Repository A commit, because `signingKeys.Verify` only checks the raw content/signature pair without validating repository context [3](#0-2) .

// CreateSignature creates a gpg signature
func (sk *GpgSigningKey) CreateSignature(contentToSign []byte, date time.Time) ([]byte, error) {
	var sigBuf strings.Builder
	if err := openpgp.ArmoredDetachSignText(
		&sigBuf,
		sk.Entity,
		bytes.NewReader(contentToSign),
		&packet.Config{
			Time: func() time.Time {
				return date
			},
		},
	); err != nil {
		return nil, fmt.Errorf("sign commit: %w", err)
	}

	return []byte(sigBuf.String()), nil
}

func (sk *GpgSigningKey) PublicKey() ([]byte, error) {
	return nil, fmt.Errorf("gpg public key not implemented")
}

// Verify method verifies whether a signature has been created by this signing key
func (sk *GpgSigningKey) Verify(signature, signedText []byte) error {
	_, err := openpgp.CheckArmoredDetachedSignature(
		openpgp.EntityList([]*openpgp.Entity{sk.Entity}),
		bytes.NewReader(signedText),
		bytes.NewReader(signature),
		&packet.Config{},
	)

	return err
}
