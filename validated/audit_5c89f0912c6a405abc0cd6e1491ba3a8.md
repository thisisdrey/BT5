### Title
Unbounded array-length field taken directly from untrusted TVM precompile calldata can trigger uncaught `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` and crash the node - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read a 32-byte length word directly out of attacker-supplied precompile calldata via `DataWord.intValueSafe()` and immediately use it to size a Java array (`new byte[len][]`), with no validation that `len` is consistent with the actual size of `words`/`data`.

### Finding Description
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  for (int i = 0; i < len; i++) {
    bytes32Array[i] = words[offset + i + 1].getData();
  }
  return bytes32Array;
}
``` [1](#0-0) 

The same pattern repeats in `extractBytesArray` and `extractSigArray`, where `len` is again taken unchecked from calldata and used to allocate `bytesArray = new byte[len][]` before looping and indexing `words[offset + i + 1]`: [2](#0-1) 

This mirrors the CVE-2021-21844 bug class: a length/offset field is taken from untrusted, attacker-controlled input and used directly in memory-allocation/copy arithmetic without validating it against the actual buffer bounds. In the original GPAC bug this produced a heap buffer overflow because C arithmetic silently overflows; in java-tron the JVM's bounds checking prevents silent memory corruption, but a sufficiently large `len` (up to `Integer.MAX_VALUE`, since `intValueSafe()` only clamps a 256-bit word into the `int` range rather than validating it against the real `words.length`) causes `new byte[len][]` to throw `OutOfMemoryError` — a JVM `Error`, not an `Exception` — while the subsequent loop can also throw `ArrayIndexOutOfBoundsException` when `offset + i + 1` exceeds `words.length`. `Error` subclasses are commonly not caught by the generic `catch (Exception e)` handlers used around precompile execution and TVM contract calls, so this can escape as an unhandled `Throwable` on the block-application/transaction-execution thread.

### Impact Explanation
If the unbounded allocation or index-out-of-bounds throws an uncaught `Error`/`RuntimeException` that propagates past the transaction-execution try/catch and into `Manager`'s block application path, it can crash the node process or halt further transaction/block processing for that node — matching the accepted "node crash or halt" impact category. Any unprivileged contract deployer or caller that reaches a precompiled contract using these helper methods with crafted calldata can trigger it.

### Likelihood Explanation
Reachability requires only a normal signed transaction that calls into a TVM precompiled contract exercising one of these array-extraction helpers with a maliciously large length word — no special privileges (SR/witness/committee status) are needed, matching the required "unprivileged transaction broadcaster/contract deployer" attacker model.

### Recommendation
Validate `len` against the real bounds of `words`/`data` (e.g., `len >= 0 && offset + len < words.length`) before allocating or indexing, and cap it to a sane maximum consistent with expected precompile input sizes, mirroring the `addSafely`/`verifyLength`-style guards already used elsewhere in the codebase (e.g., in `ModExp.getEnergyForData` and `RLP.calcLength`) [3](#0-2) [4](#0-3) .

### Proof of Concept
I was unable to fully trace, within the remaining search budget, which specific precompiled contract type(s) invoke `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (this appears to back a multi-signature/array-based precompile, e.g. a batch-signature-validation contract), nor confirm whether the outer `execute()` wrapper for that specific precompile catches `Throwable`/`Error` broadly enough to prevent propagation. This limits certainty about the exact reachable impact (full node crash vs. contained transaction failure). A concrete PoC would require constructing calldata for that precompile with the length word set to a very large value (e.g. `0x7fffffff`) and confirming whether the resulting `OutOfMemoryError`/`ArrayIndexOutOfBoundsException` is caught by the calling code or escapes to crash the executing thread/node — this should be verified in a full Devin session with code execution rather than static/index-based review, since the index does not expose the complete call graph and surrounding exception-handling for these helper methods.
