### Title
ETH-implicit accounts can be permanently created pointing to a non-existent global Wallet Contract, freezing funds - ([File: runtime/runtime/src/actions.rs])

### Summary
When the `EthImplicitGlobalContract` protocol feature is active, creation of an ETH-implicit account (triggered by an ordinary `Transfer` to a `0x…` account id) unconditionally sets the account's code pointer to `AccountContract::Global(eth_wallet_global_contract_hash(chain_id))`, without ever checking that a global contract with that hash was actually deployed by the operator. This is analogous to the reported bug class: a contract is assumed to have been "made somewhere by the operator," and functions relying on it (`rlp_execute`, the sole way to use an ETH-implicit account) silently fail if that assumption doesn't hold.

### Finding Description
`action_implicit_account_creation_transfer` handles the `EthImplicitAccount` branch by directly constructing the account with a `Global` contract pointer, with no existence check: [1](#0-0) 

Contrast this with the only other code path that attaches a global contract identifier to an account, `use_global_contract`, which explicitly checks the trie for the contract's presence and errors with `GlobalContractDoesNotExist` if missing: [2](#0-1) 

The ETH-implicit path skips this validation entirely because `GlobalContractIdentifier::CodeHash(hash).hash()` short-circuits and returns the hash unconditionally, without touching the trie: [3](#0-2) 

This means `RuntimeContractIdentifier::resolve` (used during execution) will always "successfully" resolve an ETH-implicit account's contract to `Global { code_hash, .. }` even if the corresponding code was never deployed to the shard via `deploy_global_contract`. The hardcoded per-chain hashes that this mechanism depends on are placeholders that assume an operator will deploy matching code: [4](#0-3) 

The crate's own README states the contract build is currently disabled and must not be used in production, underlining that the deployed-global-contract precondition is easy to violate operationally: [5](#0-4) 

Critically, ETH-implicit accounts cannot be deleted, and no full-access key can ever be added to them — the Wallet Contract's `rlp_execute` method is the *only* way to move funds out: [6](#0-5) 

### Impact Explanation
If the global wallet contract referenced by `eth_wallet_global_contract_hash(chain_id)` is not actually present on a given shard at account-creation time (e.g. deployment race, wrong hash configured for a custom chain_id, or deployment only reaching some shards), any `0x…` account created by an ordinary user's `Transfer` becomes permanently unusable: it has no code to execute `rlp_execute`, cannot be deleted, and can never receive an access key. Any NEAR sent to such an account is **permanently frozen** with no possible recovery path — meeting the "permanent freezing of funds" impact bar.

### Likelihood Explanation
This is reachable by any ordinary user transaction (a plain `Transfer` to an unused `0x…` account id causes implicit account creation), no special/operator privileges required to *trigger* the bug — only the precondition (operator not yet having deployed the matching global contract on the relevant shard, or a hash mismatch) needs to hold, which is plausible given the documented "must not use in production" / "build disabled" status of the wallet contract crate and the shard-by-shard propagation delay of global contracts (noted for other global-contract paths, e.g., `UseGlobalContractAction`'s docs state contract propagation "may take a while... to all shards").

### Recommendation
Before assigning `AccountContract::Global(global_contract_hash)` in `action_implicit_account_creation_transfer`, verify that the corresponding global contract code actually exists in the local shard's trie (the same check already performed in `use_global_contract`), and fail/reject implicit account creation (or fall back gracefully) if it does not, rather than silently creating a permanently-bricked account.

### Proof of Concept
Not applicable in this static analysis — reproducing requires a running shard where the `EthImplicitGlobalContract` feature is enabled but the wallet global contract has not (yet) been deployed on that shard, then sending a plain `Transfer` to a new `0x…` account and observing that any subsequent `rlp_execute` call fails permanently while the account remains funded, non-deletable, and keyless.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }

impl GlobalContractAccessExt for GlobalContractIdentifier {
    fn hash(self, store: &TrieUpdate, access: AccessOptions) -> Result<CryptoHash, StorageError> {
        if let GlobalContractIdentifier::CodeHash(hash) = self {
            return Ok(hash);
        }
        let key = TrieKey::GlobalContractCode { identifier: self.into() };
        let value_ref =
            store.get_ref(&key, KeyLookupMode::MemOrFlatOrTrie, access)?.ok_or_else(|| {
                let TrieKey::GlobalContractCode { identifier } = key else { unreachable!() };
                StorageError::StorageInconsistentState(format!(
                    "Global contract identifier not found {:?}",
                    identifier
                ))
            })?;
        Ok(value_ref.value_hash())
    }
