### Title
Unbounded `future.get()` after ignored `CountDownLatch.await()` timeout in `VerifyTransferProof.execute()` causes non-terminating wait / node DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `VerifyTransferProof` precompiled contract (used to validate Sapling shielded-transfer proofs from TVM) submits verification tasks to a shared fixed thread pool and waits on a `CountDownLatch` bounded by the remaining CPU time budget. The boolean result of the timed `await()` is captured but never checked, after which the code unconditionally calls `future.get()` on every submitted task with no timeout, exactly mirroring the libkcapi bug class: an unhandled timeout signal is followed by an unbounded wait that can hang forever if a task never completes.

### Finding Description
In `VerifyTransferProof.execute()`: [1](#0-0) 
the code does `boolean withNoTimeout = countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS);` and then iterates `futures` calling `future.get()` without ever inspecting `withNoTimeout`. If the CPU-time budget is exhausted before all `SaplingCheckSpendTask` / `SaplingCheckOutputTask` / `SaplingCheckBingdingSig` tasks finish on the shared 5-thread pool [2](#0-1) , `future.get()` for any not-yet-completed task blocks indefinitely — there is no timeout argument passed to `get()`. Because `workersInConstantCall`/`workersInNonConstantCall` are small fixed pools shared by every TVM call that reaches this precompile, once one call's future is left unresolved (e.g., a native verification call in `JLibrustzcash` stalls or a worker thread is starved by CPU-budget-exhausted concurrent calls), any thread awaiting that future via `future.get()` never returns, exactly matching the CVE's description of "reusing a handle after a prior completion error" leading to a non-terminating wait.

### Impact Explanation
Because this precompile is reachable from ordinary TVM execution (any smart contract or triggered transaction invoking the Sapling `verifyTransferProof` precompiled address with a valid input length), an unprivileged transaction sender can drive execution into a state where the calling thread — which is a TVM execution thread used during transaction processing/block application in `Manager` — blocks forever on `future.get()`. This ties up execution threads with no timeout recovery path, and can escalate into a persistent denial of service for the node’s transaction/block processing pipeline, matching the "node crash or halt" / "API the node can no longer serve" impact bar.

### Likelihood Explanation
The precondition is timing-dependent: it requires the CPU budget to run out relative to the native verification tasks (plausible under legitimate high load, contended thread pools, or slow/failed native calls), so it is not deterministically triggerable on every single call, but the code path is reachable via any transaction that calls this precompile, and the missing check-and-timeout is a straightforward logic defect (dead `withNoTimeout` variable) rather than a hypothetical scenario.

### Recommendation
Check the `withNoTimeout` result of `countDownLatch.await(...)`; if it is `false` (timed out), cancel/skip remaining futures (e.g., `future.cancel(true)` or treat as failed) rather than calling blocking `future.get()`. Additionally, bound `future.get()` calls with an explicit timeout (e.g., the remaining CPU time) so a stuck task cannot hang the calling thread indefinitely.

### Proof of Concept
1. An attacker deploys/calls a contract that repeatedly invokes the Sapling `verifyTransferProof` precompiled address with valid-length payloads (2080/2368/2464/2752 bytes) concurrently, saturating the 5-thread `workersInConstantCall`/`workersInNonConstantCall` pools.
2. Under load, some calls' `countDownLatch.await(getCPUTimeLeftInNanoSecond(), ...)` times out (returns `false`, ignored).
3. Execution proceeds to `future.get()` on tasks still queued/running on the exhausted pool; these calls block with no timeout, hanging the TVM execution thread that made the call.
4. Repeating this pattern across pending/incoming transactions can accumulate blocked threads, degrading or halting transaction/block processing. [3](#0-2)
