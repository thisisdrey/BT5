### Title
Stale-Authorization / Time-of-Check-to-Time-of-Use Window in Git Upload-Pack Negotiation Not Enforced for the SmartHTTP Transport - (File: `internal/gitaly/service/ssh/upload_command.go`)

### Summary
Gitaly already recognizes and partially mitigates a "use-after-check" (stale authorization) bug class that is structurally identical to the reported RAAC `BoostController` issue: an access grant is validated once at the start of an operation, and if the operation can be kept open indefinitely by the caller, the grant is honored long after the conditions that justified it (e.g. project visibility, user membership, token validity) may have changed. Gitaly built a dedicated `pktline.ReadMonitor` to bound this window, but it is wired into only one of the fetch transports (`SSHUploadPack`/`SSHUploadArchive`), leaving the equivalent SmartHTTP fetch path without the same time-boxing of the negotiation phase.

### Finding Description
`internal/git/pktline/read_monitor.go` documents the exact bug class explicitly: [1](#0-0) 

The mitigation is invoked from `runUploadCommand`, which is only used by the SSH `upload-pack`/`upload-archive` code path: [2](#0-1) [3](#0-2) 

The comment inside this function states the threat model directly: "Because access checks only happen at the beginning of the call, it may be the case that the client's permissions have changed since the RPC call started," and the `ReadMonitor` is the counter-measure — it cancels the underlying git process if the negotiation boundary packet (`done`/flush) isn't observed within a bounded timeout, closing the "delegated access persists after backing is withdrawn" window for SSH fetches.

A repository-wide search for consumers of `pktline.NewReadMonitor`/`Monitor` shows this mechanism is used in exactly one place in the whole codebase (`internal/gitaly/service/ssh/upload_command.go`); there is no equivalent negotiation-timeout wiring found in the SmartHTTP upload-pack handling path. Since GitLab's access check (the Rails `/internal/allowed` / `pre-receive`-equivalent check for fetches, and repository visibility/authorization checks generally) is performed once at RPC start — same pattern documented in `doc/object_quarantine.md` and `internal/gitaly/hook/prereceive.go` for the receive side — any transport that omits the `ReadMonitor`-style negotiation cutoff inherits the same unresolved TOCTOU: a client can open an authorized fetch/clone, stall the pack negotiation phase indefinitely (e.g. never send the final `done` pktline or `flush-pkt`), and later be revoked (removed from the project, token/SSH key revoked, project made private) without the still-open RPC being interrupted, allowing it to complete and hand over pack data the caller is no longer entitled to.

### Impact Explanation
This is directly analogous to the reported bug's impact: a permission/benefit ("boost"/access grant) is checked once and never re-validated against its current backing (veRAAC balance / repository authorization), letting a caller retain undeserved access for an extended, attacker-controlled duration. In Gitaly's case this means an authenticated user whose access to a repository is revoked mid-request can still complete a fetch/clone that discloses the repository's full object graph, because only the SSH transport enforces a bound on how long the negotiation phase (and therefore the "unrevalidated access window") may last.

### Likelihood Explanation
Reachable directly by any ordinary, unprivileged client performing a normal `git fetch`/`git clone` over the SmartHTTP transport — no special privilege, malicious peer, or MITM position is required, only the ability to delay sending the negotiation-terminating pktline for as long as the surrounding RPC/connection deadlines allow. The SSH transport already required this exact fix, which is strong evidence the same client-controlled stalling behavior is possible for HTTP-based upload-pack.

### Recommendation
Apply the same `pktline.ReadMonitor` negotiation-timeout pattern used in `internal/gitaly/service/ssh/upload_command.go` to the SmartHTTP `PostUploadPack`/`UploadPack` handler(s), so that the negotiation phase for HTTP-based fetches is bounded identically to SSH. More generally, any RPC that performs an authorization check once at the start and then depends on client-supplied pktline input to proceed should either (a) be wrapped with an equivalent bounded negotiation-timeout mechanism, or (b) re-run the authorization check immediately before object data is transmitted, to avoid time-of-check-to-time-of-use gaps.

### Proof of Concept
1. An attacker with legitimate, currently-valid access to a private repository initiates `git fetch` (or `git clone`) over HTTP against Gitaly's SmartHTTP `upload-pack` endpoint. Gitaly/GitLab performs the access check at connection start and passes it.
2. The attacker's client withholds the final negotiation packet (e.g. does not send the `done` line / delays it deliberately) for an extended period.
3. While the request remains open, the attacker's access to the repository is revoked (removed from project, PAT revoked, project set private).
4. The attacker finally completes negotiation; because the SmartHTTP path has no `ReadMonitor`-equivalent negotiation timeout (unlike `internal/gitaly/service/ssh/upload_command.go`), the git-upload-pack process is not cancelled and proceeds to transmit the full pack, disclosing repository contents the attacker is no longer authorized to access.

Note: due to indexing limits, the exact contents of the SmartHTTP `upload_pack.go` handler could not be directly retrieved to show the absence of the mitigation line-by-line; this conclusion is based on the fact that `pktline.NewReadMonitor`/`Monitor` has exactly one call site in the codebase (SSH), and no other consumer was found repository-wide. Confirming or ruling out equivalent protection inside `internal/gitaly/service/smarthttp/` would require starting a full Devin session with complete file access.

```go
// ReadMonitor monitors an io.Reader, waiting for a specified packet. If the
// packet doesn't come within a timeout, a cancel function is called. This can
// be used to place a timeout on the *negotiation* phase of some git commands,
// aborting them if it is exceeded.
//
// This timeout prevents a class of "use-after-check" security issue when the
// access check for a git command is run before the command itself. The user
// has control of stdin for the git command, and if they can delay input for
// an arbitrarily long time, they can gain access days or weeks after the
// access check has completed.
//
// This approach is better than placing a timeout on the overall git operation
// because there is a conflict between mitigating the use-after-check with a
// short timeout, and allowing long-lived git operations to complete. The
// negotiation phase is a small proportion of the time taken for a large git
// fetch, for instance, so tighter limits can be placed on it, leading to a
// better mitigation.
```
