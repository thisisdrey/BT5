### Title
Unbounded per-IP connection-attempt churn before per-IP rate-limit registration bypasses `max_connections_per_ipaddr_per_min` up to the global concurrency cap - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`run_server` only calls `rate_limiter.is_allowed(ip)` (a non-mutating read of `current_tokens`) before accepting a connection, and only calls the mutating `rate_limiter.register_connection(ip)` inside `setup_connection` after the QUIC handshake completes. An attacker can open many connections from one IP and never complete the handshake within `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s), so the per-IP token bucket is never actually decremented while `outstanding_incoming_connection_attempts` and `open_connections` are incremented for each attempt.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:342-407`), the accept loop:
1. Increments `stats.total_incoming_connection_attempts`.
2. Checks the global `overall_connection_rate_limiter` (consumes a token here).
3. Checks the per-IP limiter via `rate_limiter.is_allowed(&incoming.remote_address().ip())` — this only reads `current_tokens` and does **not** consume a token (`ConnectionRateLimiter::is_allowed`, `streamer/src/nonblocking/connection_rate_limiter.rs:34-40`).
4. Creates a `ClientConnectionTracker` which enforces the *global* `max_concurrent_connections` cap (`ClientConnectionTracker::new`, `quic.rs:239-251`), not a per-IP cap.
5. Increments `outstanding_incoming_connection_attempts` and spawns `setup_connection`, which awaits the handshake with `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting)`.

Only after the handshake successfully completes does `setup_connection` call `rate_limiter.register_connection(&from.ip())` (`quic.rs:483`), which is the only call that actually consumes a token from the per-IP `KeyedRateLimiter`. If the handshake times out or errors, `register_connection` is never invoked for that IP, so the per-IP token bucket is untouched by that attempt.

Because `is_allowed` never mutates state, a single IP can repeatedly open connections, stall the handshake (e.g., send only the `Initial` packet and never respond to `Handshake`), and never be charged against its per-IP quota. Each such attempt still consumes an `open_connections` slot (via `ClientConnectionTracker`) and an `outstanding_incoming_connection_attempts` slot for up to 2 seconds, and the global `overall_connection_rate_limiter`/`max_concurrent_connections` are the *only* real per-attacker bottlenecks — there is no per-IP cap on outstanding/half-open handshakes. This lets one IP consume the entire shared `max_concurrent_connections` budget (`SwQos::max_concurrent_connections`, `streamer/src/nonblocking/swqos.rs:518-522`, computed as `(max_staked_connections + max_unstaked_connections) * 5/4`) with stalled handshakes, crowding out legitimate connections from other IPs, while the attacking IP's own per-IP rate limiter budget remains essentially untouched (since it's only decremented on handshake success).

### Impact Explanation
This is a remote, unauthenticated DoS: a single-source attacker can monopolize the finite global handshake/connection-attempt capacity by repeatedly stalling handshakes, denying legitimate connections (from other IPs, staked or unstaked) for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` per stalled attempt, repeatable indefinitely. It does not evade the *global* connection/token caps (since those bound total resource consumption), but it does evade the intended purpose of the *per-IP* rate limiter — that limiter is designed to make one IP unable to hog capacity, and that guarantee is defeated because `is_allowed` doesn't reserve/consume tokens ahead of handshake completion.

### Likelihood Explanation
Highly feasible: no stake, keys, or privileged network position is required — only the ability to open TCP/UDP-like QUIC connections to the leader's TPU QUIC port and withhold completion of the handshake (e.g., send `Initial` and stop, or complete `Initial` but delay `Handshake` completion). The 2-second window and lack of per-IP charge on non-completing attempts make this trivially repeatable in a tight loop.

### Recommendation
Reserve/charge the per-IP rate limiter token at accept time (before spawning `setup_connection`), and refund it if the handshake never completes (or use a separate "pending handshake" per-IP counter with its own cap, decremented on completion or timeout). This ensures a stalling attacker is charged for each attempt regardless of whether the handshake finishes, closing the gap between `is_allowed` (read-only) and `register_connection` (the only consuming call).

```rust
    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }

    pub fn register_connection(&self, ip: &IpAddr) -> bool {
        if self.limiter.consume_tokens(*ip, 1).is_ok() {
            debug!("Request from IP {ip:?} allowed");
            true // Request allowed
        } else {
            debug!("Request from IP {ip:?} blocked");
            false // Request blocked
        }
    }
```
