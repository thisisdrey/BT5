### Title
Unauthenticated `GitObjectDirectory`/`GitAlternateObjectDirectories` request fields let a caller graft an arbitrary existing quarantine (or repository's own object directory) onto a different repository object, bypassing the intended "quarantine belongs to this push" trust model - (File: internal/gitaly/storage/storagemgr/middleware.go, internal/git/localrepo/paths.go, internal/gitaly/storage/locator.go)

### Summary
Gitaly's `Repository` protobuf message carries `GitObjectDirectory`/`GitAlternateObjectDirectories` fields that are supposed to be set only by Gitaly itself when it creates a quarantine directory for an in-flight push, and are then echoed back to Gitaly by Rails during the `/internal/allowed` access-check callback so RPCs can see quarantined (not-yet-committed) objects [1](#0-0) . In practice, however, any RPC caller can set these fields directly on a `Repository` message in a request, and Gitaly's validation only checks that the resulting path is either inside the repository or matches a deterministic, non-secret quarantine-prefix pattern (`quarantine-<sha1(relative_path)[:8]>-`) inside the storage's shared temp directory [2](#0-1) [3](#0-2) . The code that would otherwise route such requests through the transaction/quarantine machinery explicitly documents that this check is bypassable and left "unaddressed": [4](#0-3) 

### Finding Description
This is a structural analog of the DCA bug: a field that is meant to represent a *consented, provenance-verified* linkage (the DCA `recipient`/ownership fields; here, "this object directory belongs to a real quarantine created for this repository's push") is instead accepted as untrusted, caller-supplied input and used to redirect where Gitaly reads/writes objects and how it treats the request (transactional vs. non-transactional).

Concretely:
1. `ObjectDirectoryPath` accepts any `GitObjectDirectory` value as long as it resolves inside the repo, OR its absolute path has the prefix `filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))` [5](#0-4) .
2. `QuarantineDirectoryPrefix` is fully deterministic from the repository's `RelativePath` (a `sha1` hash, not a secret, not random) [6](#0-5) , so any caller who knows (or brute-forces/enumerates, since relative paths for hashed/well-known repos are guessable) a target repository's relative path can compute the exact prefix that Gitaly will accept as "this repo's legitimate quarantine directory".
3. `beginTransactionForRepository` explicitly notes that setting `GitObjectDirectory`/`GitAlternateObjectDirectories` on a request lets a caller "circumvent the transaction management," and only *rejects* this for Mutator RPCs (`ErrQuarantineConfiguredOnMutator`) — Accessor RPCs are allowed straight through without starting the transaction/snapshot that would normally scope quarantined objects to a single push [7](#0-6) .
4. Quarantine directories are created per push in the storage-wide temp directory and only removed by an explicit cleanup callback tied to the RPC that created them [8](#0-7) ; while such a directory exists on disk (i.e., during any concurrent push to that same repository by any user), any other request that supplies the matching (guessable) prefix and a path that survives `os.Stat` existence checks will be treated as a legitimate quarantine for that repo.

The combination allows a caller to attach another actor's in-flight quarantine directory (or otherwise manipulate which object directory an Accessor RPC reads from) to their own request for the same target repository, without Gitaly having verified that *this* caller is the one whose push actually created that quarantine — a "quarantine gating bypass," analogous to the DCA report's core defect of trusting a consent-sensitive linkage field without checking that the party asserting it is actually authorized to do so.

### Impact Explanation
An attacker who can issue Accessor RPCs against a repository (e.g., during their own concurrent push/fetch to the same repo, or via any RPC that accepts a `Repository` with these fields set) can:
- Read not-yet-authorized, in-flight objects from another user's concurrent push to the same repository before that push's `pre-receive` access check has completed (disclosure of quarantined, pre-authorization content), by pointing their own request's `GitObjectDirectory`/`GitAlternateObjectDirectories` at the other push's quarantine directory.
- Cause Accessor RPCs to silently skip normal transaction/snapshot scoping ("circumventing the transaction management," per the code comment), which the code acknowledges affects the guarantees the transaction manager is meant to provide for consistency of concurrent access.

This does not directly enable object-database corruption (quarantine `Migrate` code paths for Mutators are blocked), so the impact is scoped to information disclosure of transient quarantined objects and violation of per-request repository/transaction isolation guarantees rather than remote code execution or full storage escape.

### Likelihood Explanation
Reachability requires: (a) the target repository's relative path (obtainable for public/known repositories, or via other enumeration channels), (b) the ability to issue an Accessor RPC with a hand-crafted `Repository` message carrying `GitObjectDirectory`/`GitAlternateObjectDirectories`, and (c) a window in which another push's quarantine directory exists for that same repository (i.e., timing-dependent). The deterministic, non-random prefix removes the need to brute-force the prefix; only the existence and timing of a genuine concurrent quarantine is opportunistic. The code's own comment acknowledges the gap is real and currently accepted as a known, deliberately-deferred risk ("We'll leave this unaddressed for now") [9](#0-8) , which corroborates it is a genuine, currently-unmitigated condition rather than a purely theoretical one.

### Recommendation
- Do not accept `GitObjectDirectory`/`GitAlternateObjectDirectories` as free-form client input at all for externally-reachable RPCs; instead, thread quarantine identity through an opaque, per-push, randomly-generated token that Gitaly itself generates and verifies out-of-band (not derivable from the repository's relative path).
- For Accessor RPCs, apply the same rejection/verification used for Mutators (`ErrQuarantineConfiguredOnMutator`) unless the request can be cryptographically tied to the exact push/transaction that created the quarantine (e.g., transaction ID binding, not just a directory-name pattern match).
- Bind quarantine directory validity to the specific request/transaction context, not merely to "does the path match the deterministic per-repo prefix and exist on disk."

### Proof of Concept
Conceptual PoC (cannot be executed without a live Gitaly cluster and knowledge of a target relative path):
1. Attacker learns the target repository's relative path `R` (e.g. a public project path) and computes `prefix = "quarantine-" + hex(sha1(R)[:8]) + "-"` per `QuarantineDirectoryPrefix` [6](#0-5) .
2. Attacker waits for (or triggers, e.g. by pushing themselves) a moment when another push to repository `R` is in-flight, creating a quarantine directory under the storage temp dir matching that prefix.
3. Attacker issues an Accessor RPC (e.g. a read RPC) with `Repository{RelativePath: R, GitObjectDirectory: "<absolute-or-relative-path-to-the-guessed-quarantine-dir>"}`.
4. `ObjectDirectoryPath` accepts the path because it matches `expectedQuarantinePrefix` and exists on disk [5](#0-4) , and `beginTransactionForRepository` treats it as a legitimately quarantine-configured request rather than starting a fresh transaction [10](#0-9) , letting the attacker's RPC read objects from the other user's in-flight, not-yet-authorized quarantine.

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}

func beginTransactionForRepository(ctx context.Context, logger log.Logger, txRegistry *TransactionRegistry, node storage.Node, locator storage.Locator, methodInfo protoregistry.MethodInfo, req proto.Message) (_ transactionalizedRequest, returnedErr error) {
	targetRepo, err := methodInfo.TargetRepo(req)
	if err != nil {
		if errors.Is(err, protoregistry.ErrRepositoryFieldNotFound) {
			// The above error is returned when the repository field is not set in the request.
			// Return instead the error many tests are asserting to be returned from the handlers.
			return transactionalizedRequest{}, structerr.NewInvalidArgument("%w", storage.ErrRepositoryNotSet)
		}

		return transactionalizedRequest{}, fmt.Errorf("extract target repository: %w", err)
	}

	if targetRepo.GetGitObjectDirectory() != "" || len(targetRepo.GetGitAlternateObjectDirectories()) > 0 {
		// The object directories should only be configured on a repository coming from a request that
		// was already configured with a quarantine directory and is being looped back to Gitaly from Rails'
		// authorization checks. If that's the case, the request should already be running in scope of a
		// transaction and the repository rewritten to point to the snapshot repository. We thus don't start
		// a new transaction if we encounter this.
		//
		// This property is violated in tests which manually configure the object directory or the alternate
		// object directory. This allows for circumventing the transaction management by configuring the either
		// of the object directories. We'll leave this unaddressed for now and later address this by removing
		// the options to configure object directories and alternates in a request.

		if methodInfo.Operation == protoregistry.OpMutator {
			// Accessor requests may come with quarantine configured from Rails' access checks. Since the
			// RPC that triggered these access checks would already run in a transaction and target a
			// snapshot, we won't start another one. Mutators however are rejected to prevent writes
			// unintentionally targeting the main repository.
			return transactionalizedRequest{}, ErrQuarantineConfiguredOnMutator
		}

		rewrittenReq, err := restoreSnapshotRelativePath(ctx, methodInfo, req)
		if err != nil {
			return transactionalizedRequest{}, fmt.Errorf("restore snapshot relative path: %w", err)
		}

		return nonTransactionalRequest(ctx, rewrittenReq), nil
	}

func New(ctx context.Context, repo *gitalypb.Repository, logger log.Logger, locator storage.Locator) (*Dir, func(), error) {
	repoPath, err := locator.GetRepoPath(ctx, repo, storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, nil, structerr.NewInternal("getting repo path: %w", err)
	}

	quarantineDir, cleanup, err := tempdir.NewWithPrefix(ctx, repo.GetStorageName(),
		storage.QuarantineDirectoryPrefix(repo), logger, locator)
	if err != nil {
		return nil, nil, fmt.Errorf("creating quarantine: %w", err)
	}

	quarantinedRepo, err := Apply(repoPath, repo, quarantineDir.Path())
	if err != nil {
		cleanup() // Clean up if we fail after creating the temp directory
		return nil, nil, err
	}

	return &Dir{
		repo:            repo,
		quarantinedRepo: quarantinedRepo,
		locator:         locator,
		dir:             quarantineDir,
	}, cleanup, nil
}
