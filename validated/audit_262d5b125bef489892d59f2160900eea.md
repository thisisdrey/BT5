### Title
Go `net/http` Client leaks URI fragment via automatically generated `Referer` header on redirect - ([File: src/net/http/client.go])

### Summary
`net/http.Client.do` follows redirects and, unless the caller explicitly disables Referer generation via `Header.Set("Referer", "")`/opt-out, unconditionally computes a `Referer` value from the previous request URL using `refererForURL` and attaches it to the redirected request. `refererForURL` builds the referer with `lastReq.String()`, which serializes the URL fragment (`net/url.URL.String()` appends `#`+`EscapedFragment()` whenever `Fragment != ""`), so any sensitive data placed in the original request's URI fragment is copied into the `Referer` header sent to the redirect target — the exact bug class described in the Guzzle advisory (GHSA-h95v-h523-3mw8), but here it is unconditional (no opt-in "referer" setting like Guzzle has) rather than opt-in.

### Finding Description
Attacker input: a redirect `Location` returned by a server the victim's application follows via `http.Client.Do`/`Get` with default (or custom, redirect-permitting) `CheckRedirect`.
- Entry point: `(*Client).do` redirect loop in `src/net/http/client.go:645-735`.
- At `client.go:702-704`, the loop computes `ref := refererForURL(reqs[len(reqs)-1].URL, req.URL, req.Header.Get("Referer"))` and, if non-empty, sets it as the `Referer` header of the request sent to the new (potentially attacker-controlled) host.
- `refererForURL` (`client.go:144-168`) strips user info from the URL but does **not** strip the URL `Fragment`. It calls `referer := lastReq.String()`, and `net/url.URL.String()` re-serializes any set `Fragment` as `#...` in the output.
- Failed check: there is no fragment-stripping step analogous to the user-info stripping (`lastReq.User`) already performed — only same-scheme vs cross-scheme (https→http) is checked (`client.go:149-151`); fragments are retained across same-scheme (and even cross-host, non-subdomain) redirects.
- Sink: the `Referer` header sent to the redirect destination, which can be a server the attacker controls (e.g., an open redirect or a server issuing a redirect to an attacker-owned host), thereby disclosing whatever secret token/value the application embedded in the original URI's fragment (e.g., `https://victim.example/reset#one-time-secret`). ### Impact Explanation
This is a cross-boundary secret disclosure (CWE-201/CWE-212 analog): a URI fragment is designed to be handled purely client-side and never sent over the wire in the original request line, yet Go's HTTP client resurrects it into the `Referer` header of a subsequent request that can go to a different, potentially untrusted host. If an application embeds one-time tokens, session identifiers, or other secrets in a URL fragment (a common pattern for avoiding server-side/log exposure, e.g., password reset or OAuth implicit-flow fragments) and later that URL is redirected elsewhere (open redirect, load balancer, third-party link shortener, etc.), the fragment secret leaks to the destination server/its logs. Given `net/http.Client`'s Referer-generation is unconditional (unlike Guzzle's opt-in `allow_redirects.referer`), this is arguably reachable in more real-world configurations than the original Guzzle issue. However, this must be weighed against Go's explicit documentation (`client.go:588-593`) that states Client's redirect behavior is intentionally permissive by design ("sensitive headers are retained on redirect to a subdomain or to a different scheme on the same host"), which signals the Go team has accepted a permissive Referer/redirect model as documented behavior rather than a defect — though the fragment-specific leak is not explicitly called out in that documentation.

### Likelihood Explanation
Requires: (1) an application constructs requests with a sensitive URI fragment, (2) uses `net/http.Client` with redirect-following enabled (default), and (3) the request is redirected (open redirect, external redirect chain, or attacker-influenced `Location`) to a host that can observe the `Referer` header. No special privileges are needed by the attacker beyond controlling or observing the redirect destination — the same threat model as the Guzzle advisory.

### Recommendation
In `refererForURL` (`src/net/http/client.go`), strip the URL fragment before serializing the referer, mirroring the existing user-info stripping:
```go
u := *lastReq
u.Fragment = ""
u.RawFragment = ""
referer := u.String()
```
This preserves path/query (as Guzzle's fix does) while removing the fragment from the generated `Referer` header regardless of destination scheme/host.

### Proof of Concept
```go
package http

import (
	"net/url"
	"testing"
)

// Demonstrates that refererForURL leaks the URI fragment of the
// referring request into the generated Referer value.
func TestRefererForURL_FragmentLeak(t *testing.T) {
	last, _ := url.Parse("https://victim.example/reset#one-time-secret")
	next, _ := url.Parse("https://attacker.example/collect")

	got := refererForURL(last, next, "")

	if want := "https://victim.example/reset"; got != want {
		t.Errorf("refererForURL leaked fragment: got %q, want %q (no fragment)", got, want)
	}
}
```
Expected (buggy) result: `got` is `"https://victim.example/reset#one-time-secret"`, i.e. the assertion fails, proving the fragment `#one-time-secret` is included in the `Referer` value that would be sent to `attacker.example` after a same-scheme redirect. [3](#0-2)

// refererForURL returns a referer without any authentication info or
// an empty string if lastReq scheme is https and newReq scheme is http.
// If the referer was explicitly set, then it will continue to be used.
func refererForURL(lastReq, newReq *url.URL, explicitRef string) string {
	// https://tools.ietf.org/html/rfc7231#section-5.5.2
	//   "Clients SHOULD NOT include a Referer header field in a
	//    (non-secure) HTTP request if the referring page was
	//    transferred with a secure protocol."
	if lastReq.Scheme == "https" && newReq.Scheme == "http" {
		return ""
	}
	if explicitRef != "" {
		return explicitRef
	}

	referer := lastReq.String()
	if lastReq.User != nil {
		// This is not very efficient, but is the best we can
		// do without:
		// - introducing a new method on URL
		// - creating a race condition
		// - copying the URL struct manually, which would cause
		//   maintenance problems down the line
		auth := lastReq.User.String() + "@"
		referer = strings.Replace(referer, auth, "", 1)
	}
	return referer
}

	tests := []struct {
		lastReq, newReq, explicitRef string // from -> to URLs, explicitly set Referer value
		want                         string
	}{
		// don't send user:
		{lastReq: "http://gopher@test.com", newReq: "http://link.com", want: "http://test.com"},
		{lastReq: "https://gopher@test.com", newReq: "https://link.com", want: "https://test.com"},

		// don't send a user and password:
		{lastReq: "http://gopher:go@test.com", newReq: "http://link.com", want: "http://test.com"},
		{lastReq: "https://gopher:go@test.com", newReq: "https://link.com", want: "https://test.com"},

		// nothing to do:
		{lastReq: "http://test.com", newReq: "http://link.com", want: "http://test.com"},
		{lastReq: "https://test.com", newReq: "https://link.com", want: "https://test.com"},

		// https to http doesn't send a referer:
		{lastReq: "https://test.com", newReq: "http://link.com", want: ""},
		{lastReq: "https://gopher:go@test.com", newReq: "http://link.com", want: ""},

		// https to http should remove an existing referer:
		{lastReq: "https://test.com", newReq: "http://link.com", explicitRef: "https://foo.com", want: ""},

		{lastReq: "https://test.com", newReq: "https://link.com", explicitRef: "https://foo.com", want: "https://foo.com"},

		}
