### Title
Splitting a Nep245/Imt trade into unit-sized legs zeroes the protocol fee - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` returns `Pips::ZERO` for any `Nep245`/`Imt` leg whose `amount <= 1`, and `TokenDiff::execute_intent` computes the fee independently per signed `TokenDiff` intent rather than on the net amount of a token traded across a batch. An attacker (with a colluding or self-controlled counterparty account) can replace one large `-1_000_000` delta with 1,000,000 signed `TokenDiff` intents of `delta=-1` each, matched by the counterparty's corresponding `+1` legs via `TransferMatcher::finalize`, so the aggregate transfer still nets to zero but the summed fee collected is `0` instead of `Pips::fee_ceil(protocol_fee, 1_000_000)`.

### Finding Description
The broken binding: `fees_collected[T]` over a batch should equal `Pips::fee_ceil(protocol_fee, Σ|negative deltas of T|)`, but it can be forced to `0` regardless of `Σ|negative deltas of T|`.

Root cause is in `TokenDiff::token_fee` [1](#0-0) : for `Nep245`/`Imt` token types, the fee is `Pips::ZERO` whenever `amount <= 1`, and `fee` (the full protocol fee) only when `amount > 1`. This is applied per intent inside `execute_intent`: [2](#0-1) 
Each `TokenDiff` intent independently computes `amount = delta.unsigned_abs()` for its own map entry and multiplies by `token_fee(token_id, amount, protocol_fee)`. There is no aggregation of `amount` across multiple `TokenDiff` intents signed by the same or different accounts in the batch.

Balance conservation across the batch is enforced only by `TransferMatcher::finalize` [3](#0-2) , which matches deposits against withdrawals for a token across the *entire* batch, not per intent. It only rejects batches whose deltas don't net to zero — it does not check or care whether a single logical trade was split into many `TokenDiff` intents. So an attacker with two accounts under their control (or a colluding counterparty) can:
1. Sign 1,000,000 `TokenDiff` intents for account A, each `{Nep245Token: -1}` (paired with whatever token they receive as `+delta`, itself also split into unit legs if it's also Nep245/Imt, or a normal amount if the received token is Nep141).
2. Sign 1,000,000 matching `TokenDiff` intents for account B (or reuse a compliant counterparty/solver flow) with `+1` each on the same Nep245 token id.
3. Submit all of them together in one `MultiPayload` to `execute_intents`.

Each of the 2,000,000 `TokenDiff` intents is processed independently, `amount=1` on every negative-delta leg, so `token_fee` returns `Pips::ZERO` and `fee_ceil(1) == 0` for every leg. `TransferMatcher::finalize` still succeeds because the aggregate deposits/withdrawals for the token net to zero (1,000,000 in, 1,000,000 out), matching test behaviour shown in `invariant_violated`/`test_transfers` in `deltas.rs` and `tests/src/tests/defuse/intents/token_diff.rs`. None of the existing guards (`MultiPayload::verify`, nonce checks, `assert_one_yocto`, `TransferMatcher::finalize`) check the granularity/splitting of a trade or aggregate fee amounts across intents, so they do not prevent this divergence.

### Impact Explanation
The `fee_collector` account under-collects protocol revenue on every Nep245/Imt (multi-token) trade that is split into unit-sized legs, compared to the same net trade submitted as a single `TokenDiff`. This is a direct, repeatable fee bypass: it can be executed by any two colluding (or self-controlled) accounts for any amount of Nep245/Imt token traded, with the shortfall scaling with trade size and matching the "protocol fees bypassed" Critical category. It affects only Nep245/Imt tokens (Nep141 has no `amount>1` guard, so it is unaffected) and does not itself let an attacker steal other users' funds — it prevents fees from being credited to the protocol.

### Likelihood Explanation
Preconditions are minimal: `protocol_fee > 0` and the attacker needs access to at least one counterparty account providing the matching opposite deltas (their own second account or an actively cooperating solver/counterparty), both fully within the unprivileged attacker capability set (anyone can sign arbitrary `TokenDiff` payloads and call `execute_intents`). No roles, relayer keys, or DAO permissions are required. The only practical constraint is NEAR's per-transaction gas budget, which limits how many `TokenDiff` intents (each requiring signature verification, nonce checks, etc.) can be batched into a single `execute_intents` call; this bounds the maximum single-transaction fee bypass but does not prevent the exploit — it is trivially reproducible and economically profitable at smaller scales (e.g., splitting into tens or hundreds of unit legs across one or more transactions), and the underlying logic flaw is unconditional.

### Recommendation
Compute the fee for Nep245/Imt tokens based on the aggregate `|delta|` collected per `(signer, token_id)` (or per token_id) across the whole intents batch before applying the `amount <= 1` exemption, rather than per individual `TokenDiff` intent. Alternatively, remove or tighten the `amount > 1` exemption so it only applies to genuinely non-fungible/1-of-1 Nep245 entries (e.g., gate it on token supply/metadata indicating NFT-like semantics) rather than any transfer with `|delta| <= 1`, since a legitimate fungible Nep245 balance can always be artificially chunked into unit legs.

### Proof of Concept
```rust
// cargo test in contracts/defuse/core (unit-test style) or
// tests/src/tests/defuse/intents/token_diff.rs (sandbox style)

// Setup: protocol_fee = Pips::ONE_PERCENT (or any > 0), a Nep245TokenId `T`,
// account A holding 1_000_000 units of T, account B able to receive T and
// provide the matching opposite deltas (e.g. paired FT out for both cases,
// so results are directly comparable).

// Case 1 (bulk): single TokenDiff intent for A: {T: -1_000_000, OUT: +X}
// matched by single TokenDiff intent for B: {T: +1_000_000, OUT: -X}.
// Execute via execute_intents; record fees_collected[T] after execution.
// Expect: fees_collected[T] == protocol_fee.fee_ceil(1_000_000) > 0.

// Case 2 (split): 1_000_000 TokenDiff intents for A, each {T: -1, OUT_i: +x_i}
// and 1_000_000 matching TokenDiff intents for B, each {T: +1, OUT_i: -x_i},
// batched together in one MultiPayload and executed via execute_intents.
// Expect (bug): fees_collected[T] == 0, even though
// sum(|negative T deltas|) == 1_000_000 (identical to Case 1),
// and A's/B's net balance changes for T and OUT are identical to Case 1.

assert_ne!(fees_collected_case_1[T], fees_collected_case_2[T]);
assert_eq!(fees_collected_case_2[T], 0);
assert_eq!(fees_collected_case_1[T], protocol_fee.fee_ceil(1_000_000));
```
For a smaller, gas-feasible reproduction, replace `1_000_000` with e.g. `10` unit legs vs. one `-10` leg and assert `TokenDiff::token_fee(&nep245_token_id, 1, fee).fee_ceil(1) == 0` for every leg (per `contracts/defuse/core/src/intents/token_diff.rs:207-216`) while `TokenDiff::token_fee(&nep245_token_id, 10, fee).fee_ceil(10) > 0` for the unsplit case, then execute both batches end-to-end with `near-workspaces`/sandbox `execute_intents` and compare `fee_collector` balances.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
