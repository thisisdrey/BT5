### Title
Attacker-controlled `estimated_len` causes unchecked `u64` multiplication overflow in `estimate_tx_fee_from_cost_and_length` - ([File: stackslib/src/net/api/postfeerate.rs])

### Summary
`RPCPostFeeRateRequestHandler::try_parse_request` lets a remote, unauthenticated caller supply an arbitrary `estimated_len: Option<u64>` field in the JSON body, which is then taken via `max()` with the real payload length and passed unmodified into `estimate_tx_fee_from_cost_and_length`, where it is multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` with plain `*` (no `checked_mul`/`saturating_mul`).

### Finding Description
In `try_parse_request` [1](#0-0) , `estimated_len` is computed as `max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)`. `body.estimated_len` is fully attacker-controlled (deserialized straight from the JSON POST body with `#[serde(default)]`, no upper bound check) and only bounded by the outer HTTP body length check (`content_len < MAX_PAYLOAD_LEN`), which limits the *body bytes*, not the numeric value of the `estimated_len` field itself — a caller can send a tiny JSON body (`{"estimated_len":18446744073709551615,"transaction_payload":"00"}`) that easily fits under `MAX_PAYLOAD_LEN`.

That `estimated_len` value then flows unchecked into `estimate_tx_fee_from_cost_and_length`, where `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` [2](#0-1)  performs plain unchecked multiplication. In debug builds this panics on overflow; in release builds (Rust's default `overflow-checks = false`) it silently wraps to an arbitrary small `u64`, which is then used as the floor for every returned `RPCFeeEstimate.fee` [3](#0-2) .

No authentication or peer/StackerDB-specific verification gates `/v2/fees/transaction`; the handler is reachable by any remote HTTP client that can hit the RPC port, with only the generic content-length and JSON well-formedness checks in `try_parse_request` — neither of which bounds the numeric value of `estimated_len`.

### Impact Explanation
On a debug build, this is a remote, single-request DoS: sending one crafted `estimated_len` value near `u64::MAX` panics the thread handling the RPC request (`multiply with overflow`). On a release build, the value wraps and can produce a `minimum_fee` far lower than the byte-length-based floor that the API is meant to guarantee — undermining the "fee floor is a function of the real/claimed transaction length" invariant, though a wallet client would typically also see an absurd `estimated_len` in its own request and is unlikely to be deceived unless it blindly trusts the server's echoed floor. The primary concrete, reproducible issue is the panic path in debug builds and the broken safety invariant (unchecked arithmetic on wire-controlled input) regardless of build profile.

### Likelihood Explanation
Trivial and repeatable: no authentication, no node/chain state precondition, no privileged role — just one crafted JSON POST to `/v2/fees/transaction`, which is the standard RPC surface any remote HTTP client can reach. Cost to the attacker is a single HTTP request.

### Recommendation
Use `estimated_len.saturating_mul(MINIMUM_TX_FEE_RATE_PER_BYTE)` (or `checked_mul` with an explicit error response) in `estimate_tx_fee_from_cost_and_length`, and/or clamp `estimated_len` to a sane maximum (e.g., `MAX_PAYLOAD_LEN` or a configured max tx size) during `try_parse_request` before accepting the client-supplied value.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postfeerate.rs` (or equivalent) that constructs a `FeeRateEstimateRequestBody { estimated_len: Some(u64::MAX / 2), transaction_payload: "00".into() }`, drives it through `RPCPostFeeRateRequestHandler::try_parse_request` and `estimate_tx_fee_from_cost_and_length` with `MINIMUM_TX_FEE_RATE_PER_BYTE > 1`, and asserts that the call either panics with `attempt to multiply with overflow` (debug) or returns an `RPCFeeEstimate.fee` far smaller than `estimated_len as u128 * MINIMUM_TX_FEE_RATE_PER_BYTE as u128` truncated to `u64` (release wraparound), demonstrating the missing overflow guard at `stackslib/src/net/api/postfeerate.rs:112`.
