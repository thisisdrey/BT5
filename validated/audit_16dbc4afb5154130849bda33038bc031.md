### Title
Missing check for the zero/unspendable address in `AccountPermissionUpdateActuator` allows a signer to permanently brick their own account permissions - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any account owner replace their `Owner`/`Witness`/`Active` permissions via an `AccountPermissionUpdateContract`. The only address-format check performed on the keys inside a permission is `DecodeUtil.addressValid()`, which only validates length and the network prefix byte — it never rejects the all-zero (burn) address or any other address whose private key nobody controls. This mirrors the reported `Governable.transferGovernor()` bug class: a state-transition function that changes control of an account/contract with no protection against setting an unusable/zero address, permanently locking out the legitimate owner.

### Finding Description
`checkPermission()` validates each `Key` in a submitted `Permission` only with: [1](#0-0) 

`DecodeUtil.addressValid()` itself only checks the byte length (21 bytes) and that the first byte equals the network address prefix; it performs no check that the remaining bytes are non-zero or otherwise correspond to a key someone actually controls: [2](#0-1) 

As a result, an `Owner` permission can be set with a single key equal to the zero address (`0x41` followed by 20 zero bytes) and sufficient weight/threshold, and `validate()` accepts it because it only checks permission structure (key count, weight sum vs threshold, address format), never that the resulting owner permission is actually satisfiable by a key the caller (or anyone) holds: [3](#0-2) 

`execute()` then persists this permission set unconditionally via `AccountCapsule.updatePermissions()`: [4](#0-3) [5](#0-4) 

Once the `Owner` permission's sole key is the zero/unspendable address, no future transaction (including another `AccountPermissionUpdateContract` needed to fix the permission) can ever be authorized for that account, because `Owner`-permission-gated actions require a signature matching a key that satisfies the threshold — and nobody holds the private key for the zero address. This is directly analogous to the reported `Governable.transferGovernor()` issue: a permission/ownership-transfer path with no zero-address guard that leads to permanent loss of account control.

### Impact Explanation
Any TRX, TRC10, or TRC20 balances and resources (bandwidth/energy, delegated resources, votes) tied to the affected account become permanently frozen/unrecoverable, since the `Owner` permission — needed to authorize further `AccountPermissionUpdateContract` transactions to fix itself — can never be satisfied again. This matches the "permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Reaching this requires only a single signed `AccountPermissionUpdateContract` transaction from the account owner (multisig must first be enabled via `dynamicStore.getAllowMultiSign() == 1`, which is a chain parameter, not owner-controlled, but is already enabled on mainnet). No special privilege beyond normal account ownership and TRX balance for the fee is needed. It can happen accidentally (client tooling constructing a malformed permission) exactly the same way the reported `Governable` bug can happen accidentally, since there is no on-chain safeguard preventing it.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()` (or in `DecodeUtil.addressValid()`/a dedicated check), explicitly reject keys whose address is the all-zero address (or any other well-known unspendable/burn address) when constructing `Owner`/`Witness`/`Active` permissions, at least for the `Owner` permission where losing control is unrecoverable.

### Proof of Concept
1. Attacker/owner controls account `A` with balance and default `Owner` permission.
2. Owner signs and broadcasts an `AccountPermissionUpdateContract` with `owner_address = A`, and `owner` permission set to a single `Key { address: 0x41000000000000000000000000000000000000 00 (zero address with valid prefix), weight: 1 }`, `threshold: 1`.
3. `AccountPermissionUpdateActuator.validate()` passes because `DecodeUtil.addressValid()` only checks length/prefix, and `checkPermission()` finds key count=1>0, weight(1) >= threshold(1), address "valid".
4. `execute()` commits the new `Owner` permission via `AccountCapsule.updatePermissions()`.
5. From this point on, account `A`'s `Owner`-permission-gated operations (including submitting another `AccountPermissionUpdateContract` to restore a usable permission) can never be signed, since nobody holds the private key for the zero address — permanently freezing any funds/resources held by `A`.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
