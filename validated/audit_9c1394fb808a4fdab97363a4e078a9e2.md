### Title
Denial of Service via unbounded scientific-notation exponent in JSON numeric fields reaching `BigDecimal.longValueExact()` - (File: `framework/src/main/java/org/tron/core/services/http/Util.java`)

### Summary
Several HTTP transaction-creation endpoints (`DeployContractServlet`, `TriggerSmartContractServlet`, and others that call `Util.getJsonLongValue`) read numeric fields such as `call_value`, `call_token_value`, `token_id`, and `fee_limit` from the raw request JSON via `JSONObject.getBigDecimal()` and then call `BigDecimal.longValueExact()` on the result. Because the JSON parser (`org.tron.json.JSON`, backed by Jackson with `USE_BIG_DECIMAL_FOR_FLOATS`) accepts arbitrary scientific-notation numbers (e.g. `1E2147483647`), an attacker can submit a short JSON literal encoding an astronomically large exponent. This is the same bug class as CVE-2014-9490 (`numtok` in raven-ruby's `okjson.rb`): a small, well-formed scientific number token expands into an enormous magnitude during later numeric normalization, causing catastrophic CPU/memory consumption.

### Finding Description
`Util.getJsonLongValue` retrieves a `BigDecimal` from parsed JSON and immediately calls `longValueExact()`: [1](#0-0) 

The value comes from `JSONObject.getBigDecimal`, which for JSON numeric tokens returns the already-decoded `BigDecimal` node directly (no length/magnitude re-check, since the length guard in `TypeUtils.castToBigDecimal` only applies to the `String`-typed branch, not the `instanceof BigDecimal` branch): [2](#0-1) [3](#0-2) 

The JSON reader accepts standard JSON number syntax with an `e`/`E` exponent and no cap on the exponent's magnitude: [4](#0-3) 

A number such as `1E2147483647` is only a handful of characters, so it passes the `strVal.length() > 65535` guard trivially and is parsed cheaply into a `BigDecimal` with `unscaledValue=1` and `scale=-2147483647`. The expensive step happens downstream: `BigDecimal.longValueExact()` (JDK, `java.math.BigDecimal`) must materialize the exact integer value, which for a negative scale requires computing `unscaledValue.multiply(BigInteger.TEN.pow(-scale))` — i.e. computing `10^2147483647`, an operation that allocates gigabytes of memory / consumes enormous CPU before it can even report an "overflow" exception.

This is reached directly from unauthenticated HTTP endpoints, e.g. `DeployContractServlet` (`call_token_value`, `token_id`, `call_value`, `consume_user_resource_percent`, `origin_energy_limit`, `fee_limit`) and `TriggerSmartContractServlet` (`call_token_value`, `token_id`, `call_value`, `fee_limit`): [5](#0-4) [6](#0-5) 

### Impact Explanation
A single unauthenticated HTTP POST containing a short, well-formed JSON body can force the node to attempt a multi-gigabyte `BigInteger` computation, exhausting heap memory (leading to `OutOfMemoryError`) or pegging a CPU core for an extended period. Because `/wallet/deploycontract`, `/wallet/triggersmartcontract`, and similar endpoints are part of the public wallet HTTP API, this allows any anonymous API client to degrade or crash a full node / witness node, impacting availability of the JSON-RPC/HTTP query surface and potentially the node process itself.

### Likelihood Explanation
The attack requires no signature, no funds, and no special permissions — just a POST request with a crafted numeric literal in a JSON field consumed by `Util.getJsonLongValue`. The request is trivial to construct and can be repeated/parallelized to amplify impact.

### Recommendation
- In `TypeUtils.castToBigDecimal`, reject or clamp `BigDecimal` values whose `scale()` (positive or negative) exceeds a small bound (e.g. matching the existing `intValue`/`longValue` helpers' `-100..100` sanity window) before any exact-value conversion is attempted.
- In `Util.getJsonLongValue`, validate `bigDecimal.precision()`/`scale()` bounds before calling `longValueExact()`, or wrap the JSON number parsing in Jackson with a `StreamReadConstraints` limit on numeric magnitude (e.g. `maxNumberLength`).
- Apply the same safeguard to `JSONObject.get`/`convertNode` for `isBigDecimal()`/`isBigInteger()` nodes so unauthenticated large-exponent literals cannot reach `BigDecimal`/`BigInteger` arithmetic anywhere in the HTTP JSON path.

### Proof of Concept
```
POST /wallet/triggersmartcontract HTTP/1.1
Content-Type: application/json

{
  "owner_address": "<hex address>",
  "contract_address": "<hex address>",
  "call_value": 1E2147483647,
  "fee_limit": 1000000
}
```
Processing reaches `Util.getJsonLongValue(jsonObject, "call_value")` → `JSONObject.getBigDecimal` → `BigDecimal.longValueExact()`, triggering the expensive `10^2147483647` computation and exhausting node resources.

```java
  static BigDecimal castToBigDecimal(Object value) {
    if (value == null) {
      return null;
    }

    if (value instanceof Float) {
      if (Float.isNaN((Float) value) || Float.isInfinite((Float) value)) {
        return null;
      }
    } else if (value instanceof Double) {
      if (Double.isNaN((Double) value) || Double.isInfinite((Double) value)) {
        return null;
      }
    } else if (value instanceof BigDecimal) {
      return (BigDecimal) value;
    } else if (value instanceof BigInteger) {
      return new BigDecimal((BigInteger) value);
    }

    String strVal = value.toString();

    if (strVal.isEmpty() || "null".equalsIgnoreCase(strVal)) {
      return null;
    }

    if (strVal.length() > 65535) {
      throw new JSONException("decimal overflow");
    }

    if (strVal.indexOf(',') != -1) {
      strVal = strVal.replaceAll(",", "");
    }

    return new BigDecimal(strVal);
  }
```
