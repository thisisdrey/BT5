### Title
Sandwich attack on `ExchangeWithdrawContract` due to missing slippage protection — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
The TRC10 Bancor-style `Exchange` (a two-token liquidity pool) lets any account swap between the pool's two tokens via `ExchangeTransactionContract`, while only the pool creator can add/remove liquidity via `ExchangeInjectContract`/`ExchangeWithdrawContract`. Withdrawals compute the paired ("another") token amount purely from the pool's *current* balance ratio at execution time, with no way for the withdrawer to bound the outcome, unlike swaps which carry an explicit minimum-output (`expected`) field. This mirrors the PSM3 report's root cause — asset accounting driven by a manipulable shared pool balance with no floor/ceiling on the withdrawer's side — allowing any unprivileged broadcaster to sandwich a withdrawal and force it to execute against an adversarial ratio.

### Finding Description
`ExchangeWithdrawActuator.execute` computes `anotherTokenQuant` directly from `firstTokenBalance`/`secondTokenBalance` read from the `ExchangeCapsule` at the moment the withdraw transaction executes: [1](#0-0) 

`ExchangeWithdrawContract` (per the protocol definition) carries only `owner_address`, `exchange_id`, `token_id`, and `quant` — no minimum/maximum bound for the computed counter-asset amount, unlike `ExchangeTransactionContract`, which explicitly includes an `expected` field used to enforce a minimum return and reject the transaction otherwise: [2](#0-1) 

Because `ExchangeTransactionContract` swaps are permissionless, fee-free (`calcFee()` returns 0), and freely composable within the same block, an attacker can:
1. Front-run a pending `ExchangeWithdrawContract` with a large `ExchangeTransactionContract` swap that skews the pool's `firstTokenBalance`/`secondTokenBalance` ratio.
2. Let the victim's withdraw execute, receiving a far smaller (or larger, at the victim's expense) `anotherTokenQuant` than the pre-attack ratio implied.
3. Back-run with a reverse swap to restore the ratio and capture the difference, at zero cost beyond bandwidth/energy.

This is the direct analog to the report's "swap out, sandwich withdrawal, swap back in" bug class in PSM3: the shared pool balance is deliberately manipulated around a withdrawal to disadvantage the party executing it, and there is no check-3-asset/slippage safeguard on the withdrawal path even though one exists for ordinary swaps.

### Impact Explanation
A malicious, unprivileged transaction broadcaster can extract value from any exchange creator's `ExchangeWithdrawContract` call by sandwiching it, since the withdrawal has no minimum-received protection. This constitutes unauthorized value extraction/theft from the withdrawing account's expected proportional share of the pool, directly analogous to the acknowledged low/medium PSM3 finding but exploitable for concrete fund loss here because there is no slippage guard at all on withdraw (whereas the swap path deliberately has one).

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract` transactions against a target `exchange_id` at any time; `calcFee()` for exchange transactions is 0, so the cost is limited to bandwidth/energy. Front-running/back-running ordering within a block (or across adjacent blocks) is achievable by any broadcaster monitoring the mempool for withdraw transactions, requiring no special privileges — consistent with the "single signed transaction" reachability constraint.

### Recommendation
Add an optional minimum/maximum bound field to `ExchangeWithdrawContract` (analogous to `expected` in `ExchangeTransactionContract`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()`, rejecting withdrawals whose computed `anotherTokenQuant` falls outside the withdrawer-specified tolerance.

### Proof of Concept
1. Creator A owns exchange pool `firstToken`/`secondToken` with balances `F0`/`S0`.
2. Attacker observes A's pending `ExchangeWithdrawContract(tokenID=firstToken, quant=Q)` in the mempool.
3. Attacker submits `ExchangeTransactionContract` swapping a large amount of `secondToken` into `firstToken`, shifting the ratio so `S0/F0` drops sharply.
4. A's withdraw executes: `anotherTokenQuant = secondTokenBalance * Q / firstTokenBalance` per [3](#0-2)  now yields far less `secondToken` than expected under the pre-attack ratio.
5. Attacker submits a reverse `ExchangeTransactionContract` swap to restore the ratio, pocketing the `secondToken` difference extracted from A's withdrawal.
