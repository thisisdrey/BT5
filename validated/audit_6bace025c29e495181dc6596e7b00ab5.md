### Title
Floating-point unit conversion in resource-delegation validation can miscompute available FreezeV2 balance - (File: actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java)

### Summary
`DelegateResourceActuator.validate()` converts an account's bandwidth/energy *usage* (measured in bytes/energy units) back into TRX-denominated "weight" using an inline `double` multiplication/division, then subtracts owner-frozen and delegated balances to determine how much FreezeV2 balance is still available to delegate. This mirrors exactly the "overcomplicated unit conversion" pattern flagged in the external report (multiple `mul`/`div` steps mixed together without a single well-defined conversion helper), and it is inconsistent with the hardened, `BigDecimal`/strict-math conversion path (`allowHardenResourceCalculation`) that the codebase already introduced elsewhere for the same class of conversion.

Notably, the codebase already recognizes that this style of `double`-based ratio conversion (`totalWeight / totalLimit`) is numerically fragile: `BandwidthProcessor`/`EnergyProcessor` gained a parallel, hardened `BigDecimal` implementation gated by `allowHardenResourceCalculation`, validated by dedicated regression tests comparing old (double) vs. new (hardened) results: [6](#0-5) 

However, `DelegateResourceActuator.validate()` (and the identical logic in `Wallet.java`) never routes through this hardened path — it performs the `accountNetUsage * TRX_PRECISION * (weight/limit)` conversion directly with `double`, then truncates to `long` via a cast. Mixing multiplication/division order (`*`, then `/` inside a cast to `double`, then `(long)` truncation) is precisely the "confusing, multi-step unit conversion" pattern called out in the report, and it has already been shown (by the project's own hardening work) to diverge from a mathematically-precise calculation for the same class of formula.

### Impact Explanation
`getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance` is the sole solvency check that gates how much of an account's frozen V2 balance can be delegated to another account. If floating point rounding causes `v2NetUsage` to be computed lower than the mathematically correct value, an account could pass validation and delegate more resource than is actually backed by its own frozen balance after accounting for its already-consumed bandwidth/energy. This creates an inconsistency between the account's real resource backing and its delegated-out FreezeV2 balance, an "unbacked" resource state: the account continues to be billed usage against a shrunk pool while the delegated share issued to the receiver is not actually fully collateralized. Given the codebase's own precedent, this class of double-based conversion error is treated seriously enough to warrant a dedicated hardened re-implementation elsewhere in the same resource-accounting subsystem.

### Likelihood Explanation
This path is reachable by any account owner submitting a `DelegateResourceContract` transaction (an unprivileged, ordinary user operation) with the `BANDWIDTH` or `ENERGY` resource type once it has consumed some usage. No special privilege is required, and the miscalculation only depends on the ratio of `getTotalNetWeight()/getTotalNetLimit()` (or the energy equivalent) and the account's own usage value, both of which are network-wide, publicly observable quantities that an attacker can pick a moment/usage pattern to maximize rounding deviation.

### Recommendation
Route the usage→weight conversion in `DelegateResourceActuator.validate()` (and the duplicated logic in `Wallet.calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize`) through the same hardened, `BigDecimal`-based conversion already used by `BandwidthProcessor.calculateGlobalNetLimitV2`/`EnergyProcessor.calculateGlobalEnergyLimitV2`, gated consistently by `allowHardenResourceCalculation`/`disableJavaLangMath`, so that resource-delegation solvency checks use the same precise arithmetic as the rest of the resource-accounting subsystem instead of an inline `double` multiply/divide/cast chain.

### Proof of Concept
Exact reproduction requires selecting `getTotalNetWeight()`/`getTotalNetLimit()` and `accountNetUsage` values where the `double` multiplication in [1](#0-0) 
rounds down relative to an exact rational computation (analogous to the divergence already demonstrated between old/new implementations in `CalculateGlobalLimitHardenTest.testGlobalEnergyLimitV2BelowTrxPrecisionMatchesDouble`, which shows a concrete case where the double-based and BigDecimal-based results differ near `TRX_PRECISION` boundaries). I was not able to execute a live transaction against a running node to confirm the end-to-end delegation-then-fund-freeze effect within this analysis; a Devin session with test/mainnet-fork access would be needed to construct a concrete numeric example that passes `validate()` while leaving the owner's FreezeV2 balance under-collateralized.
