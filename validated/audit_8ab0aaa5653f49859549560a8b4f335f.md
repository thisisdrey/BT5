### Title
Missing zero-address (burn-address) check in fund-transfer actuators allows irrecoverable loss of TRX/TRC10 tokens - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`)

### Summary
`TransferActuator`, `TransferAssetActuator`, and other value-moving actuators only validate a destination address's *format* (20-byte length + `0x41` prefix) via `DecodeUtil.addressValid`, but never check that the address is not the reserved all-zero value. A transaction broadcaster can therefore send TRX or TRC10 tokens to `0x41` followed by 20 zero bytes — an address for which no private key is realistically discoverable — permanently and irrecoverably losing the transferred value, exactly the class of bug described in the referenced report ("missing zero-address check ... setter functions/constructors" leading to loss of funds via an unchecked address parameter).

### Finding Description
`DecodeUtil.addressValid` only checks:
1. the address is non-empty,
2. its length equals `ADDRESS_SIZE / 2` (21 bytes),
3. the first byte equals `addressPreFixByte` (`0x41` on mainnet). [1](#0-0) 

It never rejects an address whose remaining 20 bytes are all zero. `TransferActuator.validate()` relies exclusively on this check for both `ownerAddress` and `toAddress`: [2](#0-1) 

In `execute()`, if the `toAddress` account does not already exist, a brand-new account is silently created at that address and credited with the transferred balance: [3](#0-2) 

The same pattern (address-format-only validation, no zero-address rejection) exists in `TransferAssetActuator.validate()` for TRC10 asset transfers: [4](#0-3) 

This mirrors the reported bug class precisely: address parameters that are format-checked but not checked against the zero/null value, allowing value to be sent to an address nobody can control.

### Impact Explanation
Any signed `TransferContract` or `TransferAssetContract` transaction naming the zero address (`0x41` + 20 zero bytes) as `toAddress` passes validation. Because no private key can practically be derived to control that specific point on the curve, TRX or TRC10 tokens sent there become permanently unspendable — a real, concrete "permanent freezing/loss of funds" outcome reachable by a single unprivileged, signed transaction, satisfying the audit acceptance criteria.

### Likelihood Explanation
This is trivially reachable: any wallet, dApp, or user constructing a transfer transaction (accidentally via a bug, malformed input sanitization, or a malicious front-end/integration) can set `toAddress` to the zero-value address. No special privilege, contract deployment, or node compromise is required — only a normally signed and broadcast transaction.

### Recommendation
Add an explicit zero-address rejection alongside the existing `DecodeUtil.addressValid` calls in `TransferActuator.validate()`, `TransferAssetActuator.validate()`, and other actuators that move value or resources to a caller-supplied address (e.g., `DelegateResourceActuator`, `UnDelegateResourceActuator`, `ParticipateAssetIssueActuator`), for example by checking that the address bytes after the prefix are not all zero before proceeding.

### Proof of Concept
1. Construct a `TransferContract` with `ownerAddress` = attacker's funded account and `toAddress` = `0x41` followed by 20 zero bytes.
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes both `DecodeUtil.addressValid(ownerAddress)` and `DecodeUtil.addressValid(toAddress)` checks (lines 104-109) since the zero-filled address satisfies length and prefix requirements.
4. `TransferActuator.execute()` creates a new account at the zero address and credits it with `amount`, permanently removing those funds from circulation since no key controls that specific address value.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
