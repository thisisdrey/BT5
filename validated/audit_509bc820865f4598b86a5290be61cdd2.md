## Analysis Result

### Title
Block/transaction-fee rewards paid to a Super Representative with zero votes are permanently locked and unclaimable - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
The JPEG'd `LPFarming.sol` bug locks reward tokens when no LP provider is present at `epoch.startBlock`, because the reward accrued for that unattended period can never be attributed to a share-holder and there is no sweep function to recover it. java-tron's DPoS voting-reward system (`MortgageService`, `DelegationStore`, `MaintenanceManager`) has the same structural flaw: block/transaction-fee rewards are credited to a witness's per-cycle reward bucket regardless of whether any voter has a non-zero vote share recorded for that witness in that cycle. When the recorded vote total for a witness/cycle is `0`, both the legacy and the "VI" (new) reward-computation paths deliberately skip distributing that reward to anyone, and no function exists anywhere in `MortgageService` (or elsewhere) to reclaim it. The reward amount therefore stays forever in the corresponding `DelegationStore` bucket, unreachable by any account.

### Finding Description
Every time a witness produces a block or collects transaction fees, `MortgageService.payReward()` unconditionally stores the net (post-brokerage) reward under the current cycle for that witness address: [1](#0-0) 

This reward is only ever redeemable through vote-proportional computation. In the legacy algorithm, `computeReward(cycle, votes)` explicitly discards the reward whenever the witness's recorded total vote for the cycle is `0` (or `REMARK`): [2](#0-1) 

In the new "VI" algorithm, `accumulateWitnessVi`/`DelegationStore.accumulateWitnessVi` likewise skips accumulating the delta-VI (which is what lets voters later withdraw a share of the reward) whenever `voteCount == 0` for that cycle, simply "forwarding" the previous VI value and dropping the reward from ever being distributable: [3](#0-2) 

The per-cycle vote snapshot that drives this check is captured for *every* witness at each maintenance cycle, independent of whether that witness actually has any votes: [4](#0-3) [5](#0-4) 

A witness can legitimately end up with `voteCount == 0` for a cycle while still being part of the elected/active set (e.g., few witnesses exist on the network relative to the number of SR seats, or a witness's entire voter base withdraws/moves votes exactly at the maintenance boundary before the next cycle's snapshot). Registering as a witness is a normal, unprivileged, broadcastable transaction (`WitnessCreateContract`), and voting/unvoting is likewise fully user-controlled (`VoteWitnessContract`, `WithdrawBalanceContract`/`UnfreezeBalance`). Once such a zero-vote cycle occurs, any block reward or transaction-fee reward paid to that witness for that cycle (via `payBlockReward`/`payTransactionFeeReward`) is stored in `DelegationStore` but can never be attributed to any voter, since both reward-computation paths explicitly bypass zero-vote cycles. `MortgageService` provides `withdrawReward`/`queryReward` for voters, and `WithdrawRewardProcessor`/`VoteRewardUtil` for the TVM voting precompile path, but there is no method anywhere (owner-only or otherwise) that lets anyone reclaim a witness's unattributed per-cycle reward once it has been orphaned this way.

### Impact Explanation
This results in permanent freezing/loss of TRX funds: the network mints/allocates block and transaction-fee rewards to the witness's cycle bucket, but that value is unrecoverable by the witness, its (nonexistent) voters, or the protocol itself. Over time, and especially on networks with a small witness/voter set (sidechains, private/test networks, or early mainnet-like conditions), this can accumulate into a meaningful amount of permanently stuck value, matching the "permanent freezing of funds" impact class.

### Likelihood Explanation
Triggering a zero-recorded-vote cycle for an elected witness requires no privileged access — it only needs ordinary `WitnessCreateContract`, `VoteWitnessContract`, and unvoting/unfreezing transactions, all of which any account can broadcast. The likelihood is highest on chains where the number of registered witnesses is at or below the number of SR/witness seats (so a zero-vote candidate is still elected), but the underlying accounting flaw exists in the core reward-computation code regardless of network size.

### Recommendation
Add an explicit reconciliation/sweep path: when `computeReward`/`accumulateWitnessVi` detects a witness/cycle whose recorded vote total is `0` while a nonzero reward was recorded for that cycle (`delegationStore.getReward(cycle, address) > 0`), the funds should either be rolled forward into a subsequent cycle's distributable pool for that witness, redirected to a global fund, or made reclaimable through a dedicated function, rather than being silently discarded from all distribution algorithms.

### Proof of Concept
1. On a network where witness count ≤ available SR/witness seats (or after all voters for witness W unvote right before a maintenance boundary), have witness `W` become part of the active/standby witness set with `voteCount == 0` for cycle `N` (via `MaintenanceManager.doMaintenance` -> `delegationStore.setWitnessVote(N, W, 0)`).
2. `W` produces a block or collects transaction fees during cycle `N`; `MortgageService.payReward` calls `delegationStore.addReward(N, W, value)`, crediting `value` to `W`'s cycle-`N` bucket.
3. At the next maintenance, `accumulateWitnessVi`/`computeReward` see `voteCount == 0` for cycle `N` and skip distributing `value` to any voter (old algorithm `continue`s; new algorithm forwards `preVi` unchanged).
4. No account can ever call a function that reclaims `value`; it remains permanently inert in `DelegationStore`, unspendable and unbacked by any withdrawable balance, matching the reported bug class of reward funds becoming stuck when no participant is present during the relevant accrual window.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }
```
