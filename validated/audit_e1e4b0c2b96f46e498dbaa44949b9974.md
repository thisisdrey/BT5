### Title
`mime/multipart.Writer.CreatePart` writes header fields to the multipart body without CRLF validation, enabling header/part injection - (File: `src/mime/multipart/writer.go`)

### Summary
`Writer.CreatePart` serializes caller-supplied `textproto.MIMEHeader` keys and values directly into the multipart body via `fmt.Fprintf(&b, "%s: %s\r\n", k, v)` with no check for embedded `\r\n` sequences, unlike `net/http`'s header writer which validates every byte through `validHeaderFieldByte`/`validHeaderValueByte`. This is the same bug class as the undici report: an untrusted string is dropped straight into a header sink that bypasses the codebase's own validation path used elsewhere.

### Finding Description
Attacker-controlled input (e.g., an uploaded file's declared MIME type or filename, or any value an application derives from user input and stores as a header value) flows into `textproto.MIMEHeader{"Content-Type": {attackerValue}}`, which is passed to `Writer.CreatePart` [1](#0-0) . Inside `CreatePart`, the loop `for _, k := range slices.Sorted(maps.Keys(header)) { for _, v := range header[k] { fmt.Fprintf(&b, "%s: %s\r\n", k, v) } }` writes `k` and `v` verbatim into the outgoing buffer with no call to any CRLF/control-character validator [2](#0-1) . If `v` (or `k`) contains `\r\n`, the attacker can terminate the current header line early, inject arbitrary additional header lines, or even inject a premature blank line (`\r\n\r\n`) that fabricates a new part boundary/body inside the multipart stream that the receiving multipart parser will interpret differently than the sender intended.

By contrast, the convenience wrappers `CreateFormField`/`CreateFormFile`/`FileContentDisposition` route field/file names through `escapeQuotes`, which percent-encodes `\r`/`\n` before they reach `CreatePart` [3](#0-2) . However, any caller that builds a `textproto.MIMEHeader` directly (a very common pattern for setting a custom `Content-Type` on a part, e.g. `h.Set("Content-Type", detectedType)`) and calls `CreatePart` bypasses that escaping entirely, exactly mirroring the undici flaw where a `content-type`-like value reached the header sink without going through the codebase's own validation function (`isValidHeaderValue` in undici, `validHeaderFieldByte`/`validHeaderValueByte` in this Go codebase's `net/textproto` package, which `mime/multipart` never calls) [4](#0-3) .

### Impact Explanation
An application that builds multipart requests/bodies with an attacker-influenced header value (most plausibly a `Content-Type` derived from an uploaded file's sniffed/declared type, or any other field placed in a custom header) can have that value used to smuggle extra header lines or an entirely new synthetic part boundary into the resulting multipart payload. Depending on how the receiving service parses the multipart body, this can enable request/part smuggling, field spoofing (e.g., overriding `Content-Disposition` for a different form field name than intended), or bypassing size/type checks enforced by inspecting only the first declared header. This matches CWE-93 (CRLF Injection) and is a **PUBLIC** track candidate for the Go project: it's a latent injection primitive in a widely used standard-library API, though actual exploitability is entirely dependent on how a downstream, unspecified multipart parser interprets the injected bytes (unlike `net/http`, which the Go project already hardened against exactly this class in its own header-writing paths, e.g. `TestServerValidatesHeaders`/`TestHeaderWrite`/trailer validation added for issue #78775) [5](#0-4) [6](#0-5) .

### Likelihood Explanation
Likelihood is moderate: it requires an application to (a) accept untrusted input, (b) place that input into a `textproto.MIMEHeader` value (bypassing the safe `escapeQuotes`-protected convenience methods) rather than using `CreateFormField`/`CreateFormFile`, and (c) call `CreatePart` directly. This is a realistic but non-default usage pattern — for instance, a file-upload proxy that forwards an uploaded file's client-declared `Content-Type` into a new multipart body sent to a backend service.

### Recommendation
Add the same header-name/value validation used by `net/http` (`validHeaderFieldByte` for names, `validHeaderValueByte`/CRLF rejection for values, as in `net/textproto`) to `Writer.CreatePart` before writing `k`/`v`, returning an error (or stripping/escaping) if either contains `\r`, `\n`, or other control characters — analogous to how `net/http`'s `Header.write`/`writeSubset` and the recent Trailer validation (`transfer.go`'s `validateHeaders`, issue #78775) closed this exact defect class in HTTP headers.

### Proof of Concept

```go
package multipart_test

import (
	"bytes"
	"net/textproto"
	"strings"
	"testing"

	"mime/multipart"
)

func TestCreatePartCRLFInjection(t *testing.T) {
	var buf bytes.Buffer
	w := multipart.NewWriter(&buf)
	w.SetBoundary("BOUNDARY")

	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition", `form-data; name="file"`)
	// Attacker-controlled MIME type containing CRLF, analogous to
	// undici's body.type sink.
	h.Set("Content-Type", "text/plain\r\nX-Injected: evil")

	part, err := w.CreatePart(h)
	if err != nil {
		t.Fatal(err)
	}
	part.Write([]byte("data"))
	w.Close()

	out := buf.String()
	// Expected (secure) behavior: injected header must NOT appear as a
	// separate raw header line in the output.
	if strings.Contains(out, "X-Injected: evil\r\n") {
		t.Fatalf("CRLF injection succeeded, raw output:\n%q", out)
	}
}
```
Expected assertion: the test currently fails (the injected `X-Injected: evil` line appears verbatim in the multipart body), demonstrating that `CreatePart` performs no CRLF validation on header values before writing them to the wire format.

```go
func (w *Writer) CreatePart(header textproto.MIMEHeader) (io.Writer, error) {
	if w.lastpart != nil {
		if err := w.lastpart.close(); err != nil {
			return nil, err
		}
	}
	var b bytes.Buffer
	if w.lastpart != nil {
		fmt.Fprintf(&b, "\r\n--%s\r\n", w.boundary)
	} else {
		fmt.Fprintf(&b, "--%s\r\n", w.boundary)
	}

	for _, k := range slices.Sorted(maps.Keys(header)) {
		for _, v := range header[k] {
			fmt.Fprintf(&b, "%s: %s\r\n", k, v)
		}
	}
	fmt.Fprintf(&b, "\r\n")
	_, err := io.Copy(w.w, &b)
	if err != nil {
		return nil, err
	}
	p := &part{
		mw: w,
	}
	w.lastpart = p
	return p, nil
}
```

```go
var quoteEscaper = strings.NewReplacer("\\", "\\\\", `"`, "\\\"", "\r", "%0D", "\n", "%0A")

// escapeQuotes escapes special characters in field parameter values.
//
// For historical reasons, this uses \ escaping for " and \ characters,
// and percent encoding for CR and LF.
//
// The WhatWG specification for form data encoding suggests that we should
// use percent encoding for " (%22), and should not escape \.
// https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#multipart/form-data-encoding-algorithm
//
// Empirically, as of the time this comment was written, it is necessary
// to escape \ characters or else Chrome (and possibly other browsers) will
// interpet the unescaped \ as an escape.
func escapeQuotes(s string) string {
	return quoteEscaper.Replace(s)
}

// CreateFormFile is a convenience wrapper around [Writer.CreatePart]. It creates
// a new form-data header with the provided field name and file name.
func (w *Writer) CreateFormFile(fieldname, filename string) (io.Writer, error) {
	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition", FileContentDisposition(fieldname, filename))
	h.Set("Content-Type", "application/octet-stream")
	return w.CreatePart(h)
}

// CreateFormField calls [Writer.CreatePart] with a header using the
// given field name.
func (w *Writer) CreateFormField(fieldname string) (io.Writer, error) {
	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition",
		fmt.Sprintf(`form-data; name="%s"`, escapeQuotes(fieldname)))
	return w.CreatePart(h)
}

// FileContentDisposition returns the value of a Content-Disposition header
// with the provided field name and file name.
func FileContentDisposition(fieldname, filename string) string {
	return fmt.Sprintf(`form-data; name="%s"; filename="%s"`,
		escapeQuotes(fieldname), escapeQuotes(filename))
}
```

```go
// validHeaderValueByte reports whether c is a valid byte in a header
// field value. RFC 7230 says:
//
//	field-content  = field-vchar [ 1*( SP / HTAB ) field-vchar ]
//	field-vchar    = VCHAR / obs-text
//	obs-text       = %x80-FF
//
// RFC 5234 says:
//
//	HTAB           =  %x09
//	SP             =  %x20
//	VCHAR          =  %x21-7E
func validHeaderValueByte(c byte) bool {
	// mask is a 128-bit bitmap with 1s for allowed bytes,
	// so that the byte c can be tested with a shift and an and.
	// If c >= 128, then 1<<c and 1<<(c-64) will both be zero.
	// Since this is the obs-text range, we invert the mask to
	// create a bitmap with 1s for disallowed bytes.
	const mask = 0 |
		(1<<(0x7f-0x21)-1)<<0x21 | // VCHAR: %x21-7E
		1<<0x20 | // SP: %x20
		1<<0x09 // HTAB: %x09
	return ((uint64(1)<<c)&^(mask&(1<<64-1)) |
		(uint64(1)<<(c-64))&^(mask>>64)) == 0
}
```
