## Analysis

The M‑1 report describes a two‑phase pattern where an **irrevocable state transition happens in phase 1** (marking the withdrawal as finalized in `OptimismPortal`), while the **completion/replay bookkeeping happens in phase 2** (`L1CrossDomainMessenger`'s post-call accounting). If phase 2 fails after phase 1 has already committed irrevocably, the system ends up in a permanently inconsistent state that cannot be corrected.

Gitaly's `UserSquash` RPC has a structurally identical three-phase pattern, and I found a genuine, testable instance of the same bug class.

### Title
Quarantine objects are irrevocably migrated into the main object directory before the transaction's final `Committed` vote succeeds, permanently bypassing quarantine on transaction failure - (File: internal/gitaly/service/operations/squash.go)

### Summary
`Server.userSquash` stages newly created commit objects in a quarantine directory, then performs a three-phase transactional vote (`Preparing` → `Prepared` → `Committed`). Critically, `quarantineDir.Migrate(ctx)` — which irrevocably moves the objects out of quarantine into the repository's real object directory — is executed **between** the `Prepared` and `Committed` votes, not after the `Committed` vote succeeds.

### Finding Description
The intended contract of object quarantine (documented in `doc/object_quarantine.md`) is that objects live in a detached, disposable directory until the operation is confirmed to succeed; if the operation is rejected, the quarantine directory can simply be discarded and the objects vanish without ever polluting the main object store.

In `userSquash`, the sequence is:
1. Vote `Preparing` on the squashed commit ID.
2. Vote `Prepared`.
3. `quarantineDir.Migrate(ctx)` — irreversibly merges objects into the real repository.
4. Vote `Committed`. [1](#0-0) 

If step 4 (`Committed`) fails — e.g. because quorum is lost, a node disconnects, or the vote transaction otherwise errors — the function returns `structerr.NewAborted(...)` to the caller, signalling that the whole RPC failed. However, the objects were already migrated out of quarantine in step 3 and are **not rolled back**. The comment in the code even acknowledges the quarantine's purpose is defeated in this scenario: "we still use a quarantine directory to stage the new objects, vote on them and migrate them into the main directory if quorum was reached so that we don't pollute the object directory with objects we don't want to have in the first place" — yet migration happens before the final confirming vote actually succeeds.

This is confirmed by the RPC's own test suite, which explicitly documents this outcome for the "committing vote failure" case: [2](#0-1) 

The test asserts that even though the client receives an `Aborted` error (i.e., the RPC reports failure), the squashed commit object still exists in the repository afterward (when the write-ahead-log path is not used), because the quarantine migration already happened irreversibly in step 3.

### Impact Explanation
This mirrors the M‑1 bug class: an irrevocable action (`Migrate`, analogous to `OptimismPortal` finalizing) completes before the operation's final confirmation step (`Committed` vote, analogous to `CrossDomainMessenger`'s post-call bookkeeping). When the final step fails, the client is told the operation did not succeed, but the side effects of the irrevocable step persist permanently. Concretely, this is a **quarantine bypass**: unreachable, unreferenced commit/tree/blob objects that were never accepted by the transaction quorum are nonetheless written into the shared object database of the repository, defeating the entire purpose of quarantine (immediate, atomic disposal of rejected objects) and leaving unauthorized/unaccepted content permanently embedded in the repository's object store where it can later be discovered by object ID (e.g. via `cat-file`) even though the containing transaction was reported as aborted.

### Likelihood Explanation
This is triggerable by any ordinary user calling `UserSquash` on a transactional (replicated, Praefect-fronted) Gitaly setup where the final `Committed` vote can fail independently of the `Prepared` vote (e.g. transient node/network issues, a secondary going away between votes, or a deliberately timed disruption by a participant in a multi-node cluster). No privileged access is required — only a normal `UserSquash` RPC call combined with a vote-quorum failure that manifests specifically between `Prepared` and `Committed`, which the test suite shows is a real, reachable condition (`prepared vote succeeds, then Committed vote fails`).

### Recommendation
Move `quarantineDir.Migrate(ctx)` to occur only **after** the `Committed` vote has succeeded, or otherwise ensure the migration is not performed until the transaction is fully and irrevocably confirmed by all voters. If migration must happen before the final vote for performance/design reasons, add compensating logic to purge the migrated objects (or otherwise guarantee unreachability/garbage collection) when the subsequent `Committed` vote fails, so that quarantine's atomicity guarantee is preserved end-to-end.

### Proof of Concept
The existing test `testUserSquashTransactional` (case `"committing vote failure"`) already demonstrates this: it injects a `voteFn` that fails only on the `Committed` phase, then asserts the RPC returns an `Aborted` error to the client while the squashed commit object still exists in the repository (`expectedExists: !testhelper.IsWALEnabled()`), proving that quarantined objects survive an RPC that was reported as failed.
