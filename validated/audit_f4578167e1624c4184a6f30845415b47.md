### Title
Precision truncation in the legacy (default) TRX/TRC10 Exchange bonding-curve math allows rounding-based value extraction from swap pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`java-tron`'s built-in Bancor-style Exchange feature (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) computes swap/issuance amounts using either a legacy floating-point processor or a "hardened" `BigDecimal` processor. The hardened path is gated behind the `allowHardenExchangeCalculation` dynamic property, which is off by default and only turned on via a committee proposal. Any unprivileged account can invoke `ExchangeTransactionContract` against any existing exchange pool at any time, driving execution through the legacy, double-precision `ExchangeProcessor`, whose truncation behavior is the same class of bug described in the DualPools report (a share/rate calculation with precision loss that can be repeatedly exploited to skew balances in the caller's favor).

### Finding Description
`ExchangeCapsule.transaction()` picks the calculation engine per-call: [1](#0-0) 

When `hardenedCalc` is false (the default, since `allowHarden()` reads a dynamic property that defaults off until a proposal enables it): [2](#0-1) 

the legacy `ExchangeProcessor` is used, which performs the Bancor relay-token issuance/redemption using `double` arithmetic and truncates the final result with a raw `(long)` cast (not rounding, not exact), both when converting the sold token into "supply" and back into the bought token: [3](#0-2) 

This is functionally the same bug class as the DualPools exploit: a compounding/rate calculation subject to floating-point/integer truncation that does not enforce an exactness or slippage-consistency check between the value taken from one side of the pool and the value paid out from the other side. In DualPools this arose from truncation in vToken mint/redeem exchange-rate math; here it arises from truncation in the double-based bonding-curve issuance formula used by every default (non-hardened) `ExchangeTransactionContract`. Because `ExchangeProcessor` mutates its `supply` field with `(long) issuedSupply` on every intermediate step, repeated small swaps against the same exchange accumulate truncation-driven drift between the theoretical BigDecimal-exact result (as computed in the hardened path, `SafeExchangeProcessor`) and the double-computed result actually applied to the pool balances: [4](#0-3) 

The only guard against a caller receiving less than expected is `tokenExpected` in `ExchangeTransactionActuator.doValidate()`, which protects the caller from under-payment but does nothing to prevent the caller from executing many small transactions that each round in their favor at the pool's expense: [5](#0-4) 

### Impact Explanation
An attacker who repeatedly calls `ExchangeTransactionContract` (a fully permissionless, broadcastable transaction type reachable by any funded account) against a legacy-mode exchange pool can exploit accumulated floating-point truncation in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` to extract value from the pool disproportionate to what a mathematically exact (BigDecimal) calculation would allow — mirroring how the DualPools attacker exploited compounding truncation in mint/redeem math to drain ~$42k. Because the swap directly moves TRX/TRC10 balances between the caller's account and the pool via `AccountCapsule` asset/balance mutations, this is a concrete theft-of-funds vector, not merely a resource or availability issue.

### Likelihood Explanation
Exploitability requires only standard account permissions and TRX/TRC10 balances — no special role, SR/witness status, or privileged flag is needed. The vulnerable legacy path is the *default* execution path for `ExchangeTransactionContract` since the hardened calculation is opt-in via governance proposal (`allowHardenExchangeCalculation` off by default). The severity of extractable value per transaction is bounded by pool size and float precision, so a real attack would likely require many repeated calls, similar to the multi-step flash-loan sequence used in the DualPools PoC, but the reachable surface (an unauthenticated, permissionless actuator) matches the required threat model.

### Recommendation
Make the hardened `SafeExchangeProcessor` (BigDecimal, `RoundingMode.DOWN`/`HALF_UP`) the unconditional calculation path for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, removing the `allowHardenExchangeCalculation` opt-in gate, or at minimum enable it by default for all new/pre-existing exchanges. Additionally, add invariant checks after each swap (e.g., constant-product/constant-relay-supply verification) to reject any transaction whose truncation would move value out of proportion to the mathematically exact result, closing the exploitable rounding gap identified in `ExchangeProcessor`.

### Proof of Concept
Conceptual reproduction (analogous to the DualPools PoC's repeated truncation exploitation, adapted to java-tron's Exchange feature):
1. Create or locate an `Exchange` pool with `AllowHardenExchangeCalculation` proposal not yet activated (default network state).
2. Repeatedly broadcast small `ExchangeTransactionContract` swaps against the pool, alternating direction, driving `ExchangeCapsule.transaction()` through the legacy `ExchangeProcessor` double-math path shown at [3](#0-2) .
3. Because `(long) issuedSupply` / `(long) exchangeBalance` always truncates and floating-point `Math.pow` introduces additional imprecision, each round-trip swap systematically favors the caller by a small but nonzero amount versus the exact BigDecimal computation used in `SafeExchangeProcessor`.
4. Over many iterations (as demonstrated by the flash-loan-funded repeated calls in the original DualPools PoC), the accumulated truncation drains value from the exchange pool to the attacker's account.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);

        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
