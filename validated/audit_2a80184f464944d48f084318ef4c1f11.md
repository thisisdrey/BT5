# Title
Unbounded exponential purse-key lockout via attacker-triggered dispatch failure in `pallet-scarcity` - (File: `substrate/frame/scarcity/src/extension.rs`)

### Summary
`pallet-scarcity`'s `AsScarcity` transaction extension implements a Coinage-style "mint-and-delay" backoff: any failed dispatch of a purse-key `transfer`/`burn` restores the NFT and applies a temporary lock via `Locked<T>` keyed on the sender (`owner`), exactly analogous to the `dPrime.mintAndDelay` pattern in the external report. Unlike the fixed-length dPrime delay, this backoff is **unbounded and self-compounding**: each failure doubles the lock duration with no ceiling on `retries` and no way to reset except a *successful* dispatch — which the lock itself prevents. An unprivileged attacker who can force even a handful of dispatch failures against a victim's purse key (e.g. by racing the victim's `transfer` destination with a cheap, permissionless `mint`) can drive that purse into a practically permanent lockout, escalating far beyond the "temporary pause" intent that the dPrime fix (bounded, configurable threshold) established as the correct remediation shape.

### Finding Description
`pallet-scarcity` documents its own failure-handling model as intentionally mirroring the delay-after-mint pattern: `AsScarcity` removes the NFT from the sender's purse during `prepare`, and on dispatch failure restores it while imposing a cooldown (`substrate/frame/scarcity/src/lib.rs` lines 71-76):

> "Failed dispatch restores the NFT and temporarily locks the purse key; after the lock expires, the same signed transaction may be submitted again..."

The lock is computed in `AsScarcity::failed_dispatch_lock`: [1](#0-0) 

`retries` is a `u8` that only ever increases (`saturating_add(1)`), and the exponent feeding `2u64.saturating_pow(...)` is capped at `63`, not at a small, safe value — meaning the lock duration is `2^min(retries-1,63) * LockPeriod` seconds. After only ~10 failures the lock is already `512 * LockPeriod`; after 64 it saturates to `2^63 * LockPeriod`, i.e. permanently in the future for any realistic `LockPeriod`.

`Locked<T>` is set on *any* dispatch failure and only cleared on success (`substrate/frame/scarcity/src/extension.rs` lines 283-299): [2](#0-1) 

The lock key is the purse-key `owner`, not the specific destination or call that failed, so it blocks *all* future `transfer`/`burn` authorizations for that account (checked in `validate`): [3](#0-2) 

The dispatch itself can still fail with `AddressOccupied` even though `validate` pre-checks the destination, because the pallet explicitly acknowledges a race window between validation and execution (module doc, "genuine same-block races") and keeps a second check inside `transfer`: [4](#0-3) 

Minting into any *empty* purse key is a fully permissionless, feeless-adjacent operation available to anyone who first calls `create_collection` (open to any signed origin) and `define_item`/`mint`; the pallet's own documentation states destinations give "no consent" and any empty key is a valid mint target (`substrate/frame/scarcity/src/lib.rs` lines 29-35). This gives an attacker a cheap, repeatable primitive to occupy an intended `to` address ahead of a victim's `transfer` dispatch, producing an `AddressOccupied` failure that the extension's `post_dispatch_details` then converts into a growing lock on the *victim's own account* — not the attacker's.

This is the direct structural analog of the dPrime bug class: a security feature meant to bound the blast radius of a rare failure (cross-chain mint / dispatch failure) instead becomes an attacker-triggerable, compounding penalty against an uninvolved victim, because the delay/lock threshold is unbounded and keyed to the victim rather than to the triggering event.

### Impact Explanation
Because `retries` never resets except via a dispatch that requires the account to already be unlocked, a griefer who forces a small number of dispatch failures (a handful of races, each costing only trivial mint fees) can push a victim's `Locked` entry to an effectively infinite `until` timestamp. The affected account is a Scarcity purse key that is fully denied use of `transfer`/`burn` for the remainder of the lock — for large `retries` this is a **permanent lock of the purse key's NFT**, matching the "permanent user-fund ... lock" impact class called out in scope. Unlike ordinary transaction fees or bounded cooldowns, there is no economic ceiling protecting the victim once several failures have compounded.

### Likelihood Explanation
The attacker primitive (permissionless `create_collection` + `mint` into an empty purse) is unprivileged, cheap, and repeatable; no validator, collator, relayer, or governance action is required. The pallet's own module documentation acknowledges the underlying dispatch-time race ("genuine same-block races") as an accepted, reachable condition rather than a theoretical edge case, indicating the failure path is realistically triggerable in normal chain operation, and it is only the *unbounded compounding* of the resulting lock — not the race itself — that turns an expected occasional failure into an indefinite denial of service.

### Recommendation
Cap `retries` (and thus the exponential multiplier) at a small, configurable maximum analogous to the DAMfinance fix that added a configurable threshold to `mintAndDelay`. Concretely: bound `exponent` to a `Config::MaxLockRetries` (or similar) so `until` cannot exceed `MaxLockRetries * base LockPeriod` (or a fixed cap), and/or scope the lock check to the specific failing action rather than blanket-blocking every future authorization for the account. Consider also allowing a privileged or time-based path to clear stale locks independent of a successful dispatch.

### Proof of Concept
1. Victim holds NFT `N` in purse `owner` and submits a signed `AsScarcity`-authorized `transfer(to)` where `to` is currently empty; `validate()` passes.
2. Attacker (any unprivileged account) calls `create_collection` + `define_item` + `mint(..., to, ...)` such that it lands on-chain before the victim's transfer dispatch executes (the pallet's own docs concede this ordering is reachable as a "genuine same-block race").
3. Victim's `transfer` dispatch now hits `ensure!(!NftsByOwner::<T>::contains_key(&to), Error::<T>::AddressOccupied)` (`lib.rs:595`) and fails.
4. `post_dispatch_details` sets `Locked::<T>::insert(&owner, LockInfo { retries: 1, until: now + LockPeriod })`.
5. Attacker repeats steps 1-4 (re-racing each retry attempt) a handful of times; each failure doubles the lock: `until = now + 2^(retries-1) * LockPeriod`.
6. After a modest number of forced failures, `until` becomes astronomically large (`2^63 * LockPeriod` at the cap), permanently blocking the victim's `validate()` check at `extension.rs:220-224` and locking the purse key indefinitely — with no self-service recovery path, since recovery requires a successful dispatch that the lock itself now forever forbids.

	fn failed_dispatch_lock(previous: Option<LockInfo>) -> LockInfo {
		let retries = previous.map(|lock| lock.retries.saturating_add(1)).unwrap_or(1);
		let exponent = retries.saturating_sub(1);
		let multiplier = 2u64.saturating_pow(u32::from(exponent).min(63));
		LockInfo {
			retries,
			until: T::UnixTime::now()
				.as_secs()
				.saturating_add(multiplier.saturating_mul(T::LockPeriod::get())),
		}
	}

	fn post_dispatch_details(
		pre: Self::Pre,
		_info: &DispatchInfoOf<<T as frame_system::Config>::RuntimeCall>,
		_post_info: &PostDispatchInfoOf<<T as frame_system::Config>::RuntimeCall>,
		_len: usize,
		result: &DispatchResult,
	) -> Result<Weight, TransactionValidityError> {
		if let Pre::UsingNft { owner, nft } = pre {
			if result.is_err() {
				NftsByOwner::<T>::insert(&owner, nft);
				Locked::<T>::insert(&owner, Self::failed_dispatch_lock(Locked::<T>::get(&owner)));
			} else {
				Locked::<T>::remove(&owner);
			}
		}
		Ok(Weight::zero())
	}
