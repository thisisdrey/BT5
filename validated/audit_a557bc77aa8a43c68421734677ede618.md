### Title
DoS: Unrecovered goroutine panic while parsing client packfile-negotiation data crashes the whole Gitaly process - ([File: internal/gitaly/service/ssh/upload_pack.go], [File: internal/gitaly/service/smarthttp/upload_pack.go])

### Summary
Both the SSH and Smart-HTTP `upload-pack` handlers spawn a background goroutine that calls `stats.ParsePackfileNegotiation()` on client-supplied pkt-line data concurrently with the main RPC goroutine. Unlike the main RPC goroutine — which is protected by `panichandler.UnaryPanicHandler`/`StreamPanicHandler` — this side goroutine has no panic recovery. A panic there is not converted into a gRPC error; it propagates and crashes the entire `gitaly` process, taking down every other in-flight RPC on the node. This is directly analogous to CVE-2021-31525 (Golang: crash while parsing untrusted HTTP request data outside the framework's normal recovery path), except the untrusted input here is the pkt-line negotiation stream sent by an ordinary `git fetch`/`git clone` client.

### Finding Description
`sshUploadPack` in `internal/gitaly/service/ssh/upload_pack.go` and `runStatsCollector` in `internal/gitaly/service/smarthttp/upload_pack.go` both do: [1](#0-0) [2](#0-1) 

In both cases `stats.ParsePackfileNegotiation(pr, opts...)` is invoked inside a bare `go func() { ... }()` with no `recover()` and no `dontpanic.Go`/`dontpanic.Try` wrapper. The codebase explicitly documents this exact risk class in `STYLE.md` (goroutine panic risk guidance) and demonstrates the correct mitigation elsewhere in `internal/streamcache/cache.go`, where a comment states: *"unlike RPC handlers, which are guarded by a panic catching middleware, an uncaught panic can crash the whole process"* and wraps the call in `recover()`: [3](#0-2) 

The parser (`internal/git/stats/packfile_negotiation.go`) processes attacker-controlled pkt-line content — arbitrary `want`/`have`/`shallow`/`deepen`/`filter`/`command=`/`agent=` lines split on spaces and NUL bytes — as sent by any Git client performing a normal fetch/clone: [4](#0-3) 

Gitaly's global gRPC panic middleware (`panichandler.UnaryPanicHandler`/`StreamPanicHandler`) only wraps the outer RPC handler goroutine, not any child goroutines spawned by it: [5](#0-4) 

Because these stats-parsing goroutines run concurrently and outside that recovery boundary, any panic triggered while parsing crafted negotiation data (e.g. an index/slice bug introduced by a future change, or any currently-unnoticed edge case in the string-splitting logic) is fatal to the whole server rather than being converted into an `Internal` gRPC error for a single request.

### Impact Explanation
A panic inside this unshielded goroutine terminates the entire `gitaly` process. Because a single Gitaly node typically serves many repositories and clients simultaneously, this is a full denial-of-service for the node — every concurrently in-flight RPC (unrelated pushes, fetches, reads) is aborted, and the process must be restarted/supervised back into service. This matches the "DoS of a handler" acceptance criterion, but the blast radius exceeds a single handler because it crashes the whole server, not just the request.

### Likelihood Explanation
Any authenticated (or, depending on repository visibility/config, any) user capable of issuing `git fetch`/`git clone` over SSH or Smart HTTP reaches this code path — it fires on every upload-pack negotiation, not on a rare condition. The remaining question is whether the parser can currently be driven to panic with a specific byte sequence; I could not confirm a concrete panicking input in the parser as currently written (string/byte indexing in `packfile_negotiation.go` appears bounds-checked at a glance), so likelihood of an *existing* trigger is uncertain. The structural weakness — lack of panic isolation for a goroutine that processes fully attacker-controlled protocol bytes — is concrete and verified, and any future or overlooked edge case in this parser (or in `text.ChompBytes`, `strings.Split`, or Bands()/`bandToHuman` band-lookup consistency, which I could not fully verify from the index) becomes an unauthenticated process-wide DoS instead of a per-request error.

### Recommendation
Wrap the `stats.ParsePackfileNegotiation` goroutines in `internal/gitaly/service/ssh/upload_pack.go` and `internal/gitaly/service/smarthttp/upload_pack.go` with `dontpanic.Try`/`dontpanic.Go` (as used in `internal/cgroups/cgroups.go`) or an explicit `recover()` (as done in `internal/streamcache/cache.go`), so a parsing panic is logged/reported to Sentry and degrades to "no stats collected" instead of crashing the process. Additionally, audit all other `go func()` sites in the RPC path that parse client-controlled pkt-line/protocol data (e.g. `stats.ParseReceivePack`, `stats.FetchPack.Parse`, `stats.SendPack.Parse`) for the same missing isolation.

### Proof of Concept
Not verified end-to-end due to index limitations — I was unable to confirm a specific byte sequence that currently panics `stats.ParsePackfileNegotiation`. Conceptually: an attacker performs a normal `git fetch`/`git clone` (SSH: `SSHUploadPackWithSidechannel`, HTTP: `PostUploadPackWithSidechannel`) and sends a crafted negotiation pkt-line stream; if any parsing step in `PackfileNegotiation.Parse` (or a helper it calls) panics on that input, the unrecovered goroutine panic terminates the `gitaly` process, dropping all concurrent RPCs server-wide. I recommend a Devin session with fuzzing/unit-test access to `internal/git/stats/packfile_negotiation.go` to search for an actual panic-triggering input and confirm this end-to-end.

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

// StreamPanicHandler creates a new stream server interceptor that handles panics.
func StreamPanicHandler(logger log.Logger) grpc.StreamServerInterceptor {
	return func(srv interface{}, stream grpc.ServerStream, info *grpc.StreamServerInfo, handler grpc.StreamHandler) (err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(srv, stream)
	}
}
