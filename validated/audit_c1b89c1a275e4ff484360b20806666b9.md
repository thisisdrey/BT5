Audit Report

## Title
Pre-funded pool account lets an attacker DoS/skew first `add_liquidity` in `pallet-asset-conversion` - (File: `substrate/frame/asset-conversion/src/lib.rs`)

## Summary
`do_add_liquidity` derives `reserve1`/`reserve2` directly from the live, unguarded asset balance of the deterministic pool account via `Self::get_balance` [1](#0-0) , rather than from any pallet-tracked reserve state. Because the pool account address is a pure deterministic hash of the asset pair computable before pool creation [2](#0-1) , an unprivileged attacker can pre-fund it with disproportionate dust, skewing the branch decision and `quote()`-derived optimal amounts computed on the legitimate provider's first `add_liquidity` call.

## Finding Description
The reserve-zero check at line 818 (`if reserve1.is_zero() || reserve2.is_zero()`) is meant to detect a genuinely empty pool and let the first liquidity provider set the initial price freely [3](#0-2) . However this check reads raw balances of the pool account rather than checking LP-token `total_supply` (which the code correctly uses later, at line 858/861, to decide whether to mint via `calc_lp_amount_for_zero_supply`) [4](#0-3) . `do_create_pool` only touches the pool account for `asset1`/`asset2` to allow it to hold balances — it never resets or rejects any pre-existing balance there [5](#0-4) . Consequently, an attacker who transfers a small, disproportionate amount of `asset1` and/or `asset2` to the precomputed pool account before the legitimate first `add_liquidity` call forces the code into the "existing pool" branch, computing `amount2_optimal`/`amount1_optimal` via `Self::quote` skewed to the attacker's donated ratio, even though `PoolAssets::total_issuance(lp_token)` is still zero [6](#0-5) . This can cause the legitimate provider's call to revert with `AssetTwoDepositDidNotMeetMinimum`, `OptimalAmountLessThanDesired`, or `AssetOneDepositDidNotMeetMinimum` depending on slippage bounds.

## Impact Explanation
This is a permissionless griefing/DoS vector against pool bootstrapping in `pallet-asset-conversion`, deployed on Asset Hub and other system parachains for token swaps. It degrades the intended behavior of a public dispatchable (blocking or skewing legitimate first-liquidity provisioning) without requiring any privileged role, aligning with "runtime bugs that compromise intended behavior" under the impact gate. It does not result in fund theft or duplicate settlement, and its blast radius is limited to newly created, not-yet-funded pools (`total_supply == 0`), consistent with a Medium-severity classification.

## Likelihood Explanation
The attack requires only an ordinary, permissionless asset transfer to a deterministically computable account address — no special privileges, no relayer/validator compromise, and no front-running dependency since the donation can be made before the pool even exists or before the legitimate `add_liquidity` call. It is cheap (dust-level amounts) and repeatable across any asset pair, though it only affects pools that have not yet received genuine liquidity.

## Recommendation
Gate the "first liquidity" branch on LP-token `total_supply == 0` rather than on raw `reserve1.is_zero() || reserve2.is_zero()`, since `total_supply` is already used later in the function for minting decisions and is not attacker-influenceable via direct asset donation. When `total_supply == 0`, either ignore pre-existing pool-account balances when computing quoting decisions, or sweep/credit any pre-existing dust to the first minter so it cannot skew the reserve ratio used for `quote()`.

## Proof of Concept
1. Attacker computes the pool account for `(asset1, asset2)` using `AccountIdConverter`/`AccountIdConverterNoSeed` [7](#0-6)  before or after `create_pool`.
2. Attacker transfers a small, disproportionate amount of `asset1` (or `asset2`) directly to that address via `Assets::transfer`.
3. Legitimate user calls `create_pool` (if not already done) and then `add_liquidity` with a fair market ratio and tight `amount1_min`/`amount2_min`.
4. Inside `do_add_liquidity`, `reserve1`/`reserve2` reflect the attacker's donation, taking the `else` branch at line 821, computing a skewed `amount2_optimal`/`amount1_optimal` via `quote()` that fails the min-amount checks, reverting the extrinsic with `Error::AssetTwoDepositDidNotMeetMinimum` (or analogous errors) despite `total_supply == 0`.
