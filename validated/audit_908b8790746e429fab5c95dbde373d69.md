Audit Report

## Title
Unchecked `debug_assert!`-guarded payout transfers in `claim_bounty` / `claim_child_bounty` can silently strand treasury funds if a transfer fails - ([File: substrate/frame/bounties/src/lib.rs], [File: substrate/frame/child-bounties/src/lib.rs])

## Summary
`Bounties::claim_bounty` and `ChildBounties::claim_child_bounty` unconditionally clear the bounty/child-bounty storage entry after issuing payout transfers, relying only on `debug_assert!(res.is_ok())` to verify the transfer outcome rather than propagating the error with `ensure!`/`?`. Because `debug_assert!` is a no-op in release builds (which is how production runtime wasm is normally compiled), a failed transfer — e.g. due to the beneficiary/curator account being non-existent and the payout amount falling below `ExistentialDeposit` — is not detected, and the bounty record is removed as if payout succeeded, stranding the value in the un-referenced bounty sub-account.

## Finding Description
In `claim_bounty`, the fee and payout transfers are performed and checked only via `debug_assert!`, after which `*maybe_bounty = None` unconditionally clears the storage entry regardless of transfer outcome: [1](#0-0) 

The identical pattern exists in `claim_child_bounty`, where both the curator-fee transfer and beneficiary payout transfer are checked with `debug_assert!` before the child-bounty entry is cleared via `*maybe_child_bounty = None`: [2](#0-1) 

`T::Currency::transfer(..., AllowDeath)` to a non-existent account with an amount below `ExistentialDeposit` returns an `Err` (the account cannot be created below the ED). Since `debug_assert!` compiles to nothing when `debug-assertions` is not enabled, this error is silently discarded and execution proceeds to remove the bounty/child-bounty record and emit a "success" event (`BountyClaimed` / `Claimed`) even though the transfer never happened.

## Impact Explanation
This does not conserve value or settle the payout exactly once to the rightful beneficiary — it can leave the escrowed value permanently stuck in `bounty_account_id`/`child_bounty_account_id` sub-accounts with no on-chain record to reclaim it after the storage entry is cleared, matching the "permanent user-fund lock" and "payout state must only advance after settlement succeeds" pivots in the impact gate.

## Likelihood Explanation
Exploitability depends on being able to drive a real transfer failure. The scoped code was inspected for guards that would prevent the fee/payout split from producing a sub-ED transfer to a fresh account (e.g., a minimum bounty value or a check that `fee` cannot make `payout` too small), but I was unable to fully confirm within the available tool budget whether `propose_bounty`/`propose_curator` enforce a lower bound on `payout = value - fee` (searches for `BountyValueMinimum` and fee-vs-value checks in `substrate/frame/bounties/src/lib.rs` returned matches but I could not inspect their content before running out of iterations). This is a material gap: if such a check exists and guarantees `payout`/`final_fee` always exceed `ExistentialDeposit` for any valid bounty, the "silent stranding" scenario described could be unreachable in practice, and the `debug_assert!` pattern — while still poor defensive-programming practice — would not constitute an independently exploitable fund-loss bug. I could not verify this either way with confidence.

## Recommendation
Replace `debug_assert!(res.is_ok())` with `ensure!`/`?`-based propagation of the transfer result inside `try_mutate_exists`, so that the bounty/child-bounty entry is only cleared once both transfers have verifiably succeeded, and additionally verify (or add, if missing) an enforced lower bound ensuring `payout` and `final_fee` cannot fall below `ExistentialDeposit` for newly created recipient accounts.

## Proof of Concept
Unverified due to inconclusive investigation of whether a minimum-value/fee guard already prevents the triggering condition. A conclusive PoC would require: (1) confirming whether `propose_bounty`/`propose_curator` in `substrate/frame/bounties/src/lib.rs` enforce `value - fee >= ExistentialDeposit`, and if not, (2) a unit test setting a fresh, never-funded beneficiary/curator with a payout below the test runtime's `ExistentialDeposit`, then calling `claim_bounty`/`claim_child_bounty` and asserting the storage entry is removed and a success event emitted while the recipient's balance remains zero and funds remain stuck in the bounty sub-account.
