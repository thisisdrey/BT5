### Title
Bancor-style Exchange pricing uses non-deterministic floating-point math, enabling AMM-style reserve-draining rounding exploitation - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The external report describes an attacker repeatedly performing flash-swap style trades against an AMM pair whose reserve/price bookkeeping had exploitable arithmetic, letting the attacker extract far more tokens than they deposited across successive swaps. java-tron's TRC10 "Bancor" `Exchange` feature (`ExchangeCreateContract`/`ExchangeTransactionContract`) is a chain-native constant-product-like AMM reachable by any signed transaction, and by default its price/quantity calculation is done with unguarded IEEE-754 `double` arithmetic and plain `long` addition/subtraction, rather than exact integer or big-decimal math.

### Finding Description
`ExchangeCapsule.transaction()` computes the amount received in a swap via `ExchangeProcessor.exchange()` unless the hardened path (`allowHarden`) is active [1](#0-0) . The default, non-hardened `ExchangeProcessor` computes token quantities using `Math.pow`-based `double` arithmetic on the pool balances (`exchangeToSupply`/`exchangeFromSupply`), and the resulting `long` is derived by truncating a `double` [2](#0-1) . Whether this hardened, exact `BigDecimal`-based `SafeExchangeProcessor` path is used at all is gated by the `allowHardenExchangeCalculation` dynamic property, checked in `AbstractExchangeActuator.allowHarden()` [3](#0-2) ; when this proposal-gated flag is off (its default/legacy state on production chains that have not activated the corresponding hard fork proposal), reserve balances are also updated with un-checked `+`/`-` instead of exact-arithmetic checks in the same actuator helpers [4](#0-3) .

This is directly analogous to the RES exploit's root cause: an on-chain price/reserve formula that is not computed with exact, monotonic, overflow-safe arithmetic, allowing sequences of small/precisely-sized trades (all executable by any unprivileged account via `ExchangeTransactionContract`) to exploit floating-point rounding/precision loss (`Math.pow` truncation, `double` non-associativity) to extract more value from the pool than economically justified, or to desynchronize the pool's `firstTokenBalance`/`secondTokenBalance` from the real value backing it. The project's own tests already demonstrate that hardened vs. non-hardened paths produce different results for identical inputs (`Assert.assertNotEquals(anotherTokenQuant, result);` in `testStrictMath`) confirming the non-determinism/precision divergence of the default double-based processor [5](#0-4) .

### Impact Explanation
Any account can create an exchange pool (`ExchangeCreateActuator`) and any account can call `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` against it with attacker-chosen quantities [6](#0-5) . If floating-point rounding can be steered by carefully sized repeated trades (as in the RES case, which used a sequence of six flash-swap legs with attacker-chosen quantities), an attacker could drain TRX/TRC10 tokens locked in the exchange pool beyond what their deposited tokens are worth — a direct theft-of-funds / unbacked-balance scenario for exchange liquidity, consistent with the accepted impact criteria (theft of funds, unbacked balance).

### Likelihood Explanation
Medium: exploitation requires the `allowHardenExchangeCalculation` property to be disabled (the legacy/default calculation path) and requires an attacker to find an exact sequence of trade sizes that produces favorable double-precision rounding — this needs analysis/brute-forcing similar to the original RES PoC's carefully chosen swap amounts, but is fully achievable off-chain by simulating `ExchangeProcessor.exchange()` since its logic is deterministic given fixed inputs and public. No special privileges or timing constraints are required beyond ordinary transaction broadcasting.

### Recommendation
- Make `SafeExchangeProcessor` (`BigDecimal`/exact-arithmetic) with `hardenedCalc=true` reachable and mandatory for all networks, i.e., ensure `allowHardenExchangeCalculation` is enabled by default (or remove the legacy `ExchangeProcessor` double-math path entirely) so all exchange calculations use overflow-checked exact arithmetic, matching what `ExchangeCapsule.transaction(..., hardenedCalc=true)` already provides for balance floor-checks [7](#0-6) .
- Audit `ExchangeProcessor`'s `Math.pow`-based formula for edge cases where truncation/rounding can be repeatedly exploited to extract more value than deposited, and add invariant checks (e.g., constant-product/k should never decrease beyond fee tolerance) after every swap regardless of hardened mode.

### Proof of Concept
Not independently reproduced in this environment (no runtime/test harness executed here); the analog is derived from the code paths cited above. A concrete PoC would use `ExchangeCreateActuator` to open a pool, then repeatedly invoke `ExchangeTransactionActuator` with quantities chosen so that `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`'s `double` truncation systematically favors the attacker across the sequence (mirroring the six-step flash-swap sequence in the original RES `pancakeCall` exploit), while `allowHardenExchangeCalculation` is disabled.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
