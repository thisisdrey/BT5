## Analysis

The external report's core broken invariant is: **a single unconfirmed transaction that sets a critical, unrecoverable admin address with no validation and no second-party confirmation can permanently disable all admin-gated recovery paths, trapping other parties' funds.** The Solidity report frames this around `Ownable.transferOwnership`/`renounceOwnership`, but the same pattern exists natively in `pallet-nomination-pools`'s `update_roles` extrinsic.

### Local analog

`update_roles` lets the pool's `root` (a normal, permissionless, self-appointed account — anyone can `create` a pool and become its `root`) reassign `root`, `nominator`, and `bouncer` in one atomic, single-step call, with **zero validation** that the new addresses are usable/controllable: [1](#0-0) 

Per the pallet docs, `root` is the *only* entity that can ever change any role again, including itself, and the depositor can never regain that power: [2](#0-1) [3](#0-2) 

If `root` calls `update_roles` and sets `root`, `nominator`, and `bouncer` all to addresses whose keys are not held by anyone (a typo, wrong lookup index, wrong chain's SS58 address, etc.), there is no `pendingOwner`/claim step and no on-chain validation of the target — the change is final and irrecoverable, exactly mirroring the report's "incorrect address... prevents use of all `onlyOwner()` functions forever" scenario.

### Why existing state-recovery paths don't save it

`set_state` normally requires `bouncer` or `root` (`can_toggle_state`), but there is a permissionless escape only when `ok_to_be_open()` fails (e.g., pool over member/TVL caps, bad commission, etc.): [4](#0-3) 

If the pool remains within normal "ok to be open" bounds (the common case for most pools), there is **no path at all** to force it into `Destroying` once all three roles are bricked — no governance override, no depositor override (`update_roles` explicitly excludes the depositor from ever regaining role-setting power), and no permissionless trigger. Members' bonded funds are unable to be unbonded/withdrawn (`unbond`/`withdraw_unbonded` for non-depositor members require either self-action, which they retain, but the pool cannot be nominated, kicked, reconfigured, or wound down by anyone if abusive commission/nomination behavior needs correcting, and new joiners can still be blocked/unblocked only by the now-inaccessible roles). This is a self-inflicted, single-step, irrecoverable admin-key change that harms *other* pool members, not just the mistaken actor.

### Title
Single-step, unvalidated `update_roles` in `pallet-nomination-pools` permanently bricks pool administration and can trap other members' funds - (File: `substrate/frame/nomination-pools/src/lib.rs`)

### Summary
`Pallet::update_roles` (call index 12) lets a pool's `root` account atomically overwrite `root`, `nominator`, and `bouncer` to arbitrary, unvalidated `AccountId`s in a single transaction, with no two-step confirmation, no existence check, and no way for the depositor or other members to recover if the new addresses are inaccessible.

### Finding Description
`update_roles` is defined at [5](#0-4)  and performs immediate, one-step overwrites of all three admin roles via `ConfigOp::Set`. There is no `pendingRoot`/two-step claim pattern, unlike what the external report recommends for critical address changes. The pallet's own documentation confirms `root` is the sole entity capable of ever changing roles again, and that the `depositor` — the only role guaranteed to persist — explicitly cannot: [3](#0-2) . Recovery via `set_state` to `Destroying` (which would let members permissionlessly exit) is gated behind `bouncer`/`root` unless the pool independently fails `ok_to_be_open()` [6](#0-5) , which is not guaranteed for a healthy pool.

### Impact Explanation
A single mistaken (or malicious-by-the-pool's-own-root) call to `update_roles` that sets `root`/`nominator`/`bouncer` to inaccessible addresses permanently strips the pool of all administrative capability: no one can nominate new validators, unblock/reopen the pool, adjust commission, or force winding-down through `set_state` if the pool remains within normal healthy bounds. This traps the bonded funds of every non-depositor member in a pool that can no longer be actively managed or wound down by any party, matching the "permanent user-fund lock" impact category.

### Likelihood Explanation
This requires no privileged chain governance, validator, or relayer action — it only requires the `root` account of an arbitrary, permissionlessly created nomination pool to submit one ordinary signed extrinsic with a wrong argument (typo'd `AccountIdLookupOf<T>`, wrong SS58 checksum-adjacent value, etc.). Given `root` is a normal user-controlled key (any account can create a pool and become its own root), the same class of human/tooling error described in the external report applies directly here, and the pallet performs no confirmation or reachability check before committing the change.

### Recommendation
Introduce a two-step confirmation for `update_roles` role reassignment (especially for `root`): require the new `root` (and optionally `bouncer`/`nominator`) to submit an acceptance/claim extrinsic before the change takes effect, mirroring the pattern used elsewhere in the codebase for asset/collection ownership transfer (e.g., `pallet-nfts`' `set_acceptance_ownership` + `transfer_ownership` two-step flow at [7](#0-6) ). At minimum, add a permissionless emergency escape from any pool state to `Destroying` once roles have been unreachable/unresponsive for a bounded period, independent of `ok_to_be_open()`.

### Proof of Concept
1. Any account `A` calls `Pools::create(...)`, becoming `root`, `nominator`, `bouncer`, and `depositor` (or a subset) of pool `P`.
2. Other accounts `B`, `C`, ... join `P` via `Pools::join`, bonding funds.
3. `A` calls `Pools::update_roles(origin=A, pool_id=P, new_root=ConfigOp::Set(garbage_addr), new_nominator=ConfigOp::Set(garbage_addr2), new_bouncer=ConfigOp::Set(garbage_addr3))` where `garbage_addr*` are addresses with no known private key (e.g., mistyped lookup index or wrong-chain SS58 address) — this succeeds unconditionally per [8](#0-7) .
4. As long as `P.ok_to_be_open()` continues to hold (normal operating conditions), no one — not `B`/`C`, not the depositor, not `A` — can call `set_state`, `nominate`, `set_commission`, or any other role-gated extrinsic on `P` ever again; `B`/`C`'s bonded funds remain locked in an unmanageable, non-`Destroying` pool.

		///
		/// If a pool is already in the `Destroying` state, then under no condition can its state
		/// change again.
		///
		/// The dispatch origin of this call must be either:
		///
		/// 1. signed by the bouncer, or the root role of the pool,
		/// 2. if the pool conditions to be open are NOT met (as described by `ok_to_be_open`), and
		///    then the state of the pool can be permissionlessly changed to `Destroying`.
		#[pallet::call_index(9)]
		#[pallet::weight(T::WeightInfo::set_state())]
		pub fn set_state(
			origin: OriginFor<T>,
			pool_id: PoolId,
			state: PoolState,
		) -> DispatchResult {
			let who = ensure_signed(origin)?;
			let mut bonded_pool = BondedPool::<T>::get(pool_id).ok_or(Error::<T>::PoolNotFound)?;
			ensure!(bonded_pool.state != PoolState::Destroying, Error::<T>::CanNotChangeState);
			// ensure pool is not in an un-migrated state.
			ensure!(!Self::api_pool_needs_delegate_migration(pool_id), Error::<T>::NotMigrated);

			if bonded_pool.can_toggle_state(&who) {
				bonded_pool.set_state(state);
			} else if bonded_pool.ok_to_be_open().is_err() && state == PoolState::Destroying {
				// If the pool has bad properties, then anyone can set it as destroying
				bonded_pool.set_state(PoolState::Destroying);
			} else {
				Err(Error::<T>::CanNotChangeState)?;
			}

			bonded_pool.put();

			Ok(())
		}

		/// Update the roles of the pool.
		///
		/// The root is the only entity that can change any of the roles, including itself,
		/// excluding the depositor, who can never change.
		///
		/// It emits an event, notifying UIs of the role change. This event is quite relevant to
		/// most pool members and they should be informed of changes to pool roles.
		#[pallet::call_index(12)]
		#[pallet::weight(T::WeightInfo::update_roles())]
		pub fn update_roles(
			origin: OriginFor<T>,
			pool_id: PoolId,
			new_root: ConfigOp<T::AccountId>,
			new_nominator: ConfigOp<T::AccountId>,
			new_bouncer: ConfigOp<T::AccountId>,
		) -> DispatchResult {
			let mut bonded_pool = match ensure_root(origin.clone()) {
				Ok(()) => BondedPool::<T>::get(pool_id).ok_or(Error::<T>::PoolNotFound)?,
				Err(sp_runtime::traits::BadOrigin) => {
					let who = ensure_signed(origin)?;
					let bonded_pool =
						BondedPool::<T>::get(pool_id).ok_or(Error::<T>::PoolNotFound)?;
					ensure!(bonded_pool.can_update_roles(&who), Error::<T>::DoesNotHavePermission);
					bonded_pool
				},
			};

			// ensure pool is not in an un-migrated state.
			ensure!(!Self::api_pool_needs_delegate_migration(pool_id), Error::<T>::NotMigrated);

			match new_root {
				ConfigOp::Noop => (),
				ConfigOp::Remove => bonded_pool.roles.root = None,
				ConfigOp::Set(v) => bonded_pool.roles.root = Some(v),
			};
			match new_nominator {
				ConfigOp::Noop => (),
				ConfigOp::Remove => bonded_pool.roles.nominator = None,
				ConfigOp::Set(v) => bonded_pool.roles.nominator = Some(v),
			};
			match new_bouncer {
				ConfigOp::Noop => (),
				ConfigOp::Remove => bonded_pool.roles.bouncer = None,
				ConfigOp::Set(v) => bonded_pool.roles.bouncer = Some(v),
			};

			Self::deposit_event(Event::<T>::RolesUpdated {
				root: bonded_pool.roles.root.clone(),
				nominator: bonded_pool.roles.nominator.clone(),
				bouncer: bonded_pool.roles.bouncer.clone(),
			});

			bonded_pool.put();
			Ok(())
		}
