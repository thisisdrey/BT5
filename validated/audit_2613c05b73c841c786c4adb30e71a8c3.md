## Title
Hardened-exchange-calc flag re-enables the Bancor-relay `ExchangeTransactionContract`, exposing a reserve-ratio oracle to same-block/same-transaction price manipulation — ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
java-tron previously froze the internal Bancor-relay token exchange (`ExchangeTransactionContract`) at the actuator/consensus level because its price is derived directly from live, attacker-influenceable pool reserves — the exact bug class described in the Ichi-vault report (spot reserves used as a price oracle, manipulable within a single atomic operation). The current code introduces an `allowHardenExchangeCalculation` dynamic parameter that, when enabled, causes `Manager.isExchangeTransaction(...)` to report `false` for `ExchangeTransactionContract`, bypassing the `pushTransaction`/block-packing rejection gate that was put in place specifically to block this contract type. This re-opens the reserve-ratio-manipulation surface identical in kind to the reported Ichi vault LP oracle issue.

### Finding Description
`Manager.pushTransaction` and `Manager.generateBlock` both gate `ExchangeTransactionContract` execution behind `isExchangeTransaction(...)`, throwing `ContractValidateException("ExchangeTransactionContract is rejected")` when it evaluates true: [1](#0-0) [2](#0-1) 

The unit test `isExchangeTransactionBypassedWhenHardenedEnabled` confirms that this gate is conditioned on `allowHardenExchangeCalculation`: with the flag at `0` (default), `isExchangeTransaction` returns `true` (blocked); with the flag set to `1` ("hardened" mode), the same contract instance makes `isExchangeTransaction` return `false`, i.e. the block is bypassed and the contract is allowed to execute: [3](#0-2) 

Once bypassed, `ExchangeTransactionActuator.execute` runs `ExchangeCapsule.transaction(...)`, which computes the swap output purely from the `ExchangeCapsule`'s two live token reserve balances (`firstTokenBalance`/`secondTokenBalance`) via a Bancor-relay formula (`ExchangeProcessor`/`SafeExchangeProcessor`): [4](#0-3) [5](#0-4) 

This mirrors the Ichi report precisely: the traded price is a function of the pool's current on-chain reserves, which any account can shift arbitrarily within the same block/transaction sequence by issuing large `ExchangeInjectContract`/`ExchangeTransactionContract` calls immediately before the exploitative swap, since there is no TWAP, hysteresis check, or external price reference — the same missing mitigation the report recommends (`checkHysteresis`/TWAP deviation check). `ExchangeInjectActuator` and `ExchangeWithdrawActuator` similarly mutate reserve ratios directly from user-supplied deposit amounts with no external anchor: [6](#0-5) 

Because a single java-tron transaction can carry multiple contracts, and each is applied sequentially and durably to state within `processTransaction`, an attacker can, in one atomic transaction (broadcast by an unprivileged account): (1) `ExchangeInjectContract` to skew the reserve ratio, (2) `ExchangeTransactionContract` to trade against the now-mispriced pool for a favorable output, and (3) `ExchangeWithdrawContract`/reverse-inject to restore the pool — with no intervening block boundary needed to make the manipulation atomic and low-risk to the attacker, closely analogous to a flash-loan-style single-transaction price manipulation.

### Impact Explanation
Any account can drain value from other liquidity providers of a given `ExchangeCapsule` pool by manipulating the reserve ratio and immediately trading against it, since the swap price has no external/TWAP anchor and is fully attacker-influenceable within one transaction. This is a direct, unauthorized value-extraction vector (theft of pool funds) reachable by any signed transaction once `allowHardenExchangeCalculation` is enabled — which is exactly the condition under which the codebase's own tests exercise "hardened" mode success paths, implying it is an expected/reachable operating mode rather than a purely theoretical one.

### Likelihood Explanation
The blocking gate exists specifically because this contract type was recognized as unsafe/deprecated (message: "ExchangeTransactionContract is rejected"). The `allowHardenExchangeCalculation` flag re-enables it while only fixing arithmetic overflow/precision (via `SafeExchangeProcessor`/`StrictMathWrapper`), not the fundamental reserve-manipulation issue. If/when this dynamic parameter is turned on (via committee proposal, as with other `DynamicPropertiesStore` flags), the exchange functionality becomes fully reachable again by any unprivileged transaction, with no other guard reintroduced.

### Recommendation
- Do not tie the safety-relevant rejection of `ExchangeTransactionContract` to the same flag that only hardens arithmetic; keep the contract rejected independent of `allowHardenExchangeCalculation`, or
- If exchange functionality is intentionally being reactivated, add the TWAP/hysteresis-style protection recommended in the original report (e.g., compare current relay price against a time-weighted reference and reject/limit trades that deviate beyond a threshold within the same block), and impose per-block/per-transaction caps on reserve ratio change (inject/withdraw/trade) to prevent atomic manipulation.
- Add explicit tests that assert the pool price cannot be manipulated and immediately arbitraged within a single transaction/block once hardened mode is enabled.

### Proof of Concept
1. Committee/relevant governance enables `allowHardenExchangeCalculation = 1` (as exercised by `hardenedSuccessExchangeTransaction`/`isExchangeTransactionBypassedWhenHardenedEnabled` tests) — [7](#0-6) .
2. Attacker broadcasts a transaction containing an `ExchangeInjectContract` that heavily skews `firstTokenBalance`/`secondTokenBalance` of a target `ExchangeCapsule` — [8](#0-7) .
3. In the same or immediately following transaction, attacker calls `ExchangeTransactionContract` to swap against the skewed pool, receiving an output computed purely from the now-manipulated reserves via `ExchangeCapsule.transaction`/`ExchangeProcessor.exchange` — [9](#0-8) .
4. Attacker reverses the injection with `ExchangeWithdrawContract`, restoring the pool and net-extracting the arbitraged value from other pool participants — [10](#0-9) .

Note: I was not able to fully verify from the index alone under what governance conditions `allowHardenExchangeCalculation` can currently be set to 1 in production (this is defined in `DynamicPropertiesStore.java`, whose full setter/committee-proposal wiring I could not completely inspect within the available index) — a Devin session with full repository access would be needed to confirm the exact activation path and whether it is already active on mainnet-equivalent configuration.

  public void isExchangeTransactionBypassedWhenHardenedEnabled() throws Exception {
    Transaction exchange = Transaction.newBuilder().setRawData(
        Transaction.raw.newBuilder().addContract(
            Transaction.Contract.newBuilder()
                .setType(ContractType.ExchangeTransactionContract)
                .setParameter(Any.pack(ExchangeTransactionContract.newBuilder()
                    .setExchangeId(1L).setQuant(1L).setExpected(1L).build()))
                .build())).build();

    java.lang.reflect.Method m = Manager.class.getDeclaredMethod(
        "isExchangeTransaction", Transaction.class);
    m.setAccessible(true);

    // Default: hardened disabled (==0) -> contract is treated as exchange
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    Assert.assertTrue("Exchange tx must be detected when hardened disabled",
        (boolean) m.invoke(dbManager, exchange));

    // Hardened enabled -> bypass returns false
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    Assert.assertFalse("Exchange tx must be bypassed when hardened enabled",
        (boolean) m.invoke(dbManager, exchange));

    // Reset
    chainManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
