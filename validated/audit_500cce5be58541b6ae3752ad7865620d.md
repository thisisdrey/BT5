### Title
Stale PromiseYield receipts survive account deletion and execute against an unrelated re-created account of the same name - (File: runtime/runtime/src/lib.rs)

### Summary
`remove_account` (called from `action_delete_account`) deletes an account's `Account`, `ContractCode`, access keys, and contract data, but does not remove any `PromiseYieldReceipt`, `PromiseYieldStatus`, or `PromiseYieldTimeout` entries keyed on that account id. Because `PromiseResume` handling in `process_receipt` looks up the parked yield receipt purely by `(receiver_id, data_id)` with `get_promise_yield_receipt(state_update, account_id, data_id)`, a yield receipt created by one "instance" of an account can be resumed and executed after the account name has been deleted and re-created by an unrelated party, running attacker-authored actions against the new account's state.

### Finding Description
`set_promise_yield_receipt` / `get_promise_yield_receipt` / `remove_promise_yield_receipt` key state solely by `receiver_id` (an `AccountId`) and `data_id`, with no binding to the specific `Account` instance that existed when the yield was created: [1](#0-0) 

`action_delete_account` calls `remove_account`, which removes the `Account`, `ContractCode`, access/gas keys, and contract data trie entries, but never touches `PromiseYieldReceipt`, `PromiseYieldStatus`, or `PromiseYieldTimeout` keys: [2](#0-1) [3](#0-2) 

`process_receipt`'s `PromiseResume` arm fetches the parked yield receipt keyed only by `account_id`/`data_id`, with no check binding it to the currently-existing `Account` at that id, then executes it via `apply_action_receipt` against whatever account currently occupies that name: [4](#0-3) 

Exploit flow:
1. Attacker's parent account creates `X` and, via a FunctionCall, invokes `promise_yield_create`, embedding attacker-chosen actions (e.g. a `FunctionCall` or `Transfer`) to run on `X` once resumed. The parked yield receipt (with `receiver_id = X`) is stored under `PromiseYieldReceipt{receiver_id: X, data_id}` [5](#0-4) , and the attacker retains the `data_id` returned by the host call.
2. Attacker issues `DeleteAccount(X, beneficiary=attacker)`. `remove_account` wipes the `Account`/keys/contract/data for `X` but leaves the `PromiseYieldReceipt`/`PromiseYieldTimeout` entries intact [2](#0-1) .
3. Some unrelated party later creates a fresh account named `X` (NEAR permits re-registering a previously deleted account name), deploys their own contract, and funds it.
4. Attacker submits a `promise_yield_resume`-triggering call referencing the original `data_id`. Because the lookup in the `PromiseResume` arm is keyed only by name, it finds the old parked receipt and executes its actions against the new `X` account's state, effectively running attacker-crafted actions (funded/authorized at creation time by the attacker, before the victim ever owned `X`) with the new account as the execution context.

Existing checks (signature/nonce/access-key/gas) do not protect against this because the attack does not forge any signature — the attacker's original `promise_yield_create` call was legitimately signed by the attacker while they owned `X`; the vulnerability is that the runtime's state model does not associate the parked receipt with the specific account instance, only with the reusable name.

### Impact Explanation
This is an authorization-escalation / fund-theft vector: an attacker can pre-plant a "time bomb" receipt (e.g., `Transfer` draining balance to attacker's beneficiary, or a `FunctionCall` invoking privileged methods) against an account name they control, delete the account, and have that receipt fire later against whoever legitimately re-registers the same account name — without the new owner's consent. This falls under "authorization escalation across accounts/promises" and potential "theft of user funds" in the NEAR bounty categories.

### Likelihood Explanation
Preconditions are fully within attacker capability with no privileged access: creating/deleting a sub-account, calling `promise_yield_create`/`promise_yield_resume` are all standard unprivileged actions available to any funded account. The main uncertainty is timing/practicality: the attack requires a third party to re-create the exact same account name `X` after deletion, and requires the parked yield receipt (and any associated `PromiseYieldTimeout`) to still be in state (i.e., resumed before its timeout fires, or the timeout window is long enough). Because top-level account names are globally unique and namespace reuse of arbitrary top-level names is uncommon (attackers would likely need to target sub-accounts of a well-known parent, e.g. `victim.attacker-controlled-parent.near`, where they can control both deletion and who re-registers), the practical exploitability depends on the attacker also controlling or predicting re-creation of the same name — this significantly narrows real-world scenarios and was not fully verified against `promise_yield_create`'s action-attachment code or the exact timeout-queue cleanup path (not confirmed within available context) in this repository.

### Recommendation
Bind parked `PromiseYield` receipts (and their timeout entries) to the account's lifetime: either (a) have `remove_account` also purge any `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries for the account being deleted (would require an indexed scan or an account-generation counter), or (b) include an account "generation"/creation-nonce in the yield trie key and validate it matches the current account's generation when resuming, rejecting stale resumes for a different account instance.

### Proof of Concept
Integration test plan (test-loop or runtime apply-path):
1. Create account `X` under attacker-controlled parent; deploy a test contract; call `promise_yield_create` from `X`'s own contract, embedding a callback action (e.g., `Transfer` to attacker or `FunctionCall`), and capture `data_id`.
2. Submit `DeleteAccount(X, beneficiary=attacker)`; apply block; assert `Account{X}` is gone from state but `PromiseYieldReceipt{receiver_id: X, data_id}` still resolves via `get_promise_yield_receipt`.
3. Submit `CreateAccount(X)` with fresh, unrelated code/state/balance funded by an unrelated party ("victim").
4. Submit a `PromiseResume`-triggering call (`promise_yield_resume`) referencing the original `data_id`.
5. Assert the parked yield receipt executes with `receiver_id == X` against the *new* Account struct (different `storage_usage`/contract hash than at creation time), and that the attacker-embedded action (e.g. balance transfer) is applied to the victim's account — demonstrating cross-instance authorization escalation.

pub fn set_promise_yield_receipt(state_update: &mut TrieUpdate, receipt: &Receipt) {
    match receipt.versioned_receipt() {
        VersionedReceiptEnum::PromiseYield(action_receipt) => {
            assert!(action_receipt.input_data_ids().len() == 1);
            let key = TrieKey::PromiseYieldReceipt {
                receiver_id: receipt.receiver_id().clone(),
                data_id: action_receipt.input_data_ids()[0],
            };
            set(state_update, key, receipt);
        }
        _ => unreachable!("Expected PromiseYield receipt"),
    }
}

pub fn remove_promise_yield_receipt(
    state_update: &mut TrieUpdate,
    receiver_id: &AccountId,
    data_id: CryptoHash,
) {
    state_update.remove(TrieKey::PromiseYieldReceipt { receiver_id: receiver_id.clone(), data_id });
}

pub fn get_promise_yield_receipt(
    trie: &dyn TrieAccess,
    receiver_id: &AccountId,
    data_id: CryptoHash,
) -> Result<Option<Receipt>, StorageError> {
    get(trie, &TrieKey::PromiseYieldReceipt { receiver_id: receiver_id.clone(), data_id })
}
