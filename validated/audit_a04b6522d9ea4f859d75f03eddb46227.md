### Title
Single malformed StackerDB chunk reply aborts processing of all other in-flight replies in a sync round - (File: stackslib/src/net/stackerdb/sync.rs)

### Summary
`StackerDBSync::getchunks_try_finish` iterates over all collected replies from potentially multiple neighbors in a single pass, and calls `self.validate_downloaded_chunk(network, config, &data)?` with the `?` operator inside the loop body. If validation returns `Err` (rather than `Ok(false)`) for one neighbor's reply, the `?` propagates out of the function immediately, abandoning the loop before the remaining (possibly valid) replies from other neighbors in the same batch are processed.

### Finding Description
`getchunks_try_finish` drains all inflight replies via `self.comms.collect_replies(network)` and processes them in a `for (naddr, message) in ... { ... }` loop: [1](#0-0) 

The validation call uses `?`, so an `Err` return terminates the whole `getchunks_try_finish` call, not just the processing of that one neighbor's chunk. `validate_downloaded_chunk` itself calls `network.validate_received_chunk(...)?`: [2](#0-1) 

`validate_received_chunk` calls `slot_metadata.verify(&addr)?`, which itself calls into `MessageSignature` public-key recovery: [3](#0-2) 

`SlotMetadata::verify` returns `Err(Error::VerifyingError(..))` when the signature bytes cannot be recovered into a public key (e.g., an empty/malformed `MessageSignature`), rather than `Ok(false)`: [4](#0-3) 

This exact fault path is already demonstrated in the repo's own test for the push-chunk handler, which shows that a forged/empty signature produces `Err(NetError::VerifyingError(_))` instead of a graceful `Ok(false)` rejection: [5](#0-4) 

So any remote StackerDB replica peer that the local node is requesting chunks from (an unprivileged position — one of potentially several neighbors serving a StackerDB replica) can reply to a `GetChunks` request with a `StackerDBChunk` message carrying an empty/unrecoverable signature. When `getchunks_try_finish` reaches that reply in the `for` loop, `validate_downloaded_chunk` returns `Err`, and the `?` aborts the function before any subsequent, otherwise-valid replies queued in the same `collect_replies()` batch are validated and stored via `add_downloaded_chunk`.

The error then propagates further up through the sync state machine's main loop, e.g. the `GetChunks` state handler which calls `self.getchunks_try_finish(network, config)?`, terminating that pass of the sync round with an error rather than advancing state or storing legitimate chunks that were collected in the same batch.

### Impact Explanation
This is the direct in-repo analog of the reported Notional issue: a single bad response from one external/remote party in a batch aborts processing of the entire batch rather than being isolated and skipped. Here, one malicious or buggy StackerDB replica peer can cause the local node's StackerDB chunk-fetch round to bail out early, discarding/ignoring the valid chunk replies collected from other, honest neighbors in the same `collect_replies()` call. This degrades and can repeatedly disrupt StackerDB replication (e.g., signer message propagation) if the attacker is positioned as one of the configured hint-replicas/neighbors for a given StackerDB contract and repeatedly sends malformed signatures on every fetch round, causing chunk sync to stall relative to what it should achieve, an availability/robustness degradation for StackerDB (signer-set) synchronization rather than a full crash.

Because the fault is bounded to this state machine's one iteration (the loop is re-entered on the next state machine tick and the malformed chunk was already consumed via `collect_replies`'s `drain()`), it is not a persistent unrecoverable stall by itself, but a repeat attacker positioned to answer `GetChunks` requests could produce this failure on every round, indefinitely delaying convergence of the honest chunks queued alongside the bad one in the same batch — a High-severity availability degradation on the StackerDB chunk-sync read/exchange path, not a full node crash.

### Likelihood Explanation
Likelihood is moderate-to-high in a deployment where an adversary is configured/selected as a StackerDB hint replica/neighbor (which is a normal, permissionless situation for public StackerDB configs) and races to answer `GetChunks` requests alongside honest peers. No authentication bypass or privileged position is required beyond being a network peer that the victim requests chunks from, which is achievable by any observed StackerDB replica node.

### Recommendation
In `getchunks_try_finish` (and any other per-reply-in-a-loop processing that calls fallible validation with `?`), do not propagate validation `Err` out of the entire batch loop. Instead, catch/log the error for that specific neighbor's chunk, mark/drop that neighbor (similar to how NACK and unexpected-message branches already `continue`), and proceed to process the remaining replies in the same `collect_replies()` batch. This preserves availability for the honest majority of concurrently-replying neighbors even when one neighbor is malicious or misbehaving.

### Proof of Concept
1. Configure a StackerDB sync between a victim node and 2+ neighbor replicas for the same contract, so multiple `GetChunks` requests are in flight simultaneously (as in the existing multi-peer stackerdb sync tests, e.g. `stackslib/src/net/stackerdb/tests/sync.rs` lines 744-836 setup with 3 peers).
2. Have one neighbor (attacker-controlled) respond to a `GetChunks` request with a `StacksMessageType::StackerDBChunk(data)` whose `data.sig` is `MessageSignature::empty()` (an unrecoverable signature), while another honest neighbor responds with a validly signed chunk for a different slot in the same round.
3. Call `sync.getchunks_try_finish(network, config)` and observe that it returns `Err(net_error::VerifyingError(..))` due to the `?` in the loop, and that the valid chunk from the honest neighbor collected earlier in the same `for` loop iteration was never passed to `add_downloaded_chunk`, i.e., it is lost for this round.
4. Repeating this on subsequent rounds (attacker always answers with a malformed signature before/alongside honest peers) repeatedly discards/delays valid data from the batch, demonstrating the DOS-of-batch-processing behavior analogous to the Notional rebalance issue.

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
