Audit Report

## Title
`relayer_fee` in Snowbridge inbound messages is an unbounded, attacker-chosen value registered as an unbacked relayer reward with no check against actual bridged value - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

## Summary
`InboundQueue::process_message` in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` takes `message.relayer_fee` — decoded verbatim from the Ethereum Gateway event's `Payload.relayerFee` field in `bridges/snowbridge/primitives/inbound-queue/src/v2/message.rs` — and unconditionally registers it as a claimable relayer reward via `T::RewardPayment::register_reward`, with no bound relative to `message.value`, `execution_fee`, or any protocol fee schedule. The reward is ultimately paid out through `PayAccountOnLocation::pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs`), which mints the reward amount as a fresh `ReserveAssetDeposited` XCM asset rather than debiting a pool backed by actually-locked Ethereum funds, meaning an attacker who both originates the Ethereum event and submits it as "the relayer" can mint arbitrary amounts of wrapped Ether to themselves.

## Finding Description
The `Message` struct's `relayer_fee: u128` field is populated straight from the Solidity event `Payload.relayerFee` with no cross-validation against `value` (the real locked Ether) [5](#0-4) [3](#0-2) . This event is emitted whenever any unprivileged Ethereum user calls `v2_sendMessage`/`v2_registerToken` on the Gateway contract, so the field is entirely attacker-controlled off-chain input.

`submit` is a public extrinsic gated only by `ensure_signed(origin)`, and after verifying the event proof (authenticity of the log, not sanity of its field values) and decoding the message, it calls `process_message` [4](#0-3) . `process_message` performs only two content checks — `InvalidGateway` (address match) and `InvalidNonce` (replay protection) — before taking `relayer_fee`, adding any pending tip, and calling `T::RewardPayment::register_reward(&relayer, ..., total_tip)` unconditionally whenever the total is non-zero [2](#0-1) . Note that `relayer_fee` is never included in the `assets`/`execution_fee` accounting performed by the message converter (`bridges/snowbridge/primitives/inbound-queue/src/v2/converter.rs`), i.e. it is not reserve-deposited or backed by any portion of the message's locked value — it is a separate, unchecked number that flows directly into the reward ledger.

`register_relayer_reward` in `bridges/modules/relayers/src/lib.rs` simply `saturating_add`s whatever value it receives into `RelayerRewards` storage with no cap check [6](#0-5) .

Critically, the actual payout mechanism used for Snowbridge rewards, `PayAccountOnLocation::pay_reward`, does not debit an existing balance backed by real bridged Ether. It constructs an XCM containing `ReserveAssetDeposited` for the full reward amount on the Ethereum-Ether asset location, then `DepositAsset`s it to the relayer's beneficiary on AssetHub [7](#0-6) . Since `ReserveAssetDeposited` is how the bridge represents genuinely-locked-on-Ethereum Ether being recognized on the Polkadot side, using it here for a payout number that was never validated against real locked value effectively mints wrapped Ether unbacked by any actual Ethereum-side collateral.

## Impact Explanation
An attacker who controls both the Ethereum-side call to the Gateway contract and the `submit` extrinsic (trivial, since `submit` accepts any signed origin) can set `relayerFee` to an arbitrary large value while sending negligible or zero real value, then have `PayAccountOnLocation::pay_reward` mint the corresponding amount of wrapped Ether to their own account on AssetHub via `ReserveAssetDeposited`/`DepositAsset`. This is an unbacked mint of bridge-side funds, directly matching the allowed impact category "theft or unbacked mint or unlock" for Snowbridge BridgeHub code. The corrupted value is `Message.relayer_fee` (and downstream, the `reward_balance` in `RelayerRewards` and the `Asset` minted in `PayAccountOnLocation::pay_reward`).

## Likelihood Explanation
High. The attack requires only (1) calling an Ethereum contract function `v2_sendMessage` with an arbitrary `relayerFee` value — something any unprivileged Ethereum account can do — and (2) submitting the resulting proof via the public, `ensure_signed`-gated `submit` extrinsic as the attacker's own relayer account. No collusion, governance action, or key compromise is needed.

## Recommendation
Bound `relayer_fee` in `process_message` (or earlier, in message decoding/verification) against a configurable ceiling, e.g., a `Config::MaxRelayerFee`, or require that `relayer_fee` be proportional to `message.value`/`execution_fee`, or fund/cap it from value that is provably locked on the Ethereum side for that specific nonce. Reject excess fees with a new `Error` variant rather than trusting the raw, attacker-supplied event field before minting the corresponding wrapped-Ether reward.

## Proof of Concept
1. On Ethereum, call the Gateway's `v2_sendMessage`, setting `Payload.value = 0` and `Payload.relayerFee = u128::MAX` (or any amount far exceeding intended fee levels).
2. Obtain the event log and a valid receipt/execution-header proof for that event (proves the event occurred, not that its values are sane).
3. Call `EthereumInboundQueueV2::submit(origin, event_proof)` as the attacker's own account (self-relaying).
4. `process_message` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs:219-239`) computes `total_tip = relayer_fee.saturating_add(tip)` and calls `T::RewardPayment::register_reward(&relayer, ..., total_tip)`, crediting `RelayerRewards` for the full inflated amount.
5. The relayer claims the reward; `PayAccountOnLocation::pay_reward` (`bridges/snowbridge/primitives/core/src/reward.rs:127-151`) issues an XCM with `ReserveAssetDeposited` for the inflated amount and deposits it to the attacker's beneficiary account on AssetHub, minting wrapped Ether unbacked by real locked value.
