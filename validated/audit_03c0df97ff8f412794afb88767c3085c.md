### Title
Unenforced `assert totalEnergyWeight > 0` allows divide-by-zero / energy-limit overflow in `RepositoryImpl.calculateGlobalEnergyLimit` - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's energy limit by dividing by `totalEnergyWeight`, guarding the zero case only with a Java `assert` statement, which is a no-op unless the JVM is started with `-ea` (not the case in production nodes). This mirrors the reported bug class: a ratio/exchange-rate style calculation that should explicitly handle the zero-denominator case but instead relies on an ineffective guard, producing either a runtime exception or a corrupted (unbacked) result instead of a safe/consistent value.

### Finding Description
`calculateGlobalEnergyLimit` divides `totalEnergyLimit` by `totalEnergyWeight` after only checking the invariant with a Java `assert`: [1](#0-0) 

Java assertions are disabled by default at runtime unless the JVM is launched with `-ea`; production java-tron nodes do not enable assertions, so `assert totalEnergyWeight > 0;` provides no actual protection. If `totalEnergyWeight` is `0`:
- In the "hardened" branch, `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException`.
- In the legacy `double`-based branch, `(double) totalEnergyLimit / totalEnergyWeight` evaluates to `Infinity` (IEEE-754 semantics, no exception), and `(long) (energyWeight * Infinity)` casts to `Long.MAX_VALUE` — silently granting an account an astronomically large, unbacked energy limit instead of reverting or returning `0`.

Contrast this with the equivalent, properly-guarded logic elsewhere in the codebase, which explicitly checks for a zero denominator rather than relying on an assertion: [2](#0-1) [3](#0-2) 

`RepositoryImpl.calculateGlobalEnergyLimit` is invoked from the TVM energy-metering path used during contract execution (`VMActuator.java`, `ContractState.java`), which is exercised on any smart-contract-invoking transaction, i.e. reachable by any unprivileged transaction broadcaster. The exact same unguarded-division pattern is duplicated for the delegate-resource actuator paths as well: [4](#0-3) 

### Impact Explanation
This is an energy-metering / resource-accounting flaw. If `totalEnergyWeight` is `0` (e.g., in a fresh network state prior to any energy freeze, or after all energy-frozen stake has been unfrozen), any account with a frozen-for-energy balance triggers this path:
- Legacy (non-hardened) computation path: instead of returning `0` or a bounded value, the function silently returns `Long.MAX_VALUE` as the account's global energy limit — an unbacked resource grant that lets a contract call consume unlimited energy without the corresponding TRX being burned/frozen, which is an energy-metering integrity violation.
- Hardened computation path: an uncaught `ArithmeticException` is thrown from inside TVM/actuator execution logic for a legitimate transaction, which can disrupt transaction processing for otherwise valid contract-call transactions.

### Likelihood Explanation
The precondition (`totalEnergyWeight == 0`) is unlikely on a mature mainnet, since staked TRX for energy typically accumulates, but it is a genuinely possible state transiently (e.g., new/private/test networks, or degenerate edge cases where all energy-frozen stake is withdrawn). The core defect — relying on a disabled `assert` instead of an explicit guard, unlike the twin implementation in `EnergyProcessor` — is a real code-quality/security gap independent of how often the zero state occurs, matching the "should return a safe value instead of relying on a runtime check that never executes" pattern in the source report.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` (and the analogous bandwidth calculation) with an explicit runtime check that returns `0` (or otherwise safely short-circuits) when `totalEnergyWeight <= 0`, consistent with the guard already present in `EnergyProcessor.calculateGlobalEnergyLimitV2`.

### Proof of Concept
Not independently executed against a live node; based on static code review of: [1](#0-0) 
On a node state where `DynamicPropertiesStore.getTotalEnergyWeight() == 0` and an account has `getAllFrozenBalanceForEnergy() >= TRX_PRECISION`, invoking any contract-call transaction that triggers `calculateGlobalEnergyLimit` for that account would either throw `ArithmeticException` (hardened path) or return `Long.MAX_VALUE` (legacy double path), as derived from the arithmetic shown above.
