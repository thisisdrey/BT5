Audit Report

## Title
Bounty and child-bounty payout transfers rely on `debug_assert!` instead of checked results, allowing state to advance to "Claimed"/removed even when the payout transfer silently fails - ([File: substrate/frame/child-bounties/src/lib.rs])

## Summary
`claim_child_bounty()` in `pallet-child-bounties` and `claim_bounty()` in `pallet-bounties` perform curator-fee and beneficiary payout transfers via `T::Currency::transfer`, but only validate the resulting `DispatchResult` with `debug_assert!`, which compiles to a no-op in release builds. This lets the extrinsic unconditionally proceed to emit the "claimed" event and permanently delete the bounty/child-bounty storage record even if the underlying transfer failed, stranding funds in the now-untracked sovereign sub-account.

## Finding Description
In `claim_child_bounty()`, the curator-fee transfer and beneficiary transfer are checked only via `debug_assert!(fee_transfer_result.is_ok())` and `debug_assert!(payout_transfer_result.is_ok())` [1](#0-0) . Regardless of the outcome, the function proceeds to emit `Event::Claimed`, decrement `ParentChildBounties`, remove `ChildBountyDescriptionsV1`, and set `*maybe_child_bounty = None`, deleting the on-chain record [2](#0-1) .

The identical pattern exists in `claim_bounty()` of the parent `pallet-bounties`, where `res.is_ok()` for both the curator-fee and beneficiary transfers is checked only with `debug_assert!` before `*maybe_bounty = None` deletes the bounty record and `Event::BountyClaimed` is emitted [3](#0-2) .

`debug_assert!` expands to a no-op when `cfg(debug_assertions)` is disabled, which is the default for release-profile builds used for production runtime binaries. Because `curator_fee`/`payout` amounts are computed from the sub-account's own `free_balance`, most transfers succeed, but the transfer's success also depends on the *receiver* satisfying the Existential Deposit requirement when the destination account does not already exist — a condition not fully guarded by the "should not fail" comments and not checked at all in code. If the transfer to a fresh beneficiary or curator account fails for such a reason (or any other `Currency` implementation edge case), the claim logic still deletes the bounty record and reports it as paid.

## Impact Explanation
This corresponds to "permanent user-fund lock" and "duplicate/incorrect settlement": the payout amount remains stuck in `child_bounty_account_id`/`bounty_account_id`, which becomes unreachable once the bounty index is reaped from storage, while `Event::Claimed`/`Event::BountyClaimed` and the deleted storage falsely record the payout as delivered to `beneficiary`. There is no other code path capable of retrying or recovering the funds because the bounty record no longer exists.

## Likelihood Explanation
Likelihood is low-to-moderate: an unprivileged, already-signed caller can invoke the permissionless `claim_bounty`/`claim_child_bounty` extrinsics once a bounty reaches `PendingPayout`, with no special privilege required to trigger the code path. However, actually causing `T::Currency::transfer` to fail requires specific preconditions (e.g., ED/hold/freeze interactions on the receiver, or a non-standard `Currency` implementation), so it is not guaranteed but is realistically reachable in production builds where `debug_assert!` is compiled out.

## Recommendation
Replace `debug_assert!(result.is_ok())` with proper error propagation (`?` or `ensure!`) for the curator-fee and beneficiary transfers in both `claim_bounty()` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty()` (`substrate/frame/child-bounties/src/lib.rs`), so a failed transfer aborts the extrinsic via the `try_mutate_exists` closure instead of allowing the bounty state to advance to "claimed"/removed.

## Proof of Concept
1. Configure a runtime with `pallet-child-bounties::Config::Currency` (or `pallet-bounties`) such that `T::Currency::transfer` can return `Err` for the specific beneficiary/amount reached in `claim_child_bounty` — e.g., a payout amount below the Existential Deposit sent to a beneficiary account that does not yet exist.
2. Progress a child bounty through `add_child_bounty` → `propose_curator` → `accept_curator` → `award_child_bounty` to reach `ChildBountyStatus::PendingPayout`.
3. Build the runtime in release mode (`debug_assertions` disabled), wait for `unlock_at`, then call `claim_child_bounty(origin, parent_bounty_id, child_bounty_id)` as any signed account.
4. Observe that despite `T::Currency::transfer` returning `Err`, `Event::Claimed` is emitted, `ParentChildBounties` is decremented, `ChildBountyDescriptionsV1` is removed, and `*maybe_child_bounty = None` — while `payout` remains stuck in `child_bounty_account_id` with no remaining bounty record to retry or recover the funds.
