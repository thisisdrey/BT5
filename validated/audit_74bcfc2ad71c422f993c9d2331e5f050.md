### Title
Missing slippage / minimum-output protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables sandwich-attack fund loss for exchange liquidity providers - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
java-tron's built-in Bancor-style TRX/TRC10 exchange module supports `ExchangeInjectContract` (add liquidity) and `ExchangeWithdrawContract` (remove liquidity), but unlike `ExchangeTransactionContract` (a plain trade), neither of these two contracts carries a user-specified minimum/expected-amount field. This is the exact bug class described in the external report: a Uniswap-style AMM operation ("addLiquidity") that computes counter-token amounts from live pool reserves with no caller-supplied slippage bound, making it exploitable via front-running/sandwich attacks.

### Finding Description
`ExchangeTransactionContract` explicitly includes an `expected` field used as a slippage floor: [1](#0-0) 
and this is enforced in `ExchangeTransactionActuator.doValidate()`: [2](#0-1) 

By contrast, `ExchangeInjectContract` and `ExchangeWithdrawContract` only carry `token_id` and `quant` — no minimum/expected counter-token amount: [3](#0-2) 

In `ExchangeInjectActuator`, the amount of the "other" token that the liquidity provider must simultaneously deposit (`anotherTokenQuant`) is derived purely from the exchange's *current* on-chain reserve ratio at validate/execute time: [4](#0-3) 
There is no caller-supplied bound comparable to Uniswap's `amountAMin`/`amountBMin`, so the provider cannot cap how much of the paired asset they are forced to give up if the pool ratio moves between transaction construction/signing and inclusion in a block.

Similarly, `ExchangeWithdrawActuator` computes the counter-token amount to return on withdrawal from live reserves, with only a rounding/"precision" sanity check (`Not precise enough`) rather than a genuine slippage/minimum-received check: [5](#0-4) 

Because any account can create its own exchange pair (via `ExchangeCreateContract`) and then act as the liquidity-provider/creator issuing `ExchangeInjectContract`/`ExchangeWithdrawContract` transactions, and any unprivileged account can submit `ExchangeTransactionContract` trades against that same pool, an attacker observing a pending inject/withdraw transaction (or simply racing transaction ordering within a block) can execute trades immediately before it to shift the reserve ratio, causing the victim's inject/withdraw to execute at a manipulated price — analogous to a Uniswap sandwich attack on `addLiquidity`.

### Impact Explanation
A liquidity provider using `ExchangeInjectActuator` can be forced to deposit an inflated amount of the counter asset (effectively donating value to the attacker who reverses their manipulating trade afterward), or a withdrawing provider can receive a reduced counter-asset payout — both represent a direct, unauthorized transfer of value away from the victim account without any code path to bound acceptable slippage. This is a concrete fund-loss vector reachable purely through ordinary signed transactions (`ExchangeInjectContract`, `ExchangeWithdrawContract`, `ExchangeTransactionContract`), fitting the "unauthorized account operation / theft of funds" category.

### Likelihood Explanation
Exploitation requires the attacker to have TRX/tokens to trade against the target pool and to get a trade transaction ordered immediately before the victim's inject/withdraw transaction (e.g., via mempool visibility or same-block ordering influence). This is realistic for any actively used exchange pair since transaction ordering within a block is determined by the block producer / natural mempool propagation, and no cryptographic commitment prevents reordering. The precision check in withdraw only guards against rounding loss, not price manipulation, so it provides no real protection.

### Recommendation
Add explicit minimum/expected-amount fields to `ExchangeInjectContract` and `ExchangeWithdrawContract` (analogous to `expected` in `ExchangeTransactionContract`), and enforce them in `ExchangeInjectActuator.doValidate()`/`ExchangeWithdrawActuator.doValidate()` by rejecting the operation if the computed counter-token amount is less favorable than the caller-specified bound (e.g., `anotherTokenQuant` below/above a caller-supplied min/max). This mirrors Uniswap's `amountAMin`/`amountBMin` pattern and closes the sandwich-attack window for liquidity operations.

### Proof of Concept
1. Attacker monitors the mempool/blocks for a pending `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction from a victim liquidity provider on exchange `X` (first/second token reserves `R1`/`R2`).
2. Attacker submits an `ExchangeTransactionContract` trade against `X` that shifts `R1`/`R2` significantly in one direction, timed to execute immediately before the victim's inject/withdraw transaction in the same or an earlier block position.
3. The victim's `ExchangeInjectActuator`/`ExchangeWithdrawActuator` executes using the now-manipulated `firstTokenBalance`/`secondTokenBalance`, computing `anotherTokenQuant` per [6](#0-5)  — since there is no `expected`/minimum bound field on the contract, the actuator cannot reject the unfavorable rate, and the victim's transaction succeeds at a worse-than-intended price.
4. Attacker reverses their initial trade (sell back) after the victim's tx lands, extracting the value difference — a classic sandwich, exactly as described in the analog Uniswap report but here reachable through java-tron's own exchange actuators.
