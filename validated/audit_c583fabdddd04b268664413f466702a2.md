### Title
Attacker-controlled array-length header in TVM multisig precompiles causes unbounded memory allocation / DoS - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts (addresses `0x9` and `0xa`) decode ABI-encoded array lengths from attacker-controlled contract call data and use them directly to size Java arrays (`new byte[len][]`) *before* validating that the calldata actually contains that many elements. This mirrors the reported Nerdbank.MessagePack pattern: an untrusted "declared count" header field drives an eager allocation, producing memory amplification / potential `OutOfMemoryError` from a small payload.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` each read a count word directly from the decoded `DataWord[]` array (itself derived from raw calldata) and immediately allocate an array of that size: [1](#0-0)

These are invoked from the `BatchValidateSign.doExecute` and `ValidateMultiSign.execute` precompiles, which are reachable from any TVM `CALL`/`STATICCALL` to precompiled addresses `0x9`/`0xa` — i.e., from any signed `TriggerSmartContract` transaction that calls a contract making such a call: [2](#0-1) [3](#0-2) 

The bound check that limits `len` (`MAX_SIZE` = 16 for `BatchValidateSign`, 5 for `ValidateMultiSign`) is only performed when the chain has activated `VMConfig.allowTvmSelfdestructRestriction()`: [4](#0-3) [5](#0-4) 

When that hard-fork flag is not active (or on any network/version where it has not been enabled), `extractBytesArray`/`extractSigArray`/`extractBytes32Array` are called with `len` taken straight from `intValueSafe()`, which can be as large as `Integer.MAX_VALUE` for a 32-byte word encoding a huge value, before a single element is validated against the actual calldata length. This is the same pattern as the reported vulnerability class: header-declared element count drives array allocation ahead of validating the payload actually contains that many elements, enabling memory amplification with a small, cheap payload (a single ABI-encoded 32-byte word can declare an enormous element count).

### Impact Explanation
A malicious contract deployer or caller can craft calldata for a `CALL`/`STATICCALL` to precompile `0x9` or `0xa` with a length word set to a very large value. This forces the node to attempt allocating an array of that size (`new byte[len][]`), which can throw `OutOfMemoryError` or induce severe GC pressure on the executing node, causing that node to slow down, stall, or crash — a node-crash/halt / availability impact reachable from a single unprivileged transaction. Because energy metering for these precompiles (`getEnergyForData`) is based on the raw calldata length rather than the decoded array length, the energy cost charged does not correspond to the attempted allocation size, so the attacker pays for a small calldata blob while forcing a large allocation attempt.

### Likelihood Explanation
Likelihood is moderate-to-high: reaching this code only requires deploying/calling a contract that issues a `CALL`/`STATICCALL` to precompiled address `0x9` or `0xa` with crafted calldata — no special privileges, and it is directly reachable via `TriggerSmartContract`. Exploitability depends on whether `allowTvmSelfdestructRestriction` (a chain-parameter-gated hard fork) is active on the target network; where it is not yet active, the bound check is skipped entirely.

### Recommendation
- Validate the decoded array-length word against a hard maximum (e.g., `MAX_SIZE`) and against the actual remaining calldata length *before* allocating `bytesArray`/`bytes32Array`, unconditionally (not gated behind `allowTvmSelfdestructRestriction`).
- Reject with `Pair.of(true, DATA_FALSE)` (or `false, EMPTY_BYTE_ARRAY` under `allowTvmOsaka`) whenever the declared count exceeds what the calldata can actually contain, mirroring the `isValidAbiEncoding` bounds checks already used elsewhere in this file.
- Consider deriving the effective array bound from `data.length` (as is already done for `isValidAbiEncoding`) prior to calling `extractBytesArray`/`extractSigArray`/`extractBytes32Array`.

### Proof of Concept
1. Construct calldata for `batchvalidatesign(bytes32,bytes[],address[])` where the `bytes[]` offset word points to a length field encoding a very large value (e.g., `0x7FFFFFFF`), while the rest of the calldata is minimal (a few hundred bytes).
2. On a network where `allowTvmSelfdestructRestriction` has not been activated, call precompile `0x9` (`BatchValidateSign`) via `TriggerSmartContract` with this calldata.
3. `doExecute` calls `extractBytesArray(words, offset, data)` (or `extractBytes32Array` for the `address[]` argument), which executes `int len = words[offset].intValueSafe(); byte[][] bytesArray = new byte[len][];` — attempting to allocate an array with ~2^31 reference slots (~16 GB on a 64-bit JVM) from a payload of only a few hundred bytes, causing `OutOfMemoryError`/severe GC pressure on the node executing the transaction.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
