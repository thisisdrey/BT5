### Title
Attachment content is stored and resolved without verifying it hashes to the requested `content_hash`, allowing attachment/BNS mismatch - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` inserts any `Attachment` returned by a peer for a `GET /v2/attachments/<content_hash>` request without ever checking that the returned `Attachment.content`'s hash equals the requested `content_hash`. This lets a malicious/compromised peer supply arbitrary content that gets treated as if it resolved the legitimately committed attachment, while the real committed attachment for that hash is never resolved by this node.

### Finding Description
`AttachmentRequest::make_request_type` builds a GET request keyed by `self.content_hash` (`stackslib/src/net/atlas/download.rs:1104-1119`). When the batched HTTP response comes back, `extend_with_attachments` decodes it and unconditionally inserts the returned attachment: [1](#0-0) 

There is no comparison of `response.attachment.hash()` against `request.content_hash` anywhere in this function — the response is trusted purely because it deserialized successfully (`decode_atlas_get_attachment()` succeeded), not because its content matches what was asked for. The only correctness property enforced elsewhere in the system (`AttachmentsBatch::resolve_attachment`, `stackslib/src/net/atlas/download.rs:1227-1238`) removes a missing-attachment entry from `attachments_instances` by comparing the attachment's *own* computed hash (`attachment.hash()`) against the tracked committed `content_hash` — but this comparison happens against whatever hash the *attacker's* bytes happen to produce (C2), not against the originally requested `content_hash` (C1). Since `extend_with_attachments` never validated C2 == C1 at ingestion time, resolution proceeds using the wrong (attacker-controlled) hash.

The attacker's exact message: run/control a peer that the victim's `AttachmentsBatchStateMachine::DownloadingAttachment` phase queries; when the victim asks for `/v2/attachments/<C1>`, respond `200 OK` with a `GetAttachmentResponse` whose `Attachment.content` bytes hash to `C2 != C1`. `extend_with_attachments` will accept and store this into `self.attachments`, and downstream logic will attempt to resolve/insert under `C2`, never satisfying the pending requirement for `C1`.

### Impact Explanation
The legitimate, on-chain-committed attachment for `content_hash = C1` is never resolved on this node even though an honest peer could have supplied it, because the batch/retry bookkeeping treats the request as "answered" (successful request bump) with mismatched content. Junk attacker-controlled content is persisted into `AtlasDB` via `insert_instantiated_attachment` keyed by the wrong hash `C2`, with no matching `AttachmentInstance` (on-chain commitment) for `C2`. This is exactly the "attachment/BNS mismatch" / "serving non-canonical state as canonical" category called out as High impact: a node ends up believing it has serviced/attempted the download while actually storing unrelated, non-committed data and permanently failing to resolve the real committed attachment through this code path.

### Likelihood Explanation
Any remote, unprivileged party that a victim node contacts as an atlas peer for attachment downloads (which is normal peer behavior — no secret, no signature, no privileged role needed) can trigger this by simply serving a crafted `GetAttachmentResponse` on its own RPC port. It requires no bandwidth flooding, no protocol-level auth bypass, and is fully repeatable per requested `content_hash`, since nothing in `extend_with_attachments` or the later resolve path re-validates content against the original request.

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`), after decoding the response, compute `response.attachment.hash()` and compare it against `request.content_hash` before inserting into `self.attachments` and before crediting the peer's reliability report. On mismatch, treat it as a failed request (`report.bump_failed_requests()`) and do not insert the attachment, so mismatched content can never reach `AtlasDB::insert_instantiated_attachment` or falsely satisfy `AttachmentsBatch::resolve_attachment`.

4. Assert: `self.attachments` contains an `Attachment` with hash `C2` (proving insertion happened without validation) — reachable via `extend_with_attachments` at `stackslib/src/net/atlas/download.rs:547-549`.

Feed this context through `AttachmentsDownloader::run_batch`'s resolution step calling `attachments_batch.resolve_attachment(&attachment.hash())` (`download.rs:1227-1238`) and assert the batch's `attachments_instances` entry for C1 remains present/unresolved, while `AtlasDB` (via `insert_instantiated_attachment`, `atlas/db.rs:576-592`) contains a row keyed by C2 with `was_instantiated=1` and no corresponding `attachment_instances` row for C2.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
