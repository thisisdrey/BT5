### Title
Unguarded division by `totalEnergyWeight`/`totalNetWeight` in resource-limit calculation causes uncaught `ArithmeticException` node crash - ([File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java])

### Summary
Analogous to CVE-2015-6855 (QEMU IDE code performing a division using an attacker-influenced value without validating it is non-zero, causing a divide-by-zero crash), `RepositoryImpl.calculateGlobalEnergyLimit()` divides by `totalEnergyWeight` while relying only on a Java `assert` statement to guarantee it is non-zero. Java assertions are disabled by default in production JVMs (no `-ea` flag), so this "guard" is a no-op at runtime.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()` computes a node's energy limit from global chain parameters: [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
  long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
  if (frozeBalance < TRX_PRECISION) {
    return 0;
  }
  long energyWeight = frozeBalance / TRX_PRECISION;
  long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
  long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

  assert totalEnergyWeight > 0;

  if (hardenResourceCalculation()) {
    return BigInteger.valueOf(energyWeight)
        .multiply(BigInteger.valueOf(totalEnergyLimit))
        .divide(BigInteger.valueOf(totalEnergyWeight))
        .longValueExact();
  }
  return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

Unlike the equivalent legacy path in `chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java`, which explicitly short-circuits with `if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) { return 0; }` before falling back to the same bare `assert`, and unlike `calculateGlobalEnergyLimitV2()` in the same class which unconditionally checks `if (totalEnergyWeight == 0) { return 0; }`, the actuator/VM-side `RepositoryImpl.calculateGlobalEnergyLimit()` has **no runtime check at all** — only the disabled `assert`. [2](#0-1) 

If `totalEnergyWeight` (the dynamic property tracking total frozen-for-energy stake across the network) is ever `0` — e.g. on a freshly-initialized network/private chain before any account has frozen TRX for energy, or transiently if all energy-freeze positions are withdrawn — this method will:
- Throw a raw `ArithmeticException: / by zero` in the `hardenResourceCalculation()` (BigInteger) branch, or
- Produce `NaN`/silently corrupt results in the legacy double-arithmetic branch (`totalEnergyLimit / 0` as a double is `Infinity`, and `energyWeight * Infinity` propagates `Infinity`/`NaN` into a `long` cast, giving `Long.MAX_VALUE` — an unbacked, effectively unlimited energy grant).

This function is on the TVM contract-execution path (used by `VMActuator`/`ContractState`), meaning it is invoked whenever a transaction interacts with the VM's resource accounting, making it reachable from an ordinary signed transaction/contract call.

### Impact Explanation
Two divergent failure modes both map to accepted impact classes:
1. **Node crash / denial of service** — an uncaught `ArithmeticException` propagating out of block/transaction processing halts transaction execution for the node (crash analog to the CVE).
2. **Unbacked resource grant** — in the non-hardened (legacy double math) branch, division by zero yields `Infinity`/`NaN`, which truncates to `Long.MAX_VALUE` when cast to `long`, granting an account an unlimited/unbacked energy limit — effectively free, unbounded contract execution capacity, undermining the energy-metering economic model.

### Likelihood Explanation
This requires `totalEnergyWeight` (a `DynamicPropertiesStore` value tracking sum of all energy-frozen stake) to reach zero. On established mainnet this is unlikely under normal steady-state conditions, but is plausible on freshly bootstrapped/private/side chains before any freeze-for-energy has occurred, or transiently during specific migration/parameter states, since only an `assert` (disabled in production) protects this divide. The trigger condition is a chain-state condition rather than attacker-crafted transaction data, which limits likelihood on mature mainnet deployments but the missing production guard itself is a code defect analogous to the reported CVE class.

### Recommendation
Add an explicit runtime guard (not an `assert`) in `RepositoryImpl.calculateGlobalEnergyLimit()` mirroring `calculateGlobalEnergyLimitV2()`:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
before performing either the BigInteger or double division, and audit `RepositoryImpl.usageToBalance()`/other sibling methods in the same file for the same disabled-assert pattern. [3](#0-2) 

### Proof of Concept
1. Deploy/operate a java-tron node where `totalEnergyWeight` dynamic property is `0` (e.g., a freshly initialized private/test network before any `FreezeBalanceV2Contract` for `ENERGY` has been broadcast).
2. Have any account with `frozeBalance >= TRX_PRECISION` for energy (achievable once at least one freeze exists elsewhere while weight bookkeeping is transiently zero, or via the initial genesis window) trigger a TVM contract call so that `VMActuator`/`ContractState` invokes `RepositoryImpl.calculateGlobalEnergyLimit()`.
3. With `hardenResourceCalculation()` enabled, the `BigInteger.divide(BigInteger.valueOf(0))` call throws `ArithmeticException`, propagating out of transaction processing.
4. With `hardenResourceCalculation()` disabled, the double-division yields `Infinity`, and the subsequent `(long)` cast yields `Long.MAX_VALUE`, granting the account an unbacked, unlimited energy limit for that call.

    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;

    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
