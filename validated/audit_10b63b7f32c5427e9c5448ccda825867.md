### Title
Unrestricted `Operator.execute` lets any caller spend ERC20 approvals granted to `Operator` - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` is a publicly reachable arbitrary multicall that invokes attacker-selected target contracts and calldata while `msg.sender` remains the `Operator` contract. Consequently, any ERC20 allowance `victim -> Operator` can be consumed by an attacker through `token.transferFrom(victim, attacker, amount)`, resulting in direct theft of approved user assets. This is the same reachable bug class as the Seneca approval-draining vulnerability: arbitrary calldata executed from a contract that users may have approved.

### Finding Description
`execute` accepts an unrestricted list of `Call` structs and has no target whitelist, selector restrictions, or per-call sender authorization. [1](#0-0)  Each supplied call is forwarded with `target.call{value: value}(callData)`, so the token observes `Operator`, not the external caller, as `msg.sender`. [2](#0-1) [3](#0-2) 

The `setMsgSender` modifier only stores the external caller in Operator’s transient slot for Metronome’s `SynthContext` consumers. [4](#0-3)  Ordinary ERC20 contracts do not call `getActualMsgSender`, so this mechanism does not translate the token call into the attacker’s identity or protect allowances held by `Operator`. [5](#0-4) 

Normal Metronome collateral deposits approve the `DepositToken`, which pulls collateral from the resolved user, not `Operator`. [6](#0-5)  The tests confirm this approval model by approving `msdUSDC` before routing the deposit through `Operator`. [7](#0-6)  Therefore, `Operator` does not need token approvals for its intended deposit path, but can spend them if users ever grant them.

The deployed mainnet `Operator` is a production contract at `0xc06D6347915f6B5e9dBB53Fe17B988b99DbaD360`. [8](#0-7) 

### Impact Explanation
An unprivileged attacker can steal the full approved balance of any ERC20 token where `allowance[victim][Operator] > 0` and the victim retains a transferable balance. A single `execute` transaction can batch calls across multiple tokens and victims, draining all available allowances atomically.

This breaks the allowance ownership invariant: authorization granted to the `Operator` contract can be exercised by any arbitrary caller, rather than only by the account whose action is being relayed. The direct impact is theft of user-held ERC20 assets outside the protocol, including collateral tokens, stablecoins, and other wallet assets approved to `Operator`.

### Likelihood Explanation
Likelihood is conditional on users holding active allowances to `Operator`, but exploitation requires no privileged role, malformed oracle data, protocol state, or reentrancy. The attacker only calls the public `execute` function with attacker-chosen calldata.

Metronome’s intended deposit flow does not require approval to `Operator`, which reduces exposure, but it does not eliminate it. Users may approve `Operator` through mistaken frontend flows, phishing-like transactions, compatibility assumptions, or prior integrations. Once such allowances exist, theft is deterministic and can be performed in one transaction.

`nonReentrant` does not mitigate the issue because there is no need to reenter `execute`. [9](#0-8)  Pool pause and shutdown flags also do not protect arbitrary external ERC20 calls because they are enforced inside Metronome functions such as `DepositToken.deposit`, not by `Operator` before forwarding calls. [10](#0-9) 

### Recommendation
Do not expose unrestricted contract calls from an approval-bearing execution contract.

Prefer replacing `execute` with explicit typed operations for supported Metronome actions. If arbitrary batching is required:

- Restrict `target` to an explicit whitelist of Metronome contracts that implement `SynthContext`.
- Restrict function selectors for each target and exclude all direct ERC20 targets, including Metronome token addresses unless their `SynthContext` behavior is intentionally required.
- Ensure the `Operator` contract is never used as an ERC20 spender and instruct users/integrations to approve only the relevant `DepositToken` or gateway.
- Emit clear documentation and UI warnings that no token approval should ever be granted to `Operator`.
- Add regression tests proving that a caller cannot consume another account’s ERC20 allowance through `Operator.execute`.

### Proof of Concept
The following Hardhat fork-style test can be placed in `test/Operator.test.ts` alongside the existing fork tests. It demonstrates that a victim’s approval to `Operator` can be spent by an unrelated attacker.

```ts
import {expect} from 'chai'
import {parseUnits} from '@ethersproject/units'
import {ethers, deployments} from 'hardhat'
import {setTokenBalance, enableForking} from './helpers'
import Address from '../helpers/address'
import {IOperator} from '../typechain/Operator'

describe('Operator allowance drain', function () {
  before(enableForking)

  it('lets an attacker spend ERC20 approvals granted to Operator', async function () {
    const [, victim, attacker] = await ethers.getSigners()

    const operatorFactory = await ethers.getContractFactory('Operator')
    const operator = await operatorFactory.deploy()

    const usdc = await ethers.getContractAt('ERC20', Address.USDC_ADDRESS, victim)
    const amount = parseUnits('1,000', 6)

    await setTokenBalance(usdc.address, victim.address, amount)

    // Vulnerable precondition: an ERC20 allowance victim -> Operator exists.
    await usdc.connect(victim).approve(operator.address, amount)

    const calls: IOperator.CallStruct[] = [
      {
        target: usdc.address,
        value: 0,
        callData: usdc.interface.encodeFunctionData('transferFrom', [
          victim.address,
          attacker.address,
          amount,
        ]),
      },
    ]

    // Attacker is unrelated to victim and supplies arbitrary target/calldata.
    await operator.connect(attacker).execute(calls)

    expect(await usdc.balanceOf(attacker.address)).eq(amount)
    expect(await usdc.balanceOf(victim.address)).eq(0)
    expect(await usdc.allowance(victim.address, operator.address)).eq(0)
  })
})
```

The invariant failure is direct: `token.transferFrom` sees `msg.sender == Operator`, while the initiator is `attacker`. Therefore the attacker can consume the victim’s allowance to `Operator` without signature, consent, or additional authorization.
