### Title
Missing minimum-output protection in `VesperGateway.deposit` exposes users to vault-share exchange-rate slippage - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` converts a user-supplied amount of a Vesper vault's underlying asset into vault shares and then deposits all resulting shares into Metronome, but accepts no minimum share or deposit-token amount. [1](#0-0)  Because the amount of `vToken` shares minted is measured only after the external `vToken_.deposit(amount_)` call, an unfavorable change in the Vesper vault's share exchange rate between simulation and execution directly reduces the user's resulting Metronome collateral. [2](#0-1) 

### Finding Description
The public `deposit(IPool pool_, IVPool vToken_, uint256 amount_)` function first pulls `amount_` underlying from the caller. [3](#0-2)  It then approves and calls the attacker-influenceable external vault through `vToken_.deposit(amount_)` and calculates the share amount using a balance delta. [4](#0-3)  Finally, it deposits whatever share amount was received into the configured Metronome `DepositToken`, without checking `minVTokenAmount` or `minDeposited`. [5](#0-4) 

A user can therefore obtain a quote or UI simulation at exchange rate `R`, submit a deposit, and have a transaction preceding it change the vault's effective exchange rate to `R' < R`. The call still succeeds and mints the lower amount of `msdToken`, rather than reverting. [6](#0-5)  This is the same bug class as an issuance function whose minted output depends on a mutable external scale and has no caller-defined minimum output. [1](#0-0) 

### Impact Explanation
Users can receive materially less collateral than expected while still paying the full `amount_` of underlying. [7](#0-6)  Since those `msdToken` shares determine the collateral credited to the user through `DepositToken.deposit`, a lower `vToken` output is a direct loss of collateral position value. [8](#0-7) 

The gateway does provide enough caller input to make this attack surface reachable: the caller selects the registered `pool_`, the Vesper `vToken_`, and the exact underlying `amount_`, while the output amount is determined entirely by mutable external vault state. [1](#0-0) 

### Likelihood Explanation
Yield-vault share prices are not static and can move when vault accounting, yield realization, losses, donations reflected in vault valuation, or other transactions are processed before the user's transaction. [4](#0-3)  The function's registered-pool check prevents arbitrary unrelated pools, but it does not constrain the exchange rate returned by an otherwise valid Vesper vault. [9](#0-8) 

No existing modifier enforces output bounds: this entry point has no `nonReentrant` modifier and checks only pool registration; the later `DepositToken.deposit` checks nonzero input, beneficiary, pause status, and reentrancy, but not the economic adequacy of the received amount. [1](#0-0) [10](#0-9) 

### Recommendation
Add explicit slippage parameters to the gateway API, such as `uint256 minVTokenAmount_` and optionally `uint256 minDepositAmount_`. [1](#0-0)  Revert when the measured `vToken` delta or the `_deposited` result returned by `DepositToken.deposit` is below the caller's bound. [6](#0-5) [11](#0-10) 

For example:

```solidity
uint256 _vTokenAmount = vToken_.balanceOf(address(this)) - _balanceBefore;
if (_vTokenAmount < minVTokenAmount_) revert SlippageTooHigh();

(uint256 _deposited, ) = _depositToken.deposit(_vTokenAmount, _msgSender);
if (_deposited < minDepositAmount_) revert SlippageTooHigh();
```

### Proof of Concept
A Foundry fork test can reproduce the issue by executing the two semantically identical deposits around an exchange-rate change and showing that both succeed while the second receives less collateral:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";
import {IVPool} from "../contracts/interfaces/external/IVPool.sol";
import {IPool} from "../contracts/interfaces/IPool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IVesperGateway} from "../contracts/interfaces/IVesperGateway.sol";

contract VesperGatewaySlippageTest is Test {
    IVesperGateway gateway = IVesperGateway(vm.envAddress("VESPER_GATEWAY"));
    IPool pool = IPool(vm.envAddress("METRONOME_POOL"));
    IVPool vToken = IVPool(vm.envAddress("VESPER_VTOKEN"));

    function testDepositHasNoMinimumOutput() public {
        IERC20 underlying = IERC20(vToken.token());
        IDepositToken depositToken = pool.depositTokenOf(underlying);

        address alice = makeAddr("alice");
        address rateChanger = makeAddr("rate-changer");
        uint256 amount = 100 * 10 ** underlying.decimals();

        deal(address(underlying), alice, amount * 2);
        deal(address(underlying), rateChanger, amount * 1_000);

        uint256 sharesBefore = vToken.totalSupply();
        uint256 underlyingBefore = underlying.balanceOf(address(vToken));

        vm.startPrank(alice);
        underlying.approve(address(gateway), type(uint256).max);
        gateway.deposit(pool, vToken, amount);
        uint256 firstCollateral = depositToken.balanceOf(alice);
        vm.stopPrank();

        // Represent any legitimate preceding vault transaction that worsens the
        // exchange rate. On a fork this can be replaced by the concrete Vesper
        // interaction/donation recognized by the target vault's total-assets logic.
        vm.prank(rateChanger);
        underlying.transfer(address(vToken), amount * 100);

        require(
            underlying.balanceOf(address(vToken)) > underlyingBefore ||
            vToken.totalSupply() == sharesBefore,
            "exchange-rate setup failed"
        );

        vm.prank(alice);
        gateway.deposit(pool, vToken, amount);
        uint256 secondCollateral = depositToken.balanceOf(alice) - firstCollateral;

        assertLt(secondCollateral, firstCollateral);
    }
}
```

The essential assertion is that `gateway.deposit` succeeds after the vault conversion rate worsens because there is no caller-specified minimum; adding a `minVTokenAmount_` bound equal to the originally quoted amount would make the second call revert instead of crediting less collateral. [2](#0-1)
