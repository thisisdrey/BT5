Confirmed: `WITHDRAWREWARD` (opcode `0xd9`) is a standard TVM opcode reachable by any smart contract's bytecode, wired through `OperationRegistry`/`OperationActions` to `Program.withdrawReward()`, which invokes `WithdrawRewardProcessor`. This mirrors the report's bug class: a cooldown/restriction enforced on one entry point but silently skippable via another equivalent entry point.

### Title
Vote-reward withdrawal cooldown (24h) is enforced in `WithdrawBalanceActuator` but bypassed via the TVM `WITHDRAWREWARD` opcode - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/WithdrawRewardProcessor.java)

### Summary
`WithdrawBalanceContract`, executed by `WithdrawBalanceActuator`, is the normal transaction path for a witness/voter to withdraw accumulated voting rewards (`allowance`). It enforces a 24‑hour cooldown (`witnessAllowanceFrozenTime * FROZEN_PERIOD`) between withdrawals via `accountCapsule.getLatestWithdrawTime()`. The same reward-withdrawal logic is also exposed to smart contracts through the TVM opcode `WITHDRAWREWARD` (`0xd9`), which is dispatched to `Program.withdrawReward()` and ultimately `WithdrawRewardProcessor.validate()`/`execute()`. That processor's `validate()` method only checks the "guard representative" restriction and omits the cooldown check entirely.

### Finding Description
`WithdrawBalanceActuator.validate()` enforces:
```java
long latestWithdrawTime = accountCapsule.getLatestWithdrawTime();
long now = dynamicStore.getLatestBlockHeaderTimestamp();
long witnessAllowanceFrozenTime = dynamicStore.getWitnessAllowanceFrozenTime() * FROZEN_PERIOD;

if (now - latestWithdrawTime < witnessAllowanceFrozenTime) {
  throw new ContractValidateException("The last withdraw time is "
      + latestWithdrawTime + ", less than 24 hours");
}
``` [1](#0-0) 

`WithdrawRewardProcessor.validate()`, invoked from the TVM `WITHDRAWREWARD` opcode via `Program.withdrawReward()`, performs no such check — it only validates that the caller is not a genesis guard representative: [2](#0-1) 

`Program.withdrawReward()` (reachable from any deployed smart contract's bytecode executing the `WITHDRAWREWARD` opcode) directly calls this processor and commits the state change: [3](#0-2) 

The `WITHDRAWREWARD` opcode is a registered, publicly reachable TVM instruction: [4](#0-3) 

Because a smart contract calling `WITHDRAWREWARD` invokes `WithdrawRewardProcessor` directly (not `WithdrawBalanceActuator`), the 24-hour cooldown restriction that the protocol intends to enforce on reward withdrawals is completely bypassable by wrapping the withdrawal call inside a contract, exactly analogous to the reported issue where `authRedeem()`/`autoRedeem()` skip the pause check enforced elsewhere.

### Impact Explanation
The 24-hour cooldown on reward withdrawal exists to rate-limit/throttle reward extraction (likely tied to reward accrual/distribution assumptions elsewhere in the protocol). An attacker (any account, since the only restriction is not being a genesis witness) can deploy a trivial contract that calls the `WITHDRAWREWARD` opcode repeatedly (once per block/transaction) to withdraw voting rewards without waiting 24 hours between withdrawals, completely circumventing a protocol-enforced restriction on fund movement timing. This does not overdraw the actual `allowance` balance (so it isn't a direct inflation bug), but it defeats an explicit on-chain access-control/timing invariant that other code paths rely on, which the reported pattern classifies as Medium severity (rule/invariant bypass rather than pure economic loss).

### Likelihood Explanation
High likelihood of exploitation once known: any account can trigger it by deploying and calling one contract with the `WITHDRAWREWARD` opcode (e.g., via inline assembly in Solidity or hand-crafted bytecode); no special privileges, timing, or race conditions are required.

### Recommendation
Add the same cooldown check (`latestWithdrawTime` / `witnessAllowanceFrozenTime`) present in `WithdrawBalanceActuator.validate()` to `WithdrawRewardProcessor.validate()`, so both entry points to reward withdrawal enforce identical restrictions.

### Proof of Concept
1. Deploy a minimal contract whose bytecode issues the `WITHDRAWREWARD` opcode (`0xd9`) targeting the caller's own address, calling `Program.withdrawReward()` through `OperationActions`/`OperationRegistry`.
2. Have an account with accrued `allowance` (voting reward) call this contract once to withdraw the reward — `WithdrawRewardProcessor.execute()` sets `allowance` to 0 and moves it to `balance`, updating `latestWithdrawTime`.
3. Wait for new reward to accrue (even seconds later, well under 24 hours) and call the contract again.
4. Compare with attempting the same rapid re-withdraw via a normal `WithdrawBalanceContract` transaction routed through `WithdrawBalanceActuator`, which reverts with `"The last withdraw time is ..., less than 24 hours"` [5](#0-4) ; the TVM opcode path succeeds instead, demonstrating the bypass.

  public void validate(WithdrawRewardParam param, Repository repo) throws ContractValidateException {
    if (repo == null) {
      throw new ContractValidateException(STORE_NOT_EXIST);
    }

    byte[] ownerAddress = param.getOwnerAddress();

    boolean isGP = CommonParameter.getInstance()
        .getGenesisBlock().getWitnesses().stream().anyMatch(witness ->
            Arrays.equals(ownerAddress, witness.getAddress()));
    if (isGP) {
      throw new ContractValidateException(
          ACCOUNT_EXCEPTION_STR + StringUtil.encode58Check(ownerAddress)
              + "] is a guard representative and is not allowed to withdraw Balance");
    }
  }
