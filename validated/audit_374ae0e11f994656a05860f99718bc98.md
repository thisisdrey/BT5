### Title
Front-running FreezeBalance/FreezeBalanceV2 to grief a pending TVM call's energy limit and its `getTotalEnergyLimit` fee/energy calculation - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
The reported bug class is: a value computed as a ratio whose denominator is a globally mutable, permissionlessly-inflatable quantity (`float_` = circulating token supply) is read at the moment an economically important action executes, and any unprivileged user can front-run that action by inflating the denominator, thereby lowering the computed value to the detriment of a third party. The closest reachable analog in java-tron is `EnergyProcessor.calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` (and the bandwidth analog `BandwidthProcessor.calculateGlobalNetLimit`), which compute an account's resource limit as `frozenWeight * totalLimit / totalWeight`. `totalWeight` (`TOTAL_ENERGY_WEIGHT` / `TOTAL_NET_WEIGHT`) is a chain-wide counter that **any account can increase** by simply calling `FreezeBalanceContract`/`FreezeBalanceV2Contract` for as little as 1 TRX, with no cooldown or rate limit on how quickly it can be inflated between blocks.

### Finding Description
`calculateGlobalEnergyLimit` computes the energy an account can spend from its frozen stake as: [1](#0-0) 

and the bandwidth equivalent: [2](#0-1) 

`totalEnergyWeight`/`totalNetWeight` is mutated by every `FreezeBalance`/`FreezeBalanceV2` transaction via `addTotalWeight`, which any address can invoke with a minimal 1‑TRX freeze and virtually no other precondition: [3](#0-2) [4](#0-3) 

This is exactly analogous to the report's `_mint()`-based inflation of `float_`: the denominator of a division that determines a payout/allowance can be inflated by an unrelated, permissionless transaction placed immediately before the transaction that depends on the computed value.

The victim path that consumes this value is `VMActuator.call()`, which computes `energyLimit = getTotalEnergyLimit(...)` (routing through `getAccountEnergyLimitWithFloatRatio` → `RepositoryImpl.calculateGlobalEnergyLimit`, sharing the same `totalEnergyWeight` division) and then builds the `ProgramInvoke` with that `energyLimit` before executing the contract: [5](#0-4) [6](#0-5) 

Because a caller's execution `energyLimit` is fixed once at the start of `call()` using the *current* `totalEnergyWeight`, an attacker can broadcast one or more `FreezeBalanceContract`/`FreezeBalanceV2Contract` transactions in the same block (or the block immediately preceding), ordered right before a target's `TriggerSmartContract` transaction. This inflates `totalEnergyWeight` without changing the victim's own frozen balance, which — per the formula `energyWeight * totalEnergyLimit / totalEnergyWeight` — strictly *decreases* the victim's `energyLimit` for that transaction. The same mechanism reduces `calculateGlobalNetLimit` for bandwidth-funded transactions and reduces the maximum delegatable resource computed in `DelegateResourceActuator.validate()` and `Wallet.calcCanDelegatedEnergyMaxSize`/`calcCanDelegatedBandWidthMaxSize`, which read the same `TotalEnergyWeight`/`TotalNetWeight` values: [7](#0-6) [8](#0-7) 

### Impact Explanation
Reducing a victim's realized `energyLimit`/`netLimit` for a transaction they already signed and broadcast can cause their TVM execution to run out of energy mid-execution (`OUT_OF_ENERGY`), reverting state changes while still burning TRX fee for the energy actually consumed before running out — an unrecoverable loss of funds for the victim caused entirely by an unrelated attacker transaction. It can also cause `DelegateResourceActuator` validations that depend on the momentarily-reduced `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` to reject legitimate delegate/undelegate operations, or make `FreezeBalanceV2`/`DelegateResource` flows behave inconsistently with what the user observed via the API just before submitting their transaction. This matches the "griefing" impact described in the source report (owner receiving less value than expected because a third party manipulated a shared denominator immediately beforehand).

### Likelihood Explanation
`FreezeBalanceContract`/`FreezeBalanceV2Contract` are fully permissionless, require only 1 TRX, have no rate limiting, and their effect on `TotalEnergyWeight`/`TotalNetWeight` is applied unconditionally and immediately in `execute()`. An attacker only needs to observe a pending high-value `TriggerSmartContract` transaction in the mempool and submit a cheap freeze transaction ordered before it (transaction ordering within a block is influenced by fee/energy and broadcast timing, and SRs can also reorder for their own benefit) — an easily automatable, low-cost, unprivileged attack.

### Recommendation
Avoid computing per-transaction energy/bandwidth limits from a globally mutable ratio that can be changed atomically by unrelated transactions in the same block window. Options include: snapshotting `TotalEnergyWeight`/`TotalNetWeight` at the start of block execution and using that snapshot for all transactions within the block, rate-limiting how much a single `FreezeBalance(V2)` transaction can move `TotalEnergyWeight`/`TotalNetWeight` per block, or decoupling the resource-limit denominator from real-time freeze events so it only updates at fixed epoch boundaries (similar to how vote/reward snapshots are epoch-based elsewhere in java-tron).

### Proof of Concept
1. Victim broadcasts a `TriggerSmartContract` transaction `T_v` whose gas-intensive execution relies on frozen-energy-derived `energyLimit` computed via `calculateGlobalEnergyLimit` in `EnergyProcessor.java:145-166`.
2. Attacker observes `T_v` in the mempool and broadcasts `FreezeBalanceContract`/`FreezeBalanceV2Contract` `T_a` (1 TRX minimum) targeting `ENERGY`, ensured to be included/ordered before `T_v` in the same or an earlier block.
3. `T_a` executes `FreezeBalanceActuator.execute()`/`FreezeBalanceV2Processor.execute()`, calling `addTotalWeight`/`repo.addTotalEnergyWeight`, increasing `TOTAL_ENERGY_WEIGHT` (`FreezeBalanceActuator.java:134-150`).
4. When `T_v` executes, `VMActuator.call()` computes `energyLimit = getTotalEnergyLimit(...)` using the now-inflated `totalEnergyWeight` (`VMActuator.java:534-552`, `RepositoryImpl.java:992-1010`), yielding a smaller `energyLimit` than the victim expected when they signed `T_v` based on a prior `getAccountResource` query.
5. If the victim's contract call needed energy close to the previously-expected limit, execution now fails with `OUT_OF_ENERGY`, reverting state but still consuming (burning) the fee for energy used — a loss to the victim caused solely by the attacker's unrelated, low-cost transaction.

  private void addTotalWeight(ResourceCode resourceCode, DynamicPropertiesStore dynamicStore,
                              long frozenBalance, long increment) {
    long weight = dynamicStore.allowNewReward() ? increment : frozenBalance / TRX_PRECISION;
    switch (resourceCode) {
      case BANDWIDTH:
        dynamicStore.addTotalNetWeight(weight);
        break;
      case ENERGY:
        dynamicStore.addTotalEnergyWeight(weight);
        break;
      case TRON_POWER:
        dynamicStore.addTotalTronPowerWeight(weight);
        break;
      default:
        logger.debug("Resource Code Error.");
    }
  }

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
