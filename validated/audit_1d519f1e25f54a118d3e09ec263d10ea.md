### Title
Eager `Vec::with_capacity` for `server_version` length allows amplified allocation beyond `BLOCK_RESPONSE_DATA_MAX_SIZE` in `BlockProposalData::consensus_deserialize` - (File: libsigner/src/events.rs)

### Summary
`BlockProposalData::consensus_deserialize` bounds the outer `inner_bytes` buffer to `BLOCK_RESPONSE_DATA_MAX_SIZE`, but the `server_version: Vec<u8>` sub-field is deserialized via the generic `Vec<u8>` codec, which validates its declared length only against the much larger global `MAX_MESSAGE_LEN` (~16 MiB) and eagerly allocates that capacity before verifying enough bytes actually remain in the buffer. A small wire message can therefore force a transient allocation far larger than the outer cap intends.

### Finding Description
`BlockProposalData::consensus_deserialize` reads `inner_bytes` via `read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)` [1](#0-0) , then wraps this already-fully-received in-memory slice in `inner_reader` and calls `read_next(&mut inner_reader)` to get `server_version: Vec<u8>` [2](#0-1) .

`Vec<u8>::consensus_deserialize` delegates to `read_next_at_most::<R, u8>(fd, u32::MAX)` [3](#0-2) , which calls `read_next_vec` with `max_items = u32::MAX`. Inside `read_next_vec`, the declared length `len` (a 4-byte prefix read from the slice) is checked against `max_items` (u32::MAX — no effective bound) and then against `MAX_MESSAGE_LEN` (~16 MiB) via `mem::size_of::<T>() * len > MAX_MESSAGE_LEN` [4](#0-3) . If it passes, `Vec::with_capacity(len as usize)` is allocated *before* any byte is actually read from the slice [5](#0-4) .

Because `inner_reader` is a finite in-memory slice already bounded to `BLOCK_RESPONSE_DATA_MAX_SIZE`, an attacker can set the `server_version` length prefix (the first 4 bytes of `inner_bytes`) to a large value up to `MAX_MESSAGE_LEN` (~16 MiB), independent of how many bytes actually follow in `inner_bytes`. The loop will fail with an `UnexpectedEof` `ReadError` almost immediately once the slice is exhausted, but the up-front `Vec::with_capacity` call has already requested up to ~16 MiB from the allocator for a message whose real, verified/received length was at most `BLOCK_RESPONSE_DATA_MAX_SIZE`. There is no per-field cap on `server_version` tighter than the generic `MAX_MESSAGE_LEN` check; the outer `read_next_at_most(fd, BLOCK_RESPONSE_DATA_MAX_SIZE)` bound only constrains the *total* `inner_bytes` actually pulled off the wire, not the length any inner sub-field is allowed to *claim*.

Note: I was not able to confirm the exact numeric value of `BLOCK_RESPONSE_DATA_MAX_SIZE` (defined in `libsigner/src/v0/messages.rs`) within the available tool calls, but given its purpose (bounding a version string plus small diagnostic metadata) it is very likely far smaller than `MAX_MESSAGE_LEN` (~16 MiB + preamble), which is the actual effective ceiling enforced on the `server_version` length claim.

### Impact Explanation
Each crafted `BlockProposal`/`BlockProposalData` message that lies about `server_version`'s length causes the receiving signer/node to eagerly allocate up to ~16 MiB of heap before failing deserialization with an error. The wire cost to the attacker is only `BLOCK_RESPONSE_DATA_MAX_SIZE`-bounded (small), while the allocation cost to the victim is amplified toward `MAX_MESSAGE_LEN`. This is a repeatable, bounded-compute/allocation amplification affecting the read/deserialization path for `BlockProposal` (received over StackerDB chunks or the block-proposal endpoint), matching the "bounded compute DoS on a read endpoint" High-impact category. It does not cause unbounded memory growth (each allocation is transient and freed after the error), and it does not forge or store any data — impact is limited to allocator/CPU pressure per message, repeatable across many messages/connections.

### Likelihood Explanation
An unprivileged remote party who can submit a `BlockProposal` (e.g. by owning a StackerDB slot they legitimately hold, or hitting the proposal endpoint) can trigger this with a single, small, well-formed-looking message — no signature bypass or privileged role is needed beyond what's already required to submit a `BlockProposalData` payload at all. The cost per attempt is cheap (a few bytes to declare a lie), and the exploit is trivially repeatable at will, though the overall effect is bounded per-message by `MAX_MESSAGE_LEN`, not unbounded.

### Recommendation
In `read_next_vec` (or specifically for the `server_version` read site), avoid eager `Vec::with_capacity(len)` allocation for attacker-declared lengths before confirming the underlying reader actually has that many bytes remaining (e.g., check against a `Read`-provided remaining-length hint, or grow the vector incrementally instead of pre-allocating the full declared capacity). Additionally, enforce an explicit sub-field bound on `server_version`'s length that is no larger than the remaining bytes in `inner_bytes` (i.e., bounded by `BLOCK_RESPONSE_DATA_MAX_SIZE` minus bytes already consumed), rather than relying on the generic `MAX_MESSAGE_LEN` check.

### Proof of Concept
Rust test in `libsigner`:
1. Construct raw bytes for `BlockProposalData`: `version = 1`, then an `inner_bytes` vector whose declared outer length is small (e.g. 16 bytes, within `BLOCK_RESPONSE_DATA_MAX_SIZE`), but whose first 4 bytes (the `server_version` length prefix) encode a value close to `MAX_MESSAGE_LEN` (e.g. `0x00FF_FFFE`), followed by only a handful of actual trailing bytes.
2. Call `BlockProposalData::consensus_deserialize(&mut &raw_bytes[..])`.
3. Assert that the call returns `Err(CodecError::ReadError(..UnexpectedEof..))` (confirming the eventual failure) while instrumenting/observing (e.g. via a custom global allocator or `Vec::with_capacity` call count/size assertion) that an allocation request of size proportional to the claimed `server_version` length (up to ~16 MiB) occurs at `stacks-common/src/codec/mod.rs:183`, independent of the small actual `inner_bytes` size — i.e., the allocation size scales with the attacker-chosen length prefix rather than with `BLOCK_RESPONSE_DATA_MAX_SIZE` or the real transmitted byte count.
