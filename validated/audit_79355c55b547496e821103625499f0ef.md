### Title
Quarantine-ownership bypass in `ObjectDirectoryPath` via literal `"quarantine"` sentinel - (File: internal/git/localrepo/paths.go)

### Summary
`Repo.ObjectDirectoryPath` decides whether a client-supplied `GitObjectDirectory` (from the `gitalypb.Repository` message) points at a legitimate object-quarantine directory by checking whether its **basename literally equals `"quarantine"`** (or its parent is `"quarantine"` and the basename starts with `tmp_objdir`). When that string match succeeds, the function **skips** the only check that ties the quarantine directory to the *specific repository/transaction* that owns it (the SHA1-derived `expectedQuarantinePrefix` check). This is structurally the same bug class as Sherlock M-12: a mutable/ephemeral "current owner" indirection (`address(lenderManager)` there, a transaction-specific randomized staging path here) is collapsed into a fixed sentinel value (`address(lenderManager)` there, the literal string `"quarantine"` here) that is compared without verifying it still identifies the *correct* owner, so requests get resolved against the wrong owner's resource.

### Finding Description
`internal/git/localrepo/paths.go` `ObjectDirectoryPath` (lines 21-83):
```go
relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
...
parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
baseDir := filepath.Base(relativeObjectDirectoryPath)
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

if !isTransactionQuarantineDir {
    // ... only here do we verify the object directory belongs to THIS repository
    // by requiring the path prefix storage.QuarantineDirectoryPrefix(repo) (SHA1(repo.RelativePath))
}
fullPath := filepath.Join(repoPath, objectDirectoryPath)
``` [1](#0-0) 

The only remaining checks after the `isTransactionQuarantineDir` short-circuit are:
1. The path must resolve inside the storage root (`storage.ValidateRelativePath`).
2. The final path must exist on disk (`os.Stat`).

There is **no check that the directory belongs to the repository or transaction issuing the request**. `GitObjectDirectory`/`GitAlternateObjectDirectories` are ordinary fields of the `Repository` message that flow through the public RPC surface — this is exactly the mechanism GitLab Rails uses to hand quarantine info back to Gitaly on subsequent RPCs during a push's access-check phase (documented in `doc/object_quarantine.md` and exercised in `internal/gitaly/service/repository/size_test.go`, which builds `GitObjectDirectory` pointing at a directory named literally `"quarantine"` anywhere in the storage and gets it accepted). [2](#0-1) 

Real transaction quarantine directories are created per-transaction under a **randomized** staging directory (`os.MkdirTemp(mgr.stagingDirectory, "")`) and then named `.../<random>/quarantine`:
```go
txn.quarantineDirectory = filepath.Join(txn.stagingDirectory, "quarantine")
``` [3](#0-2) 

Nothing in `ObjectDirectoryPath` verifies that the `objectDirectoryPath` supplied by the caller resolves to *this* transaction's `quarantineDirectory` (or any directory the caller is actually entitled to use) — it merely checks that *some* directory that happens to be named `quarantine`, anywhere reachable within the storage root relative to the caller's own repo path, exists. As long as an attacker/client can reference (via `../` traversal, which is legal here because `storage.ValidateRelativePath` only enforces "inside storage root", not "inside repo") a directory literally named `quarantine` belonging to a different repository/transaction/pool, the ownership check is bypassed entirely, and Gitaly will treat that foreign directory as the caller's own object/quarantine directory for RPCs that consume `ObjectDirectoryPath` (e.g. `GetObjectDirectorySize`, and any Git command spawned with `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` derived from these same fields).

### Impact Explanation
This breaks the isolation guarantee that object quarantine is documented to provide (`doc/object_quarantine.md`): "the [pre-receive] hook ... will inherit the quarantine config and will be able to see the objects that are being pushed" — quarantine is meant to be strictly scoped per push/transaction/repository. By colliding on the sentinel string `"quarantine"`, a caller can:
- Have Gitaly compute sizes/content for, or spawn git subprocesses whose `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` point at, another repository's or another concurrent push's quarantine/object directory (cross-repository/cross-transaction object access), rather than the caller's own quarantined objects.
- Undermine access-check logic that depends on the quarantine directory correctly reflecting only the objects the current push actually contains (used by GitLab Rails to inspect "objects being pushed" before allowing a push) — since any directory named `quarantine` is accepted regardless of which repo/push it belongs to.

### Likelihood Explanation
Reachability requires only that the attacker control the `Repository.GitObjectDirectory` (and possibly `GitAlternateObjectDirectories`) field of an RPC request — an ordinary, unprivileged capability since these are normal fields on the public `gitalypb.Repository` message used across many repository RPCs (`GetObjectDirectorySize`, hooks/access-check round-trip flows, etc.), reachable from a standard push flow where Rails/gitlab-shell round-trips quarantine metadata supplied by Gitaly back through subsequent RPCs. The remaining requirement — locating/guessing a directory literally named `quarantine` reachable via a relative path from the caller's own repository but still inside the storage root — is a real-world condition since such directories are routinely created (transaction staging quarantines, other pushes' quarantines) throughout the storage's lifetime, though their exact ephemeral path names are randomized, which somewhat limits reliable exploitation without further path/timing knowledge that I was unable to fully verify from static analysis alone.

### Recommendation
Do not authorize the object-directory override purely by matching the literal basename `"quarantine"`/`tmp_objdir*`. Instead, always require that the resolved object-directory path be validated against a value derived from the specific repository and (if applicable) the specific transaction/staging directory the current RPC/transaction is bound to, e.g. by comparing against the transaction's own `txn.quarantineDirectory` (passed via context, not solely inferred from string matching), retaining the `QuarantineDirectoryPrefix(repo)`-style ownership check unconditionally rather than skipping it whenever the sentinel string matches.

### Proof of Concept
Static-analysis PoC (not runtime-verified in this environment):
1. Client A pushes to repository `A.git`. A transaction quarantine directory `storage/<tx-tmp-random>/quarantine/pack/...` is created and `A`'s object directory is set accordingly for the duration of the push's access checks.
2. During the access-check round trip, an attacker-controlled or malicious intermediary crafts a subsequent RPC (e.g. `GetObjectDirectorySize`) for repository `B.git` (which they have normal access to), setting `Repository.GitObjectDirectory` to a relative path such as `../../<tx-tmp-random>/quarantine` (any path whose `filepath.Base` is `quarantine` and which resolves inside the storage root via `storage.ValidateRelativePath`).
3. `ObjectDirectoryPath` computes `isTransactionQuarantineDir = true` purely from the basename match, skips the `QuarantineDirectoryPrefix(B)` ownership check, confirms the directory exists, and returns the foreign directory (belonging to A's transaction) as `B`'s object directory — as demonstrated by the accepted test case in `internal/gitaly/service/repository/size_test.go` lines 248-276, where a directory named `quarantine` created independently of the repository's own SHA1-derived quarantine prefix is accepted without further ownership validation.
