## Analysis

The external report's core broken invariant is: **trusting an unsafe/non-standard ERC20 `transfer()` return value instead of verifying the actual balance delta, silently mishandling non-compliant tokens (fee-on-transfer, deflationary, non-bool-returning)**.

The closest local analog is `ERC20Transactor` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, which bridges arbitrary `pallet_revive` (EVM/PolkaVM) contracts into XCM's fungible-asset model. It already handles reverts and non-bool return decoding failures (as shown by the existing tests `smart_contract_not_erc20_will_error` and `smart_contract_does_not_return_bool_fails`), but it does **not** verify that the actual token balance change matches the requested `amount` — it trusts the boolean `true` return and credits/debits the full nominal `amount` regardless of what was truly transferred.

### Title
ERC20Transactor trusts nominal transfer amount instead of verified balance delta, allowing unbacked XCM asset credit from fee-on-transfer/deflationary tokens - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call an arbitrary ERC20-like contract's `transfer()` function and, provided it returns `true` and doesn't revert, unconditionally credit/debit the caller-specified nominal `amount` into the XCM `AssetsInHolding` register or as the transfer amount — without ever comparing the checking account's actual balance before/after the call.

### Finding Description
In `withdraw_asset_with_surplus`, the transactor calls `IERC20::transferCall` moving `amount` from `who` to the shared `TransfersCheckingAccount`: [1](#0-0) 

If the call succeeds and decodes to `true`, it mints an `Erc20Credit(amount)` into the XCM holding register using the **nominal requested `amount`**, not the actual balance increase observed on `TransfersCheckingAccount`: [2](#0-1) 

Symmetrically, `deposit_asset_with_surplus` transfers the nominal `amount` out of the checking account and treats a `true` return as full success: [3](#0-2) [4](#0-3) 

Because `pallet_revive` allows **permissionless contract instantiation**, any unprivileged user can deploy their own ERC20-like contract whose `transfer()` returns `true` while only forwarding `amount - fee` to the recipient (a standard "fee-on-transfer"/deflationary token pattern — precisely the class of "non-compatible ERC20 tokens" named in the source report). When this attacker-controlled asset is used in `withdraw_asset` via `pallet_xcm::execute`/`transfer_assets`, `Matcher::matches_fungibles` (an `H160`-keyed matcher accepting any contract address as an asset, as demonstrated by the existing tests instantiating arbitrary `dummy`/`MyTokenFake` contracts and using them directly as `AccountKey20` asset ids) allows the transactor to accept it, and the executor credits the **full nominal `amount`** to the XCM holding register even though the checking account actually received less. The holding credit is not defensively re-derived from an observed balance delta anywhere in this file.

Existing guards (revert detection, `abi_decode_returns_validate` failure handling) only catch reverts and malformed/non-bool returns — they do nothing to catch a token that *validly* returns `true` while transferring a different amount than requested, which is exactly the non-standard-token bug class from the original report.

### Impact Explanation
The XCM executor now holds phantom value (`Erc20Credit(amount)`) that is not fully backed by the real balance moved into `TransfersCheckingAccount`. Within the same XCM program the attacker can immediately route that phantom credit through further instructions (e.g. `ExchangeAsset` against a real liquidity pool, or `DepositAsset`/`InitiateReserveWithdraw` to a beneficiary), converting unbacked credit into real, fully-backed assets (DOT/WND or other pool liquidity) — an unbacked-mint/theft primitive reachable by any unprivileged user who can deploy a contract and submit an XCM program, with no reliance on a malicious validator, collator, relayer, or governance actor.

### Likelihood Explanation
High: `pallet_revive` contract deployment and `pallet_xcm::execute` are both public, permissionless entry points on chains that enable `ERC20Transactor` (e.g. Asset Hub Westend per `xcm_config.rs`). Writing a fee-on-transfer Solidity/PolkaVM contract that returns `true` on `transfer()` while forwarding less than requested is trivial and requires no special access.

### Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, read `TransfersCheckingAccount`'s (or beneficiary's) ERC20 `balanceOf` immediately before and after the `bare_call`, and credit/treat-as-transferred only the observed delta rather than the nominal requested `amount`. Reject or partially settle the XCM operation if the delta does not match the requested amount, consistent with how OpenZeppelin's `SafeERC20`/balance-delta pattern is recommended for handling non-standard ERC20 tokens in the original report.

### Proof of Concept
1. Deploy a PolkaVM/Solidity contract via `pallet_revive` implementing `IERC20` where `transfer(to, value)` moves `value - fee` to `to`, keeps `fee` for the caller, and returns `true` (a standard fee-on-transfer pattern).
2. Register/reference this contract's `H160` address as an `AccountKey20` asset id usable by `ERC20Transactor`'s `Matcher`.
3. Submit `pallet_xcm::execute` with `WithdrawAsset((AccountKey20{key: attacker_token}, amount))` followed by `ExchangeAsset`/`DepositAsset` to a beneficiary or pool.
4. Observe: `withdraw_asset_with_surplus` credits the XCM holding register with the full `amount`, even though `TransfersCheckingAccount`'s real ERC20 balance only increased by `amount - fee`.
5. The subsequent instruction (e.g. `ExchangeAsset`) consumes the full `amount` of phantom credit against a real-asset pool, extracting real value the attacker never actually deposited.
