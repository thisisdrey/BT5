## Title
Unchecked `reduceAssetAmountV2`/`addAssetAmountV2` return values in Exchange actuators cause silent asset loss while the trade is still recorded as successful — (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The referenced PoolTogether report shows that `PrizeVault._withdraw()` treats an ERC-20 `transfer()` and an ERC-4626 `redeem()` as always succeeding, never checking their return values, so a non-reverting failure silently leaves the internal share ledger updated while the underlying asset never moves — permanently locking the user's funds. `java-tron`'s `ExchangeTransactionActuator` and `ExchangeWithdrawActuator` exhibit the same root-cause pattern: they call `AccountCapsule.reduceAssetAmountV2(...)` / `addAssetAmountV2(...)` — boolean-returning "transfer" primitives — without checking the returned boolean, then unconditionally persist the updated `ExchangeCapsule` (the internal ledger) as if the balance adjustment succeeded.

### Finding Description
`TransferAssetActuator.execute()` demonstrates that the codebase itself treats a `false` return from `reduceAssetAmountV2` as a hard failure that must abort the whole operation: [1](#0-0) 

In contrast, `ExchangeTransactionActuator.execute()` calls the same style of balance-mutating methods but discards the boolean result entirely, then commits the exchange ledger regardless: [2](#0-1) 

The same unchecked pattern exists in `ExchangeWithdrawActuator.execute()`: [3](#0-2) 

In both actuators, the trade amount (`anotherTokenQuant`) is first computed and applied to the in-memory `ExchangeCapsule` via `exchangeCapsule.transaction(...)`/`exchangeCapsule.setBalance(...)`, and that capsule is unconditionally persisted with `Commons.putExchangeCapsule(...)`. The actual crediting/debiting of the trader's TRC10 balance is a separate step performed via `addAssetAmountV2`/`reduceAssetAmountV2`, whose boolean success/failure is never inspected. If that call returns `false` (e.g., because `addAssetAmountV2` internally guards against `long` overflow when adding to an existing large asset balance, as opposed to throwing), the transaction still returns `code.SUCESS`, the exchange pool's balances are updated as if the tokens moved, but the trader's account was never actually credited or debited — exactly mirroring the "shares burned but assets never transferred" defect in the PoolTogether report.

### Impact Explanation
This can result in one of:
- Permanent loss of the sold-side tokens: `reduceAssetAmountV2` is applied to the exchange's ledger but if the mirrored account-side operation doesn't succeed as expected, the exchange's tracked reserve no longer matches the real total of participants' claims, and no code path exists to reconcile or reverse it — an unrecoverable ledger/reserve mismatch (unbacked balance) analogous to the "funds locked" scenario.
- Loss of the bought-side tokens for the trader: if `addAssetAmountV2` silently fails, the trader pays (loses) the sell-side token but never receives the buy-side token, and the exchange ledger has already recorded the trade as complete, so there is no way to retry or recover the missing credit.

This matches the required impact bar (permanent freezing/loss of funds or unbacked balance) and is reachable by any unprivileged order placer broadcasting an `ExchangeTransactionContract`/`ExchangeWithdrawContract` transaction — no privileged role is required.

### Likelihood Explanation
Triggering requires driving `addAssetAmountV2`/`reduceAssetAmountV2` into its failure branch (e.g., accumulating an asset balance close to `Long.MAX_VALUE` so the addition overflow-guard returns `false`, or another latent inconsistency between the exchange capsule's balance accounting and the account's actual TRC10 balance). Exchange pools already enforce a `balanceLimit` on the pool side but the actuators do not re-validate the *trader's own account* asset totals against overflow before calling the mutator, and no test in `ExchangeTransactionActuatorTest`/`ExchangeWithdrawActuatorTest` covers a `false`-returning `addAssetAmountV2`/`reduceAssetAmountV2` call, so this failure mode is unhandled and unexercised. This makes it a real, though not trivially common, path — it requires a TRC10 asset holder to accumulate an extreme balance or a similar edge condition, but no signature or special permission is needed to trigger it once such a state exists.

### Recommendation
Check the boolean return values of `reduceAssetAmountV2`/`addAssetAmountV2` in `ExchangeTransactionActuator.execute()` and `ExchangeWithdrawActuator.execute()`, mirroring `TransferAssetActuator`'s pattern of throwing `ContractExeException` on failure *before* committing the `ExchangeCapsule` state, so that a failed balance mutation aborts the whole transaction instead of leaving the ledger and account balances inconsistent.

### Proof of Concept
Not independently reproducible from the indexed code alone — I could not fully inspect the body of `AccountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` (the `AccountCapsule.java` file content was not returned by search, only match locations) to confirm the exact overflow-guard conditions under which they return `false` versus throw. A Devin session with full repository access would be needed to construct a concrete failing scenario (e.g., an account's TRC10 balance close to `Long.MAX_VALUE`) and to unit-test `ExchangeTransactionActuator`/`ExchangeWithdrawActuator` against it to confirm the silent-failure/locked-funds outcome.
