### Title
Dust transfer of `DepositToken`s fills a victim's `depositTokensOfAccount` set up to `MAX_TOKENS_PER_USER`, permanently DoSing deposits, fee-bearing withdrawals and liquidations for that account - (File: contracts/DepositToken.sol)

### Summary
The Rails bug is a DoS via attacker-controlled resource exhaustion: arbitrary strings are interned as symbols until memory/limits blow up. The Metronome analog is identical in shape: `Pool` enforces a hard cap (`MAX_TOKENS_PER_USER = 30`, `contracts/Pool.sol:79`) on the per-account sets `depositTokensOfAccount`/`debtTokensOfAccount`, and `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once the combined length hits 30 (`contracts/Pool.sol:143-148`). `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0 (`contracts/DepositToken.sol:517-520`). Anyone can `transfer` 1 wei of any registered msd-token to a victim, and each distinct token consumes one slot in the victim's set. This is the symbol-interning DoS mapped onto a bounded enumerable set.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's set on first receipt (`contracts/DepositToken.sol:518-520`), and `deposit()`/`_mint` do the same on mint (`contracts/DepositToken.sol:486-488`). There is no opt-in: receiving a token forces a set entry.
- `Pool.addToDepositTokensOfAccount` is guarded by `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokensOfAccount.length(account) + depositTokensOfAccount.length(account) >= 30` (`contracts/Pool.sol:143-148`; behavior confirmed in `test/Pool.test.ts:1386-1416`).
- Attack: an EOA acquires dust of deposit tokens (or receives them via `deposit(amount, onBehalfOf_=victim)` — `DepositToken.deposit` allows depositing to any beneficiary, `contracts/DepositToken.sol:211-237`) and pushes each distinct msd-token once to the target. Cost is ~30 transfers of negligible value.
- Once the target's set is at 30:
  - The victim can never receive a new collateral type (`deposit` on their behalf, transfers, and `seize` to them in `Pool.liquidate` all revert in `_transfer`/`_mint`).
  - Critical target: the pool `feeCollector`. Both `deposit()` (`_mint(_pool.feeCollector(), _fee)`, line 231) and `_withdraw()` (`_transfer(account_, _pool.feeCollector(), _fee)`, line 547) push a set entry for the fee collector on first receipt of each token. Filling the fee collector's set makes every fee-bearing deposit and withdrawal revert pool-wide until a governance/keeper removes the collector's dust (and the collector can't remove entries without zeroing balances). Since `withdraw`/`flashWithdraw`/`withdrawFrom` all route through `_withdraw`, this is a temporary freeze of user collateral withdrawals whenever `depositFee`/`withdrawFee` > 0.
- `debtTokensOfAccount` cannot be dust-filled the same way (debt tokens are only issued, not freely transferable), so the deposit-token path is the vector.

### Impact Explanation
Temporary freezing of funds / liveness break: withdrawing collateral becomes impossible for all users of a deposit token (or pool-wide once the fee collector's set is saturated) because `_withdraw` reverts inside `_transfer` to the fee collector. Individual victims are also blocked from receiving new collateral types, which can lock them out of adding collateral needed to stay healthy. Funds are recoverable (an admin or the collector can burn dust to zero a balance, or fees can be set to 0), so this is temporary rather than permanent freeze — matching the Medium severity of the reference advisory.

### Likelihood Explanation
Reachable by any unprivileged EOA using only public entry points (`transfer`, `deposit`). The blocker is configuration-dependent: the attack needs enough distinct registered deposit tokens (plus the victim's existing debt tokens) to reach 30; `addDepositToken` caps the registry at `MAX_TOKENS_PER_USER` (`contracts/Pool.sol:703`), so on pools with fewer registered collaterals the ceiling may be unreachable. Where 30 collateral types exist (or a victim already carries debt tokens reducing headroom), the attack is cheap, non-destructive to the attacker, and not stopped by `nonReentrant`, `whenNotPaused`, or `SynthContext` checks since it uses ordinary ERC20 transfers.

### Recommendation
Make set insertion non-fatal for recipients: e.g., skip adding on dust below a threshold, let `addToDepositTokensOfAccount` return false instead of reverting for the fee-collector path, or exempt `feeCollector`/system addresses from the cap. Alternatively restrict `deposit(..., onBehalfOf_)` or add a per-account "block unsolicited tokens" flag.

### Proof of Concept
Foundry/Hardhat fork outline (pool with ≥30 registered deposit tokens or reduced headroom):
1. For each deposit token `d[i]`: `d[i].deposit(1 wei, attacker)` then `d[i].transfer(victim, 1)` — or directly `d[i].deposit(1, feeCollector)`.
2. After the 30th insertion, `depositTokensOfAccount[feeCollector].length + debtTokensOfAccount[feeCollector].length == 30`.
3. Any user's `d[i].withdraw(x, to)` with `withdrawFee > 0` reverts with `UserReachedMaxTokens` inside `_withdraw → _transfer → addToDepositTokensOfAccount`; `d[i].deposit` reverts at the fee mint. Assert `vm.expectRevert(Pool.UserReachedMaxTokens.selector)`.

Caveat: I could not confirm the exact deployed `depositTokens` count per chain from the index; if no production pool registers enough collaterals for the cap to be reachable, the impact degrades to blocking deposits only for already-saturated victims.
