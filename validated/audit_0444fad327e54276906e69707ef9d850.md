### Title
Relay control messages trust attacker-supplied `RelayFromAddr`/`RelayToAddr` without binding them to the sender's certificate-verified VPN address - (File: relay_manager.go)

### Summary
The Solana report's root cause is generic: a value taken from an untrusted/self-reported source (a PDA seed derived from a field the attacker controls) is used for security-relevant logic without being checked against the value that should actually govern trust (the pool's `lp_token_mint`). The reachable analog in this Nebula codebase is in the relay control-message handling in `relay_manager.go`, where the `RelayFromAddr` field carried inside a `NebulaControl_CreateRelayRequest`/`CreateRelayResponse` message is taken at face value and used to install/mutate relay state, without verifying that it matches the actual, cert-authenticated VPN address of the peer (`h.vpnAddrs`) that sent the control message over the already-established, mutually authenticated tunnel.

### Finding Description
`relayManager.HandleControlMsg` unmarshals a `NebulaControl` message received from an already-connected `HostInfo` `h` and, for `CreateRelayRequest`/`CreateRelayResponse`, only checks that `RelayFromAddr`/`RelayToAddr` are non-nil: [1](#0-0) 

It then dispatches to `handleCreateRelayRequest`, which decodes `from := protoAddrToNetAddr(m.RelayFromAddr)` directly from the message body and uses it, unchecked against `h.vpnAddrs` (the identity established by the Noise handshake and certificate verification for that HostInfo), to add relay state, answer requests, and log/relay traffic: [2](#0-1) 

Likewise, `handleCreateRelayResponse` takes `relayFrom`/`relayTo` from the message and uses them to locate and update relay state, again without cross-checking `relayFrom` against the sending host's actual VPN address: [3](#0-2) 

In the original Solana bug, the seed used to derive/validate an account was taken from a field the attacker fully controls (`staked_token_mint`) rather than from the known-correct value (`lp_token_mint`), letting the attacker substitute an account that passes the PDA/seed check but is not actually the pool's real staking account. Structurally the same pattern exists here: the code has an authenticated source of truth for "who is this peer" (`h.vpnAddrs`, derived from the verified certificate at handshake time) but instead uses an unauthenticated, attacker-supplied field (`m.RelayFromAddr`) for the same purpose when building relay-state on behalf of that peer.

### Impact Explanation
Because `from` is not required to equal `h.vpnAddrs[0]`, a compromised or malicious authenticated peer can claim to be relaying "from" an arbitrary VPN address it does not own. This can be used to poison relay state (`AddRelay`, `relayState.QueryRelayForByIp`) for a victim address, causing the receiving node to associate relay/forwarding entries with the wrong VPN identity, or to trigger relay-establishment logic (handshakes, `CreateRelayRequest`/`Response` exchanges) impersonating a different node's relay-from identity. This is a remote state-poisoning vector reachable from any peer that has completed the mutual-TLS-like Noise handshake (i.e., holds a cert signed by a CA in the pool) but does not itself certify the `RelayFromAddr` value—so the vulnerability class matches "remote state poisoning" via unverified attacker-controlled binding, analogous to the seed-substitution issue in the original report.

### Likelihood Explanation
Exploitation requires only a valid, non-CA-signing peer certificate (any authenticated but potentially malicious peer node in the mesh) and the ability to send a `Control`-type message on an established tunnel — no special privilege beyond normal handshake participation is needed, making this attack path realistic once a node accepts connections from semi-trusted peers or an already-authenticated relay is compromised.

### Recommendation
When processing `CreateRelayRequest`/`CreateRelayResponse`, validate that `m.RelayFromAddr` (decoded via `protoAddrToNetAddr`) matches one of `h.vpnAddrs` for the `HostInfo` that actually sent the control message, mirroring how `validatePeerCert` binds `vpnAddrs` from the verified certificate rather than trusting a self-reported field. Reject the message (log and return) if the claimed `RelayFromAddr` does not correspond to the authenticated sender's own VPN address(es).

### Proof of Concept
Note: I could not fully trace `AddRelay`'s internal validation (the file read for the full body of `relay_manager.go` did not complete before the tool budget ran out), so I cannot confirm with certainty whether `AddRelay` or another downstream function performs an implicit check against `h.vpnAddrs` that would mitigate this. The PoC below assumes no such check exists, consistent with the code shown above.

1. Node A completes a legitimate handshake with Node B, obtaining a valid `HostInfo` `h` for A with `h.vpnAddrs = [A_ip]`.
2. Node A sends a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = victim_ip` (some other node's VPN IP that A does not own) and `RelayToAddr = B_ip` (or another target it wants to poison).
3. `relayManager.HandleControlMsg` on B only checks that `RelayFromAddr`/`RelayToAddr` are non-nil, then calls `handleCreateRelayRequest`, which uses `from = victim_ip` directly to call `AddRelay(..., from, ...)` and build relay state keyed on `victim_ip`, despite the packet having arrived on the tunnel belonging to `HostInfo` A with `vpnAddrs = [A_ip]`.
4. B's relay state map now contains an entry attributing relay-from identity `victim_ip` to A's connection, which can be leveraged in subsequent `CreateRelayResponse`/forwarding logic to poison how B (or downstream peers) treat traffic claiming to originate from `victim_ip`. [1](#0-0) [2](#0-1)

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}
