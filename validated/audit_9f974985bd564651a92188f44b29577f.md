### Title
Wrong-length success response from `mt_batch_transfer_call` forces full refund via `mt_resolve_withdraw`, double-crediting withdrawn balances - ([File: contracts/defuse/src/contract/tokens/nep245/withdraw.rs])

### Summary
`mt_resolve_withdraw` treats any successful promise result whose deserialized `Vec<U128>` length does not exactly equal `amounts.len()` as a *total failure* (`used = vec![U128(0); amounts.len()]`), triggering a full refund via `self.deposit`. Since the balance was already debited by `internal_mt_withdraw` before the transfer promise was scheduled, and the external `token` contract's return payload is fully attacker-controlled, an attacker who deploys the `token` contract can genuinely deliver custody to `receiver_id` while returning a malformed/short array, causing the Defuse ledger to re-credit the full amount to `sender_id` (`owner_id`) — a double credit.

### Finding Description
The broken binding: for each token, `debited_amount == delivered_amount + recredited_amount` must hold. Instead, on genuine delivery with a malformed-length success response, `A_i == A_i (delivered) + A_i (recredited)`.

Code path:
- `internal_mt_withdraw` (contracts/defuse/src/contract/tokens/nep245/withdraw.rs:60-125) debits `[A1, A2]` from `owner_id` via `self.withdraw(...)` before any promise executes.
- `do_mt_withdraw` (lines 154-197) schedules `ext_mt_core::mt_batch_transfer_call` against the attacker-controlled `token` contract.
- `mt_resolve_withdraw` (lines 200-257) inspects the promise result:
  ```
  Ok(Ok(used)) if used.len() == amounts.len() => used,
  Ok(_) => vec![U128(0); amounts.len()],
  Err(_) => amounts.clone(),
  ```
  If the promise succeeds (`Ok`) but the JSON either fails to parse or parses into a `Vec<U128>` of the wrong length, the code falls into `Ok(_) => vec![U128(0); amounts.len()]`, i.e. it assumes **zero tokens were transferred**, regardless of what actually happened on-chain at the `token` contract.
- `used` (all zeros) flows into the `self.deposit(sender_id, ...)` call (lines 235-253), where `refund = amount.0.saturating_sub(used.0)` equals the full original amount for every token, re-crediting `owner_id`'s balance for both `TokenId`s.

Root cause: the resolver trusts the *shape* of a promise's success payload as a proxy for "nothing was transferred," but the payload is produced entirely by the externally-specified `token` contract, which is attacker-controllable (`mt_withdraw`'s `token` argument has no allowlist/registration requirement enforced in this code). An attacker who: (1) deploys their own malicious NEP-245 contract, (2) deposits self-minted balances of it into the Defuse ledger (giving `owner_id` legitimate internal balance for `TokenId::Nep245(token, token_id)`), and (3) calls `mt_withdraw` with `msg` set (forcing the `is_call` / `mt_batch_transfer_call` branch) and `receiver_id` under their control, can make their malicious `token` contract genuinely transfer full custody to `receiver_id` while returning a truncated `Vec<U128>` on success. `mt_resolve_withdraw` then treats this as complete failure and refunds the full amount back to `owner_id` via `self.deposit`, even though custody already left the system.

No existing guard prevents this: the `require!(token_ids.len() == amounts.len() && !amounts.is_empty())` check only validates the callback's own static arguments, not the untrusted promise payload; `promise_result_checked_json_with_len` only bounds the JSON size, not correctness of length; there is no cross-check against what was actually debited versus what the token contract's return value independently attests, and no allowlist restricting which accounts can be used as `token`.

### Impact Explanation
This breaks the Verifier's core solvency invariant: after the sequence, the Defuse-internal ledger shows `owner_id` holding the original balances for `t1`/`t2` again, even though the corresponding tokens already left the system's custody at the `token` contract. This is precisely the documented Critical category "a batch whose balance changes do not net to zero so the Verifier owes more than it custodies." While the specific PoC uses a self-controlled/self-minted token (limiting immediate extractable value to that token type), the inflated internal balance can subsequently be used in matched swap intents against real counterparties, or withdrawn a second time, laundering the phantom balance into other assets. The bug is repeatable per withdrawal call and applies per `TokenId` in the batch, so it scales with the number of tokens included.

### Likelihood Explanation
Preconditions are entirely within attacker control: they need only deploy their own NEP-245 contract, self-mint and deposit tokens of it into the Defuse contract (any unprivileged account can do this via `mt_on_transfer`), and issue a single `mt_withdraw` call with `msg` set and a controlled `token`/`receiver_id`. No privileged role, relayer key, or victim signature is required — the attacker signs their own transaction. The only engineering effort is writing a malicious NEP-245 contract that returns a truncated `Vec<U128>` on success, which is trivial. This is fully repeatable across any number of accounts, tokens, and batches.

### Recommendation
Do not conflate "malformed/wrong-length success payload" with "zero transferred." On `Ok(_)` (successful promise but unparseable/wrong-length result), either: (a) treat it as `Err` and refund nothing (conservative for other failure paths but inconsistent here), or better, (b) fail the whole withdrawal/refund decision deterministically by requiring the callee to return exactly the expected shape, and if it does not, refuse to re-credit any amount when the outer promise otherwise succeeded — since a successful `PromiseResult` combined with an invalid payload should never be interpreted as "the receiver used nothing." A safer general fix is to only allow amounts to be refunded up to what independent evidence (e.g. verified balance deltas of `token` account) shows were not moved, or to restrict withdrawals to `token` contracts that are registered/trusted rather than arbitrary attacker-supplied accounts.
