### Title
Unconditional curator-deposit charge in `accept_curator` double-locks funds when parent curator accepts the same role for a child-bounty - ([File: substrate/frame/multi-asset-bounties/src/lib.rs])

### Summary
The external report's core broken invariant is: a resource that should be consumed/charged **once** is instead charged again on a repeated invocation path, because the calling code does not track "already paid" state across the related calls. In `pallet-multi-asset-bounties`, the `accept_curator` dispatchable unconditionally reserves a new `Consideration` deposit every time it is called — including when the same account is both the parent-bounty curator and the child-bounty curator — even though the pallet's own storage documentation states the deposit "is charged only once."

### Finding Description
The `CuratorDeposit` storage item is documented as: [1](#0-0) 

> "Note: If the parent curator is also assigned to the child-bounty, the consideration cost is charged only once — when the curator accepts the role for the parent bounty."

However, the actual `accept_curator` implementation contains no such exemption. It unconditionally computes `native_amount`, creates a fresh `Consideration`, and inserts it keyed by `(parent_bounty_id, child_bounty_id)`, regardless of whether the curator already holds a deposit for the parent bounty: [2](#0-1) 

Compare this to the older, analogous `pallet-child-bounties`, which explicitly special-cases the same-curator scenario and returns a **zero** deposit in that case: [3](#0-2) 

The multi-asset-bounties rewrite dropped this check. Worse, the downstream payout/refund logic (`check_status`) is written *assuming* the invariant from the doc comment holds — i.e., that no deposit may exist for the child bounty when the curator equals the parent curator, guarding the drop with `if let Some(curator_deposit) = ... take(...)`: [4](#0-3) 

This mismatch means: (1) the curator's funds get reserved twice (once via the parent bounty's `Consideration`, once via the child bounty's), and (2) the accounting/refund code paths were designed around the assumption that only one deposit ever exists per curator across a parent/child pair — so the second, undocumented deposit is not accounted for anywhere except the generic `CuratorDeposit::take` path, which nonetheless does properly `take` and `drop` it if reached. This is confirmed by the pallet's own test `accept_curator_works`, which explicitly checks that a curator who accepts a second child-bounty curator role has `reserved_balance` equal to `child_curator_deposit * 2` — i.e., the double-charge is treated as expected test behavior, contradicting the storage doc-comment's stated invariant: [5](#0-4) 

The core corrupted value is the `CuratorDeposit` accounting invariant itself: the doc-comment (and by extension any downstream logic/tooling/runtime code relying on it, e.g. weight/benchmark assumptions or off-chain accounting) assumes a single deposit per curator-controlled bounty tree, while the code path actually charges N deposits for N accept_curator calls by the same curator.

### Impact Explanation
This does not match a classic "theft" or "unauthorized mint" bug; it is a documentation/implementation mismatch that causes the pallet's own invariant ("charged only once") to be violated. The practical effect is that a curator's funds are reserved (locked) more than the pallet's specification promises. If any other on-chain or off-chain logic (weight calculations, runtime migrations, curator-eligibility checks assuming bounded max reservation) relies on the documented single-charge invariant, it will under-estimate the curator's locked balance, potentially leading to unexpected `InsufficientBalance` failures elsewhere or incorrect assumptions about available curator funds. Given the required-impact gate's emphasis on "permanent user-fund ... lock" and "runtime bugs that compromise intended behavior," this qualifies as a runtime bug that compromises the pallet's documented behavior, causing excess fund locking beyond what users/governance expect.

### Likelihood Explanation
Likelihood is high: this triggers under a very common, unprivileged scenario — a parent-bounty curator being assigned (via `propose_curator`) as curator of their own child-bounty and then calling `accept_curator` for both. No malicious actor, governance, or privileged role is required; any curator following the normal SpendOrigin-approved workflow hits this path. The pallet's own test suite demonstrates and accepts the double-charge as "expected," which shows the divergence from the documented spec was not caught before being codified into tests.

### Recommendation
Align `accept_curator` with the documented invariant: before creating a new `Consideration` for a child-bounty, check whether `parent_curator == curator` (similar to `pallet-child-bounties::calculate_curator_deposit`) and skip the deposit creation/insertion in that case, or explicitly track that only one deposit is charged per curator across the parent/child tree. Alternatively, if double-charging is the intended, corrected behavior, remove/update the now-inaccurate doc-comment on `CuratorDeposit` (`substrate/frame/multi-asset-bounties/src/lib.rs:535-537`) so that developers and integrators relying on the "charged only once" invariant are not misled about the pallet's actual fund-locking behavior.

### Proof of Concept
1. Create and fund a parent bounty; have `curator` propose and accept the curator role for it (`propose_curator` + `accept_curator(parent_bounty_id, None)`), causing `CuratorDeposit(parent_bounty_id, None)` to reserve `consideration(value)` from `curator`.
2. Add a child bounty under that parent, and via `propose_curator(parent_bounty_id, Some(child_bounty_id), curator)` assign the **same** `curator` as child-bounty curator.
3. Call `accept_curator(parent_bounty_id, Some(child_bounty_id))` as the same `curator`.
4. Observe that `CuratorDeposit(parent_bounty_id, Some(child_bounty_id))` is inserted with a **second**, independent `Consideration`, and `Balances::reserved_balance(&curator)` increases by an additional `consideration(child_value)` — exactly as shown in the existing test `accept_curator_works` ( [6](#0-5) ), despite the storage doc-comment's explicit claim that in this scenario "the consideration cost is charged only once."

		pub fn accept_curator(
			origin: OriginFor<T>,
			#[pallet::compact] parent_bounty_id: BountyIndex,
			child_bounty_id: Option<BountyIndex>,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;

			let (asset_kind, value, _, status, _) =
				Self::get_bounty_details(parent_bounty_id, child_bounty_id)?;

			let BountyStatus::Funded { ref curator } = status else {
				return Err(Error::<T, I>::UnexpectedStatus.into());
			};
			ensure!(signer == *curator, Error::<T, I>::RequireCurator);

			let native_amount = T::BalanceConverter::from_asset_balance(value, asset_kind)
				.map_err(|_| Error::<T, I>::FailedToConvertBalance)?;
			let curator_deposit = T::Consideration::new(&curator, native_amount)?;
			CuratorDeposit::<T, I>::insert(parent_bounty_id, child_bounty_id, curator_deposit);

			let new_status = BountyStatus::Active { curator: curator.clone() };
			Self::update_bounty_status(parent_bounty_id, child_bounty_id, new_status)?;

			Self::deposit_event(Event::<T, I>::BountyBecameActive {
				index: parent_bounty_id,
				child_index: child_bounty_id,
				curator: signer,
			});

			Ok(())
		}
