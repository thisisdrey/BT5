## Title
Legacy TRC10 Exchange AMM uses unchecked double-precision math for pricing, enabling drained/negative pool balances - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
Acala's loss stemmed from an unaudited/misconfigured on-chain incentive calculation (`incentives.claim_rewards()`) that used flawed math to mint an exponential, unbacked amount of `aUSD`, which attackers then swapped out through connected liquidity pools before the bug could be stopped. The reachable analog in java-tron is the legacy bonding-curve math in the built-in TRX/TRC10 Exchange (`ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract`), which any unprivileged account can invoke via a signed transaction. The default, non-hardened calculation path (`ExchangeProcessor`) performs pricing purely with unchecked Java `double` arithmetic and casts to `long`, with no post-condition check that resulting pool balances stay non-negative or internally consistent, unlike the newer `SafeExchangeProcessor`/`hardenedCalc` path that is gated behind a governance proposal (`allowHardenExchangeCalculation`) and off by default.

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine based on a chain parameter: [1](#0-0) 

When `hardenedCalc` is `false` (the default — controlled by `allowHardenExchangeCalculation`, activated only via committee proposal), every trade uses `ExchangeProcessor`, whose core pricing functions are computed entirely in floating point: [2](#0-1) 

Both `exchangeToSupply` and `exchangeFromSupply` cast `double` results directly to `long` with no overflow checks, no rounding-direction guarantee protecting the pool, and no post-trade invariant check. Compare this to the hardened path, `ExchangeCapsule.transaction()`'s explicit non-negative balance check that only fires `if (hardenedCalc ...)`: [3](#0-2) 

In the legacy (default) path, `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `+`/`-` and are **not validated to be non-negative** before being persisted back to the `ExchangeCapsule`: [4](#0-3) 

This means: (1) an attacker can craft `quant` values (bounded only by `long` range and `exchangeBalanceLimit`) that push the double-precision bonding-curve computation into regions of severe floating-point error/precision loss at extreme ratios (e.g., `quant` close to `newBalance`, or extremely small `supply` remaining after repeated trades), producing a `buyTokenQuant` inconsistent with the true conserved-value AMM formula; (2) because there is no invariant check in the legacy path, a resulting negative or over-large balance is written directly into the on-chain `ExchangeCapsule` and used for subsequent trades, and the actual TRX/token transferred to the trader's `AccountCapsule` in `ExchangeTransactionActuator.execute()` is credited unconditionally via `addAssetAmountV2`/`setBalance`. This mirrors the Acala root cause: a bespoke financial-math routine, reachable by any transaction sender, whose numeric edge cases were not hardened, that lets a caller extract value the pool does not actually back.

### Impact Explanation
If floating-point/precision manipulation of `ExchangeProcessor.exchange()` can be driven to return an inflated `buyTokenQuant` (or to leave the pool with negative internal `firstTokenBalance`/`secondTokenBalance`), an attacker can repeatedly call `ExchangeTransactionContract` to drain real TRX/TRC10 tokens held by the pool (funded by other users via `ExchangeCreateContract`/`ExchangeInjectContract`) while the pool's recorded balances become inconsistent with reality — an unbacked-balance/fund-theft condition directly analogous to Acala's erroneous minting and subsequent drain of the iBTC/aUSD pool. This is High severity: unauthorized extraction of pooled user funds through a standard, unprivileged, signed transaction type.

### Likelihood Explanation
Medium-High: the vulnerable path is the **default** production path (hardened math is opt-in via governance and not the default), and it is reachable by any account with TRX/TRC10 balance and no special privilege, using only `ExchangeCreateContract`/`ExchangeInjectContract`/`ExchangeTransactionContract` — standard actuators processed in `Manager`'s validate/execute pipeline. Exploitation requires finding specific `quant`/pool-ratio inputs that trigger meaningful floating-point divergence from the exact fixed-point result, which requires precise numerical analysis but is a deterministic, offline-computable search (no race condition or privileged access needed), consistent with the "unprivileged transaction broadcaster" reachability required by the rules.

### Recommendation
- Make `SafeExchangeProcessor` (BigDecimal-based, `addExact`-checked) the default and only implementation of `ExchangeCapsule.Processor`, removing/deprecating the unchecked `ExchangeProcessor` double-math path, or at minimum enforce the same non-negative-balance invariant check unconditionally (not only when `hardenedCalc` is true) as seen in `ExchangeCapsule.transaction()` lines 160-162.
- Add explicit unit-economic invariant checks after every trade (e.g., verifying the constant-product/bonding-curve invariant is not violated beyond expected fee/rounding tolerance) before persisting `ExchangeCapsule` state, regardless of which processor executed.
- Audit `exchangeToSupply`/`exchangeFromSupply` for edge cases where `newBalance`, `supply`, or `buyTokenBalance` are small relative to `quant`, and add bounds/sanity checks rejecting trades that would produce a negative or overflowed pool balance.

### Proof of Concept
Conceptual (numeric) PoC — cannot be fully executed without live-node access, but the code path is concretely reachable as follows:
1. Attacker calls `ExchangeCreateContract` or observes an existing TRC10 exchange with skewed reserves (small `secondTokenBalance` relative to `firstTokenBalance`), reachable via `ExchangeCreateActuator.execute()` [5](#0-4) .
2. Attacker submits a series of `ExchangeTransactionContract` transactions via `ExchangeTransactionActuator.execute()` with `tokenQuant` values chosen so that in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` the ratio `quant/newBalance` (or `supplyQuant/supply`) approaches values where `double` precision loss under `Maths.pow(...)` produces a `buyTokenQuant` larger than the fixed-point-correct value [6](#0-5) .
3. Because `ExchangeCapsule.transaction()` only validates non-negative balances when `hardenedCalc` is true (governance-controlled, default off), the resulting inflated `anotherTokenQuant` is credited to the attacker's account balance/asset (`addAssetAmountV2`/`setBalance`) while the exchange pool's recorded balance is updated to a value that no longer matches actual backing assets, allowing repeated extraction analogous to draining the Acala iBTC/aUSD pool.

Full exploitability (i.e., locating concrete `quant`/reserve values that produce meaningfully profitable divergence, and confirming it exceeds any implicit fee margin) requires numeric experimentation against a running node/test harness, which is outside the scope of static code review — a Devin session with code-execution access should implement the described unit-invariant checks and fuzz `ExchangeProcessor.exchange()` against `SafeExchangeProcessor.exchange()` across the `long` input space to quantify and confirm the divergence magnitude before merging a fix.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
