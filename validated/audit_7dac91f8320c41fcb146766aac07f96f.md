## Finding: Missing return-data copy fix reintroduces CVE-2021-39137 root cause

I confirmed the current repository is missing the exact fix that was released for this CVE, in the exact functions the original patch touched.

### Title
RETURNDATA/memory aliasing corruption in CALL-family opcodes (missing post-fix `CopyBytes` on `ret`) - (File: `core/vm/instructions.go`)

### Summary
The historical fix for CVE-2021-39137 added `ret = common.CopyBytes(ret)` immediately before `scope.Memory.Set(retOffset.Uint64(), retSize.Uint64(), ret)` in `opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall`, so that the return value assigned to `evm.returnData` is never the same backing array as the destination memory the `Memory.Set` call mutates [1](#0-0) . In this repository, all four of these opcode implementations still write `ret` into memory and then alias `evm.returnData = ret` afterward, with no intervening copy: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

### Finding Description
The original bug: `opCall`-family opcodes get their call input as a raw view into the caller's own memory (`args := scope.Memory.GetPtr(...)`, no copy, deliberately, to avoid a malloc-DoS) [6](#0-5) . If the callee (historically the `dataCopy`/identity precompile) returns that same backing slice unmodified as `ret`, then `scope.Memory.Set(retOffset, retSize, ret)` writes the result back into memory that overlaps (with a shift) the same backing array that `ret` points into. Because the write mutates the shared backing array, and `evm.returnData = ret` is only assigned *after* this write, `evm.returnData` silently ends up holding corrupted bytes — bytes different from what the callee actually returned. Any subsequent `RETURNDATACOPY`/`RETURNDATASIZE` (or values derived from them, e.g. stored via `SSTORE`) then diverge from the EIP-211 specified semantics, which require `RETURNDATA` to reflect exactly the last sub-call's output.

The historical patch closed this by making `ret` an independent copy *before* the memory write, decoupling `evm.returnData` from the memory buffer being mutated. That line is absent from all four affected functions in this codebase, so the structural root cause the advisory describes is present again in `opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall`.

I verified that the currently in-repo identity/`dataCopy` precompile does perform its own defensive copy (`common.CopyBytes(in)`) [7](#0-6) , which happens to prevent the exact historical proof-of-concept from reproducing through that specific precompile today. However, this is incidental to that one precompile's implementation, not the sanctioned fix — the sanctioned fix operates generically at the opcode level regardless of what any given precompile or callee returns. I was not able to fully audit every other precompile (`bigModExp`, `blake2F`, `bn256*`, `kzgPointEvaluation`, BLS12-381 operations, `P256Verify`, etc.) within the available time to rule out any other code path that could return a slice aliasing the caller's own memory without copying, so I cannot certify a fully reproduced live PoC beyond matching the exact pre-patch vulnerable pattern in the four call opcodes.

### Impact Explanation
If any reachable callee (a precompile or future code path) returns output that aliases the calling frame's own memory buffer without an independent copy, this missing fix causes `evm.returnData` to be corrupted deterministically and silently, with no error or revert. Contract logic that consumes `RETURNDATA` (via `RETURNDATACOPY`, or indirectly through common Solidity idioms that check/propagate return data) would then compute or persist different state (e.g., a different `SSTORE` value) than a spec-compliant client, producing a different `stateRoot` for the same block — the exact Critical-class consensus split this CVE originally caused on mainnet.

### Likelihood Explanation
This is only concretely exploitable if a reachable callee returns a slice that aliases the memory of the calling frame without copying it first. I confirmed that the one historically-implicated precompile (`dataCopy`/identity, address `0x04`) now copies its input independently, closing off the originally disclosed trigger. I could not, in the time available, rule out all other precompiles or code paths as potential re-enablers of this exact bug class, so likelihood is currently unconfirmed pending a full precompile-by-precompile audit, but the missing safety-net line is a direct, provable regression versus the patched/expected code.

### Recommendation
Reinstate the historical fix: insert `ret = common.CopyBytes(ret)` immediately before each `scope.Memory.Set(retOffset.Uint64(), retSize.Uint64(), ret)` call in `opCall`, `opCallCode`, `opDelegateCall`, and `opStaticCall` in `core/vm/instructions.go`, restoring the defense-in-depth regardless of any individual precompile's copy behavior.

### Proof of Concept
Based on the documented historical exploit pattern (still structurally reproducible if any precompile/callee ever returns an aliased, non-copied slice):
1. Deploy a contract that issues `CALL` to a callee whose return value is a direct view into the caller's own memory region used as call input (e.g., `CALL(gas, addr, 0, inOffset=0, inSize=4, outOffset=1, outSize=4)` — overlapping/shifted input and output ranges).
2. If the callee's returned bytes alias the caller's memory (as occurred pre-fix via the identity precompile), the `Memory.Set` call in `opCall` (`core/vm/instructions.go:767`) overwrites part of the source region that `ret`/`evm.returnData` still references.
3. Follow with `RETURNDATACOPY` to observe/propagate the corrupted return data into storage via `SSTORE`, producing a state divergence from a correctly-implemented client that copies the return value before writing to memory, per the original CVE-2021-39137 exploit at mainnet block [13107518](https://etherscan.io/block/13107518) [8](#0-7) .
