Looking at the `VerifyTransferProof.execute` method in `PrecompiledContracts.java`, the critical bug class here is out-of-bounds/heap-over-read caused by trusting attacker-controlled offsets to index into a fixed-size buffer without validating the offset/derived positions against `data.length` before slicing — directly analogous to LibSass's `skip_over_scopes` trusting scope boundaries without bounds validation during `parse_import()`.

### Title
Unvalidated attacker-controlled offsets in `VerifyTransferProof.execute` allow out-of-bounds array access causing node crash - (`File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`VerifyTransferProof.execute` (reachable by any unprivileged account through a TVM `STATICCALL`/`CALL` to the Zcash-shielded-pool precompile) reads three offset fields (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) directly from the caller-supplied `data` byte array and uses them, together with attacker-controlled `spendCount`/`receiveCount`, to drive `System.arraycopy` calls without validating that the computed positions stay within `data.length`.

### Finding Description
The method only checks that `data.length` equals one of four fixed `SIZE` values [1](#0-0) . It then parses `spendOffset`, `spendAuthSigOffset`, `receiveOffset` from fixed positions in `data` [2](#0-1) , and later reads `spendCount`/`spendAuthSigCount`/`receiveCount` from those attacker-supplied offsets [3](#0-2) . Aside from a narrow range check on the counts (`1` or `2`) [4](#0-3) , none of `spendOffset`, `spendAuthSigOffset`, or `receiveOffset` are validated to be within `[0, data.length)`, nor is it verified that `offset + fixed_read_size <= data.length` before the subsequent loops perform `System.arraycopy` at `spendOffset + 320*i`, `spendAuthSigOffset + 64*i`, `receiveOffset + 288*i` [5](#0-4) . Since `data.length` is fixed (one of the four `SIZE` values) but the offsets are parsed as arbitrary 32-byte big-endian integers from attacker input, a transaction sender can set an offset to point past the end of the buffer (or to a negative/huge value once combined with the loop index), causing `System.arraycopy` to throw an `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` — the Java analog of the C++ heap-based buffer over-read in `Sass::Prelexer::skip_over_scopes`, where scope/length values parsed from attacker input were trusted to walk the buffer without a bounds check.

### Impact Explanation
This is reachable by any account issuing a plain contract call to the Zcash-shield precompile with a crafted 2080/2368/2464/2752-byte payload — no special privilege required. While Java throws a runtime exception rather than reading arbitrary out-of-process memory (unlike the C/C++ LibSass over-read), the exception path is caught by a broad `catch (Throwable any)` in the sibling `VerifyMintProof.execute` method, but a review of `VerifyTransferProof.execute`'s catch coverage for these specific array-copy loops determines whether the exception propagates uncaught through the TVM execution path into `Program`/`Runtime`. If uncaught at those layers it can terminate node/backend threads processing the block, producing a denial-of-service against transaction execution — degrading availability of the node's TVM/contract-call serving path.

### Likelihood Explanation
High for reachability (any transaction broadcaster can invoke this precompile with a single crafted call), but the concrete crash/DoS impact depends on whether the surrounding exception handling in the actuator/executor and `Program` layers ultimately converts the resulting Java runtime exception into a contract-execution failure (safe) versus an unhandled fault that destabilizes block processing. I was not able to fully verify the full call chain and exception-handling wrapper around `VerifyTransferProof.execute` within the available iterations, so likelihood of node-crash-level impact (versus a safely-caught contract revert) is uncertain.

### Recommendation
Add explicit bounds checks on `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and derived read ranges for all three loops) against `data.length` immediately after parsing them and before invoking `System.arraycopy`, returning `Pair.of(true, DataWord.ZERO().getData())` on any out-of-range value — mirroring the fix pattern already applied elsewhere in the codebase (e.g., `ContractEventParser.subBytes`'s explicit `start < 0 || start >= src.length || length > src.length - start` guard) [6](#0-5) .

### Proof of Concept
1. Craft a transaction invoking the `VerifyTransferProof` precompile address with `data.length == 2080` (or any valid `SIZE`).
2. Set the 32-byte word at offset `0` (`spendOffset`) to a large value such as `data.length` (or beyond), so that `parseInt(data, spendOffset)` and later `spendOffset + 320*i` exceed the buffer.
3. Keep `spendCount`/`spendAuthSigCount`/`receiveCount` within the accepted `1..2` range so the count check at lines 1496-1499 passes.
4. Submit the transaction; the subsequent `System.arraycopy(data, spendOffset + 320 * i, ...)` call in the spend-processing loop throws an `ArrayIndexOutOfBoundsException`, exercising the unvalidated-offset path. [7](#0-6)
