### Title
Duplicate witness addresses in `VoteWitnessContract.votes` are not merged before being persisted, unlike the equivalent TVM native-contract path - (File: `actuator/src/main/java/org/tron/core/actuator/VoteWitnessActuator.java`)

### Summary
`VoteWitnessActuator` allows any account holder to submit a `VoteWitnessContract` containing a repeated `votes` list where the *sum* of vote counts is validated against the voter's TRON Power, but the list is never checked for (nor merged on) duplicate `vote_address` entries before being written to storage. A newer, functionally equivalent code path — `VoteWitnessProcessor` (used by the TVM `voteWitness` opcode) — explicitly merges votes for the same witness into a `Map<ByteString, Long>` before persisting, with the comment "merge vote for same witness". The legacy transaction actuator was never updated to do the same, so the two entry points for the identical operation behave inconsistently when the input array contains duplicated elements — exactly the bug class described in the external report (repeated elements in a configuration/ratio-bearing array causing the last instance to silently coexist/duplicate rather than being deduplicated).

### Finding Description
In `VoteWitnessActuator.validate()`, the votes list is only checked for: address validity, positive vote count, witness/account existence, and that the aggregate sum does not exceed the voter's TRON Power: [1](#0-0) [2](#0-1) 

There is no check that `vote.getVoteAddress()` is unique across the list. In `countVoteAccount()`, each `Vote` entry — including duplicates for the same witness — is appended independently to both the account and the `VotesCapsule` via `addVotes`/`addNewVotes`: [3](#0-2) 

This is confirmed by the actuator's own test helper `getRepeateContract`, which builds a `VoteWitnessContract` with the *same* witness address repeated N times, demonstrating that the protocol/actuator accepts such duplicated configuration: [4](#0-3) 

By contrast, the equivalent TVM-native `voteWitness` precompile path (`Program.voteWitness` → `VoteWitnessProcessor.execute`) explicitly deduplicates/merges repeated witness addresses into a map before writing votes: [5](#0-4) [6](#0-5) 

This shows the maintainers were aware that repeated elements referring to the same witness must be merged into a single accounting entry, and fixed it for the newer TVM path, but the legacy on-chain-transaction actuator (`VoteWitnessActuator`) — reachable directly by any account broadcasting a signed `VoteWitnessContract` transaction — still allows unmerged duplicate `Vote` entries to be written into `AccountCapsule`'s votes list and `VotesCapsule`'s new-votes list.

### Impact Explanation
The account's persisted votes list and the `VotesCapsule` used for reward/withdrawal accounting can end up containing multiple separate entries for the same witness instead of one merged entry, diverging from the invariant the newer TVM path enforces. Because downstream consumers of these vote records (witness ranking/maintenance aggregation and voter reward withdrawal via `MortgageService`/`VoteRewardUtil`) were not verified in this pass to tolerate duplicate per-witness entries the same way they tolerate a single merged entry, this creates the same class of risk flagged in the report: skewed aggregate accounting that depends on the assumption of one entry per configuration key. This is a Medium-severity data-integrity/consistency issue in the voting/reward bookkeeping reachable by any unprivileged account.

### Likelihood Explanation
Trivial to trigger: any account can submit a normal `VoteWitnessContract` transaction listing the same witness address multiple times (as `VoteWitnessActuatorTest.getRepeateContract` shows is already exercised in tests), as long as the vote-count sum stays within their TRON Power and the total number of vote entries stays within `MAX_VOTE_NUMBER`. No special privileges are required.

### Recommendation
In `VoteWitnessActuator.validate()` and `countVoteAccount()`, deduplicate/merge `Vote` entries by `vote_address` the same way `VoteWitnessProcessor.execute()` does (accumulate into a `Map<ByteString, Long>` before validating the sum and before calling `addVotes`/`addNewVotes`), so that the on-chain transaction path and the TVM native-contract path enforce identical semantics for repeated witness addresses.

### Proof of Concept
1. Freeze balance to obtain TRON Power.
2. Submit a `VoteWitnessContract` transaction whose `votes` list contains the same valid witness address repeated multiple times with small per-entry vote counts, such that the sum stays under the account's TRON Power (as constructed by `getRepeateContract` in the test suite).
3. Observe that `countVoteAccount()` appends one `Vote` entry per list item (not merged) into both `AccountCapsule` and `VotesCapsule`, in contrast to `VoteWitnessProcessor`, which would have merged them into a single entry. [7](#0-6)
