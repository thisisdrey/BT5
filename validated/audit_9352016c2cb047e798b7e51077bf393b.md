### Title
Missing slippage protection in ExchangeInject/ExchangeWithdraw actuators allows sandwich attacks on TRON's Bancor-style exchange pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
TRON's built-in Bancor-style token exchange (`Exchange`/`ExchangeCapsule`) supports four operations: create, inject liquidity, withdraw liquidity, and trade. Only the trade operation (`ExchangeTransactionContract`) carries a caller-specified `expected` minimum-output field for slippage protection. `ExchangeInjectContract` and `ExchangeWithdrawContract` have no equivalent bound, so the ratio-dependent amount of the "other" token that gets pulled from (inject) or paid to (withdraw) the account is whatever the pool ratio happens to be at execution time, with no way for the submitter to bound it.

### Finding Description
`ExchangeInjectActuator.doValidate`/`execute` computes `anotherTokenQuant` as `secondTokenBalance * tokenQuant / firstTokenBalance` (or the symmetric case) using the exchange's live `firstTokenBalance`/`secondTokenBalance` at the moment the transaction executes, and then unconditionally debits that computed amount from the creator's account. [4](#0-3) 

`ExchangeWithdrawActuator` does the same for withdrawals, computing `anotherTokenQuant` from the live pool ratio and crediting it to the account, again with no caller-provided min/max bound. [5](#0-4) 

Because the pool ratio can be changed arbitrarily by any account via a normal `ExchangeTransactionContract` trade (`ExchangeCapsule.transaction`, which directly mutates `firstTokenBalance`/`secondTokenBalance` using the Bancor relay-token math in `ExchangeProcessor`/`SafeExchangeProcessor`), an unprivileged transaction broadcaster can shift the ratio in the block/mempool ordering immediately before the exchange creator's `ExchangeInjectContract` or `ExchangeWithdrawContract` transaction executes, and then reverse the trade immediately afterward. [6](#0-5) 

This mirrors the reported pattern exactly: an operation that changes allocated collateral (inject/withdraw, analogous to vault deposit/withdraw) is executed based on a live, manipulable price/ratio with no minimum-output or maximum-input guard, unlike the sibling operation (`ExchangeTransactionContract`) which does have this protection via `expected`. [7](#0-6) 

### Impact Explanation
Any account that owns/creates an exchange pair (the only party permitted to call Inject/Withdraw, per `!accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())` check) can be sandwiched by any other network participant: an attacker trades against the pool to skew the ratio right before the victim's Inject (forcing the victim to pay far more of the paired token than the fair-value ratio) or right before the victim's Withdraw (causing the victim to receive far less of the paired token than fair value), then reverses the trade to extract the difference risk-free. This is a direct value-extraction/theft-of-funds vector against the exchange creator, reachable purely by broadcasting ordinary signed transactions — no privileged role required. [8](#0-7) 

### Likelihood Explanation
Likelihood is moderate-to-high in practice: it only requires an attacker to observe a pending Inject/Withdraw transaction (visible once broadcast, before it's packed into a block) and race two of their own trade transactions around it — a standard sandwich pattern, not dependent on any malicious SR/witness/committee behavior. The withdraw path adds a coarse ±0.0001 "precision" check, but this bound is a rounding-tolerance check, not a slippage/price bound, and does not prevent ratio manipulation. [9](#0-8) 

### Recommendation
Add an `expected`/minimum-output (for withdraw) and maximum-input or minimum-received (for inject) field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, analogous to the `expected` field already present on `ExchangeTransactionContract`, and enforce it in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` validation before mutating balances.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from the exchange creator for pair (A, B) requesting withdrawal of `tokenQuant` of token A.
2. Attacker submits an `ExchangeTransactionContract` selling a large amount of token B into the pool, which via `ExchangeCapsule.transaction`/`ExchangeProcessor` sharply increases `firstTokenBalance` (A) relative to `secondTokenBalance` (B), skewing the ratio.
3. The victim's `ExchangeWithdrawContract` executes next: `anotherTokenQuant = bigFirstTokenBalance * bigTokenQuant / bigSecondTokenBalance` is now computed against the skewed ratio, so the victim receives far less token B than the pre-attack fair ratio would have paid. [3](#0-2) 
4. Attacker submits a second `ExchangeTransactionContract` reversing the initial trade, restoring the ratio and capturing the difference extracted from the victim's withdrawal, all using only standard, unprivileged transaction broadcasts.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
