Audit Report

## Title
Off-by-one in BEEFY future-block-voting equivocation check (`<` instead of `<=`) - (File: substrate/frame/beefy/src/equivocation.rs)

## Summary
In `check_equivocation_proof`, the `FutureBlockVotingProof` branch rejects a proof only when `vote.commitment.block_number < frame_system::Pallet::<T>::block_number()`, so a vote whose `block_number` exactly equals the current block height is not rejected and is treated as valid "future block" equivocation evidence. Since the current block number is not strictly in the future, this is a boundary error that can cause a legitimate present-block vote to be misclassified as future-block-voting equivocation.

## Finding Description
The code at `substrate/frame/beefy/src/equivocation.rs` lines 274-288 is:
```rust
EquivocationEvidenceFor::FutureBlockVotingProof(equivocation_proof, _) => {
    let FutureBlockVotingProof { vote } = equivocation_proof;
    // Check if the commitment actually targets a future block
    if vote.commitment.block_number < frame_system::Pallet::<T>::block_number() {
        return Err(Error::<T>::InvalidFutureBlockVotingProof);
    }
    let is_signature_valid =
        check_commitment_signature(&vote.commitment, &vote.id, &vote.signature);
    if !is_signature_valid {
        return Err(Error::<T>::InvalidForkVotingProof);
    }
    Ok(())
},
``` [1](#0-0) 

The comment states the intent is to check whether the commitment "actually targets a future block." A block number equal to the current block number is not a future block — it is the block currently being executed. The strict `<` comparison only rejects proofs whose block number is *strictly less than* the current block, meaning `block_number == current_block` is treated as satisfying the "future" condition and passes through to the signature check, then returns `Ok(())`, which is used to justify slashing.

This branch is reachable from the public, unprivileged extrinsics `report_future_block_voting` (signed) and `report_future_block_voting_unsigned`, both routed through `T::EquivocationReportSystem::process_evidence` → `check_equivocation_proof`, and both defined in `substrate/frame/beefy/src/lib.rs`. [2](#0-1) 

`FutureBlockVotingProof(_, _)` carries a fixed `slash_fraction` of `Perbill::from_percent(50)`, so acceptance of this proof drives a 50% slash offence report against the target authority. [3](#0-2) 

## Impact Explanation
The code exactly matches the claim as described. The off-by-one comparison is real and would allow a vote with `block_number == current_block` to slip past the "future block" guard. This is a strict-inequality boundary bug consistent with the "runtime bugs that compromise intended behavior" and "theft or unbacked... slash" impact categories, since acceptance leads to an offence report and 50% slash via `process_evidence`.

However, I could not fully verify from available context (test coverage in `substrate/frame/beefy/src/tests.rs` was not retrievable within the available iterations) whether BEEFY vote commitments' `block_number` semantics in this codebase treat "current block == vote block number" as a genuinely honest/valid vote target that an honest validator would produce, versus whether such a vote could never legitimately be produced at exactly the block being processed (e.g., due to how BEEFY votes are gossiped relative to finality, which typically lags several blocks behind the best/current block). BEEFY votes are cast for already-finalized blocks that are behind the current chain head by design (mandatory blocks, session-boundary voting, etc.), so in practice an honest BEEFY vote's `commitment.block_number` would almost always be well below the current block number by the time a report is processed on-chain, making the `==` boundary condition unlikely to correspond to any real, honestly-produced vote.

## Likelihood Explanation
Exploiting this bug requires an attacker to submit an equivocation report in the exact block whose number equals a legitimately-signed vote's `commitment.block_number`. Because BEEFY votes reference already-agreed-upon or historical block numbers (not the current chain tip), and the report extrinsic executes at a specific, later block height, hitting this exact equality in practice would require the report to be included precisely one block after the vote references a block that is about to become "current" — a narrow, timing-dependent window rather than a generally reachable condition for arbitrary honest votes.

## Recommendation
Change the comparison to correctly identify non-future blocks:
```rust
if vote.commitment.block_number <= frame_system::Pallet::<T>::block_number() {
    return Err(Error::<T>::InvalidFutureBlockVotingProof);
}
```
This ensures only strictly future block numbers are accepted as valid future-block-voting equivocation evidence.

## Proof of Concept
1. Let `N = frame_system::Pallet::<T>::block_number()` at the block in which the report extrinsic will be included.
2. Obtain a genuinely signed BEEFY `VoteMessage` from authority `A` whose `commitment.block_number == N`.
3. Submit `report_future_block_voting_unsigned(equivocation_proof = FutureBlockVotingProof { vote }, key_owner_proof)` in block `N`.
4. The guard `vote.commitment.block_number < frame_system::Pallet::<T>::block_number()` evaluates `N < N == false`, so it is skipped; the signature check passes; `check_equivocation_proof` returns `Ok(())`.
5. `process_evidence` reports the offence with `slash_fraction = 50%` against authority `A`, even though the vote's block number equals (not exceeds) the current chain height at report time.
