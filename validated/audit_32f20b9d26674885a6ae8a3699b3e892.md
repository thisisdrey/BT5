## Analog Finding

### Title
Unbounded first-mover pricing in `ExchangeCreateContract` allows an unprivileged account to seed an insolvent/mispriced bancor pool that later traders unknowingly drain - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeCreateActuator.java)

### Summary
Any account can call `ExchangeCreateActuator` to create a new TRX/TRC10 bancor-style pool with an arbitrary, self-chosen `firstTokenBalance`/`secondTokenBalance` ratio. There is no market-price oracle, minimum-liquidity lock, or sanity check on the relative value of the two token amounts — only that each side is non-zero, within `getExchangeBalanceLimit()`, and that the creator actually owns the tokens. This mirrors the "insolvent initial position" bug class: the first participant unilaterally fixes the economic terms that every later participant is implicitly trusting when they interact with the pool.

### Finding Description
`ExchangeCreateActuator.doValidate()` only checks that:
- the two token IDs differ,
- both `firstTokenBalance`/`secondTokenBalance` are `> 0`,
- both are below `dynamicStore.getExchangeBalanceLimit()`,
- the creator's own account/asset balance covers the amounts. [1](#0-0) 

No check relates `firstTokenBalance` to `secondTokenBalance` in terms of real-world value. The creator can therefore seed a pool with, e.g., `1` unit of a valuable TRC10 token against `100_000_000_000000` TRX (or any other lopsided ratio), establishing a bancor curve (`ExchangeProcessor`/`SafeExchangeProcessor`) whose "price" has no relationship to the token's actual worth. [2](#0-1) 

Subsequent, unrelated users calling `ExchangeTransactionActuator` trade against this bancor curve. `doValidate()` there only checks the caller's own balance and that the computed `anotherTokenQuant` is `>= expected` — it has no way to know the pool's initial ratio was economically nonsensical, since the protocol treats every pool as a valid market: [3](#0-2) 

This is the direct java-tron analog of the UMA report: just as the first PricelessPositionManager sponsor can set an arbitrary/insolvent collateral ratio that later token holders unknowingly rely on, the first `ExchangeCreateContract` sender sets an arbitrary/insolvent asset ratio that later `ExchangeTransactionContract` senders unknowingly trade against, without any economic backstop analogous to a liquidation mechanism.

### Impact Explanation
A malicious or careless first pool creator can:
1. Create a pool with a wildly skewed ratio (e.g., depositing a near-worthless amount of a scarce TRC10 token against a large TRX balance, or vice versa).
2. Wait for other users/dApps/wallets to interact with the exchange by ID without independently verifying its ratio (the same "due diligence" caveat the UMA report calls out as unrealistic for average users).
3. Execute an `ExchangeTransactionContract` themselves (or induce a victim to) to extract the valuable side of the pool for a fraction of its worth, resulting in real value transfer/theft from whichever account funds the counter-trade, or from the creator's own future injected liquidity if third parties `ExchangeInjectContract` into the pool assuming it reflects a fair price.

This is a fund-theft/unbacked-value class of impact reachable purely from a broadcastable, unprivileged transaction (`ExchangeCreateContract` followed by `ExchangeTransactionContract`), satisfying the "concrete unauthorized account operation / theft of funds" bar.

### Likelihood Explanation
Likelihood is high in terms of reachability (anyone can create an exchange with any funded account and any ratio — no permission, no minimum liquidity, no cooldown), but the exploitation window depends on other users interacting with an unfamiliar/unverified exchange ID (via `ExchangeInjectContract` or `ExchangeTransactionContract`) without checking `firstTokenBalance`/`secondTokenBalance` first. Wallets/dApps that let users pick an "exchange ID" by name/token without displaying/validating the pool ratio increase the practical likelihood.

### Recommendation
- Consider requiring a minimum-liquidity lock or a bonding/challenge period before a newly created exchange can be traded against, similar to a liquidation-bond concept, so that manifestly bad ratios can be flagged/withdrawn before real value is extracted.
- Alternatively, expose/require ratio-sanity information (e.g., emit ratio in logs/APIs prominently) so wallets and the HTTP/gRPC query paths (`Wallet`/`TronJsonRpcImpl`) surface the pool's ratio clearly before allowing a trade, reducing reliance on user due diligence.
- Evaluate disallowing the same address from both creating and immediately trading against a freshly created pool within the same block/transaction window, to reduce single-actor sandwich/drain patterns.

### Proof of Concept
1. Account A funds itself with `1` unit of TRC10 token `X` and `1_000_000_000_000_000L` sun of TRX (within `getExchangeBalanceLimit()`).
2. Account A broadcasts `ExchangeCreateContract` with `first_token_id = X, first_token_balance = 1, second_token_id = "_", second_token_balance = 1_000_000_000_000_000` — this passes `doValidate()` entirely per [4](#0-3) , creating a pool where `1` unit of `X` is nominally "worth" a huge TRX balance.
3. Any third party who queries the exchange (e.g., via the HTTP API test flow shown in `ExchangeCreateServletTest`) and trades TRX for `X` via `ExchangeTransactionContract` receives a price computed straight from this skewed bancor curve [5](#0-4) , extracting far more value than intended, or losing far more TRX than the token is worth, depending on direction — mirroring the "recipient unable to settle" / "collateral vulnerable to theft" scenario from the source report.
