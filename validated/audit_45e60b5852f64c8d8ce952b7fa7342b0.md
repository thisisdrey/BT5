## Finding

### Title
Missing length validation on Sapling shielded-transfer fields before crossing into native `librustzcash` FFI calls, enabling out-of-bounds native memory access - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
The CVE-2017-12606 bug class is a classic native out-of-bounds *write* caused by trusting an attacker-influenced buffer to match a fixed internal size before copying into it. In java-tron, pure-Java code is memory-safe (JVM bounds-checks every array access), so the direct analog does not exist inside the VM interpreter. However, `ShieldedTransferActuator` forwards protobuf-supplied, attacker-controlled byte arrays across the JNI/JNA boundary into the native Rust `librustzcash` library, and — unlike several sibling methods in the same wrapper class — does not validate the lengths of those arrays before the native call.

### Finding Description
`ShieldedTransferActuator.checkProof()` extracts `SpendDescription`/`ReceiveDescription` fields straight from the transaction's protobuf `ShieldedTransferContract` and passes them to native code via `JLibrustzcash`: [1](#0-0) 

For `SpendDescription`, `cv` (`getValueCommitment()`), `anchor`, `nullifier`, `rk`, `zkproof`, and `spendAuthoritySignature` are passed with **no size check at all**. For `ReceiveDescription`, only `CEnc`/`COut` are length-checked (`ZC_ENCCIPHERTEXT_SIZE`/`ZC_OUTCIPHERTEXT_SIZE`); `cv`, `cm`, `epk`, and `zkproof` are not: [2](#0-1) 

These arrays are handed directly to `INSTANCE.librustzcashSaplingCheckSpend(...)` and `INSTANCE.librustzcashSaplingCheckOutput(...)`: [3](#0-2) 

By contrast, other native calls in the very same class explicitly validate buffer lengths before invoking the native binding (e.g. `librustzcashToScalar` calls `LibrustzcashParam.validParamLength`/`valid32Params`, and `librustzcashTreeUncommitted` calls `valid32Params`): [4](#0-3) [5](#0-4) 

This asymmetry indicates the codebase authors are aware that native `librustzcash` functions assume fixed-size C buffers (e.g. 32-byte `cv`/`anchor`/`nullifier`/`rk`/`cm`/`epk`, 192-byte `zkproof`, 64-byte signature) and require pre-validation on the Java side — exactly the "trust the caller-supplied length matches the internal fixed buffer" assumption that caused `FillColorRow4`'s OOB write in the OpenCV CVE. Protobuf `bytes` fields impose no length constraint, so an attacker fully controls the length (including zero-length or oversized) of every one of these fields inside a broadcast `ShieldedTransferContract`.

### Impact Explanation
If the native Rust FFI layer for `librustzcashSaplingCheckSpend`/`librustzcashSaplingCheckOutput` reads or writes fixed-size C arrays (`[u8; 32]`, `[u8; 192]`, etc.) using pointers obtained from these under/over-sized Java arrays, this results in native heap out-of-bounds reads/writes — a memory-safety violation outside JVM protection. Depending on the native implementation this can cause node crash/DoS on every full node that validates the transaction (since validation happens for every broadcast transaction of this type), and in the worst case memory corruption that could be leveraged for further exploitation.

### Likelihood Explanation
`ShieldedTransferContract` is a normal broadcastable transaction type; any unprivileged account can submit one with malformed-length Sapling proof fields, and `validate()` unconditionally calls `checkProof()` for every node that processes the transaction — reaching this path requires no special privilege. [6](#0-5) 

### Recommendation
Add explicit length validation (using the same `LibrustzcashParam.validParamLength`/`valid32Params` helpers already used elsewhere in `JLibrustzcash`) for every field of `SpendDescription` (`cv`, `anchor`, `nullifier`, `rk`, `zkproof`, `spendAuthoritySignature`) and the remaining `ReceiveDescription` fields (`cv`, `cm`, `epk`, `zkproof`) before they are passed to any native `librustzcash*` call, mirroring the existing `CEnc`/`COut` size checks.

### Proof of Concept
Construct and broadcast a `ShieldedTransferContract` transaction containing a `SpendDescription` (or `ReceiveDescription`) whose `zkproof`/`cv`/`anchor`/`nullifier`/`rk` fields are set to a byte array shorter or longer than the protocol-mandated fixed size (e.g. 1 byte instead of 32/192 bytes). Submit it via the normal transaction broadcast API; `ShieldedTransferActuator.validate()` → `checkProof()` will forward the malformed array directly into `JLibrustzcash.librustzcashSaplingCheckSpend`/`CheckOutput` without any prior length check, exercising the unvalidated JNI boundary on every validating node.

*Note: I could not inspect the native Rust `librustzcash` source (not present in this Java repo index), so I cannot directly confirm the internal buffer-copy behavior on the native side; the finding is based on the missing Java-side length guard that is present for analogous fields elsewhere in the same class, which is the standard mitigation pattern for this exact JNI/FFI bug class.*
