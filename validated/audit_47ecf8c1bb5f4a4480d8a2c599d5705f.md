### Title
`ft_withdraw`/`mt_withdraw`/`nft_withdraw` with `msg` permanently burns user funds when the external `*_transfer_call` genuinely fails (not just due to gas) - (File: `contracts/defuse/src/contract/tokens/nep141/withdraw.rs`)

### Summary
When a user withdraws a token via `ft_withdraw` (or `mt_withdraw`/`nft_withdraw`) with an optional `msg` (i.e. using `ft_transfer_call`/`mt_batch_transfer_call`/`nft_transfer_call` instead of the plain transfer), the resolver deliberately treats **any** unreadable/failed promise result as a fully successful transfer and skips the refund. This mirrors the BGT bug class: a transfer to an external recipient that predictably fails (e.g. unregistered/rejecting/paused/blacklisted-style receiver, or any genuine `*_transfer_call` panic) leaves the user's internal balance already debited with no way to recover it, permanently freezing the withdrawn value inside the contract.

### Finding Description
`internal_ft_withdraw` first deducts the owner's balance via `self.withdraw(...)`, then asynchronously calls `do_ft_withdraw` → `ft_transfer_call`, and finally `ft_resolve_withdraw` decides whether to refund based on the promise result: [1](#0-0) 

The `Err(_)` arm is reached whenever `env::promise_result_checked` cannot read a successful, well-formed result — this happens both (a) when there truly was insufficient gas to read a large `ft_on_transfer` return value (the specific NEP-141 issue the comment refers to), and (b) whenever the outer `ft_transfer_call` receipt itself failed/panicked for any other reason (receiver has no `storage_deposit` on `token`, receiver panics in `ft_on_transfer`, token contract pauses/blacklists the transfer, token contract has a custom guard analogous to BGT's `onlyApprovedSender`, etc.). In both cases the code takes the same branch and assumes `used = amount.0`, i.e., "the whole amount was transferred", so no refund is issued.

The identical pattern is duplicated for NEP-245 and NEP-171 withdrawals: [2](#0-1) [3](#0-2) 

The underlying helper conflates "gas insufficient to read result" with "any promise failure": [4](#0-3) 

Because `self.withdraw(...)` already subtracted the balance before the promise was even created, and the actual `*_transfer_call` never delivered the tokens to `receiver_id` (it reverted), the value is neither held by the receiver nor credited back to the withdrawing user's ledger. The tokens remain in the defuse contract's real on-chain balance but with no internal owner — an equality break between "amount debited from signer" and "amount delivered to receiver_id + amount refunded to signer".

This is exactly analogous to the BGT report's core defect: an external token/recipient that is designed (or configured) to reject a transfer causes the sender-side contract to lose track of the funds, because the code assumed the only failure mode was benign.

### Impact Explanation
This breaks the conservation invariant `value debited == value delivered + value refunded`. Whenever an `is_call = true` withdraw's outer `*_transfer_call` fails for a reason other than the specific oversized-result/insufficient-gas case (e.g. receiver missing storage, receiver-side revert, or a restricted-transfer-style token), the withdrawn amount is silently and permanently lost to the user with no refund and no delivery — meeting the "funds permanently frozen" Critical impact bucket.

### Likelihood Explanation
Medium: it requires a user (or an integrator building withdraw intents on their behalf) to submit an `FtWithdraw`/`MtWithdraw`/`NftWithdraw` intent with a non-empty `msg` targeting a `token`/`receiver_id` combination whose `*_transfer_call` genuinely fails post-panic (not just a normal `Err` reply) — e.g. omitting `storage_deposit` for a receiver that isn't registered on `token`, or withdrawing a token contract that implements transfer restrictions (blacklist/whitelist/pause), directly mirroring the BGT scenario. No privileged role, upgrade, or victim key is required — this is triggerable by any authenticated intents signer against their own withdraw.

### Recommendation
Distinguish between "insufficient gas to deserialize the result" and "the promise genuinely failed". Where possible, use a two-phase resolve (first check whether the receipt succeeded at all via a cheap void check, then attempt to deserialize the value only on success) rather than collapsing all `PromiseError` cases into "treat as fully used". At minimum, only skip the refund when there is high confidence the failure is due to the known gas-related NEP-141 issue (e.g., by bounding gas so that a genuine failure can be distinguished from a successful-but-unreadable result), and refund by default otherwise, since a false refund on a truly-successful-but-unreadable transfer is a bounded double-spend risk, whereas the current default is an unbounded fund-loss risk.

### Proof of Concept
1. User deposits `FT` into `defuse` and holds an internal balance of `N`.
2. User (or the front-end building the intent) signs an `FtWithdraw { token: FT, receiver_id: R, amount: N, msg: Some("...") , .. }` where `R` has never called `storage_deposit` on `FT` (or `FT` is a token that reverts `ft_transfer_call` to `R` for any policy reason, analogous to BGT's `onlyApprovedSender`).
3. `internal_ft_withdraw` debits `N` from the user's `defuse` balance via `self.withdraw(...)`: [5](#0-4) 
4. `do_ft_withdraw` issues `ft_transfer_call(R, N, ...)`, which panics on `FT` because `R` is unregistered/rejected.
5. `ft_resolve_withdraw` receives a promise failure, falls into `Err(_) => amount.0`, treating it as fully used, and issues **no** refund: [6](#0-5) 
6. Result: user's `mt_balance_of` for `FT` in `defuse` is now `0` (debited), `R` never received any `FT` (transfer reverted), and no refund credit was made — the `N` tokens are permanently unaccounted for/frozen.

#[near]
impl FungibleTokenWithdrawResolver for Contract {
    #[private]
    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }

/// Returns `Ok(())` if the promise at `result_idx` succeeded with an empty result.
/// This is the expected outcome for void-returning cross-contract calls
/// (e.g. `ft_transfer`, `nft_transfer`, `mt_batch_transfer`).
#[inline]
pub fn promise_result_checked_void(result_idx: u64) -> PromiseResult<()> {
    let data = env::promise_result_checked(result_idx, 0)?;
    debug_assert!(data.is_empty());
    Ok(())
}
