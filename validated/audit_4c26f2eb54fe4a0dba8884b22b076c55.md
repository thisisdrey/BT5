## Title
Floating-point reward-share computation in `MortgageService.computeReward()` can allocate more than a witness's actual reward pool, minting unbacked TRX allowance - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The external report flags PoolTogether's `_maxYieldVaultWithdraw()` for relying on an approximate conversion function (`convertToAssets`) instead of an exact one (`previewRedeem`), which can make the vault believe more assets are withdrawable than actually back the shares. The analogous bug class in java-tron is the use of imprecise `double` arithmetic to split a fixed, exact integer reward pool among many claimants, which can cause the sum of individually rounded/approximated payouts to exceed the pool that actually backs them.

### Finding Description
`MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` (the legacy/"old" reward algorithm path) computes each voter's share of a witness's total cycle reward using floating-point division and multiplication instead of exact integer math: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

Unlike the newer algorithm (`getNewRewardAlgorithmReward` / `VoteRewardUtil.computeReward`), which tracks per-witness reward accumulation with exact `BigInteger` "Vi" delta accounting [2](#0-1) , this legacy path independently computes `voteRate * totalReward` per voter with `double` precision. Because `double` cannot exactly represent most fractions, and each voter's share is rounded independently (not derived by subtracting a running remainder), the sum of all voters' individually-rounded shares for the same `(cycle, srAddress)` `totalReward` bucket is not guaranteed to equal — and can exceed — the actual `totalReward` value stored via `delegationStore.getReward(cycle, srAddress)` [3](#0-2) .

This function is used both to answer the read-only reward query (`queryReward`, exposed via `/wallet/getReward` `GetRewardServlet` and gRPC `getRewardInfoCommon`) and to actually credit `allowance` during `withdrawReward`, which is triggered by any account broadcasting a `WithdrawBalanceContract` transaction: [4](#0-3) 

`withdrawReward()` calls `adjustAllowance(address, reward)`, which unconditionally increases the target account's `allowance` field by the computed (possibly over-approximated) `reward`: [5](#0-4) 

There is no check that the cumulative amount credited to all voters of a given `(cycle, srAddress)` pair does not exceed the `totalReward` originally recorded for that witness/cycle in `delegationStore`.

### Impact Explanation
Because `adjustAllowance` directly increases `AccountCapsule.allowance`, and `WithdrawBalanceActuator`/`WithdrawRewardProcessor` later moves that `allowance` into spendable `balance` [6](#0-5) , any systematic over-approximation from the floating-point division creates TRX balance that is not backed by an equivalent debit anywhere else in the system (the source `delegationStore` reward bucket is not decremented per-claim to enforce a hard cap). Over many voters/cycles this is a genuine unbacked-balance / inflation vector, matching the "returns too much" bug class from the source report, but manifesting here as literal token minting rather than an incorrect view function.

### Likelihood Explanation
This path (`getOldReward` → `computeReward(cycle, votes)`) is only exercised for cycles prior to `NEW_REWARD_ALGORITHM_EFFECTIVE_CYCLE` and is gated by `allowOldRewardOpt()` [7](#0-6) , so its practical exposure is limited to legacy/historical cycles and to networks/testnets where this flag/era still applies, reducing likelihood on chains that have already passed the reward-algorithm cutover. It also requires many small-fraction voters splitting the same reward bucket to accumulate a meaningful drift, and is not directly triggerable at will by an attacker to an arbitrary magnitude in a single transaction.

### Recommendation
Replace the floating-point `voteRate` computation with exact integer arithmetic (e.g., `BigInteger` multiply-then-divide as already done in the new algorithm), and additionally cap the sum of rewards paid out per `(cycle, srAddress)` bucket to the recorded `totalReward`, decrementing the bucket as it is claimed, so no combination of claims can exceed the actual pool.

### Proof of Concept
1. For a given witness `W` and cycle `C`, set `totalReward = delegationStore.getReward(C, W)` to a value that does not divide evenly among many small voters (e.g. `totalReward = 100`, with 7 voters each holding `1/7` of `totalVote`).
2. Each voter calls `WithdrawBalanceContract` (or triggers the equivalent TVM `withdrawReward` native contract) for their address; `computeReward` computes `voteRate = (double) userVote / totalVote` and `reward += voteRate * totalReward` independently for each voter.
3. Sum the seven individually-credited `allowance` deltas: due to double rounding, the total credited across all seven withdrawals can exceed `100`, i.e., exceed the actual `totalReward` recorded for the witness/cycle, while `delegationStore`'s reward bucket for that witness/cycle is never decremented to enforce the cap.

```java
  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
```
