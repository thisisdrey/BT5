### Title
Signature schema in the `validatemultisign` TVM precompile allows cross-contract and cross-chain signature reuse - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract, exposed to any smart contract via the TVM opcode `validatemultisign(address,uint256,bytes32,bytes[])`, authorizes an action by recovering signer addresses from a message digest built solely from `address`, `permissionId`, and a caller-supplied `data` value. This digest contains no chain identifier, no binding to the calling/consuming contract, and no transaction-specific nonce, so a signature produced to authorize one action can be replayed verbatim by any other contract (or on any other TRON-compatible chain/fork/private deployment) that happens to present the same `(address, permissionId, data)` tuple.

### Finding Description
`ValidateMultiSign.execute` computes the signing digest as: [1](#0-0) 

```
DataWord[] words = DataWord.parseArray(rawData);
byte[] address = words[0].toTronAddress();
int permissionId = words[1].intValueSafe();
byte[] data = words[2].getData();

byte[] combine = ByteUtil.merge(address, ByteArray.fromInt(permissionId), data);
byte[] hash = Sha256Hash.hash(CommonParameter
    .getInstance().isECKeyCryptoEngine(), combine);
```

then it recovers each signer and checks accumulated permission weight against the account's on-chain `Permission`: [2](#0-1) 

The recovered address is derived purely by ECDSA/ECRecover from `hash` and the supplied signature via `recoverAddrBySign`: [3](#0-2) 

This is structurally identical to the reported Hermez `_checkSig` bug class: a fixed message-authorization schema whose digest never incorporates:
- The **consuming contract's address** (analogous to Hermez's "contract address" mitigation) — so any Solidity contract deployed on TRON that calls `validatemultisign(address,uint256,bytes32,bytes[])` with the *same* `(address, permissionId, data)` triple will accept a signature that was produced to authorize a completely different dApp/contract's operation.
- Any **chainId / network identifier** — so the identical signature remains valid if the account and permission structure are replicated on a different TRON-compatible chain (public testnet, a forked chain, or any private/enterprise TRON deployment), exactly mirroring the "re-deployment/fork" scenario in the original report.

The precompile also has no built-in nonce or expiration; `data` is entirely caller/dApp-defined semantic content (e.g., an order hash, a withdrawal request hash), so uniqueness is left entirely to each individual consuming contract's design.

### Impact Explanation
Any dApp built on TRON that relies on `validatemultisign` to authorize sensitive account operations (withdrawals, permission changes, order execution, etc.) using off-chain-gathered multisig signatures is exposed to replay: an attacker who obtains a validly-signed authorization for one purpose/contract can present the identical signature to a different consuming contract, or to the same contract redeployed/forked elsewhere, to trigger unauthorized account operations or bypass the intended authorization schema — a concrete unauthorized-account-operation / theft-of-funds impact reachable purely by an unprivileged contract caller crafting a `CALL` to the precompile address.

### Likelihood Explanation
`validatemultisign` is a documented, generally-available TVM precompile (gated only by `VMConfig.allowTvmSolidity059()`), directly callable by any deployed smart contract, which in turn is reachable by any unprivileged transaction broadcaster triggering that contract. Exploitability depends on a downstream contract's specific usage pattern (e.g., reusing the same `data` value across dApps, or the ecosystem containing multiple chains/forks sharing account/permission state), which is common in multi-chain/enterprise TRON deployments and cross-dApp authorization designs, making this a realistic, medium-to-high likelihood analog rather than a purely theoretical one.

### Recommendation
Bind the `validatemultisign` digest to context that prevents cross-contract and cross-chain reuse: incorporate the calling contract's address (`this`/`msg.sender` context) and a chain/network identifier (or explicit domain separator) into the `combine` buffer before hashing in `ValidateMultiSign.execute`, and document that consuming contracts must additionally include their own nonce/expiration in `data`. Apply the same reasoning to `BatchValidateSign`, which has an analogous unscoped hash-based signature check.

### Proof of Concept
1. Deploy Contract A on TRON mainnet; Contract A calls `validatemultisign(accountAddr, permissionId, dataHash, sigs)` to authorize a withdrawal keyed on `dataHash`.
2. A permission-key holder signs `sha256(accountAddr || permissionId || dataHash)` to authorize this one withdrawal via Contract A.
3. Deploy Contract B (same or attacker-controlled) — either on the same TRON mainnet or on a forked/private TRON-compatible chain where `accountAddr` has an identical permission configuration — designed to consume the same `dataHash` value for a different, attacker-beneficial operation.
4. Attacker calls Contract B and supplies the exact same `sigs` obtained from step 2. Because `combine = address || permissionId || data` never varies with the calling contract or chain, `ValidateMultiSign.execute` recovers the same signer address and reports sufficient permission weight, authorizing the action in Contract B without the signer ever intending it.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
