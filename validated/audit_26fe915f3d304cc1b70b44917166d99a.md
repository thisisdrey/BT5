## Title
Excess NEAR attached to `storage_deposit()` calls is not returned to the user's balance - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
When a user includes a `storage_deposit` amount with `FtWithdraw`, `MtWithdraw`, `NftWithdraw`, or a standalone `StorageDeposit` intent, the full amount is debited from the user's internal wNEAR balance, unwrapped to native NEAR, and attached in its entirety to a cross-contract `storage_deposit()` call on the target token/receiver contract. Per NEP-145, if the attached deposit exceeds the actual storage cost, the target contract refunds the excess — but that refund goes back to the intents contract itself (the direct caller/predecessor), not to the user who was debited. The contract never inspects the `storage_deposit()` result to reclaim or re-credit this excess to the user's ledger.

### Finding Description
The `withdraw()` call subtracts the entire `storage_deposit` amount from the user's wNEAR balance before any external call is made: [1](#0-0) 

That amount is unwrapped from wNEAR to native NEAR via `near_withdraw`, then the callback `do_ft_withdraw` attaches the *entire* amount as `deposit` to `ext_storage_management::ext(withdraw.token).storage_deposit(...)`: [2](#0-1) 

The same pattern is used for the standalone `StorageDeposit` intent: [3](#0-2) 

Under NEP-145, `storage_deposit()` is required to refund any deposit exceeding the amount actually needed to satisfy the storage balance bounds. That refund is sent back to the predecessor of the call — i.e., the intents (`Contract`) account — not to the user or to the intended `deposit_for_account_id`/`receiver_id`. Neither `do_ft_withdraw`, `do_storage_deposit`, `do_nft_withdraw`, nor `do_mt_withdraw` inspect the promise result of `storage_deposit()` to determine how much was actually consumed, so any refunded NEAR silently becomes part of the contract's own account balance and is never credited back into any user's internal wNEAR balance in `storage.accounts`.

This breaks the conservation binding "value debited versus value delivered plus refunded": the user is debited the full `storage_deposit` amount from their internal ledger, but only the portion actually consumed for storage registration is "delivered," and the refunded remainder is captured by the contract instead of being returned to the paying user.

The test suite for this exact code path implicitly acknowledges the surplus is retained by the contract rather than the user, only asserting that the contract's own NEAR balance does not decrease — it never asserts the excess is credited back to any user account: [4](#0-3) 

### Impact Explanation
Any unprivileged user who supplies a `storage_deposit` amount larger than the minimum required by the target contract's storage bounds (an easy, common mistake — the intents protocol does not query or cap this to the actual required bounds) permanently loses the excess wNEAR-equivalent value; it is absorbed into the intents contract's own NEAR balance rather than any user's balance. This is a concrete, unauthorized value loss for the paying user each time it occurs across `FtWithdraw`, `NftWithdraw`, `MtWithdraw`, and `StorageDeposit` intents that carry a `storage_deposit` field, matching the "value debited versus value delivered plus refunded" custody binding from the reference report.

### Likelihood Explanation
High likelihood: no special conditions or privileged roles are required. Any user submitting an intent that includes `storage_deposit` with an amount larger than the receiver's actual outstanding storage requirement (a very plausible scenario since users must estimate this externally) triggers the loss on every execution.

### Recommendation
After the `storage_deposit()` cross-contract call resolves, parse its returned `StorageBalance` (or track before/after NEAR balance of the intents contract) to determine the amount actually consumed, and re-credit any unused surplus back to the paying user's internal wNEAR balance (similar to the `ft_resolve_withdraw` refund pattern already used for FT transfers) instead of silently retaining it in the contract's own account.

### Proof of Concept
1. User submits an `FtWithdraw` intent with `storage_deposit: Some(NearToken::from_near(1000))` for a receiver that only requires a small standard NEP-141 storage deposit (e.g., 0.00125 NEAR).
2. `internal_ft_withdraw` debits the full 1000 NEAR-equivalent wNEAR from the user's balance [1](#0-0) .
3. `near_withdraw` unwraps the full 1000 NEAR, and `do_ft_withdraw` attaches all of it to `storage_deposit()` on the token contract [2](#0-1) .
4. The token contract's `storage_deposit()` implementation refunds ~999.99875 NEAR back to the predecessor, which is the intents contract itself.
5. No callback logic recovers or re-credits this refund to the user; it becomes part of the intents contract's own NEAR account balance permanently, confirmed by the test only checking the contract's own balance does not decrease, never that the user is made whole [5](#0-4) .
