### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` can throw an uncaught `ArithmeticException` during TVM contract execution - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit(AccountCapsule)`, which is on the hot path of every TVM `CALL`/contract-trigger transaction to compute the energy limit derived from frozen-for-energy balance, divides by `totalEnergyWeight` while only relying on a Java `assert` statement to prevent a zero denominator. `assert` is a no-op unless the JVM is started with `-ea`, which production java-tron nodes are not. The sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit` has an explicit runtime guard (`if (allowNewReward() && totalEnergyWeight <= 0) return 0;`) that `RepositoryImpl`'s copy is missing.

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit`: [1](#0-0) 

only checks `frozeBalance < TRX_PRECISION` before reading `totalEnergyWeight` from `DynamicPropertiesStore`, then executes:
```
assert totalEnergyWeight > 0;
if (hardenResourceCalculation()) {
  return BigInteger.valueOf(energyWeight)
      .multiply(BigInteger.valueOf(totalEnergyLimit))
      .divide(BigInteger.valueOf(totalEnergyWeight))
      .longValueExact();
}
```
`assert` statements compile to bytecode guarded by the static field `$assertionsDisabled`, and are disabled by default (the JVM must be launched with `-ea` for them to execute), so in a standard production deployment this line is a complete no-op. If `totalEnergyWeight` is ever `0` when this path is reached with `hardenResourceCalculation()` enabled, `BigInteger.divide(BigInteger.ZERO)` throws `ArithmeticException: BigInteger divide by zero`.

Contrast this with the parallel, better-guarded implementation used elsewhere: [2](#0-1) 

which explicitly returns `0` when `totalEnergyWeight <= 0` under the new-reward flag, rather than relying on an assertion. The `RepositoryImpl` copy used inside VM execution (`VMActuator.getAccountEnergyLimitWithFloatRatio`) lacks this defensive check entirely: [3](#0-2) 

This call path is reached by any unprivileged transaction broadcaster who triggers a smart contract (`TriggerSmartContract`), i.e. any account can reach `VMActuator.call()` → `getAccountEnergyLimitWithFloatRatio()` → `rootRepository.calculateGlobalEnergyLimit(account)`.

### Impact Explanation
An uncaught `ArithmeticException` thrown deep inside energy-limit computation during contract execution is not one of the checked/expected exceptions in the surrounding contract-execution flow of `VMActuator`. Depending on where in block/transaction processing it propagates to, this can manifest as an unexpected runtime exception escaping normal `ContractExeException`/`ContractValidateException` handling used elsewhere in actuators (note how other actuators, e.g. `ExchangeInjectActuator`/`ExchangeWithdrawActuator`, explicitly catch `ArithmeticException` around similar `BigInteger` divisions — a pattern absent here). This can cause a transaction to fail in an unhandled way during block application, which is a risk to node availability/consensus processing rather than a simple validation failure, matching the "node crash/halt" impact class for a Medium-severity division-by-zero bug.

### Likelihood Explanation
Reachability is only proven for the direct code path (any account triggering a contract can reach `calculateGlobalEnergyLimit`), and the divide-by-zero code path is only exercised when `hardenResourceCalculation()` is enabled AND `totalEnergyWeight == 0` at the moment a qualifying account (with `frozeBalance >= TRX_PRECISION`) calls into this function. I was **not able to conclusively determine** a concrete sequence of actuator calls that drives global `totalEnergyWeight` to exactly `0` while a specific account still retains `>= TRX_PRECISION` frozen-for-energy balance under the old freeze model that `RepositoryImpl.calculateGlobalEnergyLimit` uses (unlike `EnergyProcessor`'s version, this copy does not delegate to a V2-aware calculation even when `supportUnfreezeDelay()`/FreezeV2 is active, which is itself a discrepancy but requires further investigation to prove an exploitable state transition). Because of this residual uncertainty about state-reachability of `totalEnergyWeight == 0` concurrent with a qualifying account balance, I flag this finding with **reduced confidence on likelihood**, though the missing-guard/reliance-on-disabled-assert issue itself is a clear, provable code defect analogous to the reported `sharesToTokenAmount` division-by-zero bug class.

### Recommendation
Replace the `assert totalEnergyWeight > 0;` in `RepositoryImpl.calculateGlobalEnergyLimit` with an explicit runtime check mirroring `EnergyProcessor.calculateGlobalEnergyLimit`:
```java
if (totalEnergyWeight <= 0) {
  return 0;
}
```
before the `hardenResourceCalculation()` branch, ensuring the `BigInteger` division can never execute with a zero divisor regardless of JVM assertion settings.

### Proof of Concept
Not independently reproduced against a live node; based on static code analysis only. The exploit precondition (`totalEnergyWeight == 0` while a triggering account has `frozeBalance >= TRX_PRECISION` under the old/non-V2 freeze model consumed by `RepositoryImpl.calculateGlobalEnergyLimit`) was not fully validated within the scope of this investigation — a background engineer should trace all `addTotalEnergyWeight`/`saveTotalEnergyWeight` call sites (`FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceV2Actuator`, `UnfreezeBalanceV2Actuator`, `CancelAllUnfreezeV2Actuator`, `FreezeBalanceProcessor`, `UnfreezeBalanceProcessor`) to confirm whether such a state is reachable in a single block/transaction sequence.
