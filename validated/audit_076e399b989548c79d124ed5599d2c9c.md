Based on my investigation, I found a strong local analog to the "arbitrary pool contract" bug pattern in the Snowbridge outbound queue v2 message converter.

### Title
Ethereum-native token unlock command trusts caller-supplied token address without registry verification - ([File: bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs])

### Summary
The external report's core broken invariant is: a public entrypoint accepts an arbitrary, unregistered contract/address supplied by the caller and derives a privileged payout (mint amount) directly from that untrusted input, instead of first validating the address against an authoritative registry (the Abacus `accreditedAddresses`). The local analog lives in Snowbridge's V2 outbound XCM-to-command converter, where the Ethereum-native-asset (ENA) path builds an `UnlockNativeToken` command directly from a caller-controlled `Location`'s raw `AccountKey20` bytes, with no cross-check against any registered/known token registry — unlike the sibling Polkadot-native-asset (PNA) path in the very same file, which explicitly re-validates the asset id against the registered mapping.

### Finding Description
In `extract_polkadot_native_assets`, before emitting `Command::MintForeignToken`, the code performs a mandatory round-trip check: [1](#0-0) 
It computes `token_id` from the caller-supplied `asset_id`, then requires that `ConvertAssetId::maybe_convert(token_id)` (backed by the `ForeignToNativeId` registration storage populated only via `do_register_token`) round-trips back to the exact same `asset_id`. This guards against exactly the kind of location/hash-collision or unregistered-asset spoofing that the OtterSec report describes (an attacker substituting an untrusted source of truth for a validated one).

By contrast, `extract_ethereum_native_assets`, which emits `Command::UnlockNativeToken`, contains no equivalent registry check at all: [2](#0-1) 
It simply unpacks whatever `AccountKey20` bytes appear in the caller-supplied `Location` and uses them directly as the Ethereum `token` address in the `UnlockNativeToken` command — the analog of the vulnerable `borrow()` function trusting `getPayoutPerRes`/`getReservationStatus` from an attacker-supplied contract instead of checking `controller.accreditedAddresses(_pool)`.

The test suite even demonstrates the project's own awareness of this exact bug class on the PNA side — `xcm_converter_mints_registered_token_id_for_colliding_general_key_location` proves a location-collision mint-under-wrong-token-id was found and fixed for PNAs: [3](#0-2) 
No corresponding test or guard exists for the ENA/`UnlockNativeToken` path.

### Impact Explanation
`UnlockNativeToken` instructs the Ethereum Gateway contract to release real, reserve-backed ERC20/ETH liquidity to a recipient. If the `token` field in that command can be influenced to reference a token address the sender does not have genuine, correctly-priced reserve claim over (e.g., via a location whose `AccountKey20` bytes alias an address that was never validated as "this chain's representation of that specific Ethereum token"), the result is unauthorized unlock of bridge-held funds — a direct fund-theft / bridge-drain primitive, matching the "theft or unbacked mint or unlock" category in the impact gate.

### Likelihood Explanation
This is a design asymmetry rather than a fully proven live exploit from my read-only review: reaching `extract_ethereum_native_assets` requires that the caller's `WithdrawAsset`/holding-register content for that `Location` actually be backed by a real balance in the sender's own asset pallet (execution of prior XCM instructions on AssetHub), which is the main mitigating factor limiting exploitability. However, the complete absence of the registry round-trip check that the PNA path enforces — despite the PNA path's own commit history showing this exact bug class (collision-based mis-minting) was already found and patched once — indicates the ENA path was not audited to the same standard and is the weakest link if any code path can cause the holding register to attribute a mismatched or attacker-influenced token identity to real value (e.g., via reanchoring/asset-id aliasing quirks, or future changes to how `Location`s are constructed upstream). Given I could not fully trace every upstream caller that populates `enas`/`deposit_assets` before this function runs, I could not conclusively prove end-to-end exploitability, only the structural absence of the same safeguard applied elsewhere in the identical file.

### Recommendation
Add a registry-based validation step to `extract_ethereum_native_assets` mirroring the PNA path: verify that the `token` (H160) derived from the `Location` corresponds to a token address whose reserve/registration state is authoritative for the bridge (e.g., cross-check against a known-Ethereum-token allowlist or a `NativeToNativeId`-style reverse mapping), rather than trusting the raw bytes embedded in the caller-supplied `Location` as-is.

### Proof of Concept
Not independently reproducible from static review alone — a working PoC would require constructing an XCM program (via a live BridgeHub/AssetHub environment) whose `WithdrawAsset` holding-register entry for an ENA `Location` can be made to diverge from the token's true registered Ethereum identity, then observing `extract_ethereum_native_assets` emit an `UnlockNativeToken` command for that mismatched `token` address, analogous to the `xcm_converter_mints_registered_token_id_for_colliding_general_key_location` test already present for the PNA/`MintForeignToken` path but with no ENA/`UnlockNativeToken` equivalent test existing to rule it out.

	/// Extract ethereum native assets
	fn extract_ethereum_native_assets(
		&mut self,
		enas: &Assets,
		deposit_assets: &AssetFilter,
		recipient: H160,
	) -> Result<Vec<Command>, XcmConverterError> {
		let mut commands: Vec<Command> = Vec::new();
		for ena in enas.clone().into_inner().into_iter() {
			// Check the the deposit asset filter matches what was reserved.
			if !deposit_assets.matches(&ena) {
				return Err(FilterDoesNotConsumeAllAssets);
			}

			// only fungible asset is allowed
			let (token, amount) = match ena {
				Asset { id: AssetId(inner_location), fun: Fungible(amount) } => {
					match inner_location.unpack() {
						(0, [AccountKey20 { network, key }]) if self.network_matches(network) => {
							Ok((H160(*key), amount))
						},
						// To allow ether
						(0, []) => Ok((H160([0; 20]), amount)),
						_ => Err(AssetResolutionFailed),
					}
				},
				_ => Err(AssetResolutionFailed),
			}?;

			// transfer amount must be greater than 0.
			ensure!(amount > 0, ZeroAssetTransfer);

			commands.push(Command::UnlockNativeToken { token, recipient, amount });
		}
		Ok(commands)
	}

#[test]
fn xcm_converter_mints_registered_token_id_for_colliding_general_key_location() {
	let network = BridgedNetwork::get();
	let beneficiary_address: [u8; 20] = hex!("2000000000000000000000000000000000000000");
	let amount = 1_000_000;
	let fee_amount = 1_000;
	let (victim_location, attacker_location) = general_key_length_collision_locations();
	assert_ne!(victim_location, attacker_location, "Locations must differ");

	// Deterministic collision:
	let victim_token_id = TokenIdOf::convert_location(&victim_location).unwrap();
	let attacker_token_id = TokenIdOf::convert_location(&attacker_location).unwrap();
	assert_ne!(victim_token_id, attacker_token_id, "TokenIds should differ after the fix");

	// Optional debug prints for report clarity
	println!("victim_location     = {victim_location:?}");
	println!("attacker_location   = {attacker_location:?}");
	println!("victim_token_id     = {victim_token_id:?}");
	println!("attacker_token_id   = {attacker_token_id:?}");

	// Build XCM that reserves *attacker* asset location (but will mint under victim token_id)
	// V2 XCM format requires: WithdrawAsset(fee), PayFees, ReserveAssetDeposited, AliasOrigin,
	// DepositAsset, SetTopic
	let fee_asset = Asset { id: AssetId(Location::new(0, [])), fun: Fungible(fee_amount) };
	let assets: Assets =
		vec![Asset { id: AssetId(attacker_location.clone()), fun: Fungible(amount) }].into();
	let filter: AssetFilter = assets.clone().into();

	// Create an origin location for AliasOrigin
	let origin_location = Location::new(1, [Parachain(2000)]);

	let message: Xcm<()> = vec![
		WithdrawAsset(vec![fee_asset.clone()].into()),
		PayFees { asset: fee_asset },
		ReserveAssetDeposited(assets.clone()),
		AliasOrigin(origin_location),
		DepositAsset {
			assets: filter,
			beneficiary: AccountKey20 { network: None, key: beneficiary_address }.into(),
		},
		SetTopic([0; 32]),
	]
	.into();

	let mut converter =
		XcmConverter::<VictimOnlyTokenIdConvert, (), EverythingBut<Equals<AssetHubLocation>>>::new(
			&message, network,
		);
	let result = converter.convert();
	assert_eq!(result.err(), Some(XcmConverterError::InvalidAsset));
}
