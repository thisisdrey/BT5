### Title
Unbounded attacker-controlled length used for array allocation in `ValidateMultiSign` precompiled contract input parsing - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2017-12674 is a CPU/resource-exhaustion bug class where a parser (`ReadPDBImage`) trusts an attacker-supplied length/size field and loops/allocates based on it without validating it against the actual available input. The `ValidateMultiSign` precompiled contract in the TVM contains the same bug-class pattern: helper functions `extractBytesArray` and `extractSigArray` read a 32-byte word from the calldata and use it directly as an array-allocation size and loop bound before any bound is enforced.

### Finding Description
`ValidateMultiSign.execute()` is reachable by any account issuing a `TriggerSmartContract` transaction that calls the precompiled contract address (any contract can `CALL` it, e.g. via `abi.encodeWithSignature`). Inside `execute`, the signature array offset and length come straight from the calldata: [1](#0-0) 

The extraction helpers derive the array size directly from an attacker-controlled `DataWord`: [2](#0-1) [3](#0-2) 

`words[offset].intValueSafe()` can return any value up to `Integer.MAX_VALUE`, and this value is used immediately for `new byte[len][]` before any upper-bound check. The `MAX_SIZE` (5) check that limits the signature count is only performed for the `extractSigArray` branch, and only when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [4](#0-3) 

When that hard-fork switch is not active (or on any private/enterprise chain built from this codebase that has not activated the corresponding proposal), the `extractBytesArray` path is used, which has no length cap at all before allocating `bytesArray = new byte[len][]` and looping `len` times doing further indexed reads (`words[offset + i + 1]`), each of which can throw or, for moderately large but not immediately-OOM values of `len`, cause excessive CPU time inside a single energy-limited call while allocating references disproportionate to the flat per-signature energy price (`ENGERYPERSIGN = 1500`), which is computed from `data.length`, not from the untrusted `len` read out of the payload.

This mirrors ReadPDBImage: a size value taken from attacker-supplied data drives an allocation/loop bound with no independent verification against the real amount of available data, causing CPU/memory exhaustion.

### Impact Explanation
A crafted `TriggerSmartContract` (calling any contract that in turn calls the `ValidateMultiSign` precompile, or directly if precompile invocation is permitted) can supply a raw length word decoupled from the actual signature energy cost, forcing the node to allocate an oversized array or iterate far beyond the amount of energy actually charged for the call. Depending on the magnitude chosen, this can throw `OutOfMemoryError` (uncaught in this call path) or consume CPU disproportionate to the energy paid, both denial-of-service conditions against the validating node while the transaction is executed.

### Likelihood Explanation
Reachability depends on the `allowTvmSelfdestructRestriction()` hard-fork flag: on current mainnet where this proposal has been activated, the `extractSigArray` path is used and is capped by `MAX_SIZE`, mitigating this specific analog. The unguarded `extractBytesArray` path remains compiled and reachable on any deployment (testnet, private chain, or a chain where this particular proposal has not been activated) that has not enabled the flag, and no additional guard exists at the call site for that branch — so the vulnerable behavior is present in the source and only conditionally neutralized by chain-parameter activation state, which I could not verify from the codebase alone.

### Recommendation
Bound `len`/`sigArraySize` extracted from calldata by an explicit `MAX_SIZE` (or a sane upper bound derived from `words.length`) unconditionally in both `extractBytesArray` and `extractSigArray`, before performing any array allocation, independent of the `allowTvmSelfdestructRestriction()` feature flag. Also validate `offset` and derived indices against `words.length` before dereferencing to avoid unrelated `ArrayIndexOutOfBoundsException`s.

### Proof of Concept
Construct calldata for `ValidateMultiSign` such that:
- `words[3]` points to an offset `k` within the encoded words.
- `words[k]` (used as `len` in `extractBytesArray`, reached when `allowTvmSelfdestructRestriction()` is false) is set to a large value (e.g. `0x7FFFFFFF`).

Invoking `words[offset].intValueSafe()` at [5](#0-4) 
then executes `new byte[len][]`, immediately attempting to allocate an array of ~2^31 references, well before the `signatures.length > MAX_SIZE` check at [6](#0-5) 
can ever be reached, causing the node executing the transaction to throw `OutOfMemoryError` or spend excessive time/memory relative to the energy actually paid for the call.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
