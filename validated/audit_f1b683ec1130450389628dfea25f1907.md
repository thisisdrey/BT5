### Title
`unbond` in pallet-nomination-pools omits pending-slash application before dissolving points, unlike `withdraw_unbonded` - ([File: substrate/frame/nomination-pools/src/lib.rs])

### Summary
The external report's core broken invariant is: a value-adjustment step (interest/slash reconciliation) that is explicitly enforced in one code path is silently omitted in a sibling path that mutates the same accounted balance, letting a caller extract more value than they are entitled to. The closest verifiable local analog is in `pallet-nomination-pools`: `Pallet::<T>::withdraw_unbonded` explicitly calls `Self::do_apply_slash(&member_account, None, false)` to reconcile a member's pending slash before computing `balance_to_unbond` [1](#0-0) , while `Pallet::<T>::unbond`, which also dissolves points into balance via `bonded_pool.dissolve(unbonding_points)` and issues a withdrawable claim, contains **no** call to `do_apply_slash` before doing so [2](#0-1) .

### Finding Description
`do_apply_slash` reconciles the gap between a member's actual held/delegated balance and their `expected_balance` derived from pool points, i.e. `member_pending_slash` computes `actual_balance.saturating_sub(expected_balance)` [3](#0-2)  and `do_apply_slash` then calls `T::StakeAdapter::member_slash` to burn that pending amount from the member's delegated hold [4](#0-3) . This mechanism is explicitly described as a pre-condition the pallet tries to enforce before letting a member remove funds: the doc-comment on `withdraw_unbonded` states "If the pool has any pending slash, we also try to slash the member before letting them withdraw" [5](#0-4) , and the code enforces it with `match Self::do_apply_slash(...)` right before `ok_to_withdraw_unbonded_with` [1](#0-0) .

`unbond`, however, performs `bonded_pool.ok_to_unbond_with(...)`, pays out rewards, then goes straight to `bonded_pool.dissolve(unbonding_points)` and `T::StakeAdapter::unbond(...)` without ever calling `do_apply_slash` for the member first [2](#0-1) . `dissolve` computes `points_to_balance` from the **pool-level** `active_stake`/`points` ratio only [6](#0-5) ; it has no visibility into the member-level pending slash tracked separately via `member_pending_slash`/`member_delegation_balance` under the `DelegateStake` adapter [7](#0-6) . This is the same shape of bug as the report: a downstream accounting adjustment ("stage yield"/"apply slash") is mandatory-by-design in one entry point but is skippable via a sibling entry point (`withdraw_yt`/`merge` vs. `unbond`) that touches the same underlying value.

### Impact Explanation
If this gap is real (member-level slash not yet applied when a member with an outstanding pending slash calls `unbond`), the member's `unbonding_points` get converted to `unbonding_balance` using the pool's already-slashed aggregate ratio, and are then withdrawn from `T::StakeAdapter::member_withdraw` against a delegated hold that has *not yet* been reduced by their individual pending slash. Combined with the pallet's own test coverage that treats "apply slash first" as a required precursor before other member-affecting actions (`do_claim_trapped_balance_applies_pending_slash_first`) [8](#0-7) , the absence of the same guard in `unbond` is a genuine inconsistency in how the pending-slash invariant is enforced across sibling entry points that both mutate points/balance state.

### Likelihood Explanation
I was not able to fully trace, within the remaining tool budget, whether `T::StakeAdapter::unbond`/`member_withdraw` internally re-derive and cap the withdrawable amount by the member's currently-held delegated balance in a way that would neutralize this gap (i.e., whether `adapter.rs`'s `member_withdraw` implementation clamps to actual held funds regardless of pending slash). The `withdraw_unbonded` code path's own comment describes its `do_apply_slash` call as "defensive" and states that "in reality, pool slashes must have been already applied via permissionless `Call::apply_slash`" [5](#0-4) , which suggests the protocol may rely on permissionless `apply_slash` calls happening independently, and that the missing call in `unbond` might be intentional/non-exploitable rather than a true asymmetry. This uncertainty means I cannot assert with full confidence that this constitutes an exploitable fund-extraction bug versus a defense-in-depth omission.

### Recommendation
Given the uncertainty in fully confirming exploitability from the adapter-level clamping behavior, this should be treated as a candidate for deeper verification rather than a confirmed finding: trace `adapter::DelegateStake::member_withdraw` and `StakeAdapter::unbond` to confirm whether they cap withdrawal to the member's actual (post-slash) delegated balance. If they do not, add a `Self::do_apply_slash` (or equivalent forced reconciliation) call to `unbond` before `bonded_pool.dissolve(unbonding_points)`, mirroring `withdraw_unbonded`.

### Proof of Concept
Not constructed — I could not fully verify within the tool budget whether `adapter::DelegateStake`'s `member_withdraw`/`unbond` implementations independently bound withdrawals to the member's real post-slash delegated balance, which is required to determine if a concrete overdraw sequence (bond → pool slashed → `unbond` without `apply_slash` → `withdraw_unbonded`) actually yields excess funds beyond entitlement. This should be confirmed with a full read of `substrate/frame/nomination-pools/src/adapter.rs`'s `member_withdraw`/`member_slash` implementations, which the index did not return in full detail.

		// NOTE: do not optimize by removing `balance`. it must be computed before mutating

		self.points = self.points.saturating_sub(points);
		balance
	}

	/// Slash member against the pending slash for the pool.
	fn do_apply_slash(
		member_account: &T::AccountId,
		reporter: Option<T::AccountId>,
		enforce_min_slash: bool,
	) -> DispatchResult {
		let member = PoolMembers::<T>::get(member_account).ok_or(Error::<T>::PoolMemberNotFound)?;

		let pending_slash =
			Self::member_pending_slash(Member::from(member_account.clone()), member.clone())?;

		// ensure there is something to slash.
		ensure!(!pending_slash.is_zero(), Error::<T>::NothingToSlash);

		if enforce_min_slash {
			// ensure slashed amount is at least the minimum balance.
			ensure!(pending_slash >= T::Currency::minimum_balance(), Error::<T>::SlashTooLow);
		}

		T::StakeAdapter::member_slash(
			Member::from(member_account.clone()),
			Pool::from(Pallet::<T>::generate_bonded_account(member.pool_id)),
			pending_slash,
			reporter,
		)
	}

	/// Pending slash for a member.
	///
	/// Takes the pool_member object corresponding to the `member_account`.
	fn member_pending_slash(
		member_account: Member<T::AccountId>,
		pool_member: PoolMember<T>,
	) -> Result<BalanceOf<T>, DispatchError> {
		// only executed in tests: ensure the member account is correct.
		debug_assert!(
			PoolMembers::<T>::get(member_account.clone().get()).expect("member must exist") ==
				pool_member
		);

		let pool_account = Pallet::<T>::generate_bonded_account(pool_member.pool_id);
		// if the pool doesn't have any pending slash, it implies the member also does not have any
		// pending slash.
		if T::StakeAdapter::pending_slash(Pool::from(pool_account.clone())).is_zero() {
			return Ok(Zero::zero());
		}

		// this is their actual held balance that may or may not have been slashed.
		let actual_balance = T::StakeAdapter::member_delegation_balance(member_account)
			// no delegation implies the member delegation is not migrated yet to `DelegateStake`.
			.ok_or(Error::<T>::NotMigrated)?;

		// this is their balance in the pool
		let expected_balance = pool_member.total_balance();

		// return the amount to be slashed.
		Ok(actual_balance.saturating_sub(expected_balance))
