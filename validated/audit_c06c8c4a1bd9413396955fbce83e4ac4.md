### Title
Dust-transfer griefing fills an account's 30-slot token list and permanently blocks that account from new deposits, issuance, and inbound transfers - ([File: contracts/Pool.sol])

### Summary
`Pool` enforces `MAX_TOKENS_PER_USER = 30` across the combined per-account `depositTokensOfAccount` and `debtTokensOfAccount` sets. Any unprivileged user can push arbitrary victim accounts to the cap by transferring 1-wei dust of every pool `DepositToken` to them. Once the combined list reaches 30, every code path that tries to register a *new* token for the victim — `DepositToken.deposit`/`_mint`, `DepositToken._transfer` to the victim, and `DebtToken.issue`/`_mint` — reverts in `Pool.addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` with `UserReachedMaxTokens`. The victim can only recover by manually zeroing dust balances (one tx per token), and any *contract* recipient (e.g. a smart wallet or integration contract without an arbitrary `DepositToken.transfer` escape hatch) is permanently bricked for new positions.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30` [1](#0-0) .
- `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance was zero and `amount_ > 0` [2](#0-1) . `transfer`/`transferFrom` are public and unrestricted for unlocked balances [3](#0-2) .
- The same registration happens on mint (`DepositToken._mint` [4](#0-3) ) and on debt issuance (`DebtToken._mint` → `pool.addToDebtTokensOfAccount` [5](#0-4) ).
- Removal only occurs when a balance goes exactly to zero [6](#0-5) .

Attack: attacker deposits dust into each of the pool's `DepositToken`s (cost ≈ sum of minimum deposits), then calls `transfer(victim, 1)` for each token until the victim's combined deposit+debt list hits 30 (fillable whenever the pool has ≥30 deposit tokens, or fewer if the victim already holds debt tokens, since both lists share the cap). From then on:
- `depositToken.deposit(x, victim)` for any collateral the victim doesn't already hold reverts inside `_mint` → `addToDepositTokensOfAccount`.
- `debtToken.issue(amount, to)` reverts for any synthetic the victim doesn't already owe.
- Any `transfer`/`transferFrom`/`seize` of a new deposit token *to* the victim reverts.

### Impact Explanation
Liveness break / freezing of position management: a targeted account can no longer add new collateral types or borrow new synthetics. For a leveraged account approaching the liquidation threshold, the inability to deposit a different collateral (or issue via a new debt token) can convert the griefing into a forced liquidation — indirect loss of funds. If the victim is a contract that cannot invoke `DepositToken.transfer` to flush dust (multisig wrappers, integration contracts, `SmartFarmingManager`-style intermediaries that hold `msdTOKEN` on behalf of users), the lockout is permanent for that address: it can never again open new collateral or debt positions in that pool.

### Likelihood Explanation
Fully unprivileged and cheap: requires only dust deposits plus N `transfer` calls (attacker's own funds, no privileged role, no oracle manipulation, no governance action). The only prerequisite is that the victim's combined slot usage can be pushed to 30, which is achievable whenever a pool lists enough deposit tokens (the pool-level `ReachedMaxDepositTokens` bound is the same `MAX_TOKENS_PER_USER = 30`, so a full pool guarantees reachability; partial pools are still exploitable against accounts already holding debt tokens). Modifiers do not help: `transfer` has no `whenNotPaused`/cap check on the recipient, `_revertIfLocked` only constrains the sender, and `addToDepositTokensOfAccount` is the intended choke point that the griefing abuses.

### Recommendation
- Only register a token on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` above a minimum balance threshold (e.g. `amount_ > dustThreshold`), or
- Allow list additions to succeed beyond the cap but skip max-check reverts on *transfer-in* (cap only user-initiated `deposit`/`issue`), or
- Let accounts opt out / self-remove entries via a `Pool.removeFromDepositTokensOfAccount`-style user-facing cleanup that burns/sweeps the dust in one call.

### Proof of Concept
Hardhat sketch (fork of a deployed `Pool` with ≥30 listed `DepositToken`s, or combined deposit+debt tokens summing to ≥30):

```typescript
// attacker: deposit 1 unit of each underlying, then dust the victim
for (const dt of depositTokens /* up to 30 */) {
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, attacker.address);
  await dt.transfer(victim.address, 1); // adds dt to victim's list
}
// victim now has 30 entries
await expect(
  newDepositToken.deposit(parseEther('10'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
await expect(
  debtToken.issue(parseEther('1'), victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// anyone sending a new deposit token to the victim reverts
await expect(
  otherDepositToken.connect(holder).transfer(victim.address, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Caveat: the attack only freezes *new* token registrations — existing balances remain withdrawable — so the concrete loss path is blocked re-collateralization leading to liquidation, or permanent lockout for contracts lacking a generic `DepositToken.transfer` escape. Whether `SmartFarmingManager` (or other deployed intermediary contracts) holds `msdTOKEN` balances directly and lacks such an escape was not fully verified against the deployed configuration; if it does, griefing that address permanently bricks `leverage`/`flashRepay` flows that register new deposit tokens for it.
