## Analog identified: spot-AMM-reserve price used unguarded as a fee "oracle" in `pallet-asset-conversion-tx-payment`

### Title
Unprivileged reserve manipulation of `pallet-asset-conversion` spot price lets an attacker under-pay transaction fees converted through `SwapAssetAdapter` - (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
The Salty.IO bug is fundamentally about using **un-smoothed AMM pool reserves as a price oracle** for a security-critical calculation, letting an attacker skew the reserves (with their own funds, no privileged role needed) to distort the derived price. The same pattern exists in `pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter`, which converts a transaction fee into a non-native asset using the *live spot reserves* of a `pallet-asset-conversion` pool via `quote_price_tokens_for_exact_tokens`, with no TWAP, staleness check, or deviation guard analogous to Chainlink's heartbeat check.

### Finding Description
`SwapAssetAdapter::withdraw_fee` computes how much of a non-native `asset_id` a user must pay for a fee denominated in the target asset `A` (usually the native token) by calling: [1](#0-0) 

This delegates to `pallet_asset_conversion::Pallet::quote_price_tokens_for_exact_tokens`, which reads the pool's **current** balances directly from storage and derives the amount using `get_amount_in`/`get_amount_out` — a pure constant-product spot-price calculation with no time-weighting: [2](#0-1) [3](#0-2) 

There is no oracle-style protection (no heartbeat/staleness bound, no maximum-deviation check against a reference price, no TWAP) — the same missing guard that made `CoreSaltyFeed`'s raw-reserve price feed exploitable in the external report. `pr_12408.prdoc` even confirms that the pallet intentionally reads "full pool account balances" for pricing, i.e., the raw instantaneous reserve, reinforcing that spot reserves are the sole source of truth for this calculation: [4](#0-3) 

Because `asset_fee` is derived from whatever the pool reserves are *at the moment the extrinsic executes*, any unprivileged account holding both the native asset `A` and the alternate `asset_id` can:
1. Submit a transaction that swaps `A` → `asset_id` in the exact pool used for fee conversion, depleting the pool's `asset_id` reserve and inflating its `A` reserve.
2. In the following transaction (same account, predictable nonce ordering; no other party or validator collusion required), submit any call using `ChargeAssetTxPayment` with that `asset_id`. `quote_price_tokens_for_exact_tokens` will now return an artificially low `asset_fee` because the temporarily skewed reserves make `asset_id` look scarce/expensive relative to `A`.
3. The chain accepts and executes the underlying call while the actual value transferred to the fee beneficiary (native `A` accrued via `swap_tokens_for_exact_tokens`) is real, but the attacker paid a distorted (and swappable-back) amount of `asset_id`, extracting value from the pool rather than paying the intended market-priced fee.

### Impact Explanation
This directly matches the accepted impact category "public underpriced work that degrades block production": the on-chain fee-in-asset mechanism no longer reflects the real economic cost of the transaction, so an attacker can process transactions while contributing less real value than the fee model intends, at the pool liquidity providers' expense (arbitrage loss) and can repeat this cheaply to spam transactions priced below their intended cost.

### Likelihood Explanation
No privileged role, relayer, validator, or malicious peer is needed — only an unprivileged account with capital in both assets and control over its own transaction ordering (guaranteed by nonce sequencing, not front-running of a third party). The `ensure!(change.peek().is_zero())` guard in `withdraw_fee` only checks the swap executed exactly as quoted; it provides no protection against the quote itself being computed from a reserve state the same attacker just manipulated.

### Recommendation
Introduce a TWAP or bounded reference price check for `quote_price_tokens_for_exact_tokens`/`quote_price_exact_tokens_for_tokens` when used for fee conversion (e.g., cap the deviation from a rolling average, or require a minimum settlement window), analogous to Chainlink's heartbeat/deviation check, instead of relying purely on the instantaneous pool balance.

### Proof of Concept
1. Deploy a runtime with `pallet-asset-conversion` and `pallet-asset-conversion-tx-payment` configured with `SwapAssetAdapter`, and a thinly-liquid `asset_id`/native pool.
2. Attacker account holds both native `A` and `asset_id`.
3. Tx 1: attacker swaps a large amount of native `A` for `asset_id` in the fee-conversion pool (`AssetConversion::swap_exact_tokens_for_tokens` or equivalent extrinsic), skewing reserves.
4. Tx 2 (same block/next block, same sender, sequential nonce): attacker submits any call with `ChargeAssetTxPayment { asset_id: Some(asset_id), .. }`. Observe `quote_price_tokens_for_exact_tokens` returning a materially lower `asset_fee` than it would at the pre-manipulation reserve ratio (verifiable by comparing against `AssetConversion::quote_price_tokens_for_exact_tokens` calls before/after Tx 1 using the same fee amount, as shown in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs:1580-1586`'s exact code path).
5. Tx 3 (optional): attacker swaps `asset_id` back to `A`, closing the position while having paid for Tx 2's fee at the distorted rate.

		pub fn get_amount_in(
			fee: Permill,
			amount_out: &T::Balance,
			reserve_in: &T::Balance,
			reserve_out: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount_out = T::HigherPrecisionBalance::from(*amount_out);
			let reserve_in = T::HigherPrecisionBalance::from(*reserve_in);
			let reserve_out = T::HigherPrecisionBalance::from(*reserve_out);

			if reserve_in.is_zero() || reserve_out.is_zero() {
				Err(Error::<T>::ZeroLiquidity)?
			}

			if amount_out >= reserve_out {
				Err(Error::<T>::AmountOutTooHigh)?
			}

			let fee_complement = fee.left_from_one().deconstruct();
			let numerator = reserve_in
				.checked_mul(&amount_out)
				.ok_or(Error::<T>::Overflow)?
				.checked_mul(&T::HigherPrecisionBalance::from(Permill::ACCURACY))
				.ok_or(Error::<T>::Overflow)?;

			let denominator = reserve_out
				.checked_sub(&amount_out)
				.ok_or(Error::<T>::Overflow)?
				.checked_mul(&T::HigherPrecisionBalance::from(fee_complement))
				.ok_or(Error::<T>::Overflow)?;

			let result = numerator
				.checked_div(&denominator)
				.ok_or(Error::<T>::Overflow)?
				.checked_add(&One::one())
				.ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
