### Title
Unvalidated negative Pyth price causes an uncatchable runtime abort in `normalize-pyth`, freezing all market operations for the affected asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`normalize-pyth` converts the raw signed Pyth price to `uint` using `to-uint` before any sign/legality check is performed. `to-uint` on a negative `int` is not a recoverable Clarity error — it is a runtime type-checker abort that cannot be caught by `try!`/`unwrap!`/`asserts!`. Any Pyth feed that (even transiently) reports a negative price will cause every market entry point that resolves that asset's price to abort uncontrollably, instead of hitting the intended `ERR-ORACLE-INVARIANT` check in `oracle-price-legal`.

### Finding Description
`normalize-pyth` is defined as: [1](#0-0) 

The early-return branch `(asserts! (not (is-eq adj 0)) (to-uint p))` executes `(to-uint p)` on the raw signed Pyth price `p` whenever `expo == -8` (the common case for most feeds, e.g. `adj = expo + 8 = 0`). This happens *before* `oracle-price-legal` — the dedicated legality check further down the call chain — ever gets a chance to run: [2](#0-1) [3](#0-2) 

`oracle-price-legal` clearly signals developer intent to gracefully reject non-positive prices with `ERR-ORACLE-INVARIANT`, but that check is unreachable for the `adj == 0` branch because `to-uint p` on a negative `int` is a hard runtime abort (like Go's index-out-of-range panic in the referenced Celo bug), not a Clarity `(err ...)` response — it cannot be intercepted by any `try!`/`unwrap!`/`asserts!` combinator upstream.

`resolve-pyth` → `resolve-price-feed` → `price-resolve` → `price-multi-resolve` are all invoked from every unprivileged, user-triggered market entry point that needs to price an asset backed by a Pyth feed with `expo == -8` (STX, sBTC, USDC, etc. per `docs/oracle.md`), including `collateral-add`, `borrow`, `repay`, `collateral-remove`, `liquidate`, and `liquidate-multi`. This matches the market entry point / oracle resolution scope explicitly called out as in-scope.

### Impact Explanation
Pyth price feeds are not guaranteed to always be non-negative under all circumstances (real-world commodity feeds have gone negative historically, and any provider glitch, decoder bug, or temporary anomaly on the Pythnet side can surface a negative `price` field for an instant). Once a single relevant feed reports a negative price, every position and every user interacting with the market through that asset (collateral, debt, or via multi-price resolution reused across health checks and liquidations) becomes unable to `borrow`, `repay`, add/remove collateral, or be liquidated, since the transaction aborts before any graceful error path or pause mechanism can engage. Because liquidations are also blocked during this state, undercollateralized positions cannot be liquidated, and healthy users cannot manage their own positions — this is a temporary freezing of funds until the price recovers or the DAO intervenes (e.g., via an implementation upgrade), landing squarely in the in-scope "temporary freezing of funds" impact category.

### Likelihood Explanation
This does not require any privileged action, DAO compromise, or attacker-controlled oracle manipulation of the underlying Pyth network — it is purely a missing input-validation bug in this contract's own price-normalization code. The only precondition is that an already-trusted, correctly-functioning-per-protocol-design Pyth price update reports a negative `price` for a feed configured with `expo = -8` (the standard 8-decimal exponent used across the protocol's feeds per `docs/oracle.md`), which is within the range Pyth's price schema (`price: int`) explicitly allows and does not require any bug or attack on the oracle itself.

### Recommendation
In `normalize-pyth`, check `(< p 0)` (or use `(asserts! (>= p 0) ERR-ORACLE-INVARIANT)`) before calling `to-uint p` in the `adj == 0` early-return branch, so a negative price is turned into the same graceful `ERR-ORACLE-INVARIANT` path that `oracle-price-legal` already provides for the `adj != 0` branches.

### Proof of Concept
1. A Pyth price feed used by the market (e.g. STX/USD, configured with `TYPE-PYTH` and `expo` normally `-8`) publishes an update where `price` is negative (allowed by the Pyth schema's signed `int` price field; this has occurred for real-world feeds such as crude oil, and can also occur from any upstream data anomaly).
2. Any user calls `borrow`, `collateral-add`, `repay`, `collateral-remove`, `liquidate`, or `liquidate-multi` for a position touching that asset.
3. Internally, `price-resolve` → `resolve-price-feed` → `resolve-pyth` → `normalize-pyth` is invoked with the negative `p` and `expo = -8`, so `adj = 0`.
4. `(to-uint p)` executes on the negative `p` inside the `asserts!` early-return expression, causing an unrecoverable runtime abort of the whole transaction — `oracle-price-legal`'s `ERR-ORACLE-INVARIANT` check is never reached.
5. Every subsequent call touching that asset's price for any user fails the same way until the feed price recovers, temporarily freezing collateral/debt management and liquidations for that asset market-wide.
