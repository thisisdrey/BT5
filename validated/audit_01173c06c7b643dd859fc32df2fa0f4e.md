## Analysis

I found a strong analog in java-tron's resource delegation mechanism. This confirms an unprivileged-transaction-reachable bug class matching the "spam another user's storage with attacker-controlled entries via an unprotected, un-consented write path" pattern from the Ajna `memorializePositions` report.

### Title
Unbounded, victim-consent-free growth of `DelegatedResourceAccountIndexStore` "from-accounts" index enables gas/response-size DoS on the delegated-resource query APIs - (File: `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java`)

### Summary
`DelegateResourceActuator.execute` lets any account owner delegate as little as `1 TRX` of frozen resource to an **arbitrary receiver address** chosen by the caller, with no participation or opt-in required from the receiver. Every such delegation permanently appends an entry to the receiver's "from accounts" index in `DelegatedResourceAccountIndexStore`, which is later read back, fully materialized into an in-memory list, and sorted, whenever the receiver (or anyone) queries `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2`.

### Finding Description
`DelegateResourceActuator.validate()` only requires `delegateBalance >= TRX_PRECISION` (1 TRX) and that `receiverAddress` be a valid, existing, non-contract account different from the owner [1](#0-0) [2](#0-1) . There is no requirement that the receiver approve, whitelist, or otherwise consent to being delegated to.

In `execute()`, `delegateResource(...)` is invoked, which calls `delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress, ...)` unconditionally [3](#0-2) . `delegateV2` writes two new keys into the store: a `V2_FROM_PREFIX+from+to` entry and a `V2_TO_PREFIX+to+from` entry [4](#0-3) . Because each `(from,to)` pair is a distinct DB key, an attacker can create unlimited unique entries against a single victim `to` address simply by generating many fresh "from" accounts (each funded/frozen with the 1 TRX minimum) and delegating to the same victim.

When the victim's index is later queried via `getV2Index`, the store does a `prefixQuery` over `V2_TO_PREFIX+victim`, materializes **all** matching entries into an `ArrayList`, sorts them by timestamp, and builds the full `fromAccounts` list [5](#0-4) . The legacy (non-V2) path, `getIndex`/`getWithPrefix`, behaves identically for `FreezeBalanceActuator`-based delegation [6](#0-5) , and `FreezeBalanceActuator.delegateResource` similarly lets any owner pick any `receiverAddress` and append to that receiver's index with no receiver consent [7](#0-6) .

This index is exposed via multiple externally reachable APIs an anonymous client can call:
- gRPC `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` in `RpcApiService` [8](#0-7) 
- HTTP `/wallet/getdelegatedresourceaccountindex(v2)` servlets [9](#0-8) [10](#0-9) 
- `Wallet.getDelegatedResourceAccountIndex(V2)` [11](#0-10) 

This mirrors the Ajna `memorializePositions` bug class precisely: an unprivileged caller can attach arbitrarily many attacker-controlled, low-value entries to another party's on-chain data structure without consent, and that structure is later fully iterated/sorted by a query path that the victim (or anyone) must exercise.

### Impact Explanation
Unlike the Ajna case, the query methods here are read-only Wallet/RPC/HTTP calls rather than in-consensus state transitions, so this does not directly freeze funds or corrupt account balances. The concrete impact is:
- Denial of service against a specific node's `GetDelegatedResourceAccountIndex(V2)` API for a targeted victim address: the `prefixQuery` + `ArrayList` + sort operation is O(n log n) in the number of spammed entries and the resulting response payload grows unbounded, which can exhaust node memory/CPU or produce oversized gRPC/HTTP responses, making the node "no longer able to serve" that API for the targeted address (and potentially degrade the node broadly if repeated across many victims).
- Because delegation itself costs on-chain resources (each delegation is a distinct transaction requiring 1 TRX frozen balance per "from" account, plus fees/bandwidth), the griefing is not free, but it is cheap and entirely automatable by a single attacker controlling many funded accounts, and requires no cooperation or vulnerability on the victim's part.

### Likelihood Explanation
Likelihood is moderate: the attacker needs to control multiple funded accounts (to satisfy the ≥1 TRX freeze/delegate minimum per unique "from" key) and pay transaction fees for each delegation, but there is no cap on the number of distinct delegators that can target a single receiver, and no receiver-side opt-out/allowlist exists in `DelegateResourceActuator.validate()` or `FreezeBalanceActuator`.

### Recommendation
- Enforce a per-receiver cap on the number of distinct delegators recorded in `DelegatedResourceAccountIndexStore`, or require receiver-side authorization/allowlisting before a delegation index entry is created for that receiver.
- Alternatively, change `getWithPrefix`/`getV2Index` query paths to support pagination (bounded `limit`/`offset`) rather than unconditionally materializing and sorting the full list, mirroring the mitigation of enforcing bounds against unauthorized DoS.

### Proof of Concept
Conceptual PoC (extending the existing test `testGetDelegatedResourceAccountIndexV2` in `framework/src/test/java/org/tron/core/WalletTest.java`, lines 1005-1034):
1. Fund `N` distinct throwaway accounts, each freezing/acquiring the minimum 1 TRX bandwidth/energy via `FreezeBalanceV2Contract`.
2. For each of the `N` accounts, submit a `DelegateResourceContract` (via `DelegateResourceActuator`) with `receiverAddress` set to a single fixed victim address and `balance = TRX_PRECISION` (1 TRX), as validated in `DelegateResourceActuator.validate()` [1](#0-0) .
3. Each transaction succeeds and calls `delegatedResourceAccountIndexStore.delegateV2(...)`, appending a new `V2_TO_PREFIX+victim+from_i` entry [4](#0-3) .
4. Repeat for large `N` (thousands), none of which require the victim's participation.
5. Call `wallet.getDelegatedResourceAccountIndexV2(victimAddress)` (or the equivalent HTTP/gRPC endpoint) and observe the resulting `prefixQuery`+sort operation and response size grow linearly with `N`, demonstrating unbounded, attacker-controlled resource consumption on a query path targeting the victim's address [5](#0-4) .

**Note on verification limits:** I was unable to fully confirm the exact resource-consumption thresholds (e.g., how many delegations are needed before the API response becomes impractically large or the node experiences measurable degradation), since that depends on runtime/DB behavior not observable through static code search. A live Devin session with test execution would be needed to empirically measure the DoS threshold.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndex(ByteString address) {
    if (address == null || address.size() != DecodeUtil.ADDRESS_SIZE / 2) {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
    DelegatedResourceAccountIndexCapsule accountIndexCapsule =
        chainBaseManager.getDelegatedResourceAccountIndexStore().getIndex(address.toByteArray());
    if (accountIndexCapsule != null) {
      return accountIndexCapsule.getInstance();
    } else {
      return DelegatedResourceAccountIndex.getDefaultInstance();
    }
  }

  public DelegatedResourceAccountIndex getDelegatedResourceAccountIndexV2(ByteString address) {

      return DelegatedResourceAccountIndex.getDefaultInstance();

    DelegatedResourceAccountIndexCapsule accountIndexCapsule = chainBaseManager
        .getDelegatedResourceAccountIndexStore().getV2Index(address.toByteArray());
