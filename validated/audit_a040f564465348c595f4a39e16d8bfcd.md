### Title
Off-by-one mismatch between StackerDB push-chunk network validation and storage-layer staleness check causes false "accepted" inventory acknowledgements - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
The external report describes a bug where an accounting equality (`amountInShelter` vs actual balance) is broken when state is reset without verifying the underlying data was actually reconciled, causing tokens the contract believes are accounted for to diverge from what is truly held. The stacks-core analog is a similar broken equality between two layers that are each supposed to gate the same StackerDB chunk write: the network-facing validator accepts a chunk version that the storage-layer writer will unconditionally reject as stale, so a node acknowledges (and advertises) data it never actually commits.

### Finding Description
When a node receives an unsolicited `StackerDBPushChunk` message, `PeerNetwork::handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk` to gate acceptance: [1](#0-0) 

This check only rejects a chunk if `data.slot_version < *expected_version` — meaning a chunk whose `slot_version` is **equal** to the currently-known version is treated as valid and accepted.

After this check passes, the function patches its outgoing inventory reply to reflect the chunk as stored, wakes the sync state machine, and forwards the message onward: [2](#0-1) 

However, actual persistence of a chunk happens later via `StackerDBTx::try_replace_chunk`, whose freshness check is strictly stronger — it rejects a chunk as `StaleChunk` if its version is **less than or equal to** the currently-stored version: [3](#0-2) 

Thus, for a push chunk whose `slot_version` exactly equals the node's currently stored/expected version, `validate_received_chunk` (network layer) says "accept," but `try_replace_chunk` (storage layer) will unconditionally reject it as stale. The equality that should hold — "a chunk the node acknowledges as accepted for storage is the chunk that actually gets stored" — is broken by this `<` vs `<=` discrepancy between the two gates.

### Impact Explanation
Because `handle_unsolicited_StackerDBPushChunk` immediately builds and sends a `StackerDBChunkInv` reply patched with the pushed chunk's `slot_version` before the chunk is durably written (persistence happens only later, via the relayer path returning `forward=true`), a node can acknowledge/advertise a slot version to its peer and wake its own sync state machine for data that is guaranteed to be discarded at the storage layer with a `StaleChunk` error. This is a "served vs. committed" divergence: the node's advertised StackerDB inventory state does not match what is durably held, which can mislead peers about data availability and cause wasted/incorrect sync scheduling (peers may believe the chunk is now replicated at that node and stop trying to source it elsewhere, even though it isn't there). This falls under "serving non-canonical state as canonical" (High).

### Likelihood Explanation
This is reachable from any push of a signed chunk (which still requires a valid signature from the slot's assigned signer/owner — an attacker cannot forge arbitrary slot data), but it triggers deterministically whenever a chunk is (re-)pushed with a `slot_version` numerically equal to the node's currently expected version — a boundary condition easily hit during normal or adversarial re-transmission/retry behavior, requiring no special privilege beyond holding a valid StackerDB slot signer key (which many participants, e.g. signers/miners, legitimately hold). No blockchain admin or node-secret access is needed.

### Recommendation
Align the two gating checks so the network-facing `validate_received_chunk` uses the same strict inequality (`<=`) as the storage layer's `try_replace_chunk`, i.e. reject (return `Ok(false)`) chunks whose `slot_version <= expected_version`, ensuring a chunk is never acknowledged/advertised as accepted unless it will actually succeed at being persisted.

### Proof of Concept
1. Node A has a StackerDB slot at `slot_id=0` with stored version `v`.
2. A legitimate slot signer crafts and signs a `StackerDBChunkData` with `slot_version = v` (same as currently stored) and pushes it to Node A via `StackerDBPushChunk`.
3. `handle_unsolicited_StackerDBPushChunk` calls `validate_received_chunk`, which only checks `data.slot_version < *expected_version` (`stackslib/src/net/stackerdb/mod.rs:700`) — `v < v` is false, so validation passes.
4. Node A patches its `StackerDBChunkInv` reply's slot version to `v` (`stackslib/src/net/stackerdb/mod.rs:807`) and sends this back to the peer, and wakes its sync state machine, before ever writing the chunk.
5. When Node A's relayer later attempts to store the same chunk via `try_replace_chunk`, `slot_desc.slot_version <= slot_validation.version` (`v <= v`) is true, so it returns `Err(net_error::StaleChunk)` (`stackslib/src/net/stackerdb/db.rs:424-429`), and the chunk is never stored.
6. Result: Node A has told its peer (and any peer relying on its advertised inventory) that it holds chunk version `v`'s data, when in fact the write was rejected and the previously-stored chunk (if different) or empty slot remains.
