### Title
Unbounded array allocation from attacker-controlled length words in TVM precompile array extraction helpers can OOM/crash the node - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The Apache Avro advisory describes a Reader that trusts a length field from untrusted input and allocates memory proportional to that length without bounding it, causing OOM (CWE-770). The same bug-class pattern exists in java-tron's TVM precompiled-contract input decoders `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` in `PrecompiledContracts.java`, which are used to parse ABI-encoded arrays inside precompile call data (e.g. batch/multi-signature validation precompiles reachable from ordinary contract calls).

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read an array-length word directly from the attacker-supplied `data`/`words` and use it to size a Java array before any validation against the actual size of the input payload: [1](#0-0) 

`len` comes from `words[offset].intValueSafe()`. `DataWord.intValueSafe()` only guards against negative/overflowing values by clamping to `Integer.MAX_VALUE`; it does not check the value against the amount of remaining call data: [2](#0-1) 

Consequently, a caller can craft a `DataWord` word (fully controlled since it is part of the transaction's TVM call data) such that `len` is any value up to `Integer.MAX_VALUE`. The code then immediately executes `new byte[len][]` (an object-reference array of that size) with no upper bound check, unlike the sibling `ModExp` precompile which explicitly enforces an `UPPER_BOUND` on parsed lengths: [3](#0-2) 

These extraction helpers are used by the batch/multi-signature verification precompiled contracts (confirmed present via `BatchValidateSignContractTest.java` / `ValidateMultiSignContractTest.java`), which are precompiles reachable by any account through a normal `CALL`/`STATICCALL` TVM opcode to the corresponding precompile address — i.e., an unprivileged contract deployer or transaction broadcaster can trigger this path.

### Impact Explanation
Allocating an array sized from an uncontrolled attacker-supplied word (up to `Integer.MAX_VALUE` elements) will throw `OutOfMemoryError` synchronously in the JVM executing the TVM. Because this happens inside contract execution triggered by a single signed transaction, a malicious contract call can repeatedly or reliably force `OutOfMemoryError` in the node's execution thread, which can destabilize or crash the full node process (denial of service), consistent with the CVSS Availability-High rating of the referenced advisory.

### Likelihood Explanation
The precompile input parsing functions are directly reachable from any TVM contract call using ABI-encoded array arguments; no special privileges, keys, or witness/SR status are required — a plain contract deployer/caller can supply the crafted `data`. The lack of any bound (unlike the `UPPER_BOUND` guard present in `ModExp`) makes exploitation straightforward with a single malformed length word.

### Recommendation
Add an explicit upper bound check on `len` in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` (e.g., cap by the maximum sane element count derivable from `data.length`/`WORD_SIZE`, similar to the `UPPER_BOUND` pattern used in `ModExp`) before allocating the array, and reject/short-circuit execution if the declared length exceeds what the remaining call data can back.

### Proof of Concept
Craft a TVM call to the batch/multi-signature validation precompile with call data whose array-length word (parsed via `words[offset].intValueSafe()`) is set to a very large value (e.g., `0x7FFFFFFF`) while the rest of the call data is small; on entry to `extractSigArray`/`extractBytesArray`, `new byte[len][]` will attempt to allocate an array with `len` references, immediately throwing `OutOfMemoryError` in the node's TVM execution thread.

Note: I was unable to directly view the `BatchValidateSign`/`ValidateMultiSign` precompile `execute()` bodies (only their test files were located in the index), so the exact call chain from precompile `execute()` into these array-extraction helpers is inferred from naming/test coverage and could not be fully confirmed via direct source citation in this session. A Devin session with full file access would be able to verify the exact invocation sites and confirm whether any pre-existing length check mitigates this before the array allocation occurs.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
