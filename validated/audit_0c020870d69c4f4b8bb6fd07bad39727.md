## Analysis

The reported CVE-2018-19518 concerns a fetch helper (`rsh`) that trusted an attacker-influenced connection string and let it be reinterpreted as command-line options (`-oProxyCommand=...`) instead of purely data, because the transport layer did not enforce protocol/argument containment. Bazel's Git repository-rule implementation contains a structurally identical failure: `tools/build_defs/repo/git_worker.bzl`'s submodule-update path explicitly re-enables `git`'s `file://` transport for every submodule fetch, which is precisely the option Git upstream disabled by default to stop untrusted `.gitmodules` content from being turned into local filesystem reads outside the intended repository.

### Title
Bazel's `git_repository`/`new_git_repository` submodule handling force-enables `protocol.file.allow=always`, letting attacker-controlled `.gitmodules` content escape repository containment - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository`/`new_git_repository` clone an attacker-influenced remote (`ctx.attr.remote`, or any git server referenced from a `MODULE.bazel`/`WORKSPACE` entry, mirrors, or forks) and, when `init_submodules`/`recursive_init_submodules` is set, run `git submodule update --init [--recursive] --checkout --force` with the flag `-c protocol.file.allow=always` unconditionally injected on every invocation. [1](#0-0) 

### Finding Description
Git upstream disabled the `file://` transport by default for submodule operations (protocol.file.allow defaults to `user`, i.e. disabled for automated/non-interactive commands like `submodule update`) specifically because a hostile repository's `.gitmodules` file is attacker-controlled data that is processed automatically during clone/submodule-update, and using it to permit local-path clones enables reading files/repositories outside the intended checkout. Bazel's `_git_maybe_shallow` submodule call reverses this mitigation globally by passing `-c protocol.file.allow=always` to every submodule update, regardless of trust level of the remote being fetched: [1](#0-0) 

The `remote` value driving `add_origin`/`fetch` is likewise passed straight through to `git` without validation of scheme or leading-dash/argument-like content: [2](#0-1) 

and the underlying `_execute` helper does no sanitization beyond disabling `core.fsmonitor` and clearing a fixed set of `GIT_*` env vars — it does not restrict allowed protocols (e.g. via `GIT_ALLOW_PROTOCOL`) or otherwise contain what `.gitmodules`-declared submodule URLs are allowed to reference: [3](#0-2) 

Notably, `git.bzl` elsewhere goes out of its way to add explicit containment checks for `strip_prefix`/`add_prefix` (verifying the resolved path does not escape the checkout directory), but no equivalent containment or protocol restriction exists for submodule URLs sourced from the cloned repository's own `.gitmodules`: [4](#0-3) [5](#0-4) 

Because `.gitmodules` is fully attacker-controlled content served by whatever git host is named in `remote` (a dependency source exactly analogous to the "untrusted IMAP server name" in the CVE), a hostile or compromised git host can declare a submodule whose URL uses the `file://` scheme to point at other local paths reachable by the Bazel build process. With `protocol.file.allow=always` forced on, Git will honor this and clone/link content from outside the intended repository/output-base boundary into the external repository's checkout, which Bazel then treats as trusted build input.

### Impact Explanation
This breaks the "containment holds" invariant demanded for external-repository fetch: content from a location the victim never asked to include (arbitrary local paths reachable by the git process) can be pulled into the external repository checkout and thereby into the build graph, based solely on data supplied by the (attacker-controlled) `remote` git host. This can disclose or incorporate files that should not be exposed to the build (e.g. contents of other repositories/checkouts on the build machine) or plant unexpected inputs into a supposedly pinned repository — matching the "read outside the repository / exec root / output base" acceptance criterion.

### Likelihood Explanation
This is directly reachable via the widely used `git_repository`/`new_git_repository` rules whenever `init_submodules` or `recursive_init_submodules` is set (a common, documented option), by anyone who controls (or can compromise/redirect, e.g. via a stale/mutable `remote` reference, mirror takeover, or supply-chain compromise of the referenced git host) the target repository's `.gitmodules`. No special privileges on the victim's machine are required; only the ability to publish content that the victim's `git_repository` rule fetches. This is not blocked by any checksum equivalent to `http_archive`'s `sha256`, since `git_repository` has no content-hash pinning of submodule content, and the override is unconditional in Bazel's own Starlark, not a user opt-in.

### Recommendation
Do not force-enable `protocol.file.allow=always` globally for submodule operations. Scope any needed local-protocol allowance narrowly (e.g. only permit it for same-checkout relative submodule paths, matching the specific monorepo/local-clone use case cited in bazelbuild/bazel#17040), and otherwise restrict submodule fetch protocols via `GIT_ALLOW_PROTOCOL`/`protocol.allow` to the same protocol family used for the top-level `remote`. Additionally, validate that `remote` values (and, where feasible, discovered submodule URLs) do not use unexpected schemes before being passed to `git`.

### Proof of Concept
1. Attacker sets up a Git repository `evil.git` referenced by a `git_repository(remote = "https://evil.example/evil.git", commit = "<pinned>", recursive_init_submodules = True)`.
2. `evil.git` at the pinned commit contains a `.gitmodules` entry:
   ```
   [submodule "leak"]
       path = leak
       url = file:///home/buildagent/.other_repo_with_secrets
   ```
3. When Bazel runs `git submodule update --init --recursive --checkout --force -c protocol.file.allow=always`, Git — because `file://` is force-allowed — clones `/home/buildagent/.other_repo_with_secrets` into the `leak` submodule directory inside the external repository's checkout, even though the top-level fetch declared only `https://evil.example/evil.git`.
4. This can be encoded as a `src/test/shell/bazel` integration test: create a local bare repo with secret content, create a second local repo whose `.gitmodules` `file://`-references the first, invoke `git_repository(..., recursive_init_submodules = True)` against the second, and assert that the secret repo's contents become visible under the external repository despite never being named in `remote`.

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
    # See https://github.com/bazelbuild/bazel/issues/21438
    start = ["git", "-c", "core.fsmonitor=false"]
    return ctx.execute(
        start + args,
        environment = ctx.os.environ | _GIT_LOCAL_ENV_VARS,
        working_directory = str(git_repo.directory),
    )

def _checkout_path(ctx):
    """
    Returns the path where the git repository will be checked out.

    The path returned will be the repository directory. If `add_prefix` is set,
    the additional prefix subdirectory path is appended to the repository
    directory. If the directory escapes the "root" repository, eg. an uplevel
    reference '..', the method will fail.
    """
    root = ctx.path(".")
    if ctx.attr.add_prefix:
        add_prefix_root = root.get_child(ctx.attr.add_prefix)
        if add_prefix_root != root and not str(add_prefix_root).startswith(str(root) + "/"):
            fail(
                "add_prefix '%s' escaped the base directory of '%s': '%s'" %
                (ctx.attr.add_prefix, str(root), str(add_prefix_root)),
            )
        return add_prefix_root
    return root
