This confirms `ijar` (used via `java_common.run_ijar`) processes untrusted, attacker-supplied `.jar` dependency archives during a standard Bazel Java build. The bug is a genuine analog to CVE-2017-17121: an attacker-controlled central-directory offset field is trusted without validating it against the mapped file's length, and the bounds check that should catch an out-of-range offset silently fails due to unsigned-integer underflow.

### Title
Out-of-bounds read via unsigned underflow in ijar's ZIP central-directory offset validation - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads a fully attacker-controlled `offset` field (32-bit or, via the ZIP64 extra field, 64-bit) from a ZIP/JAR central directory entry with no validation against the file size. `InputZipFile::ProcessNext` then computes `p = zipdata_in_ + in_offset_ + offset` and immediately calls `EnsureRemaining()` to check that enough bytes remain before dereferencing `p`. `EnsureRemaining` computes `remaining = input_file_->Length() - in_offset` using unsigned `size_t` arithmetic; when the attacker-supplied `offset` pushes `in_offset` past the mmap'd file length, this subtraction underflows to a huge value, so the "not enough bytes remaining" check never fires, and the code proceeds to dereference a wild pointer. ### Finding Description
`ProcessCentralDirEntry` extracts `*offset = get_u4le(p);` (potentially overridden by a ZIP64 extra-field `u8` value) straight from the central directory bytes, with no bound check against `input_file_->Length()`: [4](#0-3) 

`ProcessNext` then trusts this value to relocate the cursor before any validation: [5](#0-4) 

The one guard in place, `EnsureRemaining`, is itself broken for an out-of-range `p`: [6](#0-5) 
`size_t in_offset = p - zipdata_in_;` can legitimately exceed `input_file_->Length()` when `offset` is attacker-controlled and large. `size_t remaining = input_file_->Length() - in_offset;` then underflows (unsigned wraparound), producing an enormous `remaining` value, so `n > remaining` is always false and the function returns success even though `p` points far outside the mapped input file. Subsequent code (`get_u4le(p)`, `get_u2le(p)`, `memcpy` of the filename, etc.) reads and copies memory from this out-of-bounds address.

This is the same bug class as CVE-2017-17121: a size/offset field taken from untrusted binary-format metadata (there, a COFF relocation; here, a ZIP/JAR central-directory "relative offset of local header") is not validated against the bounds of the section/file it indexes into, and the library's own "remaining bytes" bookkeeping is computed in a way that silently wraps around instead of rejecting the out-of-range value.

### Impact Explanation
A malicious `.jar`/`.zip` published as a build dependency (e.g., fetched via `http_jar`, `http_archive`, or any Maven/registry artifact that later flows into a `java_library`/`java_import` and is processed by `java_common.run_ijar`/`ijar`) can craft a central directory entry with an out-of-range `offset` (or a ZIP64 extra field forcing a huge 64-bit offset). When Bazel invokes `ijar` to generate the compile-time interface jar for that dependency, the underflow lets the parser read (and `memcpy` into a stack buffer as a "filename") memory outside the mmap'd input file. This can crash the `ijar` action (denial of service for the build) or leak adjacent process memory into the emitted interface jar / error output, i.e. a genuine memory-safety violation triggered purely by untrusted archive bytes, not by any local/privileged access.

### Likelihood Explanation
Every Java target with dependencies goes through `run_ijar`/`stamp_jar` when interface jars are used (the default for Java compilation caching), so the vulnerable code path is on the default build path for any project depending on an attacker-supplied jar. Constructing a ZIP file with a bogus central-directory offset field is trivial with common ZIP-crafting tools; no cryptographic bypass is needed because there is no checksum/integrity gate on the *contents* of an already-downloaded/verified archive — `sha256`/`integrity` on `http_archive` only guards the raw bytes of the archive as a whole, not out-of-range fields inside the ZIP structure once ijar starts parsing it.

### Recommendation
In `EnsureRemaining` (and anywhere else `p - zipdata_in_` is computed after applying an attacker-controlled `offset`), validate `offset`/`in_offset` against `input_file_->Length()` *before* the subtraction, e.g. reject immediately if `in_offset > input_file_->Length()` rather than relying on unsigned subtraction to "naturally" produce a large negative-turned-positive value. Also validate the raw `offset` field returned from `ProcessCentralDirEntry` (and its ZIP64 override) against the file size before it is ever added to `zipdata_in_ + in_offset_`.

### Proof of Concept
1. Craft a minimal ZIP/JAR whose single central directory entry sets the "relative offset of local header" field to a value larger than the file's total length (e.g., `0xFFFFFFF0`), optionally with a ZIP64 extra field pushing this to a 64-bit value far beyond the mmap region.
2. Run `ijar <crafted>.jar out.jar` (or exercise it through `bazel build` on a `java_library` depending on this jar via `java_common.run_ijar`).
3. Observe that `EnsureRemaining` passes despite `p` pointing outside the mapped file (add an assertion/log at [6](#0-5)  to confirm `remaining` is huge), and that the subsequent `get_u4le(p)`/`memcpy` in `ProcessLocalFileEntry`/`ProcessCentralDirEntry` reads out-of-bounds memory, producing a crash (ASan: heap/global-buffer-overflow) or corrupted output containing leaked memory bytes. This should be encoded as a `third_party/ijar` unit test (parallel to existing tests in `third_party/ijar/zip_test.cc` if present) feeding a crafted buffer with an out-of-range offset directly into `InputZipFile`/`ZipExtractor::Create`.

  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }

  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
