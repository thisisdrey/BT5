### Title
Handshake `Time` field is trusted for session-supersession decisions without any recency/bounds check - ([File: handshake_manager.go])

### Summary
The Chainlink report flags `getPriceFromChainlink()` for trusting an externally-supplied timestamp (`updateAt`) without verifying it is recent, letting a stale or out-of-range value be accepted as truth. Nebula has a structurally identical pattern: the handshake payload's `Time` field is fully peer-controlled, is copied verbatim into `Result.HandshakeTime` with zero validation, and is later used as the sole tie-breaker for whether an incoming handshake is allowed to replace/tear down an existing, live tunnel.

### Finding Description
The handshake wire payload carries a `Time` field defined in `handshake/handshake.proto` [1](#0-0)  and decoded with no range/consistency checking in `unmarshalPayloadDetails` — the parser only validates the protobuf wire type, not the value [2](#0-1) .

In `Machine.processPayload`, this attacker-supplied `Time` is copied directly into `m.result.HandshakeTime` with no comparison against the local clock or any staleness/future-skew tolerance check, analogous to `updateAt` being accepted in `getPriceFromChainlink()` without a recency check: [3](#0-2) 

That untrusted value then flows into `HostInfo.lastHandshakeTime` on both the responder path (`beginHandshake`) and the completion path (`continueHandshake`): [4](#0-3) [5](#0-4) 

Finally, `CheckAndComplete` uses this fully peer-controlled counter — with no sanity bound versus wall-clock time — as the deciding factor for whether a brand-new handshake is allowed to supersede an existing, established tunnel for the same peer identity: [6](#0-5) 

Just as the Chainlink oracle's `getTokenPrice()` returns a non-zero (and possibly stale/out-of-range) price because `updateAt` is never checked against `block.timestamp`, Nebula's handshake logic accepts a peer-chosen `Time` as ground truth for a critical state-transition decision ("is this handshake newer than the one I already trust?") with no equivalent of the recommended `block.timestamp - updateAt` tolerance check.

### Impact Explanation
An attacker who can complete a valid, certificate-authenticated handshake (any legitimate cert holder, or any host that a normal peer would handshake with) can set an arbitrarily large `Time` value in the payload. Because `lastHandshakeTime` on the existing hostinfo is only compared numerically (`>=`) against the new value with no bound against real time, this lets an attacker force `existingHostInfo.lastHandshakeTime >= hostinfo.lastHandshakeTime` to always evaluate false, causing legitimate/older sessions to always be treated as "older" and be torn down/replaced (`hm.mainHostMap.unlockedAddHostInfo` is reached, replacing the existing hostinfo) — i.e., remote state poisoning of the tunnel state machine, forcing repeated handshake churn or tunnel takeover races. It also inverts the intended anti-thrash protection: once an inflated `Time` is recorded, that peer's *genuinely* newer, legitimate handshakes could then be rejected as "too old" (`ErrExistingHostInfo`), effectively locking out the real peer.

### Likelihood Explanation
Medium. This requires the attacker to be a party that can complete a valid handshake (i.e., hold a CA-signed certificate, matching the report's constraint that only actions reachable without a "malicious peer with no cert" are in scope — here the attacker still needs a valid cert but the bug is exploitable purely through a payload field it fully controls, not through any cert forgery). No special timing or race is needed beyond sending a handshake with an inflated `Time`.

### Recommendation
- When processing an incoming handshake payload, validate `payload.Time` against the local clock with a bounded tolerance window (reject or clamp values that are unreasonably far in the future or past), the same fix pattern Connext applied for `updateAt` in PR 1602.
- Alternatively, stop using peer-supplied `Time` as the authority for handshake supersession decisions in `CheckAndComplete`; use a locally-generated monotonic sequence or the local receipt timestamp instead.

### Proof of Concept
1. Attacker (holding a valid cert) establishes a normal tunnel to victim, so `hm.mainHostMap.Hosts[vpnAddr]` holds a hostinfo with `lastHandshakeTime = T0` (derived from the first handshake's `Time` field, itself attacker-controlled since attacker is the initiator).
2. Attacker crafts and sends a second handshake stage-0 packet for the same identity with `Payload.Time` set to `math.MaxUint64` (or any value larger than any future legitimate handshake would carry).
3. `beginHandshake` → `CheckAndComplete` compares `existingHostInfo.lastHandshakeTime (T0) >= hostinfo.lastHandshakeTime (MaxUint64)` → false, so the check in `handshake_manager.go` lines 446-452 does not return `ErrExistingHostInfo`; the new handshake is accepted and replaces the existing hostinfo via `hm.mainHostMap.unlockedAddHostInfo`.
4. Any subsequent legitimate handshake attempt from the real peer with a normal, low `Time` value is now rejected as "too old" (`ErrExistingHostInfo`) because `lastHandshakeTime` is now `MaxUint64`, demonstrating persistent state poisoning/denial of legitimate reconnection.

Note: I could not locate the sender-side code that populates `Payload.Time` when initiating a handshake within the indexed portion of the codebase, so I cannot confirm whether nebula intends this field to be a monotonic local timestamp or something else; this is worth verifying with a full checkout, but the receiver-side lack of validation shown above is confirmed directly from `handshake/machine.go` and `handshake_manager.go`.
