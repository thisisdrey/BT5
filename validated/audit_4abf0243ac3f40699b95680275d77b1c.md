### Title
Legacy energy/bandwidth limit formulas truncate frozen-balance weight via division-before-multiplication, understating resource entitlement - (File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java, chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java, actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
The non-hardened ("legacy") code paths that compute an account's global energy/bandwidth limit from its frozen TRX balance perform integer division of `frozenBalance / TRX_PRECISION` *before* multiplying by the limit/weight ratio, exactly mirroring the Ajna `thresholdPrice = borrowerDebt_ * WAD / collateral_` division-before-multiplication defect. This truncates the fractional "weight" portion of a user's frozen stake before it is scaled, systematically underestimating the energy/bandwidth a frozen balance is entitled to.

### Finding Description
In `EnergyProcessor.calculateGlobalEnergyLimit` and `BandwidthProcessor.calculateGlobalNetLimit`, the legacy (non-hardened) computation is: [1](#0-0) [2](#0-1) 

`frozeBalance / TRX_PRECISION` is an integer division performed first, truncating any fractional multiple of `TRX_PRECISION` in the frozen balance, and only then is the truncated integer weight multiplied by `totalLimit/totalWeight`. This is structurally identical to the Ajna bug: a division is applied to a numerator before the compensating multiplication occurs, discarding precision that the multiplication could have preserved. The repository's own hardened test suite explicitly documents this precision loss: a `frozeBalance` of `1.5 * TRX_PRECISION` yields `floor(1.5) * 25 = 25` under the legacy path versus the mathematically correct `1.5 * 25 = 37` under the hardened path [3](#0-2) . The same pattern also exists in `RepositoryImpl.calculateGlobalEnergyLimit`, used by the TVM/energy metering path for smart-contract execution [4](#0-3) .

A hardened, hidden-behind-flag fix already exists (`allowHardenResourceCalculation` / `calculateGlobalLimitV1`/`V2`), which performs the multiplication before the division using `BigInteger` arithmetic [5](#0-4) , confirming the maintainers are aware the legacy formula is imprecise and have already engineered a correct replacement gated by a governance-controlled proposal parameter (`ALLOW_HARDEN_RESOURCE_CALCULATION`), similar to other hardening switches in this codebase (`allowStrictMath`, `AllowHardenExchangeCalculation`, etc.) referenced in `ProposalUtil.java`.

### Impact Explanation
While `TRX_PRECISION` (1e6 sun) is not astronomically large relative to typical staked amounts (unlike Ajna's 1e18 WAD scale), any frozen balance that is not an exact multiple of `TRX_PRECISION` loses its fractional weight component before scaling, systematically under-crediting available bandwidth/energy for the affected account. This does not cause direct fund theft but is an accounting-fidelity bug that understates a resource entitlement the user obtained by freezing TRX (an on-chain economic commitment), which is the closest in-scope, unprivileged-reachable analog to the reported "incorrectly computed price used to size an economic obligation" class of bug. It affects `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit`, which are invoked on every ordinary transaction (bandwidth accounting) and every TVM contract call (energy metering), both explicitly in-scope areas.

### Likelihood Explanation
The buggy legacy formula is reached whenever `allowHardenResourceCalculation()`/`hardenCalculation()` returns false, i.e., before the corresponding chain proposal is activated on the network. I was unable to confirm from the indexed code whether this proposal is enabled by default on mainnet/testnet in this fork (the `DynamicPropertiesStore` getter/constant name and its default value could not be located within the available index — this is a limitation of the codebase index, not evidence that the flag is off). Any unprivileged account can trigger this path simply by freezing a non-exact-multiple-of-`TRX_PRECISION` amount of TRX and calling a contract or sending a transaction that consumes bandwidth/energy, requiring no special privilege.

### Recommendation
Confirm the current activation status/default of `allowHardenResourceCalculation` on the live network. If it is not yet activated everywhere, treat the legacy code paths in `EnergyProcessor.calculateGlobalEnergyLimit`, `BandwidthProcessor.calculateGlobalNetLimit`, and `RepositoryImpl.calculateGlobalEnergyLimit` as still-exploitable precision bugs and prioritize activation of the hardened multiply-before-divide (`BigInteger`) formulas already implemented in `ResourceProcessor.calculateGlobalLimitV1`/`V2`, removing the double-based/truncating legacy computation once migration is complete.

### Proof of Concept
1. Freeze a balance of `1_500_000` sun (`1.5 * TRX_PRECISION`) for ENERGY on an account, with `totalEnergyLimit = 50_000_000_000` and `totalEnergyWeight = 2_000_000_000` (ratio 25).
2. With hardening disabled, `calculateGlobalEnergyLimit` computes `energyWeight = 1_500_000 / 1_000_000 = 1` (integer truncation) then `1 * 25 = 25`.
3. The mathematically correct value, computed by multiplying first (`1.5 * 25 = 37`), is what the hardened path (`calculateGlobalLimitV1`) returns, as verified by the existing test [6](#0-5) .
4. The account is credited 25 energy instead of the correct 37 — a ~32% understatement of entitled resource for this input, reproducible by any account freezing TRX in non-exact `TRX_PRECISION` multiples.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }

  /**
   * Hardened replacement of legacy V2 formula
   * {@code (long)(((double) frozeBalance / TRX_PRECISION)
   *               * ((double) totalLimit / totalWeight))}.
   *
   * <p>Preserves V2 semantics: equivalent to
   * {@code (frozeBalance * totalLimit) / (TRX_PRECISION * totalWeight)} with
   * a single integer truncation at the end. Critically, fractional weight
   * (i.e. {@code frozeBalance < TRX_PRECISION}) is preserved through the
   * multiplication and only truncated at the final divide, so small balances
   * yield the same proportional result as the double-arithmetic path.
   */
  protected long calculateGlobalLimitV2(long frozeBalance,
      long totalLimit, long totalWeight) {
    return BigInteger.valueOf(frozeBalance)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(TRX_PRECISION)
            .multiply(BigInteger.valueOf(totalWeight)))
        .longValueExact();
  }
