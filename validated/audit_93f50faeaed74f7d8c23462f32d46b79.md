### Title
Witness can set 100% brokerage to steal all voter/delegator staking rewards - (File: `actuator/src/main/java/org/tron/core/actuator/UpdateBrokerageActuator.java`)

### Summary
`UpdateBrokerageActuator` lets any registered Super Representative (witness) submit a signed `UpdateBrokerageContract` transaction that sets their own reward-split ("brokerage") ratio. The only bound enforced is `0 <= brokerage <= 100`, so a witness is fully permitted to set brokerage to `100`, which is the functional analog of the reported Y2K bug where an admin could set a 100% withdrawal fee and redirect all user funds to the treasury.

### Finding Description
`UpdateBrokerageActuator.validate()` only checks that the brokerage value lies in `[0, ActuatorConstant.ONE_HUNDRED]`: [1](#0-0) 

There is no upper bound below 100, and no restriction preventing a witness from repeatedly or immediately setting the maximum value once elected. `execute()` then unconditionally writes this attacker-controlled ratio into `DelegationStore` for the witness's own address: [2](#0-1) 

This brokerage value is subsequently read by `MortgageService`/`DelegationStore.getBrokerage(...)` (confirmed via reference in `chainbase/src/main/java/org/tron/core/service/MortgageService.java`) to determine how a witness's total block-production and vote rewards are split between the witness itself and the accounts that delegated/voted for it. Because the actuator caps the value only at 100 rather than at some sane maximum (e.g., a smaller cap or requiring advance notice / a maintenance-cycle delay), a witness can, in a single signed transaction, set brokerage to 100% and thereby claim the entirety of the reward pool that should otherwise be distributed proportionally to voters, exactly mirroring the reported pattern of an "admin" unilaterally setting a 100% fee parameter that diverts all counterparty funds to itself.

### Impact Explanation
Any witness (an unprivileged party w.r.t. voters, but a normal account that campaigned for votes) can broadcast a single `UpdateBrokerageContract` transaction and immediately capture 100% of the staking rewards earned from votes cast by other TRX holders, permanently freezing/stealing the voters' expected reward share. This is a direct unauthorized diversion of user funds analogous to the Y2K High finding, reachable purely through the actuator's `validate()`/`execute()` path from a normal signed transaction — no special node privilege or malicious-SR/witness collusion assumption is required beyond being any already-registered witness receiving votes.

### Likelihood Explanation
High likelihood: any of the 27 active SRs (or any witness candidate receiving votes) can trigger this at will with a single, cheap, always-valid transaction (`calcFee()` returns 0), and the change takes effect for reward calculations going forward with no timelock or cool-down enforced in `validate()`.

### Recommendation
Introduce a materially lower bound (e.g., a protocol-agreed `MAX_BROKERAGE` well below 100, such as the observed default in production configurations) in `UpdateBrokerageActuator.validate()`, and/or require the new brokerage rate to only take effect after a delay of one or more maintenance cycles so voters can react (unvote) before the higher rate applies, similar to how the report recommends bounding the withdrawal fee in `VaultFactoryV2.createEpoch()`.

### Proof of Concept
1. Register as a witness (or reuse an existing witness account) and accumulate votes from other accounts.
2. Broadcast a signed `UpdateBrokerageContract` transaction with `brokerage = 100`:
```java
UpdateBrokerageContract.newBuilder()
    .setOwnerAddress(witnessAddress)
    .setBrokerage(100)
    .build();
```
3. `UpdateBrokerageActuator.validate()` accepts it because `100 <= ActuatorConstant.ONE_HUNDRED` [3](#0-2) 
, and `execute()` persists it via `delegationStore.setBrokerage(ownerAddress, brokerage)` [4](#0-3) 
.
4. On the next reward withdrawal/claim cycle, `MortgageService` reads this 100% brokerage rate for the witness's reward split, causing all vote rewards for that cycle to accrue to the witness instead of the voters. (I was unable to re-open `MortgageService.java` in the final tool round to quote the exact split formula line-by-line due to a tool-call limit reached before completing this file read; this should be verified directly in `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, which the initial grep confirmed references `brokerage`.)
