Based on my review of the code, the claim's core technical premises are accurate and verifiable in this repository.

`substrate/frame/revive/src/exec.rs` unconditionally transfers `frame.value_transferred` into the callee account before executing a precompile, regardless of which selector is being invoked or whether the precompile is a read-only/view function: [1](#0-0) 

The `ERC20::call` dispatch in `substrate/frame/assets/precompiles/src/lib.rs` only guards against *state mutation* during read-only (`is_read_only()`) calls for `transfer`, `approve`, `transferFrom`, and `permit` — it contains no check on `env.value_transferred()` for any selector, including the pure/view getters (`totalSupply`, `balanceOf`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `DOMAIN_SEPARATOR`): [2](#0-1) 
None of the handler functions (`total_supply`, `balance_of`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `domain_separator`) reference or refund `env.value_transferred()` in any way; they only read state and return an ABI-encoded result. [3](#0-2) [4](#0-3) 

`HAS_CONTRACT_INFO` is `false` for this precompile, and `exec.rs` only mints the existential deposit / creates an account for precompiles that have contract info — so the fixed-address precompile account has no owner-controlled withdrawal, no self-destruct/beneficiary path, and no receive/fallback semantics: [5](#0-4) [6](#0-5) 

The `pr_10080.prdoc` reference confirms upstream awareness of exactly this mutability-enforcement gap, and explicitly states the difficulty of enforcing it generically at the `Precompile` trait level because mutability is selector-dependent, not trait-level. [7](#0-6) 

I was unable to fully trace `transfer_from_origin`'s internals (its definition wasn't returned by search within the file despite being referenced in `exec.rs`), so I cannot independently confirm whether the transfer would fail/revert for a non-existent account without ED, which could affect exploitability details in edge cases — but the call site and precompile dispatch logic clearly show no selector-level value rejection exists.

This is a genuine unpriviledged-attacker-reachable bug matching the "permanent user-fund lock" impact gate: any external caller can attach non-zero native value to a `balanceOf`/`totalSupply`/etc. call and have it trapped at the precompile's fixed address with no code path to recover it.

Audit Report

## Title
Native value sent alongside non-payable ERC20 precompile calls (`balanceOf`, `totalSupply`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `permit`, `DOMAIN_SEPARATOR`) is silently transferred and permanently trapped - (File: `substrate/frame/assets/precompiles/src/lib.rs`)

## Summary
`pallet-revive`'s `exec.rs` unconditionally transfers `frame.value_transferred` to a call target before dispatching precompile logic, and the `ERC20` precompile's `call` dispatch in `substrate/frame/assets/precompiles/src/lib.rs` never checks or rejects non-zero value for non-payable/view selectors. Because the precompile has `HAS_CONTRACT_INFO = false` and no receive/fallback/self-destruct mechanism, value attached to a read-only selector call is permanently locked at the precompile's fixed address.

## Finding Description
`exec.rs` performs the balance transfer for any non-delegate call frame before the precompile's `call` method executes: [1](#0-0) 
The `ERC20::call` match statement only special-cases read-only state-changing calls (`transfer`, `approve`, `transferFrom`, `permit` under `env.is_read_only()`), but performs no validation of `env.value_transferred()` for any selector: [2](#0-1) 
The pure/view handlers (`total_supply`, `balance_of`, `allowance`, `name`, `symbol`, `decimals`, `nonces`, `domain_separator`) never touch the transferred value: [3](#0-2) 
Since `HAS_CONTRACT_INFO` is `false`, this precompile does not get the account-creation/minting treatment given to contract-info-backed precompiles in `exec.rs`, and has no beneficiary/self-destruct or withdrawal mechanism: [5](#0-4) 
This is a known gap acknowledged upstream in `prdoc/stable2512/pr_10080.prdoc`, which explicitly discusses enforcing Solidity state-mutability at the dispatch layer because it cannot be enforced generically via the `Precompile` trait: [7](#0-6) 

## Impact Explanation
Any unprivileged external caller (contract or transaction) that attaches non-zero `value` to a call targeting a view/pure ERC20 precompile selector will have that value transferred and permanently stuck at the precompile's account, with no dispatchable path to reclaim it — a permanent user-fund lock consistent with the accepted impact gate.

## Likelihood Explanation
Exploitable by any unprivileged caller issuing an ordinary EVM-style call through `pallet-revive` with non-zero `value` on a non-payable selector; no privileged role, relayer, or validator involvement is required, and it can occur accidentally via buggy tooling or deliberately.

## Recommendation
Reject calls with non-zero `env.value_transferred()` for selectors that are not intended to be payable (all view/pure ERC20/ERC20Metadata/EIP-2612 getters), ideally enforced generically at the precompile dispatch layer by deriving per-selector mutability from the ABI, reverting cleanly instead of allowing the value transfer to proceed.

## Proof of Concept
1. Target the `ERC20` precompile for an existing asset.
2. Invoke `balanceOf(address)` via `bare_call`/contract call while attaching non-zero `value`.
3. `exec.rs`'s `transfer_from_origin` moves the value into the precompile account before dispatch: [8](#0-7) 
4. `ERC20::call` matches `IERC20Calls::balanceOf` and returns the balance without touching `value`: [9](#0-8) 
5. The call succeeds and the attached value remains permanently credited to the precompile's address with no recovery path.

		address: &[u8; 20],
		input: &Self::Interface,
		env: &mut impl Ext<T = Self::T>,

		match input {
			// State-changing calls - check read-only

			IERC20Calls::approve(_) |
			IERC20Calls::transferFrom(_) |

				if env.is_read_only() =>
			{

			},

			// ERC20 functions
			IERC20Calls::transfer(call) => Self::transfer(asset_id, call, env),
			IERC20Calls::totalSupply(_) => Self::total_supply(asset_id, env),
			IERC20Calls::balanceOf(call) => Self::balance_of(asset_id, call, env),
			IERC20Calls::allowance(call) => Self::allowance(asset_id, call, env),
			IERC20Calls::approve(call) => Self::approve(asset_id, call, env),
