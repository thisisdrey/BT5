### Title
Anti-replay window check-then-update race allows packet replay bypass - (File: `connection_state.go`)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay window check (`window.Check`) and the anti-replay window commit (`window.Update`) into two separate critical sections, releasing `decryptLock` in between while performing the (comparatively expensive, lock-free) AEAD decryption. This is the same class of bug as the SeaDrop reentrancy report: a state check ("have I already processed this nonce/mint?") is performed, then an external/expensive operation runs without holding the state lock, and only afterward is the state ("already seen") committed. Just as the SeaDrop `feeRecipient` fallback can re-enter `mintPublic` between the mint-quantity check and the point where the mint count is actually persisted, two concurrent threads processing the same duplicated on-wire packet (an attacker-replayed UDP datagram) can both pass `window.Check` for the same `messageCounter` before either calls `window.Update`, because the lock is dropped between the two calls.

### Finding Description
`Decrypt` takes `decryptLock`, calls `cs.window.Check(l, messageCounter)`, releases the lock, performs `cs.dKey.DecryptDanger(...)` (AEAD open) without holding any lock, and only afterward re-acquires `decryptLock` to call `cs.window.Update(l, messageCounter)`: [1](#0-0) 

`VerifyRelay` has the identical pattern for relay frames: [2](#0-1) 

The replay-window bookkeeping itself (`Bits.Check` / `Bits.Update`) is designed as two distinct operations — `Check` only reads whether a counter position is marked seen, `Update` performs the actual marking/sliding of the window — and neither method takes any lock internally; all synchronization is delegated to the caller's `decryptLock`: [3](#0-2) [4](#0-3) 

Because the caller releases `decryptLock` between `Check` and `Update`, and `outside.go`'s inbound packet handling can process multiple UDP datagrams concurrently (e.g., via multiple reader queues), an attacker who captures and retransmits (replays) a single ciphertext packet twice in quick succession can cause both copies to reach the `Check` call before either has reached `Update`. Both copies pass the "not yet seen" check, both are independently AEAD-decrypted and accepted, and only the second `Update` call would (at best) detect the duplicate — after the plaintext has already been delivered/processed twice. This defeats the intended nonce/counter replay protection, which is exactly the guarantee the anti-replay window exists to provide.

This mirrors the SeaDrop analog precisely: in SeaDrop, the check (`_checkMintQuantity`) happens, then an external call (fee transfer) is made that can recursively re-enter before the mint-count state is durably updated; here, the check (`window.Check`) happens, then an expensive external-facing operation (AEAD decrypt) runs without the lock, before the anti-replay state (`window.Update`) is durably committed — allowing the same packet to be "processed" twice, i.e., a replay bypass.

### Impact Explanation
A successful exploitation permits replaying an authenticated Nebula data-plane packet (or relay frame) so it is decrypted and delivered to the local processing pipeline more than once, defeating the counter-based anti-replay defense that Nebula relies on in lieu of transport-level replay protection. Depending on packet contents, this can lead to duplicate injected traffic on the TUN device, duplicate relay forwarding, or double-processing of any message-type payload — a data-plane integrity/anti-replay bypass. This falls under "traffic decryption/forgery/replay" in the accepted impact categories.

### Likelihood Explanation
The attacker does not need a CA-signed certificate or any privileged role — they only need to observe/capture one legitimate ciphertext packet on the wire (feasible for any network-position attacker, consistent with UDP being unauthenticated at the transport layer) and retransmit it twice in a tight enough window to win the race between the two lock-released windows in `Decrypt`/`VerifyRelay`. This is a timing-dependent race rather than a deterministic bypass, so likelihood is moderate: it requires precise timing to land two decrypt calls concurrently, and Nebula's use of a single lock briefly narrows the race window, but the race is structurally present and reachable purely from the network without holding any credential.

### Recommendation
Perform the check, decrypt, and window update as a single atomic operation with respect to `decryptLock` (or use an optimistic double-check pattern with a durable "provisionally reserved" state), e.g.:
1. Hold `decryptLock` for the entire `Check` → `DecryptDanger` → `Update` sequence, or
2. Reserve the counter slot (mark it as "in flight") under the lock before decrypting, and revert the reservation on decrypt failure, so no second concurrent packet with the same counter can pass `Check` while the first is still being processed.

This closes the check-then-commit gap analogous to adding a reentrancy lock around the SeaDrop fee-dispersal/mint-count update.

**Note on investigation completeness:** I was unable to fully confirm within available tool iterations whether `outside.go`'s packet-reading loop actually dispatches to `Decrypt`/`VerifyRelay` from multiple concurrent goroutines for the *same* `HostInfo`/`ConnectionState` (e.g., via multiple UDP reader queues bound to one interface) — this concurrency model determines how easily the race is triggered in practice. The lock-release gap itself between `Check` and `Update` is verified directly in `connection_state.go`, but whether nebula's packet-read architecture makes concurrent decrypts of the *same connection* routine (vs. strictly per-queue serialized) would need further confirmation, e.g. by reading `outside.go`'s caller/goroutine setup in `interface.go` and the UDP read-loop files in full.

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}

func (b *Bits) Update(l *slog.Logger, i uint64) bool {
	// Fast path: i is the next expected counter. Split out so the function
	// stays small and avoids paying for the slow paths' slog argument-build
	// stack frame on every call. The bit read/test/write is inlined to
	// touch the backing word once.
	if i == b.current+1 {
		pos := i & b.lengthMask
		word := pos >> 6
		mask := uint64(1) << (pos & 63)
		w := b.bits[word]
		if i > b.length && w&mask == 0 {
			b.lostCounter.Inc(1)
		}
		b.bits[word] = w | mask
		b.current = i
		return true
	}
	return b.updateSlow(l, i)
}
