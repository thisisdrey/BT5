The OpenKM CVE-2022-2131 concerns a Java `XMLReader` (SAX parser) that resolves external entities defined via `<!DOCTYPE>`/`<!ENTITY>` declarations because the required secure-processing flags weren't set. This bug class does not map onto Go's standard library.

In `encoding/xml`, the `Decoder.rawToken` function treats `<!DOCTYPE ...>`, `<!ENTITY ...>`, and other `<! ... >` constructs purely as opaque `Directive` tokens — it accumulates the raw bytes without ever parsing or acting on `<!ENTITY>` declarations. <cite repo="Kohvert/go--001" path="src/encoding/xml/xml.go" start="718="722">723-786</cite> The only entity resolution performed is in `Decoder.text`, which recognizes the five predefined XML entities (`lt`, `gt`, `amp`, `apos`, `quot`) and, optionally, entries from the caller-supplied `d.Entity` map — it never consults or expands entities declared in a document's own `<!DOCTYPE>`/`<!ENTITY>` section, and it performs no network or filesystem access to resolve "SYSTEM"/"PUBLIC" external identifiers. [1](#0-0)  This is confirmed by the test data showing `<!ENTITY rdf "...">` declarations preserved verbatim inside `Directive` tokens rather than being expanded, and unknown entity references like `&何;`/`&is-it;` only resolve via the explicit `testEntity` map passed by the test, not via DOCTYPE. [2](#0-1) [3](#0-2) 

Because Go's XML decoder has no DTD/external-entity resolution mechanism at all (no `XMLReader`-style feature flags to misconfigure, and no code path that fetches external resources named in a DTD), there is no analogous "missing security flag" defect to find. This is a fundamental design difference, not an unfixed bug, so no valid analog exists in this repository.
