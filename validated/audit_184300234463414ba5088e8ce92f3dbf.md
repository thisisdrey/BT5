Audit Report

## Title
Silent loss of ERC20 asset value when multiple ERC20-matched assets are deposited in a single XCM `DepositAsset` — `ERC20Transactor::deposit_asset_with_surplus` drops all but the first asset - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::deposit_asset_with_surplus` only processes the first fungible asset found in the `AssetsInHolding` collection it receives via `what.fungible_assets_iter().next()`, and on success returns only `Ok(surplus)` without reinstating or transacting any remaining assets in `what`. Any additional matched assets are consumed and dropped, with no on-chain ERC20 transfer and no corresponding balance decrease anywhere else, resulting in unrecoverable loss of asset value.

## Finding Description
`ERC20Transactor::deposit_asset_with_surplus` takes `what: AssetsInHolding` by value, uses `defensive_assert!(what.len() == 1, ...)` (a no-op in production builds), and then only inspects `what.fungible_assets_iter().next()` to obtain the single asset it transacts to the beneficiary via `pallet_revive::Pallet::<T>::bare_call` performing an `IERC20::transferCall`. [1](#0-0) 

On the success path it returns `Ok(surplus)` — the `what` value (which may still contain additional matched assets beyond the first) is not returned to the caller and is simply dropped when the function returns: [2](#0-1) 

The `TransactAsset` trait's default `deposit_asset_with_surplus` signature confirms `what: AssetsInHolding` is a plural collection potentially containing multiple assets, and the tuple implementation of `TransactAsset` (used to compose `AssetTransactors` in the runtime) is designed to pass the whole `what` to each transactor in the tuple, retrying with only unspent remainder on `AssetNotFound`/`Unimplemented`: [3](#0-2) 

The `defensive_assert!` at line 234 is compiled out / becomes a no-op in production (release) builds, so it does not prevent execution when `what.len() != 1`; it only aids debugging. There is no `Err` returned when more than one asset is present — the code proceeds and silently truncates to the first asset.

## Impact Explanation
This affects asset value conservation: an XCM program that withdraws multiple distinct ERC20 assets and deposits them together (e.g., via a wildcard/`AllCounted(n>=2)` filter that causes the executor to hand multiple matched assets to `ERC20Transactor::deposit_asset_with_surplus` in a single call) results in the sender's balance being reduced for all assets withdrawn (each `withdraw_asset_with_surplus` call transacts a single asset correctly, per the withdraw path at lines 150-216), but the beneficiary only receiving the first matched asset. The remaining asset(s)' value is permanently lost — not credited to the beneficiary, not returned to the sender, and not reflected anywhere in on-chain state. This is a value-conservation violation matching the required impact class ("Balances, assets ... must conserve value and settle exactly once to the rightful beneficiary and amount").

## Likelihood Explanation
This is reachable by any unprivileged signed account that can call `pallet_xcm::execute` (or route XCM through this transactor via cross-chain messages) with a program constructing more than one ERC20 asset in holding before a combined `DepositAsset`. No governance, admin, or privileged access is required. The only existing guard (`defensive_assert!`) is inert in production. This matches the exploit scenario already partially demonstrated by the repository's own test `withdraw_and_deposit_erc20s`, which deliberately uses `AllCounted(1)` per deposit to avoid tripping this exact bug — confirming the developers were aware multiple assets in one deposit call is unsafe.

## Recommendation
Modify `ERC20Transactor::deposit_asset_with_surplus` to iterate over all fungible assets in `what`, transact each individually, aggregate the surplus, and on partial failure return the untransacted remainder with an `Err` rather than dropping it. Alternatively, if the transactor is fundamentally restricted to a single asset per call, return an explicit `Err((what, ...))` when `what.len() != 1` instead of relying on `defensive_assert!`, and ensure the executor/asset-filter configuration guarantees single-asset invocations.

## Proof of Concept
1. Deploy two ERC20 contracts (`erc20_a`, `erc20_b`) via `pallet_revive` and fund `sender` with both.
2. Execute via `PolkadotXcm::execute` (signed by `sender`) an XCM program:
   - `WithdrawAsset((AccountKey20{erc20_a}, amount_a))`
   - `WithdrawAsset((AccountKey20{erc20_b}, amount_b))`
   - `DepositAsset(AllCounted(2), beneficiary)`
3. Observe: execution returns `Ok`, sender's balance for both `erc20_a` and `erc20_b` is reduced, but `beneficiary` receives only the first-iterated token; the other token's value is unaccounted for on-chain.
