### Title
UnDelegateResourceProcessor (TVM native contract) clears the resource-delegation index while ignoring the "locked" delegation entry, orphaning frozen resource - (File: `actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java`)

### Summary
A TRON account (or contract) can hold two independent `DelegatedResourceCapsule` records for the same owner/receiver pair: a "locked" record (`createDbKeyV2(owner, receiver, true)`, created by `DelegateResourceActuator`/`DelegateResourceProcessor` when `lock=true`) and an "unlocked" record (`createDbKeyV2(owner, receiver, false)`). The TVM-reachable native contract `UnDelegateResourceProcessor`, invoked when a contract calls the un-delegate-resource precompile, only ever reads/writes the **unlocked** key and, when that unlocked balance hits zero, unconditionally deletes the `DelegatedResourceAccountIndexStore` V2 index entries for the pair — without checking whether a "locked" entry with remaining frozen balance still exists.

### Finding Description
`UnDelegateResourceProcessor.execute()` fetches only the unlocked delegated-resource capsule: [3](#0-2) 
and, once its balance reaches zero, deletes the index without ever checking the locked key: [4](#0-3) 

This is the same class of bug as CVE-2021-28703: a resource that can legitimately reside in more than one tracked "location" (here, the `lock=true` and `lock=false` `DelegatedResourceCapsule` keys, analogous to Xen's v1/v2 grant-table status pages) is de-allocated/de-indexed based on inspecting only one of those locations. The transaction-level actuator `UnDelegateResourceActuator` correctly guards this by checking both the lock and unlock keys before clearing the index: [5](#0-4) 
but the TVM native-contract counterpart used by smart contracts omits this check entirely, so it is inconsistent with its own on-chain sibling.

An account can accumulate both a locked and an unlocked delegation to the same receiver by combining the ordinary broadcast `DelegateResourceContract` (which supports `lock=true/false`) with the TVM-callable delegate/undelegate precompiles (which always operate on the unlocked key). Once the unlocked portion is fully un-delegated through the TVM path, the `DelegatedResourceAccountIndexStore` V2 entries for that owner/receiver pair are wiped out even though the locked `DelegatedResourceCapsule` (with real frozen TRX and an active `AcquiredDelegatedFrozenV2Balance` effect on the receiver) still exists in `DelegatedResourceStore`.

### Impact Explanation
After the index is cleared:
- The delegation becomes invisible to the standard discovery path (`DelegatedResourceAccountIndexStore.getV2Index`), used by wallet/API queries, even though the receiver still benefits from the resource backed by the still-existing locked capsule — an accounting desync between the visible index and real backing state.
- Because the TVM native `UnDelegateResourceProcessor.validate()` only recognizes the unlocked key (`repo.getDelegatedResource(key)` with `lock=false`) and throws `"delegated Resource does not exist"` if that unlocked capsule is absent, the owner loses any TVM-reachable path to reclaim the still-existing locked balance once the unlocked entry is gone, effectively freezing that portion of the owner's staked TRX (permanent-freezing-of-funds class impact) unless the owner separately drives state back through the (non-TVM) `UnDelegateResourceActuator`, which does check both keys — but by then the index bookkeeping is already desynced from the actual stored capsules.

### Likelihood Explanation
Reaching this requires only ordinary, unprivileged actions: broadcasting a `DelegateResourceContract` with `lock=true`, then having the same account (which can be a contract) delegate additional resource to the same receiver via the TVM native contract path (`lock=false`), and finally calling the TVM un-delegate precompile to drain the unlocked portion. No special privileges (SR/witness/committee) are needed — any contract deployer/caller can trigger it.

### Recommendation
Make `UnDelegateResourceProcessor.execute()` mirror `UnDelegateResourceActuator.execute()`: before deleting the `DelegatedResourceAccountIndexStore` V2 index entries, also fetch the locked-key `DelegatedResourceCapsule` (`createDbKeyV2(owner, receiver, true)`) and only clear the index when both the locked and unlocked capsules are null/zero-balance.

### Proof of Concept
1. Account `A` (can be a contract) calls `DelegateResourceContract` with `lock=true`, delegating BANDWIDTH to receiver `B` — creates a locked `DelegatedResourceCapsule` at `createDbKeyV2(A,B,true)`.
2. Account `A` calls the TVM delegate-resource precompile (`DelegateResourceProcessor`) to delegate additional BANDWIDTH to `B` — creates an unlocked `DelegatedResourceCapsule` at `createDbKeyV2(A,B,false)`.
3. Account `A` calls the TVM un-delegate-resource precompile (`UnDelegateResourceProcessor`) requesting exactly the unlocked balance amount.
4. `UnDelegateResourceProcessor.execute()` zeroes the unlocked capsule and, seeing its balance at 0, deletes the `V2_FROM_PREFIX`/`V2_TO_PREFIX` index entries for `(A,B)` — even though the locked capsule from step 1 still holds frozen balance and `B` still has the corresponding `AcquiredDelegatedFrozenV2Balance`.
5. Querying `DelegatedResourceAccountIndexStore.getV2Index(A)`/`(B)` now shows no delegation between `A` and `B`, while the locked `DelegatedResourceCapsule` and its live effect on `B`'s resource remain in the store, and `A` can no longer reach that locked balance through the TVM un-delegate path (`validate()` requires the now-deleted unlocked key).
