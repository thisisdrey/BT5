### Title
Unchecked `ContractCapsule` dereference in `Program.callToAddress()` — potential NPE from CALL/DELEGATECALL/CALLCODE/STATICCALL to a code-bearing address with a missing contract record - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
CVE-2016-3120 is a NULL-pointer dereference caused by the KDC using the wrong (incorrect-type/missing) client data structure when a feature flag (`restrict_anonymous_to_tgt`) is enabled, crashing the daemon on an attacker-supplied request. The analogous pattern in java-tron is in `Program.callToAddress()`, where — gated behind the `allowTvmCompatibleEvm` chain parameter — the code unconditionally dereferences the result of `invoke.getDeposit().getContract(codeAddress)` without a null check, assuming that any address with non-empty "code" necessarily has a corresponding `ContractCapsule` in the contract store.

### Finding Description

and later, when the feature flag is on, the contract version is read directly off the contract object without any null guard: [2](#0-1) 

Every other place in the codebase that performs the analogous lookup treats a null `ContractCapsule` as an expected/handled case — e.g. `VMActuator.call()` explicitly checks `deployedContract == null` before use: [3](#0-2) 

and `Program.isContractExist()` / `Program.isContract()` treat a null result from `getContract(...)` as a valid, non-exceptional outcome: [4](#0-3) [5](#0-4) 

The `callToAddress()` code path, by contrast, assumes the invariant "code present at address ⇒ `ContractCapsule` present at address" always holds, and dereferences the capsule directly. This mirrors the CVE-2016-3120 pattern: a security/compat feature flag (`restrict_anonymous_to_tgt` in Kerberos, `allowTvmCompatibleEvm` here) causes the code to reach into a data structure (client principal / `ContractCapsule`) using an assumption about its presence/type that is not actually guaranteed for all reachable inputs, and the missing defensive null check turns a data-model inconsistency into a NullPointerException in a process that serves live, unprivileged requests.

### Impact Explanation
If the assumed invariant can be violated for any reachable `codeAddress` (e.g., through `CALLCODE`/`DELEGATECALL` targeting the special/precompiled address range, an address whose account type is `Contract` but whose `ContractCapsule` entry does not exist, or any other divergence between the "has code" and "has contract record" checks used in different code paths), a single unprivileged `TriggerSmartContract` transaction (or a `constant`/`estimateEnergy` call through the same VM path exposed via `Wallet`/JSON-RPC `eth_call`/`eth_estimateGas`) executing an internal `CALL`-family opcode would throw an uncaught `NullPointerException` inside VM execution. Because this executes inside block-application (`Manager.processBlock` → `Runtime`/`VMActuator` → `Program`), an uncaught runtime exception at this layer risks aborting transaction/block processing rather than being cleanly converted to a `ContractValidateException`/`OutOfEnergyException`, which is the intended failure mode for all other malformed-input paths in the TVM. This can manifest as a node crash or a permanently unserviceable RPC path for constant calls, which matches the CVE's "NULL pointer dereference and daemon crash" outcome, reachable by any transaction broadcaster or constant-call/JSON-RPC caller — not a privileged actor.

### Likelihood Explanation
This code path is exercised on every internal message call performed by a smart contract when `allowTvmCompatibleEvm` (a currently-active/likely-active hard-fork parameter on public networks) is enabled, so the general path is reached extremely often. The likelihood that the specific null-dereference actually fires depends on whether an attacker can produce a `codeAddress` for which `getCode()`/the preceding `isNotEmpty(programCode)` check succeeds while `getContract()` returns null — I was not able to fully confirm within the available tool budget whether such a state is reachable from ordinary contract-creation/self-destruct/precompile-address flows (this requires tracing `RepositoryImpl.getCode()` vs `RepositoryImpl.getContract()` and the account-type transitions during `SELFDESTRUCT`/`CREATE2` collisions in more depth than I could complete). This is the primary source of uncertainty in this finding, and I flag it explicitly rather than asserting definitive exploitability.

### Recommendation
Add a null check on the result of `invoke.getDeposit().getContract(codeAddress)` in `Program.callToAddress()` before calling `.getContractVersion()`, mirroring the defensive pattern already used in `VMActuator.call()` and `Program.isContractExist()`/`isContract()`. If the capsule is unexpectedly null, default the contract version (e.g., to legacy/version 0) instead of dereferencing, and add a regression test that drives a `CALL`/`DELEGATECALL`/`CALLCODE`/`STATICCALL` to a code-bearing address lacking a `ContractCapsule` record under `allowTvmCompatibleEvm=1`.

### Proof of Concept
Not fully constructible with the available read-only access: reproducing this would require confirming a concrete state-transition (via `CREATE2`/`SELFDESTRUCT`/precompiled-address collision, or an inconsistent account migration) that yields non-empty code at an address with no corresponding `ContractCapsule`, then issuing a `TriggerSmartContract` (or `eth_call`) that performs a `CALL`/`DELEGATECALL` to that address while `allowTvmCompatibleEvm=1`. I was unable to verify within the tool budget whether `RepositoryImpl.getCode()` can return non-empty data for an address where `RepositoryImpl.getContract()` returns null; this must be validated by a Devin session with full read/write access to the codebase and test harness before treating this as confirmed-exploitable rather than a defensive-coding gap analogous to the CVE pattern.
