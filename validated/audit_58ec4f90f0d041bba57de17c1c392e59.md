### Title
WriteRef RPC bypasses pre-receive/update access-check hooks that gate all other reference-writing paths - ([File: internal/gitaly/service/repository/write_ref.go])

### Summary
The Sherlock finding shows that `JUSDBank.borrow()` gates state changes through `_isAccountSafeAfterBorrow`, but `withdraw()` — which can produce an equivalent (or worse) state — omits that gate entirely, letting a user bypass the invariant by reaching the same end state through the unchecked path. The same "two roads to the same state, only one road is gated" pattern exists in gitaly: reference updates performed through `OperationService` RPCs (`UserCreateTag`, `UserCherryPick`, `UserUpdateSubmodule`, etc.) are always routed through `updateReferenceWithHooks` → `updateref.UpdaterWithHooks.UpdateReference`, which invokes the `pre-receive` hook (and therefore GitLab Rails' `/internal/allowed` access check) and the `update`/`reference-transaction` hooks before any ref is written. `RepositoryService.WriteRef`, however, updates the very same on-disk references directly via `updateref.New(ctx, repo)` and never calls the hook manager at all.

### Finding Description
`internal/gitaly/service/repository/write_ref.go` implements `WriteRef`: [1](#0-0) 

The actual ref mutation in `updateRef` builds an `updateref.Updater` and commits the change with no call into `hook.Manager`, no `PreReceiveHook`, no `UpdateHook`, and no `ReferenceTransactionHook`: [2](#0-1) 

Compare this to the mandated path for every other reference-writing RPC in `OperationService` (`UserCreateTag`, `UserCherryPick`, `UserUpdateSubmodule`, etc.), which call `s.updateReferenceWithHooks`, itself a thin wrapper over `UpdaterWithHooks.UpdateReference`: [3](#0-2) 

`UpdateReference` explicitly runs `PreReceiveHook` — which is what triggers GitLab's `/internal/allowed` access check and any admin-installed custom `pre-receive` hooks — before it ever touches the ref, and subsequently runs the `update` hook: [4](#0-3) 

Gitaly's own documentation states unambiguously that "Most RPCs in the `OperationService` that write objects into the repository manually invoke these hooks using the `updateref.UpdaterWithHooks` structure," implying an expectation that *all* privileged reference mutations flow through the hook gate: [5](#0-4) 

`WriteRef`'s `validateWriteRefRequest` only validates ref-name format and repository identity — it performs no access-check call and no hook invocation: [6](#0-5) 

Because `WriteRef` accepts an arbitrary `Ref` (any `refs/...` path) and an arbitrary `Revision`, and is reachable the same way any other Gitaly RPC is reachable from GitLab-Shell/Workhorse on behalf of an authenticated but otherwise unprivileged git user/API caller, it functions as an unguarded side-door: any consumer that can invoke `RepositoryService.WriteRef` can create, move, or delete branches/tags and thereby land the repository in exactly the same terminal ref state that the guarded `OperationService` RPCs would have blocked (e.g., pushing to a protected branch, or updating a branch to a commit that would otherwise fail Rails' `/internal/allowed` check or a custom `pre-receive` hook). This mirrors the JUSDBank pattern precisely: the invariant ("no ref update reaches disk without pre-receive/access-check approval") is enforced on one write path and completely absent on a second write path that reaches the identical underlying resource (`objects/info/refs` state).

### Impact Explanation
Any caller capable of invoking `WriteRef` can silently bypass GitLab's push-time access control gate (`/internal/allowed`) and any custom server-side `pre-receive`/`update` hooks that administrators rely on to enforce protected-branch policies, commit signing/verification, or other compliance checks. Because the gate that other RPCs treat as mandatory is simply absent here, this creates the same "systemic bypass of a supposedly always-enforced check" impact described in the source report — reference state can be manipulated (branch/tag creation, force-move, deletion) without ever triggering the checks that the rest of the system assumes are universally applied to ref writes.

### Likelihood Explanation
`WriteRef` is a real, exported gRPC method on `RepositoryService`, wired identically to the other repository/operation RPCs (same gRPC server, same interceptor stack), and its handler performs no hook invocation by design — this isn't a corner case triggered by malformed input, it is the RPC's normal, documented behavior for every call. The only mitigating factor is that in a properly configured GitLab deployment, callers other than trusted internal services (Rails/Workhorse/Gitaly itself) may not be expected to call `WriteRef` directly; however, nothing in the code visible here enforces that restriction at the Gitaly RPC layer itself (no repository-level check equivalent to the `pre-receive` gate), so the guarantee depends entirely on external authorization/network topology rather than the invariant being enforced in-code as it is for `UserCreateTag`/`UserCherryPick`/etc.

### Recommendation
Route `WriteRef`'s ref mutation through the same `updateref.UpdaterWithHooks` (or equivalent `hook.Manager`) path used by `OperationService` RPCs, so that every reference write — regardless of which RPC performs it — is gated by `PreReceiveHook`/`UpdateHook`/`ReferenceTransactionHook` before being committed. If `WriteRef` is intentionally meant to be a low-level, hook-bypassing primitive for internal/administrative use only, that intent should be enforced explicitly in code (e.g., restricting the RPC to specific trusted callers or documenting/asserting it is never reachable from user-triggered push/API flows) rather than relying purely on external deployment conventions.

### Proof of Concept
1. As a caller capable of reaching `RepositoryService.WriteRef` (e.g., via any component/proxy that forwards to Gitaly's gRPC endpoint), send:
```
WriteRefRequest{
  Repository: <target repo>,
  Ref:        []byte("refs/heads/protected-branch"),
  Revision:   []byte(<attacker-controlled commit sha>),
}
``` [7](#0-6) 
2. `writeRef` resolves the revision and calls `updateRef`, which starts an `updateref.Updater`, queues the update, and commits it directly to the ref store — no `PreReceiveHook`, no `/internal/allowed` call, no custom hook execution occurs anywhere in this path. [2](#0-1) 
3. Compare with the equivalent `UserCreateTag` flow, where the identical class of ref mutation is refused unless `PreReceiveHook`/custom hooks succeed: [8](#0-7) 
4. The `refs/heads/protected-branch` reference now points at the attacker-supplied commit even though the exact same mutation attempted via `UserCreateTag`/`UserCherryPick` would have been rejected by the pre-receive access check, demonstrating the bypass.

**Uncertainty:** I could not verify from the indexed proto whether `WriteRef` carries an `op_type`/access-scope annotation (e.g. `MAINTENANCE`) that Praefect or an authorization layer uses to restrict which callers may invoke it in production topologies; the proto search for `WriteRef`'s specific RPC definition inside `proto/repository.proto` did not return the matching lines before tool access ended. If such an annotation restricts `WriteRef` to privileged/internal-only callers, this would reduce likelihood and should be confirmed via a full read of `proto/repository.proto` (the `rpc WriteRef(...)` block and its `option (op_type)`).

func validateWriteRefRequest(ctx context.Context, locator storage.Locator, req *gitalypb.WriteRefRequest) error {
	if err := locator.ValidateRepository(ctx, req.GetRepository()); err != nil {
		return err
	}
	if err := git.ValidateRevision(req.GetRef()); err != nil {
		return fmt.Errorf("invalid ref: %w", err)
	}
	if err := git.ValidateRevision(req.GetRevision()); err != nil {
		return fmt.Errorf("invalid revision: %w", err)
	}
	if len(req.GetOldRevision()) > 0 {
		if err := git.ValidateRevision(req.GetOldRevision()); err != nil {
			return fmt.Errorf("invalid OldRevision: %w", err)
		}
	}

	if !bytes.Equal(req.GetRef(), []byte("HEAD")) && !bytes.HasPrefix(req.GetRef(), []byte("refs/")) {
		return fmt.Errorf("ref has to be a full reference")
	}
	return nil
}
