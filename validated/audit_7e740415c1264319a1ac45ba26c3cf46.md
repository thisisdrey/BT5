## Finding

### Title
Spot-ratio-based valuation in Exchange withdraw/inject actuators enables self-sandwich extraction of pooled asset value - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
The reported bug is that `USSDRebalancer` trusts a Uniswap pool's instantaneous `slot0` spot price (an easily manipulable value with low liquidity) to make a critical financial decision. The equivalent construct in java-tron is its own internal AMM ("Exchange"): `ExchangeWithdrawActuator` and `ExchangeInjectActuator` both compute the counter-asset amount purely from the pool's current instantaneous reserve ratio (`firstTokenBalance`/`secondTokenBalance`), i.e. the pool's spot price, with no TWAP, no minimum-received/slippage protection, and no fee — unlike `ExchangeTransactionActuator` which at least enforces a caller-supplied `expected` floor.

### Finding Description
`ExchangeWithdrawActuator.execute`/`doValidate` computes `anotherTokenQuant` as `secondTokenBalance * tokenQuant / firstTokenBalance` (or the symmetric case), i.e. directly reading the pool's current spot ratio: [1](#0-0) . The validate path mirrors the same spot-ratio math with only a rounding-precision check, no slippage/TWAP protection: [2](#0-1) .

`ExchangeInjectActuator` has the identical pattern for adding liquidity, deriving the required counter-asset amount from the live ratio: [3](#0-2) .

Crucially, the pool's ratio can be moved arbitrarily in the same block by anyone via `ExchangeTransactionActuator`, which executes an unrestricted swap against the pool using the Bancor-style curve in `ExchangeCapsule.transaction`: [4](#0-3) . That swap has zero built-in fee (`calcFee()` returns 0 for both trade and withdraw/inject: [5](#0-4)  and [6](#0-5) ), and only requires the caller-supplied `expected` amount, which the attacker fully controls.

Withdraw and inject are restricted to the pool's creator address (`account is not creator` check): [7](#0-6) . However, `ExchangeCreateContract` is open to any account — any unprivileged address can create its own exchange, seed it, and then let it accumulate other users' asset value through ordinary trading (`ExchangeTransactionContract` is unrestricted). Because the withdraw/inject payout is computed from the *live spot ratio* rather than any invariant-preserving/TWAP-based accounting, the creator can, within one block/transaction sequence:
1. Submit a large `ExchangeTransactionContract` swap against their own pool to skew the reserve ratio,
2. Immediately submit `ExchangeWithdrawContract` to pull out a disproportionate share of the token that became relatively scarce (valued at the manipulated ratio) while returning only the abundant token,
3. Reverse the initial swap to restore the ratio,
netting value that was contributed to the pool by other traders' prior legitimate swaps, since there is no fee, no TWAP anchor, and no minimum-outcome protection tied to a non-manipulable reference price.

### Impact Explanation
This allows the pool creator (an ordinary, unprivileged account) to atomically drain value contributed by other traders who swapped through the same exchange pool, resulting in an unauthorized transfer of asset value out of the pool. This matches the "unbacked balance / theft of funds" acceptance criteria, since honest traders' TRX/TRC10 value locked in the pool can be extracted disproportionately by the creator through spot-ratio manipulation combined with withdraw.

### Likelihood Explanation
Likelihood is moderate-to-high: any account can call `ExchangeCreateContract`, `ExchangeTransactionContract`, and (as creator) `ExchangeWithdrawContract`/`ExchangeInjectContract` with no special privileges, and all of the required calculations rely purely on the currently stored reserve balances with no anti-manipulation safeguard (no TWAP, no fee, no external price check).

### Recommendation
Do not derive withdraw/inject settlement amounts purely from the instantaneous reserve ratio at execution time. Either (a) apply a fee on trades so the pool cannot be manipulated cost-free within a single block, (b) require a caller-supplied minimum-received bound (as already done for `ExchangeTransactionContract`'s `expected` field) for withdraw/inject, or (c) base payout on a time-weighted or otherwise manipulation-resistant measure of the pool state rather than the single most-recent balance snapshot.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create pool P(TokenA, TokenB) with balanced reserves, becoming its creator.
2. Multiple independent users trade against P via `ExchangeTransactionContract`, shifting real economic value into P (e.g., depositing TokenA to withdraw TokenB over time), so P holds value contributed by third parties.
3. Attacker, in one transaction sequence, issues a large `ExchangeTransactionContract` swap of TokenA→TokenB against P to skew `firstTokenBalance`/`secondTokenBalance` (see `ExchangeCapsule.transaction`, [4](#0-3) ).
4. Attacker immediately calls `ExchangeWithdrawContract` as pool creator; `anotherTokenQuant` is computed from the now-skewed ratio ( [1](#0-0) ), letting the attacker withdraw more of the scarce token than their fair pre-skew share.
5. Attacker reverses the initial swap (TokenB→TokenA) to restore P's ratio, completing the sandwich with a net gain funded by the third-party value previously deposited into P.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
