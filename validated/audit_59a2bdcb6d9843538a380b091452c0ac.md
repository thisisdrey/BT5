## Analysis

The reported CVE-2018-10535 is a GNU Binutils BFD (`elf.c`) issue — irrelevant to Go directly, but Go's own linker (`cmd/link`) contains an ELF object-file *symbol table* reader with an almost identical bug class: an unvalidated section index taken from a symbol table entry is used directly to index into the linker's in-memory section array, causing a crash on a crafted object file.

In `readelfsym` (invoked while the linker loads a `.o`/`.syso`/archive-member ELF file, e.g. as produced by cgo or embedded by a package), the `STT_SECTION` case indexes the section table with the raw, attacker-controlled `shndx` field with no bounds check: [1](#0-0) 

Compare this to the later "sanitized" path for `STT_OBJECT/FUNC/NOTYPE/COMMON` symbols in the caller `Load()`, which explicitly validates `shndx` **before** dereferencing the section slice: [2](#0-1) 

That bounds check, however, is performed by the *caller* only for the non-section symbol types, and it runs *after* `readelfsym` has already returned — meaning it cannot protect the `STT_SECTION` branch, which dereferences `elfobj.sect[elfsym.shndx]` unconditionally inside `readelfsym` itself: [3](#0-2) 

`elfsym.shndx` is a 16-bit value parsed straight from the ELF symbol table with no validation: [4](#0-3) 

If the symbol table contains a `STT_SECTION`-typed entry whose `st_shndx` is greater than or equal to `elfobj.nsect` (the linker's parsed section count), the slice index `elfobj.sect[elfsym.shndx]` panics with "index out of range," crashing the linker/build. This is directly analogous to the reported BFD bug: a symtab entry of `SECTION` type with an invalid/unvalidated section reference causes an unchecked dereference and a crash.

### Reachability

`readelfsym`/`Load` is invoked by `cmd/link/internal/loadelf` whenever the linker consumes an ELF object as part of a normal `go build`/`go test` workflow — most commonly cgo-compiled `.o` files or `.syso` files bundled directly in a Go package's source tree (no `cgo` toolchain needed to trigger it, since `.syso` files are linked in verbatim). A malicious or compromised module can ship a crafted `.syso`/ELF object with such a symbol table entry; a normal `go build` on that module triggers the panic without requiring privileged access.

### Assessment

This qualifies as a plausible malicious-input parser panic in a production Go path (the linker's ELF object loader), reached via a standard `go build` on attacker-supplied source/module content — matching the "published module/archive/source consumed by a normal victim workflow" threat model and the Go security policy's allowance for parser panics on malicious input.

### Title
Unvalidated ELF section index causes out-of-bounds panic in linker's ELF symbol loader - (File: `src/cmd/link/internal/loadelf/ldelf.go`)

### Summary
`readelfsym` in the Go linker's ELF object loader indexes `elfobj.sect[elfsym.shndx]` for `STT_SECTION` symbols without validating that `shndx` is within the parsed section table bounds, unlike the equivalent check performed for other symbol types in the caller. A crafted ELF object (e.g. embedded `.syso` file) with an out-of-range section index in a `SECTION`-type symtab entry crashes the linker during a normal `go build`.

### Finding Description
Attacker supplies a Go package/module containing a crafted `.syso`/ELF object file → `go build` invokes `cmd/link/internal/loadelf.Load` → `readelfsym` parses the symbol table entry and reads `elfsym.shndx` directly from the file with no range check → for `elf.STT_SECTION` type symbols, `s = elfobj.sect[elfsym.shndx].sym` indexes the section slice unconditionally → if `shndx >= elfobj.nsect`, this is an out-of-bounds slice access and panics, crashing `go build`. The bounds check that exists in `Load()` (`if uint(elfsym.shndx) >= elfobj.nsect || elfsym.shndx == 0 { continue }`) runs only for the non-section symbol types and only after `readelfsym` has already returned, so it does not protect this code path.

### Impact Explanation
Denial of service: a crafted object file distributed inside an otherwise ordinary Go module/package causes any `go build`/`go test` that links it to panic and abort, rather than failing gracefully with a diagnostic error. This is a PUBLIC-track quality/robustness bug under Go's vulnerability policy (parser panic on malicious input), not memory corruption or code execution, since Go's runtime bounds-checks the slice access and converts it into a safe panic instead of memory corruption.

### Likelihood Explanation
Victim workflow is `go build`/`go test` of a module that includes a `.syso` object file (a normal supported mechanism for embedding prebuilt objects) or where cgo output is attacker-influenced. The attacker needs only to publish or get consumed as a dependency a module containing the crafted object — no elevated privileges, no special build environment required.

### Recommendation
Add the same bounds validation in `readelfsym`'s `STT_SECTION` case that is already applied later in `Load()`: validate `elfsym.shndx` (`< elfobj.nsect`) before indexing `elfobj.sect[...]`, returning a descriptive `errorf("malformed elf file: invalid section index ...")` instead of allowing an out-of-range panic.
