### Title
Malicious peer can force permanent storage of arbitrary un-committed attachment content via `insert_instantiated_attachment` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsDownloader::run` inserts every attachment returned by a peer for a `AttachmentRequest` into the `attachments` table via `AtlasDB::insert_instantiated_attachment` unconditionally, without first checking whether `find_all_attachment_instances(&attachment.hash())` returned any rows. Because the client never verifies that the returned content's hash matches the `content_hash` that was actually requested, a malicious peer can respond with arbitrary content and have it permanently persisted with `was_instantiated = 1`, which makes it immune to `evict_k_oldest_uninstantiated_attachments` (that eviction routine only targets `was_instantiated = 0` rows).

### Finding Description
The equality the system is supposed to maintain is: every row in `attachments` with `was_instantiated = 1` corresponds to some `AttachmentInstance.content_hash` confirmed on-chain (i.e., `stored_attachment.hash() == some_confirmed_AttachmentInstance.content_hash`).

Tracing the download path:
1. `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:530-558`) takes the HTTP response from a peer for an `AttachmentRequest`, calls `response.decode_atlas_get_attachment()`, and on success does `self.attachments.insert(response.attachment)` — no comparison against `request.content_hash` at all.
2. `StacksHttpResponse::decode_atlas_get_attachment` (`stackslib/src/net/api/getattachment.rs:159-165`) merely JSON-deserializes whatever bytes the peer sent into a `GetAttachmentResponse { attachment }` — it performs no hash check either.
3. In `AttachmentsDownloader::run`, once the state machine reaches `Done`, for each `attachment in context.attachments.drain()` (`stackslib/src/net/atlas/download.rs:152-169`):
   ```rust
   let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())...;
   network.atlasdb.insert_instantiated_attachment(&attachment)...;
   for attachment_instance in attachments_instances.into_iter() { ... }
   ```
   `insert_instantiated_attachment` is called **regardless of whether `attachments_instances` is empty**. There is no early-continue/guard skipping insertion when no on-chain `AttachmentInstance` matches the attachment's hash.
4. `AtlasDB::insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) executes `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` using `attachment.hash()` (a hash recomputed from the attacker-supplied content) as the key, unconditionally marking it `was_instantiated = 1`.
5. `evict_k_oldest_uninstantiated_attachments` (`stackslib/src/net/atlas/db.rs:538-547`) and `evict_expired_uninstantiated_attachments` (`stackslib/src/net/atlas/db.rs:549-560`) both filter on `was_instantiated = 0`, so any row inserted this way is permanently exempt from eviction.

The only "gate" limiting which attachments get requested is that the batch was built from a `content_hash` referenced by an `AttachmentInstance` from confirmed chain state, and the peer's inventory claimed to have it (`get_prioritized_attachments_requests`, `download.rs:404-478`). But none of this constrains what the peer actually *returns* in the attachment-fetch response — the response content is never checked against the requested `content_hash` before being staged into `context.attachments` and subsequently written to the DB.

### Impact Explanation
Any outbound peer selected via `network.get_outbound_sync_peers()` that a node queries for attachment data can return arbitrary bytes for any legitimate outstanding `AttachmentRequest`. Because there is no hash verification, this arbitrary content is:
- Permanently written to the `attachments` SQLite table.
- Marked `was_instantiated = 1`, exempting it from all existing eviction/cleanup logic (`evict_k_oldest_uninstantiated_attachments`, `evict_expired_uninstantiated_attachments`).

This lets a malicious peer accumulate unbounded, consensus-unrelated attachment storage on any node that syncs attachments from it, since the stored data has no tie-back to any confirmed `AttachmentInstance.content_hash`. This is a case of "serving non-canonical state as canonical" — the node stores and can subsequently serve (via `/v2/attachments/:hash`, see `getattachment.rs`) attachment data that was never committed to by any block, satisfying the High-severity "attachment/BNS mismatch" category. The attack is repeatable per attachment request cycle and requires no privileged role — only that the attacker be one of the node's outbound sync peers serving the Atlas HTTP attachment endpoint.

### Likelihood Explanation
Preconditions: the attacker must be (or become) one of the target node's outbound peers with a reachable data URL, and the target node must have at least one pending, unresolved `AttachmentInstance` (which happens naturally as BNS/attachment instances get registered on-chain) so that a batch/request for some `content_hash` is issued to that peer. No secrets, keys, or privileged roles are required — this is ordinary P2P/HTTP peer behavior reachable by any peer the node happens to sync attachments from. Attacker cost is minimal (run a normal Stacks node/peer and answer attachment requests with junk content); the write happens on every successful (HTTP 200) response, making it fully repeatable.

### Recommendation
In `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:152-169`), verify `attachment.hash()` against the actually-requested `content_hash` (or equivalently only call `insert_instantiated_attachment` when `attachments_instances` is non-empty) before persisting and marking `was_instantiated = 1`. Additionally, `extend_with_attachments` should validate `response.attachment.hash() == request.content_hash` immediately when processing the HTTP response, treating a mismatch as a faulty-peer response (bump `report.bump_failed_requests()` / mark peer faulty) rather than inserting it into `self.attachments`.
