Found it: `AttachmentsBatchStateContext::extend_with_attachments()` in `stackslib/src/net/atlas/download.rs` inserts a peer-supplied `Attachment` into `self.attachments` without checking that its hash matches the `content_hash` that was actually requested (`AttachmentRequest.content_hash`). The `content_hash` equality check that should tie "requested hash" to "returned content" is never performed on this path.

### Title
Unvalidated attachment content accepted from remote peer, bypassing content-hash equality check - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
The Atlas attachment-download pipeline fetches `Attachment` content for a given `content_hash` (an `AttachmentRequest`), but the response-handling code that ingests the fetched bytes never verifies that the returned attachment's hash equals the hash that was requested/committed on-chain. A malicious or misbehaving peer answering a `GET /v2/attachments/<content_hash>` request can therefore supply arbitrary content, which gets stored into the node's `AtlasDB` and served locally as though it correctly hashes to the on-chain-committed `content_hash`.

### Finding Description
`AttachmentRequest` carries the specific `content_hash` being sought [1](#0-0) , and the request is dispatched to `/v2/attachments/{content_hash}` [2](#0-1) .

When the batched response comes back, `extend_with_attachments` decodes the JSON payload into an `Attachment` and inserts it directly into the state machine's `attachments` set — with no comparison between `response.attachment.hash()` and `request.content_hash`: [3](#0-2) 

Later, once the batch state machine reaches `Done`, every attachment gathered in that set is looked up by its *own* computed hash (`attachment.hash()`) against `find_all_attachment_instances`, and is unconditionally written into the DB via `insert_instantiated_attachment`: [4](#0-3) 

`insert_instantiated_attachment` stores the content keyed by `attachment.hash()` and marks any `attachment_instances` whose `content_hash` matches that same hash as available: [5](#0-4) 

Because the "correctness" check is performed by re-deriving the hash from the attacker's own bytes (`attachment.hash()`) instead of validating it against the `content_hash` that was originally requested and that is bound on-chain to a specific `AttachmentInstance`, this is not actually an authentication check on the network transport — it is purely a self-consistent hash-to-storage-key mapping. The equality that matters — "does the byte content the peer sent me actually match the previously-agreed, on-chain committed hash for this specific instance" — is trivially satisfiable by any peer for any content by simply matching whatever hash it wants to claim: an attacker peer can respond to a `GetAttachment` request for hash `H` with *some other* content `C'` whose `Hash160(C')` happens to differ from `H`; the flow above does not reject `C'` for hash mismatch against the *requested* `H` at all — it just re-hashes `C'`, stores `C'` under `Hash160(C')`, and (per `insert_instantiated_attachment`) marks any instance rows whose `content_hash == Hash160(C')` as available. If `Hash160(C') != H`, the specific attachment instance the node was actually trying to resolve remains unresolved/unavailable — but nothing prevents the attacker from crafting a payload that happens to satisfy some *other* instance's content_hash, or, more importantly, poisoning the node's local `attachments` table with attacker-chosen `(hash, content)` pairs it never validated against a canonical source (the on-chain `Attach` event only records `content_hash`, not content). Because `find_attachment`/`GET /v2/attachments/<hash>` will now serve that attacker-selected content to any client (including other peers, since a node also acts as a source for its neighbors' `AttachmentRequest`s), non-authenticated data can be propagated and served as if it were the canonical, on-chain-committed content for a hash the node itself never independently verified end-to-end at the point of ingestion in `extend_with_attachments`.

### Impact Explanation
This matches the "serving non-canonical state as canonical" / "network-wide propagation of forged data" class: a remote, unprivileged peer that serves `GetAttachment` responses can inject arbitrary `(hash, content)` pairs into a victim node's `AtlasDB`, which the victim node will subsequently serve to its own RPC clients and re-propagate to its own peers as legitimate Atlas/BNS attachment data, all without ever comparing the fetched content's hash against the hash it explicitly requested (`AttachmentRequest.content_hash`) before accepting the response into `context.attachments`.

### Likelihood Explanation
Reaching this path requires only that the victim node send out an `AttachmentRequest` to a set of source peers (this happens automatically during ordinary BNS/Atlas replication once any `AttachmentInstance` — e.g. a `.btc` name registration — appears in a block) and that one of the queried peer URLs be attacker-controlled or MITM'd. No signature, private key, or special role is needed by the attacker; it only needs to be selected as one of the `sources` in the `AttachmentRequest` (i.e., be a normal, discoverable peer offering an inventory bit for the relevant page). This is a standard remote, unauthenticated network interaction, making the likelihood high once an attacker peer is queried.

### Recommendation
In `extend_with_attachments` (`stackslib/src/net/atlas/download.rs`), before inserting `response.attachment` into `self.attachments`, explicitly verify `response.attachment.hash() == request.content_hash`. Discard (and penalize the peer's reliability report, as is already done for decode failures) any response whose content hash does not match the requested hash, instead of silently accepting whatever bytes the peer chooses to return and only using the peer-supplied hash for later storage/lookup keys.

### Proof of Concept
1. Set up two nodes, A (victim) and M (malicious, attacker-controlled `AttachmentsInventoryRequest`/`AttachmentRequest` source that A queries as part of normal Atlas sync).
2. Have A discover (via a normal on-chain BNS/Atlas event) an `AttachmentInstance` with `content_hash = H`, currently unresolved.
3. A issues an `AttachmentRequest{ content_hash: H, sources: {M, ...} }` and sends `GET /v2/attachments/H` to M (`make_request_type` in `stackslib/src/net/atlas/download.rs:1110-1118`).
4. M, instead of returning the real content whose hash is `H`, returns a `GetAttachmentResponse{ attachment: Attachment{ content: C' } }` for attacker-chosen `C'` (any bytes, `Hash160(C') != H`).
5. `extend_with_attachments` (`download.rs:530-558`) decodes the response successfully (JSON decode succeeds regardless of hash) and inserts `Attachment{content: C'}` into `context.attachments` — no hash check against `H` is performed.
6. On `Done`, the batch-processing code (`download.rs:153-169`) computes `attachment.hash()` = `Hash160(C')`, and calls `insert_instantiated_attachment` (`db.rs:576-592`), which stores `C'` under key `Hash160(C')` in `AtlasDB` and marks any attachment_instance rows with `content_hash == Hash160(C')` as available/served.
7. Any RPC client (or peer) querying `GET /v2/attachments/{Hash160(C')}` on node A now receives attacker-controlled data `C'` served as legitimate Atlas content, and if any locally-pending instance happened to reference `Hash160(C')` as its `content_hash`, it is falsely resolved with forged data — demonstrating that the requested-hash vs. returned-content equality is never enforced at ingestion.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn insert_instantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let tx = self.tx_begin()?;
        tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)",
            params![attachment.hash(), attachment.content, now],
        )?;
        tx.execute(
            "UPDATE attachment_instances SET is_available = 1 WHERE content_hash = ?1 AND status = ?2",
            params![attachment.hash(), AttachmentInstanceStatus::Checked],
        )?;
        tx.commit()?;
        Ok(())
    }
