### Title
Time-of-check/time-of-use race in the anti-replay window allows duplicate decryption and delivery of a replayed packet - ([File: connection_state.go])

### Summary
The external report describes a class of bug where a security check (`isBorrowAllowed`) is evaluated against pre-mutation state, and the state-mutating operation that follows is not re-validated, allowing an attacker to slip past a guard that should have blocked the action. The nebula analog is the anti-replay counter check/mark sequence in `ConnectionState.Decrypt`, where the "check" (`window.Check`) and the "commit" (`window.Update`) that are supposed to atomically gate acceptance of a message counter are split across two separate lock sections with the expensive `DecryptDanger` operation running unlocked in between.

### Finding Description
`ConnectionState.Decrypt` in `connection_state.go` implements anti-replay protection using a sliding bitmap (`Bits`, in `bits.go`). The correct invariant is: a given `messageCounter` must be atomically checked-and-marked so that only one caller can ever successfully process it.

Instead, the implementation does: [1](#0-0) 

1. Lock, call `cs.window.Check(l, messageCounter)`, unlock.
2. If check passed, call `cs.dKey.DecryptDanger(...)` (AEAD decryption) with no lock held.
3. Lock again, call `cs.window.Update(l, messageCounter)` to actually mark the counter seen, unlock.
4. Only if `Update` returns false is the result discarded.

Between steps 1 and 3 the counter is not yet marked, so two concurrent invocations of `Decrypt` for the same `ConnectionState` with the identical `messageCounter` can both pass `Check` (analogous to `isBorrowAllowed` being evaluated on stale state before the fee/mutation is applied), both successfully perform `DecryptDanger`, and only afterward race for `Update` — but by then the first invocation has already returned decrypted plaintext to its caller. `VerifyRelay` in the same file has the identical Check → decrypt → Update pattern: [2](#0-1) 

Nebula supports multiple listener routines per UDP socket (`routines` config, SO_REUSEPORT-style fan-out), so packets addressed to the same tunnel/hostinfo can legitimately be picked up and processed concurrently on different goroutines, each holding its own stack-local `out`/`nb` buffers but sharing the single `ConnectionState` (and its `Bits` window) for that peer. An attacker who can duplicate a previously observed valid ciphertext on the wire (a classic UDP replay — no CA-signed certificate or key material needed, since the ciphertext itself is being replayed, not forged) can send it in extremely close succession; if the duplicate is delivered to two different listener routines before the first `Update` call commits, both goroutines can independently pass `Check`, and the anti-replay window will "win" only in terms of internal bookkeeping — it does not prevent the decrypted duplicate payload from having already been produced and (in the outer packet-processing path) written out to the TUN device.

This mirrors M-16's root cause precisely: a security gate (`isBorrowAllowed`/`window.Check`) is evaluated against state that is mutated only after the sensitive action (borrow/decrypt) has already been permitted to proceed, instead of atomically gating the check-and-mutate as one operation (as the Sherlock fix recommended: check `isAccountHealthy` after the state mutation, all under one atomic operation).

### Impact Explanation
A successful race allows a captured/duplicated ciphertext packet to be decrypted and delivered twice to the overlay (TUN) device despite the anti-replay window being designed to guarantee exactly-once delivery per message counter. This is a concrete violation of Nebula's replay-protection guarantee (an authenticated but at-most-once delivery guarantee is part of the protocol's security model) and constitutes remote state poisoning of the replay window / duplicate traffic injection, achievable by an on-path or off-path attacker who can duplicate UDP packets without needing to hold a valid Nebula certificate.

### Likelihood Explanation
Exploitability depends on timing: the attacker must get two copies of the same UDP datagram processed by two different listener goroutines within the narrow window between `Check` and `Update` (which spans a full AEAD decrypt operation). This is more feasible on multi-routine (SO_REUSEPORT) configurations, which Nebula explicitly supports and documents (`firewall.conntrack.routine_cache_timeout` guidance implies routines > 1 is a supported deployment). Network-level packet duplication (retransmission by intermediate routers/switches, or an attacker deliberately duplicating captured UDP packets to the destination) is a realistic and easy-to-trigger condition, though winning the exact race window requires some precision, making this a moderate-likelihood but realistic issue rather than a certainty on every attempt.

### Recommendation
Make the check-and-mark atomic: hold `decryptLock` across the full `Check` → `Update` sequence (or better, merge them into a single `Bits.CheckAndUpdate` operation performed once, before invoking `DecryptDanger`, and only revert/no-op if decryption itself fails). This removes the unlocked window during which a duplicate counter can pass the check twice, closing the race in both `Decrypt` and `VerifyRelay`.

### Proof of Concept
1. Establish a tunnel between two nebula nodes running with `routines` > 1 (multiple listener goroutines sharing the same `ConnectionState`).
2. Capture one valid encrypted data packet in flight (e.g. via a MITM tap on the underlay network) — no CA certificate or private key material is required, only the ability to duplicate on-wire UDP datagrams.
3. Send two copies of the captured packet to the target's UDP port at nearly the same time so that the OS/kernel networking stack dispatches them to two different listener routines.
4. Observe that both copies can pass `cs.window.Check` in `connection_state.go:64` before either commits via `cs.window.Update` at `connection_state.go:76`, resulting in the payload being decrypted and forwarded to the TUN device more than once, even though the replay-window design intends at-most-once delivery per `messageCounter`. func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error

	result := cs.window.Check(l, messageCounter)

// VerifyRelay verifies AEAD protected (but not encrypted) relay frames. packet must be length-checked by the caller.
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
}
