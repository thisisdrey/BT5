### Title
`expect()` after `checked_div` in Snowbridge fee calculation can panic on overflow, not just on zero exchange rate - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::<T>::calculate_fee` converts the Ethereum-side fee into local currency with `FixedU128::checked_div`, then immediately calls `.expect("exchange rate is not zero; qed")`. The `expect` message documents only one failure mode (a zero exchange rate), but `checked_div`/`checked_rounding_div` on `FixedU128` returns `None` for two independent reasons: a zero divisor **and** an internal multiplication overflow in `multiply_by_rational_with_rounding`. Because the pricing parameters (`fee_per_gas`, `multiplier`, `exchange_rate`) are governance-settable, and the fee itself is driven by `gas_used_at_most` for arbitrary outbound messages, a legitimate (non-zero) but small `exchange_rate` combined with a large intermediate fee can overflow the division, hit the `None` branch, and panic — even though the divisor is provably non-zero. This mirrors the GoodEntry `priceX8` bug: an unproven assumption ("the scale-down is always sufficient" / "None only means div-by-zero") silently breaks under legitimate, reachable input ranges.

### Finding Description
`calculate_fee` is on the hot path for both `do_process_message` (called for every enqueued Snowbridge outbound message, including governance messages sent through `PRIMARY_GOVERNANCE_CHANNEL`) and `send_message_impl::validate` (called for every user-submitted outbound message, e.g. ERC-20 transfers to Ethereum): [1](#0-0) 

The relevant computation is:
```rust
let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);
let fee = FixedU128::from_inner(fee)
    .saturating_mul(params.multiplier)
    .checked_div(&params.exchange_rate)
    .expect("exchange rate is not zero; qed")
    .into_inner();
``` [2](#0-1) 

`params.validate()` only guarantees `exchange_rate != FixedU128::zero()` — it does not bound `exchange_rate` away from very small values, nor does it bound `multiplier` from above, nor does it bound `fee_per_gas`/`rewards.remote` (all governance-set `U256`/`FixedU128` values consumed through `T::PricingParameters::get()`): [3](#0-2) 

`FixedU128`'s `checked_div` is implemented via `checked_rounding_div`, which returns `None` both when the divisor's inner value is `0` **and** whenever `multiply_by_rational_with_rounding` cannot represent the result (i.e., on overflow of the 128-bit fixed-point representation):
```rust
pub const fn checked_rounding_div(self, other: Self, rounding: SignedRounding) -> Option<Self> {
    if other.0 == 0 { return None; }
    ...
    match multiply_by_rational_with_rounding(lhs.value, Self::DIV as u128, rhs.value, ...) {
        Some(value) => Self::from_i129(...),
        None => None,
    }
}
``` [4](#0-3) 

Because `.saturating_mul(params.multiplier)` already lets the numerator climb toward `FixedU128::MAX` (saturating rather than erroring), and `params.exchange_rate` can legitimately be a very small non-zero rational (e.g. ETH/DOT ratio far below 1), the division `numerator.0 * DIV / exchange_rate.0` can overflow 128 bits and legitimately return `None` even though `exchange_rate != 0`. The subsequent `.expect(...)` then panics with a message that falsely attributes the cause to a zero exchange rate, when the real cause is unhandled overflow — exactly analogous to the external report's `poolMatchesOracle`, where the developer assumed a fixed scale-down was "enough" and didn't account for legitimate value ranges that violate that assumption.

### Impact Explanation
A panic inside `do_process_message` — which is executed by the `MessageQueue` pallet's `ServiceQueues`/`on_initialize` machinery every block while messages are pending — aborts the extrinsic/service-weight execution for that call. Because `calculate_fee` is also invoked from `send_message_impl::validate`, a triggerable panic here can also block or repeatedly fail public dispatch of new outbound Snowbridge messages (ERC-20 transfers, XCM-triggered exports to Ethereum), degrading or stalling bridge message processing/delivery — squarely within the "public underpriced work that degrades block production or stalls bridge processing" and "runtime bugs that compromise intended behavior" impact categories for the Snowbridge/BridgeHub scope.

### Likelihood Explanation
Triggering requires only that the governance-configured `PricingParameters` (specifically a small `exchange_rate` combined with a non-trivial `multiplier` and/or large `fee_per_gas`/reward) fall into the reachable-but-unvalidated overflow region, and then any user (or the system itself, for governance messages) enqueues an outbound message with non-trivial `gas_used_at_most`. No malicious relayer, validator, or privileged actor is required — a normal parameter configuration passing `validate()` (which enforces only non-zero, not bounded magnitude) combined with ordinary message submission is sufficient. The precise numeric threshold that overflows the 128-bit fixed-point representation was not independently reproduced with test tooling in this analysis due to tool/time constraints in this session; it should be confirmed with a concrete unit test before treating this as fully proven versus theoretical.

### Recommendation
Replace `.expect(...)` after `checked_div` with an explicit fallible path (e.g., `defensive_unwrap_or` combined with a safe fallback, or a proper `Result`/error propagation through `calculate_fee`), and validate `PricingParameters` more strictly (bound `exchange_rate` away from values that make `fee/exchange_rate` unrepresentable given the maximum possible fee and multiplier), similar to how `pallet-asset-rate`'s `to_asset_balance` treats `checked_div`'s `None` as a generic `Overflow` error rather than assuming a single root cause: [5](#0-4) 

### Proof of Concept
Conceptual reproduction (not run in this session — recommend adding as a unit test in `bridges/snowbridge/pallets/outbound-queue/src/test.rs` alongside the existing fee tests):
```rust
#[test]
fn calculate_fee_panics_on_overflowing_division() {
    new_tester().execute_with(|| {
        let gas_used: u64 = u64::MAX; // large gas usage
        let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
            // exchange_rate is legitimately non-zero but extremely small
            exchange_rate: FixedU128::from_inner(1),
            fee_per_gas: U256::from(u128::MAX),
            rewards: Rewards { local: 1_u32.into(), remote: U256::from(u128::MAX) },
            multiplier: FixedU128::from_rational(1_000_000, 1),
        };
        // Expected: calculate_fee should not panic; currently it can panic via
        // `.expect("exchange rate is not zero; qed")` when checked_div overflows.
        let _fee = OutboundQueue::calculate_fee(gas_used, price_params);
    });
}
```
This exercises the same class of assumption failure as the GoodEntry `poolMatchesOracle` overflow: a fixed/implicit assumption about "when division can fail" that does not hold for the full legitimate input domain, existing test coverage (`test_calculate_fees_with_multiplier`, etc., at [6](#0-5) ) only exercises benign, small parameter values and does not cover the overflow boundary.
