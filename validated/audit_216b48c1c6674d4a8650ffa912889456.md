### Title
Unauthenticated peer-identity hijack via self-declared handshake address on inbound connections - (File: stackslib/src/net/chat.rs)

### Summary
`validate_handshake` only checks the self-declared `addrbytes`/`port` in a `Handshake` against the actual observed socket address for **outbound** connections; inbound connections skip this check entirely by design. Combined with the fact that `Neighbor::load_and_update` and the resulting `PeerDB` write key off the *self-declared* `handshake_data.addrbytes`/`port` (not the real TCP peer address), a remote attacker can dial an inbound connection, self-sign a handshake with their own key, but claim the identity (`addrbytes`/`port`) of an already-known peer, causing the node to overwrite that peer's stored public key in `PeerDB`.

### Finding Description
Two independent gaps combine to break the equality the question describes:

1. **`validate_handshake`'s per-connection key check is address-blind for inbound connections.** In the `None` branch (no cached key yet for this `ConversationP2P`), only self-consistency of the signature is checked: [1](#0-0) 
In the `Some` branch, the self-declared address is cross-checked against the observed socket address only `if self.stats.outbound`: [2](#0-1) 
For an inbound connection there is no verification anywhere in `validate_handshake` that `handshake_data.addrbytes`/`port` matches the real remote socket address.

2. **The per-connection key cache is seeded from `PeerDB` using the real client socket address, not the self-declared handshake address.** `register_peer` looks up an existing `Neighbor` by the actual TCP `client_addr` and pre-loads its public key into the new `ConversationP2P`: [3](#0-2) 
For an attacker connecting from their own (previously-unseen) IP/ephemeral port, this lookup returns `None`, so the new conversation's cached key is empty — putting `validate_handshake` into the vulnerable self-consistency-only branch regardless of what identity the attacker claims in the handshake payload.

3. **`Neighbor::load_and_update`/`handshake_update` key off the self-declared address and overwrite the stored key unconditionally.** `NeighborKey::from_handshake` is built from `handshake_data` (attacker-controlled), used to fetch the existing `PeerDB` row, and then `handshake_update` unconditionally replaces `self.public_key` with the attacker's key: [4](#0-3) [5](#0-4) 
Downstream persistence (`PeerDB::update_peer`) does not reject a public-key change for an existing `NeighborKey` — it only uses the mismatch as a signal to drop cached StackerDB records, not to refuse the write: [6](#0-5) 

Attacker flow: open a fresh inbound TCP connection to the victim node from an address the victim has never seen before (so `register_peer`'s lookup misses and the per-connection key cache is empty), send a `Handshake` message self-signed with attacker key P2 but with `HandshakeData.addrbytes`/`port` set to the `addrbytes`/`port` of a `NeighborKey` the victim already has on record for a different peer with public key P1. `validate_handshake` accepts it purely on self-consistency (no outbound check applies). The subsequent `Neighbor::load_and_update`/`handshake_update`/save path looks up the existing DB row by the spoofed address and overwrites P1 with P2.

### Impact Explanation
This allows unauthenticated overwrite of another peer's identity record in `PeerDB` — the victim node will now believe the legitimate peer at that `addrbytes:port` uses public key P2 (attacker-controlled). This can be leveraged to disrupt/hijack subsequent authenticated exchanges keyed to that `NeighborKey` (e.g., StackerDB replication trust, since a key change drops and can be re-populated with attacker-served StackerDB contract lists) and to impersonate a known peer's identity toward the victim node, matching the "unauthenticated write to state" Critical category.

### Likelihood Explanation
The attacker only needs to be able to open a TCP connection to the victim's P2P port and knows (or guesses) the `addrbytes`/`port` of a peer already present in the victim's `PeerDB` (frontier addresses are commonly public/gossiped). No secret, credential, or privileged role is required, and it is repeatable against any known peer entry. The only constraint is that the attacker's real connecting address itself must not already be a cached/known peer to the victim (a fresh/unused address), which is trivial to arrange.

### Recommendation
For inbound connections, do not trust `HandshakeData.addrbytes`/`port` for `PeerDB` key lookups/writes; instead bind the `Neighbor`/`NeighborKey` used for persistence to the actually-observed socket address (`self.peer_addrbytes`/`self.peer_port`), or require a subsequent successful outbound-style verification (e.g., a return handshake to the claimed address) before allowing a key change to an already-known `NeighborKey`. Additionally, `handshake_update`/`PeerDB::update_peer` should refuse to silently overwrite an existing peer's public key when the connection direction/order cannot prove the new key belongs to the same physical peer.

### Proof of Concept
1. In a `stackslib::net::chat`/`db` test, populate `PeerDB` with a `Neighbor` at `NeighborKey{addrbytes: A, port: P}` with public key `P1` (as in `test_peer_insert_and_retrieval`, `stackslib/src/net/db.rs:1985`).
2. Create a `ConversationP2P` for an inbound connection from a distinct, previously-unseen `client_addr` (so `register_peer`'s `lookup_peer` returns `None` and `set_public_key(None)` is used, per `stackslib/src/net/p2p.rs:2011-2049`).
3. Craft and send a `Handshake` message self-signed with attacker key `P2`, but with `HandshakeData.addrbytes = A`, `port = P`.
4. Call `ConversationP2P::validate_handshake` and assert it returns `Ok(())` despite `A:P` already being bound to `P1` in `PeerDB`.
5. Drive the handshake through to `Neighbor::load_and_update`/`handshake_update`/`save_update` and assert that `PeerDB::get_peer(conn, network_id, &A, P)` now returns a `Neighbor` with `public_key == P2`, confirming the silent overwrite of `P1`.
