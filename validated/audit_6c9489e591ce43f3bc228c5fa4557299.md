### Title
`AccountLocks::try_lock_transaction_batch` fails to detect write-lock conflicts between transactions within the same batch - ([File: accounts-db/src/account_locks.rs])

### Summary
`try_lock_transaction_batch` validates every transaction's account keys against the lock state as it existed *before* the batch was processed, then unconditionally applies `lock_accounts` for every transaction that passed validation, without re-checking against locks taken by earlier transactions in the same batch. Two (or more) transactions in a single batch that write-lock the same account can both receive `Ok(())`, breaking the fundamental invariant that conflicting transactions never hold overlapping locks.

### Finding Description
`try_lock_transaction_batch` performs two passes over `validated_batch_keys`: [1](#0-0) 

The first pass calls `self.can_lock_accounts(keys)`, which only reads `&self` — it never mutates `write_locks`/`readonly_locks`: [2](#0-1) 

Because nothing is written to `self` during the validation loop, every entry in the batch is checked against the identical, unchanged pre-batch lock state. Consequently, if transaction *i* and transaction *j* (`i != j`) in the same batch both write-lock the same previously-unlocked `Pubkey`, both `can_lock_accounts` calls succeed (each sees the account as free), and both entries remain `Ok`.

The second pass then unconditionally calls `self.lock_accounts(keys)` for every `Ok` entry: [3](#0-2) 

`lock_accounts`/`lock_write` simply increment a reference count and never re-validate for conflicts: [4](#0-3) 

The doc comment explicitly states the intended contract — "Lock accounts for all transactions in a batch which don't conflict with existing locks" — but the implementation only guards against locks *external* to the batch, not conflicts *within* the batch itself. This function is reachable from `Bank::try_lock_accounts_with_results` (used by `prepare_sanitized_batch`/`prepare_sanitized_batch_with_results`), which is the mechanism used to lock a batch of transactions received from clients before execution: [5](#0-4) [6](#0-5) 

An attacker submitting a packet batch containing two (or more) transactions that both write to the same account pubkey, where that account has no pre-existing external locks, can force both transactions to be reported as successfully locked (`Ok(())`) within the same batch, even though they conflict with each other. Since a "locked" `TransactionBatch` is the unit that the bank treats as safe for concurrent/pipelined execution, this breaks the "conflicting transactions never execute concurrently" invariant relied upon throughout the accounts-db locking layer.

### Impact Explanation
This is a violation of the core account-locking invariant that gates concurrent transaction execution. If the resulting `TransactionBatch` is used to drive concurrent account loads/execution/commits, two transactions writing the same account without mutual exclusion can produce data races on account state, non-deterministic execution ordering, or inconsistent commit results — a correctness and potentially consensus-safety issue (a leader could observe/replay divergent results depending on execution timing), which falls under Agave's "invalid recorded block / account-lock correctness" bounty category.

### Likelihood Explanation
The precondition is simple and entirely attacker-controlled: submit a batch (single packet batch to the leader's TPU) containing ≥2 sanitizable transactions that share a common writable account and that pass `validate_account_locks` (no `TooManyAccountLocks`/duplicate-key rejection) and are not otherwise externally locked. No validator, leader, or staked-peer control is required — this is purely a client-supplied transaction-batch composition issue, reachable through the standard leader packet-ingestion path that calls into `Bank::try_lock_accounts_with_results`/`prepare_sanitized_batch`.

### Recommendation
Make the validation pass mutate lock state incrementally (or perform validation and locking together within a single pass), so that a transaction's `can_lock_accounts` check reflects locks already taken by *earlier* transactions in the same batch, e.g.:
```rust
validated_batch_keys.into_iter().map(|available_keys| {
    available_keys.and_then(|keys| {
        self.can_lock_accounts(keys.clone())?;
        self.lock_accounts(keys);
        Ok(())
    })
}).collect()
```
This ensures locks are checked and applied atomically per transaction in iteration order, so a later conflicting transaction in the same batch is correctly rejected with `AccountInUse`.

### Proof of Concept
```rust
// accounts-db/src/account_locks.rs (new test)
#[test]
fn test_try_lock_transaction_batch_intra_batch_write_conflict() {
    let mut account_locks = AccountLocks::default();
    let key = Pubkey::new_unique();

    // Two transactions in the SAME batch both write-lock `key`.
    let tx1_keys = vec![(&key, true)];
    let tx2_keys = vec![(&key, true)];

    let batch: Vec<TransactionResult<_>> = vec![
        Ok(tx1_keys.into_iter()),
        Ok(tx2_keys.into_iter()),
    ];

    let results = account_locks.try_lock_transaction_batch(batch);

    // EXPECTED (per invariant): only one of the two should succeed.
    let ok_count = results.iter().filter(|r| r.is_ok()).count();
    assert_eq!(
        ok_count, 1,
        "two write-conflicting transactions in the same batch both got Ok(()) -- \
         account-lock mutual exclusion invariant violated"
    );
}
```
Running this against the current implementation fails: `ok_count == 2`, demonstrating that both conflicting transactions are simultaneously granted locks within a single `try_lock_transaction_batch` call.

    pub fn try_lock_transaction_batch<'a>(
        &mut self,
        mut validated_batch_keys: Vec<
            TransactionResult<impl Iterator<Item = (&'a Pubkey, bool)> + Clone>,
        >,
    ) -> Vec<TransactionResult<()>> {
        validated_batch_keys.iter_mut().for_each(|validated_keys| {
            if let Ok(keys) = validated_keys.as_ref()
                && let Err(e) = self.can_lock_accounts(keys.clone())
            {
                *validated_keys = Err(e);
            }
        });

        validated_batch_keys
            .into_iter()
            .map(|available_keys| available_keys.map(|keys| self.lock_accounts(keys)))
            .collect()
    }

    fn can_lock_accounts<'a>(
        &self,
        keys: impl Iterator<Item = (&'a Pubkey, bool)>,
    ) -> TransactionResult<()> {
        for (key, writable) in keys {
            if writable {
                if !self.can_write_lock(key) {
                    return Err(TransactionError::AccountInUse);
                }
            } else if !self.can_read_lock(key) {
                return Err(TransactionError::AccountInUse);
            }
        }

        Ok(())
    }

    fn lock_accounts<'a>(&mut self, keys: impl Iterator<Item = (&'a Pubkey, bool)>) {
        for (key, writable) in keys {
            if writable {
                self.lock_write(key);
            } else {
                self.lock_readonly(key);
            }
        }
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_readonly(&self, key: &Pubkey) -> bool {
        self.readonly_locks.get(key).is_some_and(|count| *count > 0)
    }

    #[cfg_attr(feature = "dev-context-only-utils", qualifiers(pub))]
    fn is_locked_write(&self, key: &Pubkey) -> bool {
        self.write_locks.get(key).is_some_and(|count| *count > 0)
    }

    fn can_read_lock(&self, key: &Pubkey) -> bool {
        // If the key is not write-locked, it can be read-locked
        !self.is_locked_write(key)
    }

    fn can_write_lock(&self, key: &Pubkey) -> bool {
        // If the key is not read-locked or write-locked, it can be write-locked
        !self.is_locked_readonly(key) && !self.is_locked_write(key)
    }

    fn lock_readonly(&mut self, key: &Pubkey) {
        *self.readonly_locks.entry(*key).or_default() += 1;
    }

    fn lock_write(&mut self, key: &Pubkey) {
        *self.write_locks.entry(*key).or_default() += 1;
    }

    /// Attempt to take locks on the accounts in a transaction batch, and their cost
    /// limited packing status and duplicate transaction conflict status
    pub fn try_lock_accounts_with_results(
        &self,
        txs: &[impl TransactionWithMeta],
        tx_results: impl Iterator<Item = Result<()>>,
    ) -> Vec<Result<()>> {
        let tx_account_lock_limit = self.get_transaction_account_lock_limit();

        // we must fail transactions that duplicate a prior message hash
        let mut batch_message_hashes = AHashSet::with_capacity(txs.len());
        let tx_results = tx_results
            .enumerate()
            .map(|(i, tx_result)| match tx_result {
                Ok(()) => {
                    // `HashSet::insert()` returns `true` when the value does *not* already exist
                    if batch_message_hashes.insert(txs[i].message_hash()) {
                        Ok(())
                    } else {
                        Err(TransactionError::AlreadyProcessed)
                    }
                }
                Err(e) => Err(e),
            });

        self.rc
            .accounts
            .lock_accounts(txs.iter(), tx_results, tx_account_lock_limit)
    }
