### Title
Floating-point rounding/truncation in Bancor-style exchange formula allows value extraction from TRX exchange pools - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
The zkLend exploit stemmed from mixing an internally tracked, precision-sensitive accumulator (`lending_accumulator`) with integer/rounding shortcuts that could be manipulated over a sequence of flash-loan-funded operations to mint value out of thin air. java-tron's legacy TRC10 Exchange (Bancor-style) module has an analogous root-cause pattern: `ExchangeProcessor` computes the bonding-curve conversion using **double-precision floating point** (`Math.pow`) and then truncates the result to a `long` via a hard cast, rather than using exact integer/BigDecimal arithmetic. [1](#0-0) [2](#0-1) 

### Finding Description
`exchangeToSupply`/`exchangeFromSupply` compute `-supply * (1 - (1 + quant/newBalance)^0.0005)` and `balance * ((1 + supplyQuant/supply)^2000 - 1)` using `double` math, then cast to `long`, truncating toward zero. This is reachable directly from `ExchangeTransactionActuator.execute`/`doValidate`, which is invoked by any account submitting an `ExchangeTransactionContract` — an unprivileged, signed transaction. [3](#0-2) [4](#0-3) 

The codebase itself demonstrates that this legacy path produces materially different (and by implication, less trustworthy) results than a corrected exact-arithmetic implementation: a dedicated `SafeExchangeProcessor` was added that performs the identical bonding-curve math using `BigDecimal` at 18-digit precision, and a "hardened" mode flag (`allowHardenExchangeCalculation`) plus a "strict math" flag (`allowStrictMath`) were introduced specifically to bypass the non-deterministic/double-precision computation. [5](#0-4) [6](#0-5) 

`ExchangeCapsule.transaction` explicitly selects between the two processors, and the choice of processor depends entirely on a dynamic property flag rather than being unconditionally hardened. [7](#0-6)  Test evidence confirms the two paths diverge on real inputs (`Assert.assertNotEquals(anotherTokenQuant, result)` between plain-double and strict-double, and the hardened `BigDecimal` result differs again), proving the un-hardened path's rounding behavior is not exact/deterministic. [8](#0-7) 

This mirrors the zkLend bug class: a market/accumulator value computed via imprecise arithmetic (floating point / non-exact division) that is directly exposed to attacker-controlled inputs (`sellTokenQuant`) on every trade, where truncation direction/magnitude can be steered by carefully chosen quant values across a sequence of trades to skew the exchange rate in the attacker's favor and extract more of the counter-token than economically justified, incrementally draining the pool.

### Impact Explanation
If exploited, an attacker can repeatedly submit `ExchangeTransactionContract` operations with quantities chosen to maximize favorable truncation in `exchangeToSupply`/`exchangeFromSupply`, extracting TRX/TRC10 tokens from the pool in excess of what they deposited. Because pool balances (`firstTokenBalance`/`secondTokenBalance`) are directly debited/credited from these outputs and then propagated to real `AccountCapsule` balances via `addAssetAmountV2`/`setBalance` in `ExchangeTransactionActuator.execute`, this is a real, unbacked-balance/fund-theft impact, not merely a display bug. [9](#0-8) 

### Likelihood Explanation
The vulnerable, floating-point legacy path (`ExchangeProcessor` with `useStrictMath=false`, non-hardened) is the default computation unless the network has activated `allowHardenExchangeCalculation`/`allowStrictMath` via chain governance proposals; any TRC10 exchange pool operating without these proposals active is exposed on every trade to an unprivileged, permissionless `ExchangeTransactionContract`. The presence of dedicated hardening code, feature flags, and precision-mismatch tests in the repository strongly suggests this floating-point rounding issue was already a known internal concern, corroborating that the un-hardened path is realistically exploitable at scale by any external party who can compute favorable trade sizes against a specific pool's current balances (which are all public on-chain state).

### Recommendation
- Make `allowHardenExchangeCalculation` (BigDecimal/exact math) and `allowStrictMath` mandatory/always-on rather than optional flags, removing the legacy `double`-based `ExchangeProcessor` code path entirely from consensus-critical execution.
- Replace all floating point (`Math.pow`, `double`) usage in bonding-curve/accumulator math with exact integer or `BigDecimal` arithmetic with clearly-specified, symmetric rounding (as already done in `SafeExchangeProcessor`), and add invariant checks (e.g., constant-product/constant-supply bounds) after every trade to reject results that violate expected pool economics.
- Audit all other consensus-affecting numeric paths (`RewardViCalService`, `MortgageService`, `DelegationStore` VI accumulator) for similar floating-point (`double`) usage that could introduce nondeterminism or attacker-exploitable rounding drift.

### Proof of Concept
1. Attacker identifies a live TRC10 `Exchange` pool where the network has not enabled `allowHardenExchangeCalculation`/`allowStrictMath` (default state).
2. Attacker reads current `firstTokenBalance`/`secondTokenBalance` from the public `ExchangeCapsule` state.
3. Attacker computes, off-chain, a `sellTokenQuant` value for which `exchangeToSupply`/`exchangeFromSupply`'s `double` → `long` truncation yields an output more favorable than the exact BigDecimal result (verifiable by comparing against `SafeExchangeProcessor.INSTANCE.exchange(...)`, exactly as the existing `ExchangeProcessorTest.testStrictMath` test does to show divergence). [8](#0-7) 
4. Attacker broadcasts repeated `ExchangeTransactionContract` transactions with such quantities via `ExchangeTransactionActuator`, each one converting the rounding bias into extra tokens credited to their account. [10](#0-9) 
5. Repeating over many transactions drains value from the pool disproportionate to tokens deposited, analogous to zkLend's accumulator-manipulation drain.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override

    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
