### Title
Permanent lock of Kamino reward tokens via balance-delta sweep in `kamino_harvest_reward` - (File: `programs/marginfi/src/instructions/kamino/harvest_reward.rs`)

### Summary
`kamino_harvest_reward` computes the amount to sweep to the destination as `post_transfer_balance - pre_transfer_balance` on the PDA-owned `user_reward_ata`, exactly the anti-pattern flagged in the referenced Compound report (`TreasuryAction.claimCOMPAndTransfer`). Because `user_reward_ata` is a normal SPL token account owned by the bank's `liquidity_vault_authority` PDA, and the instruction itself is completely permissionless (no signer/authority check in the `KaminoHarvestReward` accounts struct), any unprivileged actor can inflate the account's balance ahead of a harvest (via a plain SPL `transfer` "donation", or simply because a prior harvest left dust) so that only the incremental delta gets swept out. Any pre-existing balance in `user_reward_ata` is permanently excluded from the transfer and becomes stuck, since this is the only instruction capable of moving tokens out of that PDA-owned account.

### Finding Description
`kamino_harvest_reward` in [1](#0-0)  snapshots the reward ATA balance before and after the Kamino Farms `harvest_reward` CPI, and only transfers the difference:

```
let pre_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
ctx.accounts.cpi_harvest_rewards(reward_index)?;
let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
let received = post_transfer_balance - pre_transfer_balance;
ctx.accounts.cpi_transfer_obligation_owner_to_destination(received)?;
```

`user_reward_ata` is declared as an `UncheckedAccount` with only a `mut` constraint and no `address =` derivation check tying it to the canonical ATA of `liquidity_vault_authority`/`reward_mint`; regardless, it is a normal SPL token account owned by the bank's `liquidity_vault_authority` PDA [2](#0-1) . Any wallet can submit a standard SPL `transfer` instruction crediting arbitrary amounts of the reward token directly into this account — SPL transfers require the *source* owner to sign, not the destination — inflating `pre_transfer_balance` for the next harvest call.

Critically, the `KaminoHarvestReward` accounts struct has **no signer/authority requirement at all** [3](#0-2) , so this instruction is fully permissionless — any unprivileged user can trigger it, and the only value that ever leaves the PDA-controlled ATA is `received = post - pre`, never the account's full balance.

Compare with the sibling instruction `drift_claim_bad_debt`, which correctly sweeps the account's **entire** balance instead of a delta: `let amount = accessor::amount(&self.claimant_token_account.to_account_info())?; ... token::transfer(cpi_ctx, amount)?;` [4](#0-3) . That pattern is precisely the mitigation recommended in the external report ("Don't use pre-and post-balances, [...] use the entire balance"), confirming `kamino_harvest_reward` still contains the vulnerable pattern the report warns against.

### Impact Explanation
Any tokens present in `user_reward_ata` beyond the exact delta harvested in a single call become permanently unreachable by the protocol: `cpi_transfer_obligation_owner_to_destination` only ever moves `received`, and `liquidity_vault_authority` is a program PDA — no other instruction can sign for it to move funds out of that specific ATA. This is a permanent lock/freeze of protocol reward funds (global fee wallet's expected Kamino reward revenue), reachable by any unprivileged user (matching the "permanent lock/freeze" acceptance criterion). As in the original report, there is no direct profit for the attacker, but it is a griefing/DoS vector against protocol fee revenue that would require a program upgrade or an out-of-band account-closure/migration to recover, exactly mirroring the disputed-but-accepted High/Medium severity of the analog.

### Likelihood Explanation
Likelihood is high for the "griefing" trigger (a simple, cheap SPL `transfer` to a publicly known token account address, no privileged access needed) and it is essentially certain to occur eventually through benign means as well: multiple bank reward calls, partial failures, or leftover dust from previous harvests will accumulate un-sweepable balances in `user_reward_ata` over time, since the delta computation resets `pre_transfer_balance` on every call to whatever is currently sitting there.

### Recommendation
Do not rely on the pre/post balance delta to decide how much to sweep. Instead, after the Kamino `harvest_reward` CPI, read the account's current full balance and transfer that entire amount (as `drift_claim_bad_debt` already does), so any pre-existing/donated balance is never stranded:
```
ctx.accounts.cpi_harvest_rewards(reward_index)?;
let amount = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
ctx.accounts.cpi_transfer_obligation_owner_to_destination(amount)?;
```
Also consider adding an `address =` constraint deriving `user_reward_ata` as the canonical ATA of `(liquidity_vault_authority, reward_mint)` to remove ambiguity about which account is being swept.

### Proof of Concept
1. Determine the canonical `user_reward_ata` address for a given Kamino-wrapped bank's `liquidity_vault_authority` and reward mint (this is a plain SPL ATA, publicly derivable/known).
2. Attacker (or anyone) submits an ordinary SPL `transfer`/`transferChecked` instruction, sending `X` reward tokens from any wallet into `user_reward_ata`. No signature from `liquidity_vault_authority` is required since it is the destination, not the source.
3. Anyone (permissionless) later calls `kamino_harvest_reward`. `pre_transfer_balance` now includes the donated `X`. After the Kamino CPI harvests `Y` new rewards, `post_transfer_balance = X + Y`, so `received = post - pre = Y`.
4. Only `Y` is transferred to `destination_token_account` (the global fee wallet's ATA); `X` remains permanently in `user_reward_ata`, which no other instruction can move since it is owned by the program PDA `liquidity_vault_authority` and only `cpi_transfer_obligation_owner_to_destination` can sign for outbound transfers from it, and that function only ever moves the freshly-computed delta on each future call.

pub fn kamino_harvest_reward(
    ctx: Context<KaminoHarvestReward>,
    reward_index: u64,
) -> MarginfiResult {
    let pre_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    ctx.accounts.cpi_harvest_rewards(reward_index)?;
    let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    let received = post_transfer_balance - pre_transfer_balance;
    ctx.accounts
        .cpi_transfer_obligation_owner_to_destination(received)?;
    Ok(())
}

    fn cpi_transfer_to_destination(&self) -> MarginfiResult<u64> {
        let amount = accessor::amount(&self.claimant_token_account.to_account_info())?;
        if amount == 0 {
            return Ok(0);
        }

        let accounts = Transfer {
            from: self.claimant_token_account.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
        };
        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(self.token_program.key(), accounts, signer_seeds);

        token::transfer(cpi_ctx, amount)?;
        Ok(amount)
    }
