### Title
Post-load contract-loading fee charge lets attacker trigger free-of-charge compile/link/instantiate CPU work before `GasExceeded` is raised - (`runtime/near-vm-runner/src/logic/gas_counter.rs`, `runtime/near-vm-runner/src/wasmtime_runner/mod.rs`)

### Summary
On mainnet (`fix_contract_loading_cost=false`, PV<129), `WasmtimeVM::with_compiled_and_loaded` performs cache lookup/compile, `Module::deserialize`, `Linker::link`, and `instantiate_pre` for a contract *before* the loading-fee gas check runs, because `before_loading_executable` is a no-op when the flag is unset and the fee is only charged afterwards, in `after_loading_executable`. An attacker can deploy a maximal-size wasm contract and call it with prepaid gas set just above the minimal per-action/byte fees but below `contract_loading_base + contract_loading_bytes * len`, so the expensive compile+link+instantiate work is fully performed and only then rejected with `GasExceeded`, while the attacker is only charged the tiny pre-loading gas amount.

### Finding Description
The loading-fee ordering is explicit in code:
- `add_contract_loading_fee` computes `contract_loading_base + contract_loading_bytes * code_len` [1](#0-0) .
- `before_loading_executable` only charges this fee `if config.fix_contract_loading_cost` [2](#0-1) .
- `after_loading_executable` charges the same fee only `if !config.fix_contract_loading_cost` (the legacy/mainnet path) [3](#0-2) .
- In `WasmtimeVM::with_compiled_and_loaded`, the cache-miss closure performs `compile_and_cache`, `Module::deserialize`, builds the `Linker`, calls `link`, and `linker.instantiate_pre(&module)` — all real CPU work — and only afterwards does the code call `gas_counter.before_loading_executable` (a no-op on mainnet) and then, on the `Ok(res)` branch, `gas_counter.after_loading_executable`, which is where the fee is actually deducted and `GasExceeded` can first be raised [4](#0-3) .

Because `fix_contract_loading_cost` activates only at nightly PV 129 and mainnet is below that version, the heavy compile/deserialize/link/instantiate_pre work is unconditionally performed regardless of whether the attached gas can ever cover it; the fee check only decides whether the *outcome* is an abort, not whether the *work* happens. This is corroborated by the component spec, which states explicitly: "On 2.13.0 mainnet `fix_contract_loading_cost` is `false` ... so the loading fee is charged post-load" (protocol-model/spec/contract-vm.md, §3/§Protocol-version-gated behavior).

Attacker path: an unprivileged account (1) deploys a near-`max_contract_size` wasm contract via `DeployContractAction` (paying only the one-time deploy/storage-staking cost), then (2) submits a `FunctionCall` action with `prepaid_gas` set to just above `function_call_base` + per-byte input costs (the costs charged for dispatching/creating the receipt) but below `contract_loading_base + contract_loading_bytes * code_len`. No existing check enforces a minimum prepaid gas tied to contract size before dispatch — action validation and the transaction verifier check balance/gas-price affordability of the *attached* prepaid gas, not that the attached gas is sufficient to cover the loading fee of the target contract. The gas ultimately burnt and paid for is only the tiny pre-loading amount; the compile (on first call)/deserialize+link+instantiate_pre (on every call) CPU cost has already been paid by the node, uncharged.

### Impact Explanation
This is a resource-hygiene / underpriced-computation issue: an attacker can force validators/chunk producers to perform full WASM decode+link+instantiate work for near-maximum-size contracts while paying only minimal gas, since the fee that is supposed to price this exact work is charged after the work is already done and can be dodged by choosing gas just below the fee threshold. Repeated across many receipts/transactions this inflates real block-apply wall-clock time relative to the gas actually burnt, which is the scoped "near-free execution / block-apply time blowup" impact called out in the question. It does not directly cause fund theft, double-spend, or state-root divergence by itself, but violates the metering-totality invariant that every unit of compiled/loaded work must be charged before it is performed.

### Likelihood Explanation
Preconditions are trivial and fully within reach of an unprivileged account: fund an account, deploy a wasm contract near `max_contract_size` (`DeployContractAction`), and submit a `FunctionCall` with a hand-picked `prepaid_gas` value between the dispatch-cost floor and the loading-fee cost. This requires no special permissions, no validator/node access, and is fully repeatable per call (each call re-triggers deserialize+link+instantiate_pre even when the compiled artifact is cache-hit, per `with_compiled_and_loaded`). The only cost to the attacker is the (small) gas actually burnt before `GasExceeded`, i.e., roughly the fixed dispatch/base fees, not the loading fee — making the attack cheap and repeatable. This is a known, already-tracked pre-fix limitation (the very reason the `FixContractLoadingCost` nightly feature at PV 129 exists), not a hypothetical new gap.

### Recommendation
Charge (or reserve) the contract-loading fee before performing compile/deserialize/link/instantiate work on all currently-supported protocol versions, not only once `fix_contract_loading_cost` activates — i.e., accelerate/backport the `before_loading_executable` pre-charge ordering (as already implemented for PV≥129) to stable mainnet versions, or otherwise gate the expensive `Module::deserialize`/`link`/`instantiate_pre` steps behind an upfront gas-sufficiency check derived from `contract_loading_base + contract_loading_bytes * wasm_bytes` before doing any of that work.

### Proof of Concept
Integration test plan (extending the existing `runtime/near-vm-runner/src/tests/runtime_errors.rs::fix_contract_loading_cost_protocol_upgrade` module pattern):
1. Build a contract near `max_contract_size` (e.g. via `near_test_contracts::LargeContract` with many functions/locals to maximize compile/link/instantiate cost).
2. On the pre-fix protocol version (mainnet PV, `fix_contract_loading_cost=false`), compute `loading_fee = contract_loading_base + contract_loading_bytes * wasm_len` from `ExtCostsConfig`.
3. Run the contract with `prepaid_gas` set to `dispatch_base_cost + 1` (just above the minimal action/byte cost, guaranteed to be `< loading_fee`).
4. Assert the outcome aborts with `HostError::GasExceeded` and `outcome.burnt_gas` / `outcome.used_gas` is far less than `loading_fee`.
5. Wrap the run with wall-clock instrumentation (e.g. `std::time::Instant`) around `with_compiled_and_loaded`/`instantiate_pre`, and assert that real elapsed CPU time is comparable to a successful run of the same contract with sufficient gas — demonstrating that the full compile/link/instantiate cost was paid in CPU but not in gas, contrary to the estimator's linear per-byte model (`runtime/runtime-params-estimator/src/lib.rs::contract_loading_base_per_byte`).

    pub(crate) fn before_loading_executable(
        &mut self,
        config: &near_parameters::vm::Config,
        method_name: &str,
        wasm_code_bytes: u64,
    ) -> std::result::Result<(), super::errors::FunctionCallError> {
        if method_name.is_empty() {
            let error = super::errors::FunctionCallError::MethodResolveError(
                super::errors::MethodResolveError::MethodEmptyName,
            );
            return Err(error);
        }
        if config.fix_contract_loading_cost {
            if self.add_contract_loading_fee(wasm_code_bytes).is_err() {
                let error =
                    super::errors::FunctionCallError::HostError(super::HostError::GasExceeded);
                return Err(error);
            }
        }
        Ok(())
    }
