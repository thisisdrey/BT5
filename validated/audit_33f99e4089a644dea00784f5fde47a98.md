### Title
Access-key nonce reset on `AddKey` after `DeleteKey` allows replay of stale signed transactions — ([File: runtime/runtime/src/access_keys.rs])

### Summary
When an access key is re-created for a public key that previously existed on the same account (`DeleteKey` followed by `AddKey`), `add_regular_key` unconditionally re-seeds the key's nonce from the current block height instead of continuing from the nonce the key had reached in its prior "incarnation." This mirrors the FlywheelV2 bug class: a per-entity counter (`storedCycle` / access-key `nonce`) that is not kept in sync with the account's true progress once the entity is removed and reinstated, letting stale state (queued rewards / previously-invalidated signed transactions) become valid again.

### Finding Description
`AccessKey.nonce` is the sole replay-protection counter for a given `(account_id, public_key)` pair, and `verify_nonce` only requires `tx_nonce > current_nonce` (Monotonic mode) or `== current_nonce + 1` (Strict mode): [1](#0-0) 

The `AccessKey` struct's own doc comment states the required invariant explicitly: if a key is recreated reusing the same public key, its nonce must equal the old key's nonce, "to avoid replaying old transactions again": [2](#0-1) 

However, `action_add_key`/`add_regular_key` does not enforce or even attempt this. `action_delete_key` fully removes the access key (and thus its nonce) from the trie with no memory of the value it reached: [3](#0-2) 

`action_add_key` only rejects an `AddKey` if a key for that public key currently exists (`AddKeyAlreadyExists`); once deleted, adding the same public key back is treated as brand new: [4](#0-3) 

`add_regular_key` then **ignores** any nonce value the caller specifies and always overwrites it with `initial_nonce_value(block_height)`: [5](#0-4) 

```rust
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
``` [6](#0-5) 

Because `verify_nonce`'s upper bound allows a transaction's nonce to be set anywhere up to `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER - 1`, an account can push its key's nonce arbitrarily close to that ceiling with a single transaction (e.g. `NonceTooLarge` is only triggered at `>= upper_bound`): [7](#0-6) 

If the account then deletes and re-adds the same public key (two actions, even within the same transaction/receipt or in the very next block), the reseeded floor `(block_height-1) * 1_000_000` can be **lower** than the nonce the key had already reached, because the previous nonce could be as high as `block_height * 1_000_000 - 1` at the same block height. This produces exactly the same class of bug as the FlywheelV2 issue: the new incarnation's counter (`nonce`, analogous to `storedCycle`) is decoupled from the true, previously-reached progress (analogous to `gaugeCycle`), and the consistency check (`tx_nonce > current_nonce`) is evaluated against the wrong, stale baseline — allowing a previously-signed-but-not-yet-submitted (or intentionally withheld) transaction with a nonce below the old high-water mark but above the new floor to become valid and replayable.

### Impact Explanation
This breaks the core "nonce monotonicity prevents replay" invariant documented as authoritative for this component: [8](#0-7) . A previously withheld or "invalidated" signed transaction (e.g., a payment/transfer, a `FunctionCall`, or a `Stake` action) that the signer believed to be permanently stale because the account's nonce had since advanced past it, can be revived and executed by anyone holding a copy of that old signed transaction, once the signer's access key is deleted and re-added. This is a double-spend/replay class impact: unauthorized re-execution of an action the signer no longer intends to authorize, potentially moving funds or otherwise re-triggering a stale but validly-signed action.

### Likelihood Explanation
Exploitation requires only unprivileged, ordinary account operations: (1) issue a transaction that jumps the key's nonce close to the block-height ceiling, (2) `DeleteKey` + `AddKey` for the same public key. No special privileges, validator status, or protocol feature gating are required — `add_regular_key`'s nonce-reseeding logic runs unconditionally for every regular `AddKey`. The main constraint is that an old, still-signed transaction with a nonce inside the "resurrection window" must exist and be resubmittable by someone (the original signer or anyone who received/observed that signed transaction, e.g. a previously-shared but withheld payment authorization).

### Recommendation
When adding an access key whose public key previously existed on the account, ensure the newly assigned nonce is never less than the maximum nonce ever observed for that `(account_id, public_key)` pair — e.g., persist a per-account "highest nonce ever issued" high-water mark independent of key deletion, or require/validate that `AddKeyAction`-supplied nonces (for recreated keys) are at least the old key's last nonce, consistent with the invariant already documented in `AccessKey`'s doc comment (`docs/DataStructures/AccessKey.md`). Alternatively, forbid recreating a previously-deleted public key at all for some cooldown, or bind replay protection to something that is never reset by delete/re-add cycles.

### Proof of Concept
1. Alice signs `TxOld`: a `Transfer` action to `Bob`, using her `FullAccess` key with nonce `N0` (not yet submitted; she keeps this transaction as a private backup/escrow rather than broadcasting it).
2. At block height `H`, Alice submits a transaction using the same access key with `tx_nonce = H*1_000_000 - 1` (just under the upper bound enforced in `verify_nonce`, `runtime/runtime/src/verifier.rs:229-235`), advancing `current_nonce` far past `N0`. `TxOld` is now permanently stale under standard reasoning.
3. In the same or next block, Alice submits a transaction with two actions: `DeleteKey` (removes the key and its nonce state, `access_keys.rs:52-91`) followed by `AddKey` for the *same* public key (`action_add_key`, `access_keys.rs:149-192`, `add_regular_key`, `access_keys.rs:230-255`). The new key's nonce is reseeded to `(H-1)*1_000_000` (or `H*1_000_000` on the next block), which is lower than `H*1_000_000 - 1` reached in step 2.
4. Whoever holds `TxOld` (nonce `N0`, which is below the new floor) — Alice herself, or anyone she had shared it with — submits `TxOld`. `verify_nonce` accepts it because `tx_nonce (N0) > current_nonce (new low floor)` if `N0` falls between the new floor and the old high-water mark, executing the previously-stale `Transfer` action against Alice's wishes.

fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }

pub(crate) fn action_delete_key(

    account: &mut Account,

) -> Result<(), RuntimeError> {
    let access_key = get_access_key(state_update, account_id, &delete_key.public_key)?;
    if let Some(access_key) = access_key {

                account,
                result,

                account_id,

            public_key: delete_key.public_key.clone().into(),
            account_id: account_id.clone(),

    }
    Ok(())
}

pub(crate) fn action_add_key(
    apply_state: &ApplyState,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;
    } else {
        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
