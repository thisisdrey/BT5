### Title
Unbounded per-Pubkey `UsageQueueLoaderInner` growth in the unified scheduler enables cheap memory-inflation DoS - ([File: unified-scheduler-pool/src/lib.rs])

### Summary
The unified transaction scheduler's `UsageQueueLoaderInner` maintains a `DashMap<Pubkey, UsageQueue>` that grows by one entry for every distinct account key touched by scheduled transactions, and entries are never individually evicted — the map is only reset wholesale when the whole scheduler is torn down as "overgrown." An unprivileged user can cheaply reference many distinct (even non-existent) account pubkeys across ordinary transactions to drive this map toward its cap every slot, similarly to how the Carousel `rolloverQueue` in the referenced report grows unbounded from cheap attacker-controlled entries that are never individually cleaned up, forcing full, repeated, costly processing.

### Finding Description
`UsageQueueLoaderInner::load` lazily inserts a new `UsageQueue` for every previously-unseen `Pubkey` and never removes individual entries: [1](#0-0) 

The type's own doc comment acknowledges this design: "Currently, the simplest implementation. This grows memory usage in unbounded way. Overgrown instance destruction is managed via `solScCleaner`." [2](#0-1) 

The only mitigation is a coarse, whole-scheduler-level check: `is_overgrown` compares the *total* entry count against `max_usage_queue_count` (default `262_144`), and if exceeded the *entire* `PooledSchedulerInner` (including its `ThreadManager`, worker threads, and all `UsageQueue`s for legitimate accounts) is marked "trashed" and destroyed by the `solScCleaner` thread: [3](#0-2) [4](#0-3) 

This mirrors the M-5 pattern exactly: a shared data structure (`rolloverQueue` there, `usage_queues` DashMap here) grows from cheap, attacker-supplied entries with no individual pruning path; the only remedy is an expensive, all-or-nothing reset that punishes legitimate work sharing the structure (destroying the whole live scheduler, not just attacker-inserted entries).

Growing this map is cheap for an attacker: any sanitized transaction can list up to `MAX_TX_ACCOUNT_LOCKS` account keys as read-only, and those keys do not need to correspond to existing accounts — `AccountLocks`/`ThreadAwareAccountLocks` only require the keys be syntactically valid and non-duplicated within a transaction: [5](#0-4) 

Each such key that reaches the unified scheduler triggers `UsageQueueLoader::load(pubkey)` and inserts a fresh entry, permanently inflating `count()` for the life of that scheduler instance: [6](#0-5) 

### Impact Explanation
Because the map is only reset by fully trashing the scheduler (with the comment explicitly noting the limit "is enforced at every slot" and the loader "is recreated without any entries at first"), an attacker who cheaply floods unique pubkeys can repeatedly force schedulers into the `is_overgrown`/trashed state: [7](#0-6) 

This causes:
- Repeated destruction/respawn of the block-production/verification scheduler and its worker thread pool (`ThreadManager`), which is a heavyweight operation as documented in the surrounding scheduler-lifecycle comments about "retired" schedulers. [8](#0-7) 
- Memory consumption approaching the documented worst case of ~512 MiB per scheduler instance (and 1.0–1.5 GiB across pooled instances) purely from attacker-chosen, non-existent pubkeys, before any legitimate scheduling work benefits.
- Legitimate in-flight transactions' `UsageQueue`s being discarded/rebuilt along with the trashed scheduler, degrading throughput for unrelated users — an analog of the "relayer unwilling to process the queue" DoS from the referenced report, here manifesting as repeated leader-side scheduler churn/latency rather than a fee incentive failure.

### Likelihood Explanation
Likelihood is bounded by the `DEFAULT_MAX_USAGE_QUEUE_COUNT = 262_144` threshold and the fact that the loader resets on each scheduler respawn, so this is a resource-inflation/thrash vector rather than truly unbounded memory growth or a crash. Reaching the threshold requires an attacker to get on the order of a quarter-million *distinct* account keys processed by a single scheduler instance within its lifetime — achievable via ordinary fee-paying transactions with maximal read-only account lists, but rate-limited by normal transaction throughput, per-transaction fees, and the `TOTAL_BUFFERED_PACKETS`/channel capacities in banking stage. This is a real but comparatively low-severity resource-exhaustion/performance-degradation concern rather than a crash or consensus-safety bug, and the code's own comments show the authors were aware of and accepted this design tradeoff (comparable to the sponsor's "acknowledged" status in the referenced report).

### Recommendation
Consider bounding `UsageQueueLoaderInner` growth incrementally rather than only via whole-scheduler destruction: e.g., evict entries whose `UsageQueue` is currently unused (`Usage::Unused`) using a bounded LRU/generational scheme, or track per-slot/per-block usage-queue reference counts so idle entries referencing never-again-used pubkeys can be pruned without discarding the entire scheduler and its legitimate in-flight work. Alternatively, tighten `DEFAULT_MAX_USAGE_QUEUE_COUNT` growth to scale with recent unique-account load and add rate limiting on distinct-pubkey referencing per fee-payer to raise the cost of driving toward the cap.

### Proof of Concept
1. An attacker crafts and sends many sanitized transactions, each referencing up to `MAX_TX_ACCOUNT_LOCKS` distinct, previously-unused (and possibly non-existent) pubkeys as read-only accounts — this passes `validate_account_locks` since it only checks length and duplicates within the same transaction: [9](#0-8) 
2. Each unique pubkey reaching the unified scheduler calls `UsageQueueLoader::load`, inserting a new entry into `usage_queues` via `or_insert_with`: [10](#0-9) 
3. As the attacker continues supplying fresh pubkeys across many transactions/blocks within one scheduler's lifetime, `count()` climbs toward `max_usage_queue_count`, at which point `is_overgrown()` returns true and the scheduler is trashed and rebuilt by `solScCleaner`, discarding legitimate concurrent scheduling state: [3](#0-2) 
This is directly analogous to the `test_scheduler_drop_overgrown` unit test, which demonstrates the trashing behavior by loading `REDUCED_MAX_USAGE_QUEUE_COUNT + 1` unique pubkeys: [11](#0-10)
