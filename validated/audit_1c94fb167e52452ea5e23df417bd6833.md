### Title
Spending-key material for shielded (Sapling) transactions transmitted via cleartext GET query parameters, exposed to webserver/proxy access-log capture - ([File: framework/src/main/java/org/tron/core/services/http/GetExpandedSpendingKeyServlet.java])

### Summary
Several `wallet` HTTP servlets that operate on Sapling shielded-transaction secret key material accept those secrets as plain URL query parameters on `GET` requests. This is the direct analog of the Pterodactyl bug class (CWE-313): sensitive credential material is placed into the query string, where it is routinely written to plaintext access logs by webservers/reverse proxies sitting in front of the node (nginx, load balancers, CDNs) as well as being retained in browser history, shell history, and referrer headers.

### Finding Description
`GetExpandedSpendingKeyServlet.doGet` reads the raw spending key from the `value` query parameter and passes it straight into `wallet.getExpandedSpendingKey`, which derives the full expanded spending key (`ask`, `nsk`, `ovk`) — the master secret for a shielded Sapling address: [1](#0-0) 

The same pattern of secret material accepted through `request.getParameter(...)` on `doGet` exists in several sibling servlets exposed under `/wallet/*`:
- `GetNkFromNskServlet.doGet` takes the nullifier spending key `nsk` via the `value` parameter [2](#0-1) 
- `GetIncomingViewingKeyServlet.doGet` takes `ak`/`nk` viewing-key components via query parameters [3](#0-2) 
- `ScanNoteByOvkServlet.doGet` and `ScanShieldedTRC20NotesByOvkServlet.doGet` take the outgoing viewing key `ovk` via query parameters [4](#0-3) [5](#0-4) 
- `GetZenPaymentAddressServlet.doGet` takes `ivk`/`d` via query parameters [6](#0-5) 

All of these servlets are registered as `GET`-capable endpoints under `/wallet/...` in `FullNodeHttpApiService`, and the java-tron documentation officially recommends deploying the full node HTTP API behind reverse proxies such as nginx, which by default log full request URLs (including query strings) in plaintext access logs. Unlike the framework's own `HttpInterceptor`/`HttpApiAccessFilter`, which only record metrics and endpoint paths (not query values) [7](#0-6) , any intermediary component fronting the node (nginx, a load balancer, an API gateway, a monitoring proxy) will capture these secrets verbatim, exactly mirroring the Pterodactyl scenario where a `DELETE` password query parameter ended up in nginx's `access.log`.

### Impact Explanation
The expanded spending key (`ask`, `nsk`, `ovk`) derived by `GetExpandedSpendingKeyServlet` and the raw spending/viewing key components handled by the sibling servlets are the cryptographic secrets that fully control a Sapling shielded account: knowledge of `ask`/`nsk` (spend authority) permits spending shielded funds, and `ivk`/`ovk` permit decrypting all incoming/outgoing shielded transaction details. If these values transit through any HTTP GET query string, any log aggregator, proxy operator, or party with read access to webserver logs (a much more commonly exposed dataset than backend server logs) gains outright key-disclosure capability, enabling theft of shielded TRX/TRC20 balances or, at minimum, a complete privacy break (viewing key disclosure lets an outsider trace/decrypt the victim's shielded transaction history).

### Likelihood Explanation
Any unauthenticated client that already interacts with the wallet HTTP API (wallets, exchanges, or dApp backends that call `getexpandedspendingkey`, `getnkfromnsk`, `getincomingviewingkey`, `scannotebyovk`, etc. via `GET`) will trigger this exposure automatically, with no attacker action required beyond passive log access — this matches the "no direct vulnerability in the software itself but a foreseeable and historically demonstrated consequence" reasoning used in the original advisory. Because full-node operators are explicitly documented to place these APIs behind reverse proxies, and default nginx/Apache configurations log full request lines, the exposure is realistic and has previously been the basis of a real, patched CVE in another product using the same architecture (backend behind a logging reverse proxy).

### Recommendation
- Remove or deprecate the `doGet` handlers for all shielded-key servlets (`GetExpandedSpendingKeyServlet`, `GetNkFromNskServlet`, `GetIncomingViewingKeyServlet`, `GetZenPaymentAddressServlet`, `ScanNoteByOvkServlet`, `ScanShieldedTRC20NotesByOvkServlet`), requiring clients to use the existing `doPost` JSON-body variants instead.
- If `GET` support must be retained for backward compatibility, document loudly that operators must disable query-string logging for these specific `/wallet/*` paths at the reverse-proxy layer, and consider emitting a deprecation warning in the API response.
- Add automated tests asserting that these sensitive-parameter endpoints reject `GET` requests (400/404) to prevent regression.

### Proof of Concept
1. Deploy a FullNode with the HTTP API behind nginx using a standard access-log format (`$request` including query string), consistent with the deployment pattern documented for java-tron.
2. Client (or dApp backend) issues:
   `GET /wallet/getexpandedspendingkey?value=<32-byte-hex-spending-key>`
   handled by `GetExpandedSpendingKeyServlet.doGet` [1](#0-0) .
3. nginx records the full URL, including `value=<spending-key>`, in `/var/log/nginx/access.log` in plaintext.
4. Anyone with read access to that log (log aggregation pipeline, misconfigured log bucket, compromised monitoring host) recovers the raw shielded spending key and can derive `ask`/`nsk`/`ovk`, enabling spending of the victim's shielded funds or full decryption of their shielded transaction history.

  @Override
  public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) {
    String endpoint = MetricLabels.UNDEFINED;
    try {
      if (!(request instanceof HttpServletRequest)) {
        chain.doFilter(request, response);
        return;
      }
      String contextPath = ((HttpServletRequest) request).getContextPath();
      endpoint = contextPath + ((HttpServletRequest) request).getServletPath();
      CharResponseWrapper responseWrapper = new CharResponseWrapper(
              (HttpServletResponse) response);
      chain.doFilter(request, responseWrapper);
      HttpServletResponse resp = (HttpServletResponse) response;
      int size = responseWrapper.getByteSize();
      MetricsUtil.meterMark(MetricsKey.NET_API_OUT_TRAFFIC, size);
      MetricsUtil.meterMark(MetricsKey.NET_API_QPS);
      if (resp.getStatus() >= HTTP_BAD_REQUEST && resp.getStatus() <= HTTP_NOT_ACCEPTABLE) {
        MetricsUtil.meterMark(MetricsKey.NET_API_FAIL_QPS);
        Metrics.histogramObserve(MetricKeys.Histogram.HTTP_BYTES,
                size, MetricLabels.UNDEFINED, String.valueOf(responseWrapper.getStatus()));
        return;
      }
      if (resp.getStatus() == HTTP_SUCCESS) {
        MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_QPS + endpoint);
      } else {
        MetricsUtil.meterMark(MetricsKey.NET_API_FAIL_QPS);
        MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_FAIL_QPS + endpoint);
      }
      MetricsUtil.meterMark(MetricsKey.NET_API_DETAIL_OUT_TRAFFIC + endpoint, size);
      Metrics.histogramObserve(MetricKeys.Histogram.HTTP_BYTES,
