### Title
Non-deterministic floating-point curve calculation in TRC10 Exchange (Bancor formula) can cause cross-platform consensus divergence - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The TRC10 `Exchange` feature computes trade output using a Bancor-style bonding curve (`(1+quant/balance)^CRR`) evaluated with IEEE-754 `double` arithmetic and `Math.pow`/`StrictMath.pow`. Any account can trigger this calculation with an ordinary, unprivileged `ExchangeTransactionContract` or `ExchangeInjectContract`. Because native `pow()` implementations can legitimately return different last-bit results across CPU architectures/JVMs, the exact curve output (and thus account balances written into consensus state) is not guaranteed to be identical on every validating node.

### Finding Description
The curve math lives in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply`, which raise `1 + quant/balance` to the power `0.0005` and `2000` using `Maths.pow(...)`, which dispatches to either `StrictMathWrapper.pow` (StrictMath) or `MathWrapper.pow` (plain `Math.pow`) depending on the `allowStrictMath` dynamic property: [1](#0-0) 

The result of this floating point exponentiation is cast to `long` and directly written into the `Exchange` capsule's balances, which are part of consensus state: [2](#0-1) 

The codebase itself documents that this is a known, real problem: the platform-specific `MathWrapper` for ARM does not simply call `Math.pow`; it maintains a hardcoded lookup table of previously observed divergent `pow()` results (indexed by exact input bit patterns) captured at specific historical mainnet block heights, falling back to `StrictMath.pow` only for inputs not in the table: [3](#0-2) [4](#0-3) 

while the x86 variant simply calls `Math.pow` directly: [5](#0-4) 

This table exists precisely because ARM and x86 JVMs previously produced different `pow()` results for the same curve inputs on live TRON mainnet, causing state divergence that had to be patched retroactively per-block. The table is a fixed, finite whitelist of known-bad `(base, exponent)` pairs; it cannot cover new `(base, exponent)` combinations produced by future exchange transactions with unseen `balance`/`quant` values. `StrictMathWrapper.pow` (used only once `ALLOW_STRICT_MATH` governance proposal has passed via `forkController.pass(ForkBlockVersionEnum.VERSION_4_7_7)`) is intended to fix this permanently by using `StrictMath.pow`, which has an identical, spec-guaranteed 1-ulp bit-for-bit result on every platform, but until/unless that proposal is active on a given deployment, or on any node build lacking the exact same hardcoded patch table, nodes running different CPU architectures can compute a different `anotherTokenQuant`/`buyTokenQuant` for the exact same on-chain transaction.

### Impact Explanation
Divergent evaluation of the exchange curve directly changes account/asset balances and `Exchange` capsule state that is committed to the block. If differently-behaving nodes (e.g., ARM validators without the exact hardcoded patch set vs. x86 validators, or any custom/forked build using vanilla `Math.pow`) apply the same signed `ExchangeTransactionContract`/`ExchangeInjectContract`, they will compute different resulting balances, producing a state root mismatch — i.e., a chain split / consensus halt. This is reachable by any account holding a small amount of TRX/TRC10 tokens simply by trading on an existing Exchange pair; no privileged role is required.

### Likelihood Explanation
The likelihood of hitting an as-yet-unpatched divergent `(base, exponent)` input is not something an attacker directly controls with precision, but it is not purely theoretical either — the project's own commit history shows repeated live incidents that required after-the-fact hardcoded fixes (~45 entries in the ARM lookup table across many mainnet blocks). An attacker who can find or brute-force `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` combinations that cross the sensitive floating-point boundary, or who runs their own JVM/instruction-set variant to detect a divergent input, can craft transactions that reliably differ across the mixed node fleet, deliberately triggering divergence.

### Recommendation
- Make the curve computation fully deterministic across all platforms by unconditionally routing exchange math through an integer/`BigDecimal`-based implementation such as the already-present `SafeExchangeProcessor` (guarded today by `allowHardenExchangeCalculation`), rather than gating determinism behind two separate opt-in governance proposals (`ALLOW_STRICT_MATH` and `ALLOW_HARDEN_EXCHANGE_CALCULATION`).
- Remove reliance on hardcoded, block-specific `pow()` correction tables (`platform/.../arm/org/tron/common/math/MathWrapper.java`) as a permanent fix; treat their existence as evidence the underlying arithmetic must be replaced with a spec-deterministic algorithm (e.g., `BigDecimal`/`BigInteger` fixed-point power) for all new deployments.
- Ensure `ALLOW_STRICT_MATH` (and/or hardened exchange calculation) is activated network-wide before any new validator hardware/JVM combination joins consensus, and add fuzz/property tests comparing `ExchangeProcessor` (double-based) and `SafeExchangeProcessor` (BigDecimal-based) outputs across a wide input space to detect divergence-prone regions proactively instead of reactively.

### Proof of Concept
1. Deploy/observe two full nodes with the exact same java-tron build but running on different CPU architectures/JVMs (e.g., x86_64 vs aarch64) prior to `ALLOW_STRICT_MATH` activation.
2. Create a TRC10 `Exchange` and submit an `ExchangeTransactionContract` (`actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`) with `sellTokenBalance`/`buyTokenBalance`/`sellTokenQuant` values chosen so that `1 + quant/newBalance` raised to `0.0005`/`2000` lands on a `double` value not present in the ARM hardcoded `powData` table.
3. Compare the computed `anotherTokenQuant` returned by `ExchangeCapsule.transaction` on each node; historically-documented cases (reflected by the ~45 entries in `platform/src/main/java/arm/org/tron/common/math/MathWrapper.java`) show these can differ, which after block application produces different `AccountCapsule` balances and thus different state roots between nodes.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
