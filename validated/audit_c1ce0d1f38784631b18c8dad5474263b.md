### Title
Uncontrolled resource consumption via unbounded `BigInteger` decimal parsing in HTTP JSON contract-field parser - (File: `framework/src/main/java/org/tron/core/services/http/JsonFormat.java`)

### Summary
`JsonFormat.parseInteger` (used by the custom protobuf-JSON bridge `JsonFormat.merge`) falls back to `new BigInteger(numberText, radix)` whenever a numeric JSON token is 16 characters or longer, with no upper bound on the length of that digit string. [1](#0-0) 
`JsonFormat.merge` is the entry point used by dozens of unauthenticated HTTP API servlets (e.g. `TransferServlet`, `TransferAssetServlet`, `ProposalCreateServlet`, `VoteWitnessAccountServlet`, `WithdrawBalanceServlet`, `UpdateBrokerageServlet`) to turn a raw JSON request body into the protobuf contract that is then handed to `wallet.createTransactionCapsule`. [2](#0-1) [3](#0-2) 

### Finding Description
`parseInteger` is the numeric-literal parser backing `consumeInt64`/`consumeUInt64`/`consumeInt32`/`consumeUInt32`, which are invoked while parsing any int64/uint64/int32/uint32 protobuf field supplied in an HTTP JSON request body (e.g. `frozen_balance`, `amount`, `balance`, `vote_count`, etc., depending on the contract type). [4](#0-3) 
For tokens shorter than 16 characters the code safely uses `Long.parseLong`, but for 16+ character tokens it unconditionally constructs a `BigInteger` from the full digit string with `new BigInteger(numberText, radix)` before any bounds check is applied: [5](#0-4) 
`BigInteger`'s String-to-value conversion for radix 10 has super-linear (effectively quadratic for very long inputs, since Java's implementation does repeated multiply-and-add / recursive splitting that is still expensive for huge decimal strings) computational cost in the number of digits — exactly the algorithmic-complexity class described in CVE-2018-18853/GHSA-f94m-mqhr-mc29 for spray-json's decimal-digit field parsing.

By contrast, the JSON-RPC number parser in the same codebase (`JsonRpcApiUtil.parseBlockNumber`) explicitly documents and enforces a length cap (`MAX_BLOCK_NUM_HEX_LEN = 20`) specifically to avoid this exact quadratic-BigInteger cost before calling `ByteArray.hexToBigInteger`. [6](#0-5) 
No equivalent length guard exists in `JsonFormat.parseInteger`, which is reachable from a much broader surface (the legacy Wallet HTTP API used for transaction construction) than the JSON-RPC block-number path.

### Impact Explanation
An anonymous HTTP client can submit a POST body such as `{"amount":"999...9"}` (a huge string of decimal digits, tens of KB to a few MB) to any transaction-construction servlet that calls `JsonFormat.merge` on an int64/uint64 field. Each such request forces the FullNode to perform an expensive `BigInteger` string-to-value conversion on the attacker-controlled digit string before any semantic validation of the value occurs. This consumes CPU (and transient memory for the resulting `BigInteger`) disproportionate to the request size, and because the endpoints are unauthenticated and rate limiting is typically per-request rather than per-CPU-cost, an attacker can send many such requests concurrently to degrade or exhaust node CPU capacity — a resource-consumption denial of service against a production Wallet HTTP API node, consistent with the CWE-400 class in the reported advisory.

### Likelihood Explanation
The `JsonFormat.merge`/`parseInteger` code path is reachable via a single unauthenticated HTTP POST to numerous standard Wallet API endpoints (`/wallet/transfer`, `/wallet/transferasset`, `/wallet/votewitnessaccount`, `/wallet/proposalcreate`, `/wallet/withdrawbalance`, etc.), all of which parse attacker-supplied JSON directly into protobuf builders via this parser. Whether request body size limits (`Util.checkBodySize` / Jetty size-limit handler, not confirmed for all of the affected servlets in this session) sufficiently cap the digit-string length to make the attack impractical could not be fully verified — some servlets that call `checkBodySize` were identified, but several transaction-construction servlets that call `JsonFormat.merge` (e.g. `TransferServlet`, `TransferAssetServlet`, `ProposalCreateServlet`) do call `Util.checkBodySize(contract)` prior to parsing based on the source read, which may bound overall payload size and thus mitigate — but not eliminate — the practical severity, since even a bounded (e.g., single-digit-MB) body still allows for a multi-hundred-thousand-digit numeric token.

### Recommendation
Add a maximum digit-length guard in `JsonFormat.parseInteger` (analogous to `JsonRpcApiUtil.MAX_BLOCK_NUM_HEX_LEN`) before constructing a `BigInteger` from `numberText`, e.g. reject any numeric token whose digit count exceeds the number of digits needed to represent `Long.MAX_VALUE`/`UINT64_MAX` (roughly 20 decimal digits, or 16 hex digits) plus a small margin, throwing a `NumberFormatException`/parse error immediately instead of invoking `new BigInteger(...)` on an unbounded string.

### Proof of Concept
1. Start a java-tron FullNode with the HTTP API enabled (default port 8090).
2. Send:
```
POST /wallet/createtransaction HTTP/1.1
Content-Type: application/json

{"to_address":"41...","owner_address":"41...","amount":"99999999999999999999999999999999999999999...(hundreds of thousands of 9s)"}
```
3. Observe elevated CPU time spent in `JsonFormat.parseInteger` → `new BigInteger(numberText, radix)` while the transaction is otherwise ultimately rejected (amount out of range), demonstrating that computation cost is incurred purely from the digit-string length, independent of request validity.
4. Repeat concurrently from multiple connections to observe FullNode CPU degradation, confirming resource-consumption impact on the HTTP API service path shared with legitimate transaction traffic.

  /**
   * Max allowed length for a JSON-RPC block number hex/decimal input.
   * API-level DoS guard: rejects pathological inputs before BigInteger parsing,
   * whose cost grows quadratically with length. A block number fits a signed long,
   * so the longest valid input is 19 chars (decimal Long.MAX_VALUE) or 18 (0x + 16
   * hex); 20 leaves a small margin.
   */
  private static final int MAX_BLOCK_NUM_HEX_LEN = 20;

  /**
   * Parse a JSON-RPC block number (hex "0x..." or decimal) into a long,
   * enforcing the {@link #MAX_BLOCK_NUM_HEX_LEN} length limit, rejecting
   * negative values, and rejecting values that overflow a signed 64-bit
   * block number.
   */
  public static long parseBlockNumber(String blockNum)
      throws JsonRpcInvalidParamsException {
    if (blockNum == null || blockNum.length() > MAX_BLOCK_NUM_HEX_LEN) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    BigInteger value;
    try {
      value = ByteArray.hexToBigInteger(blockNum);
    } catch (Exception e) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    if (value.signum() < 0) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
    try {
      return value.longValueExact();
    } catch (ArithmeticException e) {
      throw new JsonRpcInvalidParamsException(BLOCK_NUM_ERROR);
    }
  }
