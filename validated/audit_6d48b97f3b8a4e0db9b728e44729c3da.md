### Title
Unauthenticated `RecvError` packet allows any off-path/spoofing attacker to force tunnel teardown - (File: outside.go)

### Summary
Nebula's `RecvError` message type is processed as cleartext, pre-handshake protocol data. `readOutsidePackets` dispatches it directly to `handleRecvError` before any certificate or Noise-authenticated state is consulted, and `handleRecvError` tears down the tunnel identified by the packet's `RemoteIndex` field after only a source-IP/port equality check against the currently known remote address.

### Finding Description
In `outside.go`, the packet dispatcher treats `header.RecvError` as one of the few "unencrypted packets" handled before any cryptographic verification: [1](#0-0) 

The handler itself is: [2](#0-1) 

The only "authentication" applied is comparing the UDP source address of the incoming packet to the `HostInfo`'s currently recorded remote address (`hr != addr`). This is not a cryptographic check — it is a plain equality test on a value (source `netip.AddrPort`) that UDP allows any network-path attacker to spoof, since Nebula runs over UDP with no return-routability handshake for this message type. The `RemoteIndex` used to look up the victim's `HostInfo` via `QueryReverseIndex` is the only "secret," and it is a 32-bit value generated by `generateIndex`, sent in cleartext on every handshake and data packet, so it can be observed on-path or brute-forced off-path.

This mirrors the structural class of bug in the Tracer finding: a message that is processed as if issued by a legitimate, authenticated protocol participant, but is in fact reachable and forgeable by an attacker who does not hold any of the credentials (there, an authorized trader; here, a CA-signed certificate or an established Noise session) that the design implicitly assumes are required to trigger the action.

### Impact Explanation
An attacker who can spoof a UDP packet with the victim's peer's source `IP:port` (a classic off-path or same-subnet-spoof capability) and who knows or guesses the victim's local index can force `closeTunnel` and `handshakeManager.DeleteHostInfo` to fire, tearing down an established, authenticated Nebula tunnel with no cryptographic proof of authorization. This is a remote state-poisoning/denial-of-service primitive: it destroys legitimate session state using an unauthenticated, spoofable control message, exactly analogous to the Tracer bug's use of a permissionless function to manipulate escrow state that should only be actionable by parties with skin in the game.

### Likelihood Explanation
Exploitability depends on: (1) the attacker's ability to spoof the victim peer's source address (feasible for many network positions, and UDP has no handshake preventing it for this packet type), and (2) knowledge of the target's local index, which is transmitted in cleartext in every packet header and is thus observable by anyone who can see any traffic between the two peers, or brute-forceable blind. The project's own history acknowledges the sensitivity of this exact code path — e.g. `CHANGELOG.md` notes "Valid recv_error packets were incorrectly marked as 'spoofing' and ignored" (#482) and later added `listen.send_recv_error` / `pki.disconnect_invalid`-style controls specifically because of spoofing concerns: [3](#0-2) [4](#0-3) 

### Recommendation
Do not allow a bare `RemoteIndex` + source-address match to authorize tearing down an authenticated tunnel. Require the `RecvError` message (or an equivalent) to be cryptographically bound to the session it claims to terminate — e.g., authenticate it under the session's existing Noise key material, or require it to echo a value only the legitimate peer could know/derive, similar to how `header.Message` traffic is authenticated via `ConnectionState.Decrypt`/`VerifyRelay` before being acted upon.

### Proof of Concept
1. Establish tunnels: attacker observes traffic between `Alice` and `Bob` (or resides on a network segment/ISP capable of spoofing UDP source addresses toward `Bob`).
2. Attacker reads `RemoteIndex` from any packet header sent by `Bob` to `Alice` (index is always plaintext, per `header.H`).
3. Attacker crafts a `header.RecvError` packet with that `RemoteIndex`, and sends it to `Alice`'s listener with a spoofed UDP source address equal to `Bob`'s currently known `IP:port` (also observable in plaintext headers/handshake).
4. `readOutsidePackets` routes it to `handleRecvError`, which finds `Alice`'s `HostInfo` for `Bob` via `QueryReverseIndex`, sees `hr == addr` (spoofed to match), and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` — tearing down the legitimate, authenticated tunnel with no cryptographic proof the attacker is `Bob`. func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
