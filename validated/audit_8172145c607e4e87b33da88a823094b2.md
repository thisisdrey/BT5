Audit Report

## Title
Hardcoded ERC20 Transfer Gas Limit Permanently Traps XCM-Bridged Tokens for Non-Standard ERC20 Contracts - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::deposit_asset_with_surplus` and `withdraw_asset_with_surplus` call `pallet_revive::Pallet::<T>::bare_call` with a fixed, non-configurable `WeightLimit::get()` (instantiated as `ERC20TransferGasLimit = Weight::from_parts(500_000_000_000, 10 * 1024 * 1024)`, sized only for a "standard ERC20 transfer") for every XCM-triggered ERC20 transfer [1](#0-0) [2](#0-1) . Any ERC20 contract whose `transfer` logic legitimately requires more gas/weight (fee-on-transfer, rebasing, blacklist checks, proxy hooks) will make the deposit leg fail deterministically, and because `ERC20Transactor` never overrides `mint_asset`, the trapped credit is permanently unrecoverable via `pallet_xcm::claim_assets`.

## Finding Description
`withdraw_asset_with_surplus` moves tokens from the sender into `TransfersCheckingAccount` using a fixed-gas ERC20 `transfer` call [3](#0-2) . This succeeds because the sender's outgoing transfer is typically the "standard" case the gas limit was sized for. `deposit_asset_with_surplus` then attempts to move funds from the checking account to the beneficiary using the identical fixed `WeightLimit::get()` [1](#0-0) . If this errors (e.g., out of gas), the code path explicitly acknowledges there is no way for the user to adjust the XCM to recover: `Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))` [4](#0-3) .

The repository's own test, `expensive_erc20_runs_out_of_gas`, reproduces this exact failure against a contract (`MyTokenExpensive`) that performs more storage work than a standard transfer [5](#0-4) .

When `deposit_asset_with_surplus` fails after `xcm-executor`'s retry pass, the leftover holding is trapped via `AssetTrap` [6](#0-5) . Recovery is nominally possible via `pallet_xcm::claim_assets`, which calls `AssetTransactor::mint_asset` [7](#0-6) . However, `ERC20Transactor` provides no `mint_asset` implementation, so it falls through to the trait default `Err(XcmError::Unimplemented)` [8](#0-7) . Confirmed by searching the file, `ERC20Transactor` in `erc20_transactor.rs` implements only `can_check_in`, `check_in`, `can_check_out`, `check_out`, `withdraw_asset_with_surplus`, and `deposit_asset_with_surplus` — no `mint_asset` override exists anywhere in the file [9](#0-8) . In a tuple-composed `AssetTransactor`, `Err(Unimplemented)` from one member simply continues to the next tuple member [10](#0-9) , but no other transactor in the composed tuple will match an ERC20 `H160`-keyed asset, so the overall `mint_asset` call resolves to `Err(XcmError::AssetNotFound)`. The underlying ERC20 balance remains stranded in `TransfersCheckingAccount` with no code path capable of releasing it.

## Impact Explanation
This falls squarely under "permanent user-fund... lock": an unprivileged user's own XCM message involving a non-"standard" ERC20 token causes their tokens to be irreversibly stuck in `ERC20TransfersCheckingAccount` after being withdrawn from their account, with no available claim mechanism to release them since `mint_asset` is unimplemented for `ERC20Transactor`. The existing test `expensive_erc20_runs_out_of_gas` in `asset-hub-westend/tests/tests.rs` demonstrates the exact underlying failure condition against a real (fixture) contract.

## Likelihood Explanation
No privileged actor, governance, or malicious peer is required. Any user submitting an ordinary `PolkadotXcm::execute`/XCM program that withdraws and deposits an ERC20 asset whose `transfer` function does non-trivial extra work (fee-on-transfer, rebase, compliance/blacklist checks, proxy forwarding) beyond the "standard ERC20 transfer" assumption baked into the fixed `ERC20TransferGasLimit` will trigger this deterministically and repeatably, matching a realistic and common category of ERC20 token implementations.

## Recommendation
- Avoid a single hardcoded weight limit for arbitrary ERC20 contracts in `deposit_asset_with_surplus`/`withdraw_asset_with_surplus`; support per-asset configurable gas limits or dry-run/estimate gas per specific token contract before committing to a fixed limit.
- Implement a dedicated `mint_asset` for `ERC20Transactor` with an escalated/configurable weight limit specifically for claim/recovery flows so that gas-exhaustion-trapped funds are actually recoverable.
- Consider detecting/quarantining "expensive" ERC20 contracts at the XCM matcher level before funds leave the sender's account.

## Proof of Concept
The existing repository test `expensive_erc20_runs_out_of_gas` demonstrates the failure directly [5](#0-4) . To confirm permanent lock: split the same scenario into two separate XCM programs mirroring the real bridge flow — first a successful `withdraw_asset_with_surplus` moving tokens into `ERC20TransfersCheckingAccount`, then a `deposit_asset_with_surplus` that fails identically due to insufficient fixed gas. Then invoke `pallet_xcm::claim_assets` against the resulting trap and confirm it returns without minting anything (since `ERC20Transactor::mint_asset` is unimplemented and no other transactor matches the ERC20 asset id), leaving the ERC20 balance of `ERC20TransfersCheckingAccount` unchanged and permanently stranded across repeated claim attempts.

	fn deposit_assets_with_retry(
		to_deposit: AssetsInHolding,
		beneficiary: &Location,
		context: Option<&XcmContext>,
	) -> Result<Weight, XcmError> {
		let mut total_surplus = Weight::zero();
		let mut failed_deposits = AssetsInHolding::new();

		// First pass: try to deposit each asset; failures go to retry.
		for single in to_deposit.into_per_asset_holdings() {
			match Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
			{
				Ok(surplus) => total_surplus.saturating_accrue(surplus),
				Err((unspent, _)) => {
					// First-pass failure: keep for retry. A subsequent deposit in the same
					// pass may create the destination account (by satisfying ED), allowing
					// the retry pass to succeed for assets that fall here.
					failed_deposits.subsume_assets(unspent);
				},
			}
		}

		// Retry previously failed deposits, this time short-circuiting on any error.
		for single in failed_deposits.into_per_asset_holdings() {
			let surplus =
				Config::AssetTransactor::deposit_asset_with_surplus(single, beneficiary, context)
					.map_err(|(unspent, error)| {
					tracing::debug!(
						target: "xcm::deposit_assets_with_retry",
						?error,
						?unspent,
						"Retry-pass deposit failed"
					);
					error
				})?;
			total_surplus.saturating_accrue(surplus);
		}

		Ok(total_surplus)
	}

impl<T: Config> ClaimAssets for Pallet<T> {
	fn claim_assets(
		origin: &Location,
		ticket: &Location,
		assets: &Assets,
		context: &XcmContext,
	) -> Option<AssetsInHolding> {
		let mut versioned = VersionedAssets::from(assets.clone());
		match ticket.unpack() {
			(0, [GeneralIndex(i)]) => {
				versioned = match versioned.into_version(*i as u32) {
					Ok(v) => v,
					Err(()) => return None,
				}
			},
			(0, []) => (),
			_ => return None,
		};
		let hash = BlakeTwo256::hash_of(&(origin.clone(), versioned.clone()));
		match AssetTraps::<T>::get(hash) {
			0 => return None,
			1 => AssetTraps::<T>::remove(hash),
			n => AssetTraps::<T>::insert(hash, n - 1),
		}
		let mut claimed = AssetsInHolding::new();
		for asset in assets.inner() {
			match <T::XcmExecutor as XcmAssetTransfers>::AssetTransactor::mint_asset(asset, context)
			{
				Ok(minted) => {
					// SAFETY: Any fungible imbalances are now effectively duplicated because they
					// were not resolved when the asset was trapped (so total issuance tracks
					// trapped assets too), and now a duplicate asset was just minted.
					// To balance the system and keep total issuance constant, we drop and resolve
					// one of the duplicates. As a result, total issuance doesn't change.
					//
					// Note: This may emit Burned/Minted events even though the net issuance change
					// is zero. The mint creates a +X imbalance, and dropping the clone resolves -X,
					// resulting in no net change but potentially two events. This is an acceptable
					// tradeoff for the asset trap/claim mechanism.
					minted.fungible.iter().for_each(|(_, imbalance)| {
						let to_resolve = imbalance.unsafe_clone();
						core::mem::drop(to_resolve);
					});
					claimed.subsume_assets(minted)
				},
				Err(error) => tracing::debug!(
					target: "xcm::pallet_xcm::claim_assets",
					?asset, ?error, "Asset claimed from trap but unable to mint."
				),
			}
		}
		Self::deposit_event(Event::AssetsClaimed {
			hash,
			origin: origin.clone(),
			assets: versioned,
		});
		Some(claimed)
	}
