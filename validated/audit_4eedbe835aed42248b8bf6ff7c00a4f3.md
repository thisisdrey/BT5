### Title
Postponed self-authorized `ActionReceipt` (e.g. `AddKey(FullAccess)`) survives `DeleteAccount`/`CreateAccount` and executes against the recreated account, bypassing `check_actor_permissions` - ([File: runtime/runtime/src/lib.rs])

### Summary
`check_actor_permissions` authorizes self-only actions (`AddKey`, `DeployContract`, `DeleteKey`, `Stake`, etc.) purely by comparing `actor_id == account_id` as strings, using `actor_id = receipt.predecessor_id()` captured at the time the (postponed) receipt was authored. Because `action_delete_account`/`remove_account` never clears the `PostponedReceipt`, `PendingDataCount`, or `PostponedReceiptId` trie entries keyed by `receiver_id`, a postponed receipt authored by the *old* owner of an account can outlive a `DeleteAccount` + `CreateAccount` cycle and later execute a privileged self-action against the *new* owner's account.

### Finding Description
`check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) enforces `actor_id == account_id` for `AddKey`/`DeployContract`/`DeleteKey`/`Stake`/etc. `apply_action_receipt` initializes `actor_id` from `receipt.predecessor_id().clone()` (`runtime/runtime/src/lib.rs:855`), i.e., whatever predecessor was recorded in the `ActionReceipt` when it was originally created/postponed — not anything tied to the account's current "identity" or creation epoch.

When a receiver has unresolved `input_data_ids`, `process_action_receipt` stores the receipt as a `PostponedReceipt` plus `PendingDataCount`/`PostponedReceiptId` entries keyed by `(receiver_id, receipt_id/data_id)` (`runtime/runtime/src/lib.rs:1608-1655`, `core/store/src/utils/mod.rs:120-143`). These entries are only removed when the corresponding `DataReceipt` finally arrives (`process_receipt`, `runtime/runtime/src/lib.rs:1386-1473`).

Separately, `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes the `Account`, `ContractCode`, access keys, gas-key nonces, and `ContractData` — but never touches `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` for that account. There is also no check in `action_delete_account` for outstanding postponed receipts targeting the account being deleted.

Exploit flow:
1. Attacker owns `victim.near` and, acting as that account (`predecessor_id == receiver_id == victim.near`), sends itself an `ActionReceipt` containing `Action::AddKey(FullAccess, attacker_pubkey2)` with an `input_data_id` the attacker fully controls (e.g. an outstanding cross-contract promise it will resolve on its own schedule). This receipt gets postponed (`process_action_receipt`).
2. Attacker sends a second, ordinary self-receipt `DeleteAccount` for `victim.near` (locked balance is zero, so `check_actor_permissions`'s `DeleteAccountStaking` check passes). `remove_account` deletes the account but leaves the postponed `AddKey` receipt and its pending-data bookkeeping intact in the trie.
3. A third party later creates an account named `victim.near` (feasible for names not requiring registrar permission, e.g. long top-level names, or via a follow-on sub-account creation pattern), unaware of the still-pending postponed receipt.
4. Attacker supplies the missing `DataReceipt`, resolving the pending count to 0. `process_receipt`'s `Data` arm fetches the stale postponed receipt and calls `apply_action_receipt` (`runtime/runtime/src/lib.rs:1442-1455`). `check_account_existence` passes (the account now exists). `check_actor_permissions` passes because `actor_id` ("victim.near", frozen in the old receipt) still equals `account_id` ("victim.near", the new owner's account) as plain strings — with no account-identity/versioning check. The `AddKey(FullAccess, attacker_pubkey2)` executes, giving the attacker a full-access key on the new owner's account.

This is an authorization-exactness violation: the self-call permission model implicitly assumes "predecessor_id == receiver_id" implies "the entity currently controlling receiver_id authorized this action," but that invariant breaks once the account behind the name has been deleted and recreated between receipt authorship and receipt execution.

### Impact Explanation
Authorization escalation across accounts: an attacker plants a durable, self-triggerable `AddKey(FullAccess)` (or `DeployContract`) time bomb tied to an account name, then deletes the account. Once a different party recreates an account under that exact name, the attacker can resolve the pending data dependency at will and silently obtain full-access control (or contract code execution rights) over the new owner's account and its funds — a direct cross-account authorization escalation, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The attacker needs only ordinary account/transaction capabilities: create an account, send it a self-authorized action receipt with a self-controlled unresolved dependency, then self-delete. No validator, node, or privileged access is required, and the sequence is fully reproducible/repeatable at will. The remaining precondition — a third party recreating the exact same account name — limits the practical blast radius to name-squatting/front-running scenarios (e.g., pre-registering a name a target is expected to claim, or attacker-controlled/self-recreation for other griefing purposes), but the underlying mechanism (stale postponed receipts surviving delete+recreate and bypassing actor-permission checks) is unconditionally reachable and requires no assistance from the recreator.

### Recommendation
When deleting an account, either (a) reject `DeleteAccount` if there exist outstanding `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` entries for that `receiver_id`, or (b) have `remove_account`/`action_delete_account` enumerate and purge all `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` trie entries keyed by the deleted account, failing (or refunding/erroring) any postponed receipts still pending for it, so no stale self-authorized action can resolve against a subsequently recreated account of the same name.

### Proof of Concept
Integration/unit test plan (extending the pattern already used in `runtime/runtime/src/tests/apply.rs::test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`, `runtime/runtime/src/tests/apply.rs:4881-4982`):
1. Set up `victim` account owned by attacker signer.
2. Send an `ActionReceipt` to `victim` with `predecessor_id = receiver_id = victim`, `actions = [AddKey(FullAccess, attacker_pubkey2)]`, and a non-empty `input_data_ids` referencing a `data_id` that has not yet been delivered. Assert it becomes a postponed receipt (`apply_result.delayed_receipts_count`/postponed-count assertions, or verify via `get_postponed_receipt`).
3. Send a second self-receipt to `victim`: `Action::DeleteAccount`. Apply and commit; assert the account no longer exists (`get_account` returns `None`).
4. Send a `CreateAccount` receipt with a *different* predecessor/signer (simulating the third party) targeting the same `victim` account id, funding it and adding its own key.
5. Send the missing `DataReceipt` for the originally-postponed input_data_id.
6. Apply and assert: the postponed `AddKey` receipt executes successfully (`SuccessReceiptId`/`SuccessValue`), and `get_access_key(state_update, victim, attacker_pubkey2)` returns `Some(FullAccess)` on the account created by the third party in step 4 — demonstrating the attacker obtained a full-access key on an account it never legitimately owned after recreation.
