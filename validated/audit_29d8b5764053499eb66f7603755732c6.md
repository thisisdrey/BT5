### Title
Active-permission holder can self-escalate to full Owner control via AccountPermissionUpdateContract - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator.validate()` only checks internal consistency of the *new* Owner/Witness/Active permissions being set (key count, distinct addresses, weight/threshold sums, valid operation bits), but never checks that the *acting* permission used to authorize the transaction (`Transaction.Contract.getPermissionId()`) is entitled to set a broader/different permission than it was itself granted. Any account that has been delegated an Active permission whose 32-byte operations bitmap includes the `AccountPermissionUpdateContract` bit (type 46) can invoke `AccountPermissionUpdateContract` and replace the account's Owner permission with an entirely new set of keys/threshold of its own choosing — i.e. it can "reshare" itself from a narrowly scoped Active role into full Owner control, mirroring the Nextcloud CVE-2024-37882 pattern where a recipient with read&share permission could reshare with more permissions than it was granted.

### Finding Description
Authorization for any broadcast contract is delegated to `permissionId` embedded in the transaction, resolved via `AccountCapsule.getPermissionById` and gated only by `WalletUtil.checkPermissionOperations`/`TransactionUtil.checkPermissionOperations`, which merely tests whether the bit for the target `ContractType` is set in the acting permission's `operations` bitmap: [1](#0-0) 

For `AccountPermissionUpdateContract` specifically, `AccountPermissionUpdateActuator.validate()` performs no check that the acting Active permission's own privilege scope bounds what it may set for the new Owner/Witness/Active permissions. It validates only the shape of the *proposed* permissions (weights, thresholds, distinct keys, valid ContractType bits against `getAvailableContractType()`), not against the invoking permission's own restrictions: [2](#0-1) 

The per-permission validation helper `checkPermission()` bounds custom Active-permission operation bits only by `dynamicStore.getAvailableContractType()` (the set of all valid contract types), not by `getActiveDefaultOperations()` (the safer default subset that intentionally excludes `AccountPermissionUpdateContract`, id 46), confirmed by the test asserting that the default active bitmap omits `AccountPermissionUpdateContract`: [3](#0-2) [4](#0-3) 

`execute()` then unconditionally applies whatever Owner/Witness/Active permissions were supplied in the contract, with no comparison to the caller's own permission tier: [5](#0-4) 

Consequently, if the true account owner ever grants a delegate/co-signer an Active permission whose operations bitmap includes bit 46 (`AccountPermissionUpdateContract`) — for example to allow a custodial/DAO co-manager to perform routine account-permission maintenance — that delegate, by meeting only that Active permission's own (possibly low) threshold, can submit an `AccountPermissionUpdateContract` transaction that installs a brand-new Owner permission naming only the attacker's own keys and an arbitrarily low threshold. This permanently locks out the legitimate owner and all other permission holders, since Owner permission is authoritative over all account operations (transfers, resource freezing, further permission updates, etc.).

### Impact Explanation
This allows unauthorized permanent seizure of an account: an actor holding only a narrowly-scoped Active permission (intended for e.g. specific contract calls) can escalate to full Owner control, permanently freezing out the legitimate owner and other signers, and then drain funds/resources or block all future operations on the account. This satisfies the "unauthorized account operation / permanent freezing of funds" bar.

### Likelihood Explanation
Exploitation requires that an account owner has previously granted an Active permission including the `AccountPermissionUpdateContract` operation bit to a less-trusted party (a realistic scenario for exchanges, custodians, or multi-party account management setups that want a delegate able to rotate keys without needing full Owner authority for every other operation). Given that TRON's own default Active permission template explicitly excludes this bit (as shown by the test), the system's own design intent is that Active permissions should *not* normally be able to touch account permissions — but the actuator does not enforce this as a hard rule, it is left to the owner's discretion when constructing custom Active permissions, and there is no additional runtime safeguard (e.g., requiring `permissionId == 0`) preventing the delegate from using this capability to fully overwrite Owner. Likelihood is Medium-High wherever custom Active permissions are configured with this bit set for delegation purposes.

### Recommendation
Add an explicit restriction in `AccountPermissionUpdateActuator.validate()` (and in `TransactionUtil`/`WalletUtil` `checkPermissionOperations` used by broadcast/sign paths) requiring that `AccountPermissionUpdateContract` may only be authorized by the account's Owner permission (`permissionId == 0`), rejecting any transaction attempting to invoke it via an Active permission regardless of that permission's operations bitmap. Alternatively, reject Active permissions at creation time (`checkPermission`) that attempt to set the `AccountPermissionUpdateContract` bit, mirroring the default-operations exclusion already used elsewhere.

### Proof of Concept
1. Account `A` (Owner key `K_owner`) creates a custom Active permission `P2` with a low threshold and a key `K_delegate`, deliberately or mistakenly setting operations bit 46 (`AccountPermissionUpdateContract`) alongside other desired operation bits, via a normal `AccountPermissionUpdateContract` transaction signed by Owner — this passes `checkPermission()` since bit 46 is within `getAvailableContractType()`.
2. The holder of `K_delegate` crafts a new `AccountPermissionUpdateContract` transaction with `permission_id = 2` (referencing `P2`), setting `owner` to a brand-new `Permission` containing only `K_delegate` with `threshold = 1`, and a valid `active` list.
3. `K_delegate` signs the transaction; `checkPermissionOperations(P2, contract)` returns true because bit 46 is set in `P2`'s operations, and `checkWeight` passes because `P2`'s own threshold is met by `K_delegate`'s single signature.
4. Broadcast succeeds; `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(...)`, replacing Owner permission entirely with `K_delegate`-only control — `K_owner` and all prior permissions are permanently locked out of the account.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }

      logger.debug(e.getMessage(), e);

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
