### Title
Attached deposit silently lost (no refund promise) when NEP-141 `storage_balance_of` cross-contract call fails - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`WalletContract::nep_141_storage_balance_callback` tracks a caller's attached deposit via `CallerDeposit` (populated whenever `predecessor_account_id != current_account_id` and `attached_deposit` is nonzero) so it can be refunded if a downstream cross-contract call fails. However, in this specific callback's `PromiseResult::Failed` branch the function returns early without ever inspecting or refunding `caller_deposit`, unlike the sibling `rlp_execute_callback`, which explicitly creates a refund `Promise` in its analogous `Failed` branch.

### Finding Description
In `inner_rlp_execute` [1](#0-0) , `CallerDeposit::new(&context)` records the relayer's attached deposit whenever the transaction is relayed (`predecessor_account_id != current_account_id`) and the attached deposit is nonzero [2](#0-1) . For an `ERC20Transfer` transaction kind, this `caller_deposit` is threaded through to `nep_141_storage_balance_callback` [3](#0-2) .

Inside `nep_141_storage_balance_callback`, the `PromiseResult::Failed` arm for promise index 0 (the `storage_balance_of` call) immediately returns an error `ExecuteResponse` and drops `caller_deposit` without ever creating a refund `Promise`: [4](#0-3) 

Compare this to `rlp_execute_callback`'s `Failed` arm, which correctly builds a `promise_batch_create`/`promise_batch_action_transfer` refund to `caller_deposit.account_id` before returning the failure response: [5](#0-4) 

Because `nep_141_storage_balance_callback` short-circuits on failure without any equivalent logic, the `caller_deposit.yocto_near` amount — which the wallet contract already received as `attached_deposit` on the original `rlp_execute` call — remains part of the wallet contract's NEAR balance forever, with no promise, no bookkeeping, and no code path that will ever move it back out. `address_check_callback`'s `Failed` arm has the same gap.

An attacker (an ordinary account) can trigger this deterministically: sign an Ethereum-emulated transfer transaction whose `target`/`to` resolves to an ERC-20-looking Near account they control, and deploy that account's contract so that `storage_balance_of` always panics/fails. When any relayer (including the attacker acting as their own relayer, or a third-party relayer who is induced to relay this transaction) calls `rlp_execute` with `target` set to that malicious token and attaches a nonzero deposit, `inner_rlp_execute` creates the `storage_balance_of` promise chain and records `CallerDeposit`. The malicious contract's `storage_balance_of` fails, `PromiseResult::Failed` is observed in `nep_141_storage_balance_callback`, and the function returns without creating any transfer promise back to the relayer, permanently stranding the attached deposit in the wallet contract.

No existing check (signature, nonce, access-key, gas metering, or storage staking) prevents this — the bug is a pure logic omission in the `Failed` match arm, independent of those validations.

### Impact Explanation
This is a permanent freezing of funds bug: the relayer's (or self-relaying attacker's own, or an unwitting third-party relayer's) attached NEAR deposit becomes irrecoverably locked in the wallet contract's balance with no promise, method, or accounting path to reclaim it. This matches the "permanent freezing of user funds" bounty category. The magnitude is bounded by whatever deposit amount the relayer chooses to attach per transaction, but the bug is deterministically repeatable against any relayer who attaches a deposit for an ERC-20 style transfer routed through a malicious/failing token contract.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: deploy an arbitrary wasm contract acting as a fake NEP-141 token whose `storage_balance_of` always fails, and craft/sign (or have signed) an RLP-encoded transaction whose `target` points to that contract so the wallet contract classifies it as `EthEmulationKind::ERC20Transfer`. The attacker can trigger the failure by simply causing `storage_balance_of` to panic (e.g., a `env::panic_str` in the fake contract), guaranteeing `PromiseResult::Failed`. This requires no elevated privileges, no validator/node access, and is deterministic and repeatable on every invocation.

### Recommendation
Add the same refund logic used in `rlp_execute_callback`'s `Failed` arm to `nep_141_storage_balance_callback`'s (and `address_check_callback`'s) `Failed` arm: before returning the error `ExecuteResponse`, check `if let Some(CallerDeposit { account_id, yocto_near }) = caller_deposit { ... create refund promise ... }`. Ideally factor this into a shared helper function to avoid divergence between the three callback failure branches in the future.

### Proof of Concept
Unit test plan (in `runtime/near-wallet-contract/implementation/wallet-contract/src/tests`):
1. Set up a mocked Near environment where `predecessor_account_id` (relayer) differs from `current_account_id` (wallet), and `attached_deposit` on `rlp_execute` is nonzero.
2. Drive execution through `inner_rlp_execute`/`nep_141_storage_balance_callback` for an `ERC20Transfer` transaction kind so that `CallerDeposit::new` returns `Some(...)` and is passed into `nep_141_storage_balance_callback`.
3. Mock `env::promise_result(0)` to return `PromiseResult::Failed` (simulating a failing `storage_balance_of` call).
4. Call `nep_141_storage_balance_callback` directly with the `Some(caller_deposit)` argument.
5. Assert: (a) the returned `PromiseOrValue::Value(ExecuteResponse)` has `success: false`; (b) no `Promise`/`promise_batch_create` refund action was recorded (i.e., using the mocked VM context, assert zero outgoing receipts/actions were generated); (c) demonstrate that the attached deposit amount is unaccounted for — no action in the recorded receipts sends `yocto_near` back to `account_id`, proving the deposit is stranded and violating value conservation compared to the `rlp_execute_callback` `Failed` path where a refund promise is asserted to exist.

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
}
