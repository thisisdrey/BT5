### Title
Unbounded array-length field in TVM precompiled-contract calldata parsing enables memory-exhaustion DoS - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an unvalidated 256-bit length field straight out of attacker-controlled precompile calldata and use it directly to size a Java array allocation, mirroring the Pillow ICO bug (CVE-2021-27923) where an image container's declared size is trusted for a memory allocation without a sanity bound.

### Finding Description
In `extractBytes32Array`/`extractBytesArray`/`extractSigArray`, the array length `len` is taken from a `DataWord` decoded from raw calldata via `intValueSafe()`, then immediately used as the allocation size: [1](#0-0) 

None of these helpers bound `len` against the actual remaining calldata size or against any sane upper limit before allocating `new byte[len][]`. `intValueSafe()` derives from a 256-bit `DataWord` (an attacker fully controls the calldata bytes feeding this word), so an attacker can encode a length near `Integer.MAX_VALUE` while supplying only a few dozen bytes of actual calldata. The allocation of a `byte[Integer.MAX_VALUE][]` reference array (~8 bytes/slot on a 64-bit JVM, i.e. up to ~17 GB) is attempted before any of the array's elements are populated or validated, and before the loop body (which would otherwise start slicing the real payload) ever executes. This closely parallels the Pillow flaw: a length/size value taken from untrusted container data is trusted for a large `malloc`-equivalent allocation without checking it against the input's real size.

This differs from other size-controlled paths in the same file, such as `isValidAbiEncoding` which validates `data.length` against expected word-aligned sizes before use, and from EVM memory extension (`Memory.extend`) which is metered and grows in small `CHUNK_SIZE` increments rather than allocating the full requested size up front. [2](#0-1) [3](#0-2) 

### Impact Explanation
A single crafted transaction invoking the affected precompiled contract with a small calldata payload but an oversized encoded length can trigger an immediate large heap allocation attempt inside the TVM execution path shared by every node validating the block/transaction (full nodes and SRs). Depending on the requested size this can throw `OutOfMemoryError` or cause severe GC pressure/thrashing, degrading or crashing the JVM process across the network as each node re-executes the same transaction — a node-crash/availability-DoS class impact, reachable purely through an unprivileged, signed transaction that calls the precompile.

### Likelihood Explanation
The precompile parsing logic is reachable by any account able to submit a smart-contract call that invokes one of the affected precompiled contracts (no special privilege required), and constructing calldata with an inflated length word is trivial — this only requires knowledge of the calldata layout, which is fixed and public. The main uncertainty (noted below) is confirming which of the currently wired precompiled-contract addresses actually dispatches to `extractBytes32Array`/`extractBytesArray`/`extractSigArray` in this build, and whether energy metering for that specific contract's `getEnergyForData` scales with the declared length before the allocation runs; I was not able to fully trace the calling precompile or its energy-cost function within the available search budget.

### Recommendation
Before allocating `bytesArray`/`bytes32Array`, bound `len` against the remaining size of `data`/`words` (e.g., `len <= (words.length - offset - 1)` and `len * itemSize <= data.length`), and reject with a normal execution failure otherwise, matching the pattern already used in `isValidAbiEncoding`. Additionally, ensure the corresponding `getEnergyForData` charges energy proportional to the declared `len` (or rejects it) prior to entering `execute`, so a decoded length can never exceed what has already been paid for and bounded by the real calldata size.

### Proof of Concept
Conceptually (exact precompile address unconfirmed given the caller could not be located in this pass):
1. Construct a contract call to the affected precompiled-contract address.
2. Supply calldata whose word at the expected "array length" offset encodes a very large value (e.g., `0x000000000000000000000000000000000000000000000000000000FFFFFFFF`), while providing only the minimum number of trailing words needed to pass earlier length checks (there are none blocking this specific value).
3. Submit the transaction; `extractBytes32Array`/`extractBytesArray`/`extractSigArray` executes `new byte[len][]` with `len` ≈ `0xFFFFFFFF`, attempting a multi-gigabyte allocation on every validating node.

Because the exact vulnerable entry point (which precompiled-contract type dispatches to these extract* helpers, and whether its energy cost accounts for the declared length) could not be conclusively confirmed within the available tool budget, this PoC path should be validated against the live contract-address dispatch table and energy-cost implementation before treating it as fully exploitable.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
