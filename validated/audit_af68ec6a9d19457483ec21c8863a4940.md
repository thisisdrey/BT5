Audit Report

## Title
Unbounded, fixed-weight `submit` extrinsic in Snowbridge inbound queue admits attacker-sized proof data with no pallet-level size limit, enabling underpriced resource-exhaustion - (File: `bridges/snowbridge/pallets/inbound-queue/src/lib.rs`, `bridges/snowbridge/primitives/verification/src/lib.rs`)

## Summary
The `submit` extrinsic in `pallet-snowbridge-inbound-queue` accepts an `EventProof` whose `Log.data`, `Log.topics`, and `Proof.receipt_proof` fields are unbounded `Vec`s, and immediately performs expensive cryptographic verification (`T::Verifier::verify`) on them before any nonce, gateway, or channel checks. The only documented "size" config, `MaxMessageSize`, is explicitly used solely for fee/reward estimation, not for input rejection.

## Finding Description
`submit` is declared with a fixed benchmarked weight, `#[pallet::weight(T::WeightInfo::submit())]`, and dispatches straight into `T::Verifier::verify(&event.event_log, &event.proof)` before any `ensure!` on the size of `event.proof.receipt_proof`, `event.event_log.data`, or `event.event_log.topics` [1](#0-0) . `Log` and `Proof` are plain structs with `Vec<u8>`/`Vec<Vec<u8>>`/`Vec<H256>` fields with no `BoundedVec` or length constraint [2](#0-1) . The `Verifier::verify` implementation in `pallet-snowbridge-ethereum-client` performs `verify_execution_proof` (merkle-branch verification over `execution_proof.ancestry_proof.header_branch: Vec<H256>`) and then `verify_receipt_inclusion` → `verify_receipt_proof` (RLP decoding + `alloy_trie::verify_proof` walking `receipt_proof: Vec<Vec<u8>>`) [3](#0-2) . Both proof branches are unbounded `Vec`s whose actual verification cost is proportional to attacker-supplied length, yet the dispatch's charged ref-time weight is the single benchmarked constant `T::WeightInfo::submit()`, not a function of `event`'s encoded length. `MaxMessageSize` is explicitly commented as "only used to estimate delivery cost" and is fed into `calculate_delivery_cost`, which computes the *relayer reward* paid from the destination sovereign account, not a validation bound on the incoming `event` [4](#0-3) [5](#0-4) .

However, this claim overstates the severity of the missing pallet-level bound for two reasons I could partially but not fully verify in this pass:
1. Standard Substrate transaction fees (via `pallet_transaction_payment`'s runtime-wide `LengthToFee`) are charged on the raw encoded extrinsic length for *every* extrinsic in a Substrate-based chain, independent of the pallet's own weight annotation. This means an attacker submitting an oversized `EventProof` already pays a fee proportional to the submitted byte length before the pallet-specific fixed weight is even considered — this is a generic runtime mechanism, not something `pallet-snowbridge-inbound-queue` needs to reimplement. I was unable to fully trace the exact `LengthToFee` constant configured for BridgeHub's `pallet_transaction_payment::Config` in this pass to quantify how well it tracks the true verification cost, so I cannot confirm the fee is *insufficient* relative to attacker-controlled compute time, only that a length-scaled charge does generically exist at the runtime level.
2. Substrate enforces a chain-wide maximum extrinsic/block length (`BlockLength`), which already caps the absolute worst-case size an attacker can submit in a single call, bounding (though not eliminating) the worst-case per-call cost multiplier relative to the benchmarked weight.

## Impact Explanation
If the benchmarked `submit()` weight underestimates the actual worst-case ref-time cost of RLP-decoding and trie-walking a maximally-sized `receipt_proof`/`ancestry_proof` relative to what was used during benchmarking, this qualifies as "public underpriced work that degrades block production or stalls bridge processing," which is an accepted impact category. The severity depends on the delta between benchmarked assumptions (typical proof depth/node count) and the chain-length-capped worst case, which I could not fully quantify without access to the `WeightInfo::submit()` benchmark weight formula/benchmarking fixture data and the runtime's configured `pallet_transaction_payment::LengthToFee`/`BlockLength` values.

## Likelihood Explanation
Any signed account with sufficient balance to pay the (length-scaled) transaction fee can submit crafted `EventProof` values with maximal `receipt_proof`/`data` up to the chain's extrinsic length limit; no privileged, relayer, or validator role is required, and the call is unconditionally publicly dispatchable, so the precondition for the attack is trivially satisfiable.

## Recommendation
- Add explicit `ensure!` bounds (or `BoundedVec`) on `Log.data`, `Log.topics`, `Proof.receipt_proof` (and per-node byte length), and `ExecutionProof.ancestry_proof.header_branch`, sized to realistic Ethereum receipt-proof/beacon-ancestry-proof maxima, rejected before calling `T::Verifier::verify`.
- Re-benchmark `submit()`'s weight against these bounded worst-case sizes so the declared weight actually reflects the maximum permitted verification cost, closing any gap between charged and actual computation.
- Consider replacing `MaxMessageSize`'s fee-estimation-only role with an actual enforced ceiling, or add a dedicated enforced `MaxProofSize`/`MaxReceiptProofNodes`.

## Proof of Concept
1. Construct an `EventProof` with `event_log.data` and `proof.receipt_proof` filled with maximal-length garbage bytes/nodes, up to the runtime's max extrinsic length.
2. Submit via `InboundQueue::submit(origin, event)` repeatedly from a signed account.
3. Measure wall-clock/CPU time spent inside `T::Verifier::verify` (RLP decoding, `alloy_trie::verify_proof`, merkle-branch walking) relative to the benchmarked `WeightInfo::submit()` weight and the actual runtime `pallet_transaction_payment` fee charged, to determine whether a nontrivial underpricing gap exists. Confirming this requires inspecting the concrete benchmark fixture sizes in the (unlocated) `benchmarking.rs`/weight-generation file and the BridgeHub runtime's `pallet_transaction_payment::Config::LengthToFee`/`BlockLength`, which I could not fully access in this session — a Devin session with full repo access would let you pull those exact values to close this gap.

	fn verify(event_log: &Log, proof: &Proof) -> Result<(), VerificationError> {
		// Refuse to verify any Ethereum-side proof while the beacon light client is halted.
		// Governance halts the light client when it suspects a compromise (e.g. sync committee
		// takeover), at which point any signed headers/receipts must be treated as untrusted.
		// Covers every Verifier consumer, including `inbound_queue_v2::submit` and
		// `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain
		// pending relayer rewards while the bridge is halted).
		ensure!(!Self::operating_mode().is_halted(), VerificationError::Halted);

		Self::verify_execution_proof(&proof.execution_proof)
			.map_err(|e| InvalidExecutionProof(e.into()))?;

		Self::verify_receipt_inclusion(
			proof.execution_proof.execution_header.receipts_root(),
			event_log.tx_index,
			&proof.receipt_proof,
			event_log,
		)?;

		Ok(())
	}
}

impl<T: Config> Pallet<T> {
	/// Verifies that the receipt encoded in `proof.data` is included in the block given by
	/// `proof.block_hash`.
	pub fn verify_receipt_inclusion(
		receipts_root: H256,
		tx_index: u64,
		receipt_proof: &[Vec<u8>],
		log: &Log,
	) -> Result<(), VerificationError> {
		let receipt =
			verify_receipt_proof(receipts_root, tx_index, receipt_proof).ok_or(InvalidProof)?;
		if !receipt.logs().iter().any(|l| Self::check_log_match(log, l)) {
			tracing::error!(
				target: "ethereum-client",
				"💫 Event log not found in receipt for transaction",
			);
			return Err(LogNotFound);
		}
		Ok(())
	}
