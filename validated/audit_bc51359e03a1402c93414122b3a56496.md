Audit Report

## Title
Silent tip-loss on stale/invalid nonce in `snowbridge-pallet-system-v2::add_tip` — burned funds permanently unrecoverable - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

## Summary
`EthereumSystemV2::add_tip` never propagates the inner `AddTip::add_tip` error to the caller; on failure it just records the amount in `LostTips` and returns `Ok(())`. Because the corresponding Ether was already swapped and irreversibly burned on AssetHub in `snowbridge_pallet_system_frontend::add_tip` *before* the XCM `Transact` is even dispatched, any timing/race condition in nonce selection causes permanent, unrecoverable loss of the tip.

## Finding Description
The flow is: (1) user calls `system_frontend::add_tip` on AssetHub, which calls `swap_fee_asset_and_burn` → `burn_for_teleport`, irreversibly destroying the asset; (2) a best-effort, unpaid `Transact` XCM carrying `EthereumSystemCall::AddTip` is sent to BridgeHub; (3) `EthereumSystemV2::add_tip` dispatches to `InboundQueue::add_tip` (checks `Nonce::<T>::get(nonce)`) or `OutboundQueue::add_tip` (checks `PendingOrders`); (4) if the message has already been processed/delivered — a plausible race given independent, asynchronous relayer activity — `add_tip` returns an error; (5) `EthereumSystemV2::add_tip` swallows this error into `LostTips` and still returns `Ok(())`, so the extrinsic never reverts. The burn on AssetHub is unconditional and precedes any destination-side success confirmation, breaking atomicity between value destruction and crediting.

## Impact Explanation
This is a permanent user-fund loss: burned value on AssetHub has no atomic linkage to accounting on BridgeHub, and the only trace is a `LostTips` entry with no implemented recovery/claim mechanism, as explicitly noted in the storage doc comment.

## Likelihood Explanation
No malicious actor or privileged access is required — normal, unprivileged use of the public `add_tip` extrinsic under ordinary network timing (asynchronous relayer message processing racing against cross-chain XCM delivery) can trigger this loss, making it a realistic, repeatable condition rather than a contrived edge case.

## Recommendation
Do not burn/destroy the tip asset on AssetHub until the corresponding tip has been durably accepted on BridgeHub (e.g., reserve/hold and finalize burn only on confirmed success, refunding on failure), or implement the promised `LostTips` recovery/claim extrinsic now rather than leaving it as a documented future gap.

## Proof of Concept
1. On BridgeHub, a relayer submits a message with `nonce = N`, setting `Nonce::<T>::set(N)`.
2. Concurrently, the user on AssetHub calls `add_tip(MessageId::Inbound(N), tip_asset)`; `swap_fee_asset_and_burn` swaps and burns the funds.
3. The resulting XCM `Transact(AddTip{ message_id: Inbound(N), .. })` arrives at BridgeHub after step 1.
4. `InboundQueue::add_tip(N, amount)` finds `Nonce::<T>::get(N) == true`, returning `Err(AddTipError::NonceConsumed)` (analogous to `add_tip_inbound_fails_when_nonce_is_consumed`).
5. `EthereumSystemV2::add_tip` swallows the error into `LostTips::<T>::get(sender)` and returns `Ok(())`; the user's burned funds are permanently unrecoverable.
