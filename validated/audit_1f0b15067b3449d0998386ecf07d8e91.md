### Title
`freeze_collection`/item-`freeze` state is not enforced in `do_burn`, allowing item burns while frozen - (File: substrate/frame/uniques/src/functions.rs)

### Summary
`do_transfer` enforces both the collection-level freeze (`collection_details.is_frozen`) and the item-level freeze (`details.is_frozen`) in addition to the `T::Locker::is_locked` check before allowing a transfer. `do_burn`, however, only checks `T::Locker::is_locked` and never inspects `collection_details.is_frozen` or the item's own `is_frozen` flag. This means an item or collection that has been frozen via `freeze_collection`/`freeze` (blocking transfers) can still be destroyed via `burn`, which is one of the exact "lock layer consulted for one flow but ignored for another" patterns the question asks to look for.

### Finding Description
`do_transfer` performs the following checks before mutating ownership: [1](#0-0) 

- collection `is_frozen` → `Error::Frozen`
- `T::Locker::is_locked` → `Error::Locked`
- item `is_frozen` → `Error::Frozen`

`do_burn`, by contrast, only checks the external locker: [2](#0-1) 

There is no check of `collection_details.is_frozen` nor of `details.is_frozen` (the item's own frozen flag) anywhere in `do_burn`. Since `freeze_collection` sets `collection_details.is_frozen = true` and the item-level `freeze` extrinsic sets `ItemDetails.is_frozen = true` (the same fields checked in `do_transfer`), an item owner can simply call the public `burn` extrinsic to destroy an item that is supposed to be immovable/protected by a collection or item freeze — completely sidestepping the freeze invariant that `do_transfer` respects.

This breaks the stated invariant: "Any item blocked by lock, freeze, or wrapper constraints must remain unreachable through all public flows." Freeze is commonly used to protect items that are mid-listing/mid-escrow (e.g., combined with `ItemPriceOf`/`do_buy_item` flows) from being moved; being able to burn the item out from under that protection is a direct bypass of the intended guarantee, and destroys the underlying asset (with deposit unreserved) even though the freeze should have made it immutable.

### Impact Explanation
An item owner (an unprivileged, ordinary account — no elevated origin required) can burn any item they own even if the item or its containing collection has been frozen. This defeats the purpose of `freeze_collection`/`freeze`, whose entire design intent — as documented in `do_transfer`'s own doc comments — is that "the collection is frozen ... [and] the item is locked ... " should block state-changing operations. Any external system, marketplace, or protocol module that relies on freezing an item as a safety/anti-fraud mechanism (e.principle., freeze during sale, freeze during dispute, freeze to prevent collateral withdrawal) can have that item unilaterally destroyed by its owner, defeating the freeze guarantee and potentially destroying value that was supposed to be locked in place.

### Likelihood Explanation
High likelihood/trivial to trigger: no privileged operation, batching, or proxy trick is required. Any account that owns a frozen item (or an item in a frozen collection) can call the public `burn` extrinsic directly, which routes straight into `do_burn`, and the burn will succeed because `do_burn` never consults the `is_frozen` flags.

### Recommendation
Add the same freeze checks to `do_burn` that are already present in `do_transfer`: reject the burn with `Error::<T, I>::Frozen` if `collection_details.is_frozen` is true, and with `Error::<T, I>::Frozen` if the item's `details.is_frozen` is true (in addition to the existing `T::Locker::is_locked` check), unless burning while frozen is an explicitly intended design decision (in which case this should be documented clearly and audited against downstream integrations that assume freeze == fully immutable).

### Proof of Concept
1. Create a collection and mint an item to account `A` (`create_collection` + `mint`).
2. As the collection freezer/admin, call `freeze_collection(collection)` (or `freeze(collection, item)` for item-level freeze) — `collection_details.is_frozen` (or `details.is_frozen`) becomes `true`.
3. Attempt `transfer(collection, item, B)` as `A` — fails with `Error::Frozen`, confirming the freeze is enforced for transfers. [1](#0-0) 
4. As `A`, call the public `burn(collection, item, ...)` extrinsic — it succeeds because `do_burn` never checks `is_frozen` on either the collection or the item, only `T::Locker::is_locked`. [2](#0-1) 
5. The item is removed from storage (`Item::<T, I>::remove`), the deposit is unreserved, and the `Burned` event fires — demonstrating that the freeze protection was fully bypassed.

Note: I was unable to fully inspect the `burn` extrinsic wrapper in `substrate/frame/uniques/src/lib.rs` (only `do_burn` in `functions.rs` was confirmed) due to running out of tool calls; if the extrinsic-level wrapper adds an additional freeze check not present in `do_burn`, this would need to be re-verified, but based on the `do_burn` implementation itself, no such check exists at the storage-mutation layer.
