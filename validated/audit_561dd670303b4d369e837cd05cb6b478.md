### Title
Predictable, sequence-derived repository storage paths allow front-running to force `CreateRepository`/fork/import RPCs to fail - ([File: internal/praefect/datastore/repository_store.go])

### Summary
Praefect assigns every new repository's on-disk path (`replica_path`) deterministically from a single, cluster-wide monotonically increasing Postgres sequence. Because the derivation is a pure, secret-free function of that small integer, and Gitaly's actual repository-creation code path only performs a last-second "does this path already exist" check, an unprivileged user who can trigger repository creation (fork, project import, or any ordinary "create repository" action) can predict the storage path that will be assigned to a *different*, concurrently in-flight legitimate creation and pre-create a directory there. This forces the legitimate operation to fail with an `AlreadyExists` error — the same "front-run a one-time/idempotent precondition to force the victim's operation to revert" pattern described in the external report, just applied to Gitaly's repository storage-path allocation instead of an ERC-20 permit nonce.

### Finding Description
`PerRepositoryRouter.RouteRepositoryCreation` reserves a repository ID for every repository-creation RPC (`CreateRepository`, fork, import, etc.) via: [1](#0-0) 

That ID comes from a single, global, unauthenticated Postgres sequence shared by *all* virtual storages and *all* repositories in the cluster: [2](#0-1) 

The disk path (`replica_path`) is then derived **purely and deterministically** from that integer ID, with no secret or randomness involved — it's just `SHA256(id)` truncated to pick two subdirectory names, followed by the id itself: [3](#0-2) 

Because `ReserveRepositoryID` hands out strictly sequential integers (1, 2, 3, …) to any caller who triggers a repository-creation flow, an attacker can:
1. Repeatedly call `CreateRepository`/fork/import on repositories they control to consume sequence values and learn the current counter position.
2. Compute the exact future `replica_path` that will be assigned to the *next* reservation(s) — including one belonging to a different user's concurrent fork/import request whose ID has already been reserved but whose actual Gitaly-side directory has not yet been created.
3. Issue a `CreateRepository` (or equivalent) call directly to the target Gitaly node using that predicted `RelativePath`, creating a real directory there first.

On the Gitaly side, the actual repository materialization (`repoutil.Create`) only checks for a pre-existing directory right before it moves the fully-built repository into place — there is no binding between the reserved ID/path and an exclusive claim beyond this stat-and-lock check: [4](#0-3) 

When the path is already occupied, this deterministically returns `AlreadyExists("repository exists already")`, which is exactly the error surfaced to `CreateRepository`/import/fork RPCs when the target already exists: [5](#0-4) 

This closely mirrors the reported vulnerability class: a one-time state transition (a nonce/permit consumption in the original report; here, first-claim of a predictable storage path) has no binding to the legitimate caller, so any unprivileged party who can observe/predict the shared counter can consume it first and force the legitimate operation to permanently fail/revert.

### Impact Explanation
This is a griefing/DoS vector against legitimate repository-creation flows (fork, project import, or plain repository creation) cluster-wide. Any authenticated, unprivileged user capable of triggering repository creation on the same Praefect cluster can advance and predict the ID sequence and can grief specific concurrent creations by preemptively occupying the computed storage path, causing the victim's fork/import to fail with `AlreadyExists`. It does not lead to data corruption or cross-tenant object access, but it is a genuine functional-integrity/availability issue for a shared, security-relevant precondition (unique claim of a repository's storage location), consistent with the "low/DoS-of-handler" severity class of the original report.

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker needs to win a narrow race between the victim's `ReserveRepositoryID` call and the victim's actual Gitaly-side `CreateRepository` completing, and (2) the attacker must be able to observe or reliably predict the sequence's current value (trivial, since it is simply consumed by calling `ReserveRepositoryID` themselves and computing offsets) and target a specific victim operation, which requires some knowledge of when a victim's creation is in flight. This is plausible for scripted/automated abuse (e.g., griefing bulk import/fork jobs) but requires timing precision, so likelihood is moderate-to-low, similar to the "low risk, requires front-running" rating of the original finding.

### Recommendation
- Do not derive the physical storage path solely from a small, predictable, globally shared sequential integer that is exposed (even indirectly) to any client capable of triggering repository creation.
- Bind the reserved repository ID to the specific creation request atomically (e.g., have `ReserveRepositoryID` and the subsequent directory creation happen as a single distributed transaction/lease, or validate that the physical directory creation is scoped/authorized to the exact reservation, rejecting any directory that appeared through means other than the associated creation flow).
- Consider incorporating an unpredictable component (e.g., a per-reservation random suffix or token) into the physical path so that pre-creating the eventual path is infeasible without already knowing the reservation's private token.

### Proof of Concept
1. Attacker calls `CreateRepository` (or forks/imports a repo they control) repeatedly and observes the resulting `RepositoryId`/replica paths (or infers them from `storage.DeriveReplicaPath`), establishing the current value of `repositories_repository_id_seq`.
2. Attacker predicts the next sequence value `N+1` that will be assigned to a victim's concurrent fork/import request (whose `ReserveRepositoryID` call the attacker races against, e.g., by triggering their own creation immediately after observing the victim's request begin).
3. Attacker computes `replicaPath = storage.DeriveReplicaPath(N+1)` client-side using the public algorithm in `internal/gitaly/storage/repository_path.go`.
4. Attacker issues a direct Gitaly `CreateRepository` RPC with `RelativePath = replicaPath` on the corresponding storage node, materializing a repository at that exact path before the victim's flow gets there.
5. When the victim's fork/import subsequently calls Gitaly's `CreateRepository` with the same, now-reserved `replica_path`, `repoutil.Create` finds the directory already exists and returns `AlreadyExists("repository exists already")`, causing the victim's fork/import RPC to fail.

// ReserveRepositoryID reserves an ID for a repository that is about to be created and returns it. If a repository already
// exists with the given virtual storage and relative path combination, an error is returned.
func (rs *PostgresRepositoryStore) ReserveRepositoryID(ctx context.Context, virtualStorage, relativePath string) (int64, error) {
	var id int64
	if err := rs.db.QueryRowContext(ctx, `
SELECT nextval('repositories_repository_id_seq')
WHERE NOT EXISTS (
	SELECT FROM repositories
	WHERE virtual_storage = $1
	AND   relative_path   = $2
)
	`, virtualStorage, relativePath).Scan(&id); err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return 0, ErrRepositoryAlreadyExists
		}

		return 0, fmt.Errorf("scan: %w", err)
	}

	return id, nil
}

// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.
func DeriveReplicaPath(repositoryID int64) string {
	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}

func deriveDiskPath(prefixDir string, repositoryID int64) string {
	hasher := sha256.New()
	// String representation of the ID is used to make it easier to derive the replica paths with
	// external tools. The error is ignored as the hash.Hash interface is documented to never return
	// an error.
	hasher.Write([]byte(strconv.FormatInt(repositoryID, 10)))
	hash := hasher.Sum(nil)
	return filepath.Join(prefixDir, fmt.Sprintf("%x/%x/%d", hash[0:1], hash[1:2], repositoryID))
