## Title
Uncontrolled array allocation in TVM precompiled-contract signature helpers — `extractBytes32Array` / `extractBytesArray` (`PrecompiledContracts.java`)

## Summary
`PrecompiledContracts.java` contains helper routines that allocate arrays whose size is taken directly from a 256-bit word inside attacker-supplied precompile call data, before any bound check against the actual length of that data is performed. This mirrors the pypdf XMP advisory pattern: an untrusted length field drives a large allocation before the payload backing that length is validated, enabling memory exhaustion from a single crafted input.

## Finding Description
`extractBytes32Array` and `extractBytesArray` read an array length straight from `DataWord.intValueSafe()` and immediately allocate a Java array of that size: [1](#0-0) 

`intValueSafe()` returns any value that fits in 4 bytes (up to `Integer.MAX_VALUE`) as long as the encoded word occupies ≤4 bytes — it only clamps to `Integer.MAX_VALUE` on true overflow, so an attacker fully controls `len` up to hundreds of millions or more via calldata: [2](#0-1) 

The `new byte[len][]` / `new byte[bytes32Array.length][]` allocation happens **before** any per-element data availability is checked (the out-of-bounds check on `words[offset + i + 1]` only triggers inside the loop, after the top-level array object has already been created). A `len` in the tens/hundreds of millions causes the JVM to allocate an array of that many object-reference slots (8 bytes each on 64-bit JVMs) in one shot — hundreds of MB to multiple GB — independent of the actual size of the calldata supplied to the precompile call. This is functionally identical to the pypdf bug class: a size/length field embedded in otherwise-small untrusted input is trusted to drive a large upfront allocation, exhausting memory before the rest of the (small) payload is even validated.

These helpers are invoked from the multi-signature verification precompiled contracts (`ValidateMultiSign`/`BatchValidateSign` family) reachable from any TVM contract via a `CALL`/`STATICCALL` to the precompile address, i.e. from an unprivileged transaction/contract-call path.

## Impact Explanation
A crafted contract call (deployable and triggerable by any unprivileged account) that invokes the affected precompiled contract with a manipulated "array length" word can force the node to attempt a very large single-object allocation. Repeated or concurrent invocation from multiple transactions in a block can drive JVM heap pressure to the point of `OutOfMemoryError`, degrading or crashing node processes that are supposed to keep serving the network (validators/full nodes), which is a denial-of-service against chain liveness — analogous to the "node crash or halt" impact bar in scope.

## Likelihood Explanation
Likelihood is high for a determined attacker: the entry point is a plain contract call carrying attacker-chosen calldata, requires no special privileges, and the vulnerable code path (`extractBytes32Array`/`extractBytesArray`) performs the allocation immediately based on the attacker-controlled length word, with no upstream size cap tied to the actual calldata length before the allocation occurs.

## Recommendation
Before allocating `bytes32Array`/`bytesArray`, validate that `len` (and the derived `bytesOffset`/`bytesLen` per element) is consistent with the actual size of `data`/`words` — e.g. bound `len` by `(words.length - offset - 1)` and validate each element's offset/length against `data.length` prior to allocating the outer array, so array sizes can never exceed what the supplied calldata could plausibly contain.

## Proof of Concept
Construct calldata for the multi-signature precompiled contract (or any code path reaching `extractBytes32Array`/`extractBytesArray`) where the word at the "array length" offset is encoded as a large value (e.g. `0x00000000000000000000000000000000000000000000000000000005f5e100` ≈ 100,000,000) while the remainder of the calldata is only a few words long. Submitting this via a `TriggerSmartContract` that performs the corresponding `CALL` to the precompile address causes `extractBytes32Array`/`extractBytesArray` to execute `new byte[100_000_000][]` (≈800MB of reference slots on a 64-bit JVM) before any bounds failure is raised, independent of the small calldata actually transmitted.

Note: I was not able to fully trace, within the available iterations, the exact precompile dispatch method (energy-cost gating call site) that invokes these two helpers to confirm whether an energy charge proportional to `data.length` occurs strictly before the allocation in all code paths; this would need to be verified directly in the repository (e.g., via a Devin session) to confirm there is no earlier guard that rejects the oversized length before allocation.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
