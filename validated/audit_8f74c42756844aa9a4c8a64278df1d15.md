### Title
`mime/multipart.Writer.CreatePart` injects unsanitized header values, permitting multipart part/header injection - ([File: src/mime/multipart/writer.go])

### Summary
`mime/multipart.Writer.CreatePart` writes caller-supplied `textproto.MIMEHeader` key/value pairs directly into the multipart stream via `fmt.Fprintf(&b, "%s: %s\r\n", k, v)` with no check for embedded `\r`/`\n` in the header value [1](#0-0) . This mirrors the `eventsource-encoder` bug class: a field destined for a single line of a line-oriented wire protocol is interpolated without stripping/validating line terminators, letting an attacker who controls that field forge additional header lines or terminate the header section early inside a part.

### Finding Description
The higher-level convenience wrappers `CreateFormFile` and `CreateFormField` build the `Content-Disposition` value through `escapeQuotes`, which percent-encodes `\r` and `\n` (`quoteEscaper` includes `"\r", "%0D", "\n", "%0A"`), so field/file names are safe [2](#0-1) .

However, `CreatePart` — the lower-level, directly reachable public API that both of those wrappers ultimately call — takes an arbitrary `textproto.MIMEHeader` and serializes it verbatim:
```go
for _, k := range slices.Sorted(maps.Keys(header)) {
    for _, v := range header[k] {
        fmt.Fprintf(&b, "%s: %s\r\n", k, v)
    }
}
``` [3](#0-2) 

Neither the key nor the value is checked for `\r`/`\n`/CTL bytes here, unlike `net/http.Header.writeSubset`, which explicitly strips embedded newlines from header values before writing (`headerNewlineToSpace.Replace(v)`) [4](#0-3) , and unlike `net/smtp`'s `validateLine` guard used before every line-oriented command [5](#0-4) .

Attack path: an application that builds a multipart request/response by calling `mw.CreatePart(header)` with a `textproto.MIMEHeader` populated (even partially) from untrusted input — e.g., a user-supplied filename, form field name, or arbitrary extra header value forwarded into a proxy/gateway that assembles multipart bodies — can inject `\r\n` into that value. Because `CreatePart` performs no sanitization, the injected CRLF(s) terminate the current header line, and a further blank line (`\r\n\r\n`) terminates the header block early, allowing the attacker to inject a forged header field, or to inject content directly into what the receiving multipart parser will interpret as the beginning of the part body — effectively smuggling additional header fields or corrupting part boundaries within the part they control.

### Impact Explanation
If an application uses `multipart.Writer.CreatePart` with any header field value influenced by untrusted/user input (a realistic pattern for services that proxy uploads, build synthetic multipart requests from stored metadata, or expose "custom header" fields to end users), the attacker can inject additional MIME headers into their own part (e.g. override `Content-Type`, inject headers a downstream MIME/HTTP intermediary might trust) or terminate the header section early to smuggle bytes into the body region the parser expects. This is a header/protocol-injection issue analogous to CWE-113/CWE-93 in the report — integrity of the generated multipart message is compromised. It does not, by itself, achieve code execution, but it can be used to violate the integrity assumptions of any downstream consumer that trusts headers set by the writer versus the caller (e.g. bypassing an intended `Content-Type` restriction, or injecting spoofed metadata fields consumed by a backend). This would likely fall on Go's PUBLIC track as a low/medium-severity documentation-and-hardening class issue rather than urgent, since the exploitability depends entirely on an application feeding untrusted data into raw header values via the lower-level `CreatePart` API rather than the sanitized `CreateFormField`/`CreateFormFile`/`WriteField` helpers.

### Likelihood Explanation
Requires a victim workflow where the application passes attacker-controlled data into a `textproto.MIMEHeader` used with `CreatePart` (rather than the safe wrappers). This is a plausible but not universal pattern — many callers use `CreateFormField`/`CreateFormFile`, which are safe. I could not find a production caller within this repository itself that passes untrusted data through `CreatePart` (the only in-repo callers are in `net/http/fs.go` and tests, which do not appear to use attacker-controlled values) [6](#0-5) . The vulnerability is therefore in the API surface and depends on how external application code (outside this repository) consumes it — I was not able to fully confirm an in-scope, reachable, unprivileged attack path purely within this repo, which weakens confidence in this being a directly exploitable production issue in the codebase as scoped.

### Recommendation
In `CreatePart`, sanitize or reject header field values containing `\r` or `\n` before writing (mirroring `net/http.Header`'s `headerNewlineToSpace` behavior or outright returning an error, consistent with the `net/smtp.validateLine` pattern), rather than relying on callers to pre-escape values only when using `CreateFormField`/`CreateFormFile`.

### Proof of Concept
```go
package multipart

import (
	"bytes"
	"net/textproto"
	"strings"
	"testing"
)

func TestCreatePartHeaderInjection(t *testing.T) {
	var buf bytes.Buffer
	w := NewWriter(&buf)

	h := make(textproto.MIMEHeader)
	// Attacker-controlled value flowing into a header used with CreatePart
	h.Set("X-Custom", "safe\r\nX-Injected: evil")

	if _, err := w.CreatePart(h); err != nil {
		t.Fatal(err)
	}
	w.Close()

	out := buf.String()
	// Expect the injected header NOT to appear as a separate line;
	// currently it does, demonstrating the injection.
	if strings.Contains(out, "\r\nX-Injected: evil\r\n") {
		t.Fatalf("header injection succeeded, output:\n%q", out)
	}
}
```
Expected (patched) behavior: the test should pass because the encoder rejects or escapes the embedded `\r\n`. Currently, `fmt.Fprintf(&b, "%s: %s\r\n", k, v)` writes the value unmodified, so the injected `X-Injected: evil` line appears verbatim in the output, confirming the finding.

// CreatePart creates a new multipart section with the provided
// header. The body of the part should be written to the returned
// [Writer]. After calling CreatePart, any previous part may no longer
// be written to.
func (w *Writer) CreatePart(header textproto.MIMEHeader) (io.Writer, error) {
	if w.lastpart != nil {
		if err := w.lastpart.close(); err != nil {
			return nil, err
		}
	}
	var b bytes.Buffer
	if w.lastpart != nil {
		fmt.Fprintf(&b, "\r\n--%s\r\n", w.boundary)
	} else {
		fmt.Fprintf(&b, "--%s\r\n", w.boundary)
	}

	for _, k := range slices.Sorted(maps.Keys(header)) {
		for _, v := range header[k] {
			fmt.Fprintf(&b, "%s: %s\r\n", k, v)
		}
	}
	fmt.Fprintf(&b, "\r\n")
	_, err := io.Copy(w.w, &b)
	if err != nil {
		return nil, err
	}
	p := &part{
		mw: w,
	}
	w.lastpart = p
	return p, nil
}

var quoteEscaper = strings.NewReplacer("\\", "\\\\", `"`, "\\\"", "\r", "%0D", "\n", "%0A")

// escapeQuotes escapes special characters in field parameter values.
//
// For historical reasons, this uses \ escaping for " and \ characters,
// and percent encoding for CR and LF.
//
// The WhatWG specification for form data encoding suggests that we should
// use percent encoding for " (%22), and should not escape \.
// https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#multipart/form-data-encoding-algorithm
//
// Empirically, as of the time this comment was written, it is necessary
// to escape \ characters or else Chrome (and possibly other browsers) will
// interpet the unescaped \ as an escape.
func escapeQuotes(s string) string {
	return quoteEscaper.Replace(s)
}

// CreateFormFile is a convenience wrapper around [Writer.CreatePart]. It creates
// a new form-data header with the provided field name and file name.
func (w *Writer) CreateFormFile(fieldname, filename string) (io.Writer, error) {
	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition", FileContentDisposition(fieldname, filename))
	h.Set("Content-Type", "application/octet-stream")
	return w.CreatePart(h)
}

// CreateFormField calls [Writer.CreatePart] with a header using the
// given field name.
func (w *Writer) CreateFormField(fieldname string) (io.Writer, error) {
	h := make(textproto.MIMEHeader)
	h.Set("Content-Disposition",
		fmt.Sprintf(`form-data; name="%s"`, escapeQuotes(fieldname)))
	return w.CreatePart(h)
}

// FileContentDisposition returns the value of a Content-Disposition header
// with the provided field name and file name.
func FileContentDisposition(fieldname, filename string) string {
	return fmt.Sprintf(`form-data; name="%s"; filename="%s"`,
		escapeQuotes(fieldname), escapeQuotes(filename))
}
