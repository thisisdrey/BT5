### Title
`rlp_execute` on the ETH-implicit Wallet Contract silently absorbs unaccounted attached deposit into contract balance without tracking, unlike a true `payable`-with-use pattern - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
The `WalletContract::rlp_execute` entry point is marked `#[payable]` [1](#0-0) . The Hats report's bug class is about `payable` functions that don't fully account for the attached native currency. Here, the contract only tracks the caller's deposit via `CallerDeposit::new`, which explicitly **returns `None`** whenever the call is self-originated (`current_account_id == predecessor_account_id`), and additionally only tracks deposit for refund purposes on cross-contract call *failure*, not for every code path [2](#0-1) .

### Finding Description
In `inner_rlp_execute`, `CallerDeposit::new(&context)` is computed once from the attached deposit at entry [3](#0-2) . This `Option<CallerDeposit>` is threaded through the various promise-building branches and is only consulted in `rlp_execute_callback` — and only in the `PromiseResult::Failed` branch, where it triggers a refund transfer back to the original caller [4](#0-3) . On the `PromiseResult::Successful` branch, `caller_deposit` is simply dropped without any transfer — the deposit is assumed to have been consumed by the underlying action (e.g. as part of a `TransferAction`/`FunctionCallAction` deposit via `Action::try_into_near_action`'s `additional_value` mechanism) [5](#0-4) .

However, several early-return paths in `rlp_execute`/`inner_rlp_execute` do not go through `rlp_execute_callback` at all: the "transaction already in progress" early return [6](#0-5) , and the parse-error paths that return `Err(e)` directly without constructing any promise [7](#0-6) . In `rlp_execute`, any `Err(e)` (other than the specific relayer-ban case) is converted straight to `PromiseOrValue::Value(e.into())` [8](#0-7) . In all of these cases, an external, non-self caller's attached deposit (captured by `env::attached_deposit()`) is credited to the wallet contract's account balance by the NEAR protocol itself (deposits are always credited to the receiver's balance regardless of contract logic), but the contract never issues a refund and never uses the deposit for any action.

### Impact Explanation
Because the eth-implicit Wallet Contract account has **no full-access key** — it can only act through the validated `rlp_execute` logic path, gated by the Ethereum-transaction signature check — any yoctoNEAR deposited by an external caller (not the account owner/relayer) that lands in one of these silent-drop paths becomes effectively unrecoverable through the wallet's normal operation, since there is no code path that inspects a stranded `CallerDeposit` outside of the promise-failure callback. This differs from an ordinary NEAR account, where a stray deposit could always be withdrawn by the holder of a full-access key. This matches the "permanent freezing of funds" impact bar, though the affected value in these specific early-return branches is attacker/relayer-caller controlled and would typically be non-zero only if a relayer mistakenly (or the user directly) attaches a deposit that hits one of the pre-promise error branches.

### Likelihood Explanation
Likelihood is low-to-medium in practice: `test_caller_refunds` in the test suite demonstrates the developers are aware of and test the primary failure-refund path [9](#0-8) , and comments in the code show deliberate design around not incrementing nonces / relayer trust for early-error branches, but none of the tests exercise deposit refunding for the parse-error or in-flight-collision early returns specifically. This requires an external (non-owner) caller to attach a deposit while triggering one of these edge conditions, which is an unusual but reachable interaction (e.g. a user calling `rlp_execute` on someone else's wallet with a deposit attached during a race where a transaction is already in-flight).

### Recommendation
Audit every early-return branch of `rlp_execute`/`inner_rlp_execute` (the in-flight check, and all `Err` returns from `parse_rlp_tx_to_action`) to ensure that whenever `CallerDeposit::new` would have captured a non-zero, non-self deposit, that deposit is refunded to `predecessor_account_id` before returning `PromiseOrValue::Value`, mirroring the refund behavior already implemented in `rlp_execute_callback`'s failure branch.

### Proof of Concept
Not independently verified with a running test; based on static code-path analysis: an external account calls `rlp_execute` on a wallet contract that already has `has_in_flight_tx == true` while attaching a deposit — the deposit is credited to the wallet's balance by the protocol, and the function returns `PromiseOrValue::Value` at [6](#0-5)  without ever constructing a `CallerDeposit` or issuing a refund.

// An external caller gets its deposit back if the cross-contract call fails.
#[tokio::test]
async fn test_caller_refunds() -> anyhow::Result<()> {
    let TestContext { worker, wallet_contract, wallet_sk, address_registrar, .. } =
        TestContext::new().await?;

    let caller = worker.root_account()?;
    let deposit_amount = NearToken::from_near(3);
    let create_tx = |receiver_id: &AccountId, nonce: u64| {
        let method = "register";
        let args = br#"{"account_id": "birchmd.near"}"#;
        let action = Action::FunctionCall {
            receiver_id: receiver_id.to_string(),
            method_name: method.into(),
            args: args.to_vec(),
            gas: Gas::from_tgas(10).as_gas(),
            yocto_near: 0,
        };
        utils::create_signed_transaction(
            nonce,
            receiver_id,
            Wei::new_u128(deposit_amount.as_yoctonear() / (MAX_YOCTO_NEAR as u128)),
            action,
            &wallet_sk,
        )
    };

    // External caller gets a refund when the cross-contract call fails
    let pre_tx_account_balance = caller.view_account().await?.balance;
    let receiver_id: AccountId = "fake.near".parse()?;
    let result = wallet_contract
        .rlp_execute_from(
            &caller,
            receiver_id.as_str(),
            &create_tx(&receiver_id, 0),
            deposit_amount,
        )
        .await?;
    assert!(!result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            < deposit_amount.as_yoctonear()
    );

    // External caller does not get a refund when their tokens are spent
    let pre_tx_account_balance = post_tx_account_balance;
    let receiver_id = address_registrar.id();
    let result = wallet_contract
        .rlp_execute_from(&caller, receiver_id.as_str(), &create_tx(receiver_id, 1), deposit_amount)
        .await?;
    assert!(result.success);
    let post_tx_account_balance = caller.view_account().await?.balance;
    assert!(
        pre_tx_account_balance.as_yoctonear() - post_tx_account_balance.as_yoctonear()
            >= deposit_amount.as_yoctonear()
    );

    Ok(())
}
