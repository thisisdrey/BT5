### Title
Postponed action receipt surviving `DeleteAccount` bypasses `check_actor_permissions` on a recreated account with the same name - (File: runtime/runtime/src/actions.rs)

### Summary
`action_delete_account`/`remove_account` delete the `Account`, access keys and contract data for a deleted account, but leave `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` trie rows keyed by that account name untouched. If the same account name is later recreated by an unrelated principal, the stale postponed receipt (created by the original, now-different, owner) can still be released by a `Data` receipt and executed against the new account, because `check_actor_permissions` and `apply_action_receipt` derive `actor_id`/`account_id` purely from strings with no notion of account identity/incarnation.

### Finding Description
`process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) stores an action receipt with unmet `input_data_ids` as a `PostponedReceipt` keyed by `(receiver_id, receipt_id)`, plus a `PendingDataCount` and `PostponedReceiptId` link. None of these rows reference an account "version" or creation nonce — only the plain `AccountId` string.

When the attacker's own account `A` self-deletes via `DeleteAccount`, `check_actor_permissions` allows it because `actor_id == account_id == A` (self-delete, `runtime/runtime/src/actions.rs:761-776`), and `action_delete_account` calls `remove_account` (`core/store/src/utils/mod.rs:505-575`), which removes the `Account`, `ContractCode`, access keys, gas-key nonces, and contract data — but not the postponed-receipt bookkeeping keys, since `remove_account` has no knowledge of them.

If account `A` is later recreated (by the parent account for a subaccount, or any predecessor for a sufficiently long top-level name, per `action_create_account`, `runtime/runtime/src/actions.rs:167-210`), the stale `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` rows for `A` are still present. When the attacker (who created the original data dependency before deleting `A`) later delivers the matching `Data` receipt, `process_receipt`'s Data arm (`runtime/runtime/src/lib.rs:1398-1455`) finds the link, decrements the pending count to 0, fetches the stale `PostponedReceipt`, removes the bookkeeping, and calls `apply_action_receipt` on it. There, `actor_id` is freshly set to `receipt.predecessor_id()` (`runtime/runtime/src/lib.rs:855`), which is still the literal string `A` from the original receipt. `check_actor_permissions` for `AddKey` only compares `actor_id != account_id` (`runtime/runtime/src/actions.rs:746-760`); since both are the string `A`, the check trivially passes even though the account currently occupying `A` belongs to a different party, and `action_add_key` installs the attacker's planted full-access key onto the new owner's account.

### Impact Explanation
This breaks the "a promise must not carry privileges its creator did not hold over the current occupant of the name" invariant, allowing authorization escalation across accounts that happen to share a recycled name, and subsequent fund theft (planted `FullAccessKey` + `Transfer`) from the new legitimate owner. This matches NEAR's bounty category for authorization escalation across accounts/promises and fund theft.

### Likelihood Explanation
The attacker fully controls the postponed-receipt creation, the self-`DeleteAccount`, and the timing of satisfying the data dependency — all via ordinary unprivileged transactions/contracts. The one precondition outside attacker control is that a distinct, unrelated party independently recreates the exact same account name after deletion — realistic for a subaccount recreated by its (unwitting) parent, or a long top-level account name re-registered by anyone, but not attacker-forceable. This narrows likelihood to scenarios involving name reuse, which is a documented/expected occurrence on NEAR (deleted account names can be re-registered).

### Recommendation
When `action_delete_account`/`remove_account` deletes an account, also purge any outstanding `PostponedReceipt`, `PendingDataCount`, and `PostponedReceiptId` entries keyed by that `account_id` (failing the still-pending receipts, e.g. by generating failure outcomes/refunds), so no orphaned postponed receipt can survive into a subsequently recreated account of the same name.

### Proof of Concept
Runtime apply-path integration test (`runtime/runtime/src/tests/apply.rs`-style, similar to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create account `A` (owned by attacker) and a helper account `H`.
2. Have `A` produce a receipt `A -> A` containing `Action::AddKey(FullAccessKey(pub_key_planted))` with `input_data_ids: [data_id]` (no matching `ReceivedData` yet) — apply it so it is stored as a `PostponedReceipt`.
3. Apply a `DeleteAccount` receipt on `A` (self-delete, beneficiary arbitrary) — assert account `A` no longer exists.
4. Apply a `CreateAccount` receipt recreating `A` from an unrelated predecessor (e.g. `A`'s parent, if `A` is a subaccount) — assert `A` exists fresh with no access keys.
5. Deliver a `Data` receipt to `A` with the matching `data_id` — this should trigger `process_receipt`'s Data arm to look up and execute the stale `PostponedReceipt`.
6. Assert: expected/fixed behavior — `get_access_key(state_update, &A, &pub_key_planted)` returns `None` (i.e., the planted key must not be installed on the recreated account). Currently (bug present) this assertion fails because the key gets added, demonstrating the escalation.
