### Title
Remote peer can serve oversized `Attachment.content` via `GetAttachmentResponse`, bypassing `attachments_max_size` and causing unbounded SQLite BLOB writes - (File: stackslib/src/net/atlas/download.rs, stackslib/src/net/atlas/db.rs)

### Summary
`AtlasDB::should_keep_attachment` is the only place that enforces `attachments_max_size` against `attachment.content.len()`, but it is only invoked on the local mempool-ingestion path (e.g. `posttransaction.rs`). The P2P download path (`AttachmentsBatchStateContext::extend_with_attachments` in `download.rs`, feeding into `AtlasDB::insert_instantiated_attachment` in `db.rs`) writes peer-supplied `GetAttachmentResponse` content straight into the `attachments` SQLite table with no size check at all.

### Finding Description
`should_keep_attachment` (`stackslib/src/net/atlas/db.rs:249-266`) performs two checks: contract membership and `attachment.content.len() as u32 > self.atlas_config.attachments_max_size`. This function is only called from the RPC/mempool ingestion path that handles locally-submitted attachments (e.g. `posttransaction.rs`). `insert_instantiated_attachment` (`stackslib/src/net/atlas/db.rs:576-592`) contains no equivalent size guard — it directly executes `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 1, ?)` with the attachment's raw content and commits.

The P2P attachment-download flow (`AttachmentsBatchStateContext::extend_with_attachments`, `download.rs:530-558`) inserts `GetAttachmentResponse` content received from a remote peer into `self.attachments`, and this content subsequently flows into `insert_instantiated_attachment` without ever routing through `should_keep_attachment`. The download logic verifies that the returned content's hash matches the expected `content_hash` recorded in the on-chain `AttachmentInstance`, but does not enforce any bound on the content's length before persisting it.

Because content size is determined entirely by whatever the attacker committed as `content_hash` on-chain (the attacker chooses arbitrary content and derives the hash themselves before submitting the triggering transaction), the attacker fully controls the size of the blob eventually fetched and written to disk via the P2P response path — completely independent of the size gate meant to protect the local `attachments` table.

### Impact Explanation
A malicious peer (or any party controlling the origin server of an `AttachmentInstance`) can cause the receiving node to write arbitrarily large BLOBs into its SQLite `attachments` table each time it resolves a pending attachment instance via the download state machine, exhausting disk space and increasing SQLite I/O cost with no size ceiling — despite `attachments_max_size` being configured specifically to prevent this. This is a storage-write / bounded-compute DoS reachable purely through the P2P attachment-download path, repeatable for every attachment instance the attacker seeds on-chain.

### Likelihood Explanation
Preconditions: the attacker needs only to get an `AttachmentInstance` (with an oversized off-chain content whose hash they compute themselves) registered so a node's downloader queues it, then serve the corresponding `GetAttachmentResponse` when requested. No privileged role, secret, or special peer status is required — this fits the unprivileged remote-attacker model exactly, and is exploitable repeatedly.

### Recommendation
Enforce `attachments_max_size` (and ideally the contract check) inside `insert_instantiated_attachment` itself, or explicitly call `should_keep_attachment`-equivalent logic in `extend_with_attachments` before content is retained/persisted, rejecting any `GetAttachmentResponse` content whose length exceeds `atlas_config.attachments_max_size` prior to storage.

### Proof of Concept
Rust test plan (in `stackslib/src/net/atlas/tests.rs`):
1. Construct `AtlasConfig` with small `attachments_max_size` (e.g. 10 bytes).
2. Create an `AttachmentInstance` with `content_hash = Hash160::from_data(&oversized_content)` where `oversized_content.len() > attachments_max_size`.
3. Simulate a `GetAttachmentResponse` carrying `oversized_content` and feed it into `AttachmentsBatchStateContext::extend_with_attachments`.
4. Drive the state machine so the resolved attachment reaches `AtlasDB::insert_instantiated_attachment`.
5. Query `SELECT content FROM attachments WHERE hash = ?` and assert the stored content length equals `oversized_content.len()`, exceeding `attachments_max_size`, and assert `should_keep_attachment` was never invoked on this path (e.g., via a spy/counter or by confirming the DB accepted content that `should_keep_attachment` would reject).
