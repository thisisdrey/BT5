## Title
Stale Stake-Based QoS Allocation Enables Throughput QoS Evasion on Long-Lived QUIC Connections - (File: `streamer/src/nonblocking/swqos.rs`)

### Summary
The QUIC streamer's stake-weighted QoS controller (`SwQos`) computes a connection's `peer_type` and `total_stake` exactly once, at connection-establishment time, in `build_connection_context`. This snapshot is cached in `SwQosConnectionContext` and reused for the entire lifetime of the connection to gate both the maximum concurrent uni-streams and the per-interval stream throttling quota. Just as `market_two::modify_market_setting` changed the farm emission rate without first calling `increase_share_indexes` to reconcile the reward accumulator, the validator's QUIC path changes the *effective* total-stake distribution every epoch without updating the already-open connection's cached QoS parameters.

### Finding Description
`build_connection_context` is invoked once per new connection and derives `peer_type`/`total_stake` from a stake snapshot: [1](#0-0) 

That context is then stored (`in_staked_table`, `stream_counter`, etc. populated) and reused indefinitely by `cache_new_connection`, which derives `max_uni_streams` from the stale `rtt_millis`/`peer_type`/`total_stake` triple and calls `connection.set_max_concurrent_uni_streams` only once at connection setup: [2](#0-1) 

Every subsequent stream on that connection is throttled via `on_new_stream`, which again reads the same cached, unrefreshed `context.peer_type()`/`context.total_stake` to compute `max_streams_per_throttling_interval`: [3](#0-2) [4](#0-3) 

There is no mechanism in `SwQos`/`SwQosConnectionContext` (nor in `StakedStreamLoadEMA`, which only tracks aggregate EMA load, not per-connection stake) that re-derives `peer_type`/`total_stake` for an already-established connection as stake changes epoch to epoch. `total_stake` and per-peer stake are sourced from `staked_nodes` (`get_connection_stake`), which is refreshed by the leader/gossip stake-lookup pipeline over time, but only newly-accepted connections consult it.

### Impact Explanation
This is functionally the same bug class as the reported DeFi issue: a rate/weight parameter (`emission_rate` / `total_stake`) changes, but the entity that should be re-evaluated against the new rate (`share index` / `per-connection stake weight`) is never recomputed for already-active participants. Concretely:

- A peer that holds significant stake at connection time is granted a proportionally large `max_uni_streams` and `max_streams_per_throttling_interval` quota.
- If that peer's stake is subsequently reduced or fully undelegated (deactivated) in a later epoch while keeping the QUIC connection open, it continues to consume the *original*, now-unearned high-throughput quota for as long as the connection stays alive.
- Conversely, `total_stake` used in the ratio `stake / total_stake` also drifts as the overall staked set changes; a connection opened when total stake was low get an inflated share that is never re-normalized against the new total.

The net effect is QoS evasion: an unprivileged network peer can lock in favorable throughput allocation by opening a connection while stake conditions are favorable and keeping it alive, denying fair capacity to genuinely-staked, currently-participating validators/peers — the exact "QoS evasion" impact category called out as in-scope.

### Likelihood Explanation
Any unprivileged client reachable over the TPU/QUIC port can trigger this by simply establishing and holding open a QUIC connection across an epoch boundary (or across any stake-set update) — no special role or validator/operator privilege is required, and QUIC connections are commonly kept alive for extended periods by legitimate high-throughput clients, making prolonged connection lifetimes a normal, expected occurrence rather than an edge case.

### Recommendation
Periodically (e.g., alongside `StakedStreamLoadEMA::update_ema_if_needed`, or on an epoch-boundary/stake-map refresh signal) re-derive `peer_type`/`total_stake` for existing connections from the current `staked_nodes` snapshot, and re-apply `set_max_concurrent_uni_streams` and refresh the throttling quota used in `max_streams_per_throttling_interval` — analogous to calling `increase_share_indexes` before applying a new rate. At minimum, cap the maximum lifetime a connection may retain its original stake-derived QoS snapshot before being forced to re-negotiate.

### Proof of Concept
1. Have keypair `K` with high stake `S_high` at epoch `E`.
2. Open a QUIC connection to the validator's TPU port; `build_connection_context`/`cache_new_connection` grant `max_uni_streams` and a throttling quota proportional to `S_high / total_stake_E`.
3. Deactivate/withdraw `K`'s stake so that at epoch `E+1` its effective stake is ~0, while keeping the already-established QUIC connection alive (no new connection is created, so `build_connection_context` is never re-invoked).
4. Continue opening streams on the existing connection; `on_new_stream`/`max_streams_per_throttling_interval` still uses the epoch-`E` cached `total_stake`/`peer_type`, so the now-unstaked peer keeps consuming the high-throughput quota indefinitely, starving legitimately-staked peers of their fair share of streaming capacity.

impl QosController<SwQosConnectionContext> for SwQos {
    fn build_connection_context(&self, connection: &Connection) -> SwQosConnectionContext {
        let remote_address = connection.remote_address();
        get_connection_stake(connection, &self.staked_nodes).map_or(
            SwQosConnectionContext {
                peer_type: ConnectionPeerType::Unstaked,
                total_stake: 0,
                remote_pubkey: None,
                in_staked_table: false,
                remote_address,
                stream_counter: None,
                last_update: Arc::new(AtomicU64::new(timing::timestamp())),
            },
            |(pubkey, stake, total_stake)| {
                // The heuristic is that the stake should be large enough to have 1 stream pass through within one throttle
                // interval during which we allow max (MAX_STREAMS_PER_MS * STREAM_THROTTLING_INTERVAL_MS) streams.

                let peer_type = {
                    let max_streams_per_ms = self.staked_stream_load_ema.max_streams_per_ms();
                    let min_stake_ratio =
                        1_f64 / (max_streams_per_ms * STREAM_THROTTLING_INTERVAL_MS) as f64;
                    let stake_ratio = stake as f64 / total_stake as f64;
                    if stake_ratio < min_stake_ratio {
                        // If it is a staked connection with ultra low stake ratio, treat it as unstaked.
                        ConnectionPeerType::Unstaked
                    } else {
                        ConnectionPeerType::Staked(stake)
                    }
                };
