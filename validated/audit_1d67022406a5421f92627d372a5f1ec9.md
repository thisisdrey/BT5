## Finding: Unbounded recursive tree walk in `GetTreeEntries` can stack-overflow and crash a Gitaly node

### Title
Unbounded recursion in `TreeEntry.Walk`/`TreeEntry.walk` enables attacker-controlled stack-overflow DoS via `GetTreeEntries` - (File: `internal/git/localrepo/tree.go`)

### Summary
The Stellar `rs-soroban-env` report addresses missing depth limiting on recursive host operations that could exhaust the call stack. Gitaly has an analogous unbounded-recursion pattern: `TreeEntry.walk` recurses once per nesting level of a Git tree with no depth cap, and it is reachable from the `GetTreeEntries` RPC whenever a client requests recursive listing. Because any user with push access can construct a repository with an arbitrarily deep chain of nested tree objects (trivial via `git mktree`/`hash-object`, no server-side limit exists on tree nesting depth), a subsequent `GetTreeEntries(Recursive=true)` call against that ref will recurse to the same depth and can trigger Go's fatal, unrecoverable "goroutine stack exceeds … limit" error, crashing the whole `gitaly` process.

### Finding Description
`TreeEntry.walk` performs unbounded depth-first recursion over the in-memory tree structure: [1](#0-0) 

This structure is populated by `TreeEntry.populate`, which reads `git ls-tree -r` output and builds nested `TreeEntry` objects using an explicit stack (not Go-level recursion), so the object graph itself can be arbitrarily deep with no size/depth check: [2](#0-1) 

`repo.ReadTree` invokes `populate` when the `WithRecursive()` option is set: [3](#0-2) 

The `CommitService.GetTreeEntries` RPC handler calls `repo.ReadTree(... WithRecursive())` followed directly by `tree.Walk(...)` whenever the client sets `Recursive: true` on the request — a normal, unprivileged, client-controlled request parameter: [4](#0-3) [5](#0-4) 

Unlike the `AlternateObjectDirectories`/`altObjectDirs` recursion elsewhere in the codebase, which explicitly caps depth at `maxAlternatesDepth` (5) to defend against exactly this class of issue: [6](#0-5) 

...there is no analogous depth cap anywhere in the `TreeEntry` recursion path (`populate`, `walk`/`Walk`, or `Write`). Git itself imposes no server-side limit on tree nesting depth, so a user with ordinary push access can create a commit whose tree references a chain of single-entry subtrees nested to an arbitrary depth (e.g., hundreds of thousands of levels), entirely client-side, using standard plumbing commands, then push it to the Gitaly-backed repository.

### Impact Explanation
Go grows goroutine stacks dynamically but enforces a hard ceiling (`runtime/debug.SetMaxStack`, defaulting to 1 GiB). Exceeding it is a **fatal runtime error**, not a recoverable panic — it terminates the entire process, not just the offending goroutine/RPC. Since Gitaly is typically a shared multi-tenant service handling many repositories per node, one attacker-crafted repository can crash the process and take down `GetTreeEntries` (and any other in-flight RPCs) for every repository hosted on that node — a repository-agnostic denial of service.

### Likelihood Explanation
The attack requires only: (1) ordinary push/write access sufficient to create arbitrarily deep tree objects (achievable with a handful of `git hash-object -t tree --stdin` / `git mktree` invocations scripted to chain depth), and (2) invoking the already-existing, commonly used `GetTreeEntries` RPC with `Recursive: true` against that ref — a standard read operation exposed to any client with read access (e.g., GitLab's file browser view uses recursive tree listing). No special privileges, races, or MITM conditions are needed, making this readily reachable by an ordinary authenticated user.

### Recommendation
Introduce an explicit maximum tree-nesting depth (analogous to `maxAlternatesDepth` in `internal/git/dirs.go`) enforced in `TreeEntry.populate` (reject/truncate when the `ls-tree` path depth exceeds the limit) and/or convert `TreeEntry.walk`/`Write` to iterative (stack-based) traversal instead of native Go recursion, so recursion depth is decoupled from attacker-controlled tree depth. Additionally, consider bounding recursion depth in `TreeEntry.Write` (`internal/git/localrepo/tree.go:564-589`), which has the same unbounded recursive pattern for the write path (e.g., `UserCommitFiles`).

### Proof of Concept
1. As a user with push access, create a repository and construct a chain of N (e.g. 500,000) single-entry nested tree objects using `git hash-object -t tree --stdin` repeatedly, each tree's single entry pointing to the previously created tree, terminating in a commit that references the outermost tree.
2. Push this ref to the Gitaly-backed repository.
3. Call `CommitService.GetTreeEntries` with `Recursive: true` against the pushed commit.
4. `repo.ReadTree` → `populate` builds the N-deep `TreeEntry` graph, then `tree.Walk` → `walk` recurses N times on the Go call stack, eventually exceeding the goroutine stack limit and fatally crashing the `gitaly` process, terminating service for all repositories on that node.

// populate scans through the output of ls-tree -r, and constructs a TreeEntry
// object.
func (t *TreeEntry) populate(
	ctx context.Context,
	repo *Repo,
) error {
	if t.OID == "" {
		return errors.New("oid is empty")
	}

	t.Entries = nil

	entries, err := repo.listEntries(
		ctx,
		git.Revision(t.OID),
		"",
		true,
	)
	if err != nil {
		return err
	}

	stack := treeStack{t}

	// The output of ls-tree -r is the following:
	// a1
	// dir1/file2
	// dir2/file3
	// f2
	// f3
	// Whenever we see a tree, push it onto the stack since we will need to
	// start adding to that tree's entries.
	// When we encounter an entry that has a lower depth than the previous
	// entry, we know that we need to pop the tree entry off to get back to the
	// parent tree.
	for _, entry := range entries {
		if levelsToPop := len(stack) - depthByPath(entry.Path); levelsToPop > 0 {
			for i := 0; i < levelsToPop; i++ {
				stack.pop()
			}
		}

		entry.Path = filepath.Base(entry.Path)
		stack.peek().Entries = append(
			stack.peek().Entries,
			entry,
		)

		if entry.Type == Tree {
			stack.push(entry)
		}
	}

	if err != nil {
		return fmt.Errorf("listing entries: %w", err)
	}

	return nil
}

func (t *TreeEntry) walk(dirPath string, callback func(path string, entry *TreeEntry) error) error {
	nextDirPath := filepath.Join(dirPath, t.Path)
	if err := callback(dirPath, t); err != nil {
		return err
	}

	for _, entry := range t.Entries {
		if err := entry.walk(nextDirPath, callback); err != nil {
			return err
		}
	}

	return nil
}

// Walk will walk the whole tree structure and call callback on every entry of
// the tree in a depth-first like fashion.
func (t *TreeEntry) Walk(callback func(path string, entry *TreeEntry) error) error {
	for _, e := range t.Entries {
		if err := e.walk(t.Path, callback); err != nil {
			return err
		}
	}

	return nil
}
