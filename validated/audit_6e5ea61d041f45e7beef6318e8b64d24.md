### Title
Griefing DoS via Front-Runnable CREATE2 Salt Squats `deploySmartAccount` Before It Runs - (File: `contracts/SmartAccountFactory.sol`)

### Summary
`SmartAccountFactory.deploySmartAccount` deploys a Gnosis Safe through the shared, permissionless `SafeProxyFactory.createProxyWithNonce`, using a deterministic salt derived only from `(msg.sender, nonces[msg.sender])` and the ABI-encoded `initializer`. Because `SAFE_PROXY_FACTORY` is a generic, unmodified Safe factory that anyone can call directly (not gated to only be invoked by `SmartAccountFactory`), and because the exact salt/initializer for any target deployer+nonce+config is computable off-chain (or read directly via the public `predictSmartAccountAddress` view), an attacker can pre-deploy a Safe proxy to the exact CREATE2 address the legitimate call is about to use. This causes `createProxyWithNonce` — and hence `deploySmartAccount` — to revert every time it is retried with the same parameters, exactly mirroring the reported Uniswap `createPair`-revert-on-existing-pair bug class.

### Finding Description
`deploySmartAccount` computes the deployment salt purely from public/predictable inputs and never checks whether the target address is already occupied before calling the external factory: [1](#0-0) 

Key facts that make this reachable by an unprivileged actor:
- `nonces[msg.sender]` is a public mapping, so the next `deployerNonce` for any known deployer address is readable on-chain before the deploying transaction lands. [2](#0-1) 
- `predictSmartAccountAddress` is a public view that reconstructs the exact `initializer`, salt, and resulting CREATE2 address for any `(deployer, nonce, params...)` combination, meaning an attacker does not even need to sniff the mempool — they can simply compute the future address for a known deployment key (e.g., the well-known deployer address used in the documented CLI deployment flow) ahead of time. [3](#0-2) 
- `SAFE_PROXY_FACTORY` is the standard, unmodified `SafeProxyFactory`; nothing restricts callers of `createProxyWithNonce(singleton, initializer, saltNonce)` to only be `SmartAccountFactory`. Anyone can call it directly with the same three arguments to squat the target address first.

Once the attacker's front-run deploys a proxy at the predicted address, the legitimate `createProxyWithNonce` call inside `deploySmartAccount` reverts (Safe's factory reverts on CREATE2 address collision). Because the whole transaction reverts, the `nonces[msg.sender]++` increment is rolled back as well — the deployer's nonce is left unchanged, so a naive retry with identical parameters recomputes the exact same salt and collides with the same squatted address again, reproducing the "always reverts from that point onward" pattern described in the source report.

### Impact Explanation
This is a permissionless griefing vector against the protocol's own deployment/bootstrap flow: the eight role Safes (`Borrower`, `Originator`, `Investor`, `Servicer`, etc.) created via `create-role-accounts` on a new chain are exactly the kind of well-known-deployer, low-nonce, standard-parameter deployments an attacker could pre-compute and squat. If squatted before the real deployment transaction lands, the protocol's own bootstrap script (which drives loan creation, funding, and disbursement role accounts) is blocked from producing the intended deterministic Safe addresses, forcing an out-of-band parameter change or contract rework to route around the griefed address — a material production DoS on deployment/setup that can hold up funding, disbursement, and loan origination flows on that chain until manually worked around, matching the acknowledged real-world impact of the source report.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to know (or predict) the deploying EOA address and the parameters used (both are effectively public — the deployer address is fixed ahead of time in the runbook, and `predictSmartAccountAddress` exposes the exact resulting address for any guess), plus the ability to front-run a single transaction on the target chain. No compromise of any privileged role is needed; this is purely an availability/ordering race exploitable by any external address.

### Recommendation
Before calling `SAFE_PROXY_FACTORY.createProxyWithNonce`, check whether the predicted address already has code (`predictSmartAccountAddress(...).code.length == 0`) and, if a collision is detected because someone else squatted it, retry with the next nonce automatically rather than reverting the whole call and rolling back `nonces[msg.sender]`. Alternatively, salt the deployment with values not fully predictable/front-runnable by third parties (e.g., include `block.prevrandao`/a caller-supplied random nonce chosen at call time, or accept the collision and simply skip to the next nonce internally in a loop) so a griefer cannot deterministically pin the exact address in advance.

### Proof of Concept
1. Attacker reads `nonces[deployer]` (public mapping) for the known production deployer address used by the `create-role-accounts` CLI flow, and reads the standard parameters documented in the runbook (`owners = [OperationalManagementSafe]`, `threshold = 1`, empty delegates/currencies).
2. Attacker calls `predictSmartAccountAddress(deployer, nonces[deployer], ...same params...)` to get the exact future Safe address.
3. Attacker independently reconstructs the same `initializer` bytes and `saltNonce` (both derivable from the same public formula in `_buildInitializer`/salt derivation) and calls `SAFE_PROXY_FACTORY.createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce)` directly, deploying an attacker-controlled Safe proxy to that exact address.
4. When the legitimate `create-role-accounts`/`deploySmartAccount` transaction executes, `SAFE_PROXY_FACTORY.createProxyWithNonce` reverts due to the address collision, reverting the entire `deploySmartAccount` call (including the `nonces[msg.sender]++` update).
5. Every subsequent retry with the same deployer/parameters recomputes the identical salt and again collides with the attacker's squatted address, permanently blocking that specific role-account deployment until the team changes the deployment parameters or code.

  function predictSmartAccountAddress(
    address deployer,
    uint256 _nonce,
    address[] memory delegates,
    address[] memory currencies,
    address[] memory nftCollections,
    address[] memory trustedRecipients,
    uint48 validUntil,
    address[] memory owners,
    uint256 threshold
  ) public view returns (address) {
    uint256 saltNonce = uint256(keccak256(abi.encodePacked(deployer, _nonce)));

    bytes memory initializer = _buildInitializer(
      delegates,
      currencies,
      nftCollections,
      trustedRecipients,
      validUntil,
      owners,
      threshold
    );
    bytes32 salt = keccak256(abi.encodePacked(keccak256(initializer), saltNonce));

    bytes memory deploymentData = abi.encodePacked(
      SAFE_PROXY_FACTORY.proxyCreationCode(),
      uint256(uint160(SAFE_SINGLETON))
    );

    bytes32 hash = keccak256(
      abi.encodePacked(bytes1(0xff), address(SAFE_PROXY_FACTORY), salt, keccak256(deploymentData))
    );

    return address(uint160(uint256(hash)));
  }
