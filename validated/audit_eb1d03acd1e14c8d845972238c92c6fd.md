### Title
Unbounded growth of `DynamicPacketToProcessThreshold::max_packets` allows an unstaked attacker to defeat repair-response throttling and force a burst of expensive signature-verification work to be processed unthrottled - (File: `core/src/repair/packet_threshold.rs`)

### Summary
`DynamicPacketToProcessThreshold::update` raises `max_packets` by ~11% (`100/90`) every processing cycle whenever `total_packets >= max_packets` and the measured `compute_time` stays under 1 second, with no upper bound on the value. An unstaked remote attacker who floods a validator's public repair-response socket with cheap-to-reject packets can drive `max_packets` up over many cycles, and then send a burst of cryptographically expensive `Ping` packets that will be fully accepted (not dropped) in a single cycle because the inflated threshold defeats the intended admission control.

### Finding Description
`DynamicPacketToProcessThreshold::update` computes the next `max_packets` purely from `total_packets` and `compute_time`, with no ceiling: [1](#0-0) 

The `Increase` branch multiplies `max_packets` by `100/90 ≈ 1.111` with no cap, so repeated cycles compound exponentially: [2](#0-1) 

Both callers of this throttle (`ancestor_hashes_service.rs` and `block_id_repair_service.rs`) receive packets on a UDP repair-response socket, count all received packets (including malformed ones that are dropped or fail verification) as `total_packets`, and only measure `compute_time` for the packets that get pushed into `packet_batches` (i.e., not already dropped by `should_drop`): [3](#0-2) 

Because per-packet validation short-circuits cheaply on deserialization failure or nonce mismatch, an attacker can send arbitrary/garbage UDP packets (or packets with bogus nonces) to keep `compute_time` low for a full batch of `max_packets` size while still satisfying `total_packets >= max_packets`, repeatedly hitting the `Increase` branch and inflating `max_packets` without bound over multiple cycles.

Once inflated, the attacker switches to well-formed `AncestorHashesResponse::Ping` packets. Verification of a `Ping` requires only that the packet is self-signed by an attacker-controlled keypair (`ping.verify()`), and does **not** require any prior outstanding repair request or nonce match, so any unstaked attacker can forge arbitrarily many valid Pings: [4](#0-3) [5](#0-4) 

With `max_packets` inflated, `should_drop` (`total >= max_packets`) will not trip during accumulation, so the entire attacker-supplied burst is pushed into `packet_batches` and fully processed in one cycle — each triggering an `ed25519` verify plus a `keypair.sign_message` for the `Pong` — before the subsequent `update()` call (which only observes `compute_time` *after* the batch was already processed) can react and decrease the threshold. The throttle is therefore reactive rather than preventive against a single, already-inflated cycle.

### Impact Explanation
This allows CPU-cost amplification / QoS evasion against the repair-response processing threads (`solAncHashesSvc` and the block-ID repair response path): a modest volume of cheap garbage packets over multiple cycles can inflate the intended safety valve (`DEFAULT_MAX_PACKETS = 1024`) by orders of magnitude, after which a single burst forces the validator to perform a correspondingly large number of `ed25519` verify/sign operations in one uninterrupted batch, defeating the adaptive throttle's purpose of bounding compute time per cycle to ~1 second. This is scoped to the dedicated repair-response service thread(s), not the banking/PoH critical path, so impact is a localized CPU-exhaustion/QoS-evasion issue on that thread rather than a consensus-safety or memory-safety bug.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only network reachability to the validator's public repair-response UDP socket (no staking, no gossip peering, no privileged state) and the ability to send arbitrary UDP packets, which matches the granted threat model. The exploit requires sustained but unprivileged packet generation across several receive cycles to inflate the threshold, then a timed burst of self-signed `Ping` packets — both trivially scriptable and fully repeatable since `max_packets` has no ceiling and no long-term memory reset between attack attempts.

### Recommendation
Clamp `max_packets` to a fixed maximum ceiling (e.g., a small multiple of `DEFAULT_MAX_PACKETS`) in `PacketThresholdUpdate::calculate`'s `Increase` branch, and/or base the `Increase` decision on the compute time actually spent per processed packet from packets that passed cheap validation (excluding trivially-rejected garbage) rather than raw packet counts, so that malformed/rejected packets cannot be used to game the adaptive threshold upward.

### Proof of Concept
```rust
// core/src/repair/packet_threshold.rs (test)
use std::time::Duration;

#[test]
fn threshold_is_unbounded_under_cheap_packet_flood() {
    let mut threshold = DynamicPacketToProcessThreshold::default();
    let start = threshold_max_packets(&threshold); // 1024

    // Simulate ~50 cycles of an attacker flooding cheap/malformed packets
    // that are always >= max_packets in count but cheap to reject (<1s compute).
    for _ in 0..50 {
        let total = threshold_max_packets(&threshold); // attacker sends >= max_packets
        threshold.update(total, Duration::from_millis(50)); // cheap compute_time
    }

    let inflated = threshold_max_packets(&threshold);

    // Expected (desired) invariant: max_packets should never exceed a fixed ceiling
    // regardless of attacker-chosen compute_time sequence.
    assert!(
        inflated <= start * 10, // example hard ceiling
        "max_packets inflated from {start} to {inflated} with no upper bound, \
         allowing a subsequent burst of expensive packets to bypass throttling"
    );
}

// helper accessor needed for the test (max_packets is private):
// add `pub(crate) fn max_packets(&self) -> usize { self.max_packets }` for testing.
```
This test currently fails against the existing implementation (no ceiling exists), demonstrating the unbounded growth described above.

        if total_packets >= self.max_packets {
            let threshold_update = if compute_time > Self::TIME_THRESHOLD {
                PacketThresholdUpdate::Decrease
            } else {
                PacketThresholdUpdate::Increase
            };
            self.max_packets = threshold_update.calculate(self.max_packets);
        }
    }
