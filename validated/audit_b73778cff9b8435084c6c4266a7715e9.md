### Title
Uncontrolled memory allocation in TVM precompiled-contract ABI array extraction - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an array-length word directly from attacker-supplied calldata and immediately use it to size a Java array (`new byte[len][]`) without validating that `len` is consistent with the actual size of the remaining input data. [1](#0-0) 

### Finding Description
For each of these helpers, `len` is taken from `words[offset].intValueSafe()` — a value fully controlled by the caller of a precompiled contract (e.g. a multi-signature validation precompile identified by the `SIG_LENGTH` constant used in `extractSigArray`). [2](#0-1) 

The only structural sanity check performed before these extractors run is `isValidAbiEncoding`, which validates that `data.length` is a multiple of `WORD_SIZE` and that the "tail" portion is a multiple of `itemWords * WORD_SIZE`. It never compares this derived tail length against the `len` value that will actually be read from the header word: [3](#0-2) 

Because `len` is not bounded against the real remaining size of `data`/`words`, an attacker can submit a small calldata payload but set the length header word to a very large value (up to `Integer.MAX_VALUE`, since `intValueSafe()` clamps otherwise unbounded 256-bit words to that maximum). This causes `new byte[len][]` (a reference-array allocation, effectively `len * 4/8` bytes plus the per-element arrays touched by the subsequent loop) to be attempted directly on the node executing the transaction — exactly the same bug class as CVE-2026-42146, where `nb_colors` from a BMP header is used to size an allocation without checking it against the remaining file size.

### Impact Explanation
This code runs inside TVM precompiled-contract execution, reachable by any account that can send a transaction invoking `CALL`/`STATICCALL` to the corresponding precompile address with crafted calldata (no special permission required). A successful trigger causes an `OutOfMemoryError`/huge transient allocation on every full node that processes or re-validates the transaction, which can crash or destabilize the node process — a resource-exhaustion/availability impact consistent with an unprivileged contract-call path into TVM precompiles.

### Likelihood Explanation
Likelihood is high for any node that executes/validates the transaction: the attacker only needs to construct calldata for the affected precompile with an inflated length word; no elevated privileges, staking, or witness/SR status is required, and the check that exists (`isValidAbiEncoding`) does not constrain the `len` value itself.

### Recommendation
In `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, validate `len` against the actual bounds of `words`/`data` (e.g., ensure `offset + len + 1 <= words.length` and that the implied byte offsets/lengths stay within `data.length`) before allocating any array, rejecting the call (return failure / consume energy and revert) instead of allocating based on an unchecked header value.

### Proof of Concept
1. Craft a transaction that calls the precompiled multi-signature/array-based precompile (the one invoking `extractSigArray`/`extractBytesArray`) with ABI-encoded calldata that:
   - Passes `isValidAbiEncoding`'s structural check (correct total length multiple of 32 bytes, minimal actual byte payload).
   - Sets the length header word read by `extractSigArray`/`extractBytesArray`/`extractBytes32Array` (`words[offset]`) to a very large value, e.g. `0x7fffffff`.
2. Submit/broadcast the transaction (or trigger via a contract's internal `CALL` to the precompile address) so the precompile's `execute(byte[] data)` runs on a full node.
3. Observe `new byte[len][]` in the extractor attempting a huge allocation, causing an `OutOfMemoryError` / severe resource spike during transaction execution/validation on the node. [4](#0-3)

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static boolean isValidAbiEncoding(byte[] data, int headerWords, int itemWords) {
    if (data == null || data.length % WORD_SIZE != 0) {
      return false;
    }
    long tail = subtractExact(data.length, multiplyExact(headerWords, WORD_SIZE));
    return tail > 0 && tail % multiplyExact(itemWords, WORD_SIZE) == 0;
