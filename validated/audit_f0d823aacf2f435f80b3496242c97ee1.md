### Title
Stale conntrack entries bypass firewall rule re-validation for the routine-local `ConntrackCache` window - (File: firewall.go, firewall/cache.go)

### Summary
The Sentiment report describes an asset that is "delisted" (a policy change meant to block a resource) but accounts that already hold the resource can keep using it because the enforcement point is bypassed for already-established state. Nebula has a structurally analogous mechanism in `Firewall.inConns`: an already-permitted flow (conntrack entry) is normally re-validated against the current firewall ruleset when the rule version changes, but a fast-path per-routine cache (`firewall.ConntrackCache`) can short-circuit that re-validation and immediately allow the packet without ever consulting the updated rules.

### Finding Description
`Firewall.Drop` treats an existing conntrack hit as an automatic pass, then only re-checks the ruleset if the packet is not already present in the caller-supplied `localCache`: [1](#0-0) 

`inConns` implements this: if the flow tuple is present in `localCache`, it returns `true` immediately with **no rulesVersion check, no re-validation against `f.InRules`/`f.OutRules`, and no re-consultation of `caPool`**: [2](#0-1) 

Only when the flow is *not* in `localCache` does the code fall through to the slower path that compares `c.rulesVersion` against the firewall's current `rulesVersion` and re-runs `table.match(...)` against the live ruleset (this is exactly the logic that is supposed to guarantee that a firewall reload can retroactively drop flows that no longer match): [3](#0-2) 

`localCache` is a shared, per-goroutine (`ConntrackCacheTicker`) or per-batch structure, defined in `firewall/cache.go`, that is only cleared when its background ticker fires (`conntrackCacheTimeout`, default 1s when `routines > 1`, or unset/never for single-routine mode where callers may pass a batch-scoped cache): [4](#0-3) [5](#0-4) 

The reload path (`reloadFirewall` in `interface.go`) bumps `rulesVersion` on the new `Firewall` object precisely so that already-conntracked flows get re-validated against the new rules: [6](#0-5) 

But that bump is only consulted in the slow path of `inConns`. Any flow whose tuple is still sitting in a routine's `localCache` from before the reload will skip the `rulesVersion` comparison entirely and be allowed, exactly like the Sentiment bug where an entity that already "has" a permission continues to exercise it because the code path that enforces the new restriction is never reached for it.

### Impact Explanation
When a Nebula operator removes a firewall rule (e.g., revokes a peer's group/CA-based permission to reach a given host/port — the direct analog of "delisting an asset") intending an immediate `firewall.rulesVersion`-driven cutoff, traffic for flows already recorded in a worker routine's `ConntrackCache` continues to be forwarded rather than dropped, for up to the cache's refresh interval. This is a firewall-bypass / stale-authorization issue: the intended access-control change is not enforced for already-flowing connections, allowing continued (unauthorized-per-new-policy) traffic through the tunnel for the duration of the cache window.

### Likelihood Explanation
This only manifests when: (1) `firewall.conntrack.routine_cache_timeout` is enabled (the default whenever `routines > 1`), (2) an operator reloads/tightens firewall rules while a flow is actively conntracked, and (3) the flow tuple happens to still be resident in the per-routine cache. It requires no attacker action beyond having previously established a now-to-be-blocked flow before the policy change — no forged certificate or malicious peer needed, matching the report's "already-holds-the-asset" precondition. The window is bounded by the cache tick interval, which limits severity but does not eliminate the bypass.

### Recommendation
Either (a) do not allow a `localCache` hit to bypass the `rulesVersion` comparison — always compare against `f.rulesVersion` even on the fast path, invalidating/removing routine-local cache entries when the firewall is reloaded, or (b) tie the `ConntrackCacheTicker`'s reset to firewall reload events (in addition to its time-based tick) so that a rule change immediately forces re-validation on the next packet, matching the same approach already used for the shared `Conntrack` table's `rulesVersion` field.

### Proof of Concept
1. Configure `routines > 1` (enables `firewall.conntrack.routine_cache_timeout` default of 1s) and add a firewall rule allowing group `A` inbound.
2. Establish and pass traffic for a flow from a peer in group `A`; the flow is conntracked and its tuple is populated into that routine's `ConntrackCache` via `inConns`'s `localCache[fp] = struct{}{}` (`firewall.go:574`).
3. Reload the firewall config to remove group `A`'s permission (`interface.go` `reloadFirewall`, which bumps `rulesVersion`).
4. Within the cache's refresh window, send another packet for the same flow tuple. Because `localCache[fp]` still contains the tuple, `inConns` returns `true` at `firewall.go:507-509` before ever comparing `c.rulesVersion != f.rulesVersion`, so the packet is forwarded despite the new ruleset explicitly disallowing it.

func (f *Firewall) inConns(fp firewall.Packet, h *HostInfo, caPool *cert.CAPool, localCache firewall.ConntrackCache) bool {
	if localCache != nil {
		if _, ok := localCache[fp]; ok {
			return true
		}
	}
	conntrack := f.Conntrack
	conntrack.Lock()

	// Purge every time we test
	ep, has := conntrack.TimerWheel.Purge()
	if has {
		f.evict(ep)
	}

	c, ok := conntrack.Conns[fp]

	if !ok {
		conntrack.Unlock()
		return false
	}
```

// ConntrackCache is used as a local routine cache to know if a given flow
// has been seen in the conntrack table.
type ConntrackCache map[Packet]struct{}

type ConntrackCacheTicker struct {
	cacheV    uint64
	cacheTick atomic.Uint64

	l     *slog.Logger
	cache ConntrackCache
}

func NewConntrackCacheTicker(ctx context.Context, l *slog.Logger, d time.Duration) *ConntrackCacheTicker {
	if d == 0 {
		return nil
	}

	c := &ConntrackCacheTicker{
		l:     l,
		cache: ConntrackCache{},
	}

	go c.tick(ctx, d)

	return c
}
```

// Get checks if the cache ticker has moved to the next version before returning
// the map. If it has moved, we reset the map.
func (c *ConntrackCacheTicker) Get() ConntrackCache {
	if c == nil {
		return nil
	}
	if tick := c.cacheTick.Load(); tick != c.cacheV {
		c.cacheV = tick
		if ll := len(c.cache); ll > 0 {
			if c.l.Enabled(context.Background(), slog.LevelDebug) {
				c.l.Debug("resetting conntrack cache", "len", ll)
			}
			c.cache = make(ConntrackCache, ll)
		}
	}

	return c.cache
}

func (f *Interface) reloadFirewall(c *config.C) {
	cs := f.pki.getCertState()
	curCert := cs.getCertificate(cert.Version2)
	if curCert == nil {
		curCert = cs.getCertificate(cert.Version1)
	}

	// The firewall builds its routableNetworks set from the certificate's UnsafeNetworks at construction.
	// Check to see if that set has changed, and if so, rebuild the firewall.
	certUnsafeChanged := curCert != nil && !slices.Equal(curCert.UnsafeNetworks(), f.firewall.unsafeNetworks)

	if !c.HasChanged("firewall") && !certUnsafeChanged {
		f.l.Debug("No firewall config change detected")
		return
	}

	fw, err := NewFirewallFromConfig(f.l, cs, c)
	if err != nil {
		f.l.Error("Error while creating firewall during reload", "error", err)
		return
	}

	oldFw := f.firewall
	conntrack := oldFw.Conntrack
	conntrack.Lock()
	defer conntrack.Unlock()

	fw.rulesVersion = oldFw.rulesVersion + 1
	// If rulesVersion is back to zero, we have wrapped all the way around. Be
	// safe and just reset conntrack in this case.
	if fw.rulesVersion == 0 {
		f.l.Warn("firewall rulesVersion has overflowed, resetting conntrack",
			"firewallHashes", fw.GetRuleHashes(),
			"oldFirewallHashes", oldFw.GetRuleHashes(),
			"rulesVersion", fw.rulesVersion,
		)
	} else {
		fw.Conntrack = conntrack
	}

	f.firewall = fw
