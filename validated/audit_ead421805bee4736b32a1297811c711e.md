## Title
External caller's escrowed deposit is permanently lost when an intermediate cross-contract check fails in the Wallet Contract - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The `WalletContract` (the eth-implicit account contract that emulates Ethereum transactions as Near actions) tracks an external relayer/caller's attached NEAR deposit via `CallerDeposit` so it can be refunded if the emulated cross-contract call ultimately fails [1](#0-0) . This refund is correctly performed in the terminal `rlp_execute_callback` when the final promise fails [2](#0-1) . However, two intermediate callbacks used for ERC-20/NEP-141 emulation and eth-implicit address checks — `nep_141_storage_balance_callback` and `address_check_callback` — receive `caller_deposit` as an argument but silently drop it on their early-failure paths, never scheduling a refund.

### Finding Description
When a relayer submits an ABI-encoded transaction whose target resolves to `EthEmulationKind::ERC20Transfer`, `inner_rlp_execute` first calls `storage_balance_of` on the token contract and routes the result through `nep_141_storage_balance_callback` [3](#0-2) . If that first-leg promise fails (e.g. `target` does not actually implement the NEP-141 interface, analogous to the report's scenario where a bridge assumes ERC-20 semantics on a contract that doesn't implement them) or returns data that cannot be parsed as `StorageBalance`, the function returns an error `ExecuteResponse` directly, without ever touching `caller_deposit`: [4](#0-3) 

The same pattern exists in `address_check_callback`, used when the target is another eth-implicit account and the address registrar must first be consulted; a failed or unparsable registrar response returns early without refunding `caller_deposit`: [5](#0-4) 

In both cases the attached deposit was already collected into the wallet contract's balance at the start of `rlp_execute` (`env::attached_deposit()` via `ExecutionContext::new`, tracked as `CallerDeposit`) [6](#0-5) . Only the success/second-leg path threads `caller_deposit` onward into `rlp_execute_callback`, where the refund logic actually lives [7](#0-6) . On the early-error branches this hand-off never happens, so the refund transfer is never scheduled and the deposit remains stranded in the wallet contract's own balance.

This mirrors the reported bug class: a call path built assuming a specific downstream interface (native vs. ERC-20 token semantics in the original report; NEP-141/registrar semantics here) fails when that assumption doesn't hold, and the failure path lacks the same fallback/refund handling as the "happy path" or the fully-resolved failure path — resulting in funds becoming stuck.

### Impact Explanation
Any external (non-owner) relayer who attaches a deposit while calling `rlp_execute` on behalf of a wallet owner to perform an ERC-20-emulated transfer or a base-token transfer to another not-yet-registered eth-implicit account can permanently lose that deposit if the first-leg cross-contract call (`storage_balance_of` or address-registrar `lookup`) fails or returns unexpected data. This is a genuine permanent loss of funds for the caller, not merely a gas-cost issue, since the NEAR-protocol-level automatic refund-on-failed-receipt mechanism only protects against receipt-level failures of actions sent out from the contract — it does not restore state already committed inside the contract's own successful receipt (the deposit was already accepted and stored in the contract's balance in a prior, successful receipt).

### Likelihood Explanation
This is reachable by any ordinary external caller of a deployed eth-implicit wallet contract using nothing but standard `rlp_execute` calls with attached deposit; no privileged access or malicious validator/node behavior is required. Triggering it only requires targeting a token/registrar-like contract that fails the intermediate call (e.g., malformed target, insufficient gas causing `storage_balance_of`/`lookup` to fail, or a contract returning JSON that doesn't deserialize to `Option<StorageBalance>`/`Option<AccountId>`), all of which are plausible in normal operation (bad relayer input, misconfigured/incompatible token contracts, or non-standard NEP-141 implementations).

### Recommendation
In both `nep_141_storage_balance_callback` and `address_check_callback`, the early-failure branches (`PromiseResult::Failed` and JSON-deserialization errors) should schedule the same caller-deposit refund logic used in `rlp_execute_callback` before returning the error `ExecuteResponse`, ensuring the escrowed deposit is always returned to `caller_deposit.account_id` whenever the transaction ultimately does not succeed.

### Proof of Concept
1. Deploy a wallet contract and have an external relayer account (`predecessor_account_id != current_account_id`) call `rlp_execute` with an attached deposit and an ABI-encoded ERC-20 `transfer` call whose `target` is a contract that does not implement `storage_balance_of` in the standard NEP-141 shape (or returns malformed JSON).
2. `inner_rlp_execute` classifies this as `EthEmulationKind::ERC20Transfer`, records `CallerDeposit` for the relayer, and schedules `storage_balance_of(...).then(nep_141_storage_balance_callback(..., caller_deposit))` [8](#0-7) .
3. The `storage_balance_of` promise fails/returns unparsable data, so `nep_141_storage_balance_callback` hits the early-return branch and returns `ExecuteResponse{success:false,...}` without emitting any refund transfer to the relayer [4](#0-3) .
4. Query the relayer's account balance: it is short by the deposit amount, and the wallet contract's balance retains it permanently, with no receipt ever attempting to send it back.

/// A data type to keep track of the deposit given by an external caller.
/// This allows us to refund the caller's deposit if the cross-contract call fails.
#[derive(Debug, PartialEq, Eq, Clone, serde::Serialize, serde::Deserialize)]
pub struct CallerDeposit {
    pub account_id: AccountId,
    pub yocto_near: NonZeroU128,
}

impl CallerDeposit {
    pub fn new(context: &ExecutionContext) -> Option<Self> {
        // Only track for external (non-self) callers
        if context.current_account_id == context.predecessor_account_id {
            return None;
        }

        NonZeroU128::new(context.attached_deposit.as_yoctonear()).map(|yocto_near| Self {
            account_id: context.predecessor_account_id.clone(),
            yocto_near,
        })
    }
