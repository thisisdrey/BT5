## Title
DelegateAction (NEP-366 meta-transactions) lacks any chain/network-binding value, enabling cross-chain replay of a user's signed delegated actions - (File: `core/primitives/src/action/delegate.rs`)

### Summary
The `DelegateAction` payload that a NEAR user signs to authorize a meta-transaction contains no binding to a specific chain or block, unlike an ordinary `Transaction`, which is anchored to a `block_hash` from the live chain it targets. This mirrors the reported bug class: a signed authorization message lacking a chain-specific/domain-separated value (the on-chain analog of EIP-712's `chainId`), combined with the fact that anyone (any relayer) can submit it, permits the same signed payload to be replayed on a different but state-compatible chain (e.g. after a network fork, or reuse of the same access-key/account state on two live networks).

### Finding Description
`DelegateAction` is defined with only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`: [1](#0-0) 

The signature is computed purely over this struct plus a NEP-461 message-type discriminant — there is no `block_hash`, genesis hash, or any other chain-identifying value mixed into the signed bytes: [2](#0-1) [3](#0-2) 

Contrast this with an ordinary `SignedTransaction`, where the `block_hash` field is explicitly documented as replay/fork protection ("the `Transaction` object also contains some fields to prevent attacks: like `nonce` to prevent replay attack, and `block_hash` to limit the validity of the transaction"): [4](#0-3) 

On the receiving end, `validate_delegate_action_key` only checks: access-key existence, `nonce > current_nonce`, and `nonce < upper_bound` derived from `max_block_height` — it never checks that the `DelegateAction` was created for this particular chain: [5](#0-4) 

Because meta-transactions are explicitly designed to be relayed by any permissionless third party ("Meta transactions only work with a relayer... a server that accepts a `SignedDelegateAction`... and eventually forwards it inside a transaction"), the outer `SignedTransaction` that wraps the `SignedDelegateAction` is signed and submitted fresh by the relayer using *that* chain's own current `block_hash`, so the outer transaction's chain-validity check passes trivially on any live chain: [6](#0-5) 

The inner `SignedDelegateAction`, however, carries no such binding. If the sender's account (`sender_id`) exists on two live networks that share the same account/access-key nonce state — the canonical case being a chain fork/split, or a user who deployed the identical account id and key on two networks — a `SignedDelegateAction` observed on one chain can be captured and resubmitted verbatim (wrapped by any relayer) on the other chain, since the nonce and `max_block_height` checks are satisfied identically on both.

### Impact Explanation
This allows an attacker (any observer of the mempool/chain — no privileged role required, matching the "meta-transactions" and "action execution" unprivileged-signer categories) to replay a user's authorized token transfer or other delegated action on a second, unintended chain. Because `DelegateAction.actions` can include `Transfer`, `FunctionCall` (e.g. `ft_transfer`), or other state-mutating actions, this is a mechanism for unauthorized execution of a user's signed intent on a chain/network the user never intended it for — resulting in loss of funds or unauthorized action execution, analogous to the reported cross-chain-replay theft of funds.

### Likelihood Explanation
Exploitation requires a fork or shared-state scenario (two live chains where the sender account and access key state coincide) plus an attacker relaying the captured `SignedDelegateAction`. This is a lower-frequency but realistic event class for a chain that is forked or where users reuse keys/account ids across networks; when it does occur, exploitation is trivial and permissionless since relaying is by design open to anyone.

### Recommendation
Add a chain-identifying field (e.g. genesis hash or a configured network/chain id) into the `DelegateAction` struct and include it in the NEP-461 signed message (`SignableMessage`), and validate it against the executing chain's genesis/config inside `validate_delegate_action_key`, mirroring the `block_hash` protection already present for ordinary transactions.

### Proof of Concept
1. User Alice on Chain A signs a `DelegateAction { sender_id: alice, receiver_id: ft_contract, actions: [ft_transfer to attacker], nonce: N, max_block_height: H }` and hands it to a relayer, per the flow in `docs/architecture/how/meta-tx.md`.
2. Chain A forks into Chain A and Chain B at a block above where Alice's access key nonce is still `< N`, and Alice's account/access-key state is identical on both chains.
2. An attacker observes this `SignedDelegateAction` on Chain A (public data) and wraps it into a new outer `SignedTransaction`, signed with the attacker's own relayer key and a valid fresh `block_hash` from Chain B, then submits it to Chain B.
3. `validate_delegate_action_key` on Chain B (`runtime/runtime/src/actions.rs:563-650`) only checks `nonce`, `max_block_height`, and access-key/permission — all satisfied — and the delegated `ft_transfer` executes on Chain B even though Alice never intended to interact with Chain B.

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
}

            (access_key.nonce, DelegateNonceUpdate::AccessKey)

        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());

            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.

                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

            delegate_nonce: delegate_nonce.nonce(),
