## Finding

### Title
StackerDB chunk signatures omit the contract identity, enabling cross-contract/cross-reward-cycle replay of signer messages - (`libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` in `libstackerdb/src/libstackerdb.rs` signs only over `(slot_id, slot_version, data_hash)`. It never binds the signature to the `QualifiedContractIdentifier` (StackerDB contract) the chunk is destined for. Because the Nakamoto signer protocol reuses the *same* `slot_id` for the *same* signer address across many different StackerDB contracts (`signers-0-1`, `signers-0-2`, `signers-0-3`, the mirror `signers-1-*` set, and the same `signers-<parity>-<msg>` contract across every reward cycle of that parity), a chunk that was validly signed for one contract/context is also a valid signature for another contract where that address occupies the same slot. Any unprivileged relayer that has observed one signed chunk can therefore replay it into a different StackerDB replica, and it will be accepted as freshly authentic data by `StackerDBs::try_replace_chunk` / `PeerNetwork::validate_received_chunk`.

### Finding Description
The signing digest is defined as: [1](#0-0) 

`SlotMetadata::verify()` recovers the public key from that same digest and only checks it against the expected `StacksAddress` for the slot — it has no notion of *which contract* the slot belongs to: [2](#0-1) 

The storage/validation path threads the `smart_contract_id` in as a lookup key for the expected signer/version, but never mixes it into the authenticated bytes: [3](#0-2) [4](#0-3) 

Slot IDs are assigned deterministically by sorted signer order and are reused verbatim across the parallel per-message-type contracts (`signers-<set>-<message_id>`) and across reward cycles of the same parity: [5](#0-4) [6](#0-5) [7](#0-6) 

Because `num-slots` is always `u1` per signer per message-type contract (per the comment in `signers.clar`), and the same reward-cycle signer ordering is reused for `signers-<set>-1`, `signers-<set>-2`, `signers-<set>-3` (BlockResponse / StateMachineUpdate / BlockPreCommit) as well as for the `signers-<parity>-*` contracts of a later reward cycle of the same parity, a given signer address will very often occupy slot `N` in several distinct StackerDB contracts simultaneously or over time. Since the chunk signature covers only `(slot_id, slot_version, data_hash)`, a signature minted for `signers-0-1` slot 3 version 5 with data `D` is *also* a valid signature for `signers-0-2` slot 3 version 5 with data `D`, or for `signers-0-1` in a future reward cycle of parity 0 where slot 3 is again assigned to that address and the fresh contract's version counter restarts at 0.

`validate_received_chunk`'s freshness gate only rejects versions *strictly less than* the expected version — it does not reject an old, previously-retired chunk that happens to carry a version number higher than a brand-new contract's initial `expected_version = 0`: [8](#0-7) 

This precisely mirrors the reported CoreWallet bug class: a signed message's validity nonce/context is not tied to the specific "role" (there: signer/co-signer identity; here: StackerDB contract identity) it was produced for, so once that role is reassigned/reused elsewhere (there: co-signer becomes a signer; here: the same signer address gets the same slot id in another contract or a later reward cycle), the old signature can be replayed.

### Impact Explanation
This breaks the equality "authenticated for contract X" vs "stored as valid data in contract Y" — an unprivileged network relayer (no private key, no admin role) can cause a node to accept and store, then re-broadcast, a chunk into a StackerDB contract it was never signed for. Depending on which contract pair collides, this can:
- Inject a stale/obsolete `BlockResponse`/`StateMachineUpdate` chunk from a prior reward cycle into a current-cycle StackerDB for the same signer/slot, corrupting the node's live view of that signer's current message and causing it to be relayed network-wide as if fresh (`handle_unsolicited_StackerDBPushChunk` / `StackerDBSync`).
- Write attacker-selected-but-previously-legitimately-signed bytes into an unintended message-type lane's storage slot, since payload-type filtering (`signer_message_payload_matches_lane`) only runs at the higher-level event-interpretation stage, not at the point the chunk is accepted/stored/gossiped by `try_replace_chunk`/`validate_received_chunk`.

This is an unauthenticated/unauthorized write to StackerDB state and forged-data propagation, matching the Critical impact bucket.

### Likelihood Explanation
Exploitation requires no secret key and no special role — merely observing a broadcast chunk (StackerDB chunks are public gossip) and replaying it (`StackerDBChunkData`/`StackerDBPushChunkData`) against a different, structurally-compatible StackerDB replica where the signer's slot index coincides. Because slot indices are deterministic (sorted by signer key) and repeated across the fixed small set of `signers-<0|1>-{1,2,3}` contracts and across reward cycles of the same parity, such collisions are a normal, predictable occurrence rather than a rare edge case.

### Recommendation
Include the target `QualifiedContractIdentifier` (or at least a per-contract/per-cycle domain separator) inside `SlotMetadata::auth_digest()` so a signature is only valid for the exact StackerDB contract/slot it was produced for — analogous to the actual fix applied to the CoreWallet bug, which tied the signature to the specific signing context (address) rather than leaving it generically replayable.

### Proof of Concept
1. Signer `S` is assigned slot `k` in `signers-0-1` (BlockResponse) for reward cycle `N`, and also assigned slot `k` in `signers-0-2` (StateMachineUpdate) for the same cycle (same sorted-by-pubkey ordering, per `parse_signer_slots`/`stackerdb-get-signer-slots-page`).
2. `S` signs and pushes a legitimate chunk `StackerDBChunkData { slot_id: k, slot_version: v, sig, data: D }` to `signers-0-1`.
3. An observer (no key needed) copies this exact `StackerDBChunkData` and submits/relays it, unmodified, against `signers-0-2` (or against `signers-0-1`/`signers-0-2` of a future reward cycle of parity 0 where `S` is again slot `k`).
4. `PeerNetwork::validate_received_chunk` / `StackerDBTx::try_replace_chunk` looks up the expected signer for `(new_contract, k)` — it is `S` — and calls `slot_metadata.verify(&S)`, which recovers over `(k, v, hash(D))` only, succeeding regardless of contract. The freshness check passes since a fresh contract typically starts at `expected_version = 0 < v`. The forged/replayed chunk is accepted, stored, and rebroadcast. [9](#0-8) [10](#0-9)

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
