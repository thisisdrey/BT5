### Title
Uncapped per-position asset fan-out lets a borrower's dust deposits force disproportionately expensive oracle/accrual verification onto liquidators, letting undercollateralized positions become unliquidatable - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`v0-4-market.clar` allows a single account to open collateral and debt positions across up to `MAX-ASSETS = u64` distinct assets (`mainnet/contracts/registry/v0-assets.clar:22`), tracked as bits in a position `mask` (`mainnet/contracts/market/v0-market-vault.clar:91-125`). Nothing in `collateral-add` (`v0-4-market.clar:1020-1104`) or `borrow` enforces a minimum dust amount before a new asset bit can be set in the mask, so a borrower can cheaply register many near-zero collateral/debt entries. Any later `liquidate` call against that borrower is forced to fetch the *full* position (`get-full-position`, `v0-4-market.clar:470-471`) and run oracle price resolution and vault accrual for every registered asset (`accrue-user-debts`/`accrue-user-collateral` at `:1406-1407`, `get-assets`/`price-multi-resolve` at `:482-513`, `:397-418`) before any cheap correctness checks (`is-liquidation-paused`, `debt-amount > 0`, `contract-caller == tx-sender`, etc. at `:1488-1493`) are evaluated. This is the same class of bug as the Zebra advisory: cost that scales with attacker-controlled fan-out is not capped independently from the (here, implicit) per-call limits, and expensive verification work runs ahead of cheap rejection checks, so the party performing legitimate verification (the liquidator, analogous to Zebra's block-verification path) bears disproportionate, unbounded cost triggered by cheap attacker action (analogous to Zebra's cheap-to-produce invalid proofs).

### Finding Description
`collateral-add`/borrow flows set a bit in the account's `mask` for every new asset the account interacts with, with no floor on the amount required to register that bit: [1](#0-0) 
The registry backing this mask supports up to 64 simultaneously-tracked collateral assets and 64 debt assets per account (`DEBT-OFFSET u64`, `MAX-ASSETS u64`): [2](#0-1) [3](#0-2) 

When any party calls `liquidate`, the market resolves the borrower's *full* position (all collateral and all debt, `MAX-U64` mask) rather than only the specific asset pair being liquidated, and eagerly accrues/prices every registered asset before the cheap guard checks run: [4](#0-3) 
Each of those assets triggers a vault `accrue` call and, for the "enabled" subset, an oracle round-trip through `price-multi-resolve`/`price-resolve`, which itself performs cross-contract oracle calls and freshness/callcode processing per asset: [5](#0-4) [6](#0-5) 
Only after all of this expensive, per-asset work (accrual, egroup resolution, notional valuation) is the cheap, correctness-only guard section reached: [7](#0-6) 

Because the borrower fully controls how many assets appear in their own mask (up to the protocol-wide cap of 64, and growing as the DAO enables more assets over time — the DAO's registry expansion is legitimate and not attacker-controlled), and because registering a new asset bit costs the borrower only a single cheap token transfer of any nonzero (even dust) amount, an attacker can cheaply inflate their own position's asset fan-out while the *liquidator* — an ordinary, unprivileged principal acting to keep the protocol solvent — must pay the full, unbounded cost of iterating, accruing, and oracle-pricing every one of those assets on every liquidation attempt. This mirrors the Zebra pattern precisely: a count-based/structural cap (the mask/bit-width) does not bound the *verification cost* incurred by a third party (liquidator/block-verifier) processing attacker-controlled state, and expensive work (oracle calls, accrual) is performed before the cheap validity checks that could otherwise fail fast.

### Impact Explanation
If the borrower's asset fan-out (bounded only by the number of assets the DAO has enabled, up to 64) drives the cumulative read/runtime cost of a single `liquidate` call above what a block can accommodate, the liquidation transaction cannot execute at all — for any liquidator, in any block. An undercollateralized position that cannot be liquidated because processing its full position is too expensive results in bad debt that can never be socialized/repaid through the normal liquidation path, i.e., **temporary or permanent freezing of funds** (the collateral backing that debt, and the vault liquidity that debt represents, become effectively unrecoverable through liquidation). This lands squarely on the in-scope "permanent/temporary freezing of funds" impact class, driven by a bug in this code's own liquidation-cost design rather than any oracle-publisher fault, DAO misconfiguration, or economic/governance attack.

### Likelihood Explanation
Likelihood is moderate and grows with protocol adoption: as the DAO enables more assets over time (a normal, expected growth path, not a compromise), the maximum achievable fan-out per account increases toward the 64-asset ceiling, and the marginal cost to the attacker (dust deposits/borrows across many assets) stays low and fixed regardless of how many assets exist. No privileged action or DAO compromise is required — only ordinary `collateral-add`/borrow calls by the attacker into every asset the DAO happens to have enabled. The severity of the DoS scales with the number of enabled assets and is worse the more the protocol succeeds and lists more collateral/debt assets.

### Recommendation
- Enforce a minimum notional value (a dust floor) before a new asset bit can be added to an account's mask in `collateral-add`/borrow paths, so registering an asset costs more than negligible dust.
- Cap the number of distinct simultaneously-active collateral/debt assets an account may hold well below the structural 64-bit limit, independent of how many assets the DAO has enabled globally.
- In `liquidate`, move the cheap correctness/authorization checks (`is-liquidation-paused`, `debt-amount > 0`, `contract-caller == tx-sender`, same-block check) ahead of the expensive full-position accrual/oracle-pricing work, so obviously-invalid liquidation attempts fail fast without paying for the full per-asset scan.
- Consider allowing liquidators to target a bounded subset of a position (or process the full position size, but with a per-asset cost dimension for gating/prioritization) rather than always requiring `get-full-position`/`get-assets` over every registered asset.

### Proof of Concept
1. Attacker deposits a dust amount (e.g., `u1`) of every DAO-enabled collateral asset via repeated `collateral-add` calls, and takes on a dust debt in as many debt-enabled assets as possible via `borrow`, each call setting a new bit in `mask` per `v0-4-market.clar:1020-1104` and `v0-market-vault.clar:91-98`, up to the protocol's `MAX-ASSETS u64` ceiling per `v0-assets.clar:22`.
2. Attacker also builds up a real (non-dust) debt in one asset sufficient to breach `LTV-LIQ-PARTIAL` and become liquidatable.
3. A liquidator calls `liquidate` against the attacker: the call is forced through `get-liquidation-position`/`get-full-position` (`v0-4-market.clar:1393-1394`), `accrue-user-debts`/`accrue-user-collateral` over the full asset list (`:1406-1407`), and `get-assets`/`price-multi-resolve` over every enabled asset in the mask (`:1410`, `:482-493`, `:397-418`) — all before the cheap guard checks at `:1488-1493` are reached.
4. As the number of DAO-enabled assets grows (or is deliberately maximized by the attacker across all currently enabled assets), the cumulative oracle/accrual cost of step 3 approaches or exceeds the block's runtime/read-cost limits, causing every `liquidate` attempt against this account to fail, regardless of liquidator, effectively freezing the position's bad debt.

Note: I could not execute this against a live/test environment to measure exact Clarity runtime-cost units against the Stacks block cost limits, so the precise asset-count threshold at which `liquidate` becomes non-executable is unverified from static reading alone; a Devin session with Clarinet/local-testing tooling would be needed to measure actual cost consumption per additional asset and confirm the threshold empirically.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))
