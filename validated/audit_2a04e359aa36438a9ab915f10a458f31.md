### Title
Out-of-Bounds Heap Read Parsing ZIP Central Directory Entries in `InputZipFile::ProcessCentralDirEntry` - (File: third_party/ijar/zip.cc)

### Summary
`ijar`, Bazel's interface-jar generator, parses ZIP/JAR central-directory records via `InputZipFile::ProcessCentralDirEntry`. Unlike the local-file-header parser (`ProcessLocalFileEntry`), which validates every variable-length field with `EnsureRemaining()` before advancing the read cursor, `ProcessCentralDirEntry` reads attacker-controlled 16-bit length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) and immediately uses them to `memcpy()` and advance the cursor `p` with no bounds check against the mmap'd file length. This mirrors the `php_jpg_get16` class of bug: a length/offset value taken directly from untrusted binary input is trusted to index into a buffer without checking it stays inside the buffer.

None of `file_name_length`, `extra_field_length`, or `file_comment_length` — each fully attacker-controlled 16-bit values taken straight from the archive bytes — is checked against how much data actually remains in the mapped input file before being used in `memcpy` or to advance `p`/`extra_p`. Contrast this with the sibling function `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before reading `file_name_` and `extra_field_`: [2](#0-1) 

The only earlier bounds validation is in `FindZipCentralDirectory`, which checks that `cd.central_dir_offset + cd.central_dir_size <= in_length` — i.e., that the *whole* central directory region fits in the file — but this does nothing to prevent an individual, maliciously crafted entry from declaring a `file_name_length`/`extra_field_length`/`file_comment_length` that causes `p` to run past the actual end of the mmap'd region while still nominally inside (or exactly at the edge of) the central directory. [3](#0-2) 

`ProcessCentralDirEntry` is invoked both by `InputZipFile::ProcessNext` (used by `ZipExtractor::ProcessAll`, the main entry driving `ijar`'s class-stripping pass over every JAR Bazel's Java toolchain processes) and by `InputZipFile::CalculateOutputLength`: [4](#0-3) [5](#0-4) 

`ijar` is the tool Bazel runs on every `.jar` dependency (including ones fetched from external repositories/registries via `http_jar`, `http_archive`, or Maven coordinates) to build a stripped interface jar for compilation. `http_jar`/`http_archive` allow the `sha256`/`integrity` parameter to be omitted, in which case the downloaded bytes are entirely determined by whatever a hostile origin server or mirror serves — no digest binds the content before `ijar` parses it.

### Impact Explanation
A crafted JAR with an out-of-range `file_name_length`, `extra_field_length`, or `file_comment_length` in a central-directory record causes `InputZipFile::ProcessCentralDirEntry` to `memcpy()` from, and advance a raw pointer past, the end of the `mmap`'d input file. This is a classic out-of-bounds heap/mapped-memory read: it can crash the Bazel build process (denial of service via SIGSEGV) or, more critically, cause adjacent memory contents to be copied into the `filename` buffer, which is subsequently used in diagnostics, error messages, and file-acceptance logic — a potential information-disclosure vector, directly analogous to the CVE-2019-11040 `php_jpg_get16` buffer over-read in EXIF parsing.

### Likelihood Explanation
Reachable whenever Bazel's Java toolchain runs `ijar`/`ijar`-based interface-jar generation over a dependency JAR whose bytes are not integrity-pinned (e.g. `http_jar`/`http_archive` without `sha256`/`integrity`, or any JAR obtained from a registry/mirror without a verified digest). The attacker only needs control over the served archive bytes — no access to the victim's machine or credentials is required.

### Recommendation
Add explicit bounds checks (analogous to the existing `EnsureRemaining()` calls in `ProcessLocalFileEntry`) in `ProcessCentralDirEntry` before using `file_name_length`, `extra_field_length`, and `file_comment_length` to `memcpy` or advance `p`/`extra_p`, verifying the remaining buffer length relative to the mapped input file's end (`zipdata_in_ + input_file_->Length()`), and failing gracefully (as `EnsureRemaining` does) rather than reading out of bounds.

### Proof of Concept
Construct a ZIP whose central directory contains one entry where the correctly-signed central file header (`0x02014b50`) declares `file_name_length = 0xFFFF` (or a length exceeding the actual bytes remaining before the recorded end-of-central-directory record), while the physical file is truncated shortly after the header so the true remaining buffer is only a few bytes. Then run `ijar <path-to-crafted.jar> <out.jar>` (or trigger `bazel build` on a `java_library` whose `http_jar`/`http_archive` dependency — declared without `sha256`/`integrity` — resolves to this crafted JAR from a hostile server). `FindZipCentralDirectory`'s check `cd.central_dir_offset + cd.central_dir_size <= in_length` can still pass while the individual entry's declared `file_name_length` drives `memcpy`/pointer arithmetic in `ProcessCentralDirEntry` past the actual mapped file bounds, which can be verified with ASan (`-fsanitize=address`) reporting a heap-buffer-overflow read, or via a `BuildIntegrationTestCase`/`src/test/shell/bazel` test that builds a `java_library` against such a truncated/crafted JAR and observes a crash or corrupted filename output.
