### Title
Safe deployment can be frontrun via direct `SafeProxyFactory` calls, stranding users' predicted addresses - (File: `tare-io__tare-contracts/contracts/SmartAccountFactory.sol`)

### Summary
`SmartAccountFactory.deploySmartAccount` derives a deterministic Safe address from public inputs (`msg.sender`, the per-deployer nonce, and the full `initializer`) and then delegates deployment to the public Gnosis `SafeProxyFactory.createProxyWithNonce`. Because the final CREATE2 salt is fully reconstructible from public mempool data, an attacker can observe a pending `deploySmartAccount` transaction and call `SafeProxyFactory.createProxyWithNonce` directly with the same `SAFE_SINGLETON`, `initializer`, and `saltNonce`. The attacker's transaction lands first, deploying a Safe with the victim's exact owners, threshold, and module configuration at the victim's predicted address. The victim's `deploySmartAccount` then reverts because the CREATE2 target already holds code, and the Safe is not recorded in `isDeployedSmartAccount`, blocking protocol-recognized account creation.

### Finding Description
In `SmartAccountFactory.deploySmartAccount` the deployment salt is built as:

```solidity
uint256 deployerNonce = nonces[msg.sender]++;
uint256 saltNonce = uint256(keccak256(abi.encodePacked(msg.sender, deployerNonce)));
...
SafeProxy proxy = SAFE_PROXY_FACTORY.createProxyWithNonce(SAFE_SINGLETON, initializer, saltNonce);
``` [1](#0-0) 

The `SafeProxyFactory` computes the final CREATE2 salt as `keccak256(abi.encodePacked(keccak256(initializer), saltNonce))`. Both the `initializer` (derived from the victim's calldata parameters) and `saltNonce` (derived from the public `nonces[deployer]` mapping and the victim's address) are observable before the victim's transaction is mined. An unprivileged attacker can therefore call `SafeProxyFactory.createProxyWithNonce` directly, passing the victim's `SAFE_SINGLETON`, `initializer`, and `saltNonce`. This deploys a proxy to the exact address the victim predicted, with the victim's chosen owners and module configuration. The victim's subsequent factory call reverts on the existing contract, producing a griefing DoS that prevents the victim from creating a protocol-recognized Smart Account.

### Impact Explanation
This is a griefing attack that denies account creation to honest users. Because all protocol participants are expected to interact through Smart Accounts deployed by `SmartAccountFactory`, blocking the factory deployment path prevents the user from obtaining `isDeployedSmartAccount == true` for their predicted address. Even though the attacker does not gain control of the Safe (owners are the victim's), the victim cannot complete the intended deployment through the factory, and any assets or integrations pre-targeted at the predicted address may be stranded or rejected. The impact matches the allowed "Material production DoS ... across users" gate.

### Likelihood Explanation
High on any chain with a public mempool. The attacker only needs to monitor pending `deploySmartAccount` transactions, read the public `nonces` mapping, and call the public `SafeProxyFactory.createProxyWithNonce` with the same inputs. No privileged role, signature, or token approval is required. The attack is cheap (one deployment call) and can be repeated for every account creation transaction.

### Recommendation
Do not expose the deterministic CREATE2 salt to a publicly callable intermediary. Options:
1. Deploy the Safe proxy directly from `SmartAccountFactory` using `CREATE2` with a salt that is not passed through a public factory, so no external actor can replay the same salt.
2. If `SafeProxyFactory` must be used, add a pre-deployment check in `deploySmartAccount`: if the predicted address already holds code, verify it is a Safe with the expected initializer/owners and register it in `isDeployedSmartAccount` instead of reverting.
3. Alternatively, use a commit-reveal or factory-monotonic counter that makes the deployment salt unpredictable to third parties until inclusion.

### Proof of Concept
```solidity
function test_FrontrunSmartAccountDeployment() public {
  // Victim's deployment parameters
  address[] memory delegates = new address[](1);
  delegates[0] = makeAddr("delegate");
  address[] memory currencies = new address[](1);
  currencies[0] = address(usdc);
  address[] memory nftCollections = new address[](0);
  address[] memory trustedRecipients = new address[](0);
  address[] memory owners = new address[](1);
  owners[0] = bob;
  uint256 threshold = 1;
  uint48 validUntil = uint48(block.timestamp + 365 days);

  // Victim predicts address using next nonce
  uint256 bobNonce = factory.nonces(bob);
  address predicted = factory.predictSmartAccountAddress(
    bob, bobNonce, delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold
  );

  // Attacker reconstructs the initializer and saltNonce from public data
  bytes memory configureData = abi.encodeWithSelector(
    factory.configureSmartAccount.selector,
    delegates, currencies, nftCollections, trustedRecipients, validUntil
  );
  bytes memory initializer = abi.encodeWithSelector(
    ISafe.setup.selector,
    owners, threshold, address(factory), configureData, address(0), address(0), 0, address(0)
  );
  uint256 saltNonce = uint256(keccak256(abi.encodePacked(bob, bobNonce)));

  // Attacker frontruns by calling SafeProxyFactory directly
  vm.prank(alice);
  safeProxyFactory.createProxyWithNonce(safeSingleton, initializer, saltNonce);

  // Victim's factory deployment now reverts because the address is taken
  vm.prank(bob);
  vm.expectRevert();
  factory.deploySmartAccount(
    delegates, currencies, nftCollections, trustedRecipients, validUntil, owners, threshold
  );

  // The Safe exists at the predicted address but is not recognized by the factory
  assertGt(predicted.code.length, 0);
  assertFalse(factory.isDeployedSmartAccount(predicted));
}
```
