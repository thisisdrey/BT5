### Title
Attacker can permanently DoS deposits, withdrawals and liquidations by filling the feeCollector's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken.transfer`s - (File: contracts/Pool.sol)

### Summary
`Pool` tracks a per-account list of deposit/debt tokens (`depositTokensOfAccount` + `debtTokensOfAccount`) capped at `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Every mint/transfer of a `DepositToken` calls `pool.addToDepositTokensOfAccount(recipient)` when the recipient's balance goes `0 -> >0` (`contracts/DepositToken.sol:518-520`, `486-488`), which reverts with `UserReachedMaxTokens` once the combined list reaches 30 (`contracts/Pool.sol:143-148`, `216-220`). Because `DepositToken.transfer` is permissionless, an attacker can push dust of every registered deposit token to the `feeCollector`, filling its list. Since protocol fee accrual mints/seizes deposit tokens to `feeCollector`, any operation that mints a *new* deposit-token type to `feeCollector` reverts — freezing deposits, withdrawals, liquidations, reward updates that touch it, and fee collection itself, matching the CVE's "unprivileged-triggerable complete DoS" class.

### Finding Description
- `DepositToken.deposit` mints the deposit fee to `feeCollector` (`contracts/DepositToken.sol:230-234` → `_mint` → `addToDepositTokensOfAccount`).
- `DepositToken._withdraw` transfers `_fee` to `feeCollector` (`contracts/DepositToken.sol:546-548` → `_transfer` → `addToDepositTokensOfAccount`).
- `Pool.liquidate` seizes `_fee` to `feeCollector` (`contracts/Pool.sol:591-593` → `seize` → `_transfer` → `addToDepositTokensOfAccount`).

Attack path (all public, unprivileged):
1. For each deposit token `d_i` registered in the pool (up to 30 allowed, `addDepositToken` enforces `depositTokens.length() <= MAX_TOKENS_PER_USER`, `contracts/Pool.sol:703`), attacker calls `d_i.deposit(1, attacker)` (or obtains dust any way) and then `d_i.transfer(feeCollector, 1)`.
2. Each transfer adds `d_i` to `depositTokensOfAccount[feeCollector]` until the list hits 30.
3. Thereafter, any call that would add a deposit token not already in `feeCollector`'s list reverts: deposits whose fee mints a token type `feeCollector` doesn't hold, withdrawals/liquidations whose protocol fee seizes such a type, etc. When `depositFee`/`withdrawFee`/`protocolFee` are non-zero (deployed config) these core functions revert for the whole pool.

The same technique can target `SmartFarmingManager` (receives seized/minted tokens in `leverage`/`flashRepay` flows) or any individual victim to block their deposits into new collateral types and issuance of new debt (`DebtToken._mint` → `addToDebtTokensOfAccount`, `contracts/DebtToken.sol:598-600`), leaving them unable to add new collateral to rescue an unhealthy position.

### Impact Explanation
Complete denial of service of a pool: once `feeCollector`'s list is full, every `deposit`, `withdraw`, `flashWithdraw`, `liquidate`, `seize`, and `swap`-related fee mint that introduces a token type absent from the list reverts. Users cannot deposit collateral or withdraw (when `withdrawFee > 0`), and liquidations cannot execute — blocking bad-debt cleanup and exposing the pool to insolvency. Funds already held can only move for token types already in the victim's/feeCollector's list; everything else is frozen indefinitely since `feeCollector` is a fixed protocol address that cannot rotate around the cap.

### Likelihood Explanation
The attack needs no privilege: only `DepositToken.deposit`/`transfer` calls. `addDepositToken` explicitly allows up to 30 deposit tokens (`contracts/Pool.sol:703`), so a pool with ≥30 combined tokens (or fewer, plus debt tokens already counted for the fee collector if it ever holds debt) is fillable. Cost is dust of each collateral (bounded by each token's `debtFloorInUsd`-equivalent only on debt, not deposits) plus gas. The revert is unconditional once the list reaches 30 — no oracle, timing, or privileged state is required. Note the cap cannot be bypassed by `removeFromDepositTokensOfAccount` because removal only happens when a balance returns to zero, and the attacker's dust keeps balances non-zero.

### Recommendation
Do not gate protocol-critical flows on the per-account list cap for privileged protocol recipients, or make the cap victim-correctable. Options:
- Skip `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` when the recipient is `feeCollector` (fee balances can be enumerated via `depositTokens`/`debtTokens` globals instead).
- Let any account voluntarily call a `remove`-style function for its own list regardless of balance (or add a small burn-to-zero path for dust), so a filled list is recoverable.
- Alternatively, check the cap before mutating balances and emit rather than revert for recipients that are protocol contracts.

### Proof of Concept
Foundry/Hardhat fork sketch (pseudocode against deployed pool):

```solidity
// pool has N registered deposit tokens (N can be up to 30)
address[] memory dts = pool.getDepositTokens();
address fc = pool.feeCollector();

// 1. fill feeCollector's list to 30
for (uint i; i < dts.length; ++i) {
    IERC20 d = IERC20(dts[i]);
    // acquire 1 wei of msdToken (deposit dust of underlying, or transferFrom)
    uint before_ = pool.getDepositTokensOfAccount(fc).length;
    IDepositToken(dts[i]).deposit(1, attacker);          // attacker gets dust
    d.transfer(fc, 1);                                    // adds to fc list
    assert(pool.getDepositTokensOfAccount(fc).length == before_ + 1);
}

// if list < 30 because fewer deposit tokens exist, combine with debt tokens
// the check counts BOTH lists: debtTokensOfAccount + depositTokensOfAccount

// 2. now any deposit whose fee mints a token type fc lacks reverts
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(dts[0]).deposit(amount, victim); // reverts when depositFee>0

// 3. withdraw with withdrawFee>0 also reverts (fee seize to fc)
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(dts[0]).withdraw(amount, victim);

// 4. liquidate reverts on fee seize -> bad debt cannot be cleared
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
pool.liquidate(syntheticToken, underwaterAccount, amountToRepay, depositToken);
```

Verify deployed-config prerequisites before finalizing severity: pool must have enough registered deposit tokens for the combined list to reach 30, and `feeProvider.depositFee()/withdrawFee()/protocolFee` must be non-zero for the revert to hit user-facing flows.
