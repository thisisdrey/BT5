### Title
Cross-StackerDB chunk-signature replay lets an unprivileged network peer forge valid data across sibling `.signers-N-M` databases - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest` — the digest a signer signs to authenticate a StackerDB chunk — commits only to `(slot_id, slot_version, data_hash)`. It never commits to the StackerDB's smart-contract identifier ("which store/tenant this chunk belongs to"). Multiple sibling StackerDB contracts (`signers-{0|1}-0`, `signers-{0|1}-1`, ... up to `SIGNER_SLOTS_PER_USER`) that back the same reward-cycle signer set are populated with the *identical* slot_id→signer-address mapping (`stackerdb-get-signer-slots-page` in `signers.clar` returns the same list for every message-id contract, keyed only by cycle-mod). Consequently, a signature that is valid for slot N in one signer message-channel contract is also cryptographically valid for slot N in every other sibling contract for that reward cycle. Any unauthenticated peer that observes a legitimately-signed chunk on the wire (chunks are gossip data, not secret) can replay it into a different StackerDB contract's identically-numbered slot, and the node will accept and store/relay it as authentic — exactly analogous to H1514, where an invitation token was valid but not scoped to the issuing "store," letting it be replayed against a different store.

### Finding Description
- `SlotMetadata::auth_digest()` hashes only `slot_id`, `slot_version`, and `data_hash`: [1](#0-0) 
- `SlotMetadata::verify()` / `StackerDBChunkData::verify()` only check that the recovered public key hashes to the expected principal — with no smart-contract-id/tenant binding at all: [2](#0-1) 
- The write path (`try_replace_chunk`) resolves the expected signer purely from `(smart_contract, slot_desc.slot_id)` via `get_slot_validation`, then calls `slot_desc.verify(&slot_validation.signer)` — again never checking that the signature itself was scoped to `smart_contract`: [3](#0-2) 
- The gossip/push validation path (`validate_received_chunk`, used for both `StackerDBSync` downloads and unsolicited `StackerDBPushChunk` gossip) has the exact same gap — it looks up the signer for `(smart_contract_id, data.slot_id)` and calls `slot_metadata.verify(&addr)`, with no contract-scoped digest: [4](#0-3) 
- The HTTP write endpoint `/v2/stackerdb/{address}/{contract}/chunks` accepts any `StackerDBChunkData` blob whose slot signature validates for the *target* contract's configured slot-owner, with the contract identifier taken purely from the URL and never mixed into the authenticity check: [5](#0-4) 
- Root cause of the identical slot mapping across siblings: `stackerdb-get-signer-slots-page` in the `.signers` boot contract returns the *same* `stackerdb-signer-slots-{0|1}` list for every `.signers-{set}-{message_id}` contract, differentiated only by reward-cycle parity, not by `message_id`: [6](#0-5) [7](#0-6) 

This breaks the equality that should hold: "a chunk signature authenticates data *for a specific StackerDB*" — instead it only authenticates "data for slot N, version V, hash H, signed by signer S," which is portable across every sibling contract that assigns S to slot N. This is the direct analog of the H1514 bug class: an authentication artifact (invitation token / chunk signature) that is valid but not scoped to the resource instance (store / StackerDB contract) it was issued for.

### Impact Explanation
An unprivileged network observer can:
1. Passively capture a validly-signed `StackerDBChunkData` gossiped/pushed for contract `signers-1-0` (e.g., a legitimate signer's block-response message).
2. Re-POST the identical bytes (same `slot_id`, `slot_version`, `sig`, `data`) to `/v2/stackerdb/{signer-addr}/signers-1-1/chunks` (a sibling contract for a *different* message type) — or relay it as an unsolicited `StackerDBPushChunk` for that other contract.
3. Because the signer-to-slot mapping is identical across siblings and the signature carries no contract binding, the target node's `try_replace_chunk`/`validate_received_chunk` accepts it as authentic for the wrong message channel, and normal StackerDB replication propagates this misattributed/forged-context data network-wide.

This meets the Critical bar of "network-wide propagation of forged data": data legitimately signed for one purpose is accepted and re-disseminated by consensus-adjacent infrastructure (the signer StackerDB set) as authentic content for a different purpose, without requiring the attacker to hold any signer key.

### Likelihood Explanation
High. No secret material or elevated privilege is required — StackerDB chunks are, by design, publicly readable/replicated gossip data, and the write/push endpoints are reachable by any peer or unauthenticated HTTP client. The only precondition is that the signer's slot assignment is shared across sibling contracts, which is guaranteed by the current `.signers` boot contract logic (`stackerdb-get-signer-slots-page` keyed only by cycle parity). The `slot_version` monotonicity check offers only weak friction (an attacker needs the target sibling's current version to be behind the captured chunk's version, which is a normal occurrence during operation, not an obstacle requiring privilege).

### Recommendation
Bind the StackerDB chunk signature to the specific database instance by including the `smart_contract` (`QualifiedContractIdentifier`) — or a stable per-contract StackerDB ID — inside `SlotMetadata::auth_digest()`, and update `sign`/`verify` call sites (`StackerDBChunkData`, `try_replace_chunk`, `validate_received_chunk`) to pass and check this context. This requires a coordinated protocol/version change since it alters what is signed; until then, mitigate by rejecting cross-contract replays at the RPC layer (e.g., re-deriving/validating slot version and hash against the exact target contract state and increasing the signed payload wherever locally reachable) is not sufficient on its own — the digest itself must be scoped.

### Proof of Concept
1. Configure a node with two sibling StackerDB contracts for the same reward cycle, e.g. `signers-1-0` and `signers-1-1`, both populated with the same signer-address→slot_id mapping (this is the default behavior per `signers.clar`).
2. As any network observer (no private key needed), capture a validly-signed chunk broadcast for slot 0 in `signers-1-0`:
   - `slot_id=0, slot_version=V, sig=<valid signer sig>, data=<msg>`
3. Re-submit the same `(slot_id, slot_version, sig, data)` tuple via `POST /v2/stackerdb/<signer-addr>/signers-1-1/chunks` (see `RPCPostStackerDBChunkRequestHandler::try_handle_request`, `stackslib/src/net/api/poststackerdbchunk.rs:163-201`), or replay it as an unsolicited `StackerDBPushChunkData` targeting contract `signers-1-1`.
4. Observe that `try_replace_chunk`/`validate_received_chunk` accepts the chunk (assuming the target slot's current version is `< V`), because `SlotMetadata::verify` only checks `(slot_id, slot_version, data_hash)` against the resolved signer address for `signers-1-1`, and that address is identical to the one that legitimately signed for `signers-1-0`.
5. The node then relays/replicates this now-misattributed chunk under the `signers-1-1` message channel, demonstrating forged-context data propagation without possession of any signer's private key.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
