### Title
Unbounded-length decimal string fed to `new BigInteger(String, radix)` in `Wallet.getBigIntegerFromString` enables quadratic-complexity CPU DoS analogous to CVE-2025-61723 - (File: `framework/src/main/java/org/tron/core/Wallet.java`)

### Summary
The Go PEM advisory (CVE-2025-61723) is a case of an untrusted-input parser whose per-call cost grows non-linearly (quadratically) with input length, letting a small request burn disproportionate CPU. `java-tron` has the same bug-class exposure in `Wallet.getBigIntegerFromString`, which calls the JDK's `BigInteger(String, int radix)` constructor — an algorithm with known quadratic-time behavior for very long digit strings — on a caller-supplied string *before* any length or range validation is performed.

### Finding Description
`Wallet.getBigIntegerFromString` trims the input and immediately constructs a `BigInteger` from it with no upper bound on string length: [1](#0-0) 

This value is then passed into `checkPublicAmount`, which only performs range/validity checks (`checkBigIntegerRange`, scaling-factor modulo, `longValueExact()`) *after* the expensive constructor has already run: [2](#0-1) 

`BigInteger(String, radix)` in the JDK internally performs a naive digit-by-digit multiply-and-accumulate for large inputs, whose cost scales quadratically with the number of digits (the same underlying complexity class that made Go's PEM parser vulnerable when it repeatedly re-scanned untrusted data). Feeding it a multi-megabyte numeric string forces the JVM to spend a disproportionate amount of CPU time before the function ever gets to validate the value's actual bounds, exactly mirroring the "invalid input causes non-linear processing time" pattern described in the advisory.

By contrast, the project has already hardened an analogous JSON-RPC code path against this exact bug class — `JsonRpcApiUtil.parseBlockNumber` explicitly caps input length (`MAX_BLOCK_NUM_HEX_LEN`) *before* calling `ByteArray.hexToBigInteger`, with a comment calling out "BigInteger parsing, whose cost grows quadratically with length": [3](#0-2) 

`getBigIntegerFromString` / `checkPublicAmount` lacks the equivalent guard.

### Impact Explanation
`checkPublicAmount` is used to validate `fromAmount`/`toAmount` fields for shielded (TRC20) contract balance-public-amount operations, values that ultimately originate from caller-supplied strings in a public API/contract-build request. An attacker able to submit such a request with an arbitrarily long numeric string can force the node to spend excessive CPU inside a single validation call, degrading or stalling processing of other requests on that thread pool — a denial-of-service against the node's API-serving capability, consistent with the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
Reachability requires that the calling public API (shielded/TRC20 contract parameter construction path in `Wallet.java`) does not itself impose a length cap on the amount string before it reaches `getBigIntegerFromString`. I was not able to fully trace, within the available search budget, the exact HTTP/gRPC servlet or `TronJsonRpcImpl` method that supplies the string ultimately consumed by `checkPublicAmount`, nor confirm whether an outer request-size limit (e.g. `Util.checkBodySize`) already bounds the string length enough to make the constructor's cost negligible. This is the main open uncertainty in this finding.

### Recommendation
Add an explicit maximum-length check on the numeric string in `getBigIntegerFromString` (mirroring the pattern already used in `JsonRpcApiUtil.parseBlockNumber`) before calling `new BigInteger(trimmedIn, 10)`, rejecting inputs beyond what a legitimate TRX/token amount could ever require (a few dozen digits is more than sufficient for `Long`/`BigInteger` amounts actually used on-chain).

### Proof of Concept
Construct a shielded-contract "public amount" request whose `fromAmount`/`toAmount` field is a numeric string many megabytes long (e.g. a string of millions of `9` characters) and submit it through whatever public entry point invokes `Wallet.checkPublicAmount`. Because `getBigIntegerFromString` parses the entire string with the JDK's quadratic-time decimal `BigInteger` constructor before any length/range check occurs, this single call can consume CPU time disproportionate to the request size, analogous to the PEM parsing quadratic-blowup described in CVE-2025-61723. (Note: exact confirmation of the outward-facing API parameter that reaches this code was not completed due to search-budget limits; a full trace of the call sites of `getBigIntegerFromString`/`checkPublicAmount` back to the HTTP/gRPC layer is recommended to finalize exploit reachability.)

  private static final int MAX_BLOCK_NUM_HEX_LEN = 20;

   * block number.
   */
  public static long parseBlockNumber(String blockNum)
      throws JsonRpcInvalidParamsException {
