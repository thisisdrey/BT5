### Title
Concurrency-Limiter Bypass in PackObjectsHook via Attacker-Influenced `RemoteIp` Field - (File: `internal/gitaly/service/hook/pack_objects.go`)

### Summary
`packObjectsHook` only routes a `git-pack-objects` invocation through the `packObjectsLimiter` (Gitaly's concurrency/queue backpressure mechanism) when the request's `RemoteIp` field parses to a non-loopback IP address. Any request whose `RemoteIp` is empty, malformed, or resolves to a loopback address (`127.0.0.1`/`::1`) skips the limiter entirely and runs unbounded via `s.runPackObjects`, mirroring the ReserveRatio pattern of a pre-condition check ("is this remote non-loopback?") that gates enforcement but has no invariant re-validation and can be satisfied trivially.

### Finding Description
In `packObjectsHook`, the gate for whether to apply concurrency limiting is: [1](#0-0) 

```go
servedBytes, created, err := s.packObjectsCache.Fetch(ctx, cacheKey, output, func(w io.Writer) error {
    ipAddr := net.ParseIP(req.GetRemoteIp())
    if ipAddr == nil {
        if ip, _, err := net.SplitHostPort(req.GetRemoteIp()); err == nil {
            ipAddr = net.ParseIP(ip)
        }
    }
    if ipAddr != nil && !ipAddr.IsLoopback() {
        return s.runPackObjectsLimited(ctx, w, ipAddr.String(), req, args, stdin, cacheKey)
    }
    return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
})
```

The unlimited path (`s.runPackObjects`) executes `git-pack-objects` with no concurrency gating at all: [2](#0-1) 

This is structurally identical to the ReserveRatio bug class: there is a pre-check ("is the caller's IP non-loopback?") that decides whether a resource-consuming operation (arbitrary `pack-objects` invocation size/cost, analogous to the strategist's arbitrary trade size) is subject to a limiting mechanism, but:
1. The check can be satisfied by supplying an empty/unparsable `RemoteIp`, or one that resolves to loopback.
2. There is no post-operation validation that concurrency/queue invariants were respected — the operation runs to completion regardless of actual system load.

The concurrency limiter itself is the sole mechanism described in Gitaly's own backpressure documentation for preventing resource exhaustion: [3](#0-2) . Bypassing it via a spoofable/absent field defeats that protection, similar to how bypassing ReserveRatio defeats pool-utilization protection.

### Impact Explanation
If `RemoteIp` on a `PackObjectsHookWithSidechannelRequest` can be influenced to be empty or a loopback value by an ordinary user's fetch/clone flow (e.g., via a deployment path where the value is unset, malformed, or forwarded through an intermediary that fails to populate it correctly), an attacker can issue many concurrent pack-objects/clone requests that never enter the `packObjectsLimiter`'s per-key queue, defeating the `max_per_repo`/`max_queue_size`/`max_queue_wait` protections documented for this exact RPC path. Because `git-pack-objects` for large repositories is CPU/memory intensive, unlimited concurrent execution is a resource-exhaustion (DoS) vector against the Gitaly node, consistent with the "RPC-handler resource limits" category explicitly permitted by scope.

### Likelihood Explanation
Moderate-to-uncertain. The gate is trivially satisfiable by any request with an empty/unparsable `RemoteIp` string, and the code has no fallback enforcement (e.g., no default-limited path when the IP cannot be determined). What is **not verified** in this pass is the exact upstream provenance of `RemoteIp` — i.e., whether gitlab-shell/Workhorse populates this field from a value that an end user can influence (such as a spoofable header) versus a value derived strictly from the raw TCP peer address, which could not be forged by the client itself, or whether it is always non-empty in a normal push/fetch. Confirming this requires tracing `GL_REMOTE_IP` population in `cmd/gitaly-hooks/hooks.go` and the gitlab-shell integration, which the current index only partially exposed (matches found in `cmd/gitaly-hooks/hooks.go` were not fully retrievable in this session). This uncertainty should be resolved before treating this as a confirmed high-severity issue.

### Recommendation
- Do not exempt unparsable/loopback `RemoteIp` values from concurrency limiting; fail closed (apply the limiter with a default/fallback key) rather than fail open when `RemoteIp` cannot be parsed.
- Treat `RemoteIp` as untrusted input for the purposes of resource-limiting decisions, or derive the limiting key from a value that Gitaly itself controls (e.g., peer connection info at the gRPC layer) instead of a client/hook-supplied field.
- Add explicit test coverage for the "empty/invalid RemoteIp" case to assert that the concurrency limiter is still applied (current tests such as `TestPackObjects_concurrencyLimit`'s "empty IP addresses" case document `shouldLimit: false`, i.e., the bypass is treated as expected/intended behavior rather than flagged as a gap) — [4](#0-3) .

### Proof of Concept
Conceptual (not runtime-validated, since it depends on unverified upstream `RemoteIp` provenance):
1. Trigger a `PackObjectsHookWithSidechannel` RPC (e.g., via a normal clone/fetch flow whose pipeline invokes this hook) with `RemoteIp` unset or set to `"127.0.0.1"`.
2. Repeat concurrently many times against the same or different repositories.
3. Observe that `s.packObjectsLimiter.Limit` is never invoked for these calls (per the branch in `packObjectsHook`), so `gitaly_pack_objects_in_progress`/queue metrics do not reflect these calls and no `ResourceExhausted` throttling occurs, unlike the "normal IP address" test case which does get limited — compare with [5](#0-4)  and [4](#0-3) .

```go
func (s *server) runPackObjects(
	ctx context.Context,
	w io.Writer,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	// We want to keep the context for logging, but we want to block all its
	// cancellation signals (deadline, cancel etc.). This is because of
	// the following scenario. Imagine client1 calls PackObjectsHook and
	// causes runPackObjects to run in a goroutine. Now suppose that client2
	// calls PackObjectsHook with the same arguments and stdin, so it joins
	// client1 in waiting for this goroutine. Now client1 hangs up before the
	// runPackObjects goroutine is done.
	//
	// If the cancellation of client1 propagated into the runPackObjects
	// goroutine this would affect client2. We don't want that. So to prevent
	// that, we suppress the cancellation of the originating context.
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	return s.runPackObjectsFn(ctx, s.gitCmdFactory, w, req, args, stdin, key)
}
```
