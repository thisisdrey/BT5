### Title
Pack-objects concurrency limiter keys solely on client-supplied `RemoteIp`, allowing per-key resource throttling to be trivially bypassed by structuring requests across IPs - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
The `PackObjectsHookWithSidechannel` RPC throttles CPU-expensive `git pack-objects` invocations via the `packObjectsLimiter`, but the concurrency-limiting key it computes covers only the client's IP address, not the combination of user identity and repository, and it is fully separate from the cache key used to deduplicate identical fetches. An attacker who controls, spoofs, or simply varies the apparent remote IP (or triggers requests that route through different source addresses) can bypass the intended per-key concurrency cap and fan a single large fetch out into many "under-threshold" concurrent `git pack-objects` invocations against the same repository, exactly analogous to the referenced GMX finding where a global protection is bypassed by chopping a large operation into many smaller ones that each individually stay under the limiting threshold.

### Finding Description
In `packObjectsHook` [1](#0-0) , the code computes two independent keys for the same operation:

1. `cacheKey` — derived from `Repository`, `Args`, `GitProtocol`, and the hashed stdin (the requested object list) via `computeCacheKey` [2](#0-1) .
2. `limitkey` — derived only from the parsed `req.GetRemoteIp()` [3](#0-2) .

The concurrency limiter (`s.packObjectsLimiter.Limit(ctx, limitkey, ...)`) is only invoked when the resolved `ipAddr` is non-loopback [4](#0-3) . Because the limiting key is solely the caller-controlled `RemoteIp` field of the `PackObjectsHookWithSidechannelRequest` (populated from `gitaly-hooks`/upload-pack, which trusts the client-visible peer address, and in load-balanced/proxied deployments this can vary or be spoofable), and because it does not incorporate the GlId/user or repository, any threshold placed on "concurrent pack-objects per key" can be defeated by distributing the operations across multiple distinct `RemoteIp` values (or invalid/unparseable IP strings, which the code explicitly bypasses the limiter for — see the `hello-world`/empty-IP test cases showing `shouldLimit: false` in `pack_objects_test.go`). This mirrors the audit's "structuring" bug class: a protection meant to bound the *aggregate* resource cost of an actor's requests only evaluates one narrow dimension (single IP) rather than the actor's true aggregate footprint (user + repository + IP), so many smaller/spread-out requests slip through under the per-key threshold while the sum of concurrent `git pack-objects` processes triggered still lands on the same Gitaly node and repository.

### Impact Explanation
`git pack-objects` is one of the most CPU/memory-intensive operations Gitaly performs (this is precisely why the concurrency limiter and pack-objects cache exist — see `doc/design_pack_objects_cache.md` and `doc/backpressure.md`). Bypassing the per-key concurrency limit lets a single actor (or colluding actors) launch effectively unbounded concurrent `pack-objects` invocations against a repository by structuring their fetch/clone traffic across multiple apparent source IPs (or through IP strings the code fails to parse, which fall through to the unlimited/loopback-style path). This causes resource exhaustion (CPU, memory) on the Gitaly node, potentially producing a denial of service for that repository or the whole node — the "RPC-handler resource limits" bypass class explicitly listed as in-scope.

### Likelihood Explanation
Any client performing repeated clone/fetch operations already controls the pattern and cadence of its own requests; achieving multiple distinct apparent `RemoteIp` values is realistic in real deployments behind load balancers/proxies/NAT pools, via IPv6 address rotation, or in multi-tenant CI environments where many runners hit the same repository concurrently. No privileged access or malicious peer/node compromise is required — this is reachable from an ordinary user's crafted fetch/clone traffic, satisfying the "ordinary user" and "unprivileged" constraints.

### Recommendation
Base the pack-objects concurrency-limiting key on the actual accountable resource footprint of the request set — at minimum the authenticated user identity (`GlId`) combined with the target repository — rather than (or in addition to) the client-reported `RemoteIp`, and do not silently exempt requests whose IP fails to parse from limiting. Consider aggregating limits at the repository level (as is already done for `MaxPerRepo`/RPC concurrency limits) so that splitting requests across many source addresses cannot circumvent the intended aggregate cap on concurrent expensive pack-objects generation for a given repository/user.

### Proof of Concept
1. An authenticated (or unauthenticated, if allowed) user issues N concurrent fetch/clone requests against the same large repository such that each triggers `PackObjectsHookWithSidechannel` with cache misses (e.g., slightly different `--filter`/negotiation so `computeCacheKey` differs, defeating cache reuse) — analogous to "chopping a large order into smaller ones."
2. Each request is crafted/routed to present a distinct `RemoteIp` value (e.g., via different proxy egress IPs, IPv6 addresses from the same /64, or a value that fails `net.ParseIP`/`net.SplitHostPort` such as a hostname string, mirroring the `pack_objects_test.go` "invalid IP addresses" and "empty IP addresses" cases which are documented to *not* be subject to limiting, `shouldLimit: false`).
3. Because `runPackObjectsLimited` keys the semaphore purely on `ipAddr.String()`, each distinct key gets its own concurrency slot (or, for unparseable IPs, no concurrency limiting is applied at all via the `runPackObjects` unlimited path), allowing far more concurrent `git pack-objects` processes against the same repository than the configured per-key limit intends. [5](#0-4) 
4. This is directly exercised (from the defenders' own test intent) in `TestPackObjects_concurrencyLimit`, whose "empty IP addresses" and "invalid IP addresses" cases assert `shouldLimit: false` — i.e., the codebase already documents/accepts that these structured/edge-case requests escape the concurrency limiter. func (s *server) packObjectsHook(ctx context.Context, req *gitalypb.PackObjectsHookWithSidechannelRequest, args *packObjectsArgs, stdinReader io.Reader, output io.Writer) error {
	cacheKey, stdin, err := s.computeCacheKey(ctx, req, stdinReader)
	if err != nil {
		return err
	}

	// We do not know yet who has to close stdin. In case of a cache hit, it
	// is us. In case of a cache miss, a separate goroutine will run
	// git-pack-objects, and that goroutine may outlive the current request.
	// In that case, that separate goroutine will be responsible for closing
	// stdin.
	closeStdin := true
	defer func() {
		if closeStdin {
			stdin.Close()
		}
	}()

	servedBytes, created, err := s.packObjectsCache.Fetch(ctx, cacheKey, output, func(w io.Writer) error {
		ipAddr := net.ParseIP(req.GetRemoteIp())
		if ipAddr == nil {
			// Best effort, maybe the remote IP includes source port
			if ip, _, err := net.SplitHostPort(req.GetRemoteIp()); err == nil {
				ipAddr = net.ParseIP(ip)
			}
		}
		// Ignore loop-back IPs
		if ipAddr != nil && !ipAddr.IsLoopback() {
			return s.runPackObjectsLimited(
				ctx,
				w,
				ipAddr.String(),
				req,
				args,
				stdin,
				cacheKey,
			)
		}

		return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
	})

func (s *server) computeCacheKey(ctx context.Context, req *gitalypb.PackObjectsHookWithSidechannelRequest, stdinReader io.Reader) (string, io.ReadCloser, error) {
	cacheHash := sha256.New()

	repository := req.GetRepository()
	if tx := storage.ExtractTransaction(ctx); tx != nil {
		// The cache uses the requests as the keys. As the request's repository in the RPC handler has been rewritten
		// to point to the transaction's repository, the handler sees each request as different even if they point to
		// the same repository. Restore the original request to ensure identical requests get the same key.
		repository = tx.OriginalRepository(req.GetRepository())
	}

	cacheKeyPrefix, err := protojson.Marshal(&gitalypb.PackObjectsHookWithSidechannelRequest{
		Repository:  repository,
		Args:        req.GetArgs(),
		GitProtocol: req.GetGitProtocol(),
	})
	if err != nil {
		return "", nil, err
	}
	if _, err := cacheHash.Write(cacheKeyPrefix); err != nil {
		return "", nil, err
	}
	stdin, err := bufferStdin(stdinReader, cacheHash)
	if err != nil {
		return "", nil, err
	}
	cacheKey := hex.EncodeToString(cacheHash.Sum(nil))
	return cacheKey, stdin, nil
}

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}
