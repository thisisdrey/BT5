### Title
Unvalidated `RelayFromAddr` in `handleCreateRelayRequest` allows an authenticated peer to poison relay/hostmap state with a spoofed victim address - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` (target-is-me branch) trusts `m.RelayFromAddr` from the wire payload verbatim and calls `AddRelay(rm.l, h, f.hostMap, from, ...)` using that attacker-supplied `from` value as the relay's `PeerAddr`, without ever checking it against `h.vpnAddrs` (the cryptographically authenticated identity of the sender `h`). Any peer that already holds a legitimate, established tunnel to the target can therefore register itself in the target's hostmap as an "Established" relay for an arbitrary third-party victim address it does not own.

### Finding Description
`HandleControlMsg` only rejects `nil` `RelayFromAddr`/`RelayToAddr` before dispatching to `handleCreateRelayRequest`: [1](#0-0) 

Inside `handleCreateRelayRequest`, when the target address in the message matches one of my own addresses (`f.myVpnAddrsTable.Contains(target)`), the code treats the sender `h` as a relay forwarding traffic on behalf of `from = protoAddrToNetAddr(m.RelayFromAddr)` and, if no existing relay state is found, directly calls: [2](#0-1) 

`AddRelay` then inserts a `Relay{PeerAddr: vpnIp, State: Established, Type: TerminalType}` keyed by the attacker-controlled `from` value into `h.relayState`, with no check that `from == h.vpnAddrs[0]`: [3](#0-2) 

By contrast, when a node acts as the *relay* and forwards a request onward toward the real target, the code correctly re-derives the "from" identity from the authenticated peer's own `h.vpnAddrs[0]` rather than trusting the inbound `from` field: [4](#0-3) 

That authenticated re-derivation is absent on the terminal/target side. Since `h` here is any HostInfo with a fully established tunnel to the target (`h.vpnAddrs` is the attacker's own certificate-derived address), an attacker can directly send a `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to an arbitrary victim's `vpnAddr` and `RelayToAddr` set to the target's own address, and the target will register `h` as an "Established" relay entry for that victim address, keyed on the attacker's own HostInfo.

### Impact Explanation
This is remote hostmap/relay-state poisoning: the target's belief about which peer is authorized to relay traffic for a given victim address is corrupted by unauthenticated payload content. This can pollute relay routing decisions for the victim's address on the target node and interfere with legitimate relay setup for that victim, and can be used to exhaust the target's relay index space (32-attempt allocation loop in `AddRelay`) for a given peer. It does not by itself allow decryption or forgery of the victim's actual tunnel traffic, since a genuine data session with the victim would still require an independent, certificate-authenticated Noise handshake; the impact is scoped to relay/hostmap state corruption rather than authentication or crypto bypass.

### Likelihood Explanation
Requires only that the attacker maintain a normal, valid Nebula tunnel to the target (no CA control, no privileged relay role, no config access) — a precondition explicitly allowed by the audit scope. Crafting and sending an arbitrary `NebulaControl` payload over an established Control channel is trivial and fully attacker-controlled, and the vulnerable code path is reached unconditionally whenever the target address matches the receiver's own `vpnAddrs`.

### Recommendation
In the target branch of `handleCreateRelayRequest`, validate that `from` corresponds to a legitimate relay chain: at minimum, do not accept an arbitrary attacker-declared `RelayFromAddr` as the keying identity for relay state tied to `h`'s HostInfo unless `h` is authorized/expected to relay for that address (e.g., cross-check against any pending relay request state initiated locally, or restrict acceptance to cases where `from` was already recorded as pending via `StartRelays`/a corresponding outbound request), rather than trusting the field unconditionally from the wire.

### Proof of Concept
Unit test plan (extending the existing `TestRelayManager_HandleControlMsg_NilRelayAddrs` style tests in `relay_manager_test.go`/`control_test.go`):
1. Build a `HostMap` and a `relayManager` with `rm.useRelays.Store(true)`.
2. Create `HostInfo h` representing the attacker with `h.vpnAddrs = []netip.Addr{atkAddr}` and an established tunnel (`localIndexId` set).
3. Set `f.myVpnAddrsTable` to contain `myAddr` (the target/local node under test).
4. Craft a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: netAddrToProtoAddr(victimAddr), RelayToAddr: netAddrToProtoAddr(myAddr)}` where `victimAddr != atkAddr`.
5. Call `rm.HandleControlMsg(h, marshaledMsg, f)`.
6. Assert (expected fix behavior) that no `Relay` entry keyed on `victimAddr` is inserted into `h.relayState`, i.e. `h.relayState.QueryRelayForByIp(victimAddr)` returns `ok == false`, or that the handler explicitly rejects the request when `from != h.vpnAddrs[0]`.
7. Current code fails this assertion: `AddRelay` succeeds and `h.relayState.QueryRelayForByIp(victimAddr)` returns an `Established`/`TerminalType` relay entry despite `victimAddr` never being `h.vpnAddrs[0]`.
