I'll investigate this by searching for loop-based batch processing in Gitaly that could exhibit a similar "one bad item aborts entire operation" DoS pattern.### Title
`OptimizeRepository` failure on one repository aborts the daily-maintenance walk for an entire storage, starving housekeeping for all sibling repositories - (File: internal/gitaly/maintenance/optimize.go)

### Summary
Gitaly's `DailyOptimizationWorker` walks every repository in a storage once per configured window and runs `git gc`/repack/pack-refs style optimization on each one via `OptimizeRepository`. The walk loop treats *any* non-`errIterOver`/non-`os.IsNotExist` error returned by optimizing a single repository as fatal for the whole storage traversal: it returns immediately and abandons the remaining, unvisited repositories for that maintenance cycle. This mirrors the Frax `getNextValidator()` class of bug: iterating over a collection of independent items where one bad item aborts the entire batch, requiring intervention (here: waiting for the next randomized run and hoping the bad repo isn't hit early, or manual repair) before housekeeping resumes for the rest of the storage.

### Finding Description
`walkReposShuffled` iterates repositories found by `randomWalker` and calls `optimizeRepo` for each one: [1](#0-0) 

The switch statement only tolerates `errIterOver` (walk finished) and `os.IsNotExist` (repo raced away); every other error — including any error propagated from `optimizeRepo`/`OptimizeRepository` — causes `walkReposShuffled` to `return err` immediately: [2](#0-1) 

The caller, `OptimizeReposRandomly`, only logs this error and moves on to the *next storage*, not to the next repository within the same storage: [3](#0-2) 

`OptimizeRepository` itself performs real `git` subprocess work (repack, pack-refs, cruft pack, MVCC GC, etc.) and can fail for repository-specific reasons unrelated to system health — e.g., a Git command failing due to a malformed/corrupted object, a broken ref, or an unexpected repository state that an ordinary user can cause through their own pushes/writes to *their own* repository: [4](#0-3) 

Because the walk order is randomized per run (`randomWalker` shuffles directory entries and storages are shuffled too), a single persistently-broken repository does not deterministically block every run, but it has a chance of being visited before other repos on any given day, and each time it is hit, it truncates that day's optimization pass for the rest of the storage's repositories that had not yet been visited. This is architecturally identical to the reported bug class: a per-item failure inside a loop that processes many independent resources is treated as an all-or-nothing failure of the batch, rather than being skipped so remaining items can still be processed.

### Impact Explanation
Repository housekeeping (garbage collection, pack-refs, cruft packing, MVCC/WAL garbage cleanup) is what keeps repositories from growing unbounded, keeps ref lookups fast, and reclaims disk space from dangling objects and stale write-ahead-log/pool artifacts. If a single repository under a storage can reliably fail `OptimizeRepository` (whether through a corrupted state, or a resource-exhaustion condition tied to that specific repo, e.g., an extremely large or oddly-shaped pack that a `git gc`/repack step consistently errors on), then on any day the randomized walk visits it before other repositories, all of that storage's other repositories are silently skipped for housekeeping that day. Repeated over many days, this can lead to unbounded growth of unrelated repositories' loose object and stale WAL/log directories in the same storage, degrading performance and burning disk space — a low-grade denial of maintenance/availability service rather than a request-level DoS, but it is a genuine resource-starvation/DoS-of-a-background-handler in the same "one bad item halts iteration over shared population" pattern described in the report.

### Likelihood Explanation
This requires an attacker (an ordinary authenticated user able to write to their own repository) to be able to consistently make `OptimizeRepository` return a non-`os.IsNotExist` error for that specific repository. The investigation could not fully confirm a concrete, reliably reproducible input that makes `OptimizeRepository`/the underlying `git` subprocess calls fail deterministically and persistently (e.g., whether Gitaly's housekeeping already treats individual git command failures as best-effort/logged-only versus hard errors in all code paths, and which corrupted states are actually reachable and would not simply be treated as "nothing to optimize"). This limits confidence to "architecturally analogous and reachable via the walk/optimize control flow," while the precise attacker-controlled trigger for `optimizeRepository`'s error path needs further code-path verification (e.g., in `m.optimizeRepository`, `packRefsIfNeeded`, `CleanStaleData`, and the underlying `housekeeping` package) before this can be considered proven end-to-end.

### Recommendation
Change `walkReposShuffled` to log-and-continue on a per-repository optimization failure instead of aborting the whole storage walk, mirroring the `os.IsNotExist` handling already present:
```go
case err != nil:
    l.WithError(err).WithField("relative_path", relativeRepoPath).
        Error("maintenance: repo optimization failed, continuing walk")
    continue
```
Reserve `return err` only for errors that indicate the walk itself cannot make progress (e.g., failure to read the storage root), not for failures isolated to a single repository's optimization.
