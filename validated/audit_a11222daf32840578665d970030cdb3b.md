## Finding

The bazel-analog of this bug class lives in Bazel's Starlark `git_repository`/`new_git_repository` worker, specifically in `update_submodules` in [1](#0-0)  tools/build_defs/repo/git_worker.bzl.

### Title
Forced `protocol.file.allow=always` in `git_repository` submodule initialization re-enables local-clone submodule file disclosure (CVE-2022-39253 class) - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository`/`new_git_repository` (via `git_repo()` in [2](#0-1)  and `_update()` in [3](#0-2) ) invokes `update_submodules` whenever `init_submodules` or `recursive_init_submodules` is set. That function unconditionally passes `-c protocol.file.allow=always` to `git submodule update`: [1](#0-0) 

Upstream Git hardened this exact setting in 2.38.1 in response to advisories about malicious `.gitmodules` submodule URLs abusing the local-clone (`file://`/bare local path) optimization to hardlink or copy files from arbitrary local filesystem locations into the checkout, defaulting `protocol.file.allow` to `user` (i.e. disabled for automated operations like submodule init unless explicitly opted in). Bazel's worker script overrides this hardening back to `always` for every `git_repository`/`new_git_repository` invocation with submodules enabled, regardless of who controls the fetched repository's content.

### Finding Description
`git_repo()` builds fetch/reset refs from the (trusted, root-config) `remote`/`commit`/`tag`/`branch` attributes, but the **content of the fetched repository itself — including its `.gitmodules` file — is untrusted, attacker-controlled data** whenever the `remote`/`branch` points at something the attacker can write to (a PR branch a CI system builds, a repository the attacker controls that a build legitimately consumes, etc.). This is exactly the "files on an untrusted branch CI builds" scenario allowed by the threat model.

Once `_update()` clones/fetches/resets to that revision, if `init_submodules`/`recursive_init_submodules` is set it calls `update_submodules`, which forces `protocol.file.allow=always` for the `git submodule update --init [--recursive] --checkout --force` invocation [1](#0-0) . With this flag forced on, an attacker-crafted `.gitmodules` entry pointing at an arbitrary local path (e.g. an absolute path, or a `file://` URL) is honored: Git performs a *local* clone of that path using its hardlink/local-copy fast path, materializing files from outside the repository into the submodule's working tree inside the external repository directory that Bazel just created.

The comment in the code (referencing bazelbuild/bazel#17040) confirms this was a deliberate compatibility work-around after Git 2.38.1 disabled local-clone-via-submodule by default — Bazel unconditionally restores the pre-hardening, less-safe behavior rather than gating it behind an explicit opt-in or validating submodule URLs.

None of Bazel's existing containment mechanisms stop this: `_clone_or_update_repo`'s `strip_prefix` escape checks in [4](#0-3)  only validate the `strip_prefix` attribute (trusted, root-supplied) and do nothing to constrain what `git submodule update` writes into the checkout directory; there is no equivalent containment check on submodule targets.

### Impact Explanation
An attacker who only controls the content of a git repository/branch that a victim's `git_repository`/`new_git_repository` rule fetches with `init_submodules = True` or `recursive_init_submodules = True` can cause Bazel's git worker to read/copy files from arbitrary local filesystem paths on the build machine into the fetched external repository's working tree. Because that same attacker-controlled repository supplies its own BUILD files (this is the whole point of `git_repository`, as opposed to `new_git_repository` where an external `build_file` is supplied by the trusted root config), the attacker can also add rules that read and exfiltrate (e.g., embed in a build failure message, or process/upload via a build action) the disclosed file contents. This is a concrete "read outside the repository / exec root" containment break with a path to exfiltration, without any credential or MITM assumption.

### Likelihood Explanation
Requires `init_submodules`/`recursive_init_submodules = True` to be set on the `git_repository`/`new_git_repository` call and the fetched revision to be attacker-influenced (a common CI pattern: building a contributor's fork/branch). No MITM, no compromised registry, no local machine access is needed — only the ability to push/serve the git content that the build legitimately clones.

### Recommendation
Do not unconditionally force `protocol.file.allow=always`. Instead:
- Restrict submodule URL protocols to the same protocol class as the top-level `remote` (e.g. only allow `file://` local submodules when the top-level repository itself was fetched via a local path), or
- Validate/reject submodule URLs that resolve to absolute local paths or `file://`/`ext::` schemes before invoking `git submodule update`, or
- Gate the `protocol.file.allow=always` override behind an explicit new repository-rule attribute that a user must opt into, rather than applying it by default to every `init_submodules`/`recursive_init_submodules` invocation.

### Proof of Concept
1. Attacker pushes a branch to a repository that a CI pipeline builds via:
   ```python
   git_repository(
       name = "dep",
       remote = "https://github.com/victim-ci-tested/attacker-fork",
       branch = "pr-branch",           # attacker-controlled
       recursive_init_submodules = True,
   )
   ```
2. On `pr-branch`, the attacker commits a `.gitmodules` such as:
   ```
   [submodule "leak"]
       path = leak
       url = /home/ci-runner/.ssh
   ```
   (or any absolute path on the expected CI runner containing sensitive files/another git repo).
3. When Bazel resolves `@dep`, `_update()` clones/fetches/resets the repo, then calls `update_submodules(ctx, git_repo, recursive=True)`, which runs `git -c protocol.file.allow=always submodule update --init --recursive --checkout --force` [1](#0-0) . Because `protocol.file.allow` is forced to `always`, Git performs the local clone/hardlink of `/home/ci-runner/.ssh` into `@dep`'s `leak/` directory instead of refusing it (the default, safe `user` behavior since Git 2.38.1).
4. The attacker's own BUILD files inside `@dep` (fully attacker-controlled, since this is `git_repository`, not `new_git_repository`) define a target that reads `leak/` and leaks its contents (e.g., via a failing genrule that echoes file contents into the build log, or a build action with network access).

A JUnit/shell reproduction can extend `src/test/shell/bazel/starlark_git_repository_test.sh` [5](#0-4)  by creating a local "attacker" git repo with a `.gitmodules` pointing at an absolute path outside the test's git repo, invoking `git_repository(..., init_submodules = True)` against it, and asserting that the target path's contents appear (unexpectedly) inside the fetched external repository's submodule directory.

def git_repo(ctx, directory):
    """ Fetches data from git repository and checks out file tree.

    Called by git_repository rule.

    Args:
        ctx: Context of the calling rules, for reading the attributes.
        Please refer to the git_repository rule for the description.
        directory: Directory where to check out the file tree.
    Returns:
        The struct with the following fields:
        commit: Actual HEAD commit of the checked out data.
        shallow_since: Actual date and time of the HEAD commit of the checked out data.
    """
    if ctx.attr.shallow_since:
        if ctx.attr.tag:
            fail("shallow_since not allowed if a tag is specified; --depth=1 will be used for tags")
        if ctx.attr.branch:
            fail("shallow_since not allowed if a branch is specified; --depth=1 will be used for branches")

    # Use shallow-since if given
    if ctx.attr.shallow_since:
        shallow = "--shallow-since=%s" % ctx.attr.shallow_since
    else:
        shallow = "--depth=1"

    reset_ref = ""
    fetch_ref = ""
    if ctx.attr.commit:
        reset_ref = ctx.attr.commit
        fetch_ref = ctx.attr.commit
    elif ctx.attr.tag:
        reset_ref = "tags/" + ctx.attr.tag
        fetch_ref = "tags/" + ctx.attr.tag + ":tags/" + ctx.attr.tag
    elif ctx.attr.branch:
        reset_ref = "origin/" + ctx.attr.branch
        fetch_ref = ctx.attr.branch + ":origin/" + ctx.attr.branch
    else:
        reset_ref = "origin/HEAD"
        fetch_ref = "HEAD:refs/remotes/origin/HEAD"

    git_repo = _GitRepoInfo(
        directory = ctx.path(directory),
        shallow = shallow,
        reset_ref = reset_ref,
        fetch_ref = fetch_ref,
        remote = str(ctx.attr.remote),
        init_submodules = ctx.attr.init_submodules,
        recursive_init_submodules = ctx.attr.recursive_init_submodules,
    )

    _report_progress(ctx, git_repo)
    if ctx.attr.verbose:
        print("git.bzl: Cloning or updating %s repository %s using strip_prefix of [%s]" %
              (
                  " (%s)" % shallow if shallow else "",
                  ctx.name,
                  ctx.attr.strip_prefix if ctx.attr.strip_prefix else "None",
              ))

    _update(ctx, git_repo)
    ctx.report_progress("Recording actual commit")
    actual_commit = _get_head_commit(ctx, git_repo)
    shallow_date = _get_head_date(ctx, git_repo)

    return struct(commit = actual_commit, shallow_since = shallow_date)

def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)

def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
