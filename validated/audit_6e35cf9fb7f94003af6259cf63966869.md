### Title
Unauthenticated `RecvError` packet allows spoofed remote-state teardown, bypassing ConnectionManager/HandshakeManager's exclusive control of tunnel lifecycle - (File: outside.go)

### Summary
Nebula's `RecvError` message type is processed entirely outside of the Noise/cert-authenticated pipeline: it carries no cert, no encryption, and no replay protection, yet it directly triggers `closeTunnel()` and `handshakeManager.DeleteHostInfo()` on the hostinfo it names, the same kind of state-mutating action that `ConnectionManager`/`HandshakeManager` normally perform only after their own bookkeeping (traffic checks, dead-tunnel detection, handshake retries). This mirrors the external report's bug class: a privileged orchestrator (`Upkeep`) assumed exclusive control over a state-mutating action (`VestingWallet.release()`), but an unauthenticated caller could invoke it directly and desynchronize state. Here, `ConnectionManager`/`HandshakeManager` assume they are the only path to hostinfo teardown, but `handleRecvError` provides an unauthenticated side-door.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches `header.RecvError` before any cert/AEAD verification: [1](#0-0) 

`handleRecvError` is reached with only two checks: a config gate (`acceptRecvErrorConfig.ShouldRecvError`) and a comparison of the claimed source `addr` against `hostinfo.GetRemote()`: [2](#0-1) 

Both `h.RemoteIndex` (a 32-bit index, sent in cleartext in every packet header on the wire) and the UDP source `addr` are attacker-controlled/observable values with no cryptographic binding. UDP allows straightforward source-address spoofing when the attacker is on-path (or when no ingress filtering/BCP38 is present), and the `RemoteIndex` value is visible in plaintext on every packet of an active tunnel. An attacker with no CA-signed certificate — i.e., who never participates in a real Noise handshake — can:
1. Observe (sniff) or otherwise learn a victim's active `RemoteIndex` and current remote `addr` from cleartext headers of on-going traffic.
2. Forge a single unauthenticated `RecvError` packet with that index/address.
3. Cause the receiving node to unilaterally call `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` — tearing down the tunnel's state entirely outside of the components (`ConnectionManager`, `HandshakeManager`) that are supposed to be the sole arbiters of tunnel lifecycle.

This is structurally the same defect as the vesting-wallet finding: a state-mutating function reachable without any authorization check, while a separate "trusted" orchestrator assumes it is the only path to that mutation, resulting in desynchronized/lost state (in Nebula's case, a live tunnel silently destroyed and forced into re-handshake, rather than "SALT locked forever" — but the root cause class, missing access control on a privileged state transition, is analogous).

### Impact Explanation
An unauthenticated remote attacker (no valid Nebula certificate, no participation in a handshake) can force teardown of arbitrary active tunnels between legitimate nodes by spoofing a single UDP packet, provided they can observe or guess the victim's currently-active `RemoteIndex` and remote address (both of which travel in cleartext on every packet of the tunnel). This is a remote state-poisoning / denial-of-service primitive: it bypasses the connection manager's traffic-based liveness accounting entirely, and can be repeated to continuously disrupt tunnels, causing churn/flapping and denial of service without ever presenting a valid certificate.

### Likelihood Explanation
Exploitability depends on the attacker's position: an on-path attacker (able to sniff cleartext headers, e.g., anywhere along the UDP path, a shared network segment, or a compromised intermediate router/NAT) can trivially read `RemoteIndex` and the current remote `AddrPort` from any observed packet and replay them in a crafted `RecvError`. An off-path attacker would need to guess both a live random 32-bit index and match the current source `AddrPort`, which is impractical at Internet scale but becomes easier in a LAN/hole-punching scenario where source ports are more predictable. The `accept_recv_error` config can restrict this (e.g., set to "never" or "private"), but the default configuration ("always") accepts these packets from any source.

### Recommendation
- Require the `RecvError` action to at least go through the same authenticated/keyed feedback loop as other control decisions, e.g., only accept it if it can be tied to a legitimately observed OS-level `ICMP port-unreachable`/`ECONNREFUSED` originating from the interface's own send path (as originally intended), rather than trusting any inbound UDP frame with a matching index/address.
- Add a challenge/response or a short-lived cryptographic nonce to `RecvError` acknowledgement so the receiving side cannot be forced to tear down a tunnel purely from an unauthenticated packet.
- Rate-limit and log `RecvError`-triggered teardown events distinctly from `connectionManager`-triggered teardown, and consider disestablishing only "pending"/half-open state rather than fully authenticated Established tunnels via this path.
- Default `listen.accept_recv_error` to a safer value (e.g., "private" or "never") when the node is reachable from the public Internet.

### Proof of Concept
1. Establish a working Nebula tunnel between node `me` and node `them` (see `TestCloseTunnelAuthenticated` for a similar harness) using two `newSimpleServer` controls, wait for handshake completion.
2. Sniff (or, in the e2e test harness, directly read via `ControlHostInfo.RemoteIndex`/`CurrentRemote`) the live `RemoteIndex` and remote `AddrPort` values that `them` uses for its tunnel to `me` — these are visible in cleartext in the header of every packet, as demonstrated by the same test harness pattern used in `TestCloseTunnelAuthenticated` for forging a bogus `CloseTunnel` packet: [3](#0-2) 
3. Instead of crafting a `header.CloseTunnel` frame (which — per that test — is correctly rejected because it requires AEAD decryption/authentication), craft a `header.RecvError` frame with `RemoteIndex` set to the victim's known index, and inject it as if from the victim's currently-registered remote address:
```go
hdr := header.H{
    Version:     1,
    Type:        header.RecvError,
    RemoteIndex: hi.RemoteIndex, // sniffed/known cleartext index
}
buf, _ := hdr.Encode(make([]byte, header.Len))
pkt := &udp.Packet{To: <victim_listen_addr>, From: hi.CurrentRemote, Data: buf}
// inject pkt to victim's UDP listener
```
4. On the victim side, `readOutsidePackets` routes this directly to `handleRecvError` (`outside.go:81-83`) with no cert/AEAD check, and — because `addr == hostinfo.GetRemote()` — proceeds to call `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` (`outside.go:572-574`), instantly destroying the tunnel's hostmap and handshake-manager state without any cryptographic authentication, unlike the `CloseTunnel` path which is provably rejected in `TestCloseTunnelAuthenticated` because it requires valid AEAD decryption.

Note on confidence: I could not fully trace the definitions of `recvErrorAlways`/`recvErrorPrivate`/`ShouldRecvError` in `interface.go` within the available tool budget (the grep matched but I did not get to read the exact logic), so the precise semantics of the "private" mode's filtering (e.g., whether it restricts to RFC1918 sources only) are not fully confirmed here; this affects only the exact bar to reach exploitability under non-default configs, not the core finding that the default path lacks cryptographic authentication.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
