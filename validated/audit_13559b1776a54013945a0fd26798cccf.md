## Analysis

The `add_tip` extrinsic in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` presents a genuine analog to the base_pool `stored_balances` bug: an accounting action is committed on the local (AssetHub) side unconditionally, while the corresponding "settlement" action is only attempted (and may fail) asynchronously on a remote chain (BridgeHub), with no way to reconcile or reverse the local side once it has already burned real user funds.

### Title
Unrefundable Fund Burn on Unconditional Tip Swap-and-Burn Before Unverified Remote Reward Allocation — ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

### Summary
`Pallet::add_tip` at [1](#0-0)  immediately swaps the user's tip asset for ether and irrevocably burns it via `swap_fee_asset_and_burn` / `burn_for_teleport` **before** any confirmation that the remote `AddTip` bookkeeping on BridgeHub will succeed. The XCM `Transact` call that credits the tip to the message's reward on BridgeHub is only dispatched afterward, and is fire-and-forget (`UnpaidExecution`/no callback). If the remote `AddTip::add_tip` call in `bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` or `outbound-queue-v2` fails (e.g. `NonceConsumed` because the nonce was already processed, or `UnknownMessage`), the tip is only recorded into `LostTips` on BridgeHub (see [2](#0-1) ) — a storage entry with no defined mechanism in this repository to actually restore/refund the burned asset back to the user on AssetHub.

### Finding Description
This mirrors the reported Curve bug's core invariant break: an internal accounting update (`stored_balances`/here, the "ether burned for a tip") is committed unconditionally in one code path, while the state that is supposed to correspond to it (the actual reward credit, gated behind nonce-consumption checks) is updated in a separate, independently-failable path.

Specifically:
1. `add_tip` calls `Self::swap_fee_asset_and_burn(who.clone().into(), asset)?` at line 267, which performs `T::Swap::swap_exact_tokens_for_tokens` and then `burn_for_teleport::<T::AssetTransactor>` — a real, irreversible destruction of the user's asset balance on AssetHub.
2. Only afterward does it build and dispatch (via unpaid, unverified XCM `Transact`) the `AddTip` call to BridgeHub (lines 269–272).
3. On BridgeHub, `EthereumSystemV2::add_tip` ( [3](#0-2) ) calls into `InboundQueue::add_tip`/`OutboundQueue::add_tip`, which can return `AddTipError::NonceConsumed` if `Nonce::<T>::get(nonce)` is already true ( [4](#0-3) ).
4. On failure, the pallet **does not revert or refund anything** — it simply records the lost amount into `LostTips` and always returns `Ok(())` from the dispatchable (line 280 `Ok(())` unconditionally), meaning even the caller cannot detect failure on-chain except via event inspection.

The existing guards (`ensure!(!Nonce::<T>::get(nonce), ...)` on BridgeHub, and burn-before-transact on AssetHub) do not stop this because they operate on two separate chains with no atomic cross-chain commit; the AssetHub-side burn is final and non-transactional relative to the BridgeHub-side bookkeeping outcome.

### Impact Explanation
A user who tips a message whose nonce has *already been relayed* (a very plausible race — e.g., another relayer processes the underlying message while the tip transaction is in flight, or the user's tip transaction targets a stale nonce) has their real, fungible asset (e.g. DOT) irrecoverably swapped and burned, while the reward is never credited to any relayer and the user has no path to reclaim it beyond an unlinked `LostTips` ledger entry that has no corresponding extrinsic in this pallet to convert back into spendable balance. This is a permanent user-fund loss caused by ordinary (non-malicious) call ordering/race conditions, not an attacker exploit requiring a malicious relayer, governance action, or leaked keys.

### Likelihood Explanation
This is not a hypothetical: the `NonceConsumed` failure path is explicitly tested in `bridges/snowbridge/pallets/system-v2/src/tests.rs::add_tip_inbound_fails_when_nonce_is_consumed` [5](#0-4) , confirming the developers are aware `add_tip` can fail post-hoc and simply route the amount into `LostTips` rather than preventing the burn. Any ordinary relayer racing to process a message before a user's tip lands will trigger this loss condition — no privileged or malicious actor is required.

### Recommendation
Do not burn/swap the tip asset on AssetHub until the BridgeHub side has confirmed the nonce is unconsumed and the tip can be recorded (e.g., via a receipt-and-settle two-phase pattern, or by holding/escrowing the asset until an acknowledgment XCM confirms success and only then finalizing the burn). Alternatively, implement an actual `LostTips` claim/refund extrinsic that can restore the corresponding value to the affected account on AssetHub, closing the loop that currently only exists as a bookkeeping stub.

### Proof of Concept
1. User A wants to tip nonce `N`'s relayer reward. They call `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Inbound(N), tip_asset)` on AssetHub.
2. `swap_fee_asset_and_burn` executes: DOT is swapped to ether and burned via `burn_for_teleport` — irreversible, real balance change ( [6](#0-5) ).
3. Concurrently, a relayer submits and finalizes message `N` via `InboundQueueV2::submit`, which sets `Nonce::<T>::set(nonce)` ( [7](#0-6) ) before User A's tip XCM arrives at BridgeHub.
4. The `AddTip` XCM `Transact` executes `EthereumSystemV2::add_tip`, which calls `InboundQueue::add_tip(N, amount)`, hits `ensure!(!Nonce::<T>::get(nonce), AddTipError::NonceConsumed)` and returns `Err(NonceConsumed)`.
5. `EthereumSystemV2::add_tip` catches this error, adds `amount` to `LostTips::<T>::get(sender)`, and returns `Ok(())` regardless ( [8](#0-7) ).
6. User A's DOT is permanently gone (burned in step 2); no relayer received the tip; `LostTips` records the loss but this repository provides no extrinsic to convert `LostTips` back into a real balance for User A.

**Note on confidence:** I could not find, within the indexed portion of this repository, any pallet extrinsic that consumes `LostTips` to restore user funds — if such a recovery mechanism exists elsewhere and was not indexed, that would mitigate (but not eliminate, given the unconditional pre-burn) this finding. I recommend a full repository check (e.g. via a Devin session) to confirm whether a `LostTips` claim path exists anywhere in `bridges/snowbridge/pallets/system-v2/` or related runtimes.

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}

		fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
			ensure!(amount > 0, AddTipError::AmountZero);
			// If the nonce is already processed, return an error
