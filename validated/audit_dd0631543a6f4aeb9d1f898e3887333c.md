Audit Report

## Title
Per-account HOP submit rate limiter is enforced *after* the expensive authorization/signature work, letting an authorized (unprivileged, non-admin) account flood `hop_submit` and stall a collator's block production - (File: `substrate/client/hop/src/rpc.rs`)

## Summary
`HopRpcServer::submit` performs a runtime-API call for `max_promotion_size`, a second runtime-API call (state-trie read) for `can_account_promote`, and a full cryptographic signature verification before ever calling `HopDataPool::insert`, which is the only place `RateLimiter::check` is invoked. [1](#0-0)  Any account satisfying `can_account_promote` can therefore trigger this full expensive chain on every call regardless of `submit_rate_per_min`/`submit_burst`, since the token bucket only gates entry into `insert` and never gates the earlier authorization/signature work.

## Finding Description
The `submit` handler executes, in strict order: SCALE-decoding, a `max_promotion_size` runtime-API call, a `can_account_promote` runtime-API call (state read), `MultiSignature::verify`, and only then `self.pool.insert(...)`. [2](#0-1)  The rate limiter is invoked only inside `insert`, immediately before capacity bookkeeping. [3](#0-2)  `RateLimiter::check` implements a straightforward per-`SenderId` token bucket for requests and bandwidth, gated by an `enabled` flag and refilled lazily from `Instant`. [4](#0-3)  The module doc explicitly frames this as the DoS defense for the HOP submit path, alongside the node's global RPC connection limit. [5](#0-4)  The code comment at the authorization check shows the authors deliberately ordered the oversized-payload and authorization checks *before* signature verification specifically to prevent a flood from forcing cheap-relative-to-signature work, but the same reasoning was not symmetrically applied to the rate limiter itself, which remains strictly last. [6](#0-5)  Consequently, an account that the runtime authorizes via `can_account_promote` — described in the README as potentially "any other policy" the runtime chooses, including reuse of an existing on-chain authorization — can invoke `hop_submit` at an arbitrary rate, and each call still forces two runtime-API dispatches and one signature verification before the token bucket has any chance to reject it. [7](#0-6) 

## Impact Explanation
`hop_submit` is marked `blocking`, running on the JSON-RPC blocking thread pool of a HOP-enabled collator node. [8](#0-7)  Sustained flooding by one authorized account forces unbounded state-trie reads and CPU-bound signature verifications per call, consuming node resources on a public JSON-RPC surface that is supposed to be bounded by the very rate limiter that is bypassed for cost purposes — matching the "public underpriced work that degrades block production" impact category, since compute/state-read cost is incurred regardless of whether the request is ultimately rejected by the token bucket.

## Likelihood Explanation
Reproducible deterministically on every call; requires only one keypair the runtime's `can_account_promote` policy authorizes and the ability to construct syntactically valid submit RPC arguments, both of which are described in the module's own documentation as ordinary, non-privileged requirements rather than an admin or governance action.

## Recommendation
Move the `RateLimiter::check` call to the first admission-control step in `HopRpcServer::submit`, before the `max_promotion_size` and `can_account_promote` runtime-API calls and before `multi_sig.verify`, keyed on the cheaply-derivable claimed sender identity, so that over-budget callers are rejected before any runtime API dispatch or cryptographic verification occurs.

## Proof of Concept
1. Configure a node with HOP enabled and a runtime whose `can_account_promote` authorizes account `A`.
2. Using `A`'s keypair, send `hop_submit` requests via JSON-RPC well above `--hop-submit-rate-per-min`/`--hop-submit-burst`, each with a distinct payload and valid signature.
3. Observe that every request still triggers `HopRuntimeApi_max_promotion_size`, `HopRuntimeApi_can_account_promote` (state read), and full `MultiSignature::verify` — per `substrate/client/hop/src/rpc.rs:182-214` — before `RateLimiter::check` in `substrate/client/hop/src/pool.rs:374-376` ever executes, confirming the token bucket only bounds *stored* entries, not the CPU/state-read cost imposed per request.

		// Reject oversized payloads before the per-account authorization lookup so
		// a flood of too-big submits cannot force runtime state reads. The cap is
		// the runtime-declared `max_promotion_size`; the runtime is authoritative.
		let runtime_max = runtime_api::max_promotion_size::<Block, _>(&*self.client, best_hash)
			.map_err(HopError::from)?;
		if data_len > runtime_max as usize {
			return Err(HopError::DataTooLarge(data_len, runtime_max).into());
		}

		// Check authorization before verifying the signature: a flood of unauthorized
		// requests must not force a signature verification per submit.
		// `can_account_promote` returns false for any reason the runtime rejects:
		// unauthorized account or exhausted per-account quota.
		let account_id: AccountId32 = signer.clone().into_account();
		let authorized = runtime_api::can_account_promote::<Block, _>(
			&*self.client,
			best_hash,
			account_id.clone(),
			data_len as u32,
		)
		.map_err(HopError::from)?;
		if !authorized {
			return Err(HopError::NotAuthorized.into());
		}

		// Domain-separated payload so a submit signature cannot be replayed as claim/ack,
		// and bound to `submit_timestamp` so an old signature can't be replayed long
		// after the fact (the runtime enforces a tolerance window on the timestamp).
		let hash = H256(blake2_256(&data.0));
		let submit_payload = submit_signing_payload(&hash, submit_timestamp);
		if !multi_sig.verify(&submit_payload[..], &account_id) {
			return Err(HopError::InvalidSignature.into());
		}

		let sender_id: [u8; 32] = account_id.into();
		self.pool
			.insert(data.0, recipient_keys, sender_id, signer, multi_sig, submit_timestamp)?;
		Ok(SubmitResult { pool_status: self.pool.status() })
	}

	/// Check whether this account may submit `data_len` bytes right now.
	///
	/// Returns `Ok(())` on admission (tokens consumed) or `Err(retry_after_secs)`
	/// when either bucket is empty.
	pub fn check(&self, sender_id: &SenderId, data_len: u64) -> Result<(), u64> {
		if !self.cfg.enabled {
			return Ok(());
		}

		let now = Instant::now();
		let state = self.get_or_create(sender_id, now);
		let mut state = state.lock();
		state.last_touch = now;

		let req_wait = state.requests.try_consume(1.0, now).err();
		if let Some(wait) = req_wait {
			return Err(wait.as_secs().max(1));
		}

		// If the bandwidth bucket is exhausted, reject immediately and refund the request
		// token so both buckets stay consistent.
		if let Err(wait) = state.bandwidth.try_consume(data_len as f64, now) {
			// Refund the request token we just took so the two buckets stay consistent.
			state.requests.tokens = (state.requests.tokens + 1.0).min(state.requests.capacity);
			return Err(wait.as_secs().max(1));
		}

		Ok(())
	}
