### Title
Dust-transfer griefing fills a victim's `MAX_TOKENS_PER_USER` slots, blocking new collateral deposits and debt issuance - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a combined per-account cap (`MAX_TOKENS_PER_USER`) on `debtTokensOfAccount` + `depositTokensOfAccount`, enforced inside `onlyIfAdditionWillNotReachMaxTokens` on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` (contracts/Pool.sol:143-148, 204-219). Because `DepositToken._transfer` and `_mint` call `pool.addToDepositTokensOfAccount` for *any* first-time recipient (contracts/DepositToken.sol:518-525, 485-488), an unprivileged attacker can deposit dust into every collateral type and `transfer` one wei of each `msdTOKEN` to a victim, filling the victim's slot budget with junk entries. From then on, the victim cannot deposit any *new* collateral type nor issue any *new* synthetic debt — the `add` revert propagates through `_mint`/`deposit` (contracts/DepositToken.sol:211-237) and `DebtToken` issuance.

### Finding Description
- `DepositToken.transfer`/`transferFrom` have no opt-in on the recipient side; `_transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` when the recipient's prior balance is 0 (contracts/DepositToken.sol:517-520).
- `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (contracts/Pool.sol:143-148).
- Entry removal (`removeFromDepositTokensOfAccount`) only occurs when the token balance returns to 0 (contracts/DepositToken.sol:522-525). If the victim already has debt, the dust balance is *locked* collateral: `unlockedBalanceOf` returns only the portion backed by `_issuableInUsd` (contracts/DepositToken.sol:383-398), so the victim cannot send the dust away to free the slot while their position is unhealthy.
- Result: an unhealthy or near-unhealthy victim is permanently unable to add a new collateral type to recover health — the exact action designed to avoid liquidation. Their position becomes a guaranteed liquidation target, while liquidation itself (`Pool.liquidate`, contracts/Pool.sol:541-596) still succeeds since `seize` adds the token to the *liquidator's* list, which the attacker can pre-fill too to grief specific liquidators.
- No modifier stops this: `transfer` only checks `_revertIfLocked` on the *sender* (attacker), and `addToDepositTokensOfAccount` has no allowlist of senders — any holder of a deposit token can impose a slot on any address.

### Impact Explanation
Liveness/position-management DoS consistent with the CVE's null-deref→denial-of-service class: a missing-slot condition (`UserReachedMaxTokens` revert, the analog of dereferencing an unavailable entry) causes targeted victims to permanently lose the ability to deposit new collateral or open new debt positions while they carry debt, forcing their positions into liquidation they cannot defend against (indirect loss of funds via forced liquidation / temporary freezing of the deposit function for arbitrary duration). The attack is cheap: dust transfers of each supported deposit token.

### Likelihood Explanation
Any EOA can perform it with trivial cost (dust deposits + transfers). The constraint is that the victim can evade it while *debt-free* by transferring the dust back out (`balance → 0` triggers `removeFromDepositTokensOfAccount`), so the durable impact is limited to accounts already holding debt with insufficient unlocked balance — precisely the accounts most harmed by it. No privileged role, oracle manipulation, or governance input is required. Caveat not fully verified within iteration limits: the exact `MAX_TOKENS_PER_USER` constant (in storage/PoolRegistry config) and whether `DebtToken` transfers are permissionless affect how many transactions the attacker needs; if the cap equals the number of onboarded tokens, the victim may already be near the limit.

### Recommendation
- Only credit a deposit-token slot to the recipient when `recipient_ == msg.sender`-initiated deposits, or make `addToDepositTokensOfAccount` tolerant: if the list is full, skip tracking rather than revert (tracking is only needed for `depositOf`/`debtOf` iteration; an alternative is letting recipients keep an untracked balance and excluding it from collateral math).
- Alternatively, allow any account to purge its own list entries (a `removeDustToken(token)` that sweeps balance < threshold) so griefed slots are always recoverable regardless of locked state.
- Apply the same fix on the debt-token side (`addToDebtTokensOfAccount`, contracts/Pool.sol:204-208).

### Proof of Concept
Hardhat fork test (Base/Optimism deployment):

```ts
// victim has an open position (deposit + issue) so dust is locked
await msdMET.connect(victim).deposit(parseEther('100'), victim.address);
await msEthDebtToken.connect(victim).issue(parseEther('1'), victim.address);

// attacker deposits dust into every deposit token and transfers it to victim
for (const dt of [msdMET, msdDAI, /* ...all DepositTokens */]) {
  const underlying = await ethers.getContractAt('IERC20', await dt.underlying());
  await underlying.connect(attacker).approve(dt.address, MaxUint256);
  await dt.connect(attacker).deposit(1n, attacker.address);   // 1 wei
  await dt.connect(attacker).transfer(victim.address, 1n);    // occupies a slot
}
// repeat with fresh deposit-token types until combined length == MAX_TOKENS_PER_USER
expect(await pool.getDepositTokensOfAccount(victim.address))
  .to.have.length.gte(MAX_TOKENS);

// victim's new deposit of a previously-unused collateral reverts
await expect(msdNewToken.connect(victim).deposit(amount, victim.address))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// victim cannot clear slots while unhealthy: dust is locked
await expect(msdMET.connect(victim).transfer(attacker.address, 1n))
  .to.be.revertedWithCustomError(msdMET, 'NotEnoughFreeBalance');

// attacker-driven price move / time passes -> position unhealthy -> liquidated
await masterOracle.updatePrice(met.address, crashPrice);
await pool.connect(liquidator).liquidate(msEth.address, victim.address, amt, msdMET.address);
```

If the exact `MAX_TOKENS_PER_USER` value or `DebtToken` transferability differs such that the cap can never be reached on the deployed configuration, the finding degrades to no impact; otherwise this stands as a valid DoS analog.
