### Title
Stale on-chain order state after zero-quantity maker match allows double-crediting of returned sell tokens - ([File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java])

### Summary
`MarketSellAssetActuator.matchSingleOrder` contains an edge case (the "taker > maker" branch when the computed `makerBuyTokenQuantityReceive` rounds to `0`) where the maker's remaining sell tokens are refunded to the maker's balance and the order is marked `INACTIVE` in the account-order index, but the updated `MarketOrderCapsule` (state, `sellTokenQuantityRemain`) is **never persisted to `MarketOrderStore`** because the method returns before reaching the trailing `orderStore.put(...)` call. This is directly analogous to the Abracadabra bug class: a state-mutating step (self-liquidation / dust-match refund) updates auxiliary bookkeeping but leaves the authoritative object ("collateral position" / "market order") stale, so it can later be replayed against.

`MarketUtils.updateOrderState` only mutates the in-memory `orderCapsule.setState(...)` and persists a removal from `MarketAccountOrderCapsule` (the account's active-order index) — it never writes the order itself into `MarketOrderStore`: [2](#0-1) 

The dust-quantity branch's guarding comment ("it would not happen here... for the maker, when sellQuantity < buyQuantity, it will get at least one buyToken even when sellRemain = 1") is only valid for maker orders where `sellTokenQuantity < buyTokenQuantity`. `MarketSellAssetActuator.validate()` places no such constraint on the relationship between `sellTokenQuantity` and `buyTokenQuantity` — it only requires both to be `> 0` and below `getMarketQuantityLimit()`: [3](#0-2) 

Consequently, a maker who places an order selling a large quantity of tokenA for a small quantity of TRX (`sellTokenQuantity >> buyTokenQuantity`) can have `makerBuyTokenQuantityReceive = floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity)` round to `0`, hitting the "should not happen" branch. When this occurs:
1. `returnSellTokenRemain` credits the maker's account with `sellTokenQuantityRemain` (the maker's unfilled tokens) — a **real, persisted** balance change (`accountStore.put` happens inside the caller `matchOrder`/`matchSingleOrder` via `addTrxOrToken`/`returnSellTokenRemain`, which internally calls `accountStore.put`).
2. `updateOrderState` removes the order id from the account's active-order list (`MarketAccountOrderCapsule`) — a **persisted** change.
3. The `MarketOrderCapsule` object in `MarketOrderStore` is **never re-written** — on disk it still shows `State.ACTIVE` (or whatever it was before this match) with its *original, non-zero* `sellTokenQuantityRemain`.

The order is subsequently removed from the in-memory `pairPriceToOrderStore` order list by the caller (`matchOrder`) based on the in-memory object's `getSellTokenQuantityRemain() == 0`, so it disappears from the live order book — but the ghost `MarketOrderCapsule` record with stale non-zero quantity and `ACTIVE` state remains queryable/actionable in `MarketOrderStore`.

The maker can then submit a `MarketCancelOrderContract` for that same `orderId`. `MarketCancelOrderActuator.validate()` only checks `orderStore.get(orderId)` and `orderCapsule.isActive()` — both of which read the **stale, unpersisted-update** record and pass: [4](#0-3) 

`MarketCancelOrderActuator.execute()` then calls `MarketUtils.returnSellTokenRemain(orderCapsule, ...)` again, using the stale (original, non-zero) `sellTokenQuantityRemain`, crediting the maker's account **a second time** for tokens that were already refunded in step 1 above: [5](#0-4) 

This mirrors the Abracadabra pattern precisely: a failed/degenerate operation (deposit that reverts / match that yields 0 tokens) leaves an accounting object in a state disconnected from the "cleanup" that already happened (self-liquidation / INACTIVE-marking), and that stale object is then usable as if it were still valid collateral (an order still holding sellable/refundable quantity).

### Impact Explanation
If reachable, this creates unbacked TRX/TRC10 asset balance out of thin air for the attacker (double-crediting the same sell-token quantity), directly matching the "unbacked balance / theft of funds" impact criteria. The attacker only needs to: (1) place a crafted sell order with `sellTokenQuantity` and `buyTokenQuantity` chosen so that a partial maker fill rounds `makerBuyTokenQuantityReceive` to zero, (2) have (or trigger) a taker order that partially fills it triggering the zero-receive branch, and (3) call `MarketCancelOrderContract` on the same order id afterward. All three steps are ordinary signed transactions reachable by any unprivileged account — no SR/witness/committee privilege required, matching the allowed threat model (order placer / transaction broadcaster).

### Likelihood Explanation
Reaching the zero-quantity branch requires crafting an order pair/quantity and a matching taker fill amount such that integer division rounds to 0 — this is deterministic and fully attacker-controlled via the public `MarketSellAssetContract` parameters (`sellTokenQuantity`, `buyTokenQuantity`) combined with a self-controlled or colluding counter-order, so it is practically achievable without needing any privileged actor. The subsequent cancel call is a normal `MarketCancelOrderContract`. I could not fully trace whether an exception is thrown later in `MarketCancelOrderActuator.execute()` (e.g. inside `MarketAccountOrderCapsule.removeOrder` or `pairPriceToOrderStore.get(pairPriceKey)`, since the order id/price key bookkeeping may already have been cleaned up by the earlier match) that could abort the transaction and roll back the double-credit before it's committed — this needs verification of `MarketAccountOrderCapsule.removeOrder` and `MarketOrderIdListCapsule.removeOrder` semantics (whether they throw on a missing/already-removed id) and of java-tron's per-transaction rollback/session behavior on actuator exceptions, which I was unable to inspect before running out of tool budget.

### Recommendation
- In `MarketSellAssetActuator.matchSingleOrder`, always persist `makerOrderCapsule` to `MarketOrderStore` (and `takerOrderCapsule` where relevant) immediately after any state/quantity mutation, including on the early-return path for the zero-quantity branch — do not rely on a fall-through `orderStore.put` that can be skipped by a `return`.
- Remove the incorrect assumption in the comment ("it would not happen here") and add an explicit test/guard covering maker orders where `sellTokenQuantity > buyTokenQuantity`.
- After marking an order `INACTIVE`/`CANCELED` via `MarketUtils.updateOrderState`, ensure the same call site immediately persists the order capsule to `MarketOrderStore` inside `updateOrderState` itself (single source of truth) rather than leaving persistence to be handled inconsistently by each caller.
- Add invariant checks in `MarketCancelOrderActuator.validate()`/`execute()` that cross-check `MarketOrderCapsule` state consistency against `MarketAccountOrderCapsule`'s active-order list before allowing a refund.

### Proof of Concept
1. Attacker account A creates a sell order via `MarketSellAssetContract`: `sellTokenId = X`, `sellTokenQuantity = 1_000_000`, `buyTokenId = "_"` (TRX), `buyTokenQuantity = 1`. This order rests in the book as maker (assuming no immediate match).
2. A second account B (can be attacker-controlled) submits a `MarketSellAssetContract` as taker with `sellTokenId = "_"`, `buyTokenId = X`, quantities chosen so it partially fills A's order such that in `matchSingleOrder`'s "taker > maker" branch, `makerSellRemainQuantity` at the time of matching is small enough that `multiplyAndDivide(makerSellRemainQuantity, 1, 1_000_000, ...)` floors to `0` (e.g. `makerSellRemainQuantity <= 999_999`).
3. Execution takes the `makerBuyTokenQuantityReceive == 0` branch: A's remaining `sellTokenQuantityRemain` (tokenX) is credited back to A's account balance, the order is removed from A's active order list, but `MarketOrderStore` for that `orderId` retains `State.ACTIVE` and the original non-zero `sellTokenQuantityRemain`.
4. Attacker A submits `MarketCancelOrderContract` for the same `orderId`. `validate()` reads the stale `ACTIVE` order and passes; `execute()` calls `MarketUtils.returnSellTokenRemain` again, crediting A's account with the same tokenX quantity a second time.
5. Net result: account A has received tokenX refunds twice for tokens that were only ever deposited once — an unbacked balance increase, analogous to Abracadabra's "borrow against a ghost" collateral reuse.

(Note: whether step 4 fully completes without an exception from stale-index bookkeeping in `MarketAccountOrderCapsule`/`MarketOrderIdListCapsule` could not be conclusively confirmed within the available investigation and should be validated with a live/unit test against the actual store implementations before treating this as fully proven end-to-end.)

  public static void updateOrderState(MarketOrderCapsule orderCapsule,
      State state, MarketAccountStore marketAccountStore) throws ItemNotFoundException {
    orderCapsule.setState(state);

    // remove from account order list
    if (state == State.INACTIVE || state == State.CANCELED) {
      MarketAccountOrderCapsule accountOrderCapsule = marketAccountStore
          .get(orderCapsule.getOwnerAddress().toByteArray());
      accountOrderCapsule.removeOrder(orderCapsule.getID());
      marketAccountStore.put(accountOrderCapsule.createDbKey(), accountOrderCapsule);
    }
  }
