## Title
Fixed TRX↔token exchange rate in `ParticipateAssetIssueContract` never reflects TRX/token market price during the (potentially long) crowdsale window - (File: `actuator/src/main/java/org/tron/core/actuator/ParticipateAssetIssueActuator.java`)

### Summary
`ParticipateAssetIssueActuator` converts TRX to a TRC10 token using a fixed `num`/`trxNum` ratio that is set once, at asset-issue creation time, and used unchanged for every `ParticipateAssetIssueContract` transaction until the sale's `endTime`. This is the same bug class as the Alchemix `AlchemistV2.repay()` finding: the actuator assumes the fixed ratio between two assets holds true throughout the entire life of the operation, even though the relative market value of TRX and the token can drift substantially during the (governance-chosen, potentially multi-day/week) sale window. Anyone who can broadcast a `ParticipateAssetIssueContract` transaction can exploit any divergence between the fixed rate and the tokens' true relative value.

### Finding Description
When an issuer creates an asset with `AssetIssueContract`, the exchange rate is hard-coded as `trx_num` TRX buys `num` tokens [1](#0-0) . This ratio, along with `startTime`/`endTime`, is stored once and is not amongst the fields that `UpdateAssetContract` is permitted to modify — only `description`, `url`, `new_limit`, and `new_public_limit` can be changed after issuance [2](#0-1) .

Every `ParticipateAssetIssueActuator.execute()` call recomputes the exchange purely from this static ratio:
```java
long exchangeAmount = multiplyExact(cost, assetIssueCapsule.getNum());
exchangeAmount = floorDiv(exchangeAmount, assetIssueCapsule.getTrxNum());
``` [3](#0-2) 

The same fixed computation is repeated in validation [4](#0-3) , and `getNum()`/`getTrxNum()` simply return the immutable values captured at issuance [5](#0-4) . The only time-bound check is that `now` must fall between `startTime` and `endTime` [6](#0-5)  — there is no mechanism that re-anchors the price to any external or on-chain market reference during that window.

This mirrors the Alchemix root cause exactly: `_normalizeUnderlyingTokensToDebt()` uses a static `conversionFactor` regardless of the underlying token's real market price, letting arbitrageurs repay debt cheaply when the underlying depegs. Here, `num`/`trxNum` plays the role of `conversionFactor` — a static ratio that ignores real-time TRX/token valuation for the whole sale duration.

### Impact Explanation
If the true relative value of TRX versus the newly issued token moves away from the fixed `num`/`trxNum` ratio at any point during the sale window (e.g., TRX price swings, or the token's expected value becomes clearer as the sale progresses), any account can call `ParticipateAssetIssueContract` to buy the token far below its fair value (or the issuer/other participants can be made to sell it far below fair value), extracting value from the issuer's reserved token supply or from other participants. Because the ratio is fixed for the life of the sale and cannot be updated, this value leakage is systemic and repeatable for as long as the sale remains open, and it scales with the amount of TRX the arbitrageur is willing to commit (bounded only by the issuer's reserved token balance, checked via `assetBalanceEnoughV2`) [7](#0-6) .

### Likelihood Explanation
This requires only a single signed `ParticipateAssetIssueContract` transaction, needs no special privilege, and is fully reachable by any account with sufficient TRX balance during an active token sale window. The likelihood of an economically significant price divergence occurring at some point during a sale that can last from `startTime` to `endTime` is non-trivial, especially for longer sale windows or volatile TRX market conditions, making this an easily/predictably exploitable design gap rather than a purely theoretical one.

### Recommendation
Consider bounding the fixed-rate exposure window (shorter maximum sale durations), allowing the issuer to pause/adjust participation if TRX volatility exceeds a threshold, or otherwise decoupling total exposure from a single immutable ratio held open-ended over the entire sale period. At minimum, document this as an intentional crowdsale-style trust assumption (as Alchemix's team ultimately did for `repay()`) so issuers and participants explicitly account for the risk.

### Proof of Concept
1. Issuer creates an `AssetIssueContract` with `trxNum = 1`, `num = 100`, `startTime = T0`, `endTime = T0 + 30 days`.
2. At `T0`, market conditions justify 1 TRX ≈ 100 tokens.
3. Partway through the sale, TRX's market price rises sharply (or the token's real value becomes clearer and is worth much more than 100 tokens per TRX).
4. An arbitrageur repeatedly submits `ParticipateAssetIssueContract` transactions, each converting TRX to tokens at the stale `num`/`trxNum` ratio computed in `ParticipateAssetIssueActuator.execute()` [3](#0-2) , draining the issuer's reserved token supply at a price divorced from real value, until either the reserve is exhausted or `endTime` is reached.
