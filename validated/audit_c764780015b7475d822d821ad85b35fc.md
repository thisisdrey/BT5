## Title
Heap-based buffer over-read in `InputZipFile::ProcessCentralDirEntry` when parsing a crafted ZIP/JAR central directory — (`third_party/ijar/zip.cc`)

### Summary
`third_party/ijar/zip.cc` implements the ZIP/JAR reader used by `ijar` (interface-jar generation) and `singlejar`, both of which process JAR files that can originate from attacker-published, externally-fetched artifacts (e.g., `http_jar`/Maven-style JAR dependencies whose *bytes* are entirely attacker-chosen even when their declared `sha256` matches). Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before consuming header fields, `ProcessCentralDirEntry` reads the central-directory record's `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the untrusted file and advances the cursor `p` by these attacker-controlled values with **no bounds check** against the mapped file's actual length. This mirrors the CImg BMP bug class: a crafted length field drives a read cursor past the end of a memory-mapped buffer, causing a heap/mmap-based buffer over-read.

### Finding Description
`InputZipFile` memory-maps the entire ZIP/JAR file and walks it with pointer `p`. Every function that reads variable-length data validates the remaining buffer size first via `EnsureRemaining()`: [1](#0-0) 

`ProcessLocalFileEntry` uses this guard consistently before consuming `file_name_length_`/`extra_field_length_`: [2](#0-1) 

However, `ProcessCentralDirEntry` — which runs once per central-directory entry, driving the `p` cursor through attacker-controlled `file_name_length`, `extra_field_length`, and `file_comment_length` fields, as well as the nested zip64 extra-field loop — performs **no `EnsureRemaining` call at all**: [3](#0-2) 

The comment above the function even asserts an unproven trust assumption ("the central directory is always followed by another data structure that has a signature, so parsing it this way is safe") that does not hold for a crafted file. Because `file_name_length`, `extra_field_length`, and `file_comment_length` are attacker-chosen 16-bit values (up to 65535 each) and the nested extra-field loop `while (extra_p != p)` reads 4 bytes (`header_id`, `data_size`) per iteration without checking against the outer `extra_field_length` or the mapped file size, a crafted entry can push `p` past the end of the `mmap`'d region. The subsequent `memcpy` into `filename` and pointer arithmetic (`p += file_name_length`, `p += extra_field_length`, `p += file_comment_length`) then dereferences memory outside the legitimate, correctly-hash-verified input buffer — a heap-based/mmap-based buffer over-read directly analogous to CImg's `load_bmp` over-read from unvalidated header size fields.

### Impact Explanation
This is data corruption of Bazel's own parser state / potential crash (SIGSEGV on page boundary) or leakage of adjacent process memory into computed output (e.g., truncated/garbage filename copied via `memcpy`) when Bazel's `ijar`/`singlejar` tooling processes a JAR whose *bytes* were entirely chosen by an attacker (e.g., publisher of a dependency artifact fetched via `http_jar`). The checksum pinning (`sha256`/`integrity`) that Bazel enforces on the outer fetch only guarantees the bytes match what the attacker published — it does nothing to prevent the attacker from crafting an internally malformed ZIP central directory inside those verified bytes. The parser is expected to safely reject or bound-check malformed structure, and it fails to do so in `ProcessCentralDirEntry`.

### Likelihood Explanation
Any repository rule or build step that runs `ijar`/`singlejar` over an externally supplied JAR (a common path for Java external dependencies) will invoke this exact code path with fully attacker-controlled ZIP-format bytes. No privileged access or MITM is required — publishing a single crafted `.jar` is sufficient, and the correct checksum can still be published alongside it since the checksum only binds the outer bytes, not the internal structural invariants this code silently assumes.

### Recommendation
Add `EnsureRemaining()` (or an equivalent bound check against `input_file_->Length()`) at the start of `ProcessCentralDirEntry` before reading the fixed 46-byte central directory header, and again before/while consuming `file_name_length`, `extra_field_length`, `file_comment_length`, and within the zip64 extra-field loop, mirroring the pattern already used in `ProcessLocalFileEntry`.

### Proof of Concept
A JUnit/`BuildIntegrationTestCase`-style reproduction: construct a minimal ZIP file whose single central-directory entry declares `file_comment_length = 0xFFFF` (or `extra_field_length` large enough) while the actual file is only a few hundred bytes long, then invoke `ZipExtractor::Create(...)->ProcessAll()` (as exercised in `tools/test/windows/tw_test.cc`'s `TestCreateZip`) on this crafted file; observe the read cursor `p` advance past `zipdata_in_ + input_file_->Length()`, triggering an out-of-bounds read (crash or garbage data) instead of a clean `error(...)` return.   // abort with an error message.  "state" is the name of the field

  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;
  }

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
