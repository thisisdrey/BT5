### Title
Missing transaction deadline allows stale leverage/flashRepay swaps to execute at unfavorable prices - (File: contracts/SmartFarmingManager.sol)

### Summary
`SmartFarmingManager.leverage()` and `SmartFarmingManager.flashRepay()` route user-initiated swaps through `Swapper.swapExactInput()` without any deadline/expiration parameter. If a user's transaction sits in the mempool, it can be mined at a much later time under market conditions the user never agreed to, while still satisfying the absolute `amountOutMin` bounds they signed.

### Finding Description
Both public entry points perform AMM swaps where the slippage parameters are fixed minimum-output amounts evaluated at execution time, not at signing time:

- `leverage()` swaps `tokenIn_ → collateral` and `syntheticToken → collateral` via `_swap(...)` with `amountOutMin_ = 0`, relying only on `depositAmountMin_` checked after the swaps (`SmartFarmingManager.sol:184`, `:197-198`).
- `flashRepay()` swaps `collateral → synthetic` via `_swap(..., 0)` and checks only `swapAmountOutMin_` (`SmartFarmingManager.sol:125-126`).
- `_swap()` ultimately calls `swapper_.swapExactInput(tokenIn, tokenOut, amountIn, amountOutMin, to)` (`SmartFarmingManager.sol:305`), and the `ISwapper` interface exposes no deadline parameter (`contracts/interfaces/external/ISwapper.sol:6-12`).

The min-out parameters protect against intra-block sandwiching, but they are absolute numbers chosen against prices/health at signing time. A tx delayed in the mempool can execute hours later when collateral or synth prices have moved; the trade still satisfies the signed minimums yet produces a position the user would not have opened (e.g., a leveraged position priced near its liquidation threshold, or a flashRepay that leaves a worse residual debt). The health check (`PositionIsNotHealthy`) only verifies solvency, not that the trade was timely or priced fairly.

### Impact Explanation
A leveraged or deleveraged position may be opened/closed at a materially worse effective price than the user intended, because the protocol offers no way to bound the validity window of the signed slippage parameters. The loss accrues directly to the user's position value (worse collateral purchased, worse repay rate), bounded only by the absolute min-out values rather than by market conditions at execution.

### Likelihood Explanation
Requires a user transaction to be delayed in the mempool and market prices to drift in the meantime. This is an environmental/timing condition rather than active attacker exploitation, but it is a realistic occurrence during congestion or volatile periods, which is why deadline parameters are standard for swap flows. The bug is deterministic in the code — no deadline exists anywhere in the swap path — hence Medium rather than High.

### Recommendation
Add a `deadline_` parameter to `leverage()` and `flashRepay()` (and propagate it through `ISwapper.swapExactInput`), reverting if `block.timestamp > deadline_`, so users can bound the validity window of their signed slippage parameters.
