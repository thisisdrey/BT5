### Title
`VesperGateway.deposit` permanently reverts for fee-on-transfer underlyings because it forwards the nominal `amount_` instead of the actually received amount - (contracts/VesperGateway.sol)

### Summary
`VesperGateway.deposit` pulls `amount_` of the Vesper pool's underlying from the caller, then calls `vToken_.deposit(amount_)` after approving the full nominal `amount_`. Unlike `DepositToken.deposit` and `SmartFarmingManager._safeTransferFrom`, which measure the received amount via balance delta, the gateway never accounts for a transfer fee. If the underlying charges a fee (or enables one later, as USDT can), the gateway receives `amount_ - fee`, the subsequent `vToken_.deposit(amount_)` attempts to `transferFrom` more than the gateway holds, and the whole transaction reverts — permanently disabling that collateral's deposit route through the gateway.

### Finding Description
The flow at `contracts/VesperGateway.sol:44-65`:

1. `_underlying.safeTransferFrom(_msgSender, address(this), amount_)` — gateway nets `amount_ - fee` for a fee-on-transfer token (lines 50-51).
2. `_underlying.safeApprove(address(vToken_), amount_)` — approves the nominal amount (lines 54-55).
3. `vToken_.deposit(amount_)` — Vesper's `VPool.deposit` internally does `token.safeTransferFrom(msg.sender, address(this), _amount)` for the full `amount_`, which exceeds the gateway's actual balance of `amount_ - fee` and reverts (lines 56-58).

By contrast, the protocol's primary deposit path is explicitly fee-aware: `DepositToken.deposit` recomputes `amount_ = _underlying.balanceOf(_treasury) - _balanceBefore` after the pull [1](#0-0) , and `SmartFarmingManager._safeTransferFrom` returns the balance delta [2](#0-1) . Only the Vesper gateway omits the delta measurement on the inbound leg.

### Impact Explanation
For any registered Pool whose `vToken_`'s underlying is or becomes a fee-on-transfer token, `VesperGateway.deposit` reverts 100% of the time — a permanent denial of that deposit route (matching the original bug class: "part of the protocol becomes unavailable"). Users retain a workaround (deposit the vToken directly via `DepositToken.deposit`), so funds are not frozen and no theft occurs; impact is availability of a supported integration, consistent with the medium/low rating of the original Sandclock finding.

### Likelihood Explanation
Low-to-medium. It requires a whitelisted Vesper pool whose underlying token charges transfer fees. No current major collateral does, but USDT-style tokens can enable fees post-deployment, and the gateway is intended to be called by unprivileged users for any registered pool/vToken pair, so no privileged action or oracle manipulation is needed to trigger it — any user deposit attempt reverts.

### Recommendation
Measure the received amount before approving/depositing, mirroring `DepositToken.deposit`:

```solidity
uint256 _balanceBefore = _underlying.balanceOf(address(this));
_underlying.safeTransferFrom(_msgSender, address(this), amount_);
uint256 _received = _underlying.balanceOf(address(this)) - _balanceBefore;
_underlying.safeApprove(address(vToken_), 0);
_underlying.safeApprove(address(vToken_), _received);
vToken_.deposit(_received);
```

Alternatively, document that fee-on-transfer underlyings are unsupported for the Vesper route.

### Proof of Concept
Foundry fork sketch: mock/fork a fee-on-transfer ERC20 (or a token with an upgradeable fee like USDT with fee enabled) as the underlying of a registered `IVPool`.

```solidity
function testDepositRevertsForFeeOnTransferUnderlying() public {
    // fotToken takes 1% on every transfer; vPool.token() == fotToken
    uint256 amount = 100e6;
    fotToken.approve(address(vesperGateway), amount);

    // Gateway receives only 99e6, then vPool.deposit(100e6) tries to pull
    // 100e6 from the gateway -> ERC20: insufficient balance -> revert
    vm.expectRevert();
    vesperGateway.deposit(pool, IVPool(address(vPool)), amount);
}
```

The revert occurs inside `vToken_.deposit(amount_)` because the gateway's post-fee balance (`amount_ - fee`) is less than the `amount_` it is asked to forward.
