### Title
Unrestricted dust transfers fill a victim's `depositTokensOfAccount` set, blocking deposits/transfers of new collateral types (account-list exhaustion DoS) - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` enforces a per-account cap via `onlyIfAdditionWillNotReachMaxTokens` and reverts when a *new* `DepositToken` is added to an account whose list is already full. Because `DepositToken.transfer`/`transferFrom` and `deposit(amount_, onBehalfOf_)` add the recipient to the list whenever their balance of that token goes `0 -> nonzero`, any unprivileged attacker can dust-transfer one wei of each existing `DepositToken` to a victim until the cap is reached. Afterwards, every attempt to deposit a *new* collateral type on behalf of the victim, transfer a new `DepositToken` to them, or receive a new collateral type via `seize` in liquidation reverts. This mirrors the libsoup class: missing validation of attacker-controlled values (no minimum amount, no opt-in on the recipient side) causing denial of service.

### Finding Description
In `Pool.sol:216-220`, `addToDepositTokensOfAccount` is protected by `onlyIfAdditionWillNotReachMaxTokens(account_)`, so the call reverts once the account's set has reached `MAX_TOKENS_PER_USER` entries. `DepositToken._mint`/`_transfer` insert the token into `depositTokensOfAccount` when the holder's balance transitions from zero (mirrored by the removal path in `_burn` at `DepositToken.sol:459-462`, which calls `pool.removeFromDepositTokensOfAccount(_account)`). `deposit` takes an arbitrary `onBehalfOf_` (`DepositToken.sol:211-237`) and `transfer`/`transferFrom` are public, permissionless ERC20 entry points gated only by `_revertIfLocked` on the *sender* (`DepositToken.sol:348-375`). Nothing validates that the dust amount is meaningful, that the recipient consented, or that the recipient has room for a new token entry before the balance update. An attacker therefore buys `MAX_TOKENS_PER_USER` list slots on the victim for the cost of a few wei of each collateral (obtainable by dust deposits to themselves first).

### Impact Explanation
Once the victim's `depositTokensOfAccount` set is saturated, any code path that needs to add a new `DepositToken` to the victim reverts:

- `DepositToken.deposit(amount_, victim)` reverts inside `_mint` -> `addToDepositTokensOfAccount`, so deposits-on-behalf (gateways such as `NativeTokenGateway`/`VesperGateway`, `Operator.execute` batch flows, integrators) are bricked for every collateral the victim does not already hold.
- `transfer`/`transferFrom` to the victim of any new `DepositToken` reverts, breaking withdrawals routed through contracts and any pay-out in msdTOKEN.
- `DepositToken.seize(..., to_=victim)` during `Pool.liquidate` reverts if the seized collateral type is new to the victim, interfering with liquidation settlement for that recipient.

The victim can free slots only by fully zeroing out one dusted token (transferring it away), which the attacker can re-fill — a persistent griefing loop that temporarily freezes inbound collateral flows and forces victims to actively clean their account list.

### Likelihood Explanation
The attack requires no privileges: only public `deposit`/`transfer` calls with dust amounts. Cost is bounded by acquiring 1 wei of each listed `DepositToken` (deposits are open to anyone while the pool is not paused), plus gas for the dust transfers. The check `onlyIfAdditionWillNotReachMaxTokens` exists precisely because the list is bounded, but there is no validation preventing the set from being filled with economically meaningless dust balances on someone else's behalf.

### Recommendation
- Add a minimum balance/list-entry threshold (e.g., only add a token to `depositTokensOfAccount` when the credited USD value exceeds a floor), or
- Revert/remove from the set on transfers that would create dust entries (normalize dust to the sender), or
- Make `addToDepositTokensOfAccount` revert-safe on the deposit/transfer path (e.g., allow the transfer but skip accounting-only list insertion) so an attacker cannot weaponize the cap.

### Proof of Concept
Hardhat-style PoC sketch against deployed pool (`depositTokens` = list from `pool.getDepositTokens()`):

```ts
// attacker deposits 1 wei of each collateral and transfers it to victim
for (const dt of await pool.getDepositTokens()) {
  const depositToken = await ethers.getContractAt('DepositToken', dt)
  const underlying = await ethers.getContractAt('IERC20', await depositToken.underlying())
  await underlying.connect(attacker).approve(depositToken.address, 1)
  // if attacker has no balance, swap/acquire dust first; then:
  await depositToken.connect(attacker).deposit(1, attacker.address)
  await depositToken.connect(attacker).transfer(victim.address, 1)
}
// victim's list is now at MAX_TOKENS_PER_USER

// victim tries to deposit a collateral type they did not previously hold
await underlying.connect(victim).approve(depositToken.address, amount)
await expect(
  depositToken.connect(victim).deposit(amount, victim.address)
).to.be.reverted // MaxTokensPerUserReached via addToDepositTokensOfAccount
```

Note: I verified `addToDepositTokensOfAccount` is capped (`Pool.sol:216`) and that list insertion happens on balance `0 -> nonzero` with symmetric removal in `_burn` (`DepositToken.sol:459-462`), and that `deposit`/`transfer`/`transferFrom` impose no minimum amount or recipient consent. I was not able to confirm the exact `MAX_TOKENS_PER_USER` constant value or view the `onlyIfAdditionWillNotReachMaxTokens` modifier body within the available iterations; the exploit assumes the revert name/check implied by that modifier. If the modifier instead silently skips additions beyond the cap, the DoS does not materialize and this finding would not hold.
