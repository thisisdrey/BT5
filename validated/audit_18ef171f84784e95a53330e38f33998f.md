### Title
Division-before-multiplication in standby witness reward payout causes permanent loss of TRX reward - ([File: chainbase/src/main/java/org/tron/core/service/MortgageService.java])

### Summary
`MortgageService.payStandbyWitness()` distributes a fixed reward pool (`getWitness127PayPerBlock()`) proportionally to the top-127 standby witnesses by vote count. It computes the per-vote payout by **dividing first, then multiplying** — the exact anti-pattern described in the external report (division carried out before multiplication, causing systematic rounding loss) — instead of multiplying first and dividing last.

### Finding Description
`payStandbyWitness()` computes: [1](#0-0) 
```
double eachVotePay = (double) totalPay / voteSum;
for (WitnessCapsule w : witnessStandbys) {
  long pay = (long) (w.getVoteCount() * eachVotePay);
  payReward(w.getAddress().toByteArray(), pay);
}
```
`totalPay` (the fixed pool amount for this block) is divided by `voteSum` first, producing a `double` with limited precision, and only then multiplied by each witness's `voteCount` and truncated to `long`. This is mathematically equivalent to the vulnerable `getClaimableFlux` pattern in the external report: performing the division before the multiplication instead of `voteCount * totalPay / voteSum`, which loses precision on every witness's payout and truncates toward zero on every iteration.

The same order-of-operations defect also exists in the legacy `IncentiveManager.reward()` path used before `allowChangeDelegation` is enabled: [2](#0-1) 
```
long totalPay = consensusDelegate.getWitnessStandbyAllowance();
for (ByteString witness : witnesses) {
  long pay = (long) (consensusDelegate.getWitness(address).getVoteCount() * ((double) totalPay / voteSum));
  ...
}
```
Both are invoked from block/maintenance-cycle application: `IncentiveManager.reward()` is called from `MaintenanceManager.doMaintenance()` [3](#0-2)  which runs during `applyBlock` [4](#0-3) , i.e. it executes automatically for every maintenance-cycle block, driven purely by accumulated vote transactions from ordinary users (a reachable, unprivileged path per the allowed analog list: "block application in Manager" / "stake/delegation/reward math").

Neither function reconciles the sum of the truncated per-witness `pay` values against `totalPay`/`getWitnessStandbyAllowance()`. Any remainder lost to the division-before-multiplication rounding is not credited to any account, the reward pool, or burned in an accounted way — it simply disappears from the total that should have been paid out this cycle.

### Impact Explanation
This causes systematic under-payment (rounding down) of every standby witness's per-block reward, cycle after cycle. Because the fixed pool amount (`totalPay`) is never fully redistributed and the shortfall is not tracked or reclaimed, the difference between the intended payout and the actually credited amount is permanently and irrecoverably lost — matching the "Permanent freezing of unclaimed yield" impact class from the reference report. Over the lifetime of the chain (every maintenance cycle, for potentially over 100 standby witnesses each time) this compounds into a non-trivial, unrecoverable loss of TRX that should have accrued to witnesses' allowance balances.

### Likelihood Explanation
This defect triggers automatically and deterministically on every maintenance cycle as long as `voteSum >= 1` (i.e., any votes exist), requiring no attacker action beyond ordinary voting activity that any account can already perform. It is not a privileged or exceptional code path — it is core reward-accounting logic executed unconditionally during block/maintenance processing.

### Recommendation
Reorder the arithmetic to multiply before dividing and use integer/BigInteger math to avoid intermediate floating point truncation, mirroring the fix recommended for `getClaimableFlux`:
```java
long pay = Math.multiplyHigh... // or BigInteger-based:
long pay = BigInteger.valueOf(w.getVoteCount())
    .multiply(BigInteger.valueOf(totalPay))
    .divide(BigInteger.valueOf(voteSum))
    .longValueExact();
```
Additionally, track the distributed sum and either roll over or explicitly account for any leftover remainder (e.g., carry it to the next cycle's pool) rather than letting it silently vanish.

### Proof of Concept
Given `totalPay = 100`, `voteSum = 3` witnesses with vote counts `[1, 1, 1]`:
- Current code: `eachVotePay = 100.0/3 = 33.333...`; each witness receives `(long)(1 * 33.333...) = 33`; total paid = `99`, losing `1` unit of TRX every cycle this ratio recurs.
- Fixed code: `pay = (1 * 100) / 3 = 33` per witness computed via multiply-then-divide with proper remainder handling would allow explicit tracking of the `1` unit shortfall instead of it disappearing silently across compounding cycles with larger vote counts and larger reward pools, where the truncation losses are much larger in absolute TRX terms.
