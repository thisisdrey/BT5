This confirms the analog. `ExchangeWithdrawContract` has no `expected`/minimum-output field, unlike `ExchangeTransactionContract` which includes `int64 expected = 5` and is enforced in `ExchangeTransactionActuator.doValidate()` via `if (anotherTokenQuant < tokenExpected)`.

### Title
Missing slippage-protection parameter in `ExchangeWithdrawActuator` allows front-running of Bancor-style exchange withdrawals - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`, which drives `ExchangeWithdrawActuator`, only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no minimum-expected-output field for the paired token that is computed and paid out by the actuator.

### Finding Description
When an exchange creator withdraws liquidity, `ExchangeWithdrawActuator.execute()` computes `anotherTokenQuant` at execution time based on the exchange's *current* `firstTokenBalance`/`secondTokenBalance` ratio (Bancor-style constant-product-like formula), then immediately mutates the pool and pays out both `tokenQuant` and the derived `anotherTokenQuant`: [1](#0-0) 

Contrast this with `ExchangeTransactionActuator`, which accepts a caller-supplied `expected` value and enforces it before committing state changes: [2](#0-1) 

The withdraw contract carries no such field: [3](#0-2) 

Because the exchange pool ratio is fully attacker-manipulable within the same block via ordinary `ExchangeTransactionContract` trades (which have no fee and are broadcastable by any account), an attacker observing a pending `ExchangeWithdrawContract` transaction in the mempool can:
1. Front-run it with an `ExchangeTransactionContract` trade that skews `firstTokenBalance`/`secondTokenBalance` in a direction that minimizes `anotherTokenQuant` for the victim's withdraw.
2. Let the victim's withdraw execute at the manipulated ratio, receiving far less of `anotherTokenID` than the pre-attack ratio would have implied.
3. Back-run with a reverse trade to restore the ratio and capture the extracted value, extracting value from the exchange creator without the creator being able to bound their minimum-acceptable-output.

This is the direct analog of the Uniswap V3 `burn()` slippage-protection issue: both hand-computation of output values based on real-time pool state, and both pathways lack a caller-supplied minimum-output guard before committing to the trade/withdrawal.

### Impact Explanation
An unprivileged attacker (any account issuing ordinary `ExchangeTransactionContract` transactions) can sandwich `ExchangeWithdrawContract` transactions submitted by exchange creators, directly transferring value from the victim to the attacker via the manipulated exchange ratio. This is a concrete unauthorized-value-transfer / theft-of-funds scenario reachable purely from unprivileged, broadcastable transactions — no special privileges required.

### Likelihood Explanation
The `Exchange*` actuators are legacy Bancor-style TRC10 exchange functionality still present and reachable via ordinary signed transactions (`ExchangeTransactionContract` and `ExchangeWithdrawContract`), with no fee on trades (`calcFee()` returns 0), making sandwiching cheap and repeatable whenever an exchange creator withdraws.

### Recommendation
Add a minimum-expected-output field (e.g., `expected_another_token_quant`) to `ExchangeWithdrawContract`, and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` analogous to the `tokenExpected` check already implemented in `ExchangeTransactionActuator`, rejecting the withdrawal if the computed `anotherTokenQuant` falls below the caller-supplied minimum.

### Proof of Concept
1. Attacker observes a pending `ExchangeWithdrawContract` from victim (creator) for `exchangeId`, withdrawing `tokenQuant` of `firstTokenID`.
2. Attacker submits an `ExchangeTransactionContract` trade against the same `exchangeId` that shifts `firstTokenBalance`/`secondTokenBalance` so that the ratio used in `ExchangeWithdrawActuator.execute()`'s calculation of `anotherTokenQuant` (line 79-80 or 85-86) is minimized.
3. Victim's withdraw transaction executes at the skewed ratio, receiving less `secondTokenID`/`firstTokenID` than expected, with no on-chain mechanism to reject the unfavorable outcome.
4. Attacker submits a reverse `ExchangeTransactionContract` trade to restore the ratio and realize the extracted value.
