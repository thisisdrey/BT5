Audit Report

## Title
`ERC20Transactor::deposit_asset_with_surplus` silently drops all but one ERC20 asset when depositing multiple matched fungibles, permanently locking user funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::deposit_asset_with_surplus` receives the full `AssetsInHolding` set passed by the XCM executor's `AssetTransactors` tuple, but only extracts and transfers the first fungible asset returned by `what.fungible_assets_iter().next()`, then unconditionally returns `Ok(surplus)` as if the entire `what` had been settled. [1](#0-0)  Because `ERC20Matcher` matches any `AccountKey20{..}` location regardless of contract address, and `withdraw_asset_with_surplus` is invoked once per distinct asset (moving real ERC20 balances into `ERC20TransfersCheckingAccount` for each), a `DepositAsset` with a `Wild`/`AllCounted(n)` filter covering two or more distinct ERC20 assets results in the second-and-later assets being discarded from the in-memory holding without being deposited, returned, or trapped — while the corresponding on-chain balance remains stuck in the checking account. [2](#0-1) 

## Finding Description
The only safeguard against multiple assets reaching this function is `defensive_assert!(what.len() == 1, ...)`, which is a debug-only assertion that does not affect release-build behavior and does not stop execution or return an error. [3](#0-2)  The function's own doc comment explicitly documents that "the rest will be silently ignored," confirming this is a known-but-unfixed limitation rather than a guaranteed invariant enforced by the surrounding executor or trait contract. [4](#0-3) 

The generic `TransactAsset` trait's default `deposit_asset_with_surplus` simply forwards the entire `AssetsInHolding` to `deposit_asset`, and nothing in the trait signature restricts callers (i.e., the `AssetTransactors` tuple used by the XCM executor) to pass only a single asset. [5](#0-4)  `ERC20Transactor` is registered in the `AssetTransactors` tuple on Asset Hub Westend alongside other transactors that do not match `AccountKey20` locations, so any `DepositAsset` holding subset containing multiple distinct ERC20 assets is routed entirely to `ERC20Transactor` in one call. [6](#0-5) 

Exploit path: `withdraw_asset_with_surplus` operates per-`Asset` (singular) and performs a real `transfer` to `ERC20TransfersCheckingAccount` for each withdrawn ERC20 asset. [7](#0-6)  An unprivileged user can submit `pallet_xcm::execute` with a program that issues `WithdrawAsset` for two distinct ERC20 contracts (each producing a real, separate on-chain transfer into the checking account) followed by a single `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` — a wildcard-filter pattern already used natively in this codebase's Snowbridge outbound XCM programs. [8](#0-7)  When the `DepositAsset` instruction resolves its filtered holding (both ERC20 assets) and calls into `deposit_asset_with_surplus`, only the first fungible asset in iteration order is transferred to the beneficiary; the return value `Ok(surplus)` signals full success for the entire `what`, so the second asset is neither deposited to the beneficiary, returned to the depositor, nor trapped by the executor's asset-trap mechanism. Its real ERC20 balance remains stranded in `ERC20TransfersCheckingAccount` with no code path to recover it to any specific owner.

## Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for asset custody on Asset Hub: a real, on-chain ERC20 balance transfer into a pallet-controlled account is not matched by a corresponding XCM-level settlement, resulting in permanent, unbounded-per-occurrence loss of user funds with no recovery mechanism, since the balance sits in `ERC20TransfersCheckingAccount` untracked at the XCM accounting layer. This matches the required impact category of "permanent user-fund lock."

## Likelihood Explanation
The exploit requires no privileged origin, malicious relayer, prover, or validator — only a signed account calling the public `pallet_xcm::execute` extrinsic with a program that withdraws two or more ERC20-backed assets and deposits them together using a `Wild`/`AllCounted` filter, a pattern that is already used elsewhere in this exact runtime family (Snowbridge outbound programs), making it realistically and repeatably triggerable by any user holding two distinct ERC20-backed assets on Asset Hub.

## Recommendation
Modify `ERC20Transactor::deposit_asset_with_surplus` to either (a) iterate over all fungible assets in `what` matched by `ERC20Matcher`, transferring each and returning any non-matching remainder as unspent so the executor tuple/trap logic can continue processing correctly, or (b) enforce the single-asset invariant with a hard runtime check (not merely a debug-only `defensive_assert!`) that returns `Err((remaining_assets, XcmError::AssetNotHandled))` for any assets beyond the first, ensuring the executor's asset-trap mechanism captures and can later recover the undeposited assets instead of silently discarding them.

## Proof of Concept
1. Deploy two independent ERC20 contracts X and Y on `pallet-revive`; fund account `A` with balances of both.
2. `A` submits `pallet_xcm::execute` with an XCM program:
   - `WithdrawAsset((AccountKey20{X}, amount_x))`
   - `WithdrawAsset((AccountKey20{Y}, amount_y))`
   - `DepositAsset { assets: Wild(AllCounted(2)), beneficiary: B }`
3. Both `WithdrawAsset` steps execute real `transfer` calls moving `amount_x` and `amount_y` from `A` into `ERC20TransfersCheckingAccount` via `withdraw_asset_with_surplus`.
4. The `DepositAsset` step resolves a holding containing both ERC20 assets, and calling `deposit_asset_with_surplus` transfers only the first (per `fungible_assets_iter().next()`) to `B`, returning `Ok(surplus)`.
5. `B` receives only one token; the other's balance remains permanently stuck in `ERC20TransfersCheckingAccount`, verifiable via the ERC20 contract's `balanceOf` for the checking account after execution, with no XCM error or trap event recorded for the second asset.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}
