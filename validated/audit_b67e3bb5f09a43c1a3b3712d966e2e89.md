## Finding

### Title
`EntryBytesBudget` reservation is never refunded on failed PoH recording, permanently shrinking a leader's block capacity - ([File: runtime/src/bank/entry_bytes_budget.rs])

### Summary
The `SwapRouter` report describes a "reserve upfront, refund unused" pattern that fails to refund unspent value when the operation is only partially completed, letting the unspent resource leak away and be lost. Agave's `EntryBytesBudget` (used to cap the number of serialized bytes recorded into PoH per slot) implements exactly the "reserve" half of this pattern in `Consumer::execute_and_commit_transactions_locked` but has no corresponding refund/release path when the reservation is made but recording ultimately fails for a recoverable reason.

### Finding Description
`EntryBytesBudget::reserve()` [1](#0-0)  atomically adds `bytes` to a per-slot `consumed` counter and only fails if it would exceed `slot_limit`. Critically, the struct exposes no `release`/`refund`/`give_back` method at all — bytes committed via `reserve()` can never be returned to the budget for the remainder of the slot.

In `Consumer::execute_and_commit_transactions_locked`, the banking-stage worker computes `entry_bytes` from the transactions that were actually processed, reserves that many bytes from the bank's `entry_bytes_budget()`, and only *then* attempts to actually push the entry into the PoH record channel via `self.transaction_recorder.record_transactions(...)`: [2](#0-1) 

If the reservation itself fails (`ExceedsSlotLimit`), that's correctly surfaced as `MaxHeightReached` and no PoH work is attempted — consistent with intended behavior. However, if the reservation *succeeds* and `record_transactions()` then fails for any other reason (e.g. `RecordSenderError::Full` → `PohRecorderError::ChannelFull`, or `RecordSenderError::Disconnected` → `PohRecorderError::ChannelDisconnected`), the already-reserved `entry_bytes` are **not given back**: [3](#0-2) [4](#0-3) 

Note that on this failure path the code does call `Self::remove_added_transaction_costs(bank, &transaction_costs)` to undo the *cost-tracker* reservation, but there is no analogous call to release the `entry_bytes_budget` reservation — the cost-tracker "refund" exists, the entry-bytes "refund" does not.

Because `EntryBytesBudget` is only reset once per slot, in `Bank::apply_slot_time_runtime_changes()`: [5](#0-4) 

every reservation that is made but never actually turned into a recorded PoH entry permanently consumes slot capacity that was never used. `RecordSenderError::Full` is not a rare or attacker-privileged condition — it occurs whenever the bounded record channel between banking-stage workers and the PoH service is momentarily saturated, which is exactly the kind of condition that any high-throughput stream of unprivileged user transactions can trigger under load (many banking-stage worker threads racing to record against a single PoH service).

### Impact Explanation
Each time a worker's `record_transactions` call fails after a successful `entry_bytes_budget().reserve()`, that byte allotment is lost for the rest of the slot. Under sustained transaction load — which unprivileged users fully control by submitting enough transactions to create channel contention — repeated leaked reservations can drive the tracked `consumed` counter toward `slot_limit` well before the leader has actually recorded that many bytes of PoH entries. Once `consumed` reaches `slot_limit`, all further `reserve()` calls return `ExceedsSlotLimit`, which is mapped to `PohRecorderError::MaxHeightReached` for every subsequent batch in the slot — effectively terminating transaction inclusion prematurely and shrinking the leader's real block capacity, even though genuine PoH/entry capacity remains. This degrades throughput and transaction inclusion fairness for the whole cluster during the affected slot, entirely from an unprivileged-user-triggerable condition (transaction volume causing record-channel contention), with no attacker privilege required.

### Likelihood Explanation
`RecordSenderError::Full`/channel congestion is a routine operational condition under load, not an exotic or privileged trigger — any sufficiently high rate of legitimate transaction submissions from ordinary users can produce it. Because the leaking reservation requires no malicious crafting, only volume, the likelihood of the leak accumulating during high-throughput slots is non-trivial, though the direct consequence (moderately reduced block capacity for a slot) is more of a throughput/QoS degradation than a hard crash.

### Recommendation
Add a `release(&self, bytes: u64)` method to `EntryBytesBudget` that subtracts (saturating) from `consumed`, and call it from `Consumer::execute_and_commit_transactions_locked` whenever `reserved_bytes` succeeded but `record_transactions_summary`'s inner result is an `Err` (mirroring the existing `Self::remove_added_transaction_costs` refund done for the cost tracker on the same failure path).

### Proof of Concept
Conceptual reproduction (not executed, based on static code path analysis):
1. Configure/observe a leader under sustained transaction load such that the PoH `RecordSender` channel (bounded, capacity governed by `RecordReceiver`) becomes full during a slot.
2. Multiple banking-stage worker threads call `execute_and_commit_transactions_locked`; each successfully calls `bank.entry_bytes_budget().reserve(entry_bytes)`, then calls `record_transactions`, which returns `RecordSenderError::Full` → `PohRecorderError::ChannelFull`.
3. Because no code path releases the just-reserved `entry_bytes`, the bank's `entry_bytes_consumed` counter keeps climbing even though no entries were recorded for these failed attempts.
4. Repeat under sustained load until `consumed` approaches `slot_limit` (`runtime/src/bank/entry_bytes_budget.rs`); subsequent `reserve()` calls start failing with `ExceedsSlotLimit`, which banking stage maps to `MaxHeightReached`, stopping transaction recording for the remainder of the slot despite the PoH stream not actually being full.

I was unable to fully verify the runtime magnitude of this effect (e.g., exact bound on `RecordReceiver` capacity vs. typical `entry_bytes` sizes) from static analysis alone, since that depends on configured channel capacities and live contention data not present in the indexed code; a Devin session with the full checkout and load-testing harness would be needed to quantify how often/how much capacity is actually lost in production-representative conditions.

    pub fn reserve(&self, bytes: u64) -> std::result::Result<(), EntryBytesReserveError> {
        loop {
            let current = self.consumed.load(Ordering::Acquire);
            let next = current.saturating_add(bytes);
            if next > self.slot_limit {
                return Err(EntryBytesReserveError::ExceedsSlotLimit);
            }

            if self
                .consumed
                .compare_exchange(current, next, Ordering::AcqRel, Ordering::Acquire)
                .is_ok()
            {
                return Ok(());
            }
        }
    }
