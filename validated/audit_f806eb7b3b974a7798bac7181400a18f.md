Confirmed: `LocalAssetOwner`/`ForeignAssetOwner` only check that the caller owns some real `pallet_assets` asset at `asset_location` — they never inspect or cross-check that asset's actual on-chain `Metadata` (name/symbol/decimals). The caller-supplied `AssetMetadata` in `register_token` is forwarded verbatim, unvalidated against the source-of-truth token record, into the message that mints an ERC-20 representation on Ethereum.

### Title
Unvalidated caller-supplied token metadata lets any asset owner mint an impersonating wrapped ERC20 on Ethereum - (File: bridges/snowbridge/pallets/system-frontend/src/lib.rs)

### Summary
The Halborn report's root cause is a client trusting unvalidated, attacker-influenced data to decide which token metadata (name/symbol/decimals) is "legitimate" enough to add to a user's wallet, with no server-side check that the metadata corresponds to a real, vetted token. The Polkadot SDK analog is `snowbridge-pallet-system-frontend::register_token`, a public, permissionless extrinsic on Asset Hub that lets anyone who legitimately owns *any* `pallet_assets`/`pallet_assets` foreign asset submit **arbitrary** `AssetMetadata` (`name`, `symbol`, `decimals`) to be embedded in a `RegisterForeignToken` command relayed to Ethereum, where it is used to instantiate a new wrapped ERC-20 contract with that exact name/symbol on-chain.

### Finding Description
`register_token` in [1](#0-0)  takes an `asset_id` and a caller-supplied `metadata: AssetMetadata` parameter. Origin validation is delegated to `T::RegisterTokenOrigin` which, per the Asset Hub Westend runtime config, resolves to `EitherOf<EitherOf<LocalAssetOwner<...>, ForeignAssetOwner<...>>, EnsureRootWithSuccess<...>>` [2](#0-1) .

Both `LocalAssetOwner::try_origin` and `ForeignAssetOwner::try_origin` only verify that the caller is the registered `owner` of the asset behind `asset_location` via `AssetInspect::owner(...)` [3](#0-2) [4](#0-3) . Neither implementation reads or compares against the asset's actual on-chain `pallet_assets::Metadata` (the `name`/`symbol`/`decimals` fields set via `set_metadata`, see `substrate/frame/assets/src/types.rs` `AssetMetadata` struct [5](#0-4) ).

The caller-supplied `metadata` argument is passed straight through into the outbound command with no cross-check:
```
let call = Self::build_register_token_call(origin_location.clone(), asset_location, metadata, ether_gained)?;
``` [6](#0-5) 

This is relayed to `snowbridge-pallet-system-v2::register_token` on BridgeHub, which again forwards `metadata.name`/`metadata.symbol`/`metadata.decimals` unmodified into `Command::RegisterForeignToken` [7](#0-6) , which is ABI-encoded and sent to the Ethereum Gateway contract to actually create/name the wrapped token [8](#0-7) .

Because ownership is proven only over the arbitrary `asset_location` (which can be a brand-new, worthless, permissionlessly-created `pallet_assets` asset the caller just minted), an attacker can:
1. Create/own a throwaway asset on Asset Hub (permissionless via `pallet_assets::create`).
2. Call `register_token` supplying `metadata` claiming to be `name: "USD Coin", symbol: "USDC", decimals: 6` (or any other high-value token's identity) regardless of what the throwaway asset's real on-chain metadata says.
3. Cause a wrapped ERC-20 to be created on Ethereum under the Snowbridge Gateway with that spoofed name/symbol, since the Gateway trusts whatever `RegisterForeignTokenParams` it receives from the bridge.

This directly parallels the wallet bug: the "server response" (here, the trusted BridgeHub/Ethereum message pipeline) accepts attacker-controlled metadata as if it had been validated, because the actual validation step (checking metadata integrity/consistency with a real, canonical token) never happens — only unrelated asset *ownership* is checked.

### Impact Explanation
This allows an unprivileged, permissionless actor to mint a wrapped token on Ethereum whose name/symbol impersonate a legitimate/well-known asset, without any relayer, validator, governance, or admin compromise. End users or downstream integrators relying on the ERC-20 `name()`/`symbol()` (as displayed by wallets/explorers) to identify the "real" bridged token could be deceived into interacting with a worthless impersonating token, mirroring the exact "malicious/bogus token added under a spoofed identity" outcome described in the source report. It undermines the integrity of Snowbridge's token registry business logic across the AssetHub → BridgeHub → Ethereum pipeline.

### Likelihood Explanation
High feasibility for any user: creating a new `pallet_assets` asset on Asset Hub is permissionless and cheap (subject to normal asset deposit), and nothing in the `register_token` flow ties `metadata` to the asset's actual `pallet_assets::Metadata`. The existing test suite explicitly exercises only origin-ownership checks (`register_usdt_from_owner_on_asset_hub`, `register_usdt_not_from_owner_on_asset_hub_will_fail`) [9](#0-8) , never metadata authenticity, confirming this path is untested and unguarded.

### Recommendation
- In `register_token`, require that the supplied `metadata.name`/`metadata.symbol`/`metadata.decimals` exactly match (or be derived from) the asset's actual `pallet_assets::Metadata` fetched via `AssetInspect`/`fungibles::metadata::Inspect`, rather than accepting an independent, caller-controlled struct.
- Alternatively, remove the free-form `metadata` parameter entirely and have the pallet look up canonical metadata on-chain itself.
- Add a check that rejects registration if `name`/`symbol` collide with metadata of an asset already known to bridge to Ethereum, to prevent duplicate/impersonating wrapped tokens.

### Proof of Concept
1. On Asset Hub, permissionlessly create a new local asset `id=999` via `pallet_assets::create`, becoming its owner, with real on-chain metadata left blank or set to something innocuous.
2. Call `snowbridge_pallet_system_frontend::register_token(origin=signed(attacker), asset_id=Location::for(999), metadata=AssetMetadata{name:"USD Coin", symbol:"USDC", decimals:6}, fee_asset)`.
3. `LocalAssetOwner::try_origin` succeeds because attacker is indeed `owner` of asset `999` — no check on `metadata` vs real asset metadata [3](#0-2) .
4. The call proceeds through `build_register_token_call` → BridgeHub `EthereumSystem::register_token` → `Command::RegisterForeignToken{name:"USD Coin", symbol:"USDC", decimals:6, token_id: <derived from asset 999>}` [7](#0-6)  → ABI-encoded and delivered to the Ethereum Gateway, which instantiates an ERC-20 contract advertising itself as "USD Coin (USDC)" while being backed by the attacker's worthless asset `999`.

	fn try_origin(
		origin: RuntimeOrigin,
		asset_location: &L,
	) -> Result<Self::Success, RuntimeOrigin> {
		let origin_location = EnsureXcm::<Everything, L>::try_origin(origin.clone())?;
		if !IsForeign::contains(asset_location, &origin_location) {
			return Err(origin);
		}
		let asset_location: Location = asset_location.clone().into();
		let owner = AssetInspect::owner(asset_location.into()).ok_or_else(|| origin.clone())?;
		let location: Location = origin_location.clone().into();
		let from =
			LocationToAccountId::convert_location(&location).ok_or_else(|| origin.clone())?;
		if from != owner {
			return Err(origin);
		}
		Ok(location.into())
	}
