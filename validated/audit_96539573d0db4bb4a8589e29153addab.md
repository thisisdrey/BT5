### Title
`resolve_promise_yield_timeouts` re-authorizes stale yield receipts by trie-key presence only, not by account-lifetime identity - (File: `runtime/runtime/src/lib.rs`)

### Summary
The timeout-resume gate at `runtime/runtime/src/lib.rs:3051` decides whether to resolve a timed-out yielded promise solely by calling `state_update.contains_key(&promise_yield_key, ...)` where `promise_yield_key = TrieKey::PromiseYieldReceipt { receiver_id: queue_entry.account_id, data_id: queue_entry.data_id }`. This key is scoped only to the account *name* and `data_id`, not to any identifier tied to the specific account incarnation that created the yield.

### Finding Description
`resolve_promise_yield_timeouts` pops entries from the `PromiseYieldTimeout` queue and, once the timeout height is reached, checks:
```rust
let promise_yield_key = TrieKey::PromiseYieldReceipt {
    receiver_id: queue_entry.account_id.clone(),
    data_id: queue_entry.data_id,
};
if state_update.contains_key(&promise_yield_key, AccessOptions::DEFAULT)? {
    ...
}
``` [1](#0-0) 

This is a pure trie-key existence check. The `TrieKey::PromiseYieldReceipt` is keyed by `(receiver_id, data_id)` alone — nothing distinguishes "account A that existed when the yield was created" from "account A that was deleted and recreated afterward with a completely different owner/keys/contract."

Critically, `remove_account()` — the function invoked when an account is deleted — does **not** clean up any of the promise-yield-related trie entries. It only removes the `Account` record, `ContractCode`, access keys, gas key nonces, and contract data: [2](#0-1) 

It never calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or `remove_yield_id_mappings` (all of which exist as standalone helpers) for the deleted account: [3](#0-2) [4](#0-3) [5](#0-4) 

Consequently, if account `A` has an outstanding `PromiseYieldReceipt{A, data_id}` (created via a `yield_create` host call before the account was deleted) and `A` is subsequently deleted and recreated with new access keys/contract, `contains_key(PromiseYieldReceipt{A,data_id})` still returns `true` — immediately, even before the new owner of `A` has ever created a yield of their own. When the pending `PromiseYieldTimeout` entry's height is reached, the runtime treats the stale receipt as if it still belongs to the current incarnation of `A` and issues a `PromiseResume` receipt (`predecessor_id = receiver_id = A`) that re-activates the originally stored yield `Receipt`, executing its callback actions against whatever contract/state the *new* owner of `A` has deployed.

### Impact Explanation
This confirms the structural root cause described in the prompt: the timeout-resume gate is a per-name existence check, not a per-account-lifetime identity check. Standing alone, this results in stale cross-incarnation receipt delivery — the recreated account can be forced to execute a `PromiseResume`/callback it never issued, based on state left behind by a prior, unrelated owner of the same account name. This is the same class of defect flagged for the postponed-receipt cluster, since `remove_account` has an identical gap for `PostponedReceipt`. The concrete fund/authorization consequence (e.g., forced execution of a `FunctionCall` action against the new contract with `predecessor_id == receiver_id == A`, or unintended data injection) depends on chaining this with the broader postponed/promise-yield resolution path, which was not independently re-validated to completion in this pass.

### Likelihood Explanation
Preconditions match those from the paired postponed-receipt question: an account must have an outstanding yielded promise, then be deleted via `DeleteAccount`, then recreated at the same name before the timeout height is reached. This requires only an ordinary account owner (no elevated privileges) to (1) invoke a contract that calls `yield_create`, (2) delete the account, and (3) have any party recreate an account with that name — all standard, permissionless transaction flows.

### Recommendation
`remove_account()` in `core/store/src/utils/mod.rs` should also purge all promise-yield-related state for the account being deleted: iterate and remove `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries scoped to `account_id` (mirroring the existing access-key/contract-data cleanup loops), and/or have `resolve_promise_yield_timeouts` additionally validate a bound to the account's creation/lifetime nonce rather than trusting bare key presence.

### Proof of Concept
Unit test in `runtime/runtime/src/tests/` (or `core/store` test module):
1. Set up a `TrieUpdate` with account `A` created, then call `set_promise_yield_receipt` to store a `Receipt` under `TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}`.
2. Call `remove_account(&mut state_update, &A)`.
3. Assert `state_update.contains_key(&TrieKey::PromiseYieldReceipt{receiver_id: A, data_id}, AccessOptions::DEFAULT)` still returns `true` (demonstrating the entry survives deletion).
4. Re-insert an `Account` record for `A` (simulating `CreateAccount`) without ever calling `set_promise_yield_receipt` again.
5. Assert the same `contains_key` check used at `lib.rs:3051` still returns `true`, proving the gate cannot distinguish the new incarnation of `A` from the old one — before any new yield has been created by the new owner.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
