### Title
Unauthenticated `RecvError` teardown bypasses source-address anti-spoofing check for relay-established tunnels - (File: outside.go)

### Summary
`handleRecvError` in `outside.go` tears down a tunnel and deletes its pending handshake state in response to a bare, unencrypted `RecvError` packet, gated only by a spoofing check that compares the sender's UDP address against `hostinfo.GetRemote()`. For any `HostInfo` whose direct remote address was never set — which is always true for relay-only tunnels, since `SetRemote` is only called `if !via.IsRelayed` — `GetRemote()` returns an invalid `netip.AddrPort{}`, and the spoofing check `hr.IsValid() && hr != addr` is skipped entirely. This is directly analogous to the Rubicon `offer`/`insert` finding: a state-mutating entry point that is supposed to be gated (only the legitimate peer should be able to trigger teardown) has no real access control for a whole class of reachable inputs, letting an unprivileged, uncertificated attacker mutate protocol state.

### Finding Description
`RecvError` is one of the few message types dispatched in `readOutsidePackets` before any certificate check, decryption, or handshake completion is required [1](#0-0) . It flows directly into `handleRecvError`:

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	...
	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil { return }

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?", ...)
		return
	}

	f.closeTunnel(hostinfo)
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
``` [2](#0-1) 

The only authentication gate here is `hr != addr`, i.e., "does the sender's address match what we recorded as this tunnel's remote?" That check is a no-op whenever `hr` is invalid. `HostInfo.GetRemote()` returns `netip.AddrPort{}` (invalid) unless `SetRemote` was previously called [3](#0-2) . In `beginHandshake`, `SetRemote` is explicitly skipped for relayed handshakes:

```go
hostinfo.remotes = f.lightHouse.QueryCache(vpnAddrs)
if !via.IsRelayed {
    hostinfo.SetRemote(via.UdpAddr)
}
``` [4](#0-3) 

For a tunnel that is only ever reached via a relay (a common, supported configuration, exercised e.g. by `TestRelayReplayProtection` and the relay e2e tests), `hostinfo.remote` is never populated, so `GetRemote()` permanently returns an invalid `AddrPort`. Any attacker who can send a single unencrypted UDP packet of type `header.RecvError` carrying that tunnel's `RemoteIndex` (32-bit, looked up via `QueryReverseIndex`) will have it accepted with no certificate, no completed handshake, and no address match required at all — the intended "did this come from the real peer" gate is unconditionally bypassed for this class of tunnel.

### Impact Explanation
This is a remote state-poisoning / denial-of-service primitive reachable by an attacker holding no CA-signed certificate and no established Nebula session: sending a bare 16-byte `RecvError` header with a guessed/observed `RemoteIndex` tears down an active relay-mediated tunnel (`closeTunnel` + `DeleteHostInfo`), forcing renegotiation and disrupting connectivity between two legitimate, certificate-holding peers. This mirrors the Rubicon finding's core defect class: a function meant to be gated to a legitimate/authorized actor (the actual remote peer, analogous to "keepers") has no real access-control check for a reachable code path, letting any unauthorized caller mutate shared protocol state (the hostmap/tunnel lifecycle) directly.

### Likelihood Explanation
Exploitation requires only knowledge of a valid `RemoteIndex` for a relay-based tunnel (a 4-byte value transmitted in the clear in every packet header on the wire, and also visible to anyone who can observe traffic on the relay path or sniff a single packet) and the ability to send one unencrypted UDP datagram to the target's listen port. No cryptographic material, certificate, or completed handshake is needed. The `ShouldRecvError` rate-limiting gate (`acceptRecvErrorConfig`) may throttle repeated attempts from the same address but does not restrict which addresses can trigger a first teardown.

### Recommendation
Do not rely solely on `hostinfo.GetRemote()` validity to decide whether the anti-spoofing address check applies. For relay-established tunnels, compare the sender against the known relay path (`hostinfo.relayState`) or otherwise require that `RecvError` acceptance be tied to a value that only the genuine remote peer could know/produce (e.g., a recent, authenticated packet exchange or an outstanding message-counter nonce), rather than defaulting to "no restriction" when no direct remote address has ever been recorded.

### Proof of Concept
1. Establish a relay-mediated tunnel between two legitimate certificate-holding peers ("me" and "them") through a relay node, as in the existing e2e relay tests.
2. Observe (or otherwise learn) the `RemoteIndex` used in the header of any packet on that tunnel (transmitted unencrypted in `header.H`).
3. As an unauthenticated third party with no certificate, craft a 16-byte packet: `header.Encode(buf, header.Version, header.RecvError, 0, <observed RemoteIndex>, 0)` and send it directly to one peer's UDP listen address.
4. On receipt, `readOutsidePackets` routes it to `handleRecvError` without any decryption or cert check; `hostinfo.GetRemote()` is invalid because the tunnel is relay-only, so the `hr.IsValid() && hr != addr` guard is skipped, and `f.closeTunnel(hostinfo)` / `DeleteHostInfo` execute — tearing down the legitimate tunnel.
