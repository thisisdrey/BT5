Audit Report

## Title
Unrefundable Fund Burn on Unconditional Tip Swap-and-Burn Before Unverified Remote Reward Allocation - ([File: bridges/snowbridge/pallets/system-frontend/src/lib.rs])

## Summary
`Pallet::add_tip` in `bridges/snowbridge/pallets/system-frontend/src/lib.rs` unconditionally swaps and burns the user's tip asset via `swap_fee_asset_and_burn` before sending an unpaid, unverified XCM `Transact` to BridgeHub to actually credit the tip. If the corresponding nonce on BridgeHub has already been consumed, `EthereumSystemV2::add_tip` in `bridges/snowbridge/pallets/system-v2/src/lib.rs` records the amount into `LostTips` and returns `Ok(())` regardless, with no extrinsic anywhere in the repository to convert `LostTips` back into spendable balance for the user.

## Finding Description
`add_tip` at [1](#0-0)  calls `Self::swap_fee_asset_and_burn(who.clone().into(), asset)?`, which performs `T::Swap::swap_exact_tokens_for_tokens` and then `burn_for_teleport::<T::AssetTransactor>` — an irreversible balance change on AssetHub, as seen in [2](#0-1) . Only afterward is the `AddTip` call built and dispatched via a fire-and-forget `UnpaidExecution`/`Transact` XCM in `build_remote_xcm`/`send_transact_call`, shown at [3](#0-2) .

On BridgeHub, `EthereumSystemV2::add_tip` at [4](#0-3)  dispatches to `InboundQueue::add_tip`/`OutboundQueue::add_tip`. The inbound implementation at [5](#0-4)  returns `AddTipError::NonceConsumed` if `Nonce::<T>::get(nonce)` is already true — a state that is set unconditionally during ordinary message processing at [6](#0-5) . On any such error, `EthereumSystemV2::add_tip` simply adds the amount into `LostTips::<T>` and unconditionally returns `Ok(())`, per [7](#0-6) . The `LostTips` storage doc comment itself acknowledges the gap: "Capturing the lost tips here supports implementing a recovery method **in the future**" at [8](#0-7)  — confirming no such recovery mechanism currently exists in this repository. A grep across the whole indexed repository for `LostTips` shows it is only referenced in `system-v2/src/lib.rs`, its unit tests, and an integration test that asserts the loss but never reclaims it — there is no claim/refund extrinsic anywhere.

The bug is exploitable by any ordinary user tipping a message whose nonce is concurrently or previously consumed by legitimate relayer activity — no malicious actor, governance action, or leaked key is required, satisfying the "unprivileged external attacker using public extrinsics" bar.

## Impact Explanation
This is a permanent user-fund loss: the burned DOT/asset (converted to ether and destroyed via `burn_for_teleport`) is gone forever, the intended relayer reward is never credited, and the `LostTips` bookkeeping entry has no path back to a spendable balance. This matches the "permanent user-fund or bridge-state lock" category under the Polkadot SDK impact gate, with the exact corrupted/lost value being the burned ether amount (`ether_gained`) recorded only as a dangling `LostTips::<T>` map entry for the sender's `AccountId`.

## Likelihood Explanation
The failure path is explicitly exercised by existing tests — `add_tip_inbound_fails_when_nonce_is_consumed` in `bridges/snowbridge/pallets/system-v2/src/tests.rs` [9](#0-8)  and the emulated integration test `tip_to_invalid_nonce_is_added_to_lost_tips` [10](#0-9)  — both confirming the developers are aware `add_tip` can fail after the local burn and that funds are simply routed into `LostTips` with no recovery. Any ordinary relayer racing to process a message before a user's tip transaction lands on BridgeHub triggers this loss condition; it requires no privileged access, only ordinary network latency/race conditions between AssetHub and BridgeHub.

## Recommendation
Do not perform the swap/burn on AssetHub until BridgeHub has confirmed the nonce is unconsumed and the tip can be recorded — e.g., use a receipt-and-settle two-phase pattern, escrow the asset pending an acknowledgment XCM, and only finalize the burn on confirmed success. Alternatively/additionally, implement an actual extrinsic that lets an account claim/redeem their `LostTips::<T>` balance for real spendable funds, closing the loop that currently exists only as an unreachable bookkeeping stub.

## Proof of Concept
1. User A calls `SnowbridgeSystemFrontend::add_tip(origin, MessageId::Inbound(N), tip_asset)` on AssetHub for nonce `N`.
2. `swap_fee_asset_and_burn` executes: the tip asset is swapped to ether and burned via `burn_for_teleport` — real, irreversible balance change (`bridges/snowbridge/pallets/system-frontend/src/lib.rs` lines 372-404).
3. Concurrently/previously, a relayer finalizes message `N` via `InboundQueueV2::process_message`, setting `Nonce::<T>::set(nonce)` (`bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs` lines 219-225) before User A's tip XCM arrives at BridgeHub.
4. The `AddTip` XCM `Transact` executes `EthereumSystemV2::add_tip`, which calls `InboundQueue::add_tip(N, amount)`, hits `ensure!(!Nonce::<T>::get(nonce), AddTipError::NonceConsumed)` and returns `Err(NonceConsumed)`.
5. `EthereumSystemV2::add_tip` catches this error, adds `amount` to `LostTips::<T>::get(sender)`, emits `TipProcessed { success: false }`, and still returns `Ok(())` (`bridges/snowbridge/pallets/system-v2/src/lib.rs` lines 266-280) — reproduced directly by the existing test `tip_to_invalid_nonce_is_added_to_lost_tips`.
6. User A's asset is permanently gone; no relayer received the tip; `LostTips` records the loss with no extrinsic in the repository to convert it back into spendable balance.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}

		fn send_transact_call(
			origin_location: Location,
			call: BridgeHubRuntime<T>,
		) -> DispatchResult {
			let dest = T::BridgeHubLocation::get();
			let remote_xcm = Self::build_remote_xcm(&call);
			let message_id = Self::send_xcm(origin_location, dest.clone(), remote_xcm.clone())
				.map_err(|error| Error::<T>::from(error))?;

			Self::deposit_event(Event::<T>::MessageSent {
				origin: T::PalletLocation::get().into(),
				destination: dest,
				message: remote_xcm,
				message_id,
			});

			Ok(())
		}

		pub fn add_tip(
			origin: OriginFor<T>,
			sender: AccountIdOf<T>,
			message_id: MessageId,
			amount: u128,
		) -> DispatchResult {
			T::FrontendOrigin::ensure_origin(origin)?;

			let result = match message_id {
				Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
				Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
			};

			if let Err(ref e) = result {
				tracing::debug!(target: LOG_TARGET, ?e, ?message_id, ?amount, "error adding tip");
				LostTips::<T>::mutate(&sender, |lost_tip| {
					*lost_tip = lost_tip.saturating_add(amount);
				});
			}

			Self::deposit_event(Event::<T>::TipProcessed {
				sender,
				message_id,
				amount,
				success: result.is_ok(),
			});

			Ok(())
		}
