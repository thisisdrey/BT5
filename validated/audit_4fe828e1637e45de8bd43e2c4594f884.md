## Analog Finding

### Title
Unauthenticated forged event injection into the signer's `SignerEventReceiver` HTTP listener — ([File: libsigner/src/events.rs])

### Summary
The `SignerEventReceiver::next_event` handler in `libsigner/src/events.rs` accepts any HTTP `POST` to `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` and deserializes the JSON body directly into a trusted event type (`StackerDBChunksEvent`, `BlockValidateResponse`, `BurnBlockEvent`, `StacksBlockEvent`) without checking any authentication header, even though the operator-facing documentation describes an `auth_token`/`auth_password` pair that is supposed to gate this channel.

### Finding Description
`decode_http_request` in `libsigner/src/http.rs` parses the verb, path, and headers of an incoming request into a `HashMap<String, String>` [1](#0-0) , but nothing in `libsigner` ever reads back an `authorization`/token header from that map to compare it against a configured secret — a `grep` for `auth_token|Authorization|auth_password` across the entire `libsigner/**` tree returns zero matches.

`SignerEventReceiver::next_event` accepts the raw request from the `tiny_http` server and, aside from checking the HTTP method and URL path, immediately dispatches the body to `process_event::<T, E>` for the four event types: [2](#0-1) 

`process_event` reads the body, unconditionally ACKs the sender, and deserializes the JSON straight into the trusted node-event type before converting it into a `SignerEvent` that is forwarded to the signer runloop: [3](#0-2) 

The operator documentation explicitly describes this channel as requiring a shared secret between the node and the signer (`auth_token` on the node side, `auth_password` on the signer side, "must match — exact string match"), which only makes sense if the signer's receiver is meant to validate the token on incoming requests: [4](#0-3) 

No such validation exists in the code paths I could inspect (`libsigner/src/events.rs`, `libsigner/src/http.rs`). This breaks the intended equality "request came from the authenticated Stacks node" vs. "any request that reaches the listening socket", analogous to the original report's unauthenticated-write class of bug: an unauthenticated party can inject data that a downstream, trusted consumer (the signer runloop) will process as if it originated from the legitimate node.

### Impact Explanation
If the signer's event-observer endpoint is reachable by an unauthenticated network party (e.g., bound to a non-loopback interface, or reachable via port-forwarding/misconfiguration — a realistic operational scenario given the endpoint is user-configured, per `sample/conf/signer/*.toml`), an attacker can:
- POST a forged `StackerDBChunksEvent` to `/stackerdb_chunks`, causing the signer to treat attacker-supplied StackerDB chunk contents as freshly observed node state and act on it in its runloop.
- POST a forged `BlockValidateResponse` to `/proposal_response`, spoofing the outcome of block-proposal validation that the node is supposed to have performed.
- POST forged `BurnBlockEvent`/`StacksBlockEvent` data to influence the signer's view of chain state.

This is an unauthenticated write into the signer's internal state/decision inputs — matching the "unauthenticated/unauthorized write to state" Critical-impact category in the rules, since the signer's runloop consumes these events as ground truth from the node.

### Likelihood Explanation
Likelihood depends entirely on network exposure of the signer's event-observer endpoint. If bound only to `127.0.0.1`, this is not remotely exploitable. However, nothing in the code enforces loopback-only binding or an authentication check as a defense-in-depth measure — `bind()` simply opens an `HttpServer` on whatever `SocketAddr` was configured [5](#0-4) . Given the documented (but apparently unenforced) `auth_token`/`auth_password` pairing, operators are led to believe this channel is authenticated, which increases the risk of accidental exposure without additional network-layer protections.

### Recommendation
Have `SignerEventReceiver::next_event` (or `process_event`) validate an `Authorization`/token header extracted via `decode_http_request` against the signer's configured `auth_password` before deserializing and forwarding any event, rejecting non-matching or missing-token requests with an HTTP 401. This closes the gap between the documented security model and the actual code behavior.

### Proof of Concept
Given a `SignerEventReceiver` bound to `0.0.0.0:30000` (or any reachable interface), send an arbitrary POST as shown in the repo's own test harness (which itself never sets any auth header):
```
POST /stackerdb_chunks HTTP/1.1
Host: <signer-endpoint>
Connection: close
Content-Type: application/json
Content-Length: <n>

{"contract_id": "...", "modified_slots": [ ... attacker-controlled chunk ... ]}
```
As shown in the repo's test `test_simple_signer`, this exact unauthenticated request pattern (with no auth header at all) is accepted and forwarded into the signer runloop: [6](#0-5) 

**Uncertainty note:** I was not able to fully verify, within the available search iterations, whether the actual `auth_password`/`auth_token` check might be implemented elsewhere (e.g., in the `stacks-signer` crate's runloop before acting on forwarded events, rather than in `libsigner`'s HTTP layer itself). If such enforcement exists downstream of `forward_event`, the finding's severity would be reduced to defense-in-depth rather than a full bypass. Given index size limits, I could not exhaustively confirm the absence of such a check outside `libsigner/**`; a Devin session with full repository access could confirm this definitively by tracing `SignerEvent` consumption in `stacks-signer/src/runloop.rs` and related files.

```rust
        self.with_server(|event_receiver, http_server, _is_mainnet| {
            // were we asked to terminate?
            if event_receiver.is_stopped() {
                return Err(EventError::Terminated);
            }

            let request = http_server.recv()?;
            debug!("Got request"; "method" => %request.method(), "path" => request.url());

            if request.url() == "/status" {
                request
                .respond(HttpResponse::from_string("OK"))
                .expect("response failed");
                return Ok(SignerEvent::StatusCheck);
            }

                return Err(EventError::MalformedRequest(format!(
                    "Unrecognized method '{}'",
                    request.method(),
                )));

                process_event::<T, StackerDBChunksEvent>(request)
```

```rust
fn process_event<T, E>(mut request: HttpRequest) -> Result<SignerEvent<T>, EventError>
where
    T: SignerEventTrait,
    E: serde::de::DeserializeOwned + TryInto<SignerEvent<T>, Error = EventError>,
{
    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));
    }
    // Regardless of whether we successfully deserialize, we should ack the dispatcher so they don't keep resending it
    ack_dispatcher(request);
    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
```
