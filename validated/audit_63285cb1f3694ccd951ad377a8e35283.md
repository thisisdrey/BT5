### Title
Missing slippage protection in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` enables sandwich attacks on exchange liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Unlike `ExchangeTransactionContract`, which carries an `expected` field that is validated against the computed `anotherTokenQuant` before execution, the `ExchangeInjectContract` and `ExchangeWithdrawContract` protobuf messages and their actuators contain **no minimum/expected-amount parameter at all**. The pairwise-asset amount (`anotherTokenQuant`) that is deducted/credited for the counter-asset is computed purely from the exchange pool's on-chain ratio at execution time, with zero user-supplied bound, so the exchange creator has no way to protect themselves against price movement between transaction signing and inclusion in a block.

### Finding Description
`ExchangeTransactionActuator` implements slippage protection correctly: the signer supplies `expected` in `ExchangeTransactionContract`, and `doValidate()` rejects the transaction if the freshly computed `anotherTokenQuant` is less than that value. [1](#0-0) 

By contrast, `ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no `expected`/minimum field. [2](#0-1) 

`ExchangeInjectActuator.doValidate()` computes `anotherTokenQuant` strictly from the current pool ratio (`bigSecondTokenBalance.multiply(bigTokenQuant).divide(bigFirstTokenBalance)`), with no comparison to any caller-supplied bound, before deducting that amount from the creator's balance in `execute()`. [3](#0-2) [4](#0-3) 

`ExchangeWithdrawContract` (`owner_address`, `exchange_id`, `token_id`, `quant`) has the identical structural gap, and `ExchangeWithdrawActuator` computes `anotherTokenQuant` from the live pool ratio with only a fixed 0.0001 "precision" tolerance check — not a user-chosen slippage bound. [5](#0-4) [6](#0-5) 

Both operations are restricted to the exchange creator (`accountCapsule.getAddress().equals(exchangeCapsule.getCreatorAddress())`), but the creator is an ordinary, unprivileged account (an "asset issuer"), not a witness/SR, and it broadcasts a normal signed transaction that any other unprivileged party can see in the mempool and front-run. [7](#0-6) [8](#0-7) 

Because the exchange's `firstTokenBalance`/`secondTokenBalance` ratio can be moved by an intervening `ExchangeTransactionContract` from any other account before the creator's inject/withdraw transaction is packed into a block, an attacker can sandwich the creator's transaction: trade against the pool to skew the ratio, let the victim's inject/withdraw execute at the skewed ratio (paying/receiving an unfavorable counter-asset amount with zero protection), then reverse the trade to capture the difference. This mirrors the reported bug class exactly: a value that should function as slippage protection (the computed counter-amount) is not bounded by anything the caller controls, so the "protection" is ineffective/absent.

### Impact Explanation
An attacker can extract value from the exchange creator's own funds during a liquidity inject or withdraw by sandwiching the transaction with `ExchangeTransactionContract` trades, causing the creator to deposit more of the counter-asset than intended or withdraw less than fair value — an unauthorized transfer of value/permanent loss of funds for the victim account, reachable purely by broadcasting ordinary signed transactions (no privileged role required).

### Likelihood Explanation
Any account can observe pending transactions and race an `ExchangeTransactionContract` before/after a targeted `ExchangeInjectContract`/`ExchangeWithdrawContract` transaction; this requires no special privilege, only transaction ordering within the mempool, making the attack straightforward to execute whenever exchanges with non-trivial liquidity are targeted.

### Recommendation
Add an `expected`/minimum (and/or maximum) bound field to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate the computed `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()`, analogous to the existing check in `ExchangeTransactionActuator`, so the signer can bound acceptable slippage at signing time rather than relying on a pool ratio recomputed at execution time.

### Proof of Concept
1. Attacker monitors the mempool for a creator's `ExchangeInjectContract` (or `ExchangeWithdrawContract`) transaction targeting exchange `E` with tokens `A`/`B`.
2. Attacker submits an `ExchangeTransactionContract` that sells a large amount of `A` into `E`, shifting the `A`:`B` ratio unfavorably right before the victim's transaction.
3. The victim's inject transaction executes via `ExchangeInjectActuator.execute()`, computing `anotherTokenQuant` from the now-skewed ratio with no bound check, causing the creator to deposit far more of token `B` than intended for the same `A` quantity. [9](#0-8) 
4. Attacker submits a follow-up `ExchangeTransactionContract` reversing step 2's trade, extracting the value overpaid by the victim in step 3, since `ExchangeTransactionActuator`'s `expected` protection only guards the attacker's own trades, not the victim's unprotected inject.
