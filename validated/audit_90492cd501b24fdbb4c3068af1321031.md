## Title
Delegation Rewards Permanently Lost When a Witness's Vote Count is Zero During a Reward Cycle - (File: `chainbase/src/main/java/org/tron/core/store/DelegationStore.java`)

### Summary
The reported Yield-Basis bug describes rewards being silently discarded when a division denominator (`totalSupply`) is zero, so the reward delta is never credited to anyone and becomes stuck. Java-tron's DPoS reward-distribution machinery has the same structural flaw: block/transaction-fee rewards accumulated for a Super Representative (SR) are only distributed to voters by increasing a per-vote reward index (`Vi`) proportional to `reward / voteCount`. If a witness's total vote count for the cycle is `0` (fully un-voted) while it still earned rewards for producing blocks, the reward index update is skipped entirely, and the already-recorded reward silently disappears — never credited to any voter, and unrecoverable by any user action.

### Finding Description
`DelegationStore.accumulateWitnessVi()` computes the incremental reward-per-vote index for a witness in a cycle: [1](#0-0) 

If `reward == 0 || voteCount == 0`, the method just forwards the previous `Vi` value **without folding in the reward that was already recorded** via `addReward()`. The reward amount stored at `buildRewardKey(cycle, address)` is not zeroed out or refunded anywhere — it is simply never converted into an accessible `Vi` increment, so no voter can ever claim it.

This is invoked once per cycle for every witness in `MaintenanceManager.doMaintenance()`: [2](#0-1) 

using `witness.getVoteCount()`, i.e. the vote total that was fixed for the entire cycle by the previous maintenance call to `setWitnessVote`. Rewards are pushed into this per-witness/per-cycle bucket independently of the witness's current vote count, in `MortgageService.payReward()` (called from `payBlockReward`/`payTransactionFeeReward`, driven from block production in `Manager.payReward`): [3](#0-2) [4](#0-3) 

The legacy (pre-Vi) reward path has the exact same issue: `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` explicitly `continue`s (drops) any reward when `totalVote == 0`, even though `totalReward` for that cycle is positive: [5](#0-4) 

Since a witness can freely lose all its votes within the same reward cycle (any voter can call `VoteWitnessContract`/TVM `voteWitness` with 0 for that address, or unfreeze/undelegate all frozen balance backing the votes) while that witness continues to be scheduled and produce blocks for the remainder of the cycle (schedule is fixed at cycle boundary via `updateWitness`), an attacker or even ordinary user activity can trivially drive a witness's vote count to `0` for a cycle in which it still earns block/transaction-fee rewards. The reward recorded for that cycle then becomes permanently uncreditable — no voter, including the witness's own brokerage cut recipient logic, receives it, and there is no admin/reclaim path.

### Impact Explanation
Reward funds intended for distribution to TRX stakers/voters are permanently lost whenever a witness's total vote weight for a reward cycle is zero while rewards are still recorded for it. This is a direct, unattended loss of value that should have flowed to delegators — analogous to the reported `LiquidityGauge` issue where `totalSupply == 0` causes rewards to be dropped. The condition is reachable purely through normal, unprivileged voting/unfreezing transactions and requires no special privilege, matching the "stake/delegation/reward math" category explicitly in scope.

### Likelihood Explanation
Any voter can unvote (vote with `0` for a given SR, or fully unfreeze/undelegate the balance backing existing votes) to zero out a witness's cycle vote total. Combined with normal block production continuing for the remainder of the cycle by an already-scheduled witness, this is readily triggerable without any special conditions, elevated permissions, or economic cost beyond ordinary transaction fees.

### Recommendation
In `DelegationStore.accumulateWitnessVi()` and `MortgageService.computeReward(cycle, votes)`, when `voteCount`/`totalVote` is `0` but `reward > 0`, do not silently discard the reward. Instead, either (a) roll the un-distributable reward forward into the next cycle's reward bucket for the same witness so it is eventually distributed once votes exist again, or (b) redirect it to a globally claimable pool (e.g., the transaction fee pool or a dedicated "orphaned rewards" account) rather than letting it vanish.

### Proof of Concept
1. Witness `W` has vote count `N > 0` at the start of cycle `C` (persisted via `setWitnessVote(C, W, N)`), and is part of the active/standby witness schedule.
2. During cycle `C`, `W` produces one or more blocks; `Manager.payReward()` calls `mortgageService.payBlockReward`/`payTransactionFeeReward`, which call `MortgageService.payReward()` → `delegationStore.addReward(C, W, value)`, recording a positive reward for `(C, W)`.
3. Also during cycle `C`, all accounts that had voted for `W` submit `VoteWitnessContract` transactions removing their votes from `W` (or unfreeze/undelegate the underlying frozen balance), driving `W`'s effective vote count toward `0`. This is an ordinary, unprivileged operation.
4. At the maintenance boundary ending cycle `C`, `MaintenanceManager.doMaintenance()` invokes `delegationStore.accumulateWitnessVi(C, W, witness.getVoteCount())` using the vote count fixed for cycle `C`; since votes are `0` (or, in the legacy path, `totalVote == 0`), the branch in `accumulateWitnessVi` (or `computeReward`) skips folding the reward into `Vi`, and the previously recorded reward for `(C, W)` is never reflected in any voter's claimable balance.
5. No subsequent call (`withdrawReward`, `queryReward`, TVM `withdrawReward`) can recover this amount for any account, and there is no admin function to reclaim it — the reward is permanently lost. [1](#0-0) [2](#0-1) [3](#0-2) [5](#0-4)

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
