### Title
Buffer over-read in ZIP central directory Zip64 extra-field parsing - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the central directory of a ZIP/JAR archive that ijar consumes to build interface jars, including archives fetched as build inputs/dependencies. When it walks the "extra field" records to find a Zip64 field, it trusts the attacker-controlled `data_size` and `extra_field_length` values without validating that enough bytes remain, then unconditionally calls `get_u8le()` up to three times.

### Finding Description
`ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the central directory header bytes, then iterates over the extra-field bytes with: [1](#0-0) 
For each record it reads `header_id` and `data_size` via `get_u2le`, advances `extra_p` by `data_size`, and—if `header_id == ZIP64_EXTRA_FIELD_TAG`—calls `get_u8le(extra)` up to three times (24 bytes) from the `extra` pointer, which is only validated to be `data_size` bytes past `extra_p`. There is no check that `data_size >= 24`, nor any check that `extra_field_length` (and thus the whole extra-field region) stays within the bytes actually present in the mapped file.

Contrast this with `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before reading variable-length fields such as `file_name_length_` and `extra_field_length_`: [2](#0-1) 
`ProcessCentralDirEntry` has no equivalent `EnsureRemaining` calls anywhere in its body, unlike the sibling function that processes the same file. The comment above the function claims safety is guaranteed because "the central directory is always followed by another data structure that has a signature," but that only ensures a signature check will eventually catch corruption — it does not bound the number of bytes `get_u8le`/`get_u2le` advance past `extra_p`/`p` during the walk itself, so a crafted `data_size` smaller than 8 (for one field) still causes `get_u8le` to read 8 bytes starting inside the next record or past the declared extra-field boundary, and if the record sits near the end of the memory-mapped input file, past the mapped region entirely. [3](#0-2) 

### Impact Explanation
This is the direct structural analog of CVE-2019-7572: a fixed-size read (`IMA_ADPCM_nibble` reading fixed nibble counts) driven by attacker-controlled length fields without a bounds check, causing a heap/mmap buffer over-read. Here the archive being parsed is exactly the kind of "content a victim's build consumes" — a JAR built from source that ijar processes to create an interface jar — placed on disk by any process that produced or downloaded it (e.g., an untrusted dependency archive). A malformed but otherwise checksum-valid archive (checksum verification happens at fetch time on the whole archive blob, not on internal structural invariants of the ZIP format) can still trigger a read past the file's mapped extent, which is a memory-safety violation (crash/info leak) inside the Bazel-shipped `ijar` binary.

### Likelihood Explanation
I was not able to fully confirm within the available tool budget how the memory-mapped input buffer's length relates to `central_dir_current_`'s upper bound (i.e., whether `MappedInputFile`/`mapped_file_unix.cc`/`mapped_file_windows.cc` pads the mapping so a trailing over-read always lands on a valid page, which would downgrade this from an out-of-bounds read to a same-page logic bug). This affects whether the concrete impact is a hard crash/OOB read or merely reading unrelated in-bounds bytes. This is a real gap in verification, not a dismissal of the finding — the parsing logic itself is unambiguously missing bounds checks that exist in the sibling function.

### Recommendation
Add `EnsureRemaining`-equivalent checks in `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, `file_comment_length`, and before each `get_u2le`/`get_u8le` call within the extra-field loop, validating that `data_size >= 8` (or the specific size needed) before consuming a Zip64 attribute, and that the cumulative extra-field walk never advances past the declared `extra_field_length`/mapped file end.

### Proof of Concept
A `BuildIntegrationTestCase`/shell test (`third_party/ijar/test/ijar_test.sh` pattern) constructing a minimal ZIP whose central directory header declares `extra_field_length` large enough to contain a Zip64 tag (`0x0001`) but with `data_size` set to less than 8, positioned at the very end of the mapped file, would exercise `get_u8le(extra)` reading past the declared/mapped bounds when ijar processes it — this can be verified/reproduced by a background Devin session with filesystem/build access, which I do not have in this ask-only session.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}
