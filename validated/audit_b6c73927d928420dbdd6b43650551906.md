### Title
Protocol-treasury reward silently overwritten when treasury account is also a validator, permanently losing minted tokens - (File: chain/epoch-manager/src/reward_calculator.rs)

### Summary
`RewardCalculator::calculate_reward` builds a single `HashMap<AccountId, Balance>` (`res`) that is meant to hold each account's epoch reward. It first inserts the protocol-treasury reward keyed by `protocol_treasury_account`, and later, in the validator loop, inserts each validator's stake-weighted reward keyed by `account_id`. If `protocol_treasury_account` is ever also a selected validator, the second insert overwrites the first under the identical key, so the treasury's share of that account's reward is silently dropped from the returned map — while the separately-accumulated `epoch_actual_reward` total (used as `minted_amount` and added to `total_supply`) still includes the treasury share. This is the same class of bug as the referenced Flayer `_distributeFees` issue: a fee/reward split computed for two logically distinct recipients collapses into one bucket when the "beneficiary" and the "pool" (here, treasury and validator) resolve to the same key, and the code was not written to add the two shares together. ### Finding Description
`epoch_protocol_treasury` is computed and inserted into `res` keyed by `self.protocol_treasury_account`: [3](#0-2) 

`epoch_actual_reward` is initialized to `epoch_protocol_treasury` and, separately, correctly accumulates every validator's reward, so the *total* minted amount returned is correct: [4](#0-3) [5](#0-4) 

But the per-account reward map itself is populated with a plain `HashMap::insert` for every validator, unconditionally overwriting whatever was already stored under that `account_id`: [6](#0-5) 

If `protocol_treasury_account` happens to be present in `validator_block_chunk_stats` (i.e., it is also a chosen validator for the epoch), the `res.insert(account_id, reward)` at line 142 replaces the treasury entry inserted at line 84 with only the validator's stake-weighted reward — the treasury reward is nowhere in the returned map anymore.

Downstream consumers treat a single entry in this map as "the reward for this account" and explicitly assume the two are pre-combined when the treasury account is a validator: [7](#0-6) [8](#0-7) 

Specifically, `update_validator_accounts` credits `validator_rewards.get(account_id)` to the account's `locked` stake via the `stake_info` loop (lines 1668-1676), and then explicitly skips crediting a *separate* treasury reward if `stake_info.contains_key(account_id)` is true (line 1730), with the comment "If protocol treasury stakes, then the rewards was already distributed above." That assumption is false given the overwrite bug in `reward_calculator.rs`: the value actually present under that key is only the validator reward, not `validator_reward + treasury_reward`.

Net effect: `total_supply` for the epoch is incremented by `minted_amount = epoch_actual_reward` which correctly includes both the treasury share and every validator's share (block.rs new_total_supply arithmetic is untouched by this bug and doesn't detect the discrepancy), but no account anywhere in the trie is ever credited with the treasury's share for that epoch. The tokens are permanently and irrecoverably lost from any spendable/lockable balance while still being counted as "minted" in the chain's total-supply accounting, producing a persistent, unrecoverable state-root/total-supply inconsistency (minted-but-uncredited tokens).

### Impact Explanation
This causes a genuine, permanent token loss: minted supply is not zero-sum with account balances, i.e., value that the protocol believes it issued (and includes in `total_supply`, which validators/RPC clients rely on for economic invariants) is never actually deposited into any account. This matches the "token inflation or loss" and state-root-divergence categories: the chain's supply accounting diverges from the sum of account balances by exactly the treasury reward amount, every epoch the condition holds, compounding over time. Unlike the Flayer bug (a fairness/timing issue for LP shares that is eventually recoverable), this nearcore analog is a hard, permanent loss of value from the system with no path to recovery, because the overwritten map entry is discarded before ever reaching account state.

### Likelihood Explanation
The trigger condition is narrow but plausible and not "operator-only" in the excluded sense — it fires whenever the `protocol_treasury_account` (a fixed, publicly known `AccountId` from genesis config) is included among the epoch's selected validators, which happens through the completely ordinary, unprivileged `Stake` action available to any account holder. Whoever controls the keys for `protocol_treasury_account` (which could be the NEAR Foundation, a DAO, or in a permissionless/testnet/appchain deployment any operator that reuses that account id) could submit a normal `Stake` transaction from that account to become a validator, immediately triggering this bug every subsequent epoch it remains staked, with no special privilege beyond a normal signer submitting a normal transaction.

### Recommendation
In `chain/epoch-manager/src/reward_calculator.rs`, when inserting a validator's reward into `res`, add to any existing entry instead of overwriting it:
```rust
res.entry(account_id)
    .and_modify(|r| *r = r.checked_add(reward).unwrap())
    .or_insert(reward);
```
This ensures that if `protocol_treasury_account` is also a validator, its final entry in `res` equals `epoch_protocol_treasury + validator_reward`, consistent with the `update_validator_accounts` code's existing assumption ("rewards was already distributed above") and with the correctly-computed `epoch_actual_reward` total, eliminating the silent loss of minted tokens.

### Proof of Concept
1. Configure genesis so `protocol_treasury_account` is an account id, e.g. `treasury.near`.
2. Have the `treasury.near` account submit an ordinary `Stake` action with sufficient stake to be selected as a validator for the next epoch (two epochs later per the T-2 rule) — this requires no special privilege, just a signed `Stake` transaction from that account's keys.
3. Let an epoch complete. `RewardCalculator::calculate_reward` runs:
   - Inserts `epoch_protocol_treasury` under key `treasury.near` (`reward_calculator.rs:84`).
   - Later in the loop, `treasury.near` is also present in `validator_block_chunk_stats` (since it's now a validator), so `res.insert("treasury.near", validator_reward)` overwrites the treasury entry (`reward_calculator.rs:142`).
   - `epoch_actual_reward` (returned as `minted_amount`) still correctly equals `epoch_protocol_treasury + sum(validator_rewards)` (`reward_calculator.rs:90, 143`).
4. `total_supply` for the next block increases by this full `minted_amount` (`core/primitives/src/block.rs:193`), but `update_validator_accounts` only adds `res["treasury.near"] == validator_reward` (not `+ epoch_protocol_treasury`) to `treasury.near`'s locked balance, and explicitly skips the separate treasury-credit branch because `stake_info.contains_key("treasury.near")` is true (`runtime/runtime/src/lib.rs:1730`).
5. Result: `epoch_protocol_treasury` yoctoNEAR are counted in `total_supply` every epoch but never appear in any account's `amount`/`locked` balance — a permanent, compounding discrepancy between minted supply and the sum of account balances.

Note: I was not able to find an existing test in `chain/epoch-manager/src/tests/mod.rs` that exercises the case where `protocol_treasury_account` is simultaneously a selected validator, so I cannot confirm from the test suite whether this exact scenario is already guarded against elsewhere (e.g., by preventing the treasury account from being selectable as a validator) — this would need to be verified in a live session with broader code access before treating the fix as final.
