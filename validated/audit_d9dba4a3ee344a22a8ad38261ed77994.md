### Title
Precision loss due to division-before-multiplication in witness brokerage/reward calculation - (File: chainbase/src/main/java/org/tron/core/service/MortgageService.java)

### Summary
`MortgageService.payReward` computes the brokerage cut of a witness's reward by first dividing the integer brokerage percentage by 100 (producing a `double`), and only then multiplying by the reward `value`. This division-before-multiplication ordering mirrors exactly the pattern flagged in the external report (`liquidationBonus = (borrowedAmount * liq.bonusBP) / Constants.BP` reordered as divide-then-multiply causes truncation/rounding loss), and results in witnesses/voters receiving a slightly different (generally smaller) reward share than the mathematically correct one.

### Finding Description
In `payReward`:
```java
private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
}
``` [1](#0-0) 

`brokerage / 100` is computed first as a `double` and then multiplied by `value` before being truncated by the cast to `long`. Because `brokerage/100` cannot always be represented exactly in binary floating point (e.g. brokerage=33 → 0.33 is not exact), the final `(long)` truncation of `brokerageRate * value` can differ from the mathematically correct `(brokerage * value) / 100`, especially for large `value`. The reward that remains for voters (`value - brokerageAmount`, stored via `delegationStore.addReward`) is directly affected by this same rounding error.

This function is invoked from `payBlockReward` and `payTransactionFeeReward`, which are called for every block produced during normal block application [2](#0-1) , as well as from `payStandbyWitness`, which itself already performs a divide-then-multiply on `(double) totalPay / voteSum` before multiplying by `voteCount` [3](#0-2) . This is the same "divide then multiply" ordering that the reported Solidity bug singled out as the root cause of precision loss.

Elsewhere in the codebase, the project has taken deliberate steps to harden similarly-shaped calculations against precision loss by switching to `BigInteger`-based multiply-then-divide (e.g. `ResourceProcessor.calculateGlobalLimitV2`, `RepositoryImpl.usageToBalance`, `DelegationStore.accumulateWitnessVi`, `RewardViCalService`) [4](#0-3) [5](#0-4) , indicating the project is aware of this bug class in reward-related math but has not applied the same fix to `MortgageService.payReward`/`payStandbyWitness`.

### Impact Explanation
This affects reward accounting for every block produced (via `payBlockReward`/`payTransactionFeeReward`) and every maintenance-cycle standby-witness payout (`payStandbyWitness`). The brokerage split between the super representative (witness) and the voters/delegators is computed incorrectly by up to one unit of TRX-precision per call due to floating point rounding, and this error compounds over every block/cycle across the chain's lifetime. Funds are not lost from the system (they end up either with the witness's allowance or the cycle reward pool depending on rounding direction), but individual account balances are systematically miscalculated relative to the intended brokerage percentage — an accounting/precision correctness issue in the core reward-distribution logic that all TRX holders who vote for witnesses are affected by.

### Likelihood Explanation
This code path executes automatically on every single block (`payBlockReward`, `payTransactionFeeReward`) and every maintenance cycle (`payStandbyWitness`) as part of normal chain operation — no attacker action or malicious input is required. The precision loss is deterministic and will occur whenever the witness's brokerage rate is not evenly divisible in binary floating point (which is the common case, e.g. any percentage other than round numbers like 0, 50, 100, 25, 75), making this a persistently, continuously reachable but low-per-instance-magnitude defect.

### Recommendation
Replace the floating-point divide-then-multiply with an integer/BigInteger multiply-then-divide, consistent with the hardening already applied elsewhere in the codebase (e.g. `DelegationStore.accumulateWitnessVi`, `ResourceProcessor.calculateGlobalLimitV2`):
```java
long brokerageAmount = BigInteger.valueOf(value)
    .multiply(BigInteger.valueOf(brokerage))
    .divide(BigInteger.valueOf(100))
    .longValueExact();
```
Apply the same fix to `eachVotePay`/`pay` computation in `payStandbyWitness` (multiply `totalPay` by `voteCount` before dividing by `voteSum`, using `BigInteger` to avoid overflow).

### Proof of Concept
Given `brokerage = 33` and `value = 100` (TRX in sun, or any integer reward amount):
- Correct (multiply-then-divide) result: `(33 * 100) / 100 = 33`.
- Current code: `brokerageRate = (double) 33 / 100 = 0.33` (not exactly representable in binary floating point, actual stored value is `0.32999999999999996...` or similar depending on rounding), then `brokerageRate * 100 = 32.999999999999996`, and `(long)` truncation yields `32` instead of `33`.
- This 1-unit-per-call discrepancy, multiplied across every block reward and transaction fee reward for every witness over the life of the chain, is a systemic and reproducible precision-loss bug directly analogous to the reported `getLiquidationBonus` division-before-multiplication issue.     long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
