Confirmed. The `Swap` trait's `swap_exact_tokens_for_tokens` (implemented by `pallet-asset-conversion::Pallet<T>` via `do_swap_exact_tokens_for_tokens`) computes output purely from live pool reserves using the constant-product formula, and enforcing the `amount_out_min` bound is entirely opt-in by the caller [1](#0-0) . `pallet-snowbridge-system-frontend`'s `swap_and_burn` hard-codes this bound to `None`, so no protection exists at the call site [2](#0-1) . This function is reached unconditionally from the public, unprivileged `add_tip` extrinsic (call index 2) and conditionally from `register_token` (call index 1, only skipped when origin is root/`Location::here()`), both via `swap_fee_asset_and_burn` [3](#0-2) [4](#0-3) . The resulting `ether_gained` is burned via `burn_for_teleport` and forwarded as the `amount` field in the `AddTip`/`RegisterToken` Transact call to `EthereumSystem` on BridgeHub, where it is trusted as the settlement/reward value [5](#0-4) .

Since the underlying `pallet-asset-conversion` pools are public AMMs that any user can swap against via ordinary extrinsics, an attacker can atomically skew the `(fee_asset, ether)` pool reserves (e.g., via `pallet_utility::batch_all`) immediately before calling `add_tip`, causing the unprotected swap to return an inflated `ether_gained` at the expense of the pool's other liquidity providers, while that inflated value is reported and forwarded as the legitimate bridge reward/tip amount. This is a reachable, unprivileged, single-transaction exploit path with a named corrupted value (`ether_gained`/`amount` in `EthereumSystemCall::AddTip`/`RegisterToken`), and existing guards (none) are demonstrably insufficient — the claim is supported by the code as described.

Audit Report

## Title
Missing slippage protection (`amount_out_min = None`) in `swap_and_burn` allows spot-price manipulation of the AssetConversion pool to mint an inflated Snowbridge relayer reward/tip credit - (File: `bridges/snowbridge/pallets/system-frontend/src/lib.rs`)

## Summary
`Pallet::swap_and_burn` in `pallet-snowbridge-system-frontend`, reachable from the public unprivileged `add_tip` and `register_token` extrinsics, calls `pallet-asset-conversion`'s `swap_exact_tokens_for_tokens` with the `amount_out_min` parameter hard-coded to `None`. The swap's spot-priced output (`ether_gained`) is then burned and forwarded verbatim as the relayer reward/tip amount in the `AddTip`/`RegisterToken` Transact call to `EthereumSystem` on BridgeHub, with no protection against pool-price manipulation.

## Finding Description
`add_tip` (call index 2) and `register_token` (call index 1) both invoke `Self::swap_fee_asset_and_burn`, which for any non-ether fee asset calls `Self::swap_and_burn` [3](#0-2) [6](#0-5) . Inside `swap_and_burn`, the swap is executed with the minimum-output bound explicitly set to `None`:
```rust
let ether_gained = T::Swap::swap_exact_tokens_for_tokens(
    who.clone(),
    swap_path,
    tip_amount,
    None, // No minimum amount required
    who,
    true,
)?;
``` [2](#0-1) 

The `Swap` trait for `pallet-asset-conversion::Pallet<T>` computes output strictly from live constant-product pool reserves via `do_swap_exact_tokens_for_tokens`, and the `amount_out_min` bound is the *only* mechanism intended to protect a caller from an unfavorable/manipulated price at execution time [1](#0-0) [7](#0-6) . Because that bound is disabled here, `ether_gained` is fully dependent on whatever the pool reserves happen to be at the moment of execution.

`ether_gained` is subsequently burned via `burn_for_teleport` and passed unchanged as the `amount` in `EthereumSystemCall::AddTip`/`RegisterToken`, dispatched to BridgeHub via Transact, where it is used to credit relayer reward/registration fee accounting on the Ethereum side [8](#0-7) [5](#0-4) .

Since the relevant `(fee_asset, ether)` `pallet-asset-conversion` pool is a public AMM reachable by ordinary swap extrinsics, any unprivileged account can, within a single atomic `pallet_utility::batch_all`, skew the pool's reserves immediately before calling `add_tip`/`register_token`, forcing `swap_and_burn` to compute an inflated (or deflated) `ether_gained` against the manipulated reserves with zero protection.

## Impact Explanation
This is public underpriced work that corrupts bridge settlement: an unprivileged caller can extract value from `pallet-asset-conversion` liquidity providers via a classic zero-slippage sandwich, while simultaneously causing the relayer reward/tip amount recorded on BridgeHub/Ethereum (`ether_gained`, forwarded as `amount` in `AddTip`) to reflect a manipulated spot price rather than the true economic value contributed. This falls within the impact gate's "public underpriced work that degrades... bridge processing" category, and repeated exploitation could drain pool liquidity providers while inflating on-chain relayer reward credits.

## Likelihood Explanation
The attack requires no privileged role, governance action, malicious validator, or multi-block MEV — it is executable entirely within a single atomic transaction by any signed account, using standard tools (`pallet_utility::batch_all` combined with ordinary `pallet-asset-conversion` swap extrinsics) to manipulate the pool immediately before invoking the public `add_tip`/`register_token` extrinsics. This is a fully unprivileged, repeatable exploit path.

## Recommendation
Never hard-code `None` for the slippage/minimum-output parameter when a swap's output feeds settlement or reward accounting. `swap_and_burn` should derive an acceptable minimum bound — e.g., using `quote_price_exact_tokens_for_tokens` as a reference with a bounded allowed deviation, or requiring the caller to supply an explicit `min_ether_out` parameter and reverting if unmet — consistent with how other `pallet-asset-conversion` swap extrinsics require `amount_out_min`/`amount_in_max`.

## Proof of Concept
1. Attacker identifies/creates a `pallet-asset-conversion` pool for `(fee_asset, ether_location)` with liquidity shallow relative to their capital.
2. Attacker submits a single `pallet_utility::batch_all` extrinsic containing: (a) a swap that skews the pool reserves to inflate the `fee_asset → ether` exchange rate, and (b) `snowbridge_pallet_system_frontend::add_tip(message_id, fee_asset_amount)`.
3. Inside `add_tip`, `swap_and_burn` executes with `None` minimum output against the skewed reserves, returning an inflated `ether_gained`.
4. `ether_gained` is burned and forwarded via `AddTip` to `EthereumSystem` on BridgeHub, crediting a reward disproportionate to real value contributed, funded by LPs of the manipulated pool.
5. A reproducible unit/integration test in `bridges/snowbridge/pallets/system-frontend/src/tests.rs` can set up a mock `Swap` pool, execute a manipulating swap followed by `add_tip` in the same block, and assert `ether_gained` exceeds the value obtainable at the pre-manipulation price.

		fn swap_fee_asset_and_burn(
			origin: Location,
			fee_asset: Asset,
		) -> Result<u128, DispatchError> {
			let ether_location = T::EthereumLocation::get();
			let (fee_asset_location, fee_amount) = match fee_asset {
				Asset { id: AssetId(ref loc), fun: Fungible(amount) } => (loc, amount),
				_ => {
					tracing::debug!(target: LOG_TARGET, ?fee_asset, "error matching fee asset");
					return Err(Error::<T>::UnsupportedAsset.into());
				},
			};
			if fee_amount == 0 {
				return Ok(0);
			}

			let ether_gained = if *fee_asset_location != ether_location {
				Self::swap_and_burn(
					origin.clone(),
					fee_asset_location.clone(),
					ether_location,
					fee_amount,
				)
				.inspect_err(|&e| {
					tracing::debug!(target: LOG_TARGET, ?e, "error swapping asset");
				})?
			} else {
				burn_for_teleport::<T::AssetTransactor>(&origin, &fee_asset)
					.map_err(|_| Error::<T>::BurnError)?;
				fee_amount
			};
			Ok(ether_gained)
		}
