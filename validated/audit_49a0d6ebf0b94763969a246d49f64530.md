### Title
Unhandled `unwrap()` panic on Token-2022 transfer-fee calculation causes DoS in deposit/withdraw/borrow/repay - ([File: programs/marginfi/src/utils/general.rs])

### Summary
`calculate_pre_fee_spl_deposit_amount` and `calculate_post_fee_spl_deposit_amount` in `programs/marginfi/src/utils/general.rs` call `.unwrap()` on the `Option<u64>` returned by SPL Token-2022's `TransferFee::calculate_pre_fee_amount` / `calculate_epoch_fee`, which return `None` on integer overflow. Since these values derive from mint-controlled `TransferFeeConfig` fields (`transfer_fee_basis_points`, `maximum_fee`) combined with user-supplied deposit/withdraw amounts, a malformed or adversarial Token-2022 mint configuration can force the `Option` to be `None`, causing an on-chain panic. [1](#0-0) 

### Finding Description
`calculate_pre_fee_spl_deposit_amount` fetches the mint's `TransferFeeConfig` extension and computes:
```
let epoch_fee = transfer_fee_config.get_epoch_fee(epoch);
let pre_fee_amount = calculate_pre_fee_amount(epoch_fee, post_fee_amount).unwrap();
``` [2](#0-1) 

Similarly, `calculate_post_fee_spl_deposit_amount` does:
```
let fee = ... transfer_fee_config.calculate_epoch_fee(epoch, input_amount).unwrap();
``` [3](#0-2) 

SPL Token-2022's `calculate_pre_fee_amount` internally special-cases `transfer_fee_basis_points == MAX_FEE_BASIS_POINTS (10000)` by computing `maximum_fee.checked_add(post_fee_amount)`. If the mint's `maximum_fee` is set close to `u64::MAX` (a value fully controlled by whoever configures the Token-2022 mint's `TransferFeeConfig` extension, not by the marginfi program), this addition overflows for essentially any nonzero `post_fee_amount`, returning `None`. The subsequent `.unwrap()` in marginfi's wrapper then panics, aborting the transaction with a program panic instead of a handled `MarginfiError`.

This function is reachable directly from the unprivileged, user-facing `lending_account_deposit` instruction:
```
let amount_pre_fee = maybe_bank_mint.as_ref().map(|mint| {
    utils::calculate_pre_fee_spl_deposit_amount(mint.to_account_info(), deposit_amount, clock.epoch)
}) ...
``` [4](#0-3) 

The same unwrap pattern is also referenced from `borrow.rs`, `repay.rs`, `withdraw.rs`, and `handle_bankruptcy.rs`, meaning the panic can be hit from every core accounting path that moves Token-2022 assets through a bank whose mint carries a transfer-fee extension. [1](#0-0) 

### Impact Explanation
A bank backed by a Token-2022 mint with an extreme (but protocol-valid, since `transfer_fee_basis_points` and `maximum_fee` are ordinary Token-2022 fields the marginfi program does not itself validate/bound) `TransferFeeConfig` causes every deposit (and potentially withdraw/borrow/repay, since they share the same fee-calculation helper) against that bank to panic instead of failing gracefully. Because deposit and withdraw of that specific bank both route through the unchecked `unwrap()`, users who already deposited into such a bank could become unable to withdraw their funds through the standard instruction path, which is a denial-of-service on user funds for that bank (permanent lock/freeze of an account's ability to interact with that bank via the normal path).

### Likelihood Explanation
Likelihood depends on whether an unprivileged actor can get a bank created (or an existing bank's mint effectively targeted) using a Token-2022 mint with an oversized `maximum_fee`/`transfer_fee_basis_points=10000` transfer-fee config. The repo contains a `add_pool_permissionless.rs` instruction, which suggests bank creation is not always gated behind admin authority for some integrations (Kamino/Solend/Drift/Juplend pools); I was not able to fully verify within the remaining investigation whether that permissionless path allows an attacker to supply an arbitrary Token-2022 mint of this shape end-to-end. Independent of attacker intent, the bug is also reachable unintentionally: any admin who lists a legitimate Token-2022 asset whose issuer sets an aggressive transfer-fee configuration would trigger the same panic on ordinary user deposits/withdrawals, which is a real robustness defect regardless of adversarial mint crafting.

### Recommendation
Replace all `.unwrap()` calls on `calculate_pre_fee_amount(...)` / `calculate_epoch_fee(...)` in `programs/marginfi/src/utils/general.rs` (`calculate_pre_fee_spl_deposit_amount`, `calculate_post_fee_spl_deposit_amount`) with proper error propagation, e.g. `.ok_or(MarginfiError::MathError)?`, so malformed or extreme Token-2022 transfer-fee configurations return a handled program error rather than causing an on-chain panic. Audit other conversion/arithmetic call sites in the codebase for the same `unwrap()`-on-user/mint-controlled-input pattern identified in the referenced external report.

### Proof of Concept
1. Create a Token-2022 mint with a `TransferFeeConfig` extension where `transfer_fee_basis_points = 10000` (`MAX_FEE_BASIS_POINTS`) and `maximum_fee = u64::MAX - 1`.
2. Get this mint registered as a marginfi bank's mint (via an admin `lending_pool_add_bank` call, or via the permissionless pool-add path if it allows arbitrary Token-2022 mints).
3. Call `lending_account_deposit` with any `deposit_amount > 1` for that bank.
4. Inside `calculate_pre_fee_spl_deposit_amount`, `calculate_pre_fee_amount` computes `maximum_fee.checked_add(post_fee_amount)`, which overflows `u64` and returns `None`.
5. The `.unwrap()` at `programs/marginfi/src/utils/general.rs:80` panics, aborting the transaction and demonstrating the DoS. [2](#0-1)

pub fn calculate_pre_fee_spl_deposit_amount(
    mint_ai: AccountInfo,
    post_fee_amount: u64,
    epoch: u64,
) -> MarginfiResult<u64> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(post_fee_amount);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    match mint.get_extension::<TransferFeeConfig>() {
        Ok(transfer_fee_config) => {
            let epoch_fee = transfer_fee_config.get_epoch_fee(epoch);
            let pre_fee_amount = calculate_pre_fee_amount(epoch_fee, post_fee_amount).unwrap();
            Ok(pre_fee_amount)
        }
        Err(_) => Ok(post_fee_amount),
    }
}

pub fn calculate_post_fee_spl_deposit_amount(
    mint_ai: AccountInfo,
    input_amount: u64,
    epoch: u64,
) -> MarginfiResult<u64> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(input_amount);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    let fee = if let Ok(transfer_fee_config) = mint.get_extension::<TransferFeeConfig>() {
        transfer_fee_config
            .calculate_epoch_fee(epoch, input_amount)
            .unwrap()
    } else {
        0
    };

    let output_amount = input_amount
        .checked_sub(fee)
        .ok_or(MarginfiError::MathError)?;

    Ok(output_amount)
}
```
