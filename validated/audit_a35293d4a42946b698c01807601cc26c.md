Found a solid local analog: `pallet-bounties`'s permissionless `reclaim_bounty_funds` extrinsic, which mirrors the exact "reserve-sweep-that-also-sweeps-someone-else's-rightful-funds" pattern from the Morpho report.

### Title
Permissionless `reclaim_bounty_funds` can sweep a beneficiary's/curator's un-delivered payout to the treasury after a silent (`debug_assert`-guarded) transfer failure - (`substrate/frame/bounties/src/lib.rs`)

### Summary
`claimToTreasury(COMP)` in the external report sweeps a market's "reserve" to the treasury, but because reward accounting and reserve accounting share the same underlying balance, it also captures funds that legitimately belong to someone else (pending COMP rewards). The exact same pattern exists in `pallet-bounties`: `claim_bounty` pays the curator and beneficiary out of the bounty's sub-account and then unconditionally removes the bounty from storage, using `debug_assert!` (not `ensure!`) to check that the payout transfers succeeded. `reclaim_bounty_funds` is a permissionless, unprivileged extrinsic whose only precondition is that the bounty entry no longer exists in storage — it then sweeps *all* remaining balance/assets of that bounty's sub-account to the treasury.

### Finding Description
In `claim_bounty` [1](#0-0) , the payout logic is:
```
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());
*maybe_bounty = None;
```
`debug_assert!` compiles to a no-op in release/production builds. If either transfer returns `Err` for any reason (e.g. balance locks/holds/freezes on the bounty sub-account, or any `Currency`/`fungible` implementation quirk that makes `free_balance` diverge from the actually-transferable amount), the funds silently stay in `bounty_account` while the code proceeds to unconditionally clear the storage entry (`*maybe_bounty = None`) and remove child-bounty bookkeeping.

Once the `Bounties` storage entry for that `bounty_id` is gone, `reclaim_bounty_funds` becomes callable by anyone [2](#0-1) :
```
pub fn reclaim_bounty_funds(origin: OriginFor<T>, #[pallet::compact] bounty_id: BountyIndex) -> DispatchResultWithPostInfo {
    ensure_signed(origin)?;
    ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);
    ...
    let transferred = T::TransferAllAssets::force_transfer_all_assets(&bounty_account, &treasury_account)?;
```
The only guard is `contains_key(bounty_id) == false`. It has no way to distinguish "genuinely stranded dust" from "a beneficiary's/curator's payout that failed to land due to a swallowed transfer error." The corrupted invariant is: the bounty sub-account balance after `claim_bounty` is assumed to always be zero (guaranteed only by a `debug_assert!`, which provides zero protection in a release runtime), so `reclaim_bounty_funds` treats any leftover balance as fair game for the treasury even when it is actually money still owed to a specific, named beneficiary or curator.

### Impact Explanation
This is a public-entrypoint path where an unprivileged attacker (anyone signing `reclaim_bounty_funds`) can redirect funds that rightfully belong to a bounty's curator or beneficiary to the treasury, permanently denying that beneficiary their payout — matching "wrong beneficiary or amount," and "permanent user-fund lock" impact categories. Because the precondition (`!contains_key`) is satisfied unconditionally once `claim_bounty` runs (regardless of whether the internal transfers actually succeeded), no admin/governance action is needed to trigger the sweep — a normal user can race to call `reclaim_bounty_funds` right after any `claim_bounty` execution that hit a transfer failure.

### Likelihood Explanation
The trigger condition (an internal transfer from `bounty_account` failing) is not exercised in the tests I found, which only cover the happy path where `TransferAllAssets`/native transfers always succeed [3](#0-2) . It requires the `Currency`/`fungible` implementation in the concrete runtime to have holds/freezes/locks or another failure mode capable of making `free_balance` diverge from the reducible/transferable amount for the deterministic bounty sub-account. This is not certain to be reachable in every runtime configuration, but the code explicitly acknowledges the theoretical failure ("should not fail") while relying solely on a release-mode no-op (`debug_assert!`) rather than a real `ensure!`/error propagation, which is the same class of "assumed-safe assumption with no real guard" that caused the Morpho COMP issue.

### Recommendation
Replace `debug_assert!(res.is_ok())` in `claim_bounty` (and the analogous pattern in `pallet-child-bounties::claim_child_bounty`) with real error handling: propagate the error, or explicitly track/emit an event when a payout transfer fails so the funds are not silently orphaned in a since-removed bounty's account. Additionally, `reclaim_bounty_funds` should not treat every non-existent bounty ID's leftover balance as unconditionally sweepable — consider requiring a cooldown, an explicit "orphaned funds" marker set only after successful payout verification, or restricting `force_transfer_all_assets` from being invoked on sub-accounts where a payout is known/expected to have been due to a specific beneficiary.

### Proof of Concept
1. Configure (or find) a `Currency`/`fungible::Mutate` implementation for the bounty sub-account where `free_balance` can report an amount that is not fully reducible via `AllowDeath` transfer at the moment `claim_bounty` executes (e.g., a hold/freeze placed on the account by another pallet operating on the same account namespace, or a custom `Currency` impl with non-atomic balance semantics).
2. Get a bounty into `PendingPayout` status and call `claim_bounty`; the internal `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err`, but because it's checked with `debug_assert!`, in a release build the error is silently ignored and `*maybe_bounty = None` still executes, removing the bounty from `Bounties` storage while `payout` funds remain stuck in `bounty_account`.
3. Any unprivileged account then calls `reclaim_bounty_funds(bounty_id)`; since `Bounties::contains_key(bounty_id)` is now `false`, the extrinsic succeeds and sweeps the beneficiary's un-paid `payout` (and/or curator's `final_fee`) from `bounty_account` straight to the treasury, permanently denying the rightful beneficiary/curator their funds.

		pub fn reclaim_bounty_funds(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResultWithPostInfo {
			ensure_signed(origin)?;

			// A live bounty still manages its account, so leave it untouched.
			ensure!(!Bounties::<T, I>::contains_key(bounty_id), Error::<T, I>::BountyStillActive);

			debug_assert!(
				T::ChildBountyManager::child_bounties_count(bounty_id) == 0,
				"child bounties should not exist for a closed bounty"
			);

			let bounty_account = Self::bounty_account_id(bounty_id);
			let treasury_account = Self::account_id();

			let transferred = T::TransferAllAssets::force_transfer_all_assets(
				&bounty_account,
				&treasury_account,
			)?;

#[test]
fn reclaim_bounty_funds_works_for_funded_bounty() {
	ExtBuilder::default().build_and_execute(|| {
		Balances::make_free_balance_be(&Treasury::account_id(), 101);

		// Propose and approve a bounty so it gets funded.
		assert_ok!(Bounties::propose_bounty(RuntimeOrigin::signed(0), 50, b"12345".to_vec()));
		assert_ok!(Bounties::approve_bounty(RuntimeOrigin::root(), 0));
		go_to_block(2);

		// Bounty is now Funded; its sub-account holds 50.
		let bounty_account = Bounties::bounty_account_id(0);
		assert_eq!(Balances::free_balance(&bounty_account), 50);

		pallet_bounties::Bounties::<Test>::remove(0);
		pallet_bounties::BountyDescriptions::<Test>::remove(0);

		let treasury_before = Treasury::pot();

		// Anyone can call reclaim_bounty_funds.
		assert_ok!(Bounties::reclaim_bounty_funds(RuntimeOrigin::signed(1), 0));

		assert_eq!(last_event(), BountiesEvent::BountyFundsReclaimed { bounty_id: 0 },);

		// Bounty account is now empty.
		assert_eq!(Balances::free_balance(&bounty_account), 0);

		// Treasury received the funds (minus any burn that happened at go_to_block(2)).
		assert!(Treasury::pot() > treasury_before);
	});
