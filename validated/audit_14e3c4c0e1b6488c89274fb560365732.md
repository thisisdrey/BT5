### Title
A borrower can front-run `Pool.liquidate` with `DepositToken.deposit`/`withdraw` to indefinitely dodge liquidation - (File: contracts/DepositToken.sol)

### Summary
`Pool.liquidate` evaluates account health at execution time via `debtPositionOf(account_)` and reverts with `PositionIsHealthy` if the account is healthy. `DepositToken.deposit` is permissionless, has no solvency or "being-liquidated" check, and `DepositToken.withdraw` only requires the amount to be *unlocked* (`_revertIfLocked`). A borrower whose position is slightly underwater can therefore sandwich the liquidation: front-run with a small `deposit` to become healthy (liquidation tx reverts), then back-run with `withdraw` of the now-excess collateral. This repeats every time a liquidator tries, letting the user control when — if ever — they get liquidated, mirroring the reported SymmIO `allocate`/`deallocate` bug class.

### Finding Description [1](#0-0) 
`Pool.liquidate` computes `(bool _isHealthy, ...) = debtPositionOf(account_)` inline and reverts `PositionIsHealthy` if healthy. There is no "position entered liquidation" flag — health is whatever the oracle says at that instant. [2](#0-1) 
`deposit(amount_, onBehalfOf_)` is `whenNotPaused nonReentrant` and open to anyone; depositing to oneself always improves health. No minimum deposit, no cooldown, no check that the account is under liquidation. [3](#0-2) 
`unlockedBalanceOf` returns `quoteUsdToToken(underlying, _issuableInUsd.wadDiv(collateralFactor))`, and `withdraw` only enforces `_revertIfLocked`. So right after the extra deposit makes the position healthy, the surplus collateral becomes unlocked again and can be pulled back out (net cost = deposit + withdraw fees only).

Attack loop (per liquidation attempt):
1. Liquidator broadcasts `liquidate(synth, victim, amountToRepay, depositToken)`.
2. Victim front-runs with `depositToken.deposit(smallAmount, victim)` → `debtPositionOf` now reports healthy.
3. Liquidator's tx reverts `PositionIsHealthy`.
4. Victim back-runs `depositToken.withdraw(unlockedBalanceOf(victim), victim)` → position is underwater again, awaiting the next attempt.

This is exactly the report's bug class: the liquidatee toggles solvency around the liquidator's transaction using public, unconditional entry points.

### Impact Explanation
A borrower can block/delay their own liquidation indefinitely at the cost of deposit/withdraw fees, while continuing to hold the minted synthetic assets. During a fast price crash this delay is precisely when bad debt accrues — each reverted attempt buys the borrower another block, and liquidators waste gas and may give up or be out-competed by the victim's own bots. The result is direct risk of protocol insolvency (debt outliving collateral value) and temporary freezing of the liquidation liveness guarantee.

### Likelihood Explanation
The attack requires only an EOA monitoring the mempool for `liquidate` calls targeting it, plus modest capital (just enough collateral to flip `_isHealthy`, which is cheap when the position is only marginally underwater). It needs no privileged role, no oracle manipulation, no malicious contract — just public `deposit`/`withdraw`. Any chain without strong private-mempool submission by liquidators (e.g., Base, Optimism ordering) is exposed; even with private transactions, the victim can race with a same-block or next-block deposit whenever they observe liquidator intent.

### Recommendation
Add a liquidation grace/two-phase mechanism or make deposited collateral ineligible to rescue a position mid-liquidation — e.g., snapshot-based liquidation intents, or a `debtFloorInUsd`-style minimum deposit, or a lock that prevents `deposit` → `withdraw` round-trips within the same block/short window. Simplest mitigation: a short cooldown or timelock on `withdraw` after `deposit` (and/or flagging accounts targeted by a pending liquidation), so the front-run deposit cannot be costlessly reversed.

### Proof of Concept
Hardhat test (extends `test/Pool.test.ts` "when the position is unhealthy" setup, where `alice` is underwater after `masterOracle.updatePrice(met.address, newMetPrice)`):

```ts
it('alice can front-run liquidate with deposit and back-run with withdraw', async function () {
  // given: alice is unhealthy (collateral:debt >= 1, but below CF)
  const {_isHealthy: before} = await pool.debtPositionOf(alice.address);
  expect(before).false;

  // when: alice front-runs the liquidator with a small deposit
  const {_issuableInUsd} = await pool.debtPositionOf(alice.address); // negative headroom
  const neededUsd = (await pool.debtOf(alice.address))
    .sub((await pool.debtPositionOf(alice.address))._issuableLimitInUsd)
    .add(parseEther('1'));
  const neededMet = await masterOracle.quoteUsdToToken(met.address, neededUsd.wadDiv(metCF));
  await met.connect(alice).approve(msdMET.address, ethers.constants.MaxUint256);
  await msdMET.connect(alice).deposit(neededMet, alice.address);

  // then: liquidator's tx now reverts
  const amountToRepay = userMintAmount.div(2);
  await expect(
    pool.connect(liquidator).liquidate(msEth.address, alice.address, amountToRepay, msdMET.address)
  ).to.be.revertedWithCustomError(pool, 'PositionIsHealthy');

  // and: alice withdraws the excess collateral again — position back underwater
  const unlocked = await msdMET.unlockedBalanceOf(alice.address);
  expect(unlocked).gt(0);
  await msdMET.connect(alice).withdraw(unlocked, alice.address);
  expect((await pool.debtPositionOf(alice.address))._isHealthy).false;
});
```

The loop costs alice only `depositFee + withdrawFee` on `neededMet` per attempt and can be repeated for every liquidation transaction.
