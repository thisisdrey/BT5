### Title
Unchecked length field in TVM precompile call-data array extraction allows OOM/crash via single contract call - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The reported Bouncy Castle CVE-2026-59646 is a "read an unchecked length field from untrusted input, then allocate a buffer of that size" bug class. The same pattern exists in java-tron's precompiled-contract call-data decoders `extractBytes32Array`, `extractBytesArray`, and `extractSigArray`, which read a 32-byte "array length" word directly from the caller-supplied precompile input and allocate a Java array of that size before ever validating it against the actual size of the supplied call data.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` each take `len = words[offset].intValueSafe()` — a value taken straight from a word inside the attacker-supplied precompile `data` — and immediately allocate `new byte[len][]` with no upper bound check against the real length of `data`: [1](#0-0) [2](#0-1) [3](#0-2) 

`DataWord.intValueSafe()` only clamps the result to `Integer.MAX_VALUE` when the word occupies more than 4 bytes or the raw big-endian interpretation is negative; any 4-byte-representable positive value (up to `0x7FFFFFFF` = 2,147,483,647) is returned unmodified: [4](#0-3) 

This is the exact analog of the DTLS reassembler bug: a 3-to-4-byte length taken from an untrusted wire/call-data buffer is used to size an allocation with no sanity check that the declared length is consistent with the amount of data actually available. Here, `len` can be set to any value up to ~2.1 billion by crafting the corresponding call-data word, causing `new byte[len][]` (an array of ~2.1 billion object references, ~17 GB on a 64-bit JVM with compressed oops, larger without) to be allocated on the node executing/validating the transaction.

### Impact Explanation
Any account can invoke a smart contract that performs a `CALL`/`STATICCALL` to the relevant precompiled contract address with crafted input data containing an inflated length word. The resulting oversized array allocation throws `OutOfMemoryError` or otherwise exhausts heap/GC resources on every full node that executes or re-validates the transaction (since all nodes in the network execute the same TVM instructions to reach consensus), leading to a node crash/halt. Because the same call data is processed identically by every validating node, this is a broadly reachable, network-wide denial-of-service vector triggerable by a single unprivileged, correctly-signed transaction.

### Likelihood Explanation
High. Reaching this code only requires deploying/calling a contract that performs a `CALL` to the precompile address that invokes these helper functions with attacker-controlled `data`; no special privileges, whitelisting, or SR/witness status is needed — any transaction broadcaster or contract deployer can construct this input.

### Recommendation
Bound `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` to the maximum number of array elements that could actually be represented by the remaining `data`/`words` length before allocating (e.g., `len <= (data.length - offsetInBytes) / minElementSize` and `len <= words.length - offset - 1`), rejecting/reverting the precompile call if the declared length exceeds what the supplied call data can back, mirroring the existing `verifyLength` bounds check pattern already used in `RLP.decode`/`decodeLazyList`.

### Proof of Concept
1. Deploy a contract that performs a low-level `call` to the affected precompiled-contract address (the one that reaches `extractBytesArray`/`extractSigArray`/`extractBytes32Array`).
2. Craft the call data so the word at the expected "array length" offset encodes a large positive 32-bit value (e.g. `0x000000000000000000000000000000000000000000000000000000007FFFFFFF`), while the remainder of `data` is arbitrarily short.
3. Broadcast the transaction; when the precompile executes, `words[offset].intValueSafe()` returns the attacker-chosen large value unmodified, and `new byte[len][]` (or `new byte[len]`) attempts to allocate on the order of gigabytes, causing `OutOfMemoryError`/severe GC pressure on every node that executes the transaction.     int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];

   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
