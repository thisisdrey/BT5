Based on the investigation, the strongest legitimate analog in Gitaly for this bug class (an operation that optimistically assumes success/reversibility on one side of a two-phase action, but which can leave a resource permanently stuck, recoverable only through out-of-band intervention) is the object-pool alternates disconnection flow.

### Title
Non-atomic Git alternates disconnection can permanently corrupt a repository requiring administrator recovery - (File: internal/git/objectpool/disconnect.go)

### Summary
`DisconnectGitAlternates` (exposed via `ObjectPoolService.DisconnectGitAlternates`, reachable by an ordinary user unlinking a fork from its pool) performs a non-atomic sequence: hard-link pool objects into the member repository, rename away `objects/info/alternates`, run a connectivity check, and only then commit or roll back. If Gitaly is interrupted between the rename and the conditional restore, the repository is left without object access and without its alternates link, and can only be repaired by an administrator restoring the backed-up alternates file — the same "half succeeds, half fails, only an out-of-band fix can recover it" pattern described in the ERC-721 report, mapped onto Gitaly's alternates/quarantine isolation domain instead of a token-transfer domain.

### Finding Description
`Disconnect` in [1](#0-0)  is explicitly documented as risky: it hard-links the pool's objects into the member repository, then calls `removeAlternatesIfOk`, which renames `objects/info/alternates` out of the way, runs a `git rev-list --objects --all --quiet` connectivity check, and restores the alternates file from backup only if that check fails [2](#0-1) . The commit path only becomes final after the connectivity check passes and a transaction vote succeeds [3](#0-2) . Between the `os.Rename(altFile, backupFile)` and the `defer` rollback, the repository has no alternates configured; if the process crashes or the rollback itself fails (e.g., due to a concurrent filesystem issue when re-linking `backupFile`), the repository is left with a missing `objects/info/alternates` and a stray `.N.<hex>` backup file, unrecoverable without manual administrator action, exactly as documented in the function's own comment and in `proto/objectpool.proto` [4](#0-3)  and `doc/object_pools.md` [5](#0-4) .

### Impact Explanation
A repository left in this state loses access to any objects that were only reachable through its (now removed) pool alternate but were not successfully hard-linked (e.g., due to partial hard-link completion before the crash), causing `git fsck` failures and RPC failures for that repository going forward, until an administrator manually restores the backup alternates file referenced in the code comment [6](#0-5) . This is a targeted, per-repository denial of a normal Git hosting operation (fork unlinking), not a cluster-wide compromise.

### Likelihood Explanation
The RPC is reachable through an ordinary, unprivileged "unlink fork from its object pool" workflow, so no elevated privileges are required to reach the code path. However, actually landing in the broken state requires the Gitaly process (or the specific rename/rollback step) to be interrupted at a narrow window, which is not something the caller can force deterministically — this is closer to a crash-window/non-atomicity issue than a fully attacker-controlled trigger, and it is already explicitly acknowledged as a known, accepted risk in the code's own comments and in the RPC's proto documentation.

### Recommendation
Make the disconnect operation crash-safe by performing the alternates swap and connectivity check through the repository's transactional filesystem/journal (as is already done for the object hard-linking step and used elsewhere in the codebase for prepared/committed voting) rather than a bare `os.Rename` + best-effort `os.Link` rollback, so that a crash mid-operation cannot leave the repository without both alternates and complete objects.

### Proof of Concept
Concretely reproducing this requires killing the Gitaly process at the precise instant between the `os.Rename(altFile, backupFile)` call and the deferred rollback in `removeAlternatesIfOk` [7](#0-6)  while `DisconnectGitAlternates` is running against a repository whose pool member has objects not yet fully hard-linked; this is inherently a timing-dependent scenario rather than a fully deterministic exploit, matching the "acknowledged, will resolve"-style risk already called out in the source comments rather than a newly discovered, guaranteed-trigger vulnerability.

```go
// removeAlternatesIfOk is dangerous. We optimistically temporarily
// rename objects/info/alternates, and run `git fsck` to see if the
// resulting repo is connected. If this fails we restore
// objects/info/alternates. If the repo is not connected for whatever
// reason, then until this function returns, probably **all concurrent
// RPC calls to the repo will fail**. Also, if Gitaly crashes in the
// middle of this function, the repo is left in a broken state. We do
// take care to leave a copy of the alternates file, so that it can be
// manually restored by an administrator if needed.
func removeAlternatesIfOk(ctx context.Context, repo *localrepo.Repo, altFile, backupFile string, logger log.Logger, txManager transaction.Manager) error {
	// Acquire distributed lock
	if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("disconnect alternate")), voting.Preparing); err != nil {
		return fmt.Errorf("preparatory vote for disconnecting alternate: %w", err)
	}

	if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("disconnect alternate")), voting.Prepared); err != nil {
		return fmt.Errorf("preparatory vote for disconnecting alternate: %w", err)
	}

	if err := os.Rename(altFile, backupFile); err != nil {
		return err
	}

	rollback := true
	defer func() {
		if !rollback {
			return
		}

		// If we would do a os.Rename, and then someone else comes and clobbers
		// our file, it's gone forever. This trick with os.Link and os.Rename
		// is equivalent to "cp $backupFile $altFile", meaning backupFile is
		// preserved for possible forensic use.
		tmp := backupFile + ".2"

		if err := os.Link(backupFile, tmp); err != nil {
			logger.WithError(err).ErrorContext(ctx, "copy backup alternates file")
			return
		}

		if err := os.Rename(tmp, altFile); err != nil {
			logger.WithError(err).ErrorContext(ctx, "restore backup alternates file")
		}
	}()
```

```go
	// The choice here of git rev-list is for performance reasons.
	// git fsck --connectivity-only performed badly for large
	// repositories. The reasons are detailed in https://lore.kernel.org/git/9304B938-4A59-456B-B091-DBBCAA1823B2@gmail.com/
	cmd, err := repo.Exec(ctx, gitcmd.Command{
		Name: "rev-list",
		Flags: []gitcmd.Option{
			gitcmd.Flag{Name: "--objects"},
			gitcmd.Flag{Name: "--all"},
			gitcmd.Flag{Name: "--quiet"},
		},
	})
	if err != nil {
		return err
	}

	if err := cmd.Wait(); err != nil {
		return &connectivityError{error: err}
	}

	if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("disconnect alternate")), voting.Committed); err != nil {
		return fmt.Errorf("committing vote for disconnecting alternate: %w", err)
	}

	if tx := storage.ExtractTransaction(ctx); tx != nil {
		infoAlternatesRelativePath, err := filepath.Rel(tx.FS().Root(), altFile)
		if err != nil {
			return fmt.Errorf("rel info/alternates: %w", err)
		}

		if err := tx.FS().RecordRemoval(infoAlternatesRelativePath); err != nil {
			return fmt.Errorf("record info/alternates removal: %w", err)
		}
	}

	// The repository should only be disconnected from its object pool if validation is successful.
	// If validation fails or transaction quorum is not achieved, alternates rollback is performed.
	rollback = false
	return nil
}
```

```markdown
Removing a member from an object pool is slightly more involved, as members of
an object pool members will miss objects which are only part of the object pool.
It is thus not as simple as removing `objects/info/alternates`, as that would
leave behind a corrupt repository. Instead, Gitaly hard-links all objects which
are part of the object pool into the dissociating member first and removes the
alternate afterwards. In order to check whether the operation succeeded, Gitaly
now runs `git-fsck(1)` to check for missing objects. If there are none, the
dissociation has succeeded. Otherwise, it will fail and re-add the alternates
file.
```
