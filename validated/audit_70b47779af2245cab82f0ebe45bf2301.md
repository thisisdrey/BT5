### Title
Reference name is not validated for embedded newlines/whitespace before being written into the pre-receive `changes` payload, permitting change-line injection - ([File: internal/gitaly/hook/updateref/update_with_hooks.go])

### Summary
`UpdaterWithHooks.UpdateReference` builds the `changes` string fed to `PreReceiveHook` (and the reference-transaction/post-receive hooks) as `fmt.Sprintf("%s %s %s\n", oldrev, newrev, reference)`, validating only `oldrev`/`newrev` via `objectHash.ValidateHex` but never validating `reference` for embedded whitespace/newlines. Since `reference` for `UserCreateBranch`/`UserMergeBranch`/etc. is built directly from attacker-controlled RPC bytes via `git.NewReferenceNameFromBranchName(string(req.GetBranchName()))`, which is a bare string concatenation with `"refs/heads/"` and performs no validation, an attacker can embed a newline plus a second well-formed `<oldrev> <newrev> <refname>` line inside the branch name and have it appear as an additional, forged change line in the hook stdin.

### Finding Description
- `UserCreateBranch` (and sibling operations RPCs) build the reference name with `git.NewReferenceNameFromBranchName(string(req.GetBranchName()))` [1](#0-0) , and `NewReferenceNameFromBranchName` performs no character validation at all, just string concatenation [2](#0-1) .
- In `UpdateReference`, only `oldrev`/`newrev` are validated (`objectHash.ValidateHex`); `reference` is checked only for emptiness, never for embedded whitespace/newlines equivalent to what `git.ValidateRevision` enforces (`ContainsAny(revision, " \t\n\r")` rejection) [3](#0-2) , compared with the whitespace/newline checks that exist in `git.ValidateRevision` but are never invoked here [4](#0-3) .
- The unsanitized `reference` is interpolated directly into the `changes` string that is streamed as stdin to `PreReceiveHook`, `ReferenceTransactionHook`, and `PostReceiveHook` [5](#0-4) .
- A crafted `BranchName` of the form `"legit-branch\nrefs/heads/protected <oldrev2> <newrev2>"` would render `changes` as two lines: the legitimate line for the actual ref, and a second, fully attacker-controlled line naming an arbitrary reference with arbitrary old/new OIDs. Downstream consumers of the pre-receive stdin (GitLab Rails `/internal/allowed`, custom hooks) that parse stdin line-by-line as `oldrev newrev refname` would interpret this as authorization for a second, forged ref update that was never subject to Gitaly's actual `updater.Update(reference, newrev, oldrev)` call for that second ref (the real `updateref.Updater` transaction only ever updates the original, single `reference` value passed in — see the single `updater.Update(reference, newrev, oldrev)` call) [6](#0-5) .

### Impact Explanation
This could allow an unprivileged user with push/branch-creation access to smuggle a forged reference-update record into the pre-receive hook input for a completely different reference (e.g., a protected branch) that is not the one Gitaly is actually locking/updating via `updateref.Updater`. If GitLab Rails or a custom pre-receive hook uses this stdin to authorize or record changes (e.g., protected branch checks, audit logging, push rule evaluation) on a per-line basis, the forged second line could cause an incorrect authorization decision or an inconsistent audit trail for a reference the attacker does not actually control. Since the real ref write is still gated by the single `updater.Update` call inside Gitaly, the ref database itself would not be corrupted by this alone, but any Rails-side authorization/audit logic that trusts the raw `changes` content per line is undermined — matching a hook/authorization-bypass class issue.

### Likelihood Explanation
Reachable by any unprivileged user calling `UserCreateBranch` (or similar `OperationService` RPCs that construct `ReferenceName` from raw bytes via `NewReferenceNameFromBranchName`) with a `BranchName` containing embedded `\n`. No special role, secret, or non-default configuration is required — only that the specific RPC path does not otherwise reject newlines in the branch/reference name before calling `UpdateReference`. This makes it feasible and repeatable, contingent only on confirming that no earlier validation layer (e.g., request-level branch-name checks) rejects control characters — which was not found in `validateUserCreateBranchRequest` [7](#0-6) .

### Recommendation
Validate `reference` in `UpdateReference` using the same whitespace/newline/NUL checks as `git.ValidateRevision` (or a dedicated `git.ValidateReference`) before formatting it into the `changes` string, rejecting any reference name containing `\n`, `\r`, other whitespace, or NUL bytes. This validation should be applied at the point the `ReferenceName` is first constructed from RPC input (`NewReferenceNameFromBranchName` callers) rather than only deep inside `UpdateReference`, so that all callers are protected consistently.

### Proof of Concept
```go
func TestUpdateReference_RejectsNewlineInReferenceName(t *testing.T) {
	// crafted BranchName containing an embedded newline + forged change line
	maliciousBranch := "legit-branch\nrefs/heads/protected 0000000000000000000000000000000000000000 1111111111111111111111111111111111111111"
	reference := git.NewReferenceNameFromBranchName(maliciousBranch)

	err := updater.UpdateReference(ctx, repoProto, user, nil, reference, newrev, oldrev)
	require.Error(t, err, "reference names with embedded newlines must be rejected")
}
```
Expected: `UpdateReference` should return an error rejecting the malformed reference name before it is ever formatted into the `changes` string; currently no such error is produced, and `changes` would instead contain two lines, the second being a fully attacker-forged `oldrev newrev refname` record for `refs/heads/protected`.
