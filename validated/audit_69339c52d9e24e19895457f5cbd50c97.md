### Title
Deterministic-account-id truncated-hash collision permits front-running (`CREATE2`-style) hijack of pre-funded NEP-616 deterministic accounts — (File: `runtime/runtime/src/action_validation.rs`)

### Summary
NEAR's NEP-616 "deterministic accounts" (`0s...` account IDs) derive their address from `keccak256(borsh(DeterministicAccountStateInit))[12..32]`, truncated to 160 bits, exactly like Ethereum/`CREATE2` addresses. Because the pre-image space (`code` + arbitrary `data: BTreeMap<Vec<u8>, Vec<u8>>`) is fully attacker-controllable, and because the protocol explicitly supports funding a deterministic account *before* it is initialized, an attacker can perform the same meet-in-the-middle birthday search described in the Panoptic/`CREATE2` report (≈2^80 work) to find a colliding `state_init` whose derived id matches a legitimate, pre-funded "pool"-like deterministic account, then front-run its initialization with attacker-controlled code.

### Finding Description
The deterministic account id is computed purely as a truncated hash of borsh-encoded state: [1](#0-0) 

Validation of a `DeterministicStateInitAction` only checks that the *supplied* `state_init` hashes to the receiver id — it never checks that the `code`/`data` match any expected/canonical value for that address: [2](#0-1) 

Execution then deploys the contract only if none is set yet — a strict "first writer wins" race, with no re-validation against the "intended" deployer's state_init: [3](#0-2) 

Critically, the protocol explicitly documents and tests that a deterministic account can be **pre-funded via `Transfer` before its `DeterministicStateInitAction` is submitted** — the exact "undeployed pool with pending deposits" pattern from the `CREATE2` report: [4](#0-3) [5](#0-4) 

Because `data` values can be up to 4 MiB and the map is arbitrary, an attacker has an enormous, freely searchable pre-image space to mount a birthday (meet-in-the-middle) search against the 160-bit truncated address space: one branch enumerates candidate legitimate-looking `state_init`s (known `code` = a target protocol's global contract, varying plausible `data`), and the other branch enumerates attacker `state_init`s (attacker's own malicious global contract code + arbitrary `data`), looking for any collision in the shared 160-bit `0s...` address space — the same complexity class (~2^80) as the original `CREATE2`/EIP-3607-class attack.

### Impact Explanation
If an attacker finds such a collision and submits `DeterministicStateInitAction` with their malicious `state_init` before the legitimate deployer does, `action_deterministic_state_init` will install the attacker's global-contract code on that account id (since `account.contract().is_none()` is true). Any subsequent transfers intended to fund/initialize the "real" pool-like deterministic account — as well as the legitimate deployer's own later `DeterministicStateInitAction` (which will simply skip the deploy step and just top up the balance, per the `if account.contract().is_none()` gate) — end up controlled by the attacker's contract. This is concrete theft: the attacker's code can transfer out all NEAR balance and any tokens/state the account accumulates, or delete the account with itself as `beneficiary_id`.

### Likelihood Explanation
This requires an actual keccak256 birthday collision over the 160-bit truncated output — computationally expensive (comparable to the ~2^80 estimate the original report also relies on) but the same class of attack already accepted as Medium severity precedent in the cited report and its predecessors (Arcadia, Kyberswap). It further requires that some protocol pre-publish/pre-fund a deterministic account before submitting its own `DeterministicStateInitAction` — a pattern the NEAR docs and test suite explicitly support and encourage (`test_deterministic_state_init_prepay_for_storage`), making the precondition realistic rather than hypothetical.

### Recommendation
- Do not allow arbitrary, attacker-influenceable `data` to factor into the address derivation for accounts intended to hold third-party funds pre-initialization; or
- Widen the derived id beyond 160 bits (e.g., use the full 256-bit `keccak256`/`sha3-256` output as with the `0u` Universal Account ID scheme) to push the birthday-collision cost back to full security, and/or
- Require that any pre-funding of a not-yet-initialized deterministic account be non-transferable/refundable until initialization is confirmed and, if possible, bind the pre-funding transfer to the specific intended `state_init` hash rather than only to the derived account id.

### Proof of Concept
1. Attacker deploys their own malicious `GlobalContract` (e.g., via `DeployGlobalContractAction`) with logic that lets them drain any NEAR balance sent to accounts running it.
2. Attacker performs an offline birthday search: for many candidate "legitimate-looking" `DeterministicAccountStateInitV1 { code: <target protocol's known global contract>, data: <varied plausible params> }` and many `DeterministicAccountStateInitV1 { code: <attacker's malicious global contract>, data: <arbitrary> }`, compute `derive_near_deterministic_account_id` (per `core/primitives/src/utils.rs:495-503`) and look for a collision between the two sets (~2^80 work due to 160-bit truncation).
3. Once a colliding pair (`state_init_legit`, `state_init_attacker`) sharing account id `X` is found, the attacker waits for/encourages users or the protocol to send `Transfer`s to `X` (a supported pre-funding pattern, `docs/DataStructures/Account.md:180-186`).
4. Attacker submits `Action::DeterministicStateInit(state_init_attacker)` targeting `X`; `validate_deterministic_state_init` (`runtime/runtime/src/action_validation.rs:435-471`) accepts it because `derive(state_init_attacker) == X`. `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:15-52`) deploys the attacker's contract since `account.contract().is_none()`.
5. All prior/subsequent balance sent to `X` (and any later legitimate `DeterministicStateInitAction` for `state_init_legit`, which only tops up balance since the contract slot is already filled) is now controlled by the attacker's contract, which can transfer the funds out.

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}

fn validate_deterministic_state_init(
    limit_config: &LimitConfig,
    action: &DeterministicStateInitAction,
    receiver_id: &AccountId,
) -> Result<(), ActionsValidationError> {
    validate_global_contract_identifier(action.state_init.code())?;

    let derived_id = derive_near_deterministic_account_id(&action.state_init);

    if derived_id != *receiver_id {
        return Err(ActionsValidationError::InvalidDeterministicStateInitReceiver {
            derived_id,
            receiver_id: receiver_id.clone(),
        });
    }

    // State init entries must not violate limits of individual state keys and values.
    for (key, value) in action.state_init.data() {
        if key.len() as u64 > limit_config.max_length_storage_key {
            return Err(ActionsValidationError::DeterministicStateInitKeyLengthExceeded {
                length: key.len() as u64,
                limit: limit_config.max_length_storage_key,
            }
            .into());
        }

        if value.len() as u64 > limit_config.max_length_storage_value {
            return Err(ActionsValidationError::DeterministicStateInitValueLengthExceeded {
                length: value.len() as u64,
                limit: limit_config.max_length_storage_value,
            }
            .into());
        }
    }

    Ok(())
}

pub(crate) fn action_deterministic_state_init(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    maybe_account: &mut Option<Account>,
    account_id: &AccountId,
    receipt: &Receipt,
    action: &DeterministicStateInitAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // See https://github.com/near/NEPs/blob/master/neps/nep-0616.md#account-state
    // for the detailed description around deterministic account state.
    let storage_usage_config = &apply_state.config.fees.storage_usage_config;
    let account = match maybe_account {
        Some(account) => account,
        None => {
            // cspell:ignore nonexist
            // `nonexist` -> `uninit` account state transition
            // Create with zero balance now and check later how much of the
            // provided deposit is needed.
            let new_account = create_deterministic_account(Balance::ZERO, storage_usage_config);
            maybe_account.insert(new_account)
        }
    };
    if account.contract().is_none() {
        // `uninit` -> `active` account state transition. "uninit" here is the
        // NEP-616 sense, a deterministic account with no contract yet, not
        // `Account::Uninitialized`: a `0u` id can never reach this, because
        // `validate_deterministic_state_init` pins the receiver to the derived
        // `0s` id.
        deploy_deterministic_account(
            state_update,
            account,
            account_id,
            &action.state_init,
            result,
            storage_usage_config,
        )?;
    }

### Deterministic account creation

Deterministic accounts cannot be created with a `CreateAccount` nor with a `Transfer` action.
A special action, `DeterministicStateInitAction`, is required.
This action validates that the account id matches its initial state.

As with all account types, you have to attach a large enough deposit to cover for the account storage. If the code and
initial state is small enough to fit below the zero-balance limit, no balance is required. The
`DeterministicStateInitAction` has a field to include a balance specifically to cover storage. Anything above the
required amount to cover storage requirements is refunded.

A `Transfer` can also deposit a balance before the `DeterministicStateInitAction`. The account will not be usable,
however, until the `DeterministicStateInitAction` is also executed.

/// Ensure we can pre-pay the balance for a deterministic account.
///
/// It is a required feature that one can send a Transfer to a non-existing
/// deterministic account first and later initialize it without adding balance,
/// even if more storage than the ZBA limit is used.
#[test]
fn test_deterministic_state_init_prepay_for_storage() {
    let mut env = TestEnv::setup(Balance::from_near(100));
    env.deploy_global_contract(GlobalContractDeployMode::AccountId);

    let data = BTreeMap::from_iter([(b"key".to_vec(), vec![0u8; 100_000])]);
    let (state_init, det_account) = env.new_deterministic_account_with_data(data.clone());

    // Try once without pre-paying, must fail.
    let outcome = env
        .try_deploy_deterministic_account_with_data(data.clone(), Balance::ZERO)
        .expect("should be able to send transaction");
    assert_matches!(
        outcome.status,
        FinalExecutionStatus::Failure(TxExecutionError::ActionError(ActionError {
            kind: ActionErrorKind::LackBalanceForState { .. },
            index: _
        }))
    );

    // Prepay
    let required_for_storage = env.balance_for_storage(state_init);
    env.fund_with_near_balance(det_account.clone(), required_for_storage);
    assert_eq!(
        required_for_storage,
        env.get_account_state(det_account.clone()).amount,
        "account should have been created and funded now"
    );

    // Contract can't be called, yet.
    env.assert_test_contract_not_usable_on_account(det_account.clone());

    // Try creating again, with zero balance again. Must succeed this time.
    env.try_deploy_deterministic_account_with_data(data, Balance::ZERO)
        .expect("should be able to send transaction")
        .assert_success();
    env.assert_test_contract_usable_on_account(det_account);
}
