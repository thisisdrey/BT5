## Finding

The java-tron `ExchangeTransactionContract` has an `expected` field intended as slippage protection (minimum output amount), analogous in spirit to the `amount purchased` assumption in the reported Sherlock issue. In both cases, code assumes a "safety check" is in place to guarantee a minimum/expected outcome, but the actual enforcement is missing, so execution silently continues on an unfavorable outcome.

### Title
Missing slippage/minimum-output enforcement of the `expected` field in `ExchangeTransactionActuator` allows exchange trades to complete with less output than the caller specified - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
`ExchangeTransactionContract` carries a `expected` (`tokenExpected`) field which callers set as the minimum amount of the other token they expect to receive from the AMM-style bonding-curve exchange. `doValidate()` only checks that `tokenExpected > 0` [1](#0-0)  — it never compares the actual computed output (`anotherTokenQuant`) against `tokenExpected`, either in `doValidate()` or in `execute()` [2](#0-1) . A grep across the whole repository confirms `tokenExpected`/`getExpected()` is referenced only for the `>0` check and nowhere else in production code, meaning the field provides no real protection.

### Finding Description
In `execute()`, the actual amount received (`anotherTokenQuant`) is computed by `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` [3](#0-2) , using the current pool reserves at execution time via `ExchangeCapsule.transaction` / `ExchangeProcessor.exchange` [4](#0-3) . This price depends on the pool state at the moment the block is produced, which can shift due to other transactions (front-running/sandwiching, or natural pool drift) between when the caller submits the transaction and when it executes. The `expected` parameter exists precisely to prevent execution when the actual output falls below the caller's tolerance — the same logical role as the DAI-balance-delta check in the reported bug. However, unlike the reported bug (where an underflow/zero-delta silently "succeeds" due to incorrect assumption about revert), here the enforcement code is simply absent: the value is parsed, validated for positivity, and then discarded, so the transaction always succeeds regardless of how far short the output falls of `expected`.

### Impact Explanation
Any account can submit an `ExchangeTransactionContract` believing the `expected` value protects them from unfavorable trades. Because it's not enforced, a malicious actor observing the mempool can front-run the trade (e.g., via another Exchange transaction against the same pool) to shift the bonding-curve price unfavorably, then let the victim's trade execute for materially less output than intended — a direct value-loss/theft vector for TRC10 asset holders trading through java-tron's built-in Bancor-style exchange, reachable by an ordinary unprivileged transaction sender.

### Likelihood Explanation
High: exploiting this requires only submitting two ordinary signed transactions (a manipulating trade plus the victim's trade), it needs no special privilege, and the exchange feature is a core public feature (`ExchangeTransactionContract`) reachable by any account holding assets in an exchange pool. `ExchangeStore`/`ExchangeV2Store` pools are commonly small enough that a sizable manipulation trade is cheap to execute.

### Recommendation
In `ExchangeTransactionActuator.execute()`, after computing `anotherTokenQuant`, compare it against `exchangeTransactionContract.getExpected()` and throw a `ContractExeException`/fail the transaction if `anotherTokenQuant < tokenExpected`, mirroring the intended slippage-protection semantics of the field.

### Proof of Concept
1. Pool P holds tokenA/tokenB reserves R_a, R_b.
2. Victim submits `ExchangeTransactionContract{tokenId=tokenA, quant=Q, expected=E}` expecting to receive at least `E` of tokenB, computed off the current reserves.
3. Attacker submits a large `ExchangeTransactionContract` against the same pool just before the victim's transaction is packed/executed, shifting R_a/R_b so that the bonding-curve output for the victim's trade with quant `Q` now yields `anotherTokenQuant < E`.
4. `doValidate()` only checks `tokenExpected > 0` [1](#0-0) , so validation still passes.
5. `execute()` computes `anotherTokenQuant` from the now-shifted reserves and credits the victim that (lower) amount without ever comparing it to `E` [5](#0-4) , so the transaction reports `code.SUCESS` despite failing the caller's stated minimum-output requirement.
