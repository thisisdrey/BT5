### Title
Self-declared, unverified resource fields let unprivileged senders forge transaction "priority" for QoS decisions in forwarding/scheduling - (File: `core/src/forwarding_stage.rs`, `core/src/transaction_priority.rs`)

### Summary
The Sherlock report's root cause is generic: a protection bound (`amountOutMinimum`) is derived from state (`slot0()`) that is itself trivially manipulable by the same actor the check is supposed to protect against, so the guard always passes regardless of manipulation. The closest reachable analog in Agave is `calculate_priority()` in `core/src/forwarding_stage.rs` and its sibling `calculate_priority_and_cost()` in `core/src/transaction_priority.rs`, which compute a QoS-relevant "priority" score using `TransactionConfiguration`/`compute_unit_limit`/`num_requested_write_locks()` fields that are fully attacker-declared inside the (unsigned-field but user-controlled) `ComputeBudgetInstruction`s of the transaction itself, not verified against actual execution cost.

### Finding Description
`calculate_priority` in `core/src/forwarding_stage.rs` computes: [1](#0-0) 

`P = R / (1 + C)`, where `C` comes from `CostModel::estimate_cost(...)`, and that estimate is derived from `transaction.transaction_configuration(&bank.feature_set)` (i.e. the sender's own `set_compute_unit_limit` instruction) and `transaction.num_requested_write_locks()` — both values fully controlled by the unprivileged transaction sender: [2](#0-1) 

The same self-declared-value pattern feeds `calculate_priority_and_cost` used in the banking-stage scheduler path: [3](#0-2) 

This priority value directly determines standing in the bounded `PacketContainer` min-max heap that backs the forwarding queue — the heap evicts the lowest-priority entry when full: [4](#0-3) 

Because `cost` is computed from the requester's own declared `compute_unit_limit` rather than from any independently verified quantity, an attacker can declare an artificially small `compute_unit_limit` (down to the practical minimum) while still packing many/expensive instructions into the transaction. This deflates `C`, inflating `P = R/(1+C)` — the transaction ranks as extremely high priority in the forwarding queue's `MinMaxHeap`, potentially evicting legitimately higher-paying transactions from other users, even though during actual execution in banking stage the transaction would consume real CU or fail with `ComputationalBudgetExceeded`. This is structurally identical to the reported bug class: a QoS/economic gate is computed from a value that the very same untrusted party fully controls at the moment of the check, so the gate provides no real protection against the abuse it is meant to prevent.

### Impact Explanation
This is a QoS-evasion vector reachable by any unprivileged/unstaked user submitting normal transactions over the existing transaction ingestion path (no special validator/operator role required). It allows a sender to game the forwarding-stage priority queue's admission/eviction policy using self-declared, execution-unverified data, displacing legitimate higher-fee transactions from the bounded queue purely by lying about resource usage. This falls under "QoS evasion," one of the explicitly accepted impact categories.

### Likelihood Explanation
Likelihood is moderate-to-high: crafting a transaction with a low `set_compute_unit_limit` value combined with instructions that don't actually need much CU (or that are expected to fail cheaply) requires no special privileges, stake, or timing — it only requires understanding the priority formula, which is documented in code comments. The main limiting factor is that this affects the *forwarding queue* ranking, not final block inclusion economics (the banking stage's actual cost tracker uses executed/committed costs), so the real damage is queue displacement/DoS-style unfairness in forwarding rather than a state-corruption bug.

### Recommendation
Do not derive forwarding/scheduling priority solely from unverified, sender-declared fields (`compute_unit_limit`, requested write-lock count) without any floor/clamp tied to actual instruction complexity. Consider incorporating a minimum-cost floor based on the actual instruction set (e.g., number and type of instructions, accounts touched) independent of the user-supplied `compute_unit_limit`, or bound the achievable priority inflation by clamping `compute_unit_limit` to a sane minimum relative to the instructions present, analogous to the report's recommendation to avoid relying purely on a spot, attacker-influenced value and instead use a more robust/verified reference.

### Proof of Concept
Conceptual PoC (not run, since this is a design/code-review-level analog, not an executed exploit against a live cluster):
1. Construct a transaction with several instructions but include `ComputeBudgetInstruction::set_compute_unit_limit(1)` (minimum permissible), while `num_requested_write_locks()` is also kept minimal.
2. Attach a non-trivial `compute_unit_price` to inflate `R` (the reward) while `C` (estimated cost from `CostModel::estimate_cost`) stays artificially near zero due to the declared `compute_unit_limit`, per `core/src/forwarding_stage.rs:622-627` and `cost-model/src/cost_model.rs:158-178`.
3. Submit many such transactions to fill/evict entries in the `PacketContainer` `MinMaxHeap` (`core/src/forwarding_stage/packet_container.rs:15-33`), pushing out legitimately higher-paying transactions from the bounded forwarding queue.
4. Because the transaction's true resource use is not verified until actual execution in the banking stage, the QoS gate at the forwarding-stage layer is defeated using only self-declared data.

I was not able to fully verify end-to-end runtime behavior (e.g., exact capacity of the forwarding queue in production, or whether any additional pre-filters upstream of `calculate_priority` mitigate this) since this required tracing live cluster behavior beyond what static code search can confirm; this should be validated empirically if pursued further.

```rust
fn calculate_priority(
    transaction: &RuntimeTransaction<SanitizedTransactionView<&[u8]>>,
    bank: &Bank,
) -> Option<u64> {
    let transaction_configuration = transaction
        .transaction_configuration(&bank.feature_set)
        .ok()?;

    // Manually estimate fee here since currently interface doesn't allow a on SVM type.
    // Doesn't need to be 100% accurate so long as close and consistent.
    let prioritization_fee = transaction_configuration.priority_fee_lamports;
    let signature_details = transaction.signature_details();
    let signature_fee = signature_details
        .total_signatures()
        .saturating_mul(bank.fee_structure().lamports_per_signature);
    let fee_details = FeeDetails::new(signature_fee, prioritization_fee);

    let reward = bank
        .calculate_reward_and_burn_fee_details(&CollectorFeeDetails::from(fee_details))
        .get_deposit();

    let cost = CostModel::estimate_cost(
        transaction,
        transaction.program_instructions_iter(),
        transaction.num_requested_write_locks(),
        &bank.feature_set,
    );
```

```rust
    /// Return (programs_execution_cost, loaded_accounts_data_size_cost)
    fn get_estimated_execution_cost(
        transaction: &impl TransactionMeta,
        feature_set: &FeatureSet,
    ) -> (u64, u64) {
        // if failed to process compute_budget instructions, the transaction will not be executed
        // by `bank`, therefore it should be considered as no execution cost by cost model.
        let (programs_execution_costs, loaded_accounts_data_size_cost) =
            match transaction.transaction_configuration(feature_set) {
                Ok(config) => (
                    u64::from(config.compute_unit_limit),
                    Self::calculate_loaded_accounts_data_size_cost(
                        config.loaded_accounts_data_size_limit,
                        feature_set,
                    ),
                ),
                Err(_) => (0, 0),
            };

        (programs_execution_costs, loaded_accounts_data_size_cost)
    }
```
