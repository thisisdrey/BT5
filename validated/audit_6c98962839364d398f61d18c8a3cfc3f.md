### Title
`write_freq` StackerDB write-rate cap is never enforced on chunk acceptance, letting a signer spam unlimited high-rate writes to a slot — (File: stackslib/src/net/stackerdb/db.rs)

### Summary
Each StackerDB replica config declares a `write-freq` value that is supposed to bound how often a slot may be updated (a documented, cooldown-style limit analogous to the sNote 50%-per-call cap). The function that actually accepts and stores a chunk, `StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, never checks `write_freq`/`write_time` at all — it only checks chunk size, slot existence, signature, staleness (`slot_version <= latest`), and the lifetime `max_writes` ceiling. A remote, authenticated slot owner can therefore push a new, validly-signed chunk as fast as the network allows, bypassing the intended write-frequency throttle entirely, simply by calling the write path (`POST /v2/stackerdb/.../chunks` handled by `RPCPostStackerDBChunkRequestHandler`, or the P2P `StackerDBPushChunk` path) repeatedly.

### Finding Description
`StackerDBConfig` carries a `write_freq: u64` field described as "minimum wall-clock time between writes to the same slot" [1](#0-0) , and there is even a dedicated error variant `Error::TooFrequentSlotWrites(u64)` defined for this purpose [2](#0-1) .

However, the actual write-acceptance function, `try_replace_chunk`, only enforces: chunk-size cap, slot existence, signer verification, staleness (`slot_version <= slot_validation.version`), and the lifetime `max_writes` bound — there is no comparison of `get_epoch_time_secs()` against `slot_validation.write_time + config.write_freq` anywhere in this function: [3](#0-2) 

The underlying `insert_chunk` helper likewise just records the current time as `write_time` without ever gating on it: it blindly executes an `UPDATE` setting `write_time = now`, with a comment explicitly stating "It must be authenticated, and its lamport clock must be higher... These will not be checked [here]" (i.e., the frequency/rate is assumed to be checked by the caller, but the caller — `try_replace_chunk` — never does it): [4](#0-3) 

The `SlotValidation` struct that `try_replace_chunk` reads even carries a `write_time` field that would be needed for such a check, but it is fetched and then discarded without ever being compared to `config.write_freq`: [5](#0-4) [6](#0-5) 

This is the same write path used by the unauthenticated-write-prevention logic on the remote-facing HTTP endpoint, `poststackerdbchunk.rs`, which calls `tx.try_replace_chunk(...)` directly and only classifies errors it actually receives (`StaleChunk`, `NoSuchSlot`, `BadSigner`, `ChunkTooBig`, `TooManySlotWrites`) — there is no `TooFrequentSlotWrites` case ever produced because `try_replace_chunk` never returns it: [7](#0-6) 

The parallel read-side validator, `validate_received_chunk` (used when *fetching* chunks from peers during sync), explicitly documents that it "does not check write frequency, since the caller has different ways of doing this" — but no other caller in `try_replace_chunk`'s path performs that check either: [8](#0-7) [9](#0-8) 

This mirrors the sNote bug class precisely: a rate/quantity cap that is supposed to bound repeated invocations of a state-changing operation (there: 50% BPT per call; here: one write per `write_freq` interval) is only checked at the "per-call" level (max lifetime version count) and never against elapsed time since the last write, so an attacker who repeatedly calls the same function defeats the intended throttle just by calling it faster.

### Impact Explanation
StackerDB write-frequency limits exist to bound how fast a slot's contents can churn, which downstream consumers (miners/signers reading signer messages, block proposals, etc.) rely on for predictable propagation/inventory behavior and to bound the amplification of gossip relay (`StackerDBPushChunk` messages get relayed to other peers). Because `write_freq` is not enforced in `try_replace_chunk`, any principal who legitimately owns a slot (has valid signing keys for that slot per the DB's `signers` list) can write to that slot at the network's raw request rate, subject only to the (separate, and much coarser) `max_writes` lifetime ceiling and to generic bandwidth throttling (`max_stackerdb_push_bandwidth`) which only NACKs, and does not stop, an attacker from making the DB inconsistent with its documented protocol assumptions. This is a High-severity issue under the report's rubric — the cap is a control on state written and propagated (bounded compute/DoS-like amplification on a write endpoint and via gossip relay), not merely a bandwidth cap.

### Likelihood Explanation
Any party who is a configured signer for a StackerDB slot (an ordinary, unprivileged, remote participant in the protocol — not an admin) can trigger this by simply issuing repeated valid `POST .../chunks` requests (or P2P chunk pushes) with incrementing `slot_version`. No special access or secret beyond a normal signer's own key is required, and the flaw is a straightforward missing-check rather than a subtle race, so likelihood is high.

### Recommendation
In `try_replace_chunk` (`stackslib/src/net/stackerdb/db.rs`), before calling `insert_chunk`, compare `get_epoch_time_secs()` against `slot_validation.write_time + self.config.write_freq` and return `net_error::TooFrequentSlotWrites(deadline)` (the variant that already exists but is unused) if the write is too soon, mirroring the existing `TooManySlotWrites` check. Propagate this new error case through `poststackerdbchunk.rs`'s error classification (`StackerDBErrorCodes`) so clients get a proper ack/NACK rather than the write silently succeeding.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u30` (i.e., writes to the same slot should be at least 30 seconds apart) and `max-writes: u4096`.
2. As the owner of slot `N`, sign and `POST` a chunk with `slot_version = 1`; it is accepted (per `try_replace_chunk`'s checks: size OK, slot exists, signature OK, `1 > 0` not stale, `1 <= max_writes`).
3. Immediately (same second) sign and `POST` a new chunk with `slot_version = 2`; because there is no `write_freq`/`write_time` comparison in `try_replace_chunk`, this second write is also accepted immediately, violating the documented minimum 30-second interval.
4. Repeat rapidly up to `max_writes` times — all writes succeed at the caller's chosen rate, up to whatever external bandwidth NACK threshold exists, fully defeating the `write_freq` guarantee that other participants (and the sync protocol's inventory/version expectations) rely on.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
