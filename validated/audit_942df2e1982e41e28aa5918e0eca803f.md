### Title
Exchange pair balance reaching zero permanently locks the remaining side's funds with no recovery path - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The reported bug describes a bridge whose emergency-exit function is guarded by a state check (`getDeadStatus()`/unset `exitAdministrator`) that, once a certain precondition is unmet, permanently and unconditionally blocks the only recovery path, leaving user funds irretrievably stuck with no way to change that precondition afterward. Java-tron's TRC10 Bancor-style exchange market has the same structural pattern: `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, and `ExchangeTransactionActuator` all guard on the exchange pair's token balances, and once either side of the pair reaches exactly zero, every recovery function (`withdraw`, `inject`, `transaction`) unconditionally reverts forever, with no privileged or unprivileged path to unstick the remaining balance.

### Finding Description
All three actuators that touch an `ExchangeCapsule` pair share this identical guard: [1](#0-0) [2](#0-1) [3](#0-2) 

Once `firstTokenBalance == 0 || secondTokenBalance == 0` for an exchange pair, every one of `withdraw`, `inject`, and `transaction` throws `ContractValidateException("... the exchange has been closed")` unconditionally, exactly analogous to the report's `require(getDeadStatus(), "Bridge is not dead")` gate that can never be satisfied once the precondition is broken. There is no owner/admin override, no reset mechanism, and no alternate path in the codebase that can restore a zero balance or force a withdrawal once this state is reached — the remaining, non-zero side of the pair (which may still hold real value contributed by the exchange creator or other participants) becomes permanently frozen in the `ExchangeStore`/`ExchangeV2Store` capsule.

This zero-balance state is reachable through fully unprivileged, ordinary actuator calls: an exchange creator withdrawing the entirety of one token side via `ExchangeWithdrawActuator.execute()` (`actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java:77-89`) sets that side's balance to exactly zero, and validation for that specific withdraw request does not have a check against draining it to zero. Immediately afterward, the *other*, still-nonzero side becomes permanently unwithdrawable and uninjectable, since the pair-wide `firstTokenBalance == 0 || secondTokenBalance == 0` guard trips on the very next operation.

### Impact Explanation
Any funds locked into an exchange pair (TRC10 tokens or TRX) can become permanently unrecoverable once one side of the pair is driven to zero — matching the report's "unbacked/stuck value" impact class. This affects the exchange creator's own remaining assets and, in multi-participant scenarios, any other funds still tracked in that pair's balances, with no code path in `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, or `ExchangeTransactionActuator` capable of reversing the zero-balance state.

### Likelihood Explanation
Reaching the zero-balance state requires only a single unprivileged transaction — e.g., the exchange creator withdrawing 100% of one side via `ExchangeWithdrawActuator`, which is a normal, permitted operation with no floor/minimum-balance validation preventing it. This is a legacy but still-live actuator/contract type (`ExchangeWithdrawContract`, `ExchangeInjectContract`, `ExchangeTransactionContract`) reachable by any account holding assets in the exchange, without any SR/committee/witness privilege.

### Recommendation
Add a minimum-remaining-balance check (or a full-drain-to-zero prohibition) in `ExchangeWithdrawActuator.doValidate()` so that a withdrawal cannot reduce either side of the pair to exactly zero while the other side still holds a nonzero balance, or alternatively allow a full-drain that also automatically returns/frees the paired-side balance to its rightful owner(s) rather than leaving it stuck behind the same guard used for normal operation.

### Proof of Concept
1. Exchange creator Alice creates a pair with `firstTokenBalance = X`, `secondTokenBalance = Y` (Y > 0).
2. Alice calls `ExchangeWithdrawActuator` requesting `tokenQuant == firstTokenBalance` (the entire first-token balance). `doValidate()` at [4](#0-3)  only requires `firstTokenBalance >= tokenQuant`, so a full drain passes validation, and `execute()` sets `firstTokenBalance = 0` per [5](#0-4) .
3. Alice (or anyone) now attempts to withdraw/inject/trade the remaining `secondTokenBalance = Y`. Every subsequent call to `ExchangeWithdrawActuator`, `ExchangeInjectActuator`, or `ExchangeTransactionActuator` hits the `firstTokenBalance == 0` branch and reverts with "the exchange has been closed" permanently, leaving `Y` stuck in the `ExchangeCapsule` forever.
