### Title
Bank state committed but PoH record permanently dropped during Fast Leader Handover ParentReady wait, causing bank/PoH divergence - ([File: core/src/block_creation_loop.rs])

### Summary
During Fast Leader Handover (FLH), `record_and_complete_block` shuts down and drains the record channel while waiting for `ParentReady`, buffering already-committed transaction records into `accumulated_txs`. If `ParentReady` then confirms the optimistic parent was correct (the "happy path" in `handle_parent_ready`), these buffered records are silently dropped instead of being re-recorded into PoH or the bank being reset, leaving bank state that reflects transactions with no corresponding PoH entry.

### Finding Description
In `core/src/block_creation_loop.rs`, when `block_time_left` reaches zero while `optimistic_parent.is_some()` (FLH still awaiting `ParentReady`), the loop calls `shutdown_and_drain_record_receiver(&ctx.poh_recorder, &mut ctx.record_receiver, Some(&mut accumulated_txs))` [1](#0-0) . This pulls already-queued `Record`s out of the bounded record channel into `accumulated_txs` instead of calling `PohRecorder::record()` on them.

Critically, in `core/src/banking_stage/consumer.rs`, a transaction is committed to bank state (`self.committer.commit_transactions(...)`) as soon as `self.transaction_recorder.record_transactions(...)` returns `Ok`, i.e. as soon as the record is *successfully enqueued* in the bounded channel via `RecordSender::try_send` — this happens independently of whether the BlockCreationLoop thread has yet called `poh_recorder.record()` on that queued entry [2](#0-1) . The channel design explicitly documents that "once sent records can be guaranteed to be recorded" [3](#0-2) , i.e. bank-committed transactions must eventually reach PoH.

When `ParentReady` arrives and matches the optimistic parent, `handle_parent_ready` takes the "happy path": it receives `accumulated_txs` (moved in via `std::mem::take`) but returns `Ok(None)` immediately without ever re-recording those transactions into PoH, without rescheduling them to banking stage, and without clearing/resetting the working bank: [4](#0-3) 

Because the parent matched, the working bank is never cleared (`clear_bank`/`abort_working_bank` are only invoked on the sad path further down in the same function) [5](#0-4) , so the bank retains the already-committed effects of the dropped transactions. `process_parent_ready` only resets `records_shutdown` to `false` when `handle_parent_ready` returns `Some(new_bank)` (the sad path), so on the happy path recording stays shut down and `accumulated_txs` is simply dropped when the `Vec` goes out of scope [6](#0-5) . The outer loop then proceeds directly to the block-timeout completion path (`block_time_left.is_zero()` and `optimistic_parent.is_none()`), producing the block footer and tick over a bank whose account/cost state includes transactions with no matching PoH entry [7](#0-6) .

An unprivileged remote client can trigger this by simply sending a steady burst of ordinary, validly-signed transactions to the current leader's TPU during the window in which that leader is running an optimistic/fast leader handover and is waiting on `ParentReady` — i.e., timing packet submission so some transactions are recorded (and thus committed by banking stage) just before `block_timeout` elapses while `ParentReady` for the matching parent is still in flight. No staked/leader/gossip control is required; only ordinary TPU transaction submission timed against publicly observable leader-window/slot timing.

### Impact Explanation
This produces an invalid recorded block: the leader's own bank state (and resulting `bank_hash`) reflects execution of transactions that have no corresponding PoH entry in the block that gets shredded and broadcast. Replaying validators, which only reconstruct bank state from PoH entries, will diverge from the leader's bank hash for a block that the leader nonetheless completes and broadcasts with a footer — a bank-state-vs-PoH invariant violation matching the "invalid recorded block" / consensus-safety bounty category, potentially causing a fork/duplicate-block condition originating from the leader's own block production.

### Likelihood Explanation
The trigger conditions (FLH active, `ParentReady` arriving after `block_timeout`, but ultimately matching the optimistic parent) are a normal part of Alpenglow leader-window handling and are not rare; the only attacker-controlled element is ensuring transactions are being recorded right up to the `block_timeout` boundary during that FLH wait window, which requires nothing more than continuous transaction submission to the TPU — no staking, no privileged access, and it is repeatable by any client that can observe slot/leader timing.

### Recommendation
In the happy path of `handle_parent_ready` (`leader_window_info.parent_block == optimistic_parent_block`), re-record any buffered `accumulated_txs` into PoH via `ctx.poh_recorder.write().unwrap().record(...)` (restoring `records_shutdown = false` and resuming intake) before returning, or roll back the corresponding bank state for those transactions if they cannot be re-recorded, ensuring bank state and PoH content never diverge for transactions currently attributed to the working bank.

### Proof of Concept
Integration test plan for `core/src/block_creation_loop.rs`:
1. Construct a `LeaderContext` with FLH engaged (`fast_leader_handover = true`, `optimistic_parent = Some(parent_block)`), a real `record_channels` pair, and a bank with a short `block_timeout`.
2. Drive `record_and_complete_block` and inject via the mock `record_sender` several `Record`s (simulating banking stage having already committed matching transactions to the working bank, e.g. via `bank.load_and_execute_transactions` + `commit_transactions` as in `test_bank_process_and_record_transactions`) timed so at least one `Record` is enqueued right as `block_timer` reaches `block_timeout`.
3. Send a `LeaderWindowInfo` on `leader_window_info_receiver` whose `parent_block` equals `optimistic_parent_block` (happy path) after the shutdown-and-drain has already pulled records into `accumulated_txs`.
4. Assert: for every transaction whose effects are visible in `bank.get_balance`/account state (i.e., was committed), that same transaction's bytes/hash appear in an entry produced via `PohRecorder::record` (inspect `working_bank_sender` / blockstore entries) — expect this assertion to FAIL, demonstrating transactions committed to the bank with no corresponding PoH entry.
5. As a stronger invariant test, assert `bank.hash()` (or entry mixin count) is inconsistent with the recorded entry count once the footer/tick is produced by `record_and_complete_block`, showing the divergence a replaying validator would also observe.
