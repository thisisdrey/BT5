### Title
Unhandled exception in `ValidateMultiSign` precompile from unvalidated signature-array length field crashes contract execution outside its exception guard - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The gvfs CVE describes a case where a length value taken from untrusted input is used to drive a buffer read/copy without being validated against the actual allocated/expected size, causing an out-of-bounds access. The closest reachable analog in java-tron is in `ValidateMultiSign.execute()` [1](#0-0) , a TVM precompile invoked by any contract call via `STATICCALL`/`CALL` to address `0x0a`, reachable from a single unprivileged transaction.

### Finding Description
`ValidateMultiSign.execute()` reads array-length and offset fields directly from attacker-controlled `DataWord[]` derived from calldata, then calls `extractBytesArray`/`extractSigArray` to slice `rawData` using those unvalidated offsets/lengths [2](#0-1) . Before the TIP-854 ABI-encoding guard (`isValidAbiEncoding`, gated by `VMConfig.allowTvmOsaka()`) is active, and when `VMConfig.allowTvmSelfdestructRestriction()` is off (the `extractBytesArray` branch, no `MAX_SIZE` pre-check), a crafted `len`, `bytesOffset`, or `bytesLen` can drive `Arrays.copyOfRange(data, offset, offset + len)` to throw `ArrayIndexOutOfBoundsException` or `NegativeArraySizeException`. Critically, this call sits **outside** the precompile's own `try/catch(Throwable)` block, which only wraps the later `getPermissionById`/signature-recovery logic [3](#0-2) . This is corroborated by the existing test comment stating that "this precompile has no outer catch, so a too-short input raises inside the decoder" for the pre-activation path [4](#0-3) .

### Impact Explanation
An uncaught runtime exception thrown from inside a precompile during transaction execution can propagate up through the TVM call stack. Depending on how the enclosing `Program`/`Runtime` layer handles it (I was unable to fully trace `Program.callToPrecompiledAddress` before running out of tool budget), this could either be swallowed as a normal `ContractExeException` (low impact, transaction just fails) or — if uncaught at a level that processes blocks — cause a node to halt/crash while applying a block, which would be a Medium-severity denial-of-service matching the CVSS profile of the reported CVE (AV:N/AC:L/PR:N/UI:R/S:U/C:N/I:N/A:H).

### Likelihood Explanation
Reachable by any account issuing a `TriggerSmartContract` transaction that calls address `0x0a` (`validatemultisign`) with crafted calldata; no special privilege required. However, whether this path is currently reachable depends on the default state of `VMConfig.allowTvmOsaka()` and `VMConfig.allowTvmSelfdestructRestriction()` in the target network's activated feature set — if TIP-854 (Osaka) is already active on mainnet, the `isValidAbiEncoding` guard would reject malformed calldata before reaching the vulnerable code, closing this path.

### Recommendation
Wrap the `extractBytesArray`/`extractSigArray` calls (and the `words[...]` offset lookups) in `ValidateMultiSign.execute()` in the same defensive `try/catch(Throwable)` used later in the method, or apply the `isValidAbiEncoding`/`MAX_SIZE` checks unconditionally rather than only under feature flags, so malformed length/offset fields cannot produce an unguarded exception regardless of the TIP-854/selfdestruct-restriction activation state.

### Proof of Concept
I could not fully confirm the exception-propagation behavior of `Program.callToPrecompiledAddress` (I ran out of tool iterations before reading that method), so I cannot construct a concrete end-to-end crash PoC with certainty. Conceptually: deploy a contract with a `STATICCALL` to `0x0a` supplying calldata whose `words[3]`-referenced length word decodes to a negative or out-of-range value for `bytesLen`/`bytesOffset`, on a network where `allowTvmOsaka()` and `allowTvmSelfdestructRestriction()` are both disabled, and observe whether the resulting exception is contained by the VM or escapes to crash/halt block processing. **This last verification step is the key open item and should be confirmed with source access to `Program.java`'s `callToPrecompiledAddress` before treating this as a confirmed high-impact finding — treat this report as unverified regarding actual process-crash impact.**
