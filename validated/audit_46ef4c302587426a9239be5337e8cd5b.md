### Title
Claiming rewards in the same block a token speed is set credits the full balance as accrued rewards because an uninitialized `accountIndexOf` is treated as index 0 instead of `INITIAL_INDEX` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` only substitutes `INITIAL_INDEX` for a missing account index when the token index has *grown past* `INITIAL_INDEX`. When a token's speed is set for the first time, `tokenStates[token].index == INITIAL_INDEX` and stays equal until a later timestamp. In that window, a first-time account is credited `balanceOf(account) * INITIAL_INDEX` as claimable rewards, analogous to the nginx bug where regex capture variables are read before the `map` evaluation initializes them.

### Finding Description
In `_updateTokenSpeed`, a token is registered with `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` (line 298). `_calculateTokenIndex` only increases the index when `_deltaTimestamps > 0 && _speed > 0` (line 203), so within the same block the stored index remains exactly `INITIAL_INDEX` (1e18).

In `_calculateTokenDelta`:

```solidity
_tokenIndex = _tokenState.index;
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```
(contracts/RewardsDistributor.sol:222-230)

For an account that has never had `accountIndexOf` set, `_accountIndex` is 0. The fallback to `INITIAL_INDEX` is gated on `_tokenIndex > INITIAL_INDEX`, which is false while the index is still exactly `INITIAL_INDEX`. So `_deltaIndex = 1e18` and `_tokensDelta ≈ balanceOf(account_)`. `claimRewards` then settles `tokensAccruedOf` via `_transferRewardIfEnoughTokens` (line 251), paying out up to the distributor's whole `rewardToken` balance.

### Impact Explanation
An unprivileged attacker who holds (or flash-deposits in a prior block and holds) a DepositToken/DebtToken balance can call `claimRewards` in the same block the governor calls `updateTokenSpeed(s)` for that token, and receive roughly `balanceOf(attacker)` units of the reward token, bounded only by the distributor's reward balance. This is direct theft of unclaimed yield owed to all other users; the distributor's reward pool is drained by an account that accrued zero time-weighted rewards. `accountIndexOf` is then set to `INITIAL_INDEX`, so the drain is once per account per token, but a single large holder suffices to empty the contract.

### Likelihood Explanation
- The attack window requires a same-block `claimRewards` after the governor's `updateTokenSpeed` transaction. Speed updates are public mempool transactions (and `syncTokenSpeed` by `tokenSpeedKeeper` can also trigger the first initialization), so an attacker can back-run them; on chains with public mempools this is standard MEV ordering, which is within the allowed attacker model (front-running/ordering).
- The attacker only needs an existing deposit/debt balance on the token whose speed is being set; no privileged role, malicious oracle, or external infrastructure is needed.
- Limitation: the exploit only works while `tokenStates[token].index == INITIAL_INDEX`, i.e., the same block the speed transitions from 0 to non-zero for a token that has never had a positive speed. Subsequent calls compute the index correctly.

### Recommendation
In `_calculateTokenDelta`, substitute `INITIAL_INDEX` whenever `_accountIndex == 0` (i.e., treat a missing account index as the initial index regardless of whether the token index has advanced), or clamp `_deltaIndex` so that `accountIndexOf` is initialized to `max(_tokenIndex, INITIAL_INDEX)` on first touch. Alternatively, set `accountIndexOf` for all holders is impractical, so the cleaner fix is:

```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex >= INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```

ensuring `_deltaIndex` is 0 for accounts that never accrued.

### Proof of Concept
Foundry fork sketch (mainnet, using deployed `Pool`/`RewardsDistributor`):

```solidity
function test_claimRewards_sameBlockAsSpeedSet() public {
    // 1. Attacker already holds msdToken balance (deposit beforehand in earlier block)
    vm.prank(attacker);
    depositToken.deposit(amount, attacker); // separate prior block

    // 2. Governor sets a speed for that deposit token (initializes index = INITIAL_INDEX)
    vm.prank(governor);
    rewardsDistributor.updateTokenSpeed(depositToken, speed);

    // 3. Same block: attacker claims. deltaIndex = INITIAL_INDEX - 0
    uint256 balBefore = rewardToken.balanceOf(attacker);
    vm.prank(attacker);
    rewardsDistributor.claimRewards(attacker);

    // Attacker receives ~depositToken.balanceOf(attacker) reward tokens
    assertGt(rewardToken.balanceOf(attacker) - balBefore, 0);
}
```

Uncertainty note: I could not verify from indexed code whether `updateTokenSpeed` is ever re-invoked for a token whose `index` reverted to exactly `INITIAL_INDEX` after previously being positive (the else-branch at line 300-303 preserves a grown index, so the window only exists on first initialization — confirmed by the `tokenStates[token_].index == 0` check). The finding is therefore limited to the first speed-setting transaction per token, which is still a real, reachable event on each newly incentivized market.
