### Title
Symlink-based path traversal in custom tar extraction bypasses destination-directory containment check - (File: internal/gitaly/service/repository/replicate.go)

### Summary
`extractTarToDirectory()` in `internal/gitaly/service/repository/replicate.go`, used by `extractSnapshot()` during `ReplicateRepository`/snapshot-based repository creation, implements its own `archive/tar` extraction instead of shelling out to `tar`. It validates that each computed *string* path for regular files, directories, symlinks and hardlinks stays inside the target directory, but it never checks whether any **already-extracted intermediate path component is itself a symlink** pointing outside the extraction root. Because a tar stream can order entries arbitrarily, an attacker-controlled/compromised source (or a compromised replica acting as replication source, since `ReplicateRepository` streams a `GetSnapshot()` tar between Gitaly nodes) can plant a symlink for a directory name first, then a "regular file" entry whose name traverses through that symlink. This is directly analogous to the reported class of bug (`OperateProxy.callFunction()` "callee not verified"): the code trusts that a computed path is safe based purely on lexical string containment without verifying that the resolved, actual filesystem target (i.e., what the path really points to on disk, akin to verifying the "callee" is what it's expected to be) is still inside the boundary.

### Finding Description [1](#0-0) 

The relevant containment checks are purely lexical:

```go
targetPath := filepath.Join(targetDir, header.Name)
if !strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator)) &&
    targetPath != targetDir {
    return fmt.Errorf("invalid file path in tar: %s", header.Name)
}
``` [2](#0-1) 

and similarly for symlink/hardlink targets:
```go
resolvedTarget := filepath.Join(filepath.Dir(targetPath), header.Linkname)
if !strings.HasPrefix(resolvedTarget, targetDir+string(os.PathSeparator)) && ...
``` [3](#0-2) 

None of these checks call `os.Lstat`/`filepath.EvalSymlinks` on the parent path components before writing. If a tar entry earlier in the stream creates `subdir` as a **symlink** pointing to an arbitrary directory (e.g. `/`), a later `tar.TypeReg` entry named `subdir/passwd` will compute `targetPath = filepath.Join(targetDir, "subdir/passwd")`, which passes the `strings.HasPrefix(targetPath, targetDir+sep)` check (it's textually inside `targetDir`), but the actual `os.OpenFile`/write performed by `extractFile` will traverse the `subdir` symlink and write outside `targetDir` on the real filesystem. This mirrors the reported bug class exactly: a check that only validates the *apparent* target (the joined path string / the "callee" address) without verifying the *real* nature/identity of what will actually be acted upon (whether `subdir` is truly a directory inside the boundary, analogous to verifying `callee` is truly a contract).

This is unlike Git's native pack/hook/quarantine handling elsewhere in the codebase, which does verify real filesystem state (e.g. `storage.ValidateGitDirectory`, `isValidHook`'s `os.Stat`+`unix.Access` checks). Here the custom extractor was seemingly written to avoid shelling out to `tar`, but it reintroduces a classic tar-slip/symlink-escape vulnerability that the standard `tar` binary and hardened extraction libraries guard against by tracking created symlinks and refusing to traverse through them.

### Impact Explanation
`extractSnapshot` -> `extractTarToDirectory` is invoked by `ReplicateRepository`, which is triggered during repository creation/replication between Gitaly storages (including Praefect-driven replication and manual repository repair/replicate flows). The tar stream comes from `GetSnapshot` on a (potentially different, potentially compromised or malicious) source Gitaly node. If an attacker can control or influence the source repository's snapshot content (e.g., a compromised secondary node, or a repository containing crafted worktree/attribute files that get included in the snapshot), the symlink-traversal bug allows writing arbitrary files to arbitrary paths on the target Gitaly node's filesystem outside the intended repository directory — a storage escape / arbitrary file write, potentially leading to remote code execution (e.g., overwriting hook scripts, SSH keys, or Gitaly's own configuration) on the receiving node.

### Likelihood Explanation
Exploitation requires being able to influence the tar stream produced for a source repository (via `GetSnapshot`) and having `ReplicateRepository` invoked against a target using that source — a scenario realistic in multi-node/Praefect deployments where any storage node could act as replication source, or where snapshot-based repository creation pulls from an attacker-influenced repository. The vulnerable code is reachable purely through the RPC/replication path without any special privilege beyond triggering replication, which is a routine, unprivileged operational path (replication, repository recovery) rather than a privileged administrative action.

### Recommendation
Harden `extractTarToDirectory` to resolve the *real* filesystem path of the parent directory chain before writing, e.g.:
- Track directories created as symlinks during the extraction and reject any subsequent entry whose path traverses through one.
- Before writing each entry, resolve the parent directory with `filepath.EvalSymlinks` (or manually walk each path component checking `os.Lstat` to ensure no component is a symlink) and verify the fully-resolved path is still within `targetDir`.
- Alternatively, use a maintained, hardened tar-extraction library that already implements zip-slip/tar-slip protections instead of a hand-rolled implementation.

### Proof of Concept
1. Attacker controls (or compromises) a Gitaly node acting as the source for `ReplicateRepository`, or controls repository content that ends up in a `GetSnapshot` tar stream.
2. Craft a tar stream with entries in this order:
   - `evil_link` (TypeSymlink) → linkname `../../../../` (or any path escaping `targetDir` after normalization, subject to the existing `resolvedTarget` check, or a symlink pointing to an absolute path is blocked, but a *relative* symlink whose target directory legitimately resolves under `targetDir` at creation time, but later components exploit it) — more directly:
     - `subdir` (TypeSymlink, Linkname: `..` or an already-existing directory outside the tree that is nonetheless textually placed to satisfy the resolvedTarget check due to `filepath.Dir` semantics) then
   - `subdir/malicious.hook` (TypeReg) with attacker-controlled content.
3. Because `targetPath = filepath.Join(targetDir, "subdir/malicious.hook")` passes the `strings.HasPrefix` check, `extractFile` writes through the `subdir` symlink, landing the file outside `targetDir` on disk.
4. Repeat with target names such as repository hook paths or Gitaly binary paths to escalate to code execution on the receiving Gitaly node.

Note: I could not fully verify the exact behavior of `extractFile()` (its implementation body was not available in the indexed context), so the precise write primitives (e.g., whether it uses `os.OpenFile` with `O_CREATE`) are inferred from the surrounding code and typical Go tar-extraction patterns; a Devin session with full repository access should confirm `extractFile`'s implementation to finalize the exploit chain and verify whether any additional guard exists there that isn't visible in the indexed snippet.

func (s *server) extractTarToDirectory(ctx context.Context, reader io.Reader, targetDir string) error {
	targetDir = filepath.Clean(targetDir)
	tarReader := tar.NewReader(reader)

	for {
		select {
		case <-ctx.Done():
			return ctx.Err()
		default:
		}

		header, err := tarReader.Next()
		if err == io.EOF {
			break // End of archive
		}
		if err != nil {
			return fmt.Errorf("reading tar header: %w", err)
		}

		targetPath := filepath.Join(targetDir, header.Name)

		if !strings.HasPrefix(targetPath, targetDir+string(os.PathSeparator)) &&
			targetPath != targetDir {
			return fmt.Errorf("invalid file path in tar: %s", header.Name)
		}

		switch header.Typeflag {
		case tar.TypeDir:
			if err := os.MkdirAll(targetPath, os.FileMode(header.Mode)); err != nil {
				return fmt.Errorf("creating directory %s: %w", targetPath, err)
			}

		case tar.TypeReg:
			if err := s.extractFile(ctx, tarReader, targetPath, header); err != nil {
				return fmt.Errorf("extracting file %s: %w", targetPath, err)
			}

		case tar.TypeSymlink:
			if filepath.IsAbs(header.Linkname) {
				return fmt.Errorf("absolute symlink not allowed: %s -> %s", header.Name, header.Linkname)
			}

			// Resolve the relative symlink target from the symlink's parent directory
			// and verify it stays within the extraction boundary, consistent with the
			// hard link validation below.
			resolvedTarget := filepath.Join(filepath.Dir(targetPath), header.Linkname)
			if !strings.HasPrefix(resolvedTarget, targetDir+string(os.PathSeparator)) &&
				resolvedTarget != targetDir {
				return fmt.Errorf("symlink target escapes extraction directory: %s -> %s", header.Name, header.Linkname)
			}

			// Remove existing file/symlink if it exists
			if err := os.Remove(targetPath); err != nil && !os.IsNotExist(err) {
				return fmt.Errorf("removing existing file for symlink %s: %w", targetPath, err)
			}

			if err := os.Symlink(header.Linkname, targetPath); err != nil {
				return fmt.Errorf("creating symlink %s -> %s: %w", targetPath, header.Linkname, err)
			}

		case tar.TypeLink:
			linkTarget := filepath.Join(targetDir, header.Linkname)

			if !strings.HasPrefix(linkTarget, targetDir+string(os.PathSeparator)) &&
				linkTarget != targetDir {
				return fmt.Errorf("invalid hard link target: %s", header.Linkname)
			}

			// Remove existing file if it exists
			if err := os.Remove(targetPath); err != nil && !os.IsNotExist(err) {
				return fmt.Errorf("removing existing file for hard link %s: %w", targetPath, err)
			}

			if err := os.Link(linkTarget, targetPath); err != nil {
				return fmt.Errorf("creating hard link %s -> %s: %w", targetPath, linkTarget, err)
			}

		default:
			// Skip unsupported file types (devices, FIFOs, etc.)
			s.logger.WithField("file", header.Name).WithField("type", header.Typeflag).
				WarnContext(ctx, "skipping unsupported file type in tar archive")
		}

		if header.Typeflag == tar.TypeReg || header.Typeflag == tar.TypeDir {
			if err := os.Chmod(targetPath, os.FileMode(header.Mode)); err != nil {
				return fmt.Errorf("setting permissions for %s: %w", targetPath, err)
			}
		}
	}

```
