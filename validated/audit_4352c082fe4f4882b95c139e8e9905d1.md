### Title
Unauthenticated QUIC handshake-stalling floods bypass connection rate limiters and exhaust `max_concurrent_connections()`, starving legitimate TPU senders - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC ingress path in `run_server` allocates a `ClientConnectionTracker` slot (bounded by `qos.max_concurrent_connections()`) *before* the handshake completes, and the only checks performed pre-handshake — the overall `TokenBucket` and per-IP `ConnectionRateLimiter` — are non-consuming "peek" checks. Actual token consumption only happens in `setup_connection` *after* the handshake succeeds. An attacker who never completes the handshake therefore never gets rate-limited, and can repeatedly acquire and hold tracker slots for up to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2 seconds) each, exhausting the shared concurrent-connection budget indefinitely.

### Finding Description
In `run_server`, incoming QUIC `Incoming`s are gated by two "peek-only" checks before any resource is committed:
- `overall_connection_rate_limiter.current_tokens() == 0` [1](#0-0) 
- `rate_limiter.is_allowed(&incoming.remote_address().ip())` [2](#0-1) 

Both of these only read the token bucket state; neither consumes a token. `ConnectionRateLimiter::is_allowed` explicitly documents this: it assumes "only IPs with actual confirmed connections are stored in it, since we should only modify server state once source IP is verified" and returns `true` for any IP with tokens remaining or never seen, without decrementing anything. [3](#0-2) 

Immediately after these no-op checks pass, the server commits a real, bounded resource: it constructs a `ClientConnectionTracker`, which increments `stats.open_connections` and fails only when that counter reaches `qos.max_concurrent_connections()`: [4](#0-3) 

The connection is then handed to `setup_connection`, which awaits the handshake under a 2-second timeout defined as `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (not the 60s client-side constant referenced in the question — that constant lives in a different crate, `quic-client`, for outbound client connections): [5](#0-4) [6](#0-5) 

Only if the handshake *succeeds* does the code call `rate_limiter.register_connection` and `overall_connection_rate_limiter.consume_tokens(1)`, which are the only places that actually decrement tokens: [7](#0-6) 

Consequently, an attacker that sends a QUIC Initial packet and then withholds the rest of the handshake:
1. Passes both rate-limiter peek checks trivially (no tokens are ever consumed for stalled attempts).
2. Acquires a `ClientConnectionTracker` slot, incrementing the single, peer-type-agnostic `stats.open_connections` counter used for both staked and unstaked admission (the peer type is only determined later, via `qos.build_connection_context(&new_connection)` at line 512, which requires a completed handshake).
3. Holds that slot for up to 2 seconds (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`), then the slot is dropped (`connection_setup_timeout` stat incremented) and the `ClientConnectionTracker`'s `Drop` frees the counter.
4. Immediately repeats with a fresh Initial packet, since nothing about the attacker's IP or global budget was actually consumed.

By sustaining a rate of fresh half-open attempts near `qos.max_concurrent_connections() / QUIC_CONNECTION_HANDSHAKE_TIMEOUT`, the attacker can keep `stats.open_connections` pinned at `max_concurrent_connections()` indefinitely, causing all new connection attempts (legitimate unstaked or staked) to be refused via `incoming.refuse()` and counted in `refused_connections_too_many_open_connections`: [4](#0-3) 

Because tokens are only ever consumed post-handshake, this requires neither IP spoofing nor high volume relative to `TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST` — even a single real IP suffices, since `is_allowed` never depletes for an attacker that keeps stalling.

### Impact Explanation
This is a QoS-evasion / ingress-admission-fairness bug: it allows an unstaked, unprivileged attacker to fully occupy the shared `max_concurrent_connections()` budget (used by both staked and unstaked admission before peer typing occurs), refusing new connections from legitimate senders and starving TPU capacity — matching the "unfairly capture connection... QoS limits and starve legitimate senders of TPU capacity" impact category for this file/scope.

### Likelihood Explanation
Feasible with a single unstaked, unprivileged remote client capable of sending raw QUIC Initial packets and declining to complete the handshake — no stake, no spoofing, and no volume beyond `qos.max_concurrent_connections()` concurrent half-open attempts is required. The attack is trivially repeatable/sustainable since dropped/timed-out attempts free the slot only to be immediately re-occupied by a new Initial packet, and none of the pre-handshake admission checks actually rate-limit stalled attempts.

### Recommendation
Consume (or reserve) rate-limiter tokens — both the overall `TokenBucket` and the per-IP `ConnectionRateLimiter` — at the point the `ClientConnectionTracker` slot is allocated (before `incoming.accept()`), not only after a successful handshake; refund/adjust on success if finer-grained post-handshake accounting by verified IP is still desired. Alternatively, bound the number of concurrently in-flight (not-yet-handshaken) connections separately and more tightly than `qos.max_concurrent_connections()`, and/or require QUIC Retry (stateless address validation) for all Initial packets so an attacker must demonstrate a real round trip before a `ClientConnectionTracker` slot is committed.

### Proof of Concept
Integration test plan (extends existing test harness in `streamer/src/nonblocking/quic.rs` test module, using `setup_quic_server`):
1. Configure `SwQosConfig` with a small `max_staked_connections`/`max_unstaked_connections` so `qos.max_concurrent_connections()` is a known small number `N`.
2. From a raw `quinn::Endpoint` client (or an endpoint configured to send Initial packets without responding to the server's Handshake), open `N` connection attempts concurrently (`endpoint.connect(...)`), but do not await/drive them to completion (drop the driving task or block further packet I/O so the handshake never finishes).
3. Assert that `stats.open_connections` reaches `N` and stays there for `~QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
4. Concurrently, from a second legitimate client, attempt a normal connection and assert it is refused (`stats.refused_connections_too_many_open_connections` increments) while the stalled attacker connections are still pending.
5. Repeat step 2 in a loop timed against the 2-second timeout (re-issue stalled connections every ~2s) and assert that `refused_connections_too_many_open_connections` continues to increase over an extended window (e.g., 10+ seconds), demonstrating sustained starvation rather than a one-off timing coincidence, while confirming via `stats.connection_rate_limited_per_ipaddr` / `stats.connection_rate_limited_across_all` that the attacker's stalled attempts were never counted against either rate limiter (proving the bypass).

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
