## Title
Attacker-controlled contract code in `ERC20Transactor` can revert XCM asset settlement, trapping bundled legitimate assets and griefing the intended beneficiary - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
The reNFT bug allowed a lender to withhold a renter's payment by making the `onERC721Received`/`onERC1155BatchReceived` callback of a smart-contract recipient revert during `Reclaimer._reclaimRentedItems()`, causing the whole "stop rental" settlement to fail atomically while the attacker kept full, cost-free control over whether/when to release the counterparty's funds. The same broken invariant — a synchronous, atomic settlement step that must call into attacker-controlled contract code, whose revert blocks delivery to an honest counterparty — exists in `ERC20Transactor` (`cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`), which is wired into `AssetTransactors` for Asset Hub Westend.

## Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` implement the `TransactAsset` trait used by the XCM executor for any asset matched by `ERC20Matcher`: [1](#0-0) 

`ERC20Matcher` is `MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>`, and `IsLocalAccountKey20` matches **any** location of the shape `(0, [AccountKey20 { .. }])` — with no allow-list or registration check that the address is a "real" ERC20 contract: [2](#0-1) 

`ERC20Transactor` is included in the runtime's `AssetTransactors` tuple used by the XCM executor for every asset-transfer instruction: [3](#0-2) 

When an asset matched by this transactor is deposited, the transactor performs a live call into the contract at that address via `pallet_revive::Pallet::<T>::bare_call`, invoking the Solidity `IERC20::transfer` selector on **attacker-deployable code**: [4](#0-3) 

If the contract reverts, returns `false`, or its return data fails to decode, `deposit_asset_with_surplus` returns `Err((what, XcmError::FailedToTransactAsset(...)))`: [5](#0-4) 

This is exactly the reNFT pattern: a settlement primitive (`safeTransferFrom` there, `DepositAsset`/`WithdrawAsset` here) that must call into arbitrary, attacker-controlled contract code as part of an otherwise trust-minimized transfer, and whose revert aborts the transfer instead of merely failing gracefully for that one leg.

The XCM executor's `DepositAsset`/`WithdrawAsset` processing is transactional per instruction: any per-asset failure aborts the *whole* instruction and rolls back/traps the *entire* holding register accumulated so far in the program, not just the poisoned asset — as directly demonstrated by the executor's own tests: [6](#0-5) [7](#0-6) 

So if a single `DepositAsset`/`WithdrawAsset` instruction bundles a legitimate asset (e.g. DOT, a foreign asset reward) together with an `ERC20Transactor`-matched asset controlled by an attacker, the attacker's contract can unilaterally force the entire instruction — including the legitimate leg meant for an honest beneficiary — to fail and be trapped via `AssetsTrapped`, keyed to the *origin* of the XCM program, not the intended beneficiary: [8](#0-7) 

Existing guards (transactional rollback, asset trapping/`claim_assets`) only recover funds for the trap's *origin* location; they do not protect the *beneficiary* of a `DepositAsset` from having their expected settlement withheld indefinitely at the attacker's discretion, and — if the origin of the XCM program is attacker-controlled (e.g. the attacker is also the sender in a self-service claim/payout flow that bundles a malicious "asset") — the attacker can later reclaim the trapped legitimate assets for themselves via `claim_assets`, exactly mirroring the reNFT lender's zero-risk ability to release (or not) the counterparty's funds at will.

## Impact Explanation
This breaks the required invariant that "message queues, ... and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" and that value must "settle exactly once to the rightful beneficiary." A permissionless attacker who deploys a `pallet-revive` contract and gets it referenced as an asset in a multi-asset `DepositAsset`/`WithdrawAsset` XCM instruction can:
- Deny settlement to an honest beneficiary bundled in the same instruction (funds get trapped instead of delivered), and
- Depending on which account is the XCM program's origin, potentially reclaim the trapped legitimate assets back to themselves via `claim_assets`, since traps are keyed by origin, not by intended beneficiary.

This matches the external report's Medium-severity griefing pattern (temporary, attacker-reversible withholding of a counterparty's funds via a callback embedded in an atomic settlement step) and, in the origin-controlled-by-attacker sub-case, escalates it toward a fund-diversion primitive.

## Likelihood Explanation
Deploying a contract via `pallet-revive` (`instantiate`) is a fully permissionless, unprivileged operation available to any signed account; no governance, admin, relayer, or validator collusion is required. `ERC20Matcher` requires no registration of the address as a "real" asset — any `AccountKey20` location is eligible, so the only requirement is that some XCM program (which could originate from the attacker's own account, or from a public flow that lets a user select a fee/reward asset) treats that address as an asset in a `DepositAsset`/`WithdrawAsset` alongside a legitimate asset.

## Recommendation
- Do not allow `ERC20Transactor`-matched assets to be bundled with other assets in the same `DepositAsset`/`WithdrawAsset` instruction, or process each asset's deposit/withdraw independently so a revert in one asset's callback cannot roll back or trap unrelated legitimate assets.
- Require assets handled by `ERC20Transactor` to be explicitly allow-listed/registered (analogous to `pallet-assets`' foreign-asset registration) rather than matched by address shape alone (`IsLocalAccountKey20`).
- Consider using a non-reverting, push/pull-based settlement model (splitting "mark settled" from "deliver funds", as recommended in the original report) so a malicious ERC20 contract cannot block the settlement of unrelated assets or beneficiaries.

## Proof of Concept
1. Deploy a malicious `pallet-revive` contract implementing `IERC20` whose `transfer()` unconditionally reverts (or returns `false`) when called by `TransfersCheckingAccount`, mirroring `BadWallet.onERC721Received` in the original report.
2. Construct (or trigger, via any code path that builds a `DepositAsset`/`WithdrawAsset` instruction combining assets, e.g. `AllCounted(n)`/`Wild` filters) an XCM program that:
   - `WithdrawAsset([Legitimate asset (e.g. DOT), Malicious ERC20 asset at the deployed contract's `AccountKey20` location])`
   - `DepositAsset { assets: AllCounted(2), beneficiary: <honest recipient> }`
3. Observe, per the existing executor test pattern (`deposit_assets_with_retry_aborts_on_failure_and_post_process_traps`, `partial_deposit_failure_aborts_instruction_and_traps_full_holding`), that the malicious asset's failing `deposit_asset_with_surplus` call aborts the entire `DepositAsset` instruction; the honest recipient never receives the legitimate asset, and the full holding (legitimate + malicious asset) is trapped via `AssetsTrapped`, claimable only by the program's origin — not the intended beneficiary.

#[test]
fn deposit_assets_with_retry_aborts_on_failure_and_post_process_traps() {
	// fund sender
	add_asset(SENDER, (Here, 200u128));

	// sub-ED amount (< ED=2): this `DepositAsset` will fail and abort the program.
	let dust: Asset = (Here, 1u128).into();

	// ≥ED amount: would succeed on its own — but the program aborts at the first error,
	// so this instruction never runs.
	let legit: Asset = (Here, 100u128).into();

	let xcm = Xcm::<TestCall>(vec![
		WithdrawAsset((Here, 101u128).into()),
		DepositAsset { assets: Definite(Assets::from(vec![dust])), beneficiary: RECIPIENT.into() },
		DepositAsset { assets: Definite(Assets::from(vec![legit])), beneficiary: RECIPIENT.into() },
	]);

	let (mut vm, weight) = instantiate_executor(SENDER, xcm.clone());

	let err = vm
		.bench_process(xcm)
		.expect_err("a sub-ED `DepositAsset` must error out and abort the rest of the XCM");
	vm.set_error(Some((err.index, err.xcm_error)));

	let outcome = vm.bench_post_process(weight);
	assert!(
		matches!(outcome, Outcome::Incomplete { .. }),
		"Expected Incomplete, got {:?}",
		outcome
	);

	// Nothing reached the recipient: the failing `DepositAsset` rolled back its own take,
	// and the subsequent `DepositAsset(legit)` was never executed because the program is
	// already in error state.
	let here_assets = asset_list(RECIPIENT);
	assert!(here_assets.is_empty(), "no deposit should reach recipient when program aborts");

	// `post_process` trapped the leftover holding — the full 101 originally withdrawn.
	let trapped = asset_list(TRAPPED_ASSETS);
	assert_eq!(
		trapped,
		vec![(Here, 101u128).into()],
		"the entire pre-instruction holding must be trapped (claimable later), not silently lost"
	);
}
