Audit Report

## Title
`add_tip` in the Snowbridge System-V2 pallet always returns `Ok(())` and permanently strands user funds in `LostTips` when the tip target cannot be found - ([File: bridges/snowbridge/pallets/system-v2/src/lib.rs])

## Summary
`EthereumSystemV2::add_tip` on BridgeHub dispatches to `InboundQueue::add_tip`/`OutboundQueue::add_tip`, which can fail with `AddTipError::NonceConsumed` or `AddTipError::UnknownMessage` when the target nonce/order is already gone. Instead of propagating this failure, `add_tip` swallows the error, moves the amount into the `LostTips` storage map, and unconditionally returns `Ok(())`, while the AssetHub-side `system-frontend::add_tip` has already irreversibly burned the user's tip asset before this call is even made, and no extrinsic exists to reclaim `LostTips`.

## Finding Description
On AssetHub, a signed user calls `snowbridge_pallet_system_frontend::add_tip`, which swaps/burns the user's fee asset via `swap_fee_asset_and_burn` (an irreversible burn-for-teleport) and then sends an XCM `Transact` to BridgeHub invoking `EthereumSystemV2::add_tip` with the already-committed `amount`. [1](#0-0) 

On BridgeHub, `add_tip` checks `T::FrontendOrigin::ensure_origin(origin)?` (an XCM-origin check, not privileged) and then attempts to attach the tip via `InboundQueue::add_tip`/`OutboundQueue::add_tip`: [7](#0-6) 

`InboundQueue::add_tip` fails with `AddTipError::NonceConsumed` if `Nonce::<T>::get(nonce)` is already true (message already processed), and `OutboundQueue::add_tip` fails with `AddTipError::UnknownMessage` if the `PendingOrders` entry for the nonce no longer exists (order already finalized/removed). [4](#0-3) [5](#0-4) 

When that occurs, `EthereumSystemV2::add_tip` does not return the error to the caller. It instead records the amount into `LostTips::<T>` and returns `Ok(())` regardless: [8](#0-7) 

The `LostTips` storage doc explicitly acknowledges there is no recovery mechanism yet ("Capturing the lost tips here supports implementing a recovery method in the future"), and no such recovery extrinsic exists anywhere in this repository. [3](#0-2) 

Because the burn on AssetHub already happened unconditionally in `system-frontend::add_tip` before the cross-chain call, and because BridgeHub's `add_tip` cannot fail the call even when the tip cannot be attached, the entire flow has no atomic rollback: the user's asset is destroyed on AssetHub regardless of whether the BridgeHub-side operation succeeds.

## Impact Explanation
This matches the "permanent user-fund lock" impact category in the gate. Any unprivileged user calling the public `add_tip` extrinsic on AssetHub can permanently lose their tip amount purely due to a race between message/order processing and tip delivery — no malicious relayer, validator, or governance action is required. The lost value accumulates in `LostTips` with no extrinsic in the codebase capable of returning it to the user, making the loss permanent and unbounded in aggregate across many users/tips.

## Likelihood Explanation
This is a naturally occurring race condition rather than a crafted attack: any legitimate user tipping a message that is processed (inbound) or whose order is finalized (outbound) concurrently with the tip's cross-chain delivery will trigger this path. The existing test `add_tip_inbound_fails_when_nonce_is_consumed` demonstrates this exact condition is reachable and already anticipated by the pallet authors, confirming high likelihood in production given normal bridge relay timing variance. [9](#0-8) 

## Recommendation
Provide a concrete extrinsic to reclaim `LostTips` balances back to the recorded sender (e.g., a signed call from the account matching the `LostTips` key that mints/transfers the recorded amount back and zeroes the entry), or redesign the flow so the AssetHub-side burn only finalizes after BridgeHub confirms the tip was actually attached (e.g., a two-phase commit/refund XCM), instead of unconditionally returning `Ok(())` on the BridgeHub side while the asset is already irrecoverably burned on AssetHub.

## Proof of Concept
1. A relayer processes an inbound message with nonce `N`, setting `Nonce::<T>::set(N.into(), true)` in `inbound-queue-v2`, or the corresponding outbound `PendingOrders` entry for nonce `N` is removed on finalization.
2. Concurrently, a user calls `system-frontend::add_tip(message_id, asset)` on AssetHub; `swap_fee_asset_and_burn` irreversibly burns the user's asset, and an XCM `Transact` is sent to BridgeHub.
3. The XCM lands at `EthereumSystemV2::add_tip(sender, MessageId::Inbound(N), amount)` after step 1 has occurred.
4. `InboundQueue::add_tip` returns `Err(AddTipError::NonceConsumed)`; `add_tip` catches it, does `LostTips::<T>::mutate(&sender, ...)`, emits `TipProcessed { success: false, .. }`, and returns `Ok(())`.
5. Confirmed by the existing unit test `add_tip_inbound_fails_when_nonce_is_consumed`, which asserts `assert_ok!(EthereumSystemV2::add_tip(...))` succeeds at the dispatch level while `LostTips::<Test>::get(sender) == 1000`, with no subsequent call in the pallet able to reclaim it. [9](#0-8)
