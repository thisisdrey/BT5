## Analysis: Timing side-channel in HTTP auth-token comparison (CWE-208/287 analog)

The Bytebase advisory's core theme is **improper authentication allowing the effective auth secret to be derived/bypassed remotely without needing privileged access**. The closest in-scope analog in `stackslib/src/net/**` is not a "fails open" auth gate, but a family of endpoints that compare the client-supplied `authorization` header against the configured secret using Rust's default (non-constant-time) `!=` string comparison, creating a timing oracle that lets a remote, unauthenticated attacker incrementally recover the secret `auth_token`.

### Title
Timing side-channel in `Authorization` header comparison enables remote `auth_token` recovery - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
Several privileged v2/v3 RPC handlers protect state-mutating or resource-intensive endpoints with a single shared secret (`connection_options.auth_token`), checked via a plain `!=` comparison between the request's `authorization` header value and the stored password. This comparison is not constant-time: Rust's `String`/`&str` equality short-circuits on the first differing byte (and on length mismatch), so the time-to-reject leaks information about how many leading bytes of the attacker's guess are correct.

### Finding Description
The identical pattern appears across multiple handlers:

- `stackslib/src/net/api/postblock_v3.rs:104-109` — gates authenticated `broadcast=1` submissions to `POST /v2/blocks`. [1](#0-0) 
- `stackslib/src/net/api/postblock_proposal.rs:1139-1144` — gates `POST /v3/block_proposal`. [2](#0-1) 
- `stackslib/src/net/api/blockreplay.rs:575-583` and `stackslib/src/net/api/blocksimulate.rs:153-161` — gate `/v3/blocks/replay/*` and `/v3/blocks/simulate/*`. [3](#0-2) [4](#0-3) 
- `stackslib/src/net/api/txsimulate.rs:352-360` — gates `/v3/transactions/simulate`. [5](#0-4) 
- `stackslib/src/net/api/fastcallreadonly.rs` uses the same `auth_header != password` pattern for `/v3/contracts/fast-call-read/*`. [6](#0-5) 

In each case, `self.auth` (the configured `auth_token`, documented at `stackslib/src/config/mod.rs:3802-3816` as securing the node/`stacks-signer` channel and the `/v2/blocks?broadcast=1` path) is compared with `!=` against the raw header string, and the request is rejected with `401` on any mismatch, otherwise proceeding as fully authenticated. [7](#0-6) 

Because this comparison is on the network-facing HTTP path and returns a distinguishable timing signal (correct-prefix guesses take marginally longer to reject than all-wrong guesses due to the underlying byte-wise scan), a remote unauthenticated attacker can mount a classic byte-at-a-time timing attack to recover the secret token character-by-character, without ever needing physical/log access to the node, and — critically, echoing the report's "as long as the server isn't rebooted" framing — the secret is static for the lifetime of the node's configuration, so the attack window persists indefinitely.

### Impact Explanation
Recovering `auth_token` yields full authentication bypass for every endpoint gated by it: forging `broadcast=1` block submissions on `/v2/blocks`, submitting attacker-controlled `/v3/block_proposal` requests to a signer's node, and abusing `/v3/blocks/simulate`, `/v3/blocks/replay`, `/v3/transactions/simulate`, and `/v3/contracts/fast-call-read` for state/compute abuse gated behind the same secret. This matches the "Critical" bucket definition (auth bypass) in this analog's impact rules, since it defeats the sole authentication mechanism protecting these RPC surfaces.

### Likelihood Explanation
Timing side channels over a network are noisy and typically require many repeated measurements/statistical averaging to extract a secret reliably, which lowers real-world exploitability compared to a memory-safety bug or literal fail-open gate. This is a genuine but comparatively harder-to-exploit CWE-208/287-class weakness; it is a plausible, non-theoretical risk but not as trivially triggerable as the cited GitLab-login-bypass in the advisory.

### Recommendation
Replace all `auth_header != password` (and equivalent) checks with a constant-time comparison (e.g., `subtle::ConstantTimeEq`, or first compare a keyed HMAC digest of both values) across `postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, and `fastcallreadonly.rs`. Centralize this check into a single shared helper in `stackslib/src/net/httpcore.rs` to avoid re-introducing the pattern in future endpoints.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unauthenticated client, repeatedly send `POST /v3/block_proposal` (or any of the listed endpoints) with `authorization` headers guessing successive byte prefixes of the token, measuring response latency for the `401 Unauthorized` rejection at `postblock_proposal.rs:1139-1144`.
3. Statistically distinguish prefixes that match more leading bytes (slightly longer compare time before mismatch) from those that diverge earlier, and iterate byte-by-byte to reconstruct `auth_token` without ever needing the node to reboot or reset its configuration.
