### Title
Unrestricted `LinkRepositoryToObjectPool` allows cross-repository object disclosure by linking any repository to any object pool - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
The Sherlock report's root cause is that `ValueTokenFacet.sol`'s mint/burn functions treat a fungible token identically regardless of which `cid` (closure/pool) it came from, letting a caller "cash out" value from an arbitrary closure it never legitimately funded. The structural analog in gitaly is `LinkRepositoryToObjectPool`, which links any caller-controlled `repository` to any existing `object_pool` without verifying a real ancestry/ownership relationship between them, other than that both reside on the same storage/partition. Once linked, all objects that are "shared" in the pool (originally deduplicated from the pool's real fork family) become fully readable through the newly linked repository, just as the ValueToken bug lets a user "redeem" value from a closure it has no legitimate claim to.

### Finding Description
`LinkRepositoryToObjectPool` in `internal/gitaly/service/objectpool/link.go` only validates that the `repository` argument is a valid repository and that the `object_pool` resolves to an existing pool repository: [1](#0-0) 

It never checks that `repository` is actually a fork/member that is supposed to belong to that particular `pool` (e.g., that the pool was created from that repository's ancestry, or that the caller has any pre-existing relationship to the pool). The only cross-repository guard enforced elsewhere is a storage/partition match, as seen in the analogous `FetchIntoObjectPoolRequest` validator: [2](#0-1) 

The actual linking logic in `internal/git/objectpool/link.go`'s `Link` function simply writes the pool's `objects` directory path into the repository's `objects/info/alternates` file and removes the repository's bitmap - it performs no ownership/lineage check either: [3](#0-2) 

Once `objects/info/alternates` points at the pool, Git's alternate-object-directory mechanism (the same mechanism documented for quarantine object visibility) makes every object in the pool - which may include the full history and dangling/force-pushed objects from *other, unrelated* repositories that are legitimate pool members - readable from the newly linked repository: [4](#0-3) [5](#0-4) 

The existing tests confirm the mechanics: linking makes previously pool-only commits fetchable/readable from the member repository immediately, with no ownership check performed: [6](#0-5) 

This mirrors the reported bug class exactly: a shared resource (ValueToken / object pool) is redeemable/accessible by any party holding a reference to it (`cid` / `object_pool` proto field), regardless of whether that party legitimately contributed to or owns that resource. In Gitaly's case this is reachable via an ordinary RPC field (`LinkRepositoryToObjectPoolRequest.object_pool`) supplied by any caller who can invoke the RPC and who controls a target repository, i.e. a crafted-RPC-field analog rather than a privileged-actor-only issue.

### Impact Explanation
Successful exploitation grants a caller who has write access to any repository (e.g., an authenticated ordinary project maintainer whose Rails/GitLab-side authorization only checks that they can administer their own target repository) the ability to read all objects contained in an arbitrary, otherwise-unrelated object pool - including forked-repo history, dangling objects preserved by pool housekeeping, and commits from sibling forks that were never pushed to the attacker's own repository. This is a concrete cross-repository object disclosure: confidential commits/blobs of unrelated repositories become fetchable through the attacker's repository once linked. It can also corrupt the attacker's own repository state (bitmap removal, alternate file rewrite) and pollute the pool's member accounting, but the primary security impact is unauthorized object exposure across repository/project boundaries.

### Likelihood Explanation
The requests involved (`LinkRepositoryToObjectPoolRequest`) are ordinary mutator RPCs annotated with `target_repository`/`additional_repository`, meaning Praefect/Gitaly's own storage/partition routing checks are satisfied as long as both repositories are in the same partition/storage - a condition attacker-controlled forks can often satisfy since fork object pools are typically colocated with their forks on the same storage. The remaining authorization (that the repository is actually a legitimate member of that particular pool) is expected to be enforced by the calling layer (e.g., GitLab Rails), not by Gitaly itself; if that external authorization has any gap, mislabels the pool identity, or is bypassed for a given call path, Gitaly performs no independent verification. This makes the likelihood dependent on external ACL correctness, which is a plausible but not certain condition - hence moderate rather than certain likelihood.

### Recommendation
Have `LinkRepositoryToObjectPool` (and/or the underlying `objectpool.Link`) verify a genuine relationship between the target repository and the object pool before writing the alternates file - for example, by confirming the pool was created from that repository's lineage (tracked pool metadata / origin repository ID) rather than trusting the caller-supplied `object_pool` reference outright. At minimum, maintain and check a pool-membership record (as hinted by `relational.PoolStore` used in `ScanPoolMetadata`) so that Gitaly itself enforces that only repositories with an established, recorded relationship to a pool can be linked to it, rather than relying solely on same-storage/partition checks and upstream Rails-side authorization.

### Proof of Concept
Not independently reproduced in this repository (no test harness or terminal access available in this analysis mode); the code-level proof is the absence of any ownership/lineage check in `LinkRepositoryToObjectPool` / `objectpool.Link` (cited above) combined with the documented alternate-object-directory sharing semantics in `doc/object_pools.md`, which together establish that any two same-storage repositories can be linked and thereby exposed to each other's objects. A full working exploit would require constructing two unrelated repositories/pools on the same Gitaly storage/partition and issuing `LinkRepositoryToObjectPoolRequest` from one to the other's pool, then confirming the second repository's private commits become readable from the first - which mirrors the existing `TestLink` test flow at `internal/gitaly/service/objectpool/link_test.go:97-158` but using an unrelated pool instead of the repository's own fork pool.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}

**File:** doc/object_pools.md (L1-12)
```markdown
# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.
```

```markdown
## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```
