This confirms the trait doc's explicit warning: the returned "known since" block number must be checked by callers before trusting the randomness for existing commitments (ticket purchases). The `pallet-lottery` violates this contract.

### Title
Lottery winner selection uses stale, publicly-predictable randomness without checking `known_since`, letting an unprivileged attacker guarantee a win - (File: substrate/frame/lottery/src/lib.rs)

### Summary
`pallet_lottery`'s payout logic (`on_initialize` → `choose_account` → `choose_ticket` → `generate_random_number`) calls `T::Randomness::random(...)` and uses only the returned seed, discarding the second tuple element (`known_since`) that the `Randomness` trait explicitly requires callers to validate before trusting the seed for prior commitments. [1](#0-0) [2](#0-1) 

### Finding Description
The `Randomness` trait documents that its returned seed "should only be used to distinguish commitments made before the returned block number," i.e. callers must verify `known_since` is later than the last block at which a relevant commitment (here, a ticket purchase) could have been made. [3](#0-2) 

The runtime's slot-auction pallet correctly implements this check: `check_auction_end` only accepts the random offset if `late_end <= known_since`, i.e. only if the randomness was determined strictly after all bids were locked in. [4](#0-3) 

`pallet_lottery` does no such check. `generate_random_number` uses `T::Randomness::random(...)` and immediately decodes the seed, ignoring the timing guarantee entirely: [5](#0-4) 

The default runtime wiring uses `RandomnessCollectiveFlip` (`pallet_insecure_randomness_collective_flip`) as `T::Randomness`: [6](#0-5) 

That pallet derives its seed from the hashes of the previous 81 blocks and reports `known_since = block_number - 81`: [7](#0-6) 

Ticket purchases end at `config.start + config.length`, and the winner is drawn at `payout_block = start + length + delay`, using randomness evaluated in `on_initialize(payout_block)` (`known_since = payout_block - 81`). Since `delay` is an arbitrary `BlockNumber` chosen by `ManagerOrigin` with **no minimum enforced** (`start_lottery` performs no bound-check on `delay` relative to `RANDOM_MATERIAL_LEN`), whenever `delay < 81` the seed used for payout is derived from block hashes that were already fully public *before* the ticket-buying window even closed (`known_since < start + length`). Any unprivileged observer can therefore compute the exact winning ticket index in advance, and precisely time a `buy_ticket` call so their own ticket lands on `Tickets::<T>::insert(ticket_count, caller)` at that predicted index, guaranteeing they win the pot. [8](#0-7) [9](#0-8) 

This is the direct structural analog of the external report: a "random" outcome is derived from an entropy source (block-hash-derived material) that is fully predictable ahead of time, allowing an attacker to precompute the "rare" outcome (winning ticket index) before committing, exactly as the NFT starting index could be scraped from `block.number` before mint.

### Impact Explanation
This falls under "treasury or reward payouts... must settle exactly once to the rightful beneficiary" — the pot is meant to go to a fairly, unpredictably chosen participant, but an unprivileged attacker can deterministically steer the payout to themselves, effectively stealing funds contributed by other ticket buyers. No malicious validator, collator, admin, or governance actor is required — only an ordinary signed account watching public chain state and timing a normal `buy_ticket` extrinsic.

### Likelihood Explanation
Likelihood depends on the `delay` configured by `ManagerOrigin` relative to `RANDOM_MATERIAL_LEN` (81 blocks). Because `start_lottery` performs no validation forcing `delay >= 81`, any manager who configures a short delay (including the default templates/tests, several of which use `delay = 5` or similar small values) creates this exploitable window. The bug is a pure logic/config gap in the pallet itself (missing the `known_since` check that its sibling `auctions` pallet already implements for the identical trait contract), not a hypothetical misuse — it is directly triggerable via public extrinsics.

### Recommendation
Mirror the pattern already used in `polkadot/runtime/common/src/auctions/mod.rs`: after calling `T::Randomness::random`, verify that the returned `known_since` is later than the last block at which a ticket could have been purchased (`config.start + config.length`). If not, defer the draw to a later block (re-poll `on_initialize`) instead of paying out immediately, and/or enforce a minimum `delay` in `start_lottery` tied to the configured `Randomness` implementation's determinism window.

### Proof of Concept
1. `ManagerOrigin` calls `start_lottery(price, length=20, delay=5, repeat=false)` at block `N` (start = `N`).
2. Ticket sales close at block `N+20`. Payout is triggered in `on_initialize` at block `N+25` (`delay=5`).
3. `RandomnessCollectiveFlip::random` at block `N+25` returns `known_since = N+25-81 = N-56`, which is *before* ticket sales even opened.
4. Any observer can, at any point during the sale window (e.g., at `N+19`), compute `T::Randomness::random(&(PalletId, seed).encode())` exactly as `generate_random_number` will at payout time (the underlying `RandomMaterial` inputs are already fixed and public), derive `winning_index = random_number % expected_total`.
5. The attacker waits until `TicketsCount::<T>::get() == winning_index`, then calls `buy_ticket`, causing `Tickets::<T>::insert(winning_index, attacker)`.
6. At payout, `choose_account()` resolves `Tickets::get(winning_index)` = attacker, and the full pot is transferred to them via `T::Currency::transfer(..., winner, lottery_balance, KeepAlive)`. [10](#0-9)

	fn random(subject: &[u8]) -> (T::Hash, BlockNumberFor<T>) {
		let block_number = frame_system::Pallet::<T>::block_number();
		let index = block_number_to_index::<T>(block_number);

		let hash_series = RandomMaterial::<T>::get();
		let seed = if !hash_series.is_empty() {
			// Always the case after block 1 is initialized.
			hash_series
				.iter()
				.cycle()
				.skip(index)
				.take(RANDOM_MATERIAL_LEN as usize)
				.enumerate()
				.map(|(i, h)| (i as i8, subject, h).using_encoded(T::Hashing::hash))
				.triplet_mix()
		} else {
			T::Hash::default()
		};

		(seed, block_number.saturating_sub(RANDOM_MATERIAL_LEN.into()))
	}
