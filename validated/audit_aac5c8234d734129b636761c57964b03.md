### Title
Unvalidated user-controlled array index in `ValidateMultiSign` precompile causes uncaught `ArrayIndexOutOfBoundsException` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The CVE describes a Linux RDMA bug where a user-supplied `port` value was used to index/derive a resource without validation, causing an OOB access and kernel oops. The analogous pattern exists in java-tron's `ValidateMultiSign` TVM precompile: a value fully controlled by the calldata of a `TriggerSmartContract` transaction is divided and used directly as an array index into the `words` array with no bounds check, **outside** of the method's own try/catch guard.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`: [1](#0-0) 

`words` is parsed directly from attacker-supplied `rawData` via `DataWord.parseArray(rawData)`. The expression `words[3].intValueSafe() / WORD_SIZE` is fully attacker-controlled (bounded only by `intValueSafe()`'s int range) and is used at line 1067 as an index into `words`:
```
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
```
and again at line 1073/1074 when calling `extractSigArray`/`extractBytesArray`. This access happens **before** the `try { ... } catch (Throwable t) { ... }` block that starts at line 1082 and wraps the rest of the logic (permission lookup, signature recovery, weight accounting). Because the OOB-prone index computation and access at lines 1066-1074 sit outside that try/catch, a crafted `words[3]` value that resolves to an index `>= words.length` (or negative) throws an uncaught `ArrayIndexOutOfBoundsException` from within `execute()`.

This mirrors the CVE's root cause exactly: a user-provided numeric value is used to compute an offset/index into an internal structure without validating it is within bounds, before any privileged/guarded logic runs.

### Impact Explanation
An uncaught runtime exception thrown from a precompiled contract's `execute()` during TVM execution is not the same category as a Solidity-level revert; whether it is swallowed higher up in `Program`/`VMActuator` or propagates further depends on code not shown in the retrieved context (I could not locate the exact call site in `Program.java` that invokes `PrecompiledContract.execute()` and its exception handling with the tools available, so I cannot fully confirm the downstream blast radius — this should be verified directly in the repository). At minimum, this is a reachable unhandled-exception path from an untrusted, single-transaction TVM call (any account can call `TriggerSmartContract` with calldata routed to precompile address for `ValidateMultiSign`), and, depending on how the caller handles the exception, could result in incorrect execution/energy accounting divergence between nodes (potential consensus impact) or an execution abort not going through the expected `Pair.of(true, DATA_FALSE)` failure path used elsewhere in the same method for malformed input.

### Likelihood Explanation
High reachability: the precompile is invoked from ordinary TVM contract execution reachable by any signed transaction from an unprivileged account (no special SR/witness/committee role needed). The vulnerable index computation depends solely on `words[3]`, a value taken straight from calldata with no length/bounds validation prior to use, unlike other parts of the same function that do check bounds (`signatures.length == 0 || signatures.length > MAX_SIZE`, `sigArraySize > MAX_SIZE`).

### Recommendation
Validate that `words.length > words[3].intValueSafe() / WORD_SIZE >= 0` (and that the resulting index plus any subsequent word reads stay within `words.length`) before dereferencing `words[...]` at line 1067 and before calling `extractSigArray`/`extractBytesArray` with that index. Move this bounds validation ahead of any array access, returning `Pair.of(false, EMPTY_BYTE_ARRAY)` on failure, consistent with the pattern already used for other malformed-input cases in this method (e.g., the `isValidAbiEncoding` check at line 1053-1056).

### Proof of Concept
1. Deploy or use any contract that calls the TVM `validatemultisig`/`ValidateMultiSign` precompile (energy-metered) via `TriggerSmartContract`.
2. Craft `rawData` such that `words[3]` (the 4th 32-byte word) decodes to a large integer (e.g., `0x7fffffff`), which after `intValueSafe() / WORD_SIZE` yields an index far beyond `words.length` (the actual parsed array from a short `rawData` payload).
3. Send the transaction; `DataWord.parseArray(rawData)` produces a short `words` array (based on actual calldata length), and the subsequent `words[oobIndex]` access at line 1067 throws `ArrayIndexOutOfBoundsException` outside of the method's own `try/catch(Throwable)` guard, before the account/permission logic executes.

Note: I was unable to trace the exact exception-propagation path from `PrecompiledContract.execute()` back through `Program.java`/`VMActuator` within the tool budget available, so the precise consensus/crash severity (versus a benign top-level catch converting this into a normal revert) should be confirmed by a follow-up code review of the precompile dispatch and exception handling in `actuator/src/main/java/org/tron/core/vm/program/Program.java`.
