### Title
`SignalPostReceiveReady` uses a non-unique, unscoped `transaction_id` to route hook completion signals across repositories - ([File: internal/gitaly/service/hook/signal_post_receive.go])

### Summary
`SignalPostReceiveReady` authorizes callers solely by checking that the RPC arrived over *some* established backchannel connection, and then dispatches the signal to a process-wide registry keyed only by a bare `uint64` transaction ID that is not bound to the specific Praefect instance, repository, or storage that owns that transaction.

### Finding Description
`SignalPostReceiveReady` is intended to let Praefect tell the primary Gitaly node that transaction coordination (DB update + replication enqueue) has finished for a specific push, so the blocked `post-receive` hook can proceed to call Rails: [1](#0-0) 

The only authorization check performed is that the request came in via a backchannel-established peer connection: [2](#0-1) 

`backchannel.GetPeerID` merely proves that *a* backchannel handshake occurred for the connection carrying the request — it does not verify that this particular backchannel/Praefect instance is the one that actually created the `transaction_id` being signaled: [3](#0-2) 

The signal is then dispatched purely by numeric ID, without checking `storage_name`, repository, or which Praefect/transaction manager minted the ID, to a single process-wide `PostReceiveRegistry`: [4](#0-3) [5](#0-4) 

The `transaction_id` field is documented as "the Praefect transaction ID that identifies the write operation" and is generated by Praefect's in-memory `transactions.Manager`, which is a simple atomic counter local to a single Praefect process, starting at 1 and reused after transactions are cleaned up: [6](#0-5) [7](#0-6) 

Because (a) this counter is per-Praefect-process and not globally unique across an HA Praefect deployment (multiple Praefect nodes each maintain their own sequence starting at 1), and (b) the `PostReceiveRegistry` on a Gitaly node is shared across all storages/repositories served by that node and keyed only by this bare integer, two unrelated pushes — potentially against different repositories, coordinated by different Praefect nodes — can be assigned the same `transaction_id`. `SignalPostReceiveReady`'s check does not distinguish which Praefect/transaction actually "owns" that ID; any backchannel-connected caller (any Praefect proxying any RPC to that Gitaly node) can invoke it with an arbitrary `transaction_id`, including one that happens to collide with, or be guessed to match, another concurrently-running push's transaction on the same Gitaly node.

This is the direct analog of the M02 report: a "transition" (here, a specific push's post-receive gate) is identified by a value (`transaction_id`) that does not uniquely and verifiably correspond to the actual instance/session that should be permitted to resolve it, allowing a legitimate signal/attestation for one transition to be misapplied to a different, unrelated one.

### Impact Explanation
An attacker who can trigger or influence a push to be routed through Praefect (i.e., an ordinary Gitaly/Praefect user driving pushes) — or a compromised/duplicated Praefect instance in an HA fleet — can send a `SignalPostReceiveReady` request with `post_transaction_failed=true` and a guessed/colliding `transaction_id`. Because the registry keys are unscoped 64-bit integers reused from small process-local counters, colliding IDs are plausible in busy or multi-Praefect deployments. This can:
- Cause an unrelated, legitimately succeeded push's `post-receive` hook to be told the transaction failed (`post_transaction_failed`), making `git-receive-pack` exit non-zero and preventing Rails from being notified of a write that did in fact complete — a correctness/DoS issue (stuck merge requests, missed notifications, inconsistent GitLab state).
- Conversely, prematurely or incorrectly unblock a `post-receive` hook waiting for a different (still in-flight) transaction, causing Rails to be called with a `post-receive` payload before Praefect's DB state is actually consistent for that push — reintroducing the exact race the whole `SignalPostReceiveReady`/`PostReceiveRegistry` mechanism was built to prevent.

### Likelihood Explanation
Exploitability depends on being able to reach `SignalPostReceiveReady` over a valid backchannel connection and knowing/guessing a `transaction_id` currently registered on the target Gitaly node. Since transaction IDs are small monotonically-increasing integers (not random, unlike the Praefect design doc's stated intent for "random ... to avoid collisions" — the actual implementation uses `atomic.AddUint64`), and are shared across all repositories/storages on that Gitaly node and independently sequenced per Praefect replica, collisions or trivial guesses (IDs are small, sequential, and observable via normal operation/log correlation) are realistic in any cluster with concurrent write traffic or more than one Praefect node.

### Recommendation
- Bind `SignalPostReceiveReady` authorization to the specific transaction: verify the calling backchannel/Praefect identity matches the Praefect that registered the corresponding `txinfo.Transaction` (e.g., store and check `BackchannelID`/peer ID alongside the transaction, not just "any backchannel peer").
- Scope the `PostReceiveRegistry` key by `(storage_name, repository, transaction_id)` rather than a bare `uint64`, and validate the request's `Repository`/`storage_name` against the registered waiter before signaling.
- Generate transaction IDs with sufficient entropy (as originally documented) or make them globally unique across an HA Praefect fleet (e.g., prefix with a Praefect instance/election-term identifier) instead of a simple locally-scoped atomic counter.

### Proof of Concept
1. Configure Praefect in HA mode with two Praefect replicas (or, on a single Praefect, exploit ID reuse after `cancelTransaction`/cleanup) fronting one Gitaly node hosting multiple repositories.
2. Issue two concurrent pushes: push A to `repo1` (coordinated by Praefect instance #1) and push B to `repo2` (coordinated by Praefect instance #2, or a later transaction on the same instance after wraparound/ID reuse), such that both are assigned the same numeric `transaction_id` in their respective `transactions.Manager` sequence.
3. While push A's `post-receive` hook is blocked in `PostReceiveRegistry.RegisterWaiter` waiting on that ID, cause (or, as a malicious Praefect, directly send) a `SignalPostReceiveReady` call for that `transaction_id` with `post_transaction_failed=true`, originating from Praefect instance #2's backchannel connection to the shared Gitaly node.
4. Observe that Gitaly's `postReceiveRegistry.Signal` (`internal/gitaly/hook/postreceive_registry.go`) delivers the failure to push A's waiter — despite the signal actually pertaining to push B's (or an attacker-controlled) transaction — causing push A's `post-receive` hook to fail even though its own transaction succeeded.

```go
// SignalPostReceiveReady signals that Praefect has completed transaction coordination
// and the PostReceiveHook can proceed with calling Rails. This RPC is only callable via
// Praefect's backchannel to prevent abuse.
func (s *server) SignalPostReceiveReady(
	ctx context.Context,
	req *gitalypb.SignalPostReceiveReadyRequest,
) (*gitalypb.SignalPostReceiveReadyResponse, error) {
	// Validate that the request is coming via Praefect's backchannel.
	// This prevents external callers from unblocking arbitrary transactions.
	if _, err := backchannel.GetPeerID(ctx); err != nil {
		return nil, structerr.NewPermissionDenied("SignalPostReceiveReady can only be called via Praefect backchannel")
	}

	// Validate transaction ID is non-zero to prevent abuse.
	if req.GetTransactionId() == 0 {
		return nil, structerr.NewInvalidArgument("transaction_id must be non-zero")
	}

	if s.postReceiveRegistry == nil {
		return &gitalypb.SignalPostReceiveReadyResponse{}, nil
	}

	var signalErr error
	if req.GetPostTransactionFailed() {
		signalErr = errors.New("Praefect post-transaction work failed")
	}
	s.postReceiveRegistry.Signal(req.GetTransactionId(), signalErr)

	return &gitalypb.SignalPostReceiveReadyResponse{}, nil
}
```

```go
func GetPeerID(ctx context.Context) (ID, error) {
	peerInfo, ok := peer.FromContext(ctx)
	if !ok {
		return 0, errors.New("no peer info in context")
	}

	wrapper, ok := peerInfo.AuthInfo.(interface{ peerID() ID })
	if !ok {
		return 0, ErrNonMultiplexedConnection
	}

	return wrapper.peerID(), nil
}
```

```go
func (r *PostReceiveRegistry) Signal(txID uint64, err error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	ch, ok := r.waiters[txID]
	if !ok {
		r.signaled[txID] = err
		return
	}

	select {
	case ch <- err:
	default:
		// Channel already has a value, nothing to do.
	}
}
```

```go
func (mgr *Manager) RegisterTransaction(ctx context.Context, voters []Voter, threshold uint) (Transaction, CancelFunc, error) {
	mgr.lock.Lock()
	defer mgr.lock.Unlock()

	transactionID := atomic.AddUint64(&mgr.idSequence, 1)

	transaction, err := newTransaction(transactionID, voters, threshold)
	if err != nil {
		return nil, nil, err
	}

	if _, ok := mgr.transactions[transactionID]; ok {
		return nil, nil, errors.New("transaction exists already")
	}
	mgr.transactions[transactionID] = transaction

	mgr.logger.WithFields(log.Fields{
		"transaction.id":     transactionID,
		"transaction.voters": voters,
	}).DebugContext(ctx, "RegisterTransaction")

	mgr.counterMetric.WithLabelValues("registered").Add(float64(len(voters)))

	return transaction, func() error {
		return mgr.cancelTransaction(ctx, transaction)
	}, nil
}
```

```text
// SignalPostReceiveReadyRequest is the request for the SignalPostReceiveReady RPC.
message SignalPostReceiveReadyRequest {
  // storage_name is the name of the storage containing the repository.
  string storage_name = 1 [(storage)=true];
  // transaction_id is the Praefect transaction ID that identifies the write operation.
  // This corresponds to the transaction ID from the HooksPayload.Transaction.ID field.
  uint64 transaction_id = 2;
  // post_transaction_failed indicates that Praefect failed to complete post-transaction
  // work (database update and replication job enqueueing) after the transaction was
  // committed. When true, the PostReceiveHook should fail so that git-receive-pack
  // exits non-zero, preventing Rails from acting on a write that is not yet reflected
  // in Praefect's routing state.
  bool post_transaction_failed = 3;
}
```
