### Title
Handshake/HandshakeAccept Replay Enables Cross-Connection Peer Identity Spoofing - (File: stackslib/src/net/codec.rs, stackslib/src/net/chat.rs)

### Summary
`StacksMessage::verify_secp256k1` (codec.rs:1487-1502) verifies the preamble signature against whatever public key is handed to it, and `ConversationP2P::validate_handshake`'s `None` branch passes the attacker-controlled `handshake_data.node_public_key` taken from the message payload itself when the local connection has no previously-bound key. Because the signed bytes (`relayers` + `payload`) are never bound to a session nonce or to the socket the message arrives on, a byte-for-byte capture-and-replay of any legitimate signed `Handshake`/`HandshakeAccept` obtained from peer B (e.g. by simply connecting to B directly) can be replayed onto an unrelated connection C to victim A, causing A to bind peer B's public key to the attacker's own connection.

### Finding Description
`verify_secp256k1` only checks that `self.preamble.signature` is a valid secp256k1 signature over `consensus_serialize(relayers) || consensus_serialize(payload)` under the supplied `public_key` parameter [1](#0-0) . It has no notion of *which* TCP connection or session the message arrived on, and no challenge/nonce is mixed into the signed bytes.

`validate_handshake`, when `self.connection.get_public_key()` is `None` (the state of a brand-new, not-yet-authenticated connection), calls this verification using `handshake_data.node_public_key` — a value the sender embeds in the payload it is signing, i.e. attacker-supplied on the wire. Since the equality being enforced is only "does *some* signature over these bytes verify under *this claimed* key," and not "is this signature bound to *this* TCP session," any previously captured, validly-signed `Handshake`/`HandshakeAccept` from peer B verifies identically no matter which connection it is replayed on.

Exploit flow (no MITM or eavesdropping required):
1. Attacker opens its own ordinary connection to peer B and performs a normal handshake; B replies with a legitimately signed `HandshakeAccept` (or attacker inspects the `Handshake` it can obtain from B directly since B's messages are not secret to a connecting peer).
2. Attacker opens a new connection C to victim node A (whose connection state also starts with `public_key = None`).
3. Attacker replays B's captured signed message verbatim over connection C.
4. `validate_handshake`'s `None` branch verifies the signature against `handshake_data.node_public_key` (B's key, embedded in the replayed payload) — which succeeds because the bytes are identical to what B originally signed.
5. Node A now associates connection C (attacker's socket) with peer B's public key/identity, despite the attacker never possessing B's private key.

### Impact Explanation
This breaks the intended invariant that a connection's bound public key corresponds to the entity that actually established and controls that TCP session. An attacker can impersonate any peer B whose signed handshake traffic it can obtain (trivially, by connecting to B itself) toward a victim node A, poisoning A's neighbor/frontier state to associate B's identity/public-key-hash with the attacker's own address. This is a remote, unauthenticated identity/auth-bypass primitive matching the "Critical - auth bypass" category, and is repeatable against any reachable node and any peer whose handshake can be captured.

### Likelihood Explanation
- Attacker only needs the ability to connect to two P2P ports: the peer being impersonated (B) and the victim (A) — both ordinary, unprivileged remote actions.
- No secret keys, admin roles, or physical/local access are required.
- The victim connection must be new/unauthenticated (`get_public_key() == None`), which is the default state for any freshly dialed or inbound connection before a handshake completes — a common, easily reachable state.
- Replay must happen before chain-height/preamble staleness checks (if any) reject the message as stale, but the attacker fully controls timing of step 3 immediately after step 1, making the window trivial to hit.

### Recommendation
Bind the handshake signature to the specific session: include a server-issued random nonce/challenge (or at minimum bind the signed bytes to the specific socket/connection instance, e.g. via a fresh per-connection challenge that must be echoed and signed) so that a signature captured from one connection cannot be replayed to authenticate a different connection. Do not derive the verification key solely from attacker-supplied payload fields without additional session-binding proof of freshness.

### Proof of Concept
Rust test plan in `stackslib::net::chat` test module:
1. Build `ConvoA <-> PeerB`: perform a real handshake so `ConvoA` produces a valid, fully signed `StacksMessage::Handshake` (or `HandshakeAccept`) signed by `PeerB`'s private key, capturing the raw serialized bytes.
2. Construct a fresh `ConvoC` with `self.connection.get_public_key() == None`, representing a brand-new connection dialed by the attacker to victim node A.
3. Deserialize the captured bytes into a `StacksMessage` and feed them directly into `ConvoC.validate_handshake(...)` (or the equivalent `chat_message`/`handle_handshake` entry point) without modification.
4. Assert that `validate_handshake` returns `Ok(...)` and that `ConvoC`'s bound public key equals `PeerB`'s public key — demonstrating that `ConvoC` (which never possesses `PeerB`'s private key and never dialed `PeerB`) is bound to `PeerB`'s identity purely via replay, proving the cross-connection identity-binding break at `verify_secp256k1` (codec.rs:1491-1502) / `validate_handshake` (chat.rs).

    pub fn verify_secp256k1(&self, public_key: &StacksPublicKeyBuffer) -> Result<(), net_error> {
        let secp256k1_pubkey = public_key
            .to_public_key()
            .map_err(|e| net_error::DeserializeError(e.into()))?;

        let mut message_bits = vec![];
        self.relayers.consensus_serialize(&mut message_bits)?;
        self.payload.consensus_serialize(&mut message_bits)?;

        let mut p = self.preamble.clone();
        p.verify(&message_bits, &secp256k1_pubkey).map(|_m| ())
    }
