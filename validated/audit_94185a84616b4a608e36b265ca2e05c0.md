### Title
`remove_account` fails to purge `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` trie rows on `DeleteAccount`, orphaning stale receipt state that resurfaces if the account name is reused - (File: core/store/src/utils/mod.rs)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys/gas-key nonces, and `TrieKey::ContractData` entries for the deleted account. It never scans for or removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` rows keyed by the same `receiver_id`, so a postponed multi-data-dependency receipt addressed to that account survives account deletion.

### Finding Description
When a `FunctionCall` triggers a promise with multiple `input_data_ids` (e.g. `promise_and`/multiple `DataReceipt` dependencies) and only some of the corresponding `DataReceipt`s are delivered, the runtime persists the pending action receipt under `TrieKey::PostponedReceipt { receiver_id, receipt_id }`, tracks the outstanding count under `TrieKey::PendingDataCount { receiver_id, receipt_id }`, and indexes each outstanding dependency under `TrieKey::PostponedReceiptId { receiver_id, data_id }` — these keys are constructed and consumed in the postponed-receipt handling logic in `runtime/runtime/src/lib.rs` and defined in `core/primitives/src/trie_key.rs`.

`remove_account`, invoked from `action_delete_account` in `runtime/runtime/src/actions.rs` when the account owner submits `DeleteAccount`, only performs cleanup for: [1](#0-0) 
access keys and gas key nonces via prefix iteration: [2](#0-1) 
and contract data via prefix iteration: [3](#0-2) 

There is no prefix iteration or removal call touching `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` for `account_id`. Since `DeleteAccount` action processing does not check for or block on outstanding postponed receipts targeting the account (no such check exists in `action_delete_account`/`remove_account`), the account can be deleted while these rows remain in the trie, keyed by the (still valid, since it's just a string) `receiver_id`. If the account name is subsequently re-created via `CreateAccount` by any funder, these orphaned trie entries remain associated with the new account's namespace. Because `TrieKey` variants for postponed receipts are keyed purely by `receiver_id` (an `AccountId` string) rather than any per-incarnation identifier, there is no natural invalidation mechanism when an account is deleted and recreated.

### Impact Explanation
This falls under state-root divergence / orphaned trie state risk on account teardown, matching the "state-root divergence and chain split" bounty category if it can be shown to cause consensus-relevant divergent behavior (e.g., a later-delivered `DataReceipt` for the stale `data_id` triggering resumption of a stale postponed receipt against the new account's incarnation, executing with unexpected state/gas parameters, or contributing to `TrieUpdate` key sets that differ from expectations). At minimum it is a storage-hygiene/state-conservation violation: value is not fully conserved on `DeleteAccount`, and orphaned keys persist under the account's namespace.

### Likelihood Explanation
Preconditions are achievable entirely by an unprivileged attacker: create an account, issue a `FunctionCall` that generates a two-dependency promise, get only one of the two `DataReceipt`s delivered (achievable by controlling contract logic scheduling call dependencies asymmetrically), then call `DeleteAccount` as the account owner. No validator/node access, no special permission beyond normal transaction signing, is required. The scenario is fully repeatable.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also prefix-iterate and remove `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries for `account_id`, analogous to the existing access-key and contract-data cleanup loops, using the corresponding `trie_key_parsers` prefix helpers (adding one if it does not already exist for these key variants).

### Proof of Concept
Unit test on `remove_account` in `core/store/src/utils/mod.rs`:
1. Build a `TrieUpdate`, call `set_postponed_receipt` for a receipt addressed to account `"a.test.near"`, and directly `set`/write a `TrieKey::PendingDataCount` and a `TrieKey::PostponedReceiptId` entry for the same `receiver_id`/`receipt_id`/`data_id` (mirroring what `runtime/runtime/src/lib.rs` does when postponing a receipt).
2. Call `set_account` to create the account, then call `remove_account(&mut state_update, &account_id)`.
3. Commit the `TrieUpdate` and assert: `get_postponed_receipt(...)`, `get::<u32>(&TrieKey::PendingDataCount {...})`, and `get::<CryptoHash>(&TrieKey::PostponedReceiptId {...})` all still return `Some(..)` after `remove_account`, proving these rows are not cleaned up — demonstrating the asymmetry between what is written during postponement and what is removed on account deletion.

Note: I was unable to fully trace the exact byte-level `TrieKey` variants/fields for `PendingDataCount` and `PostponedReceiptId` (definitions live in `core/primitives/src/trie_key.rs`, which I located but did not fully read) and the exact call sites in `runtime/runtime/src/lib.rs`/`action_delete_account` in `runtime/runtime/src/actions.rs`; a full confirmation of downstream consequences (e.g., whether the resumed receipt after re-creation actually executes with corrupted state, and whether this is consensus-relevant) would require reading those files directly.
