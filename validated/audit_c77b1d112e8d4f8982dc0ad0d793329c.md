Found it. There is an explicit protocol-level `actor_id`/`account_id` check that prevents exactly this attack.

`check_actor_permissions` in `runtime/runtime/src/actions.rs:739-760` requires, for `Action::AddKey` (as well as `DeployContract`, `Stake`, `DeleteKey`, `DeployGlobalContract`, `UseGlobalContract`, `WithdrawFromGasKey`), that `actor_id == account_id`, i.e. that the entity acting on the receipt equals the receiver of the receipt — otherwise it returns `ActionErrorKind::ActorNoPermission`. [1](#0-0) 

This check is run inside `apply_action` (`runtime/runtime/src/lib.rs:564-567`) *before* any action (including `AddKey`) is dispatched to its handler, for every receipt regardless of how it was generated (signed transaction or promise-batch action created by a contract). [2](#0-1) 

For a receipt sent from A to B via `promise_batch_create(B)` where `sir == false`, `actor_id` is initialized to the receipt's `predecessor_id` (A), not the receiver B, unless the receipt's first action is `CreateAccount` (which flips `actor_id` to the receiver, granting the sender temporary permission over the *newly created* account only, per the documented rule in `docs/RuntimeSpec/Actions.md:26-35`). Since B already exists and A did not include a `CreateAccount` action against B (nor could it — `CreateAccount` on an existing account fails with `AccountAlreadyExists`, `runtime/runtime/src/actions.rs:787-801`), `actor_id` remains A while `account_id` is B, so `check_actor_permissions` immediately fails with `ActorNoPermission` and the `AddKey` action never executes; the whole receipt is rolled back per the atomicity model. [3](#0-2) 

The `append_action_add_key_with_function_call` host function (`runtime/runtime/src/receipt_manager.rs` and `logic.rs:3492-3538`) itself performs no authorization check when appending — that part of the audit premise is correct — but authorization is enforced later, deterministically, at receipt-apply time via `check_actor_permissions`, exactly matching the required PoC pattern ("AddKey action is only ever executed against the receiver_id... and rejected until the receipt actually executes"). There is existing test coverage of this actor-permission model (e.g. `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` explicitly notes `check_actor_permissions` gating self-only actions, `runtime/runtime/src/tests/apply.rs:4877-4886`), and the deterministic-account-id path even has an explicit design comment about preventing exactly this kind of hijack (`runtime/runtime/src/deterministic_account_id.rs:100-105`). [4](#0-3)

```rust
pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
```

**File:** docs/RuntimeSpec/Actions.md (L26-35)
```markdown
For the following actions, `predecessor_id` and `receiver_id` are required to be equal:

- `DeployContract`
- `Stake`
- `AddKey`
- `DeleteKey`
- `DeleteAccount`

NOTE: if the first action in the action list is `CreateAccount`, `predecessor_id` becomes `receiver_id`
for the rest of the actions until `DeleteAccount`. This gives permission by another account to act on the newly created account.
```

```rust
pub(crate) fn create_deterministic_account(
    initial_balance: Balance,
    storage_usage_config: &StorageUsageConfig,
) -> Account {
    // Unlike `CreateAccount`, this account creation does not change
    // actor_id. This is important to prevent hijacking the account.
    // Actor id remains the predecessor, so any actions following will
    // be checked against that for actor permissions, preventing
    // `AddKey`, `DeployContract`, or any other actions that only the
    // account owner is permitted to do.
    Account::new(
        initial_balance,
        Balance::ZERO,
        AccountContract::None,
        storage_usage_config.num_bytes_account,
    )
}
```
