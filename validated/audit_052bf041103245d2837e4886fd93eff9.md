### Title
Attacker can fill a victim's per-account token list via dust `DepositToken` transfers, blocking new borrows and deposits - (File: contracts/Pool.sol)

### Summary
`Pool` caps the combined size of `debtTokensOfAccount` + `depositTokensOfAccount` at `MAX_TOKENS_PER_USER = 30` via `onlyIfAdditionWillNotReachMaxTokens`. Because `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance moves from 0, an unprivileged attacker can push dust amounts of every listed deposit token to any victim, filling their token list. Once the combined list length reaches 30, any action that would add a *new* token to the victim's list reverts with `UserReachedMaxTokens`.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` are guarded by `onlyIfAdditionWillNotReachMaxTokens`, reverting when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`.
- `DepositToken._transfer` (called by public `transfer`/`transferFrom`/`seize`) adds the token to the recipient's list on first receipt. There is no opt-out or minimum-amount check; a 1-wei dust transfer occupies a slot.
- DebtToken minting (`issue`/`mint` via `DebtToken._beforeTokenTransfer` → `Pool.addToDebtTokensOfAccount`) reverts once the victim's list is full, so `Pool.mint`/`SmartFarmingManager.leverage` for any synthetic the victim doesn't already hold will revert.
- `DepositToken.deposit(amount, onBehalfOf=victim)` for a collateral the victim doesn't hold also reverts, as does any `seize`/`transfer` delivering a new token type to the victim.

### Impact Explanation
Liveness / temporary freezing: the victim cannot borrow any new synthetic asset, cannot receive new collateral types (including liquidation proceeds routed to them), and cannot have deposits made on their behalf — until they detect the attack and manually clear slots by transferring dust tokens to another address (removal happens automatically when the balance hits 0 in `_transfer`). Existing collateral remains withdrawable, so this is a temporary availability/DoS condition rather than permanent loss, but it can be re-applied cheaply and repeatedly (persistent griefing), and it can be timed to block a user racing to add collateral-backed debt operations.

### Likelihood Explanation
Requires only that the attacker holds dust balances of the pool's listed deposit tokens (obtainable by depositing a minimal amount of each underlying once) plus ~30 public `transfer` calls. No privileged role, oracle manipulation, or governance action needed. The attack is bounded by the number of whitelisted deposit tokens in the pool; if the pool lists ≥30 deposit tokens, an attacker alone can fill the list entirely; otherwise debt tokens the victim already holds contribute to the count. Cost per grief round is just gas.

### Recommendation
- Only count tokens that represent a meaningful position (e.g., skip adding or auto-remove below a dust threshold), or
- Allow the account (or anyone) to call a `removeFromDepositTokensOfAccount`-style cleanup, or
- Make `addToDepositTokensOfAccount` on transfer tolerant: if the list is full, revert only the *add*, not the whole transfer — or better, give users a `disableTransferIn`-style opt-out / pull-based claim model so unsolicited dust cannot occupy list slots.
