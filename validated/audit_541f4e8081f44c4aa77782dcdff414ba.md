### Title
Unbounded array allocation from unvalidated ABI length field in `ValidateMultiSign` precompile causes OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompile (and, on the legacy code path, `BatchValidateSign`) decodes an attacker-controlled 256-bit word from the smart-contract call data and uses it directly as the size of a Java array allocation, with no upper bound, before any signature-count guard is applied. This is the same bug class as CVE-2021-34268 (parsing an untrusted length field from a malformed packet without bounds checking, leading to a crash/DoS), transplanted to java-tron's calldata parser for a broadcastable `TriggerSmartContract` transaction.

### Finding Description
`extractBytesArray()` reads a length word from the parsed ABI words and immediately allocates an array of that size: [1](#0-0) 

This helper is invoked from `ValidateMultiSign.execute()`: [2](#0-1) 

Crucially, the size guard (`sigArraySize > MAX_SIZE`) is only applied on the `extractSigArray` branch, which is taken only `if (VMConfig.allowTvmSelfdestructRestriction())`. When that feature flag is not the active branch, `extractBytesArray` is called directly with no bound on `len`, which is read via `intValueSafe()`: [3](#0-2) 

`intValueSafe()` only saturates on 4-byte overflow (`Integer.MAX_VALUE`); any value that fits in 4 bytes (e.g., hundreds of millions) is returned verbatim and is *not* bounded by the actual length of the call data — the length word is just an arbitrary 32-byte value chosen by the caller at a caller-controlled offset. The energy charged for the call (`getEnergyForData`) is based only on `data.length`, not on the decoded length value, so the cost of triggering a huge `new byte[len][]` allocation is decoupled from its actual resource cost: [4](#0-3) 

The resulting `OutOfMemoryError` is an `Error`, not a `RuntimeException`. `VM.play()`'s exception handling only catches `RuntimeException` and `StackOverflowError`, not arbitrary `Error`s: [5](#0-4) 

It is only contained one layer further up, in `VMActuator.execute()`'s generic `catch (Throwable e)`: [6](#0-5) 

By contrast, `BatchValidateSign.execute()` wraps its entire body (including the equivalent unguarded `extractBytesArray` call) in a top-level `catch (Throwable t)`, which is a stronger mitigation: [7](#0-6) 

### Impact Explanation
Even though `VMActuator` ultimately catches the `Throwable`, the attempted allocation of a very large `byte[][]` (potentially hundreds of millions of elements, ~1-2GB+ of reference-array memory alone before individual element copies even begin) can trigger real GC pressure/OOM churn on the node process. This can be repeated cheaply and in parallel (many transactions/blocks calling the same precompile), degrading node memory availability and potentially destabilizing or crashing the JVM process for other unrelated transactions/services running in the same node — a resource-exhaustion DoS reachable by any account that can submit a `TriggerSmartContract` transaction. This maps to the CVE-2021-34268 bug class: parsing a length/size field from untrusted input without a sanity bound, leading to a crash/DoS condition.

### Likelihood Explanation
The vulnerable `extractBytesArray` path in `ValidateMultiSign`/legacy `BatchValidateSign` is only reached when `VMConfig.allowTvmSelfdestructRestriction()` returns `false` for the transaction being executed (i.e., before that specific hardening feature is activated on the chain, or during processing of historical blocks predating its activation). When the flag is active, `extractSigArray` is used instead and is properly bounded by the `sigArraySize > MAX_SIZE` check beforehand. This makes exploitability conditional on chain configuration/version rather than universal on every deployment — reducing but not eliminating likelihood, since older/un-upgraded networks, private forks, or replay of pre-activation blocks would still be exposed. The `BatchValidateSign` path is comparatively safer thanks to its top-level `Throwable` catch.

### Recommendation
- Add an explicit upper bound check on the length value read for `extractBytesArray()` (and `extractBytes32Array()`), mirroring the `MAX_SIZE` check already used for `extractSigArray`, regardless of the `allowTvmSelfdestructRestriction()` flag.
- Wrap `ValidateMultiSign.execute()`'s entire body in a top-level `catch (Throwable t)` similar to `BatchValidateSign.execute()`, so that any parsing-related `Error` is safely contained at the precompile boundary instead of relying on `VMActuator`.
- Consider tying the energy cost of these precompiles to the decoded array-length fields, not just `data.length`, so that an attacker cannot decouple execution cost from claimed array sizes.

### Proof of Concept
Construct calldata for `ValidateMultiSign` (or the legacy `BatchValidateSign` path) with a small overall byte length (few ABI head words) but with the signature-count word (the word pointed to by the offset word, e.g. `words[3]`) set to a large value that fits in 4 bytes (e.g. `0x0BEBC200` = 200,000,000), while `VMConfig.allowTvmSelfdestructRestriction()` is not active for that execution context:
1. Deploy/call a contract that performs a `CALL` to the `ValidateMultiSign` precompile address with the crafted calldata.
2. `extractBytesArray()` executes `new byte[200000000][]`, immediately attempting a large allocation regardless of the small calldata size/energy charged.
3. Observe `OutOfMemoryError` thrown mid-execution, propagating past `VM.play()`'s `RuntimeException`/`StackOverflowError`-only catch, only caught generically at `VMActuator.execute()`, after the allocation attempt has already stressed the JVM heap.

Note: full confirmation that `allowTvmSelfdestructRestriction()` is disabled on any currently-live java-tron network (mainnet/testnet) could not be verified from the indexed code alone; a Devin session with full repo/config access would be needed to check activation status across networks (`DynamicPropertiesStore`/`ProposalUtil`) before treating this as unconditionally exploitable today.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
