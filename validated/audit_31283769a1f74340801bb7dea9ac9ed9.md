### Title
Replay window check-then-act race lets a captured packet be decrypted and delivered twice - ([File: connection_state.go])

### Summary
`ConnectionState.Decrypt` (and its sibling `VerifyRelay`) implement replay protection with a classic check-then-act split: the anti-replay `window.Check` is taken and released under `decryptLock`, the (expensive, unlocked) AEAD decrypt runs, and only afterward is `window.Update` taken to actually record the counter as seen. This is structurally the same root-cause shape as the reported `LineOfCredit._close` bug: the state mutation that is supposed to prevent reuse (`credits[id]` deletion / here, marking a counter as consumed in the replay window) happens *after* the sensitive, reentrant-prone action (token transfer / here, AEAD decrypt and delivery), leaving a window in which the same input can be processed more than once before the guard is committed.

### Finding Description
`Decrypt` and `VerifyRelay` in `connection_state.go` both follow this pattern: [1](#0-0) 

1. `cs.decryptLock.Lock(); result := cs.window.Check(...); cs.decryptLock.Unlock()` — the lock is dropped immediately after the *read-only* replay check.
2. `cs.dKey.DecryptDanger(...)` — the AEAD decryption, which is comparatively expensive, runs entirely **without holding the lock**.
3. Only after decryption succeeds is `cs.decryptLock` re-taken and `cs.window.Update(...)` called to actually mark the counter as consumed.

Because the lock is released between step 1 and step 3, two goroutines invoking `Decrypt` concurrently for the *same* `messageCounter` (e.g. from two UDP read queues delivering the same captured packet, or from an on-path attacker replaying a single sniffed ciphertext packet twice in quick succession) can both pass `window.Check` before either has called `window.Update`. Both will then proceed to decrypt and hand the plaintext up to `handleOutsideMessagePacket`/firewall/tun, i.e. the same message is processed twice, defeating the purpose of the replay window. This is invoked from `readOutsidePackets`, which is on the fully-unauthenticated inbound UDP path (reached before/without any additional per-packet authentication beyond the AEAD tag itself), and the relay variant `VerifyRelay` is reachable by an attacker replaying frames toward a relay node (the e2e test `TestRelayReplayProtection` explicitly documents a historical bug in this exact area: a relay authenticated a frame but "never advanced the replay window"). [2](#0-1) [3](#0-2) 

The `Bits.Check`/`Bits.Update` split itself is documented as needing external locking for correctness ("Lock replay window updates so concurrent readers can't corrupt it" — CHANGELOG #1802), which confirms the bits structure is not safe against interleaved check/act across a decrypt boundary; the current code only serializes the two halves individually, not the whole check-decrypt-update sequence. [4](#0-3) [5](#0-4) 

### Impact Explanation
An attacker capable of capturing/replaying a single ciphertext packet on the wire (no valid certificate required — this is pure packet replay against an already-established tunnel) can cause the same application-layer packet to be delivered twice through the tunnel to the tun device / firewall, i.e. a traffic-replay bypass of the anti-replay window. Depending on the payload this can duplicate side-effecting traffic (e.g. non-idempotent application requests) that the replay window is specifically designed to prevent. This lands in the "traffic decryption/forgery/replay" impact bucket called out in scope.

### Likelihood Explanation
Exploitation requires winning a narrow race: the attacker must get two copies of the identical captured packet processed concurrently by the receiver (e.g., by sending it twice back-to-back so both land in different UDP-read/decrypt goroutines before either finishes). This is plausible on a busy multi-worker packet-processing path but timing-dependent, so likelihood is Medium rather than trivially reliable, and it is weaker than the original smart-contract bug (which was deterministically triggerable via a callback). No malicious peer certificate or lighthouse trust is required — only network-level packet capture/replay capability against an existing session.

### Recommendation
Hold `decryptLock` for the entire check → decrypt → update sequence (or use a CAS-style "reserve" step in `Bits` that atomically marks the counter as claimed before decrypting, rolling back only the "seen" bit — not the reject decision — if decryption fails). Concretely, move `cs.window.Update` (or an atomic "claim" primitive) before/around `DecryptDanger`, or protect the whole `Decrypt`/`VerifyRelay` body with a single lock acquisition so no other goroutine can observe an intermediate state where a counter has been checked but not yet committed.

### Proof of Concept
Conceptual PoC (network-level, not exact code since exploitation depends on Nebula's internal queue scheduling, which I could not fully verify was multi-worker from the available index):
1. Establish a normal Nebula tunnel between two nodes.
2. Capture one valid encrypted data packet (a specific `messageCounter`) sent by the initiator.
3. Immediately re-inject two copies of that identical UDP packet to the responder in rapid succession (ideally via two different sockets/threads so the OS/its receive path can schedule them onto separate goroutines before either completes `Decrypt`).
4. If both copies pass `window.Check` before either reaches `window.Update`, both are decrypted and delivered to the tun device — observable as the underlying application receiving the same payload twice, and/or as no `dupeCounter` increment despite two writes to `f.readers[q].Write(out)`.

Note: I was not able to fully confirm from the indexed code how many concurrent goroutines can call `Decrypt` for a single `HostInfo` from the UDP receive path (multi-queue setup in `interface.go`); if only a single goroutine ever calls `Decrypt` per hostinfo, this race would not be exploitable in practice and would need verification with full repository access.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

// Check returns true if i is within (or way out in front of) the window, and not a replay
func (b *Bits) Check(l *slog.Logger, i uint64) bool {
	// If i is the next number, return true.
	if i > b.current {
		return true
	}

	if b.strictlyWithinWindow(i) {
		return !b.get(i)
	}

	// Not within the window
	if l.Enabled(context.Background(), slog.LevelDebug) {
		l.Debug("rejected a packet (top)", "current", b.current, "incoming", i)
	}
	return false
}
