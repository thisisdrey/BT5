### Title
Missing bounds validation on ZIP64 extra-field lengths in central directory parsing enables out-of-bounds reads from an attacker-supplied archive - (File: third_party/ijar/zip.cc)

### Summary
The audit finding is about `LicenseFee` lacking a `maxLicenseFee` cap, so an out-of-range value flows unchecked into arithmetic and causes over/underflow. The closest analog in this codebase is `InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc`, which reads attacker-controlled 16-bit length fields (`extra_field_length`, `file_comment_length`) and a ZIP64 extra-field `data_size` from a central directory entry with **no upper-bound/cap check** against the remaining buffer size, unlike the sibling local-file-header parser which explicitly calls `EnsureRemaining()` before every variable-length read.

### Finding Description
`InputZipFile::ProcessLocalFileEntry` (used when parsing local file headers) is careful: every variable-length field is validated with `EnsureRemaining(n, state)` before being consumed: [1](#0-0) 

By contrast, `InputZipFile::ProcessCentralDirEntry`, which walks the central directory (a structure whose location/size, `cen_offset`/`cen_size`, is itself taken from the end-of-central-directory record of the input file), reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly off the wire and then advances the cursor `p` by these attacker-supplied 16-bit values with **no call to `EnsureRemaining`** anywhere in this function: [2](#0-1) 

Worse, inside the extra-field loop it reads a 16-bit `header_id`/`data_size` pair and, for the ZIP64 tag, unconditionally calls `get_u8le(extra)` three times (for uncompressed size, compressed size, and offset) without checking that `data_size` is actually large enough (24 bytes) to contain those three 8-byte quantities, and without checking that `extra_p + data_size` (or the subsequent 8-byte reads) stays within the mapped file: [3](#0-2) 

This is structurally the same bug class as the `LicenseFee` finding: a numeric field taken from untrusted input (`extra_field_length`/ZIP64 `data_size`) is used directly to drive pointer arithmetic and buffer reads with no minimum/maximum bound ("cap") enforced, so a value crafted to be inconsistent with the actual remaining data causes the parser to read past the end of the mapped input file (`zipdata_in_`).

### Impact Explanation
`third_party/ijar` is Bazel's bundled zip/jar reader; `zip.cc`'s `InputZipFile` is used both by the ijar tool and by `src/main/cpp/archive_utils.cc`'s `PartialZipExtractor` (`ZipExtractor::Create`) to scan Bazel's own self-extracting install archive and to process zip-format inputs, i.e., it processes bytes originating from a file that is not root-repo-trusted Starlark. An attacker who can supply or tamper with a zip/jar-formatted file consumed by this code path (e.g., a hostile archive served at a fetch URL, or a corrupted/crafted `.zip`) can control `extra_field_length`, `file_comment_length`, and the ZIP64 extra-field `data_size` to make the parser read bytes beyond the mmap'd input buffer. This is an out-of-bounds read (potential crash / information disclosure of adjacent process memory), reached purely by supplying hostile archive bytes, matching the "missing cap → OOB/overflow" bug class from the report, without requiring any local machine or credential access.

### Likelihood Explanation
Likelihood is moderate: the vulnerable path is invoked whenever a zip/jar file with a crafted central directory is processed by `InputZipFile`. Because `EnsureRemaining` is used pervasively elsewhere in the same file (including in the local-header parser and `SkipFile`), its conspicuous absence in `ProcessCentralDirEntry`'s field-length handling and ZIP64 extra-field parsing indicates a genuine oversight rather than an intentionally-relaxed path. Exploitability depends on whether the central directory offset/size (`cen_offset`/`cen_size`) taken from the EOCD record are themselves validated against the file length elsewhere in `Open()`; I was not able to confirm this within the available tool budget — the `Open()` implementation and EOCD-record validation logic were not fully retrieved, so it is uncertain whether an outer bound partially mitigates the unbounded reads inside `ProcessCentralDirEntry`. This should be verified in the full source before treating this as a confirmed exploitable OOB read.

### Recommendation
Add explicit bounds checks (analogous to `EnsureRemaining`) in `InputZipFile::ProcessCentralDirEntry`:
- Validate `file_name_length`, `extra_field_length`, and `file_comment_length` against the number of bytes remaining in `central_dir_`/`zipdata_in_` before advancing `p`.
- Before reading the ZIP64 extra field's `uncompressed_size`/`compressed_size`/`offset` via `get_u8le`, verify `data_size >= 24` (or the specific number of fields actually present) and that `extra + 24 <= extra_p + data_size <= p` (i.e., within the declared extra-field bounds and the file).
- Cap the central directory entry count/size derived from the EOCD/ZIP64 EOCD records against the actual mapped file length before iterating, so a malicious `cen_size`/`cen_offset` cannot cause iteration past the buffer.

### Proof of Concept
A concrete PoC would construct a minimal ZIP file whose central directory entry declares a ZIP64 extra field with `header_id = 0x0001` and `data_size` set to a value smaller than 24 (e.g., 4), while the file is truncated immediately after the extra field. Feeding this to `ZipExtractor::Create`/`ProcessAll` (e.g., via the `zip_main.cc` `extract` entry point or `PartialZipExtractor::UnzipUntil`) would cause `ProcessCentralDirEntry` to call `get_u8le` past the end of the extra field/file buffer. I could not build and run this PoC within the available tools; a `BuildIntegrationTestCase`/unit test exercising `InputZipFile` directly (mirroring existing tests in `third_party/ijar` test targets) with such a crafted byte buffer would be needed to confirm the out-of-bounds read empirically, and this should be prioritized as follow-up verification.
