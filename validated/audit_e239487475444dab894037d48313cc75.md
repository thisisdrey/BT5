### Title
Attacker can permanently block a victim from depositing/receiving new collateral types by filling the victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `deposit(onBehalfOf)` — (File: contracts/Pool.sol)

### Summary
Analogous to the Squid FTP DoS (an unauthenticated remote attacker causing denial of service through crafted input), an unprivileged attacker can deny service to any Metronome user by griefing the per-account token lists. `Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once `debtTokensOfAccount.length + depositTokensOfAccount.length >= MAX_TOKENS_PER_USER` (30), and `DepositToken._transfer`/`_mint` unconditionally push every token whose balance transitions 0 → >0 onto the victim's list. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `transfer`/`transferFrom` accept an arbitrary recipient, an attacker can force-fill a victim's list with dust amounts of every deposit token offered by the pool, after which any further deposit, transfer, or leverage operation that would register a new token for the victim reverts.

### Finding Description
- `Pool.sol` `onlyIfAdditionWillNotReachMaxTokens` (lines 143–148) reverts when the combined per-account lists reach `MAX_TOKENS_PER_USER` (line 79). The same modifier gates `addToDepositTokensOfAccount` (line 216) and `addToDebtTokensOfAccount` (line 204).
- `DepositToken._transfer` (lines 518–520) calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to positive — no opt-in from the recipient.
- `DepositToken._mint` (lines 485–488) does the same on deposit, and `deposit(amount_, onBehalfOf_)` (lines ~218–236) lets any caller mint msdTOKEN to an arbitrary `onBehalfOf_` address, pulling underlying only from the caller.
- Attack: the attacker deposits (or transfers) 1 wei of every deposit token listed in the pool to the victim. Each first-touch token appends to `depositTokensOfAccount[victim]`. Once the combined count hits 30, any subsequent deposit of a collateral type the victim does not already hold reverts inside `_mint` → `addToDepositTokensOfAccount`, and a flash-loan-assisted `SmartFarmingManager.leverage` using a new collateral type also reverts.
- The victim cannot clear slots cheaply: a slot is only freed when the balance returns exactly to 0 (`removeFromDepositTokensOfAccount`, lines 522–525), and the attacker can re-grief with a different dust amount or re-deposit after the victim withdraws, making the freeze repeatable.

### Impact Explanation
Temporary freezing of funds / forced liquidation. A user whose position becomes unhealthy cannot deposit a *new* collateral type to restore health — every rescue deposit into a token not already in their list reverts with `UserReachedMaxTokens`. Since Metronome positions are only top-up-able with collateral already held in the list, the victim is forced into liquidation that would otherwise have been avoidable. Smart-farming `leverage`/`flashRepay` flows and `NativeTokenGateway.deposit` (which routes through `DepositToken.deposit`) are blocked for the same reason. The attacker can keep the list saturated indefinitely at the cost of dust underlying, since re-filling a freed slot is trivial.

### Likelihood Explanation
Requires no privileged role, no oracle manipulation, and no capital beyond dust of each underlying token plus gas. Feasibility depends on the deployed pool offering enough distinct deposit tokens to reach the 30-slot combined cap (debt tokens cannot be pushed onto the victim, since they are minted only on the borrower's own action). On deployments with many whitelisted collaterals (e.g., mainnet/Optimism pools), the attack is fully reachable by any EOA. Cost scales linearly with the number of collateral types and must be repeated if the victim empties slots.

### Recommendation
- Do not let unsolicited transfers/deposits permanently occupy per-account slots: either revert `addTo*TokensOfAccount` only when the caller initiates the position change (i.e., skip list insertion for `transfer`-based receipt and let `debtPositionOf` derive collateral from balances), or allow list overflow to degrade gracefully (cap enforcement only on user-initiated deposits, not on inbound transfers).
- Alternatively, allow the account itself to force-remove a token from its list (e.g., a `Pool.leaveToken(token)` that requires zero balance) so griefed users can recover without relying on balance-zeroing through the attacker-controlled state.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.9;

import "forge-std/Test.sol";
import {Pool} from "contracts/Pool.sol";
import {IDepositToken} from "contracts/interfaces/IDepositToken.sol";
import {IERC20} from "contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract MaxTokensGriefTest is Test {
    Pool pool = Pool(POOL_ADDRESS);            // forked deployment
    address victim = address(0xBEEF);
    address attacker = address(0xA77AC);

    function test_GriefVictimTokenList() public {
        address[] memory dTokens = pool.getDepositTokens(); // all whitelisted DepositTokens
        uint256 need = pool.MAX_TOKENS_PER_USER()
            - pool.getDebtTokensOfAccount(victim).length
            - pool.getDepositTokensOfAccount(victim).length;
        require(dTokens.length >= need, "not enough collateral types");

        // 1) Attacker deposits 1 wei of each collateral on behalf of the victim
        for (uint256 i; i < need; ++i) {
            IDepositToken dt = IDepositToken(dTokens[i]);
            IERC20 underlying = IERC20(dt.underlying());
            deal(address(underlying), attacker, 1);
            vm.startPrank(attacker);
            underlying.approve(address(dt), 1);
            dt.deposit(1, victim); // public, arbitrary onBehalfOf_
            vm.stopPrank();
        }

        // 2) Victim's list is now full
        assertEq(
            pool.getDepositTokensOfAccount(victim).length
                + pool.getDebtTokensOfAccount(victim).length,
            pool.MAX_TOKENS_PER_USER()
        );

        // 3) Victim cannot deposit a collateral type not already in their list
        IDepositToken other = IDepositToken(dTokens[need]); // token victim does not hold
        IERC20 underlying2 = IERC20(other.underlying());
        deal(address(underlying2), victim, 100 ether);
        vm.startPrank(victim);
        underlying2.approve(address(other), 100 ether);
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        other.deposit(100 ether, victim);
        vm.stopPrank();
    }
}
```

Invariant broken: liveness — an unprivileged user can block another account's ability to add collateral, forcing liquidation and temporarily freezing the victim's position-management functions.
