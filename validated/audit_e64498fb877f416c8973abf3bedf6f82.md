Audit Report

## Title
`OutboundQueue::calculate_fee` can silently compute a zero remote relayer fee for valid, non-zero pricing parameters, letting senders queue Ethereum-bound messages without paying the relayer reward - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

## Summary
`Pallet::calculate_fee` [1](#0-0)  computes the fee a sender pays for Ethereum-bound message delivery through a chain of integer-division steps (`FixedU128::checked_div` by the exchange rate, then `convert_from_ether_decimals`'s `checked_div` by a decimals scaling factor) [2](#0-1) . `PricingParameters::validate` only rejects individually zero-valued fields and does not guard against combinations that truncate the remote fee to zero [3](#0-2) . The pallet's own regression test, `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero`, demonstrates this occurring with entirely non-zero parameters and flags the resulting `fee.remote == 0` in its own comment as "invalid... which should be avoided," yet no corresponding guard exists in production code [4](#0-3) .

## Finding Description
`SendMessage::validate` calls `calculate_fee(gas_used_at_most, T::PricingParameters::get())` and returns the ticket/fee pair without any check that `fee.remote != 0` [5](#0-4) , and `deliver` unconditionally enqueues the message into `T::MessageQueue` regardless of the fee value [6](#0-5) . `do_process_message` only checks the block message-count bound (`MaxMessagesPerBlock`), not fee validity, before appending the message to `Messages`/`MessageLeaves` for commitment to Ethereum [7](#0-6) . The only defense, `PricingParameters::validate`, checks each field individually for zero but not the derived, truncated remote-fee outcome [3](#0-2) .

## Impact Explanation
This is reachable by any sibling parachain sending XCM through the Snowbridge exporter whenever the applicable command's `GasMeter::maximum_gas_used_at_most` combined with governance-set pricing parameters produces a sub-unit remote fee, matching the accepted impact category of public underpriced work degrading bridge processing: messages consume the bounded `MaxMessagesPerBlock` capacity and merkle-commitment machinery while contributing `reward: 0` to relayers, giving relayers no incentive to deliver them, which can leave such messages unrelayed and stall throughput for legitimately-priced traffic [8](#0-7) .

## Likelihood Explanation
The pallet's own test proves the truncation occurs with simple, fully valid (non-zero) parameter values (`exchange_rate=1/1`, `fee_per_gas=1`, `reward=1`, `gas_used=250000` → `fee.remote=0`) [4](#0-3) . In practice, `fee_per_gas` reflects real Ethereum gas prices (commonly gwei-scale, i.e., ~10^9–10^10 wei) and `ConstantGasMeter::maximum_dispatch_gas_used_at_most` assigns base gas in the hundreds-of-thousands to low-millions range per command [9](#0-8) , so triggering the exact zero-truncation in a live, governance-configured deployment requires pricing parameters (exchange rate, fee-per-gas, reward) to drift into an unusually low regime relative to the decimals scaling factor (`10^(18-Decimals)`) — a condition not actively prevented by `validate()` but which is not the normal/expected operating point. The bug is a genuine latent rounding defect in production arithmetic rather than something an unprivileged attacker can force on demand, since `PricingParameters` are governance-controlled and `gas_used_at_most` is fixed by the `GasMeter` implementation, not attacker input.

## Recommendation
Add an explicit non-zero check on the computed remote fee (or use ceiling/round-up division) in `calculate_fee`, rejecting or adjusting messages whose truncated remote fee is `0` despite non-zero `gas_used_at_most`/`reward` inputs — following the minimum-fee pattern in `substrate/frame/transaction-payment/asset-tx-payment/src/payment.rs`'s `withdraw_fee` (`min_converted_fee = if fee.is_zero() { Zero::zero() } else { One::one() }`) [1](#0-0) . Convert `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` from a passive documentation of the bug into an assertion that this case is rejected or rounded up.

## Proof of Concept
Using the existing pallet test harness, `OutboundQueue::calculate_fee(250000, PricingParameters { exchange_rate: 1/1, fee_per_gas: 1, rewards: {local:1, remote:1}, multiplier: 1/1 })` returns `Fee { local: 698000000, remote: 0 }` [10](#0-9) . Since `SendMessage::validate`/`deliver` perform no check on `fee.remote` before enqueueing [11](#0-10) , any combination of `maximum_gas_used_at_most` and governance-set pricing parameters that reduces to this pattern results in an accepted, zero-relayer-reward message being queued for Ethereum delivery.

		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			ensure!(
				MessageLeaves::<T>::decode_len().unwrap_or(0) <
					T::MaxMessagesPerBlock::get() as usize,
				Yield
			);

			// Decode bytes into versioned message
			let versioned_queued_message: VersionedQueuedMessage =
				VersionedQueuedMessage::decode(&mut message).map_err(|_| Corrupt)?;

			// Convert versioned message into latest supported message version
			let queued_message: QueuedMessage =
				versioned_queued_message.try_into().map_err(|_| Unsupported)?;

			// Obtain next nonce
			let nonce = <Nonce<T>>::try_mutate(
				queued_message.channel_id,
				|nonce| -> Result<u64, ProcessMessageError> {
					*nonce = nonce.checked_add(1).ok_or(Unsupported)?;
					Ok(*nonce)
				},
			)?;

			let pricing_params = T::PricingParameters::get();
			let command = queued_message.command.index();
			let params = queued_message.command.abi_encode();
			let max_dispatch_gas =
				T::GasMeter::maximum_dispatch_gas_used_at_most(&queued_message.command);
			let reward = pricing_params.rewards.remote;

			// Construct the final committed message
			let message = CommittedMessage {
				channel_id: queued_message.channel_id,
				nonce,
				command,
				params,
				max_dispatch_gas,
				max_fee_per_gas: pricing_params
					.fee_per_gas
					.try_into()
					.defensive_unwrap_or(u128::MAX),
				reward: reward.try_into().defensive_unwrap_or(u128::MAX),
				id: queued_message.id,
			};

			// ABI-encode and hash the prepared message
			let message_abi_encoded = ethabi::encode(&[message.clone().into()]);
			let message_abi_encoded_hash = <T as Config>::Hashing::hash(&message_abi_encoded);

			Messages::<T>::append(Box::new(message));
			MessageLeaves::<T>::append(message_abi_encoded_hash);

			Self::deposit_event(Event::MessageAccepted { id: queued_message.id, nonce });

			Ok(true)
		}

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {

pub struct ConstantGasMeter;

impl GasMeter for ConstantGasMeter {
	// The base transaction cost, which includes:
	// 21_000 transaction cost, roughly worst case 64_000 for calldata, and 100_000
	// for message verification
	const MAXIMUM_BASE_GAS: u64 = 185_000;

	fn maximum_dispatch_gas_used_at_most(command: &Command) -> u64 {
		match command {
			Command::SetOperatingMode { .. } => 40_000,
			Command::AgentExecute { command, .. } => match command {
				// Execute IERC20.transferFrom
				//
				// Worst-case assumptions are important:
				// * No gas refund for clearing storage slot of source account in ERC20 contract
				// * Assume dest account in ERC20 contract does not yet have a storage slot
				// * ERC20.transferFrom possibly does other business logic besides updating balances
				AgentExecuteCommand::TransferToken { .. } => 200_000,
			},
			Command::Upgrade { initializer, .. } => {
				let initializer_max_gas = match *initializer {
					Some(Initializer { maximum_required_gas, .. }) => maximum_required_gas,
					None => 0,
				};
				// total maximum gas must also include the gas used for updating the proxy before
				// the the initializer is called.
				50_000 + initializer_max_gas
			},
			Command::SetTokenTransferFees { .. } => 60_000,
			Command::SetPricingParameters { .. } => 60_000,
			Command::UnlockNativeToken { .. } => 200_000,
			Command::RegisterForeignToken { .. } => 1_200_000,
			Command::MintForeignToken { .. } => 100_000,
		}
	}
}
