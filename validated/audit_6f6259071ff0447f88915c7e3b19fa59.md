### Title
`GET /v2/attachments/:hash` serves attachment content without verifying it matches the requested hash - ([File: stackslib/src/net/api/getattachment.rs])

### Summary
`RPCGetAttachmentRequestHandler::try_handle_request` fetches an `Attachment` from `AtlasDB::find_attachment(&attachment_hash)` and serializes it into `GetAttachmentResponse` without ever re-checking that `Hash160::from_data(&attachment.content) == attachment_hash`. If a mismatched (hash, content) pair was ever persisted into the local `attachments` table (per the two prior findings referenced), this endpoint will serve that mismatched content back out over RPC, verbatim, to any remote caller who requests it by hash.

### Finding Description
The equality that should be enforced before serving is `Hash160::from_data(&attachment.content) == attachment_hash`, but it is never checked. The handler flow is: `path_regex` captures `attachment_hash` from the URL and decodes it via `Hash160::from_hex` [1](#0-0) ; then in `try_handle_request`, the code calls `network.get_atlasdb().find_attachment(&attachment_hash)` and, on `Ok(Some(attachment))`, immediately wraps it as `GetAttachmentResponse { attachment }` with no hash re-derivation or comparison [2](#0-1) . The response is then serialized to JSON and returned as-is [3](#0-2) . The `attachments` table itself has no DB-level constraint tying `hash` to `content` (e.g., no computed/generated column or CHECK constraint enforcing `hash = sha256(content)` equivalent) [4](#0-3) . This means if the row's `content` was ever written such that it does not hash to the row's `hash` key, this endpoint will happily serve that mismatched pair to any caller — including remote peers who use `AtlasDB::find_attachment`-style verification on their own end to accept the payload based on trusting the requested hash rather than re-hashing themselves.

### Impact Explanation
Any downstream peer that queries this node's `/v2/attachments/:hash` endpoint and (incorrectly) trusts the response without independently re-hashing the content will accept forged/mismatched BNS attachment data as if it corresponded to `attachment_hash`. This is a data-integrity/propagation issue: the node acts as a relay that vouches for content-hash correspondence without verifying it, which can spread the mismatch network-wide to any consumer that doesn't independently verify. This matches the "attachment/BNS mismatch" High-impact category.

### Likelihood Explanation
This finding's likelihood is entirely gated on the precondition established by the "two prior findings" — namely, that a remote peer can get a poisoned/mismatched (hash, content) pair persisted into this node's `AtlasDB` in the first place. I was not able to fully trace and confirm the write-path constraints (`insert_uninstantiated_attachment`/attachment-instantiation logic in `stackslib/src/net/atlas/db.rs` and `stackslib/src/net/atlas/download.rs`) within the available iterations to independently verify whether those paths already re-hash content before insertion. Assuming that precondition holds (as instructed by the question), reaching this endpoint requires no privilege — it is a plain unauthenticated `GET` request, remotely reachable, and repeatable for any hash the attacker wants served.

### Recommendation
In `RPCGetAttachmentRequestHandler::try_handle_request`, after retrieving `attachment` from `find_attachment`, assert `Hash160::from_data(&attachment.content) == attachment_hash` before constructing the `GetAttachmentResponse`; if the check fails, log the integrity violation, treat it as "not found" (or a distinct 500/410 error) rather than serving the mismatched content, and consider purging/re-validating the offending row from `AtlasDB`.

### Proof of Concept
1. In a `stackslib/src/net/api/getattachment.rs` test module, construct a `TestRPC`/`StacksNodeState` harness (as used in existing `getattachment` tests) with an in-memory `AtlasDB`.
2. Directly insert a row into the `attachments` table (bypassing normal instantiation logic) with `hash = Hash160::from_data(b"original")` but `content = b"forged".to_vec()`.
3. Issue an HTTP `GET /v2/attachments/<hex of Hash160::from_data(b"original")>` through `RPCGetAttachmentRequestHandler::try_handle_request`.
4. Parse the JSON response into `GetAttachmentResponse` and assert `Hash160::from_data(&resp.attachment.content) != attachment_hash` — proving the endpoint served mismatched content instead of failing the request.
