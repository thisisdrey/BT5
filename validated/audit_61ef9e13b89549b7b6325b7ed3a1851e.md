### Title
Unsafe division-before-multiplication in legacy `calculateGlobalEnergyLimit` truncates frozen-energy allowance - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit` (used whenever the chain has not enabled `supportUnfreezeDelay`/hardening) computes the energy limit for an account with frozen TRX by first dividing `frozeBalance` by `TRX_PRECISION` in integer arithmetic, and only afterwards multiplying by the `totalEnergyLimit/totalEnergyWeight` ratio. This early integer division discards the fractional remainder of `frozeBalance / TRX_PRECISION` before the proportional multiplication is applied, matching exactly the bug class described in the external report ("division prior to multiplication will lead to truncation").

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    ...
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```
When `hardenCalculation()` (i.e. `dynamicPropertiesStore.allowHardenResourceCalculation()`) is not enabled, the code takes `energyWeight = frozeBalance / TRX_PRECISION` as an *integer* division first, truncating any TRX below `TRX_PRECISION` (1 TRX). It then multiplies by the ratio using doubles. This is the unsafe "divide-then-multiply" order the report flags: instead of `(frozeBalance * totalEnergyLimit) / (TRX_PRECISION * totalEnergyWeight)`, the implementation collapses the frozen balance into a coarse integer weight before scaling.

The project's own regression/harden tests confirm the two paths (legacy vs. `calculateGlobalLimitV1`) can diverge specifically when `frozeBalance < TRX_PRECISION`: [2](#0-1) 

The hardened replacement, gated by the same flag, performs multiplication (via `BigInteger`) before dividing, which is the mathematically correct order: [3](#0-2) 

This confirms the maintainers are aware the un-hardened formula is unsafe, but the legacy formula remains live and reachable as long as `allowHardenResourceCalculation` has not been toggled on-chain (a chain-wide, committee-controlled parameter, not something an individual caller controls). Any account with `frozeBalance` that is not an exact multiple of `TRX_PRECISION` (1,000,000 sun) — which is essentially every real freeze amount not chosen as a round multiple of 1 TRX — has its proportional energy weight rounded down to the next whole TRX before the ratio is even applied, silently discarding the fractional portion's contribution to energy allowance.

### Impact Explanation
This directly affects `EnergyProcessor.useEnergy` / `getAccountLeftEnergyFromFreeze`, which gate how much TVM energy a staking account is entitled to consume for free before paying SUN fees: [4](#0-3) 
An unrepresentative (systematically lower) energy limit means legitimate resource entitlement is permanently under-computed/wasted (freezing loss for honest stakers) each time this path runs, and conversely (depending on rounding direction elsewhere) can allow entitlement mismatches between components that use the truncated value versus places that recompute with full precision. Because this affects on-chain resource accounting for every contract-invoking transaction routed through the non-hardened path, it is a chain-wide state-computation correctness issue, not merely a display bug — it can misallocate available free energy for potentially many stakers simultaneously and is reachable by simply calling any contract as long as the account has frozen TRX for energy.

### Likelihood Explanation
Likelihood is Medium: the bug only manifests while `allowHardenResourceCalculation` is disabled (its current default/until committee toggles it) and only for balances that are not exact multiples of `TRX_PRECISION` — which is the common case, since users freeze arbitrary TRX amounts. Triggering it does not require any special privilege: any address that freezes TRX for energy and then triggers a smart contract exercises this exact code path.

### Recommendation
Enable/enforce `allowHardenResourceCalculation` (or make the hardened multiply-then-divide `calculateGlobalLimitV1` path unconditional) so that `frozeBalance * totalEnergyLimit` is computed (with overflow-safe `BigInteger`, as already done in `calculateGlobalLimitV1`) before dividing by `TRX_PRECISION * totalEnergyWeight`, eliminating the intermediate integer truncation in `calculateGlobalEnergyLimit`.

### Proof of Concept
1. Ensure `dynamicPropertiesStore.allowHardenResourceCalculation()` returns `false` (default/legacy state) and `supportUnfreezeDelay()` is `false` (pre stake-2.0 delay chain state).
2. Freeze `1_500_000` sun (1.5 TRX) for ENERGY on an account (`frozeBalance = 1_500_000`, `TRX_PRECISION = 1_000_000`).
3. With `totalEnergyLimit = 50_000_000_000L`, `totalEnergyWeight = 2_000_000_000L`:
   - Legacy path: `energyWeight = 1_500_000 / 1_000_000 = 1` (truncated from 1.5), result `= 1 * (50_000_000_000/2_000_000_000) = 25`.
   - Correct multiply-first order: `(1_500_000 * 50_000_000_000) / (1_000_000 * 2_000_000_000) = 37` (approx, exact fraction preserved).
   - The account is granted energy limit `25` instead of the proportionally correct `~37`, a ~33% under-allocation purely from the division-before-multiplication truncation, matching the pattern the hardened test `testGlobalEnergyLimitV2BelowTrxPrecisionMatchesDouble` was written to detect for the V2 sibling function.
4. Every `useEnergy`/`getAccountLeftEnergyFromFreeze` call for that account subsequently under-reports available free energy, forcing unnecessary SUN fee burns for that transaction sender — reachable purely via normal `FreezeBalance` + `TriggerSmartContract` transactions from an unprivileged account.

  protected long calculateGlobalLimitV1(long frozeBalance,
      long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
  }
