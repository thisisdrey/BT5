### Title
Non-constant-time HTTP `authorization` header comparison enables timing-based auth-token recovery - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Six RPC endpoints (`/v3/block_proposal`, `/v3/blocks` broadcast, `/v3/blocks/replay/*`, `/v3/blocks/simulate/*`, `/v3/transactions/simulate`, and the fast-call read-only endpoint) authenticate the caller by comparing the request's `authorization` header to the node's configured secret (`connection_options.auth_token`) using Rust's default `String`/`&str` `PartialEq`, i.e. `auth_header != password`. This is a byte-wise, early-exit comparison rather than a constant-time comparison, mirroring the exact bug class in CVE-2021-33880 (aaugustin `websockets` HTTP Basic Auth timing attack).

### Finding Description
In each handler's `try_parse_request`, the flow is:
```rust
let Some(password) = &self.auth else { ... };
let Some(auth_header) = preamble.headers.get("authorization") else { ... };
if auth_header != password {
    return Err(Error::Http(401, "Unauthorized".into()));
}
``` [1](#0-0) 
Rust's standard string `!=` operator (`str::eq`) compares bytes sequentially and returns as soon as it finds the first mismatching byte (or a length mismatch). This means the wall-clock time taken by the comparison is correlated with the number of correct leading bytes in the guessed `auth_token`. The same pattern recurs verbatim in: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

The equality broken here is "authenticated request vs. stored `auth_token`" — the fault site is precisely the `!=` comparisons cited above. Unlike a normal password field, this token is used to gate the `/v3/block_proposal` endpoint that a signer uses to submit blocks for validation, so leaking it lets a remote attacker impersonate the signer/miner relationship for these endpoints.

### Impact Explanation
An attacker who can measure per-byte comparison timing (over many repeated requests, e.g. via statistical timing analysis over the network) can incrementally recover the `auth_token` one byte at a time, eventually obtaining valid credentials for these authenticated RPC endpoints without ever knowing the secret. Once recovered, they gain unauthorized access to `/v3/block_proposal` (a write endpoint accepting block proposals for validation), `/v3/blocks?broadcast=1` (an endpoint that lets a caller force block broadcast), `/v3/blocks/replay` and `/v3/blocks/simulate` debug endpoints, and `/v3/transactions/simulate`. This matches the "High" impact bar of steering/abusing an authenticated-only endpoint without authorization, though full exploitation requires a timing side channel achievable over the network (harder than local, per the original CVE's own CVSS AC:H rating).

### Likelihood Explanation
Exploitability is bounded by network jitter, but CVE-2021-33880 itself was rated CVSS AC:H (high attack complexity) for exactly this reason, and was still assigned "High" severity by the advisory. The comparison is remotely triggerable by any unauthenticated peer that can reach the node's RPC port, requires no prior access, and the vulnerable code path is hit on every single request to these six handlers.

### Recommendation
Replace the `!=` string comparisons with a constant-time comparison, e.g. using `subtle::ConstantTimeEq` on the UTF-8 byte slices of `auth_header` and `password` (with a length check that itself avoids leaking timing beyond a fixed comparison, or by first hashing both sides with a keyed MAC and comparing the fixed-length digests in constant time). Apply this uniformly across `postblock_v3.rs`, `postblock_proposal.rs`, `blockreplay.rs`, `blocksimulate.rs`, `txsimulate.rs`, and `fastcallreadonly.rs`.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. Repeatedly send POST requests to `/v3/block_proposal` (or GET to `/v3/blocks/replay/<id>`) with an `authorization` header guess, measuring response latency to the 401 response.
3. Statistically, requests whose header shares a longer correct byte-prefix with the real token take marginally longer to reject (extra byte comparisons in `str::eq`) — averaging over many samples per candidate byte allows incremental recovery of the token, byte-by-byte, exactly as described in GHSA-8ch4-58qp-g3mp for the analogous Basic-Auth password check.
