### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer Capability Offers — (`aptos-move/framework/aptos-framework/sources/account/account.move`)

---

### Summary

`SignerCapabilityOfferProofChallengeV2` omits the `chain_id` field that was deliberately added to its sibling struct `RotationCapabilityOfferProofChallengeV2`. A valid `offer_signer_capability` signature observed on one chain (e.g., mainnet) can be submitted verbatim on any other chain sharing the same `source_address` and `sequence_number`, installing the attacker as the signer-capability recipient on the victim's account on that chain without any new authorization from the victim.

---

### Finding Description

`RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to include `chain_id` with the stated rationale *"which prevents replaying the challenge message"*: [1](#0-0) 

`offer_rotation_capability` faithfully binds the challenge to the current chain: [2](#0-1) 

`SignerCapabilityOfferProofChallengeV2`, however, was never given the same treatment: [3](#0-2) 

And `offer_signer_capability` constructs the proof challenge with no chain binding at all: [4](#0-3) 

The signed message is therefore `BCS(sequence_number || source_address || recipient_address)` — identical across every Aptos chain that shares those two values.

---

### Impact Explanation

Once the attacker replays the transaction on chain B and `signer_capability_offer.for` is set to their address, they can call `create_authorized_signer` (or any function that consumes a `SignerCapability`) to obtain a signer for the victim's account on chain B. With that signer they can transfer all APT and fungible assets, drain staking positions, or perform any other privileged operation on the victim's account — constituting direct, permanent theft of user funds on chain B. [5](#0-4) 

---

### Likelihood Explanation

The preconditions are realistic:

1. The victim's account exists on both chains with the **same sequence number** at the time of the original offer. This is common immediately after a fork, snapshot-based testnet, or any chain that bootstrapped from mainnet state.
2. The attacker is the `recipient_address` in the original offer (they participated in the original protocol interaction) or they observe the BCS-encoded signature bytes from the on-chain transaction and submit them to chain B.
3. No privileged access is required — `offer_signer_capability` is a public entry function callable by any unprivileged transaction sender.

---

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` and populate it with `chain_id::get()` inside `offer_signer_capability`, exactly mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,          // <-- add this
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    chain_id: chain_id::get(),   // <-- add this
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
```

### Proof of Concept

```move
// e2e test sketch
#[test]
fun test_cross_chain_replay_signer_capability() {
    // 1. Initialize harness with chain_id = 2 (simulating chain A)
    let harness_a = MoveHarness::new_with_chain_id(2);
    let victim = harness_a.new_account();
    let attacker = harness_a.new_account();

    // 2. Victim signs SignerCapabilityOfferProofChallengeV2 for chain A (chain_id=2)
    //    challenge = BCS(seq=0 || victim_addr || attacker_addr)  -- no chain_id
    let sig = sign_challenge(victim_sk, SignerCapabilityOfferProofChallengeV2 {
        sequence_number: 0,
        source_address: victim.address(),
        recipient_address: attacker.address(),
    });

    // 3. Submit on chain A — succeeds as expected
    harness_a.run_entry_function(victim, "account::offer_signer_capability", sig, ...);

    // 4. Initialize a DIFFERENT harness with chain_id = 4 (chain B / fork)
    //    Victim account exists with sequence_number = 0 (same state)
    let harness_b = MoveHarness::new_with_chain_id(4);
    harness_b.import_account(victim);   // same address, seq=0

    // 5. Replay the EXACT SAME signature bytes on chain B — should be REJECTED but is ACCEPTED
    let result = harness_b.run_entry_function(attacker_as_sender,
        "account::offer_signer_capability",
        sig,   // identical bytes, no chain_id in the signed message
        ...
    );

    // 6. Assert the call was accepted (demonstrating the vulnerability)
    assert!(result.is_ok());
    assert_eq!(
        account::get_signer_capability_offer_for(victim.address(), &harness_b),
        attacker.address()
    );
    // Attacker now holds signer capability on chain B without victim's consent on chain B
}
```

The test would pass (demonstrating the bug) because the BCS-serialized challenge bytes are chain-agnostic. A correct implementation would fail at step 5 with `EINVALID_PROOF_OF_KNOWLEDGE` because the chain_id embedded in the signed message would not match chain B's `chain_id::get()`.
