### Title
No slippage-deadline / staleness protection for pending `MarketSellAssetContract` orders enables outdated-price execution and MEV sandwiching - (File: `protocol/src/main/protos/core/contract/market_contract.proto`, `actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java`)

### Summary
`MarketSellAssetContract` — the on-chain order-placement message for java-tron's decentralized token exchange (TRC10 market) — carries only `sell_token_quantity` and `buy_token_quantity` (used as an implicit min-price ratio), with no deadline/expiration parameter tied to the user's intended execution window. [1](#0-0)  A signed transaction carrying this contract only expires according to the network-wide generic transaction expiration field (`Transaction.raw.expiration`), which is set client-side and is unrelated to price/market conditions.

### Finding Description
Any unprivileged order placer builds and signs a `MarketSellAssetContract` specifying `sellTokenQuantity`/`buyTokenQuantity` as the taker price. `MarketSellAssetActuator.execute()` unconditionally uses these values to match immediately against the resting order book (`matchOrder`/`matchSingleOrder`), and any unmatched remainder is placed as a resting maker order in the book indefinitely. [2](#0-1)  There is no field allowing the signer to bound how long they intend for the order to be actionable at that price, distinct from the network's generic anti-replay `expiration` timestamp (`trx.expiration.timeInMilliseconds`, default 60s but bounded up to `MAXIMUM_TIME_UNTIL_EXPIRATION`). That generic field only prevents replay of a specific signed tx after a fixed window — it says nothing about whether the *order itself*, once accepted and placed on the resting book, should still be considered valid economically. Once the transaction is broadcast and accepted (matched or partially matched, remainder saved via `saveRemainOrder`), the resting portion sits in `MarketPairPriceToOrderStore` **indefinitely** until manually cancelled or opportunistically matched by a future taker — with no way for the original signer to have bounded that exposure at signing time.

This differs from the report's literal "mempool-pending tx" scenario (java-tron transactions do expire from the mempool quickly), but the underlying bug class is the same: an order that specifies a price but no validity deadline. Here, the exploitable window is not "unmined tx sitting in mempool" but "matched/resting order sitting in the on-chain order book," which can persist far longer and is filled by any counterparty transaction (`MarketSellAssetActuator` as taker) that can pick off a stale resting order whenever advantageous market conditions arise — economically identical to the "unknowingly performs a bad trade" and sandwich-style MEV harm described in the report, since the maker has no way to auto-invalidate their price commitment after a chosen time/price window.

### Impact Explanation
A user's resting sell order can be executed at a stale price long after being placed, once market conditions make it profitable for a taker to consume it, resulting in the maker receiving a bad/outdated exchange rate they never intended to still honor. Because `MarketCancelOrderContract` is the only mitigation and requires the user to actively notice and cancel, any order left unmanaged is a standing exploitable liability — a concrete asset/value-loss vector for order placers, matching Medium-severity per the cited precedent (user-conditional error causing loss of funds via stale price execution).

### Likelihood Explanation
Likelihood is meaningful but conditional: it requires the resting order to remain unfilled while the market price diverges significantly, and requires a counterparty to place a matching taker order. Given java-tron's decentralized exchange has no automatic expiry/cancellation and matching is purely price-based FIFO, any inactive/forgotten sell order is permanently exposed until manually cancelled, so likelihood scales with how often users leave orders unmonitored.

### Recommendation
Add an optional `expiration_time` (or `deadline`) field to `MarketSellAssetContract`, enforced in `MarketSellAssetActuator.doValidate()`/`execute()` against `headBlockTimeStamp`: if the current chain time exceeds the order's specified deadline, reject the transaction (or, if already resting, allow/require automatic removal from the order book instead of persisting indefinitely). This gives makers the same protection recommended in the original report (`sellAllAmount`/`buyAllAmount` deadline parameter) applied to java-tron's market order primitive.

### Proof of Concept
1. Alice signs and broadcasts a `MarketSellAssetContract` selling `TOKEN_A` for `TOKEN_B` at a price she considers fair "today," per `MarketSellAssetActuator.execute()`. [3](#0-2) 
2. No matching maker order exists at that price, so the full order is saved to the order book via `saveRemainOrder`, with no expiry.
3. Weeks/months later, the relative value of `TOKEN_A`/`TOKEN_B` has shifted substantially in Alice's favor for a taker (i.e., unfavorable for Alice).
4. Any anonymous API client submits a `MarketSellAssetContract` as taker; `matchOrder`/`matchSingleOrder` blindly fills against Alice's stale resting order at her original, now-unfavorable, price ratio. [4](#0-3) 
5. Alice's assets are exchanged at a price she never re-confirmed, with no protocol mechanism to have bounded this exposure.

      throws ItemNotFoundException, ContractValidateException {

    byte[] makerSellTokenID = buyTokenID;
    byte[] makerBuyTokenID = sellTokenID;
    byte[] makerPair = MarketUtils.createPairKey(makerSellTokenID, makerBuyTokenID);

    // makerPair not exists
    long makerPriceNumber = pairToPriceStore.getPriceNum(makerPair);
    if (makerPriceNumber == 0) {
      return;
    }
    long remainCount = makerPriceNumber;

    // get maker price list
    List<byte[]> priceKeysList = pairPriceToOrderStore
        .getPriceKeysList(MarketUtils.getPairPriceHeadKey(makerSellTokenID, makerBuyTokenID),
            (long) (MAX_MATCH_NUM + 1), makerPriceNumber, true);

    int matchOrderCount = 0;
    // match different price
    while (takerCapsule.getSellTokenQuantityRemain() != 0) {
      // get lowest ordersList
      MarketPrice makerPrice = hasMatch(priceKeysList, takerPrice);
      if (makerPrice == null) {
        return;
      }

      byte[] pairPriceKey = priceKeysList.get(0);

      // if not exists
      MarketOrderIdListCapsule orderIdListCapsule = pairPriceToOrderStore.get(pairPriceKey);

      // match different orders which have the same price
      while (takerCapsule.getSellTokenQuantityRemain() != 0

        matchSingleOrder(takerCapsule, makerOrderCapsule, ret, takerAccountCapsule);

        // remove order

          // remove from market order list
          orderIdListCapsule.removeOrder(makerOrderCapsule, orderStore,
              pairPriceKey, pairPriceToOrderStore);
        }

        matchOrderCount++;
        if (matchOrderCount > MAX_MATCH_NUM) {
          throw new ContractValidateException("Too many matches. MAX_MATCH_NUM = " + MAX_MATCH_NUM);
