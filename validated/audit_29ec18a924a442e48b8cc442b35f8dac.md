### Title
Per-IP QUIC connection rate limiter can be permanently bypassed by aborting handshakes before completion, allowing unbounded handshake CPU consumption from a single unstaked IP - ([File: streamer/src/nonblocking/quic.rs, streamer/src/nonblocking/connection_rate_limiter.rs])

### Summary
The per-IP `ConnectionRateLimiter` only records/consumes a token via `register_connection` after a QUIC handshake successfully completes inside `setup_connection`, while the pre-handshake gate `is_allowed` treats any IP with no recorded tokens as automatically allowed. An attacker who repeatedly opens and aborts connections from a single real IP before `Connecting` resolves (or resolves with an error) never triggers `register_connection`, so the IP is permanently treated as "unseen" and `is_allowed` always returns `true`, letting the attacker force unlimited costly TLS/QUIC handshake attempts.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-369`), every incoming connection first passes a non-mutating per-IP check: [1](#0-0) 
`is_allowed` only consults `current_tokens`; if the limiter has never seen the IP it unconditionally returns `true`: [2](#0-1) 

Only after `incoming.accept()` succeeds and the handshake completes does `setup_connection` call `rate_limiter.register_connection(&from.ip())`, which is the only call site that actually consumes a token for that IP: [3](#0-2) 

If the handshake times out (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT` = 2s) or errors out (client aborts/RSTs before `Connecting` resolves `Ok`), execution falls into the `Err(e)` / timeout branches, and `register_connection` is never invoked: [4](#0-3) 

Because no token is ever consumed for an aborted connection, `KeyedRateLimiter` never creates/decrements a bucket entry for that IP, so subsequent `is_allowed` checks keep returning `true` indefinitely — the per-IP gate never engages for an attacker who never lets a handshake succeed. The same asymmetry also affects the global `overall_connection_rate_limiter`: its tokens are only consumed post-handshake in `setup_connection` (line 495), and the pre-accept gate only checks `current_tokens() == 0` without consuming, so failed/aborted attempts never drain it either: [5](#0-4) [6](#0-5) 

The only bound left is `ClientConnectionTracker::new`, which caps globally concurrent in-flight connections via `qos.max_concurrent_connections()` — a global, not per-IP, ceiling, and one that is trivially cycled through by immediately aborting each attempt to free the slot for the next: [7](#0-6) 

This design is explicitly intentional to avoid IP-spoofing amplification (per comment at lines 332-340: rate-limiting is deferred until the peer has "asserted control over their ip address"), but it creates the reverse problem: a genuine, non-spoofing attacker holding a real IP can indefinitely evade the per-IP limiter by simply never completing a handshake, while still forcing the server to perform the expensive QUIC/TLS crypto work associated with each handshake attempt (key derivation, transcript processing) before the attempt fails or times out.

### Impact Explanation
An unstaked, unprivileged client can generate unbounded TPU QUIC handshake CPU load from a single IP address without ever being throttled by the per-IP connection limiter (`max_connections_per_ipaddr_per_min`), since `stats.connection_rate_limited_per_ipaddr` will not increment for this attack pattern. This matches the "QoS evasion" / connection-limit-bypass bounty category: sustained handshake churn consumes leader CPU and connection-processing capacity that should be shared fairly, degrading TPU throughput available to legitimate stakers/unstaked senders and effectively starving them.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs network access to the leader's public TPU QUIC endpoint and a client capable of opening a QUIC connection and aborting it before `Connecting` resolves successfully (well within the attacker's control, e.g., dropping the future or forcing a reset). This requires no stake, no special config, and is fully repeatable at high rate, bounded only by the attacker's own network/CPU resources and the server's `max_concurrent_connections()` concurrency ceiling (which is quickly cycled through given the short-lived nature of each aborted attempt).

### Recommendation
Consume/charge a per-IP token (and the global token) at the point the connection is first accepted/attempted (pre-handshake), not only after a successful handshake — e.g., track "pending" attempts against the rate limiter and only refund/adjust on success, or apply a separate, cheap pre-handshake per-IP attempt counter (distinct from the "control-asserted" post-handshake counter) so repeated aborted attempts from the same source address are still throttled. At minimum, ensure `overall_connection_rate_limiter` tokens are consumed on every accepted `Incoming` (not just successful handshakes), and add a per-IP counter for outstanding/aborted attempts within `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` windows.

### Proof of Concept
```rust
// streamer/src/nonblocking/quic.rs (integration-style test, conceptually)
// 1. Start run_server/spawn_server with a small max_connections_per_ipaddr_per_min.
// 2. From a single client IP, repeatedly:
//    - open a QUIC connection via endpoint.connect(...)
//    - drop the returned `Connecting` future immediately (before it resolves),
//      or otherwise force it to error before the handshake completes.
//    - repeat N thousand times in a tight loop.
// 3. Assert:
assert!(stats.total_incoming_connection_attempts.load(Ordering::Relaxed) > 10_000);
assert_eq!(stats.connection_rate_limited_per_ipaddr.load(Ordering::Relaxed), 0);
// i.e., despite thousands of attempts from one IP, the per-IP rate limiter
// never triggers because register_connection was never reached.
```
Fuzz variant: vary the abort timing relative to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` and assert `connection_rate_limited_per_ipaddr` only grows in proportion to completed handshakes (`Ok(new_connection)` branch reached), never to raw attempts, confirming the churn-based bypass.

    /// Check if the connection from the said `ip` is allowed.
    /// Here we assume that only IPs with actual confirmed connections are stored in it,
    /// since we should only modify server state once source IP is verified
    pub fn is_allowed(&self, ip: &IpAddr) -> bool {
        // Check if we have records in the rate limiter for the given IP address
        match self.limiter.current_tokens(ip) {
            Some(r) => r > 0, // we have a record, and rate is not exceeded
            None => true,     // if we have not seen IP, allow connection request
        }
    }
