### Title
`lookup_peer` in p2p neighbor lookup returns inverted expiry result, breaking the "public key unexpired" equality check - (File: stackslib/src/net/p2p.rs)

### Summary
`PeerNetwork::lookup_peer` in `stackslib/src/net/p2p.rs` is documented as returning the stored `Neighbor` record for a given address "if we know of it and its public key is unexpired," but the implementation returns `Some(neighbor)` exactly when the key **is** expired, and `None` when the key is **not** expired — the opposite of the documented and evidently intended behavior [1](#0-0) .

### Finding Description
The function is:
```rust
/// Get the neighbor if we know of it and it's public key is unexpired.
fn lookup_peer(
    &self,
    cur_block_height: u64,
    peer_addr: &SocketAddr,
) -> Result<Option<Neighbor>, net_error> {
    ...
    match neighbor_opt {
        None => Ok(None),
        Some(neighbor) => {
            if neighbor.expire_block < cur_block_height {
                Ok(Some(neighbor))
            } else {
                Ok(None)
            }
        }
    }
}
``` [1](#0-0) 

`neighbor.expire_block < cur_block_height` is precisely the condition under which the stored public key has *already expired* (the block height has advanced past the recorded expiry). Per the docstring, the function should return `Some(neighbor)` only when the key is **still valid** (i.e., `expire_block >= cur_block_height`), and `None` otherwise. The implementation inverts this: an *expired* record is returned as a live/valid `Neighbor`, while a still-valid, unexpired record is discarded as if unknown (`None`).

This is directly analogous to the reported bug class: an equality/branch condition (`_referrer != address(0)`) is supposed to gate one code path but the `else` branch handling silently does the wrong thing for the untaken condition — here, the `if`/`else` arms for "expired vs. not expired" are swapped, so the function's stated invariant ("returns Some only if unexpired") is violated for every call, i.e. authenticated/stored state (the on-disk `Neighbor` with its recorded expiry) is not correctly checked against the runtime block height before being treated as valid.

### Impact Explanation
Any downstream caller that relies on `lookup_peer` to decide whether a previously-known peer's public key can still be trusted (e.g., to avoid re-registering/overwriting a peer slot, or to decide whether a peer's identity is stale and can be reused/replaced during handshake/registration) will receive the opposite answer from what it expects:
- Peers whose public key has genuinely expired will be treated as still valid/known, potentially causing the network layer to keep trusting or reusing stale key material past its expiry.
- Peers whose public key is still valid (unexpired) will be treated as unknown, which can cause the peer-registration logic to behave as if no prior record exists for that address, potentially permitting a new peer key to be issued/rekeyed for a slot that should have been protected by the recorded expiry.

This is a state-consistency bug that breaks the "authenticated/stored key is valid until expire_block" equality check inside the p2p peer bookkeeping path, similar in nature to the referenced fee-bucket-swap bug (where the `if`/`else` branches for a boolean condition were logically reversed, causing state to be misattributed).

I was not able to locate and fully trace the single call site of `lookup_peer` within the available tool budget (grep only surfaced the definition itself within `p2p.rs`), so I cannot confirm with certainty which specific remote-facing registration/handshake decision consumes this return value or the exact end-to-end exploitation path/severity tier (e.g., whether this leads to unauthorized peer-slot takeover, a stale-identity trust issue, or is otherwise mitigated by additional checks elsewhere in the registration flow). This should be verified against the call site before treating this as a confirmed, high-severity remote issue.

### Likelihood Explanation
The condition is deterministic and triggers on every call to `lookup_peer` for peers with a recorded `expire_block`, since block height only increases over time — there is no need for an attacker to craft special input; simply reaching the natural expiry of a key (or having a key with a still-far-future expiry) exercises the inverted branch. However, without the call-site confirmed, the actual remote/attacker-triggerable impact and its severity remain unconfirmed.

### Recommendation
Fix the inverted condition to match the documented contract:
```rust
if neighbor.expire_block >= cur_block_height {
    Ok(Some(neighbor))
} else {
    Ok(None)
}
```
Also add/restore a unit test asserting that `lookup_peer` returns `Some` only for unexpired records and `None` for expired ones, and audit the call site(s) to confirm the corrected semantics do not change previously-relied-upon (buggy) behavior in a way that introduces regressions.

### Proof of Concept
1. Insert a `Neighbor` record into the peer DB for address `A` with `expire_block = 100`.
2. Call `lookup_peer(cur_block_height = 50, peer_addr = A)` — key not yet expired (`50 < 100`) — current code takes the `else` branch and returns `Ok(None)`, i.e., treats a known, still-valid peer as unknown.
3. Call `lookup_peer(cur_block_height = 200, peer_addr = A)` — key expired (`200 > 100`, i.e., `100 < 200`) — current code takes the `if` branch and returns `Ok(Some(neighbor))`, i.e., treats an expired peer's key record as valid/known.
Both outcomes are the inverse of the function's documented behavior ("Get the neighbor if we know of it and it's public key is unexpired") [2](#0-1) .
