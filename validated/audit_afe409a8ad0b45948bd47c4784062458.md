### Title
Missing Pre-Synchronization in `set_beneficiary_for_operator` Allows Operator to Steal Pending Commission from Old Beneficiary - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary

`delegation_pool::set_beneficiary_for_operator` changes the commission beneficiary address without first calling `synchronize_delegation_pool`. Any commission rewards that have accrued since the last synchronization are then credited to the **new** beneficiary when the pool is next synchronized, permanently depriving the old beneficiary of earned APT.

### Finding Description

`delegation_pool::set_operator` explicitly calls `synchronize_delegation_pool` before changing the operator, with the comment *"ensure the old operator is paid its uncommitted commission rewards."* [1](#0-0) 

`update_commission_percentage` also calls `synchronize_delegation_pool` first, with the comment *"the operator is paid its uncommitted commission rewards with the old commission percentage."* [2](#0-1) 

However, `set_beneficiary_for_operator` performs no such synchronization — it directly overwrites the beneficiary address: [3](#0-2) 

The docstring acknowledges the risk but leaves it as a caller responsibility rather than enforcing it in code: [4](#0-3) 

When `synchronize_delegation_pool` is eventually called (by anyone), it computes pending commission using `pool.operator_commission_percentage` applied to rewards since the last sync, then routes that commission to `beneficiary_for_operator(stake::get_operator(pool_address))` — which is now the **new** beneficiary: [5](#0-4) [6](#0-5) 

The same structural omission exists in `staking_contract::set_beneficiary_for_operator`, which also changes the beneficiary without first calling `distribute`/`request_commission_internal`: [7](#0-6) 

### Impact Explanation

An operator can steal accrued-but-not-yet-committed APT commission from their old beneficiary:

1. Operator sets beneficiary to address A (e.g., a third-party partner).
2. The delegation pool earns staking rewards over one or more epochs; commission accrues but is not yet committed (no `synchronize_delegation_pool` call).
3. Operator calls `set_beneficiary_for_operator(new_beneficiary = operator_own_address)`.
4. The next `synchronize_delegation_pool` call (triggered by any user operation on the pool) routes all pending commission to the operator's own address.
5. Address A receives nothing for the rewards earned during the period they were the designated beneficiary.

The stolen amount equals `operator_commission_percentage × (total_rewards_since_last_sync)`. For a large delegation pool (millions of APT) with a high commission rate (e.g., 10%) and a long unsynchronized window, this can be substantial APT.

### Likelihood Explanation

The attack requires only a single unprivileged entry-function call (`set_beneficiary_for_operator`) by the operator. No governance approval, no special timing beyond waiting for rewards to accumulate. Any validator operator who previously set a third-party beneficiary can execute this at will.

### Recommendation

Add a `synchronize_delegation_pool` call inside `set_beneficiary_for_operator` for every pool the operator manages, mirroring the pattern used in `set_operator` and `update_commission_percentage`. Since `BeneficiaryForOperator` is keyed on the operator address (not a specific pool), the function should iterate over all pools operated by this operator and synchronize each one before updating the beneficiary. Alternatively, enforce that the old beneficiary must explicitly call `synchronize_delegation_pool` before a beneficiary change can take effect (a two-step commit pattern).

### Proof of Concept

```
1. initialize_delegation_pool(operator, commission=1000 /* 10% */, seed)
   pool_address = get_owned_pool_address(operator_address)

2. delegator adds 1,000,000 APT; validator becomes active.

3. end_aptos_epoch() × N   // rewards accumulate; no synchronize called
   // pending commission ≈ N × epoch_reward_rate × 1,000,000 × 10%

4. operator calls set_beneficiary_for_operator(new_beneficiary = operator_address)
   // BeneficiaryForOperator updated; NO synchronize_delegation_pool called

5. Any user calls add_stake / unlock / synchronize_delegation_pool(pool_address)
   // synchronize_delegation_pool runs:
   //   commission_active = (active - pool_active_shares) * 10% → sent to operator_address
   //   old beneficiary receives 0

// Old beneficiary has lost all pending commission earned in step 3.
``` [3](#0-2) [1](#0-0)

    public entry fun set_beneficiary_for_operator(
        operator: &signer,
        new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator = new_beneficiary;
        } else {
            move_to(operator, BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary });
        };

        emit(SetBeneficiaryForOperator {
            operator: operator_addr,
            old_beneficiary,
            new_beneficiary,
        });
    }
