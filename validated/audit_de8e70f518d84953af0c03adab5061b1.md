## #Vulnerability Found

### Title
Unbounded recursive tree-walk in `GetTreeEntries` can crash Gitaly via native stack overflow - (File: `internal/git/localrepo/tree.go`)

### Summary
The Etherlink report describes stack overflow caused by recursion depth that is fully attacker-controlled and unbounded on the native call stack. Gitaly has a directly analogous pattern: `TreeEntry.walk()` recursively descends into a `TreeEntry` graph that is built from the recursive output of `git ls-tree -r` against arbitrary repository content, with no depth limit enforced anywhere in the call chain.

### Finding Description
`repo.ReadTree(..., WithRecursive())` builds a `TreeEntry` tree in `populate()` using an **iterative** stack-based algorithm (`treeStack`), which is safe by itself: [1](#0-0) 

However, once this structure is built, `TreeEntry.Walk()` traverses it via genuine Go-level recursion, with recursion depth equal to the directory nesting depth of the tree, and with no cap on that depth: [2](#0-1) 

This `Walk` is invoked directly from the `CommitService.GetTreeEntries` RPC handler when a client requests a recursive listing: [3](#0-2) 

Unlike the flat-path computation in the same file, which is explicitly bounded to `defaultFlatTreeRecursion = 10` levels: [4](#0-3) [5](#0-4) 

...`TreeEntry.walk()`/`TreeEntry.Write()` have no equivalent depth guard. Because Git trees allow arbitrarily deep nesting (each tree can point to a single child tree, and this can be repeated an arbitrary number of times), an ordinary user with push access can construct a repository with a directory hierarchy nested to an extreme depth (e.g., tens or hundreds of thousands of levels) using nothing more than standard `git` plumbing commands, entirely outside of Gitaly's control. There is no server-side limit on tree nesting depth enforced during a push (`git-receive-pack`) or import.

This is the closest concrete analog to the reported bug class: a custom, recursive traversal routine that operates directly on the native/goroutine call stack with attacker-controlled recursion depth, instead of using a bounded, heap-based (explicit stack/queue) structure — exactly the root cause and exactly the recommended fix pattern (switch to heap-based iteration) described in the report.

### Impact Explanation
A Go goroutine stack overflow is not a recoverable panic — it is a fatal runtime error (`runtime: goroutine stack exceeds ... -byte limit`) that terminates the entire Gitaly process, not just the request. This means a single crafted `GetTreeEntries` (or any other RPC that walks a recursively-populated `TreeEntry`, such as those calling `TreeEntry.Write()` during tree modification/write-back operations) can cause a full denial of service for the Gitaly node serving that repository, impacting all other repositories and clients sharing that process/pod.

### Likelihood Explanation
Likelihood is moderate-to-high: creating a deeply nested tree structure requires only standard Git object-creation commands available to any authenticated user with push access (no elevated privileges, no malicious peer, no MITM). Triggering the vulnerable path requires only calling `GetTreeEntries` with `Recursive: true` on that repository — a normal, unprivileged read RPC.

### Recommendation
Replace the recursive `TreeEntry.walk()` (and the equally unbounded recursive `TreeEntry.Write()`) with an iterative, explicit-heap-stack traversal (similar to the `treeStack` already used in `populate()`), and/or enforce a maximum tree-nesting depth during traversal that returns a structured error once exceeded, mirroring the existing `defaultFlatTreeRecursion` bound and the `maxAlternatesDepth` pattern used in `internal/git/dirs.go`.

### Proof of Concept
1. As an ordinary user with push access, create a repository containing a chain of N nested trees, each containing exactly one child tree (e.g., via `git mktree` piped N times, or via repeated single-file commits in progressively deeper subdirectories), for a sufficiently large N (tens of thousands+).
2. Push this repository to Gitaly.
3. Call `CommitService.GetTreeEntries` with `Revision` pointing at the tip commit, `Path: "."`, and `Recursive: true`.
4. `sendTreeEntriesUnified` calls `repo.ReadTree(..., WithRecursive())` → `populate()` (safe, iterative) → `tree.Walk(callback)` → recursive `entry.walk()` with call depth = N, eventually exceeding the goroutine stack limit and crashing the Gitaly process.

func (t *TreeEntry) walk(dirPath string, callback func(path string, entry *TreeEntry) error) error {
	nextDirPath := filepath.Join(dirPath, t.Path)
	if err := callback(dirPath, t); err != nil {
		return err
	}

	for _, entry := range t.Entries {
		if err := entry.walk(nextDirPath, callback); err != nil {
			return err
		}
	}

	return nil
}

// Walk will walk the whole tree structure and call callback on every entry of
// the tree in a depth-first like fashion.
func (t *TreeEntry) Walk(callback func(path string, entry *TreeEntry) error) error {
	for _, e := range t.Entries {
		if err := e.walk(t.Path, callback); err != nil {
			return err
		}
	}

	return nil
}

func populateFlatPath(
	ctx context.Context,
	objectReader catfile.ObjectContentReader,
	entries []*gitalypb.TreeEntry,
) error {
	for _, entry := range entries {
		entry.FlatPath = entry.GetPath()

		if entry.GetType() != gitalypb.TreeEntry_TREE {
			continue
		}

		for i := 1; i < defaultFlatTreeRecursion; i++ {
			subEntries, err := catfile.TreeEntries(ctx, objectReader, entry.GetCommitOid(), string(entry.GetFlatPath()))
			if err != nil {
				return err
			}

			if len(subEntries) != 1 || subEntries[0].GetType() != gitalypb.TreeEntry_TREE {
				break
			}

			entry.FlatPath = subEntries[0].GetPath()
		}
	}

	return nil
}
