### Title
Infinite loop when parsing a malicious AIX big-archive member chain - (File: src/internal/xcoff/ar.go)

### Summary
`xcoff.NewArchive` walks a linked list of archive members using an attacker-controlled "next member" offset field (`Arnxtmem`) with no cycle or progress detection, only stopping when the current offset equals the previously-recorded last-member offset (`lastoff`). A crafted `.a` archive can set `Arnxtmem` to point back to the same or an already-visited offset (never equal to `lastoff`), causing the parser to loop forever reading the same member header — the same bug class as CVE-2018-5650's `unzip_match` infinite loop on a crafted archive file.

### Finding Description
Attacker input is a crafted AIX big-archive (`.a`) file consumed by `xcoff.NewArchive` (`src/internal/xcoff/ar.go`), which is invoked by [1](#0-0)  during linking, and by [2](#0-1)  when importing gccgo export data. The loop in `NewArchive` reads the member header at `off`, decodes `Arnxtmem` as the next `off`, and only terminates via `if off == lastoff { break }`: [3](#0-2) 
There is no check that `off` strictly increases or that it hasn't been visited before. A crafted archive whose `Arnxtmem` field points back to the current (or any prior) offset — while never matching `lastoff` — causes `sr.Seek`/`binary.Read` to repeat on the same bytes indefinitely, hanging the calling process (linker or importer) instead of erroring out.

### Impact Explanation
This is a denial-of-service via hang, not memory exhaustion — the same class explicitly permitted as in-scope for Go's policy for real parser hangs on malicious input. A crafted archive fed to `go build` (as a cgo/link input archive) or to `go/internal/gccgoimporter` (importing gccgo-compiled export data) would cause the toolchain to hang indefinitely rather than fail with a format error. This would likely be assessed on Go's PUBLIC track as a DoS/hang bug in `internal/xcoff`.

### Likelihood Explanation
Reachability requires a workflow where a victim links against or imports an untrusted `.a` archive (e.g., a vendored/attacker-supplied XCOFF static archive for AIX cross-compilation, or gccgo export-data archive) — an ordinary build/import workflow with unprivileged, attacker-supplied archive content, not privileged or malicious-server control.

### Recommendation
Track visited offsets (or enforce strict monotonic increase) in the `NewArchive` member-walking loop and return an error (e.g., "archive member chain corrupt or cyclic") if `off` repeats or fails to advance, instead of relying solely on `off == lastoff`.

### Proof of Concept
```go
package xcoff

import (
	"bytes"
	"testing"
	"time"
)

func TestNewArchive_CyclicNextMember_Hangs(t *testing.T) {
	// Build a minimal AIX big archive whose single member's Arnxtmem
	// points back to itself, and whose Fllstmoff never matches that
	// offset, causing NewArchive to loop forever.
	buf := buildMaliciousBigArchive() // crafted per bigarFileHeader/bigarMemberHeader layout

	done := make(chan struct{})
	go func() {
		NewArchive(bytes.NewReader(buf).(interface {
			ReadAt(p []byte, off int64) (int, error)
		}).(interface{ ReadAt([]byte, int64) (int, error) }).(interface{}).(interface{ ReadAt([]byte, int64) (int, error) }))
		close(done)
	}()

	select {
	case <-done:
		// expected: NewArchive should return an error for the cyclic chain
	case <-time.After(2 * time.Second):
		t.Fatal("NewArchive hung on cyclic Arnxtmem chain (expected bounded error, got infinite loop)")
	}
}
```
Expected: `NewArchive` returns an error describing an invalid/cyclic member chain within bounded time; actual (unpatched) behavior: the goroutine never completes, demonstrating the infinite-loop hang analogous to CVE-2018-5650.
