### Title
Frequent unprivileged `accrue()` calls make `reserve-inc` round down to zero every time, permanently denying the treasury its interest fee - ([File: mainnet/contracts/vault/v0-vault-usdc.clar])

### Summary
The rounding-to-zero bug class from the report (`bps2Uint()` rounding `proposalThreshold()`/`quorum()` to 0 when the base value is small) has a direct analog in Zest's vault interest-accrual/treasury-fee logic. `calc-treasury-lp-preview` / `accrue()` compute the protocol's fee cut via `mul-div-down debt-delta fee-reserve BPS`, which rounds down to `u0` whenever `debt-delta` (the interest accrued since the last update) is small. Because `accrue()` is a public, unauthenticated function that any principal can call at will, an attacker can repeatedly call it with very short elapsed time between calls, forcing `debt-delta` (and thus `reserve-inc`) to round to zero on every single call, so the treasury (`.dao-treasury`) never receives its LP-minted fee share even though borrowers continue to accrue and pay full interest.

### Finding Description
`accrue()` is defined as a `define-public` function with no `check-caller-auth`/`check-dao-auth` gate — only a pause-state check: [1](#0-0) 

Inside it, the treasury fee is computed as: [2](#0-1) 
```
(debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```
`mul-div-down` is a plain floor-division helper: [3](#0-2) 

Exactly like `(number * bps) / 10000` in the report rounding to 0 for a small `number`, here `debt-delta * fee-reserve / BPS` rounds to 0 whenever `debt-delta` is small relative to `BPS / fee-reserve`. `debt-delta` itself is derived from the interest-index delta over the elapsed time since `last-update`, via `calc-multiplier-delta`, which scales the borrow rate by `time-delta`: [4](#0-3) 

Since anyone can call `accrue()` at any time (no cooldown, no minimum-interval enforcement), an attacker can call it in rapid succession (e.g., every block) so that each call's `time-delta`, and therefore `debt-delta`, is tiny — small enough that `reserve-inc` computed from it floors to `u0` on every call. Unlike a single large-interval `accrue()` call where the same total interest would produce a non-zero `reserve-inc`, splitting the same total accrual into many tiny slices via repeated calls causes the fee to vanish completely each time it is computed, and the "remainder" that was rounded away is never carried over or reconciled — it is simply lost. Meanwhile the borrow `index` still advances by the (unrounded, precision-1e12) multiplier each call, so users are still charged full compounding interest; only the protocol's `fee-reserve` cut on that interest is nullified.

### Impact Explanation
This causes a permanent loss of protocol fee revenue (treasury LP minting is skipped every time `reserve-inc` rounds to zero), which under the specified impact taxonomy is "theft of unclaimed yield" (the `fee-reserve` share of accrued interest is unclaimed yield destined for `.dao-treasury`). The attacker doesn't need any special privileges — `accrue()` is callable by any contract-caller — and the attack can be sustained indefinitely across all vaults (`v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`), all of which share the identical `accrue`/`calc-treasury-lp-preview` logic.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: `accrue()` has no rate limiting or authorization, and any user (or a bot) can trivially call it every block. Whether the attack is fully effective depends on the magnitude of `fee-reserve`, `BPS` (10000), the borrow rate, and typical block-to-block time deltas — if per-block interest accrual per vault is small relative to `BPS/fee-reserve`, the rounding-to-zero condition is easily and repeatedly triggered. This is most impactful for vaults with lower TVL/utilization (paralleling the report's "low `TotalVotingPower`" early-stage condition), but can be forced by an attacker at will regardless of protocol size by simply increasing call frequency to shrink each `debt-delta` slice.

### Recommendation
Accumulate rounding remainders across calls (carry forward the undistributed fractional `reserve-inc`/`debt-delta` in a persisted variable) instead of discarding them on each `accrue()` call, or compute the treasury fee independent of call frequency (e.g., track un-fee'd interest cumulatively and only reset it once fee has actually been minted), so that splitting accrual into many small calls cannot zero out the protocol's fee share.

### Proof of Concept
1. Attacker (any unprivileged principal) observes a vault (e.g., `v0-vault-usdc.clar`) with a nonzero `fee-reserve` and normal borrow activity accruing interest.
2. Instead of allowing `accrue()` to be invoked naturally at typical intervals (which would yield `debt-delta` large enough for `reserve-inc > 0`), the attacker calls the public `accrue()` function every block (or as frequently as possible).
3. Each call's `time-delta` is minimal, so `calc-multiplier-delta`'s per-call multiplier increment is tiny, making `debt-delta = new-debt - old-debt` tiny.
4. `reserve-inc = mul-div-down debt-delta fee-reserve BPS` floors to `u0` on every call since `debt-delta * fee-reserve < BPS`.
5. `treasury-lp` is thus `u0` every call, and no `ft-mint? zft treasury-lp .dao-treasury` ever occurs, even though `index` keeps compounding and borrowers keep owing the un-fee'd interest. Over time, the treasury permanently loses the `fee-reserve` share of interest that it would have received under normal (less frequent) `accrue()` cadence. [1](#0-0) [3](#0-2)
