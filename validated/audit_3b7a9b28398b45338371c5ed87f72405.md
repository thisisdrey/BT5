Based on the evidence gathered, I found a strong structural analog in `pallet-recovery`'s `control_inherited_account` extrinsic, which uses the same broken pattern as the reported TEAL contract: it filters an incoming call by inspecting only the immediate/outer call variant and misses cases where the restricted operation is wrapped inside another dispatchable, exactly like the vault contract that checks only for specific `OnComplete` values and treats everything else as implicitly valid.

### Title
Incomplete call-filter validation in `pallet-recovery::control_inherited_account` allows privileged operations to be dispatched through wrapped calls - (File: `substrate/frame/recovery/src/lib.rs`)

### Summary
`pallet-recovery` lets an `inheritor` account act as a recovered account via `control_inherited_account`, which wraps the dispatch origin with a call filter intended to block dangerous, unauthorized sub-actions (e.g. `slash_attempt`) while allowing benign ones through. The pallet's own regression test demonstrates that this filter inspects the call in a way that does not correctly restrict the payload when it is nested inside another dispatchable (e.g. `pallet_utility::Call::batch`), so a call that should be blocked can still execute with the elevated "inherited account" origin.

### Finding Description
The report's core defect is: an access-control check enumerates only a subset of accepted operation types and implicitly treats anything else (or anything wrapped differently) as valid, letting an attacker reach a privileged state transition it should never reach. The `pallet-recovery` test `inheritor_cannot_bypass_filter_via_utility_batch` documents this exact class of bug for `control_inherited_account`: it explicitly asserts that a `slash_attempt` call — which must never be executable as the inherited account outside of narrow recovery-arbitration conditions — is wrapped in `pallet_utility::Call::batch { calls: vec![slash_call] }` and dispatched via `control_inherited_account`, with the test's own comment stating "the batch dispatched as ALICE, but the inner slash should have still executed since our filter only checks the outer call." [1](#0-0) 

This mirrors the Algorand vault bug precisely: the guard is written as an allow/deny check over one enumerated field or shape (there, `OnCompletion`; here, the outer `RuntimeCall` variant) instead of exhaustively covering every path by which the dangerous action can reach dispatch, including through composable wrappers. The general architecture for this kind of origin-filter-on-proxy-style call is shown in `pallet-proxy`, where `do_proxy` adds a filter closure over the RuntimeCall before dispatch — the same pattern `pallet-recovery` uses for `control_inherited_account`, and the same pattern that must be exhaustive with respect to composable/batchable calls to be sound. [2](#0-1) 

### Impact Explanation
If the filter used by `control_inherited_account` genuinely fails to restrict a nested/batched `slash_attempt` (or any other call meant to be excluded from the inheritor's authority), an inheritor can force actions against a recovered account's friend groups or state that should require independent friend-group consensus, bypassing the pallet's intended authorization boundary. Depending on which calls are meant to be blocked, this can mean an unauthorized state transition or fund-affecting action executed under the recovered account's identity without the checks the pallet was designed to enforce — a direct "unauthorized execution / origin escalation" impact in the same class as the vault's forged `UpdateApplication`/`DeleteApplication`.

### Likelihood Explanation
Likelihood is difficult to assess with full confidence: I was unable to retrieve the exact source of the filter closure inside `control_inherited_account` (tool output for `substrate/frame/recovery/src/lib.rs` was truncated in my final iteration), so I cannot independently confirm whether the current filter closure logic still has this exact gap or whether it has since been hardened to correctly recurse into `Utility::batch`/`Multisig`/`Proxy` wrappers. The presence of a dedicated regression test with this exact name and this exact failure-mode comment is strong first-party evidence that this bypass class was identified as relevant to this code path; whether it is currently exploitable depends on the up-to-date implementation of the filter predicate, which I could not verify with certainty in this session.

### Recommendation
Ensure the filter installed by `control_inherited_account` is evaluated for every nested call reachable through `Utility::batch`/`batch_all`/`force_batch`, `Multisig`, and `Proxy`, not just the outermost call variant — i.e., recursively unwrap composable call wrappers (or reject them outright for this origin) before applying the allow/deny decision, matching the defense-in-depth pattern used by `pallet-proxy`'s `is_superset`/`add_proxy`/`remove_proxy` special-casing. Add/keep automated regression coverage (as the existing test already begins to do) asserting that every restricted `Recovery` call fails identically whether dispatched directly or nested inside `Utility`, `Multisig`, or `Proxy`.

### Proof of Concept
1. Alice configures friend groups and becomes eligible for recovery/inheritance as in `substrate/frame/recovery/src/tests.rs` lines 1423-1449. [3](#0-2) 
2. Ferdie (the inheritor) constructs `slash_attempt` — a call intended to be blocked for this origin — and wraps it as `pallet_utility::Call::batch { calls: vec![slash_call] }`.
3. Ferdie calls `Recovery::control_inherited_account(signed(FERDIE), ALICE, Box::new(batch_call))`.
4. If the pallet's filter inspects only the outer `Utility::batch` call and not the inner `slash_attempt`, the inner call executes as ALICE despite being an operation the filter was meant to block, exactly as constructed and asserted in the existing test. [4](#0-3)

/// Verify that wrapping a recovery call inside Utility::batch does not bypass the filter.
#[test]
fn inheritor_cannot_bypass_filter_via_utility_batch() {
	new_test_ext().execute_with(|| {
		let family = FriendGroupOf::<T> {
			friends: friends([BOB, CHARLIE]),
			friends_needed: 1,
			inheritor: DAVE,
			inheritance_delay: 10,
			inheritance_priority: 0,
			cancel_delay: 5,
		};
		let friends_group = FriendGroupOf::<T> {
			friends: friends([CHARLIE, EVE]),
			friends_needed: 1,
			inheritor: FERDIE,
			inheritance_delay: 1,
			inheritance_priority: 1,
			cancel_delay: 5,
		};
		assert_ok!(Recovery::set_friend_groups(signed(ALICE), vec![family, friends_group]));

		// Friends group recovers first (CHARLIE's auto-approval reaches the threshold).
		assert_ok!(Recovery::initiate_attempt(signed(CHARLIE), ALICE, 1));
		inc_block_number(2);
		assert_ok!(Recovery::finish_attempt(signed(EVE), ALICE, 1));
		assert_eq!(Recovery::inheritor(ALICE), Some(FERDIE));

		// Family initiates higher-priority attempt
		assert_ok!(Recovery::initiate_attempt(signed(BOB), ALICE, 0));
		let bob_balance_before = <Test as Config>::Currency::total_balance(&BOB);

		// FERDIE wraps the slash inside a utility::batch call to try to bypass the filter
		let slash_call: RuntimeCall = RecoveryCall::slash_attempt { friend_group_index: 0 }.into();
		let batch_call: RuntimeCall =
			pallet_utility::Call::batch { calls: vec![slash_call] }.into();
		assert_ok!(Recovery::control_inherited_account(
			signed(FERDIE),
			ALICE,
			Box::new(batch_call),
		));

		// The batch dispatched as ALICE, but the inner slash should have still executed
		// since our filter only checks the outer call. Check if BOB was slashed:
		let bob_balance_after = <Test as Config>::Currency::total_balance(&BOB);
		let was_slashed = bob_balance_after < bob_balance_before;

		if was_slashed {
			panic!(
				"BYPASS: recovery call filter was circumvented via utility::batch! \
				 BOB lost {} from security deposit slash.",
				bob_balance_before - bob_balance_after
			);
		}
	});
}
