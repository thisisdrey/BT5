### Title
Unprivileged attacker can saturate a victim's per-account token list to `MAX_TOKENS_PER_USER` with dust, DoS-ing new deposits, borrows, and collateral rescue - (contracts/Pool.sol:143-148; contracts/DepositToken.sol:486-488)

### Summary
The external report (CVE-2025-21490) is a pure availability bug: a repeatable crash/DoS of the affected server. The Metronome analog is the `MAX_TOKENS_PER_USER` accounting limit in `Pool` combined with permissionless on-behalf deposits in `DepositToken`. An attacker can fill a victim's `depositTokensOfAccount`/`debtTokensOfAccount` lists to the hard cap of 30 entries with dust, after which every code path that would add a *new* token to the victim's list reverts with `UserReachedMaxTokens` — blocking the victim from depositing new collateral types, issuing new synthetic debt, and receiving transfers/seizures of token types they do not already hold.

### Finding Description
`Pool` enforces a hard cap on the number of distinct deposit + debt tokens an account may hold: [1](#0-0) [2](#0-1) 

Registration into these per-account lists is permissionless and attacker-influencable:

1. `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` address [3](#0-2) 
2. `_mint` / `_transfer` unconditionally call `pool.addToDepositTokensOfAccount(account_)` whenever the recipient's prior balance was zero and the amount is non-zero [4](#0-3) 
3. `Pool.addToDepositTokensOfAccount` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [5](#0-4) 

Attack path (all unprivileged, public entry points):
- For each registered `DepositToken` the victim does not yet hold, attacker calls `depositToken.deposit(dustUnderlying, victim)` — or deposits to themselves once and then `transfer(victim, 1 wei)` — until the victim's combined list length reaches 30. Dust is sufficient: only a nonzero minted amount is required, and the underlying cost is ~1 wei per token.
- From then on, any call that would introduce a *new* token into the victim's list reverts:
  - `depositToken.deposit(x, victim)` for a token type not already in the list → `_mint` → `addToDepositTokensOfAccount` → `UserReachedMaxTokens`.
  - `debtToken.issue(amount, victim)` for a new synthetic (issued debt registers via `addToDebtTokensOfAccount`, guarded by the same `onlyIfAdditionWillNotReachMaxTokens` at Pool.sol:204) → revert. The victim cannot open a new borrow position.
  - `transfer`/`transferFrom`/`seize` of a not-yet-held deposit token to the victim → `_transfer` → revert. This also breaks `Pool.liquidate` when the liquidator's receipt of a seized deposit token would exceed *their* cap, but critically it blocks the victim from receiving collateral top-ups of new types from any helper account/zap.

The victim can only free a slot by fully zeroing a balance (`transfer`/`withdraw` until balance hits 0 → `removeFromDepositTokensOfAccount`), which costs them a transaction per dusted token and, while they hold debt, each dust withdrawal must pass `_revertIfLocked` — locked dust cannot be removed at all.

### Impact Explanation
- **Temporary freezing of funds / forced-liquidation DoS**: an underwater or deteriorating position can be prevented from adding a *new* collateral type to restore health, and a healthy user is blocked from borrowing new synthetic assets (every `issue` into a not-listed debt token reverts). For the duration of the attack the victim's ability to manage their position is frozen; if market movement pushes them below the collateral factor while saturated, they are liquidated despite being willing and able to post collateral of types not already in their list.
- **Persistent griefing**: clearing the cap requires the victim to burn dust balances one token at a time; the attacker can re-saturate cheaply (one dust transfer re-adds a token), sustaining the DoS for as long as they front-run/monitor.
- Unlike a governance pause, no admin action triggers this — it is reachable by any EOA through `DepositToken.deposit`/`transfer`.

### Likelihood Explanation
- Cost to attacker is minimal: ~30 dust deposits/transfers worth fractions of a cent of underlying, plus gas.
- No privileged role, oracle manipulation, flash loan, or fake token is required — only legitimate registered `DepositToken`s and public functions.
- Feasibility depends on deployed configuration: the pool must have enough registered deposit/debt tokens (or the victim must already occupy slots) for the 30 cap to be reachable while still leaving some token type outside the victim's list. Metronome pools with many collaterals/synthetics make this realistic; pools with very few tokens reduce it to blocking the *last* unused slots (still DoS-ing new borrows once the victim is at 30).
- Mitigating factors: the victim can clear slots by zeroing dust balances, and can keep depositing/borrowing token types already in their list — so the impact is a denial of new-position management rather than theft of existing balances directly.

### Recommendation
- Only add to `depositTokensOfAccount`/`debtTokensOfAccount` when the *account itself* initiates the action, or let `addTo*` be a best-effort operation that skips (rather than reverts) when the cap is hit — the lists are only used for iterating positions in `debtPositionOf`, so capping must not block balance changes.
- Alternatively, restrict `deposit`'s `onBehalfOf_` registration: only register the recipient if they opted in (e.g., register on first *self*-deposit, or keep accounting via a balance-scan instead of a capped enumerable set).
- At minimum, allow removals to proceed and ensure `seize`/liquidation payouts cannot be bricked by the recipient's cap (e.g., catch-and-skip the add on seize to the fee collector/liquidator).

### Proof of Concept
Hardhat outline against deployed-style pool (`Pool`, several `DepositToken`s, `DebtToken`s):

```ts
// setup: pool with >= N deposit tokens so victim can be pushed to cap
const victim = await ethers.Wallet.createRandom().connect(provider)

// attacker dust-fills victim's list
for (const dt of depositTokens) {
  if (await dt.balanceOf(victim.address) == 0 &&
      (await pool.getDepositTokensOfAccount(victim.address)).length +
      (await pool.getDebtTokensOfAccount(victim.address)).length < 30) {
    await underlying.connect(attacker).approve(dt.address, ethers.constants.MaxUint256)
    await dt.connect(attacker).deposit(1, victim.address) // 1 wei on behalf of victim
  }
}

// assert cap reached
expect(
  (await pool.getDepositTokensOfAccount(victim.address)).length +
  (await pool.getDebtTokensOfAccount(victim.address)).length
).eq(30)

// 1) victim cannot deposit a collateral type not in their list
await otherUnderlying.connect(victim).approve(otherDepositToken.address, MaxUint256)
await expect(
  otherDepositToken.connect(victim).deposit(parseEther('1'), victim.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 2) victim cannot issue a new synthetic debt token
await expect(
  debtToken.connect(victim).issue(parseEther('1'), victim.address)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')

// 3) no one can transfer a not-listed deposit token to the victim
await expect(
  depositToken.connect(attacker).transfer(victim.address, 1)
).revertedWithCustomError(pool, 'UserReachedMaxTokens')
```

Caveat: I did not fully verify `DebtToken.issue`'s caller/health checks (whether `issue(amount, to_)` allows arbitrary `to_`), so the strongest demonstrated path is the deposit-token side via `deposit(amount_, onBehalfOf_)` and `transfer`, both confirmed in `DepositToken.sol`. A fork test should pin down whether `issue` can also be weaponized directly against arbitrary victims; even if it cannot, the borrow-blocking outcome for an already-saturated victim holds.
