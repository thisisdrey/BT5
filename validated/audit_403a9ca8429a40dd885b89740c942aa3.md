This confirms the vulnerability path. The critical detail is the ordering in `run_server`/`setup_connection`: the `overall_connection_rate_limiter` check happens purely on raw connection count (via `current_tokens()` in the accept loop and `consume_tokens(1)` in `setup_connection`) *before* stake is ever determined — `get_connection_stake`/`build_connection_context` (which reads `staked_nodes`) only runs afterward, inside `qos.build_connection_context()` at [1](#0-0) . This means the global bucket has no concept of stake weighting and treats every completed handshake identically regardless of source.

### Title
Global `overall_connection_rate_limiter` is stake-blind, allowing distributed unstaked flood to starve legitimate staked connections - ([File: streamer/src/nonblocking/quic.rs])

### Summary
The QUIC server enforces connection admission via a per-IP `ConnectionRateLimiter` and a single global `overall_connection_rate_limiter` `TokenBucket` sized at `TOTAL_CONNECTIONS_PER_SECOND` (2500/s) with `MAX_CONNECTION_BURST` (1000) burst. Because the global bucket is consumed for every completed handshake before the connection's stake is known, an attacker distributing low-and-slow connection attempts across many distinct source IPs can stay under each IP's per-IP limit while collectively exhausting the shared global token bucket, causing legitimate staked validators' connection attempts to the same leader to be rejected purely due to bucket exhaustion.

### Finding Description
In `run_server` ( [2](#0-1) ), a single global `TokenBucket` (`overall_connection_rate_limiter`) is created and shared across all incoming connections regardless of identity or stake. On each incoming connection, the accept loop first checks `overall_connection_rate_limiter.current_tokens() == 0` ( [3](#0-2) ), then applies the per-IP `ConnectionRateLimiter::is_allowed` check ( [4](#0-3) ). After the QUIC handshake completes in `setup_connection`, the per-IP limiter is registered and then `overall_connection_rate_limiter.consume_tokens(1)` is called ( [5](#0-4) ) — still before any notion of stake is determined. Stake is only resolved afterward via `qos.build_connection_context(&new_connection)`, which internally calls `get_connection_stake` against `staked_nodes` ( [6](#0-5)  and [7](#0-6) ). Because the global bucket admission gate is entirely identity/stake-agnostic and shared cluster-wide across all source IPs, an attacker who spreads slow, low-rate completed QUIC handshakes across a sufficiently large number of distinct source IPs (each individually well under `max_connections_per_ipaddr_per_min`) can sustain aggregate consumption at or above `TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST`, driving `current_tokens()` to 0. Once exhausted, all subsequent connections — including from genuinely staked validators — are rejected at the very first check in the accept loop (`incoming.ignore()`), before the connection is even accepted or its identity checked.

### Impact Explanation
This matches the Agave "loss of availability"/DoS-adjacent bounty category for TPU ingress: a leader's connection-admission gate can be monopolized by unstaked traffic, denying legitimate staked validators the ability to establish new QUIC connections to submit transactions during that leader's slot, degrading block production ingress. Note that this only affects *new connection admission* (handshake completion), not already-established staked connections, so the practical blast radius is limited to connection churn/reconnection scenarios (e.g., staked nodes that don't already hold a warm connection to the leader).

### Likelihood Explanation
Feasible for an attacker with access to many distinct source IPs (e.g., cloud/botnet IP diversity, IPv6 address space) since each individual IP only needs to stay under the fairly generous `max_connections_per_ipaddr_per_min * 10` burst allowance of the per-IP limiter. The global limiter's default (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, `MAX_CONNECTION_BURST = 1000`, defined at [8](#0-7) ) is a fixed, cluster-independent constant, not scaled by validator stake share or network size, making it a static target for aggregate exhaustion. Repeatability is high since the limiter refills continuously and can be kept saturated indefinitely with a sustained distributed low-rate flood.

### Recommendation
Reorder admission so that stake-aware prioritization happens before/alongside the global rate limit, e.g., reserve a fraction of `overall_connection_rate_limiter` capacity (or maintain a separate token bucket) exclusively for connections that resolve to non-zero stake via `get_connection_stake`, performed as early as possible (even prior to full handshake completion via the transport parameters/pubkey in the TLS handshake, similar to how `SwQos` distinguishes staked vs. unstaked connection tables). Alternatively, scale `TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST` admission checks to weight against known/expected unstaked vs. staked connection ratios, and apply the global limiter primarily to the unstaked path (mirroring the split already used for the staked/unstaked `ConnectionTable`s in `swqos.rs`), so unstaked floods cannot exhaust capacity reserved for staked peers.

### Proof of Concept
Rust integration test plan (extending existing tests in `streamer/src/nonblocking/quic.rs`, e.g. near `test_quic_server_block_multiple_connections`):
1. Spin up a QUIC test server via `setup_quic_server` with `SwQos` or `SimpleQos` configured with a small `staked_nodes` map containing one staked keypair, and reduce `TOTAL_CONNECTIONS_PER_SECOND`/`MAX_CONNECTION_BURST` (or expose them as configurable test constants) to a small value to make saturation quick in test time.
2. Spawn `N` unstaked QUIC clients, each bound to a distinct simulated source `SocketAddr`/IP (loopback aliases or a custom `AsyncUdpSocket` mock), each opening handshake connections at a rate below `max_connections_per_ipaddr_per_min` but collectively exceeding `MAX_CONNECTION_BURST`/`TOTAL_CONNECTIONS_PER_SECOND`.
3. Assert via `StreamerStats::connection_rate_limited_across_all` that the global bucket becomes exhausted (`overall_connection_rate_limiter.current_tokens() == 0`).
4. Concurrently attempt a connection from the staked keypair's client and assert that it is rejected (`incoming.ignore()` / `new_connection.close(CONNECTION_CLOSE_CODE_DISALLOWED, ...)`) purely due to the shared global bucket, despite the per-IP `ConnectionRateLimiter` for that staked IP never having been triggered — demonstrating the invariant "staked connection admission remains reserved regardless of unstaked global consumption" is violated.
