### Title
Unauthenticated CPU/memory exhaustion via unbounded hex decoding of the `sig` token segment in `ExtractAuthInfo` - ([File: auth/token.go])

### Summary
`ExtractAuthInfo` in `auth/token.go` splits the bearer token into `version`, `sig`, and `msg` and immediately calls `hex.DecodeString(sig)` on the attacker-supplied `sig` substring before any HMAC comparison or length bound is enforced. Because this runs on every incoming RPC's authentication path prior to `hmac.Equal` in `v2HmacInfoValid`, an attacker who can reach the gRPC endpoint can supply an oversized `sig` value to force repeated allocation/decoding work per request/stream, with no explicit size limit found in the server setup to cap it.

The `sig` field length is entirely attacker-controlled and is passed straight into `hex.DecodeString` before `authInfo.Version`/HMAC checks occur. `hex.DecodeString` allocates a byte slice proportional to input length and does O(n) work, so this cost is paid for every single RPC/stream attempt, authenticated or not, since `CheckToken` runs pre-auth. I checked `internal/gitaly/server/server.go` and did not find any `MaxHeaderListSize` or similar gRPC/HTTP2 header-size configuration on the server, which is the mechanism that would otherwise bound the size of the `authorization` metadata value carried in HTTP/2 headers. Without that cap (or another gateway-level limit), the attacker-supplied `sig` string can be arbitrarily large within whatever default limits the underlying `golang.org/x/net/http2`/`grpc-go` transport applies by default, and every byte of it is decoded before the token is rejected.

### Impact Explanation
This is a resource-exhaustion (DoS) vector against the Gitaly gRPC auth path: repeated concurrent requests with very large `sig` values can drive up CPU (hex decode) and memory (allocated decode buffers) proportional to attacker-chosen input size, potentially degrading or crashing the `gitaly` process before any legitimate authentication decision is made. This matches the "DoS of an RPC handler" impact class in scope.

### Likelihood Explanation
The path is reachable pre-authentication — no valid token or secret is required, only network reachability to the gRPC endpoint, matching the stated precondition of an unprivileged attacker. Exploitation only requires opening connections/streams with a crafted `Authorization: bearer v2.<large-hex>.<ts>` header, which is trivial to automate and repeat across many concurrent connections for amplification. The main uncertainty is the actual effective size limit imposed by the gRPC/HTTP2 transport defaults, since I could not find an explicit `MaxHeaderListSize`/header-size limit configured in `internal/gitaly/server/server.go`; without such confirmation, the achievable per-request payload size (and thus the real-world severity) cannot be fully quantified from static analysis alone.

### Recommendation
Bound the size of `sig` (and the overall token) before calling `hex.DecodeString`, e.g. reject tokens whose `sig` segment exceeds the expected HMAC-SHA256 hex length (64 hex chars) prior to decoding, and/or configure an explicit `grpc.MaxHeaderListSize` (or equivalent) on the gRPC server to cap metadata size globally.

    md := metadata.Pairs("authorization", "bearer "+token)

    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        _, _ = gitalyauth.ExtractAuthInfo(ctx)

// ExtractAuthInfo returns an `AuthInfo` with the data extracted from `ctx`
func ExtractAuthInfo(ctx context.Context) (*AuthInfo, error) {
	token, err := grpcmwauth.AuthFromMD(ctx, "bearer")
	if err != nil {
		return nil, err
	}

	split := strings.SplitN(token, ".", 3)

	if len(split) != 3 {
		return nil, fmt.Errorf("invalid token format")
	}

	version, sig, msg := split[0], split[1], split[2]
	decodedSig, err := hex.DecodeString(sig)
	if err != nil {
		return nil, err
	}

	return &AuthInfo{Version: version, SignedMessage: decodedSig, Message: msg}, nil
}
