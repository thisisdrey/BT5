### Title
Unsynchronized map iteration in `ConcurrencyLimiter` resize hook causes fatal concurrent map crash under adaptive limit updates - (File: internal/limiter/concurrency_limiter.go)

### Summary
`NewConcurrencyLimiter` registers an `AfterUpdate` hook that iterates over `limiter.limitsByKey` to resize every keyed semaphore whenever the adaptive limit changes. [1](#0-0) 
That iteration is performed without acquiring `ConcurrencyLimiter.m`, the `sync.RWMutex` that otherwise guards all reads/writes to `limitsByKey`. [2](#0-1) 

### Finding Description
Every RPC that goes through `ConcurrencyLimiter.Limit` calls `getConcurrencyLimit`/`putConcurrencyLimit`, which lazily insert and delete entries from `limitsByKey` under `c.m.Lock()`. [3](#0-2) [4](#0-3) 

Meanwhile, `AdaptiveCalculator.calibrateLimits` runs on a background timer (default every 30s, `DefaultCalibrateFrequency`) and calls `limit.Update(newLimit)` for every managed `AdaptiveLimiter` based purely on system load conditions (CPU/memory/PSI), which are influenced by ordinary concurrent gRPC/git traffic. [5](#0-4) 
`AdaptiveLimit.Update` synchronously invokes all registered hooks while holding only its own internal mutex. [6](#0-5) 

Because the hook iterates `limiter.limitsByKey` (a plain Go map) with a `for range` while other goroutines concurrently mutate that same map via `getConcurrencyLimit`/`putConcurrencyLimit` under a different lock (`c.m`), Go's runtime map implementation can detect the concurrent read/write and raise "fatal error: concurrent map iteration and map write" — this is not a recoverable panic and crashes the entire `gitaly` process.

This is the closest analog to the source report's core defect class: a parameter/limit change is applied across in-flight/tracked state without the correct synchronization boundary, producing an unsafe/incorrect cross-cutting update — except here the consequence is a hard crash (DoS) rather than a financial miscalculation, since Gitaly has no monetary accounting equivalent.

### Impact Explanation
A `concurrent map iteration and map write` fatal error in Go terminates the entire process immediately, taking down the `gitaly` server and all in-flight RPCs across all repositories served by that node — a full denial of service, not scoped to a single repository or handler.

### Likelihood Explanation
The race requires: (1) any RPC that uses a `ConcurrencyLimiter` backed by an `AdaptiveLimit` (e.g., per-RPC or pack-objects concurrency limiting, gated by config) to be adding/removing keyed entries — which happens on ordinary, continuous request traffic — concurrently with (2) the periodic `AdaptiveCalculator` calibration tick invoking `Update`. Since calibration runs automatically every 30 seconds by default whenever adaptive concurrency limiting is enabled, and keyed limiter churn happens on essentially every RPC under load, the race window recurs continuously during normal server operation without requiring any special or malicious actor — only sufficiently concurrent legitimate traffic to trigger the race.

### Recommendation
Acquire `c.m` (as a read or write lock, consistent with how `limitsByKey` is otherwise protected) inside the `AfterUpdate` hook in `NewConcurrencyLimiter` before iterating `limiter.limitsByKey`, e.g.:
```go
limit.AfterUpdate(func(val int) {
    c.m.RLock()
    defer c.m.RUnlock()
    for _, keyedLimiter := range limiter.limitsByKey {
        ...
    }
})
```
Note the hook must avoid calling back into methods that take `c.m.Lock()` while holding the same lock, to prevent deadlock with `getConcurrencyLimit`/`putConcurrencyLimit`.

### Proof of Concept
1. Configure Gitaly with adaptive concurrency limiting enabled (`AdaptiveCalculator` running with `DefaultCalibrateFrequency`) for a per-RPC or pack-objects limiter, backed by `NewConcurrencyLimiter`.
2. Drive sustained concurrent RPC traffic across many distinct limiting keys (e.g., many distinct repositories/users hitting the pack-objects limiter), causing continuous inserts/deletes into `limitsByKey` via `getConcurrencyLimit`/`putConcurrencyLimit`.
3. Simultaneously let the background `AdaptiveCalculator.calibrateLimits` goroutine tick (every `CalibrationInterval`) and call `AdaptiveLimit.Update`, which fires the unsynchronized `for range limiter.limitsByKey` hook in `NewConcurrencyLimiter`.
4. Under `go test -race` or under real concurrent load, Go's runtime detects the concurrent map iteration and write and the process fatally crashes, confirmable by running the existing `TestLimiter_dynamic` suite concurrently with synthetic key churn goroutines calling `getConcurrencyLimit`/`putConcurrencyLimit` in a loop while `limit.Update` is invoked from another goroutine — this reliably reproduces the "concurrent map iteration and map write" fatal error.

func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

func (c *ConcurrencyLimiter) putConcurrencyLimit(limitingKey string) {
	c.m.Lock()
	defer c.m.Unlock()

	ref := c.limitsByKey[limitingKey]
	if ref == nil {
		panic("semaphore should be in the map")
	}

	if ref.refcount <= 0 {
		panic(fmt.Sprintf("bad semaphore ref refcount %d", ref.refcount))
	}

	ref.refcount--
	if ref.refcount == 0 {
		delete(c.limitsByKey, limitingKey)
	}
}

// Update adjusts the current limit value and executes all registered update hooks.
func (l *AdaptiveLimit) Update(val int) {
	l.Lock()
	defer l.Unlock()

	if val != l.current {
		l.current = val
		for _, hook := range l.updateHooks {
			hook(val)
		}
	}
}
