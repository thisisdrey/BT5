## Analysis Summary

The LiFi bug's broken invariant is: **value is deducted/consumed on one side of a two-step operation, but the corresponding "processed" state does not correctly reflect whether the paired step actually happened**, leading to silent, unrecoverable loss of funds without any error being surfaced.

The closest verified analog in this repository is in the Snowbridge **system-v2** "tip top-up" flow, where a tip amount is burned on the sending side, but if the corresponding `add_tip` call on the message queue fails, the pallet swallows the error, reports success, and only records the loss in a purely informational storage item (`LostTips`) with no restitution path.

### Title
Snowbridge tip top-up permanently loses relayer-reward funds on `add_tip` failure with no refund path - (File: `bridges/snowbridge/pallets/system-v2/src/lib.rs`)

### Summary
`Pallet::add_tip` in `snowbridge-pallet-system-v2` accepts an `amount` that has already been burned/reserved on the calling side (per PRDoc `pr_9746.prdoc`, which documents that "relayer tips were not properly paid out, causing the tips to be lost since it had already been burnt"). When the inner `InboundQueue::add_tip`/`OutboundQueue::add_tip` call fails (e.g. `NonceConsumed` because the message was processed in the same or an earlier block, or `UnknownMessage`), the pallet does not revert, does not refund, and does not fail the extrinsic — it just records the amount into `LostTips<T>` and returns `Ok(())`. [1](#0-0) 

### Finding Description
`add_tip` computes the result of forwarding the tip to the message queue and, on error, only bookkeeps the loss:

```rust
let result = match message_id {
    Inbound(nonce) => <T as pallet::Config>::InboundQueue::add_tip(nonce, amount),
    Outbound(nonce) => <T as pallet::Config>::OutboundQueue::add_tip(nonce, amount),
};

if let Err(ref e) = result {
    tracing::debug!(...);
    LostTips::<T>::mutate(&sender, |lost_tip| {
        *lost_tip = lost_tip.saturating_add(amount);
    });
}

Self::deposit_event(Event::<T>::TipProcessed { sender, message_id, amount, success: result.is_ok() });

Ok(())
``` [2](#0-1) 

Compare this to `AddTip::add_tip` in `inbound-queue-v2`, which fails with `NonceConsumed` precisely when the message nonce has already been marked processed:

```rust
impl<T: Config> AddTip for Pallet<T> {
    fn add_tip(nonce: u64, amount: u128) -> Result<(), AddTipError> {
        ensure!(amount > 0, AddTipError::AmountZero);
        ensure!(!Nonce::<T>::get(nonce.into()), AddTipError::NonceConsumed);
        ...
    }
}
``` [3](#0-2) 

This is exactly the LiFi pattern: the "initial value" (tip amount) is committed/burned upstream (per the PRDoc describing this exact fund-loss scenario), while the downstream bookkeeping treats the operation as "processed" (`success: false` event, but the dispatchable itself still returns `Ok(())`) without atomically reconciling — the record of loss (`LostTips`) is not tied to any drain, reimbursement extrinsic, or on-chain remediation visible in this pallet. A relayer submitting a message can race an honest user's `add_tip` transaction (no malicious behavior required — ordinary processing latency/block-inclusion order is enough), causing the tip to be consumed by the frontend/burn step yet never applied to the relayer reward and never returned to the tipper.

### Impact Explanation
This breaks the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" invariant. Because the extrinsic reports `Ok(())` regardless of internal failure, and only an untouched storage counter (`LostTips`) records the amount, ordinary users lose real value (already burned/committed on the source side, per the PRDoc's own description of the underlying loss mechanism) with no recovery mechanism found in the pallet. This is a permanent user-fund loss, matching the "permanent user-fund or bridge-state lock" impact category, reachable by any unprivileged user submitting a tip near message-processing time — no relayer/prover/admin collusion is required.

### Likelihood Explanation
Likelihood is moderate-to-high: any user who calls the tip-topup flow for a message whose nonce is processed concurrently (a normal, frequent race under live bridge traffic) triggers the `NonceConsumed` failure path. No privileged actor or malicious relayer is needed — ordinary relayer competition/timing is sufficient to trigger this on mainnet-scale traffic.

### Recommendation
- Make `add_tip` fail the extrinsic (propagate the error) instead of unconditionally returning `Ok(())`, so failed state doesn't silently "succeed."
- If the tip's underlying value is burned upstream before this call, add an on-chain reimbursement/claim path keyed off `LostTips<T>` so affected accounts can recover funds, or restructure the flow so burn/hold only occurs after `add_tip` succeeds (fail-closed rather than fail-open), consistent with how `pr_9746` already fixed the sibling "burnt-and-lost" defect for a related code path.
- Add integration coverage asserting that `LostTips` entries are either refundable or that the extrinsic reverts on `add_tip` failure, matching the "atomic settlement" invariant used elsewhere in the bridge stack (e.g., `Nonce`/`Tips` handling in `process_message`).

### Proof of Concept
1. A user (via the system-frontend that burns/holds the tip amount) submits a tip top-up for `Inbound(nonce)` with `amount = X`.
2. Concurrently (or slightly earlier in the same block/queue), a relayer submits and finalizes `EthereumInboundQueueV2::submit` for the same `nonce`, causing `Nonce::<T>::set(nonce)` [4](#0-3) .
3. The frontend's XCM `Transact` calling `Pallet::<T>::add_tip(origin, sender, Inbound(nonce), X)` on BridgeHub now hits `AddTipError::NonceConsumed` inside `InboundQueue::add_tip` [3](#0-2) .
4. `system-v2::add_tip` catches this `Err`, stores `X` into `LostTips::<T>::get(sender)`, emits `TipProcessed { success: false }`, and still returns `Ok(())` [5](#0-4) .
5. The user's `X` (already burned/committed on the source chain per the PRDoc's description of this exact scenario) is never applied to any relayer reward and is never returned to the user — the only trace is the `LostTips` counter, which this pallet provides no extrinsic to redeem.

Note: I could not locate, within the available search scope, the exact system-frontend code that performs the pre-burn of the tip amount before dispatching to `system-v2::add_tip`; this is inferred from the `pr_9746.prdoc` description ("tips were not properly paid out ... because it had already been burnt") and the absence of any refund/drain extrinsic for `LostTips` in the code I was able to inspect. If a full-repository review shows a refund mechanism elsewhere (e.g., in the frontend pallet on AssetHub), this finding should be re-scoped accordingly.

			// Otherwise add the tip.
