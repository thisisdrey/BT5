### Title
Positions with debt below `debtFloorInUsd` are permanently unliquidatable when `maxLiquidable < 100%` — bad debt freezes - (File: contracts/Pool.sol)

### Summary
`Pool.liquidate` enforces two contradictory constraints: the repaid fraction cannot exceed `maxLiquidable` (initialized to 50%), and the post-liquidation debt must be either zero or ≥ `debtFloorInUsd`. For any account whose debt value has fallen below the floor, both branches revert, making the position a permanently stuck, unliquidatable bad debt — a liveness/insolvency DoS analogous to CVE-2019-2948's complete-DOS bug class.

### Finding Description
In `Pool.liquidate` the cap check and the floor check are both enforced:

- `if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) revert AmountGreaterThanMaxLiquidable();` (contracts/Pool.sol:567)
- `if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) revert RemainingDebtIsLowerThanTheFloor();` (contracts/Pool.sol:571-578)

`maxLiquidable` is initialized to `0.5e18` (contracts/Pool.sol:181), so a full repayment (`wadDiv == 1e18`) always reverts. If the account's current debt `D` satisfies `0 < D_usd < debtFloorInUsd`, then:
- any `amountToRepay_ < D` leaves `_newDebtInUsd ∈ (0, floor)` → `RemainingDebtIsLowerThanTheFloor`;
- `amountToRepay_ == D` gives ratio `1e18 > 0.5e18` → `AmountGreaterThanMaxLiquidable`.

There is no escaping value, so `liquidate` reverts for every call against that account. More generally, for `floor ≤ D < 2·floor`, the maximum allowed repay is `D − floor`, which may be arbitrarily small, so even above-floor positions can only be liquidated at a negligible rate. `quoteLiquidateMax` caps at `maxLiquidable` but does not detect this deadlock (contracts/Pool.sol:419-440).

Debt can fall below the floor without privileged action: the floor is only enforced at mint (`DebtToken._mint`, contracts/DebtToken.sol:580-588) and at `repay` (contracts/DebtToken.sol:442-451), but debt-in-USD is computed via `masterOracle().quoteTokenToUsd`, so a price move of a non-USD synth (e.g. msETH) or a governance floor increase retroactively strands existing positions. An unprivileged attacker can also deliberately open a maximal-leverage position with debt just above the floor via `DebtToken.issue`/`SmartFarmingManager.leverage` with a volatile-collateral/volatile-synth pair; once it drifts below the floor while underwater, no liquidator can clear it.

### Impact Explanation
Broken invariant: liquidation bounds / liveness. Underwater positions below the debt floor can never be liquidated and the user cannot fully exit either (a full `repay`/`repayAll` still works for the user, but a user whose collateral no longer covers the debt has no incentive to repay). The protocol accumulates permanent bad debt — the seized collateral would not cover it, and the position occupies debt supply indefinitely, degrading solvency the same way a "complete DOS of the service" degrades availability.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` and `maxLiquidable < 1e18` on the deployed configuration (the code defaults `maxLiquidable` to 50%). It triggers whenever any account's debt USD value drops below the floor — plausible for non-USD-denominated synth debt during price declines, or after a floor parameter update. I could not confirm the on-chain value of `debtFloorInUsd` for current deployments within this analysis; if it is 0 on all live pools the issue is latent rather than active.

### Recommendation
Allow full repayment in `liquidate` when it clears the entire debt, e.g. skip the `maxLiquidable` check when `amountToRepay_ == _debtTokenBalance`, or skip the floor check when `_newDebtInUsd == 0` combined with a full-repay exemption. Alternatively, treat the floor check as `remaining == 0 || remaining >= floor` (already done) but raise `maxLiquidable` cap dynamically when the position debt is below the floor.

### Proof of Concept
Hardhat (reproducible against `test/Pool.test.ts` fixtures):

```ts
// Pool initialized with maxLiquidable = 0.5e18, debtFloorInUsd > 0.
// 1. alice deposits collateral, issues msETH debt D such that
//    floor < debtUsd(D) < 2 * floor (or drops below floor after an ETH price move).
// 2. Price moves so alice is unhealthy AND debtUsd(D) < floor.
await masterOracle.updatePrice(msETH.address, lowPrice);

// 3. Full liquidation attempt reverts on maxLiquidable:
await expect(
  pool.connect(liq).liquidate(msETH.address, alice.address, D, msdWETH.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 4. Any partial repay leaves debt in (0, floor) and reverts:
await expect(
  pool.connect(liq).liquidate(msETH.address, alice.address, D.div(2), msdWETH.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// Result: no amountToRepay in [1, D] succeeds — the bad debt is frozen permanently.
```
