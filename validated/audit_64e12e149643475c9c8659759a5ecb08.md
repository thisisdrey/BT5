### Title
`remove_account` fails to clean up `PromiseYieldReceipt`/`PromiseYieldStatus`/`PromiseYieldTimeout` entries, allowing a stale yield callback to execute against a re-created account - (`core/store/src/utils/mod.rs`)

### Summary
`remove_account`, invoked by `action_delete_account` when a `DeleteAccount` action is processed, only removes `TrieKey::Account`, `TrieKey::ContractCode`, access/gas keys, and `TrieKey::ContractData` for the deleted account. It has no knowledge of, and never removes, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, or the shard-global `TrieKey::PromiseYieldTimeout` queue entries that reference the account. If the account had an outstanding, unresolved `promise_yield_create` at the time it self-deletes (e.g., via a multi-action receipt `[FunctionCall, DeleteAccount]`), the stale yield survives account deletion and will later be executed by `apply_action_receipt` against whatever account/contract now occupies that `account_id`, once a `PromiseResume` (real resume or timeout) for that `data_id` arrives.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) is the sole cleanup routine called from `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), which after computing storage/gas-key checks calls: [1](#0-0) 
`remove_account` only iterates access keys and contract-data prefixes for the account; it never touches `TrieKey::PromiseYieldReceipt`/`PromiseYieldStatus`, which are keyed by `(receiver_id, data_id)`: [2](#0-1) 

A `promise_yield_create` call from a `FunctionCall` action produces a new `ActionReceiptMetadata` marked `is_promise_yield: true` via `ReceiptManager::create_promise_yield_receipt` (`runtime/runtime/src/receipt_manager.rs:148-165`), which is converted into a `ReceiptEnum::PromiseYield`/`PromiseYieldV2` receipt in `function_call.rs:181-194`, enqueued as an **instant receipt**, and only persisted into `TrieKey::PromiseYieldReceipt` when that instant receipt is itself processed (`set_promise_yield_receipt`, `runtime/runtime/src/lib.rs:1495-1499`). Crucially, `process_receipt_and_instant_receipts` (`runtime/runtime/src/lib.rs:2641-2670`) fully executes the *originating* `ActionReceipt` (all of its actions, in order, in one `apply_action_receipt` call) before draining `instant_receipts`. This means a receipt with actions `[FunctionCall(promise_yield_create), DeleteAccount]` will have the second action (`DeleteAccount`) run in the same call as the first — but any *earlier*, already-persisted `PromiseYieldReceipt`/`PromiseYieldStatus` for that same account (created by a prior, distinct receipt) is untouched by `remove_account`.

When a matching `PromiseResume` (real resume or synthesized timeout, `resolve_promise_yield_timeouts`, `runtime/runtime/src/lib.rs:3009-3105`) is later delivered, `process_receipt`'s `VersionedReceiptEnum::PromiseResume` branch (`runtime/runtime/src/lib.rs:1500-1568`) unconditionally calls `get_promise_yield_receipt(state_update, account_id, data_receipt.data_id)` and, if found, executes it via `apply_action_receipt` — with no check that the account is the same one that created the yield, nor even that the account still exists in its original form. Since the timeout-queue entry (`TrieKey::PromiseYieldTimeout`) is also never removed by `remove_account`, the timeout mechanism itself will resurrect and deliver the stale resume automatically after `yield_timeout_length_in_blocks`, requiring no further attacker action.

The resurrected `ActionReceipt` has `predecessor_id == receiver_id == account_id` (self-call, `sir == true`), which many contracts treat as the highest-trust caller (e.g., `assert!(predecessor_account_id() == current_account_id())` guards). If the account was deleted and the same `account_id` re-created (an ordinary flow for sub-account/factory patterns where a parent account's key can `CreateAccount` + `DeployContract` on `sub.parent.near` after a prior tenant's `DeleteAccount`), the stale callback executes the *old* tenant's method name/arguments as a trusted self-call against the *new* tenant's contract state — none of the standard signature/nonce/access-key/action-validation checks apply here because this is a receipt reconstructed from stale runtime state, not a freshly signed transaction.

### Impact Explanation
This is an authorization-escalation bug: a forged, unauthorized "self-call" (`predecessor_id == receiver_id`) is delivered to a contract that never issued or expected it, months (or just `yield_timeout_length_in_blocks`) after the corresponding account was deleted. In shared/sub-account/factory deployment patterns where account names are recycled, this lets a leftover state artifact from a deleted deployment invoke privileged "self only" logic on the unrelated contract now occupying that account name, matching the "authorization escalation via self-referential multi-action receipts" bounty category.

### Likelihood Explanation
Preconditions: (1) an account calls `promise_yield_create` and never resolves it; (2) the same account is deleted via a `DeleteAccount` action while that yield is outstanding; (3) the same `account_id` is later re-created (feasible for sub-accounts controlled by a parent key, or factory-style deployments that reuse names). All steps are performed via ordinary signed transactions from an unprivileged account controlling its own (sub)account namespace — no validator/node access needed. The timeout mechanism (`resolve_promise_yield_timeouts`) guarantees eventual delivery of the stale `PromiseResume` even if no one ever calls `yield_resume`, making the bug self-triggering and fully repeatable.

### Recommendation
`remove_account` (or `action_delete_account`) should enumerate and remove all outstanding `TrieKey::PromiseYieldReceipt`/`TrieKey::PromiseYieldStatus`/`TrieKey::YieldIdToDataId`/`TrieKey::DataIdToYieldId` entries for the account being deleted (and ideally also purge/mark the corresponding `TrieKey::PromiseYieldTimeout` queue entries, or make timeout/resume processing verify the receipt's originating account is still "the same" account, e.g. via an account-generation counter) before or as part of removing the account.

### Proof of Concept
Integration test plan (test-loop / `runtime/runtime/src/tests/apply.rs` style):
1. Deploy a test contract to account `A` that exposes `call_yield_create_return_promise` (already used in `test_processed_receipt_ids_gc`) and a callback method with a `predecessor==current_account_id` self-call assertion.
2. Call `call_yield_create_return_promise` on `A`, let the instant `PromiseYield` receipt persist `TrieKey::PromiseYieldReceipt{A, data_id}` and enqueue `TrieKey::PromiseYieldTimeout`.
3. Submit a second transaction to `A` with actions `[FunctionCall(no-op or second yield_create), DeleteAccount{beneficiary: A}]` executed as one `ActionReceipt`; assert account `A` is removed from state.
4. Assert (read via `TrieUpdate`/`get_promise_yield_receipt`) that `TrieKey::PromiseYieldReceipt{A, data_id}` and `TrieKey::PromiseYieldStatus{A, data_id}` still exist post-deletion.
5. Re-create `A` (e.g. via `CreateAccount` + `DeployContract` from the parent account, deploying a *different* contract).
6. Advance blocks to `yield_timeout_length_in_blocks` so `resolve_promise_yield_timeouts` synthesizes and delivers the `PromiseResume` for `data_id`.
7. Assert the stale yield's callback FunctionCall executes against the newly deployed contract on `A` with `predecessor_id == receiver_id == A`, i.e. the new contract's self-call-guarded logic runs despite never being requested by the new deployment — demonstrating the authorization escalation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
