## Analysis

The Zivoe bug's core broken invariant is: **a public, permissionless, zero-cost call can force a reward-rate/reward-accrual recomputation whose integer-division precision loss permanently orphans already-deposited reward tokens, because the "lost" fractional portion is discarded rather than carried forward.**

The closest structural analog in this repository is `pallet-asset-rewards` (`substrate/frame/asset-rewards/src/lib.rs`), which implements a Synthetix-style JIT reward-per-token accrual scheme almost identical in shape to `ZivoeRewards`.

### The corrupted value

`reward_per_token()` computes the pool's accrued reward-per-staked-token using a fixed, very small precision multiplier: [1](#0-0) [2](#0-1) 

`PRECISION_SCALING_FACTOR` is only `4096` (12 bits), far weaker than the `1e18` WAD scaling used elsewhere in the same repository for reward math (e.g. nomination-pools' `FixedU128` reward counter, explicitly chosen to avoid exactly this class of rounding loss). Every time `reward_per_token()` rounds `reward_rate_per_block * blocks_elapsed * 4096 / total_tokens_staked` down to `0`, `update_pool_rewards()` still unconditionally advances `last_update_block` to "now" and stores the (unchanged) `reward_per_token_stored`: [3](#0-2) 

There is no leftover/remainder carried into the next window — unlike the fix Zivoe applied (accumulating `leftover` before recomputing `rewardRate`). Once `last_update_block` moves forward, the reward corresponding to that elapsed window is gone forever, even though the pool admin has already transferred the corresponding reward tokens into the pool's pot account via `deposit_reward_tokens`: [4](#0-3) 

### Why guards don't stop it

`update_pool_and_staker_rewards` is invoked from every unprivileged, signed public entrypoint that touches staker state — `stake`, `unstake`, `harvest_rewards` — with no minimum-amount check and no cooldown: [5](#0-4) [6](#0-5) 

Any unprivileged staker (no admin/governance role needed) can inflate `total_tokens_staked` and then keep calling `stake`/`unstake` in short succession (or every block), each time forcing `blocks_elapsed` to be small and the reward numerator (`reward_rate_per_block * blocks_elapsed * 4096`) to stay below `total_tokens_staked`, so the division rounds to zero on every single update. `reward_per_token_stored` never increases, `last_update_block` keeps advancing, and the reward asset already sitting in the pool's account (`pool_info.account`) becomes permanently unclaimable dust that accumulates without bound as this is repeated — precisely the "reward tokens stuck in contract" pattern from the report, just triggered via `stake`/`unstake` self-interaction instead of a zero-amount deposit.

### Title
Low-precision `reward_per_token()` scaling factor lets unprivileged stakers permanently strand deposited reward tokens in `pallet-asset-rewards` pools - (File: `substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards`'s JIT reward accrual divides `reward_rate_per_block * blocks_elapsed * PRECISION_SCALING_FACTOR` by `total_tokens_staked`, using a fixed `PRECISION_SCALING_FACTOR` of only `4096`. When `total_tokens_staked` is large relative to `reward_rate_per_block`, this integer division rounds to `0` for short elapsed-block windows. Because `update_pool_rewards()` unconditionally advances `last_update_block` and stores the unchanged `reward_per_token_stored` with no leftover/remainder carry-over, any elapsed reward window that rounds to zero is permanently lost — even though the corresponding reward-asset balance was already deposited into the pool's pot account.

### Finding Description
`reward_per_token()` (`substrate/frame/asset-rewards/src/lib.rs:787-810`) is the sole place reward accrual is computed, and it is called from `update_pool_and_staker_rewards` → `update_pool_rewards`, which every public call (`stake`, `unstake`, `harvest_rewards`) invokes before mutating any staker/pool state. The precision multiplier (`4096`) is far too small relative to realistic `Balance` magnitudes (typically 128-bit values with 10-18 decimal assets), so for many realistic `(reward_rate_per_block, total_tokens_staked)` combinations, one or a few elapsed blocks worth of reward rounds down to zero. Because `update_pool_rewards` sets `last_update_block = now` unconditionally regardless of whether `reward_per_token` actually changed, the elapsed window's true (non-zero) reward entitlement is discarded rather than being retried on the next call — there is no accumulator analogous to Zivoe's fixed `leftover` variable.

### Impact Explanation
Reward-asset tokens deposited by the pool admin/creator via `deposit_reward_tokens` become permanently stuck in the pool's pot account, unclaimable by any staker, growing without an upper bound as more zero-rounding updates occur. This is a direct, permanent fund lock reachable by any unprivileged, signed account (no governance/admin role required), matching the "permanent user-fund ... lock" impact category.

### Likelihood Explanation
Likelihood is high in any pool where the staked-asset total is large relative to `reward_rate_per_block` (e.g., high-decimal staked assets, or a pool intentionally inflated by an attacker's own large stake). An attacker only needs to submit ordinary `stake`/`unstake` transactions with minimal staked amounts at high frequency (or simply take advantage of naturally large `total_tokens_staked`) — no privileged role, validator/collator collusion, or off-chain infrastructure is required.

### Recommendation
- Increase `PRECISION_SCALING_FACTOR` substantially (e.g., to `1e12`/`1e18`-scale fixed-point, consistent with the rest of the codebase's reward-counter designs), and/or
- Accumulate and carry forward the rounding remainder between successive `update_pool_rewards` calls (mirroring Zivoe's `leftover` accumulation) so that no elapsed-block reward window is silently dropped, and/or
- Use a wider intermediate type (e.g., `U256`, as already done elsewhere in this pallet's `balance_to_point`/`point_to_balance` helpers) before the final division.

### Proof of Concept
1. Admin creates a pool with `staked_asset_id = X`, `reward_asset_id = Y`, `reward_rate_per_block = R` (a modest integer), via `create_pool`.
2. Admin funds the pool via `deposit_reward_tokens(pool_id, large_amount)`.
3. An attacker (unprivileged) calls `stake(pool_id, huge_amount)` to make `total_tokens_staked >> R * 4096`.
4. In every subsequent block, the attacker (or any staker) calls `stake(pool_id, 1)` (or `unstake`/`harvest_rewards`), each time triggering `update_pool_and_staker_rewards` with `blocks_elapsed = 1`.
5. On each call, `reward_per_token()` computes `R * 1 * 4096 / total_tokens_staked`, which rounds to `0` because `total_tokens_staked` dominates; `reward_per_token_stored` never advances, yet `last_update_block` is reset to the current block every time.
6. The reward tokens sitting in the pool's pot account (deposited in step 2) are never distributed to any staker and are permanently stranded, regardless of how many blocks pass, as long as the attacker (or ordinary chain activity) keeps resetting `last_update_block` before enough blocks accumulate to overcome the rounding threshold.

			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
