## Analog Found: Re-freezing TRX Resets the Unlock/Expiration Time of Already-Frozen (Older) Balance

### Title
Freezing additional TRX resets the unfreeze-eligibility timer of previously frozen balance, delaying withdrawal of already-earned funds - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceActuator.execute()` (and the equivalent VM native path `FreezeBalanceProcessor.execute()`) merges any newly frozen balance with the account's existing frozen balance for the same resource, but always overwrites the stored `expireTime` with the value computed from the *current* transaction's `frozenDuration`, discarding the previously-recorded (and possibly much closer) expiration time. This mirrors the `VaderBond.deposit()` bug: a legitimate follow-up action (freezing/depositing more) silently resets the unlock clock for funds a user could already be nearing eligibility to reclaim.

### Finding Description
When a user calls `FreezeBalanceContract` a second time for the same resource type (e.g. `BANDWIDTH`), the actuator computes: [1](#0-0) 

`expireTime` is derived solely from `now + freezeBalanceContract.getFrozenDuration() * FROZEN_PERIOD` for the *current* call, then the combined balance (`frozenBalance + accountCapsule.getFrozenBalance()`) is stored together with this single new `expireTime` via `setFrozenForBandwidth`: [2](#0-1) 

`setFrozenForBandwidth`/`setFrozenForEnergy`/`setFrozenForTronPower` unconditionally replace the single `Frozen` entry (protobuf only stores one `Frozen` record per resource, `frozenCount` is capped at 1 as validated in `validate()` at line 195-198), so there is no way to retain the earlier, closer expiration for the balance that was already frozen. The same overwrite pattern appears in the VM native contract implementation used by smart contracts calling the `freeze` TVM opcode: [3](#0-2) 

Because `frozenDuration` is chosen fresh on every call (bounded only by `minFrozenTime`/`maxFrozenTime` from `DynamicPropertiesStore`), a user (or contract) can add even 1 TRX with the minimum allowed duration, and this recomputed `expireTime` becomes the new unlock time for the *entire* pooled frozen balance — including the portion that was frozen much earlier and may have been due to unlock imminently.

### Impact Explanation
A user who freezes additional TRX (e.g., to gain more bandwidth/energy or delegate resources) before unfreezing their existing frozen balance unknowingly extends the lock period of funds they could otherwise have already withdrawn via `UnfreezeBalanceContract`. This is the direct structural analog of the reported bug: normal, expected interaction with the protocol ("deposit"/"freeze" again) silently resets the timer that governs when previously committed funds become reclaimable, causing an unintended, avoidable delay in the user regaining access to their own TRX.

### Likelihood Explanation
This requires only a single signed `FreezeBalanceContract` transaction from the account owner — no special privileges, no cooperation from other parties, and no dependence on validator/witness behavior. Any TRX holder who freezes twice for the same resource without first unfreezing will trigger this reset, making it trivially and frequently reachable in normal usage (staking, delegating bandwidth/energy, or via contracts using the `freeze` TVM opcode).

### Recommendation
When merging newly frozen balance into an existing `Frozen` record, retain the more favorable (earlier) `expireTime` for the previously frozen portion, e.g., by tracking a weighted/minimum expiration or by storing separate frozen "lots" the way `UnfreezeBalanceV2` tracks unfreeze entries as a list. As a simpler mitigation, only extend `expireTime` when the new value is later, and never regress access for funds already scheduled to unlock sooner, or split the additional freeze into its own vesting instance whose lock does not affect previously frozen funds.

### Proof of Concept
1. Account `A` calls `FreezeBalanceContract` freezing `X` TRX for `BANDWIDTH` with `frozenDuration = minFrozenTime` (e.g., 3 days) → `Frozen.expireTime = now + 3d`.
2. After 2.9 days, `A` calls `FreezeBalanceContract` again, freezing an additional `Y` TRX for `BANDWIDTH` with `frozenDuration = minFrozenTime` (3 days).
3. `FreezeBalanceActuator.execute()` computes `newFrozenBalanceForBandwidth = X + Y` and calls `accountCapsule.setFrozenForBandwidth(X + Y, now + 3d)` — see [4](#0-3) 
4. The original `X` TRX, which was ~0.1 days from being unfreeze-eligible, is now locked for another ~3 days along with `Y`, since only one `Frozen` entry with one `expireTime` exists per resource.
