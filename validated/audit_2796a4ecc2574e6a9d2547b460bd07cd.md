### Title
Missing V2-asset existence check in `UpdateAssetActuator.validate()` allows an unhandled `NullPointerException` in `execute()` - (File: actuator/src/main/java/org/tron/core/actuator/UpdateAssetActuator.java)

### Summary
`UpdateAssetActuator.execute()` unconditionally dereferences `assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray())` before checking whether the returned `AssetIssueCapsule` is `null`, mirroring the GStreamer `gst_gdk_pixbuf_dec_flush` bug class where a value assumed to be non-null (a "frame") is used without a null check, causing a crash.

### Finding Description
In `execute()`:
```java
AssetIssueStore assetIssueStoreV2 = assetIssueV2Store;
assetIssueCapsuleV2 = assetIssueStoreV2.get(accountCapsule.getAssetIssuedID().toByteArray());

assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit);   // NPE if assetIssueCapsuleV2 == null
``` [1](#0-0) 

This line runs **regardless of `AllowSameTokenName`**, unlike the rest of the method which branches on that flag. The `validate()` method, however, only checks the V2 asset's existence when `AllowSameTokenName == 1`:
```java
if (dynamicStore.getAllowSameTokenName() == 0) {
  if (account.getAssetIssuedName().isEmpty()) { ... }
  if (assetIssueStore.get(account.getAssetIssuedName().toByteArray()) == null) { ... }
} else {
  if (account.getAssetIssuedID().isEmpty()) { ... }
  if (assetIssueV2Store.get(account.getAssetIssuedID().toByteArray()) == null) { ... }
}
``` [2](#0-1) 

When `AllowSameTokenName == 0`, `validate()` never verifies that `account.getAssetIssuedID()` is non-empty or that a corresponding entry exists in `assetIssueV2Store`. If the account's `AssetIssuedID` field is empty or does not resolve to an entry in the V2 store (e.g., because the account issued the asset under legacy/V1-only semantics or the field was never populated), `assetIssueStoreV2.get(...)` returns `null`, and the subsequent `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` throws an uncaught `NullPointerException`.

Critically, `execute()`'s `try/catch` only handles `InvalidProtocolBufferException`:
```java
} catch (InvalidProtocolBufferException e) {
  ...
}
``` [3](#0-2) 
so the `NullPointerException` (a `RuntimeException`) is not caught here and propagates out of the actuator.

This is invoked from `RuntimeImpl.execute()`/`Manager.processTransaction()` during ordinary transaction/block processing: [4](#0-3) [5](#0-4) 
which is reachable from a broadcast `UpdateAssetContract` transaction sent by any unprivileged account that has previously issued an asset — this is not a privileged or SR-only action.

### Impact Explanation
An uncaught `NullPointerException` thrown deep inside actuator execution during `processTransaction`/`processBlock` is not one of the checked exceptions the block-application pipeline expects (`ContractExeException`, `ContractValidateException`, etc.). Because block application is deterministic, every node that processes this transaction (broadcast in mempool, or included in a block) will hit the same NPE, causing consistent crashes/exceptions on all validating nodes — a network-wide Denial of Service against transaction/block processing, matching the "node crash or halt" impact bar from the rules.

### Likelihood Explanation
I could not fully confirm from static inspection alone whether `AssetIssuedID` can actually be empty/unresolvable for real, "AllowSameTokenName == 0" issued assets in the currently indexed code (in the visible `AssetIssueActuator.execute()`, `assetIssueV2Store.put()` is invoked in both branches, which would normally keep V1 and V2 stores in sync). The exploitability therefore hinges on a state where `account.getAssetIssuedID()` is empty or stale relative to `assetIssueV2Store` (e.g., due to migration/import paths, genesis-imported accounts, or historical data predating the V2 asset store) that I was not able to fully trace to a concrete transaction sequence within the available tool budget. I flag this uncertainty explicitly rather than asserting confirmed exploitability.

### Recommendation
In `UpdateAssetActuator.validate()`, always validate the V2 asset entry (`assetIssueV2Store.get(account.getAssetIssuedID().toByteArray())`) regardless of `AllowSameTokenName`, since `execute()` always dereferences it. Additionally, add an explicit null check in `execute()` before calling `assetIssueCapsuleV2.setFreeAssetNetLimit(...)` and throw `ContractExeException` instead of allowing an NPE to propagate.

### Proof of Concept
Conceptual PoC (unverified end-to-end due to inability to trace how `AssetIssuedID` could become empty for a `AllowSameTokenName==0`-issued asset in this snapshot):
1. Obtain/construct an account whose `AssetIssuedName` is set (passes the V1 check in `validate()`) but whose `AssetIssuedID` is empty or does not correspond to any entry in `assetIssueV2Store`.
2. Broadcast an `UpdateAssetContract` transaction from that account with `AllowSameTokenName == 0`.
3. `validate()` passes (V1 checks only). `execute()` calls `assetIssueStoreV2.get(emptyOrStaleID)`, which returns `null`; the next line `assetIssueCapsuleV2.setFreeAssetNetLimit(newLimit)` throws `NullPointerException`, uncaught by the actuator's `catch (InvalidProtocolBufferException e)` block, propagating out of `RuntimeImpl.execute()` / `Manager.processTransaction()`.
