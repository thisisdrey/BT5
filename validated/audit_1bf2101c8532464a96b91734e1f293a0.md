### Title
Divide-then-multiply precision loss in bandwidth/energy limit calculation (default path) - (File: chainbase/src/main/java/org/tron/core/db/ResourceProcessor.java, chainbase/src/main/java/org/tron/core/db/BandwidthProcessor.java, chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java)

### Summary
The default (non-hardened) code paths that compute an account's bandwidth (`calculateGlobalNetLimit`) and energy (`calculateGlobalEnergyLimit`) limits from frozen TRX perform a division before the multiplication, exactly the "multiplication after division" precision-loss pattern described in the referenced report. A hardened, BigInteger-based replacement (`calculateGlobalLimitV1`/`calculateGlobalLimitV2`, gated by the `ALLOW_HARDEN_RESOURCE_CALCULATION` chain parameter) already exists but is **off by default** (`getAllowHardenResourceCalculation()` defaults to `0`), so the legacy, lossy arithmetic remains the live behavior on any chain where the SR committee has not yet activated the proposal.

### Finding Description
`BandwidthProcessor.calculateGlobalNetLimit` computes:
```java
long netWeight = frozeBalance / TRX_PRECISION;
return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
``` [1](#0-0) 

and `EnergyProcessor.calculateGlobalEnergyLimit` mirrors it:
```java
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [2](#0-1) 

In both cases `totalNetLimit / totalNetWeight` (or `totalEnergyLimit / totalEnergyWeight`) is evaluated first, in floating point, and only afterward multiplied by the account's weight — the same order-of-operations bug flagged in the report (`cache.fundingUsd = (cache.sizeOfLargerSide / Precision.FLOAT_PRECISION) * cache.durationInSeconds * cache.fundingFactorPerSecond;`). Doing the division first discards precision that the subsequent multiplication then compounds/loses, rather than first multiplying the numerators and dividing once by the combined denominator.

The codebase itself acknowledges this is a real precision bug: a hardened replacement was added that computes the same quantity via `BigInteger` with a single final division:
```java
protected long calculateGlobalLimitV1(long frozeBalance, long totalLimit, long totalWeight) {
    long weight = frozeBalance / TRX_PRECISION;
    return BigInteger.valueOf(weight)
        .multiply(BigInteger.valueOf(totalLimit))
        .divide(BigInteger.valueOf(totalWeight))
        .longValueExact();
}
``` [3](#0-2) 
and a similar `calculateGlobalLimitV2` for the fractional-weight V2 path [4](#0-3) . Both `calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` and `calculateGlobalEnergyLimit`/`calculateGlobalEnergyLimitV2` only use these hardened paths when `hardenCalculation()` (i.e. `dynamicPropertiesStore.allowHardenResourceCalculation()`) is true [5](#0-4) [6](#0-5) .

That flag defaults to `0` (off) unless a committee proposal explicitly enables `ALLOW_HARDEN_RESOURCE_CALCULATION`:
```java
public long getAllowHardenResourceCalculation() {
    return Optional.ofNullable(getUnchecked(ALLOW_HARDEN_RESOURCE_CALCULATION))
        .map(BytesCapsule::getData).map(ByteArray::toLong).orElse(0L);
}
``` [7](#0-6) 
and can only be turned on, never disabled, via a governance proposal gated behind fork `VERSION_4_8_2` [8](#0-7) . Until that proposal passes on a given network, `calculateGlobalNetLimit`/`calculateGlobalEnergyLimit` run the legacy divide-then-multiply arithmetic on **every single transaction** that consumes bandwidth or energy from frozen balance (`useAccountNet`, `useEnergy`), since these limits gate whether the transaction can use free-of-charge frozen-resource capacity [9](#0-8) [10](#0-9) .

### Impact Explanation
This is reachable from any unprivileged account submitting any ordinary transaction (transfer, contract call, etc.), since resource-limit calculation runs on the standard transaction-processing path for every account with frozen bandwidth/energy — squarely within the allowed "bandwidth accounting" analog class. The double-precision divide-then-multiply can misstate an account's true resource entitlement relative to the exact `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)` value the network intends, which can (a) let some accounts consume slightly more free bandwidth/energy than they are entitled to (an unbacked-resource condition analogous to unbacked balance) or (b) undercount entitlement and incorrectly reject/charge legitimate transactions. At network scale (aggregated across all frozen accounts, and repeated every transaction) these discrepancies are systemic rather than a one-off rounding error, matching the "larger precision loss" characterization in the referenced report.

### Likelihood Explanation
The buggy path is not an edge case — it is the **default, currently active** arithmetic on any deployment where `ALLOW_HARDEN_RESOURCE_CALCULATION` has not been enabled by proposal, and it executes on every bandwidth/energy-limited transaction from every account with frozen balance. No special privileges are required to trigger it; it fires automatically as part of standard transaction validation/execution.

### Recommendation
Make the hardened, BigInteger-based single-division computation (`calculateGlobalLimitV1`/`V2`) the default and unconditional implementation for `calculateGlobalNetLimit`, `calculateGlobalNetLimitV2`, `calculateGlobalEnergyLimit`, and `calculateGlobalEnergyLimitV2`, removing dependence on `double` arithmetic and on the opt-in `ALLOW_HARDEN_RESOURCE_CALCULATION` flag (or activate that proposal by default going forward), so that all networks compute `frozeBalance * totalLimit / (TRX_PRECISION * totalWeight)` with a single final truncation as already implemented in the hardened helpers.

### Proof of Concept
The repository's own test suite demonstrates the discrepancy between the legacy and hardened paths for the same inputs, confirming the precision-loss bug class is live in the default configuration:
```java
dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(0);
long v1Old = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule); // uses legacy divide-then-multiply
...
dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(1);
long v1New = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule); // uses BigInteger single-division
``` [11](#0-10) 
and a fractional-weight test explicitly comments on the differing results between the legacy V1 (`floor(weight)`-first) and V2 fractional paths [12](#0-11) , evidencing that the un-hardened production path (default `ALLOW_HARDEN_RESOURCE_CALCULATION = 0`) yields the imprecise result that the report's bug class describes.

  @Test
  public void testV1FlooredWeightVsV2FractionalWeight() {
    dbManager.getDynamicPropertiesStore().saveTotalEnergyCurrentLimit(50_000_000_000L);
    dbManager.getDynamicPropertiesStore().saveTotalEnergyWeight(2_000_000_000L);
    long frozeBalance = 1_500_000L; // 1.5 x TRX_PRECISION

    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(1);

    // V1 path
    dbManager.getDynamicPropertiesStore().saveUnfreezeDelayDays(0);
    ownerCapsule.setFrozenForEnergy(frozeBalance, 0L);
    dbManager.getAccountStore().put(ownerCapsule.getAddress().toByteArray(), ownerCapsule);
    long v1New = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);

    // Legacy V1 expectation: floor(1.5) * 25.0 = 1 * 25 = 25
    Assert.assertEquals(25L, v1New);

    // V2 path with the same balance keeps the fractional weight
    long v2New = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    // Legacy V2 expectation: 1.5 * 25.0 = 37.5 -> 37
    Assert.assertEquals(37L, v2New);

    // And both must match their respective legacy doubles
    dbManager.getDynamicPropertiesStore().saveAllowHardenResourceCalculation(0);
    long v1Old = energyProcessor.calculateGlobalEnergyLimit(ownerCapsule);
    long v2Old = energyProcessor.calculateGlobalEnergyLimitV2(frozeBalance);
    Assert.assertEquals(v1Old, v1New);
    Assert.assertEquals(v2Old, v2New);
  }
