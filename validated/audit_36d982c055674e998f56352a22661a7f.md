Based on my investigation, I found a valid analog. The `handleCreateRelayRequest` function in `relay_manager.go` accepts an attacker-controlled `RelayFromAddr` field from the `NebulaControl` message body and uses it directly as the key for relay state (`AddRelay(rm.l, h, f.hostMap, from, ...)`), without verifying that `from` is actually an address that the authenticated sender `h` is entitled to relay for. This mirrors the Perennial bug pattern exactly: the message is authenticated as coming from `h` (via the Noise-encrypted, cert-verified tunnel — the "signer"), but the action (installing/mutating relay routing state) is performed against an arbitrary third-party address (`from`/`RelayFromAddr`, analogous to `common.account`) taken from the message body, with no check that `h` is authorized to act on behalf of that address.

### Title
Unauthenticated `RelayFromAddr` in `handleCreateRelayRequest` allows any authenticated peer to poison another host's relay routing state for an arbitrary victim address - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` trusts the `RelayFromAddr`/`RelayToAddr` fields carried inside an attacker-supplied `NebulaControl` message body as the identity of the party being relayed, without any check that the authenticated sender `h` (verified only via the encrypted tunnel/cert) is entitled to claim that address. This lets any peer with a valid certificate install relay state on a victim terminal node that associates an arbitrary third-party VPN address with the attacker as its relay path.

### Finding Description
`HandleControlMsg` dispatches `NebulaControl_CreateRelayRequest` messages to `handleCreateRelayRequest(v, h, f, msg)`, where `h` is the `*HostInfo` of the already-authenticated tunnel peer that physically sent the control packet [1](#0-0) . Inside `handleCreateRelayRequest`, the addresses used to decide what relay state to create are taken directly from the message body supplied by that same peer:
```
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
``` [2](#0-1) 

When `target` is one of our own addresses, the code calls `AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)`, which installs relay routing state on `h` keyed by the attacker-chosen `from` address — with no verification that `from` corresponds to a real peer that legitimately uses `h` as its relay, nor that `h`'s certificate or any other trust anchor permits it to speak for `from` [3](#0-2) . Compare this to the authenticated-but-not-authorized pattern in the report: the request is signed/authenticated as coming from `h` (equivalent to `common.signer`), but the resulting state mutation is keyed to `from` (equivalent to `common.account`), which is never checked against `h`'s own identity or any allow-list.

`AddRelay` itself performs no ownership check either — it just marks `relayHostInfo` (`h`) as primary and inserts the relay keyed by whatever `vpnIp` (i.e. `from`) is passed in [4](#0-3) .

### Impact Explanation
An attacker who has a valid certificate and an established tunnel to a victim terminal node `T` can send a `CreateRelayRequest` claiming `RelayFromAddr = V` (any victim address on the network) and `RelayToAddr = T`. `T` will install `Established` relay state believing that traffic to `V` should be routed via the attacker's tunnel [3](#0-2) . Any node that later queries `T` as a relay path for `V` (e.g., via lighthouse relay advertisement or `QueryVpnAddrsRelayFor`) could be steered to route `V`'s traffic through the attacker, enabling traffic redirection/interception for a third party who never asked to be relayed through the attacker. This is a remote state-poisoning primitive: the routing/relay table of an honest node is corrupted using data that was never validated against the true owner of that address.

### Likelihood Explanation
Any node holding a valid, CA-signed certificate (a legitimate but potentially malicious peer) can trigger this by sending a single crafted `CreateRelayRequest` control message over its own already-established tunnel — no special privileges, no interaction with the victim, and no race condition are required. The relay control-message path is reachable from any authenticated peer.

### Recommendation
When processing `CreateRelayRequest`/`CreateRelayResponse`, validate that the claimed `RelayFromAddr` is consistent with the sending peer's own authenticated identity (e.g., `h.vpnAddrs`) for the terminal case, or otherwise restrict relay state installation to addresses that have an independent trust basis (such as a lighthouse-confirmed relay assignment) rather than trusting the unauthenticated address fields embedded in the control message body.

### Proof of Concept
1. Attacker `A` obtains a valid, CA-signed certificate and completes a normal handshake with terminal node `T` (both trust the same CA), giving `A` an authenticated `HostInfo` `h` on `T`.
2. `A` crafts a `NebulaControl{Type: CreateRelayRequest, RelayFromAddr: netAddrToProtoAddr(V), RelayToAddr: netAddrToProtoAddr(T's address), InitiatorRelayIndex: <any>}` where `V` is a victim address `A` does not own [5](#0-4) .
3. `A` sends this as a `header.Control` message over the existing authenticated tunnel to `T`.
4. `T`'s `handleCreateRelayRequest` sees `target == T`'s own address, finds no existing relay state for `from=V`, and calls `AddRelay(rm.l, h, f.hostMap, V, &InitiatorRelayIndex, TerminalType, Established)`, installing relay state on `h` (attacker's hostinfo) keyed by `V` [6](#0-5) .
5. `T` now believes `A` is a valid relay path to reach `V`, without `V` or any CA ever having attested to that relationship.

		}
