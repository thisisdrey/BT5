### Title
Dust deposits can permanently block `Pool.removeDepositToken` / `removeDebtToken` via `totalSupply() > 0` check - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.removeDepositToken` (Pool.sol:737-744) and `Pool.removeDebtToken` (Pool.sol:725-732) revert with `TotalSupplyIsNotZero` when the target token's `totalSupply() > 0`. An unprivileged attacker can front-run the governor's removal transaction with a dust deposit (or dust issuance) to keep `totalSupply` non-zero, indefinitely blocking removal — the same bug class as the Kelp `removeNodeDelegatorContractFromQueue` zero-balance grief, except here the attacker mints supply through a public entry point rather than donating tokens.

### Finding Description
The governor-facing removal functions are gated on zero supply:

```solidity
// contracts/Pool.sol:725-732
function removeDebtToken(IDebtToken debtToken_) external onlyGovernor {
    if (debtToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}

// contracts/Pool.sol:737-744
function removeDepositToken(IDepositToken depositToken_) external onlyGovernor {
    if (depositToken_.totalSupply() > 0) revert TotalSupplyIsNotZero();
    ...
}
```

`DepositToken._mint` (DepositToken.sol:469-489) imposes no minimum mint amount — it only enforces `SurpassMaxDepositSupply` and `onlyIfDepositTokenIsActive`. An attacker with any underlying balance can therefore call the public deposit entry point to mint 1 wei of the msdToken to themselves at negligible cost, inflating `totalSupply` above zero.

Attack path for `removeDepositToken`:
1. Governor has queued/broadcast `removeDepositToken(msdToken)` expecting `totalSupply == 0` after the last depositor withdrew.
2. Attacker monitors the mempool and front-runs with `depositToken.deposit(1)` (or `deposit(1, attacker)`), minting dust.
3. Removal reverts with `TotalSupplyIsNotZero`.
4. Attacker can repeat on every retry, or simply hold the dust forever — the token can never be removed while they refuse to withdraw.

The same applies to `removeDebtToken`: an attacker can hold a dust debt position (minted via `DebtToken` issuance through `Pool.mint` with dust collateral backing), keeping debt-token `totalSupply > 0`. This is costlier (requires collateral and a healthy position) but still fully permissionless.

### Impact Explanation
The protocol loses the ability to delist a collateral or debt token for as long as the attacker holds dust. This is a governance/liveness break rather than direct theft, but it has a concrete security consequence: a compromised, depegged, or oracle-deprecated collateral cannot be cleanly removed from `depositTokens`, and `depositTokenOf[underlying]` remains occupied — also blocking re-registration of a replacement DepositToken for the same underlying via `UnderlyingAssetInUse` (Pool.sol:701). The grief is continuous and cheap (one dust deposit per attempt, or a single permanent dust hold).

### Likelihood Explanation
- Fully permissionless: any EOA can deposit; no governor/keeper/oracle involvement.
- Cost is near zero: 1 wei of underlying plus gas; the attacker can even keep the dust position permanently.
- The only mitigation is ordering: the governor must first call `DepositToken.toggleIsActive()` (DepositToken.sol:559) or pause/shutdown deposits, then wait for all holders to withdraw — but existing holders are never forced to withdraw, so a dedicated attacker holding 1 wei still blocks removal even with deposits disabled. The check as written makes removal effectively impossible against an adversary who keeps dust on the books.
- Deposit fee (`quoteDepositIn`, DepositToken.sol:278-286) may make dust slightly more expensive but cannot reduce `totalSupply` to zero.

### Recommendation
Do not gate removal on `totalSupply == 0`, or gate it on a threshold that dust cannot violate. Concretely:
- Remove the `TotalSupplyIsNotZero` check and instead prevent new supply (require `!isActive` / paused), leaving residual balances to be withdrawn by holders; or
- Track removal via a `delisted` flag that blocks deposits/mints/issuance while permitting withdrawals/repayments, so stragglers (including dust) don't block delisting; or
- Provide a governor `seize`/`sweep` path to force-burn residual dust before removal.

### Proof of Concept
Hardhat fork outline (against deployed `Pool` + a registered `DepositToken`, e.g. msdtoken for WETH on Base):

```ts
// Assume: all real depositors have withdrawn; depositToken.totalSupply() == 0
const attacker = await ethers.getImpersonatedSigner(randomEoa);
await underlying.mint(attacker.address, 1); // or obtain 1 wei of WETH/USDC
await underlying.connect(attacker).approve(depositToken.address, 1);

// Front-run governor's removeDepositToken
await depositToken.connect(attacker).deposit(1); // mints dust msdToken
expect(await depositToken.totalSupply()).to.eq(1);

// Governor removal now reverts
await expect(
  pool.connect(governor).removeDepositToken(depositToken.address)
).to.be.revertedWithCustomError(pool, "TotalSupplyIsNotZero");
```

Caveat: I did not fully verify the exact public `deposit` function signature in `DepositToken.sol` (only `_mint` internals at lines 469-489 were read); the PoC should use the actual public deposit entry point, which exists since `_mint` is invoked by user-facing deposits.
