### Title
Permanent stuck `custom_hooks/.lock` bricks `SetCustomHooks`/`RestoreCustomHooks` forever - (File: internal/gitaly/repoutil/custom_hooks.go)

### Summary
`SetCustomHooks` and `RestoreCustomHooks` acquire a directory lock (`custom_hooks/.lock`) before extracting a new hooks tarball, and only release it via a `defer`-scheduled `Unlock()` call. If that unlock never executes (process crash, OOM-kill, container restart, or any abnormal termination between `Lock()` succeeding and the deferred `Unlock()` running), the lock file is left on disk permanently — with no automated staleness sweep to reclaim it, unlike other Gitaly lock files (`HEAD.lock`, `packed-refs.lock`, etc.) which are covered by housekeeping's `FindStaleLockfiles`/`CleanStaleData`. This is the same bug class as the ArtGobblers `randProvider` report: an unprivileged, externally-triggerable event (interrupted RPC) flips a "waiting/locked" flag that only a very specific follow-up action can clear, and if that follow-up never happens, the feature is bricked forever with no owner-level escape hatch.

### Finding Description
`internal/gitaly/repoutil/custom_hooks.go`'s `SetCustomHooks` acquires a `safe.NewLockingDirectory(repoPath, customHooksDir)` lock and schedules its release in a `defer`, explicitly acknowledging the risk in its own comment: [1](#0-0) 

```
hooksLock, err := safe.NewLockingDirectory(repoPath, customHooksDir)
...
if err := hooksLock.Lock(); err != nil {
    return fmt.Errorf("locking hooks: %w", err)
}
defer func() {
    // If the `.lock` file is not removed from the `custom_hooks` directory,
    // future modifications to the repository's hooks will be prevented. If
    // this occurs, the `.lock` file will have to be manually removed.
    if err := hooksLock.Unlock(); err != nil {
        ctxlogrus.Extract(ctx).WithError(err).Warn("failed to unlock hooks")
    }
}()
```

Both gRPC entry points, `SetCustomHooks` and `RestoreCustomHooks`, funnel into this same locking code path: [2](#0-1) [3](#0-2) 

The underlying primitive, `safe.LockingFileWriter`/`LockingDirectory`, creates the on-disk `.lock` file with `O_CREATE|O_EXCL` and only removes it via an explicit `unlock()` call — there is no TTL, expiry, or background reaper for this specific lock file, unlike the reference/pack/config lock files which are actively scanned and cleared by grace-period-based housekeeping: [4](#0-3) [5](#0-4) 

The test fixture list of lock files covered by `FindStaleLockfiles`/`CleanStaleData` (`HEAD.lock`, `config.lock`, `attributes.lock`, `alternates.lock`, `commit-graph-chain.lock`, `packed-refs.lock`, `multi-pack-index.lock`) confirms `custom_hooks/.lock` is not among the automatically-swept files: [6](#0-5) 

If the process handling `SetCustomHooks`/`RestoreCustomHooks` dies abnormally (OOM kill, `SIGKILL`, node crash, panic bypassing the deferred cleanup) after `hooksLock.Lock()` succeeds but before `Unlock()` runs, the lock file survives the process. Every subsequent call to `SetCustomHooks` or `RestoreCustomHooks` for that repository will hit `ErrFileAlreadyLocked` and fail — indefinitely, exactly as in the `waitingForSeed=true` deadlock in the ArtGobblers report, since there is neither an internal automatic reset path nor an RPC-exposed "force unlock" for an operator to call; per the code's own comment, the fix requires **manual filesystem-level removal** of the lock file.

### Impact Explanation
This denies the core "update custom server hooks" functionality for the affected repository permanently (until manual filesystem intervention), analogous to the ArtGobblers gobbler-reveal brick which permanently denied the "mint goo" functionality. Unlike Praefect's PostgreSQL-backed `RepoReferenceWriteLockManager`, which has an `expired_at` TTL and background sweep specifically to avoid this class of bug, the `custom_hooks/.lock` file has no such safety net.

### Likelihood Explanation
Any abnormal termination of the Gitaly process mid-`SetCustomHooks`/`RestoreCustomHooks` call (which can be triggered by an ordinary caller sending the RPC and having the connection or process die at the wrong moment, node OOM, or pod eviction in Kubernetes deployments) is sufficient to leave the lock behind — no malicious or privileged actor is required, only an interruption at an unlucky point in the write path. This RPC is invoked as part of normal repository lifecycle operations (custom hooks configuration, backup restore), making the trigger condition externally reachable rather than contingent on insider access.

### Recommendation
Bring `custom_hooks/.lock` cleanup in line with the other repository lock files: either (a) add it to `housekeeping.FindStaleLockfiles`'s tracked lock set so `CleanStaleData` can reclaim it after a grace period, or (b) give `LockingDirectory`/`LockingFileWriter` an age-based staleness check in `Lock()` itself (similar to `FindStalePackFileLocks`'s grace-period logic) so a new `SetCustomHooks`/`RestoreCustomHooks` call can safely steal an expired lock instead of failing forever.

### Proof of Concept
1. Call `SetCustomHooks` (or `RestoreCustomHooks`) for a repository; once `hooksLock.Lock()` succeeds and before the tar extraction/commit completes, forcibly kill the Gitaly process (e.g. `kill -9`) so the `defer hooksLock.Unlock()` never runs.
2. Restart Gitaly and observe that `<repoPath>/custom_hooks/.lock` still exists on disk.
3. Call `SetCustomHooks` again for the same repository — it fails with `structerr.NewInternal("setting custom hooks: %w", safe.ErrFileAlreadyLocked)` (via `internal/gitaly/service/repository/set_custom_hooks.go`) forever, until an operator manually deletes the lock file from disk, since no housekeeping job or RPC covers this specific lock.

```go
func (fw *LockingFileWriter) Lock() error {
	if fw.state != lockingFileWriterStateOpen {
		return fmt.Errorf("file writer not lockable")
	}

	if err := fw.checkConcurrentModification(); err != nil {
		return err
	}

	lock, err := os.OpenFile(fw.lockPath(), os.O_CREATE|os.O_EXCL|os.O_RDONLY, mode.File)
	if err != nil {
		if os.IsExist(err) {
			return ErrFileAlreadyLocked
		}

		return fmt.Errorf("creating lock file: %w", err)
	}
	_ = lock.Close()

	fw.state = lockingFileWriterStateLocked

	return nil
}

func (fw *LockingFileWriter) unlock() error {
	// We only want to unlock in case we have locked this file ourselves. Otherwise, we risk
	// removing the lock from another, concurrent locking file writer.
	if fw.state != lockingFileWriterStateLocked {
		return fmt.Errorf("file writer not locked")
	}

	if err := os.Remove(fw.lockPath()); err != nil {
		return fmt.Errorf("removing lock file: %w", err)
	}

	fw.state = lockingFileWriterStateClosed

	return nil
}
```
