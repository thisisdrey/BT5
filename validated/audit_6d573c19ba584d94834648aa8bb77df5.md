## Analysis

The core Cairo bug pattern is: **using a hard revert (`assert`) instead of graceful error return when validating cross-chain/cross-contract data, leaving the system stuck in an inconsistent intermediate state**. The strongest reachable analog in `nearcore` is the incoming-receipt validation path in the runtime, which is explicitly marked with a `TODO` acknowledging it should be handled gracefully but instead panics the entire chunk-apply process (and thus the node) when a receipt fails validation.

### Title
Incoming cross-shard receipt validation failure panics the chunk-apply pipeline instead of gracefully rejecting the receipt - (File: `runtime/runtime/src/lib.rs`, `chain/chain/src/runtime/mod.rs`)

### Summary
`Runtime::process_incoming_receipts` validates every incoming (cross-shard) receipt via `validate_receipt(..., ValidateReceiptMode::ExistingReceipt)` and, on failure, wraps the error as `RuntimeError::ReceiptValidationError` and propagates it out of `Runtime::apply`. The caller in `chain/chain/src/runtime/mod.rs::apply_chunk` explicitly converts this error class into a hard `panic!`, crashing the node's chunk-application flow rather than handling the invalid receipt gracefully (e.g., skipping/delaying it and returning an error result), exactly the same class of "assert on invalid handler/data instead of returning a controlled failure" seen in the Cairo `receive_cross_chain_callback`. [1](#0-0) [2](#0-1) 

### Finding Description
When applying a chunk, incoming receipts (produced by other shards and delivered via cross-shard receipt forwarding) are validated with `validate_receipt`: [2](#0-1) 

If validation fails, the error is mapped to `RuntimeError::ReceiptValidationError` and bubbles out of `apply()`. At the call site in the chain-runtime adapter, this specific error variant is treated as unrecoverable and turned into a `panic!`, with an explicit `// TODO(#2152): process gracefully` comment acknowledging the shortfall: [3](#0-2) 

The underlying `validate_receipt`/`validate_action_receipt` checks include things such as `NumberInputDataDependenciesExceeded`, `InvalidRefundTo`, `InvalidPredecessorId`/`InvalidReceiverId`, and action-validation errors, evaluated against the **current** `LimitConfig`/protocol version at the time the receipt is processed on the *receiving* shard: [4](#0-3) 

The `ValidateReceiptMode::ExistingReceipt` doc comment itself concedes that older/received receipts may legitimately fail the same checks a freshly-created receipt would pass, and that runtime "has to handle them gracefully until the receipt size limit bug is fixed" — yet the actual code path for `ReceiptValidationError` at the `apply_chunk` boundary does the opposite of "gracefully": it panics. [5](#0-4) 

This mirrors the Cairo bug precisely: a validation step that *should* return a controlled failure result instead uses an unconditional abort, and the code silently trusts that the "handler" (here, the incoming receipt) will always be valid — an assumption that is not actually guaranteed across protocol version boundaries or receipt-origination differences between sending/receiving shards, since limit configs and validation rules can change between chunk production and receipt consumption (this is the exact scenario the `ExistingReceipt` mode/TODO comment is trying to work around, but only partially).

### Impact Explanation
If any incoming receipt reaches a shard and fails `validate_receipt` (for example, due to a limit-config or protocol-version mismatch between the block that produced the receipt and the block that consumes it, or any other latent divergence not otherwise caught upstream), every validator applying that chunk hits the same `panic!`. Because chunk application is deterministic and executed by all validators for that shard, this is not a single-node crash but a **shard-halting panic**: the shard/chain cannot make progress past that block since all honest nodes independently panic while applying the same receipt. This falls squarely within the accepted impact class of "a shard-halting panic," and is reachable purely through the normal cross-shard receipt-forwarding path exercised by ordinary transactions — no privileged or malicious-node access is required to *trigger* it, only a receipt that fails post-hoc validation on the receiving side.

### Likelihood Explanation
The likelihood is constrained by the fact that receipts are normally validated at creation time on the sending shard, so under stable configuration this path should not normally trigger. However, the code's own documentation (`ValidateReceiptMode::ExistingReceipt`, the linked issue #12606, and the `TODO(#2152)` marker) acknowledges that such receipts can and do exist in practice, meaning this is not a purely theoretical path — it is a known, unresolved gap in defensive handling that the team itself flagged as needing graceful handling but never implemented. Given protocol upgrades, config changes, or edge-case receipts, this remains a live, reachable failure mode of at least medium-to-high likelihood in a network operating across protocol/config transitions.

### Recommendation
Do not `panic!` on `RuntimeError::ReceiptValidationError` in `chain/chain/src/runtime/mod.rs::apply_chunk`. Instead, treat validation failures for incoming/delayed receipts as a recoverable per-receipt condition: either skip/quarantine the offending receipt (analogous to how invalid transactions are already skipped elsewhere, per the doc comment on `Runtime::apply` about invalid transactions), or convert it into a proper `Error` variant that chain code can handle without aborting the whole chunk-apply pipeline, consistent with the existing (unresolved) `TODO(#2152)` intent.

### Proof of Concept
A concrete PoC would require constructing a receipt that passes the sending shard's `validate_receipt` (at receipt-creation time, under the protocol version/config then in effect) but fails when re-validated as an `ExistingReceipt` on the receiving shard in a later block operating under a different `LimitConfig`/protocol version (e.g., a receipt whose `input_data_ids` count or refund-to account id becomes invalid after a config/protocol change). I could not fully verify a concrete, currently-reachable trigger sequence (e.g., a specific protocol-version transition that shrinks a limit checked in `validate_action_receipt`) within the available code index; this would need deeper cross-referencing of `LimitConfig` history across protocol versions and the exact conditions under which a once-valid receipt can later fail `ExistingReceipt` validation, which a live Devin session with full repository/history access could confirm concretely.

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum ValidateReceiptMode {
    /// Used for validating new receipts that were just created.
    /// More strict than `OldReceipt` mode, which has to handle older receipts.
    NewReceipt,
    /// Used for validating older receipts that were saved in the state/received. Less strict than
    /// NewReceipt validation. Tolerates some receipts that wouldn't pass new validation. It has to
    /// be less strict because:
    /// 1) Older receipts might have been created before new validation rules.
    /// 2) There is a bug which allows to create receipts that are above the size limit. Runtime has
    ///    to handle them gracefully until the receipt size limit bug is fixed.
    ///    See https://github.com/near/nearcore/issues/12606 for details.
    ExistingReceipt,
}

fn validate_action_receipt(
    limit_config: &LimitConfig,
    receipt: VersionedActionReceipt,
    receiver: &AccountId,
    current_protocol_version: ProtocolVersion,
    mode: ValidateReceiptMode,
) -> Result<(), ReceiptValidationError> {
    if receipt.input_data_ids().len() as u64 > limit_config.max_number_input_data_dependencies {
        return Err(ReceiptValidationError::NumberInputDataDependenciesExceeded {
            number_of_input_data_dependencies: receipt.input_data_ids().len() as u64,
            limit: limit_config.max_number_input_data_dependencies,
        });
    }

    if let Some(account_id) = receipt.refund_to() {
        AccountId::validate(account_id.as_ref()).map_err(|_| {
            ReceiptValidationError::InvalidRefundTo { account_id: account_id.to_string() }
        })?;
    }

    validate_actions_with_mode(
        limit_config,
        receipt.actions(),
        receiver,
        current_protocol_version,
        mode,
    )
    .map_err(ReceiptValidationError::ActionsValidation)
}
