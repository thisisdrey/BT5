### Title
First depositor can steal reward tokens equal to full deposit balance via `INITIAL_INDEX` accounting flaw - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` treats an `accountIndexOf == 0` account as if it entered at `INITIAL_INDEX` only when the global index is strictly greater than `INITIAL_INDEX`. During the window where `tokenStates[token_].index == INITIAL_INDEX` (the same block in which the reward speed is first activated), an account with a nonzero token balance and `accountIndexOf == 0` accrues `deltaIndex = INITIAL_INDEX = 1e18`, i.e. `tokensDelta = balanceOf(account)` reward tokens for zero elapsed time. The accrual hooks are permissionless, so the attacker triggers this himself and immediately calls `claimRewards`.

### Finding Description
Metronome's reward accounting is index-based rather than debt-based, but it has the same "claim more than entitled" flaw.

- `updateBeforeMintOrBurn` / `updateBeforeTransfer` / `claimRewards` all skip work when `tokenStates[token_].index == 0` (contracts/RewardsDistributor.sol:176,187,156). So while a token has `speed == 0`, accounts accumulate balances with `accountIndexOf[token][account] == 0`.
- When the governor first sets a nonzero speed, `_updateTokenSpeed` initializes `tokenStates[token_] = {index: INITIAL_INDEX, timestamp: block.timestamp}` (contracts/RewardsDistributor.sol:298).
- In `_calculateTokenDelta`, the "new account" correction only applies when `_tokenIndex > INITIAL_INDEX`: 
```solidity
if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```
(contracts/RewardsDistributor.sol:225-230)
- If `_tokenIndex == INITIAL_INDEX` exactly, the fallback is skipped and `_deltaIndex = 1e18`, so `_tokensDelta = balance` (wadMul by 1e18 is identity).
- `_calculateTokenIndex` returns `(0,0)` when `deltaTimestamp == 0` (contracts/RewardsDistributor.sol:202-211), so the index stays exactly `INITIAL_INDEX` for the entire activation block.
- `updateBeforeMintOrBurn(IERC20,address)` is callable by anyone for any account (contracts/RewardsDistributor.sol:175-180), and `_updateTokensAccruedOf` adds the delta to `tokensAccruedOf` (contracts/RewardsDistributor.sol:261-265). `claimRewards` then pays out `tokensAccruedOf` up to the contract's reward balance (contracts/RewardsDistributor.sol:150-167, 248-256).

Attack path (unprivileged EOA only):
1. Before rewards are activated for a `DepositToken`/`DebtToken` (speed = 0, index = 0), deposit to hold a large share balance `B`. Hooks no-op, `accountIndexOf` stays 0.
2. When the governor's `updateTokenSpeed` (or `syncTokenSpeed`) activates the token — index becomes `INITIAL_INDEX` — the attacker back-runs it in the same block: `updateBeforeMintOrBurn(token, attacker)` → `tokensAccruedOf[attacker] += B` (in reward-token units).
3. `claimRewards(attacker)` drains up to `B` reward tokens from the distributor, stolen from all other users' unclaimed yield.

No health checks, locks, or guards intervene: `updateBeforeMintOrBurn` has no access control, and `claimRewards`'s `nonReentrant` doesn't matter since no reentrancy is needed.

### Impact Explanation
Direct theft of unclaimed yield: the attacker is credited reward tokens equal to their entire deposit/debt token balance with zero accrual time, bounded only by the distributor's reward token balance. The reward pool can be fully drained.

### Likelihood Explanation
Requires holding shares before speed activation and executing in the same block as the speed activation transaction. Both are achievable: deposits while speed is 0 are normal user actions, and `updateTokenSpeed`/`syncTokenSpeed` calls are observable in the mempool for back-running. Speeds being 0 before activation is the normal initial state of every newly listed deposit/debt token, so the vulnerable window exists once per token per distributor.

### Recommendation
Apply the `INITIAL_INDEX` fallback when `_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX` (i.e. treat any zero account index as entry at `INITIAL_INDEX`), or explicitly clamp `accountIndexOf` for accounts with zero recorded index when the global index equals `INITIAL_INDEX`. Alternatively, in `_updateTokenSpeed`, when initializing a token, iterate/check is impractical — the cleaner fix is `if (_accountIndex == 0) _accountIndex = _tokenIndex > INITIAL_INDEX ? _tokenIndex : INITIAL_INDEX;` equivalent to `_accountIndex = INITIAL_INDEX` whenever `_accountIndex == 0`.

### Proof of Concept
Hardhat-style sketch against existing test fixtures (mirroring `test/RewardDistributor.test.ts`):

```ts
// attacker deposits while speed == 0 (index == 0): hooks no-op
await depositToken.mint(attacker.address, parseEther('100'))
expect(await rewardDistributor.accountIndexOf(depositToken.address, attacker.address)).eq(0)

// governor activates rewards; attacker back-runs in same block (automine off)
await ethers.provider.send('evm_setAutomine', [false])
await rewardDistributor.updateTokenSpeed(depositToken.address, parseEther('1'))
await rewardDistributor.updateBeforeMintOrBurn(depositToken.address, attacker.address)
await rewardDistributor['claimRewards(address)'](attacker.address)
await ethers.provider.send('evm_mine', [])

// attacker received ~100 reward tokens for zero elapsed accrual
expect(await rewardToken.balanceOf(attacker.address)).eq(parseEther('100'))
```

For a fork test: impersonate governor to call `updateTokenSpeed` on an existing deposit token with speed 0, pre-seed an attacker balance via deposit, disable automine to land `updateBeforeMintOrBurn` + `claimRewards` in the activation block, and assert reward-token balance increases by the attacker's deposit-token balance.
