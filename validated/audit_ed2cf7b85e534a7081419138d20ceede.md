### Title
Unauthenticated dust transfers can exhaust `MAX_TOKENS_PER_USER` and freeze collateral/debt onboarding - ([File: `contracts/DepositToken.sol`])

### Summary
`DepositToken.transfer()` and `transferFrom()` add every first-time recipient to the recipient’s per-account `depositTokensOfAccount` set, even for a 1-wei transfer. Once the combined debt-token and deposit-token lists reach `Pool.MAX_TOKENS_PER_USER == 30`, `Pool.addToDepositTokensOfAccount()` and `addToDebtTokensOfAccount()` revert. An attacker who already holds dust balances in the supported deposit tokens can therefore fill a victim’s list and temporarily block the victim from receiving a new collateral type, depositing into a new collateral type, or adding a new debt token. [1](#0-0) [2](#0-1) 

### Finding Description
The vulnerable sequence starts at public `DepositToken.transfer()` / `transferFrom()`. Both call `_transfer()`, which unconditionally calls `Pool.addToDepositTokensOfAccount(recipient_)` when the recipient’s prior balance is zero. [3](#0-2) [4](#0-3) [5](#0-4) 

`Pool.addToDepositTokensOfAccount()` validates only that the caller is an enabled deposit token; the recipient does not consent to being added. [6](#0-5) 

The same shared cap is applied before adding either a deposit token or debt token: when `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= 30`, the addition reverts with `UserReachedMaxTokens`. [7](#0-6) [1](#0-0) [8](#0-7) 

Each distinct supported `DepositToken` can occupy one victim slot by transferring one wei. On a deployed pool with 30 or more supported deposit tokens, or fewer deposit tokens plus existing debt-token entries, an attacker can reach the cap using only ordinary public transfers. Removal normally occurs only when the recipient transfers or withdraws the dust balance back to zero. [9](#0-8) [10](#0-9) 

For an account with an unhealthy or fully collateral-utilized position, `unlockedBalanceOf()` can return zero, causing `transfer()` and `withdraw()` to revert through `_revertIfLocked()`. In that state, the forced dust cannot be removed until the victim first reduces debt or otherwise restores unlocked balance, extending the freeze. [11](#0-10) [12](#0-11) 

### Impact Explanation
This creates temporary freezing of account functionality rather than direct theft. A victim at the cap cannot receive a new deposit token, so depositing a new collateral type or receiving a liquidation/seizure transfer into a fresh token reverts. If the victim also has all slots consumed and attempts to open a new debt position, the zero-to-nonzero debt transition reverts through `Pool.addToDebtTokensOfAccount()`. [13](#0-12) 

The issue is most severe for a leveraged or unhealthy victim because forced dust may be locked and cannot be removed until the position is repaired. The invariant broken is account-list accounting: a nonzero token balance does not merely represent user-selected exposure; an untrusted third party can create it and consume a scarce protocol slot. [12](#0-11) [2](#0-1) 

### Likelihood Explanation
The attack requires no privileged role, invalid oracle, governance action, malicious bridge component, or forged contract. It does require the deployed pool to have enough supported deposit tokens, alone or combined with the victim’s existing debt tokens, to reach 30 slots. The attacker must also acquire a nonzero balance in each deposit token used for the attack, which requires depositing or purchasing the corresponding tokenized deposits. [1](#0-0) [3](#0-2) 

Likelihood is therefore deployment-dependent. It is not a generic unbounded-storage issue: each victim list is capped at 30, and the attack’s cost scales with the number of supported deposit-token positions the attacker must acquire. [7](#0-6) 

### Recommendation
Do not add recipients to `depositTokensOfAccount` on permissionless ERC20-style transfers. Prefer one of:

- Maintain the list only for protocol minting paths such as `deposit()`, while calculating transferred balances separately.
- Add an explicit opt-in method for collateral accounting and exclude unsolicited transfers from position accounting.
- Allow victims to force-remove zero-value/unwanted entries, while ensuring donated dust is not treated as collateral backing debt.
- Keep transfer functionality unrestricted but move collateral indexing to an explicit per-account accounting structure that does not revert transfers solely because the recipient has too many assets.

Any design must preserve `depositOf()`, `debtPositionOf()`, liquidation, withdrawal, and reward-accounting behavior for transferred deposit tokens. [14](#0-13) [15](#0-14) 

### Proof of Concept
A reproducible Foundry fork test should use a deployed `Pool` whose `getDepositTokens()` returns at least 30 active deposit tokens:

```solidity
function testDustTransferFillsVictimTokenSlots() public {
    IPool pool = IPool(DEPLOYED_POOL);
    address victim = address(0xB0B);
    address attacker = address(this);

    address[] memory tokens = pool.getDepositTokens();
    assertGe(tokens.length, 30);

    for (uint256 i; i < 30; ++i) {
        IDepositToken token = IDepositToken(tokens[i]);

        // On a fork, acquire a nonzero position legitimately, e.g.:
        // 1. obtain token.underlying() from a whale or AMM;
        // 2. underlying.approve(address(token), amount);
        // 3. token.deposit(amount, attacker);
        //
        // Keep only a small unlocked balance and dust the victim.
        assertGt(token.balanceOf(attacker), 0);
        token.transfer(victim, 1);
    }

    assertEq(pool.getDepositTokensOfAccount(victim).length, 30);

    IDepositToken newToken = IDepositToken(pool.getDepositTokens()[30]);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    newToken.transfer(victim, 1);

    // If victim is unhealthy, cleanup also reverts:
    vm.startPrank(victim);
    vm.expectRevert(DepositToken.NotEnoughFreeBalance.selector);
    IDepositToken(tokens[0]).transfer(attacker, 1);
    vm.stopPrank();
}
```

The same result can be shown with fewer than 30 deposit tokens by first giving the victim enough distinct debt-token entries so `debtTokensOfAccount.length(victim) + depositTokensOfAccount.length(victim) == 30`. The relevant revert is enforced before every list insertion. [1](#0-0) [6](#0-5)
