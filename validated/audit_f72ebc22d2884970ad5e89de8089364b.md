## Title
Remote fee/reward rounds down to zero on fee-collection path while the committed Ethereum message still promises a fixed non-zero relayer reward - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`Pallet::<T>::calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` computes the sender-facing `fee.remote` by scaling the wei-denominated remote fee/reward and downcasting via `convert_from_ether_decimals`, which uses integer `checked_div` and can truncate the result to zero for legitimate, `validate()`-passing `PricingParameters`. Separately, `do_process_message` embeds the raw, non-truncated `pricing_params.rewards.remote` directly into the `CommittedMessage.reward` field sent to Ethereum, independent of what was actually charged to the message sender via `SendMessage::validate`.

## Finding Description
`calculate_fee` (L368-393) computes `fee_per_gas * gas_used_at_most + reward` in wei via `calculate_remote_fee`, multiplies by `multiplier`, divides by `exchange_rate`, then calls `convert_from_ether_decimals` (L414-418) which performs `value.checked_div(denom)` to downscale from 18 Ethereum decimals to the local chain's decimals (10 for Polkadot). This integer division can round the result to `0` for small `gas_used_at_most` and unit-scale parameters, even though `PricingParameters::validate()` (bridges/snowbridge/primitives/core/src/pricing.rs L39-56) only checks that the raw input fields (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) are individually non-zero — it never checks the derived, decimal-converted output actually charged to callers.

`send_message_impl.rs::validate` (L58-60) calls `calculate_fee` and returns this (possibly zero) `fee.remote` as the amount charged to the sender. Meanwhile, `do_process_message` (L332-352) independently reads `let reward = pricing_params.rewards.remote;` directly from governance parameters (guaranteed non-zero by `validate()`) and embeds it, untruncated, into the committed `CommittedMessage.reward` field that is promised to the relayer on Ethereum. There is no code path that ties the sender-charged `fee.remote` to the on-chain-promised `reward` — they are computed independently from the same source parameter but diverge due to decimal truncation.

This is directly reproduced by the pallet's own test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` (test.rs L303-319), which uses valid, non-zero `PricingParameters` (`exchange_rate=1`, `fee_per_gas=1`, `rewards={local:1, remote:1}`, `multiplier=1`) and asserts `fee.remote == 0` while `fee.local == 698000000`.

## Impact Explanation
This is a public underpriced work condition on the Snowbridge outbound-queue fee-collection path: an unprivileged sender can construct messages whose bounded `gas_used_at_most` (from `T::GasMeter::maximum_gas_used_at_most`) causes `calculate_fee`'s remote component to round to zero, allowing them to get messages enqueued and committed into the outbound Merkle root/`CommittedMessage` stream while paying nothing toward the remote/reward fee component — even though the committed message still encodes the full, non-zero `pricing_params.rewards.remote` as the reward promised to whichever relayer delivers it on Ethereum. Repeated exploitation creates a systematic shortfall between fees collected and rewards promised, and enables low-cost spam of outbound commitments to Ethereum, which the project's own `docs/v2.md` (L99-102) acknowledges as a risk requiring a minimum reward floor "to stop spamming messages with 0 rewards."

## Likelihood Explanation
High reachability: any unprivileged account invoking `SendMessage::validate` (e.g., via XCM export to Ethereum) with a message whose `gas_used_at_most` is small relative to the configured `exchange_rate`/`multiplier`/decimals scaling triggers this truncation during ordinary use, with no reliance on malicious relayers, compromised provers, or governance misbehavior — governance only sets valid, non-zero pricing parameters as intended. The pallet's own unit test independently confirms the zero-remote-fee outcome occurs with realistic, valid parameter values, not a contrived edge case.

## Recommendation
Enforce a floor on the computed `fee.remote` in `convert_from_ether_decimals`/`calculate_fee` (e.g., round up on division, or reject/clamp to a minimum non-zero value when the computed fee would be zero) so the amount charged to the sender can never fall below what covers the promised reward. Additionally, derive the `reward` field embedded in `CommittedMessage` within `do_process_message` from the same (possibly adjusted) fee value actually charged to the sender at `validate()` time, rather than recomputing it independently from the raw, untruncated `pricing_params.rewards.remote`, so the collected fee and promised payout never diverge.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);

			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
