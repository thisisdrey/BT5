### Title
Single stale advertised tenure bit permanently blocks recomputation of `available_tenures`, stalling Confirmed-mode tenure downloads - (File: stackslib/src/net/download/nakamoto/download_state_machine.rs)

### Summary
`NakamotoDownloadStateMachine::update_available_tenures` only recomputes `self.available_tenures`/`self.tenure_block_ids` when `count_available_tenure_neighbors(&self.available_tenures) == 0`. Because `self.available_tenures` is populated once per pass from peer inventories and is only cleared when `self.tenure_download_schedule` is empty, a single malicious peer that advertises one positive inventory bit and then disconnects leaves a stale `NeighborAddress` entry in `available_tenures` that is never pruned on disconnect, keeping the neighbor count above zero and blocking recomputation for all other genuinely available tenures.

### Finding Description
The guard in `update_available_tenures`: [1](#0-0) 
only clears/recomputes state when `tenure_download_schedule` is empty AND `count_available_tenure_neighbors(&self.available_tenures) == 0`. `count_available_tenure_neighbors` simply counts distinct `NeighborAddress` values currently present in the `available_tenures` map, without checking liveness/connectivity of those neighbors: [2](#0-1) 

`self.available_tenures` is populated wholesale from the merged `find_available_tenures` result inside `update_available_tenures` itself: [3](#0-2) 

and is subsequently mutated by `update_tenure_downloaders`, which passes it by mutable reference into `self.tenure_downloads.make_tenure_downloaders(...)`: [4](#0-3) 

The entries in this map are keyed by tenure consensus hash → list of neighbor addresses that advertised that tenure; they are only removed from the map when a downloader is actually created against a specific neighbor for that tenure. If the advertising peer disconnects before that consumption happens (or is otherwise not currently reachable), nothing in `update_available_tenures` or `count_available_tenure_neighbors` re-checks reachability — the map still contains that dead `NeighborAddress`, so `count_available_tenure_neighbors > 0` remains true indefinitely, causing the early return and preventing `available_tenures`/`tenure_block_ids` from ever being recomputed for the rest of the reward cycle, even though other live peers may have complete, useful inventories.

### Impact Explanation
This stalls Confirmed-mode tenure downloads for the affected node for the remainder of the reward cycle: legitimate, reachable peers' inventories are never folded into `available_tenures`/`tenure_block_ids`, so no new tenure download schedule is built and the node cannot make progress fetching tenure data behind the canonical tip. This is a liveness/DoS impact induced by a single crafted inventory message from one unprivileged peer, achievable without any secret or privileged role, matching the "steering a node off the tip" / stall-behind-canonical-tip category.

### Likelihood Explanation
Preconditions are minimal and attacker-cheap: connect as an ordinary P2P peer, send one inventory (`NakamotoTenureInv`) message with a single `true` bit for any wanted tenure, then disconnect or stop responding to tenure-data requests. No RPC secret, no StackerDB ownership, and no admin role is required — this is achievable by any remote peer that can complete a handshake. The bug is repeatable each reward cycle/schedule reset as long as the attacker (or any similarly-behaving disconnecting peer) can get one bit registered before dropping.

### Recommendation
In `update_available_tenures`/`count_available_tenure_neighbors`, only count neighbors that are currently connected/reachable (e.g., checking `NeighborRPC`/`comms.is_connected(naddr)` or equivalent liveness state) rather than raw presence in the `available_tenures` map. Alternatively, prune `available_tenures` entries for a `NeighborAddress` immediately when that peer disconnects from the `PeerNetwork`, so stale entries cannot keep the guard permanently true.

### Proof of Concept
Rust test plan in `stackslib/src/net/tests/download/nakamoto.rs`:
1. Build a `NakamotoDownloadStateMachine` with `wanted_tenures` containing several tenures.
2. Call `update_available_tenures` with an `inventories` map containing one mock peer `naddr_evil` that advertises exactly one tenure bit as `true`, producing a non-empty `available_tenures` containing only `naddr_evil`.
3. Simulate disconnection of `naddr_evil` (remove it from the `PeerNetwork`'s conversation table / mark it unreachable) without clearing `self.available_tenures`.
4. Call `update_available_tenures` again with a fresh `inventories` map containing several other, fully-connected peers advertising complete inventories for all wanted tenures.
5. Assert that `self.available_tenures` and `self.tenure_block_ids` remain unchanged (still only reference `naddr_evil`) and that `self.tenure_download_schedule` was not repopulated with the other wanted tenures — demonstrating the early return at `download_state_machine.rs:729-733` incorrectly treats the stale, disconnected `naddr_evil` entry as "still have requests to try."

        }
