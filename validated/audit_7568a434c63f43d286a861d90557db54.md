### Title
Unprivileged attacker can force-add deposit/debt tokens to a victim's per-account list, filling `MAX_TOKENS_PER_USER` and DoS-ing the victim's ability to add new collateral or mint new synthetics - (File: contracts/Pool.sol)

### Summary
Analogous to the `MechMarketplace.create` bug (anyone can write state keyed to another identity — `mapServiceIdMech[serviceId]` — thereby crippling the legitimate registrant), `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` let an attacker write to a *victim's* per-account token set without the victim's consent. A dust `DepositToken.transfer` (or any balance change from 0) to the victim triggers `Pool.addToDepositTokensOfAccount(victim)`, which only authenticates the *token* (`_msgSender()`), not the account being keyed. By dusting the victim with every registered deposit token, the attacker fills the 30-slot `debtTokensOfAccount + depositTokensOfAccount` limit, after which any operation requiring a new list entry for that victim reverts.

### Finding Description
`Pool.addToDepositTokensOfAccount(address account_)` is external and takes an arbitrary `account_`. Its only authorization is that the caller be a registered deposit token (`_revertIfSenderIsNotDepositToken`), per `contracts/Pool.sol:194-196` and `contracts/Pool.sol:216-220`. The same applies to `addToDebtTokensOfAccount` at `contracts/Pool.sol:204-208`. Per the docstrings, these are invoked from `DepositToken`/`DebtToken` whenever an account's balance moves off zero — i.e., any `transfer`/`transferFrom`/`deposit(to_=victim)` of a dust amount inserts the token into the victim's set. The `onlyIfAdditionWillNotReachMaxTokens` modifier (`contracts/Pool.sol:143-148`) reverts once the combined list reaches `MAX_TOKENS_PER_USER = 30` (`contracts/Pool.sol:79`). Since `depositTokenOf`/`debtTokenOf` registrations are governor-gated and capped, there is no "already registered" protection for the *account-level* mapping — the attacker chooses the victim freely, just as the mech attacker chose an arbitrary `serviceId`.

### Impact Explanation
Once the victim's combined list hits 30 entries:
- The victim cannot deposit a collateral type they don't already hold (`deposit` → `addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`), cannot receive any new deposit-token transfer, and cannot mint a synthetic whose debt token isn't already in their list (`mint`/`issue` → `addToDebtTokensOfAccount` reverts). This is a liveness break on the victim's account — directly paralleling the marketplace DoS where `checkMech` reverts for the squatted `serviceId`.
- If the victim's position turns unhealthy and the only viable rescue requires collateral of a not-yet-held type (e.g., existing collateral delisted or illiquid), the victim is blocked from restoring health and can be liquidated (`liquidate` at `contracts/Pool.sol:537` has no list-add requirement for the liquidator), causing real loss.
- Removal is only possible via `removeFromDepositTokensOfAccount` (`contracts/Pool.sol:630-634`), which requires the victim's balance of that token to hit zero — the victim can self-remedy only by spending gas to transfer out every dusted token, and the attacker can re-dust or race removals.

### Likelihood Explanation
Requires only an EOA holding dust amounts of each registered deposit token (each pool's `depositTokens` set is capped at 30 entries, so the attacker needs at most ~30 distinct dust transfers; `transfer` costs are minimal). No privileged role, no flash loan, no oracle manipulation is needed — the write path is a plain public ERC20 transfer to the victim address. `SynthContext`/`Operator` do not help: the checks authenticate the token contract as `msg.sender`, which is legitimately the deposit token in the dust-transfer flow, so `onlyPool`-style modifiers and reentrancy guards are not triggered and pause flags are irrelevant.

### Recommendation
Gate list insertion so an attacker cannot add tokens to an account that never opted in. Options: (a) make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert when `account_` didn't initiate the balance change (e.g., only add on `deposit`/`mint`/`seize`-recipient flows, not on inbound `transfer`/`transferFrom`); (b) allow the account itself to call `removeFrom*` / `addTo*` so a victim can prune their list in one call; or (c) raise/decouple the `MAX_TOKENS_PER_USER` accounting so unsolicited dust cannot exhaust it. At minimum, inbound transfers to an account whose list is full should still succeed rather than reverting (treat "new token at max capacity" as account-excluded instead of revert), so the griefing vector degrades to untracked dust rather than a hard DoS.

### Proof of Concept
Reproducible as a Hardhat test against a fork where a `Pool` has ≥2 registered deposit tokens (e.g., `vETH`, `vUSDC`-style `DepositToken`s):

```javascript
it("griefs victim's token list via dust transfers", async function () {
    // attacker holds 1 wei of each registered deposit token's underlying and deposits
    // or simply transfers existing deposit tokens
    const depositTokens = await pool.getDepositTokens(); // array of DepositToken addrs
    const victim = victimAddress; // has 0 current deposit tokens, or a few

    for (const dtAddr of depositTokens) {
        const dt = await ethers.getContractAt("DepositToken", dtAddr);
        // attacker deposits dust for itself then transfers 1 wei share to victim
        await dt.connect(attacker).transfer(victim, 1); // triggers pool.addToDepositTokensOfAccount(victim)
    }

    // victim's list is now full (>= MAX_TOKENS_PER_USER = 30 combined entries)
    const newDepositToken = /* any registered deposit token not yet sent */;
    // any deposit by victim of a new collateral type reverts:
    await expect(
        newDepositToken.connect(victim).deposit(amount, victim)
    ).to.be.revertedWithCustomError(pool, "UserReachedMaxTokens");

    // any transfer of a not-yet-held deposit token to victim also reverts,
    // and mint of a synthetic whose debt token isn't in the list reverts via
    // pool.addToDebtTokensOfAccount -> UserReachedMaxTokens
});
```

The invariant broken is liveness of a victim's account: an unprivileged third party can write into the victim's `depositTokensOfAccount`/`debtTokensOfAccount` state — the same "anyone can bind state to an identity they don't own" defect as `MechMarketplace.create` accepting an arbitrary `serviceId`.

Uncertainty note: I could not read `DepositToken.sol`/`DebtToken.sol` within available iterations, so the exact hook that calls `addToDepositTokensOfAccount` on transfers (vs. only on `deposit`) should be confirmed — the function docstrings at `contracts/Pool.sol:210-214` state it is called when a user's balance changes from 0, which implies inbound transfers trigger it. If transfers to the victim do *not* call the hook, the vector reduces to `deposit(amount, victim)` still being usable since `DepositToken.deposit` accepts a recipient parameter (see `SmartFarmingManager.sol:203` calling `depositToken_.deposit(_depositAmount, _msgSender)`), which itself is an unauthenticated "create entry for arbitrary account" path.
