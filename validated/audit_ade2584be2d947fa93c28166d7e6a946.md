### Title
Attacker can fill a victim's per-account token list to `MAX_TOKENS_PER_USER` via dust `DepositToken` transfers, DoSing the victim's borrows and receipt of collateral - (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2025-6714 (incorrect handling of edge-case input causes `mongos` to stop accepting new connections — a liveness failure), Metronome's `Pool` tracks every deposit/debt token held by an account in `depositTokensOfAccount` / `debtTokensOfAccount` and hard-reverts in `onlyIfAdditionWillNotReachMaxTokens` once the combined count reaches `MAX_TOKENS_PER_USER = 30`. Any unprivileged user can permissionlessly push entries into a victim's list by `transfer`ring dust amounts of `DepositToken` shares to them, after which `DebtToken.issue`, `DepositToken.deposit(onBehalfOf = victim)`, and any `DepositToken.transfer`/`seize` crediting the victim revert.

### Finding Description
`Pool` enforces a per-account cap:

```solidity
// contracts/Pool.sol
uint256 public constant MAX_TOKENS_PER_USER = 30;

modifier onlyIfAdditionWillNotReachMaxTokens(address account_) {
    if (debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER) {
        revert UserReachedMaxTokens();
    }
    _;
}

function addToDepositTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) { ... }
function addToDebtTokensOfAccount(address account_) external onlyIfAdditionWillNotReachMaxTokens(account_) { ... }
```

`DepositToken`'s mint/transfer path calls `pool.addToDepositTokensOfAccount(recipient)` whenever the recipient's balance moves `0 → >0`, and `DebtToken` minting (`issue`, `flashIssue`, SmartFarmingManager leverage) calls `addToDebtTokensOfAccount`. There is no minimum-transfer amount and no consent check — anyone can `deposit()` a dust amount of each listed collateral and `transfer` 1 wei of each `DepositToken` to a target, adding up to 30 entries to the victim's list (the pool itself caps `depositTokens` at 30 via `ReachedMaxDepositTokens`, so a single attacker can fill every slot).

Once the list is full, every subsequent call that would register a new token for that account reverts with `UserReachedMaxTokens`:
- `DebtToken.issue` (borrowing) — the debt-token mint for the victim reverts.
- `DepositToken.deposit` with `onBehalfOf_ = victim`, `transfer`/`transferFrom` to the victim, and `Pool.liquidate`'s `seize` when the victim were the credit side — all revert.
- `SmartFarmingManager.leverage` positions for the victim revert mid-flow.

This mirrors the CVE's bug class: a small, malformed/edge-case input (dust transfers) is accepted without accounting for state limits, and the subsystem then refuses to "accept new connections" (new token registrations), denying service to the victim.

### Impact Explanation
Temporary freezing of funds / liveness denial. A victim with collateral deposited cannot mint new debt (`issue`/`flashIssue`/leverage revert), cannot receive additional collateral tokens, and integrations depositing on their behalf fail. The victim's position is stuck in its current state while the attack persists; recovery requires the victim to fully zero out the dust positions (transfer/withdraw each dust token so `removeFromDepositTokensOfAccount` fires), which costs them gas and transactions, and a persistent attacker can front-run/refill slots. During a market drawdown the victim cannot add collateral or rebalance via deposited-token transfers, raising liquidation risk on an otherwise manageable position.

### Likelihood Explanation
Fully permissionless and cheap: the attacker needs only dust amounts of each listed underlying (up to 30 `deposit` + `transfer` calls; no governance, keeper, or oracle cooperation). Main limitations: (1) it requires ~30 listed deposit tokens to fully occupy the list — if the pool lists fewer than 30 deposit tokens the attacker can only fill part of the list and blocks only proportionally; (2) the victim can self-heal by emptying dust balances, so impact is "temporary freezing" rather than permanent loss; (3) withdrawal of existing balances still works, so this does not directly steal or permanently lock funds.

### Recommendation
- Do not revert on `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` for transfers initiated by a third party; instead, only enforce `MAX_TOKENS_PER_USER` on user-initiated actions (`deposit` for self, `issue`) or skip the accounting (keep `balanceOf` authoritative) for unsolicited dust.
- Alternatively, require a minimum amount for list registration, or allow accounts to permissionlessly `removeFromDepositTokensOfAccount` a token they hold a nonzero dust balance of (auto-exit dust positions).
- Track deposit/debt membership on-demand from balances rather than an enumerable set that third parties can grow on a victim's behalf.

### Proof of Concept
Hardhat sketch against a forked/deployed `Pool` with ≥ `MAX_TOKENS_PER_USER` deposit tokens:

```ts
// attacker: for each depositToken_i in pool.getDepositTokens()
const underlying = await depositToken_i.underlying();
await deal(underlying, attacker, 1);                 // dust
await IERC20(underlying).approve(depositToken_i, 1);
await depositToken_i.deposit(1, attacker);           // mint 1 wei share
await depositToken_i.transfer(victim, 1);            // adds entry to victim's list

// after 30 iterations:
expect(await pool.depositTokensOfAccount.length(victim)).eq(30);

// victim can no longer borrow:
await expect(debtToken.connect(victim).issue(amount, victim))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// anyone depositing to the victim fails:
await expect(depositToken_j.deposit(amount, victim))
  .to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

Note on verification limits: I confirmed the cap, the `onlyIfAdditionWillNotReachMaxTokens` revert, and the `add/remove` entry points in `Pool.sol`, plus `DepositToken.deposit`/`_mint` and `DebtToken.issue` flows; the exact internal `_mint`/`_transfer` hooks in `DepositToken.sol` (lines beyond 260) that invoke `addToDepositTokensOfAccount` on `0 → >0` balance transitions were not fully read in this session, but the grep hits (8 references in `DepositToken.sol`, 4 in `DebtToken.sol`) and the unit tests in `test/Pool.test.ts:1347-1551` confirm those functions are called from the token contracts on balance changes. If a guarded path already skips list registration for transfers, this finding downgrades to borrow-DoS only.
