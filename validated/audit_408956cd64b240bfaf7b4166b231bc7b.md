Audit Report

## Title
`asset-rewards` pallet's `PRECISION_SCALING_FACTOR` is too small, causing `reward_per_token` accrual to permanently round down to zero and lose staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` computes its Synthetix-style per-token reward accumulator using a hardcoded `pub(crate) const PRECISION_SCALING_FACTOR: u16 = 4096` [1](#0-0) . Because `reward_per_token` multiplies the reward delta by this fixed 4096 factor before dividing by `total_tokens_staked` [2](#0-1) , and integer division in Rust truncates, any pool with an 18-decimal staked asset and a realistic reward rate can see this delta truncate to zero on every call, while the accumulator state (`reward_per_token_stored`, `last_update_block`) is unconditionally overwritten and persisted [3](#0-2) , permanently discarding the fractional accrual for that window.

## Finding Description
`reward_per_token` and `derive_rewards` both gate their fixed-point conversion on the same undersized 12-bit scaling constant [4](#0-3) . `update_pool_and_staker_rewards` calls `reward_per_token`, then unconditionally calls `update_pool_rewards`, which resets `last_update_block` to the current block and overwrites `reward_per_token_stored` with whatever value (possibly zero-delta) was just computed [5](#0-4) . This function is invoked from the unprivileged, publicly-callable `stake` extrinsic (and analogously `unstake`/`harvest_rewards`) [6](#0-5) , so any staker interacting with the pool advances `last_update_block` and commits the (possibly truncated-to-zero) `reward_per_token_stored`, with no mechanism to carry forward the discarded fractional remainder. For an 18-decimal staked asset with even a moderate `total_tokens_staked` (e.g., 10^21) and a realistic `reward_rate_per_block` (e.g., 10^12), the accumulator numerator `reward_rate_per_block * blocks_elapsed * 4096` stays below `total_tokens_staked` for tens of thousands of blocks, so the division yields exactly zero and that window's rewards are lost forever once `last_update_block` advances past it.

## Impact Explanation
Reward-asset balances remain custodied in the pool's dedicated account, but the truncation prevents those funds from ever being correctly attributed to the stakers who earned them; on `cleanup_pool` the pool's residual reward balance is swept to the `admin`, not to stakers [7](#0-6) . This is a beneficiary-correctness / value-settlement violation: funds are conserved on-chain but never settle to the rightful beneficiary, matching the "permanent user-fund lock" / payout-correctness impact class in scope for `pallet` runtime logic.

## Likelihood Explanation
`stake`, `unstake`, and `harvest_rewards` are ordinary signed extrinsics reachable by any account with no privileged origin required [6](#0-5) . The truncation condition depends only on ordinary parameters (18-decimal reward/staked assets, moderate pool size, moderate reward rate) that fall squarely within the pallet's documented intended use ("holders of the 'staking asset'... for example LP tokens") [8](#0-7) , making the condition highly likely to occur through normal usage, and trivially repeatable/amplifiable by any staker interacting frequently with the pool.

## Recommendation
Replace the fixed `u16` `PRECISION_SCALING_FACTOR` with a scale sized to the actual balance precision in use (e.g., a much larger constant such as `10^18`, or a proper fixed-point accumulator type analogous to `pallet-nomination-pools`'s `RewardCounter`, which uses `checked_from_rational` with a wide fixed-point type) [9](#0-8) , and/or track and carry forward the truncated remainder across calls instead of discarding it when `update_pool_rewards` overwrites `reward_per_token_stored` and `last_update_block`.

## Proof of Concept
1. Create a pool via `create_pool` with an 18-decimal `staked_asset_id`/`reward_asset_id` and `reward_rate_per_block = 10^12` [10](#0-9) .
2. Stake `1_000 * 10^18` staked-asset units via `stake` [6](#0-5) .
3. Advance fewer than ~244,000 blocks and call `harvest_rewards` (or another `stake`/`unstake`), triggering `update_pool_and_staker_rewards` → `reward_per_token` [2](#0-1) .
4. Observe the computed delta is `0` due to integer-division truncation; `reward_per_token_stored`/`last_update_block` are updated to reflect zero accrual for the elapsed window [3](#0-2) .
5. Repeat step 3 periodically to indefinitely suppress reward accrual while the pool's reward-asset balance remains funded, later reclaimable by `admin` via `cleanup_pool` [7](#0-6) .

		pub fn stake(origin: OriginFor<T>, pool_id: PoolId, amount: T::Balance) -> DispatchResult {
			let staker = ensure_signed(origin)?;

			// Always start by updating staker and pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			T::AssetsFreezer::increase_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_add_assign(amount)?;
			PoolStakers::<T>::insert(pool_id, &staker, staker_info);

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())
		}

			new_staker_info.reward_per_token_paid = pool_info.reward_per_token_stored;
			return Ok((pool_info, new_staker_info));
		}
