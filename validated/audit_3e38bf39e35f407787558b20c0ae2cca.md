### Title
Wallet Contract Ethereum-transaction signatures use a fixed, network-class-wide `CHAIN_ID` and are replayable across forked/test deployments of the same network - ([File: runtime/near-wallet-contract/build.rs])

### Summary
The Wallet Contract (NEP-518) accepts RLP-encoded Ethereum transactions as authorization for NEAR actions taken from an ETH-implicit account, and recovers the signer's address via `ecrecover`, binding the check to a fixed `CHAIN_ID` constant that is only network-class-wide (mainnet=397, testnet=398, localnet=399), not unique per deployment/genesis. Any fork, restart, or copy of a NEAR network that reuses the same network label (e.g. every "mainnet" fork, or every custom localnet) reuses the exact same `CHAIN_ID`, so a signature the user believes is only valid on one deployment can be replayed on another with matching account state (same eth-implicit address, target, and nonce). This mirrors the Hermez `_checkSig` finding: signatures only prevent cross-account and cross-network-class replay, not cross-deployment/fork replay.

### Finding Description
`rlp_execute` on the Wallet Contract parses a raw, secp256k1-signed Ethereum transaction and validates it in `validate_tx_relayer_data`, checking the recovered sender address, `to` target, and `nonce`, plus: [1](#0-0) 

The signature-scope binding value `CHAIN_ID` is not derived from the genesis hash, chain identifier of the concrete running network, or any other deployment-unique value; it is a compile-time constant selected purely by which of three network "classes" the contract is built for: [2](#0-1) [3](#0-2) 

Because every mainnet-class deployment (the real NEAR mainnet, but also any full or partial fork/copy of it that re-uses the "mainnet" wallet contract binary) shares `CHAIN_ID = 397`, and likewise every localnet/testnet-class deployment shares `398`/`399`, an Ethereum-style transaction signed by a user's Secp256K1 key for one deployment is indistinguishable, at the signature level, from the same transaction intended for a different deployment of the same class. The only other binding factors are the recovered `from` address (bound to `context.current_address`, i.e., the specific eth-implicit account on the *current* chain state) and the account's own on-chain `nonce`. Neither of these is tied to a particular chain instance — an eth-implicit account with the same address and the same nonce value can independently exist in two different deployments (e.g., a state-forked test network, a sandboxed clone of mainnet used for demos/audits, or any new network launched by copying the Wallet Contract binary and genesis).

This is the direct analog of the reported `_checkSig` bug: the signed payload's replay-scope commitment (`chain_id` in Hermez's proposed fix; here the wallet's `CHAIN_ID`) is too coarse-grained to distinguish individual contract/chain deployments, enabling cross-deployment signature reuse.

### Impact Explanation
If an attacker stands up a fork or clone of a NEAR network (or a sandboxed "test" instance sharing the mainnet CHAIN_ID/wallet binary) and convinces a user to sign an Ethereum-style transaction there (e.g., under the pretense of "testing" a new dApp or wallet integration — exactly the Hermez exploit scenario), the same signed transaction bytes are valid on the real network as long as the target eth-implicit account there has a matching nonce. Because the signature authorizes the underlying NEAR action (transfer, function call, or access-key change) via `rlp_execute`, a successful replay can move real funds out of the user's ETH-implicit account or grant an access key to an attacker-controlled relayer, constituting concrete theft of funds and authorization escalation on the account.

### Likelihood Explanation
Exploitation requires social engineering to get the victim to sign on the attacker-controlled fork/clone (as in the Hermez scenario) and requires the victim's real account nonce to align with the forged-context nonce at replay time — a nonzero but realistic bar, since a freshly created eth-implicit account starts at nonce 0 in both places, and attackers control the timing/sequence of the deception. This is a design gap rather than a straightforward guessable exploit, so likelihood is moderate, matching the "High difficulty" rating of the original Hermez report.

### Recommendation
Bind the Wallet Contract's authorization scheme to a value unique to the concrete chain instance rather than only the network class — e.g., incorporate the genesis hash or a protocol-exposed unique network/chain identifier into the signed digest verification (or into `CHAIN_ID` itself), so that transactions signed for one deployment cannot be replayed on another deployment that happens to share the same network label. Longer term, the Wallet Contract's authorization/signature scheme should follow the same principle NEP-461/NEP-483 already applies to `DelegateAction` (domain-separated, deployment-aware signing) rather than relying solely on a small fixed integer shared by every deployment of a given network class.

### Proof of Concept
1. Attacker forks/clones the NEAR "mainnet" network (or spins up a new network and deploys the mainnet-flavored Wallet Contract WASM, which bakes in `CHAIN_ID = 397`): [4](#0-3) 
2. Attacker tricks Bob into believing this is a disposable test/demo network and asks him to "try out" the Wallet Contract by signing an Ethereum-style transaction (e.g., `Transaction2930` with `chain_id: 397`, `nonce: 0`, `to: <attacker-or-real-target-address>`) for his ETH-implicit account.
3. On the forked network, `validate_tx_relayer_data` accepts the transaction because `tx.chain_id == Some(CHAIN_ID)` and `tx.address.raw() == context.current_address`: [5](#0-4) 
4. Attacker takes the identical RLP-encoded, signed transaction bytes and submits them via `rlp_execute` against Bob's real ETH-implicit account on genuine NEAR mainnet (same `CHAIN_ID = 397`, same address, matching nonce if Bob's real account is also at nonce 0). The contract has no per-deployment binding to reject the replay, and the action (e.g., a transfer or an `AddKey` granting the attacker a relayer key) executes against Bob's real funds.

fn validate_tx_relayer_data<'a>(
    tx: &NormalizedEthTransaction,
    target: &'a AccountId,
    context: &ExecutionContext,
    expected_nonce: u64,
) -> Result<TargetKind<'a>, Error> {
    if tx.address.raw() != context.current_address {
        return Err(Error::Relayer(RelayerError::InvalidSender));
    }

    if tx.chain_id != Some(CHAIN_ID) {
        return Err(Error::Relayer(RelayerError::InvalidChainId));
    }
