## Analysis Summary

The external report's core broken invariant: a predicate used to gate accounting (`IsFullyWithdrawn`) failed to check the actual terminal/success semantics of a state field, allowing invalid state to be accepted as if the underlying condition had truly completed, corrupting downstream accounting (`CumulativeNumValidatorsFullyWithdrawn`).

Searching the Snowbridge outbound queue v2 delivery-receipt flow reveals the same broken-predicate pattern: the pallet decodes a `DeliveryReceipt` that carries an explicit `success: bool` field describing whether the Ethereum-side dispatch of the message actually succeeded, but `process_delivery_receipt` never inspects it before releasing the relayer reward and clearing the pending order.

### Title
Relayer reward and order settlement ignore the `DeliveryReceipt.success` field, allowing rewards to be paid for failed message dispatch - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`process_delivery_receipt` pays the pending fee and removes the `PendingOrder` purely based on the presence of a valid, verified event log for the message's nonce, without checking whether the underlying `InboundMessageDispatched` event reports `success: true` or `success: false`.

### Finding Description
The `DeliveryReceipt` struct decoded from the Ethereum Gateway's `InboundMessageDispatched` log carries a `success` field [1](#0-0) . This field is populated correctly during decoding [2](#0-1) , but `process_delivery_receipt` never reads `receipt.success`; it only checks the gateway address and looks up the order by `receipt.nonce`, then unconditionally pays out `order.fee` and removes the order: [3](#0-2) . The pallet documentation itself frames the receipt's purpose as confirming the message "has been verified and executed" before paying the reward and clearing the order [4](#0-3) , i.e., the intended predicate for reward release is "message delivery succeeded," analogous to the intended `IsFullyWithdrawn` predicate meaning "validator balance fully exited." In both cases, the code accepts a state transition (validator status / delivery receipt) as complete for accounting purposes without validating the actual completion condition encoded in the very state it reads.

### Impact Explanation
Any relayer who is queued for reward (`reward_address == 0` defaults to the submitting relayer) can obtain the full relay fee for a message whose on-chain execution on Ethereum failed (`success == false`), because the pallet's only gate is nonce lookup, not outcome. This breaks the "settle exactly once to the rightful beneficiary and amount" invariant required for bridge reward payouts — the relayer is paid the intended amount even though the corresponding beneficiary-side work did not succeed, and the order is removed so no retry/re-verification of the actual delivery outcome can occur. This is a reward/accounting integrity issue rather than a fund-theft bug, but it constitutes unbacked payout for work that was not actually completed, degrading the correctness of bridge processing.

### Likelihood Explanation
No privileged actor, malicious relayer, or governance action is required — a normal relayer that faithfully submits a proof for a legitimately failed-dispatch event (which can happen for many benign on-chain reasons on the Ethereum side, e.g., a reverted command) will trigger this path in the course of ordinary operation. The verifier (`T::Verifier::verify`) only attests to the authenticity of the event log, not to `success`, so a fully valid, unforged receipt for a failed delivery passes all current checks.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success`: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, the order should still be resolved (e.g. removed and an event emitted, or handled per the intended incident-response design), but no fee should be granted for the failed dispatch, mirroring the fix applied to the validator report where the terminal/exit condition must be checked directly rather than inferred from an incomplete or contradictory secondary signal.

### Proof of Concept
1. A message is enqueued and processed by `do_process_message`, creating `PendingOrder { nonce, fee: F, .. }` [5](#0-4) .
2. On Ethereum, the Gateway contract emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)` because the dispatched command reverted.
3. A relayer submits `submit_delivery_receipt` with a valid proof of this event log; `T::Verifier::verify` succeeds because the log is authentic, and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` proceeds: `order.fee > 0` is true, so `T::RewardPayment::register_reward` pays out the relayer for a message that never actually succeeded on Ethereum, and `PendingOrders::remove(nonce)` clears the order — matching the test pattern already present that only checks nonce presence, not outcome: [6](#0-5) .

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

fn submit_delivery_receipt_succeeds_after_unhalt() {
