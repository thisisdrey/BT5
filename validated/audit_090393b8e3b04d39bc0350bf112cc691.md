### Title
Unvalidated `GitObjectDirectory`/`GitAlternateObjectDirectories` request fields allow cross-repository object access via path traversal - (File: internal/git/gitcmd/command_factory.go)

### Summary
The `USDToken::burn` bug pattern (a function that accepts an arbitrary, caller-supplied identifier — an address — instead of restricting the operation to the caller's own resource, with no authorization check on that identifier) has a structural analog in Gitaly's `gitalypb.Repository` message. It carries two attacker-influenceable, free-form path fields — `git_object_directory` and `git_alternate_object_directories` — that are supposed to only ever be populated by Gitaly itself (for object-quarantine loopback) but are ordinary proto fields that any RPC caller can set to any string, similar to `USDToken::burn(address)` accepting an arbitrary `address` instead of using `msg.sender`.

### Finding Description
`ExecCommandFactory.newCommand` builds the environment for every spawned Git subprocess by directly consuming these two fields off the incoming `storage.Repository`: [1](#0-0) 

which calls into: [2](#0-1) 

`alternates.Env` simply does `filepath.Join(repoPath, objectDirectory)` and `filepath.Join(repoPath, dir)` for each alternate — there is no boundary check that the resulting path stays within the repository or even within the storage root. This is materially different from the vetted code path used elsewhere, `Repo.ObjectDirectoryPath` in `internal/git/localrepo/paths.go`, which explicitly validates the relative path against the repository root or an expected quarantine-directory prefix before use: [3](#0-2) 

That stricter validation is only invoked by specific call sites (e.g. `GetObjectDirectorySize`), not by the generic command-spawning path in `command_factory.go`, meaning most RPCs that execute git subprocesses use the unchecked variant.

There is a partial mitigating gate in `internal/gitaly/storage/storagemgr/middleware.go`: when a `Repository` message arrives with either object-directory field set, `beginTransactionForRepository` refuses to start a new transaction for mutators and, for accessors, requires an `x-gitaly-snapshot-relative-path` metadata value be present (`restoreSnapshotRelativePath`) — this is designed to accept requests only when they are part of the internal Rails "access checks" quarantine-loopback flow. However:
- This is a metadata-presence check, not a content/path-escape check on the object-directory field's value itself.
- The gate only fires for RPCs that are transaction/repository-scoped through this middleware; it does not perform the same relative-path boundary validation as `ObjectDirectoryPath`.

Because the actual environment variable construction (`alternates.Env`) never re-validates the field against the repository or storage boundary, any accessor RPC reachable with a crafted `Repository{GitObjectDirectory: "../../<other-repo>/objects"}` (plus the required snapshot-relative-path metadata, which is just an arbitrary string a caller controls) can point `GIT_OBJECT_DIRECTORY`/`GIT_ALTERNATE_OBJECT_DIRECTORIES` at objects outside the intended repository, letting Git subprocesses resolve and disclose objects belonging to a different repository — the same class of "arbitrary target instead of restricted target" flaw as the `USDToken::burn(address)` report, applied to object-directory path resolution instead of a token holder address.

### Impact Explanation
If reachable, this allows disclosure of Git objects (blobs, commits, trees) from a repository the caller does not have access to, by supplying a crafted relative path in `git_object_directory`/`git_alternate_object_directories` that traverses to another repository's `objects` directory within the same storage. This is a cross-repository confidentiality violation analogous to the "burn any user's tokens" impact (acting on a resource that isn't the caller's own).

### Likelihood Explanation
Exploitability depends on whether an ordinary/lower-privileged caller can reach an accessor RPC while supplying both the `GitObjectDirectory`/`GitAlternateObjectDirectories` fields and the required `x-gitaly-snapshot-relative-path` metadata header — this metadata gate is intended to restrict the flow to Gitaly's own Rails-loopback pattern, but as implemented it is a presence check on a caller-suppliable value, not a cryptographic or session-bound authorization. I was not able to fully trace, within the available tool budget, whether an external gRPC client without Gitaly's internal token/role can supply this metadata and reach `beginTransactionForRepository`'s accessor branch end-to-end, or whether an additional layer (e.g. Praefect repository ID rewriting, or gRPC auth middleware) prevents an unprivileged caller from ever setting these fields on a live request. This uncertainty should be resolved by tracing the full auth/interceptor chain and by testing whether `alternates.Env`'s lack of boundary validation is actually reachable with attacker-controlled input in a production deployment.

### Recommendation
Route the object-directory/alternate-object-directory fields through the same boundary validation used in `Repo.ObjectDirectoryPath` (repository-root or quarantine-prefix check) before they are used to build the Git subprocess environment in `alternates.Env`/`ExecCommandFactory.newCommand`, rather than relying solely on the presence of the `x-gitaly-snapshot-relative-path` metadata header as a gate.

### Proof of Concept
Could not be concretely constructed within the available investigation budget — a full PoC requires confirming the caller-facing auth chain (interceptors/token checks) permits an unprivileged actor to invoke an accessor RPC with `Repository.GitObjectDirectory` set to a traversal path (e.g. `"../<other-repo-relative-path>/objects"`) together with a self-supplied `x-gitaly-snapshot-relative-path` metadata value, and then observing that `alternates.Env`'s unchecked `filepath.Join` causes objects from the other repository to become readable. This should be validated with a running Gitaly instance and gRPC client rather than static analysis alone.

// Env returns the alternate object directory environment variables.
func Env(repoPath, objectDirectory string, alternateObjectDirectories []string) []string {
	var env []string
	if objectDirectory != "" {
		env = append(env, fmt.Sprintf("GIT_OBJECT_DIRECTORY=%s", filepath.Join(repoPath, objectDirectory)))
	}

	if len(alternateObjectDirectories) > 0 {
		var dirsList []string

		for _, dir := range alternateObjectDirectories {
			dirsList = append(dirsList, filepath.Join(repoPath, dir))
		}

		env = append(env, fmt.Sprintf("GIT_ALTERNATE_OBJECT_DIRECTORIES=%s", strings.Join(dirsList, ":")))
	}

	return env
}
