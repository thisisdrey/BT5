### No vulnerability found for this question.

**Analysis:** The claimed break in `Display`/`FromStr` round-trip for `Nep171TokenId` does not exist in practice, because `split_once(':')` always finds the correct separator: `AccountId` (the `contract_id` field) can never itself contain a `:` character due to NEAR's account-id validation rules enforced by `near_account_id::AccountId`, so the *first* `':'` in the serialized string `"{contract_id}:{nft_token_id}"` is always the boundary inserted by `Display`, regardless of what characters (including further colons, empty strings, or unicode) appear inside `nft_token_id`. [1](#0-0) 

Tracing the exact flow: `Nep171TokenId::fmt` writes `"{contract_id}:{nft_token_id}"`, and `from_str` does `data.split_once(':')`, taking everything before the first colon as `contract_id` and everything after (including any embedded colons) as `token_id` — this reconstructs the exact same struct because `contract_id.parse::<AccountId>()` will only succeed for the original valid, colon-free account id, and the remainder (whatever it contains) is passed through unmodified into `nft_token_id`. An attacker-controlled `mt_token_id`/NFT `token_id` string containing `:`, empty content, or unicode is preserved byte-for-byte in the tail portion of the split and does not cause misparsing into a different variant or a different `contract_id`. [2](#0-1) 

The same reasoning applies identically to `Nep245TokenId` and the top-level `TokenId::from_str`, since the type prefix (`nep141`/`nep171`/`nep245`/`imt`) also cannot contain `:`. [3](#0-2) 

Existing property tests already assert this round-trip property with arbitrary generated sub-ids (`display_from_str_roundtrip` in both `nep171.rs` and the top-level `lib.rs`), and the described exploit (colon-containing or empty sub-ids causing divergent re-parsing) is not reproducible given `AccountId`'s syntactic constraints. [4](#0-3) [5](#0-4) 

Since the equality `TokenId::from_str(&t.to_string()) == t` holds for every constructible `Nep171TokenId` (and `TokenId` in general) regardless of attacker-supplied sub-id content, there is no divergence between the id written into balances and the id read back, and thus no path to fund theft as described.

impl FromStr for TokenId {
    type Err = TokenIdError;

    #[inline]
    fn from_str(s: &str) -> Result<Self, Self::Err> {
        let (typ, data) = s
            .split_once(':')
            .ok_or(strum::ParseError::VariantNotFound)?;
        match typ.parse()? {
            TokenIdType::Nep141 => data.parse().map(Self::Nep141),
            TokenIdType::Nep171 => data.parse().map(Self::Nep171),
            TokenIdType::Nep245 => data.parse().map(Self::Nep245),
            TokenIdType::Imt => data.parse().map(Self::Imt),
        }
    }
}
