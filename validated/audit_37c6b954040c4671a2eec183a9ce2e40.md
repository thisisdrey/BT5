Based on my research, the strongest and most direct analog to the WETH `totalSupply()` bug is in `pallet-revive`'s `fungibles::Inspect` implementation, where a supply-reporting getter silently falls back to `0` instead of reflecting the real, authoritative on-chain value.

### Title
`fungibles::Inspect::total_issuance` for pallet-revive ERC20 assets falls back to `0` on call failure instead of reflecting real supply - (File: `substrate/frame/revive/src/impl_fungibles.rs`)

### Summary
`pallet-revive`'s `impl<T: Config> fungibles::Inspect<...> for Pallet<T>` treats every ERC20 contract deployed under `pallet-revive` as a `fungibles`-compatible asset (keyed by the contract's `H160` address) so it can be consumed generically by XCM adapters, asset-conversion, and other pallets that rely on the `fungibles::Inspect` trait for supply/balance accounting. [1](#0-0) 

Both `total_issuance` and `balance` execute a `bare_call` into the target contract to invoke `totalSupply()`/`balanceOf()`, and unconditionally return `0` whenever that call does not succeed and cleanly ABI-decode — regardless of *why* it failed (out-of-weight, deposit-limit exceeded, contract paused/reverting, or any other transient execution failure): [2](#0-1) 

This exactly mirrors the WETH.sol defect: a value that is supposed to be an authoritative accounting figure (`totalSupply`) is derived through an indirect, failure-prone path rather than the real underlying state, and on failure it silently reports `0` (a materially wrong value) instead of surfacing an error or falling back to a safe/conservative result.

### Finding Description
`total_issuance` and `balance` use a fixed `WEIGHT_LIMIT` and a `deposit_limit` set from the *native* currency's `total_issuance()`: [3](#0-2) [4](#0-3) 

If the `bare_call` cannot complete successfully within this fixed budget (e.g., the ERC20 contract's `totalSupply()`/`balanceOf()` implementation is more complex than a simple storage read, is paused, or reverts for any transient reason), the function does not propagate an error — it returns the hardcoded fallback `0`:

Unlike the upstream Solidity WETH bug (a one-time, permanent logic error), this variant is call-dependent and can be triggered transiently, but the effect is identical in kind: a consumer of `fungibles::Inspect::total_issuance`/`balance` for this asset class receives `0` while the contract's real state shows non-zero supply/balance — exactly the "Alice has 100 WETH via `balanceOf` but `totalSupply()` returns 0" inconsistency from the report, generalized to any caller of this trait implementation (XCM `FungiblesAdapter`, `pallet_asset_conversion`, benchmarking helpers, RPCs, or any future runtime logic gating deposits/withdrawals on supply). Compounding this, `can_deposit`/`can_withdraw` are hardcoded to always return `Success` regardless of the (possibly wrong) balance/issuance figures: [5](#0-4) 

so any pallet that trusts this fungibles adapter for pre-flight sufficiency checks is relying on values that can silently collapse to zero.

### Impact Explanation
Under the "Polkadot SDK Pivots" for asset/value accounting, `total_issuance`/`balance` are used by generic asset-consuming code (XCM `FungiblesAdapter`-style logic, pricing/ratio computations, or any future runtime feature bridging ERC20 contracts as fungible assets) to determine correctness of mint/burn/settlement flows for value denominated in these ERC20-backed assets. A getter that can silently report `0` instead of the real total supply or a real balance breaks the "conserve value and settle exactly once" invariant for any logic keyed on this reported figure — e.g., miscalculated exchange ratios, incorrectly triggered "empty asset" cleanup paths, or downstream logic assuming a real balance of `0` when actual value is locked in the contract.

### Likelihood Explanation
The failure path is reachable without any privileged actor: any caller that triggers `fungibles::Inspect::total_issuance`/`balance` for a given ERC20 contract under load, gas-exhaustion, or a paused/reverting contract state will observe the fallback `0`, without any error signal distinguishing "true zero" from "call failed." Since the trait contract for `fungibles::Inspect` gives no indication of failure (it returns a plain `Self::Balance`, not a `Result`), any dependent pallet has no way to detect or reject the degraded value.

### Recommendation
Do not collapse call failures into `0`. Either:
- Cache/require a successful bare_call and propagate an error to callers where the trait allows it (or panic/defensive-log in debug builds), or
- Distinguish "genuinely zero supply" (a successful call returning `0`) from "call failed" (contract error, out-of-weight, decode failure) and refuse to treat the two the same way in any code path that gates value-affecting decisions on this return value.

### Proof of Concept
1. Deploy an ERC20 contract via `pallet-revive` whose `totalSupply()`/`balanceOf()` implementation performs enough computation (or is temporarily paused/reverting) that it cannot complete within the fixed `WEIGHT_LIMIT` used by `Self::bare_call` in `total_issuance`/`balance`. [3](#0-2) 
2. Mint real supply into the contract (e.g., via the constructor, as in the existing test `total_issuance_works`). [6](#0-5) 
3. Call `<Contracts as fungibles::Inspect<_>>::total_issuance(addr)` under conditions that make the internal `bare_call` fail (out-of-weight/deposit-limit exceeded/contract reverts).
4. Observe the function returns `0` even though the ERC20 contract's own storage (and `balanceOf` for holders) shows non-zero supply — matching the "balanceOf shows 100, totalSupply shows 0" inconsistency from the original report.

impl<T: Config> fungibles::Inspect<<T as frame_system::Config>::AccountId> for Pallet<T> {
	// The asset id of an ERC20 is its origin contract's address.
	type AssetId = H160;
	// The balance is always u128.
	type Balance = u128;

	// Need to call a view function here.
	fn total_issuance(asset_id: Self::AssetId) -> Self::Balance {
		let data = IERC20::totalSupplyCall {}.abi_encode();
		let ContractResult { result, .. } = Self::bare_call(
			OriginFor::<T>::signed(Self::checking_account()),
			asset_id,
			U256::zero(),
			TransactionLimits::WeightAndDeposit {
				weight_limit: WEIGHT_LIMIT,
				deposit_limit:
					<<T as pallet::Config>::Currency as fungible::Inspect<_>>::total_issuance(),
			},
			data,
			&ExecConfig::new_substrate_tx(),
		);
		if let Ok(return_value) = result &&
			let Ok(eu256) = EU256::abi_decode_validate(&return_value.data)
		{
			eu256.to::<u128>()
		} else {
			0
		}
	}

	fn minimum_balance(_: Self::AssetId) -> Self::Balance {
		// ERC20s don't have this concept.
		1
	}

	fn total_balance(asset_id: Self::AssetId, account_id: &T::AccountId) -> Self::Balance {
		// Since ERC20s don't have the concept of freezes and locks,
		// total balance is the same as balance.
		Self::balance(asset_id, account_id)
	}

	fn balance(asset_id: Self::AssetId, account_id: &T::AccountId) -> Self::Balance {
		let eth_address = T::AddressMapper::to_address(account_id);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		let data = IERC20::balanceOfCall { account: address }.abi_encode();
		let ContractResult { result, .. } = Self::bare_call(
			OriginFor::<T>::signed(account_id.clone()),
			asset_id,
			U256::zero(),
			TransactionLimits::WeightAndDeposit {
				weight_limit: WEIGHT_LIMIT,
				deposit_limit:
					<<T as pallet::Config>::Currency as fungible::Inspect<_>>::total_issuance(),
			},
			data,
			&ExecConfig::new_substrate_tx(),
		);
		if let Ok(return_value) = result &&
			let Ok(eu256) = EU256::abi_decode_validate(&return_value.data)
		{
			eu256.to::<u128>()
		} else {
			0
		}
	}
