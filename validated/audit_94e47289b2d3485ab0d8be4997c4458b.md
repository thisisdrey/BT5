### Title
Non-hardened bancor exchange calculation can drive AMM pool balances negative, minting unbacked token/TRX balances - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()`, invoked by `ExchangeTransactionActuator` for every `ExchangeTransactionContract`, only guards against negative resulting pool balances when the `hardenedCalc` (allow-harden) flag is true. When that dynamic property is disabled, a trade can be executed whose computed `buyTokenQuant` exceeds the current opposite-side pool balance, letting the actuator credit the trader more asset/TRX than the pool actually holds, while writing a negative `firstTokenBalance`/`secondTokenBalance` into the persisted `Exchange` capsule — directly mirroring the Kraken flash-crash pattern of a single oversized order draining an illiquid market beyond its real depth, except here the "shortfall" is created as unbacked balance rather than just a price crash.

### Finding Description
`ExchangeCapsule.transaction()` computes the counter-asset amount using either the legacy floating point `ExchangeProcessor` or the `SafeExchangeProcessor`, and only when `hardenedCalc` is `true` does it validate that the resulting pool balances remain non-negative: [1](#0-0) 

The `hardenedCalc` flag is `allowHarden()`, which is a live dynamic property (`allowHardenExchangeCalculation()`), toggled by an on-chain proposal: [2](#0-1) 

In `ExchangeTransactionActuator.execute()`, the actuator calls `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` and unconditionally credits the trader with `anotherTokenQuant` and persists the (potentially negative) resulting balances via `Commons.putExchangeCapsule`: [3](#0-2) 

The floating-point `ExchangeProcessor.exchange()` path (used whenever `hardenedCalc` is false) computes the bancor-relay amount with `double` arithmetic and `Maths.pow`, which for extreme or crafted `sellTokenQuant` values relative to a thin pool (e.g., very small `secondTokenBalance`/`firstTokenBalance` created via `ExchangeCreateActuator`, which enforces no minimum liquidity) can return a `buyTokenQuant` larger than the actual opposite balance: [4](#0-3) 

`ExchangeCreateActuator` places no floor on `firstTokenBalance`/`secondTokenBalance`, so any unprivileged account can create an arbitrarily illiquid pool: [5](#0-4) 

Because the negative-balance guard in `ExchangeCapsule.transaction()` is gated purely on the `hardenedCalc` boolean and not on the arithmetic path actually used, any deployment/period where `allowHardenExchangeCalculation` is not yet activated allows a trade against a thin pool to push `firstTokenBalance` or `secondTokenBalance` negative while still crediting the trader real TRX/TRC10 balance, minting value the pool never held.

### Impact Explanation
This meets the "unbacked balance" / "theft of funds" bar: the exchange pool balance capsule going negative means the on-chain ledger for that AMM no longer reflects real backing, and the counterparty received assets that exceed what was deposited into the pool — funds effectively created out of nothing at the expense of other liquidity holders (the pool creator/injectors) who can no longer withdraw their expected share. This is reachable by any unprivileged account that (a) creates a thin liquidity pool via `ExchangeCreateContract`, and (b) submits a single `ExchangeTransactionContract` with a large `quant`, with no special privilege required.

### Likelihood Explanation
Exploitability depends entirely on whether the `allowHardenExchangeCalculation` proposal is active on the target network. On a chain/testnet where it has not yet been enabled (the flag defaults off until an SR proposal activates it), the vulnerable floating-point path with no negative-balance check is live and directly reachable from any signed transaction. On networks where the proposal is already active, this path is not exploitable, since `hardenedCalc` gates both the arithmetic (SafeExchangeProcessor) and the guard together.

### Recommendation
Decouple the negative-balance safety check from the `hardenedCalc` feature flag — always validate `newFirstTokenBalance >= 0 && newSecondTokenBalance >= 0` in `ExchangeCapsule.transaction()` regardless of which processor computed the trade, and throw `ContractValidateException` on violation. Additionally, consider enforcing a minimum liquidity threshold in `ExchangeCreateActuator`/`ExchangeInjectActuator` to reduce feasibility of single-trade pool exhaustion.

### Proof of Concept
1. On a network/state where `allowHardenExchangeCalculation` (dynamic property gating `allowHarden()`) is disabled.
2. Attacker A calls `ExchangeCreateContract` to create a pool with an extremely skewed/thin balance, e.g. `firstTokenBalance = 1_000_000` (TRX) and `secondTokenBalance = 1` (some TRC10 token) — no minimum liquidity check exists in `ExchangeCreateActuator`.
3. Attacker A (or a colluding account) submits `ExchangeTransactionContract` selling a large `tokenQuant` of the first token; `ExchangeProcessor.exchange()`'s floating point bancor formula, given the near-zero opposite balance, can return a `buyTokenQuant` that exceeds `secondTokenBalance`.
4. Because `hardenedCalc` is false, `ExchangeCapsule.transaction()` skips the `newSecondTokenBalance < 0` check at `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java:160-166`, and `ExchangeTransactionActuator.execute()` still credits the attacker `anotherTokenQuant` of the second token via `accountCapsule.addAssetAmountV2(...)` and persists the negative pool balance.
5. The attacker now holds tokens not actually backed by the pool's real balance, which can be withdrawn/transferred freely, while other liquidity providers cannot recover their proportional share on withdrawal.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
