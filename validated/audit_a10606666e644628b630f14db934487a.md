## Analysis

The core broken invariant from the Kelp report is: **a price/rate used to value a public, unprivileged action is allowed to remain stale relative to the true market rate for an extended window, and the size of that gap is large enough that a caller can systematically extract value (or, in the on-chain-fee analog, systematically underpay for real, chain-imposed work) before the rate catches up.**

The strongest local analog in this repository is the Snowbridge outbound-queue fee model, which prices every outbound message using a governance-set, infrequently-updated `ETH/DOT` `exchange_rate` — structurally identical to the "24h heartbeat + %-deviation" staleness window in the Chainlink report, just with an even longer, unbounded staleness window (governance-controlled, "every few weeks").

### Title
Stale, unbounded `exchange_rate` in `PricingParameters` lets users systematically underpay Snowbridge message fees, starving relayer rewards and stalling bridge delivery - (File: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs`)

### Summary
`pallet_snowbridge_outbound_queue::Pallet::calculate_fee` prices every outbound P→E message using a single global `PricingParameters.exchange_rate` (`FixedU128`) that is by design only updated manually and infrequently. [1](#0-0)  Any unprivileged account calling `validate`/`deliver` (via XCM export or `pallet_snowbridge_system::send`) gets its fee computed from this stale rate with no on-chain staleness check, no deviation bound, and no fallback if the real ETH/DOT market rate has diverged. [2](#0-1)  This is the exact same "infrequently refreshed conversion rate priced into a permissionless action" pattern flagged in the Kelp report, except here the divergence directly determines whether Ethereum-side relay costs are actually covered.

### Finding Description
`calculate_fee` computes the remote (Ethereum-side) portion of the fee by taking `MaxGasRequired * fee_per_gas + reward` (in Ether) and dividing by `params.exchange_rate` to convert into the local (DOT) currency, with a `multiplier` meant to compensate for rate drift: [3](#0-2) 

The module doc explicitly states the staleness model and its assumed mitigation: [4](#0-3) 

`PricingParameters::validate` only rejects zero values — it performs no sanity/staleness/deviation check against any live price source: [5](#0-4) 

The fee is computed and charged at `validate()` time, immediately before the message is enqueued — any account can trigger this at will, with no delay or oracle freshness gate: [6](#0-5) 

Just like the Kelp rETH/stETH/cbETH feeds (each allowed to sit stale for up to 24h within a ±0.5–2% band), the ETH/DOT `exchange_rate` here is allowed to sit stale for "every few weeks" with **no bound at all** on how far it can diverge from the real market rate before governance re-updates it. If real ETH gas price or ETH/DOT spot price moves against the stale on-chain rate (e.g. ETH price rises, or gas prices spike), `RemoteFeeAdjusted` computed from the stale rate under-collects DOT relative to the real cost of `fee_per_gas * gas_used + reward` that must actually be paid out in ETH on the Ethereum side. The `multiplier` is a static safety factor picked at the last governance update and does not adapt to how much time has elapsed or how far the market has actually moved — so once real-world volatility exceeds the multiplier's assumed margin (entirely plausible over a multi-week staleness window, as ETH has repeatedly moved >20% in weeks), every message sent during that window is underpriced.

### Impact Explanation
This directly matches the Impact Gate category "public underpriced work that degrades block production or stalls bridge processing": any user can call the permissionless `validate`/`deliver` path and have real Ethereum-side execution/relay work priced using a rate that has drifted from the true market rate, with no code-level safeguard beyond a static multiplier chosen at the last manual update. Because the fee is charged once, upfront, in DOT, but the actual cost that must be covered is denominated in ETH on Ethereum, sustained underpricing means:
- Relayers are not adequately compensated for gas/reward, disincentivizing them from relaying, causing a backlog of committed-but-unrelayed messages (bridge processing stall), or
- The reward pool funding relayers is drained faster than it is replenished, since messages are systematically undercharged relative to real delivery cost.

Unlike the disputed Kelp arbitrage (which the protocol accepted as a tolerable feature), this failure mode has a direct, non-speculative chain-of-custody impact on bridge liveness rather than just LP economics.

### Likelihood Explanation
Likelihood is moderate-to-high: no attacker action or privileged access is required — ordinary bridge users trigger the vulnerable pricing path on every single outbound message, and the staleness window is a documented weeks-long interval by design ("interim measure... governance should manually update these parameters every few weeks"). Any real-world ETH/DOT or gas-price movement exceeding the static `multiplier`'s assumed buffer during that multi-week window will systematically underprice all outbound messages until the next manual update — this is a mechanical certainty of market volatility, not a probabilistic edge case.

### Recommendation
- Track and enforce a maximum age for `PricingParameters` (reject/`validate()`-fail messages if the parameters have not been refreshed within an on-chain-defined `MaxPricingParametersAge`).
- Make the `multiplier` dynamic (e.g., scale with elapsed blocks since the last update) rather than a static value chosen at update time, so the safety margin actually grows with staleness instead of remaining fixed regardless of how long the rate has been unrefreshed.
- As the module doc itself notes as the long-term fix, source `exchange_rate` from an on-chain liquidity pool (e.g. `pallet-asset-conversion`) once available, replacing the manual governance update entirely.

### Proof of Concept
Conceptual, since this requires no privileged actor:
1. Governance sets `PricingParameters.exchange_rate` and `multiplier` reflecting current ETH/DOT market conditions via `set_pricing_parameters`.
2. Over the following weeks (per design, this is the expected update cadence), the real ETH/DOT price and/or Ethereum gas price moves beyond what `multiplier` was calibrated to absorb (e.g., ETH price falls relative to DOT, or gas spikes).
3. Any unprivileged user calls `send` (via `pallet_snowbridge_system` or an XCM export) any number of times; `Pallet::validate` computes `fee` via `calculate_fee` using the now-stale `exchange_rate`/`multiplier`, unconditionally, with no check that the rate is still representative: `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` lines 366-393.
4. Each message is enqueued and later committed with `reward`/`max_fee_per_gas` baked in from the stale conversion — messages accumulate whose DOT-denominated fee does not cover real ETH-denominated relay cost, until governance performs the next manual `set_pricing_parameters` update.

Because I could not execute this end-to-end in a live runtime within this session, the quantitative threshold at which the static `multiplier` is actually exceeded by real market moves is asserted from the documented design (manual, multi-week update cadence, no on-chain freshness/deviation enforcement) rather than from a reproduced numeric trace; a background agent with runtime access should build a concrete integration test (setting `PricingParameters`, advancing blocks, and simulating a rate divergence) to quantify the exact underpayment.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}

			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}
