## Finding

### Title
Unvalidated length/offset fields in TVM precompile ABI decoding cause uncaught `OutOfMemoryError`/out-of-bounds array access - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts` contains several private ABI-decoding helpers (`extractBytes32Array`, `extractBytesArray`, `extractSigArray`) that read attacker-controlled length and offset words directly from precompile call-data and use them to size arrays and compute `System.arraycopy`/`Arrays.copyOfRange` bounds, without validating them against the actual length of the input buffer. This mirrors the JLSEC-2026-299 bug class: a decoder trusts an in-band length field from untrusted input and uses it to drive a memory operation, causing corruption/DoS.

### Finding Description
`extractBytes32Array` and `extractBytesArray` read `len` from `words[offset].intValueSafe()` — a value fully controlled by the calldata of a `TriggerSmartContract` call to a precompiled address (e.g. batch signature validation) — and then allocate `new byte[len][]` or index `words[offset + i + 1]` without checking `len` against `words.length` or the size of `data`: [1](#0-0) [2](#0-1) 

`extractSigArray` has the same pattern, deriving `bytesOffset` from a caller-controlled word and passing it straight into `extractBytes`, which does an unchecked `Arrays.copyOfRange(data, offset, offset + len)`: [3](#0-2) 

If `len` is a large positive value (up to `Integer.MAX_VALUE` via `intValueSafe()`), `new byte[len][]` at line 392/404/419 triggers a JVM `OutOfMemoryError`, which is an `Error`, not a `RuntimeException`. The TVM's opcode loop in `VM.play()` only guards against `RuntimeException`, `JVMStackOverFlowException`, `OutOfTimeException` and `StackOverflowError` — it does not catch general `Error` types such as `OutOfMemoryError`: [4](#0-3) 

An uncaught `OutOfMemoryError` escaping transaction execution can destabilize the executing node thread (and potentially the JVM heap generally), which is the functional analog of the HDF5 decode buffer-overflow causing "corruption of the instruction pointer... DoS or potential code execution" — here the analog outcome is denial of service via resource-exhaustion/crash triggered by an unchecked length field during decode. Alternatively, if `bytesOffset`/`bytesLen` computed from attacker words point past `data.length`, `Arrays.copyOfRange`/`System.arraycopy` throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`, which — while `RuntimeException` and thus caught by `VM.play()` — still demonstrates the decoder trusts untrusted length data without validating it against the real buffer bounds, the same root-cause class as the reported CVE.

### Impact Explanation
A crafted `TriggerSmartContract` transaction targeting the batch-signature-validation precompile can supply an oversized length word, causing the node to attempt a multi-gigabyte array allocation during transaction execution. This is an uncaught `Error` path not defended by the VM's `RuntimeException`-only recovery logic, risking node instability/crash (denial of service) triggerable by any unprivileged transaction broadcaster with no special permissions.

### Likelihood Explanation
The precompile is reachable by any account that can submit a `TriggerSmartContract` transaction calling the fixed precompile address with crafted calldata — no special privileges, deployed contract, or SR/witness status required. The vulnerable helper functions are simple, single-word-controlled allocations, making exploitation straightforward once calldata layout is known.

### Recommendation
Add explicit bounds validation in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before using `len`/`bytesOffset`/`bytesLen`: reject if `len` exceeds a sane maximum consistent with `data.length` / `words.length`, and validate that computed offsets and lengths stay within `data.length` before calling `Arrays.copyOfRange`/`System.arraycopy` or allocating `new byte[len][]`. Consider catching `OutOfMemoryError` (or pre-validating allocation sizes) around precompile execution in `VM.play()`/`Program` to prevent it from escaping the standard exception-handling path.

### Proof of Concept
1. Deploy or use an existing contract that performs a low-level `call` to the batch-signature-validation precompile address, or invoke it directly via `TriggerSmartContract`.
2. Construct calldata whose word at the array-length offset (consumed by `extractBytesArray`/`extractSigArray`) encodes a very large positive integer (e.g., `0x7FFFFFFF`).
3. Submit the transaction; when `PrecompiledContracts` decodes the array header at [5](#0-4) , it attempts `new byte[len][]`, forcing a large allocation attempt uncontrolled by the length of the actual supplied `data`, which can throw `OutOfMemoryError` outside the `RuntimeException`-scoped recovery in `VM.play()`.
