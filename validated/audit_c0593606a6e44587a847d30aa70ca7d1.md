### Title
Floating-point precision drift in TRC10 Exchange bonding-curve math allows value extraction via round-trip trades - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator` lets any account submit `ExchangeTransactionContract` to trade against a TRC10 bancor-style relay-pool (`ExchangeCapsule`). The default calculation path (`ExchangeProcessor`) uses `double`/`Math.pow` arithmetic instead of the exact `BigDecimal` "hardened" path (`SafeExchangeProcessor`), which is only used when the `allowHardenExchangeCalculation` chain parameter is enabled. This mirrors the Nirvana incident's root cause class: an AMM/bonding-curve whose pricing function is not conservative/monotonic under successive trades, letting a single unprivileged account manipulate the pool balances within one or a few back-to-back transactions and extract more value than deposited, purely from the floating-point rounding behavior of the curve — no flash loan primitive is needed because the exchange itself holds the liquidity that gets manipulated.

### Finding Description
`ExchangeCapsule.transaction()` selects between two `Processor` implementations depending on the `hardenedCalc` flag returned by `allowHarden()`: [1](#0-0) 

The default/legacy processor, `ExchangeProcessor`, computes the bancor relay conversion using `double` and `Math.pow`: [2](#0-1) 

This differs from the exact-arithmetic `SafeExchangeProcessor`, which uses `BigDecimal` with explicit rounding and also enforces that post-trade balances cannot go negative: [3](#0-2) [4](#0-3) 

Whether the hardened path is used is controlled by a runtime/committee-toggleable dynamic property, checked per-call from `AbstractExchangeActuator.allowHarden()`: [5](#0-4) 

`ExchangeTransactionActuator.execute()` invokes `exchangeCapsule.transaction(...)` using this same toggle and then persists the new pool balances unconditionally: [6](#0-5) 

`doValidate()` only checks that the amount received is `>= tokenExpected` (a slippage floor supplied by the caller themselves) — it does not protect the pool's own economics or bound the trade size relative to reserves beyond `getExchangeBalanceLimit()`: [7](#0-6) 

Unlike the Nirvana `buy3`/`swap` functions, which used an internally inconsistent AMM/vault design that a flash-loaned trade could push out of equilibrium and then arbitrage back for profit, java-tron's non-hardened bonding-curve path is exposed to the analogous class of bug: `double`-precision `Math.pow`/division is not guaranteed to be exactly invertible or conservative. Repeated legitimate-looking `ExchangeTransactionContract` calls (buy then sell, or trading through a chain of exchanges) can accumulate rounding bias in the attacker's favor at the expense of the pool (or vice versa causing pool insolvency/drain), since `ExchangeProcessor.exchange()` mutates `supply`/pool balances directly from floating-point results without any invariant check equivalent to `SafeExchangeProcessor`'s non-negative-balance assertion.

### Impact Explanation
If the floating-point drift is exploitable and consistently biased in one direction, an attacker can drain TRX/TRC10 reserves from an `ExchangeCapsule` pool through a sequence of ordinary, unprivileged `ExchangeTransactionContract` calls — this is an unauthorized extraction of pooled funds analogous to the $3.5M loss in the Nirvana incident, satisfying the "concrete unauthorized account operation / theft of funds" bar. Because the non-hardened `ExchangeProcessor` lacks the `SafeExchangeProcessor`'s balance-non-negative guard, a sufficiently large/repeated trade sequence could also push a pool's `firstTokenBalance`/`secondTokenBalance` negative or into an inconsistent unbacked state, corrupting on-chain accounting for that exchange.

### Likelihood Explanation
Exploitability depends entirely on whether `allowHardenExchangeCalculation` is enabled network-wide; if it is off (the legacy default before the hardening was introduced), every `ExchangeTransactionContract` on every existing `ExchangeCapsule` runs through the unguarded `double`-math path. I could not confirm within the available tool budget whether this parameter currently defaults to enabled or disabled in `DynamicPropertiesStore`, nor did I find/verify a concrete numeric round-trip profitable to an attacker (that would require running the `Maths.pow` computations against representative reserve sizes) — so this should be treated as a **potential, unconfirmed** analog requiring further arithmetic verification rather than a proven exploit.

### Recommendation
- Determine the current default and any active committee-proposal state of `allowHardenExchangeCalculation`; if legacy `ExchangeProcessor` is still reachable in production, deprecate it entirely (make `SafeExchangeProcessor` mandatory) rather than gating it behind a toggle.
- Add the same non-negative/invariant balance checks from `SafeExchangeProcessor` to the non-hardened path, or remove the non-hardened path.
- Add fuzz/property tests that assert `exchange(a,b,x)` then `exchange(b',a',y)` round trips can never yield the caller more than `x` net (conservation-of-value invariant) under the legacy processor.

### Proof of Concept
Not able to construct a concrete numeric PoC within the current investigation — this would require simulating `ExchangeProcessor.exchange()` across a buy/sell round trip with realistic reserve values (similar to the existing `ExchangeProcessorTest.testSellAndBuy`/`testSellAndBuy2` cases, which already show non-symmetric results between forward and reverse trades) to demonstrate a net attacker profit purely from floating-point rounding, e.g.: [8](#0-7) 
Such a test already illustrates that selling `sellQuant` and then immediately buying back with the resulting `result` does not return exactly the original `sellQuant`; whether this discrepancy is net-positive for an attacker across achievable trade sizes needs targeted verification before treating this as a confirmed exploit.

    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
