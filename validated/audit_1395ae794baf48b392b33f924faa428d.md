Based on my investigation, java-tron contains a directly analogous issue in the fund-transfer actuators reachable from a single signed transaction.

### Title
Missing "zero-value" address check for `to`/`toAddress` in transfer actuators allows permanent loss of funds - (File: `common/src/main/java/org/tron/common/utils/DecodeUtil.java`)

### Summary
`DecodeUtil.addressValid`, the single address-format validator used across `TransferActuator`, `TransferAssetActuator`, and the TVM's `VMUtils.validateForSmartContract`, only checks the address length and the network prefix byte. It never rejects an address whose 20-byte payload is all zeros (the TRON analog of Solidity's `address(0)`), even though no private key is known to control such an address.

### Finding Description
`DecodeUtil.addressValid` performs exactly two checks — length equal to `ADDRESS_SIZE/2` and correct prefix byte — with no check that the address body is non-zero: [1](#0-0) 

This validator is the sole address-format gate used by `TransferActuator.validate()` for `toAddress`: [2](#0-1) 

and by `TransferAssetActuator.validate()` for `toAddress`: [3](#0-2) 

and by TVM's internal TRC10 transfer validation used by contract-triggered transfers: [4](#0-3) 

In each `execute()` path, if the destination account doesn't already exist in `AccountStore`, the code silently creates a brand-new normal account at that address and credits it — this is exactly what happens for `TransferActuator.execute()`: [5](#0-4) 

Because there is no rejection of the all-zero address body, a member/broadcaster can submit a `TransferContract`, `TransferAssetContract`, or trigger a smart contract that performs an internal TRC10/TRX transfer, with `to_address` set to the prefix byte followed by 20 zero bytes. This passes `addressValid` (correct length, correct prefix), and the actuator happily creates that account and moves the asset/TRX into it. No private key is realistically known for such an address, so any TRX/TRC10 token sent there is unrecoverable.

### Impact Explanation
Funds (TRX in `TransferActuator`, TRC10 tokens in `TransferAssetActuator`, or TRC10 sent from within a smart contract via `VMUtils.validateForSmartContract`) sent to the "zero-value" address become permanently inaccessible, since no corresponding private key is known to exist for a purely-zero 20-byte payload. This constitutes permanent freezing/loss of user funds, matching the qualifying impact criteria.

### Likelihood Explanation
Any account holder (an unprivileged transaction broadcaster) can trigger this by constructing and signing a `TransferContract` or `TransferAssetContract` with `to_address` set to the zero-value address, or by writing/calling a smart contract that performs a TRC10 transfer to that address. No special privilege or witness/committee role is required — a single signed transaction suffices.

### Recommendation
Add an explicit check in `DecodeUtil.addressValid` (or immediately after it in each actuator's `validate()`) rejecting addresses whose 20-byte body is all zero, in addition to the existing length/prefix checks, mirroring the recommended `address(0)` guard from the referenced report.

### Proof of Concept
1. Construct a `TransferContract` with `owner_address` = a funded account and `to_address` = `<addressPreFixByte>` followed by 20 zero bytes (e.g. hex `41` + `0000000000000000000000000000000000000000` on mainnet prefix).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes `DecodeUtil.addressValid(toAddress)` (correct length/prefix), so validation succeeds.
4. `TransferActuator.execute()` finds no existing account at that address, creates a new `AccountCapsule` there, and credits it with the transferred amount — see [5](#0-4) .
5. The TRX is now held by an account with no known controlling private key, permanently locked. The same pattern applies to `TransferAssetActuator` for TRC10 tokens and to TVM-triggered TRC10 transfers via `VMUtils.validateForSmartContract`.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
  }
