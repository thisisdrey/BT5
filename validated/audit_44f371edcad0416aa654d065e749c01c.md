### Title
Dust-filling the fee collector's token list DoS-es deposits, withdrawals and liquidations - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` enforces a combined cap of `MAX_TOKENS_PER_USER = 30` deposit+debt tokens per account, checked inside `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` (Pool.sol:143-148, 204-220). That check runs on every `DepositToken._transfer` and `_mint` whenever the recipient's balance of that token moves from 0 (DepositToken.sol:486-488, 518-520). The protocol's own `feeCollector` is a recipient of fee transfers on `withdraw` (`_transfer(account_, feeCollector, _fee)`, DepositToken.sol:547), fee mints on `deposit` (DepositToken.sol:231), and fee seizes on `liquidate` (Pool.sol:592). An unprivileged attacker can push the fee collector over the 30-token cap by dust-depositing / dust-transferring every distinct `DepositToken` registered in the pool to it, causing every fee-charging code path to revert with `UserReachedMaxTokens`.

### Finding Description
1. The pool registers up to 30 `DepositToken`s (`addDepositToken` caps `depositTokens.length() < MAX_TOKENS_PER_USER`, Pool.sol:703).
2. `DepositToken.deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` (DepositToken.sol:234) and `transfer`/`transferFrom` move balances to arbitrary recipients (DepositToken.sol:348-376). Both routes call `pool.addToDepositTokensOfAccount(recipient)` when the recipient's balance was zero.
3. `addToDepositTokensOfAccount` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (Pool.sol:143-146).
4. The attacker calls `deposit(1 wei, feeCollector)` (or dust `transfer`s) for each `DepositToken` the fee collector does not yet hold. FeeCollector already holds some tokens from accrued fees; the attacker fills the rest until the combined count is 30.
5. From then on:
   - `DepositToken.deposit` reverts at `_mint(feeCollector, _fee)` whenever `depositFee > 0` and the fee token is one whose `balanceOf[feeCollector] == 0` — and if the attacker rotated the collector's tokens, this is every fee token.
   - `DepositToken.withdraw`/`withdrawFrom`/`flashWithdraw` revert inside `_withdraw` at `_transfer(account_, feeCollector, _fee)` when `withdrawFee > 0` (DepositToken.sol:546-547).
   - `Pool.liquidate` reverts at `depositToken_.seize(account_, feeCollector, _fee)` when `protocolFee > 0` (Pool.sol:591-593).

Note the revert only triggers for a token whose collector balance is currently 0, so the precise DoS condition is: for each deposit token in the pool, either the collector already holds it (counted toward the cap) or a first-fee event would push it over. The attacker maximizes coverage by cycling dust in/out so the collector sits at exactly 30 with zero balance in every remaining token type — but even the simple version (collector holds ≥29 tokens, attacker adds the missing ones) bricks any token where the balance would be a fresh add once slots are exhausted. The cleanest weaponization: get the collector to 30 entries, then wait — any deposit token whose collector balance later drops to 0 (e.g., via `sweep` or treasury ops) can never receive fees again.

Actually the strongest and simplest form: the attacker fills the collector to exactly 30 tokens including at least one token whose balance he can later... — no: once at 30, *any* add of a token not already in the set reverts. Tokens already in the set with balance > 0 still accept fees. So the attacker should first observe which deposit tokens the collector does *not* hold, dust-fill it to 30 using the cheapest tokens, ensuring that the tokens most likely to charge fees next (e.g., newly added collateral, or tokens the collector swept clean) are the ones excluded. More robustly, `seize` in `liquidate` targets whatever `depositToken_` the liquidator chooses — the attacker can't control that — but for `deposit`/`withdraw` the fee token is fixed by the caller's token, so the attack permanently bricks *every* deposit token type the collector doesn't currently hold, and bricks the held ones too if their balance ever hits zero and the set still has 30 entries.

### Impact Explanation
While the collector is at the cap, all `withdraw` calls on every affected `DepositToken` revert (temporary freezing of user funds), all `deposit` calls revert, and `Pool.liquidate` reverts on the fee-seize leg — blocking liquidations and enabling bad-debt accumulation during adverse price moves. Recovery requires the governor-controlled `feeCollector` to `transfer` dust out to free a slot, so the freeze is temporary but persists until manual intervention; repeated re-filling by the attacker sustains the DoS. This is an unprivileged EOA attack using only public `deposit`/`transfer` entry points — analogous to the advisory's "unauthorized ability to cause a hang or crash (complete DOS)".

### Likelihood Explanation
- Requires the pool to have enough distinct deposit tokens (or debt tokens force-able onto the collector) to reach 30. `addDepositToken` explicitly permits up to 30 collaterals (Pool.sol:703), and Metronome pools historically list many Vesper/vToken collaterals; feasibility depends on the deployed pool's collateral count being ≥ ~30 minus entries already held. If a pool has few collaterals, the cap cannot be reached and the attack fails — this is the main constraint and makes likelihood pool-dependent.
- Where reachable, cost is dust amounts × number of missing tokens; no privilege, no oracle manipulation, no timing dependence.
- Modifiers (`whenNotPaused`, `nonReentrant`, `onlyIfDepositTokenExists`) do not prevent it; `SynthContext` meta-sender paths change nothing.

### Recommendation
- Skip the cap check for privileged/internal recipients: exempt `feeCollector` (and `Treasury`) from `onlyIfAdditionWillNotReachMaxTokens`, or add the token to the set unconditionally when `account_ == feeCollector`.
- Alternatively, deliver fees to the collector without registering the token in its per-account list (e.g., direct `Treasury.pull`-style accounting or a dedicated fee path that bypasses `addToDepositTokensOfAccount`).
- Optionally also block `onBehalfOf_ == feeCollector` dust deposits is insufficient alone — `transfer` dust must also be addressed, so the set-exemption is the correct fix.

### Proof of Concept
Foundry fork sketch (Hardhat equivalent identical):

```solidity
// Setup: pool P with >= K registered DepositTokens such that
// existing collector entries + K >= 30. Let tokens[] = pool.getDepositTokens().

function test_FeeCollectorListGriefing() public {
    address feeCollector = poolRegistry.feeCollector();

    // 1. Fill collector's list to MAX_TOKENS_PER_USER
    for (uint i; i < tokens.length; ++i) {
        IDepositToken dt = IDepositToken(tokens[i]);
        if (dt.balanceOf(feeCollector) == 0 &&
            pool.getDepositTokensOfAccount(feeCollector).length
              + pool.getDebtTokensOfAccount(feeCollector).length < 30) {
            deal(address(dt.underlying()), attacker, 1);
            dt.underlying().approve(address(dt), 1);
            dt.deposit(1, feeCollector); // or transfer after self-deposit
        }
    }
    assertEq(
        pool.getDepositTokensOfAccount(feeCollector).length
          + pool.getDebtTokensOfAccount(feeCollector).length, 30);

    // 2. Pick a deposit token whose collector balance is 0 (not in set)
    IDepositToken victim = /* a token not in collector's set */;
    deal(address(victim.underlying()), alice, 100e18);
    vm.startPrank(alice);
    victim.underlying().approve(address(victim), 100e18);
    victim.deposit(100e18, alice);

    // 3. Withdraw now reverts on the fee transfer to the collector
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    victim.withdraw(50e18, alice);

    // 4. Liquidations also revert on the protocol-fee seize
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    pool.liquidate(msUSD, unhealthyAcct, repayAmt, victim);
}
```

Precondition noted above: the attack is only executable on pools where the attacker can actually reach the 30-entry cap (enough registered deposit tokens). If the deployed pool has substantially fewer than 30 collaterals and the collector holds few entries, this reduces to a non-reachable edge case — verify `pool.getDepositTokens().length` on the target deployment. Uncertainty: `DebtToken` transferability was not fully verified; if debt tokens are transferable, the cap becomes reachable with fewer collaterals.
