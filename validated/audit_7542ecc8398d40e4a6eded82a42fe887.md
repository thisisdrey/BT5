## Title
Unbounded per-address delegation index growth enables resource-exhaustion DoS on `getDelegatedResourceAccountIndexV2` query path - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
The `DelegatedResourceAccountIndexStore` stores one DB entry per `(from, to)` delegation pair under the `V2_FROM_PREFIX`/`V2_TO_PREFIX` key scheme. Any account can create such an entry cheaply (freeze the ~1 TRX minimum and issue a `DelegateResource`/`FreezeBalanceV2`-with-delegate transaction to an arbitrary receiver). There is no cap on how many distinct counterparties can delegate to (or receive from) a single address. When the index for that address is later queried, `getV2Index` → `getWithPrefix` performs an unbounded `prefixQuery` over the DB and materializes/sorts the full result set in memory with no limit, mirroring the exact bug class described in the report (an actor-controlled, unbounded, low-cost list that a later read path iterates without limit).

### Finding Description
`DelegateResourceActuator`/`DelegateResourceProcessor` create per-pair delegation index records via `DelegatedResourceAccountIndexStore.delegate`/`delegateV2` [1](#0-0) , and the V2 key-based version: [2](#0-1) 

Reading this index for a given account does not respect any bound — `getWithPrefix` performs a raw `prefixQuery` over the DB for both the "from" and "to" prefixes and materializes every matching entry into an `ArrayList`, sorts it, and builds a full response list: [3](#0-2) 

`Chainbase.prefixQuery` itself has no result-size limit, unlike other range-scan helpers (`getValuesNext`, `getKeysNext`, `getNext`) that take an explicit `limit` parameter: [4](#0-3) 

This index is reachable via `Wallet.getDelegatedResourceAccountIndexV2`, exposed through gRPC and HTTP (`GetDelegatedResourceAccountIndexV2Servlet`): [5](#0-4) [6](#0-5) 

An attacker can create a large number of distinct delegator accounts, freeze the minimum 1 TRX for a resource, and delegate it to a single victim address repeatedly (or vice versa, delegate from one account to many receivers). Each entry costs only the frozen (and later unfreezable) 1 TRX plus a negligible transaction fee — analogous to the "at least only 1gwei token is required" cost noted in the original report. There is no per-account limit on the number of distinct delegation counterparties, unlike the `frozenList` for plain (non-V2) freeze, which is explicitly limited to 1 entry (`frozenCount must be 0 or 1`) [7](#0-6) .

### Impact Explanation
Once thousands of index entries are attached to a single address, any subsequent call to `getDelegatedResourceAccountIndexV2` (gRPC/HTTP) for that address forces the node to scan and materialize the full unbounded result set in memory and CPU (`prefixQuery` + `HashMap` construction + full sort), with no pagination or limit. This is a resource-exhaustion vector against the query-serving path of full/solidity/PBFT nodes — the query for that specific poisoned address can degrade or exhaust node resources, denying that API to legitimate callers (matches the accepted impact class "an API the node can no longer serve").

### Likelihood Explanation
Likelihood is limited by two factors I could not fully verify from the available index: (1) whether `getDelegatedResourceAccountIndexV2` and the underlying HTTP/gRPC services are rate-limited (`GetDelegatedResourceAccountIndexV2Servlet extends RateLimiterServlet`, suggesting some throttling exists) [8](#0-7) , and (2) the real-world economics of creating enough entries to cause meaningful resource exhaustion (each entry requires a separate funded account due to the per-account frozen-balance requirement, unlike the original report's cheap repeated single-account bounty deposits). This makes the attack costlier than the original OpenQ analog, though still feasible at scale for a determined attacker, and the underlying code pattern (unbounded actor-controlled list, unbounded read-side iteration) is a direct structural match to the reported bug class.

### Recommendation
- Add a maximum cap on the number of distinct delegation counterparties tracked per address (analogous to the frozen-list-size==1 limit already enforced for classic `FreezeBalanceContract`), or
- Add a `limit`/pagination parameter to `getWithPrefix`/`prefixQuery` consistent with the pattern already used by `getValuesNext`/`getKeysNext`/`getNext`, and enforce a maximum scan size in `Chainbase.prefixQuery`.
- Alternatively, require a minimum non-trivial delegation size or apply a per-block/per-account rate limit on `DelegateResource` calls to increase the cost of building up index bloat.

### Proof of Concept
1. Create N distinct accounts, each funded with slightly more than 1 TRX.
2. For each account, `FreezeBalanceV2` 1 TRX for BANDWIDTH/ENERGY, then `DelegateResource` that 1 TRX to a single victim address, causing `DelegatedResourceAccountIndexStore.delegateV2` to add a new keyed record `V2_TO_PREFIX + victim + attacker_i` for each `i`.
3. Repeat for a large N (thousands), which is cheap since delegated TRX can later be un-delegated and re-frozen/redelegated from a smaller pool of accounts over time, or performed by many low-value Sybil accounts.
4. Call `getDelegatedResourceAccountIndexV2` (gRPC or HTTP `/wallet/getdelegatedresourceaccountindexv2`) for the victim address; observe the unbounded `prefixQuery` scan and in-memory sort in `getWithPrefix` consuming disproportionate CPU/memory relative to a normal query, as no code path in `DelegatedResourceAccountIndexStore.java:114-138` or `Chainbase.java:352-368` limits the number of records processed.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
  }

    Map<WrappedByteArray, byte[]> result = prefixQueryRoot(key);
    Map<WrappedByteArray, byte[]>  snapshot = prefixQuerySnapshot(key);
    result.putAll(snapshot);
    result.entrySet().removeIf(e -> e.getValue() == null);
    return result;
  }

  private Map<WrappedByteArray, byte[]> prefixQueryRoot(byte[] key) {

      result = ((RocksDB) ((SnapshotRoot) head.getRoot()).db).getDb().prefixQuery(key);
