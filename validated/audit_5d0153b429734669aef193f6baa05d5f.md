Based on the investigation, the strongest reachable analog in java-tron to the `configure_collection` bug class (a governance-configuration value being recalculated against **currently mutable state**, which retroactively changes whether a pending item gets "tipped"/approved) is the **DPoS proposal-approval threshold calculation** in `ProposalCapsule.hasMostApprovals` / `ProposalController.processProposal`.

### Title
Proposal approval threshold recalculated against mutable active-witness set at processing time, allowing stale/insufficient approvals to unexpectedly tip governance proposals - (File: `chainbase/src/main/java/org/tron/core/capsule/ProposalCapsule.java`)

### Summary
Like `configure_collection` recomputing `max_voter_weight` from the *current* collection configs (rather than the configs in effect when the proposal was created), java-tron's proposal system recomputes a proposal's pass/fail threshold from the **current** active-witness set at the moment the proposal is processed, rather than any value fixed when the proposal was created or when each approval was cast.

### Finding Description
A witness casts a `ProposalApproveContract` to approve a pending proposal; validation only checks that the witness is currently registered, not that it is an active/standby witness at approval time [1](#0-0) . Approvals simply accumulate in the `ProposalCapsule` [2](#0-1) .

The actual pass/fail decision is deferred to `ProposalController.processProposal`, which is only invoked once the proposal expires (at a maintenance cycle boundary), and it fetches the **live** active-witness list from `WitnessScheduleStore` at that moment: [3](#0-2) 

The threshold itself, `hasMostApprovals`, computes `count >= activeWitnesses.size() * 7 / 10` using whatever the active-witness list happens to be *at call time*, not the set of active witnesses when the proposal was created or when each approval vote was cast: [4](#0-3) 

The active-witness set (`ACTIVE_WITNESSES`) is itself mutated every maintenance cycle by `MaintenanceManager.doMaintenance()` / `DposService.updateWitness()`, based on the latest SR vote tally — a process entirely independent of, and with no synchronization against, outstanding proposals: [5](#0-4) [6](#0-5) 

This exactly mirrors the reported bug class: a configuration value used to gate an irreversible "tip"/finalize decision (`max_voter_weight` in the report, `activeWitnesses.size()` / the 70% quorum threshold here) is silently recomputed from whatever the *current* global state is, rather than being fixed relative to the pending item. There is no analog of the report's remediation — `ProposalCapsule`/`ProposalController` contain no equivalent guard (e.g., "reject SR-set changes while proposals are pending") to prevent the witness set from shifting under a proposal's feet.

### Impact Explanation
Because SR (witness) set membership can change between when approvals are collected and when the proposal is finally tallied at expiration, and the 70% threshold is evaluated against whatever set is active *then*:
- A proposal that genuinely never reached quorum among the witnesses that were active while it was open can still flip to `APPROVED` if the active-witness set shrinks (or reshuffles) by expiration time, lowering the absolute vote count needed.
- Approvals cast by witnesses who are no longer in the active set at tally time are silently filtered out of the numerator (`count`) via the `filter(activeWitnesses::contains)` check, while the denominator is also recomputed from the new set — so the outcome is a function of unrelated, ongoing SR election activity rather than a fixed snapshot tied to the proposal.
- `setDynamicParameters` executes chain-wide parameter changes (network fees, energy limits, TVM feature flags, etc.) once a proposal is marked `APPROVED` — see the large parameter-application switch in `ProposalService.process` [7](#0-6) , so an unintended tip here directly and irreversibly alters live network parameters.

This is a governance-integrity issue rather than a fund-theft primitive, so it is scoped as Medium under the given severity floor, since it can cause unauthorized activation of a chain parameter change without a genuine, stable quorum having approved it.

### Likelihood Explanation
Witness set churn happens naturally every maintenance cycle as SR votes shift (`MaintenanceManager.doMaintenance`), so this condition can arise organically without any single malicious actor forging signatures — it only requires a proposal to remain pending across witness-set changes, which is a normal, expected occurrence in java-tron's operation given proposal expiration windows span multiple maintenance cycles.

### Recommendation
Snapshot the qualifying witness set (or the required approval count) at proposal creation time and store it in the `ProposalCapsule`, then evaluate `hasMostApprovals` against that fixed snapshot instead of re-fetching `WitnessScheduleStore.getActiveWitnesses()` at processing time. Alternatively, adopt the audited project's remediation pattern: block active-witness-set changes (or freeze the relevant threshold) while any proposal is still pending, analogous to the `voting_proposal_count > 0` guard added to `configure_collection`.

### Proof of Concept
1. Witness set W1 (27 witnesses) is active; quorum requires `27 * 7/10 = 18` approvals.
2. A proposal is created and receives 18 approvals from witnesses in W1 — but before it expires, the maintenance cycle re-tallies SR votes and shrinks/rotates the active-witness set to W2 (e.g., 20 witnesses), some of the 18 original approvers no longer being active.
3. At expiration, `ProposalController.processProposal` calls `hasMostApprovals(W2)`. `count` is now the intersection of stale approvals with W2 (potentially far fewer than 18), and quorum is `20 * 7/10 = 14`.
4. Depending on the overlap, a proposal that never had genuine 70% support among any single consistent active set can still be marked `APPROVED`, or conversely a proposal with earlier genuine 70% support under W1 gets disapproved — demonstrating the outcome is contingent on unrelated witness churn rather than a fixed quorum snapshot, exactly as `hasMostApprovals`/`processProposal` implement it: [3](#0-2) [4](#0-3) 

**Note on investigation limits:** I was unable to fully confirm, within the available tool iterations, the precise ordering of `ProposalController.processProposals()` relative to `MaintenanceManager.doMaintenance()` inside `Manager.java`'s maintenance-cycle entry point (the exact call site in `Manager.java` was matched but not read before the iteration budget ran out). This does not affect the core finding — that `hasMostApprovals` recomputes its threshold from a mutable, externally-updated active-witness list rather than a fixed snapshot — but a full confirmation of whether witness rotation happens strictly before or after proposal processing within the same block/cycle would sharpen the exact window of exploitability.

  public boolean hasMostApprovals(List<ByteString> activeWitnesses) {
    long count = this.proposal.getApprovalsList().stream()
        .filter(witness -> activeWitnesses.contains(witness)).count();
    if (count != this.proposal.getApprovalsCount()) {
      List<ByteString> InvalidApprovalList = this.proposal.getApprovalsList().stream()
          .filter(witness -> !activeWitnesses.contains(witness)).collect(Collectors.toList());
      logger.info("InvalidApprovalList:" + getAddressStringList(InvalidApprovalList));
    }
    if (activeWitnesses.size() != MAX_ACTIVE_WITNESS_NUM) {
      logger.info("activeWitnesses size = {}", activeWitnesses.size());
    }
    return count >= activeWitnesses.size() * 7 / 10;
  }
