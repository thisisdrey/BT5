### Title
Unprivileged dust-transfer griefing fills `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, blocking deposits and collateral additions for the victim - ([File: contracts/Pool.sol])

### Summary
The `onlyIfAdditionWillNotReachMaxTokens` condition check in `Pool` is applied whenever a `DepositToken` reports that an account's balance went from 0 to positive. Because anyone can force a dust `transfer` (or `deposit` with `onBehalfOf_` = victim) of each registered deposit token to any address, an unprivileged attacker can populate a victim's `depositTokensOfAccount` set up to the `MAX_TOKENS_PER_USER = 30` cap. Once the combined `debtTokensOfAccount + depositTokensOfAccount` count reaches 30, every subsequent `addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` reverts with `UserReachedMaxTokens`, reverting any `deposit`, `transfer`/`transferFrom`, `issue`, or leverage flow that would give the victim a new token type — a denial of service driven purely by an improper conditions check, analogous to CVE-2019-11139 (improper conditions check → DoS). ### Finding Description
`DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's prior balance was 0 and `amount_ > 0`. The recipient has no opt-in and cannot reject the addition. `Pool` enforces the cap in `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`.

An attacker holding (or flash-borrowing collateral to mint) each of the pool's `N` registered `DepositToken`s can `transfer(victim, 1 wei)` on each token, adding up to `N` entries to the victim's set. If the victim already holds positions in `k` distinct tokens, sending `30 - k` distinct dust deposit tokens fills the set. Thereafter:

- `deposit(..., onBehalfOf_ = victim)` reverts for any new collateral type (the `_mint` → `addToDepositTokensOfAccount` path reverts, rolling back the whole transaction, including the treasury `safeTransferFrom`).
- The victim cannot receive any new deposit token via `transfer`/`transferFrom` (`_revertIfLocked` only checks the sender; the revert occurs in the pool callback).
- The victim cannot `issue`/borrow a new synthetic (debt token minting adds to `debtTokensOfAccount`, also gated by the same modifier).

The victim can self-heal by fully emptying a token (balance → 0 triggers `removeFromDepositTokensOfAccount`), but the attacker can cheaply re-fill the freed slot in the same or next block, making the DoS persistent as long as the attacker wishes. This is "temporary freezing of funds": the victim's ability to deposit additional collateral — e.g., to rescue a position approaching liquidation — is denied at will, and any batch/multicall (e.g., `Operator.execute` or `SmartFarmingManager.leverage`) that deposits a new collateral type into the victim's account reverts atomically. ### Impact Explanation
Unprivileged attacker can prevent a target account from receiving any additional deposit token or debt token type. Concretely: (1) griefing blocks `deposit` with `onBehalfOf_` set to the victim — users/routers depositing on behalf of a listed victim revert; (2) a victim nearing liquidation cannot add a new collateral type to restore health (they may still add to existing types or repay, mitigating severity); (3) the attack is repeatable and cost is only dust deposits/transfers across the ~number of registered deposit tokens, which is bounded by the pool's actual registered tokens (typically < 30, so the attack only fully works when the victim already occupies some slots or the pool lists many tokens — in deployments with few deposit tokens the attacker can only partially fill the set). Funds are never stolen; the impact is a persistent, attacker-controlled temporary freeze of the victim's ability to expand their position.

### Likelihood Explanation
Requires no privileges, no oracle manipulation, no privileged roles — only an EOA transferring dust deposit tokens it legitimately owns. Feasibility depends on the deployed pool listing enough distinct deposit/debt tokens (plus the victim's existing holdings) to reach 30 entries; on pools with few registered tokens the attack only partially fills the set and the victim must already hold several token types for the cap to bind. Cost is negligible (dust amounts + gas). The existing tests confirm the revert path (`UserReachedMaxTokens`) is enforced on additions. [8](#0-7) 

### Recommendation
- Do not add to `depositTokensOfAccount`/`debtTokensOfAccount` on behalf of an account for transfers it did not initiate, or
- Only enforce `onlyIfAdditionWillNotReachMaxTokens` when the account itself initiated the state change (e.g., skip the cap in `transfer`/`seize` recipient paths and revert only on self-initiated `deposit`/`issue`), or
- Allow unsolicited additions beyond the cap but exclude them from `debtPositionOf` accounting until the holder opts in (e.g., a per-account per-token "enabled" flag), so griefed dust cannot block operations and also cannot distort health checks.

### Proof of Concept
A Hardhat (smock/fork) test demonstrates the revert: register deposit tokens, transfer dust to the victim until `debtTokensOfAccount + depositTokensOfAccount == 30`, then show `deposit`/`transfer` of a new token to the victim reverts with `UserReachedMaxTokens`.

```ts
// PoC sketch (Hardhat + smock), based on test/Pool.test.ts 'should revert when reach max tokens'
it('griefing: filling victim token list blocks new deposits', async () => {
  // register MAX_TOKENS_PER_USER deposit tokens and give attacker 1 wei of each
  for (let i = 0; i < 30; i++) {
    const dt = await smock.fake('DepositToken'); // or real DepositToken on a fork
    await pool.addDepositToken(dt.address);
    // attacker transfers dust to victim -> adds dt to victim's depositTokensOfAccount
    await depositToken_i.connect(attacker).transfer(victim.address, 1);
  }
  // victim's list is full: any new token mint/transfer to victim reverts
  await expect(
    newDepositToken.deposit(amount, victim.address) // _mint -> addToDepositTokensOfAccount
  ).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
});
```

Note: full PoC requires a deployment/fork where the count of registered deposit plus debt tokens (minus those already held by the victim) is ≥ 30; on smaller pools the attack only works against accounts already holding several token types.
