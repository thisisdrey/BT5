### Title
Single repository optimization failure aborts housekeeping for all remaining repositories in a storage - (File: `internal/gitaly/maintenance/optimize.go`)

### Summary
The daily maintenance walk that optimizes repositories in a storage stops entirely the moment a single repository's optimization returns an error, instead of skipping that repository and continuing with the rest — the same "all-or-nothing" halting pattern flagged in the AMM `settleFunding` report, where a single not-ready item blocked processing of every other item in the batch.

### Finding Description
`walkReposShuffled` iterates over every repository found in a storage and calls `optimizeRepo` for each one. Any error returned by `optimizeRepo` (which wraps `Optimizer.OptimizeRepository`) is immediately propagated up and the loop returns, terminating the walk for the rest of the storage: [1](#0-0) 

The only errors treated as "keep going" are `errIterOver` (end of walk) and `os.IsNotExist` (benign race). Every other error — including any failure inside `optimizeRepository`'s `CleanStaleData`, `CleanupWorktrees`, `repackIfNeeded`, or `writeCommitGraphIfNeeded` steps — aborts the entire remaining traversal: [2](#0-1) [3](#0-2) 

The caller, `OptimizeReposRandomly`, only logs the error and moves on to the *next storage*, not the next repository within the same storage: [4](#0-3) 

This means that once the shuffled walk encounters one repository whose optimization run errors out, every repository ordered after it in that day's random walk is silently skipped for that run — exactly analogous to the AMM bug where one AMM not being "ready" (`nextFundingTime` not elapsed) caused the batch call to revert and block updates to every other AMM, instead of just returning/skipping that one entry.

### Impact Explanation
Any tenant on a shared Gitaly storage can push content that reliably makes `optimizeRepository` fail (e.g., pathological ref/worktree state, disk-pressure induced repack failures, or any other error surfaced by `CleanStaleData`/`repackIfNeeded`/`writeCommitGraphIfNeeded`). Because a single failure aborts the remainder of the randomized walk, that one problematic repository can repeatedly deny scheduled housekeeping (repacking, pruning, commit-graph generation, stale-data cleanup) to an arbitrary number of *other* repositories that happen to be ordered after it in the shuffle on the same storage. Over time this causes those repositories to accumulate loose objects, stale worktrees, and unoptimized packs, degrading performance and increasing disk usage storage-wide — a availability/DoS-class impact on the maintenance subsystem affecting unrelated users' repositories.

### Likelihood Explanation
Likelihood is moderate: the walk order is reshuffled every run via `newRandomWalker`/`shuffledStoragesCopy`, so a bad repository won't deterministically block the same victims every day, but with a large number of repositories per storage and a daily cadence, a persistently-failing repository has a non-trivial chance each run of being visited before many other repositories, denying them housekeeping for that cycle. An attacker who can reliably reproduce an optimization failure (e.g., via corrupt ref/object state reachable from an ordinary push) can make this persistent across many days.

### Recommendation
In `walkReposShuffled`, do not return early when `optimizeRepo` fails for reasons intrinsic to that single repository (i.e., any error other than context cancellation or genuine walker/filesystem errors that abort the walk itself). Log the per-repository error and `continue` the loop so remaining repositories in the storage are still optimized, mirroring the non-atomic "reject-and-continue" pattern already used elsewhere in the codebase (e.g., `procReceiveHook`'s non-atomic reference update handling, which explicitly continues past individual failures — see `internal/gitaly/hook/receivepack/receive_pack.go` lines 112-138).

### Proof of Concept
1. On a Gitaly storage containing repositories `A`, `B`, `C`, arrange (or wait for the daily shuffle to place) a repository `A` whose on-disk state makes `RepositoryManager.optimizeRepository` return a non-nil error every time (e.g. a worktree or ref state that fails `housekeeping.CleanupWorktrees` or `repackIfNeeded`).
2. Trigger `DailyOptimizationWorker` → `OptimizeReposRandomly` → `walkReposShuffled` for that storage.
3. Observe that once `optimizeRepo(ctx, l, o, A)` returns an error at `internal/gitaly/maintenance/optimize.go:174-176`, `walkReposShuffled` returns immediately, and repositories `B` and `C` (which came after `A` in the shuffled order) never have `optimizeRepo` invoked for that run, even though they are healthy and eligible for optimization.

		fi, path, err := walker.next()
		switch {
		case errors.Is(err, errIterOver):
			return nil
		case os.IsNotExist(err):
			continue // race condition: someone deleted it
		case err != nil:
			return err
		}

		if !fi.IsDir() {
			continue
		}

		relativeRepoPath, err := filepath.Rel(s.Path, path)
		if err != nil {
			return err
		}

		repo := &gitalypb.Repository{
			StorageName:  s.Name,
			RelativePath: relativeRepoPath,
		}

		if locator.ValidateRepository(ctx, repo) != nil {
			continue
		}
		walker.skipDir()

		select {
		case <-ctx.Done():
			return ctx.Err()
		case <-ticker.C():
		}

		// Reset the ticker before doing the optimization such that we essentially limit
		// ourselves to doing optimizations once per tick, not once per tick plus the time
		// it takes to do the optimization. It's best effort given that traversing the
		// directory hierarchy takes some time, too, but it should be good enough for now.
		ticker.Reset()

		if err := optimizeRepo(ctx, l, o, repo); err != nil {
			return err
		}
	}
