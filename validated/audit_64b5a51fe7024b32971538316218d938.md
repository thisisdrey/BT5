### Title
Uninterrupted interest accrual across arbitrarily-long admin bank pauses causes surprise liquidation on unpause - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
`BankImpl::accrue_interest` computes elapsed time strictly as `current_timestamp - self.last_update`, with no accounting for whether the bank was in the `Paused` operational state for part or all of that interval [2](#0-1) . Because a group admin can place a bank into `BankOperationalState::Paused` for an arbitrary, uncapped length of time (unlike the rate-limited, 6-hour-capped protocol-wide `panic_pause`) [3](#0-2) , and `Paused` blocks deposit, withdraw, borrow, repay, and liquidation [4](#0-3) , a borrower has zero opportunity to repay or otherwise react during the pause window. When the bank is unpaused, the very next interest-touching instruction (deposit/withdraw/borrow/repay/liquidate/accrue) applies interest for the *entire* pause duration in a single step, potentially pushing previously-healthy accounts straight into liquidatable territory with no chance to react.

### Finding Description
Every user-facing instruction calls `bank.accrue_interest(clock.unix_timestamp, ...)` before performing balance changes, e.g. in `lending_account_repay` [5](#0-4) , `lending_account_withdraw` [6](#0-5) , and `lending_account_liquidate` [7](#0-6) . `accrue_interest` itself is:

```
let time_delta: u64 = (current_timestamp - self.last_update).try_into().unwrap();
...
self.last_update = current_timestamp;
``` [8](#0-7) 

There is no mechanism that freezes `self.last_update` when the bank enters `Paused`, nor a stored pause-start/pause-end timestamp used to subtract the paused interval from `time_delta`. `lending_pool_configure_bank`, the only instruction that can change `operational_state`, only calls `bank.configure(&bank_config)` and never touches `last_update` or invokes `accrue_interest` on pause/unpause transitions [1](#0-0) . Consequently, the elapsed real-world pause duration is folded into the very first `time_delta` computed after unpause, and the accrued borrow-interest jump is applied atomically to all borrowers of that bank in one shot.

While marginfi's per-period interest formula is "simple" per-period growth rather than the compounding formula in the BendDAO report (`calc_accrued_interest_payment_per_period` computes `value * (1 + apr * time_delta / SECONDS_PER_YEAR)`) [9](#0-8) , the underlying risk is the same as the analog: the elapsed pause time is charged instantaneously and in full when the pause ends, and users have no ability to intervene (repay, add collateral, etc.) during the pause because those instructions are explicitly blocked by `validate_bank_state(..., InstructionKind::FailsInPausedState)` while paused [10](#0-9) .

### Impact Explanation
Borrowers whose health is close to the maintenance threshold when a bank pause begins can become immediately eligible for liquidation the moment the bank is unpaused, purely as a mechanical consequence of the one-shot interest catch-up — with no way to repay, add collateral, or otherwise react during the pause. This is an unauthorized/unavoidable state change to account health outside user control, exposing users to unanticipated liquidation losses (loss of collateral, liquidation fees, insurance-fund cut) they could not have prevented. Because there is no cap on how long an admin-set `Paused` state can last (in contrast to `panic_pause`'s 6-hour/rate-limited design), the size of this "surprise" interest jump is theoretically unbounded.

### Likelihood Explanation
Requires an admin (trusted but not necessarily infallible/instantaneous in incident response) to place a bank into `Paused` for a non-trivial duration while it still carries outstanding variable-rate debt — a realistic operational scenario for incident response, oracle outages, or asset sunset procedures described in the bank-state guide itself [4](#0-3) . No malicious action is needed; it is a byproduct of normal pause/unpause administration, making the likelihood moderate whenever pauses exceed a few hours.

### Recommendation
Track pause-state timing on the `Bank` account (e.g., a `paused_at` timestamp set when `operational_state` transitions to `Paused`, cleared/consumed on transition back to `Operational`), and subtract the paused interval from `time_delta` in `accrue_interest`, or alternatively force-call `accrue_interest` immediately before entering `Paused` and reset `last_update` to the unpause timestamp when leaving `Paused`, so that no interest accrues for the duration the bank was inaccessible to users.

### Proof of Concept
1. Admin creates/operates a bank with active borrowers; a borrower's account health is close to (but above) the maintenance threshold.
2. Admin calls `lending_pool_configure_bank` setting `operational_state = Paused` [1](#0-0) . No `last_update` snapshot occurs.
3. Time passes (days/weeks — no protocol-level cap on bank-level `Paused` duration). Attempts by the borrower to `lending_account_repay` fail with `BankPaused` via `validate_bank_state` [10](#0-9) .
4. Admin calls `lending_pool_configure_bank` setting `operational_state = Operational`.
5. Any subsequent instruction touching the bank (e.g. another user's `lending_account_liquidate`, or a permissionless `lending_pool_accrue_bank_interest`) computes `time_delta = current_timestamp - self.last_update` spanning the entire pause window and applies the corresponding interest jump to `liability_share_value` in one step [11](#0-10) .
6. The borrower's debt value jumps discontinuously; their account, previously healthy, is now eligible for `lending_account_liquidate` before they can act.

pub fn lending_pool_configure_bank(
    ctx: Context<LendingPoolConfigureBank>,
    bank_config: BankConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;

    // If settings are frozen, you can only update the deposit and borrow limits, everything else is ignored.
    if bank.get_flag(FREEZE_SETTINGS) {
        bank.configure_unfrozen_fields_only(&bank_config)?;

        msg!("WARN: Only deposit+borrow limits updated. Other settings IGNORED for frozen banks!");

        emit!(LendingPoolBankConfigureFrozenEvent {
            header: GroupEventHeader {
                marginfi_group: ctx.accounts.group.key(),
                signer: Some(*ctx.accounts.admin.key)
            },
            bank: ctx.accounts.bank.key(),
            mint: bank.mint,
            deposit_limit: bank.config.deposit_limit,
            borrow_limit: bank.config.borrow_limit,
        });
    } else {
        // Settings are not frozen, everything updates
        bank.configure(&bank_config)?;
        msg!("Bank configured!");

        let group = ctx.accounts.group.load()?;
        bank.emode.validate_entries_with_liability_weights(
            &bank.config,
            group.emode_max_init_leverage,
            group.emode_max_maint_leverage,
        )?;

        emit!(LendingPoolBankConfigureEvent {
            header: GroupEventHeader {
                marginfi_group: ctx.accounts.group.key(),
                signer: Some(*ctx.accounts.admin.key)
            },
            bank: ctx.accounts.bank.key(),
            mint: bank.mint,
            config: bank_config,
        });
    }

    Ok(())
}

fn calc_accrued_interest_payment_per_period(
    apr: I80F48,
    time_delta: u64,
    value: I80F48,
) -> Option<I80F48> {
    let ir_per_period: I80F48 = apr
        .checked_mul(time_delta.into())?
        .checked_div(SECONDS_PER_YEAR)?;

    let new_value: I80F48 = value.checked_mul(I80F48::ONE.checked_add(ir_per_period)?)?;

    Some(new_value)
}
