### Title
Blacklisted user permanently cannot claim airdrop/rewards because payout is pushed to a hard-coded recipient - ([File: contracts/utils/RecurringAirdrop.sol])

### Summary
The external report's bug class is "push-style payout to a fixed, non-configurable recipient that reverts when the recipient is blocked from receiving the token (e.g., USDC blacklist)". Metronome has the same pattern in `RecurringAirdrop.claim` and `RewardsDistributor.claimRewards`: both transfer the reward token directly to the accrued owner (`msg.sender` / `account_`) with no `to_` parameter to redirect the payout, so a blacklisted claimant's tokens are frozen in the contract.

### Finding Description
In `RecurringAirdrop.claim`, the merkle leaf commits to `msg.sender`, `claimed[msg.sender]` is incremented, and the reward is pushed via `_transferReward(msg.sender, _claimable)` → `token.safeTransfer(msg.sender, amount_)`. There is no way for the entitled account to specify an alternate recipient. [1](#0-0) 

The same pattern exists in `RewardsDistributor._transferRewardIfEnoughTokens`, which pushes `rewardToken` to `account_` (the accrued owner) and zeroes `tokensAccruedOf[account_]` — anyone can call `claimRewards(account_, tokens_)`, but the tokens can only ever go to `account_` itself. [2](#0-1) [3](#0-2) 

Compare with `DepositToken.withdraw(uint256 amount_, address to_)` and `Treasury.pull(address to_, ...)`, which already accept a recipient parameter — showing the codebase otherwise follows the recommended pattern. [4](#0-3) [5](#0-4) 

If the airdrop/reward token has a blacklist or blocking transfer hook (USDC, USDT, WBTC-style pausable/blacklistable tokens — plausible reward/collateral assets in this protocol), and the entitled account is blacklisted after the merkle root is published or rewards accrue, then `safeTransfer` reverts on every `claim`/`claimRewards` call. `claimed`/accrued accounting only updates inside the same reverting transaction, so the user cannot recover or redirect the tokens at all — they remain locked in the distributor/airdrop contract.

### Impact Explanation
Permanent (or until unblacklisted) freezing of unclaimed yield. The user has a valid merkle entitlement / accrued balance but no code path to receive it at another address, exactly matching the original report's "funder cannot refund their deposit" impact. `sweep` on `TokenHolder` requires the governor and is a manual recovery path, not a user-facing fix. This qualifies under the accepted impact "theft/freezing of unclaimed yield / temporary freezing of funds".

### Likelihood Explanation
Requires (a) the distributed/reward token to implement a receive-blocking mechanism (common for USDC/USDT-class tokens), and (b) a user being blacklisted between entitlement and claim. This is an environmental condition rather than attacker-driven; the contract design provides no mitigation. Likelihood is low-to-medium; impact is freezing of funds — consistent with the original Medium severity. Note: this cannot be forced by an unprivileged attacker on a victim (blacklisting is done by the token issuer), so the finding rests on the liveness/freeze-of-funds impact for an innocent blacklisted user, same as the source report.

### Recommendation
Add a `to_` recipient parameter (or a separate `claimFor(account, to, proof)`) to `RecurringAirdrop.claim` and to `RewardsDistributor.claimRewards`, keeping entitlement accounting keyed to the merkle-leaf/accrued account while letting the user choose where tokens are sent — mirroring `DepositToken.withdraw(amount_, to_)`.

### Proof of Concept
Foundry fork/hardhat sketch:

```solidity
// Blacklistable reward token mock (e.g., modeled on USDC):
contract BlacklistableToken is ERC20Mock {
    mapping(address => bool) public blocked;
    function blacklist(address a) external { blocked[a] = true; }
    function _update(address f, address t, uint256 v) internal override {
        require(!blocked[f] && !blocked[t], "blacklisted");
        super._update(f, t, v);
    }
}

function test_blacklistedUserCannotClaim() public {
    // setup: deploy RecurringAirdrop with BlacklistableToken, fund it,
    // publish merkle root containing leaf (alice, amount)
    uint256 amount = 100e6;
    bytes32 leaf = keccak256(abi.encodePacked(alice, amount));
    airdrop.updateMerkleRoot(leaf /* single-leaf root */, bytes32("ipfs"));

    // alice gets blacklisted after root publication
    rewardToken.blacklist(alice);

    // every claim attempt reverts; there is no `to` override
    vm.prank(alice);
    vm.expectRevert("blacklisted");
    airdrop.claim(amount, new bytes32[](0));

    // tokens remain stuck in the airdrop contract
    assertEq(rewardToken.balanceOf(address(airdrop)), amount);
}
```

The identical test applies to `RewardsDistributor.claimRewards(alice, tokens)`: `_transferRewardIfEnoughTokens` reverts on the `safeTransfer(account_, amount_)` line and `tokensAccruedOf[alice]` is never payable to an alternate address.

Caveat: I could not fully verify which concrete reward token addresses are used in production `RecurringAirdrop`/`RewardsDistributor` deployments from the index, so whether a blacklistable token is actually distributed should be confirmed against the live deployment configuration.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }

    function _transferRewardIfEnoughTokens(address account_, uint256 amount_) private {
        IERC20 _rewardToken = rewardToken;
        uint256 _balance = _rewardToken.balanceOf(address(this));
        if (amount_ > 0 && amount_ <= _balance) {
            tokensAccruedOf[account_] = 0;
            _rewardToken.safeTransfer(account_, amount_);
            emit RewardClaimed(account_, amount_);
        }
    }
