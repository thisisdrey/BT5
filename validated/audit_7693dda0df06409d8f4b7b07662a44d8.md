### Title
Hardcoded remote pallet/call-index constants for cross-chain `Transact` XCM programs are not validated against the actual target runtime, enabling misrouted dispatch analogous to the Uniswap function-signature mismatch - (File: `cumulus/parachains/runtimes/bridge-hubs/bridge-hub-westend/src/bridge_to_ethereum_config.rs`)

### Summary
The Sherlock report's root cause was a *hardcoded interface encoding* (Solidity function selectors) that no longer matched the real target contract, so calls silently reverted instead of executing the intended function. The polkadot-sdk codebase has the same structural pattern in its cross-chain `Transact` builders: SCALE `#[codec(index = N)]` enums and raw `[pallet_index, call_index]` byte pairs are hand-maintained to mirror a *different, independently-upgradeable* runtime's `construct_runtime!` layout. There is no runtime-level check that these hardcoded indices still point at the intended pallet/call on the remote chain.

### Finding Description
Several places in the repo build XCM `Transact` payloads by hardcoding the remote chain's pallet index and call index as plain constants/enum discriminants, exactly like the Uniswap V3 selector constants that were supposed to mirror an external contract's ABI:

- `bridge_to_ethereum_config.rs` defines `CreateAssetCallIndex = [53, 0]` and `SetReservesCallIndex = [53, 33]`, which are spliced directly into the SCALE-encoded call tuple used by `convert_register_token` in `bridges/snowbridge/primitives/inbound-queue/src/v1.rs`: [1](#0-0) [2](#0-1) 

- The same pattern repeats for the Coretime pallet (`#[codec(index = 66)] Coretime(...)`, with nested call indices 1/2/3/4) and for the relay-chain Broker pallet (`#[codec(index = 50)] Broker(...)`, nested indices 1/3/19/20/99): [3](#0-2) [4](#0-3) 

- And again for the People-chain `IdentityMigrator` calls (`#[codec(index = 248)]`) and the staking-async `AhClient` calls (`#[codec(index = 0/3/4)]`), used to build `Transact` XCM to a relay chain / async-staking Asset Hub pair: [5](#0-4) [6](#0-5) 

In every case the comment explicitly documents that these constants are a manually-maintained mirror and "must be kept in sync" with the remote chain's `construct_runtime!` (e.g. "The codec index must correspond to the index of `Broker` in the `construct_runtime` of the coretime chain"). None of these paths perform any on-chain assertion, version check, or metadata lookup to confirm the remote pallet/call index still matches before encoding and sending the `Transact` instruction — the exact same class of defect as the Sherlock finding, where the controller hardcoded `bytes4` selectors that were supposed to mirror the Router contract's real ABI but silently drifted out of sync.

### Impact Explanation
If any of these mirrored indices drift from the real remote runtime (e.g. a pallet is added/removed/reordered in `construct_runtime!`, or a call variant is added before the referenced one, changing its discriminant), the `Transact` instruction will decode on the remote chain either:
1. As `NoSuchCall`/decode-failure → the whole cross-chain operation (asset registration, coretime purchase renewal, identity deposit poke, validator-set/session-key propagation) silently fails, matching the "calls rejected" impact in the original report, or
2. Worse, as a *different, unintended dispatchable* whose argument layout happens to decode successfully (arguments of matching SCALE shape) — causing execution of the wrong pallet call with attacker-uncontrolled but semantically incorrect effects (e.g. crediting wrong entity, setting wrong reserve/config, or mutating unrelated pallet state) since `Transact` executes under an elevated origin (`OriginKind::Xcm`/`OriginKind::Native`/`Superuser`-derived) once decoded.

Because these constructs sit on governance/session/asset-registration/staking-sync critical paths (asset registration reserve config, coretime revenue/credit accounting, validator key rotation via `AhClientCalls::SetKeysFromAh`), a silent misroute can desynchronize cross-chain state (e.g. reserve flags never set, validator keys never rotated) or apply unintended state changes, which maps to "runtime bugs that compromise intended behavior" / "duplicate settlement or payout" / "permanent... lock" categories in the impact gate.

### Likelihood Explanation
This is not attacker-triggered in the traditional sense (no malicious relayer/validator/governance needed) — it is triggered purely by the codebase's own maintenance process: any future PR that reorders pallets/calls in the *target* runtime's `construct_runtime!` without a synchronized update to every one of these hardcoded mirror modules silently reintroduces the exact Uniswap-style signature-mismatch bug. Given how many independent copies of this pattern exist across the tree (Snowbridge asset creation, Coretime, IdentityMigrator ×2, staking-async), and that the compiler/CI provides no cross-runtime verification that indices remain aligned, the likelihood of drift is non-trivial over the SDK's release cadence, and the comments themselves acknowledge this fragility ("must be kept in sync").

### Recommendation
- Add a runtime-to-runtime CI check (e.g. comparing generated metadata of the target runtime against the hardcoded mirror enums) that fails the build if any `#[codec(index = N)]` no longer matches the actual pallet/call index in the referenced runtime's `construct_runtime!`.
- Where possible, generate these mirror types from the target runtime's metadata automatically instead of hand-maintaining constants (similar to what `subxt`/`chain-spec-metadata` tooling already does), eliminating manual drift.
- For the Snowbridge `CreateAssetCallIndex`/`SetReservesCallIndex` specifically, consider deriving these from `AssetHub`'s published runtime metadata at genesis/config time rather than as opaque `[u8; 2]` constants.

### Proof of Concept
1. On the Ethereum→AssetHub Snowbridge path, `EthereumInboundQueueV1`/`v2` builds a `Transact` call using `CreateAssetCallIndex::get() = [53, 0]` (see `bridge_to_ethereum_config.rs` lines 88-90) and encodes it as `(create_call_index, asset_id, MultiAddress::Id(owner), MINIMUM_DEPOSIT).encode()` (see `bridges/snowbridge/primitives/inbound-queue/src/v1.rs` lines 254-287).
2. Suppose a future AssetHub runtime upgrade inserts a new pallet before pallet index 53, or reorders/prepends a new call in that pallet's `Call` enum before the `create_asset`-equivalent call (analogous to Uniswap deploying "Router 2" with a changed function signature at the same conceptual slot).
3. The hardcoded `[53, 0]` byte pair no longer points at `create_foreign_asset`; it now points at pallet 53's *new* call 0 (or a different pallet entirely, if pallet indices shifted).
4. `Transact` on BridgeHub still succeeds in queueing/executing the SCALE-decoded call (as long as argument shapes coincidentally match), but on AssetHub it either fails to decode (denial of Snowbridge asset registration — mirroring the "calls rejected" impact) or invokes the wrong dispatchable with the caller-derived sovereign origin, silently corrupting AssetHub state instead of registering/backing the intended foreign asset — with no code path in this repository detecting or preventing the mismatch.
