### Title
Fixed `deploy_contract` action fee does not scale with worst-case `prepare_v3` validation/instrumentation cost on malformed near-limit contracts, allowing gas-underpriced CPU work in the apply path - ([File: `runtime/near-vm-runner/src/prepare/prepare_v3.rs`], [File: `runtime/runtime/src/actions.rs`])

### Summary
`action_deploy_contract` synchronously runs `precompile_contract_with_warming` → `prepare_contract`/`prepare_v3` on every `DeployContract` action during block application, but only charges the fixed `deploy_contract_base`/`deploy_contract_byte` fee, and it discards the compile/prepare result entirely. An attacker can craft wasm that is packed to the edge of `LimitConfig` caps (functions, locals, blocks, params, operand-stack bytes) so that the expensive `finite_wasm_6::Analysis` and `InstrumentContext` passes run over the *entire* near-`max_contract_size` module before failing at the very last check (e.g. `TooManyBlocksPerContract`/`InstrumentedCodeTooLarge`), while paying the same fee as a trivial or successfully-compiled contract of the same byte size.

### Finding Description
`action_deploy_contract` (`runtime/runtime/src/actions.rs:274-312`) calls `precompile_contract_with_warming`, which synchronously invokes `precompile_contract(code, current_config, cache)` on the apply thread and drops its result (`let _ = precompile_contract(...)`, `runtime/runtime/src/cache_warming.rs:66-78`). This means:
- The `DeployContract` action always succeeds regardless of whether the wasm passes `prepare_v3`.
- The CPU cost of `prepare_contract`/`prepare_v3` (`runtime/near-vm-runner/src/prepare/prepare_v3.rs:402-462`) is incurred in the block-apply hot path even when it ultimately returns a `PrepareError`.

`prepare_v3::prepare_contract` performs early section-by-section checks (functions/locals/tables/types decremented against `LimitConfig`, `runtime/near-vm-runner/src/prepare/prepare_v3.rs:82-125`, `308-338`), but the more expensive checks — `TooManyBlocksPerFunction/Contract`, `TooManyParamsPerFunction/Contract`, `OperandStackTooLarge`, `InstrumentedCodeTooLarge` — are only detected *after* a full `finite_wasm_6::Analysis::analyze` and `InstrumentContext::run` pass over the whole module (`prepare_v3.rs:408-461`). A contract can be built to pass every early per-section limit while maximizing total instrumentation work (many functions each near local/param limits, deeply structured blocks) up to `max_contract_size`, and only fail on the final check.

The `deploy_contract_base`/`deploy_contract_byte` fees are derived from the estimator using dummy/representative contracts, not adversarial near-limit inputs — the estimator source itself documents this gap: `runtime/runtime-params-estimator/src/action_costs.rs:400-406` states "This is not the best estimation because a dummy contract is clearly not the worst-case scenario for gas costs," and `deploy_contract_byte_send_sir/not_sir` is calibrated from `ActionSize::Max.deploy_contract()` with only a fixed `min_gas` floor (`action_costs.rs:408-430`). Similarly, `compute_compile_cost_vm`/`precompilation_cost` (`runtime/runtime-params-estimator/src/vm_estimator.rs:66-134`) calibrates the compile-cost linear model from `REAL_CONTRACTS_SAMPLE`, i.e. legitimate contracts, not adversarial malformed near-limit ones, applying only a 5/4 safety multiplier.

Because the precompile result is discarded, there is no code path that ever charges gas proportional to the actual `prepare_v3` CPU time when the contract fails preparation; only the fixed action fee (scaling linearly with raw byte count, not with function/local/block complexity near the caps) is charged.

### Impact Explanation
This is a Metering-totality violation: an attacker-controlled `DeployContract` transaction can force the validator/chunk-producer's apply step to spend CPU time proportional to worst-case `prepare_v3` validation+instrumentation over a near-`max_contract_size` payload, while being billed the standard linear byte fee calibrated on non-adversarial samples. Repeated across many receipts/blocks (each with a distinct wasm blob to avoid the compiled-contract cache, since `ContractCacheKey` is keyed by code hash), this inflates block-application time relative to the gas actually burned, a resource-exhaustion/DoS class impact (block application time blowup) rather than a direct fund-loss or consensus-divergence bug. It does not by itself cause loss of funds, double-spend, or state-root divergence.

### Likelihood Explanation
The attacker only needs to be an ordinary funded account issuing normal `DeployContract` transactions with self-crafted wasm bytecode close to `LimitConfig`'s advertised caps (`max_functions_number_per_contract`, `max_locals_per_contract`, `max_blocks_per_function`/`_contract`, `max_operand_stack_bytes_per_function`, `max_contract_size`) — no special privileges, keys, or protocol knowledge are required, and this is fully within "unprivileged attacker" scope. The magnitude of the actual CPU-cost-vs-fee gap, however, is not empirically demonstrated here (no benchmark data available in this analysis) — the finding rests on the acknowledged calibration gap in the estimator code and the fact that failure is detected only after full analysis/instrumentation, not on a measured multiplier.

### Recommendation
- Charge the `prepare_contract`/`precompile_contract` cost (or a fee that scales with the actual analysis/instrumentation work, e.g. proportional to function/block/local counts, not just raw bytes) *before* running preparation, and fail the action if the caller hasn't attached enough gas — mirroring the `add_contract_loading_fee` pre-charge pattern already used for the FunctionCall load path (`gas_counter.rs:224-255`).
- Do not discard the `precompile_contract` result in `precompile_contract_with_warming`/`action_deploy_contract`; propagate `PrepareError`/`CompilationError` as an action failure so malformed deploys don't pay for and retain broken contract state.
- Recalibrate `deploy_contract_byte`/`deploy_contract_base` (and the compile-cost regression in `runtime-params-estimator`) using adversarial near-limit-cap wasm inputs in addition to `REAL_CONTRACTS_SAMPLE`, so the linear model bounds true worst-case CPU cost.

### Proof of Concept
Integration/apply-path test plan (analogous to `integration-tests/src/tests/features/fix_contract_loading_cost.rs::preparation_error_gas_cost`):
1. Generate a family of synthetic wasm modules sized near `max_contract_size`, each packed to the edge of `max_functions_number_per_contract`/`max_locals_per_contract`/`max_blocks_per_function`/`max_operand_stack_bytes_per_function`, but deliberately violating exactly one late-checked limit (e.g. `max_instrumented_code_size` or `TooManyBlocksPerContract`) so `prepare_v3` runs the full analysis+instrumentation pass before failing.
2. Submit a batch of `DeployContract` transactions (each with a distinct such module, to defeat the on-disk/in-memory compile cache) through `env.call_main`/apply-path test harness, wall-clock/instrument the time spent inside `action_deploy_contract`/`precompile_contract_with_warming`.
3. Compare against a control batch of equally-sized, but trivially-valid, minimal-structure contracts (same byte length) deployed the same way.
4. Assert that: (a) `gas_burnt` for both batches (dominated by `deploy_contract_base`+`deploy_contract_byte * len`) is nearly identical, while (b) measured CPU/wall time for the crafted near-limit-failing batch is significantly higher (order-of-magnitude) than for the control batch — demonstrating gas charged does not scale with actual preparation CPU cost on the failure path.
