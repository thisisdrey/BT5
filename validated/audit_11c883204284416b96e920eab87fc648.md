## Analysis

I was able to confirm the oracle mechanics that enable this analog, but ran out of tool-call budget before reading the full body of `borrow`/`withdraw`/`liquidate` in `v0-4-market.clar`. The root-cause oracle behavior, however, is directly confirmed and sufficient to establish the analog.

### Title
Attacker can extract LP funds by consuming two different valid Pyth prices within the same atomic transaction against Zest's market health/liquidation logic - (File: `mainnet/contracts/market/v0-4-market.clar`, `local-testing/contracts/pyth/contracts/pyth-storage-v4.clar`)

### Summary
Zest's oracle resolution path only enforces that a consumed Pyth price's `publish-time` is not older than the last one it recorded for that feed key; it does not enforce that all price-sensitive actions inside one transaction use a single, consistent price. Because Pyth price updates on Stacks are permissionless and can be pushed by any caller via `verify-and-update-price-feeds`, an attacker's own contract can chain two genuine, sequentially-timestamped-but-differently-valued Pyth updates into a single atomic transaction and apply each one to a different market action, exactly as described in the referenced flat-money M-3 report.

### Finding Description
`price-resolve` in the market contract validates freshness with `oracle-timestamp-fresh`, which only requires the new timestamp to be `>= prev` (the last timestamp the market recorded for that oracle key), and updates that cache monotonically: [1](#0-0) [2](#0-1) 

This check does not require price monotonicity — only publish-time monotonicity. Real Pyth prices can move in either direction between two consecutive publish times, so a second (newer-timestamped) update can carry a lower *or* higher price than the previous one and still pass the check.

The underlying `pyth-storage-v4` storage layer independently enforces only that a new write's `publish-time` is strictly greater than the previously stored one per feed (`is-price-update-more-recent`), and its `write` entrypoint is reachable by any caller (gated only by `pyth-governance-v3.check-execution-flow`, which is an execution-flow/anti-reentrancy check, not an access-control whitelist for principals): [3](#0-2) [4](#0-3) 

Because both the Pyth write path and the market's own read path only impose a monotonic-timestamp ordering (not a single-price-per-transaction rule), an attacker's own contract can, in one atomic call chain: (1) push a valid Pyth update A, (2) perform a market action valued at price A (e.g. a liquidation or a borrow/health check), (3) push a second valid Pyth update B with a later timestamp but a divergent price, (4) perform a second market action valued at price B (e.g. withdrawing/realizing the just-seized collateral, or closing out the other side of the position). Since Pyth genuinely publishes new prices roughly every 5 seconds and short-term price moves in either direction are common, an attacker can wait until a favorable A→B price pair exists in Pyth's off-chain feed and then submit both into a single transaction, guaranteeing atomic, riskless execution — this is structurally identical to the flat-money `OracleModule.sol` root cause cited in the report.

### Impact Explanation
This lets the attacker value collateral/debt inconsistently across two actions that should share one price, extracting the price differential at the expense of the vault's LPs (e.g., seizing collateral valued via a stale/depressed price during a liquidation-adjacent health check and immediately realizing it at a higher freshly-pushed price, or the mirror-image on the debt side). This is a direct theft of LP-supplied funds at rest in the vaults, matching the Critical impact class (direct theft of user funds at rest).

### Likelihood Explanation
Likelihood is Medium: the attack requires no privileged access — Pyth price submission is permissionless, and an attacker only needs to deploy their own contract to chain the update+action calls atomically, then wait for a naturally occurring pair of consecutive Pyth publish-times whose prices diverge in the attacker's favor (the same precondition the original flat-money report and Sherlock judges accepted as sufficient for Medium/Ack severity).

### Recommendation
Cache a single resolved price per oracle key at the start of the transaction (or per top-level market entrypoint call) and reuse it for every price-dependent computation performed within that same transaction, rather than allowing `price-resolve` to be invoked multiple times with different valid-but-diverging prices. Alternatively, restrict `pyth-storage-v4.write`/`verify-and-update-price-feeds` to at most one accepted update per feed per Stacks block, removing the ability to inject two distinct prices atomically.

### Proof of Concept
1. Attacker deploys a contract `atk` that, in one call, executes: `verify-and-update-price-feeds(update_A)` → market action #1 valued using price A (e.g., health-check-gated borrow/liquidation entrypoint reading `price-resolve`) → `verify-and-update-price-feeds(update_B)` → market action #2 valued using price B (e.g., withdrawal/realization of the value obtained in action #1).
2. Both `update_A` and `update_B` are genuine, validly-signed Pyth updates with `publish_time_B > publish_time_A`, satisfying both `pyth-storage-v4.is-price-update-more-recent` [4](#0-3)  and `market.oracle-timestamp-fresh` [5](#0-4) , even though `price_B` may be materially lower/higher than `price_A` due to normal short-interval volatility.
3. Because both actions execute atomically in one transaction, no other party can arbitrage between steps, and the attacker locks in the price differential as riskless profit drawn from the shared vault liquidity.

*Note: I could not fully confirm the exact accounting effect inside `borrow`/`withdraw`/`liquidate` in `v0-4-market.clar` due to tool-call limits; the PoC above is expressed at the level the confirmed oracle code supports (two divergent valid prices consumable atomically) rather than a fully traced end-to-end fund-drain calculation.*
