### Title
Underwater positions become permanently unliquidatable once remaining debt falls below `debtFloorInUsd`, stranding bad debt and locked collateral - (File: contracts/Pool.sol)

### Summary
The Symmio issue describes liquidations failing to be performed (and bad debt lingering) because the liquidator's fee collapses to zero for deeply insolvent accounts. The analogous Metronome surface is `Pool.liquidate` in `contracts/Pool.sol`. Metronome's liquidator incentive itself never zeroes out — `quoteLiquidateOut` always pays `repay * (1 + liquidatorIncentive)` from seized collateral — but the combination of the `maxLiquidable` close-factor bound and the `debtFloorInUsd` check creates a liveness failure with the same effect: once an underwater position's residual debt drops into the `(0, debtFloorInUsd)` band, **every** possible `amountToRepay_` reverts, so the position's bad debt and its remaining collateral are stranded permanently.

### Finding Description
`Pool.liquidate` enforces two bounds on `amountToRepay_`:

1. `amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable` reverts with `AmountGreaterThanMaxLiquidable` (close-factor cap) — `contracts/Pool.sol:567-569`.
2. If `debtFloorInUsd > 0`, a post-liquidation debt strictly between `0` and `debtFloorInUsd` reverts with `RemainingDebtIsLowerThanTheFloor` — `contracts/Pool.sol:571-579`.
3. `_totalSeized > depositToken_.balanceOf(account_)` reverts with `AmountIsTooHigh` — `contracts/Pool.sol:583-585`.

For a deteriorating position, successive partial liquidations keep halving the debt (each allowed repay ≤ `maxLiquidable` fraction). Eventually the remaining debt `D` satisfies `D < debtFloorInUsd / (1 - 0)` such that:

- Any `amountToRepay_ < D` leaves `_newDebtInUsd ∈ (0, debtFloorInUsd)` → `RemainingDebtIsLowerThanTheFloor`.
- `amountToRepay_ == D` (full close) either violates `maxLiquidable` (when `maxLiquidable < 1e18`) → `AmountGreaterThanMaxLiquidable`, or, when `maxLiquidable == 1e18`, requires seizing `D * (1 + liquidatorIncentive + protocolFee)` worth of collateral, which exceeds the remaining `balanceOf` for an underwater account → `AmountIsTooHigh`.
- `amountToRepay_ == 0` → `AmountIsZero` (`contracts/Pool.sol:553`).

All branches revert: the account can never be liquidated again. Additionally, while `debt > 0`, `DepositToken.unlockedBalanceOf` returns 0 whenever `_issuableInUsd == 0` (`contracts/DepositToken.sol:383-398`), so the victim's leftover collateral is also permanently locked — `withdraw`/`transfer` hit `_revertIfLocked` → `NotEnoughFreeBalance` (`contracts/DepositToken.sol:180-182`).

Broken invariant: liquidation liveness / solvency — interest-accruing debt (`DebtToken.accrueInterest`) remains outstanding with no possible repayment path, and seized-able collateral remains escrowed.

### Impact Explanation
- Permanent bad debt: residual `DebtToken` balances accrue interest forever with no seizable collateral covering them, leaving circulating synthetic assets partially unbacked (protocol insolvency grows with accrued interest).
- Permanent freezing of user funds: the liquidated account's remaining deposit-token balance is locked (`unlockedBalanceOf == 0`) and can never be withdrawn or seized.
- Same end state as the Symmio finding: rational liquidators have no viable call — not because the fee is zero, but because the function reverts for all inputs once the position decays past the floor.

### Likelihood Explanation
Requires `debtFloorInUsd > 0` (a supported protocol feature designed to avoid dust debt) and a position that becomes underwater via normal oracle price movement — no privileged role, oracle manipulation, or governance action needed at attack time. A position approaching the collateral-shortfall boundary is guaranteed to enter the dead zone: each successful partial liquidation reduces debt by at most `maxLiquidable`, geometrically converging into the `(0, debtFloorInUsd)` band where the function always reverts. Attacker-controlled accounts can also deliberately park positions in this state.

### Recommendation
Allow full-close liquidations that bypass both bounds when partial repayment is impossible — e.g., skip the `RemainingDebtIsLowerThanTheFloor` check when `amountToRepay_ == _debtTokenBalance` is the only viable path, and/or cap `_totalSeized` at `depositToken_.balanceOf(account_)` (liquidate-all-for-remaining-collateral) so residual debt can be cleared rather than stranded.

### Proof of Concept
Hardhat-style reproduction against the existing test harness (`test/Pool.test.ts` liquidation fixtures):

```ts
// Setup: alice deposits MET, mints msETH up to issuable limit.
// feeProvider has liquidatorIncentive > 0, protocolLiquidationFee >= 0.
await pool.updateMaxLiquidable(parseEther('0.5'));      // 50% close factor
await pool.updateDebtFloorInUsd(parseEther('100'));   // $100 floor

// Crash MET price so alice is deeply underwater.
await masterOracle.updatePrice(met.address, crashedMetPrice);

// Repeated partial liquidations halve the debt each round.
for (let i = 0; i < N; i++) {
  const debt = await msEthDebtToken.balanceOf(alice.address);
  const debtUsd = await masterOracle.quoteTokenToUsd(msEth.address, debt);
  if (debtUsd.lte(parseEther('200'))) break;           // next partial leaves < floor
  await pool.connect(liq).liquidate(msEth.address, alice.address, debt.div(2), msdMET.address);
}

// Now remaining debt D satisfies 0 < debtUsd(D) < debtFloorInUsd.
const residual = await msEthDebtToken.balanceOf(alice.address);
expect(residual).gt(0);

// 1) Partial repay -> RemainingDebtIsLowerThanTheFloor
await expect(
  pool.connect(liq).liquidate(msEth.address, alice.address, residual.div(2), msdMET.address)
).revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor');

// 2) Full repay -> AmountGreaterThanMaxLiquidable (or AmountIsTooHigh if underwater)
await expect(
  pool.connect(liq).liquidate(msEth.address, alice.address, residual, msdMET.address)
).revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable');

// 3) Alice's leftover collateral is locked forever
await expect(
  msdMET.connect(alice).withdraw(await msdMET.balanceOf(alice.address), alice.address)
).revertedWithCustomError(msdMET, 'NotEnoughFreeBalance');
```

All calls are public, unprivileged, and reach the named code on the deployed configuration (no shutdown, nonReentrant and existence checks pass). Uncertainty: exact `debtFloorInUsd`/`maxLiquidable` values on the deployed pools are configuration-dependent and were not verified from this index; the deadlock exists whenever `debtFloorInUsd > 0`, regardless of `maxLiquidable` (with `maxLiquidable == 1e18` the full-close path fails on `AmountIsTooHigh` for underwater accounts instead).
