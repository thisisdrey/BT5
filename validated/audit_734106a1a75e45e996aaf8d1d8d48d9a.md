### Title
Unguarded `aptos_account::deposit_coins<AptosCoin>` in `distribute()` Loop Can Permanently Freeze All Vesting Shareholders' Funds — (`aptos-move/framework/aptos-framework/sources/vesting.move`)

---

### Summary

`vesting.move`'s `distribute()` iterates over every shareholder and calls `aptos_account::deposit_coins<AptosCoin>(recipient_address, share_of_coins)` inside a single atomic transaction. `deposit_coins` contains a hard abort if the recipient has not registered for coin-based APT **and** has set `allow_arbitrary_coin_transfers = false`. Because Move transactions are fully atomic, one aborting deposit reverts the entire loop, leaving all shareholders' unlocked vested APT permanently inaccessible. The same structural defect exists in `staking_contract.move`'s `distribute_internal()`.

---

### Finding Description

**`aptos_account::deposit_coins<CoinType>` abort path** [1](#0-0) 

```move
if (!coin::is_account_registered<CoinType>(to)) {
    assert!(
        can_receive_direct_coin_transfers(to),
        error::permission_denied(EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS)
    );
    coin::register<CoinType>(&create_signer(to));
};
coin::deposit<CoinType>(to, coins)
```

`can_receive_direct_coin_transfers` returns `false` whenever the target account has explicitly called `set_allow_direct_coin_transfers(account, false)`: [2](#0-1) 

**`vesting.distribute()` — the vulnerable loop** [3](#0-2) 

```move
shareholders.for_each_ref(|shareholder| {
    ...
    let recipient_address = get_beneficiary(vesting_contract, shareholder);
    aptos_account::deposit_coins(recipient_address, share_of_coins);  // ← can abort
});
```

If `deposit_coins` aborts for **any one** shareholder, the entire transaction reverts. The coins are returned to the local variable `coins`, but the on-chain state (staking pool, distribution pool) is also reverted, so the same failing shareholder will block every future call to `distribute()`.

**`create_vesting_contract` does not validate shareholders** [4](#0-3) 

Only `withdrawal_address` is checked with `assert_account_is_registered_for_apt`. The shareholder list is accepted without any APT-registration guard.

**The developers already knew about this risk for beneficiaries** [5](#0-4) 

```move
// Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
// fail and block all other accounts from receiving APT if one beneficiary is not registered.
assert_account_is_registered_for_apt(new_beneficiary);
```

The guard exists in `set_beneficiary` but is absent from `create_vesting_contract`, leaving the initial shareholder list unprotected.

**`terminate_vesting_contract` is also blocked** [6](#0-5) 

`terminate_vesting_contract` calls `distribute(contract_address)` internally. If `distribute()` is stuck, the admin cannot terminate the contract either, and `admin_withdraw` (which requires `VESTING_POOL_TERMINATED` state) is unreachable.

**Same pattern in `staking_contract.distribute_internal()`** [7](#0-6) 

The staker address is fixed at contract creation with no APT-registration check; if the staker later has `allow_arbitrary_coin_transfers = false` and no coin-based APT store, every call to `distribute`, `unlock_stake`, `request_commission`, and `switch_operator` (all of which call `distribute_internal`) will abort.

---

### Impact Explanation

A single shareholder whose address satisfies both conditions — (1) no `CoinStore<AptosCoin>` registered and (2) `allow_arbitrary_coin_transfers = false` — causes `distribute()` to abort atomically. Because the loop is not wrapped in any per-recipient error handling, **all other shareholders' unlocked vested APT is permanently frozen** inside the vesting contract. The admin's only escape hatch is `set_beneficiary`, but that requires knowing which shareholder is the problem and having an active admin key. If the admin is unavailable or the problematic address is the admin's own, the funds are unrecoverable. This is a direct permanent freezing of user-controlled staking/vesting balances.

---

### Likelihood Explanation

The trigger condition is reachable by any unprivileged user:

- `set_allow_direct_coin_transfers(account, false)` is a public entry function callable by any account owner.
- With the ongoing APT coin-to-FA migration, accounts that only hold FA-based APT (created via `aptos_account::create_account`, which calls `ensure_primary_fungible_store_exists` rather than `coin::register<AptosCoin>`) will have `coin::is_account_registered<AptosCoin>` return `false`.
- A shareholder who is a resource account or smart contract may never have registered for coin-based APT.
- A malicious shareholder can deliberately engineer this state before the vesting contract is created, or after creation if they are also a beneficiary.

---

### Recommendation

1. **In `create_vesting_contract`**: add `assert_account_is_registered_for_apt(*shareholder)` for every entry in the `shareholders` vector, mirroring the existing check on `withdrawal_address`.
2. **In `distribute()` and `distribute_internal()`**: wrap each per-recipient `deposit_coins` call in a try-catch pattern (or use a pull-payment model) so that one failing recipient does not block all others. Move the coins for the failing recipient to a claimable escrow keyed by recipient address.
3. **In `staking_contract.create_staking_contract_with_coins`**: validate that the staker address is registered for APT before accepting funds.

---

### Proof of Concept

```
1. Alice (admin) creates a vesting contract with shareholders [Bob, Mallory].
2. Mallory calls set_allow_direct_coin_transfers(mallory, false) and never registers
   coin::CoinStore<AptosCoin> (only holds FA-based APT).
3. Time passes; stake rewards accumulate; vest() is called successfully.
4. Anyone calls distribute(contract_address).
5. The loop reaches Mallory:
     aptos_account::deposit_coins(mallory_address, share)
     → coin::is_account_registered<AptosCoin>(mallory) == false
     → can_receive_direct_coin_transfers(mallory) == false
     → ABORT: EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS
6. Entire transaction reverts. Bob's share is not delivered.
7. Every subsequent call to distribute() hits the same abort.
8. terminate_vesting_contract() also calls distribute() internally → also aborts.
9. admin_withdraw() requires VESTING_POOL_TERMINATED state → unreachable.
10. Bob's vested APT is permanently frozen in the contract.
```
