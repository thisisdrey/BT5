### Title
Scope Escalation via Active Permission Delegation of AccountPermissionUpdateContract - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator.checkPermission()` validates a permission's `operations` bitmap against `DynamicPropertiesStore.getAvailableContractType()` — the set of *all currently enabled* contract types on the network — rather than against a restricted set that excludes account-authority-management contracts. Because `AccountPermissionUpdateContract` is a member of `getAvailableContractType()`, it can be legally embedded into the `operations` bitmap of a non-owner, scope-limited `Active` permission. Any address holding only that `Active` permission can then broadcast a new `AccountPermissionUpdateContract` transaction — signed solely under its own limited `permissionId` — and use it to overwrite the account's `Owner` permission (and any other `Active`/`Witness` permission), inserting its own key with full weight/threshold. This mirrors the Capgo flaw where a scope-limited credential is used to mint a broader, unrestricted credential, because the system enforces "is this contract type in the enabled set" instead of "is this operation forbidden from ever being delegated to a sub-owner permission."

### Finding Description
Signature/permission enforcement for any transaction is done in `TransactionCapsule.checkPermission()` / `validateSignature()`: if the contract carries a non-zero `permissionId`, the code only requires that the referenced permission be of type `Active` and that the specific `ContractType` bit is set in that permission's `operations` bytes [1](#0-0) [2](#0-1) .

When an `AccountPermissionUpdateContract` is itself submitted, `AccountPermissionUpdateActuator.checkPermission()` validates each proposed permission's `operations` bitmap only against `dynamicStore.getAvailableContractType()`, i.e. whichever contract types are currently network-enabled, with no special-case exclusion of `AccountPermissionUpdateContract` from what a non-owner `Active` permission may be granted: [3](#0-2) 

The account's own test suite documents that `getAvailableContractType()` includes `AccountPermissionUpdateContract`, while only the *default* `Active` permission generated at account creation (`getActiveDefaultOperations()`) intentionally excludes it: [4](#0-3) 

The actual permission‑bitmap default for a newly created account's `Active` permission is populated from `getActiveDefaultOperations()` (which excludes `AccountPermissionUpdateContract`) via `createDefaultActivePermission`: [5](#0-4) 

However, this exclusion is only a *default*; nothing in `checkPermission()` of the actuator prevents an `AccountPermissionUpdateContract` being legally added later to an `Active` permission's operations, because the validate-time check only consults the broader `getAvailableContractType()` bitmap, not a "may-never-be-delegated" restricted list. Once any active key is authorized for this operation type (whether granted deliberately by a careless owner, inherited from a compromised co-signer permission, or via a future contract type where the exclusion set is not correctly updated — see the parallel `checkAvailableContractTypeCorrespondingToCode` vs `checkActiveDefaultOperations` test divergence in the same file, which shows the two bitmaps are maintained by hand and can drift), that Active-only signer can call `AccountPermissionUpdateActuator.execute()` which unconditionally applies `account.updatePermissions(owner, witness, actives)` — replacing the `Owner` permission wholesale with attacker-supplied keys/threshold, with no re-check that the signer used owner-level authority to make that specific change: [6](#0-5) 

The `validate()` method enforces structural correctness of the new `Owner`/`Witness`/`Active` permissions (key counts, weights, thresholds) but performs no check correlating the transaction's signing `permissionId` to whether that signer is entitled to *also* redefine the `Owner` permission itself: [7](#0-6) 

### Impact Explanation
Any address that ends up holding an `Active` permission whose `operations` bitmap includes the `AccountPermissionUpdateContract` bit gains the practical equivalent of full `Owner` authority over the account: it can rewrite the `Owner` permission to add itself with sufficient weight/threshold, permanently locking out or diluting the legitimate owner, and can subsequently authorize arbitrary transfers, freezes, votes, or smart-contract actions under the compromised account. This is a full unauthorized account takeover / permanent loss-of-control primitive, matching the CVSS 9.0 "unrestricted key from scope-limited credential" class in the Capgo advisory.

### Likelihood Explanation
Exploitation requires that some `Active` permission on the target account already (or can be made to) include the `AccountPermissionUpdateContract` operation bit — which is legal per `checkPermission()`'s validation against `getAvailableContractType()`. This can happen through owner misconfiguration (a single confusing multisig setup mistake, since the UI/API surfaces `operations` as a raw 256-bit hex string), through compromise of a co-signer whose active permission was over-provisioned, or through inconsistency between the maintained "available" vs "default active" bitmaps as new `ContractType`s are added (evidenced by the two separately hand-maintained test constants in `AccountPermissionUpdateActuatorTest`). Given TRON's widespread use of multisig for custodial/exchange wallets, misconfigured over-broad `Active` operations bitmaps are a realistic and previously-seen class of operator error.

### Recommendation
In `AccountPermissionUpdateActuator.checkPermission()`, explicitly forbid `AccountPermissionUpdateContract` (and any other permission-management contract types) from ever being set in a non-owner `Active` permission's `operations` bitmap, regardless of `getAvailableContractType()`. Additionally, in `validate()`/`execute()`, require that a transaction which modifies the `Owner` permission itself must have been signed using `permissionId == 0` (true owner authority), independent of what the submitted `Active` permission's operations bitmap claims to allow.

### Proof of Concept
1. Owner account `A` configures (or is tricked/defaulted into configuring, or inherits from a template) an `Active` permission `P2` whose 32-byte `operations` field has the bit for `AccountPermissionUpdateContract` set — this passes `checkPermission()` validation since the type is present in `getAvailableContractType()`.
2. The holder of the key referenced in `P2` crafts an `AccountPermissionUpdateContract` transaction with `permissionId = 2` (referring to `P2`), setting the `owner` field to a new `Permission` containing the attacker's own address with weight ≥ threshold.
3. `TransactionCapsule.checkPermission()` accepts the signature because `permissionId != 0` only requires `Permission.getType() == Active` and the `AccountPermissionUpdateContract` bit set in `P2.operations` — both satisfied.
4. `AccountPermissionUpdateActuator.execute()` calls `account.updatePermissions(newOwner, witness, actives)`, overwriting `A`'s `Owner` permission with the attacker-controlled one.
5. The attacker now controls account `A` at owner level, despite having started with only a scope-limited `Active` key.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
  }
