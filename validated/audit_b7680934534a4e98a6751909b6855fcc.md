### Title
Missing sanity-check on `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` chain parameters in governance re-parameterization - (File: actuator/src/main/java/org/tron/core/utils/ProposalUtil.java)

### Summary
`ProposalUtil.validator()` is the sanity-check gate that every `ProposalCreateContract` must pass before a witness-voted parameter change (`ProposalService.process`) can update `DynamicPropertiesStore`. Unlike almost every other numeric parameter in this switch statement, `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` fall through with no range/threshold validation at all, mirroring exactly the bug class described in the report (`resolveReparam`-style re-parameterization with no invariant checks on critical economic parameters such as fees/costs).

### Finding Description
`ProposalUtil.validator` validates each proposed `(param, value)` pair before it is allowed onto the network's parameter-change pipeline (`ProposalCreateActuator.validate()` → `validateValue()` → `ProposalUtil.validator()`). Nearly every fee-like parameter (`ACCOUNT_UPGRADE_COST`, `CREATE_ACCOUNT_FEE`, `TRANSACTION_FEE`, `ASSET_ISSUE_FEE`, `WITNESS_PAY_PER_BLOCK`, `MARKET_SELL_FEE`, `MARKET_CANCEL_FEE`, `MEMO_FEE`, `UPDATE_ACCOUNT_PERMISSION_FEE`, `MULTI_SIGN_FEE`, etc.) is bound-checked with an explicit `[0, LONG_VALUE]` or similar range: [1](#0-0) 

However, `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` are handled by a bare `break;` with no validation whatsoever: [2](#0-1) 

Once a proposal for these codes collects enough witness approvals, `ProposalController.processProposal` calls `setDynamicParameters` → `ProposalService.process`, which unconditionally writes the raw, unchecked `long` value into the store: [3](#0-2) [4](#0-3) 

Because there is no lower/upper bound (and no `value < 0` check), `ENERGY_FEE` — the per-unit-energy conversion rate used across the TVM energy metering/receipt path (referenced in `Wallet.java`, `ReceiptCapsule.java`, `VMActuator.java`, `TronJsonRpcImpl.java`) — can be set to `0` or to a negative value, and `EXCHANGE_CREATE_FEE` — the TRX fee charged by `ExchangeCreateActuator` when creating a Bancor-style exchange pair — can likewise be set to `0` or negative.

### Impact Explanation
`ENERGY_FEE` directly determines how much TRX is burned per unit of energy consumed by smart-contract execution (see its usages in `ReceiptCapsule`/`VMActuator`/`Wallet`). If a witness majority (a reachable, in-scope actor via signed `ProposalCreateContract` + normal witness-vote/maintenance-cycle processing — not a "malicious SR" collusion scenario but the intended, permissionless proposal mechanism) sets `ENERGY_FEE` to `0`, TVM contract calls become effectively energy-free for any caller who owns/delegates enough frozen energy resources, letting them execute unlimited contract logic without burning TRX — an unbacked-resource/economic exploit and a node-level DoS vector (unbounded free CPU/energy consumption). A negative value would corrupt the fee arithmetic used when computing account balance deductions in receipt/fee computation, potentially crediting balance instead of debiting it (unauthorized balance manipulation). Similarly, an unchecked `EXCHANGE_CREATE_FEE` set to `0` or negative removes/inverts the TRX cost of `ExchangeCreateActuator`, letting any account create bancor exchanges for free or even profit, undermining the intended market-creation economics — directly analogous to the report's Scenario 2 (manipulating market parameters like `price_floor`/`list_reward` for economic gain).

### Likelihood Explanation
This requires the standard, in-scope proposal/vote governance flow (`ProposalCreateActuator` + witness approval processed by `ProposalController`), which is the exact "re-parameterization via voting" mechanism the report warns about. No fork/version gate, no extra guard, and no prerequisite proposal is required for these two parameter codes — this is the same class of "critical parameter changeable without sanity check" flaw called out in the report as Medium-difficulty. The absence of validation is a plain code-inspection fact; the only work required to trigger it is achieving the votes any other successful parameter proposal already requires.

### Recommendation
Add explicit range validation for `ENERGY_FEE` and `EXCHANGE_CREATE_FEE` in `ProposalUtil.validator` consistent with sibling fee parameters, e.g. `value` must be within `[0, LONG_VALUE]` (or a tighter, economically-sound bound), rejecting negative and zero values if zero is not a legitimate operating point. More broadly, audit every `ProposalType` case for a matching bound check, since the pattern shows most parameters are already protected — these two are outliers.

### Proof of Concept
1. An account submits a `ProposalCreateContract` with `parameters = {ENERGY_FEE: 0}` (or a negative long) via the normal transaction broadcast path.
2. `ProposalCreateActuator.validate()` calls `validateValue()` → `ProposalUtil.validator()`, which hits the `case ENERGY_FEE: ... break;` branch with no check, so validation passes: [5](#0-4) 
3. Once the proposal accumulates the required witness approvals, `ProposalController.processProposal` invokes `ProposalService.process`, which stores `0`/negative directly via `saveEnergyFee(entry.getValue())`: [6](#0-5) 
4. From the next maintenance cycle onward, all TVM contract calls are charged energy at the new (zero/negative) rate, giving callers free or balance-crediting contract execution.
