### Title
Slowloris DoS via Missing ReadHeaderTimeout on Prometheus Stats HTTP Listener - (File: stats.go)

### Summary
The Nebula `statsServer` exposes an optional Prometheus metrics HTTP endpoint whose `http.Server` is constructed without `ReadHeaderTimeout` (or `ReadTimeout`), leaving it exposed to a Slowloris-style resource-exhaustion attack, exactly the bug class described in the external report for `http_server.go`.

### Finding Description
When `stats.type` is set to `"prometheus"`, `buildRuntime` constructs the listener as: [1](#0-0) 
```go
mux := http.NewServeMux()
mux.Handle(cfg.prom.path, promhttp.HandlerFor(pr, promhttp.HandlerOpts{ErrorLog: errLog}))
return captureFns, &http.Server{Addr: cfg.prom.listen, Handler: mux}
```
This `http.Server` has no `ReadHeaderTimeout`, `ReadTimeout`, or `WriteTimeout` set anywhere in the codebase. It is then served directly via `ListenAndServe` in `serveListener`: [2](#0-1) 
The listen address (`cfg.prom.listen`, sourced from the `stats.listen` config key) is admin-configurable and, if bound to a non-loopback interface, is reachable over the network without any TLS/certificate requirement — this is a plain HTTP endpoint separate from Nebula's certificate-authenticated tunnel, so no CA-signed certificate is needed to reach it. [3](#0-2) 
Because Go's default `http.Server` has no header read deadline unless explicitly configured, an attacker can open many TCP connections and send HTTP headers at a trickle (or not at all), holding each connection — and the goroutine/file descriptor backing it — open indefinitely.

### Impact Explanation
An attacker who can reach the configured `stats.listen` address can open large numbers of slow/incomplete connections, exhausting file descriptors and goroutines on the node's stats listener. Since the stats HTTP server shares the same process as the core Nebula tunnel, resource exhaustion here can degrade or crash the entire node process, resulting in a remote, unauthenticated Denial of Service.

### Likelihood Explanation
The listener is only present when `stats.type: prometheus` is configured, and exploitability depends on it being bound to an attacker-reachable address rather than `127.0.0.1`. This is a common operational pattern for centralized metrics scraping across a fleet, so exposure to non-loopback interfaces is plausible. No authentication or certificate is required to open connections against it, matching the same "no CA-signed certificate needed" reachability class as the original finding.

### Recommendation
Set `ReadHeaderTimeout` (and ideally `ReadTimeout`/`WriteTimeout`, `IdleTimeout`) on the `http.Server` built in `buildRuntime`:
```go
return captureFns, &http.Server{
    Addr:              cfg.prom.listen,
    Handler:           mux,
    ReadHeaderTimeout: 5 * time.Second,
}
```

### Proof of Concept
1. Configure Nebula with:
```yaml
stats:
  type: prometheus
  interval: 10s
  listen: 0.0.0.0:8080
  path: /metrics
```
2. From an external host, open many TCP connections to `<node_ip>:8080` and send HTTP request headers extremely slowly (one byte every few seconds, e.g. via a Slowloris tool) or not at all after the initial `GET /metrics` line.
3. Because no `ReadHeaderTimeout` is configured, the server keeps each connection open indefinitely, tying up a goroutine per connection.
4. Repeat until the process runs out of file descriptors/goroutines, causing the stats endpoint (and potentially the whole node process, since it shares the same runtime) to become unresponsive — a remote DoS requiring no certificate or authentication.
