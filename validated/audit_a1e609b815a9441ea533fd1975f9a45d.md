## Analysis Result

### Title
Exchange actuators ignore the boolean result of `reduceAssetAmountV2`, allowing exchange pool balances to be credited without a matching debit — ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` mutate the on-chain `ExchangeCapsule` pool balances (crediting tokens into the AMM pool / crediting the trader with the "other" token) and then attempt to debit the trader's real asset balance via `AccountCapsule.reduceAssetAmountV2(...)`, but the boolean success/failure return value of that call is never checked. This is the same bug class as the Kraken incident described in the report: a balance-crediting step is allowed to complete even when the corresponding debit/verification step silently fails, producing an unbacked balance increase.

### Finding Description
In `ExchangeInjectActuator.execute()`, the exchange pool balances are updated first via `exchangeCapsule.setBalance(...)`, and only afterward is the owner's asset debited: [1](#0-0) 

Note that when the injected token is not TRX, the debit path is:
```java
accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
```
with no check on the return value, unlike `TransferAssetActuator.execute()`, which treats the very same method's return value as authoritative and aborts the transaction if it is `false`: [2](#0-1) 

The same unchecked pattern exists in `ExchangeTransactionActuator.execute()`, where the token being sold is reduced via `reduceAssetAmountV2` with no check, while the pool state (`exchangeCapsule.transaction(...)`) and the "another token" credit to the trader (`addAssetAmountV2`) have already been computed/applied: [3](#0-2) 

Because `reduceAssetAmountV2`'s result is discarded in these three actuators, any path where the actual debit method disagrees with the validate-phase check (`assetBalanceEnoughV2`, called only during `validate()`) — e.g. due to precision conversion, `AllowSameTokenName`/V1-V2 store migration edge cases, or any other divergence between the two independent code paths — results in the exchange pool balance or the trader's other-token balance being permanently inflated while the debited asset was never actually removed. This mirrors the Kraken class of bug: a crediting operation (deposit/exchange balance increase) that is allowed to finalize independently of whether the matching debit actually succeeded.

### Impact Explanation
If `reduceAssetAmountV2` fails silently for any input that `validate()`'s `assetBalanceEnoughV2` did not reject, an attacker can:
- Inflate an `ExchangeV2Store` pool's token balances (`ExchangeInjectActuator`) without actually transferring the injected tokens out of their account, creating unbacked liquidity that can subsequently be withdrawn by any party via `ExchangeWithdrawActuator`.
- Receive the "another token" amount from a trade (`ExchangeTransactionActuator`) while their sold token balance is not actually decremented, effectively minting value out of the exchange pool.

Both outcomes are direct, unbacked-balance / theft-of-funds equivalents reachable by any account issuing a single signed `ExchangeInjectContract` or `ExchangeTransactionContract` transaction — no privileged role required.

### Likelihood Explanation
Medium. Exploitation requires a concrete state where `assetBalanceEnoughV2` (validate-time check) and `reduceAssetAmountV2` (execute-time debit) disagree. I was not able to fully trace both implementations to confirm such a divergence exists in the current codebase within the available search budget — `Commons.java`/`AccountCapsule.java`'s `assetBalanceEnoughV2` implementation and the exact internals of `reduceAssetAmountV2` were not fully reviewed. The structural weakness (an unchecked return value on a method whose sibling call site in `TransferAssetActuator` explicitly treats failure as fatal) is confirmed, but a fully worked, end-to-end proof-of-concept input that reliably triggers the divergence was not established with certainty.

### Recommendation
Check the return value of `reduceAssetAmountV2` in `ExchangeInjectActuator.execute()` and `ExchangeTransactionActuator.execute()` (and similarly for `addAssetAmountV2` failure modes), throwing `ContractExeException` and aborting the state mutation if the debit does not succeed — mirroring the pattern already used in `TransferAssetActuator`. Additionally, unify the balance-sufficiency check used in `validate()` with the actual debit logic in `execute()` to eliminate any possible divergence (TOCTOU) between the two.

### Proof of Concept
Not fully constructable from static analysis alone: I could not confirm, from the retrieved code, a concrete input where `assetBalanceEnoughV2` (validate) and `reduceAssetAmountV2` (execute) diverge on the current codebase. This finding is submitted on the strength of the confirmed structural defect (unchecked return value contradicting the safe pattern established elsewhere in the same actuator family) rather than a verified working exploit chain. A background engineer with full repository/test access should attempt to reproduce a divergence (e.g., testing `AllowSameTokenName` migration boundaries, V1↔V2 asset store transitions, or precision/decimal edge cases around token IDs) to confirm exploitability before treating this as fully proven.
