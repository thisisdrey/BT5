## Finding: ECDSA (secp256k1) signature malleability is not rejected for NEAR transactions

### Title
Secp256k1 transaction signature malleability (`s` not restricted to low-S range) enables transaction-hash malleability - (File: `core/crypto/src/signature.rs`)

### Summary
The reported bug class (CL-2020-12) is a BLS point-(de)compression flaw in `py_ecc` that allowed a second, different byte encoding to verify as a valid signature for the same message/key, producing a different serialized transaction (and thus a different tx hash) that still passes verification — classic signature/transaction malleability. NEAR ships an analogous, well-known malleability primitive for its `secp256k1` transaction-signer scheme: ECDSA signatures are malleable unless the `s` component is constrained to the "low-S" half of the curve order. NEAR's crypto library implements this check but the verification path used for transactions does not invoke it.

### Finding Description
`Secp256K1Signature::check_signature_values(reject_upper: bool)` exists specifically to reject the malleable "upper" range of `s` (`s >= SECP256K1_N_HALF_ONE`), with an explicit comment "Reject upper range of s values (ECDSA malleability)": [1](#0-0) 

However, the actual signature verification entry point used everywhere a transaction, delegate action, or access key signature is checked — `Signature::verify` — parses and verifies the secp256k1 signature via `secp256k1::ecdsa::RecoverableSignature`/`SECP256K1.verify_ecdsa` directly, and never calls `check_signature_values`: [2](#0-1) 

A repo-wide search confirms `check_signature_values` has exactly one definition and no call sites in `core/crypto/src/signature.rs`, `runtime/near-vm-runner/src/logic/logic.rs`, or `wasmtime_runner/logic.rs` (the matches there are unrelated documentation references), i.e., the function is effectively dead code and never gates transaction validation.

The consensus-facing transaction validity check simply calls `signed_tx.signature.verify(hash, public_key)`: [3](#0-2) 

Because `libsecp256k1`'s `verify_ecdsa` accepts both `s` and `n - s` as valid signatures for the same `(r, message, pubkey)` triple, an attacker who observes a valid `secp256k1`-signed `SignedTransaction` on the wire (e.g., in the mempool/gossip layer, or simply resubmitted by anyone since transactions are public) can flip `s -> n - s` and the recovery id, producing a **different byte encoding and therefore a different `SignedTransaction` and different `tx.get_hash()`**, while the signature still verifies against the same signer and same semantic transaction content.

### Impact Explanation
NEAR uses the transaction hash as the execution-outcome id, and (as of `UniqueChunkTransactions`) as the de-duplication key within a chunk: [4](#0-3) [5](#0-4) 

A malleated copy of a transaction has a *different* hash than the original, so it is **not** caught by the same-hash duplicate-skip logic, yet spends the same nonce and the same funds/access key. This is the classic "transaction malleability" impact: a third party can re-derive an equally-valid, differently-hashed copy of someone else's signed transaction. Consequences on NEAR specifically:
- Any code (wallets, exchanges, indexers, bridges) that tracks a transaction by its computed hash to confirm inclusion/finality can be confused if a malleated variant is included instead of (or in a race with) the original, since both are valid for the signer/access key/nonce.
- It undermines assumptions of hash-based idempotency/tracking for `secp256k1`-signed transactions (used e.g. for Ethereum-style/relayed transactions and the `near-wallet-contract`/Aurora integration, which explicitly builds and signs `secp256k1`-based transactions): [6](#0-5) 

This does not directly enable theft of funds beyond what the original signer authorized, and it doesn't cause a state-root divergence between validators (verification is deterministic and part of consensus, so all nodes agree on which malleated bytes are valid), so it stops short of a `High`-severity fund-theft/inflation bug. It is best framed as a moderate integrity/liveness issue: transaction/tx-hash malleability that can defeat hash-based tracking and duplicate-transaction protection for `secp256k1` signers.

### Likelihood Explanation
Trivial and always exploitable by any observer of a valid transaction: computing `n - s` and flipping the recovery id is pure arithmetic with public curve parameters — no private key or special access needed. Every `secp256k1`-signed `SignedTransaction` sent to the network is malleable this way, because `check_signature_values`/low-S enforcement is defined but never invoked in the verification path.

### Recommendation
Call `Secp256K1Signature::check_signature_values(true)` (reject-upper / low-S enforcement) as part of `Signature::verify` (or as a pre-check in `ValidatedTransaction::new`/`validate_transaction`) for the `SECP256K1` variant, gated behind a protocol feature to avoid breaking existing high-S signatures already in history/state. This mirrors Bitcoin/Ethereum's BIP-62/EIP-2 style low-S malleability fixes.

### Proof of Concept
Conceptual (arithmetic on public curve order, no key material needed):
1. Take any valid `SignedTransaction` signed with a `SECP256K1` access key, with signature bytes `(r, s, v)`.
2. Compute `s' = SECP256K1_N - s` (using the `SECP256K1_N` constant already defined in `core/crypto/src/signature.rs`) and the complementary recovery id `v' = 1 - v` (mod 2).
3. Construct a new `SignedTransaction` with identical `transaction` field but signature `(r, s', v')`.
4. `Signature::verify` (`core/crypto/src/signature.rs:1076-1106`) accepts `(r, s', v')` for the same message/public key because `verify_ecdsa`/point recovery treat `s` and `n-s` as equally valid.
5. Because the signature bytes differ, `SignedTransaction::get_hash()` differs from the original, producing a second valid transaction hash for the same authorized action/nonce — while `UniqueChunkTransactions`'s hash-based dedup (`runtime/runtime/src/lib.rs:2038`) only rejects an exact-hash repeat, not this malleated variant.

impl Secp256K1Signature {
    pub fn check_signature_values(&self, reject_upper: bool) -> bool {
        let mut r_bytes = [0u8; 32];
        r_bytes.copy_from_slice(&self.0[0..32]);
        let r = U256::from(r_bytes);

        let mut s_bytes = [0u8; 32];
        s_bytes.copy_from_slice(&self.0[32..64]);
        let s = U256::from(s_bytes);

        let s_check = if reject_upper {
            // Reject upper range of s values (ECDSA malleability)
            SECP256K1_N_HALF_ONE
        } else {
            SECP256K1_N
        };

        r < SECP256K1_N && s < s_check
    }

    let mut rlp_stream = rlp::RlpStream::new();
    rlp_stream.append(&aurora_engine_transactions::eip_2930::TYPE_BYTE);
    transaction.rlp_append_unsigned(&mut rlp_stream);
    let message_hash = crate::internal::keccak256(rlp_stream.as_raw());
    let signature = sk.sign(&message_hash);
    let bytes: [u8; 65] = match signature {
        Signature::SECP256K1(x) => x.into(),
        _ => panic!(),

    let v = bytes[64];
    let r = U256::from_big_endian(&bytes[0..32]);

        transaction,
        parity: v,
        r,
        s,
