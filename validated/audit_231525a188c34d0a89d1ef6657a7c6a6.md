Based on my research, I found a strong analog in java-tron's permission-ID resolution mechanism, which mirrors the reported bug's root cause: **a stable-looking identifier is actually a mutable-index-derived value that can be reassigned to a different underlying object between the time a transaction is authorized/signed and the time it is executed.**

### Title
Active permission IDs are index-derived and can be silently reassigned by `AccountPermissionUpdateContract`, causing pending multi-sig transactions to be validated against the wrong permission - (File: `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java`)

### Summary
`Permission.id` for active permissions is not a stable, caller-chosen identifier — it is derived purely from the permission's *position* in `active_permission` list at the moment `updatePermissions()` is called: `permission.toBuilder().setId(i + 2)` for `i` in `0..actives.size()-1` [1](#0-0) . A transaction carries only this integer `permission_id`, and `getPermissionById(id)` resolves it at validation time by scanning `getActivePermissionList()` for a matching `id` field [2](#0-1) . If the account owner submits a new `AccountPermissionUpdateContract` (e.g., reordering, adding, or removing an active permission) while another multi-signature transaction referencing a specific `permission_id` is still pending in the mempool, the `permission_id` embedded in that pending transaction can end up resolving to a **completely different** `Permission` (different `threshold`, `operations` bitmask, and `keys`) once the update is mined first.

### Finding Description
The vulnerable pattern is structurally identical to the reported bug: a numeric index/ID into a mutable list is captured at signing time, but the list can be mutated (reordered/shrunk) by an authorized party before the referencing transaction is minted, causing the ID to now point at a different list element with different semantics.

- Signing/weight-checking flow always re-resolves the permission by ID at validation time, not by any snapshot of the actual `Permission` object: `TransactionCapsule.validateSignature()` and `addSign()` both call `account.getPermissionById(permissionId)` fresh [3](#0-2) .
- `checkPermission()` then validates the transaction's contract type against `permission.getOperations()` of whatever permission the ID currently resolves to [4](#0-3) .
- `checkWeight()`/`getWeight()` compute signer weight against the *current* `Permission.keys`, not the keys that existed when signatures were collected.
- `Wallet.getTransactionSignWeight()` and `getTransactionApprovedList()` exhibit the same re-resolution behavior for RPC-driven multi-sig collection flows [5](#0-4) .

Because `AccountPermissionUpdateContract` is a normal, unprivileged, self-authorized transaction (the account owner acting on their own account) and pending multi-sig transactions referencing `permission_id` can sit in the mempool for a period, a race is possible: signatures collected under one permission definition (e.g. a high-threshold active permission requiring 3 co-signers) get "revalidated" and satisfied against a different permission (e.g. a newly reordered active permission with lower threshold or a broader `operations` mask) simply because both happened to occupy the same computed `id = i + 2` slot at different times.

### Impact Explanation
This can result in a previously collected set of signatures being applied to authorize an operation they were never intended to authorize — e.g., signatures gathered to satisfy a strict, high-threshold "active" permission scoped to a narrow operation set could end up satisfying a different, less restrictive permission after a permission-list reorder, allowing an under-authorized transaction (asset transfer, resource delegation, etc.) to execute. This falls under "concrete unauthorized account operation" since funds/authority movement can occur without the intended threshold of approvals actually being met for the operation performed.

### Likelihood Explanation
This requires: (1) an account using multiple active permissions with multi-sig, (2) a pending transaction referencing a specific `permission_id` sitting unconfirmed while (3) the account owner (or someone who can trigger an `AccountPermissionUpdateContract`, which only requires the Owner permission) submits a permission-list change that reorders/removes/adds active permissions before the pending transaction is packed into a block. This is a realistic sequencing scenario in busy multi-sig wallets/exchanges that rotate signer sets, but it is a narrower window than the original plugin report (which involved any `PLUGIN_EDITOR`), since here the mutation and the affected pending transaction both belong to the same account/owner. Likelihood is Medium.

### Recommendation
Do not rely solely on the mutable `permission_id` integer at execution time. Either (a) bind signatures/approvals to a content hash of the specific `Permission` (threshold, operations, keys) at signing time and re-verify that hash still matches the currently resolved `Permission` before accepting weight, or (b) invalidate/require re-signing of all pending transactions referencing a given `permission_id` whenever `AccountPermissionUpdateContract` changes that ID's underlying `Permission` contents.

### Proof of Concept
1. Account `A` sets active permissions `[P1 (id=2, threshold=3, keys={a,b,c})]` via `AccountPermissionUpdateContract` (`updatePermissions` assigns `id=2` to `P1`) [1](#0-0) .
2. A transaction `T` with `contract.permission_id = 2` is signed by keys `a` and `b` (weight below threshold 3) and broadcast/held pending.
3. Before `T` is mined, `A` submits another `AccountPermissionUpdateContract` that changes active permissions to `[P2 (id=2, threshold=2, keys={a,b})]` (P1 removed/replaced) — this is mined first.
4. `T` is then processed: `getPermissionById(2)` now returns `P2`, whose `threshold=2` is satisfied by the existing signatures from `a` and `b`, even though those signatures were only ever intended to be evaluated against `P1`'s threshold of 3, per `TransactionCapsule.validateSignature()` [6](#0-5) .
5. `T` executes as fully authorized despite never meeting `P1`'s intended requirements.

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }
