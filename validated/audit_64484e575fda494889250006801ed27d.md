### Title
Unchecked Integer Overflow in TRC10 Token Transfer During `SELFDESTRUCT` Allows Balance Corruption/Loss - (File: `actuator/src/main/java/org/tron/core/vm/utils/MUtil.java`)

### Summary
The reported bug class is a "loop over multiple assets, one item's unsafe handling corrupts/blocks the whole batch operation." The closest reachable analog in java-tron is `MUtil.transferAllToken()`, which is invoked by the TVM `SELFDESTRUCT` opcode handling in `Program.suicide()`/`suicide2()` to migrate **all** TRC10 token balances from a self-destructing contract to the beneficiary address. Unlike every other TRC10 balance-mutation path in the codebase (`AccountCapsule.addAssetAmountV2`, `RepositoryImpl.addTokenBalance`), which use `addExact`/`subtractExact` to guard against `long` overflow, `transferAllToken` performs raw, unchecked `long` addition when merging token balances into the recipient.

### Finding Description
`MUtil.transferAllToken` iterates over every TRC10 token the self-destructing account holds and merges each balance into the beneficiary's asset map: [1](#0-0) 

Note line 35: `toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount` — a plain `+`, with no `addExact`/overflow check, in contrast to `AccountCapsule.addAssetAmountV2`, which explicitly guards overflow via `addExact`: [2](#0-1) 

This function is called from the TVM's `SELFDESTRUCT` opcode implementation, for both the "constantinople" (`suicide`) and "regular" (`suicide2`) code paths, whenever `allowTvmTransferTrc10` is enabled: [3](#0-2) [4](#0-3) 

Any account can freely acquire TRC10 balances for an arbitrary token via `TransferAssetContract`/`TransferAssetActuator` (a permissionless, broadcastable contract type), so an attacker fully controls how much of a given TRC10 token a target beneficiary address holds before a self-destruct occurs. If a self-destructing contract (attacker-controlled, and holding a large TRC10 balance of the same token) sends its balance to a beneficiary address whose existing balance for that token is already close to `Long.MAX_VALUE`, the unchecked `+` in `transferAllToken` wraps around (two's-complement overflow), producing a corrupted — potentially large-negative — stored `long` balance for that token in the beneficiary's `AssetV2Map`.

### Impact Explanation
This corrupts TRC10 accounting for the affected account: the resulting stored balance no longer reflects real backing supply. Depending on the wrapped value, this can manifest as an unbacked/negative balance entry that breaks subsequent `assetBalanceEnoughV2`/`reduceAssetAmountV2` checks (both of which require `amount <= currentAmount`, so a negative wrapped balance permanently freezes further transfers of that token for the victim), or an unintended free "topped-up" balance if the wrap lands on a large positive number — i.e., unbacked balance creation, one of the explicitly accepted impact categories.

### Likelihood Explanation
Exploitability requires reaching `Long.MAX_VALUE`-adjacent TRC10 balances, which is only practical for TRC10 tokens whose total supply is near `Long.MAX_VALUE` (issuer-controlled at `AssetIssueContract` creation, `totalSupply` field), or by an attacker who is also the token issuer/large holder. This narrows the practical attack surface, but it is fully reachable from an unprivileged, permissionless transaction (`TriggerSmartContract` invoking `SELFDESTRUCT` after acquiring/transferring TRC10 balances via `TransferAssetContract`), with no special network or validator privileges needed.

### Recommendation
Use `addExact` (matching the pattern already used in `AccountCapsule.addAssetAmountV2`) inside `MUtil.transferAllToken` when merging TRC10 balances, and handle the resulting `ArithmeticException` explicitly (e.g., reject the `SELFDESTRUCT`/transaction) rather than silently overflowing the recipient's balance.

### Proof of Concept
1. Attacker (or an issuer they control) creates/owns a TRC10 token `T` with a very large total supply.
2. Attacker uses `TransferAssetContract` (permissionless) to accumulate a balance of `T` close to `Long.MAX_VALUE` at a target beneficiary address `B` (this can be `B`'s own account if `B` is attacker-controlled, or engineered against any account that can receive TRC10 transfers).
3. Attacker deploys/uses a smart contract `C` that also holds a nonzero balance of `T`.
4. `C` executes `SELFDESTRUCT(B)`. The TVM calls `Program.suicide()`/`suicide2()`, which calls `MUtil.transferAllToken(repo, C, B)`.
5. In `transferAllToken`, `toBuilder.getAssetV2Map().getOrDefault("T", 0L) + amount` overflows `long`, silently storing a wrapped (possibly negative) value as `B`'s new balance of `T`, corrupting `B`'s TRC10 accounting without any transaction failure or warning.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  public boolean addAssetAmountV2(byte[] key, long amount,
      DynamicPropertiesStore dynamicPropertiesStore, AssetIssueStore assetIssueStore) {
    importAsset(key);
    boolean disableJavaLangMath = dynamicPropertiesStore.disableJavaLangMath();
    //key is token name
    if (dynamicPropertiesStore.getAllowSameTokenName() == 0) {
      Map<String, Long> assetMap = this.account.getAssetMap();
      AssetIssueCapsule assetIssueCapsule = assetIssueStore.get(key);
      String tokenID = assetIssueCapsule.getId();
      String nameKey = ByteArray.toStr(key);
      Long currentAmount = assetMap.get(nameKey);
      if (currentAmount == null) {
        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
          .putAsset(nameKey, addExact(currentAmount, amount, disableJavaLangMath))
          .putAssetV2(tokenID, addExact(currentAmount, amount, disableJavaLangMath))
          .build();
    }

    if (dynamicPropertiesStore.getAllowSameTokenName() == 1) {

        currentAmount = 0L;
      }
      this.account = this.account.toBuilder()
