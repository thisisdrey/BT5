### Title
Stale cached `global_fee_wallet` in `MarginfiGroup.fee_state_cache` diverts fees and account rent to old/compromised address after global fee wallet rotation - (File: `programs/marginfi/src/instructions/marginfi_account/admin_close.rs`, `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`FeeState.global_fee_wallet` is the program-wide source of truth for where protocol fees go, and the global fee admin can rotate it at will via `edit_fee_state` [1](#0-0) . However, each `MarginfiGroup` keeps its own cached copy, `fee_state_cache.global_fee_wallet`, which is only refreshed by the separate, permissionless `propagate_fee` instruction [2](#0-1)  and the `FeeStateCache` struct definition [3](#0-2) . Several unprivileged, user-reachable instructions validate and route real value transfers against this stale per-group cache instead of the live `FeeState` account, exactly mirroring the reported bug class: a fee/royalty destination cached at one point in time and never re-synced when the canonical address changes.

### Finding Description
`transfer_to_new_account` and `transfer_to_new_account_pda` check the caller-supplied `global_fee_wallet` account against `group.fee_state_cache.global_fee_wallet` (not `FeeState.global_fee_wallet`) before transferring `ACCOUNT_TRANSFER_FEE` lamports to it: [4](#0-3)  and the PDA variant [5](#0-4) , with the actual SOL CPI targeting that same unchecked account [6](#0-5) .

More seriously, the permissionless `admin_close_account` instruction closes an inactive `MarginfiAccount` and sends **all of its rent lamports** to whatever account satisfies `global_fee_wallet.key() == group.load()?.fee_state_cache.global_fee_wallet`: [7](#0-6) . Because `close = global_fee_wallet` is an Anchor account-closing constraint, this is a direct, unauthorized transfer of account lamports to the cached (potentially stale/compromised) wallet rather than the current one.

Both instructions rely on `fee_state_cache`, which is populated once at group init from the live `FeeState` [8](#0-7)  (initialize.rs references `fee_state_cache`), and thereafter only updated by the standalone, opt-in `propagate_fee` instruction. If the global fee admin rotates `global_fee_wallet` (e.g., because the old wallet is compromised or deprecated — the same scenario the external report envisions), any `MarginfiGroup` for which nobody has since called `propagate_fee` will keep accepting/transferring value to the old wallet, indefinitely, since `propagate_fee` is never automatically triggered by `edit_fee_state`.

### Impact Explanation
- Any inactive/empty account (any user's) can be permissionlessly closed by anyone via `admin_close_account`, and its full rent-exempt lamport balance will flow to the stale `fee_state_cache.global_fee_wallet` instead of the newly designated wallet — an unauthorized transfer of protocol/user-associated funds to an address the protocol has explicitly moved away from (e.g., because it was compromised).
- Every account migration via `transfer_to_new_account`/`transfer_to_new_account_pda` sends the fixed `ACCOUNT_TRANSFER_FEE` to the stale wallet as well, for as long as the affected group's cache isn't refreshed.
- This matches the report's root cause exactly: a cached destination address is not dynamically re-derived from the authoritative config, so value keeps flowing to a wallet the admin no longer wants funds sent to.

### Likelihood Explanation
Requires the global fee admin to rotate `global_fee_wallet` (a legitimate, expected admin action — e.g., in response to compromise) combined with `propagate_fee` not yet having been called for a given group. Since `propagate_fee` is a separate, non-atomic, permissionless instruction rather than being invoked automatically inside `edit_fee_state`, there is no guarantee of synchronization across all groups at rotation time — every existing group is stale by default immediately after the wallet is changed, mirroring the "low likelihood of destination-change event, high impact once it occurs" profile the original finding was judged on.

### Recommendation
Either (a) make `edit_fee_state` responsible for updating all group caches is infeasible at scale, so instead (b) have security-critical, value-moving instructions (`admin_close_account`, `transfer_to_new_account[_pda]`) validate `global_fee_wallet` against the live `FeeState` account directly (as `add_pool_with_seed.rs` and `liquidate_end.rs` correctly do via `has_one = global_fee_wallet` on `FeeState`) rather than against the per-group cache, or require `propagate_fee` to be invoked atomically as part of these flows before honoring the cached wallet.

### Proof of Concept
1. Global fee admin calls `edit_global_fee_state` with a new `fee_wallet` because the old wallet key was compromised: [1](#0-0) . `FeeState.global_fee_wallet` is now the new address.
2. No one has yet called the permissionless `propagate_fee` for `MarginfiGroup` G, so `G.fee_state_cache.global_fee_wallet` still equals the old (compromised) address: [9](#0-8) .
3. Anyone permissionlessly calls `admin_close_account` for any eligible empty/inactive account under G, passing the old compromised address as `global_fee_wallet`; the constraint check passes because it matches the stale cache, and Anchor's `close = global_fee_wallet` sends the account's full lamport balance to that old, compromised wallet: [10](#0-9) .
4. Similarly, a user calling `transfer_to_new_account` for an account under group G still pays `ACCOUNT_TRANSFER_FEE` to the old wallet, since the check only compares against `fee_state_cache.global_fee_wallet`: [4](#0-3) .
