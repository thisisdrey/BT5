Confirmed: `validateFetchIntoObjectPoolRequest` in `internal/gitaly/service/objectpool/fetch_into_object_pool.go` only checks that `origin` and `object_pool` share the same storage name — it never verifies that `origin` is an actual member/fork relationship of the `object_pool`, nor that the caller is authorized to read `origin`. `FetchFromOrigin` then runs `git fetch <originPath> +refs/*:refs/remotes/origin/*` directly against that arbitrary path [1](#0-0) , pulling all of `origin`'s objects and refs into the target pool that the attacker fully controls (via `GetObjectPool`/`LinkRepositoryToObjectPool` on their own repository). This is analogous to the reported bug class: knowledge of an identifier (there, `orgId`; here, a repository's `storage_name`/`relative_path`) is enough to pull cross-tenant data through an endpoint that checks only superficial equality (storage name) instead of verifying an actual ownership/membership relation between `origin` and `object_pool`.

### Title
Broken access control in `FetchIntoObjectPool` allows fetching arbitrary same-storage repository objects into an attacker-controlled pool - (File: internal/gitaly/service/objectpool/fetch_into_object_pool.go)

### Summary
`FetchIntoObjectPool` validates only that `origin.storage_name == object_pool.repository.storage_name` before fetching all refs/objects from `origin` into the pool. There is no check that `origin` is actually a member of, or otherwise associated with, `object_pool`. Because Gitaly relies purely on the caller-supplied `Repository` fields (storage name + relative path) to identify repositories, any actor able to invoke this RPC with a known/guessable relative path of a repository they do not own can exfiltrate its full history into an object pool they control (and read via any repository already linked to that pool), analogous to the reported `orgId`-based broken access control that let a hash for one resource be swapped in to read another user's private data.

### Finding Description
The RPC handler builds an `ObjectPool` from `req.GetObjectPool()` and an `origin` repository straight from `req.GetOrigin()`, without validating that `origin` is a legitimate pool member: [2](#0-1) . The only guard, `validateFetchIntoObjectPoolRequest`, checks storage-name equality alone: [3](#0-2) . `FetchFromOrigin` subsequently executes `git fetch <originPath> +refs/*:refs/remotes/origin/*` unconditionally against whatever path `origin` resolves to: [4](#0-3) . Contrast this with `LinkRepositoryToObjectPool`, which is similarly permissive — it links any `repository` supplied by the caller into the object pool with no membership/ownership verification either, only that it resolves to a valid repository: [5](#0-4) . Once objects from a victim repository are fetched into a pool, and that pool is (or becomes) linked as an alternate to a repository the attacker controls, `git cat-file`/`git log`/clone operations on the attacker's repository will resolve objects sourced from the victim repository via the shared `objects/info/alternates` mechanism, described in `doc/object_pools.md`. This mirrors the report's chain: obtain an identifier for a resource that is not yours (here, a `relative_path`, there an `orgId` hash), then invoke an endpoint whose authorization check only tests a shallow property (storage-name match) rather than actual ownership/membership.

### Impact Explanation
Successful exploitation discloses the full object graph (commits, blobs, trees — potentially containing source code, credentials, or other sensitive KYC-equivalent data committed to the repository) of any repository sharing the same Gitaly storage as the attacker's own pool/repository, without requiring the attacker to otherwise have read access to that repository. This is a confidentiality breach comparable in class to the reported vulnerability (CVSS C:H), since it results in unauthorized cross-tenant data disclosure via object storage rather than transport authentication bypass.

### Likelihood Explanation
Exploitation requires the attacker to (1) control an object pool and a repository linked to it (a normal, supported workflow for any repository owner via `CreateObjectPool`/`LinkRepositoryToObjectPool`), and (2) know or guess the `storage_name`/`relative_path` of a victim repository on the same storage. Gitaly's `Repository` identifiers are typically derived from predictable, hashed project paths (e.g., `@hashed/...`) that can be obtained through other information-disclosure vectors or internal APIs, mirroring the report's requirement of first obtaining the `orgId` hash via a chained vulnerability. Likelihood is elevated because no additional Gitaly-side ownership check exists at all — the only defense-in-depth layer is whatever authorization the calling layer (e.g., GitLab Rails/Praefect) performs before invoking this RPC, and if that layer is bypassed or misconfigured, Gitaly imposes no additional restriction.

### Recommendation
Add an explicit relationship check before performing the fetch/link: verify that `origin` is actually reachable as a fork/member of `object_pool` (e.g., cross-check `origin`'s recorded pool/alternates linkage, or require an authoritative mapping maintained by the control plane) rather than only comparing storage names. At minimum, `FetchIntoObjectPool` and `LinkRepositoryToObjectPool` should reject requests where `origin`/`repository` is not already an established member of the target pool's lineage, closing the same class of gap that allowed the `orgId` swap in the original report.

### Proof of Concept
1. Attacker owns `repo-attacker` (storage `default`) and creates/owns `pool-attacker` via `CreateObjectPool` from `repo-attacker`, then links `repo-attacker` to `pool-attacker` via `LinkRepositoryToObjectPool`.
2. Attacker learns/guesses the `relative_path` of a private victim repository `victim.git` on the same `default` storage (analogous to obtaining the `orgId` hash).
3. Attacker calls:
   ```
   FetchIntoObjectPool(
     origin = { storage_name: "default", relative_path: "victim.git" },
     object_pool = { repository: { storage_name: "default", relative_path: "pool-attacker.git" } }
   )
   ```
   `validateFetchIntoObjectPoolRequest` only checks storage-name equality and passes: [3](#0-2) .
4. `FetchFromOrigin` runs `git fetch <victim path> +refs/*:refs/remotes/origin/*` into `pool-attacker`: [6](#0-5) , importing all of `victim.git`'s objects/refs.
5. Since `repo-attacker` is an alternate member of `pool-attacker`, the attacker can now run `git log refs/remotes/origin/heads/*` (or similar) inside `repo-attacker` and read every commit/blob that was private to `victim.git`.

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
}
