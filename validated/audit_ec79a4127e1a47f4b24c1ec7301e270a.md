## Finding

### Title
JSON-RPC transaction builder silently drops TRC10 transfer intent when both `value` and `tokenId`/`tokenValue` are set, misrouting the call to a plain TRX transfer - (File: `framework/src/main/java/org/tron/core/services/jsonrpc/types/BuildArguments.java`)

### Summary
`BuildArguments.getContractType()` decides which contract type (TRX transfer, TRC10 asset transfer, or smart-contract call) to build from an untrusted JSON-RPC request (`eth_sendTransaction` / related calls handled by `TronJsonRpcImpl`). The routing logic mirrors the Nested `_transferInputTokens()` pattern of choosing between two mutually exclusive payment mechanisms (native currency vs. token) but — unlike the recommended fix in the report — it never rejects the case where **both** a native TRX `value` and a TRC10 `tokenId`/`tokenValue` are supplied simultaneously.

### Finding Description
`availableTransferAsset()` only routes to `ContractType.TransferAssetContract` (TRC10 transfer) when `tokenId > 0 && tokenValue > 0 && paramQuantityIsNull(value)`: [1](#0-0) 

In `getContractType()`, if the target address is not a smart contract, the code checks `availableTransferAsset()` first; if it is `false` (which happens whenever `value` is non-null/non-empty, *regardless* of whether `tokenId`/`tokenValue` are also populated), it falls through to a plain TRX `TransferContract` using only `value`, with `tokenId`/`tokenValue` silently discarded: [2](#0-1) 

There is no equivalent of the Nested mitigation (`require(msg.value == 0, ...)`) that would reject a request carrying conflicting payment intents (`tokenId`/`tokenValue` set together with a non-null `value`). Instead of failing validation, the request is silently reinterpreted as a different transaction type than the caller intended.

### Impact Explanation
An API client (anonymous JSON-RPC caller) that builds a request intending to send a TRC10 token (setting `tokenId` and `tokenValue`) but also populates `value` (e.g., a wallet/tool that always sets a `value` field, or a caller mistake) will have the token fields silently ignored and a completely different operation performed — a native TRX transfer using whatever is in `value` — with no error returned. This is a direct analog of the Nested bug class: instead of enforcing "the two payment paths are mutually exclusive," the code silently picks one and drops user-supplied state, which can result in the wrong asset/amount being moved from the caller's account to the destination address without any indication of the mismatch.

### Likelihood Explanation
Reachable via a single unauthenticated/unprivileged JSON-RPC request through `TronJsonRpcImpl`/`BuildArguments`, with no special permissions required — any client of the node's JSON-RPC endpoint can trigger it by supplying both `value` and `tokenId`/`tokenValue` in a transaction-build call.

### Recommendation
Mirror the Nested fix: explicitly reject requests that set both a non-null/non-zero `value` and a TRC10 `tokenId`/`tokenValue`, e.g.
```java
if (tokenId > 0 && tokenValue > 0 && !paramQuantityIsNull(value)) {
    throw new JsonRpcInvalidParamsException("both TRX value and TRC10 token fields are set");
}
```
instead of silently falling back to `TransferContract`.

### Proof of Concept
1. Send a JSON-RPC "build transaction" request with `to` = a non-contract account, `tokenId` = N, `tokenValue` = M (intending a TRC10 transfer), and also `value` = some non-null amount (e.g., a wallet client's default field).
2. `availableTransferAsset()` returns `false` because `value` is not null, so `getContractType()` returns `ContractType.TransferContract`.
3. The resulting transaction transfers `value` TRX instead of the intended TRC10 token amount `tokenValue`; the token fields are silently dropped with no error surfaced to the caller. [3](#0-2) 

---
**Caveat:** I was unable to fully trace `TronJsonRpcImpl`'s downstream use of `BuildArguments` (how `tokenId`/`tokenValue`/`value` are consumed once `getContractType()` returns) within the available tool budget, so the exact end-to-end transaction-construction behavior (and whether any later code path re-validates or re-injects the token fields) could not be independently confirmed. The finding is based on the routing logic in `BuildArguments.java` itself, which is the closest concrete analog to the reported bug class in this codebase.

```java
  public ContractType getContractType(Wallet wallet) throws JsonRpcInvalidRequestException,
      JsonRpcInvalidParamsException {
    // Fail fast on bad hex / conflict before the state lookup;
    // calldataEquals relies on resolveData() having validated hex first.
    String resolvedData = resolveData();
    validateCallDataConflict();

    ContractType contractType;

    // to is null
    if (paramStringIsNull(to)) {
      // data is null
      if (paramStringIsNull(resolvedData)) {
        throw new JsonRpcInvalidRequestException("invalid json request");
      }

      contractType = ContractType.CreateSmartContract;
    } else {
      // to is not null
      byte[] contractAddressData = addressCompatibleToByteArray(to);
      BytesMessage.Builder build = BytesMessage.newBuilder();
      BytesMessage bytesMessage = build.setValue(ByteString.copyFrom(contractAddressData)).build();
      SmartContract smartContract = wallet.getContract(bytesMessage);

      // check if to is smart contract
      if (smartContract != null) {
        contractType = ContractType.TriggerSmartContract;
      } else {
        // tokenId and tokenValue: trc10, value: TRX
        if (availableTransferAsset()) {
          contractType = ContractType.TransferAssetContract;
        } else {
          if (StringUtils.isNotEmpty(value)) {
            contractType = ContractType.TransferContract;
          } else {
            throw new JsonRpcInvalidRequestException("invalid json request");
          }
        }
      }
    }

    return contractType;
  }
```
