### Title
Unstaked half-open QUIC connections can exhaust the shared `ClientConnectionTracker` pool, starving legitimate staked handshakes - (File: streamer/src/nonblocking/quic.rs)

### Summary
`ClientConnectionTracker::new` enforces a single global cap (`qos.max_concurrent_connections()`) that is incremented as soon as `incoming.accept()` succeeds, before the TLS handshake completes, and is only decremented once the connection is fully processed or the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` (2s) elapses. Because peer stake cannot be known until after the handshake completes, this pre-handshake counter is necessarily shared across staked and unstaked attempts, so an attacker who opens many connections and stalls the handshake can occupy the entire headroom and cause legitimate staked connections to be refused.

### Finding Description
In `spawn_server` (`streamer/src/nonblocking/quic.rs:371-379`), each accepted `Incoming` is admitted via `ClientConnectionTracker::new(stats.clone(), qos.max_concurrent_connections())` [1](#0-0)  before the handshake (`incoming.accept()`) even begins. `ClientConnectionTracker::new` simply does an atomic `fetch_add` against a single `stats.open_connections` counter and compares it to `max_concurrent_connections`, with no notion of stake, IP, or connection stage [2](#0-1) . The tracker is only dropped (decrementing the counter) when the owning `setup_connection` task ends — including on the `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` branch [3](#0-2) [4](#0-3) . `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` is 2 seconds [5](#0-4) .

`qos.max_concurrent_connections()` for `SwQos` (the production QoS implementation) is `(max_staked_connections + max_unstaked_connections) * 5 / 4` — a single pool, not partitioned by stake [6](#0-5) . Peer stake is only determinable after `qos.build_connection_context(&new_connection)` runs post-handshake (`setup_connection`, line 512), so the pre-handshake admission gate structurally cannot discriminate staked vs. unstaked attempts.

Existing mitigations do not close this gap for an attacker with several distinct IPs (real, reachable addresses, as required by "no address spoofing" per the code comment):
- The overall rate limiter only checks `current_tokens() == 0` before `ClientConnectionTracker::new`, and only actually consumes a token *after* a successful handshake (`overall_connection_rate_limiter.consume_tokens(1)` at line 495), so it does not throttle the volume of stalled handshake *attempts* going into the tracker.
- The per-IP `ConnectionRateLimiter` allows a burst of `max_connections_per_ipaddr_per_min * 10` tokens per IP before throttling (`streamer/src/nonblocking/quic.rs:270-276`), and this limit is per source IP, so an attacker distributing connection attempts across multiple source IPs (still real, completing accept()) can multiply the effective burst by however many IPs are used, well beyond the shared `max_concurrent_connections()` capacity.
- Neither limiter is partitioned by stake, so none of them protect the shared tracker pool specifically for staked peers.

As a result, an attacker who opens `(max_staked + max_unstaked) * 5/4` connections and stalls each handshake (e.g. never sending Handshake packet after Initial) can hold the entire tracker capacity for up to 2 seconds at a time, causing subsequent legitimate staked handshake attempts to hit `ClientConnectionTracker::new`'s `Err(())` branch, incrementing `refused_connections_too_many_open_connections` and calling `incoming.refuse()` [1](#0-0) .

### Impact Explanation
This is a QoS-evasion / denial-of-service against the pre-handshake connection admission gate: an unstaked attacker can starve legitimate staked validators/RPC clients from ever getting their handshake accepted during the attack window, because the tracker limit (`max_concurrent_connections`) is a single shared resource not reserved for staked traffic. This matches the "QoS evasion" bounty category rather than a memory-safety or consensus bug, since impact is bounded to transient connection refusal, not corruption of state.

### Likelihood Explanation
Preconditions: attacker needs no stake, only network reachability to the leader's TPU QUIC port and control of a modest number of source IPs/sockets (to defeat the per-IP `ConnectionRateLimiter` burst allowance and repeat every ~2s window). The attack is fully repeatable — every `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` window (2s), the attacker can re-fill stalled connections. The remaining rate limiters (`overall_connection_rate_limiter`, per-IP `ConnectionRateLimiter`) reduce but do not eliminate feasibility, since they gate on IP/global connection *rate*, not on stake, and the tracker capacity itself (`(max_staked+max_unstaked)*5/4`) is a comparatively small, fixed number that can plausibly be exhausted within the burst allowances.

### Recommendation
Reserve a portion of `max_concurrent_connections()` headroom exclusively for the handshake path when there is reasonable prior signal of stake (e.g., track pre-validated pubkeys/IPs from prior sessions, or split the pre-handshake tracker into staked-reserved and unstaked-shared sub-pools), and/or shrink `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` further / apply IP-based backpressure earlier so stalled handshakes cannot accumulate to the full shared cap. Alternatively, make `overall_connection_rate_limiter` consume a token at accept time (not only after a successful handshake) so the rate of *attempts* entering `ClientConnectionTracker::new` is bounded independent of handshake completion.

### Proof of Concept
Integration test plan (extending existing tests in `streamer/src/nonblocking/quic.rs` / `tpu-client-next/tests/connection_workers_scheduler_test.rs`):
1. Spawn a QUIC server via `setup_quic_server` with a small `SwQosConfig { max_staked_connections: N1, max_unstaked_connections: N2, .. }`, computing `cap = (N1+N2)*5/4`.
2. From `cap` distinct client-side UDP sockets/source ports (varying source IP if possible in the test harness, or relying on relaxed per-IP burst limits), initiate `Endpoint::connect` to the server but withhold sending post-Initial handshake packets (e.g., use a raw UDP socket to send only an `Initial` packet without completing TLS, or drop the client endpoint immediately after `connect()` without awaiting the connecting future) so the connections remain half-open for close to `QUIC_CONNECTION_HANDSHAKE_TIMEOUT`.
3. Concurrently, from a legitimate staked keypair, attempt `make_client_endpoint` + full handshake against the same server.
4. Assert the legitimate staked connect either times out or fails, and that `stats.refused_connections_too_many_open_connections.load(Ordering::Relaxed) > 0` while the flood is in-flight, matching the bug's proof idea of flooding to `(max_staked+max_unstaked)*5/4` half-open connections.

impl ClientConnectionTracker {
    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);
        if open_connections >= max_concurrent_connections {
            stats.open_connections.fetch_sub(1, Ordering::Relaxed);
            debug!(
                "There are too many concurrent connections opened already: open: \
                 {open_connections}, max: {max_concurrent_connections}"
            );
            return Err(());
        }

        Ok(Self { stats })
    }
