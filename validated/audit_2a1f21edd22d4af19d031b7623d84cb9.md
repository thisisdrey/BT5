### Title
Unauthenticated remote `POST /shutdown` terminates the stacks-signer's event receiver, causing denial of service - ([File: libsigner/src/events.rs])

### Finding Description
The claimed equality — "only the node process that owns this signer may terminate its event loop" — is broken. `SignerEventReceiver::next_event` dispatches purely on the HTTP method/URL of any accepted TCP connection, with zero authentication, secret, or peer-identity check [1](#0-0) . Any of the `/stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, `/shutdown`, `/new_block` routes are reachable by simply connecting and sending a well-formed HTTP request; the legitimate intended caller (the internal `SignerStopSignaler::send`) itself just opens a plain `TcpStream` to `self.local_addr` and writes a hardcoded `POST /shutdown HTTP/1.1 ...` request with no token/HMAC/nonce [2](#0-1) . Because `bind()` starts an unauthenticated `tiny_http::HttpServer` on the configured `listener` address [3](#0-2) , and sample configs bind this to `0.0.0.0:30000` (all interfaces) [4](#0-3) , any remote party able to reach that port can send `POST /shutdown HTTP/1.1\r\nHost: ...\r\nContent-Length: 0\r\n\r\n` and trigger `event_receiver.stop_signal.store(true, Ordering::SeqCst); Err(EventError::Terminated)` [5](#0-4) . `main_loop` treats `EventError::Terminated` as "we're done" and breaks out permanently [6](#0-5) , so the signer's event-receiver thread exits for good — there is no restart logic, so all subsequent StackerDB chunks, burn-block events, and block-validation responses from the node are silently dropped.

### Impact Explanation
A single unauthenticated TCP message permanently halts a signer's ability to observe StackerDB/miner/burn-block events, effectively taking that signer offline for signing duties without crashing the process (it becomes a silent zombie). Repeatable against any signer whose event-receiver port is reachable (e.g., bound to `0.0.0.0`). If enough signers in a signing set are silenced this way, it can stall block signing for the network — matching "Critical: remote crash/unauthenticated DoS from few messages" against the signer transport.

### Likelihood Explanation
No secret, key, or role is needed — just TCP reachability to the bound `endpoint` address, which per the reference configs (`endpoint = "0.0.0.0:30000"`) is often bound to all interfaces rather than loopback-only [4](#0-3) . The attack is a single crafted HTTP request, zero cost, and immediately effective.

### Recommendation
Require the same shared secret/auth mechanism used for the node→signer event push (mirroring the node's `auth_token`/`connection_options`) to be validated on `/shutdown` (and ideally on all event routes), or restrict shutdown to a local-only control channel (e.g., a Unix domain socket, an internal channel, or a signed/nonce-based request) instead of a plaintext, unauthenticated HTTP POST reachable from the network.

### Proof of Concept
Rust test in `libsigner`:
1. Bind a `SignerEventReceiver` via `Signer::spawn` to `127.0.0.1:<port>` as in `test_status_endpoint` [7](#0-6) .
2. From a separate "foreign" thread simulating an unrelated remote peer, open a raw `TcpStream::connect(endpoint)` and write `format!("POST /shutdown HTTP/1.1\r\nHost: {endpoint}\r\nConnection: close\r\nContent-Length: 0\r\n\r\n")`.
3. Sleep briefly, then assert `event_receiver.is_stopped() == true` (via the stop signal or by observing `running_signer.stop()` returning early / `EventError::Terminated` in logs).
4. Have a second thread simulate the real node subsequently POSTing a `/stackerdb_chunks` event and assert it never reaches the runloop's result channel (`accepted_events` stays empty), proving the shutdown fully and irreversibly silenced the signer.
