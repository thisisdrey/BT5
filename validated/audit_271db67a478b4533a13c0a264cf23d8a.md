### Title
Full-Repack Timestamp Advanced Before Repack Completes Enables Indefinite Housekeeping Griefing - (File: `internal/git/housekeeping/objects.go`)

### Summary
`housekeeping.RepackObjects()` writes the on-disk "last full repack" timestamp *before* the actual repack work runs, and does so unconditionally for every full-repack attempt, whether it ultimately succeeds or fails. This timestamp is the sole gate that the heuristic optimization strategy uses to decide whether a repository is due for a full repack (which is the mechanism that expires cruft/unreachable objects, regenerates bitmaps, and refreshes delta islands). An ordinary repository owner who can trigger repeated housekeeping runs (which happens automatically after their own mutator RPCs/pushes) can perpetually reset this gate without ever completing a real full repack, mirroring the reward-accumulator griefing pattern: the "last update" marker advances every call, but the underlying accrual (a completed full repack) never happens, freezing the maintenance schedule for that repository indefinitely.

### Finding Description
`RepackObjects` explicitly updates `FullRepackTimestampFilename` up front: [1](#0-0) 

The code comment states the design intent directly — "even if the full repack fails, we would still pretend to have done it" — to avoid busy-spinning git-repack on huge/failing repositories. This means the timestamp is treated as an unconditional "claim" event, exactly like the vulnerable `rewardLastUpdateTime` in the reported bug, which is updated on every `claim()` call independent of whether a meaningful reward interval actually elapsed.

This timestamp is the only signal `HeuristicalOptimizationStrategy.ShouldRepackObjects` uses to decide whether a full repack is due: [2](#0-1) [3](#0-2) 

Housekeeping (and thus `RepackObjects`) is triggered automatically for a repository after its own mutator RPCs, gated only by an interval counter, not by any privilege check — confirming this is reachable from an ordinary user's own writes/pushes: [4](#0-3) 

The same unconditional-timestamp-write pattern is duplicated in the WAL/transaction-based housekeeping path as well: [5](#0-4) 

Because the timestamp is written before the repack completes rather than after a *verified successful* full repack, any repeatable way to make the subsequent full-repack step fail, be cancelled, or be interrupted (e.g., by shaping the repository so `git-repack` runs out of memory/time, or by cancelling the RPC context after the housekeeping run has started but before repack finishes) lets an attacker "claim" the full-repack slot without ever paying its cost — repeatedly, at the interval the housekeeping middleware allows.

### Impact Explanation
Full repacks are the only path that:
- expires unreachable/cruft objects past the grace period (`StaleObjectsGracePeriod`),
- regenerates delta islands important for cross-fork pack efficiency,
- (re)writes bitmaps and multi-pack-index in the canonical full form.

If `LastFullRepack` keeps advancing without a real full repack ever completing, cruft/unreachable objects and multiple non-cruft packfiles accumulate without bound in that repository, degrading storage efficiency, clone/fetch performance, and eventually driving unbounded disk growth — a availability/DoS impact scoped to the affected repository (and, for object pools, potentially amplified to all repositories/forks attached to the pool since pool repositories never delete objects and rely entirely on scheduled full repacks for hygiene).

### Likelihood Explanation
The trigger path (mutator RPC → automatic housekeeping → `OptimizeRepository` → `RepackObjects`) is reachable by any user with ordinary write access to a repository; no elevated privilege is required. What is not verified in the codebase search is a concrete, reliable technique to force `git-repack` itself to fail or be cancelled on demand after the timestamp write but before the repack finishes (e.g., relying on resource exhaustion, external cancellation, or crafted pathological object graphs). This part is an assumption based on the documented behavior of the code itself; further investigation/testing would be needed to confirm a deterministic failure trigger, which is outside what could be established from static code inspection alone.

### Recommendation
Only advance `FullRepackTimestampFilename` after a full repack has actually completed successfully (or apply the same "postpone to the last fully-elapsed boundary" fix pattern suggested for the original bug: don't credit an interval that wasn't actually consumed). If the busy-spin concern for huge/failing repositories must be preserved, use a separate, explicitly-labeled "last full-repack *attempt*" cooldown distinct from "last full-repack *success*", so that eviction/bitmap-refresh heuristics are driven only by verified successful repacks, not by attempts.

### Proof of Concept
Conceptual (not independently executed/verified against a live cluster):
1. As an ordinary user with push access to `repo`, create/push commits to accumulate multiple non-cruft packfiles so `ShouldRepackObjects` selects a full repack.
2. Shape the push/repository so the subsequent full `git-repack` invocation triggered by automatic housekeeping is likely to fail or be interrupted (e.g., pathological ref/object volume causing failure) while ensuring `RepackObjects` (`internal/git/housekeeping/objects.go:82`) still reaches the `stats.UpdateFullRepackTimestamp` call before the repack step errors out.
3. Repeat step 1–2 at the housekeeping-middleware's minimum trigger interval.
4. Observe that `LastFullRepack` keeps advancing (verifiable via `RepositoryInfoResponse.PackfilesInfo` / the `.gitaly-full-repack-timestamp` file) while cruft/unreachable objects and multiple packfiles keep accumulating, since `timeSinceLastFullRepack` never exceeds `FullRepackCooldownPeriod` long enough for a real repack to be scheduled and completed.

	// It is mandatory for us that we perform regular full repacks in repositories so
	// that we can evict objects which are unreachable into a separate cruft pack. So in
	// the case where we have more than one non-cruft packfiles and the time since our
	// last full repack is longer than the grace period we'll perform a full repack.
	//
	// This heuristic is simple on purpose: customers care about when objects will be
	// declared as unreachable and when the pruning grace period starts as it impacts
	// usage quotas. So with this simple policy we can tell customers that we evict and
	// expire unreachable objects on a regular schedule.
	//
	// On the other hand, for object pools, we also need to perform regular full
	// repacks. The reason is different though, as we don't ever delete objects from
	// pool repositories anyway.
	//
	// Geometric repacking does not take delta islands into account as it does not
	// perform a graph walk. We need proper delta islands though so that packfiles can
	// be efficiently served across forks of a repository.
	//
	// Once a full repack has been performed, the deltas will be carried forward even
	// across geometric repacks. That being said, the quality of our delta islands will
	// regress over time as new objects are pulled into the pool repository.
	//
	// So we perform regular full repacks in the repository to ensure that the delta
	// islands will be "freshened" again. If geometric repacks ever learn to take delta
	// islands into account we can get rid of this condition and only do geometric
	// repacks.
	if nonCruftPackfilesCount > 1 && timeSinceLastFullRepack > FullRepackCooldownPeriod {
		return true, fullRepackCfg
	}
