### Title
`get_nakamoto_blocks_in_tenure` returns orphaned blocks as canonical tenure state - [File: stackslib/src/chainstate/nakamoto/staging_blocks.rs]

### Summary
`get_nakamoto_blocks_in_tenure` filters only on `processed = 1` without excluding `orphaned = 1`, and `set_block_orphaned` marks an orphaned row with both `orphaned = 1` AND `processed = 1`. Consequently, a block that lost the signing-weight race in `store_block_if_better` and was later orphaned can still be returned by this function and served over the `/v3/tenures/fork_info` RPC endpoint as if it were part of the tenure's committed state.

### Finding Description
The query is:
```rust
let qry =
    "SELECT data FROM nakamoto_staging_blocks WHERE consensus_hash = ?1 AND processed = 1";
```

`set_block_orphaned` sets `processed = 1, orphaned = 1` on the losing block's row:
```rust
let clear_staged_block =
    "UPDATE nakamoto_staging_blocks SET processed = 1, processed_time = ?2, orphaned = 1
                          WHERE index_block_hash = ?1";
```
<cite repo="ThankGodontt/stacks-core--024" path="stackslib/src/chainstate/nakamoto/staging_blocks.rs" start="563-578" />

`set_block_processed` (used for legitimately processed/canonical blocks) sets only `processed = 1` and does not touch `orphaned`:
<cite repo="ThankGodontt/stacks-core--024" path="stackslib/src/chainstate/nakamoto/staging_blocks.rs" start="548-558" />

Since both legitimately-processed and orphaned rows satisfy `processed = 1`, and the SQL predicate lacks `AND orphaned = 0`, both rows are returned by `get_nakamoto_blocks_in_tenure`, unlike other, correctly-guarded queries in the same file (`next_ready_nakamoto_block`'s query explicitly adds `orphaned = 0`) <cite repo="ThankGodontt/stacks-core--024" path="stackslib/src/chainstate/nakamoto/staging_blocks.rs" start="470-476" />.

This is reachable from an unprivileged remote peer via the `/v3/tenures/fork_info` RPC handler (`GetTenuresForkInfo`), which calls `TenureForkingInfo::from_snapshot`, which in turn calls `chainstate.nakamoto_blocks_db().get_nakamoto_blocks_in_tenure(&sn.consensus_hash)` for any Nakamoto-epoch sortition in the requested range and returns the result directly as JSON in the HTTP response body:
<cite repo="ThankGodontt/stacks-core--024" path="stackslib/src/net/api/get_tenures_fork_info.rs" start="169-182" />
<cite repo="ThankGodontt/stacks-core--024" path="stackslib/src/net/api/get_tenures_fork_info.rs" start="197-311" />

The endpoint requires no authentication (`security: []` per the OpenAPI spec) and is remotely reachable by any peer that can issue an HTTP GET to the node's RPC port. The `TenureForkingInfo.nakamoto_blocks` field is populated straight from the unfiltered query, so an orphaned, non-canonical block hash and content is served in the JSON response as if it belonged to the tenure.

### Impact Explanation
A remote, unauthenticated caller of `/v3/tenures/fork_info/{start}/{stop}` receives, inside the `nakamoto_blocks` array for a given tenure, a block that lost `store_block_if_better`'s signing-weight race and was orphaned. This is "state served ('blocks in tenure') that includes a block no canonical chain actually committed," matching the High severity category ("serving non-canonical state as canonical"). It does not corrupt local chainstate (no write), but it misrepresents tenure history to any client trusting this RPC response (e.g., tooling doing fork analysis), and is fully repeatable for any tenure containing a resolved fork.

### Likelihood Explanation
Preconditions: attacker needs two competing signed blocks for one tenure (achievable by any block proposer/miner participant broadcasting a losing alternative that gets accepted into staging, then orphaned once the winner is processed) and the node must have processed the fork (i.e., called `set_block_orphaned`). No privileged access, secret, or admin role is required — the RPC endpoint is unauthenticated and reachable by any peer. This is not attacker-controlled in real time per se (it depends on tenure fork history existing), but is deterministic and reproducible once such a fork exists, and querying the endpoint costs a single GET request.

### Recommendation
Add `AND orphaned = 0` to the `get_nakamoto_blocks_in_tenure` SQL query, consistent with the guard already used in `next_ready_nakamoto_block`:
```rust
let qry = "SELECT data FROM nakamoto_staging_blocks WHERE consensus_hash = ?1 AND processed = 1 AND orphaned = 0";
```

### Proof of Concept
Rust test in `stackslib::chainstate::nakamoto::staging_blocks` (or `stackslib::net`):
1. Open a `NakamotoStagingBlocksConn`/`Tx`, `store_block_if_better` two blocks (`block_a`, `block_b`) sharing the same `consensus_hash` but different `block_hash`/signing weights, both with `try_store_block_with_new_signer_sighash` succeeding as separate sighash rows.
2. Call `set_block_processed(&block_a.block_id())` to simulate the canonical winner being processed.
3. Call `set_block_orphaned(&block_b.block_id())` to simulate the loser being orphaned (this sets `processed=1, orphaned=1` on `block_b`'s row per lines 569-578).
4. Call `get_nakamoto_blocks_in_tenure(&consensus_hash)` and assert:
```rust
let blocks = conn.get_nakamoto_blocks_in_tenure(&consensus_hash).unwrap();
assert!(!blocks.iter().any(|b| b.block_id() == block_b.block_id()),
    "orphaned block should not be present in tenure results");
```
Currently this assertion fails, proving `block_b`'s `index_block_hash` is present alongside `block_a`'s, i.e., the `orphaned = 0` predicate is missing.
