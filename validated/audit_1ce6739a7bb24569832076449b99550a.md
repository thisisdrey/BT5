### Title
Git submodule `protocol.file.allow=always` override disables anti-path-traversal protection - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
`git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` invoke `git submodule update` with `-c protocol.file.allow=always` forced on every invocation, unconditionally re-enabling the `file://` submodule transport that upstream Git disabled by default specifically to close a known submodule-based local file access vulnerability (the class fixed by Git's `protocol.file.allow` hardening, CVE-2022-39253). Because the URL for each submodule comes from the `.gitmodules` file inside the fetched repository tree — content fully controlled by whoever hosts the remote the victim's `git_repository` rule points at — a hostile remote can point a submodule at an arbitrary local `file://` path (including paths outside the intended checkout directory) and have Git clone/hardlink files from that location into the repository during the Bazel fetch, with none of Bazel's `strip_prefix`/checkout-path containment checks applied to that operation.

### Finding Description
`update_submodules()` in `tools/build_defs/repo/git_worker.bzl` runs: [1](#0-0) 

The comment explains the rationale is compatibility with newer Git versions, but the effect is to force `protocol.file.allow=always` on the `git submodule update --init [--recursive] --checkout --force` invocation, which is executed via `_git_maybe_shallow` → `_execute`: [2](#0-1) 

Git added `protocol.file.allow` gating for submodules precisely because a repository's `.gitmodules` file — which is ordinary tracked content, fully controlled by the party hosting the repository/branch — can declare a submodule URL of `file:///some/local/path`. When submodule URLs are trusted implicitly and the local-clone/hardlink optimization is used, this allows the clone operation to read/copy files from arbitrary paths on the machine performing the clone (or, on some Git versions, escape the intended destination via hardlinks/symlinks), independent of any commit-hash pinning of the top-level repo. Bazel's `git_repository`/`new_git_repository` rule only pins/verifies the top-level `commit`/`tag`/`branch` of the remote; it performs no validation of `.gitmodules` content, and the checkout-path containment logic in `_clone_or_update_repo` (`strip_prefix`/`add_prefix` escape checks) is applied only to the final checked-out tree, not to intermediate submodule-clone side effects: [3](#0-2) 

Because `remote` is attacker-served content (any public git host, a fork, or an untrusted CI branch that a `git_repository` rule fetches), and `init_submodules`/`recursive_init_submodules` are common, ordinary configuration flags a project may enable, this is reachable without any modification of trusted root-repo Starlark — the attacker only needs to control the bytes served at the remote git URL (i.e., the repository content itself, specifically its `.gitmodules` file and its own submodule history).

### Impact Explanation
A hostile git remote (or a compromised/malicious branch fetched in CI via `git_repository`/`new_git_repository` with submodules enabled) can leverage a crafted `.gitmodules` entry pointing to a local `file://` path to read or copy local filesystem content into the build's output tree, or otherwise abuse Git's local-clone code path that upstream Git intentionally disabled by default. This is a read/write-outside-the-intended-repository primitive triggered purely by content the attacker supplies at the fetch URL, undermining Bazel's containment assumption that only the specified `remote`+`commit`/`tag`/`branch` (not arbitrary submodule targets) determine what is read from the local machine.

### Likelihood Explanation
Any consumer of `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` against a third-party or CI-untrusted remote is exposed; no special privileges, credentials, or MITM are required — only the ability to publish/serve the git content (or a PR branch a victim's CI builds). The vulnerable flag is applied unconditionally, with no way for the caller to opt out.

### Recommendation
Do not force `protocol.file.allow=always` unconditionally for submodule updates. Restore Git's default-safe behavior (or use a narrower carve-out, e.g. only allowing local file protocol for the exact directory Bazel itself created for a shallow/local optimization, not remote-declared submodule URLs), and/or explicitly reject or sandbox `file://` submodule URLs sourced from `.gitmodules` unless the user opts in.

### Proof of Concept
1. Host a Git repository `evil.git` with a `.gitmodules` file declaring a submodule with `url = file:///etc` (or any sensitive local path reachable from the build host).
2. In a `MODULE.bazel`/`WORKSPACE`, declare:
   ```
   git_repository(
       name = "dep",
       remote = "https://example.com/evil.git",
       commit = "<pinned-malicious-commit>",
       init_submodules = True,
   )
   ```
3. Run `bazel fetch @dep//...`. `git_worker.bzl`'s `update_submodules` executes `git -c protocol.file.allow=always submodule update --init --checkout --force`, which clones/hardlinks from the attacker-declared local path into the workspace, despite Git's own default protections against exactly this behavior. def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
