### Title
Order-book maker under-paid due to floor-rounding in `MarketSellAssetActuator.matchSingleOrder` - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
When a taker's market-sell order fully consumes a maker's order (the "taker == maker" and "taker > maker" branches of `matchSingleOrder`), the TRX/token amount credited to the maker is computed with `MarketUtils.multiplyAndDivide`, which always floors the division result. The maker's entire remaining sell-side balance is transferred to the taker at full (un-rounded) quantity, while the taker only pays the floored (rounded-down) proceeds to the maker. This systematically under-pays the maker relative to the price they posted, letting the taker extract value on every trade that hits this rounding edge — the same "incorrect rounding direction drains the vault/counterparty" bug class described in the referenced DODO V3 report.

### Finding Description
In `matchSingleOrder`, when the taker's demand is greater than or equal to what the maker order has remaining, the code takes the maker's *entire* `makerSellRemainQuantity` and hands it to the taker unmodified: [1](#0-0) 

but the TRX (or counter-asset) credited back to the maker is computed via floor division: [2](#0-1) 

The same pattern repeats in the "taker > maker" branch: [3](#0-2) 

Both calls go through `MarketUtils.multiplyAndDivide`, which explicitly rounds toward negative infinity (`floorDiv`) instead of rounding up: [4](#0-3) 

Per the report's rounding-direction rule, when computing "the amount of underlying tokens a user has to provide to receive a certain amount of shares" — here, the amount of TRX the taker must pay to fully buy out the maker's remaining tokens — the calculation must round **up** (favor the counterparty/vault), not down. Because it rounds down, the maker gives away its complete remaining balance (`makerSellRemainQuantity`, exact) but only receives `floor(makerSellRemainQuantity * makerBuyQuantity / makerSellQuantity)` in return — up to `makerSellQuantity - 1` proceeds units short of what the advertised price entitles them to, per matched maker order.

Note the third branch ("taker < maker", lines 440-452) is safe: there the *taker* receives the rounded amount while paying in full, so rounding favors the maker, matching the recommended direction. Only the two branches where the maker order is being fully liquidated exhibit the harmful direction.

### Impact Explanation
Any address can place a maker sell order via `MarketSellAssetActuator`/order book (an "order placer"), and any other address (an unprivileged transaction broadcaster) can craft a taker order sized to exactly or over-consume that maker order, deterministically triggering this rounding shortfall and taking value away from the maker on every fill. Because this is fully deterministic and repeatable (an attacker can create/cancel/recreate many small maker fills or coordinate maker+taker orders under different addresses they control, or simply trade against existing user orders at scale), it results in a real, unbacked, permanent loss of TRX/TRC10 token value for makers — the same class of harm ("run the vault out") described in the source report, applied to java-tron's on-chain order book counterparties instead of a lending vault.

### Likelihood Explanation
High likelihood: this code path executes on ordinary `MarketSellAssetContract` transactions, requires no special privilege, and the rounding loss occurs whenever `makerSellRemainQuantity * makerBuyQuantity` is not exactly divisible by `makerSellQuantity` — which is the common case for arbitrary user-chosen price ratios and remaining quantities. An attacker can also intentionally pick maker/taker quantities to maximize the fractional remainder (up to `makerSellQuantity - 1`) to extract the largest possible rounding profit per trade, and repeat across many trades/blocks for cumulative gain.

### Recommendation
When a maker order is being fully consumed (the branches where `makerOrderCapsule.setSellTokenQuantityRemain(0)`), round `makerBuyTokenQuantityReceive` **up** rather than down, e.g. by using a ceiling-division variant of `multiplyAndDivide` (or computing the taker's payment as `takerBuyTokenQuantityReceive`'s exact counter-value with remainder carried to the maker) so the maker never receives less than their posted price entitles them to. Any residual dust from rounding should be assigned to the maker (the party being fully filled), not silently dropped in the taker's favor.

### Proof of Concept
1. Attacker A places a maker sell order: sell 100 unit of token X for 3 unit of TRX (`makerSellQuantity=100`, `makerBuyQuantity=3`), fully funded.
2. Attacker B (or same attacker, second account) places a taker `MarketSellAssetContract` selling TRX to buy token X with a quantity that causes `makerSellRemainQuantity=100` to fully consume A's order (`matchSingleOrder`, "taker == maker" or "taker > maker" branch).
3. `makerBuyTokenQuantityReceive = MarketUtils.multiplyAndDivide(100, 3, 100) ...` — pick quantities so `100*3/100` has a fractional remainder in the underlying price ratio used by the actual code (e.g., using non-multiple ratios such as `makerSellQuantity=7`, `makerBuyQuantity=3`, `makerSellRemainQuantity=7`): `7*3/7 = 3` exactly matches here, so instead use a ratio like `makerSellQuantity=3, makerBuyQuantity=2, makerSellRemainQuantity=1`: `multiplyAndDivide(1,2,3) = floor(2/3) = 0`. Maker gives away its entire remaining 1 unit of X and receives `0` TRX back, while taker receives the 1 unit of X in full at a rounded-to-zero cost.
4. Repeating this pattern (fully filling small remainders of maker orders) lets the taker accumulate free/underpaid tokens at the makers' expense across many trades, each time the maker's counter-asset proceeds are floored to less than the fair-price amount.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
