### Title
Attachment resubmission via `PostTransaction` can flip an already-validated attachment back to "uninstantiated", causing `RPCGetAttachmentRequestHandler` to 404 a validly-committed attachment - (File: stackslib/src/net/atlas/db.rs)

### Summary
`AtlasDB::insert_uninstantiated_attachment` performs an unconditional `INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)` keyed only on `hash`, with no check of the row's current `was_instantiated` value. Any remote caller who can resubmit the exact bytes of a previously-confirmed attachment through the one production call path that reaches this function (`stackslib/src/net/api/posttransaction.rs`) can downgrade a `was_instantiated = 1` row back to `0`, causing the RPC attachment-serving path (`WHERE hash = ?1 AND was_instantiated = 1`) to stop returning that attachment.

### Finding Description
The invariant the codebase relies on is: `find_attachment` (used by `RPCGetAttachmentRequestHandler`) should return `Some` for any hash that has ever been bound to a confirmed on-chain `AttachmentInstance` and successfully downloaded/validated (i.e. `was_instantiated = 1`), for as long as that binding remains valid. `insert_uninstantiated_attachment` at [1](#0-0)  breaks this: it does not query the existing row's `was_instantiated` state before writing, it simply `INSERT OR REPLACE`s with `was_instantiated = 0` unconditionally, using `hash` as the sole conflict key.

Because `hash` is the SQL primary key and the write is content-addressed, any caller who can get raw attachment bytes into this function with a hash matching an already-instantiated row (trivially achieved by resubmitting the *same, already-public* attachment content, since content hashes are public once served) causes the previously `was_instantiated = 1` row to be silently reset to `0`. The genesis-attachment insertion path uses an explicit `was_instantiated = 1` INSERT [2](#0-1) , but there is no corresponding protective check in `insert_uninstantiated_attachment` to avoid clobbering that state.

`insert_uninstantiated_attachment` is invoked in production code from exactly one non-test call site, `stackslib/src/net/api/posttransaction.rs`, the handler for the unauthenticated `POST /v2/transactions` RPC endpoint that accepts a transaction together with an attachment payload. [3](#0-2)  This endpoint is reachable by any remote party with no RPC secret or privileged role. Submitting a transaction whose attached payload byte-for-byte matches a previously-confirmed, already `was_instantiated = 1` attachment is sufficient to trigger the downgrade — the attacker does not need a hash collision, only knowledge of the already-public content.

### Impact Explanation
The immediate effect is that `RPCGetAttachmentRequestHandler::find_attachment`'s `WHERE hash = ?1 AND was_instantiated = 1` query stops matching the row, so the node serves a 404/absent response for an attachment (e.g. a BNS zonefile) that was legitimately committed and previously resolvable. This is a state-serving/BNS mismatch: the node's served view of "which attachments are available" diverges from the validated on-chain commitment state, even though nothing about the underlying chain state changed. This matches the "attachment/BNS mismatch" High-impact category. The row is not permanently lost (content is preserved, just flagged as uninstantiated), and the Atlas re-validation logic in `download.rs` (`check_attachment_instances`, which calls `insert_instantiated_attachment` when a matching queued `AttachmentInstance` is found) can eventually re-promote it — but only if a still-queued, not-yet-checked `AttachmentInstance` exists for that hash; otherwise the downgrade persists until some other trigger re-instantiates it.

### Likelihood Explanation
Low attacker cost: the attacker needs only to know the plaintext content of an already-served attachment (which is inherently public once served over the BNS/Atlas RPC) and resubmit it through the unauthenticated `POST /v2/transactions` endpoint. No signature bypass, no privileged role, and no special peer state is required beyond ordinary RPC reachability. It is repeatable against any attachment hash the attacker has observed.

### Recommendation
In `insert_uninstantiated_attachment`, check the existing row's `was_instantiated` flag before writing, and skip (or no-op) the insert/replace if a row for that `hash` already has `was_instantiated = 1`, e.g. `INSERT INTO attachments (...) VALUES (...) ON CONFLICT(hash) DO UPDATE SET content=excluded.content, created_at=excluded.created_at WHERE was_instantiated = 0`, or perform a `SELECT was_instantiated FROM attachments WHERE hash = ?` guard inside the same transaction before executing the write.

### Proof of Concept
Rust unit test in `stackslib::net::atlas::db` (mirrors the question's proof idea):
```rust
let mut db = AtlasDB::connect_memory(AtlasConfig::default()).unwrap();
let a = Attachment::new(b"zonefile-content".to_vec());
db.insert_instantiated_attachment(&a).unwrap();
assert!(db.find_attachment(&a.hash()).unwrap().is_some()); // served
db.insert_uninstantiated_attachment(&a).unwrap();          // attacker resubmits same bytes
assert!(db.find_attachment(&a.hash()).unwrap().is_none()); // now 404 for a committed attachment
```
Network-level PoC: send a crafted `POST /v2/transactions` request through `posttransaction.rs`'s handler carrying the identical attachment bytes of a previously-instantiated attachment, then issue `GET /v2/attachments/{hash}` and observe the transition from 200 to 404 on `RPCGetAttachmentRequestHandler::find_attachment`.

```rust
    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
```
