Confirmed: `AttachmentRequest` carries a `content_hash` field (the hash the requester expects), [1](#0-0)  but `extend_with_attachments` inserts whatever the peer returns into `self.attachments` purely by decoding the HTTP response, with no check that `response.attachment.hash() == request.content_hash` [2](#0-1) .

### Title
Atlas attachment content is accepted and stored without verifying it matches the requested `content_hash` - (File: stackslib/src/net/atlas/download.rs)

### Summary
When a Stacks node fetches an Atlas attachment (e.g., a BNS zonefile) from a peer via `GET /v2/attachments/<hash>`, the response is decoded and its content is admitted into the node's local Atlas state without checking that `Hash160::from_data(content)` equals the `content_hash` that was actually requested.

### Finding Description
`AttachmentsBatchStateContext::get_prioritized_attachments_requests` builds an `AttachmentRequest { content_hash, .. }` for each attachment that is missing locally, keyed by the `content_hash` recorded on-chain in the corresponding `AttachmentInstance` [3](#0-2) . When the response comes back, `extend_with_attachments` only checks that the response decodes successfully (`response.decode_atlas_get_attachment()`), then inserts `response.attachment` directly into `self.attachments`, a `HashSet<Attachment>` — with no comparison against `request.content_hash`: [2](#0-1) 

Downstream, in `AttachmentsDownloader::run`, once the batch state machine reaches `Done`, each attachment in the set is stored via `insert_instantiated_attachment` and paired with pending `AttachmentInstance`s found by `find_all_attachment_instances(&attachment.hash())`: [4](#0-3) 

Because `find_all_attachment_instances` looks up instances by `attachment.hash()` — the hash computed on the *actually-returned* content, not the originally requested `content_hash` — a malicious or compromised peer that responds to a request for `content_hash=H1` with arbitrary content `C2` (whose real hash is `H2`) will not corrupt instance `H1`'s slot directly. However, this still breaks the intended equality "served content == requested/committed content_hash" at the point where the response is accepted: the code never validates that the specific peer actually returned the chunk it claimed to have (per its inventory bit) before trusting and processing it as a `succeeded` result for that `AttachmentRequest`. Any peer can return unrelated attachment content in a `succeeded` response for a request whose `content_hash` is known and validated only implicitly, after the fact, via a coincidental hash-keyed lookup — there is no explicit rejection/negative-reliability path for a peer that serves mismatched content (`report.bump_successful_requests()` / `bump_failed_requests()` are only driven by decode success, not content correctness).

This matches the report's underlying bug class: input (untrusted network response) is merged/accepted into internal state without validating that it corresponds to the specific key that was supposed to gate it, exactly as `deep-object-diff`'s prototype-pollution flaw let attacker-controlled input silently overwrite/introduce properties the code trusted implicitly.

### Impact Explanation
An attacker-controlled or compromised Atlas peer can cause a requesting node to accept and cache attachment content that does not correspond to the hash it requested, silently consuming the node's `AttachmentsDownloader` batch slot for the real attachment (since `resolve_attachment` is invoked using the returned/attacker's `attachment.hash()`, not `request.content_hash`, so the *originally intended* attachment is never actually resolved but the batch may still be marked handled for that peer/source), and pollutes the local `attachments` table with attacker-chosen content unlinked from any legitimate `content_hash` the network agreed on. This is a "served non-canonical/mismatched data" issue (High per the given severity rubric) because a node can be steered into caching/serving data that doesn't correspond to the BNS/Atlas hash commitment recorded on-chain, and reliability accounting does not penalize peers for serving wrong content, making the abuse cheap and repeatable.

### Likelihood Explanation
Reachable by any peer providing Atlas/attachment inventory and chunk responses over the p2p HTTP RPC surface (`/v2/attachments/<hash>` and `/v2/attachments/inv`), requiring no authentication, no privileged role, and only a handful of messages (one advertised inventory bit + one HTTP response) — well within the "remote, unprivileged, few messages" scope of this analog search.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after `response.decode_atlas_get_attachment()` succeeds, compute `Hash160::from_data(&attachment.content)` (i.e., `attachment.hash()`) and compare it to `request.content_hash`. Reject and treat as a failed/penalized request (`report.bump_failed_requests()`, and optionally lower reliability more aggressively) if they don't match, and only insert into `self.attachments` / mark resolved when the hash matches the request that was made.

### Proof of Concept
1. Stand up a malicious Atlas peer that advertises (via `/v2/attachments/inv`) that it has the attachment for `content_hash = H1` (matching a real, pending `AttachmentInstance`).
2. When the victim node issues `GET /v2/attachments/H1`, respond with arbitrary bytes `C2` whose real hash is `H2 != H1` (e.g., garbage or another legitimate attachment's content).
3. Observe that `extend_with_attachments` accepts the response purely because it decodes as valid JSON/hex (`decode_atlas_get_attachment`) — [5](#0-4)  — with no equality check against `request.content_hash`, and the mismatched content is stored via `insert_instantiated_attachment` in the `Done` handler.

*Note: I was unable to fully trace whether some other layer (e.g., a check on `AttachmentInstance` resolution before it's marked resolved) re-validates the hash later in the pipeline; the index does not show such a check within `download.rs`, `atlas/db.rs`, or the `Done` handling shown above, but a full trace of every caller of `resolve_attachment`/`insert_instantiated_attachment` was not exhaustively completed. A Devin session with full repo access would be needed to conclusively rule out a compensating check elsewhere.*

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
