### Title
Protocol fee on NEP-245/IMT `TokenDiff` intents can be bypassed by splitting a large negative delta into many `amount == 1` legs - (`contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` waives the protocol fee for `Nep245`/`Imt` tokens whenever the *per-intent* `amount == 1`, and `TokenDiff::execute_intent` computes and collects the fee independently for each `TokenDiff` intent it processes, with no aggregation across intents in the same batch. An unprivileged signer can therefore replace a single `TokenDiff{diff:{mt_token_id:-N}}` intent (which pays `Pips::fee_ceil(N)`) with `N` intents each carrying `delta = -1` on the same token, each hitting the zero-fee branch, so the aggregate outflow of `N` units pays zero fee.

### Finding Description
The binding the fee mechanism is supposed to satisfy is: `fee_collector` balance delta for token `T` == `Pips::fee_ceil(fee, total_negative_exposure_to_T_in_batch)`. In the actual implementation this equality is evaluated per `TokenDiff` intent, not per batch: [1](#0-0) 

and the exemption logic is: [2](#0-1) 

`token_fee` only sees the single-leg `amount = delta.unsigned_abs()` of the `TokenDiff` currently being executed. If `amount > 1` for `Nep245`/`Imt`, the normal `fee` is applied; if `amount == 1` (or any NFT), `Pips::ZERO` is returned. There is no place in `execute_intent`, `DefuseIntents::execute_intent`, or the `TransferMatcher`/`Deltas` state layer (`contracts/defuse/core/src/engine/state/deltas.rs`) that aggregates negative exposure to the same `TokenId` across multiple `TokenDiff` intents (whether inside one `DefuseIntents` payload's `Vec<Intent>` or across multiple signed payloads in a `MultiPayload`) before computing the fee — each `TokenDiff::execute_intent` call is fee-independent of every other.

Exploit: the attacker (or a cooperating counterparty pair of attacker-controlled accounts, both of which the attacker profile is allowed to control) signs `N` `TokenDiff` intents, each `{diff: {mt_token_id: -1}}`, matched by corresponding `+1` legs from a counterparty (which can be the attacker's own second account, since attackers may "hold their own Verifier balances"). Every leg independently satisfies `amount == 1`, so `token_fee` returns `Pips::ZERO` and `fee_ceil(1) == 0` for every leg. The batch's `TransferMatcher::finalize` invariant (sum of deltas per token == 0 across the batch) is satisfied normally since the netting check is agnostic to fees and only balances deposits/withdrawals — it does not re-derive or enforce the fee amount. The end state is that `N` units of a valuable NEP-245/IMT token moved with zero protocol fee, whereas an equivalent single `TokenDiff{delta:-N}` intent would have paid `Pips::fee_ceil(fee, N)`.

None of the listed guards (`MultiPayload::verify`, nonce/salt checks, `TransferMatcher::finalize`, `checked_*` arithmetic) address this because they validate signature/nonce/balance-conservation, not fee correctness; fee computation happens purely inside `TokenDiff::execute_intent` per intent, before `Deltas`/`TransferMatcher` ever runs.

### Impact Explanation
The `fee_collector` account under-collects protocol fees on `Nep245`/`Imt` token trades whenever a large trade is split into unit legs, which is unrestricted for any unprivileged signer to do at will and is fully repeatable across tokens, accounts, and batches at negligible cost (each leg only requires balance sufficient for `-1`). This matches the explicitly listed Critical impact category "protocol fees bypassed... on NEP-245/IMT assets" from the rubric, since the aggregate value moved through the Verifier no longer pays the fee the protocol design intends to charge on it.

### Likelihood Explanation
The attacker only needs two accounts they control (or one counterparty willing to match unit legs) and enough of the target token to perform the `-1` legs `N` times; no privileged role, relayer key, or victim key is required. The action is fully reproducible in a single transaction (`DefuseIntents` with `N` `TokenDiff` intents in its `intents: Vec<Intent>`) or spread across a `MultiPayload`, so likelihood is high and cost is essentially only gas/storage for `N` intents (out-of-scope resource-exhaustion concerns aside, the fee bypass itself is the in-scope finding).

### Recommendation
Aggregate the negative exposure to each `TokenId` across all `TokenDiff` (and any other fee-relevant) intents within the execution scope (at minimum within one `DefuseIntents`/`MultiPayload` batch, ideally cumulative per account/token over the batch) before applying the `amount > 1` exemption threshold in `TokenDiff::token_fee`, or remove/rework the unit-amount fee exemption for `Nep245`/`Imt` so it cannot be defeated by decomposition, e.g., compute fees based on total signed exposure per token per signer in the batch rather than per individual intent leg.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (test module)
#[test]
fn fee_bypass_via_unit_legs() {
    let fee = Pips::ONE_PERCENT; // nonzero fee
    let mt = TokenId::from(Nep245TokenId::new("mt.near".parse().unwrap(), "asset1".to_string()));

    // Side A: one intent with delta = -10_000
    let fee_bulk = TokenDiff::token_fee(mt.clone(), 10_000, fee).fee_ceil(10_000);
    assert!(fee_bulk > 0);

    // Side B: 10_000 intents, each delta = -1 on the same token
    let mut fee_split_total: u128 = 0;
    for _ in 0..10_000 {
        let leg_fee = TokenDiff::token_fee(mt.clone(), 1, fee).fee_ceil(1);
        fee_split_total += leg_fee;
    }

    // Binding under test: aggregate fee should be equal regardless of decomposition.
    assert_eq!(fee_split_total, 0, "split legs pay zero fee");
    assert_ne!(
        fee_split_total, fee_bulk,
        "fee bypass: {fee_split_total} (split) != {fee_bulk} (bulk) for identical total exposure to token {mt}"
    );
}
```
This directly demonstrates, using existing `TokenDiff::token_fee`/`fee_ceil` APIs, that fee collected diverges between the two economically equivalent scenarios, confirming the bypass without needing a full sandbox run (the sandbox/`near-workspaces` version would additionally execute `N` real `TokenDiff` intents through `Engine`/`Deltas` and assert `fee_collector`'s post-batch MT balance is `0` instead of `fee_ceil(N)`).
