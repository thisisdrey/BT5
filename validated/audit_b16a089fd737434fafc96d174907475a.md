### Title
Fee bypass on `Imt` (and `Nep245`) transfers by splitting a large `TokenDiff` into unit legs of `|delta| == 1` - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` waives protocol fees whenever the per-intent `amount` for an `Imt` (or `Nep245`) token is `<= 1`, but the guard is evaluated per individual `TokenDiff` intent rather than on the aggregate economic transfer. An unprivileged signer who controls both the source and destination accounts can split a transfer of `N` units of the same `Imt` token into `N` separate `TokenDiff` intents of `delta = -1`/`+1`, each of which reports `amount == 1` and pays `Pips::ZERO`, so the total fee collected for a net transfer of magnitude `N` is `0` instead of `Pips::fee_ceil(fee, N)`.

### Finding Description
The intended binding is: for a signer moving a net `N` units of a given `TokenId` through `TokenDiff` intents in a batch, `total_fee_collected(token_id) == Pips::fee_ceil(fee, N)` when the token type is fee-bearing for that magnitude.

The actual code in `TokenDiff::execute_intent` computes the fee independently, once per `(signer, token_id)` pair *per intent*, using only that intent's own `delta`: [1](#0-0) 

and `TokenDiff::token_fee` special-cases `Nep245`/`Imt` when the *per-intent* `amount <= 1`: [2](#0-1) 

Because a `TokenDiff.diff` is a `BTreeMap<TokenId, i128>` (one delta per token id per intent), an attacker cannot put `delta = -N` in a single map entry without triggering `amount > 1`. But nothing prevents signing `N` separate `TokenDiff` intents, each with `delta = -1` on the same `Imt` token id, inside one or more `MultiPayload`s. The engine only enforces that the *sum* of all deltas across the whole batch nets to zero per token via `TransferMatcher::finalize` (`contracts/defuse/core/src/engine/state/deltas.rs`); it does not require that fees be computed on the aggregate: [3](#0-2) 

Exploit flow: attacker controls account `A` (holding `N` units of `imt:minter:token1`) and account `B` (destination, also attacker-controlled or colluding). `A` signs one `DefusePayload` containing `N` `TokenDiff` intents, each `{diff: {imt_token: -1}}`. `B` signs one `DefusePayload` containing `N` `TokenDiff` intents, each `{diff: {imt_token: +1}}`. Both payloads are submitted together to `execute_intents`. Each of the `2N` intents individually satisfies `amount == 1`, so `TokenDiff::token_fee` returns `Pips::ZERO` for every one of them; `fees_collected` stays empty and no balance is credited to `fee_collector`. Yet the net economic transfer is `N` units of the token, which — if submitted as a single `-N`/`+N` pair — would have triggered `TokenIdType::Imt if amount > 1` and charged `fee.fee_ceil(N) > 0`.

No existing guard (`MultiPayload::verify`, `has_public_key`, `verify_intent_nonce`, `TransferMatcher::finalize`, `#[private]`/`#[pause]`, `access_control_any`) inspects the aggregate `amount` across multiple intents/entries for the same token id — they only validate signatures, nonces, and that deltas net to zero, none of which is violated by this split. The `Nep245` and `Imt` variants share the exact same `if amount > 1` guard, so the split-into-unit-legs bypass that is understood to affect `Nep245` applies identically and mechanically to `Imt`.

### Impact Explanation
This under-collects protocol fees that would otherwise be credited to `fee_collector`: for any `Imt` (or `Nep245`) token, an attacker can move an arbitrarily large quantity `N` of that token between two accounts they control while paying `0` fee instead of `fee.fee_ceil(N)`. This is repeatable across any `Imt`/`Nep245` token id, any account pair, and any batch, at no cost beyond the gas for `N` intents (well within a normal `execute_intents` call). This falls under "protocol fees bypassed or over-collected" in the Critical category, since it is a strict, unauthorized deviation from the fee accounting invariant that benefits the attacker (fee not paid) at the expense of `fee_collector`.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only an `Imt`-typed (or `Nep245`) token balance under their own account and the ability to sign standard `DefusePayload`s with multiple `TokenDiff` intents — both available to any unprivileged signer. No role, relayer key, or victim key is required; the attacker can act as both counterparties (self-dealing) since `TransferMatcher` only requires deltas to net to zero, not that the two sides be distinct unrelated parties with economic intent. The attack is trivially repeatable and scales linearly in gas with `N`.

### Recommendation
Compute the fee-exemption threshold on the aggregate magnitude actually transferred for a given `(token_id)` within a batch (or disallow multiple `TokenDiff` intents against the same token id from the same signer/counterparty pair in a single execution), rather than on the per-intent `delta`. Alternatively, always apply the fee formula to `Nep245`/`Imt` tokens regardless of `amount`, or track and fee cumulative deltas per token id across the whole `Engine` execution (e.g., aggregate in `Deltas`/`TransferMatcher` before fee calculation) so `total_fee_collected(token_id) == Pips::fee_ceil(fee, |net_delta|)` holds for the true batch-level transfer.

### Proof of Concept
`cargo test` (near-workspaces sandbox, following the pattern in `tests/src/tests/defuse/intents/token_diff.rs`):
1. Deploy the `defuse` contract with `fee = Pips::ONE_PERCENT` (non-zero) and a distinct `fee_collector` account.
2. Mint/deposit `N = 100` units of an `Imt` token (`imt:minter.near:token1`) to account `A`; create account `B` with zero balance of that token.
3. Baseline check: have `A` sign a single `TokenDiff{diff: {imt_token: -100}}` matched by `B` signing `TokenDiff{diff: {imt_token: +100}}`, call `execute_intents`, and assert `fee_collector` balance for `imt_token` equals `Pips::ONE_PERCENT.fee_ceil(100) > 0`.
4. Exploit check: reset state; have `A` sign one payload containing 100 `TokenDiff` intents each `{diff: {imt_token: -1}}`, and `B` sign one payload containing 100 `TokenDiff` intents each `{diff: {imt_token: +1}}`; call `execute_intents(&[A_payload, B_payload])`.
5. Assert: `A`'s balance decreased by 100, `B`'s balance increased by 100, but `fee_collector`'s balance for `imt_token` is unchanged (`0` fee collected), demonstrating `Σ token_fee(Imt, 1, fee).fee_ceil(1) (=0) != Pips::fee_ceil(fee, 100) (>0)` for the same net transfer magnitude.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
