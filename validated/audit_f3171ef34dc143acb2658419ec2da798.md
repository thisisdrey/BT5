### Title
DeleteAccount does not cancel outstanding postponed callback receipts, allowing a stale self-callback to run AddKey/DeployContract with full authority against a later-recreated account of the same name - ([File: runtime/runtime/src/actions.rs], [File: runtime/runtime/src/lib.rs], [File: core/store/src/utils/mod.rs])

### Summary
`action_delete_account` deletes an `Account`, its code, keys and contract data, but never touches the separate `PostponedReceiptId` / `PendingDataCount` / postponed-`ActionReceipt` trie entries that key a not-yet-arrived callback to that account name. When the account is later recreated under the same name and the slow external `Data` receipt finally arrives, the runtime looks the postponed receipt up purely by account-name string, loads it, and executes it against whatever account currently exists there, granting it full "signer-is-receiver" authority because `actor_id == account_id` is a name-based, not identity/incarnation-based, check.

### Finding Description
A standard async callback pattern works like this: contract `A` runs a `FunctionCall` that does `promise_create(other_contract, ...).then(self, AddKey/DeployContract ...)`. All receipts created by this batch, including the callback, get `predecessor_id = A` (the account executing the batch) [1](#0-0) . The callback receipt B (`receiver_id == predecessor_id == A`) has an `input_data_id` pointing at `other_contract`'s eventual response, so it is stored as a **postponed receipt** keyed only by `(receiver_id=A, receipt_id)`/`(receiver_id=A, data_id)` [2](#0-1) .

`action_delete_account` removes the `Account` object, code, access keys, gas-key nonces and contract data via `remove_account`, but that function only clears those specific trie namespaces — it never removes `PostponedReceiptId`, `PendingDataCount`, or the postponed `ActionReceipt` itself: [3](#0-2) [4](#0-3) . There is also no check in `check_actor_permissions`/`action_delete_account` that rejects deletion while a postponed/pending callback exists for the account — only staking lock is checked [5](#0-4) .

`CreateAccount` (`action_create_account`) likewise starts a fresh `Account` with zero balance/`AccountContract::None` but does not purge any leftover `PostponedReceiptId`/`PendingDataCount`/postponed-receipt state for that name [6](#0-5) .

When `other_contract`'s `Data` receipt eventually arrives, the runtime looks up the postponed receipt purely by `(receiver_id, data_id)` string keys, decrements the pending count, and once it reaches zero fetches and executes the stored receipt B via `apply_action_receipt` against whichever `Account` object `get_account` currently returns for that name [7](#0-6) [8](#0-7) . Inside `apply_action_receipt`, `actor_id` is set from the immutable, previously-serialized `receipt.predecessor_id()` (which is `A`) [8](#0-7) , and `check_actor_permissions` grants full authority for `AddKey`/`DeployContract`/`Stake`/`DeleteKey` whenever `actor_id == account_id` as a plain string comparison — with no concept of account "incarnation" [9](#0-8) . Since both `actor_id` and `account_id` are literally `"A"`, the check passes even though the `Account` object is a completely different, freshly created incarnation.

### Impact Explanation
This breaks authorization exactness: an `AddKey(pubkey)`/`DeployContract` action baked into a stale callback executes with full owner authority against a name that may now belong to a different (in intent, if not always in signer identity) account state, without any current transaction from whoever controls the new account authorizing it. The most concrete exploitation path (avoiding social engineering) is self-directed but still yields authorization escalation across the promise/account lifecycle: the original account owner arranges a self-callback that adds a key or redeploys code, deletes the account (satisfying `actor_id==account_id` self-authorization trivially), transfers/repurposes/sells the freed name (top-level names over `min_allowed_top_level_account_length` characters or subaccounts under an owner they still control can be freely recreated by any predecessor per `action_create_account`'s rules), and the stale callback later silently plants a full-access key or contract on the new incarnation, enabling later fund theft or persistent backdoor access. This matches the "authorization escalation across accounts or promises" and, downstream, "theft of user funds" bounty categories.

### Likelihood Explanation
- No privileged access is required: any account owner can author the promise-then-delete-recreate pattern with a signed transaction and their own access key.
- The intermediate `other_contract` does not need to be malicious or attacker-controlled — any normal cross-contract await creates the postponed-receipt residue; a network-latency delay before the response arrives is enough.
- The bug is 100% deterministic and repeatable: `remove_account` (core/store) and `action_create_account` never touch the postponed-receipt trie namespaces, so the stale receipt persists indefinitely until its input data arrives.
- The main constraint is that the account name must be reused (self-owned subaccounts are trivially reusable by the same predecessor; long top-level names >`min_allowed_top_level_account_length` chars can be created by any predecessor without registrar approval), so cross-principal exploitation requires the victim to independently choose/reuse that specific name, while same-principal exploitation (attacker weaponizing their own future incarnation, e.g. before selling/handing over the account) is fully within an unprivileged attacker's control.

### Recommendation
- On `DeleteAccount`, scan for and purge any outstanding `PostponedReceiptId`, `PendingDataCount`, and postponed `ActionReceipt`/`PromiseYield` entries keyed to `account_id`, or explicitly refuse to delete an account that still has such pending state.
- Alternatively, bind postponed receipts and pending-data counters to an account "incarnation" identifier (e.g. a monotonically increasing generation number stored per account, bumped on every `CreateAccount`), and check that the receipt's recorded incarnation matches the current one before honoring `apply_action_receipt`'s permission grant; otherwise fail/refund the postponed receipt instead of executing it against a mismatched incarnation.

### Proof of Concept
Integration/test-loop test plan (analogous to `runtime/runtime/tests/test_async_calls.rs::test_single_promise_with_callback_batch` and `test-loop-tests/src/tests/create_delete_account.rs::test_instant_delete_account`):
1. Deploy `rs_contract` to account `A` (a subaccount owned by the test signer, e.g. `child.alice.near`, so `A` can be freely deleted and recreated by `alice.near`).
2. From `A`, call `call_promise` to build `promise_create(other_contract, "slow_method").then(A, action_add_key_with_full_access(attacker_pubkey))`, where `other_contract` is a separate, non-attacker-controlled contract intentionally holding off its response (simulate via a manual receipt injection or a contract that yields without resolving in the same chunk).
3. While the callback receipt to `A` is postponed (verify via chunk apply results / state that a `PostponedReceiptId`/`PendingDataCount` entry exists for `A`), submit a `DeleteAccount(beneficiary_id=alice.near)` transaction signed by `A`'s key. Assert it succeeds.
4. From `alice.near`, submit `CreateAccount` + `AddKey(victim_pubkey)` to recreate `A` fresh. Assert the account now exists with only `victim_pubkey`.
5. Deliver the delayed `Data` receipt from `other_contract` (complete the external call). Assert that the previously postponed `AddKey(attacker_pubkey, FullAccess)` action executes successfully against the recreated `A`, and that `attacker_pubkey` now has full access to `A` even though it was never added by any transaction signed after `A`'s recreation — demonstrating the authorization-exactness violation.

        &self,
        receipt: &Receipt,
        receipt_sink: &mut ReceiptSink,
        instant_receipts: &mut VecDeque<Receipt>,
        validator_proposals: &mut Vec<ValidatorStake>,
        state_update: &mut TrieUpdate,
        apply_state: &ApplyState,
        epoch_info_provider: &dyn EpochInfoProvider,
        pipeline_manager: &ReceiptPreparationPipeline,
        stats: &mut ChunkApplyStatsV1,
        account_id: &AccountId,
        action_receipt: VersionedActionReceipt<'_>,
        receipt_to_tx: &mut Vec<(CryptoHash, ReceiptToTxInfo)>,
    ) -> Result<Option<ExecutionOutcomeWithId>, RuntimeError> {
        let mut pending_data_count: u32 = 0;
        for data_id in action_receipt.input_data_ids() {
            if !has_received_data(state_update, account_id, *data_id)? {
                pending_data_count += 1;
                // The data for a given data_id is not available, so we save a link to this
                // receipt_id for the pending data_id into the state.
                set(
                    state_update,
                    TrieKey::PostponedReceiptId {
                        receiver_id: account_id.clone(),
                        data_id: *data_id,
                    },
                    receipt.receipt_id(),
                )
            }
        }

        if pending_data_count == 0 {
            // All input data is available. Executing the receipt. It will cleanup
            // input data from the state.
            return self
                .apply_action_receipt(
                    state_update,
                    apply_state,
                    pipeline_manager,
                    receipt,
                    receipt_sink,
                    instant_receipts,
                    validator_proposals,
                    stats,
                    epoch_info_provider,
                    receipt_to_tx,
                )
                .map(Some);
        } else {
            // Not all input data is available now.
            // Save the counter for the number of pending input data items into the state.
            set(
                state_update,
                TrieKey::PendingDataCount {
                    receiver_id: account_id.clone(),
                    receipt_id: *receipt.receipt_id(),
                },
                &pending_data_count,
            );
            // Save the receipt itself into the state.
            set_postponed_receipt(state_update, receipt);

    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {

        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {

                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),

                    account_id: account_id.clone(),

            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
