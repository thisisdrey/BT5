### Title
Missing slippage/minimum-output protection in `ExchangeInjectActuator` and `ExchangeWithdrawActuator` enables sandwich-style value extraction from TRX/TRC10 AMM liquidity providers - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The Ajna report describes a lender who deposits liquidity without any way to bound the price/fee state the deposit will actually execute against, so an intervening transaction can shift that state and cause the deposit to settle unfavorably. java-tron's on-chain bancor-style Exchange (TRX/TRC10 constant-product-like pools) has the exact analog: `ExchangeTransactionContract` (a swap) carries an `expected` field that is checked against the value computed at execution time [1](#0-0) , but the two liquidity-provider operations, `ExchangeInjectContract` (deposit into the pool) and `ExchangeWithdrawContract` (withdraw from the pool), have no equivalent bound at all. The paired "other token" amount for these two operations is computed purely from the pool's current on-chain balances at execution time [2](#0-1) [3](#0-2) , with no user-supplied minimum/maximum tolerance parameter to reject unfavorable execution.

### Finding Description
`ExchangeInjectActuator.execute()`/`doValidate()` take the injecting token's `quant` and derive `anotherTokenQuant` proportionally from whatever `firstTokenBalance`/`secondTokenBalance` happen to be in the `ExchangeCapsule` at the moment the transaction actually executes: `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` (or the symmetric case) [2](#0-1) . This ratio is exactly the pool's spot price, i.e. the AMM analog of the Ajna LUP that the original report is about. The same pattern exists in `ExchangeWithdrawActuator.execute()`, which computes the amount of the other token to return to the withdrawer from the current pool balances [4](#0-3) .

Neither `ExchangeInjectContract` nor `ExchangeWithdrawContract` carries any "expected"/minimum-output-style field, unlike `ExchangeTransactionContract`, which explicitly has `expected` and enforces `anotherTokenQuant >= tokenExpected` in validation [1](#0-0) . This confirms the protocol authors were aware slippage protection was needed for one operation type on this AMM but omitted it for the liquidity add/remove operations that touch the same pool state and same spot price.

Because any account holding TRX or the relevant TRC10 token can broadcast `ExchangeInjectContract`/`ExchangeWithdrawContract` unprivileged, and the pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be moved arbitrarily by any other account broadcasting an `ExchangeTransactionContract` swap beforehand, an attacker who observes a pending inject/withdraw transaction can:
1. Front-run it with a swap (`ExchangeTransactionContract`) that shifts the pool ratio unfavorably for the victim's pending inject/withdraw.
2. Let the victim's inject/withdraw execute at that skewed ratio, causing the victim to receive fewer tokens (withdraw) or contribute more value than intended relative to the received `anotherTokenQuant` (inject).
3. Back-run with a reverse swap to restore the ratio and capture the difference, i.e., a classic sandwich attack against an AMM liquidity operation, mirroring the "malicious lender front-runs to move LUP" scenario in the Ajna report.

### Impact Explanation
This allows unauthorized extraction of value from liquidity providers interacting with the on-chain TRX/TRC10 Exchange feature via ordinary, unprivileged transactions - no special role or node access needed, only normal transaction broadcasting and knowledge of mempool contents. The victim's resulting `anotherTokenQuant` (for inject, the amount debited from their balance; for withdraw, the amount credited to their balance) can diverge materially from what they expected when constructing/signing the transaction, resulting in theft of value comparable to the Ajna "deposit fee/slippage" impact that was judged Medium.

### Likelihood Explanation
Exploitability only requires observing a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the mempool and being able to submit a swap transaction that lands before it (and optionally one after), which is standard MEV/front-running capability available to any network participant, not a privileged actor. The lack of any user-configurable bound makes every inject/withdraw transaction unconditionally exposed.

### Recommendation
Add an `expected`-style field (e.g., minimum acceptable `anotherTokenQuant` for inject, minimum acceptable `anotherTokenQuant`/`tokenQuant` for withdraw, or a maximum-acceptable-input equivalent) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and validate it inside `ExchangeInjectActuator.doValidate()` / `ExchangeWithdrawActuator.doValidate()` analogous to the existing check in `ExchangeTransactionActuator.doValidate()` [1](#0-0) , rejecting the transaction if the pool ratio at execution time falls outside the caller's specified tolerance.

### Proof of Concept
1. Attacker observes victim's pending `ExchangeInjectContract` (deposit `tokenQuant` of `firstTokenID`) in the mempool.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of `secondTokenID` for `firstTokenID`, shifting `firstTokenBalance` down and `secondTokenBalance` up, which increases the effective `anotherTokenQuant` computed for the same `tokenQuant` in `ExchangeInjectActuator.execute()` (line 73-74/79-80 ratio calc) [5](#0-4) .
3. Victim's inject transaction executes, debiting more `secondTokenID` from the victim's account than intended relative to the pool's pre-manipulation ratio, since there is no floor/ceiling check on `anotherTokenQuant`.
4. Attacker submits a reverse `ExchangeTransactionContract` to restore the original ratio and realize the price difference as profit, completing a sandwich attack, with no validation in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` able to detect or reject the manipulated ratio.
