### Title
Missing upper-bound check on `POST /v2/mempool/query` body before `MemPoolSyncData::consensus_deserialize` - (File: stackslib/src/net/api/postmempoolquery.rs)

### Summary
`RPCMempoolQueryRequestHandler::try_parse_request` only rejects a zero-length body; it has no check equivalent to the `preamble.get_content_length() > MAX_MESSAGE_LEN` guards used in `postblock_v3.rs` and `poststackerdbchunk.rs` before invoking `MemPoolSyncData::consensus_deserialize`. This endpoint has no auth field at all, so it is reachable by any unprivileged peer that can open the RPC port.

### Finding Description
`try_parse_request` in `stackslib/src/net/api/postmempoolquery.rs` (lines 234-255) does:
```rust
if preamble.get_content_length() == 0 {
    return Err(...);
}
let mut body_ptr = body;
let mempool_body = MemPoolSyncData::consensus_deserialize(&mut body_ptr)?;
``` [1](#0-0) 

There is no comparison of `preamble.get_content_length()` (or `body.len()`) against `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN` prior to deserialization, unlike the pattern used in the sibling handlers referenced in the question. The handler struct also has no `self.auth` field, confirming the endpoint is unauthenticated. [2](#0-1) 

I traced `MemPoolSyncData` to `stackslib/src/core/mempool.rs`, where its `StacksMessageCodec`/`consensus_deserialize` implementation lives, but I was not able to fully read its body content (Bloom-filter/seed-list length handling) within the available tool budget to confirm whether it uses an attacker-controlled length prefix to call `Vec::with_capacity(len)`/similar pre-allocation before validating that many bytes remain in `body`. This is the crux of the claimed vulnerability and I could not conclusively verify it from the code I was able to inspect.

### Impact Explanation
If `MemPoolSyncData::consensus_deserialize` (or the `BloomFilter`/`BloomNodeHasher` codec it depends on) pre-allocates buffers sized directly from an untrusted length field before consuming/validating that many bytes are actually present in `body`, a single short POST request with a crafted, oversized length field could trigger a large allocation (potential OOM) or a read past `body`'s bounds. Given the endpoint is unauthenticated and has no `MAX_MESSAGE_LEN` ceiling, this would be a remotely reachable, unauthenticated, single-message DoS — matching the "Critical" category if confirmed.

### Likelihood Explanation
Preconditions are minimal: the node's RPC port must be reachable, which is the normal operating condition; no secret, peer key, or privileged role is needed since the handler has no `self.auth` gate. The missing `MAX_MESSAGE_LEN` check in `try_parse_request` is confirmed directly from the code. The remaining and decisive question — whether the inner `MemPoolSyncData`/`BloomFilter` codec actually performs unbounded pre-allocation from an untrusted length field before validating against remaining bytes — could not be verified in this session due to not being able to inspect `stackslib/src/core/mempool.rs`'s codec implementation in time.

### Recommendation
Add an explicit content-length ceiling in `try_parse_request`, mirroring `postblock_v3.rs`/`poststackerdbchunk.rs`:
```rust
if preamble.get_content_length() == 0 {
    return Err(Error::DecodeError("Invalid Http request: expected nonzero body length".to_string()));
}
if preamble.get_content_length() as u32 > MAX_MESSAGE_LEN {
    return Err(Error::DecodeError("Invalid Http request: body too long".to_string()));
}
```
Additionally, audit `MemPoolSyncData`'s codec (and any `BloomFilter`/`Vec<TxTag>` deserialization it depends on) in `stackslib/src/core/mempool.rs` to ensure any length-prefixed collection allocation is capped (e.g., via `bounded_read`/checked capacity against remaining reader bytes) rather than trusting the wire-supplied count directly.

### Proof of Concept
Add a test in `stackslib/src/net/api/tests/postmempoolquery.rs`:
1. Construct a raw byte buffer representing a `MemPoolSyncData` variant (e.g., `TxTags`/`Bloom`) where the length-prefix field for the Bloom filter bit-vector or seed/tag list is set to a very large value (e.g., `u32::MAX`), but where the buffer only contains a few actual trailing bytes.
2. Build an `HttpRequestPreamble` with `Content-Length` equal to the actual (short) buffer length, and call `RPCMempoolQueryRequestHandler::try_parse_request` directly with this preamble/body.
3. Assert that the call returns a bounded `Err` (e.g., `Error::DecodeError`/`NetError` for malformed/too-short input) instead of panicking, aborting the process (OOM), or hanging — i.e., confirm `consensus_deserialize` never allocates more memory than `body.len()` can justify, and that no `MAX_MESSAGE_LEN` bound needs to be added at `try_parse_request` if the inner codec already returns immediately on insufficient bytes.

Note: this PoC's outcome depends on the internal behavior of `MemPoolSyncData::consensus_deserialize` in `stackslib/src/core/mempool.rs`, which I was unable to fully verify in this session — a background agent with full repo access should inspect that implementation directly to confirm/deny the allocation-before-validation pattern before treating this as a confirmed exploitable finding.
