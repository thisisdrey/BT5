### Title
Unbounded Dangling-Reference Accumulation in Object Pools Enables Cost-Asymmetric DoS of `FetchIntoObjectPool` - (File: `internal/git/objectpool/fetch.go`)

### Summary
An ordinary repository owner whose fork is a member of a shared object pool can cheaply generate unbounded numbers of unreachable Git objects (e.g., via repeated force-pushes/rewrites) at effectively no cost to themselves, while the shared, privileged `FetchIntoObjectPool` housekeeping path is forced to absorb ever-growing, unbounded work (a full `git fsck --dangling` scan plus creation of one `refs/dangling/$OID` reference per unreferenced object, followed by full repack) on every run — a direct structural analog of the reported "cheap-deposit, expensive-refund" cost asymmetry: cheap client-side action vs. expensive shared-infrastructure execution that other pool members (and the operator running housekeeping) must pay for.

### Finding Description
Object pools let multiple forked repositories share objects via Git alternates, established by `ObjectPool`/`FetchIntoObjectPool` [1](#0-0) . The housekeeping/update path is `FetchFromOrigin`, invoked from the `FetchIntoObjectPool` RPC handler [2](#0-1) .

`FetchFromOrigin` fetches `+refs/*:refs/remotes/origin/*` from an origin pool member into the pool without pruning stale-but-force-updated objects, and then unconditionally calls `rescueDanglingObjects`, which runs `git fsck --connectivity-only --dangling` over the *entire pool repository* and creates a `refs/dangling/$OID` reference for every unreferenced object found, before committing all of them in a single reference-transaction update [3](#0-2) [4](#0-3) .

Because objects can never be safely pruned from a pool without risking corruption of any pool member that might still reference them, the implementation intentionally keeps every unreferenced object alive forever via a dangling ref [5](#0-4) . The project's own documentation acknowledges the resulting cost blow-up: "For busy repositories, we generate loads of dangling references... Fetches into the object pool and repacking of references can thus become quite expensive." [6](#0-5) .

Critically, there is no cap on:
- the number of unreachable objects a pool member (an ordinary, unprivileged repository owner) can push/force-push into their own fork before the next `FetchIntoObjectPool` run absorbs them,
- the number of `refs/dangling/*` references created per fetch cycle, or
- the growth of the resulting `fsck`/repack workload on the shared pool, which after `FetchFromOrigin` also triggers `OptimizeRepository`, i.e. a full repack of the pool including all dangling objects with a bitmap and delta-island computation [7](#0-6) [8](#0-7) .

An unprivileged fork owner therefore can, at negligible local cost (writing garbage commits/blobs/trees to their own repo and force-updating branches so the old objects become unreachable, then triggering routine pushes that lead to `FetchIntoObjectPool` execution), continuously and cumulatively inflate the object/ref count of the *shared* pool. Every subsequent `FetchIntoObjectPool` invocation — which affects all other pool members, not just the attacker's fork — pays an ever-increasing `git fsck --dangling` scan cost, an ever-growing set of `git-update-ref` transactions for new dangling refs, and an ever more expensive `git-repack` (which must always include cruft/dangling objects for pool repositories per `EagerOptimizationStrategy.ShouldRepackObjects`, since object pools disable cruft-pack expiry and pruning) [9](#0-8) [10](#0-9) .

This maps to the reported bug class precisely: a low-privileged actor performs many cheap operations on one side (their own repository, cheap to write garbage objects) to force the shared/expensive side (the pool's `FetchIntoObjectPool`/repack handler, run centrally and relied upon by every pool member) to do disproportionate, unbounded work — a resource-limit gap in an RPC handler (`FetchIntoObjectPool`) analogous to the "unpaid refund leaves" scenario, except here it manifests as ever-growing Gitaly-side CPU/IO/storage cost and potential timeout/failure of the shared housekeeping RPC, degrading service for every other pool member.

### Impact Explanation
Repeated exploitation degrades or denies the `FetchIntoObjectPool` handler for the entire object pool, which is shared infrastructure serving all forks of a project. As dangling references and unreachable objects accumulate without bound, each fetch/repack cycle becomes slower and more resource-intensive (CPU for `fsck`, IO for repack, memory for delta computation), potentially causing RPC timeouts, backpressure/queue exhaustion in Gitaly's concurrency limiter for this RPC [11](#0-10) , and repository unavailability for legitimate pool members whose housekeeping shares the same pool object store. This is a genuine DoS-of-a-handler condition rooted in unbounded, attacker-influenced growth of `refs/dangling/*` and pool object count.

### Likelihood Explanation
Likelihood is moderate-to-high in environments where object pools/forks are used at scale: any authenticated user who can push to their own fork (a pool member) can trigger this without any special privilege, exploiting only the documented but unmitigated design tradeoff of never pruning pool objects.

### Recommendation
- Introduce a bound (rate-limit or size cap) on the number of new dangling objects/references a single pool-member fetch cycle may introduce, or amortize dangling-ref materialization so cost does not scale unboundedly with attacker-controlled garbage.
- Consider periodic, safe consolidation/compaction strategies for `refs/dangling/*` (e.g., batching or a namespace-level packed representation) instead of one loose ref per dangling object.
- Apply RPC-level cost/queue limits specifically tuned to `FetchIntoObjectPool` proportional to observed dangling-object growth, and alert/circuit-break when the ratio of dangling to reachable objects in a pool crosses a threshold.

### Proof of Concept
1. Set up a project with an object pool and at least one additional forked pool member.
2. As the owner of the fork (unprivileged w.r.t. the pool), repeatedly: write many loose objects (blobs/trees/commits) and force-update a branch so the previous objects become unreachable; repeat at high frequency and volume (cheap: local git object writes plus a force-push).
3. Allow/trigger `FetchIntoObjectPool` to run for the pool (as normally scheduled by housekeeping) via `internal/gitaly/service/objectpool/fetch_into_object_pool.go`.
4. Observe that each run's `rescueDanglingObjects` (`internal/git/objectpool/fetch.go`) must `git fsck --dangling` scan and create a new `refs/dangling/$OID` for every unreachable object accumulated so far, and that `OptimizeRepository`'s subsequent repack cost (`EagerOptimizationStrategy.ShouldRepackObjects`) grows correspondingly — with wall-clock/resource cost increasing monotonically as the attacker repeats step 2, independent of any pool-member privilege escalation.

# Object Pools

When creating forks of a repository, most of the objects for forked repository
and the repository it forked from are shared. Storing those shared objects
multiple times is a waste of disk space and also of CPU time, given that those
shared objects would have to be repacked for both repositories. To fix this
waste of resources, we use object pools, which are essentially a repository
which holds the shared objects of both repositories.

The sharing of objects for a given repository and its object pool is done via
alternate object directories which Gitaly sets up when linking a repository to
an object pool by writing the `objects/info/alternates` file.

## Lifetime of Object Pools

The lifetime of object pools is maintained via the
[ObjectPoolService](../proto/objectpool.proto), which provides various RPCs to
create and delete object pools as well as to add members to or remove members
from the pool.

## Dangling Objects

When fetching from pool members into the object pool, then any force-updated
references may cause objects in the pool to not be referenced anymore. For
normal repositories, it is perfectly fine to delete those references after a
certain time. In the context of object pools, any other member of the pool may
still use any of those unreferenced objects. Deleting them would thus
potentially cause corrupt repositories.

This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.

func (s *server) FetchIntoObjectPool(ctx context.Context, req *gitalypb.FetchIntoObjectPoolRequest) (*gitalypb.FetchIntoObjectPoolResponse, error) {
	if err := validateFetchIntoObjectPoolRequest(req); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	objectPool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		return nil, structerr.NewInvalidArgument("object pool invalid: %w", err)
	}

	origin := s.localRepoFactory.Build(req.GetOrigin())

	if err := objectPool.FetchFromOrigin(ctx, origin, func(repo *gitalypb.Repository) *localrepo.Repo {
		return s.localRepoFactory.Build(repo)
	}); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

func (o *ObjectPool) rescueDanglingObjects(ctx context.Context) (returnedErr error) {
	stderr := &bytes.Buffer{}
	fsck, err := o.Repo.Exec(ctx, gitcmd.Command{
		Name:  "fsck",
		Flags: []gitcmd.Option{gitcmd.Flag{Name: "--connectivity-only"}, gitcmd.Flag{Name: "--dangling"}},
	},
		gitcmd.WithStderr(stderr),
		gitcmd.WithSetupStdout(),
	)
	if err != nil {
		return err
	}

	updater, err := updateref.New(ctx, o.Repo, updateref.WithDisabledTransactions())
	if err != nil {
		return err
	}
	defer func() {
		if err := updater.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("cancel updater: %w", err)
		}
	}()

	if err := updater.Start(); err != nil {
		return fmt.Errorf("start reference transaction: %w", err)
	}

	objectHash, err := o.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	scanner := bufio.NewScanner(fsck)
	for scanner.Scan() {
		split := strings.SplitN(scanner.Text(), " ", 3)
		if len(split) != 3 {
			continue
		}

		if split[0] != "dangling" {
			continue
		}

		danglingObjectID, err := objectHash.FromHex(split[2])
		if err != nil {
			return fmt.Errorf("parsing object ID %q: %w", split[2], err)
		}

		ref := git.ReferenceName(danglingObjectNamespace + split[2])
		if err := updater.Create(ref, danglingObjectID); err != nil {
			return err
		}
	}

	if err := scanner.Err(); err != nil {
		return err
	}

	if err := fsck.Wait(); err != nil {
		return fmt.Errorf("git fsck: %w, stderr: %q", err, stderr.String())
	}

	return updater.Commit()

func (s HeuristicalOptimizationStrategy) ShouldPruneObjects(context.Context) (bool, PruneObjectsConfig) {
	// Pool repositories must never prune any objects, or otherwise we may corrupt members of
	// that pool if they still refer to that object.
	if s.info.IsObjectPool {
		return false, PruneObjectsConfig{}
	}

	// When we have a number of loose objects that is older than two weeks then they have
	// surpassed the grace period and may thus be pruned.
	if s.info.LooseObjects.StaleCount <= LooseObjectLimit {
		return false, PruneObjectsConfig{}
	}

	return true, PruneObjectsConfig{
		ExpireBefore: s.expireBefore,
	}
}

// ShouldRepackObjects always instructs the caller to repack objects. The strategy will always be to
// repack all objects into a single packfile. The bitmap will be written in case the repository does
// not have any alternates.
func (s EagerOptimizationStrategy) ShouldRepackObjects(ctx context.Context) (bool, config.RepackObjectsConfig) {
	cfg := config.RepackObjectsConfig{
		WriteBitmap:         len(s.info.Alternates.ObjectDirectories) == 0,
		WriteMultiPackIndex: true,
	}

	// Object pools should generally never contain unreachable objects. However, if an object
	// pool does contain unreachable objects, they should never be deleted or we could end up
	// corrupting object pool members that depend on them. To ensure this, we disable cruft
	// packs and expiration times in this context.
	//
	// However, by disabling cruft packs Git would by default explode unreachable objects into
	// loose objects. This is inefficient as these objects cannot be deltified and thus take up
	// more space. Instead, we ask git-repack(1) to append unreachable objects to the newly
	// created packfile.
	if !s.info.IsObjectPool {
		cfg.Strategy = config.RepackObjectsStrategyFullWithCruft
		cfg.CruftExpireBefore = s.expireBefore
	} else {
		cfg.Strategy = config.RepackObjectsStrategyFullWithUnreachable
	}

	return true, cfg
}

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.
