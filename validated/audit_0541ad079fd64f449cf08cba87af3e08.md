### Title
Malicious peer can send a truncated `NakamotoInv.tenures` BitVec that `merge_tenure_inv` stores without length validation, causing `has_ith_tenure` to silently report canonical tenures as absent - ([File: stackslib/src/net/inv/nakamoto.rs])

### Summary
`NakamotoTenureInv::merge_tenure_inv` stores the attacker-supplied `BitVec<2100>` from a `NakamotoInv` reply directly into `self.tenures_inv` with no check that its bit-length matches `self.reward_cycle_len` (or the expected number of sortitions in that reward cycle). `has_ith_tenure` then queries this map with `rc_tenures.get(rc_height).unwrap_or(false)`, so any `rc_height` beyond the truncated bitvec's length is silently treated as "peer does not have this tenure," even for tenures that are actually canonical.

### Finding Description
`NakamotoTenureInv::merge_tenure_inv` [1](#0-0)  unconditionally inserts the `tenure_inv: BitVec<2100>` received from a peer's `NakamotoInv` reply into `self.tenures_inv` at the requested `reward_cycle` key, performing no comparison of `tenure_inv.len()` against `self.reward_cycle_len`. This value is fed directly from `inv_data.tenures` in `getnakamotoinv_try_finish` [2](#0-1) , which is invoked whenever the local node processes a `StacksMessageType::NakamotoInv` response to its own `GetNakamotoInv` request — a message any connected remote peer can supply after receiving the request, with attacker-controlled bit-length subject only to the wire codec's `BitVec<2100>` max-bit cap.

`has_ith_tenure` then computes `rc_height` from the absolute burn height and does `rc_tenures.get(rc_height).unwrap_or(false)` [3](#0-2) . If the stored bitvec is shorter than `reward_cycle_len` (e.g., a peer sends a 1-bit or few-bit vector for a full-length reward cycle), any `rc_height` index past that truncated length falls through `BitVec::get`'s out-of-bounds path and returns `None`, which `unwrap_or(false)` converts into "tenure absent," regardless of whether the canonical chain actually has a tenure-start there. No code path validates or pads the bitvec to `reward_cycle_len` before or after `merge_tenure_inv`.

### Impact Explanation
An attacking peer answering a `GetNakamotoInv` request can cause the querying node to believe that peer lacks tenures it actually has (or that no honest tenure exists near the end of a reward cycle), degrading the local node's picture of tenure availability used to drive tenure downloads. If an attacker controls the connections the victim relies on for this reward cycle (e.g., via Sybil/multiple outbound slots or being the only currently available peer for that inventory sync), this can suppress attempts to fetch canonical tenures from those sources and stall synchronization progress near reward-cycle boundaries — matching "steering a node off the tip via false inventory" (High). This is a per-message, repeatable falsification: every `GetNakamotoInv` request the attacker answers can be re-poisoned with truncated data.

### Likelihood Explanation
The attacker only needs to run/control a peer the victim node queries via `GetNakamotoInv` (an ordinary, unprivileged, outbound-authenticated P2P connection) — no signer keys, StackerDB slots, or RPC secret required. The victim regularly issues these requests during inventory sync via `process_getnakamotoinv_begins`, so the attack surface is reachable during normal peer operation. Impact scales with how much of the victim's peer inventory the attacker controls.

### Recommendation
In `merge_tenure_inv`, validate `tenure_inv.len()` against the expected number of sortitions for `reward_cycle` (derived from `self.reward_cycle_len`, capped appropriately for the current/tip reward cycle) before storing it; reject or truncate/pad-with-unknown-state appropriately, and disconnect/NACK-penalize peers that send inconsistent lengths instead of silently accepting them.

### Proof of Concept
Rust unit test in `stackslib/src/net/inv/nakamoto.rs` tests module:
1. Construct a `NakamotoTenureInv` with `reward_cycle_len = 2100` (or the standard test reward cycle length) and `first_block_height` set to a known value.
2. Build a `BitVec<2100>` truncated to a handful of bits (e.g., length 5, all `true` in-range) and call `merge_tenure_inv(truncated_bitvec, reward_cycle)`.
3. Call `has_ith_tenure(burn_block_height)` for a `burn_block_height` mapping to `rc_height` beyond bit 5 but within the reward cycle (e.g., `rc_height = 2000`), where the schedule is known/assumed canonical.
4. Assert `has_ith_tenure` returns `false` despite no validation ever rejecting the truncated inventory, demonstrating the silent-absence bug at [4](#0-3)  combined with the unchecked store at [1](#0-0) .

    pub fn has_ith_tenure(&self, burn_block_height: u64) -> bool {
        if burn_block_height < self.first_block_height {
            return false;
        }

        let Some(reward_cycle) = PoxConstants::static_block_height_to_reward_cycle(
            burn_block_height,
            self.first_block_height,
            self.reward_cycle_len,
        ) else {
            return false;
        };

        let Some(rc_tenures) = self.tenures_inv.get(&reward_cycle) else {
            return false;
        };

        let sortition_height = burn_block_height - self.first_block_height;
        let rc_height = u16::try_from(sortition_height % self.reward_cycle_len)
            .expect("FATAL: reward cycle length exceeds u16::MAX");
        rc_tenures.get(rc_height).unwrap_or(false)
    }

    pub fn merge_tenure_inv(&mut self, tenure_inv: BitVec<2100>, reward_cycle: u64) -> bool {
        // populate the tenures bitmap to we can fit this tenures inv
        let learned = self
            .tenures_inv
            .get(&reward_cycle)
            .map(|cur_inv| cur_inv != &tenure_inv)
            .unwrap_or(true);

        self.tenures_inv.insert(reward_cycle, tenure_inv);
        self.last_updated_at = get_epoch_time_secs();
        learned
    }
