Audit Report

## Title
Staking reward payout marks era/page as claimed before verifying the value transfer to the reward destination succeeded, permanently burning rewards on transfer failure - (File: `substrate/frame/staking-async/src/pallet/impls.rs`)

## Summary
In `do_payout_stakers_by_page`, `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` is executed unconditionally before any actual currency movement occurs. [1](#0-0)  The subsequent per-account payout via `make_payout_from_provider` performs a real `T::Currency::transfer` from the era reward pot to the attacker-controllable `RewardDestination` account, and if that transfer errors, the function merely logs the error and returns `None` — no error propagates back to abort or roll back the claimed-state write. [2](#0-1)  Since `RewardDestination` is set via the permissionless `set_payee` call, and once a page is marked claimed `AlreadyClaimed` blocks any further payout attempt for that `(era, stash, page)`, a failed transfer to a poisoned destination results in permanent, unrecoverable loss of that page's reward funds for the stash and all nominators sharing that exposure page.

## Finding Description
The exploit path is exactly as described: `Eras::<T>::set_rewards_as_claimed` commits the claimed state at line 386, strictly before the exposure/reward calculations and the calls into `payout_from_provider` → `make_payout_from_provider`, which resolves the destination via `payout_account_for_dest` (honoring `RewardDestination::Account(dest_account)` verbatim, with no validation that the account can actually receive funds) and issues `T::Currency::transfer(&staker_rewards_pot, &payout_account, amount, Preservation::Expendable)`. [3](#0-2)  On transfer failure the code path returns `Option::None` and continues execution of the extrinsic, which ultimately returns `Ok(...)` with a weight-annotated `DispatchResultWithPostInfo`. [4](#0-3)  There is no rollback of `Eras::<T>::set_rewards_as_claimed`, and no retry mechanism — the next call for that `(era, stash, page)` is rejected via the `AlreadyClaimed` guard checked at line 381. [5](#0-4) 

I verified this pattern applies uniformly to validator and nominator payouts inside `payout_from_provider`, where both the validator's and each nominator's `make_payout_from_provider` calls silently discard failures and simply skip incrementing `nominator_payout_count`/emitting `Rewarded` for that account, while the page-level claimed marker set earlier remains permanently in effect. [6](#0-5) 

## Impact Explanation
This matches the "payout state must only advance after settlement succeeds atomically" pivot in the impact gate, and constitutes a permanent user-fund lock: once the page is marked claimed and an individual transfer fails, the corresponding reward amount sitting in the era reward pot for that stash/nominator becomes unclaimable via the normal payout path, since `ClaimedRewards`/paged-claim tracking has no compensating retry path in this dispatchable. The severity is bounded by the practicality of forcing a currency transfer failure to an attacker/staker chosen destination (e.g. an account that cannot accept a deposit under the configured `T::Currency` due to existential-deposit/asset-backend constraints) — this is plausible in principle for pallets using `fungible::Mutate::transfer` with real asset backends, though I could not fully verify within the available context whether the runtimes wiring `T::Currency` for `pallet-staking-async` (e.g. the parachain/asset-hub runtimes) actually admit realistic, attacker-triggerable transfer failure conditions (such as consumer-reference exhaustion or non-mintable asset backends) versus `Currency::transfer` never failing in practice for the deposit direction under those specific configurations.

## Likelihood Explanation
`set_payee` and `payout_stakers`/`payout_stakers_by_page` are both ordinary, permissionless, signed dispatchables — any staker can set an arbitrary `RewardDestination::Account`, and any third-party account can trigger the payout for any validator/era/page. No privileged actor, governance, or compromised infrastructure is required, which satisfies the "unprivileged external attacker using public extrinsics" requirement. The main residual uncertainty is solely whether a real, deployed runtime configuration for `pallet-staking-async` makes it practically possible to force `T::Currency::transfer` to fail for a chosen destination account (this determines whether the bug is merely theoretical-but-real or fully weaponizable in a live chain).

## Recommendation
Do not call `Eras::<T>::set_rewards_as_claimed` until after the payout transfer(s) for the page have been attempted and their outcome is known. Preferably, propagate `T::Currency::transfer` errors from `make_payout_from_provider` up through `payout_from_provider` and `do_payout_stakers_by_page` so the whole extrinsic (including the claimed-state write) reverts on failure, or introduce a retryable "pending"/"failed" payout state (similar to `pallet-treasury`'s async payment status tracking) instead of unconditionally advancing the claimed marker before settlement is guaranteed.

## Proof of Concept
1. A nominator/validator calls `Staking::set_payee(origin, RewardDestination::Account(poisoned_account))`, where `poisoned_account` is engineered so a `T::Currency::transfer` deposit to it fails under the runtime's actual `Currency`/`fungible` backend configuration.
2. An era completes with `Eras::<T>::get_stakers_reward(era)` populated.
3. Any signed account calls `payout_stakers_by_page(origin, validator_stash, era, page)`.
4. `do_payout_stakers_by_page` executes `Eras::<T>::set_rewards_as_claimed(era, &stash, page)` unconditionally (line 386), then calls `make_payout_from_provider` for the poisoned payee; the `T::Currency::transfer` call errors, is logged, and `None` is returned, while the extrinsic still resolves `Ok(...)`.
5. Any subsequent call to `payout_stakers_by_page` for the same `(era, stash, page)` fails with `AlreadyClaimed`, permanently preventing recovery of the unpaid reward for that page.

This should be validated with a unit test in `substrate/frame/staking-async/src/tests/payout_stakers.rs` using a mock `Currency`/`fungible` implementation that can be configured to fail transfers to a specific account, confirming that `is_rewards_claimed` becomes `true` while the funds remain in the reward pot and unrecoverable through the normal payout API.

	/// Payout stakers from an era reward pot (transfer-based, no minting).
	fn payout_from_provider(
		era: EraIndex,
		stash: &T::AccountId,
		validator_payout: BalanceOf<T>,
		exposure: &crate::PagedExposure<T::AccountId, BalanceOf<T>>,
		overview_own: BalanceOf<T>,
		total_nominator_payout: BalanceOf<T>,
	) -> u32 {
		let mut nominator_payout_count: u32 = 0;

		if let Some((amount, dest)) = Self::make_payout_from_provider(era, stash, validator_payout)
		{
			Self::deposit_event(Event::<T>::Rewarded { stash: stash.clone(), dest, amount });
		}

		let total_nominator_stake = exposure.total().saturating_sub(overview_own);
		for nominator in exposure.others().iter() {
			let nominator_exposure_part =
				Perbill::from_rational(nominator.value, total_nominator_stake);
			let nominator_reward: BalanceOf<T> =
				nominator_exposure_part.mul_floor(total_nominator_payout);

			if let Some((amount, dest)) =
				Self::make_payout_from_provider(era, &nominator.who, nominator_reward)
			{
				nominator_payout_count.saturating_inc();
				Self::deposit_event(Event::<T>::Rewarded {
					stash: nominator.who.clone(),
					dest,
					amount,
				});
			}
		}

		nominator_payout_count
	}

	/// Determine the payout account from a reward destination.
	fn payout_account_for_dest(
		stash: &T::AccountId,
		dest: &RewardDestination<T::AccountId>,
	) -> Option<T::AccountId> {
		match dest {
			RewardDestination::Stash | RewardDestination::Staked => Some(stash.clone()),
			RewardDestination::Account(ref dest_account) => Some(dest_account.clone()),
			RewardDestination::None => None,
			#[allow(deprecated)]
			RewardDestination::Controller => Self::bonded(stash),
		}
	}

	/// Make a payment to a staker from an era reward pot (transfer, not mint).
	fn make_payout_from_provider(
		era: EraIndex,
		stash: &T::AccountId,
		amount: BalanceOf<T>,
	) -> Option<(BalanceOf<T>, RewardDestination<T::AccountId>)> {
		if amount.is_zero() {
			return None;
		}

		let dest = match Self::payee(Stash(stash.clone())) {
			Some(d) => d,
			None => {
				Self::deposit_event(Event::<T>::Unexpected(UnexpectedKind::MissingPayee {
					era,
					stash: stash.clone(),
				}));
				return None;
			},
		};

		let payout_account = Self::payout_account_for_dest(stash, &dest)?;

		let staker_rewards_pot =
			T::RewardPots::pot_account(RewardPot::Era(era, RewardKind::StakerRewards));
		if let Err(e) = T::Currency::transfer(
			&staker_rewards_pot,
			&payout_account,
			amount,
			Preservation::Expendable,
		) {
			log!(
				error,
				"Failed to transfer reward from pot for era {:?}, stash {:?}: {:?}",
				era,
				stash,
				e
			);
			return None;
		}
