Based on the code reviewed, `ConnectionRateLimiter` in `streamer/src/nonblocking/connection_rate_limiter.rs` is keyed strictly by `IpAddr` via `KeyedRateLimiter<IpAddr>`, with no ASN/prefix/subnet aggregation of any kind. `register_connection` calls `self.limiter.consume_tokens(*ip, 1)` using the raw socket IP as the map key, confirmed at `connection_rate_limiter.rs:42-50`.

### Title
Per-IP connection rate limiter is trivially bypassable via IPv6 /64 address rotation - (File: streamer/src/nonblocking/connection_rate_limiter.rs)

### Summary
`ConnectionRateLimiter::register_connection` and `is_allowed` key their `TokenBucket` state solely by exact `IpAddr`, with no /64 or ASN-level aggregation for IPv6. An attacker who owns a routed IPv6 /64 (standard on most ISPs/clouds and requiring no stake) can present a fresh source address for every QUIC handshake, so `consume_tokens(ip, 1)` in `net-utils/src/token_bucket.rs` always operates on a brand-new bucket, and the per-IP `max_connections_per_ipaddr_per_min` limit never triggers for that attacker.

### Finding Description
In `streamer/src/nonblocking/quic.rs::run_server`/`setup_connection`, connections are gated by three layers: `overall_connection_rate_limiter` (global token bucket), `rate_limiter.is_allowed(&ip)` pre-accept check, and `rate_limiter.register_connection(&from.ip())` post-handshake (lines ~347-369 and 483-493). All per-IP logic funnels into `ConnectionRateLimiter` (`connection_rate_limiter.rs:7-9`), which wraps a `KeyedRateLimiter<IpAddr>` (`net-utils/src/token_bucket.rs`). The key type is the full `std::net::IpAddr`, compared for exact equality/hash — there is no `/64` truncation, no ASN grouping, nothing that treats an entire IPv6 prefix as one identity.

Since IPv6 /64 delegation is the norm for end users, cloud VMs, and residential ISPs, an attacker controls up to 2^64 distinct source addresses within their own routed prefix without needing any additional network resources, cost, or stake. Each such address, when used to open a fresh QUIC connection, hashes to a distinct `DashMap` entry in `KeyedRateLimiter`, so `current_tokens`/`consume_tokens` sees "no record" and allows the connection (`is_allowed` returns `true` when `self.limiter.current_tokens(ip)` is `None`, `connection_rate_limiter.rs:34-40`). The per-IP rate limit is thus evaded by identity churn exactly as hypothesized.

However, this per-IP limiter is only one of several admission gates. Beyond it, `overall_connection_rate_limiter` (a single global `TokenBucket`, `TOTAL_CONNECTIONS_PER_SECOND = 2500.0`, `MAX_CONNECTION_BURST = 1000`, `quic.rs:73-76,277-281`) still throttles the aggregate rate of *all* incoming connections regardless of source IP diversity. In addition, downstream QoS controllers (`SimpleQos`/`swqos` in `simple_qos.rs`/`swqos.rs`) impose separate caps such as `max_concurrent_connections`, `max_staked_connections`, and unstaked-specific connection tables — for example `SimpleQos::try_add_connection` only admits `ConnectionPeerType::Staked` connections into its table and returns `None` for `ConnectionPeerType::Unstaked` (`simple_qos.rs:310-348`), meaning unstaked connections in that QoS variant get no persistent per-connection admission slot at all beyond the initial handshake resources. So IP rotation defeats *specifically* the per-source-IP connection cap, but does not, by itself, defeat the global connection-rate cap or the per-connection-table/stake-based caps enforced afterward.

### Impact Explanation
This is a real gap between the intended invariant ("per-source connection limits cannot be evaded by identity churn") and the implementation, which is IP-exact rather than prefix-aware. The concrete effect is that the per-IP throttle (`max_connections_per_ipaddr_per_min`) is neutralized for any attacker with an IPv6 /64, allowing them to consume a disproportionate share of the QUIC handshake/connection-setup resources, `TaskTracker` slots, and `overall_connection_rate_limiter` bucket relative to a legitimate single-IP client. This matches the "unstaked client can bypass or unfairly capture QoS limits" concern in scope, but the blast radius is bounded by the global `overall_connection_rate_limiter` (max ~2500 conn/sec, burst 1000) and by whatever QoS controller is configured (which may reject all unstaked connections from persisting past the handshake). It is not an unbounded admission / full TPU starvation on its own — it degrades fairness of the per-IP layer specifically.

### Likelihood Explanation
High feasibility: IPv6 /64 delegation to a single customer/VM is standard and requires no special privilege, stake, or additional cost — the attacker only needs to bind sockets to different addresses within their own prefix, a routine `SO_BINDTODEVICE`/address-selection operation. Repeatability is trivial and deterministic, since `KeyedRateLimiter` has no cross-address correlation.

### Recommendation
Add optional /56 or /64 IPv6 prefix aggregation (and possibly ASN-based grouping) as an additional rate-limiting key layer in `ConnectionRateLimiter`, so that `KeyedRateLimiter` buckets IPv6 addresses by network prefix rather than exact host address, while still preserving per-IPv4-address keying (or use a /32-per-host for IPv4, /64-or-broader for IPv6). This should be applied alongside, not instead of, the existing exact-IP bucket, and configured via `QuicStreamerConfig`.

### Proof of Concept
```rust
// streamer/src/nonblocking/connection_rate_limiter.rs (add to test mod)
#[tokio::test]
async fn test_ipv6_64_rotation_bypasses_per_ip_limit() {
    use std::net::Ipv6Addr;
    let limiter = ConnectionRateLimiter::new(3, 3, 4);
    let base: u128 = 0x2001_0db8_0000_0001_0000_0000_0000_0000;
    let mut accepted = 0;
    // Same /64 prefix (top 64 bits fixed), rotate low 64 bits per connection.
    for i in 0..1000u128 {
        let addr = IpAddr::V6(Ipv6Addr::from(base | i));
        if limiter.register_connection(&addr) {
            accepted += 1;
        }
    }
    // Expectation if per-IP limiting were prefix-aware: accepted should be
    // capped near max_burst (3-6). Actual behavior: every distinct address
    // gets its own bucket, so accepted == 1000.
    assert!(
        accepted > 6,
        "per-/64 admission was not capped despite identical prefix: accepted={accepted}"
    );
}
```
This demonstrates that `register_connection` admits far more than `max_connections_per_ipaddr_per_min * max_burst` connections from a single routed /64 prefix, confirming the per-IP QoS limit is bypassable through address rotation, bounded only by the separate global `overall_connection_rate_limiter` and downstream QoS connection-table caps.
