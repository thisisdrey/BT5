### Title
Floating-point Bancor pricing formula in the default (non-hardened) exchange path enables value-extraction rounding exploitation - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` allow any account to trade against a two-token liquidity pool (`ExchangeCapsule`) using a Bancor-style relay-token pricing formula. The pricing math used in `ExchangeProcessor.exchange()` is computed with native Java `double` arithmetic [1](#0-0)  rather than the precision-safe `BigDecimal` implementation available in `SafeExchangeProcessor` [2](#0-1) . Which processor is used is gated entirely by the `allowHardenExchangeCalculation` dynamic property, checked via `AbstractExchangeActuator.allowHarden()` [3](#0-2)  and passed into `ExchangeCapsule.transaction()` [4](#0-3) . Unless this proposal-gated flag has been activated on the running chain, every `ExchangeTransactionContract` broadcast by an unprivileged transaction sender is priced by the legacy, floating-point formula, which is exactly the "pricing mechanism" bug class (imprecise/manipulable AMM pricing math) that caused the Indexed Finance loss cited in the report.

### Finding Description
`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` compute the constant-product-like Bancor curve using `double` values and `Math.pow` [5](#0-4) . Double-precision floating point cannot exactly represent the fractional ratios involved in high-magnitude token balances (the code even hardcodes a `1_000_000_000_000_000_000L` synthetic "relay" supply [6](#0-5) ), so the computed `buyTokenQuant` is subject to rounding/precision error that is a function of the pool's current balances and trade size. Because any account can freely call `ExchangeTransactionActuator` (buy/sell), `ExchangeInjectActuator` (add liquidity), and `ExchangeWithdrawActuator` (remove liquidity) with arbitrary quantities [7](#0-6) , an attacker can craft a sequence of inject/trade/withdraw transactions sized to specifically land on precision-error-favorable balance ratios, repeatedly extracting more of the counter-token than the true curve would allow, or forcing the recorded pool balances to drift from their true economic value over many transactions. This mirrors the Indexed Finance root cause: a pricing/weighting formula that can be steered into an unfavorable state through ordinary, permitted operations, letting an attacker repeatedly capture the resulting discrepancy at the expense of other liquidity participants. The project's own repository history acknowledges the precision problem directly — a hardened `SafeExchangeProcessor` using `BigDecimal` exists specifically to replace this exact floating-point code path [8](#0-7) , but it is only used when `allowHardenExchangeCalculation` is enabled via a network proposal [3](#0-2) .

### Impact Explanation
If the hardened flag is not active on a given java-tron network, every exchange pool (`ExchangeStore`/`ExchangeV2Store`) priced through `ExchangeProcessor` is exposed to systematic value leakage through floating point drift, which an attacker can amplify by choosing adversarial trade sizes/timings — directly analogous to the $16M loss vector in the Indexed Finance incident (manipulable pricing enabling disproportionate value extraction from a pool). This can result in permanent loss of pooled TRX/TRC-10 assets for other liquidity participants and unbacked balances in the exchange pool's recorded reserves.

### Likelihood Explanation
Reaching this code requires only broadcasting standard, permitted `ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` transactions — actions any unprivileged account can perform once an exchange pool exists — with no special privileges needed. Exploitability depends on the specific double-precision rounding behavior at chosen balance ratios and on the hardened flag being unset, which requires further off-chain verification against the deployed network's dynamic properties to confirm current exposure.

### Recommendation
Ensure `allowHardenExchangeCalculation` is (or becomes) enabled on all networks, and consider removing/deprecating the floating-point `ExchangeProcessor` code path entirely in favor of the `BigDecimal`-based `SafeExchangeProcessor`, so pricing is not conditionally vulnerable based on a governance flag.

### Proof of Concept
Not fully verifiable without live-network state (current value of `allowHardenExchangeCalculation` and quantitative precision-loss thresholds); this requires a Devin agent with test/execution access to (1) confirm whether `allowHardenExchangeCalculation` defaults to disabled on the target network, and (2) construct a sequence of `ExchangeCreateContract` → `ExchangeInjectContract`/`ExchangeTransactionContract` calls with the legacy `ExchangeProcessor` to measure exploitable rounding deltas, similar to the existing `testTransactionLegacyVsHardenedProcessorSelection` test that already demonstrates measurable divergence between legacy and hardened results [9](#0-8) .

package org.tron.core.capsule;

import java.math.BigDecimal;
import java.math.RoundingMode;
import lombok.extern.slf4j.Slf4j;
import org.tron.common.math.StrictMathWrapper;

@Slf4j(topic = "capsule")
public class SafeExchangeProcessor implements ExchangeCapsule.Processor {

  private static final BigDecimal SUPPLY = BigDecimal.valueOf(1_000_000_000_000_000_000L);

  public static final SafeExchangeProcessor INSTANCE = new SafeExchangeProcessor();

  private SafeExchangeProcessor() {

  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }

  @Test
  public void testTransactionLegacyVsHardenedProcessorSelection() throws Exception {
    // Same input produces deterministic results in both modes.
    ExchangeCapsule legacy = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 100L, 0L,
        "abc".getBytes(), "def".getBytes());
    legacy.setBalance(100_000_000L, 100_000_000L);
    long legacyResult = legacy.transaction("abc".getBytes(), 1_000_000L, true, false);

    ExchangeCapsule hardened = new ExchangeCapsule(
        ByteString.copyFromUtf8("owner"), 101L, 0L,
        "abc".getBytes(), "def".getBytes());
    hardened.setBalance(100_000_000L, 100_000_000L);
    long hardenedResult = hardened.transaction("abc".getBytes(), 1_000_000L, true, true);

    Assert.assertTrue("Both must return positive", legacyResult > 0 && hardenedResult > 0);
    Assert.assertTrue("Hardened must not exceed pool",
        hardenedResult <= 100_000_000L);
    // Allow ±1 difference due to BigDecimal vs double precision
    Assert.assertTrue("Results should be within 1 unit",
        StrictMathWrapper.abs(legacyResult - hardenedResult) <= 1);
