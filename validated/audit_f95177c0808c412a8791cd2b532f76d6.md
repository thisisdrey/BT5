### Title
Fixed-window stream throttling reset allows an unstaked connection to double its effective stream rate at window boundaries - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (tumbling) window counter rather than a sliding window, and `throttle_stream` only checks whether the count within the *current* fixed window has reached `max_streams_per_throttling_interval`. An attacker can send a burst of `max_streams_per_throttling_interval - 1` streams just before the window boundary and another full burst immediately after the reset, achieving up to ~2x the intended `max_streams_per_ms` budget within a short interval spanning the boundary.

### Finding Description
`reset_throttling_params_if_needed` (`streamer/src/nonblocking/stream_throttle.rs:213-230`) resets `stream_count` to 0 and records a new `last_throttling_instant` only when `now - last_throttling_instant > STREAM_THROTTLING_INTERVAL`. `throttle_stream` (`streamer/src/nonblocking/stream_throttle.rs:233-271`) then compares the (possibly just-reset) `stream_count` against `max_streams_per_throttling_interval` and sleeps only if that count has been reached — the check is purely local to the current fixed window, with no memory of how many streams were processed in the immediately preceding window.

Because the window boundary is anchored to `last_throttling_instant` (set on reset, not on a fixed clock grid), and because the check-then-sleep logic only fires once `stream_count >= max_streams_per_throttling_interval`, a connection can:
1. At `t = W - epsilon`, open `max_streams_per_throttling_interval - 1` streams. Each call passes the `>=` check (count stays below the limit), so no throttling occurs, and `stream_count` ends the window one below the cap.
2. At `t = W + epsilon` (just after the window naturally rolls over, or is rolled over by the next call's own `reset_throttling_params_if_needed`), the window resets `stream_count` to 0 and a fresh full quota of `max_streams_per_throttling_interval` becomes available immediately.
3. The attacker immediately opens another full burst of `max_streams_per_throttling_interval` streams.

In the interval `[W - epsilon, W + epsilon + STREAM_THROTTLING_INTERVAL)`— which can be made arbitrarily short (bounded below by `2 * epsilon`) — up to `2 * max_streams_per_throttling_interval - 1` streams are admitted, i.e., nearly double the intended per-`STREAM_THROTTLING_INTERVAL` budget, for a duration approaching zero. This is a textbook fixed-window counter flaw: it enforces the cap per discrete window, not per any sliding `STREAM_THROTTLING_INTERVAL`-length span of time. No other guard rechecks a sliding window; `available_load_capacity_in_throttling_duration` in `StakedStreamLoadEMA` only affects the cap value passed in, not the windowing logic itself.

### Impact Explanation
This is a QoS-evasion issue: a single unstaked (or staked) connection can transiently burst its permitted stream rate by close to 2x around a window boundary, consuming disproportionate TPU stream-processing capacity relative to peers whose bursts are not so timed. This falls under the connection/stream QoS fairness category noted in the audit scope ("unfairly capture connection, stream, or per-IP QoS limits and starve legitimate senders of TPU capacity"). The effect is bounded and transient (limited to the boundary crossing, not a sustained multiplier), so the impact is a fairness/QoS degradation rather than unbounded resource exhaustion, verification bypass, or a crash/hang.

### Likelihood Explanation
Preconditions are minimal: any unstaked client that has been admitted a QUIC connection to the TPU can trigger this by controlling stream open timing relative to `STREAM_THROTTLING_INTERVAL` (100ms, `STREAM_THROTTLING_INTERVAL_MS`). The attacker needs only to observe/estimate `last_throttling_instant`'s reset cadence (which is deterministic and observable via throttling behavior/backpressure) and time two bursts around it. This is fully reproducible and repeatable every `STREAM_THROTTLING_INTERVAL`, requiring no privileged access, staking, or cluster state manipulation.

### Recommendation
Replace the fixed-window counter with a sliding-window or token-bucket algorithm that tracks stream timestamps (or sub-interval buckets) so the enforced cap always applies to any trailing `STREAM_THROTTLING_INTERVAL`-length window, not just the current discrete window. A simpler mitigation is to use multiple overlapping sub-windows (e.g., divide `STREAM_THROTTLING_INTERVAL` into N buckets and sum the last N buckets) to approximate a sliding window with bounded memory overhead.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (test module)
#[tokio::test]
async fn test_fixed_window_boundary_burst_evades_rate_limit() {
    use std::sync::atomic::Ordering;

    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let max_streams: u64 = 10; // stand-in for max_streams_per_throttling_interval

    // Simulate burst1: max_streams - 1 streams just before window boundary.
    for _ in 0..(max_streams - 1) {
        throttle_stream(
            &stats,
            ConnectionPeerType::Unstaked,
            "127.0.0.1:1".parse().unwrap(),
            &counter,
            max_streams,
        ).await;
    }
    let burst1_count = counter.stream_count.load(Ordering::Relaxed);
    assert_eq!(burst1_count, max_streams - 1);

    // Advance clock past STREAM_THROTTLING_INTERVAL to force window reset
    // (in real test, use tokio::time::pause()/advance() to simulate boundary crossing).
    tokio::time::pause();
    tokio::time::advance(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;

    // Burst2: full new quota immediately available after reset.
    for _ in 0..max_streams {
        throttle_stream(
            &stats,
            ConnectionPeerType::Unstaked,
            "127.0.0.1:1".parse().unwrap(),
            &counter,
            max_streams,
        ).await;
    }

    // Total streams admitted across the two bursts spanning the boundary:
    let total_admitted = (max_streams - 1) + max_streams;
    // Assert this exceeds the intended single-interval budget by nearly 2x,
    // proving the fixed window allowed near-double throughput at the boundary.
    assert!(total_admitted as f64 > (max_streams as f64) * 1.9);
}
```
Expected result: the assertion passes, showing `total_admitted` approaches `2 * max_streams_per_throttling_interval`, confirming the fixed-window reset in `reset_throttling_params_if_needed` allows a connection to evade the intended per-interval stream cap by timing bursts around the window boundary.     pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
