### Title
Missing `chain_id` in `SignerCapabilityOfferProofChallengeV2` Enables Cross-Chain Replay of Signer-Capability Delegation — (`File: aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary

`SignerCapabilityOfferProofChallengeV2`, the proof-of-knowledge struct signed by an account owner when delegating signer capability via `offer_signer_capability`, omits `chain_id` from its signed payload. The structurally identical `RotationCapabilityOfferProofChallengeV2` was explicitly upgraded to include `chain_id` (with a comment stating it "prevents replaying the challenge message"), but `SignerCapabilityOfferProofChallengeV2` was never given the same treatment. A valid signature produced on one Aptos network (e.g., testnet) is byte-for-byte valid on any other network where the same account address, sequence number, and recipient address coincide.

### Finding Description

`RotationCapabilityOfferProofChallengeV2` explicitly binds to a chain:

```move
struct RotationCapabilityOfferProofChallengeV2 has drop {
    chain_id: u8,          // ← present
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
``` [1](#0-0) 

`SignerCapabilityOfferProofChallengeV2` does not:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    sequence_number: u64,   // ← no chain_id
    source_address: address,
    recipient_address: address,
}
``` [2](#0-1) 

`offer_signer_capability` constructs and verifies the challenge without chain binding:

```move
let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
    sequence_number: get_sequence_number(source_address),
    source_address,
    recipient_address,
};
verify_signed_message(
    source_address, account_scheme, account_public_key_bytes,
    signer_capability_sig_bytes, proof_challenge);
``` [3](#0-2) 

`verify_signed_message` performs a straightforward Ed25519/MultiEd25519 signature check over the BCS-serialised struct — no chain context is injected: [4](#0-3) 

The same gap exists in `RotationProofChallenge` (used by `rotate_authentication_key` and `rotate_authentication_key_with_rotation_capability`), which also omits `chain_id`: [5](#0-4) 

### Impact Explanation

An attacker who observes a valid `SignerCapabilityOfferProofChallengeV2` signature produced by Alice on testnet (or any non-mainnet network) can replay the raw signature bytes in a fresh mainnet transaction whenever:

1. Alice's account exists at the same address on mainnet (deterministic from public key — common).
2. Alice's `sequence_number` on mainnet equals the one embedded in the testnet challenge (e.g., both accounts are freshly created, or the attacker waits for the numbers to align).
3. The intended `recipient_address` exists on mainnet.

Because `offer_signer_capability` requires `account: &signer` (Alice must sign the outer transaction), the attacker cannot replay the *transaction* itself across chains — the outer transaction is chain-bound. However, the inner proof-of-knowledge signature (`signer_capability_sig_bytes`) is a standalone Ed25519 signature over a chain-agnostic byte string. An attacker who obtains this signature (e.g., from a testnet transaction, a phishing flow, or a compromised off-chain signing session) can embed it in a new mainnet transaction that Alice never authorised.

Successful exploitation grants the attacker's chosen `recipient_address` a `SignerCapability` over Alice's mainnet account, allowing that address to call `create_authorized_signer` and execute arbitrary transactions as Alice — including draining APT and fungible assets.

The same structural gap in `RotationProofChallenge` affects `rotate_authentication_key_with_rotation_capability`, where the new-key proof-of-knowledge signature is also chain-agnostic, enabling cross-chain replay of authentication-key rotation when the delegate's sequence number coincides across networks.

### Likelihood Explanation

- Accounts on Aptos testnet and mainnet share the same address derivation, so the same keypair produces the same address on both networks.
- Sequence numbers start at 0 and increment monotonically; for accounts with low activity the numbers frequently coincide across networks.
- The `signer_capability_sig_bytes` parameter is transmitted over the wire and visible in transaction history, making interception straightforward.
- The asymmetry with `RotationCapabilityOfferProofChallengeV2` (which was explicitly patched) confirms the developers recognised the class of attack but did not apply the fix uniformly.

### Recommendation

Add `chain_id: u8` to `SignerCapabilityOfferProofChallengeV2` and populate it from `chain_id::get()` inside `offer_signer_capability`, mirroring the fix already applied to `RotationCapabilityOfferProofChallengeV2`:

```move
struct SignerCapabilityOfferProofChallengeV2 has copy, drop {
    chain_id: u8,           // add this
    sequence_number: u64,
    source_address: address,
    recipient_address: address,
}
```

Apply the same fix to `RotationProofChallenge` for defence-in-depth.

### Proof of Concept

1. Alice (keypair `sk_A / pk_A`, address `addr_A`) exists on both testnet and mainnet with `sequence_number = 0`.
2. On testnet Alice calls `offer_signer_capability` granting Bob (`addr_B`) signer capability. The signed challenge is:
   ```
   BCS({ sequence_number: 0, source_address: addr_A, recipient_address: addr_B })
   ```
   Signature: `sig = Ed25519Sign(sk_A, challenge_bytes)`.
3. Attacker extracts `sig` from the testnet transaction.
4. Attacker submits a **new mainnet transaction** (signed by Alice, e.g., via a sponsored or fee-payer flow, or by Alice herself if the attacker controls the UI):
   ```
   offer_signer_capability(alice_signer, sig, ED25519_SCHEME, pk_A, addr_B)
   ```
5. Mainnet constructs the identical challenge bytes (same `sequence_number=0`, same `source_address`, same `recipient_address`) and verifies `sig` — which passes because `chain_id` is absent from the signed data.
6. `addr_B` now holds a `SignerCapability` for Alice's mainnet account and can call `create_authorized_signer` to execute arbitrary transactions as Alice. [6](#0-5) [7](#0-6)

    public entry fun offer_signer_capability(
        account: &signer,
        signer_capability_sig_bytes: vector<u8>,
        account_scheme: u8,
        account_public_key_bytes: vector<u8>,
        recipient_address: address
    ) acquires Account {
        let source_address = signer::address_of(account);
        ensure_resource_exists(source_address);
        assert!(exists_at(recipient_address), error::not_found(EACCOUNT_DOES_NOT_EXIST));

        // Proof that this account intends to delegate its signer capability to another account.
        let proof_challenge = SignerCapabilityOfferProofChallengeV2 {
            sequence_number: get_sequence_number(source_address),
            source_address,
            recipient_address,
        };
        verify_signed_message(
            source_address, account_scheme, account_public_key_bytes, signer_capability_sig_bytes, proof_challenge);

        // Update the existing signer capability offer or put in a new signer capability offer for the recipient.
        let account_resource = &mut Account[source_address];
        account_resource.signer_capability_offer.for.swap_or_fill(recipient_address);
    }

    public fun verify_signed_message<T: drop>(
        account: address,
        account_scheme: u8,
        account_public_key: vector<u8>,
        signed_message_bytes: vector<u8>,
        message: T,
    ) acquires Account {
        let auth_key = get_authentication_key(account);
        // Verify that the `SignerCapabilityOfferProofChallengeV2` has the right information and is signed by the account owner's key
        if (account_scheme == ED25519_SCHEME) {
            let pubkey = ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else if (account_scheme == MULTI_ED25519_SCHEME) {
            let pubkey = multi_ed25519::new_unvalidated_public_key_from_bytes(account_public_key);
            let expected_auth_key = multi_ed25519::unvalidated_public_key_to_authentication_key(&pubkey);
            assert!(
                auth_key == expected_auth_key,
                error::invalid_argument(EWRONG_CURRENT_PUBLIC_KEY),
            );

            let signer_capability_sig = multi_ed25519::new_signature_from_bytes(signed_message_bytes);
            assert!(
                multi_ed25519::signature_verify_strict_t(&signer_capability_sig, &pubkey, message),
                error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE),
            );
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        };
    }
