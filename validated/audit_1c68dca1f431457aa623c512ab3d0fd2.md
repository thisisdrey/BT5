### Title
Fee evasion on NEP-245/IMT transfers by splitting a single `TokenDiff` delta into N unit-sized `TokenDiff` intents - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::execute_intent` computes and collects the protocol fee independently for every signed `TokenDiff` intent, using `Self::token_fee(token_id, amount, protocol_fee)` which explicitly returns `Pips::ZERO` for `Nep245`/`Imt` token types whenever `amount <= 1` [1](#0-0) . Since fee accounting is scoped per intent call (`fees_collected` is reinitialized on every `execute_intent`) rather than per aggregate net delta for a signer/token across the whole `MultiPayload`, a signer can split one logical N-unit negative delta into N separate signed `TokenDiff` intents of delta `-1` each, causing every leg to be fee-exempt while the net token movement (verified/settled via `TransferMatcher`) is identical to a single `-N` delta.

### Finding Description
The broken binding: for a genuine single `TokenDiff` with `delta == -N` on a `Nep245`/`Imt` token, the fee owed is `Pips::fee_ceil` applied once as `Self::token_fee(token_id, N, protocol_fee).fee_ceil(N)`, which for `N > 1` uses the real `protocol_fee` (not zero) [2](#0-1) . If instead the same net effect is achieved by N intents each carrying `delta == -1` on the same `token_id`, each call computes `Self::token_fee(token_id, 1, protocol_fee)`, which hits the `TokenIdType::Nep245 | TokenIdType::Imt` arm with `amount <= 1` and returns `Pips::ZERO` unconditionally [1](#0-0) , so `fee_ceil(1)` on `Pips::ZERO` is always `0`. Summed across the N legs, `fees_collected[T] == 0`, while the equivalent single-delta transfer would have yielded `Pips::fee_ceil(N) > 0` when `protocol_fee > 0` and `N > 1`.

Root cause: fee computation is performed per `(token_id, delta)` pair inside a single `TokenDiff::diff` map entry, and separately for each distinct `TokenDiff` intent in the batch — there is no aggregation of net deltas per `(signer, token_id)` across the whole `MultiPayload` before fee is assessed. The actual value-transfer settlement, however, *is* aggregated: `Deltas::internal_sub_balance` feeds every withdrawal into a single `TransferMatcher` per token, which nets deposits/withdrawals across the whole batch [3](#0-2) [4](#0-3) . So the batch-level invariant (deposits must match withdrawals per token) is enforced on the aggregate, but the fee is not — creating exactly the divergence the question describes.

Attacker's payload: sign N separate `TokenDiff` intents (each with its own nonce, same signer), each `diff = {token_id: -1}`, matched in the same `MultiPayload` by a counterparty intent (which can be the attacker's own second controlled account) supplying the aggregate `+N` deposit for the same `token_id`. Because `TransferMatcher::finalize` only cares about net deposits/withdrawals summing to zero per token (not about which intent produced which piece), this passes the invariant check just as a single `-N`/`+N` pair would [5](#0-4) . Each of the N `execute_intent` calls independently computes `Pips::ZERO` fee, so `fee_collector` receives nothing, whereas the single-leg equivalent would have paid `fee_ceil(N)`.

Existing guards do not prevent this: nonce/signature verification only ensures each intent is validly signed by its owner (not a barrier to submitting many valid intents), and `TransferMatcher`/invariant checks validate net token conservation, not fee correctness. Nothing in the code aggregates net per-token deltas per signer across the batch before charging fees.

### Impact Explanation
Protocol fee under-collection: `fee_collector`'s expected revenue on NEP-245/IMT token transfers can be reduced to zero by any unprivileged signer simply by restructuring a transfer of N units into N unit legs, for any N and any nonzero `protocol_fee`. This is repeatable per transaction, per token, per account pair, with no cap — it is a structural bypass of the fee mechanism for the entire `Nep245`/`Imt` token class, matching the "protocol fees bypassed" Critical impact category in the rules.

### Likelihood Explanation
Preconditions are minimal: signer must hold the token balance being moved (same balance requirement as the honest transfer), `FeesConfig::fee` (protocol fee) must be nonzero, and the batch needs a matching counterparty leg supplying the aggregate positive delta (which the attacker can supply from a second self-controlled account, requiring no cooperation from any third party). Cost is simply the additional signed intents (N nonces, N intents in one `MultiPayload`) — no special privileges, roles, or gas/DoS considerations required for typical N. This is fully attacker-controlled and repeatable indefinitely.

### Recommendation
Aggregate net deltas per `(signer_id, token_id)` across the entire `MultiPayload`/batch before computing `TokenDiff` fees (i.e., compute `token_fee`/`fee_ceil` on the summed negative delta per signer/token for the whole execution context, not per individual `TokenDiff` intent occurrence), or alternatively compute fees post-`TransferMatcher::finalize` on the actual matched transfer amounts rather than on each intent's raw per-leg delta.

### Proof of Concept
`near-workspaces`/sandbox `cargo test` plan (extends existing tests in `tests/src/tests/defuse/intents/token_diff.rs`):
1. Deploy defuse contract with `FeesConfig::fee = Pips::ONE_PERCENT` (nonzero) and a configured `fee_collector`.
2. Setup: attacker account A holds `N = 5` units of a NEP-245 token `T`; attacker-controlled account B is the counterparty.
3. Case 1 (single leg): sign one `TokenDiff` intent for A: `diff = {T: -5}`, and a matching `TokenDiff` for B: `diff = {T: +5}` (plus whatever B gives back, e.g. a Nep141 token, for net-zero settlement including the fee closure per `TokenDiff::closure_delta`). Execute via `execute_intents`. Assert `fee_collector`'s NEP-245 balance for `T` increases by `Pips::ONE_PERCENT.fee_ceil(5) > 0`.
4. Case 2 (split legs): sign five separate `TokenDiff` intents for A, each `diff = {T: -1}` (distinct nonces), and matching intents from B summing to `+5` for `T`. Execute via `execute_intents` in one `MultiPayload`.
5. Assert: net balance change for A and B is identical between Case 1 and Case 2 (A loses 5 of `T`, B gains 5 of `T`), but `fee_collector`'s balance for `T` after Case 2 is `0`, differing from Case 1's `fee_ceil(5)` — demonstrating `fees_collected[T] (Case 2) == 0 != Pips::fee_ceil(5) (Case 1)` for the same net token movement.

impl TransferMatcher {
    #[inline]
    pub fn new() -> Self {
        Self(HashMap::new())
    }

    #[inline]
    pub fn deposit(&mut self, owner_id: AccountId, token_id: TokenId, amount: u128) -> bool {
        self.0.entry_or_default(token_id).deposit(owner_id, amount)
    }

    #[inline]
    pub fn withdraw(&mut self, owner_id: AccountId, token_id: TokenId, amount: u128) -> bool {
        self.0.entry_or_default(token_id).withdraw(owner_id, amount)
    }

    #[inline]
    pub fn add_delta(&mut self, owner_id: AccountId, token_id: TokenId, delta: i128) -> bool {
        self.0.entry_or_default(token_id).add_delta(owner_id, delta)
    }

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
}

    pub fn finalize_into(self, token_id: &TokenId, transfers: &mut Transfers) -> Result<(), i128> {
        // sort deposits and withdrawals in descending order
        let [mut deposits, mut withdrawals] = [self.deposits, self.withdrawals].map(|amounts| {
            let mut amounts: Vec<_> = amounts.into_iter().collect();
            amounts.sort_unstable_by_key(|(_, amount)| Reverse(*amount));
            amounts.into_iter()
        });

        // take first sender and receiver
        let (mut deposit, mut withdraw) = (deposits.next(), withdrawals.next());

        // as long as there is both: sender and receiver
        while let Some(((sender, send), (receiver, receive))) =
            withdraw.as_mut().zip(deposit.as_mut())
        {
            // get min amount and transfer
            let transfer = (*send).min(*receive);
            transfers
                .transfer(sender.clone(), receiver.clone(), token_id.clone(), transfer)
                // no error can happen since we add only one transfer for each
                // combination of (sender, receiver, token_id)
                .unwrap_or_else(|| unreachable!());

            // subtract amount from sender and receiver
            *send = send.saturating_sub(transfer);
            *receive = receive.saturating_sub(transfer);

            if *send == 0 {
                // select next sender
                withdraw = withdrawals.next();
            }
            if *receive == 0 {
                // select next receiver
                deposit = deposits.next();
            }
        }

        // only sender(s) left
        if let Some((_, send)) = withdraw {
            return Err(withdrawals
                .try_fold(send, |total, (_, s)| total.checked_add(s))
                .and_then(|total| i128::try_from(total).ok())
                .and_then(i128::checked_neg)
                .unwrap_or_default());
        }
        // only receiver(s) left
        if let Some((_, receive)) = deposit {
            return Err(deposits
                .try_fold(receive, |total, (_, r)| total.checked_add(r))
                .and_then(|total| i128::try_from(total).ok())
                .unwrap_or_default());
        }

        Ok(())
    }
