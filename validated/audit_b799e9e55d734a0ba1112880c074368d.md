### Title
Retroactive interest-rate application when `accrue()` skips updating `last-update` on a zero/rounded-to-zero index delta - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent `v0-vault-*.clar` vaults)

### Summary
The vault's `accrue` function only advances the `last-update` timestamp when the freshly computed `index`/`lindex` actually differ from their previous stored values. When the elapsed period produces no measurable index change (e.g., interest rounds down to zero for a short interval, or the interpolated rate for the current utilization segment is zero), `last-update` is left stale. Any later `accrue()` call then computes `time-delta` from that stale timestamp but multiplies it by whatever interest rate is *current at call time* — silently misapplying today's rate retroactively to a past interval where a different (lower/zero) rate actually applied. This mirrors the Popcorn `feesUpdatedAt` bug class exactly, but here it drives debt/interest accrual and treasury LP minting rather than management fees.

### Finding Description
`accrue()` computes the next borrow index and liquidity index via `next-index` / `next-liquidity-index`, which derive `time-delta` from `(- stacks-block-time (var-get last-update))` and the interest rate returned by `interest-rate()` (looked up live from `points-ir` at current utilization): [1](#0-0) 

After computing `next`/`nliq`, `accrue()` only bumps `last-update` conditionally: [2](#0-1) 

```
(if (or (not (is-eq idx next)) (not (is-eq lidx nliq)))
    (var-set last-update stacks-block-time)
    false)
```

If `next == idx` and `nliq == lidx` (e.g. rate is 0 for the current utilization segment, or the elapsed time is too short for the index multiplier to move off `INDEX-PRECISION` after rounding-down math), `last-update` is **not** advanced even though real time has passed. The next time `accrue()` runs — triggered by any unprivileged principal's `deposit`, `redeem`, `system-borrow`, `system-repay`, etc. — `time-delta` is computed from the old, stale `last-update`, spanning the entire "silent" period, but it is multiplied by the rate that is current **at that later call**, not the rate(s) that were actually in force during the silent period. This is functionally identical to the reported bug: a rate parameter effective from time T2 gets applied to interest that accrued from T1 (T1 < T2), inflating debt/interest for that stretch.

Because DAO-controlled rate-curve setters (`set-points-rate`, `set-points-util`, `set-fee-reserve`) call `(try! (accrue))` *before* writing the new curve, they only correctly "checkpoint" the old rate if that pre-emptive `accrue()` call actually advances `last-update`: [3](#0-2) 
If the old curve happened to compute `next == idx` at that exact moment (zero-rate segment or rounding), the checkpoint silently fails to record the true elapsed time, and the stale `last-update` carries forward into the new-rate regime — reproducing the exact retroactive-rate defect the report warns about, purely through normal usage (no DAO malice needed, though a rate-curve change from 0 to non-zero triggered by the DAO is the most direct trigger).

### Impact Explanation
The misapplied rate inflates `total-debt` computed via `calc-cumulative-debt`, which flows into `debt-preview`, `total-assets-preview`, and the treasury LP mint calculation: [4](#0-3) 
Overcharged borrower interest is effectively unclaimed-yield theft from borrowers (transferred to LPs/treasury via `reserve-inc`/`treasury-lp` minting) for a period during which a lower/zero rate should have applied — this lands in the in-scope "theft of unclaimed yield" High impact bucket for interest accrual / treasury LP minting.

### Likelihood Explanation
Triggering requires only that at some point `next-index`/`next-liquidity-index` compute to unchanged values while real time has elapsed (rate curve returning 0 at low utilization is a plausible DAO-configured curve; rounding-to-zero for very short intervals is also possible given `Math.Rounding.Down`), followed by ordinary transaction activity (deposit/borrow/repay by any user) that changes utilization enough to push the interpolated rate above zero. All of these triggering paths are reachable by unprivileged callers of `system-borrow`, `system-repay`, deposit, or redeem, which each call `accrue` internally. Likelihood is Medium: it depends on rate-curve shape and timing, but does not require any privileged or DAO-compromise action to realize once such a zero/near-zero segment exists.

### Recommendation
Decouple `last-update` from whether the computed index changed. Always set `last-update` to `stacks-block-time` whenever `time-delta > 0` is observed in `accrue()` (i.e., unconditionally checkpoint on time elapsed, not on index delta), so that every `accrue()` call — including ones triggered right before a rate-curve change — correctly records that the up-to-now interest at the *old* rate has been fully recognized, preventing any subsequent rate from being retroactively applied to already-elapsed time.

### Proof of Concept
1. DAO (or protocol config) sets a `points-ir` curve where the rate for the current utilization band is `0` (e.g., util = 0%, rate = 0).
2. Time passes; utilization stays flat, so ordinary calls to `accrue()` (via user deposits/repays) compute `next == idx` and `nliq == lidx`, so `last-update` never advances (see the conditional block at `v0-vault-usdc.clar:858-861`).
3. Some later transaction (an ordinary borrow by any user) raises utilization into a segment where the curve returns a non-zero rate.
4. The next `accrue()` call computes `time-delta = stacks-block-time - last-update`, spanning the *entire* silent low/zero-rate period, and multiplies it by the *new* non-zero rate via `next-index`/`next-liquidity-index` (`v0-vault-usdc.clar:377-402`), inflating `total-debt` and the treasury-LP mint (`v0-vault-usdc.clar:843-861`) for a period where the effective rate should have been zero. (define-private (next-index)
  (let ((states (var-get pause-states))
        (idx (var-get index)))
    (if (get accrue states)
        idx

            (rate (interest-rate))

                          INDEX-PRECISION

          (calc-index-next idx multiplier)))))

(define-private (next-liquidity-index)
  (let ((states (var-get pause-states))
        (lidx (var-get lindex)))
    (if (get accrue states)
        lidx

            (rate (interest-rate))
