### Title
`ShieldedTransferActuator` permanently records zk-proof verification results for every submitted shielded transaction, including ones that ultimately fail — unbounded `ZKProofStore` growth reachable by any transaction broadcaster - (File: `actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java`)

### Summary
`ShieldedTransferActuator.validate()` runs `checkProof()` as effectively the last (and most expensive) validation step, and on success unconditionally calls `recordProof(tx.getTransactionId(), true)` which writes a permanent entry into `ZKProofStore` keyed by the transaction id. [1](#0-0)  This record is written before the transaction's actual state effects are applied in `execute()`/`executeShielded()`, so a transaction whose proof checks out but that later fails for other reasons (e.g. a double-spent nullifier detected in `executeShielded`, or a `BalanceInsufficientException` in the transparent/shielded balance adjustments) still leaves behind a permanent, un-prunable `ZKProofStore` entry, while the caller only sees a failed/`FAILED` transaction result. [2](#0-1)  `ZKProofStore` has no eviction, TTL, or pruning logic — every key ever written stays forever. [3](#0-2) 

### Finding Description
The advisory's bug class is: an operation reachable without meaningful privilege causes a hidden object to be persisted to storage even though the caller-visible result is an error, with no bound on how many such objects can accumulate (CWE-770). `ShieldedTransferActuator` reproduces this pattern:

1. `validate()` performs `checkSender`, `checkReceiver`, `validateTransparent`, and nullifier/anchor checks, and only at the end calls `checkProof(spendDescriptions, receiveDescriptions, fee)`. [4](#0-3) 
2. `checkProof()` first checks `proofStore.has(tx.getTransactionId().getBytes())` as a memoization cache, then performs the actual zk-SNARK verification (`librustzcashSaplingCheckSpend`, `librustzcashSaplingCheckOutput`, `librustzcashSaplingFinalCheck`) and, on success, calls `recordProof(tx.getTransactionId(), true)`. [5](#0-4) 
3. This record is written into `ZKProofStore`, a raw key-value RocksDB-backed store with `put`/`get`/`has`/`delete` but **no automatic cleanup or size bound anywhere in the codebase** — entries persist for the lifetime of the node's database. [3](#0-2) 
4. `execute()` runs *after* `validate()` has already committed this proof record, and can still fail (nullifier already spent → `ContractExeException("double spend")`, `BalanceInsufficientException` on the transparent legs, or arithmetic/pool-value errors), meaning the transaction as a whole fails and no meaningful state change is retained — but the `ZKProofStore` entry for that transaction id remains permanently. [6](#0-5) [7](#0-6) 

Because the transaction id used as the key is derived from the transaction's own signed content via `getShieldTransactionHashIgnoreTypeException`, every unique shielded-transfer transaction an attacker crafts and broadcasts (each with a valid zk proof but designed to fail at a later, cheaper check such as double-spending an already-used nullifier or an insufficient blackhole/pool balance) produces one new permanent key in `ZKProofStore`, with the failure reason hidden from any observer inspecting `ZKProofStore` in isolation — mirroring the OpenBao pattern where the caller-visible error hides the fact that a persistent object (there, an auth token; here, a proof-verification record) was created and retained.

### Impact Explanation
This is a storage-growth / resource-exhaustion issue reachable by any account able to construct and broadcast a `ShieldedTransferContract` transaction. Each malicious transaction requires only a valid zk-SNARK proof (which an attacker fully controls when constructing their own shielded note/spend) and a colliding nullifier or insufficient balance to force a late-stage failure in `execute()` while still passing all of `validate()`, including the expensive proof check that commits the record. Repeated submission causes unbounded, non-reclaimable growth of `ZKProofStore` on every full node — consistent with CWE-770 and analogous in class/severity to the referenced Medium-severity OpenBao advisory (storage-usage impact from unauthenticated/uncontrolled accumulation of hidden persisted objects).

### Likelihood Explanation
Moderate. It requires the attacker to pay the normal fee for a shielded transaction (`calcFee`) and to perform real zk-SNARK proof generation for each spend/output — this is more costly than a plain unauthenticated HTTP call, but it does not require any elevated privilege beyond being a funded transaction broadcaster, and the shielded-transfer fee does not scale with, or bound, the number of `ZKProofStore` entries created over time. An attacker with modest, sustained resources can accumulate entries indefinitely since there is no compensating cleanup.

### Recommendation
Do not persist the proof-verification record for a shielded transaction until the accompanying state changes (nullifier consumption, balance/pool adjustments in `execute()`) are known to also succeed, or add pruning/expiry of `ZKProofStore` entries once a transaction has been finalized (included or permanently rejected) so that failed transactions do not leave permanent artifacts.

### Proof of Concept
1. Construct a valid Sapling shielded note and generate a well-formed `SpendDescription`/`ReceiveDescription` pair with a genuine zk-SNARK proof for a `ShieldedTransferContract`.
2. Submit that transaction once so its nullifier is consumed by `NullifierStore` via `executeShielded`.
3. Re-broadcast a second transaction reusing the same underlying spend but with a different transaction id/signature (so it hashes to a new key), replaying the same nullifier.
4. In `validate()`, `checkProof()` succeeds (the SNARK proof itself is still cryptographically valid) and `recordProof(tx.getTransactionId(), true)` persists an entry in `ZKProofStore`. [8](#0-7) 
5. `execute()` then reaches `executeShielded`, detects the nullifier already exists in `NullifierStore`, and throws `ContractExeException("double spend")`, failing the transaction. [7](#0-6) 
6. Repeat with freshly generated (still-valid-proof, still-conflicting) transactions to accumulate an arbitrary number of permanent `ZKProofStore` entries despite every submitted transaction ultimately failing.

Note: I was unable to fully trace whether any block-application or pruning routine elsewhere in the manager clears `ZKProofStore` entries for failed/unconfirmed transactions; my search of the codebase found no such cleanup code, but the index may not cover every call site. A Devin session with full repository access could confirm this exhaustively via a runtime trace or fuller grep across `Manager`/`TransactionCapsule`.

      ret.setStatus(0, code.FAILED);
      ret.setShieldedTransactionFee(fee);
      throw new ContractExeException(e.getMessage());
    }

    ret.setStatus(0, code.SUCESS);
    ret.setShieldedTransactionFee(fee);
    return true;

  private void checkProof(List<SpendDescription> spendDescriptions,
      List<ReceiveDescription> receiveDescriptions, long fee) throws ZkProofValidateException {
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ZKProofStore proofStore = chainBaseManager.getProofStore();
    if (proofStore.has(tx.getTransactionId().getBytes())) {
      if (proofStore.get(tx.getTransactionId().getBytes())) {
        return;
      } else {
        throw new ZkProofValidateException("record is fail, skip proof", false);
      }
    }

    byte[] signHash = getShieldTransactionHashIgnoreTypeException(tx.getInstance());

    if (CollectionUtils.isNotEmpty(spendDescriptions)
        || CollectionUtils.isNotEmpty(receiveDescriptions)) {
      long ctx = JLibrustzcash.librustzcashSaplingVerificationCtxInit();
      try {
        for (SpendDescription spendDescription : spendDescriptions) {
          if (!JLibrustzcash.librustzcashSaplingCheckSpend(
              new CheckSpendParams(ctx,
                  spendDescription.getValueCommitment().toByteArray(),
                  spendDescription.getAnchor().toByteArray(),
                  spendDescription.getNullifier().toByteArray(),
                  spendDescription.getRk().toByteArray(),
                  spendDescription.getZkproof().toByteArray(),
                  spendDescription.getSpendAuthoritySignature().toByteArray(),
                  signHash)
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckSpend error", true);
          }
        }

        for (ReceiveDescription receiveDescription : receiveDescriptions) {
          if (receiveDescription.getCEnc().size() != ZC_ENCCIPHERTEXT_SIZE
              || receiveDescription.getCOut().size() != ZC_OUTCIPHERTEXT_SIZE) {
            throw new ZkProofValidateException("Cout or CEnc size error", true);
          }
          if (!JLibrustzcash.librustzcashSaplingCheckOutput(
              new CheckOutputParams(ctx,
                  receiveDescription.getValueCommitment().toByteArray(),
                  receiveDescription.getNoteCommitment().toByteArray(),
                  receiveDescription.getEpk().toByteArray(),
                  receiveDescription.getZkproof().toByteArray())
          )) {
            throw new ZkProofValidateException("librustzcashSaplingCheckOutput error", true);
          }
        }

        long valueBalance;
        long totalShieldedPoolValue = dynamicStore
            .getTotalShieldedPoolValue();
        try {
          valueBalance = addExact(subtractExact(
              shieldedTransferContract.getToAmount(),
              shieldedTransferContract.getFromAmount()), fee);
          totalShieldedPoolValue = subtractExact(
              totalShieldedPoolValue, valueBalance);
        } catch (ArithmeticException e) {
          logger.debug(e.getMessage(), e);
          throw new ZkProofValidateException(e.getMessage(), true);
        }

        if (totalShieldedPoolValue < 0) {
          throw new ZkProofValidateException("shieldedPoolValue error", true);
        }

        if (!JLibrustzcash.librustzcashSaplingFinalCheck(
            new FinalCheckParams(ctx,
                valueBalance,
                shieldedTransferContract.getBindingSignature().toByteArray(),
                signHash)
        )) {
          throw new ZkProofValidateException("librustzcashSaplingFinalCheck error", true);
        }
      } catch (ZksnarkException e) {
        throw new ZkProofValidateException(e.getMessage(), true);
      } finally {
        JLibrustzcash.librustzcashSaplingVerificationCtxFree(ctx);
      }
    }

    recordProof(tx.getTransactionId(), true);

package org.tron.core.store;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.ApplicationContext;
import org.springframework.stereotype.Component;
import org.tron.core.db.TronDatabase;

@Component
public class ZKProofStore extends TronDatabase<Boolean> {

  @Autowired
  public ZKProofStore(ApplicationContext ctx) {
    super("zkProof");
  }

  @Override
  public void put(byte[] key, Boolean item) {
    byte[] b = {(byte) (item.booleanValue() ? 0x01 : 0x00)};
    dbSource.putData(key, b);
  }

  @Override
  public void delete(byte[] key) {
    dbSource.deleteData(key);
  }

  @Override
  public Boolean get(byte[] key) {
    return dbSource.getData(key)[0] == 0x01;
  }

  @Override
  public boolean has(byte[] key) {
    return dbSource.getData(key) != null;
  }
