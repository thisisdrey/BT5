Given the tool budget is exhausted, here is the strongest local analog I was able to substantiate, along with an explicit note on what remains unverified.

### Title
NFT-fractionalization "lock" is a mutable generic attribute the original owner/collection-owner can strip, letting them reclaim/move the underlying NFT while fraction-token holders keep worthless receipts - (File: `substrate/frame/nft-fractionalization/src/lib.rs`)

### Summary
`pallet-nft-fractionalization::fractionalize` locks a `pallet-nfts` item by calling `T::Nfts::disable_transfer`, which does not move the NFT into pallet-controlled custody. Instead it sets a system-level attribute `PalletAttributes::TransferDisabled` on the item via the generic `Attribute` storage that `pallet-nfts` also exposes to end users through ordinary, permissionless-to-privileged dispatchables (`clear_attribute`, `force_set_attribute`, `set_attribute`). The NFT owner is unchanged after `fractionalize` — the item stays with the original owner (confirmed by the test assertion `Nfts::owner(nft_collection_id, nft_id) == Some(account(1))` after fractionalization) [1](#0-0) . This is structurally identical to the veAERO bug: a "receipt" (fraction tokens) is meant to represent a claim on a locked asset, but the lock is enforced only by a mutable flag/attribute that the underlying asset's controller can revoke through a channel that the receipt-issuing logic does not gate or even know about.

### Finding Description
`fractionalize` reserves a deposit, disables transfer on the NFT, mints a fungible asset ("fractions") to a beneficiary, and records `NftToAsset` — but never transfers the NFT away from its owner: [2](#0-1) 

The lock itself is implemented generically: [3](#0-2) 

`disable_transfer`/`enable_transfer` operate purely by setting/clearing the `PalletAttributes::TransferDisabled` system attribute through the pallet-nfts `Mutate`/attribute-storage API: [4](#0-3) 

`do_transfer` and `do_burn`-adjacent paths gate on this same attribute via `has_system_attribute`: [5](#0-4) 

The problem is that `pallet-nfts` exposes generic, permissioned-but-independent dispatchables (`clear_attribute`, `set_attribute`, `force_set_attribute`) that operate on the very same `Attribute` storage map that `PalletAttributes::TransferDisabled` is stored in [6](#0-5) . `pallet-nft-fractionalization`'s `NftToAsset` bookkeeping is a completely separate storage item with no cross-check against, or lock on, direct attribute mutation. When the item owner is also the collection owner (a very common self-issued-collection pattern that `fractionalize` does nothing to prevent, since it only checks `nft_owner == who`), that same account retains the `CollectionOwner`-namespace privilege needed to clear or overwrite arbitrary attributes on their own item — including one whose key happens to encode `PalletAttributes::TransferDisabled`. Clearing it removes the transfer lock outside the `unify` flow (which is the only path meant to remove it, and which additionally requires burning 100% of the fraction supply).

I was not able to fully verify, within the remaining tool budget, the *exact* namespace/key that `disable_transfer`'s internal `Mutate::set_attribute` call resolves to versus what the public `clear_attribute`/`force_set_attribute` extrinsics accept as `namespace`/`key` parameters — i.e., I could not conclusively trace whether `has_system_attribute`'s storage key is reachable byte-for-byte from the signed `clear_attribute` extrinsic (`AttributeNamespace::CollectionOwner` vs. some other namespace value used internally). This is the one open verification gap; everything else in the chain (lock-by-attribute design, unchanged ownership after fractionalize, decoupled `NftToAsset` bookkeeping, and the generic attribute-editing surface) is directly confirmed by the cited code.

### Impact Explanation
If the gap above resolves as suspected, an attacker who fractionalizes their own NFT in their own collection can: (1) sell/distribute the fraction tokens to buyers who believe they are collateralized 1:1 by the locked NFT, (2) directly strip the `TransferDisabled` attribute through `clear_attribute`/`force_set_attribute` without going through `unify` (i.e., without burning any fractions), and (3) transfer, sell, or burn the NFT freely. Fraction-token holders are left holding tokens that can never legitimately be redeemed via `unify`, because the NFT is gone or now owned by an unrelated third party — exactly the "worthless receipt left with the honest counterparty" pattern in the veAERO report. This is a direct, permissionless fund-loss vector for anyone who buys/trades `pallet-nft-fractionalization` shares (used on Asset Hub, e.g. `asset-hub-westend`) [7](#0-6) .

### Likelihood Explanation
The attack requires no privileged actor, validator, relayer, or admin — only an ordinary user acting as both collection owner and item owner, which is the default, unrestricted use case for `fractionalize` (no check prevents the fractionalizer from being the collection owner). It uses only public, already-existing extrinsics (`fractionalize`, `clear_attribute`/`force_set_attribute`, `transfer`/`burn`). The main uncertainty affecting likelihood is the unverified namespace/key match discussed above; if `clear_attribute`'s `AttributeNamespace::CollectionOwner` cannot address the exact key `disable_transfer` used, the attack path would need `force_set_attribute` (governance-only) instead, which would move this out of scope as a privileged-actor issue.

### Recommendation
Do not rely on a generically-writable NFT attribute as the sole enforcement of an economically load-bearing lock. Either: (a) transfer the NFT into `pallet-nft-fractionalization`'s pallet account custody during `fractionalize` (mirroring how the fungible "fractions" asset itself is pallet-controlled) instead of leaving it with the original owner, or (b) introduce a dedicated, non-attribute-based lock primitive in `pallet-nfts` (a distinct storage map not reachable by `set_attribute`/`clear_attribute`/`force_set_attribute`) for pallet-level transfer locks, and gate `clear_attribute`/`force_set_attribute` from ever touching `PalletAttributes`-namespaced keys.

### Proof of Concept
Conceptual (not fully attempted end-to-end due to the unverified namespace/key match noted above):
1. Attacker creates collection `C` (becomes `CollectionOwner`) and mints item `I` to themselves.
2. Attacker calls `NftFractionalization::fractionalize(C, I, asset_id, beneficiary=victim_buyer_pool, fractions=1000)`. Item `I` remains owned by attacker; `TransferDisabled` attribute is set; 1000 fraction tokens are minted to a distributable pool.
3. Victims acquire the 1000 fraction tokens believing they represent a redeemable claim on item `I`.
4. Attacker, still `CollectionOwner`, calls `Nfts::clear_attribute(C, Some(I), AttributeNamespace::CollectionOwner, key=encode(PalletAttributes::TransferDisabled))` (or `force_set_attribute` if governance-gated) to remove the lock outside of `unify`.
5. Attacker calls `Nfts::transfer(C, I, attacker_alt_account)` or `Nfts::burn(C, I)`.
6. Victims' fraction tokens can no longer be redeemed for the NFT via `NftFractionalization::unify`, which requires the NFT to still exist and be unify-able; value is lost.

			origin: OriginFor<T>,
			nft_collection_id: T::NftCollectionId,
			nft_id: T::NftId,

			beneficiary: AccountIdLookupOf<T>,

			let who = ensure_signed(origin)?;
			let beneficiary = T::Lookup::lookup(beneficiary)?;

			let nft_owner =
				T::Nfts::owner(&nft_collection_id, &nft_id).ok_or(Error::<T>::NftNotFound)?;

			Self::do_create_asset(asset_id.clone(), pallet_account.clone())?;
			Self::do_mint_asset(asset_id.clone(), &beneficiary, fractions)?;
			Self::do_set_metadata(
				asset_id.clone(),
				&who,
				&pallet_account,
				&nft_collection_id,
				&nft_id,
			)?;

			NftToAsset::<T>::insert(
				(nft_collection_id, nft_id),
				Details { asset: asset_id.clone(), fractions, asset_creator: nft_owner, deposit },
			);

			Self::deposit_event(Event::NftFractionalized {
				nft_collection: nft_collection_id,
				nft: nft_id,
				fractions,
				asset: asset_id,
				beneficiary,
			});

			Ok(())

impl<T: Config<I>, I: 'static> Transfer<T::AccountId> for Pallet<T, I> {
	fn transfer(
		collection: &Self::CollectionId,
		item: &Self::ItemId,
		destination: &T::AccountId,
	) -> DispatchResult {
		Self::do_transfer(*collection, *item, destination.clone(), |_, _| Ok(()))
	}

	fn disable_transfer(collection: &Self::CollectionId, item: &Self::ItemId) -> DispatchResult {
		let transfer_disabled =
			Self::has_system_attribute(&collection, &item, PalletAttributes::TransferDisabled)?;
		// Can't lock the item twice
		if transfer_disabled {
			return Err(Error::<T, I>::ItemLocked.into());
		}

		<Self as Mutate<T::AccountId, ItemConfig>>::set_attribute(
			collection,
			item,
			&PalletAttributes::<Self::CollectionId>::TransferDisabled.encode(),
			&[],
		)
	}

	fn enable_transfer(collection: &Self::CollectionId, item: &Self::ItemId) -> DispatchResult {
		<Self as Mutate<T::AccountId, ItemConfig>>::clear_attribute(
			collection,
			item,
			&PalletAttributes::<Self::CollectionId>::TransferDisabled.encode(),
		)
	}
