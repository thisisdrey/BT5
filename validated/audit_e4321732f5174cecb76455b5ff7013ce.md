## Title
Non-constant-time HTTP `Authorization` token comparison enables remote timing side-channel to recover `auth_token` - (File: `stackslib/src/net/api/postblock_v3.rs`)

### Summary
Six RPC handlers in `stackslib/src/net/api/` gate privileged/expensive endpoints behind a shared-secret `Authorization` header, but every one of them compares the supplied header to the configured secret using Rust's default `!=` string comparison, which is a byte-by-byte, early-exit comparison. This is the same underlying bug class as GHSA-hjp5-hv33-q58g (Plone's authentication token comparison used invariant, guessable data): here, the invariant data is the plaintext `auth_token`/`connection_options.auth_token` compared with an operation whose timing leaks how many leading bytes matched, letting a remote, unauthenticated attacker recover the secret byte-by-byte over the network without needing any credential to start with.

### Finding Description
The affected sites all follow the identical pattern: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

Each handler does `if auth_header != password { return Err(...401...) }`. Rust `&str`/`String` equality (`PartialEq`) is implemented as a straightforward memory comparison that returns as soon as a mismatching byte (or differing length) is found — it is not constant-time. A search of the codebase confirms there is no constant-time comparison primitive used anywhere for this check (no `subtle::ConstantTimeEq`, no `ct_eq`), so all six endpoints share this weakness. The documentation itself states the design intent: the `Authorization` header value "must exactly equal the node's configured password" — an invariant secret compared using variable-time equality.

The equality being broken here is: *the time taken to reject an incorrect guess should be independent of how many leading bytes of the guess are correct*. Because the comparison short-circuits on the first mismatching byte, an attacker who can measure round-trip response latency with enough samples can incrementally brute-force the shared `auth_token` one byte at a time — a well-known practical attack class (cf. timing attacks against HMAC/token comparisons), analogous to the referenced advisory's core weakness of using invariant, statically-comparable authentication material.

### Impact Explanation
Recovering the `auth_token` is a full authentication bypass for every endpoint gated on it: `/v3/block_proposal` (block proposal submission), `/v2/blocks?broadcast=1` / `/v3/blocks` broadcast path (unauthenticated write causing network propagation of attacker-supplied blocks), `/v3/blocks/replay`, `/v3/contracts/fast-call-read`, and `/v3/transactions/simulate`. This matches the "Critical" impact bucket in scope: unauthenticated/unauthorized write to state and network-wide propagation of forged data (via the broadcast-gated block posting endpoint), reachable by any remote, unprivileged party with no prior credentials.

### Likelihood Explanation
Exploitation requires only network access to the node's RPC port and the ability to send repeated requests while measuring timing — no privileged position, no other party's key, and no admin role, matching the "remote, unprivileged" requirement. Real-world timing attacks over the network are noisier than local ones but remain practical, especially as the comparison is on a short, fixed-format token and the attacker can average over many requests per byte position.

### Recommendation
Replace all `auth_header != password` checks with a constant-time comparison (e.g., using the `subtle` crate's `ConstantTimeEq`, or a manual XOR-accumulate-and-compare over fixed-length byte slices) in every one of the affected handlers (`postblock_v3.rs`, `blockreplay.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `txsimulate.rs`, `postblock_proposal.rs`), ideally centralizing the check in one shared helper function so future endpoints inherit the fix.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "<secret>"`.
2. From a remote unprivileged client, repeatedly send requests to, e.g., `/v3/transactions/simulate` with candidate `Authorization` header values that share an increasing number of correct leading bytes with the real token.
3. Measure response latency for the 401 rejection path in `RPCTransactionSimulateRequestHandler::try_parse_request` [6](#0-5) ; because `!=` short-circuits at the first mismatching byte, candidates matching more leading bytes take measurably longer to reject.
4. Iterate byte-by-byte (or with statistical timing analysis) to reconstruct the full `auth_token`, then use it to authenticate to `/v3/block_proposal` or `/v3/blocks?broadcast=1` for unauthorized writes/propagation.
