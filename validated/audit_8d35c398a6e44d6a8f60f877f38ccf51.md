Audit Report

## Title
Unchecked arithmetic underflow on attacker-supplied `AncestryProof.prev_leaf_count` causes panic in `verify_ancestry_proof` - (File: `substrate/frame/merkle-mountain-range/src/mmr/mmr.rs`)

## Summary
`verify_ancestry_proof` computes `mmr_lib::helper::leaf_index_to_mmr_size(ancestry_proof.prev_leaf_count - 1)` directly from the SCALE-decoded, caller-supplied `AncestryProof.prev_leaf_count: u64` field with no lower-bound check before the subtraction. [1](#0-0)  If `prev_leaf_count == 0`, the subtraction underflows, causing a panic in debug/overflow-checked builds or a wrapped `u64::MAX` used downstream in release builds.

## Finding Description
`AncestryProof` is a plain SCALE-decodable struct whose `prev_leaf_count` field is fully attacker-controlled. [2](#0-1)  The verifier subtracts 1 from this value with no check: [3](#0-2) 

This is reachable through `pallet-beefy-mmr`'s `AncestryHelper::is_non_canonical`, which is the mechanism for proving a BEEFY commitment is non-canonical (fork-voting/equivocation reporting) and accepts an externally supplied `AncestryProof`. [4](#0-3)  The only gate before calling into `verify_ancestry_proof` is `commitment_leaf_count != proof.prev_leaf_count`, an equality check against a value derived from `commitment.block_number` via `block_num_to_leaf_count` — this is not a `prev_leaf_count != 0` guard, and does not prevent a zero value from passing through when the commitment's own derived leaf count is also zero or when the equality happens to hold.

By contrast, the analogous leaf-proof verification path explicitly checks for a zero `leaf_count` before it is used: [5](#0-4)  `verify_ancestry_proof` has no equivalent check anywhere before the subtraction at line 98, confirming the missing-guard defect is real and asymmetric with the sibling function.

## Impact Explanation
A malformed but well-formed `AncestryProof` with `prev_leaf_count = 0` submitted to `verify_ancestry_proof` (directly, or via `pallet-beefy-mmr::is_non_canonical` in the BEEFY fork-voting/equivocation-reporting path) triggers an unchecked `u64` subtraction underflow. This causes an immediate panic in overflow-checked builds (DoS of the node/runtime executing the check) or propagates a corrupted `u64::MAX`-derived size into `mmr_lib` internals in non-checked builds, risking further panics or excessive resource use. This matches the "public underpriced work that degrades block production or stalls bridge processing" impact class, since equivocation/fork-voting reporting is designed to be triggerable by any unprivileged party supplying self-constructed proof data.

## Likelihood Explanation
Constructing an `AncestryProof` with `prev_leaf_count: 0` requires no cryptographic material — it is a single scalar field in an otherwise well-formed SCALE encoding, so any caller able to submit a proof to the ancestry/equivocation-reporting code path can attempt to trigger it. The exact extrinsic/unprivileged entrypoint that ultimately calls `is_non_canonical` in `pallet-beefy` was not directly located in this pass, and whether release-profile builds have `overflow-checks` enabled for the relevant crate could not be confirmed from the repository's root `Cargo.toml` search results alone. This leaves some uncertainty about the exact severity in production release builds (panic vs. silent wrap), but the missing validation itself is a confirmed, reachable code defect since `verify_ancestry_proof` lacks the zero-check that its sibling `verify_leaves` explicitly has.

## Recommendation
Add an eager check, e.g. `ensure!(ancestry_proof.prev_leaf_count >= 1, Error::Verify)`, at the top of `verify_ancestry_proof` in `substrate/frame/merkle-mountain-range/src/mmr/mmr.rs`, before the subtraction and any call into `mmr_lib` — mirroring the zero/consistency checks already present in `Pallet::verify_leaves`.

## Proof of Concept
1. Construct `AncestryProof { prev_peaks: vec![], prev_leaf_count: 0, leaf_count: N, items: vec![] }` with any `leaf_count`/hash values acceptable to the outer SCALE `Decode`.
2. Call `pallet_mmr::Pallet::<T>::verify_ancestry_proof(root, ancestry_proof)` directly, or route it through `pallet-beefy-mmr::Pallet::<T>::is_non_canonical` with a `commitment.block_number` whose derived `commitment_leaf_count` equals `0`.
3. Execution reaches `mmr_lib::helper::leaf_index_to_mmr_size(ancestry_proof.prev_leaf_count - 1)` at [6](#0-5)  with `prev_leaf_count = 0`, causing a `u64` underflow — panicking in debug/overflow-checked builds or producing a corrupted `u64::MAX`-derived size fed into `mmr_lib` internals in release builds.
