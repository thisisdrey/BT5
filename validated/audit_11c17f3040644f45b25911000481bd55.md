### Title
Underwater debt positions at the `debtFloorInUsd` boundary become permanently unliquidatable due to the `maxLiquidable` cap in `Pool.liquidate` — (File: contracts/Pool.sol)

### Summary
Analogous to CVE-2016-9817 — where an unprivileged guest crafts an exception state that the privileged abort handler cannot process, crashing the host — an unprivileged borrower in Metronome can engineer a debt position whose state the liquidation handler cannot process: any `Pool.liquidate` call reverts, so the position can never be liquidated. If the position is underwater, it permanently accumulates bad debt against the protocol. The defect lives entirely in `Pool.liquidate` (contracts/Pool.sol:537-596) and is reachable by a normal user via `DebtToken.issue`.

### Finding Description
`Pool.liquidate` enforces two checks on `amountToRepay_` (contracts/Pool.sol:567-579):

```solidity
if (amountToRepay_.wadDiv(_debtTokenBalance) > maxLiquidable) {
    revert AmountGreaterThanMaxLiquidable();
}

if (debtFloorInUsd > 0) {
    uint256 _newDebtInUsd = masterOracle().quoteTokenToUsd(
        address(syntheticToken_),
        _debtTokenBalance - amountToRepay_
    );
    if (_newDebtInUsd > 0 && _newDebtInUsd < debtFloorInUsd) {
        revert RemainingDebtIsLowerThanTheFloor();
    }
}
```

The second check forces the post-liquidation debt to be either exactly `0` or `>= debtFloorInUsd`. The first check caps `amountToRepay_` at `debt * maxLiquidable` (deployed configurations use values like 50%). Therefore, for any account whose total debt `D` satisfies `D * maxLiquidable < D` while `D - D*maxLiquidable` cannot reach `0` — i.e., whenever `D` is close enough to the floor that a full repay would exceed `maxLiquidable` — **no value of `amountToRepay_` satisfies both checks**.

Concretely, with `debtFloorInUsd = F` and `maxLiquidable = m < 1`, an account with debt in USD `D` is unliquidatable whenever the only admissible repay amount is `D` itself and `D > D * m`. The sharpest case is `D == F` (debt exactly at the floor): the floor check requires repaying the entire `D`, but `amountToRepay_.wadDiv(D) = 100% > m` triggers `AmountGreaterThanMaxLiquidable`. Any `amountToRepay_ < D` leaves `D - amountToRepay_` in `(0, F)` and triggers `RemainingDebtIsLowerThanTheFloor`. The revert happens before any seizure, so the position is frozen in whatever health state it is in — including deeply underwater.

The same `RemainingDebtIsLowerThanTheFloor` trap applies symmetrically in `DebtToken.repay` (contracts/DebtToken.sol:442-451), but `repayAll` exists to escape it for willing borrowers; there is no equivalent escape for `liquidate` — a liquidator cannot erase the debt without hitting the `maxLiquidable` cap, and cannot partially repay without hitting the floor.

The attacker reaches this state with purely public calls:

1. Deposit collateral via `DepositToken.deposit` (contracts/DepositToken.sol:406 area) and mint synthetic debt via `DebtToken.issue` so that total debt in USD equals (or sits in the unliquidatable band around) `debtFloorInUsd`.
2. Let the position go underwater via ordinary market movement of the collateral price — or, per the scan rules, via same-transaction AMM/oracle quote manipulation of the `masterOracle().quoteTokenToUsd` reading for the collateral, since the health check and the floor check both consume oracle prices.
3. Once underwater, every `liquidate` call against the account reverts — the "abort handler" cannot process the crafted state, and bad debt accrues interest indefinitely.

Note that `debtFloorInUsd` and `maxLiquidable` are governor-set parameters, but the vulnerability is not a parameter choice — it is a missing edge case in the code: `liquidate` has no exception path for "repay-all that exceeds `maxLiquidable`" even though repaying all is the only floor-compliant outcome. The tests confirm both revert paths are live (test/Pool.test.ts:408-436, 439-451).

### Impact Explanation
- **Protocol insolvency / bad debt**: a deliberately under-collateralized, unliquidatable position lets its debt grow via interest while the remaining collateral can never be seized. Synthetic token supply remains backed by insufficient collateral.
- **Permanent freezing**: seized-value accounting aside, the position's locked collateral (`lockedBalanceOf` at contracts/DepositToken.sol:266-270) can never be released through liquidation; it is frozen until the protocol itself intervenes.
- **Liveness break**: the liquidation safety mechanism — the protocol's core solvency invariant — is disabled for an entire class of positions reachable by any user.

### Likelihood Explanation
The window is narrow (debt must land in the band around `debtFloorInUsd` where `maxLiquidable` blocks full repay), but it is fully attacker-controllable: the attacker chooses their mint amount at `issue` time and chooses when collateral prices move against the position. No privileged role, keeper failure, or malicious endpoint is required; `liquidate` is permissionless and the reverts are deterministic. Cost to the attacker is bounded by the collateral they sacrifice, which is what makes the underwater/unliquidatable combination the damaging case.

### Recommendation
In `Pool.liquidate`, exempt full-debt repayments from the `maxLiquidable` cap, or exempt repayments that bring debt to exactly `0` from both constraints — e.g., compute `amountToRepay_` bounds as: allow `amountToRepay_ == _debtTokenBalance` unconditionally, and apply the `maxLiquidable`/floor checks only to partial liquidations. Alternatively, skip the `debtFloorInUsd` check in `liquidate` entirely, since the floor exists to prevent dust debt creation by borrowers — a liquidator reducing debt can never worsen dust conditions below what already exists.

### Proof of Concept
Hardhat sketch against the existing test scaffolding in test/Pool.test.ts:

```ts
// given: pool has debtFloorInUsd = F and maxLiquidable = 0.5 (50%)
await pool.updateDebtFloor(FLOOR_USD)           // existing config value
await pool.updateMaxLiquidable(parseEther('0.5'))

// attacker deposits MET and issues debt so debtInUsd == FLOOR_USD
await met.connect(attacker).approve(msdMET.address, MaxUint256)
await msdMET.connect(attacker).deposit(collateral, attacker.address)
await msEthDebtToken.connect(attacker).issue(debtAmount, attacker.address) // debtInUsd == FLOOR_USD

// collateral price drops; position is now unhealthy / underwater
await masterOracle.updatePrice(met.address, droppedPrice)
const {_isHealthy} = await pool.debtPositionOf(attacker.address)
expect(_isHealthy).to.be.false

const debt = await msEthDebtToken.balanceOf(attacker.address)

// full repay: blocked by maxLiquidable
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, debt, msdMET.address)
).to.be.revertedWithCustomError(pool, 'AmountGreaterThanMaxLiquidable')

// any partial repay: blocked by floor
await expect(
  pool.connect(liquidator).liquidate(msEth.address, attacker.address, debt.div(2), msdMET.address)
).to.be.revertedWithCustomError(pool, 'RemainingDebtIsLowerThanTheFloor')

// => position is permanently unliquidatable; bad debt accrues via accrueInterest
```

A fork test should confirm against the deployed `debtFloorInUsd` and `maxLiquidable` values in the `deployments/` artifacts to verify the unliquidatable band is non-empty on live configuration.
