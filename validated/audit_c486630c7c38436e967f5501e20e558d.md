### Title
Function-call access key allowance restriction is not enforced for delegate actions (meta-transactions) - (File: `runtime/runtime/src/actions.rs`)

### Summary
The reported bug is about a restriction tied to a specific identity ("Radical App International cannot call `refund`") that can be trivially bypassed by moving the restricted asset (tokens) through an unrestricted path (a transfer to another address) before invoking the sensitive function. The nearcore analog is the `FunctionCallPermission` access key: it is meant to cap how much of an account's balance a given (possibly less-trusted) key can spend, via the `allowance` field. That cap is enforced only on the direct transaction path, but not when the same key is used to sign a `DelegateAction` submitted through a relayer (meta-transaction, NEP-366).

### Finding Description
`FunctionCallPermission.allowance` is documented to be "a balance limit to use by this access key to pay for function call gas and transaction fees" [1](#0-0) . On the regular transaction path, `verify_and_charge_tx_ephemeral` enforces this by calling `check_and_compute_new_allowance`, which subtracts the total cost from the allowance and fails with `NotEnoughAllowance` on underflow [2](#0-1) .

When the same `FunctionCallPermission` key is used to sign a `DelegateAction` instead, `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` re-validates the access key's nonce, receiver-id match, method-name match, single-action/no-deposit restriction — but never calls `check_and_compute_new_allowance` or otherwise checks/decrements `allowance` [3](#0-2) . All gas and fee costs for a meta-transaction are instead paid by the relayer, who prepays everything, and the deposit/gas refunds route to the sender/relayer independent of the FunctionCallPermission's allowance bookkeeping [4](#0-3) .

This is explicitly acknowledged in nearcore's own architecture docs: "For allowance, however, there is no check. All costs have been covered by the relayer. Hence, even if the allowance of the key is insufficient to make the call directly, indirectly through meta transaction it will still work... if someone were to limit a function access key to one trivial action by setting a very small allowance, that is circumventable by going through a relayer." [5](#0-4) 

The relayer path doesn't let an attacker steal the balance/allowance restriction outright — the relayer pays the gas/deposit costs — but it means a key that was deliberately scoped with a small `allowance` (the exact mechanism used to bound how much of the account's *own funds* the key can authorize spending of, when combined with any downstream promise/deposit logic dependent on this key's authorization) loses that bound whenever invoked via a delegate action. Just like the token-contract case where the restriction ("this address cannot call `refund`") is bypassed by moving the token to an unrestricted address first, here the restriction ("this access key can authorize spending of at most `allowance`") is bypassed by moving the same authorization through an unrestricted path (the delegate/meta-transaction receipt) instead of the direct transaction path.

### Impact Explanation
An account owner who issues a `FunctionCallPermission` access key with a limited `allowance` to a semi-trusted party (e.g., a bot, dApp, or automation service) expects that party's authority to be capped by `allowance`. If that key-holder colludes with, or is, a relayer (or simply relays their own signed delegate actions through any relayer), the allowance cap is never enforced, and the key can be used to authorize function calls at will without account-balance-based limitation on the direct-transaction path, undermining the security guarantee the key issuer relied on. This is an authorization-boundary bypass on a security control (bounded access-key authority) reachable purely from ordinary client transactions/meta-transactions, without any privileged, malicious-node, or off-protocol assumption.

### Likelihood Explanation
This requires no special preconditions beyond having a `FunctionCallPermission` key and using the meta-transaction (`DelegateAction`/`DelegateV2`) path, which is standard NEP-366 functionality available to any account. It is trivially reproducible and already flagged internally as "circumventable," indicating the team is aware but the enforcement gap remains in `validate_delegate_action_key`.

### Recommendation
In `validate_delegate_action_key` (`runtime/runtime/src/actions.rs`), when the signing key carries a `FunctionCallPermission` with a finite `allowance`, invoke the same allowance-check/decrement logic used in `verify_and_charge_tx_ephemeral` (`check_and_compute_new_allowance` in `runtime/runtime/src/verifier.rs`) against the relayer-prepaid cost of the inner actions, persisting the updated allowance to the access key exactly as the direct-transaction path does, and rejecting the delegate action with `NotEnoughAllowance` on shortfall.

### Proof of Concept
1. Account `alice.near` adds a `FunctionCallPermission` access key `K` with `allowance = 1 yoctoNEAR`, `receiver_id = "app.near"`, restricted to method `"do_thing"`.
2. Sending a direct transaction signed by `K` calling `app.near::do_thing` with any nonzero effective cost fails with `NotEnoughAllowance` via `verify_and_charge_tx_ephemeral`.
3. Instead, wrap the same `FunctionCall` action in a `DelegateAction`/`DelegateActionV2` signed by `K`, and have any relayer (e.g. `bob.near`) submit it as a `SignedTransaction` with `Action::Delegate`/`Action::DelegateV2`.
4. `apply_delegate_action` → `validate_delegate_action_key` validates nonce/receiver/method but performs no allowance check [3](#0-2) ; the call to `app.near::do_thing` succeeds, funded entirely by the relayer, even though `K`'s allowance of 1 yoctoNEAR should have blocked any such invocation on the direct path.

## Function access keys in meta transactions

Assume alice sends a meta transaction and signs with a function access key.
How exactly are permissions applied in this case?

Function access keys can limit the allowance, the receiving contract, and the
contract methods. The allowance limitation acts slightly strange with meta
transactions.

But first, both the methods and the receiver will be checked as expected. That
is, when the delegate action is unwrapped on Alice's shard, the access key is
loaded from the DB and compared to the function call. If the receiver or method
is not allowed, the function call action fails.

For allowance, however, there is no check. All costs have been covered by the
relayer. Hence, even if the allowance of the key is insufficient to make the call
directly, indirectly through meta transaction it will still work.

This behavior is in the spirit of allowance limiting how much financial
resources the user can use from a given account. But if someone were to limit a
function access key to one trivial action by setting a very small allowance,
that is circumventable by going through a relayer. An interesting twist that
comes with the addition of meta transactions.
