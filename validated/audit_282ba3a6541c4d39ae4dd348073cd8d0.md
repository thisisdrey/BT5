### Title
Out-of-bounds read in ZIP central directory parsing due to unchecked length fields - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in Bazel's bundled `ijar` tool parses ZIP/JAR central directory headers (CDH) using length fields (`file_name_length`, `extra_field_length`, `file_comment_length`, and the nested Zip64 extra-field `data_size`) taken directly from attacker-controlled archive bytes, with no validation that the resulting pointer advances stay within the memory-mapped input file. This mirrors the LAPACK `*LARRV` class of bug: a size/length value read from untrusted input is used to advance a cursor/array index without bounds checking, leading to an out-of-bounds read.

### Finding Description
`ProcessCentralDirEntry` reads several 16-bit length fields straight out of the CDH bytes and blindly advances the parsing cursor `p`: [1](#0-0) 

Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before every field read to check the mapped-file bounds: [2](#0-1) 

`ProcessCentralDirEntry` performs **no** equivalent bounds check anywhere against `input_file_->Length()` / `in_length` before consuming `file_name_length`, `extra_field_length`, or `file_comment_length`. It also parses a nested Zip64 extra-field sub-loop that reads a `header_id`/`data_size` pair and then calls `get_u8le(extra)` (an 8-byte read) without verifying that at least 8 bytes remain inside the declared extra-field window, and without checking that `extra_p` cannot run past the actual mapped buffer end: [3](#0-2) 

The only bound checked before iterating entries is that the *whole* central directory fits in the file: [4](#0-3) 

That check only guards the aggregate central-directory size, not the internal, attacker-controlled per-entry length fields. A single CDH entry with an inflated `file_name_length`/`extra_field_length`/`file_comment_length` (or a Zip64 extra field with a bogus `data_size`) can push `p`/`extra_p` past the end of the mapped file. Both callers of `ProcessCentralDirEntry` — `InputZipFile::ProcessNext()` (used by the real extraction path) and `InputZipFile::CalculateOutputLength()` — then dereference this now out-of-bounds pointer on the next loop iteration via `get_u4le(p)`: [5](#0-4) [6](#0-5) 

### Impact Explanation
ijar is invoked during ordinary Java builds to strip a JAR down to its ABI-only interface jar; its input is any JAR reachable as a compile-time dependency, including JARs fetched from external repositories/mirrors (`http_jar`, `http_archive`, `maven_install`/`java_import`, etc.). An attacker who controls or compromises such a dependency URL can publish a byte-perfect, checksum-matching but structurally malformed JAR (checksums pin the bytes, not structural validity, so a declared `sha256`/integrity hash does not prevent this). Once fetched and passed through ijar, the malformed CDH triggers an out-of-bounds read of process memory, which can crash the Bazel build (denial of service against the build, not the underlying rule though it is reachable purely through data) or, more importantly, disclose adjacent heap/mmap memory contents that get copied into the interface jar’s central directory / filename buffer that is subsequently written to the build output artifact.

### Likelihood Explanation
The path is reachable with no privileges beyond publishing a JAR file consumed by a victim’s build (any `http_jar`/dependency the project depends on) — no root-repo Starlark trust, no local machine access, and no reliance on a compromised registry defeating an integrity check. Because ijar is exercised on essentially every third-party JAR dependency used at compile time in Java targets, the surface is broadly reachable, and the missing bounds checks are structural (present since the code predates `EnsureRemaining`-style hardening applied only to the local-file-header path).

### Recommendation
Add the same `EnsureRemaining`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`: before consuming `file_name_length`, `extra_field_length`, `file_comment_length`, and before each `get_u2le`/`get_u8le` read inside the Zip64 extra-field loop, verify the remaining distance to the mapped-file end (or to the central directory end previously validated by `FindZipCentralDirectory`). Reject the archive with an error instead of advancing `p`/`extra_p` past validated bounds.

### Proof of Concept
Craft a JAR whose ZIP central directory contains a single CDH entry where:
- `file_name_length` + `extra_field_length` + `file_comment_length` sums to a value that pushes the cursor past `zipdata_in_ + in_length`, or
- The Zip64 extra field declares `header_id == ZIP64_EXTRA_FIELD_TAG` with `data_size` smaller than 8 but where the subsequent `get_u8le(extra)` still reads 8 bytes, or `data_size` large enough that `extra_p` overtakes `p` and continues looping past the mapped buffer.

Feed this JAR as an `ijar` input (e.g., via `bazel-bin/third_party/ijar/ijar malicious.jar out.jar`, or as a dependency JAR consumed by a `java_import`/interface-jar action) and observe a crash or heap-adjacent bytes leaking into `out.jar`'s parsed filename/attributes, reproducible as a standalone `third_party/ijar/zip_test.cc`-style unit test that constructs the malformed CDH bytes in memory and calls `ProcessCentralDirEntry`/`ProcessNext` directly.

                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.

    return false;
  }

    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
