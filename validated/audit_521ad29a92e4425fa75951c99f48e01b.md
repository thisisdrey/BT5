This is exactly the analog. `PrecompiledContracts.extractBytes` at [1](#0-0)  performs `Arrays.copyOfRange(data, offset, offset + len)` with no validation that `offset` and `offset+len` are within `data.length` — the exact same "trust an attacker-controlled length/offset field then advance/read without a bounds check" pattern as the FastNetMon IHL bug. `offset` and `len` are derived from `extractBytesArray`/`extractSigArray`, which read `bytesOffset` and `bytesLen` straight from caller-supplied `DataWord[] words` via `intValueSafe()` with no range checks against `data.length`: [2](#0-1) . `words` itself comes from decoding the raw precompile call `data` (attacker-controlled contract-call input), so a malicious contract call can set `bytesOffset`/`bytesLen`/`len` to arbitrary attacker-chosen values.

### Title
Unbounded `offset`/`len` in `PrecompiledContracts.extractBytes` causes out-of-bounds read / node crash - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
`extractBytes(byte[] data, int offset, int len)` calls `Arrays.copyOfRange(data, offset, offset + len)` directly, trusting `offset` and `len` values that originate from attacker-supplied ABI-encoded precompile call data (`extractBytesArray`/`extractSigArray`), without first validating that `offset >= 0`, `len >= 0`, and `offset + len <= data.length`.

### Finding Description
`extractBytesArray` and `extractSigArray` decode a length-prefixed array structure directly from the raw `DataWord[] words` array (derived from the caller's `data` payload to a precompiled contract), computing `bytesOffset` and `bytesLen`/`SIG_LENGTH` purely from `intValueSafe()` on attacker-controlled words: [3](#0-2) . These are passed straight into `extractBytes`, which performs `Arrays.copyOfRange(data, offset, offset + len)` with zero bounds validation [1](#0-0) . This mirrors the CVE-2026-48682 pattern exactly: a length/offset field taken from untrusted input is used to slice a buffer without confirming the slice fits inside the buffer bounds derived from a prior, smaller validated region. `extractBytes32Array` has the analogous flaw for `words[offset + i + 1]` indexing without checking `offset + len` against `words.length` [4](#0-3) .

Any smart contract call that reaches one of these precompiled contracts (e.g. batch-validate-sign style precompiles that use `extractBytesArray`/`extractSigArray`) with crafted `data` can trigger `Arrays.copyOfRange` with an out-of-range `offset`/`len`, which throws `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`OutOfMemoryError` (if `len` is huge) inside VM execution.

### Impact Explanation
An uncaught runtime exception thrown deep inside precompiled-contract execution during TVM opcode dispatch can propagate past normal EVM revert handling if not caught by the surrounding actuator, causing the node's transaction processing/block application path to throw unexpectedly — this can crash or halt the executing node when this code path is hit during block replay by all nodes (chain-wide DoS / node crash), which is one of the accepted "concrete" impacts (node crash or halt).

### Likelihood Explanation
Reachable by any unprivileged party who can call a contract triggering this precompiled contract with attacker-controlled call data — no special privileges required, single crafted transaction is sufficient. However, exploitability depends on whether the specific precompile using these helpers is enabled/reachable in this repo's active TVM feature set, which I could not fully confirm from available context (I did not locate the top-level `execute()` dispatcher wiring these helper methods to a specific active opcode/precompile address in the code retrieved).

### Recommendation
Add explicit bounds checks in `extractBytes` (reject if `offset < 0 || len < 0 || offset + len > data.length`) and in `extractBytesArray`/`extractSigArray`/`extractBytes32Array` validate `len`, `bytesOffset`, and `bytesLen` against `words.length` and `data.length` before use, mirroring the `verifyLength`/`subBytes` bounds-checking pattern already used elsewhere in this codebase (e.g. `RLP.verifyLength` [5](#0-4)  and `ContractEventParser.subBytes` [6](#0-5) ).

### Proof of Concept
Craft a transaction calling the precompiled contract that invokes `extractBytesArray`/`extractSigArray` with ABI-encoded `data` where the length word (`words[offset]`) is a large value and/or an inner offset/length word is set so that `bytesOffset + offset + 2) * WORD_SIZE + bytesLen` exceeds `data.length`. This causes `Arrays.copyOfRange` in `extractBytes` to throw an unhandled exception during precompile execution, which — unless caught by the actuator's `execute()`/energy-metering wrapper — surfaces during block application and can halt/crash the node. Full end-to-end confirmation requires locating the exact precompile address/opcode dispatch and its exception-handling wrapper, which was not fully visible in the retrieved context; a Devin session with full repo access could confirm the dispatch path and whether exceptions here are caught before impacting block application.
