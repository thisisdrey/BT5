This confirms `ERC20Matcher` is `IsLocalAccountKey20`-gated: it matches **any** location of the shape `(0, [AccountKey20 { key, .. }])` and converts it directly to an `H160` via `AccountKey20ToH160::convert` [1](#0-0) . There is no allow-list, registry, or vetting step — any address (including a freshly, permissionlessly deployed `pallet-revive` contract) is accepted as a valid ERC20 asset id for this transactor.

This validates the claim's core exploit precondition and confirms the code exactly as described:

- `withdraw_asset_with_surplus` calls the target contract's `transfer` and, on a decoded `true` return, credits `AssetsInHolding` with the nominal `amount` requested — not a measured balance delta [2](#0-1) .
- `deposit_asset_with_surplus` mirrors this on the debit side, again trusting only the decoded boolean return value from the checking account's `transfer` call [3](#0-2) .
- The `Erc20Credit` type's own doc comment concedes this design: "does not perform runtime-level balance enforcement... the actual balance constraints are enforced by the ERC20 smart contract itself rather than the runtime" [4](#0-3) .
- The Asset Hub Westend runtime wires this transactor with `ERC20Matcher` and a single pooled `ERC20TransfersCheckingAccount` shared across all ERC20 asset flows [5](#0-4) , confirming the shared-custody-account concern in the claim's impact section.
- The standard `xcm-builder` fungibles adapter, by contrast, relies on runtime-enforced `can_deposit`/`mint_into` and `can_withdraw`/`burn_from` rather than trusting an external contract's self-reported return value [6](#0-5) .

Given that (a) contract deployment via `pallet-revive` is unprivileged, (b) `ERC20Matcher` imposes no allow-list and accepts any `AccountKey20` address, and (c) the transactor logic verifiably trusts the requested `amount` and the contract's own return value rather than measuring `balanceOf` deltas, the claim's technical premise is accurate and reproducible against this repository's code as written.

Audit Report

## Title
ERC20 Asset Transactor credits/debits XCM holding with the requested amount without verifying real balance movement - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` never measure the ERC20 checking account's actual balance before/after the ERC20 `transfer` call; they trust only that `bare_call` succeeded, did not revert, and ABI-decoded to `true`, then unconditionally mint/burn the *requested* `amount` in `AssetsInHolding` via `Erc20Credit(amount)`. Because `ERC20Matcher` (`IsLocalAccountKey20` + `AccountKey20ToH160`) accepts any local `AccountKey20` location with no allow-list, an attacker can deploy an arbitrary ERC20-compatible contract on `pallet-revive` whose `transfer` returns `true` while moving less (or none) of the requested amount, desynchronizing the XCM holding register from the real ERC20 ledger of the shared `ERC20TransfersCheckingAccount`.

## Finding Description
`withdraw_asset_with_surplus` calls `IERC20::transferCall{ to: checking_address, value: amount }` via `pallet_revive::Pallet::<T>::bare_call`, and on success/no-revert/decoded-`true`, credits holding with `Erc20Credit(amount)` — the nominal instructed value, not a measured delta. `deposit_asset_with_surplus` mirrors this: it transfers from the shared `TransfersCheckingAccount` to the beneficiary and only checks the decoded return value before treating the deposit as fully successful. The `Erc20Credit` imbalance type's own documentation states it performs no runtime-level balance enforcement, delegating that entirely to the target contract. `ERC20Matcher` in `assets_common::lib.rs` matches any `(0, [AccountKey20{..}])` location and converts it straight to the callee `H160` with no registry/allow-list check, so the callee contract address is fully attacker-chosen. The Asset Hub Westend runtime wires all ERC20 flows through a single pooled `ERC20TransfersCheckingAccount`. A non-standard/malicious ERC20 contract (fee-on-transfer, no-op transfer that still returns `true`, or arbitrary internal-ledger manipulation) causes the recorded `Erc20Credit`/debit to diverge from the real balance change of the checking account, unlike the standard `xcm-builder` fungibles adapters which rely on runtime-enforced `can_deposit`/`mint_into`/`can_withdraw`/`burn_from` instead of a foreign contract's self-reported return value.

## Impact Explanation
The shared checking account's ERC20 balance backs all XCM holding credits/debits for every ERC20 asset routed through this transactor. Divergence between the recorded amount and the real balance delta breaks the value-conservation invariant for contract-held value in the pooled checking account: it can cause legitimate `DepositAsset`/`ExchangeAsset` operations for other users to fail against real balance while their holding credit says otherwise, or leave real tokens permanently stuck in the checking account with no corresponding holding credit ever created (unclaimable/trapped value). This matches the "permanent user-fund... lock" and "theft or unbacked mint" categories of the impact gate.

## Likelihood Explanation
Deploying an arbitrary ERC20-compatible contract via `pallet-revive` is unprivileged, requires no governance, no compromised relayer/validator, and no key leak — only normal contract deployment plus standard `WithdrawAsset`/`DepositAsset` XCM instructions referencing the attacker's contract address as the `AccountKey20` asset id, which `ERC20Matcher` accepts unconditionally.

## Recommendation
Query the checking account's (and/or beneficiary's) real ERC20 `balanceOf` immediately before and after the `bare_call` to `transfer`, and use the measured delta — not the requested `amount` — to construct/destroy `Erc20Credit` in `AssetsInHolding`. If the measured delta differs from `amount`, fail with `XcmError::FailedToTransactAsset` or credit/debit only the measured amount, consistent with the enforcement pattern used by `xcm-builder`'s fungible/fungibles adapters.

## Proof of Concept
1. Deploy a Solidity-compatible contract on `pallet-revive` whose `transfer(address,uint256)` always ABI-returns `true` but moves less than (or none of) the requested `value` internally (fee-on-transfer or intentionally malicious logic).
2. Register this contract's `H160` address as an `AccountKey20` asset id and execute an XCM program via `pallet_xcm::execute` invoking `WithdrawAsset((AccountKey20{key: erc20_address}, amount))`, mirroring `withdraw_and_deposit_erc20s` in `cumulus/parachains/runtimes/assets/asset-hub-westend/tests/tests.rs` but substituting the malicious contract for `MyToken`.
3. Observe `withdraw_asset_with_surplus` credits `AssetsInHolding` with the full nominal `amount` even though the checking account's real ERC20 balance increased by less.
4. Chain a subsequent `DepositAsset`/`ExchangeAsset` using the over-credited holding to demonstrate the checking account being drained below what other users' legitimate credits assume is backed, or demonstrate real tokens accumulating in the checking account with no corresponding holding credit.
