### Title
Unbacked ERC20 credit due to trusting requested amount instead of actual received balance in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls the target Solidity ERC20 contract's `transfer(to, value)` function and, upon a `true` boolean return, unconditionally credits the XCM `AssetsInHolding` register with the full requested `amount` via `Erc20Credit(amount)` — without ever checking the actual token balance received by the `TransfersCheckingAccount` before/after the call. This is the exact bug class from the external report: trusting the nominal transferred amount instead of measuring the real balance delta, which silently breaks accounting for fee-on-transfer, deflationary, or rebasing ERC20 tokens.

### Finding Description
In `withdraw_asset_with_surplus`: [1](#0-0) 

the transactor invokes `IERC20::transferCall{ to: checking_address, value: amount }` on an arbitrary, matcher-approved ERC20 contract (`asset_id`) via `pallet_revive::Pallet::<T>::bare_call`. It only inspects the ABI-decoded boolean return value (`is_success`). If `true`, it mints `Erc20Credit(amount)` — the *requested* amount, not the amount the `checking_address` actually gained — into the XCM holding register, which the XCM executor treats as fully-backed fungible value.

The mitigation recommended in the source report (snapshot `balanceOf` before/after the transfer and use the delta) is exactly what is missing here. ERC20's `transfer` returning `true` only guarantees the call didn't revert; it says nothing about the exact amount credited to the recipient when the token implements a transfer fee, burn-on-transfer, or rebase mechanism. Since `Matcher::matches_fungibles` accepts any contract address registered by governance/asset registration without constraining it to "vanilla" OpenZeppelin-style ERC20 semantics, a token with non-standard transfer semantics (or one that later becomes fee-on-transfer/rebasing via a proxy upgrade) will cause `checking_address`'s real balance to grow by less than `amount` while the runtime's ledger (the XCM holding, and any subsequent minted representation of that credit such as a foreign asset on Asset Hub) records the full nominal `amount`.

The symmetric leak exists in `deposit_asset_with_surplus`: [2](#0-1) 

which transfers `amount` out of the checking account without verifying that `amount` was actually debited/received by the beneficiary, further compounding the drift between "accounted" and "actual" checking-account balance over repeated cycles.

### Impact Explanation
Because the checking account's on-chain ERC20 balance is the *sole* backing for all XCM credits that reference that asset, but the runtime bumps its internal ledger by the full nominal `amount` regardless of what was truly received, repeated withdraw/deposit cycles with a non-standard ERC20 (fee-on-transfer, deflationary/burn, or rebasing) cause the sum of credited holdings to exceed the checking account's real token balance. This is an unbacked-mint-class issue: value is created in the XCM/asset-accounting layer that is not backed by real tokens held in escrow, so eventually redemptions by legitimate holders fail or the last claimants cannot be paid — a permanent value-conservation break for one specific class of registered ERC20 asset, matching the "theft or unbacked mint/unlock" and "duplicate settlement or payout" impact categories in scope. No admin, relayer, or validator compromise is needed — an ordinary, unprivileged XCM sender using a chain-listed ERC20 with non-1:1 transfer semantics triggers this automatically as part of normal use.

### Likelihood Explanation
Likelihood depends on whether/how ERC20 contracts are permitted onto the `Matcher::matches_fungibles` allow-list for this transactor; if governance registers any token that isn't a byte-for-byte vanilla `_transfer`/`_update` implementation (fee-on-transfer, reflection/deflationary, rebasing, or an upgradeable proxy that later adds such logic), every transfer of that asset through this transactor silently desynchronizes escrow accounting. Given `pallet-revive` enables arbitrary EVM-compatible contracts to be deployed and referenced as XCM-transactable assets on Asset Hub, and no on-chain guard restricts registered ERC20s to strictly 1:1 transfer semantics, this is a realistic and repeatable condition, not a contrived edge case.

### Recommendation
Do not trust the boolean return of `transfer()` as proof that `amount` was received. Snapshot `balanceOf(checking_address)` before and after the `bare_call` in `withdraw_asset_with_surplus`, compute the actual delta, and credit `Erc20Credit(actual_received)` instead of `Erc20Credit(amount)`. Symmetrically, in `deposit_asset_with_surplus`, verify the beneficiary's balance delta (or the checking account's balance delta) matches `amount` before considering the deposit complete, and propagate any shortfall back into the `AssetsInHolding` (mirroring how `pallet-assets::do_transfer` already returns the "actual amount placed into dest" rather than assuming the requested amount was moved, per `substrate/frame/assets/src/functions.rs` `do_transfer`).

### Proof of Concept
1. Governance/asset registration links a Solidity ERC20 contract `T` to an XCM asset id via `Matcher` for `ERC20Transactor`; `T.transfer()` deducts a 5% fee from the transferred amount before crediting the recipient but still returns `true`.
2. A user sends an XCM program that withdraws `1000` units of `T` from their account via `withdraw_asset_with_surplus`.
3. `ERC20Transactor` calls `T.transfer(checking_address, 1000)`; the contract only credits `checking_address` with `950` (5% fee), but returns `true`.
4. `is_success == true`, so the transactor creates `Erc20Credit(1000)` in the XCM holding register — 1000 units are now "backed" in the runtime's accounting although only 950 physically sit in `checking_address`.
5. This XCM holding can subsequently be deposited to a beneficiary (locally or cross-chain) for the full `1000`, e.g. via `deposit_asset_with_surplus`, transferring out of `checking_address` more than the escrow actually gained across repeated operations, eventually leaving `checking_address` unable to honor all outstanding claims — an unbacked/duplicate settlement condition affecting Asset Hub's ERC20-bridging ledger. 	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}

	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
		let weight_limit = WeightLimit::get();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(TransfersCheckingAccount::get()),
				asset_contract_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::deposit", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::deposit", ?return_value, "Return value");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::deposit", "Contract reverted");
				Err((what, XcmError::FailedToTransactAsset("ERC20 contract reverted")))
			} else {
				match IERC20::transferCall::abi_decode_returns_validate(&return_value.data) {
					Ok(true) => {
						tracing::trace!(target: "xcm::transactor::erc20::deposit", "ERC20 contract was successful");
						Ok(surplus)
					},
					Ok(false) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", "contract transfer failed");
						Err((
							what,
							XcmError::FailedToTransactAsset("ERC20 contract transfer failed"),
						))
					},
					Err(error) => {
						tracing::debug!(target: "xcm::transactor::erc20::deposit", ?error, "ERC20 contract result couldn't decode");
						Err((
							what,
							XcmError::FailedToTransactAsset(
								"ERC20 contract result couldn't decode",
							),
						))
					},
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::deposit", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err((what, XcmError::FailedToTransactAsset("ERC20 contract execution errored")))
		}
	}
