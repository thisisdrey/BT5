**Analysis:**

`VMLogic::promise_batch_action_transfer` reads the transfer amount via `self.memory.get_u128(&mut self.result_state.gas_counter, amount_ptr)`, which is implemented by the `memory_get!` macro in `Memory` as a fixed 16-byte read directly from **guest linear memory**, not from registers. [1](#0-0) [2](#0-1) 

The underlying `get_into` helper allocates an exact `[0u8; 16]` array and calls `MemoryLike::read_memory(offset, buf)`, which every implementation (e.g. `MockedMemory`) bounds-checks via `.get(range)` before copying — returning `Err(())` (mapped to `HostError::MemoryAccessViolation`) if the 16-byte window isn't entirely inside guest memory. [3](#0-2) [4](#0-3) 

There is no code path where `get_u128` reads from a register or where register storage and linear-memory reads overlap: registers are a completely separate `HashMap<u64, Rc<[u8]>>` structure (`Registers`) addressed only by explicit register APIs (`read_register`/`write_register`/`register_len`), and `get_u128`/`amount_ptr` never dispatch into that structure the way `get_memory_or_register` does for string arguments elsewhere. [5](#0-4) [6](#0-5) 

Consequently there is no "boundary check" bug in `get_u128` to exploit via corrupting adjacent register/heap metadata — the amount buffer is always a strict, checked linear-memory slice, unrelated to register contents. Additionally, within `promise_batch_action_transfer` itself, the decoded `amount` is a single local `Balance` value used identically for both `self.result_state.deduct_balance(amount)` and `self.ext.append_action_transfer(receipt_idx, amount)`, so there is no possibility of a decode/charge mismatch even in principle. [7](#0-6) 

The attack sequence described (`write_register` corrupting a "region" later read by `promise_batch_action_transfer`'s `amount_ptr`) has no code-level basis: `write_register` only ever writes into the isolated `Registers` map bounded by `registers_memory_limit`/`max_register_size`, and `amount_ptr` is resolved purely against guest linear memory with its own independent bounds check. [8](#0-7) [9](#0-8)

    /// Checks and updates registers usage limits before setting given register
    /// to value with given length.
    ///
    /// On success, returns Entry which must be used to insert the new value
    /// into the registers.
    fn check_set_register<'a>(
        &'a mut self,
        config: &LimitConfig,
        register_id: u64,
        data_len: u64,
    ) -> Result<Entry<'a, u64, Rc<[u8]>>> {
        if data_len > config.max_register_size {
            return Err(HostError::MemoryAccessViolation.into());
        }
        // Fun fact: if we are at the limit and we replace a register, we’ll
        // fail even though we should be succeeding.  This bug is now part of
        // the protocol so we can’t change it.
        if self.registers.len() as u64 >= config.max_number_registers {
            return Err(HostError::MemoryAccessViolation.into());
        }

        let entry = self.registers.entry(register_id);
        let calc_usage = |len: u64| len + size_of::<u64>() as u64;
        let old_mem_usage = match &entry {
            Entry::Occupied(entry) => calc_usage(entry.get().len() as u64),
            Entry::Vacant(_) => 0,
        };
        let usage = self
            .total_memory_usage
            .checked_sub(old_mem_usage)
            .unwrap()
            .checked_add(calc_usage(data_len))
            .ok_or(HostError::MemoryAccessViolation)?;
        if usage > config.registers_memory_limit {
            return Err(HostError::MemoryAccessViolation.into());
        }
        self.total_memory_usage = usage;
        Ok(entry)
    }
