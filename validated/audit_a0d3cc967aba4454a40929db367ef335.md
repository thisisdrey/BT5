### Title
`LinkRepositoryToObjectPool` links arbitrary attacker-supplied pool repositories into a target repository without verifying fork/origin relationship - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` accepts a `repository` and an `object_pool` purely from the RPC request and links them by writing an `objects/info/alternates` entry, with no check that the pool was actually derived from (or is otherwise legitimately associated with) the target repository.

### Finding Description
The handler `LinkRepositoryToObjectPool` validates only that the target repository exists (`s.locator.ValidateRepository`) and resolves the pool via `poolForRequest`, then calls `pool.Link(ctx, repo)`. [1](#0-0) 
The underlying `objectpool.Link` function unconditionally computes a relative path from the repo to the pool and writes it into the repo's alternates file, giving the repo full read access to every object in the pool. [2](#0-1) 
There is no verification anywhere in this call chain that the object pool's contents were seeded from a fork of the target repository, nor any check tying `object_pool` to a specific, previously-established origin. `CreateObjectPool` similarly creates a pool from any `origin` repository the caller names, only checking that the destination path looks like a pool path (`storage.IsPoolRepository`), not that the origin is a legitimate ancestor of any particular member. [3](#0-2) 
This is the direct structural analog of the reported bug class: just as a compromised chain could deploy a `TokenManager` for an attacker-controlled token and thereby create an "untracked" balance that gets folded into a tracked one, here a caller can create an object pool from any repository, populate it with arbitrary objects, and then link ("associate") that pool to an unrelated target repository, at which point Git treats all pool objects as available/reachable from the target — objects whose provenance was never validated against that repository's actual history or ownership.

### Impact Explanation
Once linked, all objects in the attacker-controlled pool become part of the effective object graph of the target repository via the alternates mechanism used for deduplication. [4](#0-3) 
This can be leveraged to inject content into a repository's effective object store, make previously-inaccessible or crafted blobs/commits resolvable through the target repository, or later corrupt the target when the pool is repacked/fetched (`FetchIntoObjectPool`) or disconnected (`DisconnectGitAlternates`), which hard-links pool objects directly into the member's own `objects/` directory, permanently materializing the injected/untracked content inside the victim repository. [5](#0-4) 
This mirrors the "untracked balance" escape in the report: state (objects) is introduced through a channel (pool) that is not validated against the target's actual provenance, then merged into the target as if it were trusted/native.

### Likelihood Explanation
`ObjectPoolService` RPCs are `MUTATOR` operations reachable by any Gitaly client holding a standard Gitaly auth token (i.e., not restricted to a privileged admin role), and are exercised as part of ordinary fork workflows (`CreateObjectPool` + `LinkRepositoryToObjectPool` are the documented lifecycle for forks). [6](#0-5) 
Exploitability, however, ultimately depends on whether the calling layer (e.g., Rails) always supplies a pool/repository pair with an already-verified fork relationship, or whether it trusts request fields naming arbitrary storage/relative paths — I could not fully verify the caller-side validation from within Gitaly's index, so this is noted as unverified/uncertain here.

### Recommendation
Persist the pool's true origin/provenance at `CreateObjectPool` time (e.g., record the origin repository identity in the pool's metadata), and have `LinkRepositoryToObjectPool` reject link requests where the target repository is not a verified descendant/fork of that recorded origin, analogous to the report's recommendation to store the original chain of each token and restrict deployments to it.

### Proof of Concept
Conceptually (subject to verifying caller-side authorization, which was not fully confirmed):
1. Attacker calls `CreateObjectPool` with `origin` set to a repository they control, populated with arbitrary crafted objects. [3](#0-2) 
2. Attacker calls `LinkRepositoryToObjectPool` naming a victim repository as `repository` and the attacker's pool as `object_pool`. [1](#0-0) 
3. `objectpool.Link` writes the alternates file unconditionally, making all attacker-supplied objects reachable from the victim repository. [7](#0-6) 
4. A later `DisconnectGitAlternates` or repack hard-links these objects permanently into the victim's own object directory, making the injected content indistinguishable from legitimately-owned objects. [8](#0-7)

```go
func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil
```

```go
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

	alternatesWriter, err := safe.NewLockingFileWriter(altPath)
	if err != nil {
		return fmt.Errorf("creating alternates writer: %w", err)
	}
	defer func() {
		if err := alternatesWriter.Close(); err != nil && returnedErr == nil {
			returnedErr = fmt.Errorf("closing alternates writer: %w", err)
		}
	}()

	if _, err := io.WriteString(alternatesWriter, expectedRelPath); err != nil {
		return fmt.Errorf("writing alternates: %w", err)
	}
```

```go
func (s *server) CreateObjectPool(ctx context.Context, in *gitalypb.CreateObjectPoolRequest) (*gitalypb.CreateObjectPoolResponse, error) {
	if in.GetOrigin() == nil {
		return nil, errMissingOriginRepository
	}

	poolRepo := in.GetObjectPool().GetRepository()
	if poolRepo == nil {
		return nil, errMissingPool
	}

	if !storage.IsPoolRepository(poolRepo) {
		return nil, errInvalidPoolDir
	}

	// repoutil.Create creates the repositories in a temporary directory. This means the repository is not created in the location
	// expected by the transaction manager. This makes sense without transactions, but with transactions, there's no real point in
	// doing so given a failed transaction's state is anyway removed. Creating the repository in a temporary directory is problematic
	// as the reference transaction hook is invoked for the repository from unexpected location, causing the transaction to fail to
	// associate the reference updates with the repository.
	//
	// Run the repository creation without the transaction in the context. The transactions reads the created repository's state from
	// the disk when committing it, so it's not necessary to capture the updates from the reference-transaction hook. This avoids the
	// problem for now, and later with transactions enabled by default we can stop creating repositories in unexpected locations.
	ctxWithoutTransaction := storage.ContextWithTransactionID(ctx, 0)
	if err := repoutil.Create(ctxWithoutTransaction, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.repositoryCounter, poolRepo, func(poolRepo *gitalypb.Repository) error {
		if _, err := objectpool.Create(
			ctxWithoutTransaction,
			s.logger,
			s.locator,
			s.gitCmdFactory,
			s.catfileCache,
			s.txManager,
			s.housekeepingManager,
			&gitalypb.ObjectPool{
				Repository: poolRepo,
			},
			s.localRepoFactory.Build(in.GetOrigin()),
		); err != nil {
			return err
		}

		return nil
	}, repoutil.WithSkipInit()); err != nil {
		return nil, structerr.New("creating object pool: %w", err)
	}
```

```go
// Disconnect disconnects the specified repository from its object pool. If the repository does not
// utilize an alternate object database, no error is returned. For repositories that depend on
// alternate objects, the following steps are performed:
//   - Alternate objects are hard-linked to the main repository.
```

```text
// ObjectPoolService is a service that manages the lifetime of object pools.
//
// An object pool is a separate repository that can be linked to from multiple object pool members
// in order to deduplicate common objects between them. This is mostly used in the context of
// repository forks.
//
// The typical lifetime of an object pool is as follows:
//
// 1. An object pool is created via CreateObjectPool from its primary pool member. Typically this
//    would be the repository that gets forked.
// 2. One or more repositories are linked to the object pool via LinkRepositoryToObjectPool. Each
//    object pool member linked to the repository will have its objects deduplicated when its
//    objects get repacked the next time.
// 3. The object pool is regularly updated via FetchIntoObjectPool. This is typically only done from
//    the primary object pool member.
// 4. Repositories may leave the object pool via DisconnectGitAlternates. There is not much of a
//    reason to do this for any repositories except for the primary object pool member in case it
//    for example becomes private.
// 5. When the object pool does not have any members anymore it gets deleted via DeleteObjectPool.
//    It is the responsibility of the caller to ensure that it really has no members left, else
//    any existing member will become corrupt.
```
