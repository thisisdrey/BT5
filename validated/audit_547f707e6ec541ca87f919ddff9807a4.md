## Analog Found

### Title
StackerDB chunk signatures lack domain separation, enabling cross-contract signature reuse - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` — the message that signers sign to authorize a StackerDB chunk write — commits only to `slot_id`, `slot_version`, and `data_hash`. It never binds the signature to the specific StackerDB smart contract (`smart_contract_id`) or to the chain/network. This is the same root cause as the reported `_checkSig` bug: a signature scheme with no domain separator, so a signature valid in one context (one deployment/contract) is also valid in another context where the equality check (signer address + slot) happens to line up.

### Finding Description
The signed digest is built purely from slot metadata: [1](#0-0) 

`auth_digest()` hashes `slot_id`, `slot_version`, and `data_hash` — nothing else — and `verify()` recovers the pubkey from this same digest and compares its hash to the target `StacksAddress`, explicitly ignoring the address version byte ("Note that the address version is ignored").

The verifier that decides whether to accept and store a received chunk uses `smart_contract_id` only to *look up* which address currently owns `slot_id` in that particular DB — the contract identity is never mixed into the signed bytes: [2](#0-1) 

Critically, in the signer StackerDB layout, many *different* smart contracts share the exact same slot-to-signer assignment. Each reward-cycle "signer set" (parity 0 or 1) has one shared list of `(signer, num-slots)` tuples, and every message-type sub-contract (`signers-{0,1}-{message_id}`, one per `MessageSlotID`, e.g. `Transactions`, `DkgResults`, `BlockResponse`, etc.) just re-reads that *same* page: [3](#0-2) [4](#0-3) [5](#0-4) 

Because a given signer occupies the *same* `slot_id` across all of these sibling contracts, and because the signature never encodes which contract it was made for, a chunk `(slot_id, slot_version, data, sig)` that a signer validly published in one `signers-{p}-{msg_id}` StackerDB will also pass `SlotMetadata::verify()` in a sibling `signers-{p}-{other_msg_id}` StackerDB, as long as `slot_version`/`max_writes` constraints in the target DB allow it. This exactly mirrors the reported bug: the signature "authenticates" a (signer, slot) pair but not the specific deployment/contract context it was intended for.

### Impact Explanation
Any remote, unauthenticated peer that has obtained a legitimately-signed chunk (chunks are freely readable/replicable via the public StackerDB sync/gossip and `GetChunk`/push-chunk RPCs) can replay that exact `(StackerDBChunkData)` into a *different* sibling StackerDB contract for the same signer's slot. `validate_received_chunk`/`try_replace_chunk` will accept it because signature verification only checks the (slot_id, slot_version, data_hash) digest against the target contract's slot owner — it has no way to detect the chunk was authorized for a different message-type contract. This is an unauthorized write into StackerDB state: data is stored under a signer's identity without that signer ever having produced (or intended) a message for that specific DB/message-type, and it is then further gossiped/relayed to other nodes as if it were a genuine signer message for that context (network-wide propagation of forged/misattributed data). It can also be used to consume/pollute a signer's slot version in the unintended contract, blocking legitimate future writes until the real signer's version catches up (denial of availability for that signer's channel).

### Likelihood Explanation
High. No privileged access, node secret, or victim key is required — only a previously-observed, validly-signed chunk (trivially obtainable from normal StackerDB replication) and knowledge of the sibling contract's identifier (`signers-{parity}-{message_id}`, which is a well-known, enumerable boot contract naming scheme). The replay is a byte-for-byte resend of already-public data into a different, equally public/writable endpoint.

### Recommendation
Bind the signed digest to the specific StackerDB contract (and ideally the chain/network) it is intended for, e.g. include `smart_contract_id` (and `chain_id`) inside `SlotMetadata::auth_digest()` so that a chunk signature is only valid for the exact contract/DB it was created for. Also stop ignoring the address version in `SlotMetadata::verify()` so mainnet/testnet addresses sharing the same `Hash160` cannot be conflated.

### Proof of Concept
1. Signer `S` with private key `k` legitimately signs and pushes a chunk to `signers-0-3` (e.g. `BlockResponse`) at `slot_id=7`, `slot_version=5`, producing `(sig, data, data_hash)` via `StackerDBChunkData::sign` [6](#0-5) .
2. Attacker fetches this chunk from any peer (public StackerDB sync) and observes `S` also owns `slot_id=7` in `signers-0-0` (e.g. `Transactions`), since both contracts read the same signer-slot page for parity 0.
3. Attacker submits the identical `StackerDBChunkData{slot_id:7, slot_version:5, sig, data}` to `signers-0-0` via the push/POST chunk path.
4. `validate_received_chunk` looks up the slot owner for `signers-0-0`/slot 7 (still `S`), calls `slot_metadata.verify(&addr)`, which succeeds because the digest never referenced which contract it was for [2](#0-1) .
5. The chunk (originally authorized only for `BlockResponse`) is accepted and stored/propagated as `S`'s content in the `Transactions` StackerDB.

    /// Get the digest to sign that authenticates this chunk data and metadata
    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Sign this slot metadata, committing to slot_id, slot_version, and
    /// data_hash.  Sets self.signature to the signature.
    /// Fails if the underlying crypto library fails
    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
