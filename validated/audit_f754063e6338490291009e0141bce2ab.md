### Title
Position-wide oracle dependency in `collateral-remove` permanently freezes healthy collateral if any single asset's price feed breaks - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`collateral-remove` in `v0-4-market.clar` computes the withdrawer's full-position health by evaluating **every** collateral and debt asset currently in the user's position mask, not just the asset being withdrawn. If any one of those assets' price feeds enters a permanent failure state (Pyth/DIA feed removed, stale beyond `max-staleness` with no further updates, or the underlying `pyth-storage`/`dia-oracle` contract call reverting), the entire health-evaluation step reverts, and the user can no longer withdraw *any* collateral from the position - including collateral types whose own oracles are perfectly healthy. This mirrors the Perennial `BalancedVault` M-16 bug class: a break in one "market" (here, one asset's oracle) permanently locks funds unrelated to that asset.

### Finding Description
In `collateral-remove`, when the user has debt, the function builds `assets` from the user's full position mask and evaluates notional value across the whole position: [1](#0-0) 

`get-notional-evaluation` and the underlying multi-asset pricing path require `price-resolve` (or `price-multi-resolve`) to succeed for **every** asset id present in the position's collateral/debt mask, because the resulting `collateral-value`/`debt-value` and the current egroup's LTV are needed to prove the post-withdrawal position remains healthy: [2](#0-1) 

`price-resolve` itself hard-fails (via `try!`/`unwrap!`) on any oracle malfunction — call failure, non-positive price, or stale/non-monotonic timestamp: [3](#0-2) 

and the batch resolver `price-multi-resolve`/`iter-price-multi` propagates any single asset's failure as a total failure for the whole batch: [4](#0-3) 

The oracle calls themselves (`call-pyth`, `call-dia`) can permanently fail if the upstream feed contract is paused/removed/broken, or if `check-confidence` rejects an out-of-range confidence interval indefinitely: [5](#0-4) 

Because `collateral-remove`'s "HAS DEBT" branch always re-prices **all** assets in the position's mask (not just the target asset), a permanent oracle break for *any one* collateral or debt asset the user holds makes `collateral-remove` unconditionally revert for that user — even when withdrawing a completely different, healthy collateral type. There is no path in `collateral-remove` (nor visible in `borrow`/`repay`) that lets a user withdraw an unrelated healthy asset while skipping pricing of the broken one; the only bypass is the "NO DEBT" branch, which does not apply to users who have any outstanding debt.

### Impact Explanation
This falls under **temporary/permanent freezing of funds**: any user who holds collateral in more than one asset type and simultaneously has debt will have all of their collateral (not just the collateral of the broken asset) permanently locked in the protocol as soon as one asset's oracle enters an unrecoverable failure state. Unlike a single-asset lending market where an oracle break only freezes that asset's positions, Zest's multi-asset egroup design means a single broken price feed can freeze a user's entire multi-asset position, exposing depositors of "healthy" collateral to risk caused by an unrelated asset — exactly the risk class flagged in Sherlock M-16 for Perennial's `BalancedVault`.

### Likelihood Explanation
Likelihood is non-trivial given the protocol integrates external Pyth and DIA feeds with strict per-asset `max-staleness` and confidence checks, and any feed provider outage, deprecation, or contract-level incident (which is realistically possible over the protocol's lifetime, especially for less liquid assets like `stSTXbtc`/`USDH`) triggers this condition for every affected user with mixed collateral, without any admin recourse visible in `collateral-remove` to let users exit the healthy portion of their position.

### Recommendation
Add a partial/emergency withdrawal path that allows a user to withdraw collateral of an asset whose own oracle is healthy without requiring successful pricing of *other*, unrelated broken assets in the same position — e.g., by allowing withdrawal of non-broken collateral up to the amount that keeps the position's known-healthy value ratio intact, treating the broken asset's value conservatively (e.g., as zero or last-known-good price) rather than reverting the whole operation. Alternatively, provide a DAO/admin emergency override to mark a specific asset's price as failed and freeze only that asset while unlocking withdrawal logic for the rest of the position.

### Proof of Concept
1. Alice deposits sBTC and zUSDC as collateral (multi-asset position, e.g., matching an egroup with mask covering both assets) and borrows USDC against it, giving her a position with debt (`has-debt` = true).
2. The DIA oracle backing zUSDC's underlying price feed (or its `resolve-callcode`/`resolve-ztoken` cache dependency) permanently breaks — e.g., the DIA oracle contract stops returning fresh data beyond `max-staleness`, or reverts entirely.
3. Alice calls `collateral-remove` to withdraw only her sBTC collateral (which has a fully healthy, functioning Pyth feed).
4. `collateral-remove`'s has-debt branch calls `get-notional-evaluation` over `assets` derived from her full position mask, which requires pricing zUSDC via `price-resolve`; this call reverts (`ERR-ORACLE-INVARIANT` / `ERR-ORACLE-DIA`) as shown at [3](#0-2) .
5. The entire `collateral-remove` transaction reverts, so Alice cannot withdraw her healthy sBTC collateral at all, permanently, until the zUSDC oracle is fixed — which for a genuinely broken third-party feed may never happen.

(define-private (price-resolve
  (data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (let ((type (get type data))
        (ident (get ident data))
        (key { type: type, ident: ident })
        (resolution (try! (resolve-price-feed type ident)))
        (price (get value resolution))
        (callcode (get callcode data))
        (final-price (try! (resolve-callcode price callcode)))
        (last-update-time (oracle-last-update key))
        (timestamp (get timestamp resolution))
        (max-staleness (get max-staleness data)))

    ;; validate price and timestamp using max-staleness from oracle data
    (asserts! (and (oracle-price-legal final-price) (oracle-timestamp-fresh timestamp last-update-time max-staleness))
              ERR-ORACLE-INVARIANT)

    ;; update timestamp if newer
    (if (> timestamp last-update-time)
        (map-set last-update key timestamp)
        false)

    (ok final-price)))

(define-private (price-multi-resolve
  (data (list 64 { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint }))
  (aids (list 64 uint)))
  (let ((init { output: (list), valid: true, aids: aids, idx: u0 })
        (response (fold iter-price-multi data init)))
    (asserts! (get valid response) ERR-ORACLE-MULTI)
    (ok (get output response))))

(define-private (iter-price-multi
  (oracle-data { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint })
  (acc { output: (list 64 uint), valid: bool, aids: (list 64 uint), idx: uint }))
  (let ((valid (get valid acc))
        (skip? (asserts! valid acc))
        (asset-ids (get aids acc))
        (idx (get idx acc))

    { output: next,
      valid: true,
      aids: asset-ids,
      idx: (+ idx u1) }))
