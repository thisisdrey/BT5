### Title
Unguarded overflow/underflow in TRON's on-chain AMM exchange balance math (non-hardened path) - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
`ExchangeCapsule.transaction()`, the core AMM pricing/settlement routine used by `ExchangeTransactionActuator` and indirectly by `ExchangeWithdrawActuator`/`ExchangeInjectActuator`, updates the two pool balances of a TRC10 bancor-style exchange pair using plain `long` arithmetic (`firstTokenBalance + sellTokenQuant`, `secondTokenBalance - buyTokenQuant`, etc.) whenever `hardenedCalc` is `false`. The only sanity check that rejects a negative resulting pool balance (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is gated behind `if (hardenedCalc && ...)`, i.e. it is skipped entirely on the legacy/default code path. [1](#0-0) 

### Finding Description
This is directly analogous to the reported bug class: DungeonSwap was drained because its on-chain swap/liquidity accounting could be pushed into an inconsistent state that let the attacker extract more value than was deposited. In java-tron, the same class of bug exists in the built-in bancor-relay exchange actuators, which are reachable by any account via a signed `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract`.

`ExchangeCapsule.transaction()` computes the new pool balances with unchecked `long` addition/subtraction on the non-hardened path: [2](#0-1) 

and only validates the result for negativity/overflow when `hardenedCalc` is true: [3](#0-2) 

`ExchangeTransactionActuator.execute()` calls this same method and commits the resulting pool state and account balances unconditionally, relying only on `doValidate()`'s `addExact`-based balance-limit check (which bounds one side's growth but does not protect against underflow of the other side once the bancor-relay math has already produced results from unchecked pool state): [4](#0-3) [5](#0-4) 

`ExchangeWithdrawActuator` compounds the risk: it recomputes `anotherTokenQuant` proportionally from the *current* (potentially already-corrupted) `firstTokenBalance`/`secondTokenBalance` using `BigInteger` ratio math and then applies `subtractExact` to the pool, which will throw only after the corrupted state has already been used to compute a payout: [6](#0-5) 

Because the hardened, overflow-checked path (`SafeExchangeProcessor` + the `hardenedCalc && (newFirstTokenBalance < 0 ...)` guard) is only engaged when the chain parameter `allowHardenExchangeCalculation` is enabled, any deployment/period where this parameter is off (or before SR activation) executes exchange transactions purely through the unguarded legacy path. I was not able to confirm from the code I could load in this session what the compiled-in default value of `allowHardenExchangeCalculation` is (the getter/setter live in `chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java`, but I ran out of tool budget before verifying the stored default/genesis value) — this is the key remaining uncertainty for exploitability today on mainnet.

### Impact Explanation
If the non-hardened path is active (by config, network state, or a historical block range before the guard was activated), a sequence of exchange transactions/injections/withdrawals could drive one side of a pool to a negative or wrapped `long` value without the actuator rejecting the transaction, corrupting the exchange's economic invariant. Because subsequent `transaction()`/withdraw calls use the corrupted pool state as ground truth for computing token payouts, an attacker could extract more TRX/TRC10 tokens than the pool actually holds — a concrete "unbacked balance"/fund-theft scenario matching the loss pattern in the DungeonSwap incident.

### Likelihood Explanation
Reachable by any unprivileged account: `ExchangeTransactionContract`, `ExchangeInjectContract`, and `ExchangeWithdrawContract` are ordinary signed transactions requiring only that the sender own an exchange pair or trade against an existing one. No special privilege, SR status, or off-chain trust is required. The likelihood is contingent on whether `allowHardenExchangeCalculation` is currently enabled on the target network — I could not verify this default within the available tool budget, so likelihood should be treated as **unconfirmed/conditional** pending that check.

### Recommendation
- Make the negative/overflow guard (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`, and use of `addExact`/`subtractExact`) unconditional in `ExchangeCapsule.transaction()`, regardless of `hardenedCalc`.
- Audit `ExchangeWithdrawActuator` and `ExchangeInjectActuator` to ensure their balance math also uses exact/overflow-checked arithmetic and rejects any pool state transition that would leave a balance ≤ 0 or exceed accounting invariants.
- Verify and, if necessary, force-enable `allowHardenExchangeCalculation` (and `allowStrictMath`) as a mandatory hard fork rather than an optional toggle, so the safe path (`SafeExchangeProcessor`) cannot be bypassed.

### Proof of Concept
A concrete PoC requires confirming the live/default value of `allowHardenExchangeCalculation` and constructing a specific sequence of `ExchangeCreate` → `ExchangeInject`/`ExchangeTransaction` calls that drives `firstTokenBalance`/`secondTokenBalance` to the boundary where unchecked `long` subtraction underflows negative in the non-hardened path (mirrored by the repo's own hardened-mode overflow test, which demonstrates the guard's absence on the legacy path by contrast): [7](#0-6) 
I could not complete this exact numeric PoC (exchange balance sizes, fee constants, and the `allowHardenExchangeCalculation` genesis default) within the remaining tool budget; a follow-up session with direct code/test execution against `DynamicPropertiesStore` defaults is needed to fully weaponize or rule out this analog.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  @Test
  public void hardenedExecuteOverflowThrowsArithmeticException() throws Exception {
    dbManager.getDynamicPropertiesStore().saveAllowSameTokenName(1);
    dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(1);
    InitExchangeSameTokenNameActive();

    long exchangeId = 1;
    // Corrupt pool to near-MAX TRX so addExact overflows when buying.
    ExchangeCapsule pool = dbManager.getExchangeV2Store().get(ByteArray.fromLong(exchangeId));
    pool.setBalance(Long.MAX_VALUE - 5L, 10_000_000L);
    dbManager.getExchangeV2Store().put(pool.createDbKey(), pool);

    String tokenId = "_";
    long quant = 100L;
    ExchangeTransactionActuator actuator = new ExchangeTransactionActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_SECOND, exchangeId, tokenId, quant, 1));

    try {
      // addExact throws ArithmeticException, which is wrapped into ContractExeException.
      Assert.assertThrows(ContractExeException.class,
          () -> actuator.execute(new TransactionResultCapsule()));
    } finally {
      dbManager.getExchangeStore().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeStore().delete(ByteArray.fromLong(2L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(1L));
      dbManager.getExchangeV2Store().delete(ByteArray.fromLong(2L));
      dbManager.getDynamicPropertiesStore().saveAllowHardenExchangeCalculation(0);
    }
  }
