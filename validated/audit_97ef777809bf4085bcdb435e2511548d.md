### Title
Precompiled contract `ValidateMultiSign`/`BatchValidateSign` allocate attacker-controlled-size arrays from unvalidated length words before any bound check, enabling OOM/DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
CVE-2025-26306 describes a memory-exhaustion bug where `readSizedString` in libming allocates memory using an attacker-controlled length taken from a crafted file without validating it against the available data, letting a malicious file exhaust memory. The same bug class — trusting an attacker-supplied length field to size an allocation before any sanity/bounds check — exists in java-tron's `ValidateMultiSign` and `BatchValidateSign` precompiled contracts, which are reachable from any signed transaction that calls a smart contract invoking these TVM precompile addresses.

### Finding Description
`extractBytesArray` and `extractBytes32Array` read a count/length directly from the raw calldata word and immediately size a Java array with it, with no upper bound applied at that point: [1](#0-0)

`intValueSafe()` clamps the value only to the range of a 32-bit int; it does not check it against the actual calldata size, so `len` (and the per-item `bytesLen` passed into `extractBytes`) can be attacker-chosen up to `Integer.MAX_VALUE`.

The size check that is supposed to guard this is applied conditionally on a hard-fork flag, and it happens *before* deciding which extraction path to use, but it does not gate the `extractBytes32Array` call at all when the flag is disabled, and it does not gate `extractBytesArray` at all in that state either: [2](#0-1)

The `MAX_SIZE` (16) sanity check on `sigArraySize`/`addrArraySize` only runs `if (VMConfig.allowTvmSelfdestructRestriction())`. When that switch is not enabled, `extractBytesArray`/`extractBytes32Array` are invoked with a completely unvalidated `len`, so a caller can allocate `new byte[len][]` (an array of object references, at 4-16 bytes per slot depending on JVM) with `len` near `Integer.MAX_VALUE`, or trigger `extractBytes` → `Arrays.copyOfRange(data, offset, offset+bytesLen)` with `bytesLen` near `Integer.MAX_VALUE`, causing multi-gigabyte allocation attempts. The identical pattern exists in `ValidateMultiSign.execute`: [3](#0-2) 

Energy metering for both contracts is computed purely from the *outer* `data.length`: [4](#0-3) [5](#0-4) 

so an attacker pays for a small calldata blob while an internal length word (independent of `data.length`) drives the allocation size — exactly the "crafted length field drives unbounded allocation" pattern in the CVE.

### Impact Explanation
A successful call reaching the unguarded path causes the node's JVM to attempt an outsized allocation, which throws `OutOfMemoryError`/triggers GC thrashing. This is invoked from `Program.callToPrecompiledAddress`, i.e. during normal contract execution triggered by an ordinary transaction, so it can be triggered repeatedly and cheaply (bounded gas cost) to degrade or crash validating/full nodes — a Medium/High-severity denial-of-service against node availability, matching the reachable-analog criteria (unprivileged contract caller, precompile/energy-metering class).

### Likelihood Explanation
The attack requires only a single crafted transaction/contract call to address `0x66`/`0x67` (ValidateMultiSign/BatchValidateSign) with a manipulated ABI word for the array-length/offset fields; no special privileges, signer role, or witness/committee access are needed. Exploitability is conditioned on the network not having `allowTvmSelfdestructRestriction()` active (proposal/hard-fork not yet enabled on that particular chain), which is a realistic condition on private/test/side chains or historically on mainnet before that hard fork.

### Recommendation
Move the `sigArraySize > MAX_SIZE || addrArraySize > MAX_SIZE` bound check outside of the `allowTvmSelfdestructRestriction()` conditional so it always runs before `extractBytesArray`/`extractBytes32Array` are invoked, and additionally validate `len` and each `bytesLen`/`bytesOffset` against `data.length` (and a fixed small maximum) inside `extractBytesArray`/`extractBytes32Array`/`extractBytes` themselves before allocating, rather than relying solely on a feature flag.

### Proof of Concept
1. Deploy/call a contract that performs a `STATICCALL`/`CALL` to precompile address `0x0000...0067` (BatchValidateSign) with calldata shaped as: 5 header words + one item whose "offset" word points to a length word set to a very large value (e.g. `0x7FFFFFFF`), keeping outer `data.length` small so `getEnergyForData` reports a low energy cost.
2. On a network where `VMConfig.allowTvmSelfdestructRestriction()` is false, `doExecute` skips the `sigArraySize/addrArraySize` bound check and calls `extractBytesArray`/`extractBytes32Array` with the attacker-controlled `len`, which attempts `new byte[len][]` and/or `Arrays.copyOfRange` with an attacker-controlled huge size.
3. Repeated submission of such transactions drives the node toward `OutOfMemoryError`, degrading or crashing the executing node.
