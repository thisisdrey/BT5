### Title
Unauthenticated version-negotiation in `Machine.validateCert` mutates handshake state before certificate is CA-verified - (File: `handshake/machine.go`)

### Summary
`Machine.validateCert` recombines the peer's certificate and switches the machine's negotiated protocol version (`m.myVersion`) based solely on the *unverified* certificate's `Version()` field, before the certificate has been checked against the CA pool. This mirrors the reported bug class: two related values that are supposed to stay in lock-step (the credential/curve used to build the live noise session vs. the credential/version used for subsequent outgoing messages) are decoupled and one of them is driven by unauthenticated attacker input.

### Finding Description
In `validateCert`: [1](#0-0) 

The sequence is:
1. `cred := m.getCred(m.myVersion)` — fetch **our own** credential for the version this Machine was originally built with (`NewMachine` fixed the underlying noise `HandshakeState`/curve using this same version's credential: `handshake/machine.go:89-97`).
2. `cert.Recombine(...)` reconstructs the peer certificate using `payload.CertVersion` (an attacker-controlled field) and `cred.Cert.Curve()`.
3. Only a basic public-key-equality check (`bytes.Equal(rc.PublicKey(), m.hs.PeerStatic())`) is performed — this does **not** involve any CA trust check, it only confirms the recombined bytes match the noise static key already exchanged.
4. **Before calling `m.verifier(rc)`** (which is the only step that performs CA-pool verification, expiry checks, etc., delegated to `CertVerifier`), the code unconditionally does:
   ```go
   if rc.Version() != m.myVersion {
       if m.getCred(rc.Version()) != nil {
           m.myVersion = rc.Version()
       }
   }
   ```
5. Only after this mutation does it call `verified, err := m.verifier(rc)`.

This means `m.myVersion` — which controls which local `Credential` (and therefore which cert/version) will be used for all subsequent outgoing handshake messages via `marshalOutgoing` (`handshake/machine.go:406-414`) — is changed purely because the peer claimed a different `CertVersion` in the wire payload, with zero requirement that the peer's certificate be signed by a trusted CA. The gating condition `m.getCred(rc.Version()) != nil` only checks that *we* happen to have a local credential for that version; it says nothing about whether the *remote* party is trustworthy.

If `m.verifier(rc)` subsequently fails (e.g., because the certificate isn't CA-signed), the Machine is marked `m.failed = true` and aborted — so in the immediate call the state change is “thrown away” along with the whole Machine. However, the state mutation happens strictly *before* the authentication check, which is the same root-cause pattern as the report: a value that should only be set/used once its associated trust anchor (`loanToken`/CA-verified cert) is confirmed is instead set based on unverified attacker-supplied data (`_asset`/`payload.CertVersion`), creating an inconsistency window between what the live cryptographic state assumes and what higher-level negotiated policy now points to.

### Impact Explanation
- Any peer able to reach the handshake responder — including one that has **not** presented a CA-signed certificate — can influence `Machine.myVersion` purely by sending a self-consistent (curve-matching, correctly shaped) but otherwise untrusted certificate blob with an arbitrary `CertVersion` field, before any CA/verifier check succeeds.
- Because the underlying noise `HandshakeState` (and its DH/cipher suite) was already fixed at `NewMachine` time from the *original* version's `Credential` (`handshake/machine.go:89-97`), while `marshalOutgoing` later fetches a (potentially different) credential keyed by the *new* `m.myVersion` for outgoing certificate bytes, this can desynchronize “what curve/cipher the live noise session is actually using” from “which version's certificate/credential we now advertise to the peer” if the two versions carry different curves. This is a remote state-poisoning vector on the handshake responder path, triggerable pre-authentication.
- Because the mutation happens before verification, it also means the negotiation decision cannot be rolled back cleanly if verification later fails within the same message — the Machine is simply failed, but the fact that untrusted input was allowed to alter negotiated protocol state ahead of authentication is the structural flaw (same class as approving/allocating with one unvalidated field and consuming a different, validated field expected to match it).

### Likelihood Explanation
Reachable by any unauthenticated remote peer that can send a handshake packet reaching `Machine.ProcessPacket` → `processPayload` → `validateCert`; no valid CA-signed certificate is required to trigger the version switch, only a certificate blob that unmarshals successfully and whose static key/curve matches what's already been negotiated in the noise message. This satisfies the "no CA-signed certificate" reachability constraint.

### Recommendation
Move the version-negotiation state update (`m.myVersion = rc.Version()`) to occur only **after** `m.verifier(rc)` succeeds, so that untrusted/unauthenticated certificate content can never influence which credential/version is used for subsequent protocol steps. Alternatively, perform verification first, then negotiate:
```go
verified, err := m.verifier(rc)
if err != nil {
    m.failed = true
    return fmt.Errorf("verify cert: %w", err)
}
if rc.Version() != m.myVersion {
    if m.getCred(rc.Version()) != nil {
        m.myVersion = rc.Version()
    }
}
m.result.RemoteCert = verified
m.remoteCertSet = true
```

### Proof of Concept
Conceptual PoC (aligns with existing test patterns in `handshake/machine_test.go` and `handshake_manager_test.go`):
1. Configure a responder `Machine` for `Version2` credentials only (`NewMachine(Version2, ...)`), but also configure `getCred` to return a non-nil `Version1` credential (simulating dual-version support during a migration window).
2. As an unauthenticated attacker (no CA-signed cert), craft a handshake continuation packet whose Noise static key matches the already-exchanged ephemeral/static key (satisfiable since the attacker controls their own keypair for the session) but whose embedded `payload.CertVersion` is set to `Version1`, with a self-signed (non-CA-trusted) certificate that still recombines successfully (unmarshal + curve match).
3. Observe that `m.myVersion` flips to `Version1` inside `validateCert` before `m.verifier(rc)` is invoked — instrument/log `m.myVersion` before and after the call, or assert via `m.getCred(m.myVersion)` returning the `Version1` credential prior to the verifier returning an error for the untrusted cert.
4. This demonstrates that protocol/version state used for subsequent credential selection is mutated by attacker-controlled, pre-authentication data, independent of whether the final `m.verifier` call ultimately rejects the certificate.

```go
func (m *Machine) validateCert(payload Payload) error {
	cred := m.getCred(m.myVersion)
	if cred == nil {
		m.failed = true
		return fmt.Errorf("%w: %v", ErrNoCredential, m.myVersion)
	}
	rc, err := cert.Recombine(
		cert.Version(payload.CertVersion),
		payload.Cert,
		m.hs.PeerStatic(),
		cred.Cert.Curve(),
	)
	if err != nil {
		m.failed = true
		return fmt.Errorf("recombine cert: %w", err)
	}

	if !bytes.Equal(rc.PublicKey(), m.hs.PeerStatic()) {
		m.failed = true
		return ErrPublicKeyMismatch
	}

	// Version negotiation, if the peer sent a different version and we have it, switch
	if rc.Version() != m.myVersion {
		if m.getCred(rc.Version()) != nil {
			m.myVersion = rc.Version()
		}
	}

	verified, err := m.verifier(rc)
	if err != nil {
		m.failed = true
		return fmt.Errorf("verify cert: %w", err)
	}

	m.result.RemoteCert = verified
	m.remoteCertSet = true
	return nil
```
