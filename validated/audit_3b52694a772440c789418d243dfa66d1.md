### Title
Missing account-name length validation in `CreateAccountActuator` allows unbounded on-chain `Account.account_name` bloat, degrading `GetAccount`/`ListAccounts` API responsiveness - (File: `actuator/src/main/java/org/tron/core/actuator/CreateAccountActuator.java`)

### Summary
`CreateAccountActuator.validate()` never checks the length or content of `AccountCreateContract.account_name` before the account is created and persisted permanently in `AccountStore`. Every other place that sets an account name (`UpdateAccountActuator`, `SetAccountIdActuator`, asset name/url/description fields) calls `TransactionUtil.validAccountName`/`validAssetName`/`validUrl` to bound the field, but the create-account path has this check explicitly commented out.

### Finding Description
`CreateAccountActuator.validate()` contains:
```java
//    if (contract.getAccountName().isEmpty()) {
//      throw new ContractValidateException("AccountName is null");
//    }
``` [1](#0-0) 
No call to `TransactionUtil.validAccountName()` (or any length/charset check) exists anywhere in this validator, unlike `UpdateAccountActuator.validate()`, which enforces `TransactionUtil.validAccountName(accountName)` with `MAX_ACCOUNT_NAME_LEN = 200` bytes: [2](#0-1) [3](#0-2) 

`execute()` then directly constructs an `AccountCapsule` from the unvalidated contract and stores it permanently: [4](#0-3) 

The only remaining backstop is the generic bandwidth/size accounting in `BandwidthProcessor.consume()`, which bounds the *whole serialized create-account transaction* to `dynamicPropertiesStore.getMaxCreateAccountTxSize()` (only enforced when `optimizeTxs` is true, i.e. for not-yet-in-block/pending transactions, or post fork `VERSION_4_7_5` for in-block application) and otherwise to the general `Constant.TRANSACTION_MAX_BYTE_SIZE` (500 KB): [5](#0-4) [6](#0-5) 

That bound is far looser than the 200-byte cap normally enforced for account names elsewhere, and depends on dynamic/fork configuration rather than being an intrinsic field validation. As a result, any unprivileged signer who can pay the (small, fixed) `CreateNewAccountFeeInSystemContract` can broadcast an `AccountCreateContract` with an `account_name` of up to several thousand bytes of garbage (bounded only by `MAX_CREATE_ACCOUNT_TX_SIZE`/`TRANSACTION_MAX_BYTE_SIZE`, not by any name-specific validator), and this name is stored forever on-chain for that account.

Because `account_name` is returned in every subsequent `GetAccount`/`ListAccounts`/`getaccount` HTTP, gRPC, and JSON-RPC query, and `ListAccounts`/`AccountList` iterates and returns full `Account` protobuf messages unpaginated, repeated creation of many such bloated accounts (cheaply, since account creation fee is fixed and low, e.g. 1 TRX) can inflate response sizes and CPU/memory cost for any client or downstream service invoking account listing/lookup — directly analogous to the Open WebUI bug where an unauthenticated large `name` field caused the admin listing UI to become unresponsive.

### Impact Explanation
This is a resource-consumption vector reachable by any unprivileged transaction broadcaster (only requires an existing funded owner account to pay the create-account fee — no special privilege). Repeated exploitation inflates account name payload size on-chain and in every read path (`GetAccount`, `ListAccounts`, HTTP/gRPC/JSON-RPC), degrading node responsiveness for that query surface — matching the CWE-400 "Uncontrolled Resource Consumption" class of the reference advisory. It does not directly cause fund theft or consensus failure, but can render account-query APIs slow/unresponsive under moderate repeated use, which the report's rules classify at least Medium/High for a reachable, unauthenticated resource-exhaustion path into a query API.

### Likelihood Explanation
High likelihood: the vulnerable code path requires only a single signed `AccountCreateContract` transaction, and the validation gap (missing account-name check) is explicit and unconditional — it is not fork-gated or feature-flagged. The only friction is paying the account-creation fee and staying under the transaction/tx-size caps, both of which still allow name payloads far larger than the 200-byte limit enforced elsewhere in the codebase for identical semantic fields.

### Recommendation
Add an explicit `TransactionUtil.validAccountName(contract.getAccountName().toByteArray())` check (same 200-byte bound used in `UpdateAccountActuator`) to `CreateAccountActuator.validate()`, rejecting the transaction with `ContractValidateException` if the name is invalid/too large, consistent with the equivalent check that already exists for `AccountUpdateContract`.

### Proof of Concept
1. Fund an owner account with enough balance to cover `CreateNewAccountFeeInSystemContract`.
2. Build an `AccountCreateContract` with `account_address` set to a fresh valid address and `account_name` set to an arbitrary byte string (up to the `MAX_CREATE_ACCOUNT_TX_SIZE`/`TRANSACTION_MAX_BYTE_SIZE` bound, i.e. several KB), e.g. via `WalletClient.createAccountCreateContract` [7](#0-6) .
3. Sign and broadcast the transaction; `CreateAccountActuator.validate()` accepts it unconditionally because the name-length check is commented out [1](#0-0) .
4. `execute()` persists the bloated `AccountCapsule` in `AccountStore` [8](#0-7) .
5. Repeat account creation for many addresses; subsequent calls to `GetAccount`/`ListAccounts`/`/wallet/getaccount` will return/iterate these oversized records, increasing serialization/response cost for the query path.
