### Title
`liquidate()` reverts on overflow instead of capping when a liquidator passes a large `debt-amount` - (File: `mainnet/contracts/market/v0-4-market.clar`)

### Summary
`process-debt-asset` computes `(* debt-amount debt-price)` **before** capping the value against `max-debt-usd`. Because Clarity's `uint` is a fixed 128-bit unsigned integer with checked (aborting) arithmetic rather than wraparound, a caller-supplied `debt-amount` that is large enough makes this multiplication overflow and abort the entire `liquidate` transaction — even though the very next lines of the same function are designed to cap the value down to the legitimate liquidatable amount. This is the same bug class as the referenced Escher finding: an oversized-but-conventional input ("repay everything") causes a revert in a path that was explicitly written to tolerate and cap oversized inputs.

### Finding Description
In `process-debt-asset`, the debt USD value is computed by multiplying the raw `debt-amount` parameter (fully controlled by whoever calls `liquidate`) by `debt-price` *before* any capping occurs: [1](#0-0) 

```
(debt-usd (normalize (* debt-amount debt-price) debt-decimals false))
;; cap debt at maximum liquidatable amount
(debt-actual-usd (if (> debt-usd max-debt-usd) max-debt-usd debt-usd))
```

The comment "cap debt at maximum liquidatable amount" makes clear the intended design: a liquidator should be able to pass an arbitrarily large `debt-amount` (e.g., a sentinel "repay everything" value, a common convention in lending protocols) and have the protocol clamp it to `max-debt-usd`. However, the clamp is applied only *after* the multiplication `(* debt-amount debt-price)` has already executed. Since Clarity's `uint` arithmetic aborts on overflow (there is no wraparound), supplying a sufficiently large `debt-amount` makes this multiplication itself abort the transaction, defeating the capping logic entirely.

The repository's own test suite acknowledges this exact defect: [2](#0-1) 

```
describe('EDGE-01: Liquidate with MAX_UINT128 debt amount', () => {
  ...
  // Try to liquidate with a large value (but not MAX_UINT128 which causes overflow)
  // Using 10x the actual debt to test capping behavior
```

The test is explicitly designed to *avoid* `MAX_UINT128` because using it is known to cause overflow instead of exercising the intended capping path, confirming the root cause.

### Impact Explanation
`liquidate()` is a public, unprivileged entry point that any account can call on any unhealthy position. Liquidators (bots or humans) commonly pass a maximal/sentinel value to mean "repay as much debt as the protocol will allow," relying on the callee's own capping logic — which is exactly what the in-code comment says this function is supposed to support. When such a call reverts instead of capping, an already-unhealthy position that should have been liquidated is not liquidated by that call. This is a temporary freezing of the liquidation flow for that position: bad debt continues to accrue/exist against the vault until a caller instead supplies a "correctly sized" (non-overflowing) amount, delaying debt recovery and creating a window where insolvency risk on that position is not remediated as promptly as the protocol's own liquidation-incentive design intends.

### Likelihood Explanation
Any address can trigger this by simply calling `liquidate` with a large `debt-amount` (e.g., a conventional `u340282366920938463463374607431768211455` "repay-max" sentinel) against any unhealthy position — no privileged role or DAO action is required, and the protocol's own tests independently confirm the overflow occurs with such inputs.

### Recommendation
Cap `debt-amount` (or the intermediate USD value) before performing the multiplication that can overflow, e.g. compute `max-debt-usd` first, derive the corresponding maximum token amount using `debt-price`/`debt-decimals`, and take `(min debt-amount max-debt-token-amount)` prior to multiplying, so the multiplication in `process-debt-asset` is always bounded by a value the protocol has already validated as liquidatable, matching the function's documented intent.

### Proof of Concept
1. Create an unhealthy borrow position (as in `EDGE-01`): add sBTC collateral, borrow USDC, then drop the BTC price so the position becomes liquidatable.
2. Call `market.liquidate(borrower, collateralAsset, debtAsset, debtAmount = u340282366920938463463374607431768211455 /* MAX_UINT128 */, minCollateral, ..., ...)`.
3. Inside `process-debt-asset`, `(* debt-amount debt-price)` overflows Clarity's 128-bit `uint`, aborting the transaction with a runtime arithmetic error instead of capping to `max-debt-usd` and completing the liquidation, as demonstrated by the protocol's own `EDGE-01` test explicitly steering clear of `MAX_UINT128` for this reason.

(define-private (process-debt-asset
  (debt-amount uint)
  (debt-aid uint)
  (max-debt-usd uint)
  (assets (list 64 {
    id: uint, addr: principal, decimals: uint,
    oracle: { type: (buff 1), ident: (buff 32), callcode: (optional (buff 1)), max-staleness: uint },
    collateral: bool, debt: bool, price: uint
  })))
  (let ((debt-asset-info (unwrap-panic (find-asset debt-aid assets)))
        (debt-price (get price debt-asset-info))
        (debt-decimals (get decimals debt-asset-info))
        (debt-usd (normalize (* debt-amount debt-price) debt-decimals false))
        ;; cap debt at maximum liquidatable amount
        (debt-actual-usd (if (> debt-usd max-debt-usd) max-debt-usd debt-usd))
        ;; convert capped USD amount back to token amount
        (debt-actual (mul-div-down debt-actual-usd (pow u10 debt-decimals) debt-price)))
    {
      debt-actual-usd: debt-actual-usd,
      debt-actual: debt-actual,
      debt-price: debt-price,
      debt-decimals: debt-decimals
    }))
