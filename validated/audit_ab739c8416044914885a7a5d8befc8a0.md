This confirms the mechanics: `verify_nonce` requires `tx_nonce > current_nonce` (Monotonic) and only rejects `NonceTooLarge` when `tx_nonce >= block_height * 1_000_000` [1](#0-0) . So a nonce chosen anywhere in `((H-1)*1_000_000, H*1_000_000)` is valid at height `H`, and `add_gas_key`'s reset seed is exactly `(H-1)*1_000_000` computed from the *current* `block_height` at the time the add executes [2](#0-1) [3](#0-2) .

### Title
Gas-key nonce reset in `add_gas_key` can retroactively un-consume a nonce spent earlier in the same block, enabling replay of an already-executed GasKeyNonce transaction against a freshly funded balance - (File: `runtime/runtime/src/access_keys.rs`)

### Summary
`add_gas_key` unconditionally reseeds each gas-key nonce slot to `(block_height-1) * 1_000_000` using the *current* block height [3](#0-2) . If a `GasKeyNonce` transaction on the same key/index was already processed earlier in the *same* block with a nonce value greater than that seed, deleting and re-adding the gas key within that same block lowers the stored nonce below an already-spent value, making that spent nonce valid again for reuse in a later block.

### Finding Description
Transaction-to-receipt conversion (`process_transactions`) happens for the *entire* chunk before any local receipt executes (`process local receipts` runs after `process transactions` completes) [4](#0-3) . Transaction groups are keyed by `(account_id, public_key)`, so a `GasKeyNonce` transaction signed by the gas key and a `DeleteKey`/`AddKey`/`TransferToGasKey` transaction signed by the account's `FullAccess` key belong to different groups and can both be admitted into the same chunk [5](#0-4) .

Sequence within block height `H`:
1. `tx1` (signed by the gas key, `nonce_index = 0`, `tx_nonce = n` chosen close to the upper bound, e.g. `H*1_000_000 - 1`) is processed. `verify_and_charge_gas_key_tx_ephemeral` accepts it (`n > current_nonce`, `n < H*1_000_000`) and immediately commits the new stored nonce `n` to the trie during transaction conversion [6](#0-5) .
2. `tx2` (signed by the `FullAccess` key, actions `DeleteKey` + `AddKey` + `TransferToGasKey`, all self-targeting) becomes a local receipt and executes later in the same block's "process local receipts" phase. `delete_gas_key` burns the old (≤1 NEAR) balance and removes the nonce rows [7](#0-6) ; `add_gas_key` re-adds the same public key, sets a fresh `GasKeyInfo.balance` via the batched `TransferToGasKey`, and resets nonce index 0 to `(H-1)*1_000_000` [8](#0-7) . Since `(H-1)*1_000_000 < n`, the reset is strictly *lower* than the nonce already spent by `tx1`.
3. In a later block, the attacker resubmits `tx1` (or any new transaction with `nonce_index = 0`, `tx_nonce = n`). `verify_nonce`'s Monotonic check only requires `tx_nonce > current_nonce`, which now passes because current_nonce was reset below `n` [9](#0-8) . The gas cost is drawn from the *newly funded* `gas_key_info.balance`, and the transaction's actions execute a second time with a new receipt id.

No existing check prevents this: nonce upper-bound checking uses the current block height rather than a per-key monotonic counter tied to prior usage, cross-chunk transaction-hash deduplication only covers a single chunk (`skip_duplicate_txs`), and `add_gas_key` performs an unconditional reset with no comparison against the nonce value that was in place before deletion.

### Impact Explanation
This breaks the nonce-uniqueness/anti-replay invariant for gas keys ("Nonce monotonicity prevents replay") documented for the account/key model. An attacker who fully controls their own account, its `FullAccess` key, and a gas key can force any previously-executed `GasKeyNonce` transaction to become valid again after a same-block delete+recreate of the gas key, causing its receipt/actions to execute a second time, charged against a freshly deposited gas-key balance. This is a double-spend/replay of a transaction that should be permanently consumed, matching the "double-spend/replay" NEAR bounty category.

### Likelihood Explanation
Feasibility is high for a sophisticated but fully unprivileged attacker: all steps are self-contained on the attacker's own account (fund a gas key, spend part of it, then batch `DeleteKey` + `AddKey` + `TransferToGasKey` in one self-targeting transaction), require only ordinary RPC access, and depend only on getting two independently-keyed transactions from the same account into the same chunk — plausible since chunk producers admit one transaction per `(account_id, public_key)` group per pass and the attacker controls both signed transactions and can retry across blocks until both land together. The valid-nonce window for the collision spans nearly the entire `1_000_000`-wide range for the target block height, so no precise timing is needed to choose a colliding nonce.

### Recommendation
When resetting gas-key nonces in `add_gas_key`, do not allow the seed to regress below any nonce value already recorded for that `(account_id, public_key, nonce_index)` in the current block/state (e.g., seed with `max(existing_stored_nonce, (block_height-1)*1_000_000)` before removal, or otherwise track a strictly monotonic high-water mark per public key across delete/re-add cycles rather than deriving the seed purely from the current block height).

### Proof of Concept
Runtime/integration test (test-loop or `runtime/runtime/src/tests/apply.rs`-style) at a controlled block height `H`:
1. Set up an account with a `FullAccess` key and a gas key with `num_nonces >= 1`, funded with a small balance (≤ `MAX_BALANCE_TO_BURN`).
2. Submit `tx1`: `GasKeyNonce { nonce: n, nonce_index: 0 }` with `n` chosen as `H*1_000_000 - 1`, performing some observable action (e.g., a `FunctionCall` to a test contract that increments a counter). Assert it succeeds and the counter is 1.
3. In the same chunk/apply call, submit `tx2` signed by the `FullAccess` key: `[DeleteKey(gas_key_pub), AddKey(gas_key_pub, GasKeyFullAccess), TransferToGasKey(deposit: B)]`.
4. Assert after this block that `get_gas_key_nonce(state, account, gas_key_pub, 0) == (H-1)*1_000_000` and `gas_key_info.balance == B`.
5. In a subsequent block, resubmit the identical `tx1` bytes (or a new tx with `nonce_index: 0, nonce: n`). Assert it is accepted (`TxVerdict::Success`), gas is charged from the new balance `B`, and the counter increments to 2 — proving the previously-consumed nonce/transaction executed twice.
