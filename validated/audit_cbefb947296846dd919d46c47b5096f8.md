### Title
Unbounded HTTP response buffering in `run_http_request` before StackerDB chunk-size check — memory-exhaustion DoS against `stacks-signer` - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` in `libsigner/src/http.rs` calls `sock.read_to_end(&mut buf)` with no size cap whatsoever, buffering the entire HTTP response from the remote peer into memory before any parsing or validation occurs. The `body_bytes.len() > limit` check in `StackerDBSession::get_latest_chunks` (`libsigner/src/session.rs`) only runs after this unbounded read has already completed, so a malicious/compromised StackerDB RPC host can force the connecting `stacks-signer` process to allocate and buffer an attacker-controlled amount of data.

### Finding Description
`run_http_request` (`libsigner/src/http.rs`, lines 221-261) sends the HTTP request and then does:
```
let mut buf = vec![];
sock.read_to_end(&mut buf)?;
``` [1](#0-0) 
This reads from the socket until the peer closes the connection (the client itself sends `Connection: close`), with no bound tied to `Content-Length`, `MAX_MESSAGE_LEN`, or `STACKERDB_MAX_CHUNK_SIZE`. Only after the full buffer is materialized does the code proceed to `decode_http_response` and `decode_http_body`. The chunked-transfer path does cap decoded output via `HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into())`, but that cap applies to `decode_http_body`, which operates on the buffer that has *already* been fully read into memory by `read_to_end` — it does not bound the initial `read_to_end` call itself. For a non-chunked response, `decode_http_body` just does `buf.to_vec()` with no cap at all.

`StackerDBSession::get_latest_chunks` (`libsigner/src/session.rs`, lines 230-262) calls `self.rpc_request(...)` → `run_http_request(...)`, and only after the call returns does it check:
```
if body_bytes.len() > limit {
    None
} else {
    Some(body_bytes)
}
``` [2](#0-1) 
where `limit` is `SIGNERS_STACKERDB_CHUNK_SIZE` (2MB) or `STACKERDB_MAX_CHUNK_SIZE` (16MB). By the time this check executes, the full response is already buffered in memory — the check discards the oversized data but cannot undo the allocation/memory pressure that already occurred.

A malicious or compromised node that the signer is configured to pull StackerDB chunks from can simply respond to the `GET` chunk request with an arbitrarily large body (or simply never close the connection while streaming data), causing the signer's `read_to_end` to keep growing `buf` without any limit, unlike the declared 2MB/16MB chunk-size limits enforced elsewhere in the StackerDB protocol.

### Impact Explanation
A single malicious HTTP response from a node the `stacks-signer` connects to can force unbounded memory allocation in the signer process, since `run_http_request`'s `read_to_end` has no size cap and is not driven by `Content-Length` validation or `MAX_MESSAGE_LEN`/`STACKERDB_MAX_CHUNK_SIZE` enforcement during the read. This can exhaust the signer's memory and crash the process (OOM), which is a repeatable, unauthenticated DoS every time the signer polls that peer for StackerDB chunks (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk` all funnel through the same unbounded `run_http_request`).

### Likelihood Explanation
The attacker only needs to control (or compromise) one of the nodes that the `stacks-signer`'s `StackerDBSession` is configured to query over its RPC/HTTP interface — no secret, signature, or privileged StackerDB write is required, since this is purely a client-side buffering flaw triggered by the *response* to a normal read request (`GET` chunk/metadata). The cost to the attacker is trivial: return a large or slow-trickling body on any of the endpoints exercised by `rpc_request` (`list_chunks`, `get_chunks`, `get_latest_chunks`, `put_chunk`'s ack response).

### Recommendation
Bound the initial socket read in `run_http_request` to a hard maximum (e.g., `STACKERDB_MAX_CHUNK_SIZE`/`MAX_MESSAGE_LEN` plus a reasonable header allowance) using a size-limited reader (e.g., wrap `sock` with `Read::take(limit)` or track bytes read incrementally and abort early), rather than calling `read_to_end` unconditionally. Additionally, validate the `Content-Length` header against the caller's expected limit before reading the body, and enforce that limit while streaming, not only after the full body has been buffered.
