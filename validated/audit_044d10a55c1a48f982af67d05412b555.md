### Title
Relay identity bound to attacker-controlled `RelayFromAddr` field instead of the cryptographically verified peer address - ([File: relay_manager.go])

### Summary
`relayManager.handleCreateRelayRequest` and `handleCreateRelayResponse` derive the "relay owner" identity that gets stored in relay routing state from `m.RelayFromAddr`/`m.RelayToAddr`, which are attacker-supplied fields inside the (already-decrypted) `NebulaControl` payload, rather than from the cryptographically-verified identity of the peer connection the message arrived on (`h.vpnAddrs[0]`). This is the same class of bug as the reported `env::signer_account_id()` vs `env::predecessor_account_id()` issue: a self-declared identity claim embedded in a message is trusted for access/state decisions instead of the identity that is actually bound to the authenticated channel.

### Finding Description
`HandleControlMsg` receives an already AEAD-decrypted control message from `HostInfo h` — `h.vpnAddrs[0]` is the identity that was cryptographically bound to this tunnel during the certificate-authenticated handshake (the "predecessor" analog: the entity actually on the other end of this specific verified connection) [1](#0-0) .

However, when processing `CreateRelayRequest`, the code extracts `from := protoAddrToNetAddr(m.RelayFromAddr)` directly from the message body and uses that unverified value — not `h.vpnAddrs[0]` — as the key for all subsequent relay-state operations: the self-relay check, `QueryRelayForByIp(from)`, state transitions, and `AddRelay(rm.l, h, f.hostMap, from, ...)`, which permanently associates hostinfo `h` with relay identity `from` in the hostmap's relay index [2](#0-1) .

Nowhere in `handleCreateRelayRequest` is `from` checked against `h.vpnAddrs[0]` (the verified sender of this specific message). The only self-check performed is whether `from` matches *my own* address table, not whether it matches the actual sender's certificate-bound identity [3](#0-2) . The same pattern repeats in `handleCreateRelayResponse`, which uses `relayFrom`/`relayTo` taken straight from the message to look up and mutate relay state via `EstablishRelay` and `QueryRelayForByIp` [4](#0-3) .

This means any peer that has a valid, established tunnel to the target (i.e., any legitimate but potentially malicious VPN member) can send a `CreateRelayRequest`/`CreateRelayResponse` claiming an arbitrary `RelayFromAddr` — including the VPN address of a different, uninvolved host — and have the target register/mutate relay routing state (`AddRelay`, `UpdateRelayForByIpState`, `CompleteRelayByIP`) under that spoofed identity rather than the attacker's own verified `h.vpnAddrs[0]`.

### Impact Explanation
This allows remote relay-state poisoning: an authenticated-but-malicious peer can inject or corrupt relay routing entries keyed to a victim's VPN address without that victim's participation, on a connection that is actually terminated by the attacker's own `HostInfo`. Depending on downstream consumers of `relayState`/`hostMap.Relays`, this can desynchronize or corrupt relay path bookkeeping for a legitimate host (e.g., causing relay index collisions, incorrect `Established`/`Disestablished` transitions, or blocking/hijacking of relay slots intended for the real owner of that VPN address) — a concrete instance of the "remote state poisoning" impact category. It does not directly bypass certificate/handshake authentication of data-plane traffic (that is enforced later, in the handshake and firewall `Drop` checks against certificate-bound `vpnAddrs`), but it does let one authenticated node corrupt another node's relay control-plane state by impersonating it in `RelayFromAddr`/`RelayToAddr` fields.

### Likelihood Explanation
Likelihood is meaningful but not maximal: the attacker must already be a fully-authenticated member of the mesh (i.e., hold a valid certificate and have completed a handshake as `h`), and must know or guess a target VPN address to impersonate as `RelayFromAddr`. Given that VPN address space in Nebula deployments is typically small and enumerable (CIDR-based), and no additional verification ties `RelayFromAddr` to `h.vpnAddrs[0]`, a malicious insider can trivially craft such messages. This mirrors the original report's "owner can be phished/impersonated by an unrelated caller" pattern, just requiring insider rather than fully-external access.

### Recommendation
In `handleCreateRelayRequest` and `handleCreateRelayResponse`, validate that the identity used to key relay state is the cryptographically verified `h.vpnAddrs[0]` (or a value provably consistent with it), not the raw `m.RelayFromAddr`/`m.RelayToAddr` fields taken from message content. Concretely: for `CreateRelayRequest`, when the target is `f`'s own address, require `from` to equal (or be contained in) `h.vpnAddrs`, matching the same "predecessor" identity check the `TestFirewall_ConntrackSourceSpoofingAcrossPeers` and firewall `Drop()` logic already apply to data-plane traffic [5](#0-4) . Reject or log-and-drop control messages where the claimed relay-from address does not match the verified sender of the connection.

### Proof of Concept
1. Node `Attacker` establishes a normal, certificate-authenticated tunnel to `Target` (so `h.vpnAddrs[0] == Attacker`'s real VPN address on `Target`'s side).
2. `Attacker` sends a `NebulaControl_CreateRelayRequest` over this tunnel with `RelayFromAddr` set to `Victim`'s VPN address (a different, uninvolved host) and `RelayToAddr` set to `Target`'s own address.
3. `Target`'s `HandleControlMsg` → `handleCreateRelayRequest` computes `from = Victim`'s address purely from the message body, sees `f.myVpnAddrsTable.Contains(target)` is true, and calls `AddRelay(rm.l, h, f.hostMap, from /*=Victim*/, &m.InitiatorRelayIndex, TerminalType, Established)`, registering relay state for `h` (Attacker's connection) under `Victim`'s identity [2](#0-1) .
4. `Target` now has relay routing state associating the real `Victim` VPN address with a connection actually controlled by `Attacker`, with no cross-check ever performed against `h.vpnAddrs[0]`.

**Uncertainty**: I could not fully trace every downstream consumer of `hostMap.Relays`/`relayState.relayForByAddr` to confirm the precise blast radius (e.g., whether this can be escalated into data-plane traffic redirection, or is limited to control-plane bookkeeping corruption/DoS), since the `AddRelay` implementation and full `HostInfo.relayState` consumer set were not fully retrieved before the tool budget was exhausted. The impact assessment above is based on the confirmed absence of the `from == h.vpnAddrs[0]` check and the confirmed use of `from` as the storage key for relay state.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

	//nil-checks for protoAddrToNetAddr handled by caller
	from := protoAddrToNetAddr(m.RelayFromAddr)
	target := protoAddrToNetAddr(m.RelayToAddr)

	logMsg := rm.l.With(
		"relayFrom", from,
		"relayTo", target,
		"initiatorRelayIndex", m.InitiatorRelayIndex,
		"vpnAddrs", h.vpnAddrs,
	)

	logMsg.Info("handleCreateRelayRequest")
	// Is the source of the relay me? This should never happen, but did happen due to
	// an issue migrating relays over to newly re-handshaked host info objects.
	if f.myVpnAddrsTable.Contains(from) {
		logMsg.Error("Discarding relay request from myself", "myIP", from)
		return
	}

	// Is the target of the relay me?
	if f.myVpnAddrsTable.Contains(target) {
		existingRelay, ok := h.relayState.QueryRelayForByIp(from)
		if ok {
			switch existingRelay.State {
			case Requested:
				ok = h.relayState.CompleteRelayByIP(from, m.InitiatorRelayIndex)
				if !ok {
					logMsg.Error("Relay State not found")
					return
				}
			case Established:
				if existingRelay.RemoteIndex != m.InitiatorRelayIndex {
					// We got a brand new Relay request, because its index is different than what we saw before.
					// This should never happen. The peer should never change an index, once created.

						"existingRemoteIndex", existingRelay.RemoteIndex)
					return
