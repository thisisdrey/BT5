## Analysis Result

### Title
Division-before-multiplication precision loss in vote reward computation causes unbacked/incorrect reward allowances - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
The external report flags `glpToUsd` in `GlpPricing.sol` for computing a value by dividing first and then multiplying, which loses precision compared to multiplying first and dividing last. The same bug class exists in java-tron's legacy vote-reward computation path: `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` computes `voteRate = (double) userVote / totalVote` (a division) and then multiplies that already-truncated double by `totalReward`, instead of computing `userVote * totalReward / totalVote` with integer/BigInteger math (multiply first, divide last) as the newer VI-based algorithm correctly does elsewhere in the same class.

### Finding Description
In `MortgageService.java`: [1](#0-0) 

```java
private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
  long reward = 0;
  for (Pair<byte[], Long> vote : votes) {
    ...
    long userVote = vote.getValue();
    double voteRate = (double) userVote / totalVote;
    reward += voteRate * totalReward;
  }
  return reward;
}
```

`voteRate` is computed as a `double` division (`userVote / totalVote`) before being multiplied by `totalReward`. This performs the division first, which truncates precision at that step; the subsequent multiplication amplifies the already-lost precision, whereas doing `userVote * totalReward / totalVote` (multiply first, then divide) preserves precision until the final truncation — exactly the fix pattern recommended for `glpToUsd`.

This legacy path is exercised by `getOldReward`, which is called for cycles before the "new reward algorithm" effective cycle or when `allowOldRewardOpt()` is disabled: [2](#0-1) 

The new-algorithm path in the same file correctly uses `BigInteger` multiply-then-divide: [3](#0-2) 

showing the intended correct order and confirming the old-path double arithmetic is the outlier/regression.

This computation is reachable by any account holder via a standard `WithdrawBalanceContract` transaction, which any unprivileged broadcaster can submit: [4](#0-3) 

which calls `MortgageService.withdrawReward`, which in turn invokes `computeReward`/`getOldReward` for eligible cycles: [5](#0-4) 

### Impact Explanation
Because each voter's share of `totalReward` for a witness/cycle is computed independently via floating-point division-then-multiplication, the sum of rewards distributed to all voters for a given witness/cycle is not guaranteed to equal (and can exceed) the actual `totalReward` recorded for that witness/cycle. Over many cycles and many voters, this systematic floating-point rounding can cause the sum of `allowance` credited to voter accounts to diverge from the SUN actually reserved as block/transaction-fee rewards — i.e., users' `allowance` (which becomes real TRX balance upon `WithdrawBalanceContract` execution) can be inflated beyond the backing reward pool, an unbacked-balance condition, or conversely can silently underpay voters, a form of fund loss for affected accounts.

### Likelihood Explanation
This code path executes automatically whenever any account with votes calls the standard `WithdrawBalanceContract` while operating under (or transitioning through) the pre-VI reward algorithm/cycles, or when `allowOldRewardOpt()` is not enabled — no special privileges are required, only a normal signed withdraw-balance transaction from a voting account. The rounding effect is deterministic and compounds every cycle/witness/voter combination processed via this method, making it reliably triggerable, though the magnitude per individual withdrawal may be small.

### Recommendation
Replace the division-then-multiplication with multiplication-then-division using integer/BigInteger arithmetic, consistent with the corrected VI-based path in the same class:
```java
reward += BigInteger.valueOf(userVote).multiply(BigInteger.valueOf(totalReward))
    .divide(BigInteger.valueOf(totalVote)).longValue();
```
This mirrors the fix already applied for `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DelegationStore.DECIMAL_OF_VI_REWARD)` elsewhere in `MortgageService.java`.

### Proof of Concept
1. Configure a network where `allowOldRewardOpt()` is false (or a cycle prior to `newRewardAlgorithmEffectiveCycle`) so `getOldReward` invokes the legacy `computeReward(long cycle, List<Pair<byte[], Long>> votes)`.
2. Set up a witness with `totalVote` and `totalReward` values chosen such that `userVote / totalVote` is not exactly representable in double precision (e.g., `totalVote = 3`, multiple voters each holding `userVote = 1`).
3. Have each voter broadcast a `WithdrawBalanceContract` transaction (via `WithdrawBalanceActuator.execute` → `MortgageService.withdrawReward` → `computeReward`).
4. Sum the resulting `allowance`/withdrawn amounts across all voters for that witness/cycle and compare against `delegationStore.getReward(cycle, srAddress)` (the recorded `totalReward`); observe the discrepancy caused by per-voter floating-point division-then-multiplication versus the true proportional share.     long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
