### Title
Stale postponed `ActionReceipt` bookkeeping survives `DeleteAccount`, allowing privileged actions (e.g. `AddKey(FullAccess)`) authorized by a deleted account to execute against a subsequently recreated account of the same name - ([File: runtime/runtime/src/actions.rs], [File: core/store/src/utils/mod.rs])

### Summary
`remove_account` (called from `action_delete_account`) only deletes the `Account`, `ContractCode`, `AccessKey`/gas-key, and `ContractData` trie entries for the deleted account; it never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId`. If an `ActionReceipt` with unmet `input_data_ids` was postponed against that account name before deletion, its bookkeeping remains in state, keyed only by the `AccountId` string, with no notion of "account incarnation". When the missing `DataReceipt` later arrives, `process_receipt`/`apply_action_receipt` will apply the stale receipt's actions against whatever account currently occupies that name.

### Finding Description
`remove_account` at [1](#0-0)  removes `TrieKey::Account`, `TrieKey::ContractCode`, access keys, gas-key nonces, and `TrieKey::ContractData`, but has no code path that touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId`. `action_delete_account` at [2](#0-1)  calls `remove_account` and otherwise only handles storage-cap checks, gas-key burn, and the balance refund — it never cleans up postponed-receipt state for the account being deleted.

Postponed-receipt bookkeeping is written by `process_action_receipt` when a receipt's `input_data_ids` are not all satisfied: it records a `PostponedReceiptId` per missing `data_id`, a `PendingDataCount`, and the full serialized `Receipt` under `TrieKey::PostponedReceipt`, all keyed by `receiver_id` (an `AccountId` string) plus `receipt_id`/`data_id` [3](#0-2) . These keys carry no reference to "which incarnation" of the account authorized them — the trie namespace is reused verbatim if the account name is deleted and recreated.

When the outstanding `DataReceipt` finally arrives, `process_receipt` looks up `PostponedReceiptId`/`PendingDataCount` purely by `account_id` (the receiver name) and `data_id`, decrements the pending count, and once it reaches zero fetches and removes the stored `Receipt` before executing it via `apply_action_receipt` [4](#0-3) . This execution proceeds against whatever `Account` record currently exists at that name — there is no check that the account is the same one that was current when the receipt was postponed.

The privileged actions this stale receipt could carry (`AddKey`, `DeployContract`, `Stake`, `DeleteKey`, `DeleteAccount`, etc.) are gated only by `check_actor_permissions`, which does a bare string comparison `actor_id != account_id` [5](#0-4) . `actor_id` for a top-level action receipt is derived from the receipt's own (frozen, previously-serialized) `predecessor_id`, and per the documented self-authorization rule, a `CreateAccount`-first receipt or a genuine self-call (`predecessor_id == receiver_id`) satisfies this check at receipt-construction time [6](#0-5) . Because this check only compares `AccountId` values baked into the stale receipt, and never verifies the account's identity/incarnation is unchanged, a postponed self-authorized `AddKeyAction` created before deletion will still pass `check_actor_permissions` when replayed against the new account occupying the same name after recreation.

I could not fully trace the precise line initializing `actor_id` inside `apply_action_receipt` (index was insufficient to confirm this final detail with certainty), but the general mechanism — `actor_id` is fixed from the stored receipt's `predecessor_id`, unrelated to the live account's history — is consistent with the documented self-authorization semantics in `Actions.md` and the `check_actor_permissions` implementation cited above.

### Impact Explanation
This is an authorization-escalation bug: a promise/receipt created and self-authorized by one incarnation of an account can execute privileged state changes (most severely `AddKey(FullAccess)`) against a completely different, later incarnation of the same account name, without the new account owner's consent. If exploited against an account name that changes ownership (e.g., recycled top-level names via registrar, or subaccounts transferred/sold), this allows the original account holder to inject a full-access key (or other administrative action) into the new owner's account, leading to theft of funds/contract hijack of the new owner's account.

### Likelihood Explanation
Exploitation requires: (1) the attacker to control an account, issue a multi-dependency `ActionReceipt` (e.g. via `promise_and`) to itself with an `AddKeyAction`, deliberately supply only part of the required `DataReceipt`s so the receipt is postponed, then delete the account; and (2) the account name to later be reused by a different party (e.g. reused top-level name via registrar, or a purchased/transferred subaccount namespace) who deposits funds/deploys a contract before the withheld `DataReceipt` is finally delivered by the attacker. All of the attacker-side steps are achievable by an ordinary unprivileged account with a self-deployed contract, using only standard promise/cross-contract-call primitives — no special privileges are required. The main constraint is the account-name-reuse precondition, which is scenario-dependent (registrar-controlled short names, or subaccount transfer/sale) rather than universally exploitable against arbitrary accounts, but is fully within the "ordinary client" threat model once that precondition holds.

### Recommendation
When an account is deleted (`remove_account`/`action_delete_account`), also purge any `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries keyed by that `receiver_id` (analogous to the iteration already done for access keys and contract data), so no dangling receipt bookkeeping can survive account deletion. Alternatively/additionally, bind postponed-receipt execution to an account "incarnation" identifier (e.g., a monotonic account creation nonce stored on the `Account` record) and validate it matches at execution time before applying the postponed actions.

### Proof of Concept
Runtime/apply integration test plan:
1. Set up an account `victim.attacker` (or any account) owned by the "attacker" signer.
2. Send an `ActionReceipt` to `victim.attacker` with two `input_data_ids` and actions `[AddKeyAction(FullAccess, attacker_pubkey)]`, with `predecessor_id == receiver_id == victim.attacker` (self-call, satisfying `check_actor_permissions`).
3. Deliver only one of the two `DataReceipt`s; assert `get_postponed_receipt`/`TrieKey::PendingDataCount`/`TrieKey::PostponedReceiptId` are present in state.
4. Apply a `DeleteAccount` receipt for `victim.attacker` (self-authorized, `actor_id == account_id`); commit trie changes; assert via `get_postponed_receipt` that the `TrieKey::PostponedReceipt` entry (and pending-data bookkeeping) is still present even though `get_account` now returns `None`.
5. Apply a `CreateAccount` receipt recreating `victim.attacker` under a different (new-owner) predecessor, funding it and optionally deploying a contract; commit.
6. Deliver the final withheld `DataReceipt` for `victim.attacker`; run `apply`; assert the execution outcome shows the `AddKeyAction` executed successfully (`check_actor_permissions` passed) and that `get_access_key(victim.attacker, attacker_pubkey)` now returns a `FullAccess` key on the new owner's account — demonstrating unauthorized privilege injection across account recreation.

    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {

        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {

                    account_id: account_id.clone(),

                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),

For the following actions, `predecessor_id` and `receiver_id` are required to be equal:

- `DeployContract`
- `Stake`

- `DeleteKey`
- `DeleteAccount`
