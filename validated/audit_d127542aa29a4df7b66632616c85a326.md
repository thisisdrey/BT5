### Title
Unbounded array allocation in `BatchValidateSign`/`ValidateMultiSign` TVM precompiles before size validation - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `BatchValidateSign` and `ValidateMultiSign` TVM precompiled contracts (addresses `0x9` and `0xa`) decode attacker-supplied ABI-encoded arrays from calldata by first reading an array-length word and only then allocating a Java array of that length. The `MAX_SIZE` bound check that is supposed to prevent oversized allocations is gated behind `VMConfig.allowTvmSelfdestructRestriction()`, a feature flag that defaults to `0` (disabled) until a committee proposal activates it. When the flag is not active, `extractBytesArray`/`extractBytes32Array` allocate arrays sized directly from unchecked calldata, matching the same "unsanitized length passed to buffer allocation" bug class as the referenced `http-proxy-agent` advisory (CWE-400).

### Finding Description
In `PrecompiledContracts.java`, `extractBytesArray` and `extractBytes32Array` allocate an array whose size is taken straight from calldata without any upper bound: [1](#0-0) 

These helpers are invoked from `ValidateMultiSign.execute` and `BatchValidateSign.doExecute`. The `MAX_SIZE` guard (5 for `ValidateMultiSign`, 16 for `BatchValidateSign`) is only executed `if (VMConfig.allowTvmSelfdestructRestriction())`; otherwise the code falls straight into `extractBytesArray`/`extractBytes32Array` with no size check at all: [2](#0-1) [3](#0-2) 

The flag defaults to `0` (disabled) unless a committee has passed the `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` proposal (hard fork gated at `VERSION_4_8_1`): [4](#0-3) 

On any deployment where this flag has not yet been activated (e.g., a private/consortium chain, a node freshly synced before the proposal passes, or any test/staging network running this codebase), a contract can call these precompiles with a crafted `bytes[]`/`address[]` length word (`intValueSafe()` on a `DataWord`, which can return values up to `Integer.MAX_VALUE`) causing `new byte[len][]` to attempt to allocate hundreds of millions of array-reference slots before any energy-bounded validation rejects it.

### Impact Explanation
A single unprivileged TVM `CALL` (or `STATICCALL`) to precompile address `0x9`/`0xa` with malicious calldata can force the node to attempt allocating an oversized array (`new byte[Integer.MAX_VALUE][]` in the worst case), which throws `OutOfMemoryError` or induces severe GC pressure. Because `BatchValidateSign`/`ValidateMultiSign` are also invoked in `isConstantCall()` (i.e., accessible via `TriggerConstantContract`/read-only JSON-RPC `eth_call`), this is reachable from an anonymous API client without spending real energy/fees for a full transaction, amplifying the DoS potential. Repeated calls can degrade or crash node processes serving RPC/API requests, impacting availability of the node.

### Likelihood Explanation
Likelihood depends entirely on whether `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has been activated on the target network. On networks/nodes where the flag has not been enabled (default `0`), the guard is completely bypassed and the path is trivially reachable by any address that can submit a contract call or constant call — no special privilege required. On mainnet-like deployments where the proposal has already passed, the guard closes this path, reducing likelihood to those chains/nodes still pending activation.

### Recommendation
Move the `MAX_SIZE` bound check so that it is always enforced before calling `extractBytesArray`/`extractBytes32Array`/`extractSigArray`, independent of the `allowTvmSelfdestructRestriction` flag. Alternatively, add an unconditional sanity cap (e.g., reject if the declared array length exceeds a small constant, or exceeds what the remaining calldata could possibly encode) inside `extractBytesArray`/`extractBytes32Array` themselves before allocation.

### Proof of Concept
1. Deploy any contract on a java-tron network/node where `ALLOW_TVM_SELFDESTRUCT_RESTRICTION` has not been activated (default state, flag == 0).
2. From the contract (or via `TriggerConstantContract`/`eth_call`), issue a `CALL`/`STATICCALL` to address `0x000...09` (BatchValidateSign) or `0x000...0a` (ValidateMultiSign) with ABI-encoded calldata where the array-length word for the `bytes[]`/`address[]` parameter is set to a very large value (e.g., `0x7FFFFFFF`), while keeping the head words minimally valid so `DataWord.parseArray`/offset math doesn't throw before reaching `extractBytesArray`/`extractBytes32Array`.
3. Observe the node attempt `new byte[0x7FFFFFFF][]`, triggering `OutOfMemoryError`/excessive GC, degrading or crashing the executing node/JVM.

  private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
    int len = words[offset].intValueSafe();
    byte[][] bytes32Array = new byte[len][];
    for (int i = 0; i < len; i++) {
      bytes32Array[i] = words[offset + i + 1].getData();
    }
    return bytes32Array;
  }

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
