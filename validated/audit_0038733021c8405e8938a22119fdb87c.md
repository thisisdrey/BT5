### Title
Attachment size limit bypass in P2P download path allows unbounded attachment storage - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsDownloader::run` writes downloaded attachments to `AtlasDB` via `AtlasDB::insert_instantiated_attachment` without ever calling `AtlasDB::should_keep_attachment`, so the `attachments_max_size` bound enforced elsewhere (in `posttransaction.rs`) is not applied to attachments fetched from peers over P2P. A malicious outbound sync peer that responds to a `GET /v2/attachments/<hash>` request with oversized-but-hash-matching content gets that content permanently persisted to the local `attachments` SQLite table.

### Finding Description
In `download.rs`, when the `AttachmentsBatchStateMachine` reaches `Done`, the code drains `context.attachments` (populated in `extend_with_attachments`, which only checks `decode_atlas_get_attachment()` succeeded and does not check content length) and calls: [1](#0-0) 
This directly calls `network.atlasdb.insert_instantiated_attachment(&attachment)` with no size validation against `AtlasConfig.attachments_max_size`. By contrast, `should_keep_attachment` (defined in `stackslib/src/net/atlas/db.rs`) is the intended gate for enforcing `attachments_max_size`, but it is only invoked from `stackslib/src/net/api/posttransaction.rs` for locally-submitted transactions — not from the P2P attachment-download path. The `attachments` table schema itself has no size constraint (`content BLOB NOT NULL`), [2](#0-1) , so nothing at the DB layer prevents an oversized blob from being written. Since `decode_atlas_get_attachment` only validates that the response decodes and (implicitly, via the batch resolution logic) that the content hash matches, an attacker peer that serves a valid hash together with content exceeding `attachments_max_size` will have that oversized content silently accepted and stored.

### Impact Explanation
An unauthenticated (in the sense of not requiring any privileged role — merely being selected as an outbound sync peer) remote peer can cause a victim node to persist attachment BLOBs larger than the operator-configured `attachments_max_size` into its local AtlasDB. This is a write of attacker-controlled state that bypasses an existing security control (`should_keep_attachment`), and is repeatable per distinct attachment instance the node is trying to resolve. Actual per-message data volume is still bounded by the general HTTP/P2P message size limits, so this is a bypass of the atlas-specific size policy rather than truly unbounded disk exhaustion — consistent with a High-severity "guard bypass leading to unauthorized write to local state" rather than a Critical, few-message DoS.

### Likelihood Explanation
The attacker only needs to be an outbound sync peer for the victim (i.e., a running Stacks node that the victim dials, or in a small/test network, any reachable peer) and needs a pending `AttachmentInstance` for the content hash to exist on the victim (which happens automatically as the victim processes blocks that reference attachments). No secrets, no privileged role, and no additional preconditions beyond normal Atlas attachment syncing are required, making this low-cost and reliably reproducible.

### Recommendation
Apply the same `should_keep_attachment` (or equivalent size) check against `atlas_config.attachments_max_size` in `AttachmentsDownloader::run` before calling `insert_instantiated_attachment`, rejecting/discarding any downloaded attachment whose content length exceeds the configured maximum, and treating the serving peer as unreliable/faulty in that case.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` (or a new test module) that:
1. Constructs an `AtlasDB` with `AtlasConfig.attachments_max_size` set to a small value (e.g. 10 bytes).
2. Sets up a pending `AttachmentInstance` for a known `content_hash`.
3. Drives `AttachmentsBatchStateMachine` (or directly constructs the `Done` context with `context.attachments` populated) with an `Attachment` whose `content` is `attachments_max_size + 1` bytes but whose `hash()` matches the pending instance's `content_hash`.
4. Calls `AttachmentsDownloader::run` (or the `Done` arm logic directly) and then queries `atlasdb.conn` for the row in the `attachments` table.
5. Asserts the row exists with `content.len() > attachments_max_size`, proving the size limit was bypassed, in contrast to `should_keep_attachment` which would reject it if called.
