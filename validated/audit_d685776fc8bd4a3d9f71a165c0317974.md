Based on the investigation, the closest local structural analog to the INTX report is in `pallet-broker`'s Region (coretime) NFT split operations, not in nomination-pools (which is account-keyed, not token-transferable, and therefore not vulnerable to this bug class at all).

### Title
Inconsistent `paid`-status reset between `do_partition` and `do_interlace` allows a split Coretime Region to retain full purchase-price status on both fragments - (File: `substrate/frame/broker/src/dispatchable_impls.rs`)

### Summary
`pallet-broker` represents purchased bulk coretime as a transferable, splittable NFT-like `RegionId`/`RegionRecord`. A `RegionRecord` carries a `paid: Option<BalanceOf<T>>` field recording the amount the current Region was actually purchased for [1](#0-0) . Regions can be split two ways: `partition()` (time-split) and `interlace()` (core-mask split), and transferred via `transfer()` [2](#0-1) . `do_partition` explicitly wipes the purchase-price marker on split (`region.paid = None;`) before writing the two resulting records, but `do_interlace` performs no equivalent reset and copies the full, unmodified `region` (with its original `paid` value intact) into **both** resulting `RegionId` records [3](#0-2) .

### Finding Description
This is structurally the same bug class as the INTX report: a value/eligibility marker attached to a fungible-like position (`paid`, analogous to xINTX's reward-boost/penalty-eligibility state) is properly reset by one state-mutating path (`partition`, analogous to a correctly-guarded `unstake`) but is silently preserved by a sibling path that performs an equivalent "split" operation (`interlace`, analogous to the unguarded `split()` in the INTX contract). The `nft_metadata_works` test directly demonstrates the asymmetry: after `do_transfer` + `do_partition`, the `paid` attribute on the resulting region becomes `None`, while no equivalent test or code path shows `paid` being cleared by `do_interlace` [1](#0-0) . Because `do_interlace` duplicates the full `RegionRecord` (including `paid`) into two independent `RegionId` entries in storage [4](#0-3) , an attacker holding one purchased Region can call `interlace()` to obtain two independently-transferable/independently-manageable Regions that both still carry the original `paid` marker, rather than a properly prorated or cleared value as `partition` enforces.

### Impact Explanation
If `paid` is consumed downstream by fund-affecting logic (e.g. unused-region reclamation/refund via `drop_region`, or eligibility checks tied to whether a Region was "purchased" versus reserved/leased), then interlacing duplicates that purchase-credit across two independent Region records instead of splitting it. This falls into the "duplicate settlement or payout" / "unbacked mint or unlock" impact category: the same underlying paid-for value could be claimed or relied upon twice (once per interlaced fragment), each transferable to a different party, exactly mirroring how the INTX `split()` function let a single staked position spawn two independently-tradeable positions that both retained favorable non-reset state.

### Likelihood Explanation
The path is public and requires no privileged actor: any signed account that owns a purchased Region can call `interlace` [5](#0-4) , and ownership checks (`NotOwner`) are the only guard — they do not address the `paid`-field asymmetry [6](#0-5) . No malicious validator, collator, relayer, or governance action is needed.

### Recommendation
Make `do_interlace` treat `paid` the same way `do_partition` does — either clear `region.paid` to `None` on both resulting interlaced Regions (mirroring `do_partition`'s `region.paid = None;`) or, if `paid` is meant to be prorated, split it proportionally to the interlace mask ratio rather than duplicating it unchanged into both fragments [3](#0-2) .

### Proof of Concept
1. Account 1 purchases a Region, `paid = Some(price)` is set on the resulting `RegionRecord` [7](#0-6) .
2. Account 1 calls `Broker::interlace(region, pivot_mask)`, producing `region1` and `region2`, both retaining `paid = Some(price)` because `do_interlace` copies `region` unmodified into both new records [4](#0-3) .
3. Account 1 transfers `region2` to Account 2 via `Broker::transfer` [8](#0-7) .
4. Both Account 1 (`region1`) and Account 2 (`region2`) now independently hold a Region whose `paid` marker reflects the full original purchase price rather than a prorated/cleared value — contrast with the same scenario using `partition` instead of `interlace`, where `paid` is explicitly zeroed [9](#0-8) .

**Caveat:** I was not able to fully trace, within the available search iterations, every downstream on-chain consumer of the `paid` field (e.g. inside `drop_region`) to confirm the exact fund-value effect. The evidence firmly establishes the code asymmetry between `do_partition` and `do_interlace`; a background engineer should verify `drop_region` and any other `paid`-reading logic in `substrate/frame/broker/src/` to confirm the precise monetary consequence before treating this as a confirmed high-severity fund-loss bug.

	pub(crate) fn do_transfer(
		region_id: RegionId,
		maybe_check_owner: Option<T::AccountId>,
		new_owner: T::AccountId,
	) -> Result<(), Error<T>> {
		let mut region = Regions::<T>::get(&region_id).ok_or(Error::<T>::UnknownRegion)?;

		if let Some(check_owner) = maybe_check_owner {
			ensure!(Some(check_owner) == region.owner, Error::<T>::NotOwner);
		}

		let old_owner = region.owner;
		region.owner = Some(new_owner);
		Regions::<T>::insert(&region_id, &region);
		let duration = region.end.saturating_sub(region_id.begin);
		Self::deposit_event(Event::Transferred {
			region_id,
			old_owner,
			owner: region.owner,
			duration,
		});

		Ok(())
	}

	pub(crate) fn do_partition(
		region_id: RegionId,
		maybe_check_owner: Option<T::AccountId>,
		pivot_offset: Timeslice,
	) -> Result<(RegionId, RegionId), Error<T>> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let mut region = Regions::<T>::get(&region_id).ok_or(Error::<T>::UnknownRegion)?;

		if let Some(check_owner) = maybe_check_owner {
			ensure!(Some(check_owner) == region.owner, Error::<T>::NotOwner);
		}
		let pivot = region_id.begin.saturating_add(pivot_offset);
		ensure!(pivot < region.end, Error::<T>::PivotTooLate);
		ensure!(pivot > region_id.begin, Error::<T>::PivotTooEarly);

		region.paid = None;
		let new_region_ids = (region_id, RegionId { begin: pivot, ..region_id });

		// Remove this region from the pool in case it has been assigned provisionally. If we get
		// this far then it is still in `Regions` and thus could only have been pooled
		// provisionally.
		Self::force_unpool_region(region_id, &region, &status);

		// Overwrite the previous region with its new end and create a new region for the second
		// part of the partition.
		Regions::<T>::insert(&new_region_ids.0, &RegionRecord { end: pivot, ..region.clone() });
		Regions::<T>::insert(&new_region_ids.1, &region);
		Self::deposit_event(Event::Partitioned { old_region_id: region_id, new_region_ids });

		Ok(new_region_ids)
	}

	pub(crate) fn do_interlace(
		region_id: RegionId,
		maybe_check_owner: Option<T::AccountId>,
		pivot: CoreMask,
	) -> Result<(RegionId, RegionId), Error<T>> {
		let status = Status::<T>::get().ok_or(Error::<T>::Uninitialized)?;
		let region = Regions::<T>::get(&region_id).ok_or(Error::<T>::UnknownRegion)?;

		if let Some(check_owner) = maybe_check_owner {
			ensure!(Some(check_owner) == region.owner, Error::<T>::NotOwner);
		}

		ensure!((pivot & !region_id.mask).is_void(), Error::<T>::ExteriorPivot);
		ensure!(!pivot.is_void(), Error::<T>::VoidPivot);
		ensure!(pivot != region_id.mask, Error::<T>::CompletePivot);

		// Remove this region from the pool in case it has been assigned provisionally. If we get
		// this far then it is still in `Regions` and thus could only have been pooled
		// provisionally.
		Self::force_unpool_region(region_id, &region, &status);

		// The old region should be removed.
		Regions::<T>::remove(&region_id);

		let one = RegionId { mask: pivot, ..region_id };
		Regions::<T>::insert(&one, &region);
		let other = RegionId { mask: region_id.mask ^ pivot, ..region_id };
		Regions::<T>::insert(&other, &region);

		let new_region_ids = (one, other);
		Self::deposit_event(Event::Interlaced { old_region_id: region_id, new_region_ids });
		Ok(new_region_ids)
	}
