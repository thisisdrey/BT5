### Title
Unauthenticated `RecvError` Packet Allows Remote Tunnel State Poisoning via Source-Address Spoofing - (File: outside.go)

### Summary
`Interface.handleRecvError` in `outside.go` processes `header.RecvError` packets before any certificate, handshake, or encryption check is performed. The only "authentication" applied is a comparison between the packet's UDP source address and the `HostInfo`'s currently known remote address (`hr != addr`). This is directly analogous to the `NibblVault.updateTWAV` finding: a function that is reachable without passing the primary authorization gate (there, `whenNotPaused`; here, decryption/cert verification) is still allowed to mutate protocol state — closing an active, authenticated tunnel and deleting its handshake-manager entry.

### Finding Description
In `readOutsidePackets` (`outside.go:76-84`), the dispatch switch handles `header.RecvError` immediately after basic header parsing/version/subtype checks, calling `f.handleRecvError(via.UdpAddr, h)` — this happens *before* `hostinfo` is looked up, *before* any decryption, and critically before any proof that the sender possesses the session keys for the targeted tunnel: [1](#0-0) 

`handleRecvError` then:
1. Checks a config-driven policy (`acceptRecvErrorConfig.ShouldRecvError`) that is about IP privacy classification, not authentication.
2. Looks up the target `hostinfo` purely from an attacker-supplied 32-bit `RemoteIndex` in the cleartext header.
3. Compares only the observed UDP source `netip.AddrPort` against the hostinfo's last known remote address, then unconditionally tears down the tunnel and deletes handshake-manager state if the addresses "match": [2](#0-1) 

Because UDP is connectionless and source addresses are trivially spoofable (this is exactly the same on-path/off-path spoofing threat model already acknowledged elsewhere in the codebase, e.g. the `remote_allow_list` and conntrack-spoofing tests), an attacker who can guess/observe both the 32-bit `RemoteIndex` and the victim's current UDP endpoint can forge a `RecvError` packet and force `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)` — mutating live tunnel state without ever presenting a valid certificate, without completing a handshake, and without decrypting anything.

### Impact Explanation
This lets an unauthenticated network attacker remotely force teardown of an established, authenticated Nebula tunnel between two legitimate peers (denial of service / forced re-handshake), directly analogous to the reported bug's "buyout rejected without allowing other users to challenge" — here, an active session is terminated without either legitimate peer's consent or any cryptographic proof from the attacker. Repeated forgery can be used to persistently disrupt a specific tunnel (state poisoning / DoS), and forces relatively costly re-handshakes, which the maintainers themselves flagged as a concern serious enough to add a `send_recv_error`/`accept_recv_error` config knob and a changelog security note in past releases.

### Likelihood Explanation
`RemoteIndex` is a 32-bit value sent in cleartext in every packet for a tunnel, so it is observable to any on-path attacker (or one with partial visibility, e.g. via NAT/ISP-level spoofing) without needing the CA-signed certificate that gates every other state-changing path in Nebula. The UDP source-address check is the only barrier, and UDP source spoofing is a long-known, low-cost technique; the codebase's own tests (`TestFirewall_ConntrackSourceSpoofingAcrossPeers`) show the project already treats source-address spoofing as an in-scope threat model.

### Recommendation
Do not allow `RecvError` to trigger tunnel teardown based solely on `RemoteIndex` + source-address match. Options:
- Require `handleRecvError` to only act when the reporting endpoint corresponds to a session that has itself completed authentication (e.g., require a valid HMAC/counter proof bound to the session keys, or drop `RecvError` entirely by default and rely on dead-tunnel detection).
- At minimum, treat `RecvError` as an advisory signal to *probe* liveness rather than to unconditionally close the tunnel immediately — e.g., trigger a `Test`/`TestRequest` round-trip check before calling `closeTunnel`, mirroring how `SetRemoteIfPreferred`/roaming code requires observed traffic rather than accepting header claims at face value.

### Proof of Concept
1. Establish a legitimate Nebula tunnel between hosts A and B; observe A ↔ B UDP traffic to learn B's `localIndexId` (sent in cleartext as `RemoteIndex` in every packet A sends to B) and B's current UDP source/dest `AddrPort`.
2. From attacker-controlled infrastructure capable of spoofing UDP source address `B`'s address (or from an on-path position), craft a raw UDP packet to A's listener with `header.RecvError`, `RemoteIndex` = B's observed `localIndexId`, and source address spoofed to match B's known `AddrPort`.
3. Send the packet to A. `handleRecvError` finds the matching `hostinfo`, sees `hr == addr`, and calls `f.closeTunnel(hostinfo)` and `f.handshakeManager.DeleteHostInfo(hostinfo)` — tearing down the A↔B tunnel state without ever presenting a certificate or completing a handshake, exactly mirroring the reported bug class of state-changing calls that bypass the system's primary authorization gate.

func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
