### Title
OS Command Injection via unsanitized `git_repository` `remote` attribute reaching `git remote add` / `git fetch` without protocol allowlisting - (File: tools/build_defs/repo/git_worker.bzl)

### Summary
`git_repository`/`new_git_repository` accept a `remote` attribute that is forwarded verbatim into `git remote add origin <remote>` and subsequently used implicitly by `git fetch origin`, with no validation of scheme and no `GIT_ALLOW_PROTOCOL` restriction. Git supports an `ext::` remote-helper transport that executes an arbitrary shell command supplied inside the URL. A hostile Bazel registry (an unprivileged, attacker-controlled origin per the threat model) can serve a `source.json` of `"type": "git_repository"` whose `remote` field is `ext::sh -c "<attacker command>"`, and Bazel will run it during `bazel fetch`/`bazel build` with no checksum or integrity control comparable to the `sha256`/`integrity` fields used for `http_archive`.

### Finding Description
`_clone_or_update_repo` → `git_repo()` in `tools/build_defs/repo/git_worker.bzl` builds a `_GitRepoInfo` with `remote = str(ctx.attr.remote)` [1](#0-0) , then `_update` calls `add_origin(ctx, git_repo, ctx.attr.remote)` which executes `_git(ctx, git_repo, "remote", "add", "origin", remote)` [2](#0-1) . This ultimately becomes `git -c core.fsmonitor=false remote add origin <remote>` via `_execute` [3](#0-2) , followed by `git fetch origin -- <fetch_ref>` [4](#0-3) .

`remote` is declared as a plain `attr.string(mandatory = True, ...)` with no format/scheme restriction [5](#0-4) . Because `git` natively supports the `ext::<command>` remote-helper protocol, a value such as `ext::sh -c "id > /tmp/pwned"` passed as the origin URL causes the local `git` binary to invoke `sh -c` directly — this is a documented feature of git itself, not a bug in the shell quoting, so no amount of `bash -c` quoting protects against it. Unlike `http_archive`'s `sha256`/`integrity` checksum, which is verified before use (per the docstrings for `download`/`download_and_extract` [6](#0-5) ), the bzlmod registry `git_repository` source type has no equivalent integrity pinning on `remote`, `commit`, `tag`, or `branch` — the registry docs show these fields are simply forwarded verbatim to the underlying rule [7](#0-6) .

The codebase already anticipates *option*-injection via `commit`/flags (see the regression test `test_git_repository_invalid_commit`, which crafts `commit = "--upload-pack=touch $sentinel #"` and asserts the sentinel file is *not* created) [8](#0-7) , and `fetch()` defends against this specific vector by inserting a `--` separator before `git_repo.fetch_ref` [9](#0-8) . However, `add_origin`'s call — `_git(ctx, git_repo, "remote", "add", "origin", remote)` — has no `--` separator, and more importantly `ext::` is not a CLI flag/option at all, so a `--` guard would not stop it: it is a legitimate git *transport scheme* that runs a subprocess, which is a fundamentally different bug class than the leading-dash flag-injection the existing test covers.

### Impact Explanation
Successful exploitation executes arbitrary attacker-chosen commands on the machine running `bazel fetch`/`bazel build`, with the privileges of the Bazel client process, whenever the victim resolves a Bazel module backed by a `git_repository` source hosted or mirrored by a malicious/compromised registry. This satisfies "write or read outside the repository/exec root/output base" and full command execution — equivalent in severity to the CWE-78 OS Command Injection in the reference advisory.

### Likelihood Explanation
A public or third-party Bazel Registry (per `docs/external/registry.mdx`, registries can be "a local directory or a static HTTP server") is exactly the class of untrusted, attacker-published content the threat model designates in-scope: an outsider publishing content that a victim's build consumes without local trust decisions. Setting `bazel_dep()` on a module resolved from such a registry with a `git_repository` `source.json` is a normal, expected Bzlmod workflow, requiring no MITM or credential compromise — only that the registry itself (or a module maintainer within it) is hostile, matching the CVSS `AV:N/AC:L/PR:N/UI:N` vector of the reference CVE.

### Recommendation
Restrict the accepted git transport for `remote` (and equivalently for any BCR-declared `remote` fields of `git_repository`-typed modules) to safe network protocols (`https`, `http`, `git`, `ssh`, `file`) by validating the URL scheme in `tools/build_defs/repo/git.bzl`/`git_worker.bzl` before invoking `git`, and/or pass `GIT_ALLOW_PROTOCOL=http:https:git:ssh:file` in the environment used by `_execute` in `git_worker.bzl` so that `ext::` and other command-executing transports are rejected by git itself regardless of caller-side validation gaps.

### Proof of Concept
A `src/test/shell/bazel/starlark_git_repository_test.sh`-style regression test, following the pattern of the existing `test_git_repository_invalid_commit` [8](#0-7) :
```sh
function test_git_repository_ext_transport_command_injection() {
  local sentinel=$TEST_TMPDIR/sentinel_ext_transport
  cat >> MODULE.bazel <<EOF
git_repository = use_repo_rule('@bazel_tools//tools/build_defs/repo:git.bzl', 'git_repository')
git_repository(
    name = "evil_repo",
    remote = "ext::sh -c 'touch $sentinel'",
    commit = "0000000000000000000000000000000000000000",
)
EOF
  bazel fetch @evil_repo >& $TEST_log
  if [ -e "$sentinel" ]; then
    fail "Sentinel file was created - arbitrary command executed via ext:: transport!"
  fi
}
```
Note: I could not execute this test in this environment; I traced the vulnerable code path but could not confirm at runtime whether some other unseen layer (e.g., a `GIT_ALLOW_PROTOCOL` set elsewhere, or a Bazel-bundled git wrapper) blocks the `ext::` transport — no such restriction was found in the indexed Starlark or Java sources, but I could not rule out an environment-level mitigation outside the indexed code (e.g., a hardened bundled `git` binary or sandbox `PATH` restriction) that isn't visible in this codebase snapshot.

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.

        # "everything that is already specified and all tags"; before 1.9, it used to mean

            "fetch",
            "origin",

            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
