### Title
Missing verification that `RelayFromAddr` matches the authenticated peer's own VPN address allows relay state poisoning — (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` accepts an attacker-controlled `RelayFromAddr` field from a `CreateRelayRequest` control message and uses it to install relay state (`AddRelay`) without ever checking that the claimed address actually belongs to the authenticated sender `h`. Any node holding a valid, mutually-authenticated tunnel can therefore claim to be relaying "for" an arbitrary victim VPN address it does not own, poisoning the target node's relay tables and causing that node to route traffic intended for the victim through the attacker's own tunnel instead of the legitimate path.

### Finding Description
`HandleControlMsg` dispatches an incoming, already-decrypted `Control` message to `handleCreateRelayRequest`, passing `h`, the `HostInfo` of the *authenticated* peer that sent the packet: [1](#0-0) [2](#0-1) 

Inside `handleCreateRelayRequest`, the "from" address is taken directly from the attacker-supplied protobuf field, not from `h.vpnAddrs`: [3](#0-2) 

When the target is the receiving node itself, the code immediately registers a new Terminal relay keyed by the *claimed* `from` address on the authenticated `HostInfo h`, with no check that `from` is one of `h.vpnAddrs`: [4](#0-3) 

This is the same bug class as the reference "any account can exercise any option" report: the code accepts an identity/ownership claim embedded in caller-supplied data (`RelayFromAddr`) instead of checking it against the caller's own authenticated identity (`h.vpnAddrs`, established via the certificate handshake). The codebase demonstrates elsewhere that this exact check is expected: `LightHouseHandler.handleHostUpdateNotification` explicitly validates a self-reported address against the authenticated sender's `fromVpnAddrs` before trusting it ("Simple check that the host sent this not someone else"): [5](#0-4) 

No equivalent check exists for `RelayFromAddr` in `handleCreateRelayRequest`.

### Impact Explanation
`AddRelay` inserts an entry into `h.relayState`, associating the attacker's own authenticated `HostInfo` as a relay path to the victim's `PeerAddr`: [6](#0-5) 

This relay state is later consulted whenever the target node needs to send traffic to that VPN address through a relay (`QueryVpnAddrsRelayFor` / `sendNoMetrics`'s relay fallback path): [7](#0-6) [8](#0-7) 

By spoofing `RelayFromAddr` to a victim's real VPN address, an attacker can poison the responder's relay table so packets destined for the victim are instead delivered to (or routed through) the attacker's tunnel — a remote state-poisoning primitive that can be leveraged to intercept, black-hole, or redirect a victim's traffic without ever holding that victim's certificate.

### Likelihood Explanation
Any node with a valid, CA-signed certificate can complete a normal handshake and send arbitrary `Control`/`CreateRelayRequest` messages over its own authenticated tunnel; `RelayFromAddr` is fully attacker-controlled protobuf input and is not cross-checked against the sender's own certificate-derived VPN addresses at any point in `HandleControlMsg` or `handleCreateRelayRequest`. Exploitation requires no lighthouse or relay role beyond being a normal mutually-authenticated peer that another node will accept relay requests from.

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), require that the claimed `from` address be contained in `h.vpnAddrs` before creating or completing any relay state, e.g.:
```go
if !slices.Contains(h.vpnAddrs, from) {
    logMsg.Error("Discarding relay request with spoofed RelayFromAddr", "claimedFrom", from, "actualVpnAddrs", h.vpnAddrs)
    return
}
```
mirroring the existing self-reported-address check already used in `handleHostUpdateNotification`.

### Proof of Concept
1. Attacker node `A` completes a normal, valid handshake with target node `T` (both hold valid CA-signed certs; `A`'s cert grants it VPN address `10.0.0.5`).
2. `A` sends `T` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to `10.0.0.99` (belonging to victim `V`, who `A` does not control) and `RelayToAddr` set to `T`'s own address.
3. `T` receives this over its authenticated tunnel with `A` and calls `handleCreateRelayRequest`. Since `f.myVpnAddrsTable.Contains(target)` is true and there is no existing relay for `from=10.0.0.99`, `T` calls `AddRelay(rm.l, h /* = A's HostInfo */, f.hostMap, 10.0.0.99, ...)`, marking `A`'s tunnel as an `Established` Terminal relay for `10.0.0.99`.
4. If `T` subsequently needs to relay traffic toward `10.0.0.99` (e.g., because a direct path is unavailable and `T`'s relay list includes this poisoned entry via later flows, or another node queries `T`'s hostmap through `QueryVpnAddrsRelayFor`), that traffic is routed through `A`'s tunnel rather than to the legitimate host `V`, all without `A` ever presenting a certificate for `10.0.0.99`.

func (rm *relayManager) HandleControlMsg(h *HostInfo, d []byte, f *Interface) {
	msg := &NebulaControl{}
	err := msg.Unmarshal(d)
	if err != nil {
		h.logger(f.l).Error("Failed to unmarshal control message", "error", err)
		return
	}

	var v cert.Version
	if msg.OldRelayFromAddr > 0 || msg.OldRelayToAddr > 0 {
		v = cert.Version1

		b := [4]byte{}
		binary.BigEndian.PutUint32(b[:], msg.OldRelayFromAddr)
		msg.RelayFromAddr = netAddrToProtoAddr(netip.AddrFrom4(b))

		binary.BigEndian.PutUint32(b[:], msg.OldRelayToAddr)
		msg.RelayToAddr = netAddrToProtoAddr(netip.AddrFrom4(b))
	} else {
		v = cert.Version2
	}

	// validate:
	switch msg.Type {
	case NebulaControl_CreateRelayRequest, NebulaControl_CreateRelayResponse:
		if msg.RelayFromAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayFromAddr", "type", msg.Type)
			}
			return
		} else if msg.RelayToAddr == nil {
			if f.l.Enabled(context.Background(), slog.LevelDebug) {
				h.logger(f.l).Debug("Control message received with nil RelayToAddr", "type", msg.Type)
			}
			return
		}
	}

	switch msg.Type {
	case NebulaControl_CreateRelayRequest:
		rm.handleCreateRelayRequest(v, h, f, msg)
	case NebulaControl_CreateRelayResponse:
		rm.handleCreateRelayResponse(v, h, f, msg)
	}
}

func (hm *HostMap) QueryVpnAddrsRelayFor(targetIps []netip.Addr, relayHostIp netip.Addr) (*HostInfo, *Relay, error) {
	hm.RLock()
	defer hm.RUnlock()

	// This runs per relayed packet, so check the primary with a single map probe and only consult
	// moreHosts when the primary can't relay for us.
	h, ok := hm.Hosts[relayHostIp]
	if !ok {
		return nil, nil, errors.New("unable to find host")
	}

	for _, targetIp := range targetIps {
		r, ok := h.relayState.QueryRelayForByIp(targetIp)
		if ok && r.State == Established {
			return h, r, nil
		}
	}

	if list, ok := hm.moreHosts[relayHostIp]; ok {
		// list[0] is the primary we already checked
		for _, h := range list[1:] {
			for _, targetIp := range targetIps {
				r, ok := h.relayState.QueryRelayForByIp(targetIp)
				if ok && r.State == Established {
					return h, r, nil
				}
			}
		}
	}

	return nil, nil, errors.New("unable to find host with relay")
}
