### Title
Attacker can permanently block a victim from receiving new collateral types by dust-filling their `depositTokensOfAccount` list — (File: contracts/DepositToken.sol, contracts/Pool.sol)

### Summary
The SYMMIO bug class is "unprivileged lock/unlock griefing that blocks a victim's pending actions at no cost to the attacker." The strongest reachable analog in Metronome is the per-account deposit-token list cap (`MAX_TOKENS_PER_USER`): any EOA can force-push dust amounts of `DepositToken` shares to a victim via `transfer`/`transferFrom`, and each new token type permanently occupies a slot in the victim's `MappedEnumerableSet` inside `Pool` storage. Once the list is full, every mint/transfer of a *new* deposit token to the victim reverts, blocking them from depositing new collateral types or receiving seized/liquidation collateral — with no penalty mechanism for the griefer.

### Finding Description
- `DepositToken._transfer` adds the token to the recipient's per-account list whenever the recipient's prior balance of that token was zero (`contracts/DepositToken.sol:517-520`).
- `DepositToken._mint` does the same on deposit (`contracts/DepositToken.sol:485-488`), so `deposit(amount_, victim)` also routes through `pool.addToDepositTokensOfAccount(victim)`.
- `Pool` stores per-account lists in a `MappedEnumerableSet` capped by `MAX_TOKENS_PER_USER` (`contracts/Pool.sol`, `contracts/storage/PoolStorage.sol`, `contracts/lib/MappedEnumerableSet.sol`). `addToDepositTokensOfAccount` reverts once the cap is reached — this is the state-bloat lock that mirrors the pending-quote cap in the source report.
- Deposit entries are only removed when the balance returns to exactly zero (`contracts/DepositToken.sol:460-462`, `contracts/DepositToken.sol:523-525`), so the victim can only free a slot by fully withdrawing or transferring out each dusted token — and they cannot even transfer a token whose unlock check fails (`_revertIfLocked`, `contracts/DepositToken.sol:180-182`) while carrying debt.

Attack path (all unprivileged):
1. Attacker deposits dust of collateral type A (`DepositToken.deposit(1 wei underlying, attacker)`), receiving dust `msdA`.
2. Attacker calls `msdA.transfer(victim, 1)` — victim's list gains entry A.
3. Repeat for every registered deposit token (or repeatedly alternate two tokens so the victim's balance never hits zero on removal) until the victim's `depositTokensOfAccount` length hits `MAX_TOKENS_PER_USER`.
4. Any subsequent `deposit` to the victim of a token not already in their list reverts in `_mint` → `addToDepositTokensOfAccount`; `transfer`/`transferFrom` of a new token to the victim reverts in `_transfer`. `Pool.liquidate` → `DepositToken.seize` → `_transfer` also reverts if the liquidator's target list or a seize-recipient list is filled the same way.

### Impact Explanation
Direct liveness break of the deposit invariant: the victim cannot add new collateral positions (deposit onBehalfOf, transfers of new msdTOKENs) and liquidations that would credit a new token type to a full account revert. This is temporary/permanent freezing of funds (victim cannot open or grow positions; recovery requires paying gas to exit each dusted slot, and cannot be done at all for locked balances while in debt). It mirrors the source issue's impact: pending slots exhausted by an attacker with no penalty.

### Likelihood Explanation
Cost to the attacker is dust-level deposits plus gas per token; there is no fee, penalty, or rate limit on `transfer` or `deposit` of tiny amounts (deposit fee can be zero, `quoteDepositOut` returns `fee = 0` when `depositFee() == 0`). Any EOA can execute it, no privileged role or oracle manipulation needed. The cap is a fixed finite constant, so filling it is bounded work.

### Recommendation
- Require a minimum first-deposit / minimum transfer amount per new token entry, or charge a fee on additions to `depositTokensOfAccount`.
- Allow removals/cleanup by anyone (e.g., `removeFromDepositTokensOfAccount` when balance is zero already exists — ensure dust cannot be re-pushed into a slot that was just freed within the same list, or track set membership by a non-balance criterion).
- Alternatively, let `addToDepositTokensOfAccount` skip reverting at the cap and instead auto-eject zero/dust entries, so griefed slots self-heal.

### Proof of Concept
Foundry fork test sketch (Hardhat equivalent identical):

```solidity
// assume pool with >= MAX_TOKENS_PER_USER deposit tokens registered,
// or attacker deposits dust of two tokens repeatedly is not needed —
// filling requires one dust deposit + transfer per registered token.
function test_dustFillVictimList() public {
    address victim = makeAddr("victim");
    uint256 cap = pool.MAX_TOKENS_PER_USER(); // constant

    address[] memory tokens = pool.getDepositTokens();
    require(tokens.length >= cap, "need enough collateral types");

    for (uint256 i; i < cap; ++i) {
        IDepositToken dt = IDepositToken(tokens[i]);
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        vm.startPrank(attacker);
        underlying.approve(address(dt), 1);
        dt.deposit(1, attacker);           // mint 1 wei share to attacker
        dt.transfer(victim, 1);            // adds token to victim's list
        vm.stopPrank();
    }

    // victim's list is now full; any new token type reverts
    IDepositToken newToken = IDepositToken(tokens[cap]);
    deal(address(newToken.underlying()), attacker, 1 ether);
    vm.startPrank(attacker);
    newToken.underlying().approve(address(newToken), 1 ether);
    vm.expectRevert(); // addToDepositTokensOfAccount: MaxTokensPerUser
    newToken.deposit(1 ether, victim);   // _mint -> addToDepositTokensOfAccount reverts
    vm.stopPrank();
}
```

Key invariant broken: a user must always be able to deposit supported collateral into their own account. The attacker breaks it for all not-yet-held token types, at dust cost, with no penalty — the same liveness-abuse class as the unpunished `lockQuote`/`unlockQuote` cycle.

Note on verification limits: `contracts/DepositToken.sol` was fully read (lines 180-526 confirm the lock check, list add/remove on balance transitions, and the zero-fee path). The exact revert behavior inside `Pool.addToDepositTokensOfAccount` at `MAX_TOKENS_PER_USER` was not re-read line-by-line this iteration — the cap and the `MappedEnumerableSet` usage are confirmed present in `contracts/Pool.sol`/`contracts/storage/PoolStorage.sol` by grep, and the PoC assumes the cap-revert, consistent with the mapped bug class for this codebase.
