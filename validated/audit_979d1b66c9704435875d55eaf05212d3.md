### Title
Pack-Objects Concurrency Limiter Uses a Client-Influenceable `RemoteIp` Key, Allowing Trivial Bypass of Resource-Exhaustion Protection - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
Gitaly's pack-objects concurrency limiter, whose sole purpose is to cap how many concurrent `git-pack-objects` invocations a single source may trigger, keys its limiter state on the caller's `RemoteIp` string rather than on any stable, server-verified identity. Because a git client fully controls the network path (and thus effectively the "remote IP" attribute observed per connection) by rotating source addresses, an attacker can trivially reset/multiply the limiter's per-key state, defeating the resource-exhaustion protection much like the reported "transfer to a fresh EOA" cooldown bypass.

### Finding Description
`packObjectsHook` derives the limiting key directly from the IP address carried on the request and only special-cases loopback addresses: [1](#0-0) 

That key is passed straight into `runPackObjectsLimited`, which acquires a per-key concurrency token from `packObjectsLimiter.Limit`: [2](#0-1) 

The underlying `ConcurrencyLimiter` maintains one independent semaphore per distinct key value (`limitsByKey`), lazily created and destroyed as callers with that key come and go: [3](#0-2) 

The config package documents the intended protection explicitly: "Pack-objects limiting is scoped by remote IPs. This limit means a single IP could only issue at most 200 distinct requests at the same time": [4](#0-3) 

Because the limiter's admission decision is keyed purely on a value that the requester's chosen network path determines (any client that can present multiple source addresses — e.g., rotating egress IPs, IPv6 /64 blocks, proxy pools, or many cheap cloud instances — gets a brand-new, independent 200-slot bucket each time), this is directly analogous to the reported bug class: a restriction meant to bound abuse per-actor is keyed on a value the actor can change at will, so the "cooldown"/limit resets for every new identity the actor manufactures, and the aggregate protection (same actor spawning unbounded concurrent `git-pack-objects` processes across many keys) provides no real ceiling.

### Impact Explanation
Each `git-pack-objects` invocation triggered by `PackObjectsHookWithSidechannel` performs actual object-graph negotiation/packing work (CPU, memory, disk I/O) against a repository. A caller that rotates its observed `RemoteIp` can spin up effectively unbounded concurrent pack-objects processes, undermining the very backpressure/resource-exhaustion protection this limiter exists to provide, as described in Gitaly's own backpressure design document: [5](#0-4) 

This can degrade or exhaust the Gitaly node's resources, affecting all repositories and users served by that node — a DoS of the pack-objects RPC handler.

### Likelihood Explanation
The pack-objects hook path is reached on ordinary, unprivileged fetch/clone traffic (any authenticated Git protocol client triggering `uploadpack.packObjectsHook`). Rotating source IP addresses is a well-known, low-cost technique (cloud instances, IPv6 allocation, proxy/VPN pools), so exploiting the coarse per-IP keying requires no special access beyond normal fetch capability.

### Recommendation
Do not rely solely on a self-reported/observed `RemoteIp` as the sole resource-protection key for an actor. Combine the IP-based key with a stable, harder-to-rotate dimension (e.g., authenticated user/token identity, `GlId`) when available, apply a global (not purely per-key) ceiling on concurrently running pack-objects processes per Gitaly node, and/or ensure the repo/RPC-level `[[concurrency]]` limiter (which is keyed by repository path rather than attacker-chosen data) is always enabled as the primary backstop rather than treating IP-based pack-objects limiting as sufficient protection on its own.

### Proof of Concept
1. An attacker with fetch access to a repository issues many concurrent `git fetch`/`git clone` requests that each cause Gitaly to invoke `PackObjectsHookWithSidechannel`.
2. For each batch of requests, the attacker originates traffic from a distinct source IP (e.g., using a rotating proxy pool or multiple cloud egress addresses).
3. Because `packObjectsHook` builds the limiting key from `req.GetRemoteIp()` and `ConcurrencyLimiter.getConcurrencyLimit` lazily creates an independent 200-slot semaphore per unique key, each new source IP gets its own fresh limit budget.
4. The attacker can thus run far more than the configured `max_per_repo`/pack-objects concurrency ceiling of concurrent `git-pack-objects` processes against the same repository/node simultaneously, exhausting Gitaly node resources, matching the pattern of bypassing a per-actor restriction by rotating the identity value the restriction is keyed on.

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.
