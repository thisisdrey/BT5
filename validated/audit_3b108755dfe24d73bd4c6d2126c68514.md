### Title
Rewards emitted while a rewarded DepositToken/DebtToken has zero totalSupply are permanently burned/locked in `RewardsDistributor` - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor` accrues emissions at a fixed `tokenSpeeds[token_]` per second, but `_calculateTokenIndex()` silently discards all rewards for any period in which `token_.totalSupply() == 0` — the index delta is forced to `0` while `_newTimestamp` is still advanced. Those rewards are never credited to any account, can never be claimed later, and cannot be recovered because `RewardsDistributor` has no sweep/rescue function for `rewardToken`. An unprivileged user can trigger this by being (or becoming) the last holder and fully withdrawing/repaying so the rewarded token's supply returns to zero while its speed remains nonzero.

### Finding Description
The analog of the WrappedVault bug (rewards attributed during a zero-supply period are lost) exists in `_calculateTokenIndex` at `contracts/RewardsDistributor.sol:197-212`:

```solidity
uint256 _totalSupply = token_.totalSupply();
uint256 _tokensAccrued = _deltaTimestamps * _speed;
uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
_newIndex = (_supplyState.index + _ratio).toUint224();
_newTimestamp = block.timestamp.toUint32();
```

When `totalSupply() == 0`, `_ratio` is `0` but the `TokenState.timestamp` is still stored as `block.timestamp` via `_updateTokenIndex()` (lines 271-282). The elapsed interval is therefore consumed permanently: the emitted `_tokensAccrued` for that window are added to no index and to no `tokensAccruedOf` entry. Unlike the Royco fix (owner can claim address(0) rewards), `RewardsDistributor` inherits only `Manageable`/`ReentrancyGuard*`/`RewardsDistributorStorageV2` — there is no `sweep`, and the `TokenHolder` recovery helper is not part of this contract, so the stranded `rewardToken` balance is unrecoverable.

Reachable path (all public, unprivileged):

1. Governor sets a nonzero speed (`updateTokenSpeed`) — normal deployed configuration; also, any attacker can call `updateBeforeMintOrBurn(token_, account_)` directly since it is permissionless (line 175).
2. Attacker deposits then fully withdraws via `Pool.deposit`/`DepositToken.withdraw` (or repays via `DebtToken.repay`), driving `depositToken.totalSupply()` (or `debtToken.totalSupply()`) back to `0` while `tokenSpeeds[token] > 0`. No minimum-liquidity/dead-share mint exists in `DepositToken`/`DebtToken`, so supply genuinely reaches zero.
3. Time passes; attacker (or anyone) calls `updateBeforeMintOrBurn` or `claimRewards`, advancing `timestamp` with `_ratio == 0`.
4. Rewards for the zero-supply window are permanently stranded — no account index can ever capture them.

Modifiers (`onlyIfDistributorExists`, `onlyIfTokenExists`, `nonReentrant`) and pause flags do not gate the index update path, and `claimRewards` is callable by anyone for any account list.

### Impact Explanation
Permanent freezing of unclaimed yield. Every second a rewarded token sits at zero totalSupply, `speed` reward tokens are emitted but credited to nobody and are unrecoverable — a direct loss of protocol reward funds, matching the report's "rewards locked in the contract" impact.

### Likelihood Explanation
Medium-low. It requires a rewarded token's supply to hit zero while speed is nonzero — this happens naturally at token registration (speed set before first deposit), after full withdrawal/repayment events, and is trivially inducible by the last depositor/borrower as an unprivileged action. However, the loss accrues only per-second of emissions during the zero-supply window and the attacker gains nothing directly (griefing of protocol rewards).

### Recommendation
Track un-attributed accrual: when `totalSupply() == 0`, carry the elapsed time forward instead of consuming it (e.g., only advance `timestamp` when `totalSupply > 0`, or accumulate `tokensAccrued` into a pending bucket distributed once supply returns). Alternatively, add a governor sweep of `rewardToken` capped at `balance - sum(pending accrued)` to reclaim stranded emissions.

### Proof of Concept
Hardhat sketch (mirroring `test/RewardDistributor.test.ts` setup with mocked `msdTOKEN1`):

```ts
// given: speed set, zero supply
await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, parseEther('1'))
msdTOKEN1.totalSupply.returns(0)
msdTOKEN1.balanceOf.returns(0)
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address) // t0

// when: 10s of zero supply pass
await increaseTimeOfNextBlock(10); await mine()
await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address) // advances timestamp, index unchanged
const { index, timestamp } = await rewardDistributor.tokenStates(msdTOKEN1.address)
expect(index).to.eq(INITIAL_INDEX) // no accrual recorded

// then: alice deposits, 10s pass — she only gets rewards for her holding period
msdTOKEN1.totalSupply.returns(parseEther('100'))
msdTOKEN1.balanceOf.returns(parseEther('100'))
await increaseTimeOfNextBlock(10); await mine()
const claimable = await rewardDistributor['claimable(address)'](alice.address)
expect(claimable).to.eq(parseEther('10')) // the first 10 VSP are gone forever
// distributor still holds the extra 10 VSP with no way to sweep them
```

Caveat: the PoC uses the repo's mocked-token test harness as shown in `test/RewardDistributor.test.ts`; a full-fork reproduction would use real `DepositToken`/`DebtToken` supply driven to zero via `withdraw`/`repay`. I could not verify within this session whether `DepositToken` mints a nonzero minimum-liquidity amount that would keep `totalSupply > 0`; the `grep` results show `_mint` sites in `DepositToken.sol`/`DebtToken.sol` but no `address(0)` mint was confirmed.
