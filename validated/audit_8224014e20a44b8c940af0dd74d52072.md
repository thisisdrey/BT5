### Title
DelegateAction nonce replay via same-block DeleteKey+AddKey resetting access key nonce below the consumed delegate nonce - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`add_regular_key` unconditionally re-seeds a recreated access key's nonce to `initial_nonce_value(block_height) = (block_height-1) * 1_000_000`, without checking or preserving the nonce of the key that occupied the same public key before deletion. Because `validate_delegate_action_key` in `runtime/runtime/src/actions.rs` reads the *current* on-chain access-key nonce at receipt-apply time rather than a value fixed at signing time, a `DeleteKey`+`AddKey(same pubkey)` sequence executed by the sender's own account can lower the stored nonce below a delegate nonce that was already consumed, letting a stale `SignedDelegateAction` be replayed.

### Finding Description
`validate_delegate_action_key` (`runtime/runtime/src/actions.rs:558-650`) accepts a `DelegateAction` if `delegate_action.nonce() > current_nonce` where `current_nonce` is `access_key.nonce` read from the trie *at the time the receipt executes* (`runtime/runtime/src/actions.rs:590-599,632`), and it enforces only an upper bound of `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` (`:641-650`). On success it persists the new nonce back onto the access key (`runtime/runtime/src/actions.rs:713-717`).

Separately, `add_regular_key` (`runtime/runtime/src/access_keys.rs:230-241`) — invoked by `action_add_key` (`:149-192`) whenever an `AddKey` action targets a plain (non-gas) key — always overwrites the new key's nonce with `initial_nonce_value(block_height) = (block_height - 1) * 1_000_000` (`:46-49`), irrespective of what nonce the previously-deleted key at that same public key had reached. `action_add_key` only rejects the add if a key currently exists (`AddKeyAlreadyExists`, `:157-164`); it does not consult any record of a prior, now-deleted key at the same public key.

The `AccessKey` documentation explicitly states the intended invariant that this code violates: "if the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again" (`docs/DataStructures/AccessKey.md:9-11`). The implementation does not do this for `AddKey`.

Exploit flow:
1. Sender's key `K` is used to sign a `DelegateAction` with `nonce = N` where `N` is close to (but below) `block_height * 1_000_000` — a value that is naturally in this range simply because `initial_nonce_value` already seeds fresh keys near `(H-1)*1_000_000`.
2. A relayer submits the `SignedDelegateAction` in a `Delegate` action; `validate_delegate_action_key` accepts it (`N > current_nonce`) and advances `access_key.nonce` to `N`.
3. In the same block, the sender submits a directly-signed transaction containing `[DeleteKeyAction{K}, AddKeyAction{K, ...}]` on its own account. `action_delete_key`/`delete_regular_key` removes the key (`access_keys.rs:136-147`), then `action_add_key`/`add_regular_key` re-adds it with `nonce = (H-1) * 1_000_000`, which is lower than `N`.
4. Any relayer holding the original `SignedDelegateAction` bytes (signature is unaffected by later key-state changes) resubmits it in a fresh outer transaction. `validate_delegate_action_key` re-reads `current_nonce = (H-1)*1_000_000 < N`, so the check `N > current_nonce` passes again, and the already-executed delegated actions (e.g. a transfer) execute a second time.

No existing check prevents this: the outer transaction's own nonce/signature verification is independent of the inner `delegate_action.nonce`; the delegate-nonce check is the only replay guard for meta-transactions, and it is defeated by the access-key reset.

### Impact Explanation
This breaks meta-transaction replay protection (NEP-366), enabling double execution of delegated actions — e.g., a double transfer, double `FunctionCall` with a deposit, or any other delegated action being re-applied — which is a direct double-spend/replay of user-authorized value movement. This matches the "double-spend/replay" bounty category.

### Likelihood Explanation
Preconditions: the sender must delete and re-add an access key using the identical public key within the same block height range as a previously-consumed delegate nonce, and a relayer must still hold the original signed bytes. Deleting and re-adding a key with the *same* public key is an unusual but valid and cheap operation (both actions are ordinary, unprivileged, self-signed actions costing normal gas/storage fees); no validator or privileged access is required. The relayer only needs to keep the original signed payload, which is trivial. The bug is deterministic given the described sequence, not probabilistic, and is repeatable each time the sender recreates the same public key at a favorable block height.

### Recommendation
When adding a regular (or gas) access key, check whether a key at the same public key existed previously (or otherwise persist a high-water-mark nonce record for that `(account_id, public_key)` pair) and seed the new nonce as `max(initial_nonce_value(block_height), previous_nonce_high_water_mark)`, consistent with the documented invariant in `docs/DataStructures/AccessKey.md`. Alternatively, disallow re-adding a previously-existing public key entirely, or bind delegate-nonce validation to a monotonically non-decreasing, never-reset counter independent of `AddKey`/`DeleteKey` cycles.

### Proof of Concept
Test-loop integration test (similar structure to `test-loop-tests/src/tests/gas_keys.rs::test_gas_key_delegate_v2_meta_transaction`):
1. Create `sender`, `relayer`, `receiver` accounts; add a full-access key `K` to `sender` at block height `H`.
2. Determine `access_key.nonce` for `K` (≈ `(H-1)*1_000_000`); craft `DelegateAction{sender_id: sender, receiver_id: receiver, actions: [Transfer(amount)], nonce: N, max_block_height: H+..., public_key: K}` with `N` close to `H*1_000_000 - 1` (still `< H*1_000_000`), sign with `K`.
3. Relayer submits `meta_tx_1 = SignedTransaction(relayer -> sender, [Action::Delegate(signed_delegate)])`; assert success and `receiver` balance increased by `amount`.
4. In the same block height `H`, `sender` submits `tx2 = SignedTransaction(sender -> sender, [DeleteKey(K), AddKey(K, FullAccess)])`; assert success and that `get_access_key(sender, K).nonce == (H-1)*1_000_000 < N`.
5. Relayer resubmits the identical `signed_delegate` bytes from step 2 in a new outer transaction `meta_tx_2 = SignedTransaction(relayer -> sender, [Action::Delegate(signed_delegate)])` with a fresh relayer nonce.
6. Assert `meta_tx_2` succeeds (not rejected with `DelegateActionInvalidNonce`) and `receiver` balance increased by `amount` a second time, proving double execution of the delegated transfer. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,
) -> Result<(), StorageError> {
    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {

            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;

        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}
