Audit Report

## Title
Snowbridge Outbound Queue V2 accepts an unvalidated, user-supplied `fee` per message, allowing cheap AssetHub-originated spam to clog the shared per-block Merkle commitment and stall Ethereum-bound bridge delivery - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`Message.fee` is a `u128` derived directly from a user-supplied `PayFees`/`WithdrawAsset` amount in the inbound XCM program, with no lower bound and no `ensure!(fee_amount > 0)` check, and `SendMessage::validate` in the V2 pallet checks only payload size, never fee adequacy. Every accepted message, regardless of fee, is counted against the same global `MaxMessagesPerBlock` cap and hashed into the same per-block `MessageLeaves` Merkle root, so a stream of zero/near-zero-fee messages from unprivileged AssetHub accounts can consume the fixed per-block slot budget and force legitimate messages to be postponed (`Event::MessagePostponed`), while relayers gain no economic incentive to service the batch.

## Finding Description
The V2 outbound message primitive carries an attacker/user-controlled `fee: u128` field with no invariant tying it to actual dispatch/Ethereum cost: [1](#0-0) 

This fee is extracted from the XCM `WithdrawAsset`/`PayFees` pair in `XcmConverter::extract_remote_fee`, which validates only that the fee asset is Ether and that the withdrawn amount is `>=` the `PayFees` amount — it never checks that the amount is non-zero or bears any relation to the real gas cost of the commands being exported: [2](#0-1) 

`EthereumBlobExporter::validate` (V2) gates only on network match, destination, `AssetHubParaId` (an entire parachain, not a specific privileged account), and the `AllowedAliasOrigin` filter (`EverythingBut<Equals<AssetHubLocation>>` in the Westend runtime config, i.e. essentially any non-AssetHub-root origin is permitted to alias): [3](#0-2) [4](#0-3) 

`Pallet::validate` in the outbound-queue-v2 pallet performs no fee validation whatsoever — only a payload-size check — unlike V1's `validate`, which computes the fee itself via `GasMeter::maximum_gas_used_at_most` and `PricingParameters`: [5](#0-4) [6](#0-5) 

`do_process_message` takes the caller-supplied `fee` verbatim into `PendingOrder`, and every accepted message — regardless of fee — is appended to the shared `MessageLeaves` and counted against the flat `MaxMessagesPerBlock` cap with no fee-based prioritization: [7](#0-6) [8](#0-7) 

At `on_finalize`, `commit()` folds every leaf accepted that block — spam and legitimate alike — into one Merkle root written to the header digest, which a relayer must prove/relay as a unit to collect any reward for legitimate messages, and `process_delivery_receipt` only pays a reward `if order.fee > 0`: [9](#0-8) [10](#0-9) 

In production configuration `MaxMessagesPerBlock` is set to a small fixed constant (`ConstU32<32>`), making the per-block slot budget easy to exhaust: [11](#0-10) 

The exploit path is: an unprivileged AssetHub account → constructs an XCM program with `WithdrawAsset`/`PayFees` for a negligible/zero Ether amount, an `AliasOrigin` accepted by `AllowedAliasOrigin`, a `DepositAsset`, and a command → this gets routed through `EthereumBlobExporter::validate`/`convert` → `Message{fee: ~0, ...}` → `OutboundQueue::validate` (size-only check, passes) → `deliver` enqueues it → `do_process_message` accepts it up to `MaxMessagesPerBlock`, appending its leaf into the shared `MessageLeaves` and creating a `PendingOrder{fee: ~0}` that no rational relayer will service. Existing guards — payload-size check, AssetHub-parachain-only origin check, `AllowedAliasOrigin` filter — do not address fee adequacy or fee-based prioritization at all, so they do not prevent this.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category. Because acceptance into the outbound-queue-v2 pipeline is gated only by size and origin-parachain checks, not fee adequacy, an attacker can consume the fixed `MaxMessagesPerBlock` slot budget every block with near-zero-fee messages, causing legitimate fee-paying messages to be `Yield`-ed/postponed (`Event::MessagePostponed`) and delaying Ethereum-bound transfers/commands. Even when legitimate messages are included, they are committed into the same Merkle root as spam, meaning a relayer wanting to collect real rewards must incur the marginal Ethereum gas cost of proving/relaying the spam leaves too, which discourages relaying and leaves legitimate `PendingOrders` unresolved.

## Likelihood Explanation
High. No privileged role, governance action, or off-chain trust assumption is required. Any unprivileged AssetHub account can submit ordinary XCM programs that route through `EthereumBlobExporter`/`XcmConverter` with a withdrawn fee amount of 0 or near-0, bounded only by the cost of ordinary AssetHub/BridgeHub transaction and XCM execution fees, which are cheap relative to Ethereum gas and relative to the value of clogging the shared per-block commitment. The `AllowedAliasOrigin` filter (`EverythingBut<Equals<AssetHubLocation>>`) does not meaningfully restrict which AssetHub-originating accounts can alias into this path.

## Recommendation
- Enforce a protocol-computed minimum fee in `Pallet::validate` (V2), analogous to V1's `GasMeter`/`PricingParameters`-derived fee, rejecting messages whose supplied fee is below the computed minimum cost of dispatch + expected Ethereum gas.
- Add an explicit `ensure!(fee_amount > 0, ...)` (or a protocol minimum) in `XcmConverter::extract_remote_fee`.
- Make `MaxMessagesPerBlock` admission fee-aware (e.g., reserve/prioritize slots by fee tier) so zero/low-fee messages cannot crowd out fee-paying ones.
- Consider capping the number of low-fee messages committable into a single Merkle root, or provide a mechanism for relayers to exclude worthless leaves from required proofs.

## Proof of Concept
1. From an unprivileged AssetHub account, construct an XCM program targeting the Ethereum V2 export path with `WithdrawAsset`/`PayFees` specifying a `0` (or negligible) Ether amount, a `AliasOrigin` accepted by `AllowedAliasOrigin`, a `DepositAsset`, and a `Transact`/asset command, followed by `SetTopic`.
2. Submit this repeatedly from ordinary AssetHub accounts (bounded only by normal AssetHub/BridgeHub tx fees) until `MessageLeaves` reaches `MaxMessagesPerBlock` (32 in the Westend BridgeHub config) for consecutive blocks, per the cap check in `do_process_message` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:349-358`).
3. Observe legitimate, properly-fee-paying messages submitted in the same window emit `Event::MessagePostponed` because the block's leaf slots are already consumed by zero-fee spam.
4. Observe spam messages nonetheless get committed into the shared `MessageLeaves` Merkle root each block via `commit()` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:322-339`), with `PendingOrder{fee: 0}` entries that no rational relayer resolves via `submit_delivery_receipt`, since `process_delivery_receipt` only pays a reward `if order.fee > 0` (`bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs:466-473`), while relayers seeking rewards for legitimate messages in the same root must still prove/relay the spam leaves.

		use XcmConverterError::*;
		let reserved_fee_assets = match_expression!(self.next()?, WithdrawAsset(fee), fee)
			.ok_or(WithdrawAssetExpected)?;
		ensure!(reserved_fee_assets.len() == 1, AssetResolutionFailed);
		let reserved_fee_asset =
			reserved_fee_assets.inner().first().cloned().ok_or(AssetResolutionFailed)?;
		let (reserved_fee_asset_id, reserved_fee_amount) = match reserved_fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		let fee_asset =
			match_expression!(self.next()?, PayFees { asset: fee }, fee).ok_or(InvalidFeeAsset)?;
		let (fee_asset_id, fee_amount) = match fee_asset {
			Asset { id: asset_id, fun: Fungible(amount) } => Ok((asset_id, *amount)),
			_ => Err(AssetResolutionFailed),
		}?;
		// Check the fee asset is Ether (XCM is evaluated in Ethereum context).
		ensure!(fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_asset_id.0 == Here.into(), InvalidFeeAsset);
		ensure!(reserved_fee_amount >= fee_amount, InvalidFeeAsset);
		Ok(fee_amount)
	}

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge
		);

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}
		.into();
		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };

		Ok((ticket, fee))
	}

			let count = MessageLeaves::<T>::decode_len().unwrap_or_default() as u64;

			T::OnNewCommitment::on_new_commitment(root);

			Self::deposit_event(Event::MessagesCommitted { root, count });
		}

			receipt: DeliveryReceipt,
		) -> DispatchResult

			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;
