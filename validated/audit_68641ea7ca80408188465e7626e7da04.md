## Analysis

Reducing the C4 report to its core broken invariant: **an actor can permissionlessly manipulate the denominator used to compute a proportional share (voting power / pool share), causing later, honest contributors to receive far less than their fair share while the manipulator's earlier stake captures a disproportionate claim on the pooled assets.** In the crowdfund case this was done by choosing the "price" after seeing contributions; in `pallet-asset-conversion` the equivalent lever is that LP-token minting for a *non-first* liquidity provider is computed directly from the pool account's *live token balance* (`reserve1`/`reserve2`), which anyone can inflate with a bare token transfer, not just through `add_liquidity`. ### Title
Permissionless reserve-donation dilutes proportional LP-share accounting in `pallet-asset-conversion::do_add_liquidity` — ([File: substrate/frame/asset-conversion/src/lib.rs])

### Summary
`do_add_liquidity` computes minted LP tokens for non-first depositors as `amount * total_supply / reserve`, where `reserve1`/`reserve2` are read as the pool account's actual, live asset balance [2](#0-1) . Because any account can transfer tokens directly into the deterministic pool account (a plain balance/asset transfer, not through the pallet), an attacker can inflate `reserve1`/`reserve2` without minting any LP tokens, which shrinks the LP-token amount computed for subsequent, honest liquidity providers relative to the true value they deposit — the same "become majority with a small underlying stake" mechanic as the crowdfund report, just expressed via pool-share accounting instead of crowdfund voting power.

### Finding Description
The pool's LP-token accounting trusts the pool account's raw balance as the reserve, per the prdoc note that reserve reads now use "full pool account balances" for pricing and liquidity math [3](#0-2) . In `do_add_liquidity`:
- For the *first* depositor (`total_supply.is_zero()`), the minted amount is `calc_lp_amount_for_zero_supply(&amount1, &amount2)`, computed from the depositor's own `amount1`/`amount2`, not from `reserve1`/`reserve2` [4](#0-3) .
- For *every subsequent* depositor, minted LP = `min(amount1 * total_supply / reserve1, amount2 * total_supply / reserve2)` [5](#0-4) .

`reserve1`/`reserve2` come from `Self::get_balance(&pool_account, ...)`, i.e., the pool account's actual on-chain asset balance — not an internally-tracked, mint/burn-gated accumulator. There is no invariant tying the pool account's balance strictly to `sum(add_liquidity amounts) - sum(remove_liquidity amounts)`. The pallet already acknowledges dust can land in the pool account outside of `add_liquidity`, as shown by the existing `cannot_block_pool_creation` regression test, which defends only against the narrower "pre-fund the not-yet-created pool account to block/manipulate the *first* deposit" scenario [6](#0-5) . That test proves the team is aware that arbitrary accounts can pre-load the pool account with tokens via ordinary transfers, but the defenses (using `amount_desired` directly when `total_supply.is_zero()`) only protect the *first* LP mint — the `mul_div`-based branch used for every later depositor still divides by the untrusted, donation-inflated `reserve1`/`reserve2` [7](#0-6) .

The only guard on the resulting LP amount is `ensure!(lp_token_amount > T::MintMinLiquidity::get(), Error::<T>::InsufficientLiquidityMinted)` [8](#0-7) , which only prevents a *complete* rounding-to-zero; it does nothing to stop a large, partial dilution where a victim's deposit is credited far fewer LP tokens than its true proportional value, while the tokens they transferred remain in the pool backing the attacker's earlier, cheaply-minted LP tokens.

### Impact Explanation
This breaks the "public underpriced work / conserve value and settle exactly once" invariant for AMM liquidity accounting: an unprivileged attacker can, with two ordinary calls (become an early LP, then a bare `transfer` into the pool account), cause a later liquidity provider's contribution to be credited proportionally less LP than its economic value implies. When the attacker subsequently calls `remove_liquidity`, `do_remove_liquidity` redeems `lp_redeem_amount * reserve / total_supply` [9](#0-8) , letting the attacker's small, cheaply-acquired LP-token balance claim a share of the now-larger pool that includes both the donated tokens and (proportionally) part of the victim's under-credited deposit — mirroring the crowdfund report's "majority rule leads to rugging" outcome, but as a value-extraction/dilution attack against fungible-asset pools used across Asset Hub for fee payment and swaps.

### Likelihood Explanation
High feasibility for an unprivileged actor: pool accounts are deterministic (`PoolLocator::address`), publicly computable before or after pool creation, and receiving direct asset transfers requires no special permission — this is demonstrated by the codebase's own `cannot_block_pool_creation` test, which performs exactly this kind of direct transfer into the pool account [10](#0-9) . The only missing piece to turn that into value extraction (rather than the already-mitigated "block pool creation" case) is timing the donation *after* the pool already has `total_supply > 0`, which the existing tests and code path do not defend against.

### Recommendation
Track pool reserves internally (mint/burn-tracked accounting decoupled from raw `T::Assets::balance`), or reconcile/cap the effective reserve used in `mul_div` to the sum of amounts actually deposited via `do_add_liquidity`/`do_remove_liquidity`, so that direct external transfers into the pool account cannot alter LP-token minting math for any depositor, not just the first one.

### Proof of Concept
1. Attacker calls `create_pool(asset1, asset2)`, then `add_liquidity` with modest amounts (e.g., `amount1 = amount2 = 1_000`), receiving `lp_token_amount` LP tokens (`total_supply` becomes `lp_token_amount + MintMinLiquidity`).
2. Attacker directly transfers a very large amount of `asset1` and `asset2` (via `pallet_assets::transfer`/`pallet_balances::transfer_allow_death`) straight to the deterministic pool account (no `add_liquidity` call, so `total_supply` is unchanged) — exactly as demonstrated for a different purpose in `cannot_block_pool_creation` [10](#0-9) .
3. Victim calls `add_liquidity` with a large, fair-value deposit. Because `reserve1`/`reserve2` now include the attacker's donation, `mul_div(amount, total_supply, reserve)` [11](#0-10)  yields far fewer LP tokens than the victim's deposit is worth relative to the pool's pre-donation state.
4. Attacker calls `remove_liquidity` with their original LP tokens; `do_remove_liquidity`'s `amount = lp_redeem_amount * reserve / total_supply` [12](#0-11)  now returns a share of the enlarged pool (donated tokens + part of victim's deposit), disproportionate to the attacker's small original LP mint — net value extraction from the victim, analogous to the crowdfund attacker capturing majority control from a minority contribution.

#[test]
fn cannot_block_pool_creation() {
	new_test_ext().execute_with(|| {
		// User 1 is the pool creator
		let user = 1;
		// User 2 is the attacker
		let attacker = 2;

		let ed = get_native_ed();
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), attacker, 10000 + ed));

		// The target pool the user wants to create is Native <=> WithId(2)
		let token_1 = NativeOrWithId::Native;
		let token_2 = NativeOrWithId::WithId(2);

		// Attacker computes the still non-existing pool account for the target pair
		let pool_account =
			<Test as Config>::PoolLocator::address(&(token_1.clone(), token_2.clone())).unwrap();
		// And transfers the ED to that pool account
		assert_ok!(Balances::transfer_allow_death(
			RuntimeOrigin::signed(attacker),
			pool_account,
			ed
		));
		// Then, the attacker creates 14 tokens and sends one of each to the pool account
		for i in 10..25 {
			create_tokens(attacker, vec![NativeOrWithId::WithId(i)]);
			assert_ok!(Assets::mint(RuntimeOrigin::signed(attacker), i, attacker, 1000));
			assert_ok!(Assets::transfer(RuntimeOrigin::signed(attacker), i, pool_account, 1));
		}

		// User can still create the pool
		create_tokens(user, vec![token_2.clone()]);
		assert_ok!(AssetConversion::create_pool(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone())
		));

		// User has to transfer one WithId(2) token to the pool account (otherwise add_liquidity
		// will fail with `AssetTwoDepositDidNotMeetMinimum`)
		assert_ok!(Balances::force_set_balance(RuntimeOrigin::root(), user, 10000 + ed));
		assert_ok!(Assets::mint(RuntimeOrigin::signed(user), 2, user, 10000));
		assert_ok!(Assets::transfer(RuntimeOrigin::signed(user), 2, pool_account, 1));

		// add_liquidity shouldn't fail because of the number of consumers
		assert_ok!(AssetConversion::add_liquidity(
			RuntimeOrigin::signed(user),
			Box::new(token_1.clone()),
			Box::new(token_2.clone()),
			10000,
			100,
			10000,
			10,
			user,
		));
	});
}
