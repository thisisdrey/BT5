### Title
Stale postponed self-call `ActionReceipt` survives `DeleteAccount` and resumes with forged self-authorization after account recreation - ([File: core/store/src/utils/mod.rs], [File: runtime/runtime/src/lib.rs], [File: runtime/runtime/src/actions.rs])

### Summary
`remove_account` only deletes `TrieKey::Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries; it never touches `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId`. An attacker who owns account `A` can plant a self-call `ActionReceipt` (predecessor_id == receiver_id == A) containing privileged actions (e.g. `AddKey`) that is postponed on an unresolved `input_data_id`, delete `A`, wait for `A` to be legitimately recreated by an unrelated party, and later deliver the missing data to resume the stale receipt. Because `check_actor_permissions` only compares the resumed receipt's own `predecessor_id` to `account_id` (both still literally `"A"`), the privileged action executes against the new owner's account as if self-authorized.

### Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes only:
- `TrieKey::Account`
- `TrieKey::ContractCode`
- `TrieKey::AccessKey` / `TrieKey::gas_key_nonce`
- `TrieKey::ContractData` [1](#0-0) 

It never removes `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceiptId` keyed on `receiver_id = A`. These are exactly the keys `process_action_receipt` writes when a receipt cannot execute immediately: [2](#0-1) 

An attacker's own contract deployed on `A` can generate a receipt with `receiver_id = A` and `predecessor_id = A` (a self-callback via `promise_then`/yield) whose `input_data_ids` includes a data id that has not yet arrived; that receipt is stored under `TrieKey::PostponedReceipt{receiver_id: A, receipt_id: R}` via `set_postponed_receipt` (`core/store/src/utils/mod.rs:120-127`) and linked via `PostponedReceiptId`/`PendingDataCount`.

The attacker then submits `DeleteAccountAction` on `A` (kept under `Account::MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000` bytes, checked at `runtime/runtime/src/actions.rs:348`, which only inspects `Account.storage_usage`, not the orphaned postponed-receipt bytes): [3](#0-2) 

`action_delete_account` calls `remove_account` and sets `*account = None`, but the postponed-receipt trie entries for `A` remain, since `remove_account` never enumerates or removes them.

Later, `A` is recreated (e.g. as a sub-account of a registrar/parent that reuses the account name for a new, unrelated owner). `check_account_existence` permits `CreateAccount` because the account no longer exists (`runtime/runtime/src/actions.rs:794-818`). The new owner installs their own keys/contract on the fresh `A`.

When the attacker eventually causes the missing `DataReceipt` (data_id matching the still-present `PostponedReceiptId` link) to be delivered, `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1398-1455`) finds the stale `PostponedReceiptId`, decrements `PendingDataCount` to zero, fetches the still-present stale `PostponedReceipt` via `get_postponed_receipt`, and executes it via `apply_action_receipt`: [4](#0-3) 

Inside `apply_action_receipt`, `actor_id` is initialized straight from the stored (stale) receipt's `predecessor_id`: [5](#0-4) 

`check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) authorizes `AddKey`/`DeployContract`/`Stake`/`DeleteKey` purely by comparing `actor_id != account_id` — both are the literal string `"A"` from the original self-call receipt, so the check passes trivially, even though `A` now denotes a completely different, freshly created account with different keys/owner: [6](#0-5) 

No code re-validates that the account instance backing `A` at resume time is the same one that existed when the receipt was postponed (no nonce/generation binding on `Account`). The `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check does not examine or bound postponed-receipt state, so this leftover data is entirely unaccounted for and undetected.

### Impact Explanation
This is an authorization escalation across accounts: an attacker can plant a privileged action (most severely `AddKey` with a full-access key, but also `Stake` or `DeployContract`) that executes against a future, unrelated owner's account as if self-authorized, purely because the account name is reused. A successful `AddKey` grants the attacker a full-access key on the new owner's account, enabling total compromise (fund theft, contract takeover). This matches the "authorization escalation across accounts" bounty category and can lead to theft of user funds.

### Likelihood Explanation
Preconditions:
1. Attacker needs a self-controlled contract on account `A` capable of creating a postponed self-call receipt (achievable via a cross-contract call/promise callback or the yield/resume mechanism, which gives explicit, attacker-controlled timing over data delivery).
2. Attacker must delete `A` while keeping its `Account.storage_usage` under 10,000 bytes — trivial for a lightly used account.
3. `A` must be recreated by an independent authority under the same account id — realistic for sub-account/registrar patterns where names are recycled (e.g. a permissionless subaccount registrar, marketplace, or any workflow that lets names be reclaimed after deletion).
4. Attacker must be able to eventually trigger delivery of the specific missing `DataReceipt`, which they fully control if they set up the yield/promise themselves.

All steps use only ordinary transactions and a self-deployed contract; no validator, node, or privileged access is required. The attack is repeatable against any account-name-reuse workflow.

### Recommendation
Make `remove_account` symmetric with `set_postponed_receipt`/`process_action_receipt`: when deleting an account, enumerate and remove all `TrieKey::PostponedReceipt`, `TrieKey::PendingDataCount`, and `TrieKey::PostponedReceiptId` entries keyed by that `account_id` (and any related `PromiseYield*`/`YieldIdToDataId`/`DataIdToYieldId` entries), refunding/erroring out any such pending receipts. Alternatively (or additionally), bind authorization at resume time to something more than string equality of account ids — e.g. record and check an account "generation"/creation nonce so a postponed receipt created against one incarnation of an account cannot be resumed against a later, distinct incarnation.

### Proof of Concept
Runtime integration test (in `runtime/runtime/src/tests/apply.rs` style, similar to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Create account `A` (e.g. sub-account of `parent`).
2. Apply a receipt from `A` to `A` with `input_data_ids = [d]` and `actions = [AddKey(attacker_key)]`; assert it is stored as `TrieKey::PostponedReceipt{receiver_id: A, receipt_id: R}` plus `PendingDataCount`/`PostponedReceiptId` (i.e., no immediate execution since `d` is unresolved).
3. Apply `DeleteAccountAction` on `A` from `A` (small storage usage) and assert success.
4. Assert (this should fail pre-fix, and is the core regression check) that iterating trie keys under `receiver_id = A` for `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` yields the empty set.
5. Have `parent` issue `CreateAccountAction` + `AddKey(new_owner_key)` for `A`, simulating a new, unrelated owner.
6. Deliver the `DataReceipt` with `data_id = d`.
7. Assert that either (a) the stale postponed receipt is not found/executed (expected post-fix), or (b) pre-fix, that `AddKey(attacker_key)` is added to the new account `A`, proving the attacker gained a full-access key on an account they no longer legitimately own — demonstrating the authorization escalation.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}

pub(crate) fn check_actor_permissions(
    action: &Action,
    account: &Option<Account>,
    actor_id: &AccountId,
    account_id: &AccountId,
) -> Result<(), ActionError> {
    match action {
        Action::DeployContract(_)
        | Action::Stake(_)
        | Action::AddKey(_)
        | Action::DeleteKey(_)
        | Action::DeployGlobalContract(_)
        | Action::UseGlobalContract(_)
        | Action::WithdrawFromGasKey(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
        }
        Action::DeleteAccount(_) => {
            if actor_id != account_id {
                return Err(ActionErrorKind::ActorNoPermission {
                    account_id: account_id.clone(),
                    actor_id: actor_id.clone(),
                }
                .into());
            }
            let account = account.as_ref().unwrap();
            if !account.locked().is_zero() {
                return Err(ActionErrorKind::DeleteAccountStaking {
                    account_id: account_id.clone(),
                }
                .into());
            }
        }
        Action::CreateAccount(_)
        | Action::FunctionCall(_)
        | Action::Transfer(_)
        | Action::TransferToGasKey(_) => (),
        Action::Delegate(_) | Action::DelegateV2(_) => (),
        Action::DeterministicStateInit(_) => (),
    };
    Ok(())
}
