### Title
Unbounded Array Allocation from Attacker-Controlled Length in TVM `ValidateMultiSign`/`BatchValidateSign` Precompiles - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` and `BatchValidateSign` precompiled contracts decode attacker-supplied ABI call data and use a length word taken directly from that data to size a `byte[][]` allocation via `extractBytesArray`/`extractSigArray`/`extractBytes32Array`. The bound check on this length (`MAX_SIZE`) is only applied when the `allowTvmSelfdestructRestriction` chain parameter is enabled; on the legacy/disabled path the same length is used unchecked to allocate memory, and `DataWord.intValueSafe()` returns `Integer.MAX_VALUE` for any value it can't represent as a positive int instead of rejecting it, so a crafted call can force a multi-gigabyte array allocation. This mirrors the CVE-2023-39274 root cause: an integer/length value taken from untrusted input is used to size an allocation without validating it fits available/plausible bounds before allocation.

### Finding Description
`extractBytesArray`, `extractSigArray`, and `extractBytes32Array` read a length directly from the caller-controlled `data`/`words` array and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

The length comes from `intValueSafe()`, which never throws — it caps overflowed/negative values at `Integer.MAX_VALUE` instead of rejecting them: [3](#0-2) 

In `ValidateMultiSign.execute()` and `BatchValidateSign.doExecute()`, a `sigArraySize`/`addrArraySize` bound check (`MAX_SIZE`) is only performed `if (VMConfig.allowTvmSelfdestructRestriction())`; when this feature switch is off, `extractSigArray`/`extractBytesArray`/`extractBytes32Array` are invoked directly on the unchecked length: [4](#0-3) [5](#0-4) 

Because these precompiles are reachable from any smart contract via a `STATICCALL`/`CALL` to the corresponding precompile address (part of TVM execution triggered by an ordinary broadcast transaction), any contract deployer/caller can invoke `ValidateMultiSign` or `BatchValidateSign` with a malformed length word that decodes to `Integer.MAX_VALUE`, triggering a huge `new byte[Integer.MAX_VALUE][]`/`new byte[len][]` allocation attempt.

### Impact Explanation
An attacker-controlled allocation size of up to `Integer.MAX_VALUE` array slots (or `Integer.MAX_VALUE` bytes for `extractBytes` via `bytesLen`) causes an `OutOfMemoryError` in the node process executing the transaction. Because this happens during normal transaction/contract execution (not just a constant call), a witness/node processing the block could crash or become unresponsive, meeting the "node crash or halt" impact bar. This is a Denial-of-Service against any full node or SR that processes the malicious transaction.

### Likelihood Explanation
Reachable by anonymous contract deployers/callers: no special privilege is needed, only enough energy to reach the precompile call and enough calldata to encode the crafted length word. Exploitability depends on the `allowTvmSelfdestructRestriction` chain parameter being disabled (its state should be verified on the live network); if it is enabled everywhere in production, the bound check mitigates this specific path, but the underlying `intValueSafe()` design and lack of a length sanity check before allocation remain a latent bug-class risk that a background review should confirm/fix regardless of current parameter state.

### Recommendation
Enforce an upper bound on the extracted array length in `extractBytesArray`, `extractSigArray`, and `extractBytes32Array` themselves (not only in the calling actuators, and not conditioned on `allowTvmSelfdestructRestriction`), rejecting inputs where `len` exceeds a small sane constant (e.g., `MAX_SIZE`) or exceeds what the remaining `data`/`words` length can support, before allocating any array.

### Proof of Concept
Construct calldata for `ValidateMultiSign`/`BatchValidateSign` where the ABI offset word points to a "length" slot whose 32-byte value is `0xFFFFFFFF...` (i.e., decodes via `intValueSafe()` to `Integer.MAX_VALUE`), and invoke the precompile via a contract `CALL`/`STATICCALL` on a node with `allowTvmSelfdestructRestriction` disabled.   /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()

  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
