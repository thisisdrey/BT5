This confirms the vulnerability. `remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes `TrieKey::Account`, `TrieKey::ContractCode`, `TrieKey::AccessKey`/`GasKeyNonce`, and `TrieKey::ContractData` entries. It never touches `TrieKey::PostponedReceiptId`, `TrieKey::PendingDataCount`, or `TrieKey::PostponedReceipt` — confirmed by `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` in `core/primitives/src/trie_key.rs:89-102`, where these three columns are listed as separate, account-scoped columns that `remove_account` does not iterate. `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls `remove_account` and then sets `*account = None`, but never issues `remove_postponed_receipt`/`state_update.remove(TrieKey::PostponedReceiptId{...})` for entries under its own name.

When the pending `DataReceipt` later arrives, `process_receipt` (`runtime/runtime/src/lib.rs:1367-1455`) looks up `PostponedReceiptId{receiver_id: A, data_id}`, fetches the stale `PostponedReceipt` (still present because it was never cleaned up), and calls `apply_action_receipt` with it. Inside `apply_action_receipt` (`runtime/runtime/src/lib.rs:853-855`), `account` is loaded fresh from the *current* trie state (`get_account(state_update, account_id)`, i.e., the newly recreated account), while `actor_id` is derived purely from the stale receipt's own `predecessor_id` field (`let mut actor_id = receipt.predecessor_id().clone();`). Since the stale receipt was crafted A→A, `actor_id == account_id == A` textually, so `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) passes for `AddKey` even though the account currently occupying `A` is not the one that authorized the receipt.

### Title
Postponed self-receipts surviving `DeleteAccount` let a planted `AddKey` action escalate privileges on a recreated account of the same name - (File: `runtime/runtime/src/actions.rs` / `runtime/runtime/src/lib.rs` / `core/store/src/utils/mod.rs`)

### Summary
`remove_account` does not clean up `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` trie entries scoped to the deleted account's name, so a self-addressed (`predecessor_id == receiver_id == A`) postponed `AddKey` receipt created before `DeleteAccount(A)` survives the deletion and later executes against whatever account currently occupies the name `A`. Because `check_actor_permissions` only compares `actor_id` (derived from the stale receipt's own `predecessor_id`) against `account_id` textually, it passes even though the account was recreated by an unrelated party in the interim.

### Finding Description
- Attacker controls account `A` and submits a receipt `A→A` with `AddKey(FullAccessKey)` gated on `input_data_ids = [X]`, where `X` is a data dependency the attacker controls the timing of (e.g., the return value of a self-initiated cross-contract callback). This is postponed and stored at `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}`, with `TrieKey::PostponedReceiptId{receiver_id: A, data_id: X}` and `TrieKey::PendingDataCount{receiver_id: A, receipt_id}` (`runtime/runtime/src/lib.rs:1609-1655`).
- Attacker then submits `DeleteAccount(A)` (self-delete, passes `check_actor_permissions` since `actor_id == account_id == A` and `locked == 0`). `action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) calls `remove_account` (`core/store/src/utils/mod.rs:505`), which removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows — but not the postponed-receipt-related columns.
- An unrelated party later recreates account `A` (e.g., re-issuing a recycled sub-account name, or via implicit-account/registrar flow depending on naming), populating a fresh `Account` at the same trie key.
- The attacker triggers the dependency `X` (since they control its timing — it was a callback tied to their own earlier promise). `process_receipt`'s `Data` branch (`runtime/runtime/src/lib.rs:1386-1455`) finds the still-present `PostponedReceiptId`/`PendingDataCount` entries, fetches the stale `PostponedReceipt`, and calls `apply_action_receipt` on it.
- `apply_action_receipt` loads the **current** account for `A` (`runtime/runtime/src/lib.rs:853`, the freshly recreated one) but sets `actor_id = receipt.predecessor_id().clone()` (`:855`) from the **stale** receipt, which is `A`. `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`) for `Action::AddKey` only checks `actor_id != account_id`; since both equal the string `A`, the check passes and `action_add_key` installs a `FullAccessKey` chosen by the attacker onto the new occupant's account.
- This breaks the "authorization exactness" invariant: a promise crafted while owning `A` should not carry privileges over a different, later occupant of the name `A`.

### Impact Explanation
Authorization escalation across accounts sharing a name: the attacker plants a `FullAccessKey` on an account they no longer legitimately own, then can spend its funds (e.g., via a subsequent `Transfer` signed with the planted key) — direct theft of user funds from the new legitimate owner of the recreated account. This matches the NEAR bounty category "authorization escalation across accounts or promises" / "theft of user funds."

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privileged access: own account `A`, create one postponed self-receipt with an input dependency the attacker resolves at will (e.g., a self-triggered callback or a controlled cross-shard timing), then self-delete, wait for/induce recreation of the same name, and resolve the dependency. Feasibility depends on there being a realistic account-recycling flow (e.g., sub-account marketplaces, name-reuse systems, or delayed re-creation by another party) where the same account name is re-issued to a different owner; this is the main external dependency but is a recognized pattern (name squatting/reuse) rather than requiring any protocol privilege. The bug itself (missing cleanup in `remove_account`) is deterministic and fully reproducible in a unit/integration test.

### Recommendation
When `action_delete_account` removes an account, also purge any postponed-receipt state scoped to that `account_id`: iterate and remove `TrieKey::PostponedReceiptId{receiver_id: account_id, ..}`, `TrieKey::PendingDataCount{receiver_id: account_id, ..}`, and `TrieKey::PostponedReceipt{receiver_id: account_id, ..}` (and likewise `PromiseYieldReceipt`/`PromiseYieldStatus`/`ReceivedData` for completeness) as part of `remove_account`, so that no receipt authorized under the old occupant of a name can execute against a different, later occupant. Alternatively/additionally, bind postponed receipts to an account "epoch"/creation nonce so a stale postponed receipt fails to match a recreated account even if its rows survive.

### Proof of Concept
Integration/apply-path test (in `runtime/runtime/src/tests/apply.rs` style, similar to `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`):
1. Set up account `A` (attacker) and a helper account `B`.
2. Submit an `A→A` action receipt with `actions = [AddKey(FullAccessKey(pk_planted))]` and `input_data_ids = [X]` (construct directly as a `Receipt` object, bypassing needing an actual VM promise, mirroring `PostponedReceiptId`/`PendingDataCount` setup as in `process_action_receipt`). Apply it; assert it becomes postponed (no `AddKey` effect yet, `get_access_key(A, pk_planted)` is `None`).
3. Submit `A→A` `DeleteAccount(A){beneficiary_id: B}`. Apply; assert account `A` no longer exists via `get_account`.
4. Submit `C→A` `CreateAccount` (unrelated party `C`, or an implicit/sub-account creation representing "an unrelated party"), giving `A` a fresh empty `Account`.
5. Submit the `Data` receipt for `data_id = X` to receiver `A`. Apply it.
6. Assert: if the postponed `AddKey` executes, `get_access_key(state_update, A, pk_planted)` returns `Some(..)` — demonstrating the planted key lands on the recreated account. The expected/fixed behavior is that this returns `None` (either because the postponed receipt was purged on delete, or because the recreated account rejects the stale receipt).
