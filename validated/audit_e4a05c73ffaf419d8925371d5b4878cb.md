Based on my investigation, I found a strong analog to the reported GMX division-before-multiplication precision loss bug, reachable through java-tron's `UnDelegateResourceProcessor`, which is called during `unDelegateResource` transactions (a broadcastable contract type any account can issue).

### Title
Division-before-multiplication precision loss in `UnDelegateResourceProcessor.execute()` transferUsage calculation - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/UnDelegateResourceProcessor.java)

### Summary
`UnDelegateResourceProcessor.execute()` computes bandwidth/energy usage to transfer back to a delegator by first computing a division ratio as a `double`, then multiplying it by a large integer usage value, exactly the "division before multiplication" pattern flagged in the GMX report, causing systematic precision loss/truncation in resource accounting during undelegation.

### Finding Description
When a resource delegation is revoked via `UnDelegateResourceContract` (reachable by any account that previously delegated bandwidth/energy), `UnDelegateResourceProcessor.execute()` computes: [1](#0-0) 

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * dynamicStore.getTotalNetLimit() / repo.getTotalNetWeight());
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
```

and the analogous ENERGY branch: [2](#0-1) 

Here `(double) unDelegateBalance / TRX_PRECISION` and `(double) unDelegateBalance / receiverCapsule.getAllFrozenBalanceForBandwidth()` are divisions performed first, producing a `double` with limited significand precision (53 bits), and the result is then multiplied by `dynamicStore.getTotalNetLimit()` / `receiverCapsule.getNetUsage()` — both potentially large `long` values (bandwidth/energy limits can be in the tens-of-billions range, as seen in `BandwidthProcessor.calculateGlobalNetLimit`/`EnergyProcessor.calculateGlobalEnergyLimit`, which use the identical `(long) (weight * ((double) totalLimit / totalWeight))` pattern): [3](#0-2) [4](#0-3) 

Unlike newer "hardened" code paths (`calculateGlobalNetLimitV2`, `calculateGlobalEnergyLimitV2`'s `calculateGlobalLimitV2`, and `RepositoryImpl.getUsage`/`calculateGlobalEnergyLimit`) which were explicitly refactored to use `BigInteger` multiply-then-divide to avoid this exact precision-loss class (as documented in comments and dedicated regression tests such as `CalculateGlobalLimitHardenTest.testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss`), the transferUsage computation inside `UnDelegateResourceProcessor` still relies on raw double division-then-multiplication with no BigInteger/hardened equivalent: [5](#0-4) [6](#0-5) 

### Impact Explanation
`transferUsage` determines how much bandwidth/energy usage is moved from the receiver back to the owner (or effectively discarded) upon undelegation. Because the ratio `unDelegateBalance / allFrozenBalance` is computed as a double before multiplying by `netUsage`/`energyUsage` (which can be large, near `totalLimit` scale), floating-point rounding in the division step compounds with the subsequent multiplication, causing `transferUsage` to be truncated inconsistently with the exact rational value. Since this value is subtracted directly from the receiver's `netUsage`/`energyUsage` state and affects `unDelegateMaxUsage` bound used via `min(...)`, an attacker can construct delegation/undelegation amounts (`unDelegateBalance`, prior usage, frozen balance) that maximize the rounding discrepancy, systematically under- or over crediting bandwidth/energy usage state. This does not directly move TRX but corrupts resource accounting state (a form of resource-metering integrity issue), which is bandwidth/energy accounting — explicitly in scope per the allowed categories.

### Likelihood Explanation
Any account can trigger `DelegateResource`/`UnDelegateResource` contracts freely and repeatedly with attacker-chosen `unDelegateBalance` values (bounded only by their frozen balances), so the vulnerable arithmetic path is trivially and repeatedly reachable without any privileged role. The precision-loss magnitude depends on the ratio of values but is deterministic and can be maximized by choosing amounts that fall in the tail of double-precision representable ranges relative to `allFrozenBalanceForBandwidth`/`allFrozenBalanceForEnergy` (which the caller controls by choosing how much to freeze/delegate before undelegating).

### Recommendation
Refactor `UnDelegateResourceProcessor.execute()`'s `unDelegateMaxUsage` and `transferUsage` computations to perform multiplication before division using `BigInteger` (or `Math.multiplyHigh`-safe 128-bit arithmetic), mirroring the hardened pattern already used in `RepositoryImpl.calculateGlobalEnergyLimit` / `ResourceProcessor.calculateGlobalLimitV2`, e.g.:
```java
long transferUsage = BigInteger.valueOf(receiverCapsule.getNetUsage())
    .multiply(BigInteger.valueOf(unDelegateBalance))
    .divide(BigInteger.valueOf(receiverCapsule.getAllFrozenBalanceForBandwidth()))
    .longValueExact();
```
guarded by the existing `allowHardenResourceCalculation`/`disableJavaLangMath` feature-flag pattern used elsewhere in the codebase to preserve legacy behavior for old blocks while fixing new ones.

### Proof of Concept
1. Freeze and delegate a large `allFrozenBalanceForBandwidth` to a receiver so `receiverCapsule.getNetUsage()` accrues a large usage value close to the account's bandwidth limit.
2. Call `UnDelegateResourceContract` with an `unDelegateBalance` chosen such that `unDelegateBalance / allFrozenBalanceForBandwidth` is a value that cannot be exactly represented in double precision (e.g., a ratio with a long repeating binary fraction).
3. Observe that `transferUsage = (long) (receiverCapsule.getNetUsage() * ((double) unDelegateBalance / allFrozenBalanceForBandwidth))` differs from the exact integer value `receiverCapsule.getNetUsage() * unDelegateBalance / allFrozenBalanceForBandwidth` computed via `BigInteger`, by comparing both computations for the same inputs (as done for `calculateGlobalEnergyLimit` in `CalculateGlobalLimitHardenTest.testGlobalEnergyLimitV2CorrectVsDoublePrecisionLoss`) — confirming the discrepancy is reproducible and attacker-controllable.

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
