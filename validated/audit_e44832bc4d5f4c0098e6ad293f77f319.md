Based on my investigation, I found a genuine analog to the panic-based DoS bug class, though with a caveat on current exploitability that I'll note explicitly.

### Title
Unrecovered Panic in Detached Push-Stats Goroutine Can Crash the Gitaly Process - (File: internal/gitaly/service/ssh/receive_pack.go)

### Summary
Gitaly protects gRPC handlers against panics via a global interceptor, `panichandler.UnaryPanicHandler`/`StreamPanicHandler`, which recovers panics on the handler's own goroutine and converts them to `Internal` gRPC errors. [1](#0-0) 
However, Go's `recover()` only protects the goroutine it executes in — it does not catch panics raised in separately-spawned child goroutines. The `sshReceivePack` handler spawns exactly such an unprotected, detached goroutine to capture push statistics from attacker-controlled input: [2](#0-1) 

### Finding Description
When `featureflag.ReceivePackStats` is enabled, `sshReceivePack` starts a bare `go func() { ... stats.RecordReceivePack(...) }()` that copies the raw client stdin (the git-receive-pack request: pkt-line command list + packfile header, entirely attacker-controlled) into a `PrefixCapture` buffer and then parses it with `stats.RecordReceivePack` → `ReceivePack.Parse`. [3](#0-2) 
This parsing walks pkt-line records, splits fields, and reads a 12-byte packfile header from attacker-supplied bytes. [4](#0-3) 

Gitaly's own engineering guidelines explicitly call out this exact class of risk and mandate the `dontpanic` helper for any goroutine whose panic-safety isn't obviously guaranteed: [5](#0-4) 
And elsewhere in the codebase this guidance is followed correctly — e.g. `streamcache.runCreate` explicitly recovers because "unlike RPC handlers, which are guarded by a panic catching middleware, an uncaught panic can crash the whole process": [6](#0-5) 
and `keyedRunnerCache.run` wraps user-provided work with `recover()` for the same reason: [7](#0-6) 

The goroutine in `sshReceivePack` breaks this pattern: it is spawned with a plain `go func()`, is not wrapped by `dontpanic.Go`/`dontpanic.Try`, and processes fully attacker-controlled bytes from an ordinary push over SSH.

### Impact Explanation
If any panic occurs anywhere in this call chain (`io.Copy`, `PrefixCapture.Write`, or `ReceivePack.Parse` and its helpers such as `text.ChompBytes`) — whether today or introduced by a future code change to this parsing logic, similar to how the `orchard` crate's coordinate-unwrap panic was introduced — the panic propagates on its own goroutine stack, is never caught by `panichandler`'s per-RPC `recover()`, and crashes the entire Gitaly process. This is a full denial of service impacting every repository and every in-flight RPC served by that node, not just the attacker's own request — directly analogous to the Zebra CVE where a single crafted field crashed the whole node.

### Likelihood Explanation
Low-to-Medium today: I reviewed `ReceivePack.Parse` and it appears defensively written (all slice indices are guarded by prior `len()`/`IndexByte` checks, and the 12-byte packfile header is read into a fixed-size array), so I did not find a currently triggerable panic with the code as written. I was also unable to fully inspect `internal/helper/text/chomp.go` in this pass to rule out edge cases there. The structural weakness — an unprotected, attacker-input-processing goroutine detached from the RPC's panic-recovery boundary — is nonetheless real and reachable by any ordinary user's `git push` over SSH when `ReceivePackStats` is enabled, and represents exactly the fragile pattern (crafted network input reaching un-guarded parsing code with process-wide crash consequences) that the referenced CVE class describes.

### Recommendation
Wrap the stats-capture goroutine with `dontpanic.Go` (or an equivalent `recover()` guard) consistent with the pattern already used in `streamcache.runCreate` and `keyedRunnerCache.run`, so that any panic while parsing attacker-controlled push data is caught, logged/reported to Sentry, and cannot take down the whole server. Apply the same review to the equivalent `smarthttp` receive-pack code path, which also calls into `stats.RecordReceivePack`.

### Proof of Concept
I could not construct or confirm a concrete byte sequence that triggers a panic in the current `ReceivePack.Parse` implementation — the bounds checks I reviewed appear correct. The finding is therefore a structural/architectural gap (unrecovered goroutine on an attacker-input parsing path) rather than a demonstrated crash with today's code, and should be treated accordingly.

func (r *ReceivePack) Parse(body io.Reader) error {
	capsParsed := false
	inPushCert := false
	sawFlush := false
	for {
		// Use pktline.Read rather than pktline.NewScanner because we should
		// strictly consume up to the end of the command-list in the Reference
		// Update Request.
		pkt, err := pktline.Read(body)
		if err != nil {
			if errors.Is(err, io.EOF) {
				break
			}
			return fmt.Errorf("reading command list: %w", err)
		}
		if pktline.IsFlush(pkt) {
			sawFlush = true
			break
		}

		r.Packets++
		line := text.ChompBytes(pktline.Data(pkt))

		// A push certificate (git push --signed) wraps the command list
		// together with header and PGP-signature lines. Skip the whole block
		// rather than miscount its contents as reference updates.
		if inPushCert {
			if strings.HasPrefix(line, "push-cert-end") {
				inPushCert = false
			}
			continue
		}
		if strings.HasPrefix(line, "push-cert") {
			inPushCert = true
			continue
		}

		// Shallow lines precede the command list.
		if strings.HasPrefix(line, "shallow ") {
			continue
		}

		// The first command line carries the capabilities after a NUL byte:
		//   <old-oid> SP <new-oid> SP <ref-name> NUL <capabilities>
		if !capsParsed {
			capsParsed = true
			if idx := strings.IndexByte(line, 0); idx >= 0 {
				r.Caps = strings.Fields(line[idx+1:])
				for _, cap := range r.Caps {
					if agent, ok := strings.CutPrefix(cap, "agent="); ok {
						r.UserAgent = agent
						break
					}
				}
				line = line[:idx]
			}
		}

		fields := strings.SplitN(line, " ", 3)
		if len(fields) != 3 {
			continue
		}
		oldOID, newOID := fields[0], fields[1]

		r.Commands++
		switch {
		case isZeroOID(oldOID):
			r.Creates++
		case isZeroOID(newOID):
			r.Deletes++
		default:
			r.Updates++
		}
	}

	if !sawFlush {
		// An empty stream happens when the RPC fails before git-receive-pack
		// reads its input.
		if r.Packets == 0 {
			return nil
		}
		return fmt.Errorf("incomplete command list: no flush after %d packets", r.Packets)
	}

	// The packfile header is "PACK" + 4-byte version + 4-byte object count,
	// all big-endian. EOF means no packfile follows the command list.
	var header [12]byte
	if _, err := io.ReadFull(body, header[:]); err != nil {
		if errors.Is(err, io.EOF) || errors.Is(err, io.ErrUnexpectedEOF) {
			return nil
		}
		return fmt.Errorf("reading packfile header: %w", err)
	}

	if string(header[0:4]) != "PACK" {
		return fmt.Errorf("unexpected packfile signature: %q", header[0:4])
	}
	r.Objects = binary.BigEndian.Uint32(header[8:12])

func RecordReceivePack(ctx context.Context, logger log.Logger, prefix []byte, objects prometheus.Histogram) {
	var rp ReceivePack
	if err := rp.Parse(bytes.NewReader(prefix)); err != nil {
		logger.WithError(err).DebugContext(ctx, "failed parsing receive-pack request")
		return
	}
	// No packets at all means the RPC failed before git read its input. A
	// signed push reports zero commands but still carries packets and an
	// object count, so don't guard on Commands here.
	if rp.Packets == 0 {
		return
	}

	rp.UpdateLogFields(ctx)
	rp.UpdateMetrics(objects)
