### Title
Unbounded array allocation from attacker-controlled length field in `extractBytes32Array` reachable via `BatchValidateSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `BatchValidateSign` precompiled contract (TVM address `0x66`) parses an address array from call data using `extractBytes32Array`, which reads an attacker-controlled length word and immediately allocates a byte array of that size — with no check that the length is consistent with the actual size of the `words` array — before the `MAX_SIZE` sanity check that exists for the equivalent signature array is applied. This mirrors the `read_tfra()` bug class in CVE-2017-14222: a size field taken from untrusted input drives a loop/allocation with no validation against the actual amount of backing data, letting a single crafted input trigger excessive memory allocation.

### Finding Description
`extractBytesArray` explicitly guards against an out-of-range `offset` before reading the length word: [1](#0-0) 

but the sibling helper `extractBytes32Array`, used to parse the address list, has no such guard and no cap on `len` before allocating: [2](#0-1) 

In `BatchValidateSign.doExecute`, the `MAX_SIZE` (16) bound is only enforced when `VMConfig.allowTvmSelfdestructRestriction()` is active, and even then only via a separate pre-check; `extractBytes32Array` itself is invoked unconditionally with no bound on the `len` it reads: [3](#0-2) 

`len` comes from `words[offset].intValueSafe()`, which is fully attacker-controlled through the calldata to the precompile (an address any contract can call directly with `staticcall`/`call`). A crafted call can set this word to a very large 32-bit value, causing `new byte[len][]` to attempt an allocation of `len * 8` bytes of object-reference storage well before any subsequent index bound is checked in the following loop (`words[offset + i + 1]`), which itself will throw `ArrayIndexOutOfBoundsException` for a short `words` array — but only after the huge array has already been requested from the heap.

### Impact Explanation
Because this precompile is reachable directly from any TVM contract call (no privileged caller required), an attacker can repeatedly issue transactions that force large/failed heap allocations inside the VM execution path. Although `execute()` wraps `doExecute()` in a catch-all `Throwable` handler, the memory pressure from repeated large-array allocation attempts (potential `OutOfMemoryError`) still occurs on every SR/full node during transaction processing — a resource-exhaustion condition analogous to the FFmpeg `read_tfra()` DoS: an untrusted "count" field with no corresponding data-length validation is used directly to size an allocation.

### Likelihood Explanation
The precompile is invoked purely by TVM `CALL`/`STATICCALL` opcodes with attacker-supplied calldata — no special permission, staking, or node role is required. The only friction is normal transaction fee/energy cost, but the allocation attempt happens synchronously during execution before any energy-based throttling of the loop body kicks in, making it trivially reachable by any contract deployer or caller.

### Recommendation
Add the same `offset > words.length - 1` bound check used in `extractBytesArray` to `extractBytes32Array`, and additionally validate that `len` is non-negative and consistent with the remaining `words.length - offset - 1` before allocating `new byte[len][]`, mirroring the existing `MAX_SIZE` check so it applies unconditionally (not only when `allowTvmSelfdestructRestriction()` is enabled).

### Proof of Concept
Deploy any contract and issue a `TriggerSmartContract` (or an internal `CALL`) targeting precompile address `0x...66` (`BatchValidateSign`) with calldata where:
- word[0] = arbitrary hash
- word[1] (sig array offset) points to a small, valid signature array
- word[2] (address array offset) points to a word whose value (the address-array length) is set to a very large integer, e.g. `0x7FFFFFFF`

This reaches `extractBytes32Array(words, addrOffset)` unconditionally before any `MAX_SIZE` bound is enforced on this code path, driving `new byte[len][]` with an attacker-chosen huge `len`.

    }
