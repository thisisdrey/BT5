### Title
Unbounded array allocation from attacker-controlled length in `ValidateMultiSign`/`BatchValidateSign` precompiles causes OutOfMemoryError DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytesArray` and `PrecompiledContracts.extractBytes32Array` read an array-length field directly from attacker-supplied smart-contract calldata and immediately allocate a Java array of that size (`new byte[len][]`), without any upper bound check on `len` before allocation. [1](#0-0) [2](#0-1) 

This is the same bug class as the Apache mod_md OCSP CVE: "Allocation of Resources Without Limits or Throttling" driven by attacker-controlled input.

### Finding Description
`ValidateMultiSign.execute` and `BatchValidateSign.doExecute` both call these helpers to parse the signature/address arrays embedded in the calldata passed to the `validatemultisign`/`batchvalidatesign` TVM precompiles. [3](#0-2) [4](#0-3) 

The size-limiting check (`sigArraySize > MAX_SIZE`) is only performed when the `allowTvmSelfdestructRestriction` chain parameter is active:
```
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  if (sigArraySize > MAX_SIZE) {
    return Pair.of(true, DATA_FALSE);
  }
}
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(...) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```
When the flag is false, `extractBytesArray`/`extractBytes32Array` are called unconditionally with no prior bound check, and inside them:
```
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
```
`intValueSafe()` returns up to `Integer.MAX_VALUE` (2^31-1) for any oversized/overflowed word, so a single crafted 32-byte length field lets the attacker force allocation of a reference array with up to ~2^31 elements (≈16 GB on a 64-bit JVM with compressed oops, ~17 GB uncompressed) in one call. [5](#0-4) 

In `BatchValidateSign.doExecute`, `extractBytes32Array` for the address list is even more exposed: the size check block only validates `addrArraySize` when `allowTvmSelfdestructRestriction` is on; when it is off, `extractBytes32Array` is invoked with zero prior validation at all. [6](#0-5) 

The `allowTvmSelfdestructRestriction` flag is a standard chain/proposal-gated feature flag (`VMConfig.Snapshot.allowTvmSelfdestructRestriction`), defaulting to `false` until explicitly activated by an on-chain committee proposal, and is loaded per-chain via `ConfigLoader`/`DynamicPropertiesStore`. [7](#0-6) [8](#0-7) 
Any java-tron network where this proposal has not (yet) been activated — new private chains, sidechains, or a mainnet/testnet prior to the hard fork enabling this parameter — has the vulnerable code path live and reachable by any account issuing a `CALL`/`TRIGGERSMARTCONTRACT` to the `validatemultisign` (`0x...66`) or `batchvalidatesign` precompile address with crafted calldata. `BatchValidateSign.execute` wraps `doExecute` in `catch (Throwable t)`, but `OutOfMemoryError` thrown mid-allocation can still destabilize the JVM heap for the whole node process before/while being caught, and repeated concurrent calls (it also submits tasks to a shared thread pool) amplify the effect. [9](#0-8) 

### Impact Explanation
A successful trigger causes the executing node to attempt allocation of a multi-gigabyte array in a single VM opcode execution. This can:
- Throw `OutOfMemoryError`, which propagates through JVM internals and can destabilize or crash the FullNode/SR process (node crash/halt), especially since `BatchValidateSign` also spins up `ExecutorService` tasks concurrently, multiplying heap pressure.
- Be repeated cheaply (the caller only pays the energy cost computed from `data.length`, not from the huge `len` value decoded from the crafted array-length word), making it an efficient DoS primitive against any node executing the transaction, including all SR/witness nodes reproducing block execution — a chain-halt risk if it hits consensus-critical nodes uniformly.

This qualifies as a valid, in-scope impact per the validation criteria: "node crash or halt."

### Likelihood Explanation
Likelihood is High on any network (chain ID/config) where `allowTvmSelfdestructRestriction` has not been activated, since exploitation requires only a single `TriggerSmartContract` transaction — no special privilege, no waiting for network conditions, and no coordination with other participants. Likelihood is Low/None on chains where the proposal is already active (the `extractSigArray`/bounded check path is used instead), so the severity is conditional on proposal-activation state, which could not be fully confirmed from the indexed code (no explicit "is this active today on mainnet" marker was found in the reachable files).

### Recommendation
Move the `MAX_SIZE` bound check ahead of any array allocation unconditionally, regardless of `allowTvmSelfdestructRestriction`, or add an intrinsic bound check inside `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves (e.g., reject `len` values above a small constant, or above what is arithmetically consistent with `data.length`) before calling `new byte[len][]`. This removes the feature-flag dependency and guarantees the mitigation is present on every deployment regardless of proposal-activation history.

### Proof of Concept
1. Craft calldata for `batchvalidatesign(bytes32,bytes[],address[])` (or `validatemultisign`) where the ABI head correctly points to an array-length word, but that length word (`words[offset]`) is set to a very large value, e.g. `0x000000000000000000000000000000000000000000000000000000FFFFFFF0` (decodes to a huge non-negative int via `intValueSafe()`).
2. Deploy or use an existing contract that performs a `CALL`/`STATICCALL` to the batchvalidatesign precompile address, forwarding this calldata (or invoke via `TriggerConstantContract`/`TriggerSmartContract` on a contract wrapper that forwards raw calldata).
3. Submit as a normal, unprivileged `TriggerSmartContractContract`. On any java-tron node/chain where `allowTvmSelfdestructRestriction` is not enabled, `extractBytesArray`/`extractBytes32Array` will execute `new byte[len][]` with the attacker-chosen `len`, triggering a large heap allocation and `OutOfMemoryError`, which can crash or destabilize the node process executing/validating the transaction.
