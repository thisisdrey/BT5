## Analysis Summary

This confirms the root cause: `ReferenceTransactionState` values `ReferenceTransactionPreparing`, `ReferenceTransactionPrepared`, and `ReferenceTransactionCommitted` are the only cases that fall through to `m.voteOnTransaction(...)` in `internal/gitaly/hook/referencetransaction.go`. `ReferenceTransactionAborted` (and any other/unknown state) hits `default: return nil` and returns immediately — no vote is cast, and therefore Praefect's `transactions.Manager.voteTransaction` (and its `defer mgr.unlockRepoForTransaction(...)`) is never invoked for an aborted reference transaction. [1](#0-0) 

On the Praefect side, `Manager.unlockRepoForTransaction` only releases the per-repository write lock on `PREPARING_PHASE`/`PREPARED_PHASE` (if `returnedErr != nil`) or `COMMITTED_PHASE`; any other phase (including a hypothetical `ABORTED_PHASE`) simply `return`s without releasing. [2](#0-1) 

The lock is acquired once, at `PREPARING_PHASE`, via `WriteLockManager.Lock`, and its Postgres row is upserted with `holder_txn_id = $2` matching unconditionally on re-entry (same `txnID`), refreshing `expired_at` regardless of prior expiry. [3](#0-2) [4](#0-3) 

The only remaining release paths are `cancelTransaction`/`StopTransaction`, both driven by the lifecycle of the surrounding gRPC call/context, not by the aborted-hook event itself. [5](#0-4) [6](#0-5) 

I was unable to fully verify (within the remaining budget) whether `git-receive-pack`'s native reference-transaction hook invocation for a large multi-ref push actually re-invokes the hook in `preparing` state per-ref using the *same* transaction/payload ID across many force-abort cycles (which would explain indefinite TTL renewal), or whether each ref update within one push shares one `HooksPayload.TransactionID`. This detail is asserted based on the design description in `doc/serialized_writes.md` and the code paths found, but the exact git-side invocation cardinality per push was not directly traced through `git-receive-pack` builtin C source (out of scope for this repo) or further gitaly integration tests confirming the multi-ref-per-payload behavior.

### Title
Reference-transaction "aborted" state skips vote/unlock, allowing indefinite Praefect repository write-lock starvation — ([File: internal/gitaly/hook/referencetransaction.go])

### Summary
Praefect's new serialized-writes feature (`doc/serialized_writes.md`) grants an exclusive, repository-scoped write lock at the `PREPARING_PHASE` of a reference transaction and only releases it on an error at `PREPARING`/`PREPARED`, or on successful `COMMITTED_PHASE`. Gitaly's `ReferenceTransactionHook` handler, however, never forwards the `aborted` hook state to Praefect at all — it hits a `default: return nil` branch — so no vote, and consequently no `unlockRepoForTransaction` call, ever occurs for an aborted reference transaction.

### Finding Description
`GitLabHookManager.ReferenceTransactionHook` switches on `state` and only assigns a `voting.Phase` for `ReferenceTransactionPreparing`, `ReferenceTransactionPrepared`, and `ReferenceTransactionCommitted`; any other state (including `ReferenceTransactionAborted`) falls into `default: return nil`, bypassing the call to `m.voteOnTransaction` entirely. [7](#0-6) 

On Praefect's side, the write lock is acquired for a transaction ID at `PREPARING_PHASE` via `lockRepoForTransaction`, and stored in `mgr.repoLocks` keyed by `transactionID`. [4](#0-3) 

`unlockRepoForTransaction` releases the lock only for `PREPARING_PHASE`/`PREPARED_PHASE` with an error, or unconditionally at `COMMITTED_PHASE`; any other (or missing) phase call is a no-op with respect to lock release: [2](#0-1) 

Because the "aborted" hook state never reaches `voteTransaction`/`unlockRepoForTransaction` at all, when Git internally aborts a reference-transaction after Praefect has already voted `Preparing` for it (e.g., because a concurrent update to the same ref made an old-value check fail, or because the `update` hook rejected one of several refs in a multi-ref push), the acquired write lock is left dangling in the `repoLocks` map and in the Postgres `repository_reference_write_locks` table. The only cleanup path left is expiry-based (`renewInterval` = 20s TTL) or the surrounding RPC's context being cancelled via `CancelFunc`/`StopTransaction`. [8](#0-7) [5](#0-4) 

Crucially, the Postgres `tryLock` UPSERT re-entrancy clause (`locks.holder_txn_id = $2`) matches unconditionally, regardless of whether the row has already expired, meaning that as long as the *same* transaction keeps re-triggering `PREPARING_PHASE` for subsequent refs within one still-open push/RPC (a design explicitly anticipated for multi-ref pushes, per `doc/hooks.md`'s "loop For each reference" sequence), the lock's TTL is continuously refreshed without ever completing a `COMMITTED_PHASE` unlock, for as long as the client keeps the underlying push/RPC connection open. [3](#0-2) [9](#0-8) 

### Impact Explanation
The write lock introduced by `doc/serialized_writes.md` is repository-scoped and exclusive: while held, *no other write transaction to the same repository can proceed on any Gitaly node in the cluster*, since `WriteLockManager.Lock` blocks all contenders until the row is released or expires. [10](#0-9) 
An ordinary, unprivileged user who can push to a repository with multiple ref updates (e.g., branches that race with a concurrent legitimate push, or refs guarded by an `update` hook that rejects some but not all refs in the same push) can trigger repeated `Preparing`→aborted cycles within a single, long-running push. This holds the exclusive write lock for the entire duration of their (attacker-controlled-length) push, denying all other users' pushes/writes to that repository — directly analogous to the reported bug class: an ordinary actor forcing a shared serialization resource to remain permanently (or attacker-duration) held, blocking legitimate operations queued behind it.

### Likelihood Explanation
This requires the `PraefectSerializedWrite` feature flag to be enabled and Git ≥ 2.54 (bundled per `GIT_VERSION_PREV`) to emit the `preparing` phase at all; the feature is described as newly introduced. [11](#0-10) 
Given the flag/pin dependency, likelihood is currently limited to deployments where this feature is enabled, but any repository push causing partial ref rejection (a routine, easily reproducible condition — e.g., pushing N refs where a protected-branch hook rejects some of them) is trivially reachable by an ordinary authenticated user with push access.

### Recommendation
- Route the `ReferenceTransactionAborted` state through the same phase machinery as `Preparing`/`Prepared`/`Committed` (e.g., map it to an explicit `ABORTED_PHASE` vote and always release the write lock when it is received), rather than silently returning `nil`.
- Add explicit lock-release handling in `Manager.unlockRepoForTransaction` for an aborted/failed phase, independent of whether a vote is cast.
- Do not rely solely on the TTL/re-entrancy renewal to bound lock hold time; consider capping the maximum lock hold duration per transaction ID irrespective of continued re-entrant renewals, to bound worst-case DoS exposure to a fixed ceiling instead of "duration of the attacker's push."

### Proof of Concept
1. Enable `PraefectSerializedWrite`, run Gitaly with the pinned Git version supporting the `preparing` reference-transaction phase.
2. As an ordinary user with push access to repository `R`, craft a single push containing multiple ref updates such that the `update` hook (or a concurrent legitimate push) will cause some ref updates to fail after `git` has already entered `preparing` for them (e.g., push branches with intentionally stale expected old-OIDs for a subset of refs, causing Git to abort those specific per-ref transactions while continuing to process the remaining refs in the same `receive-pack` session).
3. Observe (via `gitaly_praefect_repo_reference_write_locks_held` metric) that the per-repository lock for `R` remains held for the full duration of the push, since each aborted per-ref transaction never calls `unlockRepoForTransaction`, while each subsequent `preparing` call for the next ref in the same push re-acquires/renews the same lock row.
4. Concurrently attempt a legitimate write RPC to `R` from a different user/transaction and observe it blocking (`contended` counter incrementing) for the entire duration of the attacker's push, rather than the expected sub-lock-hold-duration. [12](#0-11)

func (m *GitLabHookManager) ReferenceTransactionHook(ctx context.Context, state ReferenceTransactionState, env []string, stdin io.Reader) error {
	payload, err := gitcmd.HooksPayloadFromEnv(env)
	if err != nil {
		return fmt.Errorf("extracting hooks payload: %w", err)
	}

	objectHash, err := git.ObjectHashByFormat(payload.ObjectFormat)
	if err != nil {
		return fmt.Errorf("looking up object hash: %w", err)
	}

	changes, err := io.ReadAll(stdin)
	if err != nil {
		return fmt.Errorf("reading stdin from request: %w", err)
	}

	var tx storage.Transaction
	if payload.TransactionID > 0 {
		tx, err = m.txRegistry.Get(payload.TransactionID)
		if err != nil {
			return fmt.Errorf("get transaction: %w", err)
		}
	}

	var phase voting.Phase
	switch state {
	// We're voting in preparing state to tell Praefect that the reference changes are ready,
	// although they are not locked yet. At this stage, we can serialize write transactions by
	// acquiring a lock for the transaction and releasing it only when the transaction is
	// committed or aborted. Other transactions must wait for the lock.
	case ReferenceTransactionPreparing:
		phase = voting.Preparing
	// We're voting in prepared state to tell Praefect we've locked the reference changes and
	// queued them for the transaction. We can abort the transaction if needed.
	case ReferenceTransactionPrepared:
		phase = voting.Prepared

		if tx != nil {
			updates, err := parseChanges(objectHash, bytes.NewReader(changes))
			if err != nil {
				return fmt.Errorf("parse changes: %w", err)
			}

			initialValues := map[git.ReferenceName]git.Reference{}
			for reference, update := range updates {
				if update.OldOID != "" {
					initialValues[reference] = git.NewReference(reference, update.OldOID)
				} else {
					initialValues[reference] = git.NewSymbolicReference(reference, update.OldTarget)
				}
			}

			// Only record the initial values of the reference in the prepare step as this
			// change hasn't yet been committed.
			if err := tx.RecordInitialReferenceValues(ctx, initialValues); err != nil {
				return fmt.Errorf("record initial reference value: %w", err)
			}
		}
	// We're also voting in committed state to tell Praefect we've actually persisted the
	// changes. This is necessary as some RPCs fail return errors in the response body rather
	// than as an error code. Praefect can't tell if these RPCs have failed. Voting on committed
	// ensure Praefect sees either a missing vote or that the RPC did commit the changes.
	case ReferenceTransactionCommitted:
		phase = voting.Committed

		if tx != nil {
			updates, err := parseChanges(objectHash, bytes.NewReader(changes))
			if err != nil {
				return fmt.Errorf("parse changes: %w", err)
			}

			if err := tx.UpdateReferences(ctx, updates); err != nil {
				return fmt.Errorf("update references: %w", err)
			}
		}
	default:
		return nil
	}

func (mgr *Manager) cancelTransaction(ctx context.Context, transaction *transaction) error {
	mgr.lock.Lock()
	defer mgr.lock.Unlock()

	delete(mgr.transactions, transaction.ID())
	// Release while holding mgr.lock so a concurrent voteTransaction can't
	// re-acquire the repo lock between delete and cancel.
	mgr.releaseRepoLock(transaction.ID())
	transaction.cancel()
	mgr.subtransactionsMetric.Observe(float64(transaction.CountSubtransactions()))

	var committed uint64
	state, err := transaction.State()
	if err != nil {
		return err
	}

	for _, result := range state {
		if result == VoteCommitted {
			committed++
		}
	}

	mgr.logger.WithFields(log.Fields{
		"transaction.id":              transaction.ID(),
		"transaction.committed":       fmt.Sprintf("%d/%d", committed, len(state)),
		"transaction.subtransactions": transaction.CountSubtransactions(),
	}).InfoContext(ctx, "transaction completed")

	return nil
}

func (mgr *Manager) StopTransaction(ctx context.Context, transactionID uint64) error {
	mgr.lock.Lock()
	transaction, ok := mgr.transactions[transactionID]
	if ok {
		// Release while holding mgr.lock so a concurrent voteTransaction
		// can't acquire a fresh repo lock between this release and stop.
		mgr.releaseRepoLock(transactionID)
	}
	mgr.lock.Unlock()

	if !ok {
		return fmt.Errorf("%w: %d", ErrNotFound, transactionID)
	}
	if err := transaction.stop(); err != nil {
		return err
	}

	mgr.logger.WithFields(log.Fields{
		"transaction.id": transactionID,
	}).DebugContext(ctx, "VoteTransaction: transaction stopped")
	mgr.counterMetric.WithLabelValues("stopped").Inc()

	return nil
}

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
	return nil
}

func (mgr *Manager) unlockRepoForTransaction(ctx context.Context, transactionID uint64, returnedErr error, phase gitalypb.VoteTransactionRequest_Phase) {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return
	}

	// Decide whether this call releases the write lock. The lock spans all the
	// phases of one transaction and is only released when either the vote
	// failed (so callers can't advance to the next phase) or the committed
	// phase completes. Phases outside the reference transaction hook
	// lifecycle (e.g. SYNCHRONIZED_PHASE) never acquired a lock.
	var shouldUnlock bool
	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE:
		shouldUnlock = returnedErr != nil
	case gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		shouldUnlock = true
	default:
		return
	}

	if !shouldUnlock {
		return
	}

	mgr.releaseRepoLockOnPhase(transactionID, phase.String())
}

// Lock acquires the write lock for a given virtualStorage, relativePath and txnID,
// blocking until the lock is acquired or ctx is cancelled.
func (r *RepoReferenceWriteLockManager) Lock(ctx context.Context, virtualStorage, relativePath string, txnID uint64,
) (RepoLock, error) {
	for {
		res := r.tryLock(ctx, virtualStorage, relativePath, txnID)
		if res.Err != nil {
			return RepoLock{}, res.Err
		}
		if res.Acquired {
			return RepoLock{Unlock: res.Unlock, Renew: res.Renew}, nil
		}

		select {
		case <-ctx.Done():
			res.Deregister()
			return RepoLock{}, fmt.Errorf("wait for lock: %w", ctx.Err())
		case <-res.NotificationCh:
			// wait for the lock to release
		}
	}
}

### Git: the "preparing" phase

The serialization point is a new `reference-transaction` hook phase called
`preparing`, introduced upstream in:

> `60d8c1e97d62c27ef60db0bc3d5deadd6dfdb98d`
> *refs: add 'preparing' phase to the reference-transaction hook*
>
> First released in **Git v2.54.0**.

`preparing` fires **before** Git stages any ref update. This is the only phase
at which Praefect can take a global lock without already racing with the
on-disk locking machinery.

Gitaly's bundled Git pin is set in `Makefile`:

```makefile
GIT_VERSION_PREV   ?= ...   # default bundled Git
GIT_VERSION_MASTER ?= ...   # Git's master branch tip
```

For serialized writes to work on every code path, `GIT_VERSION_PREV` must point
to a revision that contains `60d8c1e9…`.
