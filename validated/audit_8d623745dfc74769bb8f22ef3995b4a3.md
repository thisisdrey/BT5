### Title
Contract owner can front-run `UpdateSettingContract` to mutate `consumeUserResourcePercent` and shift energy cost onto callers mid-flight - ([File: actuator/src/main/java/org/tron/core/actuator/UpdateSettingContractActuator.java])

### Summary
`UpdateSettingContractActuator` lets a smart-contract's `origin_address` change `consume_user_resource_percent` at any time, with no cooldown, timelock, or restriction tied to in-flight calls. This percentage directly determines how the energy cost of a `TriggerSmartContract` call is split between the calling account and the contract's creator. Because the value can be changed unilaterally and instantly, and is read at execution time rather than fixed when a caller submits their transaction, a contract owner can watch the mempool for a caller's transaction (sized/`feeLimit`-calibrated against the current low percentage) and front-run it with an `UpdateSettingContract` transaction that raises the percentage to 100, shifting the entire energy cost onto the unsuspecting caller. This mirrors the Cally finding: an owner-controlled, freely mutable "fee rate" is applied retroactively against a counterparty who committed based on the old rate, letting the owner capture value (here, energy/TRX) that should have been borne by the owner.

### Finding Description
`consume_user_resource_percent` is stored per-contract and can be updated with no restriction beyond range-checking (`[0, 100]`) and an owner-of-contract check: [1](#0-0) 

There is no vault-style "fixed at creation" mechanism, no timelock, and no restriction on how often or when the owner may call this actuator — any owner can submit it before every block, including immediately after seeing a victim's `TriggerSmartContract` transaction broadcast to the network.

The percentage is read live, at the moment a `TriggerSmartContract` executes, to compute how much energy the caller vs. the contract creator must pay for: [2](#0-1) 

A caller building a transaction and setting `fee_limit`/expected resource cost has no way to pin the `consumeUserResourcePercent` value that was in effect when they signed their transaction; if the owner front-runs with a higher percent, the caller's transaction will consume more of the caller's own frozen energy/TRX than expected — potentially exhausting their `fee_limit` and being charged for energy actually spent, while the owner pays little or nothing. This is the direct analog to the Cally bug, where `feeRate` (protocol owner) is applied at exercise time to consume the option seller's expected proceeds, rather than being fixed when the vault/commitment was created.

### Impact Explanation
An attacker who is the deployer/owner of a smart contract can:
1. Set `consumeUserResourcePercent` low (e.g., 0) to lure users into calling the contract cheaply.
2. Monitor the mempool for a user's `TriggerSmartContract` call.
3. Front-run it with `UpdateSettingContract` raising the percent to 100.
4. The victim's transaction then executes with the new percentage, forcing the caller's own frozen energy/TRX to cover costs the caller did not budget for, resulting in unexpected loss of TRX/energy (a concrete "theft of funds" from the caller's perspective), or an outright failed/reverted call that still consumes the caller's resources.

This is reachable by any unprivileged contract deployer targeting any unprivileged caller via ordinary signed transactions (`UpdateSettingContract` and `TriggerSmartContract`), with no special network or consensus privileges required.

### Likelihood Explanation
Likelihood is realistic: any contract owner can attempt this at will, in the same fashion the reported Cally bug describes ("owner can wait ... then snipe"), by simply front-running the caller's `TriggerSmartContract` transaction with an `UpdateSettingContract` transaction in the same or an earlier block. No special permissions, staking, or consensus power are needed — only the contract's origin address, which is a normal, unprivileged account.

### Recommendation
Do not allow `consumeUserResourcePercent` to be applied retroactively to callers who already committed to a transaction under the previous value. Options include:
- Introducing a delay/timelock (e.g., effective only after N blocks) before an `UpdateSettingContract` change takes effect, analogous to fixing Cally's `feeRate` at vault-creation time.
- Snapshotting/pinning the percent value referenced by a caller's transaction (e.g., via a nonce or explicit percent parameter the caller can assert), so a change cannot be applied mid-flight to a transaction already broadcast.
- Emitting the percent change into a future maintenance cycle rather than the immediately following block, similar to how brokerage changes are applied only at the next cycle in `MaintenanceManager`/`DelegationStore`.

### Proof of Concept
1. Deploy a smart contract and call `UpdateSettingContract` (`/wallet/updatesetting`) setting `consume_user_resource_percent = 0`, so calls appear cheap to a would-be caller. [3](#0-2) 
2. Victim signs and broadcasts a `TriggerSmartContract` call to this contract with `fee_limit` sized for the 0% split.
3. Contract owner observes the pending transaction and broadcasts (with higher priority/fee or in the same block window) another `UpdateSettingContract` transaction raising `consume_user_resource_percent` to 100.
4. Because `VMActuator.getTotalEnergyLimitWithFixRatio` reads the percent live from `ContractCapsule` at execution time rather than at the time the caller's transaction was created, the victim's call executes under the new 100% split. [4](#0-3) 
5. The victim's account is charged the full energy cost (or the call fails after burning victim's resources up to `fee_limit`), while the contract owner pays nothing — analogous to the owner in the Cally report stealing the exercise cost by adjusting `feeRate` after the vault was already committed.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    ContractStore contractStore = chainBaseManager.getContractStore();
    try {
      UpdateSettingContract usContract = any.unpack(UpdateSettingContract.class);
      long newPercent = usContract.getConsumeUserResourcePercent();
      byte[] contractAddress = usContract.getContractAddress().toByteArray();
      ContractCapsule deployedContract = contractStore.get(contractAddress);

      contractStore.put(contractAddress, new ContractCapsule(
          deployedContract.getInstance().toBuilder().setConsumeUserResourcePercent(newPercent)
              .build()));
      RepositoryImpl.removeLruCache(contractAddress);

      ret.setStatus(fee, code.SUCESS);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
