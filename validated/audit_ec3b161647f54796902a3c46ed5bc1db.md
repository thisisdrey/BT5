### Title
Predictable, sequential repository-ID-derived storage paths allow squatting/collision of not-yet-created replica or pool directories - (File: `internal/gitaly/storage/repository_path.go`)

### Summary
Praefect's `PerRepositoryRouter.RouteRepositoryCreation` reserves a monotonically-increasing repository ID and then derives the on-disk replica/pool path from that ID with a deterministic, non-secret hash (`SHA256(id)` truncated to 2 bytes for the fan-out prefix, plus the ID itself in the leaf). Because the ID sequence is predictable (next ID ≈ current max + 1), any client able to create repositories can compute the exact path that will be assigned to the *next* repository/object pool before it is created — the same class of issue as the reported CREATE-nonce address-prediction bug, here manifesting as storage-path prediction instead of contract-address prediction.

### Finding Description
`storage.DeriveReplicaPath` / `storage.DerivePoolPath` compute the storage path purely as a function of the repository ID: [1](#0-0) 

The repository ID itself comes from `RepositoryStore.ReserveRepositoryID`, which is a simple incrementing sequence (Postgres `nextval`, per `repository_store.go`/`praefect-schema.sql`), and is consumed directly in `RouteRepositoryCreation`: [2](#0-1) 

Since the sequence is predictable and not permission-scoped to a caller, any ordinary user who can trigger repository/fork/object-pool creation (or simply observe how many repositories exist) can compute the disk path for the *next* ID(s) and pre-create a directory or file at that exact path on a storage node before Praefect/Gitaly actually assigns it. The `repoutil.Create` and `objectpool.Create` code paths do defend against this by `os.Stat`-checking the target path and failing with `AlreadyExists`/`FailedPrecondition` if something is already there: [3](#0-2) [4](#0-3) 

This is exactly analogous to the report's scenario: like the `CREATE`-derived address that depended solely on a predictable nonce, the repository's future storage location depends solely on a predictable, low-entropy counter. The test suite itself demonstrates the reachability of this prediction — a test explicitly precomputes `storage.DeriveReplicaPath(2)` for a not-yet-created repository and pre-seeds the target directory to force a collision: [5](#0-4) 

### Impact Explanation
The existing pre-stat check converts a successful squat into a hard failure (`AlreadyExists`/`FailedPrecondition`) rather than silent data corruption, so a full "steal the victim's funds"-equivalent outcome is not directly achievable purely through this path today. However, the predictability still enables:
- **Denial of service**: An attacker can pre-populate the predicted next replica/pool path(s) on a storage node, causing legitimate `CreateRepository`/`CreateFork`/`CreateObjectPool` RPCs for the *next* repository IDs to fail outright with `AlreadyExists`, blocking normal repo/fork/pool creation for other users.
- **Race-window abuse**: Between `ReserveRepositoryID` and the actual `os.Stat`/lock/create sequence, an attacker with direct filesystem access to a storage node's data directory (e.g. a compromised or malicious secondary, or anyone with node-local write access) could attempt to place content at the predicted path before the legitimate write completes, since the ID is known before the repository is actually materialized on disk.
- **Reduces the security value of path opacity**: Praefect's replica/pool paths were designed to be internal, but full predictability from a simple counter undermines the assumption that these paths are non-guessable, which the `IsPoolRepository`/hashed-path scheme partially relies on elsewhere.

### Likelihood Explanation
High reachability, low complexity: the repository-ID sequence is exposed indirectly through ordinary creation RPCs (`CreateRepository`, `CreateFork`, `CreateObjectPool`) available to any authorized Gitaly/Praefect client, and `DeriveReplicaPath`/`DerivePoolPath` are simple, publicly-computable functions requiring no secret. Predicting `id+1, id+2, …` from repeated repository creation calls is trivial for any user issuing routine create requests.

### Recommendation
- Do not derive storage paths purely from a predictable sequential ID. Include a per-repository random/opaque component (e.g., a UUID or a server-generated secret salt persisted alongside the repository ID) when computing `DeriveReplicaPath`/`DerivePoolPath`, similar to the recommended `create2` salt fix in the referenced report.
- Alternatively/additionally, harden the creation flow so that discovering a pre-existing directory at the predicted path is treated as a potential attack (audit/alert) rather than only returning `AlreadyExists`, and ensure the reservation-to-materialization window is minimized/locked at the storage layer to prevent any external filesystem race.

### Proof of Concept
1. As an authorized client, call `CreateRepository`/`CreateFork` repeatedly (or observe current repository count) to learn the current maximum repository ID `N`.
2. Compute `nextPath := storage.DeriveReplicaPath(N+1)` (or `DerivePoolPath` for the next pool) — this exactly matches the logic in `internal/gitaly/storage/repository_path.go` lines 61-68 and is demonstrated concretely by the test at `internal/gitaly/service/repository/create_fork_test.go` lines 365-369, which computes `storage.DeriveReplicaPath(2)` ahead of the RPC that will actually create repository ID 2.
3. With filesystem access to the target storage node (or via a subsequent create RPC racing the real one), create a directory/file at `nextPath` before the legitimate `CreateRepository`/`CreateFork`/`CreateObjectPool` call for that ID executes.
4. The legitimate creation RPC for repository ID `N+1` fails with `AlreadyExists`/`FailedPrecondition`, confirming the path was successfully predicted and squatted (as validated by the `TestCreateFork_targetExists` test cases at lines 303-382).

// DeriveReplicaPath derives a repository's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/repositories/ab/cd/<repository-id>.
func DeriveReplicaPath(repositoryID int64) string {
	return deriveDiskPath(praefectRepositoryPathPrefix, repositoryID)
}

// DerivePoolPath derives an object pools's disk storage path from its repository ID. The repository ID
// is hashed with SHA256 and the first four hex digits of the hash are used as the two subdirectories to
// ensure even distribution into subdirectories. The format is @cluster/pools/ab/cd/<repository-id>. The pools
// have a different directory prefix from other repositories so Gitaly can identify them in OptimizeRepository
// and avoid pruning them.
func DerivePoolPath(repositoryID int64) string {
	return deriveDiskPath(praefectPoolPathPrefix, repositoryID)
}

func deriveDiskPath(prefixDir string, repositoryID int64) string {
	hasher := sha256.New()
	// String representation of the ID is used to make it easier to derive the replica paths with
	// external tools. The error is ignored as the hash.Hash interface is documented to never return
	// an error.
	hasher.Write([]byte(strconv.FormatInt(repositoryID, 10)))
	hash := hasher.Sum(nil)
	return filepath.Join(prefixDir, fmt.Sprintf("%x/%x/%d", hash[0:1], hash[1:2], repositoryID))
}
