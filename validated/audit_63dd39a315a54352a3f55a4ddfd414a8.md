### Title
`Contract::native_withdraw`/`storage_deposit` permanently debit wNEAR `token_balances` with no re-credit if `near_withdraw` fails - (File: contracts/defuse/src/contract/intents/state.rs)

### Summary
`State::native_withdraw` and `State::storage_deposit` call `self.withdraw(...)` (which invokes `internal_sub_balance`) to debit the signer's wNEAR `token_balances` entry synchronously, in the same receipt, before scheduling `ext_wnear::near_withdraw` followed by a `.then(do_native_withdraw)`/`.then(do_storage_deposit)` callback. If `near_withdraw` fails, the callback panics via `require!(promise_result_checked_void(0).is_ok(), ...)` with no subsequent resolve/refund step, so the already-committed debit is never reversed.

### Finding Description
The broken binding: `token_balances[signer][wNEAR] before` should equal `token_balances[signer][wNEAR] after` + `NEAR delivered to receiver_id` + `NEAR re-credited on failure`. In the actual code, `token_balances[signer][wNEAR] before` = `token_balances[signer][wNEAR] after` + `NEAR delivered OR ZERO on failure`, i.e. on failure the debited amount is neither delivered nor re-credited.

Path: `native_withdraw` (`contracts/defuse/src/contract/intents/state.rs:212-240`) and `storage_deposit` (`state.rs:265-297`) call `self.withdraw(owner_id, [(wnear_token_id, amount)], Some("withdraw"), false)` which reaches `internal_sub_balance` (`state.rs:171-195`) and commits the debit in the *current* function-call receipt. This receipt returns `Ok(())` and is committed to state regardless of what happens later. The contract then schedules `ext_wnear::near_withdraw(...).then(Self::ext(...).do_native_withdraw(withdraw))` (or `do_storage_deposit`), a *separate future receipt*.

In `do_native_withdraw` (`contracts/defuse/src/contract/tokens/nep141/native.rs:11-19`) and `do_storage_deposit` (`contracts/defuse/src/contract/tokens/nep141/storage_deposit.rs:13-26`), the callback does:
```rust
require!(promise_result_checked_void(0).is_ok(), "near_withdraw failed");
```
If `near_withdraw` failed, this `require!` panics, aborting that receipt before scheduling the `Promise::new(receiver_id).transfer(...)` (native) or `storage_deposit` call. There is no further `.then(...)` resolver attached to this chain that inspects the outcome and re-credits the signer — unlike the parallel `ft_withdraw` flow.

By contrast, `internal_ft_withdraw`/`do_ft_withdraw`/`ft_resolve_withdraw` (`contracts/defuse/src/contract/tokens/nep141/withdraw.rs:53-195`) explicitly chains a final `.then(ft_resolve_withdraw(...))` after `do_ft_withdraw`, which checks the promise result and calls `self.deposit(sender_id, ..., REFUND_MEMO)` to refund the sender if the transfer (or the preceding `near_withdraw`) failed. `native_withdraw`, `storage_deposit`, and `auth_call`'s deposit-carrying path (`contracts/defuse/src/contract/intents/auth_call.rs`) lack this analogous resolver — they only `require!` and panic, with no re-credit path at all.

### Impact Explanation
If `ext_wnear::near_withdraw` fails for any reason after the Verifier has already debited the signer's `token_balances` wNEAR entry, the signer's funds are permanently destroyed: neither NEAR is transferred to `receiver_id`, nor is the wNEAR balance restored inside the Verifier's `Account::token_balances`. This is a direct violation of settlement invariants (value debited must equal value delivered or refunded) and matches the "user funds permanently frozen" Critical category. The blast radius covers any account performing `NativeWithdraw` or `StorageDeposit` intents whenever the downstream `near_withdraw` call to the wNEAR (`wrap.near`) contract fails.

### Likelihood Explanation
The code path itself is exact and unconditional — any failure of `near_withdraw` (regardless of cause) triggers the loss, and this is independent of attacker sophistication. The remaining uncertainty is what specifically makes `near_withdraw` fail on the real wNEAR/wrap.near contract for the Verifier's own account (e.g., its own storage/registration state on wNEAR, insufficient balance mismatch, or gas issues) — this trigger condition depends on the external wNEAR contract's implementation, which is outside this repository and was not verifiable from the indexed code. Regardless of the exact trigger, the missing re-credit logic in `do_native_withdraw`/`do_storage_deposit` (as contrasted with the refund logic present in `ft_resolve_withdraw`) is a real code-level asymmetry/bug that breaks the settlement invariant whenever `near_withdraw` does fail.

### Recommendation
Add a resolver step to the `native_withdraw` and `storage_deposit` promise chains analogous to `ft_resolve_withdraw`: chain a final `.then(...)` callback that inspects whether `near_withdraw` and the subsequent transfer/storage_deposit succeeded, and calls `self.deposit(owner_id, [(wnear_token_id, amount)], Some(REFUND_MEMO))` to re-credit the signer's `token_balances` if any step failed, mirroring the existing NEP-141 refund pattern.

### Proof of Concept
```
cargo test (near-workspaces sandbox), e.g. in contracts/defuse/tests:
1. Deploy Verifier + wNEAR (wrap.near) contracts.
2. Fund signer's Verifier token_balances[wNEAR] with N yoctoNEAR via normal deposit flow.
3. Force `near_withdraw` to fail for the Verifier's call, e.g. by manipulating wNEAR's registered storage balance for the Verifier account (or mocking a wNEAR contract that unconditionally panics on near_withdraw) so the promise returns PromiseResult::Failed.
4. Call execute_intents with a NativeWithdraw intent signed by signer for amount N.
5. Assert: after the promise chain resolves,
   - token_balances[signer][wNEAR] == 0 (debited, not restored) -- confirms the sub_balance is permanent.
   - No NEAR was transferred to receiver_id (balance unchanged / promise not created).
   - No `deposit`/`REFUND_MEMO` credit was ever issued to signer (no resolve callback exists in do_native_withdraw chain, unlike ft_resolve_withdraw).
This demonstrates debited value (N) != delivered value (0) + refunded value (0), breaking settlement.
```
