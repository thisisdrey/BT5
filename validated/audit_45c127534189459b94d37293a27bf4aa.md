### Title
Relayer reward paid regardless of `DeliveryReceipt.success`, allowing payout for failed message execution - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`process_delivery_receipt`, the entry point that settles a queued outbound message and pays the relayer fee, decodes a `DeliveryReceipt` that carries a `success: bool` field reporting whether the message actually executed successfully on Ethereum, but never inspects it. The function unconditionally pays the reward and removes the `PendingOrder` as soon as a message with a matching nonce was ever queued, regardless of whether the corresponding Ethereum-side dispatch actually succeeded.

### Finding Description
The Ethereum gateway emits an `InboundMessageDispatched(nonce, topic, success, reward_address)` event for every message it processes, whether the dispatched call succeeded or reverted. `DeliveryReceipt` decodes this event and preserves the `success` flag: [1](#0-0) 

`process_delivery_receipt` in the outbound-queue-v2 pallet consumes this receipt to settle the pending order and pay the relayer fee: [2](#0-1) 

The function checks `gateway` (origin binding) and looks up the `PendingOrder` by `nonce` (replay/duplicate binding), but at no point does it check `receipt.success`. As a result, a legitimately-relayed proof for a message whose Ethereum-side execution failed (`success == false`) is treated identically to a successful delivery: the `order.fee` is paid out via `T::RewardPayment::register_reward` and the `PendingOrder` is removed from storage, closing the settlement window forever for that nonce.

This mirrors the Notional bug pattern: a state flag that is supposed to gate correct behavior (`pr.supplyFactor` in Notional, `receipt.success` here) exists in the data model but the consuming code path fails to branch on it, causing the payout/settlement invariant "advance state only after execution succeeds" to be silently violated. The doc comment for the pallet even states the intended design (`Fetch the pending order by nonce of the message, pay reward with fee attached in the order`) without mentioning any conditional on success, confirming the check was designed to happen based on delivery outcome but was omitted: [3](#0-2) 

The existing halted-state guard (`VerificationError::Halted`) added in a recent PR only blocks proof verification while the bridge is halted; it does nothing to gate reward payment based on the on-chain dispatch outcome once verification succeeds: [4](#0-3) 

### Impact Explanation
This breaks the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically." A relayer who submits a proof for a genuinely failed cross-chain execution (e.g., a message that reverted due to gas exhaustion, an application-level revert, or any other Ethereum-side failure not caused by the relayer) is unconditionally rewarded, and the `PendingOrder` is deleted so it can never be resettled correctly. This is a direct fund-payout/accounting bug: relayer fees are paid for work whose outcome does not match what the fee was meant to compensate, and the impacted nonce's pending order is irrecoverably consumed. There is no privileged actor, malicious relayer, or governance action required — any submitter of a valid Merkle/beacon proof for a real (but failed) Ethereum event triggers the incorrect payout.

### Likelihood Explanation
Likelihood is high in practice: message execution failures on the Ethereum side are a normal occurrence (insufficient destination gas, reverted application logic, etc.), not an attack precondition. Any relayer — not a "malicious" one, just one relaying a real emitted event — can call the permissionless `submit_delivery_receipt` extrinsic (which internally calls `process_delivery_receipt`) with a legitimately verified receipt whose `success` is `false` and still collect the reward, since no code path distinguishes the two outcomes.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before paying the reward: only call `T::RewardPayment::register_reward` when `receipt.success == true`. For `success == false`, define explicit failure-handling semantics (e.g., no reward, and/or a distinct event/error path, and a decision on whether the `PendingOrder` should be retried, refunded, or removed) instead of silently paying out and clearing the order in both cases.

### Proof of Concept
1. A message with `nonce = N` and `fee = F > 0` is queued via `process_message`, inserting `PendingOrders[N] = { nonce: N, fee: F, block_number }` — see the insertion logic: [5](#0-4) 
2. On Ethereum, the Gateway attempts to dispatch the message but it reverts/fails; the Gateway still emits `InboundMessageDispatched(nonce=N, topic, success=false, reward_address)`.
3. A relayer submits `submit_delivery_receipt` with a valid Merkle/state proof for this real event log. Verification succeeds (bridge not halted, gateway address matches, nonce exists in `PendingOrders`).
4. `process_delivery_receipt` decodes `receipt.success = false` but ignores it, executes:
```rust
if order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
<PendingOrders<T>>::remove(nonce);
```
paying `F` to `reward_account` and permanently removing `PendingOrders[N]`, even though the message dispatch failed on Ethereum.

Note: I could not find any test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` that exercises the `success == false` branch of `process_delivery_receipt` (the existing tests only cover halted-verifier and invalid-nonce cases), which is consistent with this path being unguarded and untested.

			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
