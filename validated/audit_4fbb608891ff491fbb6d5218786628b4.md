### Title
StackerDB unsolicited-push handler advertises a chunk version as stored before the write is actually committed, allowing served inventory to diverge from committed state - (File: `stackslib/src/net/stackerdb/mod.rs`)

### Summary
`PeerNetwork::handle_unsolicited_StackerDBPushChunk` optimistically patches the `StackerDBChunkInv` reply it is about to send to the pushing peer to reflect the *pushed* chunk's `slot_version`, before that chunk has actually been committed to the StackerDB. The real write happens later and asynchronously, via the relayer path (`Relayer::process_stacker_db_chunks` calling `StackerDBTx::try_replace_chunk`). A concurrent write to the same slot that lands in between can make the deferred write fail (`StaleChunk`), silently dropping the chunk, while the node has already told its peer that the new version is present.

### Finding Description
`handle_unsolicited_StackerDBPushChunk` builds a reply inventory from current on-disk state via `make_StackerDBChunksInv_or_Nack`, then validates the incoming pushed chunk with `validate_received_chunk` against that snapshot [1](#0-0) . If validation succeeds, it unconditionally patches the in-memory reply's `slot_versions[slot_id]` to the pushed chunk's version: [2](#0-1) 

This patched `StackerDBChunkInv` is then either sent immediately back to the peer (`send_reply == true`) or the message is forwarded to the relayer for actual processing (`send_reply == false`, returns `(false, true)`) — but in both cases the *actual* durable write does not happen inside this function. The real, transactional write occurs later in `Relayer::process_stacker_db_chunks`, which calls `StackerDBTx::try_replace_chunk` and can fail with `net_error::StaleChunk` if the on-disk version has since advanced (e.g. from a concurrent legitimate write via HTTP `POST /v2/stackerdb/.../chunks`, another push, or the sync state machine), in which case the chunk is dropped and never stored: [3](#0-2) [4](#0-3) 

Because the inventory patch and the durable insert are not atomic with each other, a race window exists: the reply inventory can report a `slot_version` that is never actually written, breaking the invariant that a node's advertised StackerDB inventory equals its committed StackerDB state.

### Impact Explanation
Other nodes' StackerDB sync scheduling is rarest-first/newest-first and is driven by peers' advertised inventories (`StackerDBChunkInv`) [5](#0-4) . If a node advertises a version it does not actually hold, peers may treat this replica as already synced for that slot and skip re-pushing/backfilling it, causing genuine, permanent under-replication of that chunk on the affected node while it (and its peers) believe replication succeeded. This matches the "serving non-canonical state as canonical" / "false inventory" class of High-severity impact: the advertised state diverges from the durably committed state without any error surfaced to the network.

### Likelihood Explanation
No secret key or admin role is required by the attacker: StackerDB chunks are gossip data that are broadcast to the whole network once written, so an attacker only needs to observe an already validly-signed chunk (they do not need to forge a signature) and push it to a victim node while racing it against a concurrent legitimate write to the same slot (e.g. from the real owner or from the node's own sync loop). The race window is the gap between the synchronous inventory-patch/reply in `handle_unsolicited_StackerDBPushChunk` and the asynchronous commit in `process_stacker_db_chunks`, which is not bounded or synchronized, making the race practically triggerable, though it requires some timing luck to hit exactly the right window.

### Recommendation
Do not patch/send the optimistic `StackerDBChunkInv` reply until after the chunk has been durably committed (or make the validation-and-patch step atomic with the actual DB write), or re-read and re-verify on-disk slot versions immediately before sending any `StackerDBChunkInv` reply so that advertised state can never outrun committed state.

### Proof of Concept
1. Attacker connects to victim node B as a normal p2p peer and obtains any validly-signed StackerDB chunk C (slot S, version V) — e.g., by observing prior legitimate gossip; no private key needed.
2. Concurrently, a legitimate write to slot S with version V+1 is committed on B via `try_replace_chunk` (any signer/version bump for the same slot from another source: another push, HTTP POST, or sync).
3. Attacker sends chunk C (version V) as an unsolicited `StackerDBPushChunk` to B. `handle_unsolicited_StackerDBPushChunk` builds its reply inventory (possibly still reflecting the pre-bump version), runs `validate_received_chunk`, and — if it validates against the snapshot taken at that moment — patches the reply to advertise version V and returns/forwards for storage.
4. When `process_stacker_db_chunks` later attempts `try_replace_chunk` for chunk C, it now sees the already-committed V+1 on disk and rejects C with `StaleChunk`, dropping it silently [6](#0-5) .
5. B has already advertised (or is about to advertise) version V for slot S in its `StackerDBChunkInv`, even though the actual highest committed data for that push attempt was never durably applied via this path, demonstrating the served/committed divergence.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
