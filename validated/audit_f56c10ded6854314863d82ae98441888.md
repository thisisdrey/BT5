### Title
Unchecked `frozenDuration` multiplication overflow in `FreezeBalanceActuator`/`FreezeBalanceProcessor` can corrupt frozen-balance expire time - (File: `actuator/src/main/java/org/tron/core/actuator/FreezeBalanceActuator.java`)

### Summary
`FreezeBalanceContract.frozen_duration` is a user-controlled `int64` field that is multiplied by `FROZEN_PERIOD` to compute the resource `expireTime`, with no overflow guard, mirroring the reported "duration overflow" bug class (unchecked cast/multiplication of an attacker-supplied duration into a fixed-size expire-time field).

### Finding Description
`FreezeBalanceContract` carries an unconstrained `int64 frozen_duration` field [1](#0-0) , set directly by whoever signs the transaction. In `FreezeBalanceActuator.execute`, this value is multiplied by `FROZEN_PERIOD` and added to the current timestamp to compute the resource lock `expireTime`, using ordinary Java `long` arithmetic that silently wraps on overflow (no `Math.addExact`/`multiplyExact`): [2](#0-1) 

The only bound check on `frozenDuration` in `validate()` is gated behind `CommonParameter.getInstance().getCheckFrozenTime() == 1`, a flag explicitly commented as `//for test`: [3](#0-2) 

Because this flag is a test-only toggle (not present/enabled in `reference.conf` for production nodes), the `minFrozenTime`/`maxFrozenTime` bound is effectively unenforced on a default mainnet node, so `frozenDuration` reaches the unchecked multiplication with essentially attacker-chosen magnitude.

The identical unguarded pattern exists in the TVM native-contract path used by the `freezeBalance`-family opcode, reachable from any deployed smart contract: [4](#0-3) 

By contrast, the `AssetIssueActuator` code base already recognizes and defends against exactly this overflow class for `FrozenSupply.expireTime`, using `StrictMathWrapper.addExact` and rejecting the transaction on overflow: [5](#0-4) 

No equivalent protection exists for `FreezeBalanceActuator`/`FreezeBalanceProcessor`, confirming the gap is a missed defense rather than an intentional design choice.

### Impact Explanation
A crafted `frozenDuration` large enough to overflow the `long` multiplication (or the subsequent `now + duration` addition) can wrap around to a small or negative value, producing an `expireTime` that is already in the past (or otherwise incorrect) relative to `now`. Since `expireTime` gates when a user's frozen TRX resource (bandwidth/energy/TRON_POWER) becomes eligible for unfreezing, an attacker could:
- Store a corrupted, unintended expire time in `AccountCapsule` (`setFrozenForBandwidth`/`setFrozenForEnergy`/`setFrozenForTronPower`), permanently or unpredictably desynchronizing on-chain resource/vote accounting from the intended lock period, effectively bypassing the freeze duration invariant used for stake-based resource allocation and governance (TRON_POWER voting), which can be leveraged to prematurely reclaim TRX or manipulate resource weight totals.

### Likelihood Explanation
`FreezeBalanceContract` is broadcastable by any account holding TRX (no special privilege required), and the vulnerable arithmetic executes unconditionally on `execute()` for every processed freeze transaction; the sole mitigating check (`checkFrozenTime`) is a test-only flag not enabled by default in production configuration, so the overflow path is directly reachable in the field via a single signed transaction. The `FreezeBalanceProcessor` variant is equally reachable via a TVM contract call.

### Recommendation
Add explicit overflow-safe arithmetic (e.g. `Math.multiplyExact`/`Math.addExact` or `StrictMathWrapper`, as already used in `AssetIssueActuator`) when computing `duration`/`expireTime` in `FreezeBalanceActuator.execute` and `FreezeBalanceProcessor.execute`, and enforce the `minFrozenTime`/`maxFrozenTime` bound in `validate()` unconditionally (not gated behind the test-only `checkFrozenTime` flag) so malformed or maliciously large `frozen_duration` values are rejected before reaching the multiplication.

### Proof of Concept
1. Submit a `FreezeBalanceContract` transaction with `frozen_balance = 1_000_000` (1 TRX) and `frozen_duration` set to a value large enough that `frozen_duration * FROZEN_PERIOD` overflows `Long` (e.g. `Long.MAX_VALUE / FROZEN_PERIOD + 1`).
2. On a node where `checkFrozenTime` is at its production default (disabled), `validate()` at [6](#0-5)  does not reject the value.
3. `execute()` computes `duration = frozenDuration * FROZEN_PERIOD` (wrapped) and `expireTime = now + duration`, storing a corrupted expire time via `accountCapsule.setFrozenForBandwidth(...)` at [7](#0-6) , potentially making the frozen resource immediately eligible for unfreezing regardless of the intended long lock duration.
