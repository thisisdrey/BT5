### Title
`MerkleTree::new` root collision via odd-leaf duplication padding (CVE-2012-2459-style malleability) - ([File: merkle-tree/src/merkle_tree.rs])

### Summary
`MerkleTree::new` pads an odd-length level by duplicating the last node's hash rather than using a domain-separated/counted padding scheme. As a result, for any leaf set `L1` with `len(L1)` odd, `get_root(L1)` is identical to `get_root(L1 ++ [last(L1)])`, i.e., appending an explicit duplicate of the final leaf produces the exact same Merkle root as the original odd-length set. This is the classic CVE-2012-2459 Merkle-tree malleability bug: the tree fails to injectively commit to its leaf multiset/length.

### Finding Description
In `MerkleTree::new`, when building each level, if the level has an odd number of nodes, the last node is paired with itself instead of the tree encoding the true length: [1](#0-0) 

Because `hash_leaf!` is a pure function of leaf content (no length/index prefix beyond the type-separating `LEAF_PREFIX`), for any odd `n = len(L1)`, `L2 = L1 ++ [last(L1)]` has `n+1` leaves. `L2`'s leaf level has `(n+1)/2` pairs, all real pairs (no duplication needed since it's even), and the last real pair `(h_{n-1}, h_{n-1})` is byte-identical to the *synthetic* duplicated pair `L1`'s odd level would have produced internally: [2](#0-1) 

Since `hash_intermediate!` only depends on the two child hash values (not on whether they came from real leaves or duplication, and not on the original level length), the level-1 node arrays produced for `L1` and `L2` are element-for-element identical, both of length `(n+1)/2`. All subsequent levels are computed purely as a function of this identical array via the same deterministic reduction, so the final roots for `L1` and `L2` are also identical: [3](#0-2) 

The comment at the top of the file references defending against second-preimage attacks via leaf/intermediate domain separation (`LEAF_PREFIX`/`INTERMEDIATE_PREFIX`), [4](#0-3)  but this only prevents *leaf-as-intermediate* substitution; it does nothing to prevent the *length-ambiguity* attack where two distinct leaf sequences of different cardinality produce the same root due to duplicate-padding, which is a separate, well-known vulnerability class (CVE-2012-2459).

### Impact Explanation
Any consumer of `solana_merkle_tree::MerkleTree` that relies on `get_root()` to uniquely commit to a specific leaf sequence (count and content) is vulnerable to a root-collision/second-preimage-of-length attack: two different transaction/entry sets of different sizes can produce an identical committed root, breaking the "root uniquely commits to content" invariant. This falls under a verification/commitment-bypass category: an attacker can present, or a component can be tricked into accepting, a different leaf set than the one that was actually authorized/proven, because the root alone cannot distinguish `L1` from `L1 ++ [last(L1)]`. `find_path`/`Proof::verify` are also affected transitively since the underlying node array (and thus valid proofs) is identical between the two leaf sets, meaning inclusion proofs against `L1`'s root remain valid even though the "canonical" leaf set was silently extended by one duplicate entry.

### Likelihood Explanation
The bug is deterministic and always reproducible for any odd-length leaf set; it requires no privileged access, no timing race, and no network exploitation primitives — it is a pure function-level defect reachable directly via the public `MerkleTree::new` / `get_root` API. Exploitability against a live validator depends on whether an unprivileged remote party can influence which leaves feed a given `MerkleTree` instance (e.g., transaction/entry batches processed by the leader) such that they can force an odd-to-even duplicate-boundary condition; this crate-level defect confirms the root cause and is independent of any specific call site.

### Recommendation
Fix the duplication-padding scheme so that odd-length levels are not collision-equivalent to explicit even-length duplication, e.g.:
- Encode the sibling absence explicitly by hashing the single remaining node with itself, but additionally domain-separate on the *original, unpadded* level length or leaf count at that level, or
- Follow RFC 6962 style Merkle trees which recursively split unbalanced trees into a full left subtree and a right remainder rather than duplicating nodes, avoiding the ambiguity entirely.

### Proof of Concept
```rust
use solana_merkle_tree::MerkleTree;

#[test]
fn test_duplicate_last_leaf_root_collision() {
    for n in [1usize, 3, 5, 7] {
        let l1: Vec<Vec<u8>> = (0..n).map(|i| vec![i as u8; 8]).collect();
        let mut l2 = l1.clone();
        l2.push(l1.last().unwrap().clone()); // L2 = L1 ++ [last(L1)]

        let root1 = MerkleTree::new(&l1).get_root().cloned();
        let root2 = MerkleTree::new(&l2).get_root().cloned();

        // BUG: roots collide even though L1 != L2 (different length/content)
        assert_eq!(root1, root2, "expected collision for n={n} demonstrating malleability");
    }
}
```
Property-based extension: generate random `(leaves: Vec<Vec<u8>>, /* odd length */)` via proptest, construct `L2 = leaves ++ [leaves.last()]`, and assert `MerkleTree::new(&leaves).get_root() == MerkleTree::new(&L2).get_root()` to confirm the injective-commitment property is violated across the odd→even boundary for all tested leaf counts.

```rust
// We need to discern between leaf and intermediate nodes to prevent trivial second
// pre-image attacks.
// https://flawed.net.nz/2018/02/21/attacking-merkle-trees-with-a-second-preimage-attack
const LEAF_PREFIX: &[u8] = &[0];
const INTERMEDIATE_PREFIX: &[u8] = &[1];

macro_rules! hash_leaf {
    {$d:ident} => {
        hashv(&[LEAF_PREFIX, $d])
    }
}

macro_rules! hash_intermediate {
    {$l:ident, $r:ident} => {
        hashv(&[INTERMEDIATE_PREFIX, $l.as_ref(), $r.as_ref()])
    }
}
```

```rust
    pub fn new<T: AsRef<[u8]>>(items: &[T]) -> Self {
        let cap = MerkleTree::calculate_vec_capacity(items.len());
        let mut mt = MerkleTree {
            leaf_count: items.len(),
            nodes: Vec::with_capacity(cap),
        };

        for item in items {
            let item = item.as_ref();
            let hash = hash_leaf!(item);
            mt.nodes.push(hash);
        }

        let mut level_len = MerkleTree::next_level_len(items.len());
        let mut level_start = items.len();
        let mut prev_level_len = items.len();
        let mut prev_level_start = 0;
        while level_len > 0 {
            for i in 0..level_len {
                let prev_level_idx = 2 * i;
                let lsib = &mt.nodes[prev_level_start + prev_level_idx];
                let rsib = if prev_level_idx + 1 < prev_level_len {
                    &mt.nodes[prev_level_start + prev_level_idx + 1]
                } else {
                    // Duplicate last entry if the level length is odd
                    &mt.nodes[prev_level_start + prev_level_idx]
                };

                let hash = hash_intermediate!(lsib, rsib);
                mt.nodes.push(hash);
            }
            prev_level_start = level_start;
            prev_level_len = level_len;
            level_start += level_len;
            level_len = MerkleTree::next_level_len(level_len);
        }

        mt
    }
```
