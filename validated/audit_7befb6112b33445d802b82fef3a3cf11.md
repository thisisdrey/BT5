### Title
Uniswap-V2-style spot-reserve manipulation of TRON's internal Bancor exchange pool - unprotected `ExchangeInjectActuator`/`ExchangeWithdrawActuator` computations enable sandwich theft of pool funds ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java])

### Summary
TRON's built-in TRC10 AMM (the "Exchange" contract family: `ExchangeCreateActuator`, `ExchangeInjectActuator`, `ExchangeWithdrawActuator`, `ExchangeTransactionActuator`) is directly analogous to a Uniswap V2 pool: it stores two token reserves (`firstTokenBalance`/`secondTokenBalance`) that anyone can move with a permissionless swap (`ExchangeTransactionActuator`). Just like `OCL_ZVE.sol::forwardYield` trusts the instantaneous Uniswap V2 reserve ratio to compute a settlement amount (`basis`), `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the counter-token amount to credit/debit purely from the current spot balance ratio of the pool — with no minimum-output/slippage protection parameter and no TWAP or invariant check. Because the reserve-moving swap (`ExchangeTransactionActuator`) is itself a normal, unprivileged, single-signed-transaction operation, an attacker can manipulate the ratio immediately before a withdraw/inject executes and reverse the manipulation afterward, extracting value exactly as described in the Uniswap V2 report.

### Finding Description
`ExchangeCapsule.transaction()` implements the swap logic and directly mutates `firstTokenBalance`/`secondTokenBalance` based on the Bancor formula in `ExchangeProcessor`/`SafeExchangeProcessor`: [1](#0-0) 

This swap is exposed permissionlessly via `ExchangeTransactionActuator`, callable by any signed transaction from any account, with only a caller-supplied slippage bound (`tokenExpected`): [2](#0-1) [3](#0-2) 

In contrast, `ExchangeWithdrawActuator` computes the amount of the "other" token to return using only the *current* spot balance ratio, with no slippage/minimum-output check at all: [4](#0-3) 

`ExchangeInjectActuator` has the identical pattern for deposits: [5](#0-4) 

Because Tron executes transactions sequentially within a block and each subsequent transaction observes the state written by the previous one, an attacker can:
1. Broadcast an `ExchangeTransactionContract` that heavily skews `firstTokenBalance`/`secondTokenBalance` away from its "fair" ratio (a large one-sided swap, exactly like a Uniswap V2 flash-swap manipulation).
2. Immediately follow (or front-run) the exchange creator's `ExchangeWithdrawContract`/`ExchangeInjectContract`, which is now valued at the skewed ratio and therefore returns disproportionately more/less of the counter-token than it should.
3. Reverse the initial swap with a second `ExchangeTransactionContract`, restoring the ratio and capturing the ratio-differential profit that was siphoned from the exchange's owner/liquidity — a "sandwich" identical in mechanics to the Uniswap V2 report's basis-manipulation scenario, just moved from an external DEX price feed to Tron's own in-protocol AMM state.

Neither `doValidate()` in `ExchangeWithdrawActuator` nor `ExchangeInjectActuator` bounds `anotherTokenQuant` against a caller-specified minimum/maximum, unlike `ExchangeTransactionActuator`'s `tokenExpected` field: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any exchange's liquidity is exposed to sandwich extraction whenever its owner performs a `Withdraw` or `Inject`, since both computations rely solely on the instantaneous, publicly-manipulable reserve ratio, with no protection mechanism (unlike the swap path). An attacker with no special privileges — merely broadcasting ordinary `ExchangeTransactionContract` transactions — can force a victim's withdraw/inject to settle at an unfavorable ratio, extracting real TRX/TRC10 asset value from the exchange (loss of funds), mirroring the Sherlock Medium finding's core defect: trusting a manipulable spot ratio for an accounting/settlement calculation without slippage bounds or a robust price reference.

### Likelihood Explanation
The manipulation step (`ExchangeTransactionActuator`) is fully permissionless and reachable by any signed transaction; it requires no admin/keeper role, no compromised key, and no off-chain dependency. The only condition is that the victim's `ExchangeWithdrawContract`/`ExchangeInjectContract` be broadcast/ordered adjacent (before/after) to the attacker's manipulating swaps within the block-ordering window the attacker controls (e.g., via transaction fee/ordering strategy), which is a standard MEV/sandwich precondition, directly analogous to the original report's flash-loan-and-frontrun scenario.

### Recommendation
Add a caller-specified minimum/maximum bound (slippage protection) for `anotherTokenQuant` in both `ExchangeInjectActuator` and `ExchangeWithdrawActuator`, matching the `expected` field already present in `ExchangeTransactionContract`. Consider also using a time-weighted or otherwise manipulation-resistant reference ratio rather than the raw instantaneous `firstTokenBalance`/`secondTokenBalance` for these settlement calculations.

### Proof of Concept
1. Attacker (or any user) observes an `Exchange` pool with reserves `firstTokenBalance = F`, `secondTokenBalance = S`.
2. Attacker submits `ExchangeTransactionContract` selling a large amount of the first token, skewing the ratio to `F' >> F`, `S' << S` (per `ExchangeCapsule.transaction`, `ExchangeCapsule.java:124-158`).
3. The exchange creator's pre-existing `ExchangeWithdrawContract` (or the attacker front-runs a legitimate withdraw with a manipulative swap, or colludes/uses two of their own accounts) executes against the skewed ratio; `anotherTokenQuant` is computed as `S' * tokenQuant / F'` — a value far below fair value (`ExchangeWithdrawActuator.java:77-89`), with zero slippage protection to reject this outcome.
4. Attacker immediately reverses the initial swap with a second `ExchangeTransactionContract`, restoring `F`,`S` and pocketing the difference extracted from the withdrawer, mirroring the original report's flash-loan → skew basis → drain → reverse pattern.
