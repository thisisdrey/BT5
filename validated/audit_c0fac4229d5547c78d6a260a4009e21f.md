### Title
Uncaught ArithmeticException in `MarketSellAssetActuator.execute()` causes deterministic transaction-processing exception outside the actuator's handled failure path - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
The external report's core lesson is that an actuator/settlement path computed a value (`order.amount_in`) from trusted-looking but stale/derived data and used it directly in a fund-affecting closing operation, without reconciling it against the actual balance held by the account being acted upon — causing the finalize/close step to fail. The closest reachable analog in java-tron is `MarketSellAssetActuator`, which performs balance-affecting arithmetic (`subtractExact`/`addExact`/`multiplyAndDivide`) on account/order balances computed from previously-stored quantities, inside `execute()`, but — unlike its sibling actuators (`ExchangeTransactionActuator`, `ExchangeWithdrawActuator`) — does **not** catch `ArithmeticException` in `execute()`.

### Finding Description
`ExchangeTransactionActuator.execute()` and `ExchangeWithdrawActuator.execute()` both explicitly catch `ArithmeticException` alongside `ItemNotFoundException`/`InvalidProtocolBufferException` so that an overflow/underflow during settlement degrades to a normal `ContractExeException` (failed transaction) rather than an uncaught runtime exception: [1](#0-0) [2](#0-1) 

`MarketSellAssetActuator.execute()`, however, only catches `ItemNotFoundException | InvalidProtocolBufferException | BalanceInsufficientException | ContractValidateException` — `ArithmeticException` is conspicuously absent from this catch clause: [3](#0-2) 

Yet `execute()` performs several `subtractExact`/`addExact` operations on account balances and order quantities derived from stored `MarketOrderCapsule` state and `contract` fields — e.g. `transferBalanceOrToken` (`subtractExact(accountCapsule.getBalance(), sellTokenQuantity)`), and inside `matchSingleOrder` via `MarketUtils.multiplyAndDivide` and `subtractExact`: [4](#0-3) [5](#0-4) 

Because order matching walks a live order book (`matchOrder`/`matchSingleOrder`) across potentially many maker orders accumulated over time under prior market conditions, `validate()`'s single up-front `addExact` overflow check (performed once, before the loop, on the taker's own balance) does not guarantee that every intermediate `subtractExact`/`addExact`/`multiplyAndDivide` computed while walking accumulated maker orders (whose quantities are independently chosen by other order-placers) stays within `long` bounds. If any of those computations overflows, `ArithmeticException` is thrown from deep inside `matchOrder`, propagates unhandled out of `execute()` (since it's not in the catch list), and out of the actuator invocation entirely — unlike a normal validation failure, this is not converted into a `ContractExeException`/failed-transaction result.

This mirrors the report's root cause pattern: code assumes a derived/accumulated numeric value will always be consistent with what the closing/settling operation expects, and skips defensive reconciliation/exception handling at the point where the mismatch would actually manifest (analogous to `token::close_account` failing because the actual balance ≠ the assumed `order.amount_in`).

### Impact Explanation
Because block/transaction application in java-tron is deterministic, every full node executing this transaction inside a block reaches the same overflow and throws the same uncaught `ArithmeticException`. If this exception is not caught by a higher-level generic handler in the transaction-processing pipeline, it can abort block application for that transaction/block on all nodes simultaneously, which is a chain-halt/node-crash class issue (deterministic DoS) rather than a benign single-transaction failure. This falls under "node crash or halt" impact permitted by the scope rules.

### Likelihood Explanation
Reaching `MarketSellAssetActuator` requires only a signed `MarketSellAssetContract` from any account with sufficient balance/asset and market trading enabled (`supportAllowMarketTransaction`) — a standard, unprivileged, permissionless transaction path (order placer). Triggering the overflow requires crafting sell/buy quantities and/or accumulating maker orders such that an intermediate multiplication/addition in `matchSingleOrder`/`MarketUtils.multiplyAndDivide` exceeds `Long.MAX_VALUE`, which is plausible given `sellTokenQuantity`/`buyTokenQuantity` are only bounded by `dynamicStore.getMarketQuantityLimit()` and multiple maker orders can compound the total value matched in a single taker transaction (bounded by `MAX_MATCH_NUM = 20`).

### Recommendation
Add `ArithmeticException` to the caught exception set in `MarketSellAssetActuator.execute()` (consistent with `ExchangeTransactionActuator`/`ExchangeWithdrawActuator`), and audit `MarketUtils.multiplyAndDivide`/`matchSingleOrder`/`transferBalanceOrToken` to ensure every fund-affecting arithmetic operation validates the actual resulting balances stay within safe bounds before committing state, rather than assuming the pre-validated (single) balance check remains sufficient across the entire matching loop.

### Proof of Concept
Conceptual (not verified end-to-end due to index limits on full `MarketUtils` internals):
1. Attacker/market participant seeds the order book with maker orders (`MarketSellAssetContract`) whose `sellTokenQuantity`/`buyTokenQuantity` are set near `dynamicStore.getMarketQuantityLimit()`.
2. Attacker submits a taker `MarketSellAssetContract` that matches against up to `MAX_MATCH_NUM` (20) such orders in one transaction.
3. During `matchOrder`/`matchSingleOrder`, `MarketUtils.multiplyAndDivide` or `subtractExact`/`addExact` on the accumulated quantities overflows `long`, throwing `ArithmeticException` inside `execute()`.
4. Since `execute()`'s catch clause does not include `ArithmeticException`, the exception is not converted into a `ContractExeException`; it propagates out of actuator execution during block application, potentially aborting processing deterministically on every validating/witness node that applies the block.

Note: I was unable to fully verify (due to index/context limits) exactly how far up the call stack an uncaught `RuntimeException` like `ArithmeticException` propagates before being caught generically (e.g., in `Manager`/block-application code) — confirming whether it truly reaches a chain-halt versus being swallowed by an outer generic `catch (Exception e)` would require checking the block application call path (`Manager.processTransaction`/`TransactionCapsule`) directly, which was not fully retrievable from the indexed context.
