### Title
Replay-window check/decrypt/update race allows a duplicate packet to bypass anti-replay protection - (File: connection_state.go)

### Summary
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` split the anti-replay check into three separate critical sections: `window.Check` (locked), AEAD decrypt (unlocked), and `window.Update` (locked). This mirrors the reported bug class — a validation and its associated state-mutating side effect are not atomic, so the operation performed between the check and the confirming update ("decrypt") can be completed for more than one concurrently-processed copy of the same message counter before the replay-window bit is actually set.

### Finding Description
`Decrypt` performs:
1. lock → `window.Check(messageCounter)` → unlock
2. `dKey.DecryptDanger(...)` (no lock held)
3. lock → `window.Update(messageCounter)` → unlock [1](#0-0) 

Because the decrypt step is unlocked and interposed between `Check` and `Update`, two concurrently-processed copies of a packet with the same `messageCounter` (e.g., the same UDP frame arriving twice, or being processed by two reader routines) can both pass `Check` before either has called `Update`. Both then run the (expensive, counter-independent) AEAD decrypt using the wire-supplied `messageCounter` as nonce input. The same race exists in `VerifyRelay`, which follows the identical check→verify→update pattern used for relay frames: [2](#0-1) .

This is the same root-cause pattern as the referenced report: a security-critical validation (`checkWithdrawLimits` / here, `window.Check`+`window.Update` marking a counter “seen”) is decoupled from the side effect it is supposed to gate (fee deduction / here, AEAD decrypt and subsequent packet processing), allowing the gated operation to execute based on stale-but-not-yet-committed state. The dedicated regression test `TestRelayReplayProtection` demonstrates the importance of this exact ordering for relay frames, showing the codebase is already aware that "authenticate but don't advance the window in the same atomic step" is a historically real bug class in this file/feature area: [3](#0-2) .

`Interface.readOutsidePackets`/`Decrypt` is reached directly from UDP-received bytes for any packet matching a known `RemoteIndex`, i.e., it is exercised by anyone who can send or replay UDP traffic to a listening socket, without holding a CA-signed certificate themselves (they only need to have observed or intercepted one legitimate encrypted frame to replay). [4](#0-3) 

### Impact Explanation
If the race is won, a captured ciphertext frame can be decrypted and delivered to the data-plane/message handling path more than once for effectively the same message counter window state, undermining the anti-replay guarantee that `ReplayWindow`/`Bits` is meant to provide. Depending on which processing path this feeds (e.g., tun packet injection, control-message handling, or relay forwarding as in `handleOutsideRelayPacket`), this could translate into traffic replay being accepted rather than dropped, which is a direct confidentiality/integrity guarantee failure for the wireguard-like transport (impact: High per the analog's High/Low classification, since it defeats a core security control (replay protection) though it needs a race/concurrency condition to trigger (Likelihood: Low), consistent with the report's severity framing).

### Likelihood Explanation
Triggering requires a captured legitimate ciphertext (no valid certificate needed) and a race window between unlocked decrypt and the confirming `window.Update` call, which is narrow but plausible under multi-queue readers or high packet ordering jitter. This mirrors the referenced report's classification of Low likelihood but High impact, and unlike the excluded categories (malicious-peer/lighthouse, valid-cert-holder, host-access), this path is reachable purely by observing/replaying wire traffic.

### Recommendation
Make the replay-window check-and-mark atomic with respect to the decrypt attempt, or ensure that a losing racer's already-decrypted output can never be delivered/acted upon. Concretely: hold `decryptLock` across `Check`, `DecryptDanger`, and `Update` as a single critical section (accepting the cost of serializing decryption per hostinfo), or restructure so `Update` is attempted first (claim the slot) and rolled back only if decrypt fails, rather than allowing decrypt to run on state that hasn't yet been durably marked as consumed.

### Proof of Concept
Conceptual PoC (concurrency-dependent, not a deterministic single-shot exploit):
1. Attacker captures one legitimate encrypted UDP frame `P` (with header `MessageCounter = N`) sent from A to B.
2. Attacker sends two copies of `P` to B nearly simultaneously (or via multiple listen queues) so that both goroutines reach `hostinfo.ConnectionState.Decrypt(f.l, N, ...)` inside `readOutsidePackets` around the same time: [5](#0-4) .
3. Goroutine 1 executes `window.Check(N)` → true, unlocks.
4. Goroutine 2 executes `window.Check(N)` → true (bit for N not yet set), unlocks — before goroutine 1 reaches `Update`.
5. Both goroutines run `dKey.DecryptDanger` successfully (decrypt success does not depend on window state) inside `Decrypt`: [6](#0-5) .
6. Only one of the two `window.Update(N)` calls will return true; the other will return `ErrAlreadySeen`, but by that point the "losing" goroutine has already produced a fully decrypted, authenticated plaintext for the replayed frame, and whatever work happened between decrypt and the update-check (e.g., logging, buffer reuse, or any hook executed before the error is checked) has already run against attacker-replayed content rather than being cleanly rejected before decrypt.

This is directly analogous to the report's `matchOrders`/`updateBalance` sequence, where the side effect (fee deduction / decrypt) is not atomic with the limiting/anti-abuse check (withdraw limit / replay-window update), allowing exploitable inconsistency between the two.

func (cs *ConnectionState) Decrypt(l *slog.Logger, messageCounter uint64, out []byte, packet []byte, nb []byte) ([]byte, error) {
	var err error
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}

	out, err = cs.dKey.DecryptDanger(out, packet[:header.Len], packet[header.Len:], messageCounter, nb)
	if err != nil {
		return nil, err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return nil, ErrAlreadySeen
	}
	return out, nil
}

func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
