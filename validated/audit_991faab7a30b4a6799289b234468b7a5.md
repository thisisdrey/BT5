This is a solid local analog. `pallet-asset-conversion`'s `do_remove_liquidity` enforces a check on the **pool's aggregate reserve** rather than the caller's own redeemable share, which reproduces exactly the Amun H-02 pattern: a floor check on total pool balance blocks the final withdrawal and permanently traps residual funds.

### Title
Pool-reserve floor check in `do_remove_liquidity` permanently locks the last liquidity provider's residual tokens - (File: `substrate/frame/asset-conversion/src/lib.rs`)

### Summary
`Pallet::do_remove_liquidity` rejects any liquidity removal that would push the pool's remaining `reserve1`/`reserve2` below `T::Assets::minimum_balance(asset)`. This check is evaluated against the pool's total reserve, not the caller's proportional entitlement. As pool reserves shrink toward the existential-deposit floor (e.g. after most other LPs have exited), the last liquidity provider becomes permanently unable to withdraw any further tokens, even though the LP tokens representing that residual balance are never burned and remain in their account — an unrecoverable, permanent lock, structurally identical to the Amun `BasketFacet` `MIN_AMOUNT` bug.

### Finding Description
`do_remove_liquidity` computes the withdrawable amounts from the LP tokens burned and then enforces: [1](#0-0) 

```
let reserve1_left = reserve1.saturating_sub(amount1);
let reserve2_left = reserve2.saturating_sub(amount2);
ensure!(reserve1_left >= T::Assets::minimum_balance(asset1.clone()), Error::<T>::ReserveLeftLessThanMinimal);
ensure!(reserve2_left >= T::Assets::minimum_balance(asset2.clone()), Error::<T>::ReserveLeftLessThanMinimal);
```

This guard exists to keep the pool account itself from being dusted below the existential deposit (which would reap the account). But it is checked against the *pool's total reserve after the withdrawal*, not against whether the withdrawal matches the caller's fair proportional share of the pool. Once `reserve1` (or `reserve2`) has shrunk to a value only marginally above `minimum_balance`, any further `remove_liquidity` call whose resulting `reserve*_left` would dip below that minimum is rejected in full via `ensure!` — the call reverts entirely, the LP token is not burned, and the caller is left holding a permanently non-redeemable balance.

This is not equivalent to the intentional, well-known `MintMinLiquidity` (Uniswap-style) permanent lock, which is a fixed, small, protocol-owned amount minted to the keyless pool account at pool creation: [2](#0-1) 

The `ReserveLeftLessThanMinimal` check instead traps *user-owned* LP tokens: it prevents a legitimate LP from ever bringing `reserve*_left` down to (or below) the ED floor, so any residual position whose fair-share reserve equivalent is close to the ED can never be exited, regardless of how many partial withdrawals are attempted. The pool account (`T::PoolLocator::address`) is a `PalletId`-derived account with no corresponding private key, so nobody can dispatch a call as that account to sweep the trapped dust either.

The project's own integration test explicitly documents that this residual is unrecoverable: [3](#0-2) 
```
assert_ok!(<AssetHubWestend as AssetHubWestendPallet>::AssetConversion::remove_liquidity(
    ...
    1414213562273 - 2_000_000_000, // all but the 2 EDs can't be retrieved.
    ...
));
```
The comment "all but the 2 EDs can't be retrieved" is a direct acknowledgment that a fixed amount of user-attributable value becomes permanently stuck — the exact `MIN_AMOUNT`-style lock described in the Amun report.

### Impact Explanation
Any liquidity provider whose remaining position, once other LPs (or they themselves through prior partial withdrawals) have reduced pool reserves, corresponds to a reserve value near `minimum_balance` can never fully exit the pool. Their LP tokens remain un-burnable and the underlying `asset1`/`asset2` value they represent is permanently locked in the pool account, with no path to reclaim it (no owner key for the pool account, no governance sweep function is present in the pallet). This is a permanent user-fund lock, matching the "Required Impacts" category directly.

### Likelihood Explanation
This requires no privileged actor, malicious peer, or governance action — any combination of unprivileged `add_liquidity`/`remove_liquidity` calls by ordinary users that drives pool reserves down near the ED can trigger it. It is deterministic and reproducible purely through public dispatchables (`create_pool`, `add_liquidity`, `remove_liquidity`), and is already implicitly exercised (though not flagged as a bug) in the repository's own emulated tests.

### Recommendation
Do not hard-reject the whole `remove_liquidity` extrinsic when the ED floor is crossed. Instead, either:
- cap the withdrawal at `reserve - minimum_balance` and burn only the corresponding LP tokens (returning the achievable amount) rather than reverting, or
- allow a caller who owns 100% of the redeemable (non-locked) LP-token supply to fully drain the reserve down to zero, using `Expendable`/dust-removal semantics on the pool account for that final step, so the last legitimate holder is not blocked by an aggregate-reserve check that was designed to protect the pool account, not to gate an individual member's fair share.

### Proof of Concept
1. `create_pool(asset1, asset2)` and `add_liquidity` with `amount1`, `amount2` just above `MintMinLiquidity` requirements; LP tokens `T = sqrt(amount1*amount2)` are split as `100` (locked to pool account) + `T-100` (to the sole provider).
2. The provider calls `remove_liquidity` with `lp_token_burn = T - 100` (i.e., their entire holding) once `reserve1` has been driven down (via swaps or partial prior removals) to a value only slightly above `T::Assets::minimum_balance(asset1)`.
3. `do_remove_liquidity` computes `amount1 = lp_redeem_amount * reserve1 / total_supply`; the resulting `reserve1_left` (which should approximate the tiny reserve share owned by the permanently-locked `100` LP tokens) falls below `minimum_balance(asset1)`.
4. The `ensure!(reserve1_left >= minimum_balance(asset1), Error::<T>::ReserveLeftLessThanMinimal)` at [4](#0-3)  fails, the whole extrinsic reverts, and the LP token is not burned.
5. Any smaller `lp_token_burn` amount that would satisfy the check leaves an even larger residual reserve than the protocol-intended locked share — the provider can shrink their position only down to the point where `reserve1_left == minimum_balance(asset1)`, after which no further withdrawal is ever possible: the remaining LP tokens, and the value they represent, are permanently stranded.
