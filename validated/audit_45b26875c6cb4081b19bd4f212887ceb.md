### Title
Unvalidated attacker-controlled array offset causes uncaught `ArrayIndexOutOfBoundsException` in `ValidateMultiSign` precompile - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (TVM address `0x0a`) reads a signature-array offset directly from calldata and immediately uses it to index into the parsed `DataWord[] words` array without any bounds check, before the existing helper guards (`extractBytesArray`/`extractSigArray`) are ever reached. This mirrors the CVE-2023-45682 bug class: a value decoded straight from untrusted input is used as an array index/length without validating it is in range, producing an out-of-bounds access.

### Finding Description
In `ValidateMultiSign.execute` / the shared helpers: [1](#0-0) 

```java
if (VMConfig.allowTvmSelfdestructRestriction()) {
  int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
  if (sigArraySize > MAX_SIZE) {
    return Pair.of(true, DATA_FALSE);
  }
}
byte[][] signatures = VMConfig.allowTvmSelfdestructRestriction() ?
    extractSigArray(words, words[3].intValueSafe() / WORD_SIZE, rawData) :
    extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData);
```

`words[3]` is a 32‑byte word fully controlled by the caller of the precompile (via calldata to address `0x0a`). `intValueSafe()` clamps the value into an `int` range, but the result is used directly as an index into `words` (`words[words[3].intValueSafe() / WORD_SIZE]`) with **no bounds check** — unlike the sibling helper functions `extractBytesArray`/`extractSigArray`, which do guard with `if (offset > words.length - 1) return new byte[0][];`: [2](#0-1) 

Because the `sigArraySize` computation happens **before** any of those guarded helper calls, a crafted offset (e.g. a large value that, divided by `WORD_SIZE`, exceeds `words.length`, or a negative value from a subtraction/overflow path) triggers `words[<out-of-range-index>]`, throwing `ArrayIndexOutOfBoundsException`.

This is the direct Java analog of the stb_vorbis bug: an attacker-supplied numeric field is trusted as an in-range index/length and dereferenced without validation, exactly as `DECODE_RAW`'s `var` is used without checking for negative values before the `DECODE` macro reads memory at that offset.

Critically, unlike `BatchValidateSign.execute`, which wraps its entire body in `try { ... } catch (Throwable t) { return Pair.of(true, new byte[WORD_SIZE]); }`, `ValidateMultiSign.execute` has **no outer catch** around this offset-computation code — the `try/catch (Throwable t)` inside the method only wraps the later weight-calculation loop, not the array indexing above: [3](#0-2) 

The uncaught `ArrayIndexOutOfBoundsException` (a `RuntimeException`) then propagates up through `Program.callToPrecompiledAddress` — which has no catch around `contract.execute(data)` — and further up through `VM.play()`'s per-opcode try/catch, which explicitly re-throws (`throw e;`) after logging: [4](#0-3) [5](#0-4) 

### Impact Explanation
Any account can trigger this by issuing a `CALL`/`STATICCALL` (directly from a transaction or from inside another contract) to precompile address `0x0a` (`ValidateMultiSign`) with crafted calldata containing an out-of-range offset word. Because this precompile path lacks the defensive catch that `BatchValidateSign` has, the resulting `ArrayIndexOutOfBoundsException` is not converted into a normal TVM revert/failure — it is an unchecked exception that escapes the intended TVM exception hierarchy (`Program.IllegalOperationException`, `OutOfMemoryException`, etc.) that callers up the stack (transaction execution / `TransactionTrace`) are designed to catch and convert into `ContractExeException`/`ReceiptCheckErrException`. If it is not caught by a generic fallback higher in the transaction-processing pipeline, it can abort processing of the block/transaction inconsistently or crash the node process handling the transaction — a denial-of-service condition reachable by an unprivileged contract caller. At minimum this is a reliable way to make TVM execution fail via an unintended/unhandled exception type rather than the standard revert path, which is itself a correctness/robustness issue in a security-critical signature-validation precompile.

### Likelihood Explanation
High. `ValidateMultiSign` is a permissionless precompile reachable by any address via a simple `CALL` with attacker-chosen calldata (no special permissions needed, and `VMConfig.allowTvmSelfdestructRestriction()` is a mainnet-activated feature flag, not something the attacker needs to control). Constructing calldata where `words[3]` decodes (after `/WORD_SIZE`) to an index beyond `words.length` is trivial and deterministic.

### Recommendation
Add the same bounds check used in `extractBytesArray`/`extractSigArray` before computing `sigArraySize` in `ValidateMultiSign.execute` (and the analogous `sigArraySize`/`addrArraySize` computation in `BatchValidateSign.doExecute`, even though it is currently shielded by an outer `catch (Throwable t)`): verify `words[3].intValueSafe() / WORD_SIZE` is within `[0, words.length - 1]` before indexing `words[...]`, returning `Pair.of(true, DATA_FALSE)` (or the appropriate failure tuple) otherwise. Additionally, wrap the whole `ValidateMultiSign.execute` body (or at minimum the offset-parsing section) in the same defensive `try { ... } catch (Throwable t) { return Pair.of(true, DATA_FALSE); }` pattern already used in `BatchValidateSign`, so any unexpected `RuntimeException` cannot escape the precompile into unrelated TVM-processing exception handling.

### Proof of Concept
1. Enable/assume `VMConfig.allowTvmSelfdestructRestriction()` is active (mainnet feature).
2. Craft calldata for the `ValidateMultiSign` precompile (`validatemultisign(address,uint256,bytes32,bytes[])`-style ABI layout) where:
   - `words[0]` = arbitrary address, `words[1]` = arbitrary permission id, `words[2]` = arbitrary hash data.
   - `words[3]` = a 32-byte value such that `intValueSafe() / WORD_SIZE` yields an index ≥ `words.length` (e.g., set `words[3]` to a value like `0x00000000000000000000000000000000000000000000000000000fffffff` scaled so the divided result exceeds the number of words actually present in a short calldata buffer).
3. Send a transaction (or have a contract issue a `STATICCALL`/`CALL`) to precompile address `0x0a` with this calldata and sufficient energy (`getEnergyForData` is cheap: `(data.length/32 - 5)/5 * 1500`).
4. Execution reaches `words[words[3].intValueSafe() / WORD_SIZE]` in `ValidateMultiSign.execute`, which throws `ArrayIndexOutOfBoundsException` uncaught by any surrounding `try/catch` in that method, propagating through `Program.callToPrecompiledAddress` → `VM.play()`'s explicit `throw e;` up to the transaction-execution caller — an anomalous exception path distinct from the TVM's intended `IllegalOperationException`/revert handling for this feature.

**Uncertainty note:** I was not able to fully trace whether `Runtime`/`TransactionTrace` (the top-level transaction executor) has a final catch-all for arbitrary `RuntimeException` that would downgrade this to a normal failed transaction versus letting it escape further (e.g., into `Manager`'s block-application loop, which would be far more severe — a chain-halting condition). The repository's index did not return the relevant exception-handling code in `Runtime.java`/`TransactionTrace.java` for `contract.execute()`/VM invocation. This should be verified directly in the full codebase (via a live Devin session) to determine whether the impact is "isolated failed transaction" or "node/block-processing crash."

    if (offset > words.length - 1) {

    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
