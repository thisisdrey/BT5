### Title
HTTP/2 verbose debug logging writes outgoing header values (including `Authorization`) to logs - ([File: src/net/http/internal/http2/write.go])

### Summary
When Go's HTTP/2 implementation is run with the undocumented-but-real debug knob `GODEBUG=http2debug=2` (or `=1`), the server-side header-encoding path logs every outgoing header name **and value** via `log.Printf`. Because HTTP libraries commonly set `Authorization` on outgoing requests/responses (Basic auth, bearer tokens), enabling this debug mode causes live credentials to be written to process logs, mirroring the `azure_core` CWE-532 pattern (secrets leaked at debug-level logging) reported in RUSTSEC-2026-0275.

### Finding Description
`src/net/http/internal/http2/http2.go:47-64` wires the package-level `VerboseLogs` (and frame read/write logging) flags to the `GODEBUG` setting `#http2debug`: [1](#0-0) 
When `VerboseLogs` is true, `encKV` in `src/net/http/internal/http2/write.go:201-206` logs every header field name and value being HPACK-encoded for the outgoing HEADERS/CONTINUATION frames: [2](#0-1) 
This function is invoked while encoding the actual header list a caller supplied (e.g., request headers set via `Request.Header.Set("Authorization", ...)` or `Request.SetBasicAuth`, `src/net/http/request.go:1017-1030`), with no redaction/allow-list logic for sensitive header names such as `Authorization`, `Proxy-Authorization`, or `Cookie`. [3](#0-2) 

Entry point → sink chain: application code sets `Authorization` on an `http.Request`/response headers → HTTP/2 transport/server encodes headers for the wire via the HEADERS/CONTINUATION writer path → `encKV` is called for each header field → because `VerboseLogs` (driven by the `GODEBUG=http2debug=1|2` env var) is on, the literal header value is passed to `log.Printf` and lands in the process's standard log output.

### Impact Explanation
Any credential carried in an HTTP header (bearer tokens, Basic-auth Base64 blobs, session cookies) is written in cleartext to whatever log sink the application uses whenever an operator sets `GODEBUG=http2debug=2` (or `1`) for troubleshooting — exactly the "debug-level logging enables credential leakage to logs" bug class described in the report. Anyone with read access to those logs can reuse the captured header to impersonate the client/server until the credential expires. This is a real, currently-live disclosure path in the supported HTTP/2 implementation (not vendored/test/mocked code), so it plausibly belongs on Go's PUBLIC track once independently confirmed, though it requires the operator to opt into the debug knob — it is not exploitable by a purely remote, unprivileged attacker without that local logging setting being enabled.

### Likelihood Explanation
The victim workflow is realistic: `GODEBUG=http2debug=1/2` is a genuine, user-facing Go debugging mechanism operators enable when diagnosing HTTP/2 issues in production or staging — analogous to enabling `debug`/`trace` logging in the Rust SDK. No attacker privilege beyond normal use of the service is needed; the only precondition is that the application's operator has turned on this debug flag, which is the same precondition as the original report (debug-level logging enabled).

### Recommendation
Redact or omit known-sensitive header names (`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`) in `encKV` (and the equivalent decode-side verbose logging path) before calling `log.Printf`, or replace the logged value with a fixed placeholder/length indicator when `VerboseLogs` is enabled.

### Proof of Concept
```go
package http2

import (
	"bytes"
	"log"
	"strings"
	"testing"

	"golang.org/x/net/http2/hpack"
)

func TestEncKVLeaksAuthorizationHeader(t *testing.T) {
	VerboseLogs = true
	defer func() { VerboseLogs = false }()

	var logBuf bytes.Buffer
	log.SetOutput(&logBuf)
	defer log.SetOutput(nil)

	var hbuf bytes.Buffer
	enc := hpack.NewEncoder(&hbuf)

	encKV(enc, "authorization", "Bearer sk-live-supersecrettoken123")

	if !strings.Contains(logBuf.String(), "supersecrettoken123") {
		t.Fatalf("expected authorization header value to appear in logs, got: %s", logBuf.String())
	}
}
```
Expected assertion result: the test passes, demonstrating that the literal `Authorization` header value is written to `log.Printf` output whenever `VerboseLogs` (driven by `GODEBUG=http2debug=1|2`) is enabled.

**Caveat / confidence note:** I was unable to fully trace whether an equivalent unguarded log statement exists on the HTTP/2 *decode* path (received headers) or in the client-side `transport.go` write path within the remaining tool budget — those files showed matches for `VerboseLogs`/`encKV` but I did not get to inspect their exact call sites before running out of iterations. The finding above is limited to the confirmed `encKV` sink in `write.go`, used by the server's outgoing-header encoder.

func encKV(enc *hpack.Encoder, k, v string) {
	if VerboseLogs {
		log.Printf("http2: server encoding header %q = %q", k, v)
	}
	enc.WriteField(hpack.HeaderField{Name: k, Value: v})
}
