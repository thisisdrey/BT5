### Title
Internal token supply is minted from the caller-reported `amount`, not the actual balance delivered, letting a non-standard NEP-141 token break custody conservation - (File: `contracts/defuse/src/contract/tokens/nep141/deposit.rs`)

### Summary
`ft_on_transfer` credits the depositor with exactly the `amount` value reported in the callback and mints that amount of internal MT balance, without ever verifying that the Defuse contract's real token balance increased by the same amount. For any non-standard NEP-141 token registered as a `TokenId::Nep141` (fee-on-transfer, rebasing, or "transfer-my-whole-balance" semantics such as cUSDCV3), this creates internal `total_supplies`/account balances that exceed the actual tokens the contract custodies.

### Finding Description
`ft_on_transfer` in `contracts/defuse/src/contract/tokens/nep141/deposit.rs` derives the `TokenId` from `env::predecessor_account_id()` and unconditionally calls `self.deposit(receiver_id, [(token_id, amount.0)], ...)`, minting `amount.0` internal shares: [1](#0-0) 

`Contract::deposit` in `contracts/defuse/src/contract/tokens/mod.rs` then increments `total_supplies` and the owner's `token_balances` by the raw `amount` parameter, with no comparison against the contract's actual `ft_balance_of` before/after the transfer: [2](#0-1) 

Because NEAR's `ft_transfer_call` flow only guarantees that `ft_on_transfer` is invoked with the `amount` that was *specified* in the transfer instruction — not necessarily the amount that was actually credited to the receiver's balance — a token contract with fee-on-transfer, rebasing, or `type(uint256).max`-style semantics can cause: `tokens actually received by Defuse < amount minted as internal shares`. This directly breaks the binding of "value debited versus value delivered plus refunded" for that `TokenId`'s pooled accounting: `total_supplies[token_id]` (claims against the contract) no longer equals the real custodied balance of that token contract held by Defuse. The same unchecked-mint pattern also exists in the NEP-245 deposit path (`mt_on_transfer`), which mints MT balances based on the `amounts` array reported by the calling contract: [3](#0-2) 

Note that the withdraw path (`ft_resolve_withdraw`) does correctly reconcile the promise's returned "used" amount before refunding, so the asymmetry is specific to deposits: [4](#0-3) 

### Impact Explanation
If any account with balance `token_balances[token_id]` derived from over-minted shares is later withdrawn via `ft_withdraw`, Defuse will attempt to `ft_transfer` more of that token than it actually holds, either draining the pooled balances of other legitimate holders of the same `TokenId` or causing withdrawals to fail once the shortfall is exposed — a concrete conservation-of-value violation ("total minted shares" vs "tokens actually custodied") rather than a griefing or DoS issue.

### Likelihood Explanation
Likelihood is Low: it requires the operator/relayer to register or route deposits through a NEP-141 contract that has fee-on-transfer, rebasing, or "max transfer" semantics rather than a standard, audited bridge/PoA token. Since Defuse is designed to accept arbitrary externally-controlled NEP-141 contracts as deposit assets (the `TokenId` is derived straight from `predecessor_account_id`), this is a reachable configuration risk rather than a purely theoretical one.

### Recommendation
Before minting internal shares in `deposit()`/`ft_on_transfer`/`mt_on_transfer`, compare the token contract's balance for the Defuse account before and after the transfer (or otherwise verify the actually-received amount) and mint only the delta, rather than trusting the caller-supplied `amount`. At minimum, clearly document that only tokens with standard, non-fee, non-rebasing NEP-141 semantics are safe to integrate, and gate token registration so operators are aware of this constraint.

### Proof of Concept
1. Deploy (or select) a NEP-141 token contract `T` that implements a transfer fee — e.g., `ft_transfer_call` deducts a 5% fee before invoking `ft_on_transfer`, but still reports the caller-specified `amount` (pre-fee) as the `amount` argument.
2. User calls `T.ft_transfer_call(defuse_id, 1000, "")`. `T` only credits Defuse's real balance with 950 tokens (after fee) but invokes `ft_on_transfer(sender, U128(1000), "")`.
3. `contracts/defuse/src/contract/tokens/nep141/deposit.rs::ft_on_transfer` calls `self.deposit(receiver_id, [(TokenId::Nep141(T), 1000)], ...)`, crediting the user 1000 internal MT shares for `T` while Defuse only custodies 950 real `T` tokens — `total_supplies[T] (1000) > actual T balance held by Defuse (950)`.
4. Repeating deposits/withdrawals against this inflated `total_supplies[T]` allows the depositor (or subsequent withdrawers) to withdraw more `T` than the contract holds, at the expense of other holders of `T`-denominated balances within Defuse.

            [(token_id.clone(), amount.0)],
            Some("deposit"),
        )

    fn ft_resolve_withdraw(
        &mut self,
        token: AccountId,
        sender_id: AccountId,
        amount: U128,
        is_call: bool,
    ) -> U128 {
        let used = if is_call {
            // `ft_transfer_call` returns successfully transferred amount
            match promise_result_checked_json::<U128>(0) {
                Ok(Ok(used)) => used.0.min(amount.0),
                Ok(Err(_deserialize_err)) => 0,
                // do not refund on failed `ft_transfer_call` due to
                // NEP-141 vulnerability: `ft_resolve_transfer` fails to
                // read result of `ft_on_transfer` due to insufficient gas
                Err(_) => amount.0,
            }
        } else {
            // `ft_transfer` returns empty result on success
            if promise_result_checked_void(0).is_ok() {
                amount.0
            } else {
                0
            }
        };

        let refund = amount.0.saturating_sub(used);
        if refund > 0 {
            self.deposit(
                sender_id,
                [(Nep141TokenId::new(token).into(), refund)],
                Some(REFUND_MEMO),
            )
            .unwrap_or_else(|err| err.panic());
        }

        U128(used)
    }
