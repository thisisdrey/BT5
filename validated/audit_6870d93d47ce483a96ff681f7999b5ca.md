## Local Analog Found

### Title
Contract termination (`refund_all`) sweeps *all* contributors' storage-deposit holds to a single beneficiary, bypassing per-contributor `NativeDepositOf` accounting - (File: `substrate/frame/revive/src/deposit_payment.rs`)

### Summary
`pallet-revive` tracks storage-deposit contributions per payer via `NativeDepositOf<T>` so that when a contract's storage shrinks, each contributor is refunded only up to what they personally paid. However, on contract termination the pallet calls `Deposit::refund_all`, which explicitly ignores this per-contributor cap and transfers the *entire* held balance (all contributors' deposits combined) to whichever single account is designated as the termination beneficiary/refund destination.

### Finding Description
Normal storage-deposit lifecycle (growing/shrinking storage) uses `refund_on_hold`, which caps the refund to `NativeDepositOf::<T>::get(from, to)` — i.e., it only ever returns to `to` what `to` actually contributed: [1](#0-0) 

Termination instead calls `refund_all`, whose doc comment and implementation explicitly bypass that cap: [2](#0-1) [3](#0-2) 

For the PGAS-backed backend the same pattern repeats — `refund_all` drains the full native hold via `<() as Deposit<T>>::refund_all` and the full PGAS hold via `settle_pgas_refund`, again to a single `dst`, with no per-contributor split: [4](#0-3) 

This is structurally identical to the GMX bug class in the report: normal entry points (regular storage charge/refund calls) correctly account for and return funds to the party that is actually owed them, but a separate, less-frequently-exercised entry point (contract termination) treats the commingled balance as a single lump sum and sends the *whole* thing to whoever triggers/benefits from that call, instead of the amount actually attributable to each depositor. The repository's own test suite documents this discrepancy as observed behavior: [5](#0-4) 

In that test, `CHARLIE` funds his own storage growth (creating a `NativeDepositOf[contract][CHARLIE]` entitlement), but when `ALICE` later terminates the contract, `ALICE` receives the combined native hold — i.e., Charlie's deposit is redirected to Alice via the termination path, even though Charlie never authorized or benefited from that transfer.

### Impact Explanation
Any account that can trigger a contract's self-destruct/terminate path (which contract code often permits broadly, e.g., an owner, or in adversarial contracts, anyone) captures other users' storage-deposit contributions in full. This is a wrong-beneficiary/fund-misdirection bug: value that is tracked per-contributor via `NativeDepositOf` is settled to a single unrelated party, violating the "settle exactly once to the rightful beneficiary and amount" invariant for contract-held value.

### Likelihood Explanation
This triggers deterministically whenever a contract has multiple contributors to its storage deposit (a common pattern — e.g., pooled/shared contracts, or any contract where different callers pay for their own storage growth) and is later terminated by any single caller. No privileged access, governance, or malicious infrastructure is required — only a normal multi-user contract interaction pattern followed by a standard `terminate` call, which is a public, unprivileged action gated only by whatever access control (if any) the contract itself imposes.

### Recommendation
`refund_all` should distribute the held balance proportionally (or exactly) according to the recorded `NativeDepositOf` entries for each contributor, rather than paying the entire sum to a single destination. At minimum, the pallet should iterate `NativeDepositOf::<T>::iter_prefix(contract)` and refund each contributor their own recorded contribution before allowing the remainder (if any, e.g. contract-owned dust) to go to the beneficiary, instead of applying the recipient-agnostic sweep currently implemented.

### Proof of Concept
Based on the existing regression test `refund_all_drains_multi_contributor_native_hold`: [6](#0-5) 
1. Deploy `MultiContributorStorage` contract.
2. `ALICE` calls `growStorage()` — she is charged and `NativeDepositOf[contract][ALICE]` is recorded.
3. `CHARLIE` calls `growStorage()` as a separate signed origin — he is charged and `NativeDepositOf[contract][CHARLIE]` is recorded.
4. `ALICE` calls `terminate(beneficiary)` — `refund_all` fires and the *entire* held native balance (Alice's + Charlie's contributions) is paid out to Alice (the tx origin/refund destination), even though Charlie's contribution was never owed to Alice.

Note: I was unable to fully trace, within the remaining tool budget, the exact host-function wiring in `exec.rs`/`vm` that determines who is passed as the `Funds` destination (`dst`) during `do_terminate` (e.g., whether it is always the extrinsic's tx origin or can be attacker-influenced via the contract-supplied `beneficiary` parameter). This detail affects exactly how broadly exploitable the misdirection is (self-inflicted vs. third-party theft), and should be verified in a full Devin session with repository access.

	fn refund_on_hold(
		reason: HoldReason,
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
		amount: BalanceOf<T>,
	) -> DispatchResult {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let contribution = NativeDepositOf::<T>::get(from, to);
		let native_requested = amount.min(contribution);

		let native_refunded = if !native_requested.is_zero() {
			<() as Deposit<T>>::refund_on_hold(reason, from, dst, native_requested)?;
			let new_val = contribution.saturating_sub(native_requested);
			if new_val.is_zero() {
				NativeDepositOf::<T>::remove(from, to);
			} else {
				NativeDepositOf::<T>::insert(from, to, new_val);
			}
			native_requested
		} else {
			BalanceOf::<T>::zero()
		};

	/// Refunds the full native hold to `dst` ignoring the per-contributor cap, then settles the
	/// PGAS hold via [`Self::settle_pgas_refund`] (refunding `RefundPercent` to `dst` and burning
	/// the rest). The native cap only makes sense for partial refunds on a live contract; at
	/// termination there is one recipient and the contract is gone.
	///
	/// Note: callers must run inside a storage layer so partial state rolls back on error.
	fn refund_all(
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
	) -> Result<BalanceOf<T>, DispatchError> {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let native = <() as Deposit<T>>::refund_all(from, dst)?;
		let reason = HoldReason::StorageDepositReserve;

		let pgas = Self::pgas_on_hold(reason, from);
		let pgas = Self::settle_pgas_refund(reason, from, to, pgas)?;
		Ok(native.saturating_add(pgas))
	}

/// A contract whose storage was paid for by two different signers, both via the native
/// fallback path, can still be terminated. [`Deposit::refund_all`] bypasses the per-payer
/// [`NativeDepositOf`] cap (one recipient at termination, contract gone), so the full native
/// hold goes to the terminator and any PGAS hold is settled via `settle_pgas_refund`.
#[test_case(FixtureType::Solc)]
#[test_case(FixtureType::Resolc)]
fn refund_all_drains_multi_contributor_native_hold(fixture_type: FixtureType) {
	let (code, _) = compile_module_with_type("MultiContributorStorage", fixture_type).unwrap();
	ExtBuilder::default().build().execute_with(|| {
		Balances::set_balance(&ALICE, 100_000_000_000);
		Balances::set_balance(&CHARLIE, 100_000_000_000);

		let Contract { addr, account_id } =
			builder::bare_instantiate(Code::Upload(code)).build_and_unwrap_contract();

		assert_ok!(
			builder::bare_call(addr)
				.data(MultiContributorStorage::growStorageCall {}.abi_encode())
				.build()
				.result,
		);
		assert_ok!(
			BareCallBuilder::<Test>::bare_call(RuntimeOrigin::signed(CHARLIE), addr)
				.data(MultiContributorStorage::growStorageCall {}.abi_encode())
				.build()
				.result,
		);

		let alice_entry = NativeDepositOf::<Test>::get(&account_id, &ALICE);
		let charlie_entry = NativeDepositOf::<Test>::get(&account_id, &CHARLIE);
		assert!(alice_entry > 0);
		assert!(charlie_entry > 0);

		let hold: <Test as Config>::RuntimeHoldReason = HoldReason::StorageDepositReserve.into();
		let native_held = Balances::balance_on_hold(&hold, &account_id);
		let pgas_held = AssetsHolder::balance_on_hold(PGAS_ASSET_ID, &hold, &account_id);
		assert_eq!(pgas_held, 0, "every charge fell back to native");
		assert_eq!(native_held, alice_entry + charlie_entry);

		let alice_before = Balances::balance(&ALICE);
		assert_ok!(
			builder::bare_call(addr)
				.data(
					MultiContributorStorage::terminateCall { beneficiary: DJANGO_ADDR.0.into() }
						.abi_encode(),
				)
				.build()
				.result,
		);
		let alice_after = Balances::balance(&ALICE);

		assert!(get_contract_checked(&addr).is_none(), "contract should be gone");
		assert_eq!(
			Balances::balance_on_hold(&hold, &account_id),
			0,
			"the full multi-contributor native hold has been released",
		);
		// ALICE receives the full storage-deposit hold (her own + CHARLIE's). The actual delta
		// also picks up the code-upload deposit refund and any tx-level deposit accounting,
		// so it is at least `native_held`.
		assert!(
			alice_after.saturating_sub(alice_before) >= native_held,
			"expected ALICE balance delta >= {}, got {}",
			native_held,
			alice_after.saturating_sub(alice_before),
		);
	});
}
