### Title
Potential index-out-of-range panic in TLS client certificate verification on empty `Certificate` message - ([File: src/crypto/tls/handshake_client.go])

### Summary
`(*Conn).verifyServerCertificate` in `src/crypto/tls/handshake_client.go` unconditionally accesses `certs[0]` and slices `certs[1:]` while building the intermediate pool and performing chain verification, without first checking that the parsed certificate slice is non-empty [1](#0-0) . This mirrors the reported bug class exactly: reading the first element of an attacker-influenced collection before validating that it actually contains elements.

### Finding Description
The TLS client calls `verifyServerCertificate(certificates [][]byte)` with the raw certificate list taken from the server's handshake `Certificate` message. The function builds `certs := make([]*x509.Certificate, len(certificates))` and parses each entry, but then — under both the ECH-rejected branch and the normal (`!InsecureSkipVerify`) branch — immediately does:
```go
for _, cert := range certs[1:] { opts.Intermediates.AddCert(cert) }
chains, err := certs[0].Verify(opts)
``` [2](#0-1) 
There is no `len(certs) == 0` guard before this. Even when `InsecureSkipVerify` is set, the subsequent type switch `switch certs[0].PublicKey.(type)` still dereferences index 0 [3](#0-2) . If the peer's handshake `Certificate` message contains zero certificate entries, `certs` is a zero-length slice and `certs[0]` triggers a runtime "index out of range" panic instead of a graceful handshake-failure error, analogous to the TensorFlow kernel dereferencing an empty tensor buffer without a size check.

### Impact Explanation
A crash (panic) in the TLS client's certificate-verification path is a denial-of-service against any Go program acting as a TLS client (e.g., an HTTP client) when the remote endpoint (or a network attacker able to inject handshake data before verification, e.g., an on-path attacker in the TLS handshake) sends a `Certificate` message with an empty certificate list. This maps to Go's PUBLIC/security track if reproducible against an unmodified, supported Go toolchain, since it is a remotely triggerable panic in a core `crypto/tls` code path.

### Likelihood Explanation
The victim workflow is any Go TLS client connecting to a remote server and performing normal certificate verification (default `InsecureSkipVerify=false`, or even with it set). The attacker capability required is the ability to control or manipulate the TLS handshake bytes reaching the client's `verifyServerCertificate`, i.e., malformed/adversarial handshake content — this is consistent with the allowed "TLS handshake/certificate" attacker input category. **However, I was not able to fully verify, within the available search budget, whether an earlier layer (handshake message parsing in `handshake_messages.go`, or the TLS 1.3 path in `handshake_client_tls13.go`) already rejects an empty `Certificate` list before `verifyServerCertificate` is invoked.** This is a material gap: real-world `crypto/tls` code historically enforces "server sent no certificate" checks at an earlier stage, which would make this path unreachable and this finding a false positive.

### Recommendation
Add an explicit `len(certs) == 0` (or `len(certificates) == 0`) check at the start of `verifyServerCertificate`, sending `alertCertificateRequired`/`alertHandshakeFailure` and returning a descriptive error (e.g., "tls: server sent no certificate") before any `certs[0]` access, mirroring the guard already present in the server-side `processCertsFromClient` (`if len(certs) == 0 && requiresClientCert(...)`) [4](#0-3) .

				c.sendAlert(alertBadCertificate)
				return fmt.Errorf("tls: server sent certificate containing RSA key larger than %d bits", max)
			}
		}
		certs[i] = cert
	}
