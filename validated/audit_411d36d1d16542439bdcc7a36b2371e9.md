### Title
Division by zero/near-zero `totalEnergyWeight` in TVM energy-limit calculation yields unbounded free energy or a node-crashing `ArithmeticException` - (File: `actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java`)

### Summary
This is the closest reachable analog to the GMI "zero total supply / uninitialized ratio denominator" bug. `RepositoryImpl.calculateGlobalEnergyLimit()` divides a caller-controlled numerator by the global `totalEnergyWeight` state variable without a real runtime guard — it only has a Java `assert`, which is a no-op in production builds (assertions are disabled unless the JVM is started with `-ea`, and this repo's configs don't enable it).

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit()` computes:
```
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
assert totalEnergyWeight > 0;
... divide(BigInteger.valueOf(totalEnergyWeight))   // hardened path
... energyWeight * ((double) totalEnergyLimit / totalEnergyWeight)  // legacy path
``` [1](#0-0) 

This is invoked from `VMActuator.getAccountEnergyLimitWithFloatRatio()` on every TVM contract call made by an account that has any energy frozen for itself (`totalBalanceForEnergyFreeze != 0`), to compute how much energy the caller can spend from its frozen-TRX allowance: [2](#0-1) 

This mirrors the GMI bug pattern exactly: the formula's denominator (`totalEnergyWeight`, analogous to `totalSupply`) is assumed always non-zero, and the only protection is an `assert` (compile-time/runtime no-op) rather than an explicit `if (totalEnergyWeight <= 0) return 0;` check like the one present in the equivalent chainbase-side implementation, `EnergyProcessor.calculateGlobalEnergyLimit()`, which does guard this case:
```
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
``` [3](#0-2) 

The VM-repository copy of this logic (`RepositoryImpl.calculateGlobalEnergyLimit`) omits that guard entirely, keeping only the ineffective `assert`.

### Impact Explanation
If `totalEnergyWeight` is ever zero (e.g. right after the last energy-freezer on chain fully unfreezes, or on a fresh/private/side chain before anyone freezes TRX for energy — a state directly reachable and controllable by an unprivileged actor who is the only account with frozen-for-energy balance and unfreezes it), any subsequent contract call by an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` will hit this path:
- In hardened mode (`allowHardenResourceCalculation`), `BigInteger.divide` by zero throws `ArithmeticException`, which is not caught anywhere between here and `VMActuator.call()` at this stage of the call path — an uncaught runtime exception in transaction execution can crash block application or, if caught generically elsewhere, unpredictably abort processing.
- In legacy (non-hardened) mode, `(double) totalEnergyLimit / 0` evaluates to `Infinity`, and casting that back to `long` yields `Long.MAX_VALUE`, granting the caller unlimited "free" energy for that TVM call — effectively bypassing energy metering/fee payment, analogous to the GMI bug where an unguarded zero-denominator formula produced an incorrect (here inverted — infinite instead of zero) result that breaks the economic invariant the calculation is meant to enforce.

### Likelihood Explanation
This requires `totalEnergyWeight == 0`, which is unlikely on an active mainnet with many stakers, but is a state that is directly reachable on any deployment (private chain, new sidechain, or a pathological state where all energy-freezers unfreeze) purely through standard, unprivileged `UnfreezeBalance`/`UnfreezeBalanceV2` transactions — no special privilege is required to drive `totalEnergyWeight` to zero, and any subsequent ordinary contract call transaction from an account with self-frozen energy would trigger the vulnerable code path.

### Recommendation
Add the same explicit zero/negative guard used in `EnergyProcessor.calculateGlobalEnergyLimit()` to `RepositoryImpl.calculateGlobalEnergyLimit()`:
```java
long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();
if (totalEnergyWeight <= 0) {
  return 0;
}
```
replacing the ineffective `assert totalEnergyWeight > 0;`, so behavior is deterministic and safe regardless of whether Java assertions are enabled.

### Proof of Concept
1. Deploy/operate a chain (or reach a state) where `totalEnergyWeight` becomes `0` (e.g. the sole account(s) with frozen-for-energy balance fully unfreeze via standard `UnfreezeBalanceV2Contract` transactions, driving `dynamicPropertiesStore.getTotalEnergyWeight()` to `0`).
2. As an unprivileged account, freeze at least `TRX_PRECISION` (1 TRX) for energy (`getAllFrozenBalanceForEnergy() >= TRX_PRECISION`).
3. Submit any smart-contract call transaction (`TriggerSmartContract`) from that account, exercising the non-fix-ratio energy path so `VMActuator.getAccountEnergyLimitWithFloatRatio()` → `RepositoryImpl.calculateGlobalEnergyLimit(account)` is invoked.
4. Observe either: (a) an uncaught `ArithmeticException` when hardened resource calculation is enabled, or (b) the caller receiving `Long.MAX_VALUE` worth of computed energy limit when it is disabled, allowing execution far beyond what their frozen TRX should back.

*Note: I could not fully trace every call site that reaches `getAccountEnergyLimitWithFloatRatio` vs. `getAccountEnergyLimitWithFixRatio` (e.g., which `VMConfig` flags select the float-ratio legacy path in the current default configuration) due to running out of search iterations; confirming the exact selection conditions and default flag values would require further inspection of `VMActuator.call()` and `VMConfig`.*

  public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
