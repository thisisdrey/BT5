Based on the code I traced in `stackslib/src/util_lib/bloom.rs`, the vulnerability described is real and directly reachable from an unauthenticated remote request.

### Title
Unbounded `num_hashes` field in `BloomFilter<BloomNodeHasher>::consensus_deserialize` enables CPU-exhaustion DoS via `/v2/mempool/query` - (File: stackslib/src/util_lib/bloom.rs)

### Summary
`BloomFilter<BloomNodeHasher>::consensus_deserialize` (L330-355) reads a raw `u32 num_hashes` from the wire with no upper bound check, and `insert_raw`/`contains_raw` (L283-318) then loop `0..self.num_hashes`, each iteration invoking `BloomNodeHasher::pick_bin` (L590-609), which performs a SipHash computation (plus a modulus-bias rejection loop). A remote, unauthenticated caller of the `POST /v2/mempool/query` RPC endpoint can supply `num_hashes = 0xFFFFFFFF` in a tiny (tens of bytes) `MemPoolSyncData::BloomFilter` payload, forcing billions of hash computations per mempool item examined, tying up the RPC-handling thread.

### Finding Description
The fault is: number of `pick_bin` invocations performed by `insert_raw`/`contains_raw` == the wire-supplied `num_hashes` field, with **no independent cap** anywhere in the deserialization path.

Path:
1. `RPCMempoolQueryRequestHandler::try_parse_request` in `stackslib/src/net/api/postmempoolquery.rs` (L248) calls `MemPoolSyncData::consensus_deserialize(&mut body_ptr)` directly on the raw HTTP POST body of `/v2/mempool/query`, with no additional validation of the bloom filter's internal parameters.
2. `MemPoolSyncData::BloomFilter` deserializes into `BloomFilter<BloomNodeHasher>` via the `StacksMessageCodec` impl at `bloom.rs` L330-355. This reads `seed` (32 bytes), `num_hashes: u32` (any value 0..=u32::MAX, unchecked), then `bits: BitField`. The only check performed is `bits.num_bits() == 0` (L339-343) — nothing bounds `num_hashes` relative to `bits.num_bits()` or any sane bloom-filter parameterization (contrast with `bloom_hash_count`, which is used only for locally-constructed filters, not enforced on deserialized ones).
3. The resulting `BloomFilter` is stored in `RPCMempoolQueryRequestHandler::mempool_query` and passed into `StacksMemPoolStream`, which is then queried via `MemPoolDB::static_find_next_missing_transactions` for each candidate transaction/page while streaming the mempool query response — this calls into `BloomFilter::contains_raw`/`BloomCounter` bloom-checks per row visited.
4. `contains_raw` (L303-318) and `insert_raw` (L283-300) both execute `for i in 0..self.num_hashes`, invoking `self.hasher.pick_bin(i, item, self.bits.num_bits())` per iteration — an attacker-controlled, effectively unbounded loop bound.
5. `pick_bin` (L590-609) does a SipHash-2-4 computation and a rejection-sampling `loop` that re-hashes on modulus bias; with a small `num_bins` (e.g., 8), the rejection probability is negligible (`u32::MAX % 8` is tiny relative to `u32::MAX`), so this doesn't add meaningfully to cost beyond one hash per outer iteration, but the outer iteration count itself (`num_hashes`) is the primary and sufficient amplification vector.

Existing guards do not prevent this: `MAX_MESSAGE_LEN`/body-length checks bound the *size* of the HTTP body, but `num_hashes` is a single 4-byte field independent of overall message length — a ~40-60 byte payload (seed + num_hashes=0xFFFFFFFF + a minimal `bits` field) is sufficient to set `num_hashes` to `u32::MAX`. There is no per-field cap on `num_hashes`, and `bloom_hash_count` (which computes sane `num_hashes` for locally-built filters) is never invoked to validate/bound a deserialized filter's `num_hashes`.

### Impact Explanation
A single small HTTP POST to `/v2/mempool/query` can force the node's mempool-query RPC-handling thread to perform on the order of `num_hashes` (up to ~4.29 billion) SipHash computations per bloom-membership test, and this test is invoked repeatedly as the stream walks mempool rows (`static_find_next_missing_transactions`) — multiplying the cost further by the number of mempool entries scanned. This ties up the handling thread/CPU for an extended, attacker-chosen duration from one unauthenticated request, and is trivially repeatable (send again, or from multiple connections) to sustain the exhaustion. This matches the "Critical – remote crash/unauthenticated DoS from few messages" and "bounded compute DoS on a read endpoint" impact categories, since `/v2/mempool/query` requires no authentication/secret and is reachable to any remote peer with access to the node's RPC port.

### Likelihood Explanation
- No privileged role or secret required: `/v2/mempool/query` is a public RPC endpoint reachable to any remote party who can connect to the node's RPC port.
- Attacker cost is minimal: a single ~50-byte crafted HTTP POST body.
- No node/peer state precondition is needed beyond the RPC port being up.
- Fully repeatable; can be sent repeatedly or in parallel to multiply effect across the RPC thread pool.

### Recommendation
In `BloomFilter<BloomNodeHasher>::consensus_deserialize` (`bloom.rs` L330-355), validate `num_hashes` against a sane upper bound derived from the bloom filter's own parameters (e.g., reject if `num_hashes` exceeds some small constant such as 32, or reject if `num_hashes` is inconsistent with what `bloom_hash_count` would produce for the given `bits.num_bits()` and a reasonable min error rate/max items). Alternatively, enforce a hard cap (e.g., `MAX_BLOOM_HASHES: u32 = 32`) checked immediately after reading `num_hashes`, returning `codec_error::DeserializeError` if exceeded — mirroring the existing `bits.num_bits() == 0` guard at L339-343.

    fn consensus_deserialize<R: Read>(
        fd: &mut R,
    ) -> Result<BloomFilter<BloomNodeHasher>, codec_error> {
        let hasher_type_u8: u8 = read_next(fd)?;
        match hasher_type_u8 as u8 {
            x if x == BloomHashID::BloomNodeHasher as u8 => {
                let seed: [u8; 32] = read_next(fd)?;
                let num_hashes: u32 = read_next(fd)?;
                let bits: BitField = read_next(fd)?;
                if bits.num_bits() == 0 {
                    return Err(codec_error::DeserializeError(
                        "Bloom filter must have non-zero bin count".into(),
                    ));
                }
                Ok(BloomFilter {
                    hasher: BloomNodeHasher { seed },
                    bits,
                    num_hashes,
                })
            }
            _ => Err(codec_error::DeserializeError(format!(
                "Not a supported bloom hasher type ID: {}",
                hasher_type_u8
            ))),
        }
    }

    fn pick_bin(&self, count: u32, data: &[u8], num_bins: u32) -> u32 {
        let mut initial_state = Vec::with_capacity(36 + data.len());
        initial_state.extend_from_slice(&count.to_be_bytes());
        initial_state.extend_from_slice(&self.seed);
        initial_state.extend_from_slice(data);

        let mut hasher = SipHasher::new();
        hasher.write(&initial_state);

        // be sure to remove modulus bias
        loop {
            let result_64 = hasher.finish();
            let result = (result_64 & 0x00000000ffffffff) as u32;
            if result < u32::MAX - (u32::MAX % num_bins) {
                return result % num_bins;
            } else {
                hasher.write_u64(result_64);
            }
        }
    }
