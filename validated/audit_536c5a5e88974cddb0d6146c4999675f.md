### Title
Non-hardened `ExchangeCapsule.transaction` path allows a TRC10 exchange pool to reach a state with zero or negative token balance while the other side still has liquidity - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` all validate that an exchange pool is usable by checking `firstTokenBalance == 0 || secondTokenBalance == 0` *before* execution, exactly like the LatentSwapLEX `_calculateMarketState` `baseTokenSupply == 0` guard described in the external report. However, the actual balance-mutation logic in `ExchangeCapsule.transaction()` only enforces a post-state invariant (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` → revert) when the pool is running in the "hardened" `SafeExchangeProcessor` mode. In the default (non-hardened) mode it uses `ExchangeProcessor`, which computes the new balances with double-precision floating point math and applies them unconditionally, with no post-trade invariant check.

### Finding Description
The exchange pool state transition is performed in `ExchangeCapsule.transaction()`: [1](#0-0) 

Only when `hardenedCalc` (i.e. `allowHardenExchangeCalculation()`) is true does the method check `newFirstTokenBalance < 0 || newSecondTokenBalance < 0` and throw `ContractValidateException`. When it is false (the historical/default code path, computed via `ExchangeProcessor`), no such check exists — the new balances are written to the capsule unconditionally: [2](#0-1) 

`ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` use `double` arithmetic and `Maths.pow`, so rounding can drive one side's balance to `0` (or, since results are cast with `(long) issuedSupply`/`(long) exchangeBalance`, potentially negative in edge cases) while the other side of the pool still holds a non-zero balance — the same "supply becomes 0 while the other side is non-zero" bad state the report describes for LatentSwapLEX's `baseTokenSupply`.

The three actuators only guard the *pre-trade* invariant via `firstTokenBalance == 0 || secondTokenBalance == 0` checks performed in `doValidate()`: [3](#0-2) [4](#0-3) [5](#0-4) 

But `execute()` calls `exchangeCapsule.transaction(...)` and immediately persists the result via `Commons.putExchangeCapsule(...)` without re-validating the resulting balances when not in hardened mode: [6](#0-5) 

So an attacker (any unprivileged account holding the traded token and paying the small fee) can craft a `ExchangeTransactionContract` (broadcast via a normal signed transaction, reachable through `Wallet`/gRPC) whose `quant` drives one side of the pool balance to exactly `0` via the floating-point calculation, while the other side retains a non-zero balance — permanently and irrecoverably closing/bricking that trading pair (all further `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` calls against it will hit the `firstTokenBalance == 0 || secondTokenBalance == 0` guard and revert with "the exchange has been closed"), stranding the remaining token balance recorded in the `Exchange` capsule with no path to withdraw it back out for the pool creator/LPs.

### Impact Explanation
This permanently freezes the residual asset balance recorded in the on-chain `Exchange`/`ExchangeV2` capsule for that market: once one side hits `0`, `ExchangeWithdrawActuator.doValidate()` rejects any further withdraw with "Token balance in exchange is equal with 0, the exchange has been closed", so the remaining non-zero side's balance can never be extracted by the pool's depositors. This is a fund-freezing bug matching the accepted High-impact class in the referenced report (bad/irrecoverable market state caused by a floating point edge case at one side's balance reaching zero while the other retains liquidity).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires the pool to be operating in the default (non-hardened) `ExchangeProcessor` mode and requires an attacker to find/target a trade size where floating-point rounding pushes a low-liquidity pool's balance to exactly zero (most feasible on TRC10 exchanges with very small remaining balances, analogous to the report's PoC that leaves "dust" amounts). This mirrors the report's own assessed Low likelihood / High impact rating for the analogous scenario.

### Recommendation
Apply the same post-trade invariant check used in the hardened path to the default `ExchangeProcessor` path as well: after computing `newFirstTokenBalance`/`newSecondTokenBalance`, reject (revert) the transaction if either becomes `<= 0` while the pool previously had non-zero balances on both sides, regardless of the `allowHardenExchangeCalculation` flag. Alternatively, deprecate/disable the non-hardened floating point `ExchangeProcessor` path entirely and always require the `SafeExchangeProcessor` invariant check.

### Proof of Concept
Not independently reproducible from static analysis alone — the described root cause (double-precision rounding in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` producing a balance of exactly `0` for one side while the other remains positive, with no invariant check outside `hardenedCalc` mode) is confirmed by code inspection of `ExchangeCapsule.transaction()` and `ExchangeProcessor`, but exact quant/balance values needed to trigger the exact zero-crossing were not derived here; a Devin session with test execution (mirroring `ExchangeCapsuleTest`/`ExchangeTransactionActuatorTest`) would be needed to construct a concrete numeric PoC.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
