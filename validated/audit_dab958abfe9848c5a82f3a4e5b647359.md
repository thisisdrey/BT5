Audit Report

## Title
Bounty/child-bounty claim silently deletes bounty state and reports success even when the reward-token transfer to a restricted beneficiary or curator fails - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`claim_bounty` and `claim_child_bounty` push-transfer bounty value/fee to the curator and beneficiary and only guard the `Result` with `debug_assert!`, which compiles to a no-op in release builds. If the underlying `T::Currency::transfer` call fails (e.g. beneficiary/curator blocked on a restrictable asset backing the currency), the extrinsic still deletes the bounty/child-bounty record and emits a `BountyClaimed`/`Claimed` success event.

## Finding Description
In `claim_bounty`, `T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath)` and `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` results are checked only via `debug_assert!(res.is_ok())`, then execution unconditionally proceeds to `*maybe_bounty = None`, `BountyDescriptions::<T, I>::remove(bounty_id)`, `T::ChildBountyManager::bounty_removed(bounty_id)`, and emits `Event::BountyClaimed`. [1](#0-0) 

The identical pattern exists in `claim_child_bounty`: `fee_transfer_result` and `payout_transfer_result` are checked only via `debug_assert!`, after which the `Claimed` event is emitted, `ParentChildBounties` count is decremented, the description is removed, and `*maybe_child_bounty = None` unconditionally. [2](#0-1) 

`T::Currency` in both pallets is inherited from `pallet_treasury::Config`'s generic `Currency` associated type (a `ReservableCurrency`/`Currency` trait bound), not hard-wired to `pallet_balances`. Since it is a trait, a runtime can supply any implementation, including adapters over assets that support freezing/blocking specific accounts. `debug_assert!` is stripped in release/production builds, so on a live chain the check is entirely absent — there is no `?`, `ensure!`, or rollback path if the transfer returns `Err`.

## Impact Explanation
If the transfer fails, the bounty/child-bounty record is deleted anyway, `BountyDescriptions`/`ChildBountyDescriptionsV1` are removed, and a public event asserts payout success while the funds remain stranded in the now-untracked `bounty_account`/`child_bounty_account` with no pallet-level way to retry or recover them. This is a permanent lock of treasury-derived funds and a mismatch between the emitted `BountyClaimed`/`Claimed` event and actual on-chain balance movement, matching the "payout state must only advance after ... settlement succeed atomically" and "permanent user-fund ... lock" impact criteria.

## Likelihood Explanation
This requires the runtime's treasury/bounty `Currency` implementation to be backed by a token capable of blocking a specific account (freeze/block), or another currency implementation returning `Err` for a valid-looking transfer. It does not require any privileged actor — an unprivileged claimant can trigger `claim_bounty`/`claim_child_bounty` via `ensure_signed(origin)?` (anyone can trigger claim), and the failure condition (target account blocked at the currency layer) is external to the pallet's own permission checks. Likelihood is dependent on runtime currency configuration, but the code path itself has no defense regardless of which currency is wired in.

## Recommendation
Replace `debug_assert!(res.is_ok())` with `res?` (or explicit `ensure!`/error propagation) in both `claim_bounty` and `claim_child_bounty` so any transfer failure aborts the extrinsic before any state mutation (`*maybe_bounty = None`, description removal, event emission). Alternatively, adopt the async payment/retry state machine pattern (`check_status`/`retry_payment`) already used elsewhere for handling payment failures without corrupting settlement state.

## Proof of Concept
1. Configure a test runtime with `pallet-treasury`'s `Currency` type set to an implementation over a blockable asset (e.g. a `fungible` adapter with freeze/block support).
2. Create, fund, and award a bounty to a `beneficiary`; propose/accept a curator.
3. Block/freeze the `beneficiary` account at the currency-implementation level so that `transfer` returns `Err`.
4. Call `claim_bounty(origin, bounty_id)`. In a release build, `debug_assert!(res.is_ok())` is compiled out, so despite the `Err` return, execution reaches `*maybe_bounty = None` and emits `Event::BountyClaimed { index: bounty_id, payout, beneficiary }`.
5. Assert: `Bounties::<T, I>::get(bounty_id)` returns `None` (state deleted) and `BountyClaimed` was emitted, while the actual balance of `bounty_account` still contains `payout` (funds not delivered) — demonstrating a permanent fund lock coupled with a false success event. The same steps apply to `claim_child_bounty` with `ChildBounties`/`Claimed`.
