### Title
Frequent `accrue()` calls round the treasury reserve fee (`reserve-inc`) down to zero, permanently denying protocol yield - ([File: mainnet/contracts/vault/v0-vault-usdc.clar] and equivalent code in all `v0-vault-*.clar` vaults)

### Summary
Every Zest vault (`v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) computes the treasury's cut of accrued borrower interest with an integer division (`mul-div-down`) that truncates toward zero, exactly the rounding pattern flagged in the external report for `mulDiv()`. Because `accrue()` is a public, unauthenticated function that can be invoked as often as desired, any address can force the interest that accrues per call to be small enough that the fee-reserve computation always rounds to `u0`, permanently starving the DAO treasury of its reserve-fee LP mint.

### Finding Description
`accrue()` in each vault computes the debt growth since `last-update`, and derives the treasury's share of that growth (`reserve-inc`) using truncating division: [1](#0-0) 

```clar
(old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
(new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
(debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
```

`mul-div-down` is defined as plain truncating multiply-then-divide: [2](#0-1) 

`debt-delta` is proportional to elapsed time since `last-update` (via `next-index`, which uses `time-delta = stacks-block-time - last-update` and the interest rate): [3](#0-2) 

`accrue()` itself has **no caller authorization check** — unlike `system-borrow`/`system-repay`, which call `(try! (check-caller-auth))`, the accrue logic only checks the pause flag: [4](#0-3) 

Because `reserve-inc = debt-delta * fee-reserve / BPS` (with `BPS = 10000`), whenever `debt-delta * fee-reserve < 10000` the division truncates to `0`, exactly the "mulDiv rounds to 0" pattern from the report (`makerInfo.eachTradeTax / EACH_TRADE_TAX_DECIMAL_SCALER` analog). By calling `accrue()` on every block (or in rapid succession) instead of letting interest accumulate over a longer interval, `time-delta` — and therefore `debt-delta` per call — stays small. An attacker (or simply any user/bot, since the call is free-to-call and unauthenticated) can keep the reserve fee under the truncation threshold indefinitely, so `reserve-inc` is `0` on every call, `treasury-lp` never mints, and `last-update`/`index`/`lindex` still advance (so the underlying interest is not lost to borrowers/lenders — only the treasury's cut is skipped).

This differs from the report's tax-avoidance case only in mechanism (repeated micro-accruals instead of a single micro-trade), but the root cause — integer division of a percentage fee that truncates to zero for small enough numerators — is identical, and it is fully reachable by an ordinary, unprivileged principal calling a public entry point (`accrue()`), which is also invoked implicitly on every deposit/redeem/borrow/repay path in these vaults.

### Impact Explanation
The treasury's reserve fee represents the protocol's/DAO's claim on interest accrued by borrowers — this is unclaimed protocol yield. By keeping every `accrue()` call's `debt-delta` below the truncation threshold, this yield is permanently skipped rather than merely delayed: once `index`/`lindex`/`last-update` have been advanced by a zero-fee accrual, the corresponding interest slice is baked into the index without the treasury's mint ever having occurred, and it cannot be recovered retroactively. This matches the in-scope impact "High — theft of unclaimed yield" (permanent denial of the treasury's share of interest).

### Likelihood Explanation
`accrue()` is public and unauthenticated (no `check-caller-auth`), costs only the calling gas/fee, and does not require any privileged role, flashloan, DAO compromise, or oracle manipulation. Any bot can trivially call it every block/period to keep `debt-delta` tiny across the vault's lifetime, making this both cheap and highly automatable, hence practically likely to occur if not actively front-run/mitigated.

### Recommendation
Accumulate the un-minted fractional remainder of `reserve-inc` across accrual calls instead of discarding it (e.g., track a `fee-reserve-dust` accumulator and add it back into the next `debt-delta * fee-reserve` computation before dividing by `BPS`), or use `mul-div-up` for the fee portion so at least 1 unit is never systematically dropped when `debt-delta > 0`. Alternatively, require a minimum elapsed `time-delta` before minting `treasury-lp`, or perform the fee computation over accumulated `debt-delta` since the last successful treasury mint rather than resetting per call.

### Proof of Concept
1. Deploy/observe `v0-vault-usdc.clar` with `fee-reserve` set (e.g. `500` bps = 5%) and an active borrow so `total-borrowed > 0`.
2. Instead of letting one block/period elapse before calling `accrue()`, call `accrue()` on every single block (`stacks-block-time - last-update` = one block's worth of time each call).
3. For each call, `next-index` advances by a multiplier proportional to that tiny `time-delta`; `debt-delta = new-debt - old-debt` becomes correspondingly tiny.
4. Compute `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)`. For sufficiently small `debt-delta` (any `debt-delta * fee-reserve < 10000`), `reserve-inc` truncates to `u0`, so `(if (> reserve-inc u0) ... u0)` skips the `ft-mint? zft treasury-lp .dao-treasury` branch entirely (`mainnet/contracts/vault/v0-vault-usdc.clar:847-848,855-857`), while `index`/`lindex`/`last-update` still advance.
5. Repeating this every block over the vault's lifetime means the treasury's `fee-reserve` share of interest is never minted, even though the same interest, accrued in fewer/larger `accrue()` calls, would have produced non-zero `treasury-lp` mints.
