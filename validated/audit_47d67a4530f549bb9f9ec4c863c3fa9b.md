## Title
Missing bounds validation in ZIP central‑directory entry parsing allows out‑of‑bounds read of untrusted archive content - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads the per-entry `file_name_length`, `extra_field_length`, and `file_comment_length` fields directly from the memory-mapped ZIP/JAR bytes and advances the cursor `p` by these attacker-controlled values, and separately walks a `header_id`/`data_size` extra-field loop, all **without any bounds check against the mapped file's actual length**. This mirrors the CVE-2023-38428 bug class: a length/offset value taken from untrusted input is trusted and used to compute a read location without validating it against the real buffer extent, causing an out-of-bounds read.

### Finding Description
`ProcessCentralDirEntry` is used by ijar (the interface-jar stripping tool that runs on every `.jar` consumed by `java_library`, including third-party/Maven jars fetched over HTTP) to walk the ZIP central directory of an input jar: [1](#0-0) 

`file_name_length`, `extra_field_length`, and `file_comment_length` are read straight from the mapped bytes and used to advance `p` and to bound a `memcpy` into a fixed `filename[PATH_MAX]` buffer — but only the destination buffer size is checked, not whether `p + file_name_length` etc. actually remains inside the mapped file.

The subsequent extra-field walk is worse: it reads a 2‑byte `data_size` from attacker data and advances `extra_p` by it with no upper bound check at all: [2](#0-1) 

By contrast, the sibling function `ProcessLocalFileEntry`, which parses the local file header for the *same* file, explicitly guards every read with `EnsureRemaining()`: [3](#0-2) [4](#0-3) 

The only global containment check performed before iterating entries is that the *aggregate* central directory (`central_dir_offset + central_dir_size`) fits inside the file, in `FindZipCentralDirectory`: [5](#0-4) 

That check does not validate that any individual entry's declared `file_name_length`/`extra_field_length`/`file_comment_length` (or the extra-field `data_size` chain) stays within the central directory region or the mapped file. A crafted central directory entry can declare lengths that push `p`/`extra_p` past the end of the `mmap`'d region, so the next `get_u4le/get_u2le` in `ProcessCentralDirEntry` (called again on `ProcessNext`) or the `memcpy` into `filename` reads adjacent process memory beyond the mapped file.

The code's own comment acknowledges the false assumption: "Note that the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — this is only true for a well-formed file, not for a maliciously crafted one.

### Impact Explanation
A hostile jar author (e.g., publishing a malicious artifact at a `http_jar`/`http_file`/Maven dependency URL, or via an untrusted branch that CI builds) fully controls the byte content, including whatever checksum the victim's build pins — the checksum only proves the bytes match what the attacker authored, it does not validate their structural safety. Once ijar strips such a jar (a routine action for any Java dependency), the out-of-bounds read can crash the build (SIGSEGV on unmapped pages) or leak adjacent heap/mapped memory into the `filename` buffer, which is then passed to `processor->Accept()`/`Process()` and can end up embedded in generated interface-jar entry names or error diagnostics.

### Likelihood Explanation
ijar's central-directory parser runs on every jar processed as part of normal `java_library`/`java_import` builds, with no opt-in required, and the archive's byte content is entirely attacker-controlled and un-sandboxed input data (not root-repo Starlark). No credentials or extra privileges are needed beyond publishing/serving the jar. This makes the class readily reachable by any unprivileged attacker able to place a malicious jar at a URL a build depends on.

### Recommendation
Add explicit bounds checks in `ProcessCentralDirEntry` (mirroring `EnsureRemaining` in `ProcessLocalFileEntry`) before consuming `file_name_length`, `extra_field_length`, `file_comment_length`, and before/while iterating the extra-field `(header_id, data_size)` chain, rejecting the entry if the declared lengths would advance `p`/`extra_p` past the mapped file end.

### Proof of Concept
A `BuildIntegrationTestCase`/JUnit-style proof:
1. Construct a minimal valid ZIP/JAR with one central directory entry whose `file_name_length` (or `extra_field_length`) is set to a large value (e.g. `0xFFFF`) while the actual mapped file ends shortly after the header, and/or an extra field with `data_size` chained to run past the buffer end.
2. Feed this file to `devtools_ijar::ZipExtractor::Create()` / `ProcessAll()` (as ijar's real entry point does).
3. Observe that `ProcessCentralDirEntry` reads/`memcpy`s past the end of the `mmap`'d region (detectable under ASan as heap/mmap buffer-overflow-read, or via a guard page causing SIGSEGV), whereas an equivalent malformed local-file-header path is safely rejected by `EnsureRemaining`.
