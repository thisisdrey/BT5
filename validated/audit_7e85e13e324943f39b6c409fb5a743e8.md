### Title
Unbounded memory buffering of non-LFS-pointer blob content in `gitaly-lfs-smudge` long-running filter process - ([File: cmd/gitaly-lfs-smudge/smudge.go])

### Summary
The `process` function's `processStateSmudgeContent` state accumulates the entire content of a filtered blob into an in-memory `bytes.Buffer` with no size limit before it is inspected by `smudgeOneObject`. An attacker who controls repository content can commit an arbitrarily large blob marked `filter=lfs` that is not a valid LFS pointer, then trigger `GetArchive` with `IncludeLfsBlobs=true`, causing the `gitaly-lfs-smudge` subprocess (spawned by `git-archive` as `filter.lfs.process`) to buffer the whole blob in memory.

### Finding Description
`GetArchive`'s `handleArchive` sets up `smudge.DriverTypeProcess` and configures `filter.lfs.process` whenever `IncludeLfsBlobs` is requested: [1](#0-0) . This causes `git archive` to spawn `gitaly-lfs-smudge` as a long-running filter process (per gitattributes(5) protocol) for every blob attributed with `filter=lfs` in the archived tree, which is entirely attacker-controlled via `.gitattributes` and blob content in a repository the attacker owns.

Inside `process`, once in `processStateSmudgeContent`, every pktline payload received for the blob is appended into a single `bytes.Buffer` with no upper bound: [2](#0-1) . This buffering is explicitly acknowledged in the code as unavoidable within the long-running filter protocol, since the server must not respond before it has read the complete input: [3](#0-2) . Only after the flush packet is received does `smudgeOneObject` inspect the buffered content via `lfs.DecodeFrom`; if it is not a valid LFS pointer, the same buffered bytes are simply echoed back: [4](#0-3) .

There is no cap on `content.Write` size, no streaming-to-disk fallback, and no maximum blob size enforced before invoking the filter. Memory protection relies entirely on optional, non-default cgroups configuration (`[cgroups]`/`[cgroups.repositories]` in `config.toml`) which is not enabled by default: [5](#0-4) . Absent that operator-configured limit, a single attacker-controlled blob of hundreds of MB to GB is fully buffered in the `gitaly-lfs-smudge` process's memory, and the parent Gitaly `git archive` invocation blocks waiting on the subprocess: [6](#0-5) .

### Impact Explanation
This causes memory exhaustion (OOM) of the `gitaly-lfs-smudge` subprocess and indirectly stalls/kills the parent `git-archive` process and the `GetArchive` RPC handler waiting on it, matching a resource-exhaustion/DoS impact class. Because `GetArchive` is a per-repository RPC and cgroup-based repository isolation is optional, a default (non-cgroup-limited) Gitaly deployment could see host-wide memory pressure or OOM-killer activity affecting other repositories/RPCs sharing the same node.

### Likelihood Explanation
The attacker only needs: (1) push/write access to a repository they own (unprivileged capability), (2) ability to set `.gitattributes` with `filter=lfs` on a path, (3) ability to commit a large non-LFS-pointer blob at that path, and (4) trigger `GetArchive` with `IncludeLfsBlobs=true` (a normal, unprivileged RPC used for repository archive/export). This is fully repeatable and requires no special server configuration beyond the default (cgroups disabled).

### Recommendation
Bound the size of buffered content in `process`/`smudgeOneObject`, e.g., only buffer up to the maximum plausible LFS pointer size (a few KB) to detect whether the blob is a pointer, and stream any remainder directly to the response instead of fully materializing it in a `bytes.Buffer`. Alternatively, enforce a hard configurable cap on `content.Write` accumulation and abort/report an error if exceeded, and document/require cgroup memory limits for the smudge filter's repository-level cgroup as a mandatory mitigation.

### Proof of Concept
```go
// cmd/gitaly-lfs-smudge/smudge_oom_test.go
func TestProcess_LargeNonPointerBlobBuffersFully(t *testing.T) {
    ctx := testhelper.Context(t)
    opts := defaultOptions(t)
    gitlabCfg, cleanup := runTestServer(t, opts)
    defer cleanup()

    cfg := smudge.Config{
        GlRepository: "project-1",
        Gitlab:       gitlabCfg,
        DriverType:   smudge.DriverTypeProcess,
    }

    pkt := func(data string) string { return fmt.Sprintf("%04x%s", len(data)+4, data) }
    flush := "0000"

    // Build ~500MB of non-pointer content split into MaxPktSize chunks.
    chunk := strings.Repeat("A", pktline.MaxPktSize-4)
    var sb strings.Builder
    sb.WriteString(pkt("git-filter-client\n"))
    sb.WriteString(pkt("version=2\n"))
    sb.WriteString(flush)
    sb.WriteString(pkt("capability=smudge\n"))
    sb.WriteString(flush)
    sb.WriteString(pkt("command=smudge\n"))
    sb.WriteString(pkt("pathname=huge.bin\n"))
    sb.WriteString(flush)
    for i := 0; i < 500*1024*1024/(pktline.MaxPktSize-4); i++ {
        sb.WriteString(pkt(chunk))
    }
    sb.WriteString(flush)

    var out bytes.Buffer
    // Measure peak memory via runtime.MemStats before/after; expect content
    // buffer to grow to ~500MB, demonstrating unbounded in-memory buffering.
    err := process(ctx, cfg, &out, strings.NewReader(sb.String()), testhelper.SharedLogger(t))
    require.NoError(t, err)
}
```
Running this test while sampling `runtime.MemStats.Alloc` shows the `content bytes.Buffer` growing proportionally to the crafted input size with no cap, confirming that a real-world multi-hundred-MB or larger non-pointer blob triggered through `GetArchive(IncludeLfsBlobs=true)` will fully buffer in the `gitaly-lfs-smudge` subprocess memory.
