### Title
Non-constant-time comparison of the RPC `authorization` header enables a remote timing side-channel to recover the shared `auth_token` - (File: `stackslib/src/net/api/blockreplay.rs`, `postblock_v3.rs`, `txsimulate.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, `postblock_proposal.rs`)

### Summary
Every privileged Stacks node RPC endpoint that gates access behind `connection_options.auth_token` compares the client-supplied `Authorization` header to the configured secret using Rust's default `!=`/`==` string comparison, which is not constant-time. An unprivileged remote attacker can exploit the resulting timing discrepancy to recover the secret token byte-by-byte, exactly analogous to the SilverStripe CMS timing side-channel (CVE-2017-12849) in which a response-time discrepancy on login/password-reset comparisons let an attacker enumerate valid credentials.

### Finding Description
Each of the following handlers implements `try_parse_request` and checks the client-presented token against the configured secret with a plain inequality operator: [1](#0-0) [2](#0-1) [3](#0-2) 

The same pattern (`auth_header != password`) also appears in `blocksimulate.rs`, `fastcallreadonly.rs`, and `postblock_proposal.rs`, all guarded the same way. Rust's `str`/`String` `PartialEq` implementation compares lengths first and then performs a byte-wise `memcmp`-style comparison that returns as soon as a mismatching byte is found (or uses vectorized comparison that still exits early on long mismatched runs). This means:
- A guess that is correct for its first N bytes takes measurably longer to reject than a guess wrong at byte 0.
- Because the check happens before any expensive work (`try_parse_request` returns immediately with `401` on mismatch), the elapsed round-trip time is dominated by this comparison, making the signal easier to observe over the network than in cases involving heavier request processing.

This is the direct structural analog of GHSA-fwhr-g5r4-xgxf/CVE-2017-12849: a security-relevant string equality check (there: username/password; here: bearer token) whose timing leaks information about how much of the secret the attacker already guessed correctly, letting the true secret be reconstructed via repeated queries without ever needing to know it in advance.

### Impact Explanation
`auth_token` is the single secret gating: broadcasting or replaying arbitrary Nakamoto blocks (`postblock_v3.rs`, `blockreplay.rs`), simulating transactions/blocks against node state (`txsimulate.rs`, `blocksimulate.rs`), unmetered read-only contract calls (`fastcallreadonly.rs`), and, most critically, `/v3/block_proposal` — the channel a `stacks-signer` uses to submit block proposals for validation (`postblock_proposal.rs`). Recovering this token via a remote timing attack allows a fully unauthenticated remote attacker to eventually authenticate as a trusted signer/operator and reach the privileged behaviors these endpoints guard (broadcasting attacker-controlled blocks, submitting block proposals, etc.), which constitutes an auth-bypass condition — one of the explicitly accepted impact categories.

### Likelihood Explanation
The comparison is on the earliest, cheapest code path of the request handler (before any parsing of body/block data), which minimizes noise from unrelated processing and makes the timing signal comparatively clean over a LAN or low-jitter network. No credentials, prior access, or non-default configuration are required — only that `auth_token` is configured (the normal deployment posture for nodes that serve a `stacks-signer`). The attack requires many requests to average out network jitter (statistical timing analysis), consistent with the original CVE's technique, and does not rely on volumetric traffic to succeed — it exploits the specific byte-position information leak, not sheer connection volume.

### Recommendation
Replace the ad-hoc `!=`/`==` comparisons in `blockreplay.rs`, `postblock_v3.rs`, `txsimulate.rs`, `blocksimulate.rs`, `fastcallreadonly.rs`, and `postblock_proposal.rs` with a constant-time comparison (e.g., the `subtle` crate's `ConstantTimeEq`, or an HMAC-based comparison) for validating the `authorization` header against `auth_token`. Ideally, centralize this check into a single shared helper in `net/httpcore.rs` or `net/http.rs` used by all authenticated handlers, to avoid re-introducing the discrepancy per endpoint.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3CR3T-TOKEN-VALUE"` and enable one of the affected endpoints (e.g., `/v3/tenures/replay/<block_id>` via `blockreplay.rs`).
2. From a remote unprivileged client, iterate over candidate first bytes of the token (`"A"`, `"B"`, … ) sending each as the `authorization` header value while padding the rest, measuring response latency for the immediate `401 Unauthorized` many times per candidate to average out jitter.
3. The candidate whose correct-byte-prefix is longest will show a statistically higher average latency than incorrect candidates, since the internal string comparison advances further before returning `false`.
4. Repeat byte-by-byte, extending the confirmed prefix each round, to fully reconstruct `auth_token` without ever needing it beforehand, then use the recovered token to access privileged endpoints such as `/v3/block_proposal` or `broadcast=1` on `/v3/blocks`.
