### Title
Rounding to zero in `MarketSellAssetActuator.matchSingleOrder()` "taker == maker" branch lets a taker drain a resting order's tokens without paying - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` implements TRC10 order matching. When a taker order exactly consumes a maker's remaining sell quantity ("taker == maker" branch), the amount the maker receives is computed via integer division (`MarketUtils.multiplyAndDivide`), which can floor to `0`. Unlike the sibling "taker > maker" branch, which explicitly checks `makerBuyTokenQuantityReceive == 0` and refunds the maker if so, the "taker == maker" branch performs **no such check**, so it transfers the maker's entire remaining token balance to the taker while crediting the maker with zero payment.

### Finding Description
In `matchSingleOrder`: [1](#0-0) 

```
if (takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()) {
  // taker == maker
  makerBuyTokenQuantityReceive = MarketUtils
      .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity, ...);
  takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

  long takerSellTokenLeft =
      takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
  takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
  makerOrderCapsule.setSellTokenQuantityRemain(0);
  ...
}
```

`multiplyAndDivide` performs `floor(a*b/c)` and can legitimately return `0`: [2](#0-1) 

If `makerBuyTokenQuantityReceive` rounds to `0`:
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` → taker's sell-side balance is **not decremented**, so the taker pays nothing.
- `takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain()` (the maker's full remaining balance) is credited to the taker via `addTrxOrToken`.
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` closes out the maker's order with zero proceeds.

Compare this to the sibling "taker > maker" branch, which explicitly guards against this exact rounding condition: [3](#0-2) 

The presence of an explicit zero-check and refund logic (`returnSellTokenRemain`) in the "taker > maker" branch, with a code comment explaining why the zero case "would not happen" there, indicates the developers were aware of and specifically handled this rounding hazard for one branch — but omitted the equivalent protection in the "taker == maker" branch, leaving it exploitable. This directly mirrors the UToken `redeem()` root cause: a computed "amount owed" rounds to zero due to integer division, but the corresponding "amount transferred out" is still executed at full value.

### Impact Explanation
A taker can construct a `MarketSellAssetContract` transaction (`sellTokenId`, `sellTokenQuantity`, `buyTokenId`, `buyTokenQuantity`) such that, when matched against an existing resting maker order (whose exact remaining quantity is publicly readable from `MarketPairPriceToOrderStore`/`MarketOrderStore`), the "taker == maker" branch triggers and `makerBuyTokenQuantityReceive` rounds to `0`. The attacker then receives the maker's full remaining TRC10/TRX balance for that order while their own sell-side balance is left untouched (they pay nothing). This is unauthorized extraction of another account's escrowed exchange funds — a direct theft of user funds reachable via a single signed transaction (`MarketSellAssetContract`) processed by `MarketSellAssetActuator`, satisfying the "theft of funds" impact bar.

### Likelihood Explanation
The attacker (taker) fully controls `sellTokenQuantity`/`buyTokenQuantity` in their own contract and can read the maker's exact remaining order size and price from on-chain state before submitting the transaction, so triggering the "taker == maker" equality condition and the zero-rounding condition is a matter of solving small integer constraints, which is feasible for at least a subset of price ratios and remaining quantities (particularly when `makerSellQuantity > makerBuyQuantity`, i.e., the maker is selling many units for few). No special privileges are required — this is exploitable by any account with a small trade order and one open resting maker order to target.

### Recommendation
Add the same zero-quantity guard used in the "taker > maker" branch to the "taker == maker" branch: if `makerBuyTokenQuantityReceive == 0`, return the maker's remaining sell tokens to the maker (via `MarketUtils.returnSellTokenRemain`) instead of transferring them to the taker for free, and mark the order inactive without crediting the taker with `takerBuyTokenQuantityReceive`. Alternatively, revert/skip the match instead of consuming the maker's order when the computed maker proceeds are zero, consistent with the other branch's protective pattern.

### Proof of Concept
Conceptual PoC (exact numeric ratios need to be brute-forced/verified in a local devnet, since spacing of achievable integer targets depends on `gcd(makerSellQuantity, makerBuyQuantity)`):
1. Victim (or attacker's second account) places a maker order via `MarketSellAssetContract` selling token A for token B with `sellTokenQuantity = S`, `buyTokenQuantity = B` where `S > B` (cheap-A/expensive-B price ratio), leaving it resting in the order book with some remaining quantity `R` (`R` can be the full original order or a naturally-occurring partial-fill remainder).
2. Attacker reads `R`, `S`, `B` from `MarketOrderStore`/`MarketPairPriceToOrderStore`.
3. Attacker submits a taker `MarketSellAssetContract` selling token B for token A with `sellTokenQuantity = a` chosen so that `floor(a*S/B) == R` (satisfies the "taker == maker" branch condition in `matchSingleOrder`), and such that `floor(R*B/S) == 0` (satisfies the round-to-zero condition for `makerBuyTokenQuantityReceive`).
4. Upon `matchOrder`/`matchSingleOrder` execution, the attacker's `takerOrderCapsule.sellTokenQuantityRemain` is left unchanged (no B spent), while the attacker receives `R` units of token A (`addTrxOrToken`) that belonged to the maker's escrowed order, and the maker's order is closed with zero proceeds — confirming unauthorized fund extraction.

Note: I could not execute this against a live node/testnet within this analysis to confirm concrete numeric parameters that satisfy both congruence conditions simultaneously; this would need to be validated with a script solving the two floor-division constraints (or exhaustive small-value search) in a Devin session with build/test tooling.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);
      return floorDiv(tmp, c, disableMath);
    } catch (ArithmeticException ex) {
      // do nothing here, because we will use BigInteger to compute again
    }

    BigInteger aBig = BigInteger.valueOf(a);
    BigInteger bBig = BigInteger.valueOf(b);
    BigInteger cBig = BigInteger.valueOf(c);

    return aBig.multiply(bBig).divide(cBig).longValue();
  }
