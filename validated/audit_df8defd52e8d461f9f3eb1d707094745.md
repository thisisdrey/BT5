Based on my research, I found a strong analog: the newly added TIP-2935 `HistoryBlockHashUtil.deploy()` path, invoked from `ProposalService.process()` during maintenance-time proposal activation, silently converts a pre-existing ordinary account at a fixed, publicly-known address into a system contract account and wipes its delegated-resource bookkeeping — a path any unprivileged user can pre-position funds/delegations into before the type change occurs.

### Title
Unauthorized destruction of delegated-resource records when TIP-2935 system contract is installed over a pre-existing user account - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.deploy()` is called from `ProposalService.process()` when the `ALLOW_TVM_PRAGUE` proposal is activated [1](#0-0) . It installs the TIP-2935 `BlockHashHistory` system contract at a fixed, publicly known address (`HISTORY_STORAGE_ADDRESS = 0x0000f90827f1c53a10cb7a02335b175320002935` in TRON's 21-byte form) [2](#0-1) . If an account already exists at that address (which any unprivileged user can create simply by sending TRX or delegating resources to it, as the code's own comment acknowledges), `deploy()` mutates it in place to `AccountType.Contract` and calls `account.clearDelegatedResource()` before persisting it, discarding delegation bookkeeping rather than settling it [3](#0-2) .

### Finding Description
Because `HISTORY_STORAGE_ADDRESS` is a fixed constant known ahead of activation, any unprivileged account holder can, prior to the `ALLOW_TVM_PRAGUE` proposal being enacted, use ordinary signed transactions (`FreezeBalanceV2Contract`/`DelegateResourceContract`, or a simple TRX transfer) to place a normal account with delegated/frozen resources at that address — the code comment explicitly calls this "the common case" [4](#0-3) . When the proposal is later activated during maintenance-time block processing, `deploy()` unconditionally calls `updateAccountType(Contract)` and `clearDelegatedResource()` on the pre-existing account and persists it to the `AccountStore`, mirroring the same discard-without-settlement pattern used for genuine `CREATE2` address collisions in `Program.createContractImpl` [5](#0-4) . In the `CREATE2` path this is an accepted, narrow edge case (attacker must brute-force a hash preimage to land on a specific address). Here, by contrast, the target address is a **fixed constant known in advance to every network participant**, so any user (or a third party delegating resources *to* that address on someone else's behalf) can trivially pre-position resource delegations that will later be wiped by a routine, deterministic system upgrade rather than by an adversarial hash-collision attempt.

### Impact Explanation
Delegated/frozen TRX resource records tied to the pre-existing account at `HISTORY_STORAGE_ADDRESS` are discarded by `clearDelegatedResource()` without any repayment or unfreeze accounting once the account is converted to `AccountType.Contract`. Anyone who froze TRX for bandwidth/energy and delegated it to this specific address (or had it delegated to them there) loses the ability to reclaim that resource/balance through the normal `UnDelegateResourceContract`/`UnfreezeBalanceV2Contract` flow, since the underlying account record has been overwritten. This matches the "permanent freezing of funds" impact class.

### Likelihood Explanation
The trigger condition — the committee activating `ALLOW_TVM_PRAGUE` — is a normal, expected one-time chain upgrade event, not an adversarial action, so it will occur on every affected network. Populating the target address ahead of time requires only ordinary, unprivileged transactions (`FreezeBalanceV2Contract`, `DelegateResourceContract`, or a plain transfer) sent by any account, with no special privilege, timing race, or brute-force computation required, since the destination address is a compile-time constant [2](#0-1) . This makes the setup step trivially reachable by any unprivileged transaction broadcaster.

### Recommendation
Before converting a pre-existing account at `HISTORY_STORAGE_ADDRESS` to `AccountType.Contract`, `deploy()` should detect and properly settle (rather than silently clear) any outstanding delegated-resource state — e.g., by returning delegated balances to their original owners via the standard un-delegate accounting path, or by refusing to install the system contract in place (falling back to the "foreign state" skip branch already used for code/contract collisions) whenever the account has non-empty delegation records, frozen balance, or other user-owned state.

### Proof of Concept
1. Before the `ALLOW_TVM_PRAGUE` proposal is activated on-chain, an unprivileged account `A` sends a `DelegateResourceContract` (or `FreezeBalanceV2Contract`) transaction that freezes TRX and delegates energy/bandwidth to the constant address `410000f90827f1c53a10cb7a02335b175320002935`.
2. The committee later approves and activates the `ALLOW_TVM_PRAGUE` proposal (a normal, expected governance action).
3. During maintenance-time processing, `ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)` [1](#0-0) .
4. `deploy()` finds the account already exists (created in step 1), sets its type to `Contract`, and calls `account.clearDelegatedResource()`, then persists the account [6](#0-5) .
5. Account `A`'s delegation record to that address is gone; the frozen TRX cannot be un-delegated/unfrozen through the normal contract flow, permanently locking those funds.

Note: I was unable to directly inspect the body of `AccountCapsule.clearDelegatedResource()` before running out of tool calls, so the exact bookkeeping fields it clears (and whether any partial settlement occurs) should be verified directly in `chainbase/src/main/java/org/tron/core/capsule/AccountCapsule.java` to confirm the full extent of fund loss versus mere record clearing.
