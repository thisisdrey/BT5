### Title
Unvalidated enum-derived contract-type index causes uncaught out-of-bounds exception during transaction permission verification - ([File: chainbase/src/main/java/org/tron/common/utils/WalletUtil.java])

### Summary
`WalletUtil.checkPermissionOperations` computes a bit-index into a fixed 32-byte `Permission.operations` bitmap using `contract.getTypeValue()` — the *raw* protobuf enum wire value of `Transaction.Contract.type` — without validating that it falls in the expected `0–255` range. This mirrors the CVE-2017-11600 root cause: an attacker-controlled "selector"/`dir`-like value taken directly from a message is used to index a fixed-size structure without a bounds check, allowing an out-of-range access.

### Finding Description
`checkPermissionOperations` is: [1](#0-0) 

```java
public static boolean checkPermissionOperations(Permission permission, Contract contract)
    throws PermissionException {
  ByteString operations = permission.getOperations();
  if (operations.size() != 32) {
    throw new PermissionException(...);
  }
  int contractType = contract.getTypeValue();
  boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
  return b;
}
```

`operations.size()` is fixed at 32 bytes (256 bits), so a valid `contractType` must be within `0..255`. However, `contract.getTypeValue()` returns the *unvalidated* raw int32 stored on the wire for the `ContractType type = 1;` enum field of `Transaction.Contract` [2](#0-1) 
Because protobuf-generated Java code exposes both the typed enum accessor (`getType()`, which maps out-of-range values to `UNRECOGNIZED`) and the raw accessor (`getTypeValue()`, which returns the actual wire integer including negative or arbitrarily large values, e.g. `Integer.MIN_VALUE` or `1_000_000`), a transaction crafted with an arbitrary `type` field value bypasses the enum's implicit range restriction at this call site. `contractType / 8` can then be negative or ≥ 32, causing `ByteString.byteAt(...)` to throw `ArrayIndexOutOfBoundsException`/`IndexOutOfBoundsException`.

This is reached from a fully attacker-controlled, unprivileged path: `checkPermissionOperations` is invoked from `TransactionCapsule.checkPermission` [3](#0-2) 
which is called from `validateSignature` [4](#0-3) 
whenever `permissionId != 0`, itself invoked from `validatePubSignature` [5](#0-4) 
The `catch` clause there only handles `SignatureException | PermissionException | SignatureFormatException` — an `IndexOutOfBoundsException` thrown from `byteAt` is **not caught** and propagates unhandled up the call stack (transaction verification path executed for every incoming/broadcast transaction with a non-zero `permission_id`).

### Impact Explanation
An unauthenticated network peer or API client can submit a transaction that sets `raw_data.contract[0].permission_id` to a non-zero value and crafts the `contract[0].type` field (via raw protobuf serialization, not the SDK) to an out-of-range integer (negative, or ≥ 256). When the node attempts to verify the transaction's multi-sig permission, the uncaught `IndexOutOfBoundsException` will surface during transaction validation. Depending on where in the pipeline this exception is thrown (e.g. mempool ingestion, block application), an uncaught runtime exception here can disrupt transaction processing for that node — a potential denial-of-service condition on the transaction-verification path, analogous to the OOB access in the CVE.

### Likelihood Explanation
Reachability requires only building a raw transaction with a crafted (non-enum-conformant) `type` field and a non-zero `permission_id`, and broadcasting it — no special privilege, no multi-sig setup, no witness/committee/SR role needed. This makes it directly reachable by any transaction broadcaster.

### Recommendation
Bound-check `contractType` before indexing: reject/short-circuit (or treat as non-matching) whenever `contractType < 0 || contractType >= operations.size() * 8` in both `WalletUtil.checkPermissionOperations` and the duplicate implementation in `TransactionUtil.checkPermissionOperations` [6](#0-5) 
and ensure any exception thrown from operations-bitmap checks is properly wrapped/caught along the `validatePubSignature`/`validateSignature` call chain.

### Proof of Concept
1. Construct a `Transaction` whose `raw_data.contract` list contains one `Contract` with:
   - `permission_id = 2` (non-zero, forcing the `checkPermissionOperations` path)
   - `type` field serialized on the wire as a large/negative int32 not corresponding to any declared `ContractType` value (e.g. `100000` or `-5`), which protobuf will surface via `contract.getTypeValue()` as that literal integer while `getType()` reports `UNRECOGNIZED`.
2. Sign the transaction with a key that is valid for permission id 2 on an existing account (or an account whose default active permission has id 2).
3. Broadcast the transaction to a full node.
4. During `TransactionCapsule.validatePubSignature` → `validateSignature` → `checkPermission` → `WalletUtil.checkPermissionOperations`, `operations.byteAt(contractType / 8)` is invoked with an out-of-range index, throwing an uncaught `IndexOutOfBoundsException` that is not handled by the surrounding `catch (SignatureException | PermissionException | SignatureFormatException e)` block.

Note: I was not able to trace, within the available index, the exact top-level exception handler (e.g., in `Manager` or gRPC/HTTP transaction-broadcast servicing code) that ultimately catches or fails to catch this specific `IndexOutOfBoundsException`, so the precise blast radius (single-request failure vs. broader service disruption) could not be fully confirmed from the indexed code alone.

      }

      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");

    if (weight >= permission.getThreshold()) {

  public boolean validatePubSignature(AccountStore accountStore,
      DynamicPropertiesStore dynamicPropertiesStore)
      throws ValidateSignatureException {
    if (!isVerified) {
      if (this.transaction.getSignatureCount() <= 0
              || this.transaction.getRawData().getContractCount() <= 0) {
        throw new ValidateSignatureException("miss sig or contract");
      }
      if (this.transaction.getSignatureCount() > dynamicPropertiesStore
              .getTotalSignNum()) {
        throw new ValidateSignatureException("too many signatures");
      }

      byte[] hash = getTransactionId().getBytes();

      long startNs = System.nanoTime();
      try {
        if (!validateSignature(this.transaction, hash, accountStore, dynamicPropertiesStore)) {
          isVerified = false;
          throw new ValidateSignatureException("sig error");
        }
      } catch (SignatureException | PermissionException | SignatureFormatException e) {
        isVerified = false;
        throw new ValidateSignatureException(e.getMessage());
      } finally {
        logSlowSigVerify(startNs);
      }
      isVerified = true;
    }
    return true;
  }
