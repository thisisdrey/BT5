### Title
`DebtToken.burn` skips `accrueInterest()`, storing accrued debt against a stale `debtIndex` and double-counting interest - ([File: contracts/DebtToken.sol](contracts/DebtToken.sol))

### Summary
This is a direct analog of the missing `_updateSupply` bug class: a state-mutating function updates balances while leaving a dependent accounting variable stale. `DebtToken.burn()` — the `onlyPool` entry point reached via `Pool.liquidate` — never calls `accrueInterest()` before mutating `principalOf`, `debtIndexOf`, and `totalSupply_`. Every other debt-mutating path (`issue`, `repay`, `repayAll`, `mint`, `flashIssue`, `updateInterestRate`) accrues first; `burn` does not.

### Finding Description
In `_burn`, the current debt is computed via `balanceOf(account_)`, which applies a freshly calculated (unpersisted) `debtIndex` from `_calculateInterestAccrual()`:

```solidity
// contracts/DebtToken.sol:528-534
uint256 _accountBalance = balanceOf(account_);        // principal * freshIndex / debtIndexOf
if (_accountBalance < amount_) revert BurnAmountExceedsBalance();
unchecked {
    principalOf[account_] = _accountBalance - amount_; // already includes accrued interest
    debtIndexOf[account_] = debtIndex;                 // STALE stored index, not the accrued one
    totalSupply_ -= amount_;
}
```

Because `accrueInterest()` was never called, the stored `debtIndex` still reflects `lastTimestampAccrued` from an earlier block, while `principalOf` is rebased to a value that already contains the interest accrued since then. On the next `balanceOf`, the contract computes `principalOf * newIndex / staleIndex`, applying the same elapsed interest a second time.

`totalSupply_` is also decremented by an amount that includes interest that was never written into `totalSupply_` (it is only added inside `accrueInterest` at line 170). The stored supply therefore drifts downward relative to the sum of principals — the same "supply not synced with updated balances" invariant break described in the report.

### Impact Explanation
- The liquidated account's remaining debt is overstated by a factor of `currentIndex / staleIndex` — i.e., all interest accrued since the last accrual is charged twice. This inflates the victim's outstanding debt, worsens their debt position, and causes over-seizure on subsequent repayments/liquidations — a direct loss to the user and inflated protocol claims (insolvency-accounting break in the user's favor only for the protocol, i.e., user funds extracted).
- `totalSupply_` becomes inconsistent with the sum of `principalOf`, corrupting subsequent interest accrual (`_interestAmountAccrued = rate.wadMul(totalSupply_)`) and any supply-cap or quote logic that reads it.

### Likelihood Explanation
`burn` is `onlyPool`, so the trigger path is any public `Pool.liquidate` call (or any other Pool path that calls `debtToken.burn` without first calling `accrueInterest`). Any unprivileged liquidator can invoke liquidation on an unhealthy account once time has passed since the last accrual on that debt token — a near-certain condition in production since accrual only happens on debt-token interactions. Caveat: validity requires confirming `Pool.liquidate` does not itself call `debtToken.accrueInterest()` before `burn`; I was not able to read the `Pool.sol` call sites within the search budget (grep returned match counts only). If `liquidate` accrues first, the stale-index window collapses and the finding reduces to an accounting edge case.

### Recommendation
Call `accrueInterest()` at the top of `burn()` (or at the start of `_burn`) so `debtIndex`, `totalSupply_`, and `lastTimestampAccrued` are synced before `principalOf`/`debtIndexOf` are rewritten — mirroring the report's fix of adding `_updateSupply` inside `updateWeights`:

```diff
function burn(address from_, uint256 amount_) external override onlyPool {
+    accrueInterest();
    _burn(from_, amount_);
}
```

### Proof of Concept
Hardhat fork sketch:

1. Deploy pool with a `DebtToken` at nonzero `interestRate`; alice deposits collateral and issues synth (this writes `debtIndexOf[alice] = debtIndex`).
2. Advance time so interest accrues virtually (`balanceOf(alice)` grows, but stored `debtIndex`/`totalSupply_` are unchanged because no interaction calls `accrueInterest`).
3. Drop collateral price (or manipulate oracle quote in the same tx) so alice is liquidatable; call `Pool.liquidate` from an unprivileged liquidator, which reaches `debtToken.burn(alice, amount)`.
4. Observe inside `_burn`: `principalOf[alice]` is set to `balanceOf(alice) - amount` (interest-inclusive) while `debtIndexOf[alice]` is set to the stale `debtIndex`.
5. Advance time again and read `balanceOf(alice)`: it equals `(principal - amount) * newIndex / staleIndex`, exceeding the correct remaining debt by the factor `indexAtBurn / staleIndex`. `totalSupply()` is likewise less than `Σ balanceOf` by the burned interest portion.

Confirm in step 3 that `Pool.liquidate` does not invoke `DebtToken.accrueInterest()`; if it does, the PoC will not reproduce.
