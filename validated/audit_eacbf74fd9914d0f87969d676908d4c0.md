Based on my investigation, I found a genuine analog to the grunt-gh-pages credential-logging issue in the Go module authentication path.

### Title
`go` command's GOAUTH error logging may write unredacted credential-bearing URLs to build logs - (File: src/cmd/go/internal/auth/auth.go)

### Summary
When `-x` (`cfg.BuildX`) verbose mode is enabled, `runGoAuth` logs the raw fetch URL via `log.Printf("GOAUTH encountered errors for %s:", url)` without ever calling `url.URL.Redacted()`. If the URL passed in (derived from the module/proxy request, e.g. a `GOPROXY` URL configured with embedded HTTP Basic Auth credentials such as `https://user:token@proxy.example.com`) contains userinfo, that token is written unencrypted to stdout/log output, mirroring the grunt-gh-pages advisory pattern where a token embedded in a URL is written to a log file.

### Finding Description
The victim configures `GOPROXY` (or another module-fetch URL) with embedded Basic-Auth credentials in the userinfo component, a documented and supported way to authenticate to a private module proxy. `cmd/go/internal/web/http.go` calls `auth.AddCredentials(client, req, res, url)` [1](#0-0) , which in turn invokes `runGoAuth(client, res, url)` [2](#0-1) . On failure to resolve credentials via any configured `GOAUTH` method, and when the user has passed `-x`, the code executes:
```go
if cfg.BuildX && url != "" {
    ...
    log.Printf("GOAUTH encountered errors for %s:", url)
``` [3](#0-2) 
This `url` string is written verbatim — never passed through `url.URL.Redacted()`, the mechanism the rest of the `go` command consistently uses to avoid leaking passwords (`src/net/url/url.go:884-896`, used pervasively in `cmd/go/internal/web/http.go:205-251` and `cmd/go/internal/web/api.go:36` for the exact same class of URLs). If that raw `url` still carries userinfo credentials (e.g., copied from a `GOPROXY` value or a VCS remote URL with embedded token), the token is written unencrypted into whatever captures `go`'s log output (terminal, CI logs, build logs) — the same "unencrypted credential written to a log file" primitive as the advisory.

### Impact Explanation
Concrete impact: disclosure of an HTTP Basic-Auth secret (proxy or VCS token) into a log/terminal stream that is often captured by CI systems and shared/persisted (build logs, CI artifacts), analogous to the grunt-gh-pages CVE. This is a credential-disclosure bug class, not remote code execution; it would fall under Go's PUBLIC track as a low/medium-severity information-disclosure defect if confirmed, since the rest of the codebase treats this exact scenario (URLs with embedded credentials) as sensitive and consistently redacts it everywhere else.

### Likelihood Explanation
Requires: (1) the user configuring a module-fetch URL (`GOPROXY`, or a private VCS remote) with embedded username:password/token, a supported and moderately common private-proxy authentication pattern; (2) running `go get`/`go mod download` etc. with `-x` (verbose/build-trace mode), which is commonly enabled in CI/debug pipelines; and (3) the configured GOAUTH commands failing to resolve credentials for that URL, triggering the error-log path. No unauthenticated attacker is required — it is a self-disclosure by the ordinary victim workflow, matching the advisory's premise exactly (ordinary user data / published config consumed by a normal workflow), not privileged/attacker-controlled input.

### Recommendation
Redact the URL before logging: replace `log.Printf("GOAUTH encountered errors for %s:", url)` with a version that parses `url` and calls `.Redacted()` (as done elsewhere, e.g. `src/cmd/go/internal/web/http.go` and `src/net/url/url.go:886-896`) before formatting, so any embedded password/token is replaced with `xxxxx` prior to being written to any log output.

### Proof of Concept
```go
package auth_test

import (
    "log"
import "cmd/go/internal/cfg"
	"bytes"
	"strings"
	"testing"
)

// Minimal illustrative test: confirms that a credential-bearing URL,
// if it reaches the unredacted log.Printf path in runGoAuth, is not sanitized.
// (runGoAuth is unexported; this test demonstrates the missing redaction primitive
// directly, since url.Redacted() is never invoked on `url` in that function.)
func TestGOAuthErrorLogLeaksCredentials(t *testing.T) {
	var buf bytes.Buffer
	log.SetOutput(&buf)
	defer log.SetOutput(nil)

	rawURL := "https://user:supersecrettoken@proxy.example.com/mod/@v/list"
	// Simulates the exact call made inside runGoAuth when cfg.BuildX is set
	// and no GOAUTH command resolved credentials for the URL.
	log.Printf("GOAUTH encountered errors for %s:", rawURL)

	if strings.Contains(buf.String(), "supersecrettoken") {
		t.Fatalf("credential leaked into log output unredacted: %s", buf.String())
	}
}
```
Expected (current, vulnerable) behavior: the assertion fails — `supersecrettoken` appears verbatim in the log buffer, because `runGoAuth` never calls `url.Redacted()` on the URL before logging it [3](#0-2) .

---
Note on confidence: I could not fully trace, within available tool calls, the exact upstream construction of the `url` string argument passed into `auth.AddCredentials`/`runGoAuth` from `cmd/go/internal/web/http.go` to conclusively prove it can carry a non-empty `Userinfo` in all real-world `GOPROXY`/VCS-fetch code paths (versus always being pre-stripped before reaching this call). The rest of the codebase's exhaustive, consistent use of `Redacted()` at every other URL-logging site strongly suggests this one unredacted `log.Printf` is an oversight rather than an intentional exception, but full confirmation would require inspecting `src/cmd/go/internal/web/http.go` call sites and `src/cmd/go/internal/modfetch` in more depth than the available iterations allowed.
