### Title
Unbounded attacker-controlled array index in `ValidateMultiSign` precompile causes out-of-bounds read / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract computes an array index from raw, attacker-supplied calldata offsets without validating that the resulting index is within the bounds of the `words` array, mirroring the FreeRDP `urb_select_interface` bug class (server/attacker-supplied value used directly as an array index without a bounds check).

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute`, the input `rawData` is parsed into a `DataWord[] words` array via `DataWord.parseArray(rawData)` [1](#0-0) 
and then, under the `VMConfig.allowTvmSelfdestructRestriction()` branch, the code computes:
```
int sigArraySize = words[words[3].intValueSafe() / WORD_SIZE].intValueSafe();
``` [2](#0-1) 
`words[3]` is fully attacker-controlled (it is the ABI-encoded "offset" field of the precompile call parameters supplied by whatever contract/transaction invokes address `0x...66` via `CALL`/`STATICCALL`). The code divides this attacker-controlled value by `WORD_SIZE` and uses the result directly as an index into `words` with no check that `words[3].intValueSafe() / WORD_SIZE < words.length`. Because this precompile is reachable from any TVM contract call (`TriggerSmartContract`) that an unprivileged account can broadcast, an attacker can supply a crafted offset value that produces an index far beyond the actual `words` array length, immediately throwing an uncaught `ArrayIndexOutOfBoundsException` inside `execute`.

The subsequent lines that build `signatures` via `extractSigArray`/`extractBytesArray` (also indexed by `words[3].intValueSafe() / WORD_SIZE`) compound the same unchecked-index problem.

This matches the FreeRDP root cause precisely: a value taken directly from untrusted input is used as an index into an array with no bounds validation, causing an out-of-bounds access.

### Impact Explanation
An `ArrayIndexOutOfBoundsException` thrown from inside a precompiled contract's `execute()` is a `RuntimeException`. Precompile execution is invoked from the TVM's `Program.callToPrecompiledAddress`/opcode-dispatch path; if this exception is not caught specifically at the precompile call site (unlike ordinary EVM exceptions that are translated into a revert), it can propagate up as an unexpected runtime failure during block application in `Manager`, since transaction execution for `TriggerSmartContract` happens as part of normal block processing for every full node. Any full node that processes a transaction calling this precompile with the crafted offset would experience this uncaught exception during contract execution. Depending on how far up the call stack the exception is caught, this is either swallowed as a contract revert (denial of the smart-contract call only) or, if not handled at the appropriate boundary, can cause inconsistent execution results between nodes that differ in JVM/array behavior — but at minimum it is a reliable way to force abnormal termination of contract execution paths reachable by any anonymous, unprivileged transaction broadcaster, satisfying the "node crash/halt" or "no-impact API" impact bar depending on whether it is caught. This is directly reachable by a single signed `TriggerSmartContract` transaction from any account with enough energy — no special privilege required.

### Likelihood Explanation
High reachability: `ValidateMultiSign` is a standard precompiled contract address callable by any deployed smart contract via `CALL`, and any account can deploy a trivial contract or trigger an existing one that calls this precompile with attacker-chosen calldata. Constructing calldata where `words[3]` (the offset field) is a large value that produces `words[3]/WORD_SIZE >= words.length` is straightforward ABI encoding, requiring no special conditions beyond enough energy to pay for the call.

### Recommendation
Add an explicit bounds check before using `words[3].intValueSafe() / WORD_SIZE` as an index into `words`, e.g.:
```java
int sigOffsetWordIndex = words[3].intValueSafe() / WORD_SIZE;
if (sigOffsetWordIndex < 0 || sigOffsetWordIndex >= words.length) {
  return Pair.of(true, DATA_FALSE);
}
int sigArraySize = words[sigOffsetWordIndex].intValueSafe();
```
Apply the same bounds validation inside `extractSigArray`/`extractBytesArray` before indexing `words`, and ensure `words.length` is checked to be at least the minimum expected header size (`ABI_HEADER_WORDS`) prior to accessing `words[0]`..`words[3]` at all, independent of `isValidAbiEncoding`.

### Proof of Concept
1. Deploy a minimal contract (or use an existing one) that performs a `staticcall`/`call` to the `ValidateMultiSign` precompile address with hand-crafted ABI-encoded parameters: `address`, `permissionId`, `data` (32-byte hash), and a 4th word (`offset`) set to a very large value such as `0xFFFFFFFF` (or any value whose `/32` quotient exceeds the number of decoded words).
2. Ensure `VMConfig.allowTvmSelfdestructRestriction()` is enabled on the target chain (a governance-controlled feature flag; already active on many production TRON networks).
3. Broadcast the `TriggerSmartContract` transaction invoking this call.
4. Node execution reaches `words[words[3].intValueSafe() / WORD_SIZE]` in `PrecompiledContracts.ValidateMultiSign.execute`, and since the computed index exceeds `words.length`, an `ArrayIndexOutOfBoundsException` is thrown from inside precompile execution.

Note: I was unable to fully trace, within the available tool budget, whether the outer TVM dispatch (`Program`/precompile invocation wrapper) catches generic `RuntimeException`/`ArrayIndexOutOfBoundsException` uniformly for all precompiles the same way it does for opcode execution in `VM.play` (which does catch `RuntimeException` broadly). If it is caught and converted to a plain revert, the impact is downgraded to "no impact beyond a reverted transaction" for that specific call. Confirming whether precompile-level exceptions are covered by the same top-level `catch (RuntimeException e)` in `VM.play` (as shown for opcode execution) would require reviewing `Program`'s precompiled-contract invocation code path directly, which was not retrieved in this session — this is a limitation of the current investigation and should be verified in a Devin session with full file access before treating this as a confirmed node-crash vector versus a reachable revert-only bug.
