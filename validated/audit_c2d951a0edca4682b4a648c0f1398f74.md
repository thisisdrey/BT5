Audit Report

## Title
Unchecked `Currency::transfer` in `claim_bounty` / `claim_child_bounty` permits permanent fund loss on award payout - ([File: substrate/frame/bounties/src/lib.rs] / [File: substrate/frame/child-bounties/src/lib.rs])

## Summary
`claim_bounty` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs`) perform final payout `T::Currency::transfer(..., AllowDeath)` calls to the curator and to a beneficiary chosen freely by the curator in `award_bounty`, but only guard the result with `debug_assert!`, which is a no-op in release builds. If the beneficiary is a fresh, unfunded account and the computed `payout`/`final_fee`/`curator_fee` is below `ExistentialDeposit`, the transfer fails silently, yet the code unconditionally proceeds to delete the bounty/child-bounty storage (`*maybe_bounty = None` / `*maybe_child_bounty = None`) and emit a "claimed" event as if payment succeeded.

## Finding Description
In `claim_bounty` [1](#0-0) , the code computes `final_fee` and `payout`, transfers them via `AllowDeath`, checks the result only with `debug_assert!(res.is_ok())`, then sets `*maybe_bounty = None` and emits `Event::BountyClaimed` regardless of whether the transfers actually succeeded. The equivalent pattern exists in `claim_child_bounty` [2](#0-1) .

The beneficiary is freely chosen by the curator with no ED/existence validation, as seen in `award_bounty` [3](#0-2) ; `accept_curator`'s `T::Currency::reserve(curator, deposit)?` only guarantees the curator's own reserved balance, not anything about a subsequently-chosen beneficiary's account [4](#0-3) .

The claim that `debug_assert!` is compiled out in release builds and that transfers to non-existent accounts below `ExistentialDeposit` fail is independently verified in the balances pallet: `deposit_creating`/`try_mutate_account` logic enforces `ensure!(value >= ed || !is_new, Error::<T, I>::ExistentialDeposit)` [5](#0-4) , and a corresponding balances test confirms this behavior: `Balances::transfer_allow_death(Some(1).into(), 5, 9)` fails with `TokenError::BelowMinimum` when the destination is new and the amount is below ED [6](#0-5) .

Once the transfer fails in a release build, the `debug_assert!` does nothing, execution continues, and the bounty/child-bounty index is deleted — removing the only storage reference to the sub-account's earmarked funds — while a `Claimed`/`BountyClaimed` event falsely reports successful payout.

## Impact Explanation
This directly matches the "permanent user-fund lock" and "duplicate/incorrect settlement" categories in the impact gate. Funds allocated to a beneficiary or curator can become permanently stranded in an orphaned bounty/child-bounty sub-account with no remaining code path (no bounty index, no retry/cancel/re-award mechanism) to recover them, while the chain state falsely records the payout as completed via the emitted event.

## Likelihood Explanation
This is reachable through the pallet's standard, permissionless public API without any privileged, malicious-peer, or leaked-key assumptions. A curator sets an arbitrary `fee` bounded only by `<= value`, and nominates any `beneficiary` AccountId in `award_bounty` — including a never-before-funded address. It is a routine and realistic outcome for the final computed `payout` or `final_fee`/`curator_fee` for that address to fall under `ExistentialDeposit`, especially for small bounties or bounties with many child bounties reducing the residual `final_fee`. Anyone can then trigger `claim_bounty`/`claim_child_bounty` since these calls are open to any signed account (`ensure_signed(origin)?; // anyone can trigger claim`) [7](#0-6) .

## Recommendation
Replace the `debug_assert!` checks in `claim_bounty` and `claim_child_bounty` with proper `?`/`ensure!`-based error propagation so a failed transfer aborts the claim and leaves bounty/child-bounty storage intact, only clearing state after all transfers return `Ok`. Alternatively, use ED-safe deposit semantics or top up destination accounts before finalizing removal of state. Add regression tests covering a beneficiary/curator account that does not exist and whose computed payout is below `ExistentialDeposit`.

## Proof of Concept
1. Governance approves a bounty, funding the bounty sub-account with `value`; a curator is proposed with `fee = ExistentialDeposit - 1` (or a value that, minus any `children_fee`, nets a `final_fee`/`payout` below ED).
2. Curator calls `accept_curator`, reserving only `curator_deposit` from their own balance.
3. Curator calls `award_bounty` naming a brand-new `beneficiary` AccountId that has never held a balance, structured so the computed `payout` for that account is below `ExistentialDeposit`.
4. After `unlock_at`, any signed account calls `claim_bounty` (or `claim_child_bounty`).
5. In a release build (`debug-assertions = false`), `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(Error::ExistentialDeposit)` per balances-pallet semantics, but `debug_assert!(res.is_ok())` is compiled out and does nothing.
6. Execution proceeds: `*maybe_bounty = None` deletes the bounty, `BountyDescriptions` is removed, and `Event::BountyClaimed { payout, beneficiary }` is emitted despite the beneficiary never receiving funds.
7. The plancks remain permanently stranded in the now-orphaned bounty sub-account with no bounty index left to retry, cancel, or reclaim them.
