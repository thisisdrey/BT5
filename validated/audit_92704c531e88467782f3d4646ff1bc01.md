### Title
Remote fee for Snowbridge messages can round to zero, letting users get Ethereum relayer rewards funded for free - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
`Pallet::calculate_fee` in `bridges/snowbridge/pallets/outbound-queue/src/lib.rs` computes the DOT-denominated remote fee a message sender must pay to cover gas refunds and relayer rewards on Ethereum. The computation chains multiple integer divisions/conversions (`fee_per_gas * gas_used + reward` → `FixedU128` scale/exchange-rate conversion → `convert_from_ether_decimals`), and when the resulting wei amount is small relative to the ether/DOT decimal conversion factor, the final `remote` fee rounds down to zero even though the message still carries a non-zero `reward` that Ethereum-side relayers are promised. This mirrors the Velar Sherlock finding: sequential integer division causes real economic value ("funding fee"/"remote fee") to be reported and charged as zero while the underlying obligation persists.

### Finding Description
`calculate_fee` (bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393) does:
1. `fee = fee_per_gas * gas_used_at_most + reward` (wei, `U256`) — `calculate_remote_fee`.
2. Cast to `u128`, wrap in `FixedU128::from_inner`, multiply by `params.multiplier`, divide by `params.exchange_rate`.
3. `convert_from_ether_decimals` (lines 414-418) divides the wei value by `10^(18 - Decimals)` (e.g. `1e8` for a 10-decimal chain like DOT) using plain `checked_div`, with **no minimum-fee floor and no rounding-up**.

If the wei amount produced in steps 1-2 is smaller than the decimals divisor (`10^8`/`10^6` depending on chain), the final `remote` fee is truncated to `0`, even though `reward` (which is promised and paid out on the Ethereum side per message, per the module doc: `Min(GasPrice, MaxFeePerGas) * GasUsed + Message.Reward`) is non-zero. This is confirmed by the repository's own test: [1](#0-0) 
which uses non-zero `fee_per_gas`, non-zero `reward`, and a `1:1` exchange rate/multiplier and still gets `fee.remote == 0`, with a comment noting this "should be avoided."

The public entrypoint chain is: `SendMessage::validate` → `Pallet::calculate_fee` (bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:41-74) which is invoked for **any** message sent through a registered channel (e.g. via the XCM exporter for sibling parachains, or `snowbridge-pallet-system::send`). There is no unprivileged actor gate here beyond having a valid channel — the fee charged to the user is whatever `calculate_fee` returns, and if it returns zero, the ticket is issued and the message enqueued with a zero remote fee. [2](#0-1) 

`do_process_message` (bridges/snowbridge/pallets/outbound-queue/src/lib.rs:301-364) commits the message with the full, un-discounted `reward` field into the `CommittedMessage`, independent of what was (or wasn't) charged upfront: [3](#0-2) 
i.e. the remote-side promised payout is decoupled from whether the Polkadot-side fee collection actually captured that value — there's no check that the collected fee is non-zero or covers the committed `reward`.

### Impact Explanation
This is a case of "public underpriced work that ... stalls bridge processing": governance sets pricing parameters intending gas/reward costs to be recovered from senders, but for commands with low `max_dispatch_gas`/low `fee_per_gas`*`gas`+`reward` combinations relative to the decimals conversion factor, the fee silently truncates to zero. Any user able to trigger message sends (via XCM export to a registered channel or system commands) pays nothing while the committed message still instructs Ethereum-side relayers to be paid `reward` out of the channel's pre-funded agent balance. Repeated exploitation drains the channel's Ethereum-side reward/gas-refund reserve without any corresponding Polkadot-side collection, which can eventually leave relayers unpaid/under-funded — degrading or stalling bridge message delivery (the exact "public underpriced work ... stalls bridge processing" impact class).

### Likelihood Explanation
Likelihood depends on governance-configured `PricingParameters` (`fee_per_gas`, `exchange_rate`, `multiplier`, `rewards.remote`) and the `GasMeter`-determined `gas_used_at_most` for a given command, combined with the chain's `Decimals` (10 for DOT/12 for KSM chains vs. 18 for ether — a fixed 1e6–1e8 divisor). No malicious relayer, validator, or governance action is required to trigger the truncation — an unprivileged sender only needs to submit a message whose computed value in wei is smaller than the decimals divisor. This is fundamentally a rounding/precision bug in the pricing pipeline, not a misuse of privilege, and is already demonstrated as reachable with realistic non-zero parameters in the repo's own regression test.

### Recommendation
- Enforce rounding-up (ceiling division) or a non-zero minimum fee in `convert_from_ether_decimals` and/or `calculate_fee`, analogous to the `min_converted_fee` guard already used in `substrate/frame/transaction-payment/asset-tx-payment/src/payment.rs` (`withdraw_fee`/`can_withdraw_fee`), so a non-zero wei fee never converts to a zero-balance charge.
- Alternatively, reject (or clamp) messages whose computed remote fee is zero while `reward`/`max_dispatch_gas` are non-zero, mirroring the hardening already applied to `pallet-asset-conversion`'s quote functions (see `prdoc/stable2606/pr_11795.prdoc`), which now return `None` when rounding would produce a zero output for a non-zero input.
- Add an integrity/runtime check that `calculate_fee(...).remote >= 1` whenever `params.rewards.remote > 0`, and add regression tests asserting the fee is never fully lost to rounding for the full range of supported `Decimals` values (10 and 12).

### Proof of Concept
Existing repository test demonstrates the bug directly: [1](#0-0) 
```rust
#[test]
fn test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero() {
    new_tester().execute_with(|| {
        let gas_used: u64 = 250000;
        let price_params: PricingParameters<<Test as Config>::Balance> = PricingParameters {
            exchange_rate: FixedU128::from_rational(1, 1),
            fee_per_gas: 1_u32.into(),
            rewards: Rewards { local: 1_u32.into(), remote: 1_u32.into() },
            multiplier: FixedU128::from_rational(1, 1),
        };
        let fee = OutboundQueue::calculate_fee(gas_used, price_params.clone());
        assert_eq!(fee.local, 698000000);
        // Though none zero pricing params the remote fee calculated here is invalid
        // which should be avoided
        assert_eq!(fee.remote, 0);
    });
}
```
This shows that with realistic non-zero `fee_per_gas`, `reward`, `multiplier`, and `exchange_rate`, `Pallet::calculate_fee` (bridges/snowbridge/pallets/outbound-queue/src/lib.rs:368-393, `convert_from_ether_decimals` at 414-418) returns `remote == 0`. Any message routed through `SendMessage::validate` (bridges/snowbridge/pallets/outbound-queue/src/send_message_impl.rs:41-74) with such parameters is enqueued and later committed by `do_process_message` (lines 301-364) carrying the full non-zero `reward` obligation for Ethereum-side relayers, despite the sender having paid `0` for it.
