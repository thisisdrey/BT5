### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount` to `MAX_TOKENS_PER_USER`, permanently blocking deposits/collateral top-ups and enabling forced liquidation — (File: contracts/Pool.sol)

### Summary
The WildFly-OpenSSL issue is a resource-exhaustion DoS: each HTTP session allocates memory that is never freed, letting an unprivileged attacker degrade/DoS the server by repeating a cheap operation. The Metronome analog is per-account storage exhaustion: `Pool` tracks each account's deposit/debt tokens in `MappedEnumerableSet` lists capped at `MAX_TOKENS_PER_USER = 30`, and `DepositToken._transfer` adds the token to the *recipient's* list whenever the recipient's prior balance is 0. An unprivileged attacker can dust-transfer every whitelisted `msdTOKEN` to a victim, filling all 30 slots so any subsequent `deposit()` / `transfer` of a *new* collateral type to the victim reverts with `UserReachedMaxTokens`, permanently (while maintained) blocking collateral top-ups — including the top-up needed to avoid liquidation.

### Finding Description
- `Pool.MAX_TOKENS_PER_USER` is `30`, and `onlyIfAdditionWillNotReachMaxTokens` reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` for the account [1](#0-0) [2](#0-1) .
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever `_recipientBalanceBefore == 0 && amount_ > 0`, with no consent/opt-out from the recipient [3](#0-2) .
- `Pool.addToDepositTokensOfAccount` only checks that the caller is a registered deposit token and enforces the cap — the `account_` is attacker-chosen [4](#0-3) .
- `DepositToken.deposit` mints to an arbitrary `onBehalfOf_`, which also triggers `addToDepositTokensOfAccount` via `_mint`, so direct deposits to the victim work too [5](#0-4) .
- Because `deposit()`, `transfer()`, `transferFrom()`, and `seize()` (liquidation payouts) all funnel through `_mint`/`_transfer` → `addToDepositTokensOfAccount`, once the list is full the victim cannot receive *any* token type not already in their list — every such call reverts [6](#0-5) .
- The attacker's cost is only gas: each dust `deposit`/`transfer` moves ~1 wei of `msdTOKEN`, and the underlying dust can be re-withdrawn afterwards. The victim can remove an entry only by transferring the dust out, but the attacker can cheaply re-dust (front-running or repeating), making the grief sustainable.

### Impact Explanation
This is availability loss via repeated cheap writes exhausting a fixed resource — the direct on-chain analog of a memory leak. Consequences:
- A victim approaching liquidation cannot deposit additional collateral (`deposit` reverts for any new token), so a healthy position cannot be restored → forced liquidation and loss of collateral beyond what liquidations normally allow.
- SmartFarmingManager leverage flows that mint new deposit tokens to a user's account revert.
- Liquidators' `seize` to a beneficiary whose list is full reverts, interfering with `Pool.liquidate` payouts.
- Funds are not stolen directly; the impact is temporary/persistent freezing of the ability to add collateral, causing liquidation losses — i.e., freezing of funds for as long as the attacker's dust sits in the victim's list, which the attacker can renew at gas cost only.

### Likelihood Explanation
Fully permissionless: the attacker needs only to hold tiny amounts of each whitelisted `msdTOKEN` (obtained by depositing dust of each underlying, or buying on market). No privileged role, no oracle manipulation, no governance involvement. On any chain with multiple whitelisted collaterals/synths (deployments show several deposit/debt tokens per pool), filling 30 slots is feasible; each pool's whitelisted set is bounded but the combined deposit+debt slots count toward the same 30 cap, so fewer distinct dust types may be needed if the victim already uses some slots. Requires a pool with ≥ ~30 whitelisted tokens to fill all slots purely via dust — check deployed config; if fewer tokens exist, the attack is limited to pools where `depositTokens.length + debtTokens.length >= 30` minus victim's existing entries. On mainnet/optimism/base deployments with many msAssets and collaterals this threshold is reachable; where it isn't, the attack still partially blocks the *remaining* free slots.

### Recommendation
- Only add to `depositTokensOfAccount` on user-initiated `deposit`/`issue` paths, or require a minimum amount / explicit opt-in for token list addition via `transfer`/`seize`.
- Alternatively, remove the per-account set cap by iterating only registered tokens, or raise the effective limit and make additions idempotent against unsolicited dust (e.g., check `balanceOf` was 0 *and* the action was `deposit`, not `transfer`).
- Allow the victim (or anyone) to prune zero/dust entries permissionlessly.

### Proof of Concept
Hardhat (fork a deployment where whitelisted deposit + debt tokens ≥ 30):

```ts
// Attacker holds ≥1 wei of each whitelisted DepositToken's msdTOKEN.
// For each deposit token dt_i not yet in victim's list:
for (const dt of allDepositTokens) {
  await dt.connect(attacker).deposit(1, attacker.address);        // or transfer acquired dust
  await dt.connect(attacker).transfer(victim.address, 1);          // adds dt to victim's list
}
// Also dust-transfer debt positions if needed (DebtToken mint adds to debtTokensOfAccount).
// Now: depositTokensOfAccount[victim].length + debtTokensOfAccount[victim].length == 30

// Victim tries to deposit a *new* collateral to save an unhealthy position:
await expect(
  newDepositToken.connect(victim).deposit(amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
// Reverts inside _mint -> pool.addToDepositTokensOfAccount(victim) (Pool.sol:143-148, DepositToken.sol:486-488)

// Victim is liquidated; seize() to a fresh beneficiary also reverts if that list is full.
```

    function deposit(
        uint256 amount_,
        address onBehalfOf_
    ) external override whenNotPaused nonReentrant onlyIfDepositTokenExists returns (uint256 _deposited, uint256 _fee) {
        if (amount_ == 0) revert AmountIsZero();
        if (onBehalfOf_ == address(0)) revert BeneficiaryIsNull();

        IPool _pool = pool;
        IERC20 _underlying = underlying;
        address _msgSender = _msgSender();
        address _treasury = address(_pool.treasury());

        if (_msgSender == _treasury) revert TreasuryCanNotDeposit();

        uint256 _balanceBefore = _underlying.balanceOf(_treasury);
        _underlying.safeTransferFrom(_msgSender, _treasury, amount_);
        amount_ = _underlying.balanceOf(_treasury) - _balanceBefore;

        (_deposited, _fee) = quoteDepositOut(amount_);
        if (_fee > 0) {
            _mint(_pool.feeCollector(), _fee);
        }

        _mint(onBehalfOf_, _deposited);

        emit CollateralDeposited(_msgSender, onBehalfOf_, amount_, _deposited, _fee);
    }
