### Title
Recurring airdrop claims revert or underpay when a new merkle root is not strictly cumulative-increasing per account - ([File: contracts/utils/RecurringAirdrop.sol](contracts/utils/RecurringAirdrop.sol))

### Summary
`RecurringAirdrop.claim` computes the payout as `amount_ - claimed[msg.sender]`, where `claimed` is a lifetime cumulative counter that is never reset when `updateMerkleRoot` installs a new root. If a new distribution assigns a user an amount lower than (or equal to) their lifetime claimed total, the subtraction underflows (or returns 0) and the user can never claim the new allocation — funds are locked in the contract. This is the same "ineffective accounting across proofs/roots" bug class as the Footium report.

### Finding Description
The accounting in `claim` is:

```solidity
uint256 _claimable = amount_ - claimed[msg.sender];
if (_claimable == 0) revert NothingToClaim();
claimed[msg.sender] += _claimable;
```

- `claimed[msg.sender]` accumulates across all roots (`claimed[msg.sender] += _claimable`, never cleared in `updateMerkleRoot`).
- The correctness of this depends entirely on the off-chain invariant that each new merkle tree encodes *cumulative* entitlements that are monotonically non-decreasing per account. Nothing in the contract enforces or verifies this.
- If a later root grants an account a lower cumulative amount (reallocation, correction of a prior over-allocation, vesting schedule change, or a per-round/non-cumulative tree), then `amount_ - claimed[msg.sender]` underflows and the tx reverts — the user's legitimately-proven allocation is permanently unclaimable. The revert is unconditional; there is no admin escape in `claim` for that user.
- Even in the intended cumulative model, a user holding a valid proof for a smaller-but-independent amount (the Footium scenario: two valid proofs for 1000 then 500) is bricked by underflow.
- `MetAirdrop` inherits this (deployed on mainnet, `claimed`/`claim(uint256,bytes32[])` in `deployments/mainnet/MetAirdrop.json`) and adds `esMET.lockFor`, so locked claims also mean unclaimable vested MET.

Invariant broken: conservation of allocated rewards / liveness of `claim` — proven entitlements become frozen.

### Impact Explanation
Permanent freezing of unclaimed yield for any account whose new-root entitlement is not strictly greater than its lifetime `claimed` total. The tokens remain in the airdrop contract and can only be recovered via governor `sweep` (TokenHolder), meaning the user cannot self-serve the amount their proof entitles them to.

### Likelihood Explanation
Requires a non-monotonic or non-cumulative root update, which is an operational/off-chain assumption rather than attacker-controlled input — but it is a real accounting flaw identical to the referenced bug class: the contract conflates "cumulative entitlement" (leaf amount) with "incremental claim" semantics and gives no protection or recovery when the assumption fails. Any correction round, slashing-style reallocation, or migration to a fresh tree instantly locks affected users.

### Recommendation
- Mark each leaf `(root, account)` as consumed via `mapping(bytes32 => mapping(bytes32 => bool)) claimed` (or `claimed[merkleRoot][account]`), treating each root's claim independently, and transfer the full proven `amount_` per root; or
- Explicitly reset `claimed` on `updateMerkleRoot` (e.g., track `claimed` per root epoch) so a new root is self-contained; or
- If cumulative semantics are intended, at minimum make the subtraction safe (`amount_ > claimed ? amount_ - claimed : 0`-style check reverting with a clear error) and document/enforce the monotonic-invariant off-chain, plus provide a governor recovery path.

### Proof of Concept
Hardhat (mirroring `test/MetAirdrop.test.ts` setup):

```ts
// Round 1: alice has entitlement 1000
let leaf = generateLeaf(alice.address, parseEther('1000'))
let proof = tree0.getHexProof(leaf)
await airdrop.connect(alice).claim(parseEther('1000'), proof)   // ok, claimed = 1000

// Governor publishes round 2 where alice's cumulative entitlement is 500
// (correction / reallocation / non-cumulative round)
await airdrop.connect(governor).updateMerkleRoot(merkleRoot1, proofsHash)

leaf = generateLeaf(alice.address, parseEther('500'))
proof = tree1.getHexProof(leaf)

// reverts: 500 - 1000 underflows (panic 0x11)
await expect(airdrop.connect(alice).claim(parseEther('500'), proof))
  .to.be.revertedWithPanic(0x11)

// alice's 500-token entitlement is permanently locked in the airdrop contract
```

The existing test at `test/MetAirdrop.test.ts:159-178` (`should receive correct rewards when claiming both rounds`) confirms the cumulative-delta accounting; the PoC shows the same code path locks funds when the new leaf amount ≤ prior `claimed`.
