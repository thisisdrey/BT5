### Title
`ERC20Transactor` credits XCM holding with attacker-claimed amount instead of verified ERC20 balance delta - (File: cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs)

### Summary
`ERC20Transactor` (used by `asset-hub-westend`'s `AssetTransactors` and by `pallet-revive`'s `impl_fungibles.rs`) treats any account-supplied `AccountKey20` location as a real, trustworthy ERC-20 contract. On `withdraw_asset_with_surplus` / `deposit_asset_with_surplus` it calls the contract's `transfer` function and, if the ABI-decoded return value is `true`, unconditionally credits an `AssetsInHolding` of exactly the XCM-message-supplied `amount` — never checking the contract's actual balance/state change. This is structurally identical to the Illuminate `lend()` bug: an attacker-controlled external contract's return value (not an independently verified before/after balance delta) determines how much value the runtime treats as real.

### Finding Description
`ERC20Transactor::withdraw_asset_with_surplus` (and the mirrored `deposit_asset_with_surplus`) works as follows: [1](#0-0) 

1. `Matcher::matches_fungibles(what)` extracts `(asset_id, amount)` straight from the caller-supplied XCM `Asset` — `asset_id` is simply the `H160` key embedded in an `AccountKey20` junction, i.e. **any address the caller chooses**, and `amount` is whatever value the caller put in the XCM message.
2. The pallet calls `pallet_revive::Pallet::<T>::bare_call(..., asset_id, ..., IERC20::transferCall{ to: checking_address, value: amount }.abi_encode(), ...)` on that address.
3. If the call doesn't revert, it ABI-decodes the returned `bool` and, if `true`, immediately returns `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting `amount` with **no verification that any balance actually moved**.

The identical pattern exists in `pallet-revive`'s own `fungibles::Mutate` implementation: [2](#0-1) [3](#0-2) 

Because an unprivileged user can deploy an arbitrary contract via `pallet-revive` (`Code::Upload`) and that contract's address becomes a valid ERC-20 "asset id" for XCM purposes (as documented in `prdoc/stable2506/pr_7762.prdoc` — *"asset ids of the form `AccountKey20 { key, network }` will be matched by this transactor"*), the attacker fully controls the contract's `transfer`, `balanceOf`, and `totalSupply` logic. A malicious `transfer()` can simply `return true` without moving or even tracking any balance. There is no whitelist of approved ERC20 contracts and no post-call balance-diff check — exactly the two mitigations the original report recommended ("whitelisting" or "verify returned amounts by checking the balance before and after").

This is reachable through the public, unprivileged `pallet-xcm::execute` extrinsic, as demonstrated by the existing test: [4](#0-3) 

which shows a signed account executing `WithdrawAsset`/`DepositAsset` for an `AccountKey20`-keyed ERC20 asset entirely through `PolkadotXcm::execute`.

### Impact Explanation
`AssetsInHolding` produced by `withdraw_asset_with_surplus` is treated by the XCM executor as real, backed value for the remainder of the XCM program (deposits, transfers, swaps, reserve transfers). Because the credited `amount` is not tied to any actually-verified balance change on the attacker-controlled contract, an attacker can fabricate holding-register value for a "token" they fully control. If this asset is subsequently paired against real value (e.g., registered in `pallet-asset-conversion` swap pools, used as collateral, or forwarded cross-chain through a reserve-transfer where the destination trusts Asset Hub's sovereign account as backing), the attacker can convert unbacked fabricated credit into real DOT/USDC/foreign-asset value — a direct "theft / unbacked mint" primitive matching the Impact Gate.

### Likelihood Explanation
The path requires only unprivileged actions: (1) deploy a contract via `pallet-revive` (public), (2) craft an XCM program via the public `pallet-xcm::execute` extrinsic referencing that contract as an `AccountKey20` asset id, and (3) have the crafted asset interact with any component that ascribes real value to it (pool creation/swap, cross-chain reserve transfer). No malicious peer, validator, collator, relayer, or governance action is needed — the entire trust failure is local, deterministic, and repeatable by any signed account, satisfying "Prefer public-entrypoint paths that let an unprivileged attacker cause ... fund loss."

### Recommendation
Do not treat the boolean return of an attacker-supplied contract's `transfer` as sufficient proof of value transfer. Before crediting `AssetsInHolding`/before finalizing `mint_into`/`burn_from`, read the ERC20's `balanceOf` for the relevant account(s) before and after the call and use the *actual measured delta*, capped at the requested `amount`, as done for the Illuminate PT lend bug's recommended fix. Additionally, only recognize `AccountKey20` asset ids that have gone through an explicit registration/whitelisting step (analogous to `LocalMint<NonZeroIssuance<...>>` used for other transactors) before allowing them to participate in reserve transfers, teleports, or AMM pools.

### Proof of Concept
1. Attacker deploys a "FakeToken" contract via `pallet-revive` whose Solidity `transfer(address,uint256)` always executes `return true;` without touching any storage-backed balance, and whose `balanceOf`/`totalSupply` return arbitrary attacker-chosen constants.
2. Attacker submits `pallet_xcm::execute` with an XCM program:
   - `WithdrawAsset((AccountKey20 { key: fake_token_addr, network: None }, HUGE_AMOUNT))`
   - `DepositAsset(AllCounted(1), attacker_or_pool_beneficiary)`
3. `ERC20Transactor::withdraw_asset_with_surplus` calls `transfer` on `fake_token_addr`; it returns `true`; the transactor credits `Erc20Credit(HUGE_AMOUNT)` into the holding register with zero real backing, as shown in: [5](#0-4) 
4. `DepositAsset` calls `deposit_asset_with_surplus`, which again only checks the boolean return of `transfer`, delivering `HUGE_AMOUNT` of the fabricated asset to the beneficiary.
5. If `fake_token_addr` is subsequently added to an `asset-conversion` liquidity pool paired with real DOT/USDC, or forwarded via reserve-backed transfer to another chain, the attacker converts the fabricated `HUGE_AMOUNT` into real value drained from other pool participants or destination-chain minted assets — mirroring the original "mint any amount of PT from unvalidated returned amount" exploit.

	fn withdraw_asset_with_surplus(
		what: &Asset,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<(AssetsInHolding, Weight), XcmError> {
		tracing::trace!(
			target: "xcm::transactor::erc20::withdraw",
			?what, ?who,
		);
		let (asset_id, amount) = Matcher::matches_fungibles(what)?;
		let who = AccountIdConverter::convert_location(who)
			.ok_or(MatchError::AccountIdConversionFailed)?;
		// We need to map the 32 byte checking account to a 20 byte account.
		let checking_account_eth = T::AddressMapper::to_address(&TransfersCheckingAccount::get());
		let checking_address = Address::from(Into::<[u8; 20]>::into(checking_account_eth));
		let weight_limit = WeightLimit::get();
		// To withdraw, we actually transfer to the checking account.
		// We do this using the solidity ERC20 interface.
		let data =
			IERC20::transferCall { to: checking_address, value: EU256::from(amount) }.abi_encode();
		let ContractResult { result, weight_consumed, storage_deposit, .. } =
			pallet_revive::Pallet::<T>::bare_call(
				OriginFor::<T>::signed(who.clone()),
				asset_id,
				U256::zero(),
				TransactionLimits::WeightAndDeposit {
					weight_limit,
					deposit_limit: StorageDepositLimit::get(),
				},
				data,
				&ExecConfig::new_substrate_tx(),
			);
		// We need to return this surplus for the executor to allow refunding it.
		let surplus = weight_limit.saturating_sub(weight_consumed);
		tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?weight_consumed, ?surplus, ?storage_deposit);
		if let Ok(return_value) = result {
			tracing::trace!(target: "xcm::transactor::erc20::withdraw", ?return_value, "Return value by withdraw_asset");
			if return_value.did_revert() {
				tracing::debug!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract reverted");
				Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))
			} else {
				let is_success = IERC20::transferCall::abi_decode_returns_validate(&return_value.data).map_err(|error| {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?error, "ERC20 contract result couldn't decode");
					XcmError::FailedToTransactAsset("ERC20 contract result couldn't decode")
				})?;
				if is_success {
					tracing::trace!(target: "xcm::transactor::erc20::withdraw", "ERC20 contract was successful");
					Ok((
						AssetsInHolding::new_from_fungible_credit(
							what.id.clone(),
							Box::new(Erc20Credit(amount)),
						),
						surplus,
					))
				} else {
					tracing::debug!(target: "xcm::transactor::erc20::withdraw", "contract transfer failed");
					Err(XcmError::FailedToTransactAsset("ERC20 contract transfer failed"))
				}
			}
		} else {
			tracing::debug!(target: "xcm::transactor::erc20::withdraw", ?result, "Error");
			// This error could've been duplicate smart contract, out of gas, etc.
			// If the issue is gas, there's nothing the user can change in the XCM
			// that will make this work since there's a hardcoded gas limit.
			Err(XcmError::FailedToTransactAsset("ERC20 contract execution errored"))
		}
	}
