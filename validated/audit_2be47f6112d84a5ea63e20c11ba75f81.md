### Title
Unsigned-integer underflow in reftable block parsing causes out-of-bounds panic (DoS) — ([File: internal/git/reftable/reftable.go])

### Summary
`Table.parseRefBlock` computes the restart-table offset for a reftable ref block using unsigned subtraction that is not checked for underflow, mirroring the `Treasury._loadSwapState()` underflow bug class in the source report (an unchecked `a.sub(b)` on unsigned values that reverts/breaks all dependent operations). Because the values involved (`currentBS`, `RestartCount`) are read directly out of the on-disk reftable block content, a block whose encoded restart-count/size relationship is smaller than expected drives the subtraction below zero. Since Go `uint` silently wraps instead of reverting, the result is an enormous bogus offset that is then used to index into the in-memory buffer, producing an out-of-bounds slice panic in `getRefsFromBlock`.

### Finding Description
`extractBlockLen()` reads a 3-byte block-length field directly from file bytes: [1](#0-0) 

`parseRefBlock()` then computes the restart-table start with unchecked unsigned subtraction: [2](#0-1) 

`b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)` is computed entirely in `uint`. If `currentBS < 2 + 3*RestartCount` for the block being parsed, the subtraction underflows and wraps to a value near `math.MaxUint`, instead of erroring out the way the equivalent SafeMath-guarded Solidity code would revert. `getRefsFromBlock` then loops `for idx < b.RestartStart`, walking far past the end of the in-memory `src` buffer and eventually panicking with an index-out-of-range error: [3](#0-2) 

This parser is exercised on the normal write path for repositories using the reftable reference backend: every transaction that updates references stages the tables it wrote via `reftableRecorder.stageTables`, which calls `reftable.ParseTable`/`GetReferences`-adjacent logic on freshly written table files inside the transaction's snapshot: [4](#0-3) 

This runs inside the WAL `TransactionManager` apply path rather than behind the standard gRPC unary/stream interceptors, so unlike a plain RPC-handler panic (which `panichandler.UnaryPanicHandler`/`StreamPanicHandler` would recover into an `Internal` error), a panic here can propagate into the partition's background apply goroutine. [5](#0-4) 

### Impact Explanation
Same bug class as the report: an unchecked unsigned subtraction on attacker-reachable, disk-resident data that should be validated/error-returned but instead either reverts everything (Solidity case) or, in Go, silently underflows and is then used unsafely as a buffer index, producing a panic. Because this code path sits in the write-transaction commit pipeline of the storage manager (not a per-request gRPC handler), a triggered panic can crash the partition worker responsible for applying WAL entries for the affected repository/partition, denying service to all subsequent transactions targeting it — a "critical function reverts/DoS" outcome analogous to the reported inability to recover system state once the faulty arithmetic path is hit.

### Likelihood Explanation
Likelihood is constrained: reftable block bytes are normally produced by Git's own reftable writer during ordinary reference updates (an ordinary user push/branch update that lands on a repository using the `reftable` backend), so under typical encoding the length/restart-count relationship should be internally consistent. However, no defensive check exists in Gitaly's custom parser to guard against a block whose reported length is inconsistent with its restart count — whether from an edge case in Git's block layout (e.g., very small configured `blockSize`, unusual prefix/suffix compression near block boundaries) or from a corrupted/partially written table (e.g., an interrupted write, concurrent compaction sneaking in in a way not fully synchronized with `preventReftableCompaction`/`allowReftableCompaction`). No arithmetic overflow/bounds check exists to reject such input gracefully, which is the same class of missing invariant enforcement as the reported bug.

### Recommendation
Add explicit, checked arithmetic in `internal/git/reftable/reftable.go`:
- Validate that `currentBS >= 2 + 3*uint(b.RestartCount)` before computing `RestartStart`, returning an error (e.g. `fmt.Errorf("invalid restart count for block")`) instead of performing the subtraction unconditionally.
- Similarly bound-check all offsets derived from on-disk fields (`extractBlockLen`, `getVarInt` results, `idx+suffixLength`, `idx+hashSize`, etc.) against `len(src)`/`blockEnd` before slicing, so malformed or corrupted reftable content returns a parse error rather than reaching an unchecked slice expression.
- Ensure these parse errors propagate as regular RPC/transaction errors rather than panics, and confirm the `TransactionManager`'s WAL apply loop recovers from panics in file-parsing helpers the same way the gRPC middleware does, so a single malformed table cannot take down the whole partition worker.

### Proof of Concept
Deterministic reasoning (no live git binary needed since the parser trusts raw bytes):
1. Craft (or obtain via disk corruption/incomplete write) a reftable `.ref` file whose ref block has `block_len` (3-byte big-endian field read by `extractBlockLen`) set such that `currentBS = 5`, while the trailing 2-byte restart count field is set to `RestartCount = 3`.
2. `parseRefBlock` computes `b.RestartStart = blockStart + 5 - 2 - 3*3 = blockStart - 6` — since these are `uint`, this wraps to a value close to `math.MaxUint`.
3. `getRefsFromBlock`'s loop condition `idx < b.RestartStart` (with `idx = blockStart+4`) never becomes false via normal termination, and any indexing operation on `src` (`src[idx]`, `src[idx:idx+suffixLength]`, etc.) will run off the end of the slice, panicking with `index out of range`.
4. Because `reftableRecorder.stageTables` invokes this parser as part of transaction commit staging (`internal/gitaly/storage/storagemgr/partition/reftable.go:94`), this panic occurs inside the storage manager's write path for the affected repository/partition rather than under gRPC's panic-recovery middleware, risking a crash of that partition's background processing instead of a contained per-RPC error.

Confidence caveat: I was not able to fully trace, within the available indexed code, the exact upstream conditions (e.g. specific git version quirks or `blockSize` configuration) under which Git's own reftable writer would legitimately produce a block matching this inconsistent `currentBS`/`RestartCount` relationship, nor could I confirm whether the WAL apply goroutine has its own panic-recovery wrapper distinct from the gRPC interceptors shown above. Further verification (e.g., fuzzing `reftable.ParseTable`/`GetReferences` with crafted `.ref` byte streams, or checking `transaction_manager.go` for panic recovery around the apply loop) would be needed to fully confirm exploitability and blast radius.

// parseRefBlock parses a block and if it is a ref block, provides
// all the reference updates.
func (t *Table) parseRefBlock(src []byte, headerOffset, blockStart, blockEnd uint) ([]git.Reference, error) {
	currentBS := t.extractBlockLen(src, blockStart+headerOffset)

	fullBlockSize := t.blockSize
	if fullBlockSize == 0 {
		fullBlockSize = currentBS
	} else if currentBS < fullBlockSize && currentBS < (blockEnd-blockStart) && src[blockStart+currentBS] != 0 {
		fullBlockSize = currentBS
	}

	b := &block{
		BlockStart:    blockStart + headerOffset,
		FullBlockSize: fullBlockSize,
	}

	if err := binary.Read(bytes.NewBuffer(src[blockStart+currentBS-2:]), binary.BigEndian, &b.RestartCount); err != nil {
		return nil, fmt.Errorf("reading restart count: %w", err)
	}

	b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)

	return t.getRefsFromBlock(src, b)
}

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

// StreamPanicHandler creates a new stream server interceptor that handles panics.
func StreamPanicHandler(logger log.Logger) grpc.StreamServerInterceptor {
	return func(srv interface{}, stream grpc.ServerStream, info *grpc.StreamServerInfo, handler grpc.StreamHandler) (err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(srv, stream)
	}
}
