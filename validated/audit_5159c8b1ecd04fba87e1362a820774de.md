### Title
Unvalidated attacker-controlled offsets cause out-of-bounds array access in `VerifyTransferProof.execute` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `PrecompiledContracts.VerifyTransferProof.execute` precompile (a Sapling shielded-transfer proof verifier reachable from any TVM contract call via `staticcall`/`call` to the corresponding precompile address) parses a fixed-format binary blob using attacker-supplied 32-bit offset fields taken directly from the input `data`, then uses those offsets—without validating them against `data.length`—as indices for `System.arraycopy` calls, structurally mirroring the libigl `parse_node_field` bug class described in CVE-2024-23949 (unvalidated indices derived from file/input content driving out-of-bounds array writes/reads).

### Finding Description
`execute(byte[] data)` only checks that `data.length` matches one of four fixed sizes [1](#0-0) . It then reads three offset fields directly from attacker-controlled `data` with no range validation: [2](#0-1) 

These offsets (`spendOffset`, `spendAuthSigOffset`, `receiveOffset`) are immediately used as array indices to re-parse counts from `data`: [3](#0-2) 

and later as base offsets for `System.arraycopy` loops whose bounds are also derived from attacker-controlled `spendCount`/`receiveCount`: [4](#0-3) 

Only `spendCount`/`spendAuthSigCount`/`receiveCount` are bounds-checked to be in `[1,2]` and equal to each other (line 1496-1499); the raw `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` values themselves are never checked to be within `[0, data.length)` before being used to index `data`, unlike libigl's `parse_node_field`, which trusted array indices read from an untrusted `.msh` file without validating them against buffer bounds. I could not fully confirm the implementation of the `parseInt`/`parseLong` helper methods used here (their definitions were not located in the indexed portion of this file), so I cannot verify whether they perform any bounds clamping internally before the `System.arraycopy` calls consume the resulting offsets — this is a gap that a background agent with full file access should verify.

### Impact Explanation
If the helper `parseInt`/`parseLong` do not clamp/validate against `data.length`, a crafted `data` payload (fully attacker-controlled since it is the calldata to a TVM `CALL`/`STATICCALL` to the Sapling verify-transfer precompile address) causes `System.arraycopy` to be invoked with an out-of-range source offset, throwing an uncaught `ArrayIndexOutOfBoundsException`/`IndexOutOfBoundsException`. This propagates out of the `try` block; the `catch (Throwable any)` block at line 1604 does catch generic `Throwable`, so in the current code this specific failure mode would likely be caught and handled gracefully (returning a `false`/zero result) rather than crashing the node — meaning the most severe outcome (node crash / DoS) is plausible only if any code path executes before entering the guarded `try` or if exceptions are thrown asynchronously from the worker thread pool (`workersInConstantCall`/`workersInNonConstantCall`) in a way not joined back into the `try` (the `Future.get()` calls at line 1593 do occur inside the `try`, so exceptions there should also be caught). Given the presence of the broad `catch (Throwable any)`, I could not conclusively determine a code path that results in an uncaught exception, unbacked balance, or memory corruption comparable to CVE-2024-23949's OOB write — the impact is significantly mitigated by the existing catch-all in Java's memory-safe runtime (unlike native C++ code in libigl, an OOB array access in Java throws an exception rather than corrupting memory).

### Likelihood Explanation
The precompile is reachable by any account (unprivileged) executing a smart contract that calls the corresponding precompile address with attacker-chosen calldata, making the attack surface trivially reachable via a signed transaction or contract call. However, because Java's bounds checking converts the "OOB write" primitive from the C++ analog into a catchable Java exception, and the surrounding code already wraps this parsing path in a `catch (Throwable any)`, exploitation to achieve a crash or memory-safety violation is unlikely under current code behavior as verified.

### Recommendation
Explicitly validate `spendOffset`, `spendAuthSigOffset`, and `receiveOffset` (and all derived indices used in the `System.arraycopy` calls) against `data.length` before use, rejecting the transaction/returning a failure result if any computed index or copy range would exceed array bounds — mirroring the existing bounds checks already applied to `spendCount`/`receiveCount`. This should be done defensively regardless of the current outer `catch (Throwable any)`, since relying on exception handling for input validation is fragile and could regress if the surrounding try/catch structure is refactored.

### Proof of Concept
Not verified end-to-end due to inability to inspect the `parseInt`/`parseLong` helper implementations in the available index; a background agent with full repository access should construct a 2080/2368/2464/2752-byte payload (matching `VerifyTransferProof.SIZE`) with `spendOffset`/`receiveOffset` set to large or negative 32-bit values and invoke the precompile via a TVM contract call to confirm whether `parseInt`/`parseLong` or the subsequent `System.arraycopy` calls throw, and whether that exception is fully absorbed by the existing `catch (Throwable any)` at line 1604 or can escape to affect node stability.
