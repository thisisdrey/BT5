### Title
Claiming airdrop rewards after `updatedAt + lockPeriod` bypasses the esMET lock, rewarding users who wait - (File: contracts/MetAirdrop.sol)

### Summary
`MetAirdrop._transferReward` is meant to lock claimed MET into `esMET` for `lockPeriod` (7 days). However, if `block.timestamp > updatedAt + lockPeriod`, the reward is transferred directly as fully liquid MET. Since `RecurringAirdrop.claim` has no deadline and `claimed` is cumulative, a claimant strictly profits by waiting ~7 days after each merkle root update: they receive unlocked MET instead of locked esMET. The rational strategy is to never claim early, mirroring the reported bug class — conditions monotonically improve for the actor over time, so there is no incentive to act promptly, and here waiting actively breaks the intended locking invariant.

### Finding Description
- `RecurringAirdrop.claim` verifies a merkle proof for `(msg.sender, amount_)` and pays out `amount_ - claimed[msg.sender]`; it never expires, so a user can claim at any time after `updateMerkleRoot` sets `updatedAt = block.timestamp` [1](#0-0) [2](#0-1) 
- `MetAirdrop._transferReward` computes `_end = updatedAt + lockPeriod` and, if `_end < block.timestamp`, sends the MET directly to the user with no lock; only claims made *before* `_end` are routed through `ESMET.lockFor` [3](#0-2) 
- `lockPeriod` defaults to `7 days` [4](#0-3) 

Concretely: after `updateMerkleRoot`, user A waits `> lockPeriod`, then calls `claim(amount_, proof_)`. `_end < block.timestamp` is true, so `MET.safeTransfer(to_, amount_)` executes and A receives liquid MET. A user who claimed promptly would have had the same amount locked in esMET for up to `lockPeriod`. Any EOA with a valid proof can do this — no privileged role required.

### Impact Explanation
The intended economic mechanism — airdropped MET must be locked into esMET for `lockPeriod` — is entirely bypassable by waiting. Late claimers receive strictly more economic value (unlocked, transferable MET) than early claimers (esMET with a lock). This is both a liveness/incentive failure (no incentive to claim promptly; rational users watch `updatedAt` and claim right after `_end`) and a direct erosion of the lock mechanism, which is designed to prevent immediate sell pressure of distributed MET. All unclaimed rewards in every distribution window become claimable as liquid tokens.

### Likelihood Explanation
Certain for every user who delays claiming. No attacker coordination, privileged role, or manipulation is needed — `claim` is permissionless and non-expiring. The only requirement is patience of `lockPeriod` (7 days) past the root update, which the protocol itself makes observable via the public `updatedAt` state variable and the `MerkleRootUpdated` event.

### Recommendation
Anchor the lock end to the claim time rather than the root update time — i.e., always route through `ESMET.lockFor(to_, amount_, lockPeriod)` (clamped to `MINIMUM_LOCK_PERIOD`/`MAXIMUM_LOCK_PERIOD` bounds), removing the `if (_end < block.timestamp)` escape branch. If grace for very old distributions is desired, cap it with a separate `claimDeadline` per distribution rather than letting elapsed time unlock the reward.

        // On a fork: deal MET to the airdrop contract.

        // Build a 1-leaf tree for (alice, AMOUNT)

    function test_claim_after_lockPeriod_gets_liquid_MET() public {
        // Alice waits until updatedAt + lockPeriod has passed
        vm.warp(airdrop.updatedAt() + airdrop.lockPeriod() + 1);

        vm.prank(alice);
        airdrop.claim(AMOUNT, new bytes32[](0)); // root == leaf => empty proof

        // Alice received liquid MET, nothing was locked into esMET
        assertEq(airdrop.MET().balanceOf(alice), AMOUNT);
    }

Conceptual trace on a Hardhat/Foundry fork of mainnet (MET at `0x2Ebd53d035150f328bd754D6DC66B99B0eDB89aa`):
1. Governor calls `updateMerkleRoot` → `updatedAt = t0`.
2. Attacker/claimer calls nothing for `t0 + 7 days + 1`.
3. `claim(amount, proof)` → `RecurringAirdrop.claim` succeeds (no expiry), calls `MetAirdrop._transferReward`.
4. `_end = t0 + 7 days < block.timestamp` → `MET.safeTransfer(alice, amount)` executes instead of `ESMET.lockFor`.
5. Alice holds liquid MET; the 7-day esMET lock intended for all claimants was skipped solely because she waited.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }

    function _transferReward(address to_, uint256 amount_) internal override {
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;
        }

        uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
        uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

        // Ensures valid lock period
        uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

        token.safeApprove(address(ESMET), 0);
        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
    }
