### Title
Unbounded pre-allocation via SIP-003 length prefix in `read_next_vec` ignores actual reader size, enabling allocation amplification through `parse_bytestream` HTTP bodies - ([File: stacks-common/src/codec/mod.rs])

### Summary
`read_next_vec` (`stacks-common/src/codec/mod.rs`) only checks the declared vector length against the global constant `MAX_MESSAGE_LEN`, never against the number of bytes actually remaining in the reader. Because `parse_bytestream` (`stackslib/src/net/http/common.rs`) feeds the HTTP-body slice directly into `read_next`, any handler that deserializes a length-prefixed `Vec<T>` (or a type whose codec internally calls `read_next_vec`/`read_next_at_most`/`read_next_exact`) can be made to call `Vec::with_capacity(len)` for up to `MAX_MESSAGE_LEN / size_of::<T>()` items from a request whose actual `Content-Length` is a few bytes.

### Finding Description
The invariant that should hold is: *declared item count × size_of::<T> ≤ bytes actually available to read*. Instead, `read_next_vec` enforces only: [1](#0-0) 

i.e. `size_of::<T>() * len <= MAX_MESSAGE_LEN` (~16 MiB + preamble), a constant unrelated to the actual reader's remaining length. `parse_bytestream` passes the HTTP body slice (bounded only by `Content-Length`, itself capped at `MAX_PAYLOAD_LEN`) straight to `read_next`: [2](#0-1) 

There is no check anywhere in this path comparing `len` (the wire's inner SIP-003 length prefix) to `body.len()` (the outer, verified HTTP Content-Length) before `Vec::with_capacity(len as usize)` executes at `stacks-common/src/codec/mod.rs:183`. An attacker sends a tiny HTTP body (e.g. 5 bytes: a 4-byte big-endian length prefix near `u32::MAX / size_of::<T>()` followed by 1 byte) with `Content-Length` matching that tiny size. The size check passes because it only compares against the fixed `MAX_MESSAGE_LEN` ceiling, so `Vec::with_capacity` allocates up to ~16 MiB before the very next `T::consensus_deserialize` call hits EOF on the exhausted 1-byte remainder and errors out — after the allocation has already been committed.

### Impact Explanation
Each malicious request costs the attacker only a few bytes but forces the node to perform a large (up to ~16 MiB) heap allocation before failing. Sent concurrently/repeatedly across many small requests to any RPC endpoint whose handler routes a length-prefixed `Vec<T>` (or a codec type with an internal vector field) through `parse_bytestream`, this creates a resource-amplification pattern: cheap input, disproportionate allocator work, on an unauthenticated RPC surface. This is a bounded-per-request allocation-amplification issue, not a full crash from a single message, and its severity as a "DoS via many messages" depends on how many concurrent/rapid requests are needed to cause real memory pressure — that quantification could not be fully validated here without runtime instrumentation, and I could not confirm within the available exploration which specific `postX`/`getX` handler bodies deserialize a `Vec<T>` (rather than only fixed-size structs) directly at the top level via `parse_bytestream` versus nested inside a larger consensus-serialized type where `mem::size_of::<T>()` for heap-backed elements (e.g., `StacksTransaction`) is small and misleading regardless of true encoded size.

### Likelihood Explanation
Reachable by any unprivileged remote party able to open an HTTP connection to the node's RPC port (no secret, no peer/slot ownership needed) and send a single crafted request with a mismatched inner length prefix; the outer `Content-Length`/`MAX_PAYLOAD_LEN` checks do not constrain the inner SIP-003 length field at all. The attack is trivially repeatable (attacker cost per request is ~5 bytes), but I was not able to conclusively identify, within the tool budget, a top-level HTTP handler that calls `parse_bytestream::<_, Vec<SomeFixedSizeType>>` directly (as opposed to a larger struct whose vector field is nested deeper in the codec, where `size_of::<T>()` may not reflect a fixed/large per-item size) — that concrete handler binding needs additional verification.

### Recommendation
In `read_next_vec` (`stacks-common/src/codec/mod.rs`), bound the pre-allocation by both `MAX_MESSAGE_LEN` and the actual bytes remaining in the reader (e.g., use a bounded/limited reader, or compute `len` against `fd`'s known remaining length such as `body.len()` when available), and/or replace `Vec::with_capacity(len as usize)` with incremental growth (e.g., `Vec::new()` plus periodic `reserve` in small increments, or `Vec::with_capacity(len.min(some_safe_incremental_cap) as usize)`) so that a false/inflated length prefix cannot force a large up-front allocation before any bytes are verified to exist.

### Proof of Concept
Rust test in `stackslib::net::http` (or `stacks_common::codec` unit test) constructing:
```
let body: [u8; 5] = [0xFF, 0xFF, 0xFF, 0xFF, 0x00]; // len = u32::MAX
```
Feed via `parse_bytestream::<_, Vec<T>>(&preamble_with_content_length(5), &body)` for a `T` with a known small `size_of::<T>()` (e.g. `u8` or `[u8;4]`) chosen so `size_of::<T>() * u32::MAX` overflows the `MAX_MESSAGE_LEN` check as needed to construct a `len` value that stays just under the `MAX_MESSAGE_LEN` cap; assert that `Vec::with_capacity` is invoked with a capacity far larger than `body.len()` (measurable via a custom global allocator tracking peak allocation, or by using `cap()` on an instrumented wrapper type) before the function returns `Err(Error::ReadError(UnexpectedEof))`.

pub fn parse_bytestream<R: Read, T: StacksMessageCodec>(
    preamble: &HttpResponsePreamble,
    mut body: &[u8],
) -> Result<T, Error> {
    // content-type has to be Bytes
    if preamble.content_type != HttpContentType::Bytes {
        return Err(Error::DecodeError(
            "Invalid content-type: expected application/octet-stream".to_string(),
        ));
    }

    let item: T = read_next(&mut body)?;
    Ok(item)
}
