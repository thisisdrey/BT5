## Title
Missing slippage protection on `ExchangeWithdrawContract` allows front-running to reduce the amount an exchange creator receives - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
`ExchangeWithdrawContract`/`ExchangeWithdrawActuator` computes the counter-asset amount (`anotherTokenQuant`) a liquidity-pool creator receives purely from the exchange's live token ratio at execution time, with no user-supplied minimum-output parameter, mirroring the reported `_decreaseLiquidity` slippage issue where no minimum amount check exists before returning liquidity.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no `expected`/minimum-out field, unlike `ExchangeTransactionContract` which explicitly carries an `expected` field used to bound slippage ( [1](#0-0) ). In `ExchangeWithdrawActuator.doValidate()`, `anotherTokenQuant` is derived at validation time solely from the current pool ratio (`bigSecondTokenBalance.multiply(bigTokenQuant).divideToIntegralValue(bigFirstTokenBalance)` or the symmetric branch), with only sanity checks that it is positive and "precise enough" — no user-specified floor is enforced [2](#0-1) . The same unconstrained computation is repeated in `execute()` when the withdrawal is actually applied and asset balances are updated [3](#0-2) . Because the pool ratio can be moved between the time a withdraw transaction is signed/broadcast and the time it is packed into a block (e.g., via an `ExchangeTransactionContract` swap or `ExchangeInjectContract` injected by any third party against the same `exchange_id`), the creator has no way to bound the minimum amount of the counter-asset they will accept, exactly as described in the reported `_decreaseLiquidity` bug class where a received amount of near-zero can be returned to the caller.

### Impact Explanation
An attacker who observes a pending `ExchangeWithdrawContract` transaction can submit their own `ExchangeTransactionContract` swap against the same exchange pair to shift the pool ratio just before the withdraw is included, causing the creator to receive substantially less of the counter-asset than they intended when they signed the transaction — a direct value-extraction (MEV) attack against the exchange creator with no way for them to protect themselves at the contract level. This matches the High-severity impact class of the reported issue: loss of funds due to missing slippage protection.

### Likelihood Explanation
Likelihood is high: `ExchangeTransactionContract` (a swap against the exact same pool) is callable by any account and is cheap to broadcast, and TRON's public mempool/broadcast flow makes front-running/sandwiching a pending withdraw straightforward for any actor with a broadcasting node, without needing any special privilege.

### Recommendation
Add a caller-supplied minimum-expected-output field to `ExchangeWithdrawContract` (mirroring the `expected` field already present on `ExchangeTransactionContract`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` falls below the caller's specified minimum.

### Proof of Concept
1. Exchange creator broadcasts an `ExchangeWithdrawContract` for `exchange_id=X`, expecting `anotherTokenQuant ≈ N` based on the pool ratio observed at signing time.
2. Before that transaction is packed, an attacker broadcasts an `ExchangeTransactionContract` swap on the same `exchange_id` that shifts `firstTokenBalance`/`secondTokenBalance`.
3. The withdraw transaction is then processed; `ExchangeWithdrawActuator` recomputes `anotherTokenQuant` from the now-shifted balances [4](#0-3) , giving the creator far less than `N` with no on-chain mechanism to have rejected the unfavorable execution.
