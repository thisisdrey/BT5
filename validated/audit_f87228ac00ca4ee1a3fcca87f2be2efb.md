### Title
Stale postponed self-call receipt survives `DeleteAccount` and can rebind a recreated account's `AccountContract` via `UseGlobalContract` without the new owner's consent - (`runtime/runtime/src/actions.rs`, `runtime/runtime/src/global_contracts.rs`, `core/store/src/utils/mod.rs`)

### Summary
A postponed action receipt (one waiting on an unresolved `input_data_id`) that targets an account with a `UseGlobalContract` action is stored under `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, keyed only by `account_id`/`receipt_id`/`data_id`. `action_delete_account` → `remove_account` deletes the `Account`, its code, keys and contract data, but never touches these postponed-receipt trie keys, so a stale postponed receipt outlives account deletion. When the data dependency is later satisfied (at a time the original sender fully controls) and the account name has since been recreated (by the same or a different actor), the postponed receipt is executed against the *current* account object and its `UseGlobalContract` action silently rebinds `AccountContract` to whatever `GlobalContractIdentifier` the original attacker chose.

### Finding Description
`use_global_contract` in `runtime/runtime/src/global_contracts.rs:75-108` unconditionally sets `account.set_contract(...)` for whichever `GlobalContractIdentifier` is in the action, as long as that identifier exists in global-contract storage — it performs no check that the *current* controller of the account authorized this rebind.

The only gate is `check_actor_permissions` (`runtime/runtime/src/actions.rs:739-785`), which for `Action::UseGlobalContract` requires `actor_id == account_id`. For a receipt the account sent to itself (self-call, `predecessor_id == receiver_id`), `actor_id` is initialized from `receipt.predecessor_id()` — a value fixed at the time the *original* receipt was created, not re-derived from any access key or owner check at execution time (`runtime/runtime/src/lib.rs`, `apply_action`/`apply_action_receipt`). This means the check only proves the receipt was originally sent by "itself", not that today's account owner authorized it.

The exploit path:
1. Attacker's account `A` sends itself an action receipt containing (a) a promise chained after a cross-contract call whose completion timing `A` fully controls (e.g., calling its own second contract, or using promise-yield/resume), and (b) a `UseGlobalContract` action pointing at an attacker-chosen `GlobalContractIdentifier` (e.g., the wallet contract's account-based identifier, or an attacker-controlled deployed global contract). Because the receipt has an unmet `input_data_id`, `process_action_receipt` (`runtime/runtime/src/lib.rs:1593-1658`) postpones it: `set_postponed_receipt` stores the whole receipt keyed by `(account_id=A, receipt_id)`, plus `PostponedReceiptId`/`PendingDataCount` entries.
2. `A` self-deletes via `Action::DeleteAccount` (`action_delete_account`, `runtime/runtime/src/actions.rs:314-390`), which passes `check_actor_permissions` (self-call) and `remove_account` (`core/store/src/utils/mod.rs:504-575`). `remove_account` clears `TrieKey::Account`, `ContractCode`, access keys, gas keys, and contract data — but never clears `PostponedReceipt`, `PostponedReceiptId`, or `PendingDataCount` for that account.
3. Account name `A` is later recreated (e.g., by a factory/registrar contract handing the name to a new owner, or resold/reused as a top-level name), and a new owner adds their own keys, believing they control a clean, contract-free account.
4. At a moment of the original attacker's choosing, they deliver the `Data` receipt that satisfies the stashed `input_data_id`. `process_receipt`/`lib.rs` finds the still-present `PostponedReceiptId` link, decrements `PendingDataCount` to 0, loads the stale postponed receipt via `get_postponed_receipt`, and executes it against the *current* (recreated) `Account` object. The `UseGlobalContract` action runs `use_global_contract`, and since `actor_id == account_id` trivially holds (self-call baked into the old receipt), the check passes and `AccountContract` is rebound to the attacker's identifier — without the new owner ever issuing `UseGlobalContract` themselves.

No existing check (signature, nonce, access-key permission, or the actor/account-existence checks in `check_actor_permissions`/`check_account_existence`) revalidates that the account's *current* holder authorized this state-changing action, because the authorization was captured once at original receipt-send time and never re-checked against present ownership.

### Impact Explanation
This is an authorization-escalation / contract-identity hijack: an attacker can force a re-created account's `AccountContract` binding to arbitrary global contract code chosen at attack setup time, entirely bypassing the account's real (new) owner. Depending on the chosen global contract (e.g., a malicious lookalike of a wallet contract, or code with a backdoored key-management/`FunctionCall` behavior), this can be used to steal funds or hijack control of the recreated account, matching the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
The attacker only needs standard, unprivileged capabilities: fund an account, sign transactions, initiate a self-directed cross-contract call chain with a controllable completion time, and later submit a follow-up transaction to trigger completion. No validator/node/network access is required. The main precondition is that the account name gets reused by a different (or the same) party after deletion — plausible for sub-accounts issued by a registrar/factory contract, or for reclaimed top-level names — and that the attacker keeps the postponed dependency alive/controllable across that window, which is within their control (e.g., by controlling both ends of the promise chain or using long-lived promise-yield). The attack is repeatable for any account the attacker controls before giving it up.

### Recommendation
When executing a postponed (or otherwise resumed) receipt, re-validate account-identity-changing actions (`UseGlobalContract`, `DeployGlobalContract`, `DeployContract`, `AddKey`, `DeleteKey`, `Stake`) against the account's *current* state rather than relying solely on `actor_id == account_id` derived from a possibly stale `predecessor_id`. Concretely: (1) have `action_delete_account`/`remove_account` also purge any `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` entries keyed by the deleted account, cancelling in-flight self-call receipts (mirroring how yield/resume state should also be swept); and/or (2) record an account "generation"/creation nonce and stamp it into postponed receipts or `PendingDataCount`, rejecting resumption if the account has since been deleted and recreated.

### Proof of Concept
Integration test (in `runtime/runtime/src/tests/apply.rs`, alongside `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code`), across multiple `apply` calls / chunks:
1. Create account `A` with a full access key, deploy a global contract `G_attacker` (via `DeployGlobalContractAction` with an account-based identifier).
2. Submit a self-directed action receipt from `A` to `A` with `input_data_ids = [d]` and actions `[UseGlobalContractAction { contract_identifier: AccountId(G_attacker) }]`; assert it becomes a postponed receipt (does not execute, `PostponedReceipt`/`PendingDataCount` keys present in `TrieUpdate`).
3. Submit a `DeleteAccount` receipt from `A` to `A` (zero locked balance) and commit; assert `account.contract()` no longer exists and the account is absent.
4. Recreate account `A` with a fresh access key (simulating a new owner), and commit.
5. Deliver a `Data` receipt with `data_id = d` to `A`; run `apply` and assert the postponed receipt executes.
6. Assert `get_account(state_update, "A").contract()` now equals `AccountContract::GlobalByAccount(G_attacker)` even though the new owner never sent a `UseGlobalContract` action — confirming the contract-identity hijack.
