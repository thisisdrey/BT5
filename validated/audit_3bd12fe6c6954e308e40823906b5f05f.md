### Title
Bridged synthetic tokens are permanently burned when destination minting fails - (File: contracts/ProxyOFT.sol)

### Summary
`ProxyOFT.sendFrom()` debits a transfer by immediately burning the sender’s `SyntheticToken` before the LayerZero message is accepted on the destination chain. If destination execution later fails—for example, because the mint would exceed `maxBridgedInSupply`—LayerZero stores the packet for retry, but the source-chain burn is never reversed. An unprivileged attacker can keep the destination bridged-in cap saturated, causing subsequently delivered user transfers to remain undeliverable while the corresponding source-chain tokens have already been destroyed.

### Finding Description
`sendFrom()` calls `_send()`, which calls `_debitFrom()` before dispatching the LayerZero packet. [1](#0-0) 

`_debitFrom()` verifies the sender, bridging status, and destination support, then calls `syntheticToken.burn(from_, amount_)`; it does not escrow the tokens or record a refundable pending transfer. [2](#0-1) 

On receipt, a normal `PT_SEND` packet invokes `_creditTo()`, which calls `syntheticToken.mint(toAddress_, amount_)`. [3](#0-2) 

A ProxyOFT mint increments `totalBridgedIn` and reverts with `SurpassMaxBridgingSupply` once net bridged-in supply exceeds `maxBridgedInSupply`. [4](#0-3) 

The nonblocking receiver catches that revert and stores the packet hash as a failed message. [5](#0-4) 

`retryMessage()` can execute the same payload again, but it still reaches the same capped `mint()` call; if the attacker continues to occupy the available bridged-in supply, every retry reverts. [6](#0-5) 

There is no `BurnUnlock`-style callback, failure acknowledgement, cancellation function, or source-chain refund path in `ProxyOFT`; the production contract only exposes immediate burn-on-send and mint-on-receive logic. [7](#0-6) 

### Impact Explanation
The bridge conservation invariant breaks because the source-side burn and destination-side mint are not atomic and there is no compensating transaction for a permanently failing mint.

A user can lose the full bridged amount: their balance and `totalSupply` decrease on the source chain, while no corresponding destination balance is created. [8](#0-7) 

The failed destination packet does not restore source-chain funds, so the tokens remain burned unless a retry eventually succeeds. [9](#0-8) 

An attacker who occupies the destination’s remaining bridged-in capacity can therefore keep user funds frozen indefinitely: the source burn is final, while the destination packet remains unable to mint.

### Likelihood Explanation
The attack requires the attacker to bridge or otherwise cause enough inbound supply on the target chain to exhaust `maxBridgedInSupply`; it does not require a privileged role, a malicious endpoint, forged validator signatures, or control of the victim.

The deployed caps are finite; for example, mainnet msUSD permits 10 million bridged-in supply while Base msUSD permits up to 10 million bridged-out supply. [10](#0-9) [11](#0-10) 

Mainnet msETH uses equal 4,500-token inbound and outbound caps, so an attacker with sufficient bridgeable inventory can saturate the destination cap through ordinary public `sendFrom()` calls. [12](#0-11) 

After the cap is saturated, any otherwise valid packet whose amount exceeds remaining capacity is stored as failed rather than minted. [4](#0-3) [13](#0-12) 

### Recommendation
Do not make the source-side burn irreversible before destination success is guaranteed.

A safe design should either:

1. Escrow/lock source tokens and release or burn them only through an authenticated success acknowledgement.
2. Add an authenticated failure acknowledgement that lets the original sender reclaim the escrowed source tokens.
3. If immediate burn remains necessary for supply accounting, add a source-side recovery mechanism that can verify a destination packet as permanently failed and mint/refund the original sender.
4. Record sender, amount, destination chain, nonce, and payload identity for each outbound transfer so recovery cannot be claimed twice or by another account.

Merely relying on `retryMessage()` is insufficient because a cap violation can remain true indefinitely and `retryMessage()` provides no alternative recovery action. [6](#0-5) 

### Proof of Concept
A reproducible two-fork Hardhat test can demonstrate the invariant break:

```ts
// Source fork: Base; destination fork: mainnet.
// Alice has amount msUSD on Base and attacker fills mainnet's remaining
// maxBridgedInSupply through legitimate bridge deliveries first.

const fee = await baseProxyOFT.estimateSendFee(
  MAINNET_LZ_CHAIN_ID,
  alice.address,
  amount
);

const sourceBefore = await baseMsUSD.balanceOf(alice.address);

await baseProxyOFT.connect(alice).sendFrom(
  alice.address,
  MAINNET_LZ_CHAIN_ID,
  alice.address,
  amount,
  {value: fee}
);

// The source-side debit is complete immediately.
expect(await baseMsUSD.balanceOf(alice.address)).to.eq(
  sourceBefore.sub(amount)
);

// On the mainnet fork, deliver Alice's legitimate payload through the
// configured endpoint. Because the attacker keeps the inbound cap full,
// SyntheticToken.mint() reverts with SurpassMaxBridgingSupply and
// NonblockingLzApp stores the payload in failedMessages.

const payload = ethers.utils.defaultAbiCoder.encode(
  ["uint16", "bytes", "uint256"],
  [0, baseProxyOFT.address, amount]
);

await impersonate(mainnetLzEndpoint).sendTransaction({
  to: mainnetProxyOFT.address,
  data: mainnetProxyOFT.interface.encodeFunctionData("lzReceive", [
    BASE_LZ_CHAIN_ID,
    trustedRemotePath,
    nonce,
    payload
  ])
});

// No destination tokens are credited.
expect(await mainnetMsUSD.balanceOf(alice.address)).to.eq(destinationBefore);
expect(
  await mainnetProxyOFT.failedMessages(
    BASE_LZ_CHAIN_ID,
    trustedRemotePath,
    nonce
  )
).to.eq(ethers.utils.keccak256(payload));

// Retrying while the attacker leaves the cap saturated reverts; Alice's
// source tokens remain burned and no source-side refund entry point exists.
await expect(
  mainnetProxyOFT.retryMessage(
    BASE_LZ_CHAIN_ID,
    trustedRemotePath,
    nonce,
    payload
  )
).to.be.revertedWith("SurpassMaxBridgingSupply");
```

The critical ordering is demonstrated by `_debitFrom()` burning before `_lzSend()` on the source path and `_creditTo()` minting only during later destination execution. [14](#0-13)

```text
    function retryMessage(uint16 _srcChainId, bytes calldata _srcAddress, uint64 _nonce, bytes calldata _payload) public payable virtual {
        // assert there is message to retry
        bytes32 payloadHash = failedMessages[_srcChainId][_srcAddress][_nonce];
        require(payloadHash != bytes32(0), "NonblockingLzApp: no stored message");
        require(keccak256(_payload) == payloadHash, "NonblockingLzApp: invalid payload");
        // clear the stored message
        failedMessages[_srcChainId][_srcAddress][_nonce] = bytes32(0);
        // execute the message. revert if it fails again
        _nonblockingLzReceive(_srcChainId, _srcAddress, _nonce, _payload);
        emit RetryMessageSuccess(_srcChainId, _srcAddress, _nonce, payloadHash);
```
