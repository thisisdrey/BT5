### Title
Dust `DepositToken` transfers fill a victim's per-account token list (`MAX_TOKENS_PER_USER`), permanently blocking deposits/mints of new tokens — (File: contracts/Pool.sol, contracts/DepositToken.sol)

### Summary
`Pool` enforces a combined cap of `MAX_TOKENS_PER_USER = 30` on `depositTokensOfAccount` + `debtTokensOfAccount` via `onlyIfAdditionWillNotReachMaxTokens` [1](#0-0) [2](#0-1) . `DepositToken._transfer` (and `_mint`) unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance goes from 0 to >0, with no minimum amount [3](#0-2) . Because msd-tokens are freely transferable (`transfer`/`transferFrom` only check the sender's *unlocked* balance [4](#0-3) ), an unprivileged attacker can deposit dust and transfer 1 wei of each distinct `DepositToken` to any victim, filling the victim's list to the 30-token cap. The victim can also be pre-griefed: `deposit` mints `onBehalfOf_`, so `addToDepositTokensOfAccount` can be triggered for the victim directly [5](#0-4) .

### Finding Description
- `Pool.addToDepositTokensOfAccount` and `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the combined per-account list reaches 30 [6](#0-5) .
- Any attacker can call `DepositToken.deposit(1, victim)` (no minimum, only `amount_ == 0` reverts) to force-add that deposit token to the victim's list — no transfer even needed [7](#0-6) .
- Since the pool also caps total deposit tokens at `MAX_TOKENS_PER_USER` [8](#0-7) , a pool with N deposit tokens lets the attacker insert up to N entries into a victim's list at the cost of N dust deposits (plus gas).
- Once the victim's combined list hits 30: `deposit` into any collateral they don't already hold reverts inside `_mint` → `addToDepositTokensOfAccount`, and `DebtToken.issue`/`mint` of any new synthetic reverts inside `addToDebtTokensOfAccount`. The victim cannot add new collateral types or open new debt positions.
- Front-running variant: a victim's pending `deposit`/`mint` tx for a *new* token can be reverted by first dust-filling the last free slot.
- The dusted tokens also count toward the victim's `depositOf`/collateral, but 1-wei amounts are economically meaningless.

### Impact Explanation
Liveness/DoS on a core invariant: a targeted user is prevented from depositing new collateral or issuing new debt (both revert with `UserReachedMaxTokens`), matching the accepted "temporary freezing of funds"/griefing class. Victims can only recover by fully emptying a dusted balance (`withdraw`/`transfer` the full amount triggers `removeFromDepositTokensOfAccount`), which they can do for worthless dust but must discover and repeat, and the attacker can re-grief at negligible cost — a persistent, asymmetric DoS. It also degrades liquidation flow indirectly if used against accounts that need to top-up collateral of a type not already held.

### Likelihood Explanation
Fully reachable by any unprivileged EOA: the attack only requires `DepositToken.deposit` (public, `whenNotPaused`) and optionally `transfer`. No privileged roles, no oracle manipulation, no flash loans required. Cost is bounded by acquiring trace amounts of each listed underlying; for pools with many deposit tokens the attacker's spend is still trivial relative to permanently blocking a victim.

### Recommendation
- Enforce a minimum meaningful deposit/share amount before calling `addToDepositTokensOfAccount` (e.g., only track tokens above a USD dust threshold via `masterOracle`), or
- Replace the revert-on-cap design: don't revert in `addTo*` when at cap for shares received unsolicited, or keep the per-account list as a soft view filter, or
- Charge/bound griefing: require `onBehalfOf_ == _msgSender()` for the first-time deposit of a token (opt-in via allowance), so victims can't be force-added by deposits.

### Proof of Concept
Foundry/Hardhat sketch against a deployed pool fork:

```solidity
// Setup: pool has deposit tokens d1..dN (N >= remaining slots for victim)
address victim = /* target */;
IPool pool = IPool(POOL);

for (uint i; i < N; ++i) {
    IDepositToken dt = pool.depositTokens().at(i);
    IERC20 underlying = dt.underlying();
    deal(address(underlying), attacker, 1);
    underlying.approve(address(dt), 1);
    dt.deposit(1, victim); // or deposit(1, attacker) + dt.transfer(victim, 1)
}
// victim's combined list == 30 now

// Victim tries to deposit a collateral they don't hold yet:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDepositToken(newToken).deposit(amount, victim);

// Victim tries to mint a new synthetic debt:
vm.prank(victim);
vm.expectRevert(Pool.UserReachedMaxTokens.selector);
IDebtToken(newDebtToken).issue(amount, victim);
```

Reproducible on a fork of any chain where the pool lists ≥2 deposit tokens (deployments in `deployments/mainnet`, `optimism`, `base`, `hemi`, `swell` all expose `MAX_TOKENS_PER_USER`).
