### Title
Relay peer identity spoofing via unverified `RelayFromAddr` in `handleCreateRelayRequest` - (File: relay_manager.go)

### Summary
`relayManager.handleCreateRelayRequest` derives the relay's "from" (peer) address entirely from an attacker-controlled field in the authenticated `NebulaControl` payload (`m.RelayFromAddr`/`m.OldRelayFromAddr`), without checking that this claimed address actually belongs to the certificate identity of the tunnel (`h`) that delivered the message. This mirrors the reported bug class: an action is performed "on behalf of" an address supplied by the caller rather than the caller's own verified identity.

### Finding Description
In `relay_manager.go`, `HandleControlMsg` dispatches an incoming `Control` message to `handleCreateRelayRequest(v, h, f, msg)`. `h` is the `HostInfo` of the already-authenticated Noise/cert tunnel that delivered this encrypted control message — this is the only trustworthy identity available (the cryptographic equivalent of `msg.sender`).

Inside `handleCreateRelayRequest`: [1](#0-0) 

```
from := protoAddrToNetAddr(m.RelayFromAddr)
target := protoAddrToNetAddr(m.RelayToAddr)
...
if f.myVpnAddrsTable.Contains(from) {
    logMsg.Error("Discarding relay request from myself", "myIP", from)
    return
}
```

`from` is taken directly from the peer-supplied protobuf payload and is only checked against the local node's own address (to prevent self-impersonation), never against `h.vpnAddrs` — the certificate-verified VPN address(es) of the peer that actually sent the message.

When the target is the local node, the code proceeds to bind this attacker-chosen `from` value into relay state: [2](#0-1) 

```
if f.myVpnAddrsTable.Contains(target) {
    existingRelay, ok := h.relayState.QueryRelayForByIp(from)
    if ok {
        ...
    } else {
        _, err := AddRelay(rm.l, h, f.hostMap, from, &m.InitiatorRelayIndex, TerminalType, Established)
        ...
    }
    relay, ok := h.relayState.QueryRelayForByIp(from)
    ...
}
```

`AddRelay` is called with the authenticated `h` (the real, cert-verified tunnel) but registers it as terminal relay state keyed by the caller-supplied `from` address — never validated to be one of `h`'s own certificate networks (`h.vpnAddrs`), unlike the identity checks performed elsewhere in the codebase (e.g. `validatePeerCert` in `handshake_manager.go` explicitly binds `vpnAddrs` from the certificate: [3](#0-2) , and `Firewall.Drop` explicitly checks that a packet's claimed remote address is consistent with the peer's certificate networks: [4](#0-3) ).

By contrast, `handleCreateRelayRequest` accepts `from` purely from application-layer, attacker-controlled protobuf content, with no cross-check against `h`'s certificate networks. This directly parallels the report's root cause: the function performs a privileged, state-mutating action ("removeLiquidity" ≈ "AddRelay"/relay-state binding) using an address argument supplied by the caller (`_to` ≈ `from`) instead of verifying it against the caller's own authenticated identity (`msg.sender` ≈ `h.vpnAddrs`/`h`'s certificate).

### Impact Explanation
An authenticated-but-malicious peer (any node holding a valid CA-issued certificate, which is the baseline trust model for reaching this code, since the message must arrive over an already-established encrypted tunnel) can claim an arbitrary `RelayFromAddr` that is not actually one of its own certificate-bound VPN addresses. This causes the responder to record relay/hostmap state associating that arbitrary victim address with the attacker's tunnel (`h`), and to respond with a `CreateRelayResponse` binding that relay index. Depending on how the resulting relay conntrack/relayState entries are subsequently consulted for forwarding decisions, this can poison remote/relay state for a third-party address, cause traffic intended for the spoofed address to be mis-forwarded/relayed through the attacker's session, or create a route confusion condition consistent with a remote state-poisoning class impact.

### Likelihood Explanation
Likelihood is high for any peer able to establish a tunnel and exchange `Control`/`NebulaControl` relay-setup messages, since crafting `RelayFromAddr` to an arbitrary value requires only modifying an outgoing protobuf field — no additional cryptographic bypass is needed once a legitimate handshake exists. The only defensive check present (`f.myVpnAddrsTable.Contains(from)`) blocks self-impersonation of the local node, but does nothing to stop impersonation of any *other* peer's address.

### Recommendation
In `handleCreateRelayRequest` (and the analogous logic in `handleCreateRelayResponse`), validate that the claimed `from` (`RelayFromAddr`/`OldRelayFromAddr`) address is actually contained within `h.GetCert().Certificate.Networks()` (i.e., the certificate-bound VPN networks of the authenticated sender `h`), rejecting the request/response if it is not — mirroring the binding pattern already used in `validatePeerCert` and `Firewall.Drop`.

### Proof of Concept
Conceptual/protocol-level (no code execution performed):
1. Attacker `A` establishes a legitimate, cert-authenticated Nebula tunnel to responder `R` (target of relay).
2. `A` sends a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr` set to victim `V`'s VPN address (not `A`'s own) and `RelayToAddr` set to `R`'s own address.
3. `R`'s `handleCreateRelayRequest` only rejects the case where `from == R`'s own address; since `from == V ≠ A`, the check passes.
4. `R` calls `AddRelay(rm.l, h, f.hostMap, from=V, ..., TerminalType, Established)` where `h` is `A`'s HostInfo — binding relay state for `V` to `A`'s tunnel, and sends back a `CreateRelayResponse` confirming the (spoofed) relay-from binding, without ever verifying `V` is part of `A`'s certificate networks.

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}
