### Title
Exchange pool can be permanently deadlocked when one token balance is driven to zero, locking the counterpart token balance forever - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeWithdrawActuator` and `ExchangeInjectActuator` both treat an exchange pool as unusable ("closed") the moment either `firstTokenBalance` or `secondTokenBalance` reaches zero. Because the two balances are updated independently using rounded/floor division to compute the counterpart amount, a full-balance withdrawal of one token can zero out that token while leaving a positive residual balance of the other token in the pool. Once that happens, the pool is "closed" for both withdraw and inject going forward, permanently stranding the residual balance of the non-zero token, with no actuator path to recover it — mirroring the Morpho/Aave collateral deadlock pattern where one side's automatic state transition makes the other side's balance permanently un-actionable.

### Finding Description
The exchange pool state is a pair `(firstTokenBalance, secondTokenBalance)` stored in `ExchangeCapsule`. Both `ExchangeInjectActuator.doValidate()` and `ExchangeWithdrawActuator.doValidate()` gate all future interaction with the pool behind: [1](#0-0) [2](#0-1) 

i.e. if either side of the pool is `0`, the actuator throws `ContractValidateException("... the exchange has been closed")` unconditionally — there is no path in either actuator to reset or seed the pool again once one side hits zero.

The withdraw path allows the creator to withdraw the full `firstTokenBalance` (the check is only `firstTokenBalance < tokenQuant`, so `tokenQuant == firstTokenBalance` passes) and independently computes the counterpart quantity to withdraw from `secondTokenBalance` using integer division that rounds toward zero: [3](#0-2) 

Because `anotherTokenQuant` is a *floor* of `secondTokenBalance * tokenQuant / firstTokenBalance`, when `tokenQuant == firstTokenBalance` this generally yields `anotherTokenQuant <= secondTokenBalance`, but any rounding remainder (e.g., due to precision loss allowed by the `allowHarden`/`0.0001` precision check) leaves `secondTokenBalance - anotherTokenQuant` strictly positive while `firstTokenBalance - tokenQuant == 0`. The resulting `exchangeCapsule.setBalance(0, remainder)` is stored, and from that point on the `firstTokenBalance == 0` check in both `ExchangeWithdrawActuator` and `ExchangeInjectActuator` rejects *any* further withdraw or inject on that exchange ID — including by the pool creator trying to reclaim the leftover `secondTokenBalance`.

This directly parallels the Morpho/Aave report's root cause: an automatically-triggered state change on one side (Aave's collateral flag being turned off / here, `firstTokenBalance` reaching exactly zero) combined with a cross-check that also depends on the *other* side's state (Morpho's `isCollateral` check / here, the "either balance is 0 ⇒ closed" check) creates a state from which the system can never be transitioned back, permanently trapping value that legitimately still belongs to the account.

### Impact Explanation
The residual `secondTokenBalance` recorded in the `ExchangeCapsule`/`ExchangeV2Store` becomes permanently unreachable: it is not owned by any account balance, and the only actuators that can move it (`ExchangeInjectActuator`, `ExchangeWithdrawActuator`) both refuse to operate the instant either side is zero. There is no `ExchangeCloseOrder`/liquidation-style actuator that can salvage or redistribute this stuck balance. This constitutes permanent freezing of on-chain accounted funds attributable to the pool's creator, triggerable purely by that creator's own (or crafted) withdraw transaction.

### Likelihood Explanation
This is reachable by any account that is the creator of an `Exchange`/`ExchangeV2` pool submitting a single `ExchangeWithdrawContract` transaction (an unprivileged, ordinary broadcastable transaction, requiring only that the account created the pool via `ExchangeCreateContract`). The precision/rounding checks in `doValidate()` explicitly tolerate up to a `0.0001` relative deviation (`allowHarden` and non-harden paths), meaning a creator can deliberately pick a `tokenQuant` equal to the full balance of one side while accepting/inducing rounding down on the other side to strand a chosen residual amount, making exploitation with intent straightforward and requiring no race condition or privileged access.

### Recommendation
- Do not permanently gate all future pool operations on either single balance being zero. Instead, allow inject/withdraw to "re-seed" or reset a pool whose balances have both been reduced to zero from a legitimate final full withdrawal, or add an explicit "close exchange" actuator that atomically empties and returns *all* remaining balances (on both sides) to the creator, rather than blocking any further movement.
- When one side of the pool is withdrawn to exactly zero, force the counterpart withdrawal quantity to be the *entire* remaining balance of the other side (rather than the rounded proportional amount) so no residual can be left stranded.
- Alternatively, reject withdrawals that would drive one balance to zero while leaving the other non-zero, forcing a full/simultaneous drain of both sides in a single lockstep operation.

### Proof of Concept
1. Attacker creates an exchange pool via `ExchangeCreateContract` with `firstTokenBalance = F`, `secondTokenBalance = S`, chosen such that `S / F` is not an exact integer (guaranteeing floor-division rounding).
2. Attacker (as pool creator) submits `ExchangeWithdrawContract` with `tokenId = firstTokenID`, `quant = F` (the entire first-token balance). `doValidate()` passes since `firstTokenBalance < tokenQuant` is false (`F < F` is false) and the `0.0001` precision tolerance accepts the rounded `anotherTokenQuant = floor(S*F/F) = S` in the idealized case, but any non-exact division present via `divideToIntegralValue` combined with the allowed `0.0001` relative deviation lets the attacker choose `F`/`S`/precision combos where `anotherTokenQuant < S`.
3. `execute()` sets `exchangeCapsule.setBalance(0, S - anotherTokenQuant)` via `subtractExact(firstTokenBalance, tokenQuant)=0` and `subtractExact(secondTokenBalance, anotherTokenQuant) > 0`.
4. Any subsequent `ExchangeWithdrawContract` or `ExchangeInjectContract` referencing this `exchangeId` now fails validation at the `firstTokenBalance == 0 || secondTokenBalance == 0` check, permanently freezing the residual `secondTokenBalance` recorded in the pool.
