### Title
`remove_account` fails to clear postponed-receipt / promise-yield trie keys, letting a self-authorized privileged action (e.g. `DeleteAccount`) planted before deletion silently fire against a future, unrelated account that reuses the same name - (File: `core/store/src/utils/mod.rs`)

### Summary
`remove_account` only clears `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` trie rows for an account, but `TrieKey::get_account_id()` also returns `Some(account_id)` for eight other account-scoped columns: `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`. `action_delete_account` never checks for outstanding postponed/promise-yield state before deleting an account, so an attacker can leave a "time-bomb" self-action receipt (`predecessor_id == receiver_id == account_id`) parked in one of these columns, delete the account, and later resolve the pending data dependency (which the attacker still controls via the surviving `YieldIdToDataId`/`DataIdToYieldId` mapping) once someone else re-registers the same account name and funds it — the parked receipt then executes as a legitimately self-authorized privileged action (e.g. `DeleteAccount{beneficiary: attacker}`) against the new occupant's account.

### Finding Description
`core/primitives/src/trie_key.rs:589-619` (`TrieKey::get_account_id`) recognizes account-scoping for 13 variants, and `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`core/primitives/src/trie_key.rs:89-102`) lists 12 concrete account-keyed columns. `remove_account` (`core/store/src/utils/mod.rs:505-575`) only removes:
- `TrieKey::Account` [1](#0-0) 
- `TrieKey::ContractCode` (same lines)
- Access keys / gas-key nonces via `trie_key_parsers::get_raw_prefix_for_access_keys` [2](#0-1) 
- Contract data via `trie_key_parsers::get_raw_prefix_for_contract_data` [3](#0-2) 

It never touches `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, or `DataIdToYieldId`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) only validates `account_storage_usage` and gas-key burn amount before calling `remove_account`, with no check for pending postponed receipts or promise-yields targeting the account being deleted [4](#0-3) .

Postponed/promise-yield resolution is keyed purely by `receiver_id` string and does not re-verify continuous account identity: `process_receipt`'s `Data` arm resolves `PostponedReceiptId`/`PendingDataCount`/`PostponedReceipt` for `account_id` and executes the recovered receipt via `apply_action_receipt` regardless of whether the account existed continuously [5](#0-4) ; the `PromiseResume` arm similarly looks up `PromiseYieldReceipt`/`YieldIdToDataId`/`DataIdToYieldId` by `account_id` only and executes it [6](#0-5) . `apply_action_receipt` fetches `account_id`'s current account state at execution time and dispatches actions against it [7](#0-6) ; `check_account_existence` requires `account.is_some()` for privileged actions like `DeleteAccount`/`AddKey`/`DeployContract` [8](#0-7) , which trivially passes once the same account name has been re-created by anyone. Self-authorization for `DeleteAccount`/`AddKey`/`DeployContract`/`Stake` is enforced by comparing `actor_id` (initialized from `receipt.predecessor_id()`) against `account_id` as plain strings, with no per-incarnation generation/epoch counter to distinguish the old account from a newly re-created one of the same name.

Exploit flow:
1. Attacker creates account `X` (a subaccount they control, or any name), deploys a small contract.
2. From `X`, the contract issues a self-targeted action receipt (`predecessor_id == receiver_id == X`) containing `[DeleteAccount{beneficiary_id: attacker}]`, with an unresolved data dependency (via a cross-contract call the attacker's own second contract never answers, or via `promise_yield_create`). This is recorded under `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` (or `PromiseYieldReceipt`/`YieldIdToDataId`/`DataIdToYieldId`) keyed by `X`.
3. Attacker sends an ordinary `DeleteAccount` transaction on `X` (with near-zero balance/state, passing `MAX_ACCOUNT_DELETION_STORAGE_USAGE`). `remove_account` clears `Account`/`ContractCode`/`AccessKey`/`ContractData` for `X`, but the planted postponed/promise-yield rows survive.
4. Account name `X` is now free and, at some later point (natural churn of freed/short account names on NEAR, or reuse via the `near` top-level registrar for any subaccount pattern the attacker chooses), gets re-created and funded by an unrelated third party, entirely independent of the attacker.
5. Attacker resolves the still-pending data dependency (they retained the `data_id`/`yield_id` from step 2, which is still resolvable because `YieldIdToDataId`/`DataIdToYieldId` were never cleared) by sending the corresponding `Data`/`PromiseResume` receipt.
6. The stale receipt executes `DeleteAccount{beneficiary_id: attacker}` against the *new* occupant of `X`. `check_account_existence` passes because `X` currently exists; `check_actor_permissions`'s self-check passes because `predecessor_id == account_id == "X"` as a plain string, regardless of the fact that the account was deleted and re-created in between. The new owner's balance is sent to the attacker.

None of the existing checks (signature/nonce verification, access-key permission, `check_account_existence`, `MAX_ACCOUNT_DELETION_STORAGE_USAGE`, gas-key balance cap) stop this, because they are all evaluated against the *current* account state and the receipt's *original* `predecessor_id`/`receiver_id`, with no mechanism distinguishing successive incarnations of the same account name.

### Impact Explanation
Concrete impact: theft of funds from whoever re-creates and funds the reused account name (`DeleteAccount{beneficiary_id: attacker}` sweeps the victim's entire current balance to the attacker), i.e. an authorization-escalation bug where a receipt authorized by a since-deleted account is later treated as self-authorized against a completely different, unrelated occupant of the same name. This matches the NEAR bounty categories "theft of user funds" and "authorization escalation across accounts or promises."

### Likelihood Explanation
Preconditions: the attacker needs full control of one account (trivial — any funded NEAR account can deploy a contract and issue promises/yields to itself), needs to time-bomb it with a self-targeted postponed/promise-yield receipt before self-deleting, and needs the exact account name to later be reused and funded by an independent party (which does happen on NEAR — deleted/abandoned subaccounts and short/premium top-level names are commonly re-registered). The attacker fully controls the trigger timing (it is their own pending `data_id`/`yield_id`), so the attack is repeatable at will and at negligible cost (a handful of cheap transactions). The only real-world constraint is waiting for/inducing name reuse, which does not require deceiving any specific victim (no social engineering of a targeted individual is needed — it exploits systemic account-name churn).

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also sweep the remaining account-scoped columns for the account being deleted — `ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId` — using the same prefix-iteration pattern already used for access keys/contract data (`trie_key_parsers`), or alternatively add a protocol-level check in `action_delete_account` that rejects `DeleteAccount` while the account has any pending postponed receipt / promise-yield / received-data still outstanding for it. Consider also tying `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` to a compile-time or unit-test assertion that every column in that list is provably swept by `remove_account`, so future additions to `TrieKey` cannot silently reintroduce this gap.

### Proof of Concept
Unit test plan (in `core/store` or `runtime/runtime` test suite):
1. Build a `TrieUpdate` and manually populate one row for each of the 8 survivor `TrieKey` variants for a fixed `account_id` (`ReceivedData`, `PostponedReceiptId`, `PendingDataCount`, `PostponedReceipt`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, `DataIdToYieldId`), plus one row for each of `Account`, `ContractCode`, `AccessKey`, `ContractData`.
2. Call `remove_account(state_update, &account_id)`.
3. Assert `Account`/`ContractCode`/`AccessKey`/`ContractData` rows are gone (expected to pass).
4. Assert each of the 8 survivor rows is *also* gone — expected to **fail** on current code, proving the gap. This can be automated by iterating `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`core/primitives/src/trie_key.rs:89-102`) and checking each column is empty after `remove_account`.
5. Integration/test-loop PoC mirroring `test-loop-tests/src/tests/create_delete_account.rs`: create account `X`, have it self-issue a `PromiseYield`/postponed receipt containing `DeleteAccount{beneficiary_id: attacker}` with an attacker-controlled unresolved dependency, delete `X`, re-create `X` with a fresh key and deposit funds into it, then resolve the pending dependency and assert the new `X` account is deleted and its balance transferred to `attacker` — despite `X`'s new owner never authorizing this.
