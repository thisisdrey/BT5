### Title
Ignored DMA/native-worker completion timeout in TVM precompile lets `VerifyTransferProof` bypass energy-time enforcement - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts.VerifyTransferProof.execute()` submits Sapling spend/output/binding-signature verification tasks to a shared worker pool and waits on a `CountDownLatch` bounded by the remaining CPU time budget, but discards the boolean result of the wait.

### Finding Description
In `VerifyTransferProof.execute()` the code does: [1](#0-0) 
`countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)` returns `withNoTimeout`, a boolean indicating whether all submitted `SaplingCheckSpendTask`/`SaplingCheckOutputTask`/`SaplingCheckBingdingSig` callables completed before the transaction's CPU-time budget expired. That value is assigned but never inspected — execution falls straight through to `future.get()` for every submitted task and continues to `insertLeaves(...)` as if the call finished within budget.

This is the analog of the kernel bug: `lpc32xx_xmit_dma()` ignored `wait_for_completion_timeout()`'s return and treated a timed-out DMA as successful. Here the sibling method `BatchValidateSign.doExecute()` in the same file correctly checks the identical pattern and throws on timeout: [2](#0-1) 
`VerifyTransferProof` omits this check entirely, so `withNoTimeout` is dead code and the CPU-time guardrail designed for exactly this situation (`getCPUTimeLeftInNanoSecond()`, mirrored by `MUtil.checkCPUTime()` / `Program.Exception.notEnoughTime` elsewhere in the VM) is not enforced for this precompile.

### Impact Explanation
Because the timeout is not enforced, a caller-triggered `VerifyTransferProof` invocation (reachable from any smart contract or transaction that calls the precompile at the zk-SNARK Sapling address) can consume worker-pool threads and native `librustzcash` verification time well past the transaction's allotted CPU/energy time slice, since `future.get()` blocks unconditionally rather than failing fast. Repeated or concurrent calls that exhaust the shared `workersInConstantCall`/`workersInNonConstantCall` pools (fixed size 5) can stall block processing/validation for other transactions relying on the same precompile, and — more importantly — violate the energy-time accounting invariant that every other precompile (`BatchValidateSign`) upholds, allowing execution to run without the intended timeout-based abort. This is a node-availability (processing stall / halt-class) issue reachable by any unprivileged transaction sender who can trigger `VerifyTransferProof`.

### Likelihood Explanation
Likelihood is high for anyone able to submit a transaction invoking the Sapling `VerifyTransferProof` precompile with proof/data ready to keep the native verification busy near a fork boundary or under contention; no special privileges are required, only a normally-signed transaction reaching this precompile.

### Recommendation
Check the `withNoTimeout` result exactly like `BatchValidateSign` does, and if `false`, abort verification (throw `Program.Exception.notEnoughTime(...)` or an equivalent `OutOfTimeException`) before calling `future.get()` on the outstanding futures, cancelling/interrupting the still-running tasks so the worker pool cannot be starved by a stalled call.

### Proof of Concept
1. Craft a `VerifyTransferProof` precompile call (valid-size `data` per `SIZE` array) whose proof causes `librustzcashSaplingCheckSpendNew`/`librustzcashSaplingFinalCheckNew` to run long (or drive concurrent calls to saturate the fixed 5-thread `workersInConstantCall`/`workersInNonConstantCall` pools) so that `countDownLatch.await(getCPUTimeLeftInNanoSecond(), NANOSECONDS)` returns `false`.
2. Observe execution proceeds unchanged: `future.get()` blocks until the queued tasks finally run, `withNoTimeout` is never consulted, and no `OutOfTimeException`/`notEnoughTime` is thrown — unlike the identical pattern in `BatchValidateSign`, which does abort in this situation. [3](#0-2)
