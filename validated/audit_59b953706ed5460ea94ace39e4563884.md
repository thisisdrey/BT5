### Title
`FindRemoteRepository` passes unvalidated user-supplied remote string directly into `git-ls-remote(1)` argument list, enabling SSRF / local file access via arbitrary remote URLs - ([File: internal/gitaly/service/remote/find_remote_repository.go])

### Summary
The external report describes a class of bug where a user-controlled payload (`userData`) is forwarded into a sensitive operation without validating its content or origin, letting an attacker redirect execution/flow to an unintended target. The closest reachable analog in Gitaly is `RemoteService.FindRemoteRepository`, which takes an ordinary user/API-supplied `remote` string and passes it, unvalidated beyond a non-empty check, straight into `git-ls-remote(1)` as an executable target.

### Finding Description
`FindRemoteRepository` only checks that `req.GetRemote()` is non-empty before using it as a positional argument to `git ls-remote`: [1](#0-0) 

The `Command.Args` field is documented as unsafe for direct user-controlled input; only its leading-dash requirement is enforced by `validatePositionalArg`, which does not restrict the value to legitimate `http(s)://`/`git://`/`ssh://` transports: [2](#0-1) 

The `ls-remote` command description contains no `validatePositionalArgs` override and no restriction that would prevent scheme values such as `file://`, `ext::`, or SCP-style specs from being accepted as `Args`: [3](#0-2) 

Compare this to the more careful handling in `FindRemoteRootRef`, which routes remote URLs through `GetURLAndResolveConfig` and explicitly whitelists schemes (`http`, `https`, `git`, `ssh`) before use, rejecting unknown schemes: [4](#0-3) 

`FindRemoteRepository` has no equivalent scheme validation or resolved-address pinning, so any value accepted by `git-ls-remote(1)` (including `file://<path>`, `ext::<cmd>` if allowed by protocol.allow config, or local relative paths) is passed through as-is.

### Impact Explanation
An unprivileged caller with access to the `FindRemoteRepository` RPC (exposed to GitLab Rails/API on behalf of an ordinary user action such as checking whether a mirror/import URL is reachable) can supply a `remote` value pointing at internal-only endpoints, local Gitaly-accessible paths, or `file://` targets. This can be used for SSRF against internal services/metadata endpoints, or (depending on the Git binary's `protocol.*.allow` configuration) to probe or read local storage on the Gitaly host that the Gitaly process user can access, since Git will treat the string as a valid transport locator and dial it directly. At minimum this discloses whether internal URLs/paths exist (`Exists: true/false`), and depending on configured Git transport helpers, could expand further.

### Likelihood Explanation
Likelihood is high: `FindRemoteRepository` requires only that a caller can invoke the RPC with an arbitrary `remote` string (any ordinary import/mirror-configuration flow that lets a user specify a remote URL could reach this path), and no scheme allow-list or destination validation is performed before the argument reaches `git-ls-remote(1)`.

### Recommendation
Validate `req.GetRemote()` before use: enforce an explicit scheme allow-list (`http`, `https`, `git`, `ssh`) analogous to `GetURLAndResolveConfig`/`getURLAndResolveConfigForURL`, reject `file://`, `ext::`, and other local/executable transport forms, and consider requiring/propagating a resolved IP address (as `FindRemoteRootRef` and `CreateRepositoryFromURL` already do) to avoid SSRF via DNS rebinding. At minimum, reuse the existing URL-resolution/validation helper used by the other remote RPCs instead of passing the raw string as a plain positional `Args` entry.

### Proof of Concept
1. Call `RemoteService.FindRemoteRepository` with `Remote: "file:///var/opt/gitlab/git-data/repositories/some-internal-repo.git"` (or any Gitaly-host-local path, or an internal-only `http://169.254.169.254/...`-style endpoint reachable by the Gitaly process).
2. Gitaly builds `git ls-remote <remote> HEAD` with no scheme/target validation: [5](#0-4) 
3. Git executes the transport for the supplied scheme/path directly from the Gitaly host, and the RPC response (`Exists: true/false`) leaks whether the target is a valid ref-advertising endpoint — usable as an internal network/file-existence oracle.

Note: I could not fully verify at what layer (Rails/Workhorse) authorization/scoping is applied before this RPC is reachable by an "ordinary user," since that logic lives outside the Gitaly repo; this assessment is based solely on the Gitaly-side code path shown above.

```go
func (s *server) FindRemoteRepository(ctx context.Context, req *gitalypb.FindRemoteRepositoryRequest) (*gitalypb.FindRemoteRepositoryResponse, error) {
	if req.GetRemote() == "" {
		return nil, structerr.NewInvalidArgument("empty remote can't be checked.")
	}

	var output bytes.Buffer
	cmd, err := s.gitCmdFactory.NewWithoutRepo(ctx,
		gitcmd.Command{
			Name: "ls-remote",
			Args: []string{
				req.GetRemote(),
				"HEAD",
			},
		},
		gitcmd.WithStdout(&output),
	)
```

```go
func getURLAndResolveConfigForURL(remoteURL, resolvedAddress string) (string, []ConfigPair, error) {
	u, err := url.ParseRequestURI(remoteURL)
	if err != nil {
		return "", nil, fmt.Errorf("couldn't parse remoteURL: %w", err)
	}

	port := u.Port()

	if port == "" {
		switch u.Scheme {
		case "http":
			port = "80"
		case "https":
			port = "443"
		case "git":
			port = "9418"
		default:
			return "", nil, fmt.Errorf("unknown schema provided: %s", u.Scheme)
		}
	}
```
