### Title
Unauthenticated Stage-1 Handshake Packets Force Uncharged Asymmetric Crypto, Enabling CPU-Exhaustion DoS - ([File: handshake_manager.go])

### Summary
The external report describes a bug where an unauthenticated action (transferring an NFT to a new owner) causes state to be created (`tokens_per_owner` entry) without the cost of that state being charged to the party that triggers it, letting an attacker cheaply exhaust the victim's resources. The reachable analog in this Nebula codebase is `HandshakeManager.beginHandshake` (`handshake_manager.go`), which performs a full Noise Diffie-Hellman handshake step for every inbound stage-1 packet before any certificate is verified and with no per-source rate limiting, cookie, or proof-of-work gate — the computational cost of the cryptographic operation is never "charged" to the unauthenticated sender.

### Finding Description
`HandshakeManager.HandleIncoming` dispatches any packet with `MessageCounter == 1` and `RemoteIndex == 0` directly to `beginHandshake`, gated only by a subtype check and the lighthouse remote allow list (a config-based address filter, not an authentication or cost mechanism): [1](#0-0) 

`beginHandshake` then constructs a new Noise `Machine` and immediately calls `machine.ProcessPacket(nil, packet)` — this is *before* any certificate has been verified: [2](#0-1) 

Internally, `ProcessPacket` calls `m.hs.ReadMessage(...)`, which performs the Noise `DH` operation (an elliptic-curve Diffie-Hellman computation) as part of advancing the handshake state: [3](#0-2) 

Certificate validation (`hm.validatePeerCert`) only happens *after* this expensive asymmetric operation has already completed: [4](#0-3) 

There is no rate limiting, per-source throttling, or handshake cookie mechanism anywhere in the codebase (`grep` for `rate.?limit|cookie|RateLimit` returns no matches) to bound how often an unauthenticated sender can force this DH computation. Unlike protocols such as WireGuard, which use a cookie-reply mechanism specifically to avoid spending asymmetric-crypto cycles on unauthenticated senders during high load, Nebula performs the DH step unconditionally for every syntactically valid stage-1 packet.

This mirrors the root cause of the external report: an operation that creates cost (there, storage; here, CPU cycles for ECDH) is triggered by an unauthenticated/uncharged actor, and the system has no mechanism to make the triggering party pay for or be limited in the resource it consumes.

### Impact Explanation
An attacker with no valid CA-signed certificate can send a stream of spoofed or arbitrary stage-1 handshake packets (`RemoteIndex=0`, `MessageCounter=1`, valid subtype) to any Nebula node's UDP listener. Each such packet forces the responder to allocate a new `handshake.Machine` and perform a full Noise `ReadMessage`/DH computation before the certificate is even inspected. Because the cost is identical regardless of whether the sender holds a valid certificate, and there is no per-source limiting, an attacker can drive sustained CPU consumption on the victim node with minimal cost to themselves (a single UDP packet), degrading or denying handshake processing for legitimate peers — a remote, unauthenticated CPU-exhaustion DoS.

### Likelihood Explanation
Likelihood is high: the path is reachable by any network attacker capable of sending UDP packets to the node's listening port, requires no certificate, no prior handshake state, and no knowledge of any secret. The only gate is the lighthouse `remote_allow_list`, which is an operator-configured address allowlist/denylist, not a cryptographic or rate-limiting defense, and is disabled by default.

### Recommendation
Introduce a cost/rate-limiting mechanism before performing the expensive Noise `ReadMessage`/DH step in `beginHandshake`, analogous to charging the storage cost up front in the original report. Options:
- Add per-source-IP rate limiting or a global token bucket for stage-1 handshake processing in `HandshakeManager.HandleIncoming`/`beginHandshake`.
- Add a stateless cookie/puzzle-reply mechanism (as WireGuard does) so unauthenticated senders must demonstrate return-path reachability or minimal proof-of-work before the responder invests in the DH computation.
- At minimum, cap the number of in-flight/attempted handshakes processed per source address per interval.

### Proof of Concept
1. Start a Nebula node listening on UDP (no `remote_allow_list` configured, or configured permissively).
2. From an attacker machine with no CA-issued certificate, craft raw UDP packets matching the wire format expected by `HandleIncoming`: header `Type=Handshake`, `Subtype=HandshakeIXPSK0`, `MessageCounter=1`, `RemoteIndex=0`, followed by arbitrary/garbage Noise payload bytes of sufficient length to pass `len(packet) < header.Len` (see `handshake/machine.go` `ProcessPacket`, lines 203-210).
3. Flood these packets (varying source port/content) at high rate toward the victim's listener.
4. Observe that each packet reaches `beginHandshake` and triggers `machine.ProcessPacket`, which performs a Noise `ReadMessage` (DH computation) before any certificate check fails it — repeat measurement of CPU usage on the victim shows sustained load proportional to attacker packet rate, with no corresponding rate limit or cookie challenge slowing the attacker down.

```go
func (m *Machine) ProcessPacket(out, packet []byte) ([]byte, *Result, error) {
	if m.failed {
		return nil, nil, ErrMachineFailed
	}
	if len(packet) < header.Len {
		return nil, nil, ErrPacketTooShort
	}
	// Reject packets whose subtype doesn't match the one this Machine was
	// built for. A pending handshake that suddenly receives a different
	// subtype on its index is either a stray packet that matched by chance
	// or a peer protocol violation; drop it without failing the Machine so
	// the legitimate retransmit can still complete.
	if header.MessageSubType(packet[1]) != m.subtype {
		return nil, nil, ErrSubtypeMismatch
	}
	if m.result.Initiator && m.hs.MessageIndex() == 0 {
		m.failed = true
		return nil, nil, ErrInitiateNotCalled
	}

	// The (eKey, dKey) ordering here is correct for IX, where the initiator
	// completes the handshake by reading the responder's stage-2 message.
	// noise returns (cs1, cs2) where cs1 is the initiator->responder cipher.
	// For 3-message patterns where a responder finishes by reading the final
	// message, this ordering would be wrong; revisit when XX/pqIX lands.
	msg, eKey, dKey, err := m.hs.ReadMessage(nil, packet[header.Len:])
	if err != nil {
		// Noise ReadMessage failed. The noise library checkpoints and rolls back
		// on failure, so the Machine is still alive. The caller can retry with
		// a different packet.
		return nil, nil, fmt.Errorf("noise ReadMessage: %w", err)
	}
```
