Audit Report

## Title
`revoke_inheritor` does not clear stale, higher-priority `Attempt`s left by a friend group that already lost the inheritance race, letting a discarded friend group take over the account later - (File: `substrate/frame/recovery/src/lib.rs`)

## Summary
`pallet-recovery`'s `revoke_inheritor` only removes the `Inheritor::<T>` entry for the lost account and never inspects or purges outstanding `Attempt::<T>` entries, unlike `set_friend_groups` which explicitly checks `Attempt::<T>::iter_prefix(&lost)` before allowing modification. Because `finish_attempt`'s `None` branch unconditionally installs whatever inheritor is provided once `Inheritor::<T>::get(&lost)` returns `None`, a stale, fully-approved lower-priority `Attempt` that predates the current inheritor can be finished after `revoke_inheritor` is called, silently reinstating control the account owner never approved.

## Finding Description
`initiate_attempt` (`substrate/frame/recovery/src/lib.rs` L706-711) only rejects a new attempt when an `Inheritor` already exists and the new friend group's priority is not strictly higher. It performs no check against other pending `Attempt` entries, so a lower-priority group's attempt can be initiated and fully approved concurrently with, or even before, a higher-priority group's attempt while `Inheritor` is still unset. Once the higher-priority group calls `finish_attempt` and sets `Inheritor::<T>` (L835-847), the lower-priority `Attempt` entry remains untouched in storage — `finish_attempt` only calls `Attempt::<T>::take` on the attempt actually being finished (L804-805), not on other pending attempts for the same `lost` account.

`revoke_inheritor` (L609-620) only does `Inheritor::<T>::take(&lost)` and drops the inheritor's ticket; it has no analog to the `Attempt::<T>::iter_prefix(&lost).next().is_some()` guard used in `set_friend_groups` (L638-640). Consequently, after `revoke_inheritor` clears `Inheritor`, `finish_attempt` can be called on the previously-discarded, still-approved attempt. Since `Inheritor::<T>::get(&lost)` now returns `None`, execution falls into the `None => { ... Inheritor::<T>::insert(...) }` branch (L838-847) unconditionally, reinstating an inheritor the lost account never re-approved and had no visibility into after revoking.

## Impact Explanation
This is a runtime bug that compromises intended behavior and results in unauthorized origin escalation: an account owner who has regained signing capability and explicitly revokes an unwanted inheritor relationship can have control silently handed to a different, previously-discarded friend group without any new approval action. `Inheritor::<T>` (the value gating who can call `as_recovered`/control the lost account) is corrupted to a value the owner did not sanction.

## Likelihood Explanation
Exploitability requires only unprivileged actors: the lost account owner configuring two friend groups via `set_friend_groups`, and members of those friend groups calling `initiate_attempt`/`approve_attempt`. `finish_attempt` is explicitly permissionless ("Can be called by anyone who is willing to pay for the inheritor deposit," L792). The only preconditions are (1) two friend groups with differing priorities, and (2) a lower-priority attempt reaching full approval while unresolved, then surviving past the higher-priority group's `finish_attempt` and the owner's `revoke_inheritor`. No validator, governance, or node-level compromise is needed, and the sequence is deterministically reproducible.

## Recommendation
Have `revoke_inheritor` purge all remaining `Attempt::<T>` entries under prefix `lost` (returning deposits/tickets similarly to `cancel_attempt`), or require `Attempt::<T>::iter_prefix(&lost).next().is_none()` as a precondition, forcing the owner to explicitly cancel all pending attempts before `revoke_inheritor` can succeed.

## Proof of Concept
1. Alice calls `set_friend_groups` configuring Group 0 (priority 0) and Group 1 (priority 1).
2. A Group 1 friend calls `initiate_attempt(lost=Alice, friend_group_index=1)` and gathers enough `approve_attempt` votes to reach `friends_needed`, but does not call `finish_attempt` yet — its `Attempt` entry sits fully approved in storage.
3. A Group 0 friend runs `initiate_attempt`/`approve_attempt`/`finish_attempt` for index 0; `Inheritor::<T>` becomes `(priority=0, inheritor=Group0Inheritor)`.
4. Alice calls `revoke_inheritor()`, which only clears `Inheritor::<T>` via `Inheritor::<T>::take(&lost)` (L613).
5. Anyone calls `finish_attempt(lost=Alice, friend_group_index=1)`. Since `Inheritor::<T>::get(&lost)` is `None`, the `None` branch at L838-847 executes unconditionally, setting `Inheritor::<T>` to Group 1's inheritor — reinstating control Alice never re-approved.
