Based on my research into the bazel repository's archive-parsing code, I found a strong analog in ijar's ZIP central-directory parser.

### Title
Heap-based buffer over-read in ZIP central directory extra-field parsing during interface-jar generation - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the "extra fields" of a ZIP central directory entry using attacker-controlled length values with no bounds checking against the mapped input file, allowing a crafted `.jar`/`.zip` file to drive the cursor past the end of the mapped region and read out-of-bounds heap memory, mirroring the crafted-file heap over-read pattern of CVE-2018-11625.

### Finding Description
`ProcessCentralDirEntry` reads `extra_field_length` directly from the untrusted central directory header and sets `p = extra_p + extra_field_length` [1](#0-0) . It then loops `while (extra_p != p)`, reading a 2-byte `header_id` and 2-byte `data_size` from `extra_p`, and unconditionally advances `extra_p += data_size` before dereferencing `extra` (via `get_u8le(extra)`) when the tag is `ZIP64_EXTRA_FIELD_TAG` [2](#0-1) .

Because `data_size` is a fully attacker-controlled 16-bit value taken from the file itself, nothing guarantees `extra_p` lands exactly on `p` after any iteration. If it overshoots `p`, the loop condition `extra_p != p` remains true (the pointers never become equal again in this direction), so the loop continues reading `header_id`/`data_size`/`extra` beyond the legitimate extra-field region — and beyond the mapped file entirely once it walks past the end of the memory-mapped input. Unlike `ProcessLocalFileEntry`, which calls `EnsureRemaining()` before reading `file_name`/`extra_field` [3](#0-2) , `ProcessCentralDirEntry` performs **no** `EnsureRemaining` / bounds check at all — the function's own comment asserts "parsing it this way is safe" [4](#0-3)  based only on the *outer* central-directory-entry framing, not on the inner extra-field sub-record walk.

This function is invoked both per-entry via `ProcessNext` and exhaustively via `CalculateOutputLength`, which walks the entire central directory of any jar being processed by the `ijar` tool used to build interface jars for Java compilation [5](#0-4) .

### Impact Explanation
An out-of-bounds read past the memory-mapped file can read adjacent heap/process memory. Because the OOB bytes are then interpreted as `uncompressed_size`, `compressed_size`, or `offset` via `get_u8le(extra)`, corrupted/leaked memory values are propagated into size and offset computations used downstream (e.g., `CalculateOutputLength`, subsequent `EnsureRemaining` checks in `ProcessLocalFileEntry`), which can lead to incorrect buffer sizing in later stages of ijar processing, beyond a simple crash — this is a genuine memory-safety defect in parsing of untrusted archive content, not a mocked or benign case.

### Likelihood Explanation
Any `.jar` archive processed by `ijar` (e.g., a third-party dependency fetched without a pinned/enforced checksum, or content served from a compromised/hostile mirror before checksum verification is mandatory) can trigger this by embedding a crafted extra field with a `data_size` that does not evenly divide the extra-fields length, causing the cursor to skip past the boundary. No special privileges are required — only the ability to have the build consume attacker-authored ZIP/JAR bytes.

### Recommendation
Add explicit bounds validation inside the extra-field loop in `ProcessCentralDirEntry` (and any equivalent extra-field walkers) verifying that each read of `header_id`, `data_size`, and the referenced `data_size` bytes stays within `[extra_p_start, p)` and within the file's mapped length before dereferencing, failing/erroring out rather than continuing the walk when `extra_p` would exceed `p`.

### Proof of Concept
Construct a ZIP file whose central directory entry declares `extra_field_length = N`, but embeds a single extra-field sub-record with `data_size` greater than `N - 4` (or a value that makes cumulative advances never land exactly on `N`). When `ijar`/`InputZipFile::ProcessCentralDirEntry` parses this entry (e.g. via a `BuildIntegrationTestCase` that builds a `java_library` depending on such a crafted jar, or a direct unit test invoking `ProcessCentralDirEntry` on a manually constructed buffer with `data_size` exceeding the buffer footprint), the `while (extra_p != p)` loop overshoots `p`, continuing to call `get_u2le`/`get_u8le` on memory beyond the crafted extra-field region — and, for a minimal input file, beyond the mapped file — demonstrating the heap-based buffer over-read.
