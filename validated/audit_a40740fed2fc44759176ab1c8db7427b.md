### Title
Data race on shared static `PrecompiledContract` singletons lets concurrent constant calls and block-processing transactions cross-contaminate `Repository`/caller context — ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
`PrecompiledContracts` are instantiated once as `private static final` singletons (`batchValidateSign`, `validateMultiSign`, `delegatableResource`, `checkUnDelegateResource`, etc.) [1](#0-0) . Every invocation of a precompile — whether from a real, broadcastable transaction executed on the block-application thread, or from a read-only constant call (`eth_call`, `TriggerConstantContractServlet`, `EstimateEnergyServlet`) executed on an HTTP/gRPC worker thread — mutates the *same shared instance's* fields (`setCallerAddress`, `setRepository`, `setResult`, `setConstantCall`, `setVmShouldEndInUs`) immediately before calling `contract.execute(data)` [2](#0-1) . There is no synchronization protecting this set-then-execute sequence.

### Finding Description
`Program.callToPrecompiledAddress` looks up the precompile for `codeAddress` (a process-wide singleton returned by `PrecompiledContracts.getContractForAddress`) and then does:
```
contract.setCallerAddress(...);
contract.setRepository(deposit);
contract.setResult(this.result);
contract.setConstantCall(isConstantCall());
contract.setVmShouldEndInUs(getVmShouldEndInUs());
Pair<Boolean, byte[]> out = contract.execute(data);
``` [2](#0-1) 

Real transactions inside a block are applied sequentially by the single block-processing thread in `Manager.processBlock`/`generateBlock` [3](#0-2) , but constant calls run on separate concurrent worker threads that can execute **at the same time** as block processing. This concurrency is explicitly acknowledged elsewhere in the codebase — `ConfigLoader`/`VMConfig` had to introduce a `ThreadLocal` snapshot specifically because "a constant call bound to a non-HEAD (solidity/PBFT) snapshot ... cannot pollute the flags the block-processing path reads concurrently" [4](#0-3)  and is unit-tested for cross-thread pollution in `VMConfigIsolationTest` [5](#0-4) . That fix addressed `VMConfig` flags only — it did **not** address the analogous shared, unsynchronized mutable state on the `PrecompiledContracts` singleton instances (`repository`, `callerAddress`, `result`, `isConstantCall`, `vmShouldEndInUs`).

Because the same precompile object (e.g., `DelegatableResource`, `CheckUnDelegateResource`, `BatchValidateSign`) is shared across threads, this is directly analogous to the CVE's root cause: a piece of shared, indexed/keyed execution-context state (there: `bpf_cg_run_ctx.prog_item.cgroup_storage`; here: the singleton `PrecompiledContract`'s caller/repository/result fields) is written by one execution context and can be read by a *different* logical execution context that assumed it owned that state. In the kernel, a tail call swapped in the wrong `cgroup_storage` map causing an OOB read/write; here, a race between two threads calling the same precompile can swap in the wrong `Repository`/caller address/result object between the `set*` calls and `execute()`, so an in-flight execution can end up operating on another transaction's or another caller's state.

### Impact Explanation
If a real (non-constant) transaction's precompile call has its `repository`/`callerAddress` overwritten mid-flight by a concurrently-running constant call (or vice versa), a resource/freeze precompile (`DelegatableResource`, `CheckUnDelegateResource`, `ExpireUnfreezeBalanceV2`) could read/act on the wrong account's balance/frozen-resource data, or a signature precompile (`ValidateMultiSign`/`BatchValidateSign`) could validate against the wrong caller/permission context. Because these precompiles ultimately drive balance and delegated-resource bookkeeping that gets committed via `deposit.commit()` on the *real* transaction path, cross-thread field corruption can lead to unauthorized account operations, state written against an unintended repository (in the worst case silently discarding the intended state mutation, i.e., an operation the user paid energy for is lost — a form of fund freezing/loss), or an unhandled type/state mismatch that throws and crashes the block-processing thread (node halt).

### Likelihood Explanation
Reaching this requires only ordinary, unprivileged usage: any client can submit a `TriggerSmartContract`/`CreateSmartContract` transaction that calls one of the shared precompiled addresses while, at the same time, any other client issues a constant call (`eth_call`, `/wallet/triggerconstantcontract`, `/wallet/estimateenergy`) that hits the same precompile address. Both paths are reachable without any special privilege, and constant calls are served concurrently by design (confirmed by the `VMConfig` thread-local fix). The window between `set*` calls and `execute()` is small but real, and under sustained request volume (which an attacker fully controls by flooding constant-call requests against contracts that invoke these precompiles) the race window can be hit repeatedly.

### Recommendation
Stop sharing mutable per-invocation state on process-wide singleton `PrecompiledContract` instances. Either (a) make each `PrecompiledContract` instance stateless and pass `repository`, `callerAddress`, `result`, `isConstantCall`, and `vmShouldEndInUs` as explicit parameters to `execute(...)`, or (b) instantiate a fresh `PrecompiledContract` object per call (mirroring how `Program`/`ProgramInvoke` are freshly created per call in `Program.callToAddress`) instead of reusing `private static final` singletons.

### Proof of Concept
Root cause is structural (a data race), not a single deterministic transcript, but can be demonstrated by:
1. Deploy a contract `A` that calls a shared precompiled address (e.g., the `DelegatableResource`/`CheckUnDelegateResource` address) as part of a normal `TriggerSmartContract` transaction, and submit it to be included in a block.
2. Concurrently, from a second client, flood `/wallet/triggerconstantcontract` or JSON-RPC `eth_call` requests against a contract that also invokes the same precompiled address, with a different caller address / repository each time.
3. Observe (via added instrumentation/logging inside `PrecompiledContracts` setters or by racing on a slowed-down `execute()` — e.g., a precompile with I/O like `BatchValidateSign`'s async signature checks [6](#0-5) ) that the `repository`/`callerAddress` field read inside `execute()` does not match the value set immediately before the call in `callToPrecompiledAddress`, confirming cross-thread field clobbering.

  @Test
  public void testLocalConfigDoesNotPolluteGlobalAcrossThreads() throws InterruptedException {
    VMConfig.initAllowTvmOsaka(1);            // global (HEAD) view: activated
    assertTrue(VMConfig.allowTvmOsaka());     // no thread-local -> reads global

    VMConfig.Snapshot local = new VMConfig.Snapshot();
    local.allowTvmOsaka = false;              // simulate a not-yet-solidified snapshot
    VMConfig.setLocalSnapshot(local);

    // this thread now sees its own (solidity) view...
    assertFalse(VMConfig.allowTvmOsaka());

    // ...but another thread (e.g. block processing) must still see the global HEAD value.
    AtomicBoolean otherThreadSaw = new AtomicBoolean(false);
    Thread t = new Thread(() -> otherThreadSaw.set(VMConfig.allowTvmOsaka()));
    t.start();
    t.join();
    assertTrue("global config must be unaffected by another thread's local view",
        otherThreadSaw.get());

    // after dropping the local view, this thread falls back to the global value again.
    VMConfig.clearLocalSnapshot();
    assertTrue(VMConfig.allowTvmOsaka());
  }
