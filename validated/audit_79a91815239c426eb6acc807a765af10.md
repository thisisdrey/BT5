### Title
Cross-Chain Replay of Off-Chain Authorization Signatures via `ValidateMultiSign`/`BatchValidateSign` Precompiles — No Chain-Domain Separation - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` (address `0x...0a`) and `BatchValidateSign` (address `0x...09`) TVM precompiles recover signer addresses from a digest that never includes any chain/network identifier. Any smart contract built on top of these precompiles to implement off-chain authorized actions (e.g., meta-transaction approvals, gasless withdrawals, marketplace order signing) inherits the exact bug class described in the report: a signature valid on one TRON-compatible network is replayable verbatim on any other network that shares the same account/permission state (mainnet vs. testnet vs. a private/forked chain), because the digest construction performed by the precompile provides no domain separation.

### Finding Description
`ValidateMultiSign.execute` builds its recovery hash purely from contract-controlled/off-chain data: [1](#0-0) 
`combine = address || permissionId || data`, hashed with `Sha256Hash.hash`. Nothing here mixes in a chain/network identifier (there is no TRON equivalent of EIP-155 `chainId` folded into this digest). The same applies to `BatchValidateSign`, whose recovery hash is taken directly and unmodified from caller-supplied `bytes32 hash`: [2](#0-1) 
Signature recovery for both precompiles reuses the shared helper `recoverAddrBySign`, which simply ECDSA-recovers an address from `(sign, hash)` with no chain binding at all: [3](#0-2) 
Because TRON account addresses, `Permission` structures, and thresholds are typically identical across a mainnet deployment and any testnet/fork that shares genesis/account state (Shasta, Nile, or a privately forked chain deployed from the same codebase), any contract that relies on these precompiles to verify an off-chain-signed authorization (the same usage pattern as the reported "withdraw" signature) is vulnerable to having that authorization replayed on a different chain, exactly as described in the external report.

### Impact Explanation
A DApp/contract using `ValidateMultiSign`/`BatchValidateSign` to gate a privileged action (fund withdrawal, order execution, permission-weighted approval) based on an off-chain-collected multi-signature package can have that same signature package replayed on another TRON-compatible chain where the signer's account/permission state is equivalent, resulting in unauthorized/duplicated execution of the privileged action — i.e., double execution of a withdrawal-style authorization, matching the "High" severity theft/duplicate-withdraw impact in the original report.

### Likelihood Explanation
Exploitability requires: (1) a contract that uses these precompiles for authorization without independently mixing in a domain separator (a common omission, since the precompiles themselves offer no such primitive and no documented guidance to add one), and (2) existence of a second TRON-compatible network with matching account/permission state (testnets sharing key material during testing, or forked/consortium chains). This is a realistic but not universal precondition, making it a solid Medium-to-High likelihood analog rather than a guaranteed one — it depends on downstream contract design choices, but the missing protection lives in the precompiled contract itself, which is the reusable “message digest” primitive every such contract is pushed toward using.

### Recommendation
Extend the digest construction in `ValidateMultiSign.execute` and document/encourage (or enforce) chain-domain separation for `BatchValidateSign` callers — e.g., mix `VMConfig`'s chain id (already exposed to TVM via the `CHAINID` opcode, cf. `AllowTvmCompatibleEvmTest.testChainId`) into the `combine`/hash construction so recovered signatures are intrinsically bound to the chain on which the precompile executes: [4](#0-3) 

### Proof of Concept
1. Deploy an identical contract (or reuse the same account/permission set) on two TRON-compatible networks that share genesis-derived account state (e.g., a private fork of mainnet, or a testnet seeded with the same keys).
2. Off-chain, produce a valid multi-signature package for `ValidateMultiSign`/`BatchValidateSign` authorizing a privileged action (e.g., withdraw) as done via the `combine = address || permissionId || data` hash in `PrecompiledContracts.java` lines 1062-1064.
3. Submit the transaction invoking the consuming contract on Chain A — the action executes and the precompile returns success (`dataOne()`).
4. Replay the identical signed payload against the same contract logic deployed on Chain B — because `recoverAddrBySign` (lines 371-388) performs no chain-specific binding, the same signatures recover the same addresses and satisfy the same permission threshold, executing the privileged action a second time on a different chain.

  private static byte[] recoverAddrBySign(byte[] sign, byte[] hash) {
    byte[] out = null;
    if (ArrayUtils.isEmpty(sign) || sign.length < 65) {
      return new byte[0];
    }
    try {
      Rsv rsv = Rsv.fromSignature(sign);
      SignatureInterface signature = SignUtils.fromComponents(rsv.getR(), rsv.getS(), rsv.getV(),
          CommonParameter.getInstance().isECKeyCryptoEngine());
      if (signature.validateComponents()) {
        out = SignUtils.signatureToAddress(hash, signature,
            CommonParameter.getInstance().isECKeyCryptoEngine());
      }
    } catch (Throwable any) {
      logger.info("ECRecover error", any.getMessage());
    }
    return out;
  }
