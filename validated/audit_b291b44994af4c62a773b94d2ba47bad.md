Audit Report

## Title
`process_delivery_receipt` in Snowbridge `outbound-queue-v2` never checks the decoded `success` flag before paying the relayer reward - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
`DeliveryReceipt` decoded from the Ethereum `InboundMessageDispatched` event carries a `success: bool` field indicating whether the message actually executed successfully on the Gateway contract, decoded at [3](#0-2) . `Pallet::process_delivery_receipt` verifies only the gateway address and pending nonce existence, then unconditionally pays the relayer reward and removes the `PendingOrder`, regardless of `receipt.success` at [4](#0-3) . This means failed cross-chain dispatches on Ethereum are paid and settled identically to successful ones.

## Finding Description
The `DeliveryReceipt` type is decoded from the `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` Ethereum event log via `TryFrom<&Log>`, explicitly capturing `success: event.success` into the struct [5](#0-4) .

`process_delivery_receipt`, reachable from the public extrinsic `submit_delivery_receipt` (requiring only `ensure_signed` and a valid proof verified by `T::Verifier`), performs these checks in order: [6](#0-5) 

1. `T::GatewayAddress::get() == receipt.gateway`
2. `PendingOrders::<T>::get(nonce)` exists

It then unconditionally calls `T::RewardPayment::register_reward` with `order.fee` and removes the `PendingOrder`, with no reference to `receipt.success` anywhere in the function body [2](#0-1) . The decoded `success` field is dropped on the floor.

## Impact Explanation
`PendingOrders` and its associated payout are meant to represent that a message was delivered and dispatched successfully on Ethereum. Since `success` is never checked, a receipt proof for an `InboundMessageDispatched` event with `success = false` (Gateway contract reverted/failed execution) still results in the full relayer reward being paid via `register_reward`, and the `PendingOrder` for that nonce is permanently removed with no retry/compensation path visible in this pallet. This violates the required invariant that "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically," resulting in public underpriced/incorrect settlement — reward payout and order finalization proceed even though the cross-chain command execution demonstrably failed.

## Likelihood Explanation
High. The path is reachable by any signed account via the public extrinsic `submit_delivery_receipt`, which requires only `ensure_signed` and a genuine Merkle/receipt proof verified by `T::Verifier` [6](#0-5) . No malicious relayer or forged proof is needed — an honest relayer submitting a genuine receipt for a message that failed to execute on Ethereum (a normal, expected occurrence in cross-chain messaging, e.g., revert or gas exhaustion on the Gateway contract) will trigger the incorrect unconditional payout and order removal.

## Recommendation
In `process_delivery_receipt`, add an explicit check on `receipt.success` before paying the reward and/or before removing the `PendingOrder`, e.g. `ensure!(receipt.success, Error::<T>::MessageDispatchFailed);`. If the design intent is to reward relayers purely for delivery effort independent of execution outcome, that choice should be explicit and documented, with a distinct event/path for failed dispatches so they are auditable and distinguishable from successful ones rather than being silently treated identically.

## Proof of Concept
1. A message is queued and a `PendingOrder { nonce, fee, .. }` is inserted via `do_process_message` [7](#0-6) .
2. On Ethereum, dispatch of this message to the Gateway contract fails, emitting `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer builds a valid proof for this genuine event and calls `submit_delivery_receipt(origin, event)`; `T::Verifier::verify` succeeds and `DeliveryReceipt::try_from` decodes `success: false` correctly.
4. `process_delivery_receipt` is invoked: gateway matches, `PendingOrders::get(nonce)` exists, `order.fee > 0` → the reward account is paid the full fee via `register_reward`, and `PendingOrders::remove(nonce)` finalizes the order — despite `receipt.success == false`.
5. This can be reproduced as a unit test in `bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs` by constructing a `DeliveryReceipt` with `success: false` and asserting that `register_reward` is NOT called / the reward event is not emitted — no such test currently exists; existing fixtures (e.g., `snowbridge_v2_outbound.rs`) only construct receipts with `success: true` and assert payout occurs.

		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
