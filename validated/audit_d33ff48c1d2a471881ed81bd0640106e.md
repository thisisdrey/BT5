### Title
Aborted reference transactions never release the Praefect repository write-lock, causing a lock-hold DoS on ordinary pushes - ([File: internal/gitaly/hook/referencetransaction.go])

### Summary
Praefect's new "serialized writes" feature acquires a PostgreSQL-backed, per-repository write lock at the `preparing` phase of Git's `reference-transaction` hook and releases it only when a `committed` vote is cast or a vote fails with an error. The Gitaly-side hook handler, however, silently no-ops for the `aborted` transaction state, so no vote (and therefore no unlock) is ever produced for that phase. Any ordinary push that causes Git to abort a reference transaction after `prepared` leaves the lock held until it eventually expires via a background sweep, serializing/blocking all subsequent writes to that repository in the meantime.

### Finding Description
`GitLabHookManager.ReferenceTransactionHook` maps the Git-supplied `ReferenceTransactionState` to a `voting.Phase` only for `Preparing`, `Prepared`, and `Committed`; every other value — including the `aborted` state emitted by `cmd/gitaly-hooks/hooks.go`'s `referenceTransactionHook` — falls into `default: return nil`, which returns before `m.voteOnTransaction` is ever called [1](#0-0) . The `aborted` state itself is parsed and forwarded from the git hook invocation without special handling [2](#0-1) .

On the Praefect side, `Manager.lockRepoForTransaction` acquires the PostgreSQL write lock via `repoWriteLockMgr.Lock` at `PREPARING_PHASE` and renews it at `PREPARED_PHASE`/`COMMITTED_PHASE` [3](#0-2) . The lock is only released in `unlockRepoForTransaction` when a `PREPARING`/`PREPARED` vote errors, or when a `COMMITTED` vote is cast [4](#0-3) . Because the Gitaly hook never emits any vote for the `aborted` state, `voteTransaction`/`unlockRepoForTransaction` is never invoked for that phase, so the lock acquired in `PREPARING_PHASE` (and possibly renewed in `PREPARED_PHASE`) is left dangling. The only recovery path is the background sweep `cleanUpExpiredRepoRefWriteLocks`, which runs every `2 * lockRenewInterval` (40 seconds by default) and only deletes rows whose `expired_at` has passed [5](#0-4) [6](#0-5) .

This is exactly analogous to the ERC777 report's pattern: a caller-controlled abort/revert during an in-flight, lock-holding operation is not accounted for by the code path responsible for releasing the held resource, so cleanup depends entirely on a timeout rather than an explicit release.

### Impact Explanation
`update_with_hooks.go` drives the reference-transaction hook manually and can hit this exact sequence: it votes `Preparing`, then `Prepared` (locking the repo lock/renewing it), and only afterwards calls `updater.Commit()` [7](#0-6) . If `Commit()` fails or the underlying transaction aborts for any of the many ordinary reasons a Git ref update can fail after locks are taken (conflicting concurrent ref update, disk/quota error, ref-lock contention, git-core generated `aborted` transaction), Git's `reference-transaction` hook fires with `aborted`, which the Gitaly hook code silently discards without voting. Because `PraefectSerializedWrite` requires exactly one held lock per repository, an attacker (an ordinary user who can push/write) can repeatedly trigger this abort path (e.g., racing conflicting ref updates against their own pushes) to keep the repository's write lock effectively held, serializing and delaying all legitimate write RPCs (`UserCreateBranch`, pushes, merges, etc.) to that repository for the renewal window each time, repeatable indefinitely.

### Likelihood Explanation
The `aborted` reference-transaction state is a normal, easily reachable Git outcome — it occurs whenever a ref update fails after being staged/locked, which any unprivileged pusher can provoke (e.g. two overlapping pushes racing for the same ref, or any operation that fails between `prepared` and `commit`). No special privileges, malicious peers, or leaked credentials are required; this is purely a gap in the ordinary push/write handling path guarded by the new serialized-write feature (`featureflag.PraefectSerializedWrite`).

### Recommendation
Handle the `aborted` `ReferenceTransactionState` explicitly in `GitLabHookManager.ReferenceTransactionHook` (or otherwise ensure the abort path notifies Praefect) so that an aborted transaction always results in a vote/unlock call analogous to the error path in `unlockRepoForTransaction`, rather than relying on the lock's TTL-based expiry sweep as the sole cleanup mechanism. Alternatively, ensure any hook or Git-driven termination path (`aborted`, or an unhandled/default state) triggers `mgr.releaseRepoLock`/`unlockRepoForTransaction` directly so the write lock cannot outlive the RPC that acquired it.

### Proof of Concept
1. Enable the `PraefectSerializedWrite` feature flag so writes are serialized via the PostgreSQL-backed `RepoReferenceWriteLockManager`.
2. As an ordinary authenticated user with write access, issue two racing writes to the same repository/ref such that the first reaches `prepared` (locks taken, `PREPARED_PHASE` vote cast, lock renewed) and then fails/aborts before `Commit()` succeeds (e.g., a concurrent conflicting ref update, or induce a low-level ref-lock failure).
3. Observe that Git invokes the `reference-transaction` hook with `aborted`; trace into `ReferenceTransactionHook` and confirm execution hits `default: return nil` without calling `voteOnTransaction`.
4. On the Praefect side, confirm no `COMMITTED_PHASE`/error vote arrives for that transaction ID, so `unlockRepoForTransaction` is never invoked and the row in `repository_reference_write_locks` for that repo remains until the background sweep (`cleanUpExpiredRepoRefWriteLocks`) deletes it after its TTL.
5. Repeat step 2 in a loop before each expiry window elapses to keep the lock continuously held, observing that all other legitimate writers to the repository are serialized/blocked behind the dangling lock.

	switch state {
	// We're voting in preparing state to tell Praefect that the reference changes are ready,
	// although they are not locked yet. At this stage, we can serialize write transactions by
	// acquiring a lock for the transaction and releasing it only when the transaction is
	// committed or aborted. Other transactions must wait for the lock.
	case ReferenceTransactionPreparing:
		phase = voting.Preparing
	// We're voting in prepared state to tell Praefect we've locked the reference changes and
	// queued them for the transaction. We can abort the transaction if needed.
	case ReferenceTransactionPrepared:
		phase = voting.Prepared

		if tx != nil {
			updates, err := parseChanges(objectHash, bytes.NewReader(changes))
			if err != nil {
				return fmt.Errorf("parse changes: %w", err)
			}

			initialValues := map[git.ReferenceName]git.Reference{}
			for reference, update := range updates {
				if update.OldOID != "" {
					initialValues[reference] = git.NewReference(reference, update.OldOID)
				} else {
					initialValues[reference] = git.NewSymbolicReference(reference, update.OldTarget)
				}
			}

			// Only record the initial values of the reference in the prepare step as this
			// change hasn't yet been committed.
			if err := tx.RecordInitialReferenceValues(ctx, initialValues); err != nil {
				return fmt.Errorf("record initial reference value: %w", err)
			}
		}
	// We're also voting in committed state to tell Praefect we've actually persisted the
	// changes. This is necessary as some RPCs fail return errors in the response body rather
	// than as an error code. Praefect can't tell if these RPCs have failed. Voting on committed
	// ensure Praefect sees either a missing vote or that the RPC did commit the changes.
	case ReferenceTransactionCommitted:
		phase = voting.Committed

		if tx != nil {
			updates, err := parseChanges(objectHash, bytes.NewReader(changes))
			if err != nil {
				return fmt.Errorf("parse changes: %w", err)
			}

			if err := tx.UpdateReferences(ctx, updates); err != nil {
				return fmt.Errorf("update references: %w", err)
			}
		}

		return nil

func referenceTransactionHook(ctx context.Context, payload gitcmd.HooksPayload, hookClient gitalypb.HookServiceClient, args []string) error {
	if len(args) != 1 {
		return fmt.Errorf("reference-transaction hook is missing required arguments, got %q", args)
	}

	var state gitalypb.ReferenceTransactionHookRequest_State
	switch args[0] {
	case "preparing":
		// state = gitalypb.ReferenceTransactionHookRequest_PREPARING
		// Skip invoking the RPC for the "preparing" phase as the server-side handler
		// is currently a no-op for this state.
		return nil
	case "prepared":
		state = gitalypb.ReferenceTransactionHookRequest_PREPARED
	case "committed":
		state = gitalypb.ReferenceTransactionHookRequest_COMMITTED
	case "aborted":
		state = gitalypb.ReferenceTransactionHookRequest_ABORTED
	default:
		return fmt.Errorf("reference-transaction hook has invalid state: %q", args[0])
	}

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}
	return nil
}

func (mgr *Manager) unlockRepoForTransaction(ctx context.Context, transactionID uint64, returnedErr error, phase gitalypb.VoteTransactionRequest_Phase) {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return
	}

	// Decide whether this call releases the write lock. The lock spans all the
	// phases of one transaction and is only released when either the vote
	// failed (so callers can't advance to the next phase) or the committed
	// phase completes. Phases outside the reference transaction hook
	// lifecycle (e.g. SYNCHRONIZED_PHASE) never acquired a lock.
	var shouldUnlock bool
	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE,
		gitalypb.VoteTransactionRequest_PREPARED_PHASE:
		shouldUnlock = returnedErr != nil
	case gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		shouldUnlock = true
	default:
		return
	}

	if !shouldUnlock {
		return
	}

	mgr.releaseRepoLockOnPhase(transactionID, phase.String())
}

func cleanUpExpiredRepoRefWriteLocks(ctx context.Context, qc glsql.Querier, logger log.Logger) {
	query := `
DELETE FROM repository_reference_write_locks
WHERE expired_at < NOW();`
	result, err := qc.ExecContext(ctx, query)
	if err != nil {
		logger.WithError(err).Error("cleanup expired lock")
		return
	}
	n, err := result.RowsAffected()
	if err != nil {
		logger.WithError(err).Error("cleanup expired lock")
		return
	}
	logger.WithField("count", n).Info("clean up expired repository reference write locks")
}
