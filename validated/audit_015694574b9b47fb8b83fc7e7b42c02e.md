### Title
Contract deployment can be permanently DOSed by front-running a pre-funded/pre-created account at the deterministic target address - (File: `actuator/src/main/java/org/tron/core/actuator/VMActuator.java`)

### Summary
`java-tron` computes the address for a new smart contract deterministically from the deploying transaction and then refuses to deploy if *any* account already exists at that address, exactly the same "create-if-not-exists" pattern flagged in the Solana report. Because the target address is derivable before the deployment transaction is confirmed, an unprivileged transaction broadcaster can front-run a pending `CreateSmartContract` transaction, pre-fund/pre-create the target address, and permanently block that specific deployment transaction from ever succeeding.

### Finding Description
When a `CreateSmartContract` transaction is executed, `VMActuator.create()` derives the target contract address deterministically and aborts if an account already occupies it: [1](#0-0) 

The address itself is computed purely from the transaction's own id and the owner address, with no dependency on prior confirmation state: [2](#0-1) 

Because `txRawDataHash` (the transaction id) is fixed as soon as the deployer signs/builds the raw transaction — before it is confirmed on-chain — the resulting `contractAddress` is fully computable by anyone who observes the pending transaction (e.g., in the mempool, or via `TriggerConstantContract`/estimation preflights, or simply from any resubmission attempt). An attacker who sees this pending deployment can immediately broadcast a plain TRX transfer (or an `AccountCreateContract`) to that exact address before the original deployment transaction lands. Once any `AccountCapsule` exists at that address, `rootRepository.getAccount(contractAddress) != null` is true, and the actuator throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`, permanently failing that specific transaction — since the transaction id (and thus the target address) is fixed by the transaction's own bytes, the deployer cannot resubmit the identical transaction and succeed; they must construct an entirely new transaction to get a different address.

This mirrors the reported Solana bug class precisely: a `create`-style operation that unconditionally fails on "already exists / already funded" allows any unprivileged actor to pre-empt and permanently block the intended account/contract creation for a specific, already-signed transaction.

### Impact Explanation
Any address, contract deployer transaction can be griefed by a third party at minimal cost (one TRX transfer fee), turning a legitimate contract deployment into a permanently-failing transaction (fee/bandwidth/energy still consumed, contract never created). This is a targeted denial-of-service against contract deployers reachable purely through the public transaction broadcast path (`CreateSmartContract` + a competing transfer), with no special privilege required from the attacker.

### Likelihood Explanation
Likelihood is moderate to high in adversarial environments: the attacker only needs visibility into a pending `CreateSmartContract` transaction (e.g., through mempool monitoring, `TriggerConstantContract`-based address prediction if the deploying tx bytes are otherwise known, or targeted griefing of a specific dApp deployer they wish to disrupt) and the ability to broadcast an ordinary transfer before the deployment confirms. No node-level privilege, validator collusion, or bug in signature/consensus logic is required — a single unprivileged transaction is sufficient.

### Recommendation
Do not treat pre-existence of any account (even one with a plain balance and no code/nonce) at the target address as fatal. Follow the Ethereum/EIP-684-style collision rule already partially implemented for the internal `CREATE`/`CREATE2` path — only reject if the existing account already has deployed code, a nonce > 0, or is already marked as a contract; otherwise allow the deployment to proceed and simply merge/absorb the pre-existing balance into the new contract account, mirroring the "fund, then create over" pattern recommended for Solana PDAs. Apply the same collision check used for `createContractImpl` (see `contractAlreadyExists` / `isContractExist`-style logic in `Program.java`) uniformly to the top-level `VMActuator.create()` path as well.

### Proof of Concept
1. Deployer constructs and signs `CreateSmartContract` transaction `Tx1`. Compute `addr = generateContractAddress(Tx1)` off-chain (any observer with visibility of `Tx1` bytes, e.g. in the mempool, can compute the same value using `WalletUtil.generateContractAddress`).
2. Attacker broadcasts a plain TRX transfer to `addr` and it confirms before `Tx1`.
3. `Tx1` is processed; `VMActuator.create()` finds `rootRepository.getAccount(contractAddress) != null` and throws `ContractValidateException("Trying to create a contract with existing contract address: ...")`.
4. `Tx1` permanently fails — resubmitting the exact same signed transaction cannot succeed since `contractAddress` is deterministic from `Tx1`'s own id; the deployer must build a brand-new transaction (different id → different address) to retry, and the attacker can repeat the front-run.   public static byte[] generateContractAddress(Transaction trx) {

    CreateSmartContract contract = ContractCapsule.getSmartContractFromTransaction(trx);
    byte[] ownerAddress = contract.getOwnerAddress().toByteArray();
    TransactionCapsule trxCap = new TransactionCapsule(trx);
    byte[] txRawDataHash = trxCap.getTransactionId().getBytes();

    byte[] combined = new byte[txRawDataHash.length + ownerAddress.length];
    System.arraycopy(txRawDataHash, 0, combined, 0, txRawDataHash.length);
    System.arraycopy(ownerAddress, 0, combined, txRawDataHash.length, ownerAddress.length);

    return Hash.sha3omit12(combined);

  }
