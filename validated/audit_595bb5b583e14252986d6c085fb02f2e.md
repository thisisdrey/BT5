Audit Report

## Title
Discarded `checked_sub` result in `EngineMeter::charge_ref_time` causes wasm-contract gas fuel to never be decremented - ([File: substrate/frame/contracts/src/gas.rs])

## Summary
`EngineMeter::charge_ref_time` computes `self.fuel.checked_sub(amount)` only to validate sufficient fuel via `ok_or_else`, but never assigns the result back to `self.fuel`, so the returned `Syncable(self.fuel)` is unchanged. This value is fed directly back into the wasmi engine via `__caller__.set_fuel(fuel.into())` on every host-function call boundary, meaning the wasm executor's fuel budget is effectively never reduced by ref-time actually consumed since the last sync.

## Finding Description
`EngineMeter::charge_ref_time` computes `amount` and then does `self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;` without reassignment, so `self.fuel` retains its prior value and `Ok(Syncable(self.fuel))` returns that unchanged value [1](#0-0) . This is called from `GasMeter::sync_to_executor`, invoked when leaving a host function [2](#0-1) . The generated host-function glue in the `#[define_env]` proc-macro shows the concrete downstream effect: after computing `fuel` from `sync_to_executor`, the code calls `__caller__.set_fuel(fuel.into())`, directly re-arming the wasmi engine's fuel counter with that (unreduced) value [3](#0-2) . Contrast this with `EngineMeter::set_fuel`, used in `sync_from_executor`, which correctly performs `self.fuel = fuel` [4](#0-3) , and with the equivalent `pallet-revive` metering code, which correctly reassigns weight consumed via `saturating_accrue` [5](#0-4) . This confirms `charge_ref_time` in `pallet-contracts` is the only place in this metering path that discards its computed value instead of applying it.

## Impact Explanation
Because `self.fuel` is never actually decremented, the wasm engine's internal fuel counter is repeatedly reset to the same (unreduced) `self.fuel` value on every host-function call boundary via `set_fuel`, rather than shrinking to reflect ref_time consumed between syncs. This constitutes public underpriced work: a contract can loop over lightweight host-function calls and consume far more wall-clock compute per unit of charged weight than the runtime weight system assumes, which is a concrete metering/accounting corruption of the `EngineMeter::fuel` state value, aligning with the "public underpriced work that degrades block production" impact category.

## Likelihood Explanation
This code executes unconditionally on every host-function call for any deployed contract under legacy `pallet-contracts`, requiring only an ordinary account submitting a transaction invoking a contract with a host-function-call loop — no privileged access, governance, or compromised infrastructure needed. The defect is a deterministic logic bug (an `Option` produced by `checked_sub` is discarded rather than assigned), so it is consistently and trivially reproducible.

## Recommendation
Fix `charge_ref_time` to apply the subtraction result to state:
```rust
self.fuel = self.fuel.checked_sub(amount).ok_or_else(|| Error::<T>::OutOfGas)?;
```
Add a regression test in `substrate/frame/contracts/src/gas.rs`'s test module asserting that repeated `charge_ref_time` calls monotonically decrease `EngineMeter::fuel`, and that `OutOfGas` is returned once fuel is exhausted — matching `pallet-revive`'s correctly-implemented equivalent.

## Proof of Concept
1. In a unit test for `substrate/frame/contracts/src/gas.rs`, construct an `EngineMeter::<T>` with a known fuel limit via `EngineMeter::new`.
2. Call `charge_ref_time` repeatedly with a fixed `ref_time` and observe `self.fuel` before/after each call — it remains constant instead of decreasing by `amount` each time (private field, so this requires an in-crate test or an exposed accessor).
3. Compare against the call chain `GasMeter::sync_to_executor` → generated `sync_gas_after` block in `proc-macro/src/lib.rs`, which calls `__caller__.set_fuel(fuel.into())`; because `fuel` (from `Syncable`) never decreases, the wasmi engine's fuel is never actually consumed at the engine level, allowing loops of host-function calls to run with effectively unbounded engine-side fuel while nominal weight tracking (`gas_left`) proceeds separately.
