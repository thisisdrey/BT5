### Title
Unbounded, unauthenticated disk writes to `AtlasDB` via unverified Atlas attachment download responses - (File: `stackslib/src/net/atlas/download.rs`, `stackslib/src/net/atlas/db.rs`)

### Summary
The Atlas attachment downloader requests attachment content from remote peers keyed by an on-chain committed `content_hash` (from an `AttachmentInstance`), but never verifies that the bytes a peer actually returns hash to that requested value before accepting and permanently persisting them. Any peer the node downloads from can therefore return arbitrary content instead of the committed attachment, and the node will still store it to its local `AtlasDB` with no eviction and no per-store size/count cap.

### Finding Description
When the downloader builds a request for a missing attachment, it records the expected on-chain-committed hash in `AttachmentRequest.content_hash`: [1](#0-0) 

When the HTTP response for that request comes back, `AttachmentsBatchStateContext::extend_with_attachments` simply decodes the JSON payload and inserts whatever `Attachment` it contains into `self.attachments` — it never compares `response.attachment.hash()` against `request.content_hash`: [2](#0-1) 

Once the batch state machine reaches `Done`, every attachment collected this way is looked up and stored using the hash of the *received* bytes, not the hash that was originally requested: [3](#0-2) 

`AtlasDB::insert_instantiated_attachment` performs this SQL insert unconditionally — it has no cap on the number of stored, instantiated attachments (unlike `insert_uninstantiated_attachment`, which enforces `max_uninstantiated_attachments` and evicts oldest entries): [4](#0-3) [5](#0-4) 

Only `was_instantiated = 0` (uninstantiated) rows are ever evicted by `evict_expired_uninstantiated_attachments` / `evict_k_oldest_uninstantiated_attachments`; `was_instantiated = 1` rows written via `insert_instantiated_attachment` are never expired: [6](#0-5) 

This breaks the equality that the Atlas protocol's design depends on: "content stored under a hash == the content committed on-chain for that hash." The report's LidoEthStrategy bug is about trusting an unauthenticated, attacker-influenced external value as canonical; the analog here is that the AttachmentsDownloader trusts an unauthenticated remote peer's HTTP response as canonical attachment data, storing it without validating it against the on-chain-committed `content_hash` it was originally fetching.

### Impact Explanation
Any of the node's outbound Atlas-sync peers (which need not be privileged or authenticated in any special way — just a peer the node happens to be syncing Atlas attachments from) can respond to attachment requests with arbitrary attacker-chosen bytes. Because the code never checks `hash(returned_bytes) == requested content_hash`, and `insert_instantiated_attachment` has no bound on table size, a single malicious peer can force the victim node to permanently store unbounded amounts of arbitrary data to its local SQLite-backed AtlasDB, one unique blob per fetched "attachment," with no cap and no eviction. This is a disk-exhaustion / unauthorized-write primitive reachable from the unprivileged Atlas P2P/HTTP surface, without requiring the node's own key or any special role.

### Likelihood Explanation
Likelihood is high for a node that actively participates in Atlas sync (BNS-related contracts) and fetches attachments from remote peers, since the vulnerable code path (`AttachmentsBatchStateContext::extend_with_attachments`) runs on every successful attachment HTTP response during normal peer-to-peer operation, requiring no special conditions from the attacker beyond being selected as a download source (which is a normal, low-barrier state for any reachable peer offering the relevant inventory).

### Recommendation
In `extend_with_attachments`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments`; discard (and penalize the peer's reliability score for) any response whose content does not match the requested hash. Additionally, enforce a cap (and/or eviction policy) on the number/size of rows in the `attachments` table with `was_instantiated = 1`, mirroring the existing `max_uninstantiated_attachments` bound, so that even validated attachments cannot grow disk usage unboundedly.

### Proof of Concept
1. Set up a victim node that syncs Atlas attachments and has at least one pending `AttachmentInstance` with `content_hash = H` (e.g. via a BNS name registration referencing an off-chain zonefile).
2. Run a malicious peer node that the victim selects as an Atlas download source (`get_outbound_sync_peers`/`get_data_url`).
3. When the victim requests `GET /v2/attachments/H`, have the malicious peer respond with HTTP 200 and a `GetAttachmentResponse` JSON body whose `attachment.content` is arbitrary attacker-chosen bytes `C` (with `hash(C) != H`).
4. Observe in `AttachmentsBatchStateContext::extend_with_attachments` (`stackslib/src/net/atlas/download.rs:547-549`) that the response is accepted with no hash check, and in `AttachmentsDownloader::run` (`stackslib/src/net/atlas/download.rs:153-162`) `insert_instantiated_attachment` is called and persists `C` to `AtlasDB` regardless of any match to a real pending instance.
5. Repeat with unique payloads across many distinct requested content hashes (or by having the peer simply always answer any distinct request URL) to grow the `attachments` table in the victim's `AtlasDB` without bound, since no cap/eviction applies to `was_instantiated = 1` rows.

Note: I was unable to fully verify, within the remaining tool budget, whether an upper bound on individual HTTP response/attachment size (`attachments_max_size`) is enforced at the JSON-parsing layer (`decode_atlas_get_attachment` / `parse_json`), which would affect the per-blob size ceiling but not the unbounded row-count/no-eviction issue identified above.

    pub fn extend_with_attachments(
        mut self,
        results: &mut BatchedRequestsResult<AttachmentRequest>,
    ) -> AttachmentsBatchStateContext {
        for (request, response) in results.succeeded.drain() {
            let report = self
                .peers
                .get_mut(request.get_url())
                .expect("Atlas: unable to retrieve reliability report for peer");

            let response = if let Some(r) = response {
                r
            } else {
                report.bump_failed_requests();
                continue;
            };

            if let Ok(response) = response.decode_atlas_get_attachment() {
                self.attachments.insert(response.attachment);
                report.bump_successful_requests();
            } else {
                report.bump_failed_requests();
            }
        }
        let mut events_ids = results.faulty_peers.keys().copied().collect::<Vec<usize>>();
        self.events_to_deregister.append(&mut events_ids);

        self
    }

    pub fn insert_uninstantiated_attachment(
        &mut self,
        attachment: &Attachment,
    ) -> Result<(), db_error> {
        // Insert the new attachment
        let uninstantiated_attachments = self.count_uninstantiated_attachments()?;
        if uninstantiated_attachments >= self.atlas_config.max_uninstantiated_attachments {
            let to_delete =
                1 + uninstantiated_attachments - self.atlas_config.max_uninstantiated_attachments;
            self.evict_k_oldest_uninstantiated_attachments(to_delete)?;
        }

        let tx = self.tx_begin()?;
        let now = util::get_epoch_time_secs() as i64;
        let res = tx.execute(
            "INSERT OR REPLACE INTO attachments (hash, content, was_instantiated, created_at) VALUES (?, ?, 0, ?)",
            params![
                attachment.hash(),
                attachment.content,
                now,
            ],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }

    pub fn evict_expired_uninstantiated_attachments(&mut self) -> Result<(), db_error> {
        let now = util::get_epoch_time_secs() as i64;
        let cut_off = now - self.atlas_config.uninstantiated_attachments_expire_after as i64;
        let tx = self.tx_begin()?;
        let res = tx.execute(
            "DELETE FROM attachments WHERE was_instantiated = 0 AND created_at < ?",
            params![cut_off],
        );
        res.map_err(db_error::SqliteError)?;
        tx.commit().map_err(db_error::SqliteError)?;
        Ok(())
    }
