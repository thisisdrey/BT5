### Title
Remote fee/reward rounds down to zero on fee-collection path while the committed Ethereum message still promises a fixed non-zero relayer reward - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

### Summary
The Snowbridge outbound-queue pallet computes the upfront fee a sender must pay for a bridged message via `Pallet::<T>::calculate_fee`, splitting it into a `local` component and a `remote` component that is supposed to cover the relayer reward/gas refund on Ethereum. Governance-set `PricingParameters::validate()` rejects zero `rewards.remote`, `fee_per_gas`, `exchange_rate`, and `multiplier`, giving the impression that the remote reward portion can never be zero. However, the actual arithmetic in `calculate_fee`/`convert_from_ether_decimals` can still truncate the computed `fee.remote` to zero for legitimate, non-zero pricing parameters, as the pallet's own test demonstrates. Meanwhile, the value actually embedded in the committed message sent to Ethereum (`reward: pricing_params.rewards.remote`) is taken directly from the raw, non-truncated parameter, so the promised on-chain reward stays non-zero even when the sender was charged zero for it. This mirrors the reported UMA "possible zero bond" pattern: a function meant to enforce a non-zero economic parameter (bond/reward) silently falls back to zero along one path while another path still relies on/promises the full non-zero value.

### Finding Description
`calculate_fee` in [1](#0-0)  computes the remote fee by combining `fee_per_gas * gas_used_at_most + reward` (in wei), applying the `multiplier` and `exchange_rate`, and then calling `convert_from_ether_decimals` at [2](#0-1)  to downscale from Ethereum's 18-decimal precision to the local chain's decimals (e.g. 10 for Polkadot) using integer division (`checked_div`). For small `gas_used_at_most` and unit-scale pricing parameters, this division rounds the result down to `0`, even though every individual `PricingParameters` field passed `validate()`'s non-zero checks in [3](#0-2) . This exact scenario is proven by the pallet's own regression test, whose comment states the outcome "should be avoided": [4](#0-3) .

This `fee.remote` (via `SendMessage::validate`, at [5](#0-4) ) is the amount that downstream fee-charging logic (e.g. the XCM exporter/router) is expected to collect from the sender to fund the remote reward and gas refund. Separately, when the message is actually processed and committed for delivery to Ethereum in `do_process_message`, the `reward` field embedded in the `CommittedMessage` is taken directly from the raw governance parameter `pricing_params.rewards.remote` (non-truncated, guaranteed non-zero by `validate()`), not from the (possibly zero) `fee.remote` computed for the sender's charge: [6](#0-5) .

The result is a mismatch between what is charged to the message sender (can legitimately be `0` for the remote/reward component) and what is promised/committed on-chain to the relayer (always the full, non-zero configured reward). Existing guards do not stop this: `PricingParameters::validate()` only checks the raw input fields, not the derived, decimal-converted `fee.remote` actually charged to callers; there is no check anywhere in `calculate_fee` or `send_message_impl::validate` that rejects or corrects a zero computed `fee.remote`.

### Impact Explanation
This breaks the "public underpriced work" invariant: any user can construct low-gas commands (bounded by `GasMeter::maximum_gas_used_at_most`) that cause the sender-facing `fee.remote` to round to zero, letting them enqueue and get bridge messages committed to the outbound Merkle root while paying nothing toward the remote/reward portion of the fee — yet the pallet still emits a message promising the full configured reward to whichever relayer delivers it. Over many such messages, this creates a systematic shortfall between fees actually collected from users and rewards promised to relayers, degrading the intended fee-funds-reward invariant for bridge processing and enabling cheap/free spam of the outbound queue and Ethereum-bound commitments, which is explicitly called out as a risk to avoid in the project's own design documentation (need for "a minimum relayer reward ... to stop spamming messages with 0 rewards" — see the analogous v2 design note): [7](#0-6) .

### Likelihood Explanation
High from a "reachability" standpoint: this is a pure arithmetic property of `calculate_fee`/`convert_from_ether_decimals` triggerable by any unprivileged account calling into `SendMessage::validate` with a message whose `gas_used_at_most` is small relative to the exchange-rate/decimals scaling, without needing any privileged actor, malicious relayer, or governance action — governance only sets the (valid, non-zero) pricing parameters, and the truncation occurs purely from decimal-precision loss during normal, intended usage. The pallet's own unit test independently reproduces the zero-remote-fee outcome with realistic, valid parameters, confirming this is not a contrived edge case.

### Recommendation
Enforce a floor on the computed `fee.remote` (and consequently ensure it can never be lower than what is needed to cover the reward embedded in the committed message), e.g. by rounding up during `convert_from_ether_decimals` or rejecting/clamping to a minimum non-zero value when the computed fee is zero — mirroring the SkinnyOptimisticOracle fix of always falling back to a nonzero default (final fee) rather than allowing zero. Additionally, consider deriving the on-chain `reward` field in `do_process_message` from the same possibly-adjusted fee value that was actually charged to the sender, so the promised payout and the collected fee never diverge.

### Proof of Concept
The pallet's existing test already constitutes a proof of concept: [4](#0-3) 
With `exchange_rate = 1`, `fee_per_gas = 1`, `rewards = {local: 1, remote: 1}`, `multiplier = 1`, and `gas_used = 250000`, `calculate_fee` returns `fee.remote == 0` while `fee.local == 698000000`. A sender calling `validate()` for a message with comparably small `gas_used_at_most` would be charged `0` for the remote/reward fee component, while the message committed via `do_process_message` still encodes the full configured `pricing_params.rewards.remote` as the promised relayer reward.

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);

	fn validate(
		message: &Message,
	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {
		// The inner payload should not be too large
		let payload = message.command.abi_encode();
		ensure!(
			payload.len() < T::MaxMessagePayloadSize::get() as usize,
			SendError::MessageTooLarge

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),
		}

		// The whole message should not be too large
		let encoded = queued_message.encode().try_into().map_err(|_| SendError::MessageTooLarge)?;
