## Analog Found

### Title
TRC10 Bancor-style Exchange pricing relies purely on manipulable spot on-chain reserves (no TWAP at all) — `ExchangeTransactionActuator` / `ExchangeCapsule.transaction` - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`, `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Sherlock report flags `Multipool.getAmountOut()` for deriving a swap/slippage reference price from a hardcoded, very short (150s) TWAP window, which is trivially manipulable in low-liquidity pools. java-tron's built-in TRC10 "Exchange" (a Bancor-formula AMM reachable by any signed account) has an even weaker guarantee: it computes swap output directly from the **current, single-block reserve balances** with **no time-averaging whatsoever**. Any account can shift the pool ratio in one transaction (`ExchangeInjectContract` / `ExchangeWithdrawContract`) and have a victim's `ExchangeTransactionContract` execute against that manipulated instantaneous price in the very next transaction of the same block, then reverse the injection/withdrawal to walk away with the spread.

### Finding Description
`ExchangeTransactionActuator.execute()` calls `exchangeCapsule.transaction(tokenID, tokenQuant, ...)`, which computes the counter-party amount using only the exchange's currently stored `firstTokenBalance`/`secondTokenBalance` via the Bancor relay-token formula in `ExchangeProcessor`/`SafeExchangeProcessor`: [1](#0-0) 

There is no cumulative/observed price, no minimum elapsed time, and no protection against the reserves having been moved moments earlier by the same block's transactions. Any unprivileged account holding both sides of the pair (or even just TRX plus the token) can call `ExchangeInjectActuator`/`ExchangeWithdrawActuator` to add or remove liquidity and instantly re-price the pool: [2](#0-1) [3](#0-2) 

The only protection a swapper has is a caller-supplied `expected` amount checked at validate time: [4](#0-3) 

This is exactly the bug class the report describes (a critical financial calculation trusting a cheaply-manipulable, near-instantaneous on-chain price) but worse: there is no averaging window to widen — the price is pure spot balance, updated in the same block. In low-liquidity TRC10 exchange pairs (which are common — arbitrary users create these pairs via `ExchangeCreateActuator`), an attacker can:
1. Observe (or predict) a pending `ExchangeTransactionContract` from a victim in the mempool.
2. Front-run with an `ExchangeInjectContract`/`ExchangeWithdrawContract` that shifts the reserve ratio just enough that the victim's swap still clears their `expected` floor but at a much worse effective rate.
3. Back-run to reverse the injection/withdrawal, capturing the extracted value, or simply immediately do a counter-trade after the victim to arbitrage the temporarily skewed pool against the victim's now-mispriced trade.

### Impact Explanation
An attacker can extract value from any counterparty swapping through a java-tron TRC10 Exchange pool, particularly low-liquidity ones, by manipulating the instantaneous reserve ratio in the same or an adjacent block. This constitutes theft of funds from unprivileged users interacting with a core, unprivileged, broadcastable actuator (`ExchangeTransactionContract`), matching the "High" severity classification of the analogous report.

### Likelihood Explanation
`ExchangeInjectContract`, `ExchangeWithdrawContract`, and `ExchangeTransactionContract` are all standard, unprivileged, broadcastable transaction types requiring only a signed transaction and sufficient balance/asset holdings — no special permission is needed. Low-liquidity TRC10 exchange pairs are common since anyone can create one via `ExchangeCreateActuator`, making this readily reachable and economically attractive for an attacker with modest capital relative to the pool size.

### Recommendation
Introduce a time/volume-weighted reference price (or at minimum a per-block/short-cooldown restriction preventing inject/withdraw and transaction against the same exchange within the same block or within N blocks) so that a single actor cannot both move and immediately trade against the reserve ratio. Alternatively, bound the maximum ratio change allowed per block for `ExchangeInjectContract`/`ExchangeWithdrawContract`, or require a minimum holding period before injected/withdrawn liquidity affects executable swap pricing.

### Proof of Concept
1. Attacker holds both `TRX` and asset `X`; a TRC10 Exchange pool for `TRX/X` exists with low reserves.
2. Attacker submits `ExchangeInjectContract` for a large `X` amount, skewing `firstTokenBalance`/`secondTokenBalance` and thus the swap rate computed in `ExchangeCapsule.transaction` (`ExchangeInjectActuator.execute`, lines referenced above).
3. In the same block, victim's pending `ExchangeTransactionContract` (selling `TRX` for `X`) executes against the skewed pool via `ExchangeTransactionActuator.execute` → `exchangeCapsule.transaction(...)`, receiving far fewer `X` tokens than the pre-manipulation price would have given, while still passing their `expected` check because their slippage tolerance was set for normal market conditions.
4. Attacker submits `ExchangeWithdrawContract` to restore the pool and pockets the resulting spread of `X`/`TRX` extracted from the victim's swap.
