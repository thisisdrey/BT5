Audit Report

## Title
`fungibles::Transfer`/`fungible::Transfer` default `transfer()` implementations silently destroy value when the pallet's debit-side dust-sweep rounds up the debited amount but the credit-side receives only the originally requested amount — (File: `substrate/frame/support/src/traits/tokens/fungibles/regular.rs`)

## Summary
The default `transfer()` implementation in `fungibles::Transfer` (and the analogous `fungible::Transfer`) debits the source via `decrease_balance` and discards its actual returned value, then credits the destination via `increase_balance` using only the caller-supplied `amount`. When `pallet-assets`' low-level debit logic rounds the debit up to sweep dust below `min_balance`, the extra amount debited from the source is never credited to the destination nor reflected in `total_issuance`, breaking the `sum(balances) == total_issuance` invariant. This is reachable by any signed account via `pallet_xcm::execute`'s `TransferAsset` instruction routed through `FungiblesTransferAdapter`/`FungibleTransferAdapter`.

## Finding Description
`Transfer::transfer` in `substrate/frame/support/src/traits/tokens/fungibles/regular.rs` calls `Self::decrease_balance(...)?` for the source and separately calls `Self::increase_balance(asset, dest, amount, BestEffort)` for the destination, using the caller's `amount` rather than the actual value returned by `decrease_balance`, then unconditionally returns `Ok(amount)`. [1](#0-0) 

`pallet_assets`'s `Unbalanced::decrease_balance`/`increase_balance` implementations forward to the pallet's internal debit/credit functions, with `increase_balance` explicitly returning the caller-supplied `amount` rather than any pallet-internal actual value. [2](#0-1) 

The identical pairing flaw exists in the single-asset `fungible::Transfer::transfer` default implementation, and both are exercised by the XCM `TransactAsset` adapters `FungiblesTransferAdapter`/`FungibleTransferAdapter::internal_transfer_asset`, which return `what.clone()` to the XCM executor regardless of what was actually credited.

Because the debit and credit operations are independent calls rather than a single paired operation that propagates the actual moved value, any dust-sweep rounding performed on the debit side (documented in `pallet_assets::Pallet::transfer`'s doc comment: "the amount actually transferred may be slightly greater...") is never reflected on the credit side, and no total-issuance adjustment path exists in this call chain to reconcile the discrepancy.

## Impact Explanation
This breaks the `sum(all account balances) == total_issuance` invariant for the affected asset by silently destroying user funds equal to the dust-rounding delta, without crediting the beneficiary or burning issuance — an unaccounted value-destruction bug in a shared token primitive consumed by the public XCM execution path.

## Likelihood Explanation
Any unprivileged, signed account controlling its own asset balance and `min_balance` parameters can trigger this by choosing a transfer `amount` that leaves a remaining balance strictly between `0` and `min_balance`, and submitting it via `pallet_xcm::execute`/`transfer_assets`. No privileged actor, governance, or compromised third party is required.

## Recommendation
Modify the default `transfer()` implementations in `fungibles::Transfer` and `fungible::Transfer` to capture the actual value returned by `decrease_balance` and use that exact value as the argument to `increase_balance`, mirroring the paired debit/credit logic in `pallet_assets::functions::transfer_and_die`/`do_transfer`. Additionally, `FungiblesTransferAdapter`/`FungibleTransferAdapter::internal_transfer_asset` should propagate the actual transferred amount into the XCM holding register accounting instead of returning the originally requested `what.clone()`.

## Proof of Concept
1. Create an asset in `pallet-assets` with `min_balance = M`, and mint `M + amount` to account `A` (with `amount < M`).
2. Have `A` submit `pallet_xcm::execute` with a `TransferAsset { assets: (asset_location, amount).into(), beneficiary: B }` instruction, where debiting `amount` from `A` would leave a remainder below `M`.
3. `FungiblesTransferAdapter::internal_transfer_asset` calls `Assets::transfer(asset_id, A, B, amount, Expendable)`, which internally debits the pallet's dust-swept amount (`M + amount`) from `A` via `decrease_balance`, but only calls `increase_balance(asset, B, amount)`.
4. Compare `pallet_assets::Pallet::total_issuance(asset_id)` and `balance(A) + balance(B)` before/after: `total_issuance` is unchanged while the balance sum decreases by `M`, confirming silent value destruction.
