Audit Report

## Title
Bounty and child-bounty payout transfers are only checked with `debug_assert!`, allowing permanent loss of bounty funds on transfer failure - (File: `substrate/frame/bounties/src/lib.rs`, `substrate/frame/child-bounties/src/lib.rs`)

## Summary
`claim_bounty` in `pallet-bounties` and `claim_child_bounty` in `pallet-child-bounties` perform the curator-fee and beneficiary-payout `Currency::transfer` calls and validate the result only via `debug_assert!`, which is compiled out in release/production builds. Regardless of whether the transfers actually succeed, both functions unconditionally clear the bounty/child-bounty storage record and emit a success event, permanently orphaning any residual balance left in the deterministic bounty sub-account.

## Finding Description
In `claim_bounty`, after computing `final_fee` and `payout` from the bounty account's free balance, the code executes:
```rust
let res = T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
debug_assert!(res.is_ok());
let res = T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
debug_assert!(res.is_ok());

*maybe_bounty = None;
``` [1](#0-0) 

In production WASM runtime builds, `debug_assert!` is a no-op, so an `Err` from `T::Currency::transfer` (e.g. `TokenError::ExistentialDeposit` when a non-existent beneficiary account is awarded a payout below the existential deposit, or `TokenError::Frozen`/other restrictions from `Currency`/`fungible` implementations) does not halt execution. The function proceeds to unconditionally set `*maybe_bounty = None`, remove `BountyDescriptions`, notify `ChildBountyManager::bounty_removed`, and emit `BountyClaimed` with the `payout` value as if the transfer succeeded.

The identical pattern exists in `claim_child_bounty`, where both the curator-fee and beneficiary-payout transfers are checked only via `debug_assert!` before the child bounty record is deleted from storage.

Because `bounty_account_id(bounty_id)` is a deterministic sub-account derived only from the bounty index, once the storage record backing that index is removed, there is no remaining extrinsic path to reference, retry, or recover residual funds left in that account after a failed transfer.

The existing guard (`debug_assert!`) is provably insufficient because it has no effect in release builds, which is the build profile used for on-chain runtimes, and the code comments ("should not fail") reveal this was an unverified assumption rather than an enforced invariant.

## Impact Explanation
This matches the "permanent user-fund lock" impact category from the Polkadot SDK Impact Gate: if a beneficiary or curator payout transfer fails for any reason reachable in normal operation (e.g., destination account payout below the existential deposit, or a `Frozen`/`FundsUnavailable` condition from the concrete `Currency` implementation), the bounty record is deleted and a success event is emitted regardless, while the actual funds remain stranded in the now-unreferenced bounty sub-account with no extrinsic capable of recovering them.

## Likelihood Explanation
No privileged action is required to trigger the vulnerable code path: `claim_bounty`/`claim_child_bounty` can be called by any signed account (`ensure_signed(origin)?; // anyone can trigger claim`) once the bounty reaches `PendingPayout`. The beneficiary address is set earlier by the curator via `award_bounty`, and nothing in that call restricts the beneficiary to an account guaranteed to satisfy destination-side transfer preconditions (e.g., existential deposit for new/reaped accounts, or absence of freezes/holds from unrelated pallets). This makes the failure condition reachable through ordinary account state rather than requiring privileged conditions, though it does depend on the specific payout/fee amounts and destination account state at claim time.

## Recommendation
Replace the `debug_assert!`-guarded transfer calls in both `claim_bounty` (`substrate/frame/bounties/src/lib.rs`) and `claim_child_bounty` (`substrate/frame/child-bounties/src/lib.rs`) with proper `Result` propagation (`?`) so a failed transfer aborts the extrinsic before storage mutation, or adopt a `Paymaster`/`PaymentState` retry pattern (as already implemented in `pallet-multi-asset-bounties`) so that storage state (and the "claimed" event) only advances after the transfer is confirmed successful.

## Proof of Concept
1. Curator calls `award_bounty(bounty_id, beneficiary)` where `beneficiary` is a non-existent/reaped account, and the bounty's fee is set close to the bounty value such that the resulting `payout = balance.saturating_sub(fee)` is smaller than the existential deposit.
2. After the payout delay elapses, any signed account calls `claim_bounty(bounty_id)`.
3. `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` returns `Err(TokenError::ExistentialDeposit)` (or similar); in a release build `debug_assert!(res.is_ok())` compiles to nothing.
4. Execution continues: `*maybe_bounty = None`, `BountyDescriptions::remove`, and `BountyClaimed` is emitted as if the payout succeeded.
5. The residual balance remains in `bounty_account_id(bounty_id)`, but with the bounty index removed from storage, no extrinsic can reference or recover it — the funds are permanently stranded. A unit test can assert this by configuring a mock `Currency` transfer to return `Err` and observing that `Bounties::<T,I>::get(bounty_id)` is `None` and `BountyClaimed` is still emitted. [2](#0-1)

		pub fn claim_bounty(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
		) -> DispatchResult {
			ensure_signed(origin)?; // anyone can trigger claim

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.take().ok_or(Error::<T, I>::InvalidIndex)?;
				if let BountyStatus::PendingPayout { curator, beneficiary, unlock_at } =
					bounty.status
				{
					ensure!(Self::treasury_block_number() >= unlock_at, Error::<T, I>::Premature);
					let bounty_account = Self::bounty_account_id(bounty_id);
					let balance = T::Currency::free_balance(&bounty_account);
					let fee = bounty.fee.min(balance); // just to be safe
					let payout = balance.saturating_sub(fee);
					let err_amount = T::Currency::unreserve(&curator, bounty.curator_deposit);
					debug_assert!(err_amount.is_zero());

					// Get total child bounties curator fees, and subtract it from the parent
					// curator fee (the fee in present referenced bounty, `self`).
					let children_fee = T::ChildBountyManager::children_curator_fees(bounty_id);
					debug_assert!(children_fee <= fee);

					let final_fee = fee.saturating_sub(children_fee);
					let res =
						T::Currency::transfer(&bounty_account, &curator, final_fee, AllowDeath); // should not fail
					debug_assert!(res.is_ok());
					let res =
						T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath); // should not fail
					debug_assert!(res.is_ok());

					*maybe_bounty = None;

					BountyDescriptions::<T, I>::remove(bounty_id);
					T::ChildBountyManager::bounty_removed(bounty_id);

					Self::deposit_event(Event::<T, I>::BountyClaimed {
						index: bounty_id,
						payout,
						beneficiary,
					});
					Ok(())
