### Title
Uninitialized `accountIndexOf` rewards pre-registration holders the entire `INITIAL_INDEX` delta, draining unclaimed reward tokens - (File: contracts/RewardsDistributor.sol)

### Summary
`RewardsDistributor._calculateTokenDelta` only substitutes `INITIAL_INDEX` for an unset account index when the current token index is strictly greater than `INITIAL_INDEX`. When the global `tokenStates[token_].index` still equals `INITIAL_INDEX` (token registered but no index growth yet), an account holding a deposit/debt token balance that was never checkpointed has `accountIndexOf == 0`, producing `_deltaIndex = INITIAL_INDEX` (1e18) and crediting `balance * 1e18` reward tokens. This is the uninitialized-read analog: a default (zero) slot value is consumed as if it were real state.

### Finding Description
- `tokenStates[token_]` is only initialized to `INITIAL_INDEX` inside `_updateTokenSpeed` when a governor first sets a positive speed for a token (`contracts/RewardsDistributor.sol:296-299`).
- `updateBeforeMintOrBurn` / `updateBeforeTransfer` skip accrual entirely while `tokenStates[token_].index == 0` (`contracts/RewardsDistributor.sol:175-192`), so any balance acquired before registration leaves `accountIndexOf[token_][account] == 0` — uninitialized.
- In `_calculateTokenDelta` (`contracts/RewardsDistributor.sol:217-231`):
  ```solidity
  if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
      _accountIndex = INITIAL_INDEX;
  }
  uint256 _deltaIndex = _tokenIndex - _accountIndex;
  ```
  When `_tokenIndex == INITIAL_INDEX` (no growth yet — e.g. `claimRewards` is called in the same block as registration, or while speed accrual has produced zero delta because `block.timestamp == tokenState.timestamp`), the fallback does not trigger, `_accountIndex` stays `0`, and `_deltaIndex = 1e18`.
- `claimRewards` → `_updateTokensAccruedOf` writes `tokensAccruedOf[account] += balance.wadMul(1e18)` ≈ `balance` (`contracts/RewardsDistributor.sol:261-265`), then `_transferRewardIfEnoughTokens` pays out `tokensAccruedOf` up to the distributor's full `rewardToken` balance (`contracts/RewardsDistributor.sol:248-256`).

Attack path (unprivileged EOA, no privileged role needed at call time):
1. Hold any `DepositToken`/`DebtToken` balance before it is added to a `RewardsDistributor` (existing users trivially qualify when a new reward program starts, since token registration happens after the pool is live).
2. When governance calls `updateTokenSpeed`/`updateTokenSpeeds` (or `syncTokenSpeed`) to register the token, call `claimRewards(attacker)` in the same block (or before the index accrues past `INITIAL_INDEX`) directly or via `Operator.execute`.
3. `_deltaIndex = 1e18`, `tokensAccruedOf = balanceOf(attacker)`, and the distributor transfers `rewardToken` equal to the attacker's deposit-token balance, bounded only by the contract's reward balance.

### Impact Explanation
Direct theft of the reward token balance held by the distributor (unclaimed yield of all users). A holder with a large deposit balance extracts `balance * 1e18`-scaled reward, i.e. roughly `balance` reward tokens, capped only by the distributor's `rewardToken` holdings — an amount grossly exceeding any legitimately accrued reward.

### Likelihood Explanation
Requires a token whose `tokenStates.index == INITIAL_INDEX`, i.e. the window between registration and the first index increment (same block or until a nonzero accrual occurs). Registration is a routine governance action on deployed pools, and the attacker can front-run/observe the registration transaction and claim in the same block since `claimRewards` is permissionless (`accounts_` is arbitrary). Every pre-existing holder of the token satisfies the `accountIndexOf == 0` precondition. No reentrancy guard, pause flag, or `SynthContext` check blocks the claim.

### Recommendation
Treat an unset account index as "no accrued delta" rather than "delta from zero", e.g.:
```solidity
if (_accountIndex == 0) {
    _accountIndex = _tokenIndex > INITIAL_INDEX ? INITIAL_INDEX : _tokenIndex;
}
```
or initialize `accountIndexOf[token_][account]` to the current index on first touch inside `updateBeforeMintOrBurn`/`updateBeforeTransfer` even when `index == INITIAL_INDEX`.

### Proof of Concept
Foundry fork test sketch:

```solidity
// Fork target chain; use deployed Pool, RewardsDistributor, DepositToken
function testUninitializedAccountIndex() public {
    // attacker already holds depositToken balance before reward registration
    uint256 bal = depositToken.balanceOf(attacker);
    assertGt(bal, 0);

    // governor registers depositToken with a positive speed (same block)
    vm.prank(governor);
    distributor.updateTokenSpeed(IERC20(address(depositToken)), 1e18);
    // tokenStates.index == INITIAL_INDEX, accountIndexOf[depositToken][attacker] == 0

    uint256 before = rewardToken.balanceOf(attacker);
    vm.prank(attacker);
    distributor.claimRewards(attacker);

    // attacker receives ~bal reward tokens despite zero accrual time
    assertApproxEqAbs(rewardToken.balanceOf(attacker) - before, bal, 1);
}
```
Conceptually: `_calculateTokenDelta` returns `_tokensDelta = bal.wadMul(1e18) = bal`, so `claimRewards` transfers `bal` reward tokens, draining the distributor for accounts that never earned rewards.
