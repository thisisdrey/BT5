The strongest verifiable evidence I could gather is in `third_party/ijar/zip.cc`, Bazel's native ZIP central-directory reader, which is used to build interface jars/deploy jars out of dependency jars (including externally-fetched ones).

### Title
Heap out-of-bounds read parsing ZIP central-directory extra fields in `InputZipFile::ProcessCentralDirEntry` - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` parses the central directory of a ZIP/JAR file to extract file name, sizes, and extra fields [1](#0-0) . Unlike its sibling `ProcessLocalFileEntry`, which validates remaining input via `EnsureRemaining()` before reading variable-length fields [2](#0-1) , `ProcessCentralDirEntry` performs no such bounds check before or during the extra-field walk.

### Finding Description
After reading `file_name_length`, `extra_field_length`, and `file_comment_length` directly from attacker-controlled bytes, the function advances `p` by `extra_field_length` and then walks the resulting range parsing `(header_id, data_size)` pairs with no validation that each pair stays inside the declared `extra_field_length`, nor that the region is inside the mapped input file at all: [3](#0-2) . If `data_size` for one entry is crafted so `extra_p` never lands exactly on `p` (or `extra_field_length` itself is oversized relative to the actual file), the loop keeps calling `get_u2le`/`get_u8le` past the intended extra-field buffer — and, since `extra_p` is not checked against `input_file_->Length()`, potentially past the memory-mapped file entirely. This is structurally the same bug class as `icMemDump()`: a "dump/describe" style routine that trusts an internal length field embedded in untrusted binary metadata and reads accordingly without validating it against the actual buffer bounds.

By contrast, `src/tools/singlejar/zip_headers.h`'s `ExtraField::find` — used by the newer `singlejar` tool — does perform bounds checks (`ziph::byte_ptr(start) + extra_field->size() > ziph::byte_ptr(end)`) before dereferencing [4](#0-3) , and `output_jar.cc` has an explicit regression test guarding against malformed extra fields [5](#0-4) . `third_party/ijar/zip.cc`, which is the older/legacy ZIP reader still used for interface-jar generation, has no equivalent hardening.

### Impact Explanation
A crafted JAR/ZIP consumed by Bazel's ijar tool (e.g., a dependency jar fetched via `http_jar`/`http_archive`/Maven-style external repositories whose contents an attacker controls) can trigger an out-of-bounds heap/mmap read during interface-jar generation. This matches the CVE-2026-34540 pattern: integrity of the outer file (its hash) does not protect against malformed *internal* structure that a length-trusting parser walks past its real bounds. Impact is confined to a read (crash/ASan abort, potential info leak into error paths), consistent with the reported "C:N/I:N/A:H" — availability impact via crash, no confirmed write primitive.

### Likelihood Explanation
Likelihood is moderate: any external repository or dependency whose JAR bytes are attacker-influenced (a malicious upstream release, a compromised mirror serving a jar with a valid but attacker-chosen hash, or an untrusted branch's vendored jar) is a realistic delivery vector, since `ijar` is invoked automatically whenever such a jar is used as a Java dependency. However, I could not verify from the index whether this exact `ijar/zip.cc` path is reachable from the modern Bazel external-repository extraction pipeline (vs. only from `singlejar`/`ijar`'s already-hardened logic) or whether more recent Bazel builds route archive parsing exclusively through the safer `singlejar` header classes.

### Recommendation
Add explicit bounds validation in `InputZipFile::ProcessCentralDirEntry`'s extra-field loop mirroring `ExtraField::find` in `zip_headers.h`: verify `extra_p + 4 <= p` before reading the 2-byte header/size pair, and `extra_p + data_size <= p` before advancing, aborting with a diagnostic (as `output_jar.cc` does for "malformed extra field") rather than continuing to read. Additionally, validate `extra_field_length`/`file_comment_length` against remaining mapped-file bytes before use, consistent with `EnsureRemaining()` usage elsewhere in the same file.

### Proof of Concept
A C++ unit test analogous to the existing `OutputJarSimpleTest.MalformedExtraField` [6](#0-5)  can be constructed for `third_party/ijar/test/IjarTests.java`/`ZipCount.java` harness: craft a ZIP central-directory entry whose extra-field block declares a `data_size` for a ZIP64 tag (`0x0001`) that exceeds the entry's own `extra_field_length`, and run it through `InputZipFile::ProcessCentralDirEntry` (via `ProcessNext()`); under ASan this should surface as a heap-buffer-overflow read at the `get_u2le`/`get_u8le` calls in the extra-field walk.

**Caveat on confidence:** I could not verify in this index whether the currently-shipped, security-relevant extraction path for `http_archive`/`http_jar` (the Java `ZipDecompressor`/`DecompressorValue` classes explicitly named in the taxonomy) shares this weakness or has independent bounds checks — those files were not found by my searches, which may reflect index size limits rather than their absence. If precise confirmation of the `ZipDecompressor.java` code is required, a full Devin session with unrestricted repository access should be used to inspect `src/main/java/com/google/devtools/build/lib/bazel/repository/decompressor/` directly.

  const std::string filename = "evil.bin";

  // 1. Local File Header (LFH)
  size_t lh_offset = zip_data.size();
  size_t lh_size = sizeof(LH) + filename.size();
  zip_data.resize(lh_offset + lh_size, 0);
  auto* lh = reinterpret_cast<LH*>(&zip_data[lh_offset]);
  lh->signature();
  lh->version(10);
  lh->file_name(filename.data(), filename.size());

  // 2. Extra field payload containing an oversized payload_size
  uint8_t ef_buffer[8] = {0};
  auto* ef1 = reinterpret_cast<ExtraField*>(ef_buffer);
  ef1->signature(0x000d);
  ef1->payload_size(0);

  auto* ef2 = reinterpret_cast<ExtraField*>(ef_buffer + ef1->size());
  ef2->signature(0xdead);
  ef2->payload_size(0xf000);  // Malformed size exceeding extra field buffer

  // 3. Central Directory Header (CDH)
  size_t cdh_offset = zip_data.size();
  size_t cdh_size = sizeof(CDH) + filename.size() + sizeof(ef_buffer);
  zip_data.resize(cdh_offset + cdh_size, 0);
  auto* cdh = reinterpret_cast<CDH*>(&zip_data[cdh_offset]);
  cdh->signature();
  cdh->version(20);
  cdh->version_to_extract(10);
  cdh->local_header_offset32(lh_offset);
  cdh->file_name(filename.data(), filename.size());
  cdh->extra_fields(ef_buffer, sizeof(ef_buffer));

  // 4. End of Central Directory (EOCD)
  size_t ecd_offset = zip_data.size();
  zip_data.resize(ecd_offset + sizeof(ECD), 0);
