### Title
Hardcoded, non-network-configurable `ADDRESS_REGISTRAR_ACCOUNT_ID` can desynchronize the Wallet Contract's relayer address-collision check from the actual on-chain registrar - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
The ETH-implicit Wallet Contract embeds a single, compile-time constant account ID for the "Address Registrar" contract, `ADDRESS_REGISTRAR_ACCOUNT_ID`, read from a plain text file and parsed with `.parse().unwrap_or_else(|_| env::panic_str("Invalid address registrar"))` [3](#0-2) . Unlike `CHAIN_ID`, which `build.rs` explicitly rewrites for each of mainnet/testnet/localnet before building the respective WASM artifact [4](#0-3) , no equivalent per-network substitution exists for `ADDRESS_REGISTRAR_ACCOUNT_ID`. All three WASM variants are therefore built with the exact same hardcoded registrar account id, taken verbatim from `runtime/near-wallet-contract/implementation/wallet-contract/src/ADDRESS_REGISTRAR_ACCOUNT_ID` [2](#0-1) .

### Finding Description
The Wallet Contract's `address_check` mechanism exists specifically to defend users against a malicious or faulty relayer: when a base-token transfer's Ethereum `to` address could correspond either to a bare ETH-implicit account or to a real named Near account that has registered that same address via the `AddressRegistrar`, the wallet must call out to the registrar to authoritatively resolve which one is correct before routing funds, and must ban the relayer's key if it lied about the resolution [5](#0-4) . This is documented in `internal.rs` as the core anti-relayer-fraud invariant: an honest relayer must consult the registrar before setting `target` to a bare eth-implicit account [6](#0-5) .

This entire safety property is only as good as `ADDRESS_REGISTRAR_ACCOUNT_ID` actually pointing at the real, currently-deployed registrar contract for that network. Because the file is not swapped per-network by `build.rs` (in contrast to `CHAIN_ID`, which explicitly is), there is no protocol-level or build-level guarantee that the value shipped in the mainnet WASM binary is the correct, deployed mainnet registrar. If the on-chain registrar's account is changed, migrated, or if the constant used for the mainnet build happens to reference the wrong network's registrar (directly mirroring how the Moonwell report used the Base Testnet Wormhole Bridge address in the code path meant for Base Mainnet), one of two failure modes results:
- The registrar account referenced does not exist / has no matching `lookup` method deployed. Every `EOABaseTokenTransfer` with `address_check: Some(_)` then hits `PromiseResult::Failed` in `address_check_callback` and permanently fails with "Call to Address Registrar contract failed" [7](#0-6) , silently disabling all base-token transfers to addresses that require a collision check.
- Worse, if the referenced account exists but is stale/wrong (e.g., an old or different registrar with different registered mappings), `lookup` can return `None` for an address that is in fact registered under the real registrar, causing the anti-fraud check to pass a transaction through to the raw eth-implicit account instead of detecting the collision and banning the relayer, defeating the intended protection.

### Impact Explanation
If the deployed mainnet `ADDRESS_REGISTRAR_ACCOUNT_ID` is wrong (nonexistent, deprecated, or pointing to stale data), the wallet-contract-wide anti-relayer-collision defense is compromised across all ETH-implicit accounts network-wide. This can lead to loss of user funds being routed to the wrong (eth-implicit shadow) account instead of the intended registered named account — an authorization/target-confusion failure directly reachable by an ordinary relayer/user's `rlp_execute` transaction, with no operator or validator privilege required. It mirrors the reported bug's root cause and category precisely (compile-time-hardcoded external contract identifier lacking per-network build wiring), though here the "freeze" is milder (relayer-service DoS) unless the misconfiguration also enables the collision-bypass described above, which would be a fund-misdirection/authorization issue.

### Likelihood Explanation
This requires that `ADDRESS_REGISTRAR_ACCOUNT_ID`'s value shipped in a production build not match the actually deployed/expected registrar for that network — plausible given the file has no automated per-network override the way `CHAIN_ID` does, and its correctness relies entirely on manual maintenance of a single shared text file across three build targets. I could not verify from the available index whether an out-of-band process (e.g. a checked-in per-network resource swap similar to `wallet_contract_mainnet.wasm` vs `wallet_contract_testnet.wasm`) exists to override this value at packaging time outside of `build.rs`; this is a limitation of what I could confirm from the indexed code.

### Recommendation
Parameterize `ADDRESS_REGISTRAR_ACCOUNT_ID` per network the same way `CHAIN_ID` is parameterized in `build.rs` — i.e., have `build_contract` overwrite the `ADDRESS_REGISTRAR_ACCOUNT_ID` file with the correct, deployed registrar account id for each of mainnet/testnet/localnet before invoking `docker_build`, and add a build/test-time assertion that the constant resolves to a real, existing account with a working `lookup` method on the target network before shipping the WASM artifact.

### Proof of Concept
Not applicable as executable PoC given ask-only/read access — root cause is demonstrated by comparing the network-aware `CHAIN_ID` build step [8](#0-7)  against the network-agnostic handling of `ADDRESS_REGISTRAR_ACCOUNT_ID`, which is read once at compile time via `include_str!` with no corresponding per-network substitution [9](#0-8) , and by the direct consequences of that value being wrong shown in `address_check_callback` and `inner_rlp_execute` [10](#0-9) .

    /// Callback after checking if an address is contained in the registrar.
    /// This check happens when the target is another eth implicit account to
    /// confirm that the relayer really did check for a named account with that address.
    #[private]
    pub fn address_check_callback(
        &mut self,
        target: AccountId,
        action: near_action::Action,
        caller_deposit: Option<CallerDeposit>,
    ) -> PromiseOrValue<ExecuteResponse> {
        self.has_in_flight_tx = false;
        let maybe_account_id: Option<AccountId> = match env::promise_result(0) {
            PromiseResult::Failed => {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Call to Address Registrar contract failed".into()),
                });
            }
            PromiseResult::Successful(value) => match serde_json::from_slice(&value) {
                Ok(x) => x,
                Err(_) => {
                    return PromiseOrValue::Value(ExecuteResponse {
                        success: false,
                        success_value: None,
                        error: Some("Unexpected response from account registrar".into()),
                    });
                }
            },
        };
        let current_account_id = env::current_account_id();
        let promise = if maybe_account_id.is_some() {
            // We intentionally do not increment the nonce in this case because the
            // error is caused by a faulty relayer, not the user. An honest relayer
            // may still be able to successfully send the user's intended transaction.
            if env::signer_account_id() == current_account_id {
                create_ban_relayer_promise(current_account_id)
            } else {
                return PromiseOrValue::Value(ExecuteResponse {
                    success: false,
                    success_value: None,
                    error: Some("Invalid target: target is address corresponding to existing named account_id".into()),
                });
            }
        } else {
            // We must increment the nonce at this point to prevent replay of the transaction.
            // Recall that the nonce was not incremented in `inner_rlp_execute` in the case that
            // the registrar contract was called (i.e. in the case we end up inside this callback).
            self.nonce = self.nonce.saturating_add(1);
            let ext =
                WalletContract::ext(current_account_id).with_static_gas(RLP_EXECUTE_CALLBACK_GAS);
            match action_to_promise(target, action)
                .map(|p| p.then(ext.rlp_execute_callback(caller_deposit)))
            {
                Ok(p) => p,
                Err(e) => {
                    return PromiseOrValue::Value(e.into());
                }
            }
        };
        self.has_in_flight_tx = true;
        PromiseOrValue::Promise(promise)
    }
