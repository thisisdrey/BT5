Audit Report

## Title
Unvalidated `ContractCall.value` in Snowbridge V2 XCM-to-Ethereum converter allows draining agent's Ether reserves - (File: `bridges/snowbridge/primitives/outbound-queue/src/v2/converter/convert.rs`)

## Summary
`XcmConverter::convert()` decodes an attacker-supplied `Transact` payload (`ContractCall::V1 { value, .. }`) and forwards `value` unchecked into `Command::CallContract`, without validating it against the ENA amount actually withdrawn/reserved via `WithdrawAsset` earlier in the same XCM program. The dedicated error variant `CallContractValueInsufficient` exists in the error enum but is never constructed, confirming the intended check was never implemented.

## Finding Description
`convert()` extracts ENA amounts from `WithdrawAsset` and turns them into `Command::UnlockNativeToken { amount, .. }` via `extract_ethereum_native_assets`, entirely independently of the later `Transact` parsing block. In the `Transact` handling, `ContractCall::V1 { target, calldata, gas, value }` is decoded and `value` is pushed directly into `Command::CallContract { value, .. }` with no cross-check against the ENA amount unlocked earlier: [1](#0-0) 

ENA extraction itself only enforces `amount > 0` [2](#0-1) , and is entirely optional in the overall grammar (only `commands.len() > 0` is enforced before finalizing the message) [3](#0-2) , so a `Transact`-only message with a negligible or zero ENA withdrawal can still declare an arbitrary large `value`.

The `CallContractValueInsufficient` variant is declared in `XcmConverterError` but is not referenced or returned anywhere else in this file, confirming the check was intended but never implemented: [4](#0-3) 

Downstream, `Command::CallContract.value` is ABI-encoded as-is into `CallContractParams.value` and committed for execution on Ethereum without any additional Substrate-side check, since `abi_encode` simply passes the field through: [5](#0-4) 

The associated integration test explicitly documents the missing invariant with the comment "value should be less than the transfer amount, require validation on BH Exporter", confirming this is a known-but-unimplemented check rather than an intentional design decision.

## Impact Explanation
This falls under the "theft or unbacked mint/unlock" impact class: the `value` field committed in the outbound `Command::CallContract` is not bound to, or bootstrapped from, the amount of ENA actually reserved/unlocked in the same message. Any unprivileged account able to submit an XCM via `pallet_xcm::execute`/`send` targeting the bridge (subject to passing the `AllowedAliasOrigin` filter for `AliasOrigin`) can cause the outbound queue to commit a `CallContract` instruction demanding the agent forward Ether far beyond what was reserved on the Substrate side — up to draining whatever Ether balance the agent contract holds on Ethereum.

## Likelihood Explanation
This is reachable via a public, unprivileged entry point (`pallet_xcm::execute`/`send`) with no admin, governance, or relayer collusion required. The only constraint is passing `AllowedAliasOrigin::contains(origin_location)`, which any account with an origin permitted to alias into the bridge flow (as demonstrated by existing tests exercising `AliasOrigin`/`Transact`/`ContractCall` in the same test suite) can satisfy. The value/reserve linkage is structurally absent in `convert()`, making the bug deterministically triggerable, not merely theoretical.

## Recommendation
In `XcmConverter::convert()`, after collecting ENA-based `UnlockNativeToken` commands and before/while building `Command::CallContract`, sum the ENA amounts unlocked in this message and assert `value <= total_ena_unlocked_amount`, returning the already-declared `XcmConverterError::CallContractValueInsufficient` when violated. Alternatively, derive `value` deterministically from the reserved/unlocked ENA amount instead of trusting the independently-supplied `ContractCall::V1.value` field.

## Proof of Concept
1. Attacker submits an XCM via `pallet_xcm::execute` structured as: `WithdrawAsset` (fee) → `PayFees` → `WithdrawAsset` reserving a negligible ENA amount (e.g. `amount = 1`) → `AliasOrigin` (an origin passing `AllowedAliasOrigin`) → `DepositAsset` (attacker-controlled beneficiary) → `Transact` carrying `ContractCall::V1 { target: <attacker_target>, calldata: [], gas: <g>, value: <large_value> }` → `SetTopic`.
2. `extract_ethereum_native_assets` accepts the trivial `amount = 1` withdrawal [6](#0-5) , and the `Transact` block pushes `Command::CallContract { value: <large_value>, .. }` with no cross-check [7](#0-6) .
3. The resulting `Message` is queued/committed via the outbound queue and ABI-encoded for the Gateway contract, instructing the agent to forward `<large_value>` Ether to `target`, exceeding what was ever reserved on the Substrate side.
