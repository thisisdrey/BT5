### Title
Dust-transfer state bloat permanently occupies `depositTokensOfAccount` / `debtTokensOfAccount` slots, blocking victims from adding collateral or debt positions - (File: contracts/Pool.sol)

### Summary
The CVE describes a memory leak: every call to `AP4_StdcFileByteStream::Create` allocates a resource that is never released, so repeated calls exhaust resources and deny service. The direct analog in Metronome is `Pool`'s per-account token lists (`MappedEnumerableSet`). Each entry is a storage allocation that is only released when the account's balance returns to zero, and the list is capped by `MAX_TOKENS_PER_USER = 30`. An unprivileged attacker can allocate entries in *a victim's* set by dust-transferring deposit tokens, filling all 30 slots so the victim can no longer add a new collateral or debt token type.

### Finding Description
`Pool.addToDepositTokensOfAccount` and `Pool.addToDebtTokensOfAccount` are called by `DepositToken`/`DebtToken` whenever an account balance moves from 0 to non-zero — including on plain `transfer`/`transferFrom` inbound to an arbitrary recipient [1](#0-0) .

Each call is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [2](#0-1) . Once an entry is in the victim's `Set._values` array, it is only removed when the victim's balance returns to zero (`removeFromDepositTokensOfAccount`) [3](#0-2) .

Attack steps:

1. Attacker deposits a minimal amount of each pool-supported collateral into its own `DepositToken`s (cost: 1 wei of underlying each).
2. Attacker calls `depositToken_i.transfer(victim, 1)` for each of the available deposit tokens. Each transfer triggers `addToDepositTokensOfAccount(victim)`; entries accumulate in the victim's set until `MAX_TOKENS_PER_USER` is hit. Further transfers revert, but the 30 slots are already occupied.
3. Any subsequent victim action that requires adding a *new* token to either list — `DepositToken.deposit` into a collateral type they don't already hold, `DebtToken.issue`/`mint` of a new synthetic, leverage via `SmartFarmingManager`, or inbound transfers of additional deposit tokens — reverts with `UserReachedMaxTokens`.

The resource "leak" matches the CVE pattern: entries are allocated by a third party on the victim's behalf and persist until the victim manually withdraws each dust balance. No governance, oracle, or privileged role is involved — only public `transfer`/`deposit`/`issue` entry points reachable directly or via `Operator.execute`.

### Impact Explanation
Temporary freezing of funds / denial of core functionality. While the slots are occupied, the victim cannot deposit new collateral types or open new debt positions. Critically, if the victim's position is trending toward liquidation, they cannot add a different collateral to restore health — `deposit` into a new `DepositToken` reverts at the max-tokens check, and they are forced to watch their position be liquidated. The victim can recover only by withdrawing each dust balance (which removes the entry via `removeFromDepositTokensOfAccount`) or transferring the dust away — a cleanup cost imposed on the victim by the attacker, mirroring the leaked-resource asymmetry of the CVE (attacker allocates, victim must free).

### Likelihood Explanation
- Cost is low: 1 wei of underlying per deposit token, times the number of listed collaterals in the pool.
- No privileged role required; `transfer` is permissionless.
- Modifiers do not stop it: `onlyIfAdditionWillNotReachMaxTokens` only bounds the *attacker's* fill at 30 — it does not prevent reaching 30. `ReentrancyGuardTransient`, pause flags, and SynthContext checks are irrelevant to this path.
- The victim cannot pre-block inbound dust (no opt-in/allowlist on `addToDepositTokensOfAccount`).
- Griefing is repeatable: the attacker can re-dust after the victim cleans up.

### Recommendation
- Only add an account to `depositTokensOfAccount` on explicit user actions (`deposit`, `mint`) — not on inbound `transfer`/`transferFrom` — or require `amount >= dustThreshold` before registering the token.
- Alternatively, allow the account itself (or anyone) to call a `sweepToken(account, token)` that removes a zero-dust entry without requiring a full withdraw flow, and/or let `deposit`/`issue` auto-evict the lowest-value dust entries instead of reverting.
- If per-account caps are kept, emit an event on forced registration so monitoring can alert victims.

### Proof of Concept
Hardhat/Foundry fork sketch (Mainnet `Pool` + existing `DepositToken`s):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";
import {IERC20} from "../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract DustGriefingTest is Test {
    Pool pool = Pool(<FORKED_POOL>);
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    function test_fillVictimSlots() public {
        address[] memory dts = pool.getDepositTokens();
        require(dts.length >= pool.MAX_TOKENS_PER_USER(), "need >=30 listed collaterals");

        vm.startPrank(attacker);
        // Attacker acquires 1 wei of each deposit token via deposit
        for (uint i; i < pool.MAX_TOKENS_PER_USER(); ++i) {
            IDepositToken dt = IDepositToken(dts[i]);
            IERC20 under = dt.underlying();
            deal(address(under), attacker, 1);
            under.approve(address(dt), 1);
            dt.deposit(1, attacker);            // attacker balance 0->1
            dt.transfer(victim, 1);             // victim balance 0->1, slot allocated
        }
        vm.stopPrank();

        // Victim's set is full
        assertEq(
            pool.getDepositTokensOfAccount(victim).length,
            pool.MAX_TOKENS_PER_USER()
        );

        // Victim tries to deposit into a collateral type they don't hold -> reverts
        // (use any deposit token NOT in victim's set, or a fresh debt token mint)
        vm.startPrank(victim);
        IDepositToken newDt = IDepositToken(<ANOTHER_DEPOSIT_TOKEN>);
        deal(address(newDt.underlying()), victim, 1e18);
        newDt.underlying().approve(address(newDt), 1e18);
        vm.expectRevert(UserReachedMaxTokens.selector);
        newDt.deposit(1e18, victim);
        vm.stopPrank();
    }
}
```

Expected result: the loop fills all 30 of the victim's `depositTokensOfAccount` slots; every subsequent action that would register a new token for the victim reverts with `UserReachedMaxTokens`, and entries persist until the victim withdraws each dust balance — demonstrating attacker-allocated, victim-held state that is never proactively released, the storage analog of the leaked `AP4_StdcFileByteStream` objects.
