### Title
Unmetered `SUICIDE`/`transferAllToken` loop lets an attacker inflate a contract's TRC10 token map to make self-destruct settlements arbitrarily expensive at fixed energy cost - ([File: actuator/src/main/java/org/tron/core/vm/utils/MUtil.java])

### Summary
When a TVM contract self-destructs, `Program.suicide()`/`suicide2()` call `MUtil.transferAllToken()`, which iterates the *entire* `AssetMapV2` of the self-destructing account and rewrites both the source and destination `Account` protobufs. The energy charged for `SUICIDE` (`EnergyCost.getSuicideCost/2/3`) is a small constant (0, 5000, or 30000, plus a possible `NEW_ACCT_CALL` surcharge) and does **not** scale with the number of distinct TRC10 tokens the account holds. Because any unprivileged account can send a dust amount of an arbitrary number of distinct TRC10 tokens to any address via `TransferAssetContract` (there is no cap on the number of distinct token IDs an account can accumulate in its `assetV2` map), an attacker can inflate a victim contract's token map before that contract executes `SELFDESTRUCT`, causing the settlement loop to become arbitrarily large while the attacker only ever pays the fixed `SUICIDE` energy cost. This mirrors the reported OpenQ bug class: an unbounded, attacker-growable collection is iterated by a privileged/finalizing operation without a corresponding limit or fee, letting a third party grief that operation's cost/availability.

### Impact Explanation
An attacker can create/acquire many distinct TRC10 token IDs (each `AssetIssueContract` deployment is a one-time cost) and repeatedly dust-transfer them into a target contract address using ordinary `TransferAssetContract` transactions that require no permission from the recipient. When that contract later executes `SELFDESTRUCT` (a common pattern for factory/proxy cleanup, escrow release, or emergency withdrawal logic), `transferAllToken()` must rebuild both the source and destination `Account.Builder` objects while iterating over every injected token entry, at a cost that is not reflected in the fixed `SUICIDE` energy price. This can make legitimate self-destruct-based fund settlement/cleanup operations disproportionately expensive relative to the energy actually paid, and in the worst case push a single transaction toward CPU-time limits, degrading availability of that specific finalizing operation without the attacker bearing proportional cost — directly analogous to the reported "no token-limit enforcement" bug class that caused claims to become unexecutable.

### Likelihood Explanation
Likelihood is moderate: it requires an attacker to (a) obtain/issue a number of distinct TRC10 token IDs and (b) know/target a contract address that performs `SELFDESTRUCT` as part of its normal lifecycle (e.g., an escrow, proxy, or factory contract holding funds intended to be released on self-destruct). Both steps use only standard, permissionless transaction types (`AssetIssueContract`, `TransferAssetContract`, `TriggerSmartContract`), reachable by any unprivileged broadcaster.

### Recommendation
Cap the number of distinct TRC10 tokens accounted for in `SUICIDE` settlement (e.g., reject/limit `transferAllToken` beyond a bounded number of entries, or make the `SUICIDE` energy cost scale with `AssetMapV2` size, similar to how `AssetIssueActuator` bounds `frozenSupply` count and `VoteWitnessProcessor` bounds vote count). Alternatively, enforce a global cap on the number of distinct token IDs a single account can hold, independent of self-destruct.

### Proof of Concept
1. Attacker issues (or otherwise controls) N distinct TRC10 tokens via `AssetIssueContract`.
2. Attacker repeatedly calls `TransferAssetContract` to send a dust amount of each of the N tokens to a target smart-contract address that is known to eventually call `SELFDESTRUCT` (no receiver permission is required, per `TransferAssetActuator`).
3. When the target contract executes `SELFDESTRUCT`, `Program.suicide()`/`suicide2()` invoke `MUtil.transferAllToken()`, which iterates over all N injected token balances while charging the fixed `SUICIDE`/`SUICIDE2` energy cost (`EnergyCost.getSuicideCost`/`getSuicideCost2`/`getSuicideCost3`) regardless of N, demonstrating the cost/energy mismatch and unbounded growth of the iterated collection.

Note: I could not fully trace whether a node-wide CPU-time guard (e.g., `OutOfTimeException`) would abort this loop before consensus-affecting effects occur for very large N, since the general per-opcode CPU-time checks I found (`MUtil.checkCPUTimeForSelfDestructedBeneficiary`, `checkCPUTimeForFreezeV2AfterSelfDestruct`) only guard specific narrow scenarios, not the general `transferAllToken` iteration itself. Confirming the exact blast radius (single-tx revert vs. broader node stall) would require deeper tracing of the VM's execution-time accounting, which is out of reach of the current index.

  public static void transferAllToken(Repository deposit, byte[] fromAddress, byte[] toAddress) {
    AccountCapsule fromAccountCap = deposit.getAccount(fromAddress);
    Protocol.Account.Builder fromBuilder = fromAccountCap.getInstance().toBuilder();
    AccountCapsule toAccountCap = deposit.getAccount(toAddress);
    toAccountCap.importAllAsset();
    Protocol.Account.Builder toBuilder = toAccountCap.getInstance().toBuilder();
    fromAccountCap.getAssetMapV2().forEach((tokenId, amount) -> {
      toBuilder.putAssetV2(tokenId, toBuilder.getAssetV2Map().getOrDefault(tokenId, 0L) + amount);
      fromBuilder.putAssetV2(tokenId, 0L);
    });

    deposit.putAccountValue(fromAddress, new AccountCapsule(fromBuilder.build()));
    deposit.putAccountValue(toAddress, new AccountCapsule(toBuilder.build()));
  }

  public static long getSuicideCost(Program ignored) {

  public static long getSuicideCost2(Program program) {
    DataWord inheritorAddress = program.getStack().peek();
    if (isDeadAccount(program, inheritorAddress)) {
      return getSuicideCost(program) + NEW_ACCT_CALL;
    }
    return getSuicideCost(program);
  }

  public static long getSuicideCost3(Program program) {
    DataWord inheritorAddress = program.getStack().peek();
    if (isDeadAccount(program, inheritorAddress)) {
      return SUICIDE_V2 + NEW_ACCT_CALL;
    }
    return SUICIDE_V2;
  }
