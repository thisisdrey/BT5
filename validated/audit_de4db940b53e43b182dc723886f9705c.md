### Title
Underwater borrower cannot partially deleverage via `flashRepay` because the end-of-transaction health check reverts unless the position is fully healthy — ([File: contracts/SmartFarmingManager.sol](contracts/SmartFarmingManager.sol))

### Summary
`SmartFarmingManager.flashRepay` lets a borrower atomically withdraw collateral, swap it to the synthetic asset through an external swapper, and repay debt in a single transaction. However, it ends with a hard check that the resulting position must be *fully* healthy (`PositionIsNotHealthy` revert). For an underwater borrower, collateral is locked (`unlockedBalanceOf` returns 0 / `_revertIfLocked` blocks transfers and withdrawals), so `flashRepay` is the only self-service route to unwind the position. If a single call cannot restore health — e.g. the position is spread across several deposit tokens, or the collateral→synth swap has limited liquidity — every call reverts, mirroring the Size `compensate()` bug where the borrower could not incrementally improve their collateral ratio.

### Finding Description
In `SmartFarmingManager.sol`:

```solidity
// 1. withdraw collateral
(_withdrawn, ) = depositToken_.flashWithdraw(_msgSender, withdrawAmount_);
// 2. swap it for synth
uint256 _swapAmountOut = _swap(swapper(), _collateralOf(depositToken_), _syntheticToken, _withdrawn, 0);
if (_swapAmountOut < swapAmountOutMin_) revert FlashRepaySlippageTooHigh();
// 3. repay debt
(_repaid, ) = _debtToken.repay(_msgSender, _amountToRepay);
// 5. check the health of the outcome position
(bool _isHealthy, , , , ) = _pool.debtPositionOf(_msgSender);
if (!_isHealthy) revert PositionIsNotHealthy();
``` [1](#0-0) 

The check is absolute ("must be healthy after this call") rather than relative ("must not be worse than before"). Meanwhile, an underwater user cannot exit any other way:

- `DepositToken.unlockedBalanceOf` only unlocks collateral when `_issuableInUsd > 0`; when the position is below the liquidation threshold, issuable headroom is zero, so `unlockedBalanceOf` returns 0 and `transfer`/`transferFrom`/`withdraw` revert through `_revertIfLocked`. [2](#0-1) 
- `DebtToken.repay` itself has no health check (only a `debtFloorInUsd` dust check), but the user needs synth tokens to repay and typically has none — they must sell collateral, which is exactly what `flashRepay` exists to do. [3](#0-2) 

Concretely: a borrower with debt in `msUSD` and collateral split across two `DepositToken`s (e.g. `msdMET` and a `vaUSDC`-type deposit token) where repaying against one collateral alone cannot push CR back above `liquidationThreshold` will have every `flashRepay` call revert at step 5 — even though each individual call strictly improves (or at least does not worsen) the position. They cannot sequentially unwind, so the position sits underwater until a third-party liquidator repays it via `Pool.liquidate`, charging `liquidatorIncentive` + `protocolFee`. [4](#0-3) 

### Impact Explanation
The borrower is denied any self-deleveraging path when a single transaction cannot fully heal the position. Their collateral remains locked (unwithdrawable, untransferable) and the position is forcibly liquidated by external liquidators, imposing the liquidation penalty on top of the loss. This is an avoidable loss of user funds equivalent in mechanism to the Size M-09 `compensate()` issue: the "improve CR" primitive reverts unless the improvement is complete in one shot.

### Likelihood Explanation
Requires a position that goes below the liquidation threshold (ordinary market volatility on a leveraged position — `leverage` explicitly supports up to `1/(1 - collateralFactor)` leverage) plus any condition making single-call recovery impossible: collateral spread across multiple deposit tokens, or insufficient DEX liquidity in the swapper route to convert enough collateral to synth at once. Both are realistic on deployed pools. The check is unconditional (`whenNotShutdown` + `nonReentrant` only), so there is no privileged bypass.

### Recommendation
Measure health before and after the `flashRepay` operation instead of requiring full health. For example, capture `debtPositionOf(_msgSender)` (or the CR/debt-to-collateral ratio) at the start, and revert only if the resulting position is *worse* — i.e. revert if `_debtInUsd` did not decrease or if the collateralization ratio strictly decreased. The same fix applied to Size's `compensate()` (measure CR before/after, revert only on worsening) applies directly here.

### Proof of Concept
Reproducible on the existing Hardhat suite (`test/SmartFarmingManager.test.ts` pattern):

1. User deposits collateral in two deposit tokens (`depositTokenA`, `depositTokenB`), mints `msUSD` near the max via `SmartFarmingManager.leverage`.
2. Drop the collateral price in `MasterOracle` (or move the swapper rate) so `debtPositionOf` returns `_isHealthy == false`.
3. Compute `withdrawAmount_` = full balance of `depositTokenA`; swapping it repays only part of the debt — insufficient to restore health (e.g. debt is owed against both collaterals).
4. Call `flashRepay(msUSD, depositTokenA, balanceA, minOut)` → reverts with `PositionIsNotHealthy` despite debt decreasing.
5. Confirm `depositTokenA.unlockedBalanceOf(user) == 0` and `withdraw`/`transfer` revert — the user cannot deleverage at all, and only `Pool.liquidate` by a third party can close the position.

Note on uncertainty: the exact revert inside `unlockedBalanceOf`/`_revertIfLocked` for a fully underwater account (whether `_issuableInUsd` is 0 or negative-clamped in `debtPositionOf`) was not fully traced, but either way the unlocked balance is 0, which supports the conclusion that `flashRepay` is the sole exit path.
