### Title
Dust `DepositToken` transfers fill a victim's `MAX_TOKENS_PER_USER` slots, blocking new collateral deposits and borrows needed to avoid liquidation - (File: contracts/Pool.sol)

### Summary
The NATS compression-bomb class maps to unbounded/attacker-controlled resource growth that degrades availability. In Metronome, the analogous attacker-inflated resource is the per-account token list: any unprivileged user can `transfer()` dust amounts of every whitelisted `msdTOKEN` (DepositToken) to a victim, filling the shared `debtTokensOfAccount + depositTokensOfAccount` budget of `MAX_TOKENS_PER_USER = 30` slots in `Pool`. Once saturated, `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` revert with `UserReachedMaxTokens`, so the victim cannot deposit a new collateral type or open a new synthetic debt position — including the collateral top-up needed to keep an underwater position healthy before `liquidate` seizes it.

### Finding Description
`DepositToken._transfer` adds the recipient to `depositTokensOfAccount` whenever the recipient's prior balance is zero (`DepositToken.sol:517-520`), and `Pool.addToDepositTokensOfAccount` enforces `onlyIfAdditionWillNotReachMaxTokens`, reverting once the combined debt+deposit token count reaches 30 (`Pool.sol:143-148, 216-220`). There is no minimum-amount check, no opt-in, and no per-account approval for receiving DepositTokens — `transfer`/`transferFrom` are public (`DepositToken.sol` `_transfer` only rejects zero addresses and insufficient balance). An attacker holding or cheaply acquiring dust balances of each whitelisted DepositToken can therefore push up to 30 entries into a victim's list in one transaction bundle.

Because `DebtToken` is non-transferable (`transfer`/`transferFrom` revert with `TransferNotSupported`, `DebtToken.sol:507-519`), the debt side cannot be filled directly, but filling all 30 slots with deposit tokens also blocks `_mint`'s `pool.addToDebtTokensOfAccount` (`DebtToken.sol:598-600`), since the limit counts both lists.

Invariant broken: liveness of position management — a user with healthy or marginal collateral loses the ability to add a *new* collateral type or issue a new synthetic token for as long as the attacker's dust occupies the slots.

### Impact Explanation
- **Forced liquidation / loss of funds:** a victim whose position drifts toward unhealthy cannot deposit a different collateral type to restore health; `issue`/`mint` of any new debt token also reverts. If their existing collateral types can't cover the shortfall, the position is liquidated and the liquidation fee is lost — direct, attacker-influenced loss of user funds.
- **Temporary freezing of funds/functionality:** for the duration of the griefing, deposits of new tokens, borrows, leverage via `SmartFarmingManager` (which calls `DebtToken.mint`), and receipt of airdropped/transferred new tokens all revert for the victim.
- The attack is cheap: dust amounts suffice; the only requirement is that the pool has ≥ a few whitelisted DepositTokens (capped by `ReachedMaxDepositTokens` governance additions) and the attacker holds a wei of each.

### Likelihood Explanation
The exploit requires only an EOA calling `DepositToken.transfer(victim, dust)` for each whitelisted token — no privileged role, no oracle manipulation, no flash loan needed. Mitigating factors reduce it from critical: the victim can self-recover by transferring the dust balances back out (`_burn`-style removal occurs when balance hits zero, `DepositToken.sol:522-525`), which costs gas and requires the victim to notice; and existing (non-new) collateral types can still be topped up since re-depositing an already-listed token doesn't call `addToDepositTokensOfAccount`. The attack is thus most damaging when front-run against a victim who must add a *new* collateral type or issue a *new* synth to survive — a narrow but real window, and the griefer can re-fill slots each time the victim clears one.

### Recommendation
- Apply a minimum meaningful amount (e.g., oracle-priced USD floor) before adding a token to `depositTokensOfAccount`, or only add to the list on `deposit`/`mint` paths and not on plain `transfer` receipt.
- Alternatively, allow the account itself (or `Pool.liquidate`/`deposit` paths) to evict entries, or count only tokens above a dust threshold in `onlyIfAdditionWillNotReachMaxTokens`.
- Consider separating the deposit-token and debt-token caps so filling one list can't block the other.

### Proof of Concept
Hardhat (fork/localhost), sketch:

```ts
// setup: pool with N whitelisted DepositTokens dt[0..N-1]; victim has an
// existing position in dt[0] that will need a different collateral to stay healthy.

// attacker deposits a minimal amount into each deposit token to get dust balances
for (const dt of depositTokens) {
  await underlying(dt).approve(dt.address, DUST);
  await dt.deposit(DUST, attacker.address); // or depositAndMint path
}

// grief: fill victim's slots
for (const dt of depositTokens) {
  await dt.connect(attacker).transfer(victim.address, 1); // 1 wei of each msdTOKEN
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.length(N);

// victim had N slots used; attacker pads to MAX_TOKENS_PER_USER=30 by cycling
// dust through new token types until:
const newDt = depositTokens[depositTokens.length - 1];
await underlying(newDt).connect(victim).approve(newDt.address, amount);
await expect(newDt.connect(victim).deposit(amount, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens'); // via _mint -> addToDepositTokensOfAccount

// likewise, issuing a new synth type fails:
await expect(debtToken.connect(victim).issue(x, victim.address))
  .revertedWithCustomError(pool, 'UserReachedMaxTokens');

// after price move makes victim unhealthy, liquidate succeeds while the
// victim was blocked from adding the new collateral that would have cured it:
await pool.connect(liquidator).liquidate(victim.address, repayAmt, dt0.address, liquidator.address);
```

Key code paths verified: `DepositToken._transfer` adds recipient at `DepositToken.sol:517-520`; cap enforcement at `Pool.sol:143-148`; `DebtToken._mint` add at `DebtToken.sol:598-600`; slot removal on zero balance at `DepositToken.sol:522-525` (victim recovery vector).
