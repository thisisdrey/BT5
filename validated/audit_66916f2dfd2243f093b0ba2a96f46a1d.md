This confirms a solid analog. The `costhandler` package computes a per-RPC "cost score" (`x-gitaly-cost` trailer) that Rails/Workhorse forward as the `X-Score` header for Cloudflare rate-limit budgeting, per `internal/grpc/middleware/costhandler/costhandler.go:1-9`. The dynamic component of that score is derived solely from `grpcstats.PayloadBytesStats`, which is populated by the gRPC `stats.Handler` from `stats.InPayload`/`stats.OutPayload` events on the *regular gRPC stream* [1](#0-0) , and combined with a small static per-method weight [2](#0-1) .

However, `SSHUploadPackWithSidechannel`, `PostUploadPackWithSidechannel`, and `PackObjectsHookWithSidechannel` deliberately move all bulk Git data (the actual packfile, potentially gigabytes) off the gRPC stream and onto a separate Yamux sidechannel connection specifically "to sidestep gRPC Protobuf message overhead" [3](#0-2) , confirmed by `doc/sidechannel.md:9-18`. The sidechannel bytes flow over `internal/grpc/sidechannel` connections/proxies (e.g. `internal/grpc/sidechannel/proxy.go:96-128`, `internal/grpc/sidechannel/sidechannel.go`) which are never observed by the `grpcstats.PayloadBytes` stats handler, since that handler only taps `stats.RPCStats` events on the underlying `grpc.ServerStream`. As a result, `dynamicCostFromContext` sees only the small control-plane messages (request/response protobufs) and not the actual packfile payload [4](#0-3) . These sidechannel RPCs get only a small flat `staticCostOverrides` value (10) regardless of transfer size [5](#0-4) .

This is structurally the same bug class as the Optimism report: a resource-accounting mechanism (there: L1 gas limit metering L2 execution cost; here: the `x-gitaly-cost`/`X-Score` trailer metering actual Gitaly I/O cost for downstream rate-limiting) can be starved of its real cost signal because the expensive resource consumption (multi-GB packfile transfer) happens through a channel the accounting mechanism doesn't observe (the sidechannel), while only a fixed, small cost is reported.

I did not find a way to verify how Workhorse/Rails actually consume `X-Score` for enforcement (that logic lives outside this repo, in `gitlab-org/gitlab` and `gitlab-org/gitaly-proxy`/Workhorse), so I cannot fully confirm the downstream impact (e.g., whether this actually degrades a Cloudflare/Workhorse rate limiter in practice) — this is noted as uncertain and is consistent with the "hint, not proof" caveat for the external report.

### Title
Sidechannel bulk data transfers are invisible to the gRPC cost-accounting trailer, allowing rate-limit budget evasion for expensive fetch RPCs - (File: internal/grpc/middleware/costhandler/costhandler.go)

### Summary
The `x-gitaly-cost` gRPC trailer, which downstream systems use as a rate-limiting budget signal (`X-Score`), is computed from gRPC-observed payload bytes plus a small static per-method weight. For sidechannel RPCs (`SSHUploadPackWithSidechannel`, `PostUploadPackWithSidechannel`, `PackObjectsHookWithSidechannel`), the actual bulk data (packfiles, potentially many gigabytes) bypasses the gRPC stream entirely, so it is never counted, meaning the reported cost radically understates real server resource consumption.

### Finding Description
`costhandler.computeCost` sums a static cost (`staticCostForMethod`, capped at a flat value of 10 for sidechannel RPCs via `staticCostOverrides`) and a dynamic cost derived from `grpcstats.PayloadBytesStats.InPayloadBytes + OutPayloadBytes` [6](#0-5) . `PayloadBytesStats` is populated exclusively via the gRPC `stats.Handler` interface's `HandleRPC`, reacting to `stats.InPayload`/`stats.OutPayload` events tied to the standard gRPC message stream [7](#0-6) .

By design, sidechannel RPCs move all high-volume byte-stream data (the actual Git pack/fetch data) off the gRPC stream onto a separate Yamux-multiplexed connection to avoid protobuf framing overhead [8](#0-7) , [3](#0-2) . That data is proxied through `internal/grpc/sidechannel` (`OpenSidechannel`, `proxy`) using raw `net.Conn`/Yamux stream I/O completely outside the gRPC message path [9](#0-8) , [10](#0-9) . Consequently, `grpcstats.PayloadBytes` never observes these bytes, and `dynamicCostFromContext` computes a near-zero dynamic cost regardless of how large the actual fetch/clone/pack-objects response is.

An ordinary authenticated user issuing a normal `git clone`/`git fetch` over SSH or HTTP (which routes through `SSHUploadPackWithSidechannel`/`PostUploadPackWithSidechannel`) triggers exactly this code path — no special crafting is needed beyond requesting a large repository/ref set, which is a completely ordinary fetch operation.

### Impact Explanation
Because `x-gitaly-cost` (forwarded as `X-Score`) is explicitly documented as the signal Rails/Workhorse forward for "rate-limit budget accounting" and to Cloudflare, systematically under-reporting the cost of the most resource-intensive RPC family (bulk Git fetch/pack-object generation, which is exactly the traffic sidechannels were introduced to accelerate) undermines the very rate-limiting/backpressure mechanism this signal exists to drive. This mirrors the Optimism finding where the metering mechanism (gas limit) failed to capture the actual cost of the expensive operation, allowing consumption of downstream resources without a proportional accounting signal — enabling a low apparent "cost" while imposing high actual Gitaly I/O/CPU load (git-upload-pack, pack-objects generation), consistent with a DoS/resource-exhaustion class of issue on the RPC-handler resource-limiting mechanism.

### Likelihood Explanation
High likelihood of the accounting gap being triggered: any ordinary `git clone`/`fetch` of a large repository over SSH/HTTP naturally uses the sidechannel RPCs and naturally produces a large discrepancy between actual bytes transferred and the reported cost, with zero extra effort or malicious crafting required — the gap is inherent to the current architecture rather than requiring an edge-case payload.

### Recommendation
Account for bytes transferred over sidechannel connections when computing the dynamic cost component. For example, instrument the sidechannel `ServerConn`/`ClientConn` read/write paths (`internal/grpc/sidechannel/conn.go`, `proxy.go`) to record transferred byte counts into the same context-scoped stats structure that `grpcstats.PayloadBytesStats` uses, so `dynamicCostFromContext` reflects actual data volume for `SSHUploadPackWithSidechannel`, `PostUploadPackWithSidechannel`, and `PackObjectsHookWithSidechannel`. Alternatively, raise the static cost overrides for these RPCs to a value that conservatively estimates typical sidechannel transfer sizes rather than relying on the (currently blind) dynamic component.

### Proof of Concept
1. As an authenticated Gitaly client, perform a normal `git clone`/`git fetch` of a large repository (multi-GB) via SSH, hitting `SSHUploadPackWithSidechannel`.
2. Observe that the bulk packfile bytes are proxied entirely through the sidechannel (`internal/grpc/gitalyclient/upload_pack.go:33-38`, using `stream.ProxyPktLine` over the sidechannel `ClientConn`), never passing through the gRPC message stream that `grpcstats.PayloadBytes` instruments.
3. Inspect the `x-gitaly-cost` trailer returned by `SSHUploadPackWithSidechannel` (via `costhandler.UnaryInterceptor`): it will equal the flat static override (10) plus a negligible dynamic component derived only from the small `SSHUploadPackWithSidechannelRequest`/`Response` protobuf messages, regardless of whether the actual packfile transferred was 1 MB or 10 GB — confirming the cost signal does not scale with actual resource consumption for sidechannel RPCs.

// HandleRPC implements per-RPC tracing and stats instrumentation.
func (s *PayloadBytes) HandleRPC(ctx context.Context, rs stats.RPCStats) {
	switch st := rs.(type) {
	case *stats.InPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.InPayloadBytes += int64(st.Length)
	case *stats.OutPayload:
		bytesStats := ctx.Value(payloadBytesStatsKey{}).(*PayloadBytesStats)
		bytesStats.OutPayloadBytes += int64(st.Length)
	}
}

// computeCost returns the cost score for a completed RPC. It combines a static
// base cost for the RPC type with a dynamic component from actual bytes
// transferred, read from the RPCEntry in context.
func computeCost(ctx context.Context, fullMethod string) int {
	static := staticCostForMethod(fullMethod)
	dynamic := dynamicCostFromContext(ctx)
	return static + dynamic
}

// staticCostForMethod returns the static cost weight for the given full method
// name. It first checks per-RPC overrides, then falls back to a default based
// on the method's operation type from the proto registry.
func staticCostForMethod(fullMethod string) int {
	if cost, ok := staticCostOverrides[fullMethod]; ok {
		return cost
	}

	methodInfo, err := protoregistry.GitalyProtoPreregistered.LookupMethod(fullMethod)
	if err != nil {
		return defaultUnknownCost
	}

	switch methodInfo.Operation {
	case protoregistry.OpAccessor:
		return defaultAccessorCost
	case protoregistry.OpMutator:
		return defaultMutatorCost
	case protoregistry.OpMaintenance:
		return defaultMaintenanceCost
	default:
		return defaultUnknownCost
	}
}

// dynamicCostFromContext computes the dynamic cost contribution from payload
// bytes tracked by the grpcstats.PayloadBytes stats handler.
func dynamicCostFromContext(ctx context.Context) int {
	stats := grpcstats.PayloadBytesStatsFromContext(ctx)
	if stats == nil {
		return 0
	}
	totalBytes := stats.InPayloadBytes + stats.OutPayloadBytes

	return int(math.Ceil(float64(totalBytes) / float64(byteCostDivisor)))
}

// OpenSidechannel opens a sidechannel connection from the stream opener
// extracted from the current peer connection.
func OpenSidechannel(ctx context.Context) (_ *ServerConn, err error) {
	span, ctx := tracing.StartSpanIfHasParent(ctx, "sidechannel.OpenSidechannel", nil)
	defer span.End()

	md, ok := metadata.FromIncomingContext(ctx)
	if !ok {
		return nil, fmt.Errorf("sidechannel: failed to extract incoming metadata")
	}
	ids := md.Get(sidechannelMetadataKey)
	if len(ids) == 0 {
		return nil, fmt.Errorf("sidechannel: sidechannel-id not found in incoming metadata")
	}
	sidechannelID, _ := strconv.ParseInt(ids[len(ids)-1], 10, 64)

	muxSession, err := backchannel.GetMuxSession(ctx)
	if err != nil {
		return nil, fmt.Errorf("sidechannel: fail to extract mux session: %w", err)
	}

	stream, err := muxSession.Open(ctx)
	if err != nil {
		return nil, RetryableError{error: fmt.Errorf("sidechannel: open stream: %w", err)}
	}
	defer func() {
		if err != nil {
			stream.Close()
		}
	}()

	if err := stream.SetDeadline(time.Now().Add(sidechannelTimeout)); err != nil {
		return nil, err
	}

	if _, err := stream.Write(magicBytes); err != nil {
		return nil, RetryableError{error: fmt.Errorf("sidechannel: write magic bytes: %w", err)}
	}

	if err := binary.Write(stream, binary.BigEndian, sidechannelID); err != nil {
		return nil, RetryableError{error: fmt.Errorf("sidechannel: write stream id: %w", err)}
	}

	buf := make([]byte, 2)
	if _, err := io.ReadFull(stream, buf); err != nil {
		return nil, RetryableError{error: fmt.Errorf("sidechannel: receive confirmation: %w", err)}
	}
	if string(buf) != "ok" {
		return nil, fmt.Errorf("sidechannel: expected ok, got %q", buf)
	}

	if err := stream.SetDeadline(time.Time{}); err != nil {
		return nil, err
	}

	return newServerConn(stream), nil
}
