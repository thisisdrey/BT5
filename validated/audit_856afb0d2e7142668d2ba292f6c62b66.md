### Title
Floating-point precision loss in the TRC10 Bancor-relay Exchange pricing engine allows value extraction via crafted trade sizing - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The UwU Lend incident relied on an attacker manipulating an AMM-derived price within a single transaction/session and then arbitraging the mispriced pool for profit. The closest reachable analog in java-tron is its built-in bancor-relay `Exchange` feature (`ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`), a self-contained AMM whose swap output is computed by `ExchangeProcessor` using `double`-precision floating point math rather than exact integer/BigDecimal arithmetic, unless the chain-parameter-gated "hardened" mode is enabled.

### Finding Description
`ExchangeCapsule.transaction()` selects between two pricing engines depending on the `allowHarden` flag: the legacy `ExchangeProcessor` (double/`Math.pow`-based) or `SafeExchangeProcessor` (BigDecimal-based), controlled via `AbstractExchangeActuator.allowHarden()` which reads `dynamicStore.allowHardenExchangeCalculation()`. [1](#0-0) [2](#0-1) 

The default path, `ExchangeProcessor`, computes the bancor-relay conversion using `double` arithmetic and `Maths.pow(...)`: [3](#0-2) 

This computation is reachable directly from `ExchangeTransactionActuator.execute()`/`.validate()`, invoked by any unprivileged account broadcasting an `ExchangeTransactionContract` — no special permission is required beyond owning the exchange-pair tokens/TRX. [4](#0-3) 

The test suite in this repository explicitly demonstrates that the double-based `ExchangeProcessor` and the BigDecimal-based `SafeExchangeProcessor` produce *different* results for the same inputs (`testStrictMath`), confirming rounding/precision divergence is a known, measurable property of the default calculation path: [5](#0-4) 

Because the default pricing math is not exact, an attacker who repeatedly selects `sellTokenQuant` values that maximize favorable floating-point rounding in `exchangeToSupply`/`exchangeFromSupply` can systematically extract more of the counter-asset than the bancor invariant would allow with exact arithmetic — conceptually the same "manipulate the pricing mechanism, then arbitrage the pool" pattern as the UwU Lend attack, except the mispricing here comes from floating-point precision loss in TRON's own on-chain AMM rather than an external oracle reading a manipulated Curve pool.

### Impact Explanation
If exploitable, repeated crafted `ExchangeTransactionContract` calls could drain TRX/TRC10 balances from an `Exchange` pool beyond what the intended invariant allows, resulting in unbacked withdrawal of pool funds — a concrete theft-of-funds impact reachable by any transaction broadcaster with a funded exchange counterparty asset.

### Likelihood Explanation
Likelihood is tempered by two factors I could not fully confirm from the available index: (1) the default value of the `allowHardenExchangeCalculation` dynamic property (whether the vulnerable double-based path is actually active by default or the hardened BigDecimal path has already been made mandatory), and (2) whether the magnitude of the double-precision rounding error is large enough, at TRX-scale balances, to be profitably exploitable versus merely a negligible dust-level discrepancy. I was unable to locate the property's default initialization in `DynamicPropertiesStore.java` within the available tool budget to make this determination conclusively.

### Recommendation
Confirm whether `allowHardenExchangeCalculation` defaults to enabled (hardened/BigDecimal path) on all networks; if not, make `SafeExchangeProcessor` the unconditional pricing engine for `Exchange`-related actuators, removing the legacy `double`-based `ExchangeProcessor` from the active code path entirely, and add fuzz/differential tests bounding the maximum extractable value from repeated small-quantity trades against a pool.

### Proof of Concept
Not independently reproduced; recommend a Devin session to (a) determine the default of `allowHardenExchangeCalculation`, and (b) build a differential/fuzz test harness comparing `ExchangeProcessor` vs `SafeExchangeProcessor` output over many `(sellBalance, buyBalance, sellQuant)` triples to quantify whether an attacker can accumulate a material, repeatable rounding advantage large enough to constitute practical fund theft from an `Exchange` pool.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
