## Title
Inconsistent Bancor-formula hardening across Exchange* actuators enables precision-based value extraction from AMM pools - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `ExchangeWithdrawActuator.java`)

### Summary
`ExchangeTransactionActuator` was upgraded to route its swap-amount computation through `ExchangeCapsule.transaction(...)`, which — when `allowHardenExchangeCalculation()` is enabled — delegates to `SafeExchangeProcessor`, a BigDecimal/`StrictMathWrapper`-based reimplementation of the Bancor-style relay-token formula used by TRON's on-chain `Exchange` (an AMM/bonding-curve pool). `ExchangeInjectActuator` and `ExchangeWithdrawActuator` operate on the exact same `ExchangeCapsule` pool state (`firstTokenBalance`/`secondTokenBalance`) but were **not** migrated to this hardened path — each still computes the "other token" amount with its own ad-hoc arithmetic (`floorDiv(multiplyExact(...))` in Inject, raw `BigInteger`/`BigDecimal` division in Withdraw) rather than calling `exchangeCapsule.transaction(...)`/`SafeExchangeProcessor`. This is directly analogous to the reported `StrategyBase` interface-consistency bug, where one sibling strategy (`StrategyCurveSCRVv4_1`) received a security fix to its pricing/index function while other `StrategyBase`-interfaced siblings kept the old, inconsistent logic.

### Finding Description
`AbstractExchangeActuator` centralizes `allowHarden()`, `addExact()`, and `subtractExact()` for the exchange actuator family: [1](#0-0) 

`ExchangeTransactionActuator.execute()` computes the swap output via the centralized, hardened `ExchangeCapsule.transaction(...)` call, passing `allowHarden()`: [2](#0-1) 

By contrast, `ExchangeInjectActuator.execute()` — which mutates the same pool balances for liquidity injection — still performs the ratio calculation manually with plain integer math instead of using the shared hardened processor: [3](#0-2) 

Similarly, `ExchangeWithdrawActuator.execute()` recomputes the ratio with yet another independent implementation (`BigInteger` in `execute()`, `BigDecimal` with a separate "precise enough" tolerance check in `doValidate()`), never invoking `ExchangeCapsule.transaction()`/`SafeExchangeProcessor`: [4](#0-3) [5](#0-4) 

The hardened path (`SafeExchangeProcessor`) implements a fundamentally different pricing curve (Bancor-relay power formula with `StrictMathWrapper.pow`) than the simple constant-product ratio (`x*y/x'`) used by Inject/Withdraw: [6](#0-5) 

Because Inject and Withdraw never consult `allowHarden()`/`SafeExchangeProcessor` for their core pricing math (only for `addExact`/`subtractExact` overflow checks inherited from `AbstractExchangeActuator`), the three actuators that share one `ExchangeCapsule` pool can compute divergent "another token" amounts for functionally equivalent operations once hardening is enabled — exactly the kind of interface/behavior drift the external report warns about ("keep the interface compliant … avoid wrecking business-logic using this interface with inconsistent asset index result type").

### Impact Explanation
An unprivileged account can broadcast `ExchangeInjectContract` and `ExchangeWithdrawContract` transactions (via `Wallet`/HTTP-gRPC APIs) that manipulate `firstTokenBalance`/`secondTokenBalance` using the legacy (non-hardened, lower-precision) ratio math, while other participants' `ExchangeTransactionContract` swaps are priced using the hardened Bancor-power curve. This discrepancy between the pricing model used for pool-state mutation (Inject/Withdraw) versus pool-state consumption (Transaction) can be exploited to extract value from the exchange pool or from other traders — a concrete theft-of-funds vector consistent with the "unbacked balance"/"theft of funds" acceptance criteria, since asset amounts credited/debited via `accountCapsule.addAssetAmountV2`/`reduceAssetAmountV2` and `ExchangeStore`/`ExchangeV2Store` state are computed inconsistently for what should be one unified AMM interface.

### Likelihood Explanation
Reachable by any signed transaction from an ordinary account with an existing `Exchange` id (created via `ExchangeCreateContract`); no special privilege, SR/witness role, or off-chain component is required — only enabling `allowHardenExchangeCalculation()` (a network parameter toggled by governance/committee, already referenced throughout the codebase and test suite), after which the divergence becomes actively exploitable by any user issuing Inject/Withdraw/Transaction contracts against the same exchange pair.

### Recommendation
Migrate `ExchangeInjectActuator` and `ExchangeWithdrawActuator` to compute their "another token" amounts through the same `ExchangeCapsule.transaction(...)`/`SafeExchangeProcessor` abstraction used by `ExchangeTransactionActuator`, gated by the same `allowHarden()` flag, so that all three actuators price against one consistent, audited formula for the same underlying pool.

### Proof of Concept
Not independently executed; based on static analysis of the divergent arithmetic paths cited above. A concrete PoC would require: (1) enabling `AllowHardenExchangeCalculation` via committee proposal, (2) creating an `Exchange` pair, (3) comparing swap outputs from `ExchangeInjectContract`/`ExchangeWithdrawContract` (legacy ratio math) against `ExchangeTransactionContract` (Bancor-power `SafeExchangeProcessor` math) for equivalent pool-state deltas, to demonstrate a measurable value discrepancy exploitable across repeated inject/withdraw/transaction cycles. This would need to be validated in a running node/testnet environment, which is outside the scope of this static review.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
