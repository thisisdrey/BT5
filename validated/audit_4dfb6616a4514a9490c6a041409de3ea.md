## #Vulnerability found for this question.

### Title
Unbounded per-filter result queue growth in JSON-RPC `eth_newFilter`/`eth_newBlockFilter` — (File: `framework/src/main/java/org/tron/core/services/jsonrpc/filters/LogFilterAndResult.java`)

### Summary
Any anonymous JSON-RPC client can call `eth_newFilter` (or `eth_newBlockFilter`) to register a log/block filter in `TronJsonRpcImpl`. Each filter's pending-results container (`LogFilterAndResult`/`BlockFilterAndResult`, both backed by an unbounded `LinkedBlockingQueue`) is filled by the block-application pipeline (`handleLogsFilter`/`handleBLockFilter`) with **no cap on the number of buffered elements**, unlike the analogous `RealtimeEventService.add()` path elsewhere in the codebase which explicitly checks `queue.size() >= maxEventSize` before adding. The only defense against unbounded growth is (a) a cap on the *number of filters* (`jsonRpcMaxLogFilterNum`, default 20000) and (b) a coarse 5-minute (`EXPIRE_SECONDS`) time-based expiry that is only evaluated lazily the next time a matching event is dispatched. This mirrors the quiche `PathEvent::ReusedSourceConnectionId` pattern: the *count* of "sessions" (filters) is bounded, but the *queue inside each session* is not, and the only mitigation is application-side consumption (`popAll()` via `eth_getFilterChanges`), exactly like quiche's `path_event_next()` mitigation.

### Finding Description
`eth_newFilter` creates a `LogFilterAndResult` with an internal `LinkedBlockingQueue` and stores it in `eventFilter2ResultFull`/`eventFilter2ResultSolidity`, gated only by a total-filter-count check: [1](#0-0) 

The queue itself has no size limit — `add`/`addAll` are unconditional: [2](#0-1) [3](#0-2) 

Every block/transaction processed by `Manager` feeds these queues without any per-filter backpressure: [4](#0-3) [5](#0-4) 

`FilterResult` only removes an entry lazily — by checking `isExpire()` inside `handleLogsFilter`/`handleBLockFilter` — and expiry only resets when the client actively polls (`getFilterResult` → `popAll()` → `updateExpireTime()`): [6](#0-5) [7](#0-6) 

By contrast, the codebase's own real-time event pipeline explicitly caps its queue and drops on overflow, showing the missing bound here is an inconsistency rather than an intentional design: [8](#0-7) 

A client can open up to `jsonRpcMaxLogFilterNum` (20000 by default, `framework/src/main/java/org/tron/common/parameter/CommonParameter.java:490`) wildcard filters and never call `eth_getFilterChanges`/`eth_getFilterLogs`. For the full 5-minute (`EXPIRE_SECONDS`) window before each filter is lazily evicted, every matching block hash / log element produced by chain activity (up to `netMaxTrxPerSecond` transactions/sec, `common/src/main/resources/reference.conf:335`) is appended to every live filter's queue with no per-filter cap. Because filter creation is cheap and unauthenticated, an attacker can keep re-registering filters as old ones expire, sustaining a large working set of oversized queues indefinitely.

### Impact Explanation
Sustained unbounded accumulation of `LogFilterElement`/block-hash entries across up to 20000 concurrent filters can drive heap memory usage to exhaustion, causing an OutOfMemoryError and crashing/halting the full node's JSON-RPC service (and potentially the whole JVM process, since it's a shared heap with the rest of the node). This matches the "node crash or halt" / "API the node can no longer serve" impact bar.

### Likelihood Explanation
The attack requires only unauthenticated HTTP JSON-RPC access (`eth_newFilter`) — no signed transaction, no special privilege, and no cost beyond normal API usage. Any anonymous client reachable over the JSON-RPC HTTP endpoint can trigger it, making likelihood high wherever `jsonrpc.httpFullNodeEnable` (or solidity/PBFT variants) is turned on.

### Recommendation
Add an explicit per-filter maximum queue size (mirroring `RealtimeEventService.maxEventSize`) in `FilterResult`/`LogFilterAndResult`/`BlockFilterAndResult`, dropping/evicting oldest entries or rejecting further inserts (with logging) once the cap is reached, instead of relying solely on the 5-minute lazy expiry and the total-filter-count cap.

### Proof of Concept
1. Enable JSON-RPC (`node.jsonrpc.httpFullNodeEnable = true`).
2. Repeatedly call `eth_newFilter` with an empty/wildcard `FilterRequest` (no address/topics) up to `jsonRpcMaxLogFilterNum` times, recording filter IDs.
3. Never call `eth_getFilterChanges`/`eth_getFilterLogs`/`eth_uninstallFilter` on these IDs.
4. Drive (or simply observe organic) transaction throughput on the network for the ~5-minute expiry window; each block's logs are appended via `handleLogsFilter`/`processLogFilterEntry` to every open filter's unbounded queue (`framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java:296-313`).
5. As filters approach expiry, immediately create replacement filters to keep the pool near the cap indefinitely, sustaining large-queue accumulation and growing heap usage until the node experiences memory pressure/OOM.

public abstract class FilterResult<T> {

  private long expireTimeStamp;

  @Getter
  protected BlockingQueue<T> result;

  public void updateExpireTime() {
    expireTimeStamp = System.currentTimeMillis() + TronJsonRpcImpl.EXPIRE_SECONDS * 1000;
  }

  public boolean isExpire() {
    return expireTimeStamp < System.currentTimeMillis();
  }

  public abstract void add(T t);

  public abstract List<T> popAll();
}
