### Title
Duplicate-signer weight double-counting in `ValidateMultiSign` precompile via ECDSA signature malleability - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompile is meant to require a threshold-weighted set of *distinct* signers before returning success, analogous in purpose to `bigclaim()`'s multi-signer requirement in the external report. Its duplicate-detection logic only rejects a signature if the exact same signature bytes were already used by the same recovered address, not if the same address produced a different (but still valid) signature over the same hash.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute()`, weights are accumulated for each signature in the caller-supplied array: [1](#0-0) 

For each signature, the code recovers the signer address, then only skips accumulation (`continue`) if the *identical byte sequence* (`sign`) was already recorded for that `recoveredAddr`. If the same address appears again with a **different** signature byte string, the loop does not skip it — it merely calls `MUtil.checkCPUTime()` (a CPU-time guard against repeated `ecrecover` calls) and falls through to add the weight again: [2](#0-1) 

Because ECDSA signatures are malleable — for a given `(r, s)` there is always an alternate valid signature `(r, n-s)` (with adjusted recovery id) that recovers to the exact same address for the same hash — a single private key holder can trivially produce two (or more) distinct valid signature byte arrays over the same message hash. Both would recover to the same address but differ as raw bytes, so the "already used same sign" check does not catch it, and the weight for that one signer's key is added multiple times toward `permission.getThreshold()`.

This mirrors the reported `bigclaim()` bug class exactly: the intent of requiring "several distinct signers" is undermined because the mechanism verifies "signatures", not "unique signers", and a single signer can defeat that by supplying multiple valid signature encodings of themselves.

By contrast, `TransactionCapsule.checkWeight()` — used for on-chain transaction signature/permission verification — deduplicates by recovered address (post fork `VERSION_4_7_1`), not by raw signature bytes, and explicitly throws `"has signed twice!"` if the same address appears twice: [3](#0-2) 

That code path is not vulnerable to this malleability issue. However, `ValidateMultiSign` (a TVM precompile reachable from any smart contract, hence from any unprivileged transaction broadcaster/contract deployer) uses the weaker byte-level dedup.

### Impact Explanation
`ValidateMultiSign` is a general-purpose on-chain multisig verification primitive exposed to any Solidity contract via the precompile address. Contracts that rely on it to gate privileged actions (e.g., a custom multisig wallet, an escrow release, or a token claim analogous to `bigclaim()`) under the assumption that reaching `permission.getThreshold()` requires that many distinct signers can be bypassed by a single key holder submitting two malleable variants of their own signature. This allows unauthorized execution of multisig-gated logic that should require multiple independent approvers — a concrete unauthorized-operation / fund-theft-enabling primitive for any contract built on top of this precompile.

### Likelihood Explanation
Exploitation requires only: (1) a permission/account with `Threshold > 1` verified through `ValidateMultiSign`, and (2) knowledge of one signer's valid signature, from which the attacker (who is that signer, or who obtained one valid signature) can algebraically derive a second valid, differently-encoded signature (`s' = n - s`, flip recovery id) without needing the private key beyond the one signature already available. This is a well-known, easily computed ECDSA property and requires no privileged access, no waiting, and no race condition — it's deterministic and always available to any caller of the precompile who controls (or has) one signer's signature.

### Recommendation
In `ValidateMultiSign.execute()`, deduplicate strictly by `recoveredAddr` (skip/reject as soon as an address repeats), not by the concatenation of `recoveredAddr + sign` bytes — mirroring the fix already used in `TransactionCapsule.checkWeight()`. The same audit should be applied to `BatchValidateSign` and any other precompile/actuator that accumulates weight or counts signers from raw signature arrays, to ensure they reject reused addresses regardless of malleable-signature byte encoding.

### Proof of Concept
1. Deploy/observe an account whose Active permission requires `threshold = 2` with two distinct keys `key1`, `key2` (each weight 1), as in the existing test setup `ValidateMultiSignContractTest.testDifferentCase`: [4](#0-3) 
2. Attacker controls only `key1`. Attacker computes `sigA = key1.sign(toSign)` and then derives a malleable variant `sigB` by transforming `s -> n - s` and flipping the recovery id, producing a different byte array that still recovers to `key1`'s address for the same `toSign` hash.
3. Attacker calls the `ValidateMultiSign` precompile with `signatures = [sigA, sigB]`.
4. In `execute()`, the first iteration adds `key1`'s weight (1). The second iteration recovers the same address; `executedSignList` contains the address but not the exact `sigB` bytes, so the `continue` is skipped, `checkCPUTime()` runs, and `key1`'s weight is added a second time (weight now 2), satisfying `threshold = 2` with a single signer — returning `DataWord.ONE()` success despite only one actual signer having participated.
