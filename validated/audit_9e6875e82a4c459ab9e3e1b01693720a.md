## Finding

### Title
Missing zero-address check in `TransferActuator`/`TransferAssetActuator` allows accidental permanent loss of TRX/TRC10 assets - (File: `actuator/src/main/java/org/tron/core/actuator/TransferActuator.java`, `actuator/src/main/java/org/tron/core/actuator/TransferAssetActuator.java`)

### Summary
`TransferActuator.validate()` and `TransferAssetActuator.validate()` only check that `toAddress` passes `DecodeUtil.addressValid()`, which merely verifies the address length and the network prefix byte, and that `toAddress != ownerAddress`. Neither actuator rejects a syntactically valid but unspendable "null"/zero address (`0x41` followed by 20 zero bytes). A transaction sender who mistakenly (or via a buggy wallet/integration that zero-initializes the recipient buffer) submits such a `toAddress` will have the TRX or TRC10 tokens permanently and irrecoverably transferred to that address, mirroring the reported `CreditManager` bug class where a missing `to != address(0)` check leads to loss of assets.

### Finding Description
`DecodeUtil.addressValid` only validates structural correctness: [1](#0-0) 

Both `TransferActuator.validate()` and `TransferAssetActuator.validate()` use this same check for `toAddress` and add no further semantic validation (no zero-address / burn-address check): [2](#0-1) [3](#0-2) 

`execute()` then unconditionally creates the destination account (if absent) and credits it with the transferred balance/asset, with no special handling for the zero address: [4](#0-3) [5](#0-4) 

Because a TRON address with all-zero payload bytes (`0x41` + 20 zero bytes) is extraordinarily unlikely to correspond to any derivable ECDSA public key/private key pair, sending funds to it is effectively a burn with no recovery path — functionally identical to sending to `address(0)` in the referenced EVM report.

### Impact Explanation
Any unprivileged transaction broadcaster who signs and submits a `TransferContract` or `TransferAssetContract` with a zero-valued `to_address` (e.g., due to a bug in wallet software, an SDK that fails to populate the recipient field, or a copy-paste/parsing mistake that zeroes out the address bytes while keeping the correct length and prefix) will have their TRX or TRC10 tokens irreversibly locked/lost. This is a permanent loss-of-funds condition reachable directly from a single signed transaction, without any privileged role.

### Likelihood Explanation
Likelihood is limited to accidental misuse (buggy client, malformed request, or user/integration error) rather than an attacker directly stealing another user's funds — the same characterization given in the original report, where the recommendation was purely defensive (add a sanity check). Given java-tron's broad ecosystem of third-party wallets/SDKs that construct these contracts, the probability of an all-zero address slipping through due to uninitialized buffers or serialization bugs is non-trivial.

### Recommendation
Add an explicit check in `TransferActuator.validate()` and `TransferAssetActuator.validate()` (and any other actuator that accepts a caller-supplied recipient address, e.g. resource-delegation actuators) rejecting the reserved null/burn address (`0x41` followed by 20 zero bytes), similar to the existing self-transfer check (`Arrays.equals(toAddress, ownerAddress)`).

### Proof of Concept
1. Construct a `TransferContract` (or `TransferAssetContract`) with `owner_address` set to a funded account and `to_address` set to `0x41` followed by 20 zero bytes (21 bytes total, valid length/prefix).
2. Sign and broadcast the transaction.
3. `TransferActuator.validate()` passes: `DecodeUtil.addressValid(toAddress)` returns `true` (correct length/prefix), and `toAddress != ownerAddress`.
4. `TransferActuator.execute()` creates the zero-address account if it doesn't exist and credits it with the transferred amount — funds are now controlled by an address with no discoverable private key, permanently lost.

  public static boolean addressValid(byte[] address) {
    if (ArrayUtils.isEmpty(address)) {
      logger.warn("Warning: Address is empty !!");
      return false;
    }
    if (address.length != ADDRESS_SIZE / 2) {
      logger.warn(
          "Warning: Address length need " + ADDRESS_SIZE + " but " + address.length
              + " !!");
      return false;
    }

    if (address[0] != addressPreFixByte) {
      logger.warn("Warning: Address need prefix with " + addressPreFixByte + " but "
          + address[0] + " !!");
      return false;
    }
    return true;
