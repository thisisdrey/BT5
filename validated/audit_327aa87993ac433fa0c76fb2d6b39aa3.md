### Title
Griefing via `MAX_TOKENS_PER_USER` — attacker fills victim's per-account token list with dust deposits, DoS-ing the victim's `deposit()` and `issue()` — ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` enforce a combined cap of `MAX_TOKENS_PER_USER = 30` per account. Because `DepositToken.deposit(amount_, onBehalfOf_)` and `DepositToken.transfer(to_, amount_)` add the token to the *recipient's* list without the recipient's consent, an unprivileged attacker can permissionlessly stuff a victim's list with dust positions until the cap is hit. After that, every new-token `deposit`, `transfer`, `seize` or `DebtToken.issue` to the victim reverts with `UserReachedMaxTokens`, causing a repeatable denial of service — the analog of the MySQL "hang/crash (complete DOS)" availability bug class.

### Finding Description
`Pool.sol` caps per-account tracked tokens: [1](#0-0) [2](#0-1) 

The cap is checked in `addToDepositTokensOfAccount(account_)` and `addToDebtTokensOfAccount(account_)`, which are called by `DepositToken._mint` / `_transfer` whenever the recipient's balance goes from `0` to `>0`: [3](#0-2) [4](#0-3) 

The recipient has no opt-in: `deposit(amount_, onBehalfOf_)` mints to an arbitrary `onBehalfOf_` (any non-zero address), and `transfer` pushes to any `to_`. So the attacker, for each of the pool's deposit tokens, does `deposit(1 wei, victim)` (or `transfer(victim, dust)`) to consume victim slots. `DebtToken.issue`/`mint` add the debt token to `debtTokensOfAccount`, and that function reverts once `debt + deposit tokens == 30`. A victim with no debt whose unlocked balance is 0 (fully utilized collateral) cannot remove the dust entries via `transfer`/`withdraw` (`_revertIfLocked` blocks, `unlockedBalanceOf` returns based on `debtPositionOf`), so the DoS persists as long as their position stays locked.

### Impact Explanation
- Liveness/availability impact matching the CVE class: repeatable reversion of the victim's `DepositToken.deposit` (for any token not already in their list), `DebtToken.issue`/`SmartFarmingManager.leverage` (for any new synthetic), and `Pool.swap` mint paths that add tokens.
- For a victim with `unlockedBalanceOf == 0`, the attacker-supplied dust tokens are also locked, so the victim cannot clear the slots — temporary freezing of protocol functionality (and of the dust "funds" credited to them) until market conditions change or debt is repaid.
- Cost to attacker is bounded (dust amounts of each listed underlying plus deposit fee), no privileged role required.

### Likelihood Explanation
Requires the pool to list enough deposit/debt tokens for `existing + N >= 30`, and the attacker to acquire dust of each underlying. No oracle manipulation, flash loan, or privileged actor needed; front-running a victim's legitimate `deposit`/`issue` transaction can also selectively block a specific intended action. Impact is temporary (recoverable once the victim has unlocked balance or positions close) — consistent with a medium-severity DoS.

### Recommendation
- Make the per-account list opt-in for recipients: only add to `depositTokensOfAccount` when `recipient == _msgSender()` or when `recipient` has approved the token (e.g., an allowlist/claim pattern), or add a `maxTokens` per-token-type threshold so dust (`balance < minDeposit`) doesn't register.
- Alternatively, allow a permissionless `removeDustTokenOfAccount(account, token)` when balance is below a minimum, so victims can self-clear slots.

### Proof of Concept
Hardhat (mainnet/Base fork), sketch:

```ts
// setup: pool with deposit tokens [msdA, msdB, ...]; victim holds 0 of them
const victim = bob.address;

// Attacker deposits 1 wei of each underlying on behalf of the victim
for (const msd of allDepositTokens) {
  const underlying = await ethers.getContractAt('IERC20', await msd.underlying());
  await underlying.connect(attacker).approve(msd.address, 1);
  await msd.connect(attacker).deposit(1, victim); // adds token to victim's list
}

// Optionally also push debt tokens via issue(attacker collateral) to reach 30
// Now victim's list is at MAX_TOKENS_PER_USER (30)
expect(await pool.getDepositTokensOfAccount(victim)).length.plus(
  (await pool.getDebtTokensOfAccount(victim)).length
).to.eq(30);

// Victim's own new deposit reverts
await msdNew.connect(victim).deposit(amount, victim); // inside _mint -> addToDepositTokensOfAccount
// => reverts with UserReachedMaxTokens

// Victim issuing a new synthetic reverts too
await debtToken.connect(victim).issue(parseEther('1'), victim);
// => reverts with UserReachedMaxTokens
```

For a fully-utilized victim (`unlockedBalanceOf(victim) == 0`), `msd.connect(victim).transfer(attacker, 1)` and `withdraw` revert with `NotEnoughFreeBalance`, so the victim cannot evict the dust entries — the block persists until their debt position changes.
