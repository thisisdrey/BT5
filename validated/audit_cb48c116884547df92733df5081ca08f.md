Confirmed: `intValueSafe()` clamps to `Integer.MAX_VALUE` when a `DataWord` is out of `int` range, and `intValue()` throws only when data doesn't fit `int` after shifting (actually it never throws — the javadoc is stale; it silently truncates via bit-shifting). This means offsets/sizes reaching `Memory.write()` can legitimately be `Integer.MAX_VALUE` (via `intValueSafe()`), and the vulnerable check is in `Memory.write()`'s limited-write branch.

### Title
Integer overflow in `Memory.write()` limited-write bounds check bypasses `RETURNDATACOPY`/CALL output clamping - (File: `actuator/src/main/java/org/tron/core/vm/program/Memory.java`)

### Summary
`Memory.write(int address, byte[] data, int dataSize, boolean limited)` computes the clamped copy length for "limited" writes (used to write CALL/DELEGATECALL/STATICCALL/precompile return data into caller memory without growing memory) as `address + dataSize > softSize`. Both operands are plain `int`, so a large `address` combined with a large `dataSize` can wrap around `Integer` range and produce a negative or small sum that is `<= softSize`, defeating the clamp exactly like the `hid_bpf_get_data()` case where `rdwr_buf_size + offset` wrapped below `ctx->allocated_size`.

### Finding Description
`Memory.write()` at [1](#0-0)  is called in limited mode from `Program.memorySaveLimited()` [2](#0-1) , which in turn is invoked after every internal CALL/DELEGATECALL/STATICCALL/CALLTOKEN completes, to copy the callee's return data into the caller-specified `outDataOffs`/`outDataSize` region without growing the caller's memory: [3](#0-2) 

`address` and `size` originate from `msg.getOutDataOffs().intValue()` / `msg.getOutDataSize().intValue()` — both attacker-controlled 256-bit stack words truncated via `DataWord.intValue()`, which does **not** clamp or throw; it performs `(intVal << 8) + (byte & 0xff)` over all 32 bytes, silently wrapping to an arbitrary (including negative) `int`: [4](#0-3) 

Inside `write()`, the bounds check for the limited path is:
```java
toCapture = (address + dataSize > softSize) ? softSize - address : dataSize;
```
Both `address` and `dataSize` are plain 32-bit `int`s (not cast to `long`), so their sum can silently wrap (Java `int` overflow), producing a value that is `<=` `softSize` even though the real (mathematically correct) range end vastly exceeds `softSize`. This mirrors the CVE-2026-72352 root cause precisely: an unsigned/未promoted addition of caller-controlled offset and size wraps below the allocated bound, and the range-check branch is bypassed. Contrast this with the same file's own `extend()`, which correctly uses `addExact()`(overflow-checked) for the identical offset+size computation: [5](#0-4) , showing the `write()` path was not given the same overflow-safe treatment.

When the wrap occurs, `toCapture` is set to `dataSize` (the unclamped, attacker-chosen full size) instead of the safe `softSize - address` clamp, and the subsequent capture loop calls `captureMax()` which walks memory chunks and can call `System.arraycopy` for a length far beyond the actually allocated backing chunks, since `extend()` (which grows chunks) is deliberately skipped for `limited=true` writes: [6](#0-5) .

### Impact Explanation
`captureMax()`/`chunks.get(chunkIndex)` will attempt to index chunks that were never allocated for the wrapped huge `toCapture`, throwing `IndexOutOfBoundsException` (uncaught in this internal-call return path) instead of the expected clamp-and-copy — an unprivileged contract deployer/caller can craft a CALL with a manipulated `outDataOffs`/`outDataSize` pair whose 32-bit truncated `int` sum overflows, causing the executing node to throw an unhandled runtime exception during VM execution of a broadcast transaction. This can crash/halt block processing on validating full nodes (denial of service), and depending on how deep in the call stack `write()` is invoked (from `callToAddress`), it could also corrupt sibling memory chunks by writing partial garbage into wrong offsets before the exception if `captureMax` iterates multiple times before failing.

### Likelihood Explanation
Reachable directly from any address executing a smart contract that issues an internal CALL (or any of the CALL family) with attacker-chosen stack values for `outDataOffs`/`outDataSize` — no special privileges required, only a deployed contract and a single transaction. The only requirement is picking 256-bit stack values whose low 32 bits after `intValue()` truncation wrap the `address + dataSize` sum in `Memory.write()`.

### Recommendation
Change the limited-write bounds check in `Memory.write()` to use overflow-safe arithmetic (e.g. `long` arithmetic or `Maths.addExact`) analogous to `extend()`:
```java
long end = (long) address + (long) dataSize;
toCapture = (end > softSize) ? Math.max(softSize - address, 0) : dataSize;
```
and additionally clamp/validate `address >= 0` before use, since `intValue()` can also yield a negative int for large `DataWord`s.

### Proof of Concept
1. Deploy a contract A that performs an internal `CALL` to contract B, where B's constructor/fallback simply returns some data (`callResult.getHReturn()` non-null).
2. In A's bytecode, push `outDataOffs` and `outDataSize` (256-bit stack words) such that, after `DataWord.intValue()` 32-bit truncation, `address + dataSize` (as 32-bit `int` addition) overflows to a value `<= softSize` (the caller's current soft memory size), e.g. `address = 0x7FFFFFF0`, `dataSize = 0x30` → `address + dataSize` wraps to a small/negative int while the "logical" unwrapped value exceeds any real memory size.
3. Execute the CALL; `Program.callToAddress()` reaches `memorySaveLimited(offset, buffer, size)` → `Memory.write(offset, buffer, size, true)`.
4. Because `address + dataSize` wraps, `toCapture` becomes `dataSize` (or another out-of-clamp value) instead of the safe negative/zero clamp, and `captureMax()` attempts `chunks.get(chunkIndex)` beyond the allocated `chunks` list size, throwing an uncaught `IndexOutOfBoundsException` during transaction execution — crashing/halting VM execution for that transaction and potentially the node's block-application path in `Manager`.
