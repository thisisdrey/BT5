### Title
Out-of-bounds heap read when parsing ZIP64 extra fields in a crafted jar's Central Directory - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in Bazel's native `ijar`/`singlejar` ZIP parser reads Central Directory Header (CDH) fields and the ZIP64 "extra field" without validating that the declared lengths stay inside the memory-mapped input file, allowing a maliciously crafted `.jar`/`.zip` file to trigger an out-of-bounds read, analogous to the radare2 `nds32-dis.h` OOB read that resulted from trusting attacker-controlled length/size fields during format parsing.

### Finding Description
`ProcessCentralDirEntry` reads the fixed CDH fields and then the variable-length "extra fields" region directly from the mmap'd input buffer with **no call to `EnsureRemaining`** (the bounds check used elsewhere, e.g. in `ProcessLocalFileEntry` at [1](#0-0) ). The comment at the top of the function even asserts the region is "always followed by another data structure that has a signature, so parsing it this way is safe" [2](#0-1)  — an assumption that does not protect against a crafted `extra_field_length` or ZIP64 `data_size`.

Inside the extra-field loop, the code reads a 2-byte tag and 2-byte `data_size`, then — if the tag equals `ZIP64_EXTRA_FIELD_TAG` — reads up to three 8-byte little-endian values (`get_u8le`) from `extra` without checking that `extra + 24` is still within `extra_p` (the declared extra-field end) or within the mapped file's total length: [3](#0-2) 

A hostile jar/zip can declare a ZIP64 extra field with `data_size` smaller than the 8/16/24 bytes actually consumed, or place the tag near the very end of a small mapped file, causing `get_u8le` to read past the end of the mmap'd region. The `*compressed_size`, `*uncompressed_size`, and `*offset` output values derived from this out-of-bounds memory then flow into `ProcessNext` (`p = zipdata_in_ + in_offset_ + offset`) and `CalculateOutputLength`, propagating uninitialized/adjacent process memory into subsequent size/offset computations and copy operations performed on the archive by the `ijar` and `singlejar` tools.

### Impact Explanation
`ijar`/`singlejar` process JAR/ZIP files that are ordinary build inputs — e.g. precompiled `.jar` dependencies fetched via `http_jar`/`http_archive` (checksum only pins the exact bytes, it does not validate ZIP structural invariants) or JARs produced while building an untrusted branch. A crafted file with an inconsistent ZIP64 extra field can cause the native parser to read past the mmap'd file boundary, potentially crashing the tool or leaking adjacent process memory bytes into size/offset fields that subsequently control further reads and data copies performed by the archive-merging tool. This mirrors the CVE-2023-46570 bug class: an out-of-bounds read rooted in trusting attacker-supplied length fields during binary format parsing without bounds validation.

### Likelihood Explanation
Any build that consumes a `.jar`/`.zip` dependency (via `http_jar`, `http_archive`, or a source checkout built by `ijar`/`singlejar`) is exposed once the file is fetched and the sha256/integrity check on the raw bytes passes — the checksum only confirms byte-identity with what was pinned, not internal ZIP structural consistency, so a first-time or attacker-controlled pin does not stop a structurally malicious file.

### Recommendation
Add explicit bounds validation in `ProcessCentralDirEntry` before reading the CDH and its extra fields: verify `extra_field_length`/`data_size` never causes `extra_p`/`extra` reads to exceed the mapped input file's length (mirroring the `EnsureRemaining` check already used in `ProcessLocalFileEntry`), and reject the ZIP64 extra field parse (or truncate) when the declared `data_size` is smaller than the 8/16/24 bytes the ZIP64 branch expects to consume.

### Proof of Concept
Construct a minimal ZIP whose sole Central Directory Header declares `extra_field_length = 4` with tag `0x0001` (ZIP64) and `data_size = 0`, positioned so the CDH itself sits within the last few bytes of the mmap'd file (e.g. no End-Of-Central-Directory record padding after it). Feed this file to the `ijar` binary (`bazel-bin/third_party/ijar/ijar in.jar out.jar`); `ProcessCentralDirEntry`'s ZIP64 branch at `third_party/ijar/zip.cc:531-540` will call `get_u8le(extra)` reading 8–24 bytes past `extra_p`/the end of the mapped region, which can be observed with ASan (`-fsanitize=address`) as a heap-buffer-overflow READ, matching the missing-bounds-check root cause of CVE-2023-46570.
