## Finding [1](#0-0) 

### Title
Curator can indefinitely extend `update_due` via `extend_bounty_expiry` at zero cost, blocking permissionless slashing/unassignment and locking treasury-escrowed bounty funds - ([File: substrate/frame/bounties/src/lib.rs])

### Summary
The external report describes a borrower who is allowed to "repay late" repeatedly with no fee or penalty, and where the lender's forced-liquidation path always re-checks for a late repayment before liquidating collateral — giving the borrower unlimited free extensions. The local analog is `pallet-bounties::extend_bounty_expiry`, which lets a curator push the `update_due` deadline of an `Active` bounty forward by `BountyUpdatePeriod` an unlimited number of times, at no cost and with no work requirement, which blocks the permissionless slashing path in `unassign_curator` indefinitely.

### Finding Description
When a bounty becomes `Active`, it carries an `update_due` deadline: [2](#0-1) . A curator can renew this deadline via `extend_bounty_expiry`, which any signed curator can call repeatedly, with no fee, no deposit slash, and no evidence of actual progress (the `remark` parameter is unused): [3](#0-2) 

The only permissionless recourse against an inactive/malicious curator is `unassign_curator`, but it explicitly defers to `update_due`: a non-curator caller can only trigger the slash path if `*update_due < block_number` — otherwise the call fails with `Premature`: [4](#0-3) 

This is the exact structural analog to the report's `forceLiquidateExpiredLoan()`: the "force liquidate" call (`unassign_curator` called by a non-curator) always re-checks whether the "borrower" (curator) can still make a fee-free "late repayment" (`extend_bounty_expiry`) and, as long as that call is made before the deadline, the forced-recovery path is denied. There is no cap on the number of extensions and no increasing cost — a curator can call `extend_bounty_expiry` every `BountyUpdatePeriod` blocks forever, at negligible transaction fee, to retain exclusive control of the bounty and its already-escrowed treasury value in `Self::bounty_account_id(bounty_id)` without ever completing the deliverable.

This was made worse by [5](#0-4)  which changed the `update_due` calculation to `saturating_add`, explicitly enabling bounties to "remain active indefinitely without requiring `extend_bounty_expiry`" when `BountyUpdatePeriod` is large — but even under a normal, small `BountyUpdatePeriod`, nothing stops a curator from calling `extend_bounty_expiry` on every period forever, achieving the same indefinite-hold outcome through repeated free calls instead of a large config value.

### Impact Explanation
Treasury funds for the bounty are already moved out of the pot into the bounty-specific account once the bounty becomes active (via `spend_funds`), so the value is "escrowed" but undelivered. A curator can hold this escrowed value hostage indefinitely, at only the cost of ordinary transaction fees and the (recoverable) curator deposit, with zero penalty for "being late" (never completing the work). The only remaining remedy is `close_bounty` or the `RejectOrigin` path via `unassign_curator`, both of which require the privileged `RejectOrigin` (council/governance) to intervene — meaning a purely economic, permissionless attacker forces manual governance action to unwind every instance of this behavior, rather than the protocol's own permissionless slashing/curator-rotation mechanism (`unassign_curator` from any signer) ever being effective. This degrades the intended self-correcting incentive design of the bounty curator system and can be used to grief specific high-value bounties indefinitely.

### Likelihood Explanation
Any account that has been accepted as curator (a normal, unprivileged role requiring only a modest curator deposit) can trigger this at will, at every `BountyUpdatePeriod` interval, with a single cheap signed extrinsic call requiring no special permissions, no malicious peer/validator/relayer, and no governance/admin abuse as the root cause. This makes the likelihood high for any curator wishing to stall a bounty.

### Recommendation
Introduce a cost or bound to `extend_bounty_expiry`, mirroring the report's recommendation for the loan protocol:
- Cap the total number of extensions per bounty (or a maximum aggregate delay), and/or
- Apply an increasing penalty (partial curator-deposit slash or fee) on each extension beyond the first, and/or
- Require concrete proof-of-progress (e.g., a mandatory non-empty `remark`/checkpoint plus council acknowledgment) rather than a no-op parameter, so that permissionless `unassign_curator` remains an effective, timely check against unproductive curators instead of always being pre-empted by a free "late renewal."

### Proof of Concept
1. Council calls `propose_bounty` / `approve_bounty` / `propose_curator`, curator calls `accept_curator` — bounty becomes `Active { curator, update_due }` and its value is transferred to the bounty account, per `substrate/frame/bounties/src/tests.rs::extend_expiry` setup.
2. Just before `update_due`, curator calls `extend_bounty_expiry(origin=curator, bounty_id, vec![])`. `update_due` is pushed forward by `BountyUpdatePeriod`; test `extend_expiry` (lines 1053-1119) shows this succeeding with no state cost beyond the call itself, and being repeatable ("still the same" after being called with no elapsed time, confirming free re-issuance).
3. Any other signer attempts `unassign_curator` to reclaim/slash the inactive curator; it fails with `Error::Premature` because `update_due` is still in the future (as demonstrated by the `Premature` assertions at lines 1026-1029 and 1110-1113 of the same test file).
4. Curator repeats step 2 forever, at negligible per-call cost, indefinitely retaining the bounty and its escrowed funds without delivering work, and permissionless recovery via `unassign_curator` never becomes available — only privileged `RejectOrigin` intervention (`close_bounty` / `unassign_curator` with `None` sender) can end the stall.

		/// Extend the expiry time of an active bounty.
		///
		/// The dispatch origin for this call must be the curator of this bounty.
		///
		/// - `bounty_id`: Bounty ID to extend.
		/// - `remark`: additional information.
		///
		/// ## Complexity
		/// - O(1).
		#[pallet::call_index(8)]
		#[pallet::weight(<T as Config<I>>::WeightInfo::extend_bounty_expiry())]
		pub fn extend_bounty_expiry(
			origin: OriginFor<T>,
			#[pallet::compact] bounty_id: BountyIndex,
			_remark: Vec<u8>,
		) -> DispatchResult {
			let signer = ensure_signed(origin)?;

			Bounties::<T, I>::try_mutate_exists(bounty_id, |maybe_bounty| -> DispatchResult {
				let bounty = maybe_bounty.as_mut().ok_or(Error::<T, I>::InvalidIndex)?;

				match bounty.status {
					BountyStatus::Active { ref curator, ref mut update_due } => {
						ensure!(*curator == signer, Error::<T, I>::RequireCurator);
						*update_due = Self::treasury_block_number()
							.saturating_add(T::BountyUpdatePeriod::get())
							.max(*update_due);
					},
					_ => return Err(Error::<T, I>::UnexpectedStatus.into()),
				}

				Ok(())
			})?;

			Self::deposit_event(Event::<T, I>::BountyExtended { index: bounty_id });
			Ok(())
		}
