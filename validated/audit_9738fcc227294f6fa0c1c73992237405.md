## Analysis

The reported bug class is a check‑then‑act state race: a limit/guard is evaluated, an operation proceeds, and only *afterward* is the counter that enforces the limit actually updated — letting concurrent invocations all pass the same stale check and blow past the intended cap.

The closest reachable analog in Agave is in the QUIC streamer's per‑connection stream throttling (`SwQos`, the QoS controller wired into the production TPU/TPU‑forward QUIC servers).

### Root cause

`ConnectionTable::try_add_connection` deliberately shares a single `ConnectionStreamCounter` across **all connections opened by the same peer key** (IP/pubkey), reusing the first connection's counter instead of creating a new one per connection: [1](#0-0) 

Each accepted connection is handled by its own independently-scheduled tokio task (`tasks.spawn(handle_connection(...))`), and within `handle_connection`, throttling is checked via `qos.on_new_stream()` *before* the stream count is incremented by the separate `qos.on_stream_accepted()` call: [2](#0-1) 

`SwQos::on_new_stream` calls `throttle_stream`, and only the later, distinct `on_stream_accepted` call performs the atomic increment: [3](#0-2) 

`throttle_stream` itself only *reads* the shared counter to decide whether to sleep — it never reserves/increments a slot as part of the check: [4](#0-3) 

Because the check (`stream_count.load`) and the eventual write (`stream_count.fetch_add` in `on_stream_accepted`) are two separate, non-atomic steps executed on different async tasks, a peer that opens multiple concurrent connections (up to `max_connections_per_peer`, i.e., up to 16 for a staked peer per `DEFAULT_MAX_QUIC_CONNECTIONS_PER_STAKED_PEER`) can have all of those connection tasks read the same pre-increment counter value simultaneously and all pass the throttle check in the same window, before any of them registers its increment. This is structurally the same "check happens, real state update happens later, so concurrent calls each see the stale check" flaw as the reported reentrancy bug — except here the "reentrancy" is achieved via legitimately-permitted concurrent connections from a single unstaked/staked peer rather than a single call stack.

### Title
Stream-throttle bypass via shared `ConnectionStreamCounter` race across concurrent connections from the same peer - (File: streamer/src/nonblocking/stream_throttle.rs)

### Summary
`SwQos` shares one `ConnectionStreamCounter` across every connection opened by the same peer key, but the throttle check in `throttle_stream()` and the counter increment in `on_stream_accepted()` are performed in separate steps on independently scheduled per-connection tasks. A peer holding multiple concurrent connections (allowed up to `max_connections_per_peer`) can race these checks so that several connections all read the stale counter value and pass the throttle simultaneously.

### Finding Description
`ConnectionTable::try_add_connection` reuses the first connection's `stream_counter` for every subsequent connection from the same `ConnectionTableKey` (IP or pubkey) [1](#0-0) . Each connection runs in its own spawned task (`handle_connection`), and within the per-stream loop, the throttle decision (`qos.on_new_stream(&context).await`) happens strictly before the counter is incremented (`qos.on_stream_accepted(&context)`) [2](#0-1) . `throttle_stream` only loads the shared `AtomicU64` counter to decide whether to sleep the current task; it does not reserve a slot atomically [4](#0-3) . The actual `fetch_add` occurs later in `on_stream_accepted` [5](#0-4) . When N concurrent connections from the same peer key each hit their per-stream loop iteration at roughly the same time, all N tasks can observe the same (stale, not-yet-incremented) `stream_count` value, and all pass the `>= max_streams_per_throttling_interval` check before any of them applies its increment, effectively multiplying the intended per-interval stream budget by the number of concurrently open connections from that peer.

### Impact Explanation
This allows an unprivileged client to exceed the intended stream-rate limit (`max_streams_per_ms`/EMA-derived budget) for its peer key by a factor bounded by `max_connections_per_unstaked_peer`/`max_connections_per_staked_peer` (default 8/16, configurable up to whatever value an operator sets, e.g. via `tpu_max_connections_per_staked_peer`/`tpu_max_connections_per_unstaked_peer`) [6](#0-5) . This is a QoS-evasion condition: the stream-admission control that is meant to bound per-peer packet ingestion rate (and thus CPU/allocation work in sigverify/banking stage) can be partially bypassed by opening many connections and racing their first stream acceptance, increasing the validator's exposure to per-peer resource consumption above configured limits.

### Likelihood Explanation
Reachable by any unprivileged network peer (staked or unstaked) that can open multiple QUIC connections to the validator's TPU port — no special privileges are required, only opening several concurrent connections and sending a first uni-stream on each roughly simultaneously. The race window is small (a single async check-then-later-increment gap) but is deterministically reproducible by tuning the number of simultaneous connections opened, since the shared counter and the two-step check/increment are unconditional in the code path.

### Recommendation
Make the throttle check-and-reserve atomic: replace the "load then later fetch_add" pattern with a single atomic compare-and-swap/fetch_add-then-check operation performed inside `on_new_stream`/`throttle_stream` itself (i.e., increment first, then decide to throttle/rollback), so concurrent tasks sharing the same `ConnectionStreamCounter` cannot all observe the same pre-increment value.

### Proof of Concept
1. Configure/observe default `SwQosConfig` (`max_connections_per_staked_peer` = 16, or unstaked = 8).
2. As a single peer (one IP/pubkey), open `max_connections_per_peer` concurrent QUIC connections to the validator's TPU quic endpoint.
3. On each connection, simultaneously open a first uni-stream and send data, triggering each connection's `handle_connection` task to call `qos.on_new_stream()` → `throttle_stream()` at nearly the same instant.
4. Because all connections share one `ConnectionStreamCounter` (per `try_add_connection`'s reuse logic) and the counter is only incremented after the throttle check returns, all N tasks read the same stale `stream_count` and none see the threshold reached, so all N streams pass through without throttling in the same interval — exceeding the configured `max_streams_per_throttling_interval` by up to N-1 extra streams per throttling window.

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
