### Title
Unbounded Recursion Depth in Reference-Tree Walk via Deeply Nested Ref Names Causes Gitaly DoS - (File: internal/gitaly/storage/wal/reftree/tree.go)

### Summary
The reported ElGamal bug class is "no bound on recursive input processing, causing stack overflow/panic." The Gitaly analog is in the reference-tree (`reftree`) package used by the WAL transaction manager to compute the filesystem operations of a reference transaction. The tree is walked with an unbounded, depth-first recursive function whose recursion depth is driven directly by the number of `/`-separated components in ref names supplied by an ordinary user's push. No maximum depth (or ref-name length/segment-count) check exists anywhere in this code path, unlike the analogous and correctly-bounded `altObjectDirs` alternates-resolution routine which enforces `maxAlternatesDepth = 5` [1](#0-0) .

### Finding Description
`Node.walk` in `internal/gitaly/storage/wal/reftree/tree.go` recurses once per directory level of the reference tree with no depth limit: [2](#0-1) 

This tree is built and walked from `ReferenceRecorder.RecordReferenceUpdates`, which is invoked "after each committed reference transaction" to determine the filesystem operations Git performed [3](#0-2) . The `creations`/`deletions` trees are populated straight from `git.ReferenceUpdates` — the set of ref names being created, updated, or deleted in the transaction — via `tree.InsertReference(reference.String())`, and are then walked with `WalkPreOrder`/`WalkPostOrder`: [4](#0-3) [5](#0-4) 

`Node.InsertReference` only checks that the reference starts with `refs/` — it places no limit on the number of `/`-delimited path segments (i.e., tree depth) that follow: [6](#0-5) 

Because ref names are attacker-controlled input arriving through an ordinary `git push` (creating a new branch/tag ref), a client can create a ref such as `refs/heads/a/a/a/.../a` with an extremely large number of path segments. When the transaction is recorded, `Node.walk` recurses once per segment with no bound, unlike the structurally similar `altObjectDirs` alternates-directory resolver, which explicitly caps recursion at `maxAlternatesDepth = 5` [1](#0-0) .

### Impact Explanation
Deep, unbounded recursion in Go can exhaust the goroutine stack and trigger a fatal runtime stack-overflow error. This is not caught by `recover()`/panic handlers such as `panichandler.UnaryPanicHandler`/`StreamPanicHandler` [7](#0-6) , because Go stack-overflow errors are fatal process-level errors, not recoverable panics. This means a crafted push from any client with write access could crash the entire `gitaly` process handling the reference transaction, denying service to all repositories on that node — a resource-limit/DoS issue in the RPC handling of reference transactions.

### Likelihood Explanation
The path is reachable purely from an ordinary user's `git push` creating a ref with a very deep hierarchy of slash-separated path components; no privileged access, malicious peer, or special configuration is needed. Git itself does not strictly cap the number of `/`-segments in a ref name (only total ref-name length and individual component rules via `git check-ref-format`), and no analogous limit exists in this Gitaly code path, making the precondition realistically attacker-reachable during any write transaction (`ReferenceUpdates`) processed by the WAL transaction manager (`internal/gitaly/storage/storagemgr/partition/transaction_manager_housekeeping.go` and `ReferenceRecorder`).

### Recommendation
Add an explicit maximum recursion/segment-depth check (and/or an overall ref-name length cap) in `reftree.Node.InsertReference`/`InsertNode` or in `Node.walk`, analogous to the `maxAlternatesDepth` guard used in `internal/git/dirs.go`, rejecting or truncating reference-transaction paths that exceed a safe depth (e.g., matching Git's own practical ref path-depth limits) before they are inserted or walked.

### Proof of Concept
1. As a normal user with push access to a repository, issue a `git push origin HEAD:refs/heads/<N-nested-segments>`, where the ref name is constructed as `refs/heads/a/a/a/.../a` with a very large number of `/`-separated segments (e.g., tens of thousands), staying within Git's overall ref-name byte-length limits by using single-character segment names.
2. Gitaly accepts the reference update as part of a normal `ReferenceTransaction`/mutator RPC (e.g., via `SSHReceivePack`/`ReceivePack`).
3. When the WAL transaction manager commits the log entry, `NewReferenceRecorder`/`RecordReferenceUpdates` inserts the ref into the `creations` `reftree.Node` and calls `WalkPreOrder`, causing `Node.walk` to recurse once per path segment.
4. With sufficiently many nested segments, the goroutine stack grows until the Go runtime raises a fatal (unrecoverable) stack-overflow error, crashing the `gitaly` process and denying service to all repositories on that node.

func (n *Node) walk(path string, callback WalkCallback, preOrder bool) error {
	isDir := n.children != nil

	if preOrder {
		if err := callback(path, isDir); err != nil {
			return fmt.Errorf("pre-order callback: %w", err)
		}
	}

	type child struct {
		path string
		node *Node
	}

	sortedChildren := make([]child, 0, len(n.children))
	for path, childNode := range n.children {
		sortedChildren = append(sortedChildren, child{path: path, node: childNode})
	}

	// Walk the children in lexicographical order to produce deterministic ordering.
	sort.Slice(sortedChildren, func(i, j int) bool {
		return sortedChildren[i].path < sortedChildren[j].path
	})

	for _, child := range sortedChildren {
		if err := child.node.walk(filepath.Join(path, child.path), callback, preOrder); err != nil {
			return fmt.Errorf("walk: %w", err)
		}
	}

// UnaryPanicHandler creates a new unary server interceptor that handles panics.
func UnaryPanicHandler(logger log.Logger) grpc.UnaryServerInterceptor {
	return func(ctx context.Context, req interface{}, info *grpc.UnaryServerInfo, handler grpc.UnaryHandler) (resp interface{}, err error) {
		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {
			err = toPanicError(grpcMethodName, r)
		})

		return handler(ctx, req)
	}
}

// StreamPanicHandler creates a new stream server interceptor that handles panics.

		defer handleCrash(logger, info.FullMethod, func(grpcMethodName string, r interface{}) {

		})

		return handler(srv, stream)
	}
