### Title
Unauthenticated `RecvError` packets let a spoofing attacker force denial-of-service tunnel teardown - (File: `outside.go`)

### Summary
The external report describes a privileged, unauthenticated/unlocked "kill switch" (`Option.kill`) that lets a party who does not need to hold any user credential immediately and irreversibly disrupt service (block `mint`/`exercise`) with no timelock and no cryptographic proof of authorization tied to the action. The analogous class in Nebula is a control-plane message that is processed *before* any certificate/AEAD authentication and that immediately tears down an established, encrypted tunnel based only on a coarse address check.

### Finding Description
In `outside.go`, `readOutsidePackets` dispatches two message types before any decryption or certificate verification happens: `header.Handshake` and `header.RecvError`: [1](#0-0) 

`header.RecvError` is routed straight to `f.handleRecvError(via.UdpAddr, h)`, which never checks the AEAD tag, the Noise session key, or any peer certificate — it only inspects the packet header (`h.RemoteIndex`) and the UDP source address supplied by the network layer: [2](#0-1) 

The only "authentication" performed is:
```
hr := hostinfo.GetRemote()
if hr.IsValid() && hr != addr {
    // reject as spoofed
}
```
i.e., the packet is accepted as long as its (spoofable) UDP source address matches the hostinfo's currently known remote address, and its `RemoteIndex` field matches a live `localIndexId` (a value carried in cleartext in every packet header, and therefore observable by anyone who can see any traffic to/from the victim, e.g. by sniffing on-path or when the peer is a public lighthouse). Neither of these fields is protected by the Noise handshake's cryptographic authentication — no CA-signed certificate, no valid session key, and no proof of session participation is required to trigger `handleRecvError`.

If those two conditions are met, the tunnel is destroyed immediately and unconditionally: [3](#0-2) 

This mirrors the report's bug class precisely: an action that (a) requires no proof of legitimate authority over the target's private key/session, (b) has no timelock or graceful degradation, and (c) directly and immediately disables service for the two endpoints (analogous to disabling `mint`/`exercise`).

Nebula does provide a config knob to mitigate this (`f.sendRecvErrorConfig` / `f.acceptRecvErrorConfig`, gated by `ShouldRecvError`): [4](#0-3) 
but by default (`recvErrorAlways`, or `recvErrorPrivate`) `RecvError` handling remains enabled and reachable from the untrusted underlay for any endpoint whose address the attacker can spoof or is "private" per the configured policy, and there is no cryptographic binding — only the address-match heuristic — protecting the teardown action.

### Impact Explanation
An attacker with UDP source-address spoofing capability (a common on-path or co-located capability, e.g., a shared network segment, ISP-level spoofing, or a compromised relay position) and knowledge of a target's `RemoteIndex` (obtainable by observing any packet exchanged with that host, since `RemoteIndex` is in the cleartext header) can immediately and repeatedly tear down established Nebula tunnels between two hosts with zero cryptographic proof of session participation. This is a persistent, repeatable denial-of-service primitive: every time the tunnel re-establishes, the attacker can send another forged `RecvError` and tear it down again, indefinitely preventing communication between the victims — directly analogous to the "pause" DoS in the referenced report, but requiring only network-position spoofing rather than a compromised owner key.

### Likelihood Explanation
Likelihood is moderate: exploitation requires (1) the ability to spoof the UDP source address of one of the two tunnel endpoints toward the other, and (2) knowledge of the current `RemoteIndex`, both of which are attainable by an attacker positioned to observe traffic (e.g., a malicious network intermediary, or in environments where UDP source spoofing is not filtered by upstream networks/firewalls). The project's own CHANGELOG shows this exact attack surface was already flagged as a security concern once (`listen.send_recv_error`, entry `#670`), evidencing that the Primitive-team-style trade-off ("mitigate but don't eliminate") was already made here for the send path, but the accept path's default (`recvErrorAlways`) still leaves the teardown trigger reachable without any cryptographic authentication.

### Recommendation
- Do not act on `RecvError` (or any other unauthenticated control message) to unconditionally tear down a live tunnel; require it to only accelerate re-handshake attempts rather than immediately delete `HostInfo`, or gate the teardown behind a short grace/verification period (a "timelock"-style mitigation analogous to the report's original recommendation).
- Strengthen the anti-spoofing check beyond a plain address comparison — e.g., require a small proof tied to the current session (such as echoing a recently-observed encrypted nonce/counter) before accepting a `RecvError` as authoritative.
- Default `listen.accept_recv_error` to the most restrictive safe setting (e.g., `private`/`never`) and document clearly, as recommended in the original report, under what conditions this DoS-relevant feature should be enabled, and who effectively can trigger it (anyone able to spoof UDP source addresses toward a peer, not just legitimate peers).

### Proof of Concept
1. Establish a tunnel between hosts A and B; observe (via network position) any encrypted packet from A to B, extracting the cleartext header's `RemoteIndex` value for A's connection.
2. Craft a UDP packet with header fields `Type = header.RecvError`, `RemoteIndex = <observed value>`, and no payload, per the encoder used in `sendRecvError`: [5](#0-4) 
3. Spoof the UDP source address to match B's known address (`hr` from A's perspective) and send the crafted packet to A.
4. A's `handleRecvError` finds the matching `HostInfo` via `QueryReverseIndex`, sees the source address matches the current remote, and calls `f.closeTunnel(hostinfo)` plus `f.handshakeManager.DeleteHostInfo(hostinfo)`, immediately destroying the tunnel with no cryptographic check of the sender's legitimacy: [6](#0-5) 
5. Repeating this whenever the tunnel re-establishes produces a persistent denial of service between A and B without ever needing a CA-signed certificate or valid Noise session key.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```

```go
type recvErrorConfig uint8

const (
	recvErrorAlways recvErrorConfig = iota
	recvErrorNever
	recvErrorPrivate
)

func (s recvErrorConfig) ShouldRecvError(endpoint netip.AddrPort) bool {
	switch s {
	case recvErrorPrivate:
		return endpoint.Addr().IsPrivate()
	case recvErrorAlways:
		return true
	case recvErrorNever:
		return false
	default:
		panic(fmt.Errorf("invalid recvErrorConfig value: %d", s))
	}
}
```
