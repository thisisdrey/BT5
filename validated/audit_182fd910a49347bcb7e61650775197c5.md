### Title
Any ERC-20 tokens held by `Operator` can be claimed by anyone via `execute` - ([File: contracts/Operator.sol])

### Summary
`Operator.execute` performs arbitrary `functionCallWithValue` calls to attacker-chosen targets with `Operator` as `msg.sender`. There is no allowlist on `calls_[i].target` or on the calldata. An unprivileged attacker can therefore encode a call to any ERC-20 held by the `Operator` contract (e.g. `transfer(attacker, balance)`) and drain it — the same bug class as the Arrakis report, where tokens sitting in a router/helper contract can be claimed by anyone. While most Metronome helper contracts (`NativeTokenGateway`, `VesperGateway`, `Treasury`, `Pool`, `DepositToken`) inherit `TokenHolder.sweep` gated by `onlyGovernor` [1](#0-0) , `Operator` has no such gate — the arbitrary-call surface itself is the exfiltration path.

### Finding Description
`execute` iterates over user-supplied `Call[]` and forwards each call verbatim: [2](#0-1) 

```solidity
function execute(Call[] calldata calls_) external payable nonReentrant setMsgSender returns (bytes[] memory) {
    ...
    _returnData[i] = _call.target.functionCallWithValue(_call.callData, _value);
    ...
    require(msg.value == _sumOfValues, "value-mismatch");
}
```

- `_call.target` is fully attacker-controlled. Setting `target = USDC` and `callData = transfer(attacker, bal)` executes `USDC.transfer` with `msg.sender == Operator`, spending the contract's own balance.
- The `nonReentrant` guard and `setMsgSender` transient-slot modifier do not restrict targets.
- `value-mismatch` only constrains ETH forwarded, not which contracts are called.
- `Operator` has no `receive()` restriction for ERC-20s (unlike `NativeTokenGateway`'s native-token-only `receive` [3](#0-2) ), so tokens can accumulate via accidental direct transfers or callbacks, and there is no owner-gated recovery — anyone can take them first.

The `getActualMsgSender`/`SynthContext._msgSender` mechanism is irrelevant to the drain: the theft happens because `Operator` itself is the `msg.sender` of the outgoing `transfer` call, not because of sender spoofing.

### Impact Explanation
Direct theft of funds: any ERC-20 balance (or ETH left via `selfdestruct`/refund dust) sitting in the `Operator` contract can be taken by any EOA. As in the reference finding, impact is limited to tokens the contract was not designed to custody (mis-sent user funds, airdropped tokens, leftover dust from failed multicalls), so severity is medium rather than critical — but the protocol provides no recovery path, so those funds are permanently claimable by the first taker.

### Likelihood Explanation
High certainty of exploitability (the call path is trivially reachable), moderate likelihood of meaningful balance. `Operator` is a long-lived, well-known address; users interacting through it may approve it or mis-send tokens to it, and any `transferFrom`-into-`Operator` pattern in integrated tooling would leave a balance. The attack requires no privileged role, no oracle manipulation, and no special timing — just observing a nonzero `balanceOf(operator)`.

### Recommendation
Either:
- Reject calls whose `target` would move `Operator`'s own assets (e.g. disallow `transfer`/`transferFrom` selectors to arbitrary token targets — impractical), or more simply
- Document the behavior and add an explicit governor-only `sweep` (inherit `TokenHolder`) so that stranded funds have a sanctioned recovery path and it is clear that residual balances are unclaimed — the same resolution Uniswap used with `sweepToken`. Alternatively, treat `Operator` as strictly non-custodial and revert `receive()`/fallback, which already occurs implicitly for ETH via `value-mismatch` but not for ERC-20s.

### Proof of Concept
Hardhat test sketch:

```typescript
import {ethers} from 'hardhat'
import {expect} from 'chai'

it('anyone can drain tokens held by Operator', async () => {
  const [attacker, user] = await ethers.getSigners()

  const token = await (await ethers.getContractFactory('ERC20Mock')).deploy('T', 'T', 18)
  const operator = await (await ethers.getContractFactory('Operator')).deploy()

  // tokens end up in Operator (e.g. accidental transfer / airdrop)
  await token.mint(operator.address, ethers.utils.parseEther('100'))

  const data = token.interface.encodeFunctionData('transfer', [
    attacker.address,
    ethers.utils.parseEther('100'),
  ])

  await operator.connect(attacker).execute([{target: token.address, value: 0, callData: data}])

  expect(await token.balanceOf(operator.address)).to.eq(0)
  expect(await token.balanceOf(attacker.address)).to.eq(ethers.utils.parseEther('100'))
})
```

Uncertain aspect: whether `Operator` actually holds balances on deployed chains is a configuration/history question; the drain path itself is unconditionally reachable whenever `balanceOf(operator) > 0`.
