Confirmed: `auth_digest()` in `libstackerdb/src/libstackerdb.rs` only hashes `slot_id`, `slot_version`, and `data_hash` — it does not include `contract_id`.### Title
Cross-StackerDB chunk signature replay due to missing `contract_id` binding in `SlotMetadata::auth_digest()` - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` computes the signed digest over only `slot_id`, `slot_version`, and `data_hash`, omitting `contract_id` entirely. Because `validate_received_chunk` resolves the expected signer per-contract via `StackerDBs::get_slot_signer(contract_id, slot_id)` and then calls `SlotMetadata::verify(principal)` — which never touches `contract_id` — a chunk validly signed by address `X` for slot `N` in contract A will also pass verification for slot `N` in contract B whenever `X` is also the designated slot owner of slot `N` in contract B.

The equality claimed in the prompt is confirmed: the signature authenticates `(slot_id, slot_version, data_hash)` only, never `contract_id`. Since slot-to-address assignment is a per-contract mapping (each StackerDB contract independently maps `slot_id -> owner address`, e.g., successive `.signers-N-M` reward-cycle contracts), it is entirely plausible — and in practice common, since the same signer address frequently retains the same relative slot ordering across successive per-cycle StackerDB contracts — for one StacksAddress to be the designated owner of slot `k` in two distinct contracts A and B.

Attack flow: an unprivileged peer observes (via ordinary StackerDB gossip/push, which it can legitimately receive as any P2P participant) a valid `StackerDBChunkData` broadcast for contract A, slot `k`, signed by address `X`. It then repackages that exact `(slot_id, slot_version, sig, data)` tuple and pushes it (or relays the observed `StackerDBPushChunk` message) to a peer's `handle_unsolicited_StackerDBPushChunk` path, but tagged for contract B instead of A. `validate_received_chunk` looks up `get_slot_signer(B, k)`, finds it also resolves to `X`, and `SlotMetadata::verify(X)` succeeds because the digest never encoded which contract it belonged to — so the replayed chunk is accepted and written into contract B's slot `k`, even though `X` never authored/signed anything intended for contract B.

### Impact Explanation
This is an unauthenticated/unauthorized write into a StackerDB replica: content signed for one contract's slot gets planted verbatim in another contract's identically-indexed slot without the slot owner's consent or knowledge for that destination DB. Because StackerDB chunks (e.g., signer messages) are trusted/relayed further based on slot ownership, this can inject attacker-chosen (but originally legitimately-signed) payloads into an unrelated StackerDB namespace, and that forged write propagates to all peers replicating contract B via normal StackerDB sync/gossip. This matches the "unauthenticated/unauthorized write to StackerDB" Critical category.

### Likelihood Explanation
The attacker needs no privileged key or secret — only the ability to observe a legitimately broadcast chunk on the P2P network for some contract A (any StackerDB participant can see these) and the pre-existing condition that some slot owner address is shared, at the same slot index, across contract A and a target contract B. This condition is realistic for the Stacks signer set, where the same signer's slot index is often preserved across successive per-cycle StackerDB contracts. Replay costs are trivial (repackage and resend one message), and it is fully repeatable for every future valid chunk observed for that address.

### Recommendation
Include `contract_id` (or a unique per-StackerDB domain separator, e.g., the `QualifiedContractIdentifier`) as part of the `auth_digest()` computation in `SlotMetadata`/`StackerDBChunkData`, so that a signature is cryptographically bound to the specific StackerDB contract it was produced for, preventing cross-contract replay even when slot ownership coincidentally overlaps.

### Proof of Concept
In `libstackerdb/src/libstackerdb.rs` tests module:
1. Construct `SlotMetadata` for `slot_id=0, slot_version=1, data_hash=H`, sign with `privk_X` bound conceptually to contract A.
2. Verify it succeeds: `md.verify(&addr_X).unwrap() == true`.
3. Reuse the identical `SlotMetadata`/`StackerDBChunkData` bytes, but invoke the destination contract B's `StackerDBs::get_slot_signer(contract_B, 0)` (configured so slot 0 owner is also `addr_X`), then call `validate_received_chunk`/`try_replace_chunk` for contract B with the same chunk — assert it is accepted (`accepted: true`) into contract B's slot 0 store, demonstrating the chunk authored/signed in the context of contract A was accepted as a valid write for contract B purely because `contract_id` is absent from `auth_digest()`.

    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
