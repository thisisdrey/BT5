### Title
Index-out-of-range panic parsing malformed XCOFF binaries with negative symbol section numbers - (File: src/internal/xcoff/file.go)

### Summary
`internal/xcoff.NewFile` parses the symbol table of an XCOFF object/executable and validates a symbol's `SectionNumber` only against the upper bound (`nscns`), but never rejects negative values before using it to index `f.Sections`. A crafted XCOFF file with a symbol whose section number is a legitimate-looking negative value (e.g. `N_ABS = -1` or `N_DEBUG = -2`, both valid per XCOFF spec and explicitly handled elsewhere in this codebase) causes a negative slice index and a runtime panic. This mirrors the binutils CVE-2026-6846 bug class: a crafted object file's section-index field is trusted without full bounds validation before being used as an array index during file-format parsing.

### Finding Description
Attacker-controlled input is an arbitrary file that a victim asks the Go toolchain/standard library to inspect as an XCOFF binary — e.g. via `debug/buildinfo.ReadFile`/`Read` (used by `go version -m <file>` and third-party tools such as vulnerability scanners that read untrusted binaries), or via `cmd/internal/objfile` (used by `go tool nm`, `go tool objdump`). Both call into `internal/xcoff.NewFile`.

In `src/internal/xcoff/file.go`, the symbol-table loop reads each symbol's `SectionNumber` from the file [1](#0-0) , and later validates only the upper bound: [2](#0-1) 
```
if sym.SectionNumber > int(nscns) {
    goto skip
}
if sym.SectionNumber == 0 {
    sym.Value = 0
} else {
    sym.Value -= f.Sections[sym.SectionNumber-1].VirtualAddress
}
```
No check exists for `sym.SectionNumber < 0`. Elsewhere in the very same codebase (`src/cmd/internal/objfile/xcoff.go`), the constants `N_ABS = -1` and `N_DEBUG = -2` are explicitly recognized as valid, legal `SectionNumber` values for absolute/debug symbols [3](#0-2) , confirming these negative values are a normal, spec-compliant part of the format that `internal/xcoff.NewFile` fails to special-case. When such a symbol is parsed, `f.Sections[sym.SectionNumber-1]` is evaluated with a negative index (e.g. `-2` or `-3`), which panics with "index out of range" since Go slices reject negative indices outright.

### Impact Explanation
This is a parser panic on attacker-supplied, untrusted input reached through a normal victim workflow (inspecting a downloaded/received binary with `go version -m`, `go tool nm`, `go tool objdump`, or any third-party tool built on `debug/buildinfo`). It causes a crash/denial of service of the invoking process; it does not by itself grant code execution the way the binutils heap-overflow does (Go's bounds-checked slices convert what would be a C heap-buffer-overflow into a safe panic rather than memory corruption). Under Go's own security policy, a reproducible panic from malicious-input parsing typically qualifies for a PUBLIC-track fix (a hardening/robustness bug), not an URGENT memory-safety compromise, since Go's runtime bounds checking prevents the "arbitrary code execution" outcome seen in the C-based binutils analog.

### Likelihood Explanation
Any tool that calls `debug/buildinfo.Read`/`ReadFile` or `cmd/internal/objfile` (e.g. `go version -m`, `go tool nm`, `go tool objdump`, or third-party binary-analysis tools importing `debug/buildinfo`) on an attacker-supplied file matches the "ordinary user data" premise — no privileged access or malicious peer control is required, just convincing a user to run one of these commands against a malicious file, which is a common, low-friction victim workflow (e.g., analyzing a suspicious downloaded executable).

### Recommendation
In `internal/xcoff.NewFile`, validate `sym.SectionNumber` against both bounds before indexing, e.g. `if sym.SectionNumber <= 0 || sym.SectionNumber > int(nscns) { ... }`, treating negative/absolute/debug section numbers (`N_UNDEF`, `N_ABS`, `N_DEBUG`) the same way `cmd/internal/objfile/xcoff.go` already does, skipping the section-based `Value` adjustment for them instead of indexing `f.Sections`.
