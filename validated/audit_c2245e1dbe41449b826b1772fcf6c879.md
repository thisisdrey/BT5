### Title
SMTP command-injection via bare-CR line smuggling in `textproto.dotWriter.Write` - (File: src/net/textproto/writer.go)

### Finding Description
`net/smtp.Client.Data()` returns a `dataCloser` wrapping `c.Text.DotWriter()` [1](#0-0) , and `SendMail` writes the caller-supplied `msg` byte slice directly into that writer [2](#0-1) . The dot-encoding writer's state machine in `dotWriter.Write` only treats `wstateBeginLine` (i.e. "start of a new line, escape a leading dot") as reachable via an emitted `\n`; a lone `\r` transitions to `wstateCR` and then, on any non-`\n` byte, falls through to `wstateData` without ever visiting `wstateBeginLine` [3](#0-2) . Consequently, a message body containing a bare `\r` immediately followed by a line beginning with `.` (i.e. `...\r.<data>\r\n`) is passed through the wire with the leading `.` left *unescaped*, because the writer never registered "beginning of line" for that segment. The literal byte sequence `\r.\r\n` (or any variant producing an un-doubled dot line) is exactly the SMTP end-of-DATA marker (`.\r\n`) that a downstream/receiving SMTP server tolerant of bare-CR-as-line-terminator will interpret as terminating the DATA phase, letting any subsequent attacker-controlled bytes in the same buffer be parsed as new SMTP commands — the identical "SMTP smuggling" primitive (CVE-2023-51764/51766 class) referenced in the Dovecot advisory, just realized in Go's `net/smtp`/`net/textproto` dot-encoder instead of Dovecot's relay path.

### Impact Explanation
If an application built on `net/smtp.SendMail`/`Client.Data` forwards attacker-influenced content into the message body (e.g. a web form field embedded into an email body, common practice despite the package's "should be CRLF" caveat), the attacker can smuggle additional SMTP commands (e.g. inject a spoofed `MAIL FROM`/`RCPT TO`/second message) into the same TCP session on a receiving server that still tolerates bare CR as a line terminator — an authentication/integrity bypass allowing spoofed email injection. This is a content/interpretation mismatch between the Go client's dot-encoder and downstream parsing, matching a PUBLIC-track hardening bug in Go's standard library (not RCE, but a real protocol-injection primitive) rather than a critical/urgent issue since it requires a downstream server that has not fixed the underlying SMTP-smuggling class itself.

### Likelihood Explanation
Requires an ordinary, unprivileged workflow: any Go program using `net/smtp.SendMail` (or `Client.Data`) to relay a message whose body contains attacker-influenced bytes with a bare `\r` (not `\r\n`) before a `.`-prefixed line, sent toward a mail server that is itself still vulnerable to the underlying SMTP-smuggling class. No special privileges, TLS/cert trust, or malicious server control are needed — the "attacker" is just the source of message-body content.

### Recommendation
Harden `dotWriter`'s state machine so that a bare `\r` (not immediately followed by `\n`) is normalized/rejected rather than silently emitted, and so that any byte sequence ending in `\r` (regardless of whether it came through `wstateCR`) is treated as ending a line for the purposes of leading-dot escaping — i.e., escape the dot whenever a "logical" new line begins, not only after a literal `\n` is written. Alternatively/additionally, reject or escape embedded bare `\r` characters in `net/smtp.SendMail`/`Client.Data` input up front, consistent with `validateLine`'s existing rejection of CR/LF in command arguments [4](#0-3) .

### Proof of Concept
```go
package textproto

import (
	"bufio"
	"strings"
	"testing"
)

func TestDotWriterBareCRSmuggling(t *testing.T) {
	var buf strings.Builder
	w := NewWriter(bufio.NewWriter(&buf))
	d := w.DotWriter()
	// bare \r (no \n) immediately followed by a line starting with "."
	// simulating an SMTP message body smuggled by an attacker-controlled field
	_, err := d.Write([]byte("Subject: hi\r.\r\n"))
	if err != nil {
		t.Fatal(err)
	}
	d.Close()
	out := buf.String()
	// A correctly dot-escaped stream must NOT contain a raw, un-doubled
	// ".\r\n" line except as the final terminator that Close() appends.
	// Count of ".\r\n" occurrences should be exactly 1 (the terminator).
	if strings.Count(out, ".\r\n") != 1 {
		t.Fatalf("bare-CR line was not escaped, wire bytes = %q", out)
	}
}
```
Expected (buggy) result: the test fails because `out` contains two `.\r\n` occurrences — the smuggled unescaped dot-terminator from the message body plus the legitimate closing terminator — demonstrating that a receiving server may see a premature end-of-DATA and interpret trailing bytes as new SMTP commands.
