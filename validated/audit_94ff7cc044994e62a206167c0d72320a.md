### Title
RefService.UpdateReferences and RepositoryService.WriteRef bypass GitLab access-check hooks that OperationService enforces on every other user-facing reference mutation - (File: internal/gitaly/service/ref/update_references.go, internal/gitaly/service/repository/write_ref.go)

### Summary
Gitaly's "formal" reference-mutation path (`OperationService` RPCs such as `UserUpdateBranch`, `UserCreateTag`, `UserDeleteBranch`, `UserCherryPick`, etc.) always routes writes through `UpdaterWithHooks.UpdateReference`, which invokes `PreReceiveHook` (Rails `/internal/allowed` access check + custom hooks), `UpdateHook`, and `PostReceiveHook` before a ref is committed via `git-update-ref` [1](#0-0) . In contrast, `RefService.UpdateReferences` and `RepositoryService.WriteRef` construct a bare `updateref.Updater` with `updateref.New(ctx, repo)` and commit reference changes directly, with no call into `hook.Manager`, no Rails `/internal/allowed` check, and no quarantine handling [2](#0-1) [3](#0-2) . This mirrors the reported bug class: a "formal" path enforces a mandatory control (fee / access check) while an alternate path that achieves the same end-state outcome (moving assets / updating refs) skips that control entirely.

### Finding Description
Gitaly documents that reference-transaction and receive-pack style hooks are the enforcement mechanism for GitLab's branch/tag protection, force-push restrictions, and other access policies, and states plainly that "Most RPCs in the `OperationService` that write objects into the repository manually invoke these hooks using the `updateref.UpdaterWithHooks` structure" [4](#0-3) . The `OperationServiceServer` interface's own doc comment reinforces this as the security model: "The user's operation is treated as untrusted. Any reference update is thus checked against GitLab's '/allowed' endpoint" [5](#0-4) .

`UpdaterWithHooks.UpdateReference` is the formal, fee-charging-equivalent path: it always calls `PreReceiveHook` (which posts to Rails `/internal/allowed`) before migrating quarantined objects and calling `UpdateHook`, and only then commits the ref update via a low-level updater with hooks disabled (`WithDisabledTransactions`) because hook execution has already happened manually [6](#0-5) .

`RefService.UpdateReferences`, however, takes a stream of arbitrary reference name/old-OID/new-OID triples directly from the client, validates only ref-name format and object-ID hex validity, and applies them via a bare `updateref.New(ctx, repo)` / `Update()` / `Commit()` sequence with no `hook.Manager` involved at all [7](#0-6) [8](#0-7) . Similarly, `RepositoryService.WriteRef` resolves a revision and pushes it directly to `git-update-ref` through the same unhooked `updateref.Updater`, again without going through `hook.Manager.PreReceiveHook`/`UpdateHook`/`PostReceiveHook` [9](#0-8) .

Both RPCs can create, force-update, or delete arbitrary references (including protected branches/tags) in a target repository, achieving exactly the outcome that `OperationService`'s hook-gated RPCs are designed to gate behind Rails's `/internal/allowed` check and any admin-installed custom hooks. If either RPC is reachable by a client that is not otherwise fully trusted (e.g. via an internal API path invoked with insufficiently-scoped repository access, or any caller that can reach `RefService`/`RepositoryService` with a valid repo but without going through the Rails permission gate that normally wraps `OperationService` calls), the caller can bypass branch protection, push rules, and any custom `pre-receive`/`update` hook enforcement — the direct analog of "ragequitting" instead of going through the fee-charging "distribution" path.

### Impact Explanation
A caller who can invoke `UpdateReferences` or `WriteRef` directly bypasses:
- Rails's `/internal/allowed` access check (protected branch/tag enforcement, force-push restrictions, push rules).
- Any administrator-installed custom `pre-receive`/`update`/`post-receive` hooks.
- The push-active reference counter used by GitLab to know when a repository can safely be relocated [10](#0-9) .

This allows unauthorized reference mutation (force-updates or deletion of protected branches/tags, or silent creation of refs) without any of the safeguards that the rest of Gitaly's write surface enforces, directly mirroring the value-bypass structure of the referenced smart-contract bug (formal path pays a mandatory fee/control; alternate path reaches the same end-state for free).

### Likelihood Explanation
This is not exploitable by a fully anonymous/untrusted external Git client — `RefService` and `RepositoryService` are internal gRPC services intended to be called by trusted GitLab Rails/Workhorse/Praefect components, not directly by end users pushing over SSH/HTTP. The likelihood of this being a real vulnerability therefore depends entirely on the trust boundary of whatever caller can reach these RPCs with a valid `Repository` message and whether that caller has already performed (or is expected by Gitaly to have performed) the equivalent of GitLab's permission checks before calling. I could not verify from the indexed files whether any authorization middleware or Rails-side gate universally intercepts calls to these two RPCs the way it does for OperationService calls — this needs to be confirmed against Gitaly's calling context (e.g., whether Praefect/Workhorse route arbitrary user-supplied ref updates through these RPCs without a prior Rails permission check).

### Recommendation
- Document and, ideally, enforce that `RefService.UpdateReferences` and `RepositoryService.WriteRef` are only to be called by fully-trusted internal Rails/GitLab-Shell code paths that have already performed equivalent access checks, and audit call sites in the GitLab Rails codebase to confirm this invariant holds for every caller.
- Where these RPCs are used to satisfy user-initiated actions, route them through `hook.Manager`/`UpdaterWithHooks` (as `OperationService` does) so that `/internal/allowed` and custom hooks are consistently enforced regardless of which RPC surface is used to mutate a reference.
- Consider adding a defense-in-depth check that fails closed unless the request originates from an authenticated internal context.

### Proof of Concept
1. Obtain (or be) a caller with network access to Gitaly's gRPC endpoint and a valid `Repository` message for a target repo containing a protected branch (would ordinarily require a full push/`OperationService` round-trip involving Rails's `/internal/allowed` check).
2. Call `RefService.UpdateReferences` with an `Update{Reference: "refs/heads/protected", OldObjectId: <current>, NewObjectId: <attacker-controlled commit>}` — see the update path in [8](#0-7) . No `PreReceiveHook`/Rails check is invoked.
3. Alternatively call `RepositoryService.WriteRef` with `Ref: "refs/heads/protected"`, `Revision: <attacker commit>` — see [11](#0-10) .
4. Observe the reference is force-updated/deleted with no access-check or custom-hook execution, unlike the equivalent `OperationService.UserUpdateBranch`/`UserDeleteBranch` calls which run `PreReceiveHook` and would reject the same change if disallowed (compare [12](#0-11) ).

func (s *server) UpdateReferences(server gitalypb.RefService_UpdateReferencesServer) error {
	ctx := server.Context()

	request, err := server.Recv()
	if err != nil {
		return fmt.Errorf("receiving initial request: %w", err)
	}

	if err := s.locator.ValidateRepository(ctx, request.GetRepository()); err != nil {
		return err
	}
	repo := s.localRepoFactory.Build(request.GetRepository())

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	// Unset the repository so that we can more easily verify inside of the loop that all incoming requests
	// ain't got a repository set anymore.
	request.Repository = nil

	updater, err := updateref.New(ctx, repo)
	if err != nil {
		return fmt.Errorf("creating updater: %w", err)
	}

	if err := updater.Start(); err != nil {
		return fmt.Errorf("starting updater: %w", err)
	}
