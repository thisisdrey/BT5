### Title
Unsigned integer underflow in packfile/reftable size-difference heuristics causes mis-triggered or DoS-prone repacking - (File: internal/git/housekeeping/optimization_strategy.go)

### Summary
`HeuristicalOptimizationStrategy.ShouldRepackObjects` and `ShouldRepackReferences` compute the "amount of drift" between two related counters/sizes by direct `uint64` subtraction, exactly the same anti-pattern as the Karak `_transferToSlashStore()` bug: two values that are supposed to satisfy `a >= b` are subtracted without checking the invariant first. If `b` ever exceeds `a` due to a race, stale metadata, or a size smaller than the assumed constant overhead, the subtraction underflows (Go wraps unsigned integers silently instead of panicking) and yields a huge bogus value that then drives housekeeping decisions.

### Finding Description
Two occurrences in the same file follow the pattern `larger_supposedly - smaller_supposedly` on `uint64` values without an invariant check:

1. `untrackedPackfiles := s.info.Packfiles.Count - s.info.Packfiles.MultiPackIndex.PackfileCount` [1](#0-0) 
The code comments themselves acknowledge the underlying assumption is fragile: "As we only update the MIDX during housekeeping this metric should in theory be accurate," implying it can become inaccurate in practice (e.g., concurrent optimizations, WAL-managed repacks changing packfile state between the point `RepositoryInfo` is gathered and when the multi-pack-index is updated, or object-pool member repositories where pool packfiles are merged into `mergePoolInfo` before this check runs) [2](#0-1) 
If `MultiPackIndex.PackfileCount` ever exceeds `Packfiles.Count`, `untrackedPackfiles` wraps to a value near `math.MaxUint64`, which will always exceed `actualLimit`, forcing a geometric repack on every single optimization pass for that repository.

2. In `ShouldRepackReferences`, for reftable-backed repositories:
```go
var overhead uint64 = 28
...
sizePrev := tables[i-1].Size - overhead
sizeCur := tables[i].Size - overhead
``` [3](#0-2) 
This subtracts a fixed constant from every table's on-disk size without verifying `Size >= overhead`. If a table is ever recorded with a size at or below the hard-coded overhead, both values underflow to near-`MaxUint64`, corrupting the geometric-progression comparison and forcing (or suppressing, depending on wrap direction) a references repack decision.

Both call sites are reached from `ShouldRepackObjects`/`ShouldRepackReferences`, which are invoked by Gitaly's repository optimization/housekeeping path (`OptimizeRepository` RPC and automatic housekeeping triggered by ordinary pushes), so the trigger condition is on the normal write path used by unprivileged users, not a privileged actor.

### Impact Explanation
Unlike the Solidity original where the underflow reverts the transaction (an explicit DoS), Go's `uint64` subtraction wraps instead of panicking, so the immediate effect here is not a crash but a **corrupted heuristic decision** that always evaluates true. That causes Gitaly to run the most expensive optimization branch (`geometricRepackCfg`, a full `git-repack`) on essentially every optimization cycle for the affected repository, instead of running it only when actually needed. Repeated, needless full repacks of large repositories consume CPU, memory, and disk I/O, which is a resource-exhaustion/DoS risk on Gitaly nodes servicing many repositories, and it degrades the effectiveness of the adaptive scheduling the heuristic was designed to provide.

### Likelihood Explanation
I could not find concrete evidence in the indexed code that `MultiPackIndex.PackfileCount > Packfiles.Count` or `ReftableTable.Size <= 28` actually occurs in practice — reftables always contain at least a header+footer (92–100 bytes per `internal/git/reftable/reftable.go`'s `HeaderSize`/`FooterSize` constants), and the multi-pack-index count is normally derived consistently with the packfile count. This makes the underflow condition plausible only under races or corrupted/partial state (e.g., mid-compaction states, concurrent optimizations, or pool-repository merges) rather than trivially reachable by a single crafted RPC field. This is a materially weaker analog than the original Karak finding, which had a fully worked, coded PoC demonstrating reachability; here reachability is argued from code comments and structural similarity rather than demonstrated. I flag this explicitly as unconfirmed/uncertain.

### Recommendation
Add explicit invariant checks before each subtraction, mirroring the fix applied by Karak:
```go
var untrackedPackfiles uint64
if s.info.Packfiles.Count > s.info.Packfiles.MultiPackIndex.PackfileCount {
    untrackedPackfiles = s.info.Packfiles.Count - s.info.Packfiles.MultiPackIndex.PackfileCount
}
```
and similarly guard the reftable overhead subtraction:
```go
sizePrev := uint64(0)
if tables[i-1].Size > overhead {
    sizePrev = tables[i-1].Size - overhead
}
```
Additionally, consider using signed integers or `math/bits.Sub64`-based overflow-checked subtraction helpers in these heuristics so that any future violation of the assumed invariant fails safe (e.g., defaults to "no action needed") rather than silently wrapping to a value that forces maximal, repeated work.

### Proof of Concept
I do not have a concrete, verified reproduction demonstrating that `MultiPackIndex.PackfileCount` can exceed `Packfiles.Count`, or that a reftable's `Size` can be `<= 28` bytes, in Gitaly's current production code paths. This is analogous to the *hint* in the external report (bug class: unchecked subtraction between two values assumed ordered) rather than a proven exploit chain; a background engineer would need to construct a race (e.g., concurrent `OptimizeRepository` calls, or crash-recovery producing a stale/incomplete multi-pack-index or reftable) to confirm actual reachability before treating this as a validated, high-confidence finding.

	// To calculate this we use the number of packfiles tracked by the multi-pack index:
	// the difference between the total number of packfiles and the number of packfiles
	// tracked by the index is the amount of packfiles written since the last geometric
	// repack. As we only update the MIDX during housekeeping this metric should in
	// theory be accurate.
	//
	// Theoretically, we could perform a geometric repack whenever there is at least one
	// untracked packfile as git-repack(1) would exit early in case it finds that the
	// geometric sequence is kept. But there are multiple reasons why we want to avoid
	// this:
	//
	// - We would end up spawning git-repack(1) on almost every single repository
	//   optimization, but ideally we want to be lazy and do only as much work as is
	//   really required.
	//
	// - While we wouldn't need to repack objects in case the geometric sequence is kept
	//   anyway, we'd still need to update the multi-pack-index. This action scales with
	//   the number of overall objects in the repository.
	//
	// Instead, we use a strategy that heuristically determines whether the repository
	// has too many untracked packfiles and scale the number with the combined size of
	// all packfiles. The intent is to perform geometric repacks less often the larger
	// the repository, also because larger repositories tend to be more active, too.
	//
	// The formula we use is:
	//
	//	log(total_packfile_size) / log(1.8)
	//
	// Which gives us the following allowed number of untracked packfiles:
	//
	// -----------------------------------------------------
	// | total packfile size | allowed untracked packfiles |
	// -----------------------------------------------------
	// | none or <10MB       |  2                          |
	// | 10MB                |  3                          |
	// | 100MB               |  7                          |
	// | 500MB               | 10                          |
	// | 1GB                 | 11                          |
	// | 5GB                 | 14                          |
	// | 10GB                | 15                          |
	// | 100GB               | 19                          |
	// -----------------------------------------------------
	allowedLowerLimit := 2.0
	allowedUpperLimit := math.Log(float64(s.info.Packfiles.Size/1024/1024)) / math.Log(1.8)
	actualLimit := math.Max(allowedLowerLimit, allowedUpperLimit)

	untrackedPackfiles := s.info.Packfiles.Count - s.info.Packfiles.MultiPackIndex.PackfileCount

	if untrackedPackfiles > uint64(actualLimit) {
		return true, geometricRepackCfg
	}

	member.LooseObjects.StaleCount += pool.LooseObjects.StaleCount
	member.LooseObjects.StaleSize += pool.LooseObjects.StaleSize
	member.LooseObjects.GarbageCount += pool.LooseObjects.GarbageCount
	member.LooseObjects.GarbageSize += pool.LooseObjects.GarbageSize

	member.Packfiles.Count += pool.Packfiles.Count
	member.Packfiles.Size += pool.Packfiles.Size
	member.Packfiles.ReverseIndexCount += pool.Packfiles.ReverseIndexCount
	member.Packfiles.CruftCount += pool.Packfiles.CruftCount
	member.Packfiles.CruftSize += pool.Packfiles.CruftSize
	member.Packfiles.KeepCount += pool.Packfiles.KeepCount
	member.Packfiles.KeepSize += pool.Packfiles.KeepSize
	member.Packfiles.GarbageCount += pool.Packfiles.GarbageCount
