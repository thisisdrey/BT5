Cgroups exist as an optional, non-default memory limiting mechanism (see `internal/cgroups` and `doc/cgroups.md`), but they are not enabled by default and are configured per-git-command subprocess resource management, not a built-in bound in the smudge code itself. This doesn't change the core finding since the code itself has no cap and the comment explicitly documents unbounded buffering as accepted behavior.

### Title
Unbounded in-memory buffering of non-LFS-pointer blob content in git smudge long-running process causes memory exhaustion (DoS) - ([File: cmd/gitaly-lfs-smudge/smudge.go])

### Summary
The `process()` function implementing the Git long-running filter process protocol accumulates the entire content of a blob into an in-memory `bytes.Buffer` (`content`) before it can determine whether the blob is an LFS pointer, with no upper bound on buffer size. An attacker who can get gitattributes to mark an arbitrarily large, non-LFS-pointer blob with `filter=lfs` can force `gitaly-lfs-smudge` to slurp the entire blob into memory during RPCs such as `GetArchive` with `IncludeLfsBlobs: true`.

### Finding Description
In `cmd/gitaly-lfs-smudge/smudge.go`, the `processStateSmudgeContent` case reads pktline-chunked data from the calling `git` process and writes each chunk into `content bytes.Buffer` until a flush packet is observed ( [1](#0-0) ). The comment explicitly acknowledges this design: "we have to slurp in all of its contents so that we can echo it back to the caller" ( [2](#0-1) ). There is no size cap on `content`, and `bytes.Buffer.Write` will grow to accommodate arbitrarily large input.

This code path is reachable from `GetArchive` when `IncludeLfsBlobs` is set: `handleArchive` configures `smudge.DriverTypeProcess` and injects `filter.lfs.process` git config pointing at the `gitaly-lfs-smudge` binary, then runs `git archive`, which invokes the smudge filter for every blob under `filter=lfs` gitattributes ( [3](#0-2) ). An attacker controls repository content and `.gitattributes`, so they can mark an arbitrary large blob (not a genuine LFS pointer) with `filter=lfs`; `smudgeOneObject` will fail LFS-pointer decoding and fall back to echoing the whole buffered content ( [4](#0-3) ). Before that fallback can occur, the full blob must already reside in `content`, since the flush packet triggering the LFS decode attempt is only sent once git has streamed the entire blob to the filter process ( [5](#0-4) ).

No existing size limit, streaming threshold, or backpressure mechanism exists in this code to cap `content`'s growth; the design explicitly favors correctness in relaying raw content back to `git` over bounding memory use.

### Impact Explanation
This causes unbounded memory growth in the `gitaly-lfs-smudge` subprocess proportional to attacker-controlled blob size, which is spawned per smudge invocation during `git archive`/checkout operations driven by RPCs like `GetArchive`. A sufficiently large blob (multi-gigabyte) can exhaust available memory for that subprocess and, depending on the host's OOM behavior, can affect sibling processes including the parent `git archive` process and potentially destabilize the Gitaly node under concurrent requests. This matches a resource-exhaustion/DoS impact class against a repository RPC handler.

### Likelihood Explanation
The attacker only needs to be an ordinary user able to push a repository they own with a `.gitattributes` entry mapping a large non-pointer file to `filter=lfs`, and then trigger `GetArchive` with `IncludeLfsBlobs: true` (or another checkout path using the LFS smudge process filter) — no special privilege, secret, or non-default Gitaly configuration is required. This is repeatable per request and scales with blob size and concurrency of requests, though it is bounded by how large a blob the attacker can actually push/store in the repository and by GitLab Rails-side upload size limits, which are outside Gitaly's control.

### Recommendation
Impose a maximum buffered size for `content` in `processStateSmudgeContent` (e.g., spill to a temp file once a threshold is exceeded, or read/detect the LFS pointer prefix incrementally and switch to streaming pass-through once it's clear the blob is not a pointer, since valid LFS pointers are small and bounded by definition). Alternatively, bound `content` to the maximum plausible LFS pointer size (a few hundred bytes) and stream any excess directly through without buffering the full blob.

### Proof of Concept
1. Create a repository with `.gitattributes` containing `bigfile filter=lfs diff=lfs merge=lfs -text`.
2. Commit `bigfile` as a large (e.g., several-GB) non-LFS-pointer blob (not going through `git lfs track`, just raw content).
3. Call `GetArchive` RPC with `IncludeLfsBlobs: true` on that commit, as exercised in `TestGetArchive_environment` for the `IncludeLfsBlobs` code path ( [6](#0-5) ).
4. Observe that `gitaly-lfs-smudge`'s RSS grows to match the size of `bigfile` before it emits `status=success` and streams the content back, confirming unbounded memory use as documented by the code comment at `smudge.go:263-268`.
