### Title
Access-key revocation does not invalidate pre-signed high-nonce transactions, enabling replay after key recreation - ([File: runtime/runtime/src/access_keys.rs])

### Summary
`OVM_FraudVerifier`/`OVM_BondManager` identified a State Transitioner only by `(pre-state root, tx hash)`, a pair that does not uniquely bind to one logical transition, so a stale/legitimate proof could be finalized against the wrong (later) instance. NEAR's access-key layer has the same class of problem: an access key's identity is `(account_id, public_key)`, and a signed transaction's replay-safety is anchored only to the *current* nonce of that key. When a key is deleted and a new key is added under the **same public key**, the "key epoch" is not tracked — the new key is seeded with `initial_nonce_value(block_height)`, not with any value derived from the specific nonce state of the key it replaces. A transaction validly signed under the old key epoch, whose nonce still exceeds the new epoch's seed and is still under the height-based upper bound, remains valid and can be replayed against the new key epoch.

### Finding Description
An `AccessKey` is looked up purely by `(account_id, public_key)` [1](#0-0) . The struct's own doc comment already flags the exact hazard: when a key must be recreated and the new key reuses the old public key, "the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again" [2](#0-1) .

However, the implementation of `action_add_key` never enforces this. It only rejects the add if a key already exists under that public key; if the key does not currently exist (i.e., it was deleted and is now being re-added under the same public key), the new key's nonce is unconditionally reset to a value derived only from the block height, discarding any relationship to the deleted key's actual nonce progress: [3](#0-2) [4](#0-3)

Nonce validation (`verify_nonce`) only requires the incoming nonce to be strictly greater than the *currently stored* nonce (Monotonic mode) and below a height-based upper bound; it has no notion of "key epoch": [6](#0-5) 

Critically, the upper bound is computed from the **current inclusion height**, not the signing height: `upper_bound = height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` [7](#0-6) . Because `ACCESS_KEY_NONCE_RANGE_MULTIPLIER = 1_000_000` [8](#0-7) , a signer can validly attach a nonce anywhere up to roughly `current_height * 1_000_000` at the moment of inclusion — far above the range that `initial_nonce_value` will seed for a freshly (re)created key at that same or a nearby height. If the account owner:
1. Signs (but does not yet submit) a transaction with a nonce near the current height-based ceiling,
2. Later deletes the access key (e.g., to rotate credentials after a suspected leak) and re-adds a key with the same public key (`DeleteKey` + `AddKey` in the same or a following transaction),

then the newly seeded nonce (`(block_height-1) * 1_000_000`) is not guaranteed to exceed the old, still-unused, high nonce. That previously-signed transaction remains valid: `tx_nonce > current_nonce` still holds, and `tx_nonce < upper_bound` still holds at the (still comparable) new inclusion height. The transaction can therefore be replayed even though the signer's intent (deleting/rotating the key) was to invalidate it. This mirrors the Optimism bug precisely: an identifier pair (`account_id, public_key` ~ `pre-state root, tx hash`) is reused across two distinct logical "epochs"/"transitions," and the mitigating value (initial nonce ~ single pre-state root at finalization) does not carry enough state to disambiguate stale artifacts from the current epoch.

### Impact Explanation
This allows replay of an access-key holder's own previously-signed (but unbroadcast) transaction after that key is believed to be revoked/rotated, which is a double-spend/replay category impact: funds transfers, `FunctionCall`s, or other actions the owner intended to be dead can still execute post-revocation. In counterparty/escrow scenarios (e.g., a user signs a transaction and hands it to a counterparty as part of an off-chain agreement, then revokes the key believing this invalidates the outstanding signed artifact), the counterparty can later broadcast the stale transaction and it will still be accepted, causing unintended state changes or fund loss for the signer.

### Likelihood Explanation
Exploitation requires a specific but realistic precondition: a nonce gap wide enough for a stale, previously-signed transaction's nonce to still exceed the freshly-seeded nonce at the time of key recreation. Because `ACCESS_KEY_NONCE_RANGE_MULTIPLIER` scales the valid nonce range with the *current* block height rather than with a value tied to the specific key instance, and because `initial_nonce_value` uses only block height with no linkage to the deleted key's nonce state, this gap is achievable by an ordinary signer without any special privilege — simply by pre-signing a transaction with an aggressively high (but valid) nonce and later deleting/recreating the same public key. This is a lower-likelihood, edge-case scenario compared to a directly-exploitable third-party attack (it largely depends on the victim's own key-rotation practice or being tricked/social-engineered), similar to how the referenced Optimism issue was acknowledged but deemed non-exploitable under the then-current trust assumptions.

### Recommendation
When re-adding an access key under a public key that previously existed on the account, seed (or lower-bound) the new key's nonce using the maximum of `initial_nonce_value(block_height)` and any nonce value associated with the just-deleted key (e.g., persist the last nonce reached by a deleted key, at least for some retention window, and require the new key's nonce to exceed it). Alternatively, disallow re-adding a previously-deleted public key at all, or require an explicit higher nonce floor to be supplied and validated against the account's last known usage for that public key, closing the "key epoch" ambiguity analogous to disambiguating the fraud-proof identifier with the unused `stateTransitionIndex`.

### Proof of Concept
1. Alice creates access key `K` on her account at block height `h0`.
2. Alice signs `tx_stale` with `nonce = h0 * 1_000_000 - 1` (valid: greater than the key's current low nonce, below the height-based upper bound), but does **not** submit it — she hands it to Bob as part of an off-chain agreement, or simply keeps it as a "pre-authorized" fallback transaction.
3. Shortly after (same or nearby block height `h1 ≈ h0`), Alice submits `DeleteKey(K)` followed by `AddKey(K)` (same public key) to rotate her credentials, believing this invalidates any outstanding signed transactions under `K`.
4. Per `add_regular_key`, the new key's nonce is seeded to `(h1 - 1) * 1_000_000` [9](#0-8) , which is lower than `tx_stale`'s nonce (`h0 * 1_000_000 - 1` ≈ `(h1-1)*1_000_000` range or higher, depending on the exact gap Alice chose).
5. Bob (or Alice's own leaked copy) submits `tx_stale`. `verify_nonce` passes: `tx_nonce > current_nonce` (new seed) and `tx_nonce < upper_bound` at inclusion height [10](#0-9) . The transaction executes even though Alice rotated the key specifically to prevent this.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}

    state_update: &mut TrieUpdate,
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    add_key: &AddKeyAction,

    if get_access_key(state_update, account_id, &add_key.public_key)?.is_some() {
        result.result = Err(ActionErrorKind::AddKeyAlreadyExists {
            account_id: account_id.to_owned(),
            public_key: add_key.public_key.clone().into(),
        }
        .into());
        return Ok(());
    }

    let fee_config = &apply_state.config.fees;

    if let Some(gas_key_info) = add_key.access_key.gas_key_info() {
        add_gas_key(
            fee_config,

            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            gas_key_info,
            apply_state.block_height,
        )?;

        add_regular_key(
            fee_config,
            state_update,
            account,
            account_id,
            &add_key.public_key,
            &add_key.access_key,
            apply_state.block_height,
        )?;
    }

    Ok(())
}

fn add_regular_key(
    fee_config: &RuntimeFeesConfig,
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    public_key: &PublicKey,
    access_key: &AccessKey,
    block_height: BlockHeight,
) -> Result<(), StorageError> {
    let mut access_key = access_key.clone();
    access_key.nonce = initial_nonce_value(block_height);
    set_access_key(state_update, account_id.clone(), public_key.clone(), &access_key);

    account.set_storage_usage(
        account
            .storage_usage()
            .checked_add(access_key_storage_usage(fee_config, public_key, &access_key))
            .ok_or_else(|| {
                StorageError::StorageInconsistentState(format!(
                    "Storage usage integer overflow for account {}",
                    account_id
                ))
            })?,
    );
    Ok(())
}

/// Verify that the transaction nonce is valid.
fn verify_nonce(
    tx_nonce: Nonce,
    current_nonce: Nonce,
    block_height: Option<BlockHeight>,
    nonce_mode: NonceMode,
) -> Result<(), InvalidTxError> {
    match nonce_mode {
        NonceMode::Monotonic => {
            if tx_nonce <= current_nonce {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
        NonceMode::Strict => {
            if !current_nonce.checked_add(1).is_some_and(|expected| tx_nonce == expected) {
                return Err(InvalidTxError::InvalidNonce { tx_nonce, ak_nonce: current_nonce });
            }
        }
    }
    if let Some(height) = block_height {
        let upper_bound = height
            .saturating_mul(near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER);
        if tx_nonce >= upper_bound {
            return Err(InvalidTxError::NonceTooLarge { tx_nonce, upper_bound });
        }
    }
    Ok(())
}
