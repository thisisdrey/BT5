### Title
Unauthenticated `HandshakeAccept`/`StackerDBHandshakeAccept` mutates peer identity and connection state before any signature check - ([File: stackslib/src/net/chat.rs, stackslib/src/net/connection.rs])

### Summary
`ConnectionInbox::consume_payload_known_length` only verifies a message's `Preamble.signature` when `self.public_key` is already `Some(..)` [1](#0-0) . For a brand-new outbound `ConversationP2P` (pre-handshake), `self.public_key` is `None`, so this transport-layer check is skipped for every message type, including `HandshakeAccept`/`StackerDBHandshakeAccept`. Unlike the `Handshake` path, which explicitly re-checks the signature in `validate_handshake` via `message.verify_secp256k1(&handshake_data.node_public_key)` before mutating any state, `handle_unauthenticated_control_message` routes `HandshakeAccept`/`StackerDBHandshakeAccept` straight to `handle_handshake_accept` guarded only by `is_solicited(msg)` [2](#0-1) , which is a sequence-number/expectation check, not a cryptographic one.

### Finding Description
The equality the question asks to validate is: *every field consumed from `msg.payload` before dispatch == a field covered by a verified `Preamble.signature`*. This equality holds for the `Handshake` message type (the payload's `node_public_key` is checked against `message.verify_secp256k1` before any state update), but it does **not** hold for `HandshakeAccept` / `StackerDBHandshakeAccept` on a connection whose `self.public_key` is still `None`:

- `consume_payload_known_length` gates `protocol.verify_payload_bytes(pubk, preamble, buf_bytes)` behind `if let Some(ref pubk) = self.public_key` [1](#0-0) . On a fresh connection this is `None`, so the message is fully parsed and handed to the protocol dispatcher with **zero signature verification**.
- `handle_unauthenticated_control_message` dispatches `HandshakeAccept`/`StackerDBHandshakeAccept` to `handle_handshake_accept` solely conditioned on `solicited` (i.e., that this reply's sequence number matches an outstanding request tracked by this same TCP connection object), not on any signature or proof-of-key-possession check [2](#0-1) .
- `handle_handshake_accept` calls `update_from_handshake_data`, which sets `self.public_key`, `peer_version`, `network_id`, `services`, and updates connection stats (e.g. `last_contact_time`, `peer_heartbeat`) directly from the attacker-supplied `HandshakeAcceptData`/`HandshakeData`, without ever confirming the sender actually controls the private key for the `node_public_key` it claims.

By contrast, `validate_handshake` (invoked for the `Handshake` type) explicitly performs `message.verify_secp256k1(&handshake_data.node_public_key)` before any such state is committed. That symmetric proof-of-possession check is absent on the `HandshakeAccept` path, so any party that ends up as the TCP endpoint of an outbound connection the victim node initiates (e.g., an attacker-controlled peer that got itself gossiped/dialed) can send a garbage-signed `HandshakeAccept` claiming an arbitrary public key and have it accepted as this connection's authenticated identity.

### Impact Explanation
This is an unauthenticated write to `ConversationP2P` session state: the connection's peer identity (`public_key`, `node_public_key`), protocol parameters (`peer_version`, `network_id`, `services`), and liveness/heartbeat stats can all be set from a payload with no valid signature. Once `self.public_key` is set this way, subsequent traffic on the connection is "verified" against a key the attacker chose, effectively letting the attacker impersonate any identity to this connection without ever proving key ownership — matching the Critical category of "unauthenticated/unauthorized write to state" on a `ConversationP2P` object.

### Likelihood Explanation
The attacker needs to be the answering peer of a TCP connection the victim dials (a `ConversationP2P` in the pre-handshake, `public_key == None` state) and needs the reply's sequence number to match the victim's outstanding handshake request (`is_solicited`), which is trivial since the attacker is directly responding to that same request. No secrets, privileged role, or local access are required — this fits the allowed "attacker runs their own peer" model. This is repeatable per new outbound connection/handshake attempt.

### Recommendation
Add an explicit signature check for `HandshakeAccept`/`StackerDBHandshakeAccept` analogous to `validate_handshake`'s `message.verify_secp256k1(&handshake_data.node_public_key)`, verifying the reply's signature against the `node_public_key` embedded in its own `HandshakeAcceptData` before calling `update_from_handshake_data` or mutating any connection stats.

### Proof of Concept
Rust test in `stackslib/src/net/chat.rs` (or `connection.rs`) test module:
1. Construct a `ConversationP2P` with `self.connection.public_key = None` in the "awaiting handshake accept" state (populate the outbox/expectation table so `is_solicited` returns `true` for a chosen `seq`).
2. Craft a `StacksMessage` with `StacksMessageType::HandshakeAccept(HandshakeAcceptData { handshake: HandshakeData { node_public_key: <arbitrary key>, .. }, .. })`, sign the `Preamble` with an unrelated/garbage key (or leave signature bytes zeroed).
3. Feed it through `chat_conn.recv_data` -> `handle_unauthenticated_control_message`.
4. Assert that `conversation.connection.public_key` is `None` and `conversation.stats.last_contact_time`/`peer_heartbeat` are unchanged after processing — this assertion should **fail** with current code, demonstrating the state is mutated before/without a valid signature check.
