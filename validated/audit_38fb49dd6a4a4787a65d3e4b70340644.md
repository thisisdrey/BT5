Audit Report

## Title
Stale `announce`d proxy calls survive `remove_proxy` and can be executed against re-authorized delegates - (File: `substrate/frame/proxy/src/lib.rs`)

## Summary
`pallet_proxy`'s `Announcements::<T>` storage keys pending calls only by `(delegate, real, call_hash)` with no binding to the specific `ProxyDefinition` (proxy type/delay) active at announcement time. `remove_proxy_delegate` removes the `ProxyDefinition` from `Proxies` storage but never touches `Announcements`, so a previously announced call remains pending indefinitely and can be executed with zero delay the moment the same delegate is re-authorized on the same `real` account.

## Finding Description
`Pallet::announce` inserts an `Announcement { real, call_hash, height }` into `Announcements::<T>` keyed by `delegate`, requiring only that the caller is currently a delegate of `real` at announce time: [1](#0-0) 

`proxy_announced` re-derives the *current* `ProxyDefinition` via `find_proxy(&real, &delegate, force_proxy_type)` and validates the announcement only against `real`, `call_hash`, and whether `now - height >= def.delay` using the *current* definition's delay — it never checks whether the definition active now is the same one under which the call was originally announced: [2](#0-1) 

`remove_proxy_delegate` removes the matching `ProxyDefinition` from `Proxies::<T>` and adjusts the deposit, but performs no corresponding lookup or purge in `Announcements::<T>` for that `(delegator, delegatee)` pair: [3](#0-2) 

Only `remove_announcement` (called by the delegate) and `reject_announcement` (called by `real`) purge entries from `Announcements::<T>` via `edit_announcements`: [4](#0-3) 

Because `Announcements` is never cleared automatically by `remove_proxy`/`remove_proxy_delegate`, a stale `Announcement.height` remains keyed by `delegate`. If the same `delegate` is later re-added as a proxy for the same `real` (even with a different `proxy_type`/`delay`), `find_proxy` succeeds against the new relationship and the delay check `now.saturating_sub(ann.height) < def.delay` is trivially false (since a long time has elapsed since the original, now-irrelevant announcement), allowing `proxy_announced` to execute the old call instantly, with no genuine review window under the newly established relationship. This is confirmed as accurate by direct reading of the current pallet source: `announce`, `proxy_announced`, `remove_announcement`, `reject_announcement`, and `remove_proxy_delegate` in `substrate/frame/proxy/src/lib.rs`.

The corrupted/unbound value is the `Announcement.height` record in `Announcements::<T>` keyed by `delegate` — it is never invalidated when the specific `(real, delegate)` `ProxyDefinition` it was made under is revoked via `remove_proxy`.

## Impact Explanation
This is unauthorized execution / origin escalation against the intended safety guarantee of the delay-based announcement mechanism: `real` believes revoking a proxy (`remove_proxy`) neutralizes any pending announced call from that delegate, but the announcement persists silently. If `real` later re-establishes any proxy relationship with the same delegate — a realistic pattern (re-trusting a service, rotating a shared bot/exchange delegate account) — the delegate can immediately execute the old, unreviewed call via `proxy_announced` with no fresh delay window, potentially transferring funds or performing other state-changing calls depending on the granted `ProxyType`. This matches the "unauthorized execution or origin escalation" and "runtime bugs that compromise intended behavior" categories for the live-scope program.

## Likelihood Explanation
The exploit path uses only ordinary, unprivileged public extrinsics (`add_proxy`, `announce`, `remove_proxy`, `add_proxy` again, `proxy_announced`) with no privileged actor, leaked keys, or malicious node/validator/relayer involvement. The only precondition — `real` re-adding the same delegate account after revocation — is a plausible real-world pattern, and the delegate fully controls the timing of the announce and eventual execution steps. Storage cleanup of `Announcements` is never automatic, so the stale entry persists indefinitely until `real` manually calls `reject_announcement`, which they have no obvious reason to do after already calling `remove_proxy`.

## Recommendation
When `remove_proxy_delegate` (and any bulk-removal path such as `remove_all_proxy_delegates` for `real`) removes a `ProxyDefinition`, also purge matching `Announcements::<T>` entries for that `(delegate, real)` pair and refund the associated deposit. Alternatively, bind each `Announcement` to a snapshot of the `ProxyDefinition` (proxy_type + delay + a relationship-generation counter) at announce time, and have `proxy_announced` reject execution if the current definition does not match the one recorded at announcement time.

## Proof of Concept
Using existing pallet extrinsics (adaptable as a `#[test]` in `substrate/frame/proxy/src/tests.rs`):
```rust
// 1. real=1 grants delegate=2 a proxy with delay=1
assert_ok!(Proxy::add_proxy(RuntimeOrigin::signed(1), 2, ProxyType::Any, 1));

// 2. delegate announces a dangerous call
let call = Box::new(call_transfer(6, 1000));
let call_hash = BlakeTwo256::hash_of(&call);
assert_ok!(Proxy::announce(RuntimeOrigin::signed(2), 1, call_hash));

// 3. real revokes the proxy, believing this cancels the pending call
assert_ok!(Proxy::remove_proxy(RuntimeOrigin::signed(1), 2, ProxyType::Any, 1));

// Announcement is still present in storage
assert!(Announcements::<Test>::get(2).0.iter().any(|a| a.call_hash == call_hash));

// time passes well beyond the original delay
frame_system::Pallet::<Test>::set_block_number(100);

// 4. real re-adds delegate 2 as proxy for an unrelated reason
assert_ok!(Proxy::add_proxy(RuntimeOrigin::signed(1), 2, ProxyType::Any, 1));

// 5. delegate immediately executes the stale, previously-revoked announcement
// with no fresh delay/review window
assert_ok!(Proxy::proxy_announced(RuntimeOrigin::signed(0), 2, 1, None, call));
```
This demonstrates that `remove_proxy` does not invalidate previously announced calls, allowing them to be executed the moment the same delegate/real relationship is re-established, bypassing the delay-review safeguard.

		pub fn proxy_announced(
			origin: OriginFor<T>,
			delegate: AccountIdLookupOf<T>,
			real: AccountIdLookupOf<T>,
			force_proxy_type: Option<T::ProxyType>,
			call: Box<<T as Config>::RuntimeCall>,
		) -> DispatchResult {
			ensure_signed(origin)?;
			let delegate = T::Lookup::lookup(delegate)?;
			let real = T::Lookup::lookup(real)?;
			let def = Self::find_proxy(&real, &delegate, force_proxy_type)?;

			let call_hash = T::CallHasher::hash_of(&call);
			let now = T::BlockNumberProvider::current_block_number();
			Self::edit_announcements(&delegate, |ann| {
				ann.real != real ||
					ann.call_hash != call_hash ||
					now.saturating_sub(ann.height) < def.delay
			})
			.map_err(|_| Error::<T>::Unannounced)?;

			Self::do_proxy(def, real, *call);

			Ok(())
		}

	pub fn remove_proxy_delegate(
		delegator: &T::AccountId,
		delegatee: T::AccountId,
		proxy_type: T::ProxyType,
		delay: BlockNumberFor<T>,
	) -> DispatchResult {
		Proxies::<T>::try_mutate_exists(delegator, |x| {
			let (mut proxies, old_deposit) = x.take().ok_or(Error::<T>::NotFound)?;
			let proxy_def = ProxyDefinition {
				delegate: delegatee.clone(),
				proxy_type: proxy_type.clone(),
				delay,
			};
			let i = proxies.binary_search(&proxy_def).ok().ok_or(Error::<T>::NotFound)?;
			proxies.remove(i);
			let new_deposit = Self::deposit(proxies.len() as u32);
			if new_deposit > old_deposit {
				T::Currency::reserve(delegator, new_deposit - old_deposit)?;
			} else if new_deposit < old_deposit {
				T::Currency::unreserve(delegator, old_deposit - new_deposit);
			}
			if !proxies.is_empty() {
				*x = Some((proxies, new_deposit))
			}
			Self::deposit_event(Event::<T>::ProxyRemoved {
				delegator: delegator.clone(),
				delegatee,
				proxy_type,
				delay,
			});
			Ok(())
		})
	}
