### Title
Permissioned relayer / gas-starved callback can permanently brick a `near-wallet-contract` eth-implicit wallet by leaving `has_in_flight_tx` stuck `true` - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract::rlp_execute` gates all future meta-transactions on a single boolean, `has_in_flight_tx`, which is only ever cleared inside one of the contract's private callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`). Any unprivileged relayer that submits the `rlp_execute` NEAR transaction controls the total prepaid gas attached to it. If that relayer under-funds the gas budget so that the final callback receipt runs out of gas *after* `self.has_in_flight_tx = false;` has executed but before the receipt finishes, the whole receipt fails and NEAR rolls back every state mutation the receipt made — including the reset of `has_in_flight_tx`. The flag is left permanently `true`, and `rlp_execute` will thereafter always short-circuit with "transaction already in progress," permanently freezing the wallet owner's ability to move funds/act through their eth-implicit account.

### Finding Description
`rlp_execute` is public and can be invoked by anyone holding the RLP-encoded, Ethereum-signed transaction (the relayer role is explicitly permissionless/untrusted in this design, `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:88-128`). On success it sets `self.has_in_flight_tx = true` and returns a `Promise` chain; the invariant documented at lines 48-53 requires the flag to become `false` again only inside a callback.

Every callback resets the flag as its very first statement: [1](#0-0) [2](#0-1) [3](#0-2) 

The gas reserved for these callbacks is computed from user/relayer-controlled values, e.g.: [4](#0-3) [5](#0-4) 

If the relayer attaches a total gas amount to the outer `rlp_execute` call that is just barely enough to create the promise chain but insufficient for the callback's actual computation (e.g. the two-hop NEP-141 `storage_deposit` + `ft_transfer` construction, or the refund-transfer branch inside `rlp_execute_callback` at lines 296-312), the callback receipt exhausts its allotted gas mid-execution. Per NEAR's execution model, a function-call action that fails (including "Exceeded the prepaid gas") makes the entire action receipt fail, and a failed receipt's state changes are rolled back in full: [6](#0-5) [7](#0-6) 

Because `self.has_in_flight_tx = false;` was executed inside that same now-rolled-back receipt, the persisted state still has `has_in_flight_tx == true`. There is no other code path capable of resetting it (the check is only ever cleared inside these same callbacks), so every subsequent call to `rlp_execute` is rejected forever: [8](#0-7) 

### Impact Explanation
This permanently freezes the wallet: the eth-implicit account's owner can no longer use `rlp_execute` for any Near action (transfers, ERC-20 style transfers, key management) mediated through this contract, since every call returns the "transaction already in progress" error indefinitely. Any funds or access whose movement depends on this entry point become permanently locked, matching the "permanent freezing of funds" impact category. The action is triggerable by an ordinary, unprivileged relayer (no special role beyond submitting a transaction with the victim's already-signed RLP payload and insufficient attached gas), directly analogous to the external report's "unprivileged/permissioned actor sets something that makes future calls always revert, locking depositor/vault funds."

### Likelihood Explanation
Any account can call `rlp_execute` for a given target wallet as long as it has the RLP bytes (this is inherent to the relayer model documented in `docs/architecture/how/meta-tx.md`). Constructing a transaction with gas fine-tuned to exhaust exactly inside a specific callback (particularly the multi-hop NEP-141 branch, which performs two chained cross-contract calls plus JSON formatting/serialization inside the callback) is a matter of careful/adversarial gas budgeting, not a race condition or privileged access, making this a straightforward attack path once identified. It could also occur non-maliciously from a poorly configured relayer, but it can equally be weaponized by an attacker who wants to grief a specific wallet owner (e.g. by front-running as the transaction submitter or by acting as the wallet's own designated relayer).

### Recommendation
Do not treat `has_in_flight_tx` reset as safe merely because the callback function contains the resetting statement first. Instead, ensure the flag is reset at a `PROMISE-independent` layer that cannot be rolled back with the rest of the callback's business logic — e.g., use a two-receipt pattern (a trivial guaranteed-to-succeed callback dedicated purely to clearing the flag, run with minimal/guaranteed static gas independent from the variable-cost business logic), or enforce a strict minimum-gas requirement in `rlp_execute`/`inner_rlp_execute` sufficient to guarantee the heaviest callback branch (NEP-141 double hop) cannot run out of gas, rejecting the transaction up front instead of allowing partial execution and rollback of the flag reset.

### Proof of Concept
1. Wallet owner signs (off-chain) an Ethereum-style transaction representing an ERC-20 transfer (`EthEmulationKind::ERC20Transfer`) to an unregistered recipient, so execution goes through `nep_141_storage_balance_callback`'s two-hop promise branch (`runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs:239-269`).
2. An unprivileged relayer submits `rlp_execute(target, tx_bytes_b64)` attaching only just enough total prepaid gas for `rlp_execute` + the `storage_balance_of` lookup + entry into `nep_141_storage_balance_callback`, but not enough for the callback to fully build and dispatch the `storage_deposit` + `ft_transfer` promise batch and its own trailing `.then(ext.rlp_execute_callback(...))`.
3. `nep_141_storage_balance_callback` executes: `self.has_in_flight_tx = false;` runs first (line 202), then the function runs out of allotted gas while constructing the chained promise (lines 255-268), causing the callback's action receipt to fail with an out-of-gas error.
4. Per NEAR's rollback semantics, the failed receipt's state changes — including the flag reset — are discarded; on-chain state keeps `has_in_flight_tx == true`.
5. All subsequent calls to `rlp_execute` for this wallet immediately return `"Error: transaction already in progress, please try again later."` (lines 97-105) forever, since no further path can clear the flag.
