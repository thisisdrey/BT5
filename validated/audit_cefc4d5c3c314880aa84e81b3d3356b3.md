### Title
`extend_with_inventories` never validates `response.block_id` against the requested `index_block_hash` before indexing `self.inventories` - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_inventories` stores a decoded `GetAttachmentsInvResponse` under the key derived from the *request* (`contract_id`, `pages`, `index_block_hash`) without ever comparing it to the `block_id` field embedded in the response itself. A remote peer answering a `/v2/attachments/inv` request can therefore return inventory bits it computed for an arbitrary/different tip, and those bits get filed under the requester's target `index_block_hash`, corrupting the mapping that `get_prioritized_attachments_requests` relies on to decide whether an attachment exists for that tip.

### Finding Description
The request key used to index inventories is built purely from the outgoing request: [1](#0-0) 

`extend_with_inventories` decodes the HTTP response and inserts it into `self.inventories` keyed by `request.key()` — it never reads or checks `response.block_id` at all: [2](#0-1) 

The `inventories` map itself is typed `(QualifiedContractIdentifier, Vec<u32>, StacksBlockId) -> HashMap<UrlString, GetAttachmentsInvResponse>`, where the `StacksBlockId` component comes from the *requested* `index_block_hash`, not from anything the peer asserts inside the payload: [3](#0-2) 

Later, `get_prioritized_attachments_requests` iterates `self.inventories` by this same key and inspects `response.pages` bitmaps directly to decide whether a peer "has" a given attachment, with no reference back to `response.block_id`: [4](#0-3) 

So a malicious/misbehaving peer that receives a request for `index_block_hash = IBH_A` can reply with a `GetAttachmentsInvResponse` whose internal `block_id` field is `IBH_B` (or whatever it wants) along with `pages` bitmaps that were actually computed for `IBH_B`'s atlas state (or simply fabricated). The client code accepts and stores this response keyed under `IBH_A` unconditionally, since there is no equality assertion `response.block_id == request.index_block_hash` anywhere in `extend_with_inventories`. This breaks the invariant "inventory bits recorded under key IBH == inventory bits the responding peer computed for that same IBH."

### Impact Explanation
This lets a single unprivileged remote peer feed false attachment-presence/absence bits for a given `index_block_hash` to a syncing node. Concretely:
- If the peer claims bit=0 (missing) for an attachment the node actually needs at `IBH_A`, the node's `get_prioritized_attachments_requests` will skip requesting it from that peer, potentially causing that peer to be treated as not having data it should have (denial of an attachment fetch path), and if all peers are similarly manipulated the attachment never gets fetched for that tip.
- If the peer claims bit=1 (present) using bits computed for a different tip, the node will issue a follow-on `AttachmentRequest` to that peer; the actual attachment content is separately hash-verified via `content_hash` in `check_attachment_instances`/`decode_atlas_get_attachment`, so no wrong attachment bytes are durably stored as valid — but the node wastes a round trip and its temporary belief about attachment availability for `IBH_A` is now based on data computed for `IBH_B`, i.e., false inventory steering, matching the "steering a node off the tip via false inventory" High-severity category. This is remotely triggerable from a single crafted response and is repeatable per attachment batch.

### Likelihood Explanation
Any peer the node syncs Atlas attachments from (an outbound sync peer serving `/v2/attachments/inv`) can trigger this on every request it answers; no secret, signature, or privileged role is required — just answering the node's own outbound HTTP request with a crafted body. Precondition is simply that the node has queued an `AttachmentsInventoryRequest` to that peer, which happens routinely during normal Atlas attachment sync.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_inventories` (`stackslib/src/net/atlas/download.rs`), after `decode_atlas_attachments_inv_response()` succeeds, assert `response.block_id == request.index_block_hash` before inserting into `self.inventories`; treat a mismatch as a failed/faulty response (bump `report.bump_failed_requests()` and/or mark the peer faulty) rather than silently accepting it.

### Proof of Concept
Add a test in `stackslib/src/net/atlas/tests.rs` that:
1. Builds an `AttachmentsInventoryRequest` with `index_block_hash = IBH_A`.
2. Constructs a `BatchedRequestsResult` whose `succeeded` map contains that request mapped to a synthetic `StacksHttpResponse` encoding a `GetAttachmentsInvResponse { block_id: IBH_B, pages: [...bits...], .. }` (`IBH_B != IBH_A`).
3. Calls `AttachmentsBatchStateContext::extend_with_inventories` with this result.
4. Asserts on `context.inventories` — currently it will contain an entry keyed by `(contract_id, pages, IBH_A)` holding the response whose internal `block_id` is `IBH_B`, i.e., `context.inventories.get(&(contract_id, pages, IBH_A.clone())).unwrap().values().next().unwrap().block_id == IBH_B`, demonstrating the unguarded acceptance. A fixed implementation should reject this response (empty `inventories` map, or entry not present under `IBH_A`).

                .peers
                .get_mut(request.get_url())

                r

                report.bump_failed_requests();

                let peer_url = request.get_url().clone();

                        responses.into_mut().insert(peer_url, response);
