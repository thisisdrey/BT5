### Title
StackerDB chunk signature does not bind to a specific StackerDB contract, permitting cross-contract chunk replay - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`SlotMetadata::auth_digest()` — the value a StackerDB signer signs and which `try_replace_chunk`/`validate_received_chunk` verify — commits only to `(slot_id, slot_version, data_hash)`. It never includes the target smart contract identifier (`QualifiedContractIdentifier`) of the StackerDB the chunk is destined for. Any signature that is valid for slot `N` in one StackerDB replica is therefore also valid for slot `N` in *any other* StackerDB replica whose slot `N` happens to be owned by the same signer address — exactly the "token valid for context A also accepted in unrelated context B" pattern described in the reference advisory.

### Finding Description
`SlotMetadata::auth_digest()` computes: [1](#0-0) 

and `verify()`/`sign()` operate purely on this digest, with no contract/DB-scoping component: [2](#0-1) 

Server-side, `try_replace_chunk` fetches the *per-contract* `SlotValidation.signer` and checks the signature against it, but the digest being verified says nothing about which contract it was meant for: [3](#0-2) 

Likewise, the p2p unsolicited-push and HTTP POST paths call `verify()`/`try_replace_chunk()` with only `(smart_contract_id, slot_id)` used to *look up* the expected signer, not to bind it into what was signed: [4](#0-3) [5](#0-4) 

Because many StackerDB replicas in this codebase are populated from the *same* underlying signer set — e.g. the `.signer-<cycle>-0` / `.signer-<cycle>-1` "lane" contracts written together from one `NakamotoSignerEntry` list via `stackerdb-set-signer-slots` in `update_signers` — the same address commonly owns the same `slot_id` across multiple sibling contracts within a cycle: [6](#0-5) 

Given that, a signature legitimately produced by a signer for `.signer-N-0` slot `S` version `V` will also pass `SlotMetadata::verify()` for `.signer-N-1` slot `S` (or any other StackerDB where the same address owns slot `S` with an acceptable version/size), because the verified digest never encodes *which* contract it was scoped to. An attacker who observes one legitimately-signed chunk on the wire (p2p `StackerDBChunk`/`StackerDBPushChunk`, or the public `POST /v2/stackerdb/...` HTTP endpoint) can resubmit the identical `(slot_id, slot_version, sig, data)` tuple against a different `contract_id` and have it accepted as an authentic write there, subject only to the ordinary version/size/max-writes checks of that *other* replica — none of which detect that the message was authorized for a different StackerDB.

This is a direct analog of the reported bug class: the "live preview token" (here, the chunk's ECDSA signature over `auth_digest()`) authenticates a subject-independent fact ("this address signed this slot/version/hash") but omits the resource-scoping component (which contract/DB it is valid for), so it is accepted for unrelated resources it was never issued for.

### Impact Explanation
This allows an unprivileged network peer (or any client of the public stacker-db HTTP RPC) to write attacker-replayed (not attacker-forged, but misappropriated) chunk data into a StackerDB replica that the legitimate signer never intended it for, as long as the same signer address owns the corresponding slot in both replicas. Depending on which sibling/lane contracts a given signer set backs (e.g. two message-lane contracts per reward cycle, or slot assignments that persist unchanged across some cycle boundaries), this can inject unauthorized-but-validly-signed content into a StackerDB that downstream consumers (`libsigner`'s `SignerEvent`/`StackerDBEventDispatcher`) treat as authentic signer output for that specific contract/lane, potentially corrupting mock-signing/message-lane bookkeeping or replicating stale/foreign data as if it were freshly authored for that DB. This is a write-authorization scoping failure (state written under a signature that wasn't scoped to it), matching the "unauthorized write to state" class.

### Likelihood Explanation
Moderate. It requires: (1) observing a legitimately-signed chunk (trivial, since StackerDB chunk pushes/gets are broadcast/public and the HTTP `GET`/`POST` endpoints are unauthenticated), and (2) a target StackerDB contract where the same signer address occupies the same slot id, which is architecturally likely for contracts derived from the same reward-cycle signer set. No node secret, admin role, or other party's key is required — only replay of publicly-observable signed data against a different but plausible target contract.

### Recommendation
Include the target StackerDB smart-contract identifier (and, ideally, the burn/rc-consensus-hash "view" already carried alongside pushes) in `SlotMetadata::auth_digest()` so a signature is cryptographically bound to the specific StackerDB it authorizes writes for, e.g.:
```
hasher.update(contract_id.serialize()...);
hasher.update(self.slot_id.to_be_bytes());
hasher.update(self.slot_version.to_be_bytes());
hasher.update(self.data_hash.0);
```
This is a wire/consensus-adjacent format change and needs careful versioning/rollout (old vs new digest format) across `libstackerdb`, `stackslib/src/net/stackerdb`, and `libsigner`.

### Proof of Concept
1. Signer `S` legitimately signs and posts chunk `(slot_id=0, slot_version=5, data=D)` to `.signer-10-0`, where `S` owns slot 0 in `.signer-10-0`.
2. Attacker observes this chunk via the public `GET /v2/stackerdb/.../chunks/...` endpoint or via p2p `StackerDBChunk`/`StackerDBPushChunk` gossip (`stackslib/src/net/chat.rs` `make_stacker_db_getchunk_response`).
3. If `.signer-10-1` also assigns slot 0 to `S` (same-cycle sibling lane populated from the same `NakamotoSignerEntry` ordering) and its current version for slot 0 is `< 5`, attacker `POST`s the identical `(slot_id=0, slot_version=5, sig, data=D)` to `.signer-10-1` via `RPCPostStackerDBChunkRequestHandler`.
4. `try_replace_chunk` verifies `slot_desc.verify(&slot_validation.signer)` against `.signer-10-1`'s slot-0 signer (`S`), which succeeds because `auth_digest()` never encoded which contract `D` was meant for — the chunk is accepted and stored into `.signer-10-1` even though `S` never signed data intended for that contract.

Note: I could not fully verify from the available index whether `.signer-<cycle>-0` and `.signer-<cycle>-1` always assign identical slot-to-signer mappings for every reward cycle (the `.clar` boot contract sources `signers-0-xxx.clar`/`signers-1-xxx.clar` were not retrievable in full via the index), so the exact scope of exploitable sibling-contract pairs is not fully confirmed — a Devin session with full file access would be needed to confirm slot-assignment equivalence across those contracts.

    pub fn sign(&mut self, privkey: &StacksPrivateKey) -> Result<(), Error> {
        let auth_digest = self.auth_digest();
        let sig = privkey
            .sign(&auth_digest.0)
            .map_err(|se| Error::SigningError(se.to_string()))?;

        self.signature = sig;
        Ok(())
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }
