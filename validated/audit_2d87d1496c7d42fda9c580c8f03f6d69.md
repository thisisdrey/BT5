### Title
Position-wide `last-borrow-block` guard lets a dust borrow on a healthy debt asset block liquidation of an unrelated insolvent debt asset - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
The same-block-borrow guard in `liquidate` reads `last-borrow-block` from the whole position record rather than per debt-asset, so any borrow on any asset in the position resets this single field. An attacker holding two debt assets (one healthy, one insolvent) can issue a dust `u1` `borrow` on the healthy asset every block to trigger `ERR-LIQUIDATION-BORROW-SAME-BLOCK` and block liquidation of the unrelated insolvent debt, indefinitely delaying liquidation and increasing bad debt.

### Finding Description
In `liquidate`, the guard is:
```
(last-borrow-block (get last-borrow-block position))
(same-block-check (asserts! (not (is-eq last-borrow-block stacks-block-height)) ERR-LIQUIDATION-BORROW-SAME-BLOCK))
``` [1](#0-0) 

`position` is obtained from `get-liquidation-position`, which fetches the account's whole position record (single `last-borrow-block` field, not indexed by asset) from `.v0-market-vault get-position`: [2](#0-1) 

The position type itself carries a single `last-borrow-block: uint` field describing the whole position, alongside lists of collateral and debt entries per asset: [3](#0-2) 

`borrow` does not target this field with an asset-specific key — it operates on `asset-id` for balances/debt, but the guard's `last-borrow-block` is stored once per account/position in `v0-market-vault` (confirmed present as a single field returned by `get-position`, matching the 8 references found in `v0-market-vault.clar`). Since the guard check in `liquidate` reads this position-wide value regardless of which `debt-aid` is being liquidated, a `borrow` call on any asset (including a dust `u1` amount on a fully healthy, unrelated asset) updates the same field and causes `liquidate` calls against a completely different, insolvent debt asset to revert with `ERR-LIQUIDATION-BORROW-SAME-BLOCK` in that block.

Exploit flow:
1. Attacker's position has two debt assets: asset A (healthy) and asset B (insolvent/underwater).
2. Each block, attacker calls `borrow(A-ft, u1, ...)` — this passes health checks trivially since A is healthy and the amount is dust, and it updates the account's `last-borrow-block` to the current `stacks-block-height`.
3. Any liquidator calling `liquidate(borrower, coll, B-ft, ...)` in the same block hits the guard and reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK`, even though the borrow had nothing to do with asset B.
4. Repeating this every block indefinitely prevents liquidation of the insolvent asset B, allowing bad debt to accrue unchecked (interest accrual, price drift) while protecting the position from ever being liquidated on that leg.

No existing check narrows the guard to the specific `debt-aid` being liquidated, and no cap/rate-limit prevents an attacker from re-arming the guard every block at negligible cost (a `u1` borrow, one transaction per block).

### Impact Explanation
This breaks liquidation fairness/invariant and can be used to make an insolvent position permanently unliquidatable for as long as the attacker keeps repeating the dust borrow, causing accrued bad debt on the insolvent asset to grow past what collateral can cover, directly causing protocol insolvency when liquidation eventually can occur (if ever) or the position is abandoned. This matches the in-scope "protocol insolvency" Critical impact category.

### Likelihood Explanation
Preconditions are trivial and attacker-controlled: any account can open a two-debt-asset position (borrow small amounts of two assets), let one leg become insolvent (e.g., via price movement or intentional under-collateralization on a volatile asset), and then call `borrow` for `u1` on the healthy asset every block. Capital cost is a single dust borrow transaction per block plus keeping enough collateral to keep asset A healthy; no privileged access, oracle manipulation, or flashloan is required. This is fully repeatable and requires no special timing beyond calling `borrow` once per block.

### Recommendation
Track `last-borrow-block` per debt asset (e.g., a map keyed by `{account, asset-id}` or embedded per debt-list entry) instead of one position-wide field, and in `liquidate` check only the `last-borrow-block` for the specific `debt-aid` being liquidated. Alternatively, restrict the guard to only update/matter when the borrowed asset is the same as the asset targeted for liquidation.

### Proof of Concept
Clarinet/vitest simnet plan:
1. Set up a market with two debt-enabled assets A and B, and sufficient collateral for the position to support borrowing both.
2. Attacker account borrows a substantial amount of A and B such that B's position becomes insolvent (e.g., manipulate B's price feed downward within allowed bounds, or use an asset with high volatility already below `ltv-liq-partial` threshold) while A remains healthy.
3. In block N: attacker calls `borrow(A-ft, u1, none, none)` — assert it succeeds (`(ok true)`), and note `stacks-block-height`.
4. In the same block N: a second principal calls `liquidate(borrower, coll-ft, B-ft, debt-amount, min-collateral-expected, none, none)` — assert this reverts with `ERR-LIQUIDATION-BORROW-SAME-BLOCK` (`(err u400024)`).
5. Confirm that if step 3 (the dust borrow on A) is omitted, `liquidate` on B succeeds normally, proving that the dust borrow on the unrelated healthy asset — not any change to asset B — is what causes the revert.
6. Repeat steps 3–4 across multiple consecutive blocks to show the pattern is repeatable indefinitely, and optionally simulate interest accrual on B's debt over those blocks to quantify the growing bad debt that liquidators are prevented from recovering.
