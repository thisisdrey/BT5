## Title
Stale `PromiseYieldReceipt`/`PromiseYieldStatus`/yield-id mappings survive `remove_account`, letting a resumed/timed-out yield execute a self-call function against a re-created account - (File: `core/store/src/utils/mod.rs`)

## Summary
`remove_account` clears only `Account`, `ContractCode`, all `AccessKey`/`GasKeyNonce`, and `ContractData` entries for a deleted account, but never clears `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId`. The global `TrieKey::PromiseYieldTimeout` queue is not account-scoped and is drained unconditionally by `resolve_promise_yield_timeouts`, which only checks whether `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` still exists — a check that stays true across account deletion/recreation because the key was never removed.

## Finding Description
`remove_account` (`core/store/src/utils/mod.rs:505-575`) removes `TrieKey::Account`, `TrieKey::ContractCode`, all access keys/gas-key nonces, and `TrieKey::ContractData`, but the match arm list is exhaustive only for those prefixes; it contains no logic to iterate/remove `TrieKey::PromiseYieldReceipt{receiver_id,...}`, `TrieKey::PromiseYieldStatus{receiver_id,...}`, `TrieKey::YieldIdToDataId{receiver_id,...}`, or `TrieKey::DataIdToYieldId{receiver_id,...}` even though `TrieKey::get_account_id` (`core/primitives/src/trie_key.rs:590-618`) explicitly ties all four of these key variants to `receiver_id`, confirming they belong to that account's data domain and were simply missed.

`action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` and then sets `*account = None`; it performs no additional cleanup of pending yields.

Meanwhile, `promise_yield_create` (`runtime/near-vm-runner/src/logic/logic.rs:3660-3718`) lets any account create a `PromiseYield` receipt targeting itself (`receiver_id == predecessor_id`) with an arbitrary `method_name`/`arguments` FunctionCall action baked in at creation time (`ext.create_promise_yield_receipt`, `runtime/runtime/src/ext.rs:353-369`). When this local/instant receipt is processed, `set_promise_yield_receipt` (`core/store/src/utils/mod.rs:200-212`) stores the full `Receipt` (including its embedded FunctionCall action) under `TrieKey::PromiseYieldReceipt{receiver_id, data_id}`, and `enqueue_promise_yield_timeout` (`core/store/src/utils/mod.rs:181-198`) inserts a `PromiseYieldTimeout{account_id, data_id, expires_at}` entry into the **global**, index-keyed timeout queue (`TrieKey::PromiseYieldTimeout{index}`), independent from any account-scoped state.

If the account is deleted (`DeleteAccountAction`) before the yield resolves or times out, `remove_account` leaves `PromiseYieldReceipt`, `PromiseYieldStatus`, and any `YieldIdToDataId`/`DataIdToYieldId` mappings intact in the trie. If the same account id is later re-created (which is legal under NEAR's account model whenever the parent-account naming rule permits it, e.g., an attacker deleting and recreating one of its own sub-accounts, or the parent TLA owner recreating a name), the global timeout queue is oblivious to this: `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) walks the queue strictly by `expires_at`, and for every entry only checks `state_update.contains_key(&promise_yield_key, ...)` (`lib.rs:3051`) — i.e., whether `TrieKey::PromiseYieldReceipt{receiver_id, data_id}` still exists — before synthesizing a `PromiseResume` receipt destined to `queue_entry.account_id`. Because `remove_account` never deleted that key, `contains_key` returns true even after the account was deleted and re-created, so the stale receipt is resumed. The stored function call is a self-call (`predecessor_id == receiver_id == account_id`, per `docs/RuntimeSpec/Receipts.md` and `create_promise_yield_receipt`/`append_action_function_call_weight`), so it executes against whatever contract now occupies the re-created account with the trust level of a "self" call, calling attacker-chosen `method_name`/`arguments` recorded before deletion.

## Impact Explanation
This is an authorization-escalation / receipt-confusion primitive: an attacker who controls a sub-account name (or otherwise arranges deletion+recreation of an account, e.g. within their own namespace) can plant a dormant `PromiseYield` "self-call" that survives account deletion and later fires against the recreated account's new contract, invoking an attacker-chosen method name/arguments as if it were a legitimate self-call from that account — potentially triggering privileged, self-call-gated logic (owner-only functions, `assert_self()`-style guards) in the new occupant's contract. This maps to NEAR's "authorization escalation across accounts or promises" bounty category. Note: the specific "AddFullAccessKey" mechanism named in the prompt is not directly achievable — `promise_yield_create` can only embed a `FunctionCall` action (`ReceiptManager::create_promise_yield_receipt`, `runtime/runtime/src/receipt_manager.rs:148-165`), not an arbitrary `AddKey` action — so the resumed receipt cannot itself add a full-access key; the actual, verifiable exploit vector is the surviving self-call being executed against the re-created account's contract, not a direct `AddKey` bypass of `check_actor_permissions` (which correctly requires `actor_id == account_id` for `AddKey`/`DeleteAccount`/etc., `runtime/runtime/src/actions.rs:760-785`, and is unaffected here since the resumed FunctionCall action doesn't route through that gate the same way `AddKey` would).

## Likelihood Explanation
Preconditions: the attacker must be able to both create and delete the account in question, and arrange for it (or one under the same parent-naming authority) to be recreated with a new/victim contract before the yield's `expires_at` — realistically this is exploitable when the attacker controls the parent account (able to delete/recreate its own sub-accounts) and hands off the recreated name to another party (e.g. selling/leasing sub-account names, a documented near-protocol usage pattern), or self-targets a fresh redeploy on the same account id. This is inexpensive (no elevated privileges, ordinary transactions and a self-authored WASM contract) and repeatable, but requires a plausible business scenario where account names are deleted and reused/handed off within the yield's timeout window (yield timeout length is protocol-configured, generally on the order of a limited number of blocks), which somewhat narrows real-world likelihood without a concrete victim-facing flow.

## Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to also enumerate and remove all `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, and `TrieKey::DataIdToYieldId` entries scoped to the account being deleted (there should be raw-prefix iteration helpers analogous to `get_raw_prefix_for_access_keys`/`get_raw_prefix_for_contract_data`, or these need to be added). Additionally, `resolve_promise_yield_timeouts` should not treat `contains_key(promise_yield_key)` alone as proof that the same logical account instance still owns the yield; consider also removing/invalidating pending yields whenever `action_delete_account` runs (or storing a deletion-generation nonce in the account key so stale yields cannot resolve against a differently-generation'd, re-created account).

## Proof of Concept
Integration/test-loop test plan:
1. Deploy a contract to sub-account `y.parent-attacker.near` (attacker-controlled parent) that, on `some_method`, calls `promise_yield_create` targeting itself with `method_name = "self_privileged_action"`.
2. Submit a transaction invoking that method; advance one block so the `PromiseYield` receipt is processed and `TrieKey::PromiseYieldReceipt{y.., data_id}`, `TrieKey::PromiseYieldStatus`, and a `TrieKey::PromiseYieldTimeout` entry are all persisted (assert via `get_all_promise_yield_timeouts`/state inspection helpers as in `core/store/src/utils/test_utils.rs`).
3. Submit `DeleteAccountAction` for `y.parent-attacker.near`; assert the account, contract code, and access keys are gone from state, but directly query the trie and assert `TrieKey::PromiseYieldReceipt{y.., data_id}` (and `PromiseYieldStatus`) are still present — this demonstrates the gap in `remove_account`.
4. Recreate `y.parent-attacker.near` with a different ("victim") contract that defines `self_privileged_action` as an owner/self-gated privileged function (e.g., one that would normally only be safely callable by itself).
5. Advance blocks until `expires_at` for the surviving `PromiseYieldTimeout` entry is reached; assert (as in `test_simple_yield_timeout`, `test-loop-tests/src/tests/yield_timeouts.rs:337-384`) that a `PromiseResume` receipt is generated and delivered to `y.parent-attacker.near`, and that `self_privileged_action` executes on the new contract with `predecessor_id == receiver_id == y.parent-attacker.near` — i.e., the stale receipt's self-call executes against the re-created account, confirming the authorization-boundary violation described above.
