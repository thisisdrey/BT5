Confirmed: `HistoryBlockHashUtil.deploy` at `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java` is the exact structural analog of the reported bug class — a deterministic, pre-known contract address that anyone can pre-occupy before privileged/governance code writes to it, causing that write to be silently skipped.

### Title
Permissionless front-running of the fixed TIP-2935 `HISTORY_STORAGE_ADDRESS` permanently disables BlockHashHistory activation - (File: `framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java`)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 `BlockHashHistory` system contract at the hardcoded, publicly-known address `HISTORY_STORAGE_ADDRESS` [1](#0-0)  only when the `ALLOW_TVM_PRAGUE` governance proposal is executed by `ProposalService.process` [2](#0-1) . Because the target address is fixed and public (it must match Ethereum's EIP-2935 address byte-for-byte for cross-chain parity), any unprivileged account can, with an ordinary signed transaction, occupy that address (by deploying code there, or simply sending TRX to instantiate an EOA account and later having foreign code land there) before the proposal is voted through. `deploy()` explicitly checks for pre-existing code/contract metadata and silently no-ops if found, permanently skipping the intended system contract installation.

### Finding Description
The deploy logic is:
```java
public static void deploy(Manager manager) {
    if (manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)
        || manager.getContractStore().has(HISTORY_STORAGE_ADDRESS)) {
      logger.warn("TIP-2935: foreign state at {}, skipping deploy", ...);
      return;
    }
    ...
}
``` [3](#0-2) 

This is directly analogous to the Yield `Wand`/`JoinFactory` issue: a deterministic, permissionless-reachable target (there, a CREATE2 address computed from `asset`; here, a hardcoded canonical address) can be pre-occupied by any attacker with an ordinary transaction, causing the privileged deployment logic to detect an "already exists" condition and abort/skip, rather than deploying the intended contract. In the Yield case the mitigation was to switch from CREATE2 to CREATE so the address is unpredictable; in java-tron's case the address is *intentionally* fixed for EIP-2935 parity, so the same collision-avoidance defense (skip on foreign state) that protects consensus safety directly reproduces the DoS: once foreign code or contract metadata occupies the address, `deploy()` will forever skip and there is no retry path — the `ALLOW_TVM_PRAGUE` flag still flips to `1`, but `saveBlockHashHistoryInstalled` never gets set, so `HistoryBlockHashUtil.write()` also permanently no-ops for that block-hash-serving feature [4](#0-3) . `ProposalUtil.validator` also blocks any re-proposal of `ALLOW_TVM_PRAGUE` once it has been set to `1` [5](#0-4) , so there is no governance path to retry activation after a failed/skipped deploy — the feature is permanently disabled network-wide with no remediation short of a coordinated hard-fork code change (unlike the Yield case, where redeploying a new `JoinFactory`/`Wand` sufficed).

An attacker only needs to occupy the fixed address before the `ALLOW_TVM_PRAGUE` proposal executes. This can be done trivially and far in advance (well before Shanghai/Prague activation, which itself requires prior fork votes), e.g. by transferring TRX to `HISTORY_STORAGE_ADDRESS` to create a normal account there and then, once TVM constantinople-style contract-account upgrades apply, or more directly by triggering a CREATE/CREATE2 from a factory contract whose deterministic address computation happens to land there, or simply by deploying a smart contract whose sender+nonce (CREATE) hashes to this specific address — though the simplest and fully reachable path is `manager.getContractStore().has(...)`/`codeStore().has(...)` being satisfied by any account-creation transaction that ends up writing code/contract metadata at that exact 21-byte address, which — given the address is public knowledge published in the TIP itself — an attacker can target directly using a crafted CREATE2 factory deployment (see the repo's own `Create2Test`/`FreezeTest` demonstrating CREATE2 collision handling at attacker-chosen addresses) [6](#0-5) .

### Impact Explanation
If the address is squatted before `ALLOW_TVM_PRAGUE` activates, the TIP-2935 `BlockHashHistory` feature — providing on-chain historical block-hash serving relied on by rollups, bridges, and any contract expecting EIP-2935 parity with Ethereum — is permanently and silently disabled network-wide. Unlike the original Yield finding (where redeploying a new factory fixes it), here there is no governance retry path since `ALLOW_TVM_PRAGUE` cannot be re-proposed once set [5](#0-4) , making this a permanent denial-of-service against a chain-wide feature that would otherwise be depended upon by other on-chain/off-chain systems (bridges verifying historical block hashes), constituting a concrete "API the node/chain can no longer serve" condition.

### Likelihood Explanation
The target address is public (it must match the well-known EIP-2935 address for cross-chain compatibility) and the precondition (occupying it) is reachable by any unprivileged account issuing ordinary signed transactions well ahead of the SR governance vote for `ALLOW_TVM_PRAGUE`, which itself requires prior fork/Shanghai activation and thus is publicly anticipated in advance, giving attackers ample lead time to squat the address cheaply.

### Recommendation
Do not rely on a purely-derived/fixed address for a security/consensus-relevant system contract without a fallback activation mechanism. Options: (1) add a pre-activation reservation/lock on `HISTORY_STORAGE_ADDRESS` before the fork block that rejects any transaction targeting it, (2) allow `ALLOW_TVM_PRAGUE` (or a dedicated re-deploy proposal) to be re-proposed/retried if `BLOCK_HASH_HISTORY_INSTALLED` never got set despite `ALLOW_TVM_PRAGUE == 1`, or (3) detect and forcibly overwrite/reclaim the canonical address during hard-fork activation (accepting the loss of any squatted balance/state) rather than silently skipping installation forever.

### Proof of Concept
1. Prior to the SR vote that would set `ALLOW_TVM_PRAGUE = 1`, an attacker deploys (via ordinary CREATE/CREATE2 transactions available to any account) a contract or transfers TRX so that code/contract metadata ends up stored at `HISTORY_STORAGE_ADDRESS = 410000f90827f1c53a10cb7a02335b175320002935`.
2. SRs later pass the `ALLOW_TVM_PRAGUE` proposal; `ProposalService.process` calls `HistoryBlockHashUtil.deploy(manager)` [2](#0-1) .
3. `deploy()` finds `manager.getCodeStore().has(HISTORY_STORAGE_ADDRESS)` (or `contractStore().has(...)`) true, logs a warning, and returns without writing the `BlockHashHistory` bytecode/contract, and without setting `BLOCK_HASH_HISTORY_INSTALLED` [3](#0-2) , consistent with the covering test `HistoryBlockHashIntegrationTest#deploySkipsWhenForeignBytecodePresent`/`deploySkipsWhenForeignContractPresent` [7](#0-6) .
4. `ALLOW_TVM_PRAGUE` is now permanently `1` (per `ProposalUtil.validator`'s "has been valid, no need to propose again" guard [5](#0-4) ), so there is no way to retry the deployment; `write()` is a permanent no-op for the entire chain going forward [8](#0-7) .

  @Test
  public void deploySkipsWhenForeignBytecodePresent() {
    byte[] addr = HistoryBlockHashUtil.HISTORY_STORAGE_ADDRESS;
    byte[] foreignCode = new byte[]{0x60, 0x00};
    chainBaseManager.getCodeStore().put(addr, new CodeCapsule(foreignCode));

    HistoryBlockHashUtil.deploy(dbManager);

    assertArrayEquals(foreignCode,
        chainBaseManager.getCodeStore().get(addr).getData());
    assertFalse(chainBaseManager.getContractStore().has(addr));
    assertFalse(chainBaseManager.getAccountStore().has(addr));
  }

  @Test
  public void deploySkipsWhenForeignContractPresent() {
    byte[] addr = HistoryBlockHashUtil.HISTORY_STORAGE_ADDRESS;
    SmartContract foreign = SmartContract.newBuilder()
        .setName("NotBlockHashHistory")
        .setContractAddress(ByteString.copyFrom(addr))
        .setOriginAddress(ByteString.copyFrom(addr))
        .build();
    chainBaseManager.getContractStore().put(addr, new ContractCapsule(foreign));

    HistoryBlockHashUtil.deploy(dbManager);

    assertEquals("NotBlockHashHistory",
        chainBaseManager.getContractStore().get(addr).getInstance().getName());
    assertFalse(chainBaseManager.getCodeStore().has(addr));
    assertFalse(chainBaseManager.getAccountStore().has(addr));
  }
