Based on my review of this repository (the Go language toolchain and standard library source, not an application), there is no reachable analog to the Dokploy vulnerability. All `exec.Command`/`exec.CommandContext` call sites I found either:

- Pass arguments as a discrete argv slice with no shell interpretation (e.g. `buildCommand` in [1](#0-0)  and the VCS/module-fetch runners in [2](#0-1) , [3](#0-2) , and the build-shell runner [4](#0-3) ), or
- Are test-only/example code that invoke `/bin/sh -c` with hardcoded or self-generated strings, not attacker-influenced HTTP/RPC input (e.g. [5](#0-4) , [6](#0-5) , [7](#0-6) ).

The `os/exec` package itself is explicitly documented as never invoking a system shell or performing expansion, unlike Node's `exec`: [8](#0-7) . There is no comparable "server accepts a name parameter over an authenticated RPC endpoint and embeds it into a nested shell string executed via a privileged host context" pattern anywhere in this codebase — this repository is the Go compiler/runtime/stdlib source tree, not a web backend/PaaS service, so there is no `restoreBackupWithLogs`-style entry point to compare against.

### No Vulnerability found for this question.

func privesc(command string, args ...string) error {
	ctx, cancel := context.WithTimeout(context.Background(), time.Second*5)
	defer cancel()
	var cmd *exec.Cmd
	if runtime.GOOS == "darwin" {
		cmd = exec.CommandContext(ctx, "sudo", append([]string{"-n", command}, args...)...)
	} else if runtime.GOOS == "openbsd" {
		cmd = exec.CommandContext(ctx, "doas", append([]string{"-n", command}, args...)...)
	} else {
		cmd = exec.CommandContext(ctx, "su", highPrivUser, "-c", fmt.Sprintf("%s %s", command, strings.Join(args, " ")))
	}
	_, err := cmd.CombinedOutput()
	return err
}
