### Title
Cross-contract signature replay in StackerDB chunk authentication due to missing contract-binding in `SlotMetadata::auth_digest` - (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest` (and therefore every chunk signature verified through `SlotMetadata::verify`) binds only to `slot_id`, `slot_version`, and `data_hash`. It never binds to the target StackerDB contract (`smart_contract`/`QualifiedContractIdentifier`). Because multiple StackerDB contracts share the identical signer→slot assignment (e.g. all `.signers-{0|1}-<message_id>` contracts for a given reward-cycle parity), a validly-signed chunk observed in one contract can be replayed unmodified into a different contract that the signer never intended it for. This is the same class of bug as the reported missing EIP-155 chain-ID check: an authentication token that is valid in one execution context is accepted in a different context because the context identifier is not part of what was signed.

### Finding Description
`SlotMetadata::auth_digest` computes the signed digest as: [1](#0-0) 

Verification recovers the public key from this same digest and only checks that the recovered address matches the expected signer for the *slot*, never for the *contract*: [2](#0-1) 

Both the write path (`StackerDBTx::try_replace_chunk`) and the network-receive path (`StackerDBs::validate_received_chunk`) only look up the signer/slot within the *target* contract and never verify that the chunk was authenticated *for* that specific contract: [3](#0-2) [4](#0-3) 

Crucially, the signer-slot assignment used by every `.signers-(0|1)-xxx` StackerDB contract for a given reward-cycle parity is drawn from the *same* page in the `.signers` boot contract — i.e. the same signer address occupies the same `slot_id` across every message-type contract of that parity: [5](#0-4) [6](#0-5) 

Because the signature covers only `(slot_id, slot_version, data_hash)` and not the contract identifier, a chunk that a signer legitimately signed and posted to one message-type contract (e.g. `signers-0-1` for `BlockResponse`) is a byte-for-byte valid, correctly-signed chunk for the *same slot_id* in a sibling message-type contract of the same parity (e.g. `signers-0-2` for `StateMachineUpdate`), as long as the slot_version constraint for that specific contract's independent version counter is satisfied. The public HTTP write endpoint performs no additional binding check before accepting the chunk: [7](#0-6) 

The unsolicited gossip-push path has the same gap and will also buffer/forward such a replayed chunk to the network: [8](#0-7) 

### Impact Explanation
This allows an unprivileged, remote attacker who has observed any publicly-broadcast StackerDB chunk (chunks are served/gossiped in the clear — StackerDB has no confidentiality) to replay it into a *different* message-type StackerDB contract for the same signer, as long as that contract's stored version for the slot is lower. The result is an unauthorized write of forged-context data into a StackerDB the signer never intended to write to, and this forged-context data will be relayed/propagated to other peers via the normal StackerDB inventory/push/pull mechanisms (`make_StackerDBChunksInv_or_Nack`, `handle_unsolicited_StackerDBPushChunk`). Downstream consumers that deserialize the contract's chunks expecting a specific message type (e.g. `MessageSlotID::StateMachineUpdate` vs `MessageSlotID::BlockResponse`) will either fail to parse (denial of read/consumption) or, worse, be misled into believing the signer emitted a specific protocol message for that context when they did not — directly analogous to "breaking validator/signer set accounting" cited in the source report. This matches the "unauthenticated/unauthorized write to state or StackerDB" / "network-wide propagation of forged data" impact tiers.

### Likelihood Explanation
High likelihood of exploitability: no secret key or privileged role is required — only observation of any one publicly-relayed, validly-signed chunk from a target signer, plus the ability to send a standard `POST /v2/stackerdb/{contract}/chunks` HTTP request or an unsolicited `StackerDBPushChunk` P2P message, both of which are unauthenticated remote-reachable interfaces. The only constraint is that the target contract's stored slot version must be below the replayed chunk's version, which is trivially true immediately after a signer's legitimate write to one contract when the sibling contract has not yet been advanced to that version.

### Recommendation
Bind the signed digest (`SlotMetadata::auth_digest`) to the target contract identifier (or an equivalent domain separator such as `smart_contract_id`/network id), so a chunk signature is only valid for the specific StackerDB it was created for. Concretely, add the contract's `QualifiedContractIdentifier` (or a stable hash of it) into the hash computed in `auth_digest`, and thread that context through `try_replace_chunk`/`validate_received_chunk`/`insert_chunk` so verification is contract-scoped rather than slot-scoped only.

### Proof of Concept
1. Signer `S` legitimately signs and posts chunk `C = {slot_id: 3, slot_version: 5, sig, data: D}` to StackerDB contract `signers-0-1` (message type `BlockResponse`). This chunk is publicly retrievable/observable via the normal GET chunks endpoint or via P2P gossip.
2. Attacker (no keys required) takes the exact same `C` and POSTs it (or relays it as an unsolicited `StackerDBPushChunk`) to `signers-0-2` (message type `StateMachineUpdate`) for the same reward-cycle parity, where slot 3 is also owned by `S` (same signer-slot page) and the current stored version there is `< 5`.
3. `try_replace_chunk`/`validate_received_chunk` recompute `auth_digest` from `(slot_id=3, slot_version=5, data_hash(D))`, recover `S`'s address, confirm it matches the expected signer for slot 3 in `signers-0-2`, and accept the write — even though `S` never authorized this data for the `StateMachineUpdate` context.
4. The forged-context chunk is now stored and gets propagated further via `make_StackerDBChunksInv_or_Nack`/push-chunk gossip to other peers, who will attempt to interpret `D` as a `StateMachineUpdate` message.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }
