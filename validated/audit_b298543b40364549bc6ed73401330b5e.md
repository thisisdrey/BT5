### Title
`handleCreateRelayRequest` trusts unauthenticated `RelayFromAddr`/`RelayToAddr` control-message fields to install relay state instead of verifying them against the sender's certificate-derived identity - (File: `relay_manager.go`)

### Summary
`relayManager.handleCreateRelayRequest` derives `from` and `target` directly from attacker-controlled `NebulaControl` message fields (`m.RelayFromAddr`/`m.RelayToAddr`) and uses them, unchecked, to create/complete relay routing state (`AddRelay`, `h.relayState.CompleteRelayByIP`) and to reply with a `CreateRelayResponse`. This mirrors the `RubiconRouter.withdrawForETH` bug: a value that is supposed to represent verified "ground truth" (there, the WETH actually transferred; here, the real sender identity established during the cert-verified handshake) is instead taken at face value from an untrusted party, and the receiving code proceeds to commit sensitive state changes based on it.

### Finding Description
In `relay_manager.go`, `handleCreateRelayRequest` only rejects `from` when it equals the local node's own address (self-relay guard): [2](#0-1) 

It never verifies that `from` (the claimed relay source) equals `h.vpnAddrs[0]`, i.e., the address that was cryptographically bound to host `h` during the handshake (`beginHandshake`/`continueHandshake`/`validatePeerCert`). [3](#0-2) [4](#0-3) 

Because `h` is only authenticated as controlling `h.vpnAddrs`, but `from`/`target` are taken from the message body without cross-checking against `h.vpnAddrs`, a fully-handshaked-but-malicious peer `h` can send a `CreateRelayRequest` claiming an arbitrary `RelayFromAddr` (e.g., a victim's vpn address it does not own). When this node is the relay target, it will call `AddRelay(..., from, ...)` and register a `TerminalType`/`Established` relay entry keyed by that spoofed `from` address: [5](#0-4) 

and when this node is acting as a middle-man relay, it forwards a `CreateRelayRequest` toward `target` on the attacker's behalf using the spoofed `from` value with no ownership check: [6](#0-5) 

The higher-level dispatcher `HandleControlMsg` only checks that `RelayFromAddr`/`RelayToAddr` are non-nil — it performs no identity binding either: [7](#0-6) 

### Impact Explanation
This allows an authenticated-but-malicious peer to poison relay routing state on a lighthouse/relay node by claiming to be the source of a relay for an address it does not control. This can be used to hijack relay routes intended for a legitimate victim vpn address (causing traffic destined to route through/for that address to be mis-registered against the attacker's hostinfo), effectively a remote state-poisoning attack that can enable relay-path hijacking or denial of relay service for the victim — the same class of "trust an unverified claim instead of validated ground truth" root cause as the WETH balance/transfer trust bug in the report.

### Likelihood Explanation
Any already-handshaked peer (which need not be compromised elsewhere, just a normal member of the mesh that chooses to send a malformed control message) can trigger this: it requires only sending a `Control`-type `NebulaControl_CreateRelayRequest` message with a forged `RelayFromAddr`, which is trivial to construct once any tunnel to the target/relay node exists.

### Recommendation
In `handleCreateRelayRequest` (and symmetrically in `handleCreateRelayResponse`), require that the claimed `RelayFromAddr` matches one of the entries in `h.vpnAddrs` (the certificate-verified identity of the sending `HostInfo`) before creating or completing any relay state, rejecting/logging the request otherwise instead of trusting the value taken from the wire.

### Proof of Concept
1. Node `A` completes a legitimate handshake with node `R` (a relay/lighthouse), so `R` records `hA.vpnAddrs = [10.0.0.5]`.
2. `A` sends `R` a `Control` message of type `NebulaControl_CreateRelayRequest` with `RelayFromAddr = 10.0.0.99` (a victim's real vpn address, not `A`'s) and `RelayToAddr = R`'s own address.
3. `R.relayManager.handleCreateRelayRequest` sees `target == R` (line 447), finds no existing relay for `from = 10.0.0.99` on `hA`, and calls `AddRelay(rm.l, hA, f.hostMap, 10.0.0.99, &m.InitiatorRelayIndex, TerminalType, Established)` — installing relay state for the victim's address bound to `A`'s hostinfo, without ever confirming `10.0.0.99` belongs to `A`.
4. `R` then replies with a `CreateRelayResponse` treating `A` as the authoritative relay endpoint for `10.0.0.99`, poisoning `R`'s relay routing for the victim address.

// validatePeerCert checks the peer certificate for self-connection and remote allow list.
// Returns the VPN addrs, whether any of them fall within one of our own VPN
// networks, and true if valid; false if rejected.
func (hm *HandshakeManager) validatePeerCert(via ViaSender, remoteCert *cert.CachedCertificate) ([]netip.Addr, bool, bool) {
	f := hm.f
	vpnNetworks := remoteCert.Certificate.Networks()

	// The cert package rejects host certs with no networks at parse time, so
	// reaching this state would mean an invariant was bypassed elsewhere.
	// Refuse explicitly so downstream code (which indexes vpnAddrs[0]) can't
	// panic if that invariant ever changes.
	if len(vpnNetworks) == 0 {
		f.l.Info("No networks in certificate",
			"from", via, "cert", remoteCert)
		return nil, false, false
	}

	vpnAddrs := make([]netip.Addr, len(vpnNetworks))
	anyVpnAddrsInCommon := false

	for i, network := range vpnNetworks {
		if f.myVpnAddrsTable.Contains(network.Addr()) {
			f.l.Error("Refusing to handshake with myself",
				"vpnNetworks", vpnNetworks,
				"from", via,
				"certName", remoteCert.Certificate.Name(),
				"certVersion", remoteCert.Certificate.Version(),
				"fingerprint", remoteCert.Fingerprint,
				"issuer", remoteCert.Certificate.Issuer(),
			)
			return nil, false, false
		}
		vpnAddrs[i] = network.Addr()
		if f.myVpnNetworksTable.Contains(network.Addr()) {
			anyVpnAddrsInCommon = true
		}
	}

	if !via.IsRelayed {
		if !f.lightHouse.GetRemoteAllowList().AllowAll(vpnAddrs, via.UdpAddr.Addr()) {
			f.l.Debug("lighthouse.remote_allow_list denied incoming handshake",
				"vpnAddrs", vpnAddrs, "from", via)
			return nil, false, false
		}
	}

	return vpnAddrs, anyVpnAddrsInCommon, true
}
