### Title
Unbounded per-address delegation index causes CPU-exhaustion via repeated prefix-scan + sort on every `getDelegatedResourceAccountIndexV2` / `getDelegatedResourceAccountIndex` query - (File: `chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java`)

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix()` (used by `getIndex()` and `getV2Index()`) rebuilds the full "from"/"to" account list for a queried address by performing a `prefixQuery` over **every** delegation record stored for that address, then sorting the entire result set by timestamp on **every single call**. Because a signed `DelegateResourceContract` transaction can create an unbounded number of distinct delegation-index entries under the same owner/receiver prefix for only 1 TRX of (recoverable) frozen balance per receiver, an attacker can cheaply inflate this per-address record set to a very large size and then repeatedly hit the read API to force expensive O(n) scan + O(n log n) sort work on every query — degrading node performance for a subsystem reachable by both an unprivileged transaction broadcaster and an anonymous API client. This mirrors the BIND CVE-2024-1737 bug class: unbounded growth of many records keyed to the same name/address causing performance degradation both when adding content and when serving queries for it.

### Finding Description
`DelegateResourceActuator`/`DelegateResourceProcessor`/`FreezeBalanceActuator` write new delegation index entries via `DelegatedResourceAccountIndexStore.delegateV2()` (or the legacy `delegate()`), keyed by `V2_FROM_PREFIX + owner + receiver` and `V2_TO_PREFIX + receiver + owner`: [1](#0-0) 

Nothing in the validate/execute path bounds how many distinct receiver addresses a single owner can delegate to; the only per-delegation constraint is a minimum of 1 TRX in delegated balance and that the receiver account must exist: [2](#0-1) [3](#0-2) 

There is no cap on the number of distinct `(owner, receiver)` pairs, unlike `VoteWitnessProcessor`, which explicitly caps votes at `MAX_VOTE_NUMBER`: [4](#0-3) 

When the index for an address is queried (e.g. via the `getdelegatedresourceaccountindexv2`/`getdelegatedresourceaccountindex` HTTP/gRPC endpoints), `getWithPrefix()` performs a full `prefixQuery` fetching **all** stored entries for that address, wraps them in an `ArrayList`, and sorts by timestamp — for both the "to" list and the "from" list — on every call, with no pagination or limit: [5](#0-4) 

This is functionally the same bug class as CVE-2024-1737: the amount of stored, attacker-controlled data associated with a single key (the owner/receiver address, analogous to BIND's hostname) grows unbounded, and both the write path (`delegateV2`, called on each delegation) and the read/query path (`getWithPrefix`, called on each API request) degrade as that data set grows, since the read path must re-scan and re-sort the entire set from scratch every time.

### Impact Explanation
Once an attacker has built up a large number of delegation-index entries for one address, every subsequent read query (`getdelegatedresourceaccountindex`, `getdelegatedresourceaccountindexv2` over HTTP/gRPC, and PBFT/Solidity mirrors of the same call) forces the full node to execute an O(n) LevelDB/RocksDB prefix scan plus an O(n log n) in-memory sort for that address. Because this endpoint is unauthenticated and can be called repeatedly and concurrently, an attacker can force sustained high CPU/I/O load on any full node, degrading its ability to serve legitimate JSON-RPC/gRPC/HTTP traffic — a node-availability impact consistent with the "no longer able to serve" criterion.

### Likelihood Explanation
Building the underlying state is cheap and fully reversible: each `DelegateResourceContract` only requires 1 TRX of frozen balance delegated to a distinct receiver account (which can later be un-delegated to recover the balance), and the transaction itself costs only ordinary bandwidth/energy fees. Since there is no on-chain limit on the number of distinct receivers per owner (unlike votes, which are capped by `MAX_VOTE_NUMBER`), an attacker with a modest amount of capital and many disposable receiver accounts can inflate the index to a large size over time, then repeatedly invoke the free, unauthenticated read API to trigger the expensive rebuild-and-sort path.

### Recommendation
- Add an explicit maximum number of distinct delegation-index entries per owner (or per owner/resource-type pair), analogous to `MAX_VOTE_NUMBER` for votes, enforced in `DelegateResourceActuator`/`DelegateResourceProcessor`/`FreezeBalanceActuator` validation.
- Avoid rebuilding and re-sorting the entire `to`/`from` list on every read in `getWithPrefix()`; maintain a bounded, incrementally-updated index (or paginate/limit the returned/scanned set) instead of a full `prefixQuery` + full sort per call.
- Consider rate-limiting or caching results of `getDelegatedResourceAccountIndex(V2)` queries per address to blunt repeated-query amplification.

### Proof of Concept
1. From an owner address, freeze balance for bandwidth/energy, then issue many `DelegateResourceContract` transactions (each delegating the minimum 1 TRX) to a large number of distinct, pre-created receiver addresses. Each transaction adds two new entries to `DelegatedResourceAccountIndexStore` under `V2_FROM_PREFIX+owner+receiver` and `V2_TO_PREFIX+receiver+owner` via `delegateV2()` — as demonstrated with 100 receivers in the existing test: [6](#0-5) 
2. Repeatedly call the `getdelegatedresourceaccountindexv2` (or `getdelegatedresourceaccountindex`) HTTP/gRPC endpoint for the owner address. Each call triggers `getWithPrefix()`, performing a full prefix scan and sort over the entire accumulated entry set: [5](#0-4) 
3. Scale the number of distinct receivers (thousands+) and issue concurrent repeated queries to measure sustained CPU/I/O degradation on the target full node.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;

  private void delegateResource(byte[] ownerAddress, byte[] receiverAddress, boolean isBandwidth,
                                long balance, boolean lock, long lockPeriod) {
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicPropertiesStore = chainBaseManager.getDynamicPropertiesStore();
    DelegatedResourceStore delegatedResourceStore = chainBaseManager.getDelegatedResourceStore();
    DelegatedResourceAccountIndexStore delegatedResourceAccountIndexStore = chainBaseManager
        .getDelegatedResourceAccountIndexStore();

    // 1. unlock the expired delegate resource
    long now = chainBaseManager.getDynamicPropertiesStore().getLatestBlockHeaderTimestamp();
    delegatedResourceStore.unLockExpireResource(ownerAddress, receiverAddress, now);

    //modify DelegatedResourceStore
    long expireTime = 0;
    if (lock) {
      expireTime = now + lockPeriod * BLOCK_PRODUCED_INTERVAL;
    }
    byte[] key = DelegatedResourceCapsule.createDbKeyV2(ownerAddress, receiverAddress, lock);
    DelegatedResourceCapsule delegatedResourceCapsule = delegatedResourceStore.get(key);
    if (delegatedResourceCapsule == null) {
      delegatedResourceCapsule = new DelegatedResourceCapsule(ByteString.copyFrom(ownerAddress),
          ByteString.copyFrom(receiverAddress));
    }

    if (isBandwidth) {
      delegatedResourceCapsule.addFrozenBalanceForBandwidth(balance, expireTime);
    } else {
      delegatedResourceCapsule.addFrozenBalanceForEnergy(balance, expireTime);
    }
    delegatedResourceStore.put(key, delegatedResourceCapsule);

    //modify DelegatedResourceAccountIndexStore
    delegatedResourceAccountIndexStore.delegateV2(ownerAddress, receiverAddress,
        dynamicPropertiesStore.getLatestBlockHeaderTimestamp());

    //modify AccountStore for receiver
    AccountCapsule receiverCapsule = accountStore.get(receiverAddress);
    if (isBandwidth) {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForBandwidth(balance);
    } else {
      receiverCapsule.addAcquiredDelegatedFrozenV2BalanceForEnergy(balance);
    }
    accountStore.put(receiverCapsule.createDbKey(), receiverCapsule);
  }
