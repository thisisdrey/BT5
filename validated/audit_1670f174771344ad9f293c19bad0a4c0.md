Based on my analysis, the strongest analog in java-tron is in the `ValidateMultiSign` and `BatchValidateSign` TVM precompiled contracts, where attacker-controlled offset/length words from smart-contract call data are used to index into arrays and byte buffers without bounds validation against the underlying data array.

### Title
Missing bounds validation on attacker-controlled offsets/lengths in ValidateMultiSign/BatchValidateSign precompiles enables out-of-bounds array access - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Apache NimBLE CVE stems from the "Add Source"/"Modify Source" BASS PDU parser trusting attacker-supplied length fields and using them to index/copy into fixed buffers without validating them against the actual received data size, causing OOB writes/reads. java-tron's `extractBytesArray` and `extractSigArray` helpers used by the `ValidateMultiSign` and `BatchValidateSign` precompiled contracts exhibit the same pattern: array-length and per-item offset/length values are read directly from attacker-controlled EVM call data words and used to compute array indices and byte-copy ranges without validating them against the bounds of `words`/`data`.

### Finding Description
`extractBytesArray` reads a length word `len = words[offset].intValueSafe()`, allocates `new byte[len][]`, then for each `i` reads `bytesOffset` and `bytesLen` directly from `words[offset + i + 1]` and `words[offset + bytesOffset + 1]` — both attacker-controlled — and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)`, which does `Arrays.copyOfRange(data, offset, offset + len)` with no check that `offset >= 0`, `offset + len <= data.length`, or that `offset + bytesOffset + 1 < words.length` before dereferencing `words[...]`. `extractSigArray` has the identical unguarded indexing pattern for the signature array path. [3](#0-2) 

Both `ValidateMultiSign.execute` and `BatchValidateSign.doExecute` call these helpers directly with a `words` array derived from raw EVM call data via `DataWord.parseArray(rawData)`, and the offsets passed in (`words[3].intValueSafe() / WORD_SIZE`, `words[1].intValueSafe() / WORD_SIZE`, `words[2].intValueSafe() / WORD_SIZE`) are themselves fully attacker-controlled words from the call data. ### Impact Explanation
A negative or out-of-range `bytesOffset`/`bytesLen`/array `len` value causes `Arrays.copyOfRange` to throw `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`, or excessively large `len` to attempt allocation of huge `byte[len][]` arrays (potential `OutOfMemoryError`). In `ValidateMultiSign`, only the inner permission-lookup block is wrapped in a `try/catch(Throwable)`, but the calls to `extractSigArray`/`extractBytesArray` themselves occur **before** that try block, so an uncaught runtime exception here propagates out of `execute()`. Since this precompile executes inside the TVM's execution path for every node validating the block, an unhandled exception during precompile execution can crash/halt transaction processing on all full nodes, or (if allocation-based) exhaust node memory — a node crash/halt or potential chain split if some nodes fail differently than others (e.g., due to available memory). [7](#0-6) 

### Likelihood Explanation
This is reachable by any unprivileged account: crafting a smart contract that calls the `ValidateMultiSign` (address `0x66...`) or `BatchValidateSign` precompile with malformed offset/length words in the call data, then broadcasting a single transaction that triggers this call. No special permissions, staking, or SR/witness status is required — only the ability to deploy/call a contract, which is a core unprivileged transaction path.

### Recommendation
Add explicit bounds validation in `extractBytesArray` and `extractSigArray` (and their callers) unconditionally — not only when `allowTvmOsaka()` is enabled — verifying: `offset >= 0`, `len >= 0` and `len <= MAX_SIZE`, `offset + i + 1 < words.length` for every loop iteration, `bytesOffset >= 0`, and `(bytesOffset + offset + 2) * WORD_SIZE + bytesLen <= data.length` before calling `extractBytes`/`Arrays.copyOfRange`. Wrap the precompile bodies (including the extraction calls) in a `try/catch` that safely returns `Pair.of(true, DATA_FALSE)` on any parsing failure, consistent with how `BatchValidateSign.execute` already wraps `doExecute`.

### Proof of Concept
Deploy a contract that performs a low-level `staticcall`/`call` to the `ValidateMultiSign` precompile address with ABI-encoded call data where:
- word[3] (the signature-array offset pointer) is set to a very large value or one that, after `/WORD_SIZE`, produces an index at or beyond `words.length`.
- This makes `words[words[3].intValueSafe() / WORD_SIZE]` throw `ArrayIndexOutOfBoundsException` in the `allowTvmSelfdestructRestriction()` branch, or makes `extractBytesArray`/`extractSigArray` compute an out-of-range `bytesOffset`/`bytesLen` leading to `Arrays.copyOfRange` throwing on `data`.

Since the exception is raised outside the guarded `try` block in `ValidateMultiSign.execute` (lines 1057-1080 precede the try at line 1082), it is not caught locally, and its propagation behavior up the TVM call stack needs to be confirmed against `Program`'s top-level exception handling to determine whether it is swallowed as a reverted call or actually escapes to crash block processing — this final propagation path could not be fully traced within the available index and should be verified directly in a Devin session with full repository access.
