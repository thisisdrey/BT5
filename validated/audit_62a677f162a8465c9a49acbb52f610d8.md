### Title
Per-IP QUIC connection rate limit is bypassed by never completing the handshake, allowing unbounded free handshake-CPU consumption - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`ConnectionRateLimiter::register_connection` (the token-consuming call) is only invoked *after* a QUIC handshake successfully completes, while the pre-accept gate `ConnectionRateLimiter::is_allowed` treats any IP with no recorded tokens as unconditionally allowed. An attacker who repeatedly opens connections from a fixed IP and lets each one time out (never completing the handshake) is therefore never registered in the per-IP limiter, so `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` never engages for that source, letting it consume the shared global handshake budget for free.

### Finding Description
In `run_server` (`streamer/src/nonblocking/quic.rs:331-379`), the accept loop for each incoming connection performs, in order: a global rate check (`overall_connection_rate_limiter`), a per-IP peek (`rate_limiter.is_allowed(&incoming.remote_address().ip())`), a global-concurrency-slot allocation (`ClientConnectionTracker::new(...)`), and then `incoming.accept()` which starts the actual QUIC/TLS handshake crypto work. [1](#0-0) 

`is_allowed` only consults existing entries in the `KeyedRateLimiter`; if the IP has never been *registered* it returns `true` unconditionally: [2](#0-1) 

The only place tokens are actually consumed is `register_connection`, which is called from `setup_connection` **only after `timeout(QUIC_CONNECTION_HANDSHAKE_TIMEOUT, connecting).await` resolves `Ok`** (i.e., only on a fully completed handshake): [3](#0-2) 

If the attacker deliberately never completes the handshake (e.g. never responds to the server's Handshake packet, or drops the connection right before completion), `register_connection` is never called, so the IP is never inserted into the limiter map, and `is_allowed` returns `true` forever for that IP. The 2-second timeout (`QUIC_CONNECTION_HANDSHAKE_TIMEOUT`) means each incomplete attempt costs the server: one `ClientConnectionTracker` slot (bounded only by the *global* `qos.max_concurrent_connections()`, not per-IP) plus real QUIC/TLS handshake CPU, for up to 2 seconds, before `handle_connection_error` is invoked. [4](#0-3) [5](#0-4) 

The only remaining guards are both *global*, not per-source: `overall_connection_rate_limiter` (`TOTAL_CONNECTIONS_PER_SECOND = 2500`, burst `1000`) and the global concurrent-connection cap `(max_staked_connections + max_unstaked_connections) * 5/4` (default `(2000+2000)*5/4 = 5000`). [6](#0-5) [5](#0-4) 

This means a single unstaked source can, by design of the check ordering, absorb the *entire* global handshake-processing budget (up to 2500 attempts/sec sustained, up to 5000 concurrently) purely with never-completing handshakes, denying that shared, limited resource to all other unstaked and staked sources, while the per-source cap (`DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE = 8`) that is supposed to bound this never engages. The code comment even documents the intended tradeoff/design rationale (avoid mutating state pre-verification to prevent IP-spoofing amplification), but does not account for a *real* IP address abusing this by simply never completing handshakes. [7](#0-6) 

### Impact Explanation
Concrete scoped impact: leader CPU is spent on QUIC/TLS handshake setup and connection-table bookkeeping that is entirely unpriced (no fee is ever paid, since no transaction stream is ever opened). Because the per-IP throttle is a no-op against non-completing connections, a single unstaked source can consume the entire global handshake budget (rate + concurrency), degrading TPU ingress capacity for legitimate staked and unstaked senders. This falls under the "QoS evasion / grossly underpriced pre-fee work" bounty category — the invariant that unstaked per-source connection limits bound resource consumption is violated via connection churn.

### Likelihood Explanation
Fully unprivileged and trivially reproducible: any remote client can open a QUIC connection to the public TPU/TPU-forward port and simply not complete/reply to the handshake (or explicitly drop after Initial), repeated in a tight loop. No stake, no gossip/peer control, and only standard QUIC/UDP packets are required. This is directly exploitable from a single real IP address without spoofing.

### Recommendation
Consume (or reserve) a per-IP rate-limit token at connection-attempt time (before `incoming.accept()`), not only on successful handshake completion, so incomplete/abandoned handshakes still count against the source's per-IP quota. Alternatively, track and bound in-flight (not-yet-completed) handshake attempts per source IP independently of the completed-connection registry, so the existing `DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE` invariant actually caps handshake-CPU spend per source regardless of whether the handshake ever finishes.

### Proof of Concept
Rust integration test plan (extends the existing `streamer/src/nonblocking/quic.rs` test harness, e.g. `setup_quic_server`):
1. Configure server with `SwQosConfig::default()` (`max_connections_per_unstaked_peer` default) and default `QuicStreamerConfig` (`max_connections_per_ipaddr_per_min = DEFAULT_MAX_CONNECTIONS_PER_IPADDR_PER_MINUTE = 8`).
2. From a single client IP (`bind_to_localhost_unique` reused across attempts, or loopback), repeatedly (e.g. 50 times, well above the per-minute limit of 8) create a `quinn::Endpoint` connection attempt to the server and immediately drop the client endpoint/socket before the handshake completes (simulating "connect->timeout->drop"), instead of awaiting `.connect(...).await`.
3. After each attempt, wait slightly less than `QUIC_CONNECTION_HANDSHAKE_TIMEOUT` and assert via `stats.connection_rate_limited_per_ipaddr` that it remains `0` even though far more than 8 attempts were made from the same IP — demonstrating the per-IP limiter never engages.
4. Assert `stats.total_incoming_connection_attempts` (or `stats.connection_setup_timeout`) increments once per attempt, and `stats.open_connections` transiently increases (bounded only by the global `max_concurrent_connections`), confirming real `ClientConnectionTracker` allocation and handshake-timeout CPU work occurred for every attempt despite the small per-IP limit.
5. Contrast with a control test (existing `test_rate_limiting` pattern) where a connection *is allowed to complete*, showing `connection_rate_limited_per_ipaddr` increments correctly once the completed-connection quota (post-registration) is exceeded — proving the limiter only works post-completion, never pre-completion.

    /// Check the max_concurrent_connections limit and if it is within the limit
    /// create ClientConnectionTracker and increment open connection count. Otherwise returns Err
    fn new(stats: Arc<StreamerStats>, max_concurrent_connections: usize) -> Result<Self, ()> {
        let open_connections = stats.open_connections.fetch_add(1, Ordering::Relaxed);

            );
