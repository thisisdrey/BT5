### Title
Undelegating TRON Power / Resources is gated by the same feature-flag used to enable delegation, allowing governance to permanently freeze users' already-delegated stake - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
The Morpho-Aave report describes a feature toggle ("asset used as collateral") whose *disabling* is checked at the time of a new action, but the check does not account for state that was created while the feature was *enabled*—leaving existing users unable to safely exit and exposed to liquidation. The same "single toggle gates both the creation and the reversal of a stateful position" anti-pattern exists in java-tron's resource-delegation feature: both `DelegateResourceContract` (create the position) and `UnDelegateResourceContract` (undo the position) are gated by the very same `DynamicPropertiesStore` flags (`supportDR()` / `supportUnfreezeDelay()`), with no independent, flag-agnostic path to unwind already-delegated resources.

### Finding Description
`DelegateResourceActuator.validate()` requires the feature to be enabled before a user can delegate bandwidth/energy to another account: [1](#0-0) 

Symmetrically, `UnDelegateResourceActuator.validate()` requires the *same* flags to be enabled before a user is allowed to reclaim delegated resources back: [2](#0-1) 

Both actuators check `dynamicStore.supportDR()` and `dynamicStore.supportUnfreezeDelay()` before allowing execution. These flags are controlled through governance/committee proposals (`ProposalService`), which also enable the associated system contract permissions for `DelegateResourceContract` and `UnDelegateResourceContract` together, at the same time, via `UNFREEZE_DELAY_DAYS`: [3](#0-2) 

Because the ability to *reverse* a delegation depends on the identical global switch that enables *creating* one, there is no code path that lets a user recover previously delegated TRX/resources if that global switch is later disabled (via a chain parameter change/hard fork rollback, an operational mistake, or any future governance action that resets these dynamic properties). This mirrors the Morpho bug class exactly: a global, retroactively-applied toggle interacts with already-existing per-user state (delegated stake) in a way the contract logic never validated, and the only enforcement point (the actuator's `validate()`) blocks based on current global state rather than the state that existed when the position was opened.

### Impact Explanation
If `supportDR()`/`supportUnfreezeDelay()` become `false` after resources have already been delegated (whether through misconfiguration, a bug in a future proposal, or state store corruption/rollback), all users with an active `DelegatedResourceCapsule` lose the only way to reclaim their delegated TRX stake back into `FrozenV2` balance, since `UnDelegateResourceActuator.validate()` unconditionally throws `ContractValidateException` when the flags are off. This can result in permanent freezing of funds for every account with an outstanding delegation, which meets the "permanent freezing of funds" impact bar.

### Likelihood Explanation
The delegate/undelegate feature is deployed and permission for both is turned on together only through the `UNFREEZE_DELAY_DAYS` proposal path, and there is no independent code path or grace mechanism to unwind existing delegations once the shared flags flip to disabled. The likelihood of the flags actually being disabled after being enabled depends on committee/governance proposal-processing logic in `ProposalUtil` and `DynamicPropertiesStore`, which was not fully verifiable within the available index (I could not confirm from the indexed code whether the specific parameters can be programmatically reverted to 0 once set, since the `ProposalUtil.java` validator body for `UNFREEZE_DELAY_DAYS`/`ALLOW_TVM_FREEZE`-style entries was not retrievable in full). This uncertainty should be resolved by a full review of `actuator/src/main/java/org/tron/core/utils/ProposalUtil.java` to confirm whether these parameters are one-way (monotonic) or can be reset, which materially affects the real-world likelihood of this being triggerable.

### Recommendation
Decouple the ability to reverse a delegation (`UnDelegateResourceContract`, `WithdrawExpireUnfreezeContract`) from any global enable/disable toggle that also governs the creation path (`DelegateResourceContract`, `FreezeBalanceV2Contract`). At minimum, `UnDelegateResourceActuator.validate()` and `WithdrawExpireUnfreezeActuator` should never be blocked by `supportDR()`/`supportUnfreezeDelay()` if a `DelegatedResourceCapsule` or unfreezing entry already exists for the account, ensuring users can always recover previously locked/delegated funds regardless of the current state of governance-controlled feature flags. Additionally, confirm within `ProposalUtil.java` whether these dynamic parameters can be reverted after being set to a non-zero/enabled value, and if so, require that any downgrade proposal be rejected while outstanding delegated/frozen positions exist.

### Proof of Concept
1. Committee enables `UNFREEZE_DELAY_DAYS` (sets `supportDR()`/`supportUnfreezeDelay()` to true), permitting `DelegateResourceContract`/`UnDelegateResourceContract`.
2. User A delegates bandwidth/energy to User B via `DelegateResourceActuator`, creating a `DelegatedResourceCapsule` entry (see `actuator/src/main/java/org/tron/core/actuator/DelegateResourceActuator.java:282-325` for the state written).
3. A subsequent governance action or code/config change causes `dynamicStore.supportDR()` or `supportUnfreezeDelay()` to evaluate to `false` (whether that is currently reachable via committee proposal alone requires confirming `ProposalUtil.java`'s full validator, which was not available in the indexed context).
4. User A attempts to call `UnDelegateResourceContract` to reclaim the delegated stake; `UnDelegateResourceActuator.validate()` immediately throws `ContractValidateException("No support for resource delegate")` / `"Not support unDelegate resource transaction..."`, permanently preventing recovery of the already-delegated funds.

Note: because the full body of `ProposalUtil.java`'s validator for these specific parameters could not be retrieved from the code index, I could not conclusively confirm whether these flags are strictly monotonic (only ever move from 0→1) in the current codebase. This should be verified directly in a full session before treating this as confirmed reachable, though the actuator-level coupling itself (shared flag gating both directions) is confirmed and is the root structural issue analogous to the reported Morpho bug.
