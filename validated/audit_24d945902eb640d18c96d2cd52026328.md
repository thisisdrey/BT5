### Title
Unsynchronized map access between adaptive-limit recalibration and per-key concurrency limiter creation/eviction causes a `gitaly` process crash - (File: `internal/limiter/concurrency_limiter.go`)

### Summary
`ConcurrencyLimiter` maintains a per-key limiter registry, `limitsByKey`, which is created/destroyed under a dedicated mutex (`c.m`) in `getConcurrencyLimit`/`putConcurrencyLimit`. However, the resize callback registered in `NewConcurrencyLimiter` — invoked whenever the `AdaptiveLimit` value changes — iterates over that same `limitsByKey` map without acquiring `c.m`. This mirrors the reward-report's root cause: a value ("current pool state") is read/mutated from two independent code paths that are not kept consistent with each other, except here the inconsistency is a genuine data race on a Go map rather than a stale accounting figure, and the outcome is a hard process crash rather than a miscalculated reward.

### Finding Description
`ConcurrencyLimiter.getConcurrencyLimit` and `putConcurrencyLimit` both lock `c.m` before reading, inserting, or deleting entries in `c.limitsByKey`: [1](#0-0) [2](#0-1) 

But the resize hook registered against the shared `AdaptiveLimit` in `NewConcurrencyLimiter` ranges over `limiter.limitsByKey` with no lock at all: [3](#0-2) 

This hook is invoked from `AdaptiveLimit.Update`, which only takes the `AdaptiveLimit`'s own private mutex — a completely different lock than `ConcurrencyLimiter.m`: [4](#0-3) 

`AdaptiveLimit.Update` is called periodically by `AdaptiveCalculator.calibrateLimits`, which runs on its own goroutine at `CalibrationInterval` (default 30s) whenever adaptive limiting is enabled, and increments the limit by one on every healthy calibration tick until `Max` is reached, or halves it on a backoff event: [5](#0-4) 

Meanwhile, ordinary git operations (fetch/push/upload-pack) that are subject to a keyed concurrency limit (e.g. `TypePerRPC` or `TypePackObjects`) call `getConcurrencyLimit`/`putConcurrencyLimit` on every request to add/remove entries from the very same `limitsByKey` map: [6](#0-5) 

Because one path (request admission/eviction) locks `c.m` and the other (adaptive resize) does not, a concurrent map read (range in the hook) and map write (insert/delete in `getConcurrencyLimit`/`putConcurrencyLimit`) can occur simultaneously. Go's runtime detects concurrent unsynchronized map access and terminates the process with `fatal error: concurrent map iteration and map write`, which is not recoverable via `recover()`.

### Impact Explanation
This is a process-wide, unrecoverable crash of the Gitaly server (denial of service) triggered purely by ordinary, expected traffic patterns: any RPC handler protected by a keyed `ConcurrencyLimiter` (e.g., `pack-objects` limiting keyed by remote IP/repo/user, or per-RPC limiting) combined with `AdaptiveLimiting` enabled in configuration. No privileged action, leaked token, or malicious peer is required — concurrent, unprivileged fetches/pushes from ordinary users naturally populate/evict `limitsByKey` while the adaptive calculator's periodic goroutine resizes limits in the background, racing against it.

### Likelihood Explanation
`AdaptiveLimiting` combined with `ConcurrencyLimiter`-managed RPCs (e.g. pack-objects concurrency limiting) is a documented, supported production configuration (`internal/cli/gitaly/serve.go`, `doc/load-management-architecture.md`). Under this configuration, the additive-increase path fires the resize hook on nearly every calibration tick until the max limit is hit, and any backoff event fires it again — giving a wide, recurring window for the race to align with concurrent request admission/eviction under normal load, especially on busy Gitaly nodes with many concurrent CI fetches or pushes.

### Recommendation
Protect all reads/writes of `ConcurrencyLimiter.limitsByKey` with `c.m`. Specifically, the resize hook registered in `NewConcurrencyLimiter` must acquire `c.m.Lock()` (or `RLock()` combined with proper synchronized resize primitives) before ranging over `limitsByKey`, consistent with `getConcurrencyLimit`/`putConcurrencyLimit`. Ensure the `AdaptiveLimit`'s own mutex is never held while calling back into `ConcurrencyLimiter` code that itself needs `c.m`, to avoid introducing a lock-ordering deadlock when adding the missing lock.

### Proof of Concept
1. Configure Gitaly with `AdaptiveLimiting` enabled and a keyed concurrency limiter (e.g. pack-objects concurrency limiting) so that `NewConcurrencyLimiter` is constructed with an `AdaptiveLimit` whose `AfterUpdate` hook is registered as in `internal/limiter/concurrency_limiter.go:171-186`.
2. Drive sustained concurrent, unprivileged git fetch/push traffic against multiple distinct limiting keys (different repositories/IPs/users) so that `getConcurrencyLimit`/`putConcurrencyLimit` continuously insert and delete entries from `limitsByKey` under `c.m`.
3. Simultaneously, let the `AdaptiveCalculator`'s background goroutine tick at `CalibrationInterval` (`internal/limiter/adaptive_calculator.go:171-184`), calling `c.updateLimit(limit, newLimit)` → `AdaptiveLimit.Update` → the unlocked resize hook that ranges over `limitsByKey` concurrently with the map mutations from step 2.
4. Under sufficient request concurrency, the Go runtime's concurrent map access detector triggers `fatal error: concurrent map iteration and map write`, crashing the entire Gitaly process and denying service to all users on that node.

func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

// putConcurrencyLimit drops the reference to the concurrency limit identified by the given key.
// This must only ever be called after `getConcurrencyLimit()` for the same key. If the reference
// count of the concurrency limit drops to zero then it will be destroyed.
func (c *ConcurrencyLimiter) putConcurrencyLimit(limitingKey string) {
	c.m.Lock()
	defer c.m.Unlock()

	ref := c.limitsByKey[limitingKey]
	if ref == nil {
		panic("semaphore should be in the map")
	}

	if ref.refcount <= 0 {
		panic(fmt.Sprintf("bad semaphore ref refcount %d", ref.refcount))
	}

	ref.refcount--
	if ref.refcount == 0 {
		delete(c.limitsByKey, limitingKey)
	}
}

// Update adjusts the current limit value and executes all registered update hooks.
func (l *AdaptiveLimit) Update(val int) {
	l.Lock()
	defer l.Unlock()

	if val != l.current {
		l.current = val
		for _, hook := range l.updateHooks {
			hook(val)
		}
	}
}

// AfterUpdate registers a callback when the current limit is updated. Because all updates and hooks are synchronized,
// calling l.Current() inside the update hook in the same goroutine will cause deadlock. Hence, the update hook must
// use the newVal argument instead.
func (l *AdaptiveLimit) AfterUpdate(hook AfterUpdateHook) {
	l.updateHooks = append(l.updateHooks, hook)
}
