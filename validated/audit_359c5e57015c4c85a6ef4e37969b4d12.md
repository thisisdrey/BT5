## Finding

### Title
ERC20 asset transactor silently drops all but one ERC20 token when depositing multiple matched assets, permanently locking user funds - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::deposit_asset_with_surplus` is invoked by the XCM executor with an `AssetsInHolding` set that may contain **multiple** distinct ERC20 assets (any location of the shape `AccountKey20 { key }` matches `ERC20Matcher`, regardless of which contract address). The implementation only extracts and transfers the *first* fungible asset found via `.fungible_assets_iter().next()` and returns `Ok(surplus)` — as if the whole `what` had been handled — while every other asset in the holding is discarded without being deposited, returned as unspent, or trapped. This mirrors the root cause of the external Starknet report: an operation is performed against an external contract interface using an assumption (“there is exactly one relevant asset/interface here”) that is not actually guaranteed, and the mismatch is not detected or guarded against, so the surrounding accounting silently breaks for inputs that violate the assumption.

### Finding Description
`ERC20Transactor` is registered as one of the `AssetTransactors` on Asset Hub Westend: [1](#0-0) 

Its `deposit_asset_with_surplus` implementation: [2](#0-1) 

The doc comment on the function itself acknowledges the flaw but does not fix it — it just asserts (in debug builds only, via `defensive_assert!`) that this should not happen: [3](#0-2) 

The generic `TransactAsset` trait, however, does not guarantee that a single-matcher transactor only ever receives a single asset: `deposit_asset`/`deposit_asset_with_surplus` are called with the entire (or filtered) `AssetsInHolding` register, and any location of the form `[AccountKey20 { key, network }]` is matched by `ERC20Matcher`, so two *different* ERC20 contract addresses withdrawn earlier in the same XCM program end up in the same `AssetsInHolding` passed to this one transactor: [4](#0-3) 

A normal, unprivileged user submitting an XCM program via `PolkadotXcm::execute` (as demonstrated by the existing test suite, which builds programs that `withdraw_asset` an ERC20 and later `deposit_asset(AllCounted(1), ...)`) can instead build a program that:
1. `WithdrawAsset` for ERC-20 token A (contract address X) — this already performs a real on-chain `transfer` to `ERC20TransfersCheckingAccount` in `withdraw_asset_with_surplus`.
2. `WithdrawAsset` for ERC-20 token B (contract address Y) — same real transfer to the checking account.
3. `DepositAsset { assets: Wild(AllCounted(2)), beneficiary }` — this exact pattern (`Wild(AllCounted(n))`) is already used throughout the Snowbridge XCM programs in this codebase, e.g.: [5](#0-4) 

When the deposit step reaches `ERC20Transactor`, only the first ERC20 asset in the holding (say token A) is transferred out of the checking account to the beneficiary. Token B, whose real balance was already moved into `ERC20TransfersCheckingAccount` during withdrawal, is dropped from the in-memory `AssetsInHolding` and never credited to the beneficiary, never returned to the original owner, and never surfaced as "trapped" (since the function returns `Ok`, not an error with leftover assets). The on-chain ERC20 balance for token B is now permanently stuck in `ERC20TransfersCheckingAccount` with no code path that can move it back out to any specific owner.

### Impact Explanation
This breaks the "conserve value and settle exactly once to the rightful beneficiary and amount" invariant for public asset movement on Asset Hub: real ERC20 balances are transferred into a pallet-controlled checking account, but the corresponding XCM-level accounting entry for all-but-one of the assets is silently discarded rather than deposited or trapped, resulting in a permanent, unrecoverable loss of those tokens for the user (Medium/High depending on frequency of multi-ERC20 deposits, but unbounded in amount per occurrence).

### Likelihood Explanation
Any signed account can trigger this via the public `pallet_xcm::execute` extrinsic (no privileged origin, no malicious relayer/validator/prover required) by constructing a program that withdraws two or more distinct ERC-20-backed assets and deposits them together with a `Wild`/`AllCounted` filter — a pattern already used natively elsewhere in the same runtime's Snowbridge programs, making it a realistic and easily-triggerable path rather than a contrived one.

### Recommendation
`ERC20Transactor::deposit_asset_with_surplus` (and `withdraw_asset_with_surplus`, if similarly affected) should either: (a) iterate over and transfer every fungible asset present in `what` matched by `ERC20Matcher`, accumulating and returning any assets it does not handle as "unspent" so the XCM executor tuple can continue processing or trap them, rather than silently discarding them; or (b) enforce (with a hard error, not just a `defensive_assert!`) that it only ever receives exactly one asset, returning the remainder as unspent via `Err((remaining, XcmError::AssetNotHandled))` instead of `Ok`.

### Proof of Concept
1. Deploy two independent ERC20-compatible `pallet-revive` contracts, X and Y, and fund an account `A` with balances of both.
2. `A` submits `pallet_xcm::execute` with an XCM program:
   - `WithdrawAsset((AccountKey20{X}, amount_x))`
   - `WithdrawAsset((AccountKey20{Y}, amount_y))`
   - `DepositAsset { assets: Wild(AllCounted(2)), beneficiary: B }`
3. Observe: `ERC20Transactor::withdraw_asset_with_surplus` executes real `transfer` calls moving both `amount_x` (token X) and `amount_y` (token Y) from `A` into `ERC20TransfersCheckingAccount`.
4. In the deposit step, `deposit_asset_with_surplus` calls `what.fungible_assets_iter().next()`, matches only one of {X, Y} (order depends on internal `AssetsInHolding` iteration), transfers only that one to `B`, and returns `Ok(surplus)` for the whole `what`.
5. Result: beneficiary `B` receives only one of the two tokens; the other token's balance remains stuck in `ERC20TransfersCheckingAccount` with no owner reference, permanently inaccessible to `A` or `B`.

	/// Deposits assets from holding to a beneficiary account via ERC20 transfer.
	///
	/// Note: This implementation only handles a single fungible asset at a time. The
	/// `AssetsInHolding` parameter is required by the `TransactAsset` trait, but callers
	/// should ensure only one asset is passed. If multiple assets are present, only the
	/// first fungible asset will be deposited and the rest will be silently ignored.
	/// The `defensive_assert!` helps catch misuse during development.
	fn deposit_asset_with_surplus(
		what: AssetsInHolding,
		who: &Location,
		_context: Option<&XcmContext>,
	) -> Result<Weight, (AssetsInHolding, XcmError)> {
		tracing::trace!(
			target: "xcm::transactor::erc20::deposit",
			?what, ?who,
		);
		defensive_assert!(what.len() == 1, "Trying to deposit more than one asset!");
		// Check we handle this asset.
		let maybe = what
			.fungible_assets_iter()
			.next()
			.and_then(|asset| Matcher::matches_fungibles(&asset).ok());
		let (asset_contract_id, amount) = match maybe {
			Some(inner) => inner,
			None => return Err((what, MatchError::AssetNotHandled.into())),
		};
		let who = match AccountIdConverter::convert_location(who) {
			Some(inner) => inner,
			None => return Err((what, MatchError::AccountIdConversionFailed.into())),
		};
		// We need to map the 32 byte beneficiary account to a 20 byte account.
		let eth_address = T::AddressMapper::to_address(&who);
		let address = Address::from(Into::<[u8; 20]>::into(eth_address));
		// To deposit, we actually transfer from the checking account to the beneficiary.
		// We do this using the solidity ERC20 interface.
		let data = IERC20::transferCall { to: address, value: EU256::from(amount) }.abi_encode();
