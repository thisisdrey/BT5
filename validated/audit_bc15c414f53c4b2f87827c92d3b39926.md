### Title
Object pool disconnect trusts arbitrary `objects/info/alternates` content, enabling cross-repository object exfiltration - ([File: internal/git/objectpool/disconnect.go])

### Summary
`Disconnect` (invoked by the `DisconnectGitAlternates` RPC) reads whatever path is present in a repository's `objects/info/alternates` file and unconditionally hard-links every object it finds there into the calling repository, without ever verifying that the alternate actually points to the repository's registered/expected object pool. This mirrors the report's root cause: a critical field (the alternate/"recipient" object directory) is consumed and trusted to perform a privileged data-merging action without validating it against an expected value, unlike the sibling `Link`/`linkedToRepository` code path which does perform that check.

### Finding Description
When `Link` connects a repository to its pool, it validates the alternate path against `getRelativeObjectPath` and rejects mismatches (`linkedToRepository`, `internal/git/objectpool/link.go`, `internal/git/objectpool/link.go` lines around 168-204), and `partition_assigner.go`'s `getAlternatePartitionID` similarly cross-validates alternates. `Disconnect`, however, does not perform any equivalent check: [1](#0-0) 

It merely inspects `AlternatesInfo.ObjectDirectories[0]` from the repository's own `objects/info/alternates` file: [2](#0-1) 

and then hard-links every object file discovered at that path into the repository's own object store: [3](#0-2) 

The only path constraint enforced anywhere in this flow is that the alternate stays within the storage root (`internal/git/dirs.go` `altObjectDirs`), which permits an alternate to reference *any other repository in the same storage*, not just the caller's actual, previously-linked object pool. Because a user can create a repository via `CreateRepositoryFromBundle` (or similarly `CreateRepositoryFromURL`/`FetchBundle`), and Git bundles/clones can carry an attacker-controlled `objects/info/alternates` file (the underlying `git-clone --mirror`/`git fetch` does not strip or validate this file's contents against Gitaly's pool semantics), a user can plant `objects/info/alternates` in their own repository pointing at `../../<victim-repo>/objects` (as long as it resolves under the same storage root). Calling `DisconnectGitAlternates` on that repository then causes Gitaly to enumerate and hard-link *every* loose object present under the victim's object directory into the attacker's own repository — full content, regardless of whether the attacker already knew any object IDs in the target repo.

This is the same class of bug as the report: the code reads a field that determines the source/destination of a value-transferring operation (`to` in the report; the alternates path here) and performs the transfer/merge without validating that the field matches the expected, registered counterpart (`expected_escrow` in the report; the pool relationship established via `Link`/`getRelativeObjectPath` here).

### Impact Explanation
A successful exploit lets one tenant/user completely exfiltrate the git object database of an arbitrary repository within the same Gitaly storage — including private commits, blobs, and trees they have no authorization to read — by merely creating an attacker-owned repository whose `objects/info/alternates` references the victim path and then issuing a `DisconnectGitAlternates` call on it. This is a severe cross-repository confidentiality breach (equivalent to arbitrary read access across repository boundaries within a storage shard), directly analogous to the "impact: High" classification in the report (undetectable value drained from an unrelated party).

### Likelihood Explanation
Reaching this path requires only ordinary user capabilities already available in Gitaly's threat model: creating/importing a repository with attacker-supplied bundle content and invoking a documented, non-privileged mutator RPC (`DisconnectGitAlternates`). No admin privileges, leaked tokens, or MITM position are needed — only that the target repository resides in the same storage and its relative path (or a guessable/discoverable one, e.g. through project listings) is known. The primary uncertainty is whether upstream authorization (GitLab Rails access checks) restricts which repository paths a given user may reference when crafting an import, but at the Gitaly RPC layer itself no such cross-repository validation exists for this code path.

### Recommendation
In `Disconnect`, before hard-linking any objects, verify that the alternate object directory found in `objects/info/alternates` matches the repository's actual, previously-established object pool relationship — the same way `linkedToRepository` in `internal/git/objectpool/link.go` validates alternates against `getRelativeObjectPath(ctx, pool, repo)`. Concretely:
- Require the caller to supply (or Gitaly to independently resolve via `ObjectPool.FromRepo`) the expected pool for the repository, and compare the alternates entry against that pool's path before performing any linking.
- Reject and abort (returning an error, as `Link` does with "unexpected alternates content") if the alternate does not match the expected/registered pool, instead of blindly trusting whatever is on disk.
- Additionally validate at repository-creation/import time that `objects/info/alternates` shipped in an untrusted bundle either does not exist or is rewritten/removed unless it corresponds to a Gitaly-managed pool relationship for that repository.

### Proof of Concept
1. User creates two repositories in the same storage: `attacker.git` (owned by attacker) and knows/references `victim.git` (private repo, e.g. by relative path such as `@hashed/xx/xx/xxxxx.git`, or another accessible repo they can reference).
2. Attacker builds a local Git bundle whose `.git/objects/info/alternates` file (or one they append post hoc via any RPC/tooling that permits writing into a freshly created bare repository's directory before `DisconnectGitAlternates` is called) contains a relative path such as `../../<victim-repo-relative-path>/objects`.
3. Attacker calls `RepositoryService.CreateRepositoryFromBundle` (or similar import RPC) to materialize `attacker.git` with this alternates file in place, satisfying `dirs.go`'s "stay within storage root" check since `victim.git` is in the same storage.
4. Attacker calls `ObjectPoolService.DisconnectGitAlternates` on `attacker.git`.
5. `Disconnect` reads the alternates entry, lists every object file under `victim.git/objects`, and hard-links them all into `attacker.git/objects`, then removes the alternates file — leaving all of `victim.git`'s objects permanently and fully readable from `attacker.git` (e.g. via `Fsck`, `GetArchive`, or any CommitService/BlobService RPC against `attacker.git`), without the attacker ever having needed read access to `victim.git` nor knowledge of any specific object ID.
