## Analysis

The external report's bug class is: a two-phase workflow (queue → complete) where an independent actor can revoke a piece of shared state *during the gap between phases*, causing the second phase's validation to permanently and incorrectly fail (or, worse, silently let two incompatible actions proceed as if authorized). Gitaly's Praefect write-serialization feature reproduces this exact pattern.

### Title
Write-lock theft due to fixed TTL race defeats reference-transaction write serialization - (File: internal/praefect/datastore/lock_manager.go)

### Summary
Praefect's `RepoReferenceWriteLockManager` serializes concurrent writers to the same repository across Gitaly nodes by acquiring a per-repository DB-backed lock at the `PREPARING_PHASE` of a reference transaction and renewing it at `PREPARED_PHASE`/`COMMITTED_PHASE` [1](#0-0) . The lock has a hard-coded 20-second TTL that is unconditionally applied regardless of how long the actual on-disk locking phase of a given push takes [2](#0-1) .

### Finding Description
The lock acquisition query allows a *different* transaction to unconditionally steal the lock row the moment `expired_at < NOW()`, with no coordination with the original holder: [3](#0-2) 

The original holder has no notification that its lock was stolen. It discovers this only when it calls `renew()` at the `PREPARED_PHASE`/`COMMITTED_PHASE`, at which point the conditional `UPDATE ... WHERE lock_id = $1 AND holder_txn_id = $2` matches zero rows and returns an error: [4](#0-3) 

That error is propagated straight back through `lockRepoForTransaction`, failing the whole gRPC call: [5](#0-4) 

This is structurally identical to the slasher bug: transaction 1 (an ordinary user's push) legitimately "queues" its write by acquiring the lock at `PREPARING_PHASE`. If the on-disk ref-locking phase (Git locking refs + reaching quorum on the `Prepared` vote across nodes) takes longer than the fixed 20-second window — plausible for large ref-count pushes, mirror updates, slow custom hooks, or nodes contending with concurrent housekeeping/GC — an unrelated, equally-ordinary transaction 2 can "revoke" transaction 1's authorization by stealing the row via the same UPSERT any push uses. Transaction 1 then fails to "complete" (renew) even though it did everything correctly, denying a legitimate write; per the design doc, both Gitaly nodes will already have "locks refs on disk and voted `Prepared`" before Praefect's renew call fails, meaning the very mechanism this lock exists to prevent (concurrent cross-node on-disk ref locking for the same repository, described in `doc/serialized_writes.md`'s "Why Serialize Writes" section) can recur — the two transactions now overlap in the on-disk locking window despite the DB serialization layer.

### Impact Explanation
- Denial of service for an otherwise fully valid, unprivileged push/fetch/import RPC: the RPC fails with an opaque `renew repo reference write lock (no rows)` error after the client has already done all the work of pushing objects and passing hooks.
- Defeats the correctness guarantee the feature was built for (`doc/serialized_writes.md` "Why Serialize Writes"): once the lock is stolen mid-flight, two independent writers can simultaneously be in the on-disk ref-locking phase for the same repository, reintroducing the cross-node ref-lock deadlock/corruption scenario the serialization was designed to eliminate.
- Triggerable purely through timing/load, not by any privileged operation — any two ordinary users (or one user and a background housekeeping job) racing writes to the same repository can produce it.

### Likelihood Explanation
Likelihood is moderate to high in busy repositories: the 20-second TTL is a fixed constant unrelated to the actual duration of hook execution, ref count, or node latency [6](#0-5) . Any slow `pre-receive`/reference-transaction hook execution, large batched ref update (e.g., mirror push, `ReplicateRepository`, or a fork/import job touching thousands of refs), or transient node/network latency between `Preparing` and `Prepared` votes is sufficient to exceed the window while a concurrent push to the same repository is pending.

### Recommendation
- Do not allow silent lock theft based purely on wall-clock expiry while the original holder may still be actively mid-flight; instead, fail closed by having the "steal" itself be gated on evidence the original holder is truly dead (e.g., missed heartbeats/renewals), not solely on TTL relative to acquisition time.
- Extend the TTL dynamically (heartbeat-based lease) rather than a single fixed 20s interval so that `renew` calls extend based on actual in-flight duration rather than requiring completion within a fixed window.
- Ensure that when a lock is stolen, the original holder's completion (`renew`) failure results in a hard abort of the transaction (including on-disk ref lock rollback) *before* any concurrent holder can start its own on-disk locking, closing the overlap window described above.

### Proof of Concept
1. Configure Praefect with `PraefectSerializedWrite` enabled.
2. As user A, start a push to repository `R` that updates a very large number of references (or install a custom `pre-receive`/reference-transaction hook with `sleep 25`) so that the window between the `PREPARING_PHASE` vote and the `PREPARED_PHASE` vote exceeds 20 seconds.
3. Concurrently, as user B, push a small, fast change to the same repository `R`.
4. Because user A's lock row's `expired_at` has passed 20 seconds without a renew, user B's `tryLock` UPSERT matches `locks.expired_at < NOW()` and steals the lock row, per [3](#0-2) .
5. When user A's transaction reaches `PREPARED_PHASE` and calls `Renew`, the conditional `UPDATE` in [7](#0-6)  matches no rows (held by B's txnID now), returning an error that aborts user A's otherwise-valid push, while user B's write proceeds — potentially overlapping with A's already-in-progress on-disk ref locks.

func (mgr *Manager) lockRepoForTransaction(ctx context.Context, transactionID uint64, storageName, repoRelativePath string,
	phase gitalypb.VoteTransactionRequest_Phase,
) error {
	if featureflag.PraefectSerializedWrite.IsDisabled(ctx) {
		return nil
	}

	switch phase {
	case gitalypb.VoteTransactionRequest_PREPARING_PHASE:
		lock, err := mgr.repoWriteLockMgr.Lock(ctx, storageName, repoRelativePath, transactionID)
		if err != nil {
			return fmt.Errorf("try lock: %w", err)
		}
		mgr.repoLocks.Store(transactionID, lock)

	case gitalypb.VoteTransactionRequest_PREPARED_PHASE, gitalypb.VoteTransactionRequest_COMMITTED_PHASE:
		v, ok := mgr.repoLocks.Load(transactionID)
		if !ok {
			// No Preparing was cast for this transaction. This happens when Git itself drives
			// the reference-transaction hook on a Git build that doesn't emit "preparing"
			// (i.e. pre-2.54). Skip lock work; serialization is dormant for this path
			// until GIT_VERSION_PREV is bumped past 60d8c1e9.
			mgr.logger.WithFields(log.Fields{
				"transaction.id": transactionID,
				"phase":          phase.String(),
			}).DebugContext(ctx, "skipping lock check: no preparing phase recorded")
			return nil
		}
		lock := v.(datastore.RepoLock)
		if err := lock.Renew(ctx); err != nil {
			return err
		}
	}

// NewRepoReferenceWriteLockManager creates a new RepoReferenceWriteLockManager. It starts
// a background listener for lock release notifications and a background job to
// clean up expired locks. Both run until ctx is cancelled.
func NewRepoReferenceWriteLockManager(ctx context.Context, qc glsql.Querier, conf config.DB, logger log.Logger) *RepoReferenceWriteLockManager {
	resilientListenerTicker := helper.NewTimerTicker(5 * time.Second)

	lockReleasingListener := NewResilientListener(conf, resilientListenerTicker, logger, lockReleasingListenerReconnectsTotal)
	handler := &lockReleaseDispatcher{
		waiters: make(map[LockID][]chan struct{}),
		ready:   make(chan struct{}),
	}

	// In production, we start the listener asynchronously to speed up startup.
	// Conceptually, we could block in the constructor until the connection is established,
	// since the manager cannot function correctly without the listener. However, this has
	// a downside: if the database is temporarily slow during startup, the constructor may hang.
	go func() {
		err := lockReleasingListener.Listen(ctx, handler, RepositoryReferenceWriteLockReleasesChannel)
		if err != nil && !errors.Is(err, context.Canceled) {
			logger.WithError(err).Error("notifications listener terminated")
		}
	}()

	// Start a scheduled cleanup background job to remove expired locks.
	lockRenewInterval := 20 * time.Second
	cleanUpJobTicker := helper.NewTimerTicker(2 * lockRenewInterval)

// renew extends the expiry of the write lock held by txnID by another renewInterval.
// It returns an error if the lock is not currently held by txnID.
func (r *RepoReferenceWriteLockManager) renew(ctx context.Context, virtualStorage string, relativePath string, txnID uint64) error {
	query := `
UPDATE repository_reference_write_locks as locks
SET  expired_at = (NOW() + $3::interval)
WHERE locks.lock_id = $1 AND holder_txn_id = $2
RETURNING expired_at;
`
	lockID := repoLockID(virtualStorage, relativePath)
	start := time.Now()
	rows, err := r.qc.QueryContext(ctx, query, lockID, txnID, r.renewInterval)
	r.operationDuration.WithLabelValues(virtualStorage, "renew").Observe(time.Since(start).Seconds())
	if err != nil {
		return fmt.Errorf("renew repo reference write lock (executing query): %s, %w", lockID, err)
	}
	defer func() {
		if err := rows.Close(); err != nil {
			r.logger.WithError(err).Error("close rows")
		}
	}()
	if rows.Next() {
		return nil
	}
	if err := rows.Err(); err != nil {
		return fmt.Errorf("renew repo reference write lock (iterating rows): %s, %w", lockID, err)
	}
	return fmt.Errorf("renew repo reference write lock (no rows): %s", lockID)
}
