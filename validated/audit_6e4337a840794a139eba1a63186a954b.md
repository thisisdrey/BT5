Audit Report

## Title
`PricingParameters::validate()` only checks individual fields for non-zero, allowing `calculate_fee`'s computed remote fee to round to zero via integer division while `do_process_message` still commits the full static `rewards.remote` as payout - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`PricingParameters::validate()` in `bridges/snowbridge/primitives/core/src/pricing.rs` rejects a configuration only if `exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, or `multiplier` individually equal zero, without checking whether the derived fee actually charged to a sender is non-zero. [1](#0-0)  The in-repo test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` proves `calculate_fee` can return `fee.remote == 0` from parameters that pass `validate()`. [2](#0-1)  Meanwhile `do_process_message` unconditionally embeds the static `pricing_params.rewards.remote` into `CommittedMessage.reward`, independent of what was actually collected from the sender at `validate()`/`deliver()` time. [3](#0-2) 

## Finding Description
`Pallet::validate` (the `SendMessage` implementation) computes the fee charged to the sender via `Self::calculate_fee(gas_used_at_most, T::PricingParameters::get())` and returns it as the fee the caller must pay to enqueue the message. [4](#0-3)  `calculate_fee` computes the remote-currency component in wei via `calculate_remote_fee` (`fee_per_gas * gas_used_at_most + reward`), then converts through `FixedU128` multiplier/exchange-rate math and finally divides by a decimals-adjustment denominator in `convert_from_ether_decimals`, using plain integer `checked_div`. [5](#0-4)  When the numerator is small relative to the decimals denominator (e.g., `fee_per_gas=1`, `gas_used=250000`, `reward=1`, `exchange_rate=1/1`, `multiplier=1`, with local `Decimals=10` so `denom=10^8`), the division truncates to `0`, even though every individual field passed `validate()`'s per-field non-zero checks — exactly as demonstrated by the existing unit test. [2](#0-1) 

Separately, when the message is later processed in `do_process_message`, the `reward` field baked into the `CommittedMessage` sent to Ethereum is pulled directly and unconditionally from `pricing_params.rewards.remote` — it is never derived from, or checked against, the fee that was actually computed/collected at `validate()` time. [3](#0-2)  This confirms the described decoupling between what is charged to the sender (which can round to zero in the local-currency fee) and what the protocol commits to pay out on Ethereum.

## Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact class: an unprivileged sender using the public `validate`/`deliver` path can, under specific governance-configured pricing parameter combinations, be charged `Fee.remote == 0` while the bridge still queues a `CommittedMessage` with a full non-zero `reward` value that Ethereum-side relayers can claim. This decouples collected fee from promised payout, degrading the sustainability of relayer incentives, funded from the same static `rewards.remote` value regardless of what was actually collected.

## Likelihood Explanation
Reaching the zero-rounding condition requires no privileged actor — any account that can submit XCM messages routed through the outbound queue's `SendMessage::validate` triggers `calculate_fee`. However, whether the vulnerability is *reachable in practice* depends entirely on the currently configured `PricingParameters` (`exchange_rate`, `fee_per_gas`, decimals denominator) actually landing in the zero-rounding regime; this is a governance/config-dependent precondition, not something the attacker fully controls, since `PricingParameters` is set by governance via `T::PricingParameters::get()`, not by the caller. The claim's own likelihood argument rests on the parameters used in the unit test (`fee_per_gas=1`, `exchange_rate=1/1`) being "plausible," but does not demonstrate that any currently deployed production configuration (e.g., `fee_per_gas: gwei(20)`, `exchange_rate: 1/400`) actually falls into this rounding regime — that configuration file was referenced in the claim but not verified in this repository's actual runtime configs within the scope of this review.

## Recommendation
Extend `PricingParameters::validate()` to additionally verify that `calculate_fee` (or an equivalent minimum-fee computation) yields a non-zero `remote` component for the minimum supported `gas_used_at_most`, rather than only checking individual input fields. Alternatively, derive the `reward` embedded in `CommittedMessage` in `do_process_message` from the fee actually collected at submission time rather than unconditionally from the static `pricing_params.rewards.remote`, ensuring the amount promised to relayers can never exceed what was collected from the sender.

## Proof of Concept
The existing unit test `test_calculate_fees_with_valid_exchange_rate_but_remote_fee_calculated_as_zero` in `bridges/snowbridge/pallets/outbound-queue/src/test.rs` reproduces the core primitive directly: with `exchange_rate=1/1`, `fee_per_gas=1`, `rewards={local:1, remote:1}`, `multiplier=1` — all individually non-zero and passing `PricingParameters::validate()` — `OutboundQueue::calculate_fee` returns `fee.remote == 0`, while `do_process_message` would still embed the full non-zero `pricing_params.rewards.remote` as `CommittedMessage.reward`. 	pub fn validate(&self) -> Result<(), InvalidPricingParameters> {
		if self.exchange_rate == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.fee_per_gas == U256::zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.local.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.rewards.remote.is_zero() {
			return Err(InvalidPricingParameters);
		}
		if self.multiplier == FixedU128::zero() {
			return Err(InvalidPricingParameters);
		}
		Ok(())
	}

		/// Calculate total fee in native currency to cover all costs of delivering a message to the
		/// remote destination. See module-level documentation for more details.
		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		/// Calculate fee in remote currency for dispatching a message on Ethereum
		pub(crate) fn calculate_remote_fee(
			gas_used_at_most: u64,
			fee_per_gas: U256,
			reward: U256,
		) -> U256 {
			fee_per_gas.saturating_mul(gas_used_at_most.into()).saturating_add(reward)
		}

		/// The local component of the message processing fees in native currency
		pub(crate) fn calculate_local_fee() -> T::Balance {
			T::WeightToFee::weight_to_fee(
				&T::WeightInfo::do_process_message().saturating_add(T::WeightInfo::commit_single()),
			)
		}

		// 1 DOT has 10 digits of precision
		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}
