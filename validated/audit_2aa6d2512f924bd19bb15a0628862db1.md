### Title
Fixed-window stream throttling reset allows attacker to double effective stream throughput by straddling `STREAM_THROTTLING_INTERVAL` boundaries - (streamer/src/nonblocking/stream_throttle.rs)

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed` implements a fixed (non-sliding) window rate limiter that zeroes `stream_count` only once `STREAM_THROTTLING_INTERVAL` has fully elapsed since the last reset. An attacker who opens streams right before a reset and again immediately after can push up to `2 * max_streams_per_throttling_interval` streams through in a period much shorter than `2 * STREAM_THROTTLING_INTERVAL`, and can repeat this indefinitely by timing every subsequent reset the same way.

### Finding Description
`reset_throttling_params_if_needed` [1](#0-0)  resets `stream_count` to `0` and records a new `last_throttling_instant` only when `now - last_throttling_instant > STREAM_THROTTLING_INTERVAL`. `throttle_stream` then compares the current `stream_count` against `max_streams_per_throttling_interval` and sleeps the remainder of the interval only if the cap is already exceeded [2](#0-1) .

Because this is a fixed-window counter keyed off a single `last_throttling_instant` timestamp rather than a sliding window, an attacker fully controlling the timing of stream opens on their own QUIC connection can:
1. Open streams up to the cap just before `last_throttling_instant + STREAM_THROTTLING_INTERVAL` elapses (window N).
2. Immediately after the reset fires (window N+1 starts), open another full cap's worth of streams.

Both bursts land inside a wall-clock span that can be made arbitrarily close to `STREAM_THROTTLING_INTERVAL` (100ms, per `STREAM_THROTTLING_INTERVAL_MS`), effectively doubling the number of streams accepted from that connection in that span compared to what the per-interval cap is intended to allow. Because the reset is purely time-based per connection and re-triggers identically at every subsequent boundary, this can be repeated on every window, yielding a sustained ~2x increase in accepted stream opens for that one connection relative to the intended `max_streams_per_throttling_interval` rate.

### Impact Explanation
This is a QoS-evasion class issue: the throttling scheme in `throttle_stream`/`ConnectionStreamCounter` is meant to cap the rate of streams (and thus transactions) a single connection can push into the TPU per `STREAM_THROTTLING_INTERVAL`. The boundary-straddling technique lets one unstaked or staked attacker connection sustain roughly double its allotted stream rate, i.e. evading the per-connection QoS cap that `available_load_capacity_in_throttling_duration` computes from stake/unstaked quotas [3](#0-2) . The effect is scoped to the throughput allowance of the single attacking connection — it does not directly steal a counter from other connections, since each connection has its own `ConnectionStreamCounter` — but it does let that connection push more transactions into downstream processing (sigverify/banking) than the throttle was designed to admit, within the bounty's QoS-evasion category.

### Likelihood Explanation
This requires no special privilege: any unstaked remote client opening a QUIC connection to the TPU can control exactly when it opens new streams relative to wall-clock time, and `Instant`/`tokio::time::Instant` boundaries are observable/predictable via repeated probing (e.g., via the sleep durations returned by prior throttling events, or trial-and-error with local clock). The race only needs coarse (millisecond-level) timing precision against a 100ms window, which is easily achievable from a standard network client. The technique is inherent to the fixed-window design and does not depend on races with other threads beyond the already-handled recheck-after-write-lock logic.

### Recommendation
Replace the fixed-window reset with a proper sliding-window or token-bucket algorithm (e.g., track fractional replenishment based on elapsed time, or a rolling deque/timestamp-based sliding window) so cumulative streams over any window of size `STREAM_THROTTLING_INTERVAL` are bounded by `max_streams_per_throttling_interval`, regardless of alignment with reset boundaries.

### Proof of Concept
Unit/invariant test plan for `streamer/src/nonblocking/stream_throttle.rs`:
```rust
#[tokio::test]
async fn test_boundary_straddle_doubles_throughput() {
    let stats = StreamerStats::default();
    let counter = Arc::new(ConnectionStreamCounter::new());
    let cap = 50u64; // max_streams_per_throttling_interval

    // Simulate bursts clustered at reset boundaries and record timestamps
    // of every accepted stream over multiple STREAM_THROTTLING_INTERVAL windows.
    let mut accepted_timestamps = Vec::new();

    for _ in 0..cap {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
        accepted_timestamps.push(tokio::time::Instant::now());
    }
    // Wait until just after the interval elapses (reset fires).
    tokio::time::sleep(STREAM_THROTTLING_INTERVAL + Duration::from_millis(1)).await;
    counter.reset_throttling_params_if_needed(); // triggers reset

    for _ in 0..cap {
        counter.stream_count.fetch_add(1, Ordering::Relaxed);
        accepted_timestamps.push(tokio::time::Instant::now());
    }

    // Assert: max streams observed in ANY sliding window of size
    // STREAM_THROTTLING_INTERVAL should not exceed `cap`, but this
    // will fail because 2*cap streams landed within a span < 2*STREAM_THROTTLING_INTERVAL,
    // with a sub-window straddling the reset containing close to 2*cap.
    let max_in_any_window = max_streams_in_sliding_window(&accepted_timestamps, STREAM_THROTTLING_INTERVAL);
    assert!(max_in_any_window <= cap, "throttle evaded: {max_in_any_window} > {cap}");
}
```
Expected result: the assertion fails, demonstrating that up to ~`2 * cap` streams can be observed within a single `STREAM_THROTTLING_INTERVAL`-sized sliding window when bursts are timed around the fixed-window reset boundary.

    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
