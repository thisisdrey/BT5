### Title
Unsigned integer wraparound in `EnsureRemaining()` allows out-of-bounds read of crafted ZIP/JAR entries in ijar's `InputZipFile::ProcessNext` - (`third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessNext()` computes the local-file-header pointer as `p = zipdata_in_ + in_offset_ + offset`, where `offset` is a fully attacker-controlled 64-bit value taken directly from the central directory record (or its Zip64 extra field), with no bound check against the mmapped file length before use. [1](#0-0)  The subsequent bounds check, `EnsureRemaining()`, computes `remaining = input_file_->Length() - in_offset` using unsigned `size_t` arithmetic; if the crafted `offset` pushes `p` past the end of the mapped buffer, `in_offset` exceeds `Length()` and the subtraction wraps around to a huge value, defeating the "not enough bytes remain" check entirely. [2](#0-1)  This mirrors the class of bug fixed in the erofs report: an unchecked, attacker-supplied offset/size field participates in unsigned pointer/length arithmetic that wraps, silently bypassing the bounds check that should stop out-of-bounds access.

### Finding Description
In `ProcessCentralDirEntry`, the `offset` output parameter is read straight from the 32-bit central-directory "relative offset of local header" field, and is further overridden by an attacker-controlled 64-bit value from the Zip64 extra field (`ZIP64_EXTRA_FIELD_TAG`) with no upper-bound validation against the file size: [3](#0-2) 

`ProcessNext()` then unconditionally uses that offset to move the cursor:
```
p = zipdata_in_ + in_offset_ + offset;
if (EnsureRemaining(4, "signature") < 0) { return false; }
``` [4](#0-3) 

`EnsureRemaining()` is the only guard protecting all subsequent reads (`get_u4le`, `get_u2le`, `memcpy`, etc.) in `ProcessLocalFileEntry`, `SkipFile`, and `UncompressFile`:
```
int EnsureRemaining(size_t n, const char *state) {
  size_t in_offset = p - zipdata_in_;
  size_t remaining = input_file_->Length() - in_offset;
  if (n > remaining) { return error(...); }
  return 0;
}
``` [5](#0-4) 

`Length()` returns a `size_t` obtained from the actual mmap size of the input file. [6](#0-5)  If `offset` (attacker controlled, up to 2^64-1 via the Zip64 extra field, or up to 2^32-1 via the plain 32-bit field) is chosen so that `p` lands past `zipdata_in_ + Length()`, then `in_offset > Length()`, and `remaining = Length() - in_offset` wraps to a huge unsigned value — exactly the "cur += bv_len" wraparound pattern described in the erofs report, where an attacker-controlled offset/size participates in unsigned arithmetic that is expected to detect overflow/OOB but instead produces a bogus large "remaining" value. With the check defeated, `get_u4le(p)` and later reads in `ProcessLocalFileEntry` (e.g., `get_u2le` for `file_name_length_`, `extra_field_length_`, and `memcpy` calls in `ProcessCentralDirEntry`'s filename copy) operate on a wild, out-of-bounds pointer, causing an out-of-bounds read (and potential crash/info leak) well outside the memory-mapped input file. [7](#0-6) 

Note that the comment above `ProcessCentralDirEntry` claims "the central directory is always followed by another data structure that has a signature, so parsing it this way is safe" — but this reasoning only protects central-directory parsing itself; it does not protect the `local_header_offset`-derived pointer arithmetic in `ProcessNext`/`EnsureRemaining`, which is the actual vulnerable path. [8](#0-7) 

### Impact Explanation
This code path (`third_party/ijar/zip.cc`, shared by the `ijar` interface-jar tool and `singlejar`/`InputJar`) processes ZIP/JAR files that are frequently *not* originated by the trusted root workspace — e.g., third-party `.jar` dependencies fetched via `http_jar`/`http_archive`/Maven rules and consumed directly by `java_import`/`java_library`, which get run through `ijar` to produce interface jars during ordinary builds. An attacker who controls such a dependency artifact (the "hostile origin server" scenario) can craft a ZIP whose central directory declares an out-of-range `local_header_offset` (or Zip64-extended offset). Because the file's own checksum, if pinned, only guarantees byte-for-byte integrity of the attacker's chosen (malicious) bytes — not that the ZIP structure is well-formed — checksum verification does not stop this: the corrupted structure is exactly what was fetched and hashed. The vulnerable code then dereferences a pointer derived from unchecked arithmetic, producing an out-of-bounds read relative to the mmapped buffer, which can crash the `ijar`/`singlejar` build tool (denial of service to the build) or leak adjacent process memory into build outputs/log via `get_u4le`/`memcpy` reads, depending on address-space layout.

### Likelihood Explanation
Any project that builds `java_library`/`java_import` targets with jar dependencies fetched from external sources runs `ijar` (and `singlejar` for merging) on those jars automatically as part of normal Bazel actions — no special configuration is required, and defaults do not sandbox or validate ZIP structural fields beyond the (broken) `EnsureRemaining` check. Crafting a ZIP central-directory entry with an out-of-range offset is straightforward with a hex editor or a ZIP-writing library. This requires no privileges beyond publishing/serving the malicious jar to be consumed as a build dependency.

### Recommendation
In `EnsureRemaining()` (and at the point where `p` is first computed from `offset` in `ProcessNext()`), validate that `p` lies within `[zipdata_in_, zipdata_in_ + input_file_->Length()]` before performing any subtraction; reject the entry with an error if `in_offset > input_file_->Length()` rather than computing `Length() - in_offset` unconditionally. Equivalently, bound-check the raw `offset` value against `input_file_->Length()` in `ProcessCentralDirEntry`/`ProcessNext` before it is added to `zipdata_in_`, mirroring the erofs fix's approach of adding explicit sanity checks on attacker-controlled offset/size fields before they participate in pointer/length arithmetic.

### Proof of Concept
A concrete JUnit/gtest reproduction (analogous to the existing `CreateZipWithMalformedExtraField` test scaffolding already present in `output_jar_simple_test.cc`) would:
1. Build a minimal ZIP with one central-directory entry whose `local_header_offset32` (or Zip64 extra-field 64-bit offset) is set to a value larger than the file's total length (e.g., `Length() + 0x100000000`).
2. Feed this ZIP through `InputZipFile::Open()`/`ProcessNext()` (as used by ijar/singlejar).
3. Observe that `EnsureRemaining(4, "signature")` in `zip.cc` does not return an error (because `Length() - in_offset` wraps around to a large unsigned value) and that `get_u4le(p)` subsequently reads from an out-of-bounds address, causing a crash or read of unrelated memory — demonstrating the check failed to stop the out-of-bounds access.   // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
