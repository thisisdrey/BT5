### Title
Null/empty-contract-list crash in transaction signature validation before contract-count check - (File: chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java)

### Summary
`TransactionCapsule.validateSignature()` unconditionally calls `getContract(0)` on the raw transaction's contract list before any check that the list is non-empty. This method is invoked directly from `Manager.pushTransaction()` prior to the point where `Manager.processTransaction()` enforces "contract list size must be exactly 1" [1](#0-0) . This mirrors the CVE-2023-37036 bug class: a protocol message missing an expected/required element (there, `ENB_UE_S1AP_ID`; here, the `contract` repeated field) is dereferenced/indexed without a presence check, causing an unhandled runtime exception in the transaction-processing path.

### Finding Description
`TransactionCapsule.validateSignature()` reads the first contract directly: [2](#0-1) 

This is called from `Manager.pushTransaction()` immediately after the transaction is queued and before `processTransaction()` (which is where the `getContractList().size() != 1` guard lives) is ever reached: [3](#0-2) 

The size guard that would normally prevent an empty-contract transaction from reaching `getContract(0)` only exists later, inside `processTransaction()`: [4](#0-3) 

If a transaction is submitted with zero entries in `raw_data.contract`, `getContract(0)` on an empty repeated-field list throws `IndexOutOfBoundsException`, an unchecked `RuntimeException` not declared in `pushTransaction()`'s throws clause and not caught anywhere in that method body, so it propagates out of the call. `getOwnerAddress()` has the identical unguarded pattern: [5](#0-4) 

Other call sites of `getContract(0)`/`getContractList().get(0)` in the same class (e.g. `validateSignature(Transaction, ...)` static overload) share this pattern: [6](#0-5) 

By contrast, the P2P inbound-transaction handler explicitly checks contract count before use, confirming that upstream code recognizes this precondition is required elsewhere but it is not uniformly enforced on the direct broadcast path: [7](#0-6) 

**Uncertainty**: I was unable to confirm within the available tool budget whether `Wallet.broadcastTransaction()` (the gRPC/HTTP entry point an anonymous client would use) performs its own `getContractCount()` check before calling `Manager.pushTransaction()`. If such a check exists there, this specific path would be blocked before reaching `validateSignature()`. I could not retrieve the relevant section of `Wallet.java` to verify this before running out of iterations.

### Impact Explanation
If reachable without a prior guard, an unhandled `IndexOutOfBoundsException` thrown out of `pushTransaction()` could propagate through the gRPC/HTTP request-handling thread. Depending on how the outer service layer handles uncaught runtime exceptions, this ranges from an ungraceful error response (low impact) up to disruption of the transaction-processing pipeline if the exception occurs while internal locks/sessions (`transactionLock`, `session`) are held, given the exception can be thrown after `pushTransactionQueue.add(trx)` but potentially inside the `synchronized` block depending on exact call ordering — risking inconsistent internal state or a node crash under adversarial input.

### Likelihood Explanation
Constructing a `Transaction` protobuf with an empty `contract` repeated field and valid-looking `raw_data`/signature framing is trivial for any client capable of crafting a raw transaction. The likelihood hinges entirely on whether an earlier layer (`Wallet.broadcastTransaction`) already rejects empty-contract transactions — a fact I could not verify.

### Recommendation
Add an explicit `getContractCount() == 0` guard at the very start of `TransactionCapsule.validateSignature()` and `getOwnerAddress()` (throwing `ValidateSignatureException`/returning empty, consistent with `validatePubSignature()`'s existing "miss sig or contract" check), rather than relying on callers to pre-validate. Additionally, confirm `Wallet.broadcastTransaction()` performs a contract-count check before invoking `Manager.pushTransaction()`.

### Proof of Concept
1. Craft a `Transaction` protobuf where `raw_data.contract` is an empty list but `raw_data` otherwise has valid `ref_block_bytes`/`ref_block_hash`/`expiration`, and add one arbitrary signature (or none — either path in `validateSignature()` reaches `getContract(0)` first).
2. Submit via the broadcast API to invoke `Manager.pushTransaction(trx)`.
3. Observe `trx.validateSignature(...)` at line 905 in `Manager.java` calls `this.getInstance().getRawData().getContract(0)` in `TransactionCapsule.validateSignature()`, throwing `IndexOutOfBoundsException` before the `getContractList().size() != 1` guard in `processTransaction()` is ever reached.

Because I could not confirm the absence of an earlier guard in `Wallet.broadcastTransaction()`, treat this as a candidate finding requiring confirmation via a live Devin session with full file access to `framework/src/main/java/org/tron/core/Wallet.java`, rather than a fully proven vulnerability.
