### Title
Missing slippage protection in `ExchangeWithdrawActuator` allows front-run manipulation of TRC10 exchange withdrawals - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The `ExchangeWithdrawContract` handled by `ExchangeWithdrawActuator` lets an exchange creator withdraw liquidity from a bancor-style TRC10 exchange pool, but unlike `ExchangeTransactionContract` (which carries an `expected` field enforced in `ExchangeTransactionActuator`), the withdraw contract has no minimum-output/slippage parameter at all.

### Finding Description
`ExchangeWithdrawContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — no expected/minimum counterpart amount field, as documented in the protobuf spec. [1](#0-0) 

In `ExchangeWithdrawActuator.doValidate()`/`execute()`, the amount of the "other" token returned to the withdrawer (`anotherTokenQuant`) is computed purely from the pool's current `firstTokenBalance`/`secondTokenBalance` ratio at execution time, with only a "not precise enough" rounding check — there is no check against any user-specified minimum. [2](#0-1) [3](#0-2) 

This is the same bug class described in the external report: a redemption/withdrawal operation whose output amount depends on pool state that can shift between transaction submission and execution, with no way for the caller to bound the acceptable output. In java-tron, any unprivileged account holding the traded tokens can submit a competing `ExchangeTransactionContract` (which is itself validated only by its own `expected` bound, and has no restriction preventing it from being placed immediately before a pending withdraw in the same block) to shift `firstTokenBalance`/`secondTokenBalance`, directly changing the ratio `ExchangeWithdrawActuator` will use for a subsequently-processed withdraw. [4](#0-3) 

By contrast, `ExchangeTransactionActuator` protects swappers via `tokenExpected`/`getExpected()`, confirming that the withdraw path is the one missing equivalent protection. [5](#0-4) 

### Impact Explanation
The exchange creator withdrawing liquidity can receive materially less of the counterpart asset than expected if the pool ratio is manipulated by any other network participant's `ExchangeTransactionContract` executed just before the withdrawal, causing an unexpected/unwanted loss of the withdrawn asset value — no code guarantees a minimum acceptable return. This is a Medium-impact fund-loss condition for the withdrawing party, mirroring the `initiateRedeem()`-style slippage issue from the report.

### Likelihood Explanation
Any account can freely submit `ExchangeTransactionContract` transactions against any exchange pool that has withdrawable balances, and transaction ordering within a block is not guaranteed to protect a pending `ExchangeWithdrawContract`, making this reachable by an ordinary unprivileged transaction broadcaster without any special permission.

### Recommendation
Add an `expected`/minimum-counterpart-amount field to `ExchangeWithdrawContract` (mirroring `ExchangeTransactionContract.expected`) and enforce it in `ExchangeWithdrawActuator.doValidate()`/`execute()` so a withdraw reverts if the computed `anotherTokenQuant` falls below the caller-specified minimum.

### Proof of Concept
1. Exchange creator submits `ExchangeWithdrawContract{exchange_id, token_id=firstToken, quant}` expecting `anotherTokenQuant` based on the pool's current ratio.
2. Before this transaction is packed/executed, any other account submits an `ExchangeTransactionContract` swapping a large amount into/out of the same exchange, shifting `firstTokenBalance`/`secondTokenBalance` (validated and executed per `ExchangeTransactionActuator.execute()`). [6](#0-5) 
3. The withdraw is then processed by `ExchangeWithdrawActuator.execute()`, computing `anotherTokenQuant` off the now-shifted balances with no lower bound, so the withdrawer receives a different (unfavorable) amount with no recourse. [7](#0-6)
