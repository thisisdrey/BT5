### Title
A contract called via `Operator.execute` inherits the victim's identity through the transient `MSG_SENDER` slot and can drain the victim's Synth positions - ([File: contracts/Operator.sol](contracts/Operator.sol))

### Summary
`Operator.execute` performs arbitrary user-supplied calls while the transient `MSG_SENDER` slot is set to the EOA. Every Synth contract resolves `_msgSender()` to that slot whenever `msg.sender == operator` — and this resolution happens *inside* the called contracts, not inside the Operator. A malicious contract included anywhere in the `calls_` array can therefore call `Pool`/`DepositToken`/`DebtToken`/`NativeTokenGateway`/`VesperGateway` directly and be treated as the victim, stealing unlocked deposits and collateral. This is the on-chain analog of CVE-2020-7385: the privileged client (the victim's operator session) exposes itself to whatever endpoint it connects to.

### Finding Description
In `contracts/Operator.sol:20-24`, `setMsgSender` writes `msg.sender` into transient slot `MSG_SENDER_STORAGE` for the *entire* batch, and `execute` (`contracts/Operator.sol:34-55`) then performs `functionCallWithValue` on each user-chosen `target`. In `contracts/utils/SynthContext.sol:14-24`, any Synth contract called with `msg.sender == operator` returns `getActualMsgSender()` — the victim — regardless of which intermediate contract initiated the call. So during call *i*, a malicious `target` can itself invoke e.g. `DepositToken.transfer(attacker, victimBalance)` or `DepositToken.withdraw(amount, attacker)` or `NativeTokenGateway.withdraw`/`VesperGateway.withdraw` and every `onlyIfSmartFarmingManager`-style sender check resolves to the victim.

The `nonReentrant` guard on `execute` only blocks reentry into `Operator.execute` itself (its own transient slot). `ReentrancyGuardTransient` is per-contract, so it provides zero protection for calls from the malicious target into `Pool`, `DepositToken`, etc. Nothing clears `MSG_SENDER` between calls, and nothing restricts which targets may be called — only the `msg.value == sum(values)` check constrains ETH accounting.

### Impact Explanation
Direct theft of user funds. Any call the victim could legitimately make (transfer msdTokens, withdraw unlocked collateral, burn/mint within health limits, claim via gateways) can be performed by the malicious target with the proceeds routed to the attacker, not the victim. `_revertIfLocked`/health checks limit damage to unlocked balances and healthy debt headroom, but unlocked deposit balances are fully stealable.

### Likelihood Explanation
Requires the victim to include an attacker-controlled contract in an `execute` batch — the same "connect to a malicious endpoint" precondition as the Metasploit report (a phishing/hack-back scenario: e.g., a fake swap router, zap, or helper contract advertised to Synth users, or a compromised router). The attacker is an unprivileged contract deployer; no privileged role is needed. Conditional but realistic.

### Recommendation
Whitelist/validate `target`s (e.g., only registered Synth contracts + `poolRegistry.swapper()` + gateways), or set/clear `MSG_SENDER` per-call and record which top-level call each subcall belongs to, or have Synth contracts accept the actual sender as an explicit parameter passed by `execute` rather than trusting any callee under the operator umbrella. At minimum, document that `execute` targets are fully trusted as the caller.

### Proof of Concept
```solidity
// Hardhat/Foundry sketch
// Attacker deploys:
contract Evil {
    function go(IDepositToken msd, address to) external {
        // Executes while MSG_SENDER == victim EOA
        uint256 bal = msd.unlockedBalanceOf(msg.sender == operator ? victim : msg.sender);
        msd.transfer(to, bal);            // steals victim's msdToken balance
        // or: msd.withdraw(bal, to)       // steals underlying collateral
        // or: NativeTokenGateway.withdraw(pool, bal) -> ETH to msg.sender resolution
    }
}

// Victim is enticed to run:
// operator.execute([{ target: evil, value: 0, callData: abi.encodeCall(Evil.go, (msdWETH, attacker)) }])
// During Evil.go, a call from Evil to DepositToken sees:
//   SynthContext._msgSender() == victim  (because msg.sender == operator)
// nonReentrant on Operator does not protect DepositToken.
```
Confirmed against `Operator.sol:36-54`, `SynthContext.sol:14-24`; `DepositToken.withdraw`/`transfer` and both gateways honor `getActualMsgSender` for withdrawals and transfers of unlocked balances.
