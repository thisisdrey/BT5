### Title
Out-of-bounds heap read parsing attacker-crafted ZIP central directory in ijar - (File: third_party/ijar/zip.cc)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` trusts length fields (`file_name_length`, `extra_field_length`, `file_comment_length`) taken directly from a memory-mapped ZIP/JAR file's central directory and advances/reads the buffer by those attacker-controlled values without ever validating them against the actual remaining size of the mapped file. This mirrors the libssh2 `sftp_symlink()` bug class: a length field from untrusted input drives a `memcpy`/pointer read with no check that the claimed length fits in the available buffer.

### Finding Description
`ProcessLocalFileEntry` calls `EnsureRemaining()` before reading variable-length fields such as `file_name_length_` and `extra_field_length_`: [1](#0-0) 

`ProcessCentralDirEntry`, however, reads `file_name_length`, `extra_field_length`, and `file_comment_length` straight from the mapped bytes and immediately performs a `memcpy` and pointer arithmetic based on them, with **no** call to `EnsureRemaining` or any other bounds check against `input_file_->Length()`: [2](#0-1) 

The function's own comment asserts this is "safe" only because "the central directory is always followed by another data structure that has a signature" — an assumption that holds for well-formed archives but not for a maliciously crafted one: [3](#0-2) 

If an attacker sets `file_name_length` (or `extra_field_length`) to a value larger than the bytes actually remaining in the mapped file (e.g., pointing near the true end of the mmap'd region), the `memcpy(filename, p, len)` call and the subsequent extra-field walk (`get_u2le`/`get_u8le` in the loop at lines 526-541) read past the end of the valid mapped data. This is invoked both by `ProcessNext` (used when extracting/copying entries) and by `CalculateOutputLength` (used to size the output interface jar) — both are on the hot path whenever ijar processes any input JAR: [4](#0-3) [5](#0-4) 

`ijar` is used by Bazel's Java toolchain to derive interface jars from dependency jars, so this parser directly processes third-party-supplied `.jar` files that reach a build via `http_jar`/`http_archive`-style dependencies. A whole-file `sha256`/integrity check on the downloaded archive (as used by `http_archive`/`http_jar`) verifies that the bytes match a pinned digest, but it does not validate that the internal ZIP structure is well-formed; an attacker who controls the origin of a dependency (and gets the victim to pin the corresponding hash, or exploits a hash that was pinned against attacker-supplied bytes) can still ship a byte-for-byte "correct" archive whose ZIP central directory contains an inflated length field, keeping the malicious internal structure entirely inside otherwise-verified content.

### Impact Explanation
This is a heap out-of-bounds read (potential crash / memory-disclosure into the copied `filename` buffer or into interpreted extra-field values) triggered purely by content of a dependency archive that a build consumes, with no interaction from a privileged operator. It matches the "read outside... output base" class of impact in scope: reads occur outside the bounds of the mapped input file into adjacent heap memory.

### Likelihood Explanation
Moderate. It requires the victim's build to run `ijar` over an attacker-influenced `.jar` (a normal occurrence for any external Java dependency), and requires no additional cache/credential interaction. The existing checksum/integrity mechanisms in `http_archive`/`http_jar` bind the *whole file* but do nothing to validate internal ZIP semantics, so they do not stop this class of malformed-but-hash-matching input.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry` before reading `file_name_length`, `extra_field_length`, and `file_comment_length`-sized regions, and bound-check the extra-field walk (`extra_p`/`data_size`) against the actual end of the mapped file, rejecting the archive with an error instead of reading past the mapping.

### Proof of Concept
Construct a minimal ZIP/JAR whose End-Of-Central-Directory and Central Directory Header are placed at (or very near) the true end of the mapped file, with the CDH's `file_name_length` (bytes at offset 28-29 of the CDH, per `third_party/ijar/zip_headers.h`/APPNOTE layout) set to a large value (e.g. `0xFFFF`) while only a few real bytes remain in the file. Feed this file to the existing `third_party/ijar/test/zip_test.sh` / `IjarTests.java` harness (or a new `BuildIntegrationTestCase`/shell test invoking the `ijar` binary on this crafted JAR) and observe a heap-buffer-overflow/ASan report (or crash) originating in `InputZipFile::ProcessCentralDirEntry`'s `memcpy` at line 520, rather than the graceful "invalid central file header" error that legitimate malformed inputs receive elsewhere in the parser.

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
