## Title
Integer-overflow bypass in `ValidateMultiSign` precompile signature-array bounds checks leads to uncaught runtime exception / node crash - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

## Summary
The CVE-2025-13654 bug class is a bounds check that can be bypassed because a subtraction/size calculation underflows, letting an out-of-bounds access happen. The closest reachable analog in java-tron is in the `ValidateMultiSign` precompiled contract's helper methods `extractBytesArray` / `extractSigArray`, which compute array lengths and byte offsets from fully attacker-controlled `DataWord[]` values with only partial bounds validation, and where the offset arithmetic can wrap due to `int` overflow, invalidating the earlier bounds checks.

## Finding Description
`ValidateMultiSign.execute()` is reachable from any TVM contract call (e.g. via the `validatemultisign` precompile address) with attacker-supplied `rawData`. It parses the payload into `DataWord[] words = DataWord.parseArray(rawData)` and computes an offset from `words[3].intValueSafe() / WORD_SIZE` without validating that this offset is within `words.length` before it's used to index `words[offset]`: [1](#0-0) 

The helper `extractBytesArray`/`extractSigArray` only check `offset > words.length - 1` for the initial index, but then loop `int i = 0; i < len` and index `words[offset + i + 1]` without re-checking bounds inside the loop, where `len = words[offset].intValueSafe()` is fully attacker-controlled (can be up to `Integer.MAX_VALUE`): [2](#0-1) 

Additionally, the byte offset used to slice `data` is computed as `(bytesOffset + offset + 2) * WORD_SIZE`, a plain `int` multiplication that can overflow/wrap to a negative value when `bytesOffset` (itself derived from `words[...].intValueSafe()`, unbounded) is large — analogous to the underflow condition in the CVE where a subtraction wraps and a bounds check that should reject the access instead passes: [3](#0-2) [4](#0-3) 

Because Java is memory-safe, this cannot produce a C-style out-of-bounds *read* into arbitrary memory; instead it produces `ArrayIndexOutOfBoundsException`, `NegativeArraySizeException`, or (via `new byte[len][]` with `len` up to `Integer.MAX_VALUE`) an `OutOfMemoryError`. Critically, the call to `extractSigArray`/`extractBytesArray` in `ValidateMultiSign.execute()` sits *outside* the surrounding `try { ... } catch (Throwable t)` block that wraps the rest of the signature-verification logic: [5](#0-4) 

so any exception thrown there propagates unguarded up through `execute()` into the TVM dispatch path.

## Impact Explanation
If the exception thrown by the malformed-offset arithmetic is not caught by a higher-level generic handler in the VM/precompile dispatch code (which I was unable to fully confirm due to iteration limits — see below), a crafted contract call that reaches `ValidateMultiSign` with a malicious `rawData` payload could throw an unhandled `RuntimeException`/`OutOfMemoryError` during transaction execution, potentially crashing the node process or halting block processing for that transaction. This matches the "node crash or halt" impact bucket allowed by the rules. I could not fully verify whether the TVM's transaction-execution wrapper (in `Program`/`Runtime`) already catches `Throwable` around precompile calls generically, which would downgrade this to a reverted transaction rather than a crash — this is the main open uncertainty in this finding.

## Likelihood Explanation
The precompile is reachable by any unprivileged account that can broadcast a `TriggerSmartContract` transaction targeting the `validatemultisign` precompiled address, requiring no special permission — an anonymous/ unprivileged contract caller can supply arbitrary `rawData` bytes to control `words[3]`, `words[offset]` (the claimed signature count), and `words[offset+i+1]` (per-signature offsets), directly driving the vulnerable arithmetic.

## Recommendation
- In `extractBytesArray`/`extractSigArray`, validate that `offset + len` stays within `words.length` before entering the loop, and validate `len` against a sane maximum (the code already enforces `MAX_SIZE = 5` for `sigArraySize`, but only when `allowTvmSelfdestructRestriction()` is enabled — enforce it unconditionally before calling either extraction helper).
- Perform all offset/length arithmetic using `long` (as already done elsewhere in the file, e.g. `getReturnDataBufferData`) and re-validate the resulting bounds before calling `Arrays.copyOfRange`/`System.arraycopy`.
- Move the `extractSigArray`/`extractBytesArray` invocation inside the existing `try { ... } catch (Throwable t)` block in `ValidateMultiSign.execute()` so any parsing failure degrades to `Pair.of(true, DATA_FALSE)` instead of propagating an uncaught exception.

## Proof of Concept
1. Construct a `TriggerSmartContract` transaction whose bytecode invokes the `validatemultisign` precompiled contract (address `0x...09`) with ABI-encoded input where:
   - `words[3]` (the signature-array offset word) is set to a large value such that `words[3].intValueSafe() / WORD_SIZE` lands on an attacker-chosen slot,
   - the word at that slot (`len`) is set to a large value (e.g. close to `Integer.MAX_VALUE / 32`),
   - subsequent per-signature offset words are set to large values so that `(bytesOffset + offset + 2) * WORD_SIZE` overflows `int`.
2. Broadcast the transaction with `allowTvmSelfdestructRestriction` enabled/disabled per network config to hit either `extractSigArray` or `extractBytesArray`.
3. Observe whether the resulting `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException`/`OutOfMemoryError` propagates out of `execute()` uncaught, causing abnormal termination of contract execution outside the intended `catch (Throwable t)` guard — full confirmation of node-level crash requires tracing the call up through `Program`'s precompile-dispatch code, which was not fully verified in this pass.
