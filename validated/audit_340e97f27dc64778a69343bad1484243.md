### Title
Users with multiple merkle leaves cannot claim their full allocation in `RecurringAirdrop.claim` - (File: contracts/utils/RecurringAirdrop.sol)

### Summary
`RecurringAirdrop.claim` verifies a leaf of `keccak256(abi.encodePacked(msg.sender, amount_))` but tracks per-account state via a single cumulative `claimed[msg.sender]` counter rather than per-leaf/index claim flags. If a merkle root contains more than one leaf for the same account, only the largest single leaf amount can ever be paid out; the remaining allocation is permanently locked in the contract.

### Finding Description
The claim logic is:

```solidity
bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

uint256 _claimable = amount_ - claimed[msg.sender];
if (_claimable == 0) revert NothingToClaim();

claimed[msg.sender] += _claimable;
_transferReward(msg.sender, _claimable);
``` [1](#0-0) 

The leaf carries no `index` or other per-leaf identifier, so the contract cannot distinguish "leaf N for account" from "cumulative total for account". Two failure modes mirror the TrufMigrator bug exactly:

- Claims in ascending order (leaf 100, then leaf 200 as independent allocations): the second call computes `_claimable = 200 - 100 = 100`, so the user receives 200 total instead of 300.
- Claims in descending order (leaf 200, then leaf 100): `amount_ - claimed` underflows (or equals a negative cast) — actually `100 - 200` reverts on the unchecked-adjacent subtraction, so the second claim reverts entirely.

Additionally, on every root rotation via `updateMerkleRoot` the `claimed` mapping persists across roots, which is only safe if every new tree's amounts are strictly cumulative over all prior distributions. Any non-cumulative leaf (e.g., a corrected/decreased amount, or per-epoch leaves under a fresh root) either under-pays or permanently reverts.

This affects `MetAirdrop`, which inherits `claim` unchanged and locks claimed MET into esMET via `_transferReward`, so under-claimed amounts are neither transferred nor locked on the user's behalf.

### Impact Explanation
Users whose address appears in more than one leaf of a distribution root — or whose leaf amount in a new root is not strictly cumulative — permanently lose the difference between their true total allocation and the largest single leaf amount. The unclaimed tokens remain locked in the airdrop contract with no recovery path (`claim` is the only token outflow; there is no sweep function). This is permanent freezing of unclaimed user rewards, meeting the impact bar.

### Likelihood Explanation
Exploitation requires no attacker action — it is a correctness/liveness bug triggered by a legitimate user calling `claim`. Likelihood depends on off-chain root generation: the contract enforces nothing preventing multiple leaves per account (leaves have no index field precisely because the design assumes one cumulative leaf per account). Any distribution that produces multiple leaves per account (e.g., per-epoch entries merged into one root, or additive allocations across incentive programs) triggers the loss. Root updates via `updateMerkleRoot` are governor-gated, but the bug manifests through the public unprivileged `claim` entry point.

### Recommendation
Include a leaf index (or distribution id) in the leaf encoding and track claims per leaf rather than per account:

```diff
- bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
+ bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, index_, amount_));
  if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();
- uint256 _claimable = amount_ - claimed[msg.sender];
- if (_claimable == 0) revert NothingToClaim();
- claimed[msg.sender] += _claimable;
+ if (claimed[merkleRoot][_leaf]) revert NothingToClaim();
+ claimed[merkleRoot][_leaf] = true;
- _transferReward(msg.sender, _claimable);
+ _transferReward(msg.sender, amount_);
```

Alternatively, document and enforce off-chain that each root contains exactly one cumulative leaf per account; the current code gives no on-chain guarantee of that invariant.

### Proof of Concept
Hardhat-style reproduction against `RecurringAirdrop`:

```ts
// Build a tree with two leaves for alice: (alice, 100) and (alice, 200)
// meaning two independent allocations totaling 300.
const leaf1 = keccak256(abi.encodePacked(alice.address, 100));
const leaf2 = keccak256(abi.encodePacked(alice.address, 200));
const root = merkleRootOf([leaf1, leaf2]);

await airdrop.updateMerkleRoot(root, proofsFileHash); // governor
await token.mint(airdrop.address, 300);

// Scenario A: ascending order -> underpaid
await airdrop.connect(alice).claim(100, proof1); // received: 100
await airdrop.connect(alice).claim(200, proof2); // _claimable = 200-100 = 100
// alice balance: 200, expected: 300 -> 100 permanently stuck

// Scenario B: descending order -> second claim reverts
// claim(200, proof2) succeeds; claim(100, proof1) reverts:
// 100 - 200 underflows -> panic
```

The same applies to `MetAirdrop` where the lost amount is MET that is never locked into esMET for the user.

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();
