### Title
MetAirdrop locks already-matured rewards by computing lock end from the latest root update instead of when the reward accrued - (File: contracts/MetAirdrop.sol)

### Summary
`MetAirdrop._transferReward` computes the lock end as `updatedAt + lockPeriod`, where `updatedAt` is the timestamp of the *most recent* `updateMerkleRoot` call, not the round in which the claimed rewards actually accrued. This is the same bug class as the TrufVesting `cancelVesting` issue: an "end of period" is derived from the wrong reference point, so the elapsed-time check produces an incorrect result. Here, every `updateMerkleRoot` call (a routine, recurring governor operation) resets the anchor and retroactively extends the lock end for all unclaimed rewards from earlier rounds.

### Finding Description
In `contracts/utils/RecurringAirdrop.sol:81-90`, `updateMerkleRoot` sets `updatedAt = block.timestamp` on every new round. In `contracts/MetAirdrop.sol:31-48`, `_transferReward` does:

```solidity
uint256 _end = updatedAt + lockPeriod;
if (_end < block.timestamp) {
    MET.safeTransfer(to_, amount_);
    return;
}
uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);
ESMET.lockFor(to_, amount_, _remainLockPeriod);
```

The claimed `amount_` is the *accumulated* entitlement (`amount_ - claimed[msg.sender]` in `RecurringAirdrop.claim`, line 58), which may include allocations that became fully claimable long ago. Once `lockPeriod` has elapsed after a round's `updatedAt`, the intent (per the natspec: "The `lockPeriod` starts from the current merkle root update") is that matured rewards are paid out in liquid `MET`. But because `updatedAt` is a single global timestamp overwritten by each subsequent root update, any user who claims after a newer root was published has their *entire* accumulated balance — including portions whose lock already fully expired under earlier roots — evaluated against the newest `updatedAt`.

Concrete sequence:
1. Governor posts root0 at `t0`. Alice has allocation `A0`. At `t0 + 8 days` (`lockPeriod = 7 days` elapsed), `A0` is matured — a claim would transfer liquid MET.
2. At `t0 + 8 days` the governor posts root1 (scheduled recurring round). `updatedAt = t0 + 8 days`.
3. Alice calls `claim(A1, proof)` (or even `claim(A0, proof)` against root1's cumulative tree). `_end = t0 + 8d + 7d = t0 + 15d > now`, so the entire claimable amount — including the already-matured `A0` — is pushed into `ESMET.lockFor` for ~7 more days.

Worse, when `_end - block.timestamp` is positive but below `ESMET.MINIMUM_LOCK_PERIOD() + 1`, `Math.max(..., _min)` inflates the lock to the full esMET minimum, potentially locking funds far beyond `updatedAt + lockPeriod`.

### Impact Explanation
Temporary freezing of user funds / unclaimed yield. Rewards whose lock period already expired are forcibly re-locked into esMET for up to a full `lockPeriod` (or the esMET minimum lock) merely because a new distribution round was published. Users cannot obtain liquid MET they are entitled to during that window, and esMET positions cannot be exited before `unlockTime`.

### Likelihood Explanation
High in terms of triggering conditions: `updateMerkleRoot` is designed to be called repeatedly ("Recurring"Airdrop, multi-round tests in `test/MetAirdrop.test.ts`), and late claimers claiming accumulated amounts across rounds is the normal, tested flow. Every user who claims between a root update and `updatedAt + lockPeriod` while holding matured entitlements is affected. The trigger is a routine protocol operation plus a user claim — no privileged misbehavior required.

### Recommendation
Track the lock anchor per-round or per-allocation rather than a single global `updatedAt`. E.g., store an array/mapping of `(root, updatedAt)` and compute `_end` from the timestamp of the round(s) the claimed amounts belong to; or compute claimable rewards as liquid for the portion whose round-level `updatedAt + lockPeriod` has passed and lock only the immature remainder. Alternatively, snapshot per-account lock expiry at first claim instead of re-deriving it from the latest root.

### Proof of Concept
Hardhat mainnet-fork test extending `test/MetAirdrop.test.ts` (which already uses `enableForking` and real `esMET`):

```typescript
it('re-locks matured rewards after a new root update', async function () {
  // root0 posted in fixture at t0; alice has rewards0 allocation
  const lockPeriod = await airdrop.lockPeriod()
  const updatedAt0 = await airdrop.updatedAt()

  // Let the lock for round 0 fully expire
  await time.increaseTo(updatedAt0.add(lockPeriod).add(1))

  // Control: a claim now would pay liquid MET
  // Governor posts the next recurring round -> updatedAt resets
  await airdrop.updateMerkleRoot(merkleRoot1, `0x${randomBytes(32).toString('hex')}`)

  // Alice claims accumulated amount under root1
  const amount = rewards1[alice.address]
  const leaf = generateLeaf(alice.address, amount)
  const proof = merkleTree1.getHexProof(leaf)

  const id = await esMET721.nextTokenId()
  await airdrop.connect(alice).claim(amount, proof)

  // BUG: entire claimable (incl. the matured round-0 portion) is locked again
  const {unlockTime} = await esMET.positions(id)
  expect(unlockTime).to.be.gt(updatedAt0.add(lockPeriod)) // locked past original maturity
  expect(await met.balanceOf(alice.address)).eq(0)      // no liquid MET received
})
```

Without a new root update, the same claim after `updatedAt0 + lockPeriod` returns liquid MET (`_end < block.timestamp` branch, `MetAirdrop.sol:34-36`), proving the freeze is caused solely by `updatedAt` being overwritten. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    function _transferReward(address to_, uint256 amount_) internal override {
        uint256 _end = updatedAt + lockPeriod;

        if (_end < block.timestamp) {
            MET.safeTransfer(to_, amount_);
            return;
        }

        uint256 _min = ESMET.MINIMUM_LOCK_PERIOD() + 1;
        uint256 _max = ESMET.MAXIMUM_LOCK_PERIOD();

        // Ensures valid lock period
        uint256 _remainLockPeriod = Math.min(Math.max(_end - block.timestamp, _min), _max);

        token.safeApprove(address(ESMET), 0);
        token.safeApprove(address(ESMET), amount_);
        ESMET.lockFor(to_, amount_, _remainLockPeriod);
    }

    function claim(uint256 amount_, bytes32[] calldata proof_) external nonReentrant {
        if (merkleRoot == bytes32(0)) revert NothingToClaim();

        bytes32 _leaf = keccak256(abi.encodePacked(msg.sender, amount_));
        if (!MerkleProof.verify(proof_, merkleRoot, _leaf)) revert InvalidProof();

        uint256 _claimable = amount_ - claimed[msg.sender];
        if (_claimable == 0) revert NothingToClaim();

        claimed[msg.sender] += _claimable;

        _transferReward(msg.sender, _claimable);

        emit RewardClaimed(msg.sender, _claimable);
    }

        if (merkleRoot_ == merkleRoot) revert NewMerkleRootSameAsCurrent();
        if (proofsFileHash_ == bytes32(0)) revert ProofsFileIsNull();

        merkleRoot = merkleRoot_;
        updatedAt = block.timestamp;
        proofsFileHash = proofsFileHash_;
