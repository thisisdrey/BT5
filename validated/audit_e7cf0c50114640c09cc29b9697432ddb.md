### Title
Oversized receipt bypasses `max_receipt_size` validation via post-check `output_data_receivers` mutation - (File: `runtime/runtime/src/verifier.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`validate_receipt` in `runtime/runtime/src/verifier.rs` checks a newly created receipt's serialized size against `limit_config.max_receipt_size` at the moment the receipt is created via `promise_return`/`promise_batch_create`, but `output_data_receivers` are appended to that already-validated receipt afterward during `apply_action_receipt`'s "Output data" step in `runtime/runtime/src/lib.rs`. This lets an attacker craft a receipt that is exactly `max_receipt_size` at validation time and then grows past the limit once the data receiver metadata is attached, producing a final outgoing receipt that exceeds the hard limit despite passing validation.

### Finding Description
`validate_receipt` performs the size check only `if mode == ValidateReceiptMode::NewReceipt`, computing `borsh::object_length(receipt)` and comparing against `limit_config.max_receipt_size` [1](#0-0) . This check runs when the receipt is first created inside the receipt-manager/VM logic path, before `output_data_receivers` are populated for the receipt that will ultimately hold the callee's returned data.

During `apply_action_receipt`, step 10 ("Output data") appends output-data-receiver metadata to a receipt (either an already-created `ReceiptIndex`'s receipt absorbs them, or new `Data` receipts are appended) at `runtime/runtime/src/lib.rs:1034-1073`, which happens after the per-action `validate_receipt(..., NewReceipt)` calls that occurred during action execution at `runtime/runtime/src/lib.rs:871` (per action loop) [2](#0-1) . Because the size check is a one-time gate at creation, not re-validated after this later mutation, a receipt that was exactly at the size limit when created can end up larger than `max_receipt_size` by the time it is emitted as an outgoing receipt via `receipt_sink.forward_or_buffer_receipt`.

The attack requires only: deploying `near_test_contracts::rs_contract()` (a self-deployed, unprivileged contract) and calling its `max_receipt_size_promise_return_method1` method with `args_size` sized so the resulting Promise-C receipt equals `max_receipt_size` exactly before `output_data_receivers` is attached from the `-then->` continuation. This is exactly reproduced by `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs:130-208`, whose code comment explicitly states: "Size of this receipt will be equal to `max_receipt_size`, it'll pass validation, but then `output_data_receivers` will be modified and the receipt's size will go above `max_receipt_size`. The receipt should be rejected, but currently isn't because of a bug (See https://github.com/near/nearcore/issues/12606)" [3](#0-2) . The test computes `args_size = max_receipt_size - base_receipt_size` and asserts via `assert_oversized_receipt_occurred` that a receipt above `max_receipt_size` is found in the chain's incoming receipt proofs [4](#0-3) . A sibling test `test_max_receipt_size_value_return` demonstrates the equivalent bug via a large returned value wrapped in a `Data` receipt.

No other check (signature, nonce, access-key, gas metering, storage staking) re-validates the final serialized receipt size after `output_data_receivers`/return-value wrapping, so the oversized receipt is admitted into the outgoing receipt queue.

### Impact Explanation
This matches the "shard-halting panic / state-root divergence" category: an oversized receipt that exceeds the protocol's hard size limit is forwarded/buffered as a real outgoing receipt and included by chunk producers in following chunks' incoming receipts. Since `max_receipt_size` is a protocol-level invariant that downstream code, storage proofs, congestion/bandwidth accounting, and other validators may assume holds, admitting a receipt that violates it risks cross-validator disagreement or unexpected behavior when receiving/proving/replaying this receipt on the receiving shard, as flagged by the upstream tracking issue #12606.

### Likelihood Explanation
Fully reachable by an unprivileged account: only requires funding an account, deploying the standard `near-test-contracts` rs_contract (or an equivalent custom contract using `promise_return`/value-return), and submitting one transaction with an attacker-chosen `args_size` computed from public config (`max_receipt_size`). No special permissions, validator access, or race conditions are needed, and it is fully deterministic/repeatable.

### Recommendation
Re-validate (or re-check size) the final receipt after all output-data-receiver/return-value mutations are applied — i.e., call `validate_receipt` (or a leaner size-only check) again just before the receipt is committed to `new_receipts`/handed to `receipt_sink.forward_or_buffer_receipt`, so the check happens on the fully-assembled receipt rather than only at creation time.

### Proof of Concept
Use `test_max_receipt_size_promise_return` in `test-loop-tests/src/tests/max_receipt_size.rs:130-208` (already present in the repo, currently expected to demonstrate the bug per the referenced issue): deploy `rs_contract()`, compute `base_receipt_size` via `borsh::object_length` on a template receipt, set `args_size = max_receipt_size - base_receipt_size`, call `max_receipt_size_promise_return_method1`, then assert (via `assert_oversized_receipt_occurred`) that a receipt with `borsh::object_length(receipt) > max_receipt_size` appears among the chain's incoming/outgoing receipt proofs, confirming the size check in `validate_receipt` was satisfied at creation time (`Ok`) but the final receipt exceeds the limit.

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
