### Title
Active-permission "operations" bitmap authorizes by contract type only, letting a limited-scope (trading-only) subkey drain an account's entire TRX balance via `TriggerSmartContract` - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
java-tron's multi-signature "Active permission" mechanism is the on-chain analog of a Paradex-style "subkey" used to grant limited trading-bot access without withdrawal rights. However, the permission-enforcement logic only checks whether a signer's permission has the bit for the invoked `ContractType` set; it never restricts the TRX value (`call_value`) that can be moved when that contract type is `TriggerSmartContract`. Because triggering a smart contract already allows sending an arbitrary `call_value` out of the owner account, an Active key scoped only to "trading" (`TriggerSmartContract`) can move the account's full TRX balance to any contract/attacker address in a single signed transaction, exactly mirroring the Mithril incident where subkeys "do not allow withdrawals" but ended up being powerful enough to move funds.

### Finding Description
`AccountPermissionUpdateActuator.checkPermission` only validates that the bits set in an Active permission's `operations` bitmap correspond to *known contract types*; it places no additional constraint on the semantics or value-transfer potential of any contract type: [1](#0-0) 

At transaction-processing time, the only guard that limits what an Active-permission key may do is a per-`ContractType` bit check, with no notion of value or destination restriction: [2](#0-1) [3](#0-2) 

Once a `TriggerSmartContract` transaction passes this coarse check, `VMActuator.call()` unconditionally transfers the full requested `call_value` from the caller (owner) account to the target contract before any TVM execution occurs: [4](#0-3) 

From inside that contract, the funds can be forwarded anywhere (e.g., `selfdestruct` to an attacker-controlled address, or a `transfer`/`call` in the contract body), as demonstrated by the existing test suite showing arbitrary TRX movement through triggered contracts: [5](#0-4) 

Thus, a user who—following the exact Paradex/Mithril model—creates an Active permission intended only for "trading" (enabling just the `TriggerSmartContract` bit) so a bot/subkey cannot withdraw funds, is not actually protected: any key holding that permission can sign a `TriggerSmartContract` transaction with `call_value` equal to the account's entire TRX balance directed at an attacker-deployed contract, draining the account. The permission model (`Permission.operations`, a 256-bit map keyed only by `ContractType`) has no field to cap value, so this is not misconfiguration by the account owner—it's a structural gap in the authorization model: [6](#0-5) 

### Impact Explanation
This allows unauthorized, permanent theft of TRX funds from any account that uses TRON's multisig/subkey feature to grant a "trading-only" Active permission—precisely the use case highlighted by the Paradex/Mithril incident (third-party bots holding subkeys with trading but not withdrawal rights). If such a subkey is leaked or the connected service is compromised, the attacker can immediately drain the full TRX balance of the account, not just perform limited "trading" actions, defeating the entire security assumption of TRON's permission-scoping design for delegated/bot access.

### Likelihood Explanation
Any account owner who sets up an Active permission for automated trading (a common documented use case for TRON multisig) and grants only the `TriggerSmartContract` bit is exposed. No special privilege beyond possession of that one subkey is needed—an attacker simply needs the leaked/compromised key (same threat model as the reported incident) to sign a single `TriggerSmartContract` transaction with `call_value` set to the full balance, targeting a contract the attacker controls.

### Recommendation
Introduce a value/asset-transfer constraint independent of contract-type bits for Active permissions—e.g., a configurable maximum `call_value` (and TRC10 `token_value`) per permission, or a dedicated bit/flag that must be explicitly enabled to allow non-zero `call_value` on `TriggerSmartContract`/`CreateSmartContract` when that permission is used. Enforce this new constraint in `AccountPermissionUpdateActuator.checkPermission`, `WalletUtil.checkPermissionOperations`/`TransactionUtil.checkPermissionOperations`, and in `VMActuator` prior to the `MUtil.transfer` call for callValue, so permissions intended for bounded automation (trading bots, subkeys) cannot be abused to move an account's full balance.

### Proof of Concept
1. Owner account `A` calls `AccountPermissionUpdateContract` to create an Active permission `P` with a single key `K` (the trading bot's address) and `operations` bitmap with only the `TriggerSmartContract` bit set (validated by `AccountPermissionUpdateActuator.checkPermission`).
2. Attacker obtains/leaks `K` (mirroring the Mithril bot compromise).
3. Attacker deploys or reuses any contract `C` with a `payable` fallback/function that forwards or self-destructs received TRX to attacker address `X`.
4. Attacker signs a `TriggerSmartContract` transaction from `A` with `permission_id = P.id`, `contract_address = C`, and `call_value = A.balance`, signed only by `K`.
5. `TransactionUtil.checkPermissionOperations`/`WalletUtil.checkPermissionOperations` pass because the `TriggerSmartContract` bit is set; `TransactionCapsule.checkWeight` passes with the single key's weight meeting the threshold.
6. `VMActuator.call()` executes `MUtil.transfer(rootRepository, A, C, call_value)` moving the entire balance to `C`, from which the attacker's contract logic sends it to `X`—despite `P` never being granted "withdrawal" (e.g., `TransferContract`) permission.

  public static boolean checkPermissionOperations(Permission permission, Contract contract)
      throws PermissionException {
    ByteString operations = permission.getOperations();
    if (operations.size() != 32) {
      throw new PermissionException(String.format("operations size must 32, actual: %d",
          operations.size()));
    }
    int contractType = contract.getTypeValue();
    boolean b = (operations.byteAt(contractType / 8) & (1 << (contractType % 8))) != 0;
    return b;
  }
