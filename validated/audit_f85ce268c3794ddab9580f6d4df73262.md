### Title
Native-contract resource delegation path skips the `supportUnfreezeDelay` feature-gate and lock-period checks enforced by the transaction actuators - (File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java)

### Summary
The `DelegateResourceContract`/`UnDelegateResourceContract` transaction type can be executed through two independent code paths that are supposed to enforce the same business rules: the ordinary transaction actuators (`DelegateResourceActuator`, `UnDelegateResourceActuator`) and the TVM native-contract processors (`DelegateResourceProcessor`, `UnDelegateResourceProcessor`) that are invoked when a smart contract calls the corresponding native/precompiled delegate/undelegate functionality from `Program.java`. Just like the reported `pairTransferNFTFrom()`/`pairTransferERC1155From()` vs `pairTransferERC20From()` inconsistency, one of the two sibling implementations is missing checks that the other enforces.

### Finding Description
`DelegateResourceActuator.validate()` requires both feature flags to be active before allowing delegation: [1](#0-0) 

The corresponding TVM native-contract validator, `DelegateResourceProcessor.validate()`, only checks `supportDR()` and never checks `supportUnfreezeDelay()`: [2](#0-1) 

The same asymmetry exists for the un-delegate path. `UnDelegateResourceActuator.validate()` checks both `supportDR()` and `supportUnfreezeDelay()`: [3](#0-2) 

While `UnDelegateResourceProcessor.validate()` only checks `supportDR()`: [4](#0-3) 

Additionally, `DelegateResourceActuator.validate()` performs extra lock-period bound checking gated by `supportMaxDelegateLockPeriod()` that has no counterpart visible in `DelegateResourceProcessor.validate()`: [5](#0-4) 

These processors are wired into the TVM execution path via `Program.java`, meaning any deployed smart contract can trigger delegate/undelegate resource operations through the native-contract mechanism, bypassing the committee-controlled `supportUnfreezeDelay` gate that ordinary `DelegateResourceContract`/`UnDelegateResourceContract` transactions must satisfy.

### Impact Explanation
`supportUnfreezeDelay` is a committee-activated hard-fork proposal that gates whether the "delegate/undelegate with lock" resource model is allowed to operate on the network. Because the actuator path enforces this flag but the TVM native-contract path does not, a contract can invoke delegate/undelegate resource operations (including with `lock`/`lockPeriod` parameters) even when the committee has not yet enabled this feature (as long as the older `supportDR` flag is on). This allows unauthorized use of functionality that is supposed to be feature-flagged, and — because the two code paths can diverge in behavior around a hard-fork boundary — it risks inconsistent execution results between nodes at different upgrade states, and it also skips lock-period bound validation, potentially permitting invalid/oversized lock periods to be recorded in `DelegatedResourceCapsule` state.

### Likelihood Explanation
This is reachable by any contract deployer/anonymous user simply by writing a smart contract that calls the native delegate/undelegate resource functionality, without needing any elevated privileges — matching the transaction-broadcaster/contract-deployer reachability required. No malicious SR/witness/peer role is needed.

### Recommendation
Add the same `dynamicStore.supportUnfreezeDelay()` check (and the lock-period bound validation performed in `DelegateResourceActuator`) to `DelegateResourceProcessor.validate()` and `UnDelegateResourceProcessor.validate()` so that both the transaction-actuator path and the TVM native-contract path enforce identical feature-gating and parameter validation.

### Proof of Concept
1. Deploy a contract that invokes the native delegateResource / unDelegateResource functionality (as exercised in `framework/src/test/java/org/tron/common/runtime/vm/FreezeV2Test.java`, `testDelegateResourceOperations`). [6](#0-5) 
2. On a network state where `supportDR` is enabled but `supportUnfreezeDelay` is not yet activated (e.g. during a rolling committee-proposal activation window), a normal `DelegateResourceContract`/`UnDelegateResourceContract` transaction would be rejected in `DelegateResourceActuator.validate()`/`UnDelegateResourceActuator.validate()` with "Not support Delegate/unDelegate resource transaction, need to be opened by the committee".
3. The same operation triggered via the contract's native-contract call succeeds because `DelegateResourceProcessor.validate()`/`UnDelegateResourceProcessor.validate()` never check `supportUnfreezeDelay()`, demonstrating the missing check compared to the actuator sibling function.

Note: I was not able to fully inspect `PrecompiledContracts.java`'s use of `supportUnfreezeDelay` or the complete `DelegateResourceProcessor`/`UnDelegateResourceProcessor` classes beyond the shown excerpts due to tool-call limits, so it is possible additional gating exists elsewhere in the call chain (e.g., in `Program.java` before invoking these processors) that I could not verify; this should be confirmed by a full review of `actuator/src/main/java/org/tron/core/vm/program/Program.java` and `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`.
