## Analysis

Looking at TRON's `Exchange*` actuators (the on-chain bancor-style AMM), I found a direct structural analog to the GoodEntry bug. In the GoodEntry report, `deposit()` computed a critical value (`fee0`/`fee1`) from the *live* pool state (`slot0` price) at execution time, with no bound on how much that live state could have drifted since the caller signed the transaction — so a state change between signing and execution caused an unexpectedly bad outcome for the caller, and the fix was to add a proper protection (an oracle-based, execution-time-independent calculation, as well as `expected`/slippage-style guards in later reports).

TRON's exchange actuators show the same pattern, but inconsistently: `ExchangeTransactionActuator` was deliberately hardened with a caller-supplied `expected` minimum-output check [1](#0-0) , protobuf-declared at [2](#0-1) . But `ExchangeInjectActuator` and `ExchangeWithdrawActuator` compute the "other token" amount purely from the **live pool ratio at execution time** — `firstTokenBalance`/`secondTokenBalance` read at `doValidate`/`execute` time — with no caller-supplied minimum/maximum bound at all: [3](#0-2)  and [4](#0-3) . Their protobuf contracts confirm there is no `expected` field for these two operations: [5](#0-4) .

Any account can shift the pool's `firstTokenBalance`/`secondTokenBalance` ratio via a public, unprivileged `ExchangeTransactionContract` trade [6](#0-5)  immediately before (and reverse it immediately after) an exchange creator's `ExchangeInject`/`ExchangeWithdraw` transaction lands in the same block, sandwiching the creator into injecting/withdrawing at an attacker-manipulated ratio — with zero on-chain slippage bound to reject it, unlike the `Transaction` path.

### Title
Unbounded pool-ratio dependence in `ExchangeInjectActuator`/`ExchangeWithdrawActuator` allows sandwich-attack theft of exchange liquidity - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java, actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
`ExchangeInjectActuator.execute()` and `ExchangeWithdrawActuator.execute()` derive the "other token" amount required/returned strictly from the exchange pool's current on-chain balances at execution time, with no caller-supplied minimum/maximum bound (`expected`) field, unlike `ExchangeTransactionActuator` which does enforce one. Because any unprivileged account can move the pool ratio with a public `ExchangeTransactionContract` immediately before an inject/withdraw transaction is packed into the same block, an attacker can sandwich a liquidity provider's inject/withdraw call and force it to execute at a manipulated ratio, extracting value from the exchange creator's inject/withdraw operation.

### Finding Description
`ExchangeInjectActuator.execute()` reads `firstTokenBalance`/`secondTokenBalance` from the `ExchangeCapsule` and computes `anotherTokenQuant` proportionally to whatever that ratio is at execution time: [7](#0-6) . The same pattern appears in `ExchangeWithdrawActuator.execute()`: [8](#0-7) . Neither `doValidate()` method nor the corresponding protobuf contracts (`ExchangeInjectContract`, `ExchangeWithdrawContract`) contain any caller-supplied bound comparable to `expected` in `ExchangeTransactionContract` [9](#0-8) . `ExchangeWithdrawActuator.doValidate()` only checks that the ratio computed is internally *self-consistent* (a rounding-precision check), not that it matches what the caller expected when they built the transaction: [10](#0-9) .

This is analogous to the GoodEntry `deposit()` flaw: a value central to the economic outcome of the call (`fee0`/`fee1` in GoodEntry; `anotherTokenQuant` here) is computed from live, mutable state at execution time without any protection against that state changing between signing and inclusion. In java-tron, that state can be intentionally and legitimately changed by any other account submitting an `ExchangeTransactionContract` trade against the same exchange pool in a preceding transaction within the same block, since `ExchangeTransaction` mutates `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`: [11](#0-10) .

### Impact Explanation
An attacker who observes a pending `ExchangeInject` or `ExchangeWithdraw` transaction from an exchange creator in the mempool can:
1. Submit an `ExchangeTransactionContract` trade that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably relative to what the creator intended.
2. Let the creator's `ExchangeInject`/`ExchangeWithdraw` execute against this manipulated ratio, causing the creator to deposit an over-valued token / withdraw an under-valued token relative to fair value.
3. Reverse the initial trade afterward to restore the ratio and pocket the difference.

This results in a direct, unauthorized transfer of value from the exchange creator (and indirectly the pool) to the attacker — a concrete theft-of-funds outcome, consistent with the GoodEntry finding's core impact (loss of funds due to an unprotected, execution-time-dependent ratio calculation).

### Likelihood Explanation
Both `ExchangeTransactionContract` (the manipulating leg) and `ExchangeInjectContract`/`ExchangeWithdrawContract` (the victim legs, restricted to the exchange creator) are ordinary, unprivileged, broadcastable transactions reachable by any account through the standard actuator/validate-execute pipeline. No special network role, node compromise, or off-chain condition is required — only normal transaction-ordering control within a block, which is achievable by any account submitting transactions in the appropriate order/fee to be sequenced adjacently. The exchange creator role itself is open to any account that created an exchange pair via `ExchangeCreateContract`, so this does not require any privileged/SR/witness capability.

### Recommendation
Add caller-supplied minimum/maximum bound parameters (analogous to `expected` in `ExchangeTransactionContract`) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce them in `ExchangeInjectActuator.doValidate()`/`execute()` and `ExchangeWithdrawActuator.doValidate()`/`execute()` by rejecting the transaction if the computed `anotherTokenQuant` falls outside the caller's specified tolerance — mirroring the fix pattern already used for `ExchangeTransactionActuator`.

### Proof of Concept
1. Exchange creator `C` builds `ExchangeInjectContract{exchangeId, tokenId=firstTokenID, quant=Q}` expecting `anotherTokenQuant ≈ secondTokenBalance * Q / firstTokenBalance` based on the ratio observed when building the transaction, and broadcasts it.
2. Attacker `A` observes this pending transaction and broadcasts `ExchangeTransactionContract{exchangeId, tokenId=secondTokenID, quant=X}` with higher priority/fee so it executes first in the same block, shifting `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()` [12](#0-11) .
3. `C`'s `ExchangeInjectActuator.execute()` then computes `anotherTokenQuant` from the now-manipulated balances [3](#0-2) , forcing `C` to inject a disproportionate, over-valued amount of the second token with no on-chain check preventing it.
4. `A` submits a reverse `ExchangeTransactionContract` afterward to restore the ratio, realizing a profit equal to the value `C` overpaid, with `C`'s injected liquidity (and thus funds) permanently devalued relative to fair market ratio.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();
