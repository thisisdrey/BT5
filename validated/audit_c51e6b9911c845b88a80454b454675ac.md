### Title
Account deletion leaves ReceivedData/PostponedReceipt/PromiseYield state orphaned under account_id, enabling cross-generation receipt execution - (File: core/store/src/utils/mod.rs `remove_account`)

### Summary
`remove_account` in `core/store/src/utils/mod.rs` only iterates the `ACCESS_KEY` and `CONTRACT_DATA` prefixes when cleaning up a deleted account's trie state, and unconditionally removes only the `Account` and `ContractCode` entries. It never scans or removes rows under `col::RECEIVED_DATA`, `col::POSTPONED_RECEIPT_ID`, `col::PENDING_DATA_COUNT`, `col::POSTPONED_RECEIPT`, `col::PROMISE_YIELD_RECEIPT`, `col::PROMISE_YIELD_STATUS`, `col::YIELD_ID_TO_DATA_ID`, or `col::DATA_ID_TO_YIELD_ID`, even though all of these are keyed by `account_id` per `TrieKey`'s `COLUMNS_WITH_ACCOUNT_ID_IN_KEY` list in `core/primitives/src/trie_key.rs:89-102`.

### Finding Description
`remove_account` (core/store/src/utils/mod.rs:505-575) performs:
- `state_update.remove(TrieKey::Account {..})`
- `state_update.remove(TrieKey::ContractCode {..})`
- iteration+removal over `trie_key_parsers::get_raw_prefix_for_access_keys(account_id)` (access keys + gas key nonces)
- iteration+removal over `trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[])` (contract storage) [1](#0-0) 

It never touches `TrieKey::ReceivedData`, `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount`, `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId`, all of which are addressed with `account_id` as the leading key component per `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY`: [2](#0-1) 

Because these columns are addressed purely by `account_id` (with no notion of "account generation" or deletion epoch), and NEAR's account-name model permits a fresh `CreateAccount` to reuse the exact same `account_id` string after a prior `DeleteAccount`, any outstanding `ReceivedData`/`PostponedReceipt`/`PendingDataCount`/`PromiseYield*` rows left behind by the deleted account become live again the instant the name is re-registered. If the still-pending input data later arrives (a `ReceivedDataReceipt` sent to that `account_id`), the runtime will decrement `PendingDataCount` and, once satisfied, pull and execute the orphaned `PostponedReceipt`/`PromiseYieldReceipt` against the *new* account's code/state/balance, using the old receipt's original `predecessor_id`. This lets a postponed callback constructed under one identity's context execute later under a completely different owner's contract/account, which can defeat `predecessor_id`/`assert_self`-style authorization checks that contracts rely on, and produces a trie footprint for the new account that is not a strict subset of the writes the new account's own transactions produced (violating determinism/exactness of state ownership).

I was not able to fully verify, within tool budget, whether `action_delete_account` (runtime/runtime/src/actions.rs) or `action_validation.rs` currently place any explicit precondition check blocking deletion of an account that still has pending/postponed receipts addressed to it; I located references in `runtime/runtime/src/actions.rs` and `runtime/runtime/src/action_validation.rs` but did not get to inspect their bodies before the iteration budget was exhausted. The column-boundary asymmetry in `remove_account` itself is confirmed directly from source, but full end-to-end confirmation of the attacker-reachable path (that `DeleteAccount` is not blocked while such rows exist) would require that additional check.

### Impact Explanation
If `DeleteAccount` is not itself gated on the absence of pending `ReceivedData`/`PostponedReceipt`/`PromiseYield*` rows, this asymmetry allows orphaned protocol-level receipt state to "reattach" to a differently-owned but same-named account, enabling authorization escalation across accounts/promises (a receipt/callback meant for the old account executing with old caller identity against new account code/balance) — this maps to NEAR's "authorization escalation across accounts or promises" and "state-root divergence" bounty categories, since the post-deletion trie footprint silently retains foreign, unaccounted-for entries.

### Likelihood Explanation
Preconditions are cheap for an ordinary account holder: fund `victim.near`, trigger a cross-contract call that creates one postponed action receipt (i.e., send an action receipt with more than one input data dependency, or one still-missing dependency) so that `PostponedReceipt`/`PendingDataCount`/`PostponedReceiptId` rows exist, then submit `DeleteAccount` for that account, then submit `CreateAccount` to re-register the same `account_id`. The cost is limited to standard transaction/gas fees; repeatability depends only on whether `DeleteAccount` validation rejects deletion while such rows exist, which I could not confirm in this pass.

### Recommendation
Extend `remove_account` in `core/store/src/utils/mod.rs` to enumerate and delete rows in every column listed in `col::COLUMNS_WITH_ACCOUNT_ID_IN_KEY` (`core/primitives/src/trie_key.rs:89-102`) for the account being deleted — specifically add prefix iteration/removal for `RECEIVED_DATA`, `POSTPONED_RECEIPT_ID`, `PENDING_DATA_COUNT`, `POSTPONED_RECEIPT`, `PROMISE_YIELD_RECEIPT`, `PROMISE_YIELD_STATUS`, `YIELD_ID_TO_DATA_ID`, and `DATA_ID_TO_YIELD_ID`. Alternatively/additionally, add an explicit precondition in `action_delete_account` that rejects deletion while any such account-scoped pending receipt/data state exists, preventing account-name reuse from inheriting foreign receipt state.

2. Call `remove_account(&mut state_update, &account_id)`.

```rust
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
```
