### Title
Deleted account's surviving PromiseYieldReceipt lets an attacker silently deploy a contract on a re-created account via PromiseResume, bypassing actor authorization - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/lib.rs`, `runtime/runtime/src/actions.rs`)

### Summary
`remove_account` (called from `action_delete_account`) deletes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` for a deleted account, but never removes any `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, or yield-id mapping entries tied to that `account_id`. If the same `account_id` string is later reused by a different owner (e.g. as a sub-account created by someone else), the surviving parked yield receipt still resolves against the new account, and its embedded actions execute with an `actor_id` computed from the *original* receipt's `predecessor_id`, which trivially equals the (recycled) `account_id` string, passing the self-only `DeployContract` permission check meant for the new owner.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:314-389`) refunds the balance and calls `remove_account(state_update, account_id)`, which only clears `Account`, `ContractCode`, access/gas keys, and `ContractData`: [1](#0-0) 
It never touches `TrieKey::PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, or `YieldIdToDataId`/`DataIdToYieldId` entries that reference this `account_id`.

A `PromiseYield` receipt is only ever a **self-receipt**: to satisfy `DeployContract`'s actor check (`predecessor_id == receiver_id == account_id`) the attacker, while they still own the account, issues `promise_yield_create` on themselves with a batch containing `DeployContract`. This is stored verbatim by `set_promise_yield_receipt` under `TrieKey::PromiseYieldReceipt{receiver_id: account_id, data_id}`: [2](#0-1) 

The attacker then deletes their own account. The yield receipt (and its timeout queue entry) survive in the trie, keyed only by the `account_id` string, with no binding to any specific "generation" of that account.

If the `account_id` string is later reused (recreating an account under that name is a normal, supported operation, confirmed by the existing `test_function_call_after_same_chunk_delete_recreate_resolves_fresh_code` test), the runtime keeps processing the pending yield exactly as before:

- `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3105`) walks the `PromiseYieldTimeout` queue purely by `expires_at`/`account_id`/`data_id`; when the deadline passes it synthesizes and forwards a `PromiseResume` receipt to the same `account_id`, without checking whether the account still exists or was recreated: [3](#0-2) 
- When that (or an explicit) `PromiseResume` is processed, `process_receipt` looks up `get_promise_yield_receipt(state_update, account_id, data_id)` — found, because it was never deleted — removes it, and re-executes it via `apply_action_receipt`: [4](#0-3) 
- `apply_action_receipt` initializes `actor_id = receipt.predecessor_id().clone()` from the *stored yield receipt* (the attacker's original self-receipt), not from anything tied to the new account owner: [5](#0-4) 
- `check_actor_permissions` for `DeployContract` only compares `actor_id != account_id` (string equality), and `check_account_existence` only requires `account.is_some()`: [6](#0-5) [7](#0-6) 

Because `actor_id` and `account_id` are both the recycled string, the check passes and `action_deploy_contract` runs, installing the attacker's wasm on the new owner's account — without any `AddKey`/`DeployContract` signed by the new owner, and without re-verifying that the "actor" authorization is still meaningful across the account's deletion/recreation boundary. This is an authorization-exactness violation: the runtime treats `AccountId` as a durable identity across the deletion/recreation boundary for the purpose of actor permission checks, when it should not.

### Impact Explanation
An unprivileged attacker can implant arbitrary contract code (e.g. a fund-draining or backdoored contract) onto an account belonging to a victim who has no knowledge of it, before the victim ever adds a key or deploys anything themselves. This is authorization escalation across account "generations" leading to contract implantation and potential theft of any funds subsequently sent to or held by that account, matching the "authorization escalation across accounts or promises" / "theft of user funds" bounty categories.

### Likelihood Explanation
Preconditions: the attacker must (1) own an account, (2) call `promise_yield_create` on themselves with a `DeployContract` action in the callback, (3) delete that account, and (4) have a different party recreate an account with the exact same `account_id` string within the yield's lifetime (`yield_timeout_length_in_blocks`, default 200 blocks, i.e. only a few minutes). The last condition is the main constraint — it requires either a race (attacker deletes and quickly triggers recreation, e.g. by controlling both a sub-account namespace and its child, or targeting a name that a victim is about to (re)register) — but it is entirely achievable by a normal, unprivileged client with only standard transactions, and repeatable at will (attacker fully controls timing of steps 1-3, only step 4 has some non-determinism, but the attacker can attempt this against many candidate account names/timings).

### Recommendation
When an account is deleted, `remove_account` should also purge all `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`, and yield-id mapping entries associated with that `account_id` (or the yield/timeout mechanisms should validate, at resume time, that the account has not been deleted/recreated since the yield was created, e.g. via a per-account creation nonce baked into the yield key or checked at resume time).

### Proof of Concept
Integration/test-loop test plan (modeled on `test-loop-tests/src/tests/yield_timeouts.rs` and `test-loop-tests/src/tests/create_delete_account.rs`):
1. Deploy a test contract to `attacker.near` exposing a method that calls `promise_yield_create` on itself, whose resumed callback executes `DeployContract` with attacker-controlled bytecode.
2. Call that method to create the yield; capture `data_id`.
3. Submit `DeleteAccount` on `attacker.near` (beneficiary arbitrary), removing the account while keeping the on-chain `PromiseYieldReceipt`.
4. From a different signer, create a new account named `attacker.near`-equivalent (e.g. a sub-account path allowing the exact name to be recycled, or use a hex-64 implicit-account variant) with its own key, simulating "the real owner".
5. Advance the chain past `yield_timeout_length_in_blocks` (or explicitly resume, if reachable) so `resolve_promise_yield_timeouts`/`process_receipt` re-executes the stored yield receipt against the recreated account.
6. Assert: `AccountContract` (via `get_account`/`view_state`) of the recreated account equals the attacker's contract code hash, despite no `AddKey` or `DeployContract` action ever having been signed by the new owner's key — demonstrating silent contract implantation.
