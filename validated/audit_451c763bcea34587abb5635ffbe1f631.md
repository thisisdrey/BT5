### Title
`nft_resolve_withdraw` mis-classifies a successful `nft_transfer_call` as failed when a malicious token contract returns non-bool JSON, causing a refund credit for an NFT that already left custody - (`contracts/defuse/src/contract/tokens/nep171/withdraw.rs`)

### Summary
`nft_resolve_withdraw` decides whether to refund a withdrawn NFT balance based on `promise_result_checked_json::<bool>(0)`. Because `token` in an NFT withdrawal is an attacker-controlled, arbitrary NEP-171 account, the attacker's own `nft_transfer_call` implementation can perform whatever "delivery" it wants internally while returning a promise value that succeeds (`PromiseResult::Successful`) but fails to deserialize as `bool` (e.g. the JSON integer `1`, which is ≤ `bool::max_json_length_root() == 7` bytes). This makes the resolver take the `Ok(Err(_deserialization_err)) => false` branch and re-credit the withdrawer's `token_balances`/`total_supplies` entry for that `Nep171TokenId` even though the withdrawal already "succeeded" per the malicious contract's own logic.

### Finding Description
Binding claimed broken: `debited(1) == delivered(1) + re-credited(1)` should hold as `1 == 1`, but is broken to `1 == 2` when a malicious `token` contract's `nft_transfer_call` both (a) proceeds with whatever internal state change it wants and (b) returns a non-bool JSON payload on success.

Code path:
- `internal_nft_withdraw` debits balance and total supply via `self.withdraw(...)` [1](#0-0)  then schedules `do_nft_withdraw` followed by `.then(nft_resolve_withdraw(...))` [2](#0-1) .
- `do_nft_withdraw` calls `ext_nft_core::ext_on(p).nft_transfer_call(receiver_id, token_id, ..., msg)` on the attacker-supplied `token` account when `msg` is `Some(...)` [3](#0-2) .
- `withdraw()` itself decrements both `token_balances` and `total_supplies` for the `Nep171TokenId` [4](#0-3) .
- `nft_resolve_withdraw` classifies success purely from JSON-deserializing the promise's raw bytes as `bool`: `Ok(Ok(used))` on well-formed bool, but `Ok(Err(_deserialization_err)) => false` when the promise succeeded with any other well-formed JSON that isn't a bool [5](#0-4) . On `used == false` it calls `self.deposit(sender_id, [(Nep171TokenId::new(token, token_id).into(), 1)], Some(REFUND_MEMO))`, re-adding to `token_balances` and `total_supplies` [6](#0-5) [7](#0-6) .
- The read is capped at `bool::max_json_length_root(()) == " false ".len() == 7` bytes [8](#0-7) [9](#0-8) , so a tiny non-bool payload (e.g. the JSON integer `1`) still fits and deterministically triggers the `Ok(Err(...))` branch instead of any length-based rejection.

Because `token` is a contract the attacker deploys and fully controls, they can implement `nft_transfer_call` to do anything they want internally (e.g. transition their own NFT bookkeeping to show `receiver_id` as owner) while returning `1` instead of `true`/`false`. The resolver has no way to distinguish "receiver_id already owns the token per the token contract's own semantics" from "the transfer genuinely failed" — it only inspects whether the returned bytes parse as `bool`. Existing guards (`assert_one_yocto`, `#[private]` on `nft_resolve_withdraw`, `#[pause]`) do not address this because they only gate who can call the withdraw/resolve entry points, not the semantics of an attacker-controlled callee's return value.

Attacker's exact call: deposit a self-issued NFT under a `token` account they control (`nft_on_transfer` credits `Nep171TokenId(token, "1")` balance = 1, `total_supplies` = 1), then call `nft_withdraw(token=token, receiver_id=attacker_or_controlled_contract, token_id="1", msg=Some("..."))`. Their `nft_transfer_call` implementation marks the token delivered internally and returns `1` (not `true`/`false`) as the promise's return value.

### Impact Explanation
`token_balances` and `total_supplies` for `Nep171TokenId(token, "1")` are restored to 1 by the resolver even though the withdrawal already "delivered" the token per the token contract's own state. The withdrawer can then repeat `nft_withdraw` for the same restored balance and again trigger the same misclassification, letting the ledger's single unit of "backing" be presented as delivered/settled more than once (each cycle: debit 1 → deliver via malicious `nft_transfer_call` → resolver wrongly refunds 1 back). If the attacker subsequently uses this persistently-restored `Nep171TokenId` balance inside a signed intent to trade against a counterparty's genuine tokens (a normal Defuse intent execution), the counterparty pays real value for a balance entry that the ledger claims is Defuse-custodied NFT but has, in fact, already been withdrawn/dispersed by the attacker. This matches the "refund or resolver credit that does not match what failed to settle" / repeat-settlement Critical category in the rules.

### Likelihood Explanation
Preconditions are fully within an unprivileged attacker's control: deploying and controlling their own NEP-171 contract as `token`, depositing a self-issued NFT to obtain the initial `Nep171TokenId` balance (permitted, no privileged role required), and calling `nft_withdraw` with `msg=Some(...)` themselves. No relayer key, DAO role, or victim key is required. The only genuine cost is gas and NFT-contract deployment, both trivial and repeatable across arbitrary token ids/accounts.

### Recommendation
`nft_resolve_withdraw` should not treat "promise succeeded but payload isn't a valid `bool`" as equivalent to "transfer failed, refund the sender." At minimum, an `Ok(Err(_deserialization_err))` on a successful promise result for `nft_transfer_call` should be treated the same way as `Err(_)` (i.e., `used = true`, no refund) rather than `used = false`, since a successful promise execution with malformed return data cannot be assumed to mean the receiver rejected/returned the token. More robustly, do not rely on the callee's self-reported return value at all for trust-sensitive refund decisions when `token` is an arbitrary, uncontrolled account — or restrict the meaning of "resolved refund" strictly to a well-formed `false`.

### Proof of Concept
`cargo test` plan (near-workspaces sandbox), asserting on both sides of the binding `debited == delivered + re-credited`:
1. Deploy a stub NEP-171 contract (`malicious_nft`) whose `nft_transfer_call` implementation: (a) records `token_id` as delivered/owned-by-`receiver_id` in its own storage, (b) returns the raw JSON `1` (not `true`) as its return value.
2. As `attacker`, deposit `malicious_nft`'s token id `"1"` into the Defuse contract (real NEP-171 `nft_transfer_call` to `env.defuse.contract_id()`), assert `mt_balance_of(attacker, Nep171TokenId(malicious_nft, "1")) == 1` and the contract's internal `total_supplies` view (via a query method) `== 1`.
3. Sign and execute `NftWithdraw { token: malicious_nft, receiver_id: attacker_or_controlled_receiver, token_id: "1", msg: Some(payload), .. }` via `execute_intents`.
4. Assert the stub contract's own storage shows the NFT delivered/owned by `receiver_id` (i.e., the "real" transfer succeeded).
5. Assert `mt_balance_of(attacker, Nep171TokenId(malicious_nft, "1")) == 1` again (resolver re-credited) — proving `debited(1) != delivered(1) + re-credited(1)` since the right-hand total is 2 while only one token ever existed.
6. Repeat step 3-5 a second time to demonstrate the cycle is repeatable, reinforcing the "settles more than once" characteristic.
