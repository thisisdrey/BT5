Fixed-schedule `CostPacer::scheduling_budget` computes a linear per-millisecond quota that ignores in-flight/enqueued cost, allowing bursty producers to claim a grossly under-priced share of the block's compute budget - (File: core/src/banking_stage/transaction_scheduler/scheduler_controller.rs)

### Summary
`CostPacer::scheduling_budget` (used by `SchedulerController::process_transactions` to bound `GreedyScheduler::schedule`'s `budget` argument) computes the allowed CU budget for the current scheduling pass purely from wall-clock elapsed time since leader-slot detection (`detection_time`), a fixed `fill_time`, and the *fixed* `block_limit`, then subtracts the (lagging) `shared_block_cost` snapshot. This mirrors the Teller `getMinInterestRate` bug pattern: a price/limit is derived from a *stale, time-based utilization estimate* rather than the actual amount of work that is about to be admitted, so a burst of unstaked/low-priority transactions arriving early in the linear ramp-up window can consume compute-unit budget far beyond what the intended pacing curve allows for that instant, effectively "renting" cheap admission before the schedule "catches up."

### Finding Description
`scheduling_budget` is computed as: [1](#0-0) 

```
target = allocation_per_milli * millis_since_detection   (before fill_time elapses)
budget = target.saturating_sub(shared_block_cost.load())
```

This target is a purely time-based linear ramp (`block_limit / fill_time_ms * elapsed_ms`), independent of how much cost has actually already been scheduled or is in flight in the current pass. It is called once per outer loop iteration in `process_transactions`, and the resulting `scheduling_budget` is handed directly to `GreedyScheduler::schedule` as the `budget` parameter: [2](#0-1) 

Inside `GreedyScheduler::schedule`, this `budget` is only reduced by in-flight CUs *at the very start* of the call, then consumed transaction-by-transaction within that single scheduling pass: [3](#0-2) [4](#0-3) 

Because `shared_block_cost` (the actual cost tracker state) is only updated after transactions are *executed* in `consumer.rs`'s `try_add_processed_transaction_costs` (which correctly folds in the new transaction's own cost via `cost_tracker.try_add`) — not at scheduling time — there is a window, at the very start of a leader slot (small `millis_since_detection`), where the pacer computes a small but non-zero `target`, and `shared_block_cost` is still stale/zero from the previous slot boundary detection. A burst of many small-cost but high-volume transactions scheduled in a single pass can be admitted up to the "budget" ceiling that was sized only against the *time elapsed*, not against the cost that this specific batch is about to add — analogous to Teller's bug where the rate was computed against pre-trade utilization instead of the utilization the new loan would create. The unfairness here isn't in transaction pricing (fees are unaffected) but in QoS/pacing fairness: it lets a burst of transactions bypass the intended "ramp up slowly" throttle that exists specifically to protect early-slot latency/consistency, effectively evading the designed admission-rate cap for that instant in the slot.

### Impact Explanation
This is a QoS-evasion class issue rather than a consensus-breaking one: the pacer’s job is purely to smooth out CU admission over the slot to reduce tail latency/jitter of the leader's own worker threads (`CostPacer` exists precisely to avoid dumping the whole block-cost budget into the scheduler on slot start). If the target computed doesn't account for the batch actually about to be admitted, a burst of transactions queued right at the pacing-detection boundary can consume its full window's allocation instantly, defeating the pacing goal and causing the underlying `consume_worker` threads to receive an oversized initial batch, which increases worst-case per-slot processing latency variance. This does not break the hard `CostTracker::would_fit` block-cost enforcement (which correctly always includes the new transaction's cost, per `cost-model/src/cost_tracker.rs` lines 272-310) — the real block-cost limit is still enforced downstream at execution time — so this is a pacing/fairness degradation, not an unbounded-resource or invalid-block bug.

### Likelihood Explanation
Moderate-to-low. The condition requires: (1) `SchedulerPacing::FillTimeMillis` enabled (the default), (2) a burst of transactions queued in the container right after a new leader slot is detected, before `fill_time` has elapsed. This is plausible in normal operation (leader slot boundaries happen every slot), but the impact is bounded by `target_scheduled_cus`/`GreedySchedulerConfig` limits within `GreedyScheduler::schedule` itself and by the hard block-cost check still enforced later, so exploitation only worsens pacing smoothness rather than violating any hard limit.

### Recommendation
Compute `scheduling_budget` relative to cost that has *actually been scheduled or executed so far in this slot*, not purely time-elapsed vs. a static linear allocation. Concretely, track cumulative CUs scheduled (not just in-flight) since slot start and clamp the per-call budget so that `allocation_per_milli * elapsed_ms` is treated as an upper bound only after subtracting already-scheduled-but-not-yet-reflected-in-`shared_block_cost` cost (i.e., include the scheduler's own pending batches, similar to how `GreedyScheduler` already subtracts in-flight CUs). This ensures the pacing target always reflects the true remaining allowance rather than a stale/time-only estimate.

### Proof of Concept
1. Leader slot begins; `CostPacer` is constructed with `detection_time = now`, `fill_time = Some(X ms)`, `block_limit = L`.
2. Immediately (within the first few ms), a large burst of low-cost, high-volume transactions arrives in the container (e.g., via `TransactionViewReceiveAndBuffer`).
3. `scheduling_budget(&now)` at `millis_since_detection ≈ 1ms` returns `allocation_per_milli * 1 - shared_block_cost.load()`, which, while nominally small, is computed without regard to how many transactions are already sitting in `self.common.batches`/`in_flight_tracker` for *this* pass being about to be scheduled — `GreedyScheduler::schedule` (lines 86-94) only subtracts in-flight CUs from previous passes, not the cumulative CUs the current burst is about to add across the loop until `budget` hits 0 (lines 132-219). Because `shared_block_cost` lags real scheduling by one full execute-and-commit cycle, several scheduler loop iterations can each report a similar small "budget" window and repeatedly admit transactions before `shared_block_cost` updates, cumulatively front-loading much more of the slot's CU budget early than the pacing curve intends — reproducible by unit-testing `CostPacer::scheduling_budget` with a fast sequence of calls and a `shared_block_cost` that is not updated between calls, as exercised (without the burst scenario) in `test_receive_then_schedule`'s test harness: [5](#0-4) .

```rust
impl CostPacer {
    fn scheduling_budget(&self, current_time: &Instant) -> u64 {
        let target = if let Some(fill_time) = &self.fill_time {
            let time_since = current_time.saturating_duration_since(self.detection_time);
            if time_since >= *fill_time {
                self.block_limit
            } else {
                // on millisecond granularity, pace the cost linearly.
                let allocation_per_milli = self.block_limit / fill_time.as_millis() as u64;
                let millis_since_detection = time_since.as_millis() as u64;
                allocation_per_milli * millis_since_detection
            }
        } else {
            self.block_limit
        };

        target.saturating_sub(self.shared_block_cost.load())
    }
```
