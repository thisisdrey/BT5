Confirmed: `action_to_promise(target, action)` uses `target` (the relayer-supplied `AccountId`, already validated by NEAR's `AccountId::parse`) as the actual promise receiver, not the `receiver_id: String` decoded from the ABI calldata. The `receiver_id` field inside `Action::FunctionCall`/`Action::Transfer` is discarded in `try_into_near_action` (`receiver_id: _`) at [1](#0-0) , so it never reaches the actual promise construction regardless of the equality check outcome.

### Analysis

The equality check in question is: [2](#0-1) 

`target` is a `near_sdk::AccountId`, which can only be constructed via `AccountId::validate`/`FromStr`, enforcing NEAR's strict account-id grammar (lowercase ASCII alphanumerics, `.`, `-`, `_`, no control characters, no null bytes, no non-ASCII). `target.as_str()` therefore always yields a canonical byte sequence with no possibility of alternate representations. `receiver_id` is a plain `String` decoded via ABI (`ethabi_utils::abi_decode`), which can contain arbitrary UTF-8 bytes, but the comparison `target.as_str() != receiver_id.as_str()` is a byte-for-byte `str` comparison in Rust — there is no normalization (Unicode NFC/NFD, case-folding, or null-byte-stripping) applied to either side. A trailing null byte, homoglyph, or differently-normalized Unicode form in `receiver_id` would make it byte-different from `target`, and the strict `!=` comparison would correctly detect the difference and reject it via `Error::Relayer(RelayerError::InvalidTarget)`. There is no code path in `AccountId` comparison or `str` comparison that treats byte-different strings as equal.

Furthermore, even if such a bypass existed, `receiver_id` is discarded and never used as the actual destination of the resulting NEAR action — `target` (the trusted, already-validated field) is what's passed to `action_to_promise` in [3](#0-2)  and in the main flow's `action_to_promise` call. This makes the described attack impossible on two independent levels: (1) no normalization gap exists in the comparison, and (2) the compared field isn't the one that determines routing.
