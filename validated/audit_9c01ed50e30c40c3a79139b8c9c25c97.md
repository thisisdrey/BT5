**Analysis of the claimed binding**

The question asks us to verify: `TokenId::from_str(&token_id.to_string()) == token_id` even when `mt_token_id` contains embedded colons, and whether a crafted `mt_token_id` like `"fake:realft.near"` could cause `contract_id` to resolve to `realft.near` instead of the attacker's own contract.

Tracing the actual code:

- `TokenId::from_str` splits the full string on the *first* colon to extract the type discriminant (`nep141`/`nep171`/`nep245`/`imt`) and passes the remainder (`data`) to the variant-specific parser: [1](#0-0) 
- `Nep245TokenId::from_str` then splits that remaining `data` on its *first* colon to separate `contract_id` from `mt_token_id`, and `Nep245TokenId`'s `Display` writes `"{contract_id}:{mt_token_id}"`: [2](#0-1) 

The key fact that preserves the roundtrip: `contract_id` is a `near_account_id::AccountId`, whose grammar does not permit colon characters. So in the serialized string `"{contract_id}:{mt_token_id}"`, the first colon after the type prefix is *guaranteed* to be exactly the separator NEAR account-id/token-id boundary — it cannot be confused with any colon embedded inside `mt_token_id`, because `contract_id` itself never contains one. `split_once` only splits at the first match and returns the *entire remainder* (including any further colons) as the second element, so an `mt_token_id` like `"fake:realft.near"` is preserved verbatim as the token part; it never migrates into the `contract_id` position.

Concretely, for an attacker-controlled `Nep245TokenId { contract_id: attacker_contract, mt_token_id: "fake:realft.near" }`:
- `to_string()` → `"nep245:{attacker_contract}:fake:realft.near"`
- Re-parsing: `TokenId::from_str` strips `"nep245:"`, leaving `"{attacker_contract}:fake:realft.near"`.
- `Nep245TokenId::from_str` splits this once more on the first colon → `contract_id = attacker_contract`, `mt_token_id = "fake:realft.near"` (unchanged, colon intact).

The reconstructed pair is identical to the original — `contract_id` remains the attacker's own contract and never resolves to `realft.near`. This matches the existing repo tests (`roundtrip_fixed` with cases like `"nep245:abc:xyz"`, and `display_from_str_roundtrip` using `arbitrary`-generated tokens with embedded special characters) that assert exactly this invariant: [3](#0-2) [4](#0-3) 

The same reasoning and equivalent `FromStr`/`Display` structure applies identically to `Nep171TokenId` and `ImtTokenId`: [5](#0-4) [6](#0-5) 

The binding `TokenId::from_str(token_id.to_string()) == token_id` holds because `AccountId`'s character set excludes `:`, making the first-colon split after the type prefix unambiguous regardless of how many colons appear inside the token/mt_token_id suffix. There is no path by which an attacker-crafted colon-embedded token id causes reattribution to a different `contract_id`.
