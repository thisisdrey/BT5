Audit Report

## Title
`submit_delivery_receipt` pays the relayer reward regardless of the on-chain `success` flag in the delivery receipt - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

## Summary
`DeliveryReceipt::try_from` correctly decodes the `success: bool` field from the Ethereum-emitted `InboundMessageDispatched` event log, but `Pallet::process_delivery_receipt` never inspects `receipt.success` before paying the relayer reward and removing the `PendingOrder`. Any signed account can submit a valid proof for a genuinely emitted but failed (`success == false`) delivery event and still collect the full `order.fee` reward, permanently consuming the order.

## Finding Description
The `DeliveryReceipt` struct carries a `success` field decoded faithfully from the Solidity `InboundMessageDispatched(uint64 indexed nonce, bytes32 topic, bool success, bytes32 reward_address)` event log [1](#0-0) , and populated during decode without loss [2](#0-1) .

The extrinsic `submit_delivery_receipt` only verifies the merkle/beacon proof and decodes the receipt before dispatching to `process_delivery_receipt` — it performs no success check itself [3](#0-2) .

`process_delivery_receipt` checks the gateway address, resolves the `reward_account`, looks up the `PendingOrder` by nonce, and pays the reward whenever `order.fee > 0` — with no reference to `receipt.success` anywhere in the function body, confirmed by a repository-wide search of the pallet returning zero matches for `success` [4](#0-3) . The `PendingOrder` is unconditionally removed afterward, permanently foreclosing correction for that nonce.

## Impact Explanation
This is a duplicate/incorrect settlement bug: the relayer reward pot pays `order.fee` for message deliveries that did not actually succeed on Ethereum, decoupling on-chain reward accounting from the true delivery outcome, and the `PendingOrder` is consumed (removed) so the state can never be settled correctly afterward. This matches the "duplicate settlement or payout" and "theft or unbacked … payout" categories in the impact gate, since value is disbursed for work that was not actually completed as claimed by the underlying verified proof data.

## Likelihood Explanation
High: no privileged actor, collusion, or compromised relayer/prover is required. `submit_delivery_receipt` only requires `ensure_signed(origin)?` [5](#0-4) , and any relayer submitting a proof for a genuinely emitted event with `success = false` automatically benefits — the bug is purely in the pallet's own dispatch logic failing to consult already-decoded, correctly-verified data.

## Recommendation
Gate the reward payment on `receipt.success` in `process_delivery_receipt`, e.g. only call `T::RewardPayment::register_reward` when both `receipt.success` and `order.fee > 0`. If cleanup of failed orders is still desired, separate "resolve/close order" from "pay reward" logic and emit distinct events (e.g. `MessageDelivered { nonce, success }`) so downstream consumers can distinguish rewarded vs. non-rewarded resolutions.

## Proof of Concept
1. `do_process_message` queues a message, inserting `PendingOrders[nonce] = { fee: F, .. }` [6](#0-5) .
2. On Ethereum, execution for `nonce` fails but the Gateway still emits `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. Any signed account constructs a valid proof for this genuine event log and calls `submit_delivery_receipt(origin, event)`.
4. `T::Verifier::verify` succeeds, `DeliveryReceipt::try_from` decodes `success = false`, but `process_delivery_receipt` pays `order.fee` via `T::RewardPayment::register_reward` because it never checks `receipt.success` [7](#0-6) , and removes the `PendingOrder`, making the incorrect payout irreversible for that nonce.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
