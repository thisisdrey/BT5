Based on my investigation, I found a genuine analog to the "duplicate data" bug class in java-tron's resource-weight accounting system.

### Title
Duplicated/Cached Global Resource Weight Counters (`TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, `TOTAL_TRON_POWER_WEIGHT`) Can Desync from Actual Sum of Account Frozen Balances - ([File: chainbase/src/main/java/org/tron/core/store/DynamicPropertiesStore.java])

### Summary
`DynamicPropertiesStore` maintains `TOTAL_NET_WEIGHT`, `TOTAL_ENERGY_WEIGHT`, and `TOTAL_TRON_POWER_WEIGHT` as standalone, incrementally-updated aggregate counters that duplicate information which is, in principle, derivable from the sum of every account's frozen balances [1](#0-0) . Exactly like the reported FuelToken bug (a hardcoded copy of `crowdfund.endsAt()` instead of reading it live), these totals are never recomputed from source; they are maintained purely by "add/subtract the delta" calls scattered across many independent actuators and native-contract processors.

### Finding Description
Every stake-related actuator/processor — `FreezeBalanceActuator`, `UnfreezeBalanceActuator`, `FreezeBalanceV2Actuator`/`FreezeBalanceV2Processor`, `UnfreezeBalanceV2Actuator`/`UnfreezeBalanceV2Processor`, `CancelAllUnfreezeV2Actuator`/`CancelAllUnfreezeV2Processor`, `DelegateResourceActuator`/`DelegateResourceProcessor`, `UnDelegateResourceActuator`/`UnDelegateResourceProcessor` — independently computes an "old weight" and "new weight" from an individual account and calls `addTotalNetWeight`/`addTotalEnergyWeight`/`addTotalTronPowerWeight` to nudge the global counter by the delta, e.g. [2](#0-1) . The global counters are never independently verified against, or recomputed as, the true sum of per-account frozen balances; they are pure duplicated caches, updated at dozens of independent call sites. A code comment in the codebase itself acknowledges history of exactly this class of defect: `// adjust total resource, used to be a bug here` [3](#0-2) . Any single call site that omits, double-counts, or mis-signs its delta update permanently desyncs the cached total from the real aggregate frozen balance across all accounts, with no self-healing mechanism (there is no periodic recomputation from `AccountStore`).

### Impact Explanation
`getTotalNetWeight()`/`getTotalEnergyWeight()` are the denominator in the resource-limit formula used for every account, every transaction: `accountFrozen/TRX_PRECISION * totalLimit/totalWeight`, invoked from `BandwidthProcessor.calculateGlobalNetLimit`/`calculateGlobalNetLimitV2` and `ResourceProcessor.calculateGlobalLimitV1/V2` [4](#0-3) , and it is also directly returned to clients via `Wallet.getAccountNet`/`getAccountResource` and `calcCanDelegatedBandWidthMaxSize`/`calcCanDelegatedEnergyMaxSize` [5](#0-4) . If the cached total drifts from the real sum of frozen balances (e.g., is left too low), every account's computed bandwidth/energy limit is inflated system-wide, letting transaction broadcasters get free bandwidth/energy beyond what their frozen TRX actually backs — an unbacked-resource allocation across the whole network. Conversely a total that drifts too high silently starves every account of resource they are entitled to. Because the value is a chain-consensus dynamic property, any client that can trigger an under/over-counted delta (freeze, unfreeze, delegate, undelegate, cancel-unfreeze, or their TVM native-contract equivalents reachable from ordinary contract calls) can degrade this shared value for the whole network.

### Likelihood Explanation
This requires finding one specific call path among the many independent freeze/unfreeze/delegate/undelegate/cancel code paths (actuator and TVM-processor variants) where the delta computed from an account's `getFrozenV2BalanceWithDelegated`/`getAllFrozenBalanceForBandwidth`-style helpers does not exactly match the actual balance change applied to the account (for example, edge cases around suicided/re-created contract accounts noted in `UnDelegateResourceProcessor`'s comment about accounts being "converted to a regular account in the future" [6](#0-5) , or receiver accounts that no longer exist). Given the sheer number of independent update sites (at least 8 actuators/processors) and the historical precedent of "used to be a bug here" comment, the likelihood of at least one edge case producing drift is non-trivial, though each individual path appears carefully guarded with explicit `default: // this should never happen` fallbacks.

### Recommendation
Do not maintain `TOTAL_NET_WEIGHT`/`TOTAL_ENERGY_WEIGHT`/`TOTAL_TRON_POWER_WEIGHT` purely as independently-mutated duplicated counters. Add periodic (e.g., at maintenance-cycle boundaries in `Manager`) reconciliation that recomputes the true total from `AccountStore` and corrects any drift, or add invariant assertions/logging when the incremental total diverges from a full recomputation in testing/staging. At minimum, add a canary metric comparing full-scan totals to the cached counters after upgrades touching freeze/unfreeze/delegate logic.

### Proof of Concept
Not directly exploitable as a single-transaction PoC without exhaustively auditing every delta-computation branch across the ~8 independent update sites listed above for an exact mismatch; the analog is a systemic architecture pattern (duplicated data with no reconciliation) rather than one concrete confirmed arithmetic bug in this scan. A concrete PoC would require identifying one specific branch (e.g., delegate/undelegate to a suicided-then-recreated contract account) where the old/new weight calculation reads stale account fields.

  public long calculateGlobalNetLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForBandwidth();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalNetLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long totalNetLimit = chainBaseManager.getDynamicPropertiesStore().getTotalNetLimit();
    long totalNetWeight = chainBaseManager.getDynamicPropertiesStore().getTotalNetWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalNetWeight <= 0) {
      return 0;
    }
    if (totalNetWeight == 0) {
      return 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalNetLimit, totalNetWeight);
    }
    long netWeight = frozeBalance / TRX_PRECISION;
    return (long) (netWeight * ((double) totalNetLimit / totalNetWeight));
  }
