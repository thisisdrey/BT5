Audit Report

## Title
Outbound bridge messages that never receive a delivery receipt permanently lock the prepaid relayer fee with no cancellation or refund mechanism - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

## Summary
When a message is sent from Polkadot to Ethereum via the Snowbridge V2 outbound queue, the relayer fee is withdrawn from the sender via XCM (`WithdrawAsset`/`PayFees` for the remote fee asset in the `ExportMessage` flow, or directly as a `u128` in `snowbridge_pallet_system_v2::Pallet::send`) and recorded in a `PendingOrder` keyed by nonce. [1](#0-0)  The only code path that removes an entry from `PendingOrders` and pays out the fee is `process_delivery_receipt`, which requires a valid Ethereum-side delivery proof; there is no cancellation, timeout, or sweep mechanism anywhere in the pallet, so a message that never executes on Ethereum (halted Gateway, reverted command, unprofitable relayer economics) permanently strands the fee. [2](#0-1) 

## Finding Description
The pipeline is exactly as described: `do_process_message` decodes the queued `Message`, assigns a `nonce`, and inserts a `PendingOrder { nonce, fee, block_number }` into the `PendingOrders` storage map, with the doc comment explicitly stating the fee is only released "after" a delivery proof is submitted. [3](#0-2) [4](#0-3) 

`process_delivery_receipt` is the sole extrinsic-reachable path that reads and removes a `PendingOrders` entry, and it requires `T::Verifier::verify` to succeed against a real Ethereum event log/proof for that nonce via `submit_delivery_receipt`. [5](#0-4) [2](#0-1)  The `block_number` field recorded at insertion is never read or compared elsewhere in the pallet — confirmed by inspecting the full `lib.rs`, where the only writer of `PendingOrders` is `do_process_message`/`add_tip`, and the only remover is `process_delivery_receipt`. A grep for `cancel|expire|timeout|stale|reap` across the entire `bridges/snowbridge/` tree returns no matches, confirming no expiry, cancellation, or sweep logic exists anywhere in the bridge pallets. The pallet's own test `submit_delivery_receipt_succeeds_after_unhalt` demonstrates that while the bridge verifier is halted, the order remains untouched in storage with no other removal path exercised. [6](#0-5) 

Fee funds are real: the V2 exporter and integration tests show the fee asset (e.g., WETH remote fee) is withdrawn from the user's account via `WithdrawAsset`/`PayFees`/`InitiateTransfer` and routed through `ExportMessage` before the outbound queue inserts the `PendingOrder`, and `snowbridge_pallet_system_v2::Pallet::send` similarly attaches a nonzero `fee` for governance/registration flows. This confirms the fee is genuinely custodied against the pending nonce, not merely a bookkeeping number.

Existing guards (verifier halted checks, gateway address checks, nonce existence checks in `process_delivery_receipt`) only gate the *payout* path; none of them provide an alternative path back to the sender if delivery never occurs. This matches the required invariant violation: a one-time-settlement state that must "only advance after decode, dispatch, execution, and settlement succeed atomically" instead gets stuck in a permanently unresolvable pending state with no compensating recovery, constituting a permanent bridge-state/fund lock.

## Impact Explanation
This matches the Polkadot SDK impact gate's "permanent user-fund or bridge-state lock" category. Any outbound message whose Ethereum-side execution never completes (halted Gateway via governance pause, a reverting Gateway call, or insufficient gas economics that no relayer will service) results in the associated fee being irrecoverably stuck in `PendingOrders[nonce]` forever, with no sender-initiated or permissionless path to reclaim it. [7](#0-6) 

## Likelihood Explanation
No adversarial actor is required — an ordinary halted-bridge period (a normal governance/pause action), an Ethereum-side revert, or simple relayer non-participation is sufficient to trigger permanent lock. The scenario is directly reproduced by the pallet's own test suite for the halted case. [8](#0-7) 

## Recommendation
Add a cancellation/refund extrinsic or automatic sweep (e.g., an `on_idle` hook or a permissionless `cancel_stale_order(nonce)` call) that, once `current_block_number() - order.block_number` exceeds a configurable threshold, refunds `order.fee` to the original message sender/origin and removes the entry from `PendingOrders`. Ensure this refund path is also reachable during extended halts of the bridge verifier, and bind the refund strictly to the recorded `origin`/sender to avoid misdirected payouts.

## Proof of Concept
1. Fund and route a message through `snowbridge_pallet_system_v2::Pallet::send` (or the V2 `ExportMessage` XCM flow) with a nonzero `fee`, which enqueues via `T::MessageQueue`.
2. `do_process_message` assigns `nonce`, inserts `PendingOrder { nonce, fee, block_number }` into `PendingOrders`. [1](#0-0) 
3. Call `set_verifier_halted(true)` (or simulate a permanent Ethereum-side revert) so `submit_delivery_receipt` can never succeed for that nonce — reproduced by the existing test `submit_delivery_receipt_succeeds_after_unhalt`, which shows the order untouched while halted. [8](#0-7) 
4. Observe that `PendingOrders::<T>::get(nonce)` remains `Some` indefinitely with no other extrinsic in the pallet capable of removing or refunding it, confirming the permanent fund lock.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}

// After governance resumes the bridge, legitimate delivery receipts flow through again:
// the order is paid out and removed from storage.
#[test]
fn submit_delivery_receipt_succeeds_after_unhalt() {
	new_tester().execute_with(|| {
		let nonce = 0;
		let fee: u128 = 1_000_000;
		let order = PendingOrder { nonce, fee, block_number: System::block_number() };
		PendingOrders::<Test>::insert(nonce, order);

		let relayer: AccountId32 = [7u8; 32].into();
		let origin = RuntimeOrigin::signed(relayer);
		let event = Box::new(mock_valid_event_proof());

		// Bridge halted — receipt rejected, order untouched.
		set_verifier_halted(true);
		assert_noop!(
			OutboundQueue::submit_delivery_receipt(origin.clone(), event.clone()),
			Error::<Test>::Verification(VerificationError::Halted)
		);
		assert!(PendingOrders::<Test>::get(nonce).is_some());

		// Bridge resumed — same receipt succeeds and the order is settled.
		set_verifier_halted(false);
		assert_ok!(OutboundQueue::submit_delivery_receipt(origin, event));
		assert!(PendingOrders::<Test>::get(nonce).is_none());

		System::assert_has_event(mock::RuntimeEvent::OutboundQueue(Event::MessageDelivered {
			nonce,
		}));
	});
