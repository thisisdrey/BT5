### Title
Multi-sig transaction executes against silently-changed Permission (keys/threshold/weight) via owner front-run - (File: `chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Finding Description
In java-tron's multi-signature model, a transaction's `Contract` carries only a `Permission_id` (an integer, 0=owner, 1=witness, 2-9=active) — it never commits to the actual `Permission` content (key set, weight, threshold) that co-signers observed when they added their signature via `TransactionCapsule.addSign` [2](#0-1)  or via the `wallet/getsignweight` RPC path `TransactionUtil.getTransactionSignWeight` [3](#0-2) .

When the transaction is finally broadcast, `TransactionCapsule.validateSignature` re-reads the account's permission fresh from `AccountStore` by `permissionId` and checks the collected signatures' weight against whatever permission currently exists on-chain: [4](#0-3) 

The owner permission holder can submit an `AccountPermissionUpdateContract` at any time to overwrite an Active permission's key list, weights, or threshold — `AccountPermissionUpdateActuator.execute` simply calls `account.updatePermissions(...)` and persists it, with no check that a pending multi-sig transaction (already partially signed under the old permission) exists: [5](#0-4)  and [6](#0-5) .

This mirrors the Cooler `provideNewTermsForRoll`/`rollLoan` bug class: parties commit to terms off-chain (here, co-signers sign a transaction under a specific threshold/weight/key set they believe applies), a privileged party changes those terms on-chain (here, the account owner rewrites the Active permission), and the eventual execution (`validateSignature`) is checked against the *new* terms rather than the ones the signers actually agreed to — because nothing binds the signature/weight check to a snapshotted permission state.

### Impact Explanation
An account owner (or a party that colludes with/compromises the owner permission while other active-permission co-signers are cooperating on a pending multi-sig transaction, e.g. a large transfer or `TriggerSmartContract` call) can front-run the final broadcast of that multi-sig transaction with an `AccountPermissionUpdateContract`:
- Lower the threshold so a previously-insufficient set of already-collected signatures becomes sufficient, letting a transaction execute that other co-signers had not fully approved.
- Remove or reduce the weight of a co-signer's key so their intended veto/approval no longer counts as expected, changing who effectively controls fund movement out of the shared account.
- Add a new key with high weight to the Active permission that satisfies the threshold on its own, letting the owner execute the pending transaction as if the other signers' cooperation was still required, defeating the multi-sig safety guarantee co-signers relied upon when they signed.

Because the Active permission also gates which contract types (`operations` bitmap) can be executed by that key set, an owner can also widen the operations mid-flight, causing a transaction that was pre-signed for a narrow-scope permission to be judged valid under a broadened one at broadcast time. The net effect is unauthorized account operations / theft of funds from a shared multi-sig account, contradicting the guarantees co-signers believed were in force when they contributed their signatures.

### Likelihood Explanation
This requires the attacker to control (or currently be) the Owner permission (or an Active permission with rights to call `AccountPermissionUpdateContract`) of the account under attack, and requires that other co-signers are in the process of a pending multi-sig transaction. This is a realistic scenario for shared/custodial multi-sig wallets (e.g., DAO treasuries, exchange hot wallets) where the "owner" role is trusted less than individual co-signers or where governance intends the threshold/keys to be a fixed safety mechanism. No special network position is needed — the attacker just needs to broadcast the `AccountPermissionUpdateContract` transaction before the pending multi-sig transaction lands in a block, which is standard mempool front-running.

### Recommendation
Bind the multi-sig authorization to the exact `Permission` state that was in effect when the transaction was constructed/signed, e.g., by embedding a hash or version/sequence number of the `Permission` (updated on every `AccountPermissionUpdateContract`) into the signed hash or into the `Contract`, and rejecting execution if the current on-chain permission version does not match. Alternatively, require `AccountPermissionUpdateContract` to be time-locked or itself go through the same threshold-based multi-sig scheme so pending transactions signed under the old permission cannot be invalidated or reinterpreted unilaterally by the owner mid-flight.

### Proof of Concept
1. Account `A` has an Active permission (id=2) with keys `K1` (weight 1) and `K2` (weight 1), threshold 2.
2. `K1` proposes a large transfer from `A`, referencing `permission_id=2`, and signs it via `addSign`; the transaction is held pending `K2`'s co-signature (`weight=1 < threshold=2`, per `checkWeight`) [7](#0-6) .
3. The Owner of `A` (who might be `K1` or a colluding party) broadcasts `AccountPermissionUpdateContract` lowering the Active permission's threshold to 1, or replacing `K2` with a key `K1` controls, via `AccountPermissionUpdateActuator` [8](#0-7) .
4. Once this update is included in a block, `K1` broadcasts the pending transfer transaction (still carrying only `K1`'s signature). `TransactionCapsule.validateSignature` fetches the *new* Active permission and finds `checkWeight(...) >= permission.getThreshold()` now holds with only `K1`'s signature, so the transfer executes despite `K2` never approving it.

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }

        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }

  public static boolean validateSignature(Transaction transaction,
      byte[] hash, AccountStore accountStore, DynamicPropertiesStore dynamicPropertiesStore)
      throws PermissionException, SignatureException, SignatureFormatException {
    Transaction.Contract contract = transaction.getRawData().getContractList().get(0);
    int permissionId = contract.getPermissionId();
    byte[] owner = getOwner(contract);
    AccountCapsule account = accountStore.get(owner);
    Permission permission = null;
    if (account == null) {
      if (permissionId == 0) {
        permission = AccountCapsule.getDefaultPermission(ByteString.copyFrom(owner));
      }
      if (permissionId == 2) {
        permission = AccountCapsule
            .createDefaultActivePermission(ByteString.copyFrom(owner), dynamicPropertiesStore);
      }
    } else {
      permission = account.getPermissionById(permissionId);
    }
    if (permission == null) {
      throw new PermissionException("permission isn't exit");
    }
    checkPermission(permissionId, permission, contract);
    long weight = checkWeight(permission, transaction.getSignatureList(), hash, null);
    if (weight >= permission.getThreshold()) {
      return true;
    }
    return false;
  }

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
