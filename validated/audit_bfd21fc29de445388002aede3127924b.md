### Title
Unchecked attacker-controlled offset in `ValidateMultiSign` precompile causes uncaught `ArrayIndexOutOfBoundsException` (analog of ntfs_attr_find OOB read from unchecked offset field) - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The NTFS bug stems from trusting an on-disk `attrs_offset` field without validating it against the buffer's real size before dereferencing, causing an out-of-bounds read. `PrecompiledContracts.ValidateMultiSign.execute()` (and its sibling `BatchValidateSign`) contains the same root-cause pattern: it decodes attacker-controlled 32-byte words from calldata and uses one of them directly as an array/byte offset (`words[3].intValueSafe() / WORD_SIZE`) to index into the `words` array and into the raw `rawData` byte array via `extractBytesArray`/`extractSigArray`, without first validating that the offset (and derived length fields) are within the bounds of the supplied calldata.

### Finding Description
In `ValidateMultiSign.execute()`: [1](#0-0) 
the offset used to select `signatures` is `words[3].intValueSafe() / WORD_SIZE`, fed straight into `extractBytesArray`/`extractSigArray`: [2](#0-1) [3](#0-2) 
`extractBytesArray` only performs a shallow guard (`offset > words.length - 1`) before reading `words[offset]` for the count, then loops reading `words[offset + i + 1]` and calls `extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE, bytesLen)`: [4](#0-3) 
`extractBytes` does `Arrays.copyOfRange(data, offset, offset + len)` with no bound check that `offset + len <= data.length`. Because `bytesOffset` and `bytesLen` are attacker-controlled `DataWord` values decoded directly from calldata, a crafted `offset`/`len` pair can drive `copyOfRange` to request a range beyond `rawData.length`, throwing an uncaught `ArrayIndexOutOfBoundsException`.

A recently added guard, `isValidAbiEncoding`, mitigates this — but only when `VMConfig.allowTvmOsaka()` is active: [5](#0-4) 
When that feature flag is not yet activated on a given network/chain, no such guard exists, and the malformed-offset path is fully reachable.

Critically, unlike `BatchValidateSign.execute()`, which wraps its logic in a top-level `try { return doExecute(data); } catch (Throwable t) { ... }`: [6](#0-5) 
`ValidateMultiSign.execute()` has **no outer try/catch** around the parsing/extraction calls (lines 1057-1074); only the signature-recovery loop that follows is wrapped in `try { ... } catch (Throwable t) { ... }`: [7](#0-6) 
So an `ArrayIndexOutOfBoundsException` thrown during `extractBytesArray`/`extractSigArray` propagates out of `ValidateMultiSign.execute()` entirely uncaught by the contract itself.

The caller, `Program.callToPrecompiledAddress`, invokes `contract.execute(data)` with no try/catch around it: [8](#0-7) 
so the exception propagates further up the VM call stack.

### Impact Explanation
An uncaught runtime exception escaping the intended VM execution path for a single `CALL` to the `validateMultiSign` precompile address risks disrupting the transaction execution flow in a way not accounted for by the VM's normal exception model (`Program.Exception` subclasses used for reverts). Depending on how the top-level transaction-processing harness (`TransactionTrace`/`Runtime`) handles a generic unchecked `RuntimeException` versus the expected `Program.Exception`/`OutOfTimeException` types, this could manifest as an unhandled exception during block application, potentially aborting or corrupting normal transaction processing for that block, which is a node-crash/halt class of impact reachable by any contract calling `validateMultiSign(address,uint256,bytes,bytes[])` with crafted calldata.

### Likelihood Explanation
Reachable by any user who deploys or calls a contract invoking the `validateMultiSign` precompile with crafted calldata containing an out-of-range offset word; no special privilege required. Likelihood is reduced/mitigated on networks/chains where `allowTvmOsaka` (TIP-854 guard) is already active, since `isValidAbiEncoding` rejects malformed shapes before reaching the vulnerable extraction code. On networks without this flag activated, the path is fully exposed.

### Recommendation
Add bounds validation inside `extractBytesArray`/`extractSigArray`/`extractBytes` to ensure `bytesOffset`, `bytesLen`, and derived byte ranges never exceed `data.length` regardless of `VMConfig.allowTvmOsaka()` state, and wrap `ValidateMultiSign.execute()`'s parsing/extraction logic in the same defensive `try/catch(Throwable)` pattern already used by `BatchValidateSign.execute()`, returning `Pair.of(true, DATA_FALSE)` on any parsing failure instead of allowing exceptions to propagate to `Program.callToPrecompiledAddress`.

### Proof of Concept
Craft calldata for `validateMultiSign(address,uint256,bytes,bytes[])` where the 4th head word (`words[3]`, the offset to the `bytes[]` signatures array) points near/at the end of the calldata such that `words[offset]` (array length) or a subsequent `bytesLen`/`bytesOffset` derived from attacker-controlled words causes `extractBytes(data, computedOffset, computedLen)` to request `computedOffset + computedLen > data.length`, without activating `VMConfig.allowTvmOsaka()`. Deploy a contract that performs a `CALL` to the `ValidateMultiSign` precompile address with this calldata; observe the uncaught `ArrayIndexOutOfBoundsException` propagate out of `contract.execute(data)` in `Program.callToPrecompiledAddress` (line 1752) uncaptured by any surrounding handler in that method.
