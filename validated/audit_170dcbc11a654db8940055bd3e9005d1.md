## Analysis

The external report's core broken invariant is: **a pricing/valuation function reads live, single-block AMM reserves as if they were a manipulation-resistant price, with no TWAP, staleness check, or price-impact bound**, allowing an attacker to skew reserves and have that skewed value consumed by a downstream settlement step that does not pay a correspondingly-priced counter-trade.

I found the same broken invariant in `pallet-asset-conversion`'s pricing primitives, which are consumed by the fee-conversion logic in `pallet-asset-conversion-tx-payment`.

`Pallet::get_reserves` reads only the *current* pool account balances with no history, window, or deviation check: [1](#0-0) 

`quote_price_exact_tokens_for_tokens` / `quote_price_tokens_for_exact_tokens` and `get_amount_in`/`get_amount_out` derive a price purely from these live reserves via the constant-product formula, with no TWAP or manipulation-resistance mechanism: [2](#0-1) [3](#0-2) 

`SwapAssetAdapter::withdraw_fee` calls this spot quote at pre-dispatch time to determine how much of a non-native asset to withdraw for the transaction fee, then performs the actual swap at that quoted amount: [4](#0-3) 

Critically, the wrapped extrinsic executes **between** this pre-dispatch fee withdrawal and the pallet's post-dispatch refund/correction step. If the wrapped call is itself `AssetConversion::swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` on the *same pool* used for fee conversion, the payer can move the pool's reserves during their own transaction, so the post-dispatch refund is re-quoted against reserves that the payer just changed. The test suite for this pallet explicitly documents this pool-state-changes-between-withdraw-and-post-dispatch scenario ("Path C"): [5](#0-4) 

The same unprotected-spot-price pattern is also wired into XCM execution-weight purchase (`SwapFirstAssetTrader::buy_weight`), which reads/executes against live pool reserves per message with no TWAP: [6](#0-5) 

### What I could **not** fully verify
I could not confirm, within the available tool budget, the exact `Trader` type alias wired into the production `asset-hub-westend`/`asset-hub-rococo` runtime `XcmConfig` (only test-harness usage of `AssetConversion::get_amount_in`/`get_reserves` was confirmed), nor did I trace the exact body of `SwapAssetAdapter::correct_and_deposit_fee`/post-dispatch refund computation line-by-line — only the test comments and `withdraw_fee` body were fully read. This means the precise refund arithmetic and whether it fully offsets or only partially offsets attacker-induced reserve skew is not fully confirmed. Given the strict evidentiary bar requested, I flag this rather than asserting full economic exploitability with certainty.

### Title
Fee-conversion pricing in `pallet-asset-conversion-tx-payment` uses unprotected single-block spot AMM price, re-quoted after the payer's own call can move the same pool — (File: `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

### Summary
`SwapAssetAdapter` (the `OnChargeAssetTransaction` implementation for `pallet-asset-conversion-tx-payment`) prices a transaction's fee in a non-native asset by calling `pallet-asset-conversion`'s `quote_price_tokens_for_exact_tokens`, which is a pure function of the *current* pool reserves with no TWAP, minimum-liquidity-depth, or staleness/deviation guard. Because the wrapped extrinsic executes between the pre-dispatch fee withdrawal and the post-dispatch refund/correction, and the wrapped extrinsic can itself be an `AssetConversion` swap on the very same pool, the payer can move the pool's reserves inside their own transaction so that the fee conversion rate used for withdrawal and the rate later used for refund/correction are computed against two different, self-selected reserve states.

### Finding Description
`get_reserves` simply reads `T::Assets` balances held by the pool account with no history or averaging: [1](#0-0) 

`get_amount_in`/`get_amount_out` and the `quote_price_*` view functions built on top of them are pure constant-product-formula reads of these balances — there is no oracle-style manipulation resistance anywhere in this pallet: [7](#0-6) 

`SwapAssetAdapter::withdraw_fee` uses this spot quote to size the withdrawal for a fee payment in a non-native asset: [8](#0-7) 

Because the dispatched call runs after this withdrawal and before the pallet's post-dispatch step, and the dispatched call can be `AssetConversion::swap_exact_tokens_for_tokens`/`swap_tokens_for_exact_tokens` acting on the *same* asset pair/pool used for fee pricing, the payer fully controls the reserve state that the post-dispatch refund/correction logic will re-quote against — exactly the "attacker controls the oracle's sole input, within one atomic operation, no averaging window" pattern from the external report, just relocated from a cross-pool TVL oracle to a fee-conversion oracle.

### Impact Explanation
This falls under "public underpriced work that degrades block production" and "duplicate settlement/wrong beneficiary or amount" categories: if the post-dispatch re-quote can be pushed favorably by the payer's own in-transaction swap, the effective fee actually retained by the runtime for a given amount of consumed weight can be made to deviate from the fair market rate, without any external relayer/validator/governance involvement — a plain, permissionless, non-privileged origin flow.

### Likelihood Explanation
Medium. It requires no special privileges, only a signed account able to: (1) hold assets in a pool it also uses for fee payment, and (2) submit a normal extrinsic whose call is an `AssetConversion` swap. All primitives needed (pool creation is permissionless, swaps are permissionless, `ChargeAssetTxPayment`/`SwapAssetAdapter` fee path is the default asset-fee mechanism) exist in-repo. The main open uncertainty (noted above) is the exact magnitude/direction of exploitable value in the post-dispatch correction step, which I could not fully trace within the available budget.

### Recommendation
- Do not use the pool's raw, current-block reserves as the sole price reference for both the pre-dispatch withdrawal and the post-dispatch refund of the same transaction; snapshot the rate once (at pre-dispatch) and reuse it, or
- Add a manipulation-resistant reference price (time-weighted average over N blocks, or a bound on maximum per-block reserve deviation) to `pallet-asset-conversion`'s `quote_price_*`/`get_amount_in`/`get_amount_out` before they are used for on-chain value settlement (fee conversion, XCM weight purchase), rather than only for off-chain/display `AssetConversionApi` calls.
- Explicitly forbid or special-case the wrapped call being a swap on the exact pool used to price that call's own fee.

### Proof of Concept
1. Attacker creates/holds significant liquidity in pool `(Native, X)`.
2. Attacker submits extrinsic `T` with fee asset `X`; `ChargeAssetTxPayment` (`SwapAssetAdapter::withdraw_fee`) quotes and withdraws `X` for the fee using pool `(Native, X)` reserves `R1`. [8](#0-7) 
3. The call body of `T` is `AssetConversion::swap_exact_tokens_for_tokens` on the same `(Native, X)` pool, moving reserves to `R2`.
4. Post-dispatch refund/correction logic re-quotes against `R2` (this pool-state-changed-since-withdrawal scenario is explicitly exercised in the pallet's own tests): [5](#0-4) 
5. Because `R1 ≠ R2` are both fully attacker-influenced within the same atomic transaction, the fee actually retained by the runtime is derived from a payer-selected exchange rate rather than a manipulation-resistant one.

Note: full quantification of net attacker profit (vs. AMM round-trip fee cost) was not completed in this pass; a Devin session with repo access should trace `correct_and_deposit_fee`/the refund path in full to confirm exact exploitable magnitude before treating this as fully proven.

		/// Given an input amount of an asset and pair reserves, returns the maximum output amount

		pub fn get_amount_out(
			fee: Permill,
			amount_in: &T::Balance,
			reserve_in: &T::Balance,
			reserve_out: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount_in = T::HigherPrecisionBalance::from(*amount_in);
			let reserve_in = T::HigherPrecisionBalance::from(*reserve_in);
			let reserve_out = T::HigherPrecisionBalance::from(*reserve_out);

			if reserve_in.is_zero() || reserve_out.is_zero() {
				return Err(Error::<T>::ZeroLiquidity);
			}

			let fee_complement = fee.left_from_one().deconstruct();
			let amount_in_with_fee = amount_in
				.checked_mul(&T::HigherPrecisionBalance::from(fee_complement))
				.ok_or(Error::<T>::Overflow)?;

			let numerator =
				amount_in_with_fee.checked_mul(&reserve_out).ok_or(Error::<T>::Overflow)?;

			let denominator = reserve_in
				.checked_mul(&T::HigherPrecisionBalance::from(Permill::ACCURACY))
				.ok_or(Error::<T>::Overflow)?
				.checked_add(&amount_in_with_fee)
				.ok_or(Error::<T>::Overflow)?;

			let result = numerator.checked_div(&denominator).ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}

		pub fn quote_price_exact_tokens_for_tokens(
			asset1: T::AssetKind,
			asset2: T::AssetKind,
			amount: T::Balance,
			include_fee: bool,
		) -> Option<T::Balance> {
			// Swaps reject zero amounts, match that behavior.
			if amount.is_zero() {
				return None;
			}

			let pool_account = T::PoolLocator::pool_address(&asset1, &asset2).ok()?;

			let (balance1, balance2) = Self::get_reserves(asset1.clone(), asset2.clone()).ok()?;

			if balance1.is_zero() {
				return None;
			}

			let amount_out = if include_fee {
				let fee = Self::pool_fee_for(&asset1, &asset2).ok()?;
				Self::get_amount_out(fee, &amount, &balance1, &balance2).ok()?
			} else {
				Self::quote(&amount, &balance1, &balance2).ok()?
			};

			// Small inputs can round output to zero due to integer division.
			if amount_out.is_zero() {
				return None;
			}

			// Swap withdrawals from pools use `keep_alive=true` (Preserve). Use the same
			// preservation level to determine the actual withdrawable amount.
			let max_output = T::Assets::reducible_balance(asset2, &pool_account, Preserve, Polite);
			if amount_out > max_output {
				return None;
			}

			Some(amount_out)
		}
