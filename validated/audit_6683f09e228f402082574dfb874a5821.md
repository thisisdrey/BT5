Missing Cross-Repository Authorization Check in `LinkRepositoryToObjectPool` Allows Arbitrary Object Pool Linkage and Object Access Across Repositories - ([File: internal/gitaly/service/objectpool/link.go])

### Summary
`LinkRepositoryToObjectPool` validates that the target `Repository` exists and that the `ObjectPool` path is well-formed and within the pools directory, but it never verifies any ownership/membership relationship between the two — i.e., that the calling context is authorized to attach the given repository to the given, potentially unrelated, object pool. This mirrors the reported Snap bug class: a handler that performs an operation exposing/joining sensitive state without validating that the caller is entitled to access that specific resource.

### Finding Description
`s.LinkRepositoryToObjectPool` in `internal/gitaly/service/objectpool/link.go` only:
1. Calls `s.locator.ValidateRepository(ctx, repository)` — confirms the target repo exists.
2. Calls `s.poolForRequest(ctx, req)` (`internal/gitaly/service/objectpool/util.go`) — this resolves the object pool via `objectpool.FromProto`, which only checks that the path is inside the pools directory (`storage.IsPoolRepository`) and that it is a valid git repository (`pool.IsValid`).
3. Calls `pool.Link(ctx, repo)`. [1](#0-0) [2](#0-1) 

At no point does the code check that the source `Repository` requesting the link is a pool member created from that specific pool, or that the caller (Rails/gitlab-shell) actually owns both the repository and the pool. `internal/git/objectpool/link.go`'s `Link()` function similarly performs no ownership check — it simply writes the pool's relative path into the repository's Git alternates file if not already linked: [3](#0-2) 

Any caller that can invoke `ObjectPoolService.LinkRepositoryToObjectPool` with a valid, authenticated Gitaly RPC token (i.e., any client sharing the general shared Gitaly auth token — not necessarily the specific owner of the pool) can supply an arbitrary existing `Repository` and an arbitrary existing object pool path in the same storage, causing the repository to be permanently linked via Git alternates to that pool's object database.

By contrast, related RPCs in the same service enforce cross-repository storage consistency: `FetchIntoObjectPool` explicitly checks `originRepository.GetStorageName() != poolRepository.GetStorageName()` and rejects mismatches, and `CreateObjectPool` validates the target pool directory naming convention strictly: [4](#0-3) [5](#0-4) 

`LinkRepositoryToObjectPool` has no equivalent authorization/consistency check tying the linking party to the pool's legitimate members.

### Impact Explanation
Once linked, Git treats the pool's objects as part of the repository's own object database via alternates (see `doc/object_quarantine.md` and `internal/git/localrepo/paths.go`'s quarantine/alternates handling). Any blob, tree, or commit present in the (attacker-unrelated) pool becomes fetchable/readable from the linked repository — this is a cross-repository object disclosure primitive, directly matching the "cross-repository object access" acceptance criterion. Because object pools are typically created from fork-source repositories that may contain private commits/branches (deleted branches, force-pushed commits, private forks retained in the pool for deduplication), an attacker who can trigger a link between a repository they control and an unrelated pool can exfiltrate objects belonging to other users' repositories.

### Likelihood Explanation
Exploitation requires the ability to invoke `ObjectPoolService.LinkRepositoryToObjectPool` — reachable by any client holding a valid Gitaly RPC auth token and knowledge (or brute-forceable guess, given `CreateObjectPool`'s deterministic naming scheme validated in `errInvalidPoolDir` tests) of a target pool's relative path. In a standard GitLab deployment, this RPC is normally called only by Rails after an authorization decision on the GitLab side, so exploitation in production depends on whether an untrusted or lower-privileged internal caller can reach this RPC directly — this reduces to whether Gitaly's own defense-in-depth is present, and here it is not: unlike `FetchIntoObjectPool`, there is no independent server-side check.

### Recommendation
Add a server-side authorization/consistency check in `LinkRepositoryToObjectPool` (and the underlying `Link()` in `internal/git/objectpool/link.go`) analogous to the storage-name check already present in `FetchIntoObjectPool`: verify that the pool being linked was created from, or is otherwise associated with (e.g., via project/fork-network membership metadata), the repository requesting the link, rather than trusting any caller-supplied `(Repository, ObjectPool)` pair blindly.

### Proof of Concept
1. As an authenticated Gitaly client, call `CreateObjectPool` with `Origin = victim_repo` to obtain `pool_A` (or discover an existing pool path via GitLab's deterministic pool naming scheme).
2. Call `LinkRepositoryToObjectPool` with `Repository = attacker_repo` and `ObjectPool = pool_A`, where `attacker_repo` has no legitimate relationship to `pool_A`.
3. Observe that `attacker_repo`'s `objects/info/alternates` now points at `pool_A`'s object directory (verifiable via `internal/git/localrepo/paths.go`'s `InfoAlternatesPath` and `stats.AlternatesInfoForRepository`).
4. From `attacker_repo`, fetch or read any object ID known to exist in `pool_A` (e.g., via `CommitService.FindCommit` or `git cat-file`) — the object is now accessible through `attacker_repo`, despite no authorization relationship between the two repositories.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

func (s *server) poolForRequest(ctx context.Context, req PoolRequest) (*objectpool.ObjectPool, error) {
	pool, err := objectpool.FromProto(ctx, s.logger, s.locator, s.gitCmdFactory, s.catfileCache, s.txManager, s.housekeepingManager, req.GetObjectPool())
	if err != nil {
		if errors.Is(err, objectpool.ErrInvalidPoolDir) {
			return nil, errInvalidPoolDir
		}

		if errors.Is(err, objectpool.ErrInvalidPoolRepository) {
			return nil, structerr.NewFailedPrecondition("%w", err)
		}

		return nil, structerr.NewInternal("%w", err)
	}

	return pool, nil
}

// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}
