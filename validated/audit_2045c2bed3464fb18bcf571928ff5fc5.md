## Title
Splitting `UnDelegateResourceContract` transactions truncates `transferUsage` via double-precision math, letting an attacker erase their own bandwidth/energy usage debt - ([File: actuator/src/main/java/org/tron/core/actuator/UnDelegateResourceActuator.java])

### Summary
`UnDelegateResourceActuator.execute()` computes `transferUsage` — the amount of already-consumed bandwidth/energy that must be "clawed back" from the receiver and re-attributed to the delegating owner — using floating-point division that is truncated on every call:

```java
long unDelegateMaxUsage = (long) ((double) unDelegateBalance / TRX_PRECISION
    * ((double) (dynamicStore.getTotalNetLimit()) / dynamicStore.getTotalNetWeight()));
transferUsage = (long) (receiverCapsule.getNetUsage()
    * ((double) (unDelegateBalance) / receiverCapsule.getAllFrozenBalanceForBandwidth()));
transferUsage = min(unDelegateMaxUsage, transferUsage);
``` [1](#0-0) 

This is exactly the class of bug in the Trail-of-Bits report: a per-call rounding-down division whose truncation error compounds when the same total amount is split across many smaller calls instead of one large call.

### Finding Description
`transferUsage` is subtracted from the receiver's usage and added to the owner's usage via `processor.unDelegateIncrease(...)`, effectively moving the "debt" of consumed bandwidth/energy back to the owner when they revoke a delegation: [2](#0-1) [3](#0-2) 

`(long)` casts truncate toward zero after a `double` multiplication/division on every single `UnDelegateResourceContract` transaction. If the owner splits one large `unDelegateBalance` into N smaller `UnDelegateResourceContract` calls (which is fully within their signing authority — `UnDelegateResourceContract` is a standard broadcastable contract type validated/executed by `UnDelegateResourceActuator.validate()`/`execute()`), each smaller call independently truncates `transferUsage` toward zero. The cumulative `transferUsage` transferred back across N small calls is systematically ≤ the `transferUsage` that would result from a single large call, because `floor(a₁) + floor(a₂) + ... ≤ floor(a₁+a₂+...)`.

The result: the receiver's `netUsage`/`energyUsage` is decreased by less than it should be per unlocked TRX (so the receiver ends up carrying usage debt that is no longer backed by the frozen balance that funded it), and the owner's reclaimed usage (`ownerUsage + transferUsage` in `ResourceProcessor.unDelegateIncrease`) is smaller than the "fair" amount — meaning bandwidth/energy usage the owner actually consumed effectively disappears from both accounts' tracked usage. This corresponds exactly to the "lender loses accrued value while borrower pays less" pattern from the report, mapped onto TRON's resource-delegation accounting instead of an interest accrual.

Note: `ResourceProcessor` in this codebase already contains a `hardenCalculation()` / `allowHardenResourceCalculation()` feature-flagged path (BigInteger-based, e.g. `getUsage`, `increase`, `getNewWindowSize`) that fixes analogous truncation issues elsewhere [4](#0-3) , but the `transferUsage`/`unDelegateMaxUsage` computation inside `UnDelegateResourceActuator` itself is **not** covered by that hardening — it still uses raw `double` math unconditionally.

### Impact Explanation
This causes a lasting, cumulative divergence between the resource usage recorded on-chain for owner/receiver accounts and the usage that is actually backed by frozen TRX/stake. Since `getNetUsage()`/`getEnergyUsage()` directly gate free bandwidth/energy allowances (via the window-based accounting in `ResourceProcessor`/`BandwidthProcessor`), an attacker can repeatedly perform many small `UnDelegateResourceContract` operations to make consumed-usage debt vanish from the accounting, allowing them (or a colluding receiver) to obtain more free bandwidth/energy allowance than their real, backing frozen balance justifies. This is an "unbacked" resource-accounting condition (an economic-integrity violation of the staking/resource model), reachable purely from unprivileged, self-signed transactions.

### Likelihood Explanation
`UnDelegateResourceContract` is a normal broadcastable transaction any account holder with delegated resources can submit at will and repeat cheaply (transaction fee for this actuator is `calcFee() == 0`) [5](#0-4) . No special permissions or SR/witness cooperation is required — only that the attacker previously delegated resources to an account they (or a colluding party) control and then un-delegates in many small increments. The exploit is deterministic and does not depend on network timing, making it straightforward to automate.

### Recommendation
- Replace the `double`-based `transferUsage`/`unDelegateMaxUsage` computation in `UnDelegateResourceActuator.execute()` with exact integer (`BigInteger`) arithmetic performed once, consistent with the `calculateGlobalLimitV2`/`getUsage` hardened patterns already present in `ResourceProcessor.java`.
- Ensure the rounding direction chosen does not allow the sum of many small operations to differ from one large operation (i.e., make the transfer function "linear"/order-independent), or explicitly document/enforce a rounding direction that always favors the protocol rather than the caller.
- Add a property/fuzz test asserting that repeatedly un-delegating a total balance B in K arbitrary increments yields the same aggregate `transferUsage` (within a bounded, protocol-favoring rounding error) as un-delegating B in one call.

### Proof of Concept
Conceptual (not executed, since this is a read-only analysis):
1. Attacker delegates BANDWIDTH resources such that `receiverCapsule.getAllFrozenBalanceForBandwidth()` and `receiverCapsule.getNetUsage()` are non-trivial (receiver has accrued real bandwidth usage backed by the delegation).
2. Attacker issues one `UnDelegateResourceContract` for the full delegated `balance` and records `transferUsage₁` computed at [6](#0-5) .
3. Attacker resets state (re-delegate the same amount) and instead issues N separate `UnDelegateResourceContract` calls of `balance/N` each; the same code path executes N times, each independently truncating `(long)` casts.
4. Sum the resulting `transferUsage` values across the N calls; due to `floor` truncation on each call, `Σ transferUsage_i < transferUsage₁` for sufficiently large N and/or unfavorable balance/usage ratios (analogous to the report's 100×100,000 USDC vs. 1×10,000,000 USDC example).
5. The residual usage never reclaimed from the receiver nor re-attributed to the owner represents usage no longer backed by frozen balance — an unbacked resource-accounting delta that compounds with repeated exploitation.

  private long getUsage(long oldUsage, long oldWindowSize, long newUsage, long newWindowSize) {
    if (hardenCalculation()) {
      BigInteger bi = BigInteger.valueOf(oldUsage).multiply(BigInteger.valueOf(oldWindowSize))
          .add(BigInteger.valueOf(newUsage).multiply(BigInteger.valueOf(newWindowSize)));
      return bi.divide(BigInteger.valueOf(precision)).longValueExact();
    }
    return (oldUsage * oldWindowSize + newUsage * newWindowSize) / precision;
  }
