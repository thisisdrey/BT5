### Title
Unauthenticated 16MB allocation per StackerDB chunk before per-replica chunk_size check - ([File: libstackerdb/src/libstackerdb.rs])

### Summary
`StackerDBChunkData::consensus_deserialize` allocates up to `STACKERDB_MAX_CHUNK_SIZE` (16 MB) for `data` regardless of the target StackerDB replica's configured `chunk_size`, and this allocation happens during message decoding — long before `validate_received_chunk`/`try_replace_chunk` ever check the per-replica size cap. An unprivileged remote peer can push an unsolicited `StackerDBPushChunk` (or reply to `StackerDBGetChunk`) with a ~16MB `data` field for a StackerDB configured with a much smaller `chunk_size` (e.g. 4096 bytes as in the signer StackerDBs, or any custom small config), forcing the node to allocate 16MB per message before the size check runs and rejects it.

### Finding Description
`StackerDBChunkData::consensus_deserialize` in `libstackerdb/src/libstackerdb.rs` bounds the `data` field read with `read_next_at_most(fd, STACKERDB_MAX_CHUNK_SIZE)` where `STACKERDB_MAX_CHUNK_SIZE = 16 * 1024 * 1024` [1](#0-0) , and this constant is a fixed global wire cap, not the target replica's configured `chunk_size` [2](#0-1) . This is the type used by `StackerDBPushChunkData::consensus_deserialize` (`chunk_data: StackerDBChunkData = read_next(fd)?`) in `stackslib/src/net/codec.rs` [3](#0-2) , and by the top-level `StacksMessageType::consensus_deserialize` dispatch for `StackerDBPushChunk`/`StackerDBChunk` message IDs [4](#0-3) .

The actual per-replica size gate lives in `PeerNetwork::validate_received_chunk` (`stackslib/src/net/stackerdb/mod.rs`), which checks `data.data.len() as u64 > config.chunk_size` — but this runs only *after* the full `Vec<u8>` has already been materialized by `consensus_deserialize` [5](#0-4) . The same order-of-operations exists in `StackerDBTx::try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs`, which checks `chunk.len() as u64 > self.config.chunk_size` on an already-allocated slice [6](#0-5) .

So the equality the question describes is broken: the codec allocates up to the global 16MB cap, not the target DB's `config.chunk_size`, before any per-slot/signature check runs. Real-world StackerDB configs can have `chunk_size` far below 16MB — signer StackerDBs use `SIGNERS_STACKERDB_CHUNK_SIZE = 2MB` [7](#0-6)  and test configs use even smaller values (1024 or 4096 bytes) [8](#0-7) . An attacker who knows any valid `contract_id` (StackerDB contracts are public/discoverable) and any `slot_id` can send a `StackerDBPushChunk` with ~16MB of `data`; the message is fully decoded (allocating ~16MB) and only rejected afterward by `validate_received_chunk`'s size check.

### Impact Explanation
Each malicious message forces the node to allocate up to 16MB (`STACKERDB_MAX_CHUNK_SIZE`) for the `data` Vec, regardless of the actual much-smaller `chunk_size` configured for that StackerDB replica. This is repeatable per-message and requires no privileged role, no valid slot ownership, and no valid signature — rejection happens only in `validate_received_chunk`/`try_replace_chunk`, strictly after allocation. Repeated sends amplify memory pressure disproportionately to the bytes an attacker needs to send relative to what a legitimate chunk for that replica could ever be (e.g., 16MB allocated to push into a 4KB-capped replica), which fits the "unauthenticated allocation amplification" pattern described in the question.

### Likelihood Explanation
The attacker only needs to be a P2P-connected peer capable of sending `StacksMessage` frames — no handshake privilege beyond being an accepted peer, no valid slot signature, and no ownership of the target slot is required, since `try_replace_chunk`'s and `validate_received_chunk`'s size checks are the very first checks but they run after decode. The attacker must know a valid `contract_id` for a configured StackerDB (these are typically public boot contracts like `signers-*` or `miners`), which is not a secret. The message is bounded only by the outer `StacksMessage` payload cap (up to `STACKERDB_MAX_CHUNK_SIZE`/`MAX_PAYLOAD_LEN`), so a single ~16MB message per send achieves the described amplification, and it is trivially repeatable.

### Recommendation
Pass the target StackerDB's `config.chunk_size` into the deserialization path (or perform an early cheap length check on the length-prefix before allocating) so that `StackerDBChunkData::consensus_deserialize` — or a wrapper used specifically for StackerDB chunk messages received over the wire — rejects/aborts decoding as soon as the declared length exceeds the *specific* replica's configured chunk size, rather than the static global `STACKERDB_MAX_CHUNK_SIZE`. Since the codec-level function cannot know per-contract config at generic-deserialize time, an alternative is to check the 4-byte length prefix against `config.chunk_size` in `handle_unsolicited_StackerDBPushChunk`/`StackerDBGetChunk` reply-handling code path before allocation, e.g. by peeking the length header and short-circuiting the read, or lowering the effective cap used for network-received StackerDB messages to the smallest chunk_size across all configured StackerDBs plus a safety margin.

### Proof of Concept
```rust
// stackslib/src/net/stackerdb/tests/db.rs (or a new test module)
// Build raw wire bytes for a StackerDBChunkData with `data.len() == STACKERDB_MAX_CHUNK_SIZE`
// (or close to it) for a StackerDBConfig with chunk_size = 4096, and confirm that
// StackerDBChunkData::consensus_deserialize successfully allocates the full buffer
// before validate_received_chunk/try_replace_chunk ever gets a chance to reject it.

#[test]
fn test_consensus_deserialize_allocates_before_chunk_size_check() {
    let big_len: u32 = 16 * 1024 * 1024; // STACKERDB_MAX_CHUNK_SIZE
    let mut bytes = vec![];
    bytes.extend_from_slice(&0u32.to_be_bytes());       // slot_id
    bytes.extend_from_slice(&1u32.to_be_bytes());       // slot_version
    bytes.extend_from_slice(&[0u8; 65]);                // sig (empty/garbage)
    bytes.extend_from_slice(&big_len.to_be_bytes());    // data length prefix
    bytes.extend(std::iter::repeat(0xffu8).take(big_len as usize)); // data payload

    let mut cursor = std::io::Cursor::new(bytes);
    // This succeeds and allocates 16MB, even though a StackerDBConfig for this
    // contract might have chunk_size = 4096 -- the allocation already happened
    // before any config-aware check could run.
    let chunk = StackerDBChunkData::consensus_deserialize(&mut cursor).unwrap();
    assert_eq!(chunk.data.len(), big_len as usize);

    // Only now, after the 16MB Vec is materialized, does the size gate fire:
    let mut config = StackerDBConfig::template();
    config.chunk_size = 4096;
    // validate_received_chunk / try_replace_chunk would reject here --
    // but the allocation cost was already paid.
}
```
This demonstrates that the allocation size is governed by `STACKERDB_MAX_CHUNK_SIZE`, not by the specific `StackerDBConfig.chunk_size` for the target contract, confirming the fault described in the question.
