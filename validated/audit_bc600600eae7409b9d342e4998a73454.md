### Title
Unbounded array allocation from attacker-controlled length word in `ValidateMultiSign` precompile leads to Denial of Service - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` precompiled contract (reachable via a `STATICCALL`/`CALL` to its precompile address from any deployed smart contract, i.e. from any unprivileged transaction) reads a length value directly out of the caller-supplied `data` buffer and uses it to allocate a Java array before any bound is enforced against the actual size of the submitted payload. This mirrors the LND "onion bomb" bug class (CVE-2024-38359): a length field taken from untrusted, attacker-controlled input drives a memory allocation that is disproportionate to the actual bytes the caller paid to submit, enabling a cheap memory-exhaustion DoS.

### Finding Description
`ValidateMultiSign.execute` parses the raw call data into words and locates the signature-array offset via `words[3]` [1](#0-0) . The `MAX_SIZE` bound-check on `sigArraySize` is only performed when `VMConfig.allowTvmSelfdestructRestriction()` is enabled: [2](#0-1) 

When that config flag is not enabled, execution falls straight into `extractBytesArray(words, words[3].intValueSafe() / WORD_SIZE, rawData)`, which reads a length directly from the word array and allocates a `byte[len][]` before validating `len` against `words.length` or the actual payload size: [3](#0-2) 

`len` comes from `words[offset].intValueSafe()`, an attacker-fully-controlled 256-bit word truncated/clamped to an `int`, so a malicious caller can set it to a very large positive value (e.g. close to `Integer.MAX_VALUE`). `new byte[len][]` allocates an object-reference array of that size — for a `len` near `Integer.MAX_VALUE` this is many gigabytes of reference storage — and the JVM will throw `OutOfMemoryError` (or spend significant CPU/heap churn) at that single line, before any subsequent bounds-checked loop executes. Only the `extractSigArray`/`MAX_SIZE` guarded path (used when `allowTvmSelfdestructRestriction` is on) validates `sigArraySize > MAX_SIZE` first; the ungated legacy path performs no such check.

Critically, the energy charged for this call is computed from the physical length of the submitted call data (`data.length / WORD_SIZE`), not from the attacker-chosen `len` value embedded inside that data: [4](#0-3) 

This is exactly the disconnect described in the LND onion-bomb report: a small, cheap request declares an oversized internal length field, and the node allocates memory proportional to the declared (attacker-controlled) length rather than the metered/paid-for length.

### Impact Explanation
A contract call that reaches `ValidateMultiSign` with a crafted `words[3]`/length word can force the executing full node to attempt an outsized heap allocation per invocation, independent of the actual (small) energy cost paid. Repeated or concurrent invocations (e.g., from multiple transactions in a block, or a single transaction calling the precompile many times via a loop contract) can exhaust available heap and crash or stall the node process — a node crash/halt DoS is explicitly an accepted impact class for this review.

### Likelihood Explanation
This precompile is invoked by ordinary TVM `CALL`/`STATICCALL` from any deployed contract, which any account can deploy and invoke; no special privileges are required. Reaching the vulnerable branch only requires that `VMConfig.allowTvmSelfdestructRestriction()` be disabled, which is the pre-upgrade / legacy configuration state and thus plausible on chains or historical/still-supported protocol versions where this proposal has not been activated.

### Recommendation
Move the `sigArraySize > MAX_SIZE` (and general array-length sanity/bounds) check outside the `allowTvmSelfdestructRestriction` conditional so it always executes before calling `extractBytesArray`/`extractSigArray`. Additionally, harden `extractBytesArray`/`extractBytes32Array`/`extractSigArray` themselves to validate `len` against `words.length` (and a sane maximum such as `MAX_SIZE`) before allocating any array, so a malicious length word can never drive an allocation larger than the actual supplied payload could support.

### Proof of Concept
1. Deploy a contract that performs a `STATICCALL` to the `ValidateMultiSign` precompile address.
2. Construct `rawData` such that:
   - `words[3]` encodes an offset (in the abi-encoding sense) that resolves to a word slot,
   - that resolved word slot's value is set to a very large integer (e.g. `0x7FFFFFFF`),
   - overall submitted calldata remains small (a handful of words) to minimize energy cost.
3. On a network/config where `allowTvmSelfdestructRestriction` is disabled, invoke the contract; `extractBytesArray` executes `new byte[0x7FFFFFFF][]`, driving an out-of-proportion memory allocation attempt relative to the energy paid, which can throw `OutOfMemoryError` or otherwise stress the node's heap.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }
