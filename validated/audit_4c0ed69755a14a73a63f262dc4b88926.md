Missing Slippage Protection in ExchangeInjectActuator Enables Sandwich Attack on Pool Injections - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java])

### Summary
`ExchangeInjectContract`/`ExchangeInjectActuator` computes the paired ("another") token amount to be pulled from the exchange creator's balance purely from the live pool ratio at validate/execute time, with **no caller-supplied minimum/maximum bound**. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `ExchangeTransactionActuator.doValidate()` (`anotherTokenQuant < tokenExpected` → reject), `ExchangeInjectContract` has no analogous field at all: [1](#0-0) [2](#0-1) 

This is the same bug class as the external report: an on-chain swap/liquidity operation whose expected-output/expected-cost guard is effectively hardcoded to "accept any ratio ≥ 0" rather than a caller-chosen safe bound, exposing the transaction to sandwich manipulation.

### Finding Description
`ExchangeInjectActuator.doValidate()` and `execute()` compute `anotherTokenQuant` from `firstTokenBalance`/`secondTokenBalance` read from the exchange pool at the moment the transaction is processed: [3](#0-2) 

The only sanity checks applied to `anotherTokenQuant` are that it is positive and that the resulting new pool balances stay under `getExchangeBalanceLimit()`: [4](#0-3) 

There is no field in `ExchangeInjectContract` (unlike `ExchangeTransactionContract.expected`) that lets the signer bound the acceptable ratio/amount of the paired token they will be forced to contribute: [1](#0-0) 

Because the exchange pool ratio (`firstTokenBalance`/`secondTokenBalance`) can be moved by any unprivileged account broadcasting an `ExchangeTransactionContract` against the same exchange pair (`ExchangeTransactionActuator`, callable by anyone), an attacker can:
1. Observe a pending `ExchangeInjectContract` from the exchange creator in the mempool.
2. Front-run it with a `MarketSellAssetContract`-style TRX/TRC10 swap via `ExchangeTransactionContract` that skews `firstTokenBalance`/`secondTokenBalance` unfavorably for the pending inject.
3. Let the victim's inject execute at the now-skewed ratio, forcing the creator to contribute far more of the "another" token than intended for the same `tokenQuant`.
4. Back-run with a reverse `ExchangeTransactionContract` to restore the ratio and pocket the difference, extracted permanently from the victim's account balance/asset holdings.

### Impact Explanation
The exchange creator's asset/TRX balance is permanently transferred out at an attacker-manipulated ratio with no way to bound the loss, since `ExchangeInjectContract` provides no minimum/maximum guard field and the actuator enforces none. This is a concrete permanent-loss-of-funds scenario for the exchange creator, reachable purely by broadcasting standard signed transactions (`ExchangeTransactionContract` and `ExchangeInjectContract`) against the on-chain TRC10 Bancor-style exchange, satisfying the "theft or permanent freezing of funds" acceptance bar.

### Likelihood Explanation
Medium. Exploitation requires: (a) the target exchange creator to submit an `ExchangeInjectContract`, (b) the attacker to observe it before inclusion and control transaction ordering within the same block/```validate```-```execute``` window (feasible for a witness/miner-adjacent actor, or via typical mempool front-running), and (c) sufficient TRX/asset liquidity to move the pool ratio meaningfully. This is analogous to classic AMM sandwich attacks and does not require any special privilege beyond broadcasting transactions, but does require transaction-ordering influence, which lowers likelihood relative to a fully passive victim scenario.

### Recommendation
Add an explicit slippage-bound field to `ExchangeInjectContract` (e.g., `max_another_token_quant` or a min/max ratio tolerance), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` analogous to the `expected` check already present in `ExchangeTransactionActuator`: [2](#0-1) 
This should reject the inject if the computed `anotherTokenQuant` exceeds the caller-specified bound, closing the sandwich window. The same review should be extended to `ExchangeWithdrawActuator`, which was not verified during this analysis and may have an analogous gap.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract{exchangeId, tokenId=firstTokenID, quant=Q}` intending to inject `Q` of token A along with the pool-ratio-implied amount of token B.
2. Attacker, observing this pending tx, broadcasts an `ExchangeTransactionContract` selling a large amount of token B into the pool first, shifting `firstTokenBalance`/`secondTokenBalance` so that the implied `anotherTokenQuant` for the victim's pending inject increases sharply (per `ExchangeInjectActuator.execute()` line 73-74/79-80 ratio math).
3. Victim's `ExchangeInjectContract` executes at the skewed ratio in `ExchangeInjectActuator.execute()`, deducting the inflated `anotherTokenQuant` from the victim's balance/asset holdings (lines 85-99).
4. Attacker broadcasts a reverse `ExchangeTransactionContract` restoring the ratio and extracting the excess value, which was calculable in advance because the pool state is fully deterministic and visible on-chain — no minimum-bound check in `ExchangeInjectActuator` prevents step 3 from executing at an arbitrarily unfavorable ratio.

Note: I could not fully verify whether `ExchangeWithdrawActuator` has a similar unguarded ratio computation, since it was not directly inspected in this session; this should be checked as a follow-up.
