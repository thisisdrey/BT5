### Title
Voter/witness delegation rewards accrued before a witness's vote-count snapshot exists are permanently unclaimable and stuck - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`)

### Summary
`MortgageService.payReward()` credits block/transaction-fee rewards to a per-cycle bucket (`delegationStore.addReward(cycle, witnessAddress, value)`) using whatever `currentCycleNumber()` is at the moment the block/producer reward is paid. However, the per-cycle vote-count snapshot that is required to later attribute that reward to individual voters (`delegationStore.setWitnessVote(nextCycle, ...)`) is only written by `MaintenanceManager.doMaintenance()` for `nextCycle = currentCycle + 1`, i.e. one cycle *after* rewards for the current cycle have already started accruing. Any reward recorded for a cycle whose vote snapshot was never written (`DelegationStore.getWitnessVote()` returns the sentinel `REMARK = -1`) is silently skipped by the reward-computation logic and can never be claimed by any voter, exactly mirroring the Bribe/first-epoch pattern in the referenced report.

### Finding Description
- Block/tx-fee rewards are added to a witness's per-cycle bucket with `delegationStore.addReward(cycle, witnessAddress, value)` inside `payReward()`, keyed by `dynamicPropertiesStore.getCurrentCycleNumber()` at call time: [1](#0-0) 

- The corresponding per-cycle witness vote-count snapshot, which is required to divide that reward among voters, is only populated for `nextCycle = currentCycle + 1` inside `MaintenanceManager.doMaintenance()`, i.e. always one cycle behind the cycle that just accrued rewards: [2](#0-1) 

- `DelegationStore.getWitnessVote()` returns the sentinel `REMARK` (`-1`) when no snapshot has been written for that cycle: [3](#0-2) 

- The reward-attribution logic in `MortgageService` (old-algorithm path) explicitly skips any cycle whose `getWitnessVote()` returns `REMARK` or `0`, meaning the reward accumulated for that cycle can never be distributed to any voter and is simply orphaned in the `DelegationStore`: [4](#0-3) 
The new Vi-based algorithm has the same structural gap — `computeReward()`/`getWitnessVi()` deltas are computed strictly between `beginCycle-1` and `endCycle-1`; a cycle whose Vi accumulation input (`witness.getVoteCount()`) never existed for that specific cycle boundary produces no delta and the reward for that cycle is unattributed: [5](#0-4) 

This is functionally identical to the reported Bribe bug: value ("bribes"/rewards) is deposited into a cycle bucket before the bucket has valid distribution metadata (vote-count snapshot), and the downstream claim/attribution logic has no fallback to retroactively repair or redistribute that bucket — the value is permanently stranded.

### Impact Explanation
Reward TRX that was added to `DelegationStore` for a cycle lacking a witness-vote snapshot (e.g. the very first cycle after the delegation/voting-reward feature is activated by governance, or the genesis cycle before the first maintenance ever runs) becomes permanently unclaimable by any voter. This is a genuine "funds frozen forever" condition: the value is neither refundable nor later recoverable through any other code path, matching the High-severity classification used in the referenced report (irreversible stranding of value due to a timing/snapshot misalignment between reward accrual and reward-attribution metadata).

### Likelihood Explanation
This condition is deterministic and not attacker-dependent — it occurs automatically:
1. On genesis / very first cycle of any new chain (cycle 0), since the witness-vote snapshot for cycle 0 is never written (only `nextCycle` snapshots are ever written by `doMaintenance()`).
2. Whenever the `allowChangeDelegation`/new-reward-algorithm feature is toggled on for the first time via governance proposal mid-operation, since the snapshot-write branch in `doMaintenance()` is itself gated by `dynamicPropertiesStore.allowChangeDelegation()`, so the cycle in which the flag transitions from disabled to enabled has no witness-vote snapshot despite rewards already being accrued into it.

No privileged action or malicious transaction is required; it is a structural consequence of the reward-accrual/snapshot ordering, occurring passively every time a fresh delegation reward "epoch" boundary is crossed — closely analogous to "every new pair of deployed Bribe/Gauge contracts" being affected in the original report.

### Recommendation
- Ensure the witness-vote-count snapshot for the *current* cycle is written before or atomically with the first reward accrual into that cycle, not one cycle late, e.g. write the cycle-0/initial snapshot during genesis initialization, and write the snapshot for the activation cycle at the moment the feature flag flips (not only via the `nextCycle` logic in `doMaintenance()`).
- Alternatively, extend `computeReward`/Vi-delta logic to fall back to a valid earlier or later snapshot instead of silently discarding cycles where `getWitnessVote()` returns `REMARK`, so that no reward bucket is permanently orphaned.
- Add an explicit reconciliation/sweep mechanism (or governance-triggered redistribution) for any `DelegationStore` reward entries whose cycle has no corresponding vote snapshot, so already-accrued value is not stranded indefinitely.

### Proof of Concept
1. At genesis (or immediately after a proposal enables `allowChangeDelegation`/the new reward algorithm), `dynamicPropertiesStore.getCurrentCycleNumber()` returns cycle `N`, and no witness-vote snapshot exists yet for cycle `N` (`DelegationStore.getWitnessVote(N, sr)` → `REMARK`), because `MaintenanceManager.doMaintenance()` has not yet run to populate `nextCycle = N+1`.
2. Blocks are produced and `MortgageService.payBlockReward()`/`payTransactionFeeReward()` call `payReward()`, which calls `delegationStore.addReward(N, witnessAddress, value)` — value is now stored keyed to cycle `N`.
3. `doMaintenance()` eventually runs and only ever writes the vote snapshot for `nextCycle = N+1` onward — cycle `N` never receives a snapshot.
4. Any voter later calling `withdrawReward()`/`queryReward()` computes rewards via `computeReward(beginCycle, endCycle, ...)`, which for `cycle = N` finds `getWitnessVote(N, sr)` equal to `REMARK` (or, in the old algorithm, `0`), causing the loop to `continue` and skip that cycle's reward entirely: [4](#0-3) 
5. The value stored via step 2's `addReward(N, ...)` is never read by any successful attribution path — it remains in `DelegationStore` forever, unclaimable by any voter, matching the "stuck in first epoch" pattern of the referenced report.

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }

  private long computeReward(long beginCycle, long endCycle, AccountCapsule accountCapsule) {
    if (beginCycle >= endCycle) {
      return 0;
    }

    long reward = 0;
    long newAlgorithmCycle = dynamicPropertiesStore.getNewRewardAlgorithmEffectiveCycle();
    List<Pair<byte[], Long>> srAddresses = accountCapsule.getVotesList().stream()
        .map(vote -> new Pair<>(vote.getVoteAddress().toByteArray(), vote.getVoteCount()))
        .collect(Collectors.toList());
    if (beginCycle < newAlgorithmCycle) {
      long oldEndCycle = min(endCycle, newAlgorithmCycle,
          dynamicPropertiesStore.disableJavaLangMath());
      reward = getOldReward(beginCycle, oldEndCycle, srAddresses);
      beginCycle = oldEndCycle;
    }
    if (beginCycle < endCycle) {
      for (Pair<byte[], Long>  vote : srAddresses) {
        byte[] srAddress = vote.getKey();
        BigInteger beginVi = delegationStore.getWitnessVi(beginCycle - 1, srAddress);
        BigInteger endVi = delegationStore.getWitnessVi(endCycle - 1, srAddress);
        BigInteger deltaVi = endVi.subtract(beginVi);
        if (deltaVi.signum() <= 0) {
          continue;
        }
        long userVote = vote.getValue();
        reward += deltaVi.multiply(BigInteger.valueOf(userVote))
            .divide(DelegationStore.DECIMAL_OF_VI_REWARD).longValue();
      }
    }
    return reward;
  }
