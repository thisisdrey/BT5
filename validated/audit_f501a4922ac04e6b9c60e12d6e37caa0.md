### Title
Group-Level Rate Limiter Can Be Bypassed by Batching Multiple Withdraw/Borrow Instructions in a Single Transaction - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
The group-level outflow rate limiter is checked read-only per-instruction and only mutated later, off-chain, by an admin aggregation call. Because the on-chain group counter is never incremented within the user's own transaction, an authority can chain multiple withdraw/borrow instructions against the same (or different) banks in a single atomic transaction, and each instruction independently passes the "remaining capacity" check against the same stale, unmutated counter — allowing the user to withdraw a multiple of the intended hourly/daily USD cap before the off-chain aggregator ever has a chance to observe and apply the first instruction's outflow.

### Finding Description
`record_withdrawal_outflow` in [1](#0-0)  performs two different treatments of rate limiting:
- The **bank-level** limiter is mutated immediately and in-place: `bank.rate_limiter.try_record_outflow(...)`.
- The **group-level** limiter is only *read*: `group.rate_limiter.hourly.effective_remaining_capacity(...)` / `.daily.effective_remaining_capacity(...)` are compared against the withdrawal's USD value, and no corresponding write/decrement of `group.rate_limiter` occurs in the instruction. The counter is only advanced later by the admin via `update_group_rate_limiter`, which requires off-chain aggregation of `RateLimitFlowEvent`s.

This design is explicitly documented in [2](#0-1) : "The group rate limiter is only checked read-only... A `RateLimitFlowEvent` is emitted for off-chain aggregation." The intended mitigation for cross-transaction abuse is the same off-chain settlement discussed in the analog report, but nothing prevents a *single* transaction from calling `lending_account_withdraw` / `lending_account_borrow` (or the Kamino/Drift/Juplend/Solend equivalents, which call the same helper — see [3](#0-2)  and [4](#0-3) ) multiple times against multiple banks/positions within the same atomic transaction. Each call independently re-reads `group.rate_limiter`'s unmutated counter and passes the check as long as *that single* withdrawal is under the cap — even though the cumulative outflow across all instructions in the transaction can vastly exceed the configured group daily/hourly limit.

This is directly analogous to the reported bug class: multiple "ops" (here, multiple withdraw/borrow instructions against the shared "wallet"/resource — the group's aggregate outflow budget) are validated independently against a snapshot of shared state that is not updated between operations, defeating the very purpose of the check (just as Bob's two ops each independently pass `simulateValidation` against the same stale balance).

### Impact Explanation
The group rate limiter exists specifically to cap aggregate USD outflow from the group per hour/day as "a defense if the risk workflow is abused or compromised" (see the deleverage-limit analog description in the same guide). Bypassing it lets a user (or colluding accounts) withdraw/borrow far beyond the intended safety cap in a single transaction, defeating a protocol-level solvency/liquidity safeguard. Depending on how the limit is used operationally (e.g., to throttle outflow during oracle stress or incident response), this could contribute to accelerated liquidity drain beyond what admins can react to, since the off-chain aggregator has no on-chain enforcement mechanism to stop it mid-flight within one transaction.

### Likelihood Explanation
Likelihood is **High** for any account holder able to construct a single transaction with multiple withdraw/borrow instructions (a routine capability — flashloans, order execution, and multi-bank flashloan tests in this very codebase demonstrate that multiple lending instructions are freely composable in one tx, e.g. [5](#0-4) ). No privileged role, oracle manipulation, or race condition is required — it is a deterministic property of how the group counter is checked (read-only, never mutated in-instruction).

### Recommendation
Mutate an in-transaction/session-scoped counter for the group-level limiter (not just the persisted on-chain counter) so that successive withdraw/borrow instructions within the same transaction see the cumulative outflow already consumed by earlier instructions in that transaction, rather than each checking against the same stale baseline. At minimum, decrement the group's read model in an ephemeral fashion (e.g., a transient in-account or `remaining_accounts`-passed running total) so that stacking multiple withdrawals in one atomic transaction cannot exceed the configured cap.

### Proof of Concept
1. Admin configures `configure_group_rate_limits` with a group hourly cap of, e.g., $10 (as in the test at [6](#0-5) , which shows the cap being read-only checked and only updated by a later admin call).
2. A user with sufficient collateral across multiple banks builds a single transaction containing several `lending_account_withdraw` (or `lending_account_borrow`) instructions, each individually valued at just under the $10 cap (e.g., 4 instructions of $9 each = $36 total).
3. Each instruction independently calls `record_withdrawal_outflow`, which reads `group.rate_limiter.hourly.effective_remaining_capacity(...)` — still $10, because no instruction so far has mutated it — and each passes.
4. All four withdrawals succeed atomically, producing an aggregate outflow of $36 against a $10 configured hourly cap, before any `RateLimitFlowEvent` is aggregated and applied via `update_group_rate_limiter`. This mirrors exactly the "batched event aggregation" test flow shown in [6](#0-5) , but executed atomically in one transaction rather than sequentially across separate confirmed transactions, so the cap is bypassed entirely rather than merely delayed.

pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }
    }
    Ok(())

### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.

Important details:

- Flashloans, liquidations, and deleverages skip the normal rate-limit accounting path.
- `RateLimitFlowEvent` is an indexing aid, not a source of truth. Solana log truncation can drop
  events, so the off-chain worker must reconcile gaps instead of assuming no event means no flow.

  it("(admin) batched event aggregation - multiple actions then single admin update", async () => {
    // Simulates production flow: multiple user actions happen over a period,
    // admin aggregates all emitted events and calls updateGroupRateLimiter once.
    await setRateLimits({
      bankHourly: usdcNative(1_000),
      bankDaily: new BN(0),
      groupHourly: new BN(10),
      groupDaily: new BN(0),
    });

    const allEvents: RateLimitFlowEvent[] = [];

    // Action 1: Borrow 3 USDC
    const events1 = await borrowUsdcWithEvents(usdcNative(3));
    allEvents.push(...events1);

    // Action 2: Borrow 2 USDC
    const events2 = await borrowUsdcWithEvents(usdcNative(2));
    allEvents.push(...events2);

    // Action 3: Repay 1 USDC
    const events3 = await repayUsdcWithEvents(usdcNative(1));
    allEvents.push(...events3);

    // Action 4: Borrow 1 USDC
    const events4 = await borrowUsdcWithEvents(usdcNative(1));
    allEvents.push(...events4);

    // Verify all events were captured
    assert.equal(allEvents.length, 4, "Should have 4 events total");

    // Admin aggregates all events at once (as would happen in production every ~10 minutes)
    const { totalOutflowUsd, totalInflowUsd } = aggregateFlowEvents(allEvents);
    assert.equal(totalOutflowUsd, 6, "3 + 2 + 1 = 6 USDC outflow");
    assert.equal(totalInflowUsd, 1, "1 USDC inflow");

    // Group state should still be unchanged (read-only during user instructions)
    const groupBeforeAdmin = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(groupBeforeAdmin.rateLimiter.hourly.curWindowOutflow, 0);

    // Admin submits both outflow and inflow in a single update
    await adminUpdateGroupRateLimiter({
      outflowUsd: new BN(totalOutflowUsd),
      inflowUsd: new BN(totalInflowUsd),
    });

    // Net outflow = 6 - 1 = 5
    const groupAfterAdmin = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    assertBNEqual(groupAfterAdmin.rateLimiter.hourly.curWindowOutflow, 5);

    // Borrow 2 more USDC and capture events for a second batch
    const events5 = await borrowUsdcWithEvents(usdcNative(2));
    const batch2 = aggregateFlowEvents(events5);
    assert.equal(batch2.totalOutflowUsd, 2);

    // Admin does second batch update
    await adminUpdateGroupRateLimiter({
      outflowUsd: new BN(batch2.totalOutflowUsd),
    });

    const groupAfterBatch2 = await program.account.marginfiGroup.fetch(
      marginfiGroup.publicKey,
    );
    // 5 (previous) + 2 (new) = 7
    assertBNEqual(groupAfterBatch2.rateLimiter.hourly.curWindowOutflow, 7);

    // Borrow 4 more - should fail the read-only group capacity check (7 + 4 = 11 > 10)
    await expectFailedTxWithError(
      async () => {
        await borrowUsdc(usdcNative(4));
      },
      "GroupHourlyRateLimitExceeded",
      6117,
    );
