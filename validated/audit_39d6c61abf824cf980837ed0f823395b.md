The `content_hash` on `AttachmentRequest` is only used earlier for building/deduplicating the request queue in `get_prioritized_attachments_requests`, not for validating the response [2](#0-1) .

The actual hash check happens much later and outside the reliability-scoring path: in `AttachmentsDownloader::run`, once the state machine reaches `Done`, each attachment in `context.attachments` is looked up by `attachment.hash()` via `find_all_attachment_instances`, and `resolve_attachment(&attachment.hash())` is called [3](#0-2) . If a peer returns a syntactically valid but hash-mismatched `Attachment`, `find_all_attachment_instances(&attachment.hash())` simply won't match the instance that was actually being requested (it will return zero or unrelated instances), so the batch instance remains unresolved and gets retried — but critically, the peer's `ReliabilityReport` was already bumped as successful in `extend_with_attachments` regardless of this later mismatch, and that update is never reverted.

This confirms the broken equality: `bump_successful_requests()` is triggered purely by successful JSON/deserialization of `decode_atlas_get_attachment()`, not by content-hash equality to the requested attachment. A malicious peer can serve any well-formed `Attachment` payload (any bytes deserializable into the expected structure) in response to every `AttachmentRequest` and have its reliability score inflated on every single response, with no cost beyond running a peer and answering GET-attachment requests.

### Title
Reliability score bumped on JSON-decode success without content_hash verification, enabling reliability-score poisoning - (File: stackslib/src/net/atlas/download.rs)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` bumps a peer's reliability score as soon as `decode_atlas_get_attachment()` succeeds, without ever checking that the returned attachment's hash matches the requested `content_hash`. A remote, unprivileged peer can therefore serve arbitrary (hash-mismatched) but well-formed attachments to cheaply and repeatedly inflate its own reliability score.

### Finding Description
In `extend_with_attachments` (download.rs:530-558), for each successfully-decoded response the code does `self.attachments.insert(response.attachment); report.bump_successful_requests();` with no comparison against `request.content_hash` [4](#0-3) . The `content_hash` field of `AttachmentRequest` is only used to build the outgoing request queue and to de-duplicate requests [5](#0-4) , not to validate the response payload. The genuine hash check (`attachment.hash()` used to look up matching `AttachmentInstance`s via `find_all_attachment_instances`) only happens later in `AttachmentsDownloader::run`, entirely decoupled from the peer's `ReliabilityReport`, which was already mutated inside `extend_with_attachments` [3](#0-2) . Consequently a peer can respond to every `AttachmentRequest` with any syntactically valid `Attachment` payload (regardless of hash) and have `bump_successful_requests()` called every time, since the only gate is successful decoding, not content correctness.

### Impact Explanation
The `ReliabilityReport`/`AttachmentRequest::Ord` ordering and `get_most_reliable_source`-style prioritization (built from these accumulated scores) determine which peer is queried/trusted first for future attachment (BNS zonefile) downloads. By cheaply inflating its score with garbage responses, a malicious peer can get prioritized as a preferred source for legitimate future attachment lookups, and — combined with any other weakness allowing it to eventually supply a hash-matching-looking response or simply degrade honest peers' relative standing — steer BNS resolution toward itself. This matches the High-severity category of "attachment/BNS mismatch" / steering resolution to a malicious source. This does not itself write invalid data (the DB-level hash check in `run()` still filters out mismatched attachments from being stored), so the concrete damage is reliability-score manipulation and unfair source prioritization rather than storage of forged content.

### Likelihood Explanation
Trivial and remotely reachable: any peer already selected as an outbound sync peer with a reachable data URL can respond to `AttachmentRequest`s. No secret, admin role, or special access is required — just running a peer that gets included in `network.get_outbound_sync_peers()`/has a `get_data_url` entry [6](#0-5) . The attacker only needs to return well-formed (JSON-decodable) `Attachment` bodies for every attachment GET request it receives, which is essentially free computationally, and can be repeated indefinitely for every batch cycle.

### Recommendation
In `extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compute `response.attachment.hash()` and compare it to `request.content_hash` before calling `report.bump_successful_requests()`; treat a mismatch the same as a failed request (`report.bump_failed_requests()`) and do not insert the attachment into `self.attachments`.

### Proof of Concept
Rust test plan in `stackslib/src/net/atlas/download.rs` (or a new test module) that:
1. Constructs an `AttachmentsBatchStateContext` with one peer and one `AttachmentRequest` whose `content_hash` is `H_expected`.
2. Builds a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains that peer/request paired with a `StacksHttpResponse` encoding a well-formed `Attachment` whose actual content bytes hash to `H_bogus != H_expected`.
3. Calls `context.extend_with_attachments(&mut results)`.
4. Asserts `context.peers[&peer_url].score()` increased (showing `bump_successful_requests` fired) despite `H_bogus != H_expected`, proving the missing hash-equality guard.
