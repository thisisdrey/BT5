## Analog Found: Unauthenticated `RecvError` Packets Trigger Privileged Tunnel Teardown

### Title
Missing Authentication on `RecvError` Handling Allows Unauthenticated Remote Teardown of Active Tunnels - (File: `outside.go`)

### Summary
The external report describes smart-contract functions that perform a privileged state change (releasing tokens) with no access-control check, so "anyone" can call them, when the documented design required admin-only access. The closest reachable analog in this codebase is `header.RecvError` handling: it is dispatched from the unauthenticated branch of packet processing, before any AEAD/certificate verification, and it performs a privileged operation — tearing down an established, authenticated tunnel and deleting handshake state — gated only by a spoofable source-address comparison rather than any cryptographic proof of identity.

### Finding Description
In `readOutsidePackets`, incoming packets are first parsed and dispatched by header type. `header.RecvError` is handled in the same unencrypted branch as `header.Handshake`, i.e. before any per-packet AEAD decryption or certificate check is performed: [1](#0-0) 

The handler itself, `handleRecvError`, looks up the hostinfo purely by the numeric `RemoteIndex` carried in the (unauthenticated) header, and its only defense against forgery is comparing the packet's source `netip.AddrPort` to the hostinfo's currently known remote address: [2](#0-1) 

If that comparison passes (or if the hostinfo has no remote address recorded yet), `f.closeTunnel(hostinfo)` and `hm.DeleteHostInfo(hostinfo)` are invoked unconditionally — no cryptographic proof that the sender possesses the session keys or a CA-signed certificate for that tunnel is required. `RemoteIndex` is only a 32-bit locally-chosen value carried on the wire, and UDP allows blind source-address spoofing, so an attacker who can spoof the victim's peer's `ip:port` and guess/observe a live `RemoteIndex` can invoke this teardown path without ever completing a handshake or holding a valid certificate.

The other reachable state-changing message types (`header.CloseTunnel`, `header.Control` for relay creation, `header.LightHouse` updates, `header.Message`) are all processed only *after* `hostinfo.ConnectionState.Decrypt` succeeds, meaning they require possession of the session's authenticated encryption key, which is only established through a certificate-authenticated Noise handshake. `RecvError` is the one operational message type that bypasses that authentication layer entirely.

### Impact Explanation
Successful exploitation lets a remote, uncertified attacker who can spoof UDP source `ip:port` values force any Nebula node to tear down and delete its record of an active tunnel to a peer. This is a remote state-poisoning / denial-of-service impact: an attacker can repeatedly kill legitimate authenticated tunnels between two nebula nodes without ever presenting a valid certificate or completing a Noise handshake, undermining tunnel availability guarantees that are otherwise protected by certificate-based authentication.

### Likelihood Explanation
Exploitability depends on network position: the attacker must be able to spoof the victim's peer's `udpAddr` (or find a peer's `HostInfo` that has no remote address recorded yet) and must know or guess the target's 32-bit `RemoteIndex`. There is already a config knob, `acceptRecvErrorConfig.ShouldRecvError` (`listen.accept_recv_error`/`send_recv_error`), documented in the project's own `CHANGELOG.md` as a mitigation for the fact that `recv_error` "can expose the fact that Nebula is running on a host" and can be spoofed: [3](#0-2) 

This indicates the maintainers are aware `RecvError` is unauthenticated and have provided a config-level mitigation (defaulting to accepting it, per the more recent changelog entry), rather than a cryptographic access-control fix analogous to the `onlyRole(ADMIN_ROLE)` remediation in the external report.

### Recommendation
Require some additional authenticated signal before honoring a `RecvError`-triggered teardown — e.g., only accept it if it directly follows an unanswered packet actually sent within a bounded recent window (already partially true via `ShouldRecvError`), and continue to keep `accept_recv_error` disabled by default in higher-security deployments; consider treating `RecvError` purely as a hint to trigger a re-handshake probe rather than an unconditional `closeTunnel`+`DeleteHostInfo`.

### Proof of Concept
1. Observe or infer a victim node A's live tunnel to peer B, including B's `RemoteIndex` on A (observable if on-path, or via repeated probing since the field is only 32 bits).
2. Craft a bare `header.RecvError` packet (no payload, no AEAD) with that `RemoteIndex`, and send it to A with a spoofed source `ip:port` matching B's currently known address (or targeting a hostinfo state with no remote set yet).
3. If `f.acceptRecvErrorConfig.ShouldRecvError` allows it (default-permissive per `CHANGELOG.md`), A calls `closeTunnel` and `DeleteHostInfo` for the B tunnel, tearing down the live session without B or the attacker ever presenting a valid certificate.

```go
func (f *Interface) handleRecvError(addr netip.AddrPort, h *header.H) {
	if !f.acceptRecvErrorConfig.ShouldRecvError(addr) {
		f.l.Debug("Recv error received, ignoring",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
		return
	}

	if f.l.Enabled(context.Background(), slog.LevelDebug) {
		f.l.Debug("Recv error received",
			"index", h.RemoteIndex,
			"udpAddr", addr,
		)
	}

	hostinfo := f.hostMap.QueryReverseIndex(h.RemoteIndex)
	if hostinfo == nil {
		f.l.Debug("Did not find remote index in main hostmap", "remoteIndex", h.RemoteIndex)
		return
	}

	hr := hostinfo.GetRemote()
	if hr.IsValid() && hr != addr {
		f.l.Info("Someone spoofing recv_errors?",
			"addr", addr,
			"hostinfoRemote", hr,
		)
		return
	}

	f.closeTunnel(hostinfo)
	// We also delete it from pending hostmap to allow for fast reconnect.
	f.handshakeManager.DeleteHostInfo(hostinfo)
}
```
