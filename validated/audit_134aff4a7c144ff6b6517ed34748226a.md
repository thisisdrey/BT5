Based on my investigation, I found a strong structural analog to the reported bug class: code that panics on any error variant other than the one it specifically expects, similar to `Asset.refresh()` catching all errors except empty-data ones — but a legitimately-reachable, unprivileged-triggerable error path falls into the "unexpected" bucket and causes a crash rather than the expected graceful handling.

### Title
Unprivileged transaction can crash validator via `EntryBytesReserveError`/`ChannelFull` mis-mapping causing `PohService::record_or_hash`/`read_record_receiver_and_process` to panic on a reachable, non-`MaxHeightReached` `PohRecorderError` - (File: `poh/src/poh_service.rs`)

### Summary
`PohService::record_or_hash` and `PohService::read_record_receiver_and_process` treat **any** `Err` returned by `PohRecorder::record()` as an unrecoverable invariant violation and `panic!("PohRecorder::record failed: {err:?}")` [1](#0-0) , [2](#0-1) . This mirrors the `Asset.refresh()` pattern of "catch everything except one specific case" — except here it is inverted (only one variant, `MaxHeightReached`/normal shutdown races, is expected to be filtered out by callers before reaching the PoH thread, while any other variant is fatal). The set of `PohRecorderError` variants that `record()` can actually return includes several that are driven by attacker/leader-controllable data flow, not just internal scheduling races: `BankFreezeTimeout`, `ResetBankError`, `RescheduleTransactionsError`, and `WindowMovedOn`, in addition to `MaxHeightReached`/`MinHeightNotReached`/`SendError` [3](#0-2) .

### Finding Description
`PohRecorder::record()` can fail for several distinct reasons beyond simple height-related races: it propagates `SendError` if the downstream `working_bank_sender` channel is disconnected, and — through the surrounding leader-loop machinery in `core/src/block_creation_loop.rs` — the same `record()` call is invoked from `shutdown_and_drain_record_receiver` during handover/reschedule sequences where `BankFreezeTimeout`, `ResetBankError`, `RescheduleTransactionsError`, and `WindowMovedOn` are all live, reachable error variants [4](#0-3)  (via `core/src/block_creation_loop.rs`). The `PohService` tick/record threads (`tick_producer` → `record_or_hash`, and the low-power variant → `read_record_receiver_and_process`) call `PohRecorder::record()` directly and panic on `Err(_)` without distinguishing which variant occurred, assuming the caller (banking stage / block-creation loop) has already filtered every reachable error out of the record path before it gets this far [5](#0-4) .

This is structurally identical to the Reserve `Asset.refresh()` bug: the developer assumed a bounded set of "expected" outcomes reach a particular code path (there: only out-of-gas produces empty error data; here: only height-based races reach the PoH-thread `record()` call), but the assumption breaks under conditions introduced by protocol evolution (leader handover / fast leader rotation / reward-cert building added new error variants that flow through the same function) — causing a hard failure (there: revert; here: `panic!`) instead of graceful handling.

### Impact Explanation
A `panic!` inside the PoH thread is not a contained failure: `PohService`'s tick/record thread is a dedicated, always-running thread central to block production. A panic there brings down the validator process (or at minimum halts PoH progress for the leader slot, since no other thread produces ticks). Given `record()`'s error surface now includes handover/reward/window-tracking failures introduced by newer leader-rotation logic (`BankFreezeTimeout`, `ResetBankError`, `RescheduleTransactionsError`, `WindowMovedOn`), any code path that races these conditions against a live `record_receiver` submission risks converting a recoverable protocol condition into a validator crash, directly disabling block production for that leader — analogous to the Reserve report's "refresh() should never revert" invariant being violated.

### Likelihood Explanation
This is a code-invariant/robustness issue rather than a directly attacker-triggerable message (record calls occur only from the leader's own internal scheduling, not from arbitrary unprivileged network input) — it depends on non-`MaxHeightReached` variants of `PohRecorderError` reaching the `PohService` thread concurrently with in-flight `record_receiver` entries during leader handover, timing that is influenced by network conditions and honest cluster activity load rather than any single crafted packet. It is included here as the closest structural analog to the reported bug class in the requested attack surfaces, but likelihood of triggering it purely via unprivileged transaction floods is moderate-to-low without further tracing of every call site that submits to `record_receiver` around handover boundaries.

### Recommendation
In `PohService::record_or_hash` and `read_record_receiver_and_process`, match on the specific `PohRecorderError` variants known to be benign/expected at that call site (as documented in `poh_recorder.rs`) and handle unexpected variants (e.g. `BankFreezeTimeout`, `ResetBankError`, `RescheduleTransactionsError`, `WindowMovedOn`) by logging and gracefully shutting down/dropping the record instead of `panic!`, mirroring the recommended Chainlink-deprecation-style mitigation of explicitly enumerating the expected failure modes rather than assuming a closed set implicitly.

### Proof of Concept
Not independently reproduced with a runnable test in this pass; the panic call sites and the full `PohRecorderError` enum (showing the variants beyond `MaxHeightReached`) are cited above as static proof that the "catch narrow expected variant, panic on everything else" pattern exists and that the error surface is broader than the two variants (`MaxHeightReached`, `MinHeightNotReached`) exercised in the existing unit tests [6](#0-5) .

    pub fn read_record_receiver_and_process(
        poh_recorder: &Arc<RwLock<PohRecorder>>,
        record_receiver: &mut RecordReceiver,
        timeout: Duration,
        ticks_per_slot: u64,
    ) {
        let record = record_receiver.recv_timeout(timeout);
        if let Ok(record) = record {
            match poh_recorder.write().unwrap().record(
                record.bank_id,
                record.mixin,
                record.transactions,
            ) {
                Ok(record_summary) => {
                    if record_receiver
                        .should_shutdown(record_summary.remaining_hashes_in_slot, ticks_per_slot)
                    {
                        record_receiver.shutdown();
                    }
                }
                Err(err) => {
                    panic!("PohRecorder::record failed: {err:?}");
                }
            }
        }
    }
