### Title
Fixed-size shared thread pool + unbounded `future.get()` in shielded TRC20 zk-SNARK precompile enables CPU/queue exhaustion DoS - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `VerifyTransferProof` precompiled contract (invoked from TVM when a shielded-TRC20 CALL reaches the Sapling `verifyTransferProof` address) submits up to 5 expensive native zk-SNARK verification tasks (`SaplingCheckSpendTask`, `SaplingCheckOutputTask`, `SaplingCheckBingdingSig`) per invocation into one of two **statically shared, fixed-size (5-thread)** executor pools — `workersInConstantCall` / `workersInNonConstantCall` — that are shared across **all concurrent invocations from all callers on the node**, with an unbounded backing queue and no per-caller/global admission control. [1](#0-0) 

### Finding Description
`execute()` parses attacker-supplied calldata (only size/offset sanity checks are performed, no proof validity is required to reach task submission), then submits up to `spendCount + receiveCount + 1` (max 5) native cryptographic verification jobs to a shared `ExecutorService` with exactly 5 threads: [2](#0-1) 

After submission, the calling thread does `countDownLatch.await(timeout)` and then **unconditionally** calls `future.get()` on every submitted future with no timeout: [3](#0-2) 

Because the pool is process-wide and fixed at 5 threads (not scaled to the number of concurrent callers), any number of concurrent invocations of this precompile — from concurrent `eth_call` / `triggerConstantContract` API requests (`workersInConstantCall`) or from concurrently-validated broadcast transactions (`workersInNonConstantCall`) — queue behind each other on the same 5 threads. Each task performs a computationally heavy native zk-SNARK check (`librustzcashSaplingCheckSpendNew`, `librustzcashSaplingCheckOutput`, `librustzcashSaplingFinalCheck`) that can dominate CPU. Since the executor uses an unbounded queue, submission never fails/rejects — it just queues indefinitely — and the calling thread then blocks in the unconditional `future.get()` regardless of whether the earlier `countDownLatch.await` timed out. This is a concurrency/back-pressure defect (the CVE's "race condition" bug class maps here to unsynchronized shared-resource contention across concurrent execution paths) that produces unbounded latency growth and CPU starvation under concurrent load, rather than a crash — but it can render the node unresponsive.

The reachable path: any anonymous API client can call `wallet/triggercontract` (constant call) or `eth_call` targeting the shielded TRC20 contract that performs a `CALL` to the Sapling `verifyTransferProof` precompile address, without needing valid proofs, valid signatures, or any TRX cost (constant calls consume no fee/bandwidth in the broadcast sense and are commonly rate-limited only loosely). [4](#0-3) 

### Impact Explanation
Sustained concurrent calls into this precompile from many anonymous JSON-RPC/HTTP clients can saturate the 5-thread `workersInConstantCall` pool with expensive native crypto work and grow its internal queue without bound, starving legitimate `eth_call`/`triggerConstantContract` requests and any real shielded-transfer verification (broadcast path) of CPU and worker threads. Because `pushTransaction` in `Manager` processes transactions serially under `synchronized(transactionLock)`/`synchronized(this)`, if a broadcast shielded transaction's precompile call is delayed behind a queue saturated by constant-call floods, this serialized lock is held for the duration, backing up all subsequent transaction broadcast/validation on the node — a node-level liveness degradation/DoS matching the "resource exhaustion / node unresponsive" impact category, without requiring any privileged role.

### Likelihood Explanation
High reachability, moderate exploit cost: the attacker needs no funds, valid keys, or valid zk-proof data — only correctly-sized calldata to pass the length/offset checks and reach task submission (`spendCount`/`receiveCount` between 1–2, matching sizes in `SIZE`). Firing many concurrent `eth_call`/`triggerConstantContract` requests against a public full node's HTTP/gRPC API is trivial for any anonymous client, and the fixed pool size (5) is small relative to typical node request concurrency.

### Recommendation
- Scale or bound the executor pools relative to expected concurrent load, or use a bounded queue with rejection (`RejectedExecutionHandler`) instead of the default unbounded queue.
- Apply a hard timeout to `future.get()` consistent with the `countDownLatch.await` timeout, and cancel/fail-fast on timeout instead of blocking indefinitely.
- Rate-limit or throttle per-client precompile/CALL invocations that reach zk-SNARK verification precompiles, especially via the constant-call (`eth_call`/`triggerConstantContract`) path, and consider charging energy for the actual verification cost up front rather than a flat `getEnergyForData` value that doesn't scale for constant calls (which bypass normal energy accounting).
- Add monitoring/backpressure metrics on `workersInConstantCall`/`workersInNonConstantCall` queue depth to detect and mitigate abuse in production.

### Proof of Concept
1. From any node's public JSON-RPC/HTTP API, prepare calldata of length matching `VerifyTransferProof.SIZE` (2080/2368/2464/2752 bytes) with `spendCount`/`spendAuthSigCount`/`receiveCount` fields set to valid ranges (1–2) and non-duplicate nullifier/commitment placeholder bytes — no valid zk-proof is required to reach the task-submission stage.
2. Repeatedly and concurrently invoke `triggerConstantContract` (or `eth_call`) against a contract address performing a `CALL` to the Sapling `verifyTransferProof` precompile with this calldata, from many concurrent client connections (e.g., tens to hundreds of parallel requests).
3. Observe growing latency/backlog on `workersInConstantCall`'s internal task queue and CPU saturation from concurrent native `librustzcash*` calls; concurrently issue legitimate `eth_call`/`triggerConstantContract`/shielded-transfer broadcast requests and observe severely degraded response times or timeouts, demonstrating the shared, unbounded, fixed-size pool as the bottleneck.
4. (Verification note: exact numeric impact — e.g., whether default pool/queue configuration allows practical exhaustion at typical node hardware — was not empirically measured here and would need load testing against a running node to quantify severity precisely.)
