### Title
TRC10 Exchange bonding-curve swap amount relies on non-deterministic, unpatched floating-point `Math.pow` calculations — allowing precision-bias extraction from Exchange pools - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The TRC10 `Exchange` (Bancor-style AMM) swap output is computed by `ExchangeProcessor.exchange()` using double-precision `Math.pow`/`StrictMath.pow` on the pool's live `firstTokenBalance`/`secondTokenBalance` state [1](#0-0) . This is the same bug class as the vETH report: an on-chain "price" (swap output) that is derived from a floating-point/implementation-dependent formula operating on manipulable/attacker-chosen inputs, with no independent sanity bound on the result.

### Finding Description
`ExchangeCapsule.transaction()` picks between the legacy `ExchangeProcessor` (double-based `Maths.pow`) and the newer `SafeExchangeProcessor` (BigDecimal-based) depending on the `allowHardenExchangeCalculation` chain parameter [2](#0-1) . The non-hardened path is reachable by any account through `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator`, i.e. from an ordinary signed transaction, whenever the SR-activated hardening proposal has not (yet) been enabled for a given chain/network [3](#0-2) .

Critically, `MathWrapper.pow()` — the non-strict implementation used by `ExchangeProcessor` when `useStrictMath=false` — contains a hardcoded lookup table of specific IEEE-754 bit patterns mapped to "corrected" results, annotated with mainnet block numbers [4](#0-3) . This is strong evidence that `Math.pow`'s platform-dependent, non-strict floating-point results have historically diverged from the intended/consensus value on real mainnet transactions, and the fix applied was a case-by-case patch table rather than a structural fix. Any new `(a, b)` input pair not already in that table can still produce a `pow()` result that differs from the deterministic/"correct" value that `SafeExchangeProcessor`'s BigDecimal path would produce — this is exactly the "vulnerable price dependency" pattern in the report: a swap-price function whose output can be steered away from its true value by choosing the input (attacker fully controls `sellTokenQuant`, and can inject/withdraw to influence pool balances first via `ExchangeInjectActuator`/`ExchangeWithdrawActuator`).

### Impact Explanation
If an attacker can find (or has already found, given the historic patch list) an input triplet `(sellTokenBalance, buyTokenBalance, sellTokenQuant)` for which `Maths.pow` diverges favorably from the true bonding-curve value, `ExchangeCapsule.transaction()` will mint/return more `buyTokenQuant` than the invariant allows, directly draining TRX/TRC10 value from the Exchange pool — an unbacked-balance / theft-of-funds condition reachable by a single unprivileged `ExchangeTransactionContract` transaction.

### Likelihood Explanation
Exploitability is gated entirely by whether `allowHardenExchangeCalculation` is active on the target network; on any deployment where this proposal has not been activated (or on networks/testnets that never activate it), the vulnerable `ExchangeProcessor` path remains live and reachable from ordinary transactions by any account holding TRX/TRC10 balances and knowledge of the Exchange bonding-curve math — no special privilege is required, only the ability to craft specific numeric inputs, similar to how the vETH attacker crafted a specific BIF amount to bias the vulnerable factory's price computation.

### Recommendation
Enforce `SafeExchangeProcessor` (BigDecimal-based) unconditionally for all TRC10 Exchange calculations, removing the non-hardened floating-point path entirely rather than gating it behind an activatable proposal; alternatively, add invariant checks (e.g., k-invariant / product-non-decreasing checks) in `ExchangeCapsule.transaction()` that reject any computed `buyTokenQuant` inconsistent with the exact rational bonding-curve formula, regardless of which processor computed it.

### Proof of Concept
Not fully reproducible from available context — verifying an actual precision-divergent `(balance, quant)` triple requires exhaustive search or access to the exact historical mainnet incident data referenced by the hardcoded values in `MathWrapper.java` [5](#0-4) ; the existing test `ExchangeProcessorTest.testStrictMath` demonstrates that non-hardened and strict/hardened results differ (`assertNotEquals`) for a large set of real balance/quant combinations [6](#0-5) , confirming the divergence exists broadly, though whether any given divergence is profitable to an attacker (rather than merely a rounding discrepancy) was not verified here.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
