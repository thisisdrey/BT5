### Title
Global per-block message cap in Snowbridge outbound queues allows cheap DoS of Ethereum-bound bridge messages - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
`snowbridge-pallet-outbound-queue-v2` (and the v1 equivalent) enforces a single, chain-wide cap, `MaxMessagesPerBlock`, on how many messages can be committed for delivery to Ethereum in a block [1](#0-0) . This is structurally identical to the LevelMinting per-block mint/redemption cap: a shared, block-scoped ceiling that is cheap to fill and, once filled, causes every other participant's operation for that block to be rejected/postponed. Any origin able to route an XCM through the bridge exporter can keep re-submitting messages every block for the price of ordinary parachain/XCM fees, repeatedly saturating the cap and starving legitimate deposit/withdrawal-style bridge traffic (asset transfers to Ethereum) from ever being committed, mirroring the report's "innocent users encounter a revert" DoS pattern but manifesting as indefinite `Yield`/postponement of bridged transfers.

### Finding Description
`do_process_message` checks the *global* `MessageLeaves` length against `T::MaxMessagesPerBlock` before accepting any message into that block's commitment: [1](#0-0) 

This cap is configured at `ConstU32<32>` in the Westend Bridge Hub runtime for both v1 and v2 outbound queues: [2](#0-1) 

The v2 `SendMessage::validate`/`deliver` path performs no fee assessment, quota, or per-account rate limiting before enqueuing into the shared `MessageQueue`: [3](#0-2) 

The associated `ExportXcm::validate` for v2 even returns `Assets::default()` for the delivery fee at the router level, i.e., no local delivery-cost is deducted at this stage; per-message pricing is instead embedded inside the XCM program by the user agent (via `PayFees`/remote fee assets) rather than enforced by the queue itself as a deterrent against volume: [4](#0-3) 

Because the check in `do_process_message` is over the total `MessageLeaves` count (not per-origin/per-queue), any actor capable of getting 32 messages processed first in a block (which only costs ordinary transaction/weight fees, not a bridge-specific deterrent fee) causes `Yield` for every message that arrives afterward in that same block, and this can be repeated block after block: [5](#0-4) 

### Impact Explanation
This matches the "public underpriced work that degrades block production or stalls bridge processing" impact category explicitly named in scope. A low-cost, unprivileged actor can keep the outbound bridge commitment saturated every block, causing legitimate Ethereum-bound transfers (asset withdrawals from Polkadot to Ethereum) to be perpetually deferred via `ProcessMessageError::Yield`, denying service to bridge users without needing any privileged role, malicious relayer, or validator collusion.

### Likelihood Explanation
Likelihood is bounded by how cheaply and repeatably the cap can be filled. The v1 queue does compute a real per-message fee (`calculate_fee`, covering local weight plus a `remote` gas/reward component) which raises the cost of flooding [6](#0-5) . The v2 queue does not enforce an equivalent floor at the exporter/queue level, relying instead on the sender's self-declared `PayFees` amounts inside the XCM program, which weakens the built-in economic deterrent that exists in v1. Realizing the DoS still requires being able to originate valid, routable XCM through Asset Hub with minimal remote fees repeatedly, which is feasible for any funded account but not free, so this should be treated as a lower-cost-than-intended griefing vector rather than a zero-cost one.

### Recommendation
Introduce a per-origin or per-block-per-origin sub-limit within `MaxMessagesPerBlock` accounting (e.g., reserve a fraction of the cap for round-robin fairness across distinct source locations/channels) and/or enforce a minimum, protocol-level per-message local fee in `snowbridge-pallet-outbound-queue-v2::send_message_impl` (mirroring `calculate_fee` in v1) so that filling the cap has a real, scaling cost, consistent with the report's recommendation to impose a fee on deposit/withdrawal-equivalent operations to deter cap-exhaustion attacks.

### Proof of Concept
1. An account with minimal funds submits, from Asset Hub, 32 (or `MaxMessagesPerBlock`) validly-routable `InitiateTransfer`/bridge XCM messages targeting Ethereum in a single block, each with the minimum acceptable `PayFees`/remote fee amount permitted by validation.
2. `do_process_message` accepts each until `MessageLeaves` length reaches `T::MaxMessagesPerBlock` [1](#0-0) ; any legitimate user's Ethereum-bound message enqueued afterward in that block receives `ProcessMessageError::Yield` and is postponed.
3. The attacker repeats step 1 every subsequent block (each repetition costs only ordinary weight/XCM fees, not a bridge-specific throttle), so the honest user's message is perpetually pushed behind newly-flooded messages, denying timely bridge delivery to Ethereum.
