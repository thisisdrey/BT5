### Title
Order-Book Griefing DoS via `MAX_MATCH_NUM` Revert in `MarketSellAssetActuator.matchOrder()` - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` enforces two independent, inconsistent caps: a per-account cap on open orders (`MAX_ACTIVE_ORDER_NUM = 100`, checked in `validate()`) and a global per-price-level match cap (`MAX_MATCH_NUM = 20`, enforced only during `execute()`'s `matchOrder()`). Because the per-account cap allows any single account to place up to 100 tiny orders at the exact same best price for a token pair, and the match cap aborts the *entire* transaction with `ContractExeException("Too many matches...")` once more than 20 maker orders exist at that price, an attacker can cheaply fragment liquidity at the best price of any market pair to force every subsequent taker's `MarketSellAssetContract` to revert.

### Finding Description
`MarketSellAssetActuator.validate()` only checks that the caller's *own* resting-order count is below `MAX_ACTIVE_ORDER_NUM` (100): [1](#0-0) 

This limit is per-`MarketAccountOrderCapsule` (per owner address), not per price level, so nothing prevents an attacker from placing dozens of minimal-size sell orders at the exact same price to build a deep queue at the head of the order book for a given token pair, as confirmed by the linked-list order structure in `MarketOrderIdListCapsule`: [2](#0-1) 

When any other user later submits a matching taker order, `matchOrder()` walks the maker orders at the best price and increments `matchOrderCount`; once it exceeds `MAX_MATCH_NUM` (20) it throws, which is only reachable from `execute()` (post-validation), so the whole transaction fails and is charged the market fee: [3](#0-2) 

The test `exceedMaxMatchNumLimit` demonstrates this exact revert path when more than `MAX_MATCH_NUM` maker orders exist at a matching price: [4](#0-3) 

The inconsistency mirrors the OpenQ bug class: one limit (`MAX_ACTIVE_ORDER_NUM`, per-account) governs how many orders a single malicious actor can create, while a second, unrelated limit (`MAX_MATCH_NUM`, per matching operation) governs whether *other users'* transactions succeed. An attacker only needs to reach the first limit (cheaply, using minimal token quantities) to make the second limit permanently trip for any victim trying to trade at/through that price on that pair.

### Impact Explanation
Any account (unprivileged) can permanently deny other users the ability to execute market orders against a specific TRC10 token pair at a given price level by fragmenting up to 100 tiny orders there, since matching more than 20 sub-orders at the best price aborts the taker's entire transaction (fee still charged, no partial fill possible until the maker orders are cancelled or fully matched in ≤20-order batches). This is a availability/DoS impact on the Market/Exchange feature reachable from a single signed `MarketSellAssetContract` transaction, without needing any special privilege — matching the "API the node can no longer serve" / denial-of-legitimate-operation class of impact for the affected pair.

### Likelihood Explanation
Likelihood is high: placing up to 100 minimal-quantity sell orders at the same price is cheap (bounded only by `MarketSellFee` per order and minimal token amounts), requires no special permissions, and the resulting condition persists until the attacker (or someone) removes/consumes the orders in small enough batches. Any subsequent taker transaction that would need to walk through more than 20 of these orders is guaranteed to revert.

### Recommendation
Make the two limits consistent: either (a) allow partial matching up to `MAX_MATCH_NUM` per invocation and let the taker's remaining quantity roll over/queue instead of throwing and reverting the whole transaction, or (b) cap the number of maker orders that can exist at a single price point (independent of per-account count) so that the match-count cap can never be exceeded by construction, or (c) enforce `MAX_MATCH_NUM` as a soft stop that finalizes partial fills for successfully matched orders rather than throwing `ContractExeException` for the whole transaction.

### Proof of Concept
1. Attacker account funds itself with a minimal amount of `TOKEN_ID_ONE` and `TOKEN_ID_TWO`-equivalent balance.
2. Attacker submits 21 `MarketSellAssetContract` transactions selling `TOKEN_ID_ONE` for `TOKEN_ID_TWO` at the identical price (e.g., sell quantity `X`, buy quantity `Y`, same ratio), each transaction succeeding under `MAX_ACTIVE_ORDER_NUM = 100` validation.
3. A victim submits a `MarketSellAssetContract` selling `TOKEN_ID_TWO` for `TOKEN_ID_ONE` with quantity large enough that `matchOrder()` must traverse more than 20 of the attacker's orders at that price.
4. `matchOrder()` throws `ContractValidateException`/`ContractExeException("Too many matches. MAX_MATCH_NUM = 20")` inside `execute()`, as reproduced by the existing unit test `exceedMaxMatchNumLimit` in `MarketSellAssetActuatorTest.java` (lines 1825-1873), causing the victim's transaction to fail while still being charged the market fee, and blocking normal trading at that price for that pair until the attacker's fragmented orders are cleared.

  @Test
  public void exceedMaxMatchNumLimit() throws Exception {

    InitAsset();

    int start = 10;
    int limit = MarketSellAssetActuator.getMAX_MATCH_NUM();
    int step = 1;
    int end = start + step * limit;

    //(sell id_1  and buy id_2)
    String sellTokenId = TOKEN_ID_ONE;
    String buyTokenId = TOKEN_ID_TWO;
    long buyTokenQuant = 400L;
    long sellTokenQuant = buyTokenQuant * (end / start + 1);

    byte[] ownerAddress = ByteArray.fromHexString(OWNER_ADDRESS_FIRST);
    AccountCapsule accountCapsule = dbManager.getAccountStore().get(ownerAddress);
    accountCapsule.addAssetAmountV2(sellTokenId.getBytes(), sellTokenQuant,
        dbManager.getDynamicPropertiesStore(), dbManager.getAssetIssueStore());
    dbManager.getAccountStore().put(ownerAddress, accountCapsule);
    Assert.assertEquals(sellTokenQuant,
            (long) accountCapsule.getAssetV2MapForTest().get(sellTokenId));

    // Initialize the order book

    // at least limit+1 times
    for (int i = start; i <= end; i += step) {
      addOrder(buyTokenId, (long) start, sellTokenId, i, OWNER_ADDRESS_SECOND);
    }

    // this order(taker) need to match 21 times
    MarketSellAssetActuator actuator = new MarketSellAssetActuator();
    actuator.setChainBaseManager(dbManager.getChainBaseManager()).setAny(getContract(
        OWNER_ADDRESS_FIRST, sellTokenId, sellTokenQuant, buyTokenId, buyTokenQuant));

    String errorMessage =
        "Too many matches. MAX_MATCH_NUM = " + MarketSellAssetActuator.getMAX_MATCH_NUM();
    try {
      TransactionResultCapsule ret = new TransactionResultCapsule();
      actuator.validate();
      actuator.execute(ret);
      fail(errorMessage);
    } catch (ContractExeException e) {
      Assert.assertEquals(errorMessage, e.getMessage());
    } catch (Exception e) {
      Assert.assertTrue(false);
    }
  }
