### Title
Heap-buffer over-read in `InputZipFile::ProcessCentralDirEntry` due to missing bounds checks on attacker-controlled ZIP field lengths - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` parses the ZIP central directory header (file name length, extra field length, ZIP64 extra-field sub-record sizes) and advances/dereferences the input cursor `p`/`extra_p` based entirely on attacker-controlled 16/32-bit length fields, with **no call to `EnsureRemaining()`** — unlike the sibling function `InputZipFile::ProcessLocalFileEntry`, which explicitly bounds-checks every field it reads before advancing `p`. A crafted `.jar`/`.zip` (e.g., a dependency archive processed by the `ijar`/`zipper` tooling) can declare oversized `file_name_length`, `extra_field_length`, or a ZIP64 extra-field `data_size` that exceeds the actual mapped file region, causing reads past the end of the memory-mapped input buffer.

### Finding Description
`ProcessCentralDirEntry` (`third_party/ijar/zip.cc:493-545`) reads the central directory header fields directly from the mmap'd buffer: [1](#0-0) 

and then walks the extra-field records using an attacker-supplied `data_size` with no check that `extra_p + data_size` stays within `extra_field_length` or the mapped file length: [2](#0-1) 

Contrast this with `ProcessLocalFileEntry`, which validates every field against remaining input via `EnsureRemaining()` before consuming it: [3](#0-2) 

`ProcessCentralDirEntry` has no equivalent guard anywhere in its body — `p += 16`, `get_u4le/get_u2le` reads, `memcpy(filename, p, len)`, `p += file_name_length`, `p += extra_field_length`, and the extra-field `while (extra_p != p)` loop that dereferences `get_u8le(extra)` for ZIP64 fields are all performed without verifying that the declared lengths fit inside the actual input buffer (`zipdata_in_` to `zipdata_in_ + input_file_->Length()`).

### Impact Explanation
A malicious ZIP/JAR file with a corrupted central directory entry (oversized `file_name_length`, `extra_field_length`, or ZIP64 `data_size`) causes the `ijar`/`zipper` tooling to read past the bounds of the memory-mapped input file. This can crash the process (denial of build) or, on platforms/build configurations where the read touches adjacent process memory rather than an unmapped page, leak adjacent heap/mmap contents into `filename`/parsed size fields that later influence control flow (e.g., `ProcessFile`/`ProcessNext` decisions), matching the class of the referenced CVE (unchecked length field driving an out-of-bounds heap access in a native parser).

### Likelihood Explanation
`ijar`/the `zipper` binary is invoked on ZIP/JAR content that ultimately originates from dependencies (e.g., pre-built jars supplied through `http_archive`/`http_jar`/`http_file`, or archives referenced by `java_import`). While an integrity checksum on the download may pin the exact bytes an attacker publishes, that checksum only proves byte-for-byte equality with what was declared — it does nothing to validate the internal ZIP structure. An attacker who controls the origin of such an archive (the CVE's "unprivileged origin server" analog) can craft the bytes so they still match the pinned digest while carrying a malformed central directory that triggers the OOB read once Bazel's own tooling parses it.

### Recommendation
Add the same `EnsureRemaining()`-style bounds validation used in `ProcessLocalFileEntry` to `ProcessCentralDirEntry`, validating `file_name_length`, `extra_field_length`, and each extra-field sub-record's `data_size` against the number of bytes actually remaining in `zipdata_in_` before advancing `p`/`extra_p` or dereferencing memory at those offsets.

### Proof of Concept
Construct a minimal ZIP file whose End-of-Central-Directory record points to a Central Directory Header where `file_name_length` (or the ZIP64 extra field's declared `data_size`) is set larger than the number of bytes actually remaining in the file (similar in spirit to the existing `CreateZipWithMalformedExtraField` helper used for extra-field fuzz testing): [4](#0-3) 

Feed this file to the `ijar`/`zipper` binary (`third_party/ijar/zip_main.cc`) via `ZipExtractor::Create(...)->ProcessAll()`, which invokes `ProcessCentralDirEntry`; run under AddressSanitizer to observe the out-of-bounds read when `p`/`extra_p` is advanced past `zipdata_in_ + input_file_->Length()`.
