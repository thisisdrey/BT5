### Title
Single-Tenant CPU/Memory Pressure Can Force a Node-Wide Halving of the Shared Adaptive Concurrency Limit, Denying Service to Unrelated Repositories - ([File: internal/limiter/adaptive_calculator.go])

### Summary
Gitaly's adaptive concurrency limiter uses a *single, shared* `AdaptiveLimit` object per RPC/limiter type (e.g. the `packObjects` limit built in `internal/cli/gitaly/serve.go`), whose value is fed to every per-key (`per repo`/`per IP`/`per user`) `keyedConcurrencyLimiter` inside `ConcurrencyLimiter` [1](#0-0) . The limit is recalibrated by `AdaptiveCalculator.calibrateLimits`, which polls **node/parent-cgroup-wide** CPU throttling, memory, and PSI conditions [2](#0-1)  and, on any single backoff event, multiplicatively halves the limit for *all* registered adaptive limits: `newLimit = floor(limit.Current() * BackoffFactor)` [3](#0-2) . Because the pressure signal is aggregated over the whole Gitaly process's parent cgroup rather than per-repository/per-key [4](#0-3) , any single ordinary user driving up CPU throttling or memory pressure on the node (e.g. via concurrent clones/fetches or pack-objects generation against a repository they control) collapses the concurrency budget for *every other repository and user* sharing that limiter, exactly mirroring the referenced report's bug class: a single actor manipulating a shared, aggregate utilization metric to worsen outcomes (fees/queueing) for all other unrelated participants.

### Finding Description
The `ConcurrencyLimiter` is instantiated once per RPC-type (e.g. `packObjectsLimiterAuthenticated`) with one `*AdaptiveLimit` shared across all `limitingKey`s (per-repo, or per-`RemoteIP/Repository/User` for pack-objects) [5](#0-4) . Resizing this shared limit resizes the semaphore for *every* currently-tracked key simultaneously through the `AfterUpdate` callback: `for _, keyedLimiter := range limiter.limitsByKey { ... semaphore.Resize(...) }` [6](#0-5) .

The trigger for resizing is entirely node-wide: `newCPUThrottlingCondition` fires when CPU throttling on the parent cgroup exceeds 50% of the poll interval [7](#0-6) , and `AdaptiveCalculator` treats a single such event as sufficient reason to halve every managed limit at the next 30-second calibration tick [8](#0-7) . Recovery is only additive (+1 per 30s) [9](#0-8) , so the AIMD asymmetry (instant 50% cut vs. slow linear recovery) means a small, cheap, and repeatable trigger produces an outsized and long-lasting reduction in capacity for the entire node.

An ordinary authenticated (or even unauthenticated, if `PackObjectsLimiting.Unauthenticated` is enabled) user reaches this path simply by issuing legitimate, unprivileged clone/fetch (`PostUploadPackWithSidechannel` → `packObjectsHook` → `runPackObjectsLimited`) traffic [10](#0-9)  against a repository they control, sized/parallelized to sustain CPU throttling on the shared parent cgroup. Because the watched cgroup is the Gitaly process's own parent cgroup, not a per-repository cgroup, the effect is not contained to the offending repository — it degrades the `packObjects`/`PostUploadPack` adaptive limit for all other repositories and tenants multiplexed on that Gitaly node.

### Impact Explanation
Once the shared adaptive limit is halved, unrelated clients cloning/fetching *other* repositories on the same node see their requests queued longer or rejected outright with `RESOURCE_EXHAUSTED` (`ErrMaxQueueSize`/`ErrMaxQueueTime`) [11](#0-10) . Because the attacking client's own repeated bursts can re-trigger the CPU-throttling condition roughly once per 30-second calibration window, the limit can be kept suppressed indefinitely while it only slowly grows back by +1 per interval, producing a sustained, low-cost denial-of-service against unrelated repositories/users hosted on a shared Gitaly node — the direct analog of the whale LP being able to keep utilization-driven fees elevated for everyone else at comparatively low, bounded cost to themselves.

### Likelihood Explanation
Reachable purely through standard, unprivileged git operations (clone/fetch of a repository the attacker controls or has read access to) — no special permissions, leaked tokens, or MITM position are required. The precondition is that `[adaptive_limiting]`/cgroups-based adaptive concurrency is enabled (a supported, documented production configuration, see `doc/backpressure.md` and `config.toml.example`), and that multiple repositories/tenants share the same Gitaly node's parent cgroup, which is the typical multi-tenant deployment model for Gitaly.

### Recommendation
- Scope the resource-pressure conditions and the resulting backoff decisions to the tenant/repository (or per-key) level where feasible, rather than applying a single node-wide backoff event to every key's shared `AdaptiveLimit`.
- Consider bounding how much collateral capacity reduction a single backoff event can cause across unrelated keys, e.g. applying the multiplicative decrease only to the limiter buckets whose in-flight requests correlate with the offending burden (as `BurdenMonitor`/`LoadShedder` already attempt to identify per-RPC/per-repo cost).
- Rate-limit or dampen how frequently a single condition source can re-trigger a full 50% cut (e.g. exponential backoff on the backoff-trigger frequency itself, not just the limit value) to reduce the asymmetry attackers can exploit between cheap repeated triggers and slow linear recovery.

### Proof of Concept
1. Deploy Gitaly with adaptive concurrency limiting enabled for `PostUploadPackWithSidechannel`/`packObjects` (per `doc/backpressure.md` / `AdaptiveLimiting` config), hosting multiple unrelated repositories/tenants on the same node.
2. As an ordinary authenticated user, repeatedly and concurrently clone/fetch a large repository you control (or one with pathological git history/pack generation cost) so that `git-pack-objects` sustains CPU usage high enough to cross the parent cgroup's CFS quota, producing CPU throttling.
3. Once `CPUThrottledDuration` delta over a poll interval exceeds the configured `cpu_throttled_threshold` (default 0.5) as evaluated in `internal/limiter/condition_cpu.go`, `AdaptiveCalculator.calibrateLimits` halves the shared `packObjects` `AdaptiveLimit` at the next 30s calibration tick.
4. Because this `AdaptiveLimit` is shared by every `limitingKey` inside `ConcurrencyLimiter.limitsByKey` (`internal/limiter/concurrency_limiter.go`), other clients cloning/fetching *unrelated* repositories on the same node observe reduced concurrency and increased `RESOURCE_EXHAUSTED` rejections, even though they generated no load themselves.
5. Repeating step 2 every ~30 seconds keeps the shared limit suppressed near its floor indefinitely, sustaining the denial of service to unrelated tenants at low, bounded cost to the attacker.

// NewConcurrencyLimiter creates a new concurrency rate limiter.
func NewConcurrencyLimiter(limit *AdaptiveLimit, maxQueueLength int, maxQueueWait time.Duration, monitor ConcurrencyMonitor) *ConcurrencyLimiter {
	if monitor == nil {
		monitor = NewNoopConcurrencyMonitor()
	}

	limiter := &ConcurrencyLimiter{
		limit:          limit,
		maxQueueLength: maxQueueLength,
		maxQueueWait:   maxQueueWait,
		monitor:        monitor,
		limitsByKey:    make(map[string]*keyedConcurrencyLimiter),
	}

	// When the capacity of the limiter is updated we also need to update the size of both the queuing tokens as
	// well as the concurrency tokens to match the new size.
	limit.AfterUpdate(func(val int) {
		for _, keyedLimiter := range limiter.limitsByKey {
			if keyedLimiter.queueTokens != nil {
				if semaphore, ok := keyedLimiter.queueTokens.(*resizableSemaphore); ok {
					semaphore.Resize(uint(val + limiter.maxQueueLength))
				}
			}
			if semaphore, ok := keyedLimiter.concurrencyTokens.(*resizableSemaphore); ok {
				semaphore.Resize(uint(val))
			}
		}
	})
	return limiter

// newCPUThrottlingCondition returns a Condition that evaluates to true when CPU throttling occurred for more than 50% of the
// time between the last 2 polls.
func newCPUThrottlingCondition(threshold float64) loadmonitor.Condition {
	if threshold <= 0.0 {
		threshold = defaultCPUThrottlingThreshold
	}

	return loadmonitor.Condition{
		Name: conditionCgroupCPU,
		Fn: func(ctx context.Context, previous, current loadmonitor.Stats, pollInterval time.Duration) (bool, string) {
			cur, prev := current.CGroup.ParentStats, previous.CGroup.ParentStats

			// Somehow, cgroup stats are reset. It's usually the consequence of cgroup limits being changed.
			// Alternatively, they can be overridden by another program.
			// Either way, the watcher should update the stats accordingly.
			if cur.CPUThrottledCount < prev.CPUThrottledCount || cur.CPUThrottledDuration < prev.CPUThrottledDuration {
				return false, ""
			}

			throttledDuration := cur.CPUThrottledDuration - prev.CPUThrottledDuration

			// If the total throttled duration since the last poll exceeds 50%.
			if pollInterval > 0 && throttledDuration/pollInterval.Seconds() > threshold {
				return true, eventCPUThrottling
			}
			return false, ""
		},
	}

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}
