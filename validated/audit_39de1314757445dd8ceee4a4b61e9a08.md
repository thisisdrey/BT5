### Title
Unbounded Per-Reference Hook Execution Enables Resource-Exhaustion DoS During `ReceivePack` - ([File: internal/gitaly/hook/update.go])

### Summary
Gitaly executes the Git `update` hook once for every reference contained in a single push, and each invocation spawns a fresh `gitaly-hooks` subprocess plus a gRPC round-trip into Gitaly's `HookService`, which in turn performs a filesystem scan (`os.ReadDir`) and potentially additional subprocess execs for custom hooks. Because the number of reference updates in a single `git-receive-pack` request is attacker/user controlled and Gitaly enforces no upper bound on it, an ordinary user with push access can submit one push containing an extremely large number of reference updates and force Gitaly to perform a correspondingly large, synchronous amount of process-spawning and hook-lookup work within a single RPC call.

### Finding Description
Per `doc/hooks.md`, the `update` hook is executed once for each reference being updated during `git-receive-pack`-based RPCs, and each execution goes through the full path: `git-receive-pack` execs `gitaly-hooks` → `gitaly-hooks` connects and calls the `HookService.UpdateHook` RPC → Gitaly runs `GitLabHookManager.UpdateHook`. [1](#0-0) 

`UpdateHook` invokes `m.updateHook`, which for every single call constructs a new custom-hooks executor via `newCustomHooksExecutor`: [2](#0-1) 

`newCustomHooksExecutor` performs directory reads (`findHooks` → `os.ReadDir`) against the project and global custom-hooks directories on every invocation, and then, when hook files are found, executes each of them as an external process sequentially: [3](#0-2) 

Because this whole call chain (subprocess spawn of `gitaly-hooks`, gRPC round trip, `os.ReadDir`, and any custom-hook process execs) is repeated once per reference in the push, and Gitaly does not enforce any limit on the number of reference-update commands accepted in a single `git-receive-pack` request, the total amount of process-spawning and I/O work scales linearly and unboundedly with a value fully controlled by the pushing client. This mirrors the reported bug class of iterating over an unbounded, growable set inside a hot code path (`runExecutionHooks`/`runValidationHooks`), except here the "set size" is the number of reference updates in a single push rather than a persisted collection, and the unbounded cost is CPU/process/network exhaustion rather than gas.

### Impact Explanation
A user with ordinary push access to a single repository can submit one `ReceivePack`/`PostReceivePack`/`SSHReceivePack` request containing a very large number of reference-update commands (e.g., thousands to tens of thousands of branch/tag creations pointing at existing objects, requiring no meaningful packfile payload). Gitaly will synchronously spawn and wait on one `gitaly-hooks` process plus one `HookService.UpdateHook` gRPC call per reference, each of which also performs directory listings for custom hooks. This can exhaust CPU, process/file-descriptor limits, and goroutine/gRPC stream resources on the Gitaly node handling the request, degrading or blocking that node for the duration of the single RPC, and — because the `update` hook path also drives the reference-transaction voting mechanism in Praefect deployments — can also delay quorum votes across secondary nodes.

### Likelihood Explanation
This requires only the access level of a normal user capable of pushing to a repository (no admin-installed custom hooks are required to trigger the base subprocess/gRPC overhead per reference), and Git's wire protocol readily allows a single push to contain very large numbers of ref-update commands. No code path found in the reviewed files enforces a cap on the number of commands per `git-receive-pack` request, making the primitive straightforward to trigger with a scripted push.

### Recommendation
Introduce and enforce a configurable maximum number of reference-update commands processed per `ReceivePack`/`PostReceivePack`/`SSHReceivePack` request (rejecting or chunking pushes that exceed it), and/or avoid re-scanning the custom-hooks directories and re-spawning the `gitaly-hooks` gateway process on every single reference update — for example by resolving and caching the custom-hook file list once per RPC invocation rather than once per reference, and by batching update-hook invocations where Git and the hook protocol allow it.

### Proof of Concept
1. As a user with push permission to a repository, construct a `git-receive-pack` request whose command list contains a very large number of `<old-oid> <new-oid> <ref-name>` lines (e.g., tens of thousands of new branch refs pointing at the same, already-existing commit), followed by a minimal or empty packfile.
2. Submit this via `PostReceivePack`/`SSHReceivePack`.
3. Observe that Gitaly executes the `update` hook — including a `gitaly-hooks` subprocess spawn, a `HookService.UpdateHook` gRPC call, and a custom-hooks directory scan via `findHooks`/`os.ReadDir` — once per reference in the list, sequentially, within the handling of the single RPC, as described in `doc/hooks.md`'s per-reference hook loop and implemented in `internal/gitaly/hook/update.go` and `internal/gitaly/hook/custom.go`. func (m *GitLabHookManager) updateHook(ctx context.Context, payload gitcmd.HooksPayload, repo *gitalypb.Repository, ref, oldValue, newValue string, env []string, stdout, stderr io.Writer) error {
	objectHash, err := git.ObjectHashByFormat(payload.ObjectFormat)
	if err != nil {
		return fmt.Errorf("looking up object hash: %w", err)
	}

	if ref == "" {
		return structerr.NewInternal("hook got no reference")
	}
	if err := objectHash.ValidateHex(oldValue); err != nil {
		return structerr.NewInternal("hook got invalid old value: %w", err)
	}
	if err := objectHash.ValidateHex(newValue); err != nil {
		return structerr.NewInternal("hook got invalid new value: %w", err)
	}
	if payload.UserDetails == nil {
		return structerr.NewInternal("payload has no receive hooks info")
	}

	executor, err := m.newCustomHooksExecutor(ctx, repo, "update")
	if err != nil {
		return structerr.NewInternal("%w", err)
	}

	customEnv, err := m.customHooksEnv(ctx, payload, nil, env)
	if err != nil {
		return structerr.NewInternal("constructing custom hook environment: %w", err)
	}

	if err = executor(
		ctx,
		[]string{ref, oldValue, newValue},
		customEnv,
		nil,
		stdout,
		stderr,
	); err != nil {
		return fmt.Errorf("executing custom hooks: %w", err)
	}

	return nil
}

func (m *GitLabHookManager) newCustomHooksExecutor(ctx context.Context, repo *gitalypb.Repository, hookName string) (customHooksExecutor, error) {
	repoPath, err := m.locator.GetRepoPath(ctx, repo)
	if err != nil {
		return nil, err
	}

	var hookFiles []string
	projectCustomHookFile := filepath.Join(repoPath, "custom_hooks", hookName)
	if isValidHook(projectCustomHookFile) {
		hookFiles = append(hookFiles, projectCustomHookFile)
	}

	projectCustomHookDir := filepath.Join(repoPath, "custom_hooks", fmt.Sprintf("%s.d", hookName))
	files, err := findHooks(projectCustomHookDir)
	if err != nil {
		return nil, err
	}
	hookFiles = append(hookFiles, files...)

	if m.cfg.Hooks.CustomHooksDir != "" {
		globalCustomHooksDir := filepath.Join(m.cfg.Hooks.CustomHooksDir, fmt.Sprintf("%s.d", hookName))
		files, err = findHooks(globalCustomHooksDir)
		if err != nil {
			return nil, err
		}
		hookFiles = append(hookFiles, files...)
	}

	return func(ctx context.Context, args, env []string, stdin io.Reader, stdout, stderr io.Writer) error {
		var stdinBytes []byte
		if stdin != nil {
			stdinBytes, err = io.ReadAll(stdin)
			if err != nil {
				return err
			}
		}

		for _, hookFile := range hookFiles {
			c, err := command.New(ctx, m.logger, append([]string{hookFile}, args...),
				command.WithDir(repoPath),
				command.WithStdin(bytes.NewReader(stdinBytes)),
				command.WithStdout(stdout),
				command.WithStderr(stderr),
				command.WithEnvironment(env),
				command.WithCommandName("gitaly-hooks", hookName),
			)
			if err != nil {
				return err
			}

			if err = c.Wait(); err != nil {
				// Custom hook errors need to be handled specially when we update
				// refs via updateref.UpdaterWithHooks: their stdout and stderr must
				// not be modified, but instead used as-is as the hooks' error
				// message given that they may contain output that should be shown
				// to the user.
				return NewCustomHookError(fmt.Errorf("error executing %q: %w", hookFile, err))
			}
		}

		return nil
	}, nil
}

func findHooks(dir string) ([]string, error) {
	fis, err := os.ReadDir(dir)
	if err != nil {
		if os.IsNotExist(err) {
			return nil, nil
		}

		return nil, err
	}

	var hookFiles []string
	for _, fi := range fis {
		hookPath := filepath.Join(dir, fi.Name())
		if isValidHook(hookPath) {
			hookFiles = append(hookFiles, hookPath)
		}
	}

	return hookFiles, nil
}
