Audit Report

## Title
`freeze_collection`/item-`freeze` state is not enforced in `do_burn`, allowing item burns while frozen - (File: substrate/frame/uniques/src/functions.rs)

## Summary
`do_transfer` enforces both the collection-level freeze (`collection_details.is_frozen`) and item-level freeze (`details.is_frozen`) in addition to `T::Locker::is_locked` before permitting a transfer. `do_burn` only checks `T::Locker::is_locked` and never inspects either freeze flag, so a frozen item (or an item in a frozen collection) can still be destroyed via the public `burn` extrinsic.

## Finding Description
`do_transfer` performs three checks prior to mutating ownership: collection `is_frozen` → `Error::Frozen`, `T::Locker::is_locked` → `Error::Locked`, and item `is_frozen` → `Error::Frozen`. [1](#0-0) 

`do_burn`, in contrast, performs only the locker check: [2](#0-1) 

Neither `collection_details.is_frozen` nor `details.is_frozen` is consulted anywhere in `do_burn`. Since `freeze_collection` sets `collection_details.is_frozen = true` and item-level `freeze` sets `ItemDetails.is_frozen = true` — the exact same fields checked by `do_transfer` — an item owner can call the public `burn` extrinsic (which routes directly into `do_burn`) to destroy a frozen item or an item within a frozen collection, fully bypassing the freeze invariant that transfers respect.

## Impact Explanation
This is a genuine logic inconsistency between two storage-mutating flows (`do_transfer` vs `do_burn`) in `substrate/frame/uniques`, both of which are meant to respect the same freeze/lock invariants per the module's own doc comments. An unprivileged item owner can unilaterally destroy an item that was frozen specifically to prevent state changes (e.g., during escrow, dispute, or listing), unreserving the deposit and removing the asset from storage despite the freeze. This matches the "runtime bugs that compromise intended behavior" category — the freeze guarantee, relied upon by any downstream system that assumes "frozen ⇒ immutable," is broken by omission of a check in one specific code path.

## Likelihood Explanation
Trivially reachable: no privileged origin, batching, or proxy trickery required. Any account owning a frozen item, or an item within a frozen collection, can call the public `burn` extrinsic directly, which invokes `do_burn`, and the burn succeeds because no freeze check exists there.

## Recommendation
Add the same freeze checks present in `do_transfer` to `do_burn`: reject with `Error::<T, I>::Frozen` if `collection_details.is_frozen` is true, and with `Error::<T, I>::Frozen` if `details.is_frozen` is true, in addition to the existing `T::Locker::is_locked` check — unless burning while frozen is an explicit, documented design decision that has been reviewed against downstream integrations relying on freeze semantics.

## Proof of Concept
1. Create a collection and mint an item to account `A`.
2. As the collection freezer, call `freeze_collection(collection)` (or `freeze(collection, item)`), setting `collection_details.is_frozen` (or `details.is_frozen`) to `true`.
3. As `A`, attempt `transfer(collection, item, B)` — fails with `Error::Frozen`, confirming enforcement in `do_transfer`.
4. As `A`, call the public `burn(collection, item, ...)` extrinsic — succeeds, since `do_burn` checks only `T::Locker::is_locked`.
5. `Item::<T, I>::remove` executes, the deposit is unreserved, and `Event::Burned` fires — demonstrating the freeze protection was bypassed via `do_burn`.

	pub fn do_burn(
		collection: T::CollectionId,
		item: T::ItemId,
		with_details: impl FnOnce(&CollectionDetailsFor<T, I>, &ItemDetailsFor<T, I>) -> DispatchResult,
	) -> DispatchResult {
		ensure!(!T::Locker::is_locked(collection.clone(), item), Error::<T, I>::Locked);
		let owner = Collection::<T, I>::try_mutate(
			&collection,
			|maybe_collection_details| -> Result<T::AccountId, DispatchError> {
				let collection_details =
					maybe_collection_details.as_mut().ok_or(Error::<T, I>::UnknownCollection)?;

				// TODO should it be UnknownItem instead of UnknownCollection?
				let details = Item::<T, I>::get(&collection, &item)
					.ok_or(Error::<T, I>::UnknownCollection)?;
				with_details(collection_details, &details)?;

				// Return the deposit.
				T::Currency::unreserve(&collection_details.owner, details.deposit);
				collection_details.total_deposit.saturating_reduce(details.deposit);
				collection_details.items.saturating_dec();
				Ok(details.owner)
			},
		)?;
