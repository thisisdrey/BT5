## Title
Fixed-window stream-rate throttling in the QUIC streamer allows sustained ~2x QoS evasion via boundary timing - (`streamer/src/nonblocking/stream_throttle.rs`)

### Summary
`ConnectionStreamCounter::reset_throttling_params_if_needed()` implements a coarse fixed-window rate limiter for per-connection QUIC stream creation. Because the window is reset to zero the instant wall-clock time crosses the `STREAM_THROTTLING_INTERVAL` boundary — rather than accounting proportionally for elapsed time like the `TokenBucket` used elsewhere in this codebase — a connection can burst up to the full per-window quota right before a boundary and again right after it, doubling its effectively allowed stream (transaction) rate on a sustained basis. This mirrors the reported bug class: a time-window based accounting scheme with coarse/discrete boundaries that a caller can align its actions against to systematically deviate from the intended per-unit-time rate.

### Finding Description
`ConnectionStreamCounter` tracks `stream_count` and `last_throttling_instant`, and `reset_throttling_params_if_needed` resets both whenever the elapsed time since the last reset exceeds `STREAM_THROTTLING_INTERVAL` (100ms): [1](#0-0) 

`throttle_stream` then only sleeps (throttles) the connection if `streams_read_in_throttle_interval >= max_streams_per_throttling_interval` within the *current* window: [2](#0-1) 

Both the stake-weighted QoS controller (`SwQos`) and the simple QoS controller (`SimpleQos`, via a `TokenBucket` reused with the same discrete reset semantics) invoke this on every new QUIC unidirectional stream: [3](#0-2) 

Because the window boundary is defined purely by wall-clock crossing with no carry-over/decay of unused capacity or accounting of "how much of the interval remains," a connection that sends `max_streams_per_throttling_interval` streams at time `T - ε` (just before a reset) and then another full quota at `T + ε` (just after the reset, which zeroes the counter) obtains roughly double its intended quota within a span of `2ε`. If the attacker times every subsequent window the same way, this ~2x deviation can be sustained indefinitely, not just as a one-time burst — this is the classic "fixed window counter" rate-limiting flaw, directly analogous to the referenced `noOfDays` truncation bug: both stem from quantizing a continuous rate into discrete time buckets that reset independent of how much of the previous bucket's capacity was actually consumed relative to elapsed time, letting a caller who controls timing systematically deviate from the intended rate.

### Impact Explanation
This is reachable by any unprivileged QUIC client (staked or unstaked) connecting to the TPU/TPU-forward/vote QUIC endpoints — no validator/operator role is required. By precisely timing stream creation relative to the 100ms `STREAM_THROTTLING_INTERVAL` boundary, a connection can push close to double its allotted `max_streams_per_throttling_interval` streams (i.e., transactions) into the node's ingestion pipeline (packet receipt → sigverify → banking stage), evading the per-connection QoS budget that the stake-weighted/simple QoS controllers are meant to enforce. This is a QoS evasion condition explicitly in-scope, and at scale (many connections doing this simultaneously) it increases unprivileged-user-driven load on sigverify/banking stage beyond the capacity the throttle was designed to bound.

### Likelihood Explanation
Exploitation requires only client-side control over packet timing (opening streams within a few milliseconds before/after each 100ms boundary), which is trivial for any external client to script — no elevated privileges, insider access, or multiple colluding validators needed. The throttling window is fixed and public (`STREAM_THROTTLING_INTERVAL_MS = 100`), so an attacker can precompute alignment.

### Recommendation
Replace the discrete reset-on-check window in `ConnectionStreamCounter`/`throttle_stream` with a proportional/sliding accounting scheme — e.g., decay `stream_count` gradually based on elapsed time (as `TokenBucket` in `net-utils/src/token_bucket.rs` already does for other rate limiters in this codebase) rather than zeroing it entirely at a hard boundary, so unused capacity near a boundary cannot be "stacked" with the next window's full quota.

### Proof of Concept
Conceptual timeline against `max_streams_per_throttling_interval = N`:
1. At `t = 99ms` (just before the 100ms boundary), open `N` streams — all succeed since `streams_read_in_throttle_interval < N` throughout.
2. At `t = 101ms`, the next `throttle_stream` call observes `duration_since(last_throttling_instant) > STREAM_THROTTLING_INTERVAL`, so `reset_throttling_params_if_needed` zeroes `stream_count` and resets `last_throttling_instant` (`streamer/src/nonblocking/stream_throttle.rs` lines 213-230).
3. Immediately open another `N` streams — they again all succeed in the "new" window.
4. Net effect: `2N` streams delivered within ~2ms, vs. the intended `N` streams per 100ms — repeatable every window by re-aligning to each new boundary, yielding a sustained ~2x rate over the intended cap.

    /// Reset the counter and last throttling instant and
    /// return last_throttling_instant regardless it is reset or not.
    pub(crate) fn reset_throttling_params_if_needed(&self) -> tokio::time::Instant {
        let last_throttling_instant = *self.last_throttling_instant.read().unwrap();
        if tokio::time::Instant::now().duration_since(last_throttling_instant)
            > STREAM_THROTTLING_INTERVAL
        {
            let mut last_throttling_instant = self.last_throttling_instant.write().unwrap();
            // Recheck as some other thread might have done throttling since this thread tried to acquire the write lock.
            if tokio::time::Instant::now().duration_since(*last_throttling_instant)
                > STREAM_THROTTLING_INTERVAL
            {
                *last_throttling_instant = tokio::time::Instant::now();
                self.stream_count.store(0, Ordering::Relaxed);
            }
            *last_throttling_instant
        } else {
            last_throttling_instant
        }
    }

pub(crate) async fn throttle_stream(
    stats: &StreamerStats,
    peer_type: ConnectionPeerType,
    remote_addr: std::net::SocketAddr,
    stream_counter: &Arc<ConnectionStreamCounter>,
    max_streams_per_throttling_interval: u64,
) {
    let throttle_interval_start = stream_counter.reset_throttling_params_if_needed();
    let streams_read_in_throttle_interval = stream_counter.stream_count.load(Ordering::Relaxed);
    if streams_read_in_throttle_interval >= max_streams_per_throttling_interval {
        // The peer is sending faster than we're willing to read. Sleep for what's
        // left of this read interval so the peer backs off.
        let throttle_duration =
            STREAM_THROTTLING_INTERVAL.saturating_sub(throttle_interval_start.elapsed());

        if !throttle_duration.is_zero() {
            debug!(
                "Throttling stream from {remote_addr:?}, peer type: {peer_type:?}, \
                 max_streams_per_interval: {max_streams_per_throttling_interval}, \
                 read_interval_streams: {streams_read_in_throttle_interval} throttle_duration: \
                 {throttle_duration:?}"
            );
            stats.throttled_streams.fetch_add(1, Ordering::Relaxed);
            match peer_type {
                ConnectionPeerType::Unstaked => {
                    stats
                        .throttled_unstaked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
                ConnectionPeerType::Staked(_) => {
                    stats
                        .throttled_staked_streams
                        .fetch_add(1, Ordering::Relaxed);
                }
            }
            sleep(throttle_duration).await;
        }
    }
}
