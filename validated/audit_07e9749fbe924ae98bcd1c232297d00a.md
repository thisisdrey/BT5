### Title
`CAPool.verify()` only checks the leaf certificate's fingerprint against the blocklist, never the signing CA's fingerprint - ([File: cert/ca_pool.go])

### Summary
`pki.blocklist` lets an operator revoke *any* certificate fingerprint, including a CA certificate's fingerprint, via `BlocklistFingerprint()` [1](#0-0) . However, the internal verification routine only tests the leaf certificate's own fingerprint (and its P256 alternate form) against the blocklist; it never checks whether the *signer* CA that issued the certificate has itself been blocklisted. This is structurally the same class of bug as the reported `onlyNotGameOver()` issue: the check inspects one specific piece of state (the leaf's own status) while ignoring an equally authoritative "revocation/compromise" signal (the issuing CA's blocklisted status) that should immediately invalidate everything signed by it.

### Finding Description
`CAPool.verify()` is the common core used by both `VerifyCertificate` (fresh verification) and `VerifyCachedCertificate` (fast path for already-handshaked peers, invoked every tick by the connection manager): [2](#0-1) 

The only blocklist check performed is `ncp.IsBlocklisted(certFp)` against the certificate's own fingerprint (plus, in `VerifyCertificate`/`VerifyCachedCertificate`, the P256 alternate-signature fingerprint) [3](#0-2) [4](#0-3) . The function then fetches the issuing CA via `GetCAForCert` and checks `signer.Certificate.Expired(now)` for expiry, but it never calls `ncp.IsBlocklisted(signer.Fingerprint)`: [5](#0-4) 

`BlocklistFingerprint` is a generic API documented to work on "certificate" fingerprints (the `Certificate.Fingerprint()` doc explicitly says "This acts as a unique fingerprint and can be used to blocklist certificates" [6](#0-5) ) and it is fed directly from operator config `pki.blocklist` with no restriction to leaf-only fingerprints [1](#0-0) . If an operator (or automated tooling) intends to revoke an entire compromised intermediate/CA by blocklisting its fingerprint - the natural way to signal "this trust root is no longer good," analogous to the game's domination-victory state - certificates signed by that CA still pass verification as long as they are not expired and their own leaf fingerprint isn't separately blocklisted.

This directly parallels the `onlyNotGameOver()` bug: the modifier/verification function checks one specific stored flag (`WinningEmpire`/leaf blocklist) but omits an equally valid, already-known "game over"/"revoked" condition (`domination victory`/CA blocklist) that a caller can reasonably expect to be enforced.

The impact is felt on every hot path that relies on this verification:
- Handshake certificate verification (`HandshakeManager.certVerifier` → `VerifyCertificate`) [7](#0-6) 
- Per-tick tunnel teardown for already-connected peers (`connectionManager.isInvalidCertificate` → `VerifyCachedCertificate`) [8](#0-7) 
- Firewall rule evaluation, which passes the peer's cached cert/CA name into rule matching (`caName`, group checks) that implicitly trusts the CA chain still being valid [9](#0-8) 

### Impact Explanation
If an operator revokes a compromised or malicious intermediate/root CA by adding its fingerprint to `pki.blocklist` (a supported, documented mechanism), any certificate previously or newly issued by that CA continues to be accepted for handshakes and continues to keep already-established tunnels alive, because `verify()` never re-checks the signer's blocklist status. This defeats the primary intended remediation path for a compromised CA and allows continued mutual authentication/traffic decryption with hosts whose trust anchor the operator explicitly tried to revoke.

### Likelihood Explanation
This requires the specific operational scenario of an operator blocklisting a CA fingerprint (rather than only leaf fingerprints) expecting all certs it issued to be invalidated. Given the API is generic and CA certificates are documented to have the same `Fingerprint()`/blocklisting semantics as leaf certs, this is a realistic operational expectation, not a fringe misuse. However, it does require that specific administrative action to be reachable at all, so likelihood is moderate rather than trivially always exploitable by a remote peer without any admin involvement.

### Recommendation
In `CAPool.verify()`, after resolving `signer` via `GetCAForCert`, also check `ncp.IsBlocklisted(signer.Fingerprint)` (and its alternate P256 fingerprint form, consistent with the leaf-cert handling) and return `ErrBlockListed` if the signer is blocklisted. This mirrors the report's recommendation to explicitly call the missing check (`_checkDominationVictory()`-equivalent) rather than relying on a single narrow flag.

### Proof of Concept
1. Build a CA pool with CA `A` and a leaf certificate `C` signed by `A`: `caPool.AddCA(A)`.
2. Verify `C` succeeds: `caPool.VerifyCertificate(now, C)` → no error.
3. Operator revokes the CA itself: `caPool.BlocklistFingerprint(A.Fingerprint())` (exactly the `pki.blocklist` config path used in `loadCAPoolFromConfig` [1](#0-0) ).
4. Call `caPool.VerifyCertificate(now, C)` again (or `VerifyCachedCertificate` for an existing tunnel) - it still returns success, because `verify()` [10](#0-9)  only tests `IsBlocklisted(certFp)` on `C`'s own fingerprint, never `A`'s fingerprint (`signer.Fingerprint`). The existing test suite (`TestCertificateV1_Verify`, `TestCertificateV2_Verify`, etc.) only exercises blocklisting the *leaf* cert's fingerprint [11](#0-10) , confirming there is no coverage - or enforcement - for the CA-fingerprint-blocklist case.

```go
func (ncp *CAPool) verify(c Certificate, now time.Time, certFp string, signerFp string) (*CachedCertificate, error) {
	if ncp.IsBlocklisted(certFp) {
		return nil, ErrBlockListed
	}

	signer, err := ncp.GetCAForCert(c)
	if err != nil {
		return nil, err
	}

	if signer.Certificate.Curve() != c.Curve() {
		return nil, ErrCurveMismatch
	}

	if signer.Certificate.Expired(now) {
		return nil, ErrRootExpired
	}

	if c.Expired(now) {
		return nil, ErrExpired
	}

	// If we are checking a cached certificate then we can bail early here
	// Either the root is no longer trusted or everything is fine
	if len(signerFp) > 0 {
		if signerFp != signer.Fingerprint {
			return nil, ErrFingerprintMismatch
		}
		return signer, nil
	}
	if !c.CheckSignature(signer.Certificate.PublicKey()) {
		return nil, ErrSignatureMismatch
	}

	err = CheckCAConstraints(signer.Certificate, c)
	if err != nil {
		return nil, err
	}

	return signer, nil
}
```

```go
// isInvalidCertificate decides if we should destroy a tunnel.
// returns true if pki.disconnect_invalid is true and the certificate is no longer valid.
// Blocklisted certificates will skip the pki.disconnect_invalid check and return true.
func (cm *connectionManager) isInvalidCertificate(now time.Time, hostinfo *HostInfo) bool {
	remoteCert := hostinfo.GetCert()
	if remoteCert == nil {
		return false //don't tear down tunnels for handshakes in progress
	}

	caPool := cm.intf.pki.GetCAPool()
	err := caPool.VerifyCachedCertificate(now, remoteCert)
	if err == nil {
		return false //cert is still valid! yay!
	} else if err == cert.ErrBlockListed { //avoiding errors.Is for speed
		// Block listed certificates should always be disconnected
		hostinfo.logger(cm.l).Info("Remote certificate is blocked, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else if cm.intf.disconnectInvalid.Load() {
		hostinfo.logger(cm.l).Info("Remote certificate is no longer valid, tearing down the tunnel",
			"error", err,
			"fingerprint", remoteCert.Fingerprint,
		)
		return true
	} else {
		//if we reach here, the cert is no longer valid, but we're configured to keep tunnels from now-invalid certs open
		return false
	}
}
```
