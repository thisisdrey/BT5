## Finding

### Title
`hop_submit` signature does not bind the `recipients` list, allowing signature replay with attacker-controlled recipients - (File: `substrate/client/hop/src/types.rs`, `substrate/client/hop/src/rpc.rs`)

### Summary
The HOP data-handoff subsystem lets a signer authorize storage/promotion of a data blob via `hop_submit`. The signed payload only commits to the blob hash and the submit timestamp — it never commits to the `recipients` list. This is the same bug class as the external report: a field (`recipients`, analogous to `toRecipient`/`toTrader`) that determines who receives value/data is excluded from what is cryptographically signed, so it can be swapped without invalidating the signer's signature.

### Finding Description
`submit_signing_payload` computes exactly what the client signs: [1](#0-0) 

Only `hash` (the blake2-256 of the data) and `submit_timestamp` are covered. The RPC handler decodes `recipients` completely independently of the signature check: [2](#0-1) 

Note lines ~158-176 decode `recipients` and `signer`/`signature` as unrelated arguments, and the only cryptographic check performed (line ~210-214) is `multi_sig.verify(&submit_payload[..], &account_id)`, where `submit_payload` is built solely from `hash` and `submit_timestamp`. The `Recipient` list is then stored verbatim in `HopEntryMeta` and used later to gate `claim`/`ack` via `find_recipient_idx`: [3](#0-2) 

The comment on `HopEntryMeta::signature` even states the intended security property explicitly — "submit implies consent to promote" — but that consent is only bound to the blob content and timestamp, not to who is allowed to retrieve it: [4](#0-3) 

Because a promoted entry's `(data, signer, signature, submit_timestamp)` tuple becomes permanent, public on-chain data once the maintenance task submits the unsigned promotion extrinsic — see `RuntimeApiPromoter::promote`, which forwards exactly these four values and nothing about recipients: [5](#0-4) 

— any third party can read that tuple off-chain and replay it against `hop_submit` on any honest node with an arbitrary `recipients` list of their own choosing. The signature still verifies (it never covered `recipients`), so the node accepts the submission and stores the blob keyed to the attacker's chosen recipient set. The attacker can then call `hop_claim`/`hop_ack` as an "intended recipient" for data they were never meant to receive.

### Impact Explanation
This breaks the confidentiality/exclusivity guarantee of the HOP handoff protocol: an unprivileged actor with no signing key and no special network position (only the ability to read already-public on-chain promotion data, or to observe an RPC call once) can insert themselves as a recipient of data whose sender never authorized them, and retrieve payloads intended for someone else. No malicious peer, validator, collator, or relayer is required — only public information (`signer`, `signature`, `hash`, `submit_timestamp`) which is designed to be shared with any node in order to submit, and which is permanently on-chain once promoted.

### Likelihood Explanation
High for promoted entries: promotion extrinsics are unsigned but publicly broadcast and permanently stored, so the four values needed for replay are trivially recoverable by anyone scanning chain state. The attack costs nothing (no fee, no key material) and can be repeated against any node running the HOP RPC.

### Recommendation
Include the full `recipients` list (or a commitment/hash of it) inside `submit_signing_payload`, so that the signer's signature binds who is authorized to claim the data. Reject `hop_submit` calls whose `recipients` do not match the committed value, mirroring the recommendation in the external report to bind the previously-excluded fields into the signed data (or require them to be supplied explicitly and verified at the point of use, e.g. in `LiquoriceSettlement.settle`).

### Proof of Concept
1. Sender `S` calls `hop_submit(data, [recipient_R], signature, signer_S, ts)`; entry is promoted on-chain, making `(hash(data), signer_S, signature, ts)` public.
2. Attacker `A` (no key material for `S`) reads this tuple from chain state.
3. `A` calls `hop_submit(data, [recipient_A], signature, signer_S, ts)` against any honest HOP node. `submit_signing_payload(hash, ts)` verification passes because it never covered `recipients`.
4. The node stores the entry with `recipients = [A]`. `A` then calls `hop_claim`/`hop_ack` using their own ephemeral key and retrieves `data`, despite never being authorized by `S`. [6](#0-5)

/// Compute the 32-byte payload signed at `hop_submit` time.
///
/// The runtime pallet re-derives this exact byte sequence to verify the
/// signature on-chain, so the construction must remain byte-identical to the
/// pallet's `signing_payload(data, submit_timestamp)`:
/// `blake2_256(HOP_SUBMIT_CONTEXT || blake2_256(data) || submit_timestamp.to_le_bytes())`.
pub fn submit_signing_payload(hash: &HopHash, submit_timestamp: u64) -> [u8; 32] {
	let mut buf = [0u8; HOP_SUBMIT_CONTEXT.len() + 32 + 8];
	buf[..HOP_SUBMIT_CONTEXT.len()].copy_from_slice(HOP_SUBMIT_CONTEXT);
	buf[HOP_SUBMIT_CONTEXT.len()..HOP_SUBMIT_CONTEXT.len() + 32].copy_from_slice(hash.as_bytes());
	buf[HOP_SUBMIT_CONTEXT.len() + 32..].copy_from_slice(&submit_timestamp.to_le_bytes());
	blake2_256(&buf)
}

```rust
	fn submit(
		&self,
		data: Bytes,
		recipients: Vec<Bytes>,
		signature: Bytes,
		signer: Bytes,
		submit_timestamp: u64,
	) -> RpcResult<SubmitResult> {
		let recipient_keys: RecipientVec = recipients
			.into_iter()
			.map(|r| {
				MultiSigner::decode(&mut &r.0[..])
					.map(|signer| Recipient { signer, claimed: false })
					.map_err(|_| HopError::InvalidRecipientKey)
			})
			.collect::<Result<Vec<_>, _>>()?
			.try_into()
			.map_err(|v: Vec<Recipient>| HopError::TooManyRecipients {
				provided: v.len(),
				limit: MAX_RECIPIENTS as usize,
			})?;

		let signer =
			MultiSigner::decode(&mut &signer.0[..]).map_err(|_| HopError::InvalidSigner)?;
		let multi_sig = MultiSignature::decode(&mut &signature.0[..])
			.map_err(|_| HopError::InvalidSignature)?;

		let chain_info = self.client.info();
		let best_hash = chain_info.best_hash;

		let data_len = data.0.len();

		// Reject oversized payloads before the per-account authorization lookup so
		// a flood of too-big submits cannot force runtime state reads. The cap is
		// the runtime-declared `max_promotion_size`; the runtime is authoritative.
		let runtime_max = runtime_api::max_promotion_size::<Block, _>(&*self.client, best_hash)
			.map_err(HopError::from)?;
		if data_len > runtime_max as usize {
			return Err(HopError::DataTooLarge(data_len, runtime_max).into());
		}

		// Check authorization before verifying the signature: a flood of unauthorized
		// requests must not force a signature verification per submit.
		// `can_account_promote` returns false for any reason the runtime rejects:
		// unauthorized account or exhausted per-account quota.
		let account_id: AccountId32 = signer.clone().into_account();
		let authorized = runtime_api::can_account_promote::<Block, _>(
			&*self.client,
			best_hash,
			account_id.clone(),
			data_len as u32,
		)
		.map_err(HopError::from)?;
		if !authorized {
			return Err(HopError::NotAuthorized.into());
		}

		// Domain-separated payload so a submit signature cannot be replayed as claim/ack,
		// and bound to `submit_timestamp` so an old signature can't be replayed long
		// after the fact (the runtime enforces a tolerance window on the timestamp).
		let hash = H256(blake2_256(&data.0));
		let submit_payload = submit_signing_payload(&hash, submit_timestamp);
		if !multi_sig.verify(&submit_payload[..], &account_id) {
			return Err(HopError::InvalidSignature.into());
		}

		let sender_id: [u8; 32] = account_id.into();
		self.pool
			.insert(data.0, recipient_keys, sender_id, signer, multi_sig, submit_timestamp)?;
		Ok(SubmitResult { pool_status: self.pool.status() })
```

	/// Decode `signature` and return the index of the matching recipient in
	/// `meta.recipients`. `context` is the operation's domain separator (claim
	/// / ack). Returning an index keeps a single implementation for both
	/// shared- and exclusive-borrow callers (`meta.recipients[idx]` works in
	/// either case).
	fn find_recipient_idx(
		meta: &HopEntryMeta,
		hash: &HopHash,
		signature: &[u8],
		context: &[u8],
	) -> Result<usize, HopError> {
		let multi_sig =
			MultiSignature::decode(&mut &signature[..]).map_err(|_| HopError::InvalidSignature)?;
		let payload = signing_payload(context, hash);

		meta.recipients
			.iter()
			.position(|r| multi_sig.verify(&payload[..], &r.signer.clone().into_account()))
			.ok_or(HopError::NotRecipient)
	}

	fn promote(
		&self,
		data: Vec<u8>,
		signer: MultiSigner,
		signature: MultiSignature,
		submit_timestamp: u64,
	) -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
		let best_hash = self.client.info().best_hash;
		let ext = runtime_api::create_promotion_extrinsic::<Block, _>(

			best_hash,
			data,
			signer,
			signature,
			submit_timestamp,

		self.tx_pool
			.submit_local(best_hash, ext)
			.map_err(|e| format!("submit_local failed: {:?}", e))?;
		Ok(())
	}
