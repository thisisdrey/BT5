### Title
Exchange liquidity injection has no slippage/minimum-output protection, enabling sandwich attacks against the pool creator - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract`/`ExchangeInjectActuator` computes the paired token amount (`anotherTokenQuant`) to withdraw from the injecting account purely from the *current* on-chain pool ratio at execution time, with no user-supplied minimum/maximum bound, unlike `ExchangeTransactionContract`, which does carry an `expected` field checked in `ExchangeTransactionActuator`. This is the same missing-slippage-protection pattern as the reported Uniswap-quoter issue: any unprivileged account can move the pool ratio immediately before the victim's inject transaction is packed into a block and restore it afterward, extracting value from the victim within a single block via a classic sandwich attack.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, and `quant` — there is no field to bound the resulting `anotherTokenQuant`. [1](#0-0) 

In `ExchangeInjectActuator.doValidate()`/`execute()`, `anotherTokenQuant` is derived from the exchange's live `firstTokenBalance`/`secondTokenBalance` at validation/execution time and then both `tokenQuant` and `anotherTokenQuant` are debited from the injecting account with no comparison against any caller-specified bound: [2](#0-1) [3](#0-2) 

Contrast this with `ExchangeTransactionActuator`, which validates the swap output against a caller-supplied `expected` minimum: [4](#0-3) 

Any unprivileged account can broadcast `ExchangeTransactionContract` swaps against the same exchange (no special permission is required for `ExchangeTransactionActuator`), which changes `firstTokenBalance`/`secondTokenBalance` via `ExchangeCapsule.transaction()`: [5](#0-4) 

Because block producers order transactions and an attacker can submit swap transactions before and after a pending inject transaction within a block (or across adjacent blocks under a cooperating/待-confirmation window), the attacker can:
1. Swap to skew the pool ratio unfavorably right before the creator's `ExchangeInjectContract` is applied.
2. Let the creator's inject execute at the skewed ratio, forcing them to pay more of `anotherTokenID` than the fair-value ratio would require.
3. Swap back to restore the ratio, pocketing the difference.

### Impact Explanation
This results in unauthorized value extraction (theft of funds) from the exchange creator/liquidity injector without their consent, purely through transaction ordering — the actuator has no on-chain defense (no min/max bound, no expected ratio tolerance) comparable to what `ExchangeWithdrawActuator` and `ExchangeTransactionActuator` already implement (the former enforces a "Not precise enough" tolerance check, the latter enforces `expected`): [6](#0-5) 

### Likelihood Explanation
Exploitation only requires broadcasting ordinary, permissionless `ExchangeTransactionContract` swap transactions around an observed pending `ExchangeInjectContract` transaction in the mempool — no elevated privilege, witness/SR role, or contract vulnerability is needed. Given java-tron's public mempool and deterministic block-producer ordering, front-running/sandwiching pending transactions is a well-understood and repeatedly demonstrated technique.

### Recommendation
Add a caller-specified bound to `ExchangeInjectContract` (e.g., `expected`/`max_another_token_quant`) analogous to `ExchangeTransactionContract.expected`, and validate `anotherTokenQuant` against it in `ExchangeInjectActuator.doValidate()`/`execute()` before debiting the account, rejecting the transaction if the computed amount exceeds the caller's tolerance.

### Proof of Concept
1. Exchange pool has `firstTokenBalance = X`, `secondTokenBalance = Y`.
2. Attacker observes a pending `ExchangeInjectContract` from the pool creator for `tokenQuant` of `firstTokenID`.
3. Attacker broadcasts an `ExchangeTransactionContract` selling a large amount of `secondTokenID` for `firstTokenID`, shifting the ratio so `secondTokenBalance/firstTokenBalance` increases (making `firstTokenID` "cheaper" in the pool).
4. Creator's inject executes: `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` — computed at the skewed ratio, over-charging the creator in `secondTokenID`, per `ExchangeInjectActuator.doValidate()`/`execute()` at lines 215-231/71-91.
5. Attacker immediately reverses the swap with another `ExchangeTransactionContract`, restoring the ratio and net profit equal to the extra `secondTokenID` extracted from the creator.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }
