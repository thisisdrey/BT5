Confirmed: both `ExchangeInjectActuator` (add-liquidity, "mint" analog) and `ExchangeWithdrawActuator` (remove-liquidity, "burn" analog) compute the counter-token amount purely from the exchange pool's balances at execution time, with no minimum/maximum-bound (slippage) parameter — unlike `ExchangeTransactionActuator`, which does carry an `expected` field enforcing a minimum-received check.

### Title
Missing slippage protection in `ExchangeInjectContract` / `ExchangeWithdrawContract` enables front-run sandwich losses on TRC10 exchange liquidity operations - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`, `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
The native TRC10 bancor-style exchange market supports `ExchangeInjectContract` (add liquidity) and `ExchangeWithdrawContract` (remove liquidity). Both compute the paired-token amount from the exchange's live on-chain reserve ratio with no caller-supplied bound, unlike the sibling `ExchangeTransactionContract` (a swap), which explicitly carries an `expected` minimum-output field enforced in validation.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` — no minimum/maximum bound on the counter-token amount debited from the injector's account. In `doValidate()`/`execute()`, the `anotherTokenQuant` (amount of the paired token pulled from the caller) is derived purely from the current pool ratio at execution time: `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` (or the symmetric case), computed in [1](#0-0)  and re-derived identically in `execute()` at [2](#0-1) .

`ExchangeWithdrawContract` has the identical structure — only `owner_address`, `exchange_id`, `token_id`, `quant` — with the returned counter-token amount computed the same way at execution time in [3](#0-2)  and [4](#0-3) .

By contrast, `ExchangeTransactionContract` explicitly protects the caller: it carries an `expected` field [5](#0-4)  and `doValidate()` rejects the transaction if `anotherTokenQuant < tokenExpected`: [6](#0-5) . No such check exists for inject/withdraw.

Because the exchange's reserve ratio can be moved by any preceding `ExchangeTransactionContract` (an ordinary swap any account can broadcast) included earlier in the same block or a prior block, an attacker can front-run a pending inject/withdraw transaction: swap to skew the ratio immediately before the victim's inject/withdraw executes, then swap back afterward. Since the exchange creator's inject/withdraw amount is entirely dictated by the ratio at execution time with no caller-enforced bound, the attacker can force the victim to inject a larger amount of the paired token than intended, or receive a smaller amount of the paired token on withdrawal than intended, extracting the difference for themselves.

### Impact Explanation
The exchange creator (the only account permitted to inject/withdraw per the `is not creator` check in [7](#0-6) ) suffers unauthorized value extraction: either an inflated debit of the paired token on inject, or a reduced payout on withdraw, with the delta captured by the attacker's sandwiching swaps. This is a concrete loss-of-funds condition reachable purely through ordinary signed transactions (`ExchangeTransactionContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract`) that any unprivileged account can broadcast — matching the "theft of funds" impact class.

### Likelihood Explanation
Exploitation only requires the attacker to observe a pending `ExchangeInjectContract`/`ExchangeWithdrawContract` in the mempool (or exploit block-producer transaction ordering) and broadcast bracketing `ExchangeTransactionContract` swaps against the same `exchange_id`. No special privilege, witness/SR status, or protocol-level access is required — it is a standard MEV/front-running pattern against a market mechanism that intentionally omits slippage protection on two of its three operation types.

### Recommendation
Add a caller-supplied bound field (e.g., `expected_another_token_quant` for inject, `expected_token_quant`/`expected_another_token_quant` for withdraw) to `ExchangeInjectContract` and `ExchangeWithdrawContract`, and enforce it in `doValidate()` analogous to the existing `tokenExpected` check in `ExchangeTransactionActuator` ( [6](#0-5) ), rejecting the transaction if the computed counter-token amount falls outside the caller's tolerance.

### Proof of Concept
1. Exchange creator broadcasts `ExchangeInjectContract{exchange_id, token_id=firstToken, quant=Q}` expecting to also debit `anotherTokenQuant ≈ secondTokenBalance*Q/firstTokenBalance` of the second token based on the ratio observed when signing.
2. Attacker observes this pending transaction and broadcasts an `ExchangeTransactionContract` swap against the same `exchange_id` that shifts `firstTokenBalance`/`secondTokenBalance` unfavorably (e.g., inflating `secondTokenBalance` relative to `firstTokenBalance`) immediately before the inject executes.
3. The inject executes with the manipulated ratio computed in [2](#0-1) , debiting the creator far more of the second token than intended, since no `expected`/slippage bound exists to abort the transaction.
4. Attacker broadcasts a reverse swap to restore the ratio and pocket the second-token surplus extracted from the creator. An analogous sandwich against `ExchangeWithdrawContract` ( [4](#0-3) ) instead reduces the amount the creator receives on withdrawal.
