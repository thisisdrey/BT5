### Title
`SwapFirstAssetTrader::refund_weight` performs XCM fee refund swap with no slippage protection, enabling MEV extraction from AssetConversion pool - (File: cumulus/primitives/utility/src/lib.rs)

### Summary
`SwapFirstAssetTrader::refund_weight` swaps back unused XCM weight-fee credit (held in the `Target` asset) into the asset the user originally paid with, so it can be refunded to the message's asset holding. This swap is executed via `SwapCredit::swap_exact_tokens_for_tokens` with `amount_out_min` hardcoded to `None`, meaning the refund is accepted at whatever price the permissionless `pallet_asset_conversion` pool offers at that instant, with no floor to reject an unfavorable rate.

### Finding Description
`buy_weight` converts a client's payment asset into the `Target` asset using `SwapCredit::swap_tokens_for_exact_tokens`, accumulating the result in `self.total_fee` [1](#0-0) . When an XCM instruction later reports unused weight, `refund_weight` extracts the corresponding `Target`-asset amount and swaps it back into the original payment asset via `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` — explicitly passing `None` for `amount_out_min` [2](#0-1) .

The underlying `pallet_asset_conversion` swap primitives do support a caller-supplied minimum-output guard (`amount_out_min`), and the pallet's own extrinsics/tests treat omitting or under-setting it as the classic slippage hazard (`ProvidedMinimumNotSufficientForSwap`) [3](#0-2) [4](#0-3) . `SwapFirstAssetTrader::refund_weight` deliberately opts out of this guard, so `do_swap_exact_credit_tokens_for_tokens` only checks `amount_out_min.map_or(true, |a| amount_out >= a)`, which is vacuously true when `None` is supplied [5](#0-4) . The trade therefore executes at any resulting price, however degraded.

Because `pallet_asset_conversion` pools are ordinary, permissionlessly-tradable AMM pools reachable by any signed account through `swap_exact_tokens_for_tokens` / `add_liquidity` / `remove_liquidity` extrinsics [6](#0-5) , an attacker who can predict or influence transaction ordering around the block in which an inbound XCM message's `refund_weight` executes can skew the `Target`/`refund_swap_asset` pool price beforehand (e.g., via a large one-sided swap or thin-liquidity manipulation), causing the refund swap to convert `total_fee` into a much smaller amount of `refund_swap_asset` than fair value, and then reverse the price afterward to capture the difference — a standard sandwich/MEV pattern that only exists because this call path opts out of the min-output check that the pallet otherwise provides.

### Impact Explanation
The value lost by the refund recipient (the account/message whose surplus weight fee is being returned) is captured by whoever manipulates the pool around the swap, i.e., silent value leakage from an unprivileged, public trading path with no attacker-side compromise of validators, collators, or governance — fitting "public underpriced work" / fund-loss impact for a public, permissionless entrypoint (the AssetConversion pool extrinsics combined with automatic XCM fee-refund execution).

### Likelihood Explanation
Every parachain configuring `SwapFirstAssetTrader` as its `WeightTrader` (paying XCM execution fees in a non-native asset that must be swapped into `Target`) executes this uncapped-slippage refund on essentially every inbound message that overpays weight, which is a very common, non-privileged, high-frequency code path. Exploitation only requires the attacker to be able to submit ordinary swap extrinsics against the same `pallet_asset_conversion` pool — no special access is needed.

### Recommendation
`SwapFirstAssetTrader::refund_weight` should compute and pass a real `amount_out_min` (e.g., derived from `QuotePrice::quote_price_exact_tokens_for_tokens` with an acceptable tolerance, or a configurable `Get<Permill>` slippage bound) instead of hardcoding `None`, and treat a swap failure/below-minimum result the same as the current `Err` branch (return the credit to `total_fee` and skip the refund rather than accept an arbitrarily bad rate).

### Proof of Concept
1. Configure a parachain XCM executor with `SwapFirstAssetTrader<Target, pallet_asset_conversion::Pallet<Runtime>, ...>` and a live `Target`/`AssetX` pool in `pallet_asset_conversion`.
2. Attacker observes/predicts an inbound XCM message that will pay fees in `AssetX`, overpaying weight so that `refund_weight` will later trigger.
3. Immediately before the message executes, attacker calls the public `swap_exact_tokens_for_tokens` (or adds/removes liquidity) to skew the `Target`→`AssetX` price heavily against `AssetX`.
4. The message executes; `buy_weight` swaps `AssetX`→`Target` for the exact fee (unaffected, since it is buying an exact target amount off whatever `AssetX` was provided). `refund_weight` then swaps the surplus `Target` back to `AssetX` via `swap_exact_tokens_for_tokens(..., None)`, receiving far fewer `AssetX` tokens than the pre-manipulation exchange rate implies, since no `amount_out_min` rejects the bad rate.
5. Attacker reverses the price skew afterward, having captured the spread that should have gone back to the message's fee-payer as a refund.
