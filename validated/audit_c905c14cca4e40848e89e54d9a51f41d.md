### Title
Per-connection (not per-IP/per-class) unstaked stream throttling allows multiplying effective unstaked TPS via parallel connections - ([File: streamer/src/nonblocking/stream_throttle.rs])

### Summary
`StakedStreamLoadEMA::available_load_capacity_in_throttling_duration` returns a fixed `max_unstaked_load_in_throttling_window` for every `ConnectionPeerType::Unstaked` connection, and this cap is enforced against a per-connection `ConnectionStreamCounter` rather than any aggregate counter for the unstaked class or the client's IP. Since a single unstaked client can open up to `max_connections_per_unstaked_peer` concurrent connections, it can multiply its effective stream throughput by that factor, exceeding the intended global `MAX_UNSTAKED_TPS`.

### Finding Description
`available_load_capacity_in_throttling_duration` for `ConnectionPeerType::Unstaked` unconditionally returns `self.max_unstaked_load_in_throttling_window`, a value derived once from the global `MAX_UNSTAKED_TPS` constant and independent of how many unstaked connections currently exist: [1](#0-0) 

This limit is enforced in `throttle_stream` purely against the `stream_count` of the `ConnectionStreamCounter` object tied to that one connection: [2](#0-1) 

Each unstaked connection accepted by `SwQos::try_add_connection` gets its own freshly-allocated `ConnectionStreamCounter` (via `|| Arc::new(ConnectionStreamCounter::new())` passed to `try_add_connection` on the connection table), so counters are never shared or aggregated across connections from the same peer: [3](#0-2) 

Critically, `StakedStreamLoadEMA::increment_load` — the only place that feeds the shared/aggregate `load_in_recent_interval` EMA — ignores unstaked traffic entirely (`if peer_type.is_staked() { ... }`), meaning unstaked stream volume never contributes to any cluster-wide accounting used for throttling decisions: [4](#0-3) 

The only structural limits on how many unstaked connections one peer can hold are `max_connections_per_unstaked_peer` (per-IP connection cap) and `max_unstaked_connections` (global unstaked connection table cap), both enforced purely as connection-count caps, not stream-throughput caps: [5](#0-4) 

Because each connection independently gets its own full `max_unstaked_load_in_throttling_window` streams per `STREAM_THROTTLING_INTERVAL`, an attacker holding `C` concurrent unstaked connections (up to `max_connections_per_unstaked_peer`) achieves `C * MAX_UNSTAKED_TPS` effective throughput instead of the single, class-wide `MAX_UNSTAKED_TPS` (200) the constant's name and comment imply is the intended ceiling.

### Impact Explanation
This is a QoS evasion of the intended stake-weighted scheduling: the unstaked class as a whole is meant to be capped at `MAX_UNSTAKED_TPS = 200` streams/sec cluster-wide (per validator), but an attacker can inflate this multiplicatively by connection count, up to `max_connections_per_unstaked_peer` (and further by using multiple source IPs up to `max_unstaked_connections`). This directly starves the bandwidth share reserved for legitimate staked senders, since `StakedStreamLoadEMA` bases staked capacity partly on the assumption that unstaked traffic is bounded to `EXPECTED_UNSTAKED_STREAMS_RATIO` (20%) of total load, and does not account for or throttle in response to actual aggregate unstaked volume.

### Likelihood Explanation
Fully reachable by an unprivileged remote client: opening several concurrent QUIC connections to the leader's public TPU port from the same or different unstaked source IPs requires no stake, no keys, and no validator/operator cooperation — only staying within `max_connections_per_unstaked_peer` and `max_unstaked_connections`, both of which are non-trivial (multi-connection) but standard client-side capabilities. It is fully repeatable every `STREAM_THROTTLING_INTERVAL` (100ms) and scales linearly with connection count.

### Recommendation
Enforce unstaked stream-rate limiting against an aggregate counter (shared per source IP and/or globally for the whole unstaked class) rather than per-`ConnectionStreamCounter`. For example, track `load_in_recent_interval`-style accounting for unstaked traffic too (currently skipped in `increment_load`), and derive `available_load_capacity_in_throttling_duration(Unstaked, _)` as a function of aggregate consumed unstaked capacity divided fairly across active unstaked connections/peers, so that opening additional connections from the same peer/IP does not increase total allowed throughput.

### Proof of Concept
```rust
// streamer/src/nonblocking/stream_throttle.rs (illustrative test, to be adapted into an integration test)
#[tokio::test]
async fn test_unstaked_multi_connection_bypasses_global_tps_cap() {
    let stats = Arc::new(StreamerStats::default());
    let load_ema = Arc::new(StakedStreamLoadEMA::new(
        stats.clone(),
        DEFAULT_MAX_UNSTAKED_CONNECTIONS,
        DEFAULT_MAX_STREAMS_PER_MS,
    ));

    let per_conn_cap = load_ema.available_load_capacity_in_throttling_duration(
        ConnectionPeerType::Unstaked,
        0,
    );

    // Simulate C concurrent unstaked connections from a single attacker peer,
    // each with its own ConnectionStreamCounter (as created independently by
    // SwQos::cache_new_connection for every accepted connection).
    let c = 8; // <= max_connections_per_unstaked_peer
    let mut total_allowed = 0u64;
    for _ in 0..c {
        let counter = Arc::new(ConnectionStreamCounter::new());
        for _ in 0..per_conn_cap {
            counter.stream_count.fetch_add(1, std::sync::atomic::Ordering::Relaxed);
        }
        total_allowed += counter.stream_count.load(std::sync::atomic::Ordering::Relaxed);
    }

    // Expected (bug): total_allowed == c * per_conn_cap, far exceeding the
    // intended global MAX_UNSTAKED_TPS-derived window (per_conn_cap alone).
    assert_eq!(total_allowed, c * per_conn_cap);
    assert!(total_allowed > per_conn_cap, "aggregate unstaked throughput exceeds designed single-class cap");
}
```
This demonstrates that the per-connection cap returned by `available_load_capacity_in_throttling_duration` is not reduced or shared as connection count grows, confirming the multiplicative bypass described.
