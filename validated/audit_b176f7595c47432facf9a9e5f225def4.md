### Title
Monopolization of shared per-repository concurrency slots by a single actor causes denial of service for other users - ([File: internal/grpc/middleware/limithandler/middleware.go])

### Summary
Gitaly's concurrency backpressure mechanism (`[[concurrency]]` limiter) scopes its lock key purely by RPC + repository path, with no dimension for the calling user/client identity. A single authenticated (or unauthenticated) actor issuing many concurrent RPCs (e.g. `UploadPackWithSidechannel`, `PostUploadPackWithSidechannel`) against a shared/public repository can consume the entire per-repository concurrency budget and queue capacity, starving all other legitimate users of that same repository, analogous to the "monopolization by a few actors" bug class described in the source report — except here the "bidding" resource is Gitaly's concurrency/queue token pool for a shared repository, and there is no per-actor cooldown or fairness mechanism.

### Finding Description
The concurrency limiter key is computed solely from the request's repository: [1](#0-0) 

This `LimitConcurrencyByRepo` key is the only dimension used to look up (and lazily create) a `keyedConcurrencyLimiter` instance shared by *all* callers targeting that repository/RPC pair: [2](#0-1) 

Within a `keyedConcurrencyLimiter`, admission is governed by two shared semaphores — `concurrencyTokens` (in-flight slots) and `queueTokens` (queue admission), both bounded by `MaxPerRepo`/`MaxConcurrency` and `MaxQueueSize` configured per RPC, not per user: [3](#0-2) [4](#0-3) 

Because admission is strictly a shared counting semaphore with no per-caller quota or "cool-down," a single client can repeatedly issue concurrent calls against the same repository (e.g. rapid clone/fetch bursts), filling both the concurrency slots and the queue before other users' requests arrive. Once `MaxQueueSize` is reached, subsequent legitimate requests from *other* users are immediately rejected with `ResourceExhausted`/`ErrMaxQueueSize`, and requests already queued may additionally be dropped after `MaxQueueWait` via `ErrMaxQueueTime`: [5](#0-4) 

This mirrors the report's bug class: a small number of actors with the ability to issue many rapid operations against a shared resource can monopolize it because the platform has no notion of "cool-down"/per-actor quota — only an aggregate, shared cap. The documentation confirms this design and that the historical rate-limiting alternative (which would have been per-client) was intentionally removed: [6](#0-5) [7](#0-6) 

Additionally, concurrency limiting is entirely opt-in: only `ReplicateRepository` has a hardcoded default limiter; all other RPCs (including the externally reachable pack-transfer RPCs) have no backpressure at all unless an operator explicitly configures `[[concurrency]]` for them: [8](#0-7) 

meaning that on a default/unconfigured Gitaly node, an ordinary user issuing many concurrent fetch/clone/push requests against a popular repository faces no gitaly-side push-back at all, making the monopolization scenario worse in practice.

### Impact Explanation
On deployments where operators do configure per-repo concurrency limits (the recommended hardening per `doc/backpressure.md`), the shared, user-agnostic admission queue still allows a single client to occupy the entire budget for a popular/shared repository, denying service to other legitimate users of that repository (clone/fetch/push failures with `ResourceExhausted`). On unconfigured deployments, there is no protection whatsoever for these RPCs, so the same single-actor flood directly exhausts Gitaly's git-process/goroutine resources for that repository without any queueing backpressure engaging first. This is a availability/DoS impact scoped to a specific repository (and potentially the node, depending on process/resource contention), consistent with "DoS of a handler."

### Likelihood Explanation
Any client capable of issuing multiple concurrent RPCs against the same repository (a standard capability for any authenticated user with read/fetch access, or an unauthenticated client on RPCs that permit anonymous access) can trigger this without any special privilege, MITM, or malicious-peer assumption — it purely depends on the existing repo-scoped, non-per-user admission logic. This makes the likelihood high wherever a repository receives traffic from multiple independent users (e.g., a busy shared/public/group repository), which is a normal, expected access pattern rather than an edge case.

### Recommendation
- Extend the concurrency-limiter lock key (`GetLockKey`) to incorporate caller identity (e.g., authenticated user/token identity or, for unauthenticated calls, remote IP) in addition to repository and RPC, similar to how `PackObjectsHookWithSidechannelRequest`'s `remote_ip` field is already used as an additional dimension for pack-objects limiting.
- Introduce a per-actor sub-quota or fair-queueing discipline within the per-repository queue (e.g., round-robin/weighted fairness across distinct callers, or a maximum number of concurrently queued requests per caller) so that one caller cannot occupy the full `MaxQueueSize`/`MaxConcurrency` budget for a shared repository.
- Consider providing safe, documented defaults for concurrency limiting on high-traffic externally reachable RPCs (upload-pack/receive-pack family) rather than requiring explicit opt-in configuration, so unconfigured nodes are not fully unprotected.

### Proof of Concept
1. Configure (or note the absence of) `[[concurrency]]` for `/gitaly.SmartHTTPService/PostUploadPackWithSidechannel` with `max_per_repo = N` and `max_queue_size = M` as shown in `doc/backpressure.md`.
2. As a single authenticated user with fetch access to a shared repository "A", issue `N + M + 1` concurrent `PostUploadPackWithSidechannel`/`UploadPackWithSidechannel` calls against repository "A" (e.g. parallel `git clone`/`git fetch` invocations), keeping them in flight (analogous to `TestUnaryLimitHandler`/`TestConcurrencyLimitHandlerMetrics` which demonstrate the shared-key queue filling behavior: [9](#0-8) ).
3. While these are still in flight, have a second, unrelated user attempt a normal fetch/clone against the same repository "A" — because the lock key is `repository.relative_path` only, this request is queued behind/rejected alongside the first user's flood and receives `ResourceExhausted` (`ErrMaxQueueSize`) once the shared queue for that repo/RPC is full, or is delayed until `MaxQueueWait` expires.
4. Repeat against an unconfigured RPC (no `[[concurrency]]` entry) to show no backpressure engages at all, per the fallback logic in `WithConcurrencyLimiters`/`limithandler.New` (only `ReplicateRepository` gets a default limiter).

// acquire tries to acquire the semaphore. It may fail if the admission queue is full or if the max
// queue-time ticker ticks before acquiring a concurrency token.
func (sem *keyedConcurrencyLimiter) acquire(ctx context.Context, limitingKey string) (returnedErr error) {
	if sem.queueTokens != nil {
		// Try to acquire the queueing token. The queueing token is used to control how many
		// callers may wait for the concurrency token at the same time. If there are no more
		// queueing tokens then this indicates that the queue is full and we thus return an
		// error immediately.
		if err := sem.queueTokens.TryAcquire(); err != nil {
			return err
		}
		// We have acquired a queueing token, so we need to release it if acquiring
		// the concurrency token fails. If we succeed to acquire the concurrency
		// token though then we retain the queueing token until the caller signals
		// that the concurrency-limited function has finished. As a consequence the
		// queue token is returned together with the concurrency token.
		//
		// A simpler model would be to just have `maxQueueLength` many queueing
		// tokens. But this would add concurrency-limiting when acquiring the queue
		// token itself, which is not what we want to do. Instead, we want to admit
		// as many callers into the queue as the queue length permits plus the
		// number of available concurrency tokens allows.
		defer func() {
			if returnedErr != nil {
				sem.queueTokens.Release()
			}
		}()
	}

	// We are queued now, so let's tell the monitor. Furthermore, even though we're still
	// holding the queueing token when this function exits successfully we also tell the monitor
	// that we have exited the queue. It is only an implementation detail anyway that we hold on
	// to the token, so the monitor shouldn't care about that.
	sem.monitor.Queued(ctx, limitingKey, sem.queueLength())
	defer sem.monitor.Dequeued(ctx)

	if sem.maxQueueWait != 0 {
		if sem.setWaitTimeoutContext != nil {
			ctx = sem.setWaitTimeoutContext()
		} else {
			var cancel context.CancelFunc
			ctx, cancel = context.WithTimeout(ctx, sem.maxQueueWait)
			defer cancel()
		}
	}

	// Try to acquire the concurrency token now that we're in the queue.
	return sem.concurrencyTokens.Acquire(ctx)
}

type ConcurrencyLimiter struct {
	// limit is the adaptive maximum number of concurrent calls to the limited function. This limit is
	// calculated adaptively from an outside calculator.

	// This limit is global and applies before the concurrency limit. Subsequent incoming

	// SetWaitTimeoutContext is a function for setting up timeout context. If this is nill, context.WithTimeout is
	// used. This function is for internal testing purpose only.
	SetWaitTimeoutContext func() context.Context

	// calls.

	// and will get evicted once there are no concurrency-limited calls for any such key

# Request limiting in Gitaly

In the GitLab ecosystem, Gitaly is the service that is at the bottom of the
stack for Git data access. This means that when there is a surge of
requests to retrieve or change a piece of Git data, the I/O happens in Gitaly.
This can lead to Gitaly being overwhelmed due to system resource exhaustion
because all Git access goes through Gitaly.

If there is a surge of traffic beyond what Gitaly can handle, Gitaly should
be able to push back on the client calling. Gitaly shouldn't subserviently agree
to process more than it can handle.

We employ concurrency limiting as our primary backpressure mechanism in Gitaly.
```

```markdown
An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
