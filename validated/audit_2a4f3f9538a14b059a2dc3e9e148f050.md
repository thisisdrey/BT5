### Title
Unbounded stream-slot occupation via sub-timeout drip-feeding in QUIC packet reassembly - ([File: streamer/src/nonblocking/quic.rs])

### Summary
`handle_connection` reads chunks with a per-read `tokio::time::timeout(wait_for_chunk_timeout, stream.read_chunks(...))` that is re-armed on every successful (even 1-byte) read, rather than being bounded by a total stream lifetime. An unstaked attacker can open up to `QUIC_MAX_UNSTAKED_CONCURRENT_STREAMS` (128) uni streams per connection and, on each, send a single byte every `wait_for_chunk_timeout - ε`, keeping every stream perpetually "active" and never completing a packet.

### Finding Description
In `handle_connection` (streamer/src/nonblocking/quic.rs:647-707), the inner loop reads chunks via: [1](#0-0) 
and only breaks the loop on a read error or on `wait_for_chunk_timeout` elapsing with zero bytes received. This timeout is reset every time any bytes are received, as confirmed by the existing regression test `test_quic_stream_timeout`, which sends one byte then waits `DEFAULT_WAIT_FOR_CHUNK_TIMEOUT * 2` for the timeout to fire only because no further byte is sent: [2](#0-1) 
There is no cap on total elapsed time for a single stream/packet's reassembly (`accum.start_time`/`LATE_REASSEMBLY_THRESHOLD` at streamer/src/nonblocking/quic.rs:805-813 only records a stat, it never aborts the stream), and no per-stream byte-rate/backoff enforcement.

Stream-count throttling (`throttle_stream` in streamer/src/nonblocking/stream_throttle.rs:233-271) only rate-limits how many *new* streams are opened per `STREAM_THROTTLING_INTERVAL`; it does not limit how long an already-open stream may remain half-read. The QUIC transport's `max_concurrent_uni_streams` (set in `swqos.rs::cache_new_connection`, streamer/src/nonblocking/swqos.rs:198-224) caps concurrently open streams per connection (e.g., 128 for unstaked, scaled by RTT) but does not prevent those slots from being held indefinitely by drip-feeding. The connection-level `max_idle_timeout` (`QUIC_MAX_TIMEOUT` = 30s, streamer/src/quic.rs:38,120) is reset by any traffic on the connection, so a byte sent just under `wait_for_chunk_timeout` (default likely well under 30s) keeps the whole connection alive indefinitely, not just the individual stream.

Consequently, an attacker can occupy up to `max_concurrent_uni_streams` reassembly slots (each with its own `PacketAccumulator`/`stream_counter` entry counted against `qos.max_concurrent_connections()`/QoS state) per connection, across up to `max_connections_per_unstaked_peer` connections, indefinitely, for near-zero bandwidth (1 byte per stream per `wait_for_chunk_timeout`).

### Impact Explanation
This is a resource-exhaustion / QoS-evasion issue: legitimate senders competing for the same fixed per-connection uni-stream budget and per-IP connection budget can be starved because slots are held by attacker streams that never deliver a parseable transaction and thus never contribute fee-paying work. It falls under "grossly underpriced pre-fee work" / QoS evasion — cheap drip-fed streams consume server-side buffering and per-connection stream-count budget disproportionate to the near-zero bytes transferred. It does not cause a panic, deadlock, or unbounded (unbounded in the strict sense) memory growth since streams are capped by `max_concurrent_uni_streams` and connections by `max_concurrent_connections()`/per-IP limits, so the blast radius is bounded to those configured caps, not truly unbounded.

### Likelihood Explanation
Feasible for any unstaked remote attacker with no elevated privileges — it only requires controlling per-byte send timing on the QUIC client, which is fully within an ordinary client's capability (e.g., using `quinn`/raw socket with a custom pacer). It is repeatable and sustainable as long as the attacker maintains the drip cadence; it costs the attacker very little (one packet per stream per timeout window) while consuming a full stream slot for the whole duration.

### Recommendation
Enforce a hard maximum wall-clock duration for a stream to complete reassembly, independent of chunk arrival cadence, e.g., track `accum.start_time` (already present) and break/close the stream once `accum.start_time.elapsed()` exceeds a fixed bound (e.g., a small multiple of RTT, matching the already-computed `LATE_REASSEMBLY_THRESHOLD` semantics, but making it an enforced cutoff rather than only a stat), regardless of how often bytes are trickling in. Alternatively/additionally, apply a minimum required byte-rate per stream (bytes received / elapsed time) and close the stream if it falls below a threshold, so drip-feeding below a legitimate transaction transfer rate no longer holds the slot.

### Proof of Concept
```rust
// streamer/src/nonblocking/quic.rs (extend existing test module)
#[tokio::test(flavor = "multi_thread")]
async fn test_quic_drip_feed_holds_stream_indefinitely() {
    agave_logger::setup();
    let SpawnTestServerResult { join_handle, receiver, server_address, stats, cancel } =
        setup_quic_server(None, QuicStreamerConfig::default_for_tests(), SwQosConfig::default());

    let conn1 = make_client_endpoint(&server_address, None).await;
    let mut s1 = conn1.open_uni().await.unwrap();

    let chunk_interval = DEFAULT_WAIT_FOR_CHUNK_TIMEOUT.mul_f32(0.8);
    let observation_window = DEFAULT_WAIT_FOR_CHUNK_TIMEOUT * 20; // far exceeds any single-chunk timeout
    let start = std::time::Instant::now();
    while start.elapsed() < observation_window {
        // never send enough bytes to exceed max_stream_data_bytes / complete a valid packet,
        // never send FIN
        s1.write_all(&[0u8]).await.unwrap_or_default();
        sleep(chunk_interval).await;
    }

    // Assertion expressing the bug: after an arbitrarily long observation window,
    // the stream is STILL counted active and NO read timeout / forced close occurred,
    // demonstrating the slot was held indefinitely for ~1 byte per chunk_interval.
    assert_eq!(stats.active_streams.load(Ordering::Relaxed), 1);
    assert_eq!(stats.total_stream_read_timeouts.load(Ordering::Relaxed), 0);

    cancel.cancel();
    drop(receiver);
    join_handle.await.unwrap();
}
```
Expected fix behavior: after the recommended hard per-stream duration cap, the assertions above should instead show `active_streams == 0` and a new "forced timeout due to exceeding max reassembly duration" stat incremented, regardless of the drip cadence used by the attacker.
