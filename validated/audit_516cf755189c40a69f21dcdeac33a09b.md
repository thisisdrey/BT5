### Title
Attacker can permanently block a victim from depositing new collateral types and minting new synths by dust-filling the `MAX_TOKENS_PER_USER` account token lists - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
`Pool` caps the combined size of a user's `depositTokensOfAccount` + `debtTokensOfAccount` lists at `MAX_TOKENS_PER_USER = 30`. Entries are added automatically and permissionlessly whenever a `DepositToken` balance goes from 0 to positive (deposit, transfer, or liquidation `seize`), and entries are only removed when the balance returns to exactly zero. An unprivileged attacker can push dust amounts of every whitelisted `DepositToken` to a victim, filling all 30 slots. After that, every operation that would add a *new* token type to the victim's account — `deposit` of a new collateral, `transfer`/`transferFrom` of a new deposit token, `mint`/`issue` of a new debt token, and `liquidate`/`seize` of a collateral the victim doesn't already hold — reverts with `UserReachedMaxTokens`, because the revert propagates through `DepositToken._transfer`/`_mint` and `DebtToken._mint`. This is a pure availability attack (same class as CVE-2024-21062: hang/DoS of a core component), not a value-transfer or oracle issue.

### Finding Description
- `Pool.onlyIfAdditionWillNotReachMaxTokens` reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` (`contracts/Pool.sol:143-148`).
- `DepositToken._transfer` calls `pool.addToDepositTokensOfAccount(recipient_)` whenever the recipient's balance transitions 0 → positive (`contracts/DepositToken.sol:517-520`); same hook on mint (`contracts/DepositToken.sol:486-488`). `DebtToken._mint`/`issue` do the same for `debtTokensOfAccount`.
- Removal only happens when the sender's balance hits exactly 0 (`contracts/DepositToken.sol:523-525`); there is no user-facing "remove token" function — `removeFromDepositTokensOfAccount`/`removeFromDebtTokensOfAccount` are callable only by the token contracts (`contracts/Pool.sol:618-634`).
- To clear an attacker-added slot, the victim must transfer the dust out, but `transfer`/`transferFrom` are gated by the lock check (`_revertIfLocked`/`unlockedBalanceOf`, `NotEnoughFreeBalance` in `contracts/DepositToken.sol`). When the victim's position is fully locked (all collateral needed to stay healthy), every unit of every deposit token — including attacker-deposited dust — is locked, so the victim cannot evict the entries at all while debt exists.
- The attacker can also use `seize` during liquidation or just EOA transfers; nothing in `SynthContext`/`onlyIfDepositTokenExists`/`whenNotShutdown`/`nonReentrant` blocks it — the modifier set does not distinguish "wanted" vs "unwanted" token additions.

### Impact Explanation
Temporary-to-persistent denial of service on the victim's position management:
- While the list is full and the dust is locked, the victim cannot deposit a *different* collateral type to deleverage or restore health — a standard defense against liquidation is disabled, leading to avoidable liquidation losses.
- The victim cannot mint a new synthetic type (`issue`/`mint` adds a debt-token entry → revert) and cannot receive any new deposit token via transfer or liquidation proceeds.
- For a fully-locked position this persists until the debt is repaid or the position is liquidated; for a healthy position the victim can eject dust one token at a time (costly, and the attacker can refill for the price of dust transfers — asymmetric cost favoring the attacker).

### Likelihood Explanation
High feasibility: the attack requires no privileged role, no oracle manipulation, and no flash loan. The attacker only needs to hold (or buy on the open market) dust amounts of the whitelisted deposit tokens and call `transfer(victim, dust)` on each `DepositToken` — or deposit the dust themselves and transfer. Each deposit token is itself an ERC-20 that anyone holding a balance can send. Cost is bounded by ~30 tiny transfers. The main limitation is that existing deposited collateral is not frozen — `withdraw` still works — so the impact is blocked functionality and forced-liquidation exposure rather than direct theft, which caps severity at Medium, matching the source CVE's availability-only classification.

### Recommendation
- Track deposit/debt token membership per account differently, e.g. let users opt out: add a `forfeitDepositToken(token)`/`forfeitDebtToken`-style user-facing removal that burns/redirects dust, or skip `addToDepositTokensOfAccount` for amounts below a minimum-dust threshold.
- Alternatively, don't include deposit-token entries in the cap when the balance is below a configured floor, or replace the revert in `addToDepositTokensOfAccount` with a graceful no-op for *received* transfers (count only tokens the user actively deposited as collateral), so forced receipts can't exhaust the quota.

### Proof of Concept
Hardhat fork sketch (test harness at `test/Pool.test.ts` shows the revert path is already exercised against `UserReachedMaxTokens`):

```typescript
// victim has an open position: deposited msdWETH, minted msUSD debt near the lock limit
const victim = ...; // underwater-risk account
const depositTokens: IDepositToken[] = /* all tokens from pool.getDepositTokens() */;

// attacker fills the victim's token list with 1-wei dust of each deposit token
for (const dt of depositTokens) {
  const erc20 = await ethers.getContractAt('IERC20', await dt.underlying());
  await erc20.connect(attacker).approve(dt.address, 1);
  await dt.connect(attacker).deposit(1);          // mints msdX to attacker
  await dt.connect(attacker).transfer(victim.address, 1); // adds entry for victim
}
expect(await pool.getDepositTokensOfAccount(victim.address)).to.have.lengthOf(30);

// 1) victim cannot deposit a NEW collateral type to improve health
await expect(
  newDepositToken.connect(victim).deposit(depositAmount)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 2) victim cannot mint a NEW synthetic (would add a debt-token entry)
await expect(
  pool.connect(victim).mint(otherSynthetic, amount, victim.address)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// 3) while position is fully locked, victim cannot even eject the dust
await expect(
  depositTokens[0].connect(victim).transfer(attacker.address, 1)
).to.be.revertedWithCustomError(depositTokens[0], 'NotEnoughFreeBalance');
```

Uncertainty: steps (2)–(3) depend on the exact `unlockedBalanceOf`/`_revertIfLocked` semantics and which token types already occupy the victim's list; the revert itself for new-token additions is confirmed by the existing unit test (`test/Pool.test.ts:1386-1416`). A fork run is needed to confirm the "locked victim cannot clear slots" branch against live mainnet state.
