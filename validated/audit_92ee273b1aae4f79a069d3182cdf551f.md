### Title
Stale yanked-version data trusted indefinitely under default `--lockfile_mode=update` - (docs/external/lockfile.mdx)

### Summary
Bazel's Bzlmod lockfile records `selectedYankedVersions` as "mutable information" alongside immutable, hash-pinned `registryFileHashes`. The documentation states that in the default `update` lockfile mode, "Bazel also avoids refreshing mutable information, such as yanked versions, for dependencies that haven't changed," and this data is only ever re-fetched in `refresh` mode (roughly hourly) or explicitly via `bazel mod deps --lockfile_mode=refresh`.

### Finding Description
Yanked-version status is the closest thing Bzlmod has to a registry "oracle" indicating a module release is known-bad (e.g., discovered to be malicious or broken) and should not be silently consumed. Per the docs, once a module version's yanked status has been resolved and recorded (or implicitly recorded as "not yanked") in `MODULE.bazel.lock`, the default `update` mode will not re-check the registry for that dependency again as long as nothing else about it changed. Only `refresh` mode re-polls (hourly), and `error`/`off` modes never touch the network for this data either. [1](#0-0) 

### Impact Explanation
If a registry maintainer later yanks a module version (e.g., after discovering it is compromised, malicious, or broken), consumers who already resolved and locked that version under `update` mode will not learn about the yank on subsequent builds — the lockfile's cached, stale "not yanked" state is trusted indefinitely. This is analogous to the reported "no check for oracle staleness" bug: a security-relevant piece of external state (freshness of yanked/allow status) is cached without a staleness bound in the default operating mode, so builds keep silently trusting outdated information rather than re-verifying it.

### Likelihood Explanation
This requires no attacker foothold beyond being able to publish/maintain (or compromise) a module version in a registry that a victim already depends on — consistent with the allowed "unprivileged, publishes content a victim's build consumes" threat model. It occurs by default because `update` is the default `--lockfile_mode`, and most CI/dev workflows never invoke `refresh` or `bazel mod deps --lockfile_mode=refresh` explicitly.

lockfile. The available modes are:

*   `update` (Default): Use the information that is present in the lockfile to
    skip downloads of known registry files and to avoid re-evaluating extensions

*   `refresh`: Like `update`, but mutable information is always refreshed when
    switching to this mode and roughly every hour while in this mode.
*   `error`: Like `update`, but if any information consulted during resolution
    is missing or out-of-date, Bazel will fail with an error. This mode never
    changes the lockfile or performs network requests during resolution. Module
    extensions that marked themselves as `reproducible` may still perform
    network requests, but are expected to always produce the same result. Note
    that superfluous information is ignored, not reported, so a lockfile that
    passes in this mode may nevertheless be rewritten (pruned) by `update`.
*   `off`: The lockfile is neither checked nor updated.
