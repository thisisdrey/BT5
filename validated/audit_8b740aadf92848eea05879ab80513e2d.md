The `TrieKey` enum is `#[repr(u8)]` with `#[borsh(use_discriminant = true)]`, and every variant's serialization unconditionally pushes its own fixed column byte first (e.g. `col::CONTRACT_DATA = 9` for `ContractData`, `col::ACCESS_KEY = 2` for `AccessKey`, `col::ACCOUNT = 0` for `Account`) before any attacker-controlled bytes are appended. [1](#0-0) 

That leading byte is emitted by the `ContractData` match-arm code path itself, not derived from the attacker-supplied `key: Vec<u8>` — the `key` bytes are only appended after the column byte, the `account_id` bytes, and the `ACCOUNT_DATA_SEPARATOR`. [2](#0-1) 

Since `deploy_deterministic_account` always constructs `TrieKey::ContractData { account_id, key }` for entries from `state_init.data()`, the raw trie key always begins with the fixed `col::CONTRACT_DATA` byte (9) regardless of what bytes the attacker puts in `key`. [3](#0-2) 

It is therefore structurally impossible for a `ContractData` entry to serialize to the same raw byte sequence as `TrieKey::AccessKey` (column 2), `TrieKey::Account` (column 0), or any other reserved-namespace `TrieKey` variant belonging to the same account — the column-byte prefix, not the key content, always determines which logical trie region a record maps into. The `data()` map is also a `BTreeMap<Vec<u8>, Vec<u8>>`, so within the `ContractData` namespace itself there is no possibility of two different logical keys colliding into one write either. [4](#0-3)
