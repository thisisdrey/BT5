### Title
Rewards emitted while token supply is zero are permanently lost in `RewardsDistributor` - ([File: contracts/RewardsDistributor.sol](https://github.com/Loderfordw/metronome-synth-public--023/blob/main/contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor._calculateTokenIndex` always advances `tokenStates[token].timestamp` to `block.timestamp` whenever `speed > 0`, even when `token_.totalSupply() == 0` and the accrual ratio is forced to `0`. All reward tokens notionally emitted during zero-supply windows (`_deltaTimestamps * _speed`) are therefore consumed from the emission schedule but credited to no one, leaving them permanently locked in the contract — the same bug class as the `BathBuddy` "rewards lost for initial period" finding. [1](#0-0) 

### Finding Description
`updateTokenSpeed` (or the keeper-driven `syncTokenSpeed`) sets `tokenSpeeds[token]` and stamps `tokenStates[token] = {index: INITIAL_INDEX, timestamp: block.timestamp}` when the token is first added. [2](#0-1) 

On every subsequent index update, `_calculateTokenIndex` computes:

```solidity
uint256 _deltaTimestamps = block.timestamp - uint256(_supplyState.timestamp);
if (_deltaTimestamps > 0 && _speed > 0) {
    uint256 _totalSupply = token_.totalSupply();
    uint256 _tokensAccrued = _deltaTimestamps * _speed;
    uint256 _ratio = _totalSupply > 0 ? _tokensAccrued.wadDiv(_totalSupply) : 0;
    _newIndex = (_supplyState.index + _ratio).toUint224();
    _newTimestamp = block.timestamp.toUint32();
}
```

When `totalSupply == 0`, `_ratio` is `0` but `_newTimestamp` is still set to `block.timestamp`, and `_updateTokenIndex` persists it. The `_tokensAccrued` for that window are dropped entirely — no account index can ever claim them because a new participant's `accountIndexOf` is initialized to the current index (`_accountIndex = INITIAL_INDEX` fallback only covers the initial index, not zero-supply drift). [3](#0-2) [4](#0-3) 

Two realistic zero-supply windows exist:

1. **Before the first deposit/mint**: rewards are activated via `updateTokenSpeed`/`syncTokenSpeed` while the `DepositToken`/`DebtToken` has zero supply. Every second until the first mint burns `speed` reward tokens.
2. **After full exit**: all holders withdraw/repay so `totalSupply` returns to 0 while `speed` remains non-zero (the governor/keeper has not yet set it to 0, or `syncTokenSpeed` hasn't been called because `periodFinish` passed but speed was never zeroed). All emissions during that window are lost.

Unlike `BathBuddy`, index updates here are permissionless: `updateBeforeMintOrBurn` "may be called by anyone to update stored indexes" and `claimRewards` is public, so any EOA can advance the timestamp and finalize the loss — but the loss also accrues passively with time, no attacker required. [5](#0-4) 

### Impact Explanation
Reward tokens emitted during zero-supply periods are permanently frozen in the `RewardsDistributor` contract. `_transferRewardIfEnoughTokens` only pays out `tokensAccruedOf[account]`, which is bounded by index deltas — the dropped `_tokensAccrued` are never added to any account and there is no sweep/recovery function in the contract. This is permanent freezing of unclaimed yield, matching the BathBuddy impact where half the reward amount was stuck. [6](#0-5) 

### Likelihood Explanation
Certain to occur in normal operation: rewards are typically configured (`updateTokenSpeed` by governor or `syncTokenSpeed` by the keeper reading Vesper `rewardRates`) before or independent of user deposits, and every gap between reward activation and first mint — and every period where all positions exit while speed is non-zero — burns `speed * gap` reward tokens. Triggering/finalizing the loss requires no privilege (public `updateBeforeMintOrBurn`/`claimRewards`).

### Recommendation
Do not advance `tokenStates[token].timestamp` when `totalSupply == 0`; equivalently, only start/resume accrual once supply is non-zero. Change `_calculateTokenIndex` so the zero-supply branch returns the old timestamp (or returns `_newTimestamp = _supplyState.timestamp`), so paused emissions resume rather than being burned. Alternatively, defer setting `tokenStates[token].timestamp` until the first `updateBeforeMintOrBurn` observes `totalSupply() > 0`, mirroring the BathBuddy recommendation of starting the cycle when the first participant joins.

### Proof of Concept
Hardhat-style test (mirrors the existing `test/RewardDistributor.test.ts` setup with mocked `msdTOKEN1`):

```ts
it('loses rewards emitted while totalSupply == 0', async function () {
  const speed = parseEther('1') // 1 reward token per second
  await rewardDistributor.updateTokenSpeed(msdTOKEN1.address, speed)

  // No participants yet
  msdTOKEN1.totalSupply.returns(0)
  msdTOKEN1.balanceOf.returns(0)

  // Half the reward window passes with zero supply
  await increaseTimeOfNextBlock(5000)

  // Anyone (or the DepositToken hook on Alice's first mint) updates the index
  await rewardDistributor.updateBeforeMintOrBurn(msdTOKEN1.address, alice.address)

  // Alice mints and is the sole holder for the second half of the window
  msdTOKEN1.totalSupply.returns(parseEther('100'))
  msdTOKEN1.balanceOf.returns(parseEther('100'))
  await increaseTimeOfNextBlock(5000)

  await rewardDistributor['claimRewards(address)'](alice.address)

  // Alice only receives the second half; the first 5000e18 reward tokens
  // are permanently stuck in the distributor
  expect(await rewardToken.balanceOf(alice.address)).eq(parseEther('5000'))
  expect(await rewardToken.balanceOf(rewardDistributor.address)).eq(parseEther('5000'))
})
```

The key assertion is that the distributor retains `speed * zeroSupplyDuration` tokens that no account index can ever reach, since Alice's `accountIndexOf` was set to the post-gap index at her first update.

    function _updateTokenSpeed(
        IERC20 token_,
        uint256 newSpeed_
    ) private onlyIfDistributorExists onlyIfTokenExists(address(token_)) {
        uint256 _currentSpeed = tokenSpeeds[token_];
        if (_currentSpeed > 0) {
            _updateTokenIndex(token_);
        } else if (newSpeed_ > 0) {
            // Add token to the list
            if (tokenStates[token_].index == 0) {
                if (tokens.length == MAX_REWARD_TOKENS) revert ReachedMaxRewardTokens();
                tokenStates[token_] = TokenState({index: INITIAL_INDEX, timestamp: block.timestamp.toUint32()});
                tokens.push(token_);
            } else {
                // Update timestamp to ensure extra interest is not accrued during the prior period
                tokenStates[token_].timestamp = block.timestamp.toUint32();
            }
        }

        if (_currentSpeed != newSpeed_) {
            tokenSpeeds[token_] = newSpeed_;
            emit TokenSpeedUpdated(token_, _currentSpeed, newSpeed_);
        }
    }
