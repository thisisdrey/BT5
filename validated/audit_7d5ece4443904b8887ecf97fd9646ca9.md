Confirmed: for `FetchIntoObjectPool` and `LinkRepositoryToObjectPool`, the `target_repository` used for both auth-scoping and the `LimitConcurrencyByRepo` lock key ( [1](#0-0) ) resolves to the **shared object pool's** relative path, not the caller's own fork. This is the key structural analog to the Omnipool bug: the write operation is keyed on a shared resource identity (`ObjectPool.Repository`) that is not exclusively "owned" by the caller, yet any fork member can drive requests that key on it — same shape as `depositFor(_depositFor)` writing into `lastTransactionBlock[_depositFor]`, where the caller supplies the identity used for a shared, contended lock/queue rather than an identity representing themselves alone.

### Title
Object-pool concurrency-queue exhaustion via attacker-controlled pool-repository key lets a fork member DoS all sibling forks' pool-mutating RPCs - (File: internal/grpc/middleware/limithandler/middleware.go, internal/grpc/middleware/requestinfohandler/requestinfohandler.go)

### Summary
Gitaly's per-repository concurrency limiter (`[[concurrency]]` in config, enforced by `LimiterMiddleware`) queues and throttles RPCs using a lock key computed by `LimitConcurrencyByRepo`, which reads `requestinfohandler.RequestInfo.Repository` — the RPC's `target_repository`-annotated field [2](#0-1) . For object-pool RPCs such as `FetchIntoObjectPool` and `LinkRepositoryToObjectPool`, the target repository resolved for this purpose is the **object pool repository itself** (`ObjectPool.Repository`), not the calling fork [1](#0-0) . An object pool is shared across an entire fork network: every fork that participates in deduplication invokes RPCs that resolve to the same pool repository path as their "target," analogous to how `depositFor(_amountIn, _depositFor, _minLpReceived)` lets any caller pick the identity (`_depositFor`) whose shared `lastTransactionBlock[...]` state gets written, even though the caller isn't that identity.

### Finding Description
The concurrency limiter's admission queue (`sem.queueTokens`) and in-flight semaphore (`sem.concurrencyTokens`) are both keyed per `limitingKey` returned by `getConcurrencyLimit`/`putConcurrencyLimit` in `internal/limiter/concurrency_limiter.go` [3](#0-2) . That key comes from `LimitConcurrencyByRepo`, which is just `info.Repository.GetRelativePath()` [2](#0-1) , and `info.Repository` for pool-scoped RPCs is populated from `ObjectPool.Repository` via the `TargetRepo` extension resolution in `requestinfohandler.extractRequestInfo` [4](#0-3) .

Because any member project of a fork network is authorized (via its own membership) to invoke `FetchIntoObjectPool`/`LinkRepositoryToObjectPool` naming the shared pool as `ObjectPool.Repository`, an attacker who controls (or forks into) one member of the network can repeatedly issue such calls. Every call queues against the *same* `limitingKey` (the pool's relative path) regardless of which fork issued it — exactly like the Omnipool bug, where the attacker supplies the key (`_depositFor`, here "pool repository") that indexes a shared, limited resource used by other, unrelated parties (other fork owners) for their own legitimate operations.

### Impact Explanation
If `[[concurrency]]` is configured for `/gitaly.ObjectPoolService/FetchIntoObjectPool` or `LinkRepositoryToObjectPool` with `max_queue_size`/`max_queue_wait` (as documented in `doc/backpressure.md` [5](#0-4) ), a low-privilege member of a fork network can flood requests keyed to the pool's relative path, filling `max_queue_size` and causing `ErrMaxQueueSize`/`ErrMaxQueueTime` (`internal/limiter/concurrency_limiter.go`, lines 219-233) for other legitimate fork members' pool-maintenance or fetch-into-pool operations. This is a availability/DoS impact against other tenants sharing the same object pool, which they cannot avoid since pool membership (and thus contention exposure) is inherent to being part of the fork network — not something the victim opted into per-request.

### Likelihood Explanation
Medium: exploitation requires (a) the operator to have configured `[[concurrency]]` limits scoped to these object-pool RPCs, and (b) an attacker owning or controlling at least one fork in a shared pool with other, higher-value victim forks. Both conditions are realistic in a large-scale multi-tenant GitLab.com-style deployment where object pools are heavily used for public fork networks, making this a plausible, low-cost griefing vector against unrelated repository owners sharing the pool.

### Recommendation
- Scope the concurrency-limiting key for pool-mutating RPCs to the *caller's own repository* (the fork issuing the request) rather than the shared `ObjectPool.Repository`, or use a composite key `(pool, caller-repository)` so that flooding from one fork cannot exhaust the queue slot budget for other unrelated forks.
- Alternatively, apply a per-caller-repository rate/queue budget in addition to (not instead of) the pool-wide limit, so no single fork can consume the entire queue capacity intended for the whole pool.
- Audit other RPCs where `requestinfohandler.extractRequestInfo`'s `TargetRepo` resolution can point to a shared resource (object pools, `sourceRepository` in `CreateFork`/`FetchSourceBranch`) to confirm none of them allow one authorized-but-unrelated caller to exhaust concurrency slots intended for another caller's legitimate use of that shared resource.

### Proof of Concept
1. Configure Gitaly with a `[[concurrency]]` limit for `/gitaly.ObjectPoolService/FetchIntoObjectPool` with a small `max_queue_size` (e.g., 5) as shown in `doc/backpressure.md`.
2. Set up a shared object pool `P` with fork network members `A` (victim) and `M` (attacker-controlled fork), both authorized to call `FetchIntoObjectPool`/`LinkRepositoryToObjectPool` naming pool `P`.
3. From `M`, issue `max_queue_size` concurrent slow `FetchIntoObjectPool` calls targeting `ObjectPool.Repository = P` — each resolves to `limitingKey = P.RelativePath` per `LimitConcurrencyByRepo`.
4. `A` then issues a legitimate `FetchIntoObjectPool` call for pool `P`; it is queued behind `M`'s calls and, once `max_queue_size` is reached, receives `ErrMaxQueueSize` (structured `RESOURCE_EXHAUSTED` error), denying `A`'s legitimate pool operation despite `A` not exceeding any limit tied to its own identity.

// getConcurrencyLimit retrieves the concurrency limit for the given key. If no such limiter exists
// it will be lazily constructed.
func (c *ConcurrencyLimiter) getConcurrencyLimit(limitingKey string) *keyedConcurrencyLimiter {
	c.m.Lock()
	defer c.m.Unlock()

	if c.limitsByKey[limitingKey] == nil {
		// Set up the queue tokens in case a maximum queue length was requested. As the
		// queue tokens are kept during the whole lifetime of the concurrency-limited
		// function we add the concurrency tokens to the number of available token.
		var queueTokens semaphorer
		if c.maxQueueLength > 0 {
			queueTokens = c.createSemaphore(uint(c.currentLimit() + c.maxQueueLength))
		}

		c.limitsByKey[limitingKey] = &keyedConcurrencyLimiter{
			monitor:               c.monitor,
			maxQueueWait:          c.maxQueueWait,
			setWaitTimeoutContext: c.SetWaitTimeoutContext,
			concurrencyTokens:     c.createSemaphore(uint(c.currentLimit())),
			queueTokens:           queueTokens,
		}
	}

	c.limitsByKey[limitingKey].refcount++

	return c.limitsByKey[limitingKey]
}

## Concurrency queue

Limit the number of concurrent RPCs that are in flight on each Gitaly node for each
repository per RPC using `[[concurrency]]` configuration:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
```

For example:

- One clone request comes in for repository "A" (a largish repository).
- While this RPC is executing, another request comes in for repository "A". Because
  `max_per_repo` is 1 in this case, the second request blocks until the first request
  is finished.

An in-memory queue of requests can build up in Gitaly that are waiting their turn. Because
this is a potential vector for a memory leak, two other values in the `[[concurrency]]`
configuration can prevent an unbounded in-memory queue of requests:

- `max_queue_wait` is the maximum amount of time a request can wait in the
  concurrency queue. When a request waits longer than this time, it returns
  an error to the client.
- `max_queue_size` is the maximum size the concurrency queue can grow for a
  given RPC. If a concurrency queue is at its maximum, subsequent requests
  return with an error. The queue size is per repository.

For example:

```toml
[[concurrency]]
rpc = "/gitaly.SmartHTTPService/PostUploadPackWithSidechannel"
max_per_repo = 1
max_queue_wait = "1m"
max_queue_size = 5
```
