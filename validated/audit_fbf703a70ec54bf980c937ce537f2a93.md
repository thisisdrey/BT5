### Title
Permanent loss of witness block/standby rewards when vote count drops to zero before maintenance-cycle Vi accumulation - (File: consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java)

### Summary
`MaintenanceManager.doMaintenance()` accumulates each witness's reward-per-vote index (`Vi`) once per maintenance cycle using the witness's *current* `voteCount`. If that vote count is zero at the moment of accumulation — which any voter can trigger with an ordinary `WitnessVoteContract` transaction that withdraws all votes from a witness — the reward earned by that witness during the cycle is skipped from the `Vi` index update and can never be attributed to any voter afterward, even though the raw reward was already recorded in `DelegationStore`. This mirrors the Tokemak `AbstractRewarder` bug where reward accounting driven by a "supply" value of `0` silently drops reward accrual, leaving funds unclaimable/locked.

### Finding Description
The new reward algorithm tracks a cumulative reward index `Vi` per witness per cycle: [1](#0-0) 

`accumulateWitnessVi` explicitly skips accumulating any delta into `Vi` when `voteCount == 0`, even if `reward != 0` — it only "forwards" the previous `Vi` unchanged. This is the same root pattern as `rewardPerToken()` in the Tokemak contract returning `rewardPerTokenStored` unchanged when `totalSupply() == 0`.

This function is invoked once per maintenance cycle for every witness using the witness's live vote count, *before* that cycle's vote deltas are applied to the witness capsule: [2](#0-1) 

Meanwhile, block rewards and transaction-fee rewards are paid to the *current block producer* unconditionally, independent of that witness's vote count, and are stored keyed by cycle in `DelegationStore`: [3](#0-2) [4](#0-3) 

Because the active witness set (top-27 producers) is only refreshed at maintenance boundaries, a witness can have all its votes withdrawn (vote count driven to `0` via a normal, unprivileged vote-withdrawal/re-vote transaction) yet continue producing blocks and accruing `payBlockReward`/`payTransactionFeeReward` for the remainder of the cycle. At the next `doMaintenance()`, `accumulateWitnessVi` is called with `voteCount == 0` for that witness, so the reward that was just recorded via `delegationStore.addReward(cycle, witnessAddress, value)` is never converted into a `Vi` delta. Since voter reward computation (`MortgageService.computeReward`) for the new algorithm relies exclusively on the `Vi` delta between cycles, that reward amount becomes permanently unclaimable by anyone, while it still exists as backing liability in the reward pool/`AccountStore` allowance system — i.e., funds are effectively frozen/lost from the protocol's perspective, exactly analogous to the Tokemak scenario where rewards queued while `totalSupply == 0` become undistributable.

The pre-existing (legacy) algorithm has the identical flaw: `MortgageService.computeReward(long cycle, List<Pair<byte[], Long>> votes)` skips any cycle where `totalVote == 0`: [5](#0-4) 

### Impact Explanation
Reward tokens that were already recorded as paid out of the block-reward budget (`getWitnessPayPerBlock()`, transaction fee pool) become permanently non-distributable to any account, since no voter's `Vi`-delta calculation can ever recover them. This is a direct on-chain freezing of protocol reward funds — value is minted/allocated into the delegation reward accounting but can never be withdrawn via `withdrawReward`/`queryReward`, matching the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Triggering only requires an ordinary, unprivileged action: any TRX holder can submit a `WitnessVoteContract` (via `VoteWitnessActuator`/`VoteWitnessProcessor`) to withdraw votes from a witness mid-cycle. If that withdrawal drops the witness's vote count to zero while the witness is still in the active producing set for the remainder of the maintenance cycle (which is normal, since witness set membership is fixed until the next maintenance boundary), the witness continues to earn block/standby/fee rewards that get silently dropped at the next `doMaintenance()` call. This does not require any malicious SR, witness, or node behavior — only a single signed vote transaction from a regular user.

### Recommendation
When `accumulateWitnessVi` (or the legacy `computeReward` cycle-reward path) encounters a cycle where `voteCount == 0` but `reward > 0`, the un-distributed reward must not be silently discarded — it should be carried forward and merged into the next cycle's reward pool for that witness (analogous to Tokemak's fix of rolling unaccounted rewards into the next `notifyRewardAmount` call), or attributed directly to the witness/brokerage allowance instead of the vote-index pool, so no reward becomes permanently unclaimable.

### Proof of Concept
1. Witness `W` has non-zero votes and is in the active top-27 producer set.
2. All voters withdraw their votes from `W` via `VoteWitnessContract` transactions, driving `W.getVoteCount()` to `0`. `W` remains an active producer until the next maintenance cycle (`MaintenanceManager.applyBlock`/`doMaintenance` boundary).
3. `W` continues to produce blocks; each block, `Manager.payReward()` calls `mortgageService.payBlockReward(W, getWitnessPayPerBlock())`, which calls `delegationStore.addReward(curCycle, W, value)` (`MortgageService.payReward`, lines 79-87).
4. At the next maintenance, `MaintenanceManager.doMaintenance()` calls `delegationStore.accumulateWitnessVi(curCycle, W, W.getVoteCount())` with `voteCount == 0` (lines 96-101).
5. Inside `accumulateWitnessVi` (`DelegationStore.java` lines 133-146), since `voteCount == 0`, the `Vi` is only forwarded — the reward accrued in step 3 is never converted into a `Vi` delta.
6. Any future voter delegating to `W` computes rewards via `MortgageService.computeReward(beginCycle, endCycle, accountCapsule)` using `Vi` deltas (lines 199-230); the reward from the zero-vote cycle is absent from any delta and can never be queried/withdrawn by any account, permanently freezing that portion of the reward pool.

  public void accumulateWitnessVi(long cycle, byte[] address, long voteCount) {
    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi
      if (!BigInteger.ZERO.equals(preVi)) { // Zero vi will not be record
        setWitnessVi(cycle, address, preVi);
      }
    } else { // Accumulate delta vi
      BigInteger deltaVi = BigInteger.valueOf(reward)
          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  private void payReward(byte[] witnessAddress, long value) {
    long cycle = dynamicPropertiesStore.getCurrentCycleNumber();
    int brokerage = delegationStore.getBrokerage(cycle, witnessAddress);
    double brokerageRate = (double) brokerage / 100;
    long brokerageAmount = (long) (brokerageRate * value);
    value -= brokerageAmount;
    delegationStore.addReward(cycle, witnessAddress, value);
    adjustAllowance(witnessAddress, brokerageAmount);
  }

  private long computeReward(long cycle, List<Pair<byte[], Long>> votes) {
    long reward = 0;
    for (Pair<byte[], Long> vote : votes) {
      byte[] srAddress = vote.getKey();
      long totalReward = delegationStore.getReward(cycle, srAddress);
      if (totalReward <= 0) {
        continue;
      }
      long totalVote = delegationStore.getWitnessVote(cycle, srAddress);
      if (totalVote == DelegationStore.REMARK || totalVote == 0) {
        continue;
      }
      long userVote = vote.getValue();
      double voteRate = (double) userVote / totalVote;
      reward += voteRate * totalReward;
    }
    return reward;
  }
