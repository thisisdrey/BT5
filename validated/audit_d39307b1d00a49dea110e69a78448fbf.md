### Title
Integer overflow in ValidateMultiSign precompile's array-offset arithmetic causes uncaught exception on-chain - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The `ValidateMultiSign` precompiled contract (address `0x...a`, reachable via a plain `STATICCALL`/`CALL` from any TVM contract) decodes ABI-encoded `bytes[]` signature arrays using `extractBytesArray`/`extractSigArray`, which compute byte offsets with unchecked 32-bit `int` arithmetic derived directly from attacker-controlled calldata words. Similar to the FreeType `tt_var_load_item_variation_store` bug — where offset/size fields taken from untrusted table data are multiplied without overflow checks before being used to index into a buffer — these TRON helpers multiply an attacker-supplied offset by `WORD_SIZE` (32) without any bounds validation, and the result is used directly to slice the raw calldata array.

### Finding Description
`extractBytesArray` and `extractSigArray` in `PrecompiledContracts.java` read a length word and per-item offset words straight from the parsed `DataWord[] words` array, which is fully attacker-controlled call data: [1](#0-0) 

Key points:
- `words[offset].intValueSafe()` and `words[offset + i + 1].intValueSafe()` can each return values up to `Integer.MAX_VALUE` (see `DataWord.intValueSafe()`, which clamps overflow to `Integer.MAX_VALUE` rather than rejecting the input): [2](#0-1) 
- `bytesOffset = words[...].intValueSafe() / WORD_SIZE` can be as large as ~67,108,863.
- The subsequent expression `(bytesOffset + offset + 2) * WORD_SIZE` performs plain `int` multiplication with **no overflow check**, unlike the sibling `isValidAbiEncoding` helper in the same file, which explicitly uses `multiplyExact`/`subtractExact` to guard against overflow: [3](#0-2) 
- Because `bytesOffset` can approach `Integer.MAX_VALUE/32`, multiplying `(bytesOffset + offset + 2)` by 32 silently wraps to a negative (or otherwise unintended) 32-bit value — the same overflow-in-offset-computation bug class as the FreeType HVAR/VVAR/MVAR advisory, just against a Java byte array instead of a font parser buffer.
- `extractBytes` then calls `Arrays.copyOfRange(data, offset, offset + len)` with this corrupted offset: [4](#0-3) 

Critically, in `ValidateMultiSign.execute`, the call to `extractSigArray`/`extractBytesArray` happens **outside** the local `try { ... } catch (Throwable t)` block that only wraps the later permission-check logic: [5](#0-4) 

So a negative/overflowed offset triggers an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` (Java's bounds checks convert the "out-of-bounds read" into an exception rather than actual memory corruption, since Java arrays are always bounds-checked — this differs from the C-based FreeType root cause but the *triggering condition* — unchecked integer overflow in offset math derived from untrusted length/offset fields — is identical). This exception propagates out of `contract.execute(data)` back into `Program.callToPrecompiledAddress`, which does not wrap the call in its own try/catch: [6](#0-5) 

By contrast, `BatchValidateSign.execute` explicitly wraps the equivalent logic in `try { return doExecute(data); } catch (Throwable t) { ... return Pair.of(true, new byte[WORD_SIZE]); }`, showing the developers were aware such exceptions can occur and intentionally guarded against them for that precompile but not for `ValidateMultiSign`: [7](#0-6) 

### Impact Explanation
Any unprivileged account can invoke this precompile from a deployed contract with crafted calldata that produces an integer-overflowing offset in `extractBytesArray`/`extractSigArray`. Because the resulting exception is not caught inside `ValidateMultiSign.execute` nor in `Program.callToPrecompiledAddress`, it depends on how far up the call stack a generic `RuntimeException` is caught during transaction execution — if it is not uniformly caught as a normal VM revert path (unlike the dedicated `Program.Exception` subclasses used elsewhere in this file, e.g. `Program.Exception.notEnoughTime`), this is a live path for unhandled exceptions to escape precompile execution and disrupt transaction processing for every full node validating the block (since execution is deterministic, all honest nodes hit the same exception), which is a shared/consensus-visible fault rather than an isolated one. At minimum this is a reliable way to make an entire class of transactions revert unexpectedly / fail broadcaster expectations; if the exception is not fully absorbed by the outer TVM exception hierarry, it can propagate as an unexpected runtime exception during block application, which is a node halt/DoS class issue reachable by any single crafted transaction — matching the CVSS profile of the reference (Medium severity, local/low-privilege, requires no special access beyond sending a transaction).

### Likelihood Explanation
High likelihood of triggering the exception path: an attacker fully controls the calldata to `ValidateMultiSign` (function selector `validateMultiSign(address,uint256,bytes32,bytes[])`), including the nested `bytes[]` header's offset words. No special permissions, staking, or witness/committee status is required — only the ability to deploy a contract or call an existing one that reaches this precompile address (`0x...a`), or to submit a transaction whose calldata directly triggers this call in the TVM. The `intValueSafe()` clamp to `Integer.MAX_VALUE` guarantees the arithmetic inputs are large enough to overflow the `(bytesOffset + offset + 2) * WORD_SIZE` computation deterministically.

### Recommendation
- Apply the same overflow-safe arithmetic already used in `isValidAbiEncoding` (`multiplyExact`/`addSafely`/`subtractExact`) to `extractBytesArray`, `extractSigArray`, and `extractBytes32Array`, rejecting (returning `false`/`DATA_FALSE`) rather than throwing when computed offsets/lengths are inconsistent with `data.length`.
- Bound-check `bytesOffset`, `bytesLen`, and the final byte offset against `data.length` before calling `Arrays.copyOfRange`.
- Wrap the array-extraction calls in `ValidateMultiSign.execute` in the same defensive `try/catch(Throwable)` pattern already used in `BatchValidateSign.doExecute`, to guarantee consistent revert behavior instead of relying on caller-level exception handling.

### Proof of Concept
Craft calldata for `validateMultiSign(address,uint256,bytes32,bytes[])` where the 4th parameter's dynamic offset word (`words[3]`) points to a length-array whose entries (i.e., `words[offset + i + 1]`) encode a byte offset value close to `Integer.MAX_VALUE` (e.g., `0xFFFFFFF0`, which `intValueSafe()` will accept only if `bytesOccupied() <= 4`, e.g. `0x7FFFFFF0`). This produces `bytesOffset ≈ 67,108,863`, and `(bytesOffset + offset + 2) * WORD_SIZE` overflows 32-bit `int` range, yielding an unexpected (potentially negative) offset passed to `Arrays.copyOfRange(data, offset, offset+len)` in `extractBytes`, throwing an uncaught `ArrayIndexOutOfBoundsException`/`NegativeArraySizeException` from `ValidateMultiSign.execute`, which is not locally caught, unlike its `BatchValidateSign` sibling.

*(Note: because Java performs bounds checking on array accesses, this cannot yield an actual out-of-bounds memory read as in the native FreeType case; the confirmed, code-level impact is limited to an uncaught exception escaping the precompile's execute() path. Whether this exception is absorbed harmlessly further up the transaction-execution stack, or propagates to cause abnormal node behavior, could not be fully confirmed from the available indexed files — the outer exception-handling layers around `Program.callToPrecompiledAddress`/`Runtime` were not fully traceable within this session. A Devin session with full repository access would be needed to trace the complete call chain and confirm the ultimate handling of this exception.)*
