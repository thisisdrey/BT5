### Title
Floating-point precision defect in the legacy Bancor-style `ExchangeProcessor` AMM pricing formula allows reserve-value extraction via repeated `ExchangeTransaction` calls - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The WooFi incident stemmed from a bespoke, insufficiently battle-tested price-calculation formula (the "sPMM" curve) whose numeric handling let an attacker push the price outside the intended bounds and drain the pool through repeated swaps, with no reliable fallback check covering the manipulated token. The java-tron TRC10 `Exchange`/`ExchangeV2` module implements an analogous bespoke bonding-curve ("Bancor-style") AMM in `ExchangeProcessor`, computed with Java `double` arithmetic and `Maths.pow`, and this legacy, imprecise path is still the default execution path for `ExchangeTransactionContract` unless a chain governance proposal activates the newer, exact `SafeExchangeProcessor` (`allowHardenExchangeCalculation`).

### Finding Description
`ExchangeCapsule.transaction()` selects the pricing engine based on the `hardenedCalc` flag: [1](#0-0) 

When hardening is not enabled (the default state until a committee proposal turns it on), every `ExchangeTransaction` is priced by the legacy `ExchangeProcessor`, which performs the entire Bancor-curve calculation in double-precision floating point via `Maths.pow`: [2](#0-1) 

The test suite itself demonstrates that this non-strict/double path produces a *different, less accurate* result than the exact `BigDecimal`-based `SafeExchangeProcessor` for the same inputs: [3](#0-2) 

`ExchangeTransactionActuator.execute()` invokes this same unaudited-for-precision code path directly against the live pool reserves for any unprivileged, fee-free (`calcFee()==0`) transaction, and commits the resulting reserve mutation to the store: [4](#0-3) 

Because the swap output is derived from floating-point exponentiation rather than exact rational arithmetic, sequences of small/large trades chosen by an attacker can accumulate rounding bias in the attacker's favor (analogous to WooFi's sPMM price-adjustment error going "outside the expected range" with no oracle-independent bound check). Unlike WooFi, there is no Chainlink-style fallback at all here — the "hardened" (exact-math) `SafeExchangeProcessor` is the only mitigation, and it is opt-in via `allowHarden()`/`allowHardenExchangeCalculation`, not the default.

### Impact Explanation
An attacker who identifies a rounding-favorable sequence of `ExchangeTransaction` calls against a TRC10 `Exchange`/`ExchangeV2` pool can repeatedly extract more of the counter-asset than the bonding curve should allow, draining pool reserves funded by other liquidity providers — a direct, unauthorized transfer of value / theft of funds, reachable purely through the public `wallet/exchangetransaction` HTTP endpoint or the `ExchangeTransaction` gRPC call with a normal signed transaction (no privileged role required).

### Likelihood Explanation
Exploitation only requires crafting `ExchangeTransactionContract` parameters (`token_id`, `quant`, `expected`) and submitting ordinary signed transactions in sequence against a pool where `allowHardenExchangeCalculation` has not been activated by the committee — the current default. No SR/witness collusion, leaked keys, or network-level attack is needed, matching the "unprivileged order/exchange placer" reachability required by scope.

### Recommendation
- Make `SafeExchangeProcessor` (exact `BigDecimal` math) the unconditional pricing engine for `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator`, removing the `allowHarden()`/`dynamicStore.allowStrictMath()` legacy branch instead of gating it behind an opt-in governance flag.
- Add explicit invariant checks after every swap (e.g., constant-product/curve invariant must not decrease, output must not exceed a bound derived from reserves) independent of the floating-point calculation, so any residual precision drift cannot be monetized.
- Add fuzz/property tests comparing `ExchangeProcessor` vs `SafeExchangeProcessor` outputs across adversarially chosen sequences of trades (not just single trades) to catch cumulative-rounding exploits before mainnet activation.

### Proof of Concept
1. Deploy/observe a TRC10 `Exchange` pool with `allowHardenExchangeCalculation` at its default (disabled) value, so `AbstractExchangeActuator.allowHarden()` returns `false` and `ExchangeCapsule.transaction()` uses `ExchangeProcessor` (`chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java:41-45`).
2. As an unprivileged account, submit a sequence of `ExchangeTransactionContract` transactions (via `wallet/exchangetransaction` or gRPC `ExchangeTransaction`) with token quantities chosen to bias the `double`-based `Maths.pow` rounding in the attacker's favor, exactly as demonstrated by `ExchangeProcessorTest.testStrictMath` showing non-strict vs exact results diverge for the same reserve/quant inputs (`framework/src/test/java/org/tron/core/capsule/utils/ExchangeProcessorTest.java:272-280`).
3. Repeat the sequence to accumulate the rounding bias across many transactions, extracting more of the counter-token than the exact bonding-curve formula (`SafeExchangeProcessor`) would allow, draining pool reserves at the expense of the pool creator/other participants — mirroring WooFi's price-formula-out-of-range drain, but rooted in floating-point rather than an external oracle.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
