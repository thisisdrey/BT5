Audit Report

## Title
Unbounded exponential purse-key lockout via attacker-triggered dispatch failure in `pallet-scarcity` - (File: `substrate/frame/scarcity/src/extension.rs`)

## Summary
`AsScarcity::failed_dispatch_lock` computes an exponential backoff (`2^min(retries-1,63) * LockPeriod`) keyed on the victim purse `owner`, with `retries` (`u8`) incrementing without any configured ceiling. Because the lock is set on *any* dispatch failure and can only be cleared by a *successful* dispatch — which the lock itself blocks once `until` is in the future — an attacker who can force a handful of dispatch failures against a victim's account (e.g., by racing a permissionless `mint` into the victim's intended `transfer` destination) can drive `Locked::<T>` for that account to an astronomically large `until` timestamp, permanently denying use of the purse key.

## Finding Description
`AsScarcity::validate` rejects any transaction whose purse-key `owner` has `Locked::<T>::get(&owner)` with `until > now`: [1](#0-0) . That lock is written unconditionally on dispatch failure and only removed on success, in `post_dispatch_details`: [2](#0-1) . The lock duration is computed by `failed_dispatch_lock`, which increments `retries` (`u8`, `saturating_add(1)`) and multiplies `LockPeriod` by `2^min(retries-1, 63)` with no configurable cap: [3](#0-2) .

`validate` does pre-check the transfer destination against `NftsByOwner` before admitting the transaction to the pool: [4](#0-3) , but the module's own comment concedes this only prevents "ordinary user error," and that "dispatch-time checks remain for genuine same-block races," i.e., the pallet acknowledges that `validate`'s destination check can pass while the later dispatch-time check in `transfer` still fails: [5](#0-4)  (specifically the `ensure!(!NftsByOwner::<T>::contains_key(&to), Error::<T>::AddressOccupied)` check at line 595).

Minting is permissionless and destination-consent-free: any signed account can call `create_collection`, `define_item`, and `mint` to place an NFT into *any* currently empty purse key, as the pallet's own module docs state ("the destination gives no consent; any empty key is a valid target"): [6](#0-5) . This gives an unprivileged attacker a cheap, repeatable way to occupy a victim's intended `to` address between the victim's `validate` and dispatch, producing an `AddressOccupied` failure that is then converted into a compounding lock on the *victim's* `owner` key — not the attacker's.

Because `retries` never decreases and only resets via a successful dispatch (which is impossible while `until > now`), repeated forced failures cause `until` to grow exponentially without bound (up to `2^63 * LockPeriod`), which for any realistic `LockPeriod` is effectively permanent. There is no `Config` parameter capping `retries`, the exponent, or the total lock duration, and no privileged or time-independent unlock path exists in the reviewed code.

## Impact Explanation
This is a permanent-lock-of-user-funds-class issue: an uninvolved victim's Scarcity purse key (holding an NFT) can be denied use of `transfer`/`burn` indefinitely, entirely through actions of an unprivileged third party, matching the "permanent user-fund … lock" impact category. The lock is keyed purely to the account (`owner`), not to the specific failing call or destination, so it blanket-blocks all future authorized transfers/burns for that purse once triggered enough times.

## Likelihood Explanation
The attack requires only unprivileged, cheap, repeatable actions (`create_collection` + `define_item` + `mint`) available to any signed account, and exploits a race window between `validate` and dispatch that the pallet's own documentation explicitly acknowledges as reachable ("genuine same-block races"), rather than assuming a purely theoretical or infra-level compromise. No validator, collator, or governance privilege is needed — only the ability to submit transactions that can be ordered ahead of the victim's `transfer` dispatch within the same block.

## Recommendation
Bound the exponential backoff: introduce a `Config::MaxLockRetries` (or a fixed cap on `exponent`) so `until` cannot exceed `MaxLockRetries * LockPeriod`, preventing unbounded compounding. Additionally, consider scoping locks to the specific failing destination/call rather than blanket-locking the account for all future purse-key actions, and/or provide a privileged or time-bounded recovery path independent of requiring a successful dispatch.

## Proof of Concept
1. Victim holds NFT `N` at purse `owner`; submits a signed `AsScarcity`-authorized `transfer(to)` where `to` is empty at `validate` time: `substrate/frame/scarcity/src/extension.rs` lines 229–240 pass.
2. Attacker calls `create_collection`, `define_item`, `mint(..., to, ...)` targeting the same `to` such that it lands on-chain before the victim's `transfer` executes in the same block (acknowledged as reachable per the module's race-window comment).
3. Victim's `transfer` dispatch fails at `ensure!(!NftsByOwner::<T>::contains_key(&to), Error::<T>::AddressOccupied)` (`substrate/frame/scarcity/src/lib.rs:595`).
4. `post_dispatch_details` (`extension.rs:290-296`) restores the NFT to `owner` and inserts `Locked::<T>` via `failed_dispatch_lock`, with `retries = 1`, `until = now + LockPeriod`.
5. Attacker repeats steps 1–4 (re-racing) a handful of times; each failure doubles the multiplier (`2^(retries-1)`).
6. After a modest number of forced failures, `until` becomes astronomically large, and `validate` (`extension.rs:220-224`) permanently rejects any future signed transaction from that purse key, with no self-service recovery since recovery requires a successful dispatch that the lock itself now forbids.

	fn failed_dispatch_lock(previous: Option<LockInfo>) -> LockInfo {
		let retries = previous.map(|lock| lock.retries.saturating_add(1)).unwrap_or(1);
		let exponent = retries.saturating_sub(1);
		let multiplier = 2u64.saturating_pow(u32::from(exponent).min(63));
		LockInfo {
			retries,
			until: T::UnixTime::now()
				.as_secs()
				.saturating_add(multiplier.saturating_mul(T::LockPeriod::get())),
		}
	}
