### Title
Ethereum beacon light client permanently bricks bridge message verification once the finalized-header gap exceeds `SLOTS_PER_HISTORICAL_ROOT` - (File: bridges/snowbridge/pallets/ethereum-client/src/lib.rs)

### Summary
`EthereumBeaconClient::verify_update()` gates every light-client update with a hard numeric-deviation check (`InvalidFinalizedHeaderGap`) comparing the on-chain stored finalized slot against the slot carried by the incoming update. This check can only ever fail in the direction of "too large a gap" and the gap can never shrink through normal `submit` calls — once it is exceeded, every subsequent update, from any caller, fails the same way forever, permanently halting proof verification for `inbound-queue`/`inbound-queue-v2` (and everything that depends on `Verifier::verify`, i.e. token unlocks, foreign-token minting, relayer reward registration). This mirrors the `PanopticPool.dispatchFrom()` pattern from the seed report: an unconditional live-value-vs-reference deviation gate sitting in front of all critical operations, which can enter a state where it blocks 100% of callers indefinitely with no in-pallet recovery path.

### Finding Description
`verify_update()` enforces: [1](#0-0) 

```rust
// Verify the finalized header gap between the current finalized header and new imported
// header is not larger than the sync committee period, otherwise we cannot do
// ancestry proofs for execution headers in the gap.
ensure!(
    latest_finalized_state
        .slot
        .saturating_add(config::SLOTS_PER_HISTORICAL_ROOT as u64) >=
        update.finalized_header.slot,
    Error::<T>::InvalidFinalizedHeaderGap
);
```

`SLOTS_PER_HISTORICAL_ROOT` is a fixed constant (8192 slots, roughly 27.3 hours of Ethereum time). `latest_finalized_state.slot` only advances when a `submit` call successfully passes this same check and calls `store_finalized_header` via `apply_update`: [2](#0-1) 

Because real Ethereum slots keep advancing regardless of whether anyone submits updates to this pallet, if no update lands within roughly 27 hours (relayer downtime, fee exhaustion, network partition, chain congestion that starves the `submit` extrinsic, or simply nobody bothering to submit because the operation is currently unprofitable/ungated by any incentive), the gap between the stored `latest_finalized_state.slot` and the live Ethereum finalized slot permanently exceeds `SLOTS_PER_HISTORICAL_ROOT`. From that point on:
- Every future `update.finalized_header.slot` an honest relayer can produce corresponds to the *current* (advancing) Ethereum chain, so it is always further ahead of the frozen `latest_finalized_state.slot` than the last failed attempt.
- The check can never succeed again through the normal `submit` path, because there is no mechanism in this pallet to "catch up" the stored slot in smaller increments once the gap is broken — `ExecutionHeaderTooFarBehind`/`ExecutionHeaderSkippedBlock`/`InvalidFinalizedHeaderGap` all guard on the same monotonically-growing gap.
- `Verifier::verify()` in `impls.rs` depends on `FinalizedBeaconState`/`LatestFinalizedBlockRoot` staying current; once updates stop landing, `verify_execution_proof` keeps returning `HeaderNotFinalized`/stale results, so `inbound-queue`'s and `inbound-queue-v2`'s `submit`/`process_message` calls are blocked for every relayer, exactly like `dispatchFrom()` being blocked for every liquidator in the seed report: [3](#0-2) 

No privileged bypass, degraded-mode fallback, or re-bootstrap extrinsic was found in this pallet's dispatchable surface; the only apparent recovery is a fresh `process_checkpoint_update` bootstrap, which is invoked internally and is not exposed as a permissionless recovery call in the code inspected — meaning restoring the bridge after this state requires an out-of-band, presumably governance-driven, redeployment/migration rather than any unprivileged caller being able to self-heal the light client.

### Impact Explanation
This directly matches the "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" and "public underpriced work that degrades block production or stalls bridge processing" pivots: the beacon light client's state-advancement path can enter a state where it can never advance again through normal operation, which stalls all Ethereum→Polkadot bridge message processing (`inbound-queue`, `inbound-queue-v2`), including relayer reward registration and token unlock/mint flows that depend on `Verifier::verify`. This is a permanent, protocol-level liveness failure of the bridge rather than a one-off delay, and — unlike `tickDeltaLiquidation`, which merely delays liquidations until price reconverges — this gate has no path back to convergence once tripped, making it strictly worse than the seed bug in terms of permanence.

### Likelihood Explanation
The triggering condition (no successful `submit` landing for ~27.3 hours of real Ethereum time) does not require a malicious relayer, validator, or governance actor — it only requires an absence of successful updates for a bounded, realistic window (relayer software outage, fee-market congestion on BridgeHub, chain reorg handling bugs, or a burst of invalid/malformed update spam that keeps consuming the `submit` extrinsic's dispatch slot without landing a valid update before the window closes). Given that `SLOTS_PER_HISTORICAL_ROOT` is a hard constant unrelated to how frequently relayers actually submit in practice, and there is no rate-based or incentive-based guarantee that some relayer submits within every 27-hour window, this is a plausible, low-cost liveness failure mode rather than a purely theoretical one.

### Recommendation
- Add a permissionless (or root-gated but clearly documented) re-bootstrap/`force_checkpoint`-style extrinsic that allows the light client to be re-seeded from a fresh Ethereum checkpoint without requiring the frozen `latest_finalized_state.slot` to satisfy the `InvalidFinalizedHeaderGap` invariant.
- Alternatively, allow incremental gap recovery by accepting intermediate finalized headers that reduce the gap step-by-step (e.g., accept updates whose slot is closer to, but does not need to fully bridge, the live chain), rather than an all-or-nothing single-hop check.
- Emit an on-chain alarm/event as soon as the gap crosses some fraction of `SLOTS_PER_HISTORICAL_ROOT` so operators can react before the hard failure boundary is crossed.

### Proof of Concept
1. Bootstrap `EthereumBeaconClient` via `process_checkpoint_update` at slot `S0`.
2. Do not submit any further updates for more than `SLOTS_PER_HISTORICAL_ROOT` (8192) slots of real Ethereum time (this is already exercised structurally by the existing test `submit_finalized_header_update_with_too_large_gap`, which demonstrates that a single update whose `finalized_header.slot` exceeds `latest_finalized_state.slot + SLOTS_PER_HISTORICAL_ROOT` fails with `Error::<Test>::InvalidFinalizedHeaderGap`): [4](#0-3) 
3. Because the stored slot never advances past `S0` once step 2's window has elapsed, any subsequent honest update carrying the real (advancing) Ethereum finalized slot will always fail the same check — the test above shows the failure for one such attempt, and by construction every later attempt has an even larger real slot delta, so the failure is permanent, not transient.
4. With `verify_update`/`apply_update` permanently failing, `Verifier::verify()` cannot progress, and `inbound-queue`/`inbound-queue-v2` `submit`/`process_message` calls fail indefinitely for every relayer, stalling all Ethereum→Polkadot message delivery.

		/// Applies a finalized beacon header update to the beacon client. If a next sync committee
		/// is present in the update, verify the sync committee by converting it to a
		/// SyncCommitteePrepared type. Stores the provided finalized header. Updates are free
		/// if the certain conditions specified in `check_refundable` are met.
		fn apply_update(update: &Update) -> DispatchResultWithPostInfo {
			let latest_finalized_state =
				FinalizedBeaconState::<T>::get(LatestFinalizedBlockRoot::<T>::get())
					.ok_or(Error::<T>::NotBootstrapped)?;

			let pays_fee = Self::check_refundable(update, latest_finalized_state.slot);
			let actual_weight = match update.next_sync_committee_update {
				None => T::WeightInfo::submit(),
				Some(_) => T::WeightInfo::submit_with_sync_committee(),
			};

			if let Some(next_sync_committee_update) = &update.next_sync_committee_update {
				let store_period = compute_period(latest_finalized_state.slot);
				let update_finalized_period = compute_period(update.finalized_header.slot);
				let sync_committee_prepared: SyncCommitteePrepared = (&next_sync_committee_update
					.next_sync_committee)
					.try_into()
					.map_err(|_| <Error<T>>::BLSPreparePublicKeysFailed)?;

				if !<NextSyncCommittee<T>>::exists() {
					ensure!(
						update_finalized_period == store_period,
						<Error<T>>::InvalidSyncCommitteeUpdate
					);
					<NextSyncCommittee<T>>::set(sync_committee_prepared);
				} else if update_finalized_period == store_period + 1 {
					<CurrentSyncCommittee<T>>::set(<NextSyncCommittee<T>>::get());
					<NextSyncCommittee<T>>::set(sync_committee_prepared);
				}
				tracing::info!(
					target: LOG_TARGET,
					period=%update_finalized_period,
					"💫 SyncCommitteeUpdated."
				);
				<LatestSyncCommitteeUpdatePeriod<T>>::set(update_finalized_period);
				Self::deposit_event(Event::SyncCommitteeUpdated {
					period: update_finalized_period,
				});
			};

			if update.finalized_header.slot > latest_finalized_state.slot {
				Self::store_finalized_header(update.finalized_header, update.block_roots_root)?;
			}

/// Check that a gap of more than 8192 slots between finalized headers is not allowed.
#[test]
fn submit_finalized_header_update_with_too_large_gap() {
	let checkpoint = Box::new(load_checkpoint_update_fixture());
	let update = Box::new(load_sync_committee_update_fixture());
	let mut next_update = Box::new(load_next_sync_committee_update_fixture());

	// Adds 8193 slots, so that the next update is still in the next sync committee, but the
	// gap between the finalized headers is more than 8192 slots.
	let slot_with_large_gap = checkpoint.header.slot + SLOTS_PER_HISTORICAL_ROOT as u64 + 1;

	next_update.finalized_header.slot = slot_with_large_gap;
	// Adding some slots to the attested header and signature slot since they need to be ahead
	// of the finalized header.
	next_update.attested_header.slot = slot_with_large_gap + 33;
	next_update.signature_slot = slot_with_large_gap + 43;

	new_tester().execute_with(|| {
		assert_ok!(EthereumBeaconClient::process_checkpoint_update(&checkpoint));
		let result = EthereumBeaconClient::submit(RuntimeOrigin::signed(1), update.clone());
		assert_ok!(result);
		assert_eq!(result.unwrap().pays_fee, Pays::No);
		assert!(<NextSyncCommittee<Test>>::exists());

		let second_result =
			EthereumBeaconClient::submit(RuntimeOrigin::signed(1), next_update.clone());
		assert_err!(second_result, Error::<Test>::InvalidFinalizedHeaderGap);
		assert_eq!(second_result.unwrap_err().post_info.pays_fee, Pays::Yes);
	});
}
