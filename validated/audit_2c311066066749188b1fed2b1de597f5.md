**Analysis:**

The concern describes expected, intentional design rather than a bug. `action_deploy_global_contract` burns `global_contract_storage_amount_per_byte * code.len()` tokens once from the deployer at deploy time and adds this to `result.tokens_burnt` [1](#0-0) . Any account that later references the deployed code via `UseGlobalContract` only pays for a small identifier: `use_global_contract` first calls `clear_account_contract_storage_usage` to remove any prior contract's storage usage, then adds exactly `contract_identifier.len()` bytes (32 for `Global(code_hash)`, or the account-id length for `GlobalByAccount`) to `storage_usage` via `checked_add` [2](#0-1) . This is symmetric with `clear_account_contract_storage_usage`, which subtracts `identifier_storage_usage()` via `saturating_sub` on the next transition (e.g. another `UseGlobalContract`, or `DeployContract`) [3](#0-2)  and [4](#0-3) .

The multi-MB code bytes are never duplicated into the referencing account's `storage_usage` at all — only the identifier is, which is the entire point of global contracts (shared code paid once, referenced many times cheaply). This is not "code referenced for free relative to `global_contract_storage_amount_per_byte`" — that fee only ever applies to the deployer who actually causes the code bytes to be persisted in the trie once; per-account storage stake is correctly sized to the identifier bytes actually added to that account's trie footprint, and is enforced by `check_storage_stake`, which is re-evaluated for the receiver account after every action in a receipt completes [5](#0-4) , so any increase in `storage_usage` from `UseGlobalContract` must be backed by the account's own balance or it fails with `LackBalanceForState`.

The historical asymmetry that under-subtracted the global-contract identifier length on `DeleteAccount` (only subtracting local code, not the global identifier) was a real past bug, but it is already fixed and gated behind `FixDeleteAccountGlobalContractStorageUsage`, which is enabled at the current `MIN_SUPPORTED_PROTOCOL_VERSION = 83` [6](#0-5) , and is covered by regression tests (`test_delete_account_global_contract_protocol_transition`, `test_delete_account_global_by_account_fix_enabled`) [7](#0-6) . No code path lets an account add the identifier storage usage without a corresponding removal, nor does any path let total account count multiply a free amortized cost against `global_contract_storage_amount_per_byte` — that fee is charged exactly once, at deploy, independent of how many accounts later reference the contract via `UseGlobalContract` (which instead pays `action_use_global_contract_per_identifier_byte` gas and the identifier's storage stake). No accounting drop from `total_balance_burnt` reconciliation is present.

fn get_contract_storage_usage(
    state_update: &TrieUpdate,
    account_id: &AccountId,
    account: &Account,
) -> Result<StorageUsage, StorageError> {
    Ok(match account.contract().as_ref() {
        AccountContract::None => 0,
        AccountContract::Local(code_hash) => {
            get_code_len_or_default(state_update, account_id.clone(), *code_hash)?
        }
        AccountContract::Global(_) | AccountContract::GlobalByAccount(_) => {
            account.contract().identifier_storage_usage()
        }
    })
}

/// Clears the contract storage usage based on type for an account.
pub(crate) fn clear_account_contract_storage_usage(
    state_update: &TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
) -> Result<(), StorageError> {
    let contract_storage = get_contract_storage_usage(state_update, account_id, account)?;
    account.set_storage_usage(account.storage_usage().saturating_sub(contract_storage));
    Ok(())
}
