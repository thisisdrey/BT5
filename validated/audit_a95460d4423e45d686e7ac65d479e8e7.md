Found a concrete analog: `process_delivery_receipt` in the Snowbridge outbound-queue-v2 pallet pays a relayer reward and then removes the pending order in two separate storage operations, but critically the reward is registered *before* removal, with no atomic guarantee tying the two together — and more importantly, `do_process_message` explicitly documents "This method does not roll back storage changes on error," meaning partial state (nonce increment, message leaves, pending order) can persist even when downstream steps fail, unlike the atomic dispatchable path used elsewhere.

### Title
Non-atomic outbound message processing can desynchronize `Nonce`/`PendingOrders` state from committed `MessageLeaves` on partial failure - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`Pallet::do_process_message` in the Snowbridge V2 outbound queue is explicitly documented as non-transactional ("this method does not roll back storage changes on error") [1](#0-0) , yet it performs several sequential, individually-fallible storage writes — appending to `Messages`, appending to `MessageLeaves`, inserting into `PendingOrders`, and finally setting `Nonce` — before any of them are validated as a consistent unit.

### Finding Description
The comment at line 342 is a direct admission that this processing path lacks the object-level validation/atomicity guarantee that the bug-report class describes: data structures (`Message`, `OutboundMessage`, `PendingOrder`) are mutated into long-lived storage incrementally, and only some steps have local `ensure`/`map_err` guards, while others (e.g., `<Nonce<T>>::set(nonce)` at line 438) are unconditionally applied assuming everything upstream succeeded correctly [2](#0-1) . Because this function is invoked from the `MessageQueue`'s `ProcessMessage` implementation (not from a `#[pallet::call]` dispatchable), it does not benefit from FRAME's automatic transactional-storage-layer rollback that normal extrinsics get. If any step after `Messages::<T>::append` and `MessageLeaves::<T>::append` were to fail (for example the `commands.clone().try_into()` bound check at line 394, which does return `Corrupt` after already having appended the message to `Messages` and about to compute a hash), the `Messages`/`MessageLeaves` entries used to build the committed Merkle root could diverge from `PendingOrders`/`Nonce` bookkeeping used for reward accounting on `submit_delivery_receipt`. This mirrors the report's "validated in one place, assumed valid downstream without re-validation" pattern: `Message` is decoded via `Message::decode` (line 362) but its correctness relative to gas metering (`T::GasMeter::maximum_dispatch_gas_used_at_most`) and command bounding (`try_into` on line 394) is not fully checked before the message is already recorded in `Messages` storage.

### Impact Explanation
If nonce/`PendingOrders`/`MessageLeaves` state can desynchronize, downstream `process_delivery_receipt` (which trusts `PendingOrders::<T>::get(nonce)` to resolve a fee reward, lines 464-473) could pay out a reward for a nonce whose corresponding committed message was actually rejected/corrupt, or fail to find an order for a nonce that was actually committed to the Merkle root sent to Ethereum — a duplicate-settlement / stuck-state class of bug matching the "Message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" pivot.

### Likelihood Explanation
This is a low-confidence, structural finding rather than a fully demonstrated exploit: I could not conclusively trigger a mid-function failure in `do_process_message` after `Messages::<T>::append` but before `Nonce::<T>::set` under current bounded types (the `try_into` at line 394 is the only failure point after the `Messages` append, and whether `MaxCommands`/gas bounding can actually be violated by a legitimately-enqueued message depends on upstream `send_message_impl` validation, which I was not able to fully audit given remaining time). The explicit doc-comment warning about lack of rollback is genuine repository evidence of the missing-validation/non-atomicity class, but a concrete unprivileged trigger path was not fully confirmed.

### Recommendation
Either wrap `do_process_message` in an explicit `frame_support::storage::transactional::with_storage_layer` so that any failure after partial writes rolls back cleanly, or move all fallible conversions (`try_into` for commands, gas-metering bounds) before any storage mutation occurs, so `Messages`, `MessageLeaves`, `PendingOrders`, and `Nonce` only advance together after full validation, consistent with the "advance only after decode, dispatch, execution and settlement succeed atomically" requirement.

### Proof of Concept
Not fully constructible with available context: reproducing requires crafting a `Message` whose `commands` vector passes initial decode but fails the `try_into` bound at line 394 (or a `GasMeter` computation that exceeds bounds), which depends on `MaxCommands`/`GasMeter` configuration inside the runtime that I could not fully inspect in the remaining budget. This should be verified directly against the pallet's bounded-vec limits and `send_message_impl` guarantees before treating this as a confirmed exploit.
