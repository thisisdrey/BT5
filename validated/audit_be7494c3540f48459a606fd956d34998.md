## Title
Missing historical-window bound check in beacon ancestry proof allows slot/index aliasing in `block_roots` ring buffer - ([File: bridges/snowbridge/pallets/ethereum-client/src/impls.rs])

### Summary
`Pallet::<T>::verify_ancestry_proof` computes a fixed-size ring-buffer index (`block_slot % SLOTS_PER_HISTORICAL_ROOT`) to locate a leaf in the beacon state's `block_roots` merkle tree, but only checks `block_slot < state.slot`. It never verifies that `block_slot` is within `SLOTS_PER_HISTORICAL_ROOT` (8192) slots of `state.slot`. This is the same bug class as the reported `Keep3rV1Oracle.sample()` issue: an index derived from unchecked/attacker-influenced input is used to read a fixed-size, wrap-around array without validating it still refers to the intended element rather than a stale, overwritten slot.

### Finding Description

```
    block_root: H256,
    block_slot: u64,
    block_root_proof: &[H256],

    let leaf_index = (SLOTS_PER_HISTORICAL_ROOT as u64) + index_in_array;
    ...
}
```

`SLOTS_PER_HISTORICAL_ROOT` is a fixed 8192-slot ring buffer in the beacon state used for the `block_roots` field: [2](#0-1) 

The only guard present is `block_slot < state.slot`, i.e. "not from the future" - there is no lower bound (`state.slot.saturating_sub(block_slot) < SLOTS_PER_HISTORICAL_ROOT`). Because `index_in_array = block_slot % 8192`, any `block_slot` that is a multiple of 8192 away from another slot maps to the exact same ring-buffer position. This is structurally identical to the `Keep3rV1Oracle.sample()` finding: `nextIndex`/array index is derived from an unbounded value without checking it is still inside the "currently valid" window of the underlying fixed-size array, so a stale or wrapped-around slot can be referenced as if it were current data.

Call site, `verify_execution_proof`, feeds this same `block_slot` in directly from attacker-supplied `execution_proof.header.slot`: [3](#0-2) 

### Impact Explanation
This affects the core light-client trust anchor used by Snowbridge to accept Ethereum execution headers as ancestors of a finalized beacon header, gating message/receipt inclusion proofs used to mint/settle bridged assets. If the missing distance check allows an execution/beacon header with a very old `slot` value to be accepted as an ancestor of a finalized header that is actually far in the future of it (aliasing across ring-buffer wraps of 8192 slots, ~27 hours), the pallet could accept ancestry relationships that do not correspond to the real historical chain state committed in `state.block_roots_root`, undermining the "finality/header proof must bind ... exactly once" invariant required by the pivots for delivery/finality proofs. This falls into the "forged or mis-bound proof or state acceptance" category for BridgeHub code.

### Likelihood Explanation
Exploitation requires the attacker's chosen header to actually collide with a real, merkle-committed leaf value at the aliased index (merkle proofs are still binding to whatever hash is truly stored at that leaf), so a full forgery of an arbitrary header is not immediately achievable without further work; however, the missing bound is a genuine deviation from the spec-required freshness check (`state.slot - block_slot < SLOTS_PER_HISTORICAL_ROOT`), and no test in `bridges/snowbridge/pallets/ethereum-client/src/tests.rs` exercises the boundary where `block_slot` differs from `state.slot` by more than 8192 slots, so the missing guard is unverified by the existing test suite. Because `MaxFinalizedHeadersToKeep` retains many historical `FinalizedBeaconState` entries (`EPOCHS_PER_SYNC_COMMITTEE_PERIOD * 20` slots' worth) via the ring buffer in `bridges/snowbridge/pallets/ethereum-client/src/lib.rs` (`FinalizedBeaconStateIndex`/`FinalizedBeaconStateMapping`), the window in which stale `finalized_block_root` entries with large slot gaps to a candidate `block_slot` can be picked by a caller is realistically large.

### Recommendation
Add an explicit upper-bound (freshness) check in `verify_ancestry_proof`, mirroring the missing check identified in the original report:
```rust
ensure!(
    state.slot.saturating_sub(block_slot) < SLOTS_PER_HISTORICAL_ROOT as u64,
    Error::<T>::HeaderNotFinalized
);
```
placed alongside the existing `ensure!(block_slot < state.slot, ...)` check, so that `index_in_array` can only ever refer to the ring-buffer slot that still legitimately corresponds to `block_slot` at the time `state` was captured.

### Proof of Concept
Not independently reproducible from static analysis alone: exploitation requires constructing (or finding) a real beacon-chain header whose `hash_tree_root()` collides with the value actually committed in some retained `FinalizedBeaconState.block_roots_root` at the aliased leaf index `(block_slot % 8192)`, and picking a `finalized_block_root` from the `FinalizedBeaconStateBuffer` ring buffer whose `state.slot` is `>= block_slot + 8192*k` for some `k >= 1`. This is confirmed as a missing-check gap by code review of `bridges/snowbridge/pallets/ethereum-client/src/impls.rs:145-171` and the absence of a corresponding freshness test in `bridges/snowbridge/pallets/ethereum-client/src/tests.rs`; a background Devin session would be needed to attempt fixture construction and run the existing test harness (`load_checkpoint_update_fixture`, `load_finalized_header_update_fixture`) to confirm whether a distant-slot `block_root_proof` is currently accepted.
