### Title
DoS of exchange trades via front-run liquidity withdrawal manipulating the Bancor curve depth used by the slippage check - ([File: actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java])

### Summary
The TRON built-in `Exchange` (Bancor-relay-style AMM) exposes `ExchangeCreateContract`, `ExchangeInjectContract`, `ExchangeWithdrawContract` and `ExchangeTransactionContract`, all reachable by ordinary signed transactions / HTTP-RPC calls (`/wallet/exchangecreate`, `/wallet/exchangewithdraw`, `/wallet/exchangetransaction`). The exchange creator can withdraw pool liquidity at will, immediately before a victim's swap transaction is packed into the same block, shrinking the pool depth so that the victim's precomputed `anotherTokenQuant` falls below the `tokenExpected` slippage guard, causing the victim's `ExchangeTransactionContract` to revert with `"token required must greater than expected"`. This is directly analogous to the reported `_checkVolatility`/`pendingThreshold` DoS in AegisVault, where an attacker manipulates on-chain reserve state right before a victim's transaction to trip a ratio/threshold guard and force a revert.

### Finding Description
`ExchangeTransactionActuator.doValidate()` computes the output amount via the Bancor-style curve in `ExchangeCapsule.transaction()` (which uses the current `firstTokenBalance`/`secondTokenBalance` reserves) and compares it against the caller-supplied `tokenExpected` minimum: [1](#0-0) 

The reserves consumed by this curve come straight from the `ExchangeCapsule` stored in `ExchangeStore`/`ExchangeV2Store`: [2](#0-1) 

The Bancor exchange formula (`exchangeToSupply`/`exchangeFromSupply`) is sensitive to pool *depth*, not just the ratio between the two token balances — for a fixed input quantity, a shallower pool produces a smaller output: [3](#0-2) 

An exchange's creator (any account that previously issued an `ExchangeCreateContract`, i.e., an ordinary, permissionless "asset/market issuer" role, not a validator/SR) is the only party allowed to call `ExchangeWithdrawActuator`: [4](#0-3) 

Because withdrawal removes tokens from both reserves proportionally, it does not change the price ratio but does reduce pool depth, which directly reduces the output a subsequent trader receives for the same input `tokenQuant`: [5](#0-4) 

An attacker who created (or controls) a popular exchange pair can watch the mempool/pending transactions and, right before a victim's `ExchangeTransactionContract` is confirmed, submit an `ExchangeWithdrawContract` that reduces pool depth just enough to push the victim's expected output below their `tokenExpected` floor, causing the victim's swap to revert with `"token required must greater than expected"`. Because withdrawal (and the corresponding creator-only re-injection) is fully under attacker control and costs only the withdrawn liquidity being temporarily removed (and later reinjected), this can be repeated deterministically against every incoming trade in that exchange, denying service to all traders using that pool. This mirrors the reported bug class: manipulating on-chain state that a slippage/ratio-style guard depends on, immediately before a victim's transaction, to force a revert of a legitimate, permissionless transaction (`ExchangeTransactionContract`, reachable by any account with sufficient balance — the "order placer" role explicitly in scope).

### Impact Explanation
Impact is Medium: it does not directly steal funds or crash the node, but it enables a targeted denial of service against a specific `Exchange` pool's trading function (`exchangetransaction`), repeatedly forcing legitimate swap transactions to fail (wasting the victim's bandwidth/energy fee and blocking use of that market) as long as the attacker (the pool creator) chooses to grief it. This matches the "Medium" impact bracket used for the analogous Aegis Vault finding — a reachable, repeatable denial-of-service against normal user actions, without requiring any privileged (SR/witness/node-operator) role.

### Likelihood Explanation
Likelihood is Medium: the attacker must be (or become, since exchange creation is permissionless) the creator of the specific `Exchange` instance being targeted, and must be able to observe pending/mempool transactions to time the withdraw precisely — both of which are realistic on a live TRON network. The attack imposes a mild opportunity cost (temporarily reduced liquidity, reinjection cost/fees) similar to the "front-run deposit/withdraw" cost noted in the original report, but is otherwise cheap and repeatable.

### Recommendation
- Consider recording the reserve balances at the time a trade's `tokenExpected` is validated versus executed, or add a maximum-allowed depth-change guard so that a same-block withdrawal cannot materially alter another user's expected trade outcome.
- Alternatively/complementarily, rate-limit or timelock `ExchangeWithdrawContract` (e.g., disallow inject+withdraw or withdraw+withdraw combinations within the same block as pending trades), or require a minimum cool-down between a creator's withdraw and subsequent trades being validated against pre-withdraw quotes.
- Document the trust assumption that trading against creator-controlled exchange pools inherits griefing risk from the creator, and/or expose this risk in wallet UX (front-end could warn about low-liquidity/creator-controlled pools before submitting `ExchangeTransactionContract`).

### Proof of Concept
1. Attacker calls `wallet/exchangecreate` (or targets any exchange it already created) to obtain `exchangeId` with reserves `(firstTokenBalance, secondTokenBalance)`.
2. Victim submits `ExchangeTransactionContract{exchangeId, tokenId, quant, expected}` computed off the current on-chain reserves (via `wallet/exchangetransaction`), expecting `anotherTokenQuant >= expected` per `ExchangeCapsule.transaction()`'s Bancor formula.
3. Before the victim's transaction is packed, attacker (exchange creator) submits `ExchangeWithdrawContract{exchangeId, tokenId, quant}` via `wallet/exchangewithdraw`, which is validated only against `getCreatorAddress()` and reduces both reserves proportionally, shrinking pool depth: [6](#0-5) 
4. When the victim's `ExchangeTransactionActuator.doValidate()` re-evaluates `exchangeCapsule.transaction(...)` against the now-shallower pool, the recomputed `anotherTokenQuant` is lower and trips: [1](#0-0) 
5. Victim's transaction fails with `ContractValidateException("token required must greater than expected")`, and the attacker can repeat this for every subsequent trade attempt on that pool, achieving sustained denial of service.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
