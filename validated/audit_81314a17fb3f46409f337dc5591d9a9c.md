Audit Report

## Title
Unvalidated `token = 0x0` in Snowbridge V1 `RegisterToken` lets an unprivileged Ethereum caller register AssetHub's reserved native‑ETH asset location - (File: bridges/snowbridge/primitives/inbound-queue/src/v1.rs)

## Summary
`MessageToXcm::convert_register_token` builds a `create_asset` `Transact` call using `asset_id = Self::convert_token_address(network, token)`, where `token` is an attacker-controlled `H160` field of the `Command::RegisterToken` message originating from Ethereum. `convert_token_address` deliberately maps `H160::zero()` to `Location::new(2, [GlobalConsensus(network)])`, which is confirmed by genesis configuration and test fixtures (`asset-hub-westend/src/genesis.rs:121`, `asset-hub-rococo/src/genesis.rs:120-126`, `snowbridge_common.rs:eth_location`) to be exactly the location AssetHub reserves for native Ether. Unlike the analogous v2 code path, no check rejects `token == H160::zero()` in `convert_register_token`, so a `RegisterToken` message carrying the zero address collides with the reserved Ether asset location. [1](#0-0) [2](#0-1) [3](#0-2) 

## Finding Description
`Command::RegisterToken { token, fee }` carries an Ethereum-side `H160` chosen by whoever triggers the corresponding Gateway message; the pallet-side `convert` dispatch routes it into `convert_register_token` with no upstream sanitation. [4](#0-3) 

`convert_register_token` computes `asset_id = Self::convert_token_address(network, token)` and feeds it unchecked into a `Transact` call that invokes `create_asset` on AssetHub's `ForeignAssets` pallet: [5](#0-4) 

`convert_token_address` special-cases `H160::zero()`, mapping it to `Location::new(2, [GlobalConsensus(network)])` — the identical location used as `bridge_location` two lines earlier in the same function, and confirmed elsewhere in the codebase as the canonical "native ETH" `ForeignAssets` entry (see genesis configs registering `EthereumLocation`/`eth_location()` as the Ether asset). [2](#0-1) 

By contrast, the sibling v2 converter explicitly guards against this exact collision for `NativeTokenERC20` assets: `ensure!(*token_id != H160::zero(), ConvertMessageError::InvalidAsset);`. No equivalent guard exists in `convert_register_token`. [6](#0-5) 

However, I was unable to verify from this repository whether the Ethereum-side Gateway contract's `registerToken` function (which triggers this inbound `RegisterToken` command) is truly permissionless and accepts an arbitrary/zero token address without its own validation — the Solidity contracts are not present/indexed in this repository (`bridges/snowbridge/contracts/**` returned no matches), so this part of the claim's attacker-capability premise could not be independently confirmed here.

## Impact Explanation
If exploitable end-to-end, this could allow an external caller to force AssetHub to attempt `create_asset` on the exact `Location` (`Location::new(2, [GlobalConsensus(network)])`) that the protocol reserves as its canonical native-ETH `ForeignAssets` entry, as confirmed in genesis configs. If this collision registration lands before or instead of the legitimate Ether asset registration, subsequent correct registration would fail with `AssetAlreadyExists`, potentially disrupting Ether-denominated bridge accounting on that AssetHub — matching the "public underpriced work that... stalls bridge processing" / "permanent bridge-state lock" impact categories, contingent on the missing Solidity-side validation being confirmed.

## Likelihood Explanation
The Rust-side omission is real and demonstrable: `convert_register_token` lacks the `ensure!(token != H160::zero())` guard present in the v2 converter for the analogous case. However, I could not confirm in this repository whether Ethereum-side contract logic (Gateway.sol equivalent) already prevents a zero-address `token` from reaching this inbound message path, since the Solidity contracts are not indexed here. Likelihood therefore cannot be fully assessed without that missing piece — it is plausible the Ethereum-side `registerToken` function itself validates the token address is a real, non-zero ERC20 contract before emitting the message, which would neutralize this specific attack path despite the Rust-side gap.

## Recommendation
Add a defensive guard in `convert_register_token` mirroring the v2 converter, regardless of Ethereum-side contract behavior (defense in depth):
```rust
ensure!(token != H160::zero(), ConvertMessageError::InvalidToken);
```
before computing `asset_id`, so the reserved native-ETH/bridge-root location can never be targeted via `RegisterToken`.

## Proof of Concept
1. Cause a `Command::RegisterToken { token: H160::zero(), fee }` message to be processed by BridgeHub's `MessageToXcm::convert` (via `VersionedMessage::V1(MessageV1 { command: RegisterToken { .. } })`).
2. `convert_register_token` calls `convert_token_address(network, H160::zero())`, yielding `asset_id = Location::new(2, [GlobalConsensus(network)])`, identical to `bridge_location` computed in the same function.
3. The resulting XCM's `Transact` invokes `create_asset(asset_id, owner, MINIMUM_DEPOSIT)` on AssetHub's `ForeignAssets` pallet using this reserved location, with no `ensure!` guard blocking `token == 0x0`, unlike `v2/converter.rs:170`.
4. Full exploitability depends on whether this `Command::RegisterToken` message can actually be triggered on Ethereum with `token = 0x0` — this last step could not be verified against the Solidity Gateway contract source, which is not present in this repository index.

	// Convert ERC20 token address to a location that can be understood by Assets Hub.
	fn convert_token_address(network: NetworkId, token: H160) -> Location {
		if token == H160([0; 20]) {
			Location::new(2, [GlobalConsensus(network)])
		} else {
			Location::new(
				2,
				[GlobalConsensus(network), AccountKey20 { network: None, key: token.into() }],
			)
		}
	}
