Also note that only the wallet owner (the entity holding the wallet's private key) or an already-enabled extension can add a new extension — this happens through `execute_signed` (requires valid signature) or `execute_extension` (requires being an already-enabled extension) calling `add_extension`. [3](#0-2)  An unprivileged attacker with no wallet ownership and no existing extension grant cannot make themselves an enabled extension in the first place, since that requires either the owner's valid signature (`execute_signed`) or being called from an already-enabled extension account (`check_extension_enabled` checks `env::predecessor_account_id()`). ### Conclusion

The question's premise — that an enabled extension has a scoped grant (e.g., "one specific `FunctionCall`") that is violated by unrestricted `Transfer` — is factually incorrect per this codebase's design. The README explicitly documents: "Installed extensions have full control over the wallet-contract instance" and extensions "have the same full power over the wallet-contract instance as the original signer does." [6](#0-5) [7](#0-6)  There is no per-extension scoping mechanism anywhere in `WalletOp::AddExtension`, `State`, or `execute_extension`; enabling an extension is a boolean, all-or-nothing grant of full authority equivalent to the signer's own key. [8](#0-7) 

Given this, the `1 yoctoNEAR` check in `execute_extension` merely serves as a minimal proof that the call is not coming from a Function-Call access key with zero attached deposit — it is not, and was never intended to be, a value-matching/authorization-scoping mechanism against `Request::total_deposit()`. The wallet's own NEAR balance is meant to be fully controllable by any enabled extension, exactly as it would be by the signer via `w_execute_signed`. There is no divergence between "authorized scope" and "actual transferred value" because no such narrower scope exists in the protocol — the finding conflates a general full-authority extension model with a nonexistent scoped-grant model, and the attacker precondition (being an "enabled extension" without prior owner authorization for that specific action) cannot be achieved by an unprivileged attacker as defined by the rules.
