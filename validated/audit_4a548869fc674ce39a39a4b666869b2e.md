### Title
Attacker can fill a victim's `MAX_TOKENS_PER_USER` slot list with dust `DepositToken` transfers, blocking the victim from issuing any debt or receiving new collateral types - (File: contracts/Pool.sol)

### Summary
`Pool` enforces a combined cap of `MAX_TOKENS_PER_USER = 30` on the per-account `depositTokensOfAccount` + `debtTokensOfAccount` lists via `onlyIfAdditionWillNotReachMaxTokens`. `DepositToken._transfer` unconditionally calls `pool.addToDepositTokensOfAccount(recipient_)` whenever a recipient's balance for that token goes from 0 to >0. Any EOA can therefore dust-transfer msdTOKEN shares to an arbitrary victim, consuming the victim's limited slots without consent.

### Finding Description
- `Pool.addToDepositTokensOfAccount` / `addToDebtTokensOfAccount` revert with `UserReachedMaxTokens` once the combined list length reaches 30 ( [1](#0-0) ).
- `DepositToken._transfer` adds the token to the recipient's list on any incoming transfer when the prior balance was zero; the recipient never opts in ( [2](#0-1) ).
- The same check gates `DebtToken._mint` → `pool.addToDebtTokensOfAccount`, which is reached through `DebtToken.issue` and `DebtToken.mint` ( [3](#0-2) ).
- Attack path: attacker deposits minimal amounts into each of the pool's deposit tokens (or buys dust on the open path via `deposit`), then calls `transfer(victim, 1 wei)` for 30 distinct deposit tokens. Each call adds an entry to `depositTokensOfAccount[victim]`. Once 30 slots are filled, `issue`/`mint` of any new debt token and any first-time receipt of a not-yet-held deposit token reverts for the victim.

### Impact Explanation
The victim is temporarily denied core protocol functionality: they cannot open a new debt position (`issue` reverts inside `_mint` at `addToDebtTokensOfAccount`) and cannot receive deposit tokens they do not already hold (blocking `deposit`-as-mint to them and incoming transfers). A victim with an unhealthy position that relies on receiving a new collateral type to restore health cannot do so until they manually clear slots. Existing balances remain withdrawable, so this is a temporary freeze/griefing of protocol operations rather than permanent loss — matching the availability-only impact class of the reference CVE (repeatable transaction-level DoS of a target account).

### Likelihood Explanation
Fully unprivileged: the attacker only needs dust balances of each deposit token, obtainable by depositing minimum amounts themselves. Cost is ~30 `transfer` calls plus negligible collateral. Recovery is possible (the victim transfers dust out to free slots), which is why impact is limited to temporary DoS rather than permanent freezing — consistent with a Medium-severity analog.

### Recommendation
- Do not add a deposit token to the recipient's per-account list on plain `transfer`/`transferFrom` when `amount_` is below a meaningful threshold, or only track tokens added via `deposit`/`seize`.
- Alternatively, allow anyone to call a `removeFromDepositTokensOfAccount`-style cleanup when the caller's balance is zero, or let the list auto-prune entries whose balance is zero before enforcing `MAX_TOKENS_PER_USER`.

### Proof of Concept
```solidity
// Foundry fork test sketch
function testDustFillVictimSlots() public {
    address victim = makeAddr("victim");
    // pool has >= 30 deposit tokens registered
    for (uint i; i < 30; i++) {
        IDepositToken dt = IDepositToken(pool.depositTokens().at(i));
        IERC20 underlying = dt.underlying();
        deal(address(underlying), attacker, 1);
        underlying.approve(address(dt), 1);
        dt.deposit(1, attacker);          // attacker gets dust share
        dt.transfer(victim, 1);           // adds dt to victim's list
    }
    // victim now has 30 entries; any new debt mint reverts
    vm.prank(victim);
    vm.expectRevert(Pool.UserReachedMaxTokens.selector);
    debtToken.issue(amount, victim);      // reverts in _mint -> addToDebtTokensOfAccount
    // recovery: victim transfers dust out, then issue succeeds
}
```
