Based on my investigation, I found a plausible analog in the TVM precompiled contracts array-extraction helpers, which is the closest match in java-tron to the openSAFETY dissector's "missing length validation → crash/memory exhaustion" bug class.

### Title
Unbounded attacker-controlled array length in TVM precompile calldata decoding causes uncatchable `OutOfMemoryError` - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The helper routines used to decode dynamic array parameters from smart-contract calldata inside `PrecompiledContracts` read a length field directly from attacker-supplied calldata and use it to size a Java array with no upper-bound check, mirroring the openSAFETY dissector flaw (CVE-2017-11411) where a length field taken from untrusted input was used without validation, permitting a crash or memory exhaustion.

### Finding Description
`extractBytes32Array` and `extractBytesArray` take `len` directly from a `DataWord` in the caller-supplied calldata via `intValueSafe()` and immediately allocate an array of that size: [1](#0-0) [2](#0-1) 

`extractBytesArray` performs a check that `offset` is within `words.length`, but does not bound `len` itself before allocating `new byte[len][]`. `extractBytes32Array` performs no bounds check at all before indexing `words[offset]` or allocating. Because `DataWord.intValueSafe()` can return values as large as `Integer.MAX_VALUE` for an oversized 256-bit word, an attacker can supply calldata that decodes to a length of `Integer.MAX_VALUE`, causing the JVM to attempt to allocate an object array on that order of magnitude, which throws `OutOfMemoryError` (an `Error`, not an `Exception`).

These helpers are reached from `ValidateMultiSign` and `BatchValidateSign`, TVM precompiled contracts enabled once `VMConfig.allowTvmSolidity059()` is active, dispatched from `getContractForAddress`: [3](#0-2) 

Both precompiles are directly reachable by any address that deploys or calls a contract invoking the `validateMultiSign`/`batchValidateSign` precompile addresses with crafted calldata — i.e., an unprivileged transaction broadcaster/contract caller, matching the CVE-2017-11411 threat model of an untrusted remote input driving unchecked length-based allocation.

Note: because `Error` (unlike `RuntimeException`) is generally not caught by ordinary `catch (Exception e)` blocks in the TVM execution pipeline, an `OutOfMemoryError` thrown mid-transaction-execution risks propagating out of the executing thread. Depending on how the node's block-application/transaction-execution thread handles uncaught `Error`s, this can abort in-flight processing or destabilize the node process — analogous to the "crash or exhaust system memory" impact described in the CVE. I was not able to fully trace, within the available tool budget, whether an enclosing `catch (Throwable ...)` exists specifically around precompile `execute()` invocation in `Program`/`VM`, so the exact blast radius (isolated revert vs. broader node instability) is not fully confirmed from the code I retrieved.

### Impact Explanation
If uncaught, a JVM `OutOfMemoryError` triggered during transaction execution can disrupt the node's ability to process further transactions/blocks (denial of service / potential chain halt for that node), which falls within the "node crash or halt" impact category. Even in the best case where the error is caught generically, the attempted allocation itself is a resource-exhaustion vector reachable from ordinary contract calls.

### Likelihood Explanation
Any account can broadcast a transaction that calls a contract invoking `validateMultiSign` or `batchValidateSign` with crafted calldata containing a maliciously large length word; no special privileges are required, only a valid signed transaction and enough energy to reach the precompile call.

### Recommendation
Add explicit upper-bound validation on `len` in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` (e.g., reject if `len` exceeds a small sane cap or exceeds what the remaining calldata size can support) before performing `new byte[len][]`, similar to how `isValidAbiEncoding` bounds-checks are already used elsewhere in this file: [4](#0-3) 

### Proof of Concept
Construct calldata for a call into a contract that forwards to the `validateMultiSign`/`batchValidateSign` precompile address, where the ABI-encoded dynamic array "length" word (consumed by `extractBytes32Array`/`extractBytesArray` via `words[offset].intValueSafe()`) is set to `0xFFFFFFFF`-class value (decoding to `Integer.MAX_VALUE`). Broadcasting this transaction drives the precompile's `execute(byte[] data)` into `new byte[len][]`, causing an immediate `OutOfMemoryError` during transaction execution.

---
**Caveat on confidence**: I could not retrieve the full body of `ValidateMultiSign.execute()` / `BatchValidateSign.execute()` (only their existence and test files were confirmed) due to tool-call limits, so I cannot fully confirm whether an earlier length/size check already constrains `len` before these helper calls, or whether a `catch (Throwable)` wraps precompile execution somewhere up the call stack. This should be verified directly in the full file before treating the finding as conclusively exploitable.
