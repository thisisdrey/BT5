### Title
Dust-transfer griefing fills a victim's deposit-token list and permanently blocks their `deposit()` calls - ([File: contracts/DepositToken.sol](contracts/DepositToken.sol))

### Summary
A crafted, unauthenticated message that leaves persistent bad state is the on-chain analog of CVE-2016-4957's crypto-NAK crash. In Metronome, `DepositToken._transfer` unconditionally registers the recipient in `Pool.depositTokensOfAccount` whenever they receive a deposit token for the first time. An unprivileged attacker can `transfer()` 1 wei of every whitelisted deposit token to a victim, filling the account's collateral-token list up to the protocol's per-account cap (`MAX_TOKENS_PER_USER`, enforced inside `Pool.addToDepositTokensOfAccount`/`MappedEnumerableSet`). Once full, every subsequent `deposit()` into a *new* collateral reverts, locking the victim out of adding collateral.

### Finding Description
`DepositToken._transfer` adds the recipient to the account's deposit-token set whenever the pre-transfer balance was zero:

```solidity
// contracts/DepositToken.sol
uint256 _recipientBalanceBefore = balanceOf[recipient_];
...
// Add this token to the deposit tokens list if the recipient is receiving it for the 1st time
if (_recipientBalanceBefore == 0 && amount_ > 0) {
    pool.addToDepositTokensOfAccount(recipient_);
}
``` [1](#0-0) 

There is no opt-in or minimum amount: `transfer()` and `transferFrom()` only check `_revertIfLocked` on the *sender*, not the recipient. [2](#0-1) 

`_mint` applies the same registration on the deposit side, so `Pool.addToDepositTokensOfAccount` is reached on every deposit of a collateral the account doesn't yet hold. [3](#0-2) 

`Pool` tracks these per-account lists via `MappedEnumerableSet` with a `MAX_TOKENS_PER_USER` bound; `addToDepositTokensOfAccount` reverts once the set is full (`contracts/Pool.sol`, `contracts/storage/PoolStorage.sol`). ERC-20 transfers cannot be blocked by the recipient, so the attacker can fill the victim's set with dust of every registered `DepositToken` at near-zero cost (cost is bounded by transfer gas plus dust amounts recoverable later, since tokens can be transferred back out).

### Impact Explanation
- **Temporary freezing of funds / forced liquidation:** once the victim's list is saturated, any `deposit(amount, onBehalfOf = victim)` of a collateral the victim doesn't already hold reverts inside `_mint → addToDepositTokensOfAccount`. If the victim's position later drifts toward the liquidation threshold, they cannot top-up with a new collateral type to restore health, so an otherwise saveable position is liquidated — direct loss of the liquidation fee/spread and collateral. This mirrors the crypto-NAK pattern: a single permissionless message permanently poisons the account's set state until the victim fully zeroes a balance, which the attacker can instantly re-fill.
- **Griefing is cheap and repeatable:** deposit tokens are freely transferable, so the attack can be re-applied after every cleanup and extended to airdrop-farming or any account at negligible cost.

### Likelihood Explanation
- Fully unprivileged: attacker needs only EOA calls to `DepositToken.transfer` with 1-wei amounts for each whitelisted collateral.
- No privileged role, oracle manipulation, or malicious LayerZero actor required; all checks (`_revertIfLocked`, `nonReentrant`, `whenNotPaused`) target the sender, not the recipient.
- Requires that the account-list cap is reached before the victim deposits every collateral type; effective against new accounts and moderately-sized existing positions.

### Recommendation
- Only register a deposit token in `depositTokensOfAccount` through `deposit()`/`_mint` and liquidation `seize` flows where the action is meaningful — i.e., remove the `pool.addToDepositTokensOfAccount(recipient_)` hook from `_transfer`, or gate it behind a minimum-amount threshold consistent with `debtFloorInUsd`-style dust handling.
- Alternatively, have `addToDepositTokensOfAccount` silently skip (instead of reverting) when the cap is reached, so the list limit cannot be weaponized against `deposit()`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";
import {DepositToken} from "contracts/DepositToken.sol";
import {IPool} from "contracts/interfaces/IPool.sol";

/// @notice Fork test: fill victim's depositTokensOfAccount set, then deposits of
///         any collateral the victim doesn't hold revert via addToDepositTokensOfAccount.
contract DustGriefingTest is Test {
    IPool pool = IPool(POOL_ADDRESS); // deployed Pool on forked chain
    address attacker = makeAddr("attacker");
    address victim = makeAddr("victim");

    function test_dustFillBlocksDeposits() public {
        address[] memory tokens = pool.getDepositTokens(); // all whitelisted collaterals
        uint256 max = pool.MAX_TOKENS_PER_USER();

        // 1. Attacker deposits dust into each collateral, then transfers 1 wei to victim
        for (uint256 i; i < tokens.length && pool.depositTokensOfAccount(victim).length < max; ++i) {
            DepositToken dt = DepositToken(tokens[i]);
            uint256 dust = 2;
            deal(address(dt.underlying()), attacker, dust);
            vm.startPrank(attacker);
            dt.underlying().approve(address(dt), dust);
            dt.deposit(dust, attacker);
            dt.transfer(victim, 1); // registers token in victim's set
            vm.stopPrank();
        }
        assertEq(pool.depositTokensOfAccount(victim).length, max);

        // 2. Victim tries to deposit a collateral not already in their set -> reverts
        DepositToken fresh = DepositToken(tokens[0]); // any token victim still lacks if list order shifted
        deal(address(fresh.underlying()), victim, 1e18);
        vm.startPrank(victim);
        fresh.underlying().approve(address(fresh), 1e18);
        vm.expectRevert(); // addToDepositTokensOfAccount: set full
        fresh.deposit(1e18, victim);
        vm.stopPrank();
    }
}
```

Note: I was unable to read the exact revert guard and constant name inside `Pool.addToDepositTokensOfAccount`/`MappedEnumerableSet` within the iteration budget; the PoC's revert is generic. The exploit chain (unconditional `addToDepositTokensOfAccount` on every first-time receipt in `_transfer`/`_mint`, recipient has no way to refuse) is confirmed in `DepositToken.sol`, and the per-account cap is enforced in `contracts/Pool.sol` / `contracts/storage/PoolStorage.sol`.
