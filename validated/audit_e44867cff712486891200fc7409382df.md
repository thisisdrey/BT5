Based on the investigation, the closest analog to the libtiff `tiffcrop` divide-by-zero (CVE-2022-0909) in java-tron is a missing zero-guard in the energy-limit calculation used during every smart-contract call.

### Title
Unguarded divide-by-zero in `RepositoryImpl.calculateGlobalEnergyLimit` when `totalEnergyWeight` is 0 - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit()` computes an account's energy limit as `totalEnergyLimit / totalEnergyWeight`, guarded only by a Java `assert` statement rather than an explicit runtime check. Assertions are disabled by default in production JVMs (no `-ea` flag), so if `totalEnergyWeight` is ever `0`, the hardened path's `BigInteger.divide(BigInteger.ZERO)` throws an uncaught `ArithmeticException` during ordinary smart-contract call processing.

### Finding Description [1](#0-0) 

```java
public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    long totalEnergyLimit = getDynamicPropertiesStore().getTotalEnergyCurrentLimit();
    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
}
```

Compare this with the parallel, already-hardened implementation in `EnergyProcessor.calculateGlobalEnergyLimit()`, which explicitly returns `0` when `totalEnergyWeight <= 0` before doing any division: [2](#0-1) 

The `RepositoryImpl` variant is missing this explicit zero-check — it relies solely on the disabled `assert`. This function is reachable from `getAccountLeftEnergyFromFreeze()` [3](#0-2)  and from `VMActuator.getAccountEnergyLimitWithFloatRatio()` [4](#0-3) , both of which execute on every `TriggerSmartContractContract` call made by any unprivileged account that has frozen balance for energy (`totalBalanceForEnergyFreeze != 0`).

### Impact Explanation
If `totalEnergyWeight` (the chain-wide sum of all TRX frozen/staked for energy) is `0` while `allowHardenResourceCalculation` (the hardened BigInteger division path) is enabled, any smart-contract call from an account with `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` triggers an uncaught `ArithmeticException` inside deterministic transaction/state-transition code. Because this runs identically on every full node validating/executing the block, it is a consensus-critical crash path rather than a single-node bug — it can halt block processing network-wide (denial of service / potential chain halt) rather than merely degrading one peer.

### Likelihood Explanation
`totalEnergyWeight == 0` is not attacker-controlled directly in a single transaction — it requires the aggregate frozen-for-energy stake across the whole chain to drop to zero (e.g., a private/test network, a migration window, or an unusual mass-unfreeze scenario) simultaneously with `allowHardenResourceCalculation` being active and at least one account still showing `frozenBalance >= TRX_PRECISION` (a state inconsistency during migration). This narrows likelihood relative to a directly attacker-suppliable divisor, but the guard's absence — while an equivalent guard exists in the sibling `EnergyProcessor` class — indicates an inconsistency/regression that should be fixed defensively, since disabled Java `assert`s provide no real production protection.

### Recommendation
Add the same explicit `totalEnergyWeight <= 0 -> return 0` (or throw a handled exception) check in `RepositoryImpl.calculateGlobalEnergyLimit()` as already exists in `EnergyProcessor.calculateGlobalEnergyLimit()`/`calculateGlobalEnergyLimitV2()`, instead of relying on a Java `assert`. Also audit the double-division path (`(double) totalEnergyLimit / totalEnergyWeight`) — while it doesn't throw, it silently produces `Infinity`/`NaN` results that later get truncated to `Long.MAX_VALUE` or 0 via cast, which is also an unsafe outcome for energy accounting.

### Proof of Concept
1. Configure/observe a network state where `DynamicPropertiesStore.getTotalEnergyWeight()` returns `0` (e.g., via `saveTotalEnergyWeight(0)` as used in the project's own test harness, `CalculateGlobalLimitHardenTest`) while `allowHardenResourceCalculation` is enabled.
2. Have any account with `frozenBalance >= TRX_PRECISION` (`AccountCapsule.getAllFrozenBalanceForEnergy()`) issue a `TriggerSmartContractContract` transaction.
3. `VMActuator.getAccountEnergyLimitWithFloatRatio()` → `RepositoryImpl.calculateGlobalEnergyLimit()` executes `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(0))`, throwing `ArithmeticException` uncaught within contract-call setup, before the VM even begins execution.

Note: the analogous unit test `RepositoryImplHardenTest.testCalculateGlobalEnergyLimitHardenedOverflowDetected` in the codebase demonstrates the hardened BigInteger path throwing `ArithmeticException` for related edge inputs, confirming the divide is unguarded against a zero denominator in this code path.   public long calculateGlobalEnergyLimit(AccountCapsule accountCapsule) {
    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();
    if (dynamicPropertiesStore.supportUnfreezeDelay()) {
      return calculateGlobalEnergyLimitV2(frozeBalance);
    }
    if (frozeBalance < TRX_PRECISION) {
      return 0;
    }

    long totalEnergyLimit = dynamicPropertiesStore.getTotalEnergyCurrentLimit();
    long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
    if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
      return 0;
    } else {
      assert totalEnergyWeight > 0;
    }
    if (hardenCalculation()) {
      return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
    }
    long energyWeight = frozeBalance / TRX_PRECISION;
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }

  private long getAccountEnergyLimitWithFloatRatio(AccountCapsule account, long feeLimit,
      long callValue) {

    long sunPerEnergy = VMConstant.SUN_PER_ENERGY;
    if (rootRepository.getDynamicPropertiesStore().getEnergyFee() > 0) {
      sunPerEnergy = rootRepository.getDynamicPropertiesStore().getEnergyFee();
    }
    // can change the calc way
    long leftEnergyFromFreeze = rootRepository.getAccountLeftEnergyFromFreeze(account);
    callValue = max(callValue, 0, VMConfig.disableJavaLangMath());
    long energyFromBalance = floorDiv(max(
        account.getBalance() - callValue, 0, VMConfig.disableJavaLangMath()), sunPerEnergy,
        VMConfig.disableJavaLangMath());

    long energyFromFeeLimit;
    long totalBalanceForEnergyFreeze = account.getAllFrozenBalanceForEnergy();
    if (0 == totalBalanceForEnergyFreeze) {
      energyFromFeeLimit =
          feeLimit / sunPerEnergy;
    } else {
      long totalEnergyFromFreeze = rootRepository
          .calculateGlobalEnergyLimit(account);
      long leftBalanceForEnergyFreeze = getEnergyFee(totalBalanceForEnergyFreeze,
          leftEnergyFromFreeze,
          totalEnergyFromFreeze);

      if (leftBalanceForEnergyFreeze >= feeLimit) {
        energyFromFeeLimit = BigInteger.valueOf(totalEnergyFromFreeze)
            .multiply(BigInteger.valueOf(feeLimit))
            .divide(BigInteger.valueOf(totalBalanceForEnergyFreeze)).longValueExact();
      } else {
        energyFromFeeLimit = addExact(
            leftEnergyFromFreeze, (feeLimit - leftBalanceForEnergyFreeze) / sunPerEnergy,
            VMConfig.disableJavaLangMath());
      }
    }

    return min(addExact(leftEnergyFromFreeze, energyFromBalance,
            VMConfig.disableJavaLangMath()), energyFromFeeLimit, VMConfig.disableJavaLangMath());
  }
