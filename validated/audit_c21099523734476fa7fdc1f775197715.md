### Title
Transactional Object Packing Skips Object Validity Checks Before Committing to the Repository - (`internal/gitaly/storage/storagemgr/partition/transaction_manager.go`)

### Summary
When Gitaly's WAL-based transaction system (`TransactionManager`) processes a push, it builds the transaction's packfile directly from the objects an ordinary client wrote into the push's quarantine directory. This packing step (`packObjects`) walks the quarantine objects and their reference dependencies and repacks them with `git pack-objects`/`git index-pack`, but the code explicitly does not check that the packed objects are actually valid Git objects before they are staged and later committed into the repository's real object store.

### Finding Description
`packObjects` is documented in its own comment as skipping object validity checking: [1](#0-0) 

The function reads objects out of the quarantine directory (`quarantineOnlySnapshotRepository`), walks them along with the new reference tips via `WalkObjects`, and any object encountered that is present in quarantine is fed straight into `PackObjects`/`index-pack` without invoking `git fsck`/`transfer.fsckObjects` semantics: [2](#0-1) [3](#0-2) 

By contrast, the conventional `receive-pack`/`fetch-pack` code paths that don't go through this transactional flow always force fsck validation of objects coming from an untrusted client: [4](#0-3) 

The only check that happens later, at commit time, is that the transaction's *dependencies* (objects not found in the quarantine walk, i.e. objects that must already exist in the destination repository) are present — this is an existence check, not a content/format validity check: [5](#0-4) 

This mirrors the LineaRollup pattern in the external report: data supplied by an untrusted submitter (the git client) is accepted and committed to durable state based on an internal recomputation (`_calculateY`/here, `packObjects`) without cross-checking it against the independent validity guarantee that the non-transactional path enforces (`_calculateY` vs prover `y`; here, fsck object validity). The gap is only closed later or not at all, analogous to the report’s finalization-time failure requiring resubmission.

### Impact Explanation
Because this transactional packing path is used for Gitaly's newer WAL-backed storage (used by partitioned repositories/transactions), a client pushing through this path can have malformed/non-fsck-compliant Git objects (e.g., objects that would normally be rejected by `receive.fsck`/`transfer.fsckObjects`, such as trees with duplicate entries or other structurally invalid content covered by `git-fsck(1)`) accepted and durably written into the repository's real object store, bypassing the object-quality gate that the rest of Gitaly relies on (as demonstrated for the classic path by `TestPostReceivePack_fsck`, which the transactional path has no equivalent for at the packing stage). This can degrade repository integrity guarantees and repository consistency checks (`git fsck`), and downstream consumers/mirrors of the repository.

### Likelihood Explanation
Any ordinary user capable of pushing to a repository backed by the transactional storage manager reaches this code path, since `packObjects` runs unconditionally for every repository-targeting transaction as part of processing the pushed quarantine directory. No special privileges, secrets, or race conditions are required — it's simply a consequence of how `packObjects` repacks quarantined objects.

### Recommendation
Add a validity check equivalent to `git fsck`/`transfer.fsckObjects` on the packfile being staged in `packObjects` before it is recorded via `walEntry.CreateFile` for commit, consistent with the fsck configuration already applied to git-native `receive-pack`/`fetch-pack` invocations. The referenced tracking issue (`gitlab-org/gitaly#5779`, cited directly in the code) should be resolved as part of the fix.

### Proof of Concept
1. Configure a repository under the WAL-backed transactional storage (partition) manager.
2. As a normal user, push a commit whose tree contains duplicate entries (as shown to be rejected by classic `receive-pack` fsck in `TestPostReceivePack_fsck`, `internal/gitaly/service/smarthttp/receive_pack_test.go:631-676`), but via a transaction that goes through `TransactionManager.packObjects`.
3. Observe that `packObjects` walks and packs the object without invoking any fsck-equivalent check (per the function's own doc comment, `transaction_manager.go:1317-1318`), and the object becomes part of the committed pack, whereas the same push through the classic `receive-pack` code path (with `transfer.fsckObjects=true`) would be rejected.

func receiveFsckConfiguration(ctx context.Context) []GlobalOption {

// templateFsckConfiguration generates our fsck configuration, including ignored checks.
// The prefix must either be "fsck", "receive.fsck" or "fetch.fsck" and indicates whether
// it should apply to git-fsck(1), git-receive-pack(1) or to git-fetch-pack(1).
func templateFsckConfiguration(_ context.Context, prefix string) []GlobalOption {
	configPairs := []GlobalOption{
		// When receiving objects from an untrusted source, we want to always assert that
		// all objects are valid. When fetch.fsckObjects or receive.fsckObjects are not set,
		// the value of transfer.fsckObjects is used instead. Since the fsck configuration
		// of git-fetch-pack(1) and git-receive-pack(1) is coupled, transfer.fsckObjects can
		// be used for both.
		ConfigPair{Key: "transfer.fsckObjects", Value: "true"},
	}
