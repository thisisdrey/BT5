### Title
`insert_instantiated_attachment` stores peer-served attachments without enforcing `attachments_max_size` - (File: stackslib/src/net/atlas/download.rs)

### Summary
The Atlas peer-download path (`AttachmentsBatchStateContext::extend_with_attachments` → `AtlasDB::insert_instantiated_attachment`) writes attachment content received from remote peers into the `attachments` table without ever calling `AtlasDB::should_keep_attachment`, which is the only place that checks `attachment.content.len() <= attachments_max_size`. That check is only enforced on the mempool/HTTP POST ingestion path. A malicious peer serving a `GET /v2/attachments/:hash` response can therefore have its oversized content persisted to the local Atlas DB, bounded only by the generic `MAX_MESSAGE_LEN` HTTP body cap rather than the operator-configured `attachments_max_size`.

### Finding Description
`AtlasDB::should_keep_attachment` at [1](#0-0)  is the sole enforcement point for `content.len() <= atlas_config.attachments_max_size`, and it is invoked only from the mempool contract-call attachment path (as referenced in `posttransaction.rs`). The peer attachment-download flow is entirely separate: `AttachmentsBatchStateContext::extend_with_attachments` decodes an HTTP `GetAttachmentResponse` from a remote peer and inserts the raw content into `self.attachments` with no size check at all [2](#0-1) . Those attachments are subsequently written straight into the database via `AtlasDB::insert_instantiated_attachment`, again with no size validation [3](#0-2) [4](#0-3) . The same unguarded call also occurs in `check_attachment_instances` when resolving previously-inboxed attachments [5](#0-4) . The `test_keep_uninstantiated_attachments` test in `stackslib/src/net/atlas/tests.rs` confirms `should_keep_attachment` is the only size gate that exists and it is never invoked from the download flow [6](#0-5) .

The only guard actually present on the wire is the generic HTTP decoder's `MAX_MESSAGE_LEN` cap enforced when parsing arbitrary JSON/byte HTTP bodies [7](#0-6) . However `RPCGetAttachmentRequestHandler::try_parse_response` parses the body strictly as JSON via `parse_json` [8](#0-7) , and its `decode_atlas_get_attachment` further deserializes into `GetAttachmentResponse`, whose custom `Deserialize` hex-decodes the payload string into `Attachment.content` with no additional length check [9](#0-8) . I was not able to fully pin down the exact numeric value of `MAX_MESSAGE_LEN` in this snapshot (only located it declared in `stacks-common/src/codec/mod.rs`, but did not confirm the value), so I cannot state with certainty how much larger than `attachments_max_size` (1 MiB minimum) the effective ceiling is — this is an uncertain point that a Devin session with full file access should verify. Regardless of the exact `MAX_MESSAGE_LEN` value, the equality the operator configures (`attachments_max_size`) is bypassed entirely on this path, since it is never consulted.

### Impact Explanation
A malicious or compromised peer (no privileged role required — any peer that can respond to an `AttachmentRequest`, i.e., is listed as a source in the requesting node's inventory results) can cause a victim node to persist attachment blobs into its local SQLite Atlas DB that exceed the configured `attachments_max_size`, up to whatever the generic HTTP body/message-length ceiling allows. This is repeatable per distinct `AttachmentInstance`/content hash the victim is trying to resolve, and since Atlas attachment resolution runs continuously as part of normal P2P duty cycling (`do_attachment_downloads` in `p2p.rs`), an attacker controlling or spoofing enough of the network view can serve many oversized attachments over time. The impact is storage exhaustion on the victim's Atlas database that bypasses the size ceiling the operator explicitly configured to bound it — matching the "bounded compute/storage DoS via a read endpoint" style High-severity category (storage exhaustion rather than crash, since the write path completes and just stores oversized data).

### Likelihood Explanation
Preconditions are modest: the victim node must have Atlas enabled with `attachments_max_size` at or near `ATTACHMENTS_MAX_SIZE_MIN` (1,048,576 bytes, the enforced minimum per `AtlasConfig::validate`) [10](#0-9) [11](#0-10) , and there must be at least one `AttachmentInstance` pending resolution that the victim is actively trying to fetch (created from on-chain BNS/contract-call events, so an attacker also needs a matching content hash mapping, achievable by controlling both the emitting contract-call attachment instance and the serving peer, or by being selected as a serving source for a legitimately-emitted instance). Attacker cost is low: run/control a peer that the victim treats as an outbound sync peer and reply to `GET /v2/attachments/{hash}` with an oversized (but content-hash-matching) payload. No secrets, signatures, or privileged roles are needed.

### Recommendation
Enforce `should_keep_attachment`-equivalent size (and optionally contract) validation in the download path before persisting content: call a length check against `atlas_config.attachments_max_size` inside `extend_with_attachments` before inserting into `self.attachments`, and/or add the same check inside `AtlasDB::insert_instantiated_attachment` (and the `find_uninstantiated_attachment`-triggered call in `check_attachment_instances`) so that all writers to the `attachments` table are covered by the same size ceiling, not just the mempool/HTTP POST path.

### Proof of Concept
Add a Rust unit test in `stackslib/src/net/atlas/tests.rs` (or `download.rs`) similar to `test_keep_uninstantiated_attachments`, but exercising the download path:
1. Construct an `AtlasConfig` with `attachments_max_size: 16` (as in the existing test).
2. Construct an `Attachment` whose `content.len() > 16` (e.g., `new_attachment_from("facadefacadefacade02")`, already shown in the test file to fail `should_keep_attachment`).
3. Build a `BatchedRequestsResult<AttachmentRequest>` with a `succeeded` entry whose response, when `decode_atlas_get_attachment()`'d, yields this oversized `Attachment` (mirroring how `test_try_make_response` in `stackslib/src/net/api/tests/getattachment.rs` constructs and decodes a `GetAttachmentResponse`).
4. Call `AttachmentsBatchStateContext::extend_with_attachments(&mut results)` and then drive it through to `AtlasDB::insert_instantiated_attachment`.
5. Assert: `atlas_db.find_attachment(&attachment.hash())` returns `Some(attachment)` despite `atlas_db.should_keep_attachment(&contract_id, &attachment) == false` for the same content — proving the size ceiling is bypassed on the download-insert path while being enforced on the mempool-insert path.

    pub fn should_keep_attachment(
        &self,
        contract_id: &QualifiedContractIdentifier,
        attachment: &Attachment,
    ) -> bool {
        if !self.atlas_config.contracts.contains(contract_id) {
            info!(
                "Atlas: will discard posted attachment - {} not in supported contracts",
                contract_id
            );
            return false;
        }
        if attachment.content.len() as u32 > self.atlas_config.attachments_max_size {
            info!("Atlas: will discard posted attachment - attachment too large");
            return false;
        }
        true
    }

impl Serialize for GetAttachmentResponse {

    }

impl<'de> Deserialize<'de> for GetAttachmentResponse {
    fn deserialize<D: serde::Deserializer<'de>>(d: D) -> Result<GetAttachmentResponse, D::Error> {
        let payload = String::deserialize(d)?;
        let hex_encoded = payload.parse::<String>().map_err(de_Error::custom)?;
        let bytes = hex_bytes(&hex_encoded).map_err(de_Error::custom)?;
        let attachment = Attachment::new(bytes);

    }
