### Title
Exchange pool balances can go negative under the legacy (non-hardened) TRC10 AMM math, producing incorrect internal exchange prices - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java])

### Summary
`ExchangeCapsule.transaction()` is the constant-product/bancor-style AMM math used by `ExchangeTransactionActuator`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` to update a TRC10 exchange pool's `firstTokenBalance`/`secondTokenBalance` on every trade. Just like the reported bug ("the system assumes total supply of a token will not decrease, and no explicit check/error/try-catch guards the case it does"), the legacy path here assumes the computed `buyTokenQuant` will never exceed the pool's actual reserve, and performs the balance update with plain arithmetic and no lower-bound check unless a chain-wide proposal (`AllowHardenExchangeCalculation`) has been activated.

### Finding Description
`ExchangeCapsule.transaction()` computes the new pool balances after a trade: [1](#0-0) 

When `hardenedCalc` is `false` (the default, legacy behavior), `newFirstTokenBalance`/`newSecondTokenBalance` are computed with plain `long` addition/subtraction, and the method explicitly skips the `< 0` sanity check that only runs `if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0))`. The underlying pricing math (`ExchangeProcessor.exchange()`) uses floating-point `Math.pow` on a virtual "supply" variable to compute `buyTokenQuant`: [2](#0-1) 

This float-based calculation can, under specific reserve ratios/quantities (rounding, edge cases near a fully-drained pool, or repeated small trades), yield a `buyTokenQuant` that is larger than the pool's actual reserve of the token being bought. In the legacy path there is no validation to reject this: the resulting negative `firstTokenBalance`/`secondTokenBalance` is written straight to the `Exchange` proto via `Commons.putExchangeCapsule()` and persisted in `ExchangeStore`/`ExchangeV2Store`.

Whether the `AllowHardenExchangeCalculation` proposal is active is checked per-call via `AbstractExchangeActuator.allowHarden()`: [3](#0-2) 

`ExchangeTransactionActuator.execute()` passes this flag straight into `exchangeCapsule.transaction()` without any additional guard: [4](#0-3) 

This is precisely the class of bug described in the external report: an assumption ("pool balance/available supply of a token can only move in the expected direction by the expected amount") is not defensively verified, so once it is violated the internal accounting (pool reserves, and therefore the exchange rate `firstTokenBalance/secondTokenBalance`) becomes wrong — with no explicit error, try/catch, or redesign to reject the bad state on the legacy path. Once a negative reserve is committed, every subsequent `SafeExchangeProcessor`/`ExchangeProcessor` calculation reading that corrupted balance produces further-skewed exchange rates, similar to how a decreasing rebase-token supply corrupts `LibTokenizedVault`'s internal price in the original report.

### Impact Explanation
A corrupted (negative) reserve in `firstTokenBalance`/`secondTokenBalance` permanently distorts the on-chain exchange rate for that TRC10 exchange pair, letting subsequent traders extract more of the counter-asset than the pool actually holds (arbitrage/drain), or making the pool permanently un-tradeable/inconsistent with real backing. Because `ExchangeCapsule` state is committed to `ExchangeStore`/`ExchangeV2Store` and read by every later `ExchangeTransactionActuator`/`ExchangeInjectActuator`/`ExchangeWithdrawActuator` call, this is a lasting on-chain state corruption, not merely a transient rejected transaction. This matches the "unbacked balance / incorrect internal price -> arbitrage exposure" impact class called out in the original finding.

### Likelihood Explanation
This requires the `AllowHardenExchangeCalculation` chain parameter to still be disabled (its default/legacy state, per `saveAllowHardenExchangeCalculation`/`allowHardenExchangeCalculation` gating in `DynamicPropertiesStore`), and requires finding an input (`tokenQuant`, existing pool reserves) where the floating-point bancor formula in `ExchangeProcessor` returns a `buyTokenQuant` exceeding the actual counter-reserve. This is a specific but realistic edge case (very small or heavily-skewed reserves, or repeated near-drain trades against dust reserves), reachable by any account issuing a standard `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transaction — no special privilege required.

### Recommendation
Apply the same `>= 0` invariant check used in the hardened path (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0` throws `ContractValidateException`) unconditionally, regardless of the `hardenedCalc`/`AllowHardenExchangeCalculation` flag, so that any computed trade that would push a reserve negative is rejected rather than silently committed. Alternatively, make `AllowHardenExchangeCalculation` (or an equivalent invariant check) always-on rather than proposal-gated, removing the legacy unguarded code path entirely.

### Proof of Concept
Not independently reproduced with concrete numeric inputs from static analysis alone; the vulnerable code path is confirmed via:
- Missing invariant enforcement in the legacy branch: [5](#0-4) 
- The existence of a dedicated hardened fix path guarding this exact scenario (`allowHardenExchangeCalculation`/`SafeExchangeProcessor`), which is only activated by chain proposal and not the default: [6](#0-5) 
Reproducing an end-to-end negative-balance trade would require crafting a sequence of `ExchangeCreateContract` + `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions against specific reserve ratios and confirming via a Devin session with the ability to run the existing test harness (e.g., `ExchangeProcessorTest`, `ExchangeCapsuleTest`) with fuzzed reserve/quant inputs while `AllowHardenExchangeCalculation` is left at its default (disabled) value.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
