## Analysis

I found a strong analog: unbounded, permanent growth of a per-repository data structure (`refs/dangling/$OID` references in an object pool) that is created automatically in response to unprivileged, everyday Git operations (force-pushes by any pool member), can never be pruned by design, and is iterated/processed on every subsequent `FetchIntoObjectPool` housekeeping run and repack — directly mirroring the C4 report's root cause (an ever-growing, unprunable, iterated array that any unprivileged actor can inflate to degrade/DoS future operations).

### Title
Unbounded, unprunable growth of `refs/dangling/$OID` references in shared object pools enables cross-tenant DoS of pool housekeeping - (File: internal/git/objectpool/fetch.go)

### Summary
`ObjectPool.FetchFromOrigin` fetches from any pool member into the shared object pool and then calls `rescueDanglingObjects`, which runs `git fsck --dangling` and creates a permanent `refs/dangling/$OID` reference for every dangling object found [1](#0-0) . Because the pool cannot ever determine whether an object is still needed by some other member, these references are explicitly designed to never be deleted [2](#0-1) , matching the documented design intent in `doc/object_pools.md`: "there is no point in time where it's safe to delete objects from the object pool" [3](#0-2) .

### Finding Description
Any member of an object pool (i.e., any fork of a repository sharing the pool) can trigger `FetchIntoObjectPool`, which internally prunes refs deleted at origin and then fetches with `--atomic` into the pool via `objectPoolRefspec` [4](#0-3) . Any ordinary force-push or branch deletion by a pool-member user that turns previously-reachable pool objects into "dangling" objects causes `rescueDanglingObjects` to create a brand-new, permanent `refs/dangling/$OID` reference for each such object [5](#0-4) . The `doc/object_pools.md` file itself documents this side effect as unbounded: "For busy repositories, we generate loads of dangling references... Fetches into the object pool and repacking of references can thus become quite expensive" [6](#0-5) .

This is structurally identical to the C4 finding's root cause: (1) a data structure (`ownedCurvesTokenSubjects` array / here, the set of pool refs) that any unprivileged actor's routine action can append to; (2) no mechanism exists to shrink it back down, ever, by design; (3) it is iterated/processed on every subsequent operation — here, `git for-each-ref` in `logStats` [7](#0-6) , `git pack-refs` during housekeeping, and the full `git-repack` pass that must consider these refs as reachability roots to avoid deleting objects [8](#0-7) .

### Impact Explanation
As the number of dangling references grows without bound, `FetchIntoObjectPool` (which runs `for-each-ref`, `fsck --dangling`, `pack-refs`, and `repack` over the entire ref namespace) becomes progressively slower and more resource-intensive for the shared pool, affecting every member repository that depends on the same pool for fetch/clone/housekeeping — not just the pool member that triggered the growth. Any single, unprivileged pool member (e.g., a user with push access to just one fork) can repeatedly force-push and delete branches to churn objects into "dangling" state, continuously enlarging the pool's ref namespace and degrading — or, at scale, timing out/DoSing — housekeeping and read operations for all other members sharing that same object pool. This is a genuine resource-exhaustion/DoS vector reachable purely from ordinary push activity, matching the "DoS of a handler" acceptance criterion.

### Likelihood Explanation
Likelihood is significant: `FetchIntoObjectPool` housekeeping runs automatically and routinely (not gated behind privileged actions), and simply force-pushing/rewriting history in any fork that is a pool member is enough to generate new dangling objects on the next housekeeping pass. No special privilege beyond standard push access to one's own fork is required, matching the "ordinary user's push/fetch/fork" reachability requirement in the validation criteria. The team's own documentation flags this as a known, real-world scaling problem ("loads of dangling references... fetches...can thus become quite expensive"), indicating the growth is not theoretical.

### Recommendation
- Introduce a bound or aging/expiry policy for `refs/dangling/*` references (e.g., only keep the most recent objects, or expire dangling refs after object pools are known to have converged across all members), rather than relying purely on `git fsck --dangling` output for the pool's entire lifetime.
- Consider tracking dangling references in a more scalable structure than individual loose/packed refs per object (e.g., a single manifest/pack with metadata) to avoid O(n) ref-namespace growth and the associated iteration cost in `for-each-ref`, `pack-refs`, and `repack`.
- Add rate limiting/metrics-based alerting on the growth rate of `refs/dangling/*` per pool so operators can detect an actively-abusing pool member before housekeeping becomes prohibitively expensive.
- Evaluate whether pool membership dissociation or per-member quotas could bound how much dangling-ref growth a single member can cause.

### Proof of Concept
1. Create an object pool and link two independent fork repositories (`fork-A`, `fork-B`) to it as members, as described in `doc/object_pools.md` (`Link`) [9](#0-8) .
2. As the owner of `fork-A` (an ordinary, unprivileged user with push access only to `fork-A`), repeatedly:
   a. Push new commits/branches to `fork-A`.
   b. Force-push over them or delete the branches, so objects become unreachable in `fork-A`.
3. Each time `FetchIntoObjectPool` is run for the pool (triggered by normal GitLab housekeeping scheduling for `fork-A`), `rescueDanglingObjects` will discover the newly-dangling objects via `git fsck --dangling` and permanently create a `refs/dangling/$OID` for each one [5](#0-4) .
4. Repeat steps 2–3 in a loop (scriptable, requires only push access to `fork-A`) to accumulate an arbitrarily large number of `refs/dangling/*` references in the shared pool.
5. Observe that subsequent `FetchIntoObjectPool` runs and repacks for the pool — which affect `fork-B` and any other pool members — take progressively longer due to the growing ref namespace that must be enumerated (`for-each-ref`), packed (`pack-refs`), and preserved as repack roots (`repack` with delta islands over `refs/heads`/`refs/tags`, but full connectivity still spans all dangling refs).

```go
	// objects without having to create loads of dangling references. But unfortunately keeping
	// around old refs can lead to D/F conflicts between old references that have since
	// been deleted in the pool and new references that have been added in the pool member we're
	// fetching from. E.g. if we have the old reference `refs/heads/branch` and the pool member
	// has replaced that since with a new reference `refs/heads/branch/conflict` then
	// the fetch would now always fail because of that conflict.
	//
	// Due to the lack of an alternative to resolve that conflict we are thus forced to enable
	// pruning. This isn't too bad given that we know to keep alive the old objects via dangling
	// refs anyway, but I'd sleep easier if we didn't have to do this.
	//
	// Note that we need to perform the pruning separately from the fetch: if the fetch is using
	// `--atomic` and `--prune` together then it still wouldn't be able to recover from the D/F

	// objects yet to avoid that scenario.
```

```go
const danglingObjectNamespace = "refs/dangling/"

// rescueDanglingObjects creates refs for all dangling objects if finds
// with `git fsck`, which converts those objects from "dangling" to
// "not-dangling". This guards against any object ever being deleted from
// a pool repository. This is a defense in depth against accidental use
// of `git prune`, which could remove Git objects that a pool member
// relies on. There is currently no way for us to reliably determine if
// an object is still used anywhere, so the only safe thing to do is to
// assume that every object _is_ used.
func (o *ObjectPool) rescueDanglingObjects(ctx context.Context) (returnedErr error) {
	stderr := &bytes.Buffer{}
	fsck, err := o.Repo.Exec(ctx, gitcmd.Command{
		Name:  "fsck",
		Flags: []gitcmd.Option{gitcmd.Flag{Name: "--connectivity-only"}, gitcmd.Flag{Name: "--dangling"}},
	},
		gitcmd.WithStderr(stderr),
		gitcmd.WithSetupStdout(),
	)
	if err != nil {
		return err
	}
```

```markdown
This issue is kind of unsolvable: there is no point in time where it's safe to
delete objects from the object pool, as we do not know which repositories may be
linked to it. And even if we knew, we cannot determine all references of all
repositories at once in a race-free manner. We thus must consider each object to
still be referenced somewhere.

As a safeguard to not lose any objects by accident, we thus create dangling
references in the object pool after the fetch in `FetchIntoObjectPool`. For each
dangling object, a reference `refs/dangling/$OID` is created which points into
the object. This assures that each object is still referenced.
```
