## Title
Signature malleability in `ValidateMultiSign` precompile allows double-counting the same signer's weight, bypassing multisig thresholds - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The external report flags OpenZeppelin's `ECDSA.recover`/`ECDSA.tryRecover` malleability class of bug: code that treats "the signature bytes themselves" as the replay-protection key (instead of the recovered signer/message) can be bypassed because ECDSA signatures are inherently malleable — a valid `(r, s, v)` triple has an equally valid `(r, n-s, v')` variant that recovers to the same address but has different raw bytes. `ValidateMultiSign` in java-tron exhibits exactly this anti-pattern.

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array, recovers an address for each one via `recoverAddrBySign`, and de-duplicates using the *raw signature bytes* merged with the recovered address, not the recovered address alone: [1](#0-0) 

The dedup logic is:
```
sign = merge(recoveredAddr, sign);
if (matrixContains(executedSignList, recoveredAddr)) {
    if (matrixContains(executedSignList, sign)) { continue; }   // only skips exact-byte repeats
    MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;                 // weight is added again for the SAME address
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```
If the same address appears again but the signature bytes differ, the code does *not* skip — it falls through and adds the address's weight to `totalWeight` a second time. `recoverAddrBySign` parses the signature with `Rsv.fromSignature`, which does no canonicalization of `s` (no low-S / EIP-2 style enforcement): [2](#0-1) 

Because ECDSA is malleable, any holder of a private key can locally derive a second, byte-distinct signature `(r, n-s, flipped-v)` over the exact same hash that recovers to their own address (this requires no interaction with other key holders and no secret knowledge beyond the original signature). Submitting both the original and the malleated variant in the `signatures` array passed to `ValidateMultiSign` causes the same signer's weight to be counted twice.

### Impact Explanation
`ValidateMultiSign` is the TVM precompile backing on-chain multisignature/permission checks used by broadcastable smart contracts (e.g., contract-level access control gates). A single signer who normally only holds enough weight to satisfy part of a threshold can self-generate a malleated duplicate of their own signature and reach `permission.getThreshold()` alone, without the cooperation of the other required key holders. This is an unauthorized-operation / access-control-bypass primitive reachable purely from an unprivileged contract-call transaction (anyone able to call a contract that uses this precompile with attacker-controlled signature bytes), and can lead to unauthorized approval/execution of privileged multisig-gated actions and consequent theft or misuse of funds/permissions.

### Likelihood Explanation
Likelihood is high for any deployed contract relying on `ValidateMultiSign` for M-of-N approval where the attacker already controls at least one signing key and needs to defeat the "other keys must also sign" requirement: deriving the malleated `s' = n - s` and adjusted `v` is a pure, deterministic, offline computation requiring no chain state and no additional secrets, and it is directly triggerable by any account able to invoke the precompile through a contract call.

### Recommendation
De-duplicate strictly by recovered address (not by raw signature bytes) in `ValidateMultiSign` — i.e., once `recoveredAddr` has contributed weight, skip it unconditionally regardless of the exact signature bytes supplied, matching Ethereum's/OpenZeppelin's fix of canonicalizing `s` to the lower half of the curve order (or otherwise rejecting non-canonical `s`) in `Rsv.fromSignature`/`recoverAddrBySign` before recovery.

### Proof of Concept
1. A permission requires 2-of-2 keys (`keyA`, `keyB`) with threshold 2, weight 1 each.
2. Attacker controls only `keyA`. They sign the target `hash` normally, obtaining `sigA = (r, s, v)`.
3. Attacker computes the malleated variant `sigA' = (r, n - s, v ^ 1)` (standard secp256k1 signature malleability), which also recovers to `keyA`'s address.
4. Attacker calls the contract invoking `ValidateMultiSign` with `signatures = [sigA, sigA']`.
5. In the loop: first iteration adds `keyA`'s weight (1) to `totalWeight`; second iteration recovers the same address, `matrixContains(executedSignList, sign)` fails (different bytes) so it does not `continue`, and `keyA`'s weight is added again, `totalWeight = 2`.
6. `totalWeight >= permission.getThreshold()` (2 >= 2) succeeds even though `keyB` never signed. [3](#0-2)
