### Title
Buffer over-read in `InputZipFile::ProcessCentralDirEntry` when parsing attacker-supplied ZIP central directory entries - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` in `third_party/ijar/zip.cc` reads fixed and variable-length central-directory fields (compressed/uncompressed size, filename length, extra-field length, comment length, external attributes, offset, and the ZIP64 extra-field payload) directly off the mmap'd input buffer via `get_u4le`/`get_u2le`/`get_u8le` with no `EnsureRemaining`-style bounds check against the mapped file length, unlike its sibling `ProcessLocalFileEntry`, which explicitly calls `EnsureRemaining()` before every variable-length read.

### Finding Description
`InputZipFile` mmaps an input jar/zip and walks the central directory starting at `central_dir_` using a cursor `p`/`current` that is advanced solely based on length fields taken from the file itself. [1](#0-0) 
Fields such as `file_name_length`, `extra_field_length`, and `file_comment_length` are attacker-controlled 16-bit values read straight from the archive, and the cursor `p`/`extra_p` is advanced by these values with no check that the resulting pointer stays within the bounds of the mmap'd region: [2](#0-1) 
Compare this to `ProcessLocalFileEntry`, in the same file, which calls `EnsureRemaining()` before reading the filename and extra-field bytes: [3](#0-2) 
`EnsureRemaining()` itself is only ever invoked from `ProcessLocalFileEntry`/`ProcessNext`, never from `ProcessCentralDirEntry` or the ZIP64 EOCD-location logic (`MaybeReadZip64CentralDirectory`, `FindZip64CentralDirectory`, `FindZipCentralDirectory`), all of which perform pointer arithmetic and `get_u*le`/`get_u*be` reads based on untrusted, attacker-supplied length/offset fields without validating against the mapped buffer size: [4](#0-3) [5](#0-4) 

A crafted ZIP file with a central directory entry whose `extra_field_length`/`file_comment_length`/ZIP64-locator offset fields point past the end of the mapped file causes `p`/`current` to be advanced beyond the mmap region, and the subsequent `get_u*le` calls read past the end of the mapping — an analog of the Qt `read_xbm_body` buffer over-read (CVE-2020-17507), where a length/loop-controlled parser advanced a cursor and read bytes without checking against the buffer's true bound.

### Impact Explanation
A buffer over-read here can crash the `ijar`/`singlejar`-family tooling process (mmap read past the mapped region triggers SIGSEGV on typical platforms) when processing an attacker-crafted jar/zip file, and in principle could leak adjacent memory content into computed offsets/lengths that influence subsequent reads (info disclosure is speculative and not confirmed by this analysis — it would require further data-flow tracing to show leaked bytes reach observable output). This affects any code path that decompresses/inspects a jar via this `ijar` zip reader, which is reachable when Bazel processes externally-supplied `.jar`/`.zip` inputs (e.g., via `http_jar`/`http_archive`/`java_import` style dependencies fetched from an attacker-controlled or compromised mirror).

### Likelihood Explanation
Reachability depends on whether a hostile origin can supply a `.jar`/`.zip` file that is (a) accepted despite an integrity check (e.g., sha256/integrity attribute) that a victim's build declares, or (b) consumed without any pinned checksum at all (e.g., locally-built interface jars from unpinned deps, or `ijar` invoked on a file the build didn't verify). I was not able to fully trace, within the available index, every caller of `InputZipFile`/`ijar` to confirm whether all reachable entry points enforce a checksum before this parser runs, so likelihood of a genuinely unprivileged, checksum-bypassing exploitation path is uncertain and requires further verification against the exact call sites (`third_party/ijar` binary invocation from `singlejar`/`build_java_import` style rules, and whether `DownloadCache`/`RepositoryCache` sha256 verification always precedes it).

### Recommendation
Add `EnsureRemaining()` (or an equivalent bounds check against `input_file_->Length()`/the mapped region) before every pointer advance and multi-byte read in `ProcessCentralDirEntry`, `MaybeReadZip64CentralDirectory`, `FindZip64CentralDirectory`, and `FindZipCentralDirectory`, mirroring the pattern already used in `ProcessLocalFileEntry`. Reject archives whose declared lengths/offsets would place the cursor outside the mmap'd file, with a clear error message.

### Proof of Concept
A `BuildIntegrationTestCase`/shell-level regression test analogous to Bazel's existing `third_party/ijar/test/ijar_test.sh` structure would:
1. Programmatically construct a minimal ZIP with a valid EOCD but a central-directory entry whose `extra_field_length` (or `file_comment_length`, or ZIP64 locator's `zip64_end_of_central_dir_offset`) is set to a value that, when added to the entry's start offset, exceeds the file's total length.
2. Invoke the `ijar`/`InputZipFile` reading path (`ProcessNext`/`ProcessCentralDirEntry`) on this file.
3. Observe a crash (SIGSEGV) or sanitizer (ASan) report of a heap/mmap buffer over-read, rather than the graceful "Premature end of file" error that `EnsureRemaining()` produces for the equivalent condition in `ProcessLocalFileEntry`.

Note: I could not fully confirm from the index whether an existing sanitized fuzz/unit test already exercises this exact code path, nor trace every production caller that could receive attacker-controlled zip bytes without a prior checksum gate; a background Devin session with full repo/test access would be needed to confirm exploitability end-to-end and build the concrete PoC/test.

  int EnsureRemaining(size_t n, const char *state) {
    size_t in_offset = p - zipdata_in_;
    size_t remaining = input_file_->Length() - in_offset;
    if (n > remaining) {
      return error("Premature end of file (at offset %zd, state=%s); "
                   "expected %zd more bytes but found %zd.\n",
                   in_offset, state, n, remaining);
    }
    return 0;

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;

bool MaybeReadZip64CentralDirectory(const u1 *bytes, size_t /*in_length*/,
                                    const u1 *current,
                                    const u1 **end_of_central_dir,
                                    EndOfCentralDirectoryRecord *cd) {
  if (current < bytes) {
    return false;
  }
  const u1 *candidate = current;
  u4 zip64_directory_signature = get_u4le(current);
  if (zip64_directory_signature != ZIP64_EOCD_SIGNATURE) {
    return false;
  }

  // size of zip64 end of central directory record
  // (fixed size unless there's a zip64 extensible data sector, which
  // we don't need to read)
  get_u8le(current);
  get_u2be(current);  // version made by
  get_u2be(current);  // version needed to extract

  u4 number_of_this_disk = get_u4be(current);
  u4 disk_with_central_dir = get_u4le(current);
  u8 central_dir_entries_on_this_disk = get_u8le(current);
  u8 central_dir_entries = get_u8le(current);
  u8 central_dir_size = get_u8le(current);
  u8 central_dir_offset = get_u8le(current);

  // check for a zip64 EOCD that matches the regular EOCD
  if (number_of_this_disk != cd->number_of_this_disk &&
      cd->number_of_this_disk != U2_MAX) {
    return false;
  }
  if (disk_with_central_dir != cd->disk_with_central_dir &&
      cd->disk_with_central_dir != U2_MAX) {
    return false;
  }
  if (central_dir_entries_on_this_disk !=
          cd->central_dir_entries_on_this_disk &&
      cd->central_dir_entries_on_this_disk != U2_MAX) {
    return false;
  }
  if (central_dir_entries != cd->central_dir_entries &&
      cd->central_dir_entries != U2_MAX) {
    return false;
  }
  if (central_dir_size != cd->central_dir_size &&
      cd->central_dir_size != U4_MAX) {
    return false;
  }
  if (central_dir_offset != cd->central_dir_offset &&
      cd->central_dir_offset != U4_MAX) {
    return false;
  }

  *end_of_central_dir = candidate;
  cd->number_of_this_disk = number_of_this_disk;
  cd->disk_with_central_dir = disk_with_central_dir;
  cd->central_dir_entries_on_this_disk = central_dir_entries_on_this_disk;
  cd->central_dir_entries = central_dir_entries;
  cd->central_dir_size = central_dir_size;
  cd->central_dir_offset = central_dir_offset;
  return true;
