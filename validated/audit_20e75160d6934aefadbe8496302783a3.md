Confirmed: `HookService` is registered on the **same gRPC server** as all other Gitaly-facing services via `RegisterAll` [1](#0-0) , meaning it is subject to the same standard Gitaly RPC authentication (a single, static, shared auth token/certificate used by every authenticated Gitaly client), not a request-scoped or transaction-scoped secret. This is the same trust boundary that a normal `SSHReceivePack`/`SmartHTTP ReceivePack` caller (e.g., gitlab-shell/workhorse forwarding an ordinary user's push) already crosses.

### Title
Cross-transaction `ProcReceiveHook` hijack via guessable `TransactionID` allows unauthenticated ref-update injection into another user's in-flight push - (File: internal/gitaly/service/hook/proc_receive.go)

### Summary
`HookService.ProcReceiveHook` binds an incoming, fully attacker-controlled RPC stream to someone else's in-flight `git-receive-pack` transaction using only a low-entropy, sequential `storage.TransactionID`, with no verification that the caller is the actual `gitaly-hooks` process spawned for that specific push.

### Finding Description
When a push uses the WAL/transactional receive-pack path, `SSHReceivePack`/`PostReceivePack` calls `RegisterProcReceiveHook`, which registers a waiter in the shared `ProcReceiveRegistry` keyed only by `storage.TransactionID` [2](#0-1) . The registry's `RegisterWaiter`/`Transmit` pair binds the *first* caller that presents a matching `TransactionID` to that waiter's channel, with no other identity check [3](#0-2) .

On the server side, `HookService.ProcReceiveHook` builds a `ProcReceiveHandler` purely from the `EnvironmentVariables` supplied in the *first request of the RPC stream* (i.e., attacker-supplied over the wire) and immediately calls `registry.Transmit(ctx, handler)`: [4](#0-3) 

The `TransactionID` used for lookup comes from the `HooksPayload.TransactionID` field embedded in those same client-supplied `EnvironmentVariables` [5](#0-4) . There is no cryptographic binding (no per-transaction secret/nonce) tying a legitimate `gitaly-hooks proc-receive` invocation to the specific `ReceivePack` call that spawned it — only the numeric `TransactionID`, which is a small, sequentially-issued WAL transaction counter (see test values like `1`, `2`, `3` in [6](#0-5) ) and therefore trivially guessable/brute-forceable by any client capable of calling `ReceivePack` concurrently.

Because `HookService` is registered on the same gRPC server as `SSHService`/`SmartHTTPService` [1](#0-0) , any client with normal Gitaly RPC access (the same access level an ordinary user's push already requires through gitlab-shell/workhorse) can call `HookService.ProcReceiveHook` directly and supply a crafted `HooksPayload` with a `TransactionID` equal to another, concurrently-running push's transaction. `Transmit` will then deliver the *attacker's* stream as the handler for the *victim's* `ReceivePack` RPC, since `Transmit` performs a first-come-first-served match purely on the integer ID with no ownership check.

This is the direct analog of the reported flashloan issue: just as the Balancer Vault lets **anyone** invoke `flashLoan()` and become the `recipient` that a Zapper's callback trusts merely because `msg.sender == flashLoanProvider` (without checking the callback belongs to *its own* pending operation), here **anyone** who can reach the shared `HookService` can invoke `ProcReceiveHook` and become the "recipient" that the `ReceivePack` RPC trusts merely because the `TransactionID` matches — without any check that the caller is the specific `gitaly-hooks` subprocess spawned for that push.

### Impact Explanation
An attacker who wins the race can supply arbitrary `ReferenceUpdate`s, `PushOptions`, and atomicity flags for a victim's push over the hijacked `ProcReceiveHandler` interface [7](#0-6) . Since the victim's `ReceivePack` RPC will commit whatever reference updates arrive on this handler to the write-ahead log, this allows:
- Injection of attacker-chosen reference updates into a repository as if they came from the legitimate pusher (whose already-passed `pre-receive`/`allowed` authorization is now attached to attacker-controlled ref changes).
- Denial-of-service for the victim's push (rejecting all updates, or hanging by never calling `Close`).
- Potential confusion/corruption of the WAL commit pipeline by supplying malformed or contradictory update data on behalf of another transaction.

This is a cross-repository / cross-user integrity and DoS issue reachable purely from the standard authenticated push path used by any user.

### Likelihood Explanation
Exploitability requires: (1) standard Gitaly RPC access already available to any user who can push (gitlab-shell/workhorse), (2) winning a race against the legitimate `gitaly-hooks proc-receive` process for the guessed `TransactionID`, and (3) `TransactionID`s being small sequential integers that are easy to brute force by repeatedly probing or by triggering pushes and observing transaction cadence. No token or secret beyond normal Gitaly auth is required, making this a realistic, moderate-likelihood race-condition exploitable by any authenticated Gitaly client without additional privilege.

### Recommendation
Bind the `ProcReceiveHook` callback to the specific `ReceivePack` invocation with an unforgeable, per-transaction secret (e.g., a random nonce generated at `RegisterWaiter` time and required in the `ProcReceiveHook` request, verified before `Transmit` succeeds), rather than relying solely on the guessable `TransactionID`. Additionally, `Transmit` should verify the caller's `Repository`/`GlRepository` (and ideally that the request originates from the actual `gitaly-hooks` subprocess spawned by that specific `ReceivePack` call, e.g., via a peer-credential or process-lineage check) before delivering the handler.

### Proof of Concept
1. Victim pushes to a repository via SSH/HTTP; `SSHReceivePack` calls `RegisterProcReceiveHook`, registering a waiter for `TransactionID = N` [2](#0-1) .
2. Attacker, holding only standard Gitaly RPC credentials, opens a `HookService.ProcReceiveHook` stream directly and sends a first request whose `EnvironmentVariables` contains a `GITALY_HOOKS_PAYLOAD` crafted with `TransactionID = N` and attacker-chosen `Repository`/pkt-line stdin content (arbitrary ref updates) [4](#0-3) .
3. If the attacker's `Transmit` call reaches the registry before/instead of the legitimate `gitaly-hooks` subprocess, `registry.Transmit` matches on `TransactionID` alone and delivers the attacker's handler to the victim's waiting `ReceivePack` RPC [8](#0-7) .
4. The victim's `ReceivePack` RPC now processes the attacker's injected reference updates as part of the victim's push.

// ProcReceiveHandler provides the mechanism for RPCs which invoked
// git-receive-pack(1) to interact with the proc-receive hook. It provides
// access to a list of references that a transaction is attempting to update,
// and functions to accept or reject individual updates.
type ProcReceiveHandler interface {
	// TransactionID provides the storage.TransactionID associated with the
	// handler.
	TransactionID() storage.TransactionID

	// Atomic denotes whether the push was atomic.
	Atomic() bool

	// PushOptions provides the set of push options provided to the proc-receive hook.
	PushOptions() []string

	// ReferenceUpdates provides the reference updates to be made.
	ReferenceUpdates() []ReferenceUpdate

	// AcceptUpdate tells the registry to accept a given reference update.
	AcceptUpdate(referenceName git.ReferenceName) error
	// RejectUpdate tells the registry to reject a given reference update, along
	// with a reason.
	RejectUpdate(referenceName git.ReferenceName, reason string) error

	// Write allows arbitrary data to be written to the proc-receive stderr. This is useful hook
	// outputs that need to be returned through git-receive-pack(1) as Git handles encapsulating
	// stderr in sideband packets and redirecting it to stdout.
	Write(p []byte) (int, error)

	// Close must be called to clean up the proc-receive hook. If the user
	// of the handler encounters an error, it should be transferred to the
	// hook too.
	Close(rpcErr error) error
}

// RegisterWaiter registers a waiter against the provided transactionID.
// The function returns a channel to obtain the handler, a cleanup function
// which must be called and an error if any.
func (r *ProcReceiveRegistry) RegisterWaiter(id storage.TransactionID) (<-chan ProcReceiveHandler, func(), error) {
	r.m.Lock()
	defer r.m.Unlock()

	if _, ok := r.waiters[id]; ok {
		return nil, nil, fmt.Errorf("cannot register id: %d again", id)
	}

	ch := make(chan ProcReceiveHandler)
	r.waiters[id] = ch

	cleanup := func() {
		r.m.Lock()
		defer r.m.Unlock()

		delete(r.waiters, id)
	}

	return ch, cleanup, nil
}

// Transmit transmits a handler to its waiter.
func (r *ProcReceiveRegistry) Transmit(ctx context.Context, handler ProcReceiveHandler) error {
	r.m.Lock()
	ch, ok := r.waiters[handler.TransactionID()]
	r.m.Unlock()

	if !ok {
		return fmt.Errorf("no waiters for id: %d", handler.TransactionID())
	}

	// It is possible that the RPC (waiter) returned because receive-pack
	// returned an error. In such scenarios, we don't want to block indefinitely.
	select {
	case <-ctx.Done():
		return ctx.Err()
	case ch <- handler:
	}

	return nil
}

func (s *server) ProcReceiveHook(stream gitalypb.HookService_ProcReceiveHookServer) error {
	ctx := stream.Context()

	firstRequest, err := stream.Recv()
	if err != nil {
		return structerr.NewInternal("receiving first request: %w", err)
	}

	stdin := streamio.NewReader(func() ([]byte, error) {
		req, err := stream.Recv()
		return req.GetStdin(), err
	})

	var m sync.Mutex
	stdout := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stdout: p})
	})

	stderr := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.ProcReceiveHookResponse{Stderr: p})
	})

	handler, doneCh, err := gitalyhook.NewProcReceiveHandler(
		firstRequest.GetEnvironmentVariables(), stdin, stdout, stderr,
	)
	if err != nil {
		return structerr.NewInternal("creating handler: %w", err)
	}

	registry := s.manager.ProcReceiveRegistry()
	if err := registry.Transmit(ctx, handler); err != nil {
		return sendProcReceiveHookResponse(stream, 1, fmt.Sprintf("transmitting handler: %s", err))
	}
