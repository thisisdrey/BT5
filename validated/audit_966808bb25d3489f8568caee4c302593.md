Audit Report

## Title
Zero-value ERC20 transfer in `ERC20Transactor` can cause unrecoverable trapped-asset lock when the target ERC20 reverts on zero-value transfers - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` build ERC20 `transfer()` calldata directly from the matcher-extracted `amount` and invoke it via `pallet_revive::Pallet::<T>::bare_call` with no `amount.is_zero()` guard, unlike every other transfer path in this codebase. If a registered ERC20 asset's contract reverts on zero-value transfers, a zero-valued leg in a multi-asset XCM program causes `Err(XcmError::FailedToTransactAsset("ERC20 contract reverted"))`, aborting the enclosing instruction and forcing the XCM executor to trap whatever assets are already in the local holding register for that message.

## Finding Description
`ERC20Transactor` is one of the live `AssetTransactors` on Asset Hub Westend [1](#0-0) , reachable via `pallet_xcm::execute` and ordinary inbound XCM messages. Both transact functions compute `IERC20::transferCall { .. , value: EU256::from(amount) }` directly from the matched `amount` with no minimum/zero check before calling `bare_call`, and both map a contract revert (`return_value.did_revert()`) straight to `XcmError::FailedToTransactAsset` [2](#0-1) [3](#0-2) . No `amount.is_zero()` short-circuit exists anywhere in this file, in contrast to the zero-value no-op guards used in comparable transfer paths elsewhere in the codebase (`substrate/frame/balances/src/impl_currency.rs` L399-401, `substrate/frame/revive/src/exec.rs` L1734-1736). `Fungibility::Fungible(0)` is a structurally valid XCM asset value, and nothing in `matches_fungibles`/the matcher rejects it before handing `(asset_id, amount)` to the transactor.

## Impact Explanation
When an ERC20 registered for `ERC20Transactor` reverts on a zero-value `transfer()`, any XCM instruction (`WithdrawAsset`/`DepositAsset`) that includes a zero-valued leg for that asset alongside other, valuable assets will fail mid-instruction, causing the XCM executor's standard error-recovery path (`AssetTrap`) to trap the assets accumulated in holding at that point. This aligns with the impact-gate category of a fund/state lock arising from a message-processing path that does not settle atomically, and is a genuine consequence of the missing zero-value guard confirmed in the code.

I was not able to fully trace, within available tool budget, the exact `xcm-executor` trap/claim mechanics — specifically whether `ClaimAsset` follow-up programs are forced to replay the exact failing zero-valued leg (making the lock strictly permanent) or whether a claimant can construct a follow-up program that excludes the reverting zero-value asset and thereby recovers the other trapped assets. This distinction materially affects whether the correct severity is "permanent, unrecoverable lock" versus "recoverable via manual `ClaimAsset`, but real DoS/usability risk requiring the affected party to understand XCM trap/claim semantics." The original report's own author flags this same unresolved gap. Independent of that unresolved severity question, the underlying root cause — the missing zero-amount guard in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus` causing a guaranteed, attacker-repeatable revert against a real-world ERC20 quirk (revert-on-zero-transfer) — is confirmed directly in the code and is not defended against by any existing check in this file or in `matches_fungibles`.

## Likelihood Explanation
Revert-on-zero-value-transfer ERC20 contracts are a documented real-world pattern. Any unprivileged account can call `pallet_xcm::execute` with a hand-crafted multi-asset program bundling a `Fungible(0)` leg for such a registered ERC20 alongside valuable assets, with no special privileges, timing, or cooperation from other parties required, making the triggering condition fully attacker-controlled and repeatable.

## Recommendation
Add an explicit `amount.is_zero()` no-op short-circuit at the top of both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus` in `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`, mirroring the guard pattern already used in `substrate/frame/balances/src/impl_currency.rs` and `substrate/frame/revive/src/exec.rs`, so that a zero-valued ERC20 leg never issues an on-chain `transfer(..., 0)` call and cannot revert due to non-standard ERC20 zero-value semantics.

## Proof of Concept
1. Deploy/identify an ERC20 contract `T` via `pallet-revive` whose `transfer()` reverts when `value == 0`.
2. Register `T`'s location as an ERC20 asset recognized by the matcher configured for `ERC20Transactor` on Asset Hub Westend.
3. As any signed account, call `pallet_xcm::execute` with an XCM program such as `WithdrawAsset([(T, 0), (DOT, 1000)])` followed by `DepositAsset { assets: Wild(AllCounted(2)), beneficiary: <account> }`.
4. Observe that the `(T, 0)` leg reaches `ERC20Transactor::withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, calls `IERC20::transferCall` with `value = 0`, the contract reverts, and the function returns `XcmError::FailedToTransactAsset("ERC20 contract reverted")`.
5. Confirm (via unit/integration test against `xcm-executor`) whether the remaining `AssetsInHolding` for that message is trapped via `AssetTrap`, and separately verify whether a subsequent `ClaimAsset` program can recover the non-zero assets without re-triggering the same revert — this step is required to establish the final severity (permanent vs. recoverable-with-friction lock).
