### Title
Unbounded, unmetered `receipt_proof` in Snowbridge `EthereumInboundQueueV2::submit` allows fixed-fee, CPU-underpriced spam of Merkle-Patricia proof verification - ([File: bridges/snowbridge/pallets/inbound-queue-v2/src/lib.rs])

### Summary
`submit()` charges a fixed benchmarked weight (`T::WeightInfo::submit()`, ~60µs per the generated weights) regardless of the size of the caller-supplied `Proof.receipt_proof: Vec<Vec<u8>>`, which is decoded and cryptographically verified via `verify_proof`/`verify_receipt_proof` before any nonce/gateway check filters it out. Because the field is an unbounded `Vec<Vec<u8>>` with no `MaxEncodedLen`/length cap enforced at the call boundary, and the weight is a flat constant derived from a single benchmarked fixture rather than scaled by proof length, any signed account can submit calls with arbitrarily large/deep fabricated proofs at the fixed fee, forcing the node to spend CPU proportional to attacker-chosen input while paying for constant-size work. This is the same "insufficient request-cost/throttling vs. resource consumption" class as the HAL-04 report, applied to Substrate's weight-as-price model instead of an HTTP API.

### Finding Description
`EthereumInboundQueueV2::submit` is a public, unauthenticated (any signed account) extrinsic: [1](#0-0) 

Its weight annotation is a single fixed constant produced by benchmarking with one representative proof size: [2](#0-1) 

The verification path invoked from `submit` decodes and Merkle-verifies the caller-supplied `receipt_proof: Vec<Vec<u8>>` against a fixed root, doing hashing/RLP-decoding work proportional to the number and size of proof nodes supplied: [3](#0-2) 

`Proof` and `EventProof` place no bound on `receipt_proof`'s length or the size of each node: [4](#0-3) 

The call flow in `submit()` performs the expensive verification (`T::Verifier::verify`) before the cheap, call-invalidating checks (`ensure!(gateway == ...)`, nonce bitmap check) are reached in `process_message`: [5](#0-4) 

Since the extrinsic's fee/weight is fixed by benchmarking a single fixture rather than scaled to `receipt_proof.len()` or byte size, an attacker can craft calls with proof vectors far larger than the benchmarked fixture, causing execution time in `verify_proof` (trie traversal/hash computation over attacker-chosen node count/size) to exceed what was paid for. This mirrors the HAL-04 pattern: the pallet accepts "requests" (extrinsics) that consume resources (CPU) disproportionate to what is charged, with no additional throttling beyond the flat weight fee, enabling a low-cost way to degrade block production or delay legitimate bridge message processing on BridgeHub.

### Impact Explanation
Under the Impact Gate, this fits "public underpriced work that degrades block production or stalls bridge processing." A malicious signed account (no special privilege, no validator/relayer trust assumed) can submit multiple `submit()` transactions with maximally-sized/malformed but structurally-parseable `receipt_proof` vectors that will fail verification but only after consuming CPU proportional to the (unbounded) proof size, at the same flat weight fee as a legitimate small proof. Repeated across a block, this can consume disproportionate execution time relative to the weight actually charged/reserved, congesting BridgeHub block production and delaying processing of genuine relayer messages — a chain-level availability degradation without requiring a malicious relayer, validator, or admin.

### Likelihood Explanation
Likelihood is limited by the transaction-length fee (larger `Vec<Vec<u8>>` encodings do cost more in the length-based fee component) and by needing a normal signed account with enough balance to pay for many transactions — no privileged role is required. The key gap is that the *weight* component (which caps how much of the block's fixed execution budget the call may consume) is flat and not proof-size sensitive, so the length fee alone does not guarantee CPU cost is bounded to the benchmarked figure. This makes the attack economically accessible to any funded account, though the practical severity depends on how large the mismatch between benchmarked weight and worst-case unbounded proof cost really is (this project did not have the ability to run the actual worst-case benchmark to quantify the exact multiplier).

### Recommendation
- Bound `receipt_proof` (and each node) with an explicit maximum length/size (e.g., wrap in `BoundedVec` with a `MaxEncodedLen`-backed constant reflecting the deepest realistic Ethereum trie proof), rejecting oversized proofs before verification.
- Scale `submit()`'s benchmarked weight to the worst-case bounded proof size rather than a single small fixture, or make weight a function of `receipt_proof.len()`/total encoded size (similar to how `pallet_message_queue` sizes cost by page/message size).
- Move cheap checks (gateway match, nonce-already-processed) ahead of expensive proof verification wherever the data needed for those checks is available before decoding/verifying the full proof, to fail fast on replay/malformed submissions.

### Proof of Concept
1. Construct an `EventProof` with a valid `event_log`/`gateway` but a `receipt_proof: Vec<Vec<u8>>` containing many large (near max-transaction-size) byte vectors that form a syntactically parseable but ultimately invalid trie path.
2. Call `InboundQueue::submit(origin, Box::new(event))` repeatedly from a funded signed account; each call pays the fixed weight fee from `WeightInfo::submit()` (~60µs benchmarked) while `verify_receipt_proof` performs trie-node iteration/hashing proportional to the actual (much larger) proof supplied.
3. Compare wall-clock execution time of these calls against the benchmarked weight to demonstrate the CPU/weight mismatch, and observe block-authoring slowdown when many such calls are included in a block.
(Exact numeric overrun could not be empirically measured in this session; the finding is based on the fixed-weight annotation versus the unbounded `Vec<Vec<u8>>` input to `verify_proof`.) [6](#0-5) [3](#0-2)

pub fn verify_receipt_proof(
	receipts_root: H256,
	tx_index: u64,
	proof: &[Vec<u8>],
) -> Option<ReceiptEnvelope> {
	let key = receipt_trie_key(tx_index);
	let root = B256::from_slice(receipts_root.as_bytes());
	let proof_nodes: Vec<Bytes> = proof.iter().map(|node| Bytes::copy_from_slice(node)).collect();

	// Call verify_proof with None to extract the value from an inclusion proof. For inclusion
	// proofs, alloy_trie returns ValueMismatch with the extracted value in `got`. The proof is
	// already cryptographically verified during this traversal.
	let value = match verify_proof(root, key, None, proof_nodes.iter()) {
		Ok(()) => return None, // Exclusion proof - key does not exist
		Err(ProofVerificationError::ValueMismatch { path, got: Some(v), expected: None })
			if path == key =>
		{
			v.to_vec()
		},
		Err(_) => return None,
	};

	ReceiptEnvelope::decode(&mut value.as_slice()).ok()
}
