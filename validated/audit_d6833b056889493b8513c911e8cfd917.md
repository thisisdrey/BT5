### Title
DelegateAction nonce replay via key delete/recreate at same block height defeats `action_delegate` nonce floor check - ([File: runtime/runtime/src/actions.rs])

### Summary
`action_delegate` bounds a `DelegateAction` nonce only against the *current* `access_key.nonce` and a floor recomputed from the *current* block height, while `add_regular_key`/`add_gas_key` reset a recreated access key's nonce floor from the block height at *creation* time. If a key is deleted and re-added within the same block height in which a high nonce was already consumed on the prior key instance, the new key's floor can be lower than that already-consumed nonce, allowing the exact same previously-executed `SignedDelegateAction` to be resubmitted and re-executed later.

### Finding Description
The nonce floor for a freshly (re)created access key is:
```
pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    (block_height - 1) * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
``` [1](#0-0) 
used by `add_regular_key`/`add_gas_key` at `AddKey` time [2](#0-1) .

`action_delegate` validates a delegate's nonce with:
```
if delegate_nonce.nonce() <= current_nonce { ... DelegateActionInvalidNonce ... }
let upper_bound = apply_state.block_height * AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER;
if delegate_nonce.nonce() >= upper_bound { ... DelegateActionNonceTooLarge ... }
``` [3](#0-2) 
where `current_nonce` is the *live* stored `access_key.nonce` [4](#0-3) , and `upper_bound` is derived from the *current* chunk's `apply_state.block_height`, not the height at which the key instance was created.

Under normal operation this scheme is self-consistent because every nonce ever accepted for a key at height `H` satisfies `nonce < H * MULTIPLIER`, and once a key is deleted and re-added at a strictly later height `H' > H`, the new floor `(H'-1)*MULTIPLIER >= H*MULTIPLIER` dominates any nonce previously consumed at `H`, so old nonces are always rejected by `<= current_nonce`.

This invariant breaks only if the delete+recreate (`DeleteKey` + `AddKey`, same public key) is applied at the *same* block height `H1` as the original high-nonce consumption. An attacker who fully controls their own account and its transaction submission order can:
1. Submit transaction `TX_A` that executes a `SignedDelegateAction` with nonce `X` close to `H1 * MULTIPLIER`, setting `access_key.nonce = X` at height `H1` (via `nonce_update`) [5](#0-4) .
2. Submit a second transaction `TX_B` (same signer, next nonce) containing `[DeleteKey, AddKey]` for the same public key, applied at the *same* height `H1` (both transactions land in the same chunk). This resets the key with floor `(H1-1)*MULTIPLIER < X` [1](#0-0) .
3. Much later, at height `H2 >> H1`, resubmit (via a relayer, which the attacker also controls) the identical `SignedDelegateAction` from step 1 (same nonce `X`, same signature) in a fresh enclosing transaction. `action_delegate` computes `current_nonce = (H1-1)*MULTIPLIER < X` and `upper_bound = H2 * MULTIPLIER >> X`, so both checks pass and the exact same delegate authorization executes a second time.

Because both `TX_A`/`TX_B` must land in the same block height for the floor to fall below `X`, this is a narrow timing window, but it is one the attacker can attempt to engineer by submitting both transactions back-to-back with sequential nonces to a public RPC endpoint — there is no protocol rule preventing multiple transactions from one signer landing in the same chunk.

### Impact Explanation
If the replayed `DelegateAction`'s actions target a third-party contract or promise chain that assumes single-use authorization (a meta-transaction-based one-time claim, swap, vote, or transfer), the second execution constitutes an unauthorized re-execution/double-spend of an already-consumed authorization — matching the "double-spend/replay" and "authorization escalation across... promises" bounty categories. Impact is limited to actions the DelegateAction's own signer authorized (it cannot escalate to other accounts' keys), so the blast radius is bounded to whatever the DelegateAction's action list can do (e.g., double-triggering a contract call with side effects).

### Likelihood Explanation
Exploitability requires an extremely tight precondition: the nonce-consuming delegate transaction and the subsequent `DeleteKey`+`AddKey` transaction must be applied within the *same* block height, since block heights only increase monotonically and any later height for the recreate would raise the floor above the already-consumed nonce. An ordinary user does not control chunk scheduling and can only attempt this by submitting both transactions in rapid succession, with no deterministic guarantee of same-chunk inclusion. This significantly limits practical, repeatable exploitation, even though the underlying check discrepancy is real.

### Recommendation
Persist and check against a monotonically non-decreasing high-water nonce for a given public key across delete/recreate cycles (e.g., store the last-used nonce independent of `AccessKey` existence, or forbid reusing a public key for a fresh `AddKey` at all), rather than deriving the new floor solely from the current block height at recreation time.

### Proof of Concept
Runtime/integration test in `runtime/runtime/src/tests/apply.rs` style:
1. Create account with `FullAccess` key `pk` at height `H1`.
2. Apply a transaction executing a `SignedDelegateAction` with nonce `X = H1*MULTIPLIER - 1` (near upper bound), assert success and `access_key.nonce == X`.
3. In the same simulated chunk/height `H1`, apply `[DeleteKey(pk), AddKey(pk, FullAccess)]`; assert new `access_key.nonce == (H1-1)*MULTIPLIER < X`.
4. Advance to height `H2 >> H1`.
5. Resubmit the identical `SignedDelegateAction` from step 2 wrapped in a new transaction; call `action_delegate` and assert it incorrectly returns `Ok` / success instead of `ActionErrorKind::DelegateActionInvalidNonce`.
