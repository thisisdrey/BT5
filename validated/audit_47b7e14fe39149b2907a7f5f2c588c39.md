### Title
Unbounded witness list causes iteration-based DoS during every maintenance cycle and query API - (File: `consensus/src/main/java/org/tron/consensus/dpos/MaintenanceManager.java`)

### Summary
Any unprivileged account can broadcast a `WitnessCreateContract` transaction to register as a witness/SR candidate for a fixed TRX fee, with no upper bound enforced on the total number of witnesses stored in `WitnessStore`. This mirrors the reported `divisionToFee[]` bug class: an attacker-controlled, unbounded array is later iterated by security/consensus-critical code paths that must process the *entire* collection, creating growing gas/CPU cost with no cap, all reachable from an ordinary transaction.

### Finding Description
`WitnessStore.getAllWitnesses()` returns every witness ever created by scanning the full underlying DB iterator with no pagination or limit [1](#0-0) . This list grows purely as a function of how many `WitnessCreateContract` transactions unprivileged accounts submit; each submission costs a fixed account-creation-style fee but there is no cap in the actuator on the *total number* of witnesses that can exist system-wide.

This unbounded list is then fully iterated multiple times per maintenance cycle inside `MaintenanceManager.doMaintenance()`, which is invoked from consensus/block application on every node for every maintenance window: [2](#0-1) 

Specifically, `consensusDelegate.getAllWitnesses().forEach(...)` is called multiple times to accumulate reward stats, build `newWitnessAddressList`, and set brokerage/vote for the next cycle — each of these is an O(N) or O(N log N) (sort) pass over the entire witness set [3](#0-2) .

`doMaintenance()` is driven from block processing in `Manager.processBlock()`, which calls `proposalController.processProposals()`/consensus maintenance via `consensus.applyBlock(block)` on the maintenance-time boundary [4](#0-3) , meaning this cost is paid by **every full node validating the chain**, not just an API caller.

Additionally, the same unbounded `getAllWitnesses()` is exposed directly to unauthenticated HTTP/gRPC clients via `Wallet.getWitnessList()` and `Wallet.getPaginatedNowWitnessList()`, both of which sort the entire witness collection on every call [5](#0-4) [6](#0-5) , reachable through `ListWitnessesServlet`/`GetPaginatedNowWitnessListServlet` and the corresponding gRPC methods.

### Impact Explanation
Because witness creation is a normal, unprivileged transaction available to anyone with the registration fee, an attacker can create an arbitrarily large number of witness records over time. As the witness set grows without bound, the per-block-maintenance-cycle iteration cost (`doMaintenance()`, `sortWitnesses`, `updateWitness`) and the per-API-call cost (`getWitnessList`, `getPaginatedNowWitnessList`) both scale linearly (or worse, with sorting) with the total witness count. This can degrade block-processing throughput network-wide (every full node performs this work at every maintenance boundary) and can be used to slow or stall the query APIs. In the audit-report's terms, this is the DoS-via-unbounded-array class rather than a fund-theft bug.

### Likelihood Explanation
Exploitability requires only the registration fee per witness (a fixed TRX cost enforced in `WitnessCreateActuator`, which I was not able to fully inspect within the available index to confirm whether any cap on total witness count exists beyond the fee). Given the fee is fixed and not scaling with existing witness count, an attacker with sufficient capital can register many thousands of witness accounts to inflate the array size, degrading maintenance and query performance for all nodes. This is economically bounded (cost scales with attacker spend) rather than a Sherlock-style single-transaction DoS, which lowers likelihood relative to the original report where a single privileged action becomes unusable — here the impact is degraded performance/response time rather than an outright halt, unless witness count becomes extreme.

### Recommendation
Enforce an explicit maximum on the total number of witnesses that can be registered (reject `WitnessCreateContract` once the cap is reached), and/or convert `getAllWitnesses()` consumers in `MaintenanceManager` and `Wallet` to use bounded/paginated/streaming access patterns instead of materializing and sorting the full witness set on every maintenance cycle and API call.

### Proof of Concept
1. Repeatedly submit `WitnessCreateContract` transactions from many funded accounts, each paying the fixed witness-creation fee, with no code-enforced cap on total witness count found in the actuator/validate path reachable from the index.
2. Observe `WitnessStore` grow unbounded; each subsequent maintenance-cycle block (`Manager.processBlock` → `consensus.applyBlock` → `MaintenanceManager.doMaintenance()`) performs multiple full-collection iterations/sorts over the growing witness list [2](#0-1) .
3. Concurrently, `getWitnessList`/`getPaginatedNowWitnessList` API calls become progressively more expensive as they sort the entire witness set on every invocation [6](#0-5) .

**Note on confidence**: I was unable to fully confirm within the indexed code whether `WitnessCreateActuator.validate()` enforces any cap on the total number of witnesses (only the per-transaction fee was found in searches); this is a material uncertainty for likelihood assessment. Given the moderate/uncertain severity and the economic (not purely computational) barrier to exploitation, this analog is weaker than the reference Sherlock finding, which described an outright function-breaking DoS. If you want higher confidence, a Devin session with full file access could confirm whether `WitnessCreateActuator` has any witness-count cap.

    if (dynamicPropertiesStore.useNewRewardAlgorithm()) {

      consensusDelegate.getAllWitnesses().forEach(witness -> {
        delegationStore.accumulateWitnessVi(curCycle, witness.createDbKey(), witness.getVoteCount());
      });
    }

    Map<ByteString, Long> countWitness = countVote(votesStore);
    if (!countWitness.isEmpty()) {
      List<ByteString> currentWits = consensusDelegate.getActiveWitnesses();

      List<ByteString> newWitnessAddressList = new ArrayList<>();
      consensusDelegate.getAllWitnesses()
          .forEach(witnessCapsule -> newWitnessAddressList.add(witnessCapsule.getAddress()));

      countWitness.forEach((address, voteCount) -> {
        byte[] witnessAddress = address.toByteArray();
        WitnessCapsule witnessCapsule = consensusDelegate.getWitness(witnessAddress);
        if (witnessCapsule == null) {
          logger.warn("Witness capsule is null. address is {}", Hex.toHexString(witnessAddress));
          return;
        }
        AccountCapsule account = consensusDelegate.getAccount(witnessAddress);
        if (account == null) {
          logger.warn("Witness account is null. address is {}", Hex.toHexString(witnessAddress));
          return;
        }
        witnessCapsule.setVoteCount(witnessCapsule.getVoteCount() + voteCount);
        consensusDelegate.saveWitness(witnessCapsule);
        logger.info("address is {} , countVote is {}", witnessCapsule.createReadableString(),
            witnessCapsule.getVoteCount());
      });

      dposService.updateWitness(newWitnessAddressList);

      incentiveManager.reward(newWitnessAddressList);

      List<ByteString> newWits = consensusDelegate.getActiveWitnesses();
      if (!CollectionUtils.isEqualCollection(currentWits, newWits)) {
        currentWits.forEach(address -> {
          WitnessCapsule witnessCapsule = consensusDelegate.getWitness(address.toByteArray());
          witnessCapsule.setIsJobs(false);
          consensusDelegate.saveWitness(witnessCapsule);
        });
        newWits.forEach(address -> {
          WitnessCapsule witnessCapsule = consensusDelegate.getWitness(address.toByteArray());
          witnessCapsule.setIsJobs(true);
          consensusDelegate.saveWitness(witnessCapsule);
        });

        SRMetrics.recordSrSetChange(currentWits, newWits);
      }

      logger.info("Update witness success. \nbefore: {} \nafter: {}",
          getAddressStringList(currentWits),
          getAddressStringList(newWits));
    }

    if (dynamicPropertiesStore.allowChangeDelegation()) {
      long nextCycle = dynamicPropertiesStore.getCurrentCycleNumber() + 1;
      dynamicPropertiesStore.saveCurrentCycleNumber(nextCycle);
      consensusDelegate.getAllWitnesses().forEach(witness -> {
        delegationStore.setBrokerage(nextCycle, witness.createDbKey(),
            delegationStore.getBrokerage(witness.createDbKey()));
        delegationStore.setWitnessVote(nextCycle, witness.createDbKey(), witness.getVoteCount());
      });
    }
