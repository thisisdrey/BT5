### Title
Unstaked QUIC connection eviction (`prune_oldest`) can be evaded indefinitely by cheap self-refresh of `last_update`, letting attacker-controlled connections permanently squat slots - (File: `streamer/src/nonblocking/quic.rs`)

### Summary
The unstaked QUIC connection table evicts connections using a purely time-based "least-recently-active" heuristic (`prune_oldest`), and the timestamp it relies on (`last_update`) is refreshed by the connecting peer itself on every finished stream at essentially zero cost. This mirrors the reported Vault bug: a value meant to represent "how stale/low-value this actor is" is written by the same unprivileged actor's own cheap action, letting them permanently defeat the mechanism (fee extraction in the report; eviction here) that depends on it.

### Finding Description
`ConnectionTable::prune_oldest` evicts the connection(s) with the smallest `last_update` timestamp when the unstaked table is at capacity: [1](#0-0) 

`last_update` is an `Arc<AtomicU64>` shared with the connection handling task and is stamped with the current time whenever any stream on that connection finishes: [2](#0-1) [3](#0-2) 

That store happens on the hot path immediately after a stream completes reading a packet, from `qos.on_stream_finished(&context)` in the per-connection handler loop: [4](#0-3) 

Pruning of the unstaked table is only triggered when a *new* connection needs a slot, via `prune_unstaked_connection_table`/`prune_unstaked_connections_and_add_new_connection`: [5](#0-4) [6](#0-5) 

Because sending and finishing a single tiny uni-stream is extremely cheap (bandwidth/CPU-wise) for a client, and it always refreshes `last_update` to "now" regardless of stream content or value delivered, any unstaked peer can continuously "self front-run" the eviction check: right before (or simply at a steady low cadence faster than other connections churn) it opens a trivial stream, guaranteeing its `last_update` is never the minimum in the table. This is structurally identical to the Vault bug's `highWaterMark`: a state value that is supposed to reflect "this actor has not been recently favorable/active" is unilaterally, cheaply rewritable by that same actor to escape the consequence (fee capture there, eviction here) that the value is meant to gate.

### Impact Explanation
An attacker controlling multiple unstaked connections (or IPs) can keep them permanently "fresh" with negligible cost, defeating `prune_oldest`'s intended behavior of reclaiming slots from idle/low-value connections. Combined with `max_unstaked_connections` capacity limits, this lets a resourced attacker occupy and retain a disproportionate share of the unstaked connection table indefinitely, denying other unstaked clients the ability to connect and submit transactions through the QUIC ingestion path — a QoS/admission-control evasion against unprivileged-user-facing capacity limits.

### Likelihood Explanation
Likelihood is high: no special permissions, stake, or timing precision relative to another party's transaction are required (unlike a strict blockchain front-run) — the attacker only needs to keep sending trivial streams on its own already-open connections at a modest rate, which is cheap and fully within its control.

### Recommendation
Do not let eviction priority be based solely on a timestamp the connecting peer can refresh for free. Options: incorporate connection age (time since creation, not last activity) or a decaying reputation/rate-weighted score into `prune_oldest`'s selection key; rate-limit how often `last_update` can meaningfully affect eviction ordering (e.g., only count "useful" refreshes such as ones associated with real transaction throughput above trivial noise); or combine with `prune_random` (already used for staked connections) so idle-refresh alone cannot guarantee immunity from eviction.

### Proof of Concept
1. Open an unstaked QUIC connection when `unstaked_connection_table.total_size` is near `max_unstaked_connections`.
2. Every interval shorter than the churn rate of other unstaked connections, open and immediately finish a minimal uni-stream (e.g., a 1-byte payload) — this invokes `qos.on_stream_finished` and stamps `last_update` to the current time (`streamer/src/nonblocking/swqos.rs:490-494`).
3. When new connections attempt to join and the table is full, `prune_unstaked_connection_table` calls `prune_oldest`, which always picks the connection with the minimum `last_update` (`streamer/src/nonblocking/quic.rs:964-980`) — the attacker's continuously-refreshed connection is never selected, while other connections that are actually idle (or legitimate new connections queued behind capacity) are evicted/blocked instead.

    pub(crate) fn prune_oldest(&mut self, max_size: usize) -> usize {
        let mut num_pruned = 0;
        let key = |(_, connections): &(_, &Vec<_>)| {
            connections.iter().map(ConnectionEntry::last_update).min()
        };
        while self.total_size.saturating_sub(num_pruned) > max_size {
            match self.table.values().enumerate().min_by_key(key) {
                None => break,
                Some((index, connections)) => {
                    num_pruned += connections.len();
                    self.table.swap_remove_index(index);
                }
            }
        }
        self.total_size = self.total_size.saturating_sub(num_pruned);
        num_pruned
    }

    fn prune_unstaked_connection_table(
        &self,
        unstaked_connection_table: &mut ConnectionTable<ConnectionStreamCounter>,
        max_unstaked_connections: usize,
        stats: Arc<StreamerStats>,
    ) {
        if unstaked_connection_table.total_size >= max_unstaked_connections {
            // Prune the connection table down to 90% capacity
            const PRUNE_TABLE_RATIO: f64 = 0.90;
            let max_connections = (PRUNE_TABLE_RATIO * (max_unstaked_connections as f64)) as usize;
            let num_pruned = unstaked_connection_table.prune_oldest(max_connections);
            stats
                .num_evictions_unstaked
                .fetch_add(num_pruned, Ordering::Relaxed);
        }
    }
