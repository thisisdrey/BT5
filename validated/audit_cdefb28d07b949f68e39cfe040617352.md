### Title
Leaked `PromiseYieldReceipt` / yield-id state on `DeleteAccount` allows a self-directed yielded receipt to execute against a reused account ID with self-privilege - ([File: core/store/src/utils/mod.rs] / [File: runtime/runtime/src/actions.rs] / [File: runtime/runtime/src/lib.rs])

### Summary
`remove_account` (called from `action_delete_account`) purges `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` rows, but never removes `TrieKey::PromiseYieldReceipt`, `TrieKey::PromiseYieldStatus`, `TrieKey::YieldIdToDataId`, or `TrieKey::DataIdToYieldId` rows for the deleted account. Because the global `PromiseYieldTimeout` queue only checks `contains_key` on the still-present `PromiseYieldReceipt` row - not the account's existence - a self-directed yielded receipt created before deletion survives account deletion and later fires against whichever account is subsequently (re)created under the same account ID, executing its actions with full self-trust (`predecessor_id == receiver_id`).

### Finding Description
`create_promise_yield_receipt`/`create_promise_yield_receipt_with_id` in `runtime/runtime/src/ext.rs` (lines 353-400) store a `PromiseYieldReceipt{receiver_id, data_id}` row and, for the `with_id` variant, bidirectional `YieldIdToDataId`/`DataIdToYieldId` rows via `set_yield_id_mapping` (`core/store/src/utils/mod.rs:281-297`). A queued timeout entry is also enqueued globally (`enqueue_promise_yield_timeout`, `runtime/runtime/src/function_call.rs:152-169`).

When the account later self-deletes via `DeleteAccountAction`, `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), which removes only `Account`, `ContractCode`, access keys/gas-key nonces, and `ContractData`. It never calls `remove_promise_yield_receipt`, `remove_promise_yield_status`, or `remove_yield_id_mappings`, so the `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows for that account persist in the trie after deletion.

The account ID is then reusable: `action_create_account` (`runtime/runtime/src/actions.rs:167-210`) only checks that the account currently does not exist and that the new ID is a sub-account of the predecessor (or a valid top-level name via registrar) - it performs no check against prior history. So the same predecessor that owned `A` (or `A` itself, self-recreating a sub-account it previously deleted) can freely `CreateAccount` with the exact same ID.

Once expiry is reached, `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:3009-3116`) walks the `PromiseYieldTimeout` queue and, for each expired entry, only checks `state_update.contains_key(&TrieKey::PromiseYieldReceipt{...})` (line 3051) - it does not verify the account still exists or is the same account that created the yield. Because that row was never cleaned up on deletion, the check succeeds and a `PromiseResume(data: None)` is synthesized and forwarded to account `A`. `process_receipt`'s `PromiseResume` handling (`runtime/runtime/src/lib.rs:1500-1562`) then finds the still-present `yield_receipt` via `get_promise_yield_receipt`, removes it, and executes its actions via `apply_action_receipt` against whatever account currently occupies ID `A` - with `predecessor_id == receiver_id == A`, i.e. full self-trust permission, regardless of the new account's actual owner or access keys.

No existing check (signature, access key, or account-identity binding) stops this, because receipt execution trusts the `predecessor_id`/`receiver_id` fields embedded in the already-created receipt, and those checks are never re-validated against current account state/ownership at resume time.

### Impact Explanation
This is an authorization escalation across account identities/promises: actions embedded in the stale yielded receipt (e.g. `AddKey` with full access, `DeployContract`, `Transfer`, or a privileged `FunctionCall`) execute with self-account privilege on a freshly (re)created account of the same ID, without any consent or awareness by whoever now controls that account. An attacker controlling the parent namespace (or self-recreating their own sub-account) can plant a "time bomb" receipt that fires - deterministically, via the automatic timeout mechanism - against the reused account, effectively hijacking any funds/keys placed into it afterward. This matches the "authorization escalation across accounts or promises" bounty category.

### Likelihood Explanation
Preconditions are fully attacker-controlled and require no privileged access: any funded account that can create a sub-account (or self-delete/self-recreate) can (1) call `promise_yield_create`/`promise_yield_create_with_id` with `receiver_id` set to itself, (2) craft the yielded callback actions, (3) self-delete via a normal `DeleteAccount` transaction, and (4) recreate the same account ID (own sub-account, or reuse via top-level/registrar rules where applicable) before or after the yield timeout fires. This is fully repeatable and requires only ordinary signed transactions and a deployed wasm contract - no validator, node, or leaked-key access.

### Recommendation
In `remove_account` (`core/store/src/utils/mod.rs`), enumerate and remove all `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`, and `DataIdToYieldId` rows scoped to the account being deleted (mirroring how access keys and contract data are enumerated/removed), and/or have `resolve_promise_yield_timeouts`/the `PromiseResume` handler in `runtime/runtime/src/lib.rs` verify the target account still exists before executing a resumed yield receipt, invalidating/dropping stale entries tied to since-deleted accounts.

### Proof of Concept
Integration/runtime-test-loop test:
1. Create account `x.parent.near`/deploy a contract that calls `promise_yield_create_with_id` targeting itself with a callback action list containing `AddKey(attacker_pubkey, FullAccess)`.
2. Submit `DeleteAccount` for `x.parent.near` (beneficiary = attacker).
3. Assert via direct trie inspection that `TrieKey::PromiseYieldReceipt{x.parent.near, data_id}` and `YieldIdToDataId` still exist post-deletion (bug reproduction).
4. From `parent.near`, submit `CreateAccount` for `x.parent.near` again with a brand-new, unrelated key (simulating a new/innocent occupant).
5. Advance blocks past `yield_timeout_length_in_blocks` so `resolve_promise_yield_timeouts` fires the timeout resume.
6. Assert that `attacker_pubkey` was added as a full access key to the recreated `x.parent.near` account despite never being authorized by the new owner - confirming authorization escalation.
