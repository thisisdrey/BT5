Based on the code analysis, the vulnerability is confirmed.### Title
Unbounded memory buffering in `SearchFilesByName` when `offset` is non-positive and `limit<=0` - ([File: internal/gitaly/service/repository/search_files.go])

### Summary
`SearchFilesByName` passes attacker-controlled `Offset`/`Limit` values directly into `parseLsTree` with no lower/upper bound validation. When `offset <= 0` and `limit <= 0`, every matching path from `git ls-tree` is appended to the `files` slice and none of the loop's break conditions ever trigger, so the entire tree listing is buffered in memory and returned in a single `SearchFilesByNameResponse` message.

### Finding Description
In `SearchFilesByName` (`internal/gitaly/service/repository/search_files.go:160`), `req.GetOffset()` and `req.GetLimit()` are cast straight to `int` and forwarded to `parseLsTree` with no validation (`validateSearchFilesRequest` only checks `Repository`, `Query`, and `Ref`, not `Offset`/`Limit`). Inside `parseLsTree` (lines 194-221):

```go
index++
if index > offset {
    files = append(files, path)
}
if limit > 0 && len(files) >= limit {
    break
}
```

`index` starts at 1, so if `offset <= 0`, `index > offset` is true from the very first entry, meaning every matched path is appended regardless of the (attacker-supplied, possibly huge negative) offset value. The only escape from the loop is `limit > 0 && len(files) >= limit`; if the attacker sets `Limit` to `0` or a negative number, this condition never fires, so the loop only terminates on `io.EOF` from the underlying `git ls-tree -r -z` stream. The result is that `files [][]byte` accumulates one entry per matched tree path for the *entire* repository tree before a single `stream.Send(&gitalypb.SearchFilesByNameResponse{Files: files})` call is made at line 165. Because there is no `MaxSendMsgSize`/`MaxRecvMsgSize` configuration found in the codebase, gRPC's build-time defaults apply, but the server-side allocation of `files` (and the underlying git process buffering) still happens in Gitaly's memory before any transport-level size check occurs.

An unprivileged repository owner can trivially trigger this by pushing a very large tree (e.g. many thousands to millions of small blobs, which git and Gitaly permit) and issuing `SearchFilesByNameRequest{Query: ".*", Offset: 0 (or negative), Limit: 0}`. There is no repo-side git-command or ref-validation issue here — `ref` and `query` validation are unrelated to this bound — the flaw is purely the missing offset/limit sanitization in `parseLsTree`.

### Impact Explanation
This allows a single RPC call from any authenticated user who owns/controls a repository to force the Gitaly process to allocate memory proportional to the total number of paths in the repository's tree, unbounded by any configured limit. On a multi-tenant Gitaly node, this can exhaust available memory and degrade or crash the process, impacting availability for other repositories/tenants co-located on the same node — a resource-exhaustion / DoS impact matching GitLab's "Denial of Service" bounty category for shared infrastructure components.

### Likelihood Explanation
Feasibility is high: the attacker needs only standard push access to their own repository (no special role, no config changes) and can construct an arbitrarily large tree by pushing many small files across one or more commits. The RPC call itself requires no special permission beyond normal repository access. It is fully repeatable and deterministic.

### Recommendation
Validate `Offset`/`Limit` in `validateSearchFilesRequest` (or in `SearchFilesByName`) to reject negative offsets and enforce a mandatory upper bound on the number of results processed/returned regardless of the caller-supplied `Limit` (e.g., always cap `len(files)` at a fixed maximum, and break out of `parseLsTree`'s loop once that cap is hit even when `limit <= 0`). Alternatively, refactor `parseLsTree`/`SearchFilesByName` to stream results back in chunks (similar to `sendSearchFilesResultChunked` used by `SearchFilesByContent`) instead of buffering the full match set before sending.

### Proof of Concept
```go
// internal/gitaly/service/repository/search_files_test.go (illustrative)
func TestSearchFilesByName_UnboundedOffsetLimit(t *testing.T) {
    cfg, repo, repoPath := setupRepositoryService(t)
    client := newRepositoryClient(t, cfg, ...)

    // Push a tree with N (e.g. 200_000) small blobs via CreateCommit/UpdateRef helpers
    createLargeTree(t, repoPath, 200_000)

    req := &gitalypb.SearchFilesByNameRequest{
        Repository: repo,
        Ref:        []byte("refs/heads/main"),
        Query:      ".*",
        Offset:     0,   // or a large negative value
        Limit:      0,   // no limit -> parseLsTree never breaks early
    }

    var m runtime.MemStats
    runtime.ReadMemStats(&m)
    before := m.Alloc

    resp, err := client.SearchFilesByName(ctx, req)
    require.NoError(t, err)
    require.Len(t, resp.GetFiles(), 200_000) // entire tree buffered in one response

    runtime.ReadMemStats(&m)
    after := m.Alloc
    require.Greater(t, after-before, uint64(0)) // demonstrates memory scales with N
}
```
Repeating with increasing `N` (e.g., 10k, 100k, 1M entries) and measuring peak RSS/`runtime.MemStats.Alloc` confirms memory growth is unbounded and proportional to repository tree size, independent of the `Limit` field.
