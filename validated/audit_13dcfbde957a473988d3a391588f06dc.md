### Title
Non-constant-time HTTP auth-token comparison enables remote timing attack to recover `auth_token` - (File: stackslib/src/net/api/postblock_proposal.rs)

### Summary
Several privileged Stacks node RPC endpoints protect themselves with a shared-secret `Authorization` header compared against the configured `connection_options.auth_token` using Rust's native `!=` operator on `String`/`&str`. This operator short-circuits at the first differing byte, exactly the same class of defect as CVE-2024-1729 (Gradio), where Python's early-exit string comparison let a remote, unauthenticated caller recover a password byte-by-byte via response-time measurements.

### Finding Description
The following handlers implement authentication identically, comparing the caller-supplied `authorization` header directly to the configured secret with a non-constant-time `!=`:

- `RPCBlockProposalRequestHandler::try_parse_request` (`/v3/block_proposal`) [1](#0-0) 
- `RPCNakamotoBlockSimulateRequestHandler::try_parse_request` (`/v3/blocks/simulate/:block_id`) [2](#0-1) 
- `RPCNakamotoBlockReplayRequestHandler::try_parse_request` (`/v3/blocks/replay/:block_id`) [3](#0-2) 
- `RPCTransactionSimulateRequestHandler::try_parse_request` (`/v3/transactions/simulate`) [4](#0-3) 
- `RPCFastCallReadOnlyRequestHandler::try_parse_request` (`/v3/contracts/fast-call-read/...`) [5](#0-4) 
- `RPCPostBlockRequestHandler::try_parse_request` (`/v2/blocks?broadcast=1`) [6](#0-5) 

`auth_token`/`auth_password` is documented as securing the channel between the node and a `stacks-signer`, and is required to gate block-proposal submission and authenticated block broadcast [7](#0-6) . A repo-wide search confirms no constant-time comparison primitive (e.g. the `subtle` crate) is used anywhere for this comparison — `Cargo.lock` only shows it as a transitive dependency of unrelated crates, not consumed by this auth-check code path.

Rust's derived/`str` equality for byte slices/strings compiles to a length check followed by a `memcmp`-style comparison that returns as soon as a mismatching byte is found; it provides no constant-time guarantee. An attacker who can measure response latency with enough precision (many samples, statistical averaging) can recover the shared secret one byte/prefix at a time, exactly the vulnerability class described in CVE-2024-1729/GHSA-hmx6-r76c-85g9.

### Impact Explanation
`auth_token` gates:
- submission of block proposals for validation (`/v3/block_proposal`) — an important control point on the miner/signer round trip;
- authenticated `broadcast=1` block posts;
- debugging/simulation endpoints that execute arbitrary supplied blocks/transactions against chain state (`/v3/blocks/simulate`, `/v3/transactions/simulate`, `/v3/contracts/fast-call-read`), which perform real (if sandboxed) contract execution.

Recovering this secret lets a remote, unauthenticated attacker bypass the auth gate on these RPC endpoints, potentially enabling unauthorized block proposal submission/broadcast or invocation of the simulate/fast-call-read compute endpoints. This aligns with "auth bypass" / "unauthenticated write" impact categories.

### Likelihood Explanation
Exploitation requires the attacker to make a very large number of timed HTTP requests against a node whose `auth_token` endpoint is reachable over the network, and to extract a small per-byte timing signal amid ordinary network jitter. This is a realistic remote timing side channel, but the byte-comparison overhead itself is extremely fast, and the signal is easily swamped by other work the handler does per request (regex captures, header parsing, JSON body handling before/after the check), which raises the noise floor considerably compared to a pure Python string-compare test case. It is a real defect, but harder to exploit reliably than the original Gradio finding.

### Recommendation
Replace all direct `!=`/`==` comparisons of the `authorization` header against the configured secret with a constant-time comparison (e.g. via the `subtle` crate's `ConstantTimeEq`, or a manual XOR-accumulate loop that always processes the full length of both fixed hashed representations). Consider hashing both sides (e.g. HMAC) before comparing to also normalize length, and apply the same fix uniformly across `postblock_proposal.rs`, `blocksimulate.rs`, `blockreplay.rs`, `txsimulate.rs`, `fastcallreadonly.rs`, and `postblock_v3.rs`.

### Proof of Concept
1. Configure a node with `connection_options.auth_token = "S3curePassphrase"`.
2. Send repeated POST requests to `/v3/block_proposal` (or GET to `/v3/blocks/replay/<id>`) with an `authorization` header value that is correct for `N` leading bytes and incorrect afterward, e.g. try all 256 byte values for position `N+1` after fixing the first `N` bytes.
3. Because `auth_header != password` in `try_parse_request` (e.g. [8](#0-7) ) short-circuits on the first mismatched byte, requests with more correct leading bytes take marginally longer on average than those with an incorrect first byte.
4. By statistically averaging response times per candidate byte over many trials, an attacker can incrementally reconstruct the full `auth_token` without ever needing valid credentials, then use it to submit authenticated block proposals/broadcasts.
