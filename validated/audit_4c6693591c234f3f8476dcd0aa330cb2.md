### Title
Rounding-down in `MarketUtils.multiplyAndDivide` lets a taker order drain a maker's tokens for free in the exact-match branch of `MarketSellAssetActuator.matchSingleOrder` - (File: actuator/src/main/java/org/tron/core/actuator/MarketSellAssetActuator.java)

### Summary
`MarketSellAssetActuator` implements the on-chain TRC10 order-book (`MarketSellAssetContract`). When a taker's incoming sell order exactly matches a maker's remaining sell quantity ("taker == maker" branch), the amount the **maker** is owed is computed with a floor-rounding multiply-divide helper. If that computed amount rounds down to zero, the maker's order is closed and the maker's remaining tokens are transferred to the taker, but the taker's own order remains fully un-debited (0 subtracted) and the maker receives 0 tokens in return — the taker gets an asset for free at the maker's expense, mirroring the reported ERC4626 rounding-to-zero exploit.

### Finding Description
In `matchSingleOrder`, the exact-match branch is: [2](#0-1) 

```java
if (takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain()) {
  makerBuyTokenQuantityReceive = MarketUtils
      .multiplyAndDivide(makerSellRemainQuantity, makerBuyQuantity, makerSellQuantity,
          this.disableJavaLangMath());
  takerBuyTokenQuantityReceive = makerOrderCapsule.getSellTokenQuantityRemain();

  long takerSellTokenLeft =
      takerOrderCapsule.getSellTokenQuantityRemain() - makerBuyTokenQuantityReceive;
  takerOrderCapsule.setSellTokenQuantityRemain(takerSellTokenLeft);
  makerOrderCapsule.setSellTokenQuantityRemain(0);
  ...
}
```

`makerBuyTokenQuantityReceive` is the amount the maker should be paid (in the token the taker is selling), computed via: [1](#0-0) 

which is `floorDiv(makerSellRemainQuantity * makerBuyQuantity, makerSellQuantity)` — a floor (round-down) integer division, identical in nature to Solmate's `mulDivDown` cited in the external report.

If a taker crafts `sellTokenQuantity`/`buyTokenQuantity` (validated only for `>0` and an overall quantity cap, see `validate()` at [3](#0-2) ) so that it exactly matches an existing maker order's remaining sell quantity, and the price ratio `makerBuyQuantity / makerSellQuantity` is small enough that `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity`, then `makerBuyTokenQuantityReceive` evaluates to `0`.

Consequences in that case:
- `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` → the taker's sell-side balance is **not reduced at all** (the taker pays nothing).
- `makerOrderCapsule.setSellTokenQuantityRemain(0)` → the maker's order is fully closed, its remaining sell tokens (which were already deducted from the maker's account balance at order-creation time via `transferBalanceOrToken`, see [4](#0-3) ) are handed to the taker via `addTrxOrToken(takerOrderCapsule, takerBuyTokenQuantityReceive, takerAccountCapsule)` at [5](#0-4) .
- `addTrxOrToken(makerOrderCapsule, makerBuyTokenQuantityReceive)` credits the maker `0` tokens for the assets it just gave up.

This is different from the other two branches of the same function ("taker < maker" and "taker > maker"), where the analogous rounding case is explicitly checked: `takerBuyTokenQuantityRemain == 0` is guarded at [6](#0-5)  and `makerBuyTokenQuantityReceive == 0` is guarded at [7](#0-6) . The exact-match ("taker == maker") branch has **no such zero-check**, leaving the door open for the taker to receive the maker's entire remaining balance while paying nothing.

### Impact Explanation
An attacker can:
1. Place (or wait for) a maker sell order whose remaining quantity and price ratio make `makerSellRemainQuantity * makerBuyQuantity < makerSellQuantity` true.
2. Submit a `MarketSellAssetContract` (`MarketSellAssetActuator`, reachable directly by any account via a signed transaction/broadcast, no special privilege required) whose `sellTokenQuantity`/`buyTokenQuantity` exactly equal the maker's remaining order so the "taker == maker" branch is taken.
3. Receive the maker's full remaining token balance while the attacker's own sell-side order remains fully intact (not consumed) — effectively stealing TRC10 tokens (or TRX) from the maker with zero cost.

This is a direct, unauthorized theft-of-funds primitive reachable by any account through the standard `MarketSellAssetContract` transaction path, matching the Medium/High-severity criteria (concrete theft of funds via a broadcastable transaction).

### Likelihood Explanation
The attacker fully controls both the crafted taker order's price/quantity and (indirectly, by choosing which existing maker order to target) the divisor in the vulnerable division, so triggering the exact zero-rounding condition is a matter of picking small-enough quantities/price ratios — well within reach of low TRC10 balances and typical price fractions used on the DEX. No special permissions, precompiles, or privileged roles are needed; it is exploitable by any account through `MarketSellAssetActuator.execute`.

### Recommendation
Add the same zero-result safeguard used in the other two branches to the exact-match branch: if `makerBuyTokenQuantityReceive == 0` (after `multiplyAndDivide`), do not close the maker's order/transfer its tokens to the taker; either round the payment up (ceiling division) so the maker always receives at least 1 unit, or reject/return the sell-token remainder as done in the "taker > maker" branch (`makerOrderCapsule.setSellTokenQuantityReturn(); returnSellTokenRemain(...)`).

### Proof of Concept
Let a maker order be: sell 3 units of Token A for 1 unit of Token B (`makerSellQuantity=3`, `makerBuyQuantity=1`), with `makerSellRemainQuantity=1` (partially filled already).
A taker submits a `MarketSellAssetContract` selling 1 unit of Token B for 1+ units of Token A, driving `takerBuyTokenQuantityRemain == makerOrderCapsule.getSellTokenQuantityRemain() == 1` (exact match branch entered).

`makerBuyTokenQuantityReceive = multiplyAndDivide(1, 1, 3) = floorDiv(1*1, 3) = 0`.

Result: `makerOrderCapsule.setSellTokenQuantityRemain(0)` (maker's order fully closed, its 1 unit of Token A transferred to taker), while `takerSellTokenLeft = takerOrderCapsule.getSellTokenQuantityRemain() - 0` leaves the taker's sell balance untouched — the taker receives 1 unit of Token A while spending 0 units of Token B, and the maker receives 0 units of Token B for the 1 unit of Token A it lost.

  public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
    try {
      long tmp = multiplyExact(a, b, disableMath);

    }

  }
