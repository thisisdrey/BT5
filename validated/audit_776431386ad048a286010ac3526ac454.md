### Title
Silent value loss in `fungibles::Mutate::transfer` default impl due to unchecked `increase_balance` result - (File: `substrate/frame/support/src/traits/tokens/fungibles/regular.rs`)

### Summary
The default `Mutate::transfer` implementation in the `fungibles` trait module withdraws funds from the source account unconditionally and then credits the destination account, but discards the result of the credit operation with `let _ = Self::increase_balance(...)`. This mirrors the exact bug class from the external report: a value-moving operation whose "did it actually deliver the funds" signal is thrown away, so the caller reports success even when the destination was not actually credited the full (or any) amount.

### Finding Description
`Mutate::transfer` is defined generically for all `fungibles` implementers: [1](#0-0) 

```rust
fn transfer(...) -> Result<Self::Balance, DispatchError> {
    let _extra = Self::can_withdraw(...).into_result(...)?;
    Self::can_deposit(...).into_result()?;
    if source == dest { return Ok(amount); }
    Self::decrease_balance(asset.clone(), source, amount, BestEffort, preservation, Polite)?;
    // This should never fail as we checked `can_deposit` earlier. But we do a best-effort anyway.
    let _ = Self::increase_balance(asset.clone(), dest, amount, BestEffort);
    Self::done_transfer(asset, source, dest, amount);
    Ok(amount)
}
```

The comment "This should never fail... but we do a best-effort anyway" is the same logic error as the `notifyPools`/`transferFrom` bug: it treats an unchecked, best-effort operation as if it were guaranteed to succeed, and unconditionally reports `Ok(amount)` to the caller regardless of what `increase_balance` actually delivered.

`increase_balance` under `BestEffort` precision can legitimately deposit less than requested or nothing at all: [2](#0-1) 

If a concrete implementation's `increase_balance` truncates (e.g., destination account would fall below `minimum_balance` and gets forced to zero under `BestEffort`, dust handling routes part of the amount elsewhere, or any other pallet-specific edge case not anticipated by the "can_deposit already checked it" assumption), the funds already removed from `source` via `decrease_balance` are not fully credited to `dest`. The function still returns `Ok(amount)`, and `done_transfer` fires with the full nominal `amount`, so all downstream event consumers, reconciliation logic and ledger balances believe a full, successful transfer occurred.

This exact default method is reachable from live XCM asset-transfer paths, not just theoretical trait use: `FungiblesTransferAdapter::internal_transfer_asset`, used by `FungiblesAdapter`/`FungiblesMutateAdapter` (the standard `TransactAsset` implementation wired into XCM executors for `pallet-assets`-backed foreign/local assets), calls it directly: [3](#0-2) 

```rust
Assets::transfer(asset_id.clone(), &source, &dest, amount, Expendable).map_err(...)?;
Ok(what.clone())
```

`pallet-assets` itself does not override `Mutate::transfer` — its `fungibles::Mutate` impl only supplies `done_mint_into`/`done_burn_from`/`done_transfer` hooks: [4](#0-3) 

so any `internal_transfer_asset`/`Assets::transfer` call for `pallet-assets` (including `ForeignAssets` on AssetHub, which is the settlement asset for Snowbridge bridge rewards and inbound-message asset delivery) runs through this default, unchecked-credit code path.

Additionally, `pallet-assets`'s own `Unbalanced::increase_balance` override always returns `Ok(amount)` regardless of what the internal deposit actually did: [5](#0-4) 

```rust
fn increase_balance(...) -> Result<Self::Balance, DispatchError> {
    Self::increase_balance(asset, who, amount, |_| Ok(()))?;
    Ok(amount)
}
```

This compounds the problem: even if a caller wanted to inspect the actual credited amount from `Mutate::transfer`'s `increase_balance` call, the pallet-assets implementation itself hard-codes the nominal `amount` as the return value instead of the value actually applied to storage, defeating any attempt to detect a partial/failed credit at a lower layer as well.

### Impact Explanation
This breaks the "conserve value / settle exactly once to the rightful beneficiary and amount" invariant called out in the pivots: value can be debited from the source without being fully (or at all) credited to the destination, while the transfer call still reports full success and emits a `Transferred`/`done_transfer` event for the full nominal amount. In the context of XCM asset transfers (`internal_transfer_asset`) backing bridge settlement and reserve-asset movement on AssetHub, this can silently destroy user or bridge-controlled asset balances (permanent fund loss) without any error surfacing to the runtime, since the code deliberately treats the credit step as "should never fail" and swallows its result.

### Likelihood Explanation
The unsafe pattern is baked into the generic trait default that ships in `frame_support` and is used by any `fungibles` implementer that doesn't override `transfer` — including `pallet-assets`, which backs `ForeignAssets`/bridge asset accounting on AssetHub and is invoked directly from the XCM `TransactAsset` adapters used in cross-chain and cross-consensus asset movement. Triggering the discrepancy requires only an XCM asset-transfer instruction targeting a destination account state where `increase_balance`'s `BestEffort` behavior diverges from the amount validated by `can_deposit` (e.g., destination account churn/holds/freezes changing state between the `can_deposit` check and the actual `increase_balance` call within the same extrinsic, or any asset-specific edge case in the underlying storage mutation) — no privileged actor, relayer, or governance action is needed, only a normal signed XCM/asset transfer.

### Recommendation
- Short term: change `Mutate::transfer`'s default implementation to capture the actual value returned by `increase_balance` and compare it against the requested `amount`; if they differ, return an error (and roll back the `decrease_balance` within a transactional guard) instead of silently reporting `Ok(amount)`. Alternatively, use `Exact` precision for the increase step given `can_deposit` was already validated, so any divergence surfaces as a hard error rather than being swallowed.
- Also fix `pallet-assets`'s `Unbalanced::increase_balance` override to return the balance actually applied rather than hard-coding the requested `amount`, so any caller relying on the return value gets an accurate signal.
- Long term: add an invariant/property test (or `try-runtime` `try_state` check) asserting that `total_issuance` and the sum of `source`+`dest` balances are conserved across every `fungibles::Mutate::transfer` call in test suites, and audit all default `frame_support` trait methods for `let _ = ...`/discarded-`Result` patterns on value-moving operations.

2. Call `Assets::transfer(asset_id, &source, &dest, amount, Expendable)` (e.g., via an XCM `internal_transfer_asset` reserve/local transfer instruction).

	fn increase_balance(
		asset: Self::AssetId,
		who: &AccountId,
		amount: Self::Balance,
		precision: Precision,
	) -> Result<Self::Balance, DispatchError> {
		let old_balance = Self::balance(asset.clone(), who);
		let new_balance = if let BestEffort = precision {
			old_balance.saturating_add(amount)
		} else {
			old_balance.checked_add(&amount).ok_or(ArithmeticError::Overflow)?
		};
		if new_balance < Self::minimum_balance(asset.clone()) {
			// Attempt to increase from 0 to below minimum -> stays at zero.
			if let BestEffort = precision {
				Ok(Self::Balance::default())
			} else {
				Err(TokenError::BelowMinimum.into())
			}
		} else {
			if new_balance == old_balance {
				Ok(Self::Balance::default())
			} else {
				if let Some(dust) = Self::write_balance(asset.clone(), who, new_balance)? {
					Self::handle_dust(Dust(asset, dust));
				}
				Ok(new_balance.saturating_sub(old_balance))
			}
		}
	}
