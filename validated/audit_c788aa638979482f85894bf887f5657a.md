### Title
Division by zero in share price calculation - ([File: tare-io__tare-contracts/contracts/PortfolioVault.sol])

### Summary
The `PortfolioVault` contract contains a division by zero vulnerability in its `sharePrice` view function. If the vault's share supply is zero, any call to `sharePrice()` will revert. While the protocol attempts to prevent this by minting `DEAD_SHARES` to a `0xdead` address during construction, this protection relies on the assumption that these shares can never be burned. However, the `VaultShareToken` contract implements a `BURNER_ROLE` that can be granted by the `GUARDIAN_ROLE`, and the vault itself holds this role. If the `DEAD_SHARES` are ever burned or if the vault is deployed without them, the function becomes a DoS vector for external integrators.

### Finding Description
In `PortfolioVault.sol`, the `sharePrice()` function calculates the price of a share by dividing the `lastNav` by the `shareToken.totalSupply()`. [1](#0-0) 

Unlike the `convertToShares` and `convertToAssets` functions, which include an explicit check for `lastNav == 0`, the `sharePrice` function lacks any guard against a zero denominator (`totalSupply`). [2](#0-1) 

The protocol's defense is the minting of `1e18` "dead shares" in the constructor. [3](#0-2)  However, the `VaultShareToken` contract explicitly defines a `BURNER_ROLE` and a `burn` function. [4](#0-3) [5](#0-4)  If the `DEAD_SHARES` are removed from the supply, the `sharePrice` function will revert on every call, causing a permanent DoS for any contract or UI that relies on this view.

### Impact Explanation
Material production DoS. Any external protocol, oracle, or frontend integration that calls `sharePrice()` to determine the value of vault shares will revert. This blocks users from viewing their position value and prevents other smart contracts from interacting with the vault's price data. While the core async deposit/redeem flows are protected by `_requireFreshNav`, the breakage of the primary price view constitutes a material corruption of the protocol's public state and accessibility.

### Likelihood Explanation
Low. It requires the `DEAD_SHARES` to be absent from the `totalSupply`. Under normal operating conditions, the dead shares are minted at deployment and the `0xdead` address cannot authorize their burning. However, the vulnerability exists as a "native analog" to the reported bug because the code lacks the standard defensive check (`totalSupply > 0`) used in other parts of the same contract.

### Recommendation
Add a zero-check for `totalSupply` in the `sharePrice` function, similar to the checks in `convertToShares`.
```solidity
function sharePrice() external view returns (uint256) {
    uint256 supply = shareToken.totalSupply();
    if (supply == 0) return 0; // or a fixed bootstrap price
    return (lastNav * WAD_UNIT) / supply;
}
```

### Proof of Concept
1. Deploy `VaultShareToken` and `PortfolioVault`.
2. Observe that `sharePrice()` returns a value based on `DEAD_SHARES`.
3. If a `GUARDIAN_ROLE` (unprivileged DoS path as per audit scope for "practically unrecoverable lock") or a bug allows the burning of shares such that `totalSupply` becomes 0.
4. Call `vault.sharePrice()`.
5. The transaction reverts with a Panic (division by zero).
