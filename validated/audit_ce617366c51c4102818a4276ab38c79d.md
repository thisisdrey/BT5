### Title
Missing slippage protection on `VesperGateway.withdraw` when redeeming yield-bearing `vToken` collateral - (File: contracts/VesperGateway.sol)

### Summary
`VesperGateway.withdraw` burns the user's `DepositToken` (msdToken) and redeems the corresponding `vToken` shares on a Vesper `VPool`, then forwards whatever `underlying` amount the pool returns. The Vesper pool exchange rate is time-dependent (interest accrual / rebasing share price), but the function exposes no `minAmountOut` (or deadline) parameter, so the user commits to an unknown output amount at the moment the transaction executes.

### Finding Description
In `contracts/VesperGateway.sol`, `withdraw(IPool pool_, IVPool vToken_, uint256 amount_)` (L73–93) performs:
1. Pulls `amount_` msdTokens from the caller (L80).
2. Calls `_depositToken.withdraw(amount_, address(this))` to get `_vTokenAmount` shares (L83).
3. Calls `vToken_.withdraw(_vTokenAmount)` and measures the balance delta of `underlying` (L87–89).
4. Transfers the entire `_underlyingAmount` to the caller (L92).

The amount of `underlying` received is entirely determined by the `VPool`'s current share price — a value that drifts with interest accrual and can also move within a block via pool interactions (reporting, fee harvests, losses). The caller signs a transaction that burns a fixed number of msdTokens/vTokens without any bound on the resulting output. The same gap exists in `deposit` (L44–65): the user transfers `amount_` underlying and accepts whatever `_vTokenAmount` the pool mints at the prevailing rate, with no `minSharesOut`.

This mirrors the reported `CusdcV3Wrapper._withdraw` issue: the conversion rate between the share token and the underlying is an internal, time-dependent value (`getUpdatedSupplyIndicies`/`baseSupplyIndex` there, Vesper `pricePerShare` here) that ordinary users cannot easily simulate or constrain at execution time.

### Impact Explanation
Two users redeeming equivalent msdToken amounts near the same time can receive different underlying amounts purely due to pool state drift between their transactions. A user who cannot accurately predict `pricePerShare` (e.g., a harvest or loss event lands in the same block, or the tx sits in the mempool) silently accepts a worse exchange rate. The loss is bounded but unrecoverable: the msdTokens/vTokens are already burned before the pool returns the underlying. This is a timing/slippage-class user-fund loss; no privileged role is required — any public caller of `VesperGateway.withdraw` is exposed.

### Likelihood Explanation
Medium-low. Vesper share price normally only appreciates smoothly, so the expected loss per redemption is small; meaningful divergence requires a same-block share-price event (interest reporting, strategy harvest/loss) or mempool delay. The gap is systemic (no parameter exists at all), but realized loss per call is typically minor — consistent with the Medium rating of the source finding.

### Recommendation
Add an explicit output bound to both entry points, e.g.:
```solidity
function withdraw(IPool pool_, IVPool vToken_, uint256 amount_, uint256 minUnderlyingOut_) external;
```
and after L89:
```solidity
if (_underlyingAmount < minUnderlyingOut_) revert SlippageExceeded();
```
Similarly add `minVTokenOut_`/`minMsdOut_` to `deposit`. Alternatively document/emit a quote helper so callers can bound `pricePerShare` client-side.

### Proof of Concept
Fork test (Hardhat) on a deployed pool registered in `PoolRegistry`:

```ts
// 1. Alice deposits USDC via VesperGateway into a vaUSDC pool → receives msdvaUSDC.
await usdc.connect(alice).approve(vesperGateway.address, amount);
await vesperGateway.connect(alice).deposit(pool.address, vaUSDC.address, amount);

// 2. Warp time / trigger a VPool harvest or a strategy loss so pricePerShare shifts.
await evmIncreaseTime(30 * 24 * 3600);
// (fork) poke the Vesper pool: await vaUSDCPool.reportEarning(...) or simulate loss.

// 3. Alice calls withdraw(amount_) — she has NO way to enforce a minimum out.
await msdToken.connect(alice).approve(vesperGateway.address, shares);
const balBefore = await usdc.balanceOf(alice.address);
await vesperGateway.connect(alice).withdraw(pool.address, vaUSDC.address, shares);
const received = (await usdc.balanceOf(alice.address)).sub(balBefore);

// 4. Show that received != quote at submission time (pricePerShare moved),
//    and that two identical withdraws at different block states yield different outputs,
//    proving the user burns shares at a rate they could not bound.
expect(received).to.not.eq(quotedAmount);
```

    function withdraw(IPool pool_, IVPool vToken_, uint256 amount_) external override nonReentrant {
        if (!_poolRegistry.isPoolRegistered(address(pool_))) revert UnregisteredPool();

        address _msgSender = _msgSender();

        // 1. Get `msdTokens`
        IDepositToken _depositToken = pool_.depositTokenOf(vToken_);
        _depositToken.safeTransferFrom(_msgSender, address(this), amount_);

        // 2. Withdraw `vTokens` from `Synth`
        (uint256 _vTokenAmount, ) = _depositToken.withdraw(amount_, address(this));

        // 3. Withdraw `underlying` from `VPool`
        IERC20 _underlying = IERC20(vToken_.token());
        uint256 _balanceBefore = _underlying.balanceOf(address(this));
        vToken_.withdraw(_vTokenAmount);
        uint256 _underlyingAmount = _underlying.balanceOf(address(this)) - _balanceBefore;

        // 4. Transfer `underlying` to the `_msgSender()`
        _underlying.safeTransfer(_msgSender, _underlyingAmount);
    }
