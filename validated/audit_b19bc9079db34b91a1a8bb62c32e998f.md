### Title
Unchecked `null` return from `getShieldTransactionHashIgnoreTypeException()` used directly as the signature hash in shielded-transfer proof verification - (File: actuator/src/main/java/org/tron/core/actuator/ShieldedTransferActuator.java)

### Summary
`TransactionCapsule.getShieldTransactionHashIgnoreTypeException()` is documented to "ignore" `ContractValidateException`/`InvalidProtocolBufferException` and explicitly returns `null` on failure instead of propagating the error. [1](#0-0) . Some callers (`ZenTransactionBuilder.build()`, `Wallet.getShieldTransactionHash`, `ShieldedReceiveTest` helper) explicitly check the result for `null` before use [2](#0-1) . However, `ShieldedTransferActuator.checkProof()`, which runs during actuator `validate()`/`execute()` for every `ShieldedTransferContract` broadcast to the network, calls this same method and immediately feeds the (possibly-`null`) result as `signHash` into the native zk-SNARK verification calls without any null check [3](#0-2) .

### Finding Description
`hashShieldTransaction()` throws `ContractValidateException` when the transaction's first contract is not actually a `ShieldedTransferContract`, and `InvalidProtocolBufferException` on protobuf unpack errors [4](#0-3) . `getShieldTransactionHashIgnoreTypeException()` swallows both exceptions and returns `null` instead of surfacing an error [1](#0-0) , exactly analogous to `ext4_dirhash()` being allowed to fail while its callers assumed success.

`ShieldedTransferActuator.checkProof()` calls this function and stores the result into `signHash` with no validation: [5](#0-4) 
That `signHash` (potentially `null`) is passed straight into `JLibrustzcash.librustzcashSaplingCheckSpend(...)` and `librustzcashSaplingFinalCheck(...)` — native JNI calls into `librustzcash` — as the signature/binding-signature hash input [6](#0-5) . Passing a `null` byte array reference across the JNI boundary into a native function expecting a fixed-size buffer is undefined behavior at the native layer (unlike a normal Java `NullPointerException`), and depending on the JNI binding's argument marshaling it can crash the node process (denial of service) or, if the native code dereferences the pointer without a length/null check, read out-of-bounds/uninitialized memory when constructing the verification context.

### Impact Explanation
This code path is reached by any account broadcasting a `ShieldedTransferContract` transaction — a normal user transaction type, not something requiring special privilege. If the actuator's own contract-type dispatch logic can be bypassed or if the `Any` unpack of the contract inside `hashShieldTransaction()` fails for a crafted malformed proto payload embedded in an otherwise well-typed `ShieldedTransferContract`, the exception is silently converted to `null`, and that `null` is then handed to native cryptographic code. A crash of the native verification routine on every node processing this transaction would constitute a chain-wide denial of service (block processing halt) once included in a block, since all full nodes execute the same `validate()`/`execute()` path deterministically.

### Likelihood Explanation
Likelihood is moderated by the fact that `ShieldedTransferActuator.validate()` (not shown in the excerpt but implied by the class's normal contract-type dispatch) is expected to have already unpacked the same `ShieldedTransferContract` earlier in validation, meaning `contractParameter.is(ShieldedTransferContract.class)` in `hashShieldTransaction()` should normally succeed. The remaining failure mode is `InvalidProtocolBufferException` during `contractParameter.unpack(ShieldedTransferContract.class)`, which can occur if the `Any` payload's embedded bytes are corrupted/truncated in a way that passes the `is()` type-URL check but fails full deserialization — a scenario that is plausible but requires proof/testing against the exact protobuf validation performed earlier in the actuator to confirm reachability with a truly malformed but type-matching payload.

### Recommendation
Change `ShieldedTransferActuator.checkProof()` to check `signHash != null` immediately after calling `getShieldTransactionHashIgnoreTypeException()`, throwing `ZkProofValidateException` on failure exactly as `ZenTransactionBuilder.build()` already does [7](#0-6) . More robustly, eliminate the "ignore type exception" pattern entirely in actuator/consensus-critical code paths and require `hashShieldTransaction()`'s checked exceptions to propagate and abort the transaction, consistent with the ext4 fix's approach of making callers of a possibly-failing hash function check and reflect errors upward.

### Proof of Concept
Concrete exploitation requires crafting a `ShieldedTransferContract` transaction whose `Any` parameter has a type URL matching `ShieldedTransferContract` (passing `contractParameter.is(ShieldedTransferContract.class)`) but whose serialized bytes are corrupted such that `contractParameter.unpack(ShieldedTransferContract.class)` throws `InvalidProtocolBufferException` inside `hashShieldTransaction()` while still being accepted by whatever earlier validation/deserialization step populates `shieldedTransferContract` in the actuator. I could not verify from the available index whether such a divergence between the `Any.is()` check and `unpack()` behavior, combined with the actuator's earlier field access, is actually reachable in practice — this requires either full source review of `ShieldedTransferActuator`'s constructor/`validate()` (which the index only partially exposed) or a live Devin session to construct and test the exact byte-level payload against the deserialization path.
