Audit Report

## Title
Reward-per-token checkpoint advances even when `total_tokens_staked == 0`, permanently forfeiting streamed rewards for empty pools - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` correctly refuses to accrue `reward_per_token_stored` when `pool_info.total_tokens_staked.is_zero()` [1](#0-0) , but `update_pool_rewards`, called unconditionally right after in `update_pool_and_staker_rewards`, still advances `last_update_block` to the current block regardless of whether the pool had any stakers [2](#0-1) . This permanently excludes any zero-stake window from future reward accrual, and the only recovery path, `cleanup_pool`, requires zero stakers at call time, which any unprivileged staker can block indefinitely by keeping a dust stake.

## Finding Description
`update_pool_and_staker_rewards` calls `reward_per_token` first, then unconditionally calls `update_pool_rewards(pool_info, reward_per_token)` [3](#0-2) . Inside `update_pool_rewards`, `new_pool_info.last_update_block` is always set to `T::BlockNumberProvider::current_block_number()` [4](#0-3) , even though `reward_per_token` deliberately left `reward_per_token_stored` unchanged for the zero-stake case [5](#0-4) . Since `rewardable_blocks_elapsed` in future `reward_per_token` calls is computed as `current_block - pool_info.last_update_block` [6](#0-5) , once `last_update_block` is bumped during a zero-stake window, that window's implied reward-rate accrual can never be recovered.

This path is triggered from the fully public `stake` extrinsic, which calls `update_pool_and_staker_rewards` using the pool's *pre-stake* state — meaning on the very first stake into an empty pool, `total_tokens_staked` is still zero when the checkpoint update executes [7](#0-6) . Likewise `unstake` and `harvest_rewards` invoke the same function and can drive a pool to (or leave it at) zero stakers while advancing the checkpoint [8](#0-7) .

The only escape hatch for stranded reward-asset balance is `cleanup_pool`, which requires `PoolStakers::<T>::iter_key_prefix(pool_id).next()` to be `None`, i.e., zero stakers, or it returns `Error::<T>::NonEmptyPool` [9](#0-8) . Any unprivileged staker can keep a minimal nonzero stake in the pool forever, permanently preventing this condition from being satisfied and blocking the admin's only reclaim mechanism for the pot's reducible balance [10](#0-9) .

## Impact Explanation
Reward tokens funded via the public `deposit_reward_tokens` extrinsic for any block range in which the pool had zero stakers are never credited to `reward_per_token_stored` and cannot be recovered through the normal accrual mechanism [11](#0-10) . Combined with an unprivileged staker maintaining a dust stake to permanently block `cleanup_pool`, this results in a genuine permanent lock of the unaccounted reward-asset balance in the pool's pot account, matching the "permanent user-fund lock" impact category.

## Likelihood Explanation
No privileged actor or off-chain assumption is required. Any signed account can: (1) let a pool sit with zero stakers for some blocks (trivially achieved via `unstake` of the full balance, or simply being first to stake into a freshly created pool), and (2) maintain any nonzero stake indefinitely to keep `PoolStakers` non-empty, permanently blocking `cleanup_pool`. Both preconditions are ordinary operational states reachable through the pallet's normal public extrinsics.

## Recommendation
In `update_pool_rewards`, only advance `last_update_block` when `pool_info.total_tokens_staked` is nonzero, so that the "elapsed blocks" checkpoint continues from the last block at which the pool had nonzero stake, preventing silent forfeiture of streamed rewards during empty-pool windows. Additionally, consider allowing `cleanup_pool` (or a dedicated admin reclaim function) to recover pot balance in excess of what remains claimable by current stakers, independent of whether the pool currently has stakers.

## Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R` and deposits reward tokens via `deposit_reward_tokens`.
2. The pool sits idle for `N` blocks with `total_tokens_staked == 0`.
3. Account `A` calls `stake(pool_id, 1)`: `update_pool_and_staker_rewards` observes `total_tokens_staked == 0`, so `reward_per_token` returns `reward_per_token_stored` unchanged, but `update_pool_rewards` still sets `last_update_block = current_block`, discarding the `N`-block accrual window.
4. Account `A` never fully unstakes. `cleanup_pool` always fails with `Error::<T>::NonEmptyPool`, so the admin can never reclaim the pot's leftover balance for that skipped window, even after `expiry_block` passes.

				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,

			pool_info.total_tokens_staked.ensure_add_assign(amount)?;

			// Emit event.
			Self::deposit_event(Event::Staked { staker, pool_id, amount });

			Ok(())

		#[pallet::call_index(2)]
		pub fn unstake(
			origin: OriginFor<T>,
			pool_id: PoolId,
			amount: T::Balance,
			staker: Option<T::AccountId>,
		) -> DispatchResult {
			let caller = ensure_signed(origin)?;
			let staker = staker.unwrap_or(caller.clone());

			// Always start by updating the pool rewards.
			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			let now = T::BlockNumberProvider::current_block_number();
			ensure!(now > pool_info.expiry_block || caller == staker, BadOrigin);

			let staker_info = PoolStakers::<T>::get(pool_id, &staker).unwrap_or_default();
			let (mut pool_info, mut staker_info) =
				Self::update_pool_and_staker_rewards(&pool_info, &staker_info)?;

			// Check the staker has enough staked tokens.
			ensure!(staker_info.amount >= amount, Error::<T>::NotEnoughTokens);

			// Unfreeze staker assets.
			T::AssetsFreezer::decrease_frozen(
				pool_info.staked_asset_id.clone(),
				&FreezeReason::Staked.into(),
				&staker,
				amount,
			)?;

			// Update Pools.
			pool_info.total_tokens_staked.ensure_sub_assign(amount)?;
			Pools::<T>::insert(pool_id, pool_info);

			// Update PoolStakers.
			staker_info.amount.ensure_sub_assign(amount)?;

			if staker_info.amount.is_zero() && staker_info.rewards.is_zero() {
				PoolStakers::<T>::remove(&pool_id, &staker);
			} else {
				PoolStakers::<T>::insert(&pool_id, &staker, staker_info);
			}

			// Emit event.
			Self::deposit_event(Event::Unstaked { caller, staker, pool_id, amount });

			Ok(())
		}
