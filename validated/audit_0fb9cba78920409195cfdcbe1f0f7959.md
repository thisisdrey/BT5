### Title
Unbounded memory growth in per-block solidity contract-trigger queues via attacker-controlled contract events - (File: `framework/src/main/java/org/tron/common/logsfilter/capsule/ContractTriggerCapsule.java`, `framework/src/main/java/org/tron/core/config/args/Args.java`, `framework/src/main/java/org/tron/core/db/Manager.java`)

### Summary
On any FullNode running with `eventSubscribe`'s solidity trigger mode enabled (`isSolidityEventTriggerEnable`/`isSolidityLogTriggerEnable`), every smart-contract call that emits an event or log causes an entry to be buffered in a process-wide `ConcurrentHashMap<Long, BlockingQueue<...>>` keyed by block number, using an **unbounded** `LinkedBlockingQueue`. An unprivileged contract deployer/caller can therefore force the node to accumulate unlimited numbers of trigger objects in memory for every block it submits transactions in, exactly analogous to the Xen xenstore bug where guests can force xenstored to buffer unbounded watch events/responses in memory.

### Finding Description
`ContractTriggerCapsule.processTrigger()` inserts contract event/log triggers directly into two static maps whenever the corresponding trigger type is enabled: [1](#0-0) [2](#0-1) [3](#0-2) 

The backing collections are declared as plain, uncapped `LinkedBlockingQueue` instances, created lazily via `computeIfAbsent` for every new block number: [4](#0-3) 

Because a no-argument `LinkedBlockingQueue()` has `Integer.MAX_VALUE` capacity, `offer()` on it never fails in practice, so the `"too many triggers ... lost"` log guard is effectively dead code — nothing actually caps how many trigger objects accumulate per block, and nothing caps how many block numbers can exist simultaneously as keys before solidification catches up.

This insertion path is invoked synchronously for every contract call from `postContractTrigger`, which runs during ordinary transaction/block application — reachable by any account broadcasting a transaction that calls a contract emitting events: [5](#0-4) 

The only cleanup path removes a *single* block-number key, and only for the currently reorged head block: [6](#0-5) 

Draining of the per-block queues into the plugin only happens once a block becomes solidified, via `postSolidityLogContractTrigger`/`postSolidityEventContractTrigger` driven by `postSolidityTrigger`: [7](#0-6) 

Until solidification advances (which under normal TRON consensus timing, network partitions, SR downtime, or an attacker-induced fork/`unsolidifiedBlockCheck` backlog can lag well behind the chain head), every event-emitting call an attacker submits keeps growing these in-memory queues with no size limit, unlike the sibling real-time queue `triggerCapsuleQueue`/`RealtimeEventService` which does enforce `maxEventSize`: [8](#0-7) 

### Impact Explanation
An attacker with no privileges beyond the ability to deploy and repeatedly call a contract that emits many events per transaction (trivially cheap, bounded only by energy limits, which still allow thousands of `LOG` opcodes per block) can force any operator running an event-subscribing FullNode (a standard production configuration used by exchanges/wallets consuming TRON events) to buffer unbounded trigger objects in the JVM heap. Sustained abuse leads to heap exhaustion and an OutOfMemoryError, crashing or hanging the FullNode's block-application thread — a legitimate node-crash/DoS impact reachable purely through the ordinary "broadcast a transaction that calls a contract" path.

### Likelihood Explanation
Any account can deploy a contract and call it repeatedly to emit large volumes of events; this requires no special permission, key compromise, or malicious-SR/peer role — only that the target node has solidity event/log triggers enabled, which is a documented, commonly-used production feature for services consuming chain events, not a mocked/test-only path. Likelihood is amplified whenever solidification lags (network stress, SR slowdowns, or attacker-induced load), which increases the outstanding block-number key set and per-key queue sizes simultaneously.

### Recommendation
Bound the `LinkedBlockingQueue` instances created in `Args.getSolidityContractLogTriggerMap()`/`getSolidityContractEventTriggerMap()` with an explicit capacity, and enforce/respect the `offer()` failure return in `ContractTriggerCapsule.processTrigger()` by actually dropping the oldest entries or throttling further trigger creation for a given block once the cap is hit. Additionally, bound the number of distinct block-number keys retained in these maps (e.g., evict once too many unsolidified block entries accumulate) instead of relying solely on `clearSolidityContractTriggerCache` firing on reorg of the current head.

### Proof of Concept
1. Operate (or target) a FullNode configured with `eventSubscribe.filter.event = true` (or `solidityLog`/`solidityEvent` triggers enabled) so that `isSolidityEventTriggerEnable()`/`isSolidityLogTriggerEnable()` is `true`.
2. Deploy a contract whose fallback/entry function emits the maximum practical number of `LOG` events allowed by the per-transaction energy limit.
3. Repeatedly broadcast transactions calling this contract across many blocks while solidification is delayed (naturally occurs during normal consensus latency, or can be amplified by network conditions).
4. Observe `Args.getSolidityContractEventTriggerMap()`/`getSolidityContractLogTriggerMap()` growing without bound in heap dumps as unsolidified block numbers accumulate as keys, each backed by an uncapped `LinkedBlockingQueue`, eventually leading to OutOfMemoryError on the node.

  private void postContractTrigger(final TransactionTrace trace, boolean remove, String blockHash) {
    boolean isContractTriggerEnable = EventPluginLoader.getInstance()
        .isContractEventTriggerEnable() || EventPluginLoader
        .getInstance().isContractLogTriggerEnable();
    boolean isSolidityContractTriggerEnable = EventPluginLoader.getInstance()
        .isSolidityEventTriggerEnable() || EventPluginLoader
        .getInstance().isSolidityLogTriggerEnable();
    if (eventPluginLoaded
        && (isContractTriggerEnable || isSolidityContractTriggerEnable)) {
      // be careful, trace.getRuntimeResult().getTriggerList() should never return null
      for (ContractTrigger trigger : trace.getRuntimeResult().getTriggerList()) {
        ContractTriggerCapsule contractTriggerCapsule = new ContractTriggerCapsule(trigger);
        contractTriggerCapsule.getContractTrigger().setRemoved(remove);
        contractTriggerCapsule.setLatestSolidifiedBlockNumber(getDynamicPropertiesStore()
            .getLatestSolidifiedBlockNum());
        contractTriggerCapsule.setBlockHash(blockHash);

        // Process synchronously to avoid race condition between async queue and
        // reOrgContractTrigger cache clearing. Performance is not impacted because
        // processTrigger() only enqueues events into the plugin's internal queue
        // without blocking on actual I/O.
        try {
          contractTriggerCapsule.processTrigger();
        } catch (Throwable throwable) {
          logger.warn("Post contract trigger failed.", throwable);
        }
      }

  private static BlockingQueue<Event> queue = new LinkedBlockingQueue<>();

  private int maxEventSize = 10000;

  private final ScheduledExecutorService executor = ExecutorServiceManager
      .newSingleThreadScheduledExecutor("realtime-event");

  public void init() {
    executor.scheduleWithFixedDelay(() -> {
      try {
        work();
      } catch (Exception e) {
        logger.error("Realtime event service fail.", e);
      }
    }, 1, 1, TimeUnit.SECONDS);
    logger.info("Realtime event service start.");
  }

  public void close() {
    try {
      work();
      executor.shutdown();
      logger.info("Realtime event service close.");
    } catch (Exception e) {
      logger.warn("Close realtime event service fail. {}", e.getMessage());
    }
  }

  public void add(Event event) {
    if (queue.size() >= maxEventSize) {
      logger.warn("Add event failed, blockId {}.", event.getBlockEvent().getBlockId().getString());
      return;
    }
    queue.offer(event);
  }
