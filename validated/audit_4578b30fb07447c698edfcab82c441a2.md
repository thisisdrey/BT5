Confirmed: `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` enforces chunk size and `max_writes` bound but never checks `write_freq` at all — the wall-clock rate limit is simply absent from this code path. The HTTP `POST /v2/stackerdb/...` handler in `stackslib/src/net/api/poststackerdbchunk.rs` calls this function directly with no bandwidth/frequency throttling of its own (unlike the P2P `StackerDBPushChunk` path, which is throttled by `validate_stackerdb_push` in `chat.rs` before the chunk is even accepted for storage).

### Title
Missing write-frequency ("write_freq") enforcement on StackerDB HTTP chunk writes lets a valid slot signer bypass the configured throttle - (File: `stackslib/src/net/stackerdb/db.rs`)

### Summary
`StackerDBConfig.write_freq` is meant to be the minimum wall-clock time that must elapse between successive writes to the same slot [1](#0-0) . It is enforced in the sync/pull path in `sync.rs` (`self.write_freq > 0 && write_ts + self.write_freq > now`) [2](#0-1) , but `try_replace_chunk`, the function that actually performs the write validation and storage for a chunk, never checks `write_freq` — it only checks chunk size, slot ownership/signature, staleness, and `max_writes` [3](#0-2) .

### Finding Description
The HTTP endpoint `RPCPostStackerDBChunkRequestHandler::try_handle_request` in `poststackerdbchunk.rs` accepts a signed chunk from any remote client and passes it straight to `tx.try_replace_chunk(...)` [4](#0-3) . That function's own doc-comment for the sibling P2P push-validation routine explicitly notes "the write frequency is not checked for this chunk. This is because the ConversationP2P on which this chunk arrived will have already bandwidth-throttled the remote peer..." [5](#0-4)  — i.e., the design assumes some other layer enforces the rate limit. For P2P pushes that assumption holds because `validate_stackerdb_push` applies a bytes/sec cap before the chunk reaches storage logic [6](#0-5) . But the HTTP POST endpoint has no equivalent per-peer bandwidth/frequency gate before calling `try_replace_chunk`, and `try_replace_chunk` itself performs no `write_freq` check at all (only `chunk_size` and `max_writes` bounds) [7](#0-6) . A signer who holds a valid private key for any allocated slot can therefore submit successive chunks with strictly increasing `slot_version` as fast as the network/HTTP stack allows, completely ignoring the wall-clock throttle the StackerDB's controlling contract intended via `write-freq`, up until `max_writes` is exhausted.

### Impact Explanation
This breaks the equality between "intended write cadence" (as configured by the contract's `write-freq`) and "actually enforced write cadence" on the HTTP write path. A malicious or compromised slot signer can consume the entire `max_writes` budget for a reward cycle almost instantly via repeated HTTP POSTs, causing rapid SQLite churn/storage writes and — because `StackerDBChunk`/ack responses may also be relayed to other peers via P2P inventory gossip — driving unnecessary chunk re-sync traffic across the network. This is a bounded logic/DoS-adjacent issue (write budget exhaustion / storage churn), not merely raw traffic volume, since the rate is meant to be logically capped by protocol config and that cap is silently ignored on this specific write path.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to already control a valid slot-signer private key (as any legitimate Signer/StackerDB participant would), which is a normal, non-privileged network participant condition (not an "admin" role) rather than a protocol secret. Given that, hitting the unthrottled HTTP endpoint requires no special access — any such signer can immediately fire off writes at line rate.

### Recommendation
Enforce `config.write_freq` inside `try_replace_chunk` (or in the HTTP handler before calling it), analogous to the check already performed in `sync.rs`, comparing the slot's stored `write_time` against `now` and rejecting with `net_error::TooFrequentSlotWrites` when writes arrive faster than the configured frequency, regardless of transport (HTTP or P2P).

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u60` (writes to the same slot must be ≥60s apart) and a generous `max-writes`.
2. As a valid slot signer, sign and POST two chunks to `/v2/stackerdb/<contract>/chunks` for the same `slot_id` with `slot_version = 1` then `slot_version = 2`, sent back-to-back within milliseconds.
3. Observe that `try_replace_chunk` in `stackslib/src/net/stackerdb/db.rs` accepts both writes (subject only to `chunk_size` and `max_writes` checks) even though less than 60 seconds elapsed, whereas the same rapid-fire pattern issued through the sync/pull code path would be skipped by the `write_freq` check in `sync.rs`.

    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
