### Title
Legacy `ExchangeProcessor` bancor-curve math uses floating-point division/`Math.pow`, causing systematic precision loss that shorts users on `ExchangeTransactionContract` / `ExchangeWithdrawContract` trades - ([File: chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java])

### Summary
The reported Numa bug is a class of "fixed/low-precision arithmetic in a multi-step conversion formula causes users to receive less of the target asset than the mathematically correct amount." The equivalent construct in java-tron is the legacy TRC10 bancor-relay `Exchange` (market-order) price calculation in `ExchangeProcessor`, which is the default calculation path used by `ExchangeCapsule.transaction()` unless the node operator explicitly enables the "hardened" `BigDecimal`-based calculation via a chain parameter.

### Finding Description
`ExchangeCapsule.transaction()` is the entry point invoked by `ExchangeTransactionActuator.execute/doValidate`, `ExchangeInjectActuator`, and `ExchangeWithdrawActuator` for any account that submits an `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` — i.e. it is reachable by any unprivileged order placer / transaction broadcaster. [1](#0-0) 

It selects between two `Processor` implementations depending on the `hardenedCalc` flag: [2](#0-1) 

When hardened calculation is not enabled (the historical/default behavior), `ExchangeProcessor` is used. It computes the bancor "relay" conversion using **native `double` arithmetic and `Math.pow`**, then truncates the `double` result to a `long` via a hard cast: [3](#0-2) 

This mirrors the root cause pattern in the Numa report exactly: a chained scale/divide computation performed in insufficiently precise arithmetic (there, `BASE_1000` fixed-point integer division; here, IEEE-754 `double` division and `pow`), which loses fractional precision at every step of a two-stage calculation (`exchangeToSupply` then `exchangeFromSupply`), and the final truncating cast to `long` (`(long) issuedSupply`, `(long) exchangeBalance`) always rounds toward zero rather than to the mathematically correct value.

The project's own test suite proves the two implementations diverge on real inputs — `ExchangeProcessorTest.testStrictMath` asserts `Assert.assertNotEquals(anotherTokenQuant, result)` between the legacy double path and the hardened `BigDecimal` path (`SafeExchangeProcessor`) for numerous realistic balance/quant combinations, confirming the legacy path is measurably imprecise: [4](#0-3) 

The existence of a parallel `SafeExchangeProcessor` using `BigDecimal` with explicit scale/rounding, gated behind an `AllowHardenExchangeCalculation` chain parameter, is itself evidence that the java-tron team identified and is mitigating this exact precision-loss class in the exchange math, but the legacy imprecise path remains the default/fallback behavior for any network/state where that parameter isn't enabled: [5](#0-4) 

### Impact Explanation
Every trader executing an `ExchangeTransactionContract` (buy/sell against the on-chain TRC10 bancor pool) or withdrawing liquidity via `ExchangeWithdrawContract` on a network still running the legacy (non-hardened) path receives a token amount computed by lossy `double` math and truncated toward zero, so they systematically receive less of the target asset than the exact bancor-curve amount — directly analogous to "user will receive less amount" in the source report. Because the exchange pool balances are updated using this same imprecise value (`exchange.setBalance(...)`), the loss also silently perturbs the constant-product/bancor invariant of the pool itself over many trades, compounding the shortfall for subsequent users.

### Likelihood Explanation
Any account can submit `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions with no special privileges — this is a normal, permissionless user action, and the imprecision is deterministic and occurs on essentially every trade against non-trivial pool ratios (as shown by the test data), not an edge case.

### Recommendation
Make the `BigDecimal`/`SafeExchangeProcessor`-based hardened calculation the default (or the only) exchange pricing path instead of an opt-in flag, or increase intermediate precision (larger scale, `RoundingMode.HALF_UP` instead of truncating casts) in `ExchangeProcessor.exchangeToSupply`/`exchangeFromSupply` so results match the mathematically correct bancor formula within negligible tolerance, consistent with the mitigation recommended in the source report (raise precision rather than relying on low-precision integer/float division).

### Proof of Concept
Using the actual repository test vectors, the legacy double-based `ExchangeProcessor` and the `BigDecimal`-based `SafeExchangeProcessor` produce different outputs for the same pool state and trade size, e.g. for `sellBalance=4732214`, `buyBalance=2202692725330`, `sellQuant=29218` (and dozens of similar rows), `ExchangeProcessor` (non-strict) yields a value not equal to the "safe"/precise result: [6](#0-5) 

This demonstrates that any user calling `ExchangeTransactionActuator` through the legacy path receives an amount that deviates from the correct bancor-formula amount, reproducing the "user receives less than expected due to precision loss" bug class from the source report.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }
