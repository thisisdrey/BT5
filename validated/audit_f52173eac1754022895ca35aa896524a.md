### Title
Truncated integer exponent in `calc-liq-factor-exp` produces wrong graduated liquidation curve for any non-multiple-of-BPS `curve-exponent` - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`calc-liq-factor-exp` is Zest's analog of Balancer's fractional power functions (`bpow`/`bpowi`) referenced in the external report. Like the cited Balancer bugs, it discards fractional precision when computing a power, causing the graduated liquidation curve to silently degrade to the un-curved linear factor whenever the DAO-configured `curve-exponent` is not an exact multiple of `BPS` (10000).

### Finding Description
The liquidation curve exponent is applied here: [1](#0-0) 

```
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
```

`exp` is a BPS-scaled exponent (e.g. `15000` should mean `factor^1.5`). The integer exponent is obtained via `(/ exp BPS)`, which is integer (floor) division in Clarity — it truncates any fractional part instead of computing a proper fixed-point fractional power (the correct approach, analogous to Balancer's `bpow`, would split the exponent into whole and remainder parts and combine `factor^whole * factor^remain`). For any `exp` strictly between `BPS` and `2*BPS` (e.g. `15000` = 1.5x), `(/ exp BPS)` floors to `1`, so the function computes `factor^1 / BPS^0 = factor` — identical to the linear (`exp == BPS`) case, completely discarding the intended curvature. The same truncation occurs at every subsequent integer boundary (`2x`–`3x` collapses to `factor^2`, etc.).

This feeds directly into the liquidation pipeline used by every liquidation call: [2](#0-1) 

`calc-liquidation-params` uses the (wrongly truncated) `liq-pct-scaled` to compute `liq-penalty` (via `calc-liq-factor-bound`) and `max-debt-usd` (via `calc-liq-debt-repay`), which are then used in `process-collateral-asset` / `calc-final-liquidation-amounts` / `scale-debt-for-liquidation` to determine exactly how much collateral is seized from the borrower and how large the liquidator's bonus is. [3](#0-2) 

Since `factor < BPS` (it's a percentage ≤ 1.0) and the exponent is meant to be `>1` to graduate/soften the curve (`factor^1.5 < factor^1`), truncating the exponent down to `1` for any fractional value in `(1,2)` makes `liq-pct-scaled` larger than the DAO's configured curve intends. A larger `liq-pct-scaled` increases both the maximum liquidatable debt (`max-debt-usd`) and the liquidation penalty scaling (`calc-liq-factor-bound`), meaning more collateral is seized from the borrower and a larger bonus is paid to the liquidator than the configured curve should allow — with no special/malicious DAO action required, simply any legitimate non-integer-multiple `curve-exponent` setting (e.g. 1.5x, which is a very ordinary graduated-curve parameter choice).

### Impact Explanation
This causes borrowers to lose more collateral during partial liquidations than the DAO's configured liquidation curve intends, with the excess flowing to the liquidator as an unintended bonus. This is a value transfer that should not occur under the correctly-specified design — falling under theft of user funds during liquidation (temporary/permanent loss of the borrower's excess seized collateral beyond the intended curve). The severity scales with how far `curve-exponent` sits from an exact multiple of `BPS`, and is systemic (affects every liquidation call once such an exponent is configured), not a one-off edge case.

### Likelihood Explanation
No attacker action or DAO compromise is required — the bug triggers automatically for any liquidation whenever `curve-exponent` is configured to a value that is not an exact multiple of `10000` (a very plausible and common graduated-curve setting, e.g. 1.5x/12500, 1.25x). No validation was found constraining `curve-exponent` to multiples of `BPS`, so this is reachable through ordinary DAO parameterization plus ordinary liquidator calls — no unusual or malicious DAO update is needed, since exponents like `1.5x` are natural configuration choices, not misconfigurations.

### Recommendation
Rewrite `calc-liq-factor-exp` to correctly handle fractional fixed-point exponents, splitting the exponent into an integer part and a properly-computed fractional remainder (matching Balancer's corrected `bpow` approach: `factor^whole * factor^remainder`), instead of using floor-division to derive the exponent and thereby losing the fractional component entirely.

### Proof of Concept
1. DAO configures `curve-exponent = 15000` (intending `factor^1.5`) for an asset's liquidation config.
2. A borrower's LTV crosses into partial liquidation territory such that `calc-liq-factor` returns some `factor < BPS` (e.g. `8000` = 0.8).
3. `calc-liq-factor-exp(8000, 15000)` computes `(/ 15000 10000) = 1`, so it returns `(/ (pow 8000 1) (pow 10000 0)) = 8000` — identical to what a linear (`exp = BPS`) curve would produce, instead of the intended `8000^1.5`-scaled (smaller) value.
4. The inflated `liq-pct-scaled = 8000` is passed into `calc-liq-factor-bound` and `calc-liq-debt-repay`, producing a larger `max-debt-usd` and `liq-penalty` than the graduated curve should allow, so `process-collateral-asset`/`calc-final-liquidation-amounts` seize more of the borrower's collateral than the configured curve intends, benefiting the liquidator at the borrower's expense.

;; Combines the 4-step liquidation factor calculation into a single helper
;; Returns: { liq-pct-scaled: uint, liq-penalty: uint, max-debt-usd: uint }
(define-private (calc-liquidation-params
  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)
  (curve-exponent uint)
  (total-debt-usd uint))
  
  (let ((liq-pct-linear (calc-liq-factor current-ltv ltv-liq-partial ltv-liq-full))
        (liq-pct-scaled (calc-liq-factor-exp liq-pct-linear curve-exponent))
        (liq-penalty (calc-liq-factor-bound liq-pct-scaled liq-penalty-min liq-penalty-max))
        (max-debt-usd (calc-liq-debt-repay total-debt-usd liq-pct-scaled)))
    {
      liq-pct-scaled: liq-pct-scaled,
      liq-penalty: liq-penalty,
