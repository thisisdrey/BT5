## Title
Permanent, unauthorized blocking of TIP-2935 (EIP-2935) historical block-hash serving via pre-occupation of the canonical `HISTORY_STORAGE_ADDRESS` - (File: framework/src/main/java/org/tron/core/db/HistoryBlockHashUtil.java)

### Summary
`HistoryBlockHashUtil.deploy()` installs the TIP-2935 `BlockHashHistory` contract at a fixed, publicly known address (`HISTORY_STORAGE_ADDRESS = 0x410000f90827f1c53a10cb7a02335b175320002935`) only when the `ALLOW_TVM_PRAGUE` committee proposal is processed. If any code or contract metadata is already present at that exact address at the moment the proposal is processed, `deploy()` silently skips the entire installation and never sets the `BlockHashHistoryInstalled` marker — permanently disabling the feature for the life of the chain, since the proposal can only be processed once (analogous to the Nouns bug where a pre-existing reservation at a to-be-computed slot silently blocks a critical one-time state transition).

### Finding Description
`ProposalService.process()` calls `HistoryBlockHashUtil.deploy(manager)` exactly once, at the moment the `ALLOW_TVM_PRAGUE` parameter is set: [1](#0-0) 

`deploy()` guards against a "collision" by checking only `CodeStore` and `ContractStore` for the fixed address and returning early — without ever setting `saveBlockHashHistoryInstalled(1L)` — if either already has an entry there: [2](#0-1) 

The per-block write path (`write()`), which is the only mechanism that ever populates the historical block-hash storage, is gated exclusively on this installed marker: [3](#0-2) 

Because `HISTORY_STORAGE_ADDRESS` and its bytecode template are hardcoded and known ahead of any activation (mirroring the real Ethereum EIP-2935 address by design), any unprivileged account can pre-populate `ContractStore`/`CodeStore` at that same address before the committee’s `ALLOW_TVM_PRAGUE` proposal is executed — for example by triggering the CREATE2 path in `Program.createContractImpl()` with an appropriately crafted salt/init-code so the resulting address (`generateContractAddress2`) collides with `HISTORY_STORAGE_ADDRESS`. Once any code/contract entry exists there, `deploy()` unconditionally takes the early-return branch on every future call, since the proposal can be processed only once (the proposal validator prevents re-triggering the same feature-flag transition), and no other code path ever writes the `BlockHashHistoryInstalled` marker or retries deployment. This exactly mirrors the reported class of bug: a one-time, order-dependent initialization step that can be permanently defeated by a low-cost prior "reservation" of the destination slot/address, silently blocking a core protocol upgrade forever rather than reverting or retrying.

### Impact Explanation
This permanently and irrecoverably disables the TIP-2935/EIP-2935 historical block-hash feature network-wide once triggered — a core protocol capability that user/DeFi contracts written against EIP-2935 semantics would depend on for on-chain historical block hash access. Because the skip is silent (only a log warning) and the flag write is atomic with the skip, the chain continues to operate consistently across nodes (no consensus break), but the intended committee-approved upgrade is functionally neutralized network-wide, with no way to re-enable it short of a hard fork / code change. This matches the "blocking of core functionality" impact class from the source report (permanent denial of an intended one-time state transition triggered by unprivileged action).

### Likelihood Explanation
The address is fixed and known in advance (it is deliberately made to match the Ethereum EIP-2935 canonical address per the code's own documentation), so no privileged information is needed by an attacker. The only barrier is computing a CREATE2 salt/init-code pair whose resulting deterministic address collides with the fixed 21-byte value — the code’s own comments acknowledge this requires "a SHA-3 pre-image of the address," i.e., a hash-preimage-level computational cost, which is not practically feasible with current computational resources. This significantly limits real-world exploitability even though the logical flaw (silent, unrecoverable, one-shot skip with no retry/re-validate path) is real and reachable in principle from an ordinary contract-creation transaction.

### Recommendation
Do not treat "code or contract already present at the canonical address" as a fatal, unrecoverable skip. Options:
- Allow `deploy()` to be retried/rechecked separately from the one-time `ALLOW_TVM_PRAGUE` proposal-processing event (e.g., attempt installation on subsequent blocks until it succeeds, or expose a follow-up governance action specifically for retrying TIP-2935 activation).
- Alternatively, treat any non-empty state at the canonical address the same way the "existing account" branch is already handled (in-place upgrade) rather than a full skip, so that only genuinely conflicting bytecode blocks installation, and clearly document/alert this as an emergency condition requiring committee intervention rather than a silent permanent no-op.

### Proof of Concept
1. Before any committee member submits/approves the `ALLOW_TVM_PRAGUE` proposal, an attacker computes salt `s` and init-code `c` such that `WalletUtil.generateContractAddress2(callerAddress, s, c)` equals `HISTORY_STORAGE_ADDRESS` (`0x410000f90827f1c53a10cb7a02335b175320002935`) — acknowledged by the code itself to require a SHA-3 preimage, i.e., currently computationally infeasible, but logically the only gate.
2. Attacker deploys via `CREATE2` (`Program.createContract2`/`createContractImpl`) placing code/contract metadata at that address, as verified in existing tests such as: [4](#0-3) 
3. When the committee later processes the `ALLOW_TVM_PRAGUE` proposal, `HistoryBlockHashUtil.deploy()` detects the pre-existing `CodeStore`/`ContractStore` entry and returns immediately without setting `BlockHashHistoryInstalled`: [2](#0-1) 
4. Every subsequent block's `write()` call is a no-op because `isBlockHashHistoryInstalled()` is false forever, and since the proposal transition happens only once, this state is permanent.

**Note on limitation:** the practical exploitability of this finding hinges entirely on the CREATE2 preimage cost, which the code's own authors already flag as effectively infeasible ("belt-and-braces"); I could not find any additional path (e.g., a shorter/weaker collision vector, or an ability to re-trigger `deploy()` outside the one-time proposal transition) within the indexed code to make this more directly reachable. This should be treated as a low-likelihood, logic-level design flaw rather than a demonstrated practical exploit.

  public static void write(Manager manager, BlockCapsule block) {
    // Genesis has no parent; applyBlock never invokes this for block 0, but be
    // explicit so (0-1) % 8191 = -1 in Java can never corrupt a slot.
    if (block.getNum() <= 0) {
      return;
    }
    // Defense-in-depth: deploy() skips on foreign state at the canonical
    // address, but the proposal flag still commits. Gate on the install
    // marker (set at the tail of a successful deploy()) so write() can never
    // overwrite an unrelated contract's storage. Single store hit, cached.
    if (!manager.getDynamicPropertiesStore().isBlockHashHistoryInstalled()) {
      return;
    }
