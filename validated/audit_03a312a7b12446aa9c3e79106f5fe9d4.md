### Title
Protocol fee bypass on Nep245/Imt token trades via per-intent `amount<=1` splitting - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` waives the fee (`Pips::ZERO`) for `Nep245`/`Imt` token types whenever the `amount` passed to it is `<= 1`. This `amount` is computed per-`TokenDiff`-intent (`delta.unsigned_abs()` on that single intent's diff), not aggregated across the whole `MultiPayload`/batch. An attacker can therefore split what should be a single fee-bearing trade of `N` units (`N > 1`) of a Nep245/Imt token into `N` separate signed `TokenDiff` intents, each moving exactly `1` unit, and have every one of them independently qualify for the `amount<=1` exemption — fully evading the protocol fee that a single `delta = -N` intent would have paid.

### Finding Description
The binding that should hold is:
`fees_actually_collected(token_id, N) == Pips::fee_ceil(protocol_fee, N)` for the true aggregate amount `N` of a Nep245/Imt token moved by a signer for a given trade, whenever `N > 1`.

In `TokenDiff::execute_intent` (`contracts/defuse/core/src/intents/token_diff.rs:59-79`), the fee is computed strictly per intent:
```
let amount = delta.unsigned_abs();
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
```
and `token_fee` (`token_diff.rs:206-216`) returns `Pips::ZERO` whenever `TokenIdType::Nep245 | TokenIdType::Imt` and `amount <= 1`:
```
TokenIdType::Nep245 | TokenIdType::Imt if amount > 1 => {}
TokenIdType::Nep171 | TokenIdType::Nep245 | TokenIdType::Imt => return Pips::ZERO,
```
Nothing in `Engine::execute_signed_intents` / `execute_signed_intent` (`contracts/defuse/core/src/engine/mod.rs:32-83`) or in `DefuseIntents::execute_intent` (`contracts/defuse/core/src/intents/mod.rs:97-113`) aggregates the `amount` moved for a given `token_id` across multiple `TokenDiff` intents (or multiple `MultiPayload`s) in the same batch before calling `token_fee`. Each `Intent::TokenDiff(...)` is dispatched to `TokenDiff::execute_intent` independently, and `token_fee` sees only that single intent's `delta`.

Exploit: an attacker (as taker) and a counterparty (solver, possibly also attacker-controlled) sign `N` separate `TokenDiff` intents instead of one, each with `delta = -1` / `delta = +1` on the same `Nep245TokenId` (or `ImtTokenId`), matched by corresponding opposite-side amounts on another token. Each intent independently has `amount = 1`, so `token_fee` returns `Pips::ZERO` for all `N` of them; the true aggregate amount moved is `N`, but `fees_collected` sums to `0` instead of `Pips::fee_ceil(protocol_fee, N)`.

The `Nep245`/`Imt` types are not restricted to NFT-like indivisible items — `Nep245TokenId`/`ImtTokenId` (`crates/primitives/token-id/src/nep245.rs`, `crates/primitives/token-id/src/imt.rs`) represent arbitrary multi-token quantities, so this exemption (intended to avoid taking a whole-unit fee off a single NFT) is reachable for fungible-scale trades simply by decomposing the trade into unit-sized legs. None of the listed guards (`verify`, `has_public_key`, `verify_intent_nonce`, `commit_nonce`, `is_valid_salt`, `Lock`, `TransferMatcher::finalize`, `assert_one_yocto`, `#[pause]`) check or restrict the per-token aggregate amount for fee purposes; they only ensure signature/nonce validity and that per-batch balance deltas net to a valid state — they do not recompute fees on the netted amount.

Note: the closure-math machinery (`closure_delta`/`closure_supply_delta`/`checked_mul_div_euclid`) referenced in the question is purely an off-chain helper for solvers to compute quote amounts; it is never invoked by the on-chain enforcement path (`execute_intent`), so any "divergence" there is a client-side quoting concern, not an on-chain authorization bug. The actual on-chain, exploitable defect is the per-intent (not per-aggregate) fee evaluation described above.

### Impact Explanation
This is a protocol-fee-bypass finding (matches the explicitly listed Critical category "protocol fees bypassed or over-collected"). Any pair of accounts trading Nep245/Imt-denominated value can avoid the protocol fee entirely on that leg of the trade by structuring it as many unit-sized `TokenDiff` intents rather than one intent with the true aggregate delta. This under-collects fees owed to `fee_collector`, repeatable for every trade of this token type and by any unprivileged account pair, with no protocol-level check ever recovering the lost fee. It does not, however, allow moving value without the owner's signature, double-settlement, or Verifier insolvency — each intent's delta is honestly and separately signed and settled; the only casualty is fee revenue.

### Likelihood Explanation
No privileged role is required — this only needs an attacker (or attacker plus a cooperating/attacker-controlled counterparty) able to sign `N` ordinary `TokenDiff` intents with distinct nonces in one or more `MultiPayload`s submitted to `execute_intents`. Feasibility is bounded by gas: since each `execute_intents` call has to process `N` intents (each doing balance updates, event emission, etc.), practical `N` per transaction is limited by NEAR's gas budget, but this only reduces the maximum evaded amount per call — it does not prevent the bypass, and multiple calls can be chained to scale it further. Given the code comment ("do not take fees on NFTs and MTs with `|delta| <= 1`") shows the exemption is deliberate but was evidently not designed with per-batch aggregation of many unit legs in mind for divisible Nep245/Imt balances.

### Recommendation
Compute `token_fee` based on the aggregate signed amount per `token_id` across the entire batch (all `TokenDiff` intents and, if applicable, across combined `MultiPayload`s in one `execute_intents` call) rather than per individual `TokenDiff` intent, before applying the `amount <= 1` Nep171/Nep245/Imt exemption. Alternatively, restrict the `amount <= 1` fee exemption to `TokenIdType::Nep171` only (true indivisible NFTs, always `amount == 1` by construction) and always apply the fee schedule to `Nep245`/`Imt` regardless of per-intent amount, or aggregate `amount` at the account+token+batch level before calling `token_fee`.

### Proof of Concept

```rust
// tests/src/tests/defuse/intents/token_diff.rs (new test)
#[rstest]
#[tokio::test]
async fn fee_bypass_via_unit_splitting(#[with(Env::builder().fee(Pips::ONE_PERCENT))] #[future(awt)] env: Env) {
    // Setup: attacker + solver, a Nep245TokenId `mt` with fungible-scale quantity,
    // and a second Nep141 token `ft` to be the matched counter-leg.
    // ... deposit attacker: 2 units of `mt`; solver: enough `ft`.

    // Reference: single-intent trade of amount=2, would incur fee = Pips::ONE_PERCENT.fee_ceil(2)
    let expected_fee = Pips::ONE_PERCENT.fee_ceil(2);
    assert!(expected_fee > 0);

    // Exploit: split into two TokenDiff intents, each delta = -1 / +1 on `mt`,
    // matched with two counter TokenDiff intents on `ft` from the solver.
    let attacker_intent_1 = TokenDiff { diff: TokenDeltas::default()
        .with_apply_deltas([(mt_token_id.clone(), -1), (ft_token_id.clone(), out_1)]).unwrap(), memo: None, referral: None };
    let attacker_intent_2 = TokenDiff { diff: TokenDeltas::default()
        .with_apply_deltas([(mt_token_id.clone(), -1), (ft_token_id.clone(), out_2)]).unwrap(), memo: None, referral: None };
    // solver_intent_1, solver_intent_2 mirror these (mt: +1, ft: -out_i) each.

    let signed = [/* sign attacker_intent_1, solver_intent_1, attacker_intent_2, solver_intent_2 */];

    env.defuse_execute_intents(env.defuse.contract_id(), signed).await.unwrap();

    // Assert divergence: total fee actually collected on `mt` across the batch is 0,
    // not Pips::fee_ceil(protocol_fee, 2) as a single delta=-2 intent would have paid.
    let fees_collected_on_mt = /* sum from emitted TokenDiffEvent::fees_collected for mt_token_id across both intents */;
    assert_eq!(fees_collected_on_mt, 0);
    assert_ne!(fees_collected_on_mt, expected_fee); // demonstrates the bypass
}
```
This directly matches the PoC idea in the question (two chained `TokenDiff` intents on the same `Nep245TokenId`, each `|delta| == 1`, executed in one `execute_intents` call), asserting `fees_collected == 0` versus the expected `Pips::fee_ceil(protocol_fee, 2)`.
