Audit Report

## Title
Unsafe reliance on ERC20 boolean return value in `ERC20Transactor` allows accounting desync between XCM holding credits and real checking-account balance - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` move value into/out of a shared `TransfersCheckingAccount` by calling the target contract's `IERC20.transfer()` and trusting only its boolean return value, without ever verifying the actual balance delta on the checking account. Because `ERC20Matcher` (backed by `IsLocalAccountKey20` / `AccountKey20ToH160`) permissionlessly treats any `(0, [AccountKey20 { key, .. }])` location as a valid asset id pointing to an arbitrary user-deployed `pallet-revive` contract, any unprivileged user can register a fee-on-transfer or non-conforming ERC20-like contract as an XCM asset and cause the nominal amount credited into `AssetsInHolding` to diverge from the real token balance actually held by the shared checking account.

## Finding Description
`withdraw_asset_with_surplus` calls `transfer(checking_account, amount)` via `pallet_revive::Pallet::<T>::bare_call` and, upon a `true` boolean return, unconditionally constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the full nominal `amount` regardless of what was actually transferred. [1](#0-0) 

`deposit_asset_with_surplus` mirrors this: it transfers `amount` from the checking account to the beneficiary and treats `Ok(true)` from `abi_decode_returns_validate` as full success, without measuring any real balance change. [2](#0-1) 

The `Erc20Credit` imbalance type is explicitly documented as *not* performing runtime-level balance enforcement, deferring all real balance constraints to the ERC20 contract itself. [3](#0-2) 

The asset id matcher backing this transactor accepts any `H160` embedded in an `AccountKey20` junction unconditionally — no registry or allow-list gates which contracts can be treated as assets. [4](#0-3) 

Existing guards (`did_revert()` check and `abi_decode_returns_validate` of the boolean) only reject hard failures (revert / undecodable return); they do not detect "soft" non-conformance where `transfer()` returns `true` but moves a different amount than requested (fee-on-transfer, rebasing, or deliberately falsified return values). The repository's own test `smart_contract_does_not_return_bool_fails` demonstrates that arbitrary, unregistered contracts are dispatched through this exact code path.

## Impact Explanation
Because `TransfersCheckingAccount` is a single shared account for a given asset id across all XCM operations referencing that asset, a systemic mismatch between nominal `Erc20Credit` amounts recorded in `AssetsInHolding` and the checking account's real on-chain token balance constitutes an unbacked-accounting condition. This can cause legitimate subsequent `deposit_asset_with_surplus` calls for that asset id to fail once the real balance is exhausted (locking XCM-trapped assets), or, if a malicious contract is crafted to always return `true` regardless of actual balance movement, allow extraction of more real value than was ever deposited. This matches the "theft or unbacked mint/unlock" and "permanent user-fund or bridge-state lock" impact categories in scope.

## Likelihood Explanation
High. No privileged action is required: deploying an arbitrary `pallet-revive` contract and driving `PolkadotXcm::execute`/`transfer_assets` referencing that contract's address as an `AccountKey20` location is fully permissionless, the matcher `IsLocalAccountKey20`/`AccountKey20ToH160` accepts any such address unconditionally, and the transactor's sole success criterion is the boolean return of `transfer()` rather than a verified balance delta.

## Recommendation
Query the checking account's (and beneficiary's) real ERC20 balance via `balanceOf()` before and after the `transfer()` call within `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, and use the measured delta — not the requested `amount` — to construct/consume the `Erc20Credit` imbalance in `AssetsInHolding`. Reject or explicitly account for any mismatch between the requested and actually-moved amounts, mirroring a `SafeERC20`-style verified-transfer pattern.

## Proof of Concept
1. Deploy on `pallet-revive` a contract implementing `IERC20` where `transfer(to, value)` always returns `true` but internally moves `value - fee` (or `0`) to `to`.
2. Reference this contract as an XCM asset via `Location::new(0, [AccountKey20 { key: <contract_address>, network: None }])` — no registration required, as confirmed by `ERC20Matcher`'s unconditional matching in `cumulus/parachains/runtimes/assets/common/src/lib.rs`.
3. Submit an XCM program via `PolkadotXcm::execute` that `WithdrawAsset`s this asset from the caller, invoking `ERC20Transactor::withdraw_asset_with_surplus`, which credits the full nominal `amount` to holding based only on the `true` return while the checking account's real balance increases by less than `amount`.
4. Repeat across multiple XCM operations against the same asset id until the checking account's real balance is less than the sum of nominal amounts recorded as available; a subsequent legitimate `deposit_asset_with_surplus` for that asset id then fails (fund lock) or, for a contract that always reports success irrespective of actual movement, permits withdrawal exceeding real backing.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
