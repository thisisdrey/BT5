This is a solid match. The MongoDB bug is about a setParameter command whose value (a password) leaks into debug/verbose logs. The closest Go analog is in `cmd/go`'s GOAUTH implementation: when a `git credential fill` invocation fails, its `CombinedOutput` (which contains the plaintext `password=...` field per the git-credential protocol) is wrapped into an error and, under the `-x` (verbose) build flag, printed to stderr via `log.Printf`.### Title
GOAUTH `git dir` credential errors leak plaintext passwords to stderr via `-x` logging - ([File: src/cmd/go/internal/auth/gitauth.go])

### Summary
When `go` is configured with `GOAUTH=git dir` and the module-fetch build flag `-x` is set, a failing `git credential fill` invocation causes the raw `CombinedOutput()` of that command — which follows the git-credential wire format and contains a plaintext `password=<secret>` line — to be embedded verbatim into an `error`. That error is subsequently written to the process log/stderr with `log.Printf`, disclosing the credential in plain text in build/debug output. This mirrors the MongoDB `ldapQueryPassword` bug class: a sensitive runtime/config value is written unredacted into diagnostic logging instead of being masked, as is done elsewhere in the same package (e.g. `url.Redacted()`).

### Finding Description
The victim workflow: a developer runs `go get`/`go mod tidy`/`go build ...` with `-x` (verbose command logging) while `GOAUTH` includes a `git dir` method, fetching a private module over HTTPS.

- Entry point: `runGoAuth` in `src/cmd/go/internal/auth/auth.go:53-140`, case `"git"` (lines 87-115), calls `runGitAuth(client, dir, url)`.
- `runGitAuth` in `src/cmd/go/internal/auth/gitauth.go:33-78` executes `git credential fill` and reads its output with `cmd.CombinedOutput()` (line 48). This output is the git-credential protocol response, which by design contains `username=...` and `password=...` lines in plaintext.
- If `git credential fill` exits with an error, line 50 builds:
  `fmt.Errorf("'git credential fill' failed (url=%s): %w\n%s", url, err, out)`
  — `out` (the raw combined stdout/stderr, including the `password=` line if the helper partially emitted it before failing, or if a misbehaving/verbose helper writes diagnostics to stderr that echo the query) is folded directly into the error string with no redaction.
- Back in `auth.go`, this error is appended to `cmdErrs` (line 112). If no cached credential exists for the URL and `cfg.BuildX` (the `-x` flag) is true, `auth.go:131-138` executes:
  ```go
  log.Printf("GOAUTH encountered errors for %s:", url)
  for _, err := range cmdErrs {
      log.Printf("  %v", err)
  }
  ```
  This prints the full error — including any embedded plaintext password — to the standard `log` package output (stderr).
- Contrast with the rest of the same file/package, which is careful to redact secrets: `url.Redacted()` is used throughout `modfetch/proxy.go` and `web/http.go` specifically to avoid leaking userinfo/passwords in `-x` output. `gitauth.go`'s error path is the one place that bypasses that discipline by echoing raw command output.

### Impact Explanation
Concrete impact: disclosure of a private-repository credential (git username/password or PAT) into command-line/log output that is frequently captured by CI systems, redirected to log files, or pasted into bug reports — the exact same "secret written to a log in plain text" primitive as the MongoDB CVE. This is a secret-disclosure issue. Under Go's security triage this would sit on the **PRIVATE/URGENT-track-eligible but likely PUBLIC-track** boundary: it requires the developer to opt into `-x` verbose logging and a specific `GOAUTH=git ...` configuration, and requires the git credential helper to actually fail while still emitting the password field (or attacker-influenced stderr) — a real but narrow condition, not universally reachable by an unauthenticated remote attacker.

### Likelihood Explanation
Requires: (1) `GOAUTH` configured to use the `git dir` method (not default `netrc`), (2) the developer running `go get`/`go mod tidy` with `-x`, and (3) `git credential fill` failing in a way that still emits `password=` before erroring (e.g., a credential helper that prints diagnostic info to stderr, which `CombinedOutput` captures). This is a real, unprivileged victim workflow (ordinary developer fetching a private module), but the exact failure/emission behavior is helper-dependent, so likelihood is moderate rather than high.

### Recommendation
In `gitauth.go`, redact the `password=` field (and any userinfo) from `out` before embedding it in the returned error at `runGitAuth` line 50, e.g. strip/replace `password=...` lines, or only include a summary (`err`, exit code) rather than raw `CombinedOutput`. Additionally, in `auth.go`'s error-logging loop (lines 131-138), sanitize error strings before passing them to `log.Printf`.
