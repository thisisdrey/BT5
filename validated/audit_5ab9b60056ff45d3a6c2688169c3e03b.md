### Title
Unconditional insurance-fee/group-fee/program-fee transfers can permanently DoS `LendingPoolCollectBankFees` and legacy liquidation for Token-2022 mints with a transfer hook that rejects zero-amount transfers - (File: `programs/marginfi/src/instructions/marginfi_group/collect_bank_fees.rs`, `programs/marginfi/src/instructions/marginfi_account/liquidate.rs`)

### Summary
The reported Aave-Lens issue is that fee-collection code paths unconditionally attempt an ERC20 `transfer`/`transferFrom` for a treasury fee amount, and some ERC20 tokens revert on zero-value transfers, so a zero treasury fee bricks collection. marginfi's SPL Token analog is `lending_pool_collect_bank_fees`, which unconditionally issues three separate `withdraw_spl_transfer` calls (insurance fee, group fee, program fee) regardless of whether each individual amount is zero, and the legacy liquidation path (`lending_account_liquidate`) unconditionally transfers `insurance_fee_to_transfer` to the insurance vault. Standard SPL Token/Token-2022 transfers do not revert on a zero amount, but marginfi explicitly supports Token-2022 mints with an active **transfer hook** extension as bank mints (tested in `marginfi_account_liquidation_success_with_extension`), and a transfer hook program is arbitrary logic that can legitimately reject a zero-amount transfer, exactly mirroring the "revert on zero-value transfer" weird-token behavior from the original report.

### Finding Description
`lending_pool_collect_bank_fees` computes three transfer amounts from `bank.collected_insurance_fees_outstanding`, `bank.collected_group_fees_outstanding`, and `bank.collected_program_fees_outstanding`, and calls `bank.withdraw_spl_transfer(...)` for each amount without any `if amount > 0` guard: [1](#0-0) 

`withdraw_spl_transfer` invokes `spl_token_2022::onchain::invoke_transfer_checked` (or `transfer_checked` client-side) for Token-2022 mints, passing through any `remaining_accounts` needed for a transfer-hook CPI, unconditionally on the given `amount`: [2](#0-1) 

marginfi treats mints with an active `TransferHook` extension as a fully supported bank-mint configuration for the standard lending flow (deposit/borrow/liquidation), as shown by the test matrix that explicitly exercises `SupportedExtension::TransferHook`: [3](#0-2) 

The presence of `has_transfer_hook` is only checked and rejected in the `lending_pool_emissions_deposit` path, not in `collect_bank_fees`, `withdraw_fees`, `withdraw_insurance`, or liquidation: [4](#0-3) [5](#0-4) 

Because a transfer-hook program is arbitrary CPI-invoked logic (analogous to a custom ERC20 `transfer` override), it can be implemented to reject zero-amount transfers (this is a well-known Token-2022 hook design choice, directly parallel to "weird ERC20 tokens that revert on zero-value transfers" cited in the original report). Since `collected_insurance_fees_outstanding`, `collected_group_fees_outstanding`, and `collected_program_fees_outstanding` are independently accrued and frequently land at exactly zero for a given fee category (e.g., a bank configured with insurance IR/fixed rate of zero, or one with no group fee configured, or freshly-collected fee categories reset to zero on the previous run), any single zero value among the three unconditional transfers will cause the whole `LendingPoolCollectBankFees` transaction to revert if the mint's hook rejects zero-value transfers — this blocks collection of the *other two, legitimately non-zero* fee categories as well, since all three transfers occur in one atomic instruction.

The same unconditional-transfer pattern exists in `lending_account_liquidate`, which transfers `insurance_fee_to_transfer` to the insurance vault unconditionally: [6](#0-5) 
If the legacy liquidation fee (2.5% to insurance) rounds down to zero for a small liquidation on such a hook-enabled bank, liquidation itself could be blocked, which is a stronger, higher-severity manifestation of this bug class (it directly threatens solvency by disabling liquidation rather than merely fee sweeping).

### Impact Explanation
If a bank is created with a Token-2022 mint carrying a transfer hook that rejects zero-amount transfers, then:
- `LendingPoolCollectBankFees` becomes permanently unusable for that bank whenever any one of the three fee categories is exactly zero — a common, easily-reachable state (any bank with a zero-configured fee rate, or freshly zeroed categories after a partial collection due to insufficient `available_liquidity`). This is a permanent freeze/lock of fee-collection functionality (`collected_*_fees_outstanding` accumulate indefinitely and can never be swept to the vaults), impacting protocol/group/insurance revenue accounting for that bank.
- In the liquidation path, if the computed insurance fee for a given liquidation rounds to zero, `lending_account_liquidate` would revert entirely for that bank/mint, blocking the ability to liquidate unhealthy positions — this is a more severe, insolvency-adjacent lock, since a permanently un-liquidatable bank can accrue bad debt if borrowers become undercollateralized and no liquidator can act.

### Likelihood Explanation
Likelihood is contingent on: (1) a group admin creating a bank on a Token-2022 mint with an active transfer hook (a configuration marginfi explicitly supports and tests for standard lending operations), and (2) that hook program specifically rejecting zero-amount transfers (a plausible, documented design pattern for hook programs enforcing minimum-transfer or non-trivial-transfer policies, similar to some ERC20 implementations). This requires a specific but realistic mint/hook combination; it is not exploitable on vanilla SPL-Token or "well-behaved" Token-2022 mints (which is likely why the codebase's existing test suite for zero-value flows, e.g. `d08_driftWithdraw.spec.ts`'s "Tries to withdraw 0 tokens - should succeed with no transfer" test, never surfaces this, since the drift withdraw path short-circuits before transferring when amount is zero, unlike `collect_bank_fees`/`liquidate`). Given marginfi's stated support for arbitrary Token-2022 extensions on bank mints (only excluding hooks from the emissions-deposit path specifically), this is a reachable, unprivileged-triggerable condition once such a bank exists.

### Recommendation
Guard each unconditional transfer in `lending_pool_collect_bank_fees` (insurance, group, program fee legs) and in `lending_account_liquidate`'s insurance-fee transfer with an `if amount > 0` check before invoking `withdraw_spl_transfer`, mirroring the pattern already used elsewhere in the codebase (e.g., `lending_pool_emissions_deposit`'s `if amount == 0 { return Ok(()); }` and `kamino_harvest_reward`'s zero-amount short-circuit). This ensures a zero fee/amount for any single category never blocks collection of other non-zero fees or blocks liquidation entirely.

### Proof of Concept
1. Group admin creates a bank (`lending_pool_add_bank`) with a Token-2022 mint that has an active `TransferHook` extension pointing to a hook program that reverts when the CPI `amount` parameter is `0` (a straightforward hook implementation, e.g. rejecting `require(amount > 0)` inside `execute`).
2. Configure the bank such that one of the three collected fee categories is guaranteed to be zero at collection time — e.g., set `insurance_ir_fee`/`insurance_fee_fixed_apr` to zero (or simply collect right after a prior `LendingPoolCollectBankFees` call that already zeroed that category) while group/program fees are non-zero due to normal interest accrual (see `LendingPoolCollectBankFees` accounting): [7](#0-6) 
3. Call `lending_pool_collect_bank_fees` (permissionless per `guides/ADMIN/COLLECTING_FEES.md`): [8](#0-7) 
4. The `bank.withdraw_spl_transfer(insurance_fee_transfer_amount, ...)` call with `insurance_fee_transfer_amount == 0` triggers the Token-2022 transfer-hook CPI with `amount = 0`, which the hook program rejects, causing the entire instruction — including the legitimate non-zero group/program fee transfers — to fail.
5. Because this ix is the only path that moves `collected_*_fees_outstanding` out of the bank's liquidity vault, fee collection for this bank is permanently blocked as long as any category remains at zero, which will recur every time fees are collected shortly after a previous full sweep.

    #[allow(unused_variables)]
    fn withdraw_spl_transfer<'info>(
        &self,
        amount: u64,
        from: AccountInfo<'info>,
        to: AccountInfo<'info>,
        authority: AccountInfo<'info>,
        maybe_mint: Option<&InterfaceAccount<'info, Mint>>,
        program: AccountInfo<'info>,
        signer_seeds: &[&[&[u8]]],
        remaining_accounts: &[AccountInfo<'info>],
    ) -> MarginfiResult {
        debug!(
            "withdraw_spl_transfer: amount: {} from {} to {}, auth {}",
            amount, from.key, to.key, authority.key
        );

        #[cfg(feature = "client")]
        if let Some(mint) = maybe_mint {
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                Some(mint.to_account_info()),
                to,
                authority,
                Some(mint.decimals),
                remaining_accounts,
                signer_seeds,
            )?;
        } else {
            // `transfer_checked` and `transfer` does the same thing, the additional `_checked` logic
            // is only to assert the expected attributes by the user (mint, decimal scaling),
            //
            // Security of `transfer` is equal to `transfer_checked`.
            invoke_client_token_transfer(
                program.key,
                amount,
                from,
                None,
                to,
                authority,
                None,
                remaining_accounts,
                signer_seeds,
            )?;
        }

        #[cfg(not(feature = "client"))]
        if let Some(mint) = maybe_mint {
            spl_token_2022::onchain::invoke_transfer_checked(
                program.key,
                from,
                mint.to_account_info(),
                to,
                authority,
                remaining_accounts,
                amount,
                mint.decimals,
                signer_seeds,
            )?;

/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
