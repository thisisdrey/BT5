### Title
Non-constant-time authorization token comparison enables remote timing side-channel brute-force of `auth_token`, leading to auth bypass on `/v3/blocks/upload/?broadcast=1` - (File: stackslib/src/net/api/postblock_v3.rs)

### Summary
`RPCPostBlockRequestHandler::try_parse_request` compares the caller-supplied `Authorization` header against the configured `auth_token` using the plain `!=` operator on `String`/`&str`, which is not constant-time and short-circuits on the first mismatching byte. A remote, unauthenticated attacker who can hit the RPC port can use response-latency measurements to recover the secret byte-by-byte, then use it to authenticate broadcast-writes of attacker-crafted `NakamotoBlock`s.

### Finding Description
In `try_parse_request`, the auth check is:

```rust
if let Some(password) = &self.auth {
    if let Some(auth_header) = preamble.headers.get("authorization") {
        if auth_header != password {
            return Err(Error::Http(401, "Unauthorized".into()));
        }
        authenticated = true;
    }
}
``` [1](#0-0) 

`auth_header != password` relies on the standard library's `str`/`String` `PartialEq`, which compares byte-by-byte and returns as soon as a mismatch is found (after first checking length). This means the time taken by the comparison is correlated with the number of leading bytes that match the true secret: a guess sharing a longer correct prefix takes measurably longer to reject than one that diverges early. An attacker with network access to the RPC port can repeatedly POST to `/v3/blocks/upload/?broadcast=1` with different `Authorization` header guesses and use statistical timing analysis to recover the secret one byte at a time, eventually reconstructing the full `auth_token`.

Once the attacker holds a valid guess for `auth_token`, `authenticated` becomes `true`, and combined with `broadcast=1` in the query string, the handler proceeds to `parse_postblock_octets` and ultimately `try_handle_request`, which calls `Relayer::process_new_nakamoto_block_ext` with `NakamotoBlockObtainMethod::Uploaded` and the attacker-supplied broadcast flag [2](#0-1) . If accepted, the node marks the block for relay via `node.set_relay_message(StacksMessageType::NakamotoBlocks(...))`, propagating the attacker's block to the wider network [3](#0-2) .

No constant-time comparison primitive (e.g. `subtle::ConstantTimeEq` or manual XOR-accumulate compare) is used anywhere in this handler, and no rate-limiting or generic timing-noise mitigation is present in this code path to blunt a timing side channel.

### Impact Explanation
Recovering `auth_token` grants the attacker the ability to bypass the authorization gate on `/v3/blocks/upload/?broadcast=1`, letting them submit arbitrary, non-consensus-valid `NakamotoBlock` payloads that the node will attempt to broadcast/relay to its peers, i.e., unauthenticated write plus network-wide propagation of attacker-controlled data—matching the "Critical: unauthenticated/unauthorized write... network-wide propagation of forged data ... auth bypass" category. This is repeatable: once the secret is recovered it can be reused indefinitely until the operator rotates it.

### Likelihood Explanation
Preconditions: the node operator must have configured `auth_token` (otherwise this branch is entirely skipped, since `self.auth` is `None`) [1](#0-0) , and the attacker needs unauthenticated network access to the RPC port, which is the standard threat model here. The attack requires many timed requests per secret byte to overcome network jitter—costly but not blocked by any guard in this code; there's no rate limiting, exponential backoff, or constant-time comparison in this handler. This mirrors a classic textbook timing side-channel on secret comparisons.

### Recommendation
Replace the `!=` string comparison with a constant-time comparison, e.g. using the `subtle` crate's `ConstantTimeEq`, or a manual comparison that XORs all bytes of equal-length inputs and accumulates without branching on intermediate results, ensuring the byte length check itself doesn't leak information disproportionately either (compare using a fixed-time algorithm that also normalizes for length, e.g. HMAC over both values with a random node-local key and compare the HMACs in constant time).

### Proof of Concept
Rust test plan in `stackslib::net::api::tests::postblock_v3`:
1. Configure `RPCPostBlockRequestHandler::new(Some(secret.clone()))` with a known secret string of fixed length (e.g. 32 chars).
2. Construct two guess strings of the same length: (a) one sharing a long correct prefix with `secret` but differing in the last byte, (b) one differing in the first byte.
3. Call `try_parse_request` directly (bypassing the full HTTP/TCP stack) in a tight loop (thousands of iterations) for each guess, using `std::time::Instant` to measure the wall-clock duration of just the `auth_header != password` branch (isolate by wrapping only that comparison, or measure the whole call while holding all other inputs constant/valid).
4. Assert that the mean/median time for guess (a) (long matching prefix) is statistically distinguishable (e.g., >2 standard deviations) from guess (b) (short matching prefix), demonstrating the branch's execution time correlates with prefix-match length — confirming the non-constant-time equality at `postblock_v3.rs:106`.
