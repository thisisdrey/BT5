### Title
Outbound message reward/fee permanently locked if Ethereum Gateway is redeployed - ([File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs])

### Summary
`pallet_outbound_queue_v2::process_delivery_receipt` gates the release of a previously‑committed relayer fee behind a strict equality check against a compile‑time/runtime‑constant `T::GatewayAddress`. This is the direct structural analog of the Stargate router‑address `require`: a hard‑coded counterparty address that, if the real contract is ever redeployed (upgrade, migration, incident recovery on the Ethereum side), causes the guarded state‑release call to permanently fail, leaving already‑reserved funds/state (`PendingOrders`) stuck forever with no alternate recovery path.

### Finding Description
When BridgeHub sends a message to Ethereum, `do_process_message` [1](#0-0)  creates a `PendingOrder` keyed by `nonce`, carrying the `fee` that is meant to reward the relayer that later proves delivery on Ethereum: [2](#0-1) .

The only way to resolve/settle that `PendingOrder` (pay the relayer and remove the entry from storage) is `submit_delivery_receipt` → `process_delivery_receipt`, which requires:

```
ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);
``` [3](#0-2) 

`T::GatewayAddress` is declared `#[pallet::constant]` — i.e. a fixed value baked into the runtime configuration [4](#0-3) , exactly analogous to the immutable Stargate router address checked by the vulnerable `require` in the external report. `receipt.gateway` is derived from the actual Ethereum log address that emitted the delivery event, verified independently by `T::Verifier` — it reflects reality on Ethereum, not the Substrate runtime's assumption.

If the Gateway contract on Ethereum is ever redeployed at a new address (upgrade, incident response, migration — a scenario the original Stargate report explicitly calls "difficult to estimate the likelihood of, but a risk that remains"), every legitimate delivery receipt from the new Gateway will carry a `receipt.gateway` that no longer equals the stale `T::GatewayAddress` constant. `submit_delivery_receipt` will then revert with `InvalidGateway` unconditionally and permanently (short of a full runtime upgrade to update the constant).

Unlike `inbound-queue-v2::process_message`, where the equivalent gateway check [5](#0-4)  gates entry into the pipeline *before* any state is committed (fail-closed, no side effects), here the state (`PendingOrders<T>`) was already committed by `do_process_message` at the time the message was sent — well before the receipt is later submitted. The `fee` recorded in that order is understood by the pallet's own documentation to represent value "attached in the message" that is only released "after" a valid receipt is accepted: [6](#0-5) . There is no other extrinsic, timeout, or governance call in this pallet that removes or refunds a `PendingOrders` entry — `process_delivery_receipt` is the sole path via `<PendingOrders<T>>::remove(nonce)` [7](#0-6) .

### Impact Explanation
Once the on-chain `GatewayAddress` constant diverges from the real, redeployed Ethereum Gateway contract, every outstanding and every future `PendingOrder` fee becomes permanently unclaimable: relayers can never satisfy the `InvalidGateway` check, so the reward is never paid and the `PendingOrders` entry is never cleared. This is a "permanent user/bridge-state fund lock" per the impact taxonomy — value that was earmarked for payout is stranded in pallet storage indefinitely, requiring an emergency runtime upgrade to fix, during which any relayer who already performed off-chain delivery work is unpaid and bridge processing state accumulates unresolved orders.

### Likelihood Explanation
This does not require any malicious actor, governance abuse, or leaked keys — it is purely a configuration-drift risk identical in kind to the original report: the guarded address is a static value that must always match a value controlled by an external, independently-upgradable system (the Ethereum Gateway/GatewayProxy contract). Snowbridge's own architecture explicitly anticipates Gateway upgrades (the "GatewayProxy" naming and separate `GatewayAddress` constants per pallet reinforce that the contract address is expected to be able to change over the bridge's lifetime), making this a realistic, foreseeable operational event rather than a theoretical one.

### Recommendation
Do not let fee release/settlement be strictly gated on an immutable address equality check with no fallback. Options:
- Allow `GatewayAddress` to be updated via a lightweight, non-full-upgrade governance extrinsic (as is already done for `set_operating_mode`) so stuck `PendingOrders` can be resolved without a full runtime upgrade.
- Add a permissionless/governance "expire and refund" path for `PendingOrders` older than some block threshold, so fees are not permanently unclaimable even if the gateway is never reconciled.
- Consider verifying the receipt against a set of historically valid Gateway addresses instead of a single constant, to tolerate planned migrations gracefully.

### Proof of Concept
1. Runtime is deployed with `GatewayAddress = G1` for `pallet_outbound_queue_v2`.
2. A message is sent to Ethereum; `do_process_message` records `PendingOrders[nonce] = { fee, ... }` [2](#0-1) .
3. Ethereum's Gateway contract is redeployed at address `G2` (e.g. due to an on-chain incident or planned upgrade), and the message is executed there, emitting a valid `DeliveryReceipt` with `gateway = G2`.
4. A relayer submits `submit_delivery_receipt` with a correctly verified proof; `T::Verifier::verify` succeeds since the log genuinely exists on the new address.
5. `process_delivery_receipt` executes `ensure!(T::GatewayAddress::get() == receipt.gateway, ...)` — `G1 != G2`, so the call reverts with `Error::InvalidGateway` [3](#0-2) .
6. `PendingOrders[nonce]` is never removed, the relayer is never rewarded, and there is no other call in the pallet capable of clearing or refunding this entry — the fee is permanently stuck until a runtime upgrade changes `GatewayAddress`.

		/// Process a message delivered by the MessageQueue pallet.
		/// IMPORTANT!! This method does not roll back storage changes on error.
		pub(crate) fn do_process_message(
			_: ProcessMessageOriginOf<T>,
			mut message: &[u8],
		) -> Result<bool, ProcessMessageError> {
			use ProcessMessageError::*;

			// Yield if the maximum number of messages has been processed this block.
			// This ensures that the weight of `on_finalize` has a known maximum bound.
			let current_len = MessageLeaves::<T>::decode_len().unwrap_or(0);
			if current_len >= T::MaxMessagesPerBlock::get() as usize {
				Self::deposit_event(Event::MessagePostponed {
					payload: message.to_vec(),
					reason: Yield,
				});
				return Err(Yield);
			}

			// Decode bytes into Message
			let Message { origin, id, fee, commands } =
				Message::decode(&mut message).map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: None,
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?;

			// Convert it to OutboundMessage and save into Messages storage
			let commands: Vec<OutboundCommandWrapper> = commands
				.into_iter()
				.map(|command| OutboundCommandWrapper {
					kind: command.index(),
					gas: T::GasMeter::maximum_dispatch_gas_used_at_most(&command),
					payload: command.abi_encode(),
				})
				.collect();

			let nonce = <Nonce<T>>::get().checked_add(1).ok_or_else(|| {
				Self::deposit_event(Event::MessageRejected {
					id: None,
					payload: message.to_vec(),
					error: Unsupported,
				});
				Unsupported
			})?;

			let outbound_message = OutboundMessage {
				origin,
				nonce,
				topic: id,
				commands: commands.clone().try_into().map_err(|_| {
					Self::deposit_event(Event::MessageRejected {
						id: Some(id),
						payload: message.to_vec(),
						error: Corrupt,
					});
					Corrupt
				})?,
			};
			Messages::<T>::append(outbound_message);

			// Convert it to an OutboundMessageWrapper (in ABI format), hash it using Keccak256 to
			// generate a committed hash, and store it in MessageLeaves storage which can be
			// verified on Ethereum later.
			let abi_commands: Vec<CommandWrapper> = commands
				.into_iter()
				.map(|command| CommandWrapper {
					kind: command.kind,
					gas: command.gas,
					payload: Bytes::from(command.payload),
				})
				.collect();
			let committed_message = OutboundMessageWrapper {
				origin: FixedBytes::from(origin.as_fixed_bytes()),
				nonce,
				topic: FixedBytes::from(id.as_fixed_bytes()),
				commands: abi_commands,
			};
			let message_abi_encoded_hash =
				<T as Config>::Hashing::hash(&committed_message.abi_encode());
			MessageLeaves::<T>::append(message_abi_encoded_hash);

			// Generate `PendingOrder` with fee attached in the message, stored
			// into the `PendingOrders` map storage, with assigned nonce as the key.
			// When the message is processed on ethereum side, the relayer will send the nonce
			// back with delivery proof, only after that the order can
			// be resolved and the fee will be rewarded to the relayer.
			let order = PendingOrder {
				nonce,
				fee,
				block_number: frame_system::Pallet::<T>::current_block_number(),
			};
			<PendingOrders<T>>::insert(nonce, order);

			<Nonce<T>>::set(nonce);

			Self::deposit_event(Event::MessageAccepted { id, nonce });

			Ok(true)
		}
