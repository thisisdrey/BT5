## Analog Found

### Title
TRX/TRC10 value sent to a TVM precompiled contract is permanently lost when the precompiled call fails - (File: `actuator/src/main/java/org/tron/core/vm/program/Program.java`)

### Summary
`Program.callToPrecompiledAddress` charges (transfers) the call's endowment from the caller to the destination precompiled-contract address *before* invoking the precompiled contract, and the code explicitly documents that this charge is not reversible on failure. When the subsequent precompiled-contract execution fails, the opcode merely pushes `0` (failure) onto the EVM/TVM stack and refunds no energy — it does not revert the value transfer or the enclosing transaction. This is the same bug class as the Holograph `executeJob`/`nonRevertingBridgeCall` report: value is moved as part of an inner call, the inner call can fail, and the failure is swallowed (reported as a soft failure) without returning the value, permanently trapping it.

### Finding Description
In `callToPrecompiledAddress`, when a `CALL`/`CALLCODE`/`DELEGATECALL` targets a precompiled contract address with a non-zero endowment, the value is moved directly against the account balances via `MUtil.transfer` (or token balance adjustment) on the child `deposit` repository: [1](#0-0) 

The comment on line 1712, `// Charge for endowment - is not reversible by rollback`, is explicit: unlike the ordinary internal-call path (`callToAddress`), where a failed/reverted inner call causes `deposit.commit()` to be skipped and thus discards all balance mutations made on the child repository, the endowment charge here is applied in a way that survives even when the subsequent precompiled contract call fails.

Immediately after, `contract.execute(data)` is invoked, and on failure (`out.getLeft() == false`) the method only spends energy and pushes zero — it does not undo the endowment transfer performed moments earlier: [2](#0-1) 

Compare this to the analogous `callToAddress` path used for regular contract targets, where a failed/reverted call causes the internal transaction to be rejected and `deposit.commit()` is skipped, so balance changes made on `deposit` (including the endowment transfer) are discarded together: [3](#0-2) 

The precompiled-contract path deliberately departs from that "commit-or-discard" semantics for the endowment charge, exactly matching the report's root cause: the value transfer happens as a side effect of an inner operation, that inner operation can fail without reverting the enclosing frame, and there is no refund path for the ETH/TRX that was already moved.

### Impact Explanation
Any Solidity/TVM contract compiled and deployed on-chain (fully permissionless — any account can broadcast a `TriggerSmartContract`/deploy transaction) that performs a `CALL`-with-value to a precompiled contract address can trigger this path. If the invoked precompiled contract's `execute(data)` returns failure — e.g., due to malformed/invalid input that the precompile's own validation rejects — the TRX or TRC10 tokens already charged to the precompile's address are not refunded, while the calling opcode merely reports failure (pushes `0`) rather than reverting the whole transaction. Because precompiled addresses have no user-controlled key or withdrawal logic, this value becomes permanently unspendable/frozen, and the operator/contract account that made the call loses those funds — the same category of "permanent freezing/loss of funds" as the original Holograph report.

### Likelihood Explanation
Medium. It requires a contract to intentionally or accidentally call a precompiled address with `value > 0` and supply data/conditions that make the precompile's own `execute()` return `false` (as opposed to running out of energy, which is handled by the earlier `requiredEnergy` branch and does not perform the charge). This is fully reachable by any unprivileged account that can deploy/trigger a contract — no special privilege required — matching the reachable-path restrictions of a broadcastable smart-contract transaction.

### Recommendation
In `callToPrecompiledAddress`, defer the endowment charge (`MUtil.transfer`/token-balance adjustment) until after `contract.execute(data)` returns success, or explicitly reverse the charge in the failure branch (`out.getLeft() == false`) before returning, mirroring the "commit-only-on-success" semantics already used in `callToAddress`.

### Proof of Concept
Not independently reproduced against a live TVM precompile in this analysis (would require constructing a precompiled-contract call whose `execute()` deterministically returns `false` after a non-zero endowment, e.g., via malformed input to a token-related precompile) — flagged as an open verification item that a Devin agent with test-execution access should confirm using the existing TVM test harness (`TvmTestUtils`, `VMTestBase`) by crafting a contract that does `precompiledAddr.call.value(x)(badData)` and asserting the sender's balance decreases while the precompile address's balance/state shows the value as unrecoverable.
