### Title
Front-running dust transfers can fill a victim's token list to `MAX_TOKENS_PER_USER`, blocking their deposits - (`contracts/Pool.sol`)

### Summary
`Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens` once an account's combined deposit-token + debt-token list reaches `MAX_TOKENS_PER_USER` (30). Because `DepositToken.transfer`/`transferFrom` permissionlessly adds the transferred token to the recipient's list, an attacker can front-run a victim's pending `deposit(...)`/`mint(...)`-type call with a 1-wei `depositTokenX.transfer(victim, 1)`, pushing the victim over the cap and making the victim's transaction revert — the same griefing pattern as the reference report (attacker front-runs a victim's state-changing call so it reverts on an "already occupied" condition). `DepositToken.deposit(amount_, onBehalfOf_)` offers an even simpler vector since anyone can deposit dust collateral `onBehalfOf_` the victim.

### Finding Description
The relevant chain:

- `DepositToken._transfer` adds the token to the recipient's per-account list when the recipient's prior balance was 0: [1](#0-0) 
- `DepositToken._mint` does the same on deposit: [2](#0-1) 
- `DepositToken.deposit` accepts an arbitrary `onBehalfOf_` beneficiary, so the attacker doesn't even need to hold the token: [3](#0-2) 
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts when `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30`: [4](#0-3) 
- `MAX_TOKENS_PER_USER = 30`: [5](#0-4) 

Attack: victim broadcasts `depositTokenNew.deposit(amount, victim)` where `depositTokenNew` is not yet in their list. Attacker observes the mempool tx and front-runs with `depositTokenX.deposit(1 wei, victim)` (or `depositTokenX.transfer(victim, 1)`) for a deposit token `X` the victim does not hold. This consumes the victim's last free slot; the victim's `_mint` then reverts at `pool.addToDepositTokensOfAccount` with `UserReachedMaxTokens`. Repeated front-running keeps the victim permanently unable to onboard new collateral types or take on new debt tokens (the same cap gates `addToDebtTokensOfAccount` in `Pool.sol:204`).

### Impact Explanation
Griefing / temporary freezing of funds: while the victim's list is at the cap, every deposit into a new collateral, every first-time receive of a new deposit token, and every new borrow (debt-token issue adds to `debtTokensOfAccount` under the same modifier) reverts. The victim can recover slots by zeroing out a dust balance (`transfer`/`withdraw` to zero removes the token via `removeFromDepositTokensOfAccount`), so existing funds aren't stolen, but the attacker can repeatedly re-fill slots at dust cost, forcing the victim into a front-running war. If a victim's position is at risk of liquidation and they need to deposit a *new* collateral type to restore health, the blocking of deposits can indirectly cause liquidation losses.

### Likelihood Explanation
The cap counts *both* deposit and debt tokens and is shared pool-wide. An attacker alone can only fill slots equal to the number of distinct deposit tokens registered in the pool, so fully saturating a fresh account requires the victim to already hold `30 - N` positions where `N` is the number of registered deposit tokens the attacker can dust. For victims already holding many positions (e.g., SmartFarmingManager-leveraged accounts holding several ms tokens), a small number of dust transfers suffices — e.g., a victim with 28 entries needs only 2 dust tokens to be blocked. Cost is trivial (1 wei of each underlying per token, plus gas). No privilege, oracle manipulation, or flawed parameters are required; `transfer`, `transferFrom`, and `deposit` are unprivileged and `deposit` is guarded only by `whenNotPaused`/`nonReentrant`/`onlyIfDepositTokenExists`, none of which stop the dust-add.

### Recommendation
- Apply the max-token check only to debt-bearing accounting, or exempt deposit-token *receipts* below a dust threshold from `addToDepositTokensOfAccount`.
- Alternatively, whitelist-gate the "add to list" path: only call `pool.addToDepositTokensOfAccount` when the transfer/deposit was initiated by the recipient (`_msgSender() == recipient_`) or when `amount_` exceeds a minimum meaningful amount.
- At minimum, make `deposit`'s `onBehalfOf_` path not enlarge the beneficiary's token list unless they opted in (e.g., track opt-in per token), so third parties cannot consume the cap.

### Proof of Concept
Hardhat test sketch (drop into `test/Pool.test.ts` style fixtures; assumes pool has deposit tokens `msdA`, `msdB`, ..., and `MAX_TOKENS_PER_USER = 30`):

```typescript
it('front-run dust griefing blocks victim deposit of a new token', async () => {
  const {pool, msdWETH, msdWBTC, victim, attacker} = await loadFixture(fixture)

  // Precondition: victim already has 28 tokens across deposit+debt lists
  // (simulated by prior deposits / debt issuance)
  const count = async (a: string) =>
    (await pool.getDepositTokensOfAccount(a)).length +
    (await pool.getDebtTokensOfAccount(a)).length
  expect(await count(victim.address)).eq(28)

  // Attacker acquires 1 wei of two msd tokens and dusts victim, filling slots 29,30
  await underlyingWETH.mint(attacker.address, 2)
  await underlyingWETH.connect(attacker).approve(msdWETH.address, 2)
  await msdWETH.connect(attacker).deposit(1, attacker.address)
  await msdWETH.connect(attacker).deposit(1, victim.address) // onBehalfOf griefing
  // ... same for a second deposit token, e.g. via transfer(1)
  expect(await count(victim.address)).eq(30)

  // Victim's pending deposit into a NEW deposit token reverts
  await underlyingDAI.mint(victim.address, parseEther('1000'))
  await underlyingDAI.connect(victim).approve(msdDAI.address, parseEther('1000'))
  await expect(
    msdDAI.connect(victim).deposit(parseEther('1000'), victim.address)
  ).to.revertedWithCustomError(pool, 'UserReachedMaxTokens')
})
```

The revert is deterministic: `DepositToken._mint` → `pool.addToDepositTokensOfAccount` → `onlyIfAdditionWillNotReachMaxTokens` → `UserReachedMaxTokens` [6](#0-5) . The attacker needs no roles and only dust capital; `deposit`'s `onBehalfOf_` parameter means they never need to hold the token before griefing.
