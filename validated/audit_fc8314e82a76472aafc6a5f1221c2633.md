### Title
Off-by-one boundary check in reftable varint parser can read past valid buffer region - ([File: internal/git/reftable/reftable.go])

### Summary
`Table.getVarInt()` in the reftable parser uses `start > blockEnd` as its bounds check when scanning a multi-byte varint, instead of `start >= blockEnd`. This mirrors the report's bug class exactly: the boundary comparison allows the "one past the end" index to be treated as valid, so a byte belonging to the next logical section of the buffer is read and folded into the parsed value.

### Finding Description
`getVarInt` is used by `getRefsFromBlock`/`parseRefBlock` to decode `prefixLength`, `suffixLength`, `updateIndexDelta`, and symref `size` fields while parsing a reftable ref block read from disk: [1](#0-0) 

The loop advances `start` and only rejects it once `start > blockEnd`; when `start == blockEnd` it still dereferences `src[start]` (`val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)`), even though `blockEnd` (passed in as `b.RestartStart` or `b.FullBlockSize`) is documented/used elsewhere as an exclusive boundary — i.e., the first index that is *not* part of the valid region: [2](#0-1) 

This is the same class of defect as the reported `getBytes32FromBytes()` issue: the guard rejects `index > length` but not `index == length`, so the "last" boundary position is treated as in-range and data belonging to the adjacent structure (here, the restart list or the next block) leaks into the decoded field.

Because the corrupted value directly becomes `prefixLength`/`suffixLength`/`size`, it is subsequently used, unchecked, to slice `src`: [3](#0-2) [4](#0-3) 

A corrupted length derived from the boundary byte can produce a value large enough that `idx+suffixLength` (or `idx+size`) exceeds `len(src)`, causing a Go slice-bounds panic, or can silently produce a wrong ref name / target OID if the value stays in range.

### Impact Explanation
Reftable files are the persisted on-disk reference storage format that Gitaly's storage manager reads and rewrites as part of normal write-transaction handling (`reftableRecorder.stageTables` opens and parses these tables via `reftable.ParseTable`/`reftable.ReadTablesList`, part of the transaction-commit path exercised by every reference-changing push): [5](#0-4) 

Reference-block parsing (`getRefsFromBlock`) is also used to enumerate references from these tables. Given the off-by-one, a malformed or maliciously crafted `.ref` table (e.g. arriving via replication, an imported/attacker-supplied repository, or one whose write was interrupted such that the byte immediately after a varint region happens to have the continuation bit set) can cause: (a) a panic/crash of the handler parsing the table — a DoS of whatever RPC path triggers table parsing/resequencing during transaction commit, or (b) incorrect ref names/target OIDs being derived from adjacent memory in the buffer, corrupting the observed reference graph. I was not able to fully trace, within the remaining tool budget, every production call site that invokes `GetReferences()`/`getRefsFromBlock` outside of tests, so the exact breadth of externally reachable read paths (vs. the confirmed write/resequencing path in `reftable.go`) is not fully verified.

### Likelihood Explanation
Triggering the bug requires the attacker to influence the exact byte at the block/restart boundary of a reftable file, which is derived from git-controlled binary layout rather than directly from raw pushed pack/ref content. It is reachable without special privileges (an ordinary user driving reference updates through the reftable-backed storage path, or supplying a crafted repository/table via import/replication), but it depends on precise byte-level control of an internal, git-generated binary format, making exploitation for something beyond a crash comparatively harder than a purely attacker-supplied length field.

### Recommendation
Change the bounds check in `getVarInt` from `start > blockEnd` to `start >= blockEnd`, consistent with `blockEnd` being used as an exclusive upper bound elsewhere in the parser:

```go
for (uint(src[start]) & 0x80) > 0 {
    start++
    if start >= blockEnd {
        return 0, 0, fmt.Errorf("exceeded block length")
    }
    val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
}
```

Additionally, validate `prefixLength`, `suffixLength`, and `size` against remaining buffer length (`len(src)-idx`) before slicing in `getRefsFromBlock`, to fail fast with a parse error rather than risk a slice-bounds panic.

### Proof of Concept
Conceptual PoC (Go, illustrating the boundary flaw in isolation, analogous to the Solidity PoC in the report):
```go
// src represents a ref block where the byte at blockEnd (index == blockEnd)
// still has its continuation bit (0x80) set, e.g. because it belongs to the
// following restart-list section rather than the varint being decoded.
src := []byte{0x81, 0x02} // 0x81 has continuation bit set
blockEnd := uint(1)       // valid varint bytes are only src[0]; src[1] is out of the intended region

// getVarInt(src, 0, blockEnd) will:
// 1. read src[0] = 0x81 -> continuation bit set, start++ -> start = 1
// 2. check "start > blockEnd" -> 1 > 1 is false, so it proceeds
// 3. reads src[1] (0x02), which belongs to the next section, corrupting `val`
```
A full reproduction against Gitaly would require crafting a `.ref` reftable file whose block/restart boundary lands exactly on a byte with the varint continuation bit set, then invoking a code path that parses it (`reftable.ParseTable` + `GetReferences`, or the transaction resequencing path in `reftableRecorder.stageTables`).

// getVarInt parses a variable int and increases the index.
func (t *Table) getVarInt(src []byte, start uint, blockEnd uint) (uint, uint, error) {
	var val uint

	val = uint(src[start]) & 0x7f

	for (uint(src[start]) & 0x80) > 0 {
		start++
		if start > blockEnd {
			return 0, 0, fmt.Errorf("exceeded block length")
		}

		val = ((val + 1) << 7) | (uint(src[start]) & 0x7f)
	}

	return start + 1, val, nil
}
