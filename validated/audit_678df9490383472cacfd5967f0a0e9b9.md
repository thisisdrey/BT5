Based on my research, I found a strong local analog to the Nouns bug in `pallet-nis` (Non-Interactive Staking), where an issuance-accounting function subtracts the pallet's own account balance from total/active issuance to compute the "effective" backing per receipt — exactly the same computational shape as Nouns' `adjustedTotalSupply()`.

### Title
NIS effective-issuance calculation is corrupted if the pallet's derived account changes without migrating held reserves - ([File: substrate/frame/nis/src/lib.rs])

### Summary
`pallet-nis` computes the "effective" total issuance backing outstanding receipts by subtracting the *current* balance held by `Self::account_id()` (a `PalletId`-derived account) from active issuance [1](#0-0) . This account address is recomputed live from `T::PalletId`, not stored as a fixed, migrated value [2](#0-1) . Exactly like the Nouns `adjustedTotalSupply()` bug — which subtracted `balanceOf(ds.timelock)` and broke when `ds.timelock` was repointed without moving nouns off the old timelock — if `T::PalletId` (or any future re-derivation of `account_id()`) changes during a runtime upgrade without a companion step that transfers the pallet's `holdings` from the old derived account to the new one, `Self::account_id()` starts pointing at an empty account while the real backing funds remain stranded at the old address.

### Finding Description
`issuance_with` treats `T::Currency::balance(our_account)` as the pallet's reserve backing, then computes `other = total_issuance - holdings` and `effective = proportion_owed.left_from_one().saturating_reciprocal_mul(other)` [3](#0-2) . This mirrors the Nouns pattern of computing an "adjusted" supply/backing value by subtracting a privileged account's live balance rather than a value that is guaranteed to track that account across configuration changes.

`privatize()` then uses this same live computation to size a payout: it calls `Self::issuance_with(&our_account, &summary)` to get `effective_issuance`, computes `max_amount = receipt.proportion * effective_issuance`, and pays out `min(max_amount, T::Currency::balance(&our_account))` from the (new) `our_account` [4](#0-3) . If the account derivation changes without migrating the pot balance:
- `holdings` at the new address is understated (it excludes whatever remained parked at the stale, pre-migration address), which inflates `other` and thus `effective_issuance` for every subsequent `privatize()` call, exactly analogous to how the Nouns bug inflated `adjustedTotalSupply()` and thus the per-noun claimable share.
- This corrupts the fairness of `proportion * effective_issuance` payouts across all outstanding receipts (loss/gain distributed to receipt holders depending on rounding of `proportion_owed`), not just for one caller — the same "loss per unit, cumulative across holders" shape as the original report.

Existing guards do not catch this: there is no invariant check tying `account_id()`'s balance to a fixed, migrated value, and `do_try_state`/tests in this pallet do not assert that `holdings` reflects funds moved across a `PalletId` change (only budget-allocation invariants are checked elsewhere in the DAP pallet family I inspected, not NIS's account continuity).

### Impact Explanation
An uncorrected `PalletId` (or equivalent account-derivation) change for `pallet-nis` during a runtime upgrade silently and permanently skews `effective_issuance`, causing systematic mispricing of every `privatize()` payout thereafter — either overpaying some receipt holders at the expense of others or vice versa, without any attacker action being required, purely from the accounting formula being keyed to a live, re-derivable account address instead of a value preserved across upgrades. This matches "runtime bugs that compromise intended behavior" / "theft or unbacked … settle exactly once to the rightful beneficiary and amount" in the impact gate, since payouts sized off a corrupted `effective_issuance` no longer settle the correct amount to the correct proportion of holders.

### Likelihood Explanation
This requires a runtime upgrade that changes `T::PalletId` for `pallet-nis` (or otherwise changes what `account_id()` resolves to) without a paired migration moving the reserve balance — a plausible, easy-to-miss upgrade mistake, structurally identical to the original Nouns `ProposeTimelockMigrationCleanupMainnet` oversight (a legitimate upgrade script that forgot to move an asset balance alongside a reference change), not a malicious governance action.

### Recommendation
Any future migration that changes the pallet's account derivation (`PalletId` or otherwise) must, in the same migration, transfer the full balance held by the old `account_id()` to the new one before the new value takes effect, and/or add a `try-runtime` invariant asserting that `T::Currency::balance(old_account) == 0` post-upgrade for any account previously used as `Self::account_id()`.

### Proof of Concept
1. Deploy a runtime with `pallet-nis` using `PalletId::PalletA`, with receipts outstanding and the pallet's account holding reserve `X`.
2. Perform a runtime upgrade that changes `T::PalletId` to `PalletId::PalletB` (e.g., as part of an unrelated pallet-ID rename, similar to the real `pallet-dap-satellite` → `pallet-accumulate-and-forward` PalletId rename seen elsewhere in this codebase [5](#0-4) ) without transferring balance `X` from the old derived account to the new one.
3. Call `privatize()` on any existing receipt; observe that `issuance_with` computes `holdings` from the new (empty) account, inflating `other`/`effective_issuance`, and the payout no longer reflects the true backing ratio intended by the protocol — confirmed by comparing `effective_issuance` before and after the upgrade with no change in real total token supply.

Note: I was not able to locate any existing migration file for `pallet-nis` in this index that handles a `PalletId`/account-derivation change, so I cannot confirm whether such a migration currently exists or is planned; this is flagged as an assumption limitation of this analysis.
