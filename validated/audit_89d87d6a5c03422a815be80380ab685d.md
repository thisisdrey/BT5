### Title
Protocol fee bypass on high-value NEP-245/IMT multi-tokens via unit-amount TokenDiff splitting - (File: `contracts/defuse/core/src/intents/token_diff.rs`)

### Summary
`TokenDiff::token_fee` exempts any `Nep245` or `Imt` token delta with `amount <= 1` from protocol fees, based on the comment "do not take fees on NFTs and MTs with |delta| <= 1". This assumption is wrong for NEP-245 (Multi Token standard) and IMT sub-tokens, which can represent purely fungible, high-per-unit-value balances (not just NFTs). An attacker can split what would otherwise be one large `TokenDiff` (`delta = -N`) into `N` separate `TokenDiff` intents each with `delta = -1` on the same MT token, causing `token_fee` to return `Pips::ZERO` on every single one, and collect **zero** aggregate fee on the full economic value moved.

### Finding Description
Binding claimed: `fees_collected[T]` (summed over all `TokenDiff` intents executed for token `T`) should equal `protocol_fee.fee_ceil(total |negative delta| for T)` — the fee owed for the total economic value of `T` moved, as computed once via `TokenDiff::closure_delta`/`supply_delta` for a single aggregate trade.

In `execute_intent` [1](#0-0) , fee is computed per `TokenDiff` intent, independently, using only that intent's own `amount = delta.unsigned_abs()`:

```rust
let fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount);
```

And `token_fee` [2](#0-1)  returns `Pips::ZERO` for `TokenIdType::Nep245 | TokenIdType::Imt` whenever `amount <= 1`, regardless of what that single unit is economically worth.

`TokenIdType::Nep245` is the discriminant for NEP-245 (Multi Token Standard) sub-tokens, which the token-id crate defines generically as `contract_id + mt_token_id` with no distinction between fungible and non-fungible semantics [3](#0-2) . NEP-245 explicitly supports fungible token classes (an MT contract can mint a `mt_token_id` with e.g. zero decimals and a large per-unit value), so "amount == 1" does not imply "one non-fungible item of negligible unit price" as the code's comment assumes.

Exploit flow:
1. Attacker (or a counterparty they control/collude with) deposits/holds a NEP-245 MT balance where a single unit of a given `mt_token_id` carries substantial economic value.
2. Instead of submitting one `TokenDiff` with `diff = {mt_token: -N, other_token: +N*price}`, attacker submits `N` separate signed `TokenDiff` intents (batched in one `MultiPayload`, or spread across several), each `diff = {mt_token: -1, other_token: +price}`, matched against corresponding counter-intents.
3. For each intent, `token_fee(mt_token, amount=1, protocol_fee)` hits the `amount <= 1` branch and returns `Pips::ZERO`, so `fee = Pips::ZERO.fee_ceil(1) = 0`.
4. After executing all `N` intents, the full notional value has moved but `fees_collected` for `mt_token` totals `0`, whereas a single equivalent `TokenDiff` with `delta = -N` would have paid `protocol_fee.fee_ceil(N) > 0`.

No existing guard prevents this: `MultiPayload::verify`, nonce checks, and `TransferMatcher::finalize` only concern signature/replay validity and balance conservation across the batch, not the per-token aggregate fee. The fee logic in `token_fee` looks solely at the `amount` of the single `TokenDiff` being executed, with no memory of, or aggregation across, prior/other intents in the same batch or session touching the same token.

### Impact Explanation
Protocol fee revenue for `Nep245`/`Imt` tokens can be bypassed entirely by structuring trades as many unit-`1` `TokenDiff` intents instead of one aggregate diff. This does not move funds without authorization or break balance conservation (the Verifier's internal ledger still nets deltas correctly per intent), but it under-collects protocol fees that the fee schedule (`Pips`) is meant to enforce, which is explicitly listed as a Critical-severity category ("protocol fees bypassed"). The blast radius covers any NEP-245/IMT token registered on the Verifier with meaningful per-unit value, and is repeatable indefinitely across accounts, tokens, and batches by any signer, at the cost of only extra transaction/intent overhead.

### Likelihood Explanation
The attacker needs no special privileges — any signer can construct arbitrary `TokenDiff` intents in a `MultiPayload`, matched with a willing (possibly self-controlled) counterparty. The only economic requirement is finding or minting a NEP-245/IMT token whose single-unit trades carry non-trivial value (fully within attacker's control since they can deploy and control their own MT contracts, per the threat model). This makes the exploit highly feasible and fully repeatable with no privileged access required.

### Recommendation
Do not key the fee exemption purely on the numeric `amount` of a single intent. Either: (a) restrict the `amount <= 1` fee exemption to `TokenIdType::Nep171` (true NFTs) only, and always charge the standard fee schedule for `Nep245`/`Imt` deltas regardless of amount; or (b) if a "dust"/NFT-like exemption for MTs is still desired, base it on token metadata (e.g., an explicit non-fungible flag or `decimals == 0 && total_supply == 1`) rather than the transaction's `amount`, so it cannot be gamed by splitting trades into unit-sized chunks.

### Proof of Concept
```rust
// contracts/defuse/core/src/intents/token_diff.rs (new #[test])
#[test]
fn fee_bypass_via_unit_splitting() {
    let token_id = TokenId::from(Nep245TokenId::new(
        "mt.near".parse::<AccountId>().unwrap(),
        "high_value_share".to_string(),
    ));
    let fee = Pips::ONE_PERCENT; // nonzero protocol fee

    // Aggregate trade: one TokenDiff moving 1_000 units at once
    let aggregate_fee = TokenDiff::token_fee(&token_id, 1_000, fee).fee_ceil(1_000);
    assert!(aggregate_fee > 0, "aggregate trade should pay nonzero fee");

    // Split trade: 1_000 TokenDiff intents each moving 1 unit
    let mut split_fee_total: u128 = 0;
    for _ in 0..1_000 {
        let f = TokenDiff::token_fee(&token_id, 1, fee).fee_ceil(1);
        split_fee_total += f;
    }

    // Binding violated: total fee collected on identical economic value differs
    assert_eq!(split_fee_total, 0);
    assert!(split_fee_total < aggregate_fee, "fee bypassed by splitting into unit-amount TokenDiffs");
}
```
This can be extended into a `near-workspaces` sandbox test executing `execute_intents` with a real NEP-245 contract and `N` signed unit-amount `TokenDiff` intents in one `MultiPayload`, asserting `fee_collector`'s post-execution MT-fee balance is `0` despite `N` units of high-value MT having changed hands, versus the nonzero value predicted by `TokenDiff::closure_delta`/`supply_delta` for the equivalent aggregate `-N` trade.
