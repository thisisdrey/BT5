Audit Report

## Title
`calculate_fee` truncates the ETH-denominated remote fee to zero on decimal down-scaling, letting senders under-pay for remote message dispatch that is still fully executed and rewarded - ([File: bridges/snowbridge/pallets/outbound-queue/src/lib.rs])

## Summary
`Pallet::calculate_fee` computes the remote-dispatch fee in Ether/Wei (18-decimal) fixed point and converts it to the chain's native decimals via `convert_from_ether_decimals`, which performs plain floor division by `10^(18 - Decimals)`. For realistic parameter combinations (confirmed by the pallet's own test), this floors the sender-charged `fee.remote` to `0`, while the full `reward` promised to the Ethereum relayer is still committed to the on-chain message and paid out regardless.

## Finding Description
`calculate_fee` derives the remote fee in Wei via `calculate_remote_fee`, rescales by `multiplier`/`exchange_rate`, then calls `Self::convert_from_ether_decimals(fee)`, which does `value.checked_div(denom)` with no rounding-up or minimum-floor logic [1](#0-0) [2](#0-1) .

This is invoked directly and unconditionally from the public `SendMessage::validate` implementation, on the hot path of every outbound message (channel-gated only, no fee-floor check) [3](#0-2) .

`PricingParameters::validate` only checks that the raw governance-set fields (`exchange_rate`, `fee_per_gas`, `rewards.local`, `rewards.remote`, `multiplier`) are individually non-zero — it never checks the *derived, decimal-converted* `fee.remote` for zero [4](#0-3) .

Independently of the (possibly zero) local-currency fee, `do_process_message` reads `pricing_params.rewards.remote` fresh at commit time and embeds it as `reward` in the `CommittedMessage` sent to Ethereum, in full Wei precision, with no linkage back to what was actually collected from the sender [5](#0-4) .

The pallet's own test reproduces exactly this: with non-zero pricing parameters (`exchange_rate=1`, `fee_per_gas=1`, `rewards.remote=1`, `multiplier=1`), `calculate_fee` returns `fee.remote == 0` while `fee.local` remains the (unrelated) weight-based constant, and the test comment explicitly states this "should be avoided" [6](#0-5) .

## Impact Explanation
Any unprivileged account routing a message through this exporter (via XCM `ExportMessage` or `snowbridge_pallet_system::send`) pays only the fixed `local_fee` (weight-related) while the remote/relayer-reward component is silently zeroed out, even though the full reward is still promised on Ethereum. This is public underpriced work reachable by any external caller and directly degrades the bridge's fee economics that are meant to fund/throttle relayer dispatch — matching the "public underpriced work that degrades block production or stalls bridge processing" impact category.

## Likelihood Explanation
The condition requires no privileged action or misconfiguration — only ordinary, valid `PricingParameters` where the Wei-denominated remote fee's magnitude is smaller than the decimal-scaling divisor (`10^6` for a 12-decimal chain such as typical BridgeHub configuration). This is demonstrated directly in the pallet's existing unit test with fully valid, non-zero inputs, and is reachable on every call to `validate`/`calculate_fee` for the outbound-queue v1 pallet.

## Recommendation
Change `convert_from_ether_decimals` to use ceiling (round-up) division instead of floor division, and/or add an explicit post-conversion check in `calculate_fee`/`validate` that rejects (or charges a governance-defined minimum) when the derived `fee.remote` is `0` but `pricing_params.rewards.remote` is non-zero.

## Proof of Concept
Reproducible directly via the existing test in `bridges/snowbridge/pallets/outbound-queue/src/test.rs`:

		pub(crate) fn calculate_fee(
			gas_used_at_most: u64,
			params: PricingParameters<T::Balance>,
		) -> Fee<T::Balance> {
			// Remote fee in ether
			let fee = Self::calculate_remote_fee(
				gas_used_at_most,
				params.fee_per_gas,
				params.rewards.remote,
			);

			// downcast to u128
			let fee: u128 = fee.try_into().defensive_unwrap_or(u128::MAX);

			// multiply by multiplier and convert to local currency
			let fee = FixedU128::from_inner(fee)
				.saturating_mul(params.multiplier)
				.checked_div(&params.exchange_rate)
				.expect("exchange rate is not zero; qed")
				.into_inner();

			// adjust fixed point to match local currency
			let fee = Self::convert_from_ether_decimals(fee);

			Fee::from((Self::calculate_local_fee(), fee))
		}

		// 1 KSM has 12 digits of precision
		// 1 ETH has 18 digits of precision
		pub(crate) fn convert_from_ether_decimals(value: u128) -> T::Balance {
			let decimals = ETHER_DECIMALS.saturating_sub(T::Decimals::get()) as u32;
			let denom = 10u128.saturating_pow(decimals);
			value.checked_div(denom).expect("divisor is non-zero; qed").into()
		}

	) -> Result<(Self::Ticket, Fee<<Self as SendMessageFeeProvider>::Balance>), SendError> {

		let payload = message.command.abi_encode();
		ensure!(

			SendError::MessageTooLarge

		// Ensure there is a registered channel we can transmit this message on
		ensure!(T::Channels::contains(&message.channel_id), SendError::InvalidChannel);

		// Generate a unique message id unless one is provided
		let message_id: H256 = message
			.id
			.unwrap_or_else(|| unique((message.channel_id, &message.command)).into());

		let gas_used_at_most = T::GasMeter::maximum_gas_used_at_most(&message.command);
		let fee = Self::calculate_fee(gas_used_at_most, T::PricingParameters::get());

		let queued_message: VersionedQueuedMessage = QueuedMessage {
			id: message_id,
			channel_id: message.channel_id,
			command: message.command.clone(),

		let ticket = Ticket { message_id, channel_id: message.channel_id, message: encoded };
