### Title
Global catfile process cache can be trivially evicted by an unprivileged multi-tenant client, degrading service for unrelated repositories - (File: internal/git/catfile/cache.go)

### Summary
`ProcessCache` maintains a fixed-size, per-Gitaly-node FIFO cache of `git-cat-file` processes (`objectReaders` / `objectReadersWithoutMailmap`) bounded by `maxLen` (`cfg.Git.CatfileCacheSize`, defaulting to 100). [1](#0-0)  Any client whose requests touch enough distinct repositories can force the FIFO eviction path to close and discard other tenants' cached processes, similar to how the CLOB bug allows a single attacker to churn through and wipe out an order-book slot list bounded by `maxNumLimitsPerSide`.

### Finding Description
Cache entries are keyed by `{sessionID, repoStorage, repoRelPath, repoObjDir, repoAltDir}`, where `sessionID` is not a real per-client/session identifier but simply the current time rounded to the next 5-minute boundary: `cacheKey, isCacheable := newCacheKey(fmt.Sprintf("%d", roundToNearestFiveMinute(time.Now())), repo)`. [2](#0-1)  This means the effective identity distinguishing cache entries within any 5-minute window is the **repository**, not the caller. Every distinct repository accessed generates a new cache entry, all sharing the same global, size-bounded list (`objectReaders`/`objectReadersWithoutMailmap`), rather than a per-user or per-repository quota. [3](#0-2) 

When a new entry is added and the list length exceeds `maxLen`, the oldest entry is unconditionally evicted and its underlying `git-cat-file` process is closed, regardless of who "owns" it or how active it is: [4](#0-3) 

`evictHead`/`delete` close the process directly: [5](#0-4) 

This is structurally analogous to the CLOB `_executeBidLimitOrder` bug: a bounded, shared list evicts its "worst"/oldest entry whenever a new distinct entry is added, and there is no per-caller quota preventing one client from generating enough distinct entries to evict all others. In the CLOB case an attacker spams cheap, short-lived orders across accounts to wipe out real book depth; here an attacker (any authenticated Gitaly client with access to many repositories on a shared, multi-tenant storage node — e.g. a GitLab instance serving many projects) simply issues read RPCs (e.g. `TreeEntry`, `GetBlob`, blame/log RPCs) against more than `maxLen` distinct repositories in quick succession. Each such call is a "cheap, disposable" cache entry from the attacker's perspective (they don't care whether it stays cached), but each insertion evicts one entry belonging to whatever repository — potentially another tenant's actively-used repository — happens to be at the head of the FIFO list.

The code comment for this cache explicitly acknowledges a related adversarial concern ("disallow trivial denial of service attacks against other users in case it is possible to poison the cache with broken git-cat-file(1) processes") [6](#0-5) , but the mitigation only prevents *sharing* a still-valid process across users within the same repo/time-bucket key; it does nothing to prevent one user's *volume* of distinct-repository requests from starving the shared eviction slot budget used by all other tenants.

### Impact Explanation
Eviction merely closes a cached `git-cat-file` process; the next request for that repository will transparently spawn a new one via `create(ctx)`, so there is no correctness failure or data loss. [7](#0-6)  The impact is a performance-degradation DoS: repeatedly forced cache misses increase process-spawn overhead (`git-cat-file` startup) and CPU/IO load on a shared Gitaly node for all tenants whose repositories happen to be co-located on that node, similar in spirit (though lower severity, since no funds/orders are lost) to the referenced CLOB issue where legitimate state is repeatedly displaced by cheap adversarial churn.

### Likelihood Explanation
Any authenticated caller that can enumerate/access many repositories on a shared multi-tenant Gitaly node can trigger this without any special privilege — plain read RPCs suffice, no write access, hooks, or quarantine interaction are needed. The default `maxLen` is only 100 entries per reader type [8](#0-7) , making this reachable with a modest number of distinct-repository requests. The eviction itself requires no special timing (unlike the CLOB's "expire in the next second" trick) — it is a simple, deterministic FIFO-overflow eviction, so likelihood of triggering the mechanism is high even if actual "impact felt by a victim" depends on co-location and traffic timing.

### Recommendation
Scope the FIFO eviction quota per caller/session rather than allowing a single high-repository-churn client to consume the entire node-wide budget — e.g., track and cap the number of live cache slots that a given real session (not merely a 5-minute time bucket) can occupy, or maintain per-key/per-tenant sub-limits similar to the `[[concurrency]]` per-repo queueing model already used elsewhere in Gitaly (`internal/limiter`). Alternatively, weight eviction by recency-of-use (true LRU) rather than pure insertion-order to reduce the chance that an actively-reused legitimate entry is evicted purely because many one-off repositories were recently touched by another client.

### Proof of Concept
1. On a shared Gitaly node with `Git.CatfileCacheSize` at its default (100), have Tenant A perform a normal workload that keeps warm `git-cat-file` processes cached for its 5 actively used repositories (via `ObjectReader`/`ObjectInfoReader` calls, e.g. through `GetBlob`/`TreeEntry` RPCs).
2. Have an unprivileged Tenant B (or any client with read access to ≥100 distinct repositories on the same node, e.g. many small/empty repos it created itself) issue a burst of read RPCs — one against each of 100+ distinct repositories — within the same 5-minute window.
3. Each request computes a distinct `cacheKey` (`{timeBucket, repoStorage, repoRelPath, ...}`) and is appended via `processes.Add`, which evicts the head of the shared `entries` slice once `len(p.entries) > p.maxLen`. [4](#0-3) 
4. Tenant A's previously cached processes are pushed out of the list and closed, forcing Tenant A's subsequent requests to pay full `git-cat-file` process-startup cost again, degrading Tenant A's latency purely due to Tenant B's unrelated traffic pattern.
