### Title
`write_freq` write-cooldown for StackerDB slots is defined but never enforced on the write path - ([File: stackslib/src/net/stackerdb/db.rs])

### Summary
`StackerDBConfig::write_freq` is documented as "minimum wall-clock time between writes to the same slot" [1](#0-0) , and the network layer explicitly relies on that cooldown for scheduling fetches in `StackerDBSync` (`self.write_freq > 0 && write_ts + self.write_freq > now`) [2](#0-1) . However, the actual chunk-write function that persists a signer's data, `StackerDBTx::try_replace_chunk`, never checks `write_freq`/`write_ts` at all — it only checks chunk size, slot existence, signature, staleness (`slot_version <= slot_validation.version`) and `max_writes` [3](#0-2) . This is the same code path invoked directly by the unauthenticated-adjacent RPC endpoint `poststackerdbchunk.rs` for every submitted chunk [4](#0-3) .

### Finding Description
The comment on `validate_received_chunk` explicitly states: "NOTE: does not check write frequency, since the caller has different ways of doing this" [5](#0-4) , and the unsolicited push handler similarly documents that write-frequency is deliberately skipped there, relying on bandwidth throttling elsewhere [6](#0-5) . The intended enforcement point is the actual DB write, `try_replace_chunk`, since that's the only place that persists the chunk and bumps the lamport `slot_version`. But `try_replace_chunk` performs exactly four checks — chunk size, slot existence, signer verification, and staleness/`max_writes` — with no `write_freq`/timestamp check whatsoever [7](#0-6) .

Correspondingly, `net::Error::TooFrequentSlotWrites` exists as an error variant with a `Display` implementation [8](#0-7) , but it is never constructed anywhere in the codebase (it only appears in `net/mod.rs`, in its enum definition and `Display` impl) — confirming there is no code path that actually raises this error. This mirrors the reported bug class precisely: a cooldown/"grace period" is checked in one place (`StackerDBSync::readding_needed_chunks`-style fetch throttling, analogous to `deregisterSessionKey()`'s grace check) but the corresponding "registration"/write operation (`try_replace_chunk`, exposed via the HTTP `POST /v2/stackerdb/.../chunks` endpoint) has no restriction at all, letting any legitimate slot signer bypass the intended write-rate limit simply by submitting new signed chunks with incrementing `slot_version` as fast as they want (bounded only by `max_writes`).

### Impact Explanation
`write_freq` exists specifically to bound how often a given slot's data can change and therefore how often it must be re-propagated across the whole peer network of StackerDB replicas. Because it isn't enforced at the write/insert boundary, any signer authorized for a slot (e.g. a legitimately-registered signer for a `.signers-*` or miner StackerDB contract) can write at `max_writes` speed instead of the throttled rate the contract's `stackerdb-get-config` intended, forcing constant re-propagation/re-sync load onto every replica node on the network (not just the writer's own node) — this is a network-wide amplification of write/propagation load beyond the configured contract policy, i.e., non-canonical/mismatched enforcement of the contract-specified state ("served" behavior does not match "committed" configuration).

### Likelihood Explanation
Likelihood is high for any already-authorized StackerDB slot signer: no special privilege beyond being one of the `signers` for that contract-configured DB is required, and the write path (`try_replace_chunk`/`insert_chunk`) is reachable both via the public HTTP RPC endpoint (`poststackerdbchunk.rs`) and via P2P push handling, neither of which enforces `write_freq`.

### Recommendation
Enforce `config.write_freq` inside `StackerDBTx::try_replace_chunk` (or `insert_chunk`) by comparing `get_epoch_time_secs()` against `slot_validation.write_time + config.write_freq`, returning the already-defined-but-unused `net_error::TooFrequentSlotWrites` when the cooldown has not elapsed — mirroring the staleness/`max_writes` checks already present at lines 424-436 of `db.rs`.

### Proof of Concept
1. Configure a StackerDB contract with `write-freq: u3600` (i.e., signers should write at most once per hour) and register a signer address for slot 0.
2. As the registered signer, sign and `POST` a `StackerDBChunkData` for slot 0 with `slot_version = 1` to `/v2/stackerdb/<contract>/chunks/0` via `poststackerdbchunk.rs`; it succeeds via `try_replace_chunk` [4](#0-3) .
3. Immediately sign and `POST` a second chunk for slot 0 with `slot_version = 2`. Because `try_replace_chunk` only checks `slot_version <= slot_validation.version` and `slot_version > max_writes` [9](#0-8) , this second write also succeeds despite occurring well within the configured `write_freq` window, and `write_time` is unconditionally refreshed in `insert_chunk` [10](#0-9) .
4. Repeat up to `max_writes` times in rapid succession — none of the writes are throttled, confirming `write_freq` has no effect on the actual write path, only on remote peers' opportunistic-fetch scheduling logic in `sync.rs`.

    /// Add or replace a chunk for a given reward cycle, if it is valid
    /// Otherwise, this errors out with Error::StaleChunk
    pub fn try_replace_chunk(
        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
        if slot_desc.slot_version <= slot_validation.version {
            return Err(net_error::StaleChunk {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
            });
        }
        if slot_desc.slot_version > self.config.max_writes {
            return Err(net_error::TooManySlotWrites {
                supplied_version: slot_desc.slot_version,
                latest_version: slot_validation.version,
                max_writes: self.config.max_writes,
            });
        }
        self.insert_chunk(smart_contract, slot_desc, chunk)
    }
}
