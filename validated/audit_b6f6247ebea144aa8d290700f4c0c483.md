### Title
`ReliabilityReport::bump_successful_requests` fires on any decodable-but-content-mismatched response, letting a malicious peer's URL dominate future attachment-fetch prioritization - (File: `stackslib/src/net/atlas/download.rs`)

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` and `extend_with_inventories` call `report.bump_successful_requests()` purely based on whether the HTTP response body could be decoded into an `Attachment`/`GetAttachmentsInvResponse`, without ever checking that the returned attachment's content hash matches the `content_hash` that was actually requested. This means a remote peer can return well-formed but wrong-hash attachment bodies forever and still accumulate a "successful" reliability score identical to an honest peer.

### Finding Description
In `extend_with_attachments`:
```rust
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [1](#0-0) 

There is no comparison of `response.attachment.hash()` against `request.content_hash` before `bump_successful_requests()` is invoked. The same pattern exists in `extend_with_inventories`, which bumps success on any decodable `GetAttachmentsInvResponse` regardless of whether the reported inventory bits are truthful: [2](#0-1) 

The hash of the returned attachment is only later used, in `AttachmentsDownloader::run`, to look up matching pending attachment instances (`find_all_attachment_instances(&attachment.hash())`), and the attachment is unconditionally inserted into the AtlasDB under its own self-consistent hash: [3](#0-2) 

Because attachments are stored keyed by their own computed hash (not the original request's hash), a wrong-hash response cannot be "smuggled in" as the data for a different content hash — but the reliability-tracking equality claimed in the question (`recorded success count == number of hash-verified correct responses`) is genuinely broken: `bump_successful_requests()` fires on every syntactically valid HTTP 200 response the attacker sends, whether or not it actually supplies the content the batch was trying to resolve. The `ReliabilityReport` is carried on `AttachmentRequest`/`AttachmentsInventoryRequest` (`pub reliability_report: ReliabilityReport` field, e.g. on `AttachmentsInventoryRequest`) and copied per-peer into every future prioritized request: [4](#0-3) [5](#0-4) [6](#0-5) 

I could not fully inspect the `Ord`/priority-comparison implementations for `AttachmentRequest`/`AttachmentsInventoryRequest` because the file was truncated beyond line 1000 in my review, so I cannot directly confirm the exact numeric weighting used for peer selection ordering, only that the `ReliabilityReport` (whose "success" counter is corruptible as shown above) is the field carried into and used by those request/ordering structures.

### Impact Explanation
An unprivileged remote peer that the victim node has chosen as an outbound sync peer (attainable simply by running a peer and getting gossiped/connected, no privileged role or secret required) can answer every `AttachmentRequest`/`AttachmentsInventoryRequest` it receives with syntactically valid but content-wrong data. Each such response increments its `ReliabilityReport`'s success counter identically to a genuinely correct peer, since no hash/content check gates `bump_successful_requests()`. Because `ReliabilityReport` values persist across batches in `AttachmentsDownloader::reliability_reports` and are threaded into future request prioritization structures, the attacker's URL is not penalized and keeps being treated as equally or more reliable than honest peers, while it never supplies attachment content that resolves any pending attachment instance (since the AtlasDB indexes instantiated attachments by their true content hash, and the pending instance's hash never matches). Net effect: legitimate attachment/BNS-zonefile resolution for the affected content can be starved as the corrupted-but-"reliable" peer continues to consume request slots that should have gone to honest peers, which fits the "attachment/BNS mismatch" / data-availability degradation category (High).

### Likelihood Explanation
Low cost, fully remote: the attacker only needs to (a) be selected as one of the node's outbound sync peers via ordinary p2p gossip (no admin/secret required), and (b) respond to `GET /attachment/...` requests with any well-formed but wrong-content attachment payload. This is repeatable indefinitely and requires no privileged access.

### Recommendation
In `AttachmentsBatchStateContext::extend_with_attachments`, after `decode_atlas_get_attachment()` succeeds, compare `response.attachment.hash()` to `request.content_hash` before calling `report.bump_successful_requests()`; treat a mismatch as `report.bump_failed_requests()` (and optionally treat repeated mismatches from the same peer as `faulty_peers`/deregister-worthy). Similarly, in `extend_with_inventories`, only bump success once the returned inventory is checked for plausibility (e.g., consistent page count/index versus the requested pages) rather than merely on successful decode.

### Proof of Concept
Rust test in `stackslib/src/net/atlas/tests.rs` (or a new test module colocated with `download.rs`):
1. Construct an `AttachmentsBatchStateContext` with one peer URL and an `AttachmentRequest` for a known `content_hash` H1.
2. Build a `BatchedRequestsResult<AttachmentRequest>` whose `succeeded` map contains `(request_with_hash_H1, Some(http_response_encoding_attachment_with_hash_H2))` where `H2 != H1` (i.e., a well-formed `GetAttachmentResponse` whose content hashes to a different value).
3. Call `context.extend_with_attachments(&mut result)` and assert `context.peers[&peer_url].total_requests()` / success counter increased exactly as it would for a matching-hash response — i.e., build a second scenario where the same peer answers N times with correct-hash data and N times with wrong-hash data, and assert `ReliabilityReport` scores are identical (`assert_eq!(score_wrong_hash, score_correct_hash)`), demonstrating `report.bump_successful_requests()` does not distinguish correctness of content vs. requested hash at [1](#0-0) .
