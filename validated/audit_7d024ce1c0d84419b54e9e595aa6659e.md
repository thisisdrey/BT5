### Title
Remote panic via attacker-controlled `preamble.payload_len` in relay validators (`assert!` DoS) - (File: stackslib/src/net/chat.rs)

### Summary
The original finding shows how an unchecked arithmetic operation (`totalCollateralBase - totalDebtBase`) that assumes an invariant (collateral ≥ debt) can be driven to revert by attacker-influenced state, DOSing a widely-used helper function. The analogous fault class in this repo is code that assumes an invariant on attacker-supplied wire data and enforces it with a hard `assert!` rather than a graceful error path, so violating the invariant causes a panic instead of a rejected message.

### Finding Description
In `ConversationP2P`'s relay-message validators in `stackslib/src/net/chat.rs`, each validator begins with a hard assertion on `preamble.payload_len`, a field taken directly from the wire-decoded `Preamble` sent by the remote peer: [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`validate_transaction_push`, `validate_stackerdb_push`, and `validate_nakamoto_block_push` all execute `assert!(preamble.payload_len > 1)`, and `validate_microblocks_push` executes `assert!(preamble.payload_len > 5)`, immediately followed by unchecked subtraction such as `(preamble.payload_len as u64) - 1` used for bandwidth accounting: [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

`payload_len` is a `u32` field of `Preamble`, populated from the wire during message decode (see `Preamble::new`/serialization in `stackslib/src/net/codec.rs`), and its comment ("don't count 1-byte type prefix") indicates the code merely *assumes* the sender computed it correctly relative to the payload it actually sent — the same "equality assumed but not independently verified" pattern as the original TVL bug (collateral assumed ≥ debt). If this equality/assumption doesn't hold (e.g., the remote peer sends a `Transaction`/`StackerDBPushChunk`/`NakamotoBlocksData` message type with a preamble whose `payload_len` field is 0 or 1, independent from the actual relayed payload bytes), the `assert!` fires and unwinds/panics the thread handling that peer's conversation, rather than returning a `net_error` that would be handled gracefully like every other validation path in this function (`process_relayers`, bandwidth throttling, etc.).

### Impact Explanation
An `assert!` panic in a connection-handling thread converts a malformed/adversarial field into a hard crash rather than a rejected/NACKed message. Because this is reached from `handle_data`-style relay message dispatch on an already-established `ConversationP2P` (i.e., any completed, unauthenticated-content peer connection can send `Transaction`, `StackerDBPushChunk`, `NakamotoBlocksData`, or `Microblocks` relay payloads), a single crafted preamble field can trigger this from a remote, unprivileged peer — matching the "remote crash/unauthenticated DoS from few messages" Critical bucket, or at minimum a bounded-compute DoS on message processing.

### Likelihood Explanation
Likelihood depends entirely on whether `payload_len` is independently re-derived/verified from the actually-received payload bytes prior to reaching these validators, versus being trusted as sent in the `Preamble`. Based on the code reviewed, the check is an `assert!` (i.e., a "this should never happen" invariant), not a `Result`-returning validation, which strongly suggests the invariant is not defensively re-checked against attacker input at this call site — the same class of unchecked assumption as the original TVL underflow. I could not fully trace, within available context, the exact preamble/payload length cross-validation performed earlier in the receive pipeline (e.g., in `codec.rs`'s `StacksMessage::consensus_deserialize` or `connection.rs`), so it remains possible that an earlier decode step enforces `payload_len == actual serialized message length`, which would neutralize this specific path. This should be confirmed against the full decode pipeline.

### Recommendation
Replace the `assert!(preamble.payload_len > N)` calls in `validate_transaction_push`, `validate_stackerdb_push`, `validate_nakamoto_block_push`, and `validate_microblocks_push` with a proper bounds check that returns `Err(net_error::InvalidMessage)` (mirroring the `process_relayers` failure path already present in the same functions) instead of panicking, and use `checked_sub`/`saturating_sub` for the subsequent `payload_len - N` bandwidth-accounting arithmetic.

### Proof of Concept
Conceptual PoC (pending confirmation of the exact upstream decode validation):
1. Establish (or otherwise reach) a `ConversationP2P` handling loop for a remote peer.
2. Send a P2P message whose `StacksMessageType` is `Transaction` (or `StackerDBPushChunk` / `NakamotoBlocksData`) with a `Preamble.payload_len` field set to `0` or `1`, while keeping the message otherwise well-formed enough to reach the corresponding `validate_*_push` call.
3. Observe `assert!(preamble.payload_len > 1)` panics, unwinding/crashing the thread handling that connection (`stackslib/src/net/chat.rs:2172/2210/2249`), and for `Microblocks`, `assert!(preamble.payload_len > 5)` at `stackslib/src/net/chat.rs:2135`. [9](#0-8) [10](#0-9)

    /// Validate a pushed transaction.
    /// Update bandwidth accounting, but forward the transaction along.
    fn validate_transaction_push(
        &mut self,
        network: &PeerNetwork,
        preamble: &Preamble,
        relayers: Vec<RelayData>,
    ) -> Result<Option<ReplyHandleP2P>, net_error> {
        assert!(preamble.payload_len > 1); // don't count 1-byte type prefix

        let local_peer = network.get_local_peer();
        let chain_view = network.get_chain_view();

        if !self.process_relayers(local_peer, preamble, &relayers) {
            warn!(
                "Drop pushed transaction -- invalid relayers {:?}",
                &relayers
            );
            self.stats.msgs_err += 1;
            return Err(net_error::InvalidMessage);
        }

        self.stats
            .add_transaction_push((preamble.payload_len as u64) - 1);

        if self.connection.options.max_transaction_push_bandwidth > 0
            && self.stats.get_transaction_push_bandwidth()
                > (self.connection.options.max_transaction_push_bandwidth as f64)
        {
            debug!("{:?}: Neighbor {:?} exceeded max transaction-push bandwidth of {} bytes/sec (currently at {})", self, &self.to_neighbor_key(), self.connection.options.max_transaction_push_bandwidth, self.stats.get_transaction_push_bandwidth());
            return self
                .reply_nack(local_peer, chain_view, preamble, NackErrorCodes::Throttled)
                .map(Some);
        }
        Ok(None)
    }
