## Finding

Unbounded, unauthenticated body read in the signer event receiver's HTTP endpoint enables a memory-exhaustion DoS with a single request — analogous to the Jetty `getParameter()`/`getParts()` OOM issue (GHSA-qw69-rqj8-6qw8), where a body is read fully into memory with no size cap despite the framework claiming to bound it.

### Title
Unbounded body read in libsigner event receiver causes single-request OOM DoS - (File: libsigner/src/events.rs)

### Summary
`SignerEventReceiver::next_event` dispatches every incoming `POST` to `process_event`, which reads the entire HTTP body into memory via `request.as_reader().read_to_string(&mut body)` with no length check, no cap, and no authentication, before any JSON/codec parsing occurs.

### Finding Description
The signer's HTTP listener (backed by `tiny_http`) is bound via `SignerEventReceiver::bind` [1](#0-0)  and its `next_event` loop routes any `POST /stackerdb_chunks`, `/proposal_response`, `/new_burn_block`, or `/new_block` request straight into `process_event` [2](#0-1) .

`process_event` performs the read with no upper bound at all:
```rust
let mut body = String::new();
if let Err(e) = request.as_reader().read_to_string(&mut body) {
``` [3](#0-2) 

Unlike the node's RPC HTTP layer, which explicitly preflights `Content-Length` against a hard cap (`MAX_MESSAGE_LEN` / `MAX_PAYLOAD_LEN`) *before* touching the body buffer — e.g. `stackslib/src/net/api/poststackerdbchunk.rs`:
```rust
if preamble.get_content_length() > MAX_MESSAGE_LEN {
    return Err(Error::DecodeError(
        "Invalid Http request: PostStackerDBChunk body is too big".to_string(),
    ));
}
``` [4](#0-3) 
— the libsigner event listener has no equivalent guard. `tiny_http`'s `as_reader()` will happily stream as many bytes as the client sends (bounded only by `Content-Length` if present, or by the connection if chunked), and `read_to_string` grows the `String` buffer to match, with no cap comparable to `MAX_MESSAGE_LEN`. There is also no authentication check on this listener at all (it just checks the HTTP verb is `POST` and the path).

The equality broken here is: "bytes accepted into memory should equal (or be bounded by) an enforced maximum," matching the CWE-400/770 bug class in the Jetty advisory — a request body is read to completion into a growable in-memory buffer with no cap, prior to any validation.

### Impact Explanation
Any party able to reach the signer's event-receiver TCP port can send a single `POST` with an arbitrarily large body (real bytes, or a slow-trickle stream) and force the signer process to allocate unbounded memory, up to `OutOfMemoryError`/OOM-kill of the signer process. Because signers are security-critical (block validation/signing), crashing a signer process degrades the network's fault tolerance and could be used to selectively knock signers offline. This fits the "remote crash/unauthenticated DoS from few messages" criterion, since a single request suffices — no protocol handshake, key, or authorization is required.

### Likelihood Explanation
Likelihood depends on the socket being reachable by an untrusted party. Signers normally only expect traffic from their paired stacks-node, but the endpoint itself is unauthenticated by design (there is no shared-secret check anywhere in `next_event`/`process_event`), so if the bound address/port is reachable on a network segment shared with other principals (which operators sometimes do for operational reasons, or via misconfiguration/firewall gaps), the vulnerability is directly and trivially exploitable with a single crafted HTTP request.

### Recommendation
Enforce a maximum-body-size check comparable to `MAX_MESSAGE_LEN`/`MAX_PAYLOAD_LEN` before reading the body in `process_event`, e.g., check `Content-Length` from the request headers is present and below a cap and/or wrap `request.as_reader()` in a bounded reader (similar to `BoundReader` already used elsewhere in the codebase, see `stacks-common/src/util/retry.rs`) so `read_to_string` cannot allocate past the cap, mirroring the discipline already applied in `stackslib/src/net/api/*.rs`.

### Proof of Concept
1. Start a signer process with its event receiver bound to a reachable interface (per `SignerEventReceiver::bind`).
2. From an unauthenticated remote client, send:
```
POST /stackerdb_chunks HTTP/1.1
Host: <signer-ip>:<port>
Content-Type: application/json
Content-Length: <very large number, e.g. tens of GB>

<stream tens of GB of arbitrary bytes>
```
3. `process_event` calls `request.as_reader().read_to_string(&mut body)` [5](#0-4) , which attempts to buffer the entire payload before any JSON validation, exhausting process memory and crashing/OOM-killing the signer.
