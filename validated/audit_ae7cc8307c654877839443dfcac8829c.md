This confirms the key facts: the signer's `endpoint` in `mainnet-signer-conf.toml` is explicitly documented as `endpoint = "0.0.0.0:30000"` [1](#0-0) , meaning the operator-facing reference config binds the `SignerEventReceiver`'s HTTP listener to all interfaces, not just loopback, and there is no field in the signer's config (`auth_password`, secret, or TLS) that gates the *inbound* `/stackerdb_chunks` POST endpoint — `auth_password`/`auth_token` only protects the signer's outbound calls to the node's RPC, not inbound calls to the signer's own listener [2](#0-1) .

Now let's confirm the exact code path with no signature check for the miners branch, and the `StackerDBChunkData::recover_pk` used only in the signers branch, to nail down the asymmetry.### Title
Unauthenticated forged miner messages via `SignerEventReceiver`'s `/stackerdb_chunks` HTTP listener - (File: `libsigner/src/events.rs`)

### Summary
`SignerEventReceiver::next_event` accepts any HTTP POST to `/stackerdb_chunks` with no authentication whatsoever, and `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` deserializes `.miners` contract chunk data directly into `SignerEvent::MinerMessages` without ever calling `StackerDBChunkData::recover_pk` or any other signature check, unlike the parallel `.signer-XXX-YYY` branch which explicitly calls `chunk.recover_pk()`. Reference deployment configs bind this listener to `0.0.0.0`, so this is remotely reachable.

### Finding Description
The claimed equality is: every `SignerEvent::MinerMessages` entry consumed by the signer runloop should correspond to a message actually written by the miner into a StackerDB slot on the `.miners` boot contract (i.e., signed by the sortition-winning miner's key, as enforced by StackerDB slot-ownership signature checks at write time).

Tracing the code:
- `SignerEventReceiver::bind` simply opens a plain `HttpServer` on the configured address [3](#0-2) .
- `next_event` dispatches any POST to `/stackerdb_chunks` straight into `process_event::<T, StackerDBChunksEvent>(request)` with no header/secret/token check at all [4](#0-3) .
- `process_event` reads the raw body, JSON-decodes it into `StackerDBChunksEvent`, and calls `.try_into()` — again, no signature or provenance check on the bytes [5](#0-4) .
- In `TryFrom<StackerDBChunksEvent> for SignerEvent<T>`, the `.miners` branch iterates `event.modified_slots` and calls `T::consensus_deserialize(&mut chunk.data.as_slice())` directly, pushing the result into `SignerEvent::MinerMessages(messages)` — there is no call to `chunk.recover_pk()` or any equivalent signature verification in this branch [6](#0-5) . This is asymmetric with the `.signer-XXX-YYY` branch immediately below it, which does call `chunk.recover_pk()` and discards chunks whose signature fails to recover [7](#0-6) .

Normally, chunk signatures are checked by the node's StackerDB RPC/write path (e.g. `RPCPostStackerDBChunkRequestHandler`) and by P2P StackerDB sync before the node's `event_dispatcher` re-serializes and forwards the already-verified `StackerDBChunksEvent` to the signer's listener [8](#0-7) [9](#0-8) . That trust boundary depends entirely on nothing else being able to reach the signer's HTTP listener directly and on the listener itself validating the source. `SignerEventReceiver` does neither: it has no bearer-token/auth check on inbound POSTs, and the reference signer config explicitly documents `endpoint = "0.0.0.0:30000"` [1](#0-0) . The `auth_password`/`auth_token` pair only authenticates the signer's *outbound* calls to the node's RPC (block-proposal validation endpoint) — it is never checked on the *inbound* `/stackerdb_chunks` path in `events.rs` [2](#0-1) .

Attacker's exact message: connect to the signer's bound `endpoint` (e.g. `0.0.0.0:30000`), send `POST /stackerdb_chunks` with a JSON body `{"contract_id": <.miners boot contract id>, "modified_slots": [{"slot_id": N, "slot_version": V, "data": <arbitrary consensus-encodable SignerMessage bytes>, "sig": <garbage>}]}`. Because the `.miners` branch never validates `sig`, the forged message is pushed into `SignerEvent::MinerMessages` and forwarded to the signer runloop, exactly as in `stacks-signer/src/v0/signer.rs`'s `SignerEvent::MinerMessages(messages)` handler, which dispatches on message type (`BlockProposal`, `MockProposal`, `BlockPushed`, etc.) with no additional signature gate before calling handlers like `handle_block_proposal`/`mock_sign`/`handle_post_block` [10](#0-9) .

### Impact Explanation
An unauthenticated remote party who can reach the signer's bound event port can inject arbitrary, forged "miner" messages into the signer's runloop with no valid StackerDB slot signature at all — the `.miners` deserialization path performs zero signature verification, unlike the sibling `.signer-XXX-YYY` path. This is repeatable per-connection/per-POST. Whether this translates into an accepted block signature ultimately depends on downstream checks in `handle_block_proposal` (e.g. `recover_miner_pk` against the sortition winner) for the `BlockProposal` variant, but other `MinerMessages` variants (e.g. `MockProposal`, which triggers `mock_sign`) are acted upon directly from the unauthenticated payload. This matches "unauthenticated write to state"/"forged data" style impact on the signer's internal event stream, entering via the signer's own listening port rather than any legitimately-verified StackerDB write.

### Likelihood Explanation
Precondition is only that the attacker can open a TCP connection to the signer's `SignerEventReceiver` bind address. The maintained reference/sample config for this exact binary explicitly instructs operators to set `endpoint = "0.0.0.0:30000"` [1](#0-0) , i.e., listening on all interfaces by documented default guidance, with no secret required to talk to it. No node RPC secret, no signer key, and no StackerDB slot ownership is needed by the attacker — cost is a single crafted HTTP POST, fully repeatable.

### Recommendation
Add authentication to `SignerEventReceiver`'s inbound HTTP handling (e.g., require and check a shared secret/HMAC header matching `auth_password`/`auth_token` before processing any request), and additionally verify `chunk.recover_pk()` against the expected miner/slot-owner public key in the `.miners` branch of `TryFrom<StackerDBChunksEvent> for SignerEvent<T>` in `libsigner/src/events.rs`, mirroring the existing check in the `.signer-XXX-YYY` branch. Also update sample configs to default-bind the listener to `127.0.0.1` unless explicit remote access is required.

### Proof of Concept
Rust test plan (extending the existing `test_simple_signer` pattern in `libsigner/src/tests/mod.rs`):
1. Spawn a `SignerEventReceiver<SignerMessage>` bound to `127.0.0.1:<port>` via `Signer::spawn`, as done in `test_simple_signer` [11](#0-10) .
2. From a separate "attacker" thread (no relation to the mock node), open a raw `TcpStream::connect` to that port and send a hand-built HTTP request: `POST /stackerdb_chunks HTTP/1.1 ... <StackerDBChunksEvent JSON>` where `contract_id` is `boot_code_id(MINERS_NAME, false)` and `modified_slots` contains a `StackerDBChunkData { slot_id: 0, slot_version: 1, data: SignerMessage::MockProposal(..).serialize_to_vec(), sig: MessageSignature::empty() }` — i.e. never call `chunk.sign(&privk)`.
3. Assert that the resulting event received on the runloop's channel is `SignerEvent::MinerMessages(messages)` containing the attacker's `MockProposal`, proving the message was accepted and forwarded despite `sig` being empty/invalid — contrast with the `.signer-XXX-YYY` path where an equivalent unsigned/garbage-signed chunk is silently dropped by `chunk.recover_pk()` returning `Err`.

where
    T: SignerEventTrait,

    let mut body = String::new();

    if let Err(e) = request.as_reader().read_to_string(&mut body) {
        error!("Failed to read body: {:?}", &e);
        ack_dispatcher(request);
        return Err(EventError::MalformedRequest(format!(
            "Failed to read body: {:?}",
            e
        )));

    let json_event: E = serde_json::from_slice(body.as_bytes())
        .map_err(|e| EventError::Deserialize(format!("Could not decode body to JSON: {:?}", e)))?;

    let signer_event: SignerEvent<T> = json_event.try_into()?;

    Ok(signer_event)
}
