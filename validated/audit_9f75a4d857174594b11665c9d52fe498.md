Audit Report

## Title
Transaction-fee asset conversion in `SwapAssetAdapter` prices off manipulable AMM spot reserves with no TWAP or slippage bound - (`substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs`)

## Summary
`pallet-asset-conversion-tx-payment`'s `SwapAssetAdapter::withdraw_fee`/`can_withdraw_fee` convert a user's chosen fee-asset into the native fee using `pallet-asset-conversion`'s instantaneous constant-product reserves, with no TWAP, staleness check, or attacker-facing price-impact cap, and no way for the runtime to bound how far the ratio may have been pushed just before the extrinsic executes.

## Finding Description
`get_amount_in`/`get_reserves` in `substrate/frame/asset-conversion/src/lib.rs` read only the pool account's current token balances at execution time. `SwapAssetAdapter::withdraw_fee` in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs` calls `quote_price_tokens_for_exact_tokens` then immediately `swap_tokens_for_exact_tokens` on that same live state, with no user-supplied `amount_in_max`-style bound, unlike the general-purpose `swap_tokens_for_exact_tokens` extrinsic. The `QuotePrice` trait's own documentation states the quote is only valid "if no other swaps are made after the price is quoted and before the target swap," which this code path cannot enforce across extrinsic boundaries within a block.

## Impact Explanation
An attacker who moves a specific fee-paying pool's reserve ratio via ordinary `swap_exact_tokens_for_tokens`/`add_liquidity`/`remove_liquidity` calls in an earlier extrinsic can cause their own subsequent fee-in-asset extrinsic to be charged an amount of `asset_id` below the pool's pre-manipulation ratio, extracting value from the pool's liquidity providers, then reverse the position in a third extrinsic. This falls under "runtime bugs that compromise intended behavior" and, to the extent it degrades LP backing, the "theft ... of funds" impact class in the Polkadot SDK Impact Gate.

## Likelihood Explanation
Exploitability requires no privileged role — only self-ordered, permissionless extrinsics within a single block. However, because of the constant-product AMM's own fee/convexity structure, the manipulation-and-reversal round trip's cost (LP swap fees + price impact on both legs) scales with the capital needed to shift the ratio, while the benefit is capped by the (typically small) fixed native transaction fee being underpaid — bounding practical profitability to low-liquidity pools where this asymmetry is favorable. The report's likelihood assessment already accounts for this by scoping the realistic threat to "lower-liquidity, non-DOT pools."

## Recommendation
Add a caller-supplied maximum fee-asset amount (slippage bound) to `ChargeAssetTxPayment`/`OnChargeAssetTransaction::withdraw_fee`, and/or require the fee conversion to reference a time-weighted or otherwise smoothed price rather than the single-block spot reserve ratio, rejecting the transaction if the realized conversion price deviates beyond a configured tolerance from a longer-window reference price.

## Proof of Concept
1. Attacker holds asset `X` and native asset `N`, with a live `X`/`N` pool in `pallet-asset-conversion`.
2. Extrinsic 1 (attacker): swaps `N` for `X` in the pool, depleting the `X` reserve and inflating the `N` reserve, which per `get_amount_in`'s formula reduces the `X` amount required to buy a fixed `N` output.
3. Extrinsic 2 (attacker, same block): submits any call with `ChargeAssetTxPayment { asset_id: Some(X), .. }`; `SwapAssetAdapter::withdraw_fee` quotes and swaps `X → N` at the skewed ratio, charging less `X` than the pre-manipulation rate for the fixed native fee.
4. Extrinsic 3 (attacker, same block): reverse-swaps `X → N` to restore the ratio and recapture most of the capital deployed in step 2, net of AMM trading fees, keeping the extracted price difference as profit.
