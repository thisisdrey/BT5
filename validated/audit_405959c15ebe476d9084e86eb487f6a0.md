### Title
Reference-counter increment ("check-effects" guard) is applied after untrusted custom-hook execution instead of before, opening a repository-move/quarantine race window - (File: internal/gitaly/hook/prereceive.go)

### Summary
Gitaly's documented push-hook protocol requires that the "active push" reference counter be incremented **before** the access check and before any custom hooks run, so that concurrent operations (e.g. repository moves/deletions) can rely on the counter to know a push is in flight [1](#0-0) . The actual implementation in `GitLabHookManager.preReceiveHook` inverts this order: it calls `Allowed()`, then runs the (potentially long-running) custom `pre-receive` hook executor, and only afterwards calls `gitlabClient.PreReceive()` to increment the counter [2](#0-1) .

### Finding Description
This is the same root-cause pattern as the reported reentrancy bug: a state variable that is supposed to act as a guard/lock ("effect") is updated only *after* an external, attacker/administrator-influenced interaction has already executed, instead of before it ("check-effects-interactions" being violated in reverse — the *effect that establishes the guard* is deferred past the interaction it is meant to protect).

Concretely, in `preReceiveHook`:
1. `Allowed()` is called against Rails (network round-trip, non-trivial latency) [3](#0-2) .
2. The custom `pre-receive` hook is looked up and executed via `executor(...)`, which spawns an external process that runs for an indeterminate amount of time and can itself perform arbitrary I/O against the repository (which is still in the quarantine state at this point) [4](#0-3) .
3. Only after all of that completes does the code call `m.gitlabClient.PreReceive(ctx, repo.GetGlRepository())`, which increments the "push in flight" reference counter [5](#0-4) .

Per the documented design, this counter's entire purpose is to let other subsystems (e.g., repository-move/rename workflows) detect that a push is currently active before they act on the repository: "This hook first increments a reference counter that tracks how many pushes are active at the same time. Afterwards, it posts all changes to Rails' `/internal/allowed` API endpoint" [6](#0-5) . Because the real code defers the increment until after the access check and after custom-hook execution finishes, there is a window — bounded only by the latency of the `Allowed()` HTTP call plus the full runtime of the custom hook script — during which a push is fully underway (holding quarantined objects, having already been access-checked) but the counter has not yet been incremented to reflect that.

### Impact Explanation
During this window, any concurrent process that consults the reference counter to decide whether it is safe to move, rename, or otherwise mutate the repository (the documented purpose stated in `doc/hooks.md`: "Note: The reference is per repository so GitLab knows when a certain repository can be moved") will incorrectly conclude that no push is active. If such an operation proceeds on that basis while the quarantined push is still being validated/hooked, the repository can end up corrupted or lose objects supplied by the in-flight push, or the migrated push could race with a rename of the directory it is targeting. This is a genuine violation of the "hook and quarantine gating" invariant explicitly called out as in-scope, reachable purely by an ordinary user push (no privileged actor needed to trigger the race — only the ordinary Rails `Allowed()` latency and normal custom-hook runtime create the window; a slow custom hook merely widens it).

### Likelihood Explanation
The window exists on every single push through Gitaly's own hook manager (used by `PostReceivePack`, `SSHReceivePack`, and `OperationService` RPCs) and does not require a malicious custom hook — the ordinary latency of the `/internal/allowed` HTTP round trip already creates a small window. However, actually triggering the race requires a second, independent Gitaly-external actor (e.g., GitLab Rails' repository-storage-move logic) to check the same reference counter at just the wrong time, and that consumer of the counter lives outside the Gitaly repository, so the full impact cannot be independently confirmed from the Gitaly codebase alone — it depends on how Rails uses this counter to gate moves. This limits confidence versus a definitive proof and is likelihood-limiting information worth flagging.

### Recommendation
Move the `m.gitlabClient.PreReceive(...)` reference-counter increment call to occur immediately at the start of `preReceiveHook`, before the `Allowed()` call and before the custom-hook executor runs, matching the documented protocol in `doc/hooks.md`. Ensure the counter is reliably decremented (already done in `PostReceiveHook`) even on early-return error paths, so that the guard window covers the entire duration for which the push holds quarantined objects and is being validated/hooked.

### Proof of Concept
Not independently reproducible from the Gitaly codebase alone because the consumer of the reference counter (the repository-move gating logic) resides in GitLab Rails, outside this repository's scope. The vulnerable ordering itself is directly demonstrable by tracing the call sequence in `preReceiveHook`: `Allowed()` (network call) → custom hook `executor(...)` (external process, unbounded runtime) → `gitlabClient.PreReceive()` (counter increment) [2](#0-1) , which contradicts the intended ordering documented at [1](#0-0) .
