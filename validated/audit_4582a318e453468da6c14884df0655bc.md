### Title
Unpriced direct-transfer donation to a `pallet-asset-conversion` pool account can distort reserves and cause `InsufficientLiquidityMinted` DoS / value-loss for legitimate liquidity providers - (File: substrate/frame/asset-conversion/src/lib.rs)

### Summary
`pallet-asset-conversion` prices pools using the pool account's **full raw balance** rather than a value tracked purely through `add_liquidity`/`remove_liquidity` accounting. `get_balance` simply calls `T::Assets::balance(asset, owner)` [1](#0-0)  and this is confirmed by the pallet's own changelog, which states pool pricing now reads "full pool account balances" instead of reducible balances [2](#0-1) . Because any account can `transfer` assets directly to a pool's sovereign account without going through `add_liquidity`, an unprivileged attacker can donate tokens straight into the pool to skew `reserve1`/`reserve2` without minting any LP tokens — the same "direct balance donation vs. share accounting" primitive as the `StakedUSDe` `totalAssets() == balanceOf(this)` bug.

### Finding Description
`do_add_liquidity` computes reserves via `get_balance`, which reads the pool account's raw asset balance: [3](#0-2) 

When liquidity already exists, the pricing of a new deposit is entirely reserve-ratio based (`quote`, i.e. `amount * reserve2 / reserve1`) and the LP tokens minted are `min(side1, side2)` where `side = amount * total_supply / reserve`: [4](#0-3) 

The only floor protecting minters is `lp_token_amount > T::MintMinLiquidity::get()` [5](#0-4) , and the only supply-side protection against the classic zero-supply inflation attack is that `MintMinLiquidity` tokens are permanently minted to the pool account itself on first liquidity [6](#0-5) .

That lock only prevents `total_supply` from ever reaching zero again — it does **not** prevent an attacker from directly inflating `reserve1` or `reserve2` post-creation via a plain `Assets::transfer` to the pool's sovereign account (derived deterministically by `T::PoolLocator::address`), since `get_balance`/`get_reserves` read the full live balance, not an internally-tracked reserve variable. Right after pool creation, `total_supply` is still tiny (`MintMinLiquidity` + first depositor's minimal LP amount). An attacker who has just created the pool (or watches for a freshly created, thinly-funded pool) can:
1. Provide minimal initial liquidity (e.g., `amount1 = ED`, `amount2 = 1`), receiving `total_supply ≈ MintMinLiquidity + 1`.
2. Directly transfer a large amount of `asset2` into the pool account (no `add_liquidity` call, so no LP tokens minted, no `MintMinLiquidity` re-check).
3. This inflates `reserve2` relative to `total_supply` and relative to `reserve1`.

A subsequent honest depositor calling `add_liquidity` with an unaware `amount1_desired`/`amount2_desired` will have their contribution priced by `quote()` against the now-donated, skewed reserve ratio: `side1`/`side2 = amount * total_supply / reserve` will round toward zero because `total_supply` is minuscule relative to the inflated reserve. This either reverts with `Error::<T>::InsufficientLiquidityMinted` (denial of service on providing liquidity to that pool, exactly mirroring the `MinSharesViolation` DoS in the external report) or, in cases that don't revert, mints the victim a disproportionately small number of LP tokens for a large real contribution (value loss to the attacker/pool).

This is not a governance/privileged-actor issue — pool creation and asset transfers into the deterministic pool account are both permissionless operations available to any signed account.

### Impact Explanation
- **Denial of service on liquidity provisioning**: legitimate users depositing reasonable amounts into a freshly created, thinly-capitalized pool can be permanently blocked from adding liquidity via `Error::<T>::InsufficientLiquidityMinted`, mirroring the `MinShares`-style DoS class called out in the report.
- **Value misallocation**: in non-reverting edge cases, a victim's deposited assets are absorbed into the pool at an unfair price, effectively diluting/donating value to the attacker's existing LP position — this falls under "public underpriced work" / wrong-amount settlement in the impact gate.
- This is a core AMM invariant break: pool share price should only move through `add_liquidity`/`remove_liquidity`/swap accounting, not via out-of-band transfers to the sovereign account.

### Likelihood Explanation
Likelihood is highest immediately after a new pool is created and before deep liquidity accumulates, since `total_supply` is small and cheap to manipulate relative to the token's precision. Any account can create a pool (paying `PoolSetupFee`) and any account can transfer to the deterministic pool address computed by `T::PoolLocator::address`, so no privileged role, relayer, validator, or off-chain assumption is required — this is a pure public-entrypoint, single-actor attack.

### Recommendation
Track pool reserves as pallet-internal state that is only mutated by `do_add_liquidity`/`do_remove_liquidity`/swap extrinsics, rather than re-deriving reserves from the pool account's live `Assets::balance` on every call. If live-balance pricing must be retained for compatibility, enforce a minimum absolute liquidity-addition size (analogous to a "MinShares"/minimum-deposit guard) independent of the reserve ratio, and/or seed new pools with a much larger locked `MintMinLiquidity` relative to the smallest usable liquidity increment so ratio manipulation cannot force `mul_div` rounding to zero for realistic deposit sizes.

### Proof of Concept
1. Attacker calls `create_pool(asset1, asset2)` — permissionless, pays `PoolSetupFee`.
2. Attacker calls `add_liquidity(asset1, asset2, amount1_desired=ED, amount2_desired=1, ...)` — `total_supply` becomes `MintMinLiquidity + calc_lp_amount_for_zero_supply(ED,1)` (see `substrate/frame/asset-conversion/src/lib.rs:860-867` and `:1353-1368`).
3. Attacker calls `Assets::transfer(asset2, attacker, pool_account, LARGE_AMOUNT)` directly (not through the pallet) — `get_balance`/`get_reserves` now report a heavily skewed `reserve2` (see `substrate/frame/asset-conversion/src/lib.rs:1265-1269`, `813-814`).
4. Victim calls `add_liquidity(asset1, asset2, amount1_desired=X, amount2_desired=Y, amount1_min=..., amount2_min=...)` with reasonable, real-world amounts.
5. `quote()`/`mul_div()` (lines `1343-1382`) compute `side1`/`side2` against the tiny `total_supply` and inflated reserve, rounding to ≤ `MintMinLiquidity`, tripping `Error::<T>::InsufficientLiquidityMinted` (line `874-877`) and reverting the victim's deposit — or minting them a token amount far below the fair value of their contribution.

Note: I was not able to independently execute this scenario in a live test harness (no runtime execution available in this environment); the analysis is based on static code inspection of `substrate/frame/asset-conversion/src/lib.rs` and the pallet's changelog confirming full-balance-based pricing. Recommend a Devin session with test execution (`cargo test -p pallet-asset-conversion`) to confirm the exact revert/rounding behavior with concrete numbers before filing upstream.
