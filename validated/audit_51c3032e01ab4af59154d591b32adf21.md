### Title
Buyer can unintentionally accept the wrong offer during an L1 reorg and lose USDC or receive unintended loan NFTs - (File: tare-io__tare-contracts/contracts/LoansExchange.sol)

### Summary
`LoansExchange.acceptOffer(uint64 offerId)` settles an offer by its monotonic `offerId` without binding the call to the expected offer content. [1](#0-0)  A chain reorg can reorder `createOffer` transactions so the same `offerId` references a different `SaleOffer` (different `seller`, `loanIds`, or `price`). [2](#0-1)  Because `acceptOffer` only checks `msg.sender == offer.buyer` and the deadline, the buyer can be forced to settle an offer they never reviewed. [1](#0-0)  This is the same root cause as the MorphL2 `challengeState(batchIndex)` finding: an index is treated as a stable content reference when it is not. [3](#0-2) 

### Finding Description
The external seed bug violates the invariant that an action referencing shared state by index must be bound to the content of that state so a reorg cannot substitute different content at the same index. [3](#0-2)  In Tare, the exchange invariant is that offer acceptance must settle the exact offer the buyer reviewed (same `seller`, `loanIds`, and `price`). `createOffer` assigns `offerId = ++offerCount` and writes `_offers[offerId]` once. [4](#0-3) [5](#0-4)  `acceptOffer(offerId)` reads `offer.buyer`, `offer.price`, `offer.deadline`, and `offer.loanIds` from storage and executes the transfer. [1](#0-0)  The buyer provides no expected `loanIds`, `price`, or `seller` hash for the contract to verify against `_offers[offerId]`. [1](#0-0)  If two `createOffer` transactions from the same seller naming the same buyer are reordered in a reorg, the `offerId` the buyer intended now points to a different offer, and the acceptance succeeds because the buyer and deadline checks still pass. [1](#0-0)  `PortfolioVault.acceptSaleOffer` calls the same `exchange.acceptOffer(offerId)` and is therefore exposed as a buyer of last resort. [6](#0-5) 

### Impact Explanation
The corrupted value is `offer.price` and `offer.loanIds` read from `_offers[offerId]`. [7](#0-6)  The buyer’s USDC is pulled to the seller of the swapped offer at the swapped price, and the buyer receives loan NFTs they did not intend to purchase. [8](#0-7)  If the swapped offer has a higher price or less valuable collateral, the buyer suffers a direct loss. [8](#0-7)  This falls under the Tare allowed impact gate for theft or diversion of USDC from an honest user and material corruption of offer settlement that produces real value loss. 

### Likelihood Explanation
Exploitation requires an L1 reorg that reorders two or more `createOffer` transactions naming the same buyer. [2](#0-1)  The buyer must have submitted `acceptOffer(offerId)` based on a pre-reorg view of which offer occupied that ID. [9](#0-8)  Fast-finality chains reduce the practical frequency, but the contract invariant remains broken because the on-chain settlement is not bound to the offer content. [3](#0-2) 

### Recommendation
Change `acceptOffer` to accept the expected offer content (at minimum `loanIds`, `price`, and `seller`) and verify it against `_offers[offerId]` before transferring NFTs or currency. [1](#0-0)  This mirrors the MorphL2 mitigation of passing `batchHeader` and checking `committedBatches[_batchIndex] == _batchHash`.  Alternatively, have the seller sign an offer digest and require the buyer to pass the digest so the contract can verify the stored offer hash. 

### Proof of Concept
1. Seller `S` owns loan A (fair value 100 USDC) and loan B (fair value 1000 USDC). 
2. `S` registers buyer `B` as an investor for both and creates offer `O1`: `loanIds=[A]`, `price=100`, `buyer=B`. [2](#0-1)  In the original ordering `O1` receives `offerId=1`. [10](#0-9) 
3. `S` creates offer `O2`: `loanIds=[B]`, `price=1000`, `buyer=B`, which receives `offerId=2`. [2](#0-1) 
4. Buyer `B` observes `offerId=1` as "100 USDC for loan A" and submits `acceptOffer(1)`. [9](#0-8) 
5. An L1 reorg reorders the two `createOffer` calls: `O2` is now `offerId=1` and `O1` is `offerId=2`. [10](#0-9) 
6. `B`’s `acceptOffer(1)` succeeds against `O2` because `msg.sender == offer.buyer` and the deadline are valid. [11](#0-10) 
7. The exchange transfers loan B to `B` and pulls 1000 USDC from `B` to `S`. [8](#0-7) 
8. `B` paid 1000 USDC for loan B instead of 100 USDC for loan A, a 900 USDC loss relative to intent.

  function createOffer(
    address buyer,
    uint128 price,
    uint48 deadline,
    uint64[] calldata loanIds
  ) external whenNotPaused nonReentrant returns (uint64 offerId) {
    uint256 loanIdsLength = loanIds.length;
    require(loanIdsLength > 0 && loanIdsLength <= maxLoansPerOffer, InvalidLoanIdsLength());
    require(msg.sender != buyer && buyer != address(0), InvalidBuyer());
    require(deadline > block.timestamp, InvalidDeadline());
    require(ILoansAuth(address(LOANS)).isRegisteredForRole(msg.sender, Roles.Investor, buyer), BuyerNotRegistered());

    offerId = ++offerCount;

    for (uint256 i = 0; i < loanIdsLength; ++i) {
      uint64 loanId = loanIds[i];
      require(LOANS_NFT.ownerOf(uint256(loanId)) == msg.sender, NotLoanOwner());
      require(LOANS_NFT.getLocked(uint256(loanId)) == address(0), LoanLocked());

      LOANS_NFT.lock(address(this), uint256(loanId));
    }

    _offers[offerId] = SaleOffer({
      seller: msg.sender,
      buyer: buyer,
      price: price,
      deadline: deadline,
      loanIds: loanIds
    });

    emit OfferCreated(offerId, msg.sender, buyer, price, deadline, loanIds);
  }

  function acceptOffer(uint64 offerId) external whenNotPaused nonReentrant {
    SaleOffer storage offer = _offers[offerId];

    // An inactive offer has `buyer == address(0)`, which `msg.sender` can never equal.
    require(msg.sender == offer.buyer, NotOfferRecipient());
    require(block.timestamp <= offer.deadline, OfferExpired());

    address seller = offer.seller;
    uint128 price = offer.price;

    require(ILoansAuth(address(LOANS)).isRegisteredForRole(seller, Roles.Investor, msg.sender), BuyerNotRegistered());
    require(ILoansAuth(address(LOANS)).isRegisteredForRole(msg.sender, Roles.Investor, seller), SellerNotRegistered());

    uint64[] memory loanIds = _removeOffer(offerId);

    // Send Loan NFTs to the buyer first, before any cash moves.
    uint256 loanIdsLength = loanIds.length;
    for (uint256 i = 0; i < loanIdsLength; ++i) {
      LOANS_NFT.transferFrom(seller, msg.sender, uint256(loanIds[i]));
    }

    // Pull currency from the buyer to the seller last.
    if (price > 0) {
      CURRENCY.safeTransferFrom(msg.sender, seller, uint256(price));
    }

    emit OfferAccepted(offerId, seller, msg.sender, price);
  }

**114. Insufficient Block Confirmations / Reorg Double-Spend**

- **D:** DVN relays cross-chain message before source chain reaches finality. Attacker deposits on source chain, gets minted on destination, then causes a reorg on source chain (or the chain reorgs naturally) to reverse the deposit while keeping minted tokens. - **FP:** Confirmation count matches or exceeds chain-specific finality guarantees. Chain has fast finality (e.g., Ethereum post-merge ~12 min). DVN waits for finalized blocks.
