## Finding

### Title
CREATE1 contract address computed during dry-run/RPC simulation does not match the address produced by the actual on-chain transaction - (File: `substrate/frame/revive/src/exec.rs`)

### Summary
`pallet-revive`'s `Stack::new_frame` computes the deterministic address of a to-be-instantiated contract using `address::create1(deployer, nonce)` when no salt is supplied. The nonce used depends on whether the call originates from a dry run (state-mutation-free RPC/runtime-API simulation) or a real dispatched extrinsic, but the code only adjusts for the "already incremented nonce" case via `origin_is_caller`, without distinguishing dry-run execution context from real transaction execution. This is exactly the mismatch class described in the external report: a locally re-derived address diverges from the address the system will actually bind funds/contract state to, causing reliance on the "predicted" address to break.

### Finding Description
In `substrate/frame/revive/src/exec.rs`, `Stack::new_frame` computes the instantiation address as: [1](#0-0) 

```rust
FrameArgs::Instantiate { sender, executable, salt, input_data } => {
    let deployer = T::AddressMapper::to_address(&sender);
    let account_nonce = <System<T>>::account_nonce(&sender);
    let address = if let Some(salt) = salt {
        address::create2(&deployer, executable.code(), input_data, salt)
    } else {
        use sp_runtime::Saturating;
        address::create1(
            &deployer,
            // the Nonce from the origin has been incremented pre-dispatch, so we
            // need to subtract 1 to get the nonce at the time of the call.
            if origin_is_caller {
                account_nonce.saturating_sub(1u32.into()).saturated_into()
            } else {
                account_nonce.saturated_into()
            },
        )
    };
```

The subtraction of 1 is only correct when the call is happening as part of an actual dispatched extrinsic, where `System::account_nonce` has already been incremented pre-dispatch (as noted in the comment). During a dry-run (e.g. a runtime-API/RPC simulation used by `eth_estimateGas`, `eth_call`, or off-chain address prediction tooling that calls into `bare_instantiate`/the runtime call API without going through the real pre-dispatch nonce-increment pipeline), the nonce has NOT been incremented, so subtracting 1 yields the wrong nonce, and thus a different `create1` address than what the real submitted transaction will produce.

This is confirmed by `prdoc/stable2506/pr_8504.prdoc`, which documents this exact bug ("Fix generated address returned by Substrate RPC runtime call") and states the intended fix is to gate the subtraction on `matches!(exec_context, ExecContext::Transaction)`: [2](#0-1) 

However, this repository's `exec.rs` still contains only the unconditional `origin_is_caller` check and no `ExecContext`/dry-run gating anywhere in the codebase — a search for `ExecContext` and `origin_is_caller` shows they only appear in the prdoc description and in the unfixed `exec.rs` code, confirming the described fix was never actually applied to the executable code path. [3](#0-2) 

`ExecConfig` does carry `is_dry_run` context used elsewhere (e.g. for timestamp overrides), but this context is not consulted in the address-derivation branch, so the dry-run/real-transaction distinction that the surrounding comment assumes is missing exactly where address determinism matters.

### Impact Explanation
Any unprivileged user (or any Ethereum-compatible RPC client, wallets, or contracts) that queries the predicted contract address for a `CREATE`-style instantiation via a dry run and then relies on that address (to pre-fund it, to reference it from another contract's constructor arguments, to whitelist it, or to hand it to a counterpart before the real transaction lands) will get an address that does not match the address the chain actually deploys the contract to once the real transaction executes. This mirrors the reported bug class exactly: a value computed via one deterministic derivation formula does not match the value the authoritative path produces, breaking any code/flow that assumed address parity between simulation and execution — potentially causing funds sent to the "predicted" address to be unrecoverable/misdirected, or downstream logic (e.g. constructor arguments baking in a wrong callee address) to permanently break.

### Likelihood Explanation
This does not require a malicious peer, validator, collator, or admin — it is triggered purely by normal usage patterns (dry-run/gas-estimation RPC calls followed by a real transaction) that are standard in EVM-compatible tooling (MetaMask, ethers.js, viem `eth_estimateGas`/`eth_call` simulate-then-send flows). The condition is deterministic and reproducible any time an unsalted `CREATE` instantiation's nonce path differs between a runtime-API dry run and a real dispatched extrinsic.

### Recommendation
Thread the actual `ExecContext` (dry-run vs. transaction) into `Stack::new_frame`/`FrameArgs::Instantiate` and only apply the `saturating_sub(1)` nonce adjustment when executing as part of a real dispatched transaction, matching the fix already documented (but not implemented in this codebase) in `prdoc/stable2506/pr_8504.prdoc`. Add a regression test (e.g. `nonce_not_incremented_in_dry_run`) asserting dry-run and real-transaction `create1` addresses are identical for the same sender/nonce state.

### Proof of Concept
1. Call the `pallet-revive` bare-instantiate / runtime API dry-run path (e.g. `bare_instantiate` used by RPC gas estimation) with `salt = None`, for a sender whose current on-chain nonce is `N`. The dry-run path does not increment the nonce pre-call, so `account_nonce == N`. Since `origin_is_caller` is true for a top-level instantiate call, the code computes `create1(deployer, N - 1)`.
2. Submit the real signed extrinsic performing the same instantiation. Pre-dispatch nonce increment sets `account_nonce == N + 1` by the time `new_frame` runs, and the same `origin_is_caller` branch computes `create1(deployer, N + 1 - 1) = create1(deployer, N)`.
3. Compare the two addresses: `create1(deployer, N - 1) != create1(deployer, N)` — the dry-run predicted address and the actually-deployed address differ, reproducing the "computed address does not match deployed address" defect described in the external report. [4](#0-3)

    ## Review Notes

    This PR adds a new condition to check for the `ExecContext` when calculating the nonce for address derivation:

    ```rust
    address::create1(

        // need to subtract 1 to get the nonce at the time of the call.
        if origin_is_caller && matches!(exec_context, ExecContext::Transaction) {
            account_nonce.saturating_sub(1u32.into()).saturated_into()
        } else {
            account_nonce.saturated_into()
        },
    )

/// Determine the address of a contract using CREATE semantics.
pub fn create1(deployer: &H160, nonce: u64) -> H160 {
	let mut list = rlp::RlpStream::new_list(2);
	list.append(&deployer.as_bytes());
	list.append(&nonce);
	let hash = keccak_256(&list.out());
	H160::from_slice(&hash[12..])
}
