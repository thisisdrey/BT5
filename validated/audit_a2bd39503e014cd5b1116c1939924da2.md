### Title
Floating-point precision loss in the default (non-hardened) TRC10 Bancor-style Exchange pricing formula enables value extraction / price-crash attacks analogous to AMM flash-loan exploits - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

### Summary
java-tron implements an on-chain, Bancor-style constant-relay-supply AMM ("Exchange") for TRC10 tokens, reachable by any unprivileged, signed `ExchangeTransactionContract` (and `ExchangeInjectContract`/`ExchangeWithdrawContract`) via `ExchangeTransactionActuator`. The default (non-hardened) execution path computes swap output using `double`-precision `Math.pow` in `ExchangeProcessor`, rather than the newer `BigDecimal`-based `SafeExchangeProcessor` that is only activated when the `allowHardenExchangeCalculation` dynamic property is turned on via a committee proposal. Because this feature is opt-in and off by default, the historically vulnerable floating-point formula remains the live consensus path for TRC10 Exchange swaps today.

### Finding Description
The swap math lives in `ExchangeCapsule.transaction()`: [1](#0-0) 

which selects between `ExchangeProcessor` (default) and `SafeExchangeProcessor` (only if `hardenedCalc` is true), and `hardenedCalc` is derived from `allowHarden()`: [2](#0-1) 

The default processor performs the Bancor relay calculation entirely in IEEE-754 `double` arithmetic: [3](#0-2) 

`exchangeToSupply`/`exchangeFromSupply` truncate to `long` via `(long) issuedSupply` / `(long) exchangeBalance`, and there is no bound on how small a trade can be or how many trades can be executed against the same pool within a block. Both the pool balances and the internal `supply` accumulator drift with every truncation. An attacker who repeatedly calls `ExchangeTransactionActuator` with carefully chosen `quant` values (each individually validated only by the `expected` slippage floor the caller itself controls) can exploit rounding bias across many small/edge-case trades to extract more value than economically justified from `firstTokenBalance`/`secondTokenBalance`, or conversely crash the quoted price of a thinly-liquidity TRC10 asset by repeatedly draining one side of the pool — the same fundamental bug class as the reported FCN-TRUST incident, where an attacker manipulates an AMM-style pool's internal price/reserve accounting through a rapid sequence of trades funded temporarily (a "flash loan" is not even required here, since TRON's protocol lets the attacker issue any number of transactions from their own account within the same or adjacent blocks before other participants can react).

Validation in `ExchangeTransactionActuator.doValidate()` only enforces the caller-supplied `expected` minimum output and an overall pool balance ceiling (`getExchangeBalanceLimit`) — it does not protect against precision drift accumulating across a sequence of trades, nor does it enforce any minimum trade size to prevent adversarial rounding: [4](#0-3) 

The fact that a parallel `SafeExchangeProcessor` using `BigDecimal` with explicit rounding modes was introduced specifically as a gated ("hardened") alternative is itself evidence that the double-based path has known precision-safety problems: [5](#0-4) 

Because `allowHardenExchangeCalculation` must be explicitly enabled by a committee proposal, and there is no evidence in this codebase that it is enabled by default, every TRC10 Exchange created and traded under default settings runs the unaudited, floating-point-precision-vulnerable path indefinitely.

### Impact Explanation
Any TRC10 asset issuer can create an Exchange pool via `ExchangeCreateActuator`, and any unprivileged account can inject liquidity and execute swaps against it. Sustained exploitation of floating-point rounding in `ExchangeProcessor` allows an attacker to (a) siphon TRX/TRC10 balances out of the pool beyond what correct Bancor math would allow (unbacked-balance extraction, direct theft of funds from other liquidity participants), and/or (b) collapse the quoted exchange rate of a token by repeatedly draining one side of the pool — mirroring the reported real-world impact ("price crash by 99%", "$504k loss") on a functionally equivalent Bancor/AMM design. This is a concrete theft-of-funds / unbacked-balance vector reachable purely through ordinary signed transactions.

### Likelihood Explanation
The attack requires only: (1) a TRC10 Exchange to exist (created by anyone via `ExchangeCreateActuator`), and (2) the ability to submit ordinary signed `ExchangeTransactionContract` transactions — both of which are available to any unprivileged network participant with minimal TRX for fees. No special privileges, witness/SR status, or off-chain conditions are needed. The severity of the drain depends on pool liquidity depth and the number of transactions the attacker can push through, but the underlying arithmetic weakness is deterministic and repeatable on any pool while `allowHardenExchangeCalculation` remains disabled.

### Recommendation
- Default `allowHardenExchangeCalculation` to enabled (or remove the flag entirely and always use `SafeExchangeProcessor`) so all TRC10 Exchange swaps use bounded-precision `BigDecimal` arithmetic with explicit rounding, consistent with `hardenedSuccessExchangeTransaction` test coverage.
- Add minimum trade-size and maximum trade-frequency-per-block/per-account safeguards in `ExchangeTransactionActuator.doValidate()` to prevent rounding-bias accumulation from many small trades.
- Add invariant checks after each `transaction()` call ensuring `firstTokenBalance * secondTokenBalance` cannot decrease (a k-invariant check similar to constant-product AMMs) to catch/reject any trade that would extract value inconsistent with the Bancor formula due to floating-point drift.

### Proof of Concept
1. Issue two TRC10 tokens and create an Exchange pool via `ExchangeCreateContract` with modest reserves (e.g., `firstTokenBalance = 100_000_000`, `secondTokenBalance = 100_000_000`), leaving `allowHardenExchangeCalculation` at its default (disabled) value.
2. From an unprivileged account, submit a rapid sequence of `ExchangeTransactionContract` transactions with small, carefully chosen `quant` values chosen to maximize truncation bias in `exchangeToSupply`/`exchangeFromSupply` (`(long) issuedSupply` / `(long) exchangeBalance` in `ExchangeProcessor`), each satisfying the attacker's own `expected` floor.
3. Repeat across many blocks/transactions; observe that the cumulative `anotherTokenQuant` extracted from the pool, or the resulting pool exchange rate, diverges from what the exact Bancor formula (as computed by `SafeExchangeProcessor`) would yield — draining reserves disproportionately and/or collapsing the quoted price, replicating the reported FCN-TRUST-style price crash and value extraction.

  private BigDecimal exchangeToSupply(long balance, long quant) {
    long newBalance = StrictMathWrapper.addExact(balance, quant);
    BigDecimal bdQuant = BigDecimal.valueOf(quant);
    BigDecimal bdNewBalance = BigDecimal.valueOf(newBalance);
    BigDecimal base = BigDecimal.ONE.add(
        bdQuant.divide(bdNewBalance, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 0.0005);
    return SUPPLY.negate().multiply(
        BigDecimal.ONE.subtract(BigDecimal.valueOf(powResult))).setScale(0, RoundingMode.DOWN);
  }

  private long exchangeFromSupply(long balance, BigDecimal supplyQuant) {
    BigDecimal bdBalance = BigDecimal.valueOf(balance);
    BigDecimal base = BigDecimal.ONE.add(
        supplyQuant.divide(SUPPLY, 18, RoundingMode.HALF_UP));
    double powResult = StrictMathWrapper.pow(base.doubleValue(), 2000.0);
    BigDecimal exchangeBalance = bdBalance.multiply(
        BigDecimal.valueOf(powResult).subtract(BigDecimal.ONE));
    return exchangeBalance.setScale(0, RoundingMode.DOWN).longValueExact();
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    BigDecimal relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
