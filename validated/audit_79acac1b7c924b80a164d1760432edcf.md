## Finding: `ValidateMultiSign` TVM Precompile Double-Counts Malleable ECDSA Signatures, Bypassing Multisig Threshold

### Title
Signature-malleability double-counting in `ValidateMultiSign` precompile allows single-key threshold bypass - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
The `ValidateMultiSign` TVM precompiled contract, reachable by any smart-contract call via `TriggerSmartContract`, deduplicates signer contributions using the *raw signature bytes* concatenated with the recovered address rather than the recovered address alone. Because ECDSA signature validation in this codebase does not enforce canonical low-`s` (no malleability rejection), a single private key can produce two distinct, independently-valid 65-byte signatures over the same hash. Both signatures recover to the same address but are treated as two "different" approvals, so their weights are summed twice. This lets one key satisfy a multisig threshold that is supposed to require multiple independent signers — an authorization bypass conceptually identical to the reported bug class (an alternate/legacy-shaped payload defeats an intended per-identity gating check).

### Finding Description
`ValidateMultiSign.execute` iterates over the caller-supplied signature array and tracks already-counted signers in `executedSignList`: [1](#0-0) 

The dedup check is:
```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
... totalWeight += weight; executedSignList.add(sign); executedSignList.add(recoveredAddr);
```
If `recoveredAddr` was already counted but the exact `sign` bytes differ, the code does **not** skip — it falls through and adds the weight again. This is exploitable because ECDSA signature verification here only checks `r,s ∈ [1, N)` and `v ∈ {27,28}`; it does **not** reject the malleable counterpart `(r, N-s, v')`, as shown by `ECDSASignature.validateComponents`: [2](#0-1) 

`recoverAddrBySign`, used by the precompile, calls exactly this `validateComponents()` check with no canonicalization requirement: [3](#0-2) 

Thus, for any private key and any hash, an attacker can compute two valid signatures `(r,s,v)` and `(r, N-s, v_flipped)` — both pass `validateComponents()`, both recover to the same address, but their raw bytes differ, so both increment `totalWeight` by the signer's full weight.

This is the exact class of bug the `TransactionCapsule.checkWeight` path used to have: prior to fork `VERSION_4_7_1` it deduplicated by base64-encoded signature bytes rather than by recovered address, and was explicitly fixed to key on the recovered address instead: [4](#0-3) 

The `ValidateMultiSign` TVM precompile never received the equivalent fix — it still dedups on `(address, signature-bytes)` pairs instead of address alone, leaving the legacy vulnerable pattern reachable from any contract call.

### Impact Explanation
`ValidateMultiSign` exists specifically so on-chain smart contracts (e.g., multisig wallets, DAOs, custody contracts) can verify that a threshold of independent keys authorized an action before releasing funds or executing privileged logic. Any such contract that relies on this precompile's boolean result to gate a withdrawal, approval, or governance action can have its threshold defeated by a single signer providing two malleable signatures for the same message, causing the precompile to report the threshold as met when it was not. This constitutes unauthorized approval of a fund-moving or privileged operation gated by multisig logic — a concrete unauthorized-account-operation / theft-of-funds impact for any contract built on this precompile.

### Likelihood Explanation
Trivially reachable: any address can deploy or call a contract that invokes the `ValidateMultiSign` precompile via a normal `TriggerSmartContract` transaction, and computing the malleable counterpart signature `(r, N-s, v')` for a given `(r,s,v)` requires only elementary big-integer arithmetic (`s' = N - s`) — no private key material or advanced cryptanalysis needed once the caller already controls the key that produced the first signature.

### Recommendation
Change the dedup key in `ValidateMultiSign.execute` from `(recoveredAddr, sign)` to `recoveredAddr` alone, mirroring the fix already applied to `TransactionCapsule.checkWeight` after fork `VERSION_4_7_1`: once an address has contributed weight, any further signature recovering to that same address must be skipped regardless of its raw byte encoding. Additionally, consider rejecting non-canonical (high-`s`) signatures at `validateComponents()`/`recoverAddrBySign` to eliminate malleable duplicates at the source.

### Proof of Concept
1. Deploy (or use) a contract that calls the `ValidateMultiSign` precompile address with a target account/permission requiring `threshold = 2` across two distinct keys (or even threshold 2 with one key weighted 1, since malleability lets that one key count as 2).
2. Sign the ABI-encoded `(address, permissionId, hash)` payload once with key `K` to get `(r, s, v)`.
3. Compute the malleable counterpart `(r, N-s, v_flipped)` where `N` is the secp256k1 curve order — this is a valid, independently-recoverable signature for the same key and hash.
4. Submit both `(r,s,v)` and `(r,N-s,v')` as the two entries in the `bytes[] signatures` argument.
5. `ValidateMultiSign.execute` recovers the same address twice, but since the raw signature bytes differ, `executedSignList` dedup by `(addr, sign)` fails to suppress the second entry, and `totalWeight` is doubled — satisfying a 2-of-N threshold with a single key. [5](#0-4)

    public static boolean validateComponents(BigInteger r, BigInteger s,
        byte v) {

      if (v != 27 && v != 28) {
        return false;
      }

        return false;
      }
      if (BIUtil.isLessThan(s, BigInteger.ONE)) {
        return false;
      }

        return false;
      }
