Audit Report

## Title
Bounty payout silently fails below the existential deposit, permanently stranding funds in the bounty sub-account - (File: `substrate/frame/bounties/src/lib.rs`)

## Summary
`Pallet::claim_bounty` computes `payout = balance.saturating_sub(fee)` and transfers both the curator fee and beneficiary payout via `T::Currency::transfer(..., AllowDeath)`, checking the result only with `debug_assert!(res.is_ok())`, which is compiled out in release builds. Regardless of transfer success, the bounty entry is unconditionally deleted via `*maybe_bounty = None;` immediately afterward, so a sub-existential-deposit transfer failure (`TokenError::BelowMinimum`) leaves funds permanently stranded in the bounty's derived sub-account with no on-chain state referencing them. The identical pattern exists in `claim_child_bounty` in `substrate/frame/child-bounties/src/lib.rs`.

## Finding Description
`claim_bounty` in `substrate/frame/bounties/src/lib.rs` (lines 796-844) is dispatchable by any signed account once a bounty is in `PendingPayout` status (`ensure_signed(origin)?; // anyone can trigger claim`, line 800). It computes `let payout = balance.saturating_sub(fee);` (line 811), then performs two `T::Currency::transfer(..., AllowDeath)` calls (lines 822 and 825), guarding each only with `debug_assert!(res.is_ok())` (lines 823, 826). Immediately after, regardless of whether either transfer actually succeeded, the code executes `*maybe_bounty = None;` (line 828), followed by `BountyDescriptions::<T, I>::remove(bounty_id);` and `T::ChildBountyManager::bounty_removed(bounty_id);` (lines 830-831) — deleting the only state referencing the bounty's sub-account balance.

`pallet_balances` enforces that any transfer resulting in a destination balance below `ExistentialDeposit` for a non-existent account returns `Err(TokenError::BelowMinimum)` rather than succeeding, as shown by the existing balances test (`default_indexing_on_new_accounts_should_not_work2`). In a release build (where `debug_assert!` is a no-op), this error is silently discarded rather than propagated, so `claim_bounty` proceeds to unconditionally delete the bounty record even though the transfer failed and the funds remain in `bounty_account`.

## Impact Explanation
This falls under the permanent user-fund lock impact category: value that should settle to the beneficiary (or curator) is instead stranded irrecoverably in the bounty's `PalletId`-derived sub-account after the only pointer to that balance (the `Bounties` storage entry) is deleted in the same transaction, with no governance or retry path to recover it, unlike newer pallets (`pallet-multi-asset-bounties`) that model payment failure explicitly via `PayoutAttempted`/retry mechanisms.

## Likelihood Explanation
Triggering requires only that a bounty reach `PendingPayout` with a resulting `payout` (or `final_fee`) below the chain's `ExistentialDeposit` for a beneficiary/curator account that doesn't yet exist — a plausible, easily arranged configuration for low-value bounties or bounties whose value is mostly consumed by curator fee, especially on chains with non-trivial ED. Since `claim_bounty` is permissionless (any signed account can call it), any observer can trigger the loss once such a bounty exists in `PendingPayout` state, and this depends on the runtime being built in release mode where `debug_assert!` compiles to a no-op.

## Recommendation
Propagate the `DispatchResult` of both `T::Currency::transfer` calls with `?` instead of `debug_assert!`, and only clear the `Bounties`/`BountyDescriptions` storage (and analogous `ChildBounties` storage) after both transfers succeed. Alternatively, floor `payout`/`final_fee` at the `ExistentialDeposit`, or reject bounty award/claim combinations that would produce a sub-ED payout to a non-existent account.

## Proof of Concept
1. Configure a chain with a non-trivial `ExistentialDeposit = ED`.
2. Create and fund a bounty via `propose_bounty`/`approve_bounty`, then `award_bounty`, with `value` and `fee` chosen so that `payout = value - fee < ED`, and `beneficiary` set to a fresh account with zero balance.
3. Wait for `unlock_at` (the payout delay) to elapse.
4. Have any signed account call `claim_bounty(bounty_id)`.
5. In a release build, `T::Currency::transfer(&bounty_account, &beneficiary, payout, AllowDeath)` at `substrate/frame/bounties/src/lib.rs` line 825 returns `Err(TokenError::BelowMinimum)`, discarded by the no-op `debug_assert!` at line 826.
6. `*maybe_bounty = None;` (line 828) executes unconditionally, deleting the bounty and its description.
7. The `payout` amount remains stuck in `bounty_account` with no remaining on-chain reference or recovery path.
