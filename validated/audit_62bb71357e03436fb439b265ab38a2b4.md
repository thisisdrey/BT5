## Title
Non-deterministic floating-point math in the TRC10 Bancor-curve `ExchangeProcessor` causes consensus divergence and incorrect swap accounting - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeProcessor.java`)

## Summary
The C4 finding flags that ABDKMathQuad — a fixed-precision quad-math library used to compute a bonding-curve formula — produces small, edge-case-dependent rounding errors that a fuzzer (Echidna) could surface, and recommends fuzzing to close the gap between mathematically expected and actually computed curve outputs. java-tron has the exact same class of bug in its own bonding-curve exchange engine: `ExchangeProcessor` computes the Bancor-formula swap output using raw IEEE-754 `double` exponentiation (`Math.pow`/`StrictMath.pow`) instead of arbitrary/fixed precision arithmetic, and the platform-specific implementations of that primitive are demonstrably inconsistent with each other.

## Finding Description
`ExchangeProcessor.exchangeToSupply` / `exchangeFromSupply` implement the Bancor relay-token formula entirely in `double` precision, calling `Maths.pow(base, exponent, useStrictMath)`: [1](#0-0) 

`Maths.pow` dispatches to either `StrictMathWrapper.pow` (`StrictMath.pow`) or the legacy, platform-specific `MathWrapper.pow`: [2](#0-1) 

Critically, the two platform builds of `MathWrapper.pow` are **not equivalent**:
- On x86, `MathWrapper.pow` calls raw `Math.pow`, which is intrinsic/JIT-optimized and not guaranteed bit-identical to `StrictMath.pow`: [3](#0-2) 
- On ARM, `MathWrapper.pow` returns `StrictMath.pow` by default but overrides it with a hand-maintained lookup table of previously observed *mismatches* between the two, keyed to specific historical mainnet block heights: [4](#0-3) [5](#0-4) 

The presence of dozens of hard-coded `addPowData(...)` entries tied to specific mainnet block numbers is direct evidence that `Math.pow` (x86) and `StrictMath.pow` (ARM default) have already diverged in production for real `ExchangeProcessor` inputs — this is precisely the "small difference... probably the same with all the other operations" issue the external report describes for ABDKMathQuad, except here it manifests as **cross-platform consensus divergence** rather than a one-off precision loss.

The vulnerable legacy path is still the default: `allowHardenExchangeCalculation` (which switches to the `BigDecimal`-based `SafeExchangeProcessor`) defaults to `0`/off unless a committee proposal enables it: [6](#0-5) 

and `useStrictMath` is likewise gated by the `ALLOW_STRICT_MATH` chain parameter which must be separately proposed and activated: [7](#0-6) 

Any unprivileged account can trigger this code path simply by broadcasting an `ExchangeTransactionContract`, `ExchangeInjectContract`, or `ExchangeWithdrawContract` transaction: [8](#0-7) 

The project's own tests confirm the plain double-based path yields a *different* result than both the strict-math path and the `BigDecimal` "safe" path for identical inputs: [9](#0-8) 

## Impact Explanation
Because `ExchangeProcessor.exchange()` runs during ordinary block/transaction execution (not just query paths), any divergence between `Math.pow` and `StrictMath.pow` on differing CPU architectures/JIT builds for a *new* (not yet catalogued in the ARM lookup table) input pair will cause full nodes to compute different `anotherTokenQuant`, hence different account balances and a different state root for the *same* block — a chain split between x86 and ARM-based full nodes. Independently of architecture, the reliance on lossy `double` arithmetic for a curve that manages real TRX/TRC10 reserves means computed swap outputs can silently deviate from the mathematically correct Bancor value, allowing swap results that do not conserve/back the pool invariant (unbacked balance / value drained from or stuck in the exchange pool), matching the "theft or permanent freezing of funds" and "chain split" impact classes.

## Likelihood Explanation
The vulnerable path (`useStrictMath=false`, `allowHardenExchangeCalculation=false`) is the chain's **default state** and requires no attacker privilege — any account can create an `ExchangeCreateContract` pool and drive `ExchangeTransactionContract`/`ExchangeInjectContract`/`ExchangeWithdrawContract` transactions with balances/quantities chosen to land on `pow` inputs likely to diverge (values close to representable-precision boundaries), similar to how Echidna found edge cases for ABDKMathQuad. The ARM `MathWrapper` patch table, itself built from *already observed* mainnet divergences across dozens of block heights, is empirical proof this is not merely theoretical.

## Recommendation
- Replace the `double`-based Bancor curve computation in `ExchangeProcessor` with the deterministic `BigDecimal`/fixed-point implementation already present in `SafeExchangeProcessor`, and make it the default for all new pools rather than an opt-in chain parameter.
- Enforce `StrictMath` (or an equivalent deterministic software pow implementation) unconditionally rather than allowing an x86-specific `Math.pow` code path to remain in any consensus-critical computation.
- Fuzz `ExchangeProcessor`/`SafeExchangeProcessor` (e.g., with edge-case reserve ratios and extreme quantities) the way the report recommends for ABDKMathQuad, to find and eliminate any remaining precision divergences before further activation of `ALLOW_STRICT_MATH`/`ALLOW_HARDEN_EXCHANGE_CALCULATION`.

## Proof of Concept
1. Run two full nodes built from the `x86` and `arm` platform variants respectively (`platform/src/main/java/x86/.../MathWrapper.java` vs `platform/src/main/java/arm/.../MathWrapper.java`).
2. Create a TRC10 exchange pool via `ExchangeCreateContract`, then submit an `ExchangeTransactionContract` with sell/buy reserve values and `sellTokenQuant` chosen (via brute-force/fuzzing, akin to the Echidna approach in the report) such that `Math.pow(base, 0.0005)`/`Math.pow(base, 2000.0)` on x86 differs in its lowest mantissa bits from `StrictMath.pow` on ARM, for an input **not already present** in the ARM `powData` compatibility table.
3. Observe that `exchangeToSupply`/`exchangeFromSupply` truncate the resulting `double` to `long` (`(long) issuedSupply`, `(long) exchangeBalance`) in `ExchangeProcessor.java` (lines 17-39), so even a single-ULP difference in the `pow` result can flip the truncated integer output, producing different `anotherTokenQuant`, different account/pool balances, and a diverging state root between the two nodes for the identical block — demonstrating the chain-split risk described above.

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }
