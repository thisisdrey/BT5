This confirms the mechanism. The `caller_deposit` is the "relayer" pattern: an external account (predecessor != current_account_id, meaning a relayer submitting on behalf of the wallet owner) attaches a NEAR deposit to `rlp_execute` via the `#[payable]` attribute, and `CallerDeposit::new` at [1](#0-0)  tracks this so it can be refunded if the downstream cross-contract call fails.

For an `ERC20Transfer`, `inner_rlp_execute` constructs a promise chain that first calls `storage_balance_of` on the token contract with a hard gas limit of `NEP_141_STORAGE_BALANCE_OF_GAS` (5 Tgas), then `.then()`s into `nep_141_storage_balance_callback` [2](#0-1) . If the target token's `storage_balance_of` costs more than 5 Tgas, that promise fails, and the callback's `PromiseResult::Failed` arm returns early without ever inspecting or refunding `caller_deposit`: [3](#0-2) . This is asymmetric with `rlp_execute_callback`'s `Failed` arm, which explicitly issues `env::promise_batch_action_transfer` to refund `caller_deposit` before returning failure: [4](#0-3) .

Since NEAR attaches the deposit to the contract's own balance upon receipt of the `rlp_execute` call (it is not automatically returned to the caller on later failure), any deposit tracked by `caller_deposit` that reaches this specific dead-end becomes permanently stuck in the wallet contract's balance, inaccessible to the depositor. This is a genuine, reachable bug for an ordinary unprivileged relayer/caller: any account can deploy or point to a NEP-141 token whose `storage_balance_of` view logic exceeds 5 Tgas (e.g., large storage reads, complex account lookups) and then submit a signed ERC-20-transfer Ethereum tx (as an unprivileged relayer with attached deposit) targeting that token via `rlp_execute`.

### Title
Attached caller deposit is not refunded when NEP-141 `storage_balance_of` probe fails in `nep_141_storage_balance_callback` - ([File: runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs])

### Summary
`nep_141_storage_balance_callback`'s `PromiseResult::Failed` branch (triggered when the `storage_balance_of` probe against a NEP-141 token exceeds the hard-coded 5 Tgas budget) returns an `ExecuteResponse{success:false}` without ever consulting or refunding `caller_deposit`, unlike the sibling `rlp_execute_callback`'s `Failed` arm which explicitly refunds it. Any external, unprivileged relayer who attaches a NEAR deposit to `rlp_execute` and targets an ERC-20 token whose `storage_balance_of` exceeds 5 Tgas will have that deposit permanently stranded in the wallet contract's balance.

### Finding Description
`rlp_execute` is `#[payable]`, so any external NEAR account (predecessor != current_account_id, i.e. a relayer acting on the wallet owner's behalf) can attach a deposit [5](#0-4) . `inner_rlp_execute` builds `caller_deposit` via `CallerDeposit::new(&context)`, which only tracks deposits from external (non-self) callers [1](#0-0) . For a parsed `ERC20Transfer` (from an ETH-encoded `transfer` calldata via `try_emulation` in `eth_emulation.rs`, using `FIVE_TERA_GAS`/`NEP_141_STORAGE_BALANCE_OF_GAS` constants), the promise chain first probes `storage_balance_of` with exactly 5 Tgas static gas, then routes to `nep_141_storage_balance_callback` passing `caller_deposit` along [6](#0-5) . If the target token contract's `storage_balance_of` logic (attacker-controlled, since the attacker chooses/deploys the token contract that `target` points to) burns more than 5 Tgas, the probe promise fails, and the callback's `Failed` arm returns immediately — it never touches `caller_deposit` [3](#0-2) . Compare this to `rlp_execute_callback`'s `Failed` arm, which explicitly creates a refund promise back to `caller_deposit.account_id` [4](#0-3) . No existing signature, nonce, access-key, or gas-metering check prevents this: the nonce is already incremented earlier in `inner_rlp_execute` for this transaction kind (so it isn't a mere retryable state), and the deposit was already merged into the wallet contract's account balance when the receipt executed, so nothing automatically returns it to the caller.

### Impact Explanation
Concrete, permanent loss of NEAR funds for an external caller (a relayer/user submitting `rlp_execute` with attached deposit). This matches the "permanent freezing/loss of user funds" bounty category. The lost amount is bounded by whatever deposit the external caller chooses to attach (fee amounts are typically small/relayer-gas-cost-sized, but the vulnerability is not bounded by any explicit cap in code — a caller could attach an arbitrarily large deposit and it would be equally stranded).

### Likelihood Explanation
Preconditions: attacker (or any user, even accidentally) submits `rlp_execute` as an external predecessor with attached deposit for an ERC20Transfer targeting a token contract whose `storage_balance_of` is (or becomes, e.g. via growing storage) more expensive than 5 Tgas. This is easily and cheaply achievable — the attacker/token deployer fully controls `storage_balance_of`'s implementation and can trivially make it exceed 5 Tgas (e.g., large loops, big collection reads). No special privileges are required beyond deploying an ordinary contract and submitting an ordinary transaction; the bug is fully repeatable on every such call.

### Recommendation
In `nep_141_storage_balance_callback`'s `PromiseResult::Failed` arm, mirror `rlp_execute_callback`'s behavior: refund `caller_deposit` via `env::promise_batch_create`/`env::promise_batch_action_transfer` before returning the failure `ExecuteResponse`.

### Proof of Concept
1. Deploy a NEP-141-like token contract whose `storage_balance_of` view method is intentionally made expensive (e.g., iterates a large stored `Vector`/`LookupMap` or performs heavy hashing) such that it consistently exceeds 5 Tgas.
2. Deploy a `WalletContract` instance (as in existing `src/tests/emulation.rs` integration tests, e.g. `test_erc20_emulation`), and as an external account (not the wallet's own account) call `rlp_execute` with a signed ETH `transfer` calldata targeting the expensive token, attaching a non-zero NEAR deposit alongside the call.
3. Await execution and assert: (a) `ExecuteResponse.success == false` with error `"Call to NEP-141 ... storage_balance_of failed"`, and (b) the external caller's account balance did NOT increase by the attached deposit amount (no refund transfer occurred), while the wallet contract's balance retains the deposit — confirming the funds are permanently stuck.
