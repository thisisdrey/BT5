### Title
Relayed LightHouse update messages are attributed to the wrong physical address, poisoning the lighthouse address cache - (File: outside.go)

### Summary
`readOutsidePackets` in `outside.go` processes `header.LightHouse` messages by calling `lhf.HandleRequest(via.UdpAddr, hostinfo.vpnAddrs, out, f)` without checking whether the message arrived via a relay. The code contains an explicit `//TODO: assert via is not relayed` acknowledging the gap. This mirrors the reported MSCA bug class: a component (the relay path) that is permitted to reach an internal function is not restricted from doing so in a context (identity/address attribution) where it should be, allowing state to be attributed to the wrong principal.

### Finding Description
When a packet is unwrapped from a `TerminalType` relay, `handleOutsideRelayPacket` builds a new `ViaSender` that reuses the *outer* UDP source address (`via.UdpAddr`, i.e., the relay's or the packet's raw network source) while marking `IsRelayed: true`, then recurses into `readOutsidePackets`: [1](#0-0) 

Inside the recursive call, when the decrypted inner message is a `header.LightHouse` type, the handler invokes: [2](#0-1) 

`via.UdpAddr` is passed as if it were the *direct* transport address of the peer identified by `hostinfo.vpnAddrs` (the cert-bound VPN address of the terminal relay target), with no check that `via.IsRelayed` is true. The comment directly above this call — `//TODO: assert via is not relayed` — is a code-level acknowledgment that this attribution has not been guarded.

By contrast, other paths that consume `via.UdpAddr` correctly gate on `via.IsRelayed` before trusting it for identity/roaming decisions, e.g. `handleHostRoaming`: [3](#0-2) 
and the double-encryption guard earlier in the same function: [4](#0-3) 

The LightHouse handling path lacks this same `via.IsRelayed` guard, so a relayed LightHouse update is processed with the wrong (relay/attacker-observable) source address bound to the terminal peer's certified VPN address.

### Impact Explanation
The lighthouse subsystem maintains an authoritative mapping from cert-verified VPN addresses to real UDP addr:port endpoints, which is used by all peers to discover how to reach each other (`f.lightHouse` cache, address advertisement/propagation). If a relayed LightHouse packet is processed as if it were a direct one, the address recorded for `hostinfo.vpnAddrs` can be poisoned with an incorrect or attacker-influenced address (the relay hop's address, or any spoofable UDP source since UDP has no return-routability enforcement at this layer). This is remote state poisoning of the lighthouse/hostmap address-trust database — consistent with the report's underlying bug class where a permitted call path (plugin/relay forwarding) is not sufficiently restricted from performing an action normally reserved for a directly-authenticated context (owner-only function / direct sender identity). Downstream, other peers or the terminal node itself may attempt to reach the peer at the poisoned address, degrading connectivity or, depending on how the address cache is consumed elsewhere, enabling further address-trust confusion.

### Likelihood Explanation
Reaching this path requires only a normal encrypted tunnel to a relay peer (`am_relay` role) plus a certificate-authenticated handshake to a terminal peer, both of which are standard, attacker-reachable configurations in any nebula mesh that uses relays (no CA-signed certificate compromise required — the finding does not depend on possessing another party's valid cert, only on the existing capability to run/be a relay-connected peer). The bug is a missing guard rather than a crypto break, so the barrier to triggering it is low; the explicit `TODO` in the code indicates the maintainers were aware the guard is missing but had not yet added it as of this revision.

### Recommendation
In `readOutsidePackets`, gate the `header.LightHouse` case on `via.IsRelayed`, mirroring the pattern used elsewhere (e.g., `handleHostRoaming`, the double-encryption check at the top of the function). If a LightHouse message arrives with `via.IsRelayed == true`, either drop it or explicitly document/verify that lighthouse address learning must never occur over relayed transport, ensuring `via.UdpAddr` is only trusted for lighthouse cache updates when it is a direct, non-relayed source address.

### Proof of Concept
Conceptual reproduction (based on code paths, not independently executed):
1. Stand up three nebula nodes signed by the same CA: `me` (uses relay), `relay` (`am_relay=true`), `them` (uses relay) — the same topology already exercised in `TestRelays`/`TestHandshakeRelayComplete`. [5](#0-4) 
2. Establish a relayed tunnel from `me` to `them` through `relay` so `relay` holds a `TerminalType`/`ForwardingType` relay mapping for `them`.
3. Have `relay` (or a node positioned to observe/spoof the outer UDP datagram, since UDP source addresses are not authenticated at this layer) forward or replay a `header.LightHouse` message tunneled inside a `header.MessageRelay` frame toward `me`.
4. On `me`, `handleOutsideRelayPacket` unwraps the `TerminalType` relay frame and recurses into `readOutsidePackets` with `via.UdpAddr` still set to the outer packet's source (not `them`'s real address) and `via.IsRelayed = true`. [6](#0-5) 
5. The inner message is dispatched as `header.LightHouse`, calling `lhf.HandleRequest(via.UdpAddr, hostinfo.vpnAddrs, out, f)` without any `via.IsRelayed` check, causing `me`'s lighthouse cache to associate `them`'s certified VPN address with the (incorrect/attacker-influenced) `via.UdpAddr`.
