### Title
Unguarded division by `totalEnergyWeight` in `RepositoryImpl.calculateGlobalEnergyLimit` can throw `ArithmeticException` during TVM execution - (File: actuator/src/main/java/org/tron/core/vm/repository/RepositoryImpl.java)

### Summary
`RepositoryImpl.calculateGlobalEnergyLimit` divides by `totalEnergyWeight` after only an `assert` check, which is a no-op in production JVMs (assertions are disabled by default, no `-ea` flag). This mirrors the TFLite bug class: a divisor that can reach zero is not defensively checked before being used as the denominator of a division, producing an uncaught `ArithmeticException` reachable from ordinary transaction processing (any smart-contract call that needs its energy limit computed from frozen balance).

### Finding Description
`RepositoryImpl.calculateGlobalEnergyLimit` computes an account's TVM energy limit from its frozen balance and the network-wide `totalEnergyWeight`: [1](#0-0) 

The method reads `totalEnergyWeight` from `DynamicPropertiesStore` and only guards it with a Java `assert totalEnergyWeight > 0;` before performing `BigInteger.valueOf(totalEnergyLimit).divide(BigInteger.valueOf(totalEnergyWeight))` (hardened path) or a plain `double` division (non-hardened path). Java assertions are disabled by default in production deployments (they require the `-ea` JVM flag), so this check provides no real protection at runtime — it is functionally equivalent to the TFLite pooling code that failed to validate `stride_height`/`stride_width` before calling `ComputePaddingHeightWidth`.

Contrast this with the sibling implementation `EnergyProcessor.calculateGlobalEnergyLimit`, which explicitly checks the value and returns 0 safely: [2](#0-1) 

and `calculateGlobalEnergyLimitV2`, which also has an explicit `totalEnergyWeight == 0` guard: [3](#0-2) 

`RepositoryImpl.calculateGlobalEnergyLimit` has no equivalent safe-guard, relying solely on the disabled `assert`. `totalEnergyWeight` is a chain-wide dynamic property that is decremented as accounts unfreeze balance previously frozen for energy; it is not intrinsically bounded away from zero, so a state where it reaches 0 (e.g., after broad unfreezing activity network-wide) is a legitimate, non-privileged runtime condition, not an attacker-forged single value like TFLite's model-supplied stride.

### Impact Explanation
If `totalEnergyWeight` is 0 when `RepositoryImpl.calculateGlobalEnergyLimit` executes, the hardened path throws an uncaught `ArithmeticException: / by zero` (BigInteger division by zero) during TVM execution triggered by any account's `TriggerSmartContract`/`CreateSmartContract` transaction. Since this executes inside contract execution processing for every block-applying node, an uncaught exception here can disrupt transaction/block processing on nodes evaluating that transaction, which is a node-crash/DoS-class impact under the "Medium/High/Critical" scope of this scan (denial of service / node halt during normal block application, not merely a rejected transaction).

### Likelihood Explanation
This is not directly attacker-triggerable in one transaction the way the TFLite crafted-model bug is (an attacker cannot instantaneously zero out `totalEnergyWeight`, since it is a chain-wide aggregate updated by freeze/unfreeze accounting). It requires a state where global energy-freeze weight has fully drained to zero. This is a plausible, naturally reachable network condition (particularly on low-activity/private/test networks, or after a coordinated mass-unfreeze event), rather than a purely theoretical one, but I could not fully confirm within available search depth every call site that invokes `RepositoryImpl.calculateGlobalEnergyLimit` versus `EnergyProcessor`'s guarded variants, nor confirm current runtime assertion settings in java-tron's production launch scripts. This uncertainty should be resolved by a deeper trace of `RepositoryImpl.calculateGlobalEnergyLimit` call sites within the TVM engine before treating this as fully proven exploitable in mainnet conditions.

### Recommendation
Add an explicit runtime guard in `RepositoryImpl.calculateGlobalEnergyLimit` mirroring `EnergyProcessor.calculateGlobalEnergyLimitV2`'s check (`if (totalEnergyWeight <= 0) { return 0; }`) before any division, removing reliance on the disabled `assert` statement.

### Proof of Concept
Not executable from a single external transaction; the precondition (`totalEnergyWeight == 0`) is a chain state that must be driven to zero through legitimate freeze/unfreeze activity, which I could not concretely construct and confirm as reachable within this investigation's tool budget. This should be validated by a maintainer/Devin session that can trace all call sites of `RepositoryImpl.calculateGlobalEnergyLimit` and simulate draining `totalEnergyWeight` to 0 on a test node, then triggering a smart-contract call to confirm the `ArithmeticException` and its effect on block/transaction processing.

    long frozeBalance = accountCapsule.getAllFrozenBalanceForEnergy();

      return 0;

    long totalEnergyWeight = getDynamicPropertiesStore().getTotalEnergyWeight();

    assert totalEnergyWeight > 0;

    if (hardenResourceCalculation()) {
      return BigInteger.valueOf(energyWeight)
          .multiply(BigInteger.valueOf(totalEnergyLimit))
          .divide(BigInteger.valueOf(totalEnergyWeight))
          .longValueExact();
    }
    return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
  }
