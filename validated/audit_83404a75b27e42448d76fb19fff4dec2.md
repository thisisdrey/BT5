Found a directly analogous unchecked-null dereference reachable from an anonymous JSON-RPC request.

### Title
NullPointerException / node crash via unauthenticated JSON-RPC calls when head/genesis block is unavailable - (File: framework/src/main/java/org/tron/core/services/jsonrpc/TronJsonRpcImpl.java)

### Summary
The core-geth ethstats fix addressed a panic that occurred when code dereferenced the "head block" without checking for `nil`, which becomes reachable when the canonical number→hash mapping for that block is momentarily gone (e.g., during a chain reorg race). `java-tron`'s JSON-RPC service has the same bug class: several public JSON-RPC methods fetch a block via `wallet.getNowBlock()` or `wallet.getBlockCapsuleByNum(0)` and immediately dereference the result without a null check, even though these `Wallet` methods are documented/known to return `null` when the block is not found.

### Finding Description
`Wallet.getNowBlock()` explicitly returns `null` when the block list is empty [1](#0-0) , and `Wallet.getBlockCapsuleByNum` returns `null` on any `StoreException` (e.g. `ItemNotFoundException`, `BadItemException`) [2](#0-1) .

However, `TronJsonRpcImpl.getProtocolVersion()` and `TronJsonRpcImpl.getLatestBlockNum()` call `wallet.getNowBlock().getBlockHeader()...` directly, with no null check on the returned `Block`: [3](#0-2) 

Similarly, `TronJsonRpcImpl.ethChainId()` calls `wallet.getBlockCapsuleByNum(0).getBlockId()...` and only catches the resulting `NullPointerException` implicitly via a generic `Exception` catch that wraps it into a `JsonRpcInternalException` — but this masking only happens because the surrounding try/catch is present here; the two methods above (`getProtocolVersion`, `getLatestBlockNum`) have no such protection at all: [4](#0-3) 

If `getNowBlock()` returns `null` (e.g., the block list from `getBlockByLatestNum(1)` is momentarily empty — a scenario analogous to the reorg race described in the ethstats report, where the canonical head is transiently unavailable while `Manager` is mid-way through `switchFork`/`eraseBlock`/`applyBlock`), an unauthenticated caller hitting `eth_protocolVersion` or `eth_blockNumber` over the JSON-RPC HTTP endpoint triggers an unhandled `NullPointerException` inside the request-handling thread.

### Impact Explanation
An uncaught `NullPointerException` thrown from a JSON-RPC handler is, at minimum, a denial-of-service against that RPC endpoint/thread for the specific request; if uncaught exceptions in the underlying JSON-RPC servlet dispatch are not converted into JSON-RPC error responses at a higher framework layer, this can also disrupt the JSON-RPC service availability for legitimate API clients, matching the "API the node can no longer serve" acceptance criterion.

### Likelihood Explanation
The trigger condition (the head block or genesis block capsule being transiently `null`) can occur during normal node operation (block store still initializing, or a chain-reorg window) rather than requiring any special privilege — any anonymous client issuing a standard `eth_protocolVersion`, `eth_blockNumber`, or `eth_chainId` JSON-RPC call during that narrow window can hit it, making this a reachable, low-effort, network-facing bug.

### Recommendation
Add explicit null checks after `wallet.getNowBlock()` and `wallet.getBlockCapsuleByNum(0)` in `getProtocolVersion()`, `getLatestBlockNum()`, and `ethChainId()` in `TronJsonRpcImpl.java`, returning a well-defined JSON-RPC error (e.g., throw `JsonRpcInternalException`) instead of letting a `NullPointerException` propagate, mirroring the pattern already used in `getBlockResult()` which checks `if (block == null) return null;` [5](#0-4) .

### Proof of Concept
1. Start a fullnode with JSON-RPC enabled.
2. During node startup (before the block store/head is fully populated) or during a chain-reorg window where `getBlockByLatestNum(1)` transiently returns an empty list, send `curl -d '{"jsonrpc":"2.0","method":"eth_protocolVersion","params":[],"id":1}' http://node:8545`.
3. `wallet.getNowBlock()` returns `null`; `getProtocolVersion()` calls `.getBlockHeader()` on `null`, throwing `NullPointerException` inside the RPC handler thread, which is not caught by the method itself.
