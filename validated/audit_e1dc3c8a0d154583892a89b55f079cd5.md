### Title
Privilege Escalation via AccountPermissionUpdateContract: Active-Permission Key Can Overwrite Owner Permission - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
`AccountPermissionUpdateActuator` allows any transaction signed under a non-Owner "Active" permission ID to fully overwrite the account's Owner permission, provided that Active permission was ever granted the `AccountPermissionUpdateContract` bit in its `operations` bitmap. Because the actuator's `execute()` blindly applies the `owner`/`witness`/`actives` fields taken from the contract itself, with no check that the signing permission is `Owner`-level, an Active key can promote itself (or any attacker-chosen address) to full account control — mirroring the Harbor CWE-269 pattern where a lower-privileged role could perform actions reserved for a higher-privileged role.

### Finding Description
`validate()` in `AccountPermissionUpdateActuator` [1](#0-0)  only checks structural correctness of the submitted `owner`, `witness`, and `actives` `Permission` messages (key counts, weights, thresholds, distinct addresses, and that the Active `operations` bitmap only references valid `ContractType`s via `dynamicStore.getAvailableContractType()`). It never checks which permission ID actually signed the transaction, nor restricts what an Active-level signer is allowed to set as the new Owner permission.

`execute()` then unconditionally rewrites all three permission slots from the contract payload: [2](#0-1) 

The only gate preventing an arbitrary signer from invoking this actuator is the generic per-transaction permission check in `TransactionCapsule.checkPermission`, which for non-zero `permissionId` only verifies that the *type* is `Active` and that the `operations` bitmap bit for the target contract type is set — it does not special-case `AccountPermissionUpdateContract` to prevent Active permissions from modifying the Owner permission: [3](#0-2) 

Critically, `AccountPermissionUpdateContract` is confirmed to be a *valid* bit for the Active `operations` bitmap (only `UNRECOGNIZED`, `ClearABIContract`, and `UpdateBrokerageContract` are excluded from `getAvailableContractType`), as shown by the actuator's own test asserting the full bitmap of legal operation types: [4](#0-3) 

It is only excluded from the *default* active operations set (`checkActiveDefaultOperations`), meaning it must be deliberately enabled by the Owner for a given Active permission — but once enabled, the framework treats it as a fully legitimate operation for that Active key, without any additional restriction that the resulting `owner` `Permission` must still be controlled by the original owner key(s). This allows an Active-permission co-signer (e.g., one added only for asset/TRX operations) to unilaterally replace the account's Owner permission — the highest-privilege permission in the multisig model — with keys of their own choosing, achieving full account takeover.

### Impact Explanation
Any account that has granted an Active permission the `AccountPermissionUpdateContract` operation bit (a supported, test-verified configuration) is exposed to a co-signer with that Active key completely seizing account control by rewriting the Owner permission, deleting or replacing all rightful Owner keys. This results in unauthorized account takeover, permanent loss of control/funds for the legitimate owner, and CWE-269 improper privilege management consistent with the Harbor analog.

### Likelihood Explanation
Exploitation requires only a normal signed `AccountPermissionUpdateContract` transaction from an account that has previously granted an Active permission the relevant operation bit — a state reachable purely through standard, supported multisig configuration (no special network position, no witness/SR compromise). Given multisig/active-key delegation is a common Tron feature (e.g., for automated services or team wallets), such configurations are plausible in production.

### Recommendation
In `AccountPermissionUpdateActuator.validate()`/`checkPermission()`, disallow an Active permission from being granted rights to `AccountPermissionUpdateContract` when the update would affect the Owner permission, or require that any transaction modifying the Owner permission must itself be signed under `permissionId == 0` (true Owner authority), regardless of what the Active permission's `operations` bitmap allows.

### Proof of Concept
1. Owner account `A` sets up permissions via `AccountPermissionUpdateContract`: Owner permission with key `K_owner`; an Active permission (id=2) with key `K_active` whose `operations` bitmap includes the bit for `AccountPermissionUpdateContract` (bit 46) in addition to normal operations.
2. Attacker in control of `K_active` (or a legitimate but rogue co-signer) crafts a new `AccountPermissionUpdateContract` transaction for account `A`, setting `owner` field to a Permission containing only the attacker's key, keeping `actives` minimally valid to pass `checkPermission`.
3. Sets `Transaction.Contract.Permission_id = 2` and signs with `K_active`.
4. Broadcasts; `TransactionCapsule.checkPermission` (chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java:635-645) accepts it because permission type is Active and the operations bit for `AccountPermissionUpdateContract` is set.
5. `AccountPermissionUpdateActuator.execute()` (actuator/.../AccountPermissionUpdateActuator.java:44-52) applies the new Owner permission from the contract unconditionally, overwriting `K_owner` with the attacker's key — full account takeover achieved from an Active-level key.

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
