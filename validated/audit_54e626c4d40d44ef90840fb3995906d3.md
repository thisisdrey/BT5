### Title
Non-atomic bloom-filter rotation in `TxCacheDB` can cause the duplicate-transaction cache to lose entries under concurrent access, allowing an already-executed transaction to bypass duplication checks - (File: `chainbase/src/main/java/org/tron/core/db2/common/TxCacheDB.java`)

### Summary
`TxCacheDB` implements the "seen transaction" cache that `Manager.containsTransaction()` relies on to short-circuit duplicate-transaction detection. Like the lighthouse `Observed*` caches described in the report, its internal state (`filterStartBlock`, `currentFilterIndex`, `bloomFilters[]`) is mutated via a non-atomic check-then-act sequence that is reachable from multiple concurrent call sites, without a lock protecting the whole `put()` operation.

### Finding Description
`TxCacheDB.put()` performs a compound, unsynchronized sequence: read `filterStartBlock`/`currentFilterIndex`, decide whether the active bloom filter is "full", flip `currentFilterIndex`, and then replace `bloomFilters[currentFilterIndex]` with a brand-new, empty `BloomFilter` instance: [1](#0-0) 

`filterStartBlock` and `currentFilterIndex` are declared `volatile`, but volatility only guarantees visibility of individual field reads/writes — it does not make the read-decide-write sequence atomic, and it does nothing to protect the `bloomFilters` array element replacement itself. `get()` reads both filter slots directly without any lock: [2](#0-1) 

`put()` is invoked from `Manager.processTransaction()` every time a transaction is validated/executed (both when a client's transaction is pushed to the pending pool and when a transaction is applied as part of a block): [3](#0-2) 

This is different from `flush()`, which is `synchronized` and is used only for the revoking/batch write path: [4](#0-3) 

Because `pushTransaction()` (triggered by an unprivileged client broadcasting a transaction) and block application both eventually call `processTransaction()` → `TxCacheDB.put()`, and these code paths are not all serialized under the same monitor (`pushTransaction()` only guards its own pending-pool bookkeeping under `transactionLock`/`synchronized(this)`, not the underlying cache mutation performed later during commit), concurrent `put()` calls racing on the currentFilterIndex swap can cause one thread's freshly-inserted bloom filter entries to be silently discarded when another thread creates a brand-new `BloomFilter` object for the same slot during a rotation: [5](#0-4) 

The consequence is that a transaction ID that was legitimately recorded as "seen" can be lost from both bloom filter slots. `Manager.containsTransaction()` treats a "definitely not present" bloom-filter result as authoritative and skips the persistent `TransactionStore` lookup entirely: [6](#0-5) 

Bloom filters are only supposed to produce false positives, never false negatives — but this race can manufacture a false negative by dropping previously-inserted keys during filter rotation, which defeats the entire "using the bloom filter only determines non-existent transaction" invariant documented at line 875.

### Impact Explanation
If a duplicate lookup for an already-processed transaction ID races with a `put()` call from another thread performing a filter rotation at the same time, `transactionCache.has()` can incorrectly return `false` for a transaction that is already recorded, causing `validateDup()` to pass. Because the fallback persistent check `chainBaseManager.getTransactionStore().has(transactionId)` is skipped whenever the cache says "not present," `validateDup()` in `Manager.processTransaction()` could allow re-processing of a transaction identical to one already included/committed, provided its `expiration`/TAPOS window is still valid — resulting in duplicate execution of a transaction's effects (e.g., a transfer or contract call being applied a second time). This maps to the report's "race condition in seen caches" bug class and constitutes an unauthorized/duplicated state-changing operation, which the scan scope classifies as accepted (unbacked balance change / unauthorized duplicate operation).

### Likelihood Explanation
Reaching `TxCacheDB.put()` concurrently only requires normal transaction broadcast traffic — no privileged role is needed. However, actually losing an entry requires the racy rotation window (`blockNum - filterStartBlock > MAX_BLOCK_SIZE`, i.e., roughly once per 65,536 blocks) to coincide precisely with a concurrent `put()`/`get()` on the same instant, which is a narrow timing window. This makes exploitation non-trivial to trigger deterministically, though it is a genuine, reachable data race rather than a purely theoretical one, matching the same "hard to hit under load, needs testnet-scale validation" characterization the original lighthouse fix called out.

### Recommendation
Guard the entire read-decide-write sequence in `TxCacheDB.put()` (and the corresponding read path in `get()`) with a single lock (e.g., `ReadWriteLock` or `synchronized`) so that the `filterStartBlock`/`currentFilterIndex`/`bloomFilters[]` triple is updated atomically, mirroring the "lift the locks to cover the whole compound operation" fix applied upstream in lighthouse's `Observed*` structures. Additionally, `Manager.containsTransaction()` should not treat a "not present" bloom-filter result as fully authoritative for skipping the persistent store check in TAPOS-valid time ranges, or should fall back to a persistent check whenever there is any ambiguity about cache consistency.

### Proof of Concept
Not independently verified end-to-end — establishing an exact reproducible timing window requires concurrent stress testing (two threads: one performing `TxCacheDB.put()` at a filter-rotation boundary block, another performing `Manager.containsTransaction()`/`validateDup()` for a previously inserted transaction ID at the same moment) which is outside what can be confirmed via static code reading alone. The unsynchronized compound operations shown above are confirmed by direct inspection of `TxCacheDB.java` and `Manager.java`.
