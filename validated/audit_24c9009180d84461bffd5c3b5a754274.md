### Title
Replayed byte-identical stage-1 handshake packet triggers unauthenticated remote-roam attempt and Test-packet send - ([File: handshake_manager.go])

### Summary
`HandshakeManager.CheckAndComplete` treats a stage-0/stage-1 handshake packet as "already seen" purely by comparing raw bytes (`bytes.Equal(hostinfo.HandshakePacket[handshakePacket], testHostInfo.HandshakePacket[handshakePacket])`), with no nonce, timestamp, or freshness proof tied to the UDP source address. When this branch fires, `handleCheckAndCompleteError`'s `ErrAlreadySeen` case calls `existing.SetRemoteIfPreferred(f.hostMap, via)` and, on success, sends a `header.Test`/`TestRequest` packet to the peer's VPN address, and unconditionally resends the cached stage-2 response to the packet's (possibly spoofed) source.

### Finding Description
In `beginHandshake` (`handshake_manager.go`), an inbound stage-1 packet is processed by a fresh responder `Machine`, and the resulting `hostinfo` is passed to `hm.CheckAndComplete(hostinfo, handshakePacketStage0, f)`. Inside `CheckAndComplete`: [1](#0-0) 
this loop compares only the raw handshake packet bytes against every existing hostinfo for the same vpn address, with no check that the packet's cryptographic contents are fresh (no per-source nonce/timestamp verification) or that the source address matches a previously authenticated flow. Because the IX pattern's stage-1 message is a fixed, deterministic function of the initiator's ephemeral/static keys and payload, a byte-identical stage-1 packet observed by a network-position attacker (or an attacker who can otherwise obtain the exact bytes) can be retransmitted verbatim from a different, spoofed `netip.AddrPort`.

When `ErrAlreadySeen` is returned, `handleCheckAndCompleteError` runs: [2](#0-1) 
`via` here is fully attacker-controlled (the UDP source of the replayed packet), so `existing.SetRemoteIfPreferred(f.hostMap, via)` is invoked with an unauthenticated address. Nebula's `SetRemoteIfPreferred` (hostmap.go) only overwrites `hostinfo.remote` when the candidate address falls inside the locally configured "preferred ranges" (`hm.GetPreferredRanges()`), a CIDR list normally set to trusted internal/LAN subnets for same-network optimization — this is a mitigating gate not visible directly in the audited function, but it is the actual security boundary enforced. Independent of that gate, the code also unconditionally resends the cached stage-2 handshake response to the spoofed `via.UdpAddr` and issues a `Test`/`TestRequest` transmission toward `hostinfo.vpnAddrs[0]` when the roam succeeds — none of these actions require any fresh cryptographic proof from the replayed packet, only byte equality of stale, previously-seen ciphertext-adjacent handshake bytes.

### Impact Explanation
The concrete, scoped impact is remote-address state poisoning: `existing.remote` can be redirected to an attacker-chosen address using only a replayed (not freshly signed) packet, violating the invariant that peer addressing/roaming should only change on cryptographically fresh, verified traffic. Because `SetRemoteIfPreferred` gates the actual overwrite to addresses within the configured `preferred_ranges` (normally trusted local/VPC subnets), full roam to an arbitrary internet-facing attacker address is not achieved in a default configuration; the practical redirection is bounded to peers/attackers who can spoof a source address inside that preferred CIDR (e.g., an attacker positioned on the same LAN/VPC as one of the tunnel endpoints). Even without a successful roam, the unconditional resend of the cached stage-2 response to the spoofed source is a reflection primitive (small trigger packet -> handshake-response sized reply sent to an attacker-chosen address), and the `Test` packet send is an additional side effect triggered purely by stale byte-matching.

### Likelihood Explanation
Exploitation requires the attacker to (1) obtain the exact bytes of a completed stage-1 handshake packet (via passive capture on-path, since it is not secret-derived per source) and (2) be able to spoof a UDP source address — for the roam to actually change `existing.remote`, that spoofed address must additionally fall within the victim's configured `preferred_ranges`, which in most deployments corresponds to trusted local subnets, not arbitrary WAN addresses. This substantially limits the practical severity of the roam itself versus what the question's framing implies (full unrestricted redirection to any attacker source), though the reflection/Test-send side effects fire regardless of `preferred_ranges`.

### Recommendation
Tie the "already seen" fast-path to verified freshness rather than raw byte equality: require the resend/roam logic to additionally confirm the packet's handshake MAC/signature was produced against the current session state and consider binding roam decisions to a short replay/nonce window per remote index rather than unconditional `bytes.Equal` matching. At minimum, do not call `SetRemoteIfPreferred` or trigger response/Test resends purely based on stale-packet byte equality without corroborating that the source has demonstrated possession of session-derived key material (e.g., a subsequent successfully-decrypted data or Test packet) before altering `hostinfo.remote`.

### Proof of Concept
Integration test plan (extending `e2e/handshake_manager_test.go`):
1. Complete a real handshake between two simulated nodes A and B so `A`'s `mainHostMap` has a hostinfo for B's vpn address with `HandshakePacket[handshakePacketStage0]` stored.
2. Capture the exact stage-1 packet bytes B originally sent to A.
3. Replay those exact bytes to A's UDP listener from a spoofed `netip.AddrPort` that is NOT B's real address and IS inside A's configured `preferred_ranges`.
4. Assert that `CheckAndComplete` returns `ErrAlreadySeen`, and that `existing.remote` (queryable via the hostmap) is updated to the spoofed address, and that a `Test`/`TestRequest` packet is transmitted toward B's vpn address — all without any newly-signed handshake material from the spoofed source.
5. Repeat with a spoofed address outside `preferred_ranges` and confirm `existing.remote` is unchanged, to characterize/document the actual gate, and separately assert that the stage-2 response packet is still resent to the out-of-range spoofed address (reflection), which is unconditional and unauthenticated.
