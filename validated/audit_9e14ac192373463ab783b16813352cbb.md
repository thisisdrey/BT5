### Title
Broadcast pending-transaction count check is not atomic with enqueue, allowing the accepted-transaction limit to be bypassed under concurrent load - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
`Wallet.broadcastTransaction()` checks `dbManager.isTooManyPending()` and, if the pending pool is not over `maxTransactionPendingSize`, calls `dbManager.pushTransaction(trx)`. Inside `Manager.pushTransaction()`, the transaction is added to `pushTransactionQueue` (`pushTransactionQueue.add(trx)`) *before* any locking is taken, and the actual accounting used by `isTooManyPending()`/`getCachedTransactionSize()` is only checked-and-updated later, non-atomically with the check performed by the caller. Concurrent unauthenticated broadcast requests (HTTP `/wallet/broadcasttransaction`, gRPC `BroadcastTransaction`) can all observe the pending count below the limit and all get admitted into the queue/pool before the count is incremented, letting the total accepted pending transactions exceed the configured cap — analogous to the reported bug class where certain accepted units are not counted toward the enforced total before more are admitted, allowing resource exhaustion.

### Finding Description
`Manager.isTooManyPending()` computes the currently accepted work as the sum of three collections: [1](#0-0) 

This is invoked by `Wallet.broadcastTransaction()` as a gating check prior to admission: [2](#0-1) 

After passing that check, the caller proceeds to call `dbManager.pushTransaction(trx)`: [3](#0-2) 

Inside `pushTransaction`, the transaction is unconditionally added to `pushTransactionQueue` — which is one of the three collections counted by `getCachedTransactionSize()` — *before* the method reaches the synchronized block that performs signature validation and the only other bounded-admission check (which only limits shielded transactions specifically, not general pending count): [4](#0-3) 

Because the “is total accepted work under the limit” check in `Wallet.broadcastTransaction` and the “add to the counted queue” action in `Manager.pushTransaction` are two separate, non-atomic steps with no shared lock protecting the read-then-increment sequence, many transactions submitted concurrently (from HTTP `BroadcastServlet`/`BroadcastHexServlet` or the gRPC/JSON-RPC broadcast paths) can each individually observe `isTooManyPending() == false` and be pushed onto `pushTransactionQueue` before any of them are reflected in the count. This mirrors the reported bug class: units are admitted into a resource-consuming structure without being reliably counted against the enforced cap at admission time, letting total accepted work exceed the intended limit. ### Impact Explanation
`maxTransactionPendingSize` (default 2000) exists specifically to bound memory used by in-flight transactions (`pushTransactionQueue` + `pendingTransactions` + `rePushTransactions`) and to return `SERVER_BUSY` once exceeded, protecting the node from unbounded memory growth. Because admission is check-then-act rather than atomic, a burst of concurrent broadcast calls from any anonymous client (no signature validity or balance required to reach the queue-add step — it happens before `validateSignature`) can inflate the queue well past the configured cap. Sustained abuse can drive memory pressure that leads to degraded performance or an OOM crash of the full node, which is a node-crash/DoS impact for a resource meant to protect exactly against this class of exhaustion.

### Likelihood Explanation
The check-then-act window is opened on every single broadcast call and does not require any privileged capability — a plain, valid or even structurally-valid-but-unsigned transaction reaches `pushTransactionQueue.add(trx)` before signature verification occurs. An attacker only needs the ability to open many concurrent HTTP/gRPC connections to a public API node (default rate limiter for unconfigured servlets is a generous `qps=1000`, and no per-connection cap prevents many simultaneous in-flight broadcast calls), making the race condition straightforward to trigger with standard load-testing/flooding tools. Exploitability depends on request concurrency and network conditions (to keep many requests in-flight simultaneously through the window), so likelihood is judged moderate rather than trivial-with-a-single-request.

### Recommendation
Make the pending-count check and the enqueue atomic, e.g. increment/check `getCachedTransactionSize()` (or a dedicated `AtomicInteger` counter) under the same lock used to add to `pushTransactionQueue`, and roll back the increment on failure/exception, mirroring the pattern already used for `shieldedTransInPendingCounts`. Alternatively, reserve a slot (compare-and-increment) before enqueueing and release it on any failure path (`ValidateSignatureException`, `ContractValidateException`, etc.), rather than allowing unconditional addition to `pushTransactionQueue` ahead of the accounting used for admission control.

### Proof of Concept
Not independently reproduced in this review (no runtime/terminal access). The described race is inferred directly from the source: `pushTransactionQueue.add(trx)` at `Manager.java:901` executes unconditionally and prior to any lock, while the only admission-limit check (`isTooManyPending()`, `Wallet.java:552`) is performed by the caller beforehand as a separate, unsynchronized read. A concrete PoC would involve firing a large number of concurrent `broadcasttransaction` HTTP/gRPC requests (e.g., via a load tool) against a FullNode and observing `Manager.getCachedTransactionSize()` (or memory usage) exceed `maxTransactionPendingSize` instead of the expected `SERVER_BUSY` rejection past the cap — this should be validated on a running node/testnet by a follow-up engineering task, since it cannot be executed from this read-only analysis.
