### Title
No vulnerability: seed-collision replay of Stake action cannot cause validator-proposal double-counting - (File: runtime/runtime/src/access_keys.rs)

### Summary
The described replay path (Stake(X) at nonce N → same-block DeleteKey+AddKey reseeding the key's nonce to `(block_height-1) * 1_000_000` → resubmission of the original signed Stake(X) tx at nonce N) is theoretically constrained to same-block execution and precise chunk ordering the attacker cannot control, but even granting the replay, the alleged impact does not exist: validator-proposal accounting is not additive.

### Finding Description
`add_regular_key` at `runtime/runtime/src/access_keys.rs:230-240` reseeds a recreated key's nonce to `initial_nonce_value(block_height) = (block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, and `verify_nonce` (`runtime/runtime/src/verifier.rs:211-236`) only requires the new tx's nonce to exceed this reseeded value. A resubmitted, previously-executed `Stake` transaction could in principle pass nonce validation again if its original nonce N happens to exceed the new reseed value — which is only possible when the `DeleteKey`+`AddKey` pair executes in the *same block height* as the original `Stake` tx (any later block's reseed value, `(H2-1)*1e6`, exceeds any nonce valid at height H1 < H2). This already requires exact same-block, in-order placement of three sequential transactions from the signer, which the unprivileged attacker does not control (chunk-producer transaction ordering, not client-controlled).

Even granting this replay occurs, `action_stake` (`runtime/runtime/src/actions.rs:59-110`) pushes a `ValidatorStake` entry into `result.validator_proposals` each time it runs, so a duplicate entry for the same account can appear in the per-chunk `ActionResult`/`ApplyResult.validator_proposals` list. However, this list is not accumulated additively downstream. `EpochInfoAggregator::update_tail` at `chain/epoch-manager/src/epoch_info_aggregator.rs:200-203` folds `block_info.proposals_iter()` into `all_proposals: BTreeMap<AccountId, ValidatorStake>` keyed by account id, and `merge`/`merge_prefix` (`epoch_info_aggregator.rs:224-271`) likewise combine aggregators as last-value-per-account maps, not sums. This is confirmed by the explicit regression test `test_epoch_info_aggregator_overwrites_latest_version_and_proposal` in `chain/epoch-manager/src/tests/mod.rs:1234-1283`, whose docstring states "`all_proposals` ... are last-value (not additive): the highest-height write for a producer must win."

### Impact Explanation
No concrete impact. Because validator proposal accounting is a last-value map keyed by account, a duplicated `Stake(X)` proposal for the same account collapses to the same single logical value used in `proposals_to_epoch_info` (`chain/epoch-manager/src/validator_selection.rs:166`). There is no double-counting of stake delta, no inflation of validator weight, and no confusion of epoch reward inputs — the mechanism is designed to be idempotent per account regardless of how many times a proposal for that account appears in a block.

### Likelihood Explanation
Not applicable — even under the most favorable (same-block, attacker-favorable ordering) conditions for the described replay, the downstream accounting invariant holds by construction.

### Recommendation
No fix required for the scoped concern. (Independently, the same-block nonce-reseed-vs-recent-nonce edge case in `initial_nonce_value` could be tightened for defense-in-depth by tracking a per-account "highest nonce ever used" rather than only reseeding from block height, but this is not required to prevent the specific validator-proposal impact claimed here.)

### Proof of Concept
Not applicable; no reachable impact to demonstrate. A test asserting `EpochInfoAggregator::all_proposals`/`current_proposals` contains one entry per account regardless of duplicate `Stake` actions in a block already exists in spirit via `test_epoch_info_aggregator_overwrites_latest_version_and_proposal` (`chain/epoch-manager/src/tests/mod.rs:1238`), confirming last-value semantics. pub(crate) fn action_stake(
    account: &mut Account,
    result: &mut ActionResult,
    account_id: &AccountId,
    stake: &StakeAction,
    last_block_hash: &CryptoHash,
    epoch_info_provider: &dyn EpochInfoProvider,
) -> Result<(), RuntimeError> {
    let increment = stake.stake.saturating_sub(account.locked());

    if let Some(new_balance) = account.amount().checked_sub(increment) {
        if account.locked().is_zero() && stake.stake.is_zero() {
            // if the account hasn't staked, it cannot unstake
            result.result =
                Err(ActionErrorKind::TriesToUnstake { account_id: account_id.clone() }.into());
            return Ok(());
        }

        if stake.stake > Balance::ZERO {
            let minimum_stake = epoch_info_provider.minimum_stake(last_block_hash)?;
            if stake.stake < minimum_stake {
                result.result = Err(ActionErrorKind::InsufficientStake {
                    account_id: account_id.clone(),
                    stake: stake.stake,
                    minimum_stake,
                }
                .into());
                return Ok(());
            }
        }

        result.validator_proposals.push(ValidatorStake::new(
            account_id.clone(),
            stake.public_key.clone(),
            stake.stake,
        ));
        if stake.stake > account.locked() {
            // We've checked above `account.amount >= increment`
            account.set_amount(new_balance);
            account.set_locked(stake.stake).or_inconsistent_state(account_id)?;
        }
    } else {
        result.result = Err(ActionErrorKind::TriesToStake {
            account_id: account_id.clone(),
            stake: stake.stake,
            locked: account.locked(),
            balance: account.amount(),
        }
        .into());
    }
    Ok(())
}

/// `version_tracker` and `all_proposals` are last-value (not additive): the
/// highest-height write for a producer must win. Pins that contract so any future
/// change to the aggregation order can't silently keep a stale (lower-height) value.

#[test]
fn test_epoch_info_aggregator_overwrites_latest_version_and_proposal() {
    let stake_amount = Balance::from_yoctonear(1_000_000);
    // Single validator -> block producer is id 0 at every height, so both trackers are
    // written on every block and the latest must win.
    let validators = vec![("test0".parse().unwrap(), stake_amount)];
    let mut em = setup_default_epoch_manager(validators, 100, 1, 1, 90, 60);

    let low_version = PROTOCOL_VERSION - 1;
    let high_version = PROTOCOL_VERSION;
    let small_stake = Balance::from_yoctonear(1_000);
    let large_stake = Balance::from_yoctonear(2_000);
    let account: AccountId = "test0".parse().unwrap();

    let h = hash_range(5);
    record_block(&mut em, CryptoHash::default(), h[0], 0, vec![]);
    record_block_with_version(
        &mut em,
        h[0],
        h[1],
        1,
        vec![stake("test0".parse().unwrap(), small_stake)],
        low_version,
    );
    // Block 3 (height 2 skipped): high version + large proposal. The later block must win.
    record_block_with_version(
        &mut em,
        h[1],
        h[3],
        3,
        vec![stake("test0".parse().unwrap(), large_stake)],
        high_version,
    );

    let aggregator = em.get_epoch_info_aggregator_upto_last(&h[3]).unwrap();
    assert_eq!(
        aggregator.version_tracker.get(&0),
        Some(&high_version),
        "version_tracker must hold the latest (highest-height) reported version"
    );
    assert_eq!(
        aggregator.all_proposals.get(&account).map(|p| p.stake()),
        Some(large_stake),
        "all_proposals must hold the latest (highest-height) proposal"
    );
}
