### Title
Split-lock TOCTOU in the anti-replay window lets concurrently-processed duplicate/replayed packets bypass replay protection - (File: connection_state.go)

### Summary
The reported DeFi bug is a "state-check split across two operations" flaw: a state flag (`depositBlock`) is set by one call and read by a later, logically-related call, and the check window between the two allows a legitimate second operation to be wrongly blocked/permitted because the checked state doesn't reflect the true, up-to-date condition at the moment it matters. The same bug *class*—a security-relevant check and the corresponding state update being separated across two independent critical sections, with unsynchronized work happening in between—exists in Nebula's per-tunnel anti-replay logic in `ConnectionState.Decrypt` and `ConnectionState.VerifyRelay`.

### Finding Description
`ConnectionState.Decrypt` and `ConnectionState.VerifyRelay` both perform the replay check (`window.Check`) and the replay-window commit (`window.Update`) as two *separate* lock acquisitions, with the actual AEAD decrypt/verify happening in between while the lock is released: [1](#0-0) 

```go
func (cs *ConnectionState) Decrypt(...) ([]byte, error) {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)   // step 1: check
	cs.decryptLock.Unlock()
	...
	out, err = cs.dKey.DecryptDanger(...)           // unsynchronized work
	...
	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)    // step 2: commit
	cs.decryptLock.Unlock()
	...
}
```

The same pattern appears in `VerifyRelay`: [2](#0-1) 

Inbound UDP packets for the same `HostInfo`/`ConnectionState` are dispatched to `readOutsidePackets`, which is invoked from per-queue reader goroutines (parameter `q int`): [3](#0-2)  and packets are looked up and dispatched to the shared `hostinfo.ConnectionState` for both direct data messages and relay frames: [4](#0-3) 

Because `Check` and `Update` are not atomic with respect to each other, if two copies of the same packet (e.g. a network-level duplicate, or an attacker-injected replay of a captured relay/data frame — no CA-signed certificate is required since this operates purely on already-established ciphertext) arrive close together and are processed by different reader goroutines, both can pass `Check` before either calls `Update`, because the window bit for that counter has not yet been set. Both goroutines then proceed to `DecryptDanger`/verify successfully (replaying the exact same ciphertext with the same nonce/counter decrypts identically) and both deliver the payload — once to the tun device, or once forwarded again by a relay — defeating the very purpose of the anti-replay window (`Bits`, `ReplayWindow = 1024`): [5](#0-4) 

This is precisely the "same block/window state-check split" bug class from the report: a shared piece of state (`depositBlock`/replay-window bit) is read in one step and written in a later step, and unrelated-but-concurrent activity in between invalidates the assumption that the state observed at check-time still holds at commit-time.

Notably, the relay path is exactly the scenario the project's own regression test targets — `TestRelayReplayProtection` explicitly checks that a captured relay frame replayed multiple times is dropped by the relay's replay window rather than re-forwarded: [6](#0-5)  and [7](#0-6) . That test exercises sequential replays; it does not exercise concurrent/racing delivery of the same counter across multiple reader goroutines, which is exactly the gap the split-lock design leaves open.

### Impact Explanation
An on-path or off-path attacker who can capture and duplicate/re-inject a single valid ciphertext frame (either a data message or, more impactfully, a relay-forwarded frame) can cause it to be processed twice under race conditions with the multi-queue UDP reader design, resulting in replayed traffic being delivered to the tun device twice or a relay re-forwarding a replayed frame — directly undermining the anti-replay guarantee Nebula depends on for message-counter/nonce uniqueness. This falls under "traffic decryption/forgery/replay" impact.

### Likelihood Explanation
Likelihood is Medium: it requires (a) the attacker to capture and duplicate/replay one legitimate frame at the network layer (no cert forgery needed), and (b) the duplicate to land on two different reader queues close enough in time to race past `Check` before either `Update` commits. Multiple UDP reader routines processing the same `hostinfo`/`ConnectionState` make this a real, not purely theoretical, race, and the project's changelog shows prior awareness of related replay-window race conditions ("Lock replay window updates so concurrent readers can't corrupt it", #1802; "Advance the replay window on relayed packets...", #1751), indicating this exact area has been a recurring source of races.

### Recommendation
Perform the replay-window `Check` and `Update` (or an atomic check-and-set) under a single, uninterrupted critical section that also covers/serializes against the decrypt/verify step for a given `messageCounter`, so that two concurrent deliveries of the same counter cannot both pass the check before either commits. Concretely, hold `decryptLock` across the full `Check` → `Decrypt/Verify` → `Update` sequence per packet (or use a compare-and-set primitive keyed on the counter) rather than releasing and reacquiring the lock around the decrypt call.

### Proof of Concept
1. Establish a tunnel (directly or via relay) and let one legitimate packet with message counter `N` be sent.
2. Capture the resulting ciphertext frame.
3. Re-inject the exact same UDP frame twice in rapid succession so that it is picked up by two different UDP reader goroutines (`readOutsidePackets` with different `q`) targeting the same `hostinfo`.
4. Because `window.Check(N)` is evaluated for both copies before either goroutine calls `window.Update(N)`, both goroutines observe "not yet seen," both successfully call `DecryptDanger`/verify, and both deliver the frame — once to the tun device (data path) or once forwarded again toward the relay target (relay path) — resulting in the replayed packet being processed twice despite the anti-replay window.

```go
	cs.decryptLock.Unlock()

		return nil, ErrAlreadySeen
	}
```

```go
func (cs *ConnectionState) VerifyRelay(l *slog.Logger, messageCounter uint64, packet []byte, nb []byte) error {
	cs.decryptLock.Lock()
	result := cs.window.Check(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	signedPayload := packet[:len(packet)-cs.dKey.Overhead()]
	signatureValue := packet[len(packet)-cs.dKey.Overhead():]
	_, err := cs.dKey.DecryptDanger(nil, signedPayload, signatureValue, messageCounter, nb)
	if err != nil {
		return err
	}

	cs.decryptLock.Lock()
	result = cs.window.Update(l, messageCounter)
	cs.decryptLock.Unlock()
	if !result {
		return ErrAlreadySeen
	}

	return nil
```
