### Title
Integer underflow in `InputZipFile::EnsureRemaining` bounds check bypasses bounds validation on attacker-controlled ZIP central-directory offsets - (File: `third_party/ijar/zip.cc`)

### Summary
`ijar`'s ZIP reader (`third_party/ijar/zip.cc`) computes the input cursor for each entry directly from an unvalidated, attacker-controlled 64-bit `offset` field taken from the central directory, then relies on `EnsureRemaining()` to bound subsequent reads. `EnsureRemaining()` performs an unsigned subtraction (`input_file_->Length() - in_offset`) that underflows when the crafted offset pushes the cursor past (or before) the mapped file, defeating the very check meant to prevent out-of-bounds reads.

### Finding Description
In `InputZipFile::ProcessNext()`: [1](#0-0) 

`offset` is read straight from the central directory entry (and can additionally be overridden by a Zip64 extra field, `get_u8le(extra)`), fully attacker-controlled via a crafted `.zip`/`.jar` file: [2](#0-1) 

The cursor is then computed as `p = zipdata_in_ + in_offset_ + offset;` with no validation that `offset` is within `[0, input_file_->Length())`. Immediately after, `EnsureRemaining(4, "signature")` is called to bound-check the read: [3](#0-2) 

`EnsureRemaining` computes `size_t in_offset = p - zipdata_in_;` and `size_t remaining = input_file_->Length() - in_offset;`. Both operands are `size_t` (unsigned). If the attacker-supplied `offset` is large enough that `in_offset > input_file_->Length()`, the subtraction underflows and wraps to a huge value, so the guard `if (n > remaining)` never fires. The subsequent `get_u4le(p)` and the rest of `ProcessLocalFileEntry` then dereference `p`, which points arbitrarily far outside the `mmap`'d input file region, producing an out-of-bounds read (and potential crash/segfault, or leakage of adjacent mapped memory as parsed field values) — the same "unchecked arithmetic on attacker-controlled size/offset field feeds a bounds decision" bug class as the CVE-2022-23587 analog (crop/resize cost estimator overflow driving unsafe downstream behavior from unvalidated user-controlled integers).

This mirrors the requested bug class (archive extraction/parsing of untrusted content, `ZipDecompressor`-equivalent), except here it is `ijar`'s own hand-rolled ZIP central-directory parser rather than the java `ZipDecompressor`. `ijar` is invoked on JAR files that are produced from external/third-party dependencies (e.g. via `java_import`/interface-jar generation and `singlejar`-family tools that share the same `zip.cc`/`zip_headers.h` parsing logic), meaning a malicious pre-built `.jar` served from a registry/mirror and consumed by a build is sufficient to trigger this, with no local machine access needed.

### Impact Explanation
An attacker who supplies a malicious `.jar`/`.zip` archive that is fetched and processed by `ijar` during a build (e.g., as a `java_import` dependency or through jar-processing build actions) can craft a central directory offset that causes the parser to read (and act on) memory far outside the mapped input file. This can crash the build process (denial of service for that action) or cause the parser to interpret out-of-bounds memory as attacker-influenced-adjacent header fields, propagating incorrect data into files that further outputs are derived from. It is a memory-safety violation in native (C++) code processing untrusted, attacker-served input — not merely a resource-exhaustion issue, since it stems directly from an unchecked-arithmetic containment failure in the bounds-check itself.

### Likelihood Explanation
High for reachability: any build that consumes a third-party JAR that is passed through `ijar` (a stock part of Bazel's Java toolchain for interface-jar generation) exercises this code path automatically, with no special build configuration required. The only requirement is that the attacker control the bytes of the archive fetched by the build (e.g., a compromised or malicious Maven artifact/mirror), which matches the specified "hostile origin server" threat model. The crafted offset value is a single 4-byte (or 8-byte via Zip64 extra field) integer in the central directory — trivial to construct.

### Recommendation
In `InputZipFile::ProcessNext()`, validate `offset` against `input_file_->Length()` (i.e., `offset <= input_file_->Length()`) before computing `p`, and reject the entry otherwise. Additionally, harden `EnsureRemaining()` to first check `in_offset <= input_file_->Length()` before performing the subtraction, returning an error instead of allowing an unsigned underflow to silently pass the check: [4](#0-3) 

### Proof of Concept
Construct a minimal ZIP file where the central directory entry's local-header offset (or the Zip64 64-bit offset override in the extra field) is set to a value greater than the total file length (e.g., `0xFFFFFFFFFFFFFFF0`). Feed this file to `ijar` (`devtools_ijar::ZipExtractor::Create` + `ProcessAll()`, as used by `third_party/ijar/ijar.cc`'s `OpenFilesAndProcessJar`). Expected: the crafted offset causes `p = zipdata_in_ + in_offset_ + offset` to point outside the mapped region; `EnsureRemaining(4, "signature")` underflows in its `Length() - in_offset` computation and does not report an error; `get_u4le(p)` reads out-of-bounds memory, which should be observable as a segmentation fault under ASan/valgrind or via a `BuildIntegrationTestCase`/`src/test/shell/bazel` test that builds a `java_import` target pointing at this crafted jar and asserts the build crashes/fails with a memory-safety signal rather than a clean "invalid zip" error.

bool InputZipFile::ProcessNext() {
  // Process the next entry in the central directory. Also make sure that the
  // content pointer is in sync.
  u8 compressed, uncompressed;
  u8 offset;
  if (!ProcessCentralDirEntry(central_dir_current_, &compressed, &uncompressed,
                              filename, PATH_MAX, &attr, &offset)) {
    return false;
  }

  // There might be an offset specified in the central directory that does
  // not match the file offset, so always update our pointer.
  p = zipdata_in_ + in_offset_ + offset;

  if (EnsureRemaining(4, "signature") < 0) {
    return false;
  }
  u4 signature = get_u4le(p);
  if (signature == LOCAL_FILE_HEADER_SIGNATURE) {
    if (ProcessLocalFileEntry(compressed, uncompressed) < 0) {
      return false;
    }
  } else {
    error("local file header signature for file %s not found\n", filename);
    return false;
  }

  return true;
}
