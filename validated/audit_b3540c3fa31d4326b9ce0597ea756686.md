## Analysis

Comparing this bug class (GoGo Protobuf's *"skippy peanut butter"* issue — an unmarshal skip routine that advances a cursor using a length field it never validates against the buffer boundary) to bazel's own extraction code, the closest match is in `third_party/ijar/zip.cc`'s central-directory parser.

### Title
Unvalidated length-based pointer arithmetic in ijar's ZIP central directory parser leads to out-of-bounds reads on attacker-supplied jars - (File: `third_party/ijar/zip.cc`)

### Summary
`InputZipFile::ProcessCentralDirEntry` reads `file_name_length`, `extra_field_length`, and `file_comment_length` directly from the (attacker-controlled) ZIP central directory and unconditionally advances the cursor `p` and the extra-field cursor `extra_p` by those lengths, with no check that the resulting pointers stay within the mapped input file or within the declared central-directory region.

### Finding Description
`ProcessCentralDirEntry` reads the central-directory header fields and advances `p` by `file_name_length`, then walks the "extra fields" sub-records: [1](#0-0) 

```
p += file_name_length;
const u1 *extra_p = p;
p += extra_field_length;
while (extra_p != p) {
  const u2 header_id = get_u2le(extra_p);
  const u2 data_size = get_u2le(extra_p);
  const u1 *extra = extra_p;
  extra_p += data_size;
  ...
}
```
There is no bound check that `extra_p + 4 + data_size <= p`, nor that `p` (after advancing by `file_name_length`/`extra_field_length`/`file_comment_length`) stays inside the mapped file. This is unlike sibling parsers in the same codebase that were hardened against exactly this pattern, e.g. `src/tools/singlejar/output_jar.cc`'s extra-field loop explicitly validates bounds before trusting `ef->size()`: [2](#0-1) 

By contrast, `InputZipFile::ProcessLocalFileEntry` (used for *local* file headers) does call `EnsureRemaining()` before trusting `file_name_length_`/`extra_field_length_`: [3](#0-2) 

But `ProcessCentralDirEntry`, invoked both from `ProcessNext()` (used while iterating entries) and `CalculateOutputLength()` (used to size the output buffer), has no equivalent `EnsureRemaining` calls anywhere in its body: [4](#0-3) [5](#0-4) [6](#0-5) 

The only boundary check upstream is on the central directory as a whole (`cd.central_dir_offset + cd.central_dir_size > in_length`) performed in `FindZipCentralDirectory`: [7](#0-6) 

That check bounds the aggregate declared central-directory region but does not validate that any individual entry's `file_name_length + extra_field_length + file_comment_length` fits within the remaining bytes of that region (or within the mapped file at all for the last entry). A crafted entry near the end of the central directory (or the last entry) can set these 16-bit length fields so that `p`/`extra_p` walk past `input_file_->Length()`, causing subsequent `get_u2le`/`get_u4le`/`get_u8le` calls to read out-of-bounds memory adjacent to the mmap'd region.

### Impact Explanation
ijar is invoked by the Java toolchain to generate interface jars from arbitrary jar inputs, including jars originating from external, attacker-controlled dependencies (e.g., fetched via `http_jar`/`http_archive`/Maven-resolved artifacts) — content an unprivileged, malicious registry/mirror/dependency author fully controls. Out-of-bounds reads triggered while parsing such a jar can corrupt derived values (`compressed_size`, `uncompressed_size`, `offset`) that are subsequently used to size buffers and index into the mapped input file elsewhere in the extraction pipeline (`CalculateOutputLength`, `ProcessNext`/`ProcessLocalFileEntry`), and can crash the build process or leak adjacent process memory into fields consumed downstream.

### Likelihood Explanation
Reachability requires only that a project process a maliciously crafted `.jar`/zip file through ijar, which is standard for any Java dependency in a `java_import`/interface-jar-producing target. No credentials, no MITM, and no access to the requester's machine are required — only the ability to publish a jar file that gets built into a jar target.

### Recommendation
Add `EnsureRemaining`-style bounds checks in `InputZipFile::ProcessCentralDirEntry` before advancing `p`/`extra_p` by any length field read from the central directory (`file_name_length`, `extra_field_length`, `file_comment_length`, and each extra-field's `data_size`), mirroring the validation already present in `ProcessLocalFileEntry` and in `src/tools/singlejar/output_jar.cc`'s extra-field walker.

### Proof of Concept
A `src/test/shell/bazel` (or ijar's own `third_party/ijar/test/zip_test.sh`) test constructing a ZIP file whose central directory entry declares `extra_field_length`/`file_name_length`/`file_comment_length` values that, summed with the entry's offset, exceed the file's actual length (or whose extra-field `data_size` exceeds the remaining `extra_field_length` bytes), then invoking the `ijar`/`zipper` binary (or `InputZipFile::CalculateOutputLength`) on it and observing a crash or corrupted parsed size fields — analogous to the existing `third_party/ijar/test/zip_test.sh:test_no_path_traversal` regression test pattern shown at: [8](#0-7)

bool InputZipFile::ProcessCentralDirEntry(const u1 *&p, u8 *compressed_size,
                                          u8 *uncompressed_size, char *filename,
                                          size_t filename_size, u4 *attr,
                                          u8 *offset) {
  u4 signature = get_u4le(p);

  if (signature != CENTRAL_FILE_HEADER_SIGNATURE) {
    if (signature != DIGITAL_SIGNATURE && signature != EOCD_SIGNATURE &&
        signature != ZIP64_EOCD_SIGNATURE) {
      error("invalid central file header signature: 0x%x\n", signature);
    }
    return false;
  }

  p += 16;  // skip to 'compressed size' field
  *compressed_size = get_u4le(p);
  *uncompressed_size = get_u4le(p);
  u2 file_name_length = get_u2le(p);
  u2 extra_field_length = get_u2le(p);
  u2 file_comment_length = get_u2le(p);
  p += 4;  // skip to external file attributes field
  *attr = get_u4le(p);
  *offset = get_u4le(p);
  {
    size_t len = (file_name_length < filename_size)
      ? file_name_length
      : (filename_size - 1);
    memcpy(reinterpret_cast<void*>(filename), p, len);
    filename[len] = 0;
  }
  p += file_name_length;
  const u1 *extra_p = p;
  p += extra_field_length;
  while (extra_p != p) {
    const u2 header_id = get_u2le(extra_p);
    const u2 data_size = get_u2le(extra_p);
    const u1 *extra = extra_p;
    extra_p += data_size;
    if (header_id == ZIP64_EXTRA_FIELD_TAG) {
      if (*uncompressed_size == U4_MAX) {
        *uncompressed_size = get_u8le(extra);
      }
      if (*compressed_size == U4_MAX) {
        *compressed_size = get_u8le(extra);
      }
      if (*offset == U4_MAX) {
        *offset = get_u8le(extra);
      }
    }
  }
  p += file_comment_length;
  return true;
}

u8 InputZipFile::CalculateOutputLength() {
  const u1* current = central_dir_;

  u8 compressed_size = 0;
  u8 uncompressed_size = 0;
  u8 skipped_compressed_size = 0;
  u4 attr;
  u8 offset;
  char filename[PATH_MAX];

  while (true) {
    u8 file_compressed, file_uncompressed;
    if (!ProcessCentralDirEntry(current,
                                &file_compressed, &file_uncompressed,
                                filename, PATH_MAX, &attr, &offset)) {
      break;
    }

    if (processor->Accept(filename, attr)) {
      compressed_size += (u8) file_compressed;
      uncompressed_size += (u8) file_uncompressed;
    } else {
      skipped_compressed_size += file_compressed;
    }
  }

  // The worst case is when the output is simply the input uncompressed. The
  // metadata in the zip file will stay the same, so the file will grow by the
  // difference between the compressed and uncompressed sizes.
  return (u8) input_file_->Length() - skipped_compressed_size
      + (uncompressed_size - compressed_size);
}
