## Analog Found

### Title
Integer overflow via unchecked `BigInteger.longValue()` truncation in voter reward computation allows arbitrary reward/allowance inflation - (File: `chainbase/src/main/java/org/tron/core/service/MortgageService.java`, `actuator/src/main/java/org/tron/core/vm/utils/VoteRewardUtil.java`)

### Summary
Both the legacy witness-vote reward path (`MortgageService.computeReward`) and the TVM-native reward path (`VoteRewardUtil.computeReward`) compute a voter's reward as a `BigInteger` product/division and then convert it to a primitive `long` using `.longValue()`, which silently truncates on overflow instead of throwing, unlike the `longValueExact()` calls used elsewhere in the same codebase for equivalent arithmetic (e.g. TVM `voteWitness` and `calculateGlobalLimitV1`). This mirrors the CVE-2026-48486 bug class: an unchecked integer overflow in reward/fee accounting that can silently produce an arbitrarily different (and potentially much larger) credited amount.

### Finding Description
The reward-per-vote mechanism accumulates a cumulative `BigInteger` "Vi" value per Standard Representative (SR) cycle, based on `reward * 10^18 / voteCount` [1](#0-0) . Because this accumulator is stored as an arbitrary-precision `BigInteger`, no overflow occurs there. However, when a voter withdraws their share of the reward, both reward-computation code paths convert the final result back to a bounded 64-bit `long` using the non-exact conversion: [2](#0-1) [3](#0-2) 

`BigInteger.longValue()` does not throw `ArithmeticException` on overflow — it returns the low-order 64 bits of the two's-complement representation, i.e. an essentially arbitrary wrapped value that can be far larger (or negative) than the true, economically-justified reward. This is inconsistent with the rest of the codebase's careful use of `longValueExact()` in equivalent BigInteger-to-long conversions for reward/energy accounting, e.g. in TVM's `voteWitness` opcode handler and `ResourceProcessor.calculateGlobalLimitV1`: [4](#0-3) [5](#0-4) 

The wrapped `reward` value is then passed straight into `adjustAllowance`, which credits it into the account's `allowance` field (later merged into `balance` on withdrawal) with no further magnitude/sanity check beyond a simple `<=0` early exit: [6](#0-5) 

Because `deltaVi` (the per-cycle Vi accumulation, `reward * 10^18 / voteCount`) grows unboundedly as a `BigInteger` when `voteCount` is small relative to `reward`, and the final consumption step multiplies `deltaVi` by an attacker-controlled `userVote` before dividing by the `10^18` decimal factor, the intermediate/final product can exceed `Long.MAX_VALUE` (~9.2×10^18) while remaining a valid (unbounded) `BigInteger`. The `.longValue()` truncation then yields an unpredictable, potentially large positive `long` credited to the voter's allowance — an unbacked balance inflation reachable purely by an unprivileged voter's own transactions (vote allocation + timing across cycles + withdrawal), with no cooperation from a malicious SR/witness/validator required (the SR's own reward pool math is untouched — the manipulation happens purely in the voter-side reward attribution formula).

### Impact Explanation
A successful trigger credits an attacker's account `allowance`/`balance` with an amount unrelated to (and potentially far exceeding) the actual reward pool contributed by the network, i.e. an unbacked balance / arbitrary reward inflation — matching the CVSS 7.5 Integrity-impact classification of the referenced CVE. This is reachable via the reward-withdrawal paths used by any TRX holder: `WithdrawBalanceActuator`/`UnfreezeBalanceActuator` (legacy path, `MortgageService.withdrawReward`) and the TVM `withdrawReward()` precompile (`VoteRewardUtil.withdrawReward` / `WithdrawRewardProcessor`) [7](#0-6) .

### Likelihood Explanation
Exploitation requires an attacker (as an ordinary voter, not a malicious SR) to engineer conditions where `deltaVi * userVote / DECIMAL_OF_VI_REWARD` crosses the 64-bit boundary — e.g. by voting for/holding a large vote weight against SR cycles that accrued disproportionately large Vi deltas (small `voteCount` relative to distributed `reward`) across many maintenance cycles, since Vi accumulation is unbounded (`BigInteger`) and persists indefinitely via `DelegationStore.accumulateWitnessVi`. This requires sustained setup across cycles but no special privilege, and no code path currently guards against the resulting truncation, unlike the `longValueExact()` pattern used elsewhere for analogous reward/energy math.

### Recommendation
Replace `.longValue()` with `.longValueExact()` (as already done in `Program.voteWitness` and `ResourceProcessor.calculateGlobalLimitV1`) in both `MortgageService.computeReward` and `VoteRewardUtil.computeReward`, and handle the resulting `ArithmeticException` by failing the withdrawal/reward computation safely (e.g., clamping or rejecting) rather than silently truncating. Additionally, consider capping accumulated `Vi` growth or the per-withdrawal reward to a sane upper bound tied to actual total token supply.

### Proof of Concept
1. An attacker sets up (or controls) an SR receiving block/tx-fee rewards while its total `voteCount` for a given cycle is minimized, causing `DelegationStore.accumulateWitnessVi` to record an extremely large `deltaVi = reward * 10^18 / voteCount` [8](#0-7) .
2. This repeats over multiple maintenance cycles, causing the SR's cumulative Vi (arbitrary-precision `BigInteger`) to grow far beyond `Long.MAX_VALUE`.
3. The attacker then casts (or already holds) a large `userVote` weight for that SR and calls `WithdrawBalanceContract` (or TVM `withdrawReward()`), triggering `computeReward(beginCycle, endCycle, accountCapsule)`, where `deltaVi.multiply(BigInteger.valueOf(userVote)).divide(DECIMAL_OF_VI_REWARD)` exceeds the `long` range and `.longValue()` truncates it to an arbitrary 64-bit value [9](#0-8) .
4. If the truncated value is a large positive `long`, it is credited via `adjustAllowance` into the attacker's account balance without any sanity bound, inflating funds beyond what the network's actual reward pool ever paid out.

    BigInteger preVi = getWitnessVi(cycle - 1, address);
    long reward = getReward(cycle, address);
    if (reward == 0 || voteCount == 0) { // Just forward pre vi

    } else { // Accumulate delta vi

          .multiply(DECIMAL_OF_VI_REWARD)
          .divide(BigInteger.valueOf(voteCount));
      setWitnessVi(cycle, address, preVi.add(deltaVi));
    }
  }

  public void adjustAllowance(AccountStore accountStore, byte[] accountAddress, long amount)
      throws BalanceInsufficientException {
    AccountCapsule account = accountStore.getUnchecked(accountAddress);
    long allowance = account.getAllowance();
    if (amount == 0) {
      return;
    }

    if (amount < 0 && allowance < -amount) {
      throw new BalanceInsufficientException(
          String.format("%s insufficient balance, amount: %d, allowance: %d",
              StringUtil.createReadableString(accountAddress), amount, allowance));
    }
    account.setAllowance(allowance + amount);
    accountStore.put(account.createDbKey(), account);
  }

  public long execute(WithdrawRewardParam param, Repository repo) throws ContractExeException {
    byte[] ownerAddress = param.getOwnerAddress();

    VoteRewardUtil.withdrawReward(ownerAddress, repo);

    AccountCapsule accountCapsule = repo.getAccount(ownerAddress);
    long oldBalance = accountCapsule.getBalance();
    long allowance = accountCapsule.getAllowance();
    long newBalance = 0;

    try {
      newBalance = LongMath.checkedAdd(oldBalance, allowance);
    } catch (ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractExeException(e.getMessage());
    }

    // If no allowance, do nothing and just return zero.
    if (allowance <= 0) {
      return 0;
    }

    accountCapsule.setInstance(accountCapsule.getInstance().toBuilder()
        .setBalance(newBalance)
        .setAllowance(0L)
        .setLatestWithdrawTime(param.getNowInMs())
        .build());

    repo.updateAccount(accountCapsule.createDbKey(), accountCapsule);
    return allowance;
  }
