### Title
Unbounded `CountDownLatch.await()` in parallel transaction signature verification can hang block processing indefinitely - ([File: framework/src/main/java/org/tron/core/db/Manager.java])

### Summary
`Manager.preValidateTransactionSign()` submits one `ValidateSignTask` per transaction to `validateSignService` and then blocks on `countDownLatch.await()` with **no timeout**, unlike the analogous parallel-verification patterns in `PrecompiledContracts.BatchValidateSign`/`VerifyProof` which bound the wait with `countDownLatch.await(getCPUTimeLeftInNanoSecond(), TimeUnit.NANOSECONDS)`. This mirrors the LlamaIndex CWE-755/835 pattern: a consumer loop/latch waits forever for producer threads whose completion signal is not guaranteed to always arrive. [1](#0-0) 

### Finding Description
`preValidateTransactionSign` is invoked from `processBlock` for every non-self-generated block on the main block-application path: [2](#0-1) 

For each transaction it submits a `ValidateSignTask` to the fixed-size `validateSignService` pool and awaits a `CountDownLatch` sized to the transaction count, but calls `countDownLatch.await();` with **no timeout argument**: [3](#0-2) 

`ValidateSignTask.call()` does decrement the latch in a `finally` block, so as long as every submitted task actually executes on a worker thread, the latch reaches zero. However, this is the only place in the codebase using this parallel-verify pattern without a bounded wait — `BatchValidateSign` and `VerifyProof` explicitly guard with `getCPUTimeLeftInNanoSecond()` specifically because unbounded awaits on signature-verification threads are recognized as unsafe elsewhere in the same codebase: [4](#0-3) 

`validateSignThreadNum` is a fixed pool sized from config, and the transaction count per block is unbounded relative to the pool. If the pool becomes saturated or a worker thread is lost/blocked (e.g., stuck in `recoverAddrBySign`/ECDSA verification on adversarially crafted signature bytes, or any thread starvation), tasks queued behind it may never run, and the `CountDownLatch` for that block's verification never reaches zero — main block application blocks indefinitely inside the `synchronized (blockLock)` region of `TronNetDelegate.processBlock`.

### Impact Explanation
Because `processBlock`/`pushBlock` execute under `synchronized (blockLock)` (see `TronNetDelegate.processBlock`), a hang inside `preValidateTransactionSign` stalls all subsequent block application on the node — a full node/witness denial-of-service reachable by broadcasting or relaying a block whose transactions are crafted to exhaust or starve the `validate-sign` thread pool. This matches the CVSS 3.0 AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H profile of the reference advisory (node/service availability impact, no confidentiality/integrity impact).

### Likelihood Explanation
Reachability requires triggering thread starvation/loss in the fixed `validateSignService` pool while a block is being processed. This is a plausible but not fully proven path in this analysis — I could not confirm within the available tool calls that any specific `TransactionCapsule.validateSignature`/ECDSA recovery call can hang or leak worker threads indefinitely (the underlying `recoverAddrBySign` path was not fully traced here). Without a demonstrated way to cause a worker thread to never complete or never be scheduled, this remains a structural risk (missing timeout / exception-handling symmetry with the precompiled-contract code) rather than a confirmed exploitable hang.

### Recommendation
Add a bounded timeout to `countDownLatch.await(...)` in `preValidateTransactionSign`, mirroring the `getCPUTimeLeftInNanoSecond()`/fixed-timeout pattern already used in `PrecompiledContracts.BatchValidateSign` and `VerifyProof`, and treat a timeout as a validation failure (reject the block/transactions) rather than blocking forever.

### Proof of Concept
Not independently reproduced: the analysis identifies the missing-timeout code pattern at `Manager.java:2120` by comparison with the timeout-guarded analog in `PrecompiledContracts.java:1201-1207`, but I could not confirm within this session a concrete transaction/signature payload that stalls a `validate-sign` worker thread indefinitely to trigger the hang. This should be validated with a Devin session that can run the full test suite and attempt to starve/kill worker threads in `validateSignService` under load.

  private void preValidateTransactionSign(List<TransactionCapsule> txs)
      throws InterruptedException, ValidateSignatureException {
    int transSize = txs.size();
    if (transSize <= 0) {
      return;
    }
    Histogram.Timer requestTimer = Metrics.histogramStartTimer(
        MetricKeys.Histogram.VERIFY_SIGN_LATENCY, MetricLabels.TRX);
    try {
      CountDownLatch countDownLatch = new CountDownLatch(transSize);
      List<Future<Boolean>> futures = new ArrayList<>(transSize);

      for (TransactionCapsule transaction : txs) {
        Future<Boolean> future = validateSignService
            .submit(new ValidateSignTask(transaction, countDownLatch, chainBaseManager));
        futures.add(future);
      }
      countDownLatch.await();

      for (Future<Boolean> future : futures) {
        try {
          future.get();
        } catch (ExecutionException e) {
          throw new ValidateSignatureException(e.getCause().getMessage());
        }
      }
    } finally {
      Metrics.histogramObserve(requestTimer);
    }
  }
