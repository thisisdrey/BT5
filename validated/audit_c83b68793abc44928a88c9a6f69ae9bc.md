This confirms the analog: `GlobalContractDeployMode::AccountId` explicitly makes a global contract mutable — "This allows the owner to update the contract for all its users" [1](#0-0) , and this is exactly what NEAR-Deterministic account IDs (NEP-616) can reference via `GlobalContractIdentifier::AccountId`.

### Title
Deterministic account ID does not guarantee deterministic contract code when `state_init.code` references a mutable `GlobalContractIdentifier::AccountId` - (File: `runtime/runtime/src/deterministic_account_id.rs`)

### Summary
A NEP-616 deterministic account ID is derived only from the borsh-encoded `DeterministicAccountStateInit` (its `code` identifier and `data` map), not from the actual bytecode. When `code` is a `GlobalContractIdentifier::AccountId(owner)` reference rather than `GlobalContractIdentifier::CodeHash`, the identifier hashed into the account ID is stable, but the code it resolves to at execution time is not, because the owning account can redeploy new code under that same `AccountId`-mode global contract at any time.

### Finding Description
`derive_near_deterministic_account_id` hashes the borsh encoding of `DeterministicAccountStateInit`, which contains `code: GlobalContractIdentifier` and `data: BTreeMap<...>` [2](#0-1) . `GlobalContractIdentifier::AccountId(AccountId)` is one of the two valid forms [3](#0-2) . The account-id derivation and validation (`validate_deterministic_state_init`) only check that `derived_id == receiver_id`; they never pin the identifier to a fixed code hash when it is the `AccountId` variant [4](#0-3) .

When the account is actually initialized, `deploy_deterministic_account` calls `use_global_contract(state_update, account_id, account, state_init.code(), result)` to fetch and attach the contract that is *currently* published under that `AccountId` identifier [5](#0-4) . `GlobalContractDeployMode::AccountId` is documented and tested to allow the owner to redeploy/update the code referenced by that identifier at will — "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users" [1](#0-0) , and `test_global_contract_update` demonstrates a live account switching from one deployed contract to another under the same `AccountId` identifier without any hash-pinning [6](#0-5) .

Consequently, two parties who independently compute the same deterministic account ID in advance (as intended by NEP-616, to fund/prepare an account before it is initialized) may end up with a materially different program executing at that account ID, depending only on when the `DeterministicStateInitAction` lands relative to the global-contract owner's redeploys — exactly the address/behavior non-determinism pattern described in the Maverick report, where the pre-computed target diverges from what actually gets deployed at execution time because a non-binding, mutable reference was used to construct the "address."

### Impact Explanation
An unprivileged signer that pre-derives a deterministic account ID (e.g., to fund it via `Transfer` before init, or to reason about what contract logic will run there) can be misled: the code hash actually installed at that account is controlled by a third party (the `AccountId`-mode global contract owner) and can change between the time the ID is derived/funded and the time `DeterministicStateInitAction` executes. This can result in funds/deposits being locked into, or interacting with, unexpected contract logic at an account whose ID a user believed was cryptographically bound to specific, immutable code — a state-divergence/authorization-escalation risk analogous to the CREATE2 pool-address bug (address stable, backing logic mutable).

### Likelihood Explanation
This requires deliberate use of the `AccountId` deploy mode for the referenced global contract (as opposed to the immutable `CodeHash` mode) combined with the owner updating the contract, both of which are explicitly supported, first-class, unprivileged features (`DeployGlobalContractAction` with `GlobalContractDeployMode::AccountId`, `UseGlobalContractAction`) reachable by any account, not requiring any special/validator permission. The severity depends on whether protocol/application conventions expect deterministic-account code to be immutable once the ID is derived; nothing in the validation path (`validate_deterministic_state_init`) enforces that the referenced global contract be pinned by hash.

### Recommendation
Require (or at minimum strongly recommend/enforce for the deterministic-account use case) that `DeterministicAccountStateInit.code` only accept `GlobalContractIdentifier::CodeHash`, not the mutable `AccountId` variant, so that the derived `0s...` account ID is bound to immutable bytecode — mirroring the Maverick fix of removing all non-key-determining/mutable parameters from what determines the address. If `AccountId`-mode references must remain supported for flexibility, document explicitly (and consider surfacing at the RPC/validation layer) that deterministic IDs built from such references do not guarantee code determinism, and consider snapshotting/pinning the code hash at `DeterministicStateInitAction` execution time as part of the account's on-chain, immutable record.

### Proof of Concept
1. Account `owner` deploys contract `A` via `DeployGlobalContractAction { deploy_mode: AccountId }`, giving `GlobalContractIdentifier::AccountId(owner)`.
2. A user constructs `DeterministicAccountStateInit { code: GlobalContractIdentifier::AccountId(owner), data: {...} }` and derives `det_id = derive_near_deterministic_account_id(state_init)`, then sends a `Transfer` to fund `det_id` (per NEP-616, a `Transfer` may fund it before init) — see `spread()` in the test contract for the analogous pattern of deriving-then-funding [7](#0-6) .
3. Before the `DeterministicStateInitAction` is submitted/executed, `owner` redeploys different code `B` under the same `AccountId`-mode identifier (as shown feasible in `test_global_contract_update` [6](#0-5) ).
4. When `action_deterministic_state_init` finally executes for `det_id`, `deploy_deterministic_account`/`use_global_contract` attaches whatever code is *currently* registered under `owner` — contract `B`, not `A` — even though `det_id` was derived and funds were committed under the expectation of `A`'s logic [5](#0-4) .

/// Returns a NEP-616 compliant deterministic account id.
/// This is a NEAR-implicit account ID which is fully defined by its initial state.
pub fn derive_near_deterministic_account_id(
    state_init: &DeterministicAccountStateInit,
) -> AccountId {
    use sha3::Digest;
    let mut hasher = sha3::Keccak256::new();
    borsh::to_writer(&mut hasher, state_init).expect("borsh must not fail");
    let hash: [u8; 32] = hasher.finalize().into();
    format!("0s{}", hex::encode(&hash[12..32])).parse().unwrap()
}
