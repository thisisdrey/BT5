### Title
Unauthenticated stage-1 handshake flood causes unbounded per-packet Noise DH computation with no rate limit or proof-of-work - (File: handshake_manager.go)

### Summary
`HandshakeManager.HandleIncoming` routes every stage-1 packet (`h.MessageCounter == 1`, `h.RemoteIndex == 0`) directly into `beginHandshake`, which allocates a fresh `handshake.Machine` and calls `machine.ProcessPacket`, unconditionally performing a Noise Diffie-Hellman computation via `m.hs.ReadMessage` before any certificate check occurs. There is no per-source-address rate limit, cookie, or proof-of-work gate before this expensive crypto operation, so an attacker who can send raw spoofed UDP packets can force the responder to do one DH operation per unique packet with no cost to the attacker.

### Finding Description
`HandleIncoming` only performs two cheap, non-cryptographic checks before dispatching to `beginHandshake`: a subtype check and a `RemoteIndex == 0` check, plus an optional remote allow-list check (`AllowUnknownVpnAddr`) that is a config-based ACL, not a rate limiter. [1](#0-0) 

`beginHandshake` then unconditionally constructs a new `handshake.Machine` and calls `machine.ProcessPacket(nil, packet)` for every accepted stage-1 packet: [2](#0-1) 

Inside `ProcessPacket`, `m.hs.ReadMessage(nil, packet[header.Len:])` runs before any certificate-related logic — for the IX pattern's first message this performs an actual elliptic-curve DH computation using the responder's static key and the attacker-supplied ephemeral/static key material: [3](#0-2) 

Only after `ReadMessage` succeeds does the code reach `validateCert`, which calls the `certVerifier` (`hm.certVerifier()` → `CAPool.VerifyCertificate`/`verify`). Contrary to the question's exact framing, the cert-chain walk itself is *not* unconditionally expensive for arbitrary forged certificates: `verify()` first does a cheap map lookup via `GetCAForCert` keyed on the cert's `Issuer()` string, and fails immediately (`ErrCaNotFound`) for any issuer that isn't a real, known CA fingerprint — before the costly `c.CheckSignature` call: [4](#0-3) 

However, this cheap issuer check does not protect against the primary cost, which is the Noise DH already performed in `ReadMessage` for *every* stage-1 packet regardless of what certificate (if any) follows. Since a valid Noise message-1 only requires the attacker to supply a syntactically valid curve point as their ephemeral/static key (trivial and cheap to generate), the attacker pays effectively nothing while the responder pays a DH computation per unique packet. There is no cookie/anti-amplification mechanism (unlike WireGuard's under-load cookie-reply) and no per-source-IP or per-packet rate limiting anywhere in `HandleIncoming`/`beginHandshake` before this cost is incurred. `CheckAndComplete` (reached only after a successful handshake) is irrelevant to this cost, since the DH work happens far earlier and unconditionally.

### Impact Explanation
An attacker with only raw UDP send capability (no valid cert, no CA access) can force the target node to perform one Noise ECDH operation per unique, spoofed-source stage-1 packet sent, with no verification of source-IP authenticity and no rate limiting. At sufficient packet rate/parallelism from many spoofed source addresses, this can exhaust responder CPU, degrading or denying legitimate handshake and tunnel-maintenance processing — a remote unauthenticated CPU-exhaustion DoS. This matches the "remote crash/wedge"-class impact for availability, though it is a resource-exhaustion DoS rather than a memory-safety crash or authentication bypass.

### Likelihood Explanation
Preconditions match exactly what's stated: only raw UDP send capability against the listening port is required; no cert, no config access, no privileged position. Feasibility is high — generating syntactically valid curve points for Noise messages is computationally cheap for the attacker, and UDP source spoofing (or simply many real ports/sources) makes the flood trivially repeatable and hard to block by source-IP alone. The main open question (unverified within this audit due to time/tool limits) is whether any rate-limiting exists elsewhere in the UDP receive path (e.g., in `udp` package or OS-level firewall config) that wasn't inspected; no such mechanism was found in `handshake_manager.go`, `handshake/machine.go`, or `cert/ca_pool.go`.

### Recommendation
Add a cheap, pre-DH gate for stage-1 packets: a per-source-address token bucket / rate limiter in `HandleIncoming` before calling `beginHandshake`, and/or implement a stateless cookie-reply mechanism (as WireGuard does) so the expensive Noise DH is only performed after the initiator proves round-trip reachability of the claimed source address. At minimum, cap concurrent/in-flight `beginHandshake` invocations per source IP within a time window.

### Proof of Concept
Add a benchmark/fuzz-style test in `handshake_manager_test.go`:
1. Construct a `HandshakeManager` with a valid responder credential (as in existing tests).
2. Generate N unique syntactically-valid stage-1 (`msg1`) packets, each with a distinct random ephemeral/static Noise key (no valid cert needed since the DH happens before cert validation) and `RemoteIndex == 0`.
3. Call `hm.HandleIncoming` for each packet from N distinct spoofed `via.UdpAddr` values in a tight loop, and measure wall-clock/CPU time via `testing.B` or `pprof`.
4. Assert/document: there is no early rejection prior to `m.hs.ReadMessage` (i.e., CPU time scales linearly with N with no per-source throttling), confirming the absence of a cheap pre-DH check or rate limiter.
5. Contrast with a control test sending packets with a forged issuer not present in the CA pool, showing `GetCAForCert` fails cheaply — to make explicit that the unresolved gap is the unconditional per-packet Noise DH cost in `ProcessPacket`, not the CA-chain walk itself.

func (m *Machine) ProcessPacket(out, packet []byte) ([]byte, *Result, error) {
	if m.failed {
		return nil, nil, ErrMachineFailed
	}
	if len(packet) < header.Len {
		return nil, nil, ErrPacketTooShort
	}
	// Reject packets whose subtype doesn't match the one this Machine was
	// built for. A pending handshake that suddenly receives a different
	// subtype on its index is either a stray packet that matched by chance
	// or a peer protocol violation; drop it without failing the Machine so
	// the legitimate retransmit can still complete.
	if header.MessageSubType(packet[1]) != m.subtype {
		return nil, nil, ErrSubtypeMismatch
	}
	if m.result.Initiator && m.hs.MessageIndex() == 0 {
		m.failed = true
		return nil, nil, ErrInitiateNotCalled
	}

	// The (eKey, dKey) ordering here is correct for IX, where the initiator
	// completes the handshake by reading the responder's stage-2 message.
	// noise returns (cs1, cs2) where cs1 is the initiator->responder cipher.
	// For 3-message patterns where a responder finishes by reading the final
	// message, this ordering would be wrong; revisit when XX/pqIX lands.
	msg, eKey, dKey, err := m.hs.ReadMessage(nil, packet[header.Len:])
	if err != nil {
		// Noise ReadMessage failed. The noise library checkpoints and rolls back
		// on failure, so the Machine is still alive. The caller can retry with
		// a different packet.
		return nil, nil, fmt.Errorf("noise ReadMessage: %w", err)
	}

func (ncp *CAPool) verify(c Certificate, now time.Time, certFp string, signerFp string) (*CachedCertificate, error) {
	if ncp.IsBlocklisted(certFp) {
		return nil, ErrBlockListed
	}

	signer, err := ncp.GetCAForCert(c)
	if err != nil {
		return nil, err
	}

	if signer.Certificate.Curve() != c.Curve() {
		return nil, ErrCurveMismatch
	}

	if signer.Certificate.Expired(now) {
		return nil, ErrRootExpired
	}

	if c.Expired(now) {
		return nil, ErrExpired
	}

	// If we are checking a cached certificate then we can bail early here
	// Either the root is no longer trusted or everything is fine
	if len(signerFp) > 0 {
		if signerFp != signer.Fingerprint {
			return nil, ErrFingerprintMismatch
		}
		return signer, nil
	}
	if !c.CheckSignature(signer.Certificate.PublicKey()) {
		return nil, ErrSignatureMismatch
	}
