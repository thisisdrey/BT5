### Title
Closing a lending account Balance silently wipes `emissions_outstanding`, permanently losing the user's unclaimed reward accrual - ([File: programs/marginfi/src/state/marginfi_account.rs])

### Summary
This is a direct analog of the bBRO-loss report: staking-v1's `unstake`/`claim` deleted `STAKERS[user]` (and its `pending_bro_reward`/staked-collateral) whenever the *staked amount and pending reward happened to look empty*, without checking a separate reward-bearing field. In marginfi, `Balance.close()` performs the same class of unconditional wipe: `BankAccountWrapper::close_balance` only checks that `asset`/`liability` amounts are dust-zero before calling `balance.close()`, which resets the *entire* `Balance` struct — including the unrelated `emissions_outstanding` field that tracks the user's unclaimed reward accrual for that position.

### Finding Description
`Balance` stores an independent reward-accrual field, `emissions_outstanding`, separate from `asset_shares`/`liability_shares`: [1](#0-0) 

`BalanceImpl::close()` unconditionally overwrites the whole struct with `empty_deactivated()`, which hardcodes `emissions_outstanding` back to zero, discarding whatever value was accrued: [2](#0-1) [3](#0-2) 

The permissionless, account-authority-callable `lending_account_close_balance` instruction calls `BankAccountWrapper::close_balance`, which validates only that `current_liability_amount` and `current_asset_amount` are within `ZERO_AMOUNT_THRESHOLD` — there is **no check whatsoever on `emissions_outstanding`** before `balance.close()` erases it: [4](#0-3) [5](#0-4) 

Strong corroborating evidence that this guard was intended but is unenforced: the error enum still defines `CannotCloseOutstandingEmissions` ("Cannot close balance because of outstanding emissions"), yet it is never referenced by any instruction handler (only appears in `errors.rs` and a TS test list): [6](#0-5) 

Real on-chain snapshots confirm the field carries meaningful, nonzero balances for users (`emissions_outstanding: 26891413.388324654086347` in a regression fixture), so this is not a purely theoretical/always-zero field: [7](#0-6) 

Exactly like the staking-v1 bug — where zero stake + zero pending BRO triggered deletion of the whole `STAKERS` entry and silently destroyed the user's bBRO — here, zero asset/liability shares (the "stake amount" analog) trigger `close_balance`, which silently destroys the user's `emissions_outstanding` (the "bBRO"/reward analog) with no independent zero-check or settlement step.

### Impact Explanation
Any user (or the account authority) who calls the permissionless `lending_account_close_balance` on a fully-repaid/withdrawn balance that still has unclaimed `emissions_outstanding` permanently and irreversibly loses that reward accrual — there is no other code path shown that reads, pays out, or migrates `emissions_outstanding` before the field is zeroed. This is a concrete, unauthorized loss of user-owned value (unauthorized state change / permanent loss), reachable by any ordinary account holder simply by closing a dust balance, matching the bug class and severity of the original report (impact: real value permanently lost to the user, not the protocol).

### Likelihood Explanation
Likelihood is high: `lending_account_close_balance` is a normal, documented instruction path (also invoked by CLI tooling and by risk-admin/purge flows), and any user whose asset/liability shares round down to dust while they still have unclaimed emissions from an earlier period can trigger this simply through routine account cleanup (e.g., after using `withdraw_all`/`repay all` which leave a zero-share balance that a later `close_balance` call clears). No special privilege or unusual sequence is required.

### Recommendation
Before calling `balance.close()` in `BankAccountWrapper::close_balance`, check `balance.emissions_outstanding` (and enforce the existing but currently-unused `MarginfiError::CannotCloseOutstandingEmissions`) so a balance with nonzero pending emissions cannot be closed until those emissions are settled/claimed or explicitly migrated elsewhere, mirroring the fix applied in the referenced staking-v1 patch (preserve reward-bearing data instead of deleting it alongside the zeroed principal).

### Proof of Concept
1. User deposits into Bank A, accrues emissions via the group's emissions schedule such that `balance.emissions_outstanding > 0` for that position (field is independently tracked, per `type-crate/src/types/user_account.rs:300-301`).
2. User calls `lending_account_withdraw` with `withdraw_all = true`, driving `asset_shares`/`liability_shares` to (near-)zero, but the `Balance` slot remains active since plain withdraw does not close the slot (per integrator guide: "simply withdrawing ... will always leave the Balance on your account, even with zero shares").
3. User (or anyone with authority per `LendingAccountCloseBalance` constraints) calls `lending_account_close_balance` on that bank.
4. `close_balance` (`programs/marginfi/src/state/marginfi_account.rs:1739-1799`) verifies only `current_asset_amount`/`current_liability_amount` are dust-zero, then calls `balance.close()`, which resets `emissions_outstanding` to `0` with no check or payout — the previously accrued emissions value is permanently lost.

```rust
            MarginfiError::IllegalBalanceState,
            "Balance has existing assets"

        let had_liabs = liability_shares.is_positive_with_tolerance(ZERO_AMOUNT_THRESHOLD);
```

```rust
pub fn lending_account_close_balance(ctx: Context<LendingAccountCloseBalance>) -> MarginfiResult {
    let LendingAccountCloseBalance {
        marginfi_account,
        bank: bank_loader,
        group: marginfi_group_loader,
        ..
    } = ctx.accounts;

    let mut marginfi_account = marginfi_account.load_mut()?;
    let mut bank = bank_loader.load_mut()?;

    check!(
        !marginfi_account.get_flag(ACCOUNT_DISABLED),
        MarginfiError::AccountDisabled
    );

    let group = &*marginfi_group_loader.load()?;
    bank.accrue_interest(
        Clock::get()?.unix_timestamp,
        group,
        #[cfg(not(feature = "client"))]
        bank_loader.key(),
    )?;

    bank.update_bank_cache(group)?;

    let in_receivership = marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP);
    let lending_account: &mut marginfi_type_crate::types::LendingAccount =
        &mut marginfi_account.lending_account;
    let mut bank_account =
        BankAccountWrapper::find(&bank_loader.key(), &mut bank, lending_account)?;

    bank_account.close_balance(in_receivership)?;
    lending_account.sort_balances();
    marginfi_account.sync_indexer_flags();
    marginfi_account.last_update = Clock::get()?.unix_timestamp as u64;

    Ok(())
}
```
