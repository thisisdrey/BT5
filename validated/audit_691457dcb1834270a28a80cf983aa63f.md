It is invoked locally by the node itself (e.g., when fetching microblocks from a peer) with a `PeerHost`, `StacksBlockId`, and `seq` that are already valid Rust values constructed by the caller — none of these arguments are raw, attacker-supplied bytes being parsed at this call site. The `.expect("FATAL: failed to construct request from infallible data")` only fires if `StacksHttpRequest::new_for_peer` fails to serialize a syntactically well-formed URI/host, which cannot happen given locally well-typed inputs.

The actual remote-attacker-facing parsing logic for this endpoint is `try_parse_request`, which validates the URL path via a fixed regex (`^/v2/microblocks/unconfirmed/(?P<parent_block_id>[0-9a-f]{64})/(?P<start_sequence>[0-9]{1,6})$`) and uses `request::get_block_hash`/`request::get_u32` helpers that return `Result`, with an explicit bounds check (`start_sequence_u32 > u32::from(u16::MAX)`) before use — no unwrap/panic on attacker input [2](#0-1) . Likewise `try_handle_request` uses `.ok_or(...)?` rather than unwrap when consuming parsed state [3](#0-2) .

Since the targeted function is not on any remote-attacker-controlled parsing path, the claimed panic-from-parsing is not reachable, and the question's premise does not hold for this file/function.
