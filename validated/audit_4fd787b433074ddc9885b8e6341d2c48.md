## Analog Found

### Title
Unchecked exchange pool balance after non-hardened AMM calculation can drive `ExchangeCapsule` balances negative - (File: `chainbase/src/main/java/org/tron/core/capsule/ExchangeCapsule.java`)

### Summary
The Sherlock report describes `SingleSidedLiquidityVault#claimRewards()` computing an outgoing reward amount without checking it against the vault's actual token balance before transferring, which can overflow/revert and strand funds. The equivalent bug class in java-tron is in `ExchangeCapsule#transaction()`: the amount to debit from the exchange pool (`buyTokenQuant`) is computed by a legacy double-precision bancor-style processor and is only range-checked (`< 0`) when the "hardened" calculation path is active. When the hardened path is not active, an unprivileged user broadcasting an `ExchangeTransactionContract` can drive the pool's on-chain token balance negative, corrupting the pool's accounting state without any overflow/insufficient-balance guard.

### Finding Description
`ExchangeTransactionActuator#execute()` invokes `exchangeCapsule.transaction(tokenID, tokenQuant, dynamicStore.allowStrictMath(), allowHarden())` for every trade against a Bancor-relay-style token exchange: [1](#0-0) 

Inside `ExchangeCapsule#transaction()`, when `hardenedCalc` is `false` (i.e. `allowHardenExchangeCalculation()` chain parameter not yet enabled), the legacy `ExchangeProcessor` is used to compute `buyTokenQuant` via floating-point math, and the resulting new balances are applied directly with plain `+`/`-` without any check that they stay non-negative: [2](#0-1) 

The only balance-sanity check (`newFirstTokenBalance < 0 || newSecondTokenBalance < 0`) is gated behind `hardenedCalc`: [3](#0-2) 

The legacy `ExchangeProcessor.exchange()` relies on `double`/`Math.pow` arithmetic that is susceptible to precision loss and rounding errors (this is exactly the historically known Bancor-relay rounding issue in java-tron), so `buyTokenQuant` can, in edge cases (extreme quant values, repeated small trades, or balance ratios close to precision limits), be computed larger than the pool's actual `secondTokenBalance`/`firstTokenBalance`. Because no floor/clamp against the real balance is performed on this path, the persisted `Exchange` protobuf balance field can become negative and is written straight to `ExchangeStore`/`ExchangeV2Store`: [4](#0-3) 

This mirrors the reported bug precisely: the amount "exiting" the pool (paid out to the trader as `anotherTokenQuant`) is never checked against what the pool can actually back before mutating state.

### Impact Explanation
A negative on-chain pool balance is an unbacked-balance / permanently corrupted state condition: the exchange's tracked reserves no longer reflect real backing, subsequent trades computed from a corrupted (negative) balance produce undefined/exploitable pricing, and TRX/TRC10 tokens can be extracted from the pool beyond what was ever deposited into it — a direct value-extraction / permanent-freezing-of-funds scenario reachable purely from a normal, unprivileged `TriggerContract`-style transaction (`ExchangeTransactionContract`) with no special permissions required.

### Likelihood Explanation
Exploitability depends on the `allowHardenExchangeCalculation` dynamic parameter being disabled, which is the default/legacy behavior prior to activation of that hardening proposal on a given chain/fork; on any deployment where this parameter has not yet been turned on, every ordinary trader's trade transaction runs through the unguarded legacy path, making this reachable by any anonymous transaction broadcaster without any privileged role, matching the "single signed transaction" reachability bar. Likelihood is Medium because it requires this specific (but realistic, pre-hardening) network configuration and edge-case quantities to manifest a negative-balance write, but no attacker privilege beyond a normal wallet is needed.

### Recommendation
Apply the same non-negative-balance invariant unconditionally, not only when `hardenedCalc` is `true`, in `ExchangeCapsule#transaction()`, and/or clamp the computed `buyTokenQuant` to at most the counter-token's current balance before applying/persisting the state change, throwing `ContractValidateException` (as already done for the hardened branch) if the computed payout would exceed available reserves.

### Proof of Concept
1. Attacker (any account) creates or targets an existing exchange pair (`ExchangeCapsule`) on a network where `allowHardenExchangeCalculation` is not yet activated (`allowHarden()` returns `false`). [5](#0-4) 
2. Attacker submits repeated `ExchangeTransactionContract` transactions via `ExchangeTransactionActuator`, choosing `tokenId`/`quant` values that push the pool's balance ratio toward precision-loss edge cases in the double-based `ExchangeProcessor.exchange()` formula. [6](#0-5) 
3. Because `ExchangeCapsule#transaction()` only guards against negative balances when `hardenedCalc` is true, a computed `buyTokenQuant` exceeding the actual `secondTokenBalance`/`firstTokenBalance` is applied unchecked, and the corrupted (potentially negative) balance is persisted to `ExchangeStore`/`ExchangeV2Store`, allowing extraction of tokens beyond the pool's real reserves. [7](#0-6)

```java
  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
```

```java
  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
```
