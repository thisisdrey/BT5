### Title
Uninitialized reward indexes allow theft of reward reserves during speed activation - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
`RewardsDistributor.claimRewards` treats a missing per-account index as zero even when the token index is still `INITIAL_INDEX`, allowing a holder of a newly reward-enabled deposit or debt token to claim approximately `balance * 1e18` reward units in the same transaction timestamp that reward speed is activated. [1](#0-0) 

### Finding Description
When governance first assigns a positive token speed, the distributor initializes `tokenStates[token_]` to `INITIAL_INDEX` and records the current timestamp. [2](#0-1) 
If a user calls `claimRewards` before the timestamp advances, `_updateTokenIndex` does not increase the index because `_calculateTokenIndex` returns zero values when the elapsed time is zero. [3](#0-2) 
`_calculateTokenDelta` only substitutes `INITIAL_INDEX` for a missing account index when the token index is strictly greater than `INITIAL_INDEX`; equality falls through with `_accountIndex == 0`. [4](#0-3) 
Consequently, the first holder to claim during the activation timestamp receives `token_.balanceOf(account_).wadMul(INITIAL_INDEX)`, and `_transferRewardIfEnoughTokens` pays the entire accrued amount if the reward contract holds enough tokens. [5](#0-4) 

### Impact Explanation
An attacker who already holds a relevant deposit or debt token can drain the distributor's reward-token balance when reward distribution is first enabled, directly stealing yield intended for all protocol participants. [6](#0-5) 
The vulnerable path is permissionless, has no health-check, token-existence check on the supplied account, minimum-time delay, or claim cap, and the only payout limit is the distributor's token balance. [6](#0-5) 

### Likelihood Explanation
The attack requires a positive-speed activation transaction and an attacker-held deposit or debt-token balance at that timestamp, both of which are plausible when rewards are initialized for an existing market. [7](#0-6) 
An unprivileged attacker can monitor `updateTokenSpeed` or `updateTokenSpeeds` and submit `claimRewards` in the same block after the governance transaction, without needing privileged access or manipulating oracle data. [8](#0-7) 

### Recommendation
Initialize the account index to the current token index whenever `accountIndexOf[token_][account_] == 0`, including when the token index equals `INITIAL_INDEX`. [4](#0-3) 
Additionally, update indexes for all existing holders before enabling a positive speed, or activate rewards only after a deployment-time checkpoint that prevents same-block claims. [2](#0-1) 

### Proof of Concept
The following Foundry fork test demonstrates the accounting defect once deployment addresses are supplied from the target chain's `deployments/<chain>` artifacts.

```solidity
// test/foundry/poc/RewardsInitialIndex.t.sol
// SPDX-License-Identifier: MIT
pragma solidity 0.8.24;

import "forge-std/Test.sol";

import {RewardsDistributor} from "../../../contracts/RewardsDistributor.sol";
import {IERC20} from "../../../contracts/dependencies/openzeppelin/token/ERC20/IERC20.sol";

contract RewardsInitialIndexPoC is Test {
    RewardsDistributor distributor =
        RewardsDistributor(vm.envAddress("REWARDS_DISTRIBUTOR"));
    IERC20 rewardToken = IERC20(vm.envAddress("REWARD_TOKEN"));
    IERC20 rewardedToken = IERC20(vm.envAddress("DEPOSIT_OR_DEBT_TOKEN"));
    address governor = vm.envAddress("POOL_GOVERNOR");
    address attacker = vm.envAddress("TOKEN_HOLDER");

    function test_initialIndexDrainsRewards() public {
        uint256 attackerBalance = rewardedToken.balanceOf(attacker);
        assertGt(attackerBalance, 0);

        uint256 reserveBefore = rewardToken.balanceOf(address(distributor));
        assertGt(reserveBefore, 0);

        // Governor performs the ordinary, non-malicious reward activation.
        vm.prank(governor);
        distributor.updateTokenSpeed(rewardedToken, 1);

        // Same timestamp: tokenStates.index remains INITIAL_INDEX, while the
        // attacker's account index is still the missing/default value zero.
        vm.prank(attacker);
        distributor.claimRewards(attacker);

        assertEq(rewardToken.balanceOf(address(distributor)), 0);
        assertEq(rewardToken.balanceOf(attacker), reserveBefore);
    }
}
```

On a fork where the selected account already holds the reward-bearing token and the distributor has reward-token reserves, the same-block claim pays `attackerBalance * 1e18`, capped only by the distributor reserve. [9](#0-8)

    function _calculateTokenDelta(
        TokenState memory _tokenState,
        IERC20 token_,
        address account_
    ) private view returns (uint256 _tokenIndex, uint256 _tokensDelta) {
        _tokenIndex = _tokenState.index;
        uint256 _accountIndex = accountIndexOf[token_][account_];

        if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
            _accountIndex = INITIAL_INDEX;
        }

        uint256 _deltaIndex = _tokenIndex - _accountIndex;
        _tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
    }
