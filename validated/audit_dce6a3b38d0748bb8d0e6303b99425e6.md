### Title
Unbounded HTTP response body read in the signer's StackerDB HTTP client - ([File: libsigner/src/http.rs])

### Summary
`run_http_request` in `libsigner/src/http.rs`, used by `StackerDBSession::rpc_request` to talk to a Stacks node's StackerDB HTTP RPC endpoint, reads the entire HTTP response into memory with `sock.read_to_end(&mut buf)` before any length check is applied. There is no cap on the number of bytes read from the socket, so a malicious or compromised node (or a network attacker able to intercept the plaintext TCP connection, since this client uses a raw `TcpStream` with no TLS) can return an arbitrarily large response body and exhaust the signer's memory.

### Finding Description
`StackerDBSession` connects to a configured `host` over a plain `TcpStream` (no TLS) and issues RPC requests via `rpc_request`, which calls `run_http_request`: [1](#0-0) 

`run_http_request` writes the request, then reads the response with an unbounded `read_to_end`: [2](#0-1) 

Only after the full response is buffered does the code parse headers via `decode_http_response` and then decode the body via `decode_http_body`. The header parser (`decode_http_response`) bounds header count/size (`MAX_HTTP_HEADERS`, `MAX_HTTP_HEADER_LEN`), but nothing bounds the *body* size before or during the `read_to_end` call: [3](#0-2) [4](#0-3) 

Note the chunked-body path does apply `MAX_MESSAGE_LEN` via `HttpChunkedTransferReader`, but that check only happens *after* the entire response (headers + full chunked body) has already been buffered by the preceding unbounded `sock.read_to_end(&mut buf)`. For a non-chunked response with a `Content-Length` header, the code does not even use that header to bound the read — it simply keeps calling `read_to_end` until the peer closes the connection or the socket read times out, whichever occurs later, buffering everything read in the meantime.

This is the same bug class as the referenced OpenTelemetry OpAMP CVE-2026-42348 (CWE-789: unbounded allocation from network input): a client performs an unbounded full-body read (`ReadAsByteArrayAsync` there, `read_to_end` here) with no upper bound on the number of bytes consumed, even though only a bounded amount is legitimately expected. `StacksHttp`/`httpcore.rs` on the node's own P2P/RPC side correctly enforces `MAX_MESSAGE_LEN` bounds at the connection layer (see `connection.rs::buffer_message_bytes`/`consume_payload_known_length`), but the standalone signer-side HTTP client in `libsigner/src/http.rs` does not follow that discipline.

The equality/invariant broken here is: "bytes read from an untrusted peer must be bounded by an application-defined maximum message size" — the P2P/RPC connection layer enforces this (`MAX_MESSAGE_LEN`), but the signer's StackerDB HTTP client does not, allowing a remote peer to force unbounded memory allocation.

### Impact Explanation
A malicious or compromised Stacks node that a signer is configured to talk to (or a network attacker positioned to intercept the plaintext TCP connection, since no TLS is used) can respond to any `list_chunks`/`get_chunks`/`get_latest_chunks`/`put_chunk` RPC call with an extremely large or never-ending response body. Because the client buffers everything via `read_to_end` before any size check, this can exhaust the signer process's memory and crash or hang it — a remote, unauthenticated denial-of-service against a critical signer component (`StackerDBSession` is used by the Stacks signer to fetch/post blocks and DKG-related messages).

### Likelihood Explanation
The signer must be configured to talk to the attacker's endpoint, or an attacker must be able to intercept the connection (no TLS is used for this raw `TcpStream`), which requires either a compromised/malicious configured node or a MITM position. This matches the report's own caveat for the original OpAMP finding ("application's configured server needs to behave maliciously" or be MITM'd). Given the plaintext transport and unbounded read, the effort to trigger it once positioned is trivial (send an oversized or infinite response).

### Recommendation
Bound the body read in `run_http_request` (and `decode_http_body`) similarly to how `stackslib/src/net/httpcore.rs` bounds message sizes: use `Content-Length` (when present) to read exactly that many bytes via a bounded reader (e.g., `BoundReader` with a cap such as `MAX_MESSAGE_LEN`/`STACKERDB_MAX_CHUNK_SIZE`), and impose an explicit maximum on unbounded/`read_to_end` reads, aborting the connection once the cap is exceeded, rather than accumulating all bytes into an unbounded `Vec<u8>`.

### Proof of Concept
1. Configure a `StackerDBSession` to connect to an attacker-controlled `host` (e.g., simulate a malicious/compromised Stacks node RPC endpoint) as done in the existing `libsigner/src/session.rs` test harness (`TcpListener`).
2. Have the attacker-controlled listener, upon accepting the connection, respond with a valid `HTTP/1.1 200 OK` status line/headers followed by an effectively unbounded stream of body bytes (or a very large fixed body, e.g. multi-GB), without closing the connection promptly.
3. Observe that `run_http_request`'s `sock.read_to_end(&mut buf)` ( [5](#0-4) ) keeps allocating and appending to `buf` with no upper bound, growing the signer client's memory usage until the process is starved of memory or the OS kills it — before any header/body validation logic ever executes.

pub fn decode_http_response(payload: &[u8]) -> Result<(HashMap<String, String>, usize), RPCError> {
    // realistically, there won't be more than 32 headers
    let mut headers_buf = [httparse::EMPTY_HEADER; MAX_HTTP_HEADERS];
    let mut resp = httparse::Response::new(&mut headers_buf);

    // consume respuest
    let (headers, body_offset) =
        if let Ok(httparse::Status::Complete(body_offset)) = resp.parse(payload) {
            if let Some(code) = resp.code {
                if code != 200 {
                    return Err(RPCError::HttpError(code.into()));
                }
            } else {
                return Err(RPCError::MalformedResponse(
                    "No HTTP status code returned".to_string(),
                ));
            }
            if let Some(version) = resp.version {
                if version != 0 && version != 1 {
                    return Err(RPCError::MalformedResponse(format!(
                        "Unrecognized HTTP code {version}"
                    )));
                }
            } else {
                return Err(RPCError::MalformedResponse(
                    "No HTTP version given".to_string(),
                ));
            }
            let mut headers: HashMap<String, String> = HashMap::new();
            for i in 0..resp.headers.len() {
                let value = String::from_utf8(resp.headers[i].value.to_vec()).map_err(|_e| {
                    RPCError::MalformedResponse("Invalid HTTP header value: not utf-8".to_string())
                })?;
                if !value.is_ascii() {
                    return Err(RPCError::MalformedResponse(
                        "Invalid HTTP response: header value is not ASCII-US".to_string(),
                    ));
                }
                if value.len() > MAX_HTTP_HEADER_LEN {
                    return Err(RPCError::MalformedResponse(
                        "Invalid HTTP response: header value is too big".to_string(),
                    ));
                }

                let key = resp.headers[i].name.to_string().to_lowercase();
                if headers.contains_key(&key) {
                    return Err(RPCError::MalformedResponse(format!(
                        "Invalid HTTP respuest: duplicate header \"{key}\""
                    )));
                }
                headers.insert(key, value);
            }
            (headers, body_offset)
        } else {
            return Err(RPCError::Deserialize(
                "Failed to decode HTTP headers".to_string(),
            ));
        };

    Ok((headers, body_offset))
}

/// Decode an HTTP body, given the headers.
pub fn decode_http_body(headers: &HashMap<String, String>, mut buf: &[u8]) -> io::Result<Vec<u8>> {
    let chunked = if let Some(val) = headers.get("transfer-encoding") {
        val == "chunked"
    } else {
        false
    };

    let body = if chunked {
        // chunked encoding
        let ptr = &mut buf;
        let mut fd = HttpChunkedTransferReader::from_reader(ptr, MAX_MESSAGE_LEN.into());
        let mut decoded_body = vec![];
        fd.read_to_end(&mut decoded_body)?;
        decoded_body
    } else {
        // body is just as-is
        buf.to_vec()
    };

    Ok(body)
}
