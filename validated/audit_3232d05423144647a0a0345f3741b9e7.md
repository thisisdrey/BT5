### Title
Unbounded prefix scan in `getWithPrefix()` allows an attacker to trigger an out-of-memory/CPU DoS via the public `GetDelegatedResourceAccountIndex(V2)` API - ([File: chainbase/src/main/java/org/tron/core/store/DelegatedResourceAccountIndexStore.java])

### Summary
`DelegatedResourceAccountIndexStore.getWithPrefix()` performs an unbounded `prefixQuery()` over the `FROM_PREFIX`/`TO_PREFIX` (and V2) keyspace for a given address, loading every matching record into memory, sorting it, and returning it in full. Any account can grow the number of matching records for its own address without limit by issuing many cheap `DelegateResourceContract`/`UnDelegateResourceContract` transactions to distinct receiver addresses, then any unauthenticated caller can trigger the unbounded read via the `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` HTTP/gRPC endpoints, causing excessive CPU/memory consumption analogous to the reported `at()` unbounded-iteration issue.

### Finding Description
`getWithPrefix()` builds a `List` from `this.prefixQuery(key).values()` with no limit, then sorts it: [1](#0-0) 

`prefixQuery()` in `TronStoreWithRevoking` performs a full key-prefix scan and materializes every matching entry into a `Map`, with no size cap: [2](#0-1) 

Each `delegate()`/`delegateV2()` call writes a new distinct entry keyed by `prefix + from + to` under both the FROM and TO indexes: [3](#0-2) 

This store is directly reachable from unauthenticated, public query surfaces: the HTTP servlet [4](#0-3) 
and the gRPC `GetDelegatedResourceAccountIndex`/`GetDelegatedResourceAccountIndexV2` RPCs that call straight into `Wallet.getDelegatedResourceAccountIndex[V2]()`: [5](#0-4) [6](#0-5) 

An existing unit test already demonstrates that an attacker's owner index accumulates entries proportionally to the number of distinct delegations issued (100+ receivers used just for a functional test), showing that the store places no upper bound on fan-out per address: [7](#0-6) 

Unlike the `at()` bug (unbounded backward loop by timestamp in gas-metered contract code), this is an unbounded *storage prefix scan* triggered by a public read-only API request rather than a gas-metered EVM/TVM call, so there is no gas limit to stop the iteration once it starts — it will run to completion inside the node's HTTP/gRPC handler thread, consuming CPU and allocating memory proportional to however many delegation records the attacker created.

### Impact Explanation
An attacker who cheaply delegates tiny amounts of bandwidth/energy from a single account to a very large number of distinct receiver addresses (each delegation is a low-cost transaction, no protocol-level cap on fan-out was found) inflates the number of index entries keyed to that address. Any subsequent call to `GetDelegatedResourceAccountIndex`/`V2` for that address forces the node to scan, deserialize, and sort the entire record set on every single query — with no pagination or cap. Repeated queries (which cost the attacker nothing beyond normal API rate limits) can produce sustained high CPU/memory usage on the serving full node, degrading or denying service for the HTTP/gRPC query API. This does not directly allow theft of funds, but it is a legitimate node-level resource-exhaustion / DoS vector on a publicly reachable read path.

### Likelihood Explanation
Moderate. The attacker fully controls both halves of the attack: (1) creation of unbounded delegation records via ordinary, permissionless `DelegateResourceContract` transactions, and (2) triggering of the expensive read via a public, unauthenticated API endpoint. The only friction is the (small) transaction fee/bandwidth cost to create many delegation records, and rate limiting (`RateLimiterServlet`) on the HTTP endpoint, which slows but does not prevent building the record set once, after which every subsequent query against that address remains expensive.

### Recommendation
- Add a hard cap or pagination to `prefixQuery()`/`getWithPrefix()` for the delegated-resource index (similar to the `limit` parameters already used in `getlatestValues`/`getValuesNext`), and/or cap the maximum number of distinct delegatee/delegator entries an address may accumulate.
- Alternatively, replace the "load-all-then-sort" pattern in `getWithPrefix()` with a size-bounded query and reject or paginate requests when the number of results would exceed a safe limit.

### Proof of Concept
1. Attacker account `A` freezes a minimal amount of TRX/energy and issues N `DelegateResourceContract` transactions (`DelegateResourceActuator`), each delegating to a distinct newly generated receiver address `R_1 … R_N`. Each call appends an entry via `DelegatedResourceAccountIndexStore.delegate()`/`delegateV2()` under `FROM_PREFIX + A + R_i` and `TO_PREFIX + R_i + A`. [3](#0-2) 
2. For large N (e.g., tens/hundreds of thousands), the node's `FROM_PREFIX`+`A` keyspace now contains N entries.
3. Any client calls the public HTTP endpoint `/wallet/getdelegatedresourceaccountindex` (or the gRPC `GetDelegatedResourceAccountIndex`) with `value = A`. [4](#0-3) 
4. `Wallet.getDelegatedResourceAccountIndex()` → `DelegatedResourceAccountIndexStore.getIndex()` → `getWithPrefix()` performs a full unbounded `prefixQuery()` scan, deserializes and sorts all N entries into memory and serializes them into the JSON/protobuf response on every single request, with no limit. [8](#0-7) 
5. Repeating this query (or issuing it concurrently) drives sustained CPU/memory load on the full node's query-serving threads, degrading API availability for legitimate users.

  private DelegatedResourceAccountIndexCapsule getWithPrefix(byte[] fromPrefix, byte[] toPrefix, byte[] address) {
    DelegatedResourceAccountIndexCapsule tmpIndexCapsule =
        new DelegatedResourceAccountIndexCapsule(ByteString.copyFrom(address));

    byte[] key = Bytes.concat(fromPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpToList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpToList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    List<ByteString> list = tmpToList.stream()
        .map(DelegatedResourceAccountIndexCapsule::getAccount).collect(Collectors.toList());
    tmpIndexCapsule.setAllToAccounts(list);

    key = Bytes.concat(toPrefix, address);
    List<DelegatedResourceAccountIndexCapsule> tmpFromList =
        new ArrayList<>(this.prefixQuery(key).values());
    tmpFromList.sort(Comparator.comparing(DelegatedResourceAccountIndexCapsule::getTimestamp));
    list = tmpFromList.stream().map(DelegatedResourceAccountIndexCapsule::getAccount).collect(
        Collectors.toList());
    tmpIndexCapsule.setAllFromAccounts(list);
    return tmpIndexCapsule;
