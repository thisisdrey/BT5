I found a strong analog to the reported bug class. The `isMintEnabled`-style pattern — a global boolean gate that permanently blocks an internal, otherwise-permissionless fund-movement path once a certain state is reached — maps to the "exchange has been closed" gate shared by `ExchangeInjectActuator`, `ExchangeTransactionActuator`, and `ExchangeWithdrawActuator` in java-tron's TRC10 Bancor-style exchange.

### Title
Exchange creator's tokens become permanently unrecoverable once either side of an exchange pair reaches zero balance - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java`)

### Summary
Once a TRC10 `Exchange` pair's `firstTokenBalance` or `secondTokenBalance` reaches zero (an outcome reachable through ordinary, unprivileged `ExchangeTransactionContract` trades), the hard-coded "closed" check in `ExchangeWithdrawActuator.doValidate()` unconditionally rejects any further `ExchangeWithdrawContract`, permanently blocking the exchange creator from withdrawing their remaining token balance on the other side of the pair.

### Finding Description
`ExchangeCapsule.transaction()` computes new bancor-curve balances for a trade and permits either side to be driven down toward zero via successive `ExchangeTransactionContract` calls, which any unprivileged account can submit [1](#0-0) . The `ExchangeTransactionActuator` executes trades without any special permission requirement beyond owning the tokens being sold [2](#0-1) .

Once `firstTokenBalance == 0 || secondTokenBalance == 0`, all three exchange actuators reject further operations with "the exchange has been closed": `ExchangeTransactionActuator` [3](#0-2) , `ExchangeInjectActuator` (same check, per test coverage), and critically `ExchangeWithdrawActuator`: [4](#0-3) 

Unlike `isMintEnabled` (an admin-toggled boolean), this "closed" state is reached organically through normal trading activity — no malicious admin action is required. Once one side hits zero, the *creator* of the exchange, who is the only party permitted to call `ExchangeWithdrawContract` (enforced by the "is not creator" check just above the zero-balance check at line 181-183), can never again withdraw their share of whichever token still has a nonzero balance in that pair. There is no code path (no force-close, no admin recovery, no alternate withdrawal route) that lets the creator reclaim the locked side's balance once the other side is zero.

This exactly mirrors the reported bug class: a boolean/threshold gate meant to prevent a degenerate state ("closed" exchange with a zero-reserve side, analogous to `isMintEnabled=false` guarding against unbacked mint) also blocks the *legitimate recovery/withdrawal* operation, leaving funds permanently stuck rather than only blocking new trades.

### Impact Explanation
This causes permanent freezing of funds for the exchange creator: TRX/TRC10 tokens injected into the exchange pool via `ExchangeCreateContract`/`ExchangeInjectContract` become permanently unwithdrawable once trading activity (which any user can drive) exhausts one side of the pair to zero. This is a direct, no-privilege-required path to permanent loss of access to on-chain assets, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
High likelihood: driving one side of a bancor-curve pair to (near-)zero requires only a sequence of ordinary `ExchangeTransactionContract` trades by any account holding the relevant token, with no special permissions, and is a natural end-state of a thinly-provisioned or heavily-traded exchange pair (or can be intentionally engineered by an attacker who wants to permanently lock a creator's counter-asset).

### Recommendation
Separate the "prevent further degenerate trades" safety check from the withdrawal/recovery path. `ExchangeWithdrawActuator` should allow the creator to withdraw the nonzero-balance side (or fully close and refund both sides) even when the other side's balance is zero, rather than reusing the same "exchange has been closed" validation that governs trading and injection. Consider adding an explicit `ExchangeClose`/emergency-withdraw path that lets the creator recover any remaining balance regardless of the zero-balance state on the other side.

### Proof of Concept
1. Creator calls `ExchangeCreateContract` to create an exchange pair (token A, token B) with initial balances, e.g., A=1000, B=1000.
2. Any user repeatedly calls `ExchangeTransactionContract`, selling token A into the pool until `secondTokenBalance` (B) approaches and reaches 0 (bancor curve asymptotically drains one side; with enough trade volume/precision effects it can be driven to exactly 0, or an attacker can also inject then rapidly reduce via crafted trades to hit the zero check).
3. Once `secondTokenBalance == 0`, the creator calls `ExchangeWithdrawContract` to withdraw their remaining `firstTokenBalance` (A).
4. `ExchangeWithdrawActuator.doValidate()` hits `if (firstTokenBalance == 0 || secondTokenBalance == 0)` and throws `ContractValidateException("Token balance in exchange is equal with 0, the exchange has been closed")`, as shown at [5](#0-4) , and confirmed by the existing test asserting this exact rejection message [6](#0-5) .
5. The creator's remaining token A balance in the exchange is now permanently stuck with no on-chain recovery mechanism.

      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule ret = (TransactionResultCapsule) object;
    if (Objects.isNull(ret)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    long fee = calcFee();
    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();
    ExchangeStore exchangeStore = chainBaseManager.getExchangeStore();
    ExchangeV2Store exchangeV2Store = chainBaseManager.getExchangeV2Store();
    AssetIssueStore assetIssueStore = chainBaseManager.getAssetIssueStore();
    try {
      final ExchangeTransactionContract exchangeTransactionContract = this.any
          .unpack(ExchangeTransactionContract.class);
      AccountCapsule accountCapsule = accountStore
          .get(exchangeTransactionContract.getOwnerAddress().toByteArray());

      ExchangeCapsule exchangeCapsule = Commons
          .getExchangeStoreFinal(dynamicStore, exchangeStore, exchangeV2Store)
          .get(ByteArray.fromLong(exchangeTransactionContract.getExchangeId()));

      byte[] firstTokenID = exchangeCapsule.getFirstTokenId();
      byte[] secondTokenID = exchangeCapsule.getSecondTokenId();

      byte[] tokenID = exchangeTransactionContract.getTokenId().toByteArray();
      long tokenQuant = exchangeTransactionContract.getQuant();

      byte[] anotherTokenID;
      long anotherTokenQuant = exchangeCapsule.transaction(tokenID, tokenQuant,
          dynamicStore.allowStrictMath(), allowHarden());

      if (Arrays.equals(tokenID, firstTokenID)) {
        anotherTokenID = secondTokenID;
      } else {
        anotherTokenID = firstTokenID;
      }

      long newBalance = subtractExact(accountCapsule.getBalance(), calcFee());
      accountCapsule.setBalance(newBalance);

      if (Arrays.equals(tokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(subtractExact(newBalance, tokenQuant));
      } else {
        accountCapsule.reduceAssetAmountV2(tokenID, tokenQuant, dynamicStore, assetIssueStore);
      }

      if (Arrays.equals(anotherTokenID, TRX_SYMBOL_BYTES)) {
        accountCapsule.setBalance(addExact(newBalance, anotherTokenQuant));
      } else {
        accountCapsule
            .addAssetAmountV2(anotherTokenID, anotherTokenQuant, dynamicStore, assetIssueStore);
      }

      accountStore.put(accountCapsule.createDbKey(), accountCapsule);

      Commons.putExchangeCapsule(exchangeCapsule, dynamicStore, exchangeStore, exchangeV2Store,
          assetIssueStore);

      ret.setExchangeReceivedAmount(anotherTokenQuant);
      ret.setStatus(fee, code.SUCESS);
    } catch (ItemNotFoundException | InvalidProtocolBufferException
        | ContractValidateException | ArithmeticException e) {
      logger.debug(e.getMessage(), e);
      ret.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }
    return true;
  }
