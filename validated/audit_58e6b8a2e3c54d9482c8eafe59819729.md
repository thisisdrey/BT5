### Title
DMP-queue lazy migration silently skips failed page/overweight-message exports, permanently dropping queued XCM (and any assets they carry) - (File: `cumulus/pallets/dmp-queue/src/lib.rs`)

### Summary
The `pallet-dmp-queue` lazy migration (`on_idle` hook) advances its `MigrationStatus` cursor to the next page/overweight index **unconditionally**, regardless of whether `migration::migrate_page` / `migration::migrate_overweight` returned `Ok(())` or `Err(())`. This is structurally identical to the Booster `shutdownPool()` bug: the code wraps a fallible operation, discards the failure outcome, and still advances the "done" state so that the queue never revisits the failed item and there is no retry mechanism.

### Finding Description
In `cumulus/pallets/dmp-queue/src/lib.rs`, `on_idle` drives a state machine that migrates legacy DMP pages into `T::DmpSink`: [1](#0-0) 

```
MigrationState::StartedExport { next_begin_used } => {
    ...
    let res = migration::migrate_page::<T>(next_begin_used);
    MigrationStatus::<T>::put(MigrationState::StartedExport {
        next_begin_used: next_begin_used.saturating_add(1),
    });
    if let Ok(()) = res {
        Self::deposit_event(Event::Exported { page: next_begin_used });
    } else {
        Self::deposit_event(Event::ExportFailed { page: next_begin_used });
    }
},
```

The cursor `next_begin_used` is incremented (i.e., the page is marked as consumed/migrated) *before and independently of* checking `res`. The same unconditional-advance pattern is repeated for overweight messages: [2](#0-1) 

`migrate_page` itself already destructively removes the page from storage via `Pages::<T>::take(p)` before deciding whether the migration succeeded: [3](#0-2) 

So once `migrate_page` returns `Err(())` (e.g. the empty-page branch, or any future extension of this function that can fail), the underlying page data is already gone (`take` removed it), `res` is discarded except for firing a `ExportFailed` event (documented in the pallet as something that "should never be emitted" — i.e., not actually handled), and the state machine moves on to the next page forever. There is no code path that retries the failed page, no way to reset `MigrationStatus` back to reprocess it, and once `Completed` is reached the pallet is intended to be removed from the runtime — permanently foreclosing any recovery.

This mirrors the Booster analog exactly:
- Booster: `try withdrawAll {} catch {}` → `pool.shutdown = true` unconditionally → funds unrecoverable because withdrawal logic assumes shutdown pools already hold the funds.
- dmp-queue: `migrate_page` may fail → `MigrationStatus` advances unconditionally → messages (and any assets/XCM instructions they encode, since raw DMP messages can be reserve-transfers/teleports) are unrecoverable because the page has already been taken out of storage and the cursor has moved past it.

### Impact Explanation
Downward messages queued in the legacy DMP pallet can encode XCM instructions that move assets (teleports, reserve transfers, remote calls). If a page fails to migrate for any reason (corrupted/inconsistent `PageIndex` state, a defensive bug in `migrate_page`, or any future change that introduces additional failure branches), the messages in that page are dropped silently — the only trace being a log line and an `ExportFailed` event that no on-chain logic reacts to. This is a "message queue must only advance after decode, dispatch, execution succeed atomically" violation and results in permanent loss of the enqueued cross-chain messages/funds, with no path to retry, matching the "permanent user-fund or bridge-state lock" impact class.

### Likelihood Explanation
Likelihood is low-to-moderate and, like the original report, is conditional on `migrate_page`/`migrate_overweight` actually failing — the current implementation only fails on an already-empty page (a defensive/should-never-happen branch) or (for overweight) a missing storage entry. The judge in the original C4 report accepted a Medium severity despite the failure trigger being similarly unspecified, on the basis that an unrecoverable "try/catch and mark done anyway" pattern is inherently dangerous regardless of how rare the triggering condition is. The same reasoning applies here: this is a lazy one-time storage migration running via `on_idle` in every block until `Completed`, so any transient failure (e.g., triggered by unexpected state left over from a chain that had a different history of DMP usage, or a future code change that adds new failure modes to `migrate_page`) becomes a silent, permanent loss.

### Recommendation
Do not advance `next_begin_used` (or `next_overweight_index`) when `res` is `Err(())`. Either:
- Retry the same page/index on the next `on_idle` call (bounded number of attempts, then require explicit governance intervention), or
- Transition to a distinct `Failed` state that halts automatic progress and requires a privileged, explicit decision (matching the `forced` flag pattern recommended in the original report) rather than silently treating the failure as success.

At minimum, do not remove the underlying storage (`Pages::<T>::take`) before confirming successful migration, so a failed attempt can be retried without data loss.

### Proof of Concept
1. Assume (via any future refactor of `migrate_page`, or an inconsistent `PageIndex`/`Pages` storage state) that `migration::migrate_page::<T>(p)` returns `Err(())` for some page `p` that still logically should contain messages.
2. `on_idle` calls `migrate_page`, which does `Pages::<T>::take(p)` (removing the page from storage) and then finds it empty/unparseable, returning `Err(())`. [4](#0-3) 
3. Back in `on_idle`, `MigrationStatus` is set to `StartedExport { next_begin_used: p + 1 }` regardless of the `Err`, and only an `ExportFailed` event is emitted: [5](#0-4) 
4. On subsequent blocks the migration proceeds directly to page `p + 1`; page `p`'s messages are never retried, never re-inserted, and are unrecoverable. Once all pages/overweight indices are iterated, `MigrationState::Completed` is reached and the pallet is expected to be deprecated/removed, permanently closing any avenue to recover the dropped messages.

```rust
pub(crate) fn migrate_page<T: crate::Config>(p: PageCounter) -> Result<(), ()> {
	let page = Pages::<T>::take(p);
	log::debug!(target: LOG, "Migrating page #{p} with {} messages ...", page.len());
	if page.is_empty() {
		log::error!(target: LOG, "Page #{p}: EMPTY - storage corrupted?");
		return Err(());
	}

	for (m, (block, msg)) in page.iter().enumerate() {
		let Ok(bound) = BoundedVec::<u8, _>::try_from(msg.clone()) else {
			log::error!(target: LOG, "[Page {p}] Message #{m}: TOO LONG - dropping");
			continue;
		};

		T::DmpSink::handle_message(bound.as_bounded_slice());
		log::debug!(target: LOG, "[Page {p}] Migrated message #{m} from block {block}");
	}

	Ok(())
}
```
