### Title
DelegateResourceProcessor spot-reads `TotalNetWeight`/`TotalEnergyWeight` within a single TVM transaction, allowing manipulated resource-delegation collateral checks - ([File: actuator/src/main/java/org/tron/core/vm/nativecontract/DelegateResourceProcessor.java])

### Summary
The Solidity-callable `delegateResource` TVM opcode invokes `DelegateResourceProcessor.validate`, which computes the caller's currently "used" bandwidth/energy using the *instantaneous* global `TotalNetWeight`/`TotalEnergyWeight` counters read from the same in-flight `Repository` that a preceding `freezeBalanceV2`/`unfreezeBalanceV2` call in the *same transaction* can mutate. Because these counters (analogous to the manipulable spot pool balance in the Balancer report) are read fresh mid-transaction rather than from a time-weighted/finalized snapshot, a contract can inflate or deflate them before the delegation check executes, corrupting the derived "available balance to delegate" result.

### Finding Description
`DelegateResourceProcessor.validate` derives `netUsage`/`energyUsage` directly from `repo.getTotalNetWeight()` / `repo.getTotalEnergyWeight()`, multiplied against the account's raw usage and divided by fixed limits: [1](#0-0) 

This mirrors exactly the pattern in the external report: a "collateral"-style eligibility check (`ownerCapsule.getFrozenV2BalanceForBandwidth() - v2NetUsage < delegateBalance`) is derived from a global aggregate that is stored as a simple mutable counter, not a time-weighted oracle value. That counter is updated synchronously, in-place, by `FreezeBalanceV2Processor`/`UnfreezeBalanceV2Processor` via `repo.addTotalNetWeight`/`addTotalEnergyWeight`: [2](#0-1) 

Crucially, all of these operations — freeze, unfreeze, and delegate — are exposed as TVM opcodes reachable from a single smart-contract call (i.e., a single signed transaction), each operating on the same child `Repository` before it is committed: [3](#0-2) [4](#0-3) 

Because a contract can sequence `freezeBalanceV2(...)` (which increases `TotalNetWeight`/`TotalEnergyWeight` immediately via `repo.addTotalNetWeight`) and then `delegateResource(...)` within the very same transaction/child repository, the `netUsage`/`energyUsage` denominator used in the delegation eligibility check is computed against a value the attacker just modified in the same call stack, rather than a stable, block-finalized weight. This is structurally identical to the Balancer bug: a "TWAP-labeled" or "should-be-stable" quantity is actually read as a live, attacker-influenceable spot value inside the very calculation meant to bound how much an account may safely delegate.

### Impact Explanation
An attacker-controlled contract can, within one transaction, freeze balance to inflate `TotalNetWeight`/`TotalEnergyWeight`, immediately call `delegateResource` while the artificially-changed weight lowers the computed `v2NetUsage`/`v2EnergyUsage`, and pass the `frozenV2Balance - usage < delegateBalance` check when it should have failed (or vice versa, blocking a legitimate delegation). Successfully bypassing this check lets the caller delegate more bandwidth/energy than their real remaining allowance permits, effectively minting free/unbacked network resource capacity for a receiver account — a resource-forgery condition analogous to the "unbacked balance"/over-borrowing impact described in the source report (over-leveraging based on a manipulated collateral figure).

### Likelihood Explanation
Reachability is high: `freezeBalanceV2`, `unfreezeBalanceV2`, and `delegateResource` are all directly callable TVM opcodes from any deployed contract, requiring no special privilege beyond deploying/calling a contract and controlling an account with some TRX to freeze — well within reach of an unprivileged transaction broadcaster. The relevant Program-level plumbing for chaining these calls in one transaction already exists and is exercised by unit tests combining freeze + delegate operations in a single flow. [5](#0-4) 

However, whether the specific numeric window is exploitable to a materially damaging degree depends on the magnitude of weight change achievable in one transaction relative to the network-wide totals (`TotalNetWeight`/`TotalEnergyWeight` are chain-wide aggregates), which could make single-account manipulation only marginally effective unless combined with a very large freeze amount. This mitigating factor was not fully quantified in the available code/tests, so the practical severity should be validated with a concrete PoC before treating it as definitively High.

### Recommendation
Do not compute delegation eligibility using the live, same-transaction value of `TotalNetWeight`/`TotalEnergyWeight`. Snapshot these totals prior to any freeze/unfreeze/delegate sequence within a transaction (e.g., capture at block-header-committed values, or forbid combining freeze and delegate calls to the same resource type within one transaction/child repository), and re-validate using values that cannot be altered by the same call stack that triggers the eligibility check, consistent with how the underlying report recommends avoiding spot-derived values for security-critical calculations.

### Proof of Concept
1. Deploy a contract that, in a single external call:
   a. Calls `freezeBalanceV2(largeAmount, ENERGY)` — this immediately calls `FreezeBalanceV2Processor.execute`, incrementing `TotalEnergyWeight` via `repo.addTotalEnergyWeight` in the child repository (not yet committed to the block).
   b. Immediately calls `delegateResource(receiver, delegateBalance, ENERGY)`.
2. Inside `DelegateResourceProcessor.validate`, `repo.getTotalEnergyWeight()` reflects the just-inflated total from step (a), because both operations share the same `Repository` child chain before commit. [6](#0-5) 
3. This skews `energyUsage`/`v2EnergyUsage` downward relative to what it would be against the true, previously-committed `TotalEnergyWeight`, letting `delegateBalance` pass the `ownerCapsule.getFrozenV2BalanceForEnergy() - v2EnergyUsage < delegateBalance` check when it should not, in the same manner the source report demonstrates for the Balancer vault's spot-`virtualSupply`-based `_getTimeWeightedPrimaryBalance`.

  public void updateTotalResourceWeight(AccountCapsule accountCapsule,
                                        Common.ResourceCode freezeType,
                                        long unfreezeBalance,
                                        Repository repo) {
    switch (freezeType) {
      case BANDWIDTH:
        long oldNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForBandwidthV2(-unfreezeBalance);
        long newNetWeight = accountCapsule.getFrozenV2BalanceWithDelegated(BANDWIDTH) / TRX_PRECISION;
        repo.addTotalNetWeight(newNetWeight - oldNetWeight);
        break;
      case ENERGY:
        long oldEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        accountCapsule.addFrozenBalanceForEnergyV2(-unfreezeBalance);
        long newEnergyWeight = accountCapsule.getFrozenV2BalanceWithDelegated(ENERGY) / TRX_PRECISION;
        repo.addTotalEnergyWeight(newEnergyWeight - oldEnergyWeight);
        break;

        break;

        //this should never happen
        break;

  public boolean freezeBalanceV2(DataWord frozenBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, owner,
        frozenBalance.longValue(), null,
        "freezeBalanceV2For" + convertResourceToString(resourceType), nonce, null);

    try {
      FreezeBalanceV2Param param = new FreezeBalanceV2Param();
      param.setOwnerAddress(owner);
      param.setResourceType(parseResourceCodeV2(resourceType));
      param.setFrozenBalance(frozenBalance.sValue().longValueExact());

      FreezeBalanceV2Processor processor = new FreezeBalanceV2Processor();
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
      return true;
    } catch (ContractValidateException e) {
      logger.warn("TVM FreezeBalanceV2: validate failure. Reason: {}", e.getMessage());
    } catch (ArithmeticException e) {
      logger.warn("TVM FreezeBalanceV2: frozenBalance out of long range.");
    }
    if (internalTx != null) {
      internalTx.reject();
    }
    return false;
  }

  public boolean delegateResource(
      DataWord receiverAddress, DataWord delegateBalance, DataWord resourceType) {
    Repository repository = getContractState().newRepositoryChild();
    byte[] owner = getContextAddress();
    byte[] receiver = receiverAddress.toTronAddress();

    increaseNonce();
    InternalTransaction internalTx = addInternalTx(null, owner, receiver,
        delegateBalance.longValue(), null,
        "delegateResourceOf" + convertResourceToString(resourceType), nonce, null);

    try {
      DelegateResourceParam param = new DelegateResourceParam();
      param.setOwnerAddress(owner);
      param.setReceiverAddress(receiver);
      param.setDelegateBalance(delegateBalance.sValue().longValueExact());
      param.setResourceType(parseResourceCodeV2(resourceType));

      DelegateResourceProcessor processor = new DelegateResourceProcessor();
      processor.validate(param, repository);
      processor.execute(param, repository);
      repository.commit();
