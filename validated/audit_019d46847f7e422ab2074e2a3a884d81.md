Based on my investigation, I found a concrete local analog in the Snowbridge Outbound Queue V2 pallet, structurally similar to the Redstone "time travel" bug class: a state-transition invariant (reward should be conditioned on a verified success outcome) is silently dropped, allowing value to be paid out that does not correspond to the intended, successfully-completed action.

### Title
Relayer reward is paid regardless of delivery outcome (`success` flag ignored) - (File: bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs)

### Summary
`process_delivery_receipt` in the Outbound Queue V2 pallet decodes a `DeliveryReceipt` from a verified Ethereum event log — including a `success: bool` field indicating whether the message dispatch on Ethereum actually succeeded — but never checks this field before paying out the relayer reward. Any signed account can submit a `submit_delivery_receipt` extrinsic with a legitimately-verified proof for a **failed** dispatch and still receive the full fee.

### Finding Description
The `InboundMessageDispatched` event emitted by the Ethereum Gateway contract carries a `success` flag, and this is decoded into `DeliveryReceipt.success` [1](#0-0) .

The extrinsic `submit_delivery_receipt` verifies the proof and event log via `T::Verifier::verify`, decodes the receipt, and forwards it to `process_delivery_receipt` [2](#0-1) .

`process_delivery_receipt` looks up the `PendingOrder` by `receipt.nonce`, and if `order.fee > 0`, unconditionally calls `T::RewardPayment::register_reward` — the `receipt.success` value is never read or checked anywhere in this function: [3](#0-2) 

The pallet's own top-level documentation confirms the intended flow is that the reward should only be paid "when the message has been verified and executed": [4](#0-3)  — but the implementation pays regardless of whether execution succeeded.

The `PendingOrder` itself only tracks `nonce`, `fee`, and `block_number` — no outcome data, and is created purely from the outbound message content, not from any execution result: [5](#0-4) 

### Impact Explanation
Fee/reward funds are settled to the relayer even when the underlying dispatched command failed on Ethereum (e.g., reverted due to insufficient gas allowance, a bad target contract call, or a command that is designed to always fail). This breaks the "settle exactly once to the rightful beneficiary and amount" invariant: the amount paid is decoupled from whether the paid-for service (successful execution) was actually delivered. Since any unprivileged account can act as a relayer and submit `submit_delivery_receipt` for a legitimately-proven but failed delivery, this allows systematic drain of the reward/fee pool for messages that provide no value to the protocol or its users — a form of unbacked payout at the expense of whoever funds the fee account.

### Likelihood Explanation
No privileged actor, governance action, or malicious relayer/prover assumption is required — the exploit is simply to submit a normal, cryptographically valid delivery-receipt proof for a message whose Ethereum-side dispatch failed (which can happen naturally, or can be engineered by controlling the outbound command's gas/target so that failure is deterministic). Because the check on `success` is entirely absent from the code path, this triggers on every call where `order.fee > 0` and the message dispatch failed, making it fully deterministic and repeatable, not a race condition or edge case.

### Recommendation
Gate the reward payment in `process_delivery_receipt` on `receipt.success`. On failure, either withhold the reward or route to a reduced-refund path, and still remove the pending order to prevent it from remaining unresolved:
```rust
if receipt.success && order.fee > 0 {
    T::RewardPayment::register_reward(&reward_account, T::DefaultRewardKind::get(), order.fee);
}
```

### Proof of Concept
1. Have any account send an outbound message via the normal XCM flow so a `PendingOrder{nonce, fee, ..}` with `fee > 0` is created (`do_process_message`) [5](#0-4) .
2. On the Ethereum side, ensure the corresponding command dispatch fails (e.g., by crafting a command whose gas/target guarantees a revert on `GatewayProxy`), so the emitted `InboundMessageDispatched` event has `success = false`.
3. As any signed relayer account, submit `submit_delivery_receipt` with the (legitimate) event log/proof for that failed dispatch.
4. Observe that `process_delivery_receipt` pays the reward via `T::RewardPayment::register_reward` and removes the `PendingOrder`, exactly as it would for a successful dispatch, because `receipt.success` is never consulted [6](#0-5) . This is directly demonstrated by the existing integration tests, which construct `DeliveryReceipt { success: true, .. }` and confirm reward registration — no equivalent test exists asserting that `success: false` withholds payment [7](#0-6) .

```rust
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
```
