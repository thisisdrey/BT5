### Title
Unmetered gas cost for removing an unbounded number of plain access keys during `DeleteAccount` execution enables a chunk-processing DoS - ([File: core/store/src/utils/mod.rs])

### Summary
`DeleteAccountAction` execution calls `remove_account`, which iterates over and removes **every** access key stored under an account, with no upper bound on the number of keys. While gas-key nonce removals are explicitly compute-metered via `storage_removes_compute` and charged into `result.compute_usage`, the removal of ordinary (non-gas) access keys is **not** charged any per-key compute cost — the whole `DeleteAccount` action is billed only the flat `delete_account_cost` fee regardless of how many plain access keys the account holds.

### Finding Description
`remove_account` in [1](#0-0)  walks the full access-key trie range of the account being deleted and collects every access key (and gas-key nonce row) into `keys_to_remove`, later removing them one by one from `state_update`. The count of gas-key nonces is tracked and returned in `RemoveAccountResult` so the caller can charge compute, but the number of *plain* access keys removed is not tracked or billed at all.

In `action_delete_account` (`runtime/runtime/src/actions.rs`, lines 371–386, seen in the excerpt above), only `remove_result.gas_key_nonce_count` is used to add `compute_usage` via `storage_removes_compute`; there is no analogous charge for the number of ordinary access-key trie removals performed by the same call to `remove_account`. The `DeleteAccount` action's gas cost model (per `docs/RuntimeSpec/Fees/Fees.md`, lines 73-76) is a flat `delete_account_cost` base fee plus the outgoing transfer receipt fee — it does not scale with the number of access keys on the account.

Nothing in the protocol bounds how many access keys an account may accumulate via repeated `AddKeyAction`s (unlike `MAX_DELEGATES` in the Alchemix report, or the `MAX_ACCOUNT_DELETION_STORAGE_USAGE` check that *does* exist for total storage size at line 348). An attacker only needs to pay per-key storage staking (~1 NEAR per 100kB) to accumulate an arbitrarily large number of access keys (each access key is tiny, e.g., tens of bytes, so tens of thousands fit well under `MAX_ACCOUNT_DELETION_STORAGE_USAGE`). When the attacker then submits a single `DeleteAccount` action, the runtime performs O(N) trie iteration, O(N) removals, and O(N) trie-proof/witness generation work, for a gas cost that is O(1).

This is the same root-cause pattern as the reported Alchemix issue: a user-triggerable operation whose actual computational/storage cost scales with attacker-controlled state size (number of delegates / number of access keys), but whose charged fee does not scale accordingly, letting an attacker force disproportionate validator work per unit of gas paid.

### Impact Explanation
Because the per-key work is essentially free (unlike the metered gas-key nonce path), an attacker can force chunk producers to do large amounts of trie-removal/storage-proof work while only paying the fixed `delete_account_cost`. Since `EnforcePerReceiptStorageProofLimit` and chunk-level compute/gas limits gate how much other work fits into the same chunk (see `protocol-model/spec/runtime-execution.md`, lines 106-108, 126), a sufficiently large mismatch between real cost and charged gas increases the risk of storage-witness bloat and processing time for that receipt disproportionate to its gas price, which is a resource-exhaustion/DoS vector against chunk producers — directly analogous to the Alchemix `MAX_DELEGATES` gas-DoS finding, though bounded in practice by `MAX_ACCOUNT_DELETION_STORAGE_USAGE` and by the up-front storage staking cost the attacker must pay to create the keys.

### Likelihood Explanation
Reaching this path requires no special privileges: any account owner can call `AddKeyAction` repeatedly (each individually gas-metered and requiring storage staking balance) and then submit a single `DeleteAccountAction`. The attack is entirely self-contained (attacker only affects their own account's deletion), cheap to set up incrementally over multiple transactions, and triggerable in one final transaction.

### Recommendation
Track the count (and/or total key bytes) of ordinary access keys removed by `remove_account`, analogous to `gas_key_nonce_count`/`gas_key_nonce_total_key_bytes`, and add a corresponding `storage_removes_compute` charge to `result.compute_usage` in `action_delete_account` so that the gas/compute charged for `DeleteAccount` scales with the actual number of trie removals performed, closing the metering gap between real work and charged cost.

### Proof of Concept
Conceptual reproduction (would require a running node/test-loop environment to fully confirm gas/compute numbers, which I could not execute in this read-only analysis):
1. Create an account and, over several transactions (each individually charged the standard `add_key_cost`), add N (e.g. 20,000) full-access or function-call access keys to it — well within `MAX_ACCOUNT_DELETION_STORAGE_USAGE` given the small per-key size.
2. Submit a single `DeleteAccountAction` on that account.
3. Observe that `action_delete_account` charges only the flat `delete_account_cost`/transfer fee (per `Fees.md`) while `remove_account` performs O(N) trie iteration and O(N) key removals with no additional `compute_usage` charged for the plain-key removals (confirmed by reading `action_delete_account`, `runtime/runtime/src/actions.rs` lines 371-386, where only `gas_key_nonce_count`-based compute is added).
4. Compare observed compute/gas usage against actual execution time/trie work to demonstrate the metering gap scales with N while the charged gas does not.

/// Removes account, code and all access keys and gas keys associated to it.
pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }
