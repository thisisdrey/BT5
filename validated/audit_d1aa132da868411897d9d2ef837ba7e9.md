### Title
`ValidateMultiSign` precompile double-counts a single signer's weight when the same key produces two distinct valid ECDSA signatures for the same hash - ([File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java])

### Summary
The `ValidateMultiSign` TVM precompile (address `0x0e` family, reachable from any contract call via a `STATICCALL`/`CALL` from an unprivileged caller) accumulates `Permission` weight per-signature instead of per-unique-signer-address, and its duplicate-detection logic only skips a signature when both the recovered address *and* the exact signature bytes match a previously seen entry. Because ECDSA signing is non-deterministic (or trivially malleable), a single private key can produce multiple distinct, individually valid signatures over the same message hash. Each such signature recovers to the same address but is accepted as an "additional" signer, so its weight is added to `totalWeight` again, letting one key satisfy a multi-signature `threshold` that was designed to require multiple independent authorized keys.

### Finding Description
In `PrecompiledContracts.ValidateMultiSign.execute` [1](#0-0) , the loop over `signatures` recovers `recoveredAddr` from each signature and merges it with the signature bytes to form `sign`. The skip condition is:

```
if (ByteArray.matrixContains(executedSignList, recoveredAddr)) {
  if (ByteArray.matrixContains(executedSignList, sign)) {
    continue;
  }
  MUtil.checkCPUTime();
}
long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
...
totalWeight += weight;
executedSignList.add(sign);
executedSignList.add(recoveredAddr);
```

This only `continue`s (skips adding weight) when the *exact byte-identical* `sign` (address+signature) has already been recorded. If the same key produces a second, byte-different, but equally valid signature over the same `hash` (trivial via a fresh random nonce `k`, or via canonical/non-canonical `s` malleability), `matrixContains(executedSignList, sign)` is false even though `matrixContains(executedSignList, recoveredAddr)` is true, so the code falls through and adds `weight` a second time via `totalWeight += weight`. There is no check that each `recoveredAddr` contributes weight at most once — the intended uniqueness invariant (each authorized key counted once towards `threshold`) is broken by accepting non-canonical/duplicate-by-key-but-distinct-by-bytes signatures, structurally analogous to the ML-DSA report's failure to reject non-unique/duplicate encodings that should map to a single canonical, single-counted signer.

This mirrors the reported bug class: verification logic that should treat "signed by key K" as a single, canonically-unique fact instead accepts multiple distinct byte encodings of essentially the same authorization and lets them each independently satisfy the check, defeating the intended uniqueness/threshold guarantee.

### Impact Explanation
`ValidateMultiSign` is used by smart contracts (including wallet/multisig contracts) to verify off-chain-collected signature sets against an on-chain `Permission` and its `threshold` before authorizing an action (e.g., releasing funds, approving a transfer). An attacker who controls just one key in the permission's key list — even with a low weight — can supply that key's signature twice (in two different, self-generated byte encodings) to be counted as two separate approvals. If the `threshold` can be met by summing multiple copies of a single key's weight (e.g., threshold of 2, single key weight 1, only one authorized signer available), this allows unauthorized execution of the guarded contract logic, i.e., single-key impersonation of a multi-party approval requirement — a concrete unauthorized-account-operation / theft-of-funds risk for any contract that relies on this precompile for multisig authorization.

### Likelihood Explanation
Reaching this path requires nothing more than a normal `TriggerSmartContract` transaction from an unprivileged, unauthenticated account, invoking any contract that calls `ValidateMultiSign` (a public TVM precompile, address callable by any deployed contract). Producing two distinct valid ECDSA signatures for the same message with the same private key is trivial (default randomized `k`, or simple `s`/`n-s` malleability) and requires no privileged access — only possession of one of the (possibly low-weight) permission keys, which for many use cases (e.g., self-custodied multisig wallets, exchange-signer sets where the caller controls one leg) is realistic.

### Recommendation
Track uniqueness by recovered address only, not by address+signature-bytes. Maintain a `Set` of already-counted `recoveredAddr` values and skip weight accumulation (not just `continue` on exact-byte duplicates) whenever the address has already been counted, e.g.:
```java
Set<ByteString> countedAddrs = new HashSet<>();
for (byte[] sign : signatures) {
  byte[] recoveredAddr = recoverAddrBySign(sign, hash);
  ByteString addrKey = ByteString.copyFrom(recoveredAddr);
  if (!countedAddrs.add(addrKey)) {
    continue; // already counted this signer, regardless of signature bytes
  }
  long weight = TransactionCapsule.getWeight(permission, recoveredAddr);
  if (weight == 0) {
    return Pair.of(true, DATA_FALSE);
  }
  totalWeight += weight;
}
```
This mirrors the correct pattern already used in `TransactionCapsule.checkWeight` [2](#0-1) , which keys duplicate detection strictly on the recovered address (via `addMap.containsKey(base64)`), not on the raw signature bytes.

### Proof of Concept
1. Create an account `A` with an `Active` permission containing a single key `K` (weight `1`) and `threshold = 2`.
2. Deploy/trigger a contract that calls the `ValidateMultiSign` precompile with `permissionId` pointing at that permission and `data` = arbitrary message.
3. Off-chain, compute `hash = sha256(merge(address, permissionId, data))` as done in `execute` [3](#0-2) .
4. Sign `hash` twice with the single private key `K`, obtaining two different signature byte strings `sig1 != sig2` (either by using two different random nonces, which `ECKey.sign` will naturally do, or by flipping `s` to `n-s`/adjusting recovery id).
5. Submit `signatures = [sig1, sig2]` to `ValidateMultiSign`.
6. Both signatures recover to the same address `K`. Because `sign1 != sign2` at the byte level, `matrixContains(executedSignList, sign)` returns false the second time, so the loop does not `continue` and adds `weight` (1) again, yielding `totalWeight = 2 >= threshold(2)` — the call returns `dataOne()` (success) even though only one authorized key actually approved.

This confirms that a single key can satisfy a 2-of-N (or higher) multisig threshold check enforced by `ValidateMultiSign`.
