### Title
`git_repository`/`new_git_repository` Force-Enables Git's Unsafe Local-File Submodule Protocol During Fetch, Allowing an Untrusted Repository to Exfiltrate Arbitrary Local Files - (File: `tools/build_defs/repo/git_worker.bzl`)

### Summary
Bazel's Starlark git-fetching helper `update_submodules` unconditionally passes `-c protocol.file.allow=always` to `git submodule update --init`, which re-enables Git's `file://` submodule-clone transport that upstream Git disabled by default (defaulting to `user`, i.e. off for non-interactive commands) specifically to close CVE-2022-39253 (local-clone information disclosure via malicious `.gitmodules`). Because the flag is hard-coded rather than scoped, any `git_repository`/`new_git_repository` invocation with `init_submodules`/`recursive_init_submodules = True` that fetches an attacker-influenced remote (an untrusted branch/tag/commit, a compromised mirror, or any external Git dependency) will honor a malicious `.gitmodules` entry pointing at a `file://` path, causing Git to locally "clone" and copy the contents of an arbitrary path on the machine running the build into the fetched external repository.

### Finding Description
`_update` in `tools/build_defs/repo/git_worker.bzl` performs an `init` → `add_origin` → `fetch` → `reset` → `clean` sequence, then optionally calls `update_submodules`: [1](#0-0) 

`update_submodules` executes `git submodule update --init [--recursive] --checkout --force` with the config override `-c protocol.file.allow=always` in both the recursive and non-recursive branches: [2](#0-1) 

The submodule URL that this command resolves is read from the `.gitmodules` file that is part of the fetched repository's tree — i.e., content fully controlled by whoever controls the remote/branch/tag/commit being fetched. `.gitmodules` content is *not* the pinned/verified artifact (the `commit`/`tag`/`branch` attribute only pins the top-level tree); an attacker who controls the remote (or a branch/tag on it, or a compromised mirror at the `remote` URL) can set:

```
[submodule "x"]
    path = x
    url = file:///home/victim/.ssh
```

Upstream Git changed `protocol.file.allow`'s default to `user` (disallowed for commands like `submodule update` that are typically run non-interactively/automatically) precisely to stop this class of attack (CVE-2022-39253: cloning a repo could silently local-clone unrelated files/directories on disk). Bazel's `git_worker.bzl` explicitly reverts this protection with `protocol.file.allow=always`, citing bazelbuild/bazel#17040 as the reason (workaround for local-remote repos used in Bazel's own tests), but applies it globally to every submodule update performed by the rule, including with attacker-influenced repositories.

### Impact Explanation
This breaks the "untrusted content stays data" invariant for git-based fetches: content from a repository the build only intends to read source code from (bounded to that repo's own tree) can direct Git to read and materialize the contents of an arbitrary local path on the build machine — e.g., another checked-out private repository, `~/.ssh`, or any other path reachable as a git repo — into the fetched external repository directory, which then becomes part of the build's source tree (readable by build actions, packagable into outputs, or shipped in generated artifacts). This is a "read outside the repository" violation reachable purely through content the attacker publishes (the `.gitmodules` file of the remote/branch being fetched), matching the bug class of the go-getter advisory (Git configuration is coerced into enabling unintended, dangerous Git behavior during an update/fetch operation).

### Likelihood Explanation
Any Bazel project using `git_repository`/`new_git_repository` with `init_submodules = True` or `recursive_init_submodules = True` against a remote that is not fully trusted (a third-party dependency's Git repo, a fork, a CI job building an external contributor's branch/PR via `git_repository`, or a mirror that could be tampered with) is exposed. No special privileges beyond publishing to/controlling that remote are required; the victim's own default-flags Bazel build triggers the vulnerable code path automatically whenever submodules are initialized.

### Recommendation
Do not force `protocol.file.allow=always` unconditionally. Restrict it to the narrow, already-known-safe case from #17040 (e.g., only when the top-level `remote` itself is a local `file://` path controlled by the invoking user), or drop the override entirely and let Git's safe default (`user`) apply, surfacing a clear error/instruction if a legitimate local-submodule workflow needs to opt in explicitly (e.g., via an explicit new attribute rather than a blanket override).

### Proof of Concept
1. Create a "victim-local" directory containing sensitive files, e.g. `$TEST_TMPDIR/victim_secret/` initialized as its own Git repo with a file `secret.txt`.
2. Create an attacker Git repository `attacker_repo` with a `.gitmodules`:
   ```
   [submodule "leak"]
       path = leak
       url = file:///$TEST_TMPDIR/victim_secret
   ```
   and a submodule gitlink entry pointing at that repo's current commit.
3. In a `MODULE.bazel`/`WORKSPACE`, declare:
   ```python
   git_repository(
       name = "attacker",
       remote = "<attacker_repo path or URL>",
       branch = "main",
       recursive_init_submodules = True,
   )
   ```
4. Run `bazel build @attacker//...` (or `bazel fetch`), then inspect `$(bazel info output_base)/external/+git_repository+attacker/leak/secret.txt` — it will contain the contents of `victim_secret`, demonstrating that content from outside the intended repository (`$TEST_TMPDIR/victim_secret`) was pulled into the fetched external repository via the attacker-controlled `.gitmodules` and the forced `protocol.file.allow=always` in `update_submodules` (`tools/build_defs/repo/git_worker.bzl:210-217`).

```text
def _update(ctx, git_repo):
    ctx.delete(git_repo.directory)

    init(ctx, git_repo)
    add_origin(ctx, git_repo, ctx.attr.remote)
    fetch(ctx, git_repo)
    reset(ctx, git_repo)
    clean(ctx, git_repo)

    if git_repo.recursive_init_submodules:
        ctx.report_progress("Updating submodules recursively")
        update_submodules(ctx, git_repo, recursive = True)
    elif git_repo.init_submodules:
        ctx.report_progress("Updating submodules")
        update_submodules(ctx, git_repo)
```

```text
def update_submodules(ctx, git_repo, recursive = False):
    if recursive:
        # "protocol.file.allow=always" allows the submodule command clone from a local directory.
        # It's necessary for Git 2.38.1 and assoicated backport versions.
        # See https://github.com/bazelbuild/bazel/issues/17040
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--recursive", "--checkout", "--force")
    else:
        _git_maybe_shallow(ctx, git_repo, "-c", "protocol.file.allow=always", "submodule", "update", "--init", "--checkout", "--force")
```
