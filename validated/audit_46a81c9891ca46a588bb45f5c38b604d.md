## Title
Division by zero in `calc-treasury-lp-preview` can permanently freeze vault deposits/redemptions - (File: `mainnet/contracts/vault/v0-vault-usdc.clar` and equivalent per-vault files, e.g. `v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdh.clar`)

### Summary
`calc-treasury-lp-preview`, used by `total-supply-preview`, which is in turn used by `convert-to-shares-preview`/`convert-to-assets-preview` (the functions backing every `deposit` and `redeem` call), contains a division whose denominator can become zero, exactly analogous to the reported `_onEarnings` bug in River.1.sol where `sharesToMint` divides by a value that can equal zero when the numerator components collide.

### Finding Description
In `calc-treasury-lp-preview`: [1](#0-0) 

```
(define-private (calc-treasury-lp-preview)
  (let ((scaled-principal (var-get principal-scaled))
        (idx (var-get index))
        (next (next-index))
        (old-debt (mul-div-down scaled-principal idx INDEX-PRECISION))
        (new-debt (mul-div-down scaled-principal next INDEX-PRECISION))
        (debt-delta (if (> new-debt old-debt) (- new-debt old-debt) u0))
        (reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
        (ta-preview (total-assets-preview)))
    (if (> reserve-inc u0)
        (mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))
        u0)))
```

`mul-div-down` performs a raw Clarity division `(/ (* x y) z)` with no zero-guard: [2](#0-1) 

The denominator here is `(- ta-preview reserve-inc)`. `ta-preview` (`total-assets-preview`) equals `current-assets + interest`, where `interest` is the cumulative unrealized interest not yet reflected in `assets`: [3](#0-2) 

If the vault's liquid `assets` balance is `u0` (i.e. utilization is at 100%, all liquidity currently borrowed out) and the accumulated unrealized interest at that moment is exactly equal to `reserve-inc` (the reserve-fee portion of the interest delta computed for this call), the subtraction `(- ta-preview reserve-inc)` equals zero, and the subsequent `mul-div-down` call panics on division by zero, aborting the transaction — mirroring the River `_onEarnings` division-by-zero bug where `(_assetBalance() * BASE) - (_amount * globalFee)` could hit zero.

This is directly reachable by an ordinary principal: any `deposit` or `redeem` call triggers `accrue`, and even the read-only `convert-to-shares`/`convert-to-assets` getters invoke `convert-to-shares-preview`/`convert-to-assets-preview`, which call `total-supply-preview` → `calc-treasury-lp-preview`: [4](#0-3) [5](#0-4) 

Once this state is hit, every subsequent `deposit`/`redeem` call for that vault reverts, since the same computation runs on every accrual, permanently freezing user funds/yield in that vault until the exact colliding value shifts (which may not happen deterministically since `fee-reserve` and `principal-scaled`/`index` evolve deterministically with time and borrow activity — a borrower or depositor can nudge state to try to force or avoid the collision, but once triggered by any caller, the vault is bricked for all until manually intervened).

### Impact Explanation
This lands on **High – temporary freezing of funds** (and potentially **Critical – permanent freezing of funds** if the exact colliding state persists and cannot be un-stuck through normal user calls, since the transaction reverts deterministically given the state, and the state only changes via calls that themselves trigger the same computation). At minimum, deposits/redeems on the affected vault become unusable until off-chain/DAO intervention resets state.

### Likelihood Explanation
The collision condition (utilization at 100%, i.e. `assets == u0`, combined with the fee-reserve interest slice equaling total unrealized interest) is a narrow, deterministic function of protocol state (`principal-scaled`, `index`, `fee-reserve`, `assets`) rather than of an oracle price. A vault that is frequently near-100% utilized (a design goal for lending vaults) with a nonzero `fee-reserve` is plausible to hit this arithmetic edge organically as interest accrues over time, without any admin misconfiguration or DAO compromise — only ordinary usage (borrowing to full utilization) is required.

### Recommendation
Guard the denominator in `calc-treasury-lp-preview` before dividing, e.g. treat the case `(<= ta-preview reserve-inc)` as `u0` treasury-LP contribution (mirroring the `is-eq ta u0`/`is-eq ts u0` guards already used in `convert-to-shares-preview`/`convert-to-assets-preview`), instead of relying on the implicit assumption that `ta-preview > reserve-inc`.

### Proof of Concept
1. Deploy/observe a vault (e.g. `v0-vault-usdc.clar`) with a nonzero `fee-reserve` configured.
2. Drive utilization to 100% via normal `borrow` calls so `(var-get assets)` becomes `u0`.
3. Let time pass so that `next-index` produces a `debt-delta` on the next `accrue`, such that the accumulated `interest` component of `total-assets-preview` equals `reserve-inc` (the fee-reserve share of that `debt-delta`) — achievable at the point where cumulative interest since last state settlement composes solely of reserve-share-eligible interest with `assets == u0`.
4. Call `deposit` or `redeem` (or even the read-only `convert-to-shares`/`convert-to-assets`), triggering `accrue` → `calc-treasury-lp-preview` → `(mul-div-down reserve-inc (total-supply) (- ta-preview reserve-inc))` with denominator `u0`.
5. Observe the call panics with a division-by-zero runtime error, reverting the transaction and freezing the vault's deposit/redeem path.

Note: exact numeric reproduction requires simulating the vault's interest-accrual timeline in a test harness; the index-based analysis above establishes the precondition and root cause with file/line-level certainty. If more granular contract dependencies (e.g. DAO-set bounds on `fee-reserve`) are needed to fully bound likelihood, those setter functions were only partially located in this session and would benefit from direct review in a Devin session with full repository access.
