### Title
Attacker can fill a victim's `depositTokensOfAccount` list to `MAX_TOKENS_PER_USER` with dust transfers, blocking the victim from depositing new collateral types or receiving `DepositToken` transfers - (File: contracts/Pool.sol)

### Summary
`Pool.addToDepositTokensOfAccount` is invoked from `DepositToken._transfer`/`_mint` whenever a recipient's balance goes from 0 to non-zero. Each distinct `DepositToken` occupies one slot in the per-account `MappedEnumerableSet` shared between deposit and debt tokens, capped by `MAX_TOKENS_PER_USER`. An unprivileged attacker can acquire dust amounts of every registered `DepositToken` and `transfer` them to a victim, filling all slots. Afterwards, any action that would add a new token to the victim's list — `deposit()` of a collateral type the victim doesn't yet hold, or anyone transferring a new `DepositToken` to the victim — reverts with `UserReachedMaxTokens` inside `onlyIfAdditionWillNotReachMaxTokens`. This mirrors the CVE bug class: a resource (the per-account token slot) is allocated on the recipient's behalf without their consent and is only released on the zero-balance path, so state "leaks" into the victim's account and blocks legitimate operations.

### Finding Description
- `DepositToken._transfer` credits the recipient and, when `_recipientBalanceBefore == 0 && amount_ > 0`, calls `pool.addToDepositTokensOfAccount(recipient_)` (`contracts/DepositToken.sol:498-526`). There is no opt-in; the recipient cannot reject the slot allocation.
- `DepositToken._mint` does the same for the beneficiary of `deposit()` (`contracts/DepositToken.sol:469-489`).
- `Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens(account_)` which reverts `UserReachedMaxTokens` once `depositTokensOfAccount.length(account_) + debtTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` (`contracts/Pool.sol:216-220`, storage in `contracts/storage/PoolStorage.sol` via `MappedEnumerableSet`).
- Removal happens only in `DepositToken._burn`/`_transfer` when the account's balance reaches exactly 0 (`contracts/DepositToken.sol:460-462`, `523-525`), i.e., entries persist as long as dust remains.
- Attack path: attacker deposits (or buys) minimal amounts of each registered `DepositToken`, then calls `DepositToken.transfer(victim, 1 wei)` for each. Each first-time receipt permanently occupies a slot until the victim actively zeroes it. Once `MAX_TOKENS_PER_USER` is reached:
  - `victim → depositTokenX.deposit(amount, victim)` for any not-yet-held collateral reverts inside `_mint → addToDepositTokensOfAccount`.
  - Third-party transfers/liquidation `seize` payouts (`Pool.liquidate` calls `depositToken_.seize(account_, _msgSender, _toLiquidator)` → `_transfer`, `contracts/Pool.sol:589`) to a fresh-holder liquidator account also revert if that liquidator's list is filled, which can be used to make a liquidator address unusable.

### Impact Explanation
Temporary freezing of funds / griefing: while the victim's slot list is saturated, the victim cannot add new collateral types to their position (blocking new deposits, and blocking receipt of any `DepositToken` they don't already hold). A liquidator whose list is pre-filled by an attacker cannot be sent collateral via `seize` for tokens it doesn't already hold, causing `Pool.liquidate` to revert for those collateral types. The attack costs only dust balances of each deposit token plus gas; the victim must spend transactions transferring the dust back out (full balance to trigger `removeFromDepositTokensOfAccount`) to recover, and locked/healthy-position victims with debt may be unable to freely move collateral due to `_revertIfLocked` (`contracts/DepositToken.sol:180-182`, `348-354`), extending the freeze duration since `unlockedBalanceOf` returns 0 for accounts whose collateral is fully backing debt.

### Likelihood Explanation
Fully permissionless: requires only an EOA holding dust of each registered deposit token, obtainable through normal `deposit()` calls. No privileged role, no oracle manipulation, no governance action. The cap (`MAX_TOKENS_PER_USER`) and the registered-token set bound the cost linearly in the number of pool collaterals. The mitigation is that the victim can usually self-clear slots, so severity is Medium/Low — it is a liveness/temporary-freezing issue, not theft.

### Recommendation
Do not auto-enroll recipients into `depositTokensOfAccount` on plain `transfer`/`transferFrom`, or make the cap check apply only to actions initiated by the account holder (e.g., `deposit()` with `onBehalfOf_ == _msgSender()`). Alternatively, allow overflow receipts but exclude un-enrolled tokens from `depositOf`/`debtPositionOf`, or provide a victim-callable `removeDepositTokenFromMyAccount(token_)` that forcibly sweeps dust so a user can always clear attacker-planted slots even when collateral is locked.

### Proof of Concept
Foundry fork test outline (against a deployed Pool, e.g. Optimism):

```solidity
function test_fillVictimTokenList() public {
    address victim = makeAddr("victim");
    IPool pool = IPool(POOL);
    uint256 max = pool.MAX_TOKENS_PER_USER();

    address[] memory dts = pool.getDepositTokens();
    for (uint256 i; i < dts.length && i < max; ++i) {
        DepositToken dt = DepositToken(dts[i]);
        // attacker deposits 2 wei of underlying and transfers 1 wei dust to victim
        deal(dt.underlying(), attacker, 10);
        IERC20(dt.underlying()).approve(address(dt), 10);
        dt.deposit(2, attacker);
        dt.transfer(victim, 1); // occupies a slot in victim's list
    }

    // victim's list is saturated
    assertEq(pool.getDepositTokensOfAccount(victim).length, /* filled slots */);

    // victim tries to deposit a collateral type not yet held -> reverts
    DepositToken newDt = DepositToken(dts[ /* not transferred */ ]);
    deal(newDt.underlying(), victim, 1e18);
    vm.startPrank(victim);
    IERC20(newDt.underlying()).approve(address(newDt), 1e18);
    vm.expectRevert(UserReachedMaxTokens.selector);
    newDt.deposit(1e18, victim);
    vm.stopPrank();
}
```

The revert path is `deposit → _mint → pool.addToDepositTokensOfAccount → onlyIfAdditionWillNotReachMaxTokens → UserReachedMaxTokens` (`contracts/Pool.sol:204-220`, `contracts/DepositToken.sol:469-489`).
