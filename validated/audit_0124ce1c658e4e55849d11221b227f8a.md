### Title
Unbounded array allocation from attacker-controlled ABI length in TVM precompile helpers can crash the node (OutOfMemoryError) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The netCDF-C CVE involves an integer-overflow-driven buffer allocation during parsing of untrusted NC variable data, leading to memory corruption/RCE. The closest reachable analog in java-tron is in the ABI-array extraction helpers of the TVM precompiled-contract framework, where a length field taken directly from call data is used to size a Java array without any upper-bound validation.

### Finding Description
`extractBytes32Array`, `extractBytesArray`, and `extractSigArray` in `PrecompiledContracts.java` read a length word from the caller-supplied precompile input and pass it straight into an array allocation: [1](#0-0) 

`int len = words[offset].intValueSafe();` followed by `new byte[len][]` (and similarly for `extractBytesArray`/`extractSigArray`). `intValueSafe()` does not reject out-of-range values — it merely clamps overflowing/negative results to `Integer.MAX_VALUE`: [2](#0-1) 

Because a fully attacker-controlled 256-bit word in the precompile's call data is decoded into `len`, an attacker can force `len` to `Integer.MAX_VALUE` by supplying a value that overflows 4 bytes (e.g. `0x00000000000000000000000000000000000000000000010000000000000000` or any value with `bytesOccupied() > 4`). The subsequent `new byte[Integer.MAX_VALUE][]` attempts to allocate a reference array of ~2^31 elements (multiple gigabytes on a 64-bit JVM), which throws `OutOfMemoryError` — an unrecoverable `Error`, not an `Exception`. Unlike the netCDF-C bug (which leads to memory corruption/RCE from an integer overflow before allocation), this is the same root-cause class — unchecked, attacker-controlled length feeding a buffer/array allocation before any bounds validation is performed — but the java runtime turns it into an uncatchable-by-`catch(Exception)` `OutOfMemoryError` rather than a heap overflow.

### Impact Explanation
`PrecompiledContracts` implementations are dispatched from TVM opcode execution (`CALL`/`STATICCALL` to a precompile address) as part of ordinary contract execution, meaning any account that can broadcast a transaction invoking a contract that calls the vulnerable precompile can trigger this path. Because `OutOfMemoryError` is a `java.lang.Error`, it is very likely to escape generic `catch (Exception e)` handlers used elsewhere in the VM/actuator execution pipeline, propagating up through transaction execution and potentially crashing the node process or destabilizing the JVM for all concurrently executing threads (including block application in `Manager`). This matches the "node crash or halt" impact category permitted by the validation rules.

### Likelihood Explanation
Triggering the condition only requires crafting call data with one oversized length word and invoking the corresponding precompiled contract via a normal, unprivileged transaction — no special privileges, staking, or witness/SR status is required. The exact precompiled contract(s) that route through `extractBytes32Array`/`extractBytesArray`/`extractSigArray` could not be conclusively enumerated within the available search iterations, so the specific externally callable entry point (e.g., a batch/multi-signature verification precompile) should be confirmed by a full-repository review before treating this as fully validated.

### Recommendation
Add explicit upper-bound validation on `len` (and any other attacker-controlled length taken from `intValueSafe()`/`longValueSafe()`) in `extractBytes32Array`, `extractBytesArray`, and `extractSigArray` before allocating arrays — e.g., reject if `len` exceeds the maximum plausible number of ABI-encoded words derivable from the actual `data`/`words` array length, mirroring the bounds checks already present in `isValidAbiEncoding`.

### Proof of Concept
1. Deploy/call a contract path that invokes the TVM precompile relying on `extractBytes32Array`/`extractBytesArray`/`extractSigArray` (e.g., a signature/array-based precompiled contract) via a standard `TriggerSmartContract`.
2. Encode the length word for the target array parameter as a 32-byte word whose first 28 bytes are non-zero (so `bytesOccupied() > 4`), forcing `intValueSafe()` to return `Integer.MAX_VALUE`.
3. Submit the transaction; the precompile's `execute()` call reaches `new byte[Integer.MAX_VALUE][]`, throwing `OutOfMemoryError` during transaction execution.
4. Observe whether the error propagates past the transaction-execution try/catch, destabilizing or crashing the node — confirm via full-repo inspection of the exact precompile that reaches this helper and its exception-handling wrapper in `Manager`/`TransactionTrace`.

  /**
   * In case of int overflow returns Integer.MAX_VALUE otherwise works as #intValue()
   */
  public int intValueSafe() {
    int bytesOccupied = bytesOccupied();
    int intValue = intValue();
    if (bytesOccupied > 4 || intValue < 0) {
      return Integer.MAX_VALUE;
    }
    return intValue;
  }
