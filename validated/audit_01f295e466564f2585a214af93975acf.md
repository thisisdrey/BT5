### Title
Instantaneous, TWAP-less spot pricing in the on-chain Bancor Exchange allows any user to manipulate `ExchangeTransactionContract` execution prices and extract value from other traders in the same block - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeTransactionActuator.java`)

### Summary
Exactly like the DYAD `kerosene` price, which is derived instantaneously from mutable TVL/supply values that any account can move (deposit/withdraw), java-tron's on-chain Exchange (TRC10 Bancor-style AMM) prices trades solely from the current `firstTokenBalance`/`secondTokenBalance` reserves in `ExchangeCapsule`, recomputed fresh on every `ExchangeTransactionContract` with no TWAP or other time-weighting [1](#0-0) . Any unprivileged account can submit `ExchangeTransactionContract` transactions to shift these reserves and thus the exchange rate before a victim's transaction executes in the same block, then reverse the trade afterward to capture the spread - a classic sandwich enabled purely by the spot-price design flagged in the external report.

### Finding Description
`ExchangeTransactionActuator.execute` recomputes the trade output via `exchangeCapsule.transaction(tokenID, tokenQuant, ...)`, which delegates to `ExchangeProcessor`/`SafeExchangeProcessor`, both bancor formulas operating exclusively on the *current* `firstTokenBalance`/`secondTokenBalance` fields of the pool [2](#0-1) [3](#0-2) . There is no accumulator, observation window, or block-delay mechanism - the price is the raw spot ratio of reserves at the moment of the transaction, mirroring the report's "instantaneous" kerosene price derived from TVL/supply.

`ExchangeTransactionContract` is unauthenticated with respect to *who* can trade: any account with sufficient balance/asset can call it (only balance/asset sufficiency and `tokenExpected` slippage floor are validated, see `doValidate`) [4](#0-3) . Because Tron block producers batch and order transactions within a block, an attacker can:
1. Submit a large trade against the pool to move `firstTokenBalance`/`secondTokenBalance` favorably (front-run).
2. Let the victim's `ExchangeTransactionContract` execute at the manipulated rate (the victim's own `tokenExpected` floor is typically set loosely and does not protect against third-party manipulation).
3. Submit a reverse trade to restore the ratio and capture the price difference (back-run).

This is functionally identical to the report's scenario where Alice unilaterally alters a shared "TVL" value that determines everyone else's price in the same block, since here Alice unilaterally alters the shared reserve ratio that determines everyone else's execution price in the same block.

### Impact Explanation
An attacker can extract value from any counter-party trading against the Exchange contract by sandwiching their `ExchangeTransactionContract` calls, directly transferring value away from victims (theft of funds) using only permissionless transactions - no special privilege over the victim's account or the exchange pool is required (`ExchangeTransactionContract` requires no creator/owner relationship, unlike `ExchangeInjectActuator`/`ExchangeWithdrawActuator` which are creator-gated) [5](#0-4) .

### Likelihood Explanation
The `ExchangeBalanceLimit` dynamic parameter bounds pool size but does not prevent single-block manipulation of the ratio [6](#0-5) , and any account can submit multiple `ExchangeTransactionContract` transactions targeting the same exchange within one block, so likelihood is high whenever pool liquidity is thin relative to attacker capital, exactly as the external report describes for kerosene/TVL.

### Recommendation
Add a TWAP or minimum-elapsed-block/observation mechanism to `ExchangeCapsule.transaction`/`ExchangeProcessor` so the effective trade price is derived from a time-weighted average of reserves rather than the instantaneous balances, and/or enforce per-block trade limits per exchange to reduce single-block manipulation.

### Proof of Concept
1. Attacker submits `ExchangeTransactionContract` with a large `tokenQuant` selling token A into the pool, shifting `firstTokenBalance`/`secondTokenBalance` heavily in `ExchangeCapsule.setBalance` [7](#0-6) .
2. Victim's pending `ExchangeTransactionContract` (buying token A with token B) executes in the same block against the now-skewed reserves, receiving fewer of token A than the pre-attack spot rate implied, but still above their loosely-set `tokenExpected` floor.
3. Attacker submits a second `ExchangeTransactionContract` reversing the initial trade, restoring reserves and realizing a profit equal to the fee-free spread extracted from the victim.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
  }

  private long exchangeToSupply(long balance, long quant) {
    logger.debug("balance: " + balance);
    long newBalance = balance + quant;
    logger.debug("balance + quant: " + newBalance);

    double issuedSupply = -supply * (1.0
        - Maths.pow(1.0 + (double) quant / newBalance, 0.0005, this.useStrictMath));
    logger.debug("issuedSupply: " + issuedSupply);
    long out = (long) issuedSupply;
    supply += out;

    return out;
  }

  private long exchangeFromSupply(long balance, long supplyQuant) {
    supply -= supplyQuant;

    double exchangeBalance = balance
        * (Maths.pow(1.0 + (double) supplyQuant / supply, 2000.0, this.useStrictMath) - 1.0);
    logger.debug("exchangeBalance: " + exchangeBalance);

    return (long) exchangeBalance;
  }

  @Override
  public long exchange(long sellTokenBalance, long buyTokenBalance, long sellTokenQuant) {
    long relay = exchangeToSupply(sellTokenBalance, sellTokenQuant);
    return exchangeFromSupply(buyTokenBalance, relay);
  }
