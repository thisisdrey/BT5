### Title
Cross-Shard Write-Set/Edge Mismatch Causes Permanent `RemoteStateValue` Deadlock — (`aptos-move/aptos-vm/src/sharded_block_executor/cross_shard_client.rs`)

---

### Summary

`CrossShardCommitSender::send_remote_update_for_success` iterates over the **actual write set** of the committed `TransactionOutput` and only sends cross-shard messages for keys that appear in that write set. It never sends a null/tombstone message for keys that are declared in `dependent_edges` but absent from the actual write set. Because `AnalyzedTransaction::write_hints` are explicitly documented as potentially **overestimated**, and because gas exhaustion or conditional execution paths can cause a transaction to not write a predicted key, the dependent shard's `RemoteStateValue` for that key is permanently stuck in `Waiting`, blocking `get_value()` forever with no timeout or recovery path.

---

### Finding Description

**Step 1 — Partitioner declares edges from `write_hints`**

The `PartitionerV2` builds cross-shard dependency edges from `AnalyzedTransaction::write_hints`: [1](#0-0) 

The comment explicitly states these hints "can be accurate or **strictly overestimated**." The partitioner's `init` step registers every write hint as a write candidate: [2](#0-1) 

And `take_txn_with_dep` builds `dependent_edges` from those write candidates: [3](#0-2) 

**Step 2 — Dependent shard initializes all required keys as `Waiting`**

`CrossShardStateView::create_cross_shard_state_view` collects all `required_edges` keys and initializes each as `RemoteStateValue::waiting()`: [4](#0-3) 

**Step 3 — `get_value()` blocks indefinitely with no timeout**

`RemoteStateValue::get_value()` spins on a condvar with no timeout or cancellation: [5](#0-4) 

**Step 4 — The bug: `send_remote_update_for_success` is write-set-driven, not edge-driven**

The function iterates over the **actual write set** and only sends a message if the key happens to be in `edges`. Keys in `edges` that are absent from the write set receive no message: [6](#0-5) 

The correct logic would iterate over `edges` and send a `None`-valued `RemoteTxnWrite` for every key not present in the write set.

**Step 5 — `TransactionCommitHook` has no abort path**

The trait exposes only `on_transaction_committed`; there is no `on_execution_aborted` or equivalent: [7](#0-6) 

`on_transaction_committed` is called for **all** committed outputs, including gas-exhausted transactions whose write set contains only the gas deduction and not the predicted key K: [8](#0-7) 

---

### Impact Explanation

When a transaction T on shard A is committed with a write set that omits key K (declared in `dependent_edges` for shard B):

1. No `RemoteTxnWriteMsg` is ever sent to shard B for K.
2. Shard B's `CrossShardStateView::get_state_value(K)` calls `RemoteStateValue::get_value()`, which blocks forever on the condvar.
3. The executor thread on shard B is permanently wedged; no subsequent transaction in that sub-block can proceed.
4. The `StopMsg` is never received by the `CrossShardCommitReceiver` on shard B (because the executor thread never finishes), causing the entire sharded block execution to deadlock.

This is a **material chain availability failure**: the sharded block executor cannot complete the block, and the validator cannot make progress.

---

### Likelihood Explanation

The `write_hints` are explicitly documented as overestimates. Any of the following ordinary conditions triggers the mismatch:

- A transaction is gas-exhausted before reaching the write to K (user-controlled gas limit).
- A Move transaction takes a conditional branch that skips the write to K.
- The partitioner conservatively adds K to write hints for a transaction that only reads K under some conditions.

No privileged access is required. A user submitting a transaction with a low gas limit and a write hint for a cross-shard key is sufficient.

---

### Recommendation

Change `send_remote_update_for_success` to iterate over `edges` (not the write set), and for each key in `edges` that is absent from the write set, send a `RemoteTxnWrite` with `write_op = None`. This unblocks the dependent shard's `RemoteStateValue` with a tombstone/null value, preserving the invariant that every declared cross-shard key receives exactly one update.

```rust
fn send_remote_update_for_success(&self, txn_idx: TxnIndex, txn_output: &TransactionOutput) {
    let edges = self.dependent_edges.get(&txn_idx).unwrap();
    let write_set: HashMap<&StateKey, &WriteOp> =
        txn_output.write_set().expect_write_op_iter().collect();

    for (state_key, dependent_shard_ids) in edges.iter() {
        let write_op = write_set.get(state_key).cloned();
        for (dependent_shard_id, round_id) in dependent_shard_ids.iter() {
            let message = RemoteTxnWriteMsg(RemoteTxnWrite::new(
                state_key.clone(),
                write_op.cloned(),   // None if key absent from write set
            ));
            // ... send as before
        }
    }
}
```
