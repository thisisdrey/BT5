### Title
Unbounded, unmetered directory walk in `DisconnectGitAlternates` allows repo-owner-triggered DoS via object-pool loose-object flooding - ([File: internal/git/objectpool/disconnect.go])

### Summary
`DisconnectGitAlternates` is a normal, per-repository `MUTATOR` RPC that any client with write access to a repository can invoke [1](#0-0) . Its implementation walks the *entire* alternate object directory of the shared object pool with `filepath.Walk` and no cap, then performs a per-file hard-link operation for every entry found, all synchronously inside the single RPC call and while the repository's connectivity is compromised [2](#0-1) . This is the same bug class as the reported reward-plan `GetAllBalances` issue: an unmetered, fully attacker-influenceable iteration inside a "trusted" code path that any user can reach, where the cost scales linearly (or worse) with the number of items an attacker can cheaply create.

### Finding Description
`objectpool.Disconnect` resolves the alternates directory and calls `findObjectFiles`, which does an unbounded `filepath.Walk` over every loose object and pack file in the pool's `objects` directory [3](#0-2) . The returned list is then iterated again in `Disconnect`, performing `storage.MkdirAll` + `storage.Link` for every single object file before any consistency check happens [4](#0-3) .

Object pools are shared across all fork/pool members and grow as members push new commits/blobs that later get fetched into the pool via `FetchIntoObjectPool` [5](#0-4) . Because loose objects accumulate from ordinary, unprivileged push activity across all pool members over time (and are only compacted by periodic repacking, not synchronously), an attacker who is simply a member of a large, actively used pool (e.g., a heavily forked project) can inflate the number of on-disk loose objects far beyond what a repack would normally clean up in the short term, then invoke (or wait for a legitimate trigger of) `DisconnectGitAlternates` on their own repository.

The RPC handler itself performs no limiting, batching, streaming, or cost accounting relative to the number of files walked/linked — this mirrors the reported bug where `GetAllBalances` is called with no bound on the number of denoms an attacker can deposit. The code's own comment acknowledges the operational risk: during the temporary alternates removal, "probably all concurrent RPC calls to the repo will fail" [6](#0-5) , so a long-running, unbounded walk+link phase directly extends the window in which the repository is unusable.

### Impact Explanation
An attacker-inflated pool object count turns a routine `MUTATOR` RPC into an operation whose runtime is proportional to attacker-controlled input size, with no cap. This can:
- Cause the `DisconnectGitAlternates` RPC to run for a very long time, consuming CPU/IO and gRPC worker resources.
- Extend the window during which `objects/info/alternates` is renamed away and the repository is disconnected, during which the code explicitly notes concurrent RPCs to that repository will likely fail — a denial of service scoped to the repository (and potentially to Gitaly node resources if repeated across many repos/pools).
- Be triggered without any special privilege — only ordinary write access to a repository/pool member is required to inflate the pool and to call the RPC (or provoke another actor such as Rails to call it, e.g. via unlinking a fork).

### Likelihood Explanation
Likelihood is moderate-to-high: no privileged access is required, only sustained ordinary push activity into a shared, heavily-forked pool (a realistic scenario on large multi-fork projects) plus the ability to call (or trigger) `DisconnectGitAlternates` for a pool member. No authentication bypass or exotic access is needed — the RPC is a documented, first-class part of the object pool lifecycle.

### Recommendation
- Bound the work performed per `DisconnectGitAlternates` call: enforce a maximum object count/size, or refuse to disconnect (return an actionable error) when the alternate directory contains more entries than a configured limit.
- Perform the walk and link operations with progress-based cancellation/deadline checks tied to `ctx`, and consider chunking/streaming the operation so it can be interrupted without leaving the repository half-disconnected.
- Track/report the pool's loose object count as part of routine housekeeping so pathological growth can be repacked or capped by policy before it becomes exploitable.

### Proof of Concept
1. Attacker becomes (or already is) a member of a shared object pool (e.g., forks a project whose repositories share an `ObjectPoolService` pool).
2. Attacker repeatedly pushes many small, distinct blobs/commits to their fork over time; these are periodically fetched into the shared pool via `FetchIntoObjectPool`, accumulating a very large number of loose objects in the pool's `objects` directory.
3. Attacker (or an automated action taken on their behalf, e.g. unlinking their fork from the pool) triggers `DisconnectGitAlternates` for their repository.
4. `objectpool.Disconnect` → `findObjectFiles` walks the entire (attacker-inflated) pool object directory and then hard-links every file found, all before the connectivity check runs, causing the RPC — and the temporarily-alternates-less repository — to become unavailable for an extended, attacker-controlled duration.

  //
  // 1. Link all objects from the object pool into the member repository. This essenitally
  //    reduplicates previously-duplicated objects so that the repository will continue to function
  //    after being unlinked.
  // 2. Remove the alternates link to the object pool.
  // 3. Perform a consistency check to assert that the repository is indeed fully functional after
  //    unlinking it from its pool. If the consistency check fails the alternates link is restored
  //    an the RPC fails.
  //
  // If successful, the object pool member is disconnected from the object pool and does not depend
  // on it anymore.
  //
  // This RPC does not return an error in case the repository is not linked to any object pool.

      op: MUTATOR
    };

			return err
		}

		}
