Audit Report

## Title
Unbound MMR leaf position allows mis-bound `parent_number_and_hash` to be recorded for an unrelated block number - (File: `bridges/modules/beefy/src/lib.rs`)

## Summary
`Pallet::submit_commitment` in `bridges/modules/beefy/src/lib.rs` verifies a signed BEEFY `commitment` and independently verifies that a supplied `mmr_leaf`/`mmr_proof` pair is included in that commitment's MMR root, but never checks that the leaf's proven position (`mmr_proof.leaf_indices`) corresponds to `commitment.commitment.block_number`.<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/lib.rs" start="223-248" /> This lets a caller pair a genuine signed commitment for block `N` with a genuinely valid but unrelated older leaf `L_M` (`M < N-1`), causing the pallet to store `L_M`'s `parent_number_and_hash` under key `N` in `ImportedCommitments`.

## Finding Description
`submit_commitment` calls `utils::verify_commitment` to validate the commitment's signatures/validator set and extract the MMR root, then calls `utils::verify_beefy_mmr_leaf` to check that `mmr_leaf` is included in that root via `mmr_proof`.<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/utils.rs" start="107-126" /> `verify_beefy_mmr_leaf` only hashes `mmr_leaf`, calls `verify_mmr_leaves_proof(mmr_root, ..., mmr_proof)`, and returns an error only if the structural merkle-inclusion check fails — it never compares `mmr_proof.leaf_indices` (or `leaf_count`) against `commitment.commitment.block_number`.<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/utils.rs" start="128-157" /> The underlying `verify_leaves_proof` in `substrate/frame/merkle-mountain-range/src/mmr/mmr.rs` is purely structural: it maps `proof.leaf_indices` (attacker-supplied) to tree positions and checks the merkle path against `root`, with no external binding to any independently derived expected index.<cite repo="Lauraivanka/polkadot-sdk--034" path="substrate/frame/merkle-mountain-range/src/mmr/mmr.rs" start="36-64" /> Back in `submit_commitment`, the returned `mmr_leaf.parent_number_and_hash` is stored keyed by `commitment.commitment.block_number` with no cross-check between the two.<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/lib.rs" start="239-248" />

The test helper in `mock_chain.rs` confirms the intended convention that leaf index should equal `block_number - 1` ("genesis has no leaf => leaf index is header number minus 1"), but this convention is only enforced by construction in the mock/test builder, not checked in production code.<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/mock_chain.rs" start="228-234" /> Since MMR roots are cumulative, every historical leaf remains provable against any later root, so an attacker with a real signed commitment for block `N` and any earlier leaf+proof pair from the same public MMR can satisfy both `verify_commitment` and `verify_beefy_mmr_leaf` while supplying a mismatched leaf.

## Impact Explanation
`ImportedCommitments` is documented as the on-chain light-client state ("Given the header hash, other pallets are able to verify header-based proofs") that downstream pallets rely on for header/ancestry validation.<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/lib.rs" start="17-30" /> Poisoning `ImportedCommitments[N].parent_number_and_hash` with an unrelated block's parent data corrupts the light client's ancestry record for block `N`, a forged/mis-bound proof-acceptance condition affecting bridge state integrity used by dependent pallets.

## Likelihood Explanation
`submit_commitment` only requires `ensure_signed(origin)` — any account can call it — and the only inputs needed are a legitimately signed BEEFY commitment for a new block (public gossip) and an older leaf plus its inclusion proof against that commitment's MMR root (reconstructable from public chain data).<cite repo="Lauraivanka/polkadot-sdk--034" path="bridges/modules/beefy/src/lib.rs" start="200-221" /> No privileged actor, malicious validator, or compromised relayer is required.

## Recommendation
Derive the expected leaf index from `commitment.commitment.block_number` (following the `leaf_index = block_number - 1` convention already used in the test/mock builder) and assert that `mmr_proof.leaf_indices == [expected_index]` (and that `mmr_proof.leaf_count` is consistent with `block_number`) inside `verify_beefy_mmr_leaf` or `submit_commitment`, rejecting the call if the proven leaf's position does not correspond to the commitment's claimed block number.

## Proof of Concept
1. Observe a legitimate, signed BEEFY commitment for block `N` (correct signatures, MMR root `R_N`) — public data.
2. From the historical MMR, obtain leaf `L_M` for an earlier block `M < N-1` along with a valid MMR inclusion proof of `L_M` against `R_N` (valid since `R_N` accumulates all past leaves).
3. Call `submit_commitment(origin, commitment_for_N, validator_set, Box::new(L_M), proof_of_L_M_against_R_N)` from any signed account.
4. `verify_commitment` succeeds (only checks signatures/validator set/root extraction for block `N`); `verify_beefy_mmr_leaf` succeeds because `L_M` is genuinely included in `R_N`, per `substrate/frame/merkle-mountain-range/src/mmr/mmr.rs:36-64` and `bridges/modules/beefy/src/utils.rs:128-157`.
5. `ImportedCommitments::<T, I>::get(N)` now returns `parent_number_and_hash` belonging to block `M`, not `N-1`, confirmed by the storage write at `bridges/modules/beefy/src/lib.rs:242-248` with no cross-check present.
