Confirmed: a single `DefusePayload` can contain a `Vec<Intent>` (`DefuseIntents::intents`), each executed independently via `Intent::execute_intent` → `TokenDiff::execute_intent`, so a signer can pack 100 separate `TokenDiff` intents (each with a `-1` delta on the same NEP-245 token) into one signed `MultiPayload`.

### Title
Fee bypass on NEP-245/IMT `TokenDiff` legs via unit-size splitting - ([File: contracts/defuse/core/src/intents/token_diff.rs])

### Summary
`TokenDiff::token_fee` charges zero fee whenever the per-intent `amount` for a NEP-245 (or IMT) token leg is `1`, regardless of the protocol fee rate. By splitting a large NEP-245 negative delta into many separate `TokenDiff` intents each with `delta == -1` inside one signed `DefuseIntents` payload, an unprivileged signer can move arbitrary NEP-245 volume while the cumulative fee credited to `fee_collector` stays at `0`, versus the non-zero fee that a single `delta == -N` intent would incur.

### Finding Description
The binding that should hold is: `sum(fee credited to fee_collector for token T over the batch) == Pips::fee_ceil(protocol_fee, total_negative_delta_of_T_in_batch)`. It is broken because the fee decision is made per-intent, per-leg, using only that leg's local `amount`, not the aggregate delta across the payload.

In `contracts/defuse/core/src/intents/token_diff.rs`: [1](#0-0) 
computes `amount = delta.unsigned_abs()` and `fee = Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` per intent. `token_fee` is: [2](#0-1) 
which returns `Pips::ZERO` for `TokenIdType::Nep245`/`Imt` whenever `amount <= 1`, and only applies the real `fee` when `amount > 1`.

Each `Intent` (including `TokenDiff`) in a `DefuseIntents::intents` list is executed independently in sequence: [3](#0-2) 
and one `DefusePayload` carries exactly one `nonce`/signature covering the whole `Vec<Intent>`: [4](#0-3) 

Exploit: the attacker signs a single `MultiPayload` whose message is a `DefuseIntents` with 100 `TokenDiff` intents, each `{ diff: { <nep245_token>: -1 } }`, instead of one `TokenDiff` with `delta: -100`. Each of the 100 calls to `execute_intent` independently computes `amount = 1`, so `token_fee` returns `Pips::ZERO`, and `fee_ceil(1)` on zero fee is `0`. The attacker's balance is still debited the full 100 units via `internal_apply_deltas` (real value moves), but `fees_collected` accumulated across the whole batch is `0`, whereas a single `delta = -100` intent with `Pips::ONE_PERCENT` would yield `fee_ceil(100) = 1` (or proportionally more for larger batches/fees). This is not prevented by signature verification, nonce checks, or `assert_one_yocto` — none of those guards constrain how a signer partitions deltas across intents within one payload; the flaw is purely in the per-intent fee threshold.

### Impact Explanation
This is a protocol fee bypass: the `fee_collector` account is underpaid, and the tokens that "would have" gone to fees stay with the signer/counterparty instead, matching the explicit "protocol fees bypassed" Critical category. Any account holding NEP-245 (or IMT) tokens can repeat this on every trade by simply splitting deltas into unit-size legs within a single signed payload, at no extra cost beyond slightly larger payload/gas. This scales to any NEP-245 token id and any signer, and is systemic rather than one-off — it undermines fee collection entirely for MT/IMT-token legs whenever such tokens are used as fungible-like balances rather than strictly 1-unit NFTs.

### Likelihood Explanation
Requires only: `fees.fee` nonzero (e.g., `Pips::ONE_PERCENT`), the attacker holding an NEP-245 balance in Defuse, and the ability to construct and sign one `MultiPayload` with many `TokenDiff` intents (fully within an unprivileged signer's capability — no roles needed). The only cost is a larger payload / more gas for more intents, which is trivial compared to fees saved at scale. This is fully deterministic given the code above, not probabilistic.

### Recommendation
Compute the NEP-245/IMT fee-exemption threshold based on the aggregated negative delta of that token across the whole intents batch/payload (or remove the special-case "amount <= 1 pays zero fee" carve-out and always apply `fee_ceil` regardless of amount), rather than the local per-intent `amount`. Alternatively, if the `amount <= 1` exemption is meant strictly for true non-fungible NEP-245 tokens (supply of 1), gate it on token metadata/supply rather than on the transient per-intent delta size, so it cannot be gamed by splitting.

### Proof of Concept
`cargo test` (or `near-workspaces` sandbox test) in `contracts/defuse/core/src/intents/token_diff.rs` / `tests/src/tests/defuse/intents/token_diff.rs`:
1. Deploy Defuse with `fee = Pips::ONE_PERCENT`, `fee_collector = collector`.
2. Deposit an NEP-245 token to `signer` with balance `>= 100`.
3. Test A: sign one `MultiPayload` with a single `TokenDiff { diff: { nep245_token: -100 } }`; execute via `execute_intents`; read `fee_collector`'s balance for that token; expect `Pips::ONE_PERCENT.fee_ceil(100) = 1`.
4. Test B: sign one `MultiPayload` with `DefuseIntents { intents: (0..100).map(|_| Intent::TokenDiff(TokenDiff { diff: { nep245_token: -1 } })).collect() }`; execute via `execute_intents`; read `fee_collector`'s balance for that token; expect `0`.
5. Assert Test A's collected fee (`1`) != Test B's collected fee (`0`), while the signer's net token debit is identical (`100` units) in both, proving the fee-bypass binding violation.
