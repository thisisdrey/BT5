### Title
Missing Slippage/Expected-Amount Control in `ExchangeInjectActuator` Can Cause Unexpected Asset Loss for Exchange Creators - (File: `actuator/src/main/java/org/tron/core/actuator/ExchangeInjectActuator.java`)

### Summary
`ExchangeInjectContract`/`ExchangeInjectActuator` lets an exchange's creator add liquidity to a TRX/TRC10 token pair by specifying the quantity of only one side (`quant`), while the counter-token amount (`anotherTokenQuant`) is computed on-chain from the exchange pool's *current* ratio at execution time. Unlike `ExchangeTransactionContract`, which carries an `expected` field enforced in `ExchangeTransactionActuator.doValidate()` (`if (anotherTokenQuant < tokenExpected) throw ...`), `ExchangeInjectContract` has no minimum/maximum bound field at all, so the creator cannot protect themselves against the pool ratio moving between transaction construction and on-chain execution. This mirrors the reported `AuraVault.deposit`/`mint` bug class: an action whose output/counter-amount is computed from a mutable, market-like state with no caller-supplied slippage bound.

### Finding Description
`ExchangeInjectContract` only carries `owner_address`, `exchange_id`, `token_id`, `quant` (see `protocol/src/main/protos/core/contract/exchange_contract.proto`), with no `expected`/`min`/`max` bound field, in contrast to `ExchangeTransactionContract`, which explicitly adds an `expected` field for this purpose [1](#0-0) .

In `ExchangeInjectActuator.doValidate()` and `execute()`, the counter-token amount is derived purely from the *current* `firstTokenBalance`/`secondTokenBalance` ratio of the exchange pool at validation/execution time: [2](#0-1) 

There is no user-supplied bound to reject the transaction if that computed `anotherTokenQuant` deviates from what the creator expected when they built/signed the transaction. Compare this to `ExchangeWithdrawActuator`, which at least re-derives and sanity-checks precision against the pool at validation time (though it also lacks a true slippage bound), and to `ExchangeTransactionActuator`, which enforces `anotherTokenQuant >= tokenExpected`: [3](#0-2) 

Because any account (not just the injector) can submit an `ExchangeTransactionContract` against the same `exchange_id` in an earlier-included transaction/block, the pool ratio the injector observed off-chain when they built their `ExchangeInjectContract` can be different by the time their transaction executes. The `ExchangeInjectActuator` will then silently compute and pull a different (larger or smaller) counter-token amount from the creator's account than they intended, without any means for the transaction to revert on unfavorable pricing.

### Impact Explanation
An exchange creator submitting `ExchangeInjectContract` has no way to bound the counter-asset amount they are willing to inject. If the pool ratio shifts (due to a preceding/concurrent `ExchangeTransactionContract`, `ExchangeWithdrawContract`, or another `ExchangeInjectContract` from any account, or simple mempool/block-ordering timing) before their injection executes, they can be forced to lock significantly more of the counter-token/TRX than intended for the same `quant` of the first token, or receive a much less favorable liquidity position than expected. This is a direct, unbacked financial loss to the transaction submitter with no on-chain safeguard, matching the "Medium" severity slippage-control class described in the reference report. It is reachable by any account that created the given exchange (a normal, permissionless `ExchangeCreateContract` action, not a privileged/SR role), via a single signed `ExchangeInjectContract` transaction routed through the standard actuator validate/execute path.

### Likelihood Explanation
Likelihood is moderate: it requires that the exchange pool ratio move between the time the injector observes the price and signs their transaction and the time it is included in a block — realistic in any active exchange pair with concurrent trading, or even just due to normal network propagation delay, and does not require any malicious actor, privileged role, or crafted attack; ordinary trading activity on the pair is sufficient to trigger unexpected outcomes.

### Recommendation
Add an `expected`-style bound to `ExchangeInjectContract` (e.g., `min_another_token_quant` or `max_another_token_quant` depending on the injector's role as buyer/provider of the counter token), and enforce it in `ExchangeInjectActuator.doValidate()`/`execute()` analogous to the check already present in `ExchangeTransactionActuator`: [3](#0-2) 
so the transaction reverts if the computed `anotherTokenQuant` falls outside the creator's tolerance, rather than silently executing at an unexpected ratio.

### Proof of Concept
1. Exchange creator Alice owns a TRX/TOKEN exchange pool with balances `firstTokenBalance = 1_000_000`, `secondTokenBalance = 1_000_000`.
2. Alice builds an `ExchangeInjectContract` with `token_id = TOKEN`, `quant = 100_000`, expecting to inject roughly `100_000` TRX (1:1 ratio) based on the pool state she observed.
3. Before Alice's transaction is included, another account submits a large `ExchangeTransactionContract` that shifts the pool ratio to `firstTokenBalance = 1_000_000`, `secondTokenBalance = 5_000_000`.
4. Alice's `ExchangeInjectActuator.execute()` runs `anotherTokenQuant = secondTokenBalance * tokenQuant / firstTokenBalance` [4](#0-3) , now computing `500_000` TRX instead of the expected `~100_000` TRX, and deducts that full amount from Alice's account with no way for the transaction to revert on this deviation.
