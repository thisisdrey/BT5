### Title
Dust-transfer griefing fills victim's `depositTokensOfAccount` list, DoS-ing deposits of new collateral types - ([File: contracts/Pool.sol](contracts/Pool.sol))

### Summary
The bug-class analog to "single-use `init` collateral account that can't be reused and can be griefed" is Metronome's per-account token registry. Every `DepositToken` mint/transfer pushes the token into a per-account list in `Pool`, capped at `MAX_TOKENS_PER_USER = 30` combined deposit+debt tokens. Once the cap is hit, `Pool.addToDepositTokensOfAccount` reverts with `UserReachedMaxTokens`, which makes `DepositToken._mint` and `DepositToken._transfer` revert for any *new* token. An unprivileged attacker can force this state on any victim by transferring dust amounts of deposit tokens they control.

### Finding Description
`Pool.addToDepositTokensOfAccount` is gated by `onlyIfAdditionWillNotReachMaxTokens`, which reverts once `debtTokensOfAccount.length + depositTokensOfAccount.length >= 30` [1](#0-0) . It is invoked from two permissionless-reachable paths:

- `DepositToken._mint` — triggered by `deposit(amount_, onBehalfOf_)`, where `onBehalfOf_` is attacker-chosen [2](#0-1) 
- `DepositToken._transfer` — triggered by `transfer`/`transferFrom`/`seize` whenever the recipient's prior balance was zero [3](#0-2) 

Attack path: the attacker calls `deposit(dust, attacker)` once per deposit token to acquire msdTOKEN, then calls `transfer(victim, 1)` on each deposit token. Each call adds that token to `victim`'s `depositTokensOfAccount`. After enough tokens (fewer than 30 if the victim already holds positions/debt tokens), the victim's combined list hits the cap. From then on:

- `deposit(..., onBehalfOf_=victim)` on any deposit token not already in the victim's list reverts inside `_mint` → `addToDepositTokensOfAccount`, permanently blocking new-collateral deposits to the victim while the dust persists.
- `transfer`/`transferFrom` of any not-yet-held deposit token to the victim reverts.
- `Pool.liquidate` targeting collateral not already in the victim's list still works (seize goes to the liquidator), but a liquidator whose own list is filled cannot receive new deposit tokens either.

No modifier stops this: `deposit`/`transfer` are public, `SynthContext._msgSender` only resolves the sender, `whenNotPaused`/`nonReentrant` don't apply to the griefing path, and the cap check is the bug itself — analogous to the Solana `init` failing on an already-derived account, here a bounded registry that an attacker can saturate on someone else's behalf.

### Impact Explanation
Liveness break: the victim is unable to add any new collateral type to their position. If a victim's position is deteriorating and the only viable collateral to restore health is a token not in their list, deposits revert and the position becomes liquidatable/bad debt. Deposits routed to the victim by third parties (zaps, smart-farming flows, `onBehalfOf_` deposits) also revert. This is a temporary freezing of deposit functionality and forced-liquidation risk — the victim must first spend gas transferring dust balances out (or wait for attacker dust to be removed via `removeFromDepositTokensOfAccount` on zero balance) before depositing, and the attacker can re-fill slots.

### Likelihood Explanation
Cost to the attacker is minimal: dust deposits (bounded by each token's smallest unit and `SurpassMaxDepositSupply`/deposit fee) plus ~30 `transfer` calls. No privileged role, oracle manipulation, or timing assumption is required — only that the victim has fewer than 30 list entries to begin with. Recovery requires the victim to actively flush dust tokens, and the attacker can front-run or re-dust, making the DoS repeatable.

### Recommendation
Make `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` failure non-fatal for *receipts*: on the cap, either skip adding the token to the list (deposit tokens' USD contribution is enumerable via `depositTokenOf`/balance scans anyway, or accept the list as best-effort) or allow the recipient to pre-approve/opt-in via an allowlist. Alternatively, only push to the list on user-initiated `deposit`/`mint` (where the caller can be required to be `account_` or the SmartFarmingManager), not on permissionless `transfer`/`seize`, and let governance-curated collateral still count toward `debtPositionOf` through a separate enumeration path.

### Proof of Concept
Hardhat (fork or local deployment of `Pool` + N registered `DepositToken`s):

```ts
// Assume pool has >= K deposit tokens registered and victim has 0 positions.
const victim = bob.address;

for (const dt of depositTokens /* up to 30 */) {
  // attacker acquires dust
  await underlying(dt).approve(dt.address, 1);
  await dt.deposit(1, attacker.address);           // mints msdTOKEN to attacker
  await dt.transfer(victim, 1);                    // victim list += 1
}

// victim's combined list is now at MAX_TOKENS_PER_USER
await expect(
  newDepositToken.deposit(parseEther('10'), victim)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');

// also: plain transfers of any un-held token to victim revert
await expect(
  yetAnotherDepositToken.connect(attacker).transfer(victim, 1)
).to.be.revertedWithCustomError(pool, 'UserReachedMaxTokens');
```

The second `expect` fails with `UserReachedMaxTokens`, demonstrating deposits and transfers of new collateral types to the victim are bricked until the victim transfers the dust out.
