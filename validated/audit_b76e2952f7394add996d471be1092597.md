### Title
Multi-signature transactions are validated against the *live* account permission at broadcast time rather than the permission version signers actually agreed to, allowing a threshold holder to front-run and hijack a pending co-signed transaction - (`chainbase/src/main/java/org/tron/core/capsule/TransactionCapsule.java`)

### Summary
The Rigor `inviteSC` bug is caused by a state (the task's subcontractor) that was multi-party-confirmed (`SCConfirmed`) being unilaterally reassigned without re-checking the original consenting parties' signatures, so a pending, already-authorized action (`setComplete`) executes against the new, unagreed state and redirects funds. The analogous root cause exists in java-tron's TRON multi-signature ("Permission") system: a transaction's signatures are validated against whichever `Permission` definition currently lives in the `AccountStore` for the referenced `permission_id`, not against the permission version that was actually in force when the signers produced their signatures. Because `AccountPermissionUpdateContract` lets an account (or any actor who already meets the *owner* permission's threshold) redefine an `active` permission's keys/threshold at any time, a malicious co-signer can front-run a not-yet-broadcast, partially/fully signed multi-sig transaction by first submitting a permission update that changes the active permission's key set/threshold to their advantage, then broadcasting (or letting the network validate) the original transaction — which is checked against the *new* permission rather than the one the other signers agreed to.

### Finding Description
Signature/threshold verification for any transaction is performed by `TransactionCapsule.validateSignature()` / `validatePubSignature()`, which is invoked at broadcast/execution time (not at signing time): [1](#0-0) 

This method fetches the `Permission` object fresh from the `AccountStore` via `account.getPermissionById(permissionId)` at the moment of validation, and computes `checkWeight()` against that live object: [2](#0-1) 

`TransactionUtil.getTransactionSignWeight()`, used by wallet/API sign-collection flows, does the exact same live lookup: [3](#0-2) 

Nothing in the transaction (the `raw_data` only carries a `permission_id` integer, not a hash/version of the `Permission` that was active when it was signed) binds the collected signatures to a specific permission snapshot. Meanwhile, `AccountPermissionUpdateActuator.execute()` freely overwrites the account's owner/witness/active permissions as soon as it validates, with no check for any transaction currently "in flight" that depends on the old permission definition: [4](#0-3) 

`validate()` only requires that the *owner* permission's threshold be met for the update itself (via the normal `validateSignature` path applied to the `AccountPermissionUpdateContract` transaction), which can be a different, smaller set of keys than the *active* permission that the still-pending multi-sig transaction relies on: [5](#0-4) 

This mirrors the Rigor root cause precisely: `inviteSC()`/`_inviteSC()` changed the task's `subcontractor` field with no re-verification of the multi-party signatures that had already confirmed the task, and a subsequently-broadcast `setComplete()` paid out against the new, unconsented state. In java-tron, `AccountPermissionUpdateContract` changes the account's `Permission` definition for a `permission_id` with no re-verification tying the change to signatures already collected for pending transactions that reference the *same* `permission_id`; those pending transactions are re-evaluated at broadcast time against whatever permission is current, exactly like `setComplete()` re-evaluating `tasks[_taskID].subcontractor` at call time.

### Impact Explanation
An account/wallet secured by TRON's native multi-signature ("Permission") mechanism (e.g., a shared treasury account with `active` permission requiring N-of-M co-signers for `TransferContract`/`TransferAssetContract`) is not as safe as intended: any co-signer (or anyone who alone meets the *owner* permission threshold, which may be weaker or different from the specific `active` permission threshold protecting a given operation) can:
1. Wait for other signers to produce and hand over their signatures on a legitimate, agreed transaction (e.g., a payout) that has not yet been broadcast.
2. Submit an `AccountPermissionUpdateContract` that redefines the `active` permission for that `permission_id` (e.g., lowering the threshold, adding their own key with high weight, or removing other legitimate signers) — while only satisfying the *owner* permission's separate consent requirement.
3. Broadcast the already-collected transaction; `checkWeight`/`validateSignature` now evaluate the (still partially valid, or newly satisfied) signature set against the attacker-controlled permission definition and execute the transfer, potentially to a destination or under conditions the other co-signers never agreed to in that final form, or the attacker can otherwise manipulate which of the previously-collected signatures counts toward the new threshold.

This is a concrete unauthorized-fund-movement / theft vector against any multi-signature-protected account, directly analogous to the subcontractor being swapped out from under an already-agreed, in-flight payment.

### Likelihood Explanation
Exploitation requires only broadcasting two ordinary, unprivileged transactions from an account the attacker already partially controls (holds sufficient weight in the *owner* permission, or a key already present in the account's permission set) — no special node access, no consensus-layer compromise. Multi-sig treasury/custody setups that rely on the `active` permission threshold being independent from full owner control are the primary targets; this is a realistic pattern for exchanges, DAOs, or shared custody wallets that use java-tron's native permission system.

### Recommendation
Bind the signature verification of a transaction to the specific `Permission` version that was active when the transaction references it, e.g. by hashing/versioning `Permission` and requiring `checkWeight`/`validateSignature` to also verify that version matches the one the signers actually signed under, similar to how `changeOrder()` in the Rigor contract bakes the new state directly into the signed hash. Alternatively, require any `AccountPermissionUpdateContract` that touches a permission ID to be signed under the *same* (updated) permission's own current threshold rather than only the owner permission when the two diverge, and consider invalidating/rejecting outstanding transactions signed under a permission version once that permission is updated, rather than silently reinterpreting them against the newest definition.

### Proof of Concept
1. Account `A` has `owner` permission requiring 1-of-2 (`k1`, `k2`) and `active` permission (id=2) requiring 2-of-3 (`k1`, `k2`, `k3`) for `TransferContract`.
2. A legitimate payout of `A`'s funds is agreed; `k1` and `k2` sign a `TransferContract` under `permission_id=2` and hand their signatures to a coordinator, but it is not yet broadcast.
3. Holder of `k1` alone submits an `AccountPermissionUpdateContract` (satisfying the 1-of-2 owner threshold) that redefines `active` permission id=2 to be 1-of-1 with only `k1`.
4. `AccountPermissionUpdateActuator.execute()` overwrites the permission with no check on outstanding transactions referencing id=2: [6](#0-5) 
5. `k1` now broadcasts the original (or a modified) transfer transaction; `validateSignature()`/`checkWeight()` re-fetch the *current* permission (now 1-of-1 controlled solely by `k1`) and approve it, even though `k2`'s consent was originally required and was only given for the 2-of-3 scheme, not for `k1` acting unilaterally. [7](#0-6)

  public static long checkWeight(Permission permission, List<ByteString> sigs, byte[] hash,
      List<ByteString> approveList)
      throws SignatureException, PermissionException, SignatureFormatException {
    long currentWeight = 0;
    if (sigs.size() > permission.getKeysCount()) {
      throw new PermissionException(
          "Signature count is " + (sigs.size()) + " more than key counts of permission : "
              + permission.getKeysCount());
    }
    HashMap addMap = new HashMap();
    for (ByteString sig : sigs) {
      if (sig.size() < 65) {
        throw new SignatureFormatException(
            "Signature size is " + sig.size());
      }
      String base64 = TransactionCapsule.getBase64FromByteString(sig);
      byte[] address = SignUtils
          .signatureToAddress(hash, base64, CommonParameter.getInstance().isECKeyCryptoEngine());
      long weight = getWeight(permission, address);
      if (weight == 0) {
        throw new PermissionException(
            ByteArray.toHexString(hash) + " is signed by " + encode58Check(address)
                + " but it is not contained of permission.");
      }
      if (ForkController.instance().pass(Parameter.ForkBlockVersionEnum.VERSION_4_7_1)) {
        base64 = encode58Check(address);
      }
      if (addMap.containsKey(base64)) {
        throw new PermissionException(encode58Check(address) + " has signed twice!");
      }
      addMap.put(base64, weight);
      if (approveList != null) {
        approveList.add(ByteString.copyFrom(address)); //out put approve list.
      }
      currentWeight += weight;
    }
    return currentWeight;
  }

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }

  @Override
  public boolean validate() throws ContractValidateException {

    if (chainBaseManager == null) {
      throw new ContractValidateException(ActuatorConstant.STORE_NOT_EXIST);
    }

    if (this.any == null) {
      throw new ContractValidateException(ActuatorConstant.CONTRACT_NOT_EXIST);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    DynamicPropertiesStore dynamicStore = chainBaseManager.getDynamicPropertiesStore();

    if (dynamicStore.getAllowMultiSign() != 1) {
      throw new ContractValidateException("multi sign is not allowed, "
          + "need to be opened by the committee");
    }
    if (!this.any.is(AccountPermissionUpdateContract.class)) {
      throw new ContractValidateException(
          "contract type error,expected type [AccountPermissionUpdateContract],real type["
              + any.getClass() + "]");
    }
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);
    } catch (InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      throw new ContractValidateException(e.getMessage());
    }
    byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
    if (!DecodeUtil.addressValid(ownerAddress)) {
      throw new ContractValidateException("invalidate ownerAddress");
    }
    AccountCapsule accountCapsule = accountStore.get(ownerAddress);
    if (accountCapsule == null) {
      throw new ContractValidateException("ownerAddress account does not exist");
    }

    if (!accountPermissionUpdateContract.hasOwner()) {
      throw new ContractValidateException("owner permission is missed");
    }

    if (accountCapsule.getIsWitness()) {
      if (!accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("witness permission is missed");
      }
    } else {
      if (accountPermissionUpdateContract.hasWitness()) {
        throw new ContractValidateException("account isn't witness can't set witness permission");
      }
    }

    if (accountPermissionUpdateContract.getActivesCount() == 0) {
      throw new ContractValidateException("active permission is missed");
    }
    if (accountPermissionUpdateContract.getActivesCount() > 8) {
      throw new ContractValidateException("active permission is too many");
    }

    Permission owner = accountPermissionUpdateContract.getOwner();
    Permission witness = accountPermissionUpdateContract.getWitness();
    List<Permission> actives = accountPermissionUpdateContract.getActivesList();

    if (owner.getType() != PermissionType.Owner) {
      throw new ContractValidateException("owner permission type is error");
    }
    checkPermission(owner);
    if (accountCapsule.getIsWitness()) {
      if (witness.getType() != PermissionType.Witness) {
        throw new ContractValidateException("witness permission type is error");
      }
      checkPermission(witness);
    }
    for (Permission permission : actives) {
      if (permission.getType() != PermissionType.Active) {
        throw new ContractValidateException("active permission type is error");
      }
      checkPermission(permission);
    }
    return true;
