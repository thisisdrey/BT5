### Title
Active-permission holders can silently overwrite an account's Owner permission via `AccountPermissionUpdateContract`, enabling privilege escalation from a scoped signer to full account takeover - ([File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java])

### Summary
`AccountPermissionUpdateActuator` allows any transaction signed under a non-owner (`Active`) permission — as long as that permission's 32-byte `operations` bitmap has the `AccountPermissionUpdateContract` bit set — to completely replace the account's `Owner` permission, `Witness` permission, and all `Active` permissions in a single call. There is no check that the signer's *own* scope (i.e., being merely an "Active" key rather than the account's Owner-authority holder) is preserved or that the new permissions being installed stay within the signer's granted scope. This mirrors the Keystone flaw where a limited-scope credential (trust/oauth/application-credential) could mint a new, differently-scoped (admin) credential that the caller was never actually authorized to hold.

### Finding Description
Authorization for `AccountPermissionUpdateContract` is performed generically, far from the actuator, in `TransactionCapsule.validateSignature`/`checkPermission`, which only verifies that the permission used to sign has the corresponding contract-type bit set in its `operations` bitmap: [1](#0-0) 

That is the *only* authorization gate. Once that single bit-check passes, `AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's `Owner`, `Witness`, and `Active` permissions with whatever the transaction requests, with no relationship enforced between the *scope* of the permission that signed the transaction and the *scope* of the permissions being newly installed: [2](#0-1) 

`validate()`/`checkPermission()` only sanity-checks the *shape* of the new permissions (key count, threshold, distinct addresses, valid contract-type bits, name length) — never that the caller's current scope justifies replacing the Owner permission: [3](#0-2) 

As a result, if an account owner ever grants an `Active` permission that includes the `AccountPermissionUpdateContract` bit (a routine-looking capability bit among dozens of others in the 256-bit operations bitmap, e.g. for automation/co-signer convenience), the holder of that key — who was only meant to have a bounded, "Active"-level scope — silently gains the ability to rewrite the account's `Owner` permission outright, i.e., to become the sole controller of the account or to lock the real owner out permanently. There is no distinguishing rule requiring that only the Owner-threshold signature (or a permission carrying elevated semantics) can change the Owner permission; a single `Active` key with that one bit set suffices.

### Impact Explanation
This allows an account operation exceeding the granted scope: a key intended for limited/automated `Active`-level actions can unilaterally seize full irrevocable control of the account (rewrite `Owner`) or permanently freeze the account by installing an unsatisfiable Owner permission (e.g., unreachable threshold). This satisfies "concrete unauthorized account operation" / "permanent freezing of funds" impact criteria, matching the CWE-269/privilege-escalation bug class of the Keystone advisory, where a limited-scope actor could mint a higher-privileged credential it was not authorized to create.

### Likelihood Explanation
Exploitation requires only that an account owner has previously configured an `Active` permission whose 32-byte operations bitmap includes the `AccountPermissionUpdateContract` bit (contract-type id 46) — a configuration that is easy to create inadvertently (e.g., granting an automation/co-signer key broad "management" operations) since nothing in `checkPermission`/`validate` warns that this bit is materially different from any other contract-type bit. Once granted, the holder of that single Active key can broadcast one `AccountPermissionUpdateContract` transaction with `Permission_id` set to that Active permission's id to fully overwrite Owner/Witness/Active permissions — no additional signatures or owner-threshold approval are required by the actuator.

### Recommendation
Enforce that any `AccountPermissionUpdateContract` which modifies the `Owner` permission (or removes/degrades existing Owner keys) must be authorized by the current `Owner` permission itself (permission_id == 0), not merely by an `Active` permission carrying the generic operations bit. Alternatively, treat the `AccountPermissionUpdateContract` bit specially in `checkPermission`/`validate` (e.g., disallow it from being grantable on `Active` permissions, or require the resulting Owner permission's key set to be a superset of/approved by the pre-existing Owner keys) so a bounded `Active` key can never unilaterally replace the account's Owner authority.

### Proof of Concept
1. Account `A` (owned by key `K_owner`) creates an `Active` permission (`id=2`) for key `K_agent`, intending it only for e.g. `TransferContract`, but the 32-byte `operations` bitmap also has bit 46 (`AccountPermissionUpdateContract`) set — see how bits map to contract types in `AccountPermissionUpdateActuator.checkPermission` [4](#0-3) .
2. `K_agent` crafts an `AccountPermissionUpdateContract` for account `A`, setting `Permission_id = 2`, and setting the `owner` field to a brand-new `Owner` permission containing only `K_agent`'s own address with weight ≥ threshold.
3. `K_agent` signs the transaction with only its own key and broadcasts it. `TransactionCapsule.validateSignature`/`checkPermission` passes because the used Active permission (`id=2`) has the `AccountPermissionUpdateContract` bit set and weight ≥ threshold [1](#0-0) .
4. `AccountPermissionUpdateActuator.execute()` overwrites account `A`'s Owner permission with `K_agent`'s new Owner permission, unconditionally [5](#0-4) .
5. `K_agent` now solely controls account `A`'s Owner authority; the original owner `K_owner` has been permanently locked out.

  @Override
  public boolean execute(Object object) throws ContractExeException {
    TransactionResultCapsule result = (TransactionResultCapsule) object;
    if (Objects.isNull(result)) {
      throw new RuntimeException(ActuatorConstant.TX_RESULT_NULL);
    }

    AccountStore accountStore = chainBaseManager.getAccountStore();
    long fee = calcFee();
    final AccountPermissionUpdateContract accountPermissionUpdateContract;
    try {
      accountPermissionUpdateContract = any.unpack(AccountPermissionUpdateContract.class);

      byte[] ownerAddress = accountPermissionUpdateContract.getOwnerAddress().toByteArray();
      AccountCapsule account = accountStore.get(ownerAddress);
      account.updatePermissions(accountPermissionUpdateContract.getOwner(),
          accountPermissionUpdateContract.getWitness(),
          accountPermissionUpdateContract.getActivesList());
      accountStore.put(ownerAddress, account);

      adjustBalance(accountStore, ownerAddress, -fee);
      if (chainBaseManager.getDynamicPropertiesStore().supportBlackHoleOptimization()) {
        chainBaseManager.getDynamicPropertiesStore().burnTrx(fee);
      } else {
        adjustBalance(accountStore, accountStore.getBlackhole(), fee);
      }

      result.setStatus(fee, code.SUCESS);
    } catch (BalanceInsufficientException | InvalidProtocolBufferException e) {
      logger.debug(e.getMessage(), e);
      result.setStatus(fee, code.FAILED);
      throw new ContractExeException(e.getMessage());
    }

    return true;
  }
