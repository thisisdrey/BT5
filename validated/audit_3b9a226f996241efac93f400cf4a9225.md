### Title
Unchecked `BigInteger.longValue()` narrowing conversion in `MarketUtils.multiplyAndDivide` can silently wrap the matched-order amount, corrupting order-book accounting - (File: `chainbase/src/main/java/org/tron/core/capsule/utils/MarketUtils.java`)

### Summary
`MarketUtils.multiplyAndDivide` computes `a*b/c`. When the intermediate `a*b` overflows a `long`, it falls back to `BigInteger` arithmetic, but converts the final quotient back to `long` with the non-exact `BigInteger.longValue()` instead of `longValueExact()`. If the *quotient itself* (not just the intermediate product) still exceeds `Long.MAX_VALUE`, this silently truncates/wraps to an arbitrary (and possibly negative) `long`, exactly the class of bug described in the report (unchecked u64→i64-style narrowing where the source value can exceed the destination type's range).

### Finding Description
```java
public static long multiplyAndDivide(long a, long b, long c, boolean disableMath) {
  try {
    long tmp = multiplyExact(a, b, disableMath);
    return floorDiv(tmp, c, disableMath);
  } catch (ArithmeticException ex) {
    // do nothing here, because we will use BigInteger to compute again
  }
  BigInteger aBig = BigInteger.valueOf(a);
  BigInteger bBig = BigInteger.valueOf(b);
  BigInteger cBig = BigInteger.valueOf(c);
  return aBig.multiply(bBig).divide(cBig).longValue();
}
``` [1](#0-0) 

The `multiplyExact` path is hardened (throws on `long` multiplication overflow), but the recovery path is not: `.longValue()` (unlike `.longValueExact()` used elsewhere in the same class, e.g. `exchangeFromSupply`/`ExchangeWithdrawActuator`) does not check that the `BigInteger` result actually fits in a `long` — it just returns the low 64 bits. Elsewhere in the codebase the project consistently guards against exactly this pattern with `longValueExact()` [2](#0-1) , and even has dedicated hardening tests for overflow scenarios [3](#0-2) , but `multiplyAndDivide`'s fallback path was missed.

This function is reachable from an unprivileged, single signed transaction via `MarketSellAssetActuator.matchSingleOrder`, which is invoked during on-chain order matching for the `MarketSellAssetContract` actuator:
```java
long takerBuyTokenQuantityRemain = MarketUtils
    .multiplyAndDivide(takerSellRemainQuantity, makerSellQuantity, makerBuyQuantity,
        this.disableJavaLangMath());
``` [4](#0-3) 

The three inputs (`sellTokenQuantity`, `buyTokenQuantity` of both orders) are attacker-controlled fields of `MarketSellAssetContract`, only bounded by `dynamicStore.getMarketQuantityLimit()` [5](#0-4) , a configurable dynamic property that can be set to very large values (up to `Long.MAX_VALUE` range). By crafting a maker order with a very large `sellQuantity` and a tiny `buyQuantity` (e.g. `makerSellQuantity ≈ 9e18`, `makerBuyQuantity = 1`) and a matching taker order with a similarly large sell-remain quantity, `a*b` becomes astronomically large (>10^37), and even after dividing by `c`, the quotient can still exceed `Long.MAX_VALUE`. `.longValue()` then returns an arbitrary/negative wrapped result instead of throwing.

If the wrapped result is negative, downstream logic in `matchSingleOrder` misbehaves: the `== 0` short-circuit check does not trigger, the amount is used as `takerBuyTokenQuantityReceive` (a negative token/TRX amount credited via `addTrxOrToken`/`addExact`), and it is also passed to `subtractExact(makerOrderCapsule.getSellTokenQuantityRemain(), takerBuyTokenQuantityRemain)` [6](#0-5) , which with a negative subtrahend *increases* the maker's remaining sell quantity instead of decreasing it — inflating the order book's remaining balance beyond what was actually escrowed, i.e. unbacked asset/TRX accounting in the market order book.

### Impact Explanation
This can corrupt on-chain order-book state (`MarketOrderCapsule.sellTokenQuantityRemain`) to values larger than what is actually backed by the account's escrowed balance/tokens, and can also apply negative-amount credits/debits through `addExact`/`subtractExact` in unintended directions. Depending on the exact wrapped value obtained (which is attacker-influenceable by choosing the operand magnitudes), this can be leveraged to fabricate unbacked TRX/token balance in subsequent order matches or crash matching logic via unexpected `ArithmeticException` from the later `addExact`/`subtractExact` hardened calls, causing failed transaction execution (state hasn't been proven end-to-end profitable without a live PoC, so the precise sign/magnitude of the wrapped value for a given order-book state should be validated experimentally).

### Likelihood Explanation
Reachable from a single signed `MarketSellAssetContract` transaction by any account with sufficient balance to fund the crafted maker/taker orders (bounded only by `getMarketQuantityLimit()`, an admin-configurable but potentially large limit). No special privileges are required beyond normal token/TRX ownership and market-transaction support being enabled on the chain (`dynamicStore.supportAllowMarketTransaction()`).

### Recommendation
Replace `.longValue()` with `.longValueExact()` in `MarketUtils.multiplyAndDivide`'s `BigInteger` fallback path, converting the silent overflow into an explicit `ArithmeticException` that is already caught and converted to `ContractValidateException`/`ContractExeException` by the surrounding actuator code paths, consistent with the exact-conversion pattern used throughout the rest of the codebase.

### Proof of Concept
Not independently executed in this analysis; a concrete reproduction would construct a `MarketSellAssetActuator` test similar to `ParticipateAssetIssueActuatorTest.sameTokenNameOpenAddOverflowTest` [7](#0-6) , creating a maker order with `sellQuantity` near `Long.MAX_VALUE` and `buyQuantity = 1`, and a taker order whose `sellTokenQuantityRemain` is likewise large, then invoking `matchSingleOrder` and observing the sign/magnitude of `takerBuyTokenQuantityRemain` returned by `multiplyAndDivide`, and the resulting inconsistency in `makerOrderCapsule.getSellTokenQuantityRemain()`.
