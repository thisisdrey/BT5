### Title
Griefing via dust `DepositToken` transfers fills `MAX_TOKENS_PER_USER` and DoSes victim's deposits, borrows, and liquidations - ([File: contracts/Pool.sol])

### Summary
`Pool` tracks every deposit token and debt token an account has ever interacted with in the `MappedEnumerableSet` lists `depositTokensOfAccount` / `debtTokensOfAccount`. Both additions go through `onlyIfAdditionWillNotReachMaxTokens`, which reverts with `UserReachedMaxTokens` once the combined list length reaches `MAX_TOKENS_PER_USER = 30` [1](#0-0) . `DepositToken._transfer`/`deposit` add the *recipient* to the list whenever their balance goes 0 → positive, and `DebtToken.issue`/`mint` add the borrower. An unprivileged attacker can therefore buy dust amounts of every deposit token registered in a pool and `transfer` 1 wei of each to a victim, permanently inflating the victim's list. Once the list hits 30, the victim cannot receive a new deposit-token type, cannot `deposit` a collateral they don't already hold, and cannot `issue`/`mint` a new debt token — every path reverts inside `addToDepositTokensOfAccount`/`addToDebtTokensOfAccount` [2](#0-1) .

### Finding Description
Analog of the crafted-input crash class: instead of a crafted HTML page segfaulting a process, a crafted set of ERC-20 dust transfers crashes (reverts) every subsequent state-changing call for the victim.

- `Pool.addToDepositTokensOfAccount` is callable only by a registered deposit token, but the *account* argument is the transfer recipient — fully attacker-controlled via `DepositToken.transfer(victim, 1)` [3](#0-2) .
- The limit check `debtTokensOfAccount.length(account_) + depositTokensOfAccount.length(account_) >= MAX_TOKENS_PER_USER` is global across both lists, so 30 dust transfers of distinct deposit tokens block not only new deposits but also `DebtToken.issue`/`mint` for a *new* synthetic the victim has never borrowed [4](#0-3) .
- No modifier stops this: `transfer`/`transferFrom` are unprivileged, unpaused-path, and the `_revertIfLocked` check only limits the *sender's* locked balance, never the recipient's list.
- Attacker cost is ~30 × 1 wei of collateral exposure plus gas; the dust can be recycled across many victims since removal happens only on the victim's own action.

### Impact Explanation
Broken invariant: liveness / temporary freezing of user funds and functionality. A victim whose combined token list is force-filled to 30:

- cannot deposit any collateral type not already in their list (`deposit` → mint → `addToDepositTokensOfAccount` reverts),
- cannot open a debt position in any synthetic whose debt token isn't already listed (blocks refinancing into a new msAsset and blocks `SmartFarmingManager.leverage` paths),
- cannot receive new deposit tokens (griefing any legitimate transfers or liquidation `seize` targeting an unlisted `depositToken_`... note `seize` also routes through the same list-add path for the liquidator/fee collector only if their balance was 0).

Recovery requires the victim to fully empty one listed token (transfer/withdraw dust back out), which costs the victim gas and can be re-griefed by the attacker re-sending dust in the same or next block, giving a cheap, repeatable DoS.

### Likelihood Explanation
Reachable by any EOA. Feasibility scales with the number of deposit tokens registered in the pool (`ReachedMaxDepositTokens` bounds the pool's token count). If a victim already holds N tokens, the attacker only needs `30 − N` distinct deposit-token dusts. The stronger the pool's collateral diversity, the cheaper the attack. No privileged role, oracle manipulation, or governance action is needed — only public `transfer`.

### Recommendation
Track "ever-held" tokens differently from "currently-held" tokens, or only count tokens with balance > a non-trivial threshold toward `MAX_TOKENS_PER_USER`. Alternatively, make `addToDepositTokensOfAccount` idempotent-by-dust (ignore amounts below a floor) or allow additions beyond the cap while enforcing the cap only on *debt-bearing* operations, so dust deposits can never block debt issuance.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.9;

import "forge-std/Test.sol";
import {Pool} from "../contracts/Pool.sol";
import {IDepositToken} from "../contracts/interfaces/IDepositToken.sol";

contract MaxTokensGriefingTest is Test {
    Pool pool; // deployed pool with >=30 registered DepositTokens

    function test_DustTransfersDoSVictim() public {
        address victim = makeAddr("victim");
        address[] memory dts = pool.getDepositTokens();
        uint256 need = 30 - pool.getDepositTokensOfAccount(victim).length
                          - pool.getDebtTokensOfAccount(victim).length;

        for (uint256 i; i < need; ++i) {
            IDepositToken dt = IDepositToken(dts[i]);
            // attacker acquires 2 wei of underlying, deposits, transfers 1 wei
            deal(address(dt.underlying()), address(this), 2);
            dt.deposit(1, address(this));
            dt.transfer(victim, 1); // adds victim's list entry
        }

        // victim can no longer receive a new deposit-token type
        IDepositToken fresh = IDepositToken(dts[need]); // not yet in victim list
        deal(address(fresh.underlying()), address(this), 100);
        fresh.deposit(100, address(this));
        vm.expectRevert(Pool.UserReachedMaxTokens.selector);
        fresh.transfer(victim, 1);

        // and cannot issue a debt token they don't already hold
        // pool.connect(victim).mint(msX, ...) -> addToDebtTokensOfAccount -> revert
    }
}
```

Note: exact feasibility depends on the deployed pool having enough registered deposit tokens (or the victim already holding some positions); with ~30 collaterals the attack is fully attacker-funded.
