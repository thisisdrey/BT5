### Title
Borrower rewards are accrued on time‑grown debt balances, letting holders of accrued interest siphon unclaimed yield - (File: contracts/RewardsDistributor.sol)

### Summary
The Watcher bug class is "a valid state transition path that never produces an event/hook, so the bookkeeping loop misses it." In Metronome, `DebtToken` balances grow passively over time via the debt index (interest accrual) — no mint, burn, or transfer fires, so none of the `updateBefore*` hooks in `RewardsDistributor` are invoked. Yet when a hook finally does run, `_updateTokensAccruedOf` settles the whole historical index delta against the *current* interest‑inflated `balanceOf`, over‑crediting borrowers relative to the debt they actually held during the accrual window.

### Finding Description
`RewardsDistributor._updateTokensAccruedOf` computes reward deltas as `token_.balanceOf(account_).wadMul(_deltaIndex)` where `_deltaIndex = currentIndex - accountIndex` [1](#0-0) . For a `DepositToken`, `balanceOf` is static between explicit mint/burn/transfer operations, all of which fire `updateBeforeMintOrBurn`/`updateBeforeTransfer` hooks [2](#0-1) [3](#0-2) . For a `DebtToken`, however, `balanceOf` equals `principalOf * debtIndex` and grows continuously with time-based interest accrual — a balance change that emits no event and triggers no distributor update. Interest accrued in the past is therefore treated as if it were principal held for the entire reward period, and the borrower harvests rewards on debt that did not yet exist.

`onlyIfTokenExists` explicitly accepts `DebtToken` as a reward-bearing token, and governor-set `tokenSpeeds` on debt tokens route borrower incentives through this exact path [4](#0-3) [5](#0-4) .

### Impact Explanation
Every borrower reward epoch over‑pays accounts whose balances grew via accrued interest, paid out of the fixed reward-token pool. This directly dilutes all other depositors'/borrowers' `tokensAccruedOf` — theft of unclaimed yield — and a rational attacker maximizes the drift by holding large accrued-interest positions and deferring index-touching transactions. The higher the borrow APR and the longer between `updateBefore*` triggers, the larger the skim.

### Likelihood Explanation
No privileged role is needed: any EOA can open a debt position via `Pool`/leverage, let interest accrue, and later trigger settlement (`claimRewards`, any repay/swap that calls `updateBeforeMintOrBurn`) to lock in rewards computed on the inflated balance. Impact scales with debt size, interest rate, and time between index updates — all normal operating conditions, not edge cases. The over-credit is bounded by the interest fraction rather than being unbounded, which keeps severity moderate rather than critical.

### Recommendation
For `DebtToken` rewards, settle deltas against `principalOf` (the value that only changes via hooked mints/burns) instead of the index-scaled `balanceOf`, or force a `_updateTokensAccruedOf` checkpoint whenever the debt index accrues for rewarded tokens. Alternatively, exclude `DebtToken` from `onlyIfTokenExists`-eligible reward tokens if borrower incentives aren't needed.

### Proof of Concept
Hardhat fork test sketch:

1. Governor enables `RewardsDistributor.updateTokenSpeed(msUSDDebt, speed)` and funds the distributor.
2. Alice calls `Pool` issue/borrow of `X` msUSD at `t0`; `updateBeforeMintOrBurn` checkpoints her `accountIndexOf`.
3. Time advances to `t1`; `DebtToken.accrueInterest` (or passive index growth) raises Alice's `balanceOf` from `P` to `P(1+r)`.
4. Alice calls `RewardsDistributor.claimRewards(alice, [msUSDDebt])`. Inside `claimRewards` → `_updateTokensAccruedOf`, `_tokensDelta = balanceOf(alice) * deltaIndex` uses `P(1+r)` for the entire `[t0, t1]` window instead of time-weighted `P`.
5. Assert `claimable(alice)` exceeds `P * deltaIndex` by `P*r*deltaIndex`, and that Bob (same principal, freshly borrowed) receives proportionally less — demonstrating yield stolen from the shared reward pool.

Note: I could not re-verify `DebtToken`'s exact `balanceOf`/`debtIndexOf` implementation within the search budget; the finding relies on the documented interest-indexed balance semantics in `contracts/DebtToken.sol` and should be confirmed against that file before reporting.
