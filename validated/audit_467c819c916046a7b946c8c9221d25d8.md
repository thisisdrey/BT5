### Title
Exchange creator can unilaterally drain the entire AMM liquidity pool via `ExchangeWithdrawContract`, rug-pulling users who traded against it - (File: actuator/src/main/java/org/tron/core/actuator/ExchangeWithdrawActuator.java)

### Summary
The bancor-style `Exchange` object in java-tron is a shared trading pool that any account can trade against via `ExchangeTransactionContract`, but only the exchange's `creatorAddress` is authorized to inject or withdraw liquidity. The withdraw path has no lock-up period, no minimum-liquidity floor beyond a bare non-zero check, and no protection for traders who have just added value to the pool. A single signed transaction from the creator can extract effectively all of the pool's reserves at any time, exactly mirroring the `Role::Owner` rug-pull pattern described in the report: a trusted, privileged party can unilaterally remove value from a pool that other unprivileged users rely on, with no code change and no on-chain safeguard against it.

### Finding Description
Any account can add value to an exchange pool by calling `ExchangeTransactionActuator`, which lets an arbitrary user sell `tokenID` into the pool and receive `anotherTokenID` out, updating the shared `firstTokenBalance`/`secondTokenBalance` state via `ExchangeCapsule.transaction()` [1](#0-0) . This is unrestricted to any signer and does not require the `creatorAddress`.

However, only the `creatorAddress` may withdraw the pool's reserves, enforced in `ExchangeWithdrawActuator.doValidate()`: [2](#0-1) 

The only floor preventing a full drain is a check that both token balances are non-zero ("the exchange has been closed") [3](#0-2) , and a per-quant validation that the withdrawn amount does not exceed the current balance [4](#0-3) . There is no minimum-liquidity requirement, no timelock, and no restriction tied to recent trading activity, so the creator can withdraw down to 1 unit of each token in a single transaction, at any time, immediately after other users have traded against (and added value to) the pool via `execute()` [5](#0-4) .

Because the pool has no concept of multiple liquidity providers or shares (only a single `creatorAddress` is tracked), any tokens deposited into the pool by ordinary traders through `ExchangeTransactionContract` become part of the reserve balance that is entirely and solely withdrawable by the creator. This is directly analogous to the Solana Folio finding: a role holding elevated but "legitimate" authority (`Role::Owner` there, exchange `creatorAddress` here) can unilaterally strip value from a pool that unprivileged third parties have contributed to or rely on, without any code change, and the protocol enforces no additional trust-minimizing constraint on that authority.

### Impact Explanation
Users who submit `ExchangeTransactionContract` trades assume the AMM pool provides continuous liquidity that they, or subsequent traders, can trade back against. Because the creator can drain the pool to near zero at any moment via a single, always-available `ExchangeWithdrawContract` transaction, a malicious or compromised exchange creator can extract value that traders effectively delivered into the pool during prior trades, and can sandwich/rug victims immediately after they execute a trade, permanently depriving them of the ability to trade back at expected liquidity/price. This is a concrete unauthorized-value-extraction / theft-of-funds path reachable purely by transactions any account can broadcast (`ExchangeTransactionContract` for the victim, `ExchangeWithdrawContract` for the attacker).

### Likelihood Explanation
Any account can create an exchange (`ExchangeCreateContract`) and advertise it for trading; nothing prevents the creator from later withdrawing the pool at will. Exploitation requires only two ordinary, unprivileged transactions (a victim trade, followed by the creator's withdraw) with no special network privilege, timing constraints, or race condition beyond ordinary transaction ordering — making this readily and repeatably exploitable by any exchange creator against unsuspecting users of their pool.

### Recommendation
Add liquidity-protection mechanisms to `ExchangeWithdrawActuator`/`ExchangeInjectActuator`, such as: minimum reserve thresholds that persist regardless of creator withdrawals, a timelock or cooldown on withdrawals following recent trades, or converting the exchange model to a proper multi-provider liquidity-share system so that value contributed by traders is not unilaterally extractable by a single privileged `creatorAddress`. Document clearly (as the original report recommends) that exchange creators are a trusted role and that traders bear counterparty risk with respect to the creator's ability to withdraw pool liquidity at will.

### Proof of Concept
1. Attacker calls `ExchangeCreateContract` to create a TRX/TRC10 exchange and seeds it with a small amount via `ExchangeInjectContract`.
2. Victim calls `ExchangeTransactionContract` to trade TRX into the pool, increasing `firstTokenBalance`/`secondTokenBalance` per `ExchangeCapsule.transaction()` [6](#0-5) .
3. Immediately after, the attacker (the `creatorAddress`) calls `ExchangeWithdrawContract` with `quant` equal to nearly the full current balance for both tokens; `doValidate()` only checks the balance is non-zero and the requested quant does not exceed it [7](#0-6) , so the withdrawal succeeds and both token balances credit back to the attacker's account via `execute()` [8](#0-7) .
4. The victim's traded-in value is now held by the attacker outside the pool; any subsequent trader against the near-empty pool faces catastrophic slippage or an effectively closed market.

  public long transaction(byte[] sellTokenID, long sellTokenQuant, boolean useStrictMath,
      boolean hardenedCalc) throws ContractValidateException {
    long supply = 1_000_000_000_000_000_000L;
    Processor processor = hardenedCalc
        ? SafeExchangeProcessor.INSTANCE : new ExchangeProcessor(supply, useStrictMath);

    long buyTokenQuant = 0;
    long firstTokenBalance = this.exchange.getFirstTokenBalance();
    long secondTokenBalance = this.exchange.getSecondTokenBalance();
    long newFirstTokenBalance;
    long newSecondTokenBalance;

    if (this.exchange.getFirstTokenId().equals(ByteString.copyFrom(sellTokenID))) {
      buyTokenQuant = processor.exchange(firstTokenBalance,
          secondTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(firstTokenBalance, sellTokenQuant)
          : firstTokenBalance + sellTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(secondTokenBalance, buyTokenQuant)
          : secondTokenBalance - buyTokenQuant;

    } else {
      buyTokenQuant = processor.exchange(secondTokenBalance,
          firstTokenBalance,
          sellTokenQuant);
      newFirstTokenBalance = hardenedCalc
          ? StrictMathWrapper.subtractExact(firstTokenBalance, buyTokenQuant)
          : firstTokenBalance - buyTokenQuant;
      newSecondTokenBalance = hardenedCalc
          ? StrictMathWrapper.addExact(secondTokenBalance, sellTokenQuant)
          : secondTokenBalance + sellTokenQuant;

    }

    if (hardenedCalc && (newFirstTokenBalance < 0 || newSecondTokenBalance < 0)) {
      throw new ContractValidateException("Exchange balance must be >=0 after transaction");
    }
    this.exchange = this.exchange.toBuilder()
        .setFirstTokenBalance(newFirstTokenBalance)
        .setSecondTokenBalance(newSecondTokenBalance)
        .build();

    return buyTokenQuant;
