### Title
`remove_account` fails to purge `TrieKey::PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` entries, allowing a stale postponed receipt to execute against a re-created account - ([File: core/store/src/utils/mod.rs])

### Summary
`remove_account` in `core/store/src/utils/mod.rs` deletes `Account`, `ContractCode`, access/gas keys, and contract data for an `account_id`, but never enumerates or removes `TrieKey::PostponedReceipt`, `TrieKey::PostponedReceiptId`, or `TrieKey::PendingDataCount` rows keyed by that `account_id`. Since `set_postponed_receipt` (`runtime/runtime/src/lib.rs`, `process_action_receipt`) stores an `ActionReceipt` awaiting `input_data_ids` before it is applied, a receipt containing a `DeleteKey` action targeting an account can be left dangling in the trie after `DeleteAccount` removes the account, and will later execute once the missing `DataReceipt` arrives - against whatever account now occupies that `account_id`.

### Finding Description
`set_postponed_receipt`/`process_action_receipt` write postponed action receipts under `TrieKey::PostponedReceipt { receiver_id, receipt_id }`, `TrieKey::PostponedReceiptId { receiver_id, data_id }`, and `TrieKey::PendingDataCount { receiver_id, receipt_id }` [1](#0-0) . These entries are only consulted/removed when the corresponding `DataReceipt` finally arrives, in `process_receipt`'s `VersionedReceiptEnum::Data` branch [2](#0-1) .

`remove_account` explicitly removes `Account`, `ContractCode`, access keys/gas key nonces, and contract data [3](#0-2) , but at no point iterates the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` prefixes for the account being deleted. Confirmed by reading the full body of `remove_account` — there is no call to `remove_postponed_receipt` or any prefix iteration over those trie key namespaces.

Exploit flow:
1. The account owner (unprivileged, self-funded) issues a transaction/promise that produces an `ActionReceipt` addressed to their own account containing a `DeleteKey` action and a non-empty `input_data_ids` (e.g., via `promise_then`/cross-contract callback pattern where the callback batch includes `DeleteKey`). This receipt is postponed and persisted via `set_postponed_receipt` because the awaited data hasn't arrived yet [4](#0-3) .
2. Before the awaited `DataReceipt` arrives, the owner submits `DeleteAccount`, which invokes `remove_account`. The postponed receipt, `PostponedReceiptId` link, and `PendingDataCount` for that account_id survive in the trie because `remove_account` never touches those keys.
3. The account_id is re-created (`CreateAccount`, possible immediately or later by any party since NEAR does not reserve deleted account names), and the new owner adds a full-access key.
4. When the originally-awaited `DataReceipt` (or an equivalent data_id match) is eventually delivered — something the original account owner controls the timing/content of, since it was their own promise chain — `process_receipt`'s Data branch looks up `PostponedReceiptId`, decrements `PendingDataCount`, and once it hits zero, fetches and executes the stale `DeleteKey` receipt via `apply_action_receipt`, now against the re-created account's state, deleting the new owner's freshly-added full-access key.

This bypasses all access-key/authorization checks because the executing code path is receipt replay driven purely by trie-key matching (`receiver_id`, `data_id`), not signature or access-key verification at execution time — `apply_action_receipt` trusts that a postponed receipt addressed to `account_id` was already authorized when originally accepted, an invariant broken once the account underneath that `account_id` has changed identity via delete+recreate.

### Impact Explanation
Authorization escalation: an action (`DeleteKey`) that was authorized against the old account's key set silently executes against a completely different, re-created account, deleting a full-access key the new legitimate owner just added — without their consent and without any signature check at execution time. This maps to NEAR's "authorization escalation across accounts" bounty category and can also enable griefing/permanent loss of access to funds/contract control for whoever legitimately re-registers that account_id.

### Likelihood Explanation
Preconditions: the attack requires the ability to (a) produce a self-addressed `ActionReceipt` with `DeleteKey` and unresolved `input_data_ids` (achievable by an ordinary account deploying its own contract and using `promise_then`/cross-contract calls), (b) issue `DeleteAccount` before the awaited data arrives, and (c) have the account_id re-created and a new key added before the awaited `DataReceipt` is finally delivered — a timing race the attacker who owns the original promise chain can influence (they control when/if to fulfill the callback data, subject to cross-shard/data availability timing). This is achievable purely through unprivileged transaction/contract control (no validator, node, or leaked-key access needed), repeatable, and inexpensive (only standard gas/storage costs). The main uncertainty is precise timing control over exactly when the account gets re-registered and re-keyed relative to data delivery, but the underlying missing-cleanup defect is unconditionally present and independently reproducible without any race in a unit test.

### Recommendation
`remove_account` must enumerate and delete all `PostponedReceipt`, `PostponedReceiptId`, and `PendingDataCount` trie entries for the given `account_id` (analogous to how it iterates access keys and contract data), or `DeleteAccount` validation must reject deletion while any postponed receipt/pending data count still references the account.

### Proof of Concept
Unit test in `core/store/src/utils/mod.rs` (or `runtime/runtime/src/tests`):
1. Build a `TrieUpdate`, call `set_postponed_receipt` with a `Receipt` (`ActionReceipt` containing a `DeleteKey` action) for `account_id = "alice.near"`, plus `set` for a corresponding `PendingDataCount` and `PostponedReceiptId`.
2. Call `remove_account(&mut state_update, &"alice.near".parse().unwrap())`.
3. Assert that `get_postponed_receipt(&state_update, &account_id, receipt_id)`, and lookups for `TrieKey::PostponedReceiptId`/`TrieKey::PendingDataCount` for that account, are all `None`.
4. Expected result today: the assertion fails — the `PostponedReceipt`/`PostponedReceiptId`/`PendingDataCount` rows remain present after `remove_account` returns, demonstrating the gap.
5. (Integration extension) In a runtime test-loop: create account, submit a receipt causing a postponed `DeleteKey` receipt to be stored, delete the account, re-create the same account_id, add a full-access key, then deliver the awaited `DataReceipt` and assert the newly added key is unexpectedly deleted.

pub fn remove_account(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
) -> Result<RemoveAccountResult, StorageError> {
    state_update.remove(TrieKey::Account { account_id: account_id.clone() });
    state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });

    let mut gas_key_nonce_count: usize = 0;
    let mut gas_key_nonce_total_key_bytes: usize = 0;

    // Removing access keys and gas key nonces
    let lock = state_update.trie().lock_for_iter();
    let mut keys_to_remove: Vec<TrieKey> = Vec::new();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if let Some(index) = nonce_index {
            gas_key_nonce_count += 1;
            gas_key_nonce_total_key_bytes += raw_key.len();
            keys_to_remove.push(TrieKey::gas_key_nonce(
                account_id.clone(),
                key_handle.clone(),
                index,
            ));
        } else {
            keys_to_remove.push(TrieKey::access_key(account_id.clone(), key_handle.clone()));
        }
    }
    drop(lock);

    for trie_key in keys_to_remove {
        state_update.remove(trie_key);
    }

    // Removing contract data
    let lock = state_update.trie().lock_for_iter();
    let data_keys = state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_contract_data(account_id, &[]), &lock)?
        .map(|raw_key| {
            trie_key_parsers::parse_data_key_from_contract_data_key(&raw_key?, account_id)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse data key from raw key for ContractData".to_string(),
                    )
                })
                .map(Vec::from)
        })
        .collect::<Result<Vec<_>, _>>()?;
    drop(lock);

    for key in data_keys {
        state_update.remove(TrieKey::ContractData { account_id: account_id.clone(), key });
    }
    Ok(RemoveAccountResult { gas_key_nonce_count, gas_key_nonce_total_key_bytes })
}
