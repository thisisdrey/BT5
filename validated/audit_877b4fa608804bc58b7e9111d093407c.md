### Title
Integer-overflow bypass of the Zip64 central-directory bounds check leads to unconstrained out-of-bounds heap read - (File: `third_party/ijar/zip.cc`)

### Summary
`FindZipCentralDirectory()` validates the location of a ZIP central directory with `cd.central_dir_offset + cd.central_dir_size > in_length`, but both operands can be fully attacker-controlled 64-bit values coming from a Zip64 End-Of-Central-Directory record, so the addition can wrap and defeat the very check meant to keep the parser inside the mapped file — the same bug class as CVE-2026-47251 (an overflow in a bounds check introduced to stop an earlier OOB read).

### Finding Description
`FindZipCentralDirectory` locates the regular EOCD record, then calls `FindZip64CentralDirectory` → `MaybeReadZip64CentralDirectory`, which overwrites `cd.central_dir_size` and `cd.central_dir_offset` with values read via `get_u8le`, i.e. full 64-bit fields taken directly from attacker-controlled bytes in the Zip64 EOCD record: [1](#0-0) 

After this, the bounds check and the pointer derivation are: [2](#0-1) 

`in_length` and `cd.central_dir_offset`/`cd.central_dir_size` are all 64-bit (`size_t`/`u8`). Because the two operands are attacker-supplied, `central_dir_offset + central_dir_size` can be crafted to wrap around `2^64` and produce a value ≤ `in_length`, so the guard `> in_length` never triggers even though the real offset/size describe a region far outside the mapped input file. The resulting `*central_dir = end_of_central_dir - cd.central_dir_size` then computes a wild pointer (pointer arithmetic with a huge `cd.central_dir_size`, e.g. near `UINT64_MAX`), which is stored as the starting cursor for central-directory parsing.

Critically, the per-entry parser that walks this pointer, `ProcessCentralDirEntry`, performs **no** `EnsureRemaining`-style bounds checking before reading fields — unlike local-file-entry parsing which calls `EnsureRemaining`: [3](#0-2) 

So once the initial size check is bypassed, every subsequent `get_u4le`/`get_u2le`/`memcpy` call in `ProcessCentralDirEntry` (and in `CalculateOutputLength`, which loops over all entries) reads from unconstrained memory relative to the wild `central_dir` pointer, with no further gate.

### Impact Explanation
This zip parser (`third_party/ijar/zip.cc`) backs both the `ijar`/`singlejar`-adjacent tooling and the standalone `zipper` binary (`third_party/ijar/zip_main.cc`), which Bazel invokes to extract/process `.zip`/`.jar` archives, including archives that originate from external dependencies fetched over the network (e.g., interface-jar generation from Maven/http-fetched jars, and direct extraction via the `zipper` extract() path). A hostile origin serving a crafted Zip64 archive can smuggle offset/size pairs that wrap the 64-bit addition, causing the tool to read heap memory outside the mmap'd archive bounds. This is a native out-of-bounds heap read that can crash the process or leak adjacent process memory into files/state derived from the (corrupted) central-directory parse — i.e., untrusted archive bytes are not kept as inert "data," breaking the containment invariant that archive metadata is bounds-checked before being trusted.

### Likelihood Explanation
Exploitation requires only publishing/serving a crafted `.zip`/`.jar` file containing a Zip64 EOCD record with two 64-bit fields chosen so their sum wraps mod 2^64 — no MITM, no credentials, and no access to the victim's machine or root BUILD/.bzl files are needed. The only barrier is that the existing sha256/integrity check on a `http_archive`/`http_jar` fetch would normally pin file contents, but for cases where hashes are not pinned (development iteration, or any Bazel code path that opens attacker-influenced jars without a prior content-hash gate, e.g. locally-built or third-party jars processed by `ijar`), the malformed archive reaches this parser directly.

### Recommendation
- In `MaybeReadZip64CentralDirectory`/`FindZipCentralDirectory`, validate `central_dir_size` and `central_dir_offset` individually against `in_length` **before** adding them (e.g., `if (central_dir_size > in_length || central_dir_offset > in_length - central_dir_size) return false;`), or perform the addition in a wider/overflow-checked type.
- Add `EnsureRemaining`-equivalent bounds checks inside `ProcessCentralDirEntry` before every field read, so a corrupted `central_dir` pointer cannot produce unconstrained reads even if the initial check were somehow bypassed again.

### Proof of Concept
A `JUnit`/`src/test/shell` reproduction would construct a minimal ZIP with:
1. A standard EOCD record with `central_dir_offset = 0xFFFFFFFF` (triggering the ZIP64 lookup).
2. A Zip64 EOCD record with `central_dir_size = 0xFFFFFFFFFFFFFF00` and `central_dir_offset = 0x200` (sum wraps to `0x100`, which is `≤ in_length` for a small test file), so `FindZipCentralDirectory`'s check passes.
3. Feed this file to the `zipper` tool's extract path (`third_party/ijar/zip_main.cc:extract`) or to `ZipExtractor::ProcessAll()`, and observe the out-of-bounds read/crash (e.g., under ASan) when `ProcessCentralDirEntry` dereferences the wild `central_dir_` pointer.

Note: I could not fully verify inside this session whether Bazel's higher-level Java `http_archive`/`ZipDecompressor` extraction pipeline (used for `download_and_extract`) shares this exact C++ parser or a separate Java implementation — that code was not found in the indexed repository, so the confirmed reachable consumer here is the native `ijar`/`zipper` tooling. A full audit of the Java-side zip extraction path used by repository rules is recommended to determine whether the same or an analogous overflow exists there.
