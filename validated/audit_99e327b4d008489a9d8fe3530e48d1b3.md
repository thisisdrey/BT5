### Title
Relayer reward paid regardless of delivery outcome in Snowbridge outbound-queue-v2 `process_delivery_receipt` - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The Snowbridge V2 outbound queue pays out the full relayer reward for a delivered message without checking the `success` field of the delivery receipt, which is decoded from the Ethereum `InboundMessageDispatched` event log but is never consulted before settling the payout.

### Finding Description
`submit_delivery_receipt` verifies the Ethereum event proof, decodes it into a `DeliveryReceipt`, and calls `process_delivery_receipt`: [1](#0-0) 

`DeliveryReceipt` is decoded from the `InboundMessageDispatched(nonce, topic, success, reward_address)` event and explicitly carries a `success: bool` field: [2](#0-1) 

However, `process_delivery_receipt` only checks the gateway address and looks up the `PendingOrder` by `nonce`; it pays out `order.fee` to the relayer/reward account whenever `order.fee > 0`, and then unconditionally removes the pending order — the `success` flag on the decoded receipt is never read or branched on: [3](#0-2) 

The Ethereum gateway contract's `InboundMessageDispatched` event fires with `success=false` when a bridged message's execution reverts or fails on the destination side (Ethereum), but the reward logic on Polkadot's side treats every legitimately-proved event log the same, regardless of that outcome. This breaks the invariant from the pivots that "payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — settlement here advances purely on proof-of-log-existence, not on the actually encoded success outcome carried in that same proof.

### Impact Explanation
This allows unbacked reward mint: a relayer that submits a message whose remote execution on Ethereum fails (`success=false`) still collects the full reward via `T::RewardPayment::register_reward`, exactly as if the message had succeeded. Since the reward is denominated in the bridge's `Balance` (e.g., WETH derivative) and is registered without adjustment, this results in the relayer being rewarded for work that did not achieve its intended effect, i.e. an underpriced/unconditional payout for message submission regardless of dispatch outcome. Over repeated failing-message submissions this drains the reward pool disproportionate to correctly delivered work, directly matching the "duplicate settlement or payout" / "public underpriced work" impact classes for BridgeHub Snowbridge code.

### Likelihood Explanation
This is reachable by any unprivileged relayer account (only `ensure_signed` is required) and requires only a genuinely valid Merkle/event proof from Ethereum showing a message dispatch that failed (`success = false`) — this is a normal, expected occurrence (e.g. an XCM `Transact` or execution reverting on Ethereum), not a contrived edge case, and needs no malicious peer, validator, or governance actor to trigger.

### Recommendation
In `process_delivery_receipt`, branch on `receipt.success` before registering the reward: pay the full fee (or a possibly reduced compensation) only when `success == true`, and otherwise refund/burn or handle the fee according to the intended failure-handling policy, mirroring how `order.fee` is only paid conditionally. Add an explicit test asserting that a `DeliveryReceipt` with `success: false` does not result in `RewardRegistered`.

### Proof of Concept
1. A message is enqueued via `do_process_message`, creating `PendingOrders::<T>::insert(nonce, PendingOrder { nonce, fee, .. })` with `fee > 0`. [4](#0-3) 
2. The message is delivered to Ethereum and dispatch fails there (e.g., a nested `Transact`/execution reverts), causing the gateway to emit `InboundMessageDispatched(nonce, topic, success=false, reward_address)`.
3. A relayer submits this proof via `submit_delivery_receipt(origin, event)`. `T::Verifier::verify` succeeds (it is a genuine, unforged log), and `DeliveryReceipt::try_from` decodes `success: false` correctly. [5](#0-4) 
4. `process_delivery_receipt` runs: it never inspects `receipt.success`, finds `order.fee > 0`, and calls `T::RewardPayment::register_reward(&reward_account, DefaultRewardKind, order.fee)`, then removes the pending order and emits `MessageDelivered`. [6](#0-5) 
5. Result: the relayer is rewarded exactly as in the success path even though the bridged message failed on Ethereum — the existing test suite (`bridges/snowbridge/pallets/outbound-queue-v2/src/test.rs`) only exercises the halted/unhalted success path and does not cover a `success: false` receipt, confirming the gap is untested.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
