### Title
Stale `pool.operator_commission_percentage` Used in `calculate_stake_pool_drift` Instead of Dynamic `operator_commission_percentage()` — (`File: aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

---

### Summary

`calculate_stake_pool_drift` in `delegation_pool.move` reads the static stored field `pool.operator_commission_percentage` to compute operator commission on accumulated rewards. A dynamic view function `operator_commission_percentage(pool_address)` already exists and correctly accounts for a pending commission update stored in `NextCommissionPercentage`. Because `calculate_stake_pool_drift` bypasses this dynamic function, the first call to `synchronize_delegation_pool` after a lockup cycle expires distributes commission at the **old** rate even though the new rate is already effective — and the public view functions `get_stake` / `get_pending_withdrawal` return incorrect delegator balances during the same window.

---

### Finding Description

`update_commission_percentage` stores a pending change in `NextCommissionPercentage`:

```move
// delegation_pool.move ~1322
move_to(&pool_signer, NextCommissionPercentage {
    commission_percentage_next_lockup_cycle: new_commission_percentage,
    effective_after_secs: stake::get_lockup_secs(pool_address),   // = lockup expiry
});
``` [1](#0-0) 

The dynamic view function `operator_commission_percentage` checks whether the pending value is already effective:

```move
public fun operator_commission_percentage(pool_address): u64 {
    if (is_next_commission_percentage_effective(pool_address)) {
        operator_commission_percentage_next_lockup_cycle(pool_address)   // new rate
    } else {
        borrow_global<DelegationPool>(pool_address).operator_commission_percentage  // old rate
    }
}
``` [2](#0-1) 

`is_next_commission_percentage_effective` returns `true` as soon as `timestamp::now_seconds() >= effective_after_secs`, i.e. as soon as the lockup expires: [3](#0-2) 

However, `calculate_stake_pool_drift` — the function that computes the actual commission to distribute — reads the **raw stored field** directly:

```move
let commission_active = if (active > pool_active) {
    math64::mul_div(active - pool_active, pool.operator_commission_percentage, MAX_FEE)
    //                                    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //                                    stale stored value, not the dynamic function
``` [4](#0-3) 

```move
let commission_pending_inactive = if (pending_inactive > pool_pending_inactive) {
    math64::mul_div(
        pending_inactive - pool_pending_inactive,
        pool.operator_commission_percentage,   // stale again
        MAX_FEE
    )
``` [5](#0-4) 

`synchronize_delegation_pool` calls `calculate_stake_pool_drift` first, distributes commission at the old rate, and only **then** updates the stored field:

```move
// commission distributed at old rate here ↑
...
if (is_next_commission_percentage_effective(pool_address)) {
    pool.operator_commission_percentage = borrow_global<NextCommissionPercentage>(
        pool_address
    ).commission_percentage_next_lockup_cycle;
}
``` [6](#0-5) 

By contrast, `get_add_stake_fee` correctly calls the dynamic function:

```move
rewards_rate *= (MAX_FEE - operator_commission_percentage(pool_address));
``` [7](#0-6) 

The same stale value propagates into the public view functions `get_stake` and `get_pending_withdrawal`, both of which call `calculate_stake_pool_drift`: [8](#0-7) [9](#0-8) 

---

### Impact Explanation

**On-chain commission distribution (state-changing):** Every reward epoch that elapses between lockup expiry and the first `synchronize_delegation_pool` call is charged at the old commission rate. If the new rate is lower than the old rate, the operator extracts more APT from delegator rewards than the agreed-upon rate; if higher, the operator receives less. Because `synchronize_delegation_pool` is not automatically triggered by epoch transitions (it must be called explicitly), the window can span multiple epochs.

**View functions:** `get_stake` and `get_pending_withdrawal` return incorrect delegator balances during the same window, because they compute commission using the stale field. Delegators querying their own stake see inflated or deflated values depending on the direction of the commission change.

---

### Likelihood Explanation

Every delegation pool that calls `update_commission_percentage` will experience this discrepancy at the next lockup expiry. The lockup cycle is typically 30 days on mainnet. The window of incorrect commission application lasts until the first explicit `synchronize_delegation_pool` call after expiry, which in practice is triggered by the next user interaction (add_stake, unlock, withdraw, etc.). For pools with low activity the window can be multiple epochs.

---

### Recommendation

Replace the direct field read in `calculate_stake_pool_drift` with the dynamic function. Since `calculate_stake_pool_drift` receives only a `&DelegationPool` reference, pass the pool address as an additional parameter and call `operator_commission_percentage(pool_address)`:

```move
fun calculate_stake_pool_drift(pool: &DelegationPool, pool_address: address): (bool, u64, u64, u64, u64)
    acquires NextCommissionPercentage {
    ...
    let effective_commission = operator_commission_percentage(pool_address);
    let commission_active = if (active > pool_active) {
        math64::mul_div(active - pool_active, effective_commission, MAX_FEE)
    } else { 0 };
    let commission_pending_inactive = if (pending_inactive > pool_pending_inactive) {
        math64::mul_div(pending_inactive - pool_pending_inactive, effective_commission, MAX_FEE)
    } else { 0 };
    ...
}
```

This mirrors the fix applied in the external `DIAExternalStaking` report: replace the static storage read with the dynamic getter that accounts for pending updates.

---

### Proof of Concept

1. Pool is created with 10% commission (`operator_commission_percentage = 1000`).
2. Owner calls `update_commission_percentage(owner, 500)` (5%) with 30+ days remaining in lockup. `NextCommissionPercentage { commission_percentage_next_lockup_cycle: 500, effective_after_secs: T_expiry }` is stored.
3. Lockup expires at `T_expiry`. `is_next_commission_percentage_effective` now returns `true`; `operator_commission_percentage(pool_address)` returns `500`.
4. One epoch of rewards accrues (e.g. 10 000 APT active stake, 1% epoch rate → 100 APT reward).
5. A delegator calls `add_stake`, which triggers `synchronize_delegation_pool`.
6. `calculate_stake_pool_drift` computes `commission_active = 100 * 1000 / 10000 = 10 APT` (old 10% rate).
7. The correct commission at the new 5% rate would be `100 * 500 / 10000 = 5 APT`.
8. The operator receives 10 APT instead of 5 APT; delegators lose 5 APT of staking rewards they were entitled to.
9. Only after step 5 does `pool.operator_commission_percentage` get updated to `500`.
10. Querying `get_stake` for any delegator between steps 3 and 5 also returns an incorrect (understated) active balance because `commission_active` is overstated.
