### Title
Integer overflow in MVCC manifest chunk-offset parsing bypasses bounds checks - (File: `internal/git/mvcc/manifest.go`)

### Summary
`parseChunks` in the MVCC manifest parser converts attacker/peer-influenced 64-bit chunk offsets read from a manifest file into Go `int` without checking for overflow, and then uses those values in bounds comparisons and slice indexing. On the reachable code path this mirrors the reported Solidity bug class: an externally supplied numeric value (there, `decimals()`; here, a TOC chunk offset) is trusted and fed into arithmetic/comparisons without validating its actual range, producing incorrect (including negative) results that defeat the subsequent bounds checks.

### Finding Description
`parseChunks` reads chunk offsets directly from the manifest byte buffer as `uint64` and converts them to `int`: [1](#0-0) 

`chunkOffsetInFile` and `nextChunkOffsetInFile` are derived via `int(binary.BigEndian.Uint64(...))`. If the encoded 64-bit value exceeds `math.MaxInt64` (i.e., the top bit is set), the conversion wraps to a negative `int` on 64-bit platforms. The subsequent bounds check:

```go
if chunkOffsetInFile > dataEnd || nextChunkOffsetInFile > dataEnd || nextChunkOffsetInFile < chunkOffsetInFile {
```

can be satisfied even though the "offset" no longer represents a valid, in-range position, because a large-enough crafted value becomes a negative number that is never `> dataEnd` and can still satisfy the relative ordering check. `chunkSize := nextChunkOffsetInFile - chunkOffsetInFile` is then computed from these corrupted values and stored in `manifestChunk.offset`/`.size`, later used directly as slice bounds in `ParseManifest` (e.g. `data[objsChunk.offset : objsChunk.offset+8]`, `data[refsChunk.offset+i*4 : ...]`): [2](#0-1) [3](#0-2) 

A negative or otherwise out-of-range offset used as a slice index triggers a Go runtime panic (`slice bounds out of range`), rather than the intended graceful `fmt.Errorf` rejection the code elsewhere relies on for malformed input.

`numChunks` itself is bounded to a single byte (`data[5]`), so the TOC-size arithmetic at line 285/272 cannot overflow, but the per-chunk 64-bit file offsets read from the TOC are unconstrained and directly attacker-controllable within the manifest blob.

### Impact Explanation
A crafted MVCC manifest with a corrupted (SHA-256-consistent, since the attacker also controls the trailer they append) 64-bit offset field would not be rejected by the offset/order checks and would instead reach a slice operation with a negative or overflowed index, causing a runtime panic. Since manifest parsing happens inside the Gitaly process handling repository/partition operations (MVCC storage backend), an unhandled panic in a request-handling goroutine can crash or degrade the serving Gitaly node — a denial-of-service condition — analogous to how the original report's unchecked `decimals()` value corrupts downstream arithmetic in `Investment.sol`.

### Likelihood Explanation
I could not, within the available tool budget, fully trace which gRPC-facing code path allows an ordinary/unprivileged client to supply or influence the raw bytes of a manifest file that reaches `ParseManifest` (e.g., via replication, backup/restore RPCs, or partition transaction application). `ParseManifest` is invoked from `internal/git/mvcc/cache.go`, and manifests are also referenced from `internal/gitaly/storage/storagemgr/partition/transaction_manager.go`, `internal/gitaly/storage/wal/manifest.go`, and backup/restore code, but confirming whether any of these accept manifest bytes from a network peer/ordinary user without independent trust bootstrapping (versus being purely locally generated by trusted Gitaly logic) requires deeper call-graph tracing than I completed. This is a material gap: if manifests are exclusively generated and consumed internally by Gitaly itself (never parsed from untrusted transport input), this is not exploitable by an unprivileged actor and would not qualify as a valid finding under the stated rules.

### Recommendation
- Validate the raw 64-bit offset value before narrowing to `int`: reject values greater than `math.MaxInt`/`len(data)` explicitly, instead of relying on the post-conversion comparison.
- Alternatively, keep offsets as `uint64`/`uint` through the bounds checks and only convert to `int` after confirming `offset <= uint64(len(data))`.
- Add a defensive bounds check immediately before every slice operation that uses `manifestChunk.offset`/`.size` (in addition to the TOC-parsing check) so a bug in one layer cannot lead to a panic in another.
- Add fuzz/unit tests for `parseChunks`/`ParseManifest` with offset values near `math.MaxUint64` and near `math.MaxInt64` boundaries.

### Proof of Concept
Conceptual (not fully verified against a live entry point due to incomplete call-graph tracing):
1. Construct a manifest byte buffer with a valid header (`magic`, `version=1`, `numChunks=2`, valid `pathWidth`, valid `hashAlgo`).
2. In the TOC, set one chunk's 8-byte big-endian offset field to a value with the high bit set, e.g. `0x8000000000000000`, and the following chunk's offset to a slightly larger value with the high bit also set (so `nextChunkOffsetInFile < chunkOffsetInFile` still evaluates in a way that passes when both wrap negative consistently).
3. Recompute and append the correct trailing SHA-256 checksum over the crafted payload so `ParseManifest`'s checksum check passes.
4. Feed this buffer into `mvcc.ParseManifest`; `parseChunks` converts the offsets to negative `int`s, bypasses the `> dataEnd` check, and a later slice expression (e.g. for the OBJS/REFS chunk) indexes `data` with a negative offset, causing a runtime panic.

Because I was unable to confirm within the remaining budget that untrusted/unprivileged input reaches `ParseManifest` directly (as opposed to being generated solely by trusted local Gitaly code), this finding should be treated as unconfirmed regarding reachability — a Devin session with full repository/call-graph access would be needed to trace `cache.go`, `transaction_manager.go`, and the replication/backup RPC handlers to establish or rule out an unprivileged trigger path.
