## Title
Reward ledger is settled before beneficiary deposit succeeds, allowing relayer rewards to be silently lost to an unroutable/invalid beneficiary Location - ([File: bridges/snowbridge/primitives/core/src/reward.rs])

## Summary
`PayAccountOnLocation::pay_reward` treats successful XCM *delivery* to AssetHub as proof of successful *payment*, while the actual `DepositAsset` into the caller-supplied beneficiary happens asynchronously on AssetHub and can fail independently of delivery success. `do_claim_rewards` in `pallet-bridge-relayers` removes the relayer's `RelayerRewards` entry and emits `RewardPaid` as soon as `pay_reward` returns `Ok(())`, with no confirmation that the deposit actually landed in a valid, receivable account.

## Finding Description
`claim_rewards_to` is a public, signed extrinsic that calls `do_claim_rewards`, which removes the `RelayerRewards` entry via `maybe_reward.take()` before invoking `T::PaymentProcedure::pay_reward`, and only rolls back on `Err` [1](#0-0) . For `BridgeReward::Snowbridge`, this routes through `BridgeRewardPayer::pay_reward` in `bridge_common_config.rs`, which only checks that the `VersionedLocation` converts to a `Location`, not that it is a resolvable, asset-receiving account, before calling `PayAccountOnLocation::pay_reward` [2](#0-1) . `PayAccountOnLocation::pay_reward` constructs an XCM with `ReserveAssetDeposited` followed by `DepositAsset { assets: AllCounted(1).into(), beneficiary }` targeting the caller-supplied `Location`, and returns `Ok(())` as soon as `XcmSender::deliver(ticket)` succeeds — i.e., once the message is queued, not once `DepositAsset` actually executes on AssetHub [3](#0-2) . If `beneficiary` cannot resolve to a valid account on AssetHub, `DepositAsset` fails during remote execution, the reserve-minted asset is trapped, and `RewardPaid` has already been emitted with the `RelayerRewards` entry permanently removed. The unit tests in the same file (`pay_reward_success`, `pay_reward_fails_on_delivery`, etc.) confirm that `pay_reward`'s `Ok`/`Err` outcome is determined solely by `validate_send`/`charge_fees`/`deliver`, never by remote deposit confirmation [4](#0-3) .

## Impact Explanation
This matches the pivot requiring "message queues, bridge markers, receipts, and payout state must only advance after decode, dispatch, execution, and settlement succeed atomically" — settlement (removal of `RelayerRewards` + `RewardPaid`) on BridgeHub advances strictly on send/delivery success, not on remote execution success. The concrete corrupted state is the `RelayerRewards` double-map entry (deleted) and the `RewardPaid` event (falsely emitted), while the reserve-minted asset is trapped on AssetHub with no accessible recovery path for the relayer, constituting a permanent loss of the accounted reward funds.

## Likelihood Explanation
`claim_rewards_to` is unprivileged and public; any relayer with an accrued reward directly controls the `beneficiary` argument passed all the way to `DepositAsset` with no validation of account-resolvability. No governance, malicious peer, or compromised-relayer assumption is required — a malformed `Location` (accidental or deliberate) reliably reproduces the loss.

## Recommendation
Validate that `beneficiary` resolves to a well-formed, receivable account (e.g., require a terminal `AccountId32`/`AccountKey20` junction) before removing the `RelayerRewards` entry, or defer settlement/`RewardPaid` emission until execution/deposit confirmation is available (e.g., via a callback or receipt from AssetHub), so a failed deposit can restore the relayer's claimable balance instead of silently trapping it.

## Proof of Concept
1. Relayer accrues a `BridgeReward::Snowbridge` reward via `register_reward`.
2. Relayer calls `claim_rewards_to(origin, BridgeReward::Snowbridge, BridgeRewardBeneficiaries::AssetHubLocation(VersionedLocation::V5(malformed_location)))` where `malformed_location` lacks a resolvable account junction.
3. `BridgeRewardPayer::pay_reward` → `PayAccountOnLocation::pay_reward` builds the XCM; `validate_send`/`charge_fees`/`deliver` succeed since only routability to AssetHub is checked [5](#0-4) .
4. `do_claim_rewards` observes `Ok(())`, deletes the `RelayerRewards` entry, and emits `Event::RewardPaid` [6](#0-5) .
5. On AssetHub, `DepositAsset` fails against `malformed_location`; the reserve-minted asset is trapped while BridgeHub state shows the reward as fully paid with no remaining claim for the relayer.

	fn pay_reward(
		relayer: &Relayer,
		_: (),
		reward: RewardBalance,
		beneficiary: Self::Beneficiary,
	) -> Result<(), Self::Error> {
		let ethereum_location = Location::new(2, [GlobalConsensus(EthereumNetwork::get())]);
		let assets: Asset = (ethereum_location.clone(), reward.into()).into();

		let xcm: Xcm<()> = alloc::vec![
			UnpaidExecution { weight_limit: Unlimited, check_origin: None },
			DescendOrigin(InboundQueueLocation::get().into()),
			UniversalOrigin(GlobalConsensus(EthereumNetwork::get())),
			ReserveAssetDeposited(assets.into()),
			DepositAsset { assets: AllCounted(1).into(), beneficiary },
		]
		.into();

		let (ticket, fee) =
			validate_send::<XcmSender>(AssetHubLocation::get(), xcm).map_err(|_| XcmSendFailure)?;
		XcmExecutor::charge_fees(relayer.clone(), fee).map_err(|_| ChargeFeesFailure)?;
		XcmSender::deliver(ticket).map_err(|_| XcmSendFailure)?;

		Ok(())
	}
