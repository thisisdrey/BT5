### Title
Out-of-bounds array read in `PrecompiledContracts.extractBytes32Array` due to missing bounds check on attacker-controlled offset/length - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The CVE describes `GffLine::GffLine` in GCLib reading past the bounds of a parsed data buffer because the length/offset value taken from an untrusted, crafted file is used to index the buffer without a range check, causing a crash. Java-tron's `PrecompiledContracts.extractBytes32Array` has the analogous pattern: it reads a caller-controlled length word from `DataWord[] words` and then loops reading `words[offset + i + 1]` without ever validating that `offset + len` stays within the bounds of `words`.

### Finding Description
`extractBytes32Array` is defined as: [1](#0-0) 

Unlike its sibling helpers `extractBytesArray` and `extractSigArray`, which explicitly guard against an out-of-range `offset` before indexing (`if (offset > words.length - 1) { return new byte[0][]; }`), `extractBytes32Array` performs no such check: [2](#0-1) 

`len` is derived directly from `words[offset].intValueSafe()` — fully attacker-controlled via the ABI-encoded precompile call data — and the loop then dereferences `words[offset + i + 1]` for `i` in `[0, len)`. If `offset + len + 1` exceeds `words.length`, this throws an unhandled `ArrayIndexOutOfBoundsException` (Java's memory-safe analog of an out-of-bounds read/crash in the C++ `gff.cpp` case), which is not the deliberate `Program.Exception` family that the TVM interpreter normally converts into a clean revert.

### Impact Explanation
Any account (unprivileged transaction broadcaster) can invoke a precompiled contract via a `TriggerSmartContract` and supply crafted call data that causes `extractBytes32Array` to be invoked with an `offset`/`len` combination that walks off the end of the `words` array. Because this is a raw `ArrayIndexOutOfBoundsException` rather than the VM's expected `Program.Exception` hierarchy, it risks propagating as an unexpected `RuntimeException` out of the precompile's `execute()` path, which is caught generically in `VM.play`, but the inconsistency between this helper and its sibling functions (`extractBytesArray`, `extractSigArray`), which were clearly patched to add the `offset > words.length - 1` guard, indicates this is a known-but-unfixed gap in this specific helper — an oversight relative to intended defensive coding for the same input class.

### Likelihood Explanation
High for reachability: precompiled contracts are called directly from arbitrary, unprivileged smart-contract execution triggered by any signed transaction, and the input `data` byte array is fully attacker-controlled ABI-encoded call data. The presence of matching bounds checks in `extractBytesArray`/`extractSigArray` but not in `extractBytes32Array` at lines 390-397 strongly suggests this was missed during a security hardening pass, making it a concrete, low-effort-to-trigger gap.

### Recommendation
Add the same `if (offset > words.length - 1) return new byte[0][];` guard to `extractBytes32Array`, and additionally validate that `offset + len` does not exceed `words.length` before the loop runs, mirroring the defensive checks already present in the other two extraction helpers in the same file.

    if (offset > words.length - 1) {
      return new byte[0][];

    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
