### Title
Meta-transaction (`DelegateAction`/`SignedDelegateAction`) signatures are not bound to a chain/network identifier, enabling cross-network replay of delegated actions - (File: core/primitives/src/action/delegate.rs)

### Summary
NEAR's meta-transaction scheme (NEP-366/NEP-611) has the sender sign a `DelegateAction` independently of the outer `SignedTransaction`. The bytes that get hashed and signed for that inner signature are only `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, plus a NEP-number/on-off-chain discriminant — there is no chain/genesis/network identifier bound into the signed payload, unlike the outer transaction which carries a live `block_hash` that is validated against the local chain's ancestry (`check_transaction_validity_period` / `validity_period_validate_is_ancestor`). This mirrors exactly the reported Term Finance bug class: an authentication token (here, the relayer-submittable `SignedDelegateAction`) that is portable to any chain/fork/network where the referenced account, public key and access-key nonce happen to coincide.

### Finding Description
`DelegateAction::get_nep461_hash()` / `VersionedDelegateActionPayload::get_nep461_hash()` build the signed message from `SignableMessage::new(&self, SignableMessageType::DelegateAction/…)`, i.e. only the fields listed above: [1](#0-0) [2](#0-1) 

Verification (`SignedDelegateAction::verify` / `VersionedSignedDelegateAction::verify`) checks only this signature against the embedded `public_key`: [3](#0-2) [4](#0-3) 

The only anti-replay protections applied at execution time (`apply_delegate_action` / `validate_delegate_action_key`) are: (1) `max_block_height` compared to the local `apply_state.block_height`, and (2) the delegate's `nonce` compared to the *local* access key's stored nonce for `(sender_id, public_key)`: [5](#0-4) [6](#0-5) 

Neither of these fields is unique to a single network/chain: `max_block_height` is just a height number that exists identically on any chain, and access-key nonces are chain-local state that can be identical across two independently-running networks that share account/key/nonce state (e.g., a network stood up by importing/dumping state or genesis from another live network — nearcore ships tooling for exactly this, such as the genesis/state dump utilities in `genesis-tools/genesis-populate` and `tools/state-viewer`, and the `tools/mirror` transaction-mirroring tool, which explicitly re-signs and forwards `DelegateAction`/`DelegateActionV2` payloads between networks, see `tools/mirror/src/genesis.rs`). By contrast, the *outer* `SignedTransaction` is protected because it commits to a recent `block_hash` that must be an ancestor in the local chain's `ChainStore`, so an outer transaction from chain A is provably useless on chain B: [7](#0-6) [8](#0-7) 

But that outer-transaction protection binds only the *relayer's* submission, not the *sender's* delegated authorization: any party who possesses a previously-observed `SignedDelegateAction` bytes can act as its own relayer, wrap it in a brand-new outer `SignedTransaction` (with a fresh, locally-valid `block_hash` for whichever network they are submitting to), and have it accepted by `apply_delegate_action` as long as that other network's access key state for the same `(sender_id, public_key)` has not yet advanced past `nonce` and the block height hasn't passed `max_block_height`. This is architecturally identical to the reported bug: the inner "authorization token" (the delegate signature) omits any network-binding value, relying only on a counter (nonce) and an expiry (`max_block_height`) — precisely the two fields the Term Finance report calls insufficient, and precisely why NEP-483-style recommendations (chain id in the signed payload) exist.

### Impact Explanation
If two live NEAR networks ever share account/access-key/nonce state for a given account (e.g., a network forked or bootstrapped from another network's genesis/state export, a rolled-back/forked chain that later diverges, or state-mirroring/replay tooling), a `SignedDelegateAction` a user signed and gave to a relayer for execution on network A could be resubmitted verbatim by anyone (not necessarily the original relayer) as the relayer on network B. Since `apply_delegate_action` charges the *relayer's* prepaid gas/deposit and credits/executes the delegated actions against the sender's account on that receiving network, the delegated action (e.g., a `Transfer`, `FunctionCall` moving tokens, or `AddKey`) executes a second time against independently-existing balances/state on network B without the sender ever intending or re-authorizing that second execution — a double-spend/double-execution of a signed authorization across networks, matching the "double-spend/replay" accepted-impact category.

### Likelihood Explanation
This requires a specific but realistic precondition: two networks sharing identical `(sender_id, public_key, access_key.nonce)` state, which nearcore's own tooling (genesis/state dump-and-import in `genesis-tools/genesis-populate`, `tools/state-viewer`) and mirroring infrastructure (`tools/mirror`, which itself explicitly re-signs `DelegateAction`/`DelegateActionV2` for forwarding to another chain) are designed to produce. It does not require any validator misbehavior, and it is reachable purely from an ordinary client-signed `SignedDelegateAction` plus any third party acting as relayer — no privileged position is needed to *replay* the token once such a dual-network condition exists. The likelihood is lower than a same-chain bug because it depends on operational practices (forking/mirroring/importing state) rather than being exploitable on a single canonical mainnet in isolation, but the tooling to create such conditions is part of the shipped codebase.

### Recommendation
Bind the `DelegateAction` signature to the destination network, mirroring the fix already applied for the analogous "auth token" bug in the referenced report and consistent with the outer transaction's own protection: include a genesis/chain identifier (e.g. `genesis_id`/`chain_id` as already tracked by `EpochManager`/genesis config) in the NEP-461 signed payload (`SignableMessage`) alongside `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, and `public_key`, and validate it in `apply_delegate_action` against the executing chain's own genesis/network id before accepting the delegate action.

### Proof of Concept
Conceptual (cannot be executed without a live multi-network testbed, which is outside this read-only analysis):
1. Network A and Network B are both booted from the same genesis/state export, so account `alice.near` has the same full-access key and the same `access_key.nonce` on both.
2. Alice signs `DelegateAction{ sender_id: alice.near, receiver_id: bob.near, actions: [Transfer(1000)], nonce: N+1, max_block_height: H, public_key: alice_pk }` and hands the resulting `SignedDelegateAction` to Relayer1 for execution on Network A only, per `SignedDelegateAction::sign` in `core/primitives/src/action/delegate.rs:92-95`.
3. Relayer1 wraps it in an outer `SignedTransaction` (with Network A's current `block_hash`) and submits on Network A; `apply_delegate_action`/`validate_delegate_action_key` accepts it, transfers funds, and bumps Alice's access-key nonce to N+1 on Network A only (`runtime/runtime/src/actions.rs:458-639`).
4. Any observer of that `SignedDelegateAction` (e.g., Relayer2, unrelated to Alice) wraps the *same, unmodified* `SignedDelegateAction` bytes in a new outer `SignedTransaction` addressed at Network B (using a fresh, locally valid `block_hash` for Network B, since block hashes are per-network) and submits it there.
5. Because Network B's access key nonce for `(alice.near, alice_pk)` is still N (never advanced, per its independent state), and `max_block_height` H is still in Network B's future, `validate_delegate_action_key` on Network B accepts the same signature and re-executes the `Transfer(1000)` against Alice's independent balance on Network B — a second, unauthorized execution of the same signed delegation.

    // a gas key nonce advances one of the gas key's nonces selected by
    // nonce_index.
    let delegate_nonce = delegate_action.nonce();
    let (current_nonce, nonce_update) = match delegate_nonce {
        TransactionNonce::Nonce { .. } => {
            if access_key.gas_key_info().is_some() {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresNonGasKey,
                )
                .into());
                return Ok(());
            }
            (access_key.nonce, DelegateNonceUpdate::AccessKey)
        }
        TransactionNonce::GasKeyNonce { nonce_index, .. } => {
            let Some(gas_key_info) = access_key.gas_key_info() else {
                result.result = Err(ActionErrorKind::DelegateActionAccessKeyError(
                    InvalidAccessKeyError::DelegateActionRequiresGasKey,
                )
                .into());
                return Ok(());
            };
            if nonce_index >= gas_key_info.num_nonces {
                result.result = Err(ActionErrorKind::DelegateActionInvalidNonceIndex {
                    nonce_index,
                    num_nonces: gas_key_info.num_nonces,
                }
                .into());
                return Ok(());
            }
            // The index is range-checked above and gas keys initialize every
            // nonce row at creation, so a missing row is inconsistent state.
            let current_nonce =
                get_gas_key_nonce(state_update, sender_id, public_key, nonce_index)?.ok_or_else(
                    || {
                        StorageError::StorageInconsistentState(format!(
                            "gas key nonce row missing for {} {} at in-range index {nonce_index} (num_nonces {})",
                            sender_id, public_key, gas_key_info.num_nonces,
                        ))
                    },
                )?;
            (current_nonce, DelegateNonceUpdate::GasKey { nonce_index })
        }
    };

    if delegate_nonce.nonce() <= current_nonce {
        result.result = Err(ActionErrorKind::DelegateActionInvalidNonce {
            delegate_nonce: delegate_nonce.nonce(),
            ak_nonce: current_nonce,
        }
        .into());
        return Ok(());

/// Transaction validity period check used in early prepare transactions. It's different from the
/// standard `check_transaction_validity_period` because early transaction preparation doesn't know
/// what the previous block hash is, it only knows the one before that. Normal validity check uses
/// `prev_block_header`, which is the previous block before the one which will contain the
/// transactions. This check uses `prev_prev_block_header`, which is the block before the previous
/// block and the same height as the normal check.
pub fn early_prepare_txs_check_validity_period(
    chain_store: &ChainStoreAdapter,
    prev_block_height: BlockHeight,
    prev_prev_block_header: &BlockHeader,
    base_block_hash: &CryptoHash,
    transaction_validity_period: BlockHeightDelta,
) -> Result<(), InvalidTxError> {
    let base_header =
        chain_store.get_block_header(base_block_hash).map_err(|_| InvalidTxError::Expired)?;

    metrics::CHAIN_VALIDITY_PERIOD_CHECK_DELAY
        .observe(prev_block_height.saturating_sub(base_header.height()) as f64);

    // First check the distance between blocks
    if prev_block_height > base_header.height() + transaction_validity_period {
        return Err(InvalidTxError::Expired);
    }

    // Then check if there is a path between the blocks (`base` is ancestor of `prev_prev`)
    validity_period_validate_is_ancestor(&base_header, prev_prev_block_header, chain_store)
}
