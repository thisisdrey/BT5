### Title
Missing zero-address (null-address) check in `AccountPermissionUpdateActuator` permission-key validation permanently freezes account control - (File: `actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java`)

### Summary
`AccountPermissionUpdateActuator` lets any account holder update their `Owner`, `Witness`, and `Active` permissions via a signed `AccountPermissionUpdateContract`. The only address-format check performed on each permission key is `DecodeUtil.addressValid()` [2](#0-1) , which — as shown above — accepts a syntactically valid but all-zero-payload address (e.g. `0x41` followed by 20 zero bytes) as a "valid" key. There is no check rejecting the zero/null address, mirroring exactly the bug class described in the external report (setter functions accepting a zero address for a role that subsequently gates all future privileged operations).

### Finding Description
`checkPermission()` validates key count, weight, threshold, and format via `DecodeUtil.addressValid(key.getAddress().toByteArray())`, but never asserts that the address payload is non-zero [3](#0-2) . Because `Owner` permission is exactly the credential required to call `AccountPermissionUpdateContract` again (i.e. it is self-referential/"onlyOwner"-style, analogous to `onlyGov`), setting the `Owner` permission's sole key (or all keys, if threshold logic allows) to the zero address is accepted by `validate()` and committed by `execute()` via `account.updatePermissions(...)` [4](#0-3) . Once committed, no signature can ever satisfy that owner permission again (nobody holds the private key for the zero address), so the account can never again update its permissions — the exact "locked contract" scenario the report describes for `setGov`.

### Impact Explanation
If the `Active` permission set (which gates transfers, freezing/voting, contract calls) is similarly nulled together with `Owner`, the account's funds (TRX, TRC10, frozen/staked balances) become permanently inaccessible — a permanent freezing of funds. Even if only `Owner` is zeroed, the account permanently loses the ability to ever rotate keys or recover from a later active-key compromise, which is a irreversible degradation of account security guarantees enforced on-chain.

### Likelihood Explanation
This is reachable by any unprivileged transaction broadcaster who controls an account: a single `AccountPermissionUpdateContract` transaction, or a wallet/dApp bug/UI error that fills in an empty/default address, is sufficient to trigger it — `multiSign` just needs to be enabled (`AllowMultiSign == 1`), which is a chain parameter, not a per-user privilege [5](#0-4) . No special role or witness/committee privilege is required.

### Recommendation
In `checkPermission()`, after validating `DecodeUtil.addressValid(...)`, add an explicit check that the address bytes (excluding the prefix byte) are not all-zero, and reject such keys with a `ContractValidateException`, exactly as recommended in the referenced report for `setGov`/`setGmxVaultPriceFeed`/`setSecondaryPriceFeed`.

### Proof of Concept
1. Attacker (or a buggy signer/wallet) constructs an `AccountPermissionUpdateContract` for their own `ownerAddress`, setting the `Owner` permission's single key to `ByteString` = `{addressPreFixByte, 0,0,...,0}` (20 zero bytes) with weight ≥ threshold.
2. Submit the signed transaction. `validate()` passes because `DecodeUtil.addressValid` only checks length/prefix [1](#0-0) .
3. `execute()` calls `account.updatePermissions(...)`, persisting the zero-address owner key [4](#0-3) .
4. No further `AccountPermissionUpdateContract` from this account can ever be validated by a real signature, since the owner permission threshold can never be met (nobody holds the zero address's key) — the account's permission state, and any funds gated behind an equally-nulled active permission, are permanently frozen.

      return false;

      return false;
    }
    return true;
