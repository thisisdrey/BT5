### Title
Pack-objects concurrency limiting can be fully bypassed by spoofing a loopback `remote_ip` value - ([File: internal/gitaly/service/hook/pack_objects.go])

### Summary
Gitaly's pack-objects concurrency limiter is keyed on `RemoteIp`, `Repository`, and `User`, but the limiter is skipped entirely whenever the parsed `RemoteIp` resolves to a loopback address. Since `RemoteIp` is client-influenced data that flows through the hook payload rather than being derived from a verified transport-layer peer address, a caller can set this value to a loopback address and have every pack-objects invocation for that user/repo run outside of the concurrency limiter, defeating the limit entirely.

### Finding Description
The pack-objects hook builds a cache/limiter key and, before invoking the actual limiter, special-cases loopback addresses: [1](#0-0) 

```go
servedBytes, created, err := s.packObjectsCache.Fetch(ctx, cacheKey, output, func(w io.Writer) error {
    ipAddr := net.ParseIP(req.GetRemoteIp())
    ...
    // Ignore loop-back IPs
    if ipAddr != nil && !ipAddr.IsLoopback() {
        return s.runPackObjectsLimited(ctx, w, ipAddr.String(), req, args, stdin, cacheKey)
    }
    return s.runPackObjects(ctx, w, req, args, stdin, cacheKey)
})
```

`runPackObjects` executes `git-pack-objects` directly, with **no concurrency limiting at all**, whereas `runPackObjectsLimited` funnels the call through `s.packObjectsLimiter.Limit(...)`: [2](#0-1) 

The `RemoteIp` field is documented as "the original IP of the initiator of the fetch. This field is used as the key for concurrency limiting": [3](#0-2) 

This value is not derived from an authenticated transport-layer peer address inside Gitaly's own process; it is threaded through the `HooksPayload`/gRPC metadata from the original RPC context down to `gitaly-hooks`, which forwards it verbatim into `PackObjectsHookWithSidechannelRequest.RemoteIp`: [4](#0-3) 

The existing test suite confirms the exact bypass behavior — loopback values (`127.0.0.1`, `::1`) and unparsable/empty strings all result in `shouldLimit: false`, i.e., no limiting applied, whereas any normal IP (with or without a port) is limited: [5](#0-4) 

This mirrors the reported bug class: a resource/quota-style restriction (`maxAllocationPerUser`-equivalent here is "one pack-objects invocation in flight per identity key") is enforced only when a client-supplied identifying value takes a "normal" shape. By supplying a value that falls into the excluded/degenerate category (loopback, or any string that fails IP parsing, or an empty string), the restriction is skipped altogether — analogous to how the token-sale bug bypassed a per-transaction cap by manipulating inputs so the accumulation/keying logic never saw the "real" cumulative state.

### Impact Explanation
An attacker who can influence the `remote_ip` metadata seen by Gitaly's hook (or who connects through a path where this metadata is not trustworthy/verified) can force every one of their pack-objects (fetch/clone) requests to bypass the concurrency limiter entirely. This allows them to spawn an unbounded number of concurrent `git-pack-objects` processes against a repository, consuming CPU/memory/disk I/O without the throttling that is meant to protect the Gitaly node — a DoS of the pack-objects RPC handler, potentially degrading Gitaly for all other users sharing the node.

### Likelihood Explanation
The likelihood depends on how strictly the `remote_ip` value is validated/overwritten before reaching Gitaly's hook service. In the standard GitLab deployment, Workhorse/Rails are expected to populate this value from the real connecting client IP, and it is not clear from the code available here whether Gitaly (or the intermediate `gitaly-hooks` process) independently validates that this value corresponds to the actual peer. Because the field is plumbed through generic metadata/env-based payload propagation rather than pulled from a verified `net.Conn` peer address at the limiter site itself, likelihood is best assessed as "plausible but unverified" without confirming the full trust chain from the original gRPC request context through to `HooksPayload.UserDetails.RemoteIP`.

### Recommendation
Do not rely on trusting a caller-suppliable string for the concurrency-limiting key. Either:
- Derive the limiting key from a value that Gitaly itself can independently verify (e.g., the actual authenticated connection/session identity), or
- Remove the loopback carve-out, or restrict it to only apply when it can be proven the request truly originated from Gitaly's own loopback interface (not merely because the string parses as `127.0.0.1`/`::1`), or
- Fall back to a conservative default (e.g., apply the limiter using `Repository`+`User` only) whenever `RemoteIp` is unparsable/loopback/empty, instead of skipping limiting altogether.

### Proof of Concept
Based on the existing unit test `TestPackObjects_concurrencyLimit` in `internal/gitaly/service/hook/pack_objects_test.go`, the bypass is already demonstrated by the `"IPv4 loopback addresses"`, `"IPv6 loopback addresses"`, `"invalid IP addresses"`, and `"empty IP addresses"` sub-tests, all of which assert `shouldLimit: false` — meaning two concurrent `PackObjectsHookWithSidechannel` calls sharing the same `GlId`/`Repository` but a loopback/invalid/empty `RemoteIp` are **not** subject to the concurrency limiter, unlike the `"normal IP address"` case which is limited: [6](#0-5) 

Sending repeated `PackObjectsHookWithSidechannelRequest` messages with `RemoteIp` set to `"127.0.0.1"` (or any unparsable string) while keeping `GlId`/`Repository` fixed will reproduce unlimited concurrent `git-pack-objects` invocations against the same repository.

func (s *server) runPackObjectsLimited(
	ctx context.Context,
	w io.Writer,
	limitkey string,
	req *gitalypb.PackObjectsHookWithSidechannelRequest,
	args *packObjectsArgs,
	stdin io.ReadCloser,
	key string,
) error {
	ctx = context.WithoutCancel(ctx)

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	defer stdin.Close()

	if _, err := s.packObjectsLimiter.Limit(
		ctx,
		limitkey,
		func() (interface{}, error) {
			return nil,
				s.runPackObjectsFn(
					ctx,
					s.gitCmdFactory,
					w,
					req,
					args,
					stdin,
					key,
				)
		},
	); err != nil {
		return err
	}

	return nil
}
