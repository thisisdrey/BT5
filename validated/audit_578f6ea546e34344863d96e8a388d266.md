### Title
Integer truncation of `LIQ-CURVE-EXP` in `calc-liq-factor-exp` silently applies the wrong graduated-liquidation curve, allowing more collateral to be seized than the configured curve intends - ([File: mainnet/contracts/market/v0-4-market.clar])

### Summary
`calc-liq-factor-exp` truncates `LIQ-CURVE-EXP` (a BPS-scaled exponent, e.g. `10000` = 1.0x per `docs/egroups.md`) via integer division `(/ exp BPS)` before raising `factor` to that power. Any configured exponent that is not an exact multiple of `10000` (e.g. `15000` = 1.5x, `12500` = 1.25x) is silently rounded down to the nearest integer multiplier, producing a systematically wrong (less aggressive) curve result that is then used unchecked in the liquidation-penalty and max-debt-to-liquidate calculations — the same class of "unscaled/truncated ratio silently corrupting a downstream fee/penalty calculation" as the referenced `AprPremium` finding.

### Finding Description
`calc-liq-factor-exp` is:
```clarity
(define-private (calc-liq-factor-exp (factor uint) (exp uint))
  (if (is-eq exp BPS) 
    factor
    (if (> exp BPS) 
        (/ (pow factor (/ exp BPS)) (pow BPS (- (/ exp BPS) u1)))
        (sqrti (* factor BPS))))) ;; assume factor^0.5
``` [1](#0-0) 

Per `docs/egroups.md`, `LIQ-CURVE-EXP` is a BPS-scale value where `10000` = 1.0 (linear), `>10000` = aggressive curve, `<10000` = gentle curve, with no restriction to exact multiples of `10000`: [2](#0-1) 

For the `exp > BPS` branch, `(/ exp BPS)` is Clarity integer division, so any exponent that is not an exact multiple of `BPS` (`10000`) is floored: e.g. `15000` (intended 1.5x) collapses to `1`, i.e. the same result as the linear case (`exp = BPS`), and `25000` (intended 2.5x) collapses to `2` instead of the intended fractional power. This mirrors the `AprPremium` root cause exactly: a ratio/exponent that must remain in a consistent fixed-point scale is divided down before being consumed, silently truncating precision and producing a value that is processed as valid without any revert or bound check.

For the `exp < BPS` branch, the code ignores the actual configured value entirely and always applies `sqrti` (i.e., always exactly a 0.5 exponent), regardless of whether the DAO configured `3000`, `5000`, or `9000` — compounding the mis-scaling problem for "gentle curve" configurations.

The truncated/hardcoded result (`liq-pct-scaled`) is fed directly into `calc-liq-factor-bound` (penalty scaling) and `calc-liq-debt-repay` (max liquidatable debt), which in turn drive `process-collateral-asset`'s `coll-usd-expected` via `calc-liq-collateral-repay`: [3](#0-2) [4](#0-3) 

Because `factor` (`liq-pct-linear`) is always `<= BPS` (i.e., a fraction `<=1`), truncating a fractional exponent `>BPS` down to a smaller integer power makes `factor^floor(exp/BPS)` **larger** than the mathematically intended `factor^(exp/BPS)` would be, which increases the resulting `liq-pct-scaled`, and therefore increases both `max-debt-usd` (via `calc-liq-debt-repay`) and `liq-penalty` (via `calc-liq-factor-bound`) beyond what the configured curve intends — permitting liquidators to extract more collateral/bonus from a borrower's position than the DAO-configured graduated curve was designed to allow, for any position not exactly at the linear/integer-multiple boundary.

### Impact Explanation
This directly affects fund flows during liquidation: the amount of debt eligible to be repaid and the collateral+bonus a liquidator can seize (`calc-liq-collateral-repay`, executed via `market-vault collateral-remove`) are computed from a silently mis-scaled curve value. This results in the liquidator being permitted to seize more of the borrower's collateral than the intended graduated-liquidation design allows, i.e., an unintended/excess transfer of borrower funds during an otherwise normal liquidation call — this constitutes direct loss of user funds at rest (collateral) beyond the amount the risk parameters were meant to allow, landing in the Critical/High impact classes for direct fund loss from a calculation bug in the liquidation path.

### Likelihood Explanation
The bug fires for any egroup whose `LIQ-CURVE-EXP` is not an exact multiple of `10000` and not exactly `10000` — a value explicitly presented in the docs as a continuous BPS-scaled exponent (not restricted to exact multiples), so this is a plausible, legitimate DAO configuration rather than a misuse of the parameter. Once such an egroup exists, the bug triggers automatically on every `liquidate` call against any unhealthy position in that egroup — a fully unprivileged, ordinary market-entry-point interaction, with no attacker action needed beyond calling the standard liquidation function.

### Recommendation
Reject fractional (non-exact-multiple) `LIQ-CURVE-EXP` values at the point they are validated/stored (or explicitly document and enforce that only exact multiples of `BPS` are supported), or replace the integer-`pow`-based approximation with a fixed-point exponentiation routine (e.g., a proper `ln`/`exp` based power function or a lookup/interpolation table) that correctly honors the full BPS-scale exponent without truncation, matching the documented "curve" semantics. Additionally, apply the actual configured `exp` value in the `exp < BPS` branch instead of hardcoding `sqrti`.

### Proof of Concept
1. DAO creates an egroup with `LIQ-CURVE-EXP = u15000` (1.5x aggressive curve, a value within the documented BPS range and not flagged as invalid anywhere in `egroup.clar`/`v0-egroup.clar`).
2. A borrower's position becomes liquidatable (`current-ltv >= ltv-liq-partial`).
3. Any address calls `liquidate` (unprivileged entry point). Internally `calc-liquidation-params` calls `calc-liq-factor-exp(liq-pct-linear, u15000)`:
   - `(/ u15000 BPS)` evaluates to `u1` (Clarity integer division truncates `1.5` to `1`).
   - The function executes the `exp > BPS` branch as `(/ (pow factor u1) (pow BPS u0))` = `factor`, i.e., identical to the `exp = BPS` (linear, 1.0x) case, discarding the configured 1.5x aggressiveness entirely.
4. `liq-pct-scaled` is therefore higher than the correctly-computed 1.5x-curve value would be (since `factor <= BPS` and raising a fraction to a higher power shrinks it), inflating `max-debt-usd` and `liq-penalty`.
5. `process-collateral-asset`/`calc-liq-collateral-repay` compute a larger `coll-usd-expected` bonus than the DAO's configured curve intended, and this larger amount is transferred to the liquidator via `market-vault collateral-remove`, all without any revert — the mis-scaled value is silently "processed as valid," exactly analogous to the referenced `AprPremium` precision-loss defect.

  (current-ltv uint)
  (ltv-liq-partial uint)
  (ltv-liq-full uint)
  (liq-penalty-min uint)
  (liq-penalty-max uint)

**Graduated Liquidation:**

The `LIQ-CURVE-EXP` parameter controls how liquidation penalty scales between min and max:
- `10000` (1.0): Linear scaling
- `>10000` (>1.0): Aggressive curve (penalty increases faster)
- `<10000` (<1.0): Gentle curve (e.g., square root)
