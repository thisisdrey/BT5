## Finding

### Title
Division-by-zero / silent-corruption in energy limit calculation when `allowNewReward` is not enabled - ([File: chainbase/src/main/java/org/tron/core/db/EnergyProcessor.java])

### Summary
`EnergyProcessor.calculateGlobalEnergyLimit()` only guards against `totalEnergyWeight <= 0` when the chain-parameter feature `allowNewReward()` is enabled. When that flag is not enabled, the method falls back to a Java `assert` statement instead of an actual runtime check, and then unconditionally divides by `totalEnergyWeight`, exactly mirroring the analog UFS bug class ("prevent a division by 0 when monitoring is not enabled").

### Finding Description
```java
long totalEnergyWeight = dynamicPropertiesStore.getTotalEnergyWeight();
if (dynamicPropertiesStore.allowNewReward() && totalEnergyWeight <= 0) {
  return 0;
} else {
  assert totalEnergyWeight > 0;
}
if (hardenCalculation()) {
  return calculateGlobalLimitV1(frozeBalance, totalEnergyLimit, totalEnergyWeight);
}
long energyWeight = frozeBalance / TRX_PRECISION;
return (long) (energyWeight * ((double) totalEnergyLimit / totalEnergyWeight));
``` [1](#0-0) 

The `assert` statement is a no-op in a normally-run production JVM (Java assertions are disabled by default unless started with `-ea`), so when `allowNewReward()` is `false` and `totalEnergyWeight` is `0`, execution proceeds past the guard. Two outcomes are then possible:
- If `hardenCalculation()` (`allowHardenResourceCalculation`) is enabled, `calculateGlobalLimitV1` performs a `BigInteger` division by `totalEnergyWeight`, which is a genuine `ArithmeticException: BigInteger divide by zero`, matching `RepositoryImpl.calculateGlobalEnergyLimit`'s equivalent BigInteger division pattern that is documented to throw on zero denominator [2](#0-1) .
- If hardening is disabled (legacy double-math path, the historical default), the division `(double) totalEnergyLimit / totalEnergyWeight` yields `Infinity`/`NaN` rather than throwing, silently corrupting the computed energy limit for the account.

The companion V2 path (`calculateGlobalEnergyLimitV2`), used once `supportUnfreezeDelay()` is active, does correctly special-case `totalEnergyWeight == 0` unconditionally [3](#0-2) , confirming that the guard in the V1 (legacy) method was intended to be unconditional but was instead gated behind `allowNewReward()`.

`calculateGlobalEnergyLimit` is invoked from `useEnergy()` — the routine that accounts for TVM contract-call energy on every transaction that touches a smart contract [4](#0-3)  — and from the unauthenticated `GetAccountResource` query path in `Wallet.getAccountResource` [5](#0-4) .

### Impact Explanation
If reached with the hardened calculation path enabled, an uncaught `ArithmeticException` in the middle of transaction/block-level energy accounting or in a widely-used query RPC could crash the request handler or destabilize block application. Even in the non-hardened path, corrupting `energyLimit` to `Infinity`/`NaN`/`0` produces incorrect resource accounting (over- or under-granting energy), which can enable resource-limit bypass or unwarranted denial of contract execution.

### Likelihood Explanation
This code path is only reachable on the legacy branch (`!supportUnfreezeDelay()`), which is used on chains/networks that have not yet activated the "Unfreeze Delay" hard fork feature, combined with `allowNewReward()` being disabled and `totalEnergyWeight` being exactly `0` while some account's `getAllFrozenBalanceForEnergy()` is still `>= TRX_PRECISION`. I was **not able to conclusively confirm**, within the available investigation, a concrete unprivileged transaction sequence that forces `totalEnergyWeight` to `0` while an account retains a qualifying frozen-for-energy balance under normal, correctly-functioning freeze/unfreeze bookkeeping — this would require either a chain-parameter misconfiguration/feature-flag state controlled by committee/SR (out of scope per the rules) or a latent accounting-drift bug in `addTotalEnergyWeight`/`FreezeBalanceV2Actuator` bookkeeping that I did not have iterations left to fully trace.

### Recommendation
Make the `totalEnergyWeight <= 0` (and analogous `totalNetWeight <= 0`, see `BandwidthProcessor`) checks unconditional (remove dependency on `allowNewReward()`), and replace the `assert` with an explicit runtime guard that returns `0` (or otherwise safely short-circuits) regardless of production JVM assertion settings, mirroring the already-correct `calculateGlobalEnergyLimitV2` guard.

### Proof of Concept
Not fully constructible without confirming the precondition above; conceptually:
1. Operate/observe a chain where `supportUnfreezeDelay()` is false and `allowNewReward()` is false.
2. Drive `dynamicPropertiesStore.totalEnergyWeight` to `0` while an account's `getAllFrozenBalanceForEnergy() >= TRX_PRECISION` (mechanism unconfirmed).
3. Call any contract-invoking transaction (triggers `useEnergy` → `calculateGlobalEnergyLimit`) or call the `GetAccountResource` RPC for that account.
4. With `allowHardenResourceCalculation` enabled, observe `ArithmeticException`; otherwise observe corrupted (`Infinity`/`NaN`-derived) energy limit.

Given the unverified precondition, this should be treated as a **defense-in-depth code defect** requiring further investigation (ideally with full repository/terminal access) into the exact bookkeeping of `totalEnergyWeight` versus per-account frozen-energy balances before it can be confirmed as independently, unprivileged-reachable.
