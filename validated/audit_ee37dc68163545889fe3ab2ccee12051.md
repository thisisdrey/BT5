### Title
Unbounded reference-update loop in `UpdateReferences` enables push-triggered denial of service - ([File: internal/gitaly/service/ref/update_references.go])

### Summary
The `UpdateReferences` RPC accepts a client-controlled, unbounded stream of reference-update batches and iterates over every update in every batch without any cap on the total number of updates, references, or streamed messages accepted in a single call.

### Finding Description
`UpdateReferences` reads a stream of `UpdateReferencesRequest` messages in an unbounded `for {}` loop, and for each message it loops over `request.GetUpdates()` with no upper bound on the number of updates per message or the number of messages in the stream: [1](#0-0) 

Each individual update is validated (reference format, hex object IDs) and then queued onto the `updateref.Updater` via `updater.Update(...)`: [2](#0-1) 

There is no limit anywhere in this handler on: the number of `Recv()` iterations, the number of updates per request, or the cumulative number of queued reference updates before `updater.Commit()` is finally called. This mirrors the reported bug class: a per-iteration cost (validating a reference, validating two object IDs, and queuing a git-update-ref transaction line) is incurred for each attacker-supplied item in an attacker-controlled, effectively unbounded collection, exactly like the Uniswap `swap` loop iterating once per attacker-created tick/position.

An ordinary authenticated client (anyone who can call a `MUTATOR` RPC against a repository they have write access to) can drive this loop arbitrarily wide by streaming a very large number of `UpdateReferencesRequest` messages, each containing many `updates` entries (e.g., referencing many distinct `refs/...` names). Because gRPC streaming has no built-in cap on the number of messages in a client stream, and this handler applies none either, the number of loop iterations — and thus CPU/memory/IO cost incurred inside a single RPC handler goroutine and inside the underlying `git-update-ref --stdin` process — scales linearly (or worse, given `updateref.Updater`'s internal bookkeeping) with attacker-supplied input size, with no server-imposed ceiling.

### Impact Explanation
A malicious or compromised client with ordinary push/write access to a single repository can force a single `UpdateReferences` RPC invocation to process an extremely large number of reference updates, consuming outsized CPU, memory, and file-descriptor/process resources on the Gitaly node handling the request. Because the handler blocks in `updater.Commit()` at the end (after accumulating the entire unbounded update set), a sufficiently large stream can tie up the request goroutine and its child git process for a long time, degrading availability of the RPC handler (and, transitively, of the storage/repository) for other legitimate users — a resource-exhaustion DoS entirely analogous to the reported unbounded-loop swap DoS, where the cost accrual is per-attacker-supplied unit and there is no upper bound enforced by the target.

### Likelihood Explanation
This requires only an authenticated caller that can invoke a `MUTATOR` RPC against a repository (i.e., anyone with push/write access), not a privileged actor, malicious peer, or MITM. No token leakage, no dependency compromise, and no test-only conditions are needed — a single crafted streaming RPC call from an ordinary client is sufficient, making this readily reachable from a normal user-driven code path (as opposed to requiring node-level or admin privileges).

### Recommendation
Enforce hard limits in `UpdateReferences` (and any other RPC that consumes attacker-controlled streamed collections without limits), such as: a maximum number of updates accepted per RPC call, a maximum number of stream messages, and/or a maximum aggregate payload size, returning a structured `ResourceExhausted`/`InvalidArgument` error once the limit is exceeded. Complement this with existing concurrency-limiting mechanisms (`[[concurrency]]` queue limits) tuned specifically for this RPC, and document the enforced bounds so operators can reason about worst-case per-call cost.

### Proof of Concept
1. As an authenticated user with write access to a repository, open a bidi stream to `UpdateReferences`.
2. Send a very large number of `UpdateReferencesRequest` messages (or one message with an extremely large `updates` array), each containing valid but distinct reference names (e.g., `refs/heads/attack-<n>`) and valid object IDs, without ever sending EOF.
3. Observe that the server accumulates all updates in the `for` loop at `internal/gitaly/service/ref/update_references.go:47-88` before calling `updater.Commit()`, with CPU/memory usage on the Gitaly node scaling with the number of updates supplied, and no error returned for exceeding any size/count limit — because no such limit exists in the handler.
