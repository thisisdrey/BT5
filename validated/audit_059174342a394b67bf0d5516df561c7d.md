### Title
Reachable `assert!(preamble.payload_len > 5)` panic in `validate_blocks_push`/`validate_microblocks_push` on attacker-controlled preamble field - ([File: stackslib/src/net/chat.rs])

### Summary
`ConversationP2P::validate_microblocks_push` and `validate_blocks_push` both begin with a hard `assert!` on `preamble.payload_len`, a field fully controlled by the remote peer that sent the message. Because the framing layer only bounds `payload_len` from above (to cap how many bytes are read off the wire) and does not enforce it is `> 5` before dispatching to these validators, a peer that sends a `StacksMessageType::Blocks` or `StacksMessageType::Microblocks` message whose payload decodes successfully but whose `payload_len` is `<= 5` reaches the assert and panics the connection-handling thread.

### Finding Description
Both validators open with the same pattern: [1](#0-0) [2](#0-1) 

```
assert!(preamble.payload_len > 5); // don't count 1-byte type prefix + 4 byte vector length
```

This assert encodes an assumption that has never been enforced at deserialization time: that any successfully-parsed `Blocks`/`Microblocks` payload must be strictly larger than the minimal empty-vector encoding (1-byte enum discriminant + 4-byte zero-length vector count = 5 bytes). `preamble.payload_len` is a plain `u32` read directly off the wire in the message preamble and is used by the framing/`read_payload` logic purely as an upper bound on how many bytes to read for the relayers+payload blob; nothing lower-bounds it against the minimum size required to encode a non-empty `Vec<StacksBlock>`/`Vec<StacksMicroblock>`, and nothing re-derives it from the actually-decoded payload size before `validate_blocks_push`/`validate_microblocks_push` is invoked in the dispatch path for these message types. A remote, already-authenticated (handshaked) peer can therefore send a `StacksMessage` with `StacksMessageType::Blocks`/`Microblocks` carrying an empty vector and a `preamble.payload_len` that legitimately reflects that small (`<=5`-adjacent) payload; once `read_payload` successfully decodes it, control reaches the assert with `payload_len <= 5`, and the Rust `assert!` panics the thread instead of the function returning `Err(net_error::InvalidMessage)` as the surrounding error-handling convention (used everywhere else in these same functions, e.g. `process_relayers` returning `net_error::InvalidMessage`) would suggest is the intended behavior.

Nothing in the surrounding code guards against this: `process_relayers` is only called *after* the assert, `MAX_MESSAGE_LEN`/framing caps only bound the maximum size, and there is no minimum-payload check performed prior to calling into these validators for `Blocks`/`Microblocks` message types.

### Impact Explanation
A single crafted `StacksMessage` from any already-connected/handshaked peer causes an `assert!` panic in the thread handling that peer's P2P conversation, aborting the process (Rust's default panic behavior in a non-`catch_unwind`-wrapped context) or at minimum crashing that connection's processing loop. This is a remote, single-message crash triggerable repeatedly against any node that accepts inbound handshakes or against any peer a malicious node connects to, matching the "Critical - remote crash/unauthenticated DoS from few messages" category once authentication (handshake) is completed, which any remote unprivileged attacker can perform.

### Likelihood Explanation
The precondition is only that the attacker complete a normal P2P handshake (available to any remote party who can connect to the P2P port — no secret, no privileged role, no StackerDB slot needed) and then send one `Blocks`/`Microblocks` push message with an empty vector payload. The cost is a single crafted message; the attack is trivially repeatable against the same or other nodes.

### Recommendation
Replace the `assert!(preamble.payload_len > 5)` checks in `validate_blocks_push` and `validate_microblocks_push` (and the analogous `assert!(preamble.payload_len > 1)` in `validate_transaction_push`) with a proper runtime check that returns `Err(net_error::InvalidMessage)` (or triggers `reply_nack`) when the condition is not met, consistent with how `process_relayers` failures are already handled in the same functions.

### Proof of Concept
Add a unit test in `stackslib/src/net/chat.rs`'s test module that constructs a `ConversationP2P` in a state past handshake, builds a `Preamble` with `payload_len` set to `5` (or less) and a `relayers: Vec<RelayData>::new()`, and calls `conversation.validate_microblocks_push(&network, &preamble, relayers)` directly. Confirm that in the current code this panics (assert failure) rather than returning `Ok`/`Err(net_error::InvalidMessage)`, demonstrating the reachable panic; then verify the same for `validate_blocks_push` with `payload_len <= 5`.
