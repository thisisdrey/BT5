### Title
Unbounded Server-Side Blocking on Attacker-Controlled Push RPCs (`SSHReceivePack` / `PostReceivePack`) Enables Resource-Exhaustion DoS - ([File: internal/gitaly/service/ssh/receive_pack.go], [File: internal/gitaly/service/smarthttp/receive_pack.go])

### Summary
Gitaly's fetch-side RPCs (`SSHUploadPackWithSidechannel`, `SSHUploadArchive`) are explicitly hardened against "slow/incomplete request" attacks with a negotiation timeout ticker that aborts the RPC if the client stalls before sending the terminating packet [1](#0-0) . The push-side RPCs `SSHReceivePack` and `PostReceivePack`, however, have no equivalent timeout: they read the first message, spawn `git receive-pack`, and then block on `cmd.Wait()` with no deadline tied to client input activity [2](#0-1) [3](#0-2) . This is the analog of the reported "unfinished request" DoS class: an ordinary/unprivileged authenticated user can open a push and simply never (or extremely slowly) send further stdin, tying up a goroutine, an `exec.Cmd` process, and pipe resources indefinitely, since neither gRPC keepalive settings nor any per-RPC negotiation timeout bound this idle period.

### Finding Description
`SSHReceivePack` reads the first request (repository/GlId) and then reads subsequent `Stdin` chunks via a `streamio.Reader`, feeding them into a pipe that is the stdin of the spawned `git receive-pack` process [4](#0-3) . The RPC handler then calls `cmd.Wait()`, which blocks until `git receive-pack` exits [2](#0-1) . `git receive-pack` will not exit until it either receives a flush/terminating pktline sequence or its stdin reaches EOF. If a client sends the first message and then withholds further data (or trickles it at a rate designed to avoid idle-socket detection), `cmd.Wait()` blocks indefinitely.

The exact same pattern exists for `PostReceivePack` in the SmartHTTP service: `stdin` is wired directly from the client stream into `git receive-pack --stateless-rpc`, and `cmd.Wait()` blocks with no timeout [5](#0-4) .

By contrast, the fetch-path RPCs explicitly recognize and mitigate this exact bug class. `sshUploadPack` creates a `timeoutTicker := s.uploadPackRequestTimeoutTickerFactory()` and passes it into `runUploadCommand`, with an inline comment stating: *"upload-pack negotiation is terminated by either a flush, or the 'done' packet... Add a timeout to the second case to mitigate use-after-check attacks"* [6](#0-5) . `SSHUploadArchive` has an analogous `uploadArchiveRequestTimeoutTickerFactory`, backed by the configurable `cfg.Timeout.UploadArchiveNegotiation` (default 1 minute) [7](#0-6) , and its DoS-mitigation behavior is directly covered by `TestFailedUploadArchiveRequestDueToTimeout`, which asserts the server aborts a stalled request with `DeadlineExceeded` rather than blocking forever [8](#0-7) . The same DoS scenario is proven exploitable-until-fixed for `SSHUploadPackWithSidechannel` in `testUploadPackWithSidechannelTimeout`, which explicitly comments: *"Because the client says nothing, the server would block. Because of the timeout, it won't block forever"* [9](#0-8) .

No equivalent ticker/timeout construct, config option, or test exists for `SSHReceivePack` or `PostReceivePack` — confirmed by the fact that the only matches for `RequestTimeoutTicker` in the codebase are in the `ssh` package's upload-pack/upload-archive server and tests, not in `receive_pack.go` for either SSH or SmartHTTP services.

The server-level gRPC `KeepaliveParams` only set `Time: 5 * time.Minute` (ping interval) with no `Timeout` value configured on the Gitaly gRPC server, and `KeepaliveEnforcementPolicy` only restricts how often *clients* may ping, which does nothing to bound an active-but-idle-body stream from the client's perspective [10](#0-9) . Because the stream is technically "active" (the RPC is in progress and gRPC itself has no data timeout), this is precisely the CVE-2020-8251 pattern: the transport layer has no application-level enforcement of forward progress on the request body once headers/first message are received.

### Impact Explanation
Each stalled push RPC keeps a goroutine blocked in `cmd.Wait()`, holds an OS process (`git receive-pack`) alive, and (per the code comment in `receive_pack.go` about `cmd.Stdin` goroutines) an additional `io.Copy` goroutine relaying stdin [11](#0-10) . An attacker with legitimate push access to any repository (even a low-privilege collaborator with push rights, or effectively any authenticated Gitaly client depending on deployment) can open many concurrent `SSHReceivePack`/`PostReceivePack` streams, send only the initial repository/GlId message, and never close or complete the stdin stream. Over time this exhausts Gitaly's process table, file descriptors, and concurrency-limiter slots (`MaxPerRepo`/`MaxQueueSize` in `limithandler`), denying service to legitimate git operations on the affected Gitaly node. Because `Concurrency`/limithandler limits are per-repo/per-RPC and the RPC is classified `MUTATOR` in `ssh.proto`/`smarthttp.proto` (not currently in any special negotiation-limited category), it does not inherently protect against many parallel stalled connections spread across different repositories.

### Likelihood Explanation
Likelihood is high for any environment where a user has push access (a routine, unprivileged operation, unlike a compromised token or MITM scenario). No special network position or credential is needed beyond ordinary push permission, which the "Rules" of the assessment explicitly keep in scope as an "ordinary user's push" vector. The attack requires no malformed protocol data — simply omitting/delaying the pktline body after the first gRPC message, which is indistinguishable from a slow network client until enough time has passed.

### Recommendation
Add an idle/negotiation timeout for `SSHReceivePack` and `PostReceivePack` analogous to the existing `uploadPackRequestTimeoutTickerFactory` / `uploadArchiveRequestTimeoutTickerFactory` mechanism: reset a ticker on every successful `stream.Recv()` of stdin data, and cancel the RPC's context (and thus `git receive-pack`) if no further pktline data arrives within a bounded window (e.g., a new `cfg.Timeout.ReceivePackNegotiation` mirroring `UploadArchiveNegotiation`). Ensure the ticker/timeout is wired through the goroutine that copies `stdin` into the process pipe, not just cmd.Wait(), consistent with the pattern in `upload_command.go`'s `runUploadCommand`.

### Proof of Concept
1. As an authenticated user with push rights to a repository, open an `SSHReceivePack` (or `PostReceivePack`) gRPC stream.
2. Send only the first request containing `Repository`/`GlId` (no `Stdin` payload), per validation in `validateFirstReceivePackRequest` [12](#0-11) .
3. Do not send any further messages and do not call `CloseSend()`; keep the underlying TCP/HTTP2 stream alive (well within the 5-minute keepalive ping interval, so no keepalive/idle mechanism fires).
4. Observe that the corresponding `git receive-pack` process on the Gitaly server remains running and the RPC handler goroutine remains blocked in `cmd.Wait()` indefinitely, unlike the analogous `SSHUploadPackWithSidechannel`/`SSHUploadArchive` case which is proven in existing tests to abort via `DeadlineExceeded` after the configured negotiation timeout [13](#0-12) .
5. Repeat across many concurrent connections/repositories to exhaust process/goroutine/fd resources on the Gitaly node.

func (s *server) sshReceivePack(stream gitalypb.SSHService_SSHReceivePackServer, req *gitalypb.SSHReceivePackRequest) (returnedErr error) {
	ctx := stream.Context()

	stdin := streamio.NewReader(func() ([]byte, error) {
		request, err := stream.Recv()
		return request.GetStdin(), err
	})

	var m sync.Mutex
	stdout := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.SSHReceivePackResponse{Stdout: p})
	})

	// We both need to listen in on the stderr stream in order to be able to judge what exactly
	// is happening, but also relay the output to the client. We thus create a MultiWriter to
	// enable both at the same time.
	var stderrBuilder strings.Builder
	stderr := streamio.NewSyncWriter(&m, func(p []byte) error {
		return stream.Send(&gitalypb.SSHReceivePackResponse{Stderr: p})
	})
	stderr = io.MultiWriter(&stderrBuilder, stderr)

	repoPath, err := s.locator.GetRepoPath(ctx, req.GetRepository())
	if err != nil {
		return err
	}

	config, err := gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())
	if err != nil {
		return err
	}

	// When an `exec.Cmd` has its `cmd.Stdin` configured with an `io.Reader`
	// that is not also of type `os.File` a goroutine is automatically
	// configured that performs an `io.Copy()` between the reader and a newly
	// created pipe. A problem with this can arise when `cmd.Wait()` is invoked
	// because it waits not only for the process to complete but also all the
	// goroutine to end. If the configured `cmd.Stdin` is only of type
	// `io.Reader` and never closed, the goroutine will never end. This leads to
	// `cmd.Wait()` being blocked indefinitely.
	//
	// Within Gitaly this problem can manifest itself when a git process crashes
	// before `stdin` reaches EOF. To date this has only been noticed as a
	// problem for the `SSHReceivePack` RPC, so a pipe and goroutine have been
	// created explicitly to prevent `cmd.Wait()` from blocking indefinitely.
	pr, pw, err := os.Pipe()
	if err != nil {
		return fmt.Errorf("creating pipe: %w", err)
	}

	if featureflag.ReceivePackStats.IsEnabled(ctx) {
		// Recording happens inside this goroutine rather than a deferred call
		// so the RPC never waits for stdin to drain: if the client never
		// closes stdin, the goroutine may outlive the RPC, as this pipe
		// already allows.
		statsCapture := &stats.PrefixCapture{}
		go func() {
			_, _ = io.Copy(io.MultiWriter(pw, statsCapture), stdin)
			_ = pw.Close()
			stats.RecordReceivePack(ctx, s.logger, statsCapture.Bytes(), s.receivePackObjectsMetrics)
		}()
	} else {
		go func() {
			_, _ = io.Copy(pw, stdin)
			_ = pw.Close()
		}()
	}

func (s *server) postReceivePack(
	stream gitalypb.SmartHTTPService_PostReceivePackServer,
	req *gitalypb.PostReceivePackRequest,
) (returnedErr error) {
	ctx := stream.Context()

	stdin := streamio.NewReader(func() ([]byte, error) {
		resp, err := stream.Recv()
		return resp.GetData(), err
	})

	if featureflag.ReceivePackStats.IsEnabled(ctx) {
		// The deferred call runs after cmd.Wait() has drained stdin, so the
		// capture is complete by the time it is read.
		statsCapture := &stats.PrefixCapture{}
		defer func() {
			stats.RecordReceivePack(ctx, s.logger, statsCapture.Bytes(), s.receivePackObjectsMetrics)
		}()
		stdin = io.TeeReader(stdin, statsCapture)
	}

	stdout := streamio.NewWriter(func(p []byte) error {
		return stream.Send(&gitalypb.PostReceivePackResponse{Data: p})
	})

	repo := s.localRepoFactory.Build(req.GetRepository())

	repoPath, err := repo.Path(ctx)
	if err != nil {
		return err
	}

	config, err := gitcmd.ConvertConfigOptions(req.GetGitConfigOptions())
	if err != nil {
		return err
	}

	transactionID := storage.ExtractTransactionID(ctx)
	transactionsEnabled := transactionID > 0
	if transactionsEnabled {
		procReceiveCleanup, err := receivepack.RegisterProcReceiveHook(
			ctx, s.logger, s.cfg, req, repo, s.hookManager, hook.NewTransactionRegistry(s.txRegistry), transactionID,
		)
		if err != nil {
			return err
		}
		defer func() {
			if err := procReceiveCleanup(); err != nil && returnedErr == nil {
				returnedErr = err
			}
		}()
	}

	objectHash, err := repo.ObjectHash(ctx)
	if err != nil {
		return fmt.Errorf("detecting object hash: %w", err)
	}

	cmd, err := repo.Exec(ctx,
		gitcmd.Command{
			Name:  "receive-pack",
			Flags: []gitcmd.Option{gitcmd.Flag{Name: "--stateless-rpc"}},
			Args:  []string{repoPath},
		},
		gitcmd.WithStdin(stdin),
		gitcmd.WithStdout(stdout),
		gitcmd.WithReceivePackHooks(objectHash, req, "http", transactionsEnabled),
		gitcmd.WithGitProtocol(s.logger, req),
		gitcmd.WithConfig(config...),
	)
	if err != nil {
		return structerr.NewFailedPrecondition("spawning receive-pack: %w", err)
	}

	if err := cmd.Wait(); err != nil {
		return structerr.NewFailedPrecondition("waiting for receive-pack: %w", err)
	}

func TestFailedUploadArchiveRequestDueToTimeout(t *testing.T) {
	t.Parallel()

	cfg := testcfg.Build(t)

	// Use a ticker channel so that we can observe that the ticker is being created. The channel
	// is unbuffered on purpose so that we can assert that it is getting created exactly at the
	// time we expect it to be.
	tickerCh := make(chan *helper.ManualTicker)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithArchiveRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			tickerCh <- ticker
			return ticker
		}),
	})

	ctx := testhelper.Context(t)
	repo, _ := gittest.CreateRepository(t, ctx, cfg)

	client := newSSHClient(t, cfg.SocketPath)

	stream, err := client.SSHUploadArchive(ctx)
	require.NoError(t, err)

	// The first request is not limited by timeout, but also not under attacker control
	require.NoError(t, stream.Send(&gitalypb.SSHUploadArchiveRequest{Repository: repo}))

	// We should now see that the ticker limiting the request is being created. We don't need to
	// use the ticker, but this statement is only there in order to verify that the ticker is
	// indeed getting created at the expected point in time.
	<-tickerCh

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	requireFailedSSHStream(t, structerr.NewDeadlineExceeded("running upload-archive: waiting for negotiation: context canceled"), func() (int32, error) {
		resp, err := stream.Recv()
		if err != nil {
			return 0, err
		}

		var code int32
		if status := resp.GetExitStatus(); status != nil {
			code = status.GetValue()
		}

		return code, nil
	})
}

func testUploadPackWithSidechannelTimeout(t *testing.T, ctx context.Context, opts ...testcfg.Option) {
	t.Parallel()

	cfg := testcfg.Build(t, opts...)

	cfg.SocketPath = runSSHServerWithOptions(t, cfg, []ServerOpt{
		WithUploadPackRequestTimeoutTickerFactory(func() helper.Ticker {
			// Create a ticker that will immediately tick when getting reset so that the
			// server-side can observe this as an emulated timeout.
			ticker := helper.NewManualTicker()
			ticker.ResetFunc = func() {
				ticker.Tick()
			}
			return ticker
		}),
	})

	repo, repoPath := gittest.CreateRepository(t, testhelper.Context(t), cfg)
	gittest.WriteCommit(t, cfg, repoPath, gittest.WithBranch("main"))

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	registry := sidechannel.NewRegistry()
	client := newSSHClientWithSidechannel(t, ctx, registry, cfg.SocketPath)

	ctx, waiter := sidechannel.RegisterSidechannel(ctx, registry, func(clientConn *sidechannel.ClientConn) (returnedErr error) {
		// Discard all data and block on the connection closing. The client says nothing
		// back to the server and doesn't finish the negotiation. This leads to the server
		// closing the connections once the negotiation timeout fires.
		_, err := io.Copy(io.Discard, clientConn)
		assert.NoError(t, err)
		return nil
	})
	defer testhelper.MustClose(t, waiter)

	_, err := client.SSHUploadPackWithSidechannel(ctx, &gitalypb.SSHUploadPackWithSidechannelRequest{
		Repository: repo,
	})

	// Because the client says nothing, the server would block. Because of
	// the timeout, it won't block forever, and return with a non-zero exit
	// code instead.
	testhelper.RequireGrpcError(t, structerr.NewDeadlineExceeded("running upload-pack: waiting for negotiation: context canceled"), err)
}
