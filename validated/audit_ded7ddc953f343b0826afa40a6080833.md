### Title
Unbounded Git commit/tag header field sizes (author, committer, encoding, parent, tag headers) cause repeated resource exhaustion on every catfile parse - ([File: internal/git/catfile/parser.go], [File: internal/git/catfile/parse_commit.go])

### Summary
Gitaly's commit/tag parser truncates only the commit/tag **body** to `helper.MaxCommitOrTagMessageSize` (10 KiB), but places no size limit on any of the header fields (`author`, `committer`, `encoding`, `tree`, `parent`, `tag`, `tagger`, and any unrecognized header line). An ordinary user who can push a commit/tag object into a repository can craft one with an arbitrarily large header line. Every subsequent RPC that reads that object through the catfile parser (`GetCommit`, `FindCommit`, `ListCommits`, `FindTag`, `FindAllBranches`, blame, etc.) will read the full oversized line into memory and, for known fields, return it unbounded in the gRPC response - this is the direct analog of the reported `Hats.uri`/`details`/`imageURI` unbounded-string DoS, where a single "expensive to write" resource becomes "expensive on every read."

### Finding Description
`ParseCommit` reads each header line with `p.bufferedReader.ReadString('\n')` [1](#0-0) . Go's `bufio.Reader.ReadString` has no maximum line length - if the delimiter is not found within the buffer it keeps growing an internal accumulation slice and re-filling from the underlying reader until the delimiter is seen, so an extremely long header line (many MB) is fully materialized in memory in one call.

Unlike the commit body, which is explicitly truncated: [2](#0-1) 

none of the header fields receive any equivalent cap. `encoding`, `tree`, `parent` values are assigned directly from the parsed line [3](#0-2) , and `author`/`committer` are parsed via `parseCommitAuthor`, which likewise applies no length bound to name/email [4](#0-3) . Even for headers that Gitaly doesn't recognize, the raw line is still appended in full to `payload` on every parse [5](#0-4) .

The tag parser has the identical pattern: it caps nothing on header lines (`tagger`, `tag`, `object`, `type`) and only the `Tag.Message` is later truncated by `TrimTagMessage` in a separate, opt-in call [6](#0-5) , and only `helper.MaxCommitOrTagMessageSize` (10 KiB) bounds the message body, not headers [7](#0-6) .

Since Git itself does not restrict the length of the free-form text following a header key on the `author`, `committer`, or `encoding` line (or the value of an arbitrary trailer/unknown header), a user can craft such a commit object locally (e.g., via `git commit-tree`/`git hash-object`) with a multi-hundred-megabyte `encoding` or author-name field and push it to their own repository through the ordinary push path. Once stored, every future Gitaly RPC that resolves that commit through the catfile parser re-reads and, for known fields, re-serializes that oversized data into the gRPC response.

### Impact Explanation
This mirrors the `Hats.uri` bug class exactly: the "expensive to write once, expensive to read every time" pattern. Every `GetCommit`, `FindCommit`, `ListCommits`, `FindTag`, `FindAllBranches`/`FindAllTags`, and blame-style RPC that touches the poisoned commit/tag pays the full memory/CPU/allocation cost of the oversized header on every single invocation, and, for known fields such as `encoding`/`author`/`committer`, returns that oversized data in the gRPC response - risking exceeding gRPC max message size limits and causing repeated, amplifiable CPU/memory load on the Gitaly node for any caller who merely reads history containing the crafted object (browsing, cloning, CI, mirroring, replication). This is a repeatable, low-cost DoS vector, not a one-time cost.

### Likelihood Explanation
Any authenticated user with push/write access to a repository (an "ordinary user's push", per the analog scope) can construct such a commit/tag object using standard local git plumbing commands and push it once; no special privilege or malicious peer/MITM/token leak is required. The one-time cost of writing the malicious object is bounded (a single push of one oversized-but-otherwise-normal-looking commit), while the ongoing cost is paid repeatedly by every reader thereafter - a favorable cost asymmetry for the attacker, matching the economics described in the source report.

### Recommendation
Apply the same "cap and mark-truncated" strategy already used for `helper.MaxCommitOrTagMessageSize` to header fields: introduce reasonable maximum lengths for `author`/`committer` name and email, `encoding`, `tree`/`parent` OIDs (which are naturally fixed-length and could be validated), and generic/unknown header lines, truncating or rejecting lines that exceed the cap in `ParseCommit`/`parseTag`/`parseCommitAuthor` before they're stored on the `gitalypb.GitCommit`/`gitalypb.Tag` structures or appended to `payload`. Consider also bounding the total bytes read per header section to prevent a single pathological object from causing unbounded allocation regardless of which specific header carries the bloat.

### Proof of Concept
1. Craft a commit object locally with a legitimate tree but an oversized header, e.g.:
   ```
   printf 'tree <valid-tree-oid>\nauthor A <a@a.com> 1700000000 +0000\ncommitter A <a@a.com> 1700000000 +0000\nencoding %s\n\nmsg\n' "$(python3 -c 'print("X"*50_000_000)')" | git hash-object -t commit -w --stdin
   ```
2. Update a branch to point at this commit object and push it to the Gitaly-backed repository via the normal push path (`git push origin HEAD:refs/heads/poison`).
3. Call `FindCommit`/`GetCommit`/`ListCommits` against `refs/heads/poison` repeatedly; observe that each call re-parses the full 50 MB `encoding` header via `ParseCommit`, materializing it in memory and returning it in the response, imposing repeated CPU/memory/network cost on the Gitaly node and any client per invocation.

func parseCommitAuthor(line string) *gitalypb.CommitAuthor {
	author := &gitalypb.CommitAuthor{}

	name, line, ok := strings.Cut(line, "<")
	author.Name = []byte(strings.TrimSuffix(name, " "))

	if !ok {
		return author
	}

	email, line, ok := strings.Cut(line, ">")
	if !ok {
		return author
	}

	author.Email = []byte(email)

	secSplit := strings.Fields(line)
	if len(secSplit) < 1 {
		return author
	}

	sec := git.ParseDateSeconds(secSplit[0])

	author.Date = &timestamppb.Timestamp{Seconds: sec}

	if len(secSplit) == 2 {
		author.Timezone = []byte(secSplit[1])
	}

	return author
}
