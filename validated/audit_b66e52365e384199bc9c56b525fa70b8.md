Based on the investigation, the strongest local analog is in Snowbridge's Outbound Queue V2 pallet: the message-submission path never enforces a nonzero/sufficient fee before permanently committing a message and creating a `PendingOrder`.

### Title
Outbound Queue V2 accepts and permanently commits messages with a zero (or arbitrarily low) fee, allowing free/underpriced spam of bridge state - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/send_message_impl.rs`, `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The external report describes `DAOfiV1Pair.deposit()`, a one-time state-mutating action that gets permanently locked in (`deposited = true`) without ever validating that a meaningful (nonzero) amount was actually deposited, letting an unfunded caller irreversibly damage the pool. The direct analog here is `Pallet::validate` in `send_message_impl.rs`, which accepts any well-formed `Message` regardless of its `fee` field, and `do_process_message` in `lib.rs`, which unconditionally commits the message to the Merkle tree, advances the global `Nonce`, and inserts a `PendingOrder` — even when `fee == 0`.

### Finding Description
`SendMessage::validate` for the V2 outbound queue only checks payload size: [1](#0-0) 
It performs no check on `message.fee` at all before returning `Ok` and allowing `deliver()` to enqueue the message via `T::MessageQueue::enqueue_message`.

Once dequeued, `do_process_message` decodes the message (including its `fee`) and unconditionally:
- appends it to `Messages` / `MessageLeaves` (which get Merkle-committed and written into the header digest every block),
- allocates the next `Nonce`,
- inserts a `PendingOrder { nonce, fee, block_number }` into `PendingOrders`. [2](#0-1) 

None of this path rejects `fee == 0`. The only place a zero-amount guard exists is the unrelated `add_tip` entrypoint, which explicitly rejects a zero top-up (`ensure!(amount > 0, AddTipError::AmountZero)`), showing the pallet authors recognize the "zero value corrupts state" hazard elsewhere but did not apply the same guard to the primary message-acceptance path: [3](#0-2) 

When the message is later delivered/relayed, `process_delivery_receipt` only pays a reward `if order.fee > 0`, otherwise it simply removes the pending order with no reward — again confirming that `fee == 0` is an anticipated (not rejected) state: [4](#0-3) 

### Impact Explanation
Because `fee` is never bound below by a minimum covering `calculate_local_fee`/processing weight (unlike the V1 outbound queue, which computes and requires a fee via `calculate_fee`/pricing parameters), any caller able to reach `SendMessage::deliver` for this exporter (e.g. via XCM `ExportMessage` routed by the `SnowbridgeMessageExporter`) can submit an arbitrary number of zero-fee messages. Each such message:
- consumes `MaxMessagesPerBlock` slots and Merkle-leaf/PoV space every block,
- advances the global `Nonce` monotonically and permanently,
- creates a `PendingOrder` entry that lingers in storage until (if ever) a relayer bothers to submit a delivery receipt for a message that pays them nothing.

This is exactly the accepted-impact class "public underpriced work that degrades block production or stalls bridge processing": unpriced/free work is queued and committed on-chain, growing state and displacing legitimate messages, without requiring any privileged actor, malicious relayer, or validator — only an ordinary XCM sender on a connected chain.

### Likelihood Explanation
High. No signed extrinsic or special permission is required — `deliver()`/`validate()` are invoked as part of the standard XCM `ExportMessage` -> `SnowbridgeMessageExporter` flow, and the only cost is the local processing cost, not the message's declared `fee`, since `fee` itself is attacker-controlled and unchecked. Repeating this action requires no capital and directly wastes on-chain block/PoV resources and pollutes the `PendingOrders` map.

### Recommendation
Enforce a minimum fee in `SendMessage::validate` (and/or `do_process_message`) for the V2 outbound queue analogous to the V1 pallet's `calculate_fee`/pricing-parameter model: reject messages whose `fee` is below the computed local processing cost (or an explicit nonzero floor), mirroring the guard already present in `AddTip::add_tip`. Do not allow `PendingOrders` to be created for messages that have not paid for their own inclusion.

### Proof of Concept
1. Construct any well-formed `snowbridge_outbound_queue_primitives::v2::Message` with `fee = 0` and a minimal valid `commands` vector.
2. Call `Pallet::<T>::validate(&message)` — it succeeds because only payload size is checked.
3. Call `Pallet::<T>::deliver(ticket)` — the message is enqueued via `T::MessageQueue::enqueue_message` and a `MessageQueued` event fires.
4. On processing, `do_process_message` commits the message into `Messages`/`MessageLeaves`, increments `Nonce`, and inserts a `PendingOrder { nonce, fee: 0, .. }` into `PendingOrders` — all with no economic cost to the sender beyond the local dispatch weight, and no relayer is incentivized to ever clear the resulting `PendingOrders` entry via `submit_delivery_receipt`.
