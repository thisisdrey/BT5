## Analysis: Analog of ERC1271 signature replay found in StackerDB chunk authentication

I found a valid analog. It maps to the same equality break as the report: a signature that authenticates *content* but is never bound to the *verifying entity* (there: `address(this)`; here: the StackerDB smart-contract identifier), enabling replay across sibling contracts that reuse the same signer-to-slot ordering.

### Title
StackerDB chunk signatures omit the destination smart contract from the signed digest, enabling cross-contract signature replay — (File: `libstackerdb/src/libstackerdb.rs`)

### Summary
`SlotMetadata::auth_digest()` computes the signed hash as `hash(slot_id, slot_version, data_hash)` only. It never mixes in the target `QualifiedContractIdentifier` (the StackerDB smart contract). Both the write path (`StackerDBTx::try_replace_chunk`) and the gossip-validation path (`StackerDBSync::validate_received_chunk`) call `slot_desc.verify(&signer)`, which only checks that the digest recovers to the expected signer address *for that slot*, never checking that the digest is scoped to the specific contract being written. Since the Stacks signer boot contracts (`.signers-{set}-1`, `.signers-{set}-2`, `.signers-{set}-3`, i.e. `BlockResponse`, `StateMachineUpdate`, `BlockPreCommit`) all derive their slot list from the identical `stackerdb-get-signer-slots-page` call for a given signer set, slot `N` maps to the *same* signer address across all of these sibling contracts. A chunk validly signed for one contract can therefore be replayed byte-for-byte into a sibling contract's identical slot index.

### Finding Description
- `SlotMetadata::auth_digest()`: [1](#0-0) 
signs only `slot_id`, `slot_version`, `data_hash` — no smart-contract identifier.
- `SlotMetadata::verify()` recovers the pubkey from that digest and compares only against `principal`: [2](#0-1) 
- The storage-layer write path passes `smart_contract` only to *look up* the expected signer for that slot, not to bind it into the digest: [3](#0-2) 
- The p2p gossip validation path has the same gap — `smart_contract_id` is used purely to fetch `get_slot_signer`, and the actual cryptographic check (`slot_metadata.verify(&addr)`) is contract-agnostic: [4](#0-3) 
- The Clarity boot contracts confirm that multiple distinct StackerDB smart contracts share the exact same signer ordering per signer set/reward cycle: `.signers-{set}-1/2/3` all call `stackerdb-get-signer-slots-page` with the same page argument, so slot index `N` is owned by the identical `StacksAddress` in each sibling contract: [5](#0-4) [6](#0-5) 

Because the signed digest carries no contract-scoping data, an unprivileged attacker who observes any legitimately-signed `StackerDBChunkData` (freely and publicly obtainable via `GET /v2/stackerdb/.../chunks/<id>` or via StackerDB gossip) can resubmit the identical bytes (`slot_id`, `slot_version`, `sig`, `data`) against a *different* sibling StackerDB contract in which the same address occupies the same slot index. `SlotMetadata::verify()` will still succeed there (same digest, same recovered pubkey), and provided the target slot's stored version is lower than the replayed `slot_version` (true immediately after contract deployment, or attacker can wait for/target a fresh slot), `try_replace_chunk` (write path) or `validate_received_chunk` (gossip acceptance/propagation path) will accept and store/relay the forged write — exactly the "signature valid for context A accepted in context B" break described in the report, just with "contract" playing the role of `address(this)`.

### Impact Explanation
This is an unauthenticated write into a StackerDB slot the signer never intended to target, and the accepted chunk is then relayed network-wide by `StackerDBSync`/`PeerNetwork::handle_unsolicited_StackerDBPushChunk`, matching the "Critical: unauthenticated/unauthorized write to state or StackerDB, network-wide propagation of forged data" bucket. It corrupts a peer/consumer's view of a given signer message channel (e.g., poisoning the Lamport `slot_version` in the `StateMachineUpdate` or `BlockPreCommit` channel so a legitimate signer's next real post is rejected as stale, or forcing them to skip versions), and any consumer that does not itself re-validate the payload type against the contract's expected `MessageSlotID` lane could be fed data attributable to a signer who never posted it there. The type-prefix check in `SignerEvent::try_from` (`signer_message_payload_matches_lane`) is an application-layer filter on the deserialized message content, not a cryptographic binding — it does not stop the storage layer from persisting/replicating the misattributed chunk, and it does not protect any other code path that reads raw StackerDB chunks without that specific filter.

### Likelihood Explanation
High. No secret key or privileged role is required — only the ability to observe one publicly broadcast/queryable chunk and resubmit it verbatim to a different, publicly documented contract name (`.signers-{set}-{other_msg_id}`) that is guaranteed by protocol design to share the same signer ordering. This is a pure protocol/logic flaw reachable by any remote peer.

### Recommendation
Bind the `QualifiedContractIdentifier` (and ideally the reward cycle / signer-set identifier already implicit in the contract name) into `SlotMetadata::auth_digest()`, e.g. hash `smart_contract.to_string().as_bytes()` (or a canonical serialization of it) together with `slot_id`, `slot_version`, `data_hash`, and thread the contract identifier through `sign()`/`verify()`/`recover_pk()` so every signature is scoped to the specific StackerDB it was produced for. This mirrors the recommended EIP-712 domain-separator fix in the source report (binding to `address(this)`), just substituting the Stacks equivalent of "verifying contract" — the StackerDB's `QualifiedContractIdentifier`.

### Proof of Concept
1. Signer key `SK` (address `A`) is registered at slot `N` in both `.signers-0-1` (BlockResponse) and `.signers-0-2` (StateMachineUpdate) for the current reward cycle (guaranteed by `signers.clar`'s shared `stackerdb-get-signer-slots-page`).
2. `SK` legitimately signs and posts a `StackerDBChunkData{slot_id: N, slot_version: V, data: D}` to `.signers-0-1` via `StackerDB::send_message_bytes_with_retry` (uses `chunk.sign(&self.stacks_private_key)`, i.e. `SlotMetadata::sign`, which only commits to `(N, V, hash(D))`).
3. Attacker (no key) fetches this chunk publicly, e.g. via `GET /v2/stackerdb/{signers-0-1}/{N}/chunks` (`stackslib/src/net/api/getstackerdbchunk.rs`), obtaining `(N, V, sig, D)`.
4. Attacker resubmits the identical tuple to `.signers-0-2` via `POST /v2/stackerdb/{signers-0-2}/chunks`, i.e. `stackslib/src/net/api/poststackerdbchunk.rs`.
5. Server calls `try_replace_chunk(&signers-0-2, &slot_desc, &D)`; `slot_desc.verify(&signer_for_slot_N_in_signers-0-2)` succeeds because address `A` is also the registered signer for slot `N` there, and the digest is identical since it never referenced the contract. If `V` exceeds `.signers-0-2`'s current stored version for slot `N`, the write is accepted and the forged chunk is stored under the wrong StackerDB and propagated to peers.

This confirms the fault lies precisely in `libstackerdb/src/libstackerdb.rs`'s `auth_digest()` omitting contract-scoping, with `stackslib/src/net/stackerdb/db.rs::try_replace_chunk` and `stackslib/src/net/stackerdb/mod.rs::validate_received_chunk` as the two reachable, unauthenticated sinks that trust the unscoped signature.

    fn auth_digest(&self) -> Sha512Trunc256Sum {
        let mut hasher = Sha512_256::new();
        hasher.update(self.slot_id.to_be_bytes());
        hasher.update(self.slot_version.to_be_bytes());
        hasher.update(self.data_hash.0);
        Sha512Trunc256Sum::from_hasher(hasher)
    }

    /// Verify that a given principal signed this chunk metadata.
    /// Note that the address version is ignored.
    pub fn verify(&self, principal: &StacksAddress) -> Result<bool, Error> {
        let sigh = self.auth_digest();
        let pubk = StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            sigh.as_bytes(),
            &self.signature,
        )
        .map_err(|ve| Error::VerifyingError(ve.to_string()))?;

        let pubkh = Hash160::from_node_public_key(&pubk);
        Ok(pubkh == *principal.bytes())
    }

        &self,
        smart_contract: &QualifiedContractIdentifier,
        slot_desc: &SlotMetadata,
        chunk: &[u8],
    ) -> Result<(), net_error> {
        // Check per-replica chunk-size cap.
        if (chunk.len() as u64) > self.config.chunk_size {
            return Err(net_error::StackerDBChunkTooBig(chunk.len()));
        }

        let slot_validation = self
            .get_slot_validation(smart_contract, slot_desc.slot_id)?
            .ok_or(net_error::NoSuchSlot(
                smart_contract.clone(),
                slot_desc.slot_id,
            ))?;

        if !slot_desc.verify(&slot_validation.signer)? {
            return Err(net_error::BadSlotSigner(
                slot_validation.signer,
                slot_desc.slot_id,
            ));
        }
