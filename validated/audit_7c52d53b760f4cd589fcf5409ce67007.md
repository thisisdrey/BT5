### Title
`snowbridge-pallet-outbound-queue-v2::submit_delivery_receipt` pays relayer rewards and settles pending orders with no halt/pause check - (File: `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`)

### Summary
The `outbound-queue-v2` pallet defines a `Halted` error variant and a `BasicOperatingMode` type is imported, but nowhere in this pallet is an `OperatingMode` storage item declared or checked, and there is no `set_operating_mode` call. Consequently, the public extrinsic `submit_delivery_receipt` (the reward-settlement entry point, analogous to `deleverageAccount` in the Notional report) can be invoked and fully settle/mutate `PendingOrders` state and register relayer rewards even while the bridge is meant to be paused, unlike its sibling pallets that consistently gate their public entrypoints behind an operating-mode halt check.

### Finding Description
Across the Snowbridge pallets in this repo, the established pattern is: every pallet that accepts externally-triggered proofs/messages stores its own `OperatingMode` and checks `ensure!(!Self::operating_mode().is_halted(), Error::<T>::Halted)` before doing any state-mutating work:

- `inbound-queue::submit`: [1](#0-0) 
- `inbound-queue-v2::submit`: [2](#0-1) 
- `ethereum-client::submit`: [3](#0-2) 
- `outbound-queue` (v1) `deliver`: [4](#0-3) 

Each of these pallets defines an `OperatingMode` storage item and a `set_operating_mode` root-only call, e.g. in `outbound-queue-v2` itself the `Halted` error variant and `OperatingModeChanged` event exist: [5](#0-4) 

However, in `outbound-queue-v2`, no `OperatingMode` storage item is declared anywhere in the pallet, no `set_operating_mode` call exists, and the `submit_delivery_receipt` extrinsic performs signature/proof verification and then unconditionally calls `process_delivery_receipt`, which pays out the relayer reward and removes the pending order, with **no halt check at all**: [6](#0-5) [7](#0-6) 

The `T::Verifier::verify()` call used inside `submit_delivery_receipt` delegates to the `ethereum-client` pallet's `Verifier` implementation, which does check *its own* halt flag: [8](#0-7) 

But this is the `ethereum-client`'s halt flag, not the `outbound-queue-v2` pallet's own operating mode — and `outbound-queue-v2` has no operating mode of its own to halt with. The code comment on the `Verifier::verify` implementation even acknowledges this exact gap explicitly by name: "Covers every Verifier consumer, including `inbound_queue_v2::submit` and `outbound_queue_v2::submit_delivery_receipt` (which would otherwise still drain pending relayer rewards while the bridge is halted)." This shows the authors were aware that `submit_delivery_receipt` should be halt-gated and patched around it by halting the underlying beacon light-client verifier — but this only stops the path when the light client itself is deliberately halted by governance. If an admin only wants to pause the outbound-queue-v2 pallet specifically (e.g., due to a reward-accounting bug, a `PendingOrders`/fee computation issue, or a compromised `RewardPayment` backend) there is no `set_operating_mode` call or storage to do so for this pallet — the function is un-pausable independent of the light client, exactly mirroring the Notional bug: a partial-pause mechanism exists in sibling code paths, but the specific fund-moving function lacks its own guard and can still be triggered.

### Impact Explanation
`process_delivery_receipt` mutates `PendingOrders` and calls `T::RewardPayment::register_reward` to credit relayer rewards. If governance ever needs to halt only the outbound-queue-v2 reward/settlement logic (for example while investigating a reward-computation exploit, a nonce/order desync, or an `AddTip` manipulation), there is no mechanism to do so — the pallet has no `OperatingMode` storage or `set_operating_mode` call, unlike every sibling bridge pallet. This directly matches the "public underpriced work / degraded bridge processing / permanent bridge-state" impact class: settlement can proceed unconditionally, bypassing the pause primitive that the rest of the Snowbridge codebase relies on for incident response.

### Likelihood Explanation
Likelihood is high in a governance-driven halt scenario: any unprivileged relayer can call `submit_delivery_receipt` with a valid Ethereum receipt at any time, and there is no code path that lets a root/governance actor stop this specific pallet's settlement logic short of halting the entire `ethereum-client` (which would also block all other pallets depending on that verifier, e.g. inbound queues), making targeted incident response impossible for this pallet.

### Recommendation
Add an `OperatingMode` storage item and `set_operating_mode` call to `outbound-queue-v2`, matching the pattern used in `inbound-queue-v2` and `outbound-queue` v1, and add `ensure!(!Self::operating_mode().is_halted(), Error::<T>::Halted)` at the start of `submit_delivery_receipt` (or inside `process_delivery_receipt`), before any proof verification or reward mutation occurs.

### Proof of Concept
1. Deploy/observe a live `outbound-queue-v2` pallet instance; note there is no extrinsic to halt it (confirmed by absence of `OperatingMode` storage / `set_operating_mode` call in `bridges/snowbridge/pallets/outbound-queue-v2/src/lib.rs`, versus its presence in `inbound-queue-v2` and `outbound-queue`).
2. Governance halts the `ethereum-client` pallet via `set_operating_mode(Halted)` intending to stop all bridge activity pending an investigation of a reward-processing bug in `outbound-queue-v2::process_delivery_receipt`.
3. Because `outbound-queue-v2` has no independent operating mode, the only way to block `submit_delivery_receipt` is to halt `ethereum-client`, which simultaneously blocks legitimate inbound message and other verifier-dependent processing — there is no way to pause reward settlement in `outbound-queue-v2` alone while keeping other bridge functions (e.g., inbound message processing via a different verifier instance, if configured) operational.
4. If `ethereum-client` is left active (e.g., because other pallets still need it), any relayer can continue calling `submit_delivery_receipt` and draining `PendingOrders` rewards indefinitely, with no per-pallet circuit breaker, exactly as in the Notional report where `deleverageAccount` remained callable despite the vault's `ENABLED` flag being off, because that specific function never checked the flag.

		/// Process a delivery receipt from a relayer, to allocate the relayer reward.
		pub fn process_delivery_receipt(
			relayer: <T as frame_system::Config>::AccountId,
			receipt: DeliveryReceipt,
		) -> DispatchResult
		where
			<T as frame_system::Config>::AccountId: From<[u8; 32]>,
		{
			// Verify that the message was submitted from the known Gateway contract
			ensure!(T::GatewayAddress::get() == receipt.gateway, Error::<T>::InvalidGateway);

			let reward_account = if receipt.reward_address == [0u8; 32] {
				relayer
			} else {
				receipt.reward_address.into()
			};

			let nonce = receipt.nonce;

			let order = <PendingOrders<T>>::get(nonce).ok_or(Error::<T>::InvalidPendingNonce)?;

			if order.fee > 0 {
				// Pay relayer reward
				T::RewardPayment::register_reward(
					&reward_account,
					T::DefaultRewardKind::get(),
					order.fee,
				);
			}

			<PendingOrders<T>>::remove(nonce);

			Self::deposit_event(Event::MessageDelivered { nonce });

			Ok(())
		}
