### Title
Stale Index Cache Not Invalidated on Socialize-Debt Leads to Mispriced Rehypothecated Collateral/Debt - (File: mainnet/contracts/market/v0-4-market.clar)

### Summary
`market.clar` maintains a timestamp-keyed cache (`index-cache`) of each vault's borrow/liquidity indexes to avoid repeated cross-contract accrual calls within the same block [1](#0-0) . This cache is populated exclusively through `accrue-and-cache`, which returns the cached value on a hit and only refreshes it via `vault-accrue` on a miss [2](#0-1) . However, `vault-socialize-debt` is a separate mutation path into the same vaults, invoked independently of `accrue-and-cache` [3](#0-2) , and it is never wired to update or invalidate the `index-cache` entry for that `{timestamp, aid}` key. This mirrors the reported ConcurrentMerkleTree bug class: a secondary cached structure (the canopy / here, `index-cache`) that must mirror the authoritative state (the tree / here, the vault's real index) is left stale after the authoritative state is mutated through a different code path, and consumers keep trusting the outdated cached value for subsequent validation.

### Finding Description
`index-cache` is a per-second cache keyed by `{ timestamp: stacks-block-time, aid }` [1](#0-0) . Once any transaction in that second populates the entry via `accrue-and-cache`, every subsequent operation in the same second treats it as ground truth and skips re-accrual [2](#0-1) . This cached index is what feeds ztoken (rehypothecated collateral) debt/notional valuation used in health checks, e.g. `calculate-asset-notional-value` pulls `(get index (unwrap-panic (accrue-and-cache asset-id)))` directly to compute debt notional [4](#0-3) .

`vault-socialize-debt` calls the vault's `socialize-debt` entrypoint on a different, independent code path from `accrue-and-cache`/`vault-accrue` [3](#0-2) . Socializing bad debt redistributes shortfall across the vault's liquidity index (the AAVE-style model referenced in the vault docs, where reserve/index state is updated on each state-changing operation) [5](#0-4) . Because this mutation does not go through `accrue-and-cache`, the market's `index-cache` entry for that vault/timestamp is not refreshed or invalidated. If any liquidation or other transaction earlier in the same second already caused a cache hit/write for that `aid`, all subsequent operations in that same second continue reading the pre-socialization index from `index-cache`, exactly the "leaf updated but canopy not updated" inconsistency described in the report — the derived/cached value diverges from the primary state and is still trusted for downstream validation (health checks, notional valuation).

### Impact Explanation
If the liquidity index used for ztoken collateral valuation is stale-high (pre-write-off) while the true, post-socialization index is lower, any borrow/withdraw/health-check executed later in the same second overvalues rehypothecated (zToken) collateral and/or undervalues ztoken-denominated debt in `get-notional-evaluation`/`calculate-asset-notional-value` [6](#0-5) . This lets a position pass `is-healthy`/`is-healthy-with-mask` checks that would fail under the true index, permitting additional borrowing against under-collateralized positions and evasion of liquidation, which accrues further bad debt onto the protocol — this maps to protocol insolvency.

### Likelihood Explanation
`accrue-and-cache` is on the hot path of nearly every market operation (borrow, repay, collateral add/remove) [7](#0-6) , so a cache entry for a given vault/timestamp is populated frequently. `socialize-debt` is invoked as part of the normal liquidation/bad-debt flow, which is expected to occur, especially during volatile markets — making the stale window a realistic, recurring race rather than a contrived edge case. The window is bounded to a single second (`stacks-block-time` granularity) but on a fast chain multiple transactions/blocks can land within that window.

### Recommendation
Invalidate or refresh the `index-cache` entry for `aid` whenever `vault-socialize-debt` (or any other state-mutating vault call outside `accrue-and-cache`) is executed, e.g. by calling `map-delete index-cache { timestamp: stacks-block-time, aid: aid }` immediately after `vault-socialize-debt` succeeds, or by re-running `vault-accrue` and overwriting the cache entry with the freshly returned indexes.

### Proof of Concept
Conceptual sequence within the same block/second:
1. TX A: a liquidation call triggers `accrue-and-cache` for `aid=X` (zUSDC's underlying vault), caching `index = I0` for `timestamp = T`.
2. The liquidation determines the borrower's collateral is insufficient even after seizure and calls `vault-socialize-debt` for `aid=X`, which reduces the vault's true liquidity index to `I1 < I0` to socialize the shortfall.
3. TX B (later in the same second `T`, by any unprivileged user): calls `borrow`/`collateral-remove`, which invokes `accrue-and-cache(X)`; since `map-get? index-cache {timestamp: T, aid: X}` is a cache HIT, it returns the stale `I0` instead of `I1`.
4. The stale `I0` is used in `calculate-asset-notional-value` to value the user's zUSDC-denominated debt/collateral, overstating collateral value (or understating debt), allowing `is-healthy` to pass when it should not under `I1`. [2](#0-1) [3](#0-2)

(define-private (accrue-and-cache (aid uint))
  (let ((cache-key { timestamp: stacks-block-time, aid: aid })
        (cached? (map-get? index-cache cache-key)))

    (match cached?
      ;; cache HIT: return cached value (1 read only)
      cached-indexes (ok cached-indexes)

      ;; cache MISS: accrue and cache (vault-accrue now returns indexes)
      (let ((indexes (try! (vault-accrue aid))))
        ;; store in cache
        (map-set index-cache cache-key indexes)
        (ok indexes)))))
```

### Protocol Reserves & DAO Treasury

A portion of interest earned goes to protocol reserves, which are minted directly as vault shares to the DAO treasury contract. This follows the AAVE model where treasury minting occurs on each vault state update.

**Reserve Factor:** Percentage of interest allocated to protocol (e.g., 10%)

**Treasury Minting Process:**
```clarity
;; In vault contracts (e.g., vault-stx.clar)
;; On each accrue operation:
;; 1. Calculate total interest earned
;; 2. Reserve factor determines protocol share (e.g., 10%)
;; 3. Mint vault shares directly to dao-treasury
;; 4. Remaining interest goes to suppliers
```

**Reference:** Similar to [AAVE's ReserveLogic](https://github.com/aave-dao/aave-v3-origin/blob/8a43339b6f93ea0a2f4d8e1ef3b9494c9d206a64/src/contracts/protocol/libraries/logic/ReserveLogic.sol#L85-L101) where treasury minting happens on status updates.

**Example:** 
- 10 USDC interest earned
- 10% reserve factor
- 1 USDC equivalent in zUSDC shares → dao-treasury
- 9 USDC equivalent in value → suppliers
