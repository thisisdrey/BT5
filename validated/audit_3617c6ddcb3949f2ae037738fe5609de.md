### Title
Splitting a Nep245/Imt token-in leg into unit-sized `TokenDiff` legs bypasses the protocol fee - (File: contracts/defuse/core/src/intents/token_diff.rs)

### Summary
`TokenDiff::token_fee` explicitly returns `Pips::ZERO` for `Nep245`/`Imt` token deltas whose absolute value is `<= 1` [1](#0-0) . Because the fee is computed independently per `TokenDiff` intent on the magnitude of that intent's own delta, an attacker can replace one large negative (`token_in`) delta with several unit-sized (`|delta| == 1`) negative deltas from separate signed payloads (same signer, different nonces, or several colluding signers) that are batched into a single `execute_intents`/`simulate_intents` call, while balancing the batch with one or more positive deltas elsewhere (positive deltas are never taxed, regardless of size) so that `TransferMatcher::finalize` sees a net-zero delta and does not raise `InvariantViolated`.

### Finding Description
The broken binding: for a fixed protocol `Pips` fee and a fixed net negative amount `N` moved out of `token_in` legs of a `Nep245`/`Imt` token `T` in a batch, `sum(fees_collected[T] over all TokenDiff intents in the batch)` should equal `Pips::fee_ceil(N)`, matching a single `TokenDiff` intent with `delta = -N` on `T`. Instead:

- `TokenDiff::execute_intent` computes fee per intent, per token, based only on that intent's own `delta.unsigned_abs()`: `Self::token_fee(token_id, amount, protocol_fee).fee_ceil(amount)` [2](#0-1) .
- `TokenDiff::token_fee` hard-codes `Pips::ZERO` whenever `TokenIdType` is `Nep245`/`Imt` and `amount <= 1` [1](#0-0) .
- The only cross-intent invariant enforced across the whole batch is `TransferMatcher::finalize`, which only requires that summed deltas per token net to zero (matched deposits/withdrawals); it has no knowledge of, or dependency on, fee amounts [3](#0-2) . `Engine::execute_signed_intents` only calls this net-zero check at the very end, after every intent already applied its own (zero) fee [4](#0-3) .
- Since fee is only ever assessed on negative deltas (`token_in`) and never on positive deltas (`token_out`) [2](#0-1) , an attacker splits the negative side of a swap into `N` payloads each with `delta = -1` on token `T` (each independently taxed `Pips::ZERO` because `amount <= 1`), while the compensating positive side supplies `+N` (or is itself further split, irrelevant since positive legs are never taxed). The batch's total negative delta for `T` is `-N`, the total positive delta is `+N`, `TransferMatcher::finalize` sees a matched, net-zero delta and succeeds, and `fees_collected` for `T` across the whole batch is `0`, whereas a single `TokenDiff` with `delta = -N` on the same signer would have paid `Pips::fee_ceil(N) > 0` for any `N > 1`.

No existing guard prevents this: `MultiPayload::verify` only checks signatures are valid and distinct nonces are used (an attacker's own key can sign arbitrarily many distinct-nonce payloads), `verify_intent_nonce`/`commit_nonce` only prevent nonce reuse, and `TransferMatcher::finalize`'s invariant is purely a balance-conservation check, not a fee-conservation check.

### Impact Explanation
This under-collects protocol fees on any `Nep245` (multi-token) or `Imt` swap that a user is willing to split into unit-sized legs, at the cost only of needing multiple valid nonces from the same key (or accomplices), which any unprivileged signer already controls. This matches the Critical category "protocol fees bypassed or over-collected": the fee collector (`self.fee_collector()`) receives less than `Pips::fee_ceil` of the aggregated negative deltas for token `T` in the batch, and the counterparty on the positive side of the swap receives the full untaxed amount instead of `amount - fee`. It is fully repeatable per batch, per token, and per account, and scales linearly with the number of unit legs an attacker is willing to construct (bounded only by gas/tx size, which is explicitly out of scope to consider as a mitigating factor here since the loss itself, not resource exhaustion, is the issue).

### Likelihood Explanation
No special privileges, roles, or victim keys are required — only the attacker's own signing key (to produce `N` distinct-nonce payloads) and, if solo, a counterparty willing to swap (or the attacker's own second account acting as counterparty in a self-trade, which is possible since `TokenDiff` only nets deltas and does not require distinct signers). The `amount <= 1` exemption for `Nep245`/`Imt` was clearly intended for genuinely dust/unit NFT-like items, but nothing in `token_fee` or the surrounding engine ties "amount" to the intent's own delta magnitude versus the batch's aggregate exposure on that token, making the bypass mechanical and cheap (linear number of extra signed payloads, no extra deposits or approvals needed).

### Recommendation
Compute and enforce the protocol fee on the aggregated (net) negative delta per token across the whole batch (e.g., inside `TransferMatcher`/`Deltas::finalize`, after summing all withdrawals per token, rather than per individual `TokenDiff` intent), or alternatively remove/tighten the `amount <= 1` fee exemption for `Nep245`/`Imt` so that it cannot be gamed by splitting a swap into many same-token intents within one execution batch.

    // Finalizes all transfers, or returns unmatched deltas.
    // If unmatched deltas overflow, then Err(None) is returned.
    pub fn finalize(self) -> Result<Transfers, InvariantViolated> {
        let mut transfers = Transfers::default();
        let mut deltas = TokenDeltas::default();
        for (token_id, transfer_matcher) in self.0 {
            if let Err(unmatched) = transfer_matcher.finalize_into(&token_id, &mut transfers)
                && (unmatched == 0 || deltas.apply_delta(token_id, unmatched).is_none())
            {
                return Err(InvariantViolated::Overflow);
            }
        }
        if !deltas.is_empty() {
            return Err(InvariantViolated::UnmatchedDeltas {
                unmatched_deltas: deltas,
            });
        }
        Ok(transfers)
    }
