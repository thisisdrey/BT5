### Title
JSON response injection via unescaped exception messages in `JsonFormat.printErrorMsg` - (File: framework/src/main/java/org/tron/core/services/http/JsonFormat.java)

### Summary
Analogous to the Valkey/RESP bug where Lua's `error_reply` embedded unescaped attacker-controlled bytes into the inline RESP error line and could corrupt the response stream, java-tron's HTTP API builds error JSON responses by string concatenation without escaping the exception message content: [1](#0-0) 

### Finding Description
`JsonFormat.printErrorMsg(Exception ex)` hand-builds a JSON object as a raw string and appends `ex.getMessage()` verbatim between quotes, with no escaping of `"`, `\`, control characters, or line breaks: [1](#0-0) 

This is invoked by `Util.processError`, which is the standard exception handler used by dozens of HTTP servlets (`GetAssetIssueByNameServlet`, `GetAccountServlet`, `GetContractServlet`, `GetBlockByIdServlet`, and many more) whenever any exception is thrown while processing a request: [2](#0-1) 

Many of these exception messages embed raw, attacker-controlled request data verbatim (e.g., `JsonRpcApiUtil` and similar validation helpers throw exceptions whose message is built by concatenating the raw user-supplied string, such as `"invalid topic: " + hexTopic` or `"invalid address: " + hexAddress`), and JSON/body parsing exceptions from the custom `org.tron.json` parser likewise tend to include fragments of the raw request body in their messages. If any such message contains a double quote (`"`), backslash, or control character (CR/LF), the character is written unescaped directly into the JSON text produced by `printErrorMsg`, letting an attacker terminate the intended `"Error": "..."` string early and inject additional fake JSON keys/values or malformed structure into the HTTP response body that a client actually receives.

This mirrors the root cause of the Valkey advisory: an error-message code path that assembles a wire-format response by direct string concatenation of untrusted content instead of a properly escaping serializer, allowing response-stream corruption/injection.

### Impact Explanation
A successful injection lets an attacker who can trigger a validation error on any of these public, unauthenticated HTTP endpoints control extra JSON fields in the node's own error response. Any downstream tooling, wallet, exchange integration, or automated service that parses these fields programmatically could be misled — e.g., a forged `"result":true` or additional bogus keys inserted after the intentional string terminates — turning a benign validation error into a response that downstream consumers may misinterpret. It is not by itself a memory-safety or consensus bug, but it is a genuine protocol/response-integrity flaw reachable from any unauthenticated HTTP request, matching the "response corrupted with attacker data" class described in the advisory.

### Likelihood Explanation
The `Util.processError` / `printErrorMsg` path is the default catch-all error handler across nearly the entire `framework/src/main/java/org/tron/core/services/http` servlet package, so it is reached extremely easily — any malformed/invalid parameter on any of these servlets funnels here. The remaining uncertainty is whether a specific, easily reproducible exception message contains attacker-supplied bytes with a literal `"` or control character (this depends on the exact wording of each validation exception and whether the custom `org.tron.json` parser echoes raw input in its messages); I was not able to fully trace every message-construction site to confirm a concrete quote/control-character-carrying payload before the session ended, so this should be verified with a live PoC.

### Recommendation
Rewrite `JsonFormat.printErrorMsg` to use a proper JSON writer/escaper (or the existing Jackson/`org.tron.json` serialization utilities) instead of manual string concatenation, ensuring `ex.getMessage()` is escaped for `"`, `\`, and control characters before being embedded in the response body. Audit all HTTP servlet exception messages that echo raw request parameters to confirm they cannot embed unescaped `"`/control characters, or centralize sanitization in `Util.processError`.

### Proof of Concept
Not confirmed with a concrete end-to-end payload during this investigation — a background engineer should: (1) search for validation exceptions across `framework/src/main/java/org/tron/core/services/http` that concatenate the raw request parameter into the exception message without sanitization, (2) confirm the custom `org.tron.json` parser echoes raw offending substrings (including quotes/newlines) in its `JSONException` messages, and (3) send a request containing a parameter value like `foo","injected":true,"x":"` to one of the affected servlets (e.g., `GetAssetIssueByNameServlet`, `ValidateAddressServlet`, or any servlet using `Util.processError`) to verify the resulting HTTP response body contains injected/malformed JSON.
