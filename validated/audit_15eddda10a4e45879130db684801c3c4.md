### Title
Naming-based quarantine-directory heuristic bypasses per-repository ownership validation, enabling cross-repository object-directory access - ([File: internal/git/localrepo/paths.go])

### Summary
`Repo.ObjectDirectoryPath()` resolves the value of the client-supplied `GitObjectDirectory` field on a `Repository` protobuf message. It is supposed to guarantee that any non-default object directory either lives inside the repository itself, or is a legitimate object-quarantine directory that was actually minted for *that specific repository* (verified via a SHA1-derived prefix tied to the repository's relative path). A basename-matching heuristic (`isTransactionQuarantineDir`) short-circuits that ownership check whenever the resolved path's last path component is literally `quarantine`, or its parent is `quarantine` and it starts with `tmp_objdir`. This mirrors the YSDAO bug class: a security-relevant classification heuristic based on shallow, attacker-shapeable state (a directory name) is used to skip the strong validation path (the repo-specific quarantine prefix check).

### Finding Description
In `ObjectDirectoryPath` [1](#0-0) , the code first does a coarse storage-root escape check via `storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))`, which only guarantees the path stays *somewhere inside the storage*, not inside the target repository. It then computes:

```go
parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
baseDir := filepath.Base(relativeObjectDirectoryPath)
isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))
``` [2](#0-1) 

When `isTransactionQuarantineDir` is true, the entire ownership-verification block is skipped:
```go
if !isTransactionQuarantineDir {
    if _, origError := storage.ValidateRelativePath(repoPath, objectDirectoryPath); origError != nil {
        ...
        expectedQuarantinePrefix := filepath.Join(tempDir, storage.QuarantineDirectoryPrefix(repo))
        if !strings.HasPrefix(absoluteObjectDirectoryPath, expectedQuarantinePrefix) {
            return "", structerr.NewInvalidArgument("not a valid relative path: %w", origError)
        }
    }
}
``` [3](#0-2) 

`QuarantineDirectoryPrefix` is the mechanism that is *supposed to* tie any quarantine-shaped path back to the exact repository it belongs to, by hashing the repository's relative path [4](#0-3) . The `isTransactionQuarantineDir` fast path bypasses this tie-back entirely and accepts any path whose final component is literally named `quarantine` (which is exactly how the WAL transaction manager names its per-transaction staging quarantine directory: `filepath.Join(txn.stagingDirectory, "quarantine")` [5](#0-4) ), regardless of which repository or transaction that directory actually belongs to. The function then simply `os.Stat`s the resulting path and returns it if present, with no ownership check at all [6](#0-5) .

This is structurally identical to the reported bug class: a cheap, attacker-influenceable heuristic ("does this look like a liquidity-add/remove event" vs. "does this look like a quarantine directory") is substituted for the real, state-tied check ("is the reserve consistent with the real balance" vs. "does the prefix hash match this repository"), and satisfying the heuristic skips the protective logic.

### Impact Explanation
A caller that controls the `GitObjectDirectory` (or `GitAlternateObjectDirectories`) field of a `Repository` message on any RPC that resolves `ObjectDirectoryPath` — e.g. `RepositoryService.GetObjectDirectorySize` [7](#0-6)  — can point the "object directory" at another repository's or another in-flight transaction's staging directory as long as: (1) the resulting absolute path stays inside the storage root, and (2) its basename is literally `quarantine` (or `<parent>/quarantine/tmp_objdir*`). Where this succeeds, Gitaly will treat an unrelated directory as the caller's legitimate quarantine/object directory, which can leak repository size/content information across repository boundaries and undermines the quarantine isolation guarantees documented in `doc/object_quarantine.md` [8](#0-7) .

### Likelihood Explanation
Exploitation requires the caller to supply a crafted `GitObjectDirectory` value and for a directory literally named `quarantine` (or matching the `tmp_objdir` pattern) to exist at a predictable/discoverable location within the shared storage root at the time of the call — such directories are created transiently by concurrent write transactions [5](#0-4) . This limits reliable exploitation to scenarios where the attacker can predict or race a concurrent transaction's staging path, which lowers likelihood versus a trivially deterministic path, but the underlying validation gap — bypassing the only ownership check via a name-based heuristic — is unconditional and always present for any request that manages to produce a `quarantine`-named basename.

### Recommendation
Remove the `isTransactionQuarantineDir` fast path, or at minimum require it to still pass an ownership check equivalent to the `QuarantineDirectoryPrefix` comparison (e.g., verify the path is nested under the specific transaction/staging directory that was allocated for *this* repository/transaction, not merely that its basename matches an expected string). The heuristic should never be sufficient on its own to skip the repository-specific ownership verification.

### Proof of Concept
1. Trigger (or await) a concurrent write transaction on some other repository in the same storage, whose staging directory is `<storage>/<tmp>/<txn-id>/quarantine` (per `transaction_manager.go`).
2. Issue `RepositoryService.GetObjectDirectorySize` (or another RPC resolving `ObjectDirectoryPath`) for the attacker's own repository, with `GitObjectDirectory` set to a relative path such that `filepath.Join(repoPath, objectDirectoryPath)` resolves to that other transaction's `.../quarantine` directory (e.g. `../../<tmp>/<txn-id>/quarantine`), keeping the result inside the storage root.
3. Because `filepath.Base(relativeObjectDirectoryPath) == "quarantine"`, `isTransactionQuarantineDir` is `true`, the `QuarantineDirectoryPrefix`/`ValidateRelativePath(repoPath, ...)` ownership check in `paths.go` lines 53-75 is skipped entirely, `os.Stat` succeeds on the foreign directory, and its path (and therefore its size/contents) is returned to the caller as if it belonged to the requested repository.

func (repo *Repo) ObjectDirectoryPath(ctx context.Context) (string, error) {
	repoPath, err := repo.Path(ctx)
	if err != nil {
		return "", err
	}

	objectDirectoryPath := repo.GetGitObjectDirectory()
	if objectDirectoryPath == "" {
		return "", structerr.NewInvalidArgument("object directory path is not set")
	}

	storagePath, err := repo.locator.GetStorageByName(ctx, repo.GetStorageName())
	if err != nil {
		return "", fmt.Errorf("get storage by name: %w", err)
	}

	// Ensure the path points somewhere in the storage.
	relativeObjectDirectoryPath, err := storage.ValidateRelativePath(storagePath, filepath.Join(repoPath, objectDirectoryPath))
	if err != nil {
		return "", structerr.NewInvalidArgument("validate relative path: %w", err)
	}

	parentDir := filepath.Base(filepath.Dir(relativeObjectDirectoryPath))
	baseDir := filepath.Base(relativeObjectDirectoryPath)
	isTransactionQuarantineDir := (baseDir == "quarantine") || ((parentDir == "quarantine") && strings.HasPrefix(baseDir, "tmp_objdir"))

	// Transactions quarantine a repository by pointing the object directory to a 'quarantine' named
	// directory in the transaction's temporary directory. If the base directory is `quarantine`,
	// Git push may apply an additional layer of quarantine such as `/quarantine/tmp_objdir-incoming-Gbc29N`
	// so we don't assert the `/quarantine` being the last element of the path. We thus also check for
	// whether the parent directory is in `quarantine` and whether the base directory has the expected
	// `tmp_objdir` suffix.

// QuarantineDirectoryPrefix returns a prefix for use in the temporary directory. The prefix is
// based on the relative repository path and will stay stable for any given repository. This allows
// us to verify that a given quarantine object directory indeed belongs to the repository at hand.
// Ideally, this function would directly be located in the quarantine module, but this is not
// possible due to cyclic dependencies.
func QuarantineDirectoryPrefix(repo Repository) string {
	hash := [20]byte{}
	if repo != nil {
		hash = sha1.Sum([]byte(repo.GetRelativePath()))
	}
	return fmt.Sprintf("quarantine-%x-", hash[:8])
}

## GitLab and Git object quarantine

### Why does all this matter to GitLab

GitLab uses Git hooks, among other things, to implement features that
can reject Git pushes. For example, you can mark a branch as
"protected" in the GitLab web UI, and then certain types of users can
no longer push to that branch. That feature is implemented via the
[Git `pre-receive` hook](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitaly/service/hook/pre_receive.go).

As mentioned above, Git object quarantine normally works more or less
automatically because `git` commands spawned by the `pre-receive` hook
inherit the special environment variables that contain the path to the
quarantine directory. In the case of the GitLab hooks we have a problem,
however, because the GitLab hooks are "dumb". All the GitLab hooks do
is take the inputs of the hook executable (the list of ref update
commands) and send them to the GitLab Rails internal API via a POST
request. The application logic that decides whether the push is
allowed resides in Rails. The hook just waits and reports back result
of the POST API request to GitLab.

During the POST, the internal GitLab API makes Gitaly calls back into the repo to
examine the objects being pushed. For example, if force pushes are not
allowed, GitLab will call the IsAncestor RPC. That RPC call then wants
to look at a commit that is in the process of being pushed. But
because that commit is in quarantine, the RPC will fail because the
commit cannot be found.

### How GitLab passes the object quarantine information around

To overcome this problem, the GitLab `pre-receive` hook
[reads the object directory configuration from its environment](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitlabshell/env.go#L9).
and passes this information
[along with the HTTP API call](https://gitlab.com/gitlab-org/gitaly/-/blob/71d527f4f16c1f0e76793f055def0299b375cc7d/internal/gitaly/hook/manager.go#L30-46).
On the Rails side, we then
[put the object directory information in the "request store"](https://gitlab.com/gitlab-org/gitlab/-/blob/master/lib/api/internal/base.rb#L43)
(i.e., request-scoped thread-local storage). And then during that
Rails request, when Rails makes Gitaly requests on this repo, we send back the quarantine information
[in the Gitaly `Repository` struct](https://gitlab.com/gitlab-org/gitlab/-/blob/f81f30c29a0edce20f6737fdccc3315c8baab9d1/lib/gitlab/gitaly_client/util.rb#L8-17).
And finally, inside Gitaly, when we spawn a Git process, we
[re-create the environment variables](https://gitlab.com/gitlab-org/gitaly/-/blob/969bac80e2f246867c1a976864bd1f5b34ee43dd/internal/git/alternates/alternates.go#L21-34)
that were present on the `pre-receive` hook, so that we can see the
quarantined objects.
