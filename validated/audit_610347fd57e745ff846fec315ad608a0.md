### Title
RewardsDistributor grants new depositors rewards for the entire historical index window, letting anyone drain unclaimed yield - ([File: contracts/RewardsDistributor.sol](contracts/RewardsDistributor.sol))

### Summary
The Mintbase bug paid out `storage_costs.common` unconditionally, even when the revoked approval that entitled the refund did not exist. In Metronome, the analog is in `RewardsDistributor._calculateTokenDelta`: when an account's stored `accountIndexOf` is `0` (i.e. it has never interacted), the function falls back to `INITIAL_INDEX` instead of the current index. The account's current token balance is then multiplied by the delta between the current global index and `INITIAL_INDEX`, crediting it with rewards accrued over the reward token's entire history — rewards it never participated in earning. Because `claimRewards` pays out `tokensAccruedOf` to any account with no further checks, any unprivileged user can deposit tokens (even in the same flow via Operator) and immediately claim the full historical reward accrual, draining reward tokens owed to genuine suppliers.

### Finding Description
In `_calculateTokenDelta` (contracts/RewardsDistributor.sol, around lines 217–231):

```solidity
uint256 _accountIndex = accountIndexOf[token_][account_];

if (_accountIndex == 0 && _tokenIndex > INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}

uint256 _deltaIndex = _tokenIndex - _accountIndex;
_tokensDelta = token_.balanceOf(account_).wadMul(_deltaIndex);
```

When a brand-new account is first touched by `_updateTokensAccruedOf` (called from `claimRewards`, `updateBeforeMintOrBurn`, or `updateBeforeTransfer`), its `_accountIndex` defaults to `INITIAL_INDEX`, not the current index. The resulting `_tokensDelta = currentBalance * (globalIndex - INITIAL_INDEX)` represents all rewards emitted since the reward token's speed was first set, weighted by a balance the account may have held for only a few seconds.

`claimRewards(address[] accounts_, IERC20[] tokens_)` is fully public and transfers `rewardToken` to `account_` for whatever `tokensAccruedOf[account_]` computes to — there is no per-account cooldown, no minimum holding period, and no check that the balance existed during the accrual window (it correctly zeroes `tokensAccruedOf` only when the distributor has sufficient balance, mirroring the "transfer inside/outside the if" flaw shape of the reference bug).

The attacker flow is:
1. `depositToken.deposit(amount, attacker)` for any reward-bearing DepositToken (e.g. `msdVaDAI`/`msdOP`), or acquire shares via `transferFrom` (DepositToken is a transferable ERC20; `updateBeforeTransfer` only updates accrual, it does not fix the index-backdating problem — it actively triggers the same fallback for the recipient).
2. Call `rewardsDistributor.claimRewards(attacker)` — `tokensAccruedOf[attacker]` is set to `balance * (index - INITIAL_INDEX)` and paid out in `rewardToken`.
3. `depositToken.withdraw(amount, attacker)` — the balance is fully unlocked when the account has no debt, so collateral is recovered.

### Impact Explanation
Direct theft of unclaimed yield: the attacker extracts `rewardToken` that rightfully belongs to accounts that supplied/borrowed during the entire historical accrual period. The payout is proportional to attacker balance × historical index delta, so with a large deposit (or a borrowed/delegated DepositToken balance) the attacker captures a dominant share of the distributor's `rewardToken` balance in one call. Rewards intended for long-term suppliers are stolen, and the distributor is drained for subsequent legitimate claimants. Note also that `claimable()`/`claimRewards` can be batched by a helper contract across many reward tokens in a single transaction.

### Likelihood Explanation
- `claimRewards` variants and `updateBeforeMintOrBurn`/`updateBeforeTransfer` are permissionless; only `nonReentrant` applies, which does not block the single-transaction deposit→claim→withdraw flow.
- DepositToken shares are freely transferable and withdrawable while the account has no debt; no lock or health check interferes.
- The bug only requires `tokenSpeeds[token_] > 0` and `tokenStates[token_].index > INITIAL_INDEX` for at least one registered DepositToken/DebtToken — i.e., any distributor that has been emitting rewards. If the deployment has an active reward speed and accumulated index, the exploit is a single transaction repeatable by any EOA or via `Operator.execute`/`SynthContext`.
- Repeated claims after the first are limited to newly accrued rewards, but a single call already captures the entire backdated window scaled by attacker balance.

### Recommendation
Initialize `accountIndexOf[token_][account_]` to the **current** global index (`_tokenIndex`, i.e. `tokenStates[token_].index` after `_updateTokenIndex`) the first time an account is seen, rather than `INITIAL_INDEX`. Concretely, change the fallback in `_calculateTokenDelta` to `_accountIndex = _tokenIndex` when `accountIndexOf` is `0`, or record the account's entry index at first deposit/mint. Move the reward transfer's entitlement check to mirror the reference fix: only accrue rewards for the window during which the account actually held the balance.

### Proof of Concept
Hardhat fork against a deployed `RewardsDistributor` with `tokenSpeeds[msdX] > 0`:

```ts
// setup: distributor has rewardToken balance R, index has accrued > INITIAL_INDEX
const attacker = attackerSigner
const depositToken = await ethers.getContractAt('DepositToken', MSD_TOKEN)
const distributor = await ethers.getContractAt('RewardsDistributor', REWARDS_DISTRIBUTOR)
const underlying = await ethers.getContractAt('IERC20', await depositToken.underlying())
const reward = await ethers.getContractAt('IERC20', await distributor.rewardToken())

// 1. attacker acquires shares (deposit or donation+transfer)
await underlying.connect(attacker).approve(depositToken.address, AMOUNT)
await depositToken.connect(attacker).deposit(AMOUNT, attacker.address)

// 2. indexDelta = currentIndex - INITIAL_INDEX > 0 for a fresh account
const claimable = await distributor['claimable(address)'](attacker.address)
expect(claimable).to.be.gt(0) // backdated rewards for zero holding time

// 3. claim drains distributor
const balBefore = await reward.balanceOf(attacker.address)
await distributor.connect(attacker)['claimRewards(address)'](attacker.address)
expect(await reward.balanceOf(attacker.address)).to.eq(balBefore.add(claimable))

// 4. withdraw collateral
await depositToken.connect(attacker).withdraw(await depositToken.unlockedBalanceOf(attacker.address), attacker.address)
```

Expected result: `claimable` equals `depositToken.balanceOf(attacker) * (globalIndex - INITIAL_INDEX)`, including all rewards accrued before the deposit, and the transaction succeeds — demonstrating payout for an entitlement window that never applied to the attacker, the same "payout regardless of actual entitlement" class as `nft_revoke`.
