### Title
Unsigned integer underflow in reftable restart-point parsing allows out-of-bounds slice access and RPC crash - (File: internal/git/reftable/reftable.go)

### Summary
`Table.parseRefBlock` computes the start offset of a reftable block's restart-point array using unsigned subtraction with an attacker-influenced multiplicand, analogous to the reported `convertSupplyChangeToPercentileChange` multiplication overflow in the Basis contract. Where the Solidity contract used `SafeMath` and threw on overflow, Gitaly's Go code uses plain `uint` arithmetic, which wraps silently instead of erroring, turning what should be a bounds check into an exploitable underflow that drives out-of-range slice indexing.

### Finding Description
`parseRefBlock` reads a 16-bit `RestartCount` directly from the reftable block bytes and computes: [1](#0-0) 

`b.RestartStart = blockStart + currentBS - 2 - 3*uint(b.RestartCount)`

`RestartCount` is fully attacker-controlled (it comes straight from the on-disk/on-wire block bytes with no upper-bound validation against the actual block size). Because Go's `uint` arithmetic wraps around on underflow instead of panicking or erroring (unlike Solidity's `SafeMath.mul`, which reverts), a crafted `RestartCount` larger than `(blockStart + currentBS - 2) / 3` makes `RestartStart` wrap to a huge value near `math.MaxUint`.

This corrupted `RestartStart` is then used as the loop bound in `getRefsFromBlock`: [2](#0-1) 

Since `idx < b.RestartStart` is now (almost) always true, the parser keeps consuming variable-length integers and slicing `src[idx:idx+suffixLength]` well past the end of the buffer, causing a Go slice-bounds-out-of-range panic. This is the direct Go analog of the Solidity bug: an unchecked/incorrectly-checked arithmetic operation on attacker-supplied input turns into a hard failure of the parsing routine that a legitimate caller depends on.

### Impact Explanation
`reftable.ParseTable`/`GetReferences` is exercised by Gitaly's reftable ref-backend code path (used by the transaction manager, replication/backup code, and reference listing when a repository uses the reftable backend) as shown by its callers in `internal/gitaly/storage/storagemgr/partition/reftable.go`, `internal/backup/repository.go`, and `internal/gitaly/service/repository/replicate.go`. A `.ref` table file with reachable/crafted `RestartCount` bytes — introduced via a push, fetch/mirror import, replication of a maliciously created repository, or a crafted table file - will panic when parsed. Since Go panics inside a request-serving goroutine, without a `recover`, this crashes the enclosing goroutine and denies service for that operation (or, if unrecovered at a higher level, can take down the whole `gitaly` process), a Denial-of-Service directly analogous to blocking the tally in the original report — an ordinary write path (or replicated/consumed data) can jam a legitimate, unprivileged read/verify operation.

### Likelihood Explanation
Likelihood is moderate-to-high wherever reftable-backed repositories are used: any code path that constructs or replicates a `.ref` table with attacker-influenced content (e.g., importing a repository, or an untrusted replica/backup being read back) will trigger the underflow the first time `GetReferences`/`parseRefBlock` runs on it. No authentication bypass is needed - only the ability to get such a table read by Gitaly's reftable parser, similar to the original report's requirement of only "being a delegate" (an ordinary, low-privilege participant).

### Recommendation
Validate `RestartCount` before computing `RestartStart`: ensure `3*uint(b.RestartCount) <= blockStart+currentBS-2` (using overflow-safe comparison, e.g., checking `b.RestartCount` against a bound derived from `currentBS` before multiplying) and reject/error out with a parse error instead of allowing the subtraction to wrap. More generally, treat all offsets/lengths derived from on-disk/wire data in `reftable.go` (`extractBlockLen`, `getVarInt`, block/restart computations) as untrusted and bounds-check them against `len(src)` prior to slicing, mirroring the recommendation to guard `postOracleSupplyChange`/`convertSupplyChangeToPercentileChange` against unrealistic attacker-supplied values. Add fuzz tests for `parseRefBlock`/`getRefsFromBlock` on malformed reftable blocks (a Go equivalent of the Echidna/Manticore recommendation).

### Proof of Concept
Conceptual PoC (exact byte layout would need to be validated against the reftable spec at https://git-scm.com/docs/reftable, which could not be executed in this read-only review):
1. Construct a minimal reftable with header/footer (`REFT`, version 1 or 2, valid CRC32) containing one ref block (`'r'` type byte).
2. Set the block's trailing 2-byte `RestartCount` field to a large value (e.g., `0xFFFF`) such that `3*RestartCount > blockStart+currentBS-2`.
3. Call `reftable.ParseTable(path)` followed by `table.GetReferences()`.
4. Observe `b.RestartStart` wrap to a value close to `math.MaxUint`, causing `getRefsFromBlock`'s loop condition `idx < b.RestartStart` to keep iterating past `len(src)`, ultimately panicking with `slice bounds out of range` inside `src[idx:idx+suffixLength]` or similar slicing expressions at [3](#0-2) .
