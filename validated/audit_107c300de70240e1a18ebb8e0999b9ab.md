### Title
Peer serving a mismatched/empty `Attachment` for a requested `content_hash` is accepted as "successful" and never resolves the requested hash - ([File: stackslib/src/net/atlas/download.rs])

### Summary
`AttachmentsBatchStateContext::extend_with_attachments` (lines 530-559) decodes a remote peer's `GetAttachmentResponse` via `decode_atlas_get_attachment()` and inserts `response.attachment` into `self.attachments` without ever checking that `Attachment::hash()` equals the `content_hash` (`H`) that was requested in the corresponding `AttachmentRequest`. Any peer can therefore answer with `Attachment::empty()` (or any other content), have the response counted as `bump_successful_requests()`, and cause the batch's tracked entry for `H` (`AttachmentsBatch::resolve_attachment`, called later in `run()` at line 168 using `attachment.hash()`, not `H`) to never be resolved.

### Finding Description
The state machine flow is: `get_prioritized_attachments_requests()` builds an `AttachmentRequest{ content_hash: H, sources, .. }` [1](#0-0) . Once the batched HTTP requests complete, `extend_with_attachments` processes each `(request, response)` pair:

```
if let Ok(response) = response.decode_atlas_get_attachment() {
    self.attachments.insert(response.attachment);
    report.bump_successful_requests();
} else {
    report.bump_failed_requests();
}
``` [2](#0-1) 

There is no comparison between `request.content_hash` (`H`) and `response.attachment.hash()`. `decode_atlas_get_attachment()` only parses well-formed hex-encoded JSON into a `GetAttachmentResponse`; it performs no hash validation [3](#0-2) . `Attachment::hash()` is simply `Hash160::from_data(&self.content)` and `Attachment::empty()` produces `content: vec![]` [4](#0-3) , whose hash is fixed and virtually never equal to an arbitrary on-chain-committed `H`.

Downstream, once the sub-state-machine reaches `Done`, `AttachmentsDownloader::run()` iterates `context.attachments.drain()` and resolves the batch using the **attachment's own hash**, not the originally requested hash:
```
for attachment in context.attachments.drain() {
    let attachments_instances = network.atlasdb.find_all_attachment_instances(&attachment.hash())?;
    network.atlasdb.insert_instantiated_attachment(&attachment)?;
    ...
    context.attachments_batch.resolve_attachment(&attachment.hash())
}
``` [5](#0-4) 

Because `resolve_attachment` matches by the attachment's actual hash against entries in `attachments_instances` (keyed by content_hash) [6](#0-5) , a forged empty attachment whose hash differs from `H` cannot match `H`'s entry. The `attachment_instance` for `H` therefore stays in `attachments_instances`, `has_fully_succeed()` returns false, and the batch is bumped for retry (`bump_retry_count`) and re-enqueued, eventually being dropped once `max_attachment_retry_count` is exceeded [7](#0-6) . Meanwhile the malicious peer's `ReliabilityReport` is credited with a *successful* request (`bump_successful_requests()`), which is factually wrong and increases that peer's future selection priority (`get_most_reliable_source` picks by `score()`) [8](#0-7) , compounding the starvation by making the malicious peer preferentially re-selected on retry.

Storage integrity of the AtlasDB itself is not broken: `insert_instantiated_attachment` keys the stored row by `attachment.hash()` computed locally from the actual content [9](#0-8) , so the garbage/empty attachment is stored under its own (different) hash, not under `H`. No non-canonical content is served *as* `H`. The concrete effect is denial of resolution for `H`, not forged content being accepted as authentic for `H`.

### Impact Explanation
An unprivileged remote peer that is selected as a download source for a given `content_hash` (obtained from `AttachmentRequest.sources`, populated from any responder to the earlier attachments-inventory request) can return a bogus/empty `Attachment` and have it counted as a successful download. The concrete effect: the specific on-chain-committed attachment `H` (e.g., a BNS zonefile hash) is never resolved by that peer's response, is retried up to `max_attachment_retry_count`, and then the whole batch entry is dropped ("Atlas: dropping batch ... retries count exceeded"). This denies BNS zonefile/attachment resolution for that specific instance on the node, and repeatable per attachment/per retry cycle by any peer willing to answer such requests. This does not forge accepted-as-canonical content under `H`; it is a targeted read/availability degradation (attachment/BNS mismatch causing resolution loss), matching the "High" category ("attachment/BNS mismatch").

### Likelihood Explanation
- The attacker only needs to run an ordinary peer that answers the node's outbound `GET /v2/attachments/<hash>` request (or `getattachmentsinv`, to be included as a source) — no privileged role, no secret, no StackerDB slot ownership required.
- The victim node must have a pending unresolved `AttachmentInstance` for `H` and must select the attacker's peer as one of the `sources` for that content hash (which happens automatically once the attacker's inventory falsely/genuinely claims to have the page bit set for that index).
- Cost to the attacker is a single crafted HTTP response per targeted attachment; the effect is repeatable indefinitely, and can be applied against any newly emitted BNS attachment instance.
- No cryptographic verification barrier exists in this path (`decode_atlas_get_attachment` never checks the hash), so the guard the question is asking about (content hash equality) genuinely does not exist.

### Recommendation
In `extend_with_attachments` (stackslib/src/net/atlas/download.rs:530-559), after `decode_atlas_get_attachment()`, verify `response.attachment.hash() == request.content_hash` before inserting into `self.attachments` and before crediting `bump_successful_requests()`. On mismatch, call `report.bump_failed_requests()` and drop the response (optionally treat as a "faulty peer" for deregistration, consistent with other faulty-response handling in the batching system).

### Proof of Concept
Rust unit test (mirroring existing tests in `stackslib/src/net/atlas/tests.rs`, following patterns like `new_attachments_inventory_response`):

1. Construct an `AttachmentRequest { content_hash: H, sources: {peer_url}, .. }` where `H = Hash160::from_data(b"real content")`.
2. Build a `StacksHttpResponse` via `GetAttachmentResponse { attachment: Attachment::empty() }` serialized exactly as `RPCGetAttachmentRequestHandler`'s response format (JSON hex string of empty content), analogous to `new_attachments_inventory_response` but for `decode_atlas_get_attachment`.
3. Populate a `BatchedRequestsResult<AttachmentRequest>` with `succeeded = { (request, Some(response)) }` and an `AttachmentsBatchStateContext` whose `attachments_batch` contains a tracked instance with `content_hash == H`.
4. Call `context.extend_with_attachments(&mut results)`.
5. Assert: `context.attachments` contains `Attachment::empty()` (proving unauthenticated acceptance), and that after simulating the `run()` resolution step (`attachments_batch.resolve_attachment(&Attachment::empty().hash())`), `attachments_batch.resolve_attachment(&H)` was never effectively invoked — i.e., `attachments_batch.attachments_instances_count()` remains unchanged (entry for `H` still present), demonstrating `H` is never resolved despite receiving a "successful" response.
6. Additionally assert `report.bump_successful_requests()` was invoked for the malicious peer (via `self.peers.get(&peer_url).unwrap().score()` increasing), showing the reliability-report miscrediting.

    pub fn resolve_attachment(&mut self, content_hash: &Hash160) {
        for missing_attachments in self.attachments_instances.values_mut() {
            let mut keys = vec![];
            for (k, hash) in missing_attachments.iter() {
                if hash == content_hash {
                    keys.push(*k);
                }
            }
            for key in keys {
                missing_attachments.remove(&key);
            }
        }
    }
