### Title
Excess attached deposit not refunded on successful registration in `AddressRegistrar::register` - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar` contract (part of the eth-implicit wallet infrastructure) exposes a `#[payable]` `register` method that only validates a *lower bound* on the attached deposit (`given_deposit >= required_deposit`) but never refunds the difference when the deposit exceeds the exact storage cost on a successful (`Entry::Vacant`) registration. This is the same bug class as the Pyth `fullfillOracleQueryPyth` overpayment issue: the code checks `msg.value`/`attached_deposit` is *sufficient* but does not validate/refund it against the *exact* required amount.

### Finding Description
`AddressRegistrar::register` computes the exact storage cost needed to store the new `address -> account_id` mapping: [1](#0-0) 

It panics if `given_deposit < required_deposit`, but performs no comparison for the opposite direction. When the address slot is `Entry::Vacant` (i.e., registration succeeds), the contract inserts the mapping and returns the address — it does not send back any refund for `given_deposit - required_deposit`: [2](#0-1) 

By contrast, in the `Entry::Occupied` (collision, failure) branch, the code explicitly refunds the *entire* `given_deposit` back to the caller via a transfer promise: [3](#0-2) 

This asymmetry mirrors the reported Pyth pattern exactly: the contract validates a floor (`msg.value >= fee` / `given_deposit >= required_deposit`) but has no mechanism to return any excess above the exact cost when the call succeeds. Since `register` is a plain unprivileged, permissionless entry point reachable by any account (including via the Near Wallet Contract's `rlp_execute` flow used for Ethereum-style transactions), any user who over-attaches NEAR (e.g., due to client-side estimation error, or by copying a template that attaches a fixed "safe" amount) permanently loses the difference — it stays locked in the `AddressRegistrar` contract with no withdrawal path exposed in this contract.

### Impact Explanation
Impact is Medium: any ordinary user calling `register` with more deposit than the exact byte-cost required permanently loses the excess NEAR, since the contract has no owner/withdraw function shown in this file to recover it. This is a "permanent freezing/loss of funds" for the depositor, analogous to the accepted impact class ("theft or permanent freezing of funds").

### Likelihood Explanation
Likelihood is Medium: `attached_deposit()` amounts are frequently rounded up or over-estimated by callers/wallets/SDK helpers (e.g., attaching a flat 0.01 NEAR or similar buffer instead of computing the exact per-byte storage cost), especially since `account_id.len()` varies per call and callers may not compute it precisely client-side. Every such over-attachment on a successful (non-colliding) registration silently forfeits the excess.

### Recommendation
Mirror the pattern already used in the `Entry::Occupied` branch: after successfully inserting the entry in the `Entry::Vacant` branch, compute `excess = given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` of `excess` back to `env::predecessor_account_id()`, so that only the exact required storage cost is retained by the contract in both the success and failure paths.

### Proof of Concept
1. Compute `required_deposit = storage_byte_cost * (20 + account_id.len())` for a fresh, unregistered `account_id` (e.g., `"alice.near"`).
2. Call `register(account_id)` attaching `given_deposit = required_deposit + X` yoctoNEAR for any `X > 0`.
3. Observe the call succeeds (`Entry::Vacant` branch), the mapping is inserted, and the address string is returned.
4. Query the caller's account balance: it decreased by `required_deposit + X + gas_cost`, i.e., the full `X` excess is retained by `AddressRegistrar` with no refund receipt generated, unlike the `Entry::Occupied` branch which explicitly returns the full deposit.

*Note: I was unable to fully re-read the complete file contents (line-numbered view) to double-check whether there is a separate owner-only withdrawal method elsewhere in the same crate due to a tool access issue in the final iteration; the analysis above is based on the previously retrieved contents of `register`, `lookup`, and `get_address`, which show no such withdrawal path in this file.*
