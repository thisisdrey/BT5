### Title
Newly enabled reward tokens allow users to claim their whole token balance as rewards - ([File: contracts/RewardsDistributor.sol])

### Summary
`RewardsDistributor._calculateTokenDelta()` treats an uninitialized account index as `INITIAL_INDEX` only when the token index is strictly greater than `INITIAL_INDEX`. Immediately after a reward token is enabled, its token index equals `INITIAL_INDEX`, so the fallback is skipped and the uninitialized account index remains zero. A public call to `updateBeforeMintOrBurn()` then records `balanceOf(account) * INITIAL_INDEX` as accrued rewards, which can be withdrawn through `claimRewards()`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
When `_updateTokenSpeed()` enables rewards for a deposit or debt token whose `tokenStates[token].index` is still zero, it initializes the token state to `TokenState({index: INITIAL_INDEX, timestamp: block.timestamp})` and appends it to `tokens`. [4](#0-3) 

In the same timestamp, `_updateTokenIndex()` computes no elapsed time and leaves the index at `INITIAL_INDEX`. The subsequent account update reads `accountIndexOf[token][account] == 0`; because `_tokenIndex > INITIAL_INDEX` is false, `_accountIndex` is not normalized to `INITIAL_INDEX`. The code therefore calculates `deltaIndex = INITIAL_INDEX - 0` and `tokensDelta = token.balanceOf(account).wadMul(INITIAL_INDEX)`, which equals the account's entire tracked token balance. [5](#0-4) [6](#0-5) 

`updateBeforeMintOrBurn()` is permissionless and performs this update for any supplied account. The attacker can then call `claimRewards()`, which transfers `tokensAccruedOf[attacker]` if the distributor holds enough reward tokens. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker holding a newly reward-enabled deposit token or debt-token balance can mint an unearned accrual equal to that full raw token balance before any reward time has elapsed. Claiming drains the distributor's available `rewardToken` balance up to the inflated accrual, causing direct theft of reward funds and denial of rewards to legitimate users. The broken invariant is reward accrual: zero elapsed time should produce zero new rewards, not `balance * 1e18`. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The exploit requires a token whose reward state has index zero to be assigned a positive speed. That transition is performed by `updateTokenSpeed()` or the reward-rate synchronization path, but exploitation itself is a permissionless backrun in the same block: the attacker observes the reward-enabling transaction, calls `updateBeforeMintOrBurn(token, attacker)`, and then `claimRewards(attacker)` before a later timestamp advances the index above `INITIAL_INDEX`. No attacker-controlled privileged account, malicious oracle, or malformed token is needed. [11](#0-10) [12](#0-11) 

### Recommendation
Normalize a zero account index whenever the token has been initialized, not only when the token index exceeds `INITIAL_INDEX`. For example:

```solidity
if (_accountIndex == 0 && _tokenIndex >= INITIAL_INDEX) {
    _accountIndex = INITIAL_INDEX;
}
```

Alternatively, initialize `accountIndexOf[token][account]` during every account update before calculating delta, and add a regression test asserting that a holder who calls `updateBeforeMintOrBurn()` in the same block as speed activation accrues zero rewards. [6](#0-5) 

### Proof of Concept
A Foundry fork can reproduce the issue at the reward-state transition:

```solidity
function test_uninitializedAccountIndexClaimsFullBalance() external {
    // Existing deployed configuration.
    vm.prank(governor);
    rewardsDistributor.updateTokenSpeed(depositToken, 1e18);

    // Attacker already has a deposit-token balance and backruns in the same block.
    vm.prank(attacker);
    rewardsDistributor.updateBeforeMintOrBurn(depositToken, attacker);

    uint256 expectedInflatedAccrual = depositToken.balanceOf(attacker);
    assertEq(
        rewardsDistributor.tokensAccruedOf(attacker),
        expectedInflatedAccrual
    );

    vm.prank(attacker);
    rewardsDistributor.claimRewards(attacker);

    assertEq(rewardToken.balanceOf(attacker), expectedInflatedAccrual);
}
```

The key assertion is that `tokensAccruedOf(attacker)` becomes `depositToken.balanceOf(attacker)` despite zero elapsed reward time. The accrual follows directly from the missing `INITIAL_INDEX` fallback and the subsequent reward transfer path. [2](#0-1) [8](#0-7)
