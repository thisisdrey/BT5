**Rationale:** The premise fails at the verifier stage, before `create_receipt_id_from_transaction`/`create_hash_index` are ever reached.

`create_hash_index` derives the receipt id from `(tx_hash, block_height, salt)` [1](#0-0) , and `tx_hash` is a hash over the full `SignedTransaction`, which includes the transaction's `nonce`. Resubmitting the "exact same" transaction implies the exact same nonce for that `(signer_id, public_key)` access key. But `verify_nonce` requires the nonce to strictly exceed (or, in `Strict` mode, equal `current+1`) the access key's stored nonce [2](#0-1) , and this check runs in `verify_and_charge_tx_ephemeral` / `verify_and_charge_gas_key_tx_ephemeral` prior to any receipt generation [3](#0-2) [4](#0-3) . Once the transaction is included in any block, the access key's on-chain nonce is bumped to that transaction's nonce, so a second submission of the identical transaction (same nonce) at any later height — reorg replay or duplicate relay — is rejected with `InvalidNonce` before `create_receipt_id_from_transaction` is invoked at all.

Additionally, within a single chunk, exact duplicate transaction hashes are explicitly deduplicated via `seen_tx_hashes` under `UniqueChunkTransactions` [5](#0-4) , closing the duplicate-relay-to-two-producers path as well.

Since an unprivileged attacker cannot get the same-nonce transaction accepted twice (nonce monotonicity is enforced at the verifier, independent of block height or fork choice), there is no reachable path to a repeated `(tx_hash, block_height)` pair for a *legitimate* transaction, and thus no double-crediting of the receiver's deposit via `create_hash_index` collision. The scenario also implicitly relies on chain-reorg/duplicate-producer-relay behavior, which falls under excluded categories (block/chunk production, consensus/reorg paths) rather than attacker-reachable unprivileged-client behavior.
