### Title
Non-standard `ft_transfer` return value causes double-credit on withdraw resolution (mismatched resolver refund) - ([File: contracts/defuse/src/contract/tokens/nep141/withdraw.rs])

### Summary
`ft_resolve_withdraw` assumes that a successful, non-`_call` `ft_transfer()` invocation always returns an **empty** result, exactly mirroring the external report's assumption that `approve()` always returns a `bool`. When the withdrawn token's `ft_transfer` implementation deviates from the strict NEP-141 convention and returns any non-empty payload on success, the resolver misclassifies a successful external transfer as failed and re-credits the user internally — breaking the conservation invariant `amount debited == value delivered externally + value refunded internally`.

### Finding Description
`do_ft_withdraw` builds the outgoing call for a plain (non-`_call`) withdrawal: [1](#0-0) 

The result of that promise is later checked in `ft_resolve_withdraw`: [2](#0-1) 

`promise_result_checked_void` treats the call as a failure unless the promise succeeded **and** returned a payload of length `0`: [3](#0-2) 

Any `ft_transfer` implementation that succeeds but returns a non-empty payload (e.g. a `bool`, echoing the pre-`ft_transfer` amount, or any other non-standard-but-successful response — the direct NEAR analog of USDT's non-boolean `approve`) causes `promise_result_checked_void` to return `Err`, so `used = 0` and the full `amount` is refunded via `self.deposit(...)`: [4](#0-3) 

However, the balance for that `Nep141TokenId` was already debited from the user's internal ledger before the promise was scheduled, in `internal_ft_withdraw`'s call to `self.withdraw(...)`: [5](#0-4) 

Since `token` is a fully attacker-controlled/attacker-choosable value for deposits (defuse's deposit path accepts arbitrary NEP-141 contracts via `ft_on_transfer`, with no whitelist enforced in this code path), an attacker deploys/uses a token whose `ft_transfer` succeeds but returns non-empty data. The externally transferred funds are actually delivered to `receiver_id` (real custody left the contract), yet the internal ledger is also fully re-credited via the refund path — creating tokens on the internal ledger that are not backed by the contract's actual external token balance.

### Impact Explanation
This is a mismatched resolver refund exactly as enumerated in the Critical impact category: the resolver refunds an amount whose corresponding value was already delivered externally. Repeated exploitation inflates a user's internal balance for token `T` beyond the contract's real custodied balance of `T`. Because internal balances for a shared token are drawn from one common asset pool, this leads to insolvency: other legitimate holders of the same `T` inside defuse will be unable to withdraw their real balance once the pool is drained, i.e., funds are permanently frozen/lost for other users of the same token — a Critical-tier consequence per the accepted impact list.

### Likelihood Explanation
Exploitability only requires depositing and withdrawing any NEP-141 token whose `ft_transfer` implementation returns a non-empty successful result — a scenario the code explicitly does not defend against, unlike the `_call` branch which already has bespoke handling for non-standard responses (`Ok(Err(_deserialize_err)) => 0`) but the void branch has no equivalent tolerance and instead treats any non-empty successful response as an outright failure requiring full refund. Any attacker who can list/introduce such a token (a routine, permissionless action in this contract's deposit flow) can trigger it deterministically.

### Recommendation
In `ft_resolve_withdraw`'s non-`_call` branch, do not use an all-or-nothing "empty means success" check. Instead, treat the underlying promise's **success/failure status** (ignoring payload contents/length) as authoritative for whether the transfer occurred, mirroring the safer pattern already used for the `_call` branch's error handling; or, at minimum, distinguish "promise failed" from "promise succeeded but had an unexpected non-empty payload" and only refund in the former case.

### Proof of Concept
1. Attacker deploys (or uses) an NEP-141-token contract `T` whose `ft_transfer()` implementation performs the transfer correctly but returns a non-empty value (e.g. `true`) instead of the standard empty result — a valid, non-malicious deviation similar to USDT's non-boolean `approve`.
2. Attacker deposits `X` of `T` into defuse via the standard `ft_transfer_call`/`ft_on_transfer` deposit flow, crediting their internal balance by `X`.
3. Attacker calls `ft_withdraw(token=T, receiver_id=attacker, amount=X, msg=None)`. `internal_ft_withdraw` debits `X` from the internal ledger and schedules `do_ft_withdraw` → plain `ft_transfer` (non-`_call` path) → `ft_resolve_withdraw`. [6](#0-5) 
4. `T.ft_transfer` executes successfully and delivers `X` to `attacker` externally, but returns a non-empty payload.
5. In `ft_resolve_withdraw`, `promise_result_checked_void(0)` returns `Err` because the payload length is `>0`, so `used = 0` and `refund = X` is credited back to `attacker`'s internal balance. [7](#0-6) 
6. Attacker now holds `X` externally (already received) plus `X` credited internally — net `2X` value from a single deposit of `X`, breaking `debited == delivered + refunded` and draining the shared pool backing other holders of `T`.

        &mut self,

        force: bool,

            &owner_id,
            iter::once((
                Nep141TokenId::new(withdraw.token.clone()).into(),
                withdraw.amount,
            ))
            .chain(withdraw.storage_deposit.map(|amount| {
                (
                    Nep141TokenId::new(self.wnear_id().into_owned()).into(),
                    amount.as_yoctonear(),
                )
            })),
            Some("withdraw"),
            force,
        )?;

        let is_call = withdraw.is_call();
        Ok(if let Some(storage_deposit) = withdraw.storage_deposit {
            ext_wnear::ext(self.wnear_id.clone())
                .with_attached_deposit(NearToken::from_yoctonear(1))
                .with_static_gas(NEAR_WITHDRAW_GAS)
                // do not distribute remaining gas here
                .with_unused_gas_weight(0)
                .near_withdraw(U128(storage_deposit.as_yoctonear()))
                .then(
                    // schedule storage_deposit() only after near_withdraw() returns
                    Self::ext(env::current_account_id())

                                .unwrap_or_else(|err| err.panic()),
                        )
                        .do_ft_withdraw(withdraw.clone()),
                )
        } else {
            Self::do_ft_withdraw(withdraw.clone())
        }
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(Self::FT_RESOLVE_WITHDRAW_GAS)

                .with_unused_gas_weight(0)
                .ft_resolve_withdraw(withdraw.token, owner_id, withdraw.amount.into(), is_call),
        )
        .into())
    }

/// Returns `Ok(())` if the promise at `result_idx` succeeded with an empty result.
/// This is the expected outcome for void-returning cross-contract calls
/// (e.g. `ft_transfer`, `nft_transfer`, `mt_batch_transfer`).
#[inline]
pub fn promise_result_checked_void(result_idx: u64) -> PromiseResult<()> {
    let data = env::promise_result_checked(result_idx, 0)?;
    debug_assert!(data.is_empty());
    Ok(())
}
