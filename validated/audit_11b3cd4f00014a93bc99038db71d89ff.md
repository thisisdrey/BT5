### Title
Unbounded `estimated_len` from JSON body causes `u64` multiplication overflow in fee estimation - (File: stackslib/src/net/api/postfeerate.rs)

### Summary
The `estimated_len` field of the `/v2/fees/transaction` POST body is a raw `Option<u64>` deserialized directly from attacker-supplied JSON with no upper bound check, and is only ever compared with `payload_data.len()` via `std::cmp::max` at [1](#0-0) . This value is later multiplied by `MINIMUM_TX_FEE_RATE_PER_BYTE` in `estimate_tx_fee_from_cost_and_length` at [2](#0-1)  with no overflow protection, so an attacker can drive the multiplication to overflow `u64`.

### Finding Description
`try_parse_request` enforces `0 < content_len < MAX_PAYLOAD_LEN` on the raw HTTP body byte length at [3](#0-2) , but this only bounds the size of the JSON text, not the numeric value encoded inside it. A tiny JSON payload such as `{"estimated_len": 18446744073709551615, "transaction_payload": "0x00...00"}` easily fits under `MAX_PAYLOAD_LEN` while setting `estimated_len` to `u64::MAX`.

`estimated_len` is computed only as `max(body.estimated_len.unwrap_or(0), payload_data.len() as u64)` at [1](#0-0) , so the attacker-chosen value passes through unclamped and is stored in `self.estimated_len` at [4](#0-3) .

In `try_handle_request`, this value is forwarded unmodified to `estimate_tx_fee_from_cost_and_length` at [5](#0-4) , which computes `let minimum_fee = estimated_len * MINIMUM_TX_FEE_RATE_PER_BYTE;` at [2](#0-1)  using an ordinary `*` operator with no `checked_mul`/`saturating_mul` guard. There is no minimum/maximum sanity check applied to `estimated_len` anywhere between the JSON parse and this multiplication.

Since `MINIMUM_TX_FEE_RATE_PER_BYTE` is a fixed positive constant, any `estimated_len` value greater than `u64::MAX / MINIMUM_TX_FEE_RATE_PER_BYTE` (trivially reachable by supplying `u64::MAX` in the JSON body) causes the multiplication to overflow. This endpoint requires no authentication — it is a plain RPC POST handler routed under `/v2/fees/transaction`.

### Impact Explanation
In a debug build (or any build compiled with `overflow-checks = true`, which is common for testnets/CI and some node operators), this multiplication panics, crashing the thread handling the request — an unauthenticated, single-request remote DoS. In a release build without overflow checks, the multiplication silently wraps, producing an attacker-steered, semantically incorrect `minimum_fee` value returned to any client that queries this endpoint (a shared read endpoint), which is a data-integrity concern for fee estimation but not a crash. The panic case matches the Critical DoS category (remote crash from a single unauthenticated message); the release-mode wraparound matches at most a High "bounded compute DoS/incorrect data on a read endpoint" characterization.

### Likelihood Explanation
No preconditions beyond node's RPC port being reachable and fee/cost estimators being configured (`rpc_args.get_estimators_ref()` must return `Some`, checked at [6](#0-5) , which is standard for nodes running the estimator subsystem). The attacker needs only to send one small, well-formed JSON POST with a huge `estimated_len` integer literal; no signature, secret, or peer relationship is required. This is trivially repeatable.

### Recommendation
Clamp/validate `estimated_len` at parse time in `try_parse_request`, e.g. reject values above `MAX_PAYLOAD_LEN` (or some sane maximum transaction length), and/or use `checked_mul`/`saturating_mul` in `estimate_tx_fee_from_cost_and_length` when computing `minimum_fee` so that an out-of-range `estimated_len` results in a graceful `HttpBadRequest` rather than an overflow.
