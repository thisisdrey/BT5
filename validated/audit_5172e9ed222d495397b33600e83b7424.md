### Title
Stale self-targeted postponed/yielded receipts survive `DeleteAccount` and execute privileged actions (DeployContract/AddKey/Stake/DeleteKey) against a re-registered account - (File: `core/store/src/utils/mod.rs`, `runtime/runtime/src/actions.rs`, `runtime/runtime/src/lib.rs`)

### Summary
`remove_account` (`core/store/src/utils/mod.rs:504-575`), invoked by `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`), only removes `Account`, `ContractCode`, `AccessKey`/`GasKeyNonce`, and `ContractData` entries for the deleted account. It never touches `TrieKey::PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `PromiseYieldTimeout`/`PromiseYieldIndices`, or `ReceivedData` rows keyed by that account. Because `check_actor_permissions` authorizes `DeployContract`/`AddKey`/`DeleteKey`/`Stake` purely via `actor_id == account_id` (`runtime/runtime/src/actions.rs:739-784`), and `actor_id` for a resumed postponed/yielded receipt is seeded from the receipt's own stale `predecessor_id` (`runtime/runtime/src/lib.rs:855`), a self-targeted receipt an account's owner queued *before* deleting that account will still pass authorization and execute against whichever account later reuses that name.

### Finding Description
1. **Creating the dangling receipt.** While A still exists and is owned by the attacker, the attacker's own contract on A issues a promise chain that ends in a self-call receipt (`predecessor_id == receiver_id == A`) carrying `actions = [DeployContractAction{code: backdoor}]` with an unmet `input_data_id`. This is stored via `set_postponed_receipt`/`process_action_receipt` (`runtime/runtime/src/lib.rs:1589-1657`) as `TrieKey::PostponedReceipt{receiver_id: A, receipt_id}`, `PostponedReceiptId{receiver_id: A, data_id}`, `PendingDataCount{receiver_id: A, receipt_id}`. Alternatively (and more controllably), the attacker uses `promise_yield_create` so the continuation is parked as a `PromiseYieldReceipt` plus a `PromiseYieldTimeout{account_id: A, data_id, expires_at}` entry (`runtime/runtime/src/function_call.rs:160-169`), guaranteeing eventual, fully-automatic resolution at a known block height via `resolve_promise_yield_timeouts` (`runtime/runtime/src/lib.rs:2986` per the spec notes) with **no further attacker transaction required**.
2. **Deleting the account.** The attacker (owner of A, holding a full-access key) submits `DeleteAccount(A)`. `action_delete_account` (`runtime/runtime/src/actions.rs:314-390`) calls `remove_account` (`core/store/src/utils/mod.rs:504-575`), which deletes only `Account`, `ContractCode`, access/gas keys, and `ContractData`. The postponed/yield trie rows above are never enumerated or removed.
3. **Reuse of the name.** After A is deleted, an unrelated party C creates a new account with the same id A (e.g. as a sub-account they control, or via registrar for a released top-level name).
4. **Resurrection.** Either (a) the previously in-flight `DataReceipt`/`PromiseResume` for the dependency arrives, or (b) the promise-yield timeout fires automatically at the pre-computed block height. In both cases the runtime looks up `PostponedReceipt`/`PromiseYieldReceipt` keyed only by `{receiver_id: A, ...}` (`runtime/runtime/src/lib.rs:1398-1455`, `:1500-1534`) — with no check that the account instance is the "same" logical account — and executes the stored receipt via `apply_action_receipt`.
5. **Authorization bypass.** Inside `apply_action_receipt`, `actor_id` is initialized from the stale receipt's own `predecessor_id` (`runtime/runtime/src/lib.rs:855`: `let mut actor_id = receipt.predecessor_id().clone();`), which is A. `check_actor_permissions` for `DeployContract` only checks `actor_id != account_id` (`runtime/runtime/src/actions.rs:746-760`); since both are A, the check passes with **no reference to C's access keys**, and `action_deploy_contract` installs the attacker's backdoor code on C's account.

The root cause is the absence of any account "incarnation"/generation binding: `TrieKey`s for postponed/yielded receipts are namespaced only by `AccountId` string, not by any nonce tied to the account's lifetime, and `remove_account` does not purge them on deletion.

### Impact Explanation
This is a full authorization-escalation / account-takeover primitive: an attacker can plant a time-bomb that deploys arbitrary contract code (or adds a full-access key, stakes, deletes a key, etc., since all of `DeployContract`/`AddKey`/`DeleteKey`/`Stake` share the same `actor_id == account_id` check) on any account name they once owned, to be detonated after that name is deleted and reassigned to a victim — without the victim ever signing the malicious action. This matches the "authorization escalation across accounts" and "arbitrary contract deployment / account takeover" bounty categories.

### Likelihood Explanation
- The attacker needs only to be the original owner of account A (own unprivileged funded account, ordinary contract deployment/signing capability) — no validator, node, or leaked-key access required.
- `DeleteAccount` with an outstanding postponed/yielded self-receipt is fully permitted by current validation; nothing in `validate_receipt`/`validate_actions_with_mode` rejects deleting an account that still has unresolved input-data dependencies.
- The promise-yield timeout path makes the trigger deterministic and requires zero further attacker interaction, only patience for the account name to be reused before `yield_timeout_length_in_blocks` elapses (or the attacker can keep the dependency chain alive/replayed to extend the effective window).
- Repeatable for any account the attacker controls and later abandons/sells; cost is limited to normal transaction/storage fees.
- Uncertainty: I could not verify within the available search budget whether some other, unindexed cleanup pass (e.g., background state GC) separately purges these trie rows on deletion; no such mechanism was found in `remove_account`, `action_delete_account`, or the receipt-processing code inspected. This should be confirmed with a live runtime integration test as described below.

### Recommendation
On `DeleteAccount`, enumerate and remove all account-scoped receipt-lifecycle state before or as part of `remove_account`: `PostponedReceipt`, `PostponedReceiptId`, `PendingDataCount`, `ReceivedData`, `PromiseYieldReceipt`, `PromiseYieldStatus`, `YieldIdToDataId`/`DataIdToYieldId`, and drop/ignore matching `PromiseYieldTimeout` entries in `resolve_promise_yield_timeouts` when the account no longer exists. As defense in depth, bind receipts to an account "incarnation" (e.g., re-derive/validate `actor_id` against the account's current existence/generation rather than trusting the stored stale `predecessor_id`) so a self-receipt from a deleted account's former lifetime cannot authorize actions against a subsequently created account of the same name.

### Proof of Concept
Runtime/integration test outline (extending `runtime/runtime/src/tests/apply.rs` or a `test-loop-tests` scenario):
1. Create account `A` owned by signer `attacker`.
2. From `A`, submit a `FunctionCall` that internally issues `promise_yield_create` and chains a self-call continuation `[DeployContractAction{code: BACKDOOR_WASM}]` on `A` (predecessor==receiver==A); assert `PromiseYieldReceipt{receiver_id: A, data_id}` and a `PromiseYieldTimeout` entry exist in state.
3. Submit `DeleteAccount(A, beneficiary)` from `attacker`; assert `get_account(A)` is `None` but `get_promise_yield_receipt(state, &A, data_id)` and the queued timeout entry are still present (this alone demonstrates the storage-cleanup bug).
4. Submit `CreateAccount` actions from an unrelated `victim` signer that recreate `A` (e.g., as `victim`'s sub-account) and deploy a legitimate contract / add `victim`'s key.
5. Advance blocks past `yield_timeout_length_in_blocks` so `resolve_promise_yield_timeouts` synthesizes the `PromiseResume{data: None}` automatically, or directly deliver the pending `DataReceipt`/`PromiseResume` for `data_id`.
6. Assert that after processing, `get_account(A).contract()`/`local_contract_hash()` equals `BACKDOOR_WASM`'s hash, proving the backdoor was deployed on `victim`'s account without `victim` ever signing a `DeployContract` transaction.
