### Title
Unbounded array allocation from attacker-controlled length in TVM precompiled-contract signature/array extraction helpers - (File: `actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java`)

### Summary
`PrecompiledContracts.extractBytes32Array`, `extractBytesArray`, and `extractSigArray` read an array-length value directly from calldata (via `words[offset].intValueSafe()`) supplied to a precompiled contract call and immediately use it to allocate a `byte[len][]` array, with no upper bound check against a sane maximum or against the actual size of the input buffer before allocation.

### Finding Description
In `extractBytes32Array`:
```java
private static byte[][] extractBytes32Array(DataWord[] words, int offset) {
  int len = words[offset].intValueSafe();
  byte[][] bytes32Array = new byte[len][];
  ...
``` [1](#0-0) 

and similarly in `extractBytesArray` / `extractSigArray`:
```java
int len = words[offset].intValueSafe();
byte[][] bytesArray = new byte[len][];
``` [2](#0-1) [3](#0-2) 

`len` originates from a `DataWord` decoded straight out of the precompile's `data` argument (a 256-bit word taken from the calldata an arbitrary contract call supplies to the precompile), and `intValueSafe()` converts an arbitrary 256-bit value to an `int`. Unlike `isValidAbiEncoding` (which only checks total data length is a multiple of the word size and consistent tail length, not that `len` is bounded to something the actual buffer can support), there is no explicit clamp of `len` to, e.g., the remaining bytes in `words`/`data` before the allocation happens. A crafted, tiny calldata payload can therefore encode a huge `len` (up to `Integer.MAX_VALUE`), causing the JVM to attempt to allocate an array of that many pointer slots immediately, well before any per-element bounds check on `words[offset + i + 1]` would fail.

This mirrors the CVE-2017-8327 bug class: a length value taken directly from untrusted input is used to size a memory allocation without validating it against a sane/derivable maximum, leading to attacker-triggered excessive memory consumption from a small malicious input.

### Impact Explanation
A successful trigger causes the node's JVM to attempt an oversized array allocation while executing a smart-contract-invoked precompile. Depending on heap headroom this throws `OutOfMemoryError`/`NegativeArraySizeException` inside TVM execution or induces heavy GC pressure/memory exhaustion affecting the whole node process (denial of service to block processing/serving). Because this executes inside contract/transaction execution (not a segregated sandbox with its own resource ceiling beyond energy accounting), a memory-consumption fault here can impact node availability for all callers, not just the calling transaction.

### Likelihood Explanation
Reachability requires only that some precompiled contract path passes attacker-influenced `data` into these helpers with an `offset` an attacker controls (directly or indirectly via calldata layout). I was not able to fully confirm, within the available tool budget, which specific precompiled contract(s) invoke `extractBytesArray`/`extractSigArray`/`extractBytes32Array` in this codebase (the grep only surfaced their definitions within `PrecompiledContracts.java`, not the exact call sites/contract class), so I cannot state with full certainty that the vulnerable path is reachable from an ordinary, permissionless contract call today, nor whether some caller already imposes a stricter upstream bound on `len` before invoking these helpers. This uncertainty should be resolved by inspecting the call sites of these three methods and the energy-cost/gas-metering that gates execution of whichever precompile uses them, since energy metering may make an attack economically costly per call but does not eliminate the missing bounds check itself.

### Recommendation
Before allocating `new byte[len][]` (and similarly `new byte[len]` anywhere `len` is derived from `intValueSafe()`), validate `len` against both a reasonable protocol-defined maximum and against the actual remaining size of `words`/`data`, rejecting the call (returning failure, not throwing) when `len` is inconsistent with the supplied buffer — the same pattern already used by `isValidAbiEncoding` and by `RLP.verifyLength` elsewhere in this codebase. This should be added at each of the three extraction helpers.

### Proof of Concept
Conceptually: deploy a contract that calls a precompiled contract address whose implementation reaches `extractBytesArray`/`extractSigArray`/`extractBytes32Array`, with calldata word at `offset` set to a very large value (e.g., `0x7fffffff`). This causes an immediate `new byte[0x7fffffff][]` allocation attempt inside the node's TVM execution before any subsequent per-element bounds checks run. I was unable to construct the full end-to-end PoC transaction because the exact calling precompiled-contract class (and its address/selector) could not be located within the remaining investigation budget.
