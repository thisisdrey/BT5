### Title
Front-runnable, unauthenticated `initialize` allows permanent DoS of vault bootstrap - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and sibling vault contracts)

### Summary
Each Zest v2 vault contract (`v0-vault-stx.clar`, `v0-vault-sbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`) exposes a public `initialize` function that anyone can call, with no `check-dao-auth` or `check-caller-auth` gate, unlike every other privileged setter in the same contract (`set-authorized-contract`, `set-flashloan-permissions`) which explicitly calls `check-dao-auth`.

### Finding Description
`initialize` is guarded only by a one-time state flag, not by a caller check: [1](#0-0) 

Compare this to the privileged functions immediately below it, which do call `check-dao-auth`: [2](#0-1) 

The DAO's intended bootstrap flow calls `initialize` on all vaults from a single proposal transaction, funded by the DAO executor: [3](#0-2) 

Because `initialize` has no caller restriction, any ordinary account can call it directly ahead of the DAO proposal, as long as they can supply `MINIMUM-LIQUIDITY` of the underlying token to pay for the seed deposit. This mirrors the report's bug class: an unprivileged, permissionless "create the initialization artifact first" front-run that causes the legitimate initializer's later `init`-style call to revert due to an already-satisfied precondition (`ERR-ALREADY-INITIALIZED` here, "already in use" ATA collision in the Solana report).

### Impact Explanation
When the DAO's `proposal-init-vaults` (or `proposal-protocol-init`) executes and reaches `(contract-call? .vault-X initialize)` inside a `try!` chain, if an attacker has already called `initialize` on that vault directly, the call returns `ERR-ALREADY-INITIALIZED` and the `try!` aborts the entire proposal transaction — including the cap-setting and `set-authorized-contract` steps bundled in the same proposal. Since Clarity proposals are all-or-nothing and re-executing a DAO proposal typically requires a new governance vote/threshold, this can indefinitely delay/deny market bootstrap for the affected vault (temporary freezing of funds/functionality for depositors and the protocol as a whole, since the vault cannot be authorized and used until re-proposed and passed by the DAO). This lands on the in-scope **High** impact class: temporary freezing of funds (vault deposits/functionality unusable until DAO re-executes a corrected proposal).

### Likelihood Explanation
Likelihood is high: `initialize` requires no privileged signer, only enough of the underlying token to cover `MINIMUM-LIQUIDITY` (a small seed amount), and the vault/proposal contract addresses are public and deterministic, so an attacker can trivially front-run the DAO's bootstrap transaction the moment it becomes visible in the mempool (or simply call it before the DAO even proposes it).

### Recommendation
Add a caller check to `initialize`, e.g. restrict it to `tx-sender == .dao-executor` (via `check-dao-auth`) or to the `dao-executor`'s pending proposal context, matching the pattern already used by `set-authorized-contract`/`set-flashloan-permissions` in the same file. Alternatively, make `initialize` idempotent for the DAO path — check specifically whether the vault is not yet initialized *and* that the caller is the DAO executor before proceeding, so an attacker cannot pre-empt or permanently poison the initialization step.

### Proof of Concept
1. Deploy protocol per test-setup flow (`local-testing/tests/setup/protocol-init.test.ts`), but before the DAO proposal `proposal-init-vaults` is executed.
2. An attacker account (e.g. `alice`) acquires a minimal balance of the vault's `UNDERLYING` token (equal to `MINIMUM-LIQUIDITY`, e.g. 1000 units for `vault-sbtc`).
3. Attacker directly calls `(contract-call? .vault-sbtc initialize)` — this succeeds because there is no auth check, setting `initialized` to `true` and depositing `MINIMUM-LIQUIDITY` to `NULL-ADDRESS` from the attacker's own funds.
4. The DAO subsequently executes `proposal-init-vaults`, which internally calls `(try! (contract-call? .vault-sbtc initialize))`; this now returns `ERR-ALREADY-INITIALIZED` (`801003`, as asserted in `local-testing/tests/setup/protocol-init.test.ts:188-195`), causing the entire proposal transaction (including cap-setting and `set-authorized-contract` for `.market`) to abort.
5. The vault remains uninitialized-from-DAO's-perspective in terms of authorization/config, and the DAO must draft, vote on, and execute a brand-new proposal to work around the state, at attacker's negligible cost, repeatable for every unlaunched vault. [4](#0-3)
