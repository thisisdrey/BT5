## Analysis

The Grafana bug class — a party with limited write access on an object being able to overwrite that object's ACL to grant themselves admin — maps to java-tron's multi-sig **Active permission** model and `AccountPermissionUpdateContract`.

### Title
Active-Permission Signer Can Overwrite Owner Permission via AccountPermissionUpdateContract, Seizing Full Account Control - (File: actuator/src/main/java/org/tron/core/actuator/AccountPermissionUpdateActuator.java)

### Summary
An account owner may delegate a low-threshold "Active" permission to a co-signer and authorize it (via the `operations` bitmask) to submit `AccountPermissionUpdateContract` transactions for convenience (e.g., delegated key management). Because the actuator does not require that the signer act under the account's **Owner** permission specifically, any signer who meets only the (typically much lower) Active-permission threshold can completely replace the account's Owner permission, Witness permission, and all Active permissions — effectively evicting every other keyholder and seizing exclusive control of the account, analogous to the Grafana Editor overwriting a dashboard's ACL to grant itself Admin.

### Finding Description
`AccountPermissionUpdateActuator.execute()` unconditionally overwrites the account's permission set with whatever is supplied in the contract, via `AccountCapsule.updatePermissions()`: [1](#0-0) [2](#0-1) 

Signature/permission authorization for this transaction is delegated to the generic `permissionId` mechanism, not to a rule requiring Owner-level authority to update permissions. `TransactionCapsule.checkPermission()` only verifies that the signer's Active permission's `operations` bitmask includes the bit for the contract type being submitted — it does not special-case `AccountPermissionUpdateContract` to require Owner-only authorization: [3](#0-2) 

And `validateSignature()`/`getPermissionById()` simply resolve whichever permission ID the transaction specifies (Owner id=0, Witness id=1, or any Active id≥2) and check the *that permission's* threshold, not the Owner permission's threshold: [4](#0-3) [5](#0-4) 

`AccountPermissionUpdateActuator.validate()` only validates the *structural* correctness of the newly proposed Owner/Witness/Active permissions (key counts, thresholds, address validity, allowed contract-type bits) — it never checks that the caller is acting under the existing Owner permission or that the new Owner permission preserves the original owner's keys: [6](#0-5) 

Consequently, if an account owner grants any Active permission the bit for `AccountPermissionUpdateContract` in its `operations` field (a legitimate, supported configuration for delegated administration), any signer(s) who reach that Active permission's threshold — which can be set arbitrarily low (as low as weight 1 with threshold 1) — can submit an `AccountPermissionUpdateContract` transaction that replaces the account's Owner permission with a permission containing only their own key, locking out the original owner(s) entirely and gaining unilateral control of the account (including its balance and any associated staked/voting/witness rights).

### Impact Explanation
This results in concrete unauthorized account takeover: a party with only limited, delegated Active authority can overwrite the account's Owner permission and exclude legitimate owners, gaining full control over funds, delegated resources, and any witness/voting rights tied to the account — a permanent, unauthorized privilege escalation matching "concrete unauthorized account operation" impact criteria.

### Likelihood Explanation
Exploitation requires only that the victim account's owner has previously configured an Active permission whose `operations` bitmask permits `AccountPermissionUpdateContract` — a supported, non-exotic multi-sig configuration for delegated administration (e.g., a "co-admin" key with a low threshold). Any keyholder meeting that Active permission's threshold can then broadcast a single, ordinary `AccountPermissionUpdateContract` transaction with no further access needed; no chain-halting or consensus-level compromise is required.

### Recommendation
Require that `AccountPermissionUpdateContract` transactions be authorized exclusively under the account's current **Owner** permission (`permissionId == 0`), regardless of what bits are set in any Active permission's `operations` field, since this contract type inherently changes trust roots for the account. Alternatively, explicitly exclude `AccountPermissionUpdateContract` from the set of contract types assignable to Active permission `operations` in `checkPermission()`/`getAvailableContractType()`.

### Proof of Concept
1. Account owner `O` creates an Active permission `A` (id=2) with threshold 1, containing only key `K` (a delegated co-signer), and sets `operations` to include the bit for `AccountPermissionUpdateContract` (permitted by `AccountPermissionUpdateActuator.checkPermission()`, which only rejects bits outside `getAvailableContractType()`).
2. Key `K` alone constructs an `AccountPermissionUpdateContract` transaction for account `O`, setting `permissionId = 2` (Active `A`), and defines a brand-new Owner permission containing only `K`'s own address.
3. `TransactionCapsule.validateSignature()` resolves permission `A` via `getPermissionById(2)`, and `checkPermission()`/`checkPermissionOperations()` confirm the contract type is allowed by `A`'s bitmask — signature validation succeeds with only `K`'s single signature meeting `A`'s threshold of 1.
4. `AccountPermissionUpdateActuator.execute()` calls `updatePermissions()`, replacing `O`'s Owner permission with the attacker-controlled one; `K` now solely controls the account, and the original owner keys are permanently locked out. [7](#0-6)

  public void updatePermissions(Permission owner, Permission witness, List<Permission> actives) {
    Builder builder = this.account.toBuilder();

    owner = owner.toBuilder().setId(0).build();
    builder.setOwnerPermission(owner);
    if (witness != null && builder.getIsWitness()) {
      witness = witness.toBuilder().setId(1).build();
      builder.setWitnessPermission(witness);
    }

    builder.clearActivePermission();
    if (actives != null) {
      for (int i = 0; i < actives.size(); i++) {
        Permission permission = actives.get(i).toBuilder().setId(i + 2).build();
        builder.addActivePermission(permission);
      }
    }

    this.account = builder.build();
  }
