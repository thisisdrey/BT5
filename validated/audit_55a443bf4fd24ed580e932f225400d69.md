### Title
Unbounded array allocation from attacker-controlled length word in `extractBytes32Array` (TVM precompiled contract input decoding) - (File: actuator/src/main/java/org/tron/core/vm/PrecompiledContracts.java)

### Summary
The Bento4 CVE-2018-20095 bug class is "a crafted length field, taken directly from untrusted input and used to size a memory allocation, without validating that it is reasonable relative to the actual data available, causes an attempt at excessive memory allocation." The analogous pattern exists in java-tron's TVM precompiled-contract call-data decoder `extractBytes32Array`, which is reachable by any account that can call a contract triggering a precompile that uses this helper to decode a dynamic array parameter.

### Finding Description
`extractBytes32Array` reads the declared array length directly from the calldata word array and immediately allocates an array of that size, with no upper bound check and no validation against the actual size of the supplied `data`/`words`: [1](#0-0) 

Compare this to the sibling helpers in the same file, `extractBytesArray` and `extractSigArray`, which at least perform a bounds check (`if (offset > words.length - 1) return new byte[0][];`) before reading the length word: [2](#0-1) 

`extractBytes32Array` has neither that offset-bounds check nor any cap on `len` before executing `new byte[len][]`. Since `len` is derived from `words[offset].intValueSafe()`, an attacker fully controls this value (up to `Integer.MAX_VALUE`) via TVM call data, independent of how much real payload data is actually supplied. This mirrors the Bento4 `EnsureCapacity` flaw: a size value taken from crafted/untrusted input is used to size an allocation before the input is validated to actually contain that much data.

### Impact Explanation
Any unprivileged account can call a smart contract (or directly invoke the relevant precompiled contract address) with crafted call data whose declared array-length word is set to a very large value (e.g., `0xFFFFFFFF`). Because the node must execute the same TVM opcode/precompile logic on every node applying the block (deterministic execution in `Manager`), a single crafted transaction that reaches this code path can trigger a huge/failing allocation (`OutOfMemoryError`) on every full node that processes the transaction/block, resulting in a network-wide node crash/halt — one of the explicitly accepted impacts under the validation rules (node crash or halt).

### Likelihood Explanation
Reaching this code only requires deploying/calling a contract that invokes the relevant precompiled contract with attacker-supplied call data, i.e., something any transaction broadcaster can do; no special privilege, signer role, or SR/witness status is needed. The missing bounds check makes exploitation straightforward: set the length word arbitrarily large while providing a much shorter payload.

### Recommendation
Add validation before allocation in `extractBytes32Array`, mirroring the pattern already used in `extractBytesArray`/`extractSigArray`:
1. Verify `offset` is within `words.length` before reading the length word.
2. Cap `len` against a sane maximum (e.g., bound it by the remaining number of words available, or a fixed protocol-defined maximum array size) before calling `new byte[len][]`.
3. Reject with an execution failure (as other functions do, e.g. returning `new byte[0][]`) instead of allocating based on unchecked attacker input.

### Proof of Concept
1. Craft TVM call data for the precompiled contract/opcode path that invokes `extractBytes32Array(words, offset)`, setting the calldata word at `offset` to `0xFFFFFFFF` (or another very large 32-bit value) while keeping the rest of the calldata short.
2. Submit this as a normal `TriggerSmartContract` transaction from any funded account.
3. When the node's TVM interpreter reaches the code path that decodes this array via `extractBytes32Array`, it executes `new byte[len][]` with the attacker-supplied `len`, triggering an out-of-memory allocation attempt during block/transaction execution on every node applying that transaction.

Note: I was only able to locate the definition of `extractBytes32Array` and one additional reference to it in `PrecompiledContracts.java`; due to tool-call limits I could not fully trace the exact precompiled-contract entry point (e.g., which specific `execute()` method/opcode invokes it) to build a fully concrete end-to-end call-data example. A Devin session with full-repo access would be needed to confirm the exact caller and construct exact byte-level PoC call data.

  private static byte[][] extractBytesArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
    int len = words[offset].intValueSafe();
    byte[][] bytesArray = new byte[len][];
    for (int i = 0; i < len; i++) {
      int bytesOffset = words[offset + i + 1].intValueSafe() / WORD_SIZE;
      int bytesLen = words[offset + bytesOffset + 1].intValueSafe();
      bytesArray[i] = extractBytes(data, (bytesOffset + offset + 2) * WORD_SIZE,
          bytesLen);
    }
    return bytesArray;
  }

  private static byte[][] extractSigArray(DataWord[] words, int offset, byte[] data) {
    if (offset > words.length - 1) {
      return new byte[0][];
    }
