Audit Report

## Title
Reward-per-token accumulator rounds down to zero for pools with large `total_tokens_staked`, permanently freezing staker rewards - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `reward_per_token` computes the per-token reward delta using a fixed `PRECISION_SCALING_FACTOR` of `4096` (`u16`) rather than a wide fixed-point base, and divides by the permissionlessly-controlled `total_tokens_staked` via `ensure_div`, which only errors on division-by-zero, not on truncation. [1](#0-0) [2](#0-1)  Because both pool creation and staking are exposed to any signed account in shipped runtimes, an attacker (or even ordinary large stakers using an 18-decimal asset) can drive `total_tokens_staked` high enough that `reward_rate_per_block * blocks_elapsed * 4096` never exceeds it, permanently zeroing the reward accumulator and locking reward-asset funds already deposited in the pool's account.

## Finding Description
`reward_per_token` computes: `reward_per_token_stored + (reward_rate_per_block * rewardable_blocks_elapsed * PRECISION_SCALING_FACTOR) / total_tokens_staked`. [3](#0-2)  `EnsureDiv::ensure_div` performs ordinary integer division and only surfaces an error for division-by-zero (guarded separately by the `total_tokens_staked.is_zero()` check), so ordinary truncation to `0` when the numerator is smaller than the denominator is silent and unflagged. `derive_rewards` then multiplies the staker's stake by the (possibly zero) `reward_per_token` delta and divides again by the same constant `PRECISION_SCALING_FACTOR`, so a zero delta yields zero newly accrued rewards for every staker regardless of the pool's actual funding. [4](#0-3) 

`total_tokens_staked` is incremented without any upper bound in the public `stake` extrinsic, which any signed account can call with an arbitrary `amount` of the pool's staked asset. [5](#0-4)  Pool creation is likewise gated only by `T::CreatePoolOrigin`, which shipped runtime configurations set to `EnsureSigned<AccountId>` — confirmed in `asset-hub-rococo`, `asset-hub-westend`, `substrate/bin/node/runtime`, and `staking-async/runtimes/parachain`, all of which use `CreatePoolOrigin = EnsureSigned<AccountId>`. This directly contradicts the pallet's own doc comment that "pool creation and management [is] restricted to a configured Origin" for the *current* iteration — in these runtimes it is not restricted, it is fully permissionless. Consequently any unprivileged account can create a pool for any listed asset pair and stake an arbitrarily large amount, pushing `total_tokens_staked` past the point where the reward delta computation truncates to zero for all subsequent updates, even though reward tokens continue to sit unclaimably in `pool_info.account`.

## Impact Explanation
This breaks the pallet's core value-conservation invariant that stakers accrue rewards proportional to stake, and results in a permanent lock of reward-asset funds already transferred into the pool's dedicated account — funds that can no longer be distributed to any staker once the accumulator is mathematically dead. This matches the "permanent user-fund... lock" category of the Polkadot SDK impact gate, since no privileged action, governance decision, or off-chain assumption is needed to trigger it — it's an inherent arithmetic-precision defect in scoped pallet logic reachable through public extrinsics in shipped runtime configurations.

## Likelihood Explanation
No privileged actor is required: any signed account can call the public `create_pool` and `stake` extrinsics in runtimes where `CreatePoolOrigin = EnsureSigned<AccountId>` (confirmed for `asset-hub-rococo`, `asset-hub-westend`, `substrate/bin/node/runtime`, and `staking-async/runtimes/parachain`). Given `PRECISION_SCALING_FACTOR` is only `4096`, ordinary staking of an 18-decimal asset in realistic quantities (e.g., millions of tokens) combined with a modest `reward_rate_per_block` is sufficient to reach the zero-truncation threshold, making this reachable during normal, non-adversarial protocol usage, not merely as a griefing edge case.

## Recommendation
Increase `PRECISION_SCALING_FACTOR` to a much larger fixed-point base (e.g., `1_000_000_000_000_000_000` as a wide integer type), and/or perform the `reward_per_token` computation in a wider intermediate type (e.g., `U256`) before the final division, mirroring the `T::BalanceToU256`/`U256ToBalance` pattern used in `nomination-pools`'s `point_to_balance`. Additionally, consider emitting a defensive error or event when the computed reward delta is zero despite a non-zero elapsed reward budget so the condition is detectable rather than silently dropped, and/or bound `total_tokens_staked` relative to `reward_rate_per_block` at `create_pool`/`stake` time.

## Proof of Concept
1. `create_pool` with `staked_asset_id` = an 18-decimal asset, `reward_rate_per_block` = `1_000_000_000_000` (1e12), any `reward_asset_id`, using a runtime where `CreatePoolOrigin = EnsureSigned<AccountId>` (e.g., `asset-hub-rococo`).
2. Staker A calls `stake(pool_id, 1_000_000 * 10^18)` — `total_tokens_staked` becomes `1e24`.
3. After `14_400` blocks, `reward_per_token` numerator = `1e12 * 14_400 * 4096 ≈ 5.9e19`, and `5.9e19 / 1e24 = 0` due to integer-division truncation.
4. Any staker's harvest/claim path via `update_pool_and_staker_rewards` → `derive_rewards` yields `0` newly accrued rewards despite `reward_rate_per_block * 14_400` worth of reward tokens having been deposited into `pool_info.account` (e.g. via `deposit_reward_tokens`).
5. The deposited reward tokens remain permanently stuck in the pool account, unclaimable by any staker as long as `total_tokens_staked` stays large relative to `reward_rate_per_block`.

			Ok(())

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
