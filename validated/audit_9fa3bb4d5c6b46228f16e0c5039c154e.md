### Title
Missing pool-to-repository provenance check in `LinkRepositoryToObjectPool` allows cross-repository object access via alternates - (File: internal/gitaly/service/objectpool/link.go)

### Summary
The Beedle report's root cause is that `buyLoan()` lets a caller point `poolId` at *any* pool without checking that the pool's `loanToken`/`collateralToken` match the loan being bought, letting an attacker substitute a worthless "fake" pool for the real one. The structurally identical pattern exists in Gitaly's `ObjectPoolService.LinkRepositoryToObjectPool`: the RPC accepts an attacker/caller-supplied `ObjectPool` field and links it as a Git alternate to an attacker/caller-supplied `Repository`, but never verifies that the pool is actually the one that was created for/derived from that repository (e.g. via `CreateObjectPool`/`CreateFork`). The only checks performed are generic structural ones (does the path look like a repo, does it exist), not a provenance/relationship check between the two resources, mirroring the missing "token pair must match" check in the report.

### Finding Description
`LinkRepositoryToObjectPool` resolves the pool purely from the caller-supplied `req.GetObjectPool()` field via `poolForRequest` → `objectpool.FromProto`, and resolves the target repository purely from `req.GetRepository()`: [1](#0-0) 

`objectpool.FromProto` only validates that the pool path exists and is structurally a valid pool directory (either matches the pool-naming convention or lives under a temp dir) and is a valid git repository — it performs no check that this specific pool was ever associated with, forked from, or otherwise authorized for the `Repository` being linked: [2](#0-1) 

`Link()` itself only checks whether the repository already has an alternates file pointing somewhere else; if not, it unconditionally writes the given pool's object directory into the repository's `objects/info/alternates` file, at which point **all objects in the pool repository become directly readable from the target repository** via ordinary Git operations (fetch/clone/cat-file, etc.) against the target: [3](#0-2) 

Nowhere in this call chain (`link.go` service handler → `poolForRequest`/`FromProto` → `Link`) is there a check that the `ObjectPool` and `Repository` messages the caller supplied are actually related (e.g., that the pool was created from that repository's ancestry, or that the caller-authorized fork relationship exists). This is exactly analogous to Beedle's missing check that `loan.loanToken == pools[poolId].loanToken` before letting the caller substitute an arbitrary pool — here, nothing enforces that the supplied `ObjectPool` "belongs" to the supplied `Repository` before objects are shared via alternates.

By contrast, `FetchIntoObjectPool` at least enforces that origin and pool share the same storage (a much weaker check than provenance, but still a check that `LinkRepositoryToObjectPool` lacks entirely): [4](#0-3) 

and the test suite for `Link` only asserts against a repository *already* linked to a *different* pool (clobbering protection), never against linking to a pool that was never associated with that repository in the first place: [5](#0-4) 

### Impact Explanation
If a caller can invoke `LinkRepositoryToObjectPool` with arbitrary/crafted `ObjectPool` and `Repository` field values (e.g., a caller-controlled relative path for a pool it does not own, paired with a repository it does control), Gitaly will happily wire the target repository's alternates to that pool's object directory. Once linked, every object stored in the pool — potentially originating from a completely unrelated, private repository — becomes fetchable through the linked repository via standard Git protocols, constituting cross-repository object disclosure. This is the same class of impact as the report (an attacker substitutes an unrelated resource to walk away with value/data that should not be reachable through the path they used).

### Likelihood Explanation
Exploitation requires the ability to invoke `LinkRepositoryToObjectPool` with a `Repository`/`ObjectPool` pair that was not the pair established by the legitimate `CreateObjectPool`/`CreateFork` provenance flow. Gitaly's RPC layer performs storage/path-existence validation but no ownership/provenance validation, so the guardrail against this scenario, if it exists at all, lives entirely outside Gitaly (e.g., in GitLab Rails' authorization layer, which is expected to only ever request linking a fork to *its own* pool). Because Gitaly itself is the last line of defense for the on-disk alternates linkage and it performs no cross-check here, any caller path that can reach this RPC with attacker-influenced `ObjectPool`/`Repository` fields (misconfiguration, a compromised/bugged caller, or a future caller that doesn't enforce the pairing as strictly as Rails does today) results in exploitable cross-repository object exposure.

### Recommendation
Before performing the alternates link in `Link()`, verify that the supplied `ObjectPool` is actually the pool associated with the supplied `Repository`'s lineage — e.g., require that the pool's relative path matches a value previously recorded for that repository (such as via `FromRepo`'s reverse-lookup, which does correctly derive the pool from the repository's own alternates rather than trusting a caller-supplied pool) or that `CreateObjectPool`/`CreateFork` recorded an explicit origin↔pool relationship that `LinkRepositoryToObjectPool` can check against, and reject the request otherwise.

### Proof of Concept
1. Attacker-controlled or misbehaving caller invokes `CreateObjectPool` to create pool `P` from some repository they can read (or discovers an existing pool `P` belonging to a different, unrelated private repository whose relative path is guessable/known, e.g. via `internal/gitaly/storage/repository_path.go`'s `IsPoolRepository` naming convention).
2. Caller invokes `LinkRepositoryToObjectPool` with `ObjectPool = P` and `Repository = R`, where `R` is a repository the attacker controls and which has no legitimate relationship to `P`: [1](#0-0) 
3. `objectpool.FromProto` only checks that `P` structurally looks like a pool repository and exists — it never checks that `P` is `R`'s pool: [2](#0-1) 
4. `Link()` writes `P`'s object directory into `R`'s `objects/info/alternates`: [6](#0-5) 
5. Attacker performs an ordinary `git fetch`/`git clone`/`CommitService.TreeEntry` style call against `R` and can now read any object that resides in pool `P`, even though `R` was never legitimately associated with `P`.

func (s *server) LinkRepositoryToObjectPool(ctx context.Context, req *gitalypb.LinkRepositoryToObjectPoolRequest) (*gitalypb.LinkRepositoryToObjectPoolResponse, error) {
	repository := req.GetRepository()
	if err := s.locator.ValidateRepository(ctx, repository); err != nil {
		return nil, structerr.NewInvalidArgument("%w", err)
	}

	pool, err := s.poolForRequest(ctx, req)
	if err != nil {
		return nil, err
	}

	repo := s.localRepoFactory.Build(repository)

	if err := pool.Link(ctx, repo); err != nil {
		return nil, structerr.NewInternal("%w", err)
	}

	return &gitalypb.LinkRepositoryToObjectPoolResponse{}, nil

// FromProto returns an object pool object from its Protobuf representation. This function verifies
// that the object pool exists and is a valid pool repository.
func FromProto(
	ctx context.Context,
	logger log.Logger,
	locator storage.Locator,
	gitCmdFactory gitcmd.CommandFactory,
	catfileCache catfile.Cache,
	txManager transaction.Manager,
	housekeepingManager housekeepingmgr.Manager,
	proto *gitalypb.ObjectPool,
) (*ObjectPool, error) {
	poolPath, err := locator.GetRepoPath(ctx, proto.GetRepository(), storage.WithRepositoryVerificationSkipped())
	if err != nil {
		return nil, err
	}

	if !storage.IsPoolRepository(proto.GetRepository()) {
		// When creating repositories in the ObjectPool service we will first create the
		// repository in a temporary directory. So we need to check whether the path we see
		// here is in such a temporary directory and let it pass.
		tempDir, err := locator.TempDir(proto.GetRepository().GetStorageName())
		if err != nil {
			return nil, fmt.Errorf("getting temporary storage directory: %w", err)
		}

		if !strings.HasPrefix(poolPath, tempDir) {
			return nil, ErrInvalidPoolDir
		}
	}

	pool := &ObjectPool{
		Repo:                localrepo.New(logger, locator, gitCmdFactory, catfileCache, proto.GetRepository()),
		logger:              logger,
		locator:             locator,
		gitCmdFactory:       gitCmdFactory,
		txManager:           txManager,
		housekeepingManager: housekeepingManager,
	}

	if !pool.IsValid(ctx) {
		return nil, ErrInvalidPoolRepository
	}

	return pool, nil
}

// Link will link the given repository to the object pool. This is done by writing the object pool's
// path relative to the repository into the repository's "alternates" file. This does not trigger
// deduplication, which is the responsibility of the caller.
func Link(ctx context.Context, pool, repo *localrepo.Repo, txManager transaction.Manager) (returnedErr error) {
	altPath, err := repo.InfoAlternatesPath(ctx)
	if err != nil {
		return err
	}

	expectedRelPath, err := getRelativeObjectPath(ctx, pool, repo)
	if err != nil {
		return err
	}

	linked, err := linkedToRepository(ctx, pool, repo)
	if err != nil {
		return err
	}

	if linked {
		// When the repository is already linked to the repository, cast a vote to ensure the
		// repository is consistent with the other replicas.
		if err := transaction.VoteOnContext(ctx, txManager, voting.VoteFromData([]byte("repository linked")), voting.Synchronized); err != nil {
			return fmt.Errorf("vote on linked repository: %w", err)
		}

		return nil
	}

func validateFetchIntoObjectPoolRequest(req *gitalypb.FetchIntoObjectPoolRequest) error {
	if req.GetOrigin() == nil {
		return errors.New("origin is empty")
	}

	if req.GetObjectPool() == nil {
		return errors.New("object pool is empty")
	}

	originRepository, poolRepository := req.GetOrigin(), req.GetObjectPool().GetRepository()

	if originRepository.GetStorageName() != poolRepository.GetStorageName() {
		return errors.New("origin has different storage than object pool")
	}

	return nil
}
